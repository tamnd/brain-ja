 ## 解決策
 ## 問題の理解

 各飛行機は、到着時刻から出発時刻までの連続した時間間隔の間、ゲートを占有します。 空港に存在している間は 1 つのゲートをブロックするため、重複する間隔はゲートの同時使用に対応します。 

特定のクエリ間隔に対して$[l, r]$、この時間枠内で関連する飛行機のみを考慮するように求められます。 飛行機が空港に存在することがクエリ間隔と重なって、その飛行機がその時間内のある時点で「アクティブ」になっている場合、その飛行機はクエリ中の混雑に寄与します。境界には特別なルールがあり、飛行機は正確に出発します。$l$または$r$は除外されますが、正確に到着する飛行機は$l$または$r$が含まれています。 

各クエリのタスクは、間隔内の任意の瞬間に同時に存在する平面の最大数を決定することです。$[l, r]$なぜなら、その最大値は競合を避けるために必要なゲートの最小数に等しいからです。 

制約$N \le 10^5$すべてのプレーンをスキャンしてクエリごとにオーバーラップを再計算するソリューションは直ちに除外されます。 平$Q \le 50$二次方程式を保存しない、または$N \log N$クエリごとのアプローチなので、$50 \cdot 10^5$依然として、クエリ ロジックごとに最大でも線形または線形に近いものしか許可されません。 

微妙なエッジケースは境界ルールから生じます。 飛行機がちょうど次の時間に出発した場合$l$のような単純な重複チェックであっても、それはカウントされません。$a_i \le r$そして$d_i \ge l$間違って含めてしまいます。 

たとえば、飛行機に間隔がある場合、$[5, 10]$そしてクエリは$[10, 12]$、単純な交差点チェックでは 10 でアクティブとして扱われますが、ステートメントでは境界での出発が除外されているため、まったく寄与しないはずです。 

もう 1 つのエッジ ケースは、多数の到着時に正確に開始または終了するクエリです。 境界への到着がカウントされるため、正確に開始される間隔は$l$アクティブ セットに引き続き含まれている必要があります。 

## アプローチ

 各クエリに答える直接的な方法は、時間をシミュレートすることです。 各クエリについて、すべてのプレーンを反復処理し、その間隔が境界ルールに基づいてクエリ間隔と重複するかどうかを確認し、関連するすべての時間にわたる重複の最大数を計算できます。 

これは正しいですが、高価です。 クエリごとに検査する可能性があります$10^5$間隔を設定し、時間にわたる重複を判断して、おおよその結果を導き出します。$O(NQ)$フィルタリングするだけで、時間を継続的にスキャンしようとするとさらに悪くなります。 隠れたコストは、最大の重複を検出するには、イベントの順序付けまたは時間をかけてスイープする推論が必要になり、単純なクエリごとのシミュレーションが遅すぎることです。 

重要な点は、各クエリが固定ウィンドウ内のアクティブな間隔の最大数のみを考慮していることです。 これは古典的な変換です。連続時間で考える代わりに、各飛行機を 2 つのイベント (到着イベントと出発イベント) に変換し、ソートされたイベント時間のプレフィックス カウントに問題を縮小します。 

イベントがソートされると、各イベント境界でアクティブなプレーンの数を表すプレフィックス合計配列を構築できます。 次に、クエリはイベント インデックスの制限された範囲にわたって最大プレフィックス合計値を見つけることに帰着します。 これは静的配列に対する範囲最大クエリであり、スパース テーブルまたはセグメント ツリーで答えることができます。 

なぜなら$Q \le 50$、前処理をグローバルに一度行う余裕があり、その後、ソートされたイベント リストのインデックスに時間境界をマッピングし、範囲最大クエリを取得することで各クエリに応答します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(NQ)$に$O(N^2)$方法に応じて |$O(1)$に$O(N)$| 遅すぎる |
 | スイープ + RMQ |$O(N \log N + Q \log N)$|$O(N \log N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 各間隔を 2 つのイベントに変換しますが、境界ルールを注意深く尊重する必要があります。 

1. 各飛行機を到着時の +1 イベントとして表現します$a_i$および出発時の -1 イベント$d_i$。 並べ替えで順序を正しく処理することで、到着は包括的、出発は排他的として扱います。 これにより、正確な境界時間での正確なカウントが保証されます。 
2. すべてのイベントを時間順に並べ替えます。2 つのイベントが同じ時間を共有する場合は、出発イベントの前に到着イベントを処理します。 この順序は、境界への到着はカウントされるが、出発はカウントされないというルールをエンコードしています。 
3. ソートされたイベントをスイープし、そのイベントの処理後に各位置にアクティブなプレーンの数が格納されるプレフィックス合計配列を計算します。 これにより、時間の経過に伴う区分的定数関数が得られます。 
4. 個別のイベント時間ごとに、対応するプレフィックス合計値を保存します。 これにより、タイムラインは最大で次のサイズに圧縮されます。$2N$ポイント。 
5. 任意の連続セグメントにわたるアクティブなプレーンの最大数を効率的にクエリできるように、このプレフィックス合計配列に範囲最大構造を構築します。 
6. 各クエリについて$[l, r]$、時間が次の最初のイベント インデックスを見つけます。$\ge l$および時刻が次の最後のイベント インデックス$\le r$。 これらは、クエリ ウィンドウと交差するタイムラインのセグメントを定義します。 
7. 範囲最大構造を使用して、このセグメントにわたる最大プレフィックス合計を計算します。これにより、クエリの答えが得られます。 

なぜそれが機能するのかは、スイープ ラインの構造にあります。 連続するイベント時間の間では、アクティブなプレーンの数は変化しないため、クエリ間隔内の最大値は、間隔内のイベント境界で発生する必要があります。 イベントをソートした後のプレフィックスの合計は、そのような各境界におけるアクティブなプレーンの数を正確に表すため、制限された範囲の最大値を取ることで、内部のピーク輻輳を正確に把握できます。$[l, r]$。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SparseTable:
    def __init__(self, arr):
        n = len(arr)
        self.n = n
        self.log = [0] * (n + 1)
        for i in range(2, n + 1):
            self.log[i] = self.log[i // 2] + 1

        k = self.log[n] + 1
        self.st = [[0] * n for _ in range(k)]
        self.st[0] = arr[:]

        j = 1
        while (1 << j) <= n:
            i = 0
            while i + (1 << j) <= n:
                self.st[j][i] = max(self.st[j - 1][i],
                                     self.st[j - 1][i + (1 << (j - 1))])
                i += 1
            j += 1

    def query(self, l, r):
        j = self.log[r - l + 1]
        return max(self.st[j][l], self.st[j][r - (1 << j) + 1])

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    d = list(map(int, input().split()))

    events = []
    for i in range(n):
        events.append((a[i], 1))
        events.append((d[i], -1))

    events.sort(key=lambda x: (x[0], -x[1]))

    times = []
    active = []
    cur = 0

    for t, v in events:
        cur += v
        times.append(t)
        active.append(cur)

    st = SparseTable(active)

    def lower_bound(x):
        lo, hi = 0, len(times)
        while lo < hi:
            mid = (lo + hi) // 2
            if times[mid] >= x:
                hi = mid
            else:
                lo = mid + 1
        return lo

    def upper_bound(x):
        lo, hi = 0, len(times)
        while lo < hi:
            mid = (lo + hi) // 2
            if times[mid] > x:
                hi = mid
            else:
                lo = mid + 1
        return lo - 1

    out = []
    for _ in range(q):
        l, r = map(int, input().split())
        L = lower_bound(l)
        R = upper_bound(r)
        if L > R:
            out.append("0")
        else:
            out.append(str(st.query(L, R)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```イベントの並べ替えステップでは、境界の正確性が強制されます。 時間順に並べ替え、出発前に到着を配置することで、時間どおりに到着できるようにします$t$、同じタイムスタンプで削除される前に、到着が含まれます。 

プレフィックスの累積により、各イベント後にアクティブなプレーンの正確な数が構築されるため、各インデックスは安定した状態に対応します。 スパース テーブルにより、任意のセグメントに対して一定時間の最大クエリが可能になります。 

バイナリ検索では、クエリ間隔と交差するイベント タイムラインの部分を正確に分離し、クエリ間隔内で発生する状態のみを考慮します。$[l, r]$。

 ### 例 1

 入力:```
N = 5, Q = 2
a = [2, 7, 4, 5, 9]

[1, 10]
[8, 14]
```並べ替え後のイベント:```

```プレフィックスのアクティブ数:

 | イベントインデックス | 時間 | 変更 | アクティブ |

 | 2 | 5 | +1 | 3 |
 | 3 | 7 | +1 | 4 |
 | 4 | 8 | -1 | 3 |
 | 5 | 8 | -1 | 2 |

クエリ$[8, 14]$8 ～ 11 付近のインデックスを選択し、最大アクティブ = 3 を与えます。 

これにより、アルゴリズムがグローバルではなく、制限されたウィンドウ内でピークのオーバーラップを正しくキャプチャしていることが確認されます。 

### 例 2

 入力:```
N = 3, Q = 1
a = [1, 3, 5]
d = [4, 6, 8]
query: [4, 4]
```時間 4 では、2 番目の飛行機は 6 時に出発するためまだアクティブですが、最初の飛行機はちょうど 4 時に出発し、境界ルールによって除外されます。 

クエリ時のアクティブなプレーン = 1。 

イベント表現により、4 時の到着が 4 時の出発前に含まれることが保証されるため、プレフィックスの状態は単一のアクティブな間隔を正確に反映します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(N \log N + Q \log N)$| イベントのソートと RMQ の構築、さらにクエリごとのバイナリ検索 |
 | スペース |$O(N \log N)$| 最大でもスパーステーブル以上$2N$イベントの状態 |

 制約により、最大で次のことが許可されます。$10^5$平面なので、前処理$N \log N$は十分に高速であり、各クエリは事実上一定時間または対数時間になります。 わずか 50 個のクエリで、ソリューションは問題なく制限内に収まります。

 ## 特殊なケース

 重要なエッジ ケースは、飛行機がクエリ境界から正確に出発する場合です。 入力の場合:```
a = [1], d = [5], query = [5, 5]
```解釈によっては 5 までは平面が存在するため、正しい出力は 1 になります。 指定されたルールでは、5 時の出発は除外されるため、飛行機は 5 には寄与しません。スイープ ラインの順序付けにより、到着を考慮した後、時刻 5 の -1 イベントが確実に適用され、誤った包含が防止されます。 

複数のイベントが同じタイムスタンプを共有する場合、別のエッジ ケースが発生します。 例えば：```
a = [5, 5], d = [10, 10], query = [5, 5]
```両方の飛行機が 5 で到着するため、両方をカウントする必要があり、結果は 2 になります。出発前に到着を並べ替えると、その時点で減算される前にプレフィックスが 2 に達することが保証されます。
