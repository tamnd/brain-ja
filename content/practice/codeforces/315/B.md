 ## 解決策
 ## 問題の理解

 整数の配列と一連の演算があります。 

1 回の操作で 1 つの位置が新しい値に変更されます。 別の操作では、配列内のすべての要素に同じ数値が追加されます。 3 番目の操作では、特定の位置の現在値を要求します。 

課題はグローバルな加算操作から生じます。 直接実装すると、すべてが更新されます`n`このような操作が現れるたびに要素が追加されます。 両方とも`n`そして操作の数`m`到達`100000`、そのアプローチはコストがかかりすぎます。 

入力は最初に初期配列を提供します。 次に、それは提供します`m`操作。 すべてのクエリ操作では、その前に行われたすべての更新を考慮した後、要求されたインデックスに現在格納されている値を出力する必要があります。 

この制約は、すべての操作を定数時間または対数時間で処理する必要があることを強く示唆しています。 グローバル追加中に配列全体に影響を与えるソリューションには、次のものが必要になります。$$100000 \times 100000 = 10^{10}$$最悪の場合、要素は更新されますが、これは 1 秒で実行できる速度をはるかに超えています。 

いくつかの微妙な状況により、不注意な実装が壊れる可能性があります。 

考慮する：```
3 3
1 2 3
2 5
1 1 10
3 1
```すべての要素に 5 を加算すると、論理配列は次のようになります。```
6 7 8
```次に、位置 1 に値 10 が割り当てられます。 

答えは次のとおりです。```
10
```よくある間違いは、古い値と累積された追加値を物理的に保存し、クエリ中にグローバル増分を再度追加して、10 ではなく 15 を生成することです。 

もう 1 つの注意が必要なケースは、複数のグローバル追加です。```
2 4
1 1
2 3
2 4
3 1
```正しい答えは次のとおりです。```
8
```2 つの加算が累積されます。 最新の追加のみを記憶するソリューションは、代わりに 5 を返します。 

もう 1 つの重要なシナリオは、数回の追加後に割り当てを行い、さらに追加を適用することです。```
1 4
10
2 5
1 1 7
2 2
3 1
```配列は次のように進化します。```
10
15
7
9
```正しい出力は次のとおりです。```
9
```この割り当てにより、以前の追加に関係なく、その時点で要素が正確に 7 にリセットされます。 

## アプローチ

 最も直接的な解決策は、実際の配列値を常に維持することです。 

タイプ 1 操作の場合、1 つの要素を更新します。 

タイプ 2 の操作の場合、配列全体を反復処理し、要求された値をすべての位置に追加します。 

タイプ 3 の操作の場合、要求された要素を出力します。 

格納された配列は常に実際の配列と一致するため、この方法は簡単に推論できます。 残念ながら、グローバルに追加するたびにコストがかかります`O(n)`。 もしすべてなら`m`操作がタイプ 2 の場合、全体の複雑さは次のようになります。`O(nm)`、到達できる`10^10`更新情報。 

重要な観察は、すべてのグローバル追加がすべての要素に等しく影響を与えるということです。 

配列全体をすぐに変更する代わりに、単一の変数を保持することができます。`add`これまでに各要素に追加された合計量を表します。 

仮定する`add = 17`。 この場合、要素の実際の値は次のようになります。```
stored_value + 17
```クエリが簡単になります。 保存されている値に加えて単純に返します。`add`。 

唯一の課題は割り当て操作です。 

実行すると:```
a[v] = x
```その間`add = 17`、将来のクエリが正確に返される必要があります`x`その瞬間。 

クエリは常に追加するため、`add`後で戻って、次のものを保存します。```
a[v] = x - add
```それから：```
stored + add = (x - add) + add = x
```それはまさに私たちが望んでいることです。 

これにより、すべての操作が一定時間になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | O(n) | 遅すぎる |
 | 最適 | O(n + m) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 初期配列を読み取ります。 
2. 変数を作成する`add = 0`。 

この変数には、これまでに処理されたすべてのタイプ 2 操作によってグローバルに追加された合計値が格納されます。 
3. タイプ 1 の操作の場合`(v, x)`、 店：```
a[v] = x - add
```保存された値は、現在のグローバル オフセットを加算し戻した後、論理値が正確になるように調整されます。`x`。 
4. タイプ 2 の操作の場合`(y)`、 アップデート：```
add += y
```配列要素には触れません。 
5. タイプ 3 の操作の場合`(q)`、出力:```
a[q] + add
```保存された値に累積されたオフセットを加えた値は、現在の論理値と等しくなります。 
6. すべての操作が処理されるまで続行します。 

### なぜ効果があるのか

 中心的な不変式は次のとおりです。```
real_value(i) = stored_value(i) + add
```最初は`add = 0`, したがって、不変式は true です。 

グローバルな追加が発生すると、`add`。 すべての要素の実数値は同じ量だけ増加するため、不変式は有効なままです。 

代入によって要素が次のように設定されるとき`x`、私たちは保管します`x - add`。 実際の値は次のようになります。```
(x - add) + add = x
```したがって、割り当てられた位置はすぐに正しい値を取得しますが、他のすべての位置は変更されません。 

すべての操作で不変条件が維持されるため、すべてのクエリは正しい現在値を返します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
a = list(map(int, input().split()))

add = 0
ans = []

for _ in range(m):
    op = list(map(int, input().split()))

    if op[0] == 1:
        v, x = op[1], op[2]
        a[v - 1] = x - add

    elif op[0] == 2:
        y = op[1]
        add += y

    else:
        q = op[1]
        ans.append(str(a[q - 1] + add))

sys.stdout.write("\n".join(ans))
```配列`a`実際の値は保存されません。 代わりに、現在のグローバル オフセットに相対的な値を保存します。 

変数`add`タイプ 2 のすべての操作を累積します。 これは、ソリューションの怠惰な部分です。 すべての位置を更新するのではなく、すべての要素にどれだけ追加する必要があるかを覚えています。 

割り当てには特別な注意が必要です。 単純に保管した場合`x`、後のクエリで追加される`add`再度実行すると、間違った結果が生成されます。 保管する`x - add`電流オフセットを補償します。 

配列では 0 から始まるインデックスが使用されますが、入力では 1 から始まるインデックスが使用されます。 すべての位置アクセスでは 1 を減算する必要があります。 この変換が行われないことは、最も一般的な実装エラーです。 

Python の整数は 32 ビットを超える値を自動的に処理するため、多くの加算を行った後でもオーバーフローの心配は発生しません。
