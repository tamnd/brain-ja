 ## 解決策
 ## 問題の理解

 プレイリストは、繰り返される曲のブロックから構築されます。 歌`i`期間があります`t[i]`そしてユージェニーはそれを聞きます`c[i]`次の曲に移動する前に、連続して 2 回繰り返します。 

曲が 4 分間続き、3 回繰り返される場合、そのブロックはプレイリストのタイムラインに 12 分を占めます。 クエリでは次のような質問が行われます。 

「プレイリストの先頭から 57 分の間に、どの曲が流れていましたか?」

 重要な詳細は、再生されていた曲の繰り返しではなく、曲のインデックス自体のみが尋ねられることです。 

プレイリストには最大で次のものを含めることができます`10^5`ソングブロックと`10^5`クエリ。 分ごとの直接シミュレーションは不可能です。`c[i] * t[i]`非常に大きくなる可能性があります。 プレイリストの合計時間は次のとおりです`10^9`つまり、すべての分の明示的な配列を構築するには、数十億の要素が必要になります。 

と`10^5`クエリが 2 秒以内に制限されている場合は、何らかの問題が発生することを期待する必要があります。`O(n log n)`または`O(n + m)`快適に通過するために。 すべてのクエリに対してプレイリスト全体をスキャンするソリューションでは、速度が非常に遅くなります。 

微妙な点の 1 つは、クエリは時間に関して 1 からインデックス付けされることです。 1 曲が数分かかる場合`[1, 16]`、次にクエリ`16`クエリはまだその曲に属していますが、`17`次のものに属します。 ここではオフバイワンの間違いが非常によくあります。 

次の例を考えてみましょう。```
2 3
1 3
1 2
1 3 4
```プレイリストのタイムラインは次のとおりです。```
minutes 1..3 -> song 1
minutes 4..5 -> song 2
```正しい出力:```
1
1
2
```strict を使用した不注意な実装`<`の代わりに`<=`二分探索中に分が誤ってマッピングされる`3`歌に`2`。 

1 つのソング ブロックが非常に大きい場合には、別の注意が必要なケースが発生します。```
1 3
1000000000 1
1 500000000 1000000000
```すべてのクエリは依然として曲を返す必要があります`1`。 これにより、プレイリストを分ごとに拡張するアプローチは排除されます。 

最後の詳細は、クエリはすでにソートされつつあるということです。 一部のソリューションでは 2 つのポインターを使用してこれを利用していますが、プレフィックス合計の二分検索も十分に高速で、推論が簡単です。 

## アプローチ

 ブルートフォースのアイデアは単純です。 完全なプレイリストのタイムラインを分ごとに生成し、毎分再生される曲を保存できます。 

例えば：```
song 1: duration 2, repeats 3 times
```貢献するだろう：```
[1, 1, 1, 1, 1, 1]
```この曲は合計 6 分を占めるためです。 

その後、すべてのクエリは直接検索になります。 

すべての分が明示的に表現されるため、これは論理的に機能します。 問題はサイズです。 合計持続時間は次のとおりです`10^9`したがって、この配列には 10 億のエントリが含まれる可能性があります。 メモリも実行時間も不可能になります。 

次の改善点は、各曲がグローバル タイムライン上で 1 つの連続した間隔を占めていることを観察することです。 

累積期間を計算するとします。```
song 1 ends at minute 10
song 2 ends at minute 25
song 3 ends at minute 40
```今度はクエリです`x`単に次のように尋ねます。 

「終了時間が少なくとも最初の曲は何ですか？」`x`？」

 それはまさに二分探索問題です。 

すべての曲に正の継続時間が追加されるため、累積終了時間は自然にソートされます。 各クエリについて、最初のプレフィックスの合計をバイナリ検索します。`>= x`。 

これにより作業が大幅に軽減されます。 

分を個別にスキャンするのではなく、曲ブロックごとに 1 つの数字だけを保存します。 

すべてのクエリを線形に検索する代わりに、二分検索を使用します。`O(log n)`時間。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(合計継続時間 + m) | O(合計期間) | 遅すぎる |
 | 最適 | O(n + m log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ソングブロック数を読み取る`n`そしてクエリの数`m`。 
2. プレフィックス合計の配列を構築します。 

各ソング ブロックについて、次を計算します。```
block_duration = c[i] * t[i]
```次に、これまでの累積合計期間を追加します。 

プレフィックスの合計が次のようになる場合:```
[10, 25, 40]
```それは次のことを意味します:

 曲 1 は分を占めます`1..10`曲 2 は分を占めます`11..25`曲 3 は分を占めます`26..40`3. クエリを 1 分ごとに読み取ります`x`。 
4. プレフィックス合計配列を二分探索して、次の値以上の最初の値を探します。`x`。 

これにより、分を含むソングブロックが得られます`x`。 
5. 曲インデックスを 1 から始まるインデックスとして出力します。 

### なぜ効果があるのか

 プレフィックス合計配列には、各曲ブロックの終了分が格納されます。 すべてのブロック期間は正であるため、これらの終了時間は厳密に増加しています。 

任意のクエリ分に対して`x`、正しい曲は、終了時間が少なくとも次の最初のブロックです。`x`。 

以前のプレフィックスの合計が以下の場合`x`、その後、それまでの曲はすべて 1 分前に終了しました`x`。 現在のプレフィックス合計が少なくとも`x`の場合、現在の曲はすでに開始されており、まだ終了していません。 

二分探索ではこの境界が正確に検出されるため、アルゴリズムは常に正しい曲を返します。 

## Python ソリューション```python
import sys
from bisect import bisect_left

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())

    prefix = []
    total = 0

    for _ in range(n):
        c, t = map(int, input().split())
        total += c * t
        prefix.append(total)

    queries = list(map(int, input().split()))

    ans = []

    for x in queries:
        idx = bisect_left(prefix, x)
        ans.append(str(idx + 1))

    sys.stdout.write("\n".join(ans))

solve()
```ソリューションの中核となるのは、`prefix`配列。 各エントリには、その曲ブロックが占めていた最後の分が保存されます。 

たとえば、次のような場合です。```
prefix = [6, 15, 21]
```それから：```
song 1 -> minutes 1..6
song 2 -> minutes 7..15
song 3 -> minutes 16..21
```

`bisect_left(prefix, x)`少なくとも次の値を持つ最初のインデックスを返します。`x`。 まさにその分が入った曲です`x`。 

の`+1`Python リストは 0 から始まるインデックスを使用するのに対し、曲番号は 1 から始まるため、これが必要です。 

よくある間違いは、`bisect_right`。 これは、曲がちょうど次の時間に終了する境界分では失敗します。`x`。 

もう 1 つの簡単な間違いは、タイムラインが分から始まることを忘れることです。`1`、分ではありません`0`。 累積終了時間を使用すると、この問題は自然に回避されます。 

ここでは、Python の整数は可能な最大合計を安全に処理できるため、特別なオーバーフロー処理は必要ありません。

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io
from bisect import bisect_left

def solve():
    input = sys.stdin.readline

    n, m = map(int, input().split())

    prefix = []
    total = 0

    for _ in range(n):
        c, t = map(int, input().split())
        total += c * t
        prefix.append(total)

    queries = list(map(int, input().split()))

    ans = []

    for x in queries:
        ans.append(str(bisect_left(prefix, x) + 1))

    sys.stdout.write("\n".join(ans))

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    output = sys.stdout.getvalue()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return output

# provided sample
assert run(
    "1 2\n"
    "2 8\n"
    "1 16\n"
) == "1\n1"

# minimum-size input
assert run(
    "1 1\n"
    "1 1\n"
    "1\n"
) == "1"

# boundary transition between songs
assert run(
    "2 4\n"
    "1 3\n"
    "1 2\n"
    "1 3 4 5\n"
) == "1\n1\n2\n2"

# all queries inside same large block
assert run(
    "1 3\n"
    "1000000000 1\n"
    "1 500000000 1000000000\n"
) == "1\n1\n1"

# mixed intervals
assert run(
    "3 5\n"
    "1 2\n"
    "2 3\n"
    "1 4\n"
    "1 2 5 8 12\n"
) == "1\n1\n2\n2\n3"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 つのクエリで 1 つの曲 |`1`| 有効な最小入力値 |
 | 正確に曲の境界でクエリを実行する | 正しい遷移 | オフバイワンの正確性 |
 | 巨大な繰り返しブロック | 全て`1`| 分ごとの拡張はありません |
 | 混合間隔 |`1 1 2 2 3`| 一般的な正しさ |
