 ## 解決策
 ## 問題の理解

 商人がキャビアとハチミツの 2 種類の商品を運んで川沿いを移動します。 最初は固定量の各商品を所有しており、後で各ユニットを既知の価格で販売できます。 通行料金に使用されないものはすべて売却できるため、彼の最終的な利益は、市の市場まで各商品がどれだけ生き残るかによって決まります。 

途中、税関を通過しなければなりません。 この検問所では通行料の支払いを強いられるが、支払い方法には柔軟性がある。 彼は固定金額を支払うことも、支払いをいくらかの量のキャビアまたはいくらかの蜂蜜で置き換えることもできます。 各オプションは同じ料金を完全に置き換えますが、消費するリソースは異なります。 

目標は、残りの商品を販売し、通行料金で支払った現金を考慮した後の最終的な金銭的利益を最大化する支払い方法を選択することです。 

重要な構造は、決定点は 1 つだけ、つまり 1 つの料金の支払い方法だけであるということです。 その後、残りの商品は固定価格で独立して販売されるため、すべてが直線的になります。 

制約には商品の数量に関する非常に大きな値 (最大数千万) が含まれていますが、評価する意味のある戦略は一定数しかないため、ソリューションでは数量に関するシミュレーションを回避する必要があります。 

よくある間違いは、当面の通行料金を常に最小化する必要があると考えることです。 これは、商品の支払いによって、目先の価値だけでなく、将来の販売利益が失われるため、失敗します。 

たとえば、キャビアが蜂蜜に比べて非常に価値がある場合、キャビアで支払うと、たとえ現金の支出を避けたとしても、収入の損失という点ではるかに高価になる可能性があります。 

もう 1 つの微妙なエッジケースは、支払い方法の実現可能性です。 販売者が十分なキャビアまたは蜂蜜を持っていない場合、それらのオプションは、価値の点で最適であるように見えても無効です。 

## アプローチ

 強引な考え方では、さまざまな量の物品と現金を使用して料金を支払うという考えられるすべての組み合わせを検討することになります。 ただし、この問題では部分的な支払いは認められておらず、料金は 3 つの個別の形式で固定されています。 これにより、決定空間が最大 3 つの候補戦略に分割されます。 

正しい洞察は、最適化全体が負担のかかるローカルなものであるということです。 通行料の前後のすべては残りのリソースにおいて線形であるため、通行料の影響は固定の初期値からの 1 回の減算だけです。 これにより、適用後の最終利益を計算することで、各支払いオプションを個別に評価することができます。 

オプションごとに、残りのキャビアと蜂蜜を計算し、指定された価格を使用してそれらをお金に換算し、該当する場合は支払われた現金を差し引きます。 有効な選択肢の中で最良の結果が答えになります。

 ## アルゴリズムのチュートリアル

 考えられる 3 つの料金支払い方法を直接評価して結果を計算します。

1. 料金を現金で支払わない場合のベースライン利益を計算することから始めます。合計値は i・a + m・b です。 これは、制約が適用される前の理論上の最大収益を表します。 
2. 通行料金 v を現金で支払うことを検討します。この場合、チェックポイントでは商品が消費されないため、残りの価値は i・a + m・b − v となります。 
3. cグラムのキャビアを使って通行料を支払うことを検討してください。 このオプションは、i ≥ c の場合にのみ有効です。 有効であれば、残りの財は(i − c, m)であるため、利益は(i − c)・a + m・bとなります。 これは、取り出されたキャビアの将来の販売価値の損失をモデル化します。 
4. dグラムのハチミツを使って通行料を支払うことを検討してください。 このオプションは、m ≥ d の場合にのみ有効です。 有効であれば、残りの財は (i, m − d) となるため、利益は i・a + (m − d)・b となります。 
5. すべての有効なオプションの最大値を取得します。 

なぜ効果があるのか

 各支払いオプションは、残りのリソースの個別の最終状態に対応します。 チェックポイントの後、収益は残りの商品の線形評価によって完全に決定されます。 キャビアと蜂蜜の間には、通行料の 1 回の減算を超える相互作用はないため、最適な戦略はこれら 3 つのエンドポイントのいずれかでなければなりません。 仮説的な混合戦略は、3 つの個別の遷移から 1 つの選択を強制するという、料金の固定形式の性質に矛盾します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    i, m, a, b, v, c, d = map(int, input().split())

    base = i * a + m * b
    ans = base - v  # pay money

    if i >= c:
        ans = max(ans, (i - c) * a + m * b)

    if m >= d:
        ans = max(ans, i * a + (m - d) * b)

    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、まず商品の全額の価値が控除なしで計算されます。 これは、他のすべての結果の参照点として機能します。 現金支払いの場合は、v を直接減算することで処理されます。 

次に、各商品ベースの支払いの実現可能性を確認します。 各チェックでは、単に十分な在庫が存在することを確認し、対応する数量を削除した後に結果の値を再計算します。 控除が 1 つだけ発生するため、シミュレーションは必要ありません。 

比較は段階的に行われるため、常に最良の達成可能な結果が維持されます。 

## 実用的な例

| オプション | 残り (i, m) | 値の計算 | 結果 |

 | 現金 | (5,10) | 5・2 + 10・3 − 7 | 33 |

 | ハニー | (5, 7) | 5・2 + 7・3 | 31 |

 最高はキャビアで支払うことで、34が得られます。 

これは、商品の川下での価値がより高いため、たとえ流動性が保たれたとしても、現金支払いを回避することが最適である可能性があることを示しています。 

### 例 2

 入力: i = 5、m = 10、a = 1、b = 3、v = 10、c = 6、d = 3

 | オプション | 残り (i, m) | 値の計算 | 結果 |

これは、実現可能性チェックの重要性を示しています。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    def solve():

        base = i * a + m * b
        ans = base - v

        if i >= c:
            ans = max(ans, (i - c) * a + m * b)

            ans = max(ans, i * a + (m - d) * b)

        print(ans)

    solve()
    return sys.stdout.getvalue().strip()

assert run("5 10 2 3 7 3 3\n") == "34"

# cash dominates scenario
assert run("1 1 100 100 1 0 0\n") == "199"

# forced goods payment due to large v

assert run("10 0 5 1 0 10 1\n") == "0"

# boundary: exactly enough honey
assert run("0 10 1 5 0 1 10\n") == "0"

 ## 特殊なケース

 エッジケースの 1 つは、現金での支払いが商品の損失を避けるため魅力的に見えるものの、実際には商品を販売するよりも最終利益が減少する場合です。 たとえば、キャビア控除が少額であっても、金額が大きければ現金で支払うよりも価値がある可能性があります。 

もう 1 つのケースは、物品ベースの支払いがぎりぎり実現可能な場合です。 i が c に正確に等しい場合、残りのキャビアはゼロになり、価値が大幅に変化する可能性があります。 アルゴリズムは、縮小状態を計算する前に i ≥ c をチェックするため、これを処理します。 

3 番目のケースは、両方の商品の支払いが無効な場合です。 この状況では、現金支払いのみが残り、アルゴリズムは無効な状態を比較することなく、正しく基数 − v に戻ります。
