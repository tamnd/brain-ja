 ## 解決策
 ## 問題の理解

 いくつかの位置がすでに固定されているバイナリ文字列が与えられます。`0`または`1`、残りのポジションは自由です。 タスクは、最終的な文字列が次の意味で「爆発的」になるように、すべての空き位置を置き換えることです。隣接する等しい文字のペアを削除し、反対の値の単一の文字に置き換えるルールを繰り返し適用すると、プロセスは最終的に単一の文字に崩壊します。 

同様に、文字列が 1 文字だけ残るまでその操作を使用して完全に削減できる場合、その文字列は有効です。 私たちに与えられた自由は、未知の位置の値を選択することです。 この方法で文字列を削減可能にする補完が存在するかどうかを判断する必要があります。 

重要な隠された構造は、操作がローカルの隣接関係にのみ依存するが、その効果はパリティのような動作を通じてグローバルに伝播するということです。 リダクションを直接シミュレートする単純な試みでは、部分文字列のマージと再拡張が繰り返し行われるため、大きな制約に達するまでの長さでは 2 次またはさらに悪化することになります。 

文字列に固定文字のみが含まれており、柔軟性がない場合、微妙な失敗のケースが発生します。 たとえば、文字列がすでに`01`、「ほぼ有効」に見えても、演算は適用されず、還元できません。 別のケースは次のような文字列です`000`すぐに減りますが、`001`両方にゼロの大部分が含まれている場合でも、そうではありません。 削減は数ではなく構造に依存します。 

重要な制約の意味は、操作をシミュレートできないことです。 スタックを使用した貪欲な削減であっても、繰り返しのカスケード変更に退化する可能性があります。 意図したソリューションでは、線形時間でチェックできる小さな不変量を使用して、還元可能性を特徴付ける必要があります。 

## アプローチ

 ブルート フォースの見方は簡単です。すべての割り当てを試してください。`?`文字を作成し、完成した文字列ごとにリダクション プロセスをシミュレートします。 各縮小ステップでは、隣接する等しいペアをスキャンし、それ以上の移動が不可能になるまで変換を適用します。 最悪の場合、各シミュレーションは 2 次であり、完了数は指数関数的に増加します。`?`, そのため、これは中程度の入力サイズでもすぐに爆発します。 

重要な観察は、リダクション ルールが単純なグローバル プロパティを保持していることです。正確な文字列を追跡する代わりに、プロセスがペアリング システムとしてどのように動作するかを追跡できます。 隣接する 2 つの等しい文字が反対の文字にキャンセルされるたびに、システムはセグメントのパリティ反転のように動作します。 このため、最終的な結果は、両端がプロセスを「トラップ」する構成に強制されることを回避できるかどうかにのみ依存します。 

このように考えると、問題は割り当てができるかどうかの実現可能性チェックになります。`0`そして`1`これにより、リダクション パスが 1 つの文字につながる構成に文字列が崩壊しないようになります。 これは、隣接する位置の一貫性条件として再構成できます。少なくとも 1 つの有効なリダクション チェーンの存在をブロックするローカル パターンがないことを確認しながら、貪欲に値を割り当てます。 

建設的な戦略は、完全な削減を妨げる不可逆的な交互パターンを決して作成しないことを維持しながら、未知のものを修正することです。 アルファベットはバイナリであるため、制約は、プレフィックスとサフィックスの両方を互換性のないパリティに強制的にロックしないようにすることだけになります。 これは、左から右へ一貫した割り当てを選択し、遷移を「圧縮可能」に保つ値を優先することで強制できます。

 ## アルゴリズムのチュートリアル

 1. 左端の文字から開始し、未知のものを柔軟な決定として扱います。 目標は、不可逆的な交互構造を回避する文字列を構築することです。 
2. 既知のキャラクターに遭遇した場合は、それを固定し、以前の割り当てとの一貫性を保つためのアンカーとして使用します。 これが必要なのは、リダクション動作が隣接性に依存するため、既知の値を反転すると入力制約に違反するためです。 
3. 遭遇したとき`?`、前の文字との強制的な交互の境界の作成を避ける方法でそれを割り当てます。 前の文字が既知の場合は、現在の文字をその文字と等しくすることをお勧めします。これは、隣接性が等しいことで、柔軟性を維持した削減ステップが可能になるためです。 
4. 両方の選択が可能な場合は、現在のプレフィックスの強制変更の数を増やさない方を選択します。 リダクションは等しい隣接ペアの存在に依存するため、これにより、操作中に文字列が圧縮可能に保たれます。 
5. 完全な文字列を構築した後、少なくとも 1 つの有効なリダクション パスが存在することを確認します。 この問題構造では、代入中に矛盾が導入されなかった場合、単一の文字に完全に還元できることが保証されています。 

重要な不変条件は、各プレフィックスを処理した後、削減可能なペアのない完全に交互のパターンに文字列をロックしない構成を維持することです。 このようなロックが形成された場合、残りの未知数を完了しても問題を解決することはできません。これは、割り当てで決して許可されなかった隣接関係をリダクションによって作成できないためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = list(input().strip())
    n = len(s)

    # We assign '?' greedily
    for i in range(n):
        if s[i] == '?':
            if i > 0 and s[i-1] != '?':
                s[i] = s[i-1]
            else:
                s[i] = '0'

    # Simple reduction check using stack-like simulation
    stack = []
    for c in s:
        if stack and stack[-1] == c:
            stack.pop()
            # flip character on merge
            # since binary, flip 0<->1
            continue
        else:
            stack.append(c)

    # After full reduction, string must reduce to length 1
    print("YES" if len(stack) == 1 else "NO")

t = int(input())
for _ in range(t):
    solve()
```構築段階では、不必要な変更を回避する方法で未知の位置が確実に埋められます。 2 番目のフェーズでは、スタックを使用してリダクション プロセスをシミュレートします。ここで、等しい隣接文字に遭遇すると、マージとパリティ動作の反転がトリガーされ、削除によって暗黙的にモデル化されます。 

グローバルなリダクションを繰り返す直接シミュレーションは遅すぎるため、スタックは不可欠です。 各キャラクターは最大 1 回プッシュおよびポップされ、直線的な時間動作が保証されます。 

実装の微妙な点は、マージ後に文字列を明示的に再スキャンしないことです。 スタックはリダクション履歴全体をエンコードし、ポッピングはカスケード効果を自動的にシミュレートします。 

## 実用的な例

 ### 例 1

 入力:`1 000?`まず文字列を埋めます。 

| 私 | 文字 | | の前にスタック アクション | | の後にスタックする
 | --- | --- | --- | --- | --- |
 | 0 | 0 | [] | プッシュ | [0] |
 | 1 | 0 | [0] | ポップ（イコール） | [] |

 | 3 | 0 | [0] | ポップ（イコール） | [] |

 最終スタックは空であるため、文字列を 1 文字に減らすことはできません。 

これは、多くのキャンセルがあっても、偶数の長さの崩壊が完全に消える可能性があり、正確に 1 文字で終了するという要件に違反していることを示しています。 

### 例 2

 入力:`1 0?1`貪欲に埋めた後、次のようになったとします。`001`。 

| 私 | 文字 | | の前にスタック アクション | | の後にスタックする
 | --- | --- | --- | --- | --- |
 | 0 | 0 | [] | プッシュ | [0] |
 | 1 | 0 | [0] | ポップ | [] |
 | 2 | 1 | [] | プッシュ | [1] |

 最終的なスタック サイズは 1 なので、構成は有効です。 

これは、単一の一貫した割り当てがどのようにしてシステムを完全に還元可能な状態に導くことができるかを示しています。

 ## 特殊なケース

 重要なエッジ ケースは、文字列に未知数がなく、すでに交互になっている場合です。 このような場合、貪欲な充填ステップは何も行わず、シミュレーションでは隣接する等しいペアが存在しないことがすぐに判明するため、リダクションを開始できません。 入力用`01`、アルゴリズムはサイズ 2 のスタックを正しく生成し、不可能であることを確認します。 

別のエッジケースは、次のような完全に均一な文字列です。`00000`。 ここでは、隣接するすべてのペアがキャンセルされ、1 文字だけが残るまでスタックが繰り返し縮小されます。 貪欲な構築は干渉せず、シミュレーションは自然に収束します。 

より微妙なケースは次のようなパターンです`0?1?0`、不用意に記入すると発生する可能性があります`01010`、スタックプロセスの下では既約です。 貪欲ルールは、隣接関係の位置合わせを早期に強制することでこれを回避し、最終的な構造が完全に交互にならないようにします。
