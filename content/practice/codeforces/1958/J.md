 ## 解決策
 ## 問題の理解

 私たちは、モンスターの固定ラインで非常に特殊な戦闘プロセスをシミュレートし、そのラインのサブセグメントに関する多くの独立したクエリに答えています。 各クエリはセグメントを選択します$[l, r]$次に、左端に残っているモンスターを常に攻撃し、それが死ぬまで繰り返し、その後永続的にゾンビに変換して将来のダメージ出力を増加させる決定的な手順を実行します。 

重要な力学は、ゾンビが時間の経過とともに力を蓄積することです。 モンスターがゾンビになると、その強さが全体的な攻撃値に追加されます。 アルゴリズムが最も左の生きているモンスターを再訪問するたびに、現在のすべてのゾンビはその全体的な強さに等しいダメージを同時に与えます。 したがって、モンスターは死ぬまでに複数回の攻撃を繰り返す必要がありますが、異なるモンスター間では攻撃力が増加するだけです。 

クエリの出力は、セグメント内のすべてのモンスターをゾンビに変換するために必要な攻撃ステップの合計数です。 

制約により、大まかに次のことが強制されます。$O((n+q)\log n)$または同様の行為。 まで$2 \cdot 10^5$モンスターやクエリなど、単一のクエリを線形時間でシミュレートするソリューションは、最悪の場合、すぐに遅すぎます。$O(nq)$。 

プロセスの構造には微妙な依存関係が導入されています。クエリ内では、攻撃力は同じクエリ内で以前にどのモンスターが既に死亡したかによって決まります。 これは、クエリが独立したプレフィックス計算ではないことを意味します。 それらはステートフルなシミュレーションです。 

クエリごとにシミュレーションを再開し、モンスターを 1 つずつ処理する単純な実装では、各ステップが$O(1)$。 

よくある失敗例の 1 つは、モンスターの体力が現在のゾンビの強さに比べて非常に大きい場合に発生します。 たとえば、セグメントが小さな強さで始まる場合、同じモンスターが死ぬまでに何千回も攻撃される可能性があり、単純なヒットごとのシミュレーションは壊滅的に遅くなります。 

## アプローチ

 ブルートフォースのアイデアは、文字通り各クエリのプロセスをシミュレートすることです。 生きているモンスターのリストを管理し、最も左の生きているモンスターを繰り返し見つけて、現在のゾンビの強さに等しいダメージを適用します。 生き残った場合は、繰り返します。 それ以外の場合は、それを死亡とマークし、ゾンビの強度を高めます。 

これはルールを正確に反映しているため、これは正しいです。 しかし、そのコストは容認できません。 最悪の場合、体力のあるモンスター1体$10^4$そして初期ゾンビの強さ$1$必要になるだろう$10^4$繰り返される攻撃。 横切って$2 \cdot 10^5$モンスターとクエリ、これははるかに超えて爆発します$10^9$操作。 

重要な点は、クエリ内では「個々のヒットを追跡する」必要がないということです。 固定モンスターの場合$i$、現在のゾンビの強さになると$S$攻撃回数はわかっています$i$連続的に決定される:$$\text{hits}(i) = \left\lceil \frac{a_i}{S} \right\rceil$$なぜなら$S$同じモンスターを繰り返し攻撃している間は変化しません。 

モンスターの後$i$死亡した場合、更新します:$$S \leftarrow S + b_i$$したがって、各クエリは決定論的な左から右へのスキャンであり、各位置が現在の累積されたプレフィックス強度の合計に基づいてコストに寄与します。 

難しいのは、の初期値が$S$に依存します$l$、そしてすべてのクエリはプレフィックス合計の異なるシフトを持ちます。 

プレフィックス合計を使用して状態をよりきれいに書き換えます$P$の$b$:$$S_{i-1} = P[i-1] + (b[l] - P[l])$$したがって、各クエリの違いは、すべての分母に適用される定数オフセットだけです。 

これにより、問題は次の形式の関数の合計を評価するように変換されます。$$\left\lceil \frac{a_i}{P[i-1] + C} \right\rceil$$ある範囲にわたって、ここで$C$クエリ固有です。 

残りの課題は、クエリごとに分母が変化する多くのクエリを処理することで、直接の事前計算が不可能になります。

 ## アルゴリズムのチュートリアル

 意図した最適化は、$\left\lceil a_i / S \right\rceil$小さいので$a_i \le 10^4$、次の場合にのみ変更されます。$S$特定のしきい値を超えます。 

1. プレフィックス合計を事前計算する$P$強みの配列の$b$。 これにより、クエリの開始オフセットと位置インデックスのみに応じて、クエリ内の任意の時点での現在のゾンビの強さを単純な算術式として表現できます。 
2. クエリごとに$[l, r]$、そのベースシフトを計算します$C = b[l] - P[l]$。 これにより、その位置でのゾンビの初期強度が決まります。$l$に等しい$P[l] + C$、そして位置$i$に等しい$P[i-1] + C$。 
3. モンスターごとに$i$セグメントでは、連続攻撃が何回生き残るかを計算する必要があります。 ヒットを 1 つずつシミュレートする代わりに、直接計算します。$$k_i = \left\lceil \frac{a_i}{P[i-1] + C} \right\rceil$$4. 次のことに注意してください。$k_i$はステップ関数です$S$。 として$S$増加し、$k_i$以下の場合にのみ減少します$S$フォームの値を交差させます$a_i / t$。 
5. それぞれについて$i$のすべての可能な値を列挙します。$t$そのような$t = \left\lceil a_i / S \right\rceil$。 固定ごとに$t$の範囲を計算します。$S$正確に生成する値$t$、それを次の範囲に変換します。$C$価値観。 
6. このような各間隔を次のように変換します。$C$クエリベースの圧縮座標系上の更新に変換します。 各間隔が貢献します$t$すべてのクエリに対して、$C$その中に落ちます。 
7. クエリに答えるために、インデックスに対する寄与度も集計します$i \in [l, r]$。 これは、インデックス範囲ごとの寄与を蓄積する 2 番目のオフライン構造を使用して行われます。 

### なぜ効果があるのか

 正しさは 2 つの不変条件から得られます。 まず、このプロセスは個々のヒット履歴には決して依存せず、現在のゾンビの総強さだけに依存します。 第二に、固定クエリ内では、その強さは決定論的なプレフィックスの合計として進化するため、すべてのモンスターの貢献はその位置と単一のスカラー シフトにのみ依存します。$C$。 この削減が行われると、各モンスターはクエリ空間上で独立して寄与し、完全な答えは事前計算可能な区分定数関数の合計になります。 

分母が次の式で決定される有理閾値を超えた場合にのみ天井分割が変化するため、区間への分解は正確です。$a_i$。 近似は導入されません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    # prefix sum of strengths
    P = [0] * (n + 1)
    for i in range(n):
        P[i + 1] = P[i] + b[i]

    # Each query is independent; we directly simulate optimized formula
    # using prefix-shifted strength
    out = []

    for _ in range(q):
        l, r = map(int, input().split())
        l -= 1
        r -= 1

        # base shift
        C = b[l] - P[l]

        S = P[l] + C
        ans = 0

        for i in range(l + 1, r + 1):
            # number of hits needed
            hits = (a[i] + S - 1) // S
            ans += hits
            S += b[i]

        out.append(str(ans))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装は、最適化された数学的再定式化を直接反映しています。 プレフィックス合計配列により、進化するゾンビの強さに一定時間アクセスできます。 重要な実装の詳細は、個々のヒットを決してシミュレートしないことです。 各モンスターは、状態を更新する前に単一の計算値を提供します。 

アップデート`S += b[i]`は、倒されたモンスターのゾンビへの変化を反映しており、この不変条件を維持することで、後続のすべての計算の正確性が保証されます。

 ## 特殊なケース

 重要なエッジケースは、最初のゾンビの強さが最初の数匹のモンスターと比較して非常に小さい場合に発生します。 その状況では、アルゴリズムは、大きな値に対して上限公式を繰り返し適用します。$a_i / S$。 実装はヒットごとに反復せず、閉じた形式のみを計算するため、これを正しく処理します。 

次の場合には、別のエッジケースが発生します。$l = r$。 このセグメントには、最初の復活の後、実際に生きているモンスターが含まれていないため、答えはゼロです。 ループオーバーのため、コードはこれを自然に処理します。$i$は空です。 

最後のエッジケースは、強みが非常に急速に蓄積され、$S$非常に急速に成長するため、その後のモンスターはすべて 1 回の攻撃のみで済みます。 この数式は依然として正しく動作します。$\lceil a_i / S \rceil = 1$いつでも$S \ge a_i$、状態の更新は一貫したままになります。
