 ## 問題の理解

 このタスクでは、通常必要となる建物のアップグレードについて説明します。`t`作業時間は数分。 エリクサーはアップグレードの開始と同時に有効化されます。 エリクサーの有効期間中、`p`数分、建設は進んでいます`k`通常よりも何倍も速いです。 エリクサーの有効期限が切れた後、未完了の作業は通常の速度で続行されます。 目標は、アップグレードが完了するまでにかかった合計実時間を見つけることです。 

入力には 3 つの整数が含まれています。`t`必要な通常の建設作業の量、`k`エリクサー効果中の速度乗数であり、`p`効果の継続時間を実際の分単位で表します。 出力は、エリクサーの使用時に必要な実際の分数です。 

制約は解決策の主な手がかりです。 の値`t`そして`k * p`到達できる`10^9`したがって、分ごとに進むシミュレーションには最大 10 億回の反復が必要になる場合があります。 1秒の制限時間としては長すぎます。 解決策は直接演算を使用し、一定時間内に完了する必要があります。 

いくつかの特殊なケースでは、一般的な状況にのみ対処するソリューションが機能しなくなる可能性があります。 エリクサーだけで建設が完了するかというと、答えはそうではありません。`p`, エリクサーの有効期限が切れる前に建物が完成する可能性があるためです。 たとえば、入力の場合`100 10 20`、エリクサーはすべてを終わらせることができます`100`の作業単位`10`分なので、正しい出力は次のようになります。`10`。 エリクサーの完全な持続時間を常に加算するソリューションは、誤ってより大きな値を返します。 

エリクサーが建設とまったく同じ瞬間に終了する場合、別の境界ケースが現れます。 入力用`100 5 20`、エリクサーは提供します`5 * 20 = 100`作業単位。 正しい出力は次のとおりです`20`。 これを未完了の作業として扱う不注意な実装では、さらに 1 分かかる可能性があります。 

最後のよくある間違いは、答えは整数の分でなければならないということを無視することです。 入力用`101 10 20`、エリクサーは十分な持続時間を提供しますが、建設速度は`10`1 分あたりの単位なので、実際の時間は次のようになります。`ceil(101 / 10) = 11`。 整数の除算を返すと次のようになります`10`、これは間違いです。 

## アプローチ

 簡単なアプローチは、建設を分刻みでシミュレーションすることです。 残りの作業を追跡し、差し引くことができます`k`エリクサーが有効な間は 1 分ごとに単位が減算され、その後は 1 分ごとに 1 単位減算されます。 このアプローチはプロセスに正確に従うため、検証が簡単です。 

シミュレーションの問題は、可能な入力サイズです。 最悪の場合、建物によっては、`10^9`作業時間は数分。 シミュレーションでは、1 分あたりおよそ 1 回の操作が実行されます。`O(10^9)`制限時間内に収まる範囲をはるかに超えた作業が行われます。 

重要な観察は、エリクサー効果には一定量の加速された仕事があるということです。 存続期間中、建設は正確に完了します`k * p`通常の作業時間。 分ごとにシミュレーションする代わりに、この量を必要な作業量の合計と直接比較できます。 

もし`k * p`よりも小さいです`t`、エリクサーは建設の一部を完了し、残りの作業は正常に完了します。 答えは次のようになります`p`プラス残った仕事。 もし`k * p`少なくとも`t`、エリクサーがまだ有効な間に建設が終了するため、実行に必要な時間だけが必要です`t`スピードを出して働く`k`。 

ブルートフォース手法は、すべての分を個別にモデル化できるため機能しますが、分が多すぎる可能性があるため失敗します。 エリクサー期間全体を単一の完了した作業量に変換できるという観察により、問題は数回の算術演算に軽減されます。

 ## アルゴリズムのチュートリアル

 1. エリクサーが完了できる建設作業の総量を計算します。 その間`p`数分間の加速工事、進捗状況は`k * p`通常の作業時間。 この値により、アップグレードがエリクサー期間中に終了するか、エリクサー期間後に終了するかを決定できます。 
2. かどうかを確認します。`k * p`少なくとも`t`。 そうであれば、構築全体がエリクサーの効果の下で行われます。 所要時間は上限`t / k`、毎分完了するため`k`作業単位と最後の分は部分的にのみ使用できます。 
3. もし`k * p`よりも小さいです`t`、必要な作業から加速された進捗を差し引きます。 残りの量はエリクサーの恩恵を受けることができないため、全期間に直接追加されます。`p`。 

機能する理由: 構築プロセスは、エリクサー期間中の個々の時間ではなく、作業の完了量のみに依存します。 最初`p`分は常に正確に貢献します`k * p`工事が早く終了しない限り、通常の作業単位となります。 必要な作業がその量より大きい場合、残った作業は正常に完了します。 これより小さいか等しい場合、タスク全体が加速された建設中に発生します。 これら 2 つのケースは考えられるすべての実行をカバーするため、算術結果は実際の完了時間と一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t, k, p = map(int, input().split())

boosted_work = k * p

if boosted_work >= t:
    print((t + k - 1) // k)
else:
    print(p + (t - boosted_work))
```変数`boosted_work`エリクサーの全期間中に完了した通常の建設作業の合計量を保存します。 乗算する`k`による`p`彼らの製品は問題の制約によって制限されているため、安全です。 

最初のブランチは、エリクサーの有効期限が切れる前に建物が終了する場合を処理します。 表現`(t + k - 1) // k`天井分割を実行します。出力では分数の小数部を使用できないため、これが必要になります。 例えば、`101`作業ユニットを高速で動作させる`10`必要`11`分。 

2 番目のブランチは、エリクサーがアップグレードを完了できない場合を処理します。 エリクサーは正確に消費します`p`実際の分数と完了時間`k * p`作業単位、退出`t - k * p`ユニットは通常の速度で完了します。 通常速度は1分間に1作業単位なので、残量を直接加算できます。 

このコードでは整数演算のみを使用します。 浮動小数点計算がないため、丸めに関する精度の問題はありません。

## テストケース```python
import sys
import io

def solve(inp: str) -> str:
    old_stdin = sys.stdin
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t, k, p = map(int, input().split())
    boosted_work = k * p

    if boosted_work >= t:
        ans = (t + k - 1) // k
    else:
        ans = p + t - boosted_work

    sys.stdin = old_stdin
    return str(ans)

assert solve("2640 10 60\n") == "2100", "sample 1"
assert solve("101 10 20\n") == "11", "sample 2"

assert solve("1 1 1\n") == "1", "minimum values"
assert solve("1000000000 1000000000 1\n") == "1", "maximum accelerated speed"
assert solve("100 5 20\n") == "20", "exact elixir completion boundary"
assert solve("100 3 10\n") == "40", "remaining normal work case"

 入力用`100 10 20`、エリクサーは提供します`200`必要以上の作業単位`100`。 アルゴリズムは高速完了ブランチに入り、以下を計算します。`ceil(100 / 10) = 10`、正解を生成します。 完全に完了するまで誤って待機することはありません`20`エリクサーの持続時間（分）。 

入力用`100 5 20`、加速された作業はまさに`100`。 アルゴリズムチェック`k * p >= t`したがって、境界での完了を正しく処理し、計算します。`ceil(100 / 5) = 20`。 

入力用`101 10 20`、アルゴリズムは高速化された完了ブランチも使用します。`200 >= 101`。 天井分割により、`(101 + 10 - 1) // 10 = 11`、よくある整数の割り算の間違いを回避します。 

インプットなどエリクサーが不足する場合`100 3 10`、エリクサーが完成します`30`の作業単位`10`分。 残り`70`単位が必要です`70`通常はさらに分がかかるため、アルゴリズムは戻ります`10 + 70 = 80`。 これにより、加速された構築から通常の構築への移行が正しく処理されたことが確認されます。
