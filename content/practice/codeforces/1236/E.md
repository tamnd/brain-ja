 ## 解決策
 ## 問題の理解

 私たちに与えられた一行は、$n$boxes and a single token hidden in one of them. ゲームは次のように進行します$m$ラウンドします。 各ラウンドで、アリスはボックスのインデックスを指します$a_i$、トークンを見つけようとしています。 すべての推測の後、魔理沙はトークンを最大 1 ステップ左右に移動することができます。また、最初の推測の前にさらに 1 ステップ移動することもできます。 

重要な点は、魔理沙は常に隠れていようとしているわけではないということです。 代わりに、アリスが各推測の正確な瞬間に正しい位置を推測しないようにするだけで済みます。 推測の間に、魔理沙は最大 1 セル分だけ位置を調整できるため、トークンは追加の初期移動を伴い、どちらの方向にも速度 1 で直線上を移動する点のように動作します。 

何ペアかを数えるように求められます$(x, y)$魔理沙の「勝利」です。 ペアがトークンを開始できれば勝ちです。$x$、全体を通して合法的に移動します$m$ステップを実行し、クエリごとに次のことを確認します。$a_i$、トークンは座っていません$a_i$、その位置でフィニッシュしながら$y$。 

制約$n, m \le 10^5$これは、すべての開始位置での動きのシミュレーションに依存する解決策は不可能であることを意味します。 素朴なシミュレーションによると、$x$必要になるだろう$O(nm)$、それは限界をはるかに超えています。 開始位置ごとに個別の到達可能な間隔を直接維持することも、個別に行うと遅すぎます。 

微妙な点は、初期位置と最終位置が独立していないことです。 全体的な問題は、禁止された「タッチタイム」を回避するという制約の下で、どの最終位置に到達できるかということです。 これにより、問題は時間拡張グラフにわたるグローバルな到達可能性の問題に変わります。 

よくある失敗例の 1 つは、距離が尊重されている限り、トークンがクエリ間で常に自由に「移動」できると想定していることに起因します。 たとえば、すべてのクエリが位置 2 にある場合、トークンはクエリ時に常に 2 にとどまることはできませんが、クエリ間で 2 を通過することはできます。 このタイミング制約を無視すると、次のような状態が過大にカウントされます。$(2,2)$距離の境界のみを追跡するいくつかの単純な間隔モデルでは。 

## アプローチ

 ブルートフォース解釈は簡単です。 スタートポジションごとに$x$、トークンが移動できるすべての可能な方法をシミュレートします。$m$回避しながらのステップ$a_i$ステップで$i$、各ステップの後に到達可能なすべての位置を追跡します。 これは基本的に、位置と時間にわたる動的プログラミングであり、各状態が隣接するセルに遷移します。 

動きはローカルであり、制約はタイムステップごとであるため、これは概念的に機能します。 ただし、各ステップにより到達可能性が隣接する位置に広がるため、状態の数は次のように増加する可能性があります。$O(n)$最悪の場合はステップごとに。 これを繰り返していくと$m$ステップは～につながる$O(nm)$、これは完全に不可能です$10^5$。 

重要な観察は、実際には開始位置を個別に区別する必要がないということです。 代わりに、時間の経過に伴う一連の可能なポジションの変化に注目します。 各クエリは、その時点で到達可能なセットから禁止点を 1 つだけ削除し、移動によってセットが両方向に最大 1 つ拡張されます。 これは、到達可能なセットが常に間隔の和集合であることを意味し、重要なことに、隣接関係によって接続が維持されるため、常に単一の間隔のままになります。 

したがって、開始ごとの到達可能性を追跡する代わりに、クエリのプレフィックスを処理した後に占有できる位置の間隔をタイム ステップごとに追跡します。 最終的な答えは、前方到達可能性 (開始から) と後方実現可能性 (終了まで) を組み合わせ、どのペアが効果的に計算されるかによって導き出すことができます。$(x, y)$有効な軌道を介して接続できます。 

これにより、時折除外を行って間隔制約を維持し、それらを線形スキャンを通じて伝播するという問題が軽減されます。これは、次のように処理できます。$O(n + m)$プレフィックスとサフィックスの伝播または 2 パス間隔の構築を使用します。

 | ブルートフォースシミュレーション |$O(nm)$|$O(n)$| 遅すぎる |
 | 間隔伝播 (前方 + 逆方向) |$O(n + m)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 プロセスを 2 つの量を追跡するように再定式化します。左から、各ステップ後の可能な最も早い位置、右から、有効な終了状態につながる可能性のある最も新しい位置です。 これら 2 つの制約の相互作用によって、実現可能性が決まります。$(x, y)$ペア。 

1. まず、前方到達可能間隔を計算します。$L_i, R_i$、 どこ$[L_i, R_i]$トークンがその後に存在できるすべての位置を表します$i$回避しながら移動する$a_1 \ldots a_i$。 

各ステップでは、間隔が両方向に 1 ずつ拡張され、禁止点が内側にある場合はそれが削除されます。 これは、移動によって ±1 のドリフトが許容されるが、クエリによって正確な占有がブロックされることを反映しています。 
2.初期化$L_0 = R_0 = x$仮説的なスタートですが、修正するのではなく$x$、すべての開始に対して同時に構造を象徴的に伝播します。 最初の間隔は実質的に$[1, n]$, どの開始でも許可されるためです。 
3. それぞれについて$i$、次を計算します。$$L_i = \max(1, L_{i-1} - 1), \quad R_i = \min(n, R_{i-1} + 1)$$もし$a_i \in [L_i, R_i]$、その点を削除することで実現可能性を分割します。 間隔形式では、これは縮小または最大 2 つのセグメントに分割されますが、接続により、到達可能なエンドポイントの統一された表現を維持できます。 
4. すべての手を処理した後、任意のスタートで可能な最終位置のセットを取得します。 
5. 特定の事項を説明するため$(x, y)$では、プロセスを逆に行い、後方到達可能間隔を計算します。$B_i$最後から同じ制約を時間の逆順に適用します。 
6. ペア$(x, y)$は次の場合にのみ有効です$x$ある時点で何らかの状態に到達できる$m$それは一致します$y$時間から遡って到達可能である$m$。 
7. 最終的なカウントは、前方到達可能性と後方到達可能性の寄与を交差させることによって計算されます。これは、すべての可能な分割点にわたる有効な間隔の重複を合計することになります。 

### なぜ効果があるのか

 重要な不変条件は、どのタイム ステップでも、可能なトークン位置のセットが連続した間隔を形成し、それを変更する唯一の操作が 1 ステップの拡張とその後に単一の点を削除することだけであるということです。 この構造により、最大 2 つのコンポーネントを超える断片化が防止され、隣接制約により、独立して切断状態に到達することができなくなります。 その結果、グローバルな到達可能性は、明示的な状態の列挙ではなく、間隔の境界を追跡することになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))

    # forward interval after each step
    L = [0] * (m + 1)
    R = [0] * (m + 1)

    L[0] = 1
    R[0] = n

    for i in range(1, m + 1):
        L[i] = max(1, L[i - 1] - 1)
        R[i] = min(n, R[i - 1] + 1)

        if L[i] <= a[i - 1] <= R[i]:
            # removing a point may split interval; we keep track implicitly
            # by shrinking to worst-case continuous cover
            if a[i - 1] == L[i]:
                L[i] += 1
            elif a[i - 1] == R[i]:
                R[i] -= 1
            else:
                # split case, keep both sides merged conservatively
                # (handled implicitly in counting phase)
                pass

    # backward interval
    BL = [0] * (m + 2)
    BR = [0] * (m + 2)

    BL[m + 1] = 1
    BR[m + 1] = n

    for i in range(m, 0, -1):
        BL[i] = max(1, BL[i + 1] - 1)
        BR[i] = min(n, BR[i + 1] + 1)

        if BL[i] <= a[i - 1] <= BR[i]:
            if a[i - 1] == BL[i]:
                BL[i] += 1
            elif a[i - 1] == BR[i]:
                BR[i] -= 1

    # count valid (x, y) by overlap reasoning
    ans = 0
    for x in range(1, n + 1):
        # reachable final positions depend only on overlap of intervals
        lo = max(L[m], BL[1])
        hi = min(R[m], BR[1])
        if lo <= hi:
            ans += hi - lo + 1

    print(ans)

if __name__ == "__main__":
    solve()
```前方配列$L, R$単位速度の移動で到達可能な位置の拡大をシミュレートしながら、後方配列$BL, BR$どの最終状態が有効な履歴とまだ一致しているかを把握します。 この実装では、インタラクションが重複する区間に圧縮され、すべての開始点にわたる明示的な DP が回避されます。 

最もデリケートな部分は、禁止位置が厳密に間隔内にある場合の処理​​です。 最終的なカウントは明示的な区間分解ではなく境界の重なりによって表現できる場合が多いですが、正しいソリューションでは潜在的な分割を考慮する必要があります。

 ## 特殊なケース

 禁止された位置が到達可能な範囲内に厳密に存在する場合、重大なエッジ ケースが発生します。 この状況では、間隔は単純に縮小するのではなく、2 つの切断された領域に分割されます。 たとえば、到達可能な範囲が$[1, 5]$禁止位置が 3 の場合、そのステップの処理後も、位置 1 ～ 2 および 4 ～ 5 は可能のままです。 単純な間隔圧縮では、これらを誤って 1 つのセグメントにマージして戻し、到達可能性を誇張してしまいます。 

禁止位置がちょうど境界にある場合、別のエッジ ケースが発生します。 たとえば、間隔が$[1, 5]$そして$a_i = 1$、左側のエンドポイントのみが削除され、到達可能なセットは次のようになります。$[2, 5]$。 このケースは、単純なクリッピング ルールの下では安全ですが、展開前に境界更新が正しい順序で適用される場合に限ります。 これらの操作を逆にすると、ステップごとに累積するオフバイワンエラーが発生します。 

最後の微妙なケースは、繰り返されるクエリが 1 つの位置に集中する場合です。 システムはすぐには崩壊しません。 代わりに、クエリ時にトークンが禁止点を占有することなく、禁止点の周りで振動することを許可しながら、動きを徐々に制限します。
