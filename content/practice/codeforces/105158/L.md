 ## 解決策
 ## 問題の理解

 私たちには次のようなプログラムが与えられています。$n$行とそのサブセット$m$これらの行にはバグが含まれています。 すべてのバギー ラインの位置は事前にわかっており、厳密に増加しています。 

Toxel はデバッグ操作を繰り返し実行します。 1 回の操作で、プレフィックスの長さを選択します。$i$。 彼はプログラムを次の行までだけ実行します$i$のコストを支払う$i$実行までの秒数。 実行後、このプレフィックス内のバグのある行をすべて検査して修正します。 プレフィックスに次のものが含まれる場合、$x$バグのある行、デバッグコストは$x^4$数秒かかると、それらのバグはすべてそれらの行から永久に削除されます。 

目標は、すべてのバグのある行が最終的にカバーされて修正されるように一連のプレフィックスを選択し、実行コストとデバッグ コストの両方を含む合計時間を最小限に抑えることです。 

主要な構造は、各操作でプレフィックスが選択され、そのプレフィックスによって内部のすべてのバグが「クリア」されるということです。 バグは一度修正されると元に戻らないため、後の操作では未修正の位置のみが処理されます。 

制約により、最大で$2 \cdot 10^5$したがって、考えられるすべてのプレフィックスの選択や操作のすべてのサブセットを考慮したソリューションは不可能です。 決定空間は本質的に$O(n)$ステップごとに選択肢があり、場合によっては多数のステップが必要になります。 

複数のバグのある行が近くにある場合、微妙な問題が発生します。 素朴な直感は、次のバグを含めるのに十分なだけプレフィックスを常に拡張することを提案するかもしれませんが、それは複数のバグを 1 つのプレフィックスにグループ化する間の相互作用を無視しています。$x^4$この用語は大規模なバッチに大きなペナルティを与えます。 もう 1 つの失敗モードは、各バグを個別に扱うことです。これは、単一のプレフィックスで多くのバグを同時にカバーできることを無視し、各バグを正確な位置のサイズの別個のプレフィックスで修正できると誤って想定することになります。 

小さな例として、バグが初期に密集している場合があります。 

入力:

 n = 10、バグのある行 = [1, 2, 3]

 操作ごとに常に 1 つのバグを修正すると、小さなプレフィックスの実行の 3 倍の料金を支払うことになりますが、繰り返しの発生も発生します$1^4$費用がかかります。 代わりにサイズ 3 の単一プレフィックスを使用する場合、1 回の実行に 3 プラスを支払います。$3^4$、修理期間が大幅に大きくなります。 最適な戦略は、これら 2 つの相反するコストのバランスをとることです。 

## アプローチ

 ブルートフォース手法では、考えられるすべてのプレフィックス選択シーケンスが試行されます。 各ステップで、$i$のすべてのバグの修正をシミュレートします。$[1, i]$、残りのバグを再帰的に調べます。 すべての有効な戦略はそのようなプレフィックス操作のシーケンスであるため、これは概念的に機能します。 しかし、州の数は爆発的に増加します。 残りの未解決のバグの観点から考えると、各操作でプレフィックス セグメントを削除することができ、一連のバグ位置をプレフィックス グループに分割する方法は指数関数的に多く存在します。 サブセットに対する動的プログラミングさえ不可能です。$m$できる$2 \cdot 10^5$。 

重要な点は、どのような操作においても重要なのは、選択したプレフィックスに以前に修正されていないバグがいくつあるかだけであるということです。 プレフィックス内の実際の位置は、実行コストを決定すること以外は重要ではありません。$i$。 バグのある位置を分類し、プレフィックス境界がそれらの上をどのようにスイープするかを考慮すると、すべての操作が効果的に正しい境界を選択していることになります。$i$、これは、残りのバグの連続した接尾辞をカバーすることに対応します。 

これにより、ソートされたバグの位置をセグメントに分割する方法を決定することが問題になります。 各セグメントは 1 つの操作に対応し、セグメントがインデックスからバグをカバーする場合$l$に$r$の場合、プレフィックスは次まで拡張する必要があります$a_r$、コストは、その前にすでに削除されているバグの数によって異なります。$l$。 

これは、順序付けされたバグ リストに対する動的プログラミングの解釈につながります。つまり、カット ポイントをどこに配置するかを決定します。 セグメントのコストは、セグメントに含まれるバグの数と、最後のバグをカバーするためにプレフィックスがどこまで続くかによってのみ決まります。 実行コストはセグメント内の最大位置のみに依存し、修復コストはセグメント サイズのみに依存するため、プレフィックス数とプレフィックス位置を使用して遷移を効率的に計算できます。 

したがって、最適な解決策は、処理されたバグの数に対する DP であり、トランジションは位置で終了する次のセグメントを試行します。$j$、コストはバグ数とプレフィックス長から計算されます。

 ## アルゴリズムのチュートリアル

 1. バグの位置を並べ替える$a_1, a_2, \dots, a_m$。 これはすでに保証されていますが、それらを連続セグメントに分割するシーケンスとして扱います。 
2. DP 状態を定義する$dp[i]$最初の部分を修正するための最小総コストとして$i$ソートされた順序でバグのある行。 解釈としてはバグです$1$を通して$i$はすでに削除されており、残りを修正する方法を検討中です。 
3. それぞれについて$i$で終わるセグメントを修正する最後の操作を考えてみましょう。$i$。 このセグメントが次から始まるとします。$j+1$、バグをカバーすることを意味します$j+1$を通して$i$。 次に、から移行します$dp[j]$に$dp[i]$。 
4. 固定ペアの場合$(j, i)$、操作では次の行までプログラムを実行する必要があります。$a_i$セグメント内の最後のバグを含める必要があるためです。 これにより実行コストが発生します。$a_i$。 
5. この操作のバグの数は$x = i - j$したがって、デバッグコストは次のようになります。$x^4$。 このコストはセグメントの長さのみに依存し、実際の位置には依存しません。 
6. したがって、遷移は次のようになります。$$dp[i] = \min_{0 \le j < i} \left(dp[j] + a_i + (i-j)^4\right)$$7. この DP を次から反復的に計算します。$i = 1$に$m$、維持$dp[0] = 0$。 

の計算$(i-j)^4$直接実行できるので、$i-j \le m$。 式は単純ですが、検出力を誤って再計算しないように注意する必要があります。 

### なぜ効果があるのか

 最適なソリューションでは、最後の操作を考慮します。 残りのバグのいくつかのサフィックスをソート順に修正します。 その接尾辞はその長さによって完全に特徴付けられます$i-j$そしてその最後の位置$a_i$、前に終わる接頭辞があるため$a_i$最後のバグを含めることができず、それを超えて拡張されてしまいます。$a_i$含まれるバグは変更せずにコストが増加するだけです。 これにより、ソートされたバグ リストのプレフィックスにわたって問題を独立した最適なサブ問題に分解できるようになり、カット ポイント上の DP が漏れや重複なくすべての有効な戦略を確実に捕捉できるようになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))

    INF = 10**30
    dp = [INF] * (m + 1)
    dp[0] = 0

    for i in range(1, m + 1):
        ai = a[i - 1]
        best = INF
        for j in range(i):
            x = i - j
            cost = dp[j] + ai + x * x * x * x
            if cost < best:
                best = cost
        dp[i] = best

    print(dp[m])

if __name__ == "__main__":
    main()
```コードは、処理されたバグの数に対して DP を直接実装します。 外側のループは、すでに処理されているバグの数を修正し、内側のループは、考えられるすべての以前のカット ポイントを試みます。 必要なプレフィックスの長さが決定されるため、実行コストは常にセグメント内の最後のバグから取得されます。 

最も微妙な点は、プレフィックスコストが$a[i-1]$、セグメント内の以前の値ではありません。 これは、プレフィックスがセグメント内の最後のバグに達すると、それ以前のバグがすべて自動的に含まれるという事実を反映しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    a = list(map(int, input().split()))

    INF = 10**30
    dp = [INF] * (m + 1)
    dp[0] = 0

    for i in range(1, m + 1):

        for j in range(i):
            x = i - j
            dp[i] = min(dp[i], dp[j] + ai + x * x * x * x)

 ## 特殊なケース

 すべてのバグが連続した初期位置にある場合、重要なエッジ ケースが発生します。 この状況では、それらを 1 つのプレフィックスにマージすると、$x^4$そのため、最適解は積極的に分割される傾向があります。 入力用$a = [1,2,3]$、DP は、3 つすべてをグループ化するとコストが発生するかどうかを評価します。$3 + 81$、一方、分割により 4 次コストが大幅に削減され、遷移ではすべてのセグメントの長さを比較することで明示的に取得されます。 

もう 1 つのエッジ ケースは、バグがまばらで離れて存在する場合です。$a = [1, 100000]$。 ここでは、実行コストが初期のセグメントで支配的であり、最適解は 4 次ペナルティにもかかわらずグループ化を優先する可能性があります。 DP は、最後のバグで終了する遷移を通じて両方の可能性を正しく考慮し、長距離のグループ化が時期尚早に除外されないようにします。
