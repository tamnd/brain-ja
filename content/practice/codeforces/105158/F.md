 ## 解決策
 ## 問題の理解

 文字列のコレクションが与えられ、その中で非常に特殊な構造パターンを満たすものがいくつあるかを数える必要があります。 文字列の長さがちょうど 5 で、3 番目と 5 番目の文字が同じで、最初の 4 文字がすべて互いに異なる場合、その文字列は有効であるとみなされます。 

したがって、各入力文字列について、変換したり、他の文字列と比較したりすることはありません。 これらの制約を独立して満たすかどうかのみを確認し、満たしている数を数えます。 

入力サイズは大きく、最大 100,000 個の文字列で、すべての文字列を組み合わせた合計の長さは最大 200,000 です。これにより、各文字列を基本的に一定時間で処理する必要があることがすぐにわかります。 負荷の高い操作で各文字列をスキャンしたり、文字列の数に比例して追加の割り当てを実行したりするソリューションは、全体として線形を維持する場合にのみ合格します。 

素朴な解釈では、順列のチェックや部分文字列の相互比較を示唆するかもしれませんが、制約はローカルで固定長です。 各文字列の長さは 5 であるかどうかのどちらかであるため、文字列ごとに 5 文字を超える文字を考慮する必要はありません。 

「distinct」が最初の 4 文字だけではなく 5 文字すべてで区別されることを意味すると仮定すると、微妙な失敗例が発生します。 たとえば、「abaca」のような文字列には繰り返し文字が含まれていますが、その繰り返しは条件とは無関係な位置で発生する可能性があります。 もう 1 つの落とし穴は、最初の 4 つの位置のみが区別される必要があり、5 番目の文字は 3 番目の位置にのみ関連付けられており、区別性要件には含まれていないことを忘れていることです。 

具体的な例:

 入力:

 「アブデ」

 3 番目の文字「c」が 5 番目の文字「e」と等しくないため、これは無効です。 最初の 4 つの区別のみをチェックする不注意な実装では、誤ってカウントされてしまいます。 

別の例:

 「アババ」

 ここでは、3 番目と 5 番目の文字は一致します (「a」) が、最初の 4 文字はすべて異なるわけではありません (「a」が繰り返されます)。 等価条件を検証するだけの単純なチェックでは、等価条件が誤ってカウントされます。 

## アプローチ

 ブルートフォースアプローチは簡単です。 各文字列について、最初にその長さを確認します。 5 でない場合は、すぐに拒否されます。 それ以外の場合は、文字を検査します。位置 3 が位置 5 と等しいことを確認し、最初の 4 文字がペアごとに異なるかどうかを確認します。 これは、最初の 4 つの位置のすべてのペアを比較するか、それらをセットに挿入してそのサイズを確認することで実行できます。 

各文字列の長さが一定であるため、このアプローチはすでに十分に効率的です。 文字列ごとに O(1) の作業を実行したとしても、合計の複雑さは O(n) です。 セットなどのデータ構造を繰り返し使用する場合、唯一の潜在的な非効率性は不必要なオーバーヘッドから生じますが、それも固定サイズが小さいため制限内にとどまります。 

重要な観察は、構造が固定されており、非常に小さいことです。 長い部分文字列のハッシュや大きなドメインの頻度カウントは必要ありません。 すべてのチェックは定数 (最大 5 文字) によって制限されるため、問題は文字列ごとの定数時間の述語評価に帰着します。 

これにより、グローバルな推論や前処理の必要がなくなります。 各文字列は個別に個別に検証できます。

 | ブルートフォース | O(n) | 文字列ごとに O(1) 余分 | 承認済み |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 各文字列を 1 つずつ処理し、固定の検証ルーチンを適用します。

1. 文字列を読み取り、すぐにその長さを確認します。 ちょうど 5 でない場合は破棄します。 このステップにより、無効な候補に対する不必要な文字チェックが防止されます。 
2. 長さが 5 文字の場合、3 文字目と 5 文字目を比較します。 それらが異なる場合、文字列は有効ではないため、次に進みます。 これは固定位置に依存するため、可能な限り最も早い拒否条件です。 
3. 位置の等価性が成立する場合は、最初の 4 文字を調べます。 4 つすべてが異なることを確認する必要があります。 長さは一定であるため、小さなブール配列またはセットを使用して、表示された文字を記録できます。 繰り返しが発生した場合、その文字列は拒否されます。 
4. 両方の条件が満たされた場合、回答カウンターがインクリメントされます。 

チェックの順序は効率性にとって重要です。 長さチェックと位置の等価性チェックは定数時間で低コストであり、残りの文字を検査する前に無効な文字列に対する不必要な作業を回避します。 

### なぜ効果があるのか

 各文字列は独立して処理され、検証ロジックは「優れた」文字列の定義を直接反映します。 3 番目と 5 番目の文字の条件は 1 回だけ適用され、区別条件は意図した位置のサブセットに対して正確に検証されます。 すべてのチェックが完了し、近似は行われないため、アルゴリズムに合格した文字列は両方の制約を満たし、少なくとも 1 つの条件を満たさない文字列は拒否されます。 文字列間には相互作用がないため、正確性はインスタンスごとに保持され、フルカウントにまで及びます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def is_good(s: str) -> bool:
    if len(s) != 5:
        return False
    if s[2] != s[4]:
        return False
    # check first four characters are all distinct
    seen = set()
    for i in range(4):
        if s[i] in seen:
            return False
        seen.add(s[i])
    return True

def main():
    n = int(input())
    ans = 0
    for _ in range(n):
        s = input().strip()
        if is_good(s):
            ans += 1
    print(ans)

if __name__ == "__main__":
    main()
```このソリューションでは、定義をヘルパー関数に直接エンコードします。 インデックス作成の想定を避けるために、長さのチェックが最初に行われます。 条件`s[2] != s[4]`不一致があると直ちに文字列が不適格となるため、データ構造を構築する前にチェックされます。 

セットベースの一意性チェックは最初の 4 文字のみをカバーし、問題の要件を正確に満たします。 5 番目の文字は別の条件によって管理されるため、このチェックには意図的に含めません。

 ## 特殊なケース

 特殊なケースの 1 つは、5 文字より短いまたは長い文字列です。 たとえば、「abc」や「abcdef」などです。 アルゴリズムは、インデックスにアクセスすることなく、長さチェック時にこれらを即座に拒否し、範囲外の仮定を防ぎます。 

もう 1 つの特殊なケースは、「aaaaa」など、3 番目と 5 番目の文字は一致するが、最初の 4 文字が頻繁に繰り返される場合です。 アルゴリズムは、位置的等価性テストに合格した後の区別性チェック中に正しく不合格になります。 

3 番目のケースは、最初の 4 文字はすべて異なるが、3 番目と 5 番目が一致しない場合です (「abcde」など)。 アルゴリズムは位置チェックの早い段階でそれを拒否し、両方の条件が独立して適用され、どちらも冗長ではないことを示しています。
