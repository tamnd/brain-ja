 ## 解決策
 ## 問題の理解

 長さの配列から始めます`n`完全にゼロで埋められます。 

がある`m`セグメント。 セグメント内の 1 の数が、同じセグメント内の 0 の数よりも厳密に大きい場合、そのセグメントは美しいとみなされます。 ある長さのセグメントの場合`len`、この条件は次と同等です。$$\text{ones} > \frac{\text{len}}{2}$$また、次のシーケンスも与えられます。`q`更新情報。 の`i`- 番目の更新ターン位置`x_i`の中へ`1`。 ポジションは明確に区別されているため、ポジションが決まると`1`、それは残ります`1`。 

タスクは、指定されたセグメントの少なくとも 1 つが美しくなる最も早い更新番号を見つけることです。 すべての更新を適用しても美しいセグメントがない場合は、出力します。`-1`。 

この制約は、すべての更新をシミュレートし、すべてのセグメントを最初から再チェックするのはコストが高すぎることをすぐに示唆しています。 すべてのテスト ケースの合計は、`n`せいぜい`10^5`ただし、1 つのテスト ケースには最大で次のものが含まれる場合があります。`10^5`セグメントと`10^5`更新情報。 に比例した作業を実行するソリューション`m × q`2秒に収まる範囲をはるかに超えています。 

微妙な所見は、更新ではさらに多くのものが追加されるだけであるということです。 一度美しくなったセグメントは、その美しさを止めることはできません。 この単調な動作が解決の鍵となります。 

小さな例を考えてみましょう。```
n = 5
segment = [1,5]
updates = 5,3,1,2,4
```最初の更新後には 1 つあります`1`、2つ目以降は2つ、3つ目以降は3つです。 セグメントの長さは5つなので、3つあれば十分綺麗です。 答えは`3`。 

もう 1 つの簡単な間違いは、条件が厳密には大きいことを忘れていることです。```
segment length = 4
ones = 2
zeros = 2
```これは美しくありません。 を使用した不注意な実装`>=`の代わりに`>`間違って受け入れてしまうだろう。 

セグメントが単一の位置で構成されている場合、別のエッジ ケースが発生します。```
segment = [3,3]
```瞬間位置`3`になる`1`、セグメントには 1 と 0 のゼロが含まれているため、すぐに美しくなります。 答えは次のとおりかもしれません`1`。 

最後に、一部のインスタンスでは美しいセグメントが生成されません。```
n = 4
segments = [1,1], [4,4]
updates = 2,3
```どちらのセグメントも触れられていないため、正解は次のとおりです。`-1`。 

## アプローチ

 直接シミュレーションは簡単です。 更新するたびに、新しい位置を次のようにマークします。`1`、次にすべてのセグメントを調べます。 各セグメントについて、現在含まれているセグメントの数を数え、その数がセグメントの長さの半分を超えているかどうかを確認します。 

ブルート フォース バージョンは文字通り定義を実装しているため、正しいです。 問題はコストです。 と`q`アップデートと`m`セグメント内でのカウントが定数時間だったとしても、引き続き実行します。`m × q`小切手。 最悪の場合、これはおおよそ次のようになります`10^10`まったく実行不可能な操作です。 

転換点は、「あるセグメントが美しい」という性質が単調であることを観察したときに起こります。 

最初の後の場合`k`更新によって一部のセグメントは美しくなりますが、更新回数が増えても、更新はセグメントを追加するだけであるため、美しいままになります。 これは、単調述語が true になる最初の位置が答えであることを意味します。 

問題で単調条件が現れる最も早い点を求めるときは常に、二分探索が自然な候補になります。 

値を推測するとします`mid`。 私たちはこう尋ねます:

 > 最初の適用後`mid`更新情報、美しいセグメントは存在しますか?

 これに効率的に答えるために、最初の位置のうちどの位置がアクティブ化されたかをマークする配列を構築します。`mid`更新情報。 プレフィックスの合計により、任意のセグメント内の 1 の数を一定時間で計算できます。 

セグメントの場合`[l,r]`:$$\text{ones} = pref[r] - pref[l-1]$$次の場合、セグメントは美しくなります。$$\text{ones} > (r-l+1) - \text{ones}$$全セグメントのコストを確認する`O(m)`、およびプレフィックス合計コストの構築`O(n)`。 

したがって、述語は次のように評価できます。`O(n+m)`時間。 それを二分探索と組み合わせると、`q`更新により、受け入れられる解決策が提供されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(qm) 以上 | O(n) | 遅すぎる |
 | 最適 | O((n + m) log q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべてのセグメントとすべての更新位置を読み取ります。 
2. 関数を定義する`check(k)`最初の適用後に一部のセグメントが美しいかどうかを判断します`k`更新情報。 
3. 内部`check(k)`、長さの配列を作成します`n`ゼロで初期化されます。 
4. 最初のマークを付けます`k`として位置を更新しました`1`。 
5. このバイナリ配列に対してプレフィックス合計配列を構築します。 
6. セグメントごとに`[l,r]`、プレフィックスの合計を使用して、その中の 1 の数を計算します。 
7. しましょう`length = r - l + 1`。 1 の数が厳密に より大きい場合`length / 2`、すぐに戻ります`True`。 
8. 条件を満たすセグメントがない場合は、リターンします。`False`。 
9. 二分探索の前に、評価します。`check(q)`。 false の場合、どのセグメントも美しくならないので、出力します。`-1`。 
10. それ以外の場合は、答えを二分探索します。 述語が真である最小の更新数を維持します。 
11. 左端の有効な更新番号を出力します。 

### なぜ効果があるのか

 によってチェックされる述語`check(k)`は:

 > 最初のセグメントの後に少なくとも 1 つのセグメントが美しい`k`更新情報。 

さらに更新を適用すると、各セグメントの 1 の数が増えるだけです。 美しいセグメントが後で美しくなくなることはありません。 したがって、述語は単調です。一度 true になると、永遠に true のままになります。 

プレフィックスの合計は、各セグメント内のアクティブ化された位置の正確な数を計算します。`check(k)`問題の条件が満たされた場合に、正確に true を返します。`k`更新情報。 

単調述語の二分探索では、述語が true になる最小のインデックスが常に見つかります。 このインデックスは、正確には、一部のセグメントが美しくなる最初の更新です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())

    for _ in range(t):
        n, m = map(int, input().split())

        segments = []
        for _ in range(m):
            l, r = map(int, input().split())
            segments.append((l, r))

        q = int(input())
        queries = [int(input()) for _ in range(q)]

        def check(k):
            arr = [0] * (n + 1)

            for i in range(k):
                arr[queries[i]] = 1

            pref = [0] * (n + 1)
            for i in range(1, n + 1):
                pref[i] = pref[i - 1] + arr[i]

            for l, r in segments:
                ones = pref[r] - pref[l - 1]
                length = r - l + 1

                if ones * 2 > length:
                    return True

            return False

        if not check(q):
            print(-1)
            continue

        lo, hi = 1, q
        ans = q

        while lo <= hi:
            mid = (lo + hi) // 2

            if check(mid):
                ans = mid
                hi = mid - 1
            else:
                lo = mid + 1

        print(ans)

if __name__ == "__main__":
    solve()
```解決策は以下を中心に展開します`check`関数。 最初の配列の後に配列状態を再構築します。`k`更新後、プレフィックス合計配列を使用して、一定時間内にセグメント数のクエリに応答します。 

条件```
ones * 2 > length
```これは、1 の数が 0 の数を超えているかどうかを確認することと同じです。 乗算を使用すると、整数の除算に関する問題が回避されます。 

二分探索では、次の最初の値が検索されます。`k`誰のために`check(k)`trueを返します。 述語は単調であるため、標準の左端の真の二分探索が直接適用されます。 

間違いやすい実装の詳細の 1 つはインデックス付けです。 セグメントのインデックスは 1 であるため、プレフィックス合計配列もインデックスが 1 として構築されます。 これにより式が成り立ちます```
pref[r] - pref[l - 1]
```自然に働きます。 

もう一つの微妙な点はチェックです`check(q)`二分探索前。 すべての更新後でも述語が false の場合、二分探索では有効な答えが得られません。 このケースを個別に処理すると、検索ロジックが単純になります。 

## 実用的な例

 ### 例 1

 入力:```
n = 5
segments = [1,2], [4,5], [1,5], [1,3], [2,4]
updates = 5,3,1,2,4
```二分探索の評価:

 | k | アクティブなポジション | 美しいセグメントは存在しますか? |
 | --- | --- | --- |
 | 3 | {1,3,5} | はい |
 | 1 | {5} | いいえ |
 | 2 | {3,5} | いいえ |

 検索で最初に発見されるのは、`k=3`動作します。 次に、どちらでもないことを検証します`1`または`2`動作します。 有効な最小値は次のとおりです。`3`。 

この例は、述語の単調な性質を示しています。 一度`k=3`が有効になっても、それより大きな値はすべて有効のままです。 

### 例 2

 入力:```
n = 4
segments = [1,1], [4,4]
updates = 2,3
```状態の進化:

 | k | アクティブなポジション | セグメント [1,1] | セグメント [4,4] | 存在しますか？ |
 | --- | --- | --- | --- | --- |
 | 1 | {2} | 0 件 | 0 件 | いいえ |
 | 2 | {2,3} | 0 件 | 0 件 | いいえ |

 すべての更新を行っても、どちらの監視位置も変化しません`1`。 

予備的な`check(q)`失敗するので、答えは`-1`。 

この例は、二分探索を開始する前にアルゴリズムが完全チェック テストを実行する理由を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + m) log q) | 各述語の評価では配列とすべてのセグメントがスキャンされ、二分探索では O(log q) の評価が実行されます。 
| スペース | O(n) | アクティベーション ステータスとプレフィックスの合計の配列 |

 の合計額`n`テストケース全体では最大でも`10^5`。 各二分探索反復では、線形作業が実行されます。`n + m`、反復回数は最大でも約 17 回です。`q ≤ 10^5`。 これは制限時間内に問題なく収まり、リニア メモリのみを使用します。

## 特殊なケース

 長さが偶数のセグメントを考えてみましょう。```
