 ## 解決策
 ## 問題の理解

 左から右に文字のインデックスが付けられた文字列と、現在の文字列の指定されたセグメントから特定の文字を繰り返し削除する一連の操作が与えられます。 各操作により、現在のすでに縮小している文字列内のセグメントと文字タイプが与えられます。 そのセグメント内では、その文字が出現するたびに削除されますが、他のすべての文字はそのまま残ります。 削除によって位置が変更されるため、後の操作では常に、以前のすべての削除後に更新された文字列が参照されます。 

出力は、すべての削除が順番に適用された後の単なる最終文字列です。 

制約が十分に大きいため、文字列のスキャンと再構築を繰り返して物理的に削除をシミュレートするソリューションは遅すぎます。 n と m は両方とも最大 200,000 であるため、操作ごとに各文字を扱う単純なアプローチでは二次関数の動作が発生します。 わずかに最適化された繰り返しスライスであっても、最悪の場合、限界をはるかに超える O(nm) まで劣化する可能性があります。 

主な問題は、削除がグローバルではなく、各操作後に変更される動的な位置に依存することです。 このため、明示的に変更可能な文字列を維持して文字を直接消去したくなりますが、その場合は文字列の大部分を繰り返しシフトする必要があります。 

いくつかの特殊なケースでは、単純なシミュレーションの落とし穴が明らかになります。 すべての操作が広い範囲にわたる同じ文字をターゲットにしている場合、文字列は徐々に縮小する可能性があり、コピーを繰り返すと致命的な結果になります。 たとえば、次のように始めます。`"aaaaa"`そして繰り返し削除する`'a'`プレフィックスを過度に縮小すると、フル スキャンとシフトが繰り返され、二次カスケードが生成されます。 

もう 1 つの微妙なケースは、操作が大きく重複しているものの、異なる文字に影響を与える場合に発生します。 単純な操作ごとのスキャンでは、すでに「論理的に削除」された文字を繰り返し再訪問する可能性があり、削除を注意深く追跡しない限り時間を無駄にします。 

## アプローチ

 直接シミュレーションでは、文字列を変更可能な構造に保持し、操作ごとに位置 l から r をスキャンして、一致する文字を削除します。 これは問題定義に正確に従っているため、論理的には正しいです。 ただし、削除するたびに文字を移動する必要があり、各文字は操作中に何度も検査される可能性があります。 最悪の場合、各操作に O(n) のコストがかかり、結果として O(nm) になる可能性があります。 

重要な観察は、キャラクターは決して再導入されることはなく、削除されるだけであるということです。 これにより、視点を逆転させることができます。縮小する文字列を繰り返し変更する代わりに、元の文字ごとに、すべての操作が存続するかどうかを判断します。 

操作を逆の順序で処理します。 すべての操作後にどの文字が生き残るかがわかっている場合、プロセスを逆にすると、最終的な空の削除状態から開始し、削除を逆方向に「復元」することになります。 逆に、操作は、その操作によって削除された文字を「復活させる」ことに相当しますが、それは、後の操作によってまだブロックされていない場合に限ります。 これをポジションで直接管理するのは困難になります。 

より実用的な観点は、セグメント ツリー (または追加のロジックを備えたバイナリ インデックス構造) を使用して、現在のフィルター処理された文字列内でどの元の位置がまだ「生きている」かを維持することです。 各操作は、元のインデックスではなく、現在の文字列の動的連続セグメントにのみ影響するため、現在の位置を元の位置に効率的にマップする必要があります。 

これは、元のインデックスに対してセグメント ツリーを維持することによって実現され、各ノードはその範囲内に残っている生きている文字の数を追跡します。 次に、O(log n) で k 番目の生存位置を見つけることができます。 各操作 [l, r, c] は、最初に l 番目と r 番目の生きている文字に対応する実際の元のインデックスを見つけてから、現在文字 c を含み、その範囲内にある位置のみを反復処理することによって処理されます。 文字による高速検索をサポートするために、26 + 26 + 10 個の個別の順序付けられたアクティブなポジションのセットを維持します。 

各削除は、セグメント ツリーと文字セットの両方から対応するインデックスを削除することによって適用されます。 各位置は最大 1 回削除されるため、合計の削除は直線的になります。 

この構造が機能するのは、非アクティブな文字を決してスキャンせず、すべての削除が O(log n) であるため、全体の複雑さが管理可能になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | O(n) | 遅すぎる |
 | 最適 (セグメント ツリー + セット) | O((n + m) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは 2 つの構造を維持します。1 つは元のインデックスがまだ存在しているかを追跡するセグメント ツリーで、もう 1 つは各文字から、その文字が現在生きているソートされたインデックスのセットへのマップです。 

指定された順序で操作を処理します。 

1. 演算 (l、r、c) の場合、セグメント ツリーを使用して、まず l と r を「現在の文字列位置」から元のインデックスに変換します。 これは、l 番目と r 番目の生存位置を見つけることによって行われます。 
2. 元のインデックス境界を取得したら、元のインデックスがこの範囲内にある文字 c のすべての出現を反復処理します。 
3. このようなインデックスごとにセグメント ツリーから削除します。つまり、インデックスは文字列の一部ではなくなります。 
4. 再度処理できないように、キャラクターのセットからも削除します。 
5. 文字 c の有効なインデックスが区間内に残らなくなるまで続行します。 

セグメント ツリーにより、削除が何度も行われた後でも、「現在位置」と「元のインデックス」の間の変換が効率的に維持されることが保証されます。 

### なぜ効果があるのか

すべてのステップで、セグメント ツリーは現在の文字列位置と残っている元のインデックスの間の正確な対応を表します。 文字セットは、生き残った位置を文字ごとに分割します。 各削除は永続的であり、各インデックスは 1 回だけ削除されるため、どの操作によっても削除された文字が誤って再導入されたり、残っている文字がスキップされたりする可能性はありません。 不変条件は、セグメント ツリーが元のインデックスの任意の間隔で生きている文字を常に正確にカウントし、セットには特定の文字でまだ生きているインデックスが常に正確に含まれていることです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def kth(self, k):
        idx = 0
        bitmask = 1 << (self.n.bit_length())
        while bitmask:
            nxt = idx + bitmask
            if nxt <= self.n and self.bit[nxt] < k:
                k -= self.bit[nxt]
                idx = nxt
            bitmask >>= 1
        return idx + 1

n, m = map(int, input().split())
s = input().strip()

fen = Fenwick(n)

pos = {}
for i, ch in enumerate(s, 1):
    fen.add(i, 1)
    pos.setdefault(ch, set()).add(i)

for _ in range(m):
    l, r, c = input().split()
    l = int(l)
    r = int(r)

    if c not in pos:
        continue

    total = fen.sum(n)
    if l > total:
        continue

    left_idx = fen.kth(l)
    right_idx = fen.kth(r)

    remove_list = []
    for i in list(pos[c]):
        if left_idx <= i <= right_idx:
            remove_list.append(i)

    for i in remove_list:
        fen.add(i, -1)
        pos[c].remove(i)

ans = []
for i in range(1, n + 1):
    if fen.sum(i) - fen.sum(i - 1) == 1:
        ans.append(s[i - 1])

print("".join(ans))
```フェンウィック ツリーは、元の文字列のプレフィックス範囲内で生き残っている文字の数を維持します。 k 番目の関数は、現在の文字列内の位置を元のインデックスに変換します。これは、操作が固定インデックスではなく動的位置に対して定義されているため、不可欠です。 

セットの辞書は各文字の現在有効なインデックスをすべて追跡するため、関連する位置のみの削除を制限できます。 

各操作中に、まず操作範囲を元のインデックスにマッピングします。 次に、ターゲット文字にまだ対応しているインデックスのみをスキャンし、間隔内のインデックスを削除します。 各インデックスは一度削除されるため、セット内で反復処理を行いますが、合計作業量はすべての操作にわたって線形のままです。

これにより、削除後に位置の再マッピングが正しく機能することが確認されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + m) log n) | 削除するたびにフェンウィックが更新され、一度設定されます。 
| スペース | O(n) | フェンウィック ツリーとキャラクター位置セットのストレージ |

 すべての操作は対数的な作業とキャラクターごとの償却定数除去のみを実行するため、この解は制限内に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    class Fenwick:
        def __init__(self, n):
            self.n = n
            self.bit = [0] * (n + 1)

        def add(self, i, v):
            while i <= self.n:
                self.bit[i] += v
                i += i & -i

        def sum(self, i):
            s = 0
            while i > 0:
                s += self.bit[i]
                i -= i & -i
            return s

        def kth(self, k):
            idx = 0
            bitmask = 1 << (self.n.bit_length())
            while bitmask:
                nxt = idx + bitmask
                if nxt <= self.n and self.bit[nxt] < k:
                    k -= self.bit[nxt]
                    idx = nxt
                bitmask >>= 1
            return idx + 1

    n, m = map(int, input().split())
    s = input().strip()

    fen = Fenwick(n)
    pos = {}

    for i, ch in enumerate(s, 1):
        fen.add(i, 1)
        pos.setdefault(ch, set()).add(i)

    for _ in range(m):
        l, r, c = input().split()
        l = int(l)
        r = int(r)

        if c not in pos:
            continue

        total = fen.sum(n)
        if l > total:
            continue

        left = fen.kth(l)
        right = fen.kth(r)

        to_remove = []
        for i in list(pos[c]):
            if left <= i <= right:
                to_remove.append(i)

        for i in to_remove:
            fen.add(i, -1)
            pos[c].remove(i)

    return "".join(s[i-1] for i in range(1, n+1) if fen.sum(i)-fen.sum(i-1) == 1)

# provided sample
assert run("4 2\nabac\n1 3 a\n2 2 c\n") == "b"

# custom cases
assert run("1 1\na\n1 1 a\n") == ""
assert run("3 2\nabc\n1 3 a\n1 3 a\n") == "bc"
assert run("5 1\nabcde\n1 5 z\n") == "abcde"
assert run("6 2\naaaAAA\n1 6 a\n1 6 A\n") == ""

 | --- | --- | --- |
 | 単一の削除 | 空 | 完全除去エッジ |
 | 同じ操作を繰り返しました | 紀元前 | 冪等な削除 |
 | no-op キャラクター | ABCDE | 欠落文字の処理 |

 ## 特殊なケース

 完全に削除されたケースは、終了の正確さを示します。 入力用`"a", 1 1 a`、フェンウィック ツリーは 1 つの生存位置から始まります。 k 番目のマッピングはインデックス 1 を返し、削除され、最後の走査では生きている位置が見つからず、空の文字列が生成されます。 

同一の操作を繰り返すと、冪等性がテストされます。 のために`"abc"`の 2 つの同一の欠失を伴う`'a'`全範囲にわたって、最初の実行ではインデックス 1 が削除され、2 番目の実行では生き残っているものが見つかりません。`'a'`セット内にあるため、何も機能しません。 最後の文字列が残ります`"bc"`。 

次のような no-op 文字のケース`"abcde"`の除去とともに`'z'`文字セットが空であるため、削除ループに入ることはありません。そのため、フェンウィック構造は変更されず、出力は元の文字列になります。 

大文字と小文字が混在した処理により、次のことが保証されます。`'a'`そして`'A'`異なるセットで個別に追跡されるため、削除が文字クラスを誤って横断することはありません。
