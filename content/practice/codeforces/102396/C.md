 ## 解決策
 ## 問題の理解

 都市を、現在利用可能な鉄道路線をエッジとする無向グラフの頂点と考えてください。 ルートは双方向であるため、2 つの都市がこのグラフの同じ接続コンポーネントに属している場合、それらの都市は正確に相互に到達できます。 

同じ頂点上に 2 番目の無向グラフがあり、友情を表しています。 お問い合わせの場合`? v`、頂点の数が必要です`u`そのような`u`の友人です`v`そして`u`同じ接続コンポーネント内にあります`v`トレイングラフで。 現在連絡できない友人もいる可能性があるため、答えは友人の総数ではありません。 

2種類のアップデートが可能です。 あ`T a b`この操作ではトレイン エッジが挿入されるため、以前は別々だった 2 つのトレイン コンポーネントが結合される可能性があります。 アン`F a b`操作により友情エッジが挿入されます。 どちらのタイプのエッジも削除されることはなく、これが増分接続ソリューションを可能にする構造的特性です。 

初期入力には、最大 (10^5) 個の都市、(10^5) 個の友人関係、(10^5) 個の鉄道路線、および (10^5) 個の後続の運行が含まれます。 すべてのクエリに対してすべての都市またはすべての友人関係をスキャンするソリューションには、最大 (10^{10}) 回の操作が必要となり、2 秒の制限をはるかに超えます。 対数係数を許容できる、ほぼ線形またはほぼ線形の総作業量が必要です。 

直接実装を騙す可能性のあるエッジケースがいくつかあります。 まず、友情は、そのエンドポイントが列車に接続される前に存在することができます。 例えば：```
2 1 0
1 2
0
```鉄道路線がないため、出力はありません。 代わりにクエリを追加すると、次のようになります。```
2 1 0
1 2
1
? 1
```出力は`0`、都市1と都市2は友人であるにもかかわらず。 電車の接続状況を確認せずに友人関係をカウントするソリューションでは、誤って印刷される可能性があります。`1`。 

次に、新たに追加された友情により、すでに到達可能な 2 つの都市を接続できます。```
2 0 1
1 2
1
F 1 2
```クエリはありませんが、友情が挿入されると、両方のエンドポイントの貢献度がすぐに 1 になります。 トレイン エッジが追加されたときにのみ実装が友情を処理する場合、この更新は失われます。 

第三に、トレイン エッジが 2 つのコンポーネントを結合すると、複数の既存の友情が同時に有効になる可能性があります。 例えば：```
4 2 1
1 3
2 4
1 2
1
? 1
```トレイン グラフは 1 と 2 を接続しますが、3 と 4 はそのコンポーネントの外側にあります。 都市 1 には連絡可能な友人がいないため、答えは次のようになります。`0`。 トレインのエッジが 1 と 3 を含むコンポーネントを結合する場合、友情は`(1,3)`すぐに有効になります。 新しいトレイン エッジの 2 つの端点のみをチェックする不注意な実装では、マージされた 2 つのコンポーネントの任意の頂点間の友情関係を見逃す可能性があります。 

## アプローチ

 ブルートフォースアプローチは簡単です。 トレイン グラフを維持し、クエリごとに`? v`から DFS または BFS を実行します。`v`現在の連結成分を決定します。 それから彼らのすべての友情を調べてください`v`そして、エンドポイントが訪問された人をカウントします。 これは正しいです。DFS は、から到達可能な都市を正確に識別します。`v`。 

問題はコストです。 最悪の場合、1 回の接続性検索で (O(n+k+q)) 個の頂点とエッジが検出される可能性があり、(10^5) 個のクエリが発生する可能性があります。 十分に密度の高い一連の操作では、(10^{10}) 個のグラフ操作が行われますが、これでは遅すぎます。 

より良い出発点は、トレイン エッジが挿入されるだけであるという事実を利用することです。 接続されたコンポーネントは、素のセット ユニオン構造 (DSU) で維持できます。 クエリ`? v`現在の列車コンポーネントを即座に識別できます`v`。 

残りの問題は、コンポーネント内に各頂点の友人が何人いるかを維持することです。 させて`ans[v]`まさにその数字になります。 友情のとき`(a,b)`が挿入された場合、可能性は 2 つだけです。 もし`a`そして`b`すでに同じ列車コンポーネントに属している場合、両方の答えが 1 ずつ増加します。 そうしないと、友情はまだ役に立ちませんが、将来の列車の併合によって役立つ可能性があるため、覚えておく必要があります。 

列車のエッジが 2 つの異なるコンポーネントを結合すると仮定します。 これら 2 つのコンポーネントをまたぐすべての友情は、マージ後に有効になります。 2 つのコンポーネント間のすべての関係を検査することもできますが、単純にそれを行うと、巨大なコンポーネントを繰り返しスキャンする可能性があります。 

重要な点は、常に小さいコンポーネントを処理することです。 すべての DSU コンポーネントに属する頂点のリストを保存します。 2 つのコンポーネントをマージする場合、小さい方のコンポーネントのすべての頂点を反復処理し、そのすべての友情エッジを検査します。 もう一方のエンドポイントがより大きなコンポーネントにある友情はカットを越えて有効になるため、両方のエンドポイントの回答を増加させます。 

なぜこれで十分速いのでしょうか? コンポーネントのマージ中に頂点が処理されるときは常に、頂点は小さい方のコンポーネントに属していました。 マージ後、そのコンポーネントのサイズは少なくとも 2 倍になりました。 したがって、特定の頂点は最大でも (O(\log n)) 回小さい側に属することができます。 頂点が処理されるたびに、その友情隣接リストがスキャンされるため、各友情隣接関係は合計で (O(\log n)) 回だけスキャンされます。 

これにより、問題の公式分析で使用されるのと同じ大小のアイデアが得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O(q(n+m+k))) | (O(n+m+k)) | 遅すぎる |
 | 最適 | (O((m+q+k)\log n\cdot\alpha(n)) | (O(n+m+k)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべて (n) の都市を含む DSU を作成します。 すべてのコンポーネントについて、現在の頂点リストを維持します。 最初は、すべてのコンポーネントに 1 つの都市が含まれています。 
2. すべての友情を隣接リストに保存する`friends[v]`。 それぞれの友情`(a,b)`に 1 回、2 回保存されます。`friends[a]`そして一度入ったら`friends[b]`後で頂点のすべての友人を検査する必要があるためです。 
3. 最初の列車ルートを DSU に追加します。 トレイン エッジは接続を追加するだけであるため、DSU はすべての初期ルートが挿入された後に正確な接続コンポーネントを表すことができます。 
4.初期化`ans[v]`最初の友情をすべて処理することで`(a,b)`。 もし`a`そして`b`同じ DSU ルートを持っている場合は、両方をインクリメントします`ans[a]`そして`ans[b]`。 この時点で`ans[v]`は、現在連絡可能な友人の数と同じです`v`。 
5.`F a b`操作、追加`b`に`friends[a]`そして`a`に`friends[b]`。 2 つのエンドポイントが現在同じ DSU ルートを持っている場合は、インクリメントします。`ans[a]`そして`ans[b]`。 コンポーネントが異なる場合は、まだ回答を変更しないでください。コンポーネントが結合された後でのみ友情が有効になるためです。 
6. のために`T a b`操作、ルーツを見つける`a`そして`b`。 それらがすでに等しい場合、新しいルートでは接続も応答も変更されないため、操作は終了します。 
7. ルートが異なる場合は、コンポーネントのサイズを比較し、小さい方を次のルートとして指定します。`small`そして大きいものは`large`。 のメンバーリストは、`small`列挙する必要がある唯一のコンポーネントです。 
8. DSU の親を変更する前に、すべての頂点を反復処理します。`v`で`small`そしてすべての友達`u`の`v`。 もし`u`現在所属している`large`、 それから`(v,u)`それは2つの要素を超えた友情です。 新しい鉄道ルートを挿入すると、2 つの都市が相互にアクセス可能になるため、両方の都市を増分します。`ans[v]`そして`ans[u]`。 
9. マージ`small`の中へ`large`DSU 内に頂点を追加します。`small`のメンバーリストへ`large`。 コンポーネントのサイズも、2 つの古いサイズの合計になります。 
10. のために`? v`操作、印刷`ans[v]`。 この値に影響を与える可能性のあるすべての変更は、対応する友情または列車のマージが発生したときにすでに処理されているため、グラフのトラバースは必要ありません。 

### なぜ効果があるのか

 不変条件は、処理されたすべての操作の後に、`ans[v]`発生する友情エッジの数に等しい`v`もう一方のエンドポイントは、同じ現在のトレイン コンポーネント内にあります。`v`。 

新しく挿入された友情は、そのエンドポイントがすでに接続されているときにすぐにカウントされます。 接続されていない場合、友情関係は両方の隣接リストに保存され、後のコンポーネントのマージに使用できるようになります。 

2 つの列車コンポーネントがマージされる場合、ステータスが変更される可能性がある友情は、各コンポーネント内の 1 つのエンドポイントとの友情だけです。 より小さいコンポーネントのすべての頂点とそのすべての友情を検査するため、交差するすべての友情が見つかります。 内部の友情はすでにカウントされていますが、両方のコンポーネントの外部への友情は無効のままです。 したがって、新しく有効になったすべての友情は、両方のエンドポイントの回答に 1 回だけ寄与します。 

併合後、DSU は新しい列車の接続を表すため、不変式が再び保持されます。 すべての操作はエッジを追加するだけなので、以前に有効だった友情が無効になることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())

    friends = [[] for _ in range(n)]
    friendship_edges = []

    for _ in range(m):
        a, b = map(int, input().split())
        a -= 1
        b -= 1
        friends[a].append(b)
        friends[b].append(a)
        friendship_edges.append((a, b))

    parent = list(range(n))
    size = [1] * n
    members = [[i] for i in range(n)]

    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x

    def merge(a, b):
        a = find(a)
        b = find(b)
        if a == b:
            return a

        if size[a] < size[b]:
            a, b = b, a

        parent[b] = a
        size[a] += size[b]
        members[a].extend(members[b])
        members[b] = []
        return a

    for _ in range(k):
        a, b = map(int, input().split())
        merge(a - 1, b - 1)

    ans = [0] * n

    for a, b in friendship_edges:
        if find(a) == find(b):
            ans[a] += 1
            ans[b] += 1

    q = int(input())
    out = []

    for _ in range(q):
        parts = input().split()
        typ = parts[0]

        if typ == '?':
            v = int(parts[1]) - 1
            out.append(str(ans[v]))

        elif typ == 'F':
            a = int(parts[1]) - 1
            b = int(parts[2]) - 1

            friends[a].append(b)
            friends[b].append(a)

            if find(a) == find(b):
                ans[a] += 1
                ans[b] += 1

        else:
            a = int(parts[1]) - 1
            b = int(parts[2]) - 1

            ra = find(a)
            rb = find(b)

            if ra == rb:
                continue

            if size[ra] > size[rb]:
                large, small = ra, rb
            else:
                large, small = rb, ra

            for v in members[small]:
                for u in friends[v]:
                    if find(u) == large:
                        ans[v] += 1
                        ans[u] += 1

            parent[small] = large
            size[large] += size[small]
            members[large].extend(members[small])
            members[small] = []

    sys.stdout.write('\n'.join(out))

if __name__ == "__main__":
    solve()
```初期列車ルートによって開始接続コンポーネントが決定されるため、DSU は初期友情が評価される前に初期化されます。 初期の友情エッジは個別に保存されるため、すべての初期の列車ルートが挿入された後に評価できます。 

の`members`array は、小規模から大規模へのマージを可能にする追加の構造です。 DSU だけでも 2 つの頂点が接続されているかどうかを知ることができますが、コンポーネントに属するすべての頂点を効率的に列挙することはできません。 メンバー リストは、欠落している操作を正確に提供します。 

列車の合流内の順序は微妙です。 小さいコンポーネントは、親が変更される前にスキャンされます。 このスキャン中に、`find(u) == large`ということです`u`実際にはマージ前は他のコンポーネントに属していました。 最初に親を変更した場合、両方の頂点間の友情は`small`友人関係を超えたと誤解され、2 回カウントされる可能性があります。 

の`F`この操作により、接続に関係なく友情隣接リストが更新されます。 友情は、エンドポイントが切断されても保存されたままにしておく必要があります。`T`操作により有効になる場合があります。 

すべてのカウントは Python の整数に快適に収まります。 C++ では、答えは最大 (n-1) であるため、通常の 32 ビット符号付き整数でも十分ですが、Python では整数オーバーフローの心配はありません。 

反復`find`再帰オーバーヘッドを回避し、パス圧縮を実行します。 コンポーネント サイズによるユニオンでは、メンバー リストが常に小さいリストから大きいリストにマージされることが保証されます。 

## 実用的な例

 ### サンプル 1

 最初のトレイン エッジは次のとおりです。`(1,2)`そして`(1,4)`、したがって、列車のコンポーネントは次のようになります。`{1,2,4}`そして`{3}`。 初期の友人関係は、`(1,2)`そして`(1,3)`。 のみ`(1,2)`都市 1 のコンポーネント内にあるため、`ans[1]`1から始まります。 

| 操作 | コンポーネント | 新しい友情効果 |`ans[1]`|

 最後のトレインの挿入では、より小さなコンポーネントがスキャンされます`{3}`。 その唯一の友好関係は、他のコンポーネントに属する都市 1 とのものであるため、`(3,1)`到達可能になり、`ans[1]`2個から3個に増えます。

            if ra == rb:
                continue

            if size[ra] >= size[rb]:
                large, small = ra, rb
            else:
                large, small = rb, ra

            for v in members[small]:
                for u in friends[v]:
                    if find(u) == large:
                        ans[v] += 1
                        ans[u] += 1

            parent[small] = large
            size[large] += size[small]
            members[large].extend(members[small])
            members[small] = []

    return '\n'.join(out)

def run(inp: str) -> str:
    old_stdin = sys.stdin
    sys.stdin = io.StringIO(inp)
    try:
        return solve()
    finally:
        sys.stdin = old_stdin

 ## 特殊なケース

 ### 友情は存在するが、都市は切り離されている

 次のことを考慮してください。```
2 1 0
1 2
1
? 1
```友情隣接リストには都市 1 に対して都市 2 が含まれていますが、`find(1)`そして`find(2)`は異なります。 最初の友情は何の役にも立たない`ans[1]`、クエリは次のように出力されます`0`。 後であれば`T 1 2`操作が発生し、小さいコンポーネントに 1 つの都市が含まれ、他のコンポーネントとの友好関係がマージ中に検出されます。`ans[1]`になる`1`。 

### フレンドシップは既存の列車コンポーネント内に追加されます

 次のことを考慮してください。```
2 0 1
1 2
2
F 1 2
? 1
```最初の鉄道ルートでは、両方の都市が同じ DSU ルートの下に置かれます。 いつ`F 1 2`が処理されるとルートが一致するため、両方の答えがすぐに増分されます。 クエリが出力されます`1`。 

### 列車の併合で多くの旧交が活性化

 次のことを考慮してください。```
4 2 1
1 3
1 4
1 2
2
? 1
T 2 3
```最初は都市 1 が属しています`{1,2}`、都市 3 と都市 4 は別々です。 最初のクエリが出力されます`0`。 いつ`T 2 3`挿入され、`{1,2}`と合併する`{3}`。 小さい方のコンポーネントは、`{3}`、その友情リストには都市 1 が含まれています。マージは増分します。`ans[3]`そして`ans[1]`、だから友情は`(1,3)`がカウントされるようになりました。 

同じメカニズムが、任意の多くの交差する友情を処理します。 小さいコンポーネントに (x) 個の頂点が含まれ、そのフレンドシップ リストに (r) 個の関連エッジが含まれている場合、マージ中にすべての (r) 個のエッジが処理されます。 

### トレインエッジは、同じコンポーネント内にある都市を接続します

 次のことを考慮してください。```
3 1 2
1 3
1 2
2 3
1
? 1
```2 番目の列車の端が考慮される前に、3 つの都市はすべてすでに接続されています。 2 と 3 の DSU ルートは等しいため、2 番目のエッジではスキャンも応答の変更も発生しません。 都市 1 には都市 3 という友人が 1 人いるため、クエリは次のように出力されます。`1`。 

無視する`ra == rb`この場合、新しい接続がないにもかかわらずコンポーネントがスキャンされると、不必要な作業が発生し、間違った繰り返しカウントが発生する可能性があります。 

### 小さいコンポーネントはマージごとに変化します

 鉄道グラフが最初は 5 つの孤立した都市であり、ルートが次のように挿入されているとします。`(1,2)`、`(3,4)`、`(1,3)`、`(1,5)`。 最初の 2 つのマージは、1 つの都市のコンポーネントを処理します。 3 番目のマージでは、1 つの 2 都市コンポーネントを別の 2 都市コンポーネントに対して処理します。 4 番目のマージでは、5 を含む 1 つの都市コンポーネントを、すでに大きいコンポーネントに対して処理します。 

都市が小さい側になるのは、そのコンポーネントのサイズが結果として得られるコンポーネントのサイズの最大でも半分の場合のみです。 このようなイベントはすべて、そのコンポーネントのサイズが少なくとも 2 倍になります。 サイズ 1 から開始すると、これは最大 (\lfloor\log_2 n\rfloor) 回発生する可能性があり、これが、繰り返される友情スキャンが制限されたままになる理由です。
