 ## 解決策
 ## 問題の理解

 n 行 m 列の長方形のセル配置が与えられています。 各行 i には最初、左側に詰め込まれた ai 石のブロックが含まれているため、行 i では列 1 から ai までが埋められ、残りのセルは空になります。 説明されている操作は、列方向に適用される重力に似た変換です。すべての石は、それぞれの列の可能な限り低い空の位置に到達するまで、垂直下に落下します。 

この落下プロセスが安定した後、各柱はその柱にもともと存在していた数の石で単純に底から満たされ、空いたスペースは上部に残ります。 タスクは、この再構成後に各行に最終的にいくつの石が入るかを計算することです。 

主な難点は、初期状態が圧縮された行単位の形式で与えられるが、降下プロセスは列駆動であるため、頭の中で構造を置き換える必要があることです。 

制約 n、m ≤ 10^4 は、明示的なグリッドに対する O(nm) シミュレーションでは、最悪の場合、時間とメモリの両方が大きすぎることを意味します。 完全なシミュレーションには最大 10^8 セルが必要ですが、厳しい制限の下では Python では境界線に達するか安全ではありません。 これにより、明示的なグリッドではなくカウントについて推論する方向に進みます。 

行の ai 値が大きく異なる場合、微妙なエッジ ケースが発生します。 たとえば、n = 3、m = 5、および a = [5, 1, 1] の場合、最初の行はすべての列にわたって多くの石に貢献しますが、下位の行は最初の列にのみ貢献します。 落下後、列の高さは大幅に異なり、列方向の蓄積を明示的に考慮しない限り、素朴な行ごとの再配分では石の位置が間違ってしまう可能性があります。 

もう 1 つの障害モードは、行が独立してカウントを保持しているという誤った仮定から発生します。 たとえば、落ちると石が列間に再配分されるため、各列に AI 石が保持されると考えるのは間違いです。 

## アプローチ

 ブルートフォース解釈では、明示的なグリッドを構築し、すべての AI で左揃えの石をマークし、列ごとに、または安定するまで繰り返し石を押し下げることによって重力を繰り返しシミュレートします。 これは文字通りプロセス定義に従っているため、これは正しいです。 ただし、グリッドには最大 n × m 個のセルを含めることができ、各シミュレーション ステップでは列を複数回スキャンするか、セルごとの移動を実行する必要がある場合があります。 最悪の場合、すべてのセルが複数回処理され、実装のオーバーヘッドに応じてメモリがおよそ O(nm) になり、場合によっては O(nm) 以上の時間がかかる可能性があります。 n と m が 10^4 までの場合、これは大きくなりすぎます。 

重要な観察は、最終的な構成は列の合計のみに依存し、石が最初に列内にどのように配分されたかには依存しないということです。 各行 i は、最初の a_i 列に分散された a_i 石を提供します。 視点を逆にすると、各列 j は、a_i ≥ j となる行数 i を正確に受け取ります。 列の合計がわかったら、重力はこれらの合計を行にソートするだけです。最終的に各行 i は、高さが少なくとも i に達する列の合計数を受け取ります。 

したがって、動きをシミュレートする代わりに、列の高さにわたる頻度配列を計算し、それをサフィックスの累積を使用して行数に変換します。

 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | O(nm) | 遅すぎる |
 | 最適 | O(n + m) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. サイズ m の配列 cnt を構築します。ここで、cnt[j] は、ai ≥ j + 1 を持つ行の数を数えます。これは、落ちる前に列 j + 1 に出現する石の数に対応します。 このステップでは、明示的なグリッド構築をカウントの視点に置き換えます。 
2. 1 から n までの各行 i について、少なくとも i 個の石がある列が何列あるかを知りたいと思います。 その数は正確に cnt[i - 1] です。 これが機能するのは、列が少なくとも i 以上の高さを持っている場合に限り、落下後に列が行 i に寄与するからです。 
3. 最終行数として cnt[0]、cnt[1]、...、cnt[n - 1] を出力します。

変換は純粋に視点の変更です。最終構成の行は列の高さによって決まり、列の高さは元の ai 値のプレフィックス カバレッジによって決まります。 

### なぜ効果があるのか

 元の各行は、列の接頭語にのみ石を提供するため、各列 j は、少なくとも j に及ぶ行の数だけ正確に蓄積されます。 落下後、柱は高さが固定された独立したスタックになります。 重力が下から上に隙間なく満たされるため、最後の行 i はスタック高さが少なくとも i である列に正確に占有されます。 これにより、「最終行占有率」と「高さ ≥ i の列数」の間に直接の等価性が確立され、カウント変換の正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
a = list(map(int, input().split()))

cnt = [0] * (m + 2)

for x in a:
    cnt[1] += 1
    if x + 1 <= m:
        cnt[x + 1] -= 1

for i in range(1, m + 1):
    cnt[i] += cnt[i - 1]

ans = []
for i in range(1, n + 1):
    ans.append(str(cnt[i]))

print(" ".join(ans))
```このコードはグリッドの構築を回避します。 代わりに、列インデックスの差分配列を使用して、各列に及ぶ行数を計算します。 プレフィックスの合計により、これが実際の列の高さに変換されます。 次に、各行 i は、少なくとも高さ i に達する列の数を読み取ることによって直接答えられます。 

よくある落とし穴は、行インデックスと列インデックスを混同することです。 配列 cnt は、行ではなく列の高さのしきい値によってインデックスが付けられます。 もう 1 つの微妙な点は、m を超える列は更新してはいけないため、差分配列を適用するときに境界を確保することです。 

## 実用的な例

 ### 例 1

 入力:

 n = 3、m = 4

 a = [3, 1, 2]

 カラムカバレッジを計算します。 

| ステップ | a[i] | CNT への更新効果 | プレフィックス | の後の cnt
 | --- | --- | --- | --- |
 | 1 | 3 | + 1 で、- 4 で | [0,1,1,1] |
 | 2 | 1 | 1 で +、2 で - | [0,2,1,1] |
 | 3 | 2 | 1 で +、3 で - | [0,3,2,1] |

 プレフィックスの後の cnt は次のことを意味します。 

列 1 には石が 3 つ、列 2 には 2 つ、列 3 には 1 つ、列 4 には 0 があります。 

最終行:

 行 1 = 高さ ≥ 1 = 3 の列

 行 2 = 高さ ≥ 2 の列 = 2

 行 3 = 高さ ≥ 3 の列 = 1

 したがって、出力は [3, 2, 1] になります。 

これは、各行が純粋に列の高さのしきい値によって決定されることを確認します。 

### 例 2

 入力:

 n = 4、m = 5

 a = [5, 3, 3, 1]

 列の高さは次のようになります。 

[4、3、2、1、1]

 次に、行出力を計算します。 

行 1 = 5 列

 行 2 = 3 列

 行 3 = 3 列

 行 4 = 1 列

 出力: [5、3、3、1]

 これは、値が繰り返される場合でも、メソッドが明示的なシミュレーションを行わなくても、重複するプレフィックスを正しく集約することを示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    a = list(map(int, input().split()))

    cnt = [0] * (m + 2)

    for x in a:
        cnt[1] += 1
        if x + 1 <= m:
            cnt[x + 1] -= 1

    for i in range(1, m + 1):
        cnt[i] += cnt[i - 1]

    ans = [str(cnt[i]) for i in range(1, n + 1)]
    return " ".join(ans)

# sample-like case
assert run("3 4\n3 1 2\n") == "3 2 1"

# all equal
assert run("3 5\n5 5 5\n") == "3 3 3"

# minimal case
assert run("1 1\n1\n") == "1"

# strictly increasing prefix lengths
assert run("4 5\n1 2 3 4\n") == "4 3 2 1"

 ## 特殊なケース

 主なエッジケースは、n = 3、m = 5、a = [5, 1, 1] など、1 つの行がすべての列を支配する場合です。 列の高さは大きく偏ります。列 1 には 3 つの石があり、列 2 ～ 5 には 1 つしかありません。cnt[j] は列ごとの行カバレッジを直接カウントするため、アルゴリズムはこれを正しく処理します。したがって、均一性についての仮定は必要ありません。 

もう 1 つのエッジ ケースは、a = [1, 1, 1, 1] など、すべての ai が小さい場合です。 この場合、最初の列のみがゼロ以外であり、プレフィックスの累積後に列の高さ [4, 0, 0, ...] が得られます。 行出力は [1, 0, 0, 0] になり、これは、下位行のみが立ち下がり後に 1 つの占有列を受け取るという事実と一致します。 

最後のエッジ ケースは、すべての ai = m の場合の最大彩度です。 この場合、すべての列の高さは n なので、すべての行に m 個の石が入ります。 このアルゴリズムは、すべての i に対して cnt[i] = m を生成します。これは、完全な長方形の塗りつぶしを正しく反映します。
