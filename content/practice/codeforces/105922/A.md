 ## 解決策
 ## 問題の理解

 私たちには、小さなレジスター マシンのように動作する対話型システムが与えられています。 4 つのレジスタは未知の正の整数で始まり、4 つの補助レジスタは 0 で始まります。 初期値を確認することはできず、唯一のアクセス方法は、レジスタ間の算術演算の発行と比較のクエリによるものです。 

タスクは、最初のレジスタのペアの積が 2 番目のレジスタのペアの積より大きいか、等しいか、または小さいかを判断することです。 つまり、比較したいのは、$a \cdot b$と$c \cdot d$ただし、値を間接的に操作できるのは、加算、減算、乗算、除算、レジスタ間の比較をサポートする制限された命令セットを介してのみ許可されており、厳格なオーバーフロー制約と演算数のハードキャップが設けられています。 

主な難点は、値を直接読み取ったり、任意に大きな中間式を計算したりできないことです。 すべての操作は制限された 1024 ビット整数環境内で実行され、無効な操作が発生するとプログラムが直ちに終了します。 このため、一見安全な式でも不用意に構築するとオーバーフローする可能性があるため、単純な戦略は危険になります。 

出力は、2 つの製品の順序に対応する 3 つの可能性の中の 1 つの最終決定です。 インタラクションでは、すべての隠れた入力の下での正確性と、操作制限の遵守が必要です。 

微妙なエッジケースは、部門の安全性です。 除算はゼロに向かって切り捨てられ、ゼロによる除算は無効であるため、次のような比率を正規化しようとするアプローチはすべて無効です。$a/b$そして$c/d$分母がゼロになることは慎重に避ける必要があります。 もう 1 つのエッジ ケースは、中間乗算中のオーバーフローです。最終積が適合する場合でも、次のような中間構造が発生します。$(a+c)(b+d)$構造によっては制限を超える可能性があるため、制御のない単純な相互乗算は、このような厳密な環境では安全ではありません。 

## アプローチ

 最初の直感は、両方の積をレジスタで明示的に計算し、比較することです。 つまり、計算します$a \cdot b$1つのレジスタに入れて、$c \cdot d$別のものに変換してから、比較演算を使用します。 これは概念的には正しく、2 つの乗算と 1 つの比較のみを使用します。 

ただし、この素朴なアプローチは、算術演算が常に安全であると仮定した場合にのみ対話型制約を無視します。 このシステムでは乗算が許可されていますが、中間のオーバーフローが発生すると実行が中止されます。 すべての入力は最大 1024 ビットの整数であるため、順序と再利用に注意しないと、完全な値の直接乗算がすでに表現可能な範囲を超えてしまう可能性があります。 さらに重要なのは、不注意なシーケンスにより、必要な値を上書きする形でレジスタを誤って再利用し、再計算が強制され、演算数が不必要に増加する可能性があることです。 

重要な観察は、代数変換や縮約が必要ないということです。 構造はすでに最小限になっています。必要なのは 2 つの製品と 1 つの比較だけです。 比率や並べ替えを伴うトリックはありません。 問題は純粋に、対話型モデルでの操作を安全に調整することに関するものです。 

したがって、最適な解決策は、単純に 2 つの積を別々のレジスタで個別に計算して比較し、中間の上書きを確実に行わず、演算を最小限に抑えることです。

 ## アルゴリズムのチュートリアル

 利用可能なレジスタを使用して計算をシミュレートします。 

1. コンピューティング$a \cdot b$そしてそれを補助レジスタに保存します。 

これにより、比較する最初の量が得られ、入力レジスタは後で必要になるため、上書きしないことが保証されます。 
2. コンピューティング$c \cdot d$そしてそれを別の補助レジスタに保存します。 

これにより 2 番目の量が分離され、共有レジスタへの破壊的な更新が再び回避されます。 
3. 比較演算を使用して 2 つの計算値を比較します。 

この比較の結果は、次の関係を直接決定します。$a \cdot b$そして$c \cdot d$。 
4. 比較結果を最終回答として出力します。 

なぜ効果があるのか

 このアルゴリズムは、比較が行われる前に、両方の積を別々のレジスタに正確に保存します。 すべての算術演算は 1024 ビット整数系内で正確であり、2 つの式を決して混合しないため、比較結果は数学的値の比較と同じになります。$a \cdot b$そして$c \cdot d$。 順序を歪める可能性のある変換は導入されず、切り捨てアーティファクトを引き起こす可能性のある除算や正規化も使用されません。 

## Python ソリューション

 問題は対話型ですが、論理構造は単純です。2 つの乗算と 1 つの比較を実行します。```python
import sys
input = sys.stdin.readline

def main():
    # compute a*b into r0
    print("* r0 a b", flush=True)
    resp = input().strip()
    if resp == "err":
        return

    # compute c*d into r1
    print("* r1 c d", flush=True)
    resp = input().strip()
    if resp == "err":
        return

    # compare r0 and r1
    print("? r0 r1", flush=True)
    resp = input().strip()
    if resp == "err":
        return

    # output final answer
    print(f"! {resp}", flush=True)
    resp = input().strip()
    return

if __name__ == "__main__":
    main()
```最初の演算では、最初のペアの積を専用レジスタに計算します。 システムが内部的に再利用パターンを制限している場合でも安全を確保できるよう、入力レジスタの再利用を意図的に避けています。 

2 番目の操作は 2 番目のペアに対して同じことを行います。 両方の値が完全に具体化された後でのみ、比較演算を呼び出し、正確さを保証します。 

対話型システムが相対的な順序付けをすでに提供しているため、最終出力は比較結果の直接パススルーです。 

実装の微妙な詳細は、すべてのコマンドの後にすぐにフラッシュされることです。 インタラクティブな問題では、ジャッジがクエリを受信しないため、フラッシュを逃すとタイムアウトが発生します。 もう 1 つの微妙な点は、無効な状態の後に続行すると対話プロトコルが非同期になる可能性があるため、「エラー」応答が発生した場合は直ちに停止する必要があることです。

 ## 特殊なケース

 トリッキーなシナリオは、一方の製品が非常に大きく、もう一方の製品が近い場合ですが、両方が個別に安全範囲内にある一方で、中間の操作が正しく結合されないとオーバーフローする可能性がある場合です。 たとえば、計算しようとすると、$(a+c)(b+d)$、最終積が有効であっても、中間合計は 1024 ビットの安全範囲を超える可能性があります。 提示されたアルゴリズムは、2 つの式を決して混合しないことで、これを完全に回避します。 

もう 1 つの特殊なケースは平等です。 もし$a \cdot b = c \cdot d$、両方のレジスタは同じ値になるため、比較演算は正確に等価性を返す必要があります。 近似や除算を行わずに正確な積を計算するため、等価性は正確に保たれます。 

最後に、無効なインタラクション シーケンスは、実装における実際的なエッジ ケースです。 「err」を受信し、プログラムがコマンドの発行を続ける場合、判定状態は不定になります。 このソリューションはエラー応答で明示的に終了し、プロトコルの正確性を維持します。
