 ## 解決策
 ## 問題の理解

 この問題は、整数で表されるタイプを持つ花の 1 次元の庭園を提示します。 サラは、連続した花の一部を新しい種類に置き換えることで庭を変えることができ、住民は、連続したサイズの窓を見て庭の「美しさ」を評価します。$K$そして各ウィンドウ内の異なる花の種類の数を数えます。 全体的な美しさは、その長さのすべての可能なウィンドウの合計です。 

入力は花の数で構成されます$N$、花の種類の初期配列、および$Q$クエリ。 各クエリは、花のセグメントを単一の種類に変更するか、指定されたウィンドウ サイズでの庭の全体的な美しさを尋ねます。$K$。 

与えられた$N$そして$Q$それぞれ最大で可能です$10^5$、タイプ 2 のクエリごとに個別の要素を再計算する単純なソリューションです。$O(N \cdot K)$必要になるだろう$10^{10}$最悪の場合、合理的な制限時間を大幅に超えて操作が行われる可能性があります。 同様に、関連するすべてのウィンドウを再計算して各タイプ 1 更新を単純に処理することも遅すぎます。 

セグメントにすべて同じ花がある場合、トリッキーなエッジ ケースが発生します。 もし$K=1$、各ウィンドウには美しさ 1 がありますが、$K>1$、同じ花の上のウィンドウは、追加の異なるタイプを蓄積しません。 たとえば、配列`[5,5,5]`と$K=2$窓がある`[5,5]`そして`[5,5]`、それぞれ 1 としてカウントされ、合計の美しさは 4 ではなく 2 になります。個別のカウントを追跡するのではなく、位置によってインクリメントする不注意なスライディング ウィンドウの実装により、カウントがオーバーカウントされる可能性があります。 

もう 1 つの微妙なケースは、更新によって以前の個別のパターンが完全に上書きされる場合です。 考慮する`[1,2,3]`と$K=2$。 交換後`[1,2]`と`3`、 我々は持っています`[3,3,3]`。 新しい窓`[3,3]`そして`[3,3]`それぞれが 1 を寄与し、更新によって個別のカウントがどのように大幅に削減されるかを示しています。 

## アプローチ

 ブルート フォース アプローチでは、すべてのタイプ 2 クエリを反復し、次にすべての長さのウィンドウにわたって反復します。$K$セットを使用して個別の要素をカウントします。 タイプ 1 の更新は単に配列を上書きします。 ブルートフォースアプローチが機能するのは、セットによる個別の要素の計算が正しいためです。 ただし、必要なのは$O(N \cdot K)$タイプ 2 クエリごとの操作。 最悪の場合、$N=10^5$そして$K \approx N$、与える$O(10^{10})$、それは不可能です。 

重要な洞察は、タイプ 1 更新では常に単一の花のタイプが連続したセグメントに割り当てられるということです。 これは、配列が同じタイプの連続したブロックのリストとして表現できることを意味します。 このブロック構造を維持することで、タイプ 1 クエリの配列を迅速に調整できます。$O(\log N)$セグメントツリーやブロック位置をキーとしたバランスのとれたBSTのようなバランスのとれたデータ構造を使用する場合。 タイプ 2 クエリの場合、各ブロックには繰り返し値が含まれるため、個々の花の代わりにブロック上にスライディング ウィンドウを使用できます。 ウィンドウがブロック境界を越えるたびに、ハッシュ マップを使用して個別の花の種類の数を追跡するだけで済み、クエリごとの複雑さが大幅に軽減されます。$O(N)$最悪の場合の個別ブロックの場合、これは許容されます。 

また、タイプ 1 の更新後、同じ値の大きなブロックによってウィンドウごとの一意の要素の数が減少することを利用することもできます。 したがって、タイプ 2 のクエリには、現在のウィンドウ内の花の種類の頻度をカウントするハッシュ マップを使用したスライディング ウィンドウで十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(Q * N * K) | O(K) | 遅すぎる |
 | ブロック付き引き違い窓 | 写真 O(Q * N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 庭を単純な配列として表現します。 タイプ 1 更新の場合、セグメントを上書きします`[L-1:R]`新しいタイプで`X`。 Python スライスは連続した代入を効率的に処理するため、配列自体にブロックを明示的に格納する必要はありません。 
2. ウィンドウ サイズを使用したタイプ 2 クエリの場合`K`、周波数カウンターを使用したスライディング ウィンドウ アプローチを使用します。 初期化する`freq`辞書として、そして`distinct_count`0 として最初の値を繰り返します。`K`花。 花の種類ごとに、その頻度を増やします。 これが初めて発生した場合は、増分します`distinct_count`。 
3.トータルな美しさを保つ`B`で初期化されました`distinct_count`最初のウィンドウの後。 
4. ウィンドウを一度に 1 花ずつ前方にスライドさせます。 窓から出てくる花を周波数カウンターから取り除きます。 カウントがゼロになると、デクリメントされます。`distinct_count`。 カウンターに入る花を追加します。 カウントが 0 の場合はインクリメントします`distinct_count`。 追加`distinct_count`に`B`。 
5. すべてのウィンドウが処理されたら、出力します。`B`。 

不変条件は、各ステップで、`distinct_count`現在のウィンドウ内の個別の花の種類の数を正確に反映します。 周波数カウンタによって各タイプが正確に追跡されるため、追加および削除のたびにカウントが正しく更新されます。 これにより正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import defaultdict

def main():
    N, Q = map(int, input().split())
    A = list(map(int, input().split()))
    
    for _ in range(Q):
        parts = list(map(int, input().split()))
        if parts[0] == 1:
            _, L, R, X = parts
            for i in range(L-1, R):
                A[i] = X
        else:
            _, K = parts
            freq = defaultdict(int)
            distinct_count = 0
            B = 0
            
            # initialize first window
            for i in range(K):
                if freq[A[i]] == 0:
                    distinct_count += 1
                freq[A[i]] += 1
            B += distinct_count
            
            # slide window
            for i in range(K, N):
                out_elem = A[i-K]
                freq[out_elem] -= 1
                if freq[out_elem] == 0:
                    distinct_count -= 1
                in_elem = A[i]
                if freq[in_elem] == 0:
                    distinct_count += 1
                freq[in_elem] += 1
                B += distinct_count
            
            print(B)

if __name__ == "__main__":
    main()
```このソリューションでは、タイプ 1 クエリとタイプ 2 クエリを慎重に分離します。 更新には Python スライスが使用されます。`O(R-L+1)`アップデートごとに。 スライディング ウィンドウは、再計算を避けるために辞書を使用して個別の要素を追跡します。 オフバイワン調整`L-1`入力の 1 から始まるインデックスが Python の 0 から始まる配列と一致することを保証します。 使用する`defaultdict(int)`明示的な存在チェックを行わずにカウントを自動的に処理します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
