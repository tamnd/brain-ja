 ## 解決策
 ## 問題の理解

 配列を構築する必要があります$a_0, a_1, \dots, a_n$から始まる$a_0 = 0$。 

次のポジションごとに、正確に 2 つの選択肢があります。 現在の値を増やすには、次のいずれかを実行します。$x$、またはそれを減らします$y$。 唯一の制限は、シーケンス内のすべての値が最大でも次の値でなければならないことです。$B$。 負の値は完全に許可されます。 

すべての有効なシーケンスの中で、要素の合計ができるだけ大きいものが必要です。 

制約は十分小さいため、各位置を個別に処理できます。 それでも$t$と同じ大きさにすることができます$10^4$、すべての合計$n$値は最大でも$2 \cdot 10^5$。 つまり、$O(n)$テストケースごとのアルゴリズム、より正確には$O(\sum n)$すべてのテスト ケースにわたって、制限時間内に簡単に収まります。 すべてのポジションには 2 つの選択肢があるため、考えられるすべての選択肢を指数関数的に探索することは不可能です。$2^n$シーケンス。 

難しいのは、総和の最大化は動的プログラミングを必要とする全体的な最適化問題ではないことを認識することです。 構造ははるかに単純です。 

次の入力を考えてみましょう。```
1
4 1 7 3
```正しい順序は次のとおりです。```
0, -3, -6, 1, -2
```合計付き$-10$。 

常に追加しようとする迂闊な戦略$x$すぐに境界に違反してしまうため、$0 + 7 > 1$。 値が負になることが許可されているため、最適解は最初に意図的に下向きに移動し、後で初めて上向きのステップを実行する可能性があります。 

もう 1 つの興味深いケースは次のとおりです。```
1
3 5 5 1
```最適な順序は次のとおりです。```
0, 5, 4, 3
```合計付き$12$。 

到達後$5$、さらに追加$5$を超えるだろう$B$, したがって、減算する必要があります$1$。 やみくもに演算を交互に実行したり、限界に達した後に常に減算を優先したりするソリューションでは、最適な合計を逃してしまいます。 

大きな答えも可能です:```
1
7 1000000000 1000000000 1000000000
```答えは次のとおりです。```
4000000000
```32 ビット整数を使用するとオーバーフローが発生します。 実装では、Python 整数または他の言語の 64 ビット算術を使用する必要があります。 

## アプローチ

 最も直接的なアプローチは、すべてのポジションを二者択一の選択肢として見ることです。 ステップで$i$、どちらかを追加します$x$または減算する$y$。 有効な値が生成されるたびに両方の可能性を再帰的に試し、最良の合計を維持することができます。 

この総当たり検索は、すべての有効なシーケンスを検査するため、正確です。 残念ながら、それは$2^n$最悪の場合は状態。 と$n$まで$2 \cdot 10^5$、これはまったく不可能です。 

重要な観察は、目的はすべてのシーケンス値の合計を最大化することであるということです。 あらゆる段階で、未来は現在の値にのみ依存します。 両方の操作が許可されている場合は、結果として得られるより大きな値を選択する方が常に適切です。 

現在の値が$cur$。 

もし$cur + x \le B$の場合、次の 2 つの候補値は次のとおりです。$$cur + x$$そして$$cur - y$$以来$x > 0$そして$y > 0$、$$cur + x > cur - y.$$次の値が大きくなると、答えに対する現在の寄与が大きくなるだけでなく、将来のすべての決定の開始点も大きくなります。 加算が有効な場合に減算を選択する理由は決してありません。 

つまり、決定が強制されることになります。 

追加する場合$x$制限内にとどまります、それを実行してください。 

それ以外の場合は減算します$y$。 

これにより、単純な貪欲なシミュレーションが得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(2^n)$|$O(n)$| 遅すぎる |
 | 最適な貪欲なシミュレーション |$O(n)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 現在の値を次のように初期化します。$cur = 0$。 
2. 答えを次のように初期化します。$ans = 0$、 以来$a_0 = 0$合計に貢献します。 
3. 各ポジションについて、$1$に$n$、追加するかどうかを確認します$x$値を許容範囲内に保ちます。 
4. もし$cur + x \le B$、 セット$cur = cur + x$。 

これは、より厳密に大きな値を生成するため、可能な限り最良の選択です。$cur - y$。 
5. それ以外の場合は、設定します$cur = cur - y$。 

この状況では加算は禁止されているため、有効な手段は減算のみです。 
6. 新しい値を追加します。$cur$現在の合計に。 
7. すべての処理が完了したら$n$ポジションの累積合計を出力します。 

### なぜ効果があるのか

 貪欲な選択は、ローカルおよびグローバルに最適です。 

いつでも$cur + x \le B$、どちらの操作も合法です。 加算後の結果の値は、減算後の結果の値よりも常に大きくなります。$x$そして$y$ポジティブです。 

より大きな値を選択すると、合計の現在の期間が直ちに増加します。 また、将来のステップのために、より大きな現在値が残ります。 選択後に取得可能な任意のシーケンス$cur - y$より大きな状態から複製できる$cur + x$将来的には同等以上の貢献が期待できます。 

したがって、加算が利用可能な場合は常に、加算が減算よりも優先されます。 減算するのは、加算が制約に違反する場合のみです。 すべてのステップでこのルールを繰り返すと、可能な最大の合計が生成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    answers = []

    for _ in range(t):
        n, B, x, y = map(int, input().split())

        cur = 0
        total = 0

        for _ in range(n):
            if cur + x <= B:
                cur += x
            else:
                cur -= y

            total += cur

        answers.append(str(total))

    sys.stdout.write("\n".join(answers))

solve()
```変数`cur`現在のシーケンス値を保存します。 から始めます`0`、に対応$a_0$。 

新しいポジションごとに、最初に追加するかどうかを確認します。$x$上限内にとどまる$B$。 そうであれば、私たちはそのオプションを採用します。 それ以外の場合は減算する必要があります$y$。 

新しい値を決定したら、すぐにそれを追加します。`total`。 以来`total`ゼロから始まり、$a_0 = 0$、最初の要素に個別の処理は必要ありません。 

よくある間違いの 1 つは、負の値は禁止されていると考えることです。 この問題は上からの値を制限するだけなので、減算によって任意の負の数値が生成される可能性があります。 

もう 1 つのよくある間違いは、32 ビット整数の使用です。 サンプル自体には次の回答が含まれています$4 \times 10^9$、これは符号付き 32 ビットの範囲を超えています。 Python はこれを自動的に処理します。
