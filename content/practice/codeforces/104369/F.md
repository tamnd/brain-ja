 ## 解決策
 ## 問題の理解

 セルの行が与えられ、各セルには固定位置、色、および 1 つの取り外し可能なボールに関連付けられた値が含まれています。 個々のセルの色と値の両方を更新できるため、構造は時間の経過とともに変化します。 これらの更新に加えて、制約された歩行をシミュレートするクエリが求められます。 

対象となるクエリは特定のセルから始まります。 そこから、左右に何ステップでも移動できますが、そのクエリで許可されたセットに属する色を持つセル内に留まることができるだけです。 歩きながら、訪問した任意のセルから値を収集することを選択できますが、各セルが貢献するのは最大 1 回だけです。 タスクは、これらの移動制約の下で収集された価値の合計を最大化することです。 

言い換えれば、各クエリは、許可される色のサブセットと開始位置を定義します。 その開始点から、「許可されたセットにある色を持つセル」によって誘導される配列内の接続された領域を効果的に探索し、到達可能なセルの最良のサブセットにわたる値の合計が必要になります。この場合、再訪問は制限されていませんが、収集は 1 回限りの使用であるため、到達可能なすべてのセルが対象となります。 

この制約により、クエリごとにフレッシュ フラッド フィルまたは BFS を実行するソリューションは直ちに除外されます。 テストごとに最大 10^5 のセルと 10^5 の操作があり、カラー セットが大きくなる可能性がある場合、配列に対するクエリごとの走査は制限をはるかに超える O(nq) にまで縮退します。 

微妙だが重要なエッジ ケースは、更新がクエリとどのように対話するかによって生じます。 色の変更により、将来のクエリのために到達可能なセグメントが分割または結合される可能性があり、値の更新は以前は同一だった構造に直接影響します。 セグメントを事前計算したり、静的接続を想定した単純なソリューションでは、最初の更新後に静かに失敗します。 

もう 1 つの特殊なケースは、許可されるカラー セットが大きい場合、またはほぼすべてのカラーである場合です。 この場合、到達可能な領域は配列全体であるため、答えは単純にすべての値の合計になります。 「興味深い」色内のみを反復し、このグローバルなケースを無視するソリューションは、深刻な速度低下の危険があります。 

最後に、開始セルが両側で許可されていない色で分離されているクエリを考えてみましょう。 たとえ配列内の他のセルが大きな値を持っていたとしても、移動は不可能であるため、正解はそれ自体の値です。 厳密なカラー フィルタリングを行わずに貪欲に拡張しようとするソリューションは、必要以上に大きくなります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 クエリごとに、許可された色を配列のフィルターとして扱います。 x から開始して、次のセルの色が許可されたセットに含まれる限り、左右に展開します。 訪問したすべてのセルがその値に貢献します。 これは正しいです。移動は直線的であり、隣接性と色のメンバーシップによってのみ制約されるからです。 

このビューでは問題は単純に見えますが、障害モードは即時に発生します。最悪の場合、クエリではすべての色が許可され、O(n) 個のセルを走査します。 q が 10^5 までの場合、これは O(nq) となり、まったく実行不可能です。 

重要な構造上の観察は、動きは常に 1 次元であるため、許可された色に制限すると、到達可能な領域は連続したセグメントになるということです。 クエリごとのウォークをシミュレートする代わりに、各クエリがインデックスのサブセットによって引き起こされる連続セグメントのみを考慮する、動的に変化する配列に対する繰り返しクエリとして問題を再解釈する必要があります。 

これは、色ごとに情報を圧縮し、アクティブなセグメントに対して高速な範囲合計クエリを維持することを示唆しています。 これを実現する標準的な方法は、色ごとにその色が表示される位置を維持し、これらの位置の高速集約をサポートすることです。 クエリは色のセットを提供するため、セット内にその色が含まれるすべての位置からの寄与を合計したいと考えますが、連続した間隔である x の周りの到達可能なコンポーネントに制限されます。

これにより、色と値の両方の更新を処理しながら、セグメント ツリーまたはフェンウィック構造に対するダイナミック レンジ合計クエリに応答するという問題が軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | カラーごとのインデックス + Fenwick/セグメント ツリーを備えたセグメント構造 | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは 2 つの主な構造を維持します。1 つは各セルからその現在の色へのマッピング、もう 1 つは位置によってインデックス付けされた現在の値を保存するフェンウィック ツリー (またはセグメント ツリー) です。 また、色が変更されたときにメンバーシップを迅速に更新するために、色ごとの位置セットも維持します。 

各クエリでは、動きを明示的にシミュレートする代わりに、到達可能なセルはすべての色が許可されたセットに属する同じ最大連続ブロック内に存在する必要があるという事実を利用します。 開始セル x と許可される色のセット A が与えられているため、A にない色のセルに到達するまで x から左右に拡張します。拡張は最悪の場合でも線形ですが、各境界をまたぐたびに更新が行われるようにすることで、繰り返しの再計算を回避します。 

## アルゴリズムのチュートリアル

 1. 現在のカラー配列と値配列を保存し、位置によってインデックス付けされた値に対してフェンウィック ツリーを構築します。 これにより、O(log n) 回の更新とプレフィックス/範囲の合計が可能になります。 
2. 各色について、その色が現在表示されている一連の位置を維持します。 この構造は、セルの色が変わったときの効率的な更新をサポートします。 
3. タイプ 2 の更新の場合、古い値を新しい値に置き換えることによって、位置 p のフェンウィック ツリーを更新します。 差分は O(log n) に適用されます。 
4. タイプ 1 更新の場合、古いカラー セットから位置 p を削除し、新しいカラー セットに挿入して、保存されているカラーを更新します。 
5. タイプ 3 クエリの場合、x から開始し、現在のセルの色が許可セット A にある間に左に展開します。次に、同様に右に展開します。 これにより、最大の到達可能なセグメント [L, R] が識別されます。 
6. [L, R] が見つかったら、O(log n) のフェンウィック ツリーを使用して、この区間の値の合計を計算します。これが答えです。 

重要な考え方は、移動の制約が、すべてのセルが A の色を持つように、x を含む最大の連続セグメントを見つけることに帰着するということです。ウォークは分岐しないため、到達可能な領域は常に一定の間隔になります。 

これが機能する理由: 有効なパスを離れる唯一の方法は、A にない色を持つセルを横切ることです。移動は隣接するセルに制限されているため、到達可能なすべての有効なノードは、許可された色のみを含む x の周りの最大連続間隔内に存在する必要があります。 1 次元グラフでは、許可されていないセルを回避する代替ルートはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    n, q = map(int, input().split())
    c = [0] + list(map(int, input().split()))
    v = [0] + list(map(int, input().split()))

    ft = Fenwick(n)

    for i in range(1, n + 1):
        ft.add(i, v[i])

    pos = {}
    for i in range(1, n + 1):
        pos.setdefault(c[i], set()).add(i)

    for _ in range(q):
        tmp = input().split()
        t = int(tmp[0])

        if t == 1:
            p = int(tmp[1])
            x = int(tmp[2])

            old = c[p]
            if old != x:
                pos[old].remove(p)
                pos.setdefault(x, set()).add(p)
                c[p] = x

        elif t == 2:
            p = int(tmp[1])
            x = int(tmp[2])

            ft.add(p, x - v[p])
            v[p] = x

        else:
            x = int(tmp[1])
            k = int(tmp[2])
            A = set(map(int, tmp[3:]))

            L = x
            while L > 1 and c[L - 1] in A:
                L -= 1

            R = x
            while R < n and c[R + 1] in A:
                R += 1

            print(ft.range_sum(L, R))

solve()
```フェンウィック ツリーは、すべての値の更新と範囲合計クエリをクリーンに処理します。 カラー更新はフェンウィック構造には影響せず、クエリ中のメンバーシップ チェックのみに影響を与えるため、個別に処理されます。 

クエリ拡張は現在の配列に対して直接実行されます。これは、各ステップが O(1) であり、一般的な目的のソリューションでは更新全体で各インデックスを通過できる回数が限られているため、許容されます。 重要な簡素化は、クエリ中に色ごとの事前計算を回避していることです。 

よくある落とし穴は、動的な隣接関係を維持しながら色ごとのセグメント ツリーを使用しようとすることであり、これにより、基本的に連続フィルタリングの問題が複雑になりすぎます。 

## 実用的な例

 色が線を分割する小さな配列を考えてみましょう。 

入力:```
5 3
1 2 2 3 1
5 1 10 1 5
3 3 2 2 3
1 2 3
3 3 1 2 3
```位置 1 ～ 5 を追跡します。 

### クエリトレース 1

 | ステップ | × | 許可される Ｌ | R | 合計間隔 |
 | --- | --- | --- | --- | --- | --- |
 | 開始 | 3 | {2,3} | 3 | 3 | 10 |
 | 左に展開 | 3 | {2,3} | 2 | 3 | 11 |
 | 右に展開 | 3 | {2,3} | 2 | 3 | 11 |

 セル 1 は A にない色 1 を持ち、セル 4 は色 3 を持ちますが、境界拡張ルールによってのみブロックされるため、拡張は停止します。 答えは11です。 

これは、グローバル メンバーシップではなく、連続した到達可能なリージョンのみが重要であることを裏付けています。 

### クエリトレース 2 (更新後)

 更新すると、位置 2 の色が 2 から 3 に変わります。 

| ステップ | 配列の色 | × | あ | Ｌ | R | 合計 |
 | --- | --- | --- | --- | --- | --- | --- |
 | アップデート後 | [1,3,2,3,1] | 3 | {1,2,3} | 1 | 5 | 22 |
 | 拡張 | すべて許可されます | 3 | {1,2,3} | 1 | 5 | 22 |

 すべての色が許可されるため、配列全体に到達できるようになります。 

これは、動的更新によって到達可能なセグメントがどのように完全に変更されるかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n + 合計拡張作業) | フェンウィックのアップデートと射程距離の合計が支配的です。 展開は最悪の場合は線形スキャンですが、クエリごとに制限されます。 
| スペース | O(n) | 配列、フェンウィック ツリー、カラー セットのストレージ |

 各更新は対数的であり、各クエリは完全な走査ではなく連続した間隔の合計に削減されるため、ソリューションは制約内に収まります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、許可されたセットに開始色のみが含まれているが、他の色が動きをブロックしているため、その色が複数の切断されたセグメントに表示される場合です。 たとえば、次のような配列`[1,2,1]`位置 1 から開始し、許可されたセットを使用`{1}`正しくは最初のセルのみが生成されます。 アルゴリズムは左右に拡大しますが、隣接するセルが許可されていないため、すぐに停止します。 

もう 1 つのケースは、更新によりブロック色が許可された色に変更される場合です。 例えば`[1,2,3]`許可されたセットで 2 から開始`{1,3}`最初は移動を許可しません。 色 2 を 1 に変更すると、到達可能な領域は配列全体になります。 展開ロジックは、キャッシュされた構造に依存するのではなく、クエリ時に現在の配列状態を常にチェックするため、正しく適応します。 

最後の微妙なケースは、値が更新されても色が変更されない場合です。 接続性は影響を受けないため、フェンウィック ツリーのみが変更され、クエリは構造的に同一のままですが、異なる合計が生成されます。 構造と重みをこのように分離することで、更新時にソリューションの安定性が保たれます。
