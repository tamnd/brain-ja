 ## 解決策
 ## 問題の理解

 空のシーケンスから始めて、2 種類の演算を使用して非常に大きな配列を徐々に構築します。 最初の操作では、単一の値を末尾に追加し、事実上シーケンスを 1 要素分拡張します。 2 番目の操作は、現在の配列全体を取得し、その配列のいくつかの完全なコピーをそれ自体に連結します。 

重要な点は、すべての複製操作で現在のサイズが追加されるのではなく乗算されるため、配列が非常に速く増大する可能性があることです。 多くても$10^5$操作を行うと、最終的な配列の長さは最大で$10^{18}$なので、明示的に構築することは不可能です。 

各クエリは、すべての操作が適用された後の最終配列内の特定の位置にある値を要求します。 したがって、タスクは構築をシミュレートすることではなく、反復コピーを通じて最終的な配列内の位置が以前の状態にどのように遡るかを推論することです。 

この制約により、直接的なシミュレーションや部分的な構築さえも即座に除外されます。 最終的な配列の各要素に関わるものは実行不可能です。 クエリごとの線形トラバーサルでも失敗します。$n$そして$q$大きいです。 

タイプ 1 の操作のみをシミュレートし、構造を無視しようとすると、微妙な失敗例が発生します。 

入力:```
3 1
1 1
1 2
2 1000000000
1
```最終的な配列は単なるものではありません`[1,2]`素朴なループで繰り返されます。 それは`[1,2]`に続く$10^9$のコピー`[1,2]`。 文字通りコピーを構築する単純な実装では、すぐにメモリが不足してしまいます。 

もう 1 つの隠れた問題は、各重複が構造を追跡せずに現在の長さのみを知る必要があると想定していることです。 長さが追跡されたとしても、セグメントがどのように形成されたかを覚えていなければ、クエリを逆方向に解決する方法はありません。 

主な問題点は、複製操作では配列の構造全体が保持されることです。つまり、コピーされたブロック内のすべての要素は以前のプレフィックスと同一になります。 これにより、悪用する必要がある再帰的な構造が作成されます。 

## アプローチ

 ブルートフォースアプローチでは、配列全体が明示的に維持されます。 タイプ 1 の操作ごとに、1 つの要素を追加します。 タイプ 2 の操作ごとに、$x$現在の配列のコピー。 これはルールに正確に従っているため、概念的には単純で正しいものです。 

ただし、配列のサイズは倍増して大きくなります。 一連の操作に大きな乗算器を使用したタイプ 2 の繰り返し操作が含まれる場合、配列サイズはすぐにメモリ制限を超え、段階的に計算することさえ不可能になります。 最悪の場合は、時間と空間の指数関数的な爆発につながります。 

重要な点は、実際には完全な配列が必要ではなく、その長さと位置を後方にトレースする方法だけが必要であるということです。 すべての操作の後、すべての位置は直接追加 (タイプ 1) またはコピーされたブロック (タイプ 2) から取得されます。 これらのマッピングを逆にできれば、配列を実体化せずにクエリに答えることができます。 

前方に構築するのではなく、各操作後に長さを維持します。 次に、位置のクエリに答えるには$k$、操作を通じて後方に進みます。 重複が見つかった場合は、削減します$k$各コピーはその時点での元の配列と同一であるため、前の長さを法的に計算します。 

これにより、問題は操作履歴の逆走査に変わります。

 | 最適 |$O(n + q \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 操作を 1 回処理して、各ステップの後に配列の長さを計算します。 長さを超える可能性があるため、$10^{18}$、安全な上限 (最大クエリを超える任意の値で十分です) に制限しますが、64 ビット整数の正確な値を保持しても問題ありません。 

また、各操作を順番に保存して、逆方向にたどることができます。 

### ステップ

 1. すべての操作を読み取り、配列を計算します`len[i]`、 どこ`len[i]`演算後の配列のサイズです$i$。 

操作がタイプ 1 の場合、長さは 1 ずつ増加します。 

操作が値のあるタイプ 2 の場合$x$、現在の長さを乗算します。$x+1$。 

これは追加を反映します$x$完全な配列のコピー。 
2. 各クエリ値について$k$、ポインタを設定します$i = n$。 位置の原点が見つかるまで操作を逆方向に進めます$k$。 
3. その間$i > 0$、動作確認$i$:

 タイプ 1 の場合、$k$現在の長さに等しい場合、要素は直接見つかりました。 壊す。 
4. 操作の場合$i$因子付きタイプ 2 です$x$の場合、このステップの配列は次のようになります。$x+1$同じサイズのブロック`len[i-1]`。 

交換する$k$と$k \bmod len[i-1]$。 余りが0の場合は設定$k = len[i-1]$。 

その後、後進を続けます。 

このステップは、すべてのコピーが正確なレプリカであるため機能します。$k$元の配列内の同じ相対位置に対応する必要があります。 
5. デクリメント$i$タイプ 1 の基本要素に到達するまで続けます。 

### なぜ効果があるのか

 どの時点でも、配列は複製操作によって作成された同一のセグメントを連結したものになります。 タイプ 2 の操作は新しい情報を作成せず、既存の構造を繰り返すだけです。 したがって、繰り返されるブロック内のすべてのインデックスは、複製前の元のブロック内の同一のインデックスにマップされます。 

不変条件は、処理後の操作です。$i$、の値$k$演算後に形成された配列内の正しい位置を常に参照します。$i$、しかしそれを超えるすべての拡張を遡って追跡します。 各モジュロ ステップでは、以前のバージョンの配列内の相対位置の正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    
    ops = []
    length = [0] * (n + 1)

    for i in range(1, n + 1):
        b, x = map(int, input().split())
        ops.append((b, x))
        if b == 1:
            length[i] = length[i - 1] + 1
        else:
            length[i] = min(10**18, length[i - 1] * (x + 1))

    queries = list(map(int, input().split()))

    for k in queries:
        cur_k = k
        i = n

        while i > 0:
            b, x = ops[i - 1]
            if b == 2:
                prev_len = length[i - 1]
                cur_k %= prev_len
                if cur_k == 0:
                    cur_k = prev_len
            i -= 1

        print(cur_k, end=' ')
    print()

t = int(input())
for _ in range(t):
    solve()
```最初のフェーズでは長さの配列を構築するので、すべての操作でその時点でのシーケンスの大きさがわかります。 拡張前にブロック サイズを知る必要があるため、これは複製手順を元に戻すために不可欠です。 

クエリの解決中は、操作を逆方向に進めます。 タイプ 2 の各演算では、モジュロ演算を使用してインデックスを以前のバージョンの配列に圧縮します。 タイプ 1 の操作は構造を変更しないため、実際の値が導入されるアンカーとしてのみ機能します。 

主な微妙な点は、モジュロを慎重に処理することです。 いつ$k$が前の長さで正確に割り切れる場合、余りはゼロになるため、ブロックの最後の要素にマップし直す必要があります。

 ## 特殊なケース

 重要なエッジ ケースは、クエリ インデックスが重複セグメント内のブロック境界と正確に位置合わせされている場合に発生します。 その場合、単純なモジュロ ロジックはゼロを生成するため、前の配列の最後の要素に再マッピングする必要があります。 この調整を行わないと、次のような位置をターゲットとするクエリが実行されます。$len[i-1]$、$2 \cdot len[i-1]$などは、誤ってゼロまたは範囲外の値を返します。 

もう 1 つのケースは、配列が非常に大きいのにクエリが小さい場合に発生します。 アルゴリズムが構造を具体化することはありません。そのため、長さが超過した場合でも、$10^{18}$、後方リダクションは値を有効な範囲内に保ち、常に基本の追加操作に解決されます。 

最後のエッジケースは、タイプ 2 の操作がまったくない場合です。 その場合、ソリューションは単純なプレフィックス配列検索に縮退し、逆方向トラバーサルは対応するタイプ 1 操作で即座に終了します。
