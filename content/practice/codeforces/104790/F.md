 ## 解決策
 ## 問題の理解

 ケーブルカーの前には、日中一定時間運行される行列システムがあります。 毎分、既知の数の人々が到着して列に加わり、それらの到着が処理されるとすぐに馬車が出発し、最大で固定数の人々を列の先頭​​から排除します。 

操作時間枠内で到着までの時間を選択できます。 分 i に到着した場合、その分に到着したすべての人の後に列に加わります。つまり、その分新たに到着した人全員の後ろ、およびすでに待っている全員の後ろに配置されます。 その瞬間から、システムが最終的にサービスを提供するまで待ちます。 待ち時間は、到着分から車両に乗車するまでの分数です。 

目標は、この待ち時間を最小限に抑える到着時間を選択することです。 複数の分で最小待ち時間が同じになる場合は、最も早い分を選択する必要があります。 日中に最終的に馬車に乗れる時間がない場合、答えは不可能です。 

この制約により、最大 100,000 分と 1 分あたりの非常に大きな到着数が許可されます。 これにより、考えられるすべての到着時間に対してキューの状態を最初から再計算するシミュレーションが除外されます。 候補分ごとのキュー展開の単純な O(n^2) シミュレーションは、最悪の場合、10^10 のオーダーで実行され、時間内に終了しません。 

正確さのためには、いくつかの特殊なケースが重要です。 到着が多すぎて、1 分あたりのサービス容量 c を n 分続けてもキューが空にならない場合、到着時間は無効になります。 たとえば、n = 5、c = 1、a = [5, 0, 0, 0, 0] の場合、システムは合計 5 人しかサービスできませんが、表示されるのはあなたを含めて 6 人であり、決して乗車することはできません。 

もう 1 つの微妙なケースは、キューが大きくなっても、遅く到着すると待ち時間が短縮される場合があります。これは、数分早く到着すると、大きなバーストの後ろに置かれ、長い残りの待機間隔が生じる可能性があるためです。 このため、貪欲な直感に頼るのではなく、一貫した式に基づいてすべての候補の到着時間を評価する必要があります。 

## アプローチ

 ブルートフォースアプローチでは、考えられる到着分 i を個別に考慮します。 i ごとに、1 日の始まりからキューをシミュレートし、分 i までの完全な状態を再構築し、自分自身を挿入し、サービスが提供されるかその日が終了するまで分ごとにシミュレーションを続けます。 これはプロセスを正しくモデル化しますが、各 i に対してほぼ全体のシミュレーションを繰り返します。 シミュレーションあたりの作業時間が n 分で O(n) の場合、これは O(n^2) になります。n が 100,000 の場合、これは遅すぎます。 

重要な点は、参加した時点で自分より先に何人いるのかがわかれば、段階的にシミュレーションする必要がなくなるということです。 システムは到着後常に 1 分あたり c 人を削除するため、私たちの順位は 1 分ごとに c ずつ決定的に減少します。 これにより、問題は単純な算術質問に変わります。つまり、ポジションがゼロになるまでに完全な「サービス ラウンド」が何回必要になるかということになります。 

固定到着分 i の場合、prefix[i] を分 i までに到着した人の総数とします。 分 i に ai 人の後に到着するため、キュー内の私たちの位置は prefix[i] + 1 になります。その瞬間から、1 分ごとに c 人が先頭から削除されます。したがって、私たちに到着するまでに必要な分数は、k · c ≥ prefix[i] + 1 となる最小の k になります。これにより、待機時間の閉形式の式が得られます。 

プレフィックスの前処理後に O(1) のすべての i についてこの値を計算し、最適な候補を選択します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n^2) | O(1) または O(n) | 遅すぎる |
 | プレフィックス + 閉じた形式 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

1. prefix[i] が 0 分から i 分までに到着した人の数を表すように、到着のプレフィックスの合計を計算します。 これにより、再シミュレーションすることなく、到着前に正確なキュー サイズをいつでも知ることができます。 
2. 候補者が到着する分 i ごとに、i に到着した後にすでにシステム内にいる人数を決定します。 これは prefix[i] で、同分到着後に参加するので、位置は prefix[i] + 1 になります。 
3. このキューの位置を、到着までに車両が何回出発する必要があるかに変換します。 出発ごとに c 人が削除されるため、k = ceil((prefix[i] + 1) / c) 回の出発が必要になります。 
4. 必要な出発回数を待ち時間に換算します。 分 i に到着した後、最初に出発できる可能性があるのは同じ分内に発生するため、待機する分数は k − 1 です。 
5. すべての i にわたる最小待ち時間を追跡します。 複数の i が同じ値になる場合は、最小の i を保持します。 
6. 実現可能性を確認します。 候補者が最適に見えたとしても、それが有効なのは、サービスウィンドウが実際に連絡を取るのに十分な長さである場合に限られます。 いいえ、n 分が終了する前にサービスを受けることができない場合は、「不可能」と出力します。 

### なぜ効果があるのか

 重要な不変条件は、到着分 i を確定した後、キュー内の相対位置は、将来のすべての到着とは無関係に、1 分ごとに正確に c だけ決定論的に減少するということです。 今後のすべての到着は、列から外される速度ではなく、後ろの人々にのみ影響します。 これにより、システムは初期位置のみが重要となる単一の変数プロセスに縮小されます。 待ち時間は prefix[i] のみに依存するため、候補の比較は i に対する閉形式関数の評価に帰着し、すべての i に対する最小値がグローバルに最適であることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, c = map(int, input().split())
    a = list(map(int, input().split()))

    pref = 0
    best = None
    best_i = 0

    total = 0
    for x in a:
        total += x

    # If even all capacity cannot serve everyone + us
    if total + 1 > n * c:
        print("impossible")
        return

    for i in range(n):
        pref += a[i]
        pos = pref + 1

        # ceil(pos / c)
        k = (pos + c - 1) // c
        wait = k - 1

        if best is None or wait < best or (wait == best and i < best_i):
            best = wait
            best_i = i

    print(best_i)

if __name__ == "__main__":
    solve()
```このソリューションは、各候補分が一定時間で評価されるように、実行中のプレフィックス合計を維持します。 位置計算`pref + 1`同じ分に到着した人があなたより先に到着するというルールをエンコードします。 天井部門は、目の前の全員を追い払うために何台の車両が満員になる必要があるかを計算します。 実現可能性チェックにより、最良の場合でも、すべての分にわたる合計サービス容量がお客様を含めるのに十分であることが保証されます。 そうでなければ、どの候補者も成功することはできません。 

最終的な選択では、最小待機時間と最も早いインデックスの両方が維持され、インデックスを直接比較することで同点が解決されます。

 ## 特殊なケース

 到着が総容量を超える完全に飽和したシステムの場合、プレフィックスサムの実現可能性チェックが即座にトリガーされます。 たとえば、`n=3, c=1, a=[2,2,2]`、合計到着数は 6 ですが、キャパシティーは 3 であるため、アルゴリズムは 1 分もシミュレーションせずに「不可能」を出力します。 

到着時間が早い時間帯に大きく偏っている場合。`a=[100,0,0,...]`、0 分のプレフィックスにより、すでに大きなキューの後ろに配置されています。 アルゴリズムは、早期到着に対する長い待ち時間を正確に計算し、プレフィックスが変更されない後の数分を優先する可能性がありますが、実現可能性は依然として総容量にのみ依存し、アルゴリズムは分ごとの評価とは独立してチェックします。
