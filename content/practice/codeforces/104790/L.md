 ## 解決策
 ## 問題の理解

 ドアでつながった部屋のコレクションが与えられます。 各ドアは両方向に移動できるため、物理的にはレイアウトは方向のない接続されたグラフになります。 ただし、各ドアには制約があります。ロックできるのは 1 つの特定のエンドポイント (次のエンドポイント) からのみです。`a`入力ペアで`(a, b)`。 

ドアをロックするには、部屋の中に立っていなければなりません`a`そのドアを扱っている間。 開いたドアの中を自由に移動できるため、唯一の困難は、建物内を移動する際に、すべてのドアを少なくとも 1 回はロックできる正しい位置にいることを確認することです。 

建物内からスタートすると、正面玄関はすでに施錠されており、一部の部屋では追加の「出口」をリクエストすることができます。 出口は、その部屋から建物への出入りを可能にする特別な接続です。 各出口を使用すると、その部屋でトラバース セグメントを開始または終了できます。 

タスクは、必要な出口の最小数を決定することです。これにより、すべてのドアがその制約に従ってロックされ、すべての作業が完了したら退出できるように、建物内の散歩を計画できるようになります。 

重要な構造的制約は、各ドアが歩行中にどのように「カバー」されるべきかについて方向要件を課すことです。`(a, b)`、それは、あなたがいる方法でそれを横断するときにのみ満足されます。`a`現時点ではロックされています。 これにより、問題は、特定のノードから開始する必要がある「操作」の数のバランスをとることになります。 

入力制約は大きく、最大 100,000 の部屋と 1,000,000 のドアがあります。 これにより、パス上の二次シミュレーションまたは二次二次シミュレーションさえも即座に除外されます。 正しいソリューションは、グラフを線形時間 (本質的には O(n + m)) で処理する必要があります。 

単純なトラバーサル戦略を考えると、微妙なエッジケースが発生します。 たとえば、貪欲に歩いて、遭遇したドアに鍵をかけようとすると、順序によっては失敗する可能性があります。 

単純な構造を考えてみましょう。```
3 2
2 1
3 1
```部屋2から始めると施錠できます`(2,1)`ただし、ロック制約を適切に満たすことができなくなる可能性があります。`(3,1)`他の場所で再起動することなく。 素朴な貪欲なウォークは、追加の開始点がなければ実現可能性を保証しません。 

重要な問題は、一部の部屋では、1 回の連続歩行で自然にサポートできるよりも、より制約された移動を「開始」する必要があることです。 

## アプローチ

 ブルートフォース戦略では、建物内のすべての可能な歩行命令をシミュレートし、さまざまな開始点とドア通過のシーケンスを試みます。 各州は、どのドアがすでにロックされているか、および作業員が現在どこにいるかを追跡することになる。 各ドアは複数回通過する可能性があり、決定は将来の制約に依存するため、これは本質的に急速に指数関数的になります。 ローカルな決定がグローバルな実現可能性を妨げる可能性があるため、最短またはヒューリスティックなウォークに制限しても失敗します。 

ブルート フォースの失敗モードは、方向の制約によって引き起こされるグローバル バランス要件を捕捉できないことです。 重要なのは、正確な走査順序ではなく、送信ロック要件を満たすために各ルームが何回「開始ソース」として機能する必要があるかです。 

重要な観察は、各ドアを再解釈することです`(a, b)`から始まる容量の 1 単位を事実上「消費」する要件として`a`。 無向グラフでは移動が制限されないため、あらゆる要件を中間の部屋を経由してルーティングできるため、グラフの接続性によって実現可能性が制限されることはありません。 唯一の制限要因は、そのような要件を 1 回のウォークに自然に連鎖させることができる数だけです。 

各部屋`v`ロックする必要があるドアの数をカウントします。 これに電話してください`out_req[v]`。 対称性の要件はありません`b`ロックは片側のみに拘束されるためです。 問題は、できるだけ少ない歩行セグメントを使用して、これらすべての方向性要件をカバーすることになります。 

各歩行セグメントは、開始機能を効果的に「注入」するある部屋から始まる連続的な移動に対応します。 ルームに単一の連続チェーンで吸収できる以上の発信要件がある場合は、新しいセグメントを開始するために追加の出口が必要になります。 

これにより、問題は必要な独立起動の数を数えるということになります。これはまさに、ノード全体に分散された「追加の需要ユニット」の数です。 

したがって、解は、連鎖制約によって引き起こされる自然なバランスの下で需要が正であるノードの寄与を合計することによって得られます。

 ## アルゴリズムのチュートリアル

 すべてのロック要件を満たすために必要な独立したトラバース開始の数を数えるという問題として問題を再定式化します。 

### 1. 部屋ごとに方向の要件を数える

 各ドアごとに`(a, b)`、 増加`out_req[a]`1つずつ。 これは、部屋に立っている間は最終的にこのドアをロックする必要があることを表します`a`。 

このステップでは、走査順序を気にせずに、すべての制約をローカルでキャプチャします。 

### 2. 要件を連鎖制約として解釈する

 各部屋は、連続した横断パスのコネクタとして機能します。 単一の走査セグメントは、それらの間のグラフ内を移動できる場合、複数の要件を満たすことができます。 

ただし、多くの発信要件があるルームでは、既存のセグメントにチェーンできる範囲を超えて、新たなスタートを余儀なくされる場合があります。 

### 3. 計算余剰の開始

 各要件には「開始容量」の単位が必要であると解釈します。 単一の歩行セグメントは 1 回の開始にのみ寄与するため、必要なセグメントの数は、そのような開始が全体で何回必要かによって決まります。 この定式化では、各要件が 1 単位に寄与するため、答えは、以前に開始されたトラバーサルに吸収できない要件の総数となり、すべてのノードの寄与のカウントが簡素化されます。 

### 4. 結果の出力

 出口の最小数は、すべての部屋で必要な開始ユニットの合計数に等しくなります。 

### なぜ効果があるのか

 重要な不変条件は、すべての有効な横断計画が一連の連続した歩行セグメントに分解され、各セグメントが出口のある部屋から始まるということです。 各ドアロック要件は、そのようなセグメントの 1 つ、具体的には最初に部屋に到達するセグメントに属します。`a`その要件が満たされたとき。 

連続性を失わずにセグメントをマージすることはできないため、すべての独立した「要件フローの単位」は終了によって開始される必要があります。 グラフの接続性によりルーティングの柔軟性が保証されるため、唯一の制約は独立した開始が必要な数だけであり、これはまさにカウント公式で把握されるものです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    out_req = [0] * (n + 1)

    for _ in range(m):
        a, b = map(int, input().split())
        out_req[a] += 1

    # each outgoing requirement corresponds to one needed initiation unit
    print(sum(out_req))

if __name__ == "__main__":
    solve()
```このソリューションでは、部屋全体に 1 つのカウンター配列のみが保存されます。 各入力エッジは、その開始エンドポイントで要件を増分します。 最終的な合計は、必要なすべての開始ユニットを集計し、必要な終了数に直接対応します。 

接続により制約間のルーティングが常に可能であることが保証されるため、トラバーサル検索やグラフ検索は必要ありません。 

よくある実装上の間違いは、移動をシミュレートしようとしたり、隣接リストを構築して DFS を実行しようとしたりすることです。 これは不必要であり、TLE と連鎖制約の誤った処理の両方の危険性があります。 

## 実用的な例

 ### 例 1

 入力:```

1 2
```ここで、部屋 1 には 1 つのロック要件があります。 

| ステップ | アウト_要求[1] | アウト要求[2] | 合計 |
 | --- | --- | --- | --- |
 | エッジ後 | 1 | 0 | 1 |

 結果は 1 です。これは、必要なロック アクションのみを開始するには 1 つの終了で十分であることを意味します。 

これにより、必要な 1 つの開始点が 1 つの出口に直接変換されることが確認されます。 

### 例 2

 入力:```
3 2
2 1
3 1
```| ステップ | アウト_要求[1] | アウト要求[2] | アウト要求[3] | 合計 |
 | --- | --- | --- | --- | --- |
 | 2→1の後 | 0 | 1 | 0 | 1 |
 | 3→1以降 | 0 | 1 | 1 | 2 |

これは、ロック要件が 2 つの別個の部屋から発生し、追加の出口がなければ 1 回の連続開始では満たすことができないため、2 つの独立した開始点が必要であることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m) | 各ドアは 1 回処理され、ノード間の合計は線形です。 
| スペース | O(n) | サイズ n の配列のみが維持されます。 

このソリューションは、入力に対して 1 回のパスと最終的な線形集計のみを実行するため、最大 1,000,000 枚のドアを簡単に処理できます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    out_req = [0] * (n + 1)

    for _ in range(m):
        a, b = map(int, input().split())
        out_req[a] += 1

    return str(sum(out_req))

# provided samples
assert run("2 1\n1 2\n") == "1"
assert run("3 2\n2 1\n3 1\n") == "2"

# custom cases
assert run("2 0\n") == "0", "no doors"
assert run("4 3\n1 2\n2 3\n3 4\n") == "3", "chain structure"
assert run("5 4\n1 2\n1 3\n1 4\n1 5\n") == "4", "star centered at 1"
assert run("3 3\n1 2\n2 3\n3 1\n") == "3", "cycle"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | エッジなし | 0 | 空のグラフ |
 | チェーン | 3 | 線形累積 |
 | 星 | 4 | 根の需要が大きい |
 | サイクル | 3 | 循環累積 |

 ## 特殊なケース

 ドアのない最小限のケースでは、ロック アクションが必要ないため、すぐに出口が 0 になります。また、要件配列が空のままであるため、アルゴリズムは正しく 0 を返します。 

星型のグラフでは、1 つの部屋がロック ソースとして他のすべての部屋に接続されます。たとえば、次のようになります。```
5 4
1 2
1 3
1 4
1 5
```アルゴリズムが増加します`out_req[1]`これは、4 つの独立したロック要件が同じ部屋から発生し、それぞれに開始容量が必要であることを反映しています。 

次のような循環構造の場合:```
3 3
1 2
2 3
3 1
```各ノードは 1 つの要件を正確に提供し、出力 3 を生成します。グラフの接続性は完全に対称ですが、ロック制約はエッジごとに独立しているため、連鎖がないため、個別の開始の必要性が軽減されます。
