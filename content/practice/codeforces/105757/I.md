 ## 解決策
 ## 問題の理解

 一連の整数が与えられ、その連続するセグメントを選択することができます。 各セグメントについて、そのすべての要素のビットごとの XOR を計算します。タスクは、考えられるすべてのセグメントの中で達成可能な最小の XOR 値を見つけることです。 

この問題を直接的に考えると、すべてのセグメントは 2 つのエンドポイントによって定義され、セグメントの値はプレフィックス XOR 値がそれらのエンドポイント間でどのように相互作用するかによって完全に決定されるということになります。 これにより、問題は「すべてのサブ配列」からプレフィックス状態に関する構造に変わります。 

入力形式は単純ですが、部分配列の数が配列の長さに応じて二次関数的に増加するという隠れた難しさがあります。 配列サイズが 10^5 程度の場合、すべてのセグメントを列挙するには、すでに約 10^10 の XOR 計算が必要になりますが、これは 2 秒の制限で処理できる範囲をはるかに超えています。 これにより、要素ごとにほぼ線形または対数線形の時間で処理できるものに問題を圧縮することが直ちに強制されます。 

すべての要素が同一である場合、または配列に多くのゼロが含まれる場合、微妙なエッジ ケースが発生します。 たとえば、配列が次の場合、`[7, 7, 7]`、すべての部分配列 XOR は次のいずれかです`7`または`0`長さに応じて最小値は`0`。 全範囲の XOR または隣接するペアのみをチェックする単純な実装では、長さ 2 のセグメントが完全にキャンセルされることを見逃してしまいます。 もう 1 つの特殊なケースは、次のような単一要素の配列です。`[5]`、答えはただここにあります`5`なぜなら、何かをキャンセルする空ではないセグメントを形成する方法がないからです。 

主な課題は、最適なセグメントが非常に短いか、配列全体にわたる可能性があり、セグメントの長さに単調性がないことです。 

## アプローチ

 ブルートフォースのアイデアは単純です。 実行中の XOR を維持しながら、左端を固定し右端を拡張することで、すべてのサブ配列の XOR を計算します。 これは、考えられるすべてのセグメントを列挙しているため、正しいです。 ただし、それぞれについて、`n`出発点から次まで拡張することができます`n`終わり、大まかに与える`O(n^2)`サブアレイ。 定数時間の XOR 更新を使用しても、これは依然として大きすぎます。`n`100,000に達します。 

これを改善するために、プレフィックス XOR を使用してサブ配列 XOR を書き換えます。 もし`pref[i]`最初の XOR です`i`要素、次にセグメントの XOR`[l, r]`になる`pref[r] XOR pref[l-1]`。 これにより、問題は、XOR が最小化される 2 つのプレフィックス値を見つけることに変換されます。 

ここで問題は、すべてのプレフィックス値の中から、XOR ができるだけ小さくなるように、任意の 2 つ (おそらく空のプレフィックスを含む) を選択することです。 これは、整数のセット内の最小の XOR ペアを見つけるという古典的な問題です。 

ここでバイナリ表現の構造が役に立ちます。 すべてのペアを比較する代わりに、プレフィックス値をバイナリ トライに挿入し、値ごとにトライを貪欲に実行して、XOR の意味で最も近い可能な値を見つけます。 各ビットで、現在のビットに一致する分岐をたどって XOR を小さく保ち、必要な場合にのみ逸脱することを好みます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | サブ配列に対するブルート フォース | O(n²) | お(1) | 遅すぎる |
 | プレフィックス XOR + バイナリ トライ | O(n log A) | O(n log A) | 承認済み |

 ここ`A`は最大値の範囲です (通常は最大 30 ビットまたは 60 ビット)。 

## アルゴリズムのチュートリアル

 1. 配列を左から右にスキャンしながら、プレフィックス XOR を計算します。`pref[0] = 0`。 これにより、すべてのサブ配列 XOR を 2 つのプレフィックス状態の XOR として表現できるようになります。 
2. これまでに確認されたすべてのプレフィックス XOR 値を保存するバイナリ トライを維持します。 各ノードは、挿入された数値のビット プレフィックスを表します。 
3. 最初のプレフィックスを挿入します`0`配列を処理する前にトライに取り込みます。 これは、インデックス 1 から始まるサブ配列を考慮します。 
4. 新しいプレフィックス値ごとに`x`、トライをクエリして、最小化する格納された値を見つけます。`x XOR y`。 このクエリ中に、最高位から最低位までの各ビットで、現在のビットに等しい分岐をたどろうとします。`x`存在する場合、ビットが一致するとその位置での XOR 寄与が減少するためです。 
5. クエリ中に、たどったパスを追跡して、達成可能な最良の XOR 値を蓄積します。 これにより、現在のプレフィックスに対する最小の XOR パートナーが生成されます。 
6. このクエリの結果を使用してグローバル回答を更新します。 
7.挿入`x`トライに追加すると、将来のプレフィックスで使用できるようになります。 

重要な設計上の選択は、現在のプレフィックスを挿入する前にクエリを実行することです。 これにより、プレフィックス順で右エンドポイントが厳密に左エンドポイントの後にある有効なペアのみが考慮されるようになります。 

### なぜ効果があるのか

 すべてのサブ配列はプレフィックス XOR のペアに対応し、プレフィックス XOR のすべてのペアは正確に 1 つのサブ配列 XOR を定義します。 try クエリ ステップでは、プレフィックスごとに、以前のすべてのプレフィックスの中から可能な最良のパートナーを計算し、すべての有効なペアが 1 回考慮されることを保証します。 XOR の最小化は辞書編集的に最上位ビットから下に向かって決定され、下位ビットは上位ビットの差を補償できないため、トライの貪欲なビットごとの降下は正しいです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class TrieNode:
    __slots__ = ("child",)
    def __init__(self):
        self.child = [None, None]

class BinaryTrie:
    def __init__(self):
        self.root = TrieNode()
        self.B = 31  # enough for typical constraints

    def insert(self, x):
        node = self.root
        for b in reversed(range(self.B)):
            bit = (x >> b) & 1
            if node.child[bit] is None:
                node.child[bit] = TrieNode()
            node = node.child[bit]

    def query_min_xor(self, x):
        node = self.root
        res = 0
        for b in reversed(range(self.B)):
            bit = (x >> b) & 1
            if node.child[bit] is not None:
                node = node.child[bit]
            else:
                res |= (1 << b)
                node = node.child[bit ^ 1]
        return res

def solve():
    n = int(input())
    arr = list(map(int, input().split()))

    trie = BinaryTrie()
    trie.insert(0)

    pref = 0
    ans = 10**30

    for v in arr:
        pref ^= v
        ans = min(ans, trie.query_min_xor(pref))
        trie.insert(pref)

    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは、プレフィックス XOR とそれらのプレフィックスに対するバイナリ トライの維持を中心に構築されています。 トライには以前のすべてのプレフィックス状態が保存され、新しいプレフィックスがそれと比較されて最適な XOR ペアが見つかります。 そのクエリは現在のインデックスで終わる最適なサブ配列に対応するため、答えは各クエリの直後に更新されます。 

よくある実装の落とし穴は、最初のコードを挿入し忘れることです。`0`接頭辞。 これがないと、インデックス 0 から始まるサブ配列は決して考慮されません。 もう 1 つの微妙な問題は、挿入とクエリの順序です。 これを逆にすると、プレフィックスとそれ自体のペアが誤って許可され、有効なサブ配列を表しません。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n・B) | 各プレフィックスは、トライ | 内の B ビットに対して挿入され、クエリされます。 
| スペース | O(n・B) | 挿入された各プレフィックスは最大で B トライ ノードを作成します。 

ビット長 B は固定されている (通常は約 31) ため、解は n において効果的に線形に動作します。 これは、最大 10^5 以上の n の一般的な制約内に問題なく適合します。

 ## 特殊なケース

 次のような単一要素配列の場合`[7]`、トライには最初に含まれています`0`, したがって、クエリは次の結果を返します。`7 XOR 0 = 7`、他に候補は存在しません。 アルゴリズムは正しく返します`7`それが可能な唯一の部分配列であるためです。 

次のような重複が交互に存在する配列の場合`[4, 4, 4, 4]`、プレフィックス XOR が繰り返し交互に繰り返されます。`4`そして`0`。 トライでは両方の値がすぐに蓄積され、2 番目ごとに一致する前のプレフィックスが検索され、XOR が生成されます。`0`。 これにより、偶数長のサブ配列がプレフィックス衝突を通じて適切に表現されることが確認されます。
