 ## 解決策
 ## 問題の理解

 整数の配列が与えられており、この配列のセグメントに対する「交互の合計」を含む演算をサポートする必要があります。 セグメントの交互の合計は、セグメントの最初の要素にプラス記号を付け、次の要素にマイナス記号を付け、次に再びプラスというように、左から右に移動するたびに符号を反転することによって計算されます。 

中心的なタスクは、複数のクエリを効率的に処理することです。 各クエリは、配列内の単一の位置を更新するか、連続する部分配列の交互の合計を要求します。 範囲にわたるクエリの場合$[l, r]$、結果は次の値になります。$a_l - a_{l+1} + a_{l+2} - \dots$からのインデックス距離によって純粋に決定される符号付き$l$グローバル配列内の元のパリティによるものではありません。 

入力サイズが十分に大きいため、範囲を反復して各クエリの合計を再計算すると時間がかかりすぎます。 まである場合$10^5$要素と$10^5$素朴な疑問$O(n)$クエリごとのアプローチにより、$10^{10}$通常の制限時間をはるかに超えた最悪の場合の操作。 このため、ポイント更新と高速範囲集約の両方をサポートする何らかの構造を維持する必要があります。 

プレフィックス合計を直接再利用しようとすると、微妙な問題が発生します。 交互の符号は、クエリの左側の境界によって異なります。 たとえば、配列を考えてみましょう。$[1, 2, 3, 4]$。 交互の合計$[1, 3]$は$1 - 2 + 3 = 2$, しかしセグメントをずらすと符号のパターンが全く変わります。 開始インデックスへのこの依存関係により、正規化しない限り直接プレフィックス合計が不十分になります。 

エッジ ケースは、更新によって値が変更され、多くの重複するクエリに影響を与える場合に発生します。 たとえば、配列が 1 つの更新された位置を除いてすべて 0 である場合、単純な再計算では影響を受けていない領域を繰り返し再スキャンすることになります。 もう 1 つのエッジ ケースは単一要素クエリです。この場合、符号規則に関係なく、答えはその位置の値にすぎず、縮退範囲であっても符号反転を誤って適用する実装では、誤った結果が返される可能性があります。 

## アプローチ

 ブルート フォース アプローチでは、交互の合計クエリを個別に計算します。 お問い合わせの場合$[l, r]$から反復します$l$に$r$、オフセット パリティに応じて要素を加算および減算します。 これは定義に直接従うため、単純かつ正しいです。 ただし、各クエリにはコストがかかります$O(r - l + 1)$、そして多くのクエリを繰り返すと、これは二次的な動作に退化します。 入力が大きい場合、数百億回の操作が必要になります。 

重要な観察は、交互の符号パターンが予測可能であり、配列自体の変換に吸収できることです。 新しい配列を定義すると$b[i] = a[i]$いつ$i$は均等であり、$b[i] = -a[i]$いつ$i$が奇数 (またはインデックス付け規則によってはその逆) の場合、プレフィックスの合計は次のとおりです。$b$固定原点から始まる交互の動作をエンコードします。 課題は、クエリが任意の位置で開始されるため、符号パターンをクエリの左側のエンドポイントに揃える必要があることです。 

この位置合わせは、変換された配列のプレフィックスの合計を保存し、そのパリティによって調整することで処理できます。$l$。 この変換が行われると、各範囲クエリは 2 つのプレフィックス合計の差になり、ポイント変更をサポートするフェンウィック ツリーまたはセグメント ツリーを使用して更新を処理できます。 

自然に適合する構造はフェンウィック ツリーです。これは、対数時間での両方の演算をサポートし、実装を単純に保つためです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n)$クエリごと |$O(n)$| 遅すぎる |
 | 符号変換を伴うフェンウィック ツリー | 写真$O(\log n)$クエリごと |$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 配列の変換されたバージョン上でフェンウィック ツリーを維持します。 

1. 各インデックスの変換値を定義します。$i$: 乗算する$a[i]$による$+1$または$-1$位置パリティに応じて。 これにより、クエリとは独立したグローバルな交互パターンが修正されます。 このステップの理由は、シフト符号の問題を静的な問題に変換するためです。 
2. この変換された配列上にフェンウィック ツリーを構築します。 これにより、変換された値のプレフィックス合計を効率的にクエリできるようになります。 
3. インデックスで更新を処理するには$i$、新しい変換された値と古い値の差を計算し、フェンウィック ツリーにポイント更新を適用します。 これにより、ツリーが常に現在の配列状態を反映するようになります。 
4. 質問に答えるため$[l, r]$、プレフィックスの合計を計算します。$r$プレフィックスの合計を減算して、$l - 1$ただし、クエリ内の交互符号が次の要素に依存するという事実を修正する必要があります。$l$。 もし$l$変換に対して誤ったパリティがある場合は、結果の符号を反転します。 
5. 調整した結果を答えとして返します。 

これが機能する重要な理由は、変換されたプレフィックスの合計が固定原点から始まる交互の累積を表すためです。 どのセグメントも、このような 2 つのプレフィックスの合計の差として表すことができ、唯一の不一致は、セグメントの開始パリティが変換の基本パリティと一致するかどうかです。 

### なぜ効果があるのか

 不変条件は、どの時点においても、フェンウィック ツリーが配列のグローバルに交互するバージョンのプレフィックスの合計を格納するということです。 この固定符号規則に基づいて、クエリ範囲の合計を 2 つのプレフィックスの累積に分解できます。 唯一の不一致はクエリ開始の相対的なシフトから生じ、この不一致は 1 回のパリティ修正によって完全に捕捉されます。 更新とクエリの両方で変換された表現の一貫性が維持されるため、一連の操作によってツリー状態と基礎となる配列の間に不整合が生じる可能性はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    n, q = map(int, input().split())
    a = [0] + list(map(int, input().split()))

    fw = Fenwick(n)

    def val(i):
        return a[i] if i % 2 == 0 else -a[i]

    for i in range(1, n + 1):
        fw.add(i, val(i))

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == '1':
            i = int(tmp[1])
            x = int(tmp[2])

            old = val(i)
            a[i] = x
            new = val(i)

            fw.add(i, new - old)

        else:
            l, r = int(tmp[1]), int(tmp[2])

            res = fw.sum(r) - fw.sum(l - 1)

            if l % 2 == 1:
                res = res
            else:
                res = -res

            print(res)

if __name__ == "__main__":
    solve()
```フェンウィック ツリーは、変換された配列のプレフィックスの合計を維持することのみを担当します。 の`val(i)`関数はグローバルな交互パターンをエンコードします。 更新では、以前に変換された値に対してデルタが計算されるため、ツリーの一貫性が維持されます。 

クエリ ロジックは、変換された空間内の範囲の合計がインデックス 1 から始まる交互の合計に対応するという事実に依存しています。実際のクエリが異なるパリティで始まる場合は、符号を 1 回反転します。 

よくある実装の落とし穴は、更新で符号変換も適用する必要があることを忘れていることです。 もう 1 つは、0 ベースと 1 ベースのインデックス付けを混合することです。これにより、パリティ アラインメントが静かに破壊されます。 

## 実用的な例

 配列を考えてみましょう$[1, 2, 3, 4]$交互の合計を求めるクエリを使用します。$l = 2$に$r = 4$。 

私たちは変革された価値観を維持します$b[i] = (+a[i], -a[i], +a[i], -a[i])$パリティに応じて。 

| ステップ | l | r | フェンウィック・サム(r) | フェンウィック・サム(l-1) | 生の範囲 | パリティ修正 | 答え |
 | --- | --- | --- | --- | --- | --- | --- | --- |
 | クエリ | 2 | 4 | 計算された | 計算された | b[2]+b[3]+b[4] | サインフリップ | 最終 |

 生の変換された合計は、固定起源の交互シーケンスに対応し、パリティ補正によりインデックス 2 から始まるシーケンスと整列されます。これは、クエリごとに符号を再計算しないことを示しています。 単一のグローバル解釈を調整するだけです。 

ここで、シングルポイント更新の変更を検討してください。$a[3]$。 フェンウィック ツリーは、新しい変換値と古い変換値の差分を使用してインデックス 3 でのみ更新されます。 更新の前後のクエリには変更が即座に反映され、動的変更下でも構造の一貫性が維持されることがわかります。

 ## 特殊なケース

 次のような単一要素セグメント$[i, i]$常に戻ってくるはずです$a[i]$パリティ変換とは関係ありません。 このアルゴリズムでは、変換された配列に対するフェンウィックの合計により、次のいずれかが得られます。$+a[i]$または$-a[i]$ただし、パリティ補正は必要に応じてその効果をキャンセルし、元の値に戻します。 たとえば、次の場合$a = [5]$、クエリする$[1,1]$範囲の減算が発生せず、符号補正が固定基数と一致するため、5 が生成されます。 

別の特殊なケースは、最初または最後の要素を繰り返し更新することです。 各更新は 1 つの Fenwick インデックスにのみ影響するため、構造は安定したままになります。 たとえば、以下から始めます$[1, 2, 3]$、インデックス 1 を 10 に更新すると、位置 1 に格納されているデルタのみが変更されます。後続の範囲クエリでは、これが再計算なしですぐに反映され、更新されたインデックスの外側に隠れた依存関係が存在しないことが確認されます。
