 ## 解決策
 ## 問題の理解

 私たちは 1 つのシーケンスを与えられていますが、それはもともと 2 つの隠れたシーケンスを取得し、それらをインターリーブすることによって形成されたと言われます。 1 つの隠れたシーケンスは厳密に増加し、もう 1 つは厳密に減少し、マージ中に内部順序は維持されましたが、それらの要素は任意の位置で混合されました。 

私たちの仕事は、元のシーケンス自体を再構築することではなく、そのような分割が可能かどうかを判断することだけです。 可能であれば、指定された配列内の各位置を 2 つのシーケンスのいずれかに割り当てる必要があります。 1 つのラベルは増加シーケンスを表し、もう 1 つのラベルは減少シーケンスを表します。 

難しいのは、厳密な順序付けに違反する場合、両方のシーケンスに同じ値を出現させることができないことです。また、要素をシーケンスに割り当てた後は、同じシーケンスの以前に割り当てられたすべての要素に対する単調性制約との一貫性を維持する必要があります。 

制約$n \le 2 \cdot 10^5$すべてのパーティションを試行するアプローチは除外されます。 単純なサブセットの割り当てでは、$2^n$可能性はありますが、それは完全に不可能です。 すべての分割にわたる 2 次 DP でさえ遅すぎます。 

微妙なエッジケースは、値が繰り返される場合、または貪欲な代入が局所的には有効であるように見えても、後で矛盾が生じる場合に発生します。 たとえば、次のようなシーケンス$[3, 1, 2, 0]$柔軟性があるように見えますが、貪欲な代入は、後で 1 つのシーケンスを簡単にトラップして単調性制約に違反させる可能性があります。 もう 1 つの失敗例は、両方のシーケンスがあまりにも早く「使い果たされる」高低交互パターンです。 

中心的な課題は、将来の柔軟性を考慮しながら、増加する制約と減少する制約の両方を同時に尊重する方法で各要素を割り当てる必要があることです。 

## アプローチ

 ブルート フォース ソリューションでは、あらゆる方法で各要素を増加シーケンスまたは減少シーケンスのいずれかに割り当て、その後、両方のシーケンスを個別に検証します。 各割り当てについて、両方のサブシーケンスをスキャンして、厳密な単調性をチェックします。 これには必要です$2^n$課題と$O(n)$それぞれを検証することで、$O(n \cdot 2^n)$、合理的な制限をはるかに超えています。 

重要な点は、各シーケンスで最後に使用された値を追跡するだけでよいということです。 配列を左から右に処理する場合、各位置で、現在の値を増加シーケンスに入れるか減少シーケンスに入れるかを決定します。 制約は 2 つの「フロンティア」を維持することになります。増加するシーケンスに配置される最後の値は厳密に増加する必要があり、減少するシーケンスに配置される最後の値は厳密に減少する必要があります。 

ただし、現在の比較に基づいて貪欲に選択することは失敗します。ローカルでは両方の選択が有効である場合もありますが、将来の実現可能性を維持できるのはどちらか 1 つだけであるためです。 正しい構造は、これを 2 つの状態が進行する決定問題として扱い、指定された最終値構成で各プレフィックスを処理した後に、ある状態に到達できるかどうかを追跡することです。 

これを解決する標準的な方法は、2 つの動的状態を維持することです。1 つは最後に選択された増加値を表し、もう 1 つは最後に選択された減少値を表します。 各ステップで両方の割り当てを試しますが、不可能な遷移は排除します。 値には制限があるため、プレフィックスごとに各ロールの実行可能な最小限の最後の値のみを保持することによって状態を圧縮します。 重要な洞察は、実現可能性を得るには、各プレフィックスを処理した後、各シーケンスに対して可能な限り最良の境界条件を維持するだけで十分であるということです。 

これにより、制限された方法で両方の可能性をシミュレートし、両方のシーケンスを可能な限り柔軟に保つ割り当てを常に優先する、線形の貪欲な伝播が生じます。

 ## アルゴリズムのチュートリアル

 2 つの値を維持します。増加シーケンスに対して選択された最後の要素と、減少シーケンスに対して選択された最後の要素です。 最初は両方とも未定義であり、無限に柔軟な境界として扱います。 

配列を左から右に処理し、各要素をどこに割り当てるかを決定します。 

1. 現在の値が増加シーケンスを拡張できる場合 (つまり、最後の増加値よりも厳密に大きい場合)、その値をそこに配置することを検討します。 
2. 減少シーケンスを拡張できる場合 (最後の減少値よりも厳密に小さいことを意味します)、そこに配置することも検討します。 
3. 両方の選択肢が可能な場合は、今後のステップでより柔軟性を維持できる方を選択します。 具体的には、値が大きい場合、減少シーケンスの制限がより厳しくなるため、すぐに減少シーケンスが不可能にならない場合は、増加シーケンスに配置することを好みます。 
4. 割り当てが 1 つだけ可能な場合は、それを引き受けなければなりません。 
5. どちらの割り当ても不可能な場合は、直ちに分割は不可能であると結論付けます。 
6. 割り当てを記録し、対応する最終値トラッカーを更新します。 

このアルゴリズムは貪欲ですが、任意の優先順位ではなく、実現可能性の制約によって導かれます。 

### なぜ効果があるのか

 アルゴリズムは、配列のどのプレフィックスでも、現在の最終値の状態と一致する、処理されたすべての要素の有効な割り当てが存在するという不変条件を維持します。 実行可能な継続が存在する場合、各決定は少なくとも 1 つの継続を保持します。 単調性制約は、最後に選択された値によってのみ各シーケンスの将来の自由度を低下させるため、有効な最後の値を保存するだけで、将来のすべての可能性を特徴付けるのに十分です。 解が存在する場合は常に、各ステップで少なくとも 1 つの実行可能な拡張が保持されるため、矛盾なく最後まで到達すると、有効な分割が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    inc_last = -10**18
    dec_last = 10**18
    res = []
    
    for x in a:
        can_inc = x > inc_last
        can_dec = x < dec_last
        
        if not can_inc and not can_dec:
            print("NO")
            return
        
        # Prefer the assignment that keeps future flexibility
        if can_inc and (not can_dec or x - inc_last <= dec_last - x):
            res.append(0)
            inc_last = x
        else:
            res.append(1)
            dec_last = x
    
    print("YES")
    print(*res)

if __name__ == "__main__":
    solve()
```この解では 2 つの境界変数が維持されます。`inc_last`増加シーケンスで使用された最後の値を追跡します。負の無限大に初期化されているため、どの値でも開始できます。`dec_last`減少シーケンスで使用された最後の値を追跡し、正の無限大に初期化されます。 

各ステップで、現在の値がいずれかのシーケンスを拡張できるかどうかをテストします。 どちらも不可能な場合、構築は直ちに失敗します。 

タイブレーク条件は、1 つのシーケンスが時期尚早に締め付けられることを避けるように設計されています。 両方の配置が可能な場合は、値がその境界からどれだけ離れているかによって測定され、もう一方のシーケンスにより多くの余地を残す方を選択します。

 ## 特殊なケース

 単一要素の配列は、単調性制約を破ることなくどちらのシーケンスにも属することができるため、常に有効です。 最初は両方の遷移が可能であるため、アルゴリズムはデフォルトでそれを増加シーケンスに割り当てます。 

厳密に増加する配列の場合、減少シーケンスは必要ありません。 アルゴリズムは常に増加するシーケンスに代入し続けます。`can_inc`真実のままであり、`can_dec`最初のステップ以降は関係なくなります。 

厳密に減少する配列の場合、最初の要素が増加するものに割り当てられた後、後続のすべての要素は減少するシーケンスに移る必要があります。 境界の増加によってさらなる割り当てがブロックされると、アルゴリズムは役割を正しく切り替えます。 

ハイとローを交互に繰り返すシーケンスでは、両方の選択肢が利用できることがよくあります。 タイブレーク ルールは、境界間に大きな余裕を残す割り当てを優先することで時期尚早のコミットメントを防止し、プロセスが誤って早期に実現可能性を排除してしまうことがないようにします。
