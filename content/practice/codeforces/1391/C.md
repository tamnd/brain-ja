 ## 解決策
 ## 問題の理解

 数字の順列が与えられています`1...n`。 その順列から、配列のインデックスに基づいてグラフが構築されます。 

あらゆるポジションについて`i`、そのような要素が存在する場合は常に、左側の最も近い大きな要素と右側の最も近い大きな要素に接続します。 グラフには方向性がありません。 

結果のグラフに少なくとも 1 つの単純なサイクルが含まれる場合、置換は循環的と呼ばれます。 タスクは、特定の順列のグラフを構築することではありません。 その代わりに私たちに与えられているのは、`n`、長さの順列が何回あるかを数えなければなりません`n`サイクルを含むグラフを作成します。 

答えはモジュロで報告する必要があります`10^9 + 7`。 

制約は重要な観察です。 ここ`n`と同じ大きさにすることができます`10^6`。 これほど大きな値を指定すると、個々の順列を考慮するアプローチが即座に除外されます。 がある`n!`順列を生成することさえ不可能です。 値を線形または線形に近い時間で計算できる純粋に数学的な計数式が必要です。 

グラフの構築は複雑に見えますが、この制約は、最終的な答えが順列を 1 つずつ調べるのではなく、そのようなすべてのグラフの構造特性に依存する必要があることを強く示唆しています。 

よくある間違いは、グラフにはさまざまなタイプのサイクルが含まれている可能性があり、それらを直接カウントする必要があると想定することです。 たとえば、`n = 4`、 がある`24`順列、およびサイクルを手動でチェックすることは実行可能と思われます。 のために`n = 10^6`、その視点は絶望的です。 

もう 1 つの簡単な罠は、グラフが接続されている順列を数えることです。 つながりはサイクルを含むことと同じではありません。 ツリーは接続されており、非循環的です。 この区別こそが、まさに解決策の鍵を握るものであることがわかります。 

## アプローチ

 ブルート フォース ソリューションでは、すべての順列を生成し、グラフを構築し、DFS などのグラフ アルゴリズムを実行してサイクルを検出します。 

単一の順列の場合、各辺で最も近い大きい要素を見つけるには、次の単調スタックを使用します。`O(n)`。 周期検出も`O(n)`。 したがって、1 つの順列は線形時間で処理できます。 

問題は順列の数です。 がある`n!`彼らのうち。 たとえ`n = 15`、これはもう`1.3 × 10^12`可能性。 ブルートフォース手法は、ほぼすぐに使用できなくなります。 

画期的な発見は、この構造によって生成されるグラフを理解することから始まります。 

このグラフはよく知られたデカルト ツリー グラフです。 順列の最大要素を取ると、それが根になります。 再帰的に、左側の要素は左側のサブツリーを形成し、右側の要素は右側のサブツリーを形成します。 

重要な特性は、ステートメントで構築されたグラフが常に接続されていることです。 最大要素を除くすべてのノードには、より大きな要素への接続が少なくとも 1 つあるため、すべての頂点が最終的​​にグローバル最大値に到達できます。 

次にエッジの数を考えてみましょう。 

すべての位置は、左側の最も近い大きな要素に最大 1 つのエッジを寄与でき、右側の最も近い大きな要素に 1 つのエッジを寄与できます。 この構造をより深く分析すると、結果のグラフが正確に`n - 1`順列が分岐サイクルのないデカルト ツリーに対応する場合に限り、エッジ。 実際、最大の要素が順列の端の 1 つに位置する場合、グラフは正確にツリーになり、残りの部分の両方に再帰的に同じ特性が当てはまります。 

この再帰的条件は、現在の最大残り値を左端または右端のいずれかに繰り返し配置することによって得られる順列を特徴づけます。 

このような順列はいくつ存在しますか?

 場所`n`初め。 それは一端にあるはずです。 

取り外し後`n`、同じ条件が次の場合にも当てはまります。`n-1`。 

それぞれの値について、`n`まで`2`、残りのシーケンスの左端に行くか右端に行くかを独自に選択します。 

それはまさに`2^(n-1)`グラフがツリーである順列。 

すべての順列は接続されたグラフを生成するため、グラフがツリー**ではない**場合、グラフは正確に循環的になります。 

順列の合計数は、`n!`。 

したがって、次のようになります。$$\text{cyclic permutations} = n! - 2^{\,n-1}$$すべての計算はモジュロで実行されます`10^9+7`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n・n!) | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.読む`n`。 
2. コンピューティング`n! mod M`、 どこ`M = 10^9 + 7`。 
3. コンピューティング`2^(n-1) mod M`。 
4. 最初のモジュロから 2 番目の値を減算します。`M`。 
5. 結果を出力します。 

唯一重要な部分はカウント引数です。 非循環グラフが正確に再帰的なエンドマックス順列であることがわかれば、それらを数えることは単純な 2 の累乗になります。 

### なぜ効果があるのか

 構築によって生成されたすべてのグラフは接続されています。 接続されたグラフ`n`頂点が非循環であるのは、頂点に正確に含まれている場合に限ります。`n-1`エッジ、つまり木です。 

ツリーを生成する順列は、現在の最大要素が常に現在の間隔の端の 1 つに現れる順列です。 最大値を削除しても何も分割されず、同じ条件が残りの要素に対して再帰的に保持される必要があります。 

このような順列を最大から最小まで構築すると、各値には左端または右端の 2 つの選択肢があります。 がある`n-1`独立した決定、譲歩`2^(n-1)`ツリーを生成する順列。 

あるので`n!`合計の順列、少なくとも 1 つのサイクルを生成する数は次のとおりです。$$n! - 2^{n-1}.$$## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

n = int(input())

fact = 1
for i in range(2, n + 1):
    fact = (fact * i) % MOD

trees = pow(2, n - 1, MOD)

print((fact - trees) % MOD)
```実装はカウント式に直接続きます。 

最初のループは計算します`n!`モジュロ`10^9+7`。 以来`n ≤ 10^6`100 万回のモジュラー乗算は簡単に十分に高速です。 

Python の組み込みモジュール累乗計算`2^(n-1)`で`O(log n)`時間。 

減算はモジュロで実行されます`MOD`。 表現```
(fact - trees) % MOD
```負の中間値を正しく処理します。 

再帰は使用されないため、最大の入力に対する再帰の深さの問題が回避されます。

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io

MOD = 10**9 + 7

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    n = int(sys.stdin.readline())

    fact = 1
    for i in range(2, n + 1):
        fact = (fact * i) % MOD

    trees = pow(2, n - 1, MOD)

    return str((fact - trees) % MOD)

# provided sample
assert run("4\n") == "16", "sample"

# minimum valid n
assert run("3\n") == "2", "minimum size"

# small manual case
assert run("5\n") == "104", "5! - 2^4 = 120 - 16"

# another small manual case
assert run("6\n") == "688", "720 - 32"

# large boundary case, just verify execution and range
ans = int(run("1000000\n"))
assert 0 <= ans < MOD
```| テスト入力 | 期待される出力 | 検証内容 |

 ## 特殊なケース

 最小の有効な入力を考えてみましょう。```
3
```アルゴリズムは計算します$$3! - 2^2 = 6 - 4 = 2.$$カウントに関する議論は引き続き適用されます。 ツリーを生成する順列が 4 つと循環順列が 2 つあります。 特別な取り扱いは必要ありません。 

減算が負のモジュロになる場合を考えてみましょう。`MOD`。 より大きな値の場合、`n`、 両方`n! mod MOD`そして`2^{n-1} mod MOD`は剰余であり、元の数値ではありません。 その可能性は十分にあります$$(n! \bmod MOD) < (2^{n-1} \bmod MOD).$$使用する```
(fact - trees) % MOD
```結果を正しい剰余クラスに自動的に変換し、よくあるモジュラー算術のバグを回避します。 

最大入力を考慮してください。```
1000000
```このアルゴリズムは、100 万回の剰余乗算と 1 回のべき乗剰余演算を実行します。 に比例する配列はありません`n`が割り当てられ、再帰は使用されません。 このソリューションは、メモリと時間の制限内に快適に収まります。
