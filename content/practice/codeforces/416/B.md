 ## 解決策
 ## 問題の理解

 私たちは生産ラインを与えられており、複数の絵画が一定の順序の画家によって移動されます。 すべての絵画は、最初から最後まで順番にすべての画家を通過する必要があります。 各ペインターは独自のキューでピクチャを順番に処理し、同時に複数のピクチャを処理することはできません。 ただし、画家が絵の自分の役割を終えると、その絵はすぐに次の画家が利用できるようになりますが、その絵はすでに待っているか忙しい場合があります。 

各画像の処理時間はペインターごとに異なります。 目標は、すべての絵について、最終段階が終了する正確な瞬間、つまり最後の画家を離れる正確な瞬間を判断することです。 

これを考えるのに役立つ方法は、複数のステージを持つパイプラインです。 各ステージには 1 つのワーカーとジョブのキューがあり、各ジョブはすべてのステージを順番に通過する必要があります。 この難しさは、ペインターが新しい絵を開始できるのは、前のペインターから絵が到着し、ペインターが空いている場合のみであるという事実にあります。 

制約は重要です。 画像の数は最大 50,000 枚まで可能ですが、ペインターの数は最大 5 人です。これにより、時間を段階的にシミュレートしたり、画像ごとに完全なスケジュールを個別に再計算しようとしたりするアプローチは即座に排除されます。 画像の数が二次関数に近いものは遅すぎます。 

素朴な誤解は、各画像が時間の合計として独立して処理できると考えることから生じることがよくあります。 これにより、パイプラインのブロックによる待機が無視されます。 たとえば、2 つのピクチャの両方が最初のペインターを長時間必要とする場合、順序に応じて後のペインターがアイドル状態になったり混雑したりする可能性があります。 

各画家が前の絵を描き終えた直後に新しい絵を描き始めると仮定すると、別の微妙な失敗例が現れます。 これは、その絵が前の画家からまだ到着していない可能性があるという事実を無視しています。 

小さな失敗例:

 入力:```
2 2
5 1
1 5
```ピクチャごとの合計を誤ると、両方とも時間 6 で終了します。正しい動作は異なります。2 番目のペインタは、最初のペインタがリリースするまで 2 番目のピクチャを開始できないため、遅延が発生します。 

これが中心的な課題です。つまり、連続したキュー間のグローバル同期です。 

## アプローチ

 直接シミュレーションでは、すべてのペインターおよびすべての画像について、いつ利用可能になり、いつペインターが空くかを追跡します。 それぞれの画像について、すべてのペインターにそれを伝播し、利用可能な時間を更新します。 これは正しいのですが、各ピクチャには O(n) ステップが必要で、最大 50,000 枚のピクチャがあり、約 250,000 回の操作が必要になります。これは問題ありませんが、ループ内の待機条件の単純なシミュレーションは、実装が非効率な場合、簡単に性能が低下する可能性があります。 ただし、本当の問題は、時間を継続的にシミュレートしたり、次に利用可能なスロットを検索しようとすると、速度が非常に遅くなるということです。 

重要な観察は、システムが厳密な階層構造を持っていることです。 各ペインターは固定順序でピクチャを処理するため、ペインター j とピクチャー i の開始時間は 2 つの値のみに依存します。ペインター j が空になったときと、ペインター j-1 からピクチャー i が到着したときです。 順番に処理していくとどちらも分かります。 

これにより、2D グリッドに対する動的プログラミングの定式化が可能になります。 dp[i][j] は、ピクチャ i がペインタ j を終了する時間です。 各状態は、dp[i][j−1] (前のペインターからの到着) と dp[i−1][j] (前のピクチャーの後でペインターがフリーになったとき) にのみ依存します。 n が小さいため、前の行と現在の行のみ、またはペインターごとに 1D 配列のみを維持できます。 

画像を入力順に処理し、各ペインターを順番に更新し、前の画像のペインターごとの完了時間を維持します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(m・n) | O(m・n) | 受け入れられるがやりすぎ |
 | パイプライン DP | O(m・n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 配列を維持します`finish[j]`ペインター j が前の画像を処理した後、自由になる時間を表します。 

各画像 i について、その完了時間を段階ごとに計算します。 

1. 変数を初期化する`current_time`この画像の場合、ペインター 1 に画像が到着した時刻を表します。画像は順番に処理されるため、これは単にペインター 1 が空になったとき、つまり、ペインター 1 が空になったときです。`finish[0]`。 
2. 0 から n−1 までの各ペインター j について、このペインターが絵の作業を開始できる瞬間を計算します。 これは、前の画家から絵が届くまでの時間と、この画家が以前の作業から解放される時間の最大値です。 つまり:`start = max(current_time, finish[j])`。 
3. 画家の支出`t[i][j]`時間単位なので、この段階での終了時間は次のようになります。`start + t[i][j]`。 
4.アップデート`finish[j]`ペインター j は、その時点まで将来の画像のために占有されているため、この新しい値に設定されます。 
5. この終了時間を次のように伝播します。`current_time`、次の画家の到着時間になります。 
6. すべてのペインターを処理した後、最終的な`current_time`絵の完成時間です。 

重要なアイデアは、各ステーションに「ビジー ンティル」タイムスタンプがあるチェーンを通じて単一の移動ジョブをシミュレートしているということです。 

### なぜ効果があるのか

 いつでも、ペインター j でのピクチャー i のスケジュールに関連する情報は、いつ j-1 からピクチャーが到着するか、いつペインター j が空くかだけです。 どちらの値も、以前に処理された画像によって完全に決定されます。 写真を順番に加工していきますので、`finish[j]`は常に、以前のピクチャによって引き起こされた正しいブロッキング時間を表します。 この不変条件により、有効な依存関係が決して上書きされず、すべての開始時間がローカルに最適でグローバルに一貫したものになることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    m, n = map(int, input().split())
    
    finish = [0] * n
    res = []

    for _ in range(m):
        t = list(map(int, input().split()))
        
        current = 0
        
        for j in range(n):
            start = max(current, finish[j])
            current = start + t[j]
            finish[j] = current
        
        res.append(current)

    print(*res)

if __name__ == "__main__":
    solve()
```このソリューションでは、パイプラインの状態をコンパクトに表現します。 配列`finish`各ペインタが利用可能になったときに保存し、`current`現在の画像が次の段階に到達した時点を追跡します。 

重要なのは更新の順序です。 更新しなければなりません`finish[j]`古い値を使用して開始時間を計算した後にのみ。 これにより、ペインターが誤って現実よりも早く開始することを許可することがなくなります。 

各画像は独立して処理されますが、共有状態を通じてリンクされます。`finish`。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    m, n = map(int, input().split())
    finish = [0] * n
    res = []

    for _ in range(m):
        t = list(map(int, input().split()))
        current = 0
        for j in range(n):
            start = max(current, finish[j])
            current = start + t[j]
            finish[j] = current
        res.append(current)

    return " ".join(map(str, res))

# provided sample
assert run("5 1\n1\n2\n3\n4\n5\n") == "1 3 6 10 15"

# all equal times
assert run("3 2\n1 1\n1 1\n1 1\n") == "2 4 6"

# single picture multiple painters
assert run("1 3\n5 1 2\n") == "8"

# pipeline blocking
assert run("2 2\n5 1\n1 5\n") == "6 11"

# maximum n=1 edge
assert run("4 1\n2\n2\n2\n2\n") == "2 4 6 8"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | すべて同じ時間 | 逐次累積 | 均一なパイプライン動作 |
 | 単一の写真 | 純粋なチェーン依存性 | 画像間ブロッキングなし |
 | ブロッキングケース | キューの干渉 | 順序付け効果 |
 | n=1 | 縮退したパイプライン | プレフィックスの合計に換算します |

 ## 特殊なケース

 特殊なケースの 1 つは、塗装担当者が 1 人だけである場合です。 システムは単純なシーケンスに縮退し、各ピクチャは前のピクチャが終了した後にのみ開始されます。 アルゴリズムはこれを自然に処理します。`finish[0]`常に最後の完了時間を追跡し、`current`単に継続時間を蓄積するだけです。 

もう 1 つのケースは、後のペインターが以前のペインターよりも遅く、ボトルネックを引き起こす場合です。 そのような場合には、`finish[j]`多くの写真の開始時間の大半を占めています。 max 操作により、どの画像もボトルネックを回避できなくなり、画像の伝播が防止されます。`current`キューの構築を正しくモデル化します。 

最後の微妙なケースは、絵が画家の自由時間よりも遅く到着する場合に発生します。つまり、画家は待たなければなりません。 の`max(current, finish[j])`はこれを明示的に取得し、否定的または時期尚早なスケジューリングを防止し、特別な処理を行わなくても正確さを保証します。
