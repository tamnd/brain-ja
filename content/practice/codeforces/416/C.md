 ## 解決策
 ## 問題の理解

 予約リクエストのコレクションが渡されました。各リクエストは、全員が一緒に着席するか、まったく来ないゲストのグループを表します。 各リクエストには、到着する人数を意味するサイズと、そのグループが受け入れられて着席した場合にレストランが得る金額を意味する利益があります。 

これに加えて、それぞれに収容人数が設定された固定テーブルのセットが与えられます。 テーブルは最大 1 つのグループをホストでき、グループは少なくともグループ サイズ以上の収容人数を持つテーブルにのみ着席できます。 各テーブルは最大 1 回使用され、各リクエストは 1 つの適切なテーブルに割り当てられるか、完全に拒否されます。 目的は、総利益を最大化する方法で、リクエストのサブセットを選択し、それらを個別のテーブルに割り当てることです。 

キーのテンションが明確な入力構造となっております。 重みを最大化するためにアイテムの一部のみを選択しながら、容量の制約の下で 2 つのマルチセットからアイテムを照合します。 両側のスキップが許可されているため、これは純粋なマッチングの問題ではありません。また、容量は連続的なバジェットではなく個別のオブジェクトであるため、単純なナップザックではありません。 

制約は小さく、リクエストの数とテーブルの数は両方とも最大 1000 で、容量とグループ サイズは 1000 によって制限されます。これは、n² または n² log n 程度の解は受け入れられるが、1000 要素を超える 3 次の要素は境界線であり、不要であることをすぐに示唆します。 

正確性を保つためには、いくつかの特殊なケースが重要です。 

1 つのケースは、すべてのテーブルがすべてのリクエストに対して小さすぎる場合です。 たとえば、リクエスト`(5, 10)`とテーブル`[1, 2]`受け入れられた予約はゼロになります。 利益に貪欲な単純な人は、それでも割り当てを試みるかもしれませんが、正しく失敗するはずです。 

もう 1 つのケースは、複数のテーブルが同じリクエストを処理できる場合です。 たとえば、サイズ 3 とテーブルのリクエスト`[3, 5, 10]`。 最初にそれを最大のテーブルに割り当てると、大きなテーブルにのみ適合する将来のより大きなリクエストがブロックされ、総利益が減少する可能性があります。 

3 番目のケースは、2 つの大きな利益リクエストが 1 つの大きなテーブルをめぐって競合する一方で、小さなリクエストは他の場所に収まる場合です。 利益だけを考えて貪欲に考えていると、大きなテーブルが間違って割り当てられ、より適切なグローバル割り当てが妨げられる可能性があります。 

## アプローチ

 ブルート フォース ビューでは、リクエストをテーブルに直接割り当てることを検討します。 リクエストごとに、適合する未使用のテーブルにリクエストを割り当て、すべての組み合わせを再帰的に探索することができます。 これは事実上、リクエストとテーブル間のすべての一致に対する検索となり、各ステップでリクエストをスキップするか、潜在的に k 個のテーブルの 1 つにリクエストを割り当てます。 

最悪の場合、この分岐は非常に急速に成長します。 割り当ての選択肢だけを考慮したとしても、各リクエストは最大 k 個の可能性に分岐する可能性があり、およそ O(k^n) の構造が得られますが、これは実現可能性をはるかに超えています。 

重要な点は、構造が基本的に重み付きの 2 部マッチングですが、テーブルの容量が小さい整数であり、複数のテーブルが同じ容量を共有できるという非常に特殊な制約があることです。 これにより、テーブルを個別に扱うのではなく、テーブル側を容量ごとのカウントに圧縮することができます。 

テーブルを容量別にソートし、各容量がどれだけ残っているかを管理したら、問題はリクエストを 1 つずつ選択し、それらを利用可能な互換性のある容量に配置するかどうかを決定することになります。 これは、リクエストに対する動的プログラミングと利用可能なテーブル容量の配分を示唆しています。 ただし、より効率的な解釈は、リクエストを固定順序で処理し、小さなリクエスト用に常に小さなテーブルを予約する構造を使用して、リクエストを可能な限り最適なテーブルに貪欲に割り当てることです。 

標準的な手法は、リクエストを利益の降順に並べ替え、各リクエストをそれを収容できる最小のテーブルに割り当てようとすることです。 大きなテーブルは大きなリクエストに対してより価値があり、小さなリクエストでテーブルを無駄にすると将来の実現可能性が低下するため、これは最適です。 

使用可能なテーブルを頻度配列または並べ替えられた構造で維持し、リクエストごとに二分探索を実行して使用可能な最小のテーブルを見つけることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(k^n) | O(n + k) | 遅すぎる |
 | 最適 (貪欲 + 検索) | O(n log k) | O(k) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、特定のグループ サイズに対してどのテーブルが利用可能であるかを効率的にクエリできるようにテーブルを構造化します。 

1. すべてのテーブル容量を昇順に並べ替えます。 これにより、リクエストに適合する最小のテーブルを常に見つけることができます。 
2. リクエストを利益の降順に並べ替えます。 その理由は、後で最適に配置するのが難しいため、より高い利益のリクエストを最初に検討する必要があるということです。 
3. 要求ごとに、ソートされたテーブル リストに対して二分検索を実行して、少なくともグループ サイズ以上の容量を持つ最小の未使用テーブルを見つけます。 
4. そのようなテーブルが存在する場合は、そのテーブルにリクエストを割り当て、テーブルを使用済みとしてマークし、応答に利益を追加します。 
5. 適切なテーブルが存在しない場合は、リクエストをスキップします。 
6. 出力を再構築できるように、割り当てをリクエスト インデックスとテーブル インデックスのペアとして保存します。 

微妙なのは、テーブルが一度使用されると永久に削除されるため、削除をサポートする構造を維持する必要があることです。 k が小さいため、マーキング付きの単純なリスト、または二分探索と削除を実装したマルチセットのような構造で十分です。 

### なぜ効果があるのか

プロセスのどの時点でも、すべての未割り当てのリクエストの中で、最も利益の高いリクエストを、それを収容できる最小のテーブルに最初に配置しようとするという特性を維持します。 これにより、代替割り当てではより大きなテーブルが不必要に使用されるか、後で必要になるより大容量のテーブルがブロックされるため、総利益を減少させることなく、受け入れられたリクエストを別のリクエストとスワップできないという不変条件が維持されます。 貪欲な選択により、容量の不足とリクエスト サイズの順序が調整され、大きなテーブルを使用できる唯一のテーブルが大きなリクエストに対して確実に保存されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
requests = []
for i in range(n):
    c, p = map(int, input().split())
    requests.append((p, c, i + 1))

k = int(input())
tables = list(map(int, input().split()))

tables.sort()
used = [False] * k

requests.sort(reverse=True)

assignments = []
total = 0

for p, c, idx in requests:
    best = -1
    for j in range(k):
        if not used[j] and tables[j] >= c:
            best = j
            break
    if best != -1:
        used[best] = True
        total += p
        assignments.append((idx, best + 1))

print(len(assignments), total)
for a, b in assignments:
    print(a, b)
```このソリューションではテーブルを 1 回ソートするので、常に最小容量から最大容量までスキャンできます。 の`used`配列により、各テーブルが最大 1 回使用されることが保証されます。 

リクエストは利益の降順に並べ替えられるため、貪欲な注文が行われます。 リクエストごとに、テーブルを線形にスキャンして、最初に適合する利用可能なテーブルを見つけます。 k ≤ 1000 の場合、この O(nk) スキャンは実際にはまだ十分に高速です。 

実装の微妙な点は、出力に元の番号付けが必要なため、ソート前に元のリクエスト インデックスを保持することです。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n = int(input())
    req = []
    for i in range(n):
        c, p = map(int, input().split())
        req.append((p, c, i + 1))

    k = int(input())
    tab = list(map(int, input().split()))

    tab = sorted([(v, i + 1) for i, v in enumerate(tab)])
    used = [False] * k

    req.sort(reverse=True)

    ans = []
    total = 0

    for p, c, idx in req:
        for j in range(k):
            if not used[j] and tab[j][0] >= c:
                used[j] = True
                total += p
                ans.append((idx, tab[j][1]))
                break

    out = [f"{len(ans)} {total}"]
    for a, b in ans:
        out.append(f"{a} {b}")
    return "\n".join(out)

# provided sample

5 30

""") == """2 130
2 1
3 2"""

""") == """1 10

""") == """0 0"""

# all fit same size

 ## 特殊なケース

 特殊なケースの 1 つは、どのテーブルもリクエストに適合できない場合です。 入力の場合、すべて`r_i < c_i`の場合、スキャンは常に失敗し、割り当ては記録されません。 すべてのリクエストの反復で使用可能なテーブルが見つからないため、アルゴリズムは正しくゼロ利益を返します。 

もう 1 つのエッジ ケースは、複数のテーブルが同じ容量を共有する場合です。 テーブルはインデックスによって区別されるため、テーブルを個別にマークすることで、容量が同じであっても物理テーブルを再利用することがなくなります。 

最後のケースは、大きなテーブルが存在するが、小さなリクエストが利益順に最初に到着する場合です。 常に最も高い利益を最初に選択するため、大規模なリクエストは、より高い価値がある場合でも優先され、大容量を早期に消費するという古典的な貪欲な間違いを防ぎます。
