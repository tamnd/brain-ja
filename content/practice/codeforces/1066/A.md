 ## 解決策
 ## 問題の理解

 この設定は、位置 1 から位置 L までの 1 次元のパスであり、分 i に Vova が座標 i にあるように時間と位置が同期されます。 このパスに沿って、一定の間隔で光源が v 単位ごとに配置されているため、v で割り切れる位置にのみランタンが含まれます。 

同時に、l から r までの単一の連続したブロックされたセグメントがあり、そこではランタンが物理的に存在しますが、その区間全体が停車中の電車によって覆われているため見ることができません。 ランタンは、v の倍数上にあり、そのブロックされたセグメント内にない場合にのみ役立ちます。 

各クエリについて、このタスクは、[l, r] 内に収まるものを除いて、1 から L の範囲内にある v の倍数を数えることになります。 

制約は十分大きいため、L、v、l、および r はそれぞれ最大 10^9 にすることができ、最大 10^4 のクエリが存在します。 これにより、クエリごとに v の倍数すべてを反復するアプローチは即座に除外されます。 最悪のケースでは、v が 1 に等しい場合、クエリごとに最大 10^9 個の候補ランタン位置が存在する可能性があり、1 秒以内の直接シミュレーションは不可能になります。 

ブロックされたセグメントの処理に関して単純な間違いがよく発生します。 L までの v のすべての倍数を正しく数えることができますが、境界を慎重に再計算せずに、[l, r] 内のすべての点またはその範囲内のすべての倍数を誤って減算してしまう可能性があります。 もう 1 つの微妙な問題は、l または r が v の倍数ではない場合に発生します。これは、区間の長さ自体ではなく、区間内の倍数のみが問題となるためです。 

## アプローチ

 単一のクエリを解決する直接的な方法は、L までの v のすべての倍数を反復し、[l, r] 内に収まらないものの数を数えることです。 これは定義と正確に一致するため、概念的には正しいです。 問題はパフォーマンスです。 倍数はfloor(L / v)で、vが1に等しい場合、最悪のケースでは10^9に達するため、このアプローチは制限時間の直前に失敗します。 

重要な観察は、ランタンの位置が単純な等差数列を形成しているということです。 それらを反復する代わりに、整数の除算を使用して、有効な倍数がいくつ存在するかを数えることができます。 パス上のランタンの総数は、floor(L / v) です。 この合計から、ブロックされたセグメント [l, r] 内に v の倍数がいくつ入るかを差し引きます。 

接頭辞 [1, x] 内の v の倍数を数えるのも、floor(x / v) を使用すると簡単です。 したがって、[l, r] 内の倍数の数は、floor(r / v) から floor((l - 1) / v) を引いたものになります。 これにより、各クエリが一定数の算術演算に変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | クエリごとの O(L / v) | お(1) | 遅すぎる |
 | 最適 | クエリごとに O(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 1 から L までのランタン位置の合計数をフロア (L / v) として計算します。 これは、障害物に関係なく、すべての有効な倍数をカウントします。 
2. [1, r] に v の倍数がいくつあるかを、floor(r / v) として計算します。 これにより、ブロックされたセグメントの右側の境界までのすべてのランタンが表示されます。 
3. [1, l - 1] に v の倍数がいくつあるかを、floor((l - 1) / v) として計算します。 これを減算すると、ブロックされたセグメントより前のすべてが厳密に削除されます。 
4. ステップ 2 からステップ 3 の結果を減算して、[l, r] 内にあるランタンの数を取得します。 これにより、ブロックされたランタンが正確に分離されます。 
5. ランタンの総数からブロックされたランタンを減算して、クエリの最終的な答えを取得します。 

ステップ 3 が必要な理由は、r による直接除算だけでは、ブロックされた区間内の倍数だけでなく、パスの先頭からのすべての倍数がオーバーカウントされるためです。 

### なぜ効果があるのか

ランタンの位置は、まさに k・v の形式の整数のセットです。 それらを境界 x までカウントすることは、k・v ≤ x となるような整数 k をカウントすることと同じであり、これは正確に Floor(x / v) です。 このマッピングは、幾何学的な問題をプレフィックス内の整数のカウントに変換します。 プレフィックスは減算で閉じられるため、間隔カウントは 2 つのプレフィックス カウントの差になります。 したがって、最終的な答えは、単調算術シーケンスの区間分解の直接の結果です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        L, v, l, r = map(int, input().split())

        total = L // v
        blocked = r // v - (l - 1) // v
        print(total - blocked)

if __name__ == "__main__":
    solve()
```コードは各クエリを独立して処理します。 変数 total は、整数除算を使用して、L までのすべてのランタンをカウントします。 ブロックされたカウントでは、標準のプレフィックス差分トリックを使用して、セグメント [l, r] 内の v の倍数をカウントします。 これらを差し引くと、目に見えるランタンが得られます。 

よくある実装上の落とし穴は、(l - 1) 項を忘れることです。 これがないと、計算には誤って r までのすべての倍数が含まれますが、l より前の倍数は除外されず、解釈に応じて過剰な減算または過小な減算が発生します。 

## 実用的な例

 ### 例 1

 入力:```

```計算を追跡します。 

| ステップ | 式 | 値 |

 | ランタンの総数 | 10 // 2 | 5 |
 | rまで | 7 // 2 | 3 |

 これは、[3, 7] の外側の 2 の倍数のみが表示されるという考えと一致します。

    sys.stdin = io.StringIO(inp)

        L, v, l, r = map(int, input().split())
        total = L // v

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、ブロックされたセグメントが 1 から始まる場合です。その場合、l - 1 は 0 になり、floor(0 / v) は 0 になります。これは、インターバルの前にランタンがないことを正確に意味します。 この式は変更しなくても機能します。 

もう 1 つのケースは、v が L より大きい場合です。この場合、v の倍数が範囲内に収まらないため、ランタンの総数は 0 になります。 ブロックされた計算は引き続き値を生成する可能性がありますが、削除するランタンがないため、減算の結果は 0 のままです。 

3 番目のケースは、ブロックされたセグメントが範囲全体をカバーする場合です。 次に、 r // v マイナス (l - 1) // v は L // v に等しく、合計数と正確に一致します。これにより、予想どおり、目に見えるランタンはゼロになります。 

これらの動作は、プレフィックス カウントの定式化が境界条件を越えて安定しており、特別なケーシングを必要としないことを確認します。
