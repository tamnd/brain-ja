 ## 解決策
 ## 問題の理解

 英小文字の文字列が与えられます。 各クエリは連続する部分文字列を選択し、固定ルールを使用してその部分文字列を変換します。すべての文字は独立して展開され、位置にある文字は`x`アルファベットが正確に繰り返される`x`回。 例えば、`a`1部になりますが、`b`2部になりますが、`c`3 部になります。 タスクは、変換された文字列を構築することではなく、各クエリの最終的な長さを計算することだけです。 

したがって、各クエリは基本的に部分文字列に対する重み付けされた合計を要求しており、文字の重みはその ID にのみ依存します。 地図を作るなら`a -> 1, b -> 2, ..., z -> 26`、各クエリは、範囲にわたるこれらの重みの合計を要求します。 

入力制約により、最大 100,000 文字と 100,000 クエリが許可されます。 クエリごとに合計を最初から再計算するソリューションでは、最大で次のスキャンが必要になります。`O(n)`クエリごとの文字数により、`O(nq)`最悪の場合、これは次のようなものです`10^10`操作が実行され、時間内に実行されません。 これにより、定数または対数のクエリ時間による前処理ベースのソリューションが即座に強制されます。 

変換を文字通りに実行しすぎると、微妙な問題が発生します。 展開された文字列を構築したり、文字ごとに繰り返しをシミュレートすると、時間とメモリの両方が爆発的に増加します。 単一のクエリでも、最大長の文字列が生成される可能性があります。`26 * n`、これは実現可能な建設をはるかに超えています。 唯一意味のある量は寄与の合計です。 

もう 1 つの特殊なケースは、部分文字列が 1 文字である場合です。 答えは正確にそのアルファベットのインデックスであるはずです。 ここではプレフィックス合計の 1 つずつの間違いがよく現れるため、これはプレフィックス処理の正確さを検証するのに役立ちます。 

## アプローチ

 ブルートフォースのアイデアは単純です。クエリごとに、部分文字列を反復処理し、各文字をアルファベットの位置に変換し、合計を累積します。 各文字は最終的な長さに独立して影響するため、これは正しいです。 ただし、このアプローチでは、重複する範囲に対して同じ作業が繰り返されます。 と`n = 100000`そして`q = 100000`、最悪の場合、文字列の大きなセグメントが繰り返しスキャンされ、約`10^10`キャラクター操作。 

重要な観察は、各文字がコンテキストに関係なく固定値に寄与するということです。 これは、これらの値に対してプレフィックスの合計を事前計算できることを意味します。 配列を構築したら`pref`、 どこ`pref[i]`最初の貢献度の合計を保存します`i`文字、任意のクエリ`[l, r]`次のように答えることができます`pref[r] - pref[l-1]`。 これにより、O(n) 回の前処理後の各クエリ時間は O(1) に短縮されます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | プレフィックス合計 | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 文字列を数値配列に変換します。`c`にマッピングされます`ord(c) - ord('a') + 1`。 これは、架空の展開された文字列内でその文字が何回繰り返されるかを直接表しますが、その文字列を構築することはありません。 
2. プレフィックス合計配列を構築する`pref`サイズの`n + 1`、 どこ`pref[i]`最初の値の合計に等しい`i`文字。 このステップでは、繰り返されるすべての範囲計算を単一の構造に圧縮します。 
3. クエリごとに`[l, r]`、答えを次のように計算します`pref[r] - pref[l - 1]`。 これが機能するのは、プレフィックスの合計が累積的な寄与を保存し、減算によって範囲が分離されるためです。 
4. 各結果をすぐに出力するか、保存して最後に印刷します。 

唯一の本当の落とし穴はインデックス作成です。 この問題では 1 から始まるインデックスが使用されますが、Python 配列は 0 から始まります。 プレフィックス構築時とクエリ時の両方で一貫してシフトすることが不可欠です。 

### なぜ効果があるのか

 各文字は最終的な長さに独立して影響し、変換ルールによって位置間の相互作用は発生しません。 これにより、問題は区間にわたる線形加算関数になります。 プレフィックス合計は、減算時に正確な間隔合計を保持するため、すべてのクエリは、事前に計算された 2 つの累積値の差を評価することになります。 近似や状態依存性は含まれないため、正確さは線形性から直接得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n, q = map(int, input().split())
    s = input().strip()

    pref = [0] * (n + 1)

    for i in range(n):
        val = ord(s[i]) - ord('a') + 1
        pref[i + 1] = pref[i] + val

    out = []
    for _ in range(q):
        l, r = map(int, input().split())
        out.append(str(pref[r] - pref[l - 1]))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```コードはまず、文字の重みに基づいてプレフィックス合計配列を構築します。 各位置はそのアルファベット インデックスに寄与し、プレフィックス配列はこれらの値を蓄積します。 

各クエリは、2 つのプレフィックス値の減算を使用して回答されます。 引き算`pref[r] - pref[l - 1]`包含範囲を正しく処理します。`pref`先頭にゼロのエントリを付けて定義されます。 

よくある実装上の間違いは、`+1`プレフィックスインデックスのシフト、またはクエリ内での 0 ベースのインデックスと 1 ベースのインデックスの混合。 もう 1 つは、プレフィックス配列をグローバルに 1 回ではなくクエリごとに再構築することです。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, q = map(int, input().split())
    s = input().strip()

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + (ord(s[i]) - ord('a') + 1)

    out = []
    for _ in range(q):
        l, r = map(int, input().split())
        out.append(str(pref[r] - pref[l - 1]))
    return "\n".join(out)

 ## 特殊なケース

 次のような単一文字のクエリ`s = "c", l = r = 1`直接返す`3`。 プレフィックス配列は次のようになります`[0, 3]`、したがって、答えは次のとおりです`pref[1] - pref[0] = 3`。 これにより、基本インデックス作成が特別な処理を必要とせずに機能することが確認されます。 

全範囲クエリは、プレフィックス配列が文字列全体を正しく集計しているかどうかをテストします。 例えば、`s = "abc"`プレフィックスを与える`[0,1,3,6]`、およびクエリ`[1,3]`収量`6`、直接和と一致します。 

均一な文字列のような`"aaaaaa"`繰り返された同一の寄与が正しく蓄積されることを検証します。 各プレフィックス ステップはちょうど 1 ずつ増加するため、範囲の合計は部分文字列の長さに比例する単純な差に減ります。 

これらのケースを総合すると、インデックス作成と蓄積ロジックの両方がすべてのクエリ タイプにわたって一貫性を保つことが保証されます。
