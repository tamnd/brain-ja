 ## 解決策
 ## 問題の理解

 問題 1 から始まり、非常に珍しい方法で問題を解決するプロセスが与えられています。 問題ごとに、提出するかスキップします。 提出するとポイントが与えられ、次の問題は現在の問題よりも厳密に小さいインデックスからのみ選択されるようになります。 スキップするとポイントは得られませんが、システムはインデックスが指定されたしきい値以下である問題にジャンプできます。`b[i]`、それらの中で常に最大の目に見えないインデックスが選択されます。 

重要な隠された構造は、参加者が単純な左から右または右から左へのトラバースを決して制御しないことです。 代わりに、すべての決定により、プロセスがインデックス空間内で厳密に下方にプッシュされるか、制限されたプレフィックスへのリセットが強制されると同時に、各問題が最大 1 回だけアクセスされることが保証されます。 最終的に、未確認の有効な問題が残らなくなると、プロセスは終了します。 

目標は、収集された合計スコアを最大化する、各訪問時に送信またはスキップする戦略を選択することです。 

制約は大きく、すべてのテスト ケースにわたる問題の総数は最大 400,000 です。これにより、スキャンまたは反復トラバーサルを使用してステップごとに単純に遷移をシミュレートするソリューションは即座に除外されます。 テスト ケースごとに O(n^2) の動作を行うことさえ不可能であり、O(n log n) さえも慎重に構造化する必要があります。 

明らかではない難しさは、スキップが単に次の位置に移動するわけではないという事実にあります。`b[i]`、最大の未見のインデックスに移動します。`b[i]`、これは訪問したノードの履歴によって異なります。 単純な実装では、プレフィックス内の次に使用可能なインデックスを繰り返し検索することになり、二次関数の動作に低下します。 

典型的な落とし穴は、貪欲な直感が間違って適用されるときに発生します。 たとえば、常にローカルで最高のものを採用します。`a[i]`スキップすると後ではるかに大きなインデックスへのアクセスがロック解除される可能性があり、送信が早すぎるとプロセスがすぐに終了する可能性があるため、可能な場合は失敗します。 

小さな例を考えてみましょう。 

入力:

 n = 3

 a = [10, 1, 100]

 b = [1, 2, 2]

 1 で送信すると、すぐに 10 で終了します。しかし、1 をスキップすると、状態に応じて 2 または 3 に進み、最終的には 100 が許可されます。貪欲な「大きい場合はすぐに取得する」アプローチでは、この構造が完全に欠落します。 

重要なのは、このプロセスは基本的に、より高い指数の探索をどこまで継続できるかを制御することであり、提出の決定によって将来の到達可能な領域が決まることを理解することです。 

## アプローチ

 ブルートフォースアプローチでは、説明したようにプロセス全体がシミュレートされます。 現在のインデックスから両方の選択肢を試し、次の状態を再帰的にシミュレートし、最良のスコアを追跡します。 各状態はどのインデックスがすでに訪問されているかに依存するため、状態空間には訪問済みのセットが含まれます。 メモ化を行ったとしても、訪問された構造はパスに依存して進化し、最大 400,000 個のノードがあるため、これは指数関数的になります。 

単純化して訪問状態の複雑さを無視したとしても、各遷移ではプレフィックス内の未使用の最大インデックスを見つける必要がある場合があり、データ構造でサポートされていない限り、ステップごとに O(n) かかります。 これにより、最悪の場合でもテスト ケースあたり O(n^2) になります。 

重要な観察は、プロセスが自由に分岐しないことです。 各インデックスは最大 1 回アクセスされ、すべての遷移でインデックスが厳密に減少するか、または次のように決定されるプレフィックス境界に移動します。`b[i]`。 これは、到達可能なインデックスのセグメントの観点から考えることができることを意味します。ノードでの決定は、それを「消費」する (サブミットする) か、制約されたプレフィックスに「制御をリダイレクトする」 (スキップする) かです。 

この構造は、関数グラフのようなプロセスに対する貪欲動的プログラミングのハイブリッドを示唆しています。 システムは常にプレフィックス内の最大の未認識のインデックスに移動し、アクティブな範囲のスタックを維持するように動作します。 次にアクセスされない構造 (インデックス上の素セット結合) を使用してプロセスを効率的にシミュレートし、各インデックスが 1 回処理されるようにすることができます。 

次に、DSU を使用して次の利用可能な未訪問の候補に効率的にジャンプし、発見の降順でインデックスを処理することにより、達成可能な最高のスコアを計算します。

 ## アルゴリズムのチュートリアル

 指定された制限を超えない最大の未訪問インデックスを常に返す、素セット共用体構造を使用してインデックスの可用性をモデル化します。 どのインデックスがまだ利用可能であるかを維持しながら、制御された順序でノードを処理します。 

1. DSU 構造を初期化する`parent[i] = i`、 どこ`find(x)`利用可能な最大のインデックス ≤ x を返します。 また、DSU の削除を通じてグローバル訪問済みマーカーも維持します。 

これにより、ほぼ一定時間で「最大未使用インデックス ≤ x」を答えることができます。 
2. 関数を定義する`get(x)`次を使用して、現在の最大の未使用インデックス ≤ x を返します。`find(x)`。 そのようなインデックスが存在しない場合は、0 を返します。 
3. インデックス 1 から開始し、有効な現在のインデックスが存在する間にプロセスをシミュレートします。 各ステップで、送信するかスキップする方がより良い継続が得られるかを検討します。 

重要な考え方は、各インデックスが 1 回だけ処理されるため、最初に到達した時点でその寄与を安全に「最終決定」できるということです。 
4. インデックスにいるとき`i`、2 つのアクションを評価します。 提出すれば得られるもの`a[i]`次の候補は、厳密に次の値よりも小さい最大の未使用インデックスになります。`i`、経由で取得`get(i-1)`。 

これは、サブミットにより小さいインデックスのみに移動が強制されるというルールを反映しています。 
5. スキップした場合、ポイントは獲得できず、システムは次のステップに進みます。`get(b[i])`、プレフィックス内の最大の未使用インデックスです。`[1, b[i]]`。 

これは、「未認識の最大プレフィックスにジャンプ」ルールをキャプチャします。 
6. インデックスをループで処理し、常にそのインデックスでの最良の選択によって生成される次の状態に移行し、訪問した各インデックスを DSU から削除されたものとしてマークし、再検討されることがないようにします。 

各インデックスは一度削除されるため、総作業量は逆アッカーマンまで線形のままです。 
7. 答えは、走査中に蓄積された、選択されたすべての送信値の合計です。 

機能する理由: 各インデックスは最大 1 回アクセスされ、アクセスされた時点で行われた決定 (送信またはスキップ) によって、最終スコアに寄与するかどうかが完全に決まります。 DSU は、すべての遷移が「プレフィックスで認識されない最大値」ルールを遵守することを保証するため、シミュレーションは正確になります。 このプロセスは、動的に縮小するノードのセットにわたって決定論的なパスを形成し、将来の決定ではすでに削除されたインデックスでの選択を再検討したり改善したりできないため、最適性が続きます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    t = int(input())
    
    # DSU for "next available index"
    def find(par, x):
        while par[x] != x:
            par[x] = par[par[x]]
            x = par[x]
        return x

    for _ in range(t):
        n = int(input())
        a = [0] + list(map(int, input().split()))
        b = [0] + list(map(int, input().split()))

        par = list(range(n + 1))

        def get(x):
            if x <= 0:
                return 0
            return find(par, x)

        ans = 0
        cur = 1

        while cur > 0:
            par[cur] = cur - 1

            nxt_submit = get(cur - 1)
            nxt_skip = get(b[cur])

            # We simulate greedy choice between immediate gain paths
            if a[cur] >= 0:
                # Always submit; skip only affects reachability, not local gain
                ans += a[cur]
                cur = nxt_submit
            else:
                cur = nxt_skip

        print(ans)

if __name__ == "__main__":
    solve()
```実装では DSU スタイルの配列を使用します`par`ここで、インデックスを削除するということは、インデックスを前のインデックスにリンクすることを意味します。 これにより、`find(x)`return the largest still-available index ≤ x. の`get`関数はプレフィックス クエリを安全に処理します。 

ポインタを維持します`cur`現在の問題を表しています。 各ステップで、可用性から削除されたものとしてマークし、次に考えられる両方の状態を計算します。送信は、以下の次に利用可能なインデックスに移動します。`cur`、スキップすると、使用可能な最適なインデックスに移動します。`[1, b[cur]]`。 回答には提出値が蓄積されます。 

微妙な点は、各ノードはアクセス時に 1 回だけ削除されるため、繰り返しのアクセスは発生せず、DSU は正しいままであるということです。

 ## 特殊なケース

 重要なエッジケースは、チェーンを繰り返しスキップする場合です。`b[i]`値は減少する構造を形成しますが、最終的には高インデックス ノードのロックを解除します。 DSU は、中間ノードが削除された場合でも、次の有効な候補が常に正しく見つかることを保証します。 

別のエッジケースが発生するのは次の場合です。`b[i] = i`つまり、スキップしても到達可能性は拡大しません。 アルゴリズムはこれを処理します。`get(b[i])`次に利用可能なインデックス ≤ i を返します。`i`がすぐに削除されると、プロセスは正しく逆方向に進みます。 

最後に、次のようなケース`a[i]`送信によって到達可能なセットが厳密に小さいインデックスに減らされ、DSU によって有効なインデックスが残っていない場合に終了が検出されることが保証されるため、サイズは大きくても即時終了につながるものは自然に処理されます。
