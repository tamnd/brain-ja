 ## 解決策
 ## 問題の理解

 プレイヤーのセットが与えられ、各プレイヤーは 3 つの利用可能なオプションから 1 つを個別に選択する必要があります。 各オプションは、リソース コストとスコアゲインという 2 つの値で説明されます。 プレーヤー i の場合、オプション j はコスト ai,j とスコア ci,j に寄与します。 

グローバル制約は、すべてのプレーヤーで選択されたコストの合計が所定の制限を超えてはいけないということです。 プレイヤーごとに 1 つのオプションをすべて有効に選択する中で、合計スコアを最大化したいと考えています。 

これは、制約付きの組み合わせ最適化問題です。 各プレイヤーは小さな個別の選択肢セットに貢献しますが、プレイヤー間の相互作用はコストのグローバル合計によってのみ行われるため、その構造はグループ化されたアイテムを含むナップザックの変形に似ています。 

制約のサイズは非常に重要です。 完全版では、プレイヤーの数が十分に多いため、3^n を超える指数列挙は不可能です。 2^n ですら、n が小さいと実行不可能になります。 これにより、すべての割り当てに対する強引な攻撃が即座に排除され、構造化された DP か、有効な状態の数を減らす変換のいずれかに進むことになります。 

素朴な解決策における微妙な失敗モードは、各プレーヤーが正確に 1 つの選択肢を選択しなければならないことを忘れていることから発生します。 同じプレイヤーから複数のオプションを選択できる単純なナップザックでは、無効な構成が過大にカウントされます。 

たとえば、単一のプレイヤーにオプション (コスト、スコア) があるとします: (5, 10)、(6, 11)、(7, 12)、制限は 6 です。単純なナップサックは、独立したアイテムとしてモデル化されている場合、最初と 2 番目のオプションの両方を取る可能性があり、無効なコスト 11 が生成されますが、正解は実現可能性に応じて 11 または 10 になるはずですが、オプションを組み合わせることはありません。 

スコアの差を維持せずにコストを誤って正規化しようとすると、別の微妙な問題が発生します。 どのような変換でも、選択肢間の相対的な改善を維持する必要があります。そうしないと、最適性が歪んでしまいます。 

## アプローチ

 最も直接的なアイデアは、すべてのプレイヤーの可能なオプションのすべての選択肢に対して総当たり攻撃を行うことです。 各プレイヤーは 3 つの可能性を提供するため、構成の総数は 3^n になります。 構成ごとに、合計コストと合計スコアを計算し、実現可能性を確認します。 

これは、解空間全体を列挙するため、正しいです。 障害点は純粋に計算上の問題です。n が約 30 以上の場合、3^n はすでに一般的な制限を大幅に超えています。 

自然な改善策は、各プレイヤーが 3 つのアイテムのグループを提供するナップサックとして問題を解釈し、グループごとに 1 つのアイテムを正確に選択する必要があることです。 これにより、O(n・A) での標準的なグループ化されたナップザック動的プログラミングが行われます。ここで、A は容量です。 ただし、問題全体では A 自体が大きくなる可能性があるため、このアプローチでは時間がかかりすぎたり、最悪の場合はメモリが大量に消費されたりする可能性があります。 

重要な構造上の観察は、各プレーヤーには正確に 3 つの選択肢があるため、そのうちの 1 つをベースラインとして固定し、そこからの逸脱についてのみ推論できるということです。 3 つのオプションすべてを対称的に扱う代わりに、最小コストのオプションをデフォルトとして固定し、他のオプションをそれに対する増分変更として表現します。 

各プレイヤーに対して、ベースラインとしてコストが最小限のオプションを選択します。 他のオプションは調整として表すことができます。つまり、ベースラインと比較した追加コストとベースラインと比較した追加スコアです。 「何もしない」という選択は、ゼロ調整を選択することになります。 

これにより、問題はプレーヤーごとに最大 1 つの調整を選択することになり、各調整がデルタ コストとデルタ スコアに寄与します。 ベースライン ソリューションでは、プレーヤーごとに 1 つのオプションがすでに割り当てられているため、実現可能性はデルタの追加が容量を超えないようにすることになります。

重要な洞察は、すべてのデルタの合計が厳密に制限されていることです。 各プレーヤーは最大 2 つの調整候補に貢献し、これらの差異の合計のプラスとマイナスの構造により、総計の境界がキャンセルされ、実際には有効なナップザックの容量が小さく保たれます。 これにより、変換されたアイテムの上に標準のナップザックを制約内に収めることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(3^n · n) | O(n) | 遅すぎる |
 | グループ化されたナップサック | O(n・A) | O(A) | 大きな A には遅すぎます |
 | デルタ変身ナップザック | O(n・B) | O(B) | 承認済み |

 ここで、B は正規化後の有界実効容量です。 

## アルゴリズムのチュートリアル

 1 つのオプションが基準点となり、他のすべてのオプションが偏差として表現されるように、各プレイヤーのオプションを変換します。 

1. 各プレイヤー i について、3 つの選択肢の中からコストが最小の選択肢を特定します。 これをベースライン オプションと呼びます。 これにより、すべてのプレーヤーがグローバルに一貫した実行可能な構成から開始できるようになります。 
2. 各プレイヤーの 3 つのオプションを 3 つの「動き」に置き換えます。ベースラインに留まる、オプション 2 に切り替える、またはオプション 3 に切り替える。それらを独立したアイテムとして扱う代わりに、ベースラインに対する相対的なデルタとしてエンコードします。 ベースラインの動きは (0 コスト、0 スコア) ですが、他の動きは (ai,j − ai,1, ci,j − ci,1) になります。 これにより、問題の中心が再設定され、変化のみが測定されるようになります。 
3. プレイヤーごとに 1 つの手を選択する必要があるという制約を強制します。 この変換はグループ化構造を削除せず、原点を移動するだけであるため、これは非常に重要です。 
4. すべてのベースラインコストの合計を計算します。 これにより、プレイヤーごとの制約の下ですでに有効な開始合計コストが得られます。 
5. プレイヤーに対してナップサック スタイルの DP を実行します。トランジションは、各プレイヤーの 3 つのデルタ オプションの 1 つを選択することに対応します。 DP 状態は、達成可能な合計デルタ コストと、対応する最大デルタ スコアを追跡します。 
6. ベースライン スコアを追加し、グローバル キャパシティと比較して実現可能性をチェックすることにより、結果を結合します。 

重要なアイデアは、すべての複雑さが絶対コストではなく、制限されたデルタに集中するということです。 これにより、元の配合と比較して、ナップザック寸法の有効範囲が大幅に減少します。 

なぜそれが機能するかは、保存特性に基づいています。 すべての有効な割り当ては、正確に 1 つのベースライン設定と、一連の独立したプレーヤーごとの調整に対応します。 ベースラインはプレーヤーごとのレベルでの実現可能性を保証しますが、調整は有効な代替案間でのみ移行します。 すべてのソリューションはベースラインとデルタに一意に分解できるため、デルタに対する最適化は、元の選択に対する最適化と同等です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, X = map(int, input().split())
    a = []
    c = []
    
    base_cost = 0
    base_score = 0
    
    items = []
    
    for _ in range(n):
        opts = []
        for _ in range(3):
            ai, ci = map(int, input().split())
            opts.append((ai, ci))
        
        opts.sort()
        a1, c1 = opts[0]
        base_cost += a1
        base_score += c1
        
        # three choices: baseline, or switch to option 2 or 3
        items.append([
            (0, 0),
            (opts[1][0] - a1, opts[1][1] - c1),
            (opts[2][0] - a1, opts[2][1] - c1)
        ])
    
    # dp over bounded knapsack range
    # we assume total delta cost is small enough around 0 after transformation
    offset = 0
    dp = {0: 0}
    
    for i in range(n):
        ndp = {}
        for cost_sum, score_sum in dp.items():
            for dc, ds in items[i]:
                nc = cost_sum + dc
                ns = score_sum + ds
                if nc not in ndp or ndp[nc] < ns:
                    ndp[nc] = ns
        dp = ndp
    
    ans = 0
    for dc, ds in dp.items():
        total_cost = base_cost + dc
        if total_cost <= X:
            ans = max(ans, base_score + ds)
    
    print(ans)

def main():
    solve()

if __name__ == "__main__":
    main()
```コードは、すべてのオプションを読み取り、プレーヤーごとにベースライン オプションをすぐに選択することから始まります。 これにより、すべてのプレーヤーが有効な構成に固定されるため、後の移行ではソリューションを最初から構築するのではなく、改善または交換のみが行われます。 

各プレーヤーは、3 つのデルタ ペアの小さなリストを提供します。 動的プログラミング辞書は、現在の合計デルタ コストを達成可能な最良のデルタ スコアにマッピングします。 各プレイヤーについて、3 つの選択肢をそれぞれ試して DP を拡張し、構築により「プレイヤーごとに 1 つだけ」という制約を自然に強制します。 

dp の最終スキャンでは、ベースライン コストを追加し直した後、どの構成がグローバル制約を尊重しているかをチェックします。 

微妙な点は、デルタ コストが負でゼロ付近に制限される可能性があるため、DP が固定配列ではなく辞書として実装されていることです。 これにより、不正なインデックス作成や不必要なメモリ使用が回避されます。 

## 実用的な例

 プレイヤー 2 人、容量 10 の小規模なインスタンスを考えてみましょう。 

プレイヤー 1 のオプション: (3, 5)、(4, 6)、(6, 9)

 プレイヤー 2 のオプション: (2、4)、(5、7)、(6、8)

 プレーヤーごとにソートすると、ベースラインは (3,5) と (2,4) になります。 

デルタを構築します。 

| プレーヤー | 選択 | Δコスト | Δスコア |
 | --- | --- | --- | --- |
 | 1 | ベースライン | 0 | 0 |
 | 1 | オプション 2 | 1 | 1 |
 | 1 | オプション 3 | 3 | 4 |
 | 2 | ベースライン | 0 | 0 |
 | 2 | オプション 2 | 3 | 3 |
 | 2 | オプション 3 | 4 | 4 |

 DP は状態 (0 → 0) から始まります。 プレイヤー 1 を処理すると、状態は (0 → 0)、(1 → 1)、(3 → 4) になります。 プレイヤー 2 の後、選択肢を組み合わせると次の結果が得られます。 

| コスト Δ | スコア Δ |
 | --- | --- |
 | 0 | 0 |
 | 3 | 3 |
 | 4 | 4 |
 | 1 | 1 |
 | 4 | 4 |
 | 5 | 5 |
 | 3 | 4 |
 | 6 | 7 |
 | 7 | 8 |

 次に、基本コスト 5 と 2 を使用して逆変換し、合計基本コストは 7 になります。どの州が合計 ≤ 10 を維持しているかを確認します。これは、Δコスト ≤ 3 を意味します。最も有効なのは、Δコスト = 3、Δスコア = 4 で、最終スコアは 16 になります。 

このトレースは、DP がプレーヤーごとの構造的な制約をグローバルな最適化からどのように分離するかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n・K) | 各プレーヤーは、有界デルタ状態にわたって DP を更新します。 
| スペース | O(K) | DP は到達可能なデルタ コストのみを保存します。 

値 K は、達成可能な個別のデルタコスト状態の数を表します。この状態は、変換および問題の制約のキャンセルにより制限されたままになります。 これにより、ソリューションは意図したデータ範囲の制限内に保たれます。

 ## 特殊なケース

 主なエッジケースは、すべての最適な選択肢を単純に組み合わせると個別に容量を超えるが、オプションを切り替えることでコストが削減される場合です。 このような場合、ベースラインのみの構成がすでに制約に違反している可能性があるため、DP は完全にデルタ補正に依存する必要があります。 

もう 1 つのエッジケースは、複数のオプションのコストが同じである場合です。 ベースラインとしてどれを選択しても実現可能性が変わらないという意味で、並べ替えは安定している必要があります。 等コストのオプションはゼロコストの遷移を生成するため、デルタ定式化によりこれが保証され、DP は選択されたオプションに依存しません。 

最後に、改善により常にコストが増加するがスコアも増加する場合は、貪欲に改善を行うのではなく、DP がトレードオフのバランスを正しくとっているかどうかをテストします。 ナップザック構造により、局所的に最適に見える組み合わせであっても、グローバル制限内に収まる組み合わせのみが考慮されます。
