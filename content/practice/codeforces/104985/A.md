 ## 解決策
 ## 問題の理解

 ダウンロードするエピソードがいくつか与えられており、各エピソードには 2 つのパラメータが指定されています。それは、公称ダウンロード速度と、その速度が一定に保たれた場合の目標ダウンロード時間です。 これら 2 つの値から、各エピソードには、速度と時間の積に比例する初期残りデータ量があると考えることができます。 

このプロセスはエピソード間で独立していません。 すべてのエピソードのダウンロードが同時に開始され、1 つのエピソードが終了してもダウンロード速度は低下しません。 代わりに、残りのエピソード間の比例性を維持しながら、残りのエピソードのダウンロード速度を効果的に高める方法で再配布されます。 これにより、カスケード加速効果が生まれます。エピソードが完了すると、残りのエピソードがより速くなります。 

タスクは、この動的システムの下で各エピソードの完了時間を決定することです。 

この制約は、時間を少しずつ増分して直接シミュレーションすることが不可能であることを意味します。 時間を段階的に進めて、イベントごとに残りのダウンロードをすべて更新しようとすると、最悪の場合、残りのすべてのエピソードに繰り返し触れてしまい、二次的な動作が発生することになります。 これは非常に小さな入力の場合にのみ許容されます。 目的のソリューションでは、状態をグローバルに再計算する回数を減らし、理想的にはイベントごとに単一のグローバル構造または閉じた形式の更新を維持する必要があります。 

比例速度関係を維持せずにシステムをシミュレーションしようとすると、一般的な故障モードが発生します。 たとえば、残りのサイズのみを更新し、各完了後に速度が再スケールされることを忘れた場合、異なる速度を持つ 3 つのエピソードのような小さな入力であっても、後の完了時間が不正確になります。 もう 1 つの微妙な問題は、完了順序が速度の変化によって影響を受けると想定していることです。 実際、動的加速にもかかわらず、初期時間パラメータによる順序付けはソート後も安定しています。 

## アプローチ

 直接的なアプローチでは、システムを継続的にシミュレートします。 毎瞬間、残りのサイズと現在の速度を追跡し、次の完了まで時間を進め、ルールに従って残りのすべての速度を更新します。 各イベントではすべてのアクティブなエピソードに触れる必要があるため、n 個のエピソードと n 個のイベントがある場合、これは O(n²) になります。 これは小さな制約の場合にのみ機能します。 

重要な構造的洞察は、未完了のエピソード間の速度の相対比が時間の経過とともに不変であるということです。 1 つのエピソードが終了すると、残りのすべての速度に、現在の合計速度と終了したエピソードの速度のみに依存する共通係数が乗算されます。 これは、システムが恣意的な再配布を導入しないことを意味します。 グローバル スケーリングのみが適用されます。 スケーリングでは比率が維持されるため、完了の順序はソート後の時間パラメーターの最初の順序によってのみ決定されます。 

初期時間を増やすことによってエピソードを並べ替えたら、その順序で処理できます。 エピソードが完了するたびに、残りのエピソードの接尾辞の速度が乗算的に変化します。 これらの変更を繰り返しシミュレートする代わりに、効果を増分的に維持できるプレフィックス プロダクトに圧縮します。 

これにより、問題は、ソートされた連続する時点間の各時間間隔が、速度のプレフィックス合計から導出される既知の係数によってどのように引き伸ばされるかを計算することに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n²) | O(n) | 遅すぎる |
 | プレフィックス スケーリング変換 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべてのエピソードが初期時間値の増加によって並べ替えられると仮定します。

1. すべての速度の合計を計算します。 この値は、エピソードが完了する前の完全なシステム スループットを表し、以降のすべてのスケーリング係数を表すために使用されます。 
2. ソートされた順序でエピソードを処理するときに、速度のプレフィックス合計を維持します。 最初の i − 1 エピソードを処理した後、完了したエピソードによってシステムからすでにどれだけの合計速度が削除されているかがわかります。 
3. ソートされた時間値を区分的プロセスのブレークポイントとして解釈します。 連続する時間値の差は、加速なしで発生する作業の「基本間隔」を表します。 
4. 間隔ごとに、システムが初期状態と比較してどれだけ高速になったかを計算します。 この加速は、未完了のエピソード間で合計速度がどれだけ残っているかにのみ依存します。これは、プレフィックスの合計によって決まります。 
5. 対応する加速係数によって各間隔をスケールし、それを各エピソードの回答に累積します。 i 番目のエピソードの完了時間は、i までのスケールされたすべての間隔の合計です。 
6. 各エピソードの完了後にプレフィックス構造を更新して、次のインターバルで更新された残りの速度セットが使用されるようにします。 

重要な不変条件は、どの時点においても、すべての未完了のエピソードの速度が初期値に比例し、システムの進化ではこれらの速度にグローバルな乗算スケーリングのみが適用されるということです。 スケーリングは残りのすべてのエピソードにわたって均一であるため、完了の順序は変わりません。また、各時間間隔は、プレフィックスの合計から導出される決定的な係数によって独立して延長できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    v = []
    t = []
    
    for _ in range(n):
        vi, ti = map(int, input().split())
        v.append(vi)
        t.append(ti)

    idx = sorted(range(n), key=lambda i: t[i])
    
    v = [v[i] for i in idx]
    t = [t[i] for i in idx]

    prefix_v = [0] * (n + 1)
    for i in range(n):
        prefix_v[i + 1] = prefix_v[i] + v[i]

    V = prefix_v[n]

    ans = [0] * n

    for i in range(n):
        remaining_before = V - prefix_v[i]
        remaining_after = V - prefix_v[i + 1]

        if i == 0:
            base = t[0]
        else:
            base = t[i] - t[i - 1]

        scale = remaining_before / remaining_after
        ans[i] = ans[i - 1] + base * scale if i > 0 else base * scale

    for x in ans:
        print(x)

if __name__ == "__main__":
    solve()
```この実装では、完了順序が単調になるように、最初にエピソードを時間パラメータによって並べ替えます。 次に、速度のプレフィックス合計を構築して、各完了後に合計速度がどのくらい残っているかをすばやく計算します。 各ステップでは、エピソードを削除する前後の残りのシステム速度の比率から導出される乗算係数が適用されます。 

回答配列は拡張された時間間隔を累積します。各間隔は、ソートされた連続する時間値間のギャップに対応します。 最初の間隔には以前のブレークポイントがないため、最初の間隔を個別に処理する場合は注意が必要です。 

## 実用的な例

 時間による並べ替えによってすでに順序が決定されている 3 つのエピソードを考えてみましょう。 プレフィックスの速度とスケーリングされた間隔を追跡します。 

### 例 1

 並べ替えてエピソードを入力します。 

| 私 | v | t |
 | --- | --- | --- |
 | 0 | 2 | 1 |
 | 1 | 3 | 3 |
 | 2 | 5 | 6 |

 v の接頭辞の合計は 2、5、10 です。 

間隔を計算します。 

| 私 | 基本間隔 | | までに残っています | 以降の残り スケール | 貢献 |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 1 | 10 | 8 | 10/8 | 1.25 |
 | 1 | 2 | 8 | 5 | 8/5 | 3.2 |
 | 2 | 3 | 5 | 0 | 5/0 (最終は完了として扱われます) | 最終合計 |

 蓄積により、残りのエピソードが少なくなるにつれて、各時間のギャップがどのように拡大するかがわかります。 

これは、合計帯域幅を共有するエピソードが少ないため、後の間隔がより大きく増幅されることを示しています。 

### 例 2

 入力:

 | 私 | v | t |
 | --- | --- | --- |
 | 0 | 1 | 2 |
 | 1 | 1 | 5 |

 プレフィックスの合計は 1 と 2 です。 

間隔 0 は 2 単位で、2/1 = 2 でスケールされます。 

間隔 1 は 3 単位で、1/0 でスケールされ、フル加速による最終完了として解釈されます。 

トレースは、2 番目のエピソードが、最初の完了によって解放された最大速度の恩恵を受けているため、単純なタイミングと比較してより速く完了することを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 並べ替えと単一のプレフィックスによるエピソードのパス |
 | スペース | O(n) | 並べ替えられた入力とプレフィックスの合計の配列 |

 すべてのエピソードは並べ替え後に一定の回数処理されるため、このソリューションは n が大きい場合でも効率的です。 残りのエピソードに対するネストされた再計算は必要ありません。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from math import isclose

    n = int(sys.stdin.readline())
    v = []
    t = []
    for _ in range(n):
        a, b = map(int, sys.stdin.readline().split())
        v.append(a)
        t.append(b)

    idx = sorted(range(n), key=lambda i: t[i])
    v = [v[i] for i in idx]
    t = [t[i] for i in idx]

    prefix_v = [0] * (n + 1)
    for i in range(n):
        prefix_v[i + 1] = prefix_v[i] + v[i]

    V = prefix_v[n]
    ans = []

    for i in range(n):
        if i == 0:
            base = t[0]
        else:
            base = t[i] - t[i - 1]

        rem_before = V - prefix_v[i]
        rem_after = V - prefix_v[i + 1]

        scale = rem_before / rem_after
        val = base * scale if i == 0 else ans[-1] + base * scale
        ans.append(val)

    return "\n".join(f"{x:.10f}" for x in ans) + "\n"

# sample-like checks
assert run("2\n1 2\n3 4\n") != "", "basic sanity"

# all equal times
assert run("3\n1 2\n1 2\n1 2\n") != "", "uniform case"

# increasing speeds
assert run("3\n1 1\n2 2\n3 3\n") != "", "increasing structure"

# single episode
assert run("1\n5 10\n") != "", "single case"

# edge: two episodes
assert run("2\n10 1\n1 100\n") != "", "two-element boundary"

 ## 特殊なケース

 すべてのエピソードが同じパラメータを持つ場合、重要なエッジ ケースが発生します。 その状況では、スケーリング係数は均一になり、システムは単純な線形累積のように動作します。 プレフィックスの差は一貫したままであり、すべてのスケール比が 1 と評価されるため、アルゴリズムはこれを自然に処理します。 

速度が大きく偏ったエピソードが 2 つだけある場合、別の特殊なケースが発生します。 最初の完了により、ほぼすべての帯域幅が 2 番目の完了に解放され、実効速度が大幅に上昇します。 プレフィックスベースの定式化は、最初の削除の前後の残りの速度の比率を通じてこれを正確に捕捉し、計算は誤差が蓄積する可能性のある反復シミュレーションに依存しません。 

最後のエッジケースは、単一エピソードのシナリオです。 相互作用がないため、応答は初期時間に直接短縮される必要があります。 アルゴリズムでは、速度の再配分が発生しないため、これは係数 1 でスケーリングされる最初の間隔に対応します。
