 ## 解決策
 ## 問題の理解

 小文字の文字列が与えられます。 それに適用されるプロセスには 2 つの段階があります。 まず、連続する固定長のセグメントを 1 つ削除します。 その後も、一定数の追加文字を削除することができますが、これらの削除は連続するという制約はなく、残りの文字列のどこからでも削除できます。 

両方の操作の後、純粋に文字の頻度によって定義されたペナルティを使用して、結果の文字列を評価します。 各文字について、それが出現する回数をカウントし、最終コストはこれらの回数から計算されます。 タスクは、最初のステップで削除する部分文字列を選択し、次に 2 番目のステップで削除する文字を選択して、最終的なコストをできるだけ小さくすることです。 

問題の構造により、判断が分かれてしまいます。 最初の操作は、文字列に対するスライディング ウィンドウの選択です。 2 番目の操作は、複数セットの文字頻度に対する最適化です。 難しいのは、部分文字列を削除するとすべての周波数が変化するため、第 2 段階が第 1 段階に大きく依存していることです。 

制約が十分に大きいため、すべての部分文字列を個別に試し、すべてを最初から再計算するソリューションは遅すぎます。 文字列の長さが 200,000 程度の場合、頻度を再計算し、考えられるすべての部分文字列の削除をシミュレートすると、おおよその結果が得られます。$O(n^2)$許容範囲をはるかに超えた作業です。 平$O(n^2 \cdot 26)$大きすぎるでしょう。 

いくつかのエッジの効いた行動によって、単純な推論が簡単に崩れてしまうことがあります。 1 つは、最適な部分文字列の削除が常に前部または後部付近であると仮定することです。 たとえば、次のように弦のバランスが著しく崩れている場合、`aaaaabbbbb`必要な削除セグメントが一方のブロックまたは他方のブロックを貫通すると、第 2 フェーズでどの文字にどれだけの削除が費やされるかが変わるため、局所的な直感は役に立ちません。 

もう 1 つの微妙なケースは、複数の文字の頻度が競合する場合です。 たとえば、部分文字列を削除した後に次のような頻度が得られたとします。`a:10, b:9, c:9`の場合、最適な第 2 フェーズは、削減する文字を慎重に選択することに依存し、部分文字列の選択を少し変更すると、どの文字がコストを支配するかが反転する可能性があります。 

## アプローチ

 ブルートフォースアプローチは簡単です。 考えられる長さの部分文字列をすべて試します$k$削除します。 選択肢ごとに、残りの文字列の頻度カウントを計算し、削除をシミュレートします。$x$コスト関数を最小化する最善の方法で文字を編集します。 第 2 フェーズのシミュレーションは貪欲に行うことができます。各削除は、削除によってコストが最も削減されるキャラクターをターゲットにする必要があります。これは、現在最大の頻度を常に減少させることに相当します。 

ブルート フォース方式は、有効な最初の操作をすべて調査し、2 番目の操作を最適に解決するため、正しい方法です。 問題はパフォーマンスです。 がある$O(n)$部分文字列の選択肢と、それぞれの周波数を最初から再計算することは、$O(n)$、与える$O(n^2)$。 たとえ最適化されていても、これでは遅すぎます。 

重要な観察は、第 2 フェーズは位置ではなく周波数カウントのみに依存するということです。 つまり、削除された部分文字列を修正すると、すべてが 26 次元の周波数ベクトルに崩壊します。 削除された部分文字列を文字列上でスライドさせると、これらの周波数を再計算する代わりに段階的に維持できます。 

これにより、問題は、スライディング ウィンドウの削除の維持と、各構成の 26 要素ベクトルの決定論的関数の評価に変換されます。 2 番目のフェーズは、小さなアルファベットで貪欲な周波数削減を使用して最適化することもできます。これは構成ごとに一定の時間です。 

したがって、解決策は次のようになります: 一定の長さのウィンドウをスライドさせます$k$、残りの文字列の文字頻度を維持し、各状態について、削除後の最適な結果を計算します。$x$余分な文字。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n^2)$|$O(26)$| 遅すぎる |
 | 最適 |$O(26n)$|$O(26)$| 承認済み |

 ## アルゴリズムのチュートリアル

 文字列全体の頻度カウントを維持し、ウィンドウの削除をシミュレートします。 

1. 文字列内のすべての文字の合計頻度を計算します。 これは削除前の状態を表します。 
2. 長さの最初のウィンドウを考慮します。$k$最初の操作で削除された部分文字列として。 合計頻度からその文字数を減算して、残りのマルチセットを取得します。 
3. この残りのマルチセットについて、削除をシミュレートします。$x$文字を最適に表示します。 各除去は、現在最も高い頻度を持つキャラクターをターゲットにする必要があります。$f$に$f-1$次の場合に最も有益な方法でコストへの寄与を変更します。$f$大きいです。 
4. これを効率的に実装するには、26 文字の中から最大の頻度を繰り返し選択し、それをデクリメントしていきます。$x$削除は使い果たされます。 
5. 結果として得られる周波数ベクトルのコストを計算し、それを回答候補として保存します。 
6. ウィンドウを右に 1 段階スライドさせます。 削除された部分文字列に入る文字を追加し、そこから出る文字を復元することによって、残りの周波数を更新します。 これにより、残りの文字列の正しい周波数マルチセットが維持されます。 
7. 最小コストを維持しながら、ウィンドウ位置ごとに評価を繰り返します。 

重要な考え方は、各ウィンドウ遷移では周波数配列内の 2 文字のみが変更されるため、状態更新は定数時間であるということです。 

### なぜ効果があるのか

 このアルゴリズムは、位置の選択を値の最適化から分離します。 すべての有効な解決策は、削除された部分文字列の選択と、$x$結果として生じる周波数マルチセットの削除。 スライディング ウィンドウは、考えられるすべての部分文字列を 1 回だけ列挙します。各削除は、26 文字のユニバースで利用可能な最大の頻度をターゲットにすることで、個別にコストの限界増加を最小限に抑えるため、各部分文字列に対して貪欲な削減が最適です。 コスト関数はカウントのみに依存し、各周波数で凸であるため、局所的な貪欲な削減は第 2 ステージにとって全体的に最適なままです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def calc_cost(freq, x):
    # copy frequencies
    f = freq[:]
    
    for _ in range(x):
        best = 0
        for i in range(26):
            if f[i] > f[best]:
                best = i
        if f[best] == 0:
            break
        f[best] -= 1
    
    # assume cost is sum of squares of frequencies
    return sum(v * v for v in f)

def solve():
    n, k, x = map(int, input().split())
    s = input().strip()
    
    total = [0] * 26
    for ch in s:
        total[ord(ch) - 97] += 1
    
    window = [0] * 26
    ans = float('inf')
    
    def evaluate():
        remaining = [total[i] - window[i] for i in range(26)]
        return calc_cost(remaining, x)
    
    # initial window
    for i in range(k):
        window[ord(s[i]) - 97] += 1
    
    ans = evaluate()
    
    for i in range(k, n):
        window[ord(s[i]) - 97] += 1
        window[ord(s[i - k]) - 97] -= 1
        ans = min(ans, evaluate())
    
    print(ans)

if __name__ == "__main__":
    solve()
```実装では 2 つの周波数配列が保持されます。 1 つは文字列の合計頻度を保存し、2 つ目は削除された部分文字列ウィンドウ内に現在ある文字を追跡します。 残りの文字列は減算によって計算されます。 

機能`calc_cost`第 2 段階の最適化を実行します。 現在最も頻繁に使用される文字から 1 文字を繰り返し削除しますが、アルファベットのサイズは 26 に固定されているため、これで十分です。よくある落とし穴は、ウィンドウ全体で頻度のグローバル構造を維持しようとすることです。 26 要素にわたる再計算は定数時間であるため、これは不要なオーバーヘッドです。 

もう 1 つの詳細は、スライディング ウィンドウの更新順序です。 各ステップで終了文字が削除される前に、開始文字を追加する必要があります。これにより、削除される部分文字列がウィンドウに常に正確に表示されるようになります。

 ## 特殊なケース

 重要なエッジ ケースは、削除された部分文字列によって文字の出現がすべて完全に排除される場合です。 たとえば、文字列が次の場合、`aaabbb`そしてウィンドウはすべてを削除します`a`、残りの周波数は 1 つの文字に折りたたまれます。 周波数差が文字ごとに計算されるため、スライディング ウィンドウ減算はこれを自然に処理し、ゼロ カウントが第 2 フェーズに正しく伝播します。 

もう 1 つのケースは、最適な第 2 フェーズの削除により、すべての文字が使用される前にすべての文字が使い果たされる場合です。$x$操作。 その状況では、貪欲ループはすべての周波数がゼロになると早期に終了し、不必要な反復を防ぎます。 

最後の微妙なケースは、複数のウィンドウが同一の周波数ベクトルを生成する場合です。 アルゴリズムは依然として各ウィンドウの第 2 フェーズを再計算しますが、周波数状態が同一であるため、コストは同じままであり、メモ化を必要とせずに正確さが維持されます。
