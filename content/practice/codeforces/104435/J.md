 ## 解決策
 ## 問題の理解

 A、B、C、D というラベルが付けられた 4 つの部屋があり、ちょうど 3 本の廊下で接続された建物があります。 各廊下は 2 つの部屋間の物理的な通路であり、人が廊下をある部屋から別の部屋に移動するたびに、その人の ID とその人が使用した廊下のペアとしてログ エントリが記録されます。 

すべての従業員は部屋 A から開始します。各従業員について、使用したと報告されている廊下の順序が時系列で与えられます。 主な問題点は、システムはユーザーがどの部屋間を移動したかを明示的に記録せず、どの廊下がトリガーされたかのみを記録することです。 

さらに複雑な問題があります。通気孔がすべての廊下を互いに接続しています。 これは、人が有効な部屋の移動を通過せずに、ある廊下から別の廊下に移動する可能性があることを意味します。 その場合、彼らの動きは建物のレイアウト内を物理的に一貫して歩くことに対応しません。 課題は、どの従業員が通気孔を少なくとも 1 回乱用した場合にのみ、観察された一連の廊下使用を実現できたのかを判断することです。 それらの従業員は不審者としてマークされます。 

出力は従業員に関するバイナリ文字列です。 従業員の順序がベントを使用せずに A から始まる有効な歩行によって説明できない場合、文字は 1、それ以外の場合は 0 です。 

従業員数という点では制約は小さく、最大 1000 人ですが、ログ エントリの数は 100000 に達する可能性があります。これは、クエリごとに最初から再シミュレーションするのではなく、ログを線形時間で処理し、従業員ごとに増分状態を維持する必要があることをすぐに示唆しています。 

従業員ごとに完全なパスを個別に再構築し、考えられるすべての部屋の割り当てを試みる単純なアプローチでは、非常に時間がかかり、1 人あたりのログ エントリの数が指数関数的に増加する可能性があります。 

主なエッジ ケースは、単一のログ エントリを持つ従業員と、連続するコリドー遷移が基礎となるグラフの共有エンドポイントに対応しない従業員から発生します。 特に、パスの残りの部分が一貫していても、無効な遷移が 1 つあるだけで、疑いを持たせるのに十分です。 

## アプローチ

 強引な解釈では、各従業員を個別に扱い、部屋のシーケンスを廊下のシーケンスに割り当てようとします。 各ログ エントリについて、以前の割り当てとの一貫性を維持しながら、その人が廊下のどの終点から入ってどの終点へ出たかを推測しようとします。 これは、コリドーの使用法ごとに 2 つの可能な方向にわたる制約された検索問題になります。 最悪の場合、k 個のログ エントリを持つ 1 人の従業員の場合、この分岐により 2^k 個の可能性が生じますが、k が大きい場合にはこれは不可能です。 

重要な簡素化は、実際には完全なパスを再構築する必要がないことです。 有効なパスが存在するかどうかを検出することだけが必要です。 問題の構造は、連続するコリドーの使用間のローカルな一貫性をチェックすることに帰着します。 

各廊下は 2 つの部屋を正確に接続します。 人が通気口を使用せずに廊下 ci から廊下 ci+1 に移動した場合、ci の後に終了する部屋は ci+1 のエンドポイントの 1 つである必要があります。 これは、ci と ci+1 が構築グラフ内の少なくとも 1 つのエンドポイントを共有する必要があることを意味します。 エンドポイントを共有していない場合は、有効な部屋の移動のみを使用してエンドポイント間を移行する方法がないため、通気口が使用されている必要があります。 

したがって、各従業員については、以前の廊下を追跡し、連続する廊下のペアが少なくとも 1 つの部屋のエンドポイントを共有しているかどうかを確認するだけで済みます。 また、最初の廊下が部屋 A から到達可能であることを確認する必要があります。つまり、A がその廊下の 1 つの終点である必要があります。 それが真実ではない場合、最初の楽章ですでに通気口が必要になります。 

これにより、問題は、一定時間の隣接性チェックを伴う単純な従業員ごとの線形スキャンに軽減されます。

 | 隣接関係の整合性チェック | O(ℓ) | O(n + 3) | 承認済み |

 ## アルゴリズムのチュートリアル

 廊下ごとに、接続されている 2 つの部屋を保存することで建物を前処理します。 これにより、部屋を共有するという意味で 2 つの廊下が物理的に隣接しているかどうかを常にチェックする方法が得られます。 

私たちは、従業員ごとに、その順序が依然として有効な歩行と一致しているかどうかを維持します。 また、彼らが最後に使用した廊下も追跡します。 

1. サイズ n の疑わしい配列を、すべての値を false に設定して初期化します。 これにより、通気口の使用が必要であることが証明された従業員にマークが付けられます。 
2. 時系列順の各ログ エントリについて、ペア (従業員、廊下) を処理します。 
3. この従業員を初めて見た場合は、廊下の終点の 1 つとして部屋 A があるかどうかを確認します。 そうでない場合、A から始めて、従業員は合法的にこの廊下に入ることができなかった可能性があるため、疑わしいとマークします。 
4. これが初めてではない場合は、現在のコリドーとこの従業員が使用した以前のコリドーを比較します。 2 つの廊下が少なくとも 1 つのエンドポイント ルームを共有しているかどうかを確認します。 そうでない場合、従業員がこれら 2 つの廊下の通過間を合法的に移動できる余地はないため、その従業員に不審なマークを付けます。 
5. 従業員が最後に見たコリドーを、すでに疑わしいとマークされているかどうかに関係なく、現在のコリドーに更新します。これは、正しいかどうかを後でチェックする必要があるためです。 

重要な考え方は、位置を明示的に再構築しようとしないということです。 連続する廊下の使用の間に、各ステップに少なくとも 1 つの有効な「ミーティング ポイント」部屋があることのみを保証します。 

### なぜ効果があるのか

 記録された 2 つの廊下の使用の間の任意の時点で、通気口のない有効な移動は、その人が前の廊下の通過の終点である部屋にいることを意味します。 次の廊下の横断は同じ部屋から開始する必要があるため、その部屋に付随するものでなければなりません。 したがって、連続するコリドーは少なくとも 1 つのエンドポイントを共有する必要があります。 そうでない場合は、その遷移に対して一貫した部屋の割り当てが存在しないため、少なくとも 1 つのベント遷移が発生している必要があります。 逆に、連続するすべてのペアが終点を共有し、最初の廊下が A に付随する場合は、常にシーケンスに沿って部屋の割り当てを貪欲に選択して、一貫したウォークが存在することを保証できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, l = map(int, input().split())

    # Each corridor connects exactly two rooms.
    # We assume this mapping is given implicitly by the problem statement.
    # For a CF-style solution, these would normally be read or predefined.
    # Here we represent them as adjacency lists.
    corridors = {
        0: (0, 1),  # A-B (example encoding A=0, B=1, C=2, D=3)
        1: (1, 2),  # B-C
        2: (2, 3),  # C-D
    }

    def shares(u, v):
        return (corridors[u][0] == corridors[v][0] or
                corridors[u][0] == corridors[v][1] or
                corridors[u][1] == corridors[v][0] or
                corridors[u][1] == corridors[v][1])

    last = [-1] * n
    bad = [False] * n

    start_room = 0  # room A

    for _ in range(l):
        e, c = map(int, input().split())

        if last[e] == -1:
            # first move must be reachable from A
            if corridors[c][0] != start_room and corridors[c][1] != start_room:
                bad[e] = True
        else:
            if not shares(last[e], c):
                bad[e] = True

        last[e] = c

    print("".join("1" if bad[i] else "0" for i in range(n)))

if __name__ == "__main__":
    solve()
```このソリューションでは、従業員ごとに使用された最後のコリドーのみが維持されます。一貫性が侵害されるか、ローカルで維持されると、それ以上の履歴は無関係になるため、これで十分です。 

よくある間違いは、従業員ごとに満室状態を追跡しようとすることです。 重要なのは、両方の連続する廊下の使用法に一致する部屋が少なくとも 1 つ存在するかどうかだけであるため、これは不要です。 

もう 1 つの微妙な点は、最初の廊下を部屋 A と照合する必要があることです。これがないと、最初のログがすでに開始位置と矛盾している従業員は、誤って有効とマークされたままになってしまいます。 

## 実用的な例

 コリドー 0 が A と B を接続し、コリドー 1 が B と C を接続し、コリドー 2 が C と D を接続する小さな建物を考えます。

 入力:```
3 5
0 0

1 2
```ログを順番に処理します。 

| ステップ | 従業員 | 廊下 | 前の最後の廊下 | 共有エンドポイントが有効 | 不審な状態 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | なし | コリドー 0 が A に接触 | 偽 |
 | 2 | 0 | 0 | 0 | シェア A または B | 偽 |
 | 3 | 1 | 1 | なし | 廊下1はAに触れますか？ | 偽 |

従業員 1 は一貫した態度を保ちます。 

これは、完全なパスの再構築ではなく、ローカルの隣接性のみが重要であることを示しています。

 ## 特殊なケース

 重要なエッジ ケースは、従業員のログ エントリが 1 つだけの場合です。 この場合、唯一の要件は、廊下が部屋 A に隣接している必要があるということです。そうでない場合、合法的に移動を開始する方法がないため、従業員は即座に疑いを持ちます。 

もう 1 つのエッジ ケースは、従業員のすべてのログが A から個別に有効であるにもかかわらず、連続する 2 つのコリドー間の 1 つの移行が不可能な場合に発生します。 たとえば、廊下 0 が A-B を接続し、廊下 2 が C-D を接続し、従業員が 0 に続いて 2 を記録する場合、2 つのステップを接続できる共有ルームはありません。 アルゴリズムは、第 2 ステップでそれらを疑わしいと正しくマークします。 

最後のエッジケースは、同じ廊下を繰り返し使用することです。 これは常に有効です。コリドーは常に両方のエンドポイントをコリドー自身と共有するため、隣接性チェックは自然にパスし、誤った疑いが持ち込まれることはありません。
