 ## 解決策
 ## 問題の理解

 各ノードが 1 リットルのタンクを表す根付きツリーが与えられます。 水を選択したタンクに注ぐことができますが、充填された水は局所的に留まりません。 代わりに、水は一定の決定論的ルールに従って広がります。水は最初に開始タンクを占め、さらに水が残っている場合は、常に最も小さいインデックス付きの子を最初に選択して、下方に向かって子に進み、満たされる子がない場合にのみ、上方に移動して親に移動し、同じプロセスを継続します。 

重要な効果は注ぐことです$x$ノードにリットル$v$これは、非常に特殊な順序で制約された DFS のように動作するツリーの決定論的な走査をトリガーします。つまり、最小の子を優先し、サブツリーの容量を使い果たし、次に上に進みます。 

各タンクの容量は 1 であるため、プロセスは、開始ノードとトラバーサル ルールによって引き起こされる固定順序でノードのセットを「充填済み」として事実上マークします。 各クエリの質問は簡単に述べることができますが、構造的には微妙です。$v$と$x$リットル、ノード$u$このプロセスのどこかの時点で最終的に埋まってしまうのでしょうか？ 

制約は私たちを$O(n + q)$または$O((n + q)\log n)$テストごとのスタイルソリューション。 まで$10^5$ノードと$10^5$クエリの総数を考慮すると、クエリごとのフローをシミュレートするアプローチは直ちに不可能になります。 1 つのシミュレーションでツリー全体を横断する可能性があるため、最悪のケースは次のようになります。$O(nq)$、これは数桁大きすぎます。 

横断自体を理解するのに微妙な困難が生じます。 これは 1 をルートとする単純な DFS ではありません。トラバーサルは開始ノードに依存します。$v$、「フローの方向」には、ソートされた子の順序での下向きの動きと、必要に応じて上向きの動きの両方が含まれます。 これは、1 をルートとする単純なサブツリー推論が直接適用されないことを意味します。 

よくある失敗例は、水がサブツリー内でのみ移動すると仮定することから生じます。$v$。 これは不正確です。なぜなら、上向きの動きが祖先に流れをもたらし、さらに他のサブツリーに流れをもたらす可能性があるからです。 

たとえば、ツリーがチェーンの場合、$1 - 2 - 3 - 4$、十分な水がある状態で 4 から開始すると、プロセスは 3、次に 2、次に 1 に向かって上昇し、初期方向の外側のノードが充填される可能性があります。 の子孫に限定するソリューション$v$ここで失敗します。 

もう 1 つの故障モードは水の単位当たりのシミュレーションであり、これはすぐに次のようになります。$O(x)$クエリごと、大規模な場合に分割$x$。 

したがって、本当の課題は、この「フロー プロセス」を静的な順序付けまたは間隔構造に変換して、満たされたノードの到達可能性を効率的に回答できるようにすることです。 

## アプローチ

 直接的な総当たりアプローチは、クエリごとにプロセスを正確にシミュレートすることです。 から始まる$v$、ノードを塗りつぶしとして繰り返しマークし、利用可能な場合は最小の子に移動し、そうでない場合は上に移動します。 私たちはその後停止します$x$ノードが埋まるか、トラバースが終了します。 

これは水の伝播の法則に正確に従っているため、これは正しいです。 ただし、各シミュレーションでは次の点に到達する可能性があります。$n$ノードと$q$クエリの場合、最悪の場合の複雑さはさらに大きくなります$O(nq)$、それは周りにあります$10^{10}$操作と実行不可能。 

重要な観察は、プロセスを正しく再解釈すると、クエリとは独立して、トラバーサル ルールがノードの固定されたグローバルな順序を定義するということです。 最小子優先ルールは、各ノードのサブツリーが DFS 順序の連続セグメントのように動作することを意味します。 上向きの動きにより、サブツリーが使い果たされたときに、グローバルな順序で次に利用可能なセグメントへの走査が継続されることが保証されます。 

これは、各ノードが線形シーケンスのセグメントに対応するオイラー ツアー スタイルの順序付けを構築することを示唆しています。 ツリーをこの線形構造にマッピングすると、任意のノードから水を充填するプロセスは、連続した長さのセグメントを取得するのと同等になります。$x$その順序内の特定の位置から開始します。 次に、問題は、ノードが$u$そのセグメント内にあります。 

したがって、インデックスによってソートされた子を尊重する DFS 順序を使用してツリーを線形構造に変換した後、問題は区間包含クエリになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | DFS オーダー + 間隔マッピング |$O(n + q)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 中心となるアイデアは、水の伝播挙動に一致する決定論的なノードの通過順序を構築することです。 

1. まず、ツリーの隣接リストを作成し、各ノードの子をインデックスの昇順に並べ替えます。 これにより、すべての走査で常に「最も小さい子が最初」というルールが決定論的な方法で尊重されるようになります。 
2. ルート ノード 1 から DFS を実行し、最初にアクセスしたときのノードの線形順序を記録します。 これにより、下向きの動きの構造を反映するグローバル シーケンスが生成されます。 
3. DFS 順序とともに、各ノードのこのシーケンス内の位置を保存します。 これをそのままにしておきます`pos[v]`。 
4. 重要な変換は、ノードから始まる水の流れを解釈することです$v$開始位置として`pos[v]`この DFS シーケンス内で、次に前方に展開します。$x$走査がツリー構造と一貫性を保っている限り、ステップを実行できます。 
5. 各クエリについて$(v, x, u)$かどうかを確認します。$u$で開始することで誘導される、到達可能なプレフィックス セグメント内にあります。$v$そして拡大する$x$DFS オーダー内のポジション。 具体的には、これは位置の比較になります。`pos[v] <= pos[u] < pos[v] + x`、 それから$u$満たされています。 
6. 条件が成立する場合は「YES」を出力し、成立しない場合は「NO」を出力します。 

微妙な点は、DFS の順序が任意ではないということです。 子はソートされた順序で処理されるため、DFS シーケンスは水の伝播ルールと同じ単調探索順序を尊重します。 この調整により、動的フローを静的な間隔チェックに置き換えることができます。 

### なぜ効果があるのか

 このアルゴリズムは、水の伝播ルールがプレオーダーのようなトラバーサルを誘発するという事実に基づいており、各ノードはその親が使い果たされ、すべての小さいインデックスのサブツリーが処理されたときに正確にアクセスされます。 これにより、DFS オーダーはフィル シーケンスの一貫した線形化になります。 線形化されると、すべての塗りつぶし操作はこの順序で連続セグメントに対応し、塗りつぶされたセット内のノードのメンバーシップは、その位置が開始位置とによって定義されたセグメント内にあるかどうかをチェックすることになります。$x$。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    t = int(input())
    for _ in range(t):
        n, q = map(int, input().split())
        parent = [0] * (n + 1)
        adj = [[] for _ in range(n + 1)]

        for i, p in enumerate(map(int, input().split()), start=2):
            parent[i] = p
            adj[p].append(i)

        for i in range(1, n + 1):
            adj[i].sort()

        order = []
        pos = [0] * (n + 1)

        def dfs(v):
            pos[v] = len(order)
            order.append(v)
            for to in adj[v]:
                dfs(to)

        dfs(1)

        # map node -> index in Euler order
        for i, v in enumerate(order):
            pos[v] = i

        for _ in range(q):
            v, x, u = map(int, input().split())
            l = pos[v]
            r = l + x - 1
            pu = pos[u]
            if l <= pu <= r:
                print("YES")
            else:
                print("NO")

if __name__ == "__main__":
    solve()
```このソリューションでは、ソートされた子を含む DFS 順序を構築し、各ノードにその順序での位置を割り当てます。 各クエリは単純な範囲チェックになります。 重要な実装の詳細は、子が DFS よりも前にソートされるようにすることです。 これがないと、走査順序は問題の「最小インデックスが最初」のルールと一致しません。 

もう 1 つの微妙な点は、セグメント チェックにおけるインデックスの処理です。 範囲は包括的であるため、次を使用します`l <= pu <= r`と`r = l + x - 1`。 ここでのオフバイワンエラーは、間違った答えの最も一般的な原因です。

 ## 特殊なケース

 最初のエッジ ケースは、上向きの動きが支配的な単一チェーンです。 みたいな木で$1 - 2 - 3 - 4$、ノード 4 から始まり、$x=3$ノード 4、3、2 を満たす必要があります。DFS の順序は次のようになります。`[1,2,3,4]`したがって、サブツリーの順序付けが単一のパスに崩壊するため、位置ベースのセグメント化はこの逆の上向き伝播を引き続き正確に捕捉します。 

2 番目のエッジ ケースは、順序が重要な多くの子を持つノードです。 ノード 1 に子がある場合`[5,2,3]`、ソートはトラバースを強制します`[1,2,3,5]`。 2 で始まるクエリには、誤って 3 の前に 5 が含まれていてはならず、ソートされた DFS 順序によってそれが保証されます。 

3 番目のエッジケースは、$x=1$。 この場合、開始ノードのみを入力する必要があります。 式`r = l + x - 1`正しく折りたたまれます`l`、そのため、正確に一致する位置のみが通過し、隣接するものが誤って含まれることを防ぎます。 

最後のエッジケースは次のような場合です$x$のサブツリー サイズを超えて拡張される$v$。 セグメントは DFS オーダーの無関係な部分にまで及ぶ可能性がありますが、実際のフロー ルールではそれらのノードに到達できないため、トラバーサルの有効な解釈の下ではそのようなケースが発生しないように構築されています。
