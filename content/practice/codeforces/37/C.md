 ## 問題の理解

 バイナリプレフィックスコードを構築する必要があります。 

入力により、言語内のすべての単語の長さが得られます。 すべての単語に含まれるのは次のとおりです`0`そして`1`、どの単語も別の単語の接頭辞として使用することはできません。 私たちはそのような単語のセットを構築するか、それが不可能であると判断する必要があります。 

たとえば、長さが次の場合、`[1, 2, 3]`、有効な構文の 1 つは次のとおりです。```
0
10
110
```これらの文字列はいずれも、別の文字列の接頭辞ではありません。 言葉`0`は接頭辞ではありません`10`なぜなら`10`から始まる`1`、 そして`10`は接頭辞ではありません`110`なぜなら`110`から始まる`11`。 

最大の難点は、長さが固定されていることです。 任意のコードワードの長さを自由に選択できるわけではなく、実際のバイナリ文字列だけを選択できます。 

制約が十分小さいため、アルゴリズムを考慮する余裕があります。`O(n log n)`あるいは`O(total_length^2)`実際には、`n ≤ 1000`そしてそれぞれの長さは最大で`1000`。 それでも、バイナリ文字列のブルートフォース攻撃は完全に不可能です。`1000`あることを意味します`2^1000`考えられる候補者。 

プレフィックスのないバイナリ文字列の構造は、バイナリ トライの観点から考えることを強く示唆しています。 すべてのノードはプレフィックスに対応しており、単語を選択することは、1 つのノードを終端としてマークすることを意味します。 ノードが終端になると、その下の長い文字列にその単語がプレフィックスとして含まれるため、そのサブツリー全体が使用できなくなります。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

すべての長さが次のようになると仮定します。`1`:```
3
1 1 1
```長さのバイナリ文字列は 2 つだけです`1`、つまり`0`そして`1`。 不注意で貪欲なアルゴリズムでは、より深い文字列を試行し続ける可能性がありますが、より深い文字列にはこれらの単語の 1 つがプレフィックスとして含まれることになります。 正しい出力は次のとおりです。```
NO
```もう 1 つの注意が必要なケースは、繰り返される長さです。```
4
2 2 2 2
```長さのバイナリ文字列がちょうど 4 つあるため、これは有効です。`2`:```
00
01
10
11
```トライ内で兄弟を誤ってブロックする不適切な実装では、この有効なケースが拒否される可能性があります。 

もう 1 つの微妙な状況は、短い単語がスペースを消費しすぎる場合に発生します。```
3
1 2 2
```長さ 1 のワードを 1 つ選択すると、トライの分岐は 1 つだけ使用可能になります。 そのブランチには、同じ長さの文字列が 2 つだけ含まれています`2`, しかし、そのうちの 1 つは選択された長さ 1 の単語で始まり、禁止されます。 長さ 2 のワードの最大数が制限されます。 正しい答えは次のとおりです。```
NO
```これはまさに、トライ構造を慎重に扱わない限り、局所的な貪欲な選択を危険なものにする種類の相互作用です。 

## アプローチ

 ブルートフォースのアイデアは単純です。 必要な長さのバイナリ文字列を 1 つずつ生成し、新しい文字列が以前に選択した文字列と競合するかどうかを確認します。 2 つの文字列のどちらかがもう一方のプレフィックスである場合、2 つの文字列は競合します。 

これは短い長さの場合に機能します。 各候補文字列について、以前に選択したすべての単語と比較できます。 問題は検索スペースです。 一本の長さでも`1000`言葉には`2^1000`可能性。 最悪の場合、いくら剪定を行ってもこのアプローチを救うことはできません。 

実際の観察は、プレフィックスのないセットがバイナリ トライのリーフに自然に対応するということです。 

すべてのバイナリ文字列を無限バイナリ ツリー内のパスとして考えてください。 左に移動すると追加`0`、右に移動すると追加します`1`。 長さの言葉`k`深さのノードに対応します`k`。 

このビューでは、プレフィックス条件が単純になります。 ノードを単語として選択した場合、そのノードの祖先または子孫を選択することは禁止されます。 したがって、選択されたすべての単語は、選択されたノード内のリーフである必要があります。 

これは貪欲な構築を示唆しています。 

最初に短い長さを処理すると、その深さで現在利用可能な辞書編集上最小のノードを常に割り当てることができます。 ノードが使用されると、そのサブツリーは自動的に考慮から消えます。 

これを実装するクリーンな方法は、現在利用可能なプレフィックスのセットを維持することです。 最初は空の文字列のみが存在します。 より深い文字列を生成するには、プレフィックスを置き換えることによってノードを繰り返し拡張します。`x`と`x0`そして`x1`。 

重要な不変条件は、利用可能なセットにはペアごとに競合しないプレフィックスが常に含まれていることです。 長さの単語が必要な場合`L`、利用可能なプレフィックスが深さに達するまで拡張します。`L`。 そのようなノードが存在しない場合、構築は不可能です。 

これにより、指数関数的な検索が決定論的な貪欲なトライのトラバーサルに変わります。

 | ブルートフォース | 指数 | 指数 | 遅すぎる |

 ## アルゴリズムのチュートリアル

 1. すべての長さを元のインデックスとともに読み取ります。 

回答は入力順に出力する必要がありますが、短い単語は長い単語を制約するため、ソートされた順序で長さを処理する方がはるかに簡単です。 
2. 単語を長さ順に並べ替えます。 

短い単語はサブツリー全体をブロックするため、最初に短い単語を割り当てるのが安全です。 短い言葉を遅らせると、後で衝突が生じる可能性があります。 
3. 現在利用可能なプレフィックスのキューを維持します。 

最初はキューには空の文字列のみが含まれています`""`。 
4. 必要な長さごとに`L`、キューの先頭が長くなるまで、利用可能な最も短いプレフィックスを繰り返し拡張します。`L`。 

プレフィックスの展開`x`取り外して挿入することを意味します`x0`そして`x1`。 

これは、バイナリ トライ内で 1 レベル深く下降することをシミュレートします。 
5. 拡張後、フロントプレフィックスの長さが正確であるかどうかを確認します`L`。 

使用可能なすべてのプレフィックスがすでに次の値よりも深い場合`L`、その場合、長さの有効な単語がありません`L`もう存在します。 出力`NO`。 
6. それ以外の場合は、フロントプレフィックスをこのリクエストに対して選択されたワードとして取得し、キューから削除します。 

これを削除すると、子孫が後で使用されなくなり、プレフィックスのない状態が自動的に保持されます。 
7. 選択した単語を元のインデックスに保存します。 
8. すべてのリクエストを処理した後、出力します。`YES`保存された単語を入力順に印刷します。 

### なぜ効果があるのか

 このアルゴリズムは、使用可能なすべてのプレフィックスがバイナリ トライの未使用のサブツリーを表すという不変条件を維持します。 

プレフィックスを展開すると`x`の中へ`x0`そして`x1`をルートとするサブツリーを分割します。`x`将来の文字列を失うことなく、その 2 つの子サブツリーに変換されます。 

言葉を選ぶとき`x`の場合、そのサブツリーを将来の考慮事項から永久に削除します。 これにより、それ以降の単語が`x`接頭語として。 

長さを昇順に処理することで、貪欲な選択が有効になります。 短い単語は常に長い単語よりも多くのスペースをブロックするため、短い単語を遅らせると柔軟性が低下するだけです。 必要な深さで辞書編集的に最小の利用可能なプレフィックスを常に取得することにより、利用可能なトライ領域を無駄にすることはありません。 

アルゴリズムが一定の長さで失敗した場合`L`、残りの利用可能なプレフィックスはすべて、すでに次の値よりも深いです`L`。 トライの深さは拡張中にのみ増加するため、その深さで新しいノードを作成する方法はありません。`L`。 有効な構造は存在できません。 

## Python ソリューション```python
import sys
from collections import deque

input = sys.stdin.readline

def solve():
    n = int(input())
    lengths = list(map(int, input().split()))

    arr = [(lengths[i], i) for i in range(n)]
    arr.sort()

    q = deque([""])
    ans = [""] * n

    for length, idx in arr:
        while q and len(q[0]) < length:
            cur = q.popleft()
            q.append(cur + "0")
            q.append(cur + "1")

        if not q or len(q[0]) != length:
            print("NO")
            return

        ans[idx] = q.popleft()

    print("YES")
    print("\n".join(ans))

solve()
```解決策は try 解釈に直接従います。 

キューには、使用可能なプレフィックスが辞書順に格納されます。 最初は空の文字列のみが存在します。 ノードを展開することは、ノードをその 2 つの子で置き換えることに相当します。 

の`while`ループは、利用可能な最も浅いプレフィックスが必要な深さに達するまで拡張され続けます。 ターゲットの深さよりも短いプレフィックスはまだ単語として使用できないため、これは重要です。 

障害の状態は微妙です。```
if not q or len(q[0]) != length:
```利用可能な最短のプレフィックスが既に次の値よりも深い場合は、`length`の場合、利用可能なすべてのプレフィックスも同様に深くなります。 トライ内で上に進むことは決してできないので、この正確な長さの単語を構築することは不可能です。 

選択したプレフィックスをキューから削除すると、プレフィックスフリーが強制されます。 単語が選択されると、そのサブツリーは永久に消えます。 

キューのサイズが問題を引き起こすほど大きくなることはありません。 展開するたびにノードの数が 1 つずつ増加し、選択される単語の総数はわずか`1000`。

# minimum size
