 ## 問題の理解

 のグラフから始めます$n$頂点にラベルが付いており、エッジはありません。 目標は正確に終わることです$m$無向エッジ。 頂点間の各エッジ$u$そして$v$は自由に選択できません。その重みは固定されており、次の値と等しくなります。$\gcd(u, v)$。 ただし、エッジを構築する実際のコストは、個々のエッジに直接依存しません。 代わりに、エッジ作成をバッチ処理する操作を繰り返し実行できます。 

1 回の操作で数値を選択します$k \ge 1$。 選択可能であれば$k$現在エッジが欠落している場合、それらをすべて追加し、合計コストを支払います$k + 1$、個人のアイデンティティに関係なく。 これは、バッチ内のエッジあたりのコストがエンドポイントではなく、バッチ サイズのみに依存することを意味します。 この制約は純粋に組み合わせによるものです。含めることができるのは、まだ存在せず、自己ループまたは重複ルールに違反しない有効なエッジのみです。 

重要な問題は、エッジを 1 つずつ選択するわけではないことです。 代わりに、最終セットを分割する必要があります。$m$エッジをグループに分けます。グループのサイズは$k$費用$k + 1$。 グラフの構造 (gcd 制約による) は、必要なバッチを形成するのに十分な有効なエッジが存在するかどうかという実現可能性においてのみ重要です。 

制約は大きく、合計すると$n$テストケース全体で最大$10^6$。 すべてのペア間のエッジを明示的に構築または列挙しようとする解決策は、完全なグラフが$O(n^2)$エッジ。 テスト ケースごとに隣接構造を保存するだけでも、メモリと時間の制限を超えます。 ソリューションは、テスト ケースごとに線形または線形に近い時間で機能する必要があります。 

gcd 構造によって課される実現可能性の制限を理解せずに貪欲なバッチ処理を試みると、微妙な失敗のケースが発生します。 たとえば、小さいところでは、$n$、必要なプロパティを持つ有効なエッジが少なすぎる可能性があるため、すべてのバッチ サイズが達成できるわけではありません。 もう 1 つのよくある間違いは、次のパーティションが存在すると仮定することです。$m$バッチ サイズに分割することは可能ですが、互換性のあるエッジが限られているために一部のバッチ サイズを形成できないことは無視されます。 

## アプローチ

 強引な視点とは、すべてを考慮することです$\binom{n}{2}$考えられるエッジを選択し、有効なものにマークを付けて、選択したサイズのサブセットを分割してみます。$m$バッチに分割します。 サイズごとのバッチ$k$費用$k + 1$したがって、すべてのパーティションを検索します。$m$そして、有効なエッジを使用してそれらのパーティションを実現するあらゆる方法。 これは組み合わせ的に爆発的です。分割する前であっても、エッジの列挙は危険です。$O(n^2)$、およびパーティションの数$m$指数関数的に成長します。 

重要な観察は、エッジの実際のアイデンティティはコストにとって重要ではなく、各バッチで取得するエッジの数だけが重要であるということです。 したがって、グラフの構造は、どのバッチ サイズが実現可能かを決定する場合にのみ重要になります。 これにより、問題はどの整数を決定するかに減ります。$k$バッチ サイズとして達成可能であり、パーティション全体にわたるコスト式を最小化します。$m$。 

より深い構造は gcd エッジから生じます。 任意の頂点に対して$x$の倍数に接続します。$x$、したがって、頂点は割り算によってグループ化できます。 これにより、より大きな gcd 値がより制約されたエッジ セットに対応する階層が作成されます。 最適な構築では、この分割構造を効果的に使用して、各「レベル」で形成できるエッジの数と、それらをバッチにグループ化する方法を決定します。 

実現可能性を除数層の観点から再解釈すると、問題は、構造化容量関数に対する貪欲なコスト最小化、つまり、与えられた最小 gcd 寄与で利用可能なエッジの数に帰着します。

 ## アルゴリズムのチュートリアル

 重要なアイデアは、gcd で少なくとも指定された値で形成できるエッジの数を数え、この能力を使用して、最も安価なバッチから最も高価なバッチまで貪欲に組み立てることです。 

1. すべての整数について$d$、頂点の倍数がいくつあるかを計算します。$d$。 これにより、レベルでの gcd 構造に寄与する頂点のグループのサイズがわかります。$d$。 

gcd を持つエッジは正確に割り切れるため、これは重要です。$d$の倍数のペアによって決定されます$d$。 
2. これから、各レベルによって寄与される潜在的なエッジの数を計算します。$d$倍数内の組み合わせペアリングを使用します。 各レベルは、バッチ処理に利用可能な「ユニット」として解釈できるエッジの容量に寄与します。 
3. コストの昇順に gcd レベルを並べ替えるか反復します。 より低い gcd レベルは、より安価な有効エッジ構造に対応します。 

直感的には、より小さな構造的制約に関連付けられたエッジの方が豊富であり、最初に使用する必要があると考えられます。 
4. 残りの要件を維持する$m$、利用可能な容量レベルをレベルごとに減算します。 

各レベルで、取るエッジの数を決定します。 レベルに容量がある場合$c$、 取る$x = \min(c, m)$。 
5. 選択した金額ごとに$x$、これが対応する完全なバッチの数と、それらが引き起こすコストを計算します。 サイズのバッチ$k$費用$k + 1$したがって、エッジをより大きなバッチに分散することは有益です。 
6. 各レベル内でバッチ サイズを最大にしてオーバーヘッドを削減します。 これは局所的な貪欲な最適化になります。つまり、バッチが少ないほど追加コストが少なくなります。 
7. すべてのレベルを処理した後もまだ残っている場合は、$m > 0$、出力$-1$十分な有効なエッジが存在しないためです。 

### なぜ効果があるのか

 このアルゴリズムは、分割可能性によって引き起こされるエッジ実現可能性の単調構造に依存しています。 すべてのエッジは gcd 制約の階層に属し、この階層はすべての可能なエッジを独立した容量バケットに分割します。 コストはバッチ サイズとバッチごとの固定オーバーヘッドで線形であるため、コストを最小限に抑えると、容量を考慮しながらバッチ数を最小限に抑えることができます。 より高い gcd レベルは使用可能なエッジのセットを制限するだけで拡張することはないため、実現可能な最大の構造を最初に貪欲に消費しても、後の選択が妨げられることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    cnt = [0] * (n + 1)
    for d in range(1, n + 1):
        cnt[d] = n // d

    # number of pairs where gcd is divisible by d
    cap = [0] * (n + 1)
    for d in range(n, 0, -1):
        c = cnt[d]
        cap[d] = c * (c - 1) // 2
        for j in range(2 * d, n + 1, d):
            cap[d] -= cap[j]

    total = 0
    rem = m

    for d in range(1, n + 1):
        if rem == 0:
            break
        use = min(rem, cap[d])
        if use == 0:
            continue

        rem -= use

        k = use
        total += k + 1

    if rem > 0:
        print(-1)
    else:
        print(total)

t = int(input())
for _ in range(t):
    solve()
```この解決策は、除数格子のバックボーンを形成する各整数の倍数をカウントすることから始まります。 これらのカウントから、倍数に対する包含-排他を使用して、各値で正確に割り切れる gcd を持つペアがいくつあるかを計算します。 

配列`cap[d]`gcd レベルで構造的に利用可能なエッジの数を表します$d$。 これは、グラフの制約から数値容量への重要な変換です。 

最後のループは、小さい容量から貪欲に容量を消費します。$d$上向きに。 より小さい$d$はより柔軟なエッジに対応するため、最初にそれらを使用すると、後の要件で制約された構造を無駄にしないことが保証されます。 

コストの累積は、$k$バッチ内のエッジのコスト$k + 1$。 この単純化された貪欲なビューでは各レベルが単一のバッチとして扱われるため、コードによりオーバーヘッドの追加の数が効果的に最小限に抑えられます。

 ## 特殊なケース

 主なエッジケースは次のような場合です$m$gcd 構造によって暗示される可能なエッジの合計を超えています。 たとえば、次の場合$n=3$、最大エッジは 3 つだけであり、それを超えるリクエストは返される必要があります。$-1$。 アルゴリズムはこれを次のように検出します。`rem > 0`すべての容量を使い果たした後。
