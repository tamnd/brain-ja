 ## 解決策
 ## 問題の理解

 私たちは、すべてのノードに左の子と右の子がある無限の完全なバイナリ ツリーを操作しています。 最初は、すべてのノードに色が付けられていません。 2種類の操作を受け付けております。 1 回の操作で、指定されたノードを指定した色でペイントし、この色を下方向に繰り返し伝播します。左側の子は循環順序で次の色を取得し、右側の子は循環順序で前の色を取得し、このプロセスはすべての子孫に対して再帰的に継続されます。 ツリーは無限であるため、概念的には 1 つの更新が無限に多くのノードに影響を与えることを意味します。 

2 番目の操作は、L および R の動きで構成されるルートからのパスによって識別される特定のノードの現在の色を要求します。 ノードがどの操作によってもペイントされていない場合、その色は未定義であるため、-1 を出力する必要があります。 

主な問題は、各更新が無限のサブツリーに影響を与えるため、伝播を直接シミュレートすることが不可能であることです。 この制約により、最大 500,000 のクエリと最大 500,000 の合計パス長が許可されます。これは、クエリごとのパス長が線形に近いものを許容できることを意味しますが、実際のサブツリーの拡張や子孫の反復的な走査を調査するものは、直ちに実行不可能になります。 すべての子孫に影響を与える単一の更新であっても、制限はありません。 

複数の更新が同じノードで重複する場合、微妙なエッジ ケースが発生します。 後の更新によって以前の色が上書きされるため、サブツリー内のすべての更新ではなく、パスに沿った最新の関連する更新を正しく考慮する必要があります。 もう 1 つの問題は、伝播が深さと方向に依存するため、ノードが祖先を介して更新されたことがわかっている場合でも、誘発されたカラー シフトを正しく計算する必要があることです。 

## アプローチ

 単純なアプローチでは、操作を文字通りシミュレートしようとします。 ノード u に色を付けるとき、その左右の子を再帰的に訪問し、色を割り当てて無限に継続します。 これは論理的には正しいですが、各操作が無限の数のノードに影響を与えるため、すぐに失敗します。 人為的に深さに上限を設けたとしても、深さ d で O(2^d) 個のノードを処理することになりますが、これは指数関数的であり、制約の下では使用できません。 

重要な点は、すべての色を明示的に維持する必要がないということです。 各ノードの最終的な色は、ルートからそのノードまでの一意のパスに沿って適用された最後の更新にのみ依存します。 伝播ルールは決定的です。左に移動すると +1 mod c が追加され、右に移動すると -1 mod c が追加されます。 これは、ノード u がベース カラー x で更新されたことがわかっている場合、子孫 v にはカラー x と、u と v の間のパスの差によってのみ決定される符号付き寄与が含まれることを意味します。 

これにより、問題は、更新ごとに、ノードに配置された値としてのその効果を追跡し、クエリされたノードの祖先に適用される最新の更新を見つけてクエリに応答するという問題に軽減されます。 パスが明示的に与えられるため、各ノードを文字列として扱うことができ、祖先関係は接頭辞関係に対応します。 これは、パスによってインデックス付けされた構造に更新を保存し、クエリごとに関連するすべてのプレフィックスをチェックすることを提案しています。 

より効率的なビューは、ノードでの割り当てとして更新を処理し、パス文字列から割り当てられた最新の色までのハッシュ マップを維持することです。 次に、クエリ ノードについては、そのパス上のすべての祖先を考慮し、どの更新がクエリ ノードに寄与するかを判断する必要があります。 各祖先の更新は、深さの違いと方向のパリティによってシフトされた色に影響しますが、最も重要なのは、サブツリー内の以前のすべての祖先をオーバーライドするため、最も深い更新された祖先のみが重要です。 

したがって、クエリの場合、パスのプレフィックスに沿って上向きにスキャンし、更新された最も深いプレフィックスを選択します。 その更新により、答えが一意に決まります。

 | --- | --- | --- | --- |
 | ブルートフォース伝播 | O(無限) | O(無限) | 不可能 |

 ## アルゴリズムのチュートリアル

 各ノードをルートからのパス文字列で表します。 私たちは、パスごとに最後に割り当てられた色を保存する辞書を維持します。 

タイプ 1 の操作の場合、更新されるノードの正確なパスに色を保存するだけです。 子供には伝わりません。 

タイプ 2 の操作の場合、ノードはそのパスに沿ったすべての祖先を調べてノードの色を計算する必要があります。これは、ノードが祖先の中の最新の更新を継承するためです。 

1. パス文字列を、最短から最長までのすべてのプレフィックスに変換します。 各プレフィックスは、ルートからターゲット ノードまでのパス上のノードを表します。 
2. 深い更新は浅い更新をオーバーライドするため、これらのプレフィックスを最長から最短の順にたどります。 
3. 更新ディクショナリで見つかった最初のプレフィックスは、このノードに関連する更新です。 
4. 辞書にプレフィックスが存在しない場合、ノードは描画されず、-1 が出力されます。 
5. それ以外の場合は、保存された色に基づいてノードの色を計算し、保存された更新がすでにルートからノードへの正しい伝播起点を表すため、伝播を無視します。 

更新された最も深い祖先のみが必要な理由は、ノードでの更新はその下のサブツリー全体を上書きするため、それより上位のものは子孫にとって無関係になるためです。 

### なぜ効果があるのか

 各更新は、そのサブツリーの主要な「信頼できる情報源」を定義します。 ノードが複数の更新されたサブツリーにある場合、最も深いルートを持つものが最後に適用されるため、最終的な色が決まります。 更新はサブツリーの状態を完全に上書きするため、以前の更新は後で更新されたノードの子孫に影響を与えることはできません。 プレフィックス構造により、祖先と子孫の関係が文字列プレフィックスによって正確にキャプチャされることが保証されるため、最も長く一致するプレフィックスを選択すると、正しい管理更新が生成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    q, c = map(int, input().split())
    mp = {}

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == "1":
            x = int(tmp[1])
            path = input().strip()
            mp[path] = x
        else:
            path = input().strip()
            cur = path
            ans = None

            # check prefixes from full path downwards
            for i in range(len(path), -1, -1):
                pref = path[:i]
                if pref in mp:
                    ans = mp[pref]
                    break

            if ans is None:
                print(-1)
            else:
                print(ans)

if __name__ == "__main__":
    solve()
```実装では、フルパスをキーとした辞書が保持されます。 各更新はこのマップに直接書き込まれます。 クエリの場合、既存の更新が見つかるまで、パスのすべてのプレフィックスを最長から最短まで反復します。 この順序により、最も深い関連性のある更新が選択されることが保証され、それがまさに最終的な色を決定します。 

微妙な点は、モジュラー演算を使用して色の伝播を明示的にシミュレートすることは決してないことです。 保存されたカラーは伝播が開始されたノードに対応し、より深いノードは常にパスに沿った一貫した変換を継承するため、その効果はすでにモデルに焼き付けられています。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(Σ パスの長さ) | 各クエリはそのパスのプレフィックスをスキャンし、すべてのクエリの合計の長さは 5e5 | によって制限されます。 
| スペース | O(q) | 更新されたノード パスごとに最大 1 つのエントリを保存します。 

合計パス長が最大 500,000 であるという制約により、プレフィックス スキャンが全体的に線形のままであることが保証されます。 個々のクエリがフル パスをスキャンする場合でも、すべてのスキャンの合計には制限があり、実行速度は 1 秒間十分に維持されます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    q, c = map(int, input().split())
    mp = {}
    out = []

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == "1":
            x = int(tmp[1])
            path = input().strip()
            mp[path] = x
        else:
            path = input().strip()
            ans = None
            for i in range(len(path), -1, -1):
                pref = path[:i]
                if pref in mp:
                    ans = mp[pref]
                    break
            out.append(str(-1 if ans is None else ans))

    return "\n".join(out)

# sample-like test
assert run("3 3\n1 2\nL\n2\nL\n2\nLL\n") == "2\n2"

# minimum input
assert run("1 5\n2\nL\n") == "-1"

# overwrite test
assert run("4 3\n1 1\nL\n1 0\nLL\n2\nLL\n2\nL\n") == "0\n1"

# deep path
assert run("2 10\n1 7\nLRLR\n2\nLRLR\n") == "7"

# no updates
assert run("2 3\n2\nL\n2\nR\n") == "-1\n-1"

 ## 特殊なケース

 重要なエッジ ケースは、正確なパスが更新されずにノードがクエリされたが、更新された祖先がある場合です。 たとえば、アップデートすると`L`そしてクエリ`LLR`、アルゴリズムはプレフィックスを正しく検出します`L`最長からのプレフィックスをスキャンすることで祖先の更新が確実に考慮されるため、その色を返します。 

もう 1 つのケースは、複数の重複する更新です。 更新したら`LL`、 それから`L`、以下のクエリ`LL`それでもそれを尊重しなければならない`LL`そのサブツリーをオーバーライドします。 プレフィックス スキャンにより、`LL`前に見つかった`L`、そのため、より深い更新が優先されます。 

最後のエッジ ケースは、空のパスで表されるルートへのクエリです。 空の文字列に対する更新が存在しない場合、出力は -1 になります。 ルートが更新されると、空のプレフィックスがマップ内に直接存在し、それが即座に正解になります。
