 ## 解決策
 ## 問題の理解

 すべての文字位置に付加された文字列と整数の重みが与えられます。 文字を削除することは許可されており、削除ごとに、文字列内に元々表示されていた削除位置の重みがかかります。 削除後、残りの文字を順番に確認し、結果の文字列にサブシーケンスとして「hard」が含まれていないことを確認します。 

重要な点は、「hard」を部分文字列としてではなく、部分列として禁止しようとしているということです。 これにより、構造がはるかに緩やかになり、必要な文字は 4 文字だけになります`h → a → r → d`残りの文字列のどこかに順番に出現しますが、必ずしも連続しているとは限りません。 私たちの目標は、削除コストの合計を最小限に抑えながら、そのような順序付けされた 4 つ組が存在しないように文字を削除することです。 

文字列の長さは最大 100,000 で、各文字には関連するコストがあります。 サブセットまたは位置を明示的に列挙しようとするソリューションは、すぐに失敗します。$2^n$行為は不可能です。 すべての部分文字列に対する 2 次 DP ですら遅すぎます。 この構造は、線形または$O(n \cdot k)$どこに近づくか$k$小さいです。 

微妙な問題はコストの定義にあります。文字を削除するコストは、以前の削除後の位置ではなく、元のインデックスに依存します。 これにより、削除間の相互作用が排除されるため、各削除を独立して処理できるようになります。これは、動的プログラミングの正確性にとって重要です。 

注目に値するエッジケースの 1 つは、文字列にすでに何も含まれていない場合です。`h`、`a`、`r`、 または`d`使いやすい順番で。 この場合、削除は必要ないため、答えはゼロになります。 もう 1 つは、文字が集中している場合です。`"hhharddd"`ここには、「hard」の重複するサブシーケンスが多数存在するため、1 つの文字の出現をすべて貪欲に削除するのではなく、どの文字を削除するかを慎重に選択する必要があります。 

## アプローチ

 直接的なアイデアは、文字を削除するすべての方法を検討し、部分列として「ハード」が残っているかどうかを確認することです。 これには、インデックスのサブセットの選択、線形時間でのサブシーケンス条件の検証、および削除コストの合計が含まれます。 枝刈りを試みたとしても、サブセットの数は最悪の場合でも指数関数的に増加するため、このアプローチは実行できません。 

禁じられたパターンの構造は、別の視点を示唆しています。 どの文字を削除するかを考える代わりに、文字列をスキャンしながら部分シーケンスの形成を「ハードに」追跡する方法を考えます。 プロセスのどの時点でも、プレフィックスに関する唯一の関連情報は、サブシーケンスとしてすでに一致した「ハード」の文字数です。 これにより、当然のことながら、パターンの進行を表す動的プログラミング状態が得られます。 

文字列のプレフィックスを処理した後、残っている部分シーケンスとして「ハード」という特定のプレフィックスと一致した後の削除の最小コストを表す状態を定義します。 新しい文字を処理するときは、それを削除するか (コストを支払い、状態を変更しないままにします)、保持します。その場合、文字に応じて、一致したプレフィックスが進む可能性があります。 

重要な構造的洞察は、サブシーケンスのマッチングは相対的な順序のみに依存するため、遷移は単調であるということです。`h`、私たちはそれを「一致させない」ことはありません。 これにより、DP は小さく安定し、意味のある状態が 4 つだけになります。

 ## アルゴリズムのチュートリアル

 この問題は、どの文字を削除するかを決定しながら、残りの文字列で「ハード」な部分シーケンスの形成にどれだけ近づいているかを維持することであると解釈します。 

1. 「ハード」の文字がすでに一致している数に対応する 4 つの DP 状態を定義します。0 は一致しないことを意味し、1 は一致したことを意味します`h`, 2の意味`ha`, 3の意味は`har`、4 は、禁止されたサブシーケンスがすでに形成されていることを意味します。 最後の状態は望ましくないため、最適なソリューションでは回避されます。 
2. 状態 0 のコスト 0、および他のすべての状態のコストが無限である文字列を処理する前に DP を初期化します。 これは、削除も一致するサブシーケンスも存在しない状態から開始することを反映しています。 
3. 文字を左から右に処理します。 各位置で、キャラクターを削除するか保持するかを決定します。 それを削除すると、そのコストが追加され、すべての DP 状態は変更されません。 
4. キャラクターを保持する場合、現在の状態とキャラクター自体に応じてトランジションを更新します。 たとえば、状態 0 から見ると、`h`状態 1 への遷移を許可します。 他の文字を見ると状態は変化しません。 
5. 状態 1 については、次のようになります。`a`、状態 2 に進むことができます。 それ以外の場合は状態 1 に留まります。同じロジックが続きます。つまり、状態 2 は状態 3 に進みます。`r`、状態 3 が 4 に進みます。`d`。 
6. 最終的な答えでは、遷移によって状態 4 に到達することが明示的に許可されないようにします。 文字を保持すると「ハード」が完了する場合、最終文字列は簡単でなければならないという要件に違反するため、そのオプションは破棄されます。 
7. すべての文字を処理した後、状態 4 は無効な構成を表すため、答えは状態 0 ～ 3 の間の最小 DP 値になります。 

正しさは、どのプレフィックスにおいても、将来の実現可能性を決定するために必要な唯一の情報は、これまでサブシーケンスとしてどれだけの「ハード」が一致したかであるという事実に基づいています。 同じ状態に達する 2 つの履歴は将来の決定に対して同等であるため、DP 圧縮は有効です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    s = input().strip()
    a = list(map(int, input().split()))

    INF = 10**18
    dp = [0, INF, INF, INF]  # states: '', 'h', 'ha', 'har'

    for i in range(n):
        ndp = [INF, INF, INF, INF]

        # delete current character
        for j in range(4):
            ndp[j] = min(ndp[j], dp[j] + a[i])

        c = s[i]

        for j in range(4):
            if dp[j] >= INF:
                continue

            if j == 0:
                if c == 'h':
                    ndp[1] = min(ndp[1], dp[0])
                else:
                    ndp[0] = min(ndp[0], dp[0])

            elif j == 1:
                if c == 'a':
                    ndp[2] = min(ndp[2], dp[1])
                elif c == 'h':
                    ndp[1] = min(ndp[1], dp[1])
                else:
                    ndp[1] = min(ndp[1], dp[1])

            elif j == 2:
                if c == 'r':
                    ndp[3] = min(ndp[3], dp[2])
                elif c == 'h':
                    ndp[2] = min(ndp[2], dp[2])
                else:
                    ndp[2] = min(ndp[2], dp[2])

            elif j == 3:
                if c == 'd':
                    continue
                else:
                    ndp[3] = min(ndp[3], dp[3])

        dp = ndp

    print(min(dp))

if __name__ == "__main__":
    solve()
```DP 配列は、禁止されたサブシーケンスの構築がどこまで進んでいるかを追跡します。 削除トランジションは常に有効であり、単純にコストが蓄積されます。 キープトランジションは、キャラクターのステート 3 からの最終トランジションを禁止することで、「ハード」が完了することを慎重に防ぎます。`d`。 

よくある落とし穴は、コストのインデックス付けを誤って処理することです。コストは元のポジションに関連付けられているため、常に`a[i]`削除を調整せずに直接。 もう 1 つの微妙な問題は、複数の DP 状態が共存可能であり、各ステップで個別に更新する必要があることを忘れていることです。そうしないと、最適な組み合わせが失われます。

 ## 特殊なケース

 長さが 1 または 2 の最小文字列には、サブシーケンスとして「ハード」が含まれることはありません。そのため、DP が状態 3 に到達しないため、最適コストは常にゼロになります。貪欲な削除戦略では、実際のサブシーケンスの進行状況を追跡するのではなく「安全に」しようとすると、誤って不必要に文字が削除されてしまいます。 

次のような完全に一致する文字列`"hard"`形成後に反応するのではなく、完了を防ぐ必要性を示しています。 DP は、禁止された終了状態への移行を明示的にブロックし、アルゴリズムが無効な構成を決して受け入れないようにします。
