 ## 解決策
 ## 問題の理解

 グリッドに埋め込まれた平面の「ストリート グラフ」が与えられます。 各交差点は既知の座標を持つ頂点であり、各道路は 2 つの交差点間の水平または垂直の直線セグメントです。 各交差点で、Brice は決定論的なエージェントのように動き、利用可能な外向き方向の数に応じたローカル順序付けルールに基づいて常に次の道路を選択します。 

各道路には耐久性にも限界があります。 Brice がエッジを横切るたびに、残りの容量が 1 つずつ減少します。 道路が十分な回数使用されると、Brice にとってその道路は消滅します。これは、その道路が将来の意思決定に利用できなくなることを意味し、そのエンドポイントの程度が効果的に低下します。 

歩行は、指定された交差点と最初の方向から始まります。 そこから、ブライスは交差点から交差点へと繰り返し移動し、そのたびにローカル ルールに従って次のエッジを選択し、使用可能な出力エッジがなくなる点に到達します。 タスクは、歩行が停止する最後の交差点を出力することです。 

グラフの幾何学的性質が重要です。 すべてのエッジは軸に沿って配置されているため、各交差点の入射方向は最大で 4 つです (北、南、東、西)。 これにより、ローカルの決定空間は小さく保たれますが、時間の経過とともにエッジが消えるため、プロセスは動的になります。 

この制約には、最大 2500 個の頂点と不特定数のエッジが含まれており、それぞれに大きな使用制限がある可能性があります。 エッジ セット全体を繰り返しスキャンしたり、隣接関係を最初から再構築したりする単純なシミュレーションでは、時間がかかりすぎます。 ただし、各ステップには最大 4 方向の間でのローカルな選択のみが含まれるため、ボトルネックとなるのは分岐ではなく、すべてのエッジにわたるトラバースの合計数です。 

歩行の途中でエッジが消え、交差点の「形状」が変化する場合、微妙なエッジケースが現れます。 

最初に 3 つの使用可能な方向があるノードを考えてみましょう。 1 つのエッジが使い果たされると、それが次数 2 の決定点になり、選択ルールが完全に変わります。 固定の順序を事前に計算し、決して更新しない単純なソリューションでは、利用可能なブランチのセットが動的であるため、ここでは失敗します。 

ジオメトリを無視し、隣接関係を順序なしリストとして扱う場合、別の障害モードが発生します。 たとえば、北、東、南に隣接する頂点では、「中央の枝」という規則は任意ではなく、角度の順序に依存します。 方向によって分類しないと、一貫性のない経路を選択し、意図した決定論的な歩みから逸脱してしまう可能性があります。 

## アプローチ

 ブルート フォース シミュレーションはステートメントに直接続きます。 完全なグラフを保存し、各ステップで現在のノードのすべてのインシデント エッジをスキャンし、使い果たされたエッジを除外し、残りの選択肢の数に基づいて次の手を決定します。 走査するたびにエッジ カウンタが減少します。 これはプロセスを正確に反映しているため、これは正しいです。 

このアプローチの問題は、各ステップでノードのすべてのエッジをスキャンし、順序付けを繰り返し再計算する必要がある可能性があることです。 各ノードの次数が小さい場合でも、エッジの容量が大きいため、ステップの総数は大きくなる可能性があります。 エッジの容量が最大 10^6 で、サイクルの一部である場合、エッジは何度も走査される可能性があり、シミュレーションの合計長が非常に長くなる可能性があります。 O(1) を超えるステップごとのオーバーヘッドは危険になります。 

重要な観察点は、グラフのジオメトリが固定されており、各ノードには最大 4 つの近傍ノードがあることです。 これは、角度に基づいて各ノードの周囲の近傍の一貫した循環順序を事前計算できることを意味します。 それが完了すると、すべての決定は、最大 4 つの候補を持つ小さな順序付きリストから 1 つの要素を選択することになります。 唯一の動的コンポーネントは、エッジがまだアクティブであるかどうかです。

したがって、構造を再計算する代わりに、各ノードに対して、隣接ノードの小さな順序付きリストとエッジごとのアクティブなカウンターを維持します。 各ステップで、最大 3 つの候補 (着信方向を除く) をフィルターし、残りの候補数に応じて決定的なルールを適用します。 

これにより、シミュレーションが一定時間の遷移による純粋なポインタの移動に縮小されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(総走査数 × 度) | O(n + m) | 実際には遅すぎる |
 | 順序付けされたローカル シミュレーション | O(総走査数) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 各エッジを、残りの使用量カウンターを持つ双方向オブジェクトとして扱います。 また、幾何学的埋め込みを方向ベクトルに変換して、各近傍にその端点を基準とした方向を割り当てることができるようにします。 

### ステップ

 1. 交差点ごとに隣接リストを構築し、近隣インデックスと座標から導出された方向ベクトルの両方を保存します。 

これは、移動ルールが左、中央、右の順序に依存し、インデックスベースではなく幾何学的であるため、これが重要です。 
2. 各ノードについて、極角を使用して、その点を中心に反時計回りの順序で隣接ノードを並べ替えます。 

これにより、「左」と「右」がインデックス シフトとなる循環構造が作成されます。 
3. 各エッジに、両方向で共有される残りの容量を保存します。 
4. 既知の着信方向を使用して、開始ノードでウォークを初期化します。 
5. 各ステップで、現在横断しているエッジを残りの容量から削除します。 ゼロに達すると、将来の決定がブロックされたとみなされます。 
6. 現在のノードで、来た方向を除き、使い果たされたエッジを除く、使用可能な発信エッジのリストを作成します。 
7. 出力エッジが残っていない場合は、プロセスを停止し、現在のノードを出力します。 
8. 発信オプションが 2 つだけ残っている場合は、循環順序で着信方向の左側にあるオプションを選択します。 

これは、入力エッジの後の最初の有効な反時計回りの近傍を取得することに対応します。 
9. 送信オプションが 3 つだけ残っている場合は、循環的な順序で中央のものを選択します。 

これは、左端と右端をスキップして中央方向を選択することに対応します。 
10. 選択した近隣に移動し、それに応じて着信方向を更新し、これを繰り返します。 

### なぜ効果があるのか

 不変条件は、すべてのノードで、隣接ノードの循環順序が固定されており、ジオメトリと一貫性があり、局所的に意味のある間隔に循環する着信方向のパーティションであることです。 「左」と「中央」のルールは常にこの固定サイクルを基準にして解釈されるため、エッジが消えても、残りの構造は同じ相対的な順序を保持します。 各ステップは現在のノードと現在の入力方向のみに依存し、両方が状態によって完全にキャプチャされるため、シミュレーションは決定的で正確なままになります。 

エッジ削除では、これらのローカル セットから要素が削除されるだけです。 残りのエッジの相対的な循環順序は決して変更されないため、以前に定義された「左」と「中央」の関係は、生き残ったエッジ間で有効なままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def angle(dx, dy):
    # map direction to angle for sorting CCW
    # atan2 would work but avoid float: use quadrant ordering
    if dx == 0 and dy > 0:
        return 0
    if dx > 0:
        return 1
    if dx == 0 and dy < 0:
        return 2
    return 3

def dir_vec(a, b, coords):
    x1, y1 = coords[a]
    x2, y2 = coords[b]
    return x2 - x1, y2 - y1

n, m = map(int, input().split())
coords = []
vals = list(map(int, input().split()))
for i in range(n):
    coords.append((vals[2*i], vals[2*i+1]))

adj = [[] for _ in range(n)]
edges = {}

for _ in range(m):
    i, j, k = map(int, input().split())
    i -= 1
    j -= 1
    adj[i].append([j, k])
    adj[j].append([i, k])
    edges[(i, j)] = k
    edges[(j, i)] = k

s, d = input().split()
s = int(s) - 1

dir_map = {'N': (0, 1), 'S': (0, -1), 'E': (1, 0), 'W': (-1, 0)}
incoming = dir_map[d]

def order(node):
    # sort neighbors CCW
    x0, y0 = coords[node]
    res = []
    for nei, cap in adj[node]:
        x1, y1 = coords[nei]
        dx, dy = x1 - x0, y1 - y0
        ang = (dx, dy)
        res.append((ang, nei))
    # simple lexicographic proxy for CCW since grid directions only
    def key(item):
        dx, dy = item[0]
        if dx == 0 and dy > 0: return 0
        if dx > 0 and dy == 0: return 1
        if dx == 0 and dy < 0: return 2
        return 3
    res.sort(key=key)
    return [nei for _, nei in res]

while True:
    x, y = coords[s]

    candidates = []
    for nei, cap in adj[s]:
        if edges.get((s, nei), 0) <= 0:
            continue
        dx, dy = coords[nei][0] - x, coords[nei][1] - y
        if (dx, dy) == (-incoming[0], -incoming[1]):
            continue
        candidates.append(nei)

    if not candidates:
        print(x, y)
        break

    # order candidates CCW
    def key(nxt):
        dx, dy = coords[nxt][0] - x, coords[nxt][1] - y
        if dx == 0 and dy > 0: return 0
        if dx > 0 and dy == 0: return 1
        if dx == 0 and dy < 0: return 2
        return 3

    candidates.sort(key=key)

    if len(candidates) == 1:
        nxt = candidates[0]
    elif len(candidates) == 2:
        nxt = candidates[0]
    else:
        nxt = candidates[1]

    edges[(s, nxt)] -= 1
    edges[(nxt, s)] -= 1

    incoming = (coords[s][0] - coords[nxt][0], coords[s][1] - coords[nxt][1])
    s = nxt
```この実装における中心的な考え方は、シミュレーション ループが現在のノードと受信方向のみを維持するということです。 すべての決定で最大 4 つの候補が再計算されるため、走査回数が多い場合でも、ステップごとのオーバーヘッドは一定のままです。 

エッジ ディクショナリは残りの容量を対称的に格納するため、両方の方向で枯渇が一貫します。 これにより、向きごとの状態管理の重複が回避されます。 

## 実用的な例

 ノードに北、東、南の 3 つの下り道路がある小さな交差点を考えてみましょう。 

### 例 1

 西からノード A から開始します。 

| ステップ | ノード | 受信中 | 候補者 (CCW) | 選択 |
 | --- | --- | --- | --- | --- |
 | 1 | あ | W | N、E、S | E (中ルール) |
 | 2 | B | W | ... | ... |

 これは、アルゴリズムが循環順序で一貫して中央方向を選択する、「3 つの分岐は中間の選択を暗黙的に示す」動作を示しています。 

### 例 2

 後のノードでは、枯渇した後に有効なエッジが 2 つだけ残ります。 

| ステップ | ノード | 受信中 | 候補者 | 選択 |
 | --- | --- | --- | --- | --- |
 | 1 | C | N | E、W | W (左ルール) |
 | 2 | D | E | ... | ... |

 これは、エッジが消えると、構造を変更することなく、ルールが「中央の選択」から「左に偏った選択」に自動的に折りたたまれることを示しています。 

これらのトレースは、アルゴリズムがローカル状態のみに依存し、グラフが進化しても安定したままであることを確認します。

 ## 特殊なケース

 重要なエッジ ケースとは、エッジが使用直後に消滅し、3 方向ジャンクションが 2 方向ジャンクションに減少する場合です。 この状況では、候補リストはステップ間で変化します。 

たとえば、ノードに最初は北、東、南があるとします。 東が尽きれば残るは北と南だけ。 アルゴリズムは自然に毎回候補を再計算するため、次の決定では 3 方向ルールではなく 2 方向ルールが正しく使用され、一貫性が維持されます。 

もう 1 つのケースは、ちょうど使い果たされた接続を除いて、着信方向自体が唯一残っている接続である場合です。 その状況では、逆方向をフィルタリングして除外すると空の候補セットが得られ、無効な移動を試みるのではなく、そのノードでの終了が正しくトリガーされます。 

どちらの場合も、古い隣接情報に依存するのではなく、現在のエッジ容量から候補を再計算することによって暗黙的に処理されます。
