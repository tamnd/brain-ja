 ## 解決策
 ## 問題の理解

 整数グリッド上の木の位置を示す固定マップと、ロボットによって生成された 2 番目の観察セットが与えられます。 ロボットは、自分がどこにいるのか、どちらを向いているのかを教えてくれませんが、現在見えているすべての木の相対位置を報告します。 

各センサーの読み取り値は、ロボットのローカル座標系で与えられます。 1 つの軸はロボットが向いている方向 (前方) に対応し、もう 1 つの軸はそれに垂直です (右)。 ロボットはグローバル グリッドの 4 つの軸方向のいずれかに合わせて配置されることが保証されているため、ローカル フレームは常にグローバル軸の 90 度回転であり、場合によっては符号が反転します。 

タスクは、指定された相対ツリー座標セットを正確に生成できる、ロボットの位置と向きで構成される一意のペアが存在するかどうかを判断することです。 そのような設定が存在しない場合は、「不可能」と出力されます。 複数の構成が可能な場合は、「Ambiguous」と出力されます。 それ以外の場合は、ロボットのグローバル座標を出力します。 

制約はすでにソリューションの構造を示唆しています。 ツリーの数は最大 5000、感知されたポイントの数は最大 1000 であるため、すべての構成をすべてのサブセットに対して直接照合しようとするソリューションは、候補ごとにすべてを単純に再計算すると遅すぎます。 ただし、数千万回の単純なハッシュ ルックアップや算術演算を実行する余裕はあります。このことは、ソリューションでは検索スペースを少数の変換候補に削減し、それらを効率的に検証する必要があることを強く示唆しています。 

微妙な点は、センサーの読み取り値がラベル付けされていないことです。 どの感知点がどの木に対応するかはわかりません。 これは、4 つの回転のうちの 1 つと平行移動の下で 2 つの点セット間の剛体変換マッチング問題を扱っていることを意味します。 

一般的な失敗ケースは、一貫性を検証せずに、センサー ポイントとツリー間の単一の任意の組み合わせによってソリューションが修正されると想定した場合に発生します。 たとえば、1 つのペアを選択すると、そのペアは誤って位置合わせされるが、構造の残りの部分は位置合わせされない候補ロボット位置が得られる可能性があります。 

もう 1 つの失敗例は、曖昧さの要件を無視したことに起因します。 有効な位置合わせが 1 つ存在する場合でも、データを説明する別の方向または位置が存在する可能性があり、正しい出力にはそれが反映されている必要があります。 

## アプローチ

 直接的なアプローチは、4 つの方向すべてを試しながら、感知された点と樹木の間で可能なすべての割り当てを試みることです。 方向ごとに、各センサー ポイントを個別のツリー ポイントと照合し、一貫した変換が存在するかどうかを確認します。 これはすぐに、検知点の数がおおよそ階乗複雑になる組み合わせ割り当て問題になり、実現可能な限界をはるかに超えています。 

重要な観察は、変換が厳密であり、単一の対応関係によって完全に決定されるということです。 センサー点と木の点を1つずつ固定し、姿勢も固定すればロボットの位置は一意に決まります。 ロボットの位置が固定されると、1 つおきのセンサー ポイントがグローバル座標に決定論的にマッピングされ、その座標がツリー セットに存在するかどうかを確認するだけで済みます。 

これにより、一致の検索の問題が、管理可能な数の変換候補の列挙にまで軽減されます。 方向ごとに、1 つのセンサー ポイントと 1 つの木のポイントを組み合わせて、原点候補を定義します。 これにより、最大で約 4 × 5000 × 1000 個の候補が生成されますが、コストのかかる方法ですべてのペアを完全に処理する必要はありません。 各候補は、ツリー セットへの定数時間ハッシュ ルックアップを使用して、センサー セット全体にわたって線形時間で検証できます。

これが機能するのは、正しいソリューションでは、同じ変換の下ですべてのセンサー ポイントを実際のツリー ポイントにマッピングする必要があるためです。 センサー ポイントが 1 つでも存在しないツリー座標にマッピングされると、間違った候補はすぐに失敗します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべての割り当てをブルート フォースで照合する | O(ns!) | お(1) | 遅すぎる |
 | 1 つの対応を修正 + 検証 | O(4 · nt · ns) | O(nt) | 承認済み |

 ## アルゴリズムのチュートリアル

 考えられる 4 つの方向をそれぞれ個別に検討します。 各方向は、ロボットのローカル座標からグローバル座標への固定マッピングを定義します。 

1. 高速メンバーシップ クエリのために、すべてのツリー座標のハッシュ セットを構築します。 これにより、変換されたセンサー ポイントが森林内に存在するかどうかを常時チェックできます。 
2. 選択した方向に対して、センサーの読み取り値をロボットの位置に対するグローバル オフセットに変換する関数を定義します。 この関数は、ロボットの向きによって暗示される回転をエンコードします。 
3. すべてのツリー ポイントとすべてのセンサー ポイントのペアを繰り返します。 各ペアについて、木の座標と変換されたセンサー座標の差としてロボットの候補位置を計算します。 このステップでは、単一の対応関係から翻訳が推測されます。 
4. ロボットの候補位置ごとに、同じ方向を使用してすべてのセンサー ポイントをグローバル座標に変換し、結果の各ポイントがツリー セットに存在するかどうかを確認することによって検証します。 
5. すべてのセンサー ポイントが既存のツリーにマッピングされている場合、この候補を有効なソリューションとして記録します。 
6. すべての方向とすべての候補原点を確認した後、結果を決定します。 有効な設定が存在しない場合は、「Impossible」と出力されます。 1 つだけ存在する場合は、その座標を出力します。 複数存在する場合は「Ambiguous」と出力します。 

### なぜ効果があるのか

 有効な解決策は方向と変換によって完全に決定されます。 その変換の下で単一のセンサーとツリーの対応が正しいと、変換が修正されます。 変換が本当に正しい場合は、すべてのセンサーの読み取り値を同時に保存する必要があるため、他のすべてのセンサー ポイントも既存のツリーに到達する必要があります。 ペアリングが間違っていると、少なくとも 1 つの点で変換が直ちに失敗します。これは、2 つの異なる点セットがグローバルに一貫性がない限り、剛体変換は部分的に一致できないためです。 

検証ステップでは、ローカル互換性ではなくグローバル一貫性が強制されるため、誤った候補が排除されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def transform(x, y, orient):
    # returns (dx, dy) in global frame from robot-local coordinates
    # but we only need transformed sensor point relative to robot origin
    if orient == 0:   # north: forward +y, right +x
        return x, y
    if orient == 1:   # south: forward -y, right -x
        return -x, -y
    if orient == 2:   # east: forward +x, right -y
        return y, -x
    # west: forward -x, right +y
    return -y, x

def solve():
    nt, ns, rmax = map(int, input().split())
    trees = set()
    tree_list = []
    for _ in range(nt):
        x, y = map(int, input().split())
        trees.add((x, y))
        tree_list.append((x, y))

    sensors = []
    for _ in range(ns):
        sx, sy = map(int, input().split())
        sensors.append((sx, sy))

    solutions = set()

    for orient in range(4):
        # pre-transform all sensors for this orientation
        t_sensors = [transform(x, y, orient) for x, y in sensors]

        for tx, ty in tree_list:
            sx0, sy0 = t_sensors[0]
            ox = tx - sx0
            oy = ty - sy0

            ok = True
            for i in range(1, ns):
                x = ox + t_sensors[i][0]
                y = oy + t_sensors[i][1]
                if (x, y) not in trees:
                    ok = False
                    break

            if ok:
                solutions.add((ox, oy))

                if len(solutions) > 1:
                    print("Ambiguous")
                    return

    if len(solutions) == 0:
        print("Impossible")
    else:
        x, y = solutions.pop()
        print(x, y)

if __name__ == "__main__":
    solve()
```実装の中心的な選択は、ロボットのフレームが単純な変換問題に還元されるように、方向ごとにセンサー座標を事前に変換することです。 それが完了すると、各候補起点は減算を使用した単一のセンサー ツリー ペアから導出され、検証はハッシュ セット内の単純なメンバーシップ チェックになります。 

微妙な点は、検証中に 1 つのセンサー ポイントをアンカーとして固定することです。 これにより、すべてのセンサー ツリー ペアから候補原点を繰り返し再計算することが回避されます。 代わりに、すべてのツリーが最初のセンサー ポイントの潜在的な一致として機能し、すべての可能な変換を生成するには十分です。 

曖昧さは、すべての有効なロボット位置を保存することによってグローバルに追跡されます。 複数の異なるポジションが出現した時点で、早期に終了することができます。 

## 実用的な例

 2 本の木が単純な形状を形成し、センサーが北向きの向きで同じ形状を検出するという小さな概念的な例を考えてみましょう。 アルゴリズムは、最初のセンサー読み取り値と一致する可能性のあるものとして各ツリーを試し、そこから候補原点を導き出します。 

| ステップ | 方向 | アンカーペア | 原点（牛、牡） | 検証結果 |
 | --- | --- | --- | --- | --- |
 | 1 | 北 | (木 A、センサー 0) | 計算された | 部分チェック |
 | 2 | 北 | (木 B、センサー 0) | 計算された | 失敗する |
 | 3 | 北 | ... | ... | ... |

 正しいアンカーのペアのみが、すべてのセンサー チェックに合格する原点を生成します。 

次に、2 つの異なる方向が両方とも同じセンサー構成を説明する場合を考えてみましょう。 アルゴリズムは、解セット内で 2 つの異なる起点を見つけます。 

| 方向 | 原点が見つかりました | 有効なセンサー範囲 | 保存済み |
 | --- | --- | --- | --- |
 | 北 | (2, 3) | はい | はい |
 | 東 | (5, 1) | はい | はい |

 2 つの異なる解が存在するため、最終的な出力は「あいまい」になります。

 ## 特殊なケース

 複数の木の点が異なる方向で一致し、同一の原点候補が生成される場合には、注意が必要なケースが発生します。 すべての候補起源がローカルだけでなくグローバルに検証されるため、アルゴリズムはこれを処理します。 

もう 1 つのケースは、正しいアンカー ペアが存在するが、その変換下で他のセンサー ポイントが失敗する場合です。 これは検証中に即座に拒否され、部分的な幾何学的一致による誤検出を防ぎます。 

最後のエッジケースは、センサー ポイントが 1 つだけ存在する場合です。 この状況では、すべてのツリー ポイントが有効な原点候補を生成します。ソリューションでは、すべての候補原点が一致しない限り、曖昧さを正確に検出する必要があります。これは、ツリー ポイントが 1 つだけ存在する場合にのみ発生します。
