 ## 解決策
 ## 問題の理解

 私たちには次のようなシステムが与えられています$N$～のラベルが付いたフィギュア$0$に$N-1$。 以上$N$日に、各フィギュアは 1 回だけ棚に挿入され、その後 1 回だけ取り外されるため、各フィギュアは連続的なアクティブ間隔を定義します。$[l_j, r_j)$。 どの日でも$i$、棚にはその日の間隔をカバーするフィギュアが正確に含まれており、セットを形成しています$S(i)$。 

この進化するセットと並行して、いくつかの数値をシミュレートします。$x$から始まる$x_0 = 0$。 当日$i$、現在の値を見てみましょう$x_i$そして、現在棚にある少なくともラベルが付いているフィギュアの数を数えることによってそれを増やします$x_i$。 更新された値は次のようになります$x_{i+1}$、ただしモジュロを取ります$N$。 プロセスはすべてに対して実行されます$N$数日かけて出力します$x_N$。 

重要な問題は、しきい値が$x_i$時間の経過とともに変化し、以前のカウントに依存します。 これにより、同じ進化するセットに対して毎日異なるクエリが尋ねられるため、カウントが動的になります。「アクティブな要素が少なくともいくつあるか」$x_i$?」。 

制約$N \le 100{,}000$アクティブ セットを再計算したり、1 日ごとにスキャンしたりするソリューションは直ちに除外してください。 素朴なシミュレーションは次のようになります$O(N^2)$最悪の場合、毎日すべてのアクティブなフィギュアをスキャンする必要がある可能性があるためです。 

微妙な点は、アクティブ セットは 1 日ごとに任意ではなく、間隔の挿入と削除によって定義されることです。 各フィギュアは連続した範囲に表示されます。これは、時間の経過に伴う構造が、独立した更新ではなく間隔イベントによって完全に決定されることを意味します。 

見落としやすいエッジケースの 1 つは次のような場合です。$x_i$剰余を拡大してラップする$N$。 単純な実装では、カウントしきい値とのモジュロ相互作用を忘れてしまう可能性があります。 

たとえば、次のように仮定します。$N = 3$、そしてある日すべてのフィギュア$\{0,1,2\}$活動的であり、$x_i = 2$。 次に、答えは要素をカウントします$\ge 2$、これは 1 つの要素にすぎません。 しかし、アップデートがプッシュされると、$x_{i+1}$に$3$、それはラップされます$0$、次のクエリを劇的に変更します。 治療するあらゆるアプローチ$x$モノトーンは正しくありません。 

もう 1 つの微妙な問題は、同じフィギュアが連続的な間隔で寄与するため、状態が変化するのは次の場合だけであることです。$2N$恣意的にではなくエンドポイント。 これを無視すると、イベント駆動型の更新ではなく、1 日ごとに再計算が行われることになります。 

## アプローチ

 直接シミュレーションでは現在のセットが維持されます$S(i)$マルチセットやラベル上のフェンウィック ツリーなどのバランスの取れた構造で。 毎日、その日の出来事に応じてフィギュアを挿入したり削除したり、要素を数えることで質問に答えます$\ge x_i$。 これはもう$O(N \log N)$ただし、「カウント ≥ x」に効率的に答えることへの依存は依然として残ります。 

ラベルとフェンウィック ツリーの頻度配列を維持する場合、挿入と削除のポイント更新と、カウントのプレフィックス合計をサポートできます。 次に、各クエリは、アクティブな合計からプレフィックスの合計を引いたプレフィックスの合計クエリに帰着します。$x_i - 1$。 

ただし、これでは、完全に動的な構造を毎日クエリすると同時に、正確に処理する必要があるという依存関係が残ります。$N$順番に日々。 

重要な観察は、実際には任意のクエリ順序を処理する必要がないということです。日の順序は固定されており、構造は予測可能な方法で進化します。 これを次のように扱うのではなく、$N$独立した範囲カウント クエリを使用すると、アクティブな間隔を事前に計算し、イベントを順番に処理して、ラベル上のフェンウィック ツリーを維持できます。 

各フィギュアは、挿入と削除という 2 つのイベントに影響します。 日々、構造を適宜更新していきます。 したがって、毎日のクエリは 1 つの Fenwick プレフィックス クエリだけになります。 

これにより、問題は次の動的セットの維持に軽減されます。$O(\log N)$更新と問い合わせ。

 ## アルゴリズムのチュートリアル

 すべてのフィギュアをインターバルとして処理し、毎日シミュレーションします。 

1. フィギュアごとに入力を解析して再構築する$j$、挿入した日と抜かれた日。 これでペアが得られます$(l_j, r_j)$。 このステップでは、問題を「1 日あたりのログ」から集計が容易な間隔形式に変換します。 
2. 日ごとにインデックスが付けられたイベントのリストを 2 つ作成します。1 つは挿入用、もう 1 つは削除用です。 フィギュアごとに$j$、追加します$j$その日の挿入リストへ$l_j$、その日の削除リストへ$r_j$。 これにより、アクティブ セットを線形時間で段階的に更新できるようになります。 
3. インデックスに対してフェンウィック ツリーを維持する$0 \ldots N-1$、各インデックスには、フィギュアが現在アクティブかどうかが格納されます。 フィギュアがアクティブになると、$+1$そのインデックスで。 非アクティブになった場合は減算します$1$。 この構造により、ラベルの任意のプレフィックスにアクティブなフィギュアがいくつあるかを問い合わせることができます。 
4.初期化$x = 0$。 また、フェンウィック ツリーが常に正確に表現していることも主張します。$S(i)$、当日のアクティブ セット。 
5. 毎日について$i$から$0$に$N-1$、まず、この日に予定されているすべての削除を適用し、次にすべての挿入を適用します。 その日のセットのクエリを計算する前にその日の両方の操作が適用される限り、順序は基本的に重要ではありません。 
6. コンピューティング$y_i$ラベルが付いたアクティブなフィギュアの数として$\ge x$。 これは次のように得られます$\text{active\_count} - \text{prefix\_sum}(x-1)$。 
7.アップデート$x \leftarrow (x + y_i) \bmod N$。 これは値が変化する唯一の場所であり、現在のアクティブな分布と現在のしきい値にのみ依存します。 
8. 全日処理後、出力$x$。 

### なぜ効果があるのか

 いつでもフェンウィックの木はセットを正確に表します$S(i)$なぜなら、すべてのフィギュアは正確に 1 つの挿入と 1 つの削除に寄与しており、これらはその存続期間の境界で正確に適用されるからです。 したがって、すべてのクエリは正しいセットで評価されます。 の計算$y_i$フェンウィック ツリーはアクティブな要素を以下の要素に分割するため、これはまさに問題の更新ルールの定義です。$x_i$およびそれ以上または同等のもの。 モジュロ更新は今後のクエリにのみ影響し、正確性を遡って変更することはないため、シミュレーションは元のプロセスに忠実なままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        i += 1
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        if i < 0:
            return 0
        i += 1
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    n = int(input())
    insert = [[] for _ in range(n)]
    remove = [[] for _ in range(n)]

    for day in range(n):
        parts = input().strip().split()
        i = 0
        while i < len(parts):
            sign = parts[i][0]
            j = int(parts[i][1:])
            if sign == '+':
                insert[day].append(j)
            else:
                remove[day].append(j)
            i += 1

    for j in range(n):
        d = int(input())
        remove[d].append(j)

    fw = Fenwick(n)
    active = 0
    x = 0

    for day in range(n):
        for j in remove[day]:
            fw.add(j, -1)
            active -= 1
        for j in insert[day]:
            fw.add(j, +1)
            active += 1

        less = fw.sum(x - 1)
        y = active - less
        x = (x + y) % n

    print(x)

if __name__ == "__main__":
    solve()
```実装では、最初にすべての間隔エンドポイントが再構築されます。 重要な設計上の選択は、各イベントが 1 回だけ処理されるように、1 日ごとに挿入リストと削除リストを分離することです。 フェンウィック ツリーにはフィギュア インデックスごとにアクティブなインジケーターが保存され、高速なプレフィックス クエリが可能になります。 

微妙な実装の詳細が処理されます$x = 0$。 プレフィックス クエリで使用されるのは、$x - 1$となり、$-1$この場合、フェンウィック ツリーは安全にゼロを返します。 これにより、特殊なケースが回避されます。 

もう 1 つの重要な点は、明示的な情報を維持することです。`active`カウンタ。 フェンウィック ツリーから合計アクティブ数をクエリすることは可能ですが、別のカウンターを保持すると、1 日あたりの余分な対数演算が回避されます。

 ## 特殊なケース

 エッジケースの 1 つは、すべてのフィギュアが数日前に削除された場合です。 アクティブセットは空になるので、$y_i = 0$、 そして$x$は変わらないままです。 この場合、すべてのポジションが非アクティブであるため、フェンウィック ツリーは当然 0 を返します。 

もう一つのケースは次のような場合です。$x$蓄積により大きくなりゼロにラップします。 プレフィックス クエリ ロジックはこれを適切に処理します。$x-1$は負になりゼロになります。これは、すべてのアクティブな要素がカウントされることを意味します。 

最後の微妙なケースは、同じ日に複数の挿入と削除が発生する場合です。 アルゴリズムはこれらを 1 日あたり一括で処理し、フェンウィック ツリーは 1 日あたりの最終状態のみを考慮するため、クエリの前にすべての更新が適用される限り、その日の順序は正確さに影響しません。
