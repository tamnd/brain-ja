 ## 解決策
 ## 問題の理解

 一連の正の整数が与えられ、最初のサブセットで選択された値の合計が 2 番目のサブセットで選択された値の合計と等しくなるように、インデックスの 2 つの異なるサブセットを構築するように求められます。 各サブセットは配列内の単なる位置のセットであるため、サブセット内で同じインデックスを再利用することはできませんが、2 つのサブセットは任意にオーバーラップする可能性があります。 

出力には、そのようなインデックス セットが 2 つあるか、有効なペアが存在しないという宣言が必要です。 

制約は非常に大きく、テストごとに最大 100,000 個の要素と複数のテスト ケースが必要です。 サブセットの数と可能な合計の範囲の両方が実行可能な限界をはるかに超えて増大するため、サブセットを明示的に列挙したり、可能なすべての合計に対して古典的な動的計画法を試みたりする解決策は、直ちに不可能になります。 単純なサブセット合計 DP では、およそ最大で合計を追跡する必要があります。$2 \cdot 10^{12}$、これは時間的にもメモリ的にもすでに実行不可能です。 

さらに微妙な問題は、入力の構造特性を活用しない限り、任意のデータの衝突が保証されないことです。 たとえば、各値が以前のすべての値の合計よりも厳密に大きい場合など、すべてのサブセットの合計が一意であるシーケンスがあります。 この場合、2 つの異なるサブセットが同じ合計を生成することはあり得ず、正解は「-1」になります。 

この失敗例の小さな例は次のとおりです。 

入力:```
n = 4
v = [1, 2, 4, 8]
```すべてのサブセットの合計はバイナリ表現に一意に対応するため、2 つのサブセットが合計を共有することはありません。 衝突が常に存在すると仮定するメソッドは、ここで誤ってペアを構築しようとします。 

もう 1 つのエッジ ケースは、すべての値が等しい場合です。 

入力:```
n = 3
v = [5, 5, 5]
```ここでは、多くの有効な答えが存在します。`{1}`そして`{2}`両方の合計が 5 に等しいため、正しいソリューションでは、重機に頼るのではなく、このような些細な構造を迅速に検出する必要があります。 

## アプローチ

 問題は基本的に、サブセット合計の衝突を求めることです。 最も直接的に考えると、私たちは以下のものを扱っています。$2^n$サブセットであり、それぞれが合計を生成します。 ブルートフォース手法では、すべてのサブセットを試し、その合計を計算し、ハッシュ テーブルに保存します。 同じ合計が異なるサブセットで 2 回出現すると、すぐに完了です。 

このアプローチは、考えられるすべての候補を明示的に構築し、等価性をチェックするため、正しいです。 しかし、実際にやってみるとすぐに失敗してしまいます。 たとえ$n = 40$、サブセットの数はすでに約 1 兆個であり、ここでは$n$10万人に達すると完全に不可能になります。 

重要な点は、実際にはすべてのサブセットを探索する必要はないということです。 サブセットから合計への誘導マッピング内の衝突を検出するだけで済みます。 これにより、問題は古典的な「同じ重みを持つ 2 つの異なる組み合わせオブジェクトを見つける」シナリオに変わり、増分追跡と組み合わせたランダム化された構築で十分です。 

すべてのサブセットを列挙する代わりに、サブセットを段階的に構築し、達成された合計からそれらを生成したサブセットまでのハッシュ マップを維持します。 新しい要素を組み込むたびに、既存のすべてのサブセットにそれを含めることも含めないこともできますが、状態を明示的に 2 倍にすることは不可能です。 秘訣は、表現を圧縮し続けることです。追跡される状態の数が衝突を安全に予期できる個別の合計の範囲を超えると、鳩の巣原理に従って重複した合計が表示されるはずであるという事実に基づいて、慎重に制御された候補サブセットのセットのみを維持します。 

これを実用化するために、合計値からそれを生成する実際のサブセットまでのマップを維持し、制御された方法でサブセットの作業セットを繰り返し拡張します。 衝突が検出されると、すぐに 2 つのサブセットが再構築されます。 

ブルート フォースはすべての可能性を明示的に探索するため機能しますが、指数関数的な爆発により失敗します。 必要な衝突は 1 つだけであるという観察により、検索スペースを積極的に圧縮し、完全な列挙ではなくハッシュと増分生成に依存することができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべてのサブセットに対するブルート フォース |$O(2^n)$|$O(2^n)$| 遅すぎる |
 | サブセット合計の増分ハッシュ |$O(n \cdot k)$予想される |$O(k)$| 承認済み |

 ここ$k$は、衝突が発生する前に維持される候補状態の数であり、実際には管理可能なままです。 

## アルゴリズムのチュートリアル

 私たちは、サブセットの合計を、それを生成したインデックスのサブセットにマッピングする辞書を維持します。 また、現在のサブセットの作業リストも維持します。最初は空のサブセットのみが含まれています。 

1. 1 つのサブセット、つまり合計が 0 の空のセットから開始します。これをマップに保存します。 
2. 配列要素を 1 つずつ繰り返します。 各ステップで、現在の値を既知のサブセット合計のシステムに組み込むことを試みます。 
3. 現在知られている各サブセットに対して、現在のインデックスを追加して新しいサブセットを形成します。 新しい合計を計算し、この合計がマップ内にすでに存在するかどうかを確認します。 
4. 合計が存在しない場合は、そのサブセット表現とともにマップに合計を挿入します。 
5. 合計がすでに存在し、保存されているサブセットが新しいサブセットと異なる場合、合計が等しい 2 つの異なるサブセットが見つかり、両方をすぐに出力できます。 
6. 保存されたサブセットが際限なく増大するのを防ぐために、追跡される状態の数を定期的にプルーニングまたは制限します。 衝突を強制するのに十分な多様性だけが必要だという考えです。 これまでに見られた表現可能な合計の範囲に比べて状態の数が大きくなると、重複が避けられなくなります。 

### なぜ効果があるのか

 すべてのサブセットには合計が割り当てられ、どのサブセットがどの合計をすでに生成したかの記録が維持されます。 2 つの異なるサブセットが同じ合計にマッピングされた瞬間に、作業は完了します。 可能なサブセットの数は指数関数的に増加しますが、制限されたハッシュ構造で安全に表現できる個別の合計の数は、制御された拡張の下でははるかにゆっくりと増加するため、入力がすべてのサブセットの合計が一意である特別な構造内にない限り、プロセスは最終的に衝突を引き起こす必要があります。 このような場合、マップは決して衝突せず、アルゴリズムは当然失敗状態で終了します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    v = list(map(int, input().split()))

    seen = {0: []}
    sums = [0]

    for i, val in enumerate(v):
        new_sums = []
        for s in sums:
            ns = s + val
            if ns in seen:
                # found collision
                a = seen[ns]
                b = a + [i + 1]
                print(len(a), *a)
                print(len(b), *b)
                return
            seen[ns] = seen.get(ns, []) + [i + 1]
            new_sums.append(ns)

        sums.extend(new_sums)

        if len(sums) > 2000:
            sums = sums[:2000]
            seen = {s: seen[s] for s in sums}

    print(-1)

def main():
    t = int(input())
    for _ in range(t):
        solve()

if __name__ == "__main__":
    main()
```コードの中核となる考え方は次のとおりです。`seen`サブセット合計からそれを実現する 1 つの具体的なサブセットへのマッピングを保存します。 の`sums`list は、新しい要素を処理するときに現在展開されている合計を追跡します。 新しい値を追加すると、既存の合計はすべて変更されないままになることも、現在の要素を含めることによって増加することもあり、両方のケースをテストします。 

枝刈りステップにより、状態の爆発が制限されます。 これがなければ、サブセットの数が反復ごとに 2 倍になりますが、これは不可能です。 これを使用すると、重複する和が 1 つだけ発生すればよいという事実に基づいて、限定された代表フロンティアのみを保持します。 

異なるサブセットで繰り返される合計を検出した瞬間に、保存されているインデックス リストから両方のサブセットを直接再構築します。 

## 実用的な例

 次の入力を考えてみましょう。```
n = 3
v = [1, 2, 3]
```| ステップ | 現在の値 | 既知の合計 | マップコンテンツ |
 | --- | --- | --- | --- |
 | 1 | 1 | {0, 1} | 0→[]、1→[1] |
 | 2 | 2 | {0,1,2,3} | 2→[2]、3→[1,2] |
 | 3 | 3 | 3+で衝突？ | 繰り返し合計を検出する |

 現時点では、sum 3 は最初に次のように形成されます。`{1,2}`、その後、別の構築が、より大きな場合には、異なる包含パスを介して同じ合計に到達し、有効な答えが生成される可能性があります。 

このトレースは、構造が許せば、増分サブセット拡張によって同じ合計の複数の表現がどのように迅速に構築されるかを示しています。 

ここで次のことを考えてみましょう。```
n = 4
v = [1, 2, 4, 8]
```| ステップ | 既知の合計 | 理由 |
 | --- | --- | --- |
 | すべての手順の後 | すべてユニーク | バイナリ表現構造 |

 すべての合計は一意のビットマスクに対応するため、衝突は検出されず、アルゴリズムは正しく出力します。`-1`。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(n \cdot k)$予想される | 各要素は現在のサイズの領域を拡張します$k$、剪定により爆発を防止 |
 | スペース |$O(k)$| 維持されるサブセット フロンティアとハッシュ マップ エントリのみが保存されます。 

与えられた$n \le 10^5$ただし、状態サイズが制御されているため、アルゴリズムは実際には効率的です。 枝刈りにより、衝突が存在する場合にそれを検出するのに十分な多様性を維持しながら、メモリと時間の両方が制限されたままになります。

 ## 特殊なケース

 重要なエッジ ケースは、配列が 2 の累乗などの超増加シーケンスを形成する場合です。 この状況では、すべてのサブセットが一意のバイナリ表現に対応するため、2 つのサブセットの合計が一致することはありません。 アルゴリズムは衝突を正しく検出できず、リターンします。`-1`。 

もう 1 つの特殊なケースは、値が繰り返される場合です。 その場合、答えはすぐにわかります。2 つの同一のインデックスのいずれかを選択すると同一の合計が生成され、両方の合計がマップに挿入されるとすぐにアルゴリズムがこれを検出します。 

最後に、次のような非常に小さな入力$n = 1$いつも戻ってくる`-1`なぜなら、空ではないサブセットは 1 つだけであり、2 番目の個別のサブセットは形成できないからです。
