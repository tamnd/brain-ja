 ## 解決策
 ## 問題の理解

 2 つの CPU を使用して順番に実行する必要がある一連のプログラムが与えられています。 各プログラムには 2 つの実行時間があります。1 つは CPU が最後に別のプログラムを実行した場合に適用されるコールド タイム、もう 1 つは CPU が最後に同じプログラムを実行した場合に適用されるホット タイムです。 プログラムが順番に実行されるという要件を尊重し、合計の経過時間を最小限に抑えるために 2 つの CPU にわたってプログラムをスケジュールしたいと考えています。つまり、前のプログラムが終了するまでプログラムを開始することはできません。 

入力は複数のテスト ケースを提供します。 各テスト ケースは、プログラムのシーケンス、各プログラムのコールド時間とホット時間、およびプログラムの数で構成されます。 出力は、各テスト ケースの最小合計時間です。 

制約が厳しい:$n$そして$k$到達できる$3 \cdot 10^5$、すべてのテスト ケースの合計はこの境界を超えません。 と$t$と同じくらい大きい$10^5$、テスト ケースあたりの時間が線形より悪いソリューションは遅すぎます。 具体的には、$O(n^2)$ソリューションは最大でパフォーマンスを発揮します$10^{10}$最悪の場合の操作ですが、これは明らかに実行不可能です。 私たちのアプローチは次のようなものでなければなりません$O(n)$テストケースごと、または$O(\sum n)$全体。 

エッジケースは明らかではありません。 たとえば、1 つのプログラムが頻繁に繰り返されるシーケンスでは、CPU ごとの慎重なホット/コールド追跡が必要です。 最後のプログラムの履歴を考慮せずに、常に最初に使用可能な CPU に次のプログラムを割り当てる単純なアプローチでは、コールド時間をカウントしすぎる可能性があります。 たとえば、入力シーケンスの場合、`[1, 1, 1]`と`cold = [10]`そして`hot = [1]`、最小時間は`10 + 1 + 1 = 12`。 2 番目のプログラムを他の CPU に誤って割り当てると、次のような結果が得られます。`10 + 10 + 1 = 21`。 

もう 1 つの注意が必要なシナリオは、シーケンスが 2 つのプログラム間で切り替わる場合です。 各プログラムを実行する CPU の選択は、ホット タイムが適用されるかどうかに影響し、CPU ごとに最後に使用されたプログラムを処理する際の小さな間違いが、最適ではないスケジュールにつながる可能性があります。 

## アプローチ

 ブルート フォース ソリューションでは、順序を尊重して CPU へのプログラムの割り当てをすべて試行します。 各プログラムについて、CPU1 または CPU2 で実行することを決定し、ホット/コールド ルールに基づいて時間を計算し、再帰することができます。 これは原理的には正しいですが、割り当ての数は$2^n$、これは天文学的に大きい$n \sim 10^5$。 CPU ごとの最終プログラム状態のメモ化でも結果は得られるだけです$O(n \cdot k^2)$ですが、それでも最大の制約に対して遅すぎます。 

重要な観察は、どの時点においても、決定は各 CPU で実行された最後のプログラムにのみ依存するということです。 完全な履歴は必要ありません。 2 つの状態を維持できます。CPU1 で実行された最後のプログラムが次の場合の最小合計時間です。`x`そしてCPU2では`y`。 シーケンスを繰り返す際に、プログラムごとに、その CPU 上でホットとして実行されるかコールドとして実行されるかを検討し、それに応じて合計時間を更新することによって、どの CPU で実行するかを決定します。 これにより、問題は、シーケンスの各要素を順番に処理するときに 2 つの「最後のプログラム」状態を更新する動的プログラミング アプローチに帰着します。 

この観察により、線形時間の解決策が可能になります。 シーケンス内の各プログラムについて、CPU1 または CPU2 に配置するという 2 つのオプションをチェックするだけで済みます。 高温/低温の状態に基づいて増分コストを計算し、それに応じて合計時間を更新します。 正確性を保証するには、CPU ごとに実行された最後のプログラムのみを追跡するだけで十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n) | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 2 つの変数を初期化する`last1`そして`last2`に`-1`CPU1 と CPU2 で実行された最後のプログラムを表します。 初期化もする`time1`そして`time2`最後のプログラムがそれぞれ CPU1 または CPU2 上にあった場合に、現在のポイントに到達するまでの累積時間を表します。 
2. 各プログラムを反復処理する`p`シーケンスで。 各プログラムについて、CPU1 または CPU2 に配置した場合の新しい時間を計算します。 費用は`hot[p]`CPUが最後に実行された場合`p`、 さもないと`cold[p]`。 
3. CPU1 の場合、新しい累積時間は次の最小値になります。`time1 + cost_on_CPU1`そして`time2 + cost_on_CPU1`, CPUを切り替えることができるので。 CPU2についても同様に更新します。 ここ、`time1 + cost_on_CPU1`前の CPU1 プログラムの後に CPU1 で実行することに対応します。`time2 + cost_on_CPU1`CPU2 プログラムの後に CPU1 で実行することに対応します。 
4. 2 つの新しい時間を計算した後、更新します`last1`そして`last2`必要に応じて現在のプログラムに割り当て、新しい累積時間を再び割り当てます。`time1`そして`time2`。 
5. シーケンス全体を処理した後の最小合計時間は次のとおりです。`min(time1, time2)`。 これは、いずれかの CPU で最後のプログラムを最小限の経過時間で終了することを表します。 

機能する理由: アルゴリズムは、次の不変条件を維持します。`time1`そして`time2`最後に実行されたプログラムを考慮して、各 CPU の現在のプログラムまでの最小合計時間を常に保存します。 CPU ごとの最後のプログラム履歴のみを考慮し、段階的に更新することで、完全な再帰を行わずにすべての実行可能なスケジュールを探索し、最適性を確保します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        cold = list(map(int, input().split()))
        hot = list(map(int, input().split()))

        last1 = last2 = -1
        time1 = time2 = 0

        for p in a:
            p -= 1  # convert to 0-based indexing
            cost1 = hot[p] if last1 == p else cold[p]
            cost2 = hot[p] if last2 == p else cold[p]

            new_time1 = min(time1 + cost1, time2 + cost1)
            new_time2 = min(time1 + cost2, time2 + cost2)

            last1 = last2 = p
            time1, time2 = new_time1, new_time2

        print(min(time1, time2))

solve()
```配列アクセスのためにプログラムを 0 から始まるインデックスに変換します。 各プログラムについて、最終プログラム履歴を使用して両方の CPU オプションの増分コストを計算します。 最小更新により、CPU の切り替えが確実に考慮されます。 設定`last1`そして`last2`各反復で現在のプログラムに追加することで、次のステップのコスト計算が簡素化され、オフバイワンの間違いが回避されます。
