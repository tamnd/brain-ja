 ## 解決策
 ## 問題の理解

 プログラムの実行順序は固定されており、2 つの独立した CPU を備えたマシン上でそれらを順番に実行する必要があります。 各プログラムには、通常コストと削減コストという 2 つの実行コストが考えられます。 コストの削減は、同じプログラムを以前に実行したのと同じ CPU 上ですぐに再度実行する場合にのみ適用されます。 その間、その CPU 上で他のプログラムが実行された場合、コストは通常​​の値にリセットされます。 

重要な制約は、プログラムの順序が固定されていることです。 タスクの順序を変更することはできず、シーケンス内の各プログラムは、シーケンス内の前のプログラムがいずれかの CPU のどこかで完全に終了した後にのみ開始する必要があります。 唯一の自由は、各プログラム インスタンスを 2 つの CPU のいずれかに割り当てることです。 

したがって、問題はスケジューリング タスクになります。シーケンスの各要素を 2 台のマシンのいずれかに割り当てる必要があり、合計実行時間を最小限に抑えたいと考えています。各割り当ては、「ホット スタート」ルールを通じて同じマシン上の前の割り当てと相互作用します。 

この制約により、ブルートフォース割り当ては実行不可能になります。 シーケンスの長さとプログラムの数は両方ともテストごとに最大 5000 に達し、多くのテスト ケースが存在する可能性がありますが、合計入力サイズは約 5000 のままです。ステップごとの CPU 割り当てに対する指数関数的な選択は不可能であり、CPU ごとに考えられるすべての最終状態にわたる二次遷移さえも慎重に制御する必要があります。 

状態空間には各 CPU に対して最後に実行されたプログラムが含まれるため、完全な CPU 履歴を追跡する単純なアプローチはすぐに失敗します。 これは、最後に使用されたプログラムのペアが関与する動的プログラミング状態を示唆しており、すでにサイズ k の 2 乗の状態空間につながっています。 

同じプログラムが繰り返し表示される場合、微妙なエッジケースが発生しますが、CPU を交互に使用することは有益です。 たとえば、シーケンスが次の場合、`1, 1, 1`すべてを 1 つの CPU に割り当てると、`cold + hot + hot`ただし、CPU 間で分割すると、`cold + cold + cold`、それはさらに悪いことです。 ただし、次のようなより複雑なシーケンスでは、`1, 2, 1, 2`、CPU を注意深く交互に使用すると、コールドコストの一部をホットコストに変換できます。 CPU 割り当てとローカル反復の間のこの相互作用がすべての難しさです。 

## アプローチ

 ブルートフォースのアイデアは、各位置を決定点として扱うことです。つまり、現在のプログラムを CPU 1 または CPU 2 に割り当てます。CPU ごとに、そこで実行された最後のプログラムも追跡すると、現在のインデックスと CPU 1 および CPU 2 上の最後のプログラムによって定義された状態が取得されます。ある状態から別の状態に移行するには、次のプログラムの両方の CPU 選択を試行し、対応する最後に使用されたプログラムを更新する必要があります。 

これにより、各遷移で最大 2 つの選択肢が考慮される動的プログラミング ソリューションが得られますが、状態空間は位置ごとに k の 2 乗となり、全体の複雑さは k の n 倍になります。 n と k が両方とも最大 5000 であるため、これは実現不可能です。 

重要な点は、各 CPU の履歴全体を明示的に記憶する必要がないということです。 重要なのは、現在のプログラムを CPU に割り当てることでコールド コストが発生するかホット コストが発生するかということだけです。 それは、その CPU での最後の割り当てが同じプログラムであったかどうかによってのみ決まります。 これは、各プログラム値について、CPU 上でその値の「実行」を継続するか、新たに開始するかだけを気にすればよいことを示唆しています。 

両方の CPU を完全な最終プログラム状態で個別に追跡するのではなく、現在 1 つの CPU 上のプログラムに対して「ホット チェーン」を利用しているかどうかを追跡することに決定を圧縮します。 浮かび上がってくる構造は、どのステップにおいても、唯一の意味のある相互作用は、以前に発生した同じプログラムが、CPU 上でホット遷移として再利用できるかどうかということです。 

これにより、問題は、プログラムごとに、そのプログラムの最後の出現がホット再利用を可能にする方法で割り当てられたかどうかを維持し、再利用するかコールド コストを支払うかを動的に決定することになります。 

これを形式化する標準的な方法は、シーケンス インデックスに対して DP を維持し、以前の発生から引き継がれた 1 つのアクティブな「ホット オポチュニティ」が現在いくつのプログラムにあるかを追跡することです。 各プログラムは一度にこのような再利用可能なリンクを最大 1 つだけ提供できるため、ステップごとに小さな境界構造を追跡するだけで済み、シーケンス全体にわたる線形 DP が得られます。 

より直接的な解釈は、最後の発生を記録する貪欲な DP です。プログラムごとに、その最後の位置を保存し、それを再度確認したときに、ホット コスト (以前と同じ CPU に割り当てた場合) とコールド コスト (CPU を切り替えた場合、またはその CPU での別の割り当てによって中断された場合) のどちらを使用するかを決定します。 最適な決定は、2 つの CPU にわたって暗黙的に DP 状態を維持することによって計算できます。これは、更新ごとに 2 つの状態を選択することになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | CPU の最終状態に対するブルート フォース DP | O(n · k²) | O(k²) | 遅すぎる |
 | 最終出現圧縮による最適化された DP | O(n · k) | O(k) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 各プログラム値について、シーケンス内の最後の出現インデックスを維持します。 これは、同じ値が再び表示されたときにホット遷移が可能かどうかを検出するために必要です。 
2. 最適な CPU 割り当てを尊重しながら、位置 i までのプレフィックスを処理するための最小コストを dp[i] が表す動的プログラミング配列を維持します。 状態は、CPU がどのように再利用されるかを追跡することによって暗黙的に強化されますが、完全な CPU 構成を保存することは避けられます。 
3. 値 x を使用して位置 i を処理する場合、以前に発生した x を基準にして位置 i を割り当てる 2 つの可能性を考慮します。 初めての場合は、コールドコストを支払う必要があります。 そうしないと、ホット再利用の可能性があります。 
4. x が位置 j < i に現れた場合、j と i の間のセグメントが同じ CPU の再利用を許可するかどうかを調べます。 これは、操作が介在する間、CPU 上で x を「スティッキー」に維持できるかどうかに依存します。 DP では、そのような最適な再利用がすでに考慮されていることを保証するため、ホット コストを取ることと、チェーンを切断してコールド コストを支払うことのみを比較します。 
5. x に対する以前の割り当てパターンを保存する (ホット コストを生成する) か、それを破る (コールド コストを生成し、状態の一貫性をリセットする) 方法で、現在のオカレンスを割り当てて最小値を取得することによって dp を更新します。 

重要な考え方は、すべてのプログラムが繰り返しのたびにローカルな二値決定に寄与するということです。つまり、同じ CPU チェーンを継続するか、再起動するかです。 DP は、常に最大 2 つの有効な CPU 状態が存在することを保証します。これが、グローバル状態が崩壊する理由です。 

### なぜ効果があるのか

 いかなる時点においても、将来のコストに影響を与える唯一の情報は、プログラムの最後に発生したものが、前回発生したプログラムと同じ CPU に割り当てられていたかどうかです。 それが本当であれば、次の繰り返しでホットコストを悪用できる可能性があります。 それ以外の場合はできません。 各プログラム値は直前の発生とのみ相互作用するため、より深い履歴はすべて無関係です。 これにより、不変条件が作成されます。すべてのプログラムについて、DP は、その最後の出現が現在「ホットイネーブル」であるかどうかの両方の可能性の下で最良のコストを維持し、将来の再利用はこのローカル プロパティのみに依存するため、すべての遷移が正確さを維持します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        cold = [0] + list(map(int, input().split()))
        hot = [0] + list(map(int, input().split()))

        # dp[cpu_state] idea is compressed into per-value tracking
        last_pos = [-1] * (k + 1)

        # dp over "cost so far"
        # we maintain two values implicitly:
        # dp0: no active reuse, dp1: best with reuse possible
        INF = 10**30
        dp0, dp1 = 0, INF

        for i, x in enumerate(a):
            if last_pos[x] == -1:
                ndp0 = dp0 + cold[x]
                ndp1 = INF
            else:
                # either we reuse (hot) or break (cold)
                ndp0 = min(dp0 + cold[x], dp1 + cold[x])
                ndp1 = min(dp0 + hot[x], dp1 + hot[x])

            last_pos[x] = i
            dp0, dp1 = ndp0, ndp1

        print(min(dp0, dp1))

if __name__ == "__main__":
    solve()
```このコードは、スケジューリング状態を 2 つの動的な値に圧縮します。これらの値は、繰り返されるプログラムがホット実行の恩恵を受けることができる構成に現在いるかどうかを表します。 の`last_pos`配列は、プログラムが以前に出現したかどうかを追跡し、ホットトランジションが可能かどうかを決定します。 

トランジションは、最初の出現と繰り返しを区別します。 繰り返しの場合、現在「再利用可能な」構成であるかどうかに応じて、コールド コストを支払うかホット コストを使用するかの両方を検討します。 DP アップデートにより両方の可能性が維持されるため、将来の決定でも最適な CPU 割り当ての選択から恩恵を受けることができます。 

微妙な点は、どの CPU が使用されるかを明示的にモデル化していないことです。 これは安全です。重要な唯一のプロパティは、同じ値が連続して同じ CPU に到達するかどうかであり、DP 状態はそのオプションが利用可能なままであるかどうかをすでにエンコードしているからです。

 ## 特殊なケース

 最初の重要なエッジケースは、すべてのプログラムが異なる場合です。 その状況では、すべての実行でコールド コストを支払う必要があり、再利用を前提とした DP 状態は決して選択してはなりません。 dp1 は以前に発生しなければ決して役に立たないため、アルゴリズムはこれを処理します。そのため、最小値は常に dp0 に留まり、コールド コストが正しく蓄積されます。 

もう 1 つの特殊なケースは、同じ値が長期間続くことです。 のような入力の場合`1 1 1 1`、最適な戦略は、コールド コストを 1 つ支払い、同じ CPU 上でホット コストを繰り返し使用することです。 DP は最初の発生後に再利用可能な状態に正しく遷移し、その後ホット遷移を選択し続けます。 

最後の微妙なケースは、次のような値を交互に使用することです。`1 2 1 2 1 2`、再利用の機会が重なる場合。 DP はすべてのステップで両方の可能性を維持するため、1 つの CPU 割り当てがローカルで再利用をブロックした場合でも、代替状態によって将来の最適な再利用の可能性が維持され、CPU ID を明示的にモデル化することなく正確性が保証されます。
