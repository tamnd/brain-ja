 ## 解決策
 ## 問題の理解

 曲を表す小文字の文字列と、その文字列の連続する部分文字列に対する多くのクエリが与えられます。 

各文字は、アルファベット内のその位置に等しい値を与えます。 例えば、`a = 1`、`b = 2`、`c = 3`、 等々。 お問い合わせの場合`[l, r]`、位置から部分文字列を調べます`l`位置を決める`r`。 すべての文字はそのアルファベット値と同じ回数繰り返され、結果として展開された文字列の長さが必要になります。 

展開された文字列を実際に構築する代わりに、各文字が最終的な長さにどれだけ寄与するかを考えることができます。 キャラクターが`c`、貢献します`3`。 キャラクターが`z`、貢献します`26`。 部分文字列の答えは、その範囲内のすべての文字にわたるこれらの値の単純な合計です。 

制約は問題の重要な部分です。 文字列の長さとクエリの数は両方とも次の範囲に達する可能性があります。`100000`。 すべてのクエリの部分文字列全体をスキャンするソリューションには、最大で`100000 × 100000 = 10^10`最悪の場合、2 秒以内に実行できる処理をはるかに超えます。 いくつかの前処理を行った後、各クエリに定数時間または対数時間で答える方法が必要です。 

簡単な間違いの 1 つは、タスクを個別の文字を数えるものと解釈することです。 考慮する：```
s = "aaa"
query = [1, 3]
```それぞれ`a`貢献する`1`、したがって、答えは次のようになります。```
1 + 1 + 1 = 3
```正しい出力は次のとおりです`3`、 ない`1`。 

もう 1 つのよくある間違いは、入力で 1 から始まる位置を使用しているにもかかわらず、0 から始まるクエリ インデックスを使用することです。 

例：```
s = "ab"
query = [1, 1]
```部分文字列は`"a"`、したがって、答えは次のとおりです`1`。 

誤ってクエリをゼロベースとして扱ってしまうと、間違った文字にアクセスし、間違った結果が生成されてしまいます。 

3 番目の微妙なケースは、クエリが文字列全体をカバーする場合に発生します。```
s = "zzz"
query = [1, 3]
```答えは次のとおりです。```
26 + 26 + 26 = 78
```プレフィックス合計の境界でオフバイ 1 エラーが発生すると、そのような範囲では直ちに誤った結果が生成されます。 

## アプローチ

 最も直接的な解決策は、すべてのクエリを個別に処理することです。 お問い合わせの場合`[l, r]`、その部分文字列内のすべての文字を反復処理し、各文字をアルファベットの位置に変換し、値を合計し、結果を出力します。 

必要な答えがまさにその合計であるため、このアプローチは正しいです。 問題は効率です。 部分文字列には最大で次のものを含めることができます`100000`文字があり、`100000`クエリ。 最悪の場合、約`10^10`キャラクターの訪問が遅すぎます。 

問題の構造は、より良いアプローチを示唆しています。 すべてのクエリは、同じ配列の連続したセグメントにわたる値の合計を要求します。 各文字をそのアルファベット値に変換すると、タスクは古典的な範囲合計クエリの問題になります。 

静的配列に対する範囲合計クエリの場合、プレフィックス合計が標準ツールです。 もし`pref[i]`最初の合計値を格納します`i`文字、任意の間隔での合計`[l, r]`2 つのプレフィックスの合計を減算することで取得できます。```
pref[r] - pref[l - 1]
```前処理には線形時間がかかり、すべてのクエリは定数時間の計算になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | 最適 | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.読む`n`、`q`、および文字列`s`。 
2. プレフィックス合計配列を作成する`pref`長さの`n + 1`、 と`pref[0] = 0`。 
3. 文字列を左から右にトラバースします。 
4. 各文字について、次を使用してアルファベットの位置を計算します。```
ord(character) - ord('a') + 1
```5. 累積合計をプレフィックス配列に格納します。`pref[i]`最初の合計値が含まれている必要があります`i`文字。 
6. あらゆるクエリに対して`[l, r]`、次を計算します。```
answer = pref[r] - pref[l - 1]
```7. 答えを出力します。 

### なぜ効果があるのか

 プレフィックス配列は、次の不変式を維持します。`pref[i]`位置の文字値の合計に等しい`1`を通して`i`。 

計算するとき`pref[r] - pref[l - 1]`、ポジションの貢献`1`を通して`l - 1`は両方の項に現れて相殺されます。 残るのは正確に位置からの値の合計です`l`スルーポジション`r`、これは展開された文字列の必要な長さです。 すべての文字が最終的な長さに独立して寄与するため、この合計がまさに答えになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    s = input().strip()

    pref = [0] * (n + 1)

    for i in range(1, n + 1):
        pref[i] = pref[i - 1] + (ord(s[i - 1]) - ord('a') + 1)

    ans = []

    for _ in range(q):
        l, r = map(int, input().split())
        ans.append(str(pref[r] - pref[l - 1]))

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    solve()
```最初の部分は入力を読み取り、文字列をアルファベット値の累積合計に変換します。 表現`ord(s[i - 1]) - ord('a') + 1`地図`a`に`1`、`b`に`2`、 等々。 

プレフィックス配列では、1 から始まるインデックスが使用されます。 この選択はクエリ形式と一致し、範囲式が単純になります。 の値`pref[0]`ゼロの場合、位置から始まるクエリが許可されます。`1`特別な場合を除いて処理されます。 

各クエリについて、答えは 1 回の減算で得られます。 部分文字列の文字は再度スキャンされません。 

よくある実装上の間違いは、文字列インデックスとプレフィックス インデックスを混合することです。 文字列自体はゼロベースなので、文字`i`プレフィックス構造では次のようになります`s[i - 1]`。

 ## 特殊なケース

 可能な最小の入力を考えてみましょう。```
1 1
a
1 1
```プレフィックス配列は次のようになります。```
pref = [0, 1]
```答えは次のとおりです。```
pref[1] - pref[0] = 1
```アルゴリズムは、position で始まる範囲を正しく処理します。`1`なぜなら`pref[0]`存在します。 

ここで、文字列全体をカバーする範囲を考えてみましょう。```
3 1
zzz
1 3
```プレフィックス配列は次のとおりです。```
pref = [0, 26, 52, 78]
```クエリの結果は次のとおりです。```
78 - 0 = 78
```全範囲クエリには特別な処理は必要ありません。 

最後に、最後の文字で終わり、最初の文字では始まらないクエリを考えてみましょう。```
5 1
abcde
3 5
```プレフィックスの合計は次のとおりです。```
[0, 1, 3, 6, 10, 15]
```答えは次のようになります。```
15 - 3 = 12
```等しい`3 + 4 + 5`。 これにより、減算することが確認されます。`pref[l - 1]`不要なプレフィックスを正確に削除し、要求された部分文字列のみを残します。
