 ## 解決策
 ## 問題の理解

 一連の短い文字列が与えられ、それぞれが 6 桁のチケット番号を表します。 各チケットは同じ長さの 2 つの半分に分割する必要があります。 タスクは、左半分の桁の合計が右半分の桁の合計と一致するかどうかを判断することです。 

各テスト ケースは独立しているため、計算はチケット文字列ごとにリセットされます。 出力は、チケットごとに、このバランス条件を満たすかどうかという単純な二項判定です。 

入力形式は非常に小さいですが、注意すべき主な点は、数字が文字として与えられることです。 これらを整数として扱うには明示的な変換が必要です。そうしないと、比較や算術が暗黙のうちに正しく動作しなくなります。 

制約は十分に厳しいので、合理的な解釈で十分です。 チケットが最大 1000 個で、チケットあたりの文字数がわずか 6 文字であれば、テスト ケースごとに冗長な作業を行うソリューションであっても、制限内で快適に実行できます。 これにより、問題は実装のカテゴリにしっかりと押し込まれ、アルゴリズムの最適化ではなく、慎重なインデックス作成と変換によって正確さがもたらされます。 

ここで最も一般的なエッジケースは、文字列に先行ゼロが含まれる可能性があることを忘れていることです。 みたいなチケット`"045207"`先頭のゼロを除いた数値としてではなく、正確に 6 桁として扱う必要があります。 もう 1 つの微妙な間違いは、数値の代わりに ASCII 値を誤って合計してしまうことです。これは、引き算を忘れた場合に発生します。`'0'`。 

## アプローチ

 この問題を考える強引な方法は、文字列を明示的に 2 つの部分に分割し、それぞれの辺の合計を計算することです。 各チケットについて、最初の 3 文字をループし、整数に変換して合計します。 次に、最後の 3 文字に対して同じプロセスを繰り返します。 最後に、2 つの結果を比較します。 

このアプローチは、この設定ではすでに最適です。 テストごとの入力サイズは一定であるため、直接集計以外に利用できる構造はありません。 代替方法を使用しても、6 桁すべてを少なくとも 1 回読み取る必要があるため、チケットごとの直線的な作業を漸近的に改善することはできません。 

重要な観察点は、この問題には全体的な推論や前処理が必要ないということです。 各チケットは独立しており、計算は固定サイズです。 したがって、解決策は単純な文字処理に帰着します。

 ## アルゴリズムのチュートリアル

 各チケットを個別に処理し、2 つの合計を計算します。 

1. チケット文字列を読み取ります。 長さは常に 6 なので、境界チェックなしで安全にインデックスを付けることができます。 
2. 2 つのアキュムレータを初期化します。1 つは左半分用、もう 1 つは右半分用です。 
3. 各文字を整数に変換した後、左側の合計に位置 0、1、および 2 の数字を加算します。 これにより、文字エンコード空間ではなく数値空間で作業することが保証されます。 
4. 同様に、3、4、5 番目の数字を右側の合計に加算します。 
5. 2 つの合計を比較します。 一致する場合は出力します`"YES"`、それ以外の場合は出力`"NO"`。 

### なぜ効果があるのか

 各チケットは、2 つの素な数字のセットに分割されます。 すべての桁が左または右の合計に 1 回だけ寄与し、重複がないため、合計の比較は問題で説明されている条件を直接捉えます。 位置間には隠れた依存関係がないため、正確性は位置ごとの正確な蓄積に帰着します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
out = []

for _ in range(t):
    s = input().strip()
    
    left = 0
    right = 0
    
    left += ord(s[0]) - ord('0')
    left += ord(s[1]) - ord('0')
    left += ord(s[2]) - ord('0')
    
    right += ord(s[3]) - ord('0')
    right += ord(s[4]) - ord('0')
    right += ord(s[5]) - ord('0')
    
    if left == right:
        out.append("YES")
    else:
        out.append("NO")

print("\n".join(out))
```このソリューションは、各チケットを生の文字列として読み取り、改行を明示的に削除して、偶発的な文字汚染を回避します。 各桁は次のように変換されます。`ord(c) - ord('0')`、これは、速度の低下を回避する信頼性の高い定時間変換です。`int()`ただし、この問題ではどちらでも問題ありません。 

わかりやすくするために合計は別々に計算され、半分の間でインデックスが混在しないようにします。 最終的な比較は、テスト ケースごとに一定時間で実行されます。

## テストケース```python
import sys, io

def solve():
    import sys
    input = sys.stdin.readline
    t = int(input())
    res = []
    for _ in range(t):
        s = input().strip()
        left = sum(ord(s[i]) - 48 for i in range(3))
        right = sum(ord(s[i]) - 48 for i in range(3, 6))
        res.append("YES" if left == right else "NO")
    return "\n".join(res)

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return solve()

 ## 特殊なケース

 主なエッジケースでは、先頭のゼロが正しく処理されます。 たとえば、`045207`、左半分には次のものが含まれます`0,4,5`、これは数値的に次のように扱う必要があります。`0 + 4 + 5 = 9`。 プログラマが誤って部分文字列を変換した場合`"045"`構造を落として数字を誤って処理する方法で整数解析を使用すると、位置が誤って解釈されたり、誤って処理されたりする可能性がありますが、文字ごとの直接変換により、その問題が完全に回避されます。 

もう 1 つの微妙なケースは、すべての桁がゼロであるチケットです。`000000`。 正しい行動は常に`"YES"`両方の和がゼロになるからです。 各文字はゼロに変換され、実行を通じて両方のアキュムレータが等しいままであるため、アルゴリズムはこれを自然に処理します。 

最後に、次のような最大の不均衡があるケース`999000`分割境界が正しく処理されるかどうかをテストします。 左の合計は次のようになります`27`そして正しい合計は次のようになります`0`、そして半分は互いに素であり、一貫してインデックスが付けられているため、比較では正しく次の結果が得られます。`"NO"`オフバイワンのリスクなし。
