 ## 問題の理解

 文字列があります。 デコード ラウンドでは、次の形式の 3 つの連続する文字が出現するたびに検索されます。`~XY`、 どこ`X`そして`Y`は 16 進数であり、そのような各トリプルを、ASCII コードが 16 進数である 1 文字で置き換えます。`XY`。 1 ラウンド内のすべての置換は同時に行われます。 

最終的にデコードされた文字列を再構築するように求められることはありません。 必要なのは、連続する自明でないラウンド、つまりそのようなトリプルが少なくとも 1 つ存在するラウンドの最大数だけです。 

興味深いのは、置換によって別のチルダを作成できることです。 特に、`~7e`ASCIIコードの文字になります`0x7e`、それはもう一つです`~`。 その新しいチルダは、次のラウンド中にパターンに参加できます。 置換によって 16 進数を作成することもできますが、これは後で左側のチルダによって消費される可能性があります。 

入力長は最大 300,000 であるため、文字列全体を 1 回スキャンするアルゴリズムが適切です。 二次時間を要するアルゴリズムは遅すぎます。 デコードラウンドの数自体は線形になる可能性があるため、これは重要です。 たとえば、次の文字列`~7e7e7e`として減少します`~7e7e7e`、 それから`~7e7e`、 それから`~7e`、 それから`~`, したがって、ラウンド数は入力の長さに比例します。 

ラウンドごとに文字列を明示的に構築する単純な実装では、結果的に 300,000 回程度のフル スキャンを実行できます。 重要なラウンドごとに少なくとも 2 ラウンドの長さが短縮されるため、最悪の場合には約 150,000 ラウンドが含まれ、検査される文字の総数は Θ(n²) (ラウンドごとに 1 つのパターンのみが削減されるチェーンではおよそ n²/4) に達する可能性があります。 

見落としがちなエッジケースがいくつかあります。 

のために`~7e7e`、最初のラウンドが変わります`~7e`の中へ`~`、出発`~7e`。 第 2 ラウンドでは、これが次のように変更されます。`~`したがって、答えは 2 です。元の文字列のみを検索する実装では、1 つのパターンが見つかり、新しく作成されたチルダが見つかりません。 

のために`~~37~45~fF`、3つのパターン`~37`、`~45`、 そして`~fF`すべて初期状態で存在し、同じラウンドでデコードする必要があります。 そのラウンドの後、文字列には次のものが含まれます`~7E`続いてデコードされた`0xFF`キャラクターなので、別のラウンドが可能です。 正解は 2 です。各置換を個別のラウンドとして扱う順次実装では、これらの操作が誤ってカウントされる可能性があります。 

のために`~00`の場合、置換により ASCII コード 0 が生成されますが、これは印刷できず、入力アルファベットの範囲外です。 これは依然として文字値として内部的に表現される必要があります。 正解は 1 で、結果の文字で別のエンコーディングを開始することはできません。 

のために`~7g`、トリプルは無効です。`g`は 16 進数ではありません。 何も起こらないので、答えは 0 です。2 つの文字がアルファベットであるかどうかだけをチェックすると、このケースが誤って受け入れられてしまいます。 

大文字と小文字の 16 進数は両方とも有効です。 したがって`~7E`は有効なパターンであり、答えは 1 です。 

## アプローチ

 直接的なアプローチは、デコードプロセスを正確にシミュレートすることです。 1 ラウンド中に、現在の文字列を左から右にスキャンします。 いつでも`~XY`が見つかった場合は、デコードされた文字を次の文字列に追加し、3 つの位置をスキップします。 それ以外の場合は、現在の文字を変更せずに追加します。 スキャン後、現在の文字列を新しく構築された文字列に置き換え、パターンが見つからなくなるまで繰り返します。 

このシミュレーションは、ラウンドの同時定義に正確に従っているため、正確です。 パターンは重複できません: 先頭の後に`~`、次の 2 文字は 16 進数でなければならないため、これらの位置のいずれかで別のパターンを開始することはできません。 問題はその稼働時間だ。 非自明なラウンドでは文字列の長さが少なくとも 2 だけ減少するため、Θ(n) ラウンドが存在する可能性があります。 ラウンドごとに 1 つのパターンだけが消える場合、スキャンの長さは約`n, n-2, n-4, ...`、これは Θ(n²) 文字処理を行います。 n = 300,000 の場合、これは数百億回の操作に相当します。 

重要な点は、実際にはすべての中間文字列を実体化する必要はないということです。 置換ごとに 1 つの新しい文字が作成され、その文字には、その文字が出現する明確に定義されたラウンド番号が付けられます。 

現在のすべての文字が 2 つの値 (ASCII コードとその文字が作成されたラウンド) を含むオブジェクトであると想像してください。 元の文字の丸めは 0 です。3 つの隣接するオブジェクトが形成されると仮定します。`~XY`。 置換は 3 つのオブジェクトがすべてすでに存在している場合にのみ行われるため、新しいキャラクターは丸い形で表示されます。`1 + max(depth of the three objects)`。 

これにより、プロセス全体がリダクション ツリーに変わります。 ラウンドをグローバルにシミュレートする代わりに、元の文字列をスキャンしながらこれらの削減をローカルで構築できます。 

すべてのエンコードされたトリプルが 3 つの隣接する現在の文字を消費し、1 つの文字を生成するため、スタックで十分です。 新しい文字が追加される場合、新しく可能なパターンは、その文字で終わるパターンか、その文字の直前の縮小によって作成されるパターンのみです。 このようなパターンをスタックの一番上で繰り返し削減できます。 結果として得られる各文字とともに保存される深度は、その文字が表示されるラウンドとまったく同じです。 

これが同時ラウンドで機能する決定的な理由は、2 つの有効なパターンが決して重複できないためです。 パターンが現在使用可能な場合、そのパターンを縮小しても、現在使用可能な別のパターンを無効にすることはできません。 新しい文字を使用する後のパターンは、単により大きな深度を受け取ります。これは、次のデコード ラウンドを待機することに正確に対応します。

 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適なスタック | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 可能なすべてのバイトの 16 進値を事前計算します。 キャラクター用`0`を通して`9`、`A`を通して`F`、 そして`a`を通して`f`、0 から 15 までの値を格納します。他の文字はすべて無効なマーカーを受け取ります。 これにより、文字列検索の繰り返しが回避され、16 進表記の両方のケースが直接処理されます。 
2. 入力を左から右にスキャンします。 すべての元の文字について、その ASCII コードを深さ 0 とともにスタックにプッシュします。元の文字は、最初のデコード ラウンドの前にすでに存在します。 
3. 文字をプッシュした後、最後の 3 つのスタック エントリが次の形式になっているかどうかを確認します。`~XY`。 以前のすべての縮小では連続するブロックが 1 つのスタック エントリに置き換えられるため、エントリは現在の縮小文字列の隣接する文字を表します。 
4. 最後の 3 つのエントリが有効なパターンを形成している場合は、それらを削除し、デコードされた ASCII コードを次のように計算します。`16 * value(X) + value(Y)`。 その深さは、削除された 3 つのエントリの最大深さより 1 つ大きくなります。 
5. 結果の文字とその計算された深さをスタックにプッシュします。 新しい文字は、元の入力の縮小されたブロック全体を表します。 
6. スタックの最上位に有効なパターンが含まれている間、縮小チェックを繰り返します。 新しく作成したキャラクターは直前のキャラクター2人とパターンを作ることができるため、一度だけチェックすると減少の連鎖を見逃してしまいます。 
7. これまでに生成された最大の深さを維持します。 その深さは、連続する非自明な復号化ラウンドの最大数です。 

### なぜ効果があるのか

 すべてのスタック エントリが、ブロック内部のすべてのリダクションが実行された後の元の文字列の 1 つの連続ブロックを表し、その格納された深さが現在の文字が出現するラウンドと正確であるという不変条件を維持します。 

隣接する 3 つのエントリが形成される場合`~XY`、対応する文字は、格納された深さが経過した後に同時に存在します。 3 つすべてが存在する最も早いラウンドは、その最大深度よりも 1 つ大きいため、これらを置き換えると、そのラウンドで実際のプロセスが作成する特性が正確に生成されます。 有効なパターンは重複できないため、このリダクションをローカルで実行しても、同じラウンドで発生するはずの別のリダクションに干渉することはできません。 

スタックによって行われるすべての縮小は実際のデコード操作に対応し、すべての実際のデコード操作は最終的にスタック上で有効なトリプルとして表示されるようになります。 したがって、保存された最大の深さは、まさに最後の重要なラウンドになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def decode_rounds(s: str) -> int:
    hex_value = [-1] * 256

    for i in range(10):
        hex_value[ord('0') + i] = i

    for i in range(6):
        hex_value[ord('A') + i] = 10 + i
        hex_value[ord('a') + i] = 10 + i

    stack_char = []
    stack_depth = []

    answer = 0

    for ch in s:
        stack_char.append(ord(ch))
        stack_depth.append(0)

        while len(stack_char) >= 3:
            c0 = stack_char[-3]
            c1 = stack_char[-2]
            c2 = stack_char[-1]

            if c0 != 126:
                break

            v1 = hex_value[c1]
            v2 = hex_value[c2]

            if v1 == -1 or v2 == -1:
                break

            d = max(
                stack_depth[-3],
                stack_depth[-2],
                stack_depth[-1]
            ) + 1

            value = 16 * v1 + v2

            stack_char.pop()
            stack_char.pop()
            stack_char.pop()

            stack_depth.pop()
            stack_depth.pop()
            stack_depth.pop()

            stack_char.append(value)
            stack_depth.append(d)

            if d > answer:
                answer = d

    return answer

def main() -> None:
    s = input().rstrip('\n')
    print(decode_rounds(s))

if __name__ == "__main__":
    main()
```16 進ルックアップ テーブルは一度作成されます。 ASCII コードでインデックス付けされた配列を使用すると、文字定数のチェックが時間的に行われ、デコードされた値は 0 から 255 まで自然に処理されます。 

2 つのスタックは並列に保たれます。`stack_char`縮小された各ブロックの現在の文字を保存します。`stack_depth`そのキャラクターが存在するラウンドを保存します。 配列を別々にしておくことで、文字がプッシュまたはリデュースされるたびにタプルを割り当てる必要がなくなります。 

すべての入力文字は 1 回だけプッシュされます。 縮小が成功すると、3 つのエントリが削除され、1 つ追加されるため、縮小するたびにスタック サイズが 2 ずつ減少します。 最大でも存在する可能性があります`floor(n / 2)`削減。 内側の`while`したがって、ループはスキャン内にネストされているにもかかわらず、合計で O(n) 回のみ実行されます。 

境界チェック`len(stack_char) >= 3`最後の 3 つの要素を読む前に必要です。 すべての内部文字は単純に整数の ASCII 値で表されるため、16 進数テーブルは、33 未満および 126 を超えるデコードされた文字も特別なケースなしで処理します。 

Python の整数には任意の精度があるため、深さの計算にはオーバーフローの問題はありません。 実際には、最大深度は次のとおりです。`floor((n - 1) / 2)`。

import sys
import io

def decode_rounds(s: str) -> int:
    hex_value = [-1] * 256

    for i in range(10):
        hex_value[ord('0') + i] = i

    for i in range(6):
        hex_value[ord('A') + i] = 10 + i
        hex_value[ord('a') + i] = 10 + i

    stack_char = []
    stack_depth = []
    answer = 0

    for ch in s:
        stack_char.append(ord(ch))
        stack_depth.append(0)

        while len(stack_char) >= 3:
            c0 = stack_char[-3]
            c1 = stack_char[-2]
            c2 = stack_char[-1]

            if c0 != ord('~'):
                break

            v1 = hex_value[c1]
            v2 = hex_value[c2]

            if v1 == -1 or v2 == -1:
                break

            depth = max(
                stack_depth[-3],
                stack_depth[-2],
                stack_depth[-1]
            ) + 1

            value = 16 * v1 + v2

            stack_char.pop()
            stack_char.pop()
            stack_char.pop()

            stack_depth.pop()
            stack_depth.pop()
            stack_depth.pop()

            stack_char.append(value)
            stack_depth.append(depth)

            answer = max(answer, depth)

    return answer

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return str(decode_rounds(inp.rstrip('\n')))

 ## 特殊なケース

 チェーン用`~7e7e`、スタックは最初に読み取ります`~7e`そしてそれを深さ 1 のチルダで置き換えます。残りの部分は`7e`は生成されたチルダの直後にあるため、スタックは別の有効なトリプルを形成し、それを深さ 2 のチルダに置き換えます。最終スタックにはそのチルダのみが含まれており、答えは 2 です。これにより、元の入力パターンのみを検査する実装が捕捉されます。 

のために`~~37~45~fF`、初期パターンは同時です。 スタックが減る`~37`に`7`深さ1の場合、`~45`に`E`これら 2 つの縮小により、深さ 1 が明らかになります。`~7E`、深さ 2 のチルダになります。`~fF`になる`0xFF`深さは 1 です。答えは 2 です。これにより、個々の置換とデコード ラウンドを混同する実装が捕捉されます。 

のために`~00`の場合、スタックは両方の数字を有効な 16 進数字として認識し、整数値 0 を生成します。深さは 1 になり、結果のゼロ バイトはチルダではないため、新しいパターンを形成できません。 答えは 1 です。アルゴリズムでは、中間文字が印刷可能であるとは決して想定されていません。これは、デコードされた値がバイト範囲全体を占める可能性があるため、必要なことです。 

のために`~7g`、最初の文字はチルダであり、`7`は有効な 16 進数ですが、`g`ルックアップ値があります`-1`。 スタックでは 3 文字すべてが変更されないため、リダクションはカウントされず、答えは 0 になります。これは、16 進数の検証が正確に受け入れなければならない理由を示しています。`0`を通して`9`、`A`を通して`F`、 そして`a`を通して`f`。 

最大サイズチェーンの場合`~`続いて 149999 部`7e`その後`!`、長さはちょうど 300000 です。各ラウンドで最初の部分が削除されます。`7e`アクティブなチェーンから離脱し、別のチェーンを残します`~7e`したがって、正確に 149999 個の非自明なラウンドが存在します。 決勝戦`!`追加ラウンドを防ぎます。 これは、答えにとって最悪の構造的なケースであり、ラウンドごとのシミュレーションに二次時間が必要になる理由も示しています。 

300000 個のチルダで構成される文字列の場合、チルダの後に 2 つの 16 進数字が続くことはないため、スタックはリダクションを実行しません。 すべてのエントリの深さは 0 で、答えは 0 のままです。これは、アルゴリズムが誤ってチルダ自体をエンコードとして扱っていないことを確認します。
