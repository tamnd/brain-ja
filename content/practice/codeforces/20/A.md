 ## 解決策
 ## 問題の理解

 ファイルシステムのパスが文字列として与えられます。 このオペレーティング システムでは、複数の連続した`'/'`文字は単一の文字とまったく同じように扱われます。`'/'`。 つまり、次のようなパスが`///home//user///docs`そして`/home/user/docs`同じ場所を指します。 

タスクは、パスを正規化された形式に変換することです。 正規化されたパスは 1 つだけ保持します`'/'`ディレクトリ名の間。 唯一の例外はルート ディレクトリ自体であり、ルート ディレクトリ自体は正確に維持される必要があります。`"/"`。 

入力長は最大 100 文字と非常に小さいです。 二次解でも制限内で快適に実行できます。 この問題では当然、文字を 1 つずつ処理し、各スラッシュを保持するか破棄するかを決定する必要があるため、リニア スキャンが依然として最もクリーンなアプローチです。 

難しいのは、末尾のスラッシュを正しく処理することです。 次のようなパス:```
/usr/local///
```になる必要があります:```
/usr/local
```連続するスラッシュのみを圧縮する不注意な実装では、次のような誤った結果が生成されます。```
/usr/local/
```もう 1 つの特殊なケースは、ルート ディレクトリ自体です。 例えば：```
////
```次のように正規化する必要があります:```
/
```繰り返されるスラッシュをすべて盲目的に削除し、その後末尾のスラッシュを削除すると、必要なルート パスの代わりに誤って空の文字列が生成される可能性があります。 

もう 1 つの微妙なケースは、スラッシュが中央に表示される場合です。```
/a////b///c
```正しい出力は次のとおりです。```
/a/b/c
```連続するスラッシュの各グループは、ゼロではなく、正確に 1 つのスラッシュに折りたたむ必要があります。 

## アプローチ

 ブルートフォース戦略では、文字列内で次の出現箇所を繰り返し検索します。`"//"`それらを次のように置き換えます`"/"`二重スラッシュがなくなるまで。 その後、結果のパスの長さが 1 より大きい場合は、末尾のスラッシュを削除できます。 

これが機能するのは、置換するたびに文字列が短くなり、最終的には連続したスラッシュが残らなくなるからです。 文字列の長さがわずか 100 なので、繰り返し置換しても十分高速です。 

弱点は、文字列の再構築を繰り返すのは原理的に非効率であることです。 文字列の長さがはるかに長かったとします。`10^5`。 文字列は不変であり、多数の置換を実行する可能性があるため、各置換には直線的な時間がかかる可能性があります。 最悪の場合、次のようなことになります。```
//////////////////////////////////////////////////
```一度に 1 文字ずつ縮小を繰り返すと、二次的な動作が発生します。 

もっと良い観察は、実際には以前の文字を再訪する必要がないということです。 左から右にスキャンするとき、重要なのは、保持した前の文字が`'/'`。 

現在のキャラクターがそうでない場合`'/'`、常に保管しております。 

現在のキャラクターが`'/'`、以前に保持されていたキャラクターがそうでなかった場合にのみ保持されます。`'/'`。 

これにより、問題は文字列上の単一の線形パスに変わります。 

圧縮パスを構築した後も、末尾のスラッシュを処理する必要があります。 パス全体が完全でない限り、末尾のスラッシュは削除する必要があります。`"/"`。

 | 最適 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 入力パス文字列を読み取ります。 
2. 正規化された文字を格納する空のリストを作成します。 
3. パスを 1 文字ずつ繰り返します。 
4. 現在のキャラクターがそうでない場合`'/'`、結果に直接追加します。 

ディレクトリ名と文字は常に変更しないでください。 
5. 現在のキャラクターが`'/'`、結果にすでに保存されている最後の文字を確認してください。 

結果が空であるか、最後に保存された文字がそうでない場合`'/'`、スラッシュを追加します。 

それ以外の場合は、連続するスラッシュは 1 つのスラッシュと同等であるため、スキップします。 
6. 収集した文字を文字列に変換します。 
7. 文字列の長さが 1 を超える場合は、末尾のスラッシュを削除します。 

条件`length > 1`ルートディレクトリパスを保護します`"/"`空っぽになることから。 
8. 最終的な正規化されたパスを出力します。 

### なぜ効果があるのか

 このアルゴリズムはスキャン中に単純な不変条件を維持します。つまり、部分的に構築された結果には 2 つの連続するスラッシュが含まれることはありません。 

スラッシュに遭遇するたびに、以前に保持されていた文字がスラッシュではなかった場合にのみ、スラッシュを追加します。 これにより、元の文字列内のすべての最大スラッシュ ブロックが結果内で正確に 1 つのスラッシュになることが保証されます。 

スラッシュ以外の文字はすべて変更されずに順番にコピーされるため、ディレクトリ名はそのまま残ります。 

最後に、少なくとも 1 文字を保持しながら末尾のスラッシュを削除すると、次のようなパスが保証されます。`"/usr///"`なる`"/usr"`ルート ディレクトリを表すパスは正確に残りますが、`"/"`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

path = input().strip()

result = []

for ch in path:
    if ch != '/':
        result.append(ch)
    else:
        if not result or result[-1] != '/':
            result.append('/')

ans = ''.join(result)

while len(ans) > 1 and ans[-1] == '/':
    ans = ans[:-1]

print(ans)
```コードの最初の部分はリニア スキャンを実行します。 の`result`list は変更可能な文字列ビルダーとして機能するため、文字列を繰り返し連結するよりも効率的です。 

条件:```
if not result or result[-1] != '/':
```が重要なステップです。 現在のスラッシュが新しい区切りブロックで始まるか、既存の区切りブロックに属するかを決定します。 

文字列連結の代わりにリストを使用すると、中間文字列の不必要な再構築が回避されます。 このような小さな制約があるため、これは必須ではありませんが、競技プログラミングの良い実践となります。 

決勝戦`while`ループは末尾のスラッシュを慎重に削除します。```
while len(ans) > 1 and ans[-1] == '/':
```の`len(ans) > 1`状態は重大です。 それがない場合、入力は次のようになります。```
////
```ではなく、誤って空の文字列になってしまいます。`"/"`。

## テストケース```python
# helper: run solution on input string, return output string
import sys, io

def solve():
    import sys
    input = sys.stdin.readline

    path = input().strip()

    result = []

    for ch in path:
        if ch != '/':
            result.append(ch)
        else:
            if not result or result[-1] != '/':
                result.append('/')

    ans = ''.join(result)

    while len(ans) > 1 and ans[-1] == '/':
        ans = ans[:-1]

    print(ans)

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    out = io.StringIO()

    backup_stdout = sys.stdout
    sys.stdout = out

    solve()

    sys.stdout = backup_stdout

    return out.getvalue().strip()

# provided sample
assert run("//usr///local//nginx/sbin\n") == "/usr/local/nginx/sbin", "sample 1"

# minimum-size input
assert run("/\n") == "/", "single root slash"

# multiple slashes representing root
assert run("//////\n") == "/", "root normalization"

# trailing slash removal
assert run("/usr/local///\n") == "/usr/local", "remove trailing slashes"

# consecutive middle slashes
assert run("/a////b///c\n") == "/a/b/c", "compress middle slashes"

# already normalized path
assert run("/home/user/docs\n") == "/home/user/docs", "unchanged normalized path"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`/`|`/`| 有効な最小入力値 |
 |`//////`|`/`| ルートディレクトリの保存 |
 |`/usr/local///`|`/usr/local`| 末尾のスラッシュのクリーンアップ |
 |`/a////b///c`|`/a/b/c`| 内部スラッシュ ブロックの圧縮 |
 |`/home/user/docs`|`/home/user/docs`| すでに正規化されたパスは変更されません。 

## 特殊なケース

 次の入力を考えてみましょう。```
/usr/local///
```スキャン中に、アルゴリズムにより最終データが圧縮されます。`///`単一の末尾のスラッシュに変換すると、次のようになります。```
/usr/local/
```文字列の長さが 1 より大きいため、クリーンアップ ループによって末尾のスラッシュが削除されます。 最終的な答えは次のようになります。```
/ usr/local
```スペースなし:```
/usr/local
```これにより、ルート以外のパスが不要なスラッシュで終わらないことが確認されます。 

次に、次のことを考えてみましょう。```
////
```スキャンでは最初のスラッシュのみが保持され、残りのスラッシュはすべてスキップされます。 中間結果は次のとおりです。```
/
```クリーンアップ ループは以下をチェックします。```
len(ans) > 1
```長さが等しいので`1`、何も削除されません。 ルート ディレクトリは有効なままです。 

最後に、次のことを考慮してください。```
/a////b///c
```スキャンでは、各スラッシュ グループが個別に処理されます。 最大の連続ブロックはすべて 1 つのスラッシュになり、次のようになります。```
/ a / b / c
```スペースなし:```
/ a/b/c
```そして最後に:```
/a/b/c
```これは、アルゴリズムが冗長な区切り文字を排除しながらディレクトリ構造を保持していることを確認します。
