 ## 解決策
 ## 問題の理解

 いくつかの独立したテスト ケースが与えられています。 各テスト ケースでは、人々の列が固定された順序で並び、各人はアップタ​​ウンまたはダウンサイドのいずれかの出身です。 このラインの連続するセグメントを 1 つ選択することができ、そのセグメントが「バランスが取れている」、つまりアップタウン派とダウンサイダーがまったく同数含まれるようにする必要があります。 このようなすべてのバランスの取れたセグメントの中で、可能な限り最大の長さが必要です。 

したがって、テスト ケースごとの重要なタスクは、バランスのとれたセグメントを見つけることではなく、次の数が含まれる最長の部分文字列を見つけることです。`U`そして`D`等しいです。 

制約が非常に厳しいため、すべての部分文字列を直接チェックするアプローチは実行不可能です。 テスト ケース全体の長さが最大 ​​200,000 であるため、テスト ケースごとの 2 次スキャンでは、最悪の場合でも 10^10 のオーダーの演算が発生します。これは、Python の 2 秒の制限をはるかに超えています。 

いくつかの特殊なケースが構造的に重要です。 

完全に 1 文字で構成される文字列。たとえば、`UUUUU`には、正の長さの有効なセグメントがないため、答えは 0 でなければなりません。有効なペアが少なくとも 1 つ存在すると仮定する単純なアプローチでは、誤って少なくとも 2 が返されます。 

次のような完全な交互文字列`UDUDUD`すべてのプレフィックスはある時点でバランスがとれる可能性があるため、完全な長さを返す必要がありますが、それは累積バランスを正しく追跡した後でのみです。 

のようなケース`UUDDUD`異なる長さの複数の有効なセグメントを持つことができるため、最初のバランスのとれたプレフィックスだけを取得しないようにする必要があります。 

## アプローチ

 ブルートフォースのアイデアは簡単です。考えられるすべてのセグメントを試してください。`[l, r]`、何個数えますか`U`そして`D`と表示され、一致するかどうかを確認します。 答えた場合は、次のように回答を更新します`r - l + 1`。 これは、すべての候補を明示的に評価するため、正しいです。 

問題はパフォーマンスです。 開始インデックスごとに`l`、すべてスキャンします`r > l`カウントを再計算するか、実行カウントを維持したとしても、テスト ケースごとに O(n^2) セグメントを検査します。 全長が 2・10^5 までになると、これでは遅くなりすぎます。 

重要な観察は、実際には、生のカウントを気にしていないということです。`U`そして`D`、しかし、それらの違いだけです。 地図を作るなら`U`+1 と`D`-1 にすると、セグメントの合計がゼロになると、セグメントは正確にバランスが取れます。 これにより、問題は合計がゼロになる最長の部分配列を見つけることに変換されます。 

これは古典的なプレフィックス合計構造です。 定義すると`prefix[i]`インデックスの合計として`i`、次にセグメント`[l, r]`和がゼロになるのは、次の場合に限ります。`prefix[r] == prefix[l-1]`。 したがって、問題は、インデックス間の最大距離を持つ 2 つの等しいプレフィックス値を見つけることになります。 

これは、各プレフィックス合計値が出現する最も古い位置を保存することで解決できます。 同じプレフィックスの合計が再び表示されると、最初の出現からの距離を計算し、答えを更新します。

 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 遅すぎる |
 | プレフィックス合計 + ハッシュマップ | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。 

1. 処理してストリングをランニングバランスに変換します。`U`+1として、そして`D`-1として。 変数を維持します`pref`これにより、問題は等しいプレフィックスの合計を検出することに変換されます。 
2. 辞書の初期化`first_pos`プレフィックス合計値を、それらが出現する最も古いインデックスにマッピングします。 設定しました`first_pos[0] = 0`開始前のゼロサムによりインデックス 1 から始まるサブ配列が許可されるためです。 
3. 文字列を左から右に繰り返して更新します。`pref`それぞれの位置で。 加工後の位置`i`、`pref`で終わるプレフィックスの残高を表します`i`。 
4. もし`pref`以前に見たことがあるので、セグメントの長さを計算します`i - first_pos[pref]`これが大きい場合は回答を更新します。 これは、プレフィックスの合計が等しいということは、それらのインデックス間のゼロサム セグメントを意味するため、機能します。 
5. もし`pref`これまでに見たことのない、ストア`first_pos[pref] = i`。 以降の出現は可能なセグメントを短くするだけであるため、後の距離を最大化するために最初の出現のみを保存します。 
6. 文字列全体を処理した後の答えは、見つかったバランスのとれたセグメントの最大長です。 

### なぜ効果があるのか

 プレフィックス合計変換は、問題全体を等価比較にエンコードします。 すべてのバランス セグメントは、同じプレフィックス合計値を持つ 2 つのインデックスに正確に対応します。 各プレフィックス合計の最も早い発生を追跡することにより、その合計を再検討するたびに、正味残高がゼロの現在のインデックスで終わる可能な限り最長のセグメントが形成されることが保証されます。 これにより、すべての有効なセグメントが 1 回だけ考慮され、その中で最も長いセグメントがキャプチャされることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input().strip())
        s = input().strip()

        first_pos = {0: 0}
        pref = 0
        ans = 0

        for i, ch in enumerate(s, start=1):
            if ch == 'U':
                pref += 1
            else:
                pref -= 1

            if pref in first_pos:
                ans = max(ans, i - first_pos[pref])
            else:
                first_pos[pref] = i

        print(ans)

if __name__ == "__main__":
    solve()
```実装の中心的な選択は、ループ内の 1 から始まるインデックス付けです。 これは、位置 0 が空のプレフィックスを表すプレフィックス定義と自然に一致し、きれいな減算が可能になります。`i - first_pos[pref]`オフバイワン調整なし。 

更新も避けます`first_pos`最初の発生後、これは重要です。 これを上書きすると、最大長のセグメントを形成する可能性が失われます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        s = input().strip()

        first_pos = {0: 0}
        pref = 0
        ans = 0

        for i, ch in enumerate(s, start=1):
            pref += 1 if ch == 'U' else -1
            if pref in first_pos:
                ans = max(ans, i - first_pos[pref])
            else:
                first_pos[pref] = i

        out.append(str(ans))

    return "\n".join(out)

# provided samples
assert run("4\n4\nUDUD\n7\nUUUDDDD\n10\nDDUDDUDUUD\n2\nDD\n") == "4\n6\n8\n0"

# custom cases
assert run("1\n1\nU\n") == "0", "single element"
assert run("1\n6\nUUUUUU\n") == "0", "all same"
assert run("1\n6\nUDUDUD\n") == "6", "fully alternating"
assert run("1\n8\nUUDDUDUD\n") == "8", "multiple valid segments"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`U`|`0`| 最小長のエッジケース |
 |`UUUUUU`|`0`| 有効なバランスセグメントがありません |
 |`UDUDUD`|`6`| 全長オルタネイトバランス |

 ## 特殊なケース

 なしの文字列`U`またはいいえ`D`最も重要な変性ケースです。 入力用`DDDD`、プレフィックスの合計は減少するだけで繰り返されないため、辞書で一致が生成されることはなく、答えは 0 のままです。最初の 0 以降はプレフィックスの合計が等しくなることは決してないため、アルゴリズムは誤検知を正しく回避します。 

のようなケース`UDUDUD`以前に確認されたプレフィックス合計に繰り返し戻ります。 返されるたびに、現在のインデックスで終わる候補セグメントが生成されます。最も古いセグメントのみが保存されるため、各位置で終わる最長のセグメントが常に考慮されます。 

のようなブロックが混在しているケース`UUDDUD`最適なセグメントは文字列の途中で開始および終了する可能性があり、必ずしもブロック境界に沿って整列するとは限らないことを示しています。 プレフィックス合計の等価性は、特別なケースを使用せずにこれを自然に処理します。
