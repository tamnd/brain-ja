 ## 解決策
 ## 問題の理解

 各テストでは、エッセンス タイプのコレクションと、レベルごとに分割されたワーカー ドラゴンのコレクションが提供されます。 各エッセンス タイプには必要な量があり、完成したドラゴンの卵はそれぞれ、正確にその量の各エッセンス タイプを消費します。 

ワーカードラゴンは平等に貢献するわけではありません。 レベル$i$労働者が生産する$2^{i-1}$1 日あたりのエッセンスの単位、および各労働者は永続的に 1 つのエッセンス タイプに正確に割り当てられなければなりません。 複数のワーカーを同じエッセンス タイプに割り当てることができ、彼らの貢献は合計されます。 

ワーカーを割り当てた後、各エッセンス タイプ$j$ある程度の総供給量が蓄積される$S_j$。 そのエッセンスは限られた数の卵しかサポートできません。$\left\lfloor \frac{S_j}{a_j} \right\rfloor$。 卵にはすべてのエッセンス タイプが同時に必要となるため、最終的に生成される卵の数は、すべてのエッセンス タイプにわたるこれらの値の最小値になります。 目標は、この最小値を最大化する割り当てを選択することです。 

制約の構造が解決策の原動力となります。 多くても$5 \times 10^4$エッセンス タイプはテスト ケース全体で全体的に異なりますが、ワーカー レベルの数は最大 20 です。これが重要な不均衡です。ワーカー タイプの種類は非常に少ないですが、各タイプは大量に出現する可能性があります。 このことは、従業員を個別に扱うべきではなく、レベルごとに集計すべきであることをすぐに示唆しています。 

素朴な解釈では、ワーカーのエッセンス タイプへのすべての割り当てを試みることになります。 たとえ命令を無視したとしても、各労働者は$n$選択肢が多く、ワーカーの総数が非常に多くなる可能性があります。$b_i$まで上がります$10^9$。 ワーカーごとのシミュレーションは不可能です。 

もう少し素朴な試みとしては、正しさの議論を行わずに貪欲な割り当てを試行することもできます。たとえば、常に最も強いワーカーを最も弱いエッセンスに割り当てる、またはその逆を行うなどです。 この目的は、すべてのエッセンス タイプにわたる最小比率のバランスに依存しているため、これは失敗します。 単一のエッセンスタイプが不十分に満たされていると、答えが減少するため、慎重に構造化しない限り、貪欲なローカル決定は明らかに安全ではありません。 

さらに微妙な失敗例は、割り算を無視した場合に起こります。 世界全体で資源の総量が十分であっても、配分が不十分な場合は、1 つの種類のエッセンスが不足する可能性があります。 たとえば、あるエッセンスが少量を必要とするが低レベルのワーカーのみを受け取る一方で、別のエッセンスが高レベルのワーカーをすべて受け取る場合、合計が問題ないように見えても最小値が崩れる可能性があります。 

したがって、本当の困難は、リソースの合計をカウントすることではなく、重み付けされたリソースをビンに分割して最小比率を最大化することです。 

## アプローチ

 強引な視点は卵の数を推測することです$x$次に、すべてのエッセンス タイプが少なくとも$a_j \cdot x$総生産量。 これにより、問題は実現可能性のチェックに変換されます。つまり、重み付けされたアイテム (ワーカー) をパックできるかどうかです。$n$下限のあるグループ?

 割り当てを修正すれば、チェックするのは簡単です。 問題は、割り当てが組み合わせであることです。 ワーカーが多い場合、すべてのディストリビューションを試すのは指数関数的です。 

重要な観察は、決定バージョンが単調であるということです。$x$。 生産できれば$x$卵があれば、さらに少ない数を生産することもできます。 これにより二分探索が可能になります$x$。 残りのタスクは、実現可能性チェックの設計です。 

労働者の価値観の構造により、これは管理可能になります。 すべての労働者の貢献は 2 のべき乗であり、$1$まで$2^{k-1}$と$k \le 20$。 これは、ワーカーを同じ重さの 20 個のバケツとして扱うことができることを意味します。 実現可能性に関しては、各ウェイト クラスをいくつ割り当てるかだけを考慮します。 

固定の実​​現可能性を判断するには$x$、各エッセンスタイプが需要になります$d_j = a_j \cdot x$。 すべての要求を満たすためには、重み付けされたアイテムを割り当てる必要があります。 正しい貪欲な戦略は、「最大の需要を優先する」という考えから生まれます。つまり、利用可能な最大のワーカーを最初に使用して、最も要求の厳しいエッセンス タイプを満たすことです。これは、大規模なワーカーが最も柔軟であり、小規模なワーカーでは効率的に埋めることができない大きなギャップをカバーできるためです。 

需要の高いエッセンス タイプから順に処理します。 それぞれについて、需要が満たされるか不可能になるまで、利用可能な最大のワーカー タイプを最初に貪欲に消費します。 重みは 2 の累乗であるため、分割の決定には複雑なナップザック DP は必要ありません。 貪欲な抽出が機能するのは、大きな項目は常に、要求が高い初期段階でより有用であるためです。 

これにより、実現可能性が 20 種類の項目にわたって制御された貪欲な割り当てのようなものになり、$n$要求します。

 ## アルゴリズムのチュートリアル

 ### 1. ワーカーの重みを事前計算する

 レベルごとに変換します$i$重りに$w_i = 2^{i-1}$多重性のある$b_i$。 これにより、ワーカー セット全体が最大 20 種類に圧縮されます。これは、後のすべての操作が重みごとのカウントのみに依存するため、非常に重要です。 

### 2. 答えの二分探索範囲を設定する

 卵の数の妥当な上限を計算します。 利用可能なリソースの合計は、$\sum b_i \cdot 2^{i-1}$なので、それを最小値で割ります。$a_j$に安全な上限を与える$x$。 これにより、物理的に可能な生産を超えて検索することがなくなります。 

### 3. 卵の数の二分探索

 値を推測します$x$そしてそれが実現可能かどうかをテストします。 可能であれば、より大きな値を試します。 それ以外の場合は削減します。 

単調性は、増加するという事実から来ます。$x$すべての要求が直線的に増加するだけであり、実現可能性が難しくなります。 

### 4. それぞれの本質を需要に変換する

 固定の場合$x$、各エッセンスタイプ$j$総リソースが必要です$d_j = a_j \cdot x$。 これらの要求を降順に並べ替えて、常に最も難しい制約を最初に満たすようにします。 

満たされていない大規模な要件を処理する場合、大規模なワーカーが最も価値があるため、この順序は重要です。 

### 5. 利用可能なワーカーを使用した貪欲な割り当て

 各レベルの残りのワーカー数を維持します。 ソートされた順序で各エッセンスについて、利用可能な最大のワーカー タイプを繰り返し使用することで、その需要を満たすよう試みます。 私たちは常に、より低いレベルに移動する前に、最も高いレベルから可能な限り多くのものを取得します。 

この貪欲なステップにより、下位レベルで満たせる小さな要求に高価値のワーカーを無駄にすることを確実に回避できます。 

### 6. 実現可能性の決定

 すべてのエッセンスが利用可能なワーカーを使って需要を満たすことができるとしたら、$x$実現可能です。 そうでなければそうではありません。 

### なぜ効果があるのか

 重要な不変条件は、実現可能性チェックのどの時点でも、必要な場合を除き、後で小規模なワーカーのみを使用して満たすことができるエッセンスに大規模なワーカーを割り当てることは決してないということです。 需要は降順に処理されるため、大きなワーカーは常に、小さなワーカーでは不十分または効率が低下するコンテキストで使用されます。 2 のべき乗構造により、小規模な労働者の組み合わせが、赤字をカバーする際に大規模な労働者よりも厳密に優れたパフォーマンスを発揮するという病的なケースが発生しないことが保証されます。 これにより、需要の固定順序の下で、貪欲な割り当てが最適なパッキング戦略と一致するようになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def feasible(x, a, b, k):
    # copy available workers
    cnt = b[:]
    
    # build demands
    req = [ai * x for ai in a]
    req.sort(reverse=True)
    
    # process each essence
    for need in req:
        # try to satisfy this need using largest workers first
        for i in range(k - 1, -1, -1):
            if need <= 0:
                break
            if cnt[i] == 0:
                continue
            w = 1 << i
            use = min(cnt[i], (need + w - 1) // w)
            cnt[i] -= use
            need -= use * w
        
        if need > 0:
            return False
    
    return True

def solve():
    T = int(input())
    for _ in range(T):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))
        
        lo, hi = 0, 10**18
        
        while lo < hi:
            mid = (lo + hi + 1) // 2
            if feasible(mid, a, b, k):
                lo = mid
            else:
                hi = mid - 1
        
        print(lo)

if __name__ == "__main__":
    solve()
```実装は実現可能性ロジックに直接に従います。 ワーカー数は固定サイズの配列に格納されます。$k$、各実現可能性チェックは最高レベルから下に向かって繰り返し消費されます。 

微妙な点は、特定のレベルのワーカーが何人必要かという計算です。`(need + w - 1) // w`重量のワーカーの最小数を計算します$w$残りの要件をカバーするために必要です。 過剰な消費を避けるために、利用可能な労働者によってこの上限を設定しています。 

二分探索では、最悪の場合の累積をカバーするのに十分な大きさの上限が使用されるため、Python 整数が使用されている限り、オーバーフローの懸念は正確性に影響しません。

 ## 特殊なケース

 重要なエッジケースは、1 つのエッセンスの要件が非常に大きく、他のエッセンスの要件が小さい場合です。 このような場合、アルゴリズムは高レベルのワーカーを最初に需要の多いエッセンスに積極的に割り当てます。 これにより、小さなエッセンスが高レベルのワーカーを消費し、大きなエッセンスが満足できないままになるというシナリオが回避されます。 ソート済みデマンド処理により、正しい順序付けが保証されます。 

もう 1 つのエッジ ケースは、ワーカーの総能力がグローバルに十分であるにもかかわらず、適切に分割できない場合に発生します。 貪欲な消費では常に最も効率的な利用可能な割り当てが最初に使用されるため、すべてのレベルを使い果たした後でも一部の需要を満たすことができない場合、実行可能性チェックは正確に失敗します。 これにより、隠れた「不正な分布」が見逃されるのではなく、確実に検出されます。
