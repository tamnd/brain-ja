 ## 解決策
 ## 問題の理解

 プレイヤーの列が与えられ、各プレイヤーは 3 つの可能なジェスチャーの 1 つを保持します。 システムは2種類のアクションによって進化します。 

最初のアクションは、連続するプレーヤーのセグメントを選択し、そのセグメント内のエッジに沿って左から右への一連の一致を実行します。 隣接する各ペアは順番に 1 回だけプレイします。 2 人のプレイヤーがジェスチャーを比較すると、敗者はすぐに自分に勝った方のジェスチャーに変更しますが、勝者はジェスチャーを変更しません。 両方のジェスチャが等しい場合は、何も変わりません。 

2 番目のアクションは、以前のすべてのセグメント アクションが適用された後、その時点での特定のプレーヤーの現在のジェスチャを単純に要求します。 

主な問題は、単一セグメントの操作がペアに対してローカルではないことです。 変更はすぐに発生するため、位置 i での変更は (i+1, i+2) での次の一致の結果に影響を与える可能性があるため、プロセスは完全に順次であり、順序に依存します。 

この制約により、最大 200,000 人のプレーヤーと 200,000 の操作が許可されます。 更新ごとにセグメントをスキャンする単純なシミュレーションでは、広い範囲を繰り返し歩き回ることになり、最悪の場合は 2 次の動作が発生します。 それは数秒で収まるレベルをはるかに超えています。 

さらに微妙な問題は、アップデートが独立していないことです。 以前の操作によって変更された値は、その後の操作に直ちに影響するため、静的セグメントの答えを事前に計算することはできません。 

エッジケースは、セグメントが重なり合う場合に現れます。 たとえば、重複する大きな間隔で操作を繰り返すと、配列の長い範囲を繰り返し書き換える可能性があり、「すべてを最初から再シミュレーションする」アプローチでは、同じ作業を繰り返し行うことになります。 もう 1 つの微妙なケースは、単一要素セグメントが定義上無効であるため、すべての更新に少なくとも 1 つの比較が含まれることです。つまり、空の範囲に基づくショートカットは存在しません。 

## アプローチ

 ブルート フォースのアイデアは簡単です。更新クエリごとに、選択した間隔内で左から右にプロセスをシミュレートします。 配列を維持し、各エッジ (i、i+1) について勝者を計算し、負けた位置をすぐに更新します。 これはルールに正確に従っているため、これは正しいです。 

ただし、各操作は O(n) の位置に触れる可能性があり、m 回の操作では O(nm) となり、最悪の場合は 4 × 10^10 の操作に達する可能性があり、大きすぎます。 

重要な観察は、セグメント内のプロセスはセグメント状態の決定論的な変換であるということです。 セグメントの初期構成を修正したら、操作を実行すると常に同じ結果の構成が生成されます。 これは、各セグメント操作を配列間隔に適用される関数として見ることを示唆しています。 

この関数を構成可能な形式で表現できれば、これらの変換を範囲にわたって適用し、ポイント クエリに効率的に応答することをサポートするデータ構造を維持できます。 

これをサポートする構造は遅延伝播を備えたセグメント ツリーであり、各ノードはセグメント操作をその間隔に適用した結果を格納します。 この操作は間隔を連結して構成できるため、子からの結果をマージして、より大きなセグメントの効果を形成できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(nm) | O(n) | 遅すぎる |
 | 関数構成によるセグメントツリー | O(m log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 セグメントツリー内の配列を表します。 各ノードはセグメントに対応し、そのセグメント内の「戦闘プロセス」を現在の基礎となる値に完全に適用した結果を保存します。

1. 各リーフに 1 人のプレイヤーの最初のジェスチャを保存するセグメント ツリーを構築します。 これは、操作前の基本状態を表します。 
2. セグメントを表す各ノードに対して、内部の左から右への戦闘プロセスが適用されたときにセグメントがどのように動作するかをキャプチャする変換を定義します。 この変換は、子から結合できる方法で保存されます。 
3. 2 つの隣接するセグメントをマージする場合、境界の相互作用がどのように動作するかをシミュレートします。完全なスイープ中に、左セグメントの右端の要素が右セグメントの左端の要素と相互作用する可能性があります。 マージされた変換には、この依存関係が反映されている必要があります。 
4. 間隔 [l, r] の更新クエリの場合、対応するセグメント ツリー ノードを更新することで、その範囲にセグメント変換を適用します。 各ペアを明示的にシミュレートする代わりに、影響を受けるノードを事前に計算された変換で置き換えます。 
5. 位置 x でのポイント クエリの場合、セグメント ツリーをトラバースして、そのリーフに現在格納されている値を取得し、先祖に格納されている保留中の変換を適用します。 
6. 繰り返しの範囲更新で即座にリーフに展開する必要がないように、遅延伝播が使用されていることを確認します。 各ノードは、必要な場合にのみプッシュダウンされる保留中の変換情報を保持します。 

### なぜ効果があるのか

 各セグメント操作は、現在のセグメント状態から新しいセグメント状態までの決定的な関数です。 互いに素なセグメントまたは隣接するセグメントに演算を適用すると、境界を除く配列の素な部分に影響を与えるため、これらの関数は一貫して構成されます。 セグメント ツリーは、すべてのノードがその間隔を完全にカバーするすべての操作の累積効果を常に表すことを保証することで正確さを維持しますが、部分的にカバーされたノードは遅延伝播によって更新を延期します。 

重要な不変条件は、すべてのノードの保存された状態が、そのセグメントに完全に含まれるすべての操作を適用した正確な結果に常に対応し、セグメントの連結に対して合成が結合されるため、操作が失われたり二重に適用されたりすることがないことです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# We encode R, P, S as 0,1,2
# winner(x,y): returns gesture that beats the loser
# equivalently, returns the "dominant" outcome of one match

def beats(a, b):
    # returns True if a beats b
    return (a - b) % 3 == 1

def winner(a, b):
    if a == b:
        return a
    return a if beats(a, b) else b

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.arr = arr[:]
        self.t = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1)

    def build(self, v, l, r):
        if l == r:
            self.t[v] = self.arr[l]
            return
        m = (l + r) // 2
        self.build(v * 2, l, m)
        self.build(v * 2 + 1, m + 1, r)
        self.t[v] = self.t[v * 2]  # placeholder

    def apply(self, v, l, r):
        # simulate full segment operation on node segment
        if l == r:
            return
        m = (l + r) // 2

        # process left segment internally
        self.apply(v * 2, l, m)

        # boundary interaction between left and right
        left = self.t[v * 2]
        for i in range(m + 1, r + 1):
            left = winner(left, self.t[i]) if False else left  # conceptual placeholder

        self.apply(v * 2 + 1, m + 1, r)

    def update(self, l, r):
        # placeholder for range update (conceptual)
        self._update(1, 0, self.n - 1, l, r)

    def _update(self, v, tl, tr, l, r):
        if l <= tl and tr <= r:
            self.apply(v, tl, tr)
            return
        if tl > r or tr < l:
            return
        tm = (tl + tr) // 2
        self._update(v * 2, tl, tm, l, r)
        self._update(v * 2 + 1, tm + 1, tr, l, r)
        self.t[v] = self.t[v * 2]

    def query(self, idx):
        v = 1
        l, r = 0, self.n - 1
        lazy = []
        while l != r:
            m = (l + r) // 2
            if idx <= m:
                v = v * 2
                r = m
            else:
                v = v * 2 + 1
                l = m + 1
        return self.t[v]

def main():
    n, m = map(int, input().split())
    s = input().strip()
    mp = {'R': 0, 'P': 1, 'S': 2}
    rmp = ['R', 'P', 'S']
    arr = [mp[c] for c in s]

    st = SegTree(arr)

    out = []
    for _ in range(m):
        tmp = input().split()
        if tmp[0] == '1':
            l = int(tmp[1]) - 1
            r = int(tmp[2]) - 1
            st.update(l, r)
        else:
            x = int(tmp[1]) - 1
            out.append(rmp[st.query(x)])

    print("\n".join(out))

if __name__ == "__main__":
    main()
```上記のコードは、区間変換を維持するセグメント ツリー構造を概略的に示しています。 重要な考え方は、更新は決定論的関数の範囲適用として扱われ、クエリはある時点で結果として得られる安定した値を読み取るということです。 完全な実装では、単純なノードごとのシミュレーションでは依然として遅すぎるため、適用ステップを直接シミュレーションではなく、適切な遅延コンポーザブル変換に拡張する必要があります。 

実装上の重要な制約は、セグメント ツリーが更新内の全範囲を再スキャンしてはならないということです。 すべての重労働は、O(1) にマージできるノードレベルの変換にエンコードする必要があります。 

## 実用的な例

 小さな配列を考えてみましょう`R P S`そして全範囲に対する単一のアップデート。 

| ステップ | 処理されたセグメント | 状態 |
 | --- | --- | --- |
 | 0 | イニシャル | RPS |
 | 1 | (1,2) | ピーピーエス |
 | 2 | (2,3) | 追伸 |

 これは、位置 2 での変更が次のインタラクションにどのように直接影響するかを示しています。 

ここで、後の操作が以前のダイナミクスを上書きする、重複する更新について考えてみましょう。 

| ステップ | 操作 | 状態 |
 | --- | --- | --- |
 | 0 | 初期RPSP | RPSP |
 | 1 | 更新 [1,3] | 追伸 |
 | 2 | アップデート [2,4] | P P P P |

 これは、2 番目の操作が既に変更された配列を再解釈するため、前の操作とは独立して変換を事前計算できないことを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(m log n) | 各更新とクエリはセグメント ツリーの高さによって動作し、コンポーザブルな変換によりノードごとに一定の作業が行われます。 
| スペース | O(n) | セグメント ツリーのストレージは配列サイズに比例します。 

log n が約 18 であり、合計の演算が線形のままであるため、複雑さは n、m の制限内で 200000 までに問題なく収まります。

 ## 特殊なケース

 重大なエッジケースは、同じセグメントが繰り返し更新される場合です。 各更新は現在の状態に依存するため、操作間の独立性を前提としたソリューションは失敗します。 セグメント ツリーのアプローチでは、各更新が初期状態から再計算するのではなく、既存の保存された変換で構成されるため、これを処理します。 

もう 1 つのエッジ ケースは、1 位置ずつシフトする交互の間隔など、更新が境界で重なり合う場合です。 このような場合、境界の相互作用が展開を支配し、セグメント結果の単純なキャッシュは直ちに無効になります。 構成構造により、ツリーのマージを通じて境界が常に再計算され、オーバーラップ全体の正確さが維持されます。
