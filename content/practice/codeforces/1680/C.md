 ## 解決策
 ## 問題の理解

 バイナリ文字列が与えられ、非常に特殊な方法でそれを切り取ることができます。つまり、削除するプレフィックスとサフィックスを選択し、中央に単一の連続した部分文字列を残します。 残りの部分文字列は「保持」されますが、その外側の部分文字列はすべて削除されたとみなされます。 

保持された部分文字列を選択するコストは 2 つの量によって異なります。 まず、保持された部分文字列内にゼロがいくつ残っているかを数えます。 次に、元の文字列から削除された 1 の数を数えます。これは、選択した部分文字列の外側にある 1 の数と正確に一致します。 最終的なコストは、これら 2 つの値のうち大きい方になります。 目標は、この最大値ができるだけ小さくなるように保持する部分文字列を選択することであり、まったく保持しないこともできます。 

重要な制約は、すべてのテスト ケースの合計長が最大 200,000 であることです。 これにより、テスト ケースごとの部分文字列の二次列挙が即座に除外されます。 すべての左右の境界を独立して試行すると、最悪の場合、約 10¹⁰ の操作にまで低下し、実行不可能になります。 おそらくプレフィックス計算またはスライディング構造を使用した、テスト ケースごとの線形または線形に近いソリューションを期待する必要があります。 

最適な戦略がすべてを削除するか、文字列全体を保持することである場合、微妙なエッジ ケースが発生します。 たとえば、すべて 1 の文字列は、すべてを削除することで最もよく処理されます。これは、何かを保持するとゼロのコストがゼロになりますが、削除されたもののコストが不必要に増加する可能性があるためです。 逆に、すべてゼロの文字列は完全に保持するのが最適です。何かを削除しても、削除されたものの数が増えるだけで何のメリットもありません。 

「バランスの取れた」カットのみを試行したり、文字が均等に分散された中間セグメントから答えが得られると仮定したりする単純なアプローチは、次のような単調な文字列では失敗します。`00000`または`11111`ここで、最適な答えは自明のことながらゼロですが、間違ったヒューリスティックによってプラスのコストが発生する可能性があります。 

## アプローチ

 直接的な総当たり戦略は、接頭辞と接尾辞を削除した後に残る可能性のあるすべての部分文字列を考慮することです。 各候補区間について$[l, r]$、内側にゼロがいくつあるか、外側にゼロがいくつあるかを計算します。 次に、これら 2 つの値の最大値としてコストを評価し、すべての間隔で最小値を取得します。 

これは、許可されているすべての構成を徹底的にチェックするため、正しいです。 ただし、$O(n^2)$テスト ケースごとの部分文字列、および各評価にかかる時間$O(1)$プレフィックスの合計が事前に計算されている場合。 プレフィックスの合計を使用しても、合計作業量は次のようになります。$O(n^2)$が遅すぎます。$2 \cdot 10^5$全長。 

重要な観察は、コストは「内部のゼロ」と「外部の 1」のバランスのみに依存するということです。 分割点を修正し、プレフィックスとサフィックスの寄与という観点から考えると、問題は境界を選択し、増分的に維持できる関数を最適化することと同等になります。 部分文字列を明示的に選択する代わりに、保持するゼロと削除されるゼロをトレードオフするカットを選択するという問題を再定式化します。 

部分文字列を保持することを接頭辞と接尾辞の削除と解釈する接頭辞ベースの変換を定義し、境界を移動したときにコストがどのように変化するかを追跡します。 これにより、すべての有効な分割を線形時間で評価できるように、0 と 1 のカウントを維持しながら文字列をスキャンすることになります。

 ## アルゴリズムのチュートリアル

 カット位置を選択し、残すゼロの数と破棄するゼロの数を評価するという観点から問題を書き直します。 主なアイデアは、プレフィックスとサフィックスの間の考えられるすべての境界を考慮し、その構成で達成可能な最適なコストを効率的に計算することです。 

1. 文字列内の 1 の合計数を事前計算します。 これにより、繰り返しスキャンすることなく、保持されたセグメントの「削除されたもの」を計算できます。 セグメントに次の内容が含まれている場合`ones_inside`、 それから`ones_removed = total_ones - ones_inside`。 
2. 左側から削除するプレフィックスを定義するすべての可能な分割ポイントを反復処理します。 このような各点について、それを保持されたセグメントの開始点として扱います。 
3. 保持されたセグメントの右境界を移動している間、セグメント内の 0 と 1 の連続カウントを維持します。 これにより、各候補間隔のカウントの再計算が回避されます。 
4. 各候補セグメントについて、次の最大値としてコストを計算します。 

- セグメント内のゼロ
 - total_ones からセグメント内の 1 を引いた値

 これは定義から直接導き出されます。内側のゼロは残り、外側のゼロは削除されます。 
5. すべての有効なセグメントにわたってこのコストの最小値を追跡します。 

より効率的な観点では、両方の境界を個別に明示的に列挙する必要がなくなります。 代わりに、分割点を修正し、プレフィックス/サフィックスの累積を使用して、線形時間で最適な値を導き出します。 

### なぜ効果があるのか

 有効な操作はすべて、保持される単一の連続セグメントによって完全に記述されます。 コストは、内側のゼロと外側の 1 という 2 つの量にのみ依存します。 両方の量は、セグメントが 1 文字ずつ拡大または縮小されるときに段階的に更新できます。 各文字はカウントを ±1 だけ変更するため、すべての候補セグメントを再計算せずに評価できます。 これにより、すべての有効な構成が 1 回だけ考慮され、これらの評価の最小値がグローバルに最適化されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        s = input().strip()
        n = len(s)

        total_ones = s.count('1')

        zeros_inside = 0
        ones_inside = 0

        ans = float('inf')

        l = 0
        for r in range(n):
            if s[r] == '0':
                zeros_inside += 1
            else:
                ones_inside += 1

            while l <= r:
                ones_removed = total_ones - ones_inside
                cost = max(zeros_inside, ones_removed)
                ans = min(ans, cost)

                if s[l] == '0':
                    zeros_inside -= 1
                else:
                    ones_inside -= 1
                l += 1

        print(ans)

if __name__ == "__main__":
    solve()
```このソリューションでは、保持された部分文字列を表すスライディング ウィンドウが維持されます。 右側の境界を延長するたびに、1 つの文字がウィンドウに組み込まれます。 次に、現在の右側の境界で終わるすべての有効な構成を評価しながら、左側の境界を縮小します。 重要な実装の詳細は、ウィンドウ内のカウントが常に一貫して保たれるため、内側の 0 と外側の 1 の両方が一定時間で計算されることです。 

よくある落とし穴は、文字列全体の削除が許可されていることを忘れることです。 次の場合にウィンドウが空になる可能性があるため、これは自然に処理されます。`l > r`、その場合、内部のゼロはゼロで、削除されたものは合計の値と等しくなり、正しいコスト候補が生成されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    output = io.StringIO()
    sys.stdout = output

    import sys
    input = sys.stdin.readline

    t = int(input())
    res = []
    for _ in range(t):
        s = input().strip()
        total_ones = s.count('1')

        zeros_inside = 0
        ones_inside = 0

        ans = float('inf')
        l = 0

        for r in range(len(s)):
            if s[r] == '0':
                zeros_inside += 1
            else:
                ones_inside += 1

            while l <= r:
                ans = min(ans, max(zeros_inside, total_ones - ones_inside))
                if s[l] == '0':
                    zeros_inside -= 1
                else:
                    ones_inside -= 1
                l += 1

        res.append(str(ans))

    return "\n".join(res) + "\n"

 ## 特殊なケース

 次のようなゼロのみの文字列`00000`文字列全体を削除するか完全に保持すると、コストはゼロになります。 アルゴリズムは自然にこの状態に到達します。`ones_removed`は常にゼロであり、ウィンドウを縮小すると、最終的に内部はゼロになります。 

次のようなもののみの文字列`11111`すべてを削除すると最適です。 この場合、内部のゼロはゼロで、削除されたものは合計の 1 に等しくなりますが、両方の値がゼロである空のウィンドウで最小値が達成されます。 

次のような交互の文字列`101010`内部のゼロの局所的な増加と削除されたゼロのグローバルな減少のバランスをとるようにアルゴリズムを強制します。 スライディング ウィンドウは各境界遷移を評価し、ゼロの限界増加が除去された 1 の限界減少と等しいときに最適点が表示されます。
