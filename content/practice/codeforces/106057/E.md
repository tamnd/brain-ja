 ## 解決策
 ## 問題の理解

 長さの初期配列が与えられます$N$。 その後、一連の範囲更新によって変更されます。更新ごとにセグメントが選択されます。$[L, R]$そして価値を追加します$d$そのセグメント内のすべての要素に適用されます。 すべての更新が適用されると、配列が修正されます。 次に、$K$この最後の配列内の 2 番目に大きい値。 

このタスクは基本的に 2 つのフェーズに分かれています。 まず、多くの範囲の増分を静的配列に効率的に適用する必要があります。 次に、最終的に変換された配列に対する順序統計クエリをサポートする必要があります。 

一般的な Codeforces 設定に含まれる制約は、$N, Q, M$あたりまで$2 \cdot 10^5$単純なシミュレーションを即座に除外します。 範囲更新コストごとにすべての要素を更新する直接的なアプローチ$O(NQ)$、それはあたりでしょう$10^{10}$最悪の場合、制限時間内に操作が実行されなくなる可能性があります。 同様に、配列をスキャンして各クエリの答えを再計算すると、クエリごとの並べ替えや線形スキャンのコストが不必要に増大するため、時間がかかりすぎます。 

エッジケースは主にインデックス作成と更新の境界付近で発生します。 よくある間違いの 1 つは、$R + 1$差分配列内の位置。 

もし$N = 5$、そして私たちは適用します$(L=2, R=5, d=3)$、その後、位置での減算に失敗します$R+1 = 6$または、範囲外の更新を誤って書き込むと、増分が配列を超えてリークするか、ロジックがクラッシュします。 もう 1 つの微妙なケースは、複数の更新が重複する場合です。 単純なアプローチでは寄与が二重に適用されたり、順序が間違ったりする可能性がありますが、正しい方法では線形累積を保証する必要があります。 

最後に、次のことを求めるクエリ$K = 1$または$K = N$ソート後のインデックス作成の境界の正確さをテストします。 

## アプローチ

 簡単な解決策は、以下を反復して各更新を適用します。$L$に$R$そして追加$d$直接。 これは操作の定義を反映しているため、これは正しいです。 ただし、各アップデートにより次の点が修正される可能性があります。$N$要素と$Q$更新すると、全体の複雑さは次のようになります$O(NQ)$。 入力が大きい場合、これは不可能になります。 

重要な観察は、各更新が連続セグメントにわたって一定の値に寄与するということです。 要素ごとに適用する代わりに、差分配列を使用してその効果をエンコードできます。 位置に +d をマークすることで$L$そして位置に -d$R+1$では、範囲の更新をポイントの更新に変換します。 この構造のプレフィックス合計により、最終的な配列が線形時間で再構築されます。 

最終的な配列が構築されたら、それを並べ替えることで注文統計に直接アクセスできるようになります。 の$K$- 番目に大きい要素は、昇順でソートした後、直接インデックス検索になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(NQ + M)$|$O(1)$| 遅すぎる |
 | 最適 |$O(N \log N + Q + M)$|$O(N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 この問題を 2 つの独立したフェーズに変換します。つまり、範囲の更新を効率的に適用し、次に選択クエリに応答します。 

1. 差分配列を作成する`df`サイズの$N+1$、ゼロに初期化されます。 この構造は、実際の値を直接保存するのではなく、連続する位置間で値がどのように変化するかを表します。 
2. アップデートごとに$(L, R, d)$、 追加$d$に`df[L]`。 これは、から始まるすべてのポジションを意味します。$L$増加するはずです$d$。 
3. 減算$d$から`df[R+1]`もし$R+1 \le N$。 これにより、セグメントを超えた効果がキャンセルされ、増分が正確に停止することが保証されます。$R$。 この境界処理により、表現が範囲更新と同等になります。 
4. プレフィックスの合計を計算します。`df`各位置の実際の増分を再構築します。 各ポジションには、それに影響を与えるすべてのアクティブな貢献が蓄積されます。 
5. これらの増分を元の配列に追加します$A$、最終的に変換された配列が生成されます。 
6. 結果の配列を昇順に並べ替えます。 並べ替えにより値が整理されるため、順序統計が直接インデックスにアクセスできるようになります。 
7. 各クエリについて$K$、インデックスの要素を出力します$N - K$。 これは、$K$- インデックス作成が 0 から開始されてから 2 番目に大きい値。 

### なぜ効果があるのか

 差分配列は、各範囲の更新を境界変更のペアとしてエンコードします。 すべての更新は、連続セグメント全体にわたる一定のオフセットに寄与し、プレフィックス合計により、各位置がその範囲をカバーする更新を正確に集計することが保証されます。 これにより、再構築後、配列内のすべての要素が、それに適用されたすべての有効な更新の合計を 1 回だけ反映することが保証されます。 次に、並べ替えによって問題が静的な順序統計クエリに変換され、各クエリは決定論的なインデックス検索によって回答されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q, m = map(int, input().split())
    a = list(map(int, input().split()))

    df = [0] * (n + 1)

    for _ in range(q):
        l, r, d = map(int, input().split())
        df[l - 1] += d
        if r < n:
            df[r] -= d

    cur = 0
    for i in range(n):
        cur += df[i]
        a[i] += cur

    a.sort()

    out = []
    for _ in range(m):
        k = int(input())
        out.append(str(a[n - k]))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```実装は差分配列ロジックに正確に従います。 重要な点は、一貫して 0 から始まるインデックスに変換することです。 でのアップデート$L$になる`df[l - 1] += d`、およびでのキャンセル$R+1$になる`df[r] -= d`インデックスを 1 つシフトすると境界が正しく整列するためです。 

プレフィックス累積変数`cur`位置にあるすべてのアクティブな更新の累計を表します$i$。 各配列要素は適切な場所で更新され、余分なメモリが回避されます。 

並べ替え後、配列の末尾からの直接インデックス付けを使用して、クエリは一定時間内に応答されます。

    df = [0] * (n + 1)

    res = []
    for _ in range(m):

        res.append(str(a[n - k]))

    return "\n".join(res)

assert run("1 0 1\n5\n1\n") == "5"

# single update full range
assert run("3 1 1\n1 2 3\n1 3 10\n1\n") == "13"

# overlapping updates

# all equal final

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、更新がまさに最後の要素で終了する場合です。 例えば、$N=4$アップデートあり$(2,4,d)$。 正しい動作は、配列の境界外では減算が発生しないことです。 実装はチェックすることでこれを処理します。`if r < n`申請する前に`df[r] -= d`、無効なインデックスがアクセスされず、効果が境界で正確に停止することが保証されます。 

もう一つのケースは次のような場合です。$K = N$、最小の要素が要求されることを意味します。 並べ替え後、アクセスすると、`a[n - k]`になる`a[0]`、それは正しいです。 この境界により、1 ベースのクエリ定義と 0 ベースの配列の間で変換するときに、off-by-one エラーが発生することがよくありますが、インデックス付けの式では一貫してランクが位置にマップされます。 

最後のケースは、すべての更新がキャンセルされるか、同じ値が生成される場合です。 並べ替えは引き続き正しく動作し、順序統計は一意性ではなく位置のみに依存するため、要素の繰り返しはインデックス作成に影響しません。
