 ## 解決策
 ## 問題の理解

 私たちには、秒単位で測定されるタイムラインにわたって生き残るキャラクターが与えられます。 開始時に、彼にはいくつかの最大健康上限と初期健康量があります。 1秒経過するごとに彼の健康状態は1単位ずつ減少し、健康状態がゼロになった場合、彼は死亡したものとみなされます。 

敵は複数存在し、各敵を倒すまでに一定回数攻撃する必要があります。 キャラクターは 1 秒あたり 1 回の攻撃を実行し、毎秒どの敵を攻撃するかを選択できます。 敵が必要な攻撃をすべて受けると、すぐに敗北とみなされ、健康回復ボーナスが与えられますが、健康の合計が元の最大上限を超えることはできません。 

重要な問題は、敵全体に攻撃を分散する方法を選択している間、時間が継続的に体力を消耗し続けることです。 この消耗を相殺する唯一の方法は、敵を早く終わらせることです。敵を完了すると体力が即座に回復するためです。 問題は、プロセス全体でキャラクターの体力が決してゼロにならないような、すべての敵にわたるヒットの順序が存在するかどうかです。 

制約が十分に大きいため、秒ごとのアクションをシミュレートするソリューションは不可能です。 すべてのテスト ケースの合計ヒット数は 200,000 に達する可能性があり、これは、実行可能なソリューションでは、各敵を個々の秒単位でシミュレートするのではなく、時間のブロック全体として扱う必要があることを直ちに示唆しています。 

構造化せずに貪欲な直感を適用すると、微妙な失敗例が現れます。 たとえば、早い段階で大きな回復を持つ敵を優先しても、必要な時間が長すぎると失敗する可能性があります。これは、敵の実行中に報酬を得る前に体力がゼロになる可能性があるためです。 逆に、背の低い敵だけに集中すると、大安定回復が遅れすぎると失敗する可能性があります。 正確さは、個々のヒットではなく、タスク全体の順序に依存します。 

最も重要な問題は、生存が費やした時間と得られる健康状態の間の継続的なバランスに依存しており、このバランスは完了した作業のすべてのプレフィックスでマイナスでない状態を維持する必要があることです。 

## アプローチ

 直接シミュレーションでは、毎秒ヒットを割り当て、そのたびに体力を更新し、どの敵を攻撃するかについて可能な選択肢をすべて試してみます。 毎秒最大 n 個の選択肢が提供され、合計秒数はすべての ti の合計に等しいため、これは構造的に明らかに指数関数的です。 たとえ最適化されたとしても、この視点は基本的に粒度が細かすぎます。 

正しい抽象化は、各敵を ti 単位の時間を消費するジョブとして扱い、完了すると 1 回限りの体力増加を提供することです。 ジョブの処理中、ヘルスは時間の経過とともに継続的に減少し、完了時点でのみ増加します。 これにより、問題は、スケジュールのすべてのプレフィックスで蓄積された健全性がゼロを下回らないようにジョブの順序を決定することに変わります。 

順序を修正すると、k 人の満員の敵を処理した後の現在の体力という単一の量を追跡できます。 安全のための条件は、各敵を倒す直前に、時間のロスと以前の獲得後の残りの体力がマイナスでないことです。 これにより、問題はプレフィックスの実現可能性制約に変換されます。 

重要な洞察は、各ジョブには 2 つの競合する効果があるということです。 長い ti は、報酬が得られる前に生存時間を消費するため危険です。 大きな Hi は役に立ちますが、それは完了後に限られます。 したがって、健康状態を早期に安定させるという点で「効率的」なジョブは最初に実行されるべきですが、時間のかかるジョブは、十分な補償がない限り遅らせる必要があります。

これは当然、量 ti − hi によって捉えられる、実行中にバランスを悪化させるジョブの正味の傾向によるソートにつながります。 ti − hi が小さいジョブは、消費時間が短いか、コストに比べてより多くの回復が得られるため、より早くスケジュールした方が安全になります。 このように並べ替えたら、単純にプレフィックスをシミュレートし、健全性がゼロを下回らないことを確認します。

 ## アルゴリズムのチュートリアル

 1. すべての敵の値 di = ti − hi を計算します。 この値は、敵が報酬を適用する前にどれだけの「ネットダメージプレッシャー」を生み出すかを測定します。 
2. すべての敵を di の昇順に並べ替えます。 有害性が低い、または単位時間当たりの報酬が高い敵は、より早く配置されます。 
3. 現在のヘルスを m として初期化し、実行時間カウンターをゼロとして初期化します。 
4. ソートされた順序で敵を処理します。 敵ごとに、実行中の経過時間を反映して、時間を ti だけ増加させ、体力を​​ ti だけ減少させます。 
5. 敵を倒した後、再生を表すためにすぐに体力に hi を追加します。 
6. 各アップデートの後、完了直後に健全性が厳密にプラスのままであるか、または正確にゼロであるかどうかを確認します。 ヘルスがゼロを下回った場合、スケジュールは無効になります。 
7. 条件を破らずにすべての敵を処理できれば、答えは実行可能です。 

### なぜ効果があるのか

 このプロセスは、単一の接頭辞の不変条件を維持するものと見なすことができます。つまり、どの時点でも、現在のヘルスは、初期ヘルスから費やした合計時間、完了した敵から得られる再生の合計を差し引いた値に等しくなります。 この値が回復できるのは完了ポイントのみであるため、タイムライン上の最小値は常に敵を完了する直前または直後に発生します。 

ti − hi で並べ替えることで、遅らせたほうが危険な敵を早期に処理できるようになり、長期にわたる高報酬の仕事が延期されて早期の枯渇を引き起こす状況を防ぐことができます。 2 つの隣接する敵の間でこの順序を逆転しても、実現可能性は向上しないことが示されています。これは、順序に違反するペアを交換しても、報酬を遅らせながら時間的プレッシャーを後でシフトさせるだけであり、これにより、初期のプレフィックスでの生存が弱まるからです。 これにより、ソートされた順序が非負の正常性プレフィックスを維持するのに最適であることが確立されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        enemies = []
        for _ in range(n):
            ti, hi = map(int, input().split())
            enemies.append((ti - hi, ti, hi))
        
        enemies.sort()
        
        health = m
        time_spent = 0
        ok = True
        
        for _, ti, hi in enemies:
            time_spent += ti
            health -= ti
            health += hi
            if health < 0:
                ok = False
                break
        
        print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()
```コードは、派生優先度キー ti 〜 hi を使用して各敵をエンコードし、それに応じて並べ替えます。 シミュレーションは毎秒明示的にモデル化するわけではありません。 代わりに、各敵を 1 つのトランジションに圧縮し、時間と体力が一括で更新されます。 

実装の微妙な詳細は、減算と加算の順序です。 健康状態は報酬が付与される直前の時点で評価されるため、再生を適用する前に時間を減算する必要があります。 これは、継続的な衰退により死が起こるが、完了するとすぐに治癒が適用されるという問題のステートメントと一致します。

 ## 特殊なケース

 再生イベントの直前に健康状態がちょうどゼロに達した場合、微妙なケースが発生します。 再生成は完了時に即座に適用されるため、実装ではこれを安全なものとして扱います。 たとえば、体力が 1 で、次のタスクに 1 秒かかる場合、完了時に体力はゼロになりますが、報酬はすぐに適用され、回復することができます。 

非常に大きな hi が非常に大きな ti と組み合わされると、別のエッジ状況が発生します。 単純な戦略では、その報酬を理由に早期に優先順位を付けようとする可能性がありますが、正しい順序で実行すると、その利点に比べて過度の時間が消費される場合、戦略が遅れます。 このようなタスクは ti − hi が大きく、後でプッシュされるため、ソート ルールはこれを自動的に処理し、長時間の実行中に早期に枯渇するのを防ぎます。 

最後に、m が個々の ti 値と比較して小さい場合は、順序付けが重要である理由を強調しています。 全体的な修復が全体的に十分である場合でも、初期の選択が間違っていると、後の報酬が現れる前にプロセスを強制終了する一時的な欠陥が生じる可能性があります。これは、貪欲な順序付けによって、高圧のタスクを初期のプレフィックスから遠ざけることで明示的に回避されます。
