 ## 解決策
 ## 問題の理解

 ビデオブロガーのシーケンスが固定された順序で与えられています。 各ブロガーには閾値があります`a[i]`。 左から右にブロガーにアプローチする場合、ブロガーはマーケターによって明示的に納得されている場合、またはブロガーに到達する前にすでに記録されているレビューの数が少なくとも`a[i]`。 

私たちができる重要なコントロールは、一部のブロガーを事前に「説得」できることです。 確信を持ったブロガーは、しきい値条件に関係なく常にレビューを作成します。 残りは受動的であり、現在の累積レビュー数がしきい値に達した場合にのみレビューを生成します。 

このプロセスは連続的であり、一度ブロガーを通り過ぎると、二度と戻ることはできません。 目標は、最終的に少なくとも次のことを保証することです。`m`レビューが表示されるため、強制的に説得するブロガーの数を最小限に抑えたいと考えています。 

入力サイズは極端です: 最大`n = 5 × 10^7`。 これにより、メモリ内に線形時間で配列を明示的に格納または処理するものは直ちに除外されます。 重い定数を含む O(n log n) でも境界線に達します。 制約構造は、次のことを強く示唆しています。`a[i]`シーケンスは明示的に与えられるのではなく、その場で生成されます。つまり、シーケンスを保存せずにストリーミングで処理する必要があります。 

素朴な解釈では、ブロガーのすべてのサブセットを説得しようとすることになりますが、n 人の中から k 人のブロガーを選択するだけでも指数関数的になります。 もう少し合理的な試みは、答えを二分探索することです。`x`ブロガーに到達できるかどうかをシミュレーションする`m`レビュー。 これは O(n log n) ですが、5 × 10^7 にはまだ遅すぎます。 

素朴な推論を打ち破るエッジケースは、多くの場合、順序付け効果から生じます。 たとえば、遅いブロガーを説得することは通常、初期のブロガーよりも価値がありますが、常にそうとは限りません。 初期のしきい値は小さいが、後のしきい値が急上昇する状況を考えてみましょう。 最適な戦略には、初期の説得をいくつかスキップして、後の自動トリガーのロックを解除することが含まれる場合があります。 

もう一つの微妙なケースは次のような場合です。`m`小さいです。 もし`m = 1`の場合、答えは常に 1 です。1 人のブロガーを説得すると必要なレビューが即座に生成されますが、貪欲な推論やしきい値ベースの推論では不必要な伝播をシミュレートする可能性があるためです。 

## アプローチ

 この強引なアイデアは、どのブロガーを説得するかを選択し、そのプロセスをシミュレーションしてみるというものです。 固定の選択の場合、左から右にスキャンし、現在あるレビューの数を維持し、作成されたレビューの数を数えます。 これはプロセス定義に直接従うため、正しいです。 問題は、サブセットの数が 2^n であることですが、これは不可能です。 

より構造化された改善点は、どのブロガーを説得するか、また、リーチできるかどうかではなく、何人のブロガーを説得するかだけを気にしていることを観察することです。`m`最大でもレビュー`k`強制アクティベーション。 これはバイナリ検索を示唆しています`k`。 固定の場合`k`、実現可能性を確認したいと考えています。 

実現可能性のチェック自体が中核的な難しさになります。 どちらかを決める必要があります`k`ブロガーは、プロセスが少なくとも`m`レビュー。 重要な観察は、強制ブロガーを最適に選択できるのであれば、強制ブロガーを即時レビューの投稿として扱うべきである一方、受動的ブロガーは現在のカウントがしきい値に達した場合にのみ投稿する必要があるということです。 

これは貪欲なスケジューリングの問題になります。左から右にスキャンするときに、現在のレビュー数の増加を最大化したいと考えます。 すでにしきい値を満たしているブロガーに遭遇すると、彼らは自動的に投稿します。 それ以外の場合、強制スロットがまだ残っている場合は、それらを「アクティブ化」することを選択できます。 

最適な戦略は、選択を迫られた場合に、最も有益なブロガーに対して常に強制アクティベーションを使用することです。 これは、現在アクティブ化できないが強制できる候補の構造を維持し、遅れを防ぐために必要な場合にのみ強制選択を使用することによってモデル化できます。 

ただし、さらに深い単純化が存在します。バイナリ検索の代わりに、貪欲不変式を使用して強制アクティベーションの最小数を直接シミュレートできます。 私たちはレビューの数を維持しており、しきい値を満たしていないブロガーに遭遇したときはいつでも、そのブロガーを潜在的な強制候補者として扱いますが、確実に達成に向けて前進するために必要な場合にのみコミットします。`m`。 

重要な洞察は、プロセスが単調なシステムのように動作するということです。つまり、ブロガーが一度合格できるようになると (現在のレビューがしきい値以上)、ブロガーは常に合格のままになります。 これにより、シーケンスを 1 パスの貪欲な累積問題として扱うことができ、チェーンの進行を維持するためにレビューを「注入」する必要がある場合のみ決定します。

 ## アルゴリズムのチュートリアル

 現在のレビュー数という 2 つの値を維持しながら、生成されたシーケンスをオンザフライで処理します。`cur`、および使用された強制ブロガーの数`ans`。 

また、私たちは実現可能性について指針のような考え方を維持しています。つまり、まだ達成していない限り継続するだけです。`m`レビュー。 

1.初期化`cur = 0`そして`ans = 0`。 私たちはレビューも強制的な決定も行わずにスタートします。 これは、まだ何も処理されていないことを示しています。 
2. ブロガーを順番に繰り返し、それぞれを生成します`a[i]`LCGルールを使用します。 
3. もし`cur >= m`, 追加のレビューによって答えが変わるわけではないため、早期に終了することができます。 この剪定は大規模な植物にとって非常に重要です`n`。 
4. 各ブロガーについて、次のことを確認します。`cur >= a[i]`。 「はい」の場合、このブロガーは自然にレビューを生成するため、増加します`cur`。 
5. もし`cur < a[i]`、このブロガーは納得しない限りレビューは作成しません。 これを強制アクティベーションとして扱い、両方をインクリメントします。`cur`そして`ans`。 
6. どちらかに到達するまで続けます`n`ブロガーとか`cur >= m`。 

重要な構造上の考え方は、すべての強制アクティベーションが直接的に増加するということです。`cur`、自然なプロセスが続行できない場合にのみ、そのコストを支払います。 早期に増加するため、強制アクティベーションを遅らせてもメリットはありません。`cur`後のしきい値を簡単にするだけです。 

### なぜ効果があるのか

 プロセスのどのプレフィックスであっても、重要な状態は、すでに作成されたレビューの数だけです。 ブロガーが受動的であるか強制的であるかの決定は、その瞬間にその閾値が満たされているかどうかによってのみ決まります。 ブロガーに強制すると増えるだけなので`cur`、将来のブロガーを満足させるのが難しくなることは決してありません。 したがって、強制アクティベーションを延期することは決して有益ではなく、必要なときに正確に貪欲に強制することで、強制されるブロガーの数は最小限に抑えられます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a1, k = map(int, input().split())

    # read LCG blocks
    params = []
    for _ in range(k):
        cj, xj, yj, zj = map(int, input().split())
        params.append((cj, xj, yj, zj))

    cur = 0
    ans = 0

    ai = a1
    block_id = 0
    used_in_block = 0
    cj, xj, yj, zj = params[0] if params else (n-1, 0, 0, 1)

    for i in range(1, n + 1):
        if i == 1:
            ai = a1
        else:
            # move to correct block
            while used_in_block == cj:
                block_id += 1
                used_in_block = 0
                cj, xj, yj, zj = params[block_id]
            ai = (xj * ai + yj) % zj
            used_in_block += 1

        if cur >= m:
            break

        if cur >= ai:
            cur += 1
        else:
            cur += 1
            ans += 1

    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、生成されたシーケンスを保存せずに直接ストリーミングします。 LCG 生成はブロック境界を尊重し、現在のブロックが`cj`カウントが尽きました。 

核となる決定は、`if cur >= ai`支店。 現在のレビュー数が十分であれば、ブロガーは自然に投稿します。 それ以外の場合は、ユーザーを説得するシミュレーションを行い、レビュー数と回答の両方を増加させます。 

早期停止の場合`cur >= m`不必要なサフィックスを決して処理しないようにします。これは、極端な上限を考慮すると不可欠です。`n`。

これは、現在のプレフィックスがしきい値を満たせない場合にのみ強制が使用され、十分な増加が発生すると、後の制約は無関係になることを示しています。

 ## 特殊なケース

 重要なエッジケースは、最初のブロガーがすでに高いしきい値を持っている場合です。 たとえば、次の場合`a[1] = 10`そして`cur = 0`、アルゴリズムはすぐにこのブロガーを強制します。 これにより、プロセスでレビューの蓄積を開始できるようになります。 

もう 1 つのケースは、しきい値がすべてゼロなど、非常に小さい場合です。 すべてのブロガーが満足するため、アルゴリズムは強制をトリガーしません。`cur >= a[i]`最初から。 答えはゼロのままで、介入は必要ないという直観と一致します。 

最後の重要なケースは早期終了です。 仮定する`m`規模は小さく、最初の数回の強制アクティベーション内で達成されます。 ループはすぐに中断され、最大 5 × 10^7 の生成値の不必要な処理が防止されます。これは、制限時間内のパフォーマンスの正確性にとって不可欠です。
