 ## 解決策
 ## 問題の理解

 固定の参照文字列が与えられ、多くの短いクエリ文字列を処理するように求められます。 クエリごとに、クエリ文字列を参照に一時的に追加し、結果の連結でプレフィックス関数を計算し、追加された部分に対応するプレフィックス関数の値のみを出力します。 各クエリの後、状態は元の参照文字列にリセットされます。 

重要な問題は、位置上の接頭辞関数が$i$で終わるプレフィックスの最長の境界線に依存します。$i$、これは、以前のプレフィックス関数の値と文字の比較に依存します。 クエリごとにすべてを最初から再計算すると、最大長の長い基本文字列を繰り返しスキャンすることになります。$10^6$、これは不可能です。$10^5$クエリ。 

この制約は、どのソリューションでも基本文字列を前処理された構造として扱い、クエリの長​​さにのみ比例して時間内に各クエリを処理する必要があることを意味します。 各クエリ文字列の長さは最大 10 であるため、クエリごとの追加作業の合計は次のようになります。$O(|t|)$そうでない場合、ソリューションは制限を超えます。 

単純な実装では、次のプレフィックス関数を再計算します。$s+t$クエリごとに完全に表示されます。 それだけですでに次のことを意味します$10^6 + 10$クエリごとの作業、繰り返し$10^5$これは許容範囲をはるかに超えています。 

接尾辞部分のみを再計算しようとして、それでも完全な接頭辞と繰り返し比較する場合、より微妙な失敗ケースが発生します。$s$永続的なオートマトンや圧縮された遷移構造を維持する必要はありません。 プレフィックス関数は 1 ステップで何度も「ジャンプバック」できるため、完全な文字列に対する文字ごとのシミュレーションは、最悪の場合、線形動作に低下する可能性があります。 

たとえば、次の場合$s = aaaa\ldots a$そして$t = aaaaa$、すべてのプレフィックス関数ステップは、一致の長いチェーンを繰り返しフォールバックします。 毎回逆方向にスキャンする単純なループは、すべてのクエリにわたって最悪の場合には 2 次になります。 

## アプローチ

 ブルート フォースのアイデアは単純です。クエリごとに、フォームを作成します。$s+t$、標準の線形 KMP プロシージャを使用してプレフィックス関数を計算し、最後の関数を出力します。$|t|$価値観。 これは正しいです。プレフィックス関数は純粋に連結された文字列に基づいて定義され、クエリ構造には依存しないからです。 

問題はコストです。 それぞれの計算は$O(|s|+|t|)$、だから向こう側$q$これはクエリになります$O(q|s|)$、それは約です$10^{11}$最悪の場合の運用。 これでは通れません。 

重要な観察は、プレフィックス関数の計算が、プレフィックス関数の障害リンクによって定義されたオートマトンの中を歩くのと同等であるということです。 各プレフィックスの長さを状態として解釈すると、新しい文字ごとに遷移が発生します。現在の文字によって拡張できる状態が見つかるまで、失敗リンクを繰り返したどります。 

この構造は前処理を示唆しています。すべての状態に対して構築します。$v$そしてすべての手紙$c$、現在状態にある場合の次のプレフィックス関数の状態$v$そして読んでください$c$。 これはまさに KMP オートマトンです。 構築されると、各クエリは、完全な文字列に対応する状態から始まるこのオートマトンに対する単純なシミュレーションになります。$s$。 

まず、次のプレフィックス関数を計算します。$s$。 これにより開始状態が得られます$cur = p[|s|]$。 次に、障害リンクを使用して遷移を事前計算します。 その後、クエリ内の各文字は次のように処理されます。$O(1)$、次のプレフィックス状態を即座に生成し、それを出力します。 

これにより、問題は線形前処理とすべてのクエリ文字に対する合計線形作業に集約されます。

 ## アルゴリズムのチュートリアル

 1. 基本文字列の接頭辞関数を計算します。$s$。 これにより、あらゆる位置のサフィックスでもある最長の適切なプレフィックスにジャンプできる障害リンクが得られます。 
2. 各プレフィックス長の処理$v$オートマトン内の状態として。 州から$v$、文字を追加するとどこになるかを知りたいです。$c$。 
3. 遷移テーブルを事前計算する`nxt[v][c]`すべての州にとって$v$そして手紙$c$。 正しく計算するために、一致を最初から再計算するのではなく、失敗リンクを介して以前に計算された遷移を再利用します。 
4. クエリの初期状態を次のように設定します。`cur = p[len(s)]`これは、ベース文字列全体を読み取った後の最長の接頭辞と接尾辞の一致を表します。 
5. 各クエリ文字列について$t$、文字を 1 つずつ処理します。 

1.アップデート`cur = nxt[cur][t[i]]`。 
2. 出力`cur`連結された文字列内のその位置のプレフィックス関数値として。 
6. クエリを終了した後は、何もリセットしないでください。`cur`すでに後の状態を表しています$s$、各クエリは独立しています。 

正確さは、オートマトンの遷移がプレフィックス関数の更新ルールを正確にエンコードしているという事実にかかっています。常に次の文字によって拡張できる最長のプレフィックスに移動し、失敗リンクにより無効な一致が効率的にスキップされます。 

### なぜ効果があるのか

 どの時点でも、変数は`cur`最長のプレフィックスの長さを表します$s + t_{processed}$これはその文字列の接尾辞でもあります。 これはまさにプレフィックス関数の状態の定義です。 移行ルールは、すべての更新が現在一致するプレフィックスを拡張するか、有効な拡張が見つかるまで障害リンクに沿ってフォールバックするため、この不変状態を維持します。 障害リンクは常に境界プロパティを保持するため、有効な候補はスキップされず、結果の状態は常に最大になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_pi(s):
    n = len(s)
    pi = [0] * n
    for i in range(1, n):
        j = pi[i - 1]
        while j > 0 and s[i] != s[j]:
            j = pi[j - 1]
        if s[i] == s[j]:
            j += 1
        pi[i] = j
    return pi

def build_automaton(s, pi):
    n = len(s)
    nxt = [[0] * 26 for _ in range(n + 1)]

    for v in range(n + 1):
        for c in range(26):
            if v < n and ord(s[v]) == ord('a') + c:
                nxt[v][c] = v + 1
            else:
                if v == 0:
                    nxt[v][c] = 0
                else:
                    nxt[v][c] = nxt[pi[v - 1]][c]
    return nxt

def solve():
    s = input().strip()
    q = int(input())
    pi = build_pi(s)
    nxt = build_automaton(s, pi)

    cur = 0
    for ch in s:
        cur = nxt[cur][ord(ch) - 97]

    out = []
    for _ in range(q):
        t = input().strip()
        ans = []
        for ch in t:
            cur = nxt[cur][ord(ch) - 97]
            ans.append(str(cur))
        out.append(" ".join(ans))
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、まずベース文字列のプレフィックス関数を構築し、次に KMP オートマトンの完全な遷移テーブルを構築します。 各状態はプレフィックスの長さに対応し、遷移は文字を読み取った後に次に可能な境界の長さをエンコードします。 

微妙な点は、`nxt`。 文字がプレフィックス内の予期される次の文字と一致しない場合、すぐにゼロから再開しません。 代わりに、失敗リンクをたどります。`pi[v-1]`、次善の境界候補を表します。 この再帰により、文字を再チェックすることなく正確さが保証されます。 

もう 1 つの詳細は、次の初期化です。`cur`オートマトンを通じてベース文字列を再生することによって。 これにより、処理後のプレフィックス関数の状態との一貫性が保証されます。$s$、前処理とクエリ シミュレーション間の不一致を回避します。

 ## 特殊なケース

 エッジ ケースの 1 つは、クエリ文字が既存の一致をすべて直ちに破棄する場合です。 たとえば、次の場合$s = "aaaa"$そしてクエリは次で始まります$b$、オートマトンは状態 0 に直接ジャンプし、そこに留まるはずです。 すべての不一致パスは最終的にルート状態に到達するため、遷移テーブルによってこれが保証されます。 

もう 1 つのエッジ ケースは、クエリが元の文字列の長さを超えて一致を継続的に拡張する場合です。 もし$s = "abc"$そして$t = "abcabc"$、オートマトンは以前のプレフィックスを新しい境界線として正しく再利用する必要があります。 障害リンク チェーンは、完全な一致長に達した後、間違って再開されるのではなく、正しい境界からさらなる一致が継続されることを保証します。 

最後のエッジケースは最小限の入力です。$s$この場合、すべての遷移は、一致する文字の場合は状態 1 に進み、そうでない場合は状態 0 に進みます。 オートマトンは 2 状態マシンに正しく縮退し、ロジックは一般的なケースと一貫性を保ちます。
