 ## 解決策
 ## 問題の理解

 プロジェクトのコレクションが与えられ、プロジェクトごとにそれを実行するための相互に排他的な方法がいくつかあります。 それぞれの方法にはコストと収益があります。 すべてのプロジェクトについて、利用可能な方法の 1 つを正確に選択するか、プロジェクトを完全にスキップする必要があります。 選択したすべての方法の総コストは世界予算を超えてはなりませんが、目標は収益の合計を最大化することです。 

構造を再解釈する便利な方法は、各プロジェクトが項目の小さな「選択グループ」を提供することです。 各グループから 1 つの項目を取得するか、何も取得しません。 各項目にはコストに等しい重みと収益に等しい価値があります。 制約は、すべてのグループで共有される 1 つのナップザックの容量ですが、各グループから複数のアイテムを取得できないという追加の制限があります。 

制約は意図的に非対称になっています。 プロジェクトの数は最大 20 で、すべてのプロジェクトにわたるオプションの合計数も最大 20 です。ただし、予算は最大 10^9 と非常に大きくなる可能性があるため、ディメンションとして予算に依存する DP は直ちに除外されます。 コスト状態を反復しようとするソリューションは、メモリと時間の両方で失敗します。 

これにより、全体の難しさが容量ベースのナップザックから項目またはグループのサブセット列挙へと移行します。 

プロジェクトに高価なオプションしかなく、スキップが最適な場合には、微妙なエッジケースが発生します。 たとえば、プロジェクトにオプション (収益 100、コスト 10) と (収益 80、コスト 9) があり、予算が 5 の場合、両方のオプションは実行不可能であるため、正しい動作はプロジェクトを完全にスキップし、そこから収益が 0 になることです。 「プロジェクトごとに 1 つのオプションを選択する必要がある」と想定した単純な実装では、誤って予算を超える選択が強制されてしまいます。 

もう 1 つのエッジケースは、すべてのコストがゼロの場合です。 そうすれば、すべてのプロジェクトを自由に実施でき、予算は無関係であるため、最適な答えは単にプロジェクトごとの最良の収益オプションの合計になります。 このケースでは、コスト制約を厳密ではなくオプションとして誤って扱う実装も明らかになります。 

最後に、すべてのプロジェクトにわたるオプションの合計は小さいため、重要な構造上のヒントは、すべての個々のオプションをグローバル サブセット問題のアトミックな項目として扱うことができますが、同じプロジェクトから 2 つの項目を決して選択しないようにする必要があるということです。 

## アプローチ

 直接的なアプローチは、これを DP ディメンションとしての予算を持つ複数選択のナップザックとして扱うことです。 これにより、最初の i プロジェクトと予算 b の後の最高の収益を表す dp[i][b] のような状態が得られます。 b は 10^9 に達するため、単一の DP 層ですら実行不可能であるため、これは直ちに不可能です。 

観測されたコストのみを使用して予算を圧縮することもできますが、コストは 10^9 までは任意であり、合計の制限がないため、それでも役に立ちません。 

重要な観察は、選択肢の総数がわずか 20 であることです。これは、利用可能なすべてのオプションのサブセットを指数関数的に列挙できるほど十分に小さいです。 ただし、20 項目にわたる単純なサブセット列挙では、2^20 (約 100 万) の可能性が得られ、完全に許容可能です。 

複雑なのはプロジェクトごとの制約です。同じプロジェクトに属する 2 つのオプションを選択することはできません。 これは、プロジェクトの競合の観点からサブセットの実現可能性をエンコードする必要があることを示唆しています。 

これを解決するきれいな方法は、各オプションをプロジェクト インデックスでラベル付けされた項目として扱うことです。 次に、すべてのオプションのサブセットを列挙し、2 つの項目がプロジェクトを共有していないことを確認して、サブセットごとに妥当性をチェックします。 有効な場合、総コストと収益を計算し、予算の実現可能性を確認します。 

項目の合計は 20 しかないため、各サブセットのチェックは O(20) であり、合計は O(20 * 2^20) となり、効率的です。

別の観点としては、プロジェクトのサブセットに対してプロジェクトごとに DP をグループ化することですが、各プロジェクトには複数のオプションがあるため、サブセットのフラット化と検証の方が簡単でエラーが発生しにくくなります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | コストよりも予算の DP | O(n・b) | O(b) | b が 1e9 までなので不可能 |
 | すべてのオプションのサブセット列挙 | O(2^m・m) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. 使用可能なすべてのオプションを 1 つのリストに収集します。各オプションにはプロジェクト ID、コスト、収益が格納されます。 すべてのオプションを省略するサブセットを許可することで、プロジェクトのスキップを暗黙的に含めるものとして扱います。 
2. 0 ～ 2^m − 1 のビットマスクを使用して、これらのオプションのすべてのサブセットを反復します。ここで、m はオプションの総数です。 
3. サブセットごとに、ブール配列またはビットマスクを使用してプロジェクトがすでに選択されているかどうかを追跡します。 同じプロジェクトに属する 2 つのオプションが見つかった場合、このサブセットは直ちに破棄されます。 これにより、不正な構成が防止されます。 
4. 有効なサブセットをスキャンしながら、総コストと総収益を累積します。 この増分計算により、最初から再計算するのではなく、各サブセットの評価が O(m) になることが保証されます。 
5. 総コストが予算内にある場合は、これまでに確認された最大収益で回答を更新します。 

事前フィルタリングではなく反復中に明示的に検証する理由は、競合が個々の項目単独ではなく、選択した項目の組み合わせに依存するためです。 

### なぜ効果があるのか

 すべての実現可能なソリューションは、プロジェクトごとに最大 1 つのオプションを含み、総コストが予算を超えないオプションのサブセットに正確に対応します。 このアルゴリズムはオプションのすべてのサブセットを列挙するため、実行可能なすべての解決策を確実に列挙します。 妥当性チェックでは、プロジェクトごとに 1 つのオプションのルールに違反するサブセットが正確に除外され、予算チェックでは実現可能性が強制されます。 すべての有効な構成の収益を評価するため、記録された最大値は最適なソリューションと等しくなる必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, b = map(int, input().split())
    items = []

    for i in range(n):
        k = int(input())
        for _ in range(k):
            r, c = map(int, input().split())
            items.append((i, c, r))

    m = len(items)
    ans = 0

    for mask in range(1 << m):
        used_projects = 0
        total_cost = 0
        total_rev = 0
        ok = True

        for j in range(m):
            if mask & (1 << j):
                pid, cost, rev = items[j]

                if used_projects & (1 << pid):
                    ok = False
                    break

                used_projects |= (1 << pid)
                total_cost += cost
                total_rev += rev

        if ok and total_cost <= b:
            if total_rev > ans:
                ans = total_rev

    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、プロジェクトのアイデンティティを維持しながら、すべてのプロジェクト オプションを単一の配列に平坦化します。 サブセット列挙では、これらのオプションに対してビットマスクが使用されます。 マスクごとにプロジェクト使用ビットマスクを維持し、選択されたオプションを複数提供するプロジェクトがないことを保証します。 

コストと収益のアキュムレータは単純な合計です。 予算チェックは妥当性を確保した後にのみ実行されるため、無駄な比較が回避されます。 

実装の微妙な詳細は、プロジェクトの使用にセットではなく別のビットマスクを使用することです。 これにより、項目ごとにチェック O(1) が維持され、Python のオーバーヘッドが回避されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, b = map(int, input().split())
    items = []
    for i in range(n):
        k = int(input())
        for _ in range(k):
            r, c = map(int, input().split())
            items.append((i, c, r))

    m = len(items)
    ans = 0

    for mask in range(1 << m):
        used = 0
        cost = 0
        rev = 0
        ok = True

        for j in range(m):
            if mask & (1 << j):
                pid, c, r = items[j]
                if used & (1 << pid):
                    ok = False
                    break
                used |= (1 << pid)
                cost += c
                rev += r

        if ok and cost <= b:
            ans = max(ans, rev)

    return str(ans)

# sample-like
assert run("2 10\n2\n100 10\n80 9\n1\n10 1\n") == "100"

# single project
assert run("1 5\n2\n50 3\n40 2\n") == "50"

# zero budget
assert run("1 0\n1\n10 0\n") == "10"

# all too expensive
assert run("2 1\n1\n10 5\n1\n20 6\n") == "0"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | サンプルっぽい | 100 | 無効なサブセットの正しいプルーニング |
 | 単一プロジェクト | 50 | プロジェクトごとの選択の処理 |
 | 予算ゼロ | 10 | ゼロコスト境界動作 |
 | あまりにも高価すぎる | 0 | すべてのプロジェクトをスキップします |

 ## 特殊なケース

 エッジケースの 1 つは、予算がゼロの場合です。 アルゴリズムは依然としてサブセットを列挙しますが、総コストがゼロのサブセットのみが生き残ります。 これにより、収益がゼロになるか、コストがゼロのオプションが存在する場合、そのいずれかが正しく生成されます。 

もう 1 つのケースは、プロジェクトに複数の安価なオプションがあるにもかかわらず、1 つだけを選択する必要がある場合です。 プロジェクト ビットマスクにより、同じプロジェクトから 2 つのオプションを選択するサブセットは即座に拒否されるため、両方が個別に手頃な価格であっても、一緒に貢献することはありません。 

最後のケースは、すべてのオプションが高価である場合です。 サブセット ループは引き続き実行されますが、空でないすべてのサブセットはバジェット チェックに失敗し、空のサブセットのみが有効なままとなり、出力が 0 になります。
