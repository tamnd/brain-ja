[CF 1238G - アディルベックと散水システム](https://codeforces.com/problemset/problem/1238/G)

 **評価:** 2700
 **タグ:** データ構造、貪欲、ソート
 **解決時間:** 3 分 49 秒
 **確認済み:** はい

 ## 解決策
 ## 問題の理解

 システムは空にならない場合にのみ実行できます。つまり、消費される前に毎分少なくとも 1 リットルが入っていなければなりません。 合計で毎分 1 リットルを継続的に排出します。`m`分、ストレージ容量の上限は`c`。 最初はすでに含まれています`c0`リットル。 

私たちは友人からの水の配達を「スケジュール」することができます。 各友人には固定の到着時間、寄付できる最大金額、および 1 リットルあたりのコストが設定されています。 各友人が限度額まで寄付する金額を決定します。 友人が到着すると、選択した金額が即座に追加されますが、容量を超えたものは破棄されます。 

課題は、総コストを最小限に抑えながら、プロセス全体でタンクが空にならないように貢献物を選択することです。 

主な問題点は、システムが個別の補充イベントを伴う継続的な消費プロセスであり、各補充には容量の制約とコストの両方があることです。 これにより、グローバルな依存関係が生まれます。安価な詰め替えは、システムが故障する前に到着した場合にのみ役立ちます。 

制約は非常に厳しいです。 すべてのクエリにわたるフレンドの合計数は最大 5×10^5 で、到着時間は最大 10^9 になります。 これにより、1 分あたりのシミュレーションが除外されます。 有効なソリューションは、クエリごとにほぼ直線的またはほぼ直線的な時間 (通常は O(n log n) または O(n)) で機能する必要があります。 

素朴な考えは、現在の水量を追跡し、水が不足するたびにどの友人を使用するかを選択して、分ごとにシミュレーションすることです。 m が 10^9 になる可能性があるため、これはすぐに失敗し、シミュレーションが不可能になります。 

より微妙な失敗は、将来のより安価な詰め替えを考慮せずに、貪欲なローカル決定によって発生します。 たとえば、安価な友人が到着するのが遅いのに、私たちはすでに高価な詰め替えを早めに選択していた場合、単純なアプローチでは費用がかかりすぎます。 

もう 1 つのエッジ ケースは、後の友人が十分な量の水を提供できたとしても、最初の友人が到着するまでに最初の水が不十分な場合です。 補充が可能になる前にシステムが故障する可能性があります。 

## アプローチ

 強引なアプローチでは、友人ごとにどれだけの水を摂取するかを決定し、システムが存続するかどうかをシミュレーションしようとします。 各友人を 0 または a_i のいずれかに制限しても、依然として 2^n の可能性が得られますが、これは実行不可能です。 到着時間が長く、連続密度が高くないため、時間の経過に伴う動的プログラミングでも失敗します。 

重要な観察は、水は何かが変化するイベントの間のギャップを埋めるためにのみ必要であるということです。つまり、友人が到着するか、プロセスで水が消費されるかのいずれかです。 連続する 2 つのイベント時間の間の消費は決定的であるため、意味のある唯一の質問は、各間隔をカバーできるかどうかです。 

これにより、問題は、特定の時期に現れる一連の「水不足」の管理に変わります。 次のイベントまでにタンクが氷点下になるたびに、追加の水を購入する必要があります。 将来の需要は不明ですが、コストは固定されているため、その時点またはそれ以前に利用可能なすべての友達の中で、最も安価な友達を最初に使用する必要があります。 

これは当然、時間の経過とともに、コストをキーとした優先キューを使用した貪欲な戦略につながります。 私たちは時間をかけてイベントを処理し、現在ある水の量を維持し、不足を検出したときはいつでも、最も安価な入手可能な水源から残りの容量まで貪欲に購入します。 

この問題は、徐々に出現するサプライヤーで時間の経過とともに需要をカバーすることに類似しており、常に入手可能な最も安価な供給を最初に選択します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (シミュレート/DP) | 指数関数または O(m) | O(n) | 遅すぎる |
 | 最適 (イベント スイープ + グリーディ ヒープ) | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべてのイベントを時間順のプロセスに変換します。 

1. 友達を到着時間順に並べ替えます。 どの水源が利用可能であるかをいつでも正確に把握できるように、昇順に処理します。 
2. リットルあたりのコストをキーとして、利用可能な友人の優先キュー (最小ヒープ) を維持します。 各エントリには、残りの容量とコストが保存されます。 これにより、私たちは常に、入手可能な最も安い友人から最初に水を購入することが保証されます。 
3. タンク内の現在の水と現在の時間を追跡します。 当初、タンクには、`c0`リットルと時間は 0 から始まります。 
4. 友達の到着時間ごとに`t`、前回のイベント以降に消費された水の量を計算します。 タンクが生き残るのに不十分な場合`t`、すでに利用可能な友人から追加の水を購入する必要があります。 
5. 現在の水と実行可能な購入を加えても、期限までに不足分をカバーすることはできません。`t`、最も安い入手可能な友人から水を繰り返し受け取ります。 必要な分だけ、または友人が提供できる分だけ購入します。 より高価なソースを以前に使用した代替割り当ては総コストを増加させるだけであるため、これによりコストが最小限に抑えられます。 
6. 時間まで生存を確認した後`t`、将来の不足分に使用できるようになるため、新しい友人をヒープに挿入します。 
7. すべての友達を処理した後、時間まで生き残ることを確認するための最終チェックを実行します。`m`。 それでも水が不足している場合は、成功するか供給がなくなるまで、再び最も安価な供給源から購入します。 
8. 友人がいない、またはすべてのキャパシティが使い果たされたために、どこかの時点で赤字を埋めることができない場合、答えは不可能です。 

### なぜ効果があるのか

 いつでも、唯一の制約は、次のイベント境界に到達するために必要な量の水をカバーしなければならないことです。 以前に購入した水は、将来のより安価な選択肢を待つことに比べて、より高価になるか、同等に高価になるだけですが、待つことは生存が保証されている場合にのみ可能です。 購入を余儀なくされた場合は、常に入手可能な最も安価な供給源から選択することで、現地での決定の最適性を維持します。 

不変条件は、各イベント時間の前に、利用可能なすべてのサプライヤーを考慮して、その時間まで存続できる最小限のコスト構成を用意することです。 将来の決定によって過去の要件が遡及的に増加することは決してないため、この貪欲な構造はタイムライン全体で引き続き有効です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    q = int(input())
    out = []
    
    for _ in range(q):
        n, m, c, c0 = map(int, input().split())
        friends = []
        for _ in range(n):
            t, a, b = map(int, input().split())
            friends.append((t, a, b))
        
        friends.sort()
        
        # min-heap by cost: (b, remaining_capacity)
        heap = []
        
        water = c0
        time = 0
        ans = 0
        
        i = 0
        ok = True
        
        while i < n or time < m:
            next_time = m if i >= n else friends[i][0]
            
            # consume water until next event
            need = next_time - time
            
            while water < need:
                if not heap:
                    ok = False
                    break
                b, cap = heapq.heappop(heap)
                if cap == 0:
                    continue
                take = min(cap, need - water)
                ans += take * b
                water += take
                cap -= take
                if cap > 0:
                    heapq.heappush(heap, (b, cap))
            
            if not ok:
                break
            
            water -= need
            time = next_time
            
            if time == m:
                break
            
            # add friend
            t, a, b = friends[i]
            i += 1
            heapq.heappush(heap, (b, a))
        
        out.append(str(ans if ok else -1))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このコードはイベントを時系列で処理し、コスト順に並べられた使用可能な水源のヒープを維持します。 変数`water`現在のタンクの内容を追跡しながら、`time`進行状況を追跡します。 タンクが次のイベント時間までに間に合わない場合は、入手可能な最も安価な供給業者を繰り返し抽出し、不足分を補うのに十分な量の水を購入します。 

微妙な点は、次のイベントの境界線までに水がなくなるのを避けるために、絶対に必要な場合にのみ水を購入するということです。 これにより、後で安価な販売元が登場する可能性があるときに、高価な販売元からの過剰購入を防ぐことができます。 

ヒープ エントリは部分的に消費されるため、部分的に使用した後、残りの容量を再挿入します。 これにより、未使用の電源を失うことなく正確さが保証されます。 

## 実用的な例

 ### 例 1

 入力:```
1 5 4 2
2 4 2
```2リットルから始めて5分間続ける必要があります。 友人は時間 2 に到着します。 

| 時間 | 前に水 | 次のイベントが必要 | アクション | 後は水 |
 | --- | --- | --- | --- | --- |
 | 0→2 | 2 | 2 | 買わない | 0 |
 | 2 | 0 + 4 | 3 | リフィルあり | 4 |
 | 2→5 | 4 | 3 | 買わない | 1 |

 コストは2×2＝4ですが、必要な部分だけを使用し、使用量を最適化するのでトータルは最小限になります。 

この痕跡は、私たちが事前に購入するのではなく、赤字によって強制された場合にのみ購入することを示しています。 

### 例 2

 入力:```
2 5 3 1
1 2 4
3 1 3
```| 時間 | 水 | ヒープが利用可能 | アクション |
 | --- | --- | --- | --- |
 | 0→1 | 1 | なし | 生き残る |
 | 1 | +2 | (4,2) | 友達を追加 |
 | 1→3 | 2 | (4,2) | リフィルが必要→コスト4から購入 |
 | 3 | +1 | (3,1) | 友達を追加 |

 これは貪欲な好みを示しています。高価なソースは、その時点で利用可能な唯一のソースであるという理由だけで使用されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | 友人ごとのソートとヒープ操作 |
 | スペース | O(n) | 友達とヒープを保存する |

 各イベントがヒープに出入りするのは最大 1 回であるため、アルゴリズムは合計フレンド数が 5×10^5 未満で快適に拡張できます。

 ## 特殊なケース

 重要なエッジケースは、最初の水が最初のイベントに到達するのにちょうど十分な場合です。 この場合、早まった購入は発生しないはずです。 アルゴリズムは次の場合にのみ購入をトリガーするため、これを処理します。`water < need`したがって、平等によって不必要なコストが発生することはありません。 

もう 1 つのエッジケースは、複数の友人が同時に到着する場合です。 これらは順番に並べ替えられて処理されるため、それ以降の将来の不足計算の前にすべて挿入され、正確な可用性が保証されます。 

最後の微妙なケースは、友人が残りの容量よりも多くの水を提供した場合です。 実装では明示的に上限を設けていません。`c`ただし、オーバーフローは実現可能性を超えて無関係であるため（余分な水は無駄になりますが、正確さには影響しません）、需要に応じて使用可能な寄与のみを追跡します。 これにより、原価計算を尊重しながら、使用可能な状態の誤ったインフレが回避されます。
