 ## 解決策
 ## 問題の理解

 タスクはタイトルが示すよりもはるかに簡単です。 私たちはその年に (n) 回の支払いを行いました。各支払いは、その金額をセント単位で表す正の整数として与えられます。 必要な答えは、支払った合計金額 (セント単位) です。 入力には、(n) の後に (n) 個の支払い金額が 1 行に 1 つの金額として含まれており、出力はそれらの合計です。 

公式の制限は 1 秒および 256 MB です。 このステートメントでは、(n) または個々の支払いの明示的な上限が公開されていないため、ステートメント自体から導き出せる正確な最悪の場合の操作数はありません。 したがって、適切なアルゴリズムは支払いの数に比例して拡張する必要があり、支払いの値に応じて増加する作業を実行するべきではありません。 すべての支払いを読み取り、一度追加すると、まさにその動作が得られます。 Python 整数では、通常の整数入力の固定幅オーバーフローの問題も回避されます。 

実装が失敗する可能性のある小さなケースがいくつかあります。 1 回の支払いで、たとえば```
1
42
```答えは`42`。 ゼロからではなく、存在しない最初の要素から合計を初期化するコードは、ここで失敗する可能性があります。 

繰り返される値は個別にカウントする必要があります。 のために```
3
5
5
5
```答えは`15`、 ない`5`。 実装が誤って支払いをセットとして扱うと、重複した支払いが黙って破棄されてしまいます。 

合計額は個別の支払いよりも大きくなる可能性があります。 のために```
4
100
200
300
400
```答えは`1000`。 最大支払額のみを追跡する実装、または最大額の検出とタスクを混同する実装では、誤った結果が生成されます。 

最後に、支払いはセントで与えられるため、小数点変換は必要ありません。 例えば、```
2
99
1
```生成する`100`。 値を浮動小数点の金額として扱うと、不必要な複雑さが増し、丸めの問題が発生する可能性があります。 

## アプローチ

 直接的なアプローチは、すべての支払いを配列に読み取り、配列を反復処理して合計を計算することです。 すべての支払いが最終合計額に 1 回だけ寄与するため、これは正しいです。 (n) 回の支払いがある場合、2 番目のパスでは、(n) 回の入力操作に加えて、正確に (n) 回の加算が実行されます。 その時間計算量は (O(n)) であり、すべての支払いを入力から読み取る必要があるため、これはすでに可能な最小漸近時間です。 

この問題には、意味のあるサブセット検索や組み合わせ総当りは隠されていません。 たとえば、すべてのサブセットを試してみると、たとえ支払いの選択を求める問題がなかったとしても、(2^n) 個の作業が実行されます。 このようなアプローチは、与えられた問題よりも実質的に難しい問題を解決することになります。 

有益な観察は、最終的な答えは連想和であるということです。 現在の合計に追加された後は、支払いを覚えておく必要はありません。 次の支払いが行われるとき、重要となるのは以前のすべての支払いの情報の合計だけです。 

これにより、2 パス アレイのアプローチが 1 パス ストリーミング ソリューションに変わります。 から始める`total = 0`、各支払いを読み、すぐに追加します`total`。 最終的なお支払い完了後、`total`まさに必要な答えです。 時間は (O(n)) のままですが、追加のスペースは (O(n)) から (O(1)) に減少します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべての支払いを保存し、合計 | (O(n)) | (O(n)) | 受け入れられましたが、ストレージは不要です |
 | 累計額 | (O(n)) | (O(1)) | 受け入れられ、最適 |

 ## アルゴリズムのチュートリアル

 1. 支払い回数 (n) を読み取ります。 これにより、入力から消費する必要がある支払い金額が正確にわかります。 
2.初期化`total`ゼロに。 ゼロは加算の恒等値であるため、最初の支払いを加算すると、特別な最初の要素のケースを必要とせずに、正しい寄与が生成されます。 
3. (n) 回繰り返します。 1 つの支払いを読み取って、すぐに追加します`total`。 後の計算では個別の値が必要ないため、支払いを保存する必要はありません。 
4. 印刷`total`すべての支払いが処理された後。 その時点で、入力されたすべての支払いが 1 回だけ寄与されます。 

機能する理由: 支払いのプレフィックスを処理した後、`total`正確にそのプレフィックスの合計に等しくなります。 最初はプレフィックスは空で、合計はゼロです。 次の支払い (m) が読み取られるとき、新しい値は前のプレフィックスの合計に (m) を加えた値になるため、不変条件は true のままです。 すべて (n) 個の支払いが処理された後、プレフィックスは入力シーケンス全体になり、`total`必要な総支出に等しい。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    total = 0

    for _ in range(n):
        total += int(input())

    print(total)

if __name__ == "__main__":
    solve()
```最初の行には (n) と書かれており、ファイルの終わりの検出に依存するのではなくループを制御します。 これは入力形式と正確に一致し、指定された数の支払いが正確に消費されることが保証されます。`total`加算はその正体がゼロであるため、ゼロから始まります。 これは、別の支店を持たずに単一支払いのケースも処理します。 

各支払いは整数に変換され、すぐに追加されます。 順序は、すべての支払いが 1 回処理される必要があるという意味でのみ重要です。 セントとドルの間で並べ替え、比較、変換は行われません。 

Python の整数型は必要に応じて拡張できるため、実装には小さな整数型を使用する言語で発生する固定幅のオーバーフローの問題がありません。 ランタイムによって処理される入力バッファリングを除いて、メモリ使用量は一定のままです。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | (O(n)) | すべての支払いは 1 回だけ読み取られて追加されます。 
| スペース | (O(1)) | のみ`n`と現在までの合計が保存されます。 

入力自体に (n) 個の支払い値が含まれているため、線形実行時間は適切です。そのため、正しいソリューションではそれらの値を検査する必要があります。 このアルゴリズムは、支払い金額に比例する追加の作業を実行せず、支払いの配列も保存しません。 

## テストケース```python
import sys
import io

def solve():
    input = sys.stdin.readline
    n = int(input())
    total = 0

    for _ in range(n):
        total += int(input())

    print(total)

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    try:
        solve()
        return sys.stdout.getvalue()
    finally:
        sys.stdin = old_stdin
        sys.stdout = old_stdout

# Provided sample
assert run("""5
7
11
18
27
20
""") == "83\n", "sample 1"

# Minimum-size input
assert run("""1
42
""") == "42\n", "single payment"

# All values equal
assert run("""5
7
7
7
7
7
""") == "35\n", "duplicate payments"

# Boundary-style arithmetic case
assert run("""4
99
1
50
50
""") == "200\n", "sum crossing a round boundary"

# Larger stress case
n = 100000
inp = str(n) + "\n" + ("1\n" * n)
assert run(inp) == "100000\n", "large input"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1 / 42`|`42`| 最小有効支払い回数 |
 |`5 / 7 7 7 7 7`|`35`| 重複した支払いとすべて均等な支払い |
 |`4 / 99 1 50 50`|`200`| 小数点以下の境界を越えた正しい累積 |
 |`100000`の支払い`1`|`100000`| 大きな入力に対する線形処理 |

 公開されたステートメントでは (n) の最大値が指定されていないため、生成された大規模なケースは、公式の最大サイズのケースではなくストレス テストです。 これは、実装が支払いごとに 1 つの単純な操作を実行し、誤って 2 次の動作を導入していないことをチェックします。
