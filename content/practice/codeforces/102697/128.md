 ## 解決策
 ## 問題の理解

 少なくとも 2 つの正の分数を含む 1 つの式が与えられます。`+`すべてのペアの間。 各分数には整数の分子と分母があります。 タスクは、全体の合計を正確に評価し、結果を最小値で出力することです。 削減された分母が`1`、答えは整数としてではなく整数として出力されます。`x/1`。 

中心的な難しさは、分数の足し算の数学ではありません。 中間整数のサイズを制御します。 この問題は、最終的な答えが Java に適合することが保証されている場合でも、不注意な実装によって膨大な共通分母が作成されるように設計されています。`int`計算が効率的に行われるとき。 公式の制限はわずか 1 秒であるため、実装では、不必要に大きな共通分母を構築するのではなく、すべての入力分数に対して少数の整数演算と GCD 演算を実行する必要があります。 

個別のテスト ケース数はありません。 式全体が 1 つの入力行に表示され、分数の数が大きくなる可能性があります。 6 つの分数を含むサンプルは、問題設定者によるパフォーマンス チェックとして明示的に使用されます。 すべての分母を 1 つの巨大な積に繰り返し乗算するソリューションでは、中間値が実際の答えよりもはるかに速く増加する可能性があります。 実行結果を削減し続けるソリューションは、不必要な増加を回避します。 

一般的なエッジ ケースは、答えが整数になることです。 例えば、```
2/3 + 7/3
```価値がある`3`したがって、正しい出力は次のようになります。```
3
```不注意に実装すると、次のように出力される可能性があります。`3/1`、同じ数学的値を表しますが、必要な出力形式に従っていません。 

もう 1 つのエッジ ケースは、分母が因数を共有する場合です。 例えば、```
1/6 + 1/4
```LCMあり`12`、結果は次のようになります`5/12`。 分母を乗算すると、`24`これでも数学的に正しい結果が生成されますが、不必要に大きな中間分母が作成されます。 この間違いを多くの分数にわたって繰り返すと、中間の整数が必要以上に大きくなる可能性があります。 

3 番目のエッジ ケースは、入力部分自体が削減されない場合に発生します。 例えば、```
2/4 + 1/4
```単純に`3/4`。 この加算式は、最初の部分が減らされなくても、加算後に実行結果が減れば機能します。 すべての入力端数がすでに最下位項にあると想定する実装では、その後のすべての操作で不要な要素を静かに運ぶことができます。 

## アプローチ

 最も直接的な強引な方法は、式全体の共通の分母を 1 つ選択することです。 分数が`a1/b1`、`a2/b2`、 を通して`ak/bk`、私たちは取ることができます`B = b1*b2*...*bk`、すべての分子に適切な欠損分母因数を乗算し、結果の分子を加算し、最後に 1 回減算します。 元のすべての分数は分母を持つ同等の分数に変換されるため、これは数学的に正しいです。`B`。 

問題はそのサイズです`B`。 最終的な換算された答えが小さい場合でも、すべての分母の積が膨大になる可能性があります。 入力に次のものが含まれている場合`k`サイズのペアごとの互いに素な分母`M`、共通点は約`M^k`。 このアルゴリズムは O(k) 分数項のみを実行しますが、その算術演算は Θ(k log M) ビットの整数に対して実行されます。 Java などの固定幅言語では、最終的な答えが式に収まる値に戻るずっと前に、乗算がオーバーフローする可能性があります。`int`。 この問題は、最終的な入力値と出力値が Java の値に適合しているとしても、効率的な計算が必要であることを明示的に警告しています。`int`範囲。 

より良いアプローチは、分数を一度に 1 つずつ追加し、追加するたびに実行中の分数を減らすことです。 現在の結果が次のようになっているとします。`p/q`そして次の分数は`a/b`。 使用する代わりに`q*b`すぐに、最初に計算します`g = gcd(q,b)`。 分母の最小公倍数は次のようになります。`(q/g)*b`。 新しい分子は、まさにその分母に対して構築できます。 その後、分子と分母を GCD で割ります。 

これが機能する理由は、最終的な答えには、分母に実際に必要な共通因数だけが必要であるということです。 2 つの分母が因数を共有する場合、最小公倍数は両方のコピーを乗算するのではなく、その因数の 1 つのコピーを保持します。 加算のたびに削減すると、後で取り消される要素が式の残りの部分に引き継がれるのを防ぎます。 

この総当たり法は、共通の分母がすべての分数を正確に表すため機能しますが、その分母には最終的にキャンセルされる多くの要素が含まれる可能性があるため、失敗します。 すべての部分和自体は 1 つの約分数で表すことができるという観察により、それらの不必要な要素をすぐに破棄できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(k) 算術演算ですが、指数関数的なサイズの整数を使用する可能性があります。 O(1) 入力を超えます | 遅すぎる、またはオーバーフローが発生しやすい |
 | 最適 | O(k log V) GCD/算術演算、`V`関連する整数サイズによって制限される | O(1) 入力を超えます | 承認済み |

 ここ`k`は分数の数であり、`V`は、縮小された中間の分子と分母の大きさを表します。 GCD 演算の引数は対数です。 

## アルゴリズムのチュートリアル

 1. 完全な式を読み取り、すべての分数を抽出します。 すべての演算は加算であるため、次のトークンが含まれます。`+`は無視でき、次の形式の文字列が残ります。`numerator/denominator`。 
2. 実行結果を最初の部分から開始し、次のように保存します。`p/q`。 すぐに減らしてください。 実行分数が減少するという不変条件を維持することで、不要な要素が蓄積するのを防ぎます。 
3. 残りの端数ごとに`a/b`、計算する`g = gcd(q, b)`。 値`g`まさに、LCM で複製する必要のない 2 つの分母の部分です。 
4.セット`q1 = q/g`そして`b1 = b/g`。 新しい分母は`q1*b`、つまり`lcm(q,b)`。 
5. 両方の分数をその共通の分母に変換します。 最初の貢献者`p*b1`、新しい部分が寄与する一方で、`a*q1`したがって、新しい分子は次のようになります。`p*b1 + a*q1`。 
6. 計算によって結果の端数を削減します。`h = gcd(numerator, denominator)`両方の値を次の値で割ります`h`。 これにより、分子と分母が互いに素であるという不変式に実行結果が返されます。 
7. すべての分数が処理された後、分母が次の場合は分子を直接出力します。`1`。 それ以外の場合は印刷します`numerator/denominator`。 

### なぜ効果があるのか

 すべての反復の後、実行中のペアは`p/q`これまでに処理されたすべての分数の正確な合計を表し、`gcd(p,q) = 1`。 次の分数については`a/b`、`q/g * b`、 どこ`g = gcd(q,b)`、2 つの分母の最小公倍数です。 したがって、構築された分子は、まさにその共通の分母の合計の分子になります。 両方の部分を GCD で除算すると、値ではなく表現のみが変更されるため、不変条件は true のままになります。 最後の小数の後の実行値は要求された合計とまったく同じであり、すでに最も単純な形式になっています。 

## Python ソリューション```python
import sys
from math import gcd

input = sys.stdin.readline

def solve():
    expr = input().strip()

    tokens = expr.replace("+", " ").split()

    first_num, first_den = map(int, tokens[0].split("/"))
    g = gcd(first_num, first_den)
    p = first_num // g
    q = first_den // g

    for token in tokens[1:]:
        a, b = map(int, token.split("/"))

        g = gcd(q, b)

        q1 = q // g
        b1 = b // g

        p = p * b1 + a * q1
        q = q1 * b

        g = gcd(p, q)
        p //= g
        q //= g

    if q == 1:
        print(p)
    else:
        print(f"{p}/{q}")

if __name__ == "__main__":
    solve()
```最初の解析操作では、式が独立した分数トークンに変換されます。 交換中`+`式には加算のみが含まれているため、演算子の優先順位や括弧を処理する必要がないため、スペースで十分です。 

最初の部分はループの前に削減されます。 これは正確さを保つために厳密には必要ありませんが、2 番目の部分を処理する前に同じ不変式を確立し、最初から中間値を小さく保ちます。 

ループ内では、`gcd(q, b)`分母を乗算する前に使用されます。 表現`q1 * b`したがって、生の製品ではなく LCM になります。 分子はマッチング係数を使用します`b1`そして`q1`したがって、両方の分数は正確にその最小公倍数上で表されます。 

2 番目の GCD が必要なのは、合計の分子によって分母との追加の共通因数が導入される可能性があるためです。 たとえば、追加`1/2`そして`1/2`生成する`4/4`削減の前に、これは次のようになる必要があります`1/1`。 

Python の整数はオーバーフローしません。問題の保証が Java に関して記述されているため、これはここでは役に立ちます。`int`効率的な実装のための値。 Python であっても巨大な整数を避けることはパフォーマンスにとって重要であるため、アルゴリズムは依然として中間の増加を意図的に制御します。 

出力チェックでは、`q == 1`かどうかを確認するのではなく、`p % q == 0`。 分数は最小項で維持されるため、分母は`1`は、出力形式で必要とされる条件とまったく同じです。

 ## 特殊なケース

 最初のエッジ ケースは整数の結果です。 のために```
2/3 + 7/3
```最初の状態は`2/3`。 2 番目の分母はすでに次と等しいです`3`, したがって、新しい分子は次のようになります。`2 + 7 = 9`、与える`9/3`。 2 番目の GCD は、`3`、状態を次のように縮小します`3/1`。 決勝戦`q == 1`チェックプリント`3`、サンプルで要求されているとおりです。 

2 番目のエッジ ケースは、縮小されていない入力部分です。```
2/4 + 1/4
```最初の分数はすぐに次から減算されます。`2/4`に`1/2`。 次の分数には分母があります`4`、 それで`gcd(2,4) = 2`。 LCM は`2/2 * 4 = 4`、分子は次のようになります。`1*2 + 1*1 = 3`。 状態は`3/4`したがって、出力は次のようになります`3/4`。 入力端数が既に縮小されていると仮定した解でも、数学的にはこのケースを解決できますが、縮小されていない表現を保持すると、不必要な因数が作成されてしまいます。 

3 番目のエッジ ケースは、共通の分母要素です。```
1/6 + 1/4
```分母には​​GCDがある`2`したがって、LCM は`6/2 * 4 = 12`。 分子は`1*2 + 1*3 = 5`、与える`5/12`。 分母を直接乗算するには、`24`、生産`10/24`削減前。 どちらの表現も数学的には同等ですが、LCM 法により不必要な増大が回避されます。 

最後のエッジ ケースは、いくつかの加算後の整数へのキャンセルです。```
1/2 + 1/3 + 1/6
```最初の 2 つの分数の後、状態は次のようになります。`5/6`。 最後の分数は分母が同じなので、分子は次のようになります。`5 + 1 = 6`、与える`6/6`。 最終的な GCD はこれを次のように短縮します。`1/1`、そしてプログラムは出力します`1`。 このケースでは、加算のたびにリダクションが行われることと、分数が完全にリダクションされた後にのみ整数の書式設定が適用されることをチェックします。
