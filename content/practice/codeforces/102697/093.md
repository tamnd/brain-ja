 ## 解決策
 ## 問題の理解

 曲のプレイリストが与えられます。 各曲にはタイトルと長さがあり、次のように書かれています。`MM:SS`、分と秒は 2 桁を使用します。 タスクは、最も長い曲のタイトルを出力することです。 複数の曲がまったく同じ長さである場合、入力内で最も早く出現する曲が優先されます。 

持続時間を単一単位に換算すると比較しやすくなります。 長持ちする曲`06:13`続く`6 * 60 + 13 = 373`数秒間、`05:57`続く`357`秒。 結果の整数を比較するのは、元の文字列を比較するよりも簡単で、エラーが発生しにくくなります。 

公式声明では、曲数の明確な上限は指定されていません。 制限時間は 1 秒、メモリ制限は 256 MB です。 すべての曲を 1 回正確に調べることで必要な答えが見つかるため、`O(n)`scan は自然なターゲットであり、一定の追加スペースのみを使用します。 二次アルゴリズムは約`n(n-1)/2`ペアごとの比較。プレイリストが大きくなるにつれて、不必要にコストがかかります。 

不注意な実装により、誤って間違った曲が選択される可能性があるケースがいくつかあります。 まず、ネクタイは以前の曲を保持する必要があります。 例えば：```
3
First 10:00
Second 10:00
Third 09:59
```正しい出力は次のとおりです`First`。 新しい期間が等しい場合に現在の回答を置き換える実装では、誤って出力されます。`Second`。 

次に、比較では分と秒の両方を考慮する必要があります。 例えば：```
2
Short 09:59
Long 10:00
```正しい出力は次のとおりです`Long`。 期間を通常の 10 進数として誤って扱うと、無効な比較が発生する可能性があります。 

最後に、最初の曲が最も長い場合は、正しく処理する必要があります。```
2
OnlyGoodOne 12:00
Smaller 11:59
```正しい出力は次のとおりです`OnlyGoodOne`。 最良のデュレーションをゼロに初期化することは、有効な正のデュレーションに対して機能しますが、最良のタイトルを任意の後の曲に初期化すると、回避可能な特殊なケースが発生する可能性があります。 

## アプローチ

 直接的な総当たりのソリューションでは、すべての曲を他のすべての曲と比較し、長い方を保持できます。 これは正しいです。すべてのペアが検討された後、すべての曲がすべての可能な競合相手と比較されたからです。 ただし、同じ情報が何度も繰り返されます。 のために`n`歌、ありますよ`n(n-1)/2`順序のないペアであるため、最悪の場合の比較数は次のようになります。`n(n-1)/2`、つまり`O(n²)`。 

2 つのデュレーションの比較は定数時間であるため、総当たり法は機能しますが、最も長い曲をすべての曲に対して個別に比較する必要がないため、失敗します。 プレイリストを左から右にスキャンしながら、これまでに見た中で最高の曲を維持できます。 次の曲が長くなると、それが新たなベストソングになります。 同じかそれより短い場合は何も変わりません。 

重要な観察点は、最初の処理後、`i`曲の場合、それらの曲に関する情報は 1 つだけ必要です。それは、それらの曲の中で最長の再生時間と、その再生時間を持つ最も古いタイトルです。 その後のすべての決定は、以前の個々の曲ではなく、この概要のみに依存します。 これにより、問題は入力を 1 回通過するだけで済みます。 

タイルールにより、当然のことながら比較演算子が決まります。 新しい期間が現在の最適な期間よりも厳密に大きい場合にのみ更新されます。 継続時間が等しい場合、既存の回答を維持すると、プレイリスト内の以前の位置が保持されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) または O(1) | n が大きいと遅すぎます |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 曲数を読み取ります。 各曲を一度処理するため、プレイリスト全体を保存する必要はありません。 
2. 曲ごとに、入力行をタイトルと再生時間に分割します。 タイトルは空白で区切られた最初のトークンであり、期間は指定された入力形式の 2 番目のトークンです。 
3. 継続時間を次のように変換します。`MM:SS`数秒に。 議事録が`m`そして秒は`s`、合計期間は`60 * m + s`。 1 つの整数を使用すると、正確かつ直接的な比較が可能になります。 
4. これまでに見た中で最高の曲を表す 2 つの変数、つまりタイトルと長さを保持します。 最初の曲では、これらの変数をデータから直接初期化します。 これにより、考えられるすべての入力に対して有効であるとは限らない人為的な継続時間に依存することがなくなります。 
5. 後続のすべての曲について、その長さを現在の最適な長さと比較します。 新しい継続時間が厳密に大きい場合にのみ、保存されているタイトルと継続時間を置き換えます。 現在の曲が以前に見つかったため、タイは意図的に無視されます。 
6. すべての曲が処理されたら、保存されているタイトルを印刷します。 その時点で、これは入力全体の中で最も長い曲を表し、長さが等しい場合には最も早いものが選択されます。 

不変条件は、プレイリストのプレフィックスを処理した後、`best_time`はそのプレフィックスの最大継続時間であり、`best_title`は初出時のタイトルです。 短い曲は最大値を変更できません。また、同じ曲で最初の出現を置き換えることはできません。 厳密に長い曲は、処理されたプレフィックス内で独自の最適な長さになります。 不変式はすべての入力行の後で保持されるため、最終行の後でも保持され、保存されたタイトルが正確に必要な答えになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    best_title = None
    best_time = -1

    for _ in range(n):
        title, duration = input().split()

        minutes, seconds = map(int, duration.split(':'))
        total_seconds = minutes * 60 + seconds

        if total_seconds > best_time:
            best_time = total_seconds
            best_title = title

    print(best_title)

if __name__ == "__main__":
    solve()
```ループは一度に 1 曲を読み取り、その長さをすぐに秒数に変換します。 回答の候補ではなくなった曲を保持する理由はないため、入力はストリームとして処理されます。 

条件は以下を使用します`>`それよりも`>=`。 これは、タイ ルールの中心となる実装の詳細です。 と`>`、同じ長さの曲では既存の回答は変更されないため、その長さの最初の曲が選択されたままになります。 

継続時間を分割する`:`2 つの 10 進整数を与えます。 変換`minutes * 60 + seconds`文字列が辞書編集的にどのように比較されるかへの依存を回避し、すべての有効な文字列に対して機能します。`MM:SS`間隔。 

Python の整数はオーバーフローしませんが、実際の期間フィールドは十分小さいため、通常の固定幅の整数型でも十分です。 

初期化`best_time = -1`これは、最初の有効な曲が常に最初の候補になることを意味します。 問題には少なくとも 1 曲が含まれているため、`best_title`決勝戦までに割り当てられることが保証されている`print`。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | すべての曲が 1 回だけ読み取られ、解析され、比較されます。 
| スペース | お(1) | 現在の最高のタイトルと再生時間のみが保存されます。 

このソリューションは、曲ごとに一定量の作業を実行するため、1 秒の制限時間に簡単に適合します。 また、プレイリスト全体が保存されることはないため、プレイリストに含まれる曲の数に関係なく、256 MB のメモリ制限内に収まります。 

## テストケース```python
import sys
import io

def solve_io(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    n = int(sys.stdin.readline())

    best_title = None
    best_time = -1

    for _ in range(n):
        title, duration = sys.stdin.readline().split()
        minutes, seconds = map(int, duration.split(':'))
        total_seconds = minutes * 60 + seconds

        if total_seconds > best_time:
            best_time = total_seconds
            best_title = title

    print(best_title)

    result = sys.stdout.getvalue()

    sys.stdin = old_stdin
    sys.stdout = old_stdout

    return result

# Provided sample 1
assert solve_io(
    """6
TheRobots 06:13
Spacelab 05:57
Metropolis 06:01
TheModel 03:41
NeonLights 08:53
TheManMachine 05:32
"""
) == "NeonLights\n", "sample 1"

# Provided sample 2
assert solve_io(
    """4
ReallyShortSong 01:30
ReallyLongSong 18:16
AnotherReallyLongSong 18:16
NotAsLongSong 11:01
"""
) == "ReallyLongSong\n", "sample 2"

# Minimum-size input
assert solve_io(
    """1
Solo 00:01
"""
) == "Solo\n", "single song"

# All durations equal, so the first title must win
assert solve_io(
    """4
First 05:30
Second 05:30
Third 05:30
Fourth 05:30
"""
) == "First\n", "all equal"

# Boundary between minutes and seconds
assert solve_io(
    """3
AlmostTen 09:59
ExactlyTen 10:00
AfterTen 10:01
"""
) == "AfterTen\n", "minute boundary"

# Large input, catches accidental quadratic implementations
songs = ["Song0 00:01"] + [
    f"Song{i} 00:{i % 60:02d}" for i in range(1, 100000)
]
large_input = "100000\n" + "\n".join(songs) + "\n"
assert solve_io(large_input) == "Song59\n", "large input"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1 / Solo 00:01`|`Solo`| 最小サイズの入力と初期化 |
 | 全部で4曲続く`05:30`|`First`| 同点の場合は早い者勝ち |
 |`09:59`、`10:00`、`10:01`|`AfterTen`| 分単位の境界を越えた正しい変換 |
 | 100000 曲 |`Song59`| 線形処理とスケーラビリティ |

 大規模なテストでは、反復期間のケースも実行されます。 生成されたデュレーションには次の値が使用されるため、いくつかの曲は同じ 2 番目の値を持ちます。`i % 60`ただし、最初に発生した最大期間のみが保持されます。 

## 特殊なケース

 単一曲のプレイリストの場合、入力は次のようになります。```
1
Solo 00:01
```アルゴリズムは次から始まります`best_time = -1`。 唯一の曲に長さがある`1`、 それで`1 > -1`そして状態は次のようになります`best_title = Solo`、`best_time = 1`。 他には何も処理されず、出力は次のようになります。`Solo`。 したがって、初期化は可能な限り小さい入力サイズでも有効です。 

同じ期間については、次のことを考慮してください。```
3
First 10:00
Second 10:00
Third 09:59
```最初の曲では、最適なデュレーションが次のように設定されます。`600`。 2曲目にも長さがある`600`、 しかし`600 > 600`false であるため、状態は変化しません。 3曲目は長さあり`599`, したがって、これも無視されます。 出力は`First`、必要な最古出現ルールに正確に一致します。 

分単位の境界については、次の点を考慮してください。```
2
AlmostTen 09:59
ExactlyTen 10:00
```最初の継続時間は次のようになります。`9 * 60 + 59 = 599`。 2番目は次のようになります`10 * 60 + 0 = 600`の方が大きいため、答えは次のように変わります。`ExactlyTen`。 その結果、出力は次のようになります。```
ExactlyTen
```これは、`MM:SS`通常の 10 進表現としてのテキスト。 

大規模なプレイリストの場合、アルゴリズムは以前の曲を再検討する必要はありません。 各行は 1 つの期間変換と最大 1 つの更新に寄与します。 100,000 曲の場合でも、メインループの反復回数はちょうど 100,000 のままですが、ペアごとの総当たり比較には約 50 億のペア チェックが必要になります。 シングルパスの不変条件により、ソリューションが適切にスケールされます。
