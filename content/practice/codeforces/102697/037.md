 ## 解決策
 ## 問題の理解

 この問題では、2 つの正の整数の最小公倍数 (LCM) が求められます。`a`そして`b`。 LCM は、両方の数値で割り切れる最小の正の整数です。 たとえば、次の最小公倍数は、`2`そして`4`は`4`、 なぜなら`4`は両方で割り切れ、それより小さい正の整数はその性質を持ちません。 

入力には 2 つの正の整数が含まれています`a`そして`b`。 出力は単一の整数としての LCM です。 公式声明では、明示的な数値の上限は示されていません。`a`そして`b`ですが、目的のソリューションでは GCD にユークリッド アルゴリズムが使用されており、その実行時間は入力値で対数になります。 これにより、整数が例に示されている小さな値よりもはるかに大きい場合でも適切になります。 可能な倍数をスキャンしたり、割り算を繰り返しテストしたりするソリューションでは、答え自体に比例した数の操作が必要になる可能性があり、入力サイズよりも大幅に大きくなる可能性があります。 

素朴な公式に基づく実装が失敗する可能性がある小さなケースがいくつかあります。 一方の数値がもう一方の数値をすでに割っている場合、最小公倍数は大きい方の数値になります。 入力用`2 4`、正しい出力は次のとおりです。`4`。 から検索を開始する方法`a * b`共通因数で削減しないと作業が無駄になりますが、両方の厳密な倍数のみを誤って検索する実装では、答えを見逃す可能性があります。 

数値が等しい場合、最小公倍数は同じ数値になります。 入力用`7 7`、正しい出力は次のとおりです。`7`。 倍数の生成に基づいた不注意な実装では、最初の数値がすでに公倍数であることを認識せずに、2 番目の出現を不必要に検索する可能性があります。 

数値は互いに素である場合もあります。 入力用`3 5`、正しい出力は次のとおりです。`15`。 この場合、GCD は次のようになります。`1`したがって、製品から削除する共通因数はありません。 自明ではない GCD が常に存在することを前提とした実装では、誤った結果が生成されます。 

2 つの入力の順序は重要ではありません。 のために`4 6`そして`6 4`、最小公倍数は`12`どちらの場合も。 ユークリッド アルゴリズムはどちらの順序も自然に処理するため、GCD を計算する前に入力を手動で交換する必要はありません。 

## アプローチ

 直接的なアプローチは、両方の数値で割り切れる数値が見つかるまで倍数を検索することです。 大きい方から始めることもできます`a`そして`b`、両方で割り切れるかどうかをテストし、公倍数が見つかるまで次の整数を続けます。 これは正しいです。最初に現れる公倍数が正確に最小公倍数であるからです。 ただし、最悪の場合、検索には Θ(LCM(a, b)) の可分性チェックが必要になる可能性があります。 互いに素数の場合、最小公倍数は次のようになります。`a * b`したがって、最悪の場合には Θ(`a * b`）の操作。 適度に大きな入力の場合でも、これは現実的ではありません。 

もう 1 つの直接的な数学的アプローチは、両方の数値を因数分解し、それらの素因数から最小公倍数を構築することです。 これは機能しますが、ファクタリングには必要以上に多くの作業が必要です。 この問題により、GCD と LCM の間の重要な関係がすでにわかります。`LCM(a, b) = a * b / GCD(a, b)`。 

残りのタスクは、GCD を効率的に計算することです。 

ユークリッド アルゴリズムはまさにそれを提供します。 正の整数の場合、次のように置き換えます。`(a, b)`と`(b, a mod b)`GCD を維持します。 この変換を繰り返し適用すると、2 番目の値がゼロになるまで小さくなります。 この時点で、最初の値は GCD です。 反復回数は、入力が小さいほど対数になります。 

LCM 式の実装にも小さな改善が加えられています。 コンピューティングの代わりに`a * b // gcd(a, b)`、計算できます`a // gcd(a, b) * b`。 数学的にはこれらは同じですが、最初に除算すると中間値が小さくなります。 Python の整数はオーバーフローしませんが、これは依然として従来の形式であり、C++ などの固定幅言語に直接転送されます。 

ブルートフォース手法は、最初の公倍数を明示的に検索するため機能しますが、検索スペースが膨大になる可能性があるため失敗します。 LCM が GCD によって決定されるという観察により、検索全体をユークリッド アルゴリズムに置き換えることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | 最適 | O(log min(a, b)) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 2 つの正の整数を読み取ります。`a`そして`b`。 GCD と LCM は両方とも対称であるため、それらの順序は重要ではありません。 
2. コンピューティング`g = gcd(a, b)`ユークリッドアルゴリズムを使用します。 その間`b`ゼロ以外の場合は置き換えます`(a, b)`と`(b, a % b)`。 いつ`b`がゼロに達すると、残りの値が`a`GCDです。 

この変換が機能する理由は、`a`そして`b`も分割します`a % b`、およびすべての公約数`b`そして`a % b`も分割します`a`。 したがって、公約数のセットは変わりません。 
3. 概念的に元の値を復元し、計算します。`a // g * b`。 1 つの入力を GCD で除算すると、2 つの数値ですでに共有されている因数が正確に削除されるため、もう 1 つの入力を乗算すると、必要なすべての因数を含む最小の数値が生成されます。 
4. 結果の LCM を印刷します。 両方の入力が正であるため、結果も正になります。 

### なぜ効果があるのか

 しましょう`g = gcd(a, b)`。 書けます`a = g * x`そして`b = g * y`、 どこ`x`そして`y`共通因数がありません。 次の公倍数`a`そして`b`共有因子が含まれている必要があります`g`、2 つの数値で必要な残りの係数は次のように表されます。`x`そして`y`。 以来`x`そして`y`が互いに素である場合、両方を含む最小の数は次のようになります。`g * x * y`、これは次と等しい`a * b / g`。 ユークリッド アルゴリズムはこれを正確に計算します。`g`したがって、最終的な式は常に最小公倍数を生成します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def gcd(a, b):
    while b:
        a, b = b, a % b
    return a

def solve():
    a, b = map(int, input().split())

    g = gcd(a, b)
    lcm = (a // g) * b

    print(lcm)

if __name__ == "__main__":
    solve()
```の`gcd`関数はユークリッド アルゴリズムの反復形式です。 各反復では、ペアが次のように置き換えられます。`(b, a % b)`、残りは厳密に以下より小さい`b`したがって、ループは終了する必要があります。 

ループ後は、`a`GCDが含まれています。 関数パラメータはローカルであるため、元の入力値は引き続き使用できます。`gcd`, したがって、LCM は直後に計算できます。 

表現`(a // g) * b`より好ましい`a * b // g`。 どちらも同じ数学的結果をもたらしますが、乗算する前に除算することで、不必要に大きな中間値が回避されます。 Python には任意精度の整数があるため、この実装では整数オーバーフローの懸念はありません。 

ユークリッド アルゴリズムにはオフバイ 1 条件はありません。 2 番目の値がゼロ以外である間、ループは正確に続行されます。 ゼロになると、アルゴリズムの定義により、最初の値が GCD になります。

import sys
import io

def gcd(a, b):
    while b:
        a, b = b, a % b
    return a

def solve():
    a, b = map(int, input().split())
    g = gcd(a, b)
    print((a // g) * b)

def run(inp: str) -> str:
    global input
    old_stdin = sys.stdin
    old_input = input

    try:
        sys.stdin = io.StringIO(inp)
        input = sys.stdin.readline

        old_stdout = sys.stdout
        sys.stdout = io.StringIO()

        try:
            solve()
            return sys.stdout.getvalue()
        finally:
            sys.stdout = old_stdout
    finally:
        sys.stdin = old_stdin
        input = old_input

# Provided samples
assert run("2 4\n") == "4\n", "sample 1"
assert run("1101 1816\n") == "1999416\n", "sample 2"

# Equal values
assert run("7 7\n") == "7\n", "equal values"

# Coprime values
assert run("3 5\n") == "15\n", "coprime values"

# Large values, useful for catching brute-force solutions
assert run("999999937 1000000000\n") == "999999937000000000\n", "large coprime values"

# Divisibility and boundary behavior
assert run("1 1000000000\n") == "1000000000\n", "one divides the other"

 ## 特殊なケース

 入力が等しい場合は、次のことを考慮してください。```
7 7
```最初のユークリッドステップの変更`(7, 7)`に`(7, 0)`したがって、GCD は次のようになります。`7`。 最終的な計算は`(7 // 7) * 7 = 7`。 出力は次のとおりです。```
7
```検索ベースの実装では不要な作業が実行される可能性がありますが、GCD ベースのメソッドはすぐに終了します。 

一方の数値がもう一方の数値を割る場合については、次のことを考慮してください。```
2 4
```GCD は`2`、そして最小公倍数は`(2 // 2) * 4 = 4`。 出力は次のとおりです。```
4
```アルゴリズムは、割り算を特殊なケースとして扱う必要はありません。 これは当然 GCD 式から外れます。 

互いに素数については、次のことを考慮してください。```
3 5
```ユークリッド アルゴリズムは次の GCD を生成します。`1`。 したがって、LCM は次のようになります。`(3 // 1) * 5 = 15`、与える：```
15
```これにより、積から共通因数を除去できない場合がチェックされます。 

大きな相互素数のペアについては、次のことを考慮してください。```
999999937 1000000000
```彼らのGCDは`1`したがって、結果は次のようになります。```
999999937000000000
```ブルートフォース検索では、この公倍数に達するまでに膨大な数の候補を調べる必要があります。 代わりに、ユークリッド アルゴリズムは、対数的に多くのモジュロ演算を行った後に終了します。これが、最適なソリューションが適切に拡張される主な理由です。
