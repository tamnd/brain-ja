 ## 解決策
 ## 問題の理解

 この課題は基底変換問題です。 最初の外来種は基数 (a) を使用して整数を書き込みますが、2 番目の外来種は基数 (b) を使用します。 2 つの基数と、基数 (a) で有効な数字を使用して書かれた数値 (n) が与えられます。 基数 (b) に書かれたのと同じ整数を出力する必要があります。 

たとえば、入力基数 (7) の場合、数値は`63642`を表します

 [
 6\cdot7^4+3\cdot7^3+6\cdot7^2+4\cdot7+2。 
】

 出力の基数は (9) であるため、その式の 10 進数値は (9) の累乗を使用して表す必要があり、次のようになります。`23550`。 公式声明では (a,b\le 10) となっているため、すべての数字は文字で直接表すことができます。`0`を通して`9`。 この問題には 1 秒の時間制限と 256 MB のメモリ制限があります。 現在のステートメントには桁数の明示的な上限が記載されていないため、アルゴリズムの自然なパラメーターは入力長 (L) です。 解決策では、位置検出力を繰り返し再計算するアルゴリズムは避けるべきです。アルゴリズムの仕事は (L) に応じて二次関数的に増大するからです。 

誤って処理されやすい境界ケースがいくつかあります。 単一のゼロは、可能な最小の数値です。 例えば、`2 10`に続く`0`生産しなければならない`0`。 値を繰り返し除算して桁を構築する変換ルーチンでは、誤ってゼロの空の文字列が生成される可能性があります。 

入力表現で許可されている場合は、先頭のゼロも表示できます。 例えば、`2 10`と`000101`と同じ値を表します`101`、つまり`5`したがって、出力は次のようになります。`5`、 ない`000101`または空の結果。 

ソースと宛先のベースは同じであってもかまいません。 例えば、`10 10`と`123456`生産しなければならない`123456`。 中間整数による正しい変換により、これが自動的に処理されます。 

出力には入力よりも多くの桁が含まれる場合があります。 例えば、`2 10`十分に長い 2 進数を使用すると、同等以上のテキスト長の 10 進数を生成できます。 実装では、出力が入力と同じ長さであると想定してはなりません。 

## アプローチ

 簡単なアプローチは、位置検出力を使用してすべてのソース数字を個別に評価することです。 数値が (L) 桁の場合、各項は (d_i a^{L-1-i}) として計算できます。累乗は (a) を繰り返し乗算することで得られます。 位置表記はこれらの項の正確な合計であるため、この方法は数学的に正しいです。 ただし、べき乗をゼロから計算すると、

 [
 (L-1)+(L-2)+\cdots+1=\frac{L(L-1)}2
 】

 最悪の場合、ソース変換のためだけに乗算が行われます。 仕事は (O(L^2)) ですが、これは不要です。 

重要な観察は、位置表記は段階的に評価できるということです。 これまでに見た数字が値 (x) を表すと仮定します。 次の桁が (d) の場合、その桁を基数 (a) に追加すると、値が次のように変更されます。 

[
 x\cdot a+d。 
】

 電力を再計算する理由はありません。 ゼロから開始して、この繰り返しを桁ごとに 1 回適用すると、ソース表現全体が (O(L)) の算術ステップで変換されます。 

整数値がわかったら、その逆の演算から宛先表現が続きます。 整数 (x) を (b) で割ると、商と余りが得られます。 

[
 x=q\cdot b+r、
 】

 ここで、(r) は正確に基数 (b) の最下位桁です。 (q) に対してこの操作を繰り返すと、残りの桁が右から左に抽出されます。 収集された剰余を反転すると、必要な表現が得られます。 

これにより、クリーンな 2 段階のソリューションが得られます。 位置表記は桁重み付き累乗の合計であるため、総当り攻撃は機能しますが、それらの累乗が繰り返し再計算されると失敗します。 ホーナー スタイルの評価ではその繰り返しが削除され、分割が繰り返されると新しいベースでの正規表現が得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O(L^2)) 算術ステップ | (O(L)) | 大きな入力には遅すぎる |
 | 最適 | (O(L)) 位置ステップ、および出力変換 | (O(L)) | 承認済み |

 複雑さの表記は、累算された整数の算術を 1 つの演算として扱います。これが、この基本的な変換問題の標準モデルです。 Python の任意精度の整数では、実際のビットの複雑さはその整数のサイズにも依存します。 

## アルゴリズムのチュートリアル

 1. ソースベース (a)、デスティネーションベース (b)、および数字列 (n) を読み取ります。 文字列はソース表現の個々の数字であるため、文字列は最初は文字列のままでなければなりません。 
2. 累積された整数値をゼロに設定します。 ソース文字列内のすべての文字を数値 (d) に変換し、次を使用して値を更新します。`value = value * a + d`。 これは位置の反復であるため、接頭辞を処理した後、`value`は、その接頭辞によって表される整数そのものです。 
3. 累積値がゼロの場合は、印刷します。`0`すぐに。 そうしないと、正しい表現に 0 桁が 1 つ含まれている場合でも、除算を繰り返しても剰余は生成されません。 
4. 値が正の場合、それを宛先の基数で割ります (b)。 剰余を数字リストに追加し、値を商で置き換えます。 各剰余は、最下位から始まる次の宛先桁になります。 
5. 収集した数字を反転して文字に変換します。 除算プロセスでは数字が逆方向に検出されるため、逆にすると通常の最上位から最下位の順序が復元されます。 
6. 結果の文字列を出力します。 どちらの基数も最大 10 であるため、すべての数字は対応する 10 進文字で表されます。 

最初のフェーズの背後にある不変条件は、最初の (k) ソース桁を処理した後、累積値が基数 (a) のそれらの (k) 桁で表される整数と正確に等しいということです。 1 桁を追加すると、位置規則 (x\mapsto xa+d) が正確に適用されるため、不変式は反復ごとに存続します。 

第 2 段階では、各除算後に (x=q b+r) が得られるため、(r) は (x) の最下位基数 (b) の数字になります。 商には、残りのすべての上位桁が含まれます。 この引数を繰り返すと、収集された剰余がまさに逆順の宛先表現であることが証明されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    a, b = map(int, input().split())
    s = input().strip()

    # Convert from base a to an ordinary Python integer.
    value = 0
    for ch in s:
        digit = ord(ch) - ord('0')
        value = value * a + digit

    # Zero needs a special representation.
    if value == 0:
        print(0)
        return

    # Convert the integer to base b.
    digits = []
    while value > 0:
        value, remainder = divmod(value, b)
        digits.append(chr(ord('0') + remainder))

    print(''.join(reversed(digits)))

if __name__ == "__main__":
    solve()
```最初のループは、アルゴリズム ウォークスルー ステップ 2 の繰り返しを実装します。`ord(ch) - ord('0')`数字変換を明示的に行い、ライブラリベースのパーサーへの依存を回避します。 

蓄積されたもの`value`は Python 整数であるため、固定幅のオーバーフローはありません。 このステートメントでは桁数に小さな上限が設定されておらず、有効な入力は 64 ビット値よりもはるかに大きな整数を表すことができるため、これが重要になります。`divmod(value, b)`ステップ 4 で必要な商と剰余の演算を 1 回の操作で実行します。 余りは常に次の間にあります`0`そして`b - 1`したがって、これは有効な宛先番号です。 

ループが発生するため、ゼロチェックが必要です。`while value > 0`値が 0 の場合は 0 回実行されます。 チェックを行わないと、プログラムは代わりに空行を出力します。`0`。 

反転も必須です。 たとえば、10進数を変換すると、`13`基地へ`2`剰余を生成します`1`、 それから`0`、 それから`1`。 これらは次のように発見されます`1, 0, 1`最下位から最上位へ。この例ではたまたま回文になっています。 のために`10`、残りは`0, 1`、それらを逆にすると正しい表現が得られます`10`。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | (O(L)) 位置ステップと出力変換 | 各ソース桁は 1 回処理され、各出力桁は 1 回抽出されます。

## テストケース```python
import sys
import io

def solve():
    input = sys.stdin.readline
    a, b = map(int, input().split())
    s = input().strip()

    value = 0
    for ch in s:
        value = value * a + (ord(ch) - ord('0'))

    if value == 0:
        print(0)
        return

    digits = []
    while value:
        value, r = divmod(value, b)
        digits.append(chr(ord('0') + r))

    print(''.join(reversed(digits)))

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    try:
        solve()
        return sys.stdout.getvalue()
    finally:
        sys.stdin = old_stdin
        sys.stdout = old_stdout

# Provided samples
assert run("7 9\n63642\n") == "23550\n", "sample 1"
assert run("10 3\n8790971\n") == "121112121221112\n", "sample 2"
assert run("5 6\n3124\n") == "1530\n", "sample 3"

# Minimum-size input and zero handling
assert run("2 10\n0\n") == "0\n", "zero"

# All digits equal
assert run("10 10\n111111\n") == "111111\n", "same base"

# Leading zeroes
assert run("2 10\n000101\n") == "5\n", "leading zeroes"

# Boundary between bases, binary to decimal
assert run("2 10\n11111111\n") == "255\n", "binary boundary"

# Larger custom value, hexadecimal is unnecessary because bases are <= 10
assert run("9 2\n888888\n") == "1001001010101001000\n", "large base-9 value"

## 特殊なケース

 ゼロのケースは、繰り返し除算の実装で最も一般的なサイレント障害です。 考慮する：```
2 10
0
```ホーナー位相の計算`value = 0`。 条件が以下であるため、除算ループは実行できません。`value > 0`したがって、専用のゼロチェックがなければ、出力は空になります。 実装はゼロを検出し、正確に出力します。`0`。 

先頭のゼロは、表現される整数を変更しません。 のために：```
2 10
000101
```累積された値は`0, 0, 0, 1, 2, 5`。 宛先変換は分割されます`5`10 で余りを求める`5`、およびプリント`5`。 ソース基数でゼロを乗算してもゼロが得られるため、先頭のゼロは数学的値に影響しません。 

ソースと宛先のベースが等しい場合、特別な分岐は必要ありません。 と：```
10 10
111111
```最初のフェーズでは整数 (111111) が取得されます。 2 番目のフェーズでは、同じ整数を 10 進数で表現し、次のようになります。`111111`。 これは、2 つの変換フェーズが独立して正しいことを確認するのに役立ちます。 

出力が長くなる境界ケースは次のとおりです。```
2 10
11111111
```ソース値は (255) になります。 10で割る抽出`5`、 それから`5`、 それから`2`、したがって剰余を逆にすると、`255`。 このアルゴリズムでは、入力と出力の桁数が同じであるとは決して想定されません。 

最後に、塩基自体が許容範囲の両端にあっても構いません。 例えば：```
9 2
888888
```ソース評価では、あらゆるものを扱います。`8`有効な基数 9 の数字として。 結果の整数は繰り返し 2 で除算され、バイナリ表現が生成されます。`1001001010101001000`。 サポートされているすべての基数が最大 10 であるため、数字変換は正しいままです。`0`を通して`9`可能なすべての数字を表すのに十分です。
