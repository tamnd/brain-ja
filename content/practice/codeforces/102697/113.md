 ## 解決策
 ## 問題の理解

 あなたは複数の空港のうちの 1 つに向かって飛行しています。 各空港には、滑走路の空きスペースの数、現在位置からの距離、飛行機が空港に到達するために飛行する必要がある方向があります。 また、通常飛行できる最大マイル数として表される燃料の残量や現在の風向きもわかります。 

空港は、少なくとも 1 つの利用可能な滑走路スペースがあり、残りの燃料で飛行を完了できる場合にのみ使用できます。 風は実効燃料コストを変化させます。 必要な飛行方向が風向きと同じ場合、燃料消費量は半分になるため、飛行距離が`d`費用`d / 2`燃料の単位。 飛行機が風に向かって直接飛行すると、消費量は2倍になるため、同じ距離でもコストがかかります`2d`。 残りの方向については、通常の距離が使用されます。 

利用可能な空港のうち、最も近い空港を選択します。 問題文では明示的な数値制約が提供されていませんが、制限は 1 秒で、入力は空港の単純なリストです。 自然な解決策は 1 回のスキャンであり、空港ごとに継続的な作業が必要です。 空港の数がこれだけあったとしても`10^5`または`10^6`、`O(n)`スキャンは意図したアプローチで問題ありませんが、空港のすべてのペアを試したり、並べ替えを繰り返したりすると、不必要な作業が追加されます。 

風の計算は間違いの主な原因となります。 距離自体は変化せず、距離を移動するのに必要な燃料の量のみが変わります。 たとえ追い風で旅行料金が安くなったとしても、空港までの物理的な距離が残りの燃料よりも長いため、空港を誤って拒否することが簡単に起こります。 

たとえば、次のことを考えてみましょう。```
2
20
S
1 20 S
1 20 N
```最初の空港では、まさに風に乗って南に飛行する必要があります。 その実効燃料費は、`20 / 2 = 10`, 到達可能です。 2 番目の空港では、風に逆らって北に飛行する必要があるため、コストは次のとおりです。`20 * 2 = 40`、到達不能になります。 正しい出力は次のとおりです`1`。 風を考慮せずに生の距離を比較する不用意な実装は、両方の空港を同等に到達可能であるとして誤って扱うことになります。 

もう 1 つの境界ケースは、調整コストがまさに利用可能な燃料である空港です。 飛行機が飛べるなら`20`マイルと空港の料金は正確です`20`、その空港は到達可能です。 比較する必要があるのは、`cost <= fuel`、 ない`cost < fuel`。 

2 番目によくある間違いは、滑走路の空きスペースがゼロの空港を受け入れることです。 例えば：```
1
100
N
0 10 N
```空港は十分近いのですが、着陸する場所がないので選択できません。 正しい実装では、距離を考慮する前にそれを拒否する必要があります。 

## アプローチ

 この問題を考える強引な方法は、考えられるすべての空港の選択肢を生成し、その空港が到達可能かどうかを計算し、それを他のすべての候補と比較してどれが最も近いかを決定することです。 すべての空港が明示的にチェックされるため、これは正しいですが、ペアごとの比較は不要です。 と`n`空港、すべてのペアの所要時間を比較`n(n - 1) / 2`比較、つまり`5 * 10^9`比較する場合`n = 100000`。 これは、1 秒のコンテスト プログラムで処理できる範囲をはるかに超えています。 

有益な観察は、空港が独立しているということです。 空港かどうか`i`到達可能かどうかは、滑走路の数、距離、方向、および全世界の風向きによってのみ決まります。 空港間の相互作用はありません。 空港を有効燃料コストに変換したら、これまでに確認された最良の候補を維持するだけで済みます。 

これにより、問題は単純なスキャンに変わります。 空港ごとに、滑走路スペースがない場合はまず拒否します。 次に、空港と風の相対的な方向から有効燃料コストを計算します。 コストが利用可能な燃料を超える場合は、拒否します。 それ以外の場合は、これまでに見つかった最も近い有効な空港と物理的な距離を比較します。 すべての空港が 1 回だけ考慮されるため、最終的に保存されたインデックスが必要な答えとなります。 

風調整は浮動小数点演算を行わずに実行することもできます。 追い風の場合の条件は、`d / 2 <= fuel`と同等です`d <= 2 * fuel`。 向かい風の場合、コンディションは`2 * d <= fuel`を直接確認することができます。 中立方向の場合、条件は単純です。`d <= fuel`。 整数比較を使用すると、次のような場合に精度の問題が回避されます。`d`奇数です。 

公式声明では、1 秒の時間制限と 256 MB のメモリ制限が示されていますが、空港の数については明示的な数値制限は指定されていません。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | n が大きいと遅すぎます |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 空港の数、利用可能な燃料、風向きを読み取ります。 これらの値は、すべての空港が検査される間、固定されたままになります。 
2. 最適な空港を存在しないものとして、最適な距離を無限大として初期化します。 これにより、特別な場合を必要とせずに、最初の有効な空港が自動的に現在の候補になります。 
3. 各空港の滑走路の空き状況、物理的な距離、必要な飛行方向を読み取ります。 滑走路数がゼロの場合は、燃料の有無に関わらず空港は使用できないため、直ちに廃棄してください。 
4. 風から燃料乗数を決定します。 必要な方向が風向きと等しい場合、有効コストは次のようになります。`d / 2`。 必要な方向が逆方向の場合、コストは`2d`。 それ以外の場合のコストは、`d`。 
5. 残りの燃料で空港に到達できるかどうかをテストします。 実際に計算するのではなく、整数不等式を使用する`d / 2`これにより浮動小数点値が回避されるためです。 
6. 空港に到達可能で、その物理的距離がこれまでに確認された最良の距離よりも短い場合は、その 1 から始まるインデックスを答えとして保存します。 目的は近接性であるため、実行可能なすべての空港の中で物理的距離が最も小さいことが正しい選択です。 
7. すべての空港の処理が完了したら、保存されているインデックスを印刷します。 

不変条件は、最初の処理後の`k`空港の場合、保存された候補は、正確にそれらの空港の中で最も近い使用可能な空港です。`k`空港。 拒否された空港はすべて、滑走路がないか、燃料制限を超えているため使用できません。 受け入れられたすべての空港は現在の最良の空港と比較されるため、次の空港が処理された後も不変条件は true のままです。 最終空港の後の候補は、すべての空港の中で最も近くにある使用可能な空港になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def opposite(direction):
    return {
        "N": "S",
        "S": "N",
        "E": "W",
        "W": "E",
        "NE": "SW",
        "SW": "NE",
        "NW": "SE",
        "SE": "NW",
    }[direction]

def solve():
    n = int(input())
    fuel = int(input())
    wind = input().strip()

    best_distance = float("inf")
    answer = -1

    for i in range(1, n + 1):
        runway, distance, direction = input().split()
        runway = int(runway)
        distance = int(distance)

        if runway == 0:
            continue

        if direction == wind:
            reachable = distance <= 2 * fuel
        elif direction == opposite(wind):
            reachable = 2 * distance <= fuel
        else:
            reachable = distance <= fuel

        if not reachable:
            continue

        if distance < best_distance:
            best_distance = distance
            answer = i

    print(answer)

if __name__ == "__main__":
    solve()
```入力は次を使用して読み取られます`sys.stdin.readline`これは、リニア スキャンには十分であり、必要な競合プログラミング I/O パターンに従います。 

の`opposite`関数は、各コンパスの方向をその正反対の方向に変換します。 これは、北や南などの基本方向と、北東や南西などの対角方向の両方を処理します。 

メインループは以下を使用します`range(1, n + 1)`そのため、保存されているインデックスはすでに 1 から始まり、出力で予期される空港番号と一致します。 

追い風の場合、実際のコストは次のとおりです。`distance / 2`。 その値を計算する代わりに、コードはチェックを行います。`distance <= 2 * fuel`。 逆風の場合のコストは、`2 * distance`、それでテストは`2 * distance <= fuel`。 これらの等価な整数比較により、浮動小数点境界エラーの可能性が回避されます。 

このコードは、最適な空港を選択する際に物理的な距離を比較します。 風は空港に到達できるかどうかに影響しますが、この声明の近接基準は空港までの所定の距離を指します。 到達可能な 2 つの空港の距離が同じ場合、更新では次の機能が使用されるため、最初に見つかった空港が保持されます。`<`それよりも`<=`。 

表示されるステートメントには、使用可能な空港がない場合に何を印刷するかは指定されていません。 実装では使用します`-1`その場合のために。 このタイプの問題のコンテスト バージョンでは、通常、隠しテストで有効な空港の保証が必要な場合に、有効な空港が保証されます。

 最も重要なエッジケースは、物理的な距離と燃料コストの違いです。 と```

```空港 1 までの距離は 20 ですが、風と飛行方向が一致しているため、必要な燃料は 10 単位だけです。 空港 2 の物理的距離は同じですが、飛行機が風に向かって飛行するため、40 ユニットが必要です。 スキャンは空港 1 を受け入れ、空港 2 を拒否し、`1`。 これは、ステートメントで説明されている風の調整を直接実行します。
