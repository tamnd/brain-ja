 ## 解決策
 ## 問題の理解

 2 つのバスケットボール チームが試合を行い、各チームの最終スコアを再構成するのに十分な統計が得られました。 各チームの入力により、ゴールされたバスケットの総数、3 ポイントシュートであったバスケットの数、およびフリースローの数が得られます。 

作成されたバスケットは 2 ポインタまたは 3 ポインタのいずれかになります。 合計バスケット数には両方のタイプが含まれるため、`b`合計バスケットと`t`スリーポイントが作られました`b - t`ツーポインタ。 したがって、そのバスケットポイントは`2 * (b - t) + 3 * t`。 

を追加すると、`f`フリースローで完全なスコアが得られます。`2 * (b - t) + 3 * t + f`。 

これを単純化すると、`2 * b + t + f`。 タスクは、両方のチームのこの値を計算し、スコアが大きい方のチームの名前を出力するだけです。 このステートメントはスコアが異なることを保証するため、解決すべき同点のケースはありません。 

公開された声明には数値カウントの明示的な上限はありません。 入力には一定数の整数と文字列のみが含まれるため、目的のソリューションでは一定量の算術演算と文字列処理が実行されます。 非常に大きな整数値であっても、バスケット、スリーポイント、フリースローを個別に繰り返す必要はありません。 Python では、整数演算により、異常に大きな値が指定された場合に固定幅言語で発生するオーバーフローの問題も回避されます。 

主なエッジケースは、バスケット数の意味を正しく解釈することで得られます。 よくある間違いは、すべてのバスケットを 2 ポイントとして扱い、3 ポインターごとに個別に 3 ポイントを加算することです。 これにより、スリーポイントの 2 ポイント部分が 2 倍にカウントされます。 

たとえば、次のことを考えてみましょう。```
A B
1 0
1 0
0 0
```チーム`A`1つのバスケットを作り、そのバスケットはスリーポイントシュートでした。 そのスコアは`3`、 その間`B`もっている`0`したがって、正しい出力は次のようになります。```
A
```を使用した不注意な実装`2 * baskets + 3 * three_pointers`与えるだろう`5`のために`A`。 ここでは勝者がたまたま正しいままですが、計算されたスコアは間違っており、同じ間違いによって別の入力で勝者が変わる可能性があります。 

フリースローも別の得点カテゴリーです。 例えば：```
A B
0 0
0 0
5 4
```スコアは`5`そして`4`したがって、正しい出力は次のようになります。```
A
```バスケットとスリーポイントシュートのみを考慮した実装では、両チームの得点がゼロであると誤って結論付けられてしまいます。 

最後に、チームには通常の 2 ポインターが多数存在し、3 ポインターが存在しない場合があります。 例えば：```
A B
3 2
0 0
0 0
```スコアは`6`そして`4`したがって、正しい出力は次のようになります。```
A
```スリーポイントシュートの数はバスケットの総数ではありません。 具体的には、3 点に相当するバスケットの数であり、残りのバスケットは 2 点に相当します。 

## アプローチ

 ブルートフォースアプローチでは、得点イベントを 1 つずつ再構築しようとする可能性があります。 たとえば、`E`イベントを合計してスコアリングすると、不必要に一般的な検索では、各イベントに対して 3 つの可能なポイント値が考慮され、最大で 3 つのポイント値が生成される可能性があります。`3^E`可能なシーケンス。 その後、各候補者と選択された勝者について最終スコアが計算されます。 実際の試合はそれらのシーケンスの 1 つであるため、考えられるすべての得点シーケンスを考慮した場合、これは正しいです。 

問題は、採点イベントの順序に、最終スコアに影響を与える情報が含まれていないことです。 この入力により、各チームが 2 ポインター、3 ポインター、およびフリースローを正確に何本行ったかを決定するために必要な集計数がすでに得られています。 したがって、考えられる注文を列挙するのは無駄な作業です。 もし`E`大きかった、`3^E`検索はすぐに実行不可能になり、より慎重に制限されたブルートフォース列挙も不要になります。 

重要な観察は、2 ポインターの数が直接与えられるわけではないが、すぐに導出できるということです。 チームが作った場合`B`合計バスケットと`T`そのうちの3ポイントシュートはまさにスリーポイントシュートだった`B - T`ツーポインタでした。 結果的にスコアは`2(B - T) + 3T + F`これを単純化すると`2B + T + F`。 

この公式が認識されると、2 回のスコア計算と 1 回の比較でゲーム全体を解くことができます。 ブルートフォースは最終的に同じ合計を回復できるため機能しますが、答えが依存しない情報を探索するため失敗します。 集計スコア カウントのみが重要であるという観察により、問題は定数時間の演算に帰着します。

 ## アルゴリズムのチュートリアル

 1. 2 つのチーム名を読み上げます。 入力内の順序によって、どのスコアがどのチームに属するかが決まるため、後続のすべての統計と同じ順序で名前を保持します。 
2. 2 つの合計バスケット数を読み取ります。 電話してください`b1`そして`b2`。 これらのカウントには、2 ポインターと 3 ポインターの両方が含まれます。 
3. 2 つのスリーポインタのカウントを読み取ります。`t1`そして`t2`。 各チームの通常の 2 ポインターの数は、合計バスケット数から 3 ポインター数を引いたものになります。 
4. 2 つのフリースローのカウントを読み取り、`f1`そして`f2`。 フリースローはバスケットカウントとは無関係であるため、スコアに直接追加されます。 
5. 以下を使用して各チームのスコアを計算します。`2 * baskets + three_pointers + free_throws`。 これは、2 ポインターを明示的に次のようにカウントするのと同じです。`2 * (baskets - three_pointers)`そしてスリーポインターとして`3 * three_pointers`ただし、簡略化された式の方が短く、不必要な中間作業が回避されます。 
6. 2 つのスコアを比較します。 このステートメントは勝者が存在することを保証するため、平等を扱う必要はありません。 大きい方のスコアに対応する名前を出力します。 

### なぜ効果があるのか

 各チームごとに、`B`バスケットの総数と`T`スリーポイントの数になります。 その通り`B - T`バスケットは 2 ポインタであるため、バスケットの貢献度は次のようになります。`2(B - T) + 3T`。 追加`F`フリースローが与える`2B + T + F`。 したがって、アルゴリズムは各チームの正確な最終スコアを計算します。 勝者はまさに最終スコアの大きいチームであるため、これら 2 つの計算値を比較すると、常に必要な答えが得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    teams = input().split()

    baskets = list(map(int, input().split()))
    threes = list(map(int, input().split()))
    free_throws = list(map(int, input().split()))

    score1 = 2 * baskets[0] + threes[0] + free_throws[0]
    score2 = 2 * baskets[1] + threes[1] + free_throws[1]

    if score1 > score2:
        print(teams[0])
    else:
        print(teams[1])

if __name__ == "__main__":
    solve()
```最初の行は次のように保存されます`teams`、各チームの名前とその統計の間の対応を維持します。 すべてのスコア情報は数値であるため、次の 3 行は整数リストに変換されます。 

スコアの計算には簡略化された式が使用されます。`2 * baskets + threes + free_throws`。 から始まる`2 * baskets`すべてのバスケットをツーポインタとして扱います。 すべての 3 ポインターには 2 点ではなく 3 点の価値があるため、さらに 1 点が必要です。`threes`それらのバスケットを正確に修正します。 フリースローは個別に追加されます。 

入力によって集計カウントがすでに提供されているため、個々のスコアリング イベントをループすることはありません。 固定位置を超えるインデックスに関連する境界の問題もありません。`0`そして`1`、ちょうど 2 つのチームが存在するためです。 

Python の整数は、使用可能なメモリに応じて任意の大きな値を表すことができるため、算術演算には特別なオーバーフロー処理は必要ありません。 この問題では勝者も保証されており、`else`別の等号のケースを使用せずに 2 番目のチームを安全に代表するための分岐。
