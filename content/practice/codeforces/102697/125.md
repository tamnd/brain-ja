 ## 解決策
 ## 問題の理解

 メジャートライアドを形成する 3 つの音符を受け取ります。 音符はどのような順序で書いてもよく、音符では次のようなシャープ表記を使用できます。`C#`または次のような平坦な表記法`Df`。 3 つの音のうちどれがルートであるかを判断する必要があります。 

1 オクターブ内の 12 のピッチ クラスに整数値を割り当てることができます。`0`を通して`11`:`C, C#, D, D#, E, F, F#, G, G#, A, A#, B`。 

半音離れた 2 つの音符は連続した値を持ち、オクターブが折り返されます。`B`に戻る`C`。 ルートに価値があるメジャーコード`r`3 つのピッチ クラスが含まれています`r`、`r + 4`、 そして`r + 7`、すべての算術を剰余として取得`12`。 入力には、これら 3 つのノートを任意の順列で含めることができます。 

この表記により、見落としがちな実装の詳細が 1 つ作成されます。`C#`そして`Df`同じピッチクラスを表します。`D#`そして`Ef`、`F#`そして`Gf`、`G#`そして`Af`、 そして`A#`そして`Bf`。 比較のために両方のスペルを同じ数値に変換する必要がありますが、ルートを出力するときは、入力に現れた元のスペルを出力する必要があります。 

音符は 3 つだけで、可能なピッチ クラスは 12 しかありません。 したがって、制約は非常に小さいため、従来の線形アルゴリズムや二次アルゴリズムが遅すぎるというリスクはありません。 考えられるすべてのルートを徹底的に検索しても、一定数の操作しか実行されません。 ここでの有用な目標は、漸近的な最適化ではなく、問題を間違えにくいクリーンな間隔チェックに減らすことです。 

最初のエッジ ケースは、ルートが最初の入力ノートではないコードです。 例えば、```
E G C
```価値観がある`4, 7, 0`。 正しい出力は次のとおりです`C`。 最初の音符がルートであると想定する実装では、誤って出力されます。`E`。 

2 番目のエッジ ケースは、ピッチ クラスのフラット スペルです。 例えば、```
Bf Ef G
```価値観を表します`10, 3, 7`、変ホ長調のコードの音です。 正しい出力は次のとおりです`Ef`。 もし`Bf`そして`Ef`フラットをピッチクラスに変換するのではなく、無関係な文字列として扱われると、インターバルテストは正しく機能しません。 

3 番目のエッジ ケースは、オクターブ境界を越えて発生します。 例えば、```
B D# F#
```値を表す`11, 3, 6`。 根は`B`、 なぜなら`11 + 4 = 15`、つまり`3`モジュロ`12`、 そして`11 + 7 = 18`、つまり`6`モジュロ`12`。 モジュロ演算を行わずに通常の整数の差を使用する不注意な実装では、この有効なコードが拒否される可能性があります。 

4 番目のエッジ ケースは、5 番目が最初に現れる別の反転です。```
G C E
```正しい出力は次のとおりです`C`。 ノートを数値的に並べ替え、最小ピッチがルートであると仮定すると、ルートは必ずしも最初または最小の入力値ではなく、音のピッチ クラスであるため、他の転回形式でも失敗します。 

## アプローチ

 最も直接的な強引な解決策は、12 のピッチ クラスのすべてをルート候補として試してみることです。 候補ルートの場合`r`、対応するメジャーコードには正確に含まれている必要があります。`r`、`(r + 4) mod 12`、 そして`(r + 7) mod 12`。 これら 3 つの値を 3 つの入力ノートと比較します。 12 の候補と 3 つの音符があるため、最悪のケースでは最大 36 の基本メンバーシップ比較が実行され、さらに各候補コードを構築するために必要な少量の演算が実行されます。 これはすでに一定時間であり、十分に高速です。 

この問題では、入力がメジャー コードであることと、そのルートが指定された 3 つのノートの 1 つであることが保証されるため、総当たり法は正しいです。 したがって、正確に 1 つの候補ルートが、指定された一連のピッチ クラスを記述します。 

その最終的な保証を使用することで、検索を小さくすることができます。 12 のピッチ クラスすべてを試す代わりに、3 つの入力ノートのみをルートにできます。 これら 3 つの候補のそれぞれについて、他の 2 つの音が正確に 4 と 7 半音上であるかどうかを確認します。 候補ルート`r`は、入力ピッチクラス セットが次の値に等しい場合にのみ有効です。`{r, r + 4, r + 7}`モジュロ`12`。 

メジャー トライアドには一定の間隔パターンがあるという観察が、重要な単純化です。 音符が提供された順序について推論する必要はなく、さまざまな転回形を区別する必要もありません。 すべてのスペルがピッチ クラスにマッピングされると、コードは既知のパターンを持つ単なる 3 つの要素のセットになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 12 ルートすべてに対するブルート フォース | お(1) | お(1) | 承認済み |
 | 提供された 3 つのノートをルートとしてテストします。 お(1) | お(1) | 承認済み |

 2 番目のアプローチは、入力によって約束された構造を直接使用し、正しさの議論を簡単にするため、推奨されます。 

## アルゴリズムのチュートリアル

 1. 考えられるすべての入力スペルからそのピッチクラス番号へのマッピングを作成します。`0`に`11`。 例えば、`C`にマップします`0`、`C#`そして`Df`両方ともマップされます`1`、 そして`B`にマップします`11`。 
2. 3 つの音符列を読み取り、それぞれを数値的なピッチ クラスに変換します。 必要な出力ではルートに指定されたスペルを使用する必要があるため、元の文字列も保持します。 
3. 3 つの数値を 1 つのセットに入れます。 入力はメジャー コードの 3 つの異なるノートを記述するため、このセットはコード内のピッチ クラスの完全なコレクションを表します。 
4. 3 つの入力ノートのそれぞれをルート候補として試してください。 候補値としては`r`、予想されるメジャートライアドを構築します`{r, (r + 4) % 12, (r + 7) % 12}`。 
5. 予想されるトライアドを入力セットと比較します。 それらが等しい場合、候補はルートであるため、元の入力スペルを出力します。 
6. 入力は有効なメジャーコードであることが保証されているため、3 つの候補のうち 1 つが成功する必要があります。 有効なジャッジデータにはフォールバックケースは必要ありません。 

### なぜ効果があるのか

 すべての候補者に対して`r`、アルゴリズムは、3 つの入力ピッチ クラスが次の場合に正確にそれを受け入れます。`{r, r + 4, r + 7}`モジュロ`12`。 それはまさにルートを持つメジャートライアドの定義です`r`。 実際のルートは 3 つの入力ノートの中にあることが保証されているため、アルゴリズムは最終的にそれをテストして受け入れます。 ルート以外の入力ノートは同じテストに合格できません。そのノートを 4 と 7 半音シフトすると、異なる長三和音のパターンが生成されるからです。 したがって、返された候補はルートであり、その候補に付加された元のスペルが必要な出力となります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

NOTE_VALUE = {
    "C": 0,
    "C#": 1,
    "Df": 1,
    "D": 2,
    "D#": 3,
    "Ef": 3,
    "E": 4,
    "F": 5,
    "F#": 6,
    "Gf": 6,
    "G": 7,
    "G#": 8,
    "Af": 8,
    "A": 9,
    "A#": 10,
    "Bf": 10,
    "B": 11,
}

def solve():
    notes = input().split()
    values = [NOTE_VALUE[note] for note in notes]
    chord = set(values)

    for i, root in enumerate(values):
        expected = {
            root,
            (root + 4) % 12,
            (root + 7) % 12,
        }

        if expected == chord:
            print(notes[i])
            return

if __name__ == "__main__":
    solve()
```の`NOTE_VALUE`辞書はシャープスペルとフラットスペルの両方を処理します。 この問題では、等倍音のピッチ クラスが同じであるため、複数の弦を同じ整数にマッピングできます。 

オリジナル`notes`リストは別個に保存されます`values`。 これが必要なのは、入力に次のものが含まれている場合です。`Ef`、必要な答えは次のとおりです`Ef`のような正規の綴りではありません。`D#`。 

セット`chord`入力から順序付けを削除します。 ルート候補の場合、予想されるメジャーコードもセットとして表されるため、比較は、入力がルート位置、第一転回形、第二転回形のいずれで与えられたかには依存しません。 

による追加`4`そして`7`モジュロで実行される`12`。 これは、次のコードと交差するコードを処理します。`B`に戻る`C`、Bメジャーコードなど`B D# F#`。 

すべての値が次の値の間にあるため、整数オーバーフローの懸念はありません。`0`そして`11`、Python の整数も任意の精度を処理します。 ループには正確に 3 回の反復があるため、追加の最適化は必要ありません。

## 特殊なケース

 最初のエッジケースは反転です。 と```
E G C
```値は`4, 7, 0`。 アルゴリズムは最初にテストします`E`、 期待して`{4, 8, 11}`、一致しません。 次にテストします`G`、 期待して`{7, 11, 2}`、これも失敗します。 最後にテストします`C`、 期待して`{0, 4, 7}`、まさに入力セットです。 出力します`C`。 重要な特性は、アルゴリズムが 3 つの音符をセットとして扱うため、入力順序は影響を受けないことです。 

2 番目の特殊なケースは、同調スペリングです。 と```
Bf Ef G
```辞書は変換します`Bf`に`10`、`Ef`に`3`、 そして`G`に`7`。 テスト`Ef`与える`(3 + 4) % 12 = 7`そして`(3 + 7) % 12 = 10`、生産`{3, 7, 10}`。 これは入力セットと等しいため、アルゴリズムは元の文字列を出力します。`Ef`。 元の文字列を保持しながら音符を数値に変換すると、比較と出力の両方が正しく処理されます。 

3 番目のエッジ ケースはオクターブの終わりを横切ります。 と```
B D# F#
```ルート候補`B`価値がある`11`。 その3つ目は、`(11 + 4) % 12 = 3`、つまり`D#`、その5番目は`(11 + 7) % 12 = 6`、つまり`F#`。 予想されるセットは、`{11, 3, 6}`、まさに入力です。 モジュロ演算がないと、3 番目と 5 番目の音がオクターブの外側にあるように誤って表示されてしまいます。 

4 番目のエッジ ケースは、最初の数値音符でも最小の数値音符でもないルートに関するものです。 と```
G C E
```値は`7, 0, 4`。 候補者`G`期待されるメジャー トライアドが次のとおりであるため、失敗します。`{7, 11, 2}`。 候補者`C`で成功します`{0, 4, 7}`、したがって、答えは次のとおりです`C`。 これが、値を並べ替えて最初に並べ替えられた値がルートであると仮定することが無効なショートカットとなる理由です。 

このアルゴリズムは、次のようなルートがすでに最初にある場合も自然に処理します。```
C E G
```ここで、最初の候補はすぐに生成します`{0, 4, 7}`、 それで`C`が返されます。 入力の順序に関係なく、同じ不変式が使用されます。候補は、その 4 ハーフステップおよび 7 ハーフステップの間隔が、指定された 3 つのピッチ クラスを正確に生成する場合にのみ受け入れられます。
