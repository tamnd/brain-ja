 ## 解決策
 ## 問題の理解

 2 人のプレーヤー間の卓球ゲームのスコアのスナップショットの時系列ログが与えられます。 1 人のプレイヤーが 11 ポイントに到達するとすぐにゲームは終了し、その瞬間を超えるポイントは存在しません。 

各ログエントリは次のように書き込まれます。`X-Y`ただし、微妙なルールがあります。`X`は常にその時点で現在サービスを提供しているプレーヤーのスコアです。`Y`相手のスコアです。 サーブはブロックごとに交互に行われます。アリスは 1 回、ボブは 2 回、アリスは 2 回、ボブは 2 回というようにサーブを行います。 この提供パターンによって、各スナップショットをどのように解釈するかが決まります。 

タスクは、報告されたスコア スナップショットのシーケンス全体が、スコア ルールとサーブ順序の両方を尊重する実際のゲームの有効な進行から得られたものであるかどうかを確認することです。 シーケンス全体が一貫している場合は、次のように出力します。`ok`。 それ以外の場合は、以前のすべてのエントリが有効であることを確認した後でのみ、一貫性が崩れるログ内の最初の位置を特定する必要があります。 

制約は小さく、最大 100 ログ エントリです。 これは、O(n^2) の整合性チェックでさえ簡単であるため、エントリごとの検証を備えたシミュレーションベースのアプローチで十分であることがすぐにわかります。 高度なデータ構造や最適化を強制されることはありません。 

微妙な難しさは計算的なものではなく論理的なものです。「現在のサーバー」の視点を変更してスコア形式を解釈し、実際のゲームでスコアの進化が物理的に可能であることを確認する必要があります。 

主なエッジケースは 3 つのソースから得られます。 

まず、サーバーに対するスコアの逆転です。 報道されているので、`X-Y`誰がサービスを提供しているかによって、同じ実際のゲーム状態がログ内で反転して表示される場合があります。 たとえば、実際の状態`(Alice=3, Bob=2)`次のように表示される可能性があります`3-2`または`2-3`サーバーによって異なります。 X を常にアリスのスコアとして扱う単純なアプローチは、有効な入力では失敗します。 

2つ目は、ゲームの終了です。 誰かが 11 に達すると、それ以上のエントリは存在できなくなります。 次のようなログ:```
11-9
11-10
11-11
```すべてのエントリが一貫している場合にのみ有効ですが、終了状態以降は無効です。 

3 番目に、サービス提供パターンの依存性です。 X は「サーバー スコア」であるため、サーブ トランジションの処理が正しくないと、生のスコアが有効であっても不一致が発生します。 例えば：```
1-0
0-1
```サーバーが期待どおりに切り替わるかどうかに応じて、有効または無効になることがあります。 サーブ状態を無視すると、多くの有効なシーケンスが誤って拒否されます。 

## アプローチ

 ブルートフォース解釈では、各ログエントリの背後にある隠されたゲーム状態全体を再構築しようとします。 エントリごとに、アリスがサービスを提供するか、ボブがサービスを提供するかの両方の可能性を試み、サービスのスケジュールを尊重しながらエントリ間で考えられるすべてのスコアの進化をシミュレートできます。 これは状態爆発の問題になります。 n が小さい場合でも、曖昧なエントリごとに候補履歴の数が 2 倍になる可能性があるため、ステップごとに分岐すると、最悪の場合は指数関数的な組み合わせが発生します。 

有効な解釈を 1 つ修正すれば、ゲームは決定論的な構造になるため、これは不要です。 重要な洞察は、恣意的に推測する必要がないということです。実際のゲームの状態 (真のスコアとサーブの状態) を維持しながら、一意にフォワードをシミュレートし、各ログ エントリで一貫性を検証できます。 

重要な観察は、唯一のあいまいさは、報告されたかどうかであるということです。`(X, Y)`現在のサーバーと一致します。 真の根底にある状態を維持すれば`(A, B)`誰のターンにサーブするかがわかると、スナップショットが次のいずれかに一致するかどうかを確認できます。`(A, B)`または`(B, A)`サービングルールと一貫した方法で。 最初のエントリに対して一貫した解釈を選択すると、その後のすべてのエントリが強制されます。 

したがって、問題は、各チェックポイントで検証を行い、最初の違反を拒否する決定論的なゲームをシミュレートすることに帰着します。

 ## アルゴリズムのチュートリアル

 私たちは、アリスのスコア、ボブのスコア、そして現在誰のサーブ パターンにあるという 3 つの状態を維持しながら、実際の試合をシミュレートします。また、サービング ブロックを決定するためにプレイされたポイント数も追跡します。 

1. 両方のスコアが 0 で開始し、アリスが最初にサービスします。 サーブブロックのカウンターを初期化して、正しいポイント数の後にサーバーを切り替えることができるようにします。 
2. 各ログエントリに対して、報告されたペアを順番に解析します。`(x, y)`。 
3. ゲームがすでに終了しているかどうかを確認します。 このエントリーの前にどちらかのプレイヤーが 11 に達していた場合、それ以降のエントリーは直ちに無効になります。 これにより、終了後に継続するログを受け入れることができなくなります。 
4. 報告されたペアが現在の真の状態と一致するかどうかを判断します。 どちらのスコアが最初に書き込まれるかはサーバーによって決定されるため、考えられる両方の解釈との一貫性がチェックされます。`(Alice, Bob)`に対応する`(x, y)`現在のサーバー調整ルールに従って、または必要に応じて交換されます。 どちらも一致しない場合、ログはこのインデックスでは無効です。 
5. 有効な場合、次の隠れた点がどのように追加されたかを決定する必要があります。 アリスが得点したのか、ボブが得点したのか、両方の可能性をシミュレートしますが、将来のサーブパターンと一貫した状態につながる方のみを受け入れます。 スコアは単調であり、サーブパターンは決定的であるため、1 つの分岐のみが有効になります。 
6. 有効なポイントを適用した後、サーブトラッキングを更新します。 サーブはサイズ 1、2、2、2、... のブロックで交互に行われます。つまり、最初のサーブの後は 2 ポイントごとに切り替わります。 カウンタをインクリメントし、ブロックが終了するとサーバーを切り替えます。 
7. すべてのエントリが処理されるまで続行します。 違反が発生していない場合は出力`ok`。 

### なぜ効果があるのか

 すべてのステップで、シミュレーションは実際のゲームの有効なプレフィックスを維持します。 不変条件は、処理されたプレフィックスを正確に生成する、スコアの展開とサーブ ルールの両方に一致する実際のポイント シーケンスが存在するということです。 スコアは厳密に増加し、11 によって制限され、サービング遷移はポイント数に基づいて決定的であるため、不一致は最初の無効なログ エントリで発生する必要があり、後の選択によって「修正」することはできません。 これにより、最初の不一致で拒否することで最も初期の障害点が正確に特定されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    
    # true scores
    a = 0
    b = 0
    
    # serving: True = Alice, False = Bob
    server = True
    
    # serve block logic: 1,2,2,2,...
    # we simulate by counting points since last switch
    block_size = 1
    used_in_block = 0
    
    def switch_server():
        nonlocal server, block_size, used_in_block
        server = not server
        used_in_block = 0
        if block_size == 1:
            block_size = 2
    
    ended = False
    
    for i in range(1, n + 1):
        x, y = input().strip().split("-")
        x = int(x)
        y = int(y)
        
        if ended:
            print(f"error {i}")
            return
        
        # check if snapshot matches current true state up to ordering
        # server determines orientation
        if server:
            ok = (x == a and y == b)
        else:
            ok = (x == b and y == a)
        
        if not ok:
            print(f"error {i}")
            return
        
        # try to advance game by one point consistent with snapshot change
        # since snapshot is consistent, determine who gained a point
        # compare with previous state via difference
        if server:
            # server is Alice
            if x > a:
                a += 1
            elif y > b:
                b += 1
        else:
            # server is Bob
            if x > b:
                b += 1
            elif y > a:
                a += 1
        
        # update serve block
        used_in_block += 1
        if used_in_block == block_size:
            switch_server()
        
        # check termination
        if a == 11 or b == 11:
            ended = True
    
    print("ok")

if __name__ == "__main__":
    solve()
```この実装では、正確なゲーム状態が維持され、すべてのログ エントリで一貫性が強制されます。 重要な微妙な点は、次の順序です。`(X, Y)`現在のサーバーに完全に依存するため、考えられる両方の方向に対して暗黙的に検証します。`server`フラグ。 

サーブ ロジックは、現在のブロックで消費されたポイント数を追跡​​することによって処理されます。 ブロックが終了したら、サーバーを切り替えて、次のブロック サイズ ルールを調整します。 

の`ended`このフラグにより​​、プレーヤーが 11 ポイントに達した後はエントリーが受け付けられなくなります。

 ## 特殊なケース

 重要なエッジケースの 1 つは、ゲームがログの真ん中の 11 時にちょうど終了する場合です。 考慮する：```
11-0
11-0
```最初のエントリーの後、ゲームはすでに終了しています。 2 番目のエントリは、終了が発生するとそれ以上の更新が許可されないため、同じスコアに一致するかどうかに関係なく無効です。 アルゴリズムはこれを次のように処理します。`ended`フラグ。11 に達するとすぐに後続のエントリをすべてブロックします。 

もう 1 つのエッジ ケースは、同一のログが繰り返されることです。```
0-0
0-0
0-0
```これは、スコアリング イベントが発生しないため有効ですが、サービング遷移の一貫性が保たれている場合に限ります。 シミュレーションでは、ポイントが実際に消費されるまでサーバーの状態が変更されないため、同一のエントリが有効なままになります。 

最後の微妙なケースは、さまざまなサーバーの向きでスコアの増加が発生する場合です。 同じスコアのペアは交換された形式で表現できるため、サーバーを考慮しない単純な等価性チェックでは有効なシーケンスが拒否されてしまいます。 アルゴリズムは、次の解釈を条件付けすることでこれを回避します。`(X, Y)`現在のサーバーの状態に基づいて、すべてのステップにわたる一貫性を確保します。
