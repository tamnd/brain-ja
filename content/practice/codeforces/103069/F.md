 ## 解決策
 ## 問題の理解

 無限整数グリッド上の 2 セットの点が与えられます。 1 セットはパン教授のもの、もう 1 セットはショウ教授のものです。 各ポイントはルークのように動作します。別のルークを「攻撃」できるのは、両方が水平または垂直に並んでおり、同じ行または列上でそれらの間に厳密に他のルークが存在しない場合に限られます。 

タスクは、攻撃をグローバルにカウントすることではなく、すべてのルークについて、相手のルークに対する少なくとも 1 つの有効な攻撃に参加しているかどうかを判断することです。 各ルークについて、その行または列に沿って少なくとも 1 人の「見える」対戦相手がいて、その間にブロッキング ルークが存在しないかどうかに応じて、バイナリ インジケーターを出力します。 

制限は大きく、プレイヤーあたり最大 200,000 ポイント、合計で最大 400,000 ポイントとなります。 すべてのルーク間の素朴なペアワイズチェックは二次関数的であり、非常に遅すぎます。 どのソリューションも基本的に、座標グループごとにほぼ線形または対数線形の時間ですべての点を処理する必要があります。 

素朴な考えによる微妙な失敗例は、複数のルークが同じ行または列にある場合に現れます。 

同じ行に 3 つのルークがあるとします。```
P at (0, 0), S at (2, 0), P at (4, 0)
```中飛車が攻められたとしても、「間に飛車を挟まない」ルールを正しく実行しない限り、必ずしも外飛車が両方とも攻められるとは限りません。 同じ列にある反対色のルークの存在を確認するだけの単純なアプローチでは、すべてが攻撃されていると誤ってマークされてしまいます。 

もう 1 つの注意が必要なシナリオは、両方向に複数の相手ルークが存在する場合です。 各方向で最も近いものだけが重要です。 

## アプローチ

 ブルートフォースアプローチでは、すべてのルークを反対側のプレイヤーの他のすべてのルークと比較します。 各ペアについて、同じ x 座標または y 座標を共有しているかどうかを確認し、それらの間に他のルークがあるかどうかを確認します。 位置を事前に計算したとしても、ブロッキングを検証するには、その間のポイントをスキャンするかセットを維持する必要があり、密な行または列ではおよそ O(N^2) の動作が発生します。 

重要な観察は、ブロック条件により、ソート順で直接隣接するもののみが関連するということです。 任意の固定 x 座標で、すべてのルークを y でソートすると、ルークはその上下に最も近いルークしか見ることができません。 遠いルークは、最も近いルークによってブロックされます。 同じことが各 y 座標に対称的に当てはまります。 

したがって、すべてのペアをチェックするのではなく、ルークを行と列ごとにグループ化します。 各グループ内でソートし、隣接する要素のみを比較します。 隣接ごとに、2 つのルークが異なるプレイヤーに属している場合、両方とも攻撃済みとしてマークされます。 

これにより、問題は 2 つの独立したスキャンに分割されます。1 つはすべての x グループに対して、もう 1 つはすべての y グループに対して行われます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n1・n2) | O(n) | 遅すぎる |
 | 近傍をグループ化 + 並べ替え | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 攻撃は行と列に沿って独立して定義されるため、可視性を行と列に沿って個別に処理します。 

1. すべてのルークを X 座標でグループ化します。 各 X 値について、それを共有するすべてのルークを収集し、Y 座標とプレイヤー ID を保存します。 これにより、垂直方向の相互作用が分離されます。 
2. 各 x グループについて、ルークを y 座標で並べ替えます。 「間にルークがない」ことが、ソートされた順序での隣接と同等になるようにソートする必要があります。 
3. ソートされた各 x グループを下から上にスキャンします。 隣接するすべてのペアについて、それらが異なるプレイヤーに属しているかどうかを確認します。 そうなった場合は、両方のルークを攻撃済みとしてマークします。 隣接するだけで十分な理由は、他の 2 つのルークの間にルークがあると直接の視認性が損なわれるため、連続したポイントのみが互いを見ることができるからです。 
4. 同じグループ化プロセスを繰り返しますが、ここでは Y 座標を基準にします。 これは水平方向の可視性をまったく同じ方法で処理しますが、列ではなく行に沿って処理します。 
5. 配列を維持する`attacked`すべてのルークの場合、false に初期化されます。 異なるプレーヤー間で有効な隣接ペアがいずれかの次元で見つかった場合は、対応する両方のエントリを true に設定します。 
6. 各プレイヤーの結果を入力順に出力します。 

### なぜ効果があるのか

 重要な不変条件は、固定座標グループ内で並べ替えた後、その並べ替え順序で連続する 2 つの点の間に有効な可視エッジが発生する必要があるということです。 2 つの点が 1 つの線を共有し、連続していない場合、少なくとも 1 つの他の点がそれらの間に存在し、攻撃をブロックします。 したがって、すべての有効な攻撃は、x グループまたは y グループのスキャンの 1 つの隣接に正確に対応し、プレーヤーが異なる場合、すべての隣接チェックで有効な攻撃が捕捉されます。 これにより、到達可能なペアを欠落したり二重にカウントしたりすることなく、完全性と正確性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n1, n2 = map(int, input().split())
    
    pts = []
    attacked = [False] * (n1 + n2)

    for i in range(n1):
        x, y = map(int, input().split())
        pts.append((x, y, 0, i))

    for i in range(n2):
        x, y = map(int, input().split())
        pts.append((x, y, 1, n1 + i))

    # process by x (vertical visibility)
    pts.sort()
    i = 0
    while i < len(pts):
        j = i
        x = pts[i][0]
        group = []
        while j < len(pts) and pts[j][0] == x:
            group.append(pts[j])
            j += 1
        
        group.sort(key=lambda t: t[1])

        for k in range(len(group) - 1):
            if group[k][2] != group[k + 1][2]:
                attacked[group[k][3]] = True
                attacked[group[k + 1][3]] = True

        i = j

    # process by y (horizontal visibility)
    pts.sort(key=lambda t: (t[1], t[0]))
    i = 0
    while i < len(pts):
        j = i
        y = pts[i][1]
        group = []
        while j < len(pts) and pts[j][1] == y:
            group.append(pts[j])
            j += 1
        
        group.sort(key=lambda t: t[0])

        for k in range(len(group) - 1):
            if group[k][2] != group[k + 1][2]:
                attacked[group[k][3]] = True
                attacked[group[k + 1][3]] = True

        i = j

    res1 = ''.join('1' if attacked[i] else '0' for i in range(n1))
    res2 = ''.join('1' if attacked[n1 + i] else '0' for i in range(n2))

    print(res1)
    print(res2)

if __name__ == "__main__":
    solve()
```この実装は、理論上の垂直走査と水平走査への分解を反映しています。 各スキャンは座標グループを再構築し、ソートに依存して隣接関係の等価性を強制します。 重要な点は、任意のペア間の検索を試みないことです。これにより、二次関数の動作が完全に回避されます。 

微妙な実装上の選択の 1 つは、x スキャン結果と y スキャン結果の両方を同じ場所に保存することです。`attacked`配列。 これは、ルークが一度マークされると、方向に関係なくマークされたままになるという意味で、攻撃が単調であるため安全です。 もう 1 つの詳細は、安定したインデックス作成です。各ルークはグローバル インデックスを保持しているため、ソート後に曖昧さなく回答を更新できます。

 ## 特殊なケース

 重要なエッジケースは、複数のルークが同じ座標ラインを共有し、所有権が交互になる場合です。 例えば：```
(0,0) P, (0,1) S, (0,2) P, (0,3) S
```x グループのスキャン中に、y でソートし、隣接するペアのみをチェックします。 隣接するペアはすべてクロスプレイヤーであるため、スキャンではすべてのルークがマークされます。 これにより、長距離チェックを必要とせずに、攻撃ステータスがチェーン全体に正しく伝播されます。 

もう 1 つのケースは、ライン上にルークが 1 つだけ存在する場合です。 隣接するペアがないため、何もマークされません。これは、攻撃が不可能であることを正しく反映しています。 

最後に、多くのルークが 1 つの座標で重なっているが、他の場所に分散している密集した構成を考えてみましょう。 このアルゴリズムは各座標グループを独立して分離し、無関係な線が互いに干渉しないようにし、グリッド全体にわたって正確さを維持します。
