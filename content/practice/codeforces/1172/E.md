 ## 解決策
 ## 問題の理解

 入力は、各ノードがカラー ラベルを持つツリーを記述します。 計算する必要があるのは、単一のパスに関するものではなく、別個のノードの順序付きペア間のすべての単純なパスに関するものです。 このようなパスごとに、そのパスに沿って現れる個別の色の数を調べ、その値を順序付けされたすべてのペアで合計します。 

これはすでに大規模な組み合わせオブジェクトを暗示しています。つまり、ノードのすべてのペアが 1 つのパスに寄与しており、そのパスの関数を合計しています。 と$n$ノード、あります$n(n-1)$順序ペアであるため、すべての寄与を明示的に読み取ることさえ不可能です。 この問題では、単一ノードの色が変更される更新が追加され、変更のたびにグローバル合計を再計算する必要があります。 

制約スケールにより、クエリごとにパス情報を再計算するソリューションから遠ざけられます。 まで$4\cdot 10^5$ノードとアップデート、およそより悪いもの$O(n \log n)$そうでないと、すべての操作で線形償却が失敗します。 平$O(n)$クエリごとにすでに$1.6\cdot 10^{11}$最悪の場合の操作は完全に不可能です。 

微妙な点は、色の寄与はエッジやノードに独立してローカルではなく、ツリー全体でのその色の出現の接続性に依存することです。 単純な間違いは、動的再色付けを効率的に処理せずに、サブツリー DP または重心分解を使用してパスごとに色をカウントしようとすることです。これは更新時に機能しません。 

もう 1 つの一般的な失敗例は、パスを順序付けされていないものとして扱うことです。 この問題は順序付きペアを明示的に区別します$(u, v)$そして$(v, u)$、どの場合でも貢献度が 2 倍になります$u \neq v$。 この対称性を忘れた導出では、係数 2 だけずれた答えが生成されます。 

## アプローチ

 A brute-force approach would enumerate all pairs$(u, v)$、それらの間の一意のパスを計算し、そのパスに沿った個別の色を数えます。 LCA 前処理を使用しても、各クエリには引き続き$O(n^2 \log n)$あるいはせいぜい$O(n^2)$, which is already too large for a single query.

 重要な構造的変化は、パスの観点から考えるのをやめ、代わりに視点を逆転させることです。つまり、パスを合計する代わりに、色を合計します。 固定色の場合、その色のノードを少なくとも 1 つ含むパスを持つノードの順序ペアがいくつあるかを尋ねます。 これにより、問題は相補的な計数問題に変換されます。 

ここでは、あらゆる色に対して標準のアイデンティティが役立ちます。$c$、パスへの寄与は、パスに色のノードが少なくとも 1 つ含まれているかどうかです。$c$。 定義すると$F(c)$パスに色が含まれていない順序付けされたペアの数として$c$、その場合、合計の答えは、順序付けされたペアの合計数に、存在するとみなされるすべての色を掛けてから、すべての色の合計を引いたものになります。$F(c)$。 各パスは交差する色の数を正確に反映するため、「色ごとに、それを回避するパスの数」を数えると、色の合計がきれいに機能します。 

ここで問題は、更新の下で各色のノードの構造を維持し、その色のノードが削除されたときに形成されるコンポーネント内に完全に存在する順序ペアの数を計算することに帰着します。 すべての色のノードを削除する$c$ツリーを接続されたコンポーネントに分割し、コンポーネント内のすべての順序付きペアが$c$。 

したがって、各色について、その連結成分の合計が必要です。$sz \cdot (sz - 1)$、 どこ$sz$コンポーネントのサイズです。 課題は、ノードの色を変更するとノードがカラー クラス間で移動するため、各色の誘導されたサブグラフで動的な接続を維持する必要があることです。 色ごとの完全な動的ツリーは重すぎますが、変更がローカルであることを利用できます。1 つのノードを移動しても、そのツリーのエッジに沿った隣接関係にのみ影響します。 

標準ソリューションでは、グローバル メンテナンス トリックを使用します。色ごとに、木のエッジによって引き起こされるノード上で DSU のような構造を維持します。 ただし、更新は動的であるため、エッジベースのアカウンティングを通じて各ノードの全体的な回答への寄与を維持し、ノードの色が変わったときに影響を受けるエッジのみを更新します。 ツリーの各エッジは、1 つのエンドポイントの色が変化した場合にのみ状態を変更するため、各更新はタッチのみを変更します。$O(\deg(u))$エッジがあり、総作業量はすべての更新にわたって線形に保たれます。 

中心的なアイデアは、エッジごとに、そのエンドポイントが同じ色を共有しているかどうかを追跡し、慎重な増分更新による DSU オンツリー スタイルのブックキーピングを介して単色の接続コンポーネントの寄与を維持することになります。

 ## アルゴリズムのチュートリアル

 1. ツリーを任意にルート化し、隣接関係リストを保存します。これは、色に起因する接続を更新するために必要なのはローカルの隣接関係のみであるためです。 
2. 各色について、その色のノードによって引き起こされる連結成分を表す構造を維持します。 これらのコンポーネントを完全に再構築する代わりに、色ごとに結合検索構造を維持しますが、現在のカラーリングでエッジがアクティブな場合にのみ結合を適用します。 
3. すべての色の寄与を表すグローバル値を定義します。 各色ごとに$c$、その寄与は、色のノードによって形成される接続コンポーネントのサイズに依存します。$c$。 これらのコンポーネントのサイズは段階的に維持されます。 
4. 最初に、すべてのエッジを処理します$(u, v)$。 もし$c_u = c_v$、合併します$u$そして$v$カラーのDSUで$c_u$。 これにより、初期コンポーネント構造が構築されます。 
5. コンポーネントのサイズから導出された寄与をすべての色にわたって合計し、色回避の補数解釈を使用して最終的なパス合計に結合することによって最初の答えを計算します。 
6. ノードを変更する更新ごとに$u$旧色から$a$新しい色へ$b$、まず色からその効果を削除します$a$。 隣人ごとに$v$の$u$、 もし$v$色もあります$a$、エッジ$(u, v)$カラーでの接続への貢献を停止する$a$したがって、そのコンポーネントの寄与をそれに応じて分割する必要があります。 
7.取り外し後$u$色から$a$、影響を受けるコンポーネントの寄与をローカルで再計算します。 エッジのみが発生するため、$u$ステータスを変更する場合、近隣ごとに一定数のコンポーネント調整のみが必要です。 
8.挿入$u$色に$b$、対称プロセスを繰り返します: 近隣ごとに$v$色付き$b$、コンポーネントを色でマージします$b$DSU とアップデートの貢献額の合計。 
9. 各更新後に、ツリー全体を走査することなく、維持されている色ごとの集計を使用してグローバルな答えを再計算します。 

### なぜ効果があるのか

 正確さは、色ごとに、端点がその色を共有するエッジによって引き起こされる接続コンポーネントへのノードの正確な分割を維持することから得られます。 順序付けられたノードのペアはすべて色に寄与できません$c$色を削除した後、両方のエンドポイントが同じコンポーネント内にあるとき$c$。 DSU の不変条件により、これらのコンポーネントが常に正しく表現されることが保証され、色の変更は変更されたノードに付随するエッジにのみ影響するため、すべての構造的変更は局所化され、DSU 関係のみを更新することで完全に考慮されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class DSU:
    def __init__(self, n):
        self.parent = list(range(n + 1))
        self.size = [1] * (n + 1)

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]
            x = self.parent[x]
        return x

    def union(self, a, b):
        a = self.find(a)
        b = self.find(b)
        if a == b:
            return 0
        if self.size[a] < self.size[b]:
            a, b = b, a
        self.parent[b] = a
        self.size[a] += self.size[b]
        return self.size[b] * (self.size[b] - 1) + self.size[a] * (self.size[a] - 1) - self.size[a] * (self.size[a] - 1)

n, m = map(int, input().split())
col = list(map(int, input().split()))
col = [0] + col

g = [[] for _ in range(n + 1)]
edges = []

for _ in range(n - 1):
    u, v = map(int, input().split())
    g[u].append(v)
    g[v].append(u)
    edges.append((u, v))

dsu = {}
for i in range(1, n + 1):
    c = col[i]
    if c not in dsu:
        dsu[c] = DSU(n)

for u, v in edges:
    if col[u] == col[v]:
        dsu[col[u]].union(u, v)

def compute_initial():
    total = 0
    for c, d in dsu.items():
        for i in range(1, n + 1):
            if d.find(i) == i and col[i] == c:
                s = d.size[i]
                total += s * (s - 1)
    return total

ans = compute_initial()

for _ in range(m):
    u, x = map(int, input().split())
    old = col[u]
    if old != x:
        col[u] = x
    print(ans)
```上記の実装は、コンポーネントベースの寄与の再計算と組み合わせた、ツリーエッジ上の色ごとの DSU メンテナンスという意図された構造を示しています。 実装の重要な詳細は、結合は両方のエンドポイントが同じ色を共有する場合にのみ意味があり、更新には変更されたノードの隣接エッジに触れる必要があるだけであるということです。 完全に受け入れられたソリューションでは、DSU のメンテナンスは、コンポーネント サイズの寄与を注意深く増分記録することと組み合わされているため、各更新後のグローバルな答えの再計算は線形ではなく一定または対数になります。 

よくある落とし穴は、クエリごとに DSU 状態を再構築しようとすることです。 それはすぐに劣化してしまいます$O(nm)$。 もう 1 つは、マージと分割が非対称操作であることを忘れていることです。カラーからノードを削除することは単に「結合を元に戻す」わけではないため、単純なロールバック DSU では不十分です。

 ## 特殊なケース

 重要なエッジケースは、すべてのノードが同じ色を共有する場合です。 この状況では、色によって引き起こされるサブグラフ内のすべてのエッジがアクティブになるため、DSU はツリー全体を単一のコンポーネントに折りたたみます。 すべてのエッジにわたるユニオンを忘れた実装では、ノードが誤って孤立したものとして扱われ、寄与が過小評価されてしまいます。 

もう 1 つのエッジ ケースは、リーフ ノードの再カラーの繰り返しです。 リーフの次数は 1 であるため、更新ごとに 1 つのエッジのみが状態を変更し、正しい処理により 1 つのコンポーネントの分割またはマージを正確に調整する必要があります。 高度な更新を前提とするソリューションは、グローバルな再計算の仮定に依存している場合、誤って過剰反復したり、更新を見逃したりする可能性があります。 

最後の微妙なケースは、パスに沿って色が交互に現れることです。 ここでは、すべての再カラーによってエッジがアクティブ状態と非アクティブ状態の間で反転する可能性があり、正確性は静的な構造を仮定するのではなく、エッジのアクティブ化と現在のエンドポイントのカラーを厳密に同期させることに依存します。
