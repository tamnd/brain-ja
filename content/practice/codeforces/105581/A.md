 ## 解決策
 ## 問題の理解

 私たちは、離散的な瞬間にしか開始できないプロセスを観察しています。 Vitya は定期的にスキャナーを訪問します。`t`時刻 0 から分が始まり、時刻 に 1 日が終わります`T`。 訪問するたびに、新しいドキュメントのスキャンを開始する機会がありますが、その時点でスキャナーがアイドル状態である場合に限ります。 ドキュメントのスキャンが開始されると、ドキュメントはマシンを占有します。`k`中断することなく数分間。 スキャナーがまだビジー状態の間に Vitya が到着すると、彼はすぐに立ち去り、その機会を失います。 

このタスクは、時刻 0 から時刻までの間隔内で Vitya がスキャンを正常に開始した回数を判断することです。`T`。 

制約は小さく、すべてのパラメーターが最大 100 です。これは、可能なすべての訪問に対する直接シミュレーションでも効率的であることを意味します。 訪問数は最大 100 であるため、訪問数が線形であるソリューションは制限内で快適に実行されます。 

微妙なエッジケースがその日の境界に現れます。 Vitya が時間通りに到着した場合`T`場合でも、スキャンの開始を試行することは許可されています。 その時点でスキャナーが空いている場合は、就業日が終了した後に終了する可能性があっても、新しいスキャンが開始されます。 最終時点を除外する単純なアプローチでは、最終到着が有効である場合に過小評価されてしまいます。 

別の例外的なケースが発生する場合`k`よりも大きいです`t`。 そのような状況では、ヴィティアは繁忙期に頻繁に到着し、多くの機会をスキップします。 たとえば、次の場合`t = 2`そして`k = 10`、試行の間に十分なアイドル時間が経過しない限り、最初に成功した開始のみが問題となります。 

## アプローチ

 直接シミュレーションを行うのが最も自然な出発点です。 Vitya がスキャナーにアクセスするたびに列挙します。`0, t, 2t, ...`まで`T`。 訪問のたびに、スキャナーが無料かどうかを確認します。 ビジーである場合は、新しいスキャンを開始し、現在時刻までビジーとしてマシンをマークします。`k`。 そうでなければ何もしません。 これは正しいです。なぜなら、プロセスは各到着時間におけるローカルな決定によって完全に定義されるからです。 

このブルートフォース手法のパフォーマンスは最大でも`T / t + 1`チェック回数は、最悪の場合でも最大 101 回の操作です。 それぞれのチェックは継続的に行われるため、非常に高速です。 

このシミュレーション以上に意味のある漸近的な改善は必要ありませんが、重要な観察は、維持する必要がある唯一の状態はスキャナーが利用可能になったときであるということです。 これにより、タイムライン全体を分ごとに追跡するのではなく、問題が単一の実行中の変数に縮小されます。

 ## アルゴリズムのチュートリアル

 プロセスを一連の到着イベントに圧縮し、スキャナーが次にいつ空になるかを維持します。 

1. 変数を初期化する`free_time = 0`、新しいスキャンが開始できる最も早い瞬間を表します。 初期化もする`count = 0`成功した開始の数を保存します。 
2. すべての到着時間を反復処理します。`time = 0, t, 2t, ...`その間`time ≤ T`。 各値は、Vitya がスキャナーをチェックする瞬間を表します。 
3. それぞれについて`time`と比較してください`free_time`。 もし`time ≥ free_time`の場合、その時点ではスキャナーはアイドル状態であるため、新しいドキュメントを開始できます。 
4. スキャンが開始されると、`time`、増分`count`そしてセット`free_time = time + k`、スキャナは次の動作までビジー状態のままになるため、`k`分。 
5. もし`time < free_time`, Vitya は進行中のスキャン中に到着しますが、何もせず、状態は変更されません。 

このプロセスは、それまでのすべての到着瞬間まで続きます。`T`処理されます。 

重要なプロパティは次のとおりです`free_time`は常に、最後に開始されたスキャンの正確な終了を表します。 すべての決定は、現在の到着者がその境界に到達したか、境界を超えたかどうかによってのみ決まります。 過去の経歴は一度では関係ありません`free_time`が更新されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t, k, T = map(int, input().split())

free_time = 0
count = 0

time = 0
while time <= T:
    if time >= free_time:
        count += 1
        free_time = time + k
    time += t

print(count)
```コードは単一のタイムライン ポインターを維持します。`time`段階的にジャンプする`t`、これはヴィティアの到着スケジュールに正確に一致します。 変数`free_time`スキャナが到着するたびにビジー状態かアイドル状態かをエンコードします。 

よくある間違いは、スキャンが 時刻に開始されることを忘れることです。`T`後に終了しても有効です`T`。 この条件では開始時刻のみがチェックされ、スキャンが就業時間内に完了するかどうかはチェックされません。 

もう 1 つの微妙な点は初期化です。 設定`free_time = 0`システムがアイドル状態で開始するという事実と一致して、時間 0 での最初の到着が常にスキャンを開始することを保証します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys as _sys
    input = _sys.stdin.readline

    t, k, T = map(int, input().split())

    free_time = 0
    count = 0

    time = 0
    while time <= T:
        if time >= free_time:
            count += 1
            free_time = time + k
        time += t

    return str(count)

# provided samples
assert run("4 5 17\n") == "3"
assert run("5 5 20\n") == "5"

# minimum values
assert run("1 1 1\n") == "2"

# large k blocking most attempts
assert run("2 10 10\n") == "1"

# t equals T boundary case
assert run("7 3 7\n") == "2"

# no overlap case
assert run("3 1 9\n") == "4"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 1 1 | 2 | 時間 0 および T における境界の包含 |
 | 2 10 10 | 1 | 長いスキャンは今後の試行をブロックします。 
| 7 3 7 | 2 | ちょうど一日の終わりに到着したことがカウントされます。 
| 3 1 9 | 4 | 短いスキャンで頻繁に到着 |

 ## 特殊なケース

 最初の到着が時刻 0 に発生した場合、システムはスキャナをすぐに使用可能なものとして扱う必要があります。 入力あり`1 5 3`、到着の順序は 0、1、2、3 です。時刻 0 でスキャンが開始され、時刻 5 までブロックされます。それ以降の到着はすべて、それぞれが より小さいため無視されます。`free_time`したがって、答えは 1 です。シミュレーションではこれが自然に処理されます。`free_time`は0に初期化されます。 

いつ`k`よりも小さいです`t`、スキャナーは常に次の訪問前に終了するため、到着するたびにスキャンが開始されます。 のために`t = 4, k = 1, T = 12`、到着は 0、4、8、12 時に発生し、それぞれが満たされます。`time ≥ free_time`, したがって、ステップごとにカウントが増加します。 状態は次のように進化します`free_time = 1, 5, 9, 13`。 

いつ`k`よりも大きいです`t`、重複するスキャンが優勢です。 のために`t = 2, k = 6, T = 10`、到着は 0、2、4、6、8、10 です。中間の到着はアクティブな間隔内にあるため、0、6、および 10 のみがスキャンを開始します。 条件`time ≥ free_time`は、間隔に関する明示的な推論を必要とせずに、これらのケースを正しくフィルタリングします。
