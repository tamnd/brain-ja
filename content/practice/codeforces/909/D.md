 ## 解決策
 ## 問題の理解

 入力は、各文字が線上の点の色を表す文字列です。 隣接する文字は隣接する点に対応します。 

1 回の操作中に、異なる色の隣接点が少なくとも 1 つあるすべての点が削除されます。 重要な点は、すべての削除が同時に行われるということです。 まず、削除するすべてのポイントを決定し、次にそれらをすべて一緒に削除します。 構造が変化すると、新しい隣接要素が形成され、このプロセスが繰り返されます。 

異なる色の隣接点がない状態に達するまでに、何回の操作を実行できるかを計算する必要があります。 

文字列の直接シミュレーションはすぐに不可能になります。 届く長さは$10^6$、したがって、$O(n^2)$アルゴリズムは完全に実行不可能です。 100 万文字を使用するには、線形時間に近いものが必要です。 平$O(n \log n)$許容されますが、ラウンドごとに文字列を繰り返し再構築したり、構造全体をスキャンしたりすることは許容できません。 

また、ポイントが同時に消えるため、このプロセスは最初に見えるよりも微妙です。 

次の文字列を考えてみましょう。```
aabb
```中央の 2 つのポイントは最初のラウンドで削除され、以下が残ります。```
ab
```その後、残りのポイントは両方とも第 2 ラウンドで消滅します。 

連続削除シミュレーションでは、ラウンドが終了する前に 1 つのポイントを削除すると別のポイントの近傍が変更されるため、異なる結果が生成されます。 

もう 1 つの簡単な間違いは、単色ブロックの内部点が境界点よりも長く存続することを忘れていることです。 

例えば：```
aaaaabaaaaa
```中央に隣接する 2 つの境界層`b`まず消えてください。 次のラウンドでは次のレイヤーが消え、以下同様に続きます。 答えは 1 ではありません。破壊は層ごとに内側に広がります。 

3 番目のエッジ ケースは、文字列全体がすでに 1 つの色で構成されている場合です。```
aaaaaa
```隣接する点の色の異なる点はないので、答えは次のようになります。```
0
```少なくとも 1 つの操作が存在することを前提としたソリューションは、ここで失敗します。 

## アプローチ

 この強引なアイデアは文字通りこの声明に続きます。 生き残ったポイントの現在のシーケンスを保存します。 各ラウンドで、異なる色の隣接点を持つすべてのポイントを識別し、それらを同時に削除してから、シーケンスを再構築して続行します。 

このシミュレーションはプロセス定義と正確に一致するため、正確です。 

最悪のケースを分析すると問題が見えてきます。 次のような文字列```
aaaaaabaaaaaa
```ラウンドごとに 1 つのレイヤーのみを縮小します。 ラウンド数は次のように比例します。$n$。 ラウンドごとに残っているすべてのポイントをスキャンすると、複雑さは次のようになります。$O(n^2)$が遅すぎます。$n=10^6$。 

重要な観察は、個々の点は実際には重要ではないということです。 重要なのは、同じ文字の最大ブロック数です。 

例えば：```
aaabbbccccaa
```は次のように表すことができます。```
(aaa) (bbb) (cccc) (aa)
```すべての内部ブロックは両面で異なる色になっています。 1 回の操作中に、このようなブロックは左側の境界から 1 ポイント、右側の境界から 1 ポイントを失います。 サイズが 2 小さくなります。 

エッジ ブロックには隣接するブロックが 1 つしかないため、操作ごとに失われるポイントは 1 つだけです。 

ブロックが空になると、そのブロックに隣接するブロックが隣接します。 それらの色が等しい場合、それらはより大きなブロックに結合されます。 

このプロセスは、繰り返し間隔が縮小するのと似ています。 100 万点を追跡する代わりに、同じ文字の実行を追跡します。 実行数は最大です$n$、そしてすべての実行は一定の回数だけ消えるかマージされます。 

残りの課題は、各ブロックがいつ消えるかを効率的に判断することです。 優先キューを使用すると、次に消えるブロックを常に処理できます。 実行の二重リンクリストと組み合わせると、すべてのマージをシミュレートできます。$O(m \log m)$、 どこ$m$実行回数です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n^2)$|$O(n)$| 遅すぎる |
 | 最適 |$O(m \log m)$|$O(m)$| 承認済み |

 ここ$m$は、最大の同色ランの数を示します。 

## アルゴリズムのチュートリアル

 ### 実行表現

 それぞれの最大の同色セグメントをノードにします。 

すべてのノードについて、以下を保存します。 

- その色
 - 現在の長さ
 - その左隣の実行
 - その右隣の実行

 また、ランが現在エッジランであるか内部ランであるかどうかも分類します。 

### 失踪時間

 実行は継続的に縮小します。 

エッジランの場合、操作ごとに 1 ポイントが失われます。 

室内ランの場合は1操作につき2点を失う。 

ランに長さがあると仮定します$L$。 

エッジランの場合、次の後に消えます。$$L$$操作。 

内部走行の場合、次の後に消えます。$$\left\lceil \frac{L}{2} \right\rceil$$操作。 

この消失時間は、現在の近傍でランがアクティブになった瞬間を基準にして測定されます。 

### イベントベースのシミュレーション

 1. 文字列を最大のラン数に圧縮します。 
2. 隣接するランを接続する二重リンクリストを作成します。 
3. 初期位置でのすべての実行の消失時間を計算します。 
4. すべての失踪イベントを時間順の優先キューに挿入します。 
5. 最も古い有効なイベントを繰り返し抽出します。 
6. 時間切れでランが消えた場合$t$、リンクされたリストから削除します。 
7. 削除後、その左右の隣接ランが隣接します。 
8. 2 つの隣接するランが同じ色である場合、それらを 1 つの大きなランにマージします。 
9. マージされた実行は に存在し始めます。$t$。 その残りの長さは、その時点での両方のランの残りの長さに等しい。 新しい実行を作成し、将来の消滅をスケジュールします。 
10. 実行が 1 つだけ残るまで続けます。 
11. 処理された最大の消失時間は、まさに実行できる操作の数です。 

### なぜ効果があるのか

 実行はマージ イベント間で独立して進化します。 その長さは、それがエッジランであるか内部ランであるかによってのみ決定される一定の割合で減少します。 このため、グローバル構造が変化する唯一の瞬間は、一部の実行が空になる瞬間です。 

プライオリティ キューは、これらの瞬間を時系列順に処理します。 すべてのマージは、対応する数の同時削除ラウンド後に存在する構成を正確に再構築します。 リンクされたリストは現在の隣接するランを維持し、すべての新しいマージされたランは作成された時点で正しい残りの長さを受け取ります。 

実際のプロセスのすべての構造変化はシミュレーションの 1 つのイベントに対応し、シミュレーションのすべてのイベントは実際の消失に対応するため、計算された最終時間は元のプロセスによって実行された操作の数と等しくなります。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    colors = []
    lengths = []

    i = 0
    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1
        colors.append(s[i])
        lengths.append(j - i)
        i = j

    m = len(colors)

    if m == 1:
        print(0)
        return

    alive = []
    color = []
    length = []
    left = []
    right = []
    born = []

    for i in range(m):
        alive.append(True)
        color.append(colors[i])
        length.append(lengths[i])
        left.append(i - 1)
        right.append(i + 1 if i + 1 < m else -1)
        born.append(0)

    pq = []
    node_cnt = m

    def schedule(v):
        l = left[v]
        r = right[v]

        if l == -1 or r == -1:
            death = born[v] + length[v]
        else:
            death = born[v] + (length[v] + 1) // 2

        heapq.heappush(pq, (death, v))

    for i in range(m):
        schedule(i)

    answer = 0

    while pq:
        t, v = heapq.heappop(pq)

        if v >= len(alive) or not alive[v]:
            continue

        l = left[v]
        r = right[v]

        current_death = born[v] + (
            length[v]
            if l == -1 or r == -1
            else (length[v] + 1) // 2
        )

        if current_death != t:
            continue

        alive[v] = False
        answer = max(answer, t)

        if l != -1:
            right[l] = r
        if r != -1:
            left[r] = l

        if l != -1 and r != -1 and alive[l] and alive[r] and color[l] == color[r]:
            rem_left = length[l] - (
                t - born[l]
                if left[l] == -1 or right[l] == -1
                else 2 * (t - born[l])
            )

            rem_right = length[r] - (
                t - born[r]
                if left[r] == -1 or right[r] == -1
                else 2 * (t - born[r])
            )

            rem_left = max(rem_left, 0)
            rem_right = max(rem_right, 0)

            alive[l] = False
            alive[r] = False

            nl = left[l]
            nr = right[r]

            alive.append(True)
            color.append(color[l])
            length.append(rem_left + rem_right)
            left.append(nl)
            right.append(nr)
            born.append(t)

            idx = len(alive) - 1

            if nl != -1:
                right[nl] = idx
            if nr != -1:
                left[nr] = idx

            schedule(idx)

    print(answer)

if __name__ == "__main__":
    solve()
```最初の部分では、文字列を最大の同色のランに圧縮します。 ラン内のポイントは境界に到達するまで同じように動作するため、これは不可欠です。 

リンクリスト配列`left`そして`right`一定時間内に削除を実行できるようにします。 Python リストから物理的に削除するとコストがかかりすぎます。 

の`born`value には、実行が現在の形式で存在し始めたときの操作番号が記録されます。 元の実行の場合、これはゼロです。 マージされた実行の場合、それはマージ時間です。 これにより、各ラウンドを個別にシミュレートすることなく、後で実行の残りの長さを計算できます。 

プライオリティキューには消失イベントが格納されます。 一部のイベントはマージ後に廃止されます。 The validity check using`current_death`このような古いエントリは破棄されます。 

最もデリケートな部分はコンピューティングです`rem_left`そして`rem_right`。 マージ前にすでに侵食された量を差し引く必要があります。 エッジランは操作ごとに 1 ポイントを失いますが、インサイドランは 2 ポイントを失います。 マージの直前に実行の近傍を使用すると、正しい残りのサイズが得られます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(m \log m)$| 各実行では、一定数の優先キュー イベントのみが生成されます。 
| スペース |$O(m)$| 実行ごとの配列およびヒープストア情報 |

 ここ$m$は、最大の同色実行の数です。 

以来$m \le n \le 10^6$、アルゴリズムは引き続き効率的です。 すべての実行は一定の回数だけ作成、削除、場合によってはマージされますが、ヒープ操作は対数係数に寄与します。 

## テストケース```python
import sys
import io

def run(inp: str) -> str:
    import heapq

    s = inp.strip()

    colors = []
    lengths = []

    i = 0
    while i < len(s):
        j = i
        while j < len(s) and s[j] == s[i]:
            j += 1
        colors.append(s[i])
        lengths.append(j - i)
        i = j

    if len(colors) == 1:
        return "0\n"

    # Reference brute force for small tests.
    cur = list(s)
    ans = 0

    while True:
        kill = [False] * len(cur)

        for i in range(len(cur)):
            if i > 0 and cur[i - 1] != cur[i]:
                kill[i] = True
            if i + 1 < len(cur) and cur[i + 1] != cur[i]:
                kill[i] = True

        if not any(kill):
            break

        cur = [cur[i] for i in range(len(cur)) if not kill[i]]
        ans += 1

    return str(ans) + "\n"

assert run("ab\n") == "1\n", "two different colors"

 ## 特殊なケース

 次のことを考慮してください。```
aaaaaa
```There is only one run. 異なる色の隣接点を持つ点はありません。 圧縮フェーズでは 1 つのセグメントが生成され、アルゴリズムはすぐに 0 を返します。イベントを処理する必要はありません。 

考慮する：```
ab
```各点には、異なる色の隣接点があります。 どちらも最初の操作中に消えます。 ラン表現には、長さ 1 の 2 つのエッジ ランが含まれています。それらの消失時間は両方とも 1 であるため、最終的な答えは 1 です。 

次のことを考慮してください。```
aaabaaa
```The center run disappears after one operation. この時点では、外側の 2 つのランにはまだそれぞれ 2 ポイントが含まれています。 それらは長さ 4 の 1 つのランに統合され、縮小し続けます。 同じ色の近傍をマージできないソリューションでは、5 ではなく 3 が誤って返されます。 

次のことを考慮してください。```
aaaaabaaaaa
```中央`b`が先に消えます。 大きいのは２つ`a`ランは合流する前に部分的に侵食されます。 アルゴリズムは、元の長さを使用するのではなく、マージ時に残りの長さを計算します。 マージされた実行の将来の存続期間は、元のブロック サイズではなく、生き残ったポイントに依存するため、この区別は不可欠です。
