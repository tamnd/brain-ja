 ## 解決策
 ## 問題の理解

 プログラムは、依存関係グラフと一致する順序で実行する必要があるタスクで構成されます。 各タスクは以前のタスクに依存し、すべての前提条件が完了した場合にのみ実行が許可される有向非巡回グラフを形成する場合があります。 

すべてのタスクには固定の実行場所があります。 一部のタスクはメイン プロセッサで実行する必要がありますが、その他のタスクはコプロセッサに制限されます。 重要な問題は、コプロセッサが任意の順序でタスクを 1 つずつ実行しないことです。 代わりに、これを呼び出すたびに、コプロセッサ専用タスクのセットを選択します。 そのセットは、その中のすべてのタスクの依存関係がすべてすでに完了しているか、同じセットに含まれている場合にのみ有効です。 

目標は、コプロセッサの呼び出し回数を最小限に抑えながらすべてのタスクを実行することです。 メインプロセッサ タスクは呼び出しに関しては無料ですが、依然として依存関係に参加しており、コプロセッサ タスクをブロックする可能性があります。 

この制約では、最大 100,000 のタスクと依存関係が許可されるため、サブセットをシミュレートしたり、到達可能性を再計算して有効なグループの構築を繰り返し試行したりするアプローチは直ちに除外されます。 ノードまたはエッジの数が 2 次のものはすべて失敗します。 線形または線形に近いグラフの走査が必要であり、通常は O(N + M) です。 

コプロセッサ タスクがメインプロセッサ タスクを介してチェーンされている場合、微妙な障害が発生します。 たとえば、長い依存関係チェーンがメインのみのタスクとコプロセッサのみのタスクを交互に繰り返す場合、単純なグループ化ではマージが積極的すぎたり、保守的すぎたりする可能性があります。 

次の入力を考えてみましょう。```
3 2
1 0 1
0 1
1 2
```タスク 0 と 2 はコプロセッサ タスクで、タスク 1 はメイン専用です。 0 は 1 に依存し、1 は 2 に依存しますが、0 は 2 から 1 に間接的に依存しますが、1 はコプロセッサ セットにないため、0 と 2 を 1 つの呼び出しにバンドルすることはできません。 中間のメインタスクを無視する単純なアプローチでは、それらを誤ってマージする可能性があります。 

もう 1 つのエッジ ケースは、複数の独立したコプロセッサ サブツリーが存在する場合です。 グローバルな依存関係を考慮せずにそれぞれを独立して処理すると、呼び出しが過剰にカウントされたり、複数の準備完了コンポーネントに対して 1 つの呼び出しを再利用できなくなったりする可能性があります。 

## アプローチ

 ブルートフォース戦略では、実行を段階的にシミュレートします。 依存関係が満たされているすべてのコプロセッサ タスクを常に識別し、できるだけ多くのコプロセッサ タスクを 1 つのコプロセッサ呼び出しに貪欲に詰め込もうとします。 各呼び出しの後、グラフを更新して繰り返します。 これは原理的には正しいですが、最大の有効なセットを効率的に決定することが重要な点です。 最悪の場合、各呼び出しには 1 つのタスクしか含まれない可能性があり、各呼び出し後にすべてのタスクの適格性を再計算すると、グラフ全体でスキャンが繰り返されることになります。 これは、密な依存関係チェーンでは O(N²) の動作に変質します。 

構造的な洞察は、グラフが半順序を課しており、メインプロセッサのタスクがその順序で強制セパレータとして機能するということです。 コプロセッサ呼び出しは本質的にコプロセッサ ノードに対する「クロージャ操作」です。開始コプロセッサ タスクを選択したら、すでに処理されたノードまたはさらなる包含をブロックするメイン専用タスクに到達するまで、他のコプロセッサ タスクを介して後方に到達可能なすべてのコプロセッサ タスクを含める必要があります。 

サブセットの観点から考えるのではなく、視点を逆転させます。 トポロジカルな順序でタスクを処理し、コプロセッサの「セグメント」の状態を維持します。 以前の処理ではまだ満たされていないコプロセッサ タスクが発生するたびに、新しいコプロセッサ呼び出しを開始する必要がある場合があります。 呼び出しの数は、コプロセッサの世界の外に出た後、強制的にその世界に「入る」回数に相当します。つまり、メインのみのタスクが連続性を壊すことになります。 

これにより、問題は、トポロジカル トラバーサルにおける依存関係の追跡と、未解決のコプロセッサ ノードの新しいクロージャの開始を強制される頻度をカウントすることになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(N²) | O(N + M) | 遅すぎる |
 | トポロジカル + 貪欲なグループ化 | O(N + M) | O(N + M) | 承認済み |

 ## アルゴリズムのチュートリアル

 まずグラフを構築し、標準的なトポロジー順序付けの度数を計算します。 

1. カーンのアルゴリズムを使用して DAG のトポロジー次数を計算します。 これにより、すべての依存関係が、それに依存するタスクの前に処理されるようになります。 これがなければ、タスクがいつ利用可能になるかについての推論は信頼できません。 
2. 依存関係を満たすという観点から各タスクが「処理」されたかどうかを追跡する配列を維持します。 これは、すべての前提条件が満たされているかどうかに対応します。 
3. トポロジ順にタスクを繰り返します。 各タスクで、すべての依存関係がすでに解決されていることがわかります。 
4. コプロセッサー上で実行する必要があるタスクが見つかった場合、そのタスクが以前のコプロセッサー呼び出しによってすでにカバーされているかどうかを確認します。 そうでない場合、このタスクは新しいコプロセッサーの呼び出しを強制的に開始します。これは、コプロセッサーの依存関係構造における新しい接続要件を表すためです。 
5. コプロセッサ呼び出しが開始されると、概念的には、メインプロセッサのみのタスク境界を越えることなく到達できるすべてのコプロセッサ タスクが含まれます。 この伝播はトポロジー順序によって暗黙的に処理されます。ノードのすべての依存関係はすでに処理されているため、グループ化は遷移をカウントすることになります。 
6. すべてのノードが処理されるまで続行します。 新しいコプロセッサのグループ化を開始する回数が答えです。 

### なぜ効果があるのか

重要な不変条件は、コプロセッサ呼び出しを開始するたびに、依存関係の順序でコプロセッサ関連の作業の最大の連続領域をカバーしていることです。 現在アクティブな領域から到達できないコプロセッサ タスクが発生すると、そのタスクは、すでに閉じられている領域外のタスクに (直接的またはメイン タスクを通じて間接的に) 依存する必要があります。 これにより、新しい呼び出しが強制されます。 トポロジー的順序では依存関係が考慮されるため、今後の操作ではこれらの分離された領域をマージすることはできないため、カウンターの各増分は必要かつ十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, m = map(int, input().split())
    e = list(map(int, input().split()))

    g = [[] for _ in range(n)]
    indeg = [0] * n

    for _ in range(m):
        a, b = map(int, input().split())
        g[b].append(a)
        indeg[a] += 1

    q = deque(i for i in range(n) if indeg[i] == 0)
    topo = []

    while q:
        v = q.popleft()
        topo.append(v)
        for to in g[v]:
            indeg[to] -= 1
            if indeg[to] == 0:
                q.append(to)

    visited = [False] * n
    active = False
    ans = 0

    for v in topo:
        if e[v] == 0:
            continue

        if not visited[v]:
            ans += 1
            stack = [v]
            visited[v] = True

            while stack:
                x = stack.pop()
                for to in g[x]:
                    if e[to] == 1 and not visited[to]:
                        visited[to] = True
                        stack.append(to)

    print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、依存関係の方向と一致する逆隣接リストを構築し、トポロジカル ソートの次数を計算することから始まります。 カーンのアルゴリズムにより、すべての前提条件が解決された後にのみタスクが処理されることが保証されます。 

トポロジー順序を取得した後、それをスキャンし、未訪問のコプロセッサー タスクが見つかるたびに DFS のような拡張をトリガーします。 DFS は、コプロセッサ専用ノード間の依存関係の閉鎖により同じ実行バッチに強制的に組み込まれるすべてのコプロセッサ タスクをマークします。 このような各 DFS は、1 つのコプロセッサ呼び出しに正確に対応します。 

訪問された配列により、前のバッチに既に割り当てられているタスクを二重にカウントすることがなくなります。 重要な点は、コプロセッサのみのタスクを通じてのみ伝播することです。 メインプロセッサのタスクはバリアとして機能し、拡張の一部ではありません。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべてのタスクがメインのみである場合です。 このアルゴリズムは単純にすべてのノードをスキップし、DFS がトリガーされないため、答えはゼロのままです。 

もう 1 つのケースは、エッジのない完全に独立したコプロセッサ タスクのセットです。 各ノードは独自のトポロジー ルートであるため、訪問されていない各コプロセッサ ノードは、グループ化できないという事実と一致して、ちょうど 1 つの呼び出しをトリガーします。 

3 番目のケースには、コプロセッサーとメインタスクの間で交互に行われる長い依存関係チェーンが含まれます。 DFS 拡張はメイン タスクと交差することがないため、各コプロセッサ セグメントは正しく分離されます。 例えば：```
5 4
1 0 1 0 1
1 0
2 1
3 2
4 3
```ここでは、すべてのコプロセッサ ノードがメイン専用ノードによって分離されているため、それぞれが個別の呼び出しをトリガーし、3 を生成します。伝播がメイン専用頂点で停止するため、トラバーサルにより不正なマージが発生しないことが保証されます。
