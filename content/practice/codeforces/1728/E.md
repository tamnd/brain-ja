 ## 解決策
 ## 問題の理解

 各料理には、赤唐辛子または黒胡椒のいずれかの調味料を 1 つ選択する必要があります。 料理に赤唐辛子が使われている場合、それが貢献します$a_i$全体の美味しさには貢献しますが、そうでなければそれは貢献します$b_i$。 したがって、すべての料理のバイナリ割り当てを決定すると、最終スコアが完全に決定されます。 

制約は、料理ごとに赤と黒を自由に選択できないことです。 代わりに、最初に 1 つのショップを選択する必要があります。 私たちはその店から、赤いパッケージと黒いパッケージをいくつか購入します。 赤いパッケージはそれぞれ味付け可能$x_j$料理に合わせて、それぞれの黒いパッケージに味付けができます。$y_j$食器。 買ったら$x$赤いパッケージと$y$黒いパッケージの場合、赤い味付けの料理の総数は$x \cdot x_j$、黒味付けの料理は、$y \cdot y_j$、これらの合計は正確に次のようになります。$n$。 食べ残しは許されないので、すべてを分割する必要があります$n$皿を 2 つのグループに分け、そのサイズがこの線形制約に一致するようにします。 

したがって、各ショップに対して、私たちは次のことを尋ねています。$n$以下の非負の組み合わせとして$x_j$そして$y_j$、「はい」の場合、選択した金額の達成可能な最大の合計はいくらですか$a_i$または$b_i$その制限の下での値。 

制約は大きく、両方とも$n$ショップの数は最大で$3 \cdot 10^5$。 考えられるすべてのパッケージ数をショップごとに 2 次またはショップごとに列挙することは不可能です。 Even a per-shop$O(n)$再計算が遅すぎる可能性があります。 

主な難しさは、実現可能性が店舗ごとのディオファントスの線形方程式を解くことに依存し、最適化が赤と黒に割り当てられる皿の数に依存することです。 

いくつかのエッジの状況は見逃しがちです。 

1 つはパリティまたは割り算の制約です。 両方の場合$x_j$そして$y_j$が偶数であれば、達成可能な合計はすべて偶数になります。 奇数の場合$n$、答えはすぐにわかります$-1$。 たとえば、次の場合$n = 3$、$x_j = 2, y_j = 2$、解決策は存在しません。 

もう 1 つの微妙なケースは、1 種類のパッケージのみが実質的に重要である場合です。 もし$x_j = y_j$の場合、すべてのパッケージが同じサイズに寄与し、可能な合計はその値の倍数だけになります。 単純なソルバーは、赤と黒の割り当てを混合しようとするかもしれませんが、実現可能性を決して尊重しません。 

最後に、たとえ実現可能性があったとしても、どの皿が赤であるかの最適な割り当ては、店舗の構造とは独立しており、強制的に割り当てる赤の数によってのみ決まります。 

## アプローチ

 固定ショップに対する直接総当たりアプローチはすべてのペアを試行します$(x, y)$そのような$x x_j + y y_j = n$。 実行可能なペアごとに、どちらを選択するかを決定する必要があります。$x x_j$皿が赤くなる。 一定数の赤いスロットの場合$k$、最良の課題は、$k$の最大値$a_i - b_i$、皿を黒から赤に変換すると、その差分だけスコアが増加するためです。 

したがって、ショップごとに総当りを行うと、次のようになります: 実行可能なものをすべて列挙する$k$、そのための最良のゲインを計算します$k$、最大値を取ります。 差分を事前に計算して一度ソートし、実行可能なものをすべて列挙したとしても$k$それでも、ショップごとにコインの方程式を解き、複数の候補を評価する必要があります。 最悪の場合、解の数は次のようになります。$O(n)$ペットショップにつながる$O(nm)$それは限界をはるかに超えています。 

構造的な観察によると、実現可能な値は$k$、赤い皿の数は任意ではなく、次のように決定される等差数列内にあります。$x_j$そして$y_j$。 方程式を書き直すと$$k = x x_j,\quad n - k = y y_j,$$実現可能性は次のようになります。$$k \equiv 0 \pmod{x_j}, \quad n - k \equiv 0 \pmod{y_j}.$$これは古典的な 2 モジュラス制約です。 これは、解が存在しないか、単一剰余クラスのモジュロを形成する解がある線形合同系を解くことになります。$\mathrm{lcm}(x_j, y_j)$。 

valid の構造がわかったら、$k$の場合、最適化は、いくつかの候補値にわたってソートされた差異の最適なプレフィックスを選択することになります。 進行ステップが大きいか、有効な値の数が少ないため、ソートされたプレフィックス合計を前処理した後、各ショップを対数時間または定数時間で処理できます。$a_i - b_i$。 

ソートされた差分配列を 1 回事前計算します。 次に、プレフィックスの合計を使用して、任意の値を評価できるようになります。$k$で$O(1)$。 各ショップはモジュラー方程式を解き、せいぜい 1 つまたは 2 つの候補をチェックするだけです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ブルートフォース |$O(m \cdot n)$|$O(n)$| 遅すぎる |
 | 最適 |$O(n \log n + m)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 差を計算する$d_i = a_i - b_i$すべての料理について配列を降順に並べ替えます。 これにより、最初の$k$要素は常に、選択から可能な最大の利益をもたらします。$k$赤い皿。 
2. 正確に選択した場合の最良の寄与を迅速に計算できるように、ソートされた差分に対してプレフィックス合計配列を構築します。$k$赤い皿。 これにより、合計を繰り返し再計算する必要がなくなります。 
3. 店舗ごとに制約を解釈する$x x_j + y y_j = n$。 赤い皿の数を条件として書き直す$k = x x_j$、 それで$n - k$で割り切れる必要があります$y_j$。 
4. 合同系を解きます。$$k \equiv 0 \pmod{x_j}, \quad k \equiv n \pmod{y_j}$$モジュラー演算を使用して。 これにより、解が得られないか、単一の剰余クラスモジュロが得られます。$\mathrm{lcm}(x_j, y_j)$。 
5. 有効な形式が完成したら、$k$が決定されている場合、実現可能な値のみを列挙します。$k$に横たわっている$[0, n]$。 実際には、ステップ サイズが少なくとも 1 つの完全なパッケージ アライメントであるため、ショップごとに最大でも一定数の候補が生成されます。 
6. 各候補者について$k$、合計の美味しさを次のように計算します。 

上からの最高の赤の貢献$k$違いに、すべての皿が黒いベースラインを加えたものです。 
7. 候補の最大値を出力する、または$-1$有効でない場合$k$存在します。 

### なぜ効果があるのか

 並べ替え順$a_i - b_i$赤い皿の数がわかったら、任意の割り当ての最適な構造を修正します。 唯一の自由はどちらを選択するかです$k$皿は赤くなり、最大の差を貪欲に取ることで利益が最大化されます。 

モジュラー制約により、実現可能な値が保証されます。$k$ショップによって完全に決定された厳格な算術構造を形成します。 すべての有効な解はこの構造に分類されるため、最適な割り当てを見つけるには、その構造の代表のみをチェックするだけで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def extended_gcd(a, b):
    if b == 0:
        return a, 1, 0
    g, x1, y1 = extended_gcd(b, a % b)
    return g, y1, x1 - (a // b) * y1

def mod_inv(a, mod):
    g, x, _ = extended_gcd(a, mod)
    if g != 1:
        return None
    return x % mod

n = int(input())
a = []
b = []

base = 0
diff = []

for _ in range(n):
    ai, bi = map(int, input().split())
    a.append(ai)
    b.append(bi)
    base += bi
    diff.append(ai - bi)

diff.sort(reverse=True)
pref = [0]
for v in diff:
    pref.append(pref[-1] + v)

m = int(input())
out = []

for _ in range(m):
    x, y = map(int, input().split())

    # solve x*k + y*(n-k) structure -> k = x*red_count
    # brute reduction via modular alignment
    g = extended_gcd(x, y)[0]

    if n % g != 0:
        out.append(-1)
        continue

    # reduce equation: x*r + y*b = n, r+b = packages not directly needed
    # we search k = number of red dishes = x*r

    # We derive r from linear equation:
    # x*r + y*s = n => r = (n - y*s)/x
    # but we only need feasible k values

    # Instead compute using modular inverse on reduced system
    x0, y0 = x // g, y // g
    n0 = n // g

    inv = mod_inv(x0, y0)
    if inv is None:
        out.append(-1)
        continue

    # one solution for r modulo y0
    r0 = (n0 % y0) * inv % y0

    k0 = r0 * x
    step = (x * y0)

    # try candidates k = k0 + t*step
    best = -1

    # we only need at most 2 candidates within [0,n]
    for t in range(3):
        k = k0 + t * step
        if 0 <= k <= n:
            red = k
            val = base + pref[red]
            best = max(best, val)

    out.append(best)

print("\n".join(map(str, out)))
```解決策は、すべての料理をベースラインの黒の値に加え、赤になった場合のゲインに変換することから始まります。 この分離により、プレフィックス合計が有効になります。 

モジュラー演算部分は、ショップの実現可能性条件をエンコードします。 割り算の制約が一貫するように gcd を使用して方程式を縮小し、逆モジュラーを使用して縮小合同を解きます。 

最後のループでは、すべての有効な解が大きなステップ サイズの周期構造内に存在し、完全な列挙が不要になるため、一定数の候補赤カウントのみが評価されます。 

よくある間違いは、何かを想定してしまうことです。$k$割り算が成り立つと達成可能です。 一致ステップは、赤と黒のパッケージ数が同時に整数であることを強制するものです。

 ## 特殊なケース

 いつ$x_j$そして$y_j$両方とも大きいですが、1 より大きい gcd を共有しており、多くの$n$価値観はすぐに不可能になります。 アルゴリズムは、最適化の前に gcd 削減ステップを通じてこれを捕捉します。 

いつすべて$a_i = b_i$、すべての差はゼロです。 ソートとプレフィックスの合計はすべて 0 を生成するため、実行可能などのショップでも同じ合計が得られ、アルゴリズムは実行可能性のチェックのみに正しく組み込まれます。 

いつ$n$は小さいですが、パッケージのサイズが大きいため、有効なショップは非常に限られています。 モジュラーチェックはほぼすべてを即座にフィルタリングし、縮退した入力でも効率を確保します。
