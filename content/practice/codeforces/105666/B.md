 ## 解決策
 ## 問題の理解

 私たちには、それぞれ 2 つの強さの値で記述される独自のモンスターのセットが与えられます。 最初の値はタイプ 0 の敵と戦うときのモンスターの強さを表し、2 番目の値はタイプ 1 の敵に対するそのモンスターの強さを表します。 また、それぞれが 2 つのタイプのいずれかに正確に属する、対戦相手のモンスターのコレクションも与えられます。 タイプ 0 の敵は最初の戦力値を使用してのみ戦うことができ、タイプ 1 の敵は 2 番目の戦力値を使用してのみ戦うことができます。 

このタスクは、すべての敵が個別のモンスターによって倒され、選択されたモンスターが対応するタイプで十分な強さを持っているように、すべての敵モンスターに自分のモンスターを割り当てることが可能かどうかを判断することです。 

最大の難点は、各モンスターはどちらの役割でも使用できる可能性があるという意味で柔軟ですが、一度割り当てられると消費されてしまうことです。 強力な万能モンスターを間違った場所で使用すると、後で実現可能性が妨げられる可能性があるため、この決定はローカルなものではありません。 

入力サイズは、モンスターと敵の数が両方とも最大 100,000 のオーダーまで大きくなる可能性があることを示唆しています。 これにより、すべてのペアリングを試したり、大きなオーバーヘッドを伴うフロー アルゴリズムを実行したりするなどの 2 次マッチング アプローチが即座に除外されます。 解は線形または対数線形に近い必要があり、通常は O(n log n) であり、これは並べ替えと貪欲な選択を強く示唆しています。 

1 つのタイプが大きく優勢な場合、微妙な特殊なケースが発生します。 たとえば、タイプ 0 の敵が多数いて、それらを処理できるモンスターが少数である場合、利用可能な最強のモンスターを貪欲に各敵に割り当てるという単純な戦略は、後でタイプ 1 の敵がさらに強力な割り当てを必要とするときに失敗する可能性があります。 もう 1 つの失敗モードは、2 つのモンスターの属性を独立して処理することです。これは、各モンスターが両方のタイプ間で共有されるリソースであることを無視します。 

## アプローチ

 強引な解釈は、これを 2 部構成の割り当て問題とみなすことです。 各敵は、その要件を満たす個別のモンスターと一致する必要があります。 バックトラッキングまたは最大 2 部マッチングを試みることもできます。 正しいとはいえ、このアプローチでは多くの割り当てを検討する必要があります。 最悪の場合、n 個のモンスターのそれぞれが複数の方法で n 人の敵に割り当てられる可能性があり、指数関数的な分岐、またはフローベースのメソッドでは少なくとも O(n³/2) 個の動作が発生しますが、これは大規模な入力には遅すぎます。 

重要な観察は、各敵タイプ内で必要な強さによって分類すると、支配構造が明らかになるということです。 固定タイプの敵を強さの降順に処理すると、より強い敵を倒すことができるモンスターは、同じタイプの弱い敵をすべて倒すことができます。 これにより、単調な実現可能領域が作成されます。 

この順序を修正すると、問題は、敵の要件のしきい値ごとに、それを満たす最も弱いモンスターを選択することになります。 これが最適な理由は、後のより厳しい制約のためにより強力なモンスターを保存しておくことで、将来の失敗を防ぐためです。 これは、しきい値制約の下での古典的な貪欲マッチングです。 

まず、モンスターの最初の強さの値のみを使用して、すべてのタイプ 0 の敵を解決します。 次に、タイプ 1 の敵を 2 番目の強度値を使用して個別に解決します。 この正しさは、有効なグローバル割り当てが存在する限り、利用可能な最適な割り当てを使用してすべてのタイプ 0 の敵を処理することにコミットすると、残りのプールはタイプ 1 の処理に十分であるという事実から来ています。

 ## アルゴリズムのチュートリアル

 各敵のタイプを個別に扱いますが、常にモンスターの共有プールから消費します。

まず、すべての零式の敵を強さの降順に並べ替えます。 これにより、モンスターを割り当てるときに、最も制限的な制約が最初に処理されるようになります。 最も難しい要件を満たすことができれば、強いモンスターを誤って簡単なモンスターに浪費することはなくなります。 

2つ目は、無駄を最小限に抑えながら、特定の敵を倒すことができるモンスターを素早く選択できる構造を維持することです。 具体的には、所定のしきい値 q に対して、関連する次元で少なくとも q の強さを持つすべての未使用のモンスターの中で、可能な限り最小の二次的な強さを持つモンスターが必要です。 この選択により、将来の制約に対して柔軟なモンスターを利用できるようになります。 

3 番目に、タイプ 0 の敵をソート順に繰り返し処理します。 それぞれの敵に対して、十分なタイプ 0 の強度を持つ有効なモンスターを見つけ、タイプ 1 の強度が最も小さいモンスターを貪欲に選択します。 いかなる時点でもそのようなモンスターが存在しない場合、完全な割り当ては不可能であると即座に結論付けます。 

第 4 に、タイプ 0 の敵をすべて割り当てた後、残りのモンスターの 2 番目の強度値を使用してタイプ 1 の敵に対して同じ手順を繰り返します。 

最後に、両方のフェーズが成功すると、すべての敵に固有のモンスターが割り当てられ、YES が返されます。 

### なぜ効果があるのか

 不変条件は、固定された敵タイプを処理する各ステップで、将来の割り当てのために最も有用な残りのモンスターを常に保存することです。 敵を降順に処理することにより、現在の敵に対して有効なモンスターは、そのタイプの残りの弱い敵すべてに対しても有効になります。 クロスタイプの強さを最小限に抑えたモンスターを選択することで、不必要に柔軟性を破壊することがなくなります。 この貪欲な構造は、より強力なクロスタイプのモンスターを先に使用する代替割り当ては、後のステップの解決スペースを減らすだけであるため、ローカルの決定がグローバルな実現可能性を妨げることを防ぎます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    ours = []
    for _ in range(n):
        a, b = map(int, input().split())
        ours.append([a, b])
    
    t0 = []
    t1 = []
    for _ in range(m):
        t, p = map(int, input().split())
        if t == 0:
            t0.append(p)
        else:
            t1.append(p)
    
    def check(idx):
        import heapq
        
        monsters = ours[:]
        monsters.sort(key=lambda x: x[idx])
        
        enemies = t0 if idx == 0 else t1
        enemies.sort(reverse=True)
        
        # we maintain a pointer and a heap of candidates
        i = 0
        heap = []
        
        for q in enemies:
            while i < n and monsters[i][idx] >= q:
                # push by the other attribute
                heapq.heappush(heap, monsters[i][1 - idx])
                i += 1
            
            if not heap:
                return False
            
            heapq.heappop(heap)
        
        return True
    
    if check(0) and check(1):
        print("YES")
    else:
        print("NO")

if __name__ == "__main__":
    solve()
```この実装では、プロセスを 2 つの対称フェーズに分割し、次のように制御します。`idx`。 いつ`idx = 0`、モンスターの最初の属性を使用してタイプ 0 の敵をマッチングし、2 番目の属性によって候補を優先します。 アクティブな属性によってモンスターを並べ替えることで、敵の閾値が減少するにつれて有効な候補を段階的にアクティブ化できるようになります。 

ヒープには、現在または将来の敵に対して現在適格であるすべてのモンスターの二次的な強さの値が保存されます。 新しい敵の閾値に遭遇するたびに、新たに適格なモンスターをすべてヒープに押し込みます。 ヒープポップは常に最小の二次コストを持つモンスターを選択します。これは柔軟性を維持するという貪欲な要件に一致します。 

よくある間違いは、資格はポインタを介して段階的に維持する必要があることを忘れていることです。`i`。 敵ごとにすべてのモンスターを再スキャンすると、複雑さは O(n²) まで増加します。 もう 1 つの微妙な点は、割り当て時にヒープから削除されるため、各モンスターはフェーズごとに最大 1 回しか使用されないことです。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、同じ種類の敵に対処できるモンスターよりも多くの敵が存在する場合です。 すべてのモンスターのタイプ 0 の強さは最大 3 ですが、5 を必要とする敵がいるとします。ソート中、この敵が最初に表示され、ヒープは有効な候補を受け取らないため、アルゴリズムはすぐに NO を返します。 これにより、後で不正確な部分割り当てが行われるのを防ぎます。 

もう 1 つのエッジ ケースは、単一の非常に強力なモンスターですべての敵を処理できるにもかかわらず、貪欲な選択により、単純なアプローチでは早すぎるタイミングでそれを割り当ててしまう場合です。 このアルゴリズムでは、有効な候補の中から二次的な強さが最小限のモンスターを常に選択し、閾値の実現可能性のために厳密に必要な場合にのみ強いモンスターを保存するため、そのようなことは起こりません。 

最後のケースは、実現可能性がグローバルに存在するが、慎重にタイプ間分散を行った場合のみである場合です。 2 つのフェーズへの分離が機能するのは、タイプ 0 の割り当てが貪欲に修正されると、タイプ 1 の残りの構造では、完全な解決策が存在するときは常に有効なマッチングが許可されるためです。これは、貪欲によってすべての有効な割り当てが同時にブロックされることがないためです。
