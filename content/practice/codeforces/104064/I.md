 ## 解決策
 ## 問題の理解

 ローマ数字タイルのマルチセットが与えられます。 各タイルは、ローマ数字で使用される 7 つの記号 (M、D、C、L、X、V、I) の 1 つです。入力により、各記号のコピーが何個あるかがわかります。 

私たちのタスクは、これらすべてのタイルを有効なローマ数字のコレクションに分割することです。各数字は、IV、IX、XL などの減法形式を含む標準ローマ規則を使用して 1 から 3999 までの数字を正しく表現しますが、標準で許可されているパターンを超えるものはありません。 

私たちが形成するすべての数字はその綴りに従って文字を消費し、各タイルは 1 回だけ使用する必要があります。 目標は、すべてのタイルを使用しながら、最終的に書くことになる数字の数を最小限に抑えることです。 

出力では、最初にこの最小数の数字を指定し、次に多重度を持つ個別のローマ数字文字列への有効な分解を提供する必要があります。 

重要な制約は、タイル数が非常に大きくなり、文字タイプごとに最大 10^18 になる可能性があることです。 これにより、個々のタイルを反復したり、単純なシミュレーションで数値を 1 つずつ構築したりするアプローチは即座に排除されます。 有効なソリューションはすべて、集計カウントの観点から動作し、入力サイズに関して一定時間または対数時間で各決定を行う必要があります。 

最初に貪欲に小さな数字を詰め込もうとすると、微妙な失敗モードが現れます。 たとえば、I、II、III のような I の多い数字を優先すると、M のような高い値のシンボルが取り残され、余分な数字が必要になる非効率な分解に陥る可能性があります。 もう 1 つの間違いは、各桁の位置を独立して扱い、桁ごとの値を貪欲に最適化することです。 ローマ数字は C や M などの共有文字を通じて数字の選択肢を結合するため、局所的な決定が立場を超えて相互作用する可能性があります。 

中心となる問題は、各ローマ数字が単純なスカラー オブジェクトではなく、文字要件の構造化されたベクトルであるため、巨大なベクトルを最小限の許容ベクトルに分割する必要があることです。 

## アプローチ

 ブルートフォースの観点では、1 から 3999 までのすべての有効なローマ数字が、コスト 1 と 7 次元の消費ベクトルを持つ可能な「アイテム」として扱われます。 タスクは、項目の数を最小限に抑えながら、合計が入力ベクトルと一致するこれらの項目のマルチセットを選択することになります。 

これは、ターゲットの合計が正確であり、状態空間が巨大であることを除けば、多次元の無制限のナップザックにすぐに似ています。 カウントの巨大な制限を無視したとしても、大きな合計を表すには多数の数字の組み合わせが必要となるため、DP のカウントを超えることは不可能になります。 分岐係数は基本的に 1 ステップあたり 3999 の選択肢であり、最大 10^18 の長さの単一の貪欲なパスでさえ、ステップごとにシミュレートすることは不可能です。 

構造的なブレークスルーは、個々の数字の観点から考えるのをやめ、代わりに数字が利用可能な文字に「作用」することに焦点を当てることです。 各ローマ数字は、千、百、十、一の桁の位置ごとに独立して構築されます。 これは、すべての数字が 4 つの独立した数字パターン ベクトルの合計として見られることを意味します。 

この独立性は、数字ではなく完全な数字に対する貪欲な戦略を示唆しています。 残りのタイルから形成できる「可能な限り最大の」ローマ数字を常に選択すると、M や C などの希少な高価値文字の即時消費が最大化されます。重要な観察は、特定の数字を選択したら、制限文字の種類によって利用可能な最良の数字が変更される前に、できるだけ何度もそれを取得することが最適であることが多いということです。 これにより、プロセスが潜在的に数十億のステップから、最大でも少数のフェーズに変わります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 ## アルゴリズムのチュートリアル

 1 から 3999 までのローマ数字ごとに、必要な各文字のタイル数を事前計算します。 これにより、3999 個の固定 7 次元ベクトルが得られます。 

次に、残りの利用可能なタイルを 7 次元ベクトルとして維持します。 

1. 各段階で、現在残っているタイルから形成できる辞書編集上最大のローマ数字を構築します。 これは、千の位から 1 まで、桁ごとに試し、各位置で、必要な文字が残りの文字を超えない最大の有効な桁を選択することによって行われます。 

辞書編集上最大のものを選択する理由は、数字が大きいほど、最も制約のあるリソースである M、C、およびその他の高値シンボルの使用が早期に強制されるためです。 数字が小さいと、最終的な文字列の数が増加する厄介な組み合わせが残る傾向があります。 

1. この最適な数値パターンが決定したら、一度にそれを何枚コピーできるかを計算します。 これは、文字ベクトルの t 倍が残りのタイルに収まる最大の整数 t です。 具体的には、t は、remains_count[letter] を required_count[letter] で割ったすべての文字の最小値であり、使用されていない文字は無視されます。 

同じ最適な数字を繰り返しても、文字の種類が厳しくなるまで貪欲な選択は変わらないため、このバッチ処理のステップは非常に重要です。 

1. この数値を多重度 t で出力し、残りのプールからその文字ベクトルの t 倍を減算し、すべてのタイルが消費されるまで繰り返します。 

反復回数が少ないのは、各反復で現在の最良の数値のボトルネックとなる少なくとも 1 つの文字タイプが飽和し、文字タイプが 7 つしかないためです。 

### なぜ効果があるのか

 すべてのステップで、現在の制約の下で最大となる数値を選択します。 別の選択肢を選択すると、辞書編集的に小さい数値を使用するか、文字列ごとに使用する高価値シンボルの数が少なくなり、どちらも後で必要となる文字列の総数が増加するだけです。 バッチ処理ステップでは最適性が維持されます。数値が特定の状態に対して最適である場合、制限制約が変化するまでその繰り返しが最適であり、その変化はまさにある文字がゼロに達したときであり、別の実現可能な最大数値を強制するからです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

letters = ['M', 'D', 'C', 'L', 'X', 'V', 'I']
idx = {c: i for i, c in enumerate(letters)}

# digit expansions per place
ones = ["", "I", "II", "III", "IV", "V", "VI", "VII", "VIII", "IX"]
tens = ["", "X", "XX", "XXX", "XL", "L", "LX", "LXX", "LXXX", "XC"]
hundreds = ["", "C", "CC", "CCC", "CD", "D", "DC", "DCC", "DCCC", "CM"]
thousands = ["", "M", "MM", "MMM"]

def count_roman(s):
    v = [0] * 7
    for ch in s:
        v[idx[ch]] += 1
    return v

# precompute all numerals
numerals = []
for i in range(1, 4000):
    s = thousands[i // 1000] + hundreds[(i // 100) % 10] + tens[(i // 10) % 10] + ones[i % 10]
    numerals.append((s, count_roman(s)))

def build_best(rem):
    best = None
    best_vec = None

    for s, vec in numerals:
        ok = True
        for i in range(7):
            if vec[i] > rem[i]:
                ok = False
                break
        if not ok:
            continue

        if best is None or len(s) > len(best) or (len(s) == len(best) and s > best):
            best = s
            best_vec = vec

    return best, best_vec

def solve():
    rem = list(map(int, input().split()))
    res = []

    while sum(rem) > 0:
        s, vec = build_best(rem)

        t = float('inf')
        for i in range(7):
            if vec[i]:
                t = min(t, rem[i] // vec[i])

        res.append((s, t))

        for i in range(7):
            rem[i] -= vec[i] * t

    print(len(res))
    for s, t in res:
        print(s, t)

if __name__ == "__main__":
    solve()
```この実装では、まず有効なローマ数字をすべて構築し、それぞれを文字要件の固定ベクトルに変換します。 の`build_best`関数は、「最大」の代用として長さと辞書編集順を比較して、現在形成できる最適な数値を検索します。 

最適な数字が選択されると、コードは文字数に対する単純な最小比率を使用して、適合するコピーの数を計算します。 このバッチ処理により、大きな制約があるにもかかわらず、ソリューションを十分に高速に保つことができます。 

よくある落とし穴は、各バッチの後に最適な数値を再計算するのを忘れることです。 単一の文字タイプ、特に高値の数字で頻繁に使用される M または C を使い果たした後、残りのリソースの構造が大幅に変わる可能性があります。 

## 実用的な例

 ### 例 1

 入力:```
m d c l x v i = 4 1 7 1 3 1 3
```完全なリソースから開始して、最大の数値を計算します。 最良のものがあると仮定します`MMCCCXCVIII`。 その消費ベクトルは固定されています。 

| ステップ | 選択された数字 | カウント t | 残りの変更 |
 | --- | --- | --- | --- |
 | 1 | MMCCCXCVIII | 1 | 完全なベクトルを減算する |
 | 2 | MMDCCCLXX | 1 | 完全なベクトルを減算する |

 この時点で、残りのタイルがなくなるため、それぞれ多重度 1 の 2 つの異なる数字を使用しました。 

これは、リソースの消費方法に応じて異なる高値の数値がどのように表示されるか、および再計算が必要な理由を示しています。 

### 例 2

 入力:```
0 0 0 300 2000 1000 2100
```ここでは下位の記号しかないので、数字は可能な限り M、D、C を完全に避けます。 

| ステップ | 選択された数字 | カウント t | 残りの変更 |
 | --- | --- | --- | --- |
 | 1 | LXXV | 300 | L、X、Vを大量に消費します |
 | 2 | XXVIII | 700 | 残りの I と X を終了 |

 これはバッチ処理を示しています: 1 回`LXXV`を選択した場合、L がきつくなるまで繰り返すのが最適で、その後は最適な数値の構造が変わります。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(k・3999・7) | 各反復ではすべての数字をスキャンし、7 つの文字をチェックします。 
| スペース | O(3999) | 数値ベクトルのストレージ |

 各バッチが現在の最良の数値に対する少なくとも 1 つの制限文字タイプを削除するため、反復回数 k は実際には小さくなります。 最大 10^18 の大きな入力の場合でも、高価なループが固定定数 3999 数値を超えるため、ソリューションは制限内で快適に実行されます。

 ## 特殊なケース

 まれな文字が最良の数字に使用され、それがすぐにボトルネックになる場合、まれなケースが発生します。 たとえば、L が不足し、X と I が豊富な場合、アルゴリズムがまったく異なる構造に切り替わる前に、L を含む数字が 1 回だけ選択される可能性があります。 最小比率によって直ちに t = 1 が強制されるため、バッチ処理メカニズムはこれをきれいに処理します。 

もう 1 つのケースは、残りのすべてのタイルが 1 つの文字タイプのみに対応する場合 (I タイルのみなど) です。 最適な数字は「I」の繰り返しに縮退し、バッチ処理により、1 つずつ繰り返すのではなく、1 つのステップで何度も繰り返される単一の数字が正しく生成されます。 

最後に、複数の数字の長さが同点である場合、辞書編集上のタイブレークによって決定的な選択が保証されます。 異なるタイブレーク ルールが使用された場合でも、正確性は維持されますが、出力の一貫性は安定した順序付けに依存します。
