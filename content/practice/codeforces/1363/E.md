 ## 解決策
 ## 問題の理解

 各ノードが 2 ビットの情報 (最初の 2 進数と必要な最後の 2 進数) を運ぶルート付きツリーが与えられます。 タスクは、任意のサブツリーを取得し、その中のノードの任意のサブセットを選択し、選択したノード間でビットを自由に並べ替えることができる特別な操作を使用して、初期構成をターゲット構成に変換することです。 このような操作のコストは、サブツリー ルートと選択したノードの数のみに依存します。具体的には、選択したサブセットのサイズにそのサブツリー ルートのコストを乗算した値に比例します。 

操作の主な効果は、サブツリー内の選択されたサブセット内で、値を任意に再分配できることです。 これは、エッジに沿って段階的に移動するのではなく、操作のルートとして選択する先祖に応じて安くなったり高価になったりする柔軟な「混合ゾーン」を作成することを意味します。 

この制約は十分に大きいため、操作を明示的にシミュレートしようとするソリューションは不可能です。 最大 200,000 ノードの場合、ノードのサブセットまたはペアごとの転送を推論するアプローチはすぐに 2 次またはそれ以上のものになります。 これにより、各ノードが上に送信する必要があるもの、または下から吸収する必要があるものを要約するツリー DP の観点に進むことができます。 

微妙な難しさは実現可能性から生じます。 初期構成の 1 の合計数がターゲット構成の 1 の合計数と一致しない場合、シャッフルではマルチセットがグローバルに保持されるため、一連のシャッフルではこれを修正できません。 このグローバル制約を無視する単純な実装では、誤ってコストを構築しようとします。 

別の失敗例は、サブツリーに 1 種類の数字しか含まれていないが、変換後に両方の種類を生成する必要がある場合に発生します。 たとえば、サブツリーにゼロのみが含まれているが、ターゲットには 1 が必要で、移動できる場所が他に存在しない場合、答えは不可能であるはずです。 これはノードごとにローカルではなく、欠損がツリー全体にどのように伝播するかによって異なります。 

## アプローチ

 ブルート フォース ビューでは、選択したサブツリー内でトークンを移動するように各操作をモデル化し、考えられるすべてのサブセットと順列を効果的にシミュレートしようとします。 最適なサブセットの選択に限定したとしても、すべてのサブセットが有効で、すべての順列が許可されるため、ノードあたりの可能性の数はサブツリー サイズで指数関数的に増加します。 これはすぐに手に負えなくなります。 

重要な観察は、この操作が実際にはノードの ID には依存せず、0 と 1 のカウントのみに依存するということです。 サブツリー操作の内部では、ビットの供給と需要が効果的に再配分され、コストは操作を実行する場所を選択するかどうかによって異なります。 上位の祖先を選択すると、ツリーの下位で複数のローカル操作を実行する場合と比較して、ノードごとに支払うコストが少なくなります。 

これは貪欲なアイデアにつながります。つまり、各ノードで、そのサブツリー内の初期構成とターゲット構成の間の不一致の数を、このノードを通じて「解決」する必要があるかを決定したいと考えています。 各ノードは、その子からの余剰と不足を照合できる潜在的な「コンベヤー」のように動作します。 最適な戦略は、不一致をボトムアップで結合し、常にペアリングが発生する最も安価な場所を考慮することです。 

これにより、問題はツリー DP に還元され、各ノードがそのサブツリーに残っている過剰な 0→1 および 1→0 変換の数と、内部ペアをローカルで解決するための最小コストを計算します。

 | --- | --- | --- | --- |
 | ブルート フォース (サブセット シミュレーション) | 指数 | O(n) | 遅すぎる |

 ## アルゴリズムのチュートリアル

ノード 1 でツリーをルート化し、事後 DFS を実行します。 各ノードについて、サブツリー内で未解決のまま残っている各タイプの不一致の数を追跡します。 

ノードごとに 2 つの数量を定義します。サブツリー内で現在 1 を持つ 0 を必要とするノードの数と、現在 0 を持つ 1 を必要とするノードの数です。 

1. ルートから DFS を実行して、各ノードが自身を処理する前に子からの情報を集約します。 これにより、現在のノードでサブツリーを解決する方法を決定する前に、サブツリーの完全な不一致構造を常に知ることができます。 
2. 各ノードについて、そのノード自体の初期ビットとターゲット ビットに基づいてローカルな不一致を計算します。 0→1 の場合、1 に対する 1 つの要求が寄与します。1→0 の場合、0 に対する 1 つの要求が寄与します。これにより、ノードの要件がサブツリー構造から独立して分離されます。 
3. 不一致数を合計して、子の結果を現在のノードにマージします。 この段階で、サブツリー内のすべての未解決の要求の完全なビューが得られます。 
4. ノード u で、子からの反対側の不一致を「一致」させようとします。 サブツリー内では値を任意にシャッフルできるため、0→1 の不一致は 1→0 の不一致をキャンセルできます。 このようなキャンセルの数は、2 つのカウントの最小値です。 
5. 各キャンセルは、u をルートとする演算を使用して修正できるノードのペアを表します。 このようなペアを 1 つ修正するコストは、ペアリングを明示的にシミュレートした場合にのみ 2 * a_u ですが、最適な解釈は、u を通るフローの各単位が a_u に比例するコストに寄与するということです。 したがって、ローカルキャンセル後に u を通過する不一致の数に基づいてコストが累積されます。 
6. キャンセル後、残りの不一致は親に渡されます。これは、不一致はこのサブツリー内で完全には解決できず、操作が潜在的に低コストとなるツリーの上位で処理する必要があるためです。 

重要な認識は、すべての不一致はペアになる場所を見つけるまで移動する必要があるということです。 このような最も安価な場所は、両方のタイプの不一致がまだ含まれているパス上の可能な限り高いノードです。 これが、DFS での集約が機能する理由です。 

### なぜ効果があるのか

 このアルゴリズムは、ノード u を処理した後、そのサブツリー内のすべての不一致が 1 つのタイプの純余剰としてのみ表されるという不変条件を維持します。これは、ローカルでペアになることができた場合に、両方のタイプを同時に上に運ぶことは決してないことを意味します。 操作ではサブツリー内での任意の置換が許可されるため、ローカルで実行できるペアリングは常に、上方向に遅延させるのと少なくとも同じくらい効果があり、一般に祖先コストは小さくないため、遅延させるとコストが増加するだけです。 これにより、すべてのキャンセルが最も有益なポイントで実行され、全体的に最小限のコストが生成されると同時に、不一致の要件が根元で解決されないままにならないようにすることで実現可能性が確保されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    n = int(input())
    a = [0] * (n + 1)
    b = [0] * (n + 1)
    c = [0] * (n + 1)

    for i in range(1, n + 1):
        ai, bi, ci = map(int, input().split())
        a[i] = ai
        b[i] = bi
        c[i] = ci

    g = [[] for _ in range(n + 1)]
    for _ in range(n - 1):
        u, v = map(int, input().split())
        g[u].append(v)
        g[v].append(u)

    INF = 10**30

    def dfs(u, p):
        zero = 0
        one = 0
        cost = 0

        if b[u] == 0 and c[u] == 1:
            one += 1
        elif b[u] == 1 and c[u] == 0:
            zero += 1

        for v in g[u]:
            if v == p:
                continue
            z, o, cst = dfs(v, u)
            cost += cst

            # match opposite demands
            m = min(zero, o)
            zero -= m
            o -= m

            m = min(one, z)
            one -= m
            z -= m

            zero += z
            one += o

        # if both remain, they must be paired at this node
        m = min(zero, one)
        zero -= m
        one -= m

        # each remaining pair contributes cost at this node
        cost += (zero + one) * a[u]

        return zero, one, cost

    z, o, ans = dfs(1, -1)

    if z != 0 or o != 0:
        print(-1)
    else:
        print(ans)

if __name__ == "__main__":
    solve()
```DFS は、サブツリーごとに、最大のローカル ペアリングの後に残っている不一致の要求の数を計算します。 変数`zero`そして`one`は、それぞれタイプ 1→0 および 0→1 の不一致を表します。 子をマージすると、反対側の不一致はすぐにキャンセルされます。これは、そのようなペアは上にプッシュする必要がなく、現在のノードのサブツリーで解決できるためです。 

マージ後、現在のノードで残りのペアを再度キャンセルし、一致しない残りの数量にコストが請求されます。`a[u]`、これらの不一致は、有効な操作シーケンスで少なくとも 1 回はノード u を通過する必要があることを表します。 

最終チェックでは、一致しない要件がルートから漏れていないことを確認します。 そうでなければ変換は不可能です。

 ## 特殊なケース

 重大なエッジ ケースは、不一致が存在するが、それらがすべて同じタイプであるためにツリー内のどこにも一致しない場合です。 たとえば、すべてのノードが b[i] = 0 および c[i] = 1 である場合、アルゴリズムは 1 つの不一致タイプのみを累積し、ゼロ以外の剰余をもつルートに到達します。 最終チェックでは正しく -1 が返されます。 

もう 1 つのエッジ ケースは、不一致がルートに到達する前にサブツリー内で完全にキャンセルされる場合です。 その場合、両方のカウンタは中間ノードでゼロになり、キャンセル ポイントを超えるコストは追加されません。 このアルゴリズムは、伝播前に常にローカル キャンセルを実行することでこれを保証するため、人為的な増加コストは発生しません。 

3 番目のケースは、交互の不一致がルートでのみ出会う長いチェーンです。 DFS は、それらが収束するまで分離されたままであることを保証し、費用は最上位の有効な会議ポイントで 1 回だけ請求され、高価な解決を必要になるまで遅らせるという最適な戦略と一致します。
