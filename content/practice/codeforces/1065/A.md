 ## 解決策
 ## 問題の理解

 Vasya には決まった金額があり、繰り返しのプロモーションで最終的に手に入るチョコレート バーの数を最大化したいと考えています。 すべてのバーには固定価格があるため、彼の初期購買力は単純に直接購入できるバーの数になります。 おもしろいのは、店がボーナスを提供していることです。一定数のバーを購入するたびに、追加のバーを無料で受け取ることができます。 このプロモーションは、十分な量のバーを購入し続ける限り、繰り返しトリガーできます。 

タスクは、有料購入とすべての可能な無料報酬の両方を組み合わせて、Vasya が最適に行動した場合に取得できるバーの総数をテスト ケースごとに計算することです。 

制約は次のとおりです$10^9$これにより、一度に 1 つのバーを購入するシミュレーションや、素朴なループでプロモーション サイクルを繰り返すシミュレーションが除外されます。 各購入や各プロモーションのアクティベーションを個別に処理するアプローチでは、最悪の場合、反復回数が数十億回に達する可能性があるため、非常に時間がかかりすぎます。 

貪欲なシミュレーションについて考えると、微妙な問題が生じます。 購入のシミュレーションを繰り返し試みるかもしれません$a$バー、収集$b$無料のバーをお金がなくなるまで繰り返します。 これは、各サイクル後の残りのお金を非効率的に追跡しているか、残りのお金がまだフルバンドル以外の追加購入に寄与していることを忘れていると暗黙的に仮定しているため、単純な形では正しくありません。 

別の特殊なケースは、プロモーションがコスト比よりも弱い場合に発生します。たとえば、次のような場合です。$b = 0$。 その場合、解決策は、無駄なプロモーションを「適用」しようとすることなく、単純に金額を価格で分割するものに完全に劣化するはずです。 

## アプローチ

 この強引なアイデアは、Vasya の動作を直接シミュレートすることです。 彼が自分のお金で購入できるバーの数を計算し、ルールを繰り返し適用します。彼が購入したバーが十分に蓄積されるたびに、次のグループを変換します。$a$にバーを購入しました$b$追加の無料バーは、それ自体がさらなるプロモーションに貢献できます。 これは、プロモーション アプリケーションごとに状態が変更され、サイクル数がバーの総数に比例する可能性があり、最悪の場合は膨大になるため、すぐに非効率になります。 

重要な観察は、問題の構造が線形かつ乗算的であるということです。 あらゆるグループの$a$購入したバーは効果的に生産されます$a + b$バーの合計。 これは、繰り返しの交換をシミュレートする代わりに、プロセス全体を圧縮して、完全なグループの数を数えることができることを意味します。$a$Vasya が購入できるバーと、それらのグループにグループごとの合計収量を掛けます。 

完全なグループを完成させなかった残りのバーは、$a$プロモーションには何も貢献しませんが、最終的な合計にはカウントされます。 この完全なグループと残りへの分離により、すべての動的な動作が排除されます。

 ## アルゴリズムのチュートリアル

 1. Vasya が自分のお金で直接買えるチョコレート バーの数を除算して計算します。$s$による$c$。 各バーのコストがかかるため、これにより有料バーの数がわかります。$c$ルーブル。 
2. 購入したバーをサイズの完全なグループに分割します。$a$。 完全なグループごとにプロモーションが 1 回だけトリガーされます。 
3. 完全なグループの数に次の値を掛けます。$a + b$、各グループの$a$購入したバーからはそれらが得られます$a$バープラス$b$余分なバー。 
4. 完全なグループを形成していない購入済みバーを追加します。これらはボーナスには寄与しませんが、合計にはカウントされます。 
5. 最終的な合計を出力します。 

重要な考え方は、プロモーションは部分的なグループ間では相互作用しないため、グループ化は次のとおりです。$a$考えられるすべてのボーナスアクティベーションを完全にキャプチャします。 

### なぜ効果があるのか

 購入した各バーは、完全なブロックの形成に貢献します。$a$またはプロモーションの観点から未使用のままです。 すべての完全なブロックが決定的に結果をもたらします$a + b$購入の順序に関係なくバーが作成され、ブロック間に依存関係はありません。 Vasya の購入能力は固定されているため、$s // c$、完全なブロックと残りへの分解により、損失や二重カウントなしでプロセスのすべての構造が保存されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        s, a, b, c = map(int, input().split())

        bought = s // c

        groups = bought // a
        rem = bought % a

        total = groups * (a + b) + rem
        print(total)

if __name__ == "__main__":
    solve()
```このソリューションでは、まずお金を購入可能なバーの数に変換します。 次に、これらのバーを完全なプロモーション ブロックと残り物に分離します。 乗算ステップでは、プロモーションが増分ではなく一括で適用されます。 残りはオファーをトリガーできないため、変更されずに追加されます。 

整数の除算には注意が必要です。 フロア除算とモジュロの両方が不可欠です。 浮動小数点演算を使用すると、大きな制約により精度エラーが発生します。 

## 実用的な例

 ### 例 1

 入力:```
10 3 1 1
```Vasya が購入できるバーの数を計算します。$10 // 1 = 10$。 

次に、それらをグループ化します。 

| 購入しました | グループ | 残り | 合計の計算 |
 | --- | --- | --- | --- |
 | 10 | 3 | 1 | 3 * (3 + 1) + 1 = 13 |

 結果は 13 で、3 つのバーからなる完全なブロックごとに合計 4 つのバーが生成されるという考えと一致します。 

これにより、残ったバーはプロモーションに参加しないことが確認されます。 

### 例 2

 入力:```
1000000000 1 1000000000 1
```ここでは、バーを購入するとすぐにプロモーションがトリガーされます。 

| 購入しました | グループ | 残り | 合計の計算 |
 | --- | --- | --- | --- |
 | 1000000000 | 1000000000 | 0 | 1000000000 * (1 + 1) = 2000000000 |

 ただし、各グループはグループ自体と大きさが等しいフリー バーを生成するため、最終的な値は合計寄与度の意図した線形スケーリングと一致します。 

これは、次のことを示しています。$a = 1$、すべての購入は 2 倍の成果に直接影響するため、グループ化は簡単になります。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(t) | 各テスト ケースは定数算術演算で処理されます。 
| スペース | お(1) | 固定数の変数のみが使用されます。 

このソリューションは制限内に簡単に収まります。$t \le 100$そしてそれぞれのケースはいくつかの整数演算で処理されます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque
    import sys

    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        s, a, b, c = map(int, input().split())
        bought = s // c
        groups = bought // a
        rem = bought % a
        out.append(str(groups * (a + b) + rem))
    return "\n".join(out)

# provided samples
assert run("2\n10 3 1 1\n1000000000 1 1000000000 1\n") == "13\n1000000002000000000"

# custom cases
assert run("1\n1 10 5 1\n") == "1"
assert run("1\n100 2 0 1\n") == "100"
assert run("1\n10 1 1 1\n") == "20"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 10 5 1 | 1 | グループを形成できません |
 | 100 2 0 1 | 100 | ボーナス拠出なし |
 | 10 1 1 1 | 20 | 購入するたびにボーナスが発生します |

 ## 特殊なケース

 エッジケースの 1 つは次の場合に発生します。$a >$購入したバーの数。 たとえば、Vasya がバーを 2 つしか購入できないが、ボーナスをトリガーするには 5 つ必要な場合、プロモーションは適用されないため、アルゴリズムはグループを正しく 0 に設定し、購入したバーのみを返します。 

もう 1 つのエッジケースは次のような場合です$b = 0$。 各グループは追加の利益を提供しないため、式は購入されたバーの数のみに減ります。 グループ化ステップは次のように乗算されるため、引き続き正しく機能します。$a + 0$、特別な処理を行わずに正確さを維持します。 

最後のエッジケースは、$a = 1$、購入したすべてのバーが独自のグループを形成します。 アルゴリズムは正しく 2 倍になります (またはスケールします)。$1 + b$) プロモーションの意図された繰り返し適用に一致する、各バーの貢献度。
