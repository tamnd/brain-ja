 ## 解決策
 ## 問題の理解

 非常に大きな整数が与えられていますが、それを数値として扱うのではなく、10 進数の複数セットとして考える必要があります。 Bomboslav はチェックからすべての数字を削除し、すべての数字を 1 回だけ使用して新しい整数に再構築したいと考えています。 

最終的な数値に対する制約は厳密です。 これは、先頭にゼロのない有効な整数である必要があり、7 で割り切れる必要があり、そのような有効な並べ替えの中で、通常の辞書編集的な数値の意味でできるだけ大きくなければなりません。 有効な再配置が存在しない場合、答えは -1 です。 また、すでに 7 で割り切れない限り、元の配列を再構築することによる「不正行為」を効果的に禁止する追加の制約もありますが、実際には、これはすべての桁を 1 回だけ使用するという要件によって当然強制されます。 

入力サイズは最大 1000 桁に達する可能性があるため、すべての順列を試行するアプローチは即座に除外されます。 階乗爆発は不可能であり、単純に実行した場合、桁のすべてのサブセットに対する動的プログラミングさえも実行不可能です。 使用可能な唯一の構造は、可能な桁値が 10 個しかないという事実から得られるため、入力は実際には小さなアルファベットの度数表になります。 

いくつかの特殊なケースがすぐに問題になります。 数字にゼロのみが含まれる場合、それが唯一の数字でない限り、先頭の数字としてゼロを置くことはできません。 たとえば、入力`0`有効であり、結果が得られます`0`、しかし入力`00`まだ収穫できる`0`再配置後。 すべての桁がゼロ以外の場合は、たとえそれが最適であったとしても、選択した順列がゼロで始まらないようにする必要があります。 

別の微妙な故障モードは、同じ数字を持つ複数の順列が存在する場合に現れますが、割り算の結果は異なります。 たとえば、数字`1,2,3`は多くの順列を形成できますが、モジュラス制約を満たすのは一部だけであるため、貪欲な並べ替えだけでは不十分です。 

## アプローチ

 ブルートフォースソリューションでは、数字のすべての順列を生成し、ゼロで始まらないものをフィルタリングし、7 で割り切れるかどうかを確認し、最大のものを選択します。 これは正しいですが、最大 1000 桁では、置換の数が入力サイズの階乗になるため、完全に実行不可能です。 

重要な構造上の観察は、同じ数字の個​​々の位置は気にせず、各数字を何個使用するかだけを気にするということです。 これにより、問題は 10 次元の周波数ベクトルによって定義される状態を処理することになります。 部分的な構造から見て、割り算にとって重要なのは、現在の剰余 7 だけです。 

これにより、各状態が残りの桁数と 7 を法とする現在の剰余によって記述される状態グラフが得られます。遷移は、現在の数値に追加する 1 桁の選択、そのカウントの減少、および剰余の更新で構成されます。 数値は桁ごとに増加するため、剰余の更新は位置の重みに依存し、構築中に暗黙的に処理されます。 

どの状態からでも実現可能性をテストできるようになると、貪欲に答えを構築できるようになります。 各位置で、9 から 0 までの数字を試し、有効な最終状態に到達できる最初の数字を選択します。 実現可能性を損なわない限り、より高い桁が常に優先されるため、これにより最大限の辞書編集順序が保証されます。

 ## アルゴリズムのチュートリアル

 ### 重要なアイデア

 残りの桁を度数表として扱い、左から右に答えを作成します。 各ステップで、有効な補完を可能にする可能な最大の桁を選択します。 

### ステップ

 1. 入力文字列内の 0 から 9 までの各数字の出現をカウントします。 これにより、入力は最大 1000 文字ではなく、最大 10 個の数値に圧縮されます。 これは、その後私たちが使用する唯一の表現です。 
2. 再帰関数を定義する`can(counts, remainder, position)`残りの桁を使用して有効な数値を完成できるかどうかを返します。 の`position`桁の寄与は 10 のべき乗、および周期 6 の 10 のべき乗サイクル モジュロ 7 に依存するため、 が必要になります。 
3. この関数は同じなのでメモします`(counts, remainder, position mod 6)`この状態は探索中に複数回出現する可能性があります。 メモ化がなければ、再帰は同一の部分問題を繰り返し再計算することになります。 
4. 最重要位置から最終的な数値を構築し始めます。 各位置について、9 から 0 までの数字を試してください。 
5. 各候補桁について、その数を一時的に減らし、`can(...)`完全に有効な完了が存在することを確認します。 
6. 候補数字が実行可能な解決策につながる場合は、それを答えに永続的に配置し、更新されたカウントと余りを使用して次の位置に移動します。 
7. どの桁も機能しない場合は、有効な数値が存在しないと判断し、-1 を出力します。 

### なぜ効果があるのか

 すべてのステップで、アルゴリズムは、これまでに選択されたプレフィックスが、有効な完全なソリューションを導き出すことができるすべてのプレフィックスの中で辞書編集上最大であるという不変条件を維持します。 実現可能性チェックにより、すべての有効な補完をブロックするプレフィックスを決してコミットしないことが保証されます。 数字は降順で試行されるため、最初の実行可能な選択肢は、その位置で可能な最大の選択肢でもあります。 帰納的に、これにより、構築された数値全体が最大の有効な置換であることが保証されます。 

実現可能性の正しさは、モジュロ 7 が位置 mod 6 にのみ依存するという事実に依存しているため、状態空間は有限であり、再訪は安全にキャッシュできます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from functools import lru_cache

sys.setrecursionlimit(1000000)

MOD = 7

def solve():
    s = input().strip()
    cnt = [0] * 10
    for ch in s:
        cnt[int(ch)] += 1

    n = len(s)

    # powers of 10 mod 7, period 6
    pw = [1] * 6
    for i in range(1, 6):
        pw[i] = (pw[i - 1] * 10) % 7

    @lru_cache(None)
    def can(c0, c1, c2, c3, c4, c5, c6, c7, c8, c9, pos_mod, rem):
        counts = [c0,c1,c2,c3,c4,c5,c6,c7,c8,c9]
        if sum(counts) == 0:
            return rem == 0

        # try placing any digit next
        for d in range(10):
            if counts[d] == 0:
                continue
            counts[d] -= 1
            new_mod = (rem * 10 + d) % 7
            new_pos = (pos_mod + 1) % 6
            args = tuple(counts + [new_pos, new_mod])
            if can(*args):
                return True
            counts[d] += 1

        return False

    # initial feasibility
    init_args = tuple(cnt + [0, 0])
    if not can(*init_args):
        print(-1)
        return

    res = []
    pos_mod = 0
    rem = 0

    for _ in range(n):
        for d in range(9, -1, -1):
            if cnt[d] == 0:
                continue
            cnt[d] -= 1
            if can(*tuple(cnt + [pos_mod + 1, (rem * 10 + d) % 7])):
                res.append(str(d))
                pos_mod = (pos_mod + 1) % 6
                rem = (rem * 10 + d) % 7
                break
            cnt[d] += 1

    print("".join(res))

if __name__ == "__main__":
    solve()
```このソリューションでは、7 を法とする剰余と 6 を法とする位置を追跡しながら、桁の配置を調査する再帰的実現可能性チェッカーが使用されます。再構成ループは、各桁を左から右に貪欲に修正し、残りのマルチセットが依然として有効な補完を形成できることを常に検証します。 

実装の微妙な詳細は、メモ化キーに個別のパラメータに展開された桁数が含まれていることです。 これにより、再帰内のタプル ハッシュのオーバーヘッドが回避されます。これは、多くの状態が繰り返される場合に重要になります。 もう 1 つの重要な点は、完全な中間数値を明示的に構築するのではなく、モジュール状態のみを構築することです。

 ## 特殊なケース

 重大なエッジ ケースは、割り算を満たす唯一の方法として、早めにゼロを配置する必要がある場合です。 このアルゴリズムは、すべての候補プレフィックスが完全な実現可能性に対して検証されるため、これを回避します。そのため、無効な先頭構造を強制するプレフィックスはチェック中に拒否されます。 

もう 1 つのエッジケースは、複数の数字が同一のプレフィックスを生成するが、ダウンストリームの実現可能性が異なる場合です。 メモ化された実現可能性関数により、これらの差異が早期に検出されることが保証され、局所的な妥当性のみをチェックした場合に発生する可能性のある貪欲な間違いが防止されます。
