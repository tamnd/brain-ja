 ## 問題の理解

 小文字で構成される長い文字列が与えられます。 パターン文字列を選択できます`T`長さは 3 です。 選択した後`T`、決定論的なプロセスが実行されます:`T`現在の文字列のどこかに出現する場合、常に左端の出現箇所を削除します。`T`、短縮された文字列を再度続行します。 

削除するたびに文字列が即座に変更されるため、新しく結合された境界を越えて新しい文字列が現れる可能性があります。 固定のスコア`T`このプロセス中にトリプルを削除できた合計回数です。 すべての可能な長さの中で 3 つの文字列`T`、最大の削除数が得られるものが必要であり、複数の削除が同じ最大数に達する場合は、辞書編集的に最小のものを選択します。`T`。 

入力サイズは最大 100 万文字です。 これにより、候補ごとに文字列を最初から繰り返し再スキャンするソリューションはすでに除外されています`T`可能なパターンは 263 個あるため、約 17,000 個あり、パターンごとに 1 つの線形パスを実行するだけでも、Python では遅すぎます。 

微妙な特殊なケースは、削除によって新しい隣接関係が作成されるという事実から生じます。 たとえば、文字列が次の場合、`abca`そして削除します`abc`、残りの文字`a`そして`a`隣接するようになり、後のステップで周囲のコンテキストを含む新しい有効なトリプルを形成する可能性があります。 これは、単純に発生数を数えることはできないことを意味します。`T`元の文字列で。 

もう 1 つの例外的なケースは、貪欲な左端の削除によって将来の構造が変化することです。 「重複する出現をカウントするだけ」のような単純な考えは失敗します。 たとえば、`aaaaaa`と`T = aaa`、左端の削除が繰り返されると配置が変更され続け、削除の数は部分文字列の最初の数だけではありません。 

重要な難点は、スコアが固定されていることです。`T`静的なパターンのカウントではなく、完全な動的なプロセスに依存します。 

## アプローチ

 ブルートフォースのアイデアは単純です。 候補を修正する`T`、説明どおりにプロセスを正確にシミュレートします。左端の出現箇所を繰り返しスキャンして削除します。 これは正しいですが、高価です。 各削除後の単純スキャンには O(n) のコストがかかり、最悪の場合は O(n) 個の削除が発生する可能性があり、パターンごとに O(n²) になります。 約 17,000 のパターンがあるため、これは完全に不可能です。 

スタックベースの観察を使用して、単一のシミュレーションを改善できます。 左端の出現箇所を繰り返し検索する代わりに、スタックを維持しながら文字列を左から右に処理します。 スタックの上位 3 文字が等しいときはいつでも`T`、それらをポップし、削除を 1 つカウントします。 これが機能するのは、成長するストリームの左端のオカレンスを常に削除することは、スタック プロセスでパターンを検出して折りたたむことと同等であるためです。 これにより、1 回のシミュレーションが O(n) に削減されます。 

ただし、17,000 パターンすべてを評価する必要があります。 これにより、約 1.7 × 10⁷ の操作が必要になりますが、Python では、各ステップにタプルの比較や大規模なデータのスタック操作が含まれる場合、これでもまだ大きすぎます。 

この問題を実行可能にする重要な観察点は、考えられる可能性はたくさんあるものの、`T`、内部シミュレーションは非常にローカルです。 すべてのステップで、削除が行われるかどうかに影響するのは、スタックの最後の 2 文字と現在入ってくる文字だけです。 これにより、各実行が非常にキャッシュしやすくなり、Python レベルの最適化により、すべてのパターンに対して定数係数を十分に小さく保つことができます。 アルファベットはわずか 26 個であるため、パターンの総数は十分に少ないため、文字列の線形スキャンですべての候補に対して二重ループを慎重に実装できます。 

したがって、意図した解決策は、あらゆる可能なスタック プロセスをシミュレートすることです。`T`ただし、内側のループが緊密で、遷移ごとのオーバーヘッドが最小限に抑えられます。

 ## アルゴリズムのチュートリアル

 考えられるすべての文字列を評価します`T = (c1, c2, c3)`小文字を調べて、生成される削除の数を計算します。 

1. 26 個の候補パターンをすべて列挙します`T`。 各パターンは個別に処理され、プロセス全体を一からシミュレートします。 
2. 固定の場合`T`、空のスタックと削除用のカウンターを初期化します。 スタックは、以前のすべての折りたたみ後の現在の縮小文字列を表します。 
3. 元の文字列をスキャンします`S`左から右へ。 キャラクターごとに`x`、それをスタックにプッシュします。 
4. プッシュ後、スタックの最後の 3 文字が等しいかどうかを確認します。`T`。 存在する場合は、それらの 3 文字を削除し、削除カウンターをインクリメントします。 このステップでは、有効なパターンの即時の崩壊をシミュレートします。 
5.最後まで続ける`S`。 最後のカウンターが今回の得点です`T`。 
6. 全体で最高のスコアを追跡する`T`。 複数のパターンが同じスコアを達成する場合は、辞書順に最も小さいパターンを選択します。 

正確さは、スタックが「常に左端の利用可能な出現を削除する」というルールに基づいて、処理された文字列の完全に縮小されたプレフィックスを常に表すという不変条件から得られます。 検出するたびに`T`スタックの最上位にある文字列は、文字列の現在の状態で考えられる最も古い出現に正確に対応するため、ローカルで削除することはグローバル ルールと同等です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def simulate(s, a, b, c):
    stack = []
    cnt = 0
    for ch in s:
        stack.append(ch)
        if len(stack) >= 3:
            if stack[-1] == c and stack[-2] == b and stack[-3] == a:
                stack.pop()
                stack.pop()
                stack.pop()
                cnt += 1
    return cnt

def main():
    n = int(input().strip())
    s = input().strip()

    best_cnt = -1
    best_t = ""

    letters = [chr(ord('a') + i) for i in range(26)]

    for a in letters:
        for b in letters:
            for c in letters:
                cur = simulate(s, a, b, c)
                if cur > best_cnt or (cur == best_cnt and a + b + c < best_t):
                    best_cnt = cur
                    best_t = a + b + c

    print(best_cnt)
    print(best_t)

if __name__ == "__main__":
    main()
```この実装では、文字列のスライスや再構築操作を回避することでシミュレーションを厳密に保ちます。 スタックは単純な Python リストであり、比較は最後の 3 つの要素に対して直接行われるため、部分文字列の構築によるオーバーヘッドが回避されます。 

辞書編集上のタイブレークは、候補文字列を直接比較することによって処理されます。これは、とにかく辞書編集順に反復するため機能します。

 ## 特殊なケース

 重大なエッジ ケースは、次のような繰り返しの多い文字列です。`aaaaaa`。 のために`T = "aaa"`、折りたたむたびに文字列が短くなり、すぐに再び一致する新しい配置が作成されます。`aaa`。 スタック シミュレーションではこれを自然に処理します。これは、各ポップの後、次の受信キャラクタがスタックの最上位にある有効なトリプルを再公開するためです。 

もう 1 つのエッジ ケースは、次のような繰り返し構造を持たない文字列です。`abcdef`。 すべての候補者`T`欠失はゼロです。 この場合、正確さは辞書編集上のタイブレークに完全に依存し、実装により可能な限り最小の値が返されることが保証されます。`T`、つまり`"aaa"`すべてがゼロで、列挙が辞書順に並べられている場合、より一般的には、最初に見つかった最小パターンです。
