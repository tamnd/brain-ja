 ## 解決策
 ## 問題の理解

 このシステムは、電気セットアップをモデル化した根のあるツリーです。 ルートは電力制限が固定された単一のソケットであり、他のすべてのノードは電気デバイスまたは電源タップのいずれかです。 リーフは消費電力が固定されたデバイスですが、内部ノードは容量制限が固定された電源タップです。 

どのノードでも、その「負荷」はそのサブツリー内のすべてのデバイスの電力の合計です。 ルート ソケットを含むすべての電源タップに少なくともそのサブツリー負荷と同じ容量がある場合、構成は有効です。 

ツリーの構造は固定されています。 許可される唯一の操作は、任意の 2 つの内部ノードの容量値を交換することです。 リーフの値は固定されており、移動できません。 

ここでのタスクは、内部ノード間の容量を任意に並べ替えた後、各ノードの容量制約がそのサブツリー負荷によって満たされるように各容量を電源タップに割り当てることが可能かどうかを判断することです。 

この制約は、O(n) または O(n log n) の解が必要であることを意味します。 n が 100000 までの場合、順列を明示的に考慮したり、スワップをシミュレートしたりする試みは実行不可能です。 主な問題は、サブツリーの負荷が構造的に固定されている一方で、容量がグローバルに再配置されることです。 

単純な推論による微妙な失敗のケースは、貪欲なローカル割り当てによって発生します。 たとえば、最も深いノードまたは最大のサブツリーを持つノードに最大の容量を割り当てるのは合理的であるように思えるかもしれませんが、これは重複するサブツリー間の相互作用を無視します。 

根元にたくさんの葉がある星形の木を考えてみましょう。 リーフの重みが偏っている場合、兄弟サブツリーの合計を考慮せずにリーフの親に最大容量を割り当てると、別のグローバル割り当てが成功したとしても失敗する可能性があります。 ローカルの貪欲な割り当てでは、グローバルな実現可能性の制約が捕捉されません。 

## アプローチ

 ブルート フォース アプローチでは、内部ノード間の容量のすべての順列が試行され、結果の割り当てがすべてのサブツリー制約を満たすかどうかがチェックされます。 これは内部ノードの数の要因であり、n が 15 または 20 程度であってもすぐに不可能になります。 

重要な観察は、サブツリーの合計が固定されており、スワップから独立していることです。 唯一の自由は、複数の容量セットを必要なサブツリー負荷の複数セットに一致させることですが、各ノードは少なくともその独自のサブツリーの合計に等しい容量を受け取る必要があるという制限があります。 

これにより、問題は実現可能性の問題に変換されます。capacity[i] ≥ required[i] となるように各内部ノードに容量を割り当てることができるでしょうか。ここで、required[i] はノード i でのサブツリーの合計です。 

容量は交換可能であるため、基本的には、優勢制約の下で 2 つのマルチセット間に一致が存在するかどうかをチェックしています。 最適な戦略は、両方のリストをソートし、最小の要件とそれを満たすことができる最小の容量を貪欲に一致させることです。 

これが機能するのは、解決策が存在する場合、両方のシーケンスをソートすることで、小さい要件と大きすぎる容量が組み合わされるたびに割り当てを交換することで、実現可能性を損なうことなく有効な組み合わせを構築できるためです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(k!) | O(n) | 遅すぎる |
 | ソート + 貪欲なマッチング | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、すべてのノードのサブツリーの合計を計算します。 これは、リーフの重みを上向きに集約するルートからの単一の DFS です。 

次に、2 つの配列を収集します。1 つはすべての内部ノードのサブツリーの合計 (これらは必要な最小容量です) であり、もう 1 つは内部ノードから利用可能なすべての容量です。 

次に、両方の配列を非降順で並べ替えます。

ソートされた要件リストを反復処理し、容量配列上のポインターを使用して各要件に容量を割り当てようとします。 現在利用可能な最小容量が要件を下回る場合は、有効な容量が見つかるまで続行します。 キャパシティが不足すると、答えは不可能になります。 

最終チェックは、すべての要件が満たされるかどうかです。 

### なぜ効果があるのか

 正しさは標準の交換引数から得られます。 何らかの有効な割り当てが存在すると仮定します。 その割り当てで、より小さい要件にはより大きな容量が使用され、より大きな要件にはより小さな容量が使用される場合、それらを交換しても有効性は失われません。 このプロセスを繰り返すと、両方のシーケンスがソートされた順序で整列した構成が得られます。 これは、有効な割り当てが存在する場合、貪欲なソート マッチングも成功することを意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
sys.setrecursionlimit(10**7)

n = int(input())
children = [[] for _ in range(n + 1)]
is_leaf = [True] * (n + 1)
a = [0] * (n + 1)

for i in range(1, n + 1):
    fi, ai = map(int, input().split())
    children[fi].append(i)
    is_leaf[i] = True
    is_leaf[fi] = False
    a[i] = ai

sub = [0] * (n + 1)

def dfs(u):
    if not children[u]:
        sub[u] = a[u]
        return sub[u]
    s = 0
    for v in children[u]:
        s += dfs(v)
    sub[u] = s
    return s

dfs(0)

req = []
cap = []

for i in range(1, n + 1):
    if children[i]:
        req.append(sub[i])
        cap.append(a[i])

req.sort()
cap.sort()

i = j = 0
while i < len(req) and j < len(cap):
    if cap[j] >= req[i]:
        i += 1
        j += 1
    else:
        j += 1

print("YES" if i == len(req) else "NO")
```DFS はサブツリーの合計をボトムアップで計算し、すべてのノードの負荷が使用前に正しく集約されていることを確認します。 内部ノードは少なくとも 1 つの子を持つことによって識別され、それらのみが割り当てプロセスに参加します。 

貪欲マッチングでは、ソートされた配列に対する 2 つのポインターを使用します。 容量が現在の要件に対して小さすぎる場合、それより大きな要件を満たすこともできないため、その容量は破棄されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 | 時間 | O(n log n) | DFS は線形であり、並べ替えが優先されます。 
| スペース | O(n) | 隣接リスト、サブツリーの合計と容量の配列 |

    import sys as _sys

    # Re-run solution
    input = _sys.stdin.readline
    sys.setrecursionlimit(10**7)

    n = int(input())

    a = [0] * (n + 1)

        fi, ai = map(int, input().split())
        children[fi].append(i)
        a[i] = ai

    sub = [0] * (n + 1)

    def dfs(u):
        if not children[u]:
            sub[u] = a[u]
            return sub[u]
        s = 0
        for v in children[u]:
            s += dfs(v)
        sub[u] = s
        return s

    dfs(0)

    req = []
    cap = []

            j += 1

 ## 特殊なケース

 単一ノード ツリーにはルートのみが含まれるため、内部スワップは必要ありません。 DFS はリーフ値を直接割り当てますが、要件リストは空であるため、アルゴリズムはすぐに YES を返します。 

1 つのサブツリーにほぼすべての葉が含まれる、非常に偏ったツリーでは、支配的な要件が生成されます。 この大きなサブツリーの合計をカバーできる容量がない場合、貪欲アルゴリズムは正しく失敗します。これは、その要件が並べ替えられたリストの最後に表示され、最後に利用可能な最大の容量を消費するためです。 

多数の小さなサブツリーと 1 つの大容量のケースでは、ポインター スキップ ロジックが正しく動作するかどうかをテストします。 このアルゴリズムは、使用できない小さな容量を破棄し、残りのすべての要件に対して有効な一致を見つけ、容量のローカルな並べ替えが完全に十分であることを確認します。
