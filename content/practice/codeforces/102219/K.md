 ## 解決策
 ## 問題の理解

 顧客のリクエストにはそれぞれ処理時間があります`t`。 ニーナが時間から始まるなら`0`、そのリクエストは時間までに完全に処理される必要があります`2t`お客様に満足していただくために。 Nina はリクエストを処理する順序を選択でき、期限に間に合うリクエストの数を最大化したいと考えています。 

入力には、最大 20 の独立したテスト ケースが含まれます。 それぞれの場合について、`n`と同じ大きさにすることができます`10^5`、各処理時間は次のように長くなる可能性があります。`10^9`。 答えは、個々の期限までに完了できるリクエストの最大数です。 以来`n`到達する`10^5`、サブセットまたは順列を列挙することは不可能です。 周りに何かが必要です`O(n log n)`場合によってはそれ以上です。 また、時間制限が 1 秒であるため、二次アプローチは最大のケースには適していません。 

最初の構造上の観察は、処理時間のあるリクエストであるということです。`t`期限があります`2t`。 したがって、処理時間と期限は同じ値によって決まります。 2 つのリクエストに処理時間がかかる場合`a <= b`、その場合、期限も満たされます`2a <= 2b`。 リクエストを処理時間で並べ替えると、結果として期限も並べ替えられます。 

たとえば、入力の場合`1 / 1`、単一のリクエストは時間どおりに終了するため、常に満たされます。`1`、最大でも期限です`2`。 かどうかをチェックする不用意な実装`t <= 0`または期限を次のように扱います`t`誤って拒否してしまうでしょう。 

考慮する`1 / 3 / 1 1 1`。 正しい答えは、`2`。 最初の 2 つのリクエストが完了すると、現在時刻は次のようになります。`2`、これはまさに 2 番目のリクエストの期限です。 3 番目のリクエストは時間通りに終了します`3`、期限後`2`。 を使用した実装`<`の代わりに`<=`2 番目のリクエストを誤って拒否して返します`1`。 

さらに興味深いケースは、`1 / 4 / 1 1 1 3`。 最初の 2 つのリクエスト後の累積時間は次のようになります。`2`。 3 番目のリクエストは期限までに完了できません。`2 + 1 > 2`, したがって、スキップする必要があります。 長さのご要望`3`その後、時間内に完了できます`5`、締め切り直前に`6`。 正しい答えは、`3`。 よくある間違いは、その後の長い期限まで検査を続けるのではなく、最初に失敗したリクエストの後で停止してしまうことです。 

最後に、値が大きい場合は、累積処理時間を十分に広い整数型で格納する必要があります。 と`10^5`リクエストごとに`10^9`、合計は到達することができます`10^14`。 Python の整数はこれを自動的に処理しますが、別の言語での固定幅の実装には 64 ビットの整数が必要になります。 

## アプローチ

 直接的なブルート フォース ソリューションでは、リクエストのすべてのサブセットを考慮し、そのサブセットを処理時間で並べ替え、選択したすべてのリクエストが期限前に終了するかどうかを確認できます。 これは正しいです。なぜなら、満足した顧客の考えられる選択肢はすべて 1 つのサブセットで表され、選択したサブセットを期限を増やすことで並べ替えることで、正しい実現可能性の順序が得られるからです。 がある`2^n`サブセット、および 1 つのサブセットのチェックには時間がかかる場合があります`O(n)`時間、与えること`Theta(n 2^n)`簡単な実装で動作します。 サブセットの数だけでもすでに不可能です`n = 10^5`。 

この便利な構造は、期限が処理時間のちょうど 2 倍であるという事実から来ています。 すべてのリクエストを並べ替える基準`t`。 現在選択されているリクエストの合計処理時間がかかると仮定します。`S`、次のリクエストには処理時間があります`t`。 追加すると、完了時間は`S + t`。 その期限は`2t`, したがって、それを受け入れるための条件は次のようになります。`S + t <= 2t`これを単純化すると`S <= t`。 

これが異常に便利なんです。 ソート後、今後のすべてのリクエストの処理時間は、少なくとも現在のリクエストと同じになります。 現在のリクエストが適合しない場合、それを維持しても、より多くのリクエストを満たすことができません。 これはこれまでに考慮された最大のリクエストであるため、すでに選択されているリクエストをそれに置き換えても、合計処理時間が増加するだけです。 

ブルート フォース ソリューションは、考えられるすべてのサブセットを明示的に考慮するため機能しますが、サブセットが指数関数的に多いため失敗します。 リクエストは昇順に処理でき、現在の累積時間が最大でも独自の処理時間に達するときにリクエストが正確に適合するという観察により、すべてのリクエストに対して個別に貪欲な決定を下すことができます。 

貪欲なルールは単純です。値を並べ替え、最小値から最大値までスキャンし、現在の累積時間がそのリクエストの値を超えたときに正確にリクエストを追加します。 それ以外の場合はスキップして続行してください。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |`O(n 2^n)`|`O(n)`| 遅すぎる |
 | 最適 |`O(n log n)`|`O(n)`| 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべてのリクエストの処理時間を降順で並べ替えます。 これにより、期限もソートされます。これは、価値のあるリクエストであるためです。`t`期限があります`2t`。 選択したリクエストをこの順序で処理するだけで、実現可能性を確認できます。 
2.セット`total = 0`そして`answer = 0`。 ここ`total`は、満たすことを決定したリクエストにすでに費やした時間を表します。 
3. ソートされたすべてのリクエストと処理時間`t`、どうかを確認してください`total <= t`。 リクエストを受け入れると完了時間がかかるため、これはまさに期限条件です。`total + t`、その期限は`2t`。 
4. もし`total <= t`、リクエストを受け入れます。 増加`total`による`t`そして増加します`answer`1つずつ。 リクエストは遅くとも次の時間までに完了することが保証されます`2t`。 
5. もし`total > t`、リクエストをスキップします。 以前に考慮されたリクエストはすべて以下のサイズ以下であるため、`t`、このリクエストはこれまでに確認された中で最大のものです。 選択したリクエストを置き換えて、より短い合計処理時間で同じ数のリクエストを取得することはできません。 
6. すべてのリクエストを処理した後、印刷します。`answer`現在のテストケースの場合。 

### なぜ効果があるのか

 ソートされた配列の接頭辞を処理した後、次の不変条件を維持します。`answer`は、そのプレフィックスからの、そのサイズのすべての実行可能な選択のうち、満たせるリクエストの最大可能数です。`total`できるだけ小さいです。 

現在のリクエストのとき`t`満足する`total <= t`、それを追加すると、`total + t <= 2t`, したがって、もう 1 つのリクエストを含む実行可能な選択が得られます。 前のプレフィックスには最大でも次の値を含めることができるため、`answer`リクエストの場合、この新しい選択には可能な限り最大のカーディナリティがあり、可能な限り小さい以前の合計を選択すると、新しい合計が最小限に保たれます。 

いつ`total > t`、現在のリクエストを追加するには、すでに以上のものが必要になります。`2t`時間。 もう 1 つのリクエストを含む選択では、以前に選択したリクエストの一部を置き換えるか、現在のリクエストを含める必要があります。 現在のリクエストは、以前のすべてのリクエストと少なくとも同じ大きさであるため、以前に選択したリクエストをそれに置き換えても、合計を小さくすることはできません。 不変式は言う`total`はすでに選択されているリクエストの現在数の最小合計であるため、追加のリクエストを 1 つ含む実行可能な選択は存在しません。 スキップ`t`結果的に最適となります。 

スケジューリング順序もソートで十分です。 期限は処理時間に比例するため、処理時間が短いほど期限も短くなります。 選択したリクエストのスケジュールを増加中`t`は最も早い期限の順序であり、すべてのプレフィックス期限を満たすことで、選択したセット全体を実行可能にするのに十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    m = int(input())
    out = []

    for case in range(1, m + 1):
        n = int(input())
        a = list(map(int, input().split()))

        a.sort()

        total = 0
        answer = 0

        for t in a:
            if total <= t:
                total += t
                answer += 1

        out.append(f"Case #{case}: {answer}")

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```プログラムはまずテスト ケースの数を読み取り、各ケースを個別に処理します。 配列には処理時間が正確に含まれるため、別の期限配列は必要ありません。 値の期限`t`常に次のように導出できます`2t`。 

並べ替えた後、`total`現在のリクエストが開始される直前の完了時間が含まれます。 表現`total <= t`元の期限条件とは異なって見えるかもしれませんが、代数的には同じです。`total + t <= 2t`と同等です`total <= t`。 

単純化された条件を使用すると、不必要な乗算が回避され、貪欲なルールがより明確になります。 

等しい場合は受け入れられる必要があります。 もし`total == t`、リクエストは正確に終了します`2t`、まだ間に合います。 だからこその条件なのですが、`<=`、 ない`<`。 

Python の整数型は、オーバーフローすることなく累積時間を表すことができます。 それぞれの価値観は最大でも`10^9`、合計はおよそになる可能性があります`10^14`。 

出力は次のように蓄積されます。`out`そして最後に一度書きます。 これにより、テスト ケースが多い場合に出力操作が繰り返されることがなくなります。

 ## 特殊なケース

 単一リクエストのケースは単純ですが、初期化を確認するのに役立ちます。 入力用```
1
1
1000000000
```

`total`から始まります`0`、 それで`0 <= 1000000000`それは本当です。 リクエストは受け入れられ、`Case #1: 1`。 このアルゴリズムでは、次のような特別なケースは必要ありません。`n = 1`。 

値が等しい場合、境界条件が明らかになります。 のために```
1
3
1 1 1
```最初のリクエストが変更される`total`から`0`に`1`、2番目はそれをから変更します`1`に`2`。 3回目のリクエストについては、`total = 2`その間`t = 1`, なのでスキップされます。 答えは`2`。 2 番目のリクエストは時間どおりに終了します`2`、期限があるので、`<`の代わりに`<=`間違った結果が生じます。 

リクエストがスキップされたが、後のリクエストが受け入れられるケースは次のとおりです。```
1
4
1 1 1 3
```最初の 2 つのリクエストの後、`total = 2`。 次は`1`失敗する理由`2 > 1`, したがって無視されます。 最後のリクエストは、`t = 3`、 そして`2 <= 3`, したがって、受け入れられます。 最終的な答えは、`3`。 これは、リクエストが失敗した後もスキャンを続行する必要がある理由を示しています。 

等価境界は、複数のリクエストの後に発生することもあります。 のために```
1
3
1 1 2
```最初の 2 つのリクエストによって生成されるのは、`total = 2`。 のために`t = 2`、状態はまさに`2 <= 2`, したがって、リクエストは受け入れられます。 その完了時間は、`4`、まさにその期限`2 * 2`。 答えは`3`。 

最後に最大サイズのケース```
1
100000
1 1 1 ... 1
```100,000 件の同一のリクエストが含まれています。 最初の 2 つは完了時間が次のとおりであるため、満足できます。`1`そして`2`、期限前または期限前に`2`。 後続のすべてのリクエストはその後終了します`2`したがって、残りのリクエストはすべてスキップされます。 答えは`2`。 このアルゴリズムは依然として 1 つのソートと 1 つの線形スキャンのみを実行するため、入力が大きくても漸近的な動作は変わりません。
