 ## 解決策
 ## 問題の理解

 私たちには、特定の暦日に発生する n 旅行日からなる固定の旅程が与えられています。 これらの日ごとに、1 枚のチケットを個別に購入することにした場合、費用がかかります。 これらの日はすでに時間順に並べ替えられており、同じタイムスタンプを共有する 2 日はありません。 

これに加えて、k 種類の鉄道パスもあります。 各パスの種類は、少し特殊な方法で動作します。 ある日にパスをアクティブ化すると、連続する暦日 p の固定ウィンドウの間はアクティブなままになります。 その枠内で、計画されている旅行日数の最大 d 日をカバーするために使用できます。 期間内に d 日を超える旅行日数が発生する場合、パスの対象となるのはそのうちの最初の d 日のみであり、同じ期間内のそれ以降の旅行日は、パスがまだ有効であっても個別に支払う必要があります。 重大な問題は、パスが自由に重なることです。複数のパスが同時にアクティブになる可能性があり、その日の最終的な支払い決定が 1 つだけであっても、旅行日ごとに複数のアクティブなパスの使用量が同時に消費される可能性があります。 

タスクは、旅行日ごとに、個別の運賃を支払うか、1 つ以上の有効なパスに依存するかを決定し、すべての旅行日がカバーされ、総コストが最小限に抑えられるようにすることです。 

制約は非常に構造的な意味で重要です。 移動日数は最大 10,000 ですが、パス タイプの数は最大 100 です。10,000 日を超える 2 次または 3 次アプローチでさえすでに大きすぎるため、1 日または間隔ごとにパスのすべての組み合わせを試すソリューションはすぐに実行不可能になります。 ただし、パス タイプの数が少ないということは、各パス タイプを個別に評価し、相互作用を明示的に列挙するのではなく、グローバルな動的プログラミング構造を通じて組み合わせる必要があることを強く示唆しています。 

微妙だが重要なエッジ ケースは、重複するパスと「最初の d 個の使用」ルールから発生します。 有効期間が長くても d が小さいパスを考えてみましょう。 旅行期間の早い段階で旅行日数が集中している場合、パスはまだ有効であっても、割り当てが早期に期限切れになり、後の日には使用できなくなる可能性があります。 「一度パスを購入すれば、有効期限内のすべての日がカバーされる」と想定する単純なアプローチでは、その有用性が過大評価されてしまいます。 

別のエッジケースは、一部のセグメントではパスが個々の運賃よりも厳密に悪いが、他のセグメントでは有利である場合に発生します。 パスは再利用可能で複数回購入できるため、決定はタイプごとに単一のグローバルな選択ではなく、異なる開始日に複数のアクティベーションが行われる可能性があります。 

## アプローチ

 直接総当り戦略では、すべての旅行日を独立して扱い、3 つの可能性の中から決定します。運賃を直接支払うか、その日から始まる何らかのタイプのパスを購入するか、その日をすでに有効なパスに割り当てるかです。 これを正しくするためには、各アクティブなパスの使用回数や、将来どこまで続くかなど、すべてのアクティブなパスの完全な状態を追跡する必要があります。 

これにより、毎日が前日だけでなく、すべてのアクティブなパス使用のマルチセットに依存する状態空間が得られます。 注意深く離散化したとしても、状態の数は k とオーバーラップするパスの数とともに指数関数的に増加します。 最悪の場合、毎日パスが開始され、他のすべてのパスと対話し、実現可能な制限をはるかに超えた構成の爆発につながる可能性があります。 

構造を単純化する鍵となるのは、視点を逆転させることです。 私たちは、「現在どのパスが有効であるか」を考えるのではなく、「ここで決定を下した後、次の対象外の旅行日は何になるか」を考えます。 各決定は、現在の旅行日の料金を直接支払うか、注文された旅行リストの将来のセグメントをカバーするようにモデル化できるパスを開始しますが、スライディング タイム ウィンドウ内でカバーできるインデックスの数には上限があります。

これにより、ソートされた旅行リスト内の位置にわたる最短経路として問題を再定式化できます。 dp[i] が i 日目以降のすべての旅行日をカバーする最小コストである DP を定義します。 各位置 i からは、i 日目の運賃を支払うことで i+1 に直接移行できます。 パス タイプの場合、i 日目に有効化する場合、その時間枠と割り当て d 内で将来の旅行日数をカバーできるかを決定する必要があります。 これにより、i から j へのジャンプが行われ、パス コスト c が追加されます。 微妙な部分は、この j がインデックス距離だけでなく実際のカレンダー時間に依存するため、各 i および各パス タイプに対して、到達可能な最も遠いインデックス j(i, type) を事前計算します。 

これらのジャンプがわかると、問題は O(nk) 遷移を持つライン上の標準的な DP になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | アクティブなパスに対するブルート フォース | 指数 | 指数 | 遅すぎる |
 | パス遷移のあるインデックス上の DP | O(nk) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 移動日数を昇順に処理し、各ポジションを決定点として扱います。 

1. まず、旅行日を並べ替えるか、すでに並べ替えられていると仮定し、カレンダー時刻 t[i] と運賃 f[i] の 2 つの配列を保持します。 これにより、単純な比較を使用してパスの有効性ウィンドウを推論できるようになります。 
2. インデックス i から始まる旅行日数をカバーする最小コストを表す DP 配列 dp[i] を定義します。 最後の旅行日以降は旅行日数が残っていないため、dp[n] = 0 に設定します。 これにより、自然な右から左への計算順序が与えられます。 
3. 各インデックス i および各パス タイプについて、i で開始した場合にこのパスがどこまで拡張できるかを計算します。 旅行日数が t[i] から p 日以内である間前方にスキャンし、d 回の使用に達するまでこのウィンドウに含まれる旅行日数をカウントします。 結果のエンドポイントは j(i, type) です。 このステップでは、カレンダー制約をインデックスベースのジャンプに変換します。 
4. dp[i] の再帰では 2 つの選択肢が考慮されます。 i 日目の料金を直接支払うことができ、コスト f[i] + dp[i+1] が得られます。 あるいは、すべてのパス タイプについて、コスト c に dp[j(i, type)] を支払って、i 日目にそのパスを購入することもできます。 これらすべてのオプションから最小値を採用します。 これは、パスが旅行日数の末尾を消費して先にスキップするという考えをエンコードしています。 
5. 必要なときにすべての遷移がすでにわかっているように、n−1 から 0 までの dp を計算します。 答えは dp[0] です。 

それが機能する理由は、実行可能なすべての戦略が、旅行当日の最も早い時点で最初の決定を下さなければならないという事実から来ています。 どのソリューションでも、その日の料金を支払うか、その日からパスを開始します。 その決定が修正されると、問題の残りの部分は同じになりますが、後のインデックスに移されます。 DP はこの分解を正確に捕捉し、j(i, type) の事前計算により、重複するアクティブなパスを明示的に追跡する必要なく、パスのすべての効果を正しくエンコードします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    t = []
    f = []
    for _ in range(n):
        ti, fi = map(int, input().split())
        t.append(ti)
        f.append(fi)

    passes = []
    for _ in range(k):
        p, d, c = map(int, input().split())
        passes.append((p, d, c))

    dp = [0] * (n + 1)

    for i in range(n - 1, -1, -1):
        best = f[i] + dp[i + 1]

        for p, d, c in passes:
            limit_time = t[i] + p
            cnt = 0
            j = i
            while j < n and t[j] <= limit_time and cnt < d:
                cnt += 1
                j += 1
            best = min(best, c + dp[j])

        dp[i] = best

    print(dp[0])

if __name__ == "__main__":
    solve()
```実装は DP 定義に直接準拠します。 内側のループは、パスがカバーできる旅行日数を i から計算し、時間枠を超えるか、使用制限 d に達したときに停止します。 結果として得られるインデックス j は、パスを使用した後の最初のカバーされていない日です。 その後、遷移は dp[j] に直接移動します。 

主な微妙な点は、j が暦日ではなく実際の旅行日数のみをカウントするようにすることです。 これが、算術限界を計算するのではなく、インデックスを反復処理する理由です。 もう 1 つの重要な詳細は、dp[j] が常に既知であるように dp が逆方向に計算されることです。

 ## 特殊なケース

 重要なエッジケースは、パスの有効期間が長いものの、使用制限が非常に小さい場合です。 たとえば、旅行日の前半は混雑しているが、後半はまばらである場合、パスはウィンドウが終了する前に割り当てを使い果たす可能性があります。 このアルゴリズムは、ウィンドウ全体をカバーすると仮定するのではなく、実際にカバーされる旅行日数を明示的にカウントすることでこれを処理します。 

もう 1 つのエッジ ケースは、パスが時間的に重複しているものの、カバレッジ内では重複していない場合です。 複数のパスが同時にアクティブになる場合でも、DP は各パスを i から j(i, type) への単一のジャンプに圧縮することでモデリングの重複を完全に回避し、可用性を二重にカウントしないようにします。 

最後のエッジケースは、移動シーケンスの終わり近くでパスが開始されるときに発生します。 この場合、j(i, type) はすぐに n になり、dp[j] は正確にゼロになります。つまり、特別な処理を必要とせずにパス料金が残りの運賃とのみ比較されることになります。
