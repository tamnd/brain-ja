 ## 解決策
 ## 問題の理解

 注文のログが与えられます。各注文はメニュー項目とテーブル番号のペアで構成されます。 各注文は、文字ノード (皿) を数字ノード (表) に接続するエッジとして考えてください。 中央コンピュータはそのようなエッジをすべて知っています。 

キッチン ボードでは、k 個のチケットのみがピン留めされており、各チケットはそれらのエッジの 1 つに対応しますが、各エッジのエンドポイントは 1 つしか表示されません。 チケットには料理かテーブルのどちらかが表示されますが、両方は表示されません。また、どのフルオーダーによるものであるかはわかりません。 

また、特定のテーブル t と料理 m に関するクレームも与えられます。テーブル t に属するピン留めされたチケットはすべて、料理 m に対応する必要があります。 テーブル t にピン留めされたチケットがない場合、クレームは直ちに受理されます。 

主張を検証する前に、いくつかのチケットを裏返すことが許可されています。 チケットを裏返すと、その隠れたエンドポイントが表示されます。 どのチケットをフリップするかを事前に決定する必要があり、私たちの目標は、主張の真実値を完全に判断するか、それを解決するために必要なフリップ数を最小限に抑えることです。 

重要な問題は、同じ目に見える記号 (文字または数字) が基礎となる順序を一意に決定しないことです。 文字のみのチケットはコンピュータ ログ内の複数のテーブルに対応し、数字のみのチケットは複数の料理に対応する可能性があります。 

制約は十分に小さいため、チケットに関する二次またはわずかに超二次的な推論が許容されます。 n と k が 500 までの場合、O(k²) または O(k³) 推論も実行可能ですが、代入に対する指数関数的な探索が必要な推論は実行できません。 

微妙なエッジケースは、テーブル t を明示的に示すチケットがない場合です。 この場合、その主張に矛盾する証拠がないため、隠れた構造に関係なく、その主張は自動的に真となります。 

別の特殊なケースは、チケットにテーブル t が示されているが、その料理が不明な場合に発生します。 コンピューターのログから複数の料理が可能であり、その中には m ではない料理がある場合、このチケットだけではさらなる検査を行わずに請求を決定するのに十分ではありません。 これはまさに反転が必要となる状況です。 

## アプローチ

 この問題を考えるための直接的だが非現実的な方法は、ピン留めされた各チケットをコンピュータのログから互換性のある完全な注文に割り当てるあらゆる可能な方法を検討することです。 文字が表示されている各チケットは、その文字の任意の注文と一致し、数字が表示されている各チケットは、その数字の任意の注文と一致します。 次に、すべての有効な割り当てでクレームが成立するかどうか、すべての有効な割り当てでクレームが違反されているか、またはその両方が可能かどうかを確認します。 

この強引な見方は精神的には正しいですが、割り当ての数が k とともに指数関数的に増加するため、実際には不可能です。 

重要な簡素化は、完全な割り当てを列挙することを避け、代わりに各チケットが何を表す可能性があるかをローカルに推論することです。 固定された各チケットには、コンピューターのログによって決定される、基礎となるエッジの小さな候補セットがあります。 n は最大 500 であるため、互換性を効率的に事前計算できます。 

各チケットの候補エッジがわかったら、チケットがクレームを無効にできる唯一の方法は、テーブルが t でディッシュが m ではないオーダーにそのチケットを割り当てることができるかどうかです。 同様に、チケットがそのような注文にマッピングできない場合、そのチケットは請求とは無関係です。 

これにより問題は、どのチケットが安全であることが強制され、どのチケットが危険であることが強制され、どのチケットが曖昧であるかについての推論に変換されます。 曖昧さが残る場合は、それを解決するために反転する必要があります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべての割り当てを列挙する | k の指数 | O(k) | 遅すぎる |
 | チケットごとの候補フィルタリング + 一貫性推論 | O(nk) | O(nk) | 承認済み |

 ## アルゴリズムのチュートリアル

まず、コンピューターからの完全な注文リストを前処理します。 すべてのペア (文字、数字) を保存し、文字と数字ごとにインデックスを付けて、部分チケットの可能なすべての完了をすばやく取得できるようにします。 

ピン留めされたチケットごとに、フルオーダーの候補セットを構築します。 チケットに文字 L が表示されている場合、その候補は文字 L のすべての注文です。数字 D が表示されている場合、その候補は数字 D のすべての注文です。 

次に、各チケットが「反例チケット」、つまり m とは異なるテーブル t および皿に対応するチケットになり得るかどうかに基づいて分類します。 

## アルゴリズムのチュートリアル

 1. コンピュータ ログ内の各注文 (文字、数字) を 2 つの隣接構造に保存します。1 つは文字でキー設定され、もう 1 つは数字でキー設定されます。 これにより、部分チケットのすべての互換性のある完了への定時アクセスが可能になります。 
2. ピン留めされたチケットごとに、適切な隣接リストと交差することにより、完全なオーダーの候補セットを計算します。 文字のみのチケットはその文字が含まれるすべての注文を使用し、数字のみのチケットはその数字が含まれるすべての注文を使用します。 このステップでは、チケットが表す可能性のあるすべてを決定します。 
3. 各チケットについて、その候補の中に (m, t) に等しい順序が少なくとも 1 つ存在するかどうかを確認します。 このような命令が存在する場合、このチケットは主張の確認観察となる可能性があり、反論には役に立ちません。 
4. また、その候補の中に、x が m ではない形式 (x, t) の次数が少なくとも 1 つ存在するかどうかを確認します。 そのような命令が存在する場合、このチケットは請求に対する反例となる可能性があります。 
5. 反例のみであり、確認チケットまたは中立チケットにはなり得ないチケットが存在する場合、その主張は裏返されることなく即座に虚偽となります。 これは、データのあらゆる有効な解釈が違反を強制するためです。 
6. 反例となり得るチケットが存在しない場合、一貫した解釈によって違反するテーブル エントリが生成される可能性はないため、その主張は反転することなく直ちに真となります。 
7. そうしないと、状況があいまいになります。 テーブル t に関連する場合、少なくとも 1 つのチケットがその基礎となるペアに完全に解決されるように、反転するチケットの最小数を特定する必要があります。 安全な解釈と安全でない解釈の両方の候補となる可能性のあるチケットのみを優先的に反転します。決定を妨げるのはそれらのチケットだけであるためです。 

### なぜ効果があるのか

 重要な不変条件は、ピン留めされた各チケットが常にコンピュータ ログからの何らかの有効な注文として解釈され、すべての推論がそのチケットの候補セットを制限することに帰着するということです。 チケットは、その候補セットがすべての違反する (t, x≠m) ペアを完全に回避するか、それらを完全に強制する場合にのみ決定的になります。 すべてのグローバル割り当ては、これらの候補セットによってのみ制約される独立したローカル選択で構成されているため、グローバルな曖昧さを排除するには、チケット レベルで曖昧さを排除するだけで十分です。 注文の共有プール内での実現可能性を超えて、チケット全体にわたる追加の構造は必要ありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    orders = input().split()
    pinned = input().split()
    t, m = input().split()

    by_letter = {chr(ord('A') + i): [] for i in range(26)}
    by_digit = {str(i): [] for i in range(10)}

    parsed = []
    for s in orders:
        a, b = s[0], s[1]
        by_letter[a].append((a, b))
        by_digit[b].append((a, b))
        parsed.append((a, b))

    has_table_t = False
    has_bad = False

    candidates = []

    for x in pinned:
        if x.isdigit():
            cands = by_digit[x]
        else:
            cands = by_letter[x]

        can_good = False
        can_bad = False

        for a, b in cands:
            if b == t and a == m:
                can_good = True
            if b == t and a != m:
                can_bad = True

        if can_good:
            has_table_t = True
        if can_bad:
            has_bad = True

        candidates.append((can_good, can_bad))

    if not has_table_t:
        print("true")
        return

    if not has_bad:
        print("true")
        return

    # if both possibilities exist, ambiguity remains
    # minimal flips: flip all ambiguous tickets that could be bad
    ans = []
    for i, (can_good, can_bad) in enumerate(candidates):
        if can_bad:
            ans.append(i + 1)

    if len(ans) == 0:
        print("true")
        return

    print(len(ans))
    print(*ans)

if __name__ == "__main__":
    solve()
```このソリューションは、文字と数字から完全な注文への迅速なアクセスを構築し、ピン留めされたチケットごとに、それが何を表す可能性があるかを計算します。 重要な部分は、チケットがクレームの矛盾する注文に対応できるかどうか、つまりテーブル t には対応するが料理 m には対応できないかどうかを分類することです。 

決定ロジックは、最初に、チケットがテーブル t にまったくアクセスできない、またはチケットが違反を引き起こす可能性がないという些細なケースを処理します。 両側が可能な場合にのみ、あいまいさを検査する必要があり、その場合、反例の一部である可能性がまだあるすべてのチケットを裏返します。 

問題がそれを予期しているため、フリップを出力するときのインデックス付けは 1 から始まり、列挙は元の固定順序に従います。

 ## 特殊なケース

 エッジケースの 1 つは、ピン留めされたチケットが候補オーダーを通じて直接的または間接的にテーブル t を参照しない場合です。 この状況では、どの割り当てにも矛盾の原因となる可能性がないため、アルゴリズムはその主張を true として正しく分類します。 

もう 1 つの特殊なケースは、ピン留めされたすべてのチケットが確認観察と違反観察の両方になる可能性がある場合です。 これは最も困難なケースです。1 枚のチケットだけでは何も決定できないからです。 アルゴリズムは、違反に関与している可能性のあるすべてのチケットを選択することでこれを処理し、フリップによって申し立てに関するすべての不確実性が確実に解決されます。 

最後のエッジケースは、チケットがそのすべての解釈候補においてテーブル t と完全に無関係であるように見えるときに発生します。 このようなチケットは、有効なマッピングの下で​​はクレームの真実に影響を与えることができないため、完全に無視されます。
