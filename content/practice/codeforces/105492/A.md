 ## 解決策
 ## 問題の理解

 私たちには、いくつかのチームがすでに最高から最悪の順に並べられた、凍結されたコンテストのスコアボードが与えられます。 各チームには、問題ごとの提出ステータス (承認、拒否、保留中、またはまったく提出なし) を説明する行があります。 授賞式中に保留中のエントリーが 1 つずつ解決されるため、動的に重要となるのは保留中のエントリーだけです。 

解決プロセスは決定的です。 すべてのステップで、現在のランキングを確認し、保留中の提出が少なくとも 1 つ残っている最も低いランクのチームを選択します。 そのチーム内では、常に左端の保留中の送信を解決します。 その後、その保留中の提出は、提供された一連の視聴者の反応に従って、承認または拒否されたことが明らかになります。 それが拒否された場合、他は何も変わりません。 それが受け入れられた場合、そのチームの解決した問題の数は 1 つ増加し、ランキングでの地位が向上する可能性があります。ランキングは常に受け入れられた問題の数によって決定され、この問題に曖昧さが生じることのない固定の同点順位が設定されているためです。 

出力では、保留中の送信がすべて処理された後の特定のチームの最終ランクが求められます。 

制約は小さく、最大でも 100 チーム、100 個の問題があります。 これにより、すべてのチームを繰り返しスキャンし、時々再並べ替えるシミュレーションが十分に高速であることがすぐにわかります。 ここでは、n の 2 次または 3 次であっても安全です。これは、演算の総数が数万回に制限されているためです。 

微妙なエッジ ケースは、「左端の保留中の提出」がグローバルではなくチームごとであるという事実から生じます。 チームに複数の保留スロットがある場合は、常に左から右の順序でスロットを消費するようにする必要があります。 もう 1 つの注意が必要な点は選択順序です。各ステップで最高位のチームではなく、常に最低ランクの適格なチームを選択します。 誤って上からスキャンする単純な実装では、異なる更新シーケンスが生成され、最終的なランキングも異なります。 

## アプローチ

 強引な解釈は簡単です。授賞式を段階的に繰り返しシミュレーションします。 各ステップでチームを下から上にスキャンして、まだ保留中の提出物がある最初のチームを見つけます。 そのチーム内で、問題を左から右にスキャンして、最初の保留中の問題を見つけます。 結果を適用し、必要に応じて受け入れられた数を更新し、受け入れられた数を使用してチームを並べ替えることによってランキングを最初から再計算します。 

これが機能するのは、各操作が明示的に定義されており、制約が小さいためです。 ただし、受け入れのたびに注文全体を再計算すると、原則としてコストが高くなる可能性があります。 最大 100 のイベントと 100 のチームがある場合、100 の要素を最大 100 回並べ替えることはまだ簡単ですが、概念的には無駄です。 

重要な観察は、順序に影響を与える唯一の動的状態は、チームごとに受け入れられる問題の数であるということです。 保留中の送信の構造は、どのチームが次に処理されるかを決定するだけであり、ランキングの計算方法は決定しません。 これにより、チームごとに保留中のインデックスの単純なリストを維持し、必要に応じて順序を再計算することができます。 

クリーンな実装では、各チームの承認された数を追跡し、承認された提出ごとにチームを繰り返し並べ替えるだけです。 n が小さいため、これはすでに十分に最適です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (再スキャン + 再スキャン + 毎回ソート) | O(n² m + n m log n) | O(nm) | 承認済み |
 | 最適 (定期的なソートを使用したシミュレーション) | O(n m log n) | O(nm) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは 3 つの状態を維持します。各チームの現在の受け入れ済み問題数、チームの固定された初期順序、および各チームの左から右の順序での保留中の提出のインデックスのリストです。 

また、承認が発生するたびに更新されるチームのグローバルな順序も維持しています。

1. 各チームの受け入れられた数をその行の「A」を数えて初期化し、各チームの保留ポジションのリストを作成します。 これにより、チームごとに常に一定時間内に次の保留中の提出物を取得できるようになります。 
2. 承認された数に基づいてチームを降順に並べ替えて、初期ランキングを作成します。 このランキングは、セレモニーが始まる前に凍結されたスコアボードの順序を表します。 
3. 指定された順序の各イベントについて、次にどの提出が解決されるかを特定します。 これを行うために、保留リストが空ではないチームが見つかるまで、ランキングの下から上に向かってチームをスキャンします。 そのチームはこの出来事の影響を受けたチームです。 
4. 問題は左端の保留中の解決を指定しているため、そのチームから最初の保留中のポジションを削除します。 
5. チャントが拒否を示している場合、私たちはそれ以上何もしません。 それが受け入れを示している場合、そのチームの受け入れ数を 1 つ増やします。 
6. 承認後、更新された承認数を使用してチームを再度並べ替えることにより、ランキングを再計算します。 これは順位が上昇する可能性を反映している。 
7. すべてのイベントが処理された後、対象チームのランキングにおける最終順位を特定し、出力します。 

### なぜ効果があるのか

 不変条件は、各イベント後に維持される順序が、それまでに処理されたすべての送信の受け入れられた数による順序とまったく同じであり、保留選択ルールが常に未解決の作業を持つ最下位のチームに適用されるということです。 ランキングは受け入れられた数のみに依存し、各受け入れは次の選択の直前に適用されるため、シミュレーションはスコアボードの正確な進化を反映します。 将来のイベントに依存する決定はないため、貪欲な選択順序は全体を通じて有効です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, r = map(int, input().split())
    r -= 1

    grid = []
    pending = [[] for _ in range(n)]
    acc = [0] * n

    for i in range(n):
        s = input().strip()
        grid.append(s)
        for j, ch in enumerate(s):
            if ch == 'A':
                acc[i] += 1
            elif ch == 'P':
                pending[i].append(j)

    order = list(range(n))

    def rebuild():
        order.sort(key=lambda i: (-acc[i], i))

    rebuild()

    for _ in range(sum(len(pending[i]) for i in range(n))):
        # pick lowest ranked team with pending
        team = None
        for i in reversed(order):
            if pending[i]:
                team = i
                break

        idx = pending[team].pop(0)

        _, result = input().split()

        if result[0] == 'A':
            acc[team] += 1
            rebuild()

    # find final rank of team r
    rebuild()
    for i, t in enumerate(order):
        if t == r:
            print(i + 1)
            return

if __name__ == "__main__":
    solve()
```このソリューションは、チームごとに保留中の送信を追跡するため、リストからポップした後、左端の保留中の要素が常に一定時間選択されるようにします。 拒否されても順序は変更されないため、ランキングは提出が受け入れられた後にのみ再計算されます。 

重要な実装上の選択は、必要な場合にのみ並べ替えを再計算することです。 保留中の操作は合計で最大 10,000 件あるため、毎回最大 100 個の要素を並べ替えるのは快適に高速です。 

次のチームの選択は、現在のランキングの最下位からスキャンすることによって行われ、保留中の提出物がある場合は下位ランクのチームが最初に処理されるという要件と一致します。

 初期状態:

 | ステップ | 順番（上→下） | 選択保留中 | アクション | 受け入れられた数 |

 | 1 | T1、T2 | T2 最初の保留中 | 受け入れる | 更新されました |

 最初の受付後、他のチームを追い抜くかどうかによって順位が変わる場合があります。 2 番目のイベントはランキングに影響しません。 

これは、受け入れられたイベントのみが構造変化を引き起こすことを示しています。 

### 例 2

 ここでは両方のイベントが受け入れられます。 

| ステップ | 注文 | 選ばれたチーム | アクション | 効果 |

 これは、選択順序が更新されたランキングに依存するため、承認されるたびに再計算が必要であることを示しています。

 ## 特殊なケース

 エッジ ケースの 1 つは、チームに保留中の提出物があるにもかかわらず、プロセスの後半まで最低ランクの適格チームにならない場合です。 下からのスキャンにより正確性が保証されます。 

もう 1 つのケースは、複数回連続して拒否が発生した場合です。 拒否によって受け入れられた数は変更されないため、ランキングは安定したままとなり、不必要な並べ替えがトリガーされることはありません。 

最後のエッジケースは、チームの承認により一度に複数のポジションが飛び出す場合です。 完全な再並べ替えでは、ランキングが更新されたカウントに基づいてグローバルに再計算され、スコアボードの定義との一貫性が維持されるため、これが自動的に処理されます。
