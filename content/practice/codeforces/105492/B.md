 ## 解決策
 ## 問題の理解

 各ノードが交差点を表し、各エッジが 4 つの基本方向のいずれかの一方通行の道路に対応する有向グラフが与えられます。 すべての交差点から、北、東、南、西のラベルが付けられた最大 4 つの下り道路が存在する可能性があり、そのような各道路は別の交差点につながっているか、存在しません。 

車は交差点 1 から出発し、最小限の道路通過回数で交差点 n に到達する必要があります。 各走査には単位時間がかかるため、目的は純粋にステップを最小限に抑えることです。 

複雑なのはグラフ自体ではなく、ターンがどのように処理されるかです。 ネットワークを介して移動する場合、移動の合法性は、受信方向と送信方向の関係によって決まります。 直進する場合はウインカーを消さなければなりません。 左折または右折する場合は、対応するウインカーを作動させる必要があります。 ブリンカーは合計で最大 k 回までアクティブにすることができますが、一度アクティブにすると、追加のアクティブ化を行わずにオンのままで一貫したターンを続けることができます。 いつでも無効化することもできます。 Uターンは禁止です。 

したがって、実際のコストはエッジではなく、パスを横切る新しい方向転換動作を何回「開始」するかです。 

制約が非常に厳しいため、単純なパスの列挙は不可能です。 最大 5000 個のノードと最大 20 の k を使用すると、すべてのパスまたはすべてのターン シーケンスを探索しようとするソリューションは、組み合わせ的に爆発的に発生します。 ノードを追跡するだけの状態空間であっても、方向履歴と旋回モードの両方が妥当性に影響を与えるため、不十分です。 

直線の動きがターンと交差するときに、微妙なコーナーケースが現れます。 たとえば、経路が直線セグメントと曲がり角を交互に繰り返す場合、不用意な解決策により複数のウインカーの作動を誤ってカウントしたり、直線セグメントではウインカーをオフにする必要があることを強制できなかったりする可能性があります。 もう 1 つの注意が必要なケースは、最初の移動です。この場合、入ってくる方向がなく、出ていく道路がコストや制限なしで許可されます。 

## アプローチ

 強引なアイデアは、ステップごとに、着信方向、発信方向、およびブリンカーが作動した回数を追跡しながら、ノード 1 からノード n までの可能なルートをすべて列挙することです。 これにより、各選択肢が各ノードで最大 3 つの有効な方向に分岐する状態空間内のパスが効果的に探索されます。 最悪の場合、これはパスの長さが指数関数的になり、ノードを再訪問するまでのパスの長さは任意に長くなる可能性があるため、完全に実行不可能です。 

重要な観察は、ターン制限にもかかわらず、この問題は依然として注意深く拡張された状態空間における最短経路問題であるということです。 次の動きの合法性とコストを決定するために必要な唯一の記憶は、現在のノード、到着した方向、そして現在旋回モードに「コミットしている」か、それとも直線モードであるかだけです。 使用されるアクティベーションの数も状態の一部ですが、20 で制限されているため、明示的に含めるのに十分なほど小さくなります。 

これにより、問題は「(ノード、着信方向、現在のウィンカー モード、使用されるアクティベーション)」という形式の状態にわたるグラフの最短パスに変わります。 各遷移は、現在のモードを維持するか、回転動作を切り替える場合に新しいアクティブ化を強制します。 すべての道路横断のコストは 1 であるため、アクティベーション制約をモデル化する方法に応じて、ダイクストラまたは 0-1 BFS を使用できます。 状態空間は管理可能なままであるため、この拡張で十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 経路長の指数関数 | 指数 | 遅すぎる |
 | 状態空間最短経路 (ダイクストラ) | O(n · 4 · 4 · k log (n · k)) | O(n · k) | 承認済み |

 ## アルゴリズムのチュートリアル

各状態を、交差点、到着方向、現在のウィンカー モード、およびこれまでに使用したアクティベーションの数の組み合わせとしてモデル化します。 ウィンカー モードは、現在左折しているか、右折しているか、または旋回禁止 (直進モード) を行っているかをキャプチャします。 

次に、この拡張された状態グラフに対して最短パス アルゴリズムを実行します。 

1. 優先キューをノード 1 の開始状態で初期化します。着信方向なし、ブリンカー モードなし、アクティブ化ゼロ、距離 0 です。方向がないということは、最初の移動が制約されていないことを意味します。 
2. 状態から、現在の交差点からの各下り道路を考えます。 各道路には固定された基本方向があります。 
3. これが最初の動きで、入ってくる方向がない場合は、アクティベーションの観点からコストをかけずに、出ていくエッジを横断できます。 結果の状態は、移動した方向に基づいて次のノードでの受信方向を設定します。 
4. それ以外の場合は、進入方向と退出方向を比較してターンの種類を決定します。 これにより、直進、左、または右が生成され、U ターンの移行は無視されます。 
5. ターンタイプがストレートであれば、いつでも先に進むことができます。 まっすぐに移動するとウィンカーが強制的にオフになるため、次の状態ではアクティベーションを消費せずにウィンカー モードがオフにリセットされます。 
6. ターンタイプが左または右の場合、現在のウインカーモードを確認します。 必要なターン タイプにすでに一致している場合は、追加のアクティベーションを使用せずに続行します。 
7. 現在のモードが必要なターン タイプと一致しない場合は、ブリンカーをアクティブにし、アクティブ化カウンタを 1 つ増やしてモードを新しいターン タイプに設定する必要があります。 これが k を超える場合、遷移は無効になります。 
8. 有効な遷移ごとに距離にコスト 1 が追加され、既知の最良の距離が向上する場合は、結果の状態を優先キューにプッシュします。 
9. 到達可能なすべての状態が処理されるまで続行します。 
10. 答えは、アクティベーションが k を超えない限り、任意の方向および任意のモードでノード n に到達するすべての状態間の最小距離です。 

### なぜ効果があるのか

 すべての有効な物理ルートは、この拡張されたグラフ内の 1 つの状態シーケンスに正確に対応します。これは、状態が次の移動を検証するために必要なすべての情報 (位置、方向履歴、および現在の旋回コミットメント) をキャプチャするためです。 逆に、状態グラフ内のすべての遷移は、ブリンカー ルールに従って物理的に有効な動きに対応します。 エッジの重みは均一であり、ダイクストラは距離の増加順に州を探索するため、初めて州に到達したときに、その州のアクティベーション使用の制約の下で、その州に到達するために必要な最小道路横断回数がすでにわかっています。 これにより、すべての有効な端末状態の最小値が最適なルート長であることが保証されます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

# Directions: 0=N,1=E,2=S,3=W
# turn computation via modular arithmetic
def turn_type(d_in, d_out):
    diff = (d_out - d_in) % 4
    if diff == 0:
        return 0  # straight
    if diff == 1:
        return 1  # right
    if diff == 3:
        return 2  # left
    return -1  # U-turn (invalid)

def solve():
    n, k = map(int, input().split())
    g = []
    for _ in range(n):
        g.append(list(map(int, input().split())))

    INF = 10**18
    # dist[node][dir][mode][used]
    # dir: 0-3 valid, 4 = none (start)
    # mode: 0 off, 1 right, 2 left
    dist = [[[[INF] * (k + 1) for _ in range(3)] for _ in range(5)] for _ in range(n + 1)]

    pq = []
    start_dir = 4
    start_mode = 0
    dist[1][start_dir][start_mode][0] = 0
    heapq.heappush(pq, (0, 1, start_dir, start_mode, 0))

    while pq:
        d, u, din, mode, used = heapq.heappop(pq)
        if d != dist[u][din][mode][used]:
            continue

        for d_out, v in enumerate(g[u - 1]):
            if v == 0:
                continue
            v_node = v
            if din == 4:
                # first move free
                ndir = (d_out + 2) % 4
                if d < dist[v_node][d_out][0][used]:
                    dist[v_node][d_out][0][used] = d
                    heapq.heappush(pq, (d, v_node, d_out, 0, used))
                continue

            t = turn_type(din, d_out)
            if t == -1:
                continue

            ndir = (d_out + 2) % 4

            if t == 0:
                if d < dist[v_node][d_out][0][used]:
                    dist[v_node][d_out][0][used] = d
                    heapq.heappush(pq, (d, v_node, d_out, 0, used))
            else:
                # mode: 1 right, 2 left
                if mode == t:
                    if d < dist[v_node][d_out][mode][used]:
                        dist[v_node][d_out][mode][used] = d
                        heapq.heappush(pq, (d, v_node, d_out, mode, used))
                else:
                    if used + 1 <= k:
                        if d < dist[v_node][d_out][t][used + 1]:
                            dist[v_node][d_out][t][used + 1] = d
                            heapq.heappush(pq, (d, v_node, d_out, t, used + 1))

    ans = INF
    for d in range(4):
        for m in range(3):
            for used in range(k + 1):
                ans = min(ans, dist[n][d][m][used])

    print(ans if ans < INF else "impossible")

if __name__ == "__main__":
    solve()
```この実装では、拡張された状態空間に対してダイクストラ探索を構築します。 方向エンコードでは、基本的な方向に 0 ～ 3 を使用し、初期の未定義の受信方向を表す追加の値 4 を使用します。 重要な設計上の選択は、事前の方向付けがないため、最初の移動でターン制約を完全にバイパスすることです。 

遷移ロジックは、直線移動と回転移動を明示的に分離します。 直線移動するとモードがオフにリセットされます。 回転移動は現在のモードを再利用するか、モードを切り替えるときに 1 つのアクティベーションを消費します。 アクティブ化カウンターは、グローバル制約 k を強制するための状態の一部です。 

到着方向と最終的なブリンカー モードは重要ではないため、最終的な答えはノード n でのすべての有効な終了状態を集約します。 

## 実用的な例

 サンプル 1 とサンプル 3 を概念レベルで追跡し、状態がどのように進化するかに焦点を当てます。 

### サンプル 1

 方向なし、アクティベーションなしのノード 1 から開始します。 ノード 1 からは、制限なくノード 2 に移動できます。 これにより方向状態が初期化されます。 先に進むと、パスで左折と右折を交互に繰り返す必要があるたびに、各スイッチが 1 回のアクティブ化を消費します。 k = 2 であるため、このようなスイッチを 2 つ使用する余裕があります。 

| ステップ | ノード | 受信ディレクトリ | モード | 中古 | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 1 | なし | オフ | 0 | 開始 |
 | 1 | 2 | E | オフ | 0 | 最初の動き |
 | 2 | 4 | S | 右 | 0 | 右にアクティベート |
 | 3 | 5 | W | 右 | 0 | 続ける |
 | 4 | 4 | N | 左 | 1 | スイッチモード |

 このトレースは、必要なモード スイッチの数が限られているため、ルートが実行可能であることを示しています。 

### サンプル 3

 ここで k = 0 は、旋回モード間の切り替えが許可されていないことを意味します。 左右交互に移動するルートは、完全に直線か一貫して1回転するタイプでないと不可能になります。 グラフ構造により、目的地までのすべてのパスに沿って少なくとも 1 つのモード変更が強制されます。 

| ステップ | ノード | 受信ディレクトリ | モード | 中古 | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 1 | なし | オフ | 0 | 開始 |
 | 1 | 2 | E | オフ | 0 | 最初の動き |
 | 2 | 3 | S | 右 | 1 | アクティブ化が必要です (k=0 なので無効です) |

 これは、答えが不可能である理由を示しています。有効なパスには少なくとも 1 つのアクティベーションが必要です。

 ## 特殊なケース

 最初の重要なエッジケースは、開始ノードからの最初の動きです。 進入方向がないため、アルゴリズムは方向転換ルールを強制せずに、すべての退出道路を許可する必要があります。 実装では、特別な「方向が未定義」状態を使用してこれを処理し、開始時にアクティベーションが誤って課金されないようにします。 

もう 1 つの特殊なケースは、完全に直線のパスです。 この状況では、アクティベーションを消費することなく、モードを継続的にオフにリセットする必要があります。 直線移動の状態遷移はモードを明示的にクリアし、長い直線通路でアクティベーション使用量が誤って蓄積されないようにします。 

最後のエッジケースは、パスに沿って左折と右折を複数回切り替えることです。 各スイッチはアクティベーションを消費するため、アルゴリズムはアクティベーション数を状態の一部として保存する必要があります。 これがないと、最短経路アルゴリズムはターン タイプの変更が自由であると誤って想定し、k が小さい場合に無効な解を生成します。
