 ## 解決策
 ## 問題の理解

 このタスクは、ルート ツリー内の祖先関係を維持し、クエリすることです。 接続された非巡回グラフが与えられ、1 つのノードを構造のルートとして解釈します。 各クエリでは、2 つのノードの最も低い共通祖先、つまりルートからノードへの両方のパス上にあるルート付きツリーの最も深いノードが求められます。 

より具体的に言えば、各ノードを階層内の点として想像してください。 2 つのノードの場合、ルートへのパスは最終的にマージされます。 上に移動するときにパスが交わる最初のノードがクエリに対する答えになります。 

入力は、エッジによって記述され、その後に複数のクエリが続くツリーとして理解できます。 各クエリは 2 つのノードを提供し、出力は最も近い共有祖先を表す 1 つのノードです。 

このタイプの問題における主な制約の意味は、ツリーが大きくなり、通常は最大 10^5 のノードと同様の規模のクエリが存在する可能性があることです。 すべてのクエリに対して上向きのパスを再計算するソリューションでは、長いチェーンを繰り返し走査することになり、最悪の場合は二次的な動作が発生します。 10^5 クエリでは、クエリごとの線形走査でも遅すぎるため、各クエリを対数時間または定数時間に短縮する前処理アプローチが必要です。 

この設定では、いくつかの特殊なケースが重要になります。 クエリされた一方のノードが他方のノードの祖先である場合、答えは自明のことながら祖先ノード自体になります。 たとえば、ルート 1 のチェーン 1-2-3-4 では、(2, 4) をクエリすると 2 が返されるはずです。単純な上方ウォーク実装では、比較前に両方のノードが均等にリフトされる必要があると想定している場合、これを簡単に見逃す可能性があります。 

もう 1 つのエッジ ケースは、構造がリンク リストに縮退する、歪んだツリーです。 たとえば、1-2-3-4-5-6。 前処理を行わないと、上向きトラバーサルの繰り返しがクエリごとに最悪の場合線形になり、正確性は保たれていてもパフォーマンスの保証が損なわれます。 

## アプローチ

 直接的なアプローチでは、パスが交差するまで両方のノードからルートに向かって上向きに歩くことで、各クエリを独立して処理します。 これは、両方のノードの深さが一致するまで 1 つのノードをその親に繰り返し移動し、一致するまで両方を一緒に上に移動することで実装できます。 これが機能するのは、ツリー内ではルートへのパスが一意であるため、最初に見つかった共有ノードが最下位の共通祖先となるためです。 

正確さは単純ですが、トラバーサルを繰り返すことで非効率性が生じます。 各クエリは縮退ツリーで O(n) ステップを必要とする可能性があり、多くのクエリでは O(nq) につながり、n と q の両方が大きい場合には遅すぎます。 

重要な観察は、祖先クエリが同じ構造に対して繰り返されるということです。 上向きのジャンプを段階的に再計算する代わりに、すべてのノードに対して 2 の累乗のサイズの「ジャンプ」を事前計算できます。 これにより、上向きの動きが対数ホップに変換されます。 各ノードが 1 番目、2 番目、4 番目、8 番目などの祖先を認識したら、ノードを O(log n) で同じ深さまでリフトし、祖先が一致するまで同時にリフトできます。 

この手法は一般にバイナリ リフティングと呼ばれます。 ツリーは、直接の親を計算するために深さ優先検索または BFS で一度前処理され、その後、動的プログラミングによって上位の祖先が構築されます。 次に、各クエリは、上位から順に上位を比較することによって解決されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース上向きウォーキング | クエリあたり O(n) | O(n) | 遅すぎる |
 | バイナリリフティング | クエリあたり O(log n)、前処理 O(n log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 特に指定がない限り、ツリーのルートはノード 1 であると仮定します。

1. ツリーを効率的に走査できるように、エッジ リストから隣接リストを構築します。 このステップでは、エッジ スキャンを繰り返すことなく、構造を横断できるように準備します。 
2. 深さ優先検索または幅優先検索をルートから実行して、各ノードの深さと直接の親を計算します。 祖先を比較する前にノードを位置合わせするには深さが必要です。 
3. テーブルを事前計算します。`up[v][k]`はノード v の 2^k 番目の祖先を表します。最初の列は走査によってすでにわかっており、再帰を使用してより高い値が埋められます。`up[v][k] = up[up[v][k-1]][k-1]`。 これが機能するのは、2^k ジャンプが 2 つの 2^{k-1} ジャンプに分割できるためです。 
4. 各クエリ (u, v) について、まず u がより深いノードであることを確認します。 そうでない場合は、交換してください。 これにより、リフティング ロジックの一貫性が保証されます。 
5. 両方のノードが同じ深さになるまで、より深いノードを上に持ち上げます。 これは、深さの差のビットをチェックし、対応するジャンプを適用することによって行われます。 
6. アライメント後にノードが等しい場合、そのノードは LCA であり、すぐにそれを返すことができます。 これは、一方のノードが他方のノードの祖先である場合を処理します。 
7. それ以外の場合は、両方のノードを 2 の最大累乗から 0 まで同時に上に移動します。 2^k の祖先が異なる場合は常に、両方のノードをそれらの祖先までリフトします。 これにより、LCA をオーバーシュートしないことが保証されます。 
8. このプロセスの後、両方のノードは最下位の共通祖先のすぐ下にあるため、どちらかの親を返すと正しい答えが得られます。 

正確さはキーの不変条件を維持することにかかっています。ステップ 5 の後、両方のノードは同じ深さにあり、ステップ 7 の後、それらは LCA の異なるサブツリーに残りますが、その上の同じ直接の親チェーンを共有します。 バイナリリフティングテーブルは、祖先が異なる場合にのみジャンプが行われるため、真の祖先を越えてスキップすることがないことを保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

LOG = 20

def solve():
    n, q = map(int, input().split())
    g = [[] for _ in range(n + 1)]

    for _ in range(n - 1):
        u, v = map(int, input().split())
        g[u].append(v)
        g[v].append(u)

    up = [[0] * LOG for _ in range(n + 1)]
    depth = [0] * (n + 1)

    sys.setrecursionlimit(10**7)

    def dfs(v, p):
        up[v][0] = p
        for k in range(1, LOG):
            up[v][k] = up[up[v][k - 1]][k - 1]

        for to in g[v]:
            if to == p:
                continue
            depth[to] = depth[v] + 1
            dfs(to, v)

    dfs(1, 0)

    def lift(v, d):
        for k in range(LOG):
            if d & (1 << k):
                v = up[v][k]
        return v

    def lca(a, b):
        if depth[a] < depth[b]:
            a, b = b, a

        a = lift(a, depth[a] - depth[b])

        if a == b:
            return a

        for k in reversed(range(LOG)):
            if up[a][k] != up[b][k]:
                a = up[a][k]
                b = up[b][k]

        return up[a][0]

    out = []
    for _ in range(q):
        a, b = map(int, input().split())
        out.append(str(lca(a, b)))

    print("\n".join(out))

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from io import StringIO
    old_stdout = sys.stdout
    sys.stdout = StringIO()
    solve()
    out = sys.stdout.getvalue()
    sys.stdout = old_stdout
    return out.strip()

if __name__ == "__main__":
    solve()
```DFS は、1 回の走査で深さと直接の親の両方を構築し、同時に各ノードのバイナリ リフティング テーブルを埋めます。 の`lift`関数は、高さの差のビット表現に基づいてバイナリ ジャンプを適用し、直線的な上昇を回避します。 

の`lca`関数はまず深さを正規化し、次に位置合わせ後に 1 つのノードがもう 1 つのノードの祖先になるかどうかを確認します。 最終的な上向き同期リフティング ループは、LCA を越えることなくジャンプを最大化できるように、高パワーから低パワーまで慎重に書き込まれています。 

微妙な実装の詳細が初期化されています`up[1][k]`と取り扱い`0`null の親として。 これにより、ルートを超えてリフトするときのインデックス エラーが防止されます。 

## 実用的な例

 1 をルートとする単純なツリーを考えます。1 は 2 と 3 に接続され、2 は 4 と 5 に接続されます。クエリは LCA(4, 5) と LCA(4, 3) を要求します。 

| ステップ | | b | アクション |
 | --- | --- | --- | --- |
 | イニシャル | 4 | 5 | 深さが等しい |
 | リフトアライメント | 4 | 5 | 変更は必要ありません |
 | 上方比較 | 2 | 2 | 両方とも親に移動します |
 | 結果 | 2 | 2 | LCA が見つかりました |

 これは、両方のノードが同じサブツリー内にあり、その親に収束する場合を示しています。 

2 番目のクエリの場合:

 | ステップ | | b | アクション |
 | --- | --- | --- | --- |
 | イニシャル | 4 | 3 | 異なる深さ |
 | リフトアライメント | 4 | 3 | 3 すでに浅い |
 | 上方比較 | 2 | 1 | 不一致になるまで移動 |
 | 最後の親 | 1 | 1 | LCA |

 これは、LCA が両方のノードよりもルートに近い場合を示しています。

 ## 特殊なケース

 1-2-3-4-5 のような歪んだチェーンは、最悪の構造変性をテストします。 このアルゴリズムは依然として O(n log n) 前処理で祖先を計算し、各クエリは対数ジャンプのみを使用するため、LCA(5, 1) のようなクエリでも、バイナリ ステップ (5 → 3 → 1) を通じてノード 5 を上方にリフトすることによって解決され、すべての中間ノードに触れることなく正しく収束します。 

チェーン 1-2-3-4-5 の LCA(2, 5) など、あるノードが別のノードの祖先である場合、位置合わせステップではより深いノードのみが持ち上げられます。 リフティング後、すぐに等価性チェックがトリガーされ、最終比較ループに入らずに 2 が返されます。
