 ## 解決策
 ## 問題の理解

 ピザ屋での一連のイベントを処理します。 

次のタイプのクエリのたびに`1 m`と表示されると、新しい顧客が到着します。 顧客は次から始まる連続 ID を受け取ります。`1`、到着順に。 各顧客には予測支出額もあります`m`。 

タイプのクエリ`2`まだサービスを受けていない最も早い顧客にサービスを提供するよう求められます。 

タイプのクエリ`3`現在サービスを受けていない顧客に、予測される最大の費用でサービスを提供するよう求められます。 複数の顧客が同じ支出額を持っている場合は、その中で最も早い到着を選択する必要があります。 

各顧客に対して 1 回だけサービスを提供できます。 タイプのすべてのクエリに対して`2`または`3`、サービスを受けた顧客の ID を出力する必要があります。 

制約`q ≤ 5 · 10^5`サービス クエリが表示されるたびにすべてのアクティブな顧客をスキャンすることは直ちに除外されます。 最悪の場合、数十万人の顧客が同時に待機する可能性があります。 アン`O(q)`操作ごとにスキャンすると、おおよその結果が得られます`O(q²)`あまりにも大きすぎる仕事。 

次の両方を返すことができるデータ構造が必要です。 

1. 最も早くサービスを受けなかった顧客。 
2. 最も優先度の高いサービスを受けていない顧客。 

各操作は対数時間以上で実行される必要があります。 

微妙な問題は、どちらのウェイターでも同じ顧客を選択できることです。 一度サービスを提供すると、その顧客は両方の選択システムから消える必要があります。 これを忘れると重複した回答が作成されます。 

考慮する：```
1 10
1 20
3
2
```お客様`2`最初にポリカルプが奉仕します。 2 番目のクエリに対する答えは顧客でなければなりません`1`、顧客ではありません`2`また。 

別の微妙なケースは、複数の顧客が同じ支出をしている場合に現れます。```
1 10
1 10
3
```答えは顧客でなければなりません`1`, 到着順で紐が切れるからです。 

## アプローチ

 ブルート フォース ソリューションでは、すべてのアクティブな顧客がリストに保存されます。 

クエリタイプの場合`2`、サービスを受けていない最初の顧客が見つかるまで前方にスキャンします。 

クエリタイプの場合`3`、すべてのアクティブな顧客をスキャンして最大の支出額を見つけ、タイブレーク ルールを適用します。 

このアプローチは問題定義に直接従うため、正しいです。 残念ながら、1 つのクエリで調査が必要になる場合があります。`O(q)`顧客。 まで`5 · 10^5`オペレーションの場合、最悪の場合の複雑さは次のようになります。`O(q²)`。 

重要な観察は、2 人のウェイターが 2 つの異なる注文を使用していることです。 

Monocarp は常に最小の到着インデックスを望みます。 

Polycarp は、到着順を二次キーとして、常に最大の支出額を求めます。 

1 つの複雑な構造を維持するのではなく、同じ顧客に対する 2 つの独立したビューを維持します。 

キューのような構造により、最も早い到着者にアクセスできます。 

優先キューを使用すると、最大の支出額にアクセスできます。 

残りの課題は同期です。 1 人のウェイターが顧客にサービスを提供しているとき、その顧客はまだ他の構造内に存在しています。 ヒープまたはキューから任意の要素を削除するにはコストがかかります。 

標準的な解決策は遅延削除です。 顧客にすでにサービスが提供されているかどうかを示すブール配列を保持します。 構造が顧客を返すたびに、すでにサービス済みとしてマークされているエントリを繰り返し破棄します。 

これにより、両方の操作が効率的な対数時間クエリに変わります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | ブルートフォース | O(q²) | O(q) | 遅すぎる |
 | 2 つの構造 + 遅延削除 | O(q log q) | O(q) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 到着するすべての顧客に一意の ID を割り当てます。 

2. 到着する各顧客を到着順に配列またはキュー構造内に格納します。 

3. また、顧客をキーがキーの最大ヒープに挿入します。`(spending, arrival order)`。 

4. ブール配列を維持する`served[id]`。 

5. クエリタイプの場合`2`、サービスを受けていない顧客に到達するまで、到着順にポインターを進めます。 その ID を出力し、サービス済みとしてマークします。 

6. クエリタイプの場合`3`、顧客にすでにサービスが提供されているヒープ エントリを繰り返し削除します。 残りの最初のエントリが有効な回答です。 その ID を出力し、サービス済みとしてマークします。 

7. すべてのクエリの処理を続行します。 

### なぜ効果があるのか

 到着ポインタは常に左から右に移動し、すでに対応済みとしてマークされている顧客を正確にスキップします。 したがって、サービスを受けていない最初の顧客が、まさに Monocarp が選択する顧客になります。 

ヒープには常に、これまでに到着したすべての顧客が含まれます。 遅延削除では、古いエントリが先頭に達した場合にのみ削除されます。 最上位のサービスを受けた顧客がすべて破棄された後、残った最上位の要素は、サービスを受けていない最大支出額の顧客です。 到着 ID はヒープ キーに含まれているため、必要に応じて、より早い到着に向けてタイが解決されます。 

すべての顧客には最大 1 回のサービスがマークされるため、どちらのウェイターも同じ顧客に 2 回サービスを提供することはできません。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    q = int(input())

    arrivals = []
    served = [False] * (q + 5)

    heap = []

    next_id = 1
    front = 0

    ans = []

    for _ in range(q):
        parts = input().split()

        if parts[0] == '1':
            m = int(parts[1])

            arrivals.append(next_id)

            heapq.heappush(heap, (-m, next_id))

            next_id += 1

        elif parts[0] == '2':
            while served[arrivals[front]]:
                front += 1

            cid = arrivals[front]
            served[cid] = True
            ans.append(str(cid))

        else:
            while heap and served[heap[0][1]]:
                heapq.heappop(heap)

            _, cid = heapq.heappop(heap)

            served[cid] = True
            ans.append(str(cid))

    print(" ".join(ans))

solve()
```の`arrivals`配列は、顧客がレストランに入った正確な順序で保存します。 変数`front`キューヘッドのように機能します。 

ヒープにはペアが格納されます`(-money, id)`。 Python は最小ヒープを提供するため、支出値を否定すると最大ヒープに変わります。 顧客 ID を 2 番目のコンポーネントとして使用すると、ID が小さいほど早い到着に対応するため、必要なタイブレーク ルールが自動的に適用されます。 

の`served`array は遅延削除の鍵となります。 顧客に 1 人のウェイターが対応するたびに、その顧客にマークを付けます。 もう一方のデータ構造は最終的に古いレコードに遭遇し、それを破棄します。 

どちらの構造でも顧客が途中から外されることがないため、すべての業務が効率的に維持されます。
