 ## 解決策
 ## 問題の理解

 固定された順序で一連の単語が与えられており、そのブロックを長方形のバナーに印刷できるように、ある位置から開始して後で終了する連続したブロックを選択したいと考えています。 バナーの行数は固定で、各行の文字数も固定です。 単語は順番に表示する必要があり、複数の行に分割することはできず、同じ行に配置する場合は少なくとも 1 つのスペースで区切る必要があります。 ただし、余分なスペースは許可されるため、実際の制約は一連の単語が物理的に行幅内に収まるかどうかだけです。 

タスクは、これらの制約の下で最大 r 行内に配置できる、可能な限り長く連続する単語のセグメントを見つけ、そのようなセグメントの有効なレイアウトを出力することです。 

制約は大きく、最大 10^6 ワード、バナー全体の合計文字数は最大 10^6 です。 これにより、すべての候補セグメントに対してライン レイアウトを最初から再計算しようとするソリューションは即座に排除されます。 単一セグメントのチェックには既に単語数で線形時間がかかるため、単語間隔にわたる二次走査は遅すぎます。 

2 番目の微妙な困難は、実現可能性は全体の長さだけではなく、単語が行にどのように詰め込まれるかによって決まるという事実から生じます。 貪欲な左から右へのパッキングは固定セグメントに最適ですが、セグメントは重なり合うことが多いため、これを繰り返し再計算するのは冗長な作業になります。 

単純な間違いは、総文字数が r·c を超えるまで単語を単純に蓄積できると考えることです。 This fails because line breaks matter.

 たとえば、r = 2、c = 10、単語が次のようになると仮定します。```
["aaaaa", "aaaaa", "aaaaa"]
```合計の長さは 15 で、20 未満ですが、3 つの単語すべてを収めることはできません。最初の行には 2 つの単語を含めることができます (5 + 1 + 5 = 11 > 10)。したがって、実際には 1 行に 1 つの単語のみが収まり、2 行に 2 つの単語のみが収まることになります。 これは、合計の長さだけではなく、行のパッキングをシミュレートする必要があることを示しています。 

もう 1 つの障害モードは、ライン遷移を追跡しない貪欲なセグメント拡張です。 注意深いメンテナンスを行わないと、必要な行数を過剰にカウントしてしまう可能性があります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 すべての開始インデックス i を試し、単語 i から j までを配置するのに必要な行数を維持しながら、j を前方に拡張します。 拡張子ごとに、単語を貪欲に行に配置し、現在の単語が収まらない場合は常に新しい行を開始することをシミュレートします。 

これは正しいです。セグメントごとの貪欲な配置が最適であるためです。固定セグメント内では、常に単語を左から右に詰め込み、必要な場合にのみ改行します。 

ただし、このアプローチは遅すぎます。 各 i について最大 n 個の位置をスキャンし、拡張ごとに配置のシミュレーションに O(n) 時間を費やす可能性があります。 これにより、O(n^2) またはさらに悪い動作が発生しますが、n が 10^6 までではこれは不可能です。 

重要な観察は、実現可能性が単調に動作するということです。セグメント i..j が適合する場合、i..j+1 は失敗する可能性があり、一度失敗すると、その固定開始では再度有効になることはありません。 これは、2 つの指針によるアプローチを示唆しています。 前方にのみ移動する右ポインタを維持し、現在ウィンドウで使用されている行数を追跡します。 ウィンドウを拡張するときは、最初から再計算するのではなく、回線使用量を段階的に更新します。 

各単語は 1 回追加され、1 回削除されるため、プロセスは直線的になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 遅すぎる |
 | 2 つのポインター + 貪欲なパッキング | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは単語に対してスライディング ウィンドウを維持します。 各開始位置の候補について、r ラインの制約を尊重しながら、終端を可能な限り延長しようとします。 

1. 2 つのポインタ i = 0 と j = 0 を初期化し、現在の行数と最終行の残り容量を追跡します。 

空のレイアウトから始めるので、まだ線は使用されていません。 
2. 単語 j を現在の行に配置してみます。 適合する場合は、その長さと必要に応じてスペースを差し引きます。 
3. 収まらない場合は、新しい行を開始し、そこに単語を配置します。 

これは、単語が収まらなくなると、以前の配置では行数を増やさずに単語を入れることができないという貪欲な性質を反映しています。 
4. 行数が r を超える場合、この i の拡張は停止されます。 次に、i を前方に移動して、それに応じてウィンドウを調整します。 
5. 最大長の点でこれまでに確認された最良の (i, j) ペアを維持します。 
6. 最適なセグメントを見つけた後、同じグリーディ パッキング ルールを使用してそのレイアウトを再度再構築します。 

重要な詳細は、現在のウィンドウの「状態」は段階的に更新できるということですが、先に進むときはその寄与を慎重に削除する必要があります。 これは、実装の選択に応じて、再計算するか、新しい i から効率的に再起動することによって処理されます。 

### なぜ効果があるのか

 正しいかどうかは、固定セグメントの場合、行に貪欲にパッキングすることで使用される行数が最小限に抑えられるという事実に基づいています。 したがって、欲張りパッキングでセグメントが r 行以内に収まらない場合、他の配置によってセグメントを適合させることはできません。 これにより、実現可能性テストが正確になります。 j の単調拡張と i の制御された動きと組み合わせると、すべての単語が一定回数処理され、有効なセグメントがスキップされないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can_extend(words, r, c, start):
    n = len(words)
    lines = 1
    cur_len = 0
    best_end = start

    j = start
    while j < n:
        w = words[j]
        wlen = len(w)

        if wlen > c:
            return start, start - 1

        if cur_len == 0:
            cur_len = wlen
        elif cur_len + 1 + wlen <= c:
            cur_len += 1 + wlen
        else:
            lines += 1
            if lines > r:
                return start, j - 1
            cur_len = wlen

        best_end = j
        j += 1

    return start, best_end

def build_layout(words, l, r, c):
    res = []
    line = []
    cur_len = 0

    for i in range(l, r + 1):
        w = words[i]
        if cur_len == 0:
            line = [w]
            cur_len = len(w)
        elif cur_len + 1 + len(w) <= c:
            line.append(w)
            cur_len += 1 + len(w)
        else:
            res.append(" ".join(line))
            line = [w]
            cur_len = len(w)

    if line:
        res.append(" ".join(line))

    return res

def main():
    n, r, c = map(int, input().split())
    words = input().split()

    best_len = 0
    best_l = 0
    best_r = -1

    i = 0
    j = 0

    lines = 1
    cur_len = 0

    for i in range(n):
        if j < i:
            j = i
            lines = 1
            cur_len = 0

        while j < n:
            wlen = len(words[j])
            if wlen > c:
                break

            if cur_len == 0:
                new_len = wlen
            elif cur_len + 1 + wlen <= c:
                new_len = cur_len + 1 + wlen
            else:
                lines += 1
                if lines > r:
                    break
                new_len = wlen

            cur_len = new_len
            j += 1

        if j - 1 - i + 1 > best_len:
            best_len = j - i
            best_l = i
            best_r = j - 1

    ans = build_layout(words, best_l, best_r, c)
    print("\n".join(ans))

if __name__ == "__main__":
    main()
```メイン ループは、すべての i にわたって前方にのみ移動する右ポインタ j を維持します。 これが二次関数の動作を妨げる原因で​​す。 それ以上の拡張に失敗した場合は、最初から再計算しません。 代わりに、ウィンドウの構造により、償却された直線的な進行が保証されます。 

最初にセグメントを最大化し、その後フォーマットすることのみを考慮するため、再構成ステップは別個になります。 この分離により、行カウントに微妙なバグが発生することが多い、最適化ロジックと出力フォーマットの混合が回避されます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、単一の単語が正確に 1 行を埋める場合です。 アルゴリズムは、誤って改行を早期に強制してはなりません。 次のような入力の場合:```
3 2 5
aaa aa aaa
```1 行目は容量 5 を正確に満たす「aaa aa」となり、2 行目は「aaa」を保持します。 貪欲ルールでは、条件が等価性を正しくチェックするため、途中で改行が発生しないことが保証されます。 

もう 1 つのエッジ ケースは、単語が c を超える場合です。 その場合、それを含むセグメントは無効となります。 アルゴリズムは、そのような単語が拡張子を直ちに中断することを保証する必要があります。これは、配置前に単語の長さをチェックすることによって処理されます。
