 ## 解決策
 ## 問題の理解

 開き括弧と閉じ括弧のみで構成される文字列が与えられます。 唯一許可される操作は、ある位置から閉じ括弧を取り出し、その左の任意の場所に再挿入することです。 開き括弧は所定の位置に固定されます。 

目的は、このような動きを何度でも繰り返した後、シーケンスを整形式の括弧シーケンスに変換できるかどうかを判断することです。つまり、`+`そして`1`文字の間。 

許可された操作の重要な結果は、右に移動しない限り、閉じ括弧は完全に並べ替え可能であるということです。 つまり、すべて`')'`文字は任意に並べ替えることができますが、元の位置に対して左に移動する方法に限ります。 左括弧は移動できません。 

入力サイズは最大 200,000 文字です。 部分文字列や繰り返しシミュレーションに対する二次関数または二次関数に近いアプローチは遅すぎます。 リニア スキャン、または一定のエクストラ ステートを伴うリニア スキャンが必要です。 

文字列が多くの閉じ括弧で始まる場合、微妙なエッジ ケースが発生します。 例えば、`"))(("`これは修正できません。どの操作も閉じ括弧を開き括弧を超えて右に移動できず、プレフィックスの有効性が最初から根本的に壊れているためです。 もう 1 つのエッジ ケースは、数がグローバルに一致しているにもかかわらず、閉じ括弧の数がプレフィックス順に開き括弧と一致するには十分に「分散可能」ではない場合です。 

## アプローチ

 ブルートフォース解釈では、閉じ括弧を移動する可能なすべての方法をシミュレートします。 各操作で選択されるのは、`')'`それを先に挿入するので、理論的には、右に移動できないという制約の下で、閉じ括弧のすべての順列を生成しようとすることができます。 これにより、閉じ括弧の数が指数関数的な状態空間が得られます。 貪欲なローカル修正を試みても、スキャンと更新を繰り返す必要があり、最悪の場合、二次的な動作が発生します。 

重要な点は、この操作により、右に交差できないことを除いて、閉じ括弧の位置制限がすべて取り除かれることです。 これは事実上、すべてを再配置できることを意味します`')'`文字が占める位置の複数セットが、元の位置の右側ではない場所に留まる限り、文字は自由に相互に結合できます。 正しい括弧シーケンスを形成できるかどうかのみが問われるため、唯一の本当の問題は、プレフィックスのバランスを満たすのに十分な数の閉じ括弧を十分な早さで割り当てることができるかどうかです。 

正しい括弧シーケンス条件は、古典的なプレフィックス ルールに帰着します。つまり、すべてのプレフィックスには少なくとも同じ数が必要です。`'('`として`')'`、合計数が一致する必要があります。 

閉じ括弧を効果的に左に「シフト」できるため、唯一の障害は、早期に提供できる開始部分と比較して、閉じ括弧が多すぎるプレフィックスによって発生します。 この構造は、移動できないことを前提として、シーケンスを有効な Dyck 単語に再配置できるかどうかをチェックするために崩壊します。`'('`。 

これにより、貪欲なチェックが行われます。つまり、文字列の読み取りをシミュレートし、利用可能な開始部分を追跡し、残りのサフィックスの合計から提供できる以上の終了部分が必要ないことを確認します。

 ## アルゴリズムのチュートリアル

 この問題を、右括弧の制約された動きの下でのプレフィックスバランスの実現可能性チェックに変換します。 

1. 合計数を数える`'('`そして`')'`。 等しくない場合は「No」を返します。 正しい括弧シーケンスには等しい数が必要であり、操作によってカウントが変更されることはありません。 
2. これまでに確認した左括弧の数を維持しながら、文字列を左から右に繰り返します。 これは、一致しないものの数を表します`'('`将来の閉じ括弧をサポートするために利用できる可能性があります。 
3. すでに有効な位置に「固定」された閉じ括弧の数のカウンターを維持します。 実際の動きを考えるのではなく、すべての接頭辞で、必要な閉じ括弧の数が供給可能な数を超えないようにするものとして扱います。 
4. 各ポジションで、将来の有効性を維持するために保存しなければならない一致しないオープンの最小数を計算します。 いずれかの時点で、プレフィックスにさらに多くの要求が必要な状況に追い込まれる可能性がある場合`')'`入手可能なものよりも`'('`、不可能であると結論付けます。 
5. 閉じ括弧は左にシフトできるため、サフィックスの位置全体に補うのに十分な空きがない場合、プレフィックスの欠落を修復することはできません。 貪欲なスキャンにより、オープンが早すぎてオーバーコミットすることがなくなります。 

### なぜ効果があるのか

 不変条件は、プレフィックスを処理した後、利用可能なプレフィックスの数が`'('`これは、実際に確認されたオープン数から、これまで論理的に一致したクローズ数を引いたものです。 私たちは動くことしかできないから`')'`左に示すように、有効な構造は、その時点までの文字列全体に存在する開始よりも多くの終了を要求するプレフィックスがないことを考慮する必要があります。 プレフィックスがこれに違反している場合、新しいものを導入できないため、再配置しても修正できません。`'('`早くするか、右に移動します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)
    
    open_cnt = s.count('(')
    close_cnt = n - open_cnt
    
    if open_cnt != close_cnt:
        print("No")
        return
    
    balance = 0
    for ch in s:
        if ch == '(':
            balance += 1
        else:
            balance -= 1
        if balance < 0:
            print("No")
            return
    
    print("Yes")

if __name__ == "__main__":
    solve()
```有効な括弧シーケンスには同じ数の開き括弧と閉じ括弧が必要であるため、このソリューションではまずカウントによって全体的な実現可能性をチェックします。 次に、標準のプレフィックス バランス スキャンを実行します。 重要な考え方は、許可された操作にもかかわらず、どの操作もより早い開始値を作成したり、開始値を右に移動したりできないため、終了値が開始値を超えるプレフィックスを修正できないということです。 プレフィックス シミュレーションは、この障害物を正確にキャプチャします。 

微妙な点は、許可される再挿入を明示的にシミュレートしていないことです。 この操作は閉じ括弧の相対的な順序にのみ影響しますが、開始によって課される基本的な接頭辞の制約は変更しないため、従来の妥当性チェックで十分です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    def solve():
        s = sys.stdin.readline().strip()
        n = len(s)
        
        if s.count('(') != n - s.count('('):
            return "No"
        
        bal = 0
        for c in s:
            if c == '(':
                bal += 1
            else:
                bal -= 1
            if bal < 0:
                return "No"
        return "Yes"
    
    return solve()

# provided sample
assert run("((()))\n") == "Yes"

# minimum size
assert run("()\n") == "Yes"

# impossible due to prefix
assert run("())\n") == "No"

# all closing
assert run("))))((\n") == "No"

# already balanced but tricky order
assert run("()()()\n") == "Yes"

 ## 特殊なケース

 重大なエッジ ケースは、文字列がグローバルにバランスが取れているにもかかわらず、初期のプレフィックス違反がある場合です。`")(()"`。 アルゴリズムは次のように処理します。最初の文字では、バランスは次のようになります。`-1`、即時拒否を引き起こします。 これは、許可された操作では開始ブラケットを位置 1 より前に移動できないため、プレフィックスを修復できないという事実と一致します。 

もう一つのケースは、`"()())("`、合計カウントは等しいですが、プレフィックスは 5 文字目で区切られます。 スキャンがバランスに達しました`-1`その時点でアルゴリズムは拒否します。 たとえ後で余分な開口部があったとしても、それをプレフィックス境界での不足を修正するのに十分なほど左に移動することはできません。 

最後のエッジケースは、次のようなすでに正しいシーケンスです。`"((()))"`。 残高はゼロを下回ることはなく、アルゴリズムは並べ替え操作を考慮する必要なく受け入れます。これは、操作が再配置が必要な場合にのみ関連するが、実行可能なプレフィックス有効文字列のクラスを拡張しないことを反映しています。
