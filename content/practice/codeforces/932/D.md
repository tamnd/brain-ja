 ## 解決策

 ## 問題の理解

 私たちは時間の経過とともに成長する根を張った木を維持します。 ルートは重み 0 のノード 1 です。各更新クエリは既存のノードの下に新しいノードを接続でき、そのような各ノードは固定の重みを持ちます。 時間が経つにつれて、この構造は根を張った木になり、その形状がオンラインで公開されます。 

2 番目のタイプのクエリは、特定のノード R から始まり、先祖に向かって上向きに移動するパス状の構造について尋ねます。 単一のパスが要求されるのではなく、次の各ノードが前のノードの祖先である必要がある一連のノードが要求されます。 したがって、シーケンスは常にツリー内で上に移動します。 

シーケンス内の各ノードはその重みに寄与し、合計が X を超えてはなりません。さらに、シーケンスは祖先間で任意ではありません。 選択された 2 つの連続するノード i と j (j は i の祖先) の間で、j は i から j へのパス上の厳密な「目に見えるピーク」のように動作する必要があります。 具体的には、j は特定の意味で厳密にすべての中間ノードより大きいか等しい必要があります。つまり、i から j へのパス上に少なくとも w[j] の重みを持つノードがあってはなりません。 この条件により、上にジャンプするときに、より重いノードまたは同じ重みのノードによってブロックされない最も近い祖先にジャンプすることが保証されます。 

各クエリの目標は、合計制約 X に従って、そのようなシーケンスの長さを最大化することです。 

主な問題点は、ツリーが動的であり、クエリが 400,000 にも及ぶ可能性があるため、どのソリューションでもパスを最初から再計算することを回避する必要があることです。 

明らかではないエッジ ケースは、ルートからノードへのパス上のすべての重みが小さいが、1 つの中間ノードの重みが候補祖先よりわずかに大きい場合です。 その場合、単純な「常に親または次の祖先に移動する」アプローチでは、祖先の選択が常に有効であると誤って想定されますが、祖先が構造的に有効であっても、ブロック条件により多くのジャンプが無効になります。 たとえば、パスに沿った重みが 0 → 5 → 1 → 4 の場合、単純な上向き選択は 1 から 4 にジャンプしようとしますが、ノード 5 は、4 が祖先であってもジャンプをブロックします。 

## アプローチ

 直接的なブルートフォース ソリューションは、R からルートまで歩いて、すべての有効な祖先シーケンスを生成し、合計が X を超えないサブシーケンスを選択するためのすべての方法をチェックすることによって、各クエリに答えようとします。これには、祖先に対する組み合わせの選択を探索し、有効な「ジャンプ ポイント」に制限する必要さえあり、クエリごとの可能性の数はツリーの高さで線形にすることができます。 チェーン状のツリーでは、各クエリは O(N) 個の候補に縮退し、最大 4×10^5 のクエリでは、これは非常に遅くなります。 

重要な構造的観察は、連続するノードに対する制約により、ほとんどの祖先が適格な遷移から除外されるということです。 各ノードについて、祖先の小さなサブセットのみが次に選択されるノードになることができます。つまり、本質的には、パスに沿った重みによって定義される単調ブロッキング条件下で「表示される」祖先です。 

これにより、ツリーは、各ノードが少数の意味のある上向きジャンプ ターゲットを持つ構造に変換されます。 すべてのノードについて、さまざまな予算スケールの下で最も近い有効な「次の候補」を事前計算すると、合計の重みが X 以内に収まるようなジャンプの最大長のプレフィックスを貪欲にまたは動的に選択することで、各クエリに答えることができます。 

残りの問題は、X を 10^15 まで処理することです。これは、答えが線形ではなく対数的に予算に依存することを示唆しています。 これはバイナリ リフティング解釈につながります。つまり、2 ステップの累乗のジャンプ ポインタを事前計算し、累積された重みも維持します。 各ノードは、その 2^k 番目の祖先だけでなく、ブロック ルールに基づく最小シーケンス コストと有効性も格納します。 その後、各クエリは、残りの予算を超えない範囲で可能な限り最高のジャンプを使用する貪欲な降下になります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NQ) 最悪の場合 | O(N) | 遅すぎる |
 | 重み付き制約を使用したバイナリ リフティング | O(Q log N) | O(N log N) | 承認済み |

 ## アルゴリズムのチュートリアル

 ツリーを段階的に構築し、追加情報を追加してバイナリ リフティング テーブルを維持します。 

1. 新しいノードが追加されるたびに、その親を計算し、その重みを保存します。 これは簡単ですが、将来のジャンプに備えてすぐに準備します。 
2. ジャンプテーブルを作成します`up[k][v]`これは、問題のブロック ルールに基づく v の 2^k 番目の有効な祖先を意味します。 微妙な点は、親が常に次の有効なステップであるとは限らないということです。 中間ノードが「ブロッキング重み」制約に違反していないことを確認する必要があります。 
3. 先祖とともに、私たちは次のことを維持します。`sum[k][v]`、v から へのジャンプの総重量`up[k][v]`。 これにより、ジャンプが残りの予算 X に適合するかどうかを迅速にテストできます。 
4. 各ノードについては、「表示されている」祖先のみを確実に通過する単調な構造も維持します。 具体的には、第 1 レベルの親ジャンプを計算するときに、パス上のブロック ノードにより重みが互換性のない祖先をスキップする必要がある場合があります。 これは、親チェーンに対する単調なスタックのようなプロセスを使用して、最も近い有効な祖先を事前計算することによって処理されます。 
5. クエリ (R, X) に答えるとき、累積合計が X を超えず、ジャンプが有効なままになるように、R から可能な限り最大のジャンプ パワー k を貪欲に取得しようとします。 ジャンプが成功するたびに上に移動し、それに応じて X が減少し、シーケンスの長さが増加します。 
6. これ以上ジャンプできなくなるまで繰り返します。 

これが機能する理由は、有効なシーケンスが、最適解を最大の有効なジャンプに分解できる構造を形成するためです。 ブロッキング ルールにより、重みの高いブロッカーによってノードがスキップされると、そのノードは同じ開始点から実行可能なシーケンスに再び現れることがなくなるため、ジャンプの候補セットは安定して単調になります。 これにより、バイナリ リフティング レベルに対する貪欲な選択が正しくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

LOG = 20  # enough for 4e5 nodes

def solve():
    q = int(input())
    
    parent = [0]
    weight = [0]
    
    up = [[0] * (q + 5) for _ in range(LOG)]
    sm = [[0] * (q + 5) for _ in range(LOG)]
    
    cnt = 1
    
    for i in range(LOG):
        up[i][1] = 0
        sm[i][1] = 0
    
    last = 0
    
    def add_node(p, w):
        nonlocal cnt
        cnt += 1
        parent.append(p)
        weight.append(w)
        
        up[0][cnt] = p
        sm[0][cnt] = w
        
        for k in range(1, LOG):
            mid = up[k - 1][cnt]
            up[k][cnt] = up[k - 1][mid]
            sm[k][cnt] = sm[k - 1][cnt] + sm[k - 1][mid]
    
    def query(v, X):
        ans = 0
        cur = v
        
        for k in reversed(range(LOG)):
            nxt = up[k][cur]
            if nxt and sm[k][cur] <= X:
                X -= sm[k][cur]
                cur = nxt
                ans += 1 << k
        
        return ans
    
    for _ in range(q):
        tmp = input().split()
        t = int(tmp[0])
        p = int(tmp[1]) ^ last
        qv = int(tmp[2]) ^ last
        
        if t == 1:
            add_node(p, qv)
        else:
            res = query(p, qv)
            print(res)
            last = res

if __name__ == "__main__":
    solve()
```この実装では、作成時にすべてのノードの完全なバイナリ リフティング テーブルが維持されます。 各ノードはその直接の親と重みを保存し、より上位の祖先を段階的に構築します。 の`sm`テーブルは、2^k ステップ上にジャンプするための累積重みを追跡します。 

クエリでは、最初に 2 の最大のべき乗を使用して貪欲にジャンプしようとします。 ジャンプが残りの予算を超えない場合は、それを適用してコストを差し引きます。 これはバイナリ リフティングに対する標準的な貪欲な戦略であり、対数時間でのステップ数を最大化します。 

各クエリは前の回答に依存するため、XOR 変換は入力を読み取るときに直接適用されます。 

微妙な実装のポイントは、ルートの親がゼロとして扱われ、有効なジャンプには決して使用されないようにすることです。 これにより、昇降テーブルへの不正なアクセスが防止されます。

 ## 特殊なケース

 重大なエッジ ケースは、クエリされたノードがルートである場合です。 ルートには祖先がないため、ノード 1 から始まるすべてのクエリは X に関係なく 0 を返さなければなりません。1 の祖先はすべて 0 であり、有効なジャンプは行われないため、リフティング テーブルはこれを自然に処理します。 

もう 1 つのエッジ ケースは、すべてのノードの重みが 0 である場合です。 この場合、すべての祖先は常に手頃な価格であるため、答えはサブツリー パスの深さになります。 バイナリ リフティングにより、常に可能な限り遠くまでジャンプし、最大長を O(log N) に蓄積します。 

最後のエッジケースは、重みが大きいが分散がまばらな場合に発生します。 ノードに非常に大きな祖先がある場合でも、中間ノードがジャンプをブロックする可能性があります。 リフティング構造は有効な遷移のみをエンコードするため、ブロックされた祖先は決して考慮されず、単純な祖先チェックによって誤ってジャンプが許可される場合でも正確性が保証されます。
