 ## 解決策
 ## 問題の理解

 私たちにはいくつかのビットコインウォレットが与えられ、それぞれにある程度のサトシが入っています。 目標は、これらのコインをおそらくより多くのウォレットに再分配し、最終的に固定制限を超えて保持できるウォレットが存在しないようにすることです。$x$。 新しいウォレットの作成は無料ですが、あるウォレットから別のウォレットへのコインの転送には固定手数料がかかります$f$、ソースウォレットから支払われます。 

1 回の送金は単なる帳簿上の移動ではなく、実際に 1 つのウォレットから新規または既存のウォレットにプラスの量のコインを移動します。移動されるコインの数に関係なく、そのようなすべてのアクションには同じ手数料が発生します。 タスクは、すべての操作後にすべてのウォレットに最大で$x$サトシたち。 

入力は、ウォレット残高の初期マルチセットと、ウォレットごとの最大許容残高と転送ごとのコストという 2 つのパラメータを記述します。 出力は、制約を達成するための最小総コストです。 

重要な問題は、分割が 1 つのステップで強制されないことです。 大きすぎるウォレットは、複数のトランザクションを使用して複数の小さなウォレットに分割することができ、トランザクションごとにソース残高が減り、新しい宛先ウォレットが作成されます。 

この制約により、ブルート シミュレーションは不可能になります。 最大 200,000 個のウォレットと最大値$10^9$、転送を繰り返しシミュレートしたり、個々のコインを追跡したりするアプローチは、遅すぎます。 ソリューションでは、各ウォレットを個別に決定的な操作数まで削減する必要があります。 

いくつかの特殊なケースでは、単純な推論の失敗が明らかになります。 

最初の失敗ケースは、各ウォレットが必要であると仮定した場合です。$\lceil a_i / x \rceil - 1$残りの集計ロジックを誤って考慮せずに操作を行う。 たとえば、次の場合$a_i = x$、操作は必要ありませんが、不注意な数式では依然として 1 つの分割がカウントされることがよくあります。 

2 番目の失敗例は、異なるソース間で貪欲に「新しいウォレットを埋める」ことを試みており、ウォレット間の誤った結合につながります。 各取引コストは独立しているため、ウォレット間で分割を調整するメリットはありません。 

## アプローチ

 ブルートフォース解釈では、ウォレットを 1 つずつシミュレートします。 残高のあるウォレットごとに$a_i > x$、新しいウォレットの作成と次のステップへの移行を繰り返します。$x$ソースウォレットが有効になるまで、そこにコインを投入します。 そうした移動ごとに費用がかかります$f$。 このプロセスは、すべてのウォレットが制約を満たすまで継続されます。 

これは正しいですが、高価です。 最悪の場合、そのサイズの財布が1つだけ$10^9$およそ必要になるかもしれない$10^9 / x$転送、および横断$200{,}000$ウォレットではこれは完全に不可能になります。 

重要な点は、各ウォレットが独立しているということです。 サイズの財布$a_i$他のウォレットに関係なく、一定数の必要な「追加ウォレット」を提供します。 すべての財布に最大で収納できるのは、$x$、したがって、保管するために必要なウォレットの最小数は$a_i$は：$$\left\lceil \frac{a_i}{x} \right\rceil$$ウォレットがすでに存在する場合は、1 つのスロットが提供されます。 転送ごとに新しいウォレットが 1 つだけ作成されるため、追加のスロットはすべて 1 つの転送操作に対応します。 

したがって、ウォレットに必要な操作の数は$i$は：$$\left\lceil \frac{a_i}{x} \right\rceil - 1$$これをすべてのウォレットで合計すると、合計転送数が得られ、次の値を掛けます。$f$答えを出します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション |$O(\sum a_i / x)$|$O(N)$| 遅すぎる |
 | 数学的な数え方 |$O(N)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各ウォレットの値について$a_i$、全容量のウォレットがいくつ必要か計算します。 これは、次のように整数演算を使用して行われます。$(a_i + x - 1) // x$。 この式は、浮動小数点演算を行わずに上限除算を実行します。 
2. この数から 1 を引いて、追加のウォレットを作成する必要がある数を決定します。 この減算は、元のウォレットがすでに存在しており、作成する必要がないことを反映しています。 
3. この値を操作の累計に加算します。 この合計の各単位は、正確に 1 回の転送に対応します。 
4. すべてのウォレットを処理した後、合計操作数に固定料金を掛けます$f$最終コストを取得します。 

ステップ 2 の背後にある理由は、ウォレットが容量を超えた場合にのみ分割が必要になるということです。 正確に適合するウォレットはすでに制約を満たしているため、操作は必要ありません。 

### なぜ効果があるのか

 転送では異なるソース間の制約がマージされないため、各ウォレットは独立しています。 サイズの財布$a_i$最大でも次のサイズのグループに分割する必要があります$x$、グループの数は容量だけで決まります。 転送ごとに新しいウォレットが 1 つだけ作成されるため、追加のグループと操作の間には 1 対 1 の対応関係があります。 これにより、合計コストはウォレット全体で純粋に加算されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    x, f = map(int, input().split())

    ops = 0
    for v in a:
        ops += (v + x - 1) // x - 1

    print(ops * f)

if __name__ == "__main__":
    solve()
```コードは、派生した式を直接実装します。 表現`(v + x - 1) // x`指定された残高に対して必要なウォレットの数を計算します。 1 を減算すると、元のウォレットがカウントから削除され、必要な転送数だけが残ります。 

アキュムレータ`ops`転送の合計数を追跡します。 乗算`f`オペレーションをサトシコストに変換します。

 ## 特殊なケース

 ウォレットがすでに制限を正確に満たしている場合、微妙なエッジケースが発生します。 入力用`a = [6]`と`x = 6`、計算により次のことが得られます。`(6 + 5) // 6 - 1 = 1 - 1 = 0`, したがって、操作はカウントされません。 これにより、常に少なくとも 1 つのグループを数えるというよくある間違いを回避できます。 

もう 1 つのエッジ ケースは、値が の倍数をわずかに上回る場合です。$x$。 のために`a = [7]`そして`x = 6`、式は次のようになります`(7 + 5) // 6 - 1 = 2 - 1 = 1`、単一の必要な分割を 6 と 1 に一致させます。 

すべての操作はウォレットごとに一定時間で計算されるため、大きな入力によって動作が変化することはなく、シミュレーションの爆発を防ぎます。
