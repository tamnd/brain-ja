 ## 解決策
 ## 問題の理解

 ゲームレベルの統計を数回観察します。 各観察で、レベルが何回プレイされたか、何回クリアされたかという 2 つの値がわかります。 

試行が成功すると、両方の数値が同時に 1 ずつ増加します。 失敗した場合は再生回数のみが増加します。 2 つの観察の間に、プレイヤーがゼロの場合も含め、任意の数のプレイヤーがレベルを試行した可能性があります。 

すべてのテスト ケースについて、記録されたシーケンスが実際に発生する可能性があるかどうかを判断する必要があります。 成功した試行と失敗した試行のシーケンスによって、時系列順にそれらの観察結果が正確に得られた場合、次のように出力します。`"YES"`。 それ以外の場合は印刷します`"NO"`。 

制約はわずかです。 テスト ケースは最大 500 個あり、各テスト ケースには最大 100 個の観測値が含まれます。 すべての観測値のペアを比較するアルゴリズムであっても、快適に実行できます。 高度なデータ構造や最適化は必要ありません。 観測結果をリニアスキャンするだけで十分です。 

微妙な部分は、プレイとクリアの関係を理解することです。 無害に見えるいくつかの状況は、実際には不可能です。 

プレイ数が一定でクリア数が増えたとします。 

入力：```
1
3
0 0
1 1
1 2
```正しい答えは次のとおりです。```
NO
```新しいクリアは常に新しいプレイから得られるため、クリアの増加がプレイの増加を超えることはありません。 両方のシーケンスが非減少であるかどうかだけをチェックする不注意な解決策は、このケースを誤って受け入れることになります。 

もう 1 つの注意が必要な状況は、合計クリア数が合計プレイ数を超える場合です。 

入力：```
1
1
3 5
```答えは次のとおりです。```
NO
```5 回の試行が成功するには、少なくとも 5 回のプレイが必要です。 

もう 1 つの落とし穴は、値を減らすことです。 

入力：```
1
3
10 2
15 3
14 3
```答えは次のとおりです。```
NO
```統計は時間の経過とともに増加するだけです。 少しでも減少すると、すぐに記録が不可能になります。 

## アプローチ

 強引な解釈では、観測間の個々の試みをすべて再構築しようとします。 プレイ数が 1000 回増加した場合、その 1000 回の試行が成功した実行と失敗した実行に分割されるあらゆる方法を想像することができます。 このような方法は、プロセスを明示的にシミュレートするため正しいですが、可能な履歴の数は試行回数に応じて指数関数的に増加します。 1,000 回の新しいプレイを含む 1 つのインターバルでも、すでに膨大な数の可能性が秘められています。 

重要な点は、成功と失敗の正確な順序を知る必要がないということです。 重要なのは3つの条件だけです。 

まず、再生数を減らすことはできません。 

次に、クリア数を減らすことができません。 

第三に、ある観察から次の観察に移るときは常に、新しいクリアの数が新しいプレイの数を超えることはできません。 成功するたびに 1 プレイと 1 クリアが与えられるため、さらに 5 つのクリアを獲得するには、少なくとも 5 つの追加プレイが必要です。 

同じ考え方が最初の観察にも当てはまります。 いかなる時点においても、合計クリア数が合計プレイ数を超えることはできません。 

連続するペアごとにこれらの条件がチェックされると、答えが決まります。 無効なペアが 1 つあると、レコード全体が不可能になります。

 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | 指数 | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 現在のテスト ケースのすべての観察結果を読み取ります。 
2. 最初の観察結果を確認します。 クリア数がプレイ数を上回った場合、答えは`"NO"`なぜなら、すべてのクリアはプレイから生まれなければならないからです。 
3. 観察結果を左から右にたどります。 
4. 連続した観察のペアごとに、プレーとクリアの変化を計算します。 
5. 再生数が減少すると、統計は決して遡ることができないため、記録は不可能になります。 
6. クリア数が減った場合も同様の理由で記録できなくなります。 
7. クリア数の増加がプレイ数の増加よりも大きい場合、記録は不可能です。 合計試行回数を超える成功試行は発生できません。 
8. これらのチェックがいずれも失敗しない場合は、次のように出力します。`"YES"`。 

### なぜ効果があるのか

 連続する観測のペアを処理した後、アルゴリズムは、これまでに観測されたすべての観測を生成する試行のシーケンスが少なくとも 1 つ存在するという不変条件を維持します。 

ある観察から次の観察に移るときに重要な情報は、新しいプレイと新しいクリアが何回出現したかだけです。 両方の量が負でなく、新しいクリアの数が新しいプレイの数を超えない限り、それらの新しいクリアは成功した試行として解釈でき、残りの新しいプレイは失敗した試行として解釈できます。 したがって、有効な拡張機能は常に存在します。 これらの条件のいずれかに違反した場合、一連の試行によってその遷移を説明することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())

for _ in range(t):
    n = int(input())
    records = [tuple(map(int, input().split())) for _ in range(n)]

    ok = True

    if records[0][1] > records[0][0]:
        ok = False

    for i in range(1, n):
        prev_p, prev_c = records[i - 1]
        cur_p, cur_c = records[i]

        dp = cur_p - prev_p
        dc = cur_c - prev_c

        if dp < 0 or dc < 0 or dc > dp:
            ok = False

    print("YES" if ok else "NO")
```解決策は、1 つのテスト ケースのすべての観測値を読み取ることから始まります。 それらをリストに保持すると、ペアごとの比較が簡単になります。 

最初の観察は特別な扱いに値します。 すでにレベルのクリア数がプレイ数よりも多い場合、移行を考慮する前に記録することは不可能です。 

連続するペアごとに、プレイとクリアの増加を計算します。 マイナスの差は、何らかの統計が減少したことを意味しますが、そのようなことは起こり得ません。 条件`dc > dp`は、新しく完了した実行の数が新しく開始された実行の数を超える、より微妙なケースを捉えています。 

違反があれば答えが得られるため、チェックの順序は重要ではありません。`"NO"`。 エラーを見つけたらすぐに停止する必要はありませんが、そうすることもできます。 

すべての値は最大 1000 であるため、Python では整数のオーバーフローは問題になりません。

    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        records = [tuple(map(int, input().split())) for _ in range(n)]

        ok = True

        if records[0][1] > records[0][0]:

            dc = cur_c - prev_c

            if dp < 0 or dc < 0 or dc > dp:
                ok = False

        out.append("YES" if ok else "NO")

    return "\n".join(out)
