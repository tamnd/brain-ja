 ## 解決策
 ## 問題の理解

 私たちには、アパートをシェアする人々のグループと、限られた数の物理的な鍵が与えられます。 時間が経つにつれて、各人はアパートを出ては戻ってくることを繰り返します。 このような外出はすべて独立しており、出発時刻と戻り時刻という単一の間隔で記述されます。 2 つのイベントがまったく同時に発生することはありません。そのため、すべてのイベントを出発と復帰のきれいなタイムラインとして考えることができます。 

重要な制約は、誰かが戻ってきたときに何が起こるかということです。 少なくとも 1 人が既にアパート内にいる場合、戻ってきた人はベルを鳴らすだけで鍵なしで入ることができます。 その時点で誰も中にいない場合、戻ってきた人はドアのロックを解除するための鍵を持っていなければなりません。 出発者が鍵を携帯するかどうかは、旅行ごとに私たちが決定することができます。 常に鍵を保持できるのは最大で k 人であり、「空のアパートに戻る」イベントはすべて、その旅行中に鍵を携行する誰かによってカバーされるようにする必要があります。 

出力は旅行ごとの二者択一の決定です。つまり、旅行の担当者が鍵を携帯する必要があるかどうか、またはすべての制約を満たす割り当てがないことを報告する必要があります。 

制約 n と q は最大 100000 までなので、どの解もイベント数が線形または対数線形に近い必要があります。 すべてのイベントまたはすべての旅行ペアにわたる二次シミュレーションは直ちに不可能です。 時間は最大 10^9 と大きく、実際の時間値ではなく、イベントの順序のみが重要であることが強く示唆されています。 

微妙な失敗例は、複数の人が近くに戻ってきて鍵が不足している場合に発生します。 たとえば、k = 1 で、2 人の人がそれぞれ異なる時間に空のアパートに戻り、内部の存在が重複しない場合、両方ともキーが必要になりますが、グローバルに存在するキーは 1 つだけです。 個人ごとにキーをローカルに割り当てる単純な貪欲な人は、このグローバルな結合を見逃す可能性があります。 

もう 1 つのエッジケースは、誰かが何度も外出して戻ってくる場合です。 個人の旅行は重複しないため、それらを個別に扱いたくなるかもしれませんが、キーはグローバルに共有されるため、1 つの旅行にキーを割り当てると、他のすべての旅行の可用性に影響します。 

## アプローチ

 ブルートフォースアプローチでは、旅行ごとのキー使用の可能なすべての割り当てをシミュレートします。 各旅行では鍵を持っているか持たないかのどちらかであるため、2^q 通りの可能性があります。 割り当てごとにタイムラインをシミュレートし、屋内にいる人数を追跡し、アパートが空になって誰かが戻ってくるたびに、その戻りがキー割り当てによってサポートされていることを確認します。 q が 100000 に達するため、これはすぐに実行不可能になります。実行可能性は間隔間のグローバルな相互作用に依存するため、枝刈りさえも役に立ちません。 

重要な観察は、問題は基本的に、k 個のアクティブなキー キャリアという限られた予算を使用して「空間隔リターン」のカバレッジを確保することにあるということです。 人ごと、または旅行ごとに考えるのではなく、イベントを時系列で考え、現在アクティブな一連の旅行を維持する必要があります。 旅行は出発から帰国までアクティブです。 帰国イベントで他に誰もいない場合は、そのイベントにキーを割り当てる必要があり、そのキーは現在アクティブな旅行の 1 つから取得する必要があります。 これは当然、時間の経過とともに貪欲な戦略を示唆します。 

すべてのイベントを時間順に処理します。 現在内部にいる人々のセットを維持します。 また、どのトリップが現在キーを保持しているかも維持します。 返品が発生し、アパートが空になる場合、少なくとも 1 つのアクティブな旅行が鍵を携行するように指定されていることを確認する必要があります。 存在しない場合は、現在アクティブな旅行の 1 つにキーを割り当てます。 どのアクティブなトリップにキーを持たせるかの選択は、最も重要な貪欲な決定です。将来の強制的な割り当てを最小限に抑える方法でキーを割り当てたいので、最長の期間使用可能であるため、戻り時刻が最も遅いアクティブなトリップにキーを割り当てます。

これにより、問題は、アクティブな間隔にわたる優先構造を備えたスイープ ラインに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^q · q) | O(q) | 遅すぎる |
 | 貪欲 + ヒープのスイープ ライン | O(q log q) | O(q) | 承認済み |

 ## アルゴリズムのチュートリアル

 各旅行を開始イベントと終了イベントの 2 つのイベントに変換し、すべてのイベントを時間順に並べ替えます。 次に、現在アクティブな旅行のセットを維持しながら、時系列でプロセスをシミュレートします。 

1. 各旅行のアイデンティティを維持しながら、すべての出発イベントと帰国イベントを時間順に並べ替えます。 これにより、変更が発生した順序でシステムが正確に処理されることが保証されます。 
2. 開始したがまだ終了していない一連のアクティブな旅行を維持します。 アクティブな各トリップは、キーを保持する候補になります。 
3. 現在キーを持たないアクティブなトリップの戻り時間によってキー付けされた最大ヒープも維持します。 この構造により、必要なときにキーを受け取るための「最適な候補」を迅速に選択できます。 
4. 私たちは現在アパート内に何人いるかを追跡するカウンターを維持しています。 Leave イベントが発生すると値をデクリメントし、Return イベントが発生すると、リターン前にフラットが空であったかどうかを知る必要があるため、キー ロジックの処理後にのみ値をインクリメントします。 
5. 戻りイベントを処理するときに、以前のイベントを処理した後の内部カウントが、この戻りが空のアパートに発生することを示している場合、アクティブな旅行にドアのロックを解除するために使用できるキーがあることを確認する必要があります。 現在キーを保持しているアクティブなトリップがない場合は、最も遠い将来のリターンを持つアクティブなトリップに 1 つのキーを割り当て、そのトリップを「キー持ち運び」としてマークします。 
6. トリップが終了すると、アクティブ セットからトリップが削除され、ヒープ内の考慮事項からも確実に削除されます。 
7. どこかの時点でキーを割り当てる必要があるが、既に k 回のキーの持ち運びがアクティブになっている場合は、不可能を返します。 

なぜそれが機能するのかは、単純な交換引数に関係しています。 キーを割り当てる必要がある場合は常に、最も遅く終了するアクティブなトリップを選択すると、より早く終了するトリップに対する柔軟性が維持されるため、実現可能性が悪化することはありません。 キーをより短い間隔に割り当てるソリューションは、有効性を損なうことなく、キーをより長い間隔と交換することで変換できます。これは、より長い間隔は、少なくとも同じ将来の期間をカバーし、より短い間隔であったであろうすべての状況で利用可能なままであるためです。 

維持される不変条件は、システムが潜在的な「ロックアウト イベント」に遭遇するたびに、キーを提供できる現在アクティブな間隔の間で常に有効な割り当てがあり、同時キー ホルダーの数が k を超えることがないということです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k, q = map(int, input().split())
    trips = []
    events = []

    for i in range(q):
        p, l, r = map(int, input().split())
        trips.append((p, l, r, i))
        events.append((l, 0, i, p))  # leave
        events.append((r, 1, i, p))  # return

    events.sort()

    # active trips
    active = set()
    has_key = [0] * q

    # max-heap by return time (negative for heapq)
    import heapq
    heap = []

    inside = 0

    # map trip index to (r, p, l)
    info = [(trips[i][2], trips[i][0], trips[i][1]) for i in range(q)]

    for time, typ, idx, p in events:
        if typ == 0:
            # leave
            active.add(idx)
            heapq.heappush(heap, (-info[idx][0], idx))
        else:
            # return event
            # before return, check if inside is zero
            if inside == 0:
                # need at least one key-holder active
                while heap and heap[0][1] not in active:
                    heapq.heappop(heap)
                if not heap:
                    print("impossible")
                    return
                # assign key if possible
                if sum(has_key) < k:
                    # assign to best candidate
                    r_neg, j = heapq.heappop(heap)
                    has_key[j] = 1
                else:
                    print("impossible")
                    return

            # person returns, now inside increases
            inside += 1
            # after return, when they leave later, inside will decrease elsewhere

        # process leave effect on inside after event type if needed
        if typ == 0:
            inside -= 1

    ans = ''.join(str(x) for x in has_key)
    print(ans)

if __name__ == "__main__":
    solve()
```このコードはまず、すべてのアクティビティが時間順に処理されるように、統合されたイベント リストを構築します。 各旅行は、間隔および 2 つのイベントの両方として追跡されます。 アクティブ セットは、現在進行中のトリップを追跡し、キー割り当ての候補トリップを最新の戻り時刻順に並べてヒープに保存します。 トリップは終了するとアクティブ セットから消えますが、ヒープには残るため、遅延削除が必要です。 

内部カウンターは、空のアパートに返品が発生したかどうかを判断するために、イベントに応じて更新されます。 これはキー割り当ての重要なトリガーです。 

キー制約 k は、現在キー ホルダーとしてマークされている旅行の数を追跡することによってグローバルに適用されます。 

## 実用的な例

 ### サンプル 1

 アパートが空になり、キーの割り当てがいつ行われるかに焦点を当て、イベントを時系列に示します。 

| 時間 | イベント | アクティブな旅行 | 内部 | 主要なアクション |
 | --- | --- | --- | --- | --- |
 | 0 | 3を残す | {3} | 0 | なし |
 | 2 | 1を残す | {3,1} | 0 | なし |
 | 4 | 2を残す | {3,1,2} | 0 | なし |
 | 7 | リターン2 | {3,1,2} | 0 → 空の戻り値 | キーを割り当てる |
 | 9 | リターン 3 | {3,1} | 1 | なし |

 キーの割り当ては、空のアパートに戻ってきた最初の瞬間に行われます。 貪欲な選択により、キーが長期間有効な間隔に移動し、後で返される柔軟性が維持されます。 

### サンプル 2

 | 時間 | イベント | アクティブな旅行 | 内部 | 主要なアクション |
 | --- | --- | --- | --- | --- |
 | 1 | 2を残す | {2} | 0 | なし |
 | 2 | 1を残す | {2,1} | 0 | なし |
 | 3 | リターン2 | {2,1} | 0 → 空の戻り値 | キーを割り当てる必要があります |
 | 4 | 1を返す | {1} | 1 | なし |

 k = 1 の場合、キーを持ち運べるのは 1 つの旅行のみです。 アルゴリズムはそれをより適切な間隔に割り当て、タイムライン全体にわたって実現可能性を確保します。 

これらのトレースは、キーの割り当てが構造的なボトルネックでのみトリガーされ、一度割り当てられると一貫性が保たれることを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(q log q) | イベントをソートし、アクティブな間隔にわたってヒープを維持する |
 | スペース | O(q) | イベント、アクティブ セット、割り当て配列の保存 |

 最も大きなコストはソートとヒープ操作であるため、複雑さは q が 100000 までに適切であり、効率的な実装により Python で 5 秒間の制限内で快適に実行できます。

 ## 特殊なケース

 重要なエッジケースの 1 つは、全員が屋外にいて、複数の返品が連続して発生する場合です。 アルゴリズムは、戻りイベントごとにやみくもにではなく、必要な「空の状態遷移」ごとに 1 つのキー割り当てのみが行われることを保証する必要があります。 次のような入力の場合:```
2 1 2
1 0 2
2 1 3
```最初の戻り値にはすでにキーが必要である可能性があり、その後はシステムが空ではなくなるため、2 番目の戻り値で別の割り当てがトリガーされることはありません。 内部カウンターは、誰かが内部に入ると、その後の戻りでは空の状態が表示されないため、この動作を保証します。 

もう 1 つのケースは、k が十分に大きく、複数の間隔でキーを同時に保持できるが、サブセットのみが必要な場合です。 ヒープベースの貪欲により、長いキー割り当てが利用可能な場合でも、短い間隔でキー割り当てを無駄にしないことが保証されるため、k を早期に使い果たすことがなくなります。
