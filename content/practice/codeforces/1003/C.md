 ## 解決策
 ## 問題の理解

 毎日の一連の気温が与えられ、少なくとも所定のしきい値以上の長さの連続する時間間隔をすべて評価するように求められます。 このような間隔ごとに、その平均温度を計算します。これは、その値の合計をその長さで割ったものを意味します。 タスクは、すべての有効な間隔にわたって可能な最大の平均を見つけることです。 

したがって、最適化しているオブジェクトは固定ウィンドウ サイズではなく、長さが最小値から始まり配列全体まで拡張できるすべてのセグメントです。 これにより、セグメントが長くなると合計密度が低くなり、スパンが長くなる可能性があるため、問題は固定ウィンドウの最大平均よりもすぐに微妙になります。 

入力サイズの制約により、最大 5000 日が許可されます。 すべての部分配列に対する単純な 3 次アプローチと合計の再計算は、すでに境界線に達しています。 合計を再計算する二重ループでも、プレフィックス合計で最適化しない限り、速度が遅すぎます。 ただし、接頭辞の合計を使用しても、Python では約 2,500 万の操作が許容されるため、n = 5,000 の場合でもすべての O(n²) セグメントを列挙することは可能です。 

隠れた難しさは、線形関数ではなく比率を最適化していることです。 これは、最良のセグメントが必ずしも許容される最短または最長のセグメントの 1 つであるとは限らず、セグメントの長さに単調な構造が存在しないことを意味します。 

いくつかの特殊なケースでは、誤った貪欲なアイデアが明らかになります。 

すべての温度が等しい場合、すべてのセグメントの平均値は同じになるため、有効なセグメントが最適になります。 正しい解決策は、特定の長さを選択することに依存してはなりません。 

配列が厳密に増加している場合、初期の低い値を含めると平均が低下するため、最良の平均は長いプレフィックスではなく短いサフィックス セグメントから得られる可能性があります。 

k が n に等しい場合、答えは単純に配列全体の平均になります。 セグメントの長さを柔軟に選択できることを前提としたソリューションでは、この境界を適切に処理する必要があります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 すべての開始インデックスを考慮して、終了インデックスを拡張し、少なくとも k 以上の長さのセグメントのみを評価します。 各候補セグメントについて、その合計を計算し、その長さで割って、最大値を追跡します。 

プレフィックスの合計を使用すると、O(1) の任意のセグメントの合計を計算できます。 約 n²/2 個のセグメントがあるため、これにより全体の複雑さが O(n²) に軽減されます。 n = 5000 では、これは約 1,250 万回の評価に相当し、それぞれの評価はいくつかの算術演算で構成されており、これは許容範囲内です。 

重要な観察は、多くのセグメントのチェックを避けることはできないが、合計を繰り返し再計算することは回避できるということです。 比率構造では、目的がセグメント長またはエンドポイントにおいて単調ではないため、より高速な枝刈りや二分探索トリックは使用できません。 

したがって、最適な解決策は本質的に、プレフィックス合計を使用して効率化された強引なアイデアです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n3) | お(1) | 遅すぎる |
 | すべてのセグメントにわたるプレフィックスの合計 | O(n²) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. prefix[i] が最初の i 要素の合計を格納するプレフィックス合計配列を構築します。 これにより、任意のセグメントの合計を一定時間で計算できます。 
2. 考えられるすべての左端点 l を 1 から n まで繰り返します。 各選択により、候補セグメントの開始が固定されます。 
3. 各 l について、すべての右端点 r を l + k - 1 から n まで反復します。 これにより、すべてのセグメントの長さが少なくとも k になることが保証されます。 
4. 各ペア (l, r) について、prefix[r] − prefix[l − 1] を使用してセグメントの合計を計算します。 
5. 合計を (r − l + 1) で割って平均を計算します。 
6. すべての有効なセグメントにわたって見られる最大平均を追跡します。 

r を l + k − 1 から開始する理由は、より短いセグメントは許可されておらず、答えに寄与せずに無効な候補が導入されるだけであるためです。 

### なぜ効果があるのか

すべての有効なセグメントは、r − l + 1 ≥ k のエンドポイントのペア (l, r) によって一意に表されます。 アルゴリズムは、そのようなペアをすべて 1 回だけ列挙します。 平均はセグメントごとに正確に計算され、最大値は候補の完全なセットにわたって取得されるため、結果は全体的な最適値と一致する必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]

    best = 0.0

    for l in range(n):
        for r in range(l + k - 1, n):
            total = pref[r + 1] - pref[l]
            length = r - l + 1
            avg = total / length
            if avg > best:
                best = avg

    print(best)

if __name__ == "__main__":
    solve()
```プレフィックス合計配列は、各範囲合計クエリが 1 つの減算になるように構築されます。 これがないと内側のループが O(n³) になってしまうため、これは重要です。 次に、ネストされたループは、インデックス範囲内の最小長の制約を直接尊重しながら、すべての有効なセグメントを列挙します。 

必要な精度は 1e-6 であり、Python の倍精度は最大約 5000 × 5000 の合計に十分であるため、浮動小数点除算は安全です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, k = map(int, input().split())
    a = list(map(int, input().split()))

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]

    best = 0.0
    for l in range(n):
        for r in range(l + k - 1, n):
            total = pref[r + 1] - pref[l]
            best = max(best, total / (r - l + 1))

    return str(best)

assert run("4 3\n3 4 1 2\n")[:5] == "2.666", "sample 1"
assert run("3 3\n1 2 3\n") == "2.0", "whole array only"

assert run("5 1\n5 5 5 5 5\n") == "5.0", "all equal"

assert run("5 2\n1 100 1 1 100\n")[:4] == "50.5", "multiple peaks"

assert run("1 1\n7\n") == "7.0", "single element"

assert run("6 3\n1 2 3 4 5 6\n")[:4] == "4.5", "increasing array"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 単一要素 | 7 | 最小境界 |
 | すべて等しい | 5 | 均一な安定性 |
 | 複数のピーク | 50.5 | 非固有の最適 |

 ## 特殊なケース

 n が k と等しい場合でも、各 l に対して有効な r が 1 つだけ存在するため、ループ構造は引き続き機能します。 この場合、アルゴリズムは配列全体の平均を効果的に計算します。 

For a strictly increasing sequence like [1, 2, 3, 4, 5], the best segment of length at least k = 2 is not necessarily the full array. The enumeration checks segments like [4, 5] whose average is 4.5, which beats longer segments such as [1, 2, 3, 4, 5] with average 3. This confirms that restricting attention to full-range segments would be incorrect, and the exhaustive enumeration is necessary.
