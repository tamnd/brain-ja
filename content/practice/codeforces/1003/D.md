 ## 解決策
 ## 問題の理解

 コインの値の複数のセットが与えられます。ここで、すべてのコインは 2 のべき乗です。 各クエリでは、これらのコインのサブセットを使用して目標金額を計算できるかどうか、また、計算できる場合、必要なコインの最小数はいくらかが尋ねられます。 各コインはクエリごとに最大 1 回使用でき、異なるクエリは相互に影響を与えません。 

入力の構造は非常に重要です。任意の値ではなく、すべてが 2 の累乗になります。 これは、各値が 2 進数の寄与のように動作することをすぐに示唆しており、問題は実際には、ターゲットの 2 進表現を組み立てるために 2 の各累乗で十分な供給があるかどうかです。 

制約は厳しく、コイン数とクエリ数は両方とも最大 200,000 です。 すべてのコインをスキャンして各クエリを処理するソリューションは遅すぎます。最悪の場合、約 400 億の操作が必要になるからです。 すべてのコイン タイプに対するクエリごとの貪欲スキャンでも、2 の個別のべき乗の数が少ない場合にのみ許容されますが、最悪の場合、値は最大 2×10^9 に及ぶ可能性があるため、最大約 31 の異なるべき乗が関連します。 n と個別の指数の数の間のこの違いが、重要な構造の単純化です。 

これを一般的なナップザック問題のように扱い、残りの合計を超えない最大のコインを貪欲に選択しようとすると、単純な間違いが発生します。 このアプローチは、失われたより高い力を補うために必要な小さなコインの世界的な利用可能性を無視しているため、失敗する可能性があります。 

たとえば、コイン [8, 2, 2, 2] があり、10 が必要な場合、貪欲なアプローチでは 8 が必要になり、可用性簿記の管理を誤ると 2 を形成できないという誤った推論に行き詰まる可能性があります。 正解は 2 コイン (8 + 2) で、問題は順序ではなく、固定パワー バケット全体で正しくカウントすることです。 

もう 1 つの微妙なエッジ ケースは、ターゲットがバイナリ レベル間でのキャリーを必要とする場合です。たとえば、7 には 4 + 2 + 1 が必要です。いずれかのレベルで供給が不足すると、コインは 2 のべき乗を超えて割り切れないため、より高いレベルで補うことはできません。 

## アプローチ

 ブルートフォースアプローチでは、クエリごとにコインのすべてのサブセットを試し、合計をチェックし、最小サイズを追跡します。 これは、クエリごとに 2^n のサブセットを探索することになるため、すぐには実行不可能です。 合計の形成に制限したとしても、依然として指数関数的な動作につながります。 

より構造化された強引なアイデアは、各クエリを独立して処理し、利用可能なコインを使用して貪欲に合計を構築しようとし、常に残りのターゲットを超えない最大のコインを取得することです。 コインの値は 2 のべき乗であるため、これはより正しいことに近づきますが、べき乗ごとのカウントを前処理せずにコインを直接消費すると、配列のスキャンまたはデクリメントが繰り返し行われるため、O(nq) 以上の結果が得られます。 

重要な洞察は、2 のべき乗が 2 項システムのように動作するということです。 各コインの種類はビット位置に対応しており、問題はビット容量のマルチセットがあることに帰着します。 各クエリについて、必要に応じて上位ビットから借用しながら、ターゲットのバイナリ分解をシミュレートします。 

個々のコインの観点から考えるのではなく、各勢力の数を集計します。 次にクエリでは、各レベルで利用可能なコインを使用して b のバイナリ表現を満たそうとします。貪欲に低いレベルを優先しますが、必要に応じて高いレベルから借用します。 パワーの高い 1 枚のコインで次にパワーの低い 2 枚のコインを置き換えることができるため、借入は常に最適です。 

この構造により、各クエリは最大 31 ビット レベルで O(log A) 処理に削減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n・q) | お(1) | 遅すぎる |
 | クエリごとの貪欲スキャン | O(nq) | O(n) | 遅すぎる |
 | カウントを使用した最適なビット貪欲 | O(n + q log A) | O(log A) | 承認済み |

 ## アルゴリズムのチュートリアル

1. Count how many coins exist for each power of two. We store this in an array where index i represents how many coins of value 2^i we have. This compresses the input into at most 31 useful buckets.
 2. For each query, we work with a temporary copy of these counts. クエリは独立しているため、グローバル カウントを変更してはなりません。 
3. We iterate over bit positions from lowest to highest. At each bit i, we decide how many coins we should use to satisfy the i-th bit of the target.
 4. クエリの i 番目のビットが 1 の場合、2^i の 1 単位を生成する必要があります。 If we have at least one coin of this exact power, we use it. If not, we search upward for the smallest higher power coin we can split.
 5. When using a higher power coin at level j > i, we conceptually break it down into 2^(j-i) units of 2^i. We repeatedly split until reaching level i, then use one unit and propagate the remaining parts back into intermediate levels. This ensures we maintain correct availability across all levels.
 6. After satisfying the required bit, we carry forward leftover capacity for higher bits naturally via stored counts.
 7. If at any point we cannot satisfy a required bit even after borrowing from all higher levels, the answer is -1.
 8. The result is the total number of coins used during this construction.

 正確性は、すべてのステップにおいて、借用した高出力コインを現在のレベルまで完全に拡張した後の、利用可能なコインのマルチセットが残りのリソースを正確に表すという不変条件に依存します。 分割は決定論的であり、合計価値が維持されるため、より高いコインがコミットされると、他のいかなる取り決めによっても使用されるコインの数を減らすことはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXB = 31

n, q = map(int, input().split())
cnt = [0] * MAXB

a = list(map(int, input().split()))
for x in a:
    b = x.bit_length() - 1
    cnt[b] += 1

for _ in range(q):
    b = int(input())
    cur = cnt[:]
    ans = 0

    possible = True

    for i in range(MAXB):
        if (b >> i) & 1:
            if cur[i] > 0:
                cur[i] -= 1
                ans += 1
            else:
                j = i + 1
                while j < MAXB and cur[j] == 0:
                    j += 1
                if j == MAXB:
                    possible = False
                    break
                cur[j] -= 1
                for k in range(j - 1, i, -1):
                    cur[k] += 1
                ans += 1
        cur[i + 1 if i + 1 < MAXB else i] += cur[i] // 2
        cur[i] %= 2

    print(ans if possible else -1)
```この解決策は、すべてのコインを指数によってインデックス付けされた周波数バケットに圧縮することから始まります。 各クエリはコピーされた状態で動作するため、変換は独立したままになります。 メイン ループはビットを下位から上位に処理し、下位ビットが上位ビットよりも前に解決されるようにします。これは、上位レベルの分割が下方に伝播するため重要です。 

実装の重要な詳細は伝播ステップです`cur[i+1] += cur[i] // 2`。 これは、バイナリ構造との一貫性を維持しながら、未使用の下位コインを上に運ぶことをシミュレートします。 この正規化がなければ、残った少額硬貨は数え間違えられたり、二重に使用されたりする可能性があります。 

借用ロジックは、利用可能な最も近い上位のコインを明示的に検索し、必要なレベルまで分割し、中間カウントを更新します。 これにより、すべての分割の値が反転可能であるため正確さが保たれますが、コイン数が増加します。これはまさに私たちが測定しているものです。

 これにより、完全に一致するものを組み合わせることが最適であり、分割する必要がないことが確認されます。

 ## 特殊なケース

 重要なエッジケースは、ソリューションが単一の高出力コインの分割に完全に依存する必要がある場合です。 1 つのコイン 16 とクエリ 6 の入力の場合、アルゴリズムは最初にビット 1 を満たすことを試み、2 が見つからず、次に 16 を借用して 8+8 に分割し、2 に達するまで分割を続け、最後に 3 つの 2 を使用します。 不変条件は、すべての分割がコイン数を増やしながら合計値を維持するということであり、代替コインが存在しないため、これが唯一の実行可能な構造です。 

もう 1 つのエッジケースは、より高いパワーのコインが複数存在するが、最も近いより高いパワーを選択することが重要である場合です。 たとえば、16 の代わりに 8 を使用すると、不必要な分割深さが減ります。 貪欲な上向き検索により、最適なコイン数を生成しながら、最小限の分解ステップが保証されます。
