 ## 問題の理解

 私たちには番号が与えられています$n$そしてパラメータ$k$。 から始まる$n$、許可される 2 つの演算を使用してゼロに到達したいとします。1 を減算するか、現在の値が次の値で割り切れるかどうかです。$k$で割った後の商に置き換えます。$k$。 各操作には 1 ステップのコストがかかり、目標はステップの合計数を最小限に抑えることです。 

これは本質的に、割り切れる可能性がある場合に、徐々に、または時折大きくジャンプして数値を繰り返し縮小するプロセスです。 難しいのは、割り算ができるのはたまにしかないため、割り切れる数にするために必要な手順を考慮せずに自由に「貪欲に割り算」することはできないということです。 

制約は非常に大きく、$n$そして$k$まで$10^{18}$。 これにより、1 つずつデクリメントされるシミュレーションが即座に除外されます。 リニアスキャンでも、$n$それは不可能です、なぜなら$10^{18}$作戦は制限時間をはるかに超えている。 有効な解法では、通常は長い連続減算をスキップすることによって、対数または対数に近い段階で数値を減らす必要があります。 

単純なアプローチでは、プロセスをシミュレートします。$n$で割り切れない$k$、割り切れるまで繰り返し 1 を引き、割り切れたら割ります。 これは正しいですが、次の場合にひどく劣化する可能性があります。$n$大きくて、$k$小さいです。 たとえば、次の場合$n = 10^{18}$そして$k = 2$、単純なシミュレーションでは、偶数になるまで 1 を繰り返し減算してから除算し、このパターンを何度も繰り返します。 ステップ数は次のようになります。$n$、それは不可能です。 

別の微妙なエッジケースが発生するのは、$k = 1$。 1 で除算しても値は変わらないため、意味のある演算は 1 を減算することだけです。 その場合の答えは単純に、$n$。 このケースを防ぐことができない実装は、永久にループしたり、無駄な除算を繰り返し適用したりする可能性があります。 

## アプローチ

 ブルートフォース戦略とは、常に利用可能な最良の手を段階的に適用することです。 各状態で割り切れる場合、$k$、 分ける; それ以外の場合は 1 を減算します。 これは局所的に合理的です。なぜなら、除算は数値を急速に縮小し、減算は将来の除算に備えるためです。 

これは正しく機能しますが、減算フェーズが実行時間の大半を占めるため、効率が低下します。 最悪の場合、各分割の前に最大で$k-1$これは、ゼロまでの範囲全体にわたって何度も繰り返される可能性があります。 以来$n$までです$10^{18}$、これにより、無制限の操作が発生します。 

重要な点は、減算を 1 つずつシミュレートする必要がないということです。 代わりに、最も近い倍数に直接ジャンプできます。$k$。 現在の番号が$x$、計算します$x \bmod k$。 この値は、割り切れる状態に到達するために必要な減算の回数を正確に示します。 これらを 1 つの集約されたステップで適用します。 その後も数値が少なくとも残っている場合は、$k$、分割を実行して続行します。 

これにより、プロセスが一連の大きなジャンプとそれに続く少数の分割に変換され、反復回数がおよそ$O(\log_k n)$。

 ## アルゴリズムのチュートリアル

 一括減算と時々の除算を組み合わせて、繰り返し数値を減らします。 

1. もし$k = 1$、唯一有用な手は 1 を引くことなので、答えは次のようになります。$n$。 すぐに戻ります。 これにより、何も変更しない除算によって引き起こされる無限ループが回避されます。 
2. その間$n \ge k$、最初に計算します$r = n \bmod k$。 これは、最も近いより小さい倍数からどれだけ離れているかを示します。$k$。 
3. 引き算します$r$ワンステップで削減$n$の倍数に$k$、と追加します$r$答えに。 これにより、多くの単位演算が 1 つの算術ジャンプに置き換えられます。 
4. 次に分割します$n$による$k$、答えを 1 つ増やします。 これは唯一の有効な除算ステップであり、大きさが大幅に減少します。 
5. までこのプロセスを繰り返します。$n < k$、つまり、分割は不可能になります。 
6. 最後に、残りを差し引きます。$n$ゼロに到達するには、追加します$n$答えに。 

これが機能する理由は、すべての段階で最適なローカル戦略を正確なコスト分解に変換しているためです。有効なシーケンスは、除算が発生する前に最終的に同じ剰余を削除する必要があるため、一括で支払いをしても最適性は変わりません。 

### なぜ効果があるのか

 不変条件は、各反復後に、現在の状態を最も近い有効な除算点にするために必要な減算演算の正確な数を考慮していることです。 除算は常に可能になるとすぐに実行され、すべての減算は 1 回だけカウントされるため、演算の順序を変更しても総コストを削減できません。 最適なパスは分割する前に剰余を「クリア」する必要があるため、これらの操作をグループ化すると、非効率を排除しながら正確性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n, k = map(int, input().split())
        
        if k == 1:
            out.append(str(n))
            continue
        
        steps = 0
        
        while n >= k:
            r = n % k
            steps += r
            n -= r
            n //= k
            steps += 1
        
        steps += n
        out.append(str(steps))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```コードはバッチ処理のアイデアを直接実装しています。 モジュラス演算は、除算の前に必要な減分数を計算します。 それらを適用した後、一度分割して続行します。 数値が以下の場合、ループは終了します。$k$、この時点では引き算のみが残ります。 

特別な場合$k = 1$不要なループを回避し、デクリメントのみが可能であることを正しく反映するために、明示的に処理されます。

 ## 特殊なケース

 いつ$k = 1$, 除算はいつでも可能ですが、役に立ちません。 アルゴリズムは明示的に返します$n$、減算のみが数値を減らすという事実と一致します。 入力用$n = 5, k = 1$、5を直接出力します。 

いつ$n < k$、分割はまったく発生しません。 例えば、$n = 7, k = 10$、ループはスキップされ、ゼロまで減算するだけなので、答えは単純に 7 になります。 

いつ$n$は正確に割り切れます$k$、 のような$n = 100, k = 10$、余りはゼロなので、追加コストなしですぐに除算します。 アルゴリズムは、終了するまで分割ごとに 1 つのステップを正しく実行します。
