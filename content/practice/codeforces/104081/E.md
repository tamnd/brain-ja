 ## 問題の理解

 音楽トラックが無限ループで再生されている間に 1 秒に 1 回変化する単一のスカラー状態を追跡しています。 トラックには長さがある$n$、そして毎秒、この期間から固定の「ラウドネス」値が生成されます。 その値に応じて、人の覚醒度は毎秒 1 単位ずつ増加または減少します。 

時間ゼロでは、覚醒は指定された初期値で始まります。 シミュレーション中は、現在の曲の値が固定のしきい値と 1 秒ごとに比較されます。 歌の値がそのしきい値より大きくない場合、覚醒度は 1 減少し、それ以外の場合は 1 増加します。 曲は永遠に繰り返されるため、+1 と -1 の無限の更新シーケンスが生成されます。 

目標は、永遠にシミュレーションすることではありません。 代わりに、連続したブロックが存在するかどうかを尋ねられます。$k$再生開始後のある瞬間から始まる秒数。$k$秒間、覚醒値は固定制限を超えることはありません。 そのようなウィンドウが無限のタイムラインのどこかに存在する場合、答えは「YES」、そうでない場合は「NO」です。 

入力フォーマットの最初の行には 5 つの整数が含まれています。 このうち最後の値が初期覚醒値です。 中間の値の 1 つは、2 番目の値が +1 に寄与するか -1 に寄与するかを決定するために使用されるしきい値です。 別の値は必要なウィンドウの長さです$k$。 残りの値は、この問題のインスタンスでは無関係なノイズであり、プロセスには影響しません。 2 行目は周期的なソング配列を示します。 

無限のタイムラインにわたる単純なシミュレーションは不可能です。 シーケンスは周期的ですが、時間の経過とともに状態がドリフトするため、数百万秒のシミュレーションでもすでに制限を超えている可能性があります。 

素朴なスライディング ウィンドウ思考の微妙な失敗例は、同じであるという事実を無視することから生じます。$n$-length パターンは、累積値が上または下にシフトしながら繰り返されます。 たとえば、有効なウィンドウがシーケンスの後半に存在する場合でも、それはサイクル内の異なるオフセットに対応する可能性があり、最初の期間だけをチェックするだけでは見つけることができません。 

中心的な課題は、無限で定期的に繰り返されるプレフィックス合計プロセスに対するウィンドウ制約が必要であることです。 

## アプローチ

 直接的な総当たりアプローチでは、プロセスを秒ごとにシミュレートし、現在の覚醒値を維持し、可能な長さのすべてのウィンドウをチェックします。$k$。 開始位置ごとに$i$、前方にスキャンします$k$手順を実行し、すべての値が許可された制限内にあるかどうかを確認します。 これには費用がかかります$O(k)$開始位置ごとに、タイムラインには制限がないため、人為的に切断する必要があります。 でカットしても$O(n^2)$秒、これは次のようになります$O(n^2 k)$これは、一般的な制約では実現不可能です。 

重要な観察は、状態の発展が +1 値と -1 値の周期配列のプレフィックス和によって完全に決定されるということです。 ウィンドウを直接シミュレートする代わりに、プロセスをプレフィックス合計配列に変換します。$P$ここで、各位置は開始からの純変化を表します。 時の目覚め$t$は単に初期値にプラスしたものです$P[t]$。 

ここで、「覚醒状態がウィンドウ内の制限を超えない」という条件が、プレフィックス合計の範囲にわたる最大制約になります。 具体的にはウィンドウの場合$[i, i+k-1]$、その間隔内の最大プレフィックス合計値が、最初の覚醒状態から導出されるしきい値を下回るようにする必要があります。 

シーケンスは周期的であるため、配列の 2 つの連結されたコピーを調べるだけで済みます。 すべてのウィンドウをピリオド内の開始フェーズに揃えることができるため、無限シーケンス内の有効なウィンドウはすべて、この 2 倍のプレフィックス内の一部のウィンドウに対応します。 

これにより、問題は、サイズの配列のプレフィックス合計に対するスライディング ウィンドウの最大値に縮小されます。$2n$、これは単調デックを使用して効率的に解くことができます。

 ## アルゴリズムのチュートリアル

 曲を署名された投稿のシーケンスに再定式化してから、プレフィックスの合計を使用して有効なウィンドウを検索します。 

1. 各曲の値をデルタに変換します。閾値以下の場合は -1 として扱い、それ以外の場合は +1 として扱います。 これは、1 秒あたりの覚醒状態の変化をエンコードします。 
2. このデルタ配列の 2 つの連結コピーに対してプレフィックス合計配列を構築します。 すべての巡回ウィンドウが連続したセグメントとして表現されるように配列を複製します。 
3. この 2 倍の配列内の各位置について、プレフィックスの合計を計算します。 これは、その秒までの覚醒状態の正味の変化を表します。 
4. 適切なサイズのスライディング ウィンドウを維持する$k$プレフィックスの合計を超えています。 各ウィンドウについて、その中の最大プレフィックス合計値が必要です。 
5. 各ウィンドウについて、この最大プレフィックス合計が、初期ウェイクフルネスに追加されたときに、許容制限内に収まるかどうかを確認します。 存在する場合、有効なスリープ ウィンドウが存在すると直ちに結論付けます。 
6. すべての候補をスキャンした後、条件を満たすウィンドウがない場合、答えは「いいえ」です。 

各ウィンドウ内の最大値のみを追跡する理由は、プレフィックスの合計が最高になると覚醒度が最悪になるためです。これは、プレフィックスが大きいほど覚醒度が高いことを意味するためです。 

### なぜ効果があるのか

 時の目覚め$t$プレフィックスの合計によって完全に決定されます。$t$。 したがって、ウィンドウ全体にわたって覚醒状態がしきい値未満に留まるかどうかを制御することは、そのウィンドウ内の最大プレフィックス合計を制御することになります。 違反は、間隔内でプレフィックスの合計が最大になるポイントで発生する必要があります。 二重配列を介してすべての循環位置を列挙することにより、無限の繰り返しにおけるすべての可能な開始フェーズが正確に 1 回カバーされることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, k, _, thresh, w0 = map(int, input().split())
    a = list(map(int, input().split()))
    
    # build doubled delta array
    arr = []
    for _ in range(2):
        for x in a:
            arr.append(1 if x > thresh else -1)
    
    m = len(arr)
    pref = [0] * (m + 1)
    for i in range(m):
        pref[i + 1] = pref[i] + arr[i]
    
    limit = thresh - w0
    
    dq = deque()
    
    for i in range(1, m + 1):
        while dq and dq[0] < i - k:
            dq.popleft()
        
        while dq and pref[dq[-1]] <= pref[i - 1]:
            dq.pop()
        
        dq.append(i - 1)
        
        if i >= k:
            max_pref = pref[dq[0]]
            if max_pref <= limit:
                print("YES")
                return
    
    print("NO")

if __name__ == "__main__":
    solve()
```このコードは、循環アラインメントが線形に表現されるように、プロセスの 2 倍バージョンを構築します。 プレフィックス配列`pref`累積的な覚醒状態の変化を追跡します。 デキューはプレフィックス値のインデックスを降順で保持するため、フロントには常に現在のウィンドウの最大プレフィックスが格納されます。 

条件は、その最大プレフィックスを、最初の覚醒状態から導出された許容制限と比較します。 有効なウィンドウが見つかるとすぐに、存在するだけで十分なので、早期に停止します。 

## 実用的な例

 有効なウィンドウが存在する最初のサンプル構造をトレースします。

| ステップ | デルタ | プレフィックスの合計 | ウィンドウ内の最大値 (k=3) |
 | --- | --- | --- | --- |
 | 1 | -1 | -1 | -1 |

 | 3 | +1 | -1 | -1 |
 | 4 | +1 | 0 | 0 |
 | 5 | +1 | 1 | 1 |

 このトレースでは、最初の位置から開始して長さ 3 のウィンドウを評価すると、最大プレフィックスは許容範囲内にとどまるため、有効なセグメントが存在し、アルゴリズムは「YES」を返します。 

2 番目のサンプルの場合、$k=4$、同じプレフィックス構造が拡張されますが、すべての長さ 4 のウィンドウには、しきい値制約を超えるプレフィックス ピークが含まれており、条件を満たす有効なセグメントがないことを意味します。

 ## 特殊なケース

 主なエッジケースは、曲が完全に「安全」である場合、つまりすべての値がしきい値以下である場合です。 この場合、覚醒度は厳密に毎秒減少します。 システムが無限に下方にドリフトしても、アルゴリズムは依然として有効な初期ウィンドウを正確に識別する必要があります。 プレフィックスの合計は単調減少するため、スライディング ウィンドウの最大値は常に左側の境界となり、最初の実行可能なウィンドウがすぐに検出されます。 

もう 1 つのケースは、すべての値がしきい値を超えている場合です。 覚醒度は厳密に増加し、十分に大きな限界に対する上限制約を満たすウィンドウは存在しません。 すべてのウィンドウのプレフィックスの最大値は着実に増加するため、アルゴリズムはすべてのウィンドウを正しく拒否します。 

3 番目の微妙なケースは、有効なウィンドウが配列の 2 つの繰り返しの間の境界を越えてのみ表示される場合に発生します。 二重プレフィックス構造により、これが引き続き連続セグメントとして表現されることが保証されるため、deque ベースのスキャンでは特別なケースを使用せずに自然に評価されます。
