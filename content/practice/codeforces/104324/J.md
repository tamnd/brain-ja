 ## 解決策
 ## 問題の理解

 一連の参加者が与えられ、それぞれに 2 つのしきい値が設定されています。$a_i$、そしてより高い要件$b_i$、 どこ$a_i < b_i$。 各参加者は少なくとも何かを受け取ると「満足」します。$a_i$少なくともステーキを受け取ると「満腹」になります$b_i$ステーキ。 

Egor が配布できるのは最大でも$k$参加者全員の合計でステーキ。 彼は、全員が少なくとも満足できるようにしなければなりません。つまり、すべての参加者が少なくとも$a_i$ステーキ。 それに加えて、一部の参加者は追加のステーキを最大で受け取ることができます。$b_i$、いっぱいになります。 

構築中の実現可能性を決定する追加のグローバル制約があります。プロセスのどの時点でも、完全な参加者の数が満足した参加者の数を決して超えてはなりません。 すべての完全な参加者も満足しているため、この条件は、十分な数の他の参加者が少なくとも満足する前に、人々をどれだけ積極的に完全なステータスに「アップグレード」できるかを事実上制限します。 

タスクは、これらの制約の下で満員にできる参加者の最大数を決定すること、または全員を満足させるにもそれ以上の参加者が必要な場合は不可能であることを報告することです。$k$ステーキ。 

制約は大きく、最大で$10^5$参加者とステーキのカウントアップ$10^9$。 これにより、ステーキごとの分布をシミュレートしたり、参加者間の二次比較を使用したりするソリューションは即座に除外されます。 実行可能な解決策は次のとおりである必要があります。$O(n \log n)$またはそれ以上です。 

貪欲にできるだけ早く参加者を満員にしようとすると、微妙な失敗モードが現れます。 たとえば、誰かの間に小さなギャップがある場合、$a_i$そして$b_i$、早めにアップグレードしたくなるでしょう。 ただし、そうすることで、満足するだけの参加者が少なすぎると、後でグローバル バランス条件に違反する可能性があります。 

もう 1 つのよくある落とし穴は、まず全員を満足させるという実現可能性を無視することです。 もし$\sum a_i > k$、どんなに巧妙なスケジュールを立てても、答えはすぐに不可能になります。 

## アプローチ

 ブルートフォース解釈では、参加者のサブセットごとに、どのサブセットがどのような順序で満員になるかを決定しようとします。 候補番号ごとに$x$を選択できるかどうかを確認してみます。$x$参加者は少なくとも配布を続けながらフルにアップグレードできます$a_i$すべての人に、そしてグローバルな制約を尊重します。 

これは組み合わせ爆発につながります。 修正の実現可能性チェックも$x$順序と割り当てに関する推論が必要になるため、すぐに指数関数的、または少なくとも$O(n^2)$バランス条件を動的に強制しようとするときのシミュレーション。 

重要な洞察は、問題を 2 つのフェーズに分けることです。 まず、全員が基本満足コストを受け取る必要があります$a_i$。 これは必須であり、注文とは独立しています。 この後、予算が残っています$k' = k - \sum a_i$、各参加者には「プロモーション費用」がかかります。$c_i = b_i - a_i$、これはそれらをいっぱいにするためのコストです。 

ここで問題は、コストを払って完全に昇格する参加者のサブセットを選択することです。$c_i$、決定のどのプレフィックスでも、満足した参加者に対して完全な参加者が多すぎることはできないという制約を尊重しながら、カウントを最大化します。 すべての基本的な満足の後、すべての参加者はすでに満足しているため、この制約は事実上、昇格を選択する順序のプレフィックス制約になります。すでに昇格している参加者の数が、概念的な順序付けで「アクティブ化」されているまだ昇格していない参加者の数を超えない限り、誰かを昇格させることはできません。 

このタイプの条件は、従来、次の基準で並べ替えることによって処理されます。$b_i$(または同等の緊密さによって) 優先順位構造を使用して貪欲な選択を維持し、実現可能な候補者の中で常に最も安価なプロモーションを確保します。 

具体的には、参加者を昇順に処理します。$b_i$。 私たちは、彼らを潜在的な完全な候補者として含めようとしていると仮定します。 私たちは選択したプロモーション費用を大量に管理し、総費用を追跡します。 コストが残りの予算を超える場合は、最も高価なプロモーションが削除されます。 これにより、選択されるアップグレードの数が最大化されます。 残高条件は注文によって強制されます。$b_i$これにより、より厳しい制約を早期に検討するという要件に違反することがなくなります。 

これにより、問題は古典的な貪欲な「順序制約を設けて予算内でカウントを最大化する」構造に帰着します。

 ## アルゴリズムのチュートリアル

 1. 必須コストを計算する$S = \sum a_i$。 もし$S > k$, output -1 immediately. いくら賢いスケジューリングを行っても不十分な基本満足度を補うことはできないため、このステップでは実現可能性が最適化から切り離されます。 
2. 残りの予算を定義する$R = k - S$。 これは、満足から完全へのアップグレードにのみ使用できるものです。 
3. 参加者ごとにアップグレードコストを計算します$c_i = b_i - a_i$。 これにより、段階的な決定が分離されます。各完全な参加者には、まさにこの追加料金がかかります。 
4. 参加者を並べ替える$b_i$昇順で。 その理由は、参加者の身長が低いためです。$b_i$グローバル構造を満たすという点で、より「緊急」である。 それらを遅らせると、暗黙のプレフィックス実現可能性制約に違反する危険があります。 
5. ソートされたリストを調べて、選択したアップグレード コストの最大ヒープを維持します。 参加者ごとに、$c_i$をヒープに追加し、現在の合計に加算します。 
6. いずれかの時点で、選択したアップグレード費用の合計が超過した場合$R$、ヒープから最大のコストを削除して差し引きます。 これにより、固定予算内でカウントを最大化するという観点から、選択が最適に保たれます。 
7. 答えは、すべての参加者を処理した後のヒープのサイズです。 

正しさは貪欲な交換議論から生まれます。 並べ替え順$b_i$参加者がアップグレードの対象となる時期についての構造的制約を確実に尊重するようにします。 すべての有効なサブセットの中で、アップグレード コストを最小限に抑えることが常に最適です。選択した高価なアップグレードをより安価なアップグレードに置き換えても、実現可能性が低下することはなく、同じ予算内で達成可能なアップグレードの数が減少することもありません。 ヒープはまさにこの不変条件を維持します。つまり、各プレフィックスを処理した後、そのプレフィックスの最小総コストで可能なアップグレードの最大数を保持します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    n, k = map(int, input().split())
    a = []
    b = []
    total = 0

    arr = []
    for _ in range(n):
        ai, bi = map(int, input().split())
        total += ai
        arr.append((bi, ai))

    if total > k:
        print(-1)
        return

    R = k - total

    arr.sort()

    heap = []
    cur = 0

    for bi, ai in arr:
        cost = bi - ai
        heapq.heappush(heap, cost)
        cur += cost

        if cur > R:
            cur -= heapq.heappop(heap)

    print(len(heap))

if __name__ == "__main__":
    solve()
```実装はすべてを合計することから始まります$a_i$、必須要件の実現可能性を強制します。 それが失敗した場合は、早めに終了します。 それ以外の場合は、各参加者を単一のアップグレード コストに変換します。$c_i$、次に並べ替えます$b_i$構造的な順序付けの制約を強制します。 

ヒープには、選択されたアップグレード コストが保存されます。 これは、コストを直接プッシュし、最大のビアサイントリックを削除するか、必要に応じてマイナスを格納することにより、最小ヒープを使用して最大実現可能なマルチセットとして維持されます。 ここでは、慎重な減算ロジックを備えた Python のヒープに依存しています。 累計はアップグレードの合計コストを追跡し、予算を超えるたびに、可能な最大数を維持しながら最も高価なアップグレードを削除します。 

最終的なヒープ サイズは、完全な参加者の数です。

 ## 特殊なケース

 最も敏感なエッジケースは、基本要件の合計が正確に一致する場合です。$k$。 その場合、どんなに小規模であってもアップグレードは不可能です$b_i - a_i$は。 アルゴリズムはこれを正しく処理します。$R = 0$したがって、ヒープが空になるまで、プッシュを試行するとすぐに削除がトリガーされます。 

もう 1 つのエッジ ケースは、参加者の 1 人が非常に小さい場合に発生します。$b_i - a_i$しかし非常に大きい$b_i$。 ソート順$b_i$これにより、この参加者が後で考慮されるようになり、以前の実行可能な選択が誤ってブロックされることがなくなります。 予算が許す場合のみヒープに含まれ、そうでない場合は削除されます。 

最後のケースは、すべてが$a_i$小さいですが$k$よりわずかに大きいだけです$\sum a_i$。 2 番目の選択は予算を超えて削除され、最適な 1 つのアップグレードが正確に残るため、アルゴリズムは最も安価なアップグレード コストのみを正しく選択します。
