 ## 解決策

 ## 問題の理解

 ゴールキーパー、ディフェンダー、フォワードという 3 つの独立したプレーヤー グループが与えられます。 各選手には固有の背番号があります。 私たちは、ゴールキーパー 1 名、ディフェンダー 2 名、フォワード 3 名からなるチームを形成しなければなりません。 

選択は、選択された 6 人のプレーヤーが背番号に関するグローバル制約を満たす場合にのみ有効です。つまり、選択されたプレーヤーのどのペアでも、大きい番号は小さい番号の最大 2 倍でなければなりません。 同様に、選択したセットの最小値と最大値を取得した場合、最大値は最小値の 2 倍を超えることはできません。 

タスクは、これらの役割の制約と数値の制約の下で、有効なチームがいくつ編成できるかをカウントすることです。 

プレイヤーの総数は最大でも 1000 人であるため、グループ全体で 6 つすべてを列挙しようとするアプローチは即座に除外されます。 単純な組み合わせ数でも、$\binom{1000}{6}$実現可能な限界をはるかに超えています。 ただし、1000 個の要素は十分小さいので、$O(n^2)$または$O(n^2 \log n)$アプローチは実行可能です。 

微妙なエッジ ケースは、異なるグループ内で重複しているように見える値から発生します。番号はグローバルに異なっていても、異なる役割グループに重複する範囲の番号が含まれる場合があります。 もう 1 つのエッジ ケースは、有効なウィンドウが非常に小さい場合です。たとえば、少数の数値のみが比率制約を満たす場合です。カウントが慎重に処理されないと、単純なスライディング ウィンドウ推論が失敗する可能性があります。 

## アプローチ

 直接的な強引なアプローチは、ゴールキーパーを 1 人選択し、次にディフェンダーのすべてのペアを選択し、次にフォワードのトリプルをすべて選択し、すべての組み合わせの状態をチェックすることです。 これはすでに与えられています$O(g \cdot d^2 \cdot f^3)$組み合わせを明示的に拡張すると、最悪の解釈になります。これは、最小の制約に対しても大きすぎます。 

組み合わせを慎重に扱ったとしても、フォワードのトリプルすべてを単独で反復するのは困難です。$O(f^3)$、そしてそれ以来$f \le 1000$、これはもう$10^9$、これは受け入れられません。 

重要な観察は、制約が選択した 6 つの数値の最小値と最大値にのみ依存するということです。 候補の最小値と最大値を修正したら、有効な選択はすべてその数値範囲内に完全に収まる必要があり、選択されたすべてのプレーヤーは 3 つのグループのいずれかに属している必要があります。 これにより、問題はサブセットの列挙から、ソートされた配列上の制約されたスライディング ウィンドウ内の組み合わせのカウントへと移行します。 

すべてのプレイヤーを一緒にソートすると、エンドポイント間の比率が最大 2 であるという条件を維持しながら、考えられる左側の境界ごとに右側の境界を拡張できます。 このようなウィンドウ内で、ゴールキーパー 1 人、ディフェンダー 2 人、フォワード 3 人を選択する方法が何通りあるかを数えるだけで済みます。 グループは独立しているため、これは組み合わせカウントの積になります。$C(g_i, 1) \cdot C(d_i, 2) \cdot C(f_i, 3)$窓の中、どこで$g_i, d_i, f_i$ウィンドウ内の各ロールの数です。 

残りの問題は、ウィンドウをスライドさせながらこれらのカウントを効率的に維持することです。 プレイヤーの総数は最大でも 1000 人であるため、ロール カウントのプレフィックス累積による 2 ポインタ アプローチは線形時間で機能します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべてのチームに対するブルートフォース |$O(g \cdot d^2 \cdot f^3)$|$O(1)$| 遅すぎる |
 | ソート + 2 つのポインター + 組み合わせ |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 すべての選手を役割別にタグ付けした後、一律に扱い、背番号順に並べ替えます。 

1. すべてのプレーヤーを番号順に並べ替え、各プレーヤーがゴールキーパー、ディフェンダー、またはフォワードであるかどうかを追跡します。 有効なチームが値の範囲に関して連続したウィンドウに対応するように、並べ替えが必要です。 
2. 左右の 2 本のポインタを維持します。 max ≤ 2 * min の条件が成立している間、右ポインタが展開されます。 配列はソートされているため、最小値が左側、最大値が右側になります。 
3. 左の位置ごとに、右ポインタが有効なままできるだけ右にあることを確認します。 これにより、左から始まるすべての有効な間隔が 1 回だけ考慮されることが保証されます。 
4. 現在のウィンドウ内で、各役割のカウント (g_count、d_count、f_count) を維持します。 
5. ウィンドウが g_count ≥ 1、d_count ≥ 2、f_count ≥ 3 を満たす場合、この正確なウィンドウで有効なチームを選択する方法は次のとおりです。$g\_count \cdot \binom{d\_count}{2} \cdot \binom{f\_count}{3}$。 
6. この投稿を回答に追加します。 
7. 左前方に移動する場合は、続行する前にカウントから一番左の要素を削除します。 

実装の重要な詳細は、事前計算された値を使用して組み合わせ値を効率的に計算する必要があることです。$nC2$そして$nC3$数式:$nC2 = n(n-1)/2$、$nC3 = n(n-1)(n-2)/6$。 

### なぜ効果があるのか

 有効なチームには、明確に定義された最小および最大の背番号があります。 条件はこれらの極値のみに依存するため、6 人のプレーヤー全員がその最小値と最大値によって定義される間隔内に位置する必要があります。 私たちのスライディング ウィンドウは、そのような間隔をすべて一度に正確に列挙します。 各間隔内では、すべての有効なチームは、その間隔内のカウントとは独立してロールを選択することによって一意に決定されるため、各ウィンドウ内の組み合わせをカウントすると、各有効なチームが 1 回だけカウントされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def c2(x):
    return x * (x - 1) // 2

def c3(x):
    return x * (x - 1) * (x - 2) // 6

def solve():
    g, d, f = map(int, input().split())
    
    arr = []
    
    for x in map(int, input().split()):
        arr.append((x, 0))  # goalie
    
    for x in map(int, input().split()):
        arr.append((x, 1))  # defender
    
    for x in map(int, input().split()):
        arr.append((x, 2))  # forward
    
    arr.sort()
    
    n = len(arr)
    ans = 0
    
    dg = dd = df = 0
    r = 0
    
    for l in range(n):
        while r < n and arr[r][0] <= 2 * arr[l][0]:
            if arr[r][1] == 0:
                dg += 1
            elif arr[r][1] == 1:
                dd += 1
            else:
                df += 1
            r += 1
        
        if dg >= 1 and dd >= 2 and df >= 3:
            ans += dg * c2(dd) * c3(df)
        
        # remove left element
        if arr[l][1] == 0:
            dg -= 1
        elif arr[l][1] == 1:
            dd -= 1
        else:
            df -= 1
    
    print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、すべてのプレーヤーをロール タグを持つ単一のリストにマージすることから始まります。 並べ替えにより、有効なチームが連続した数値セグメントに限定されるようになります。 2 ポインター拡張では、各左エンドポイントの最大有効範囲が維持されます。 

組み合わせ部分はローカライズされています。ウィンドウが固定されたら、位置を気にせずに、役割を選択する方法が何通りあるかだけを数えます。 の公式$C(n,2)$そして$C(n,3)$ネストされたループの繰り返しを避けます。 

微妙な点は、左ポインタを前方に移動しても右ポインタがリセットされないことです。 これは、配列がソートされており、制約が単調であるため有効です。左側の境界を縮小しても、将来の右側の拡張の有効性が高まるだけです。

 ## 特殊なケース

 数値制約が非常に厳しい場合、エッジ ケースが 1 つ発生します。 例えば：```
1 2 3
100
1 2
3 4 5
```ここで、有効なチームは狭い間隔内に存在する必要がありますが、その間隔内のロール数は依然として組み合わせ論を満たしている可能性があります。 このアルゴリズムは 2 * min までしか正しく拡張しないため、100 付近のウィンドウではそれより小さい値がすべて除外され、ゼロが寄与します。 

もう 1 つのケースは、多くのプレイヤーが有効範囲内にあるにもかかわらず、役割の配分が不十分な場合です。 例えば：```
1 5 0
10
1 2 3 4 5
```ディフェンダーがたくさんいるのに、フォワードがいなくなると貢献度がゼロになってしまいます。 このアルゴリズムは、組み合わせ式を適用する前にカウントのしきい値を明示的にチェックし、無効な寄与を防ぎます。 

最後の微妙なケースは、ウィンドウが有効であるにもかかわらず、左側の境界を縮小すると右側の境界の拡張が大幅に増加する場合です。 単調なポインタの動作により、すべての左位置が到達可能な最大の右境界を使用して正確に 1 回処理されるため、有効な間隔がスキップされることはありません。
