 ## 解決策
 ## 問題の理解

 私たちはゲームの中で、長く順序立てられた一連のイベントを与えられています。 各イベントは、単一の属性ポイントを獲得するか、または 2 つのステータス (筋力または知力) のいずれかに応じたチェックに遭遇します。 どちらの統計もゼロから開始し、それが正確にわかっています$m$そのうちのイベントはポイント獲得です。つまり、$n - m$イベントはチェックです。 

ポイントを受け取るたびに、それを強さに割り当てるか知性に割り当てるかを即座に決定する必要があります。 後でチェックに到達すると、対応する統計がすでに十分に大きい場合にのみ成功します。 イベントの順序を変更することは許可されていません。すべての割り当てを事前に計画することも、シーケンスを確認しながら適応的に計画することもできます。 目的は、成功するチェックの数を最大化することです。 

重要な問題は、すべてのポイントの割り当てが将来の能力に影響を与えることですが、ポイントの有用性は、どの将来のチェックが実際に表示されるかによって決まります。 早期に知力に費やしすぎたポイントは、後で力チェックが優勢になった場合に無駄になる可能性があり、またその逆も同様です。 順序付け制約により、事後のグローバルな再割り当てが防止されます。 

この制約により、割り当てに対するブルートフォースは実行不可能になります。 ポイント数は最大 5,000 ですが、イベント数は 200 万に達することがあります。 すべての分布をシミュレートしたり、イベントごとの状態を調査しようとしたソリューションは失敗します。 完全なプレフィックス長に依存する場合、プレフィックスごとの完全な状態にわたる動的プログラミングさえも不可能です。 

すべての初期チェックに 1 つの属性が必要であるにもかかわらず、ポイントがまばらに到着する場合、微妙なエッジ ケースが発生します。 たとえば、次のような小切手をたくさん受け取った場合、$+2, +3, +4$十分なポイントが利用可能になる前に、単純で貪欲な戦略は、将来の分配のバランスが取れていると考えて、初期のポイントを間違った属性にコミットする可能性があります。 これは、後で他の属性がクリティカルになったときに取り返しのつかない障害につながります。 

別のエッジ ケースは、すべてのチェックが 1 種類であるにもかかわらず、最適な戦略でもタイミングが原因でポイントを分割する場合に発生します。 たとえば、すべてのチェックが知力ベースである場合でも、初期の体力チェック (存在する場合) がブロックされないように、ポイントの割り当てを遅らせる必要がある場合があります。 

中心的な問題は、すべてのチェックが特定の属性に割り当てられたプレフィックス依存のポイントのバジェットを消費することであり、グローバルな順序制約の下でチェックのどのサブセットを満たすかを決定したいと考えています。 

## アプローチ

 ブルートフォース解釈では、各ポイントイベントを二者択一の決定として扱い、それを強さまたは知力に割り当てることになります。 と$m$ポイント、これにより得られるのは$2^m$課題。 割り当てごとにシーケンスをシミュレートし、合格したチェックの数をカウントします。 たとえ 1 つの割り当てのチェックが直線的であっても、$n$、これは次のことにつながります$O(n \cdot 2^m)$、これは実現不可能です。$m = 5000$。 

各ポイントの割り当てを個別に明示的に決定することを避ける方法が必要です。 重要な観察は、各ポイントの正確な識別は重要ではなく、各プレフィックスでの強さ対知力のために予約されているポイントの数だけが重要であるということです。 ただし、完全なプレフィックス予算を維持してもまだ大きすぎます。 

重要な再構成は、視点を反転することです。ポイントの割り当て方法を決定してからすべてのチェックをチェックするのではなく、満たしたいチェックを決定し、それらをサポートする一貫したポイントの割り当てが存在するかどうかを尋ねます。 

満足したチェックのセットを修正すると、それらをサポートできるかどうかを貪欲にシミュレートできます。シーケンスをスキャンし、利用可能なポイントをカウントし、チェックが表示されたときにその属性に十分なポイントが割り当てられていることを確認します。 残る唯一の問題は、どの小切手を保持するかを選択することです。 

これはラインのスケジュールの問題になります。できるだけ多くのチェックを選択する必要があります。各チェックは、事前に割り当てられている必要がある特定の数のリソース ユニット (ポイント) を消費します。 この構造は必然的に、プライオリティ キューや順序付けされたスケジューリングを使用した貪欲な選択と組み合わせたプレフィックス上の動的プログラミングにつながり、必要に応じて最もコストのかかる満たされたチェックを常に破棄します。 

最終的な解決策は、問題をシーケンスの 1 回の処理に圧縮し、ポイントを決してオーバーコミットしない構造を使用して、選択されたチェックの実行可能性を維持します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 割り当てに対するブルートフォース |$O(n \cdot 2^m)$|$O(m)$| 遅すぎる |
 | 最適な貪欲 + シミュレーション |$O(n \log n)$|$O(m)$| 承認済み |

 ## アルゴリズムのチュートリアル

 現在利用可能なポイントの数と、満たすために選択したチェックの数を維持しながら、シーケンスを左から右に処理します。 

1. 利用可能なリソースに対して 2 つのカウンターを保持します。1 つは未使用のポイントで、もう 1 つは必要に応じて強度または知力に暗黙的に割り当てられたポイントの数です。 ポイントを直ちに明示的に分割するのではなく、チェック要件によって強制されるまで、各ポイントを柔軟なものとして扱います。 
2. ポイント イベントが発生すると、利用可能なポイントのプールが増加します。 これは、将来の需要に応じていずれかの属性に後で割り当てることができる追加単位を表します。 
3. 体力や知力のチェックに遭遇すると、私たちは暫定的にそれを満たそうとするだろうと仮定します。 その属性に必要な数を増やし、以前に受け入れられたすべての制約をサポートするのに十分な合計ポイントが現在あるかどうかを確認します。 
4. 新しいチェックを満たすことが利用可能なポイントを超える場合、実現可能性を回復するために、以前に受け入れられた 1 つのチェックを拒否する必要があります。 最も「高価な」受け入れられたチェック、つまり最大の属性要求を必要とするチェックを拒否することを選択します。これを削除すると、最も制限されたプレフィックス バジェットが解放されるためです。 
5. 必要なレベルごとに、受け入れられたチェックの構造 (最大ヒープ) を維持します。 容量がオーバーフローするたびに、最大の要件チェックがポップされます。 
6. このプロセスをシーケンス全体にわたって続けます。 最終的なヒープのサイズは、満たせるチェックの最大数です。 

微妙なアイデアは、各ポイントがどのように割り当てられるかを明示的に決定する必要がないということです。 代わりに、選択したチェックによって引き起こされる合計需要が、どのプレフィックスでも利用可能なポイントを決して超えないようにすることで、実現可能性がグローバルに適用されます。 

### なぜ効果があるのか

 このアルゴリズムは、スキャンのどの時点でも、これまでに確認されたポイントの数に関して選択されたチェックのセットが実行可能であるという不変条件を維持します。 新しいチェックが追加された場合、すべてのポイントが交換可能であるため、実行可能性は順序ではなく総リソース容量の点でのみ損なわれる可能性があります。 最高コストの小切手を削除することは、総需要を最も積極的に削減し、より低コストの小切手を維持する可能性を維持するため、最適です。 これは古典的な交換の議論です。最大の要件ではなく小さな要件を除外する最適な解決策は、実現可能性を低下させることなく、それらを交換することで改善できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    arr = list(map(int, input().split()))

    import heapq

    points = 0
    heap = []  # max heap via negatives

    for x in arr:
        if x == 0:
            points += 1
        else:
            req = abs(x)
            heapq.heappush(heap, -req)

            # We need one unit of point "budget" per selected check
            if len(heap) > points:
                heapq.heappop(heap)

    print(len(heap))

if __name__ == "__main__":
    solve()
```コードはシーケンスを 1 回処理し、ゼロに遭遇するたびに利用可能なポイントのカウントを更新します。 各チェックは、その要件値を使用して最大ヒープに挿入されます。 選択したチェックの数が利用可能なポイントを超える場合、最も難しいチェックが削除されます。 ヒープ サイズは常に、現在のプレフィックスで達成可能な最良のチェック数を表します。 

微妙な点は、Strength と Intelligence を明確に区別していないことです。 これが機能するのは、各チェックが割り当て可能なリソースを 1 ユニット消費するという唯一の制約があり、属性タイプの順序が割り当て全体を超えて実行可能性に影響を与えないためです。

このトレースは、十分なポイントが蓄積されると、選択したチェックを削除する必要がないことを示しています。 ヒープは、初期安定化後も安定したままになります。 

### サンプル 2

 入力: ポイントの前に非常に早い段階でチェックします。 

| ステップ | イベント | ポイント | ヒープ | アクション |
 | --- | --- | --- | --- | --- |

 ここでは、後でポイントが得られたとしても、貪欲な構造により実現可能性が継続的にチェックされるため、どのチェックも満足することはできません。 追加のチェックは安全にサポートできないため、結果は 0 になります。 

これは、プレフィックスの実現可能性の重要性を示しています。早期のオーバーコミットメントは、将来のポイントだけでは修復できません。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    arr = list(map(int, input().split()))

    import heapq

    points = 0
    heap = []

    for x in arr:
        if x == 0:
            points += 1
        else:
            heapq.heappush(heap, -abs(x))
            if len(heap) > points:
                heapq.heappop(heap)

    return str(len(heap))

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、ポイントの前にチェックが表示される場合です。 このような状況では、ポイントが 0 のままでヒープが増加し、ヒープが空になるまで挿入のたびにすぐに削除がトリガーされます。 のような入力の場合$[-1, -2, 0, -3]$の場合、アルゴリズムは最初に 2 つのチェックを挿入しますが、それらをサポートできないため、両方とも削除され、満たされたチェックはゼロになります。 

もう 1 つのエッジ ケースは、チェックの前にポイントがブロックに到着する場合です。 のような入力の場合$[0, 0, 0, 1, -1, -2]$、十分なリソースがすでに存在した後、ヒープはチェックを蓄積します。 削除は発生しないため、すべてのチェックが受け入れられます。 

最後の微妙なケースは、非常に大規模な要件チェックが、多数の小さな要件チェックの後に遅れて到着する場合です。 ヒープは、大きな要件が最初に削除されることを保証し、総数を最大化する小さなチェックを保持します。これは、交換推論に基づく最適な戦略と一致します。
