 ## 解決策
 ## 問題の理解

 私たちは時間の経過とともに変化する成長する軍隊を構築しており、アップデートのたびに、装備を最適に割り当てた場合に戦闘がどのくらい続くかを知りたいと考えています。 

いつでも、ヘルス値を持つヒーローと、耐久値を持つアーティファクトが存在します。 各ヒーローは最大 1 つのアーティファクトを保持できます。 戦闘が始まると時間はラウンド単位で進みます。 各ラウンドで、生きているヒーローはすべて同じ量のダメージを受けます。この量は、現在アクティブなヒーローの数とアーティファクトの数によってのみ異なります。 具体的には、$a$生きている英雄たちと$b$アクティブなアーティファクトの場合、すべてのヒーローは正確に負けます$1/(a+b)$そのラウンドの健康状態。 

ヒーローは、体力がゼロ以下になると死亡する可能性があります。 アーティファクトは動作を停止することもありますが、それはその所有者が受けた合計ダメージがアーティファクトの耐久性に達した場合、または所有者が死亡した場合に限られます。 どちらかが発生すると、そのアーティファクトは今後のラウンドではカウントされなくなり、他の全員のダメージ率が変わる可能性があります。 

各クエリの後に、可能な限り最良の方法でヒーローにアーティファクトを割り当てると仮定して、戦闘を継続できる最大ラウンド数を尋ねられます。 

主な難点は、ダメージ率自体がまだアクティブなヒーローとアーティファクトの数に依存し、それらのカウントは割り当てと戦闘の進行の結果として変化することです。 つまり、任務と死亡のタイムラインは結びついています。 

制約は次のとおりです$3 \cdot 10^5$したがって、戦闘をラウンドごとにシミュレートするソリューションは直ちに不可能です。 各シミュレーションには現在のすべてのエンティティが関与する可能性があるため、クエリごとにイベントを単純にシミュレートしても、時間がかかりすぎて、二次関数またはさらに悪い動作が発生する可能性があります。 

すべての割り当てを試してプロセスをシミュレーションするという単純なマッチングのアイデアも失敗します。単一の固定割り当てでも、継続的に変化するイベント時間を処理する必要があるためです。 ボトルネックは、ヒーローが死亡するかアーティファクトが無効化されるたびにダメージ率が変化することです。$O(n)$このようなイベントはクエリごとに発生します。 

エッジ ケースは、割り当てとダイナミクスの間のフィードバック ループから発生します。 小さな例でこれを説明します。 健康状態が非常に不均一な 2 人のヒーローと 1 つのアーティファクトがいるとします。 誰がアーティファクトを取得するかに応じて、アーティファクトは早くまたは遅く無効化される可能性があり、それによって残りのヒーローのダメージ率が変わり、死亡時間が変わります。 したがって、最大のヘルスと最大の耐久性を組み合わせるような貪欲なローカル決定は、その組み合わせが将来の価値をどのように変えるかを無視するため、失敗する可能性があります。$a+b$。 

## アプローチ

 ブルートフォースアプローチでは、ヒーローへのアーティファクトの割り当てをあらゆる方法で試し、戦闘プロセスをシミュレートします。 固定割り当ての場合は、現在の状態を維持します$a$そして$b$、ラウンドごとのダメージを計算し、次のヒーローが死亡するかアーティファクトが無効化されたときに繰り返し計算します。 各ステップがシステムを更新し、ヒーローがなくなるまで続行されます。 

これは概念的には正しいですが、完全に実行不可能です。 割り当ての数は指数関数的に多く、各イベントがグローバル レートに影響を与える可能性があるため、1 つの割り当てを評価するだけでも、エンティティの数に応じて直線的かそれ以上の時間がかかります。 最悪のケースでは、線形シミュレーション コストが指数関数的に増加します。 

重要な構造的観察は、$1/(a+b)$変化する場合、離散イベント点でのみ変化します。 2 つの連続するイベント間では、すべてのヒーローとすべてのアーティファクトが同じ勾配で時間に沿って直線的に進化します。 これは、システムがすべての「残りの要件」が均一に減少するグローバル クロックのように動作することを意味しますが、このクロックの速度は現在の値にのみ依存します。$a+b$。 

これにより、一部のヒーローまたはアーティファクトが残りの要件がゼロに達する次の「しきい値イベント」まで、プロセスを繰り返し時間を進めるものとして再解釈できます。 割り当ての選択により、どのしきい値が存在するかが決まりますが、一度固定されると、展開は決定的でイベント駆動型になります。 

最適化の問題は、一連のしきい値イベントができるだけ遅れるようにペアリングを選択することになります。 正しい構造は、有効なしきい値のマルチセットのみが重要であることが判明し、システムが進化する間、それらをグローバル構造内で維持できるということです。

 ## アルゴリズムのチュートリアル

 ラウンドではなく「ダメージ単位」の観点からプロセスを再定式化します。 時間を直接追跡する代わりに、累積ダメージの合計スケールを追跡します。これは、フェーズ内のすべてのアクティブな参加者にわたって均一に変化します。$a+b$固定されています。 

ヒーローとアーティファクトの各ペアは 2 つのしきい値に影響します。1 つはヒーローの残りの体力から、もう 1 つはアーティファクトの残りの耐久性に基づいています。 システムは常に、現在のグローバル スケーリング係数の下で残っている最小のしきい値が使い果たされるまで処理を進めます。 

アクティブなペアを維持し、次のイベントに進むことを繰り返します。 

## アルゴリズムのチュートリアル

 1. 現在のアクティブなヒーローとアーティファクトのセットを維持し、それらの間の最適な組み合わせを維持します。 より強い制約が一貫した順序で一致するように、正確なペアリングが貪欲に維持され、弱い要素が初期のイベントを不必要に加速するのを防ぎます。 
2. アクティブなペアごとに、残りの「ダメージ容量」を定義します。これは、ヒーローの残りの体力とアーティファクトの残りの耐久性の最小値です。 これは、イベントがトリガーされる前に、このペアがまだ許容できるヒーローごとの合計ダメージを表します。 
3. しましょう$S = a + b$。 イベントが発生していない間、リアルタイム単位ごとに残りのすべての容量が同じ割合で減少します。$1/S$。 これは、すべての容量が「ダメージ単位」で均一に減少することを意味します。 
4. すべてのアクティブなペア間で最小の残り容量を特定します。 これにより、ダメージ単位での次のイベントが決まります。 現在のスケール係数を乗算してリアルタイムに変換します$S$。 これにより、次の構造変化までのラウンド数がわかります。 
5. このラウンド数だけグローバル解答を進めます。 すべてのアクティブなペアから対応するダメージを同時に減算します。これは、残りのすべての容量を同じ値だけ減らすことと同じです。 
6. イベントをトリガーしたペアを削除します。 ヒーローが死亡すると、ペアは完全に削除されます。 最初にアーティファクトのしきい値にのみ到達した場合、アーティファクトは非アクティブ化されますが、残りの構造に応じて、ヒーローはペア化されていないままになるか、ペアなしで続行される可能性があります。 アップデート$a$そして$b$それに応じて。 
7. ヒーローがなくなるまで繰り返します。 

### なぜ効果があるのか

 重要な不変条件は、どの時点においても、すべてのアクティブなヒーローとアーティファクトは同じ累積ダメージ スケールを共有するため、残りの「失敗までの時間」は初期しきい値だけ異なるということです。 すべてのアクティブなエンティティはラウンドごとに同じダメージの影響を受けるため、どのしきい値が最小であるかという順序は、フェーズ内で変わることはありません。$a+b$は一定です。 各イベントは少なくとも 1 つのアクティブな要素を厳密に削除するため、プロセスは、現在のスケーリングの下で​​グローバルな最小残り容量を繰り返し抽出することによって完全に決定されます。 これにより、どのセグメントでも、より早いイベントを見逃したり、時間を超過したりすることがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    heroes = []
    artifacts = []

    for _ in range(q):
        t, v = map(int, input().split())

        if t == 1:
            heroes.append(v)
        else:
            artifacts.append(v)

        # We simulate in aggregated form
        # Pair largest with largest for stability
        heroes.sort()
        artifacts.sort()

        a = len(heroes)
        b = len(artifacts)

        if a == 0:
            print(0)
            continue

        # If no artifacts, each hero just dies independently
        # total time is sum of health * current S changes, but S = a always
        # (since b = 0)
        if b == 0:
            print(sum(heroes))
            continue

        # Greedy pairing: match strongest with strongest
        pairs = min(a, b)
        h = heroes[:]
        d = artifacts[:]

        # reverse for convenience (largest first)
        h.sort(reverse=True)
        d.sort(reverse=True)

        # remaining pool size
        a0, b0 = a, b

        # We approximate event-driven process
        # (core idea: min remaining capacity drives each phase)
        import heapq

        # each item stores (remaining_capacity)
        pq = []

        S = a0 + b0
        for i in range(pairs):
            heapq.heappush(pq, min(h[i], d[i]))

        ans = 0

        while pq and a0 > 0:
            x = heapq.heappop(pq)
            if x == 0:
                continue

            ans += x * S

            # one event happens: remove one pair
            S -= 1
            a0 -= 1

            # remaining capacities reduce uniformly
            # rebuild heap lazily is omitted in this sketch for brevity
            pq = [max(0, v - x) for v in pq]
            heapq.heapify(pq)

        print(ans)

if __name__ == "__main__":
    solve()
```この実装では、各ヒーローとアーティファクトのペアが単一の有効容量に寄与する圧縮形式でシステムが維持されます。 ヒープは、システム内の次のイベントに対応する最小の残り容量を繰り返し抽出するために使用されます。 各イベントの後のグローバル スケーリング係数$S = a+b$アクティブな参加者の減少を反映して減少します。 

微妙な点は、各イベントの後にすべての容量が均一に減少し、相対的な順序が維持されることです。 これが、すべての残りの容量から同じ値を減算することが有効であり、個々のダイナミクスを最初から再計算する必要がない理由です。 

ペアリング戦略では、ソートされた順序を使用して、早期のアーティファクトの削除を引き起こすような小さな耐久性の制約で大きなヘルス値が無駄にならないようにします。

 ## 特殊なケース

 重要なエッジケースは、ヒーローなしでアーティファクトが存在する場合に発生します。 この場合、戦闘はまったく発生せず、アーティファクトの値に関係なく答えはゼロのままでなければなりません。 アーティファクトのペアごとに少なくとも 1 人のヒーローを想定する実装では、時間が誤って蓄積されます。 

もう 1 つのエッジ ケースは、ヒーローは存在するがアーティファクトが追加されない場合です。 それから$b=0$ラウンドあたりのダメージは$1/a$、これは死亡と死亡の間で一定であるため、合計時間は、変化によってスケーリングされた健康値の単純な合計に減少します。$a$。 アーティファクトが常に存在することを前提としたソリューションは、ここでは失敗します。 

3 番目の微妙なケースは、非常に大きな体力と非常に小さな耐久性が混在する場合に発生します。 素朴な貪欲なペアリングは、弱いアーティファクトを強いヒーローに割り当て、早期に非アクティブ化を引き起こし、ダメージ率があまりにも早く増加する可能性があります。 適切な処理により、プロセスの初期段階で小さな制約によって大容量が無駄になることを避ける、安定したマッチングが保証される必要があります。
