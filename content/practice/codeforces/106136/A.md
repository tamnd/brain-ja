 ## 解決策
 ## 問題の理解

 私たちには、小規模な ICPC チームと、コンテストでチームが獲得したメダルの数の記録が与えられます。 金、銀、銅の各メダルは固定賞金プールに対応しており、金はチームあたり 7,500 元、銀はチームあたり 3,000 元、銅はチームあたり 1,500 元の価値があります。 チームのメンバーは最大 3 名で、チームが獲得した賞金の総額はすべてのメンバーに均等に分配されます。 

このタスクは、チームの規模と各メダルの種類の数を考慮して、特定のメンバーが受け取る金額を計算することです。 

入力には、チームの規模とそれに続く金、銀、銅のメダルの数の 4 つの整数が含まれます。 出力は、賞金総額に対する 1 人のメンバーの取り分を表す単一の整数です。 

制約は非常に小さいです。 チームの人数は最大 3 人、メダルの総数は最大 7 個です。これにより、最適化テクニックや慎重なデータ構造さえも必要なくなります。 すべての演算は定数時間演算です。 

すべての値は整数であり、割り算は構造上正確であるため (意図した解釈では、賞金総額は常にチームの規模で割り切れます)、主な落とし穴は、精度を失ったり割り算の順序を混同したりすることなく、単純に算術を正しく実装することです。 

いくつかの特殊なケースは依然として注目に値します。 

エッジケースの 1 つは、メダルがまったくない場合です。 たとえば、入力`2 0 0 0`譲るべきだ`0`, 賞金総額はゼロなので。 

もう 1 つは、チームのサイズを可能な限り小さくすることです。 例えば、`1 1 0 0`何も分割されないため、金賞の 7500 全額を返還する必要があります。 

3 つ目は、整数の除算が早すぎて計算が正しくなかった場合、賞金が均等に分割されない場合です。 たとえば、合計する前に各メダル賞品を誤って各人に個別に分割すると、浮動小数点エラーや切り捨てエラーが発生する可能性があります。 正しいアプローチは、最初に賞金総額を計算してから、一度除算することです。 

## アプローチ

 ここでは強引な解釈はほとんど必要ありませんが、それでも各メダルイベントをシミュレートし、チームメンバーごとに賞金を蓄積すると説明できます。 金メダルごとに累計に 7500 を加算し、銀メダルごとに 3000 を加算し、銅メダルごとに 1500 を加算し、最後にチームの規模で割ります。 

各メダル報酬を直ちにメンバー間で分配するという誤った考えがあったとしても、最悪の場合の操作数は依然としてメダルの数に制限されており、最大でも 7 です。したがって、すべてのメダル イベントの文字通りのシミュレーションさえも簡単です。 

重要な観察は、問題は純粋に相加的かつ線形であるということです。 メダルが処理される順序は重要ではなく、メダル間の相互作用はありません。 これにより、加重和を計算し、最後に 1 回除算するだけで済みます。

 ## アルゴリズムのチュートリアル

 1. チームの規模と金、銀、銅のメダルの数を表す 4 つの整数を読み取ります。 これにより、計算に必要なすべての入力が 1 つのステップで確立されます。 
2. チームが獲得した賞金の合計を加重合計として計算します。各金メダルは 7500、各銀メダルは 3000、各銅メダルは 1500 となります。このステップにより、コンテスト履歴全体が 1 つのスカラー値にまとめられます。これは、各メダルが独立して貢献するため有効です。 
3. 賞金総額をチームの規模で割ります。 チームは賞金を均等に分配するため、各メンバーが受け取る金額が計算されます。 
4. 結果を整数として出力します。 

### なぜ効果があるのか

 賞品システムはメダル数に対して直線的です。 各メダルは報酬総額に対して固定の独立した金額を寄与し、分割操作は最終的な合計に 1 回適用されます。 合計後に除算が適用されるため、分配性により、各メダル報酬をメンバー間で均等に分配して合計した場合と同等の結果が得られます。 これにより、順序付けやグループ化の影響によって最終的な答えが変わることがないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, g, s, b = map(int, input().split())

total = g * 7500 + s * 3000 + b * 1500
print(total // n)
```このソリューションは入力を 1 行で読み取り、すぐに 4 つの整数を解凍します。 賞金総額はカウントとそれぞれの値の直接乗算を使用して計算され、ループが回避されます。 

除算は整数除算を使用して最後に行われます。 すべての賞金の値は 500 の倍数であり、問​​題の定義に基づいて除算が正確になるように意図されているため、これは安全です。 使用する`//`整数演算を維持し、浮動小数点の問題を回避します。 

よくある間違いは、合計する前に各メダルの貢献を個別に分割することです。 ここでも数学的には機能しますが、より一般的な問題で丸め誤差の不必要なリスクが生じ、意図した構造がわかりにくくなります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline
    n, g, s, b = map(int, input().split())
    total = g * 7500 + s * 3000 + b * 1500
    return str(total // n)

# provided samples
assert run("3 2 1 2") == "7000", "sample 1"
assert run("1 0 0 4") == "6000", "sample 2"

# custom cases
assert run("1 0 0 0") == "0", "no medals"
assert run("3 0 0 0") == "0", "team with no reward"
assert run("2 1 1 1") == str((7500 + 3000 + 1500)//2), "mixed medals"
assert run("3 7 0 0") == str((7*7500)//3), "max gold case"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 0 0 0 | 0 | 報酬ゼロのエッジケース |
 | 3 0 0 0 | 0 | チーム分けでメダルなし |
 | 2 1 1 1 | 6000 | 混合メダル集計 |
 | 3 7 0 0 | 17500 | 最大のゴールド境界 |

 ## 特殊なケース

 入力用`3 0 0 0`の場合、アルゴリズムは賞金総額をゼロとして計算し、3 で割ってゼロを生成します。 これは、分子がゼロの場合、除算ステップでアーチファクトが発生しないことを確認します。 

のために`1 0 0 4`、計算では、除算前に 6000 が得られます。 チーム サイズは 1 であるため、除算では値は変更されず、最小チーム サイズが正しいことが確認されます。 

のために`3 7 0 0`、賞金総額は`7 × 7500 = 52500`、および除算の結果`17500`。 これは、アルゴリズムが Python でオーバーフローを考慮せずに最大メダル数を処理し、最後に整数の除算を正しく適用していることを示しています。
