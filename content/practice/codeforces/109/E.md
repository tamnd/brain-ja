 ## 解決策
 ## 問題の理解

 から始まる連続する整数の間隔が与えられます。`a`そして長さがある`l`。 あらゆる数字について`x`、 定義する`F(x)`10 進表現内の幸運の数字の数として。 数字のみ`4`そして`7`幸運だと考えられています。 

タスクは最小の整数を見つけることです`b > a`シーケンスが`F(a), F(a+1), ..., F(a+l-1)`と全く同じです`F(b), F(b+1), ..., F(b+l-1)`。 

言い換えれば、一定期間にわたる幸運の数字のカウントのパターンは、次から始まるように繰り返す必要があります。`b`。 

の値`a`そして`l`と同じくらい大きい`10^9`、これにより、巨大な範囲を直接スキャンするアプローチは即座に除外されます。 区間内のすべての数値を 1 回繰り返すことさえ、最悪の場合はすでに不可能です。`l`それ自体は10億かもしれません。 関数内の構造を活用する必要がある`F(x)`数値ごとに個別に評価するのではなく。 

重要な観察は、`F(x)`10 進数のみに依存します。 多くの場合、上位の数字を変更すると、大きな連続ブロックにわたって幸運の数字のカウント パターンが保持されます。 問題は、桁の動作が正確に一致する別の間隔を構築することになります。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

考慮する：```
a = 7, l = 1
```最小のものが必要です`b > 7`と`F(b) = F(7) = 1`。 答えは`14`、 ない`17`、 なぜなら`14`すでに幸運の数字が 1 つあります。 幸運な数字の中だけを検索するソリューションは失敗します。 

もう 1 つの注意が必要なケースは、間隔が 10 のべき乗の境界を越える場合です。```
a = 98, l = 5
```順序は次のとおりです。```
F(98)=0
F(99)=0
F(100)=0
F(101)=0
F(102)=0
```多くの数値はすべて 0 を生成しますが、単純な 10 乗でシフトすると、キャリーに幸運な数字が誤って含まれる可能性があります。 この問題における主な危険はキャリーの伝播です。 

より微妙な例は次のとおりです。```
a = 447, l = 3
```順序は次のとおりです。```
3, 1, 1
```なぜなら：```
447 -> three lucky digits
448 -> one lucky digit
449 -> one lucky digit
```不用意に数字を置換すると、最初の値は保持されますが、隣接する数字間のローカルな遷移動作が破壊される可能性があります。 

全体的な課題は、間隔全体にわたってキャリーが幸運の数字にどのように影響するかを維持することです。 

## アプローチ

 ブルートフォースのアイデアは単純です。 シーケンスを計算する```
S(i) = F(a+i)
```みんなのために`0 <= i < l`、次に増加する値を検索します。`b`同じシーケンスが再び現れるまで。 

これが機能するのは、定義が直接的であり、等価性のチェックが簡単であるためです。 残念ながら、絶望的に遅くなります。 最悪の場合`l = 10^9`, したがって、元のシーケンスを一度生成することさえ不可能です。 の検索スペース`b`も無制限です。 

重要な洞察は次のとおりです`F(x)`は桁ごとに決定され、桁上げが特定の位置に到達しない場合、10 進加算は周期的に動作します。 

区間内のすべての数値に十分大きな 10 の累乗を加算するとします。 作成された加算が下位桁にキャリーを作成しない場合、区間内のすべての数値の下位桁は変更されません。 変更されるのは上位 1 桁だけであり、その桁を選択してどちらにもならないようにすることができます。`4`または`7`。 その後、幸運の数字の数は同じままになります。 

これにより、問題はシーケンスの明示的な一致から安全なシフトの構築へと変換されます。 

危険なのはキャリー伝播です。 追加すると`10^k`上位ブロックが近い番号に`999...9`、キャリーが下に波紋を起こし、多くの桁が変更される可能性があります。 これを回避するには、間隔が 1 つのサイズのブロック内に完全に収まる小数点位置を見つける必要があります。`10^k`。 

具体的には、最小のものを探索します。`10^k`次のような:```
a / 10^k == (a + l - 1) / 10^k
```間隔全体が単一の長さのブロック内にあることを意味します`10^k`。 

次に正確に追加します`10^k`そのブロックの上の数字のみを変更し、下位の数字は残します`k`間隔全体で数字は変わりません。 変更した数字が1つ増えるので、その数字が大きくなった場合のみラッキーカウントが変わります。`4`または`7`、または以前は`4`または`7`。 

繰り返し追加できます`10^k`変更された数字が幸運な遷移を回避するまで。 変更されるのは 1 桁だけなので、次の 4 つのケースを回避するだけで済みます。```
3 -> 4
4 -> 5
6 -> 7
7 -> 8
```他のすべての増分では、ラッキー カウントが保持されます。 

これにより、一定時間の建設的な解決策が得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(l × 探索範囲) | O(l) | 遅すぎる |
 | 最適 | O(桁数) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. しましょう`r = a + l - 1`、間隔の最後の番号。 
2. 最小の電力を見つける`p = 10^k`次のような:```
a / p == r / p
```これは、間隔全体が 1 つのサイズのブロック内に収まることを意味します。`p`。 
3. 次のようにしましょう。```
prefix = a / p
```これは、区間内のすべての数値で共有される上位部分です。 
4. 低い値を維持しながら、このプレフィックスを増やしたいと考えています。`k`桁は変わりません。 各候補シフトは次のとおりです。```
b = a + t * p
```何らかの正の整数の場合`t`。 
5. プレフィックスを 1 つ増やすと、最後の 10 進数のみが変更されます。 ラッキー カウントは、その桁の遷移が次のいずれかの場合にのみ変更されます。```
3 -> 4
4 -> 5
6 -> 7
7 -> 8
```6. から始める`prefix + 1`、から増加する最初の値を見つけます。`prefix`プレフィックス内の幸運の数字の数は変更されません。 
7. 選択した新しいプレフィックスを次のようにします。`np`。 次に、次のように構築します。```
b = np * p + (a % p)
```8. 出力`b`。 

### なぜ効果があるのか

 下のほう`k`間隔が次の倍数にまたがることがないため、間隔内のすべての数値の桁は変更されません。`p`。 の倍数を追加する`p`上位の桁のみを変更します。 

オフセットごとに`i`間隔内:```
a+i = prefix * p + low(i)
b+i = np * p + low(i)
```どこ`low(i)`は両方の式で同じです。 

下の部分からの幸運桁の寄与はまったく同じです。 私たちが選ぶ`np`となることによって`F(prefix) = F(np)`、つまり、より高い部分も同じ数の幸運な数字に貢献します。 したがって、次のようになります。```
F(a+i) = F(b+i)
```インターバル全体にわたって。 

候補プレフィックスを昇順にテストするため、最小性が続きます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def lucky_count(x: int) -> int:
    cnt = 0
    while x:
        d = x % 10
        if d == 4 or d == 7:
            cnt += 1
        x //= 10
    return cnt

def solve():
    a, l = map(int, input().split())

    r = a + l - 1

    p = 1
    while a // p != r // p:
        p *= 10

    prefix = a // p
    low = a % p

    target = lucky_count(prefix)

    np = prefix + 1
    while lucky_count(np) != target:
        np += 1

    b = np * p + low

    print(b)

if __name__ == "__main__":
    solve()
```最初の部分では最小のブロック サイズを計算します。`p`間隔が完全に 1 つのブロック内に収まるようにします。 これが問題の核となる構造的観察です。 このようなブロックが存在すると、下位の桁はすべて、次の倍数でシフトしても安定します。`p`。 

機能`lucky_count`数はせいぜい周囲にあるため、小さいです`10^10`, したがって、最大でも 10 桁になります。 

変数`prefix`は、間隔全体で共有される上位の桁を表します。 同じ幸運の数字の数を持つ、最も小さくて大きなプレフィックスを検索します。 桁数が小さいため、このローカル検索をブルートフォース攻撃しても完全に安全です。 

再構築:```
b = np * p + low
```下位桁を正確に保持します。 これは微妙な部分です。 のみを使用する`a + t*p`直接は数学的に同等ですが、部分から数値を再構築すると不変式が明示的になります。 

よくある間違いは選択です`p`間違っています。 条件は、単に間隔を保証するだけでなく、間隔全体が 1 つのブロック内に収まることを保証する必要があります。`a`それ自体は境界に一致します。 それ以外の場合は、間隔内の一部の値の下位桁にキャリーが表示されます。 

もう 1 つのよくあるバグは、次のことを忘れることです。`prefix`ゼロかもしれない。 ゼロには幸運の数字が含まれていないため、ヘルパーはこれを正しく処理します。

import io

def solve_io(inp: str) -> str:

    input = sys.stdin.readline

    def lucky_count(x: int) -> int:
        cnt = 0
        while x:
            d = x % 10
            if d == 4 or d == 7:
                cnt += 1
            x //= 10

    r = a + l - 1

    target = lucky_count(prefix)

    np = prefix + 1
    while lucky_count(np) != target:
        np += 1

    b = np * p + low

    return str(b)

 ## 特殊なケース

 次のことを考慮してください。```
1 1
```我々は持っています：```
F(1)=0
```幸運の数字が 0 の最も大きい数字は次のとおりです。`2`。 

アルゴリズムは以下を計算します。```
p=1
prefix=1
target=0
```するとすぐに次のものが見つかります。```
np=2
```そして出力`2`。 

次にキャリー境界の場合を調べます。```
98 5
```間隔は 2 桁から 3 桁になります。```
98,99,100,101,102
```による素朴なシフト`10`次の理由で失敗します:```
108
```キャリーにより、間隔の後半に幸運の数字が導入されます。 

代わりに、アルゴリズムは以下を選択します。```
p=100
```間隔全体が 1 つのサイズのブロック内に収まるため`100`。 

これにより、区間内のすべての要素に対してサフィックスが安定した状態に保たれます。 

最後に、次のことを考慮してください。```
447 3
```移行:```
447 -> 448
```～からのラッキーカウントを落とす`3`に`1`。 

下位の桁を個別に変更すると、このローカルな動作はすぐに壊れてしまいます。 

アルゴリズムはサフィックス全体を保持します`7,8,9`したがって、同じ遷移パターンが新しい間隔に自動的に表示されます。
