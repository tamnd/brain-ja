 ## 解決策

 ## 問題の理解

 従業員 1 がルートとなる、ルート付きツリーを形成する会社階層が与えられています。 他のすべての従業員には 1 人の直属のマネージャーがいるため、各ノードには親ポインターがあり、構造には循環がありません。 ノードのサブツリーは、監督下にあるすべての従業員を表します。 

時間の経過とともに、従業員は休暇に出たり戻ったりを繰り返します。 いつでも、各従業員はグローバルな「休暇セット」に参加するか参加しないかのどちらかです。 各マネージャーにとって重要なのは、何人の部下 (自分を除くサブツリー内のノード) が現在休暇中であるかです。 

各従業員には許容値があります。 サブツリー内の休暇中の部下の数がこの許容範囲を超え、部下自身が休暇を取っていない場合、その従業員は不満を抱きます。 

このタスクは動的です。各イベント (1 人の従業員が休暇に行く、または戻る) の後に、現在不満を抱いている従業員の数を出力する必要があります。 

この制約により、100,000 ノードのツリー上で最大 100,000 件の更新を処理する必要があります。 イベントごとに最初から再計算するには、すべてのサブツリーを走査する必要があり、およそ O(nm) となり、実現可能な制限をはるかに超えています。 最悪の場合、操作ごとに O(n log n) であっても遅すぎる可能性があります。 ソリューションでは、慎重に選択された構造上で、各更新を対数または償却定数作業に近い値に削減する必要があります。 

従業員のサブツリーが大きいものの影響がまばらである場合、微妙なエッジ ケースが発生します。 たとえば、リーフ ノードのみが頻繁に切り替わる場合、単純な DFS 再計算では、たとえ少数のカウンターしか変更されなかったとしても、サブツリー全体を繰り返し走査することになります。 

もう 1 つの注意が必要な状況は、先祖が休暇中であるかどうかに応じて、更新が与える影響が異なる場合です。 単純なアプローチでは、従業員自身が休暇中である場合でも、従業員が不機嫌であると誤ってマークされる可能性があります。その場合、ルールでは従業員のカウントが明示的に免除されているためです。 この依存関係により、ノードごとの状態を維持しないとローカル更新が不十分になります。 

## アプローチ

 直接シミュレーションでは、各イベントの後に、すべてのサブツリー内の休暇中のノードの数が再計算されます。 各従業員について、サブツリーをたどってアクティブな休暇をカウントし、しきい値と比較します。 これは正しいですが、高価です。 各更新のコストは O(n) で、m 回の更新で合計は O(nm) となり、最悪の場合で約 10¹⁰ の操作になります。 

重要な観察は、完全なサブツリーの再計算が決して必要ないということです。 各更新では、単一ノードの休暇ステータスのみが変更されます。 ノードの切り替えの効果は、ルートとリーフの関係に沿ってローカルに行われます。そのノードのすべての祖先は、その「休暇中の従属の数」が 1 だけ増加または減少するのを確認します。 

したがって、サブツリー数を再計算する代わりに、すべてのノードについて、そのサブツリー内の休暇中のノードの現在の数を維持します。 各イベントは、切り替えられたノードのすべての祖先に沿ってこのカウンターをインクリメントまたはデクリメントするポイント更新です。 残りの課題は、すべての祖先を効率的に特定して更新することです。 

私たちは、サブツリー集約をサポートする構造と組み合わせた親ポインターを通じて実装された、ノードからルートまでのパスのヘビーライト スタイルの分解を使用してこれを解決します。 より効率的な定式化は、ツリーのオイラー ツアーでサブツリーの更新を範囲の更新に変換することです。この場合、各サブツリーは連続したセグメントになります。 

オイラー ツアー順序では、すべてのサブツリーが区間に対応します。 単一の位置での +1 または -1 の追加、およびサブツリー間隔内の合計アクティブ数のクエリをサポートするグローバル構造を維持します。 これは、フェンウィック ツリー (BIT) を使用して実行できます。 各更新は 1 つの位置に触れ、各サブツリー クエリは範囲の合計になります。

ただし、各ノードが現在不満を抱いているかどうかを知る必要があります。 ノードが休暇中でなく、そのサブツリー内のアクティブな休暇ノードの数がしきい値を超えている場合、そのノードは不満を感じます。 重要な洞察は、更新されたノードからルートまでのパス上のノードのみがサブツリー数を変更できるが、BIT を使用して明示的にそのパスをたどることを避けているということです。 

サブツリー数が変化したときに条件が満たされたノードから違反されたノード、またはその逆に遷移するノードのみを追跡することにより、「現在不良なノード」のセットを維持します。 サブツリー数は更新ごとに ±1 ずつ変化し、範囲構造を通じて暗黙的にすべての先祖に影響を与えるため、プレフィックス合計を使用して必要な場合にのみ変更を計算し、しきい値超過検出のための補助構造を維持します。 実際には、アクティブ数の BIT を維持し、サブツリーの合計がしきい値の境界を超えて変化した場合にのみ、影響を受ける各ノードの状態を再計算します。 

各ノードの「不良ステータス」は、そのサブツリー数がちょうど 2 つの臨界値 t_i と t_i + 1 を超えた場合にのみ変化するため、この構造は効率的になります。

 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | O(n) | 遅すぎる |
 | しきい値追跡を備えたオイラー ツアー + BIT | O((n + m) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ノードのすべてのサブツリーが連続した区間に対応するように、ツリーをオイラー ツアーに変換します。 これにより、サブツリー操作を配列に対する範囲クエリとして扱うことができます。 
2. オイラー次数配列上にフェンウィック ツリーを構築します。 各位置は、ノードが現在休暇中 (1) かそうでないか (0) を表します。 ツリーは、ポイントの更新とプレフィックスの合計をサポートします。 
3. 配列を維持する`on[i]`従業員 i が現在休暇中かどうかを示します。 
4. 各ノードのオイラーエントリ時間とサブツリー間隔を事前計算します。`[tin[i], tout[i]]`。 この間隔は、そのサブツリーを正確にキャプチャします。 
5. 各ノードについて、現在のサブツリー休暇数をフェンウィック範囲の合計として計算します。`[tin[i], tout[i]]`。 
6. グローバルカウンターを維持する`bad_count`現在不満を抱いている従業員の割合。 
7. すべてのノードを休暇なしで初期化し、すべてのサブツリー数が 0 になるようにします。`bad_count`ゼロから始まります。 
8. ノード v が休暇ステータスを切り替えるイベントごとに、次のようにします。 

1.アップデート`on[v]`。 
2. 位置に +1 または -1 を追加します`tin[v]`フェンウィックの木の中。 
3. これにより、v のすべての祖先のサブツリーの合計が暗黙的に変更されます。 
4. サブツリー範囲がこの変更によって影響を受けるノードのみについて条件を再計算します。 祖先のサブツリーの合計のみが変化するため、v のルート パスに沿ったノードのみをチェックします。 
5.アップデート`bad_count`それに応じて、ノードがしきい値を超えたとき、またはノード自体が休暇を開始または停止したときも同様です。 

重要な効率は、各サブツリー合計の更新が対数的であり、各ノードの状態変化がその集計合計がしきい値の境界を超えた場合にのみ検出されるという事実から来ています。 

### なぜ効果があるのか

 各ノードの状態は、休暇中かどうかと、そのサブツリー内にアクティブな休暇がいくつあるかという 2 つの値のみに依存します。 オイラー ツアーにより、サブツリー集約が範囲合計の問題になることが保証されます。 フェンウィック ツリーは、ポイント更新の下でこれらの合計を維持します。 各更新は 1 つのリーフ位置にのみ影響しますが、暗黙的にすべての祖先範囲に伝播するため、すべてのサブツリーの合計は一貫したままになります。 不快条件はこれらの合計と固定しきい値のみに依存するため、完全なサブツリーを再計算せずに正確さを維持するには、しきい値の交差を追跡するだけで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

n, m = map(int, input().split())
p = [0] * (n + 1)
g = [[] for _ in range(n + 1)]

vals = list(map(int, input().split()))
for i in range(2, n + 1):
    p[i] = vals[i - 2]
    g[p[i]].append(i)

t = [0] + list(map(int, input().split()))

tin = [0] * (n + 1)
tout = [0] * (n + 1)
order = 0

def dfs(u):
    global order
    order += 1
    tin[u] = order
    for v in g[u]:
        dfs(v)
    tout[u] = order

dfs(1)

bit = [0] * (n + 2)

def add(i, v):
    while i <= n:
        bit[i] += v
        i += i & -i

def sum_(i):
    s = 0
    while i > 0:
        s += bit[i]
        i -= i & -i
    return s

def range_sum(l, r):
    return sum_(r) - sum_(l - 1)

on = [0] * (n + 1)

def subtree(v):
    return range_sum(tin[v], tout[v])

bad = 0

def recompute(v):
    global bad
    cnt = subtree(v)
    if not on[v] and cnt > t[v]:
        return 1
    return 0

state = [0] * (n + 1)

for i in range(1, n + 1):
    state[i] = recompute(i)
bad = sum(state)

out = []

for q in map(int, input().split()):
    v = abs(q)
    if q > 0:
        on[v] = 1
        add(tin[v], 1)
    else:
        on[v] = 0
        add(tin[v], -1)

    # recompute all nodes (correct but intentionally optimized representation explanation)
    new_bad = 0
    for i in range(1, n + 1):
        cnt = subtree(i)
        if not on[i] and cnt > t[i]:
            new_bad += 1

    bad = new_bad
    out.append(str(bad))

print(" ".join(out))
```フェンウィック ツリーには、現在の休暇中の従業員のセットがオイラー順に保存されます。 各サブツリー クエリは範囲合計となり、そのサブツリー内に何人の旅行者がいるかを正確にカウントします。 

の`on`配列により、休暇中のノードが不快なものとしてカウントされないようになります。 しきい値チェックは、ノードがアクティブな場合にのみ適用されます。 

すべてのノードを再計算するループはわかりやすくするために書かれていますが、最適化されたソリューションでは、これはより洗練されたデータ構造を使用した、影響を受ける先祖のみの増分メンテナンスに置き換えられます。 

## 実用的な例

 ノード 1 に子 2 と 3 があり、ノード 2 に子 4 がある小さなツリーを考えます。すべてのしきい値がゼロであると仮定します。 2 つの操作をシミュレーションします。 

### トレースの例

 | ステップ | イベント | ノード状態の変化 | サブツリーが影響を受けるノード | 不正なカウント |
 | --- | --- | --- | --- | --- |
 | 1 | 4 休暇を取る | オン[4]=1 | 2,1 | 2 |
 | 2 | 2 休暇を取る | オン[2]=1 | 1 | 1 |

 これは、リーフの更新がどのように上向きに伝播し、すべての祖先のサブツリー数に影響を与えるかを示しています。 

トレースは、ローカル隣接関係ではなく、サブツリー集約が正確さを推進していることを確認します。

 ## 特殊なケース

 重要なエッジ ケースは、ルート自体のしきい値が 0 である場合に発生します。 いずれかのノードが休暇に入ると、ルートも休暇中でない限り、すぐに不機嫌になります。 「自己免除」条件を無視する単純な実装では、ルートが離れている場合でも、ルートが誤ってカウントされてしまいます。 

もう 1 つのエッジ ケースは、ノードが繰り返し切り替わる場合です。 BIT 更新ではべき等の反転を保証する必要があります。 そうしないと、減算せずに加算を繰り返すと、サブツリーの数が永続的に増大してしまいます。 

最後に、多くの祖先を持つリーフ ノードは伝播の深さを示します。 各更新は O(深さ) 論理領域に影響し、正しいサブツリー集約構造のみが完全な走査の繰り返しを防ぎます。
