 ## 解決策
 ## 問題の理解

 私たちにはサーバーのプールが与えられており、それぞれのサーバーの容量はリソース単位で測定されて固定されています。 2 つの独立したサービスを展開する必要があり、各サービスは同時に複数のサーバーを使用できます。 サービスが複数のサーバーを使用する場合、その合計負荷はそれらのサーバー間で均等に分割されるため、選択された各サーバーはサービスの合計要件の一部のみを処理する必要があります。 

需要のあるサービスの場合$x$、割り当てられている場合$k$サーバーの場合、それらのサーバーのそれぞれが提供することが期待されます$x / k$単位。 サーバーは、その容量が少なくとも必要な共有である場合にのみサービスに使用できます。 各サーバーは未使用にすることも、2 つのサービスのうちの 1 つに正確に割り当てることもできます。 

ここでのタスクは、サーバーを 2 つの独立したグループに分割して、各グループがこの均等共有ルールに基づいてサービスをサポートできるかどうかを決定し、分割できる場合は 1 つの有効な割り当てを出力することです。 

重要な問題は、セットサイズが同じであることです$k$サーバーごとの要件が変更されるため、グループの実現可能性は、どのサーバーが選択されるか、および選択されるサーバーの数の両方に依存します。 

この制約により、最大 300,000 台のサーバーが許可されるため、すべてのサブセット、さらにはサブセットのすべてのペアを試行するアプローチは即座に除外されます。 それを超えたもの$O(n \log n)$または$O(n \log^2 n)$慎重に正当化する必要があります。 

いくつかの失敗例は自然に現れます。 

1 つのサービスにあまりにも多くの弱いサーバーが割り当てられている場合、より小さなサブセットが機能する場合でも、サービスが失敗する可能性があります。 たとえば、容量 10 のサーバーは、$x = 20$単独または適切にペアになっている場合のみ。 「サーバーが多ければ常に役立つ」と誤って仮定すると、間違った貪欲な選択をすることになります。 

もう 1 つの微妙なケースは重複です。2 番目のサービスを考慮せずに最初のサービスに最適なグループを選択すると、有効なグローバル パーティションが存在する場合でも、2 番目のサービスに対する有効な割り当てがすべてブロックされる可能性があります。 これがこの問題の中心的な難しさです。 

## アプローチ

 ブルートフォース解釈では、あらゆる方法を試してサーバーを 2 つのセットに分割し、実現可能性を確認します。 サブセットごとに、考えられるすべてのサイズを試し、その中のすべてのサーバーがしきい値を満たしているかどうかを確認します。$x/k$。 パーティションの数だけでも膨大な数になるため、これはすぐに爆発します。$2^n$、さらには単一の分割コストを検証することもできます。$O(n)$、不可能につながる$O(n 2^n)$。 

サーバーを容量ごとに分類すると、より構造化された観察が得られます。 サービスを修正し、正確に使用することに決めたとします。$k$サーバー。 実現可能性を最大限に高めたい場合は、常に以下を選択する必要があります。$k$弱いサーバーをより強力なサーバーに置き換えることは、制約を満たすのに役立つだけであるためです。 

降順に並べ替えた後$c_1 \ge c_2 \ge \dots \ge c_n$、最初のものを取ると、$k$サーバーの場合、制限制約はそれらの中で最も弱いものになります。$c_k$。 実現可能性の条件は次のようになります。$$c_k \ge \frac{x}{k} \quad \Leftrightarrow \quad k \cdot c_k \ge x$$これにより、候補サイズのチェックが軽減されます$k$単一の不等式に。 各サービスについて、実現可能な最大値を見つけることができます。$k$二分探索を使用します。 

残りの課題は、2 つの互いに素なグループを割り当てる必要があることです。 1 つのサービスのプレフィックスを選択したら、残りのサフィックスから他のサービスを形成する必要があり、その実現可能性をその縮小された配列で再計算する必要があります。 両方のサービスが最強のサーバーをめぐって競合するため、最初にサービス 1 を割り当て、次にサービス 2 を割り当てる、またはその逆の両方の順序を試します。

 | ブルートフォース |$O(2^n)$|$O(n)$| 遅すぎる |
 | ソート + 二分探索 + 2 つの代入 |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 元のインデックスを維持したまま、サーバーを容量の降順に並べ替えます。 次に、各サービスが任意のプレフィックスから取得できるサーバーの数を計算します。 

1. サーバーを容量の降順に並べ替えます。 これにより、選択したサイズに対して、$k$、可能な限り最良のセットは長さの接頭辞です$k$。 
2. 需要のあるサービスの場合$x$、サイズの実現可能性を定義します$k$として$c_k \cdot k \ge x$。 最大値を二分探索します$k$この条件を満たすものです。 これが機能する理由は、$k$双方を弱体化させる：$c_k$一方で減少します$k$が増加し、実現可能性が単調になります。 
3. しましょう$k_1$完全な配列を使用してサービス 1 に最適なサイズにする必要があります。 
4. 最初の値を割り当ててみます$k_1$残りのサーバーは、ソートされた配列のサフィックスを形成します。 
5. 残りのサフィックスに対して、サービス 2 に対して同じ実現可能性検索を実行しますが、サフィックスを新しい配列として扱います。 有効な値が見つかった場合$k_2$、有効なパーティションがあります。 
6. これが失敗した場合は、サービスの役割を交換し、同じロジックを繰り返します。 
7. いずれかの順序付けが成功した場合は、パーティションを出力します。 それ以外の場合は出力できません。 

### なぜ効果があるのか

 サイズのすべてのサブセットのうち、サービスごとに$k$、ソートされた容量の接頭辞が他のすべての選択肢を支配します。 有効な割り当ては、実現可能性を損なうことなく、プレフィックスを使用する割り当てに変換できます。 これにより、プレフィックスの分割のみを考慮する必要があり、残る対話は 2 つのプレフィックス間の分割ポイントがどのように選択されるかだけになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def max_k(arr, x):
    # arr is sorted descending, return max k such that k * arr[k-1] >= x
    n = len(arr)
    lo, hi = 1, n
    ans = 0
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid - 1] * mid >= x:
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1
    return ans

def solve_order(c, x1, x2):
    n = len(c)
    k1 = max_k(c, x1)
    if k1 == 0:
        return None

    # try using k1 for service 1, then service 2 on suffix
    def try_split(k1):
        if k1 == 0 or k1 >= n:
            return None
        c2 = c[k1:]
        k2 = max_k(c2, x2)
        if k2 == 0:
            return None
        return k1, k2

    res = try_split(k1)
    if res:
        return (k1, res[1], 1)

    # swap attempt
    k2 = max_k(c, x2)
    if k2 == 0:
        return None

    def try_split2(k2):
        if k2 == 0 or k2 >= n:
            return None
        c2 = c[k2:]
        k1b = max_k(c2, x1)
        if k1b == 0:
            return None
        return k1b, k2

    res = try_split2(k2)
    if res:
        return (res[0], k2, 2)

    return None

def main():
    n, x1, x2 = map(int, input().split())
    a = list(map(int, input().split()))
    idx = list(range(1, n + 1))

    arr = sorted(zip(a, idx), reverse=True)
    c = [v for v, _ in arr]
    ids = [i for _, i in arr]

    # first order: S1 then S2
    k1 = max_k(c, x1)
    if k1 > 0:
        c2 = c[k1:]
        k2 = max_k(c2, x2)
        if k2 > 0:
            print("Yes")
            print(k1, k2)
            print(*ids[:k1])
            print(*ids[k1:k1 + k2])
            return

    # swap order
    k2 = max_k(c, x2)
    if k2 > 0:
        c2 = c[k2:]
        k1 = max_k(c2, x1)
        if k1 > 0:
            print("Yes")
            print(k1, k2)
            print(*ids[k2:k2 + k1])
            print(*ids[:k2])
            return

    print("No")

if __name__ == "__main__":
    main()
```この解決策は、すべての最適な選択がプレフィックスの問題になるようにサーバーを並べ替えることから始まります。 二分探索機能`max_k`実現可能条件を把握する$k \cdot c_k \ge x$、グループのサイズとその中で最も弱いサーバーの両方をエンコードします。 

The main function then tries assigning one service first, taking its best possible prefix, and checks whether the remaining suffix can satisfy the other service. それが失敗した場合、役割は逆転します。 出力は、ソートされた配列から格納された元のインデックスを使用して再構築されます。 

容量とインデックスの整合性を維持するには注意が必要です。 ソート時にインデックスを保持するのを忘れるのは一般的な実装エラーであり、実行可能性チェックは正しく行われますが、出力は無効になります。 

## 実用的な例

 ### 例 1

 入力:```
6 8 16
3 5 2 9 8 7
```並べ替え:

 | 容量 | インデックス |
 | --- | --- |
 | 9 | 4 |
 | 8 | 5 |
 | 7 | 6 |
 | 5 | 2 |
 | 3 | 1 |
 | 2 | 3 |

 のために$x_1 = 8$、実現可能なプレフィックス サイズ:

 | k | c_k | k*c_k |
 | --- | --- | --- |
 | 1 | 9 | 9 |
 | 2 | 8 | 16 |
 | 3 | 7 | 21 |
 | 4 | 5 | 20 |
 | 5 | 3 | 15 |

 それで$k_1 = 4$。 

残り: [3,2]。 のために$x_2 = 16$、 のみ$k=2$以来動作します$2 * 3 = 6$失敗して、$1 * 3 = 3$失敗するため、この順序で解決することはできません。 最初にサービス 2 を割り当てると、スワップが成功します。 

これは、順序が重要である理由を示しています。グローバル ソリューションが存在する場合でも、一方のサービスを貪欲に選択すると、もう一方のサービスがブロックされる可能性があります。 

### 例 2 (構築済み)

 入力:```
5 10 6
6 5 4 3 2
```もう並べ替え済み。 

のために$x_1 = 10$、$k_1 = 2$以来$2*5=10$。 残りの [4,3,2] は許可されます$x_2=6$と$k_2=1$以来$1*4=4$失敗しますが、$2*3=6$動作します。 

このトレースは、サフィックスの再計算がいかに重要であるかを示しています。 強力なサーバーを削除すると、実現可能性の境界が変わります。

 ## 特殊なケース

 重大なエッジ ケースは、1 つのサービスがすべてのサーバーを必要とする一方で、もう 1 つのサービスがまだ少なくとも 1 台のサーバーを必要とする場合に発生します。 すべてのサーバーを最初のサービスに貪欲に割り当てると、2 番目のサービスはすぐに失敗します。 サフィックスが空になるため、アルゴリズムがこれを処理します。`max_k`ゼロを返し、強制的にスワップを試行します。 

別のケースとして、大規模なシステムに容量がぎりぎり十分な場合が考えられます。$k$。 実現可能性はプレフィックス内の最も弱い要素に依存するため、インデックス作成時のオフバイワンエラー$c_k$の代わりに$c_{k-1}$誤った承認または拒否につながります。 二分探索公式は、一貫して評価することでこれを直接防ぎます。$k * c[k-1]$。
