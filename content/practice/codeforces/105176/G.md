 ## 解決策
 ## 問題の理解

 私たちは円の中に配置された一連の要素を扱っています。 循環シフト操作は、すべての要素を左また​​は右に移動し、何も失われないように端を包み込みます。 このようなシフトをいくつか実行した後、シーケンスの最終的な配置を決定するか、特定の要素がどこに配置されるかについての質問に答えるように求められます。 

ほとんどのバリアントでは、入力は初期配列と、時間の経過とともに蓄積されるシフト操作の数または合計シフト距離のいずれかで構成されます。 出力は、すべてのシフトを適用した後の最終配列、またはすべての変換後のクエリ位置の値のいずれかです。 

重要な構造的観察は、循環シフトによって要素の相対的な順序は変更されず、要素の絶対インデックスのみが変更されるということです。 これは、プロセス全体を、要素を物理的に移動させる代わりに、単一のオフセット値を追跡することに減らすことができることを直ちに意味します。 

複雑さの観点から見ると、配列サイズが最大 10^5 または 10^6 で、最大 10^5 の操作が存在する場合、操作ごとに実際に配列の回転を実行するソリューションは遅すぎます。 各回転は O(n) であり、最悪の場合は O(nq) になりますが、これは実現可能な限界をはるかに超えています。 したがって、配列を暗黙的に表現する必要があります。 

一般的なエッジ ケースは、総シフト数が配列サイズよりも大きい場合に発生します。 たとえば、長さ 5 の配列を右に 12 位置回転すると、効果的なシフトは 12 mod 5 = 2 になります。法 n を減らさない単純な実装では、誤って回転しすぎたり、冗長サイクルの実行で時間を無駄にしたりする可能性があります。 

負のシフトが許可される場合、別の微妙なケースが発生します。 たとえば、k による左シフトは、n - (k mod n) による右シフトと同等です。 符号正規化の処理が間違っていると、間違ったインデックス付けや off-by-one エラーが発生します。 

## アプローチ

 ブルート フォース手法では、各循環シフトを明示的にシミュレートします。 すべての操作で、要素を 1 つずつ移動するか、スライスを使用して配列を再構築します。 これは文字通り操作の定義に従っているので、これは正しいです。 ただし、各シフトのコストは O(n) であり、q 回の操作で合計コストは O(nq) になります。 入力が大きい場合、これは 10^10 程度の演算を必要とし、実行不可能です。 

重要な洞察は、巡回シフトが加算法 n の下でグループ構造を形成するということです。 すべてのシフトは整数の変位として表すことができ、複数のシフトは単純に累積されます。 配列を変更する代わりに、配列の「開始」が現在どこにあるかを示す単一の整数オフセットを維持します。 シフト後の i 番目の要素にアクセスするには、モジュラー演算を使用して要素を元のインデックスにマッピングし直す必要があります。 

これにより、反復的なデータ移動の問題が定数時間のインデックス演算に軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 最適 (オフセット追跡) | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 長さ n の配列と一連のシフト演算を想定します。

1. 配列を読み取り、標準リストに保存します。 元の順序を参照状態として保持したいため、この段階では変換は適用されません。 
2. オフセット変数をゼロに初期化します。 この変数は、配列の論理的な開始位置が、元の配列のインデックス 0 を基準にしてどれだけ回転したかを表します。 右にシフトするとこのオフセットが増加し、左にシフトすると減少します。 
3. 巡回シフト演算ごとに、それに応じてオフセットを更新します。 シフトが k だけ右にある場合、オフセットに k を追加します。 k だけ左にある場合は、k を減算します。 各更新の後、オフセットが常に [0, n-1] の範囲内に収まるように、法 n を使用してオフセットを正規化します。 この正規化により、オフセットが際限なく増大することがなくなり、インデックス シフトとしての意味が維持されることが保証されます。 
4. すべての操作を処理した後、アレイは物理的には変更されていませんが、論理的な開始点は移動しています。 最終配列内の論理的に位置 i にある要素は、元の位置 (i - オフセット + n) mod n に対応します。 
5. 問題が完全な最終配列を要求する場合は、0 から n-1 までのすべての位置 i を反復処理し、計算された式を使用して各位置を元の配列にマップし直すことによって配列を構築します。 
6. 問題がクエリを要求する場合、各クエリは同じインデックス変換を適用することで O(1) で応答されます。 

### なぜ効果があるのか

 正確さは、オフセットが常に配列に適用される正味の回転の合計を表すという不変式に依存します。 各巡回シフトは前のシフトと加算的に構成され、モジュラー演算によりラップアラウンド時の等価性が保証されます。 配列要素が明示的に並べ替えられることはないため、最終インデックスと元のインデックス間のマッピング関数は、すべての操作を通じて一貫性を保ちます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    offset = 0

    for _ in range(q):
        typ, k = input().split()
        k = int(k)

        if typ == 'R':
            offset = (offset + k) % n
        else:
            offset = (offset - k) % n

    res = []
    for i in range(n):
        res.append(a[(i - offset) % n])

    print(*res)

if __name__ == "__main__":
    solve()
```実装の中核はオフセット変数です。 リストを物理的に回転させるのではなく、リストを固定された循環構造として扱い、算術演算を通じてインデックスを再解釈します。 モジュロ演算により、オフセットが負になるか n を超える場合でも、正しいラッピングが保証されます。 

最後の再構築ステップは、出力が完全な配列を必要とする場合にのみ必要です。 クエリベースのバリアントでは、同じマッピング式がクエリごとに直接適用されます。 

よくある実装の落とし穴は、Python の負の剰余は依然として有効な正の剰余を生成しますが、それは括弧を慎重に配置した場合に限られるということを忘れていることです。`(i - offset) % n`。 もう 1 つの問題は、各演算後のオフセットの正規化に失敗することです。これにより中間値が大きくなる可能性がありますが、モジュロが一貫して適用されていれば正確さに影響はありません。 

## 実用的な例

 ### 例 1

 配列が次のようになっているとします。`[1, 2, 3, 4, 5]`そして、2 だけ右シフトを適用し、次に 1 だけ左シフトを適用します。 

オフセットのみを追跡します。 

| ステップ | 操作 | オフセット |
 | --- | --- | --- |
 | 0 | イニシャル | 0 |
 | 1 | R2 | 2 |
 | 2 | L1 | 1 |

 最終的な配列は次を使用して再構築されます。`(i - 1) mod 5`。 

| 私 | マップされたインデックス | 値 |
 | --- | --- | --- |
 | 0 | 4 | 5 |
 | 1 | 0 | 1 |
 | 2 | 1 | 2 |
 | 3 | 2 | 3 |
 | 4 | 3 | 4 |

 これにより、要素を物理的に動かすことなく、回転が正しく適用されていることを確認できます。 

### 例 2

 配列`[10, 20, 30, 40]`, 右に 6 シフトします。 

オフセットは次のように進化します。 

| ステップ | 操作 | オフセット |
 | --- | --- | --- |
 | 0 | イニシャル | 0 |
 | 1 | R6 | 2 |

 6 mod 4 = 2 なので、実質的に 2 回転します。 

マッピング:

 | 私 | マップされたインデックス | 値 |
 | --- | --- | --- |
 | 0 | 2 | 30 |
 | 1 | 3 | 40 |
 | 2 | 0 | 10 |
 | 3 | 1 | 20 |

 これは、モジュロ リダクションがなぜ不可欠であるかを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、シフトの大きさが配列サイズよりはるかに大きい場合です。 このような場合、モジュロン n の削減に失敗すると、自動正規化がない言語では不必要な累積が発生し、論理エラーが発生する可能性があります。 

もう 1 つのエッジ ケースは、n が 1 に等しい場合です。この状況では、すべての巡回シフトは事実上 no-op であり、モジュロ動作を考慮しない誤ったインデックス演算は、慎重でない実装でも誤った結果を生み出す可能性があります。 

3 番目のケースでは、右に k ずつ、次に左に k を繰り返しシフトするなど、交互にシフトが繰り返されます。 オフセットはゼロに戻るはずです。これにより、アルゴリズムがモジュロ演算の下でシフトを加法逆数として正しく扱うことが確認されます。
