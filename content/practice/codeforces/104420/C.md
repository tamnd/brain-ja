 ## 解決策
 ## 問題の理解

 バイナリ文字列が与えられます$y$そして整数$k$。 別のバイナリ文字列を構築する必要があります$x$2 つの条件が同時に満たされるようにします。 初め、$x$より小さくない 2 進数を表す必要があります$y$。 次に、内部の 0 と 1 を数えると、$x$、ゼロの数と 1 の数の差は正確に一致する必要があります。$k$。 有効なものの中で$x$、辞書編集的および数値的な意味で可能な限り最小の 2 進数が必要です。先行ゼロのないバイナリ文字列の場合、これは通常の整数の順序付けと同等です。 

主な困難は、数値を比較するだけでなく、文字数に対するグローバルな制約も強制していることです。 数値を大きくするための変更は、満足のいく結果の実現可能性に影響を与える可能性があります。$c_0(x) - c_1(x) = k$したがって、建設では注文と実現可能性のバランスを慎重にとらなければなりません。 

制約は大きく、最大で$10^5$テスト ケースと合計入力サイズは最大$4 \cdot 10^5$。 これにより、すべての候補を試したり、プレフィックス決定ごとに複数の完全な構造をシミュレートしたりするアプローチは除外されます。 テストケースごとに線形または線形に近い貪欲な構造が必要です。 

素朴なアプローチは、以下から始めることです$y$、2進数としてインクリメントし、各候補をチェックします。 有効な候補間のギャップが指数関数的である可能性があり、候補ごとの実現可能性のチェックも長さが直線的であるため、これはすぐに失敗し、壊滅的なパフォーマンスにつながります。 

2 番目の単純なアイデアは、同じ長さの文字列をすべて試してみることです。$n$または$n+1$、ただし、固定長の場合でも、$2^n$可能性があり、制約によるフィルタリングは不可能です。 

制約によって 1 よりも 0 の数が多くなる場合、またはその逆の場合、微妙なエッジ ケースが発生します。 たとえば、次の場合$k$は非常に大きな正なので、多くのゼロが必要ですが、バイナリの順序付けでは、最小化のために先行するゼロが優先されます。$\ge y$。 もう 1 つの注意が必要なケースは次のような場合です。$y$すでに必要なバランスに違反しているため、大幅に増やす必要があり、長さが変わる可能性があります。 

## アプローチ

 ブルートフォースの観点では、問題をすべてのバイナリ文字列の検索として解釈します。$x$、差の制約を満たすものをフィルタリングし、少なくとも差の制約を満たすものの中から最小のものを選択します。$y$。 これは定義に直接従うため、概念的には正しいですが、検索スペースは文字列の長さが指数関数的に増加するため、使用できなくなります。 

重要な観察点は、制約が$c_0(x) - c_1(x) = k$ポジションではなくカウントのみに依存します。 文字列に長さがある場合$L$、その後、$z$ゼロの数であり、$o$1 の数、次のようになります。$$z - o = k,\quad z + o = L$$それで：$$z = \frac{L + k}{2}, \quad o = \frac{L - k}{2}$$これは直ちに 2 つのことを示唆します。 初め、$L + k$均等でなければなりません。 2番、$L \ge |k|$。 固定長の場合、実現可能性は単純な組み合わせチェックに帰着します。 

ここで問題は次のようになります。ある長さのすべてのバイナリ文字列の間で$L$0 と 1 の固定数を満たす場合、少なくとも$y$。 これは古典的な「制約と下限のある最小文字列」問題であり、貪欲なプレフィックス構築によって解決できます。 

から始まる長さを試します$n$上向きに。 長さごとに、カウントが有効かどうかを確認します。 次に、それが以下でないことを確認しながら、最小の有効な文字列を構築しようとします。$y$。 貪欲なアイデアは、可能であれば常に「0」を優先しながら、残りの必要なカウントと下回らないという制約の両方を尊重して、少しずつ答えを構築することです。$y$最初に分岐する位置です。 

At each prefix, we maintain whether we are still equal to the prefix of$y$または、すでに厳密には大きくなっています。 If we are equal, we must respect the current digit of$y$。 すでに大きくなっている場合は、貪欲に自由に最小化することができます。 

また、暫定ビットを配置した後、残りの位置が必要な数の 0 と 1 をまだ収容できるかどうかを確認することで、実現可能性を確認します。

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。 

1. 可能なターゲットの長さを計算する$L$。 カウントはパリティに依存するため、次のようにする必要があります。$L \ge |k|$そして$(L + k) \% 2 = 0$。 私たちはそのような最小のものを試します$L$ただし、辞書編集的に失敗した場合は、長さを増やす必要があるかもしれません。 

その理由は、長さを延長すると、順序とバランスの両方の制約を満たすための柔軟性が高まるからです。 
2. 固定の場合$L$、必要な 0 と 1 の数を計算します。$$z = (L + k) / 2,\quad o = (L - k) / 2$$どちらかが負の場合、この長さは無効です。 
3. 最小の有効な文字列を構築しようとします$x$長さの$L$そのような$x \ge y$。 

建物のシミュレーションをします$x$左から右へ。 
4. 状態変数を維持します。 

残りの 0 と 1 の数、およびブール値`tight`現在のプレフィックスが次のプレフィックスと等しいかどうかを示します。$y$。 
5. 各位置で、次のビットを決定します。 

もし`tight`それは真実です、私たちはそれに匹敵するかそれを超えるように努めます$y[i]$。 許可され、実行可能な場合は「0」を使用しますが、それは結果が以下の値よりも小さくならない場合に限ります。$y$。 それ以外の場合は、「1」を選択する必要があります。 

もし`tight`が false の場合、まだゼロが残っている場合は貪欲に「0」を配置し、そうでない場合は「1」を配置します。 
6.ビットを配置した後、残りのカウントを更新し、更新します`tight`。 より少し大きい値を配置すると、$y[i]$、設定しました`tight = False`。 
7. 選択を確定する前に、残りの 0 と 1 で残りの位置を埋めることができるかどうかを確認することで、実現可能性を確認します。 

すべての位置が埋められた後、構築された文字列を出力します。 

### なぜ効果があるのか

 どのステップでも、アルゴリズムは、構築されたすべてのプレフィックスが次のプレフィックスと正確に等しいかどうかを維持します。$y$、またはすでに厳密にはそれより大きい。 プレフィックスのすべての有効な補完の中で、可能な限り「0」を選択すると、辞書編集上最小の拡張子が得られます。 実現可能性チェックにより、必要なゼロと 1 のバランスを備えた有効な完全な文字列に完成できないプレフィックスを決してコミットしないことが保証されます。 したがって、貪欲な決定によってすべての最適解が排除されることはなく、最初に得られる完全な構築は全体的に最小になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def feasible(rem0, rem1, rem_len, k):
    # rem0 - rem1 must match k contribution over remaining length + current partial handled outside
    # Here we only ensure counts are consistent with total length constraint:
    return rem0 >= 0 and rem1 >= 0 and rem0 + rem1 == rem_len

def build(y, L, z, o):
    n = len(y)
    res = []
    tight = True

    for i in range(L):
        for bit in '01':
            if z - (bit == '0') < 0 or o - (bit == '1') < 0:
                continue

            if tight:
                if i < n:
                    if bit < y[i]:
                        continue
                else:
                    pass

            nz = z - (bit == '0')
            no = o - (bit == '1')
            rem = L - i - 1

            if nz + no != rem:
                continue

            # check lexicographic constraint
            if tight and i < n and bit > y[i]:
                # becomes strictly larger
                pass
            elif tight and i < n and bit == y[i]:
                pass

            # accept
            res.append(bit)
            z, o = nz, no
            if tight and i < n and bit > y[i]:
                tight = False
            elif i >= n:
                tight = False
            elif i < n and bit < y[i]:
                # should not happen due to filter
                pass
            break

    return ''.join(res)

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        y = input().strip()

        best = None

        # try minimal feasible length
        L = max(n, abs(k))
        while True:
            if (L + k) % 2 == 0:
                z = (L + k) // 2
                o = (L - k) // 2
                if z >= 0 and o >= 0:
                    cand = build(y, L, z, o)
                    if cand and (best is None or int(cand, 2) < int(best, 2)):
                        best = cand
                        break
            L += 1

        print(best)

if __name__ == "__main__":
    solve()
```このコードは、問題を、実行可能な長さの選択と、接頭辞制約の下で辞書編集上で最小の有効な文字列の構築に分割します。 ループオーバー$L$これにより、バランス制約を満たすことができる長さを最終的に見つけることができます。 構築関数は、残りの 0 と 1 を追跡することによって、各ステップでのカウントの実行可能性を強制します。 

微妙な点は、バイナリ文字列を比較することです。`int(cand, 2)`長さは入力制約によって制限されており、制御された方法でテストごとにのみ実行されるため、ここでは安全です。 より厳密な実装では、変換の繰り返しを避け、代わりにパディング ルールを使用して辞書順に比較します。

 ## 特殊なケース

 重要なエッジケースの 1 つは次のような場合です。$y$すでに有効な解に非常に近づいていますが、パリティに違反しています。 たとえば、次の場合$y = 1$そして$k = 0$、長さ 1 は制約を満たすことができません。$z - o = 0$均等な長さが必要です。 アルゴリズムは長さ 2 に移動し、次のように計算します。$z = 1, o = 1$、および構築します`10`、これは最小の有効な 2 進数です。`1`。 

もう一つのケースは次のような場合です。$k$は大きくて正なので、多くのゼロが強制されます。 もし$y$'1' で始まる場合、貪欲な構築ではすぐには一致できないため、下限を尊重しながら十分なゼロをサフィックスに配置できるまで発散を延期します。 実現可能性チェックにより、後で必要なゼロカウントに達することが不可能になるようなプレフィックスの選択が防止され、初期の決定が直観に反しているように見える場合でも正確さが保証されます。 

最後のエッジケースは、最適なソリューションで長さを 1 倍以上増やす必要がある場合に発生します。 これは、すべての短い長さがパリティに違反しているか、またはカウント制約と同時に辞書編集上の制約を満たすことができない場合に発生します。 インクリメンタルサーチオーバー$L$有効な最適な長さがスキップされないことを保証します。
