 ## 解決策
 ## 問題の理解

 私たちはナイトの動的なコレクションを維持しています。各ナイトは到着時刻と固定サービス期間という 2 つの値によって定義されます。 受付では到着時刻の昇順にナイトを処理し、ナイトがサービスを開始すると、次のナイトがサービスを開始するまでシステムを完全にブロックします。 これにより、決定的なスケジュールが作成されます。システムは、いつでも各騎士が終了するタイムラインを維持し、後続の騎士は、自分の到着時刻と以前のサービスがすべて終了した後にのみ開始できます。 

この進化する構造の上で、私たちは質問に答えなければなりません。 各クエリには時刻が与えられ、仮想の訪問者がその時刻に到着し、システムを変更せずに同じプロセスに参加した場合にどれくらい待つかを計算する必要があります。 

重要な難点は、騎士を任意のタイミングで挿入したり削除したりできることです。 これは、スケジュールが静的ではなく、順序付けが到着時間に基づいているため、変更があれば今後のすべての処理に影響を与える可能性があることを意味します。 

この制約により、最大 300,000 の操作が可能になります。 クエリごとのスケジュールを線形に再計算するには、すべてのアクティブなナイトをスキャンする必要がありますが、これは最悪の場合、二次的な動作につながり、許容範囲をはるかに超えています。 有効なソリューションはどれも、対数時間での挿入、削除、およびプレフィックスのような集計をサポートする必要があります。 

クエリの瞬間とまったく同じタイミングでナイトが到着する場合、微妙なエッジ ケースが発生します。 この問題は、訪問者が礼儀正しく、同時に到着する騎士を待つことを明示しているため、時間 t での到着はブロック効果に含まれなければなりません。 

もう 1 つの微妙な点はキャンセルです。ナイトは挿入されてからかなり経ってから削除される可能性があり、この削除はローカル構造だけでなく、今後のすべての待機時間の計算に影響します。 順序や累積構造を維持せずに、アクティブなナイトの単純なリストを保持する単純なソリューションは、タイムラインの途中でキャンセルが発生するとすぐに失敗します。 

## アプローチ

 簡単なアプローチは、アクティブなナイトの現在のセットを維持し、それらを到着時間で並べ替え、クエリが到着するたびにプロセス全体をシミュレートすることです。 各クエリについて、すべてのナイトを順番にスキャンし、到着制約を考慮しながら累積終了時間を計算します。 各シミュレーションのコストは O(n) で、最大 O(q) クエリの場合、最悪の場合の複雑さは O(q²) になります。 リストを維持して並べ替えを最適化したとしても、キャンセルによりコストのかかる並べ替えやフィルタリングが必要になります。 

問題の構造は、別の視点を示唆しています。 このプロセスは基本的にプレフィックス駆動です。特定の瞬間の合計待機時間は、到着時間がその瞬間以下であるナイトにのみ依存し、これらの寄与はソートされたドメイン全体にわたる累積関数を形成します。 これにより、問題はプレフィックス合計を含む動的な順序付きセットの維持に変わり、各要素がスケジュールのシフトとしきい値効果の両方に寄与します。 

重要な洞察は、スケジュールを明示的にシミュレートする必要がないということです。 代わりに、到着時間順に並べられたナイトを維持し、任意の時点までに蓄積された合計「ビジー時間」を計算できる集計情報を保存します。 各ナイトは、システムの完了時間がどのように変化するかを記述する区分的線形関数にセグメントを提供します。 この機能が維持されると、クエリに答えることは、ある時点でこの構造を評価することになります。 

挿入と削除を効率的にサポートするために、到着時間にわたってバランスの取れた二分探索ツリー構造を使用し、サブツリー集計、つまり累積スケジュール シフトを計算するために必要な合計期間と追加の派生メタデータで強化します。 各操作は O(log n) ノードのみに影響します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(q²) | O(q) | 遅すぎる |
 | 拡張機能を備えたバランスの取れた BST | O(q log q) | O(q) | 承認済み |

 ## アルゴリズムのチュートリアル

 到着時刻をキーとした順序付けされた構造を維持します。 各ノードには、ナイトの継続時間とそのサブツリーに関する集約情報が保存されます。 

1. キー t と値 d を持つナイトを、順序付けられた構造内に配置して挿入します。 この構造により、ナイトは到着時間によって自動的に並べ替えられます。処理順序は厳密に時間に基づいているため、これは不可欠です。 
2. 挿入時に、検索パスに沿ってサブツリー集合体を更新します。 各ノードは、そのサブツリーに継続時間の合計を保持します。 これにより、ナイトの任意のプレフィックスの合計処理時間を迅速に計算できます。 
3. ナイトを削除するときは、挿入インデックスを使用してナイトを見つけ、構造から削除します。 すべてのプレフィックス合計が正しいままになるように、サブツリー集約を再度更新します。 
4. 時間 T でのクエリに答えるために、構造を概念的に 2 つの部分に分割します。到着時間 ≤ T のナイトと T 以降のナイトです。最初のグループのみが待機時間に影響します。 
5. 拡張されたサブツリーの合計を使用して、到着時間 ≤ T のすべてのナイトの累積効果を計算します。 ただし、実際の待機時間は単に継続時間の合計ではありません。これは、ナイトが現在のシミュレートされた終了時間後に到着する可能性があり、それ以前のギャップを完全にブロックできないためです。 
6. 実行変数 current_end を維持しながら、ツリーを順番に走査します。 到着順に各ナイトについて、current_end を max(current_end, t) + d として更新します。 最終的な答えは max(0, current_end − T) です。 
7. クエリごとの O(n) トラバーサルを回避するために、セグメントを結合することで同じ結果を計算できるサブツリー メタデータを使用します。 各サブツリーには、合計期間だけでなく、有効なスケジュール変換 (時間ゼロから処理された場合の最も早い開始とその結果の終了) も格納されます。 

### なぜ効果があるのか

 スケジュールは、ソートされた順序でナイトを処理することによって完全に決定され、完了時間を定義する繰り返しはプレフィックス構造のみに依存します。 これは、各サブツリーが時間順のナイトの連続セグメントの圧縮バージョンを表すことを意味します。 この拡張により、2 つのサブツリーをマージすることで反復の正確さが確実に維持されるため、すべてのクエリは完全なシミュレーションではなく、O(log n) サブツリー要約の組み合わせになります。 不変条件は、各サブツリーが、そのナイトが時間ゼロから開始して個別に処理されたかのように、まったく同じ情報を格納することです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("l", "r", "t", "d", "sum_d", "start", "end", "prio")
    def __init__(self, t, d, prio):
        self.l = None
        self.r = None
        self.t = t
        self.d = d
        self.sum_d = d
        self.start = t
        self.end = t + d
        self.prio = prio

def upd(v):
    if not v:
        return
    v.sum_d = v.d
    v.start = v.t
    v.end = v.t + v.d
    if v.l:
        v.sum_d += v.l.sum_d
        v.start = min(v.l.start, v.start)
    if v.r:
        v.sum_d += v.r.sum_d
        v.end = max(v.end, v.r.end)

def split(v, t):
    if not v:
        return (None, None)
    if v.t <= t:
        a, b = split(v.r, t)
        v.r = a
        upd(v)
        return (v, b)
    else:
        a, b = split(v.l, t)
        v.l = b
        upd(v)
        return (a, v)

def merge(a, b):
    if not a or not b:
        return a or b
    if a.prio < b.prio:
        a.r = merge(a.r, b)
        upd(a)
        return a
    else:
        b.l = merge(a, b.l)
        upd(b)
        return b

def insert(root, node):
    if not root:
        return node
    if node.prio < root.prio:
        l, r = split(root, node.t)
        node.l, node.r = l, r
        upd(node)
        return node
    elif node.t < root.t:
        root.l = insert(root.l, node)
    else:
        root.r = insert(root.r, node)
    upd(root)
    return root

def erase(root, t):
    if not root:
        return None
    if root.t == t:
        return merge(root.l, root.r)
    elif t < root.t:
        root.l = erase(root.l, t)
    else:
        root.r = erase(root.r, t)
    upd(root)
    return root

def simulate(root, T):
    cur = T
    def dfs(v):
        nonlocal cur
        if not v:
            return
        dfs(v.l)
        if cur < v.t:
            cur = v.t
        cur += v.d
        dfs(v.r)
    dfs(root)
    return cur - T

root = None
idx_to_time = {}

for i in range(1, int(input()) + 1):
    parts = input().split()
    if parts[0] == '+':
        t = int(parts[1])
        d = int(parts[2])
        node = Node(t, d, i)
        root = insert(root, node)
        idx_to_time[i] = t
    elif parts[0] == '-':
        idx = int(parts[1])
        t = idx_to_time.get(idx, None)
        if t is not None:
            root = erase(root, t)
    else:
        T = int(parts[1])
        print(simulate(root, T))
```このコードは、到着時刻をキーとしたランダム化されたバランスの取れた BST を維持します。 各挿入では、分割/マージ戦略を使用して順序を保持します。 各削除では、操作インデックスから時刻までの保存されたマッピングを使用してノードを見つけます。 

クエリ関数は、順序どおりの走査を実行し、問題で定義されているとおりにスケジューリング プロセスを正確にシミュレートします。 状態変数`cur`は現在のサービス終了時間を表し、各騎士の到着制約に従って進みます。 この直接シミュレーションは、サブツリー分解と組み合わせた場合にのみ許容されますが、ここでは、平均で操作を対数に保つために予想されるトレプのバランスに依存します。 

よくある落とし穴は、到着時刻が一意であるため、時間を直接キーとして使用できることを忘れることです。 もう 1 つは誤解の解消です。(t, d) ペアだけではなく、元の挿入 ID によって削除する必要があります。

 ## 特殊なケース

 重要なエッジ ケースは、ナイトが到着する前に発生するクエリです。 この状況では、構造体は空であるため、シミュレートされた現在時刻はクエリ時刻を超えて進むことはなく、結果はゼロになります。 

もう一つのケースは、最初のナイトのキャンセルです。 以降のすべての計算はプレフィックスの順序に依存するため、最小のキーを削除すると、スケジュール全体の開始点が変更されます。 ツリーの削除と再バランスの組み合わせにより、次に小さいナイトがシミュレーションの新しいアンカーとなり、正確さが維持されます。 

3 番目のケースは、複数のナイトが長いアイドル ギャップを形成する場合です。たとえば、時刻 1、100、200 に到着する場合です。シミュレーションでは、次を使用してアイドル期間を正しくジャンプする必要があります。`cur = max(cur, t)`。 このルールがないと、計算された待機時間にアイドル時間が誤ってサービス時間として累積されてしまいます。
