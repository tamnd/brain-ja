 ## 問題の理解

 一定の長さの労働日をどのように配分するかを決定しています$m$横切って$n$作物の種類。 それぞれの作物$i$直線的な利益が得られます。それに費やされたすべての時間単位が寄与します。$w_i$利益。 したがって、総利益は単純に次の合計になります。$w_i \cdot x_i$、 どこ$x_i$私たちが作物に取り組む時間はどれくらいですか$i$。 

各作物には通常の制約があります。つまり、その時間は一定の間隔内に収まらなければなりません。$[l_i, r_i]$。 したがって、すべての作物には、最小限必要な作業負荷と最大許容作業負荷の両方があります。 重要なグローバル制約は、選択されたすべての時間を正確に合計しなければならないということです。$m$。 すべての間隔内の値を選択することが可能であることが保証されています。 

これに加えて、特別な操作が 1 つあります。 最大 1 つの作物を選択し、その上限を削除することが許可されています。つまり、その時間は次のとおりです。$0$まで$m$。 他のすべての作物は元の状態を維持します$[l_i, r_i]$制約。 

課題は、おそらくこの緩和を 1 つの作物に適用した後、総利益を最大化することです。 

この制約は、作物に対する二次または三次アプローチが不可能であることを即座に示唆しています。 と$n$まで$10^5$そして$m$まで$10^{11}$、割り当てを明示的に検索したり、時間を単位ごとにシミュレートしたりする方法は実行できません。 平$O(n \log n)$ソリューションは依存を避ける必要があります$m$全体的に。 

構造化せずに欲張って考えると微妙な失敗例が現れます。 グローバルな再配分の影響を考慮せずに、独立して時間を配分したり、単一の作物を調整したりしようとする人もいるかもしれません。 

たとえば、次の 2 つの作物について考えてみましょう。```
n = 2, m = 10
1 0 10
100 5 5
```単純な考えでは、最初の作物には制限がないため、余分な時間をすべて最初の作物に割り当て、適度な利益が得られる可能性があります。 しかし、第 2 作物の単位あたりの利益ははるかに高く、最適なソリューションでは、制約を尊重しながら、可能な限り多くの時間をそこに集中させます。 下限と上限の相互作用により、問題をグローバル割り当てモデルに変換しない限り、ローカル推論の信頼性が低くなります。 

## アプローチ

 目的は直線的であるため、問題は固定予算の配分です。$m$下限と上限のある項目間で。 標準的な変換により構造が明確になります。 

必須の割り当てから始める$l_i$。 それらを割り当てた後、残りを分配する必要があります。$$D = m - \sum l_i$$単位。 それぞれの作物$i$まで受け入れることができます$c_i = r_i - l_i$追加ユニットがあり、各ユニットが利益をもたらします$w_i$。 

そこで問題は次のようになります。$D$同一のユニット$n$それぞれに容量のあるアイテム$c_i$、単位当たりの価値で合計価値を最大化します$w_i$。 

ブルートフォースアプローチでは、キャップに関するすべてのディストリビューションが試行されます。 ユニットごとに分配することだけを考えても、各ステップには$n$選択肢、それにつながる$O(nD)$、それは不可能です$D$と同じ大きさにすることができます$10^{11}$。 

重要な観察は、値の寄与を除いてすべてのユニットが同一であるため、最適性は常に次に利用可能なユニットを最も高いユニットに割り当てることによって得られるということです。$w_i$まだ容量が残っているということ。 これにより、問題はソートされたリストに対する古典的な貪欲なプロセスに縮小されます。 

しかし、私たちはまだ特別な操作を行っています。つまり、1 つの作物の生産能力を 1 つから 2 倍まで増やすことができます。$c_i$に$m - l_i$。 これにより、価値による順序は変わりませんが、価値の高い作物が吸収できる単位数が変わり、価値の低い作物からの割り当てが置き換えられる可能性があります。 

ベースライン ソリューションは、降順で貪欲な塗りつぶしです。$w_i$。 課題は、作物ごとに、その能力が拡張された場合にソリューションがどのように変化するかを評価することです。 この拡張により、ソート順で後の作物からユニットが引き離されます。 

したがって、構造は次のようになります。グローバルな貪欲な割り当てを一度計算し、次に各候補作物の生産能力増加の効果をシミュレートします。 これは、貪欲な割り当ての末尾からシフトされるユニットの数を追跡し、それらのユニットをより価値の高いユニットに置き換えることによる純利益を測定することによって行うことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 割り当ての完全な列挙 |$O(nD)$|$O(n)$| 遅すぎる |
 | 貪欲なベースライン + 作物ごとの再計算 |$O(n^2)$|$O(n)$| 遅すぎる |
 | ソートされた貪欲 + プレフィックス/サフィックス構造 |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各作物を基本要件に変換します$l_i$、残りの予算を計算します$D = m - \sum l_i$。 これらの必須の割り当てによる利益は固定されており、最後に追加できます。 
2. 各作物の追加生産能力を定義する$c_i = r_i - l_i$。 ただいま配布中です$D$これらの容量にわたるユニット。 
3. 作物を降順に並べ替えます。$w_i$。 この順序は、すべての追加ユニットが常に最も残存価値の高いクロップに割り当てられる必要があるため、貪欲な割り当てがどのように動作するかを定義します。 
4. このソートされたリストに対する貪欲な割り当てをシミュレートします。 残りのカウンターを維持する$D$、そして作物ごとに割り当てます$y_i = \min(c_i, D)$から減算します。$D$。 これにより、ベースラインの最適な分布が生成されます。 
5. この貪欲な結果に対して、割り当てられたユニットを順番に表す構造を構築します。各ブロックは値を持ちます。$w_i$そしてサイズ$y_i$。 これは、後の変更によりユニットがブロックを越えて移動する可能性があるため必要です。 
6. 作物ごとに$i$、その緩和された容量を計算します$c_i' = m - l_i$。 追加容量は、$\Delta_i = c_i' - c_i$。 
7. もし$\Delta_i = 0$、スキップします。 それ以外の場合は、追加ユニットのクロップ数をシミュレートします。$i$ベースラインを超えて吸収することができます。 グリーディでは常により高い値のブロックが最初に埋められるため、これらのユニットはグリーディ割り当ての最後から取得する必要があります。 
8. サフィックス内のユニット数を計算します (位置以降のすべてのクロップ)$i$ソート順) が置き換えられます。 純利益は、それらのユニットを元の作物から作物に移動した値です。$i$、これは接尾語セグメントに対する合計の改善として計算されます。 
9. ブロック サイズに対するプレフィックスの合計と加重合計を使用して、取得時にサフィックスからどれだけの値が削除されるかを迅速に計算します。$k$単位は端から。 
10. 答えは、ベースライン利益に、緩和作物のすべての選択肢に対する最大の改善を加えたものです。 

### なぜ効果があるのか

 貪欲なベースラインにより、すべての実行可能な分布の中で、より高い分布が保証されます。$w_i$常に、より低い容量よりも先に容量を消費します。 これにより、最終的な割り当てがソートされたブロックのシーケンスによって完全に決定される単調な構造が作成されます。 1 つの生産能力が増加すると、この順序付けられた構造に沿って割り当てが後方に押し進められるだけであり、作物間の相対的な優先順位は決して変更されません。 これは、すべての変更が、最も値が満たされたユニットのサフィックス セグメントを削除し、選択したクロップからより高い値のユニットに置き換えることと同等であることを意味します。これにより、ローカル置換推論の最適性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        if r < l:
            return 0
        return self.sum(r) - self.sum(l - 1)

def solve():
    n, m = map(int, input().split())
    w, l, r = [], [], []
    base = 0
    extra = 0

    items = []
    for _ in range(n):
        wi, li, ri = map(int, input().split())
        w.append(wi)
        l.append(li)
        r.append(ri)
        base += wi * li
        items.append((wi, li, ri))

    items.sort(reverse=True)

    cap = []
    val = []
    for wi, li, ri in items:
        cap.append(ri - li)
        val.append(wi)

    D = m - sum(l)

    n = len(items)

    use = [0] * n
    rem = D
    for i in range(n):
        take = min(cap[i], rem)
        use[i] = take
        rem -= take

    base_extra = sum(use[i] * val[i] for i in range(n))

    # Fenwick over blocks
    bit_cnt = Fenwick(n)
    bit_val = Fenwick(n)

    for i in range(n):
        bit_cnt.add(i + 1, use[i])
        bit_val.add(i + 1, use[i] * val[i])

    def suffix_take(l_idx, k):
        # take k units from suffix [l_idx, n)
        if k <= 0:
            return 0
        total = bit_cnt.range_sum(l_idx, n)
        if k >= total:
            return bit_val.range_sum(l_idx, n)

        # find split position
        lo, hi = l_idx, n
        while lo < hi:
            mid = (lo + hi) // 2
            if bit_cnt.range_sum(l_idx, mid) >= k:
                hi = mid
            else:
                lo = mid + 1

        pos = lo
        before = bit_cnt.range_sum(l_idx, pos - 1)
        res = bit_val.range_sum(l_idx, pos - 1)
        need = k - before
        res += need * val[pos - 1]
        return res

    ans = base + base_extra

    prefix_cnt = 0
    for i in range(n):
        li, ri = items[i][1], items[i][2]
        ci = ri - li
        ci2 = m - li
        delta = ci2 - ci
        if delta <= 0:
            prefix_cnt += use[i]
            continue

        # suffix starts after i
        k = min(delta, bit_cnt.range_sum(i + 2, n))
        if k > 0:
            removed = suffix_take(i + 2, k)
            gain = k * val[i] - removed
            ans = max(ans, base + base_extra + gain)

        prefix_cnt += use[i]

    print(ans)

if __name__ == "__main__":
    solve()
```コードは最初に、以下から必須のベースライン寄与を計算します。$l_i$。 次に、残りの容量に対して貪欲な割り当てをソート順に構築します。$w_i$。 Fenwick trees store both counts and weighted sums of allocated units, which allows fast queries over suffix segments.

 ヘルパーさん`suffix_take`最後の合計値を計算します$k$範囲内のユニットを割り当てます。 プレフィックス数に対する二分探索を使用して、サフィックス分割が発生する場所を特定し、その境界ブロックから部分的な寄与を再構築します。 

各作物は、どれだけの追加単位を吸収できるか、また接尾辞から何を置き換えるかを計算することによって、緩和の候補としてテストされます。 最大の改善がベースラインに追加されます。

 ## 特殊なケース

 貪欲な充填の境界にない作物に緩和が適用される場合、微妙な状況が発生します。 その場合、その追加の生産能力は単にそれ自体の割り当てを拡張するのではなく、その後の作物からの一連のシフトを引き起こします。 

たとえば、中位の作物が緩和された場合、その追加された容量は、最初に下位の作物に割り当てられるはずだったユニットを消費します。 これらの下位ランクのクロップはすでに部分的に埋められている可能性があるため、アルゴリズムは影響を受ける完全なブロックと部分的なブロックの数を正確に計算する必要があります。 

サフィックス クエリ ロジックはこれを正確に処理します。 割り当てられたユニットのプレフィックス合計を使用して分割ポイントを特定することにより、ブロック内の部分消費が正しく考慮され、サフィックスから削除された正確な値、したがって正しいネットゲインが維持されることが保証されます。
