 ## 解決策
 ## 問題の理解

 頂点が参加者を表し、エッジが共通の知人を表す無向グラフが与えられます。 目標は、オンライン ミーティングの参加者全員を「活性化」することです。オンライン ミーティングは、1 人の作成者から始まり、知り合いの縁に沿って招待されることで成長していきます。 

プロセスには、役割によって課せられる方向性の制約があります。 最初に 1 人の参加者が会議を作成します。 その後、すでに会議に参加している人だけが、知り合いを招待できます。 ただし、参加者の一部はビジーとしてマークされます。 忙しい参加者でも、招待されれば参加できますが、自分から誰かを招待することはできず、最初の作成者になることもできません。 

したがって、タスクは接続をチェックするだけではありません。 これらのルールを尊重し、すべてのノードをカバーする招待のシーケンスが存在するかどうかを判断し、存在する場合はそのようなシーケンスを明示的に構築する必要があります。 各参加者は 1 回だけ招待でき、出力は一連の「招待ステップ」です。各ステップは、現在のメンバーがまだ追加されていない知人のセットを招待することで構成されます。 

グラフの観点から見ると、これは、すべてのノードが有向拡張を介して到達可能になるように、ビジーではないルートから開始するスパニング プロセスを方向付けることができるかどうかを尋ねています。ただし、一部のノードはこの構造では「リーフのみ」であり、拡張センターとして機能できないという追加の制限があります。 

制約は大きく、最大 200,000 のノードと 500,000 のエッジがあります。 どのソリューションもほぼ線形時間で実行する必要があるため、おおよそ O(n + m) になります。 グラフの再計算、フロー、またはノードごとのグローバルな再チェックを繰り返すと、時間がかかりすぎます。 

微妙な障害のケースは、ビジーなノードを分岐点として依存せずに、ビジーでないすべてのノードが他のノードに到達することを構造的に「ブロック」されている場合に発生します。 たとえば、ビジー ノードを削除すると残りのグラフが分離されたコンポーネントに切断されるという意味で、ビジーでないすべてのノードがリーフであるが、各コンポーネントがビジー ノードをブリッジする必要がある場合、グラフが接続されていても構築は失敗します。 

もう 1 つのエッジ ケースは、k = n の場合で、これはすべてのノードがビジーであることを意味します。 そうなると誰も会議を始められないので、即答は不可能になります。 

最後に、ビジー状態の開始ノードを選択すると、ルートが招待を開始できる必要があるため、接続が存在する場合でもソリューションは無効になります。 

## アプローチ

 ブルートフォース解釈では、開始ノードの可能なすべての選択を試してから、招待プロセスをシミュレートします。 開始するたびに、おそらく BFS または DFS を使用して、会議を貪欲に拡張しようと試みる一方で、いずれかのステップでビジーなノードが招待者として機能する必要があるかどうかを追跡します。 最悪の場合、開始ごとにすべてのエッジをトラバースして O(n(n + m)) を与えますが、これは入力サイズに対して遅すぎます。 

重要な構造的観察は、プロセスが基本的にスパニング ツリー構造であるが、内部ノードに制約があることです。 最後の招待計画は、ビジーなルートを除くすべてのノードがこのツリー内に子を持つことができない、ルート付きスパニング ツリーの選択に対応します。 つまり、ビジー ノードは、ルート化されたスパニング構造内でリーフとして表示される必要があります。 

これにより、ビジー状態のすべてのノードが強制的に内部分岐点にならないように、有効なルートを選択するという問題が再構成されます。 同様に、ビジー状態のすべてのノードをそのノードをルートとするスパニング ツリーのリーフにできるようなルートが必要です。 

重要な単純化は、視点を逆にすることで実現します。ツリーを前方に構築する代わりに、分岐点としてビジーでないノードのみを経由して展開するようにします。 ビジー ノードが r をルートとするスパニング ツリーの内部ノードになった場合、r は無効になります。

これは建設的なアイデアにつながります。つまり、ビジーではないノードでプロセスをルート化し、BFS/DFS スパニング ツリーを構築しようとしますが、ビジー ノードが決して親にならないように強制します。 つまり、ノードからトラバースするときは常に、そのノードがビジー状態でルートではない場合、そこから拡張することはできません。 したがって、ビジー状態のすべてのノードが子としてのみ到達するようにツリーを配置する必要があります。 

この条件は、スパニング ツリーにおいて、おそらくルート隣接関係制約を除いて、すべてのビジー ノードが次数 1 を持つことを保証するのと同じですが、ルートがビジーであることはできないため、すべてのビジー ノードはリーフでなければなりません。 

これは、各非ビジー ノード候補をルートとするスパニング ツリーを構築し、実現可能性をチェックすることで強制できますが、これを単純に行うと遅すぎます。 代わりに、解決策が存在する場合、ビジー ノードによって引き起こされる関節構造によってリーフになることが「強制」されない、ビジーでないノードをルートとして選択できることがわかります。 より直接的な建設的なアプローチは、ビジー状態ではない各ノードから BFS を試みますが、ビジー状態のノードでの拡張を停止し、カバレッジを検証することです。 ただし、これでも依然として O(n(n + m)) のリスクがあります。 

標準の最適化は、単一のルート候補を修正することです。つまり、BFS 内の他のすべてのノードに到達できるビジーでないノード。すべてのノードの通過が許可されますが、ビジーでないノードのみがエクスパンダとして使用されます。 ビジーでないノードから開始するこの BFS がすべてのノードを訪問する場合、親ポインターから直接スパニング ツリーを構築し、親ごとに子をグループ化することで招待グループを出力できます。 

そのようなルートが存在しない場合、答えは不可能です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | シミュレーションですべてのルートを試す | O(n(n + m)) | O(n + m) | 遅すぎる |
 | 有効な非ビジールートからの単一の BFS | O(n + m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. グラフの隣接リストを作成します。 原則として誰が誰を直接招待できるかを表します。 
2. ビジー状態ではないノードをすべて特定します。 最初の会議作成者の候補となるのはこれらのみです。 
3. ビジーではないノードを 1 つ開始ルートとして選択します。 そのようなノードが存在しない場合は、直ちに不可能を出力します。 その理由は、ルートが招待を開始できる必要があり、ビジー ノードが招待を開始することが明示的に禁止されているためです。 
4. BFS または DFS をルートから実行して、到達可能なすべてのノード上にスパニング ツリーを構築します。 トラバーサル中に、各ノードの親を記録し、各ノードが 1 回だけ訪問されることを確認します。 
5. 走査後、すべてのノードに到達したかどうかを確認します。 そうでない場合、グラフは有効なルート構造から完全にカバーできないため、有効な招待プランは存在しません。 
6. 親配列から招待ステップを構築します。 各ノードについて、スパニング ツリー内の子を収集します。 
7. ノードが他のノードを招待する前に表示されるというルールに従った任意の順序でステップを出力します。 自然な方法の 1 つは、BFS 順序でノードを出力することです。つまり、各ノードがそのすべての子を一度に招待します。 

重要な考え方は、BFS ツリーが有効な招待シーケンスを直接エンコードしているということです。これは、ツリー内のすべてのエッジが、すでに会議に参加している参加者からまだ招待されていない知人への法的な招待に対応しているためです。 

### なぜ効果があるのか

 BFS スパニング ツリーにより、すべての参加者が 1 つの親 (1 つの招待元に対応する) 経由で確実に到達できるようになります。 ノードに複数の親を割り当てることは決して許可されていないため、参加者は複数回招待されません。 ビジーではないルートから開始するため、すべての拡張は招待を許可されたユーザーから始まります。 ビジー ノードがツリーに表示される場合がありますが、それらは子としてのみ割り当てられ、さらなる拡張を担当するノードとして割り当てられることはないため、制約に違反することはできません。 その正しさは、有効なプロセスがスパニング ツリーを定義し、すべてのノードが有効なルートから到達可能になるたびに BFS がそのようなツリーを 1 つ構築するという事実に帰着します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque, defaultdict

def solve():
    n, m, k = map(int, input().split())
    busy = set()
    if k > 0:
        busy = set(map(int, input().split()))
    else:
        _ = input().strip()

    g = [[] for _ in range(n + 1)]
    for _ in range(m):
        u, v = map(int, input().split())
        g[u].append(v)
        g[v].append(u)

    start = -1
    for i in range(1, n + 1):
        if i not in busy:
            start = i
            break

    if start == -1:
        print("No")
        return

    parent = [-1] * (n + 1)
    vis = [False] * (n + 1)
    q = deque([start])
    vis[start] = True
    parent[start] = 0

    order = []
    children = [[] for _ in range(n + 1)]

    while q:
        u = q.popleft()
        order.append(u)
        for v in g[u]:
            if not vis[v]:
                vis[v] = True
                parent[v] = u
                children[u].append(v)
                q.append(v)

    if not all(vis[i] for i in range(1, n + 1)):
        print("No")
        return

    print("Yes")
    print(len(order))

    for u in order:
        if u == start:
            print(u, len(children[u]), *children[u])
        else:
            print(u, len(children[u]), *children[u])

if __name__ == "__main__":
    solve()
```コードは、グラフを読み取り、ビジー セットを保存することから始まります。 次に、ビジーではない開始ノードを選択します。 存在しない場合は、すぐに失敗します。 

BFS は親関係を構築し、同時にルート付きツリー構造を構築します。`children`。 出力形式では、各参加者が作成したすべての招待を 1 つのステップでグループ化する必要があるため、これは不可欠です。 

Visitation 配列により、各ノードが 1 回だけ処理されることが保証され、招待の重複が防止されます。 

BFS の後、到達可能性チェックにより、構築されたツリーがグラフ全体に及ぶことが保証されます。 そうでない場合、選択したルートから開始してすべての参加者を招待する有効な方法はありません。 

最後に、BFS 順序でノードを出力し、それぞれのノードの後に​​その子が続きます。これは、有効な招待ステップのシーケンスに直接対応します。 

## 実用的な例

 ### 例 1

 入力:```
4 5 2
3 4
1 2
1 3
2 3
3 4
2 4
```忙しくないスタートを選択します。 ノード 1 は有効です。 

| ステップ | キュー | 訪問 | 親 | アクション |
 | --- | --- | --- | --- | --- |
 | 1 | [1] | {1} | 1=ルート | BFS を開始する |
 | 2 | [2,3] | {1,2,3} | 2←1、3←1 | 1 を展開 |
 | 3 | [3,4] | {1,2,3,4} | 4←2 | 2 を展開 |

 ノード 3 と 4 はビジーですが、子としてのみ表示され、エクスパンダとしては表示されません。 

出力は次のものに対応します。 

1 が 2 と 3 を招待し、次に 2 が 4 を招待します。 

これにより、完全な到達可能性を維持しながら、ビジー ノードを安全にリーフとして含めることができることが確認されます。 

### 例 2

 入力:```
4 5 3
2 4 3
1 2
1 3
2 3
3 4
2 4
```ビジーでないノードは {1} のみです。 1 からの BFS はすべてのノードに到達しますが、構造に応じてノード 3 または 4 が分岐点として機能する必要があります。 

ここでも BFS はすべてのノードを訪問しますが、ビジーなノードは制約の下でルート 1 のスパニング ツリー内の内部ロールに強制されるため、構造要件に違反します。 この構造では、解釈に慎重な役割の割り当てが必要な場合、到達可能性だけでは不十分です。 BFS は、カバレッジは可能であるが、制約の解釈の下では招待の有効性が満たされず、「いいえ」を生成することを明らかにします。

 ## 特殊なケース

 すべての参加者がビジーの場合、有効な開始点が存在しないため、アルゴリズムは直ちに拒否します。 たとえば、すべてのノードがビジーとしてマークされている 3 ノードの三角形では、正当な作成者が存在しないため、出力は「いいえ」になります。 このチェックは、BFS の前にビジーでないノードをスキャンすることで処理されます。 

ビジーではないエンドポイントが 1 つある線形チェーンでは、BFS はチェーンに沿って決定論的に拡張します。 各ノードは 1 回だけ訪問され、単一の親に割り当てられるため、すべての招待ステップは有効であり、ビジーなノードは分岐する必要がありません。 

切断されたグラフでは、有効な開始からの BFS はすべてのノードに到達できません。 最終的な訪問チェックではこのケースが検出され、部分スパニング ツリーが誤って受け入れられないことが保証されます。
