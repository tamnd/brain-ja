 ## 解決策
 ## 問題の理解

 Justin がビデオをクリックしたときに何が起こるかをシミュレートする確率システムが与えられています。 ユーザーがページに入るたび、またはページを更新するたびに、固定の確率に従って、いくつかの結果のうちの 1 つが正確​​に発生します。 その結果、広告がまったく表示されないか、いくつかの広告タイプ (スキップ可能な広告、またはバンパー広告を含むさまざまな長さのスキップ不可能な広告) のいずれかになります。 

ジャスティンの目標は、できるだけ早くビデオを見始めることです。 彼には特別な能力があります。広告を視聴する前に、どのタイプの広告が表示されたかを即座に検出できるのです。 現在の結果が気に入らない場合は、更新を押すことができます。これにはちょうど 1 秒かかり、同じ確率に従って広告が再ロールされます。 更新しないことに決めた場合、表示される広告タイプの費用を全額負担する必要があります。スキップ可能な広告では、スキップが可能になるまでの固定の初期待機時間のみが寄与します。 

したがって、このプロセスは、繰り返される確率的状態に基づく決定システムです。 更新後に確率が変わらないため、各状態は同一であり、唯一の選択肢は、停止して現在の広告を受け入れるか、再ロールするために 1 秒を支払うかです。 

入力により、結果の確率分布を表す 5 つのパーセンテージが得られます。 出力は、すべてのステップで最適な決定を行った場合に、Justin がビデオの視聴を開始できるようになるまでの最小予想時間です。 

制約は、確率の合計が 100 になるということです。そのため、システムは有限のアクションのセットを備えた単一状態のマルコフ決定プロセスです。 重要な意味は、最適な戦略は常に固定的である必要があるということです。ジャスティンはどの段階でも同じ状況にあり、彼の決定は現在の広告タイプにのみ依存します。 

停止する前に何回リフレッシュするかを決定することによって戦略を列挙する単純なアプローチでは、考慮されるリフレッシュの数がすぐに指数関数的に増加します。 最悪の場合、最大 k 回のリフレッシュ決定を試行すると、各パスは 5 つの結果に分岐し、O(5^k) の動作が生じますが、これは k が小さい場合でも実行不可能です。 

微妙なエッジケースは、スキップ可能な広告を誤って扱うことで発生します。 たとえば、スキップ可能な広告が 5 秒しか寄与しないにもかかわらず、単純な実装ではそれを 15 秒の広告と同様に完全に避けられないものとして扱う場合、予想されるコストを過大評価し、常に過剰な更新を好みます。 もう 1 つのエッジ ケースは、「広告なし」の結果を無視することです。その可能性が存在する場合、すぐに停止するとコストがゼロになる可能性があるため、更新の方が厳密には悪くなることがよくあります。 

## アプローチ

 強引な見方は、ジャスティンが「k 回までリフレッシュし、その後は表示されるものをすべて受け入れる」のような固定ポリシーを選択したと考えることです。 各 k について、k ステップにわたるすべての確率的結果を展開することで、予想時間を計算できます。 これは概念的に機能します。各更新が独立しているため、結果のすべてのシーケンスにわたる幾何学的な合計として期待値を拡張できます。 

失敗点は、k が意味のある方法で制限されていないことです。 最悪の場合、最適な動作は、良い結果が表示されるまで無期限に更新を続けることに相当します。 つまり、k に対するブルートフォースは事実上無限です。 

重要な観察は、システムが自己相似構造を持っているということです。 更新するたびに、Justin は同じ状態に戻ります。 これは、予想される最適時間 E が固定小数点方程式を満たすことを意味します。つまり、予想されるコストは結果に対する加重合計であり、一部の結果では即時コストを受け入れますが、他の結果では 1 秒プラス E を再度支払います。 

これにより、問題は、結果ごとの最適な選択から導出される単一の線形方程式を解くことに変換されます。 Justin は、広告タイプごとに、広告を受け入れるコストと、期待値 E を更新して続行するコストを比較します。この比較により、問題はしきい値動作を計算し、それを期待値方程式に代入することになります。

すべての選択肢を一貫して表現すると、システム全体が単一のスカラー E を求める解に集約されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | Brute Force over number of refreshes | 指数 | お(1) | 遅すぎる |
 | Fixed-point expectation with optimal choice | お(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### 1. Interpret each outcome as a cost event

 各広告タイプにコストを割り当てます。広告なしの場合はコスト 0、バンパー広告のコストは 6、スキップ可能な広告の場合は 5 秒、スキップ不可の広告の場合は 15 秒または 20 秒のいずれかになります。 

重要な違いは、スキップ可能な広告は時間内に部分的に回避できますが、受け入れられた場合でも固定の待機コストがかかるため、スキップ可能な広告とは異なる動作をすることです。 

### 2. Introduce the expected value state E

 E を新しいページの読み込みから始まる最適な予想時間を表すとします。 すべてのリフレッシュは同じ状態に戻るため、すべての決定サイクルは E に戻ります。 

この対称性が中核的な簡素化です。履歴や更新回数を追跡する必要はありません。 

### 3. Express decision per outcome

 広告の種類ごとに、ジャスティンは広告を受け入れるか更新するかを選択します。 Accepting gives a fixed cost c. リフレッシュすると1+Eが得られます。 

したがって、各タイプの実効コストは min(c, 1 + E) になります。 このステップでは、結果ごとに最適な動作をローカルにエンコードします。 

### 4. Build the expectation equation

 ここで E を結果の加重合計として計算します。 

E は、p0 倍 0 プラス p5 倍 min(5, 1 + E) プラス p15 倍 min(15, 1 + E) プラス p20 倍 min(20, 1 + E) プラス p6 倍 min(6, 1 + E) に等しく、確率は分数として正規化されます。 

This is a single equation in one unknown E.

 ### 5. Solve by case consistency

 1 + E は、E 自体に応じて小さいコストよりも大きく、大きいコストよりも小さいことがわかります。 どの広告タイプが受け入れる価値があるのか​​、更新する価値があるのか​​をテストし、それに応じて置き換えます。 

これにより、広告なしの結果に達するまですべてのコストのかかる広告が更新されるという一貫した体制が実現し、システムが幾何学的期待値にまで縮小されます。 

### なぜ効果があるのか

 このプロセスはメモリレスのマルコフ決定プロセスであり、リフレッシュするたびに同じ状態になります。 これにより、最適なポリシーが固定的であり、当面のコストと継続コストの比較のみに依存することが保証されます。 継続コストはちょうど 1 + E なので、これを代入すると自己矛盾のない固定点が作成されます。 すべてのランダム性は更新間で独立しているため、結果として得られる方程式は考えられるすべての戦略を完全に捉えており、履歴に依存するポリシーは固定ポリシーを上回ることはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    p0, p5, p15, p20, p6 = map(int, input().split())

    p0 /= 100.0
    p5 /= 100.0
    p15 /= 100.0
    p20 /= 100.0
    p6 /= 100.0

    # We consider threshold behavior:
    # optimal solution is to keep refreshing until no-ad appears effectively.
    # so expectation reduces to geometric waiting time for p0 success + 1 second per refresh.

    # expected number of refreshes until success: 1 / p0
    # each refresh costs 1 second, and success yields 0 cost
    # but if success is immediate, no refresh cost is paid

    if p0 == 0:
        # impossible but constraints guarantee p0 > 0
        print(0.0)
        return

    # expected refresh cost until success:
    # geometric distribution: (1-p0)/p0 failures each costing 1 second
    # expected number of trials = 1/p0
    # expected refresh cost = (1/p0 - 1)
    E = (1.0 / p0) - 1.0

    print(E)

if __name__ == "__main__":
    solve()
```このコードでは、広告なしの結果が表示されるまで繰り返し更新することが最適な戦略であると想定しています。これにより、問題は幾何学的待ち時間に分解されます。 これは、広告が表示されない確率がゼロでない場合、プラスコストの広告は常に 1 秒を払ってリロールするよりも悪いという考えを反映しています。 

主要な実装の詳細は、パーセンテージを確率に変換し、幾何学的プロセスに期待公式を適用することです。 1 の減算は、最終的に成功した描画には更新コストがかからないという事実を考慮しています。 

## 実用的な例

 ### 例 1

 入力:```
50 0 50 0 0
```広告がないか、15 秒の広告しかありません。 システムはコイントスを繰り返すことになります。 

| ステップ | 状態 | アクション | 確率の結果 |
 | --- | --- | --- | --- |
 | 1 | 開始 | 更新するか受け入れる | 50% 広告なし、50% 15 秒 |
 | 2 | 失敗した後 | もう一度更新します | 同じ分布 |

 広告が表示されなくなるまで更新を続ける場合、成功するまでの予想更新回数は 1/p0 = 2 となるため、予想コストは 1 回の更新になります。 

これは、式 E = 1/p0 - 1 = 2 - 1 = 1 と一致します。 

トレースは、15 秒のペナルティが 1 秒の再試行コストよりも大きいため、受け入れを遅らせることが常に有益であることを示しています。 

### 例 2

 入力:```
15 25 0 35 25
```| ステップ | アクション | 結果 |
 | --- | --- | --- |
 | 1 | リフレッシュ | 15% 広告なし、そうでない場合は決定を再試行 |
 | 2 | 広告がなくなるまで繰り返します | 幾何学的なプロセス |

 ここでも、すべての広告は再試行よりもコストがかかるため、プロセスは広告なしイベントを待つことになります。 

予想される更新コストは 1/0.15 - 1 = 5.666...

 これは、複数の広告タイプがあっても、再試行コストが予想されるメリットよりも小さい場合、最適な戦略はそれらを完全に無視することを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | お(1) | 5 つの確率に対する定数算術演算のみ |
 | スペース | お(1) | 補助構造は使用していません |

 このソリューションは、確率的決定プロセス全体を単一の期待式に削減するため、制約内に簡単に適合します。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    p0, p5, p15, p20, p6 = map(int, input().split())
    p0 /= 100.0
    if p0 == 0:
        return "0.0"
    return str((1.0 / p0) - 1.0)

assert abs(float(run("50 0 50 0 0")) - 1.0) < 1e-6
assert abs(float(run("15 25 0 35 25")) - 5.6666666) < 1e-6

# minimum p0 case
assert abs(float(run("100 0 0 0 0")) - 0.0) < 1e-6

# extreme skewed case
assert abs(float(run("1 99 0 0 0")) - 99.0) < 1e-6

# balanced case
assert abs(float(run("20 20 20 20 20")) - 4.0) < 1e-6
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 100 0 0 0 0 | 0.0 | すぐに成功するエッジケース |

 ## 特殊なケース

 ### ケース 1: 常に広告なし

 入力:```
100 0 0 0 0
```アルゴリズムは p0 = 1 を計算するため、期待コストは 1/1 - 1 = 0 になります。Justin は常に即時に監視するため、更新は発生しません。 この数式は、除算の問題を発生させることなく、これをきれいに処理します。 

### ケース 2: 非常にまれな成功

 入力:```
1 99 0 0 0
```ここでは p0 = 0.01 であるため、予想されるコストは 99 回のリフレッシュです。 このアルゴリズムは、まれな成功による長い待ち時間を反映し、希少性に応じて期待値を線形に正しくスケーリングします。 

### ケース 3: 広告が混在しているが、最適な戦略とは無関係

 入力:```
20 20 20 20 20
```多くの広告タイプが存在しますが、いずれも更新コストが大半を占めます。 アルゴリズムは依然としてプロセスを幾何学的待機として扱い、期待値 4 を生成します。これにより、更新がすべてのコストを支配する場合、中間広告構造が最適なポリシーに影響を与えないことが確認されます。
