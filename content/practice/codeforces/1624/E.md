 ## 解決策
 ## 問題の理解

 ターゲットの数字列が与えられます`s`すべて同じ長さの既知の数字列のコレクション。 目標は再建です`s`連続したセグメントのシーケンスとして、各セグメントは既知の文字列の 1 つから取得された部分文字列と正確に一致する必要があります。 すべてのセグメントの長さは少なくとも 2 でなければならないため、単一の数字を単独で「説明」することはできません。 

有効な答えは、ポジションの分割です。`s`連続したブロックに分割します。 各ブロックについて、そのブロックがどの既知の文字列からのものであるか、およびその文字列内の正確な部分文字列境界も指定する必要があります。 異なるブロックは、異なる既知の文字列から取得される場合があります。 

したがって、実際のタスクは、部分文字列が存在するかどうかをチェックするだけではなく、文字列のタイリングを選択することです。`s`最小セグメント長の制約のある、再利用可能な部分文字列ソースを使用します。 

制約はテストごとではなく全体として厳しいものです。 の合計`n * m`すべてのテスト ケースで最大 10^6 です。これは、部分文字列の一致を位置ごと、文字列ごとに繰り返し再計算するなどのソリューションは、この合計サイズが線形または線形に近い場合にのみ許容されることを強く示唆しています。 立方体のものなら何でも`m`テストケースごとに失敗します。 

いくつかの故障モードが自然に発生します。 

最初の単純な間違いは、位置 1 から一致する最も長いセグメントを貪欲に取得することです。これは失敗します。長い一致により、後で必要な短い分解がブロックされる可能性があるためです。 たとえば、次の場合`s`ある文字列内に存在する長い部分文字列で始まりますが、強制的に行き止まりになり、貪欲な選択では回復できません。 

2 番目の微妙な問題は、1 つの既知の文字列からのマッチングで十分であると仮定していることです。 正しい解決策には、さまざまな既知の文字列からのソースを混合することが必要な場合があるため、位置ごとに単一の「最もよく一致する音」を事前に選択するアプローチでは不十分です。 

最後に、重複が重要です。複数の部分文字列が同じ位置で一致する可能性があり、その 1 つを選択することが将来の到達可能性に影響します。 これにより、問題は独立したローカル一致ではなく、制約されたパス構築に変わります。 

## アプローチ

 強引なアイデアは、問題を位置のパス検索として扱うことです。`s`。 それぞれの立場から`i`、少なくとも 2 の長さのすべてのセグメントを試し、各セグメントについて、既知の文字列のいずれかにそのセグメントが存在するかどうかを確認します。 存在する場合は、次の位置から再帰的に続行します。 これにより、巨大な分岐ツリーが形成されます。各インデックスで次のことを試みることができます。`m`終了位置、それぞれについてすべてをスキャンできます`n`部分文字列を検証するための文字列。 

ハッシュを使用した部分文字列の比較が O(1) である場合でも、状態ごとの遷移の数は依然として O(m^2) であり、状態が m 個あるため、最悪の場合はテストごとに O(m^3) になります。 複数のテスト ケースでは、これは 10^9 の演算を軽く超えます。 

重要な点は、すべての出来事を独立して考慮する必要はないということです。 重要なのは、各ポジションについてです。`i`、エンドポイント`j`部分文字列を許可する`s[i..j]`少なくとも 1 つの既知の文字列に出現すること。 から始まるすべての有効な間隔がわかったら、`i`、問題はインデックス上の最短経路/到達可能性の問題になります。 

これにより、既知の文字列のすべての部分文字列を前処理し、どの部分文字列が存在するかを保存し、動的プログラミングまたは BFS を使用して位置を指定するタスクが軽減されます。`s`。 

標準的な手法は、既知の文字列から長さ 2 以上のすべての部分文字列をハッシュ セットに保存することですが、これを単純に行うと大きすぎます。 代わりに、既知の文字列ごとにローリング ハッシュを事前計算し、文字列ごとに O(m^2) のすべての部分文字列を挿入します。これはグローバル制約の下で許容されます。 

この前処理の後、次のポジションに対して DP を実行します。`s`:`dp[i]`からセグメント化できるかどうかを示します`i`最後まで。 全部試してみます`j >= i+1`かどうかを確認してください`s[i..j]`セットに入っています。 また、ソリューションを再構築するために親ポインターも保存します。 

これが機能するのは、制約が慎重に実装された場合にのみ最悪の場合でも O(sum n_m^2) を許可するためですが、ここでは n_m の合計が制限されているため、部分文字列の合計列挙は依然として管理可能です。

 ## アルゴリズムのチュートリアル

 すべての既知の電話番号を、部分文字列の存在を迅速にテストできる構造に変換し、有効なタイリングを検索します。`s`。 

1. 既知の文字列ごとに、すべてのプレフィックスのローリング ハッシュを計算し、部分文字列のハッシュを O(1) で取得できるようにします。 これにより、等価性をチェックする際に文字比較を繰り返すことがなくなります。 
2. すべての既知の文字列から少なくとも 2 の長さのすべての部分文字列をグローバル ハッシュ マップまたはセットに挿入し、代表的な出現も 1 つ保存します。`(string_id, l, r)`復興のために。 このステップでは、許可されたセグメントの「辞書」を構築します。 
3. DP アレイの作成`dp[i]`サフィックスをセグメント化できるかどうかを意味します`s[i:]`。 初期化する`dp[m] = True`空のサフィックスが有効であるため。 
4. 位置を右から左に処理します。 それぞれについて`i`、すべて試してください`j`そのような`j >= i+1`。 部分文字列の場合`s[i..j]`辞書に存在しており、`dp[j+1]`true、設定されています`dp[i] = True`そしてその選択を記録します`(i, j)`。 
5. DP の後、次の場合`dp[0]`false の場合、出力は -1 です。 
6. それ以外の場合は、位置 0 から格納されている選択肢に従って再構築し、格納されているソース文字列と部分文字列のインデックスをセグメントごとに出力します。 

なぜ効果があるのか​​: あらゆるポジションで`i`で始まる有効なセグメントが少なくとも 1 つ存在する場合、到達可能とマークします。`i`それは到達可能なサフィックスにつながります。 DP は、完全なパーティションと一致するセグメントのみを受け入れることを保証します。 すべての有効な部分文字列を探索するため、実行可能な継続を見逃すことはありません。また、遷移は許可されたセグメントと正確に一致するため、無効なセグメントを構築することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_hashes(s, base=91138233, mod=(1 << 64)):
    n = len(s)
    pref = [0] * (n + 1)
    power = [1] * (n + 1)
    for i in range(n):
        pref[i + 1] = (pref[i] * base + (ord(s[i]) - 48)) & ((1 << 64) - 1)
        power[i + 1] = (power[i] * base) & ((1 << 64) - 1)
    return pref, power

def get_hash(pref, power, l, r):
    return (pref[r] - pref[l] * power[r - l]) & ((1 << 64) - 1)

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        input()
        n, m = map(int, input().split())
        a = [input().strip() for _ in range(n)]
        s = input().strip()

        substr_map = {}

        # preprocess all substrings
        for idx, st in enumerate(a):
            pref, power = build_hashes(st)
            for i in range(m):
                for j in range(i + 1, m):
                    h = get_hash(pref, power, i, j + 1)
                    if h not in substr_map:
                        substr_map[h] = (idx, i, j)

        dp = [False] * (m + 1)
        parent = [None] * (m + 1)
        dp[m] = True

        pref_s, power_s = build_hashes(s)

        for i in range(m - 1, -1, -1):
            for j in range(i + 1, m):
                h = get_hash(pref_s, power_s, i, j + 1)
                if h in substr_map and dp[j + 1]:
                    dp[i] = True
                    parent[i] = (j, substr_map[h])
                    break

        if not dp[0]:
            out.append("-1")
            continue

        res = []
        i = 0
        while i < m:
            j, (idx, l, r) = parent[i]
            res.append(f"{l + 1} {r + 1} {idx + 1}")
            i = j + 1

        out.append(str(len(res)))
        out.extend(res)

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションは、部分文字列の存在をハッシュ ルックアップに変換することを中心に構築されています。 前処理ステップでは、すべての候補セグメントを列挙し、代表的なソース オカレンスを保存するため、再構成が可能になります。 DP ステップにより、多くのセグメントがローカルで有効であっても、完全なカバーにつながるセグメントのみが受け入れられることが保証されます。 

実装の微妙な詳細の 1 つは、ハッシュごとに 1 つのオカレンスのみを保存することです。 この問題では任意の有効な答えが許容されるため、すべての一致は必要なく、代表者は 1 人だけであるため、これで十分です。 

もう 1 つの重要な点は、前処理中に長さを少なくとも 2 にすることを強制することです。 この制限がないと、DP は問題の制約に違反する無効な 1 桁のセグメントを生成します。

 ## 特殊なケース

 重要なエッジ ケースは、有効な短い部分文字列しか存在しないが、より長い貪欲なセグメントが魅力的に見える場合です。 DP は、コミットする前にサフィックスの到達可能性を検証することで正確さを保証します。 

もう 1 つのケースは、多くの既知の数値に現れる繰り返し部分文字列です。 有効な分解であればどれでも受け入れられ、再構成には 1 つの証人だけが必要なため、代表的な出来事を 1 つだけ保存することも機能します。 

最後に、いつ`s`有効な部分文字列に決して出現しない数字が含まれている場合、ハッシュ一致が見つからないため、これらの位置は DP で到達不能のままになり、失敗が直ちに開始状態に伝播されます。
