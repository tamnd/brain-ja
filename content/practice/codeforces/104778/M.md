 ## 解決策
 ## 問題の理解

 単一文字の反転を通じて時間の経過とともに変化するバイナリ文字列が与えられます。 これらの更新に加えて、部分文字列に関する構造的な質問が繰り返し出されます。つまり、各色クラスが元の順序で読み取られたときに、隣接する 2 つの等しいビットが存在しない文字列を形成するには、その文字に割り当てる色が何色必要かという問題です。 

言い換えると、部分文字列のインデックスをグループ (色) に分割する必要があります。 任意の 1 つのグループを取得し、部分文字列の文字を元の順序で読み取る場合、結果のシーケンスは厳密に 0 と 1 の間で交互になる必要があります。したがって、単一の色は、射影後に 2 つの等しい連続ビットを含めることができないチェーンのように動作します。 

各クエリ部分文字列について、それをカバーするのに必要な交互チェーンの最小数を見つけなければなりません。 文字列は動的であるため、ポイント フリップと範囲クエリの両方がサポートされている必要があります。 

制約は大きく、最大 4 · 10^5 文字と 2 · 10^5 演算です。 全範囲にわたってクエリごとに情報を再計算するソリューションは制限を超えます。 クエリあたり O(n) であっても、最悪の場合、およそ 8 · 10^10 の操作が必要になりますが、これは不可能です。 これにより、対数更新または償却更新とクエリをサポートする構造が即座に強制されます。 

部分文字列がすでに交互になっている場合、微妙なエッジケースが発生します。 たとえば、s = 01010 の場合、答えは 1 でなければなりません。単純な解釈では、定義により複数の色が常に必要であると誤って考える可能性がありますが、単一の色は条件を簡単に満たします。 もう 1 つのエッジ ケースは、00000 のような定数部分文字列です。この場合、すべてのペアが同一であり、各要素が強制的に異なる交互のチェーンになり、長さに等しい答えが得られます。 正しい解は、これらの極端な値の間を正しく補間する必要があります。 

## アプローチ

 まず、直接的な構築の観点から考えます。 部分文字列を修正します。 各位置に色を割り当て、各色内で隣接する等しい値が決して表示されないようにしたいと考えています。 これは、2 つの等しいビットが同じ色で表示されるときは常に、元の順序でそれらの間に少なくとも 1 つの反対のビットが存在する必要があることを保証することと同じです。 

強引なアイデアは、部分文字列を左から右に処理し、交互制約に違反しない最初の有効な色に各位置を貪欲に割り当てることです。 有効性をチェックするには、色ごとに最後に割り当てられたビットを追跡する必要があります。 各文字では、既存の色をすべてスキャンする必要がある場合があります。 最悪のケース（同一のビットの文字列など）では、すべての位置に新しい色を作成し、挿入のたびに以前のすべての色がスキャンされる可能性があるため、最悪の場合、クエリごとに O(n^2) の動作が発生します。 

重要な観察は、部分文字列を最大の等しいセグメントに圧縮するときにバイナリ値が何回変化するかによってのみ、答えが決まるということです。 各セグメントは同一のビットの連続です。 ラン内ではすべての文字が同一であるため、同じ色のシーケンス内の反対側のランで区切られない限り、2 つの文字が同じ色を共有することはできません。 これにより、実行間の遷移をカバーするのと同等の制約が作成されます。 

値が 0 から 1、または 1 から 0 に切り替わるたびに、重なりを増やさずに隣接するラン間での色の再利用を防ぐ「境界」が導入されます。 最適な色の数は、そのような実行境界の数を切り上げた数の半分であることがわかります。 直観的には、各色は交互を維持した形で最大 2 つの実行トランジションをカバーできるため、すべてのトランジションをペアでカバーするのに十分な色が必要です。 

したがって、問題は、フリップ下でラン構造を動的に維持することと、任意の範囲について、隣接する等しいペアまたは遷移がいくつ存在するかを答えることに帰着します。 これにより実行回数を計算し、そこから答えを導き出すことができます。

更新と範囲クエリを効率的にサポートするために、各セグメントの最初と最後の値、およびセグメント内の遷移の数を保存するセグメント ツリーを維持します。 2 つのセグメントをマージする場合、トランジション数を追加し、それらの間の境界によって余分な変更が導入されるか、または 2 つの実行がマージされるかどうかを調整します。 

これにより、O(log n) 内の任意の部分文字列の実行数を計算できるため、遷移数も計算できます。 答えは実行回数の単純な算術関数になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | クエリあたり O(n^2) | お(1) | 遅すぎる |
 | セグメント ツリーのオーバーラン | クエリ/更新ごとに O(log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列を等しい文字の連続として扱いますが、それをセグメント ツリー内で暗黙的に維持するため、更新の際に実行をグローバルに再構築する必要はありません。 

1. 各ノードがセグメント内の最初の文字、最後の文字、およびトランジションの数を格納するセグメント ツリーを構築します。 遷移とは、そのセグメント内で s[i] != s[i+1] となるような位置 i です。 
2. リーフ ノードの場合、初期化は簡単です。first = last = s[i]、transitions = 0 です。これは、長さ 1 の単一のランをエンコードします。 
3. 2 つの子をマージする場合、それらの遷移カウントを合計します。 左の子の最後の文字が右の子の最初の文字と異なる場合は、トランジションを 1 つ追加します。 このステップは、中央を横切るラン境界を正確に考慮します。 
4. 更新クエリごとに、単一の文字を反転して対応するリーフを更新し、値を上方に再計算します。 各再計算は子にのみ依存するため、対数的な時間がかかります。 
5. 範囲クエリごとに、セグメント ツリーをクエリして、[l, r] のマージされたノードを取得します。これにより、その部分文字列内の遷移の合計数が得られます。 
6. 遷移ごとに実行数が 1 ずつ増加するため、遷移を実行数に変換します (実行 = 遷移 + 1)。 
7. 答えを (runs + 1) // 2 として計算します。これは、各カラー クラス内の交互に違反することなくすべての実行をカバーするために必要な交互カラー チェーンの数を反映します。 

### なぜ効果があるのか

 どのカラー クラス内でも、抽出されたシーケンスは交互に配置される必要があるため、抽出された順序で 2 つの等しいビットが連続して出現することはできません。 元の部分文字列内の各ランでは、ラン全体にわたる色の割り当て間の分離制約が強制されます。 単一の色は、交互に違反することなく最大 1 つの境界を安全に「スキップ」できますが、競合を強制することなく連続する 2 つの境界を「スキップ」することはできません。 これにより、単一の色がラン構造をいかに効率的にカバーできるかが制限されます。 セグメント ツリーはマージ中のラン構造を正しく保存し、トランジションからランへの変換では交互チェーンの最小数を計算するために必要なすべての情報を保存します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("lch", "rch", "first", "last", "trans")
    def __init__(self, first=0, last=0, trans=0):
        self.lch = None
        self.rch = None
        self.first = first
        self.last = last
        self.trans = trans

def merge(a, b):
    if a is None:
        return b
    if b is None:
        return a
    res = Node()
    res.first = a.first
    res.last = b.last
    res.trans = a.trans + b.trans + (1 if a.last != b.first else 0)
    return res

class SegTree:
    def __init__(self, s):
        self.n = len(s)
        self.s = s
        self.size = 1
        while self.size < self.n:
            self.size *= 2
        self.tree = [Node(0, 0, 0) for _ in range(2 * self.size)]
        self.build()

    def build(self):
        for i in range(self.n):
            v = int(self.s[i])
            self.tree[self.size + i] = Node(v, v, 0)
        for i in range(self.size - 1, 0, -1):
            self.tree[i] = merge(self.tree[2 * i], self.tree[2 * i + 1])

    def update(self, idx):
        i = self.size + idx
        v = 1 - self.tree[i].first
        self.tree[i] = Node(v, v, 0)
        i //= 2
        while i:
            self.tree[i] = merge(self.tree[2 * i], self.tree[2 * i + 1])
            i //= 2

    def query(self, l, r):
        l += self.size
        r += self.size
        left_res = None
        right_res = None
        while l <= r:
            if l % 2 == 1:
                left_res = merge(left_res, self.tree[l])
                l += 1
            if r % 2 == 0:
                right_res = merge(self.tree[r], right_res)
                r -= 1
            l //= 2
            r //= 2
        return merge(left_res, right_res)

def solve():
    n = int(input())
    s = list(input().strip())
    q = int(input())

    st = SegTree(s)

    out = []
    for _ in range(q):
        tmp = input().split()
        if tmp[0] == '1':
            i = int(tmp[1]) - 1
            s[i] = '1' if s[i] == '0' else '0'
            st.update(i)
        else:
            l = int(tmp[1]) - 1
            r = int(tmp[2]) - 1
            res = st.query(l, r)
            transitions = res.trans
            runs = transitions + 1
            ans = (runs + 1) // 2
            out.append(str(ans))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```セグメント ツリーには、連結全体で実行構造を保持するために必要な 3 つの情報が正確に保存されます。 更新操作では、単一のリーフを反転し、影響を受けるパスのみを再構築します。 クエリは部分文字列を表す完全にマージされたノードを返し、そこから遷移が実行に変換され、さらに最終的な応答に変換されます。 この式は集計後にのみ適用され、ポジションごとのシミュレーションが回避されます。 

よくある落とし穴は、境界文字を保存せずに更新の直下で実行カウントを維持しようとすることです。 最初/最後の情報がないと、エンドポイントの同等性に応じて新しい遷移が表示されたり消えたりする可能性があるため、2 つのセグメントをマージすると境界で正確さが失われます。 

## 実用的な例

 小さな文字列 s = 00110 を考えてみましょう。 

全範囲をクエリする:

 | ステップ | セグメント | 最初 | 最後 | トランジション | 走る |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | 0 | 0 | 1 |
 | 2 | 00 | 0 | 0 | 0 | 1 |
 | 3 | 001 | 0 | 1 | 1 | 2 |
 | 4 | 0011 | 0 | 1 | 1 | 2 |
 | 5 | 00110 | 0 | 0 | 2 | 3 |

 実行数 = 3 なので、答え = (3 + 1) // 2 = 2 となります。 

これは、文字列に遷移がわずかしかない場合でも、交互の色チェーンにグループ化すると、すべての実行で単一の色を再利用できないことがわかります。 

ここで、s = 01010 について考えてみましょう。 

| ステップ | セグメント | 最初 | 最後 | トランジション | 走る |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | 0 | 0 | 1 |
 | 2 | 01 | 0 | 1 | 1 | 2 |
 | 3 | 010 | 0 | 0 | 2 | 3 |
 | 4 | 0101 | 0 | 1 | 3 | 4 |
 | 5 | 01010 | 0 | 0 | 4 | 5 |

 実行 = 5、答え = (5 + 1) // 2 = 3。 

これは、実行ごとに色の再利用に依然として制約が課されるため、完全な代替では必要な色の数が文字列の長さの線形分数よりも減らない場合を示しています。

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n) | 各更新とクエリはセグメント ツリー パスをたどります。

 ## 特殊なケース

 単一文字の部分文字列には常に遷移が 0 つと実行が 1 つあります。 セグメント ツリーは trans = 0、runs = 1 を返し、式は (1 + 1) // 2 = 1 を与えます。これは、1 つの色が交互を自明に満たすという事実と一致します。 

000000 のような定数部分文字列の場合、すべてのマージでは first = last = 0 が維持され、内部遷移は蓄積されません。 セグメント全体にわたる各拡張は 1 つの実行のままで、答え (6 + 1) // 2 = 3 が生成されます。これは、どのカラー クラスも非交互射影を作成しないように、同一のブロックを分離する必要性に一致します。 

010101 のような完全に交互の部分文字列の場合、遷移は n - 1 に等しく、実行は n に等しくなります。 この式はおよそ n / 2 + 1 をもたらします。これは、元の文字列が完全に交互しているにもかかわらず、各カラー クラスが、抽出されたシーケンス内の隣接性制約に違反することなく、制限されたラン構造間でのみ安全にインターリーブできることを反映しています。
