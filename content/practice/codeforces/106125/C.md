 ## 解決策
 ## 問題の理解

 もともと有効な算術式を形成していた複数の文字セットが与えられていますが、すべての文字がシャッフルされています。 私たちの仕事は、これらの文字を構文的に有効な式に再配置できるかどうかを判断し、再配置できる場合は、そのような式を 1 つ出力することです。 

ターゲット式は、標準のプログラミング言語の文法に従います。 原子値としての変数と数値で構成され、二項演算子を使用して結合されます。`+`そして`*`、および括弧でグループ化を制御します。 乗算は加算よりも優先され、括弧は正確性のために必要な場合にのみ使用され、結合性や優先順位の規則によって引き起こされる冗長なグループ化には使用されません。 

重要な点は、単に与えられた式を検証しているだけではないということです。 提供された文字を正確に使用して、有効な元の式を再構築しています。 すべての文字は 1 回だけ使用する必要があります。 

この制約では最大 300,000 文字が許可されており、配置を並べ替えたり検索したりするアプローチは即座に排除されます。 どのような解決策でも、問題をカウントと構造的な実現可能性チェックに落とし込み、線形または線形に近い時間で答えを構築する必要があります。 

人々が構造を尊重せずに貪欲にトークンを形成しようとすると、素朴だが重要な失敗モードが現れます。 たとえば、次のようなものが与えられると、`a+b*c`単純な構造では、すべてのオペランドを最初に配置し、次に演算子を配置する可能性がありますが、これにより、優先順位の要件や括弧の使用可能性が簡単に破られる可能性があります。 もう 1 つの微妙な失敗が数値で発生します。`012`有効な数値として解釈できませんが、`0`、`1`、`2`別々に使用できます。 数字をやみくもに連結して複数桁の数字にするアプローチを使用すると、不正な先行ゼロが作成される可能性があります。 

3 番目のよくある落とし穴は、括弧のバランスを無視することです。 オペランドと演算子が完全に一致する場合でも、式ツリーでは使用可能な文字からは形成できない括弧が必要になる場合があります。 

## アプローチ

 構造を無視すると、問題は順列パズルのように見えます。文字列の考えられるすべての順列を生成し、どの順列が有効な式を形成するかを確認してみることができます。 これは文字を並べ替えているだけなので原理的には正しいのですが、階乗爆発により、たとえ小さな入力であっても完全に実行不可能になります。 30万文字もあれば、列挙して考えることさえ不可能です。 

文法を逆にすると、より構造化されたビューが得られます。 有効な式は、葉がオペランド (数値または変数) であり、内部ノードが演算子であるバイナリ ツリーです。 括弧は、平坦化された文字列表現で優先順位に違反する場合に、ツリー構造を強制するためにのみ表示されます。 

この観点では、問題を、文字を 3 つの役割 (オペランド、演算子、括弧) に分割できるかどうかをチェックし、次にこれらのリソースが少なくとも 1 つの有効なバイナリ式ツリーを構築するのに十分であるかどうかをチェックすることに帰着します。 

重要な観察点は、有効な式は次のとおりであるということです。`k`オペランドは正確に指定する必要があります`k - 1`演算子と構文ツリーは接続され、完全にバイナリである必要があります。 括弧は、ツリーを文字列に平坦化するときにサブツリーを明示的に表す場合にのみ必要です。 したがって、問題はカウントの実行可能性チェックとなり、その後、演算子の優先順位と一致する有効なバイナリ ツリーを構築することになります。 

実現可能性が確立されたら、左の深さの式ツリーを貪欲に構築し、使用可能な括弧文字を使用して、必要な場合にのみ部分式をラップすることができます。

 ## アルゴリズムのチュートリアル

 シャッフルされた文字列を文字のプールとして扱い、形成できるオペランドの数、使用できる演算子の数、構造をエンコードするのに十分な括弧があるかどうかを決定します。 

### 1. 文字を分類する

 文字列をスキャンし、文字を文字 (変数)、数字 (数値)、演算子の 4 つのプールに分割します。`+`そして`*`、および括弧。 

変数はすでに有効なオペランドです。 数字は数字にグループ化できますが、正確に一致しない限り、各数字の先頭にゼロを付けることは避けてください。`"0"`。 

### 2. オペランドと演算子の数を決定します。 

有効な式ツリーが必要です。 私たちが選ぶなら`k`オペランドは正確に指定する必要があります`k - 1`オペレーター。 演算子は入力によって固定されるため、これにより即座に決定されます。`k = ops + 1`。 

利用可能なオペランド トークン (変数と数字から形成できる有効な数値) の数が以下の場合は、`k`、建設は不可能です。 

数字の処理は柔軟です。数字を自由に並べ替えることができるため、常に最大で次の数字を形成できます。`d`～からの一桁の数字`d`したがって、最も安全な構造は、最大でも 1 つのスタンドアロンを確保する必要があることを除いて、各桁を独立した数値として扱うことです。`"0"`ゼロ桁ごとに有効です。 これにより、数えられる以上に実現可能性が制限されることはありません。 

### 3. 括弧の実行可能性を確認する

 バイナリ式ツリー`k`葉は持っています`k - 1`内部ノード。 各内部ノードは演算子に対応します。 ツリーが中置形式で記述されている場合、括弧は、優先順位から推測できないサブツリー境界を具体化する場合にのみ必要になります。 

完全に有効な再構成では、ルート以外の各サブツリーに少なくとも 1 組のかっこが必要です。 したがって、十分な量が必要です`'('`そして`')'`少なくとも割り当てるべき文字`k - 1`合計ペア。 

括弧が不十分な場合、有効な完全に構造化された式を形成できません。 

### 4. 有効な式を構築する

 左の深さのバイナリ ツリーを構築します。 

単一のオペランドから始めます。 次に、1 つの演算子を使用して次のオペランドを繰り返し付加し、次の形式を形成します。`(current op next)`毎回。 これにより有効性が保証され、すべての演算子が新しいサブツリー境界を 1 つだけ導入することが保証されます。 

サブツリーの境界が必要な場合は、利用可能な場合は常に括弧のペアを使用します。 括弧が未使用のままの場合は、単に不必要なラップを避けるだけです。 

最後に、使用可能な順序で演算子をインターリーブします。`*`そして`+`優先順位は構造内の括弧の配置によって自然に処理されるため、任意です。 

### なぜ効果があるのか

 この構築では、処理後に不変条件が維持されます。`i`オペランドを使用して、単一のサブツリーを表す有効な式を構築しました。`i - 1`内部オペレーターノード。 各ステップでは、構文の有効性を損なうことなくこのツリーを拡張します。 常にツリー一貫性のある方法でオペランドを接続するため、既に導入されている内部ノードの数を超える構造括弧が必要になることはありません。 これにより、括弧の供給がグローバルに十分である限り、競合することなく括弧を割り当てることができることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    letters = []
    digits = []
    ops = []
    lp = rp = 0

    for c in s:
        if c.isalpha():
            letters.append(c)
        elif c.isdigit():
            digits.append(c)
        elif c == '+' or c == '*':
            ops.append(c)
        elif c == '(':
            lp += 1
        elif c == ')':
            rp += 1

    k = len(ops) + 1  # required operands

    # operands available: each letter is operand, each digit can form single-digit number
    operands = len(letters) + len(digits)

    if operands < k:
        print("impossible")
        return

    # parentheses requirement: need at least k-1 pairs
    if lp < k - 1 or rp < k - 1:
        print("impossible")
        return

    # build operand list
    operands_list = letters + digits[:k - len(letters)]

    # build expression left-deep
    expr = operands_list[0]
    op_idx = 0
    par_used = 0

    for i in range(1, k):
        op = ops[op_idx]
        op_idx += 1

        nxt = operands_list[i]

        # use parentheses when possible for structure
        if par_used < k - 1:
            expr = "(" + expr + op + nxt + ")"
            par_used += 1
        else:
            expr = expr + op + nxt

    print("possible")
    print(expr)

if __name__ == "__main__":
    solve()
```コードはまず各タイプの文字をカウントし、演算子の数から必要なオペランドの数を導き出します。 次に、使用可能な文字と数字が十分なオペランドを提供できることを確認します。 その後、括弧の供給が各内部マージ ステップをラップするのに十分であるかどうかをチェックします。 

構築フェーズでは、左の深さの式を構築し、中間結果がなくなるまで継続的に括弧で中間結果を包みます。 これにより、複雑な解析やバックトラッキングを必要とせずに、すべての構造要件が満たされることが保証されます。 

微妙な点は、数字が独立したオペランドとして扱われることです。 この問題では有効な解釈が可能になるため、正確性を維持しながら、先行ゼロ制約の処理が完全に回避されます。

 ## 特殊なケース

 重大なエッジ ケースは、演算子がちょうど十分であるにもかかわらず、オペランドとして機能するには文字または数字が少なすぎる場合です。 このような場合、式が構造的に構築可能に「見える」場合でも、アルゴリズムはそれを即座に拒否する必要があります。 たとえば、入力`++a`演算子に 1 を加えたものに一致するオペランドが不足しているため、失敗します。 

もう 1 つのエッジ ケースは、括弧が存在するものの、各中間サブツリーをラップするには不十分な場合に発生します。 たとえば、5 オペランド式を作成する必要があるが、括弧が 1 組しかない場合、完全に有効な非冗長構造で必要なグループ化をすべて明示的に表すことはできません。 

ゼロが優勢な場合、数字によって微妙な境界ケースも作成されます。 のような文字列`000+++`各ゼロは独立して動作できるため、引き続き有効なオペランドを形成できますが、数字を複数桁の数字に結合しようとすると、誤って先頭ゼロ違反が発生します。 

最後に、演算子は存在するが意味のあるオペランド ベースが存在しない場合、純粋に構造的な障害が発生します。 かっこがたくさんある場合でも、少なくとも 1 つの有効な開始オペランドがなければ構築を開始できず、アルゴリズムは直ちに拒否する必要があります。
