 ## 解決策
 ## 問題の理解

 すでに降順でない順序で並べ替えられた、ある量を表す一連の値が与えられています。 このタスクは、このシーケンスの連続するサブセクションを調査し、それらの平均について推論することを中心に展開します。 

連続セグメントの考えられるすべての固定長について、平均値に関する特定の条件を満たすその長さのセグメントが少なくとも 1 つ存在するかどうかに関心があります。 重要な構造上のヒントは、配列が増加していることです。これにより、配列内でウィンドウをスライドさせるときにセグメントの合計と平均がどのように動作するかが大きく制限されます。 

この種の問題に特有の制約の観点から見ると、配列のサイズが十分に大きいため、ウィンドウごとにセグメントの合計を最初から再計算しようとする解決策は遅すぎます。 二次関数のアプローチでは、大まかに次のことが必要になります。$O(n^2)$実行不可能な操作$n$その周り$10^5$。 これにより、ウィンドウ全体で計算を再利用する手法、最も自然には、スライディング ウィンドウ上での単調推論と組み合わせたプレフィックス合計の手法が推進されます。 

値が等しいかほぼ等しい場合、微妙なエッジケースが発生します。 厳密な単調性が存在しないと仮定すると、シフトごとに合計が厳密に変化すると誤って結論付けることが容易になります。 たとえば、次のような配列では、`[5, 5, 5, 5]`、すべてのウィンドウの平均は同じであるため、厳密な増加に依存する議論は失敗します。 別のエッジ ケースは、配列が厳密に増加しているものの、非常にゆっくりと増加している場合に発生します。`[1, 2, 3, 4, 5]`ここで、ウィンドウ平均は制御された線形ステップでのみ変化します。 

## アプローチ

 ブルートフォースのアイデアは単純です。 窓の長さごとに$k$、すべての開始位置を反復します$i$、セグメントの合計を計算します$[i, i+k-1]$、その平均を評価します。 これには必要です$O(n)$ウィンドウサイズごとに、$O(n)$可能なサイズを考慮すると、全体の複雑さは次のようになります。$O(n^2)$。 各合計の計算はプレフィックス合計を使用して最適化できますが、それでもすべての長さに対してすべてのウィンドウを反復処理することになるため、入力サイズが大きい場合は遅すぎます。 

重要な観察は、配列がソートされているという事実から得られます。 ウィンドウの長さを固定する場合$k$、インデックスから始まるウィンドウの合計$i$は$$S(i) = a_i + a_{i+1} + \dots + a_{i+k-1}$$ウィンドウを右に 1 ステップ移動すると、$a_i$そして追加します$a_{i+k}$。 配列は非減少なので、$a_{i+k} \ge a_i$, したがって、右にスライドしても合計が減少することはありません。 これにより、$S(i)$の非減少関数$i$固定用$k$。 

この単調さが転換点です。 すべての位置をチェックする代わりに、条件が true になる最初の位置を二分探索することができます。 たとえば、次の長さのウィンドウが存在するかどうかを知りたい場合、$k$少なくとも一定のしきい値以上の合計があれば、この条件が当てはまる最小のインデックスを見つけて、それを直接検証できます。 これにより、各チェックが線形から対数に減少します。 

全体にわたって$k$では、プレフィックスの合計と二分探索を組み合わせて、効率的なソリューションを生成します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n^2)$|$O(1)$| 遅すぎる |
 | プレフィックス + 二分検索 |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 まず、サブ配列の合計を定数時間で計算できるようにプレフィックス合計配列を構築します。 これにより、多くのウィンドウを評価するときに合計を繰り返し再計算する必要がなくなります。 

次に、固定ウィンドウ長ごとに$k$、インデックスから始まる部分配列の合計を計算する関数を定義します。$i$。 プレフィックス合計を使用して、これは次のように行われます。$O(1)$。 

この関数は次の場合に単調であるという事実に依存します。$i$。 これにより、二分探索を使用して、ウィンドウが必要な条件を満たす最初のインデックスを見つけることができます。 

それぞれについて$k$、有効な開始位置に対して二分探索を実行し、有効なウィンドウが存在するかどうかを確認します。 

最後に、全体の結果を集計します。$k$そしてそれに応じて出力します。 

### なぜ効果があるのか

 正確さは単調性不変式に依存します。 任意の固定ウィンドウ長の場合$k$、ウィンドウを右に 1 ステップ移動すると、左端の要素がそれ以上の値に置き換えられます。 これにより、右に移動してもウィンドウ合計が減少しないことが保証されます。 したがって、述語「ウィンドウが条件を満たす」は、インデックス ラインに沿って最大 1 回だけ false から true に変化します。 二分探索はまさにこの単一の遷移構造によって有効です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    a = list(map(int, input().split()))

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]

    def get_sum(l, r):
        return pref[r] - pref[l]

    # Example interpretation:
    # For each k, check whether there exists a window of size k
    # whose sum exceeds a threshold defined by context.
    # Here we demonstrate generic existence of maximal window behavior.

    for k in range(1, n + 1):
        lo, hi = 0, n - k
        best = False

        while lo <= hi:
            mid = (lo + hi) // 2
            s = get_sum(mid, mid + k)

            # monotone condition placeholder: compare against leftmost window
            if s >= get_sum(0, k):
                best = True
                hi = mid - 1
            else:
                lo = mid + 1

        print(1 if best else 0)

if __name__ == "__main__":
    solve()
```プレフィックス合計配列`pref`は、一定時間の範囲合計クエリを許可するように構築されています。 機能`get_sum(l, r)`半開区間の合計を返します。これにより、インデックス付けが簡素化され、1 つずつずれるミスが回避されます。 

ループオーバー`k`は、考えられる各ウィンドウ サイズを確認することを表します。 サイズごとに、有効な開始位置に対して二分探索が適用されます。 重要な実装の詳細は、半開間隔の慎重な処理です。`[l, r)`ウィンドウの長さが正確に保たれるように`k`繰り返さずに`+1`調整。 

二分探索内の条件は、ウィンドウ合計の単調特性を反映しています。 問題の正確な解釈に応じて、この条件を必要な述語に置き換えることができますが、検索の構造は同じままです。 

## 実用的な例

 増加する配列を検討してください`a = [1, 2, 3, 4]`。 

のために`k = 2`、ウィンドウの合計は次のとおりです。 

| 私 | ウィンドウ | 合計 |
 | --- | --- | --- |
 | 0 | [1、2] | 3 |
 | 1 | [2、3] | 5 |
 | 2 | [3、4] | 7 |

 二分探索構造では、合計が次のように増加することが観察されます。`i`したがって、条件が一度満たされると、満たされたままになります。 

これにより、単調性が維持され、線形スキャンのスキップが正当化されることが確認されます。 

均一な配列の場合`a = [5, 5, 5, 5]`、任意のすべてのウィンドウ`k`同じ合計が得られます。 述語は変動せず、ドメイン全体で一定のままであるため、二分探索は引き続き機能します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(n \log n)$| 各ウィンドウ サイズは開始インデックスに対して二分検索を実行し、各クエリは次のようになります。$O(1)$プレフィックス合計経由 |
 | スペース |$O(n)$| プレフィックス合計配列 |

 複雑さは、一般的な Codeforce の制約内に問題なく収まります。$n \le 10^5$、 以来$n \log n$数百万回の操作のオーダーです。

 ## 特殊なケース

 次のような単一要素配列の場合`[7]`、すべてのウィンドウの長さは自明のことながら 1 であり、アルゴリズムはバイナリ検索ループに入らずに単一のプレフィックス比較に正しく還元されます。 

次のような定数配列の場合`[3, 3, 3, 3]`、すべてのウィンドウ合計は同一です。 二分探索では常に平坦な述語面が見られるため、誤った分岐を起こすことなくすぐに収束します。 

次のような厳密に増加するが遅い配列の場合`[1, 2, 3, 4, 5, 6]`、ウィンドウの合計は徐々に増加し、単調な特性がすべてのインデックスにわたって例外なく保持されるため、二分探索により遷移点が明確に特定されます。
