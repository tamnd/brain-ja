 ## 解決策
 ## 問題の理解

 各位置が正または非正のいずれかにラベル付けされた配列が与えられます。 正の値はその位置を良好なオブジェクトとしてマークし、非正の値はその位置を不良オブジェクトとしてマークします。 不良オブジェクトが配列内に連続して出現すると、当然、連続したブロックを形成し、そのような最大のブロックはそれぞれ「グループ」として扱われます。 

この問題の重要な構造は、相互作用がこれらの不良オブジェクトのグループに依存しており、それらのグループを良好なオブジェクトとどのように照合できるかということです。 同じ連続ブロック内の不良オブジェクトはペアリング動作の観点から分離できませんが、異なるブロックの不良オブジェクトは独立して動作します。 さらに、位置 i にある不良オブジェクトは、j が i の右側にない場合にのみ、良好なオブジェクト j とペアにすることができます。 

タスクは、明示的なマッチングを構築することではなく、これらの制約の下ですべての不良オブジェクトの完全なペアリングが可能かどうかを判断することです。 不可能の条件は、不良セグメント [l, r] と、配列全体内の不良オブジェクトの総数と位置 l までに現れる正常なオブジェクトの数という 2 つの量との比較によって説明されます。 

直観的には、各不良セグメントは、すべての不良オブジェクトとその左側に表示される良好なオブジェクトによって形成される利用可能なマッチング容量に「適合」する必要があります。 この利用可能な容量に対してセグメントが大きすぎる場合、配置は失敗します。 

複雑さの観点から見ると、入力は単一の配列であり、ソリューションは線形または線形に近い時間で実行される必要があります。 考えられるすべてのペアリングをシミュレートしたり、マッチングについて明示的に推論しようとする単純なアプローチは 2 次的になります。これは、一般的な Codeforce の制約 (約 2 秒、n が最大 2e5 または 1e5) には遅すぎます。 

主な微妙なエッジ ケースは、不良セグメントが大きく、アレイの初期にある場合に発生します。 たとえば、配列が不正な値の長いブロックで始まり、その後に適切な値が含まれる場合、貪欲なマッチングの直感は、たとえインデックス制限により使用できない場合でも、将来の適切な値が役立つ可能性があると誤って想定する可能性があります。 

不良オブジェクトが多くの小さなセグメントに分割される場合、別の特殊なケースが発生します。 単純な解決策では、不良オブジェクトをグループ化する代わりに個別にチェックする可能性がありますが、制約が要素ベースではなくセグメントベースであるため、ロジックが破綻します。 

## アプローチ

 ブルートフォースの観点は、ペアリングを明示的にシミュレートすることです。 すべての不良オブジェクトを、別のセグメントの別の不良オブジェクト、またはその左側に表示される適切な良好なオブジェクトと照合しようとします。 これにより、当然のことながら、二者間マッチングを構築したり、有効なパートナーを繰り返しスキャンしたりすることを考えるようになります。 貪欲な戦略を使用した場合でも、各不良オブジェクトが一致を見つけるために配列全体のスキャンをトリガーする可能性があり、すべてのオブジェクトが不良であるか交互になる最悪の場合、O(n²) 動作が発生します。 

重要な簡素化は、唯一の意味のある障害は個々のペアではなく、不良要素の連続ブロック全体であることを認識することで実現します。 配列をこれらのブロックに圧縮すると、各ブロックは単一の制約のように動作します。つまり、不良オブジェクトのグローバル プールと、左側の境界より前に現れる良好なオブジェクトに対して十分な「容量」が要求されます。 

これにより、問題は動的マッチングからプレフィックス アカウンティングの問題に軽減されます。 全体的に不良オブジェクトがいくつ存在するか、および各不良セグメントが開始される前に正常なオブジェクトがいくつあるかを知る必要があるだけです。 次に、各セグメントが 1 つの不等式を独立してチェックし、その不等式に違反するセグメントがあるかどうかによって全体の答えが決まります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースマッチング | O(n²) | O(n) | 遅すぎる |
 | セグメント + プレフィックス分析 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

この配列を 2 種類の情報に分割します。1 つは正常なオブジェクトのプレフィックス数、もう 1 つは不良オブジェクトの最大連続セグメントのリストです。 

1. 配列を 1 回スキャンし、プレフィックス配列を計算します。prefixGood[i] には、位置 [1, i] に出現する良好なオブジェクトの数が格納されます。 これにより、任意の位置の左側に良好なオブジェクトがいくつあるかを即座に知ることができます。 
2. 同じスキャン中に、不良オブジェクトの最大の連続セグメントをすべて識別します。 各セグメントは、その左端点 l、右端点 r、およびその長さ len = r - l + 1 で表されます。制約は要素ごとではなくセグメントごとに適用されるため、この圧縮は不可欠です。 
3. アレイ全体内の不良オブジェクトの総数を計算します。 この値は、ステートメントで言及されているグローバル プール P を表し、すべてのセグメントで共有されます。 
4. 不良セグメント [l, r] ごとに、セグメントの開始点またはその前にある正常なオブジェクトの数である prefixGood[l] として Q を計算します。 これは、このセグメントの制約の一致に有意義に貢献できる、良好なオブジェクトの唯一の部分です。 
5. 各セグメントの条件を確認します: サイズが totalBad + prefixGood[l] を超えているかどうか。 いずれかのセグメントがこの不等式に違反する場合、完全なペアリングは不可能であると即座に結論付けられます。 
6. すべてのセグメントが条件を満たしていれば配置可能です。 

このチェックの背後にある理由は、各セグメントは、すべての不良オブジェクトとその前に現れる使用可能な良好なオブジェクトの組み合わせによってサポートされなければならないということです。 セグメントが大きすぎると、後で適切なオブジェクトがどのように配置されるかに関係なく、有効なペアに分解できません。 

これが機能する理由は、不良オブジェクトを集約すると、すべての制約がセグメント境界に対してローカルになるという観察から来ています。 セグメントは、その開始点の右側から使用可能な良好なオブジェクトを「借用」することはできません。また、異なるセグメント間の相互作用は、利用可能な柔軟性を高めるだけであり、低下させることはありません。 したがって、唯一考えられる障害モードは、単一セグメントがグローバルに定義された利用可能な総容量をその境界まで超過することです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    a = list(map(int, input().split()))

    prefix_good = [0] * (n + 1)
    total_bad = 0

    for i in range(1, n + 1):
        prefix_good[i] = prefix_good[i - 1]
        if a[i - 1] > 0:
            prefix_good[i] += 1
        else:
            total_bad += 1

    i = 1
    ok = True

    while i <= n:
        if a[i - 1] > 0:
            i += 1
            continue

        l = i
        while i <= n and a[i - 1] <= 0:
            i += 1
        r = i - 1

        seg_len = r - l + 1
        good_left = prefix_good[l]

        if seg_len > total_bad + good_left:
            ok = False
            break

    print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()
```実装ではまず、「インデックス l までに良好なオブジェクトがいくつ存在するか」に関するクエリが O(1) になるように、良好な値のプレフィックス カウントを構築します。 同時に、すべての不良オブジェクトをグローバルにカウントします。 

次に、再度スキャンして、連続した不良セグメントを抽出します。 不良セグメントが見つかるたびに、その長さを計算し、導出された容量式と比較します。 

実装の微妙な詳細は、prefix_good[l] がセグメントの右側ではなく左側の境界で取得されることです。 prefix_good[r] を使用すると、ペアリング ルールでそのセグメントを支援することが許可されていない良好なオブジェクトが誤ってカウントされます。 

ループ構造により、すべてのインデックスが 1 回アクセスされることが保証されるため、セグメント化とチェックが線形時間で行われます。

 ## 特殊なケース

 重大なエッジ ケースは、アレイが長い不良セグメントから始まる場合です。 この状況では、prefixGood[l] は 0 であるため、セグメントは不良オブジェクトの総数に対してのみチェックされます。 セグメントはまだグローバルな不良容量によって制限されており、将来の正常なオブジェクトがそれを支援できないため、アルゴリズムはこれを正しく処理します。 

別の特殊なケースは、良いオブジェクトが最後にのみ表示される場合に発生します。 このような場合、prefixGood[l] はすべての初期セグメントに対して 0 のままであり、右側からの無効な借用がカウントされないことが保証されます。 

3 番目のエッジ ケースは、不良オブジェクトが多数の単一要素セグメントに分割される場合です。 このアルゴリズムは依然としてそれぞれを別個の制約として扱い、各セグメントの長さは 1 であるため、グローバル構造が縮退していない限り、不等式は自明に満たされます。
