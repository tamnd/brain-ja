 ## 解決策
 ## 問題の理解

 ツリーはボトムアップの多数決のようなルールを定義し、リーフのみが固定情報を保持し、すべての内部ノードがその子から状態を導き出します。 各葉は赤または青のいずれかであり、他のすべてのノードは、直接の子の何個が青であるか赤であるかを比較することによって、その色を継続的に再計算します。 パラメータ$k$バランスを変える: ノードは少なくとも$k$赤い子供より青い子供が多い。 

重要な問題は、この条件がすべてのノードで評価され、サブツリーの状態に依存するため、リーフでの変更がルートにまで伝播する可能性があることです。 さらに、$k$それ自体は変更される可能性があります。つまり、木や葉の色を変更せずに、すべての内部ノードの解釈が変更される可能性があります。 

単純なアプローチでは、ルートから DFS を実行することにより、クエリごとにツリー全体を再計算します。 ノード数とクエリの両方が最大であるため、これではすぐに遅すぎます。$10^5$、各再計算コスト$O(n)$、につながる$O(nq)$。 

もっと微妙な問題が現れるのは、$k$変化します。 葉が変化しない場合でも、内部ノードの色がグローバルに反転する可能性があります。 正しいソリューションは、ローカル更新 (リーフの色変更) とグローバルしきい値シフトの両方に効率的に反応する必要があります。 

さらなる落とし穴は、単調性を仮定することです。各ノードは合計ではなくカウントの差に依存するため、青になったノードはその親が単純な線形で青になることを意味しません。 

## アプローチ

 ブルート フォース戦略では、クエリが到着するたびにツリーを走査してすべてのノードの色を再計算します。 これは簡単です。リーフを固定ソースとして扱い、その子から各内部ノードの状態を再帰的に計算します。 定義は子状態が与えられたノードごとに純粋にローカルであるため、これは正しく機能します。 

失敗は繰り返しから生まれます。 各更新またはクエリは、全体にわたって再計算をトリガーする可能性があります。$n$ノードと$10^5$これにより生じるクエリ$10^{10}$最悪の場合の運用。 

重要な観察は、各ノードがその子からの 1 つの集計値、つまり青と赤のカウントの差だけを知る必要があるということです。 ノードごとに定義すると$v$

$$d_v = (\#\text{blue children}) - (\#\text{red children}),$$ノードはまさにそのとき青色になります$d_v \ge k$。 これは、ツリー全体の状態が、これらの値にグローバルしきい値を加えたものによって決定されることを意味します。 

これで構造は静的になります。$d_v$葉の色が変化したときにのみ変化し、根への経路に沿ってのみ上向きに伝播します。 これにより、問題は、リーフでのポイント更新とすべてのノードでのしきい値依存のクエリによるツリー上のサブツリー集約の維持に変わります。 

ツリーを 1 にルートし、すべてのリーフ更新が 1 つのリーフ ノードにのみ影響し、その後、そのノードが更新されることを観察します。$d_v$すべての先祖の価値観。 各祖先の値は、子が赤から青に反転するか、またはその逆に反転するかに応じて +2 または -2 変化します。 

したがって、中心的なタスクはこれらを維持することになります。$d_v$値を動的に計算し、ノードが$d_v$現在のしきい値を超えています$k$。 This is handled efficiently using a Fenwick tree over an Euler tour combined with a multiset-like structure per node, or more cleanly by maintaining all$d_v$マルチセット内の値は、現在の計算状態によってインデックス付けされ、グローバルしきい値シフトを暗黙的にサポートします。 

標準的なソリューションでは、DFS オーダーに加えて、各ノードが現在青色かどうかを格納するノード上のセグメント ツリーまたは BIT を使用します。 リーフが変更されると、保存されている祖先を調整してすべての祖先を更新します。$d_v$、各更新は次のように処理されます。$O(\log n)$重光分解、または事前計算された隣接リストを使用したオイラー + 親ポインターを使用します。 

重要な単純化は、サブツリーの色を最初から再計算しないことです。 数字のバランスを維持するだけです$d_v$との比較を使用して、オンデマンドで色を導き出します。$k$。

 ## アルゴリズムのチュートリアル

 ツリーをノード 1 にルートし、親子関係を事前計算します。 また、入力からどのノードが葉であるかを特定します。 

1. 各ノードに値を割り当てます$d_v$、最初は子の色から計算されます。 葉の場合、この値は構造的に無関係ですが、基本ソースとして扱います。 
2. ポストオーダー DFS によって最初に計算された、配列内のすべてのノードの現在の色を維持します。 これにより、すべてのユーザーにとって一貫した開始状態が得られます。$d_v$。 
3. すべての内部ノードについて$v$、その現在を保存します$d_v$、これは青と赤の子の数の差です。 これは、現在の色を決定するために必要な唯一の情報です。$k$。 
4.葉っぱのとき$v$色が変わると、古い寄与分と新しい寄与分の差分が計算されます。 赤から青に変化すると、その親への寄与は +2 増加します。 逆にすると -2 減少します。 
5. このデルタを葉から根まで上向きに伝播します。 各祖先はその祖先を更新します$d$-それに応じて値を設定します。 この伝播は親ポインタに従うため、各更新は$O(\text{height})$ノード。 
6. 影響を受けるものをすべてアップデートした後$d_v$、ノードに関するあらゆるクエリに答えることができます$v$かどうかを確認することで$d_v \ge k$。 
7. いつ$k$変更がある場合は、グローバル変数を更新するだけです。 ツリーの再計算は必要ありません。$d_v$値は有効なままです。 閾値のみがシフトします。 

### なぜ効果があるのか

 各内部ノードは、スカラーによって完全にキャプチャされる青と赤の子の数にのみ依存します。$d_v$。 リーフの更新は、祖先ごとに 1 つの子コントリビューションにのみ影響を与えるため、すべてのノードに対する影響はルート パスに沿って追加的かつローカルになります。 直接の子を超えるより深い構造に依存するノードはないため、正しい状態が維持されます。$d_v$値は、すべてのノードの色の決定が常に定義と一致していることを保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

n, k = map(int, input().split())
g = [[] for _ in range(n + 1)]

for _ in range(n - 1):
    u, v = map(int, input().split())
    g[u].append(v)
    g[v].append(u)

s = list(map(int, input().split()))

parent = [0] * (n + 1)
children = [[] for _ in range(n + 1)]
order = []

# build rooted tree
stack = [1]
parent[1] = -1

while stack:
    v = stack.pop()
    order.append(v)
    for to in g[v]:
        if to == parent[v]:
            continue
        parent[to] = v
        children[v].append(to)
        stack.append(to)

# compute initial dp = (#blue children - #red children)
color = [0] * (n + 1)
dp = [0] * (n + 1)

# initialize leaves from s
for i in range(1, n + 1):
    if s[i - 1] != -1:
        color[i] = s[i - 1]

# postorder compute dp
for v in reversed(order):
    if not children[v]:
        continue
    val = 0
    for to in children[v]:
        val += 1 if color[to] == 1 else -1
    dp[v] = val
    color[v] = 1 if dp[v] >= k else 0

# helper to update path
def update_leaf(v, newc):
    global k
    if color[v] == newc:
        return
    delta = (1 if newc == 1 else -1) - (1 if color[v] == 1 else -1)
    color[v] = newc

    cur = v
    while parent[cur] != -1:
        p = parent[cur]
        dp[p] += delta
        new_col = 1 if dp[p] >= k else 0
        if new_col == color[p]:
            cur = p
            break
        color[p] = new_col
        cur = p

q = int(input())
for _ in range(q):
    tmp = input().split()
    if tmp[0] == '1':
        v = int(tmp[1])
        print(color[v])
    elif tmp[0] == '2':
        v = int(tmp[1])
        c = int(tmp[2])
        update_leaf(v, c)
    else:
        k = int(tmp[1])
        # recompute colors (safe O(n) per k change in this implementation)
        for v in reversed(order):
            if children[v]:
                val = 0
                for to in children[v]:
                    val += 1 if color[to] == 1 else -1
                dp[v] = val
                color[v] = 1 if dp[v] >= k else 0
```このコードはツリーをルート構造に分割するため、すべてのノードが明確な親ポインターを持ちます。 dp 配列には、青から赤を引いた子の差が格納されます。 カラー配列には、現在の派生状態が格納されます。 リーフの更新は、祖先チェーンに沿って dp 値を調整することによって上向きに伝播されます。 唯一の微妙な部分は、ノードの色が変わらない場合に伝播を早期に停止することです。これは、しきい値の決定が安定している場合、上位の祖先は影響を受けないためです。 

クエリ タイプ 3 の処理は、色の再計算によって実装されます。これは概念的には単純ですが最適ではありません。 完全に最適化されたソリューションでは、これはよりグローバルな構造に吸収されます。 残りのロジックの正確さは変わりません。 

## 実用的な例

 ノード 1 に 2 つの子 2 と 3 (両方とも葉) がある小さなツリーを考えてみましょう。 最初は 2 が青、3 が赤で、$k = 1$。 

| ステップ | ノード 2 | ノード 3 | d1 | カラー(1) |
 | --- | --- | --- | --- | --- |
 | 初期化 | 1 | 0 | 0 | 0 |
 | セットアップ後 | 1 | 0 | 1 | 1 |

 これは、不均衡がしきい値を超えた場合にのみルートが青になることを示しています。 

ここで、ノード 3 を赤から青に変更するリーフ フリップを考えてみましょう。 

| ステップ | ノード 2 | ノード 3 | d1 | カラー(1) |
 | --- | --- | --- | --- | --- |
 | 前 | 1 | 0 | 1 | 1 |
 | 更新 | 1 | 1 | 2 | 1 |

 根元は青いままですが、縁が大きくなります。 

これは、更新が祖先集合体にのみ影響すること、および色の変化がしきい値を超えることに完全に依存していることを示しています。

 ## 特殊なケース

 すべてのノードに子が 1 つだけある偏ったツリーでは、チェーンに沿った更新の伝播が強制されます。 この場合、各リーフ更新はすべての祖先を経由し、正確性は中間ノードをスキップせずに一貫した dp 更新を維持することに依存します。 このアルゴリズムは、有効性を維持しながら、各祖先でデルタを正しく蓄積します。 

いつ$k$が非常に大きな正の値に設定されている場合、極端な不均衡がない限り、内部ノードが青になることはありません。 dp 値は次数によって制限されるため、すべてのノードは赤と評価され、アルゴリズムは当然どこでもゼロを生成します。 

いつ$k$が非常に負の場合、すべての dp が不等式を満たすため、すべてのノードが青になります。 比較はローカルであり、符号スケーリングとは無関係であるため、アルゴリズムは引き続き正しく動作します。
