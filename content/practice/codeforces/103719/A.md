 ## 解決策
 ## 問題の理解

 私たちは石の長い列を維持しており、それぞれの石には数値が含まれています。 最初は、すべてのポジションが固定ベースライン (通常はゼロ) から始まります。 その後、一連の操作が適用されます。 単一の位置を変更する操作もあれば、行全体を新しい値で上書きする操作もあります。 更新の合間に、すべての石の値の合計を報告するように求められます。 

主な困難は、単一の合計を計算するのではなく、混合更新の下で計算することです。つまり、すべての要素に一度に影響を与えるグローバル上書きと、1 つのインデックスのみに影響を与えるローカル更新ですが、将来のグローバル上書きの後でも正しく反映される必要があります。 出力は、現在の合計合計を求める各クエリの結果です。 

インターフェイスは単純に見えますが、制約は、ストーンの数と操作の数の両方が十分に大きくなり、操作ごとに配列全体を走査することが不可能になる可能性があることを意味します。 グローバルな上書きのたびに合計を再計算する単純なアプローチでは、このようなクエリごとに線形時間がかかり、最悪の場合は 2 次の動作が発生します。これは、大規模な入力に対して通常の 2 秒の制限で処理できる速度をはるかに超えています。 

間違った素朴な推論を暴露するいくつかの特殊なケースがあります。 配列全体を値 5 で上書きし、その後 1 つの位置を 10 に更新するとします。不注意な実装では、新しい値を追加する前に、前のグローバル ベースラインから 1 つの位置を減算する必要があることを忘れる可能性があります。 たとえば、サイズ 4 の配列のすべての値を 5 に設定すると、合計は 20 になります。その後、位置 2 を 10 に設定すると、正しい合計は 30 ではなく 25 になります。これは、位置 2 が以前は 0 ではなく 5 に寄与していたためです。 

複数のグローバル上書きが発生した場合、別の微妙なケースが発生します。 すべての値を 3 に設定し、次に 7 に設定すると、2 回目の上書きの前に発生した以前の個々の更新は事実上消去されるため、無視する必要があります。 このリセット境界を追跡できないと、古い更新と新しいグローバル状態が混在することになります。 

## アプローチ

 直接的なブルート フォース ソリューションでは、配列全体が明示的に維持されます。 ポイント更新は単に 1 つのインデックスを割り当て、合計クエリは配列全体をスキャンします。 難しい部分はグローバル上書き操作であり、n 個の要素すべてを 1 つずつ更新する必要があります。 そのため、各大域演算は O(n) となり、このような演算が頻繁に現れる場合、総コストは O(n・q) となり、n と q が両方とも大きい場合には過大になります。 

重要な観察は、操作の構造が時間をフェーズに分割していることです。 グローバル上書き後、ローカル更新によって変更されるまで、すべての要素は同じ値を共有します。 配列を物理的に書き換える代わりに、現在のグローバル ベースラインを記憶し、そこからの逸脱を追跡するだけで済みます。 

秘訣は、配列を 2 つの層で構成されているものとして扱うことです。 最初のレイヤーは、最新の完全上書きによって割り当てられたグローバル値です。 2 番目のレイヤーは、上書き後に適用される個別の修正で構成されます。 単一のインデックスを変更するたびに、古い寄与分を削除し、新しい寄与分を追加して合計を調整します。 これを効率的に行うには、最後のグローバル上書き以降にそのインデックスが変更されているかどうかを知る必要があります。 そうでない場合は、その古い値が現在のグローバル ベースラインになります。 

これにより、配列全体に明示的に触れることがないため、すべての操作が O(1) に削減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースアレイ再構築 | O(nq) | O(n) | 遅すぎる |
 | レイジー グローバル バリュー + ポイント デルタ | O(q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 最新の完全な上書き後のすべての要素の現在値を表すグローバル値を初期化します。 上書きがまだ行われていないため、最初はゼロです。 
2. 配列の現在の合計を維持します。 これも最初はゼロです。 
3. グローバルな上書きが発生するたびに増加するタイムスタンプまたはバージョン カウンターを維持します。 これにより、位置が最後に上書きされる前に更新されたか後かどうかを区別できるようになります。 
4. 各インデックスについて、その最終更新バージョンと現在の値を保存します。 これは、再度変更するときにその寄与を再構築するために必要です。 
5. 値 x によるグローバル上書き操作を受信したら、グローバル値を x に更新し、合計を x の n 倍にリセットします。 また、グローバル バージョン カウンターをインクリメントして、以前のインデックスごとの更新がすべて無関係になるようにします。 
6. 値 x を持つインデックス i でのポイント更新を受信すると、最初にその以前の寄与を決定します。 保存されているバージョンが現在のグローバル バージョンよりも古い場合、その古い値がグローバル値になります。 それ以外の場合は、古い値が保存された値になります。 これを合計額から差し引きます。 
7. 新しい値 x を位置 i に割り当て、そのバージョンを現在のバージョンとしてマークし、合計に x を加算します。 
8. 合計を求められたら、保存されている合計を出力するだけです。 

中心となる考え方は、すべての要素には、現在のグローバル上書きまたは最新の個別の更新によって決定される、明確に定義された寄与が常にあるということです。 アレイ全体をスキャンする必要のある操作はありません。 

### なぜ効果があるのか

 どの時点でも、各要素は 2 つの状態のいずれかに属します。つまり、最後のグローバル上書き以降変更されていない状態、またはその後に個別に更新された状態です。 グローバル上書きでは、すべての未処理の要素に対して均一のベースラインが定義されます。 すべてのポイント更新では、その要素の以前の正しい値を使用して合計合計が明示的に調整されるため、すべての操作の後でも合計は一貫したままになります。 バージョン管理メカニズムにより、古い更新が新しいグローバル状態に干渉することがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    arr = [0] * n
    ver = [0] * n

    global_val = 0
    global_ver = 0
    total = 0

    for _ in range(q):
        cmd = input().split()

        if cmd[0] == '1':
            i = int(cmd[1]) - 1
            x = int(cmd[2])

            if ver[i] == global_ver:
                old = arr[i]
            else:
                old = global_val

            total -= old
            total += x

            arr[i] = x
            ver[i] = global_ver

        else:
            x = int(cmd[1])
            global_val = x
            global_ver += 1
            total = n * x

        print(total)

if __name__ == "__main__":
    solve()
```この実装は、論理状態を物理ストレージから分離することに依存しています。 配列`arr`そして`ver`インデックスごとのオーバーライドと、最後のグローバル上書きを基準としたその鮮度を保存します。 ペア`(global_val, global_ver)`は最後の完全なリセットを表します。 ポイントの更新を処理するとき、重要なステップは、以前の値が次の値からのものであるかどうかを判断することです。`arr[i]`またはから`global_val`、これはまさにバージョンチェックでエンコードされるものです。 

よくある間違いは、グローバル上書きが発生したときにインデックスごとの履歴をリセットするのを忘れることです。 配列をクリアする代わりに、バージョン カウンターは古いエントリに触れることなく自動的に無効にします。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(q) | 各操作は一定数の変数を更新し、一度出力します。 
| スペース | O(n) | インデックスごとの値とバージョン情報を保存します。 

すべての操作で配列のスキャンが回避され、定数時間のブックキーピングに置き換えられるため、このソリューションは制限内に問題なく収まります。

 ## 特殊なケース

 いくつかのポイント更新後にグローバル上書きが発生すると、以前のインデックスごとの状態はすべて無関係になります。 バージョン カウンターは、古いエントリを現在のグローバル バージョンと論理的に非互換にすることでこれを保証します。 たとえば、完全なリセットの前にインデックス 1 を更新する場合、その更新は後の計算に影響を与えてはなりません。 

入力：```
2 3
1 1 5
2 3
3
```実行すると、グローバル上書きの後、以前の割り当てに関係なくインデックス 1 が値 3 を持つものとして扱われ、合計が 6 になることがわかります。古い値 5 は、そのバージョンが現在のグローバル バージョンと一致しないため、再度使用されることはありません。 

このメカニズムにより、更新が任意の順序でインターリーブされた場合でも正確さが保証されます。
