 ## 解決策
 ## 問題の理解

 固定のバイナリ文字列が与えられ、長さ 3 の連続セグメントに対する 2 種類のローカル変換を繰り返し検討します。`011`の中へ`110`、または逆スワップ`110`の中へ`011`。 各操作は連続する 3 文字のみを操作し、1 の合計数を保持しますが、文字列内で 1 を移動する可能性があります。 

中心的な質問は、操作を直接適用することではありません。 代わりに、部分文字列に関する到達可能性について質問されます。元の文字列の 2 つの等しい長さの部分文字列について、部分文字列内の任意の場所に適用されるこれらのローカル スワップのシーケンスを使用して、一方を他方に変換できるかどうかを判断する必要があります。 

このステートメントにすでに隠されている重要な観察は、操作が部分文字列の境界を越えて、グローバルな実現可能性を変えるような相互作用をすることは決してないということです。 したがって、各クエリは、これらのローカル クエリによって生成された制約付き置換システムの下で、2 つのバイナリ文字列間の構造的等価性テストを要求します。`011 <-> 110`交換します。 

制約は大きく、文字列の長さとクエリの数は両方とも最大 200,000 です。 クエリごとに部分文字列を単純に検査するソリューションは、クエリされたすべての部分文字列を読み取るだけでも、最悪の場合すでに 2 次関数になるため、すぐに失敗します。 これにより、ほぼ一定または対数的なクエリ時間による前処理アプローチが強制されます。 

単純な考えは、考えられるすべての変換をシミュレートするか、文字列を介して BFS を実行することです。 長さの状態空間があるため、これは不可能です。`n`バイナリ文字列は`2^n`、ローカルトランジションさえも多すぎます。 

微妙な落とし穴もあります。 よくある間違いの 1 つは、1 の数だけが到達可能性を決定すると考えることです。 それは失敗します。 例えば、`0110`そして`1010`同じ数の 1 を持ちますが、部分文字列が制限されたコンテキストで許可された操作で常に到達できるとは限りません。 もう 1 つの間違いは、操作を 1 の任意の並べ替えとして扱うことです。これは、隣接構造によって引き起こされるパリティのような制約を無視します。 

正しい不変式は、単なるカウントよりもさらに洗練されていることがわかります。 

## アプローチ

 ブルートフォース解釈では、各部分文字列を巨大な暗黙的なグラフのノードとして扱います。エッジは、`011 <-> 110`スワップ。 ある部分文字列状態から BFS または DFS を実行して、別の部分文字列状態に到達できるかどうかを確認します。 各状態には O(n) 個の可能な移動があり、状態の数は指数関数的であるため、単一のクエリであってもこれは実行不可能です。 

重要な簡素化は、操作がグローバルに実際に何を行うかを理解することから生まれます。 スワップ`110 -> 011`を動かす`1`を挟んで右側の 1 つの位置`0`、 そして`011 -> 110`を動かす`1`を挟んで左側の 1 つの位置`0`ただし、隣接する 2 つの 1 または 0 を含む非常に特殊なパターンのみです。 これは、ゼロを介して事実上「バブリング」できることを意味しますが、特定のパターン間の相対的な順序が部分的に保持されるという制約があります。 

より有用な観点は、文字列を 1 の位置としてエンコードすることです。 この操作では、1 と 0 の隣接した交換が可能ですが、これは、`1`別のものを通過します`1`間接的に`0`ギャップ。 これは重要な事実につながります。どの部分文字列内でも、到達可能性は連続する部分文字列間の距離の複数セット、または同等の部分文字列の位置から導出されるプレフィックス構造にのみ依存します。 

標準的な解決策は、1 の接頭辞の合計と変換された座標系を使用して問題を再構成します。 プレフィックス配列を定義すると`pref[i]`位置までの 1 の数として`i`の場合、インデックスをシフトすることで各部分文字列を正規化し、比較が絶対位置に依存しないようにすることができます。 到達可能な部分文字列を区別する残りの不変式は、部分文字列内のギャップ間のシーケンスのハッシュのようなエンコードです。 

これを効率的に計算するために、1 の位置を事前計算し、連続する 1 の間の距離を表す配列に対してプレフィックス ハッシュを構築します。 次に、各部分文字列クエリは、プレフィックス事前計算によるハッシュを使用して O(1) で計算された 2 つの正規表現を比較することに帰着します。 

ブルート フォースは変換を直接探索するため機能しますが、変換は本質的に指数関数的であるため失敗します。 システムが相対間隔にわたって構造化された不変量を保持するという観察により、問題は事前計算されたシーケンスの間隔比較に軽減され、O(n) 個の前処理後に O(1) 個のクエリが可能になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | クエリごとに O(2^n) | O(n) | 遅すぎる |
 | 最適 | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、許可されたスワップの下で安定した文字列に関する構造情報を抽出します。 

1. アレイを構築する`pos`すべてのインデックスを含む`1`文字列内の s。 これにより、文字列が操作時に実際に移動する構造に圧縮されます。 
2. 派生配列を構築する`g`連続するものの間のギャップを表し、次のように定義されます。`g[i] = pos[i+1] - pos[i]`。 これは、各要素の間隔がどのように配置されているかをキャプチャします。 
3. プレフィックスハッシュを事前計算する`g`ローリングハッシュを使用します。 これにより、到達可能性は正規化後に 2 つの部分文字列が同一のギャップ構造を引き起こすかどうかに依存するため、ギャップの任意のセグメントを O(1) で比較できます。 
4. 1 を数えるために追加のプレフィックス配列を作成します。これにより、各クエリで部分文字列に 1 がいくつあるかを迅速に判断できます。 これが必要なのは、1 の数が異なる部分文字列には到達できないためです。 
5. クエリごとに、部分文字列を抽出します。`[l1, r1]`そして`[l2, r2]`。 1 の数が異なる場合は、すぐに NO を返します。 
6. それ以外の場合は、二分探索を使用して、両方の部分文字列を誘導ギャップシーケンスにマッピングします。`pos`、それらのハッシュ値を比較します。 ハッシュが一致する場合は、YES を返します。 それ以外の場合は「いいえ」です。 

これが機能する理由は、許可された操作は、それらの間のギャップの相対的な構造を変更せずに、ローカルに並べ替えるだけであるためです。 有効なスワップのシーケンスは、サブストリング内の連続するスワップ間のギャップ長のマルチセットを保持し、ハッシュ ステップはこの不変条件を正確に取得します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = (1 << 61) - 1
BASE = 91138233

def modmul(a, b):
    return (a * b) & MOD

def build_hash(arr):
    n = len(arr)
    h = [0] * (n + 1)
    p = [1] * (n + 1)
    for i in range(n):
        p[i + 1] = modmul(p[i], BASE)
        h[i + 1] = (modmul(h[i], BASE) + arr[i] + 1) & MOD
    return h, p

def get_hash(h, p, l, r):
    return (h[r] - modmul(h[l], p[r - l])) & MOD

def solve():
    n = int(input())
    s = input().strip()

    pos = []
    pref = [0] * (n + 1)

    for i, c in enumerate(s):
        pref[i + 1] = pref[i] + (c == '1')
        if c == '1':
            pos.append(i)

    g = []
    for i in range(len(pos) - 1):
        g.append(pos[i + 1] - pos[i])

    if g:
        h, p = build_hash(g)
    else:
        h, p = [0], [1]

    q = int(input())

    def get_sub_hash(l, r):
        # extract ones in range via two pointers
        import bisect
        L = bisect.bisect_left(pos, l)
        R = bisect.bisect_right(pos, r) - 1

        if L >= R:
            return 0

        return get_hash(h, p, L, R)

    for _ in range(q):
        l1, l2, ln = map(int, input().split())
        l1 -= 1
        l2 -= 1
        r1 = l1 + ln
        r2 = l2 + ln

        if pref[r1] - pref[l1] != pref[r2] - pref[l2]:
            print("No")
            continue

        if get_sub_hash(l1, r1) == get_sub_hash(l2, r2):
            print("Yes")
        else:
            print("No")

if __name__ == "__main__":
    solve()
```ゼロは 1 を区切る場合にのみ重要であるため、実装ではまず文字列を 1 の位置に圧縮します。 プレフィックス配列`pref`部分文字列ごとに 1 を定数時間でカウントできるため、簡単な拒否テストとして使用できます。 

の`g`配列は、連続するものの間隔をグローバルにエンコードします。 次に、ギャップの間隔を効率的に比較できるように、この配列に対してローリング ハッシュを構築します。 ヘルパー関数`get_sub_hash`部分文字列を対応する区間にマッピングします。`pos`二分探索を使用して、それを範囲に変換します。`g`。 

微妙な点は、0 または 1 を含む部分文字列の処理です。 この場合、ギャップはなく、正規表現は空であるため、ハッシュとしてゼロを返します。 

## 実用的な例

 単純な文字列を考えてみましょう`t = 11011`。 

1 の位置を前処理します。 

| インデックス | 0 | 1 | 2 | 3 | 4 |
 | --- | --- | --- | --- | --- | --- |
 | 文字 | 1 | 1 | 0 | 1 | 1 |

 それで`pos = [0, 1, 3, 4]`、ギャップ`g = [1, 2, 1]`。 

比較するクエリの場合`[1, 3, 3]`そして`[3, 5, 3]`:

 最初の部分文字列`110`位置に 1 がある`[0,1]`したがって、そのギャップ署名は`[1]`。 

2 番目の部分文字列`011`位置にも 2 つあります`[3,4]`、ギャップも`[1]`。 

| ステップ | 部分文字列 1 | 部分文字列 2 |
 | --- | --- | --- |
 | L、R の位置 | [0,1] | [2,3] |
 | ギャップ範囲 | g[0:1] | g[2:3] |
 | ハッシュ | h(1) | h(1) |

 どちらも一致するため、答えは YES です。 

これは、絶対的な位置は重要ではなく、内部間隔のみが重要であることを示しています。

 ## 特殊なケース

 最初のエッジ ケースは、部分文字列に 0 または 1 が含まれる場合です。`1`。 たとえば、`10000`、部分文字列`[2,5]`誰もいません。 アルゴリズムはこれを空のギャップ シーケンスにマップするため、他のすべてゼロの部分文字列は同じ正規ハッシュを生成し、正しく YES を返します。 

もう 1 つのケースは、部分文字列の 1 の数は同じだが内部間隔が異なる場合です。 例えば、`10100`対`10010`どちらも 2 つを含みますが、ギャップ構造が異なります。 二分探索では、さまざまな区間が抽出されます。`pos`、異なるギャップ配列が生成されるため、ハッシュが異なり、アルゴリズムは正しく NO を返します。 

最後の微妙なケースは、部分文字列がグローバル文字列と異なる形で重複する場合です。`pos`配列の境界。 マッピングは経由で行われるため、`bisect_left`そして`bisect_right`、抽出された間隔は常に部分文字列内の実際の間隔に揃えられ、境界ゼロが 1 つずつ含まれることを防ぎます。そうしないとギャップ構造が破損します。
