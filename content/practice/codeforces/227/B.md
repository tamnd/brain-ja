 ## 解決策
 ## 問題の理解

 1 から _n_ までの整数の順列と、特定の要素の位置を求めるクエリのリストが与えられます。 このタスクは、2 つの線形検索戦略を比較することです。 Vasya の戦略は配列の最初の要素から最後に向かって検索を開始しますが、Petya の戦略は最後の要素から最初の要素に向かって検索します。 検索では、クエリごとに、ターゲットが見つかるまで比較の数がカウントされます。 各アプローチがすべてのクエリに対して行う比較の合計数を計算する必要があります。 

制約により、_n_ と _m_ は両方とも 100,000 まで大きくできることがわかります。 線形検索の単純なシミュレーションでは、クエリごとに配列を反復処理する必要があり、最悪の場合の複雑さは O(_n_·_m_) になります。これは 10^10 の演算に相当する可能性があり、2 秒の制限内では実行不可能です。 これにより、クエリごとに実際に配列をスキャンするアプローチが除外されます。 

エッジ ケースには、最初または最後の要素に対するクエリが含まれており、これにより最小または最大の比較が生成される可能性があります。 たとえば、配列が次の場合、`[1,2]`そしてクエリは`2`Vasya のアプローチでは 2 回の比較が必要ですが、Petya のアプローチでは 1 回の比較しか必要ありません。クエリの繰り返しもまた微妙な点です。 もし`1`が複数回クエリされる場合、比較は常に元の配列内の要素の位置によって決定されるため、異なる出現に対して誤って異なる値をカウントしないようにする必要があります。 

## アプローチ

 ブルートフォース手法では、クエリごとに配列を反復処理し、ターゲットが見つかるまで比較をカウントします。 これは線形探索ルールを直接シミュレートするため正しいですが、_n_ と _m_ が大きい場合は遅くなりすぎます。 最悪の場合、各クエリですべての _n_ 要素がスキャンされ、O(_n_·_m_) 回の操作が発生する可能性があります。 

最適化するための重要な洞察は、配列内の各要素の位置が固定されていることです。 すべての要素のインデックスを事前に計算すると、要素の位置を調べるだけで、あらゆるクエリに O(1) で答えることができます。 Vasya の場合、比較は 1 から始まるインデックスと等しくなります。 Petya の場合、それらは _n_ から 1 から始まるインデックスを引いたものに 1 を加えたものに等しくなります。これは、最後から数えることを表します。 各要素をそのインデックスにマッピングする辞書を事前計算すると、クエリ処理が単純な算術演算に削減され、全体的なソリューションは O(_n_ + _m_) になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n・m) | O(n) | 遅すぎる |
 | 最適 | O(n + m) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 整数 _n_ とサイズ _n_ の順列配列を読み取ります。 この配列には、1 から _n_ までのすべての整数が何らかの順序で含まれています。 
2. 各要素から配列内の 1 から始まるインデックスへのマッピングを作成します。 これにより、任意の要素の位置を O(1) で取得できるようになります。 
3. 整数 _m_ とサイズ _m_ のクエリのリストを読み取ります。 
4. 合計を比較するために 2 つのカウンターを初期化します。`vasya_total`そして`petya_total`。 
5. 各クエリ要素について、マッピングからインデックスを取得します。 インクリメント`vasya_total`インデックスによって、そして`petya_total`(_n_ - インデックス + 1) によって。 これは、それぞれ最初と最後からの線形検索を反映します。 
6. すべてのクエリを処理した後、2 つの合計を出力します。 

機能する理由: マッピングにより、配列を反復処理することなく、クエリごとに各戦略で必要な比較の数が正確にわかります。 不変条件は、位置マッピングが固定されており、配列内の正確な位置を表すことです。 Petya の算術演算では逆方向のトラバーサルが考慮されており、すべてのクエリを合計すると正しい合計が得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
arr = list(map(int, input().split()))
pos = [0] * (n + 1)  # 1-based indexing

for i, val in enumerate(arr):
    pos[val] = i + 1  # store 1-based index

m = int(input())
queries = list(map(int, input().split()))

vasya_total = 0
petya_total = 0

for q in queries:
    idx = pos[q]
    vasya_total += idx
    petya_total += n - idx + 1

print(vasya_total, petya_total)
```コードはまず位置マップを構築します。これは高速検索に不可欠です。 クエリのループは、事前に計算されたインデックスに基づいて単純に合計を累積します。 1 から始まるインデックスを使用すると、Petya の比較を計算する際の off-by-one エラーを回避できます。 キーが 1 から _n_ までの連続した整数であるため、マッピングに辞書ではなく配列を選択すると、若干高速になります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m) | 位置マップの構築に O(n)、すべてのクエリの処理に O(m) |
 | スペース | O(n) | サイズ n+1 の位置マップ配列 |

 n と m が最大 10^5 の場合、アルゴリズムは最大 2 · 10^5 の演算と小さなオーバーヘッドを実行し、2 秒の時間制限と 256 MB のメモリ制限を十分に満たします。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n = int(input())
    arr = list(map(int, input().split()))
    pos = [0] * (n + 1)
    for i, val in enumerate(arr):
        pos[val] = i + 1
    m = int(input())
    queries = list(map(int, input().split()))
    vasya_total = petya_total = 0
    for q in queries:
        idx = pos[q]
        vasya_total += idx
        petya_total += n - idx + 1
    return f"{vasya_total} {petya_total}"

# provided samples
assert run("2\n1 2\n1\n1\n") == "1 2", "sample 1"
assert run("2\n1 2\n1\n2\n") == "2 1", "sample 2"

# custom test cases
assert run("1\n1\n1\n1\n") == "1 1", "single element"
assert run("5\n5 3 1 2 4\n3\n1 4 5\n") == "10 9", "random permutation"
assert run("3\n1 2 3\n3\n3 3 3\n") == "9 3", "repeated queries"
assert run("4\n4 3 2 1\n4\n1 2 3 4\n") == "10 10", "reverse array"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 要素、クエリ 1 | 1 1 | ミニマルサイズのケース |
 | 5 要素の順列、ランダム クエリ | 10 9 | 一般的な順列とクエリの蓄積 |
 | 繰り返されるクエリ | 9 3 | 繰り返されたクエリは正しくカウントされます。 
| 逆配列 | 10 10 | 配列を反転したときの対称性 |

 ## 特殊なケース

 クエリを含む単一要素配列の場合`1`、位置マップはインデックス 1 を割り当てます。Vasya と Petya は両方とも 1 の比較をカウントします。 クエリが繰り返される場合、マップは各クエリが毎回同じインデックスを正しく取得することを保証し、再計算を回避します。 逆配列では、クエリ セットに応じて Petya と Vasya の合計が等しい可能性があり、アルゴリズムが極端なトラバース方向を正しく処理していることが確認されます。
