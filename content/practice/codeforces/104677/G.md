 ## 解決策
 ## 問題の理解

 問題のリストが与えられ、それぞれに必要な時間コストとポイント値が示されます。 問題は、これらの問題が常に利用できるわけではないということです。 代わりに、複数のクラスがあり、各クラスは問題の連続したセグメントのみを教えます。 授業中、生徒の時間は限られており、教えられた問題のサブセットを選択できますが、各問題はそのクラス内で最大 1 回しか解決できません。 

すべてのクラスについて、区間内の問題のサブセットを選択することで得られる最大の合計値を知りたいと考えています。$[l, r]$合計時間が超えない方$t$。 最終的な答えは、すべてのクラスにわたる最適値の合計です。 

制約はソリューションを強力に形作ります。 問題の数は最大で$10^4$、クラスの数は最大です。$10^5$。 ただし、問題ごとの時間制限とクラスの定員はどちらも小さく、最大でも 100 です。この組み合わせが重要なシグナルです。ナップザックの次元が制限されているため、クエリごとの擬似多項式 DP または事前計算戦略が示唆されます。 

範囲内のすべてのクエリに対してナップザックを再計算する単純なアプローチ$[l, r]$遅すぎるでしょう。 各ナップザックの容量は小さいですが、最大$10^4$クエリごとのアイテムとそれを実行する$10^5$時代は～につながる$10^9$移行は不可能です。 

さらに微妙な問題は、問題がクエリ間で繰り返されますが、常に独立して再計算されることです。 クエリ間で構造を再利用しないソリューションや、小さな容量を利用できないソリューションはタイムアウトになります。 

エッジケースは、間隔は小さいが容量が大きい場合、または容量は小さいが間隔が大きい場合に発生します。 たとえば、次の場合$t = 1$、最も効率的な単一項目のみが重要です。 単純なサブセット列挙では、依然として複数の項目を考慮しようとする可能性があり、時間を無駄にします。 もう 1 つのエッジ ケースは、同一の範囲でクエリが繰り返される場合で、再計算が冗長になります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 クエリごとに、すべての問題を考慮します。$[l, r]$容量0/1のナップザックを実行します$t$。 これは、各問題がクラスごとに最大 1 回しか受験できないという制約を直接モデル化しているため、これは正しいです。 各クエリの処理にかかるコストは次のとおりです。$O(N \cdot t)$、最悪のケースを与えると、$10^5 \cdot 10^4 \cdot 100 = 10^{11}$限界をはるかに超えた移行。 

重要な観察点は、レンジサイズは大きいものの、容量は非常に小さいということです。 これは、各クエリに線形な動的プログラミング構造を使用して回答できることを示唆しています。$t$、ではありません$r-l+1$。 標準的な手法は、セグメントにわたるナップザック遷移を事前計算することですが、完全な項目リストに対して素朴に実行すると、DP 状態を含むセグメント ツリーが重くなりすぎます。 

代わりに、視点を反転します。$v_i$注文には関係ありませんが、重量は$s_i$が小さい場合、プレフィックスごとに、最大 100 までの容量ごとに達成可能な最良の値を格納する DP テーブルを維持できます。その後、各ノードがサイズのナップザック遷移テーブルを格納するセグメント ツリーを使用してプレフィックスの状態を組み合わせることで、範囲クエリに答えることができます。$101 \times 101$。 各ノードは、「容量 c から開始した場合、このセグメントを使用して達成可能な最高の値はいくらか」を表します。 

これにより、各マージが容量を超えた制限された畳み込みに短縮され、ノードごとに一定の時間がかかります。 したがって、セグメント ツリーは範囲クエリをサポートします。$O(\log N \cdot 100^2)$、これは許容範囲です。

 ## アルゴリズムのチュートリアル

 各ノードが DP 変換テーブルを格納するセグメント ツリーを構築します。 

1. 問題ごとに$i$、ベース DP 遷移を初期化します。 この遷移は、何もしないか、問題を解決するかのいずれかを表します$i$容量が許せば。 テーブルにはサイズがあります$(T+1)$どこ$T = 100$。 
2. リーフ ノードの場合、DP テーブルはその単一の問題から直接構築されます。 あらゆる容量に対応$c$、次の場合にアイテムを引き取るかどうかを決定します。$c \ge s_i$、そうでない場合は、値を変更しないままにします。 
3. 内部ノードは、左と右の子をマージすることによって構築されます。 マージは、最初に左側のセグメントを適用し、次に右側のセグメントを適用することを表します。 容量ごとに$c$に分割してみます。$k$左側の部分に使用されており、$c-k$すべての分割の最大値を取得して、右側の部分で使用されます。 

これは本質的に、2 つの DP テーブルに対するナップザック畳み込みです。 
4. お問い合わせの場合$[l, r]$では、範囲クエリと同様に、セグメント ツリーを走査し、関連するすべてのノードを順番に結合します。 結果は、間隔全体を表す 1 つの DP テーブルになります。 
5. クエリの答えは、容量に保存されている値です$t$最終的にマージされた DP テーブル内。 

これが機能する理由は、各セグメント ツリー ノードが、その間隔にわたって入力容量から出力最良値への完全かつ正確な変換をエンコードしているためです。 セグメントの結合は、これらの変換の関数合成に対応し、セグメント ツリーによって正しい順序で適用されることが保証されます。 

### なぜ効果があるのか

 各ノードは関数を表します$F(c)$容量のあるセグメント内のアイテムを使用して達成可能な最大値を与える$c$。 リーフ ノードは、単一項目のナップザックの決定を直接エンコードするため、正しい基本関数を定義します。 ノードのマージは機能の合成に対応します。最初に左側のセグメントを適用すると容量が削減され、次に右側のセグメントが残りの容量で動作します。 別々のセグメントでのナップザックの選択は独立しており、容量は DP テーブルで完全に考慮されるため、合成された関数は正確なままです。 すべてのクエリはセグメントの互いに素な結合に分解されるため、最終的な構成では、間隔全体にわたって最適なサブセット選択が再現されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXT = 100

def merge(a, b):
    res = [0] * (MAXT + 1)
    for c in range(MAXT + 1):
        best = 0
        for k in range(c + 1):
            val = a[k] + b[c - k]
            if val > best:
                best = val
        res[c] = best
    return res

class SegTree:
    def __init__(self, items):
        self.n = len(items)
        self.size = 1
        while self.size < self.n:
            self.size *= 2
        self.data = [[0] * (MAXT + 1) for _ in range(2 * self.size)]

        for i, (s, v) in enumerate(items):
            dp = [0] * (MAXT + 1)
            for c in range(s, MAXT + 1):
                dp[c] = v
            self.data[self.size + i] = dp

        for i in range(self.size - 1, 0, -1):
            self.data[i] = merge(self.data[2 * i], self.data[2 * i + 1])

    def query(self, l, r):
        l += self.size
        r += self.size + 1
        left = [0] * (MAXT + 1)
        right = [0] * (MAXT + 1)

        while l < r:
            if l % 2 == 1:
                left = merge(left, self.data[l])
                l += 1
            if r % 2 == 1:
                r -= 1
                right = merge(self.data[r], right)
            l //= 2
            r //= 2

        return merge(left, right)

def solve():
    n = int(input())
    items = [tuple(map(int, input().split())) for _ in range(n)]
    seg = SegTree(items)

    q = int(input())
    ans = 0
    for _ in range(q):
        l, r, t = map(int, input().split())
        l -= 1
        r -= 1
        dp = seg.query(l, r)
        ans += dp[t]
    print(ans)

if __name__ == "__main__":
    solve()
```セグメント ツリーはボトムアップで構築され、各ノードには全容量の DP テーブルが格納されます。 リーフの初期化は、アイテムをスキップするか、容量が許せば 1 回だけ取得するかの、簡単なナップザックの選択をエンコードします。 マージ操作は、2 つの独立したナップザック セグメントを結合する有界たたみ込みです。 

クエリ ロジックは標準のセグメント ツリー範囲クエリ パターンを使用しますが、値を保存する代わりに DP 変換を構成します。 ナップザックの構成は可換ではないため、左右のアキュムレータによって順序が確実に保持されます。 

微妙な点の 1 つは、両方とも`left`そして`right`方向順にマージする必要があります。 DP の構成はセグメントの順序に依存するため、どちらかの側を逆にすると正確さが失われます。

 ## 特殊なケース

 主なエッジケースは、容量がセグメント内のすべてのアイテムの重量よりも小さい場合です。 たとえば、次のような単一のアイテム$s = 10$そして$t = 3$すべての容量に対してゼロのままの DP テーブルが生成され、マージ操作ではその中立性が維持されます。 

もう 1 つの特殊なケースは、クエリ全体で同じ範囲が繰り返されることです。 各クエリはセグメント ツリーから DP を再計算するため、正確さには影響しませんが、単純なソリューションでは同一のナップザックを複数回再計算することになり、大幅な非効率が生じます。 

最後の微妙なケースは、最適なソリューションにセグメント ツリー クエリの両端の項目を混合することが含まれる場合です。 たとえば、アイテムが左半分と右半分に分割されている場合は、正しい DP 構成順序が必要です。 セグメント ツリーは左から右へのマージを保証するため、次のような 2 つのアイテムのような場合は、$s = 2$と容量$t = 3$部分的な容量分割ごとに 1 つの項目のみを許可することで正しく処理されます。
