 ## 解決策
 ## 問題の理解

 私たちに与えられているのは、$n \times n$各セルに建物の初期高さが含まれるグリッド。 2 種類の操作を使用してグリッドを変更できます。 行にはタイプAの労働者を雇うことができます$i$、その行のすべての値を 1 ずつ増やします。または、列にタイプ B のワーカーを雇うこともできます。$j$これにより、その列のすべての値が 1 ずつ増加します。各ワーカーは最大 1 回のみ使用でき、それぞれに固定コストがかかります。 

行操作と列操作の一部を適用した後、最終的なグリッドには、水平方向または垂直方向に隣接する 2 つのセルが同じ値を持たないというプロパティが必要になります。 目標は、総コストを最小限に抑えること、またはどの操作を選択しても有効なグリッドを実現できないと判断することです。 

重要な構造的制約は、すべてのセルが$(i,j)$行の有無によってのみ影響を受けます。$i$が選択されているかどうかの列$j$が選ばれます。 これは、最終値が単純な加算形式になることを意味し、各セルは最大 2 つの二分決定によってシフトされます。 

制約は全体として厳しいです: 合計$n$すべてのテスト ケースの数は最大 1000 であり、各テスト ケースには$n$これにより、3 次以上の依存性が即座に排除されます。$n$。 行と列のすべてのサブセットをチェックするソリューションは不可能です。$2^{2n}$。 平$O(n^3)$テスト ケースごとの値は境界線にありますが、非常に小さい定数の場合にのみ許容されます。 意図したソリューションでは、問題をテスト ケースごとに本質的に線形または二次的なものに削減する必要があります。 

微妙な点は、均等性制約は隣接するセル間でのみ重要であるということです。 隣接しない関係は無関係であり、問​​題がグリッド グラフのエッジ上の局所的な制約に分解されることを示唆しています。 

素朴な落とし穴は、行と列を独立して扱うことです。 たとえば、最初に行の違いを修正し、次に列の違いを貪欲に修正しようとする場合があります。 これは、行の選択がすべての列に同時に影響するため、失敗します。そのため、1 つの列でローカルに有効な修正が別の列の制約を破る可能性があります。 

別の失敗モードは、元のグリッドのローカル比較に基づいて各行または列が独立して決定できると仮定することです。 これは、制約が共有セルを通じて行と列の決定を結合することを無視します。 

## アプローチ

 ブルートフォースのアイデアは、行と列のすべてのサブセットを試すことです。 サブセットごとに、結果のグリッドを計算し、すべての隣接制約をチェックします。 これは正しいですが、すぐには実行不可能です。$2^n$行の選択肢と$2^n$列の選択により、指数関数的な爆発が起こります。 

完全な割り当てをグローバルに考慮することを回避する方法が必要です。 重要な観察は、各行の決定が 2 値であり、隣接するセル間の制約には、これら 2 値の決定の違いのみが含まれるということです。 

させて$x_i \in \{0,1\}$操作 A を行に適用するかどうかを示します$i$、 そして$y_j \in \{0,1\}$操作 B を列に適用するかどうかを示します$j$。 最終的な高さは、$$h'_{i,j} = h_{i,j} + x_i + y_j.$$ここで、次の間の水平隣接制約を考えてみましょう。$(i,j)$そして$(i,j+1)$。 必要なものは次のとおりです。$$h_{i,j} + x_i + y_j \ne h_{i,j+1} + x_i + y_{j+1}.$$行の項は完全にキャンセルされ、次のものが残ります。$$h_{i,j} + y_j \ne h_{i,j+1} + y_{j+1}.$$これは重要な構造の単純化です。水平方向の制約は列の決定にのみ依存します。 同様に、垂直制約は行の決定のみに依存します。$$h_{i,j} + x_i \ne h_{i+1,j} + x_{i+1}.$$したがって、グリッドは 2 つの独立した 1D 問題に分解されます。1 つは行に関するもの、もう 1 つは列に関するものですが、合計コストが加算される点が異なります。 ただし、行と列の割り当ての両方が同時に制約を満たさなければならないことが難しいのです。 

各行と列は、パス グラフ上でバイナリのラベル付け問題を形成します。隣接するノードは、次の形式の不等式制約を満たさなければなりません。$$x_i \ne x_{i+1} \text{ or } x_i = x_{i+1},$$高さが与えられた割り当ての下で平等を強制するかどうかに応じて。 

より正確には、隣接するペアごとに、制約によって (0,0)、(1,1) が許可されるか、または強制的に変更が行われるかを導き出します。 これは、ノードごとに 2 つの状態を持つチェーン上の古典的な DP になります。 

ライン上の DP を使用して行の制約を個別に解決し、列についても同様に解決します。 どちらかが不可能になったら、答えは不可能です。 

最後に、有効な行構成と列構成の最小コストを追加します。

 | 行と列を個別に DP |$O(n^2)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 行のソリューションについて説明します。 列は対称です。 

1. 隣接する行のペアごとに$i$そして$i+1$の組み合わせを決定します。$(x_i, x_{i+1})$有効です。 

与えられた選択肢のペアの下で等価性が生じるかどうかを列ごとにチェックします。 いずれかの列が等しくなる場合、その代入は禁止されます。 
2. 行遷移ごとに、4 つの可能性に対して制約マスクを構築します。$(0,0), (0,1), (1,0), (1,1)$。 

これは、DP の意味でどの遷移が許可されるかをエンコードします。 
3. 状態が次の行に対して DP を実行します。$dp[i][t]$、行までの最小コストを意味します$i$割り当て付き$t \in \{0,1\}$。 
4. 行からの遷移$i$に$i+1$許可された遷移のみを使用します。 

遷移が制約によって禁止されている場合、遷移はスキップされます。 
5. 国家のコスト$t$列で$i$は$a_i \cdot t$、行を選択するとコストが追加されるため$a_i$。 
6. 最終行で両方の状態の最小値を計算します。 到達可能な状態がない場合、行システムは不可能です。 
7. 次を使用して列に対して同じプロセスを繰り返します。$b_j$そして垂直方向の制約。 
8. 最終的な答えは、最適な行コストと列コストの合計です。 

分解が有効である理由は微妙です。水平制約は列変数のみに依存し、垂直制約は行変数のみに依存するため、代入の実現可能性は明確に分離されます。 コストも分離できるため、最小化は分割されます。 

### なぜ効果があるのか

 各隣接制約は、バイナリ変数のペアに対する制約になります。 各変数は 1 つの次元に沿った制約にのみ現れるため、制約グラフは 2 つの独立したチェーンに分割されます。 DP は、グローバルに一貫したバイナリのラベル付けをすべて調査しながら、すべてのペアごとの制限を強制し、無効な構成が決してカウントされないようにします。 すべての有効な構成は 1 つの DP パスにのみ対応し、すべての DP パスは有効な構成に対応するため、最適な値が保持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**18

def solve_line(cost, bad_pairs):
    n = len(cost)
    dp0 = 0
    dp1 = cost[0]
    
    for i in range(n - 1):
        ndp0 = ndp1 = INF
        
        for cur in [0, 1]:
            cur_dp = dp0 if cur == 0 else dp1
            if cur_dp >= INF:
                continue
            for nxt in [0, 1]:
                if bad_pairs[i][cur][nxt]:
                    continue
                val = cur_dp + (cost[i + 1] if nxt else 0)
                if nxt == 0:
                    ndp0 = min(ndp0, val)
                else:
                    ndp1 = min(ndp1, val)
        
        dp0, dp1 = ndp0, ndp1
    
    return min(dp0, dp1)

def build_row_constraints(h, n):
    bad = [[[False]*2 for _ in range(2)] for _ in range(n-1)]
    
    for i in range(n - 1):
        for x in [0, 1]:
            for y in [0, 1]:
                ok = True
                for j in range(n):
                    if h[i][j] + x == h[i+1][j] + y:
                        ok = False
                        break
                bad[i][x][y] = not ok
    return bad

def build_col_constraints(h, n):
    bad = [[[False]*2 for _ in range(2)] for _ in range(n-1)]
    
    for j in range(n - 1):
        for y in [0, 1]:
            for z in [0, 1]:
                ok = True
                for i in range(n):
                    if h[i][j] + y == h[i][j+1] + z:
                        ok = False
                        break
                bad[j][y][z] = not ok
    return bad

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n = int(input())
        h = [list(map(int, input().split())) for _ in range(n)]
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))
        
        row_bad = build_row_constraints(h, n)
        col_bad = build_col_constraints(h, n)
        
        row_cost = solve_line(a, row_bad)
        col_cost = solve_line(b, col_bad)
        
        ans = row_cost + col_cost
        if ans >= INF:
            ans = -1
        out.append(str(ans))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```行 DP と列 DP は構造的に同一ですが、制約の事前計算方法が異なるだけです。 各 DP は問題をパス上のバイナリのラベルとして扱い、各エッジが状態のいくつかの組み合わせを禁止します。 

実装の微妙な詳細は、隣接するペアごとに 4 つの状態遷移すべてを明示的に列挙することです。 これにより、一方向のみが有効な非対称ケースの欠落が回避されます。 もう 1 つの重要なポイントは、dp 状態を慎重に初期化することです。最初の行 (または列) のコストは 0 またはそれに対応する雇用コストのいずれかです。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、隣接する行のペアのすべてのセルが 4 つの状態の組み合わせすべてで等しくなる場合です。 その状況では、遷移行列は完全に禁止され、DP は実行不可能性を正しく伝播する必要があります。 

行全体に交互パターンを強制するなど、割り当てが 1 つだけ有効な場合には、別のエッジ ケースが発生します。 DP は両方の状態を明示的に追跡し、有効な遷移のみを許可するため、これを処理します。 

最後のエッジ ケースは、行と列のソリューションが個別に実行可能であるにもかかわらず、その複合効果により有効な最終制約が生成される場合です。 分解は独立しているため、アルゴリズムは結合エラーなしで最小コストを正しく合計します。
