 ## 解決策
 ## 問題の理解

 配列を段階的に構築するプロセスが与えられています。 最初は配列が空で、1 から n までの数値が値の昇順に 1 つずつ挿入されます。 各数値 i は現在の配列内の指定された位置 pi に挿入され、その位置以降のすべてが右にシフトされるため、構造は常に有効なシーケンスになります。 

挿入するたびに、現在の配列の最長増加サブシーケンス (LIS) の長さを計算する必要があります。 

重要な問題は、配列が単に拡大するだけでなく、途中での挿入によって動的に並べ替えられることです。 したがって、LIS は静的配列プレフィックス上ではなく、位置挿入操作によって展開されるシーケンス上にあります。 

制約により、n は最大 200000 まで許可されるため、挿入のたびに LIS を最初から再計算するアプローチは遅すぎます。 ステップごとに 1 回の O(n^2) 個の LIS 計算はすでにステップごとに 2 次計算になり、合計作業量はおよそ O(n^3) になりますが、これは完全に実行不可能です。 2e5 の 2 乗は約 4e10 回の演算となるため、全ステップの合計が O(n^2) であっても遅すぎます。 

したがって、順序統計または LIS のような構造を動的に維持するデータ構造を使用する可能性が高い、O(n log n) または O(n log^2 n) あたりの解決策が期待されるはずです。 

微妙な問題は、すべての挿入後の最終配列は 1 から n の順列ですが、中間状態はその完全なセットのランダムな順列ではないことです。 それらは増加するセットの接頭辞の順列です。 静的順列 LIS トリックに依存するソリューションでは、進化する構造を注意深く処理する必要があります。 

素朴な直感を打ち破るエッジケースの 1 つは、挿入が前方に大きく偏っている場合です。 たとえば、次のすべての要素を位置 1 に挿入すると、配列は [n, n-1, ..., 1] になり、すべてのステップで LIS 1 が含まれます。 「価値が増加しているので、LIS は成長するはずだ」という素朴な直観は、ここでは位置力学が優勢であるため完全に失敗します。 

もう 1 つのエッジ ケースは、毎回最後に挿入するなどの交互の挿入で、完全に増加する配列 [1,2,3,...] を生成します。ここで、LIS は現在のサイズと等しくなります。 位置の影響を無視したアプローチでは、この単調な成長を見逃すことになります。 

## アプローチ

 直接的な総当たりアプローチでは、各挿入後に LIS が再計算されます。 k 回目の挿入の後、サイズ k の配列が得られ、標準の O(k log k) 忍耐ソート LIS アルゴリズムを実行します。 より大きな配列を繰り返し処理するため、すべての k を合計すると、総コストは n^2 log n のオーダーになります。 対数係数がない場合でも、二次関数の増加が支配的となり、n が 200000 までは遅すぎます。 

重要な観察は、挿入プロセスが 1 から n の順列を構築するのと同等であり、各数値は挿入の時点で固定されているということです。 LIS を繰り返し再計算するのではなく、LIS を段階的に維持したいと考えています。 問題は、要素を中間に挿入すると多くの要素の相対位置が変更されるため、LIS の直接メンテナンスが簡単ではなくなることです。 

これに対処する標準的な方法は、プロセスを逆に再解釈するか、ポジションにわたる動的構造としてモデル化することです。 有用な観点は、各値 i について、配列内の最終位置を維持することを考えることです。 i は 1 から i-1 までのすべての値がすでに存在するときに挿入されるため、空のスロットを維持するセグメント ツリーを使用して最終的な順列の構築をシミュレートできます。 各挿入では、値 i が pi 番目の空の位置に配置されます。 

最終的な順列を位置に関して再構築すると、古典的な考え方を使用してその順列の LIS を計算できます。順列の LIS は、値に対するフェンウィック ツリーまたはセグメント ツリーを使用して計算できます。この場合、位置を左から右に処理し、各値で終わる最適な増加部分列を維持します。

ただし、最後だけでなく、挿入するたびに答えが必要です。 これは、構造を動的に維持することを示唆しています。各 i を配置した後、その位置を更新し、LIS 寄与を更新します。 重要な洞察は、挿入の順序統計マッピングをサポートするセグメント ツリーを通じて位置を管理しながら、i で終わる LIS である dp[i] を値の順序で維持できることです。 

最終的な解決策は、動的置換ビルダーと、位置によってキー化された値に対する BIT を使用した値に対する LIS DP を維持することであり、新しい値が最終位置に挿入されるたびに段階的に更新されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 各挿入後に LIS を再計算する | O(n^2 log n) | O(n) | 遅すぎる |
 | セグメントツリー位置構築+BIT LIS保守 | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各セグメントに残っている空きスロットの数を格納するセグメント ツリーをポジションごとに維持します。 最初はすべての位置が空で、値 1 ～ n を挿入すると、各値が残りの空のスロットの正しい位置に配置されます。 これにより、配列を明示的にシフトすることなく、各値の最終インデックスを決定できます。 
2. 各値 i について、セグメント ツリーをたどることによってその実際の位置 pos[i] を見つけます。常に、空きスロットがどれだけ残っているかに応じて、挿入が左のサブツリーに入るのか右のサブツリーに入るのかを決定します。 このステップにより、シフトプロセスを効率的にシミュレートできるようになります。 
3. pos[i] がわかったら、(pos[i], i) を順列内の点として扱います。ここで、pos は座標、i は値です。 ここで、これらの点を i の昇順で明らかにするときに、これらの点の LIS を維持したいと考えています。 
4. 任意の位置について、その位置で終了する最大 LIS 長を格納するフェンウィック ツリーを位置にわたって維持します。 値 i を処理するときは、拡張可能な最適な LIS を見つけるために、pos[i] より前のすべての位置を厳密にクエリします。 
5. dp[i] を 1 にその最良のクエリ結果を加えたものとして設定し、pos[i] のフェンウィック ツリーを dp[i] で更新します。 これにより、将来の要素がこの位置を介してサブシーケンスを拡張できるようになります。 
6. 各挿入後の答えは、フェンウィック ツリーに保存されている最大値になります。これは、これまでに挿入されたすべての要素の中で最良の LIS を表すためです。 

重要なアイデアは、動的シフト配列を静的順列に段階的に変換し、標準 LIS DP を位置順に適用するということです。 

### なぜ効果があるのか

 セグメント ツリーは、たとえ以前の挿入によって位置が移動したとしても、pos[i] が完全に構築された配列内の値 i の最終インデックスであることを保証します。 次に、フェンウィック ツリー DP は、(pos[i], i) で定義された順列に対して LIS を計算します。 値を昇順で処理するため、すべての有効な増加サブシーケンスは、位置が増加する増加値のシーケンスに対応し、DP 再帰は、構成を欠落することなく、そのような拡張をすべてキャプチャします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def update(self, i, v):
        while i <= self.n:
            if v > self.bit[i]:
                self.bit[i] = v
            i += i & -i

    def query(self, i):
        res = 0
        while i > 0:
            if self.bit[i] > res:
                res = self.bit[i]
            i -= i & -i
        return res

class SegTree:
    def __init__(self, n):
        self.n = n
        self.t = [0] * (4 * n)
        self.build(1, 1, n)

    def build(self, v, l, r):
        if l == r:
            self.t[v] = 1
            return
        m = (l + r) // 2
        self.build(v * 2, l, m)
        self.build(v * 2 + 1, m + 1, r)
        self.t[v] = self.t[v * 2] + self.t[v * 2 + 1]

    def kth(self, v, l, r, k):
        if l == r:
            return l
        m = (l + r) // 2
        if self.t[v * 2] >= k:
            return self.kth(v * 2, l, m, k)
        else:
            return self.kth(v * 2 + 1, m + 1, r, k - self.t[v * 2])

    def remove(self, v, l, r, idx):
        if l == r:
            self.t[v] = 0
            return
        m = (l + r) // 2
        if idx <= m:
            self.remove(v * 2, l, m, idx)
        else:
            self.remove(v * 2 + 1, m + 1, r, idx)
        self.t[v] = self.t[v * 2] + self.t[v * 2 + 1]

n = int(input())
p = list(map(int, input().split()))

seg = SegTree(n)
fen = Fenwick(n)

pos = [0] * (n + 1)
ans = []

for i in range(1, n + 1):
    idx = seg.kth(1, 1, n, p[i - 1])
    seg.remove(1, 1, n, idx)
    pos[i] = idx

    best = fen.query(idx - 1)
    dp = best + 1
    fen.update(idx, dp)

    ans.append(str(fen.query(n)))

print("\n".join(ans))
```セグメント ツリーは、利用可能な位置のセットを維持することによって、シフト挿入プロセスを処理します。 k 番目の各クエリは、現在の値が到達する実際の位置を見つけます。 

フェンウィック ツリーはポジション全体で LIS を維持しますが、更新は単調な改善のみであるため、値を減らす必要はありません。 

よくある落とし穴は、ポジションのインデックスが 1 であること、および k 番目の選択は元のインデックスではなく残りのスロットで行う必要があることを忘れていることです。

 ## 特殊なケース

 すべての要素が位置 1 に挿入されると、概念的には各操作が残りのスペースの前に挿入されますが、すべての新しい要素は最終的な順序で前の要素の後に配置されます。 セグメント ツリーは正確な位置追跡を保証し、フェンウィック ツリーは単純に位置の増加シーケンスにわたって LIS を蓄積し、直線的な LIS の増加を生成します。 

すべての要素がそれぞれの増加位置に挿入されると、配列は全体にわたってソートされたままになります。 k 番目の選択メカニズムは、各値を次に利用可能な位置に割り当てるため、pos[i] は i と等しくなります。 その後、フェンウィック ツリーでは厳密に増加する位置のシーケンスが表示され、更新のたびに LIS が 1 ずつ拡張され、直感的な結果と一致します。 

挿入が前後で交互に行われる場合、セグメント ツリーは自明ではない順列を生成しますが、LIS DP は挿入履歴ではなく位置の相対的な順序のみに依存するため、正しいままです。 格納されているすべての値が、特定の位置で終了する最適なサブシーケンスを表すという DP の不変条件は、全体を通じて有効です。
