 ## 解決策
 ## 問題の理解

 長さの隠し配列が与えられます$n$、からの数値の順列が含まれます。$1$に$n$。 配列を直接見ることはできません。 それと対話する唯一の方法は 2 つの位置を選択することです$i < j$そして裁判官にそれらの位置の値を比較するように依頼します。 左の値が右の値より大きい場合、裁判官はそれらを交換し、交換が起こったと報告します。 それ以外の場合は何も変化せず、裁判官は何も起こらなかったと報告します。 

目標は、配列を恒等順列、つまり位置に変換することです。$i$値を含める必要があります$i$あらゆる人にとって$i$。 クエリの後はいつでも、ジャッジは比較結果の代わりに WIN で応答する可能性があります。これは、配列が完全にソートされているため、直ちに停止する必要があることを意味します。 

問題は、アレイが安定していないことです。 ブロックごとに$2n$クエリに応じて、裁判官は密かに 2 つのポジションを均一にランダムに選択し、それらの値を交換します。 これは通知なしに発生し、進行状況が破壊される可能性があります。 それでも、10000 クエリ以内で、裁判官がチェックする時点で最終的にソートされた状態に達することを保証する必要があります。 

制約$n \le 50$二次または三次の手順さえも許容できることを強く示唆します。$n$なぜなら、配列に対する 1 回の完全なパスのコストは最大でも数千回の操作にかかるからです。 本当の難しさは効率そのものではなく、ランダムな破損に対する堅牢性です。 

単純な解釈では、順列を正確に再構築し、精神的に並べ替えをシミュレートしようとすることになりますが、配列が予期せず変化するため、これは失敗します。 もう 1 つの素朴なアイデアは、破損がないと仮定して標準の並べ替えアルゴリズムを 1 回実行することですが、ランダム スワップの各バッチの後、配列は再び無効になり、確実に収束することはありません。 

重要なエッジケースは次の状況です。 ある時点で配列がソートされたが、ランダムなスワップの直後に、クエリを実行する前に再びソートされなくなったとします。 私たちのアルゴリズムが固定チェックポイントでのみ完了をチェックするか、単調な改善を想定している場合、WIN の瞬間を完全に逃すか、安定しない可能性があります。 

したがって、時折ランダムに入れ替えた後でも、配列がソートされた順序に繰り返し戻されるように、ローカルな順序を継続的に強制するプロシージャが必要です。 

## アプローチ

 ブルートフォース戦略では、各破損イベントの後に順列全体を回復し、それを最初から並べ替えようとします。 これには、順序を完全に推定するために多くのペアを繰り返しクエリし、各サイクルで配列を効果的に再構築することが含まれます。 たとえ順列を特定できたとしても$O(n \log n)$比較、毎回これを繰り返す$2n$この作戦は最悪の場合、大規模な爆発を引き起こす$O(\text{cycles} \cdot n \log n)$必要な破損サイクルの数に制限がないため、このアプローチでは 10000 クエリ以内に完了するという保証はありません。 

重要な観察は、置換をグローバルに再構築する必要がないということです。 すべてのクエリは、2 つの位置間の正しいローカル順序付けをすでに提供しています。 隣接する位置に一貫性を繰り返し適用すると、配列は軽度の摂動下でも継続的にソートされているかのように動作します。 

これは当然、比較ベースのソート ネットワーク スタイルのアプローチ、具体的にはバブル ソートや奇数偶数転置ソートに似た隣接スワップの繰り返しにつながります。 各比較では、局所的な不変条件が強制されます。反転が検出されるたびに、小さい値は左に移動し、大きい値は右に移動します。 ランダムなスワップによって新たな反転が生じたとしても、スイープを繰り返すと再び反転が除去されます。 

以来$n$最大 50、隣接する修正コストのフルパス$O(n)$このようなパスを制限された回数だけ繰り返すと、10,000 回の操作予算に簡単に収まります。

 | 破損サイクルごとの完全な再構築 |$O(\infty)$効果的に |$O(n)$| 遅すぎる/信頼性が低い |

 ## アルゴリズムのチュートリアル

 明示的な配列は維持しません。 代わりに、許可された比較交換操作を使用して繰り返されるローカル修正に完全に依存します。 

### ステップ

 1. 隣接する比較を使用して、左から右へ位置全体のフルパスを繰り返し実行します。$(i, i+1)$。 各クエリは、大きい要素が小さい要素の左側にある場合に、その要素が正しい方向に交換されることを保証します。 これはバブルソートと同じ仕組みです。 
2. フルパスを終了したら、すぐに次のパスを開始します。 ランダムなスワップでは配列内の任意の場所で反転が再導入される可能性があるため、1 回のパス後に停止しません。 
3. ジャッジが何らかの質問に対して WIN と応答するまで、これらのパスを実行し続けます。 この応答は、通常の SWAPPED または STAYED 出力を置き換え、配列が現在完全にソートされていることを示します。 
4. WIN を受信したら、それ以上の操作を出力せずに、常に直ちに停止します。 

隣接比較を使用する理由は、補正の最大の局所性を保証するためです。 十分なスワップが値を伝播した後、反転は最終的に隣接する反転として現れる必要があり、一度発生するとすぐに修正可能です。 

### なぜ効果があるのか

 核となる不変条件は、各比較でローカルな反転が排除されるか、ローカルな順序が変更されないままになるということです。 ランダムなスワップでは反転の数が一時的に増加する可能性がありますが、完全なスイープごとに、現在隣接している、または修正できるほど十分に近い反転の数が厳密に減少します。 繰り返しの掃引中にすべての反転が最終的に隣接する必要があるため、このプロセスにより繰り返しシステムから無秩序が排出されます。 

システムは有限であり、修正が成功するたびに配列が完全にソートされた構成に近づくため、中断されない限り、配列がソートされる瞬間が無数に存在します。 ジャッジはこれらの瞬間の 1 つを検出し、WIN を出力し、その時点で終了します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def ask(i, j):
    print(i, j, flush=True)
    res = input().strip()
    if res == "WIN":
        sys.exit(0)
    return res

def main():
    n = int(input().strip())
    max_ops = 10000
    used = 0

    while used < max_ops:
        for i in range(1, n):
            if used >= max_ops:
                break
            ask(i, i + 1)
            used += 1

if __name__ == "__main__":
    main()
```この実装は、左から右への隣接する比較を繰り返すという最も単純な形式の奇偶偶数転置のアイデアに従います。 各クエリは即座に発行され、WIN を受信すると即座に終了します。 

主な微妙な点は、配列の保存や再構築を決して試みないことです。 ローカルでシミュレートしようとすると、隠れたランダム スワップによりジャッジから同期が解除されます。 プログラムは純粋にリアクティブなままです。 

また、すべての出力をフラッシュし、WIN 直後に停止することで、対話プロトコルを厳密に尊重します。

 ## 特殊なケース

 微妙なエッジケースは、ランダムなスワップが適切な構成で停止するために、配列が 2 つの操作間で正確にソートされる場合です。 この状況では、アルゴリズムはソート状態を明示的に検出する必要はありません。 それは、ジャッジが次のクエリで WIN を返すかどうかに依存します。 たとえば、配列が次のようになった場合、$[1,2,3,4]$非表示のスワップ イベントの後、次の比較クエリがすぐに WIN をトリガーし、正常に終了します。 

もう 1 つのケースは、ランダムなスワップが単一のパスで修復できるよりも早くグローバルな秩序を継続的に破壊する場合です。 それでも、各ローカル修正は、発生した場合に少なくとも 1 つの反転を削除します。 各スイープではすべての隣接するペアが系統的に再チェックされるため、永久に検査されない反転は存在しません。 最終的に、クエリの時点で反転がまったく存在しない瞬間が発生し、WIN がトリガーされます。
