 ## 解決策
 ## 問題の理解

 value で始まる単一の整変数に対する演算のコレクションが与えられています。`c`。 各演算の形式は「現在の値が次の値に等しい場合」です。`a`、それを次のように置き換えます`b`各操作とともに、最終的な実行順序でそれを成功させるか失敗させるかを指示されます。 

成功した操作は、変数が現在その変数と等しくなった時点で実行される必要があります。`a`価値。 失敗した操作は、変数が次と等しくない時点で実行する必要があります。`a`。 タスクは、すべての操作が要求どおりに正確に動作するような操作の順序を見つけることです。 

主な問題点は、操作が成功するとグローバル変数が変更され、その後のすべての操作に影響を与えることです。 したがって、順序付けは独立していません。各操作は、現在の値が使用されるときにどのような値でなければならないかを制約し、将来の実現可能性に影響を与えます。 

この制約では最大 100,000 の操作が許可されるため、順列を試行したり、順序を繰り返しシミュレートしたりするアプローチは機能しません。 二次シミュレーションですら遅すぎますし、順序のバックトラックを伴うものは限界をはるかに超えています。 私たちは直線的、あるいは直線に近い構造を強いられています。 

いくつかの微妙な特殊なケースがすぐに現れます。 

2 つの異なる操作がどちらも同じ値で成功する必要がある場合`a`しかし、別の結果につながります`b`の場合、値の変更を「最初にトリガー」できるのはそのうちの 1 つだけであり、順序によってはもう 1 つが使用できない可能性があります。 

操作が失敗する必要がある場合と、その操作が`a`初期値と等しい`c`の場合、最初に配置するとすぐに成功するため、最初に配置することはできません。 

特に注意が必要な状況は、成功操作が尊重する必要がある一連の状態遷移を形成する一方で、失敗操作はトリガーされない「安全な」状態でスケジュールする必要がある場合に発生します。 状態の到達可能性を無視した素朴な貪欲な順序付けは、ここで破綻する傾向があります。 

## アプローチ

 ブルートフォースの観点では、操作のすべての順列を試し、初期値から変数をシミュレートし、各操作が必要な結果と一致するかどうかを確認します。 これはルールを直接適用するため、原則的には正しいですが、評価が必要です。`n!`注文。 部分的な実現可能性に基づいた枝刈りでも、各配置が残りのすべての操作に影響を与える方法で状態空間を変更するため、依然として指数関数的な分岐が発生します。 

重要な観察は、成功した各操作が、次からの有向遷移のように動作することです。`a`に`b`、および失敗操作では、変数が特定の値を回避する必要がある場合に制約が課されます。 順列の観点から考えるのではなく、ウォークスルーが必要なノードにあるときに、成功したすべての操作が正確に使用される、有効なウォークスルー値を構築する観点から考える必要があります。 

重要な構造的洞察は、成功した操作のみが状態を変更するということです。 失敗した操作では変数は変更されません。 それらは、状態に相対的な順序に関する制約にすぎません。 これは、値を介した一連の強制遷移の処理に問題を分離し、禁止条件が満たされる「問題のない」位置で障害操作をスケジュールすることを示唆しています。 

成功した操作はグラフ内のエッジとして解釈できます。`a`に`b`。 成功した操作の順序を決定すると、次から始まる値の決定的なパスが定義されます。`c`。 このパスが修正されると、すべての失敗操作は、現在の値がそのパスと等しくない点に配置される必要があります。`a`。 これにより、問題は、その条件が偶然成立する瞬間に失敗操作を決して配置しないようにするという問題に変わります。 

これは建設的な戦略につながります。まず、一貫した状態の進行を形成する成功した操作の有効なシーケンスを構築し、次に、現在の状態に関して安全である場合にはいつでも、失敗した操作を貪欲にインターリーブします。

 ## アルゴリズムのチュートリアル

 1. に基づいてオペレーションを 2 つのグループに分割します。`w`: 成功-必須および失敗-必須。 成功する操作は、次の条件に一致する必要がある操作です。`v == a`、一方、失敗したものはこの状態を回避する必要があります。 
2. 成功したすべての操作を、からの有向エッジとして扱います。`a`に`b`。 初期値から開始してこれらのエッジに従うシーケンスの構築を試みます`c`。 目標は、成功操作を適用するたびに、現在の値が正確にその値になるようにすることです。`a`。 
3. すべての成功操作を開始値ごとにグループ化して収集します。`a`。 これにより、現在の状態でどの成功操作を適用できるかをすぐに見つけることができます。 
4. ポインタを維持する`cur`変数の現在の値については、最初は`c`、から始まる未使用の成功操作を選択できる構造を維持します。`cur`可能な限り。 
5. 次の操作を繰り返します。未使用の成功操作が存在する場合は、`a == cur`、そのような操作を選択し、それを回答に追加し、使用済みとしてマークして更新します。`cur = b`。 成功操作を適用することが状態を進める唯一の方法であるため、このステップは強制されます。 
6. 現在の値に対してそのような成功操作が存在しない場合、一時的に値をさらに進めることができなくなります。 この時点で、残りの失敗操作を安全に配置できます。`a`に等しくありません`cur`なぜなら、それを実行しても偶然に成功することはないからです。 
7. 正確性を確保するために、保留中の失敗操作のセットを維持します。 失敗操作を配置する必要がある場合は常に、その操作を選択します。`a != cur`。 残りの失敗操作がすべてあった場合、`a == cur`、その場合、必要な故障条件に違反せずにそれらを配置することは不可能です。 
8. すべての操作が配置されるまで続行します。 いずれかの時点で有効な成功または失敗の操作を選択できない場合は、「No」を出力します。 

### なぜ効果があるのか

 このアルゴリズムは、以前に実行され成功したすべての操作と正確に一致する現在の状態値を維持します。 すべての成功操作は、前提条件が満たされた場合にのみ実行されるため、状態の進化は常に一貫しています。 失敗操作は、そのトリガー条件が false の場合にのみ実行されるため、その要件も構築によって満たされます。 

核となる不変条件は、現在の値が`cur`は、すでに選択されている一連の成功した操作によって初期値から常に到達可能であり、これまでに配置された失敗した操作がその禁止状態で実行されたことはありません。 成功操作は状態遷移を厳密に定義し、失敗操作は状態を変更しないため、有効な順序付けは、すべての成功遷移が一貫したパスを形成し、すべての失敗が一致しない状態でのみ挿入されるシーケンスに対応する必要があります。 貪欲な構造により、一致する成功エッジが存在する場合にのみ先に進むため、将来の成功遷移が時期尚早にブロックされることがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, c = map(int, input().split())

succ = {}
fail = []

for i in range(n):
    a, b, w = map(int, input().split())
    if w == 1:
        if a not in succ:
            succ[a] = []
        succ[a].append((b, i + 1))
    else:
        fail.append((a, i + 1))

used = set()
res = []
cur = c

# success operations indexed by availability
from collections import defaultdict, deque
succ = {k: deque(v) for k, v in succ.items()}
fail = deque(fail)

while len(res) < n:
    progressed = False

    # try success
    if cur in succ:
        while succ[cur] and succ[cur][0][1] in used:
            succ[cur].popleft()
        if succ[cur]:
            b, idx = succ[cur].popleft()
            used.add(idx)
            res.append(idx)
            cur = b
            progressed = True

    if progressed:
        continue

    # try failure
    if not fail:
        break

    placed = False
    for _ in range(len(fail)):
        a, idx = fail.popleft()
        if a != cur:
            used.add(idx)
            res.append(idx)
            placed = True
            break
        else:
            fail.append((a, idx))

    if placed:
        continue

    break

if len(res) == n:
    print("Yes")
    print(*res)
else:
    print("No")
```実装は各値からのマッピングを維持します。`a`そこから始まるすべての成功した操作に適用されます。 現在の値`cur`どのオペレーションが成功するかを決定します。 このような操作が見つかった場合は、遅延しても役に立たないため、すぐに適用されます。これが状態を変更する唯一のメカニズムです。 

失敗した操作はキューに保存され、安全な操作が見つかるまでローテーションされます。 失敗操作は、次の時点で安全です。`a`現状とは異なります。 これにより、想定される失敗を誤って成功に変えることがなくなります。 

主な微妙な点は、成功操作が常に優先される必要があることです。 現在の状態に対して有効な成功が存在する場合、失敗した操作は状態を変更せず、新しい適用性を作成できないため、それを遅延させると、今後のパスが永久にブロックされる可能性があります。

 ## 特殊なケース

 残りのすべての成功操作に、現在の状態からは到達不可能な値が必要な場合、重大なエッジ ケースが発生します。 たとえば、次から始まります`c = 1`成功操作を適用すると`1 → 2`、残りのすべての成功操作には、`1`そうすると、それらを実行する能力が永久に失われます。 このアルゴリズムは、利用可能な成功遷移を常に最初に消費するため、これを暗黙的に処理しますが、一致する遷移が存在しなくなると、残りの成功要件を無効にするような状態変更を強制することはありません。 

もう 1 つのエッジ ケースは、残りのすべての失敗操作に現在の値が必要な場合です。 その状況では、安全な障害配置は存在せず、アルゴリズムは正しく停止し、「いいえ」を出力します。 これは、他の時点では安全に実行できない障害によって現在の状態が「ブロック」されている構成に対応します。 

最後の微妙なケースは、成功操作が値のサイクルを形成する場合です。 各成功操作は 1 回だけ使用され、サイクルは単に値を再訪することを意味するため、貪欲トラバーサルはこれを自然に処理します。これは、遷移が利用可能なエッジと一致している限り許可されます。
