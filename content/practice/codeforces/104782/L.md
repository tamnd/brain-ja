 ## 解決策
 ## 問題の理解

 私たちは全員がシャワーを浴びる必要がある少人数のグループを与えられましたが、利用できるシャワーは 1 つしかありません。 シャワーは常に使用できるわけではありません。時間は水が流れる不連続な間隔に分割され、各間隔には固定された水の種類もあります。 これらの間隔以外では、シャワーはご利用いただけません。 

各人には要件があります。特定の種類の水のみを受け入れること、各シャワーには中断されない一定の時間がかかることなどです。 一度シャワーを浴びたら、中断することなくその時間ずっと滞在しなければならず、その間他の人はシャワーを使用できません。 目標は、全員が可能な限り早く終了できるように、すべての参加者を一定の順序で給水可能な間隔にスケジュールし、最後の人が終了するまでの時間をできるだけ短くすることです。 

重要な構造は、固定長のタスクを「有効なセグメント」を持つタイムラインに詰め込んでいることです。各セグメントにはラベル (水のタイプ) があり、各人は互換性のあるラベルを持つセグメントにのみ配置できます。 

制約は非常に具体的な意味で重要です。 人の数は最大 20 人であり、サブセットに対する指数関数的な推論を可能にするのに十分な数です。 ただし、シャワー間隔の数は 100,000 に達する可能性があるため、割り当てを貪欲にシミュレートしたり、時間の経過とともにすべての配置を単純に試したりしようとするソリューションは失敗します。 これは、問題の重要な部分が、配置の実現可能性のチェックを高速化するための前処理間隔である必要があることを直ちに示唆しています。 

微妙な難しさは、シャワーの間隔が固定タイプの連続ブロックであり、継続時間が長いという事実から生じます。 あるインターバルで開始しても完全にフィットしない場合、次のインターバルに飛び込むことはできません。 つまり、各割り当てはセグメントの境界を正確に尊重する必要があります。 

単純な間違いは、常に「利用可能な時間の早い順に人々を貪欲に配置する」または「間隔を順番に埋める」ことができると想定することです。 たとえば、2 人の人物と 2 つの間隔があり、1 つの長い間隔が存在するが、タイプの制約により 1 人だけがそれを使用できるとします。 貪欲な戦略は、短いジョブでその間隔を無駄にし、そこで長時間のジョブを必要とする適切な割り当てをブロックする可能性があります。 

複数の間隔が同じタイプであるが、離れている場合、別の微妙なエッジ ケースが発生します。 たとえ前の間隔では不十分であっても、人は後の間隔に適合する可能性があり、この柔軟性をスキップすると、貪欲な順序付けが妨げられます。 

## アプローチ

 ブルートフォースアプローチでは、各人を有効な間隔に割り当て、人の順序も選択しようとします。 N 人がいるため、順列の数だけでも N 階乗となり、N = 20 の場合でもすでに実行不可能です。順序を無視してサブセットの代入のみを試みたとしても、連続時間パッキングに依存する間隔容量との互換性を考慮する必要があります。 そのため、単純なアプローチは、インターバル スキャンと組み合わせた指数関数的な割り当ての探索のようなものに押し込まれますが、これでは非常に遅すぎます。 

重要な観察は、N が非常に小さいため、人々のサブセットの観点から考える必要があるということです。 順番を直接決めるのではなく、時間 T までにどのグループが完了できるかを判断し、その答えを二分探索で求めます。 

そこで問題を再定式化します。時間 T が与えられた場合、遅くとも T までに終了するように全員のスケジュールを設定できるでしょうか? この実現可能性チェックに答えることができれば、最小 T を二分探索することができます。 

ここで、問題はサブセットにわたる制約充足問題になります。 固定 T の場合、各間隔は使用可能な時間ウィンドウに寄与しますが、その一部だけが T より前に存在する可能性があります。各間隔について、タイプごとにどれだけの使用可能な時間が存在するかを知る必要があります。 次に、各人は、合計容量を考慮して、重複することなく互換性のあるタイプの間隔に割り当てられる必要があります。

これは、状態がどの人がすでにスケジュールされているか、およびインターバル容量をどのように消費しているかを表す、古典的なサブセット DP / ナップサックスタイルの割り当て問題に変わります。 

N は最大 20 であるため、ビットマスクを使用して人々のサブセットを表すことができます。 固定 T の場合、タイプごとに利用可能な「スロット」（T にクリップされた間隔）のリストを計算します。 次に、DP over サブセットを使用してこれらのスロットに人を割り当てようとします。そこでは、互換性のある容量のチャンクに人を貪欲に詰め込みます。 

重要な単純化は、各間隔が独立しており、タイプ内では使用可能な時間チャンクの合計のみを考慮することです。 タイプ内の順序は実現可能性にとって重要ではないため、各間隔をキャパシティのビンとして扱い、期間が一致するタイプのビンに収まる人々を割り当てます。 

したがって、実現可能性は、タイプごとにグループ化された箱にすべての人々を詰め込むことができるかどうかをチェックすることに帰着します。ここで、箱は最大 T までの間隔の長さです。 

次に、パッキングが可能な最小 T を二分探索します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース順列と間隔シミュレーション | O(N!・M) | お(お) | 遅すぎる |
 | 二分探索 + タイプごとのサブセット DP パッキング | O(log S · 2^N · M または最適化されたグループ化) | O(2^N) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. まず、すべての間隔を水の種類ごとに分け、開始時間ごとに並べ替えます。 それらを使用して、候補時間 T までの各タイプにどれだけの使用可能な期間が存在するかを計算します。 
2. 関数を定義する`can(T)`これは、全員が時間 T までに終了できるかどうかをチェックします。この関数内で、すべての間隔を T にクリップし、各タイプが寄与する使用可能な期間を計算します。 間隔が T を超える場合は、T より前の部分のみがカウントされます。 
3. タイプごとに、容量チャンクのリストが表示されます。 正確な位置は考慮せず、チャンクごとの利用可能な合計容量のみを考慮します。 
4. 人材をタイプごとに割り当てることを検討します。 私たちは各人に必要なタイプと期間を知っています。 必要なタイプごとに人々をグループ化します。 
5. 固定タイプの場合、すべての従業員を利用可能な容量のチャンクに割り当てようとします。 これは古典的なパッキング問題となり、期間の合計を指定された容量のビンに分割できるかどうかを判断する必要があります。 N が小さいため、そのタイプの人々のサブセットに対してビットマスク DP を使用し、サブセットを利用可能なビンに詰め込むことができるかどうかを追跡します。 
6. DP トランジションは、容量が残っている場合は現在のビンに人を配置しようとし、必要に応じて次のビンに移動しようとします。 すべての人が詰め込まれるか、トランジションが残らなくなるまで、サブセットを探索します。 
7. すべてのタイプのグループを正常にパックできれば、`can(T)`trueを返します。 
8. 次を使用して、十分に広い範囲にわたって T を二分探索します。`can(T)`検索をガイドし、実行可能な最小値を返します。 

正確さは、間隔が独立したリソースであり、各タイプ内で合計容量とセグメント化された容量のみを考慮するという事実に基づいています。 N が小さいため、サブセット DP はスケジュールを明示的に構築する必要がなく、可能なすべての割り当てを正確に取得します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(T, people, intervals):
    # group intervals by type
    by_type = {-1: [], 0: [], 1: []}
    for s, d, t in intervals:
        if s >= T:
            continue
        end = min(T, s + d)
        if end > s:
            by_type[t].append(end - s)

    # sort capacities per type (greedy packing works better)
    for t in by_type:
        by_type[t].sort(reverse=True)

    # group people by type
    people_by_type = {-1: [], 0: [], 1: []}
    for x, y in people:
        people_by_type[x].append(y)

    # check each type independently
    for t in [-1, 0, 1]:
        req = people_by_type[t]
        if not req:
            continue

        caps = by_type[t]
        if sum(req) > sum(caps):
            return False

        # DP over subset packing into bins
        n = len(req)
        dp = {0: 0}  # mask -> current bin used
        for mask in range(1 << n):
            if mask not in dp:
                continue
            used = dp[mask]
            for i in range(n):
                if mask & (1 << i):
                    continue
                dur = req[i]
                # try same bin
                if used + dur <= caps[-1]:
                    nm = mask | (1 << i)
                    dp[nm] = max(dp.get(nm, 0), used + dur)
                # try next bin
                else:
                    for c in caps:
                        if dur <= c:
                            nm = mask | (1 << i)
                            dp[nm] = max(dp.get(nm, 0), dur)
                            break

        if (1 << n) - 1 not in dp:
            return False

    return True

def solve():
    N, M = map(int, input().split())
    people = [tuple(map(int, input().split())) for _ in range(N)]
    intervals = [tuple(map(int, input().split())) for _ in range(M)]

    lo, hi = 0, 10**18
    ans = hi

    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid, people, intervals):
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1

    print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、実現可能性を二分探索にラップすることから始まります。 の`can(T)`関数は、すべてのシャワー間隔を水の種類ごとに時間 T までの使用可能な容量に圧縮します。 これにより、時間の明示的なシミュレーションが回避され、リソース割り当ての問題が軽減されます。 

各タイプの内部では、人を容量の塊に詰め込むという問題が軽減されます。 ビットマスク上の DP により、順序を固定せずに割り当てのすべてのサブセットを探索できるようになります。順序が異なるとビンの使用パターンも異なるため、これは不可欠です。 

T では実現可能性が単調であるため、二分探索構造により、答えを直接推測することがなくなります。

 ## 特殊なケース

 微妙なエッジ ケースの 1 つは、人がゴミ箱の残りの断片にぴったり収まる場合です。 実装が厳密な不平等のみをチェックする場合、有効な配置が誤って拒否されます。 DP では、これは許可することで処理されます。`used + dur <= capacity`、正確なフィット感が受け入れられることを保証します。 

もう 1 つのケースは、合計容量は十分であるが、ビン間で誤って断片化されている場合です。 たとえば、1 人が 10 ユニット必要で、サイズ 6 と 6 のゴミ箱があります。貪欲な合計チェックは合格しますが、梱包は失敗します。 10 ユニット要件を満たす有効なサブセット割り当てがないため、サブセット DP はこのケースを正しく拒否します。 

3 番目のケースは、複数の間隔のタイプが重複しているものの、時間的には互いに素である場合です。 アルゴリズムはそれらを独立して扱います。これは、それらをマージすると時間の連続性が誤って仮定されるため、これが必要ですが、問題ではそれが保証されていません。
