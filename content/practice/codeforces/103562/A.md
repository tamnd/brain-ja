 ## 解決策
 ## アプローチ

 ブルート フォース アプローチはまさにこの問題が示唆しているものです。連絡先ごとに、電話番号を数字に変換し、それらの合計を計算し、パリティをチェックします。 合計への寄与を知るためにすべての桁を少なくとも 1 回検査する必要があるため、これはすでに最適です。 コストはすべての連絡先の合計桁数 (最大約 9000) に比例するため、これは即座に実行されます。 

より深い組み合わせ構造や前処理のトリックは必要ありません。 唯一の「最適化」は、文字列を整数に変換することを避け、代わりに文字コードから直接合計を累積することです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース ディジット スキャン | O(合計桁数) | O(1) おまけ | 承認済み |
 | 高度な前処理 | O(合計桁数) | お(1) | やりすぎ |

 ## アルゴリズムのチュートリアル

 1. 連絡先の数を読み取り、各行を 1 つずつ処理します。 ストリーミングの性質により、不要なデータの保存が回避されます。 
2. 各行を名前と電話番号の文字列に分割します。 分割は行ごとに 1 回行われるため、解析は線形のままです。 
3. 電話番号の各文字を数値に変換し、合計を累積します。 このステップが必要なのは、決定が部分構造ではなく全桁合計のパリティに依存するためです。 
4. 合計を計算した後、それが偶数であるかどうかを確認します。 偶数の場合は、関連付けられた名前をすぐに出力します。 それ以外の場合は破棄します。 
5. すべてのコンタクトが処理されるまで続行します。出力は同じ走査順序で生成されるため、入力順序は自動的に維持されます。 

### なぜ効果があるのか

 このアルゴリズムは、i 番目の連絡先を処理した後、その電話番号の正確な桁数の合計が正しく計算されたという不変式に依存しています。 各桁は独立して合計に寄与し、パリティは合計のモジュロ 2 のみに依存するため、桁をスキップしたり近似したりすることはできません。 したがって、「名前を印刷するかどうか」の決定は各連絡先に対して局所的に正しく、他のエントリには依存しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    for _ in range(n):
        line = input().strip().split()
        name = line[0]
        number = line[1]

        s = 0
        for ch in number:
            s += ord(ch) - ord('0')

        if s % 2 == 0:
            print(name)

if __name__ == "__main__":
    solve()
```このソリューションは入力を単一パスで処理します。 各行は正確に 2 つのトークンに分割されるため、名前が英数字であっても解析に曖昧さはありません。 

桁の合計は直接文字算術を使用して計算されます。これにより、整数変換のオーバーヘッドが回避され、先頭のゼロの正確さが維持されます。 パリティ チェックがすぐに実行され、出力がストリーミングされるため、メモリ使用量が一定に保たれます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、次のような電話番号がゼロのみで構成されている場合です。```
1
Zero 000000
```アルゴリズムは 0 の合計を計算します。これは偶数であるため、名前が出力されます。 ここでの間違いは、最初に文字列を整数に変換することです。これでも数値的には機能しますが、不要な解析が複雑になり、他のバリアントでオーバーフローが発生する可能性があります。 

もう 1 つの特殊なケースは、次のような 1 桁の数字です。```
1
Odd 7
```合計は 7 で奇数であるため、何も出力されません。 アルゴリズムは最小長を想定していないため、これを正しく処理します。 

最後に、先行ゼロが混在していることを考慮します。```
1
Lead 00012
```合計は 1+2 = 3 で奇数なので除外されます。 先頭のゼロは何も寄与しませんが、それでも反復する必要があります。 それらをスキップすると正確さが変わります。
