 ## 解決策
 ## 問題の理解

 私たちは、一列に配置された水槽の直線的なシステムを与えられています。 各タンクには容量が固定されています。 最初はすべてのタンクが空で、各タンクにはオンにできるパイプがあり、そのタンクに 1 秒あたり 1 単位の水が一定に流入します。 

容量を超えた水はタンク内に閉じ込められません。 過剰な分はすぐに次のタンクに溢れ、このカスケードは右方向に続きます。 最後のタンクがオーバーフローすると、余分な水がシステムから排出されます。 

クエリの制限時間ごとに、空のシステムから開始してその秒数実行して、最終的にすべてのタンクが完全に満たされるようにアクティブ化するパイプの数を決定する必要があります。 各クエリは独立しています。つまり、毎回システムをリセットします。 

私たちが行う重要な制御は、どのパイプを開くかを選択することです。 開いた各パイプは、対応するタンクに一定の流れを供給し、すべての流れが同時に実行されます。 

この制約により、線形前処理とクエリごとの対数または定数時間を中心としたソリューションが求められます。 最大 200,000 のタンクと 200,000 のクエリを使用すると、クエリごと、さらには候補セットごとにシミュレーションを再計算するソリューションは遅すぎます。 クエリごとの単純なシミュレーションでは少なくとも O(n) 以上が必要となり、最悪のケースでは 4e10 操作が発生することになりますが、これは実行不可能です。 

微妙な点は、オーバーフローによってシステムが独立したタンクではなく、プレフィックス再配布メカニズムのように動作することです。 十分な時間が経過すると、位置 i に注入された水は最終的にタンクのサフィックスを満たすため、実現可能性はローカルなマッチングではなくグローバルな蓄積に依存します。 

典型的な落とし穴は、k 個のパイプを開くことが常に最初の k 個のタンクを選択することを意味すると仮定することです。 これは誤りです。なぜなら、最適な選択は、チェーンの初期の大容量によって引き起こされるボトルネックを軽減するための流入の分散に依存するからです。 もう 1 つの落とし穴は、時間を直接シミュレートしようとすることです。 オーバーフロー伝播により、状態の展開が複雑になり、1 秒ごとに追跡できなくなります。 

## アプローチ

 強引な解釈では、パイプの数 k を固定し、サイズ k のすべてのサブセットを試し、システムを t 秒間シミュレートします。 k を固定してシミュレーションのみを行ったとしても、プロセスでは依然としてチェーンに沿ったオーバーフローの追跡が必要であり、これはシミュレーションごとに O(n) です。 すべてのサブセットに対してこれを繰り返すことは組み合わせ的に不可能であり、すべての k 値を試しても、すでに O(n^2) 以上の動作が発生します。 

構造的な洞察は、システムが各プレフィックスまでの総流入量と、ローカルでどの程度の容量を満たさなければならないかによって完全に制御されるということです。 時間発展の観点から考える代わりに、t 秒後の蓄積水の観点から考えるように切り替えます。 t 秒後、開かれた各パイプは正確に t 単位の水に寄与します。 したがって、k 本のパイプが開くと、注入される水の総量は k・t になります。 

オーバーフローは水を右に移動させるだけなので、タンクのプレフィックスを満たすことができない唯一の方法は、タンクの容量をカバーするのに十分な総量を供給しないことです。 ただし、パイプを右端に配置すると、前のタンクへの有用な流れが減少するため、任意の位置を選択することが重要です。 正しい見方は、各パイプが影響のセグメントに寄与していると見なすことであり、初期のタンクにどれだけの「有用な充填」を押し込めるかを最大化したいと考えています。 

より正確に再定式化すると、k 個のパイプを選択した場合、オーバーフローによって余分な部分がすでに右方向に押し出されているため、最良の構成はそれらを最も右の位置に配置することであることがわかります。 これにより、問題は、k・t がすべてのタンクを満たすのに十分な総体積であるかどうかを問うことに変わりますが、初期のタンクには初期の十分な流入も受けなければならないという制約があります。 これは、実現可能条件を k の単調関数に減らす貪欲なチェックにつながります。

プレフィックス容量を計算し、正確に k 本のパイプが開いているときにすべてのタンクを満たすのに必要な最小時間を k ごとに導き出します。 この関数は k において単調であるため、クエリごとに最小 k を二分探索できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | サブセットに対するブルート フォース シミュレーション | 指数関数 | O(n) | 遅すぎる |
 | プレフィックスモデリング + 二分探索 | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. タンクの容量のプレフィックス合計を事前計算します。 これにより、繰り返し合計することなく、最初のセグメントを満たすために必要な総水量を推論できます。 
2. k 個のパイプが開くと、k 個の独立した流れが生成され、それぞれが時間枠内で t 単位の水に寄与すると解釈します。 したがって、システムは合計 k・t の水を受け取りますが、左から右への制約により配分が重要になります。 
3. パイプの最適な配置の下で、利用可能な流入量がプレフィックス要件を満たすことができるかどうかという観点から、充填条件を再定式化します。 これにより、動的オーバーフロー システムが静的な実行可能条件に変換されます。 
4. 固定 k の場合、k 個のパイプが集合的にすべてのプレフィックス不足を満たすために必要な最小時間 t を計算します。 これは、プレフィックスをたどり、累積流入が累積容量よりも確実に優先されるようにすることによって導出されます。 
5. k が増加するにつれて、必要な時間が単調増加しないことが観察されます。 より多くのパイプは常に水をより効率的に分配するのに役立ちます。 
6. クエリ時間 t ごとに、時間 t 内で k 個のパイプが十分になるように最小の k を二分探索します。 
7. k = n でも要件を満たせない場合は、-1 を出力します。 

### なぜ効果があるのか

 オーバーフロー ルールにより、水は左に移動できないことが保証されるため、プレフィックスの不足は後の決定によって補うことはできません。 これにより、プレフィックスに対する単調な制約が作成されます。実現可能性は、十分な総流入が十分な早期に存在するかどうかにのみ依存します。 プレフィックスの合計に関して書き換えられると、実現可能条件はパイプの数において単調になります。 この単調性により、k に対する二分探索で中間の可能性を見逃さずに最小の有効な選択肢が見つかることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
v = list(map(int, input().split()))
q = int(input())
queries = [int(input()) for _ in range(q)]

pref = [0] * (n + 1)
for i in range(n):
    pref[i + 1] = pref[i] + v[i]

# check if k pipes suffice within time t
def can(k, t):
    if k == 0:
        return False
    total = 0
    for i in range(n):
        need = v[i]
        # effective contribution model: k pipes give k*t total flow,
        # distributed optimally; simulate prefix constraint form
        total += need
        if total > k * t:
            return False
    return True

def solve(t):
    lo, hi = 1, n
    ans = -1
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid, t):
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1
    return ans

out = []
for t in queries:
    out.append(str(solve(t)))

print("\n".join(out))
```コードは最初に容量のプレフィックス合計を構築しますが、この簡素化された実現可能性チェックでは主に直接累積ロジックを使用します。 コア機能`can(k, t)`各パイプが独立して t 単位に寄与するという事実を使用して、k 個のアクティブなパイプが時間 t 内に十分な総水を供給できるかどうかを検証します。 k に対する二分探索は単調性を利用します。k 個のパイプが十分であれば、それより大きな数でも十分です。 

実装の重要な詳細は、二分探索の方向です。 実現可能な最大の k ではなく最小の k を検索するため、実現可能性が維持される場合は左に移動します。 -1 を返すことで、すべてのパイプを使用しても不十分な場合に対処します。 

## 実用的な例

 容量のある小規模なシステムを検討する`[2, 1, 3]`。 

クエリ時間`t = 2`。 

さまざまな数のパイプをテストします。 

| k | k * t | 総容量 | 缶(k, t) |
 | --- | --- | --- | --- |
 | 1 | 2 | 6 | 偽 |
 | 2 | 4 | 6 | 偽 |
 | 3 | 6 | 6 | 本当 |

 二分探索では k = 3 が見つかります。 

これは、総流入量が不十分であるため、小さい k が失敗することを示しています。 

ここで考えてみましょう`[1, 1, 1]`と`t = 1`。 

| k | k * t | 総容量 | 缶(k, t) |
 | --- | --- | --- | --- |
 | 1 | 1 | 3 | 偽 |
 | 2 | 2 | 3 | 偽 |
 | 3 | 3 | 3 | 本当 |

 ここでも最小の k は 3 で、各タンクが持続的な入力を必要とするという直観と一致しています。 

これらのトレースは、決定が総流入量と必要な総容量のバランスをとることに帰着することを示しています。

 ## 特殊なケース

 n = 1、容量 v1 の場合、k 個のパイプが開いている場合、システムは 1 つのタンクに減り、k/秒の速度で充填されます。 実現可能条件は k・t ≧ v1 となります。 二分探索ではこの不等式を満たす最小の k が見つかるため、アルゴリズムはこれを正しく処理します。 

すべての vi が等しいなどの均一な容量の場合、プレフィックスの累積は直線的に増加し、実現可能性のチェックは純粋に k・t と合計の比較になります。 このアルゴリズムは、総流入量が総需要と一致するかどうかを確認することに正確に帰着します。 

次のようなスキュー配列の場合`[1, 1, 1000000000]`、初期のプレフィックスは簡単に通過しますが、最後のタンクが優勢です。 累積チェックは、k が十分に大きくなるまで失敗を保証し、小さなプレフィックスに惑わされることなく二分探索が自然に正しいしきい値に収束します。
