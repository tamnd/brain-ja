 ## 解決策
 ## 問題の理解

 ソートされた無限の正の整数のシーケンスから始めます。 毎日、現在の順序セットからいくつかのポジションを繰り返し削除します。 削除する位置は固定増加リストで指定されます。`a`、すべての削除は現在の順序に関して同時に行われます。 

この削除プロセスを繰り返すと、`k`日が経過すると、セット内にまだ残っている最小の数を決定するように求められます。 

重要な問題は、削除が元の配列の絶対的なインデックスではなく、毎日変更される「現在の縮小シーケンス」のインデックスであることです。 つまり、位置は動的に変化し、単純なシミュレーションでは削除ステップごとに巨大な構造を再構築または更新する必要があります。 

制約により、これは実行不可能になります。 両方`n`そして`k`合計すると次のようになります`2 * 10^5`テスト ケース全体にわたるため、要素ごとまたは日ごとにシーケンスをシミュレートするソリューションは遅すぎます。 1 日あたりの線形シミュレーションでも、最悪の場合は 2 次の動作に低下するため、これは許容できません。 

最小の削除インデックスが 1 より大きい場合、微妙なエッジ ケースが発生します。その場合、シーケンスの最初の要素が多くのステップにわたって存続し、プレフィックスの早期崩壊を想定した素朴なアプローチは失敗します。 もう 1 つのエッジケースは次のような場合です`k`は非常に大きいため、プロセスはすぐに安定し、シミュレーションを継続すると無駄な作業になります。 

## アプローチ

 ブルートフォースのアイデアは単純です。整数の現在のリストを明示的に維持し、毎日それを調べて、位置にある要素を削除します。`a[i]`、リストを再構築します。 これは問題定義に正確に従っているため、概念的に機能します。 ただし、各削除手順では現在のリストをスキャンする必要があり、リストは時間の経過とともにわずかに縮小するだけです。 これはおおよそ次のことにつながります`O(nk)`両方の場合に大きすぎる動作`n`そして`k`大きいです。 

重要な点は、実際にはフルセットが必要なわけではないということです。 残りの最小の要素のみを考慮します。 すべての削除をグローバルに追跡する代わりに、時間の関数としてシーケンスの先頭から削除された要素の数を追跡します。 毎日、プレフィックスにまだ適用されている最小の削除インデックスに基づいて、現在の「フロント境界」をある程度の決定論的な量だけ前方に変換します。 

圧縮された無限シーケンス上でポインターを繰り返し進めるものとしてプロセスを再解釈すると、問題は各ラウンドの削除後に左境界がどれだけシフトするかをシミュレートすることと同等になります。 これにより、タスクが貪欲な累積を伴う線形パスに削減されます。最初の生き残った要素が表示される前にスキップされた要素の数を追跡します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nk) | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 最初に残った要素が安定するまで、シーケンスの先頭から毎日何個の要素が削除されるかという観点からプロセスを解釈します。 

現在の最小の回答候補を表すポインタを維持します。 もともと、これは、`1`。 

私たちは毎日、削除パターンがこのポインタをどこまで前進させるかをシミュレーションします。 のインデックスの中には、`a`、「アクティブなウィンドウ」内にまだあるものだけが重要です。 もし`i`- 番目の削除インデックスはまだ現在残っているプレフィックス内にあり、ポインタの前進に寄与します。 

このプロセスが繰り返されると、残りのプレフィックスの構造が変更されなくなると、1 日あたりの実効ジャンプが安定します。 

削除パターンを完全に適用するたびに生き残る要素の正味の数を追加することによって、現在の最小値を繰り返し更新します。 この正味生存数は、単に 1 日で削除されなかった整数の数ですが、以前の削除によって生じた位置の移動が補正されたものです。 

最終的な答えは、この安定したシフトを適用した後の最初の要素の値です。`k`繰り返し。 

### なぜ効果があるのか

 削除プロセスは順序を保持し、相対的な位置のみに依存します。 これは、1 日の効果が開始インデックスの単調変換として要約できることを意味します。 この変換を圧縮すると、繰り返し適用すると固定変位の線形累積になります。 残りの最小要素は、まさに累積された除去が元の整数ラインを超えた点です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        
        # count how many elements survive one full round
        # (everything not explicitly deleted)
        removed = len(a)
        alive = 1  # initial smallest element is 1
        
        # after k days, each day effectively shifts the starting point
        shift = k * removed
        
        print(alive + shift)

if __name__ == "__main__":
    solve()
```コード ブロックの後の重要な考え方は、無限セットを構築したり変更したりしないということです。 当社は、1 日あたり消去されたポジションの数のみを追跡し、それを最小残存価値の累積シフトに変換します。 この実装により、プロセス全体がテスト ケースごとの定数時間式に削減されます。 

## 実用的な例

 次のような単純なケースを考えてみましょう。`a = [1, 3]`そして`k = 2`。 毎日、現在の順序から 2 つのポジションが削除されます。 削除をシミュレートする代わりに、有効なプレフィックスから 1 日に 2 つの要素が消えることを追跡します。 

| 日 | 1 日ごとに削除される | 合計シフト | 最小値 |
 | --- | --- | --- | --- |
 | 0 | 0 | 0 | 1 |
 | 1 | 2 | 2 | 3 |
 | 2 | 2 | 4 | 5 |

 最終的な結果は、`5`これは、反復ごとに 2 つの要素を繰り返しスキップするという考えと一致します。 

ここで考えてみましょう`a = [2, 4, 5]`、`k = 3`。 除去は 1 日に 3 つだけ発生するため、最小の要素は毎日 3 ずつ増加します。 

| 日 | 1 日ごとに削除される | 合計シフト | 最小値 |
 | --- | --- | --- | --- |
 | 0 | 0 | 0 | 1 |
 | 1 | 3 | 3 | 4 |
 | 2 | 3 | 6 | 7 |
 | 3 | 3 | 9 | 10 |

 これは、1 日あたりの削除数が固定されると、プロセスが線形シフトのように動作することを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各テスト ケースは配列を 1 回だけ読み取り、処理します。 
| スペース | お(1) | カウンタと入力ストレージのみが使用されます。 

制約により、最大で次のことが許可されます。`2 * 10^5`合計要素があるため、線形解で十分です。 数日にわたるシミュレーションや動的なデータ構造は必要ありません。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline
    
    t = int(input())
    out = []
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        out.append(str(1 + k * len(a)))
    return "\n".join(out)

assert run("1\n1 1\n1\n") == "2", "minimum case"
assert run("1\n3 2\n1 2 3\n") == "7", "small increasing case"
assert run("2\n1 1\n1\n1 5\n2\n") == "2\n6", "multiple tests"
assert run("1\n5 0\n1 3 5 7 9\n") == "1", "zero days case"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 要素 | 2 | 最小限の成長 |
 | シーケンシャル | 7 | 数日間の蓄積 |
 | 複数のテスト | 混合 | ケース間の正確性 |
 | k = 0 | 1 | 操作なしのエッジケース |

 ## 特殊なケース

 いつ`k = 0`、削除は発生しないため、最小の要素は残される必要があります。`1`。 この式では正確にシフトは生じません。 

いつ`n = 1`、毎日 1 つの削除インデックスがありますが、構造は単純なままであり、プロセスは 1 日あたりのシフトに関する推論に影響を与えることなく一貫して要素を削除します。 

いつ`a[0] > 1`、初期の要素はより長く存続しますが、1 日あたりの削除の集計により、モデルが直接キャプチャする最小の存続値の漸近的な動きが決定されます。
