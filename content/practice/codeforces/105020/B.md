 ## 解決策
 ## 問題の理解

 私たちは、すでにお店に並んでいる顧客の列を 1 つ与えられます。 列に並んでいる各顧客の対応には既知の時間がかかり、店舗はそれらの顧客を順番に厳密に処理します。 キューのプレフィックスをクリアするための合計時間は、これらのサービス時間の合計にすぎません。 

Hendy には、クエリごとに食べ物を取得する 2 つの方法があります。 

最初のオプションは、実際にお店に行くことです。 彼は移動時間を費やします$x$数分後、彼は現在のキューの最後尾に加わります。 すでに行列ができているので、$n$彼の前に顧客がいる場合、彼はすべての顧客が終わった後でのみサービスを開始します。 彼自身のサービス時間は事実上無関係です。なぜなら、私たちは彼が食べ物を受け取ったときだけを尋ねられ、重要な瞬間は彼の前で列が空になったときです。 したがって、このオプションの完了時間は、彼の到着時間に、すべての既存の顧客を処理するのに必要な合計時間を加えたものになります。 

2 番目のオプションは配送です。 このモードでは、店はまさに最初のものを提供します$m$顧客を列に並べ、すぐに支払います$y$ヘンディの注文を届けるのに数分。 したがって、彼の待ち時間は、最初の処理にどれだけ時間がかかるかによってのみ決まります。$m$顧客に加えて配送の遅延も発生します。 

各クエリは、これら 2 つの戦略の最小値を独立して要求します。 

制約からすると、どちらも$n$そして$q$まで可能です$10^5$。 すべてのクエリのキューの合計を再計算するソリューションでは、最大で$10^5$長さの合計$10^5$、につながる$10^{10}$これは許容範囲をはるかに超えています。 これは、各クエリを一定時間にするためにプレフィックスの合計が必要であることを直ちに示唆しています。 

微妙なエッジケースは、「ショップに行く」オプションを正しく解釈することで発生します。 誰かがヘンディが列に割り込むことができる、または到着したらすぐにサービスを受けることができると誤って想定している場合、その人は時間を過小評価することになります。 正しいモデルは厳密な FIFO です。彼は最後に参加し、現在のすべての顧客を待ちます。 

別のエッジケースが処理されています$m = n$、配信はキュー全体を待機するため、両方の戦略がほぼ同等になります。 また、いつ$x$または$y$が非常に大きいため、プレフィックスの合計によっては比較が大きく反転する可能性があります。 

## アプローチ

 ブルート フォース ソリューションでは、各クエリを個別にシミュレートします。 配送オプションの場合、最初の金額を合計します。$m$毎回のサービスタイム。 ショップオプションの場合は、すべてを合計します$n$サービス時間と追加$x$。 これは、プロセスを直接ミラーリングするため論理的に機能しますが、各クエリで最大$10^5$要素、最大で生成$10^{10}$トータルオペレーション。 

重要な観察は、キューがクエリ間で決して変化しないことです。 サービス時間のプレフィックス構造により、累積合計を 1 回だけ事前計算できます。 その後、必要な量、合計キュー時間とプレフィックスの合計の両方が O(1) ルックアップになります。 これにより、各クエリが 2 つの事前計算された値の間の定数時間の比較に縮小されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | プレフィックス合計 | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. サービス時間の配列を読み取り、各位置がそのインデックスまでのすべての顧客にサービスを提供するのに必要な合計時間を格納するプレフィックス合計配列を計算します。 これにより、すべてのプレフィックス合計がその時点までのキューの完全な履歴をエンコードするため、後で一定時間の範囲合計クエリが可能になります。 
2. キュー全体の合計サービス時間を最後のプレフィックス合計値として計算します。 これは、Hendy がキューの最後に参加した場合に必要な時間を表します。 
3. 各クエリについて、次の内容を読み取ります。$x$、$y$、 そして$m$。 これらは、店舗までの移動時間、配達の遅延、配達が始まるまでに何人の顧客にサービスを提供するかを定義します。 
4. ショップオプションの時間を次のように計算します。$x + \text{total queue time}$。 これは、旅行後の到着と、その後の現在の顧客全員の待機を反映しています。 
5. 配送オプションの時間を次のように計算します。$\text{prefix}[m] + y$。 これは最初の待機を反映しています。$m$顧客とその後の配達遅延。 
6. これら 2 つの値の最小値を出力します。 

### なぜ効果があるのか

 このアルゴリズムは、キューの処理順序が固定され、クエリから独立しているという不変条件に依存します。 サービス時間は加算的であり、システムは厳密に順次であるため、キュー内の任意のポイントに到達する時間はプレフィックスの合計のみに依存します。 すべてのクエリは、この固定タイムラインの互いに素なセグメントから導出された 2 つの独立した線形式を比較することに帰着し、クエリ間の相互作用が事前計算を無効にする可能性がないことを保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]
    
    total = pref[n]
    
    q = int(input())
    out = []
    
    for _ in range(q):
        x, y, m = map(int, input().split())
        
        go_shop = x + total
        delivery = pref[m] + y
        
        out.append(str(min(go_shop, delivery)))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```プレフィックス合計配列は一度構築されるため、反復せずにセグメント合計を取得できます。 変数`total`キューの完全な処理時間を取得し、すべてのクエリで再利用します。 

各クエリは算術アクセスと配列アクセスのみを実行し、定時間動作を保証します。 

よくある実装上の間違いは、この定式化ではプレフィックス配列が 1 から始まるインデックスであることを忘れていることです。`pref[i]`最初の合計を表します`i`要素。 これにより、クエリ時のオフバイワンの混乱が回避されます。`pref[m]`。

 ## 特殊なケース

 重要なケースの 1 つが次のような場合です。$m = 1$、配送は最初の顧客のみに依存します。 プレフィックスの合計は 1 つの要素に減少し、インデックス付けにおける off-by-one エラーはすぐに表面化します。 アルゴリズムは、1 からなるインデックスのプレフィックス配列を使用してこれを処理します。`pref[1]`は常に有効です。 

もう一つのケースは次のような場合です。$n = 1$。 ここでは両方の戦略がほぼ対称になり、「キューに参加」と「即時提供」の解釈を誤ると、誤った結果が生じます。 計算された合計には、単一のサービス時間が正しく含まれています。 

いつ$x$非常に大きく、$y$が小さい場合、キューのサイズに関係なく配信が優先されるはずです。 両方の式が線形で独立したままであるため、式はこれを自然に反映しており、特別なケースを使用せずに正しい比較が保証されます。
