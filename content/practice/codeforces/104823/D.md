 ## 問題の理解

 私たちは「ダーク オーブ」を中心とした Slay the Spire スタイル システムの簡略化されたバージョンをシミュレートしています。 このシステムは、一連のオーブ、グローバルな「フォーカス」値、ターン終了時の効果のタイムラインを維持する長い一連の操作を通じて進化します。 

各ダークオーブには数値カウンターがあります。 このカウンターが作成されると、このカウンターは 6 から始まります。その後、ターンが終了するたびに、既存のすべてのダーク オーブが現在のフォーカスに応じた値だけカウンターを同時に増加させます。 その後、オーブが明示的にトリガーされると、オーブは削除され、現在のカウンターに等しいダメージを与えます。 

グローバルフォーカスは、即時フォーカスを追加するカード、または次のターンの開始時にトリガーされる遅延ペナルティと一緒にフォーカスを追加するカードにより、時間の経過とともに変化します。 このシステムは、オーブの容量の増加と、右端のオーブを削除し、そのダメージを記録し、すぐにそのオーブの新しいコピーを作成する特別な「再帰」アクションもサポートしています。 

最終的な答えは、すべてのオーブ トリガーによって与えられる合計ダメージです。これには、フル スロットによる自然な召喚と明示的な再帰アクションの両方が含まれます。 

主な難点は、シミュレーションが最大 100 万回の操作で実行されることですが、単純なシミュレーションではすべてのオーブが毎ターン更新されるため、非常に遅すぎます。 

重要な点は、オーブ カウンターがオーブごとのインタラクションではなく、作成されてから経過したエンド ターンの数のみに基づいて決定的に進化することです。 これにより、各ターン中にすべてのオーブに触れないようにすることができます。 

単純な実装は、2 つの一般的な状況でも失敗します。 まず、終了ターンごとにすべてのオーブ カウンターを再計算すると、多くのオーブと多くのターンがある場合、約$10^6 \times 10^6$更新は不可能です。 次に、グローバル時間を追跡せずにオーブの状態を完全に再構築して再帰をシミュレートしようとすると、オーブ カウンターとフォーカス履歴の間の一貫性が失われ、不正確なダメージ値が生成されます。 

## アプローチ

 ブルートフォース手法では、すべてのオーブの明示的なリストを維持し、ターン終了ごとにそれらを反復してカウンターを増やします。 また、オーブが呼び出されるたびにダメージを直接計算します。 これはルールを正確に反映しているため、概念的には簡単です。各 Orb はターンごとに更新され、再帰は同じ操作を再利用するだけです。 

問題は、ターンごとの更新数がオーブの数に対して線形になる可能性があり、ターン数が線形になる可能性があることです。 最悪の場合、これは二次関数になります。 

重要な観察は、すべてのオーブがターン終了時のスケーリングに関して同じように動作するということです。 すべてのオーブは各ターンでまったく同じ増分を受け取ります。そのため、各カウンターを段階的に保存して更新する代わりに、特定のターンまでにグローバルに適用された合計増分がどのくらいかを知るだけで済みます。 各 Orb は、いつ作成されたかを記憶するだけでよいため、グローバル増分のプレフィックス合計を使用して現在の値を再構築できます。 

これにより、オーブごとのシミュレーションの問題が、エンドターン寄与のグローバルな時系列の維持に加え、出生時刻を保存するオーブの単純なスタックにまで軽減されます。

 ## アルゴリズムのチュートリアル

 私たちは 3 つの主要なアイデアを維持しています。それは、オーブのスタック、フォーカスのためのグローバル カウンター、およびターン終了時の貢献に対するプレフィックスの合計です。 

1. 各オーブは、完了したターンの観点から作成された時間によってのみ表されます。 これをインデックスとしてプレフィックス合計配列に保存します。 
2. 私たちはグローバルリストを維持しています`S`、 どこ`S[t]`すべての Orb に適用される合計累積増分を格納します。`t`エンドターン。 終了ターンごとに、現在のフォーカスから派生した値が追加されます。 
3. 私たちはオーブのスタックを維持します。 各 Orb は、その作成時のインデックスを次の場所に保存します。`S`。 
4. Orb が作成されると、まず容量を確認します。 スタックがいっぱいの場合は、すぐに右端のオーブを削除し、現在のプレフィックスの合計と保存されている作成値の差に基づく式を使用してダメージを計算します。 
5. オーブの現在のカウンターをいつでも計算するには、すべてのオーブが 6 から始まり、終了ターンごとにまったく同じ合計増分を得るというアイデンティティを使用します。 したがって、現在の値は、作成されてから終了ターンが何回発生したかによって決まります。 
6. 再帰操作により、最後の Orb が削除され、その現在の値が応答に追加され、作成時刻が現在である新しいコピーが再挿入され、将来の拡張が正しく継続されることが保証されます。 
7. 各ターン終了操作では、グローバル タイム インデックスが増加し、現在のフォーカスを使用してオーブごとの増分が計算され、それがプレフィックス合計に追加され、保留中の遅延フォーカス削減が適用されます。 

正しさは、オーブの進化が経過したエンドターンと現在のフォーカスのみに依存し、他のオーブの正体や位置には依存しないという事実にかかっています。 

### なぜ効果があるのか

 どの時点でも、すべてのオーブは作成時からまったく同じ一連の終了ターン増加を経ています。 これは、Orb の状態の違いが、プレフィックス合計配列内の作成タイムスタンプの違いによって完全に捕捉されることを意味します。 受動的成長において Orb 固有の非対称性を導入する操作は存在しないため、すべての Orb 値を正確に再構築するには、増分をグローバルに累積するだけで十分です。

import sys
input = sys.stdin.readline

MOD = 10**9 + 7

def solve():
    q = int(input())

    orbs = []
    S = [0]

    focus = 0
    pending_debuff = 0
    turns = 0
    cap = 3
    ans = 0

    def value(ct):
        return 6 + (S[turns] - S[ct])

    for _ in range(q):
        parts = input().split()
        op = int(parts[0])

        if op == 1:
            if len(orbs) == cap:
                ct = orbs.pop()
                ans = (ans + value(ct)) % MOD
            orbs.append(turns)

        elif op == 2:
            cap += int(parts[1])

        elif op == 3:
            focus += int(parts[1])

        elif op == 4:
            A = int(parts[1])
            B = int(parts[2])
            focus += A
            pending_debuff += B

        elif op == 5:
            if orbs:
                ct = orbs.pop()
                ans = (ans + value(ct)) % MOD
                orbs.append(turns)

        else:
            turns += 1
            gain = 6 + focus
            if gain < 0:
                gain = 0
            S.append(S[-1] + gain)
            focus -= pending_debuff
            pending_debuff = 0

    print(ans % MOD)

if __name__ == "__main__":
    solve()
```実装では、オーブの状態を時間の発展から分離します。 各 Orb はその作成タイムスタンプのみを保存します`turns`。 プレフィックス配列`S`すべてのエンドターン更新を圧縮します。 再帰は、現在の時間インデックスを使用して Pop-then-Push によって処理され、再作成された Orb が今後も同様に動作することが保証されます。 

順序には注意が必要です。デバフは次のターンの開始時にトリガーされるため、ターン終了時の更新は遅延デバフを適用する前に行う必要があります。 また、容量の削除は、新しい Orb を挿入する直前に行われます。

 ## 特殊なケース

 重要なエッジ ケースは、エンド ターンを行わずに単一のオーブで再帰を繰り返すことです。 この状況では、グローバル増分が適用されていないため、オーブの値は 6 で一定の​​ままです。 作成時間と現在の時間インデックスが両方とも同一であり、プレフィックスの差がゼロになるため、アルゴリズムはこれを正しく処理します。 

もう 1 つのケースは、焦点が十分にマイナスになった場合です。`6 + focus`マイナスになる。 実装ではこれをゼロにクランプし、Orb カウンターの減少が発生しないようにします。 この値はターン終了時にのみ計算されるため、プレフィックスの合計は一貫したままであり、オーブの再構成が中断されることはありません。 

最後の微妙なケースは、作成と削除を交互に行い、その間にゼロエンド ターンを入れることです。 スタックベースの構造により、エビクションでは常に正しい最新の作成時間が使用され、プレフィックスの違いは有効なままになります。`turns`非終了ターン操作中は前進しません。
