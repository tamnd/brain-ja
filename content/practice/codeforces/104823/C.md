 ## 解決策
 ## 問題の理解

 「ワープ」を表す 32 個の整数の固定サイズの配列が与えられます。 各操作は、この配列に対する制限されたインプレース変換を記述します。 この制限はビットマスクによるもので、バイナリ表現にマスクに設定されたすべてのビットが含まれるインデックスのみが操作に参加できます。 具体的にはインデックス`p`すべてのビットが設定されている場合にアクティブになります`mask`にも設定されています`p`、これは条件と同等です`(p & mask) == mask`。 

次に、各操作は、アクティブなインデックスのみに対して 3 つの構造化された「並列コピーと追加」動作の 1 つを実行します。 上位バージョンでは、各アクティブ ポジション`p`からの値を追加します`p - delta`そのソースインデックスもアクティブである場合。 下位バージョンでは、から追加します`p + delta`。 xorバージョンでは、から追加します`p ^ delta`。 すべての更新は同時に行われます。つまり、すべての追加は操作前の元の配列状態から読み取ります。 

すべての操作を適用した後、最終的な配列は出力しません。 代わりに、32 個の要素すべてのビットごとの XOR を計算します。 

状態のサイズという点では、制約は非常に小さいです。 各テスト ケースは 32 個の整数と最大 10 個の演算のみを操作します。 最大 1000 のテスト ケースであっても、各操作を O(32) 時間でシミュレートするソリューションは快適に高速です。 これにより、高度なデータ構造やテスト ケース全体の最適化の必要性が即座に排除されます。 

主な微妙な点は、同時更新です。 反復中に配列をインプレースで更新する単純な実装では、後の更新ですでに変更されたエントリが読み取られるため、値が破損します。 正しい動作には、各操作の前にアレイのスナップショットを取得する必要があります。 

2 番目の微妙な問題は、マスクの状態です。 よくある間違いは、マスクを等しいものとして解釈することです`(p == mask)`サブセットを含める代わりに`(p & mask) == mask`これにより、参加するインデックスが変更され、誤った伝播が発生します。 

## アプローチ

 ブルート フォース シミュレーションは、意図した問題の構造とすでに一致しています。 各操作は 32 のインデックスにわたってローカルに定義され、すべての更新は固定された小さな近傍 (デルタによるシフトまたはデルタによる XOR) のみに依存します。 このため、単一の操作ステップを超えるグローバルな依存関係はありません。 

単純な方法では、まず現在の配列のコピーを構築することで各操作を処理します。 次に、インデックスごとに`p`0から31までマスク条件を満たしているかチェックします。 存在する場合、対応するルールを適用します。`up_add`、私たちは見ます`p - delta`、 のために`down_add`、私たちは見ます`p + delta`、そしてのために`xor_add`、私たちは見ます`p ^ delta`。 ソース インデックスもアクティブな場合は、その値をスナップショットから新しい配列に追加します。 

これが機能するのは、各操作がサイズ 32 の定数ドメインに対する純粋にローカルな変換であるためです。失敗する可能性がある唯一の理由は、スナップショットによって解決されるインプレース更新です。 

除去すべき漸近的なボトルネックはありません。 重要な洞察は、「ワープ」サイズが固定されているため、シミュレーションがすでに最適化されているということです。

 ## アルゴリズムのチュートリアル

 32 要素の配列を維持します`a`。 

テスト ケースごとに、操作を繰り返し適用します。 

1. 現在の配列を一時配列にコピーします`b`。 このスナップショットには元の値が保存されるため、すべての更新が同時に行われます。 
2. 以下を使用してアクティブなインデックスのセットを暗黙的に計算します。`(p & mask) == mask`。 
3. インデックスごとに`p`0 ～ 31 でアクティブかどうかを確認します。 そうでない場合、この操作では完全に無視されます。 
4. 操作タイプに応じて、ターゲット ソース インデックスを計算します。 

1. もし`op == 0`、 セット`q = p - delta`。 
2. もし`op == 1`、 セット`q = p + delta`。 
3. もし`op == 2`、 セット`q = p ^ delta`。 
5. かどうかを確認します。`q`0 ～ 31 の範囲内であるかどうか`q`も同じマスク条件下でアクティブになります。 両方が当てはまる場合は更新します`b[p] += a[q]`。 
6. すべてのインデックスを処理した後、次のように置き換えます。`a`と`b`。 

すべての操作が完了したら、次のすべての要素の XOR を計算します。`a`。 

これが機能する理由は、各操作が古い配列から新しい配列への決定論的な変換を定義し、すべての更新が以前の状態のみに依存するためです。 スナップショットにより、依存関係が 1 つの操作内でカスケードされず、意図した並列セマンティクスが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def apply_op(a, op, mask, delta):
    b = a[:]  # snapshot

    for p in range(32):
        if (p & mask) != mask:
            continue

        if op == 0:
            q = p - delta
        elif op == 1:
            q = p + delta
        else:
            q = p ^ delta

        if 0 <= q < 32 and (q & mask) == mask:
            b[p] += a[q]

    return b

def solve():
    T = int(input())
    out = []

    for _ in range(T):
        n = int(input())
        a = list(map(int, input().split()))

        for _ in range(n):
            op, mask, delta = map(int, input().split())
            a = apply_op(a, op, mask, delta)

        x = 0
        for v in a:
            x ^= v
        out.append(str(x))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```中心となる実装の詳細は、次の使用です。`a[:]`各操作の前に。 これがないと、更新が同じ操作内の後続の計算に漏れ込み、同時性が損なわれてしまいます。 

マスク チェックは 2 回表示されます (宛先インデックスに対して 1 回)。`p`、ソースインデックスに対して 1 回`q`。 参加は操作ごとにグローバルに定義されるのではなく、インデックスごとに定義されるため、両方が必要です。

 ## 特殊なケース

 最初のエッジケースは次の場合に発生します。`mask = 0`。 すべての指標が満たされている`(p & 0) == 0`, したがって、この操作はすべての位置に適用されます。 これは多くの場合、伝播がまばらではなくグローバルになる隠れた「ストレス ケース」です。 マスク チェックは常に true になり、同じシミュレーション ルールが引き続き適用されるため、アルゴリズムはこれを自然に処理します。 

2 番目のエッジケースは、`delta = 0`。 3 つの操作すべてにおいて、ソース インデックスは宛先インデックスと等しくなります。 更新は追加的かつ同時であるため、各アクティブな位置は操作ごとに 1 回その値を 2 倍にします。 スナップショットにより、同じ操作内で二重カウントが行われないことが保証されます。 

3 番目のエッジ ケースは、計算されたソース インデックスが`q`アップ/ダウン操作で範囲外になります。 それらの貢献は完全に無視されなければなりません。 境界チェック`0 <= q < 32`これを強制して、不注意な実装によって引き起こされる可能性のある偶発的なラップアラウンド動作を防ぎます。 

4 番目のエッジ ケースは、XOR 接続です。 いつでも`p ^ delta`が有効である場合、マスク制約を非対称に満たさない可能性があります。つまり、論理ペアの一方の側だけが寄与することになります。 実装では、両方のエンドポイントがアクティブであることが正しく必要とされ、部分的な更新が非アクティブな領域に漏れないようにします。
