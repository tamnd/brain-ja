 ## 解決策
 ## 問題の理解

 トランザクションを表す一連の整数が与えられ、それが 1 つずつ累積されて累計値となります。 この合計を計算するマシンには、パラメータによって決定される固定の整数範囲があります。$k$したがって、累計は常にゼロを中心とした対称区間内に収まる必要があります。 いずれかの時点で部分和がこの間隔の外に出ると、計算はオーバーフローして無効になります。 

タスクは合計を計算することではなく、すべてのプレフィックス合計が許容範囲内に収まるように指定された数値を並べ替えられるかどうかを判断することです。 そのような順序が存在する場合は、それを出力する必要があります。 そうでない場合は、不可能であることを報告する必要があります。 

入力はビット制限パラメータで構成されます$k$、配列のサイズ$n$、および配列自体。 暗黙の制約は、すべての中間プレフィックスの合計が、次の式で決定される固定範囲内に収まらなければならないということです。$k$、これは符号付き整数の容量のように動作します。 

重要な問題は、順序を変更するとプレフィックスの合計が大幅に変化することです。 合計が有効な場合でも、順序が間違っていると、プレフィックスの合計が一時的に安全な範囲の外に押し出される可能性があります。 このため、根本的に問題は最終結果ではなく、部分和の制御に関するものになります。 

単純なアプローチでは、すべての順列を試したり、構造を持たずに貪欲な選択をシミュレートしたりする可能性があります。 これは大きな場合にはすぐに壊れます$n$階乗増加は不可能であり、順列ごとの二次検査ですら遅すぎるためです。 

大きな正の値と負の値が同時に存在する場合、微妙な失敗のケースが発生します。 たとえば、すべての大きなポジティブを早期に配置すると、たとえそれを補う大きなネガティブが後で存在したとしても、上限を超える可能性があります。 同様に、ネガティブを最初に配置すると、ポジティブが到着する前に下限を下回る可能性があります。 正しいソリューションでは、配列を自由に並べ替えることができるものとして扱うのではなく、極端なバランスを慎重にとらなければなりません。 

## アプローチ

 ブルートフォース戦略では、配列のすべての順列を生成し、プレフィックスの合計がそれぞれの範囲内にあるかどうかをチェックします。 これは制約を直接強制するので正しいですが、それには次のことが必要です。$n!$順列と$O(n)$順列ごとに検証が行われるため、実行不可能になります$O(n \cdot n!)$複雑。 たとえ$n = 10$、これは非現実的になります。 

重要な観察は、各ステップで重要なのは累計額の大きさのみであり、危険は極端な場合に発生するということです。 大きな正の値は上限を脅かし、大きな負の値は下限を脅かします。 これは、プレフィックスの合計が境界からできるだけ遠くなるような順序で要素を常に配置する必要があることを示唆しています。 

これを実現する標準的な方法は、数値を正と負に分けてから、現在の合計と比較して最も安全な要素を常に選択することです。 直観的には、合計が正または上限に近い場合は負の値を選択して元に戻す必要があり、合計が負または下限に近い場合は正の値を選択する必要があります。 

これにより、問題は組み合わせ検索から制御された貪欲な構築に変換されます。

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. 配列を 2 つのグループ (非負の数と負の数) に分割します。 現在の合計に応じてこれら 2 つのプールを切り替えることで、プレフィックス合計を制御します。 
2. 負でない数値を降順に並べ替え、負の数値を昇順に並べ替えます。 これにより、常に最も「極端な」安全な動きを最初に考慮することが保証されます。これは、極端な値がプレフィックス合計のドリフトを最も効果的に修正するためです。 
3. 累計をゼロに初期化し、空の結果リストを準備します。 
4. 各ステップで、現在の合計が上限または下限のどちらに近いかを判断します。 上限に近い場合は、利用可能な最小の負の数値を使用して下方に引き下げることを好みます。 それが下限に近い場合は、利用可能な最大の正の数値を使用してそれを上方に押し上げることを好みます。 
5. 数値を選択する前に、その数値を追加しても合計が許容範囲内に収まるかどうかを確認してください。 優先選択が境界に違反する場合は、他のグループを試してください。 どちらの選択も有効でない場合、構築は失敗し、有効な順序が存在しません。 
6. すべての要素が使用されるまで続行します。 

この決定ルールが機能する理由は、利用可能な最も効果的な修正アクションが常に使用されるためです。 大きな値は、プレフィックスの合計が無効な領域に偏ることを防ぐために必要な状況のために予約されています。 

### なぜ効果があるのか

 このアルゴリズムは、各ステップの後、残りの未使用の数値が境界に違反することなくシーケンスを完了するのに十分であるという不変条件を維持します。 それぞれの選択は、現在近い境界から合計を遠ざけることにより、次のステップでのリスクを軽減するために行われます。 すべての移動は次のステップでの実現可能性を優先するため、要素の配置に失敗した場合は、その時点で制約に違反せずに要素を配置できなかった順列を意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    data = input().split()
    if not data:
        return
    k = int(data[0])
    n = int(data[1])
    arr = list(map(int, data[2:]))

    limit = 1 << k

    pos = sorted([x for x in arr if x >= 0], reverse=True)
    neg = sorted([x for x in arr if x < 0])

    i = j = 0
    res = []
    s = 0

    for _ in range(n):
        placed = False

        # decide direction
        if s >= 0:
            # try negative first
            if j < len(neg) and limit >= s + neg[j] >= -limit:
                s += neg[j]
                res.append(neg[j])
                j += 1
                placed = True
            elif i < len(pos):
                if -limit <= s + pos[i] <= limit:
                    s += pos[i]
                    res.append(pos[i])
                    i += 1
                    placed = True
        else:
            # try positive first
            if i < len(pos) and -limit <= s + pos[i] <= limit:
                s += pos[i]
                res.append(pos[i])
                i += 1
                placed = True
            elif j < len(neg):
                if -limit <= s + neg[j] <= limit:
                    s += neg[j]
                    res.append(neg[j])
                    j += 1
                    placed = True

        if not placed:
            print("N")
            return

    print("S")
    print(*res)

if __name__ == "__main__":
    solve()
```このソリューションでは、まず値を符号で区切ってから、最も影響力のある要素が最初に考慮されるように値を並べ替えます。 シミュレーションは貪欲に進行し、常に現在の合計に基づいて境界違反のリスクを最も軽減する動きを試みます。 

重要な点は、要素を盲目的に消費しないということです。 すべての候補は受け入れられる前にオーバーフロー範囲に対して検証され、プレフィックスの安全性が常に確保されます。

 ## 特殊なケース

 重大なエッジ ケースは、単一の大きな大きさの要素が境界を支配する場合です。 このような場合、配置順序のみが実現可能性を決定します。 アルゴリズムは、間隔をオーバーフローする可能性のあるステップを即座に拒否するため、これを正しく処理します。 

別のエッジ ケースは、正と負の大きさが交互に切り替わり、プール間の繰り返し切り替えが強制される場合に発生します。 貪欲なルールにより、合計が常に区間のより安全な側に移動することが保証され、1 つの符号に早期にコミットすることが防止されます。 

3 番目のケースは、配列が大きく偏っている場合です。たとえば、多くの大きな正と少数の小さな負があります。 ここでアルゴリズムは、十分なバランスが達成されるまで大きなプラスの消費を遅らせ、たとえ合計が安全であっても早期のオーバーフローを防ぎます。
