 ## 解決策
 ## 問題の理解

 配列が与えられ、固定長のすべての連続セグメントを調べるように求められます。$k+1$。 位置から始まる各セグメントについて$i$、要素を乗算することで概念的に変換します。$j$(セグメントの開始を基準にして) by$2^j$。 この指数関数的な重み付けの後、結果のシーケンスが厳密に増加しているかどうかを確認します。 タスクは、有効なセグメントを生成する開始位置の数をカウントすることです。 

直接読み取ると構造が隠蔽されます。何も並べ替えたり並べ替えたりせず、非常に特殊な不等号の連鎖がスライディング ウィンドウ全体で保持されるかどうかをチェックするだけです。 各ウィンドウに課せられるのは、$k$比較するたびに、隣接する値が 2 の係数で混合されます。 

制約により、テスト ケースごとに線形または線形に近い解決策が強制されます。 合計から$n$すべてのテストケース全体で最大でも$2 \cdot 10^5$、それを実現するあらゆるソリューション$O(nk)$次の場合、テスト ケースごとの作業がすぐに遅すぎます。$k$大きくすることもできます。 これにより、比較を前処理して各ウィンドウをチェックインできるようにするアプローチが推進されます。$O(1)$または償却された$O(1)$。 

スケーリング後に値が等しいかほぼ等しい場合、微妙なエッジ ケースが発生します。 たとえば、次の場合$a = [2, 1]$そして$k = 1$、比較します$2 \cdot 2$そして$1 \cdot 1$、平等を得る。 要件は厳密な不等式であるため、このウィンドウはカウントしてはなりません。 浮動小数点の 2 の累乗を使用したり、比較を誤って並べ替えたりする単純な実装では、計算時に等価性を暗黙的に有効なものとして扱ったり、整数オーバーフローを誤って処理したりする可能性があります。$2^j \cdot a_i$。 

もう 1 つのエッジ ケースは、オーバーフローまたは 2 のべき乗の不必要な再計算です。 以来$2^k$単純に実装すると標準の整数の範囲を超える可能性があり、ウィンドウごとの直接累乗に依存するソリューションは脆弱で非効率になります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 あらゆるインデックスに対して$i$、窓を確認します$[i, i+k]$。 変換された各値を計算します$a_{i+j} \cdot 2^j$すべての隣接するペアが厳密に増加していることを確認します。 これには費用がかかります$O(k)$ウィンドウごとに、$O(nk)$テストケースごとに。 いつ$n$大きくて、$k$も大きいので、これは約に縮退します$10^{10}$限界をはるかに超えた最悪の場合の操作。 

重要な観察は、スケールされた値を実際に具体化する必要がないということです。 ウィンドウ内の 2 つの隣接する要素間の条件は次のとおりです。$$a_{i+j} \cdot 2^j < a_{i+j+1} \cdot 2^{j+1}.$$両辺をで割ると$2^j$(これは正であり、不等号の方向が維持されます)、簡略化された形式が得られます。$$a_{i+j} < 2 \cdot a_{i+j+1}.$$これが中心的な単純化です。すべての隣接する比較は、ウィンドウ内の位置とは無関係に、元の配列値のペアのみに依存します。 指数関数的な重みは完全に消えます。 

したがって、再計算でウィンドウ全体をチェックする代わりに、隣接する各ペアが条件を満たすかどうかを示すブール配列を事前計算します。$a_i < 2a_{i+1}$。 次に、元の問題は長さを数えることになります-$k$このブール配列内の連続するセグメントは完全に true です。 

これにより、問題はバイナリ配列上のスライディング ウィンドウに縮小されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nk)$|$O(1)$| 遅すぎる |
 | 最適 |$O(n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 隣接するペアごとに$(a_i, a_{i+1})$かどうかを計算します。$a_i < 2a_{i+1}$。 結果を配列に格納する`good[i]`。 

これにより、乗算指数制約が単純な局所条件に変換されます。 
2. 有効な開始インデックスが設定されていることを確認します。$i$元の問題は連続したセグメントに対応します`good[i] ... good[i+k-1]`すべて真実です。 

この再定式化により、ウィンドウの長さが次のように短縮されます。$k+1$要素を$k$ブール条件。 
3. スライディング ウィンドウの合計を維持する`good`。 最初の合計を初期化します$k$の値`good`。 

合計が等しい場合$k$、そのセグメント内のすべての条件が満たされています。 
4. ウィンドウを 1 段階ずつスライドさせます。 から移動するとき$i$に$i+1$、減算`good[i]`そして追加します`good[i+k]`。 

これにより、各ウィンドウ チェックが一定の時間で行われます。 
5. 合計が等しい各ウィンドウをカウントします。$k$これは、セグメント内のすべての比較が有効であることを意味するためです。 

正しさは、元のすべての不等式連鎖が、2 の累乗をキャンセルした後の独立した隣接条件の連鎖と同等であるという事実に依存しています。 各ウィンドウの有効性は、その内部のすべてのローカル制約が保持されるかどうかによってのみ決まります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))

        if k == 1:
            # window size 2, directly check condition
            ans = 0
            for i in range(n - 1):
                if a[i] < 2 * a[i + 1]:
                    ans += 1
            print(ans)
            continue

        good = [0] * (n - 1)
        for i in range(n - 1):
            if a[i] < 2 * a[i + 1]:
                good[i] = 1

        window_sum = sum(good[:k])
        ans = 1 if window_sum == k else 0

        for i in range(1, n - k):
            window_sum -= good[i - 1]
            window_sum += good[i + k - 1]
            if window_sum == k:
                ans += 1

        print(ans)

if __name__ == "__main__":
    solve()
```コードはまず、指数関数的不等号連鎖を、`good`。 特別な場合$k=1$わかりやすくするために直接処理されますが、一般的なスライディング ウィンドウも均一に機能します。 スライディング ウィンドウの合計は、制約のセグメント全体が保持されるかどうかを追跡し、再計算を回避します。 

よくある落とし穴は、off-by-one インデックス作成です。`good[i]`間の条件に相当します`a[i]`そして`a[i+1]`、つまり で始まるウィンドウ`i`用途`good[i]`を通して`good[i+k-1]`。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 ## 特殊なケース

 隣接する値が等しい場合、条件は$a_i < 2a_{i+1}$両方が等しい場合は常に失敗します。$a_i < 2a_i$、これは次の場合を除いて真です。$a_i = 0$ただし、元のチェーンの厳密な不等式は、変換を通じて正しく伝播されます。 アルゴリズムはそのようなペアを正しくマークし、それらを含むウィンドウがカウントされるのを防ぎます。 

非常に大きな値の場合、計算は成立しません$2^k \cdot a_i$したがって、オーバーフローのリスクはありません。 ソリューション全体は、比較ごとに 1 回の 2 の乗算のみに依存しており、Python および一般的な 64 ビット環境の標準整数制限内に収まります。 

小型用$k$、 特に$k=1$の場合、アルゴリズムは直接隣接スキャンに縮小されます。 実装ではこれを均一に処理しますが、ロジックではこれをサイズ 1 の縮退スライディング ウィンドウとしても明示的に扱います。`good`、ウィンドウの初期化でオフバイワンエラーが発生しないようにします。
