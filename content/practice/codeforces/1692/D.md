 ## 解決策
 ## 問題の理解

 24 時間制の開始時刻と、観測間の固定の分数が与えられます。 ビクターは指定された時刻から開始し、毎時間ごとに繰り返し時計を見ます。$x$分。 

24 時間時計は 1 日で一巡するため、表示される時間の順序は最終的に周期的になります。 この繰り返しシーケンスの中に、**異なる回文時刻**がいくつ出現するかを数えなければなりません。 

時間は次のように書かれます`"HH:MM"`。 回文かどうかをチェックするには、コロンを含む文字列全体を処理します。 例えば、`"12:21"`そして`"05:50"`5 文字の文字列を逆から読むと同じ文字列が得られるため、回文になります。 

制約は非常に小さいです。 時計には次のものしか含まれていません$24 \times 60 = 1440$明確な瞬間。 の価値とは関係なく、$x$、最大 1440 回の遷移の後、以前に見た時間に戻らなければなりません。 最大 100 個のテスト ケースの場合、各テスト ケースの 1440 回すべてを処理する場合でも、必要な反復は約 144,000 回のみであり、これはわずかです。 

主な課題はパフォーマンスではなく、サイクル構造を正しく処理することです。 

簡単な間違いの 1 つは、個別の回文時刻ではなく、回文の出現を数えることです。 考慮する：```
11:11 1440
```あらゆる観察が示しているのは、`11:11`、しかし答えは`1`、無限のカウントや観測値の数ではありません。 

もう 1 つのよくある間違いは、シーケンスが繰り返されるまでではなく、正確に 1440 分間シミュレーションすることです。 例えば：```
00:00 720
```順序は次のとおりです。```
00:00 -> 12:00 -> 00:00
```異なる時間は 2 回だけ到達します。 正しい解決策は、開始状態が再び表示されると停止します。 

3 番目の微妙な問題は、深夜のラップアラウンドの処理です。 例えば：```
23:59 1
```1 分追加すると、次のようになります。`00:00`、 ない`24:00`。 合計分を 1440 で割って作業すると、そのようなバグは完全に回避されます。 

## アプローチ

 最も直接的なアイデアは、時計を繰り返し進めることです。$x$分を記録し、遭遇するたびに記録します。 表示された時刻が回文である場合は、それをセットに追加します。 以前に訪れた時間に戻ると、プロセスは停止します。 

この総当たりシミュレーションはすでに十分に高速です。 状態空間には可能なクロック値が 1440 個しか含まれていないため、シミュレーションはテスト ケースごとに最大 1440 回の反復を実行します。 

シーケンスは循環的であるため、注意を怠るとブルート フォースが無期限に継続される可能性があります。 重要な観察は、クロックの状態がその日の現在の分によって完全に決定されるということです。 存在する状態は 1440 個だけであるため、ある状態を再訪問することは、将来のシーケンス全体が正確に繰り返されることを意味します。 

プロセスが最大 1440 状態のサイクルで存在することがわかれば、解決策は簡単になります。 シーケンスをシミュレートし、訪問回数を保存し、1 つの完全なサイクル中に遭遇した個別の回文文字列をカウントします。 

結果として得られるアルゴリズムはシンプルであり、特定の制約に対して最適です。

## アルゴリズムのチュートリアル

 1. 開始時刻を換算する`"HH:MM"`真夜中からの分数に変換します。 
2. 訪問したクロック状態のセットを作成します。 これにより、シーケンスの繰り返しが開始されるタイミングを検出できるようになります。 
3. 回文時間用の別のセットを作成します。 セットを使用すると、サイクル内で複数回出現する場合でも、各回文が 1 回だけカウントされることが保証されます。 
4. 現在のクロック状態にアクセスしていない間、次の操作を行います。 

状態を訪問済みセットに追加します。 
5. 現在の分カウントを次のように変換します。`"HH:MM"`形式。 
6. 結果の文字列が回文であるかどうかを確認します。 

存在する場合は、回文セットに挿入します。 
7. 時計を進める$x$1440 を法とする分。 

モジュロ演算は、午前 0 時をまたぐラップアラウンドを自動的に処理します。 
8. 以前に訪れた状態に到達したら、シミュレーションを停止します。 
9. 回文セットのサイズを出力します。 

### なぜ効果があるのか

 各クロック状態は、1 日に可能な 1440 分の 1 つに対応します。 初期状態から繰り返し追加$x$分は決定的なシーケンスを生成します。 状態が繰り返されると、シーケンスは再び同じサイクルに入り、新しい時間が現れることはありません。 

アルゴリズムは、このサイクル内のすべての個別の状態を 1 回だけ訪問します。 サイクル内に現れるすべての回文時間が回文セットに挿入され、セットは重複を自動的に削除します。 サイクルには、ビクターがこれまでに見ることのできるすべての時間が含まれるため、最終的なセットのサイズは、まさに彼に見えるさまざまな回文の数になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def is_palindrome_time(minutes):
    h = minutes // 60
    m = minutes % 60
    s = f"{h:02d}:{m:02d}"
    return s == s[::-1], s

t = int(input())

for _ in range(t):
    time_str, x = input().split()
    x = int(x)

    h = int(time_str[:2])
    m = int(time_str[3:])
    cur = h * 60 + m

    visited = set()
    palindromes = set()

    while cur not in visited:
        visited.add(cur)

        ok, s = is_palindrome_time(cur)
        if ok:
            palindromes.add(s)

        cur = (cur + x) % 1440

    print(len(palindromes))
```最初のステップでは、開始時刻を午前 0 時からの分を表す単一の整数に変換します。 この表現では、クロックを進めることが単に加算とそれに続くモジュロ 1440 であるため、算術演算がはるかに簡単になります。 

の`visited`set は、フォーマットされた文字列ではなく分の値を保存します。 これにより各クロック状態を一意に識別し、一定時間でのサイクル検出が可能になります。 

回文テストは、フォーマットされた`"HH:MM"`弦。 必要な形式には常に先行ゼロが含まれるため、次のように形式設定します。`:02d`が不可欠です。 先行ゼロなしの場合、次のような場合`"05:50"`は正しく表現されず、回文の検出は失敗します。 

ループは、状態が繰り返されるとすぐに停止します。 その時点で、将来のシーケンス全体も同様に繰り返されることがわかっているため、続行すると、以前に処理された時間を再訪するだけになります。

# helper: run solution on input string, return output string
import sys
import io

def run(inp: str) -> str:
    input_stream = io.StringIO(inp)

    def input():
        return input_stream.readline()

    t = int(input())
    out = []

    for _ in range(t):
        time_str, x = input().split()
        x = int(x)

        h = int(time_str[:2])
        m = int(time_str[3:])
        cur = h * 60 + m

        visited = set()
        pals = set()

        while cur not in visited:
            visited.add(cur)

            hh = cur // 60
            mm = cur % 60
            s = f"{hh:02d}:{mm:02d}"

            if s == s[::-1]:
                pals.add(s)

            cur = (cur + x) % 1440

        out.append(str(len(pals)))

    return "\n".join(out) + "\n"
