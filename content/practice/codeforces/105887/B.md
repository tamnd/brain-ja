 ## 解決策
 ## 問題の理解

 1 から n までの駅番号が付けられた鉄道路線が与えられます。 m列車あります。 各列車は固定駅 li で出発し、ri で終了し、定員 ci を持ちます。 列車を利用するすべての乗客は、li で乗車しなければならず、その後、ri までのルート上のどの駅でも降車できます (場合によっては終着駅 ri も含む)。 

当初、膨大な数の人がステーション 1 で待機しており、全員がステーション n に到着しようとしています。 移動の唯一の方法はこれらの列車を利用することですが、場合によっては中間駅で乗り換えて複数の列車を連結することになります。 問題は、列車の定員を考慮して乗客を最適に割り当てた場合、駅 1 から駅 n まで何人をうまく輸送できるかということです。 

この構造は本質的に、線上の有向非巡回グラフです。各トレインは容量 ci の li から ri への有向エッジであり、ノード 1 からノード n への可能な最大のフローが必要です。 微妙な点は、ri が 10^9 まで大きくなる可能性があるため、ステーションに関するグラフを直接構築できないことです。 

制約が重要な問題です。 ステーションの数は最大 10^9 と膨大であるため、ステーションをノードとして明示的にモデル化するアプローチは即座に除外されます。 ただし、すべてのテスト ケースにわたって列車の数は最大でも 2×10^5 であり、このことは、ソリューションが点ではなく間隔に関して動作し、圧縮された座標に対するソートまたはスイープ ラインのアイデアに依存する必要があることを強く示唆しています。 

素朴な解釈では、すべての駅をノードとして、すべての列車をエッジとして扱い、最大流量を試みることになります。 これは規模の問題だけでなく、10^9 ノードにわたる隣接関係を保存することさえ不可能であるために失敗します。 もう 1 つの素朴なアイデアは、列車内での乗客の貪欲な前方移動をシミュレートすることですが、慎重に順序付けしないと、重複する間隔が同じ限られた定員をめぐって競合するため、これは失敗します。 

典型的なエッジケースは、複数の列車が重なり合っているものの、異なる地点から出発する場合に発生します。 たとえば、n = 10 で、定員 1 の 1 ～ 10、定員 100 の 1 ～ 5、および定員 100 の 5 ～ 10 の 2 つの列車があるとします。最適な戦略では最初に直通列車を使用する場合でも、初期の短いセグメントに多くの人を送り込む貪欲なアプローチは、誤って長い直通パスをブロックする可能性があります。 正しい答えは 100 (最適な分割の解釈によっては 101 ですが、重要なのは優先順位付けです) ですが、単純な割り当ては順序によっては行き詰まってしまう可能性があります。 

別の失敗例は、出発点が遅い列車がより効率的な長距離ルートのロックを解除する場合に発生します。 右のエンドポイントで順序付けしないと、左から右への貪欲なシミュレーションにより、容量が早期に消費される可能性があります。 

## アプローチ

 問題は基本的に、間隔エッジのあるライン上の最大流量ですが、ライン構造により、一般的な流量アルゴリズムを回避できます。 重要な観察は、位置の増加による 1 から n への到達可能性のみを考慮しており、すべての列車が前方への乗り換えを可能にする間隔であるということです。 

ブルートフォースアプローチは、すべての駅をノードとして扱い、すべての列車を li から ri への有向エッジとして扱い、その後 Dinic などの最大フローアルゴリズムを実行することです。 各列車には定員があり、乗客はルート間で分割できるため、これは概念的には正しいです。 ただし、n は 10^9 まで大きくなるため、グラフを作成することさえできません。 それを無視して座標圧縮を想像したとしても、グラフには最大 2×10^5 のエッジが存在する可能性があり、これは問題ありませんが、本当の問題はラインに沿った転送のモデル化です。 単純なフロー グラフには連続するステーション間のエッジが必要ですが、これを明示的に表すことは不可能です。

重要な洞察は、視点を逆転させることです。 人々がどのように前進するかを追跡するのではなく、各列車の終点でどれだけの「流動容量」が蓄積できるかを追跡します。 各列車は、そのエンドポイントに到達するために限られた量の追加容量を提供しますが、これは以前の間隔からの十分な流入フローがある場合に限られます。 右の終点の昇順に列車を処理すると、r で終わる列車を考慮するときに、より早い点に到達するすべての方法がすでに考慮されていることが保証されます。 

動的プログラミング スタイルの配列 dp を維持できます。ここで、座標における dp は、その点に到達できる最大人数を表します。 座標が大きいため、関連するエンドポイントのみを圧縮し、位置でソートします。 各トレインは、cap ci を使用してフローを li から ri に移動する転送のように機能し、可能な限り多くのフローを貪欲に前方に押し出します。 

これにより、間隔を順番に処理し、到達可能な流量値を効率的に更新するという問題が軽減されます。 セグメント ツリーまたは順序付けされたマップで十分ですが、遷移は li から ri へのみであるため、スイープのような方法でイベントを処理し、最もよく知られている到達可能性を維持できます。

 ## アルゴリズムのチュートリアル

 まず問題を意味のある座標のみに絞り込みます。 すべての列車は、li と ri という 2 つの関連ポイントに寄与します。 すべてのエンドポイントを収集して並べ替えるので、問題を圧縮軸上で動作しているものとして扱うことができます。 

次に、すべての列車を右の終点 ri で並べ替えます。 この順序により、列車を処理するときに、より早い駅に到着するすべての可能な方法がすでに考慮されることが保証されます。 

各圧縮座標に到達できるフローの量を格納するマップまたは配列 dp を維持します。 最初はステーション 1 のみが無限の供給を持っていますが、実際には dp[1] を非常に大きな数値に設定します。 

各列車について、ri の増加順に、最初に li で利用可能な流量を決定します。 この値は、この列車を利用できる可能性のある人数を表します。 列車は ci 人以上を運ぶことができないため、この利用可能な流量と列車定員 ci の最小値を採用します。 

次に、この量を dp[ri] に加算し、ri に到達できる人の数を増やします。 これは、この列車を利用したすべての人が今リに到達することをモデル化しています。 

すべての列車を処理した後の答えは dp[n]、つまり最終駅に到達する総流量になります。 

重要な考え方は、ri でソートすることで間接的なルートを見逃さないようにするということです。 li に到達するフローは、li より前または li で終了する以前の列車からすでに計算されています。 

### なぜ効果があるのか

 スイープの任意の点で、 dp[x] は、終点が最大でも x である列車のみを使用して駅 x に到着できる最大人数を表します。 トレイン (l, r) を処理するとき、l への可能な寄与はすべてすでに確定しています。これは、l に到達するのに役立つ可能性のあるトレインは、将来の計算に役立つ場合には r までに終了するためです。 したがって、ソースとして dp[l] を使用することは安全であり、フローを dp[r] にプッシュしても以前の決定を無効にすることはできません。 r によるソートによって引き起こされる単調性により、状態がフローを前進させるために使用されると、後で過去の遷移を変更するような形で改善されないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    INF = 10**18

    for _ in range(T):
        n, m = map(int, input().split())
        trains = []
        coords = {1, n}

        for _ in range(m):
            l, r, c = map(int, input().split())
            trains.append((l, r, c))
            coords.add(l)
            coords.add(r)

        coords = sorted(coords)
        idx = {v: i for i, v in enumerate(coords)}

        dp = [0] * len(coords)
        dp[idx[1]] = INF

        trains.sort(key=lambda x: x[1])

        for l, r, c in trains:
            li = idx[l]
            ri = idx[r]

            flow = min(dp[li], c)
            dp[ri] += flow

        print(dp[idx[n]])

if __name__ == "__main__":
    solve()
```実装は、最大 10^9 の大きな値が管理可能なインデックスになるようにステーション座標を圧縮することから始まります。 すべての遷移は列車のエンドポイントのみに依存するため、これは不可欠です。 

dp 配列には、各圧縮ステーションで到達可能な流量が格納されます。 無制限の乗客供給を表すために、ステーション 1 を非常に大きな値で初期化します。 各列車は終点の順に処理され、開始時の現在の dp を使用して通過できる乗客の数を計算します。 

重要な点は、dp[ri] を上書きするのではなく、dp[ri] に flow を追加することです。 これにより、同じ駅に集まる複数の独立したルートがキャプチャされます。 min(dp[li], c) を使用するキャップにより、トレインが過剰に使用されないようになります。 

## 実用的な例

 ### 例 1

 入力:

 n = 5、列車 = (1,3,2)、(3,5,1)

 座標 [1,3,5] を圧縮します。 

| 電車 | dp[1] | dp[3] | dp[5] | 使用されるフロー |
 | --- | --- | --- | --- | --- |
 | 開始 | INF | 0 | 0 | - |
 | 1-3 | INF | 2 | 0 | 2 |
 | 3-5 | INF | 2 | 1 | 1 |

 最初の列車は 2 人を 1 から 3 まで押します。2 番目の列車は 3 で利用可能な 2 人のうち 1 人しか使用できないため、1 から 5 まで押します。最終的な答えは 1 です。 

このトレースは、容量制限がどのように前方に伝播するか、および中間蓄積がどのように重要であるかを示します。 

### 例 2

 入力:

 n = 6、列車 = (1,6,3)、(1,3,10)、(3,6,10)

 | 電車 | dp[1] | dp[3] | dp[6] | 使用されるフロー |
 | --- | --- | --- | --- | --- |
 | 開始 | INF | 0 | 0 | - |
 | 1-3 | INF | 3 | 0 | 3 |
 | 3-6 | INF | 3 | 3 | 3 |
 | 1-6 | INF | 3 | 3 | 3 |

 ここでは直接ルートと間接ルートの両方が寄与していますが、ボトルネックは最初のセグメントであるため、6 に達する合計は 3 になります。 これは、複数のオーバーラップ パスが共有制約を超えて総フローを増加させないことを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、輸送力の高い短い列車が、輸送力の低い長い列車の前に出現する場合です。 たとえば、1 から 3 までの列車は容量 100 で、もう 1 から n までの列車は容量 1 です。 r の昇順に処理することで、短い列車が誤ってグローバル ボトルネックをブロックすることがなくなります。これは、長い列車はステーション 1 への寄与がすべて考慮された後に処理され、それ自体の限られた定員が n に直接寄与するためです。 

もう 1 つのケースは、同じエンドポイントを共有する複数のトレインです。 dp[r] に累積するため、すべての独立した寄与が正しく合計され、パスが別のパスを上書きすることはありません。 たとえば、(1,5,3) と (2,5,4) はどちらもステーション 5 に寄与しており、アルゴリズムはそれらの実行可能なフローを正しく集約します。 

最後の微妙なケースは、中間駅が終点としてのみ表示され、列車の終点として表示されない場合です。 座標圧縮にはそれらも含まれており、関連するすべての転送ポイントに dp エントリが存在することが保証され、遷移の損失が防止されます。
