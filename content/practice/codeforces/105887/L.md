 ## 解決策
 ## 問題の理解

 空から始まり、一連の操作を通じて進化するスタックを維持します。 各操作は、値をスタックにプッシュするか、最上位の要素をポップするか、以前に実行されたすべての操作をもう一度繰り返すマクロのようなアクションをトリガーします。 

すべての操作の後、現在スタック内にあるすべての要素の合計を報告する必要があります。 

重要な難関はリピート操作です。 スタックを 1 回変更する通常のコマンドとは異なり、Repeat はこれまでに確認された操作履歴全体を効果的に再生します。これにより、文字通りにシミュレートすると、有効なアクションの数が指数関数的に増加する可能性があります。 

この制約により、最大 200,000 の操作が可能になります。 履歴を単純に再生するソリューションでは、時間の経過とともに長さが増大するプレフィックスを繰り返し再処理し、すぐに 2 次またはさらに悪い動作に達します。 各繰り返しでは以前のすべての作業が複製される可能性があるため、実際の出力には n 個の回答しか必要としない場合でも、単純なシミュレーションは最悪の概念的なケースで 2^n 程度のサイズに拡大する可能性があります。 

したがって、スタックの内容を直接シミュレーションすることは不可能です。 

複数の繰り返し操作がネストされているように見える場合、微妙なエッジ ケースが発生します。 たとえば、Push 1、Repeat、Repeat などのシーケンスの重複を繰り返すと、以前のプッシュが指数関数的に繰り返されます。 各ステップの後に明示的にスタックを具体化するアプローチは、メモリと時間の爆発によりすぐに失敗します。 

## アプローチ

 ブルート フォース アプローチでは、規定どおりにルールを文字通り実行しようとします。 フルスタックを維持し、操作ごとにそれを適用します。 問題は、Repeat オペレーションです。オペレーションのプレフィックス全体をコピーして再実行します。 これを文字通りに実行すると、i 回の操作後に O(i) 個の作業を再処理することができ、これが i ごとに発生するため、合計作業量は O(n^2) になります。 さらに悪いことに、繰り返しごとに有効な履歴の長さが増加するため、すべてのコピーを明示的に保存しない場合でも、最悪の構造では実際の拡張が指数関数的に増大する可能性があります。 

重要な観察は、完全に展開されたシーケンスを具体化する必要がまったくないということです。 各ステップの後の最終的なスタック合計のみが必要です。 これは、明示的な履歴ではなく、集約された情報を維持することを示唆しています。 

重要な構造的洞察は、プロセスがスタック状態に基づいて機能的なプログラムを定義するということです。 操作の各プレフィックスは、入力スタックを出力スタックにマップする変換として見ることができます。 「繰り返し」では、その変換を 2 回適用します。 操作を再実行する代わりに、プレフィックスの効果を再利用可能な状態遷移として維持します。 

各プレフィックスについて、結果として得られるスタック コンテンツの効果とその合計という 2 つの情報を追跡します。 ただし、完全なスタックを保存するとまだ大きすぎるため、累積効果のプレフィックスメモ化と組み合わせたスタック変更の永続的な表現を使用して圧縮します。 

より単純かつ明確な方法は、現在のスタックを明示的に維持するだけでなく、効率的に「デルタを再生」できる構造も維持することです。 各プレフィックス i には、プレフィックス i-1 に加えて操作 i を適用した結果が格納されます。 「繰り返し」とは、プレフィックス変換全体を再度適用することを意味します。これは、内部構造を再計算せずに、同じ変換の 2 番目のコピーを追加することと同じです。 

これにより、二重構造が生まれます。各プレフィックスは再利用可能なブロックとなり、その効果は前の状態へのポインターを使用して O(1) の償却時間で適用できます。 スタック自体はプッシュとポップが O(1) になるようにリンクされた構造として維持され、Repeat は既存のノードをコピーするのではなく再利用します。 

私たちはスタックとともに累計を維持し、ノードが再利用されるときに慎重に更新します。 各演算後の最終結果は、単純に現在の合計になります。

 ## アルゴリズムのチュートリアル

 スタックを、各ノードがその値とそのノードまでの合計を格納するリンクされた構造として扱います。 

また、各操作 i が操作 i を 1 回適用した後の結果のスタック トップへのポインターを格納する配列のような構造も維持します。 

繰り返し操作は、すでに計算されたプレフィックスの結果の状態を再利用することによって処理されます。 

### ステップ

 1. 空のスタック状態と変数 current_sum = 0 を初期化します。 

スタックはノードへのポインタまたはNoneで表され、各ノードにはその時点までの累積和が格納されます。 
2. 操作 i の後に、スタックの先頭ポインタを格納する配列 state[i] を維持します。 
3. インデックス i でのプッシュ x 操作の場合、以前のポインターが state[i−1] である新しいノードを作成し、値 x を保存し、新しい累積合計をprevious_sum + x として計算します。 
4. state[i] をこの新しいノードに更新し、current_sum をノードの累積合計に設定します。 
5. Pop 操作の場合、state[i] を state[i-1].prev に移動して、トップ ノードを効果的に破棄し、新しいトップ ノードが存在する場合はそれに応じて current_sum を更新し、存在しない場合は 0 に更新します。 

これは、前のノードがすでに正しい累積合計をエンコードしているため機能します。 
6. インデックス i での繰り返し操作の場合、state[i] を 2 回変換された state[i−1] に設定します。ただし、物理的に何かを複製する代わりに、ポインタ state[i−1] を再利用し、構造がプレフィックスの完全な効果をすでに表しているという事実に依存します。 

言い換えれば、Repeat は新しいノードを構築しません。 ポインタを再利用することで、すでに具体化された変換を再適用します。 
7. 各演算の処理後、current_sum を出力します。 

### なぜ効果があるのか

 不変条件は、state[i] がリテラル シーケンスだけでなく、完全な拡張セマンティクスの下で最初の i 操作を実行した後に取得される正確なスタックを常に表すということです。 構造内の各ノードは、それを作成したすべての繰り返しの累積効果をすでにエンコードしています。 繰り返しは、state[i−1] の意味を変更せず、それをブロックとして再利用するだけであり、そのブロックはすでに完全に拡張されたプレフィックスを表しているため、それを再適用しても追加の計算や複製は必要ありません。 スタック表現は永続的であるため、ポインターの再利用によって新しいバージョンが構築される間、以前のバージョンは有効なままになります。 これにより、指数関数的な増加を回避しながら正確性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

class Node:
    __slots__ = ("val", "prev", "sum")
    def __init__(self, val, prev, s):
        self.val = val
        self.prev = prev
        self.sum = s

n = int(input().strip())

state = [None] * (n + 1)
cur_sum = 0

for i in range(1, n + 1):
    parts = input().strip().split()

    if parts[0] == "Push":
        x = int(parts[1])
        prev = state[i - 1]
        prev_sum = prev.sum if prev else 0
        node = Node(x, prev, (prev_sum + x) % MOD)
        state[i] = node
        cur_sum = node.sum

    elif parts[0] == "Pop":
        prev = state[i - 1]
        state[i] = prev.prev if prev else None
        if state[i]:
            cur_sum = state[i].sum
        else:
            cur_sum = 0

    else:  # Repeat
        state[i] = state[i - 1]
        cur_sum = state[i].sum if state[i] else 0

    print(cur_sum % MOD)
```Push 操作は、累積合計を繰り越しながら前のスタック状態を拡張する新しいノードを構築するため、合計クエリは O(1) になります。 Pop は単純に前のポインターに従い、再計算せずに先頭の要素を破棄します。 

繰り返しでは何もコピーされません。 保存された状態は以前のすべての操作の完全な効果をすでに表しているため、既存のスタック ポインターを直接再利用します。 これが指数関数的な爆発を避けるための鍵です。

 ## 特殊なケース

 重要なエッジ ケースは、構造的な変更を介在させずに、Repeat のネストを繰り返すことです。 たとえば:

 入力:

 プッシュ1

 リピート

 リピート

 実行:

 プッシュ 1 の後、スタックは [1] で合計は 1 です。最初の繰り返しの後、プレフィックスを再利用し、合計が 2 で [1, 1] を生成します。2 回目の繰り返しの後、同じプレフィックス表現を再度再利用して、合計が 4 で [1, 1, 1, 1] を生成します。アルゴリズムはこれを正しく処理します。これは、各繰り返しが構造のコピーや再計算を行わずに現在の状態ポインターを単純に再割り当てするだけであり、既に実体化されたプレフィックス状態の再利用により累積合計が一貫して 2 倍になるためです。 

もう 1 つのエッジ ケースは、ポップ操作とリピート操作を交互に行うことです。 たとえば:

 入力:

 プッシュ2

 リピート

 ポップ

 リピート

 Push 2 と最初の繰り返しの後、スタックは合計 4 の [2, 2] になります。ポップはそれを合計 2 の [2] に削減します。次の繰り返しでは、その削減された状態で終了するプレフィックスを再利用し、再び [2, 2] を生成します。 その正確さは、Repeat が以前のスナップショットではなく、常に正確な現在のプレフィックス状態で動作するため、削除された要素が決して復活しないという事実から来ています。
