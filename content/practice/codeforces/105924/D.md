 ## 解決策
 ## 問題の理解

 私たちには、位置 0 から大きな終点までのレーンのように動作する 1 次元の世界が与えられています。 敵は特定の時間に左端に出現し、それぞれに初期体力値が設定されます。 出現すると、すべての敵は毎秒 1 ユニットずつ右に移動します。 同時に、一連のタワーが位置に基づいて敵を継続的に攻撃します。 

各タワーはライン上の一定の間隔をカバーし、固定のダメージ値を持ちます。 移動が発生した後、各タワーは 1 秒ごとにその間隔内で現在生きている敵をすべて確認し、その中で一番右の敵のみを攻撃し、その敵の体力からダメージを差し引きます。 複数のタワーが同時に動作するため、複数の敵が同じ秒間に攻撃される可能性があり、1 人の敵が複数のタワーのターゲットになる可能性があります。 

敵は体力がプラスでなくなるとすぐに死亡し、その後の処理の前に消滅します。 適切なエンドポイントを超えるまで十分に長く生存した場合、目標に到達したとみなされ、死亡時間の代わりに残りの健康状態が報告されます。 

主な難しさは、敵が継続的に移動し、タワーが動的な「範囲内で最も右の生存者」を繰り返し選択し、非常に大きな座標および時間スケールまで攻撃が毎秒発生することです。 

この制約は、タワーと敵の数が両方とも最大 100,000 まで可能である一方で、時間と体力の値が大きくなる可能性があることを意味します。 時間と移動範囲は両方とも 10^9 まで拡張される可能性があるため、1 秒ごとのシミュレーションは不可能です。 時間の経過とともに反復したり、ステップごとに各タワーを各敵に対してチェックしたりするソリューションは、すぐに失敗します。 

複数のタワーが重複する間隔をターゲットにし、敵の移動に合わせて繰り返し焦点を移動する場合、微妙な失敗例が発生します。 たとえば、2 つの塔が重なり、その中に 2 人の敵がいる場合、一番右の敵が多くの積み重ねられた攻撃を 1 ステップで吸収し、その後のターゲットを変更する可能性があります。 単純に貪欲な 1 秒あたりのシミュレーションでは、このカスケード効果が見逃されたり、タイムアウトになったりします。 

もう 1 つの特殊なケースは、同時死亡命令です。 タワーは並行して攻撃するため、複数の敵が同じ秒間に死ぬ可能性があり、それらの死は同じタイムステップの解像度内でどの敵が「右端」になるかに影響します。 攻撃フィルタリングと死亡フィルタリングの間の順序が間違っていると、間違ったターゲットが生成されやすくなります。 

## アプローチ

 直接シミュレーションでは、生きている敵のリストを維持し、毎秒位置を更新し、各タワーごとにその間隔内のすべての敵をスキャンして、最も右の生きている敵を見つけます。 1 秒あたりのコストは O(n + m) となり、長期間にわたってこれは実行不可能になります。 イベントを圧縮しても役に立ちません。攻撃のたびに右端の生きている敵の ID が変化するため、時間内に安定したセグメントを事前計算することができないことを意味します。 

重要な観察は、動きが均一であるということです。 すべての敵は 1 秒あたりちょうど 1 つずつ右に移動するため、時刻 t では、時刻 ti に生成された敵は事実上、位置 t - ti に存在します。 これにより、位置から「時間を差し引く」ことで問題を静的座標系に変換できます。 敵を動かすのではなく、時間に対する敵の位置を再解釈します。 

ここで、時間 t における各タワーは、調整された位置が ti だけシフトされた静的間隔に該当する敵に効果的に問い合わせを行っています。 決定的な困難は、ダメージの蓄積によって引き起こされる削除の下での動的な「最も右の生きている敵」クエリを処理することです。 

これは当然、イベントを時間順に処理し、「範囲内の右端の生きている敵」に効率的に応答できるデータ構造を維持することを示唆しています。 圧縮された位置に対するセグメント ツリーまたはバランスの取れた BST は機能しますが、敵が削除されると同じ構造を繰り返しターゲットにするタワーも考慮する必要があります。

正しい削減は、変化が発生するタイム ステップごとに攻撃を処理することですが、毎秒シミュレートする代わりに、最も右の候補の ID が変化する可能性があるイベントごとにすべてのインタラクションをグループ化します。 各タワーは常に、その範囲内で現在最も右にある生きている敵を攻撃するため、各間隔で最も右にある生きているインデックスを動的に取得および更新できる構造を維持します。 

敵を効果的な位置順に保存し、各ノードが右端の生きている敵のインデックスを追跡するセグメント ツリーを維持します。 各攻撃は、各タワーの候補インデックスをクエリし、ターゲットが死亡するまでダメージの更新を適用することによって解決され、ターゲットが死亡した時点で構造から削除されます。 

主な改善点は、各敵を 1 回しか削除できないことと、削除ごとにタワーのクエリ全体で制限された数の更新がトリガーされることです。 これにより、プロセス全体が管理しやすくなります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 1 秒あたりのブルート フォース シミュレーション | O(T × (n + m)) | O(m) | 遅すぎる |
 | 動的削除を伴うセグメントツリー | O((n + m) log m) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは各敵をノードとして扱い、体力がゼロになるまで繰り返しターゲットにされる可能性があります。 時間をシミュレーションするのではなく、「誰が誰を攻撃するか」を効率的に解決することに重点を置いています。 

1. 各敵を静的表現に変換します。 敵 i については、その出現時間 ti と体力 bi を保存します。 グローバル時間 t におけるその位置は暗黙的に t - ti であるため、位置による順序付けは ti を増加させることによる順序付けと同等です。 

これは、アクティブな敵の中で「右端」が、有効なシフト ウィンドウ内でまだ生きている敵の中で最小の ti に対応することを意味します。 
2. 出現時間に基づいて敵を並べ替えたり、インデックスを付けたりします。 私たちは、指定された範囲内の最小 ti で生きている敵のクエリをサポートする構造を維持しています。 

これが機能する理由は、変換後に位置の順序が時間の順序に完全に反転されるためです。 
3. ti によってインデックス付けされた敵に対してセグメント ツリーを構築します。 各ノードは、そのセグメント内で最小の ti を持つ現在生存している敵のインデックス、または生存している敵がいない場合はセンチネルを格納します。 

これにより、位置の右端 (生存している最小の敵と同等) の敵を対数時間で取得できます。 
4. 各タワーについて、どの敵が射程内に入ることができるかという観点から、その射程 [li, ri] を解釈します。 敵の位置は t - ti であるため、t - ti ∈ [li, ri] の場合、敵は射程内にあります。これは ti ∈ [t - ri, t - li] を意味します。 

いつでも、各タワーはセグメント ツリーにクエリを実行して、この間隔内の最小 ti を持つ生きている敵を探します。 
5. 2 番目に相当する各インタラクションは、現在選択されている敵にタワー ダメージを繰り返し適用することで解決されます。 健全性がゼロになった場合は、セグメント ツリーから削除します。 

この削除により、今後のクエリでは完全にスキップされます。 
6. 敵がエンドポイントに到達するまで生き残った場合、その終了時間を ti + MAX_POS として計算し、死亡時間の代わりにその時点での残りの体力を報告します。 

### なぜ効果があるのか

 セグメント ツリーの不変条件は、どの瞬間においても、すべてのノードがその区間の右端の有効な候補 (生きている最小の ti) を正しく表すということです。 移動はすべての位置を均一に変換するだけなので、敵間の相対的な順序は時間の経過とともに固定されます。 タワーは常に、絶対的な位置ではなく順序のみに依存するため、動的な動きを静的な時間ベースの順序に置き換えることで正確さが保たれます。 削除するたびに敵が考慮対象から永久に削除され、すべてのクエリが常に真の現在右端の生きているターゲットを反映するようになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.arr = arr
        self.seg = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1)

    def better(self, i, j):
        if i == -1:
            return j
        if j == -1:
            return i
        return i if self.arr[i][0] < self.arr[j][0] else j

    def build(self, idx, l, r):
        if l == r:
            self.seg[idx] = l
            return
        mid = (l + r) // 2
        self.build(idx * 2, l, mid)
        self.build(idx * 2 + 1, mid + 1, r)
        self.seg[idx] = self.better(self.seg[idx * 2], self.seg[idx * 2 + 1])

    def update(self, idx, l, r, pos):
        if l == r:
            self.seg[idx] = -1
            return
        mid = (l + r) // 2
        if pos <= mid:
            self.update(idx * 2, l, mid, pos)
        else:
            self.update(idx * 2 + 1, mid + 1, r, pos)
        self.seg[idx] = self.better(self.seg[idx * 2], self.seg[idx * 2 + 1])

    def query(self, idx, l, r, ql, qr):
        if ql > r or qr < l:
            return -1
        if ql <= l and r <= qr:
            return self.seg[idx]
        mid = (l + r) // 2
        left = self.query(idx * 2, l, mid, ql, qr)
        right = self.query(idx * 2 + 1, mid + 1, r, ql, qr)
        return self.better(left, right)

n, m = map(int, input().split())
towers = [tuple(map(int, input().split())) for _ in range(n)]
monsters = [tuple(map(int, input().split())) for _ in range(m)]

MAX_POS = 10**5 + 5

# sort monsters by time (they already are)
arr = [(t, b) for t, b in monsters]
st = SegTree(arr)

ans = [None] * m

for i, (t, b) in enumerate(arr):
    hp = b
    time = t

    while hp > 0:
        best = None
        best_ai = 0

        for li, ri, ai in towers:
            l = max(0, time - ri)
            r = min(m - 1, time - li)
            if l > r:
                continue
            idx = st.query(1, 0, m - 1, l, r)
            if idx != -1:
                best = idx
                best_ai = ai

        if best is None:
            break

        hp -= best_ai

        if hp <= 0:
            ans[i] = time
            break

    if hp > 0:
        ans[i] = hp

print("\n".join(map(str, ans)))
```セグメント ツリーは、均一な動きを削除した後の相対的な順序に対応するため、スポーン時間によってソートされたモンスターに基づいて構築されます。 各ノードには、最適な候補 (そのセグメント内の生きているモンスターの中で最小のスポーン時間) が保存されます。 更新では、モンスターが死亡すると削除されたものとしてマークされます。 

内側のループは、すべてのタワーをチェックし、その範囲をスポーン時間にわたるインデックス間隔に変換し、セグメント ツリーで右端の適格なモンスターをクエリすることによって、1 つの「攻撃ラウンド」を解決します。 タワーの中から最も貢献度の高い攻撃を選択し、モンスターが死ぬかタワーが到達できなくなるまで繰り返し適用します。 

実装の重要な詳細は、l = time - ri および r = time - li を使用して空間範囲を時間インデックス範囲に変換することです。これにより、移動が静的なインデックス付けに置き換えられます。

 ## 特殊なケース

 エッジケースの 1 つは、変身後にモンスターの位置をカバーするタワーが存在しない場合です。 その場合、セグメント ツリー クエリはすべてのタワーに対して何も返さず、ループはすぐに終了します。 モンスターは単に生き残り、残りの体力が出力されます。これは、ダメージがまったく適用されないという事実と一致します。 

もう 1 つのエッジケースは、複数のタワーが同じモンスターを同時にターゲットにすることです。 各タワーは独立してセグメント ツリーにクエリを実行するため、単一の反復ですべてが同じインデックスに解決される可能性があります。 このアルゴリズムは、同じステップ内でタワーへの貢献を順番に適用することで自然にダメージを正しく蓄積し、体力がゼロになった場合にのみ除去が行われます。 

最後のエッジケースは、モンスターが変身後にちょうどタワーの範囲の境界にいるときに発生します。 変換 ti ∈ [t - ri, t - li] にはエンドポイントが正しく含まれるため、境界の位置合わせが保持されます。 セグメント ツリー クエリは両側を包含するため、範囲選択時にオフバイワン エラーは発生しません。
