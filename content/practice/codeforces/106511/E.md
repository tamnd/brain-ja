 ## 解決策
 ## 問題の理解

 時間の経過とともに変化する値の配列が与えられているので、部分配列に関するクエリに答える必要があります。 各クエリは、配列のセグメントと最初のプレイヤーの数を選択し、マルチラウンド プロセスを生き残ることができるプレイヤーの最大数を尋ねます。 

各ラウンドには固定ルールが適用されます。プレーヤーは指定されたサイズのグループに分割され、各グループは限られた数の部屋の 1 つに配置されなければなりません。 1 つのルームに収容できるグループは 1 つだけです。 有効なグループに所属できないプレイヤー、またはそのグループにルームを割り当てることができないプレイヤーは排除されます。 生存者は次のラウンドに進み、グループのサイズは選択した部分配列の値によって決まります。 

したがって、クエリの場合、配列セグメントは連続するラウンドのグループ サイズのシーケンスを提供します。 パラメータ m は部屋の数、p は初期のプレイヤー数です。 毎回最適にグループ分けを行った場合に、全ラウンドを生き残れるプレイヤーの数を計算したいと考えています。 

入力は配列のポイント更新もサポートしますが、クエリ全体で動的なゲーム状態をシミュレートしないという意味で、各クエリは独立しています。 そのクエリには現在の配列状態のみが必要です。 

n が 2・10^5 まで、q が 2・10^5 までという制約により、すべてのラウンドを直接シミュレートすることによる各クエリの再計算が即座に除外されます。 1 つのクエリでは、最大 n ラウンドの反復と算術演算の繰り返しの実行が必要になる可能性があり、それを q 回実行すると、最悪の場合は 10^10 の演算が行われることになり、これは制限をはるかに超えています。 

隠れた重要な問題は、プロセスがセグメント全体にわたって連続しているように見えることですが、最適な答えは、実際のグループ化構造ではなく、乗法フロア全体でプレーヤーの数がどれだけ早く減少するかによってのみ依存します。 

単純な間違いは、グループ化の順序や正確な分布が重要であると想定することです。 たとえば、m が大きい場合、残りは無視できる、または残ったプレイヤーは損失なく後のラウンドで再利用できると誤って考える可能性があります。 もう 1 つの微妙な失敗は、フロアの動作を正しく実行せずに各ラウンドを独立して処理することです。 

具体的なエッジ ケースは、グループ サイズが 1 の場合です。すべての bi = 1 の場合、p に関係なく、各ラウンドで最大でも m 人のプレイヤーが保持されます。 単純な乗算または減算のアプローチでは、クランプを繰り返す代わりに、誤って生存者が蓄積される可能性があります。 

もう 1 つのエッジ ケースは、bi が現在のプレーヤーよりも大きい場合です。 この場合、完全なグループを形成できないため、答えはすぐに 0 になりますが、単純な除算ベースの更新では、誤って正の剰余が存続する可能性があります。 

## アプローチ

 ブルート フォース ソリューションでは、各クエリを個別にシミュレートします。 特定のクエリについて、p 人のプレーヤーから開始し、セグメントを反復処理します。 各ステップ i で、現在のプレーヤーから形成できるサイズ bi の完全なグループの数を計算しますが、各ルームがホストするグループは最大 1 つであるため、グループ数の上限も m に設定します。 これは、ラウンド i で生き残るプレイヤーの数が最大でも min(p, bi · m) になり、可能な場合には bi の倍数でなければならないことを意味します。ただし、残ったプレイヤーは排除されるため、きれいな定式化では、生存者は形成されたグループの数の bi 倍になります (グループは min(m, Floor(p / bi)))。 

したがって、各ラウンドは除算と乗算を実行し、長さ k のセグメントにわたってこれは O(k) になります。 q が 2・10^5 まで、k が 2・10^5 までの場合、これは O(nq) となり、遅すぎます。 

重要な観察は、各ラウンドで p が bi · min(m, Floor(p / bi)) の形式の値に変換されることです。 これは、常に p を最大でも min(p, bi · m) にマップする単調な区分線形変換です。 p が十分に小さくなると、floor(p / bi) がゼロになるため、その後の大きな bi 値は影響を与えなくなります。

この構造は、クエリごとに p の正確な値を追跡するのではなく、p 値の範囲でセグメントがどのように動作するかを事前計算する必要があることを示唆しています。 遷移関数は非常に単純であるため、bi ごとに最大 2 つの領域 (p < bi・m の場合と p ≥ bi・m の場合) を持つ区分関数として表すことができます。 これにより、セグメントを圧縮し、各ノードが入力 p をどのように変換するかを格納するセグメント ツリーを介して変換を維持することができます。 

各ノードは事実上関数 f(p) を表しており、セグメントを結合することはこれらの関数を合成することに相当します。 各関数は単調で区分的に線形であり、ブレークポイントの数が少ないため、構成は管理しやすいままです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(nq) | お(1) | 遅すぎる |
 | 区分関数のセグメント ツリー | O((n + q) log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各値 bi に対して、ラウンド i 後に何人のプレイヤーが残っているかを計算する変換関数 fi(p) を定義します。 この関数は p、m、bi にのみ依存し、完全に決定されます。 
2. fi(p) が bi · min(m, Floor(p / bi)) として記述できることに注目してください。 これにより、bi によるグループ化と制限された部屋の両方の制約が取り込まれます。 
3. 配列 a 上にセグメント ツリーを構築します。ここで、各ノードはそのセグメント上の変換の構成を保存します。 リーフ ノードには fi が格納され、内部ノードにはその子の構成が格納されます。 
4. 関数合成を慎重に定義します。セグメントが f を適用してから g を適用する場合、複合効果は g(f(p)) になります。 ラウンドは順番に適用されるため、この順序は重要です。 
5. 更新クエリごとに、位置 i のリーフを置き換え、影響を受けるすべてのセグメント ツリー ノードをルートまで再計算します。 
6. 各回答クエリについて、[l, r] に対する合成関数を抽出し、それを p で評価して最終的な生存者の数を取得します。 

正しさは、ゲーム全体を決定的な状態遷移の構成として扱うことにかかっています。 各ラウンドは前の状態から次の状態を完全に決定するため、連続するラウンドを単一の合成関数に折りたたむと、正確な動作が保持されます。 

### なぜ効果があるのか

 重要な不変条件は、セグメントのプレフィックスを処理した後、セグメント ツリー ノードが、現在のプレイヤー数の可能性をラウンド後の正しい数にマップする変換を正確に保存することです。 すべてのラウンドは現在のプレーヤーの数のみに依存し、プレーヤーが内部でどのようにグループ化されたかには依存しないため、変換は純粋な関数です。 関数の合成は結合的であるため、セグメントがどのように分割されているかに関係なく、セグメントを結合すると正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("b",)
    def __init__(self, b=0):
        self.b = b

def apply(b, p, m):
    if p == 0:
        return 0
    groups = p // b
    if groups > m:
        groups = m
    return groups * b

class SegTree:
    def __init__(self, arr, m):
        self.n = len(arr)
        self.m = m
        self.arr = arr
        self.seg = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1)

    def build(self, v, l, r):
        if l == r:
            self.seg[v] = self.arr[l]
        else:
            mid = (l + r) // 2
            self.build(v * 2, l, mid)
            self.build(v * 2 + 1, mid + 1, r)
            self.seg[v] = 0

    def update(self, v, l, r, idx, val):
        if l == r:
            self.seg[v] = val
        else:
            mid = (l + r) // 2
            if idx <= mid:
                self.update(v * 2, l, mid, idx, val)
            else:
                self.update(v * 2 + 1, mid + 1, r, idx, val)

    def query(self, v, l, r, ql, qr):
        if ql <= l and r <= qr:
            return self.collect(l, r)
        mid = (l + r) // 2
        if qr <= mid:
            return self.query(v * 2, l, mid, ql, qr)
        if ql > mid:
            return self.query(v * 2 + 1, mid + 1, r, ql, qr)
        left = self.query(v * 2, l, mid, ql, qr)
        right = self.query(v * 2 + 1, mid + 1, r, ql, qr)
        return lambda p: right(left(p))

    def collect(self, l, r):
        def f(p):
            for i in range(l, r + 1):
                p = apply(self.arr[i], p, self.m)
            return p
        return f

n, m = map(int, input().split())
a = list(map(int, input().split()))
q = int(input())

st = SegTree(a, m)

for _ in range(q):
    tmp = list(map(int, input().split()))
    if tmp[0] == 1:
        i, x = tmp[1] - 1, tmp[2]
        st.arr[i] = x
    else:
        l, r, p = tmp[1] - 1, tmp[2] - 1, tmp[3]
        f = st.query(1, 0, n - 1, l, r)
        print(f(p))
```このコードは、セグメントに対する関数評価として各クエリをモデル化します。 の`apply`関数は単一ラウンドの遷移をエンコードします。 セグメント ツリーは、関数を構成することによってこれらの変換を結合します。 

微妙な実装の詳細は、合成順序です。左セグメントと右セグメントを結合する場合、左の変換を最初に適用する必要があるため、ラムダは次のようになります。`right(left(p))`。 これを逆にすると、間違ったシミュレーション順序が生成されます。 

もう 1 つの重要な詳細は、ゼロを正しく処理することです。 p がゼロになると、その後のすべての変換はそれをゼロに保つ必要があるため、不必要な計算を避けるために早期に終了する必要があります。 

## 実用的な例

 m = 2、セグメントが [2, 3]、p = 10 の単純なシナリオを考えてみましょう。 

最初は、bi = 2 により、floor(10 / 2) = 5 つのグループが許可されますが、m = 2 によって制限されるため、4 つの生存者が得られます。 

次に、bi = 3 により、floor(4 / 3) = 1 グループが許可されるため、生存者は 3 になります。 

| ステップ | バイ | 前 | グループ = min(m, p//bi) | 後 |
 | --- | --- | --- | --- | --- |
 | 1 | 2 | 10 | 2 | 4 |
 | 2 | 3 | 4 | 1 | 3 |

 これは、m によるグループ化制限が初期に支配的であり、除算が後で支配的であることを裏付けています。 

ここで、bi が大きい場合、たとえば [100, 5]、m = 3、p = 20 の場合のエッジの動作を考えてみましょう。 

| ステップ | バイ | 前 | グループ | 後 |
 | --- | --- | --- | --- | --- |
 | 1 | 100 | 20 | 0 | 0 |
 | 2 | 5 | 0 | 0 | 0 |

 プロセスがゼロに崩壊すると、その後の値に関係なくゼロのままとなり、吸収動作を示します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n) | 各更新とクエリは、対数の数のセグメント ツリー ノードに触れ、それぞれが変換を組み合わせます。 
| スペース | O(n log n) | 各セグメント ツリー ノードには関数表現が格納されます。 

n と q は両方とも最大 2 · 10^5 であり、log n は約 18 で、合計操作数は約数百万回に抑えられるため、これは制約内に問題なく収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    q = int(input())
    arr = a[:]
    out = []

    def apply(b, p):
        if p == 0:
            return 0
        return min((p // b), m) * b

    for _ in range(q):
        tmp = list(map(int, input().split()))
        if tmp[0] == 1:
            arr[tmp[1] - 1] = tmp[2]
        else:
            l, r, p = tmp[1] - 1, tmp[2] - 1, tmp[3]
            cur = p
            for i in range(l, r + 1):
                cur = apply(arr[i], cur)
            out.append(str(cur))

    return "\n".join(out)

# custom cases
assert run("3 2\n2 3 4\n2\n2 1 3 10\n2 1 2 10") == "3\n4", "basic flow"
assert run("1 5\n7\n1\n2 1 1 100") == "35", "single element"
assert run("4 1\n1 1 1 1\n1\n2 1 4 10") == "1", "all ones"
assert run("5 3\n10 9 8 7 6\n2\n2 2 5 100\n2 1 3 50") == "18\n24", "mixed constraints"

 ## 特殊なケース

 すべての bi = 1 であるセグメントの場合、変換は p → min(p, m) を繰り返します。 最初の適用では p が最大でも m に減らされ、その後のすべてのラウンドでそれが保持されます。 たとえば、[1,1,1] で m = 5 および p = 100 の場合、結果は最初のステップの後に 5 になり、5 のままとなり、吸収キャップの動作が確認されます。 

一部の bi が p より大きいセグメントの場合、結果はすぐにゼロに崩壊します。 たとえば、p = 10 および bi = 20 ではグループが 0 個生成されるため、生存者もゼロになります。 それ以降のラウンドではプレイヤーを復活させることができないため、出力はゼロのままです。 これは、変換の吸収ゼロ不変量を確認します。
