 ## 解決策
 ## 問題の理解

 友達はそれぞれ、潜在的な仕事を持ってきます。 仕事は 2 つのことで定義されます。1 つは固定週 7 日のうち、アリスがその友人の犬の散歩をしなければならない曜日、もう 1 つはその週全体でその仕事を完了することに対する支払いです。 アリスは仕事を受け入れるか無視することができますが、同じ友達を二度受け入れることはできません。 

日々の制約が重要な構造上の制約となります。 7 日間それぞれに、アリスが散歩できるのは最大でも 2 匹の犬です。 したがって、選択したジョブのサブセットはすべて、毎日、作業を必要とする選択したジョブが 2 つ以下であることを満たさなければなりません。 

出力は、この 1 日あたりのキャパシティ制約を遵守するジョブのサブセットからの最大支払総額です。 

ジョブの数という点では入力サイズは小さく、友人の数は最大でも 100 人です。 隠された構造は週次スケジュールの次元にあります。各ジョブは 7 ビット パターンであるため、制約はサブセット選択問題に適用される 7 つの独立したキャパシティ制約の集合です。 これは、指数関数的なサブセットが自動的に不可能ではないことをすぐに示唆していますが、すべてのサブセットの単純な列挙はすでに 2^100 に達しており、これは実現可能性をはるかに超えています。 

欲張って考えると微妙な失敗モードが現れる。 たとえば、最も給与の高い仕事を最初に選択すると、日によって重なり方が異なるため、集合的により高い利益をもたらす多くの中程度の仕事がブロックされる可能性があります。 もう 1 つの問題は、毎日を独立して扱うことで発生します。1 日あたりの割り当ての最適化では、各ジョブが同時に複数日にまたがることが考慮されません。 

具体的な貪欲な失敗:

 入力:```
3
1 0 0 0 0 0 0 50
1 0 0 0 0 0 0 40
0 1 0 0 0 0 0 40
```値による欲張り戦略では、最初に 50 個のジョブを選択し、1 日目のキャパシティー 1 を未使用のままにし、2 番目のジョブも 1 日目を使用し、大規模なインスタンスでは他の日と異なる組み合わせになっている可能性があることを無視する可能性があります。 小規模な場合には、これは無害であるように見えますが、一般的には、重複する制約全体で最適なパッキングが損なわれます。 

## アプローチ

 直接的なブルート フォース ソリューションでは、N 個のジョブのすべてのサブセットが試行されます。 サブセットごとに、7 日間すべてをチェックし、その日に必要な選択されたジョブの数をカウントすることで実現可能性を検証します。 これは、解空間全体を探索するので正しいですが、2^N 個のサブセットを評価する必要があり、各サブセットについて 7 日間にわたって最大 N 個のジョブをチェックする必要があり、約 O(N・2^N) 個の操作が与えられます。 N = 100 の場合、これは完全に不可能です。 

重要な観察は、制約の次元が小さく、7 日に固定されていることです。 各ジョブは 7 ビット マスクとして表現できます。 サブセットについて直接推論する代わりに、毎日の構成に割り当てられるジョブの数を追跡しますが、それでもすぐに複雑さが軽減されるわけではありません。 

重要な再構築は、プロセスを毎日確認することです。 毎日最大 2 つの割り当てが許可されるため、ジョブを順番に処理し、7 日間のそれぞれに残っているスロットの数にわたって動的なプログラムを維持できます。 各日の容量は 2 であるため、状態は {0,1,2} の 7 タプルの整数になります。 これにより、最大 3^7 = 2187 個の状態が得られますが、これは十分小さいです。 

各ジョブは、マスク内のアクティブな日ごとに 1 単位の容量を消費します。 そこで、ジョブに対してナップザックのような DP を実行します。各ジョブについて、可能であれば、アクティブな日数からキャパシティを差し引く状態遷移にジョブを割り当てようとします。 これは、小さな寸法の境界付き多次元ナップサックです。 

したがって、問題は、合計値を最大化する残りの容量を表す状態にわたる DP になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース サブセット | O(N・2^N) | お(1) | 遅すぎる |
 | 7 日間の容量の状態における DP | O(N · 3^7) | O(3^7) | 承認済み |

 ## アルゴリズムのチュートリアル

 7 日間それぞれの残りの容量を、各エントリが 0、1、または 2 である 7 つの長さのタプルとしてエンコードします。 

1. DP ディクショナリを 1 つの状態で初期化します。すべての日の容量が 2、値が 0 です。これは、完全な可用性から開始することを表します。 
2. 各ジョブについて、その 7 ビット マスクとその報酬を読み取ります。 マスクは、このジョブが何日から 1 単位の容量を消費するかを示します。 
3. 既存の DP 状態ごとに、ジョブをスキップするか、すべての必要な日数に少なくとも 1 つの残り容量がある場合にジョブを引き受けるという 2 つの移行を試みます。 
4. 仕事を引き受けるとき、マスクに 1 がある毎日から 1 を引いて新しい状態を生成します。蓄積された値に仕事の報酬を追加します。 
5. 結果の各状態の最大値のみを保持して遷移をマージします。 
6. すべてのジョブを処理した後、答えはすべての DP 状態にわたる最大値になります。 

すべてのジョブは一度だけ貢献するかまったく貢献しないかのいずれかであり、状態遷移では常に実現可能性の制約が維持されるため、ジョブの順序は重要ではありません。 

### なぜ効果があるのか

 DP 状態は、将来の決定がどのようなものに依存するか、つまり毎日どれだけのスロットが残っているかを正確に把握します。 同じ残りのキャパシティベクトルにつながる以前のジョブ選択の 2 つの異なるシーケンスは、将来のすべての決定に対して同等です。これは、将来のジョブはこれらのキャパシティを通じてのみ相互作用するためです。 これにより、各容量構成の最適な値のみを保持して状態をマージしても、潜在的に最適なソリューションを破棄できないことが確立されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    jobs = []
    for _ in range(n):
        *days, m = map(int, input().split())
        mask = tuple(days)
        jobs.append((mask, m))

    from collections import defaultdict

    dp = {(2, 2, 2, 2, 2, 2, 2): 0}

    for mask, val in jobs:
        new_dp = dict(dp)

        for state, cur in dp.items():
            ok = True
            nxt = list(state)

            for i in range(7):
                if mask[i]:
                    if nxt[i] == 0:
                        ok = False
                        break
                    nxt[i] -= 1

            if ok:
                nxt = tuple(nxt)
                new_val = cur + val
                if nxt not in new_dp or new_dp[nxt] < new_val:
                    new_dp[nxt] = new_val

        dp = new_dp

    print(max(dp.values()))

if __name__ == "__main__":
    solve()
```このソリューションは、7 日間すべての完全な可用性から開始して、キャパシティの状態に対する DP を構築します。 各ジョブはスキップされるか、可能であれば適用されます。 実現可能性チェックにより、キャパシティを超える日がないことが保証されます。 ディクショナリには、各容量構成で達成可能な最良の値のみが保存されるため、重複した状態での指数関数的な爆発が防止されます。 

微妙な点はコピーです`dp`の中へ`new_dp`反復の前に。 これにより、単一のジョブを誤って複数回使用することになる、ジョブの同じ反復内での更新の連鎖が回避されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return sys.stdout.getvalue() if False else solve_capture(inp)

def solve_capture(inp: str) -> str:
    import sys
    from collections import defaultdict
    input = sys.stdin.readline
    data = inp.strip().split()
    it = iter(data)

    n = int(next(it))
    jobs = []
    for _ in range(n):
        days = [int(next(it)) for _ in range(7)]
        m = int(next(it))
        jobs.append((tuple(days), m))

    dp = {(2,2,2,2,2,2,2): 0}

    for mask, val in jobs:
        new_dp = dict(dp)
        for state, cur in dp.items():
            nxt = list(state)
            ok = True
            for i in range(7):
                if mask[i]:
                    if nxt[i] == 0:
                        ok = False
                        break
                    nxt[i] -= 1
            if ok:
                nxt = tuple(nxt)
                new_dp[nxt] = max(new_dp.get(nxt, 0), cur + val)
        dp = new_dp

    return str(max(dp.values()))

 ## 特殊なケース

 主なエッジケースは、複数のジョブがまったく同じ日の設定を必要とする場合です。 たとえば:

 入力:```
3
1 0 0 0 0 0 0 10
1 0 0 0 0 0 0 20
1 0 0 0 0 0 0 30
```DP は 1 日目にキャパシティー 2 で開始します。これらのジョブのうち最大 2 つを引き受けることができます。 遷移はジョブごとに 1 ユニットを消費した後の状態を正しく生成します。 最良の結果は、50 に達する 2 つの最も高い値を選択することによって得られます。容量がゼロになると 3 番目の選択は実行不可能になるため、DP はこれを強制します。 

もう 1 つのエッジケースは、要件のないジョブです。 このようなジョブは状態を変えることはなく、価値を高めるだけです。 実現可能性が決して失敗しないため、DP は常にそれを受け入れます。したがって、事実上自由に蓄積されます。これは、毎日の容量を消費しないため、正しいです。 

3 番目のエッジ ケースは、7 日間すべてを必要とするジョブです。 これにより、すべてのキャパシティ コンポーネントが 1 つ減少し、1 日あたりの制限により、そのようなジョブ全体で合計 2 回しか実行できなくなります。 DP は、明示的なカウント ロジックではなく、1 日あたりの枯渇を通じてこのグローバル制約を自然に強制します。
