 ## 解決策
 ## 問題の理解

 (n) 人の友達がいて、それぞれの友達は異なるサイズの T シャツを望んでいます。 Monocarp は友達ごとに 1 つのコンテストに参加し、その友達のサイズを正確に要求します。 各コンテストは独立して 1 枚のシャツを作成しますが、納品されるサイズは 1 つ移動する可能性があります。(x) のリクエストは確率 (p) で (x-1) を生成し、確率 (q) で (x+1) を生成し、確率 (r=1-p-q) で (x) 自体を生成します。 

すべてのコンテストの後、少なくとも 1 枚の配送されたシャツがその友人が要求したサイズである場合、その友人はシャツを受け取ります。 シャツを受け取る予定の数の友人が必要です。 

重要な点は、要求されたサイズが異なることです。 固定の要求サイズ (x) の場合、サイズ (x) のシャツを作成できるコンテストは 3 つだけです。(x) を要求するコンテスト、(x-1) を要求するコンテスト、および (x+1) を要求するコンテストです。 すべての配信でリクエストされたサイズが最大 1 だけ変更されるため、他のリクエストは (x) に到達できません。 

制約 (n\le 2\cdot10^5) は、すべてのサブセットやすべての可能な配信結果はもちろんのこと、サイズのペアを考慮するメソッドを除外します。 (O(n^2)) であっても、最悪の場合はおよそ (4\cdot10^{10}) 回の操作を意味し、2 秒の制限をはるかに超えます。 サイズ自体は (10^9) まで大きくなる可能性があるため、サイズでインデックス付けされた配列を割り当てることはできません。 (n) 個の異なるサイズを並べ替えてからそれらをスキャンするのが自然な目標であり、(O(n\log n)) が得られます。 

いくつかの特殊なケースは、誤って処理されやすいものです。 (n=1) の場合、隣接するリクエストがないため、答えは単純に (r) になります。 たとえば、入力の場合`1 250000 250000`そしてサイズ`7`、唯一のコンテストが確率 (1/2) でサイズ (7) を配信するため、期待される数は (1) ではなく (1/2) です。 

2 番目の罠は、隣接するコンテストは独立しているものの、成功イベントは相互に排他的ではないということです。 たとえば、リクエスト (1,2) および (p=q=1/2) の場合、正確な配信確率はありません。 (2) を要求しているコンテストが下に移動した場合、サイズ (1) の友人はシャツを受け取ります (確率は 1/2)。また、サイズ (2) の友人は、(1) を要求しているコンテストが上に移動した場合、同じく確率 (1/2) でシャツを受け取ります。 予想される答えはまさに (1) です。 重複を考慮せずに不注意に確率を含めるのは、一般的なケースでは誤りです。 

3 番目の罠は、厳密に 1 つの違いだけが問題になるということです。 入力あり`3 500000 500000`そして要求されたサイズ`1 3 5`、すべてのコンテストは常に要求されたサイズを変更しますが、他の要求されたサイズのいずれかを生成できるコンテストはありません。 (r=0) なので、配られる期待数は (0) です。 近くのサイズを原因の可能性があるものとして扱うと、不正確な答えが生成されます。 

最後に、このステートメントは、要求されたすべてのサイズが異なることを保証します。 したがって、「すべて等しい値」テストは、この問題に対する有効なテスト ケースではありません。 実装は重複した値を使用して防御的にテストされる可能性がありますが、正当性の引数や期待される出力がそのような入力に依存すべきではありません。 

## アプローチ

 最も直接的な強引なアプローチは、すべてのコンテストで考えられるすべての結果を列挙することです。 各コンテストには 3 つの可能な配信サイズがあるため、(3^n) 通りの結果の組み合わせが考えられます。 すべての組み合わせについて、納品されたシャツの中で要求されたサイズが何個出現するかを数え、その数に組み合わせの確率を掛けることができます。 これは文字通り確率空間全体を列挙するため正しいですが、結果のチェックに (O(n)) かかる場合は、(O(n3^n)) 個の作業が必要になります。 (n=2\cdot10^5) では、結果の数だけでも天文学的に大きくなります。 

成功した友人の最終的な数は、個々のゼロ 1 指標の合計として記述できるため、総当り攻撃が機能します。 この観察により、期待値の線形性を利用できるようになります。 複数の友人が同時に成功する確率は必要ありません。 個々の友人の成功確率だけが必要です。 

サイズ (x) を要求している友人を修正します。 (L) はサイズ (x-1) も要求されることを意味し、(R) はサイズ (x+1) も要求されることを意味します。 (x) を要求するコンテストは、確率 (r=1-p-q) で希望のサイズを生成します。 (x-1) が要求された場合、そのコンテストは確率 (q) で (x) を生成します。 (x+1) が要求された場合、そのコンテストは確率 (p) で (x) を生成します。 

補数を計算する方が簡単です。 友人がサイズ (x) のシャツを受け取ることができないのは、(x) を要求しているコンテストで (x) が生成されず、(x-1) を要求している可能性のあるコンテストが (x) に上がらず、(x+1) を要求している可能性のあるコンテストが (x) に下降していない場合に限られます。 これらのイベントは別のコンテストに関係しているため、独立しています。 

その結果、

 r\cdot
 \begin{ケース}
 1-q,&x-1\text{ が要求されています},\
 1,&\text{そうでない場合}
 \end{ケース}
 \cdot
 \begin{ケース}
 1-p,&x+1\text{ が要求されています},\
 1,&\text{そうでない場合}。 
\end{ケース}
 】

 したがって、成功確率は 1 からこの積を引いたものになります。 

残っている唯一のタスクは、要求されたサイズのセット内に (x-1) と (x+1) が存在するかどうかを判断することです。 並べ替え後、これらのチェックには前と次の要素のみが含まれます。 すべてのサイズは異なるため、前に並べ替えられた値が (x-1) と等しい場合は (x-1) が存在し、次に並べ替えられた値が (x+1) と等しい場合は (x+1) が存在します。 これにより、ソート後の確率計算全体が 1 回の線形スキャンに減ります。 同じ期待値の線形性と局所的隣接観測は、この問題の標準的な解決策の基礎でもあります。

 ## アルゴリズムのチュートリアル

1. (n,P,Q) を読み取り、(10^6) の逆モジュラを乗算して、(P,Q) をモジュラ確率 (p,q) に変換します。 (r=1-p-q) を設定します。 必要な出力がモジュロで表現された期待値 (998244353) であるため、モジュラー演算は有効です。 
2. 要求されたサイズを並べ替えます。 正確な値 (x-1) と (x+1) が発生するかどうかだけを知る必要があり、並べ替えにより、各 (x) について両方のチェックが一定時間行われます。 
3. ソートされたサイズ (x) ごとに、前の要素が正確に (x-1) であるかどうかを判断します。 そうである場合、(x-1) を要求するコンテストはサイズ (x) のシャツを作成でき、その失敗確率は (1-q) になります。 
4. 次の要素が正確に (x+1) であるかどうかを判断します。 そうである場合、(x+1) を要求するコンテストはサイズ (x) のシャツを作成でき、その失敗確率は (1-p) です。 
5. 友人 (x) が何も受け取らない確率を計算します。 (x) を要求するコンテストは (x) を生成できないはずなので、(r) から始めます。 左の近傍が存在する場合は (1-q) を乗算し、右の近傍が存在する場合は (1-p) を乗算します。 
6. 答えに (1-\text{failure}) を追加します。 これは、期待値の線形性によって正当化されます。(I_x) が、(x) をリクエストした友人がシャツを受け取る指標である場合、成功した友人の総数は (\sum I_x) となるため、その期待値は個々の確率の合計になります。 
7. 累積値のモジュロ (998244353) を出力します。 すべての確率分母は (10^6) のべき乗であり、(10^6) は可逆モジュロ (998244353) であるため、モジュラー表現は明確に定義されています。 

### なぜ効果があるのか

 アルゴリズムは、要求されたサイズ (x) ごとに、配送されたシャツのサイズ (x) が存在しない確率を正確に計算します。 このようなシャツのソースとして考えられるのは、(x-1)、(x)、および (x+1) を要求するコンテストの 3 つだけです。 対応する失敗イベントは異なるコンテストに属し、独立しているため、失敗確率を乗算すると、友人 (x) が何も受け取らない正確な確率が得られます。 その補数を取得すると、この友人がサービスを受ける正確な確率が得られます。 すべての友人についてこれらの確率を合計すると、期待の線形性により、サービスを受けた友人の予想総数が得られます。 したがって、アルゴリズムによって追加されたすべての項は 1 人の友人に正確に対応し、最終的な合計が必要な期待値となります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353
INV_MILLION = pow(10**6, MOD - 2, MOD)

def solve():
    n, P, Q = map(int, input().split())
    a = list(map(int, input().split()))
    a.sort()

    p = P * INV_MILLION % MOD
    q = Q * INV_MILLION % MOD
    r = (1 - p - q) % MOD

    ans = 0

    for i, x in enumerate(a):
        fail = r

        if i > 0 and a[i - 1] == x - 1:
            fail = fail * (1 - q) % MOD

        if i + 1 < n and a[i + 1] == x + 1:
            fail = fail * (1 - p) % MOD

        ans = (ans + 1 - fail) % MOD

    print(ans)

if __name__ == "__main__":
    solve()
```最初のモジュラー演算は、フェルマーの小定理を使用して (10^6{}^{-1}) を計算します。 (998244353) は素数であり、(10^6) はそれで割り切れないため、逆数が存在します。 次に、(p=P/10^6)、(q=Q/10^6)、および (r=1-p-q) を有限体で直接取得します。 

並べ替えは、アルゴリズムの唯一の非線形部分です。 サイズがソートされると、インデックス (i) の要素についてのみ、`a[i - 1]`そして`a[i + 1]`関連する可能性があります。 境界チェック`i > 0`そして`i + 1 < n`配列外へのアクセスを防止します。 

(x-1) を要求するコンテストが確率 (q) で (x) に到達するため、左隣は (1-q) の係数に寄与します。 (x+1) の要求は確率 (p) で下に移動するため、右隣は (1-p) に寄与します。 これら 2 つの確率を逆にすることは、間違った答えの一般的な原因です。 

変数`fail`(r) から始まり、(x) を要求するコンテスト自体がサイズ (x) を与えない確率です。 隣接障害係数を乗算すると、考えられるすべてのソースが失敗する確率 (x) が求められます。 コードは次に追加します`1 - fail`、まさにこの友人にとって望ましい確率です。 

確率を変換した後のすべての算術は、モジュロ (998244353) で実行されます。 Python の整数はオーバーフローしないため、整数幅に関する追加の懸念はありません。 表現`(1 - fail) % MOD`は最後のモジュール加算によって処理され、これによって答えも正規化されます。
