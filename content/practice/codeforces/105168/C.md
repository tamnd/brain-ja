 ## 解決策
 ## 問題の理解

 私たちには次のようなシステムが与えられています$n$ランプと$n$1 から 1 までのインデックスが付けられたボタン$n$。 すべてのランプが消灯し始めます。 ボタンを押す$i$インデックスが次の値で割り切れるすべてのランプの状態を反転します。$i$したがって、ローカル セグメントではなく、ランプ上の通常の算術構造に影響します。 

各ボタンは最大 1 回使用され、空ではないボタンのセットを選択して押すように求められます。 さらに、有向依存関係ルールがあります: ボタンを押した場合$u$、次に ボタン$v$も押す必要があります。 これらのルールは暗示のように動作するため、ボタンを選択すると、他のボタンのカスケード全体が強制される可能性があります。 

セットを選択し、すべてのトグルを適用した後、最終的に点灯するランプの数を確認します。 要件は、この数値を超えないことです。$\lfloor \sqrt{n} \rfloor$。 有効な選択が存在しない場合は、不可能であることを報告する必要があります。 

制約により、最大で$2 \cdot 10^5$すべてのテスト ケースにわたってランプを使用するため、すべてのソリューションはテスト ケースごとに線形または線形演算に近い必要があります。 ボタンのサブセットの列挙を伴うものは直ちに実行不可能です。$2^n$成長が早すぎる。 構造を持たずに任意のサブセットのエフェクトをシミュレートしても、各ボタンは最大で影響を与える可能性があるため、遅すぎます。$O(n)$ランプ。 

依存関係のルールに微妙な問題が生じます。 単純なアプローチでは、トグル効果のみに基づいて「良い」ボタンを選択しようとする可能性がありますが、強制的な包含は無視されます。 これにより、正しさが損なわれる可能性があります。 

たとえば、ボタン 5 を押すとボタン 1 が強制的に押され、ボタン 1 がすべてのランプに影響を与えるという小さな例を想定します。 影響を与えるランプが少ないため、5 だけでも適切に見えますが、1 を強制的に含めると突然すべてのランプが反転し、制約が破壊されます。 これは、実現可能性がグラフ構造と選択したインデックスの算術効果に共同で依存することを示しています。 

影響の小さいボタンを複数選択するほうが常に良いと仮定した場合、別の失敗例が発生します。 依存関係により多くの追加ボタンの組み込みが強制される可能性があり、最終的な効果は予想よりもはるかに大きくなります。 

## アプローチ

 ブルートフォース戦略では、ボタンのすべてのサブセットを試し、各サブセットの強制依存関係を伝播し、押されたボタンの結果のセットを計算し、すべてのランプの切り替えをシミュレートします。 サブセットごとにコストを切り替える$O(n \log n)$または$O(n)$可分性マーキングを使用して慎重に行う場合。 あるので$2^n$サブセットの場合、このアプローチは非常に小さい場合でも実行不可能です。$n$。 

重要な構造的観察は、依存関係がボタン上の有向グラフを形成し、有効な選択はすべて出力エッジの下で閉じられる必要があるということです。ノードを選択する場合は、そこから到達可能なすべてのものも選択する必要があります。 これは、すべての有効なソリューションは、到達可能性の下で安定したセットを選択することによって効果的に決定されることを意味します。 

任意のサブセットの観点から考える代わりに、追加を強制しないノードに焦点を移します。 グラフ用語では、これらは出力エッジのないノードです。そのようなノードを選択しても、それ自体を超える追加の選択が強制されないからです。 このようなノードは、「安全な端末の選択」のように動作します。 

単一ボタンの選択肢に減らすと、切り替え構造がシンプルになります。 ボタンのみを選択する$i$正確に次の倍数をオンにします$i$, したがって、点灯しているランプの数は次のようになります。$\left\lfloor \frac{n}{i} \right\rfloor$。 制約を満たすには、この量が最大でも次の値である必要があります。$\lfloor \sqrt{n} \rfloor$、これはインデックスを選択するのと同じです$i \ge \sqrt{n}$。 

したがって、問題は、発信依存関係がなく、十分に大きなインデックスを備えたノードを見つけることに帰着します。 そのようなノードが存在する場合は、それを出力します。 そうしないと、すべての安全なノードが小さすぎるか、すべてのノードが追加の選択肢を強制し、必要な範囲内で点灯するランプの数を制御できなくなります。

 ## アルゴリズムのチュートリアル

 1. 各制約が含まれる有向グラフを構築します。$u \rightarrow v$押すという意味です$u$力で押す$v$。 同時に、すべてのノードの出次数を計算します。 
2. 出次数が 0 に等しいすべてのノードを特定します。 これらのノードは、それ自体を超える追加のボタンを強制しないため、それらの 1 つを選択すると、選択したセットの意図しない展開が回避されます。 
3. 閾値を計算する$B = \lfloor \sqrt{n} \rfloor$。 選択した単一のボタン$i$正確に生成します$\lfloor n/i \rfloor$点灯したランプ。 
4. 出次数が 0 のノードから任意のノードを選択します$i$そのような$i \ge B$。 これにより、ランプ数の制約が確実に満たされます。 
5. そのようなノードが存在する場合は、出力$k = 1$そして選択したインデックス$i$。 そのようなノードが存在しない場合は、出力$-1$。 

### なぜ効果があるのか

 依存関係グラフでは、選択したノードがそこから到達可能なすべてのノードに確実にドラッグされるため、有効なソリューションは到達可能性の下で閉じられる必要があります。 出次数が 0 のノードは他のノードを強制できないため、それを選択しても追加の制約は発生しません。 したがって、そのような単一のノードを選択することは常に一貫しています。 

ボタンひとつでランプ効果が得られる$i$は割り算によって完全に決まります: の倍数のみです。$i$が切り替わります。 そのようなランプの数は正確に$\lfloor n/i \rfloor$、次の場合に最大化されます。$i$小さいです。 に限定することで、$i \ge \sqrt{n}$、私たちは最大で保証します$\sqrt{n}$ランプが影響を受けます。 ボタンを 1 つだけ使用するため、切り替え間の相互作用はなく、最終状態はこのカウントと正確に一致します。 

適切なノードが存在しない場合、各ノードは追加の選択を強制するか、切り替えられるランプの数を必要な範囲内に維持するには小さすぎるため、制約の下では有効な構造を形成できません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    outdeg = [0] * (n + 1)
    
    for _ in range(m):
        u, v = map(int, input().split())
        outdeg[u] += 1

    limit = int(n ** 0.5)

    for i in range(1, n + 1):
        if outdeg[i] == 0 and i >= limit:
            print(1)
            print(i)
            return

    print(-1)

if __name__ == "__main__":
    t = int(input())
    for _ in range(t):
        solve()
```単一ノード構築下での実現可能性に関して重要なのは出力エッジの存在のみであるため、この実装では出力依存関係の数のみが追跡されます。 隣接リストを保存する必要がないため、メモリ使用量が最小限に抑えられます。 

平方根のしきい値はテスト ケースごとに 1 回計算され、スキャンは線形です。$n$。 これにより、全体的な制約の下でもソリューションの効率性が維持されます。 

実装でよくある落とし穴は、出力エッジのみが重要であるということを忘れていることです。 入力エッジは強制的な追加をトリガーしないため、何を選択する必要があるかを制限しません。 

## 実用的な例

 小さなケースを考えてみましょう。$n = 4$そして依存関係は$4 \rightarrow 3$そして$1 \rightarrow 2$。 

出次数を計算し、出次数がゼロのノードを特定します。 

| ノード | 出次数 | 候補者？ | アクション |
 | --- | --- | --- | --- |
 | 1 | 1 | いいえ | フォース 2 |
 | 2 | 0 | はい | 小さすぎる |
 | 3 | 0 | はい | しきい値をチェック |
 | 4 | 1 | いいえ | フォース 3 |

 ここ$\lfloor \sqrt{4} \rfloor = 2$したがって、ノード 3 は有効です。 3 を選択すると、制限を満たすランプ 3 のみが切り替わります。 

このトレースは、依存関係フィルターによって問題が、組み合わせを探索するのではなく、小さな候補セットのみをチェックするように軽減される様子を示しています。 

ここで考えてみましょう$n = 10$エッジがまったくありません。 

| ノード | 出次数 | 候補者？ | アクション |
 | --- | --- | --- | --- |
 | 1-10 | 0 | はい | 3 つ以上のいずれかを選択します |

 以来$\lfloor \sqrt{10} \rfloor = 3$、ノード 3 以降のいずれかが有効です。 たとえば、5 を選択すると、ランプ 5 と 10 が切り替わり、正確に 2 つのランプが点灯します。 

これは、制約がない場合、解は純粋に割り算の算術構造に依存することを示しています。

 ## 特殊なケース

 重大なエッジ ケースは、すべてのノードに少なくとも 1 つの送信依存関係がある場合です。 そのような状況では、単一の安定したノードを選択する方法はありません。 たとえば、入力では$1 \rightarrow 2, 2 \rightarrow 1$、両方のノードが相互に強制するため、どちらかを選択するとすぐにもう一方がトリガーされ、シングルトン ソリューションが存在しないことを意味します。 アルゴリズムは正しく出力します$-1$出次数ゼロのノードがないためです。 

もう 1 つのケースは、出次数ゼロのノードが存在するものの、すべてが小さすぎる場合です。 たとえば、次の場合$n = 16$そして唯一のターミナルノードは$i = 3$、 それから$\lfloor 16/3 \rfloor = 5$を超える$\lfloor \sqrt{16} \rfloor = 4$。 アルゴリズムはこのノードを拒否し、出力します。$-1$、グラフ制約が満たされている場合でも、算術制約を正しく処理します。
