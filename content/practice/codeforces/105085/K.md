 ## 問題の理解

 素数から派生した特定の無限シーケンスを扱うように求められます。 素数ではない 1 より大きい奇数の整数を考慮します。 これらの数値のうち、2 つの素数の和として記述できるものだけを保持します。 このフィルタリングされた増加リストは次のように呼ばれます。$G$。 タスクの形式は単純です: 各クエリ インデックスに対して$i$を出力する必要があります。$i$の - 番目の要素$G$。 

入力は、最大 500,000 のクエリのシーケンスです。 各クエリは、この事前計算されたシーケンス内の 1 つの位置を要求し、出力はその位置の対応する数値になります。 隠れた難しさは、シーケンスが明示的に制限されていないため、要求された最大のインデックスに応えるのに十分な範囲でシーケンスを生成する必要があることです。 

この制約により、クエリごとの素数テストや分解検索が直ちに除外されます。 数百万までの素数チェックを繰り返し行う場合でも、500,000 回実行すると、すでに遅すぎます。 正しい方向は、素数を一度事前計算してから、シーケンスを段階的に構築することです。 

単純な間違いは、すべての素数のペアをチェックすることによって、各奇数のゴールドバッハのような条件を個別に検証しようとすることから発生します。 100,000 のような数値の場合、候補ごとに数千の素数を繰り返す必要があり、検索空間全体で二次関数の動作が発生します。 もう 1 つの微妙な失敗モードは、ふるいを再利用する代わりにクエリごとに素数を繰り返し生成することです。これにより、同じ構造の再計算が繰り返し行われます。 

エッジ ケースには、構造が始まる 9、15、21 などの小さな数値、および 27 は奇数で合成であるにもかかわらず、2 つの素数の合計として表現できないため明示的に除外されるという事実が含まれます。 このことから、すべての奇数複合が適格であるわけではないため、「一部の例外を除いてすべての奇数複合」のような直接的な算術ショートカットは信頼できないことがわかります。 

## アプローチ

 ブルートフォース戦略は、9 から始まる奇数を繰り返し、各数値について、合計がそれに等しい素数のペアが存在するかどうかを確認することです。 これには、現在の値までのすべての数値の素数テストに加えて、素数ペアの検索が必要です。 素数を事前に計算したとしても、各候補をチェックするには、最大で素数を反復する必要があります。$n/2$。 500,000 番目の有効な数値を見つける必要があり、値が数百万に及ぶ場合、このアプローチは次のように実行されます。$10^{10}$に$10^{11}$プリミティブチェックは実行不可能です。 

重要な観察は、素数性と「2 つの素数の合計」はどちらも、ふるいを使用して制限された範囲にわたって事前に計算できるプロパティであるということです。 少なくとも 500,000 個の有効な数値を含むのに十分な大きさの上限を決定したら、エラトステネスの篩を使用してすべての素数を事前に計算し、どの奇数の合成数が 2 つの素数の合計として表現できるかをマークできます。 この前処理の後、シーケンスを構築します$G$は、定数時間のメンバーシップ チェックを伴う単なる線形スキャンです。 

重要な構造の簡素化は、素数の和として表現をチェックするという高価な部分を、クエリごとに繰り返し検索する代わりに、ふるいを使った畳み込みのようなマーキング プロセスに変換できることです。

 ## アルゴリズムのチュートリアル

 まず世代の上限を決めます。 最大 500,000 の有効な数値が必要であり、それらは奇数の複合値の中に現れるため、実際には数百万程度の安全なふるい分けで十分です。 固定制限を選択し、すべてのクエリを快適にカバーできるようにします。 

1. 選択した限度までエラトステネスのふるいを作成し、すべての素数にマークを付けます。 これにより、後で定数時間の素数チェックが行われます。 これが必要な理由は、ペアの構築中に素数性を繰り返しテストするため、再計算するとコストが高すぎるためです。 
2. すべての素数のリストを配列に抽出します。 これにより、合計を計算するときに主要な候補を直接反復することができます。 
3. ブール配列を作成する`ok[x]`すべての値が false に初期化されます。 これにより、奇数の合成数が 2 つの素数の合計として表現できるかどうかがマークされます。 
4. 各素数について$p$、素数を反復処理する$q \ge p$そのような$p + q < \text{limit}$。 マーク`ok[p+q] = true`。 このステップでは、2 つの素数の合計として表現できるすべての数値を効果的に記録します。 合計が制限を超えると、不必要な作業を避けるために早期に停止します。 
5. 9 から始まる奇数を繰り返します。各数値について、それが素数でないかどうかを確認し、`ok[x]`それは本当です。 その場合は、シーケンスに追加します$G$。 
6. 500,000 個の要素を収集したら停止します。 それらを配列に格納すると、各クエリが O(1) で回答できるようになります。 

この構成で十分である理由は、すべての有効な表現がペアの列挙中に 1 回だけ検出され、多重性ではなく存在のみを考慮するためです。 

### なぜ効果があるのか

 ふるいは正しい素数分類を保証します。 すべての合計$p+q$少なくとも 1 つの有効な素数ペアに対応するとマークします。 すべての素数ペアを列挙するので、$p \le q$、表現可能なすべての数値が最終的にマークされます。 奇数の合成数のみをフィルタリングすることで、次の定義と一致することが保証されます。$G$。 数値の昇順でシーケンスを構築するため、格納された配列には正しいインデックスが保持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

LIMIT = 2_000_000

is_prime = [True] * (LIMIT + 1)
is_prime[0] = is_prime[1] = False

for i in range(2, int(LIMIT ** 0.5) + 1):
    if is_prime[i]:
        step = i
        start = i * i
        for j in range(start, LIMIT + 1, step):
            is_prime[j] = False

primes = [i for i in range(2, LIMIT + 1) if is_prime[i]]

ok = [False] * (LIMIT + 1)

for i, p in enumerate(primes):
    for q in primes[i:]:
        s = p + q
        if s > LIMIT:
            break
        ok[s] = True

G = []
for x in range(9, LIMIT + 1, 2):
    if x <= LIMIT and not is_prime[x] and ok[x]:
        G.append(x)
        if len(G) >= 500000:
            break

C = int(input())
for _ in range(C):
    i = int(input())
    print(G[i - 1])
```ふるいセクションは標準であり、主要な設計選択は素数の生成とペアのマーキングを分離することです。 これにより、素数チェックの繰り返しが回避されます。 素数に対する二重ループは、合計が制限を超えたときに早期に中断することによって最適化されます。これは、時間内に構築を維持するために不可欠です。 

の建設`G`両方の条件を直接適用します: 非素数、および 2 つの素数の合計として表現可能。 インデックス調整`i - 1`問題ステートメントではシーケンスが 1 から始まるため、必須です。

 ## 特殊なケース

 最初の微妙なケースはシーケンスの開始時です。 最初の有効な数値は、3、5、7 ではなく 9 です。ふるいは 3、5、7 を素数としてマークするため、アルゴリズムはこれを自然に処理し、シーケンスの構築が開始される前に除外されます。 9 からスキャンすると、最初のヒットが正しくキャプチャされます。 

もう 1 つのエッジ ケースは、27 など、奇数の合成であるが 2 つの素数の合計として表現できない数値です。構築中、27 は残ります。`not ok`素数のペアの和が存在しないからです。 マーキングステップが設定されない`ok[27]`true なので、「奇数および非素数」フィルターを通過してもスキップされます。 これにより、フィルタリング ロジックの正確さが保証されます。 

最後のエッジ ケースは、特に多くのクエリが大きなインデックスを要求する場合のクエリ分散です。 シーケンスは最大 500,000 要素まで 1 回事前計算されるため、各クエリは単純に配列インデックスにアクセスします。 再計算やクエリ順序への依存がないため、最悪の場合の入力順序であっても正確性やパフォーマンスに影響を与えません。
