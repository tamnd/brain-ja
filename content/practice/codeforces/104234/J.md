 ## 解決策
 ## 問題の理解

 私たちは、独立した賭けというよりも、制限された「タイムトラベル」リセットを備えた制御されたステートマシンのように動作する、制約されたギャンブルプロセスをシミュレートしています。 

プリンスは 1 枚のコインから開始し、正確に通過する必要があります`n`ベッティングラウンド。 各ラウンドで、彼は賭け金 (少なくとも 1 コイン) と公平な 50-50 ルーレットのサイドを選択します。 勝つと賭け金が2倍になり、負けると賭け金が減ります。 ツイストは、賭けの結果を見た後、その賭けの直前に時間を巻き戻し、別の方法で再プレイできることです。 このロールバックは以下に限定されます`m`合計で使用され、ロールバック後に賭けをやり直すと追加のラウンドは消費されません。 

目標は、すべてを失うことを避けることだけではありません。 彼は、すべてのことを行う前に、それを保証しなければなりません。`n`賭けが必要な場合、彼は合法的な賭けが可能であるように少なくとも 1 枚のコインを利用可能です。 この生存制約を満たすすべての戦略の中で、予想される最終的なコイン数を最大化したいと考えています。 生存が保証できない場合、答えは「破産」です。 

重要な問題は、ロールバックによってリスクの構造が根本的に変化してしまうことです。 負けた結果が必ずしも最終的なものであるとは限りませんが、修復できる損失の数は限られています。 これにより、問題は単なる賭けの期待値ではなく、最悪の場合の損失シーケンスに関する推論に変わります。 

制約が意味するのは、`n`そして`m`どちらも最大です`10^5`、合計で`m`テストケース全体で最大`10^6`。 どのようなソリューションも、テスト ケースごとに本質的に線形である必要があります。 これにより、「コイン × ラウンド × ロールバック数」のような状態に対する動的プログラミングは即座に除外されます。これは、コインの値に制限がなく、確率的分岐が爆発的に発生するためです。 

微妙なエッジケースが現れるのは、`m`に比べて小さいです`n`。 ロールバックが不十分な場合、敵対的な一連の損失により、プリンスが賭けなければならないが、コインが残っておらず、取り戻すためのロールバックが存在しないという状況が強制される可能性があります。 たとえば、次の場合`n = 3`そして`m = 0`、次の必要な賭けの前に状態を修復する方法がないため、最初の賭けで損失が発生すると、即座に失敗につながります。 

もう 1 つのエッジ ケースは、非常に特殊なタイミング パターンでロールバックが使用される場合に限り、損失から回復することが技術的に可能である場合です。 これにより、貪欲な「常に 1 コインを賭ける」戦略は無効になります。これは、最悪の場合の枯渇経路が考慮されていないためです。 

## アプローチ

 ブルートフォース解釈では、勝ちと負けのあらゆる可能なシーケンスをシミュレートし、各ステップでのコイン数とロールバックの使用状況を追跡しようとします。 各ベットで勝ちか負けに分岐し、オプションでロールバックの決定を適用します。 これにより、各ノードが結果と巻き戻しの可能な履歴を表す巨大な状態ツリーが構築されます。 枝刈りを行っても、到達可能な状態の数は指数関数的に増加します。`n`, 各ベットは分岐係数を 2 倍にし、ロールバックでは追加の組み合わせの選択肢が導入されるためです。 

重要な単純化は、確率と実現可能性を分離することから生まれます。 ロールバックは期待ツールではなく、生存を保証するツールです。 これにより、プレーヤーは効果的に最大まで「消去」できるようになります。`m`つまり、システムが回復不能になる前にどれだけの損失を許容できるかだけを気にすることになります。 

このように考えると、問題は、プロセスのどのプレフィックスにおいても、避けられない損失の数が利用可能な回復能力を決して超えないようにすることになります。 各ロールバックは、必要な賭けの前にコインがゼロになるという壊滅的な赤字イベントを修復するものと考えることができます。 

これは構造的な観察につながります。ゲームは次の場合にのみ保証されます。`n`初期リソースが、各障害がロールバック容量を消費する最悪の一連の障害に耐えられるかどうかに賭けます。その後、残りの構造は決定論的な成長プロセスのように動作します。 

最適な戦略は、維持の実現可能性の確認に集約されます。`n`最悪の場合の損失圧力下でのステップを実行し、可能であれば、分岐シミュレーションに依存しない決定論的な期待成長を計算します。

 ## アルゴリズムのチュートリアル

 重要なアイデアは、ロールバックを「破産の瞬間からのリセット」の制限された数として再解釈することです。 このシステムは、必要な賭けの前に、コインのカウントがゼロで、以前に選択した賭けを修復するためのロールバックが残っていない場合にのみ無効になります。 

私たちは、最悪の場合の結果の下で可能な最小のコイン軌道を追跡することによってプロセスをモデル化します。 常に負けている場合、各賭けはコインプールを減らします。 ロールバックを使用すると、そのような崩壊を回復に変換でき、ロールバックを犠牲にして利用可能なリソースを効果的に 2 倍にすることができます。 

## アルゴリズムのチュートリアル

 1. 最悪の場合の動作で各ベットがリソースを減らし、強制ゼロコイン状態が現れた場合にのみロールバックが役立つことに注目してください。 これは、ロールバック容量が消費されるのは、通常のプレイ中ではなく、軌道が無効になった場合のみであることを意味します。 
2. 次の順序を検討します。`n`すべての賭けは損失であるという前提の下で賭けます。 これにより、コインが毎回ベット額ずつ減少する決定的な減少パスが生成されます。 実現可能性の問題は、ステップの前にゼロに達することを回避できるかどうかになります。`n`せいぜい使用`m`修理。 
3. 各ロールバックは、1 つの障害イベントを「修復」し、システムを以前の安全な状態に効果的に復元し、有効資本を増やして継続できるようにするものと解釈できます。 つまり、ロールバックは、壊滅的なドロップをキャンセルするための限られた予算のように機能します。 
4. 最悪の場合の軌道における不可避の崩壊点の数が以下の場合、システムは実現可能になります。`m`。 崩壊はコイン数がゼロに達した場合にのみ発生する可能性があるため、この構造は、勝利による初期の成長が最悪の場合の損失を相殺できることを保証することになります。 
5. 実現可能性が保証されると、期待値は標準的な公正なベッティングの増加にまで減少します。 各ベットは期待における期待寄与を 2 倍にするため、最終期待値は残存資本に対して線形回帰のように動作します。 
6. まず最悪の場合の枯渇の貪欲なシミュレーションを使用して実現可能性を計算し、破産を防ぐために何回ロールバックが必要になるかを追跡します。 これを超えると`m`、「破産」と出力されます。 
7. それ以外の場合は、ベットを繰り返して期待値の更新を適用することで期待値を計算します。`E = E + 0.5 * bet`、`E = E + 0.5 * (-bet)`この構造により、最適なロールバック使用下での決定的な倍加動作が簡素化されます。 

### なぜ効果があるのか

 不変条件は、ロールバックはプロセスが未定義になるポイント (必要なベットの前にコインがゼロ) でのみ消費されるということです。 各ベットが対称的であるため、このようなポイント間では、プロセスは期待に基づいて決定論的に動作します。 ロールバックの使用には制限があるため、唯一の意味のある制約は、最悪のパスが利用可能なロールバック バジェットよりも多くの障害イベントを生成するかどうかです。 その制約が満たされると、期待値はパスの分岐とは関係なく、公平な 2 倍化の線形期待値のみに依存します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 9

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())

        # feasibility check: minimal interpretation of collapse events
        # each rollback can fix at most one forced bankruptcy event
        # worst case requires n-1 repairs if structure is linear
        if m < n - 1:
            print("bankrupt")
            continue

        # if feasible, expected growth reduces to doubling each step
        # starting from 1 coin
        ans = 1
        for _ in range(n):
            ans = (ans * 2) % MOD

        print(ans)

if __name__ == "__main__":
    solve()
```実現可能性チェックは、十分なロールバックがなければ、完全に負けた軌道により、必要なベットがすべて完了する前に無効な状態が繰り返されるという考えに対応しています。 条件`m < n - 1`最初の障害カスケード後の各ステップの修復が必要となる最悪のケースを示しています。 

2 番目の部分では、最適なプレイの下で期待される結果を計算します。 各賭けは公平であり、ロールバックによってプロセスの存続が保証されるため、現在の資本が繰り返し 2 倍になるにつれて期待値が進化し、それは反復によるべき乗モジュラーとして実装されます。

import sys, io

def solve():
    input = sys.stdin.readline

    out = sys.stdout.getvalue()
    sys.stdin = old_stdin
    sys.stdout = old_stdout

 ## 特殊なケース

 重大なエッジケースは次のような場合です。`n = 1`。 この状況では、複数のベットにわたって回復するシーケンスがないため、ロールバックは必要ありません。 アルゴリズムは、次の条件に関係なくこれを実行可能として正しく処理します。`m`、期待値は次のようになります`2`、単一の公正な賭けで期待値が 2 倍になることを反映しています。 

別のエッジケースが発生するのは次の場合です。`m = 0`そして`n > 1`。 ここで、複数回の賭けを生き残るには、修復できない損失の連鎖から回復する必要があります。 実行可能性チェックでは、このケースは即座に拒否され、シーケンスの早い段階で 1 つの不運な結果が発生すると完了が不可能になるという事実と一致します。 

最後に、いつ`m >= n - 1`、システムは完全に存続可能な状態に移行し、最悪の場合の軌道で発生する可能性のあるすべての崩壊をロールバックで十分に修復できます。 この体制では、すべてのランダム性が期待値に吸収され、最終結果は繰り返しの 2 倍化にのみ依存します。`n`ステップ。
