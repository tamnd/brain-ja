 ## 解決策
 ## 問題の理解

 文字列のシーケンスが与えられるので、最初は空の文字列にそれらを 1 つずつ挿入する必要があります。 新しい文字列はそれぞれ、現在の結果の左端または右端に配置できます。 すべての挿入の後、単一の最終文字列が得られます。 私たちの仕事は、この最終的な文字列がすべての可能な選択肢の中で辞書編集的に最小になるように、挿入の方向を選択することです。 

重要な問題は、それぞれの決定が将来の構造に世界的な影響を与えることです。 局所的に見栄えの良い選択をすると、後でより良い配置が妨げられる可能性があります。これは、文字列が側面に配置されると、その内部の文字が構造の残りの部分に対して固定されるためです。 

制約は文字列の数の点で小さく、テストごとに最大 1000、合計の長さは最大 4000 です。これにより、方向の 2^n の割り当てをすべて試行するアプローチは即座に除外されます。 2^1000ですら全く実現不可能です。 したがって、局所的に最適なルールを使用して各文字列を一度配置する貪欲な決定プロセスを探しています。 

微妙なエッジケースは、同一の文字列または長いプレフィックスを共有する文字列から発生します。 たとえば、次のような文字列がある場合、`"ab"`そして`"aa"`、配置`"ab"`左と右では、最終的な辞書編集の比較でどの文字が最初に比較されるかが変わります。 構築されたシーケンス全体の両方の方向を考慮せずに、単に文字列を独立して比較する単純なアプローチは失敗します。 

もう 1 つの特殊なケースは、複数の文字列が同じ文字で始まる場合です。 最終的な完全な連結を確認せずに最初の文字のみを比較する貪欲なルールでは、初期の配置が間違ってしまう可能性があります。これは、決定的な比較が連結されたブロックの内部のより深いところで行われる可能性があるためです。 

## アプローチ

 強引なアイデアは、左側または右側のいずれかへの各文字列の可能なすべての割り当てを試みることです。 2^n 構成ごとに、結果の文字列を構築し、辞書編集的に最小値を取得します。 これは、考えられるすべての結果を調査するため正しいですが、n では指数関数的であり、n = 1000 ですぐに失敗します。 

重要な点は、完全な候補文字列を構築する必要がないということです。 各ステップで、次の文字列を前に置くか後ろに置くかという 2 つの可能性のどちらかを決定するだけです。 最後の文字列はブロックの連結であるため、2 つの完全な結果間の辞書編集的な比較は、それらが異なる最初の位置に依存します。 その位置は、ブロックの 1 つの内側またはブロック間の境界に完全に存在する必要があります。 

これにより、問題は、文字列ごとに個別に貪欲な順序付けを決定することになります。文字列の配置を検討する場合`x`では、2 つの仮説的な結果、つまり最後に現在の結果 + x と、前にある x + 現在の結果を比較します。 両方の完全な文字列を構築する代わりに、どちらの連結が辞書編集的に小さいかを知るだけで済みます。 

重要な簡素化は、各ステップで安全に貪欲に決定できることです。`x`左または右で比較します`x + current`対`current + x`。 2 つのうちの小さい方が、このステップの最適な配置を決定します。 

これは、決定が将来の文字列に依存しないため機能します。将来の挿入では、どちらかの側にさらにブロックが追加されるだけですが、両方のブランチに対称的に影響します。 したがって、ステップ i で小さい方向を選択すると、その後の選択は、最初の異なる位置で確立された辞書編集的な順序を逆転させることはできません。

 ## アルゴリズムのチュートリアル

 現在の文字列を維持します`s`、最初は空です。 

1. から始める`s = ""`。 これは、挿入前の空の構造を表します。 前と後ろの挿入の両方で同じ結果が生成されるため、最初の文字列に対して行う決定はありません。 
2. 次の各文字列について`x`、考えられる 2 つの結果を検討してください。`x`前に与えます`x + s`、後ろに置くと、`s + x`。 
3. これら 2 つの候補文字列を辞書順に比較します。 辞書編集上の順序は、異なる最初のインデックスに依存するため、Python の文字列比較を使用して直接比較をシミュレートします。 
4. もし`x + s`小さくなりました、更新してください`s = x + s`。 それ以外の場合は設定`s = s + x`。 これにより、各文字列を処理した後、`s`は、処理された文字列のプレフィックスとして達成可能な最良の結果です。 
5. すべての文字列が処理されて出力されるまで続行します。`s`。 

これが機能する理由は、文字列を片側に配置すると、その後のすべての文字列は、2 つのオプション間の最初の不一致点を超えて結果を拡張するだけだからです。 この不一致点によって順序が永続的に決定されるため、以降の操作によってステップ i で確立された相対順序を変更することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        arr = input().split()

        s = ""

        for i in range(n):
            x = arr[i]

            # compare two possible placements
            if x + s < s + x:
                s = x + s
            else:
                s = s + x

        print(s)

if __name__ == "__main__":
    solve()
```実装は貪欲ルールに直接準拠します。 唯一重要な部分は比較です`x + s < s + x`これは、このステップで考えられる 2 つの最終状態間の辞書編集的な順序を正確にモデル化します。 

よくある間違いは、最初の文字または長さだけを比較しようとすることです。 決定文字がいずれかの文字列の奥深くに現れる可能性があるため、これは失敗します。 Python の文字列比較はすでに完全な辞書編集評価を正しく処理しているため、安全に信頼できます。

 ## 特殊なケース

 特殊なケースの 1 つは、すべての文字列が同一である場合です。 アルゴリズムは常に比較します`x + s`そして`s + x`、これらは等しいため、一貫して右側に追加されます。 これにより、曖昧さのない単純な連結が生成されます。 

もう 1 つのケースは、文字列が別の文字列のプレフィックスである場合です。 例えば、`"a"`そして`"ab"`配置に応じて、辞書編集上の結果が異なる場合があります。 アルゴリズムはこれを正しく解決します。`"ab" + "a" = "aba"`より大きい`"a" + "ab" = "aab"`、 それで`"a"`が最初に配置され、辞書編集上の最適性が維持されます。 

最後の微妙なケースは、小さい文字列と大きい文字列を交互に使用することです。 ローカル比較で逆転が示唆される場合でも、完全連結比較により、最初の異なる文字のみが配置を決定するため、以前の決定はグローバル辞書編集順序と一貫したままになります。
