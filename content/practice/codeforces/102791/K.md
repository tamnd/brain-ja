 ## 解決策
 ## 問題の理解

 私たちは銃を保持できるマガジンを持っています`k`弾丸。 がある`n`独立したモンスターウェーブ。 時とともに波が現れる`l_i`、含まれています`a_i`モンスター、そしてその波からのすべてのモンスターは遅くとも時間までに殺されなければなりません`r_i`。 波はすでに順序付けられており、重なり合うことはありませんが、次の波が始まるときにちょうど 1 つの波が終了する可能性があります。 

射撃は瞬時に行われるため、時間を消費する唯一のアクションはリロードです。 リロードには 1 単位の時間がかかり、現在のマガジンが完全なマガジンと交換され、残っている弾丸はすべて捨てられます。 目標は、モンスターに当たる弾を最小限に抑えるだけでなく、リロード時に失われる弾も最小限に抑えることです。 正常に完了したときにインベントリから残される弾丸の総数が最小である必要があります。 

ウェーブの数は最大 2000 までですが、時間とモンスターの数は最大 2000 に達する可能性があります。`10^9`。 単一の間隔は数十億の瞬間に及ぶ可能性があるため、これにより、あらゆる瞬間のシミュレーションが直ちに除外されます。 アン`O(n^2)`解決策は受け入れられます。`n`十分に小さいため、約 400 万の遷移を管理できます。 サイズに応じた解決策`l_i`または`r_i`実現不可能です。 

いくつかの詳細により、間違った解決策が失敗することがあります。 よくある間違いは、マガジンがいっぱいになるため、リロードが常に適切であると仮定することです。 例えば：```
1 10
5 6 6
```答えは`6`。 最初の数匹のモンスターを撃った後すぐにリロードする貪欲なアプローチは、有用な弾丸を捨てて消費する可能性があります`10`or more bullets.

 もう一つの罠は、波が触れる可能性があることを忘れていることです。 考慮する：```
2 3
2 3 6
3 4 3
```答えは`9`。 The second wave starts at the exact moment the first wave ends, so time`3`can be used for both finishing old monsters and preparing the next reload. Treating intervals as strictly separated loses a valid action.

 3 番目のエッジケースが最後のマガジンです。 例えば：```
1 10
100 111 1
```答えは`1`。 最後のマガジンに残った弾は戦闘後に破棄されないため、最後のリロードは無駄な弾としてカウントされません。 

## アプローチ

 直接的なアプローチは、可能なすべてのリロード スケジュールを決定することです。 ウェーブごとに、可能な限りのリロード回数と、それらを実行する可能なあらゆる時点を試すことができます。 間隔には次の値まで含めることができるため、可能な回数は膨大になります。`10^9`したがって、このアプローチは効率的に表現することさえできません。 

有益な観察は、波の間のギャップ内の正確な瞬間は気にしないということです。 重要なのは、ウェーブを完全に処理した直後、次のウェーブが始まる前の状態です。 マガジンが満載のウェーブに到達したことがわかっている場合は、このウェーブとそれに続くいくつかのウェーブがその間に不必要なリロードを行わずに処理された場合に何が起こるかを貪欲にシミュレートできます。 

リロード決定の固定シーケンスによって消費される弾丸の数が完全に決定されるため、ブルート フォースは機能しますが、可能なシーケンスの数が膨大であるため失敗します。 重要な洞察は次のとおりです`n`は小さいので、セグメントの可能なすべての開始波を試すことができます。 開始点ごとに、セグメントを前方に拡張し、後の波まで生き残るための最善の方法をシミュレートします。 これにより、問題は波の境界を越える動的プログラミングに帰着します。 

させて`dp[i]`最初のクリア後に消費する最小弾丸である`i`波に乗り、次の波までにマガジンをフルに準備しておくこと。 州から`i`、私たちは波をクリアしようとします`i`を通して`j`ウェーブの前に強制リロードなしで連続して`j`が始まります。 このシミュレーション中に、残りの弾丸の数とすでに消費された弾丸の数を追跡します。 マガジンが足りなくなった場合、何回リロードが必要か、使用可能な時間が許すかどうかを計算します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | リロード スケジュールの数が指数関数的に増加 | お(1) | 遅すぎる |
 | 最適な動的プログラミング | O(n²) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.初期化`dp[0] = 0`。 これは、最初の波の前に弾丸を消費しておらず、最初の弾倉がいっぱいであることを意味します。 
2. 考えられるすべての開始ウェーブに対して`i`、現在のセグメントを後のすべてのウェーブまで拡張してみてください`j`。 ウェーブ前の状態`i`マガジンがいっぱいであることはすでに保証されているため、これがシミュレーションの有効な開始点となります。 
3. セグメントを延長する間、現在のマガジンに残された弾丸を維持します。 現在のマガジンにウェーブの弾数が十分にある場合`j`、それらの弾丸を費やして続行します。 ウェーブはリロードせずに完了できます。 
4. 現在のマガジンが十分でない場合は、残りのモンスターを倒すのに必要なリロード回数を計算します。 リロードするたびに追加される`k`弾丸を使用しますが、リロードごとに 1 単位の時間も消費されます。 リロード数は、ウェーブの時間間隔内に収まる必要があります。 
5.ウェーブクリア後`j`、次のウェーブまでにマガジンが再び満杯になるのに十分な時間があれば、次の動的プログラミング状態を更新します。 トランジションには、これまでに消費された弾丸と、次のフルマガジンを準備するときに破棄された弾丸が保存されます。 
6. 考えられるすべてのトランジションを処理した後、`dp[n]`すべてのウェーブ後に消費される最小限の弾丸が含まれます。 到達できなかった場合、波をクリアすることはできません。 

なぜ機能するのか: 不変条件は、到達可能なすべてのものが`dp[i]`最初の実際の状況を説明します。`i`ウェーブが終了し、次のウェーブの前にマガジンがいっぱいになります。 すべての最適解には、ウェーブの前にマガジンがいっぱいになる最後のポイントがあり、動的計画法で考慮される遷移の 1 つとして表示されます。 トランジション内のシミュレーションでは、常にその固定セグメントに必要な最小限のリロード数が使用されます。これは、余分なリロードは弾丸を破棄し、コストを増加させるだけであるためです。 したがって、すべての候補が有効であり、すべての候補の最小値が最適になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    waves = [tuple(map(int, input().split())) for _ in range(n)]

    INF = 10**30
    dp = [INF] * (n + 1)
    dp[0] = 0

    for i in range(n):
        if dp[i] == INF:
            continue

        spent = dp[i]
        bullets = k

        for j in range(i, n):
            l, r, a = waves[j]
            extra = 0

            if a <= bullets:
                bullets -= a
                finish = l
            else:
                need = a - bullets
                reloads = (need + k - 1) // k
                if reloads > r - l:
                    break

                extra = reloads * k
                finish = l + reloads
                bullets = (k - need % k) % k

            spent += a + extra

            if j == n - 1:
                dp[n] = min(dp[n], spent)
            elif finish <= waves[j + 1][0]:
                dp[j + 1] = min(dp[j + 1], spent + bullets)

    print(-1 if dp[n] == INF else dp[n])

if __name__ == "__main__":
    solve()
```外側のループは、開始前にマガジンがいっぱいになっているウェーブを選択します。 内側のループは、現在の連続セグメントの考えられるすべてのエンドポイントを試行します。 これは、上で説明した動的プログラミングの遷移と一致します。 

シミュレーションの中で、`bullets`は、セグメント内の以前のすべてのウェーブを処理した後の現在のマガジンを表します。 現在のウェーブを終了できない場合、コードは天井分割で必要な最小リロード数を計算します。 条件`reloads > r - l`これらのリロードがウェーブの期限前に収まるかどうかを確認します。 

表現`(k - need % k) % k`最後のリロード後の残りの弾丸を計算します。 追加モジュロは、最後のマガジンが完全に空になった場合を処理します。 セグメントを終了した後、追加する`bullets`次の状態へは、次のウェーブの前にリロードすることで失われる弾丸を表します。 

すべての計算では Python 整数が使用されるため、可能な最大値に近い値は安全です。

## 特殊なケース

 接触波の場合:```
2 3
2 3 6
3 4 3
```アルゴリズムは 3 つの箇条書きから始まります。 最初の波で即座にそれらを消費し、さらに 3 発の弾丸が必要であることを検出し、1 回のリロードを使用します。 リロードは時間通りに終了します`3`、次のウェーブも で始まるため、これは許可されます。`3`。 第 2 ウェーブでは新しいマガジンを完全に使用し、`9`。

```最初のマガジンにはすでに十分な弾が入っています。 シミュレーションでは 1 つの弾丸が消費され、9 つの弾丸は未使用のままになります。 次のウェーブがないため、コードはそれらの残りの弾丸を破棄コストとして追加せず、正しい答えを与えます。`1`。
