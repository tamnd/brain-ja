 ## 解決策
 ## 問題の理解

 トンネル システムを表す根の生えたツリーが与えられます。 各ノードは、洞窟 (パンが最終的に行き着くターミナル ノード) またはゲート (パンをさらに下方に転送する内部ノード) のいずれかです。 ルートはノード 0 (サーフェス ゲート) であり、他のすべてのノードには 1 つの先行ノードがあるため、構造はルート付きツリーになります。 

各ゲートには複数の発信トンネルがあり、これらのトンネルは同時に使用されません。 代わりに、ゲートは 1 つの送信子へのポインタを維持し、パンがそのゲートを通過するたびに、ポインタは固定された循環順序で次の子へ回転します。 パンが到着する前の初期状態は、すべてのゲートがその順序で最初の子を指していることです。 

Q個のパンを根元から一つずつ落としていきます。 各パンは、訪問するすべてのゲートで現在アクティブな発信エッジに従い、訪問した各ゲートにその後そのポインタを回転させます。 タスクは、各パンについて、最終的にどのリーフ ノード (洞窟) に到達するかを決定することです。 

この構造は、最大 3·10^5 のノードと最大 3·10^5 のクエリを持つルート ツリーです。 これにより、ルートからリーフまでの完全なパスを O(N) 時間で走査することによって各パンを個別にシミュレートするアプローチは直ちに除外されます。これは、O(NQ) に低下する可能性があるためです。 

重要な制約は、各ゲートの出力エッジが循環的に使用されることです。 これにより、各発信エッジの選択は完全な履歴ではなく、そのノードがこれまでにアクセスされた回数のみに依存するため、強力な償却構造が作成されます。 

ルート ゲートがメンテナンス モードで、アクティブな発信トンネルがない場合、微妙なエッジ ケースが発生します。 その状況では、すべてのパンはノード 0 に留まり、同時に洞窟とみなされます。 通常のトラバーサル ロジックでは少なくとも 1 つの出力エッジが想定されるため、どのソリューションでもこの縮退ケースを明示的に処理する必要があります。 

## アプローチ

 直接シミュレーションでは、各パンを個別に処理します。 1 つのパンの場合、ルートから開始して、各ゲートで現在アクティブな子に繰り返し移動し、進むにつれてポインタを更新します。 これを文字通り実装すると、各移動は O(1) ですが、1 つのパンは長さ O(N) のパスを移動できるため、Q 個のパンが存在します。 これにより、最悪の場合は O(NQ) が発生しますが、これはまったく実行不可能です。 

重要な観察は、ノードを通過するたびに、循環リストから 1 つの要素を効果的に消費していることです。 個々のパンの観点から考える代わりに、各ノードには、これまでに訪問された回数によって決定される一連の「次の訪問」があると考えることができます。 

しかし、長い道を繰り返し歩くことを避ける方法がまだ必要です。 構造的なブレークスルーは、視点を逆転させることです。各パンを段階的に押し下げる代わりに、各ノードが着信訪問を順番に子供たちに分配するという観点から考えることができます。 各ノードはその子を循環するため、k 回目にノードに到着すると、k mod 次数番目の子が取得されます。 

これは DFS スタイルのシミュレーションを示唆していますが、単純な DFS は依然として訪問ごとにサブパスを再計算します。 最後の改善点は、各ノードが複数回訪問される動的トラバーサルとしてプロセスを扱うことですが、エッジ トラバーサルの合計数は、正確に Q にポインターの移動によって引き起こされる内部遷移の数を加えたものになります。これは、すべてのサイクルで使用されるエッジの合計数が線形になります。 

各ノードに対してポインタ インデックスを維持し、プロセスをシミュレートしますが、重要なのは、既に使用された遷移を不必要に再検討しないことです。 エッジをトラバースするたびに、ポインタを更新して続行します。 すべてのエッジの選択はサイクルごとに 1 回だけ消費されるため、すべてのクエリの合計作業量は線形です。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(NQ) | O(N) | 遅すぎる |
 | 償却更新によるポインタベースのトラバーサル | O(N + Q) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 説明どおりにプロセスを正確にモデル化しますが、ポインターの回転による償却に依存します。 

1. 指定された固定順序でその子を表す各ノードの隣接リストを作成します。 ゲートはその順序で子を循環するため、この順序は不可欠です。 
2. 各ノードに対して、パンがノード v に到着したときに使用する次の子を表す整数ポインタ idx[v] (最初は 0) を維持します。 
3. 各クエリ (各パン) について、ルート ノード 0 から開始します。 
4. 現在のノードは洞窟ではありませんが、その現在の子 idx[v] に移動し、子の数を法として idx[v] をインクリメントします。 これは、各パスの後に回転するゲートをシミュレートします。 
5. 子のないノードに到達するまでこのプロセスを続けます。 そのノードはパンが終わる洞窟です。 

システム定義では、ゲートを訪問するたびにローテーションがトリガーされ、パンが現在アクティブなトンネルを通過するようにルーティングされることが明示されているため、各ステップは正しいです。 

### なぜ効果があるのか

 本質的な不変条件は、すべてのノード v について、idx[v] が常に v が訪問された回数を出力エッジの数で割った値に等しいということです。 これは、アルゴリズムが問題で説明されている物理システムとの同期を失わないことを意味します。 すべてのトラバーサルの決定は、実際のシステム状態を定義するものである訪問数のみに依存します。 各訪問でポインターが 1 回だけ更新されるため、シミュレートされた状態は実際の周期的な動作と一致したままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    parent = list(map(int, input().split()))

    children = [[] for _ in range(n)]
    for i, p in enumerate(parent, start=1):
        children[p].append(i)

    idx = [0] * n

    out = []

    for _ in range(q):
        v = 0
        while children[v]:
            nxt = children[v][idx[v]]
            idx[v] += 1
            if idx[v] == len(children[v]):
                idx[v] = 0
            v = nxt
        out.append(str(v))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```構築ステップでは、入力によって暗示される正確な順序で子リストを構築します。 idx 配列は、各ゲートの回転ポインターの状態です。 各クエリ中に、リーフに到達するまで決定論的な遷移ルール​​を繰り返し適用します。 

最もデリケートな部分は、モジュロ動作が正しく処理されることを確認することです。 使用する代わりに`%`、次数に達したときに idx[v] を明示的に 0 にリセットします。これにより高速になり、モジュロ演算の繰り返しが回避されます。 

## 実用的な例

 最初のサンプル構造を考えてみましょう。ノード 0、1 はゲートとして機能し、その他は洞窟です。 

各パンはノード 0 から始まり、現在のポインター シーケンスに従います。 追跡する重要な点は、クエリを通じて idx[0] がどのように変化するかです。 

| パン | 開始 | 0 でステップ | 次のステップ | 洞窟 |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | 子 0 を取得、idx[0]=1 | リーチリーフ | L1 |
 | 2 | 0 | 子 1 を取得、idx[0]=2→0 | リーチリーフ | L2 |
 | 3 | 0 | 子 0 を取る | サイクルを繰り返す | L1 |

 この表は、ルートがサブツリーとは独立してどのように循環するかを示しており、クエリ間で状態が保持されることを確認しています。 

ここで、分岐ノードを除く各ノードに 1 つの子がある、より深いチェーンのような構造を考えてみましょう。 

| パン | 進路決定 | 最後の洞窟 |
 | --- | --- | --- |
 | 1 | 常に最初の子供 | 一番左の葉 |
 | 2 | 最初のノードが回転し、次のルーティングに影響を与える | 別の葉 |
 | 3 | 回転はより深くまで伝わります | 3番目の葉 |

 これは、ローカル ポインタの変更が再計算なしで将来のルーティングにどのように影響するかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N + Q) | 各ノード ポインタはアクセスされたときにのみ進み、各クエリはリーフへの完全な走査を 1 回だけ実行します。 
| スペース | O(N) | 隣接リストとポインタ配列はツリー構造と状態を格納します。 

この制約では最大 3·10^5 のノードとクエリが許可されるため、線形ソリューションが必要です。 このアルゴリズムは、ポインター更新ごとおよびクエリ走査ステップごとに一定の作業のみを実行し、制限内に快適に収まります。

 ## 特殊なケース

 重大なエッジケースは、ルートに子がない場合です。 システムは、地表であると同時に洞窟である単一のノードに縮退します。 すべてのパンはノード 0 で直ちに終了する必要があります。children[0] が空であり、ループに入らずに 0 を追加するため、アルゴリズムはこれを自然に処理します。 

もう 1 つのエッジ ケースは、子が 1 つあるノードです。 この場合、idx[v] は常に 0 にリセットされるため、ポインターの回転には目に見える効果はありません。これにより、長いチェーンが決定論的に動作し、不要な循環オーバーヘッドが発生しないことが保証されます。 

最後に、ツリーのバランスが著しく崩れていると、単純な再帰またはクエリごとの DFS 実装にストレスがかかる可能性があります。 各クエリはパスに従うため、実装ではクエリごとの再帰的 DFS を回避し、代わりに図に示すように反復的なポインター トラバーサルに依存する必要があります。
