 ## 解決策
 ## 問題の理解

 厳密に左から右に倒さなければならないモンスターのシーケンスが与えられています。 各モンスターには必要な強さのしきい値があり、スキップしたり並べ替えたりすることはできません。 ヒーローも揃っています。 各ヒーローには、モンスターとの遭遇を生き延びることができるかどうかを決定する戦闘力と、1 日に倒せるモンスターの数の上限を示す耐久力があります。 

このプロセスは数日で完了します。 毎日、ヒーローを 1 人だけ選びます。 その主人公は最初の無敗のモンスターから戦い始めます。 どこかの時点でモンスターが主人公よりも厳密に優れた力を持っている場合、ヒーローは即座に失敗し、そのモンスターから先に進むことなくその日が終了します。 それ以外の場合、主人公は耐久力が尽きるかモンスターがなくなるまでモンスターを 1 匹ずつ倒すことができます。 

課題は、シーケンス全体を破るまでに必要な日数を最小限に抑えるか、それが不可能であると判断することです。 

この制約により、私たちは単純なシミュレーションから遠ざけられます。 テストごとに最大 2×10^5 のモンスターとヒーロー、および最大 10^5 のテストがあるため、1 日ごとにモンスターのスキャンを再開したり、ポジションごとにすべてのヒーローの選択を貪欲に試したりするソリューションでは、制限時間を超えてしまいます。 O((n + m) log n) または O((n + m) log m) に近いアプローチが必要です。 

微妙な難しさは、持久力とパワーの相互作用から生じます。 大きなセグメントを倒すことができるヒーローであっても、単一の強力なモンスターが早い段階でブロックした場合は役に立たない可能性があります。 逆に、耐久力の高い弱いヒーローは、適切なプレフィックスに割り当てられた方が優れている可能性があります。 

素朴な貪欲な考えを打ち破るエッジケースには、非常に強力なモンスターが遅れて現れるような状況が含まれます。`[1, 1, 1, 100, 1]`。 利用可能な最強のヒーローを常に使用するという貪欲な戦略は、早期にヒーローを無駄にする可能性がありますが、十分な耐久力を備えた少し弱いヒーローが初期のセグメントには最適である可能性があります。 

別の失敗例は、ヒーローが 1 匹のモンスターを追い越せない場合です。 たとえば、モンスターのパワーが 10 であるのに、すべてのヒーローのパワーが 9 以下である場合、耐久力に関係なく、答えは即座に不可能になります。 

最後に、耐久力は大きいがパワーが小さい場合、誤解を招くケースが発生します。 このようなヒーローは長いセグメントでは強そうに見えますが、初期の高いピークを通過できない場合は実際には役に立ちません。 

## アプローチ

 ブルートフォースのアイデアは単純です。 毎日、すべてのヒーローを試し、現在のモンスターの位置からどれだけ遠くまで移動できるかをシミュレーションします。 最も多くのモンスターを倒したヒーローを選択してください。 これは常に局所的に進捗を最大化するため、これは正しいです。 ただし、各シミュレーションでは最大 n 個のモンスターをスキャンする可能性があり、合計で最大 n 個のステップがあるため、最悪の場合、テストごとに O(n²) となり、遅すぎます。 

改善するには、プレフィックスの繰り返しシミュレーションを避ける必要があります。 重要な観察は、モンスターのプレフィックスにとって重要なのは、これまでに使用されたヒーローの正確な順序ではなく、特定の強さのしきい値まで生き残ることができるヒーローの中で可能な限り最高の耐久力だけであるということです。 

位置 i で終わる接頭辞を固定する場合、i で終わるセグメントをカバーする有効な日は、パワーが少なくともそのセグメントの最大モンスターであり、耐久力が少なくともセグメントの長さであるヒーローを使用する必要があります。 これは、各パワー閾値に対して達成可能な最高の耐久力が分かる構造にヒーローを圧縮することを示唆しています。 

ヒーローをパワー別に並べ替えてから、耐久力に対するプレフィックスの最大値を前処理します。 これにより、次の形式のクエリに答えることができます。パワー ≥ x を持つすべてのヒーローの中で、利用可能な最大耐久力はどれくらいですか。 

現在、モンスターを貪欲にシミュレートしていますが、ヒーローを直接試すのではなく、これまでに確認されたモンスターの最大値を維持しながら現在のセグメントを継続的に拡張します。 セグメントを拡張しようとすると、現在の最大モンスターとセグメント長の両方を処理できるヒーローが存在するかどうかを問い合わせます。 「はい」の場合は延長します。 それ以外の場合は、現在の日を確定して再開します。 

これを効率的に行うために、すべての適格なパワー レベルで最高の持久力を維持しながら、ソートされたヒーロー上を移動するポインターを事前計算して使用します。 各拡張は実装に応じて償却定数または対数になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n²) | お(1) | 遅すぎる |
 | ソート + 貪欲 + 前処理 | O(n log n + m log m) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。 

1. ソートモンスターはすでに順番に指定されているので、それらの上にポインタを置きます。 
2. ヒーローをパワーの昇順に並べ替えます。 そうすることで、必要な最小パワーに対して、その要件を満たすヒーローの中で利用可能な最大の持久力を教えてくれる構造を維持します。 これは、ヒーローを最低のパワーから最高のパワーまでスキャンし、サフィックスの最大の耐久力を維持することによって構築されます。 
3. 必要な最小パワーと必要なセグメント長を指定して、ヒーローが両方を処理できるかどうかをチェックする関数を定義します。 これは、十分なパワーを持つ最初のヒーローをバイナリ検索し、そのインデックス以降で事前に計算された最大耐久力をチェックすることで答えられます。 
4. 最初のモンスターから開始して、1 日で可能な限り長いセグメントを構築しようとします。 現在のセグメントとその長さの最大モンスターパワーを追跡します。 
5. 各ステップで、セグメントを 1 モンスターずつ拡張しようとします。 延長後、誰かのヒーローがそれを処理できるかどうかを確認します。 「はい」の場合、拡大を続けます。 
6. 現在のセグメントを処理できるヒーローがいない場合は、前のセグメントを 1 日として終了し、現在のモンスターから再開します。 日カウンターをインクリメントします。 
7. いずれかの時点で、単一のモンスターをどのヒーローも処理できない場合は、すぐに -1 を返します。

重要な不変条件は、いつでも、有効なヒーローによって 1 日でクリアできる、現在の位置から始まる最長のプレフィックスを維持していることです。 拡張に失敗するたびに、拡張セグメントの両方の制約を満たすヒーローが存在しないことが原因です。つまり、前のセグメントが最大であり、最適な日の境界に対応する必要があります。 

この貪欲なセグメンテーションは、有効なソリューションでも配列を連続セグメントに分割する必要があり、拡張できない場合にカットを遅らせても将来の実現可能性が向上しないため、安全です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    m = int(input())

    heroes = []
    for _ in range(m):
        p, s = map(int, input().split())
        heroes.append((p, s))

    heroes.sort()

    best = [0] * m
    best[-1] = heroes[-1][1]
    for i in range(m - 2, -1, -1):
        best[i] = max(best[i + 1], heroes[i][1])

    def can(power_req, len_req):
        # find first hero with power >= power_req
        l, r = 0, m
        while l < r:
            mid = (l + r) // 2
            if heroes[mid][0] >= power_req:
                r = mid
            else:
                l = mid + 1
        if l == m:
            return False
        return best[l] >= len_req

    i = 0
    days = 0

    while i < n:
        days += 1
        seg_max = 0
        seg_len = 0

        j = i
        while j < n:
            seg_max = max(seg_max, a[j])
            seg_len += 1

            if not can(seg_max, seg_len):
                break
            j += 1

        if i == j:
            print(-1)
            return

        i = j

    print(days)

t = int(input())
for _ in range(t):
    solve()
```このコードは、まずパワー別にヒーローを並べ替えてから、実現可能性のクエリが高速になるように、耐久性に関するサフィックスの最大配列を構築します。 の`can`この関数は、最初の適格なヒーローをバイナリ検索し、その時点以降で利用可能な最高の持久力をチェックすることによって、ヒーローが指定された最大モンスター パワーと長さのセグメントを処理できるかどうかをチェックします。 

メインループは毎日のセグメントを貪欲に構築します。 モンスターが1体でも起動できない場合は、回答は不可能です。 それ以外の場合、各セグメントは実現可能性の制約の下で可能な限り拡張されます。 

実装の微妙な詳細は、セグメントの最大値を常に増分的に再計算することです。 これにより、以前のモンスターの再スキャンが回避されます。 もう 1 つの微妙な点は、サフィックスの最大配列です。これがないと、耐久性のチェックにリニア スキャンが必要になり、パフォーマンスが低下します。

 ## 特殊なケース

 重大なエッジケースは、最強のモンスターが早い段階で出現する場合です。 アルゴリズムは、セグメント拡張をただちに失敗させ、そのモンスターの前で強制的にカットすることでこれを処理し、無効なヒーローの割り当てが続かないようにします。 

もう 1 つのエッジケースは、耐久力は高いもののパワーが不十分なヒーローが存在する場合です。 耐久性がチェックされる前に二分探索によって電力制約が強制されるため、前処理により、それらが高電力セグメントとして誤って考慮されることがなくなります。 

最後のエッジケースは、高いパワーと大きな耐久力の両方を備えた単一のヒーローです。 その場合、実現可能性はすべてのプレフィックスで真のままであり、セグメントが途中で切断されることはないため、アルゴリズムは 1 つのセグメント内の配列全体を拡張します。
