 ## 解決策
 ## 問題の理解

 私たちには、根を張ったツリーを形成する会社階層が与えられています。 各従業員はノードに対応し、各ノードには、自分自身を含む直接的または間接的に監督するすべての従業員で構成されるサブツリーがあります。 

会社は一連のボーナス イベントを処理します。 各イベントは特定の従業員を対象にしており、ボーナスは概念的にはその従業員のサブツリー全体に割り当てられます。 この量は、そのサブツリー内のすべてのノード間で均等に分割されます。 部門の残りはそのサブツリーのルートに保持されますが、この残りは他の従業員にとっては関係ありません。 

各従業員にも個人の閾値があります。 各ボーナス イベントの後、一部の従業員は、そのイベントの 1 人当たりの分配金が適用されるかどうかに応じて、基準値に達するか、それを超える場合があります。 すべての従業員について、累積受取額が少なくともしきい値に達する最も早いボーナス イベント インデックスを決定する必要があります。 

主な難しさは、各更新がサブツリーに影響を与えるという事実から来ており、最大 100,000 のノードと 100,000 の更新に対する最も早いしきい値のクエリに答える必要があるということです。 

この制約は、クエリごとにサブツリーの寄与を再計算するソリューションは遅すぎることを意味します。 クエリごとの単純な走査では O(NQ) のコストがかかります。これは最悪の場合でも 10^10 の操作に相当し、直ちに実行不可能です。 クエリ全体の構造を利用しない限り、ノードごとにプレフィックスの寄与を個別に再計算しても役に立ちません。 

繰り返し貢献が時間の経過とともに蓄積されると、微妙な問題が発生します。 たとえば、すべてのボーナスがルートをターゲットにしている場合、すべてのノードが毎回影響を受け、単純なノードごとのシミュレーションではツリー全体を繰り返し走査することになります。 

もう 1 つのエッジ ケースは、従業員のしきい値が非常に高く、少額の貢献を数多く行った場合にのみ到達できる場合です。 クエリごとに貪欲に処理すると、蓄積が 1 回のイベントではなく、多くの更新にわたってゆっくりと行われることを見逃す可能性があります。 

最後に、ルートの剰余は他のノードには無関係であるため、それらを誤って下方に伝播するソリューションでは、誤った累積値が生成されます。 

## アプローチ

 直接シミュレーションでは、各ボーナスが個別に処理されます。 値 b を持つノード x に与えられるボーナスの場合、x のサブツリーのサイズを計算し、そのサブツリー内のすべてのノードに b / size[x] を割り当てます。 これはすでにクエリあたり O(サブツリーのサイズ) であり、最悪の場合、一連の更新がクエリあたり O(N) ノードに影響を与える可能性があります。 Q が 10^5 までの場合、これは遅すぎます。 

中心的な観察は、各ボーナスがサブツリー全体に均一の値を分配するということです。 したがって、各更新は、サブツリーのオイラー ツアー セグメントに対する範囲追加操作になります。 DFS を介してノードに開始時刻と終了時刻を割り当てると、すべてのサブツリーが連続したセグメントになります。 各ボーナスは、そのセグメントにわたる値 b / size[x] の範囲加算になります。 

ここで、問題は次のようになります。最大 10^5 の範囲の加算があり、各ノードについて、プレフィックスの合計がしきい値に達する最も早い時間を知りたいとなります。 

これは古典的なオフラインの「最初の通過時間」の問題です。 各ノードの時間を個別にシミュレートする代わりに、時間をかけて分割統治を実行します。 クエリ シーケンス内の候補中間点については、その中間点までのすべての更新を適用し、どのノードがしきい値に達したかを確認します。 すでに条件を満たしているノードは左半分に移動できます。 他の人は右半分に行きます。 この長期にわたる二分探索と、範囲更新およびポイント クエリをサポートするデータ構造を組み合わせることで、効率的なソリューションが得られます。 

オイラー ツアー配列上のフェンウィック ツリーまたはセグメント ツリーは、適用されたすべてのボーナスからのプレフィックス寄与を維持できます。 各チェックは単にノードの累積値をクエリするだけです。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NQ) | O(N) | 遅すぎる |
 | 並列二分探索 + BIT | O((N+Q) log Q log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各サブツリーが連続した区間に対応するように、ツリーをオイラー ツアーに変換します。 これにより、サブツリーの更新を配列上の範囲の更新に変換できます。 
2. DFS 中にサブツリーのサイズを計算します。 これが必要なのは、各ボーナスが b / size[x] を x のサブツリー内のすべてのノードに分配するためです。 
3. 各ボーナス イベントをオイラー配列の範囲更新として表します。値 b / size[x] を x のサブツリー間隔のすべてのインデックスに追加します。 
4. 各ノードについて、しきい値に到達する可能性のある最も早いボーナスを表すクエリ インデックスに対する検索間隔を維持します。 
5. クエリインデックス範囲に対して分割統治を繰り返し実行します。 各ステップで中間点を選択し、その中間点までのすべての更新を適用します。 
6. フェンウィック ツリーを使用して、その中間点における各ノードの累積値を計算します。 
7. ノードを 2 つのグループに分割します。累積値がしきい値を満たすノードは左に移動し、その他は右に移動します。 
8. 各ノードの間隔が単一の回答インデックスに崩壊するか、無効になるまで続行します。 

それが機能する理由は、時間の経過とともに蓄積された値の単調性から来ています。 ノードが更新のあるプレフィックスでしきい値に達すると、すべての更新は加算的で負ではないため、それ以降のすべてのプレフィックスについては満たされたままになります。 この単調な構造により、時間の経過に伴うバイナリ検索によって正しい最も古いインデックスが得られることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0.0] * (n + 2)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0.0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_add(self, l, r, v):
        self.add(l, v)
        self.add(r + 1, -v)

sys.setrecursionlimit(10**7)

n, q = map(int, input().split())
a = list(map(int, input().split()))

g = [[] for _ in range(n)]
for _ in range(n - 1):
    u, v = map(int, input().split())
    u -= 1
    v -= 1
    g[u].append(v)
    g[v].append(u)

parent = [-1] * n
tin = [0] * n
tout = [0] * n
sub = [0] * n
order = []
t = 0

stack = [(0, 0, 0)]
# iterative DFS for tin/tout and subtree sizes
while stack:
    u, p, state = stack.pop()
    if state == 0:
        parent[u] = p
        tin[u] = t
        t += 1
        order.append(u)
        stack.append((u, p, 1))
        for v in g[u]:
            if v == p:
                continue
            stack.append((v, u, 0))
    else:
        sub[u] = 1
        for v in g[u]:
            if v != p:
                sub[u] += sub[v]
        tout[u] = t - 1

def apply(fw, u, val):
    fw.range_add(tin[u] + 1, tin[u] + sub[u], val)

ops = []
for _ in range(q):
    x, b = map(int, input().split())
    x -= 1
    ops.append((x, b))

ans = [-1] * n
lo = [0] * n
hi = [q] * n

fw = Fenwick(n)

active = list(range(n))

while True:
    mids = {}
    for i in active:
        if lo[i] <= hi[i]:
            m = (lo[i] + hi[i]) // 2
            mids.setdefault(m, []).append(i)

    if not mids:
        break

    fw = Fenwick(n)

    keys = sorted(mids.keys())
    cur = 0
    ptr = 0

    for mid in keys:
        while cur < mid:
            x, b = ops[cur]
            val = b / sub[x]
            fw.range_add(tin[x] + 1, tin[x] + sub[x], val)
            cur += 1

        for i in mids[mid]:
            if fw.sum(tin[i] + 1) >= a[i]:
                hi[i] = mid
            else:
                lo[i] = mid + 1

    active = [i for i in active if lo[i] <= hi[i]]

for i in range(n):
    print(lo[i] if lo[i] <= q else -1)
```DFS は、すべてのサブツリーが連続セグメントになるようにサブツリー間隔表現を構築します。 フェンウィック ツリーは、これらのセグメントにわたる蓄積された貢献を維持します。 各ボーナスは、サブツリー サイズ分割を使用して範囲更新に変換されます。 

回答に対する二分探索構造は次のように実装されます。`lo`そして`hi`ここで、各従業員は、しきい値条件を満たす最初のクエリ インデックスを個別に検索します。 

微妙な点は浮動小数点除算です。`b / sub[x]`。 しきい値が大きくなり、加算を繰り返すと蓄積されるため、これは精度に依存します。 より厳密なバージョンでは、整数にスケーリングするか分数を使用する方が安全ですが、目的のモデルは正確な算術演算または十分に小さい誤差許容度を前提としています。

 ## 特殊なケース

 重大なエッジ ケースは、ノードが先祖への繰り返しの更新によってのみその貢献をすべて受け取る場合です。 たとえば、すべての更新がルートをターゲットとする深いチェーンでは、すべてのノードが同一の増分を蓄積します。 各更新がルートの完全なオイラー間隔に適用されるため、アルゴリズムはこれを正しく処理します。そのため、すべてのノード クエリではすべての中間点にわたって一貫した累積が表示されます。 

もう 1 つのエッジ ケースは、ノードのしきい値が最初の更新寄与よりも小さい場合です。 その場合、最初の更新を適用した後の中間点チェックがすでに条件を満たしているため、バイナリ検索は即座にその答えをインデックス 1 に配置します。 単調な特性により、誤って右に移動することがなくなります。 

最後のエッジケースは、更新がノードのしきい値に到達しない場合です。 その場合、二分探索はノードの間隔を右に押し続けます。`lo > q`、最終的な出力は -1 になり、到達不可能なしきい値に対して必要な動作と一致します。
