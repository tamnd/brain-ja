 ## 解決策
 ## 問題の理解

 トムはいくつかのばらばらな時間間隔でラップトップを使用します。 彼がアクティブに使用している間、ラップトップは通常モードのままで、消費電力が高くなります。`P1`毎分ワット数。 彼がラップトップとの対話をやめても、マシンはすぐには低電力状態に切り替わりません。 

まず最初に`T1`非アクティブ状態が数分間続いても、通常モードのままになります。 その後、スクリーンセーバーモードが開始され、消費量は`P2`毎分ワット数。 スクリーンセーバーがアクティブになったら、`T2`さらに分が経過すると、ラップトップはスリープ モードに入り、消費電力が増加します。`P3`毎分ワット数。 

すべての勤務間隔が与えられています`[li, ri]`ここで、トムはインターバル全体を通じてラップトップと継続的に対話します。 タスクは、最初の間隔の開始から最後の間隔の終了までに消費される総エネルギーを計算することです。 

制約はわずかです。 作業間隔は最大 100 回あり、すべての時間は 1 日以内です。 1 日を通して分単位のシミュレーションを行う場合でも、最大 1440 回の反復が必要になりますが、これはすでに十分な速度です。 これは、問題は最適化のトリックに関するものではなく、オフバイワンの間違いなく状態遷移を正しく実装することにあることを意味します。 

最も危険なのは、作業間隔のギャップに対処することです。 ラップトップは非アクティブな間は徐々にモードを変更するため、各ギャップを慎重に 3 つのセグメントに分割する必要があります。 

1. 最初の`T1`費用は分単位`P1`2. 次は`T2`費用は分単位`P2`3. その後はすべて有料`P3`不注意な実装では、移行分が古いモードに属するか新しいモードに属するかが混同されることがよくあります。 

次の例を考えてみましょう。```
1 10 5 1 5 5
0 5
```ラップトップは 0 分から 5 分まで継続的に使用されるため、答えは簡単です。```
5 * 10 = 50
```この問題では消費が要求されるのは次のとおりであるため、その後の非アクティブ期間はありません。`r_n`。 

もう 1 つの微妙なケースは、非アクティブ期間が以下の場合です。`T1`。```
2 10 5 1 5 5
0 5
7 10
```ギャップの長さはわずか2分です。 ラップトップは決してスクリーンセーバー モードにならないため、どちらの分もコストがかかります`P1`。 バグのある実装により、非アクティブが開始された直後にスクリーンセーバーが誤ってアクティブになる可能性があります。 

3 番目の注意が必要な状況は、非アクティブ期間が両方のしきい値を超えた場合です。```
2 10 5 1 2 3
0 1
10 11
```ギャップの長さは 9 です。 

電力使用量は次のようになります。 

- 最初の 2 分間`P1`- 次の 3 分間`P2`- 残り 4 分`P3`正しい追加コストは次のとおりです。```
2*10 + 3*5 + 4*1 = 39
```最後のセグメントを見逃すことはよくある間違いです。 

## アプローチ

 最も直接的な解決策は、次から毎分をシミュレートすることです。`l1`に`rn`。 私たちは毎分、トムがラップトップをアクティブに使用しているかどうか、マシンがまだ通常の非アクティブ期間内にあるかどうか、スクリーンセーバー モードに達しているかどうか、またはすでにスリープ状態に陥っているかどうかを判断します。 

ラップトップの状態は整数分の境界でのみ変化するため、この強引な方法は正しいです。 1 日は最大でも 1440 分なので、最悪の場合の作業はわずかです。 

それでも、問題の構造により、よりクリーンなものが可能になります。 

ラップトップは、連続した作業間隔の間のギャップ中にのみ動作を変更します。 トムがアクティブに働いている間、毎分コストがかかります`P1`。 唯一興味深いのは、非アクティブなことです。 

現在の間隔が次の時点で終了すると仮定します。`ri`そして次はから始まります`l(i+1)`。 非アクティブ期間は次のとおりです。```
gap = l(i+1) - ri
```各分を個別にシミュレートする代わりに、このギャップを 3 つのチャンクに直接分割できます。 

- まで`T1`分`P1`- まで`T2`さらに数分`P2`- 残りの分`P3`これにより、問題は間隔の長さに関する単純な算術に変換されます。 

タイムラインが短いため総当り攻撃は機能しますが、間隔ベースの観察により不必要なシミュレーションが完全に削除されます。 結果として得られる実装は、より短く、推論が容易になり、タイムラインがはるかに大きくなった場合でも、自然に拡張できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | お(1440) | お(1) | 承認済み |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべての入力値を読み取り、作業間隔を保存します。 
2. 作業間隔ごとに`[l, r]`、 追加`(r - l) * P1`答えに。 

アクティブな使用中、ラップトップは通常モードのままであることが保証されます。 
3. 連続する間隔のペアごとに、非アクティブ期間を計算します。```
gap = l[i] - r[i-1]
```4. 最初の非アクティブ段階では、できるだけ多くの時間を費やします。```
first = min(gap, T1)
```追加：```
first * P1
```この数分でも通常モードの電力が消費されます。 
5. 残りのギャップからこれらの分を削除します。```
gap -= first
```6. 残りの時間をできるだけスクリーンセーバー モードで過ごします。```
second = min(gap, T2)
```追加：```
second * P2
```7. これらの議事録も削除します。```
gap -= second
```8. 残りの時間はスリープ モードで費やされます。 

追加：```
gap * P3
```9. すべての間隔とギャップを処理した後、合計の答えを出力します。 

### なぜ効果があるのか

 間の毎分`l1`そして`rn`belongs to exactly one of two categories:

- Tom is actively using the laptop.
 - ラップトップは 2 つの作業間隔の間にアイドル状態になります。 

Active minutes always consume`P1`, so their contribution is immediate.

 アイドル セグメントの場合、ラップトップは固定の順序で固定の期間で状態を遷移します。 アルゴリズムは、ギャップを正確にこれらの状態期間に分割します。 

- まず`T1`分
 - 次へ`T2`分
 - 残り分

 1 分がスキップされることはなく、1 分が 2 回カウントされることもありません。 各セグメントは正しい電力値で充電されるため、最終的な合計は実際の総エネルギー消費量と等しくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, p1, p2, p3, t1, t2 = map(int, input().split())

intervals = [tuple(map(int, input().split())) for _ in range(n)]

ans = 0

for l, r in intervals:
    ans += (r - l) * p1

for i in range(1, n):
    gap = intervals[i][0] - intervals[i - 1][1]

    first = min(gap, t1)
    ans += first * p1
    gap -= first

    second = min(gap, t2)
    ans += second * p2
    gap -= second

    ans += gap * p3

print(ans)
```最初のループは、すべてのアクティブな作業期間を処理します。 トムはその間常にラップトップと対話するため、マシンが通常モードを離れることはありません。 

2 番目のループでは、非アクティブなギャップを 1 つずつ処理します。 ラップトップは常に状態を順番に通過するため、順序は重要です。 まず通常のアイドル段階でできる限り多くのギャップを消費し、次にスクリーンセーバー モードに移行し、最後に残りの時間をスリープ モードに割り当てます。 

引き算の手順は間違いやすいです。 1 つのフェーズに分を割り当てたら、次のフェーズを処理する前に分を削除する必要があります。 そうしないと、同じ分が複数回カウントされてしまいます。 

インターバルではハーフオープンのタイミング動作が自然に使用されます。 間隔`[l, r]`まさに続く`r - l`分。問題文と一致します。 使用する`r - l + 1`すべての作業期間を過大評価することになります。 

Python の整数は最大応答サイズを簡単に処理できるため、オーバーフローは心配ありません。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各間隔と各ギャップは 1 回処理されます。 
| スペース | お(1) | 入力ストレージ以外には、少数の整変数のみが使用されます。 

最大 100 間隔の場合、アルゴリズムは即座に実行されます。 この実装では単純な算術演算のみが使用され、時間とメモリの制限内に問題なく収まります。 

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    input = sys.stdin.readline

    n, p1, p2, p3, t1, t2 = map(int, input().split())

    intervals = [tuple(map(int, input().split())) for _ in range(n)]

    ans = 0

    for l, r in intervals:
        ans += (r - l) * p1

    for i in range(1, n):
        gap = intervals[i][0] - intervals[i - 1][1]

        first = min(gap, t1)
        ans += first * p1
        gap -= first

        second = min(gap, t2)
        ans += second * p2
        gap -= second

        ans += gap * p3

    return str(ans)

# provided sample
assert run(
"""1 3 2 1 5 10
0 10
"""
) == "30", "sample 1"

# minimum-size input
assert run(
"""1 1 1 1 1 1
0 1
"""
) == "1", "single minute"

# gap shorter than T1
assert run(
"""2 10 5 1 5 5
0 5
7 10
"""
) == "100", "only normal mode during gap"

# gap enters all states
assert run(

0 1

"""
) == "45", "gap exactly T1 + T2"

# all equal power values

"""

```| テスト入力 | 期待される出力 | 検証内容 |

 | 長さ 1 の単一区間 | 1 | 最小サイズの動作 |
 | ギャップが以下より短い`T1`| 100 | スクリーンセーバーは早期にアクティブ化すべきではありません |

## 特殊なケース

 非アクティブ期間がスクリーンセーバー モードに達しない次の入力を考えてみましょう。```
2 10 5 1 5 5
0 5
7 10
```アクティブな間隔では次のものが消費されます。```
5*10 + 3*10 = 80
```ギャップの長さは次のとおりです。```
7 - 5 = 2
```以来`2 < T1`、ギャップ全体のコスト`2*10 = 20`。 

最終的な答えは次のようになります。```
80 + 20 = 100
```最初のフェーズでギャップ全体が消費され、後のフェーズには何も残らないため、アルゴリズムはこれを正しく処理します。 

ここで、スリープ モードに達するギャップを考えてみましょう。```
2 10 5 1 2 3
0 1
10 11
```ギャップの長さは9です。 

アルゴリズムは次のように処理します。```
first = min(9, 2) = 2
remaining = 7

second = min(7, 3) = 3
remaining = 4

sleep = 4
```コストは次のようになります。```
2*10 + 3*5 + 4*1 = 39
```これにより、3 つのフェーズすべてが使用されている場合でも、状態進行ロジックが正しいことが確認されます。 

最後に、正確な遷移境界を調べます。```
2 10 5 1 2 3
0 1
6 7
```ギャップの長さは正確に次のとおりです。```
2 + 3 = 5
```ラップトップには次のような費用がかかります。 

- 通常のアイドルモードで 2 分間
 - スクリーンセーバー モードで 3 分間
 - スリープモードで0分

 第 2 フェーズの後に残りのギャップがゼロになるため、アルゴリズムはこれを自然に処理します。 追加の睡眠料金はかかりません。
