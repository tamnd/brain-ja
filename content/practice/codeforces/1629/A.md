 ## 解決策
 ## 問題の理解

 RAM を一時的に消費して RAM を永続的に増加できるシステムをモデル化するように求められます。 各ソフトウェアには、実行に必要な RAM の量と、使用後に提供される RAM の量という 2 つの数値があります。 私たちの PC は特定の初期 RAM から起動します。 目標は、現在の RAM が要件以上である場合にのみプログラムを実行できるというルールを尊重し、ソフトウェアを何らかの順序で実行することによって達成可能な最大 RAM を決定することです。 複数のテスト ケースが与えられ、それぞれがソフトウェア項目の数、開始 RAM、要件とゲインの 2 つのリストを指定します。 各テスト ケースの出力は単一の数値、つまり到達可能な最大 RAM です。 

制約は小さく、各テスト ケースは最大 100 個のソフトウェア項目を含み、RAM 値は最大 1000 です。これは、テスト ケースごとに O(n²) アルゴリズムでも実行可能であることを意味します。最悪の場合、約 100×100² = 10⁶ の操作を実行することになるため、これは 1 秒の制限時間内で許容可能です。 時間的に O(n log n) まで最適化する必要はありませんが、すべてのエッジケースを処理するための明確で正しい方法が必要です。 

すべてのソフトウェア項目が当初よりも多くの RAM を必要とする場合、明らかではないエッジ ケースが発生します。 たとえば、初期 RAM が 1 で、すべてのソフトウェアに少なくとも 2 が必要な場合、どのソフトウェアも使用できません。 正しい出力は初期 RAM 自体です。 必要性の低いプログラムが複数存在する場合、別の微妙なシナリオが発生します。後でより大きなゲインのソフトウェアをロック解除するには、特定の順序でそれらを選択する必要がある場合があります。 ソフトウェアを任意の順序で実行する不用意なアプローチでは、これを見落として最大 RAM を過小評価する可能性があります。 

## アプローチ

 強引なアプローチは、ソフトウェアのすべての組み合わせを試すことです。 各順列について、ソフトウェアを使用して順次シミュレーションし、最終的な RAM を記録します。 これにより、考えられるすべてのシーケンスが調査されるため、正確さが保証されます。 ただし、順列の数は n! であり、n=10 の場合でも実行できなくなります。 したがって、このアプローチは明らかに遅すぎます。 

重要な点は、どの時点においても、RAM 要件が現在の RAM を超えないソフトウェアを実行することが最適な選択であるということです。 このようなすべての選択肢のうち、実行可能性の観点からは順序は重要ではありません。現在使用できるソフトウェアは、延期すれば後で使用することもできます。 したがって、単純な貪欲な戦略を適用できます。要件が現在の RAM 以下であるソフトウェアを繰り返し選択し、適用し、リストから削除します。 使用できるソフトウェアがなくなるまで続行します。 これが機能するのは、各ソフトウェアが RAM を永続的に増加させ、以前はアクセスできなかったソフトウェアが実行できる可能性が開かれるためです。 すぐに実行可能なソフトウェア間の順序は実現可能性に影響しませんが、少ないステップで最大の利益を得たい場合は効率に影響する可能性があります。 ここでは、問題は最大 RAM のみを要求するため、任意の順序で十分です。

 | --- | --- | --- | --- |
 | ブルートフォース | お(ん!) | O(n) | 遅すぎる |
 | 最適な貪欲さ | O(n²) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. テスト ケースの数を読み取ります。 
2. 各テスト ケースについて、n と初期 RAM k を読み取り、RAM 要件とゲインの配列を読み取ります。 
3. 各ソフトウェアの要件とそのゲインを組み合わせて、タプル (要件、ゲイン) のリストを作成します。 これにより処理が簡素化され、どのソフトウェアが残っているかを確実に追跡できるようになります。 
4. 要件が現在の RAM 以下であるソフトウェアが少なくとも 1 つ存在する場合、リストを順番にスキャンして最初のそのようなソフトウェアを見つけます。 ソフトウェアのゲインによって現在の RAM を増分し、リストから削除します。 このプロセスを繰り返します。 
5. ソフトウェアが使用できなくなったら、現在の RAM を達成可能な最大値として出力します。

これが機能する理由: 維持される不変条件は、各反復で、現在実行可能なすべてのソフトウェアが考慮されるということです。 このようなソフトウェアを実行すると RAM が増加し、より多くのソフトウェアを使用できるようになります。 各ソフトウェアは一度しか使用できないため、最終的には残りのソフトウェアが使用できなくなる状態になります。 この時点で、要件に違反せずに追加のソフトウェアを実行できないため、現在の RAM は最大になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n, k = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    
    software = list(zip(a, b))
    
    while True:
        progressed = False
        for i in range(len(software)):
            if software[i][0] <= k:
                k += software[i][1]
                software.pop(i)
                progressed = True
                break
        if not progressed:
            break
    print(k)
```この実装では、現在実行できるソフトウェアを繰り返し検索します。 の`progressed`flag は、フル スキャンが進行したかどうかを追跡します。 使用する`pop(i)`使用可能なソフトウェアを見つけたらすぐに、同じソフトウェアを再検討することがなくなります。 RAM が変更され、以前は使用できなかったソフトウェアが使用可能になる可能性があるため、ソフトウェアを実行するたびに中断します。 これにより、RAM を更新せずに 1 回のパスで複数のソフトウェアを実行しようとするミスを回避できます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n²) | 各テスト ケースでは、最悪の場合、残りのソフトウェアをすべて n 回スキャンし、各スキャンで最大 n 個の項目を検査できます。 |

 n ≤ 100 および t ≤ 100 の場合、解法は最大 10⁶ 反復を実行し、制限時間内に十分収まります。 メモリ使用量も 256 MB の制限を大幅に下回っています。

    output = io.StringIO()

    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))

        while True:

            for i in range(len(software)):
                if software[i][0] <= k:
                    k += software[i][1]
                    software.pop(i)
                    progressed = True
                    break
            if not progressed:
                break
        print(k)
    return output.getvalue().strip()
