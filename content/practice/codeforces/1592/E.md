 ## 解決策
 ## 問題の理解

 一連の整数が与えられ、特定のビット単位の不等式が成立する最長の連続セグメントを見つけるように求められます。つまり、セグメント内のすべての要素のビット単位の AND が、同じセグメントのビット単位の XOR よりも厳密に大きくなります。 

簡単に言えば、すべての部分配列について 2 つの値を計算できます。 1 つは、サブ配列のすべての要素に設定されているビットのみを保持することによって形成されます。 もう 1 つは、すべての要素の XOR 演算によって形成され、パリティに応じてビットが相殺されます。 最初の量が 2 番目の量を支配する最大長のセグメントが必要です。 

配列の長さは最大 100 万、値も最大約 100 万であるため、各数値は約 20 ビット以内に収まります。 これにより、すべての部分配列の AND と XOR を個別に再計算するソリューションは即座に除外されます。 部分配列の単純な O(n²) 列挙では、それぞれが O(n) または O(1) の償却再計算を必要とし、それでも遅すぎます。 

条件は連続した範囲のみに依存するため、問題の構造はスライディング ウィンドウ アプローチを示唆しています。 ただし、単純な単調条件とは異なり、不等式は明らかな拡張または縮小の下では安定しないため、正確さはウィンドウの状態を注意深く維持するかどうかに依存します。 

いくつかの特殊なケースで構造を説明します。 

すべての要素が同一の場合、次のようになります。`[1, 1, 1]`の場合、AND はパリティに応じて XOR が 1 または 0 に等しくなりますが、厳密にそれより大きくなることはないので、答えは 0 になります。大きなセグメントのみをチェックする単純なアプローチでは、長い均一配列が有効であると誤って想定する可能性があります。 

配列に非常に大きな要素と小さな要素が混在している場合、次のようになります。`[8, 1, 1, 1]`の場合、AND はすぐに 0 に崩壊しますが、XOR は小さいままか変動する可能性があります。 ブルート フォース手法では、有効な短いウィンドウは検出されても、すべての開始位置が考慮されていない場合、真の最長セグメントを見逃す可能性があります。 

主な問題点は、セグメントを拡張すると AND が縮小する傾向があるのに対し、XOR は予期せず増加または減少する可能性があることです。 

## アプローチ

 ブルートフォース手法では、すべてのサブ配列をチェックし、その AND と XOR を最初から計算します。 左のエンドポイントごとに、右のエンドポイントを拡張し、両方の値を再計算します。 段階的に更新したとしても、各拡張機能の XOR には依然として O(1) のコストがかかりますが、AND には依然として注意深い処理または再計算が必要です。 最悪の場合、これにより約 n² の遷移が発生します。これは、n が 10⁶ の場合、約 10¹² の操作となり、実現可能な限界をはるかに超えています。 

この改善は、現在のウィンドウを維持し、その境界を調整するだけでよいことを認識することで得られます。 ウィンドウの XOR は段階的に維持するのが簡単です。 AND はさらに複雑ですが、ビット頻度を使用して追跡できます。ビットが AND に存在するのは、ウィンドウ内のすべての要素にそのビットが設定されている場合のみです。 

これにより、問題は、エンドポイントを移動するときに AND と XOR の両方を効率的に更新できる動的ウィンドウの維持に変わります。 これが可能になると、条件が失敗するたびに右側の境界を拡張し、左側の境界を縮小するという 2 ポインタ戦略を試行できます。 

重要な構造上の観察は、固定された右端点の場合、有効な左端点が存在する場合、左から貪欲に縮小することによってそのような最小の左端点を見つけることができるということです。 これにより、古い位置を再度訪問することなく、有効性がローカルに復元される移動ウィンドウを維持することができます。

 ## アルゴリズムのチュートリアル

 We maintain a sliding window`[l, r]`ウィンドウの XOR とウィンドウ全体の各ビットの頻度カウントの 2 つの量を追跡します。 ビット数から、各ビットが AND に設定されているかどうかを再構築します。 

1. 両方のポインターを先頭に置き、すべてのカウンターを空にして開始します。 XOR は 0 で、すべてのビット カウントは 0 です。 
2. 右ポインタを一度に 1 ステップずつ展開します。 新しい要素がウィンドウに入ると、その要素に XOR を適用して XOR を更新します。 また、新しい値に設定されているすべてのビットをインクリメントして、ビット数を更新します。 このステップでは、現在の候補ウィンドウを構築します。 
3. 各展開後、現在のウィンドウが AND > XOR の条件を満たすかどうかを確認します。 AND は暗黙的に計算されます。ビットは、そのカウントがウィンドウ長と等しい場合にのみ AND に存在します。 
4. 条件が満たされない場合は、ウィンドウを左から縮小します。 要素を削除するときは、再度 XOR 演算して XOR を更新し、そのビット数をデクリメントします。 これにより、その寄与が効果的に除去されます。 
5. 縮小するたびに、条件が満たされるかどうかを再計算します。 条件が true になるか、ウィンドウが空になるまで縮小を続けます。 
6. 各右エンドポイントのウィンドウを安定させた後、現在の有効なウィンドウの長さで答えを更新します。 

これが機能する主な理由は、固定された右端点ごとに、有効な左境界が必要なだけ右端に移動されるためです。 ウィンドウが有効になったら、右のエンドポイントを拡張することがウィンドウを再度無効にする唯一の方法であるため、以前の左側の位置を再訪する必要はありません。 

### なぜ効果があるのか

 スライディング ウィンドウは、各右端点について、左端点が部分配列が有効である最小のインデックスであるという不変条件を維持します。 XOR は現在のウィンドウに対して正確に維持されます。 AND は、ウィンドウ全体のビット カバレッジによってのみ決定され、周波​​数カウントによって完全にキャプチャされます。 左側の境界をシフトするときに両方の更新が可逆であるため、情報が失われることはなく、すべてのサブ配列が右側のエンドポイントごとに最小の有効な形式で考慮されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    B = 21  # enough for values up to 1e6
    
    cnt = [0] * B
    xor_val = 0
    
    def compute_and(length):
        res = 0
        for b in range(B):
            if cnt[b] == length:
                res |= (1 << b)
        return res
    
    l = 0
    ans = 0
    
    for r in range(n):
        x = a[r]
        xor_val ^= x
        for b in range(B):
            if x >> b & 1:
                cnt[b] += 1
        
        while l <= r:
            length = r - l + 1
            and_val = compute_and(length)
            if and_val > xor_val:
                break
            y = a[l]
            xor_val ^= y
            for b in range(B):
                if y >> b & 1:
                    cnt[b] -= 1
            l += 1
        
        if l <= r:
            ans = max(ans, r - l + 1)
    
    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、現在のウィンドウの AND を効率的に再構築するために、ビットごとの周波数配列が保持されます。 XOR はステップごとに一定時間で増分更新されます。 内側のループは左ポインタを前方に移動するだけなので、各要素の追加と削除は最大 1 回です。 

微妙な点は、チェックごとにビット数から AND を再計算することです。 これは 21 回の操作ですが、各ウィンドウ調整は実行全体にわたって償却されるため、全体としては線形のままです。 もう 1 つの重要な詳細は、ウィンドウが有効な場合にのみ回答を更新することです。これにより、ウィンドウが有効な場合に無効な状態が記録されるのを避けることができます。`l`過去に移動しました`r`。 

## 実用的な例

 配列を考慮してください`[5, 6]`。 

から始めます`r = 0`、窓`[5]`。 AND は 5、XOR は 5 であるため、条件は false です。 ウィンドウは空になるまで縮小されます。 

で`r = 1`、窓口がございます`[5, 6]`。 ここで XOR は次のようになります`3`、AND となります。`4`, したがって、条件が成り立ちます。 以下の表はプロセスを追跡します。 

| r | l | 窓 | XOR | そして | 有効 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | [5,6] | 3 | 4 | はい |

 これは、ウィンドウ全体が有効であることを示しており、答え 2 が得られます。 

ここで考えてみましょう`[1, 3, 3, 1]`。 

ウィンドウを拡大し、安定性を追跡します。 重要な動作は、ビットの繰り返しにより AND が正のままである一方で、XOR がキャンセルされるときに現れます。 

| r | l | 窓 | XOR | そして | 有効 |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 0 | [1] | 1 | 1 | いいえ |
 | 1 | 0 | [1,3] | 2 | 1 | いいえ |
 | 2 | 1 | [3,3] | 0 | 3 | はい |
 | 3 | 1 | [3,3,1] | 1 | 1 | いいえ |
 | 3 | 2 | [3,1] | 2 | 1 | いいえ |

 有効なセグメントは`[3,3]`ただし、拡大および縮小すると、すべての部分配列を再計算するのではなく、ウィンドウがどのように動的に適応するかを示します。

 ## 特殊なケース

 次のような単一要素の配列`[x]`AND は XOR に等しいため、厳密な不等号は不可能であるため、常に失敗します。 このアルゴリズムはウィンドウを正しく初期化し、すぐに縮小します。長さが 1 になることはありません。 

次のような均一な配列`[1, 1, 1, 1]`すべての展開で等しい AND と XOR が生成されます。 左ポインタは毎回ウィンドウが空になるまで前進し、答えが 0 のままであることを確認します。 

上位ビットと下位ビットが交互に配置される配列。たとえば、`[7, 0, 7, 0]`、頻繁な XOR キャンセルを示しますが、AND はすぐに低下します。 両方の構造が段階的に更新され、無効なウィンドウは記録される前に常に縮小されるため、スライディング ウィンドウは引き続きこれを正しく処理します。
