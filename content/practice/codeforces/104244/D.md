 ## 解決策
 ## 問題の理解

 この問題は、最初の金額を持って都市 1 から出発し、直行便を利用して都市 n に到達したいと考えている旅行者について説明しています。 各フライトには費用がかかり、旅行者が現在少なくともその費用を利用できる場合にのみ利用できます。 問題は、旅行者が最初に強盗に遭い、その資金が限られていることですが、どの都市でも追加のお金を稼ぐ方法があるということです。ショーを行うことで、その都市でショーごとに一定の収入が得られます。 彼は飛行機に乗る前に市内で好きなだけショーを行うことができるため、現地で利用できる予算を効果的に増やすことができます。 

このタスクは、目的地の都市に到着できるかどうかを判断し、到着できる場合は、都市 1 から都市 n までの経路に沿って必要なすべてのフライトを実行可能にするために必要な最小限のパフォーマンス数を計算することです。 

重要な問題は、お金が単純な追加のパスコストではないことです。 代わりに、エッジを横断する実現可能性は、これまでにどれだけのお金を蓄積したかに依存し、その蓄積はショーを行う場所と頻度によって決まります。 これにより、パスの選択とリソースの蓄積の間に結合が作成されます。 

この制約 (最大 800 の都市と数千のフライト、および非常に大きな金額) により、各都市での可能なすべての金額またはパスごとの可能なすべての公演数を明示的にシミュレートするソリューションは除外されます。 パスごとに正確な金額やパフォーマンス カウントを追跡する単純な状態空間探索では、お金は最大 10^9 まで増加する可能性があり、パフォーマンス カウントには原則として制限がないため、爆発的に増加します。 

初期資金がすでにパフォーマンスなしで最適なパスを通過するのに十分な場合、微妙なエッジケースが発生します。 このような場合、正しい解決策は不必要な探索を行わずにゼロを返す必要があります。 貪欲な戦略により、エッジ コストが局所的に最も安いパスが選択されるが、後で多くの高価なパフォーマンスが強制される場合、別の障害モードが発生します。 最適な解決策は、代わりに、全体的に必要なパフォーマンスの数を減らすために、少し高価なフライトを早めに利用することです。 

## アプローチ

 強引なアイデアは、これを、各州が現在の都市と現在の金額からなるペアである拡張された州空間にわたる最短経路問題として扱うことです。 各州から、ショーを行うか（wi でお金を増やす）、またはせいぜい現在の金額で出発する飛行機に乗ることができます。 これはすべての選択肢を明示的にモデル化しているため、原則として正しいです。 

ただし、可能な通貨値の数には制限がなく、関連する最大しきい値で制限したとしても、遷移によって依然として膨大な数の状態が生成されます。 各都市はさまざまな資金レベルで再訪問することができ、最悪の場合には州の空間が指数関数的に増加します。 

重要な観察は、目的は資金を最小限に抑えることではなく、公演数を最小限に抑えることであるということです。 これは、視点を逆転させることを示唆しています。つまり、資金を追跡する代わりに、フライトが使用可能になる状態に達するまでにどれだけのパフォーマンスが必要かを尋ねます。 

固定都市について、その都市に到達するために必要なパフォーマンスの最小数がわかっているとします。 これによりある程度の資金が得られますが、パスが異なれば、資金とパフォーマンスとのトレードオフも異なる可能性があります。 重要な洞察は、コスト フライトに到達するためには、十分な蓄積資金がある都市に到達できるかどうかだけを気にしており、同じか、より少ないパフォーマンスで都市に到達するすべての方法の中で、将来のエッジに使用できる残りの電力を最大化する方法を好むということです。

これは、コストがパフォーマンスの数であり、必要に応じてエッジを満たすのに十分なお金をトランジションで「買う」というダイクストラのような定式化につながります。 金額の増分を 1 つずつ明示的にシミュレートする代わりに、各フライトのしきい値に達するまでに必要なショーの数を計算します。 

エッジに沿って移動するための移行コストは、既に持っているお金を超えてどれだけの追加のお金が必要になるか、その都市の Wi で割って切り上げた関数になります。 これにより、問題は、エッジの重みが現在最もよく知られている状態に依存するグラフ上の最短経路に変換されます。

 ## アルゴリズムのチュートリアル

 私たちは、各都市に到達するために必要な最小限の公演数を維持しながら、最もよく知られている経路に沿ったその公演数で達成可能な最大金額を暗黙的に追跡します。 

公演数順の優先キューを使用しております。 

1. すべての都市までの距離を無限大として初期化し、開始都市 1 のパフォーマンスをゼロに設定します。 開始金額は初期値 p です。 
2. 都市 1 をコスト 0 の優先キューにプッシュします。 
3. 公演数が最も少ない都市を繰り返し抽出します。 これにより、実行される総作業量を最小限に抑えるという観点から、常に最も有望な状態を最初に拡張することができます。 
4. 現在の都市から近隣都市への出発便ごとに、現在利用可能な資金がその費用を支払うのに十分であるかどうかを確認します。 
5. お金が足りない場合は、必要な閾値に達するために、現在の都市でさらに何回の公演が必要かを計算します。 各公演ごとにwiマネーが付与されるため、追加公演数は不足額の天井分割で計算されます。 
6. 近隣都市に到達するための合計公演数を更新します。 この値がその都市の最もよく知られている値を改善する場合は、それを更新して優先キューにプッシュします。 
7. 到達可能なすべての州が処理されるか、目的地の都市が決定されるまで続行します。 

核となる考え方は、各緩和ステップが財務上の制約をパフォーマンスに関する個別のコスト増分に変換するというものです。 

### なぜ効果があるのか

 このアルゴリズムは、都市が優先キューから抽出されるたびに、最適な一連の決定の下でその都市に到達するために必要な最小限のパフォーマンス数を見つけたという不変条件を維持します。 より少ないパフォーマンスでその都市に到達するための代替手段は、キューの早い段階で処理される必要がありました。これは、すべての移行はマイナスではないコストを追加するだけであるためです。 「不十分な資金」を必要なパフォーマンスの決定論的な数に変換することで、すべてのエッジ緩和がそのエッジを現在の状態から使用可能にする最も安価な方法を確実に捕捉します。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m, p = map(int, input().split())
    w = [0] + list(map(int, input().split()))
    
    g = [[] for _ in range(n + 1)]
    for _ in range(m):
        a, b, s = map(int, input().split())
        g[a].append((b, s))
    
    INF = 10**18
    dist = [INF] * (n + 1)
    
    # (performances, city, current_money)
    pq = []
    
    dist[1] = 0
    heapq.heappush(pq, (0, 1, p))
    
    while pq:
        d, u, money = heapq.heappop(pq)
        
        if d != dist[u]:
            continue
        
        for v, cost in g[u]:
            cur_money = money
            
            if cur_money >= cost:
                nd = d
                nm = cur_money - cost
            else:
                need = cost - cur_money
                add = (need + w[u] - 1) // w[u]
                nd = d + add
                nm = cur_money + add * w[u] - cost
            
            if nd < dist[v]:
                dist[v] = nd
                heapq.heappush(pq, (nd, v, nm))
    
    print(-1 if dist[n] == INF else dist[n])

if __name__ == "__main__":
    solve()
```このコードは、各州がこれまでに使用されたパフォーマンスの数と、都市に到着した後の現在のお金の両方を保持するダイクストラ スタイルの拡張を実装しています。 隣接リストには、直行便とそのコストが保存されます。 エッジを緩和するときは、可能であれば直接支払うか、しきい値コストに達するまでに必要なパフォーマンスの数を計算し、それをパス上の追加コストに変換します。 

微妙な実装の詳細は、遷移後の残りのお金がヒープ状態に保存されることです。 残りのお金が正しく繰り越されると、将来のエッジを通過するのが安くなる可能性があるため、これは重要です。 

もう 1 つの重要な点は、追加のパフォーマンスを計算するときの整数の除算です。 天井分割を使用すると、無効なトランジションが発生する可能性がある、必要なショーの数を過小評価することがなくなります。 

## 実用的な例

 ### 例 1

 旅行者が早めに行動するか、後で支払うかを決定する必要がある 3 つの都市の単純なチェーンを考えてみましょう。 

| ステップ | 都市 | 公演 | お金 |
 | --- | --- | --- | --- |
 | 開始 | 1 | 0 | p |
 | 移動 | 2 | エッジ経由で更新 | 計算された |
 | 移動 | 3 | 最終 | 最終 |

 このトレースは、アルゴリズムが収益を恣意的に事前計算するのではなく、エッジによって強制された場合にのみパフォーマンスを調整することを示しています。 

実証された重要な動作は、フライトのロックを解除することが厳密に要求されない限り、アルゴリズムがパフォーマンスを向上させることはないということです。 

### 例 2

 高コストのエッジが早期に現れても、全体的な進行が安くなるケースを考えてみましょう。 

| ステップ | 都市 | 公演 | お金 |
 | --- | --- | --- | --- |
 | 開始 | 1 | 0 | p |
 | オプション A | 直接の格安パス | 後のコストが高くなる | 残りわずか |
 | オプション B | 初期投資 | 初期費用が若干高め | 高い柔軟性 |

 このアルゴリズムは、優先キューを介して両方の遷移を正しく調査し、最小限のパフォーマンス カウントを維持します。 

これは、局所的に高価な決定が後で全体的なパフォーマンスの低下につながる場合でも考慮されることを裏付けています。

 ## 特殊なケース

 1 つのエッジ ケースは、最初の資金が開始都市からのすべての送出エッジをすでに満たしているときに発生します。 その状況では、アルゴリズムはパフォーマンス計算をトリガーせず、ゼロコストの遷移を直接伝播します。 たとえば、p が大きく、都市 1 からのすべての航空コストが p 未満の場合、緩和するたびにパフォーマンス カウントが 0 に保たれます。 

もう 1 つのケースは、Wi がエッジ コストと比較して非常に大きい場合です。 そうなると、1回のパフォーマンスで必要な金額を大幅に超過してしまう可能性があります。 このアルゴリズムは、セル除算を計算することでこれを処理し、必要な増分を過小評価しないようにし、余剰分を正しく繰り越して後のエッジがその恩恵を受けるようにします。 

3 番目のケースには、各エッジが利用可能なお金をわずかに超える長いチェーンが含まれます。 ここでは、小さなパフォーマンスの増加が繰り返され、蓄積されます。 プライオリティ キューにより、中間状態がパフォーマンス コストの高い順に探索されるようになり、最適ではないルートへの早まったコミットが防止されます。
