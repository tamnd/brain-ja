 ## 解決策
 ## 問題の理解

 2 つのシーケンスが与えられ、それらを A と B と呼びます。各クエリには、A[1..x] と B[1..y] という 2 つのプレフィックスが与えられます。 タスクは、これら 2 つのプレフィックスが対称的な方法で「異なる要素に関して一致する」かどうかを判断することです。A のプレフィックスに表示されるすべての値は B のプレフィックスにすでに表示されている必要があり、B のプレフィックスに表示されるすべての値は A のプレフィックスにすでに表示されている必要があります。 

同様に、各プレフィックスをそれに含まれる個別の値のセットに圧縮すると、クエリはこれら 2 つのセットが同一であるかどうかを尋ねます。 

微妙な点は、重複はまったく問題ではないということです。 プレフィックス内の各値の存在のみが重要であり、それが何回出現するかは問題ではありません。 

複雑さの観点から見ると、この種の問題に対する自然な制約は十分に大きいため、クエリごとにセットを再計算することは不可能です。 n 個の要素と q 個のクエリがある場合、クエリごとにプレフィックスをスキャンするアプローチでは O(nq) が発生し、これは一般的な制限をはるかに超えています。 クエリごとにセットを個別に維持する場合でも、単純に行うとすぐに機能が低下します。 

2 番目の微妙な点は、値が本質的に小さくない、または連続しているわけではないことです。 圧縮やハッシュを行わずに直接周波数配列に依存するソリューションでは、最初に値を正規化するかマップを使用する必要がありますが、これを繰り返し行うとボトルネックになる可能性があります。 

典型的な失敗例は、一方の側にもう一方の側にはない重複が含まれている場合、または要素が異なる順序で同一のセットで表示されている場合に発生します。 

たとえば、A = [1, 2, 1, 3] および B = [1, 3, 2] と仮定します。 x = 4、y = 3 の場合、両方のプレフィックスに正確に {1, 2, 3} が含まれるため、答えは YES です。 個別のセットではなくプレフィックスの合計または頻度を比較する不注意な実装では、これが異なるものとして誤って扱われてしまいます。 

もう 1 つのエッジ ケースは、一方のプレフィックスが厳密に小さいものの、もう一方のプレフィックスの異なる要素がすべてすでに含まれている場合です。 たとえば、A = [1、2、3、3、3]、B = [1、2、3、4]。 x = 5、y = 3 では、A には {1, 2, 3} があり、B には {1, 2, 3, 4} があるため、ほとんどの要素が重複していますが、答えは NO になります。 

主な問題は、多くのクエリの下でプレフィックス セットを効率的に維持することです。 

## アプローチ

 直接的なアプローチは、A のすべてのプレフィックスと B のすべてのプレフィックスに対して個別のセットを構築することです。プレフィックスごとに、これまでに確認された要素のセットを保存し、クエリごとに 2 つのセットを比較します。 

これは正しいですが、プレフィックスごとにセットを構築し、クエリごとにそれらを比較するとコストがかかります。 セットの比較が最適化されている場合でも、各比較ではプレフィックス内の個別の要素の数に比例して時間がかかる可能性があります。 すべての要素が異なる最悪の場合、各クエリのコストは O(n) となり、合計時間は O(nq) になります。 

重要な点は、プレフィックスにとって重要なのは完全なセット構造ではなく、2 つのプレフィックスにまったく同じ異なる要素が含まれているかどうかであるということです。 これは、各プレフィックスをコンパクトなフィンガープリントに変換することを示唆しています。 2 つのプレフィックスが同一のセットを持つ場合、それらのフィンガープリントは一致する必要があります。 個別の要素のセットのローリング表現を維持できれば、O(1) で各クエリに答えることができます。 

これを行う標準的な方法は、それぞれの個別の値にランダムなハッシュを割り当て、プレフィックスごとに、これまでに確認されたすべての個別の要素のハッシュの XOR を維持することです。 重要な点は、重複を 2 回カウントしてはいけないということです。そのため、要素がプレフィックスにすでに出現しているかどうかを追跡します。 最初に要素を見たとき、そのハッシュをプレフィックス値に XOR します。 それ以降の出現は無視されます。 

これにより、各プレフィックスが 1 つの整数 (または安全のため整数のペア) に変換され、セットの等価性がハッシュの等価性になります。 その後、各クエリは、事前に計算された 2 つのプレフィックス ハッシュを比較することになります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (クエリごとに設定) | O(nq) | O(n) | 遅すぎる |
 | プレフィックス個別ハッシュ | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 A と B に対して別々にソリューションを構築します。 

1. 考えられる各値にランダムな 64 ビット整数ハッシュを割り当てます。 これは、その値の一意のフィンガープリントの寄与として機能します。 
2. 値がすでに出現しているかどうかを示すブール配列またはハッシュ マップを維持しながら、配列 A を左から右にスキャンします。 実行中の XOR 値を維持する`hashA[i]`A[1..i] 内の個別の要素のセットを表します。 A[i] が初めて見つかった場合は、そのハッシュを現在の値に XOR します。 
3. 配列 B に対して同じプロセスを繰り返し、次のように生成されます。`hashB[j]`。 
4. 各クエリ (x, y) について、比較します。`hashA[x]`そして`hashB[y]`。 等しい場合はYESを出力し、等しくない場合はNOを出力します。 

重要な設計上の選択は、繰り返しの出現を無視することです。 これがないと、XOR は重複を誤ってキャンセルし、正確性を損なってしまいます。 

### なぜ効果があるのか

 どのプレフィックスでも、各値はそのプレフィックス内に少なくとも 1 回出現する場合にのみ、1 回だけ寄与します。 XOR は可換で自己反転であるため、XOR の累積は集合インジケーターのように動作します。 値は最初に出現したときにのみ挿入するため、プレフィックス ハッシュは、そのプレフィックス内のすべての個別要素のハッシュの XOR になります。 2 つのプレフィックスは、同じハッシュのマルチセットを XOR した場合に限り、同一の別個のセットを持ちます。これは、十分に大きなランダム ハッシュを使用すると、高い確率で同じ結果が生成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, q = map(int, input().split())
    A = list(map(int, input().split()))
    B = list(map(int, input().split()))

    import random
    rnd = random.getrandbits

    # assign hash per value
    H = {}

    def get_hash(x):
        if x not in H:
            H[x] = rnd(64)
        return H[x]

    seenA = set()
    seenB = set()

    prefA = [0] * (n + 1)
    prefB = [0] * (m + 1)

    cur = 0
    for i in range(1, n + 1):
        v = A[i - 1]
        if v not in seenA:
            seenA.add(v)
            cur ^= get_hash(v)
        prefA[i] = cur

    cur = 0
    for i in range(1, m + 1):
        v = B[i - 1]
        if v not in seenB:
            seenB.add(v)
            cur ^= get_hash(v)
        prefB[i] = cur

    out = []
    for _ in range(q):
        x, y = map(int, input().split())
        out.append("YES" if prefA[x] == prefB[y] else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションは、両方の配列のプレフィックス表現を独立して構築します。 重要な実装の詳細は、`seenA`そして`seenB`セット。 これらがないと、繰り返し発生すると XOR 値が誤って切り替わり、「設定のみ」の動作が壊れてしまいます。 

もう 1 つの微妙な点は、Python の組み込みハッシュに依存するのではなく、辞書ベースのランダム ハッシュ割り当てを使用することです。これはプロセスごとにソルト処理されており、制御された方法で実行すると安定しません。 明示的なランダムな 64 ビット整数により再現性が保証されます。 

最後に、プレフィックス配列には 1 のインデックスが付けられ、クエリの処理が簡素化され、インデックスのシフトの繰り返しが回避されます。

 ## 特殊なケース

 重要なエッジケースの 1 つは、繰り返しが多いことです。 A = [5,5,5,5] および B = [5] の場合、A のすべてのプレフィックスは、最初に出現した後は同じように動作する必要があります。 アルゴリズムはこれを処理します。`seenA`XOR トグルの繰り返しを防ぐため、プレフィックス ハッシュは最初の 5 の直後に安定します。 

もう 1 つのエッジ ケースは、要素が異なる方法でインターリーブされているが、セットは一致する場合です。 A = [1,2,1,3,2] および B = [3,2,1] の場合、B の方が短く順序付けされていない場合でも、最終的なプレフィックス ハッシュは一致する必要があります。 アルゴリズムは両方を XOR(h(1), h(2), h(3)) に正しく変換します。 

3 番目のエッジ ケースは、同一の (x, y) を含むクエリが繰り返されることです。 答えは事前に計算された配列のみに依存するため、クエリを繰り返しても余分な状態変更は発生せず、再計算せずに常に一貫した結果が返されます。
