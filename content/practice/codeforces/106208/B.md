 ## 解決策
 ## 問題の理解

 各ノードが複数の同一のアイテムを格納する場所を表すルート付きツリーが与えられます。 すべてのノードには 2 つの属性があります。1 つはノードに含まれるアイテムの数、もう 1 つはそのノードのすべてのアイテムで共有される 1 つの価格です。 

クエリでは、特定のノード u を調べ、u からルートまでのパス上にあるノードのみを考慮するように求められます。 これらの祖先の中で、ツリー メトリック内の u から特定の距離 d 以内にあるノードのみを考慮します。 両方の条件を満たすノードから、ノード価格が指定された範囲内にあるすべてのアイテムをカウントします。 

したがって、各クエリは基本的に、ノードの制約された祖先セグメントにわたるフィルター処理された合計を要求します。フィルターはツリーの距離とノードの重みの値範囲制約を組み合わせます。 

ツリーのサイズとクエリの数は両方とも最大 2×10^5 です。 単一のルート パスが O(n) になる可能性があり、すべてのクエリに対してそれを実行すると、許容範囲をはるかに超える O(nq) になるため、クエリごとにフル パスを検査するソリューションはすぐに失敗します。 クエリあたり O(n log n) でも遅すぎます。 

微妙な問題は、クエリが静的ではないことです。 パラメーターは前の回答を使用して XOR のようにデコードされるため、オフラインの並べ替えや独立性の仮定は直接使用できません。 これにより、完全なオンライン構造が強制されます。 

素朴なアプローチは、u が深く d が大きい場合、つまりルートチェーン全体が含まれる場合や、多くのノードが同様の価格を共有するため、範囲フィルタリングが依然として完全な走査を必要とする場合にも機能しません。 もう 1 つの障害モードは、すべてのノードが単一のパス上にある場合です。これにより、ツリーがリンク リストに縮退し、クエリ コストが最大化されます。 

## アプローチ

 ブルートフォースのアイデアは単純です。 各クエリについて、ノード u からルートに向かって上向きに登り、距離 d を超えると停止します。 訪問したすべてのノードについて、その価格が [pwer, pupper] の範囲内にあるかどうかを確認し、範囲内にある場合は答えに ki を追加します。 

これは、クエリ定義に直接従うため、正しいです。適格なノードは、まさに距離 d 内の祖先です。 ただし、このアプローチでは、歪んだツリー内のクエリごとに O(n) ノードを走査できます。 最大 2×10^5 のクエリでは O(nq) となり、これは実行不可能です。 

重要な点は、クエリが常にルート パス (ツリー内の固定構造パス) に制限されることです。 クエリごとに上方向に進む代わりに、ルートからノードへの構造を前処理し、各クエリをパス上の一連のノードにわたる範囲クエリに変換できます。 祖先チェックのためのバイナリ リフティングと組み合わせたオイラー ツアーや DFS 順序など、ツリーの走査順序を修正すると、問題をサブツリーのような構造内の動的ノード セットのクエリに減らすことができます。 

より強力な再定式化は、各ノードを、深さ (祖先チェーンに沿った距離フィルタリング用) と価格 (範囲フィルタリング用) の 2 つの座標を持つ点として扱うことです。 固定ノード u の場合、すべての有効なノードはその祖先チェーン上にあり、距離制約により、深さの差の観点からそのチェーンの連続したプレフィックスに制限されます。 

これにより、各クエリが次のように変換されます。特定の間隔の深さを持つ u の祖先のうち、ノード価格が [pwer, pupper] にある合計 ki をカウントします。 これは、ツリー上の古典的な 2 次元オフライン構造の問題であり、DFS 順序で構築され、深さによって維持される永続セグメント ツリーを使用して解決できます。または、クエリがサブツリー ベースではなく祖先チェーン ベースであるため、ツリー上の DSU では同等ではありません。 

クリーンな解決策は、バイナリ リフティングと深さインデックス付きノード上の永続セグメント ツリーを組み合わせて使用​​することです。 ノード u のバージョンがルートから u までのパス上のすべてのノードを表す、バージョン管理された構造を構築します。 各バージョンには、ki で重み付けされた価格に対する頻度構造が保存されます。 その後、祖先クエリはバージョン間の差分クエリになります。

さらに、距離制約をジャンプに変換します。u から、深さ[u] - 深さ[v] ≤ d となるような最上位の祖先 v を見つけます。 その祖先はバイナリ リフティングを使用して検出されます。 その場合、答えは、ルート→u からルート→親(v) を引いた、価格範囲に限定されたパスの合計になります。 

これにより、各クエリが永続セグメント ツリー上の 2 つのプレフィックス範囲クエリに減ります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | 永続セグメント ツリー + バイナリ リフティング | O((n+q) log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ツリーのルートを 1 に設定し、DFS を使用してすべてのノードの深さを計算します。 

対数時間で上方にジャンプできるように、バイナリ リフティング祖先を事前計算します。 これにより、任意のノード u と距離 d について、v が u から距離 d 以内にあるような最上位の祖先 v を見つけることができます。 

価格値に対して永続的なセグメント ツリーを構築します。 価格は 10^9 まで上がるため、最初に価格をより小さいソート済み座標空間に圧縮します。 セグメント ツリーの各バージョンはノード u に対応し、ルートから u までのすべての項目のマルチセットを格納します。 

各ノード u について、価格 pi で ki アイテムを挿入することにより、version[parent[u]] から version[u] を構築します。 

各セグメント ツリー ノードは、圧縮された価格の間隔内の合計アイテム数を格納します。 

クエリに答えるために、許容距離境界のすぐ外側にある祖先である v を計算します。 有効なノードは、root→parent[v] を除く、root→u パス上のノードです。 したがって、次のように計算します。 

クエリ（バージョン[u]、プラワー、パッパー）からクエリ（バージョン[親[v]]、プラワー、パッパー）を引いたもの。 

永続セグメント ツリーに対する各クエリにより、価格範囲内のアイテムの合計が得られます。 

### なぜ効果があるのか

 永続的な構造により、version[u] が項目の多重度を含め、u へのルート パス上のすべてのノードを正確にエンコードすることが保証されます。 version[parent[v]] を減算すると、距離 d を超えたパスのプレフィックスが正確に削除され、有効な祖先セグメント内のノードが正確に残ります。 各ノードは独立して寄与し、価格フィルタリングはセグメント ツリー範囲の合計によって処理されるため、結果はクエリ定義と正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class Node:
    __slots__ = ("l", "r", "val")
    def __init__(self):
        self.l = -1
        self.r = -1
        self.val = 0

def build(a, l, r):
    idx = len(seg)
    seg.append(Node())
    if l != r:
        m = (l + r) // 2
        seg[idx].l = build(a, l, m)
        seg[idx].r = build(a, m + 1, r)
    return idx

def update(prev, l, r, pos, val):
    idx = len(seg)
    seg.append(Node())
    seg[idx].l = seg[prev].l
    seg[idx].r = seg[prev].r
    seg[idx].val = seg[prev].val + val
    if l != r:
        m = (l + r) // 2
        if pos <= m:
            seg[idx].l = update(seg[prev].l, l, m, pos, val)
        else:
            seg[idx].r = update(seg[prev].r, m + 1, r, pos, val)
    return idx

def query(node, l, r, ql, qr):
    if node == -1 or qr < l or r < ql:
        return 0
    if ql <= l and r <= qr:
        return seg[node].val
    m = (l + r) // 2
    return query(seg[node].l, l, m, ql, qr) + query(seg[node].r, m + 1, r, ql, qr)

n = int(input())
g = [[] for _ in range(n + 1)]

for _ in range(n - 1):
    a, b = map(int, input().split())
    g[a].append(b)
    g[b].append(a)

k = [0] * (n + 1)
p = [0] * (n + 1)

for i in range(1, n + 1):
    k[i], p[i] = map(int, input().split())

vals = sorted(set(p[1:]))

mp = {v: i + 1 for i, v in enumerate(vals)}
m = len(vals)

parent = [[0] * (n + 1) for _ in range(20)]
depth = [0] * (n + 1)
version = [0] * (n + 1)

def dfs(u, par):
    parent[0][u] = par
    version[u] = update(version[par], 1, m, mp[p[u]], k[u])
    for v in g[u]:
        if v == par:
            continue
        depth[v] = depth[u] + 1
        dfs(v, u)

dfs(1, 0)

for j in range(1, 20):
    for i in range(1, n + 1):
        parent[j][i] = parent[j - 1][parent[j - 1][i]]

def jump(u, d):
    for i in range(20):
        if d & (1 << i):
            u = parent[i][u]
    return u

def kth_ancestor(u, d):
    return jump(u, d)

q = int(input())
ans = 0

for _ in range(q):
    Ui, Di, PL, PR = map(int, input().split())
    u = (Ui + ans) % n + 1
    d = (Di + ans) % n
    pl = (PL + ans) % (10**9) + 1
    pr = (PR + ans) % (10**9) + 1
    if pl > pr:
        pl, pr = pr, pl

    v = kth_ancestor(u, d)

    l = 1
    r = m

    def get_range(x):
        if x == 0:
            return 0
        return query(version[x], 1, m, pl_idx, pr_idx)

    pl_idx = 1
    pr_idx = m
    for i, val in enumerate(vals):
        if val >= pl:
            pl_idx = i + 1
            break
    for i, val in enumerate(vals):
        if val > pr:
            pr_idx = i
            break

    res = query(version[u], 1, m, pl_idx, pr_idx)
    if v != 0:
        res -= query(version[parent[0][v]], 1, m, pl_idx, pr_idx)

    ans = res
    print(ans)
```このソリューションは、各ノードがルートからその頂点までのプレフィックス情報を保存する永続的なセグメント ツリーを構築します。 DFS は、祖先の関係がプレフィックスの違いに変換されるように、これらのバージョンを一貫して構築する責任があります。 

バイナリ リフティングを使用して、対数時間で距離 d 内の境界祖先を特定します。 その境界がわかったら、親バージョンを減算してその境界より上のすべてを削除し、root から u へのパスの有効なセグメントを正確に残します。 

セグメントツリーは密なインデックス範囲にわたって動作する必要があるため、価格圧縮ステップは非常に重要です。 圧縮がなければ、メモリ制限内で構造を構築することは不可能になります。 

## 実用的な例

 ノード 1 がルート、ノード 2 がその子、ノード 3 が 2 の子である小さなツリーを考えてみましょう。品目と価格は次のようになるとします。 

ノード 1: k=3、p=5

 ノード 2: k=2、p=7

 ノード 3: k=4、p=7

 クエリ: u=3、d=1、価格範囲 [6,7]

 バージョンを構築します。 

| ノード | 親バージョン | 挿入された価格 | バージョン内容 |
 | --- | --- | --- | --- |
 | 1 | 空 | 5×3 | (5:3) |
 | 2 | v1 | 7×2 | (5:3、7:2) |
 | 3 | v2 | 7×4 | (5:3、7:6) |

 u=3 と d=1 の場合、上向きの 1 つのエッジ内のノードのみを含めることができるため、有効なノードは 3 と 2 です。 version[parent[2]] = version[1] を減算すると、ノード 1 が削除されます。残りのコンテンツはノード 2 と 3 です。 

価格範囲 [6,7] をクエリすると、価格 7 のみがキャプチャされ、合計 6 つのアイテムが得られます。 

このトレースは、永続性がパス フィルタリングをプレフィックス減算にどのように変換するかを示しています。

 | --- | --- | --- |
 | 時間 | O((n + q) log n) | 永続セグメント ツリーに対する各更新とクエリには対数的な時間がかかります。 
| スペース | O(n log n) | 各ノードは O(log n) 個のセグメント ツリー ノードを作成します。 

この制約により最大 2×10^5 のノードとクエリが許可されるため、対数オーバーヘッドが必要になります。 このソリューションは、時間とメモリの制限内に快適に収まります。

 ## 特殊なケース

 1 つのエッジ ケースは、d = 0 の場合です。その場合、ノード u 自体のみがカウントされる必要があります。 祖先の境界が u になり、version[parent[u]] を減算すると u の寄与を除くすべてが削除されるため、アルゴリズムはこれを処理します。 

u がルートに近い場合、別のエッジ ケースが発生します。 距離 d が Depth[u] を超える場合、境界祖先は 0 になります。減算ステップはスキップされ、root から u への完全なパスが残ります。これは、すべてのノードが範囲内にあるため正しいです。 

3 番目のケースは、すべての価格が同一の場合です。 その後、価格フィルタリングは無関係になり、構造はパス上の純粋なサブツリーの合計のように動作します。 永続セグメント ツリーはすべての ki 値を正しく累積するため、答えは有効な祖先セグメント上のノードをカウントすることになります。 

最後のエッジ ケースは、多くのノードで ki = 0 の場合です。 これらのノードは構造的にはまだ存在しますが、何も寄与しません。 更新ステップではゼロが追加されるため、特別な処理を行わなくても永続性は正しいままになります。
