 ## 問題の理解

 私たちは貯水池のコレクションを与えられました。 各貯水池には固定容量とその中に蓄えられている現在の水の量があります。 許可される操作は非常に具体的です。つまり、最大 2 つの貯水池、たとえば i と j を選択し、j からすべての水を i に注ぐことができます。 オーバーフローした場合は、その容量で満杯になるだけで、そうでない場合は、合わせた水で終わります。 

目標は、このような注入操作を最大 1 回実行した後で、最終的な水量が正確に x になる貯水池を取得できるかどうかを判断することです。 何もしないことも（どこかの貯水池にすでに x 個の水がある場合）、1 つの目的地貯水池 i と 1 つの供給源貯水池 j を選んで i に注ぐこともできます。 

出力は、そのような操作を記述するペア i j 、またはリザーバー i に最初から x がすでに含まれている場合は i 0、または有効な構成が存在しない場合は -1 -1 です。 

制約は n = 10^5 までなので、リザーバーのすべてのペアを直接チェックするソリューションでは、最悪の場合、最大 10^10 の操作が必要となり、これは 1 秒の制限をはるかに超えています。 これにより、二次アプローチは即座に除外されます。 

微妙な点は、容量制限に達した場合、j から i に注入する場合、完全な転送は必要ないことです。 結果の値は min(vi, wi + wj) です。 これにより、単調ではあるが線形ではない飽和動作が作成されます。 

重要なエッジケース:

 貯水池にはすでに x 個の水が含まれている可能性があり、すぐに i 0 を出力する必要があります。たとえば、ある i に対して x = 3 および wi = 3 である場合、それはすでに有効な答えです。 

貯水池全体の水の総量が大きい場合でも、容量の制約により正確に x に到達できない可能性があるため、どの組み合わせも機能しない可能性があります。 たとえば、vi = [2, 2]、wi = [2, 2]、x = 3 では不可能になります。 

入力解釈において i と j が等しいことも重要ですが、同じコンテナに注ぎ込んでも意味のある変更は何もないため、実質的には何も新しいものにはなりません。 

## アプローチ

 ブルートフォース手法では、考えられるすべてのペア (i, j) が考慮されます。 各ペアについて、j を i に注ぎ込むことをシミュレートし、min(vi, wi + wj) を計算します。 x と等しい場合は、そのペアを返します。 これには、n^2 個の遷移をそれぞれ一定時間で評価する必要があり、複雑さは O(n^2) になります。 n が 100000 までの場合、これは不可能です。 

重要な観察は、j から注いだ後の貯留層 i の最終値は wi と wj のみに依存し、他の構造には依存しないということです。 2 つのケースのうちの 1 つを使用して x に到達できるかどうかだけを気にします。 

最初のケースは自明です。一部の wi はすでに x に等しいです。 

2 番目のケースは自明ではありません。min(vi, wi + wj) = x となるペア (i, j) が必要です。 この状態は、相互に排他的な 2 つの状況に分けられます。 

wi + wj = x および wi + wj が vi を超えない、つまり飽和が起こらないか、vi が十分小さいため結果が vi および vi = x まで飽和しますが、これは最初のケースですでにカバーされています。 

したがって、非ゼロ効果に寄与する j を持つ有効なペアの場合、wi + wj = x および x ≤ vi が必要です。 これは、j が wi​​ の補数を提供する必要があることを意味します。 

これを書き直すと、古典的な補数検索が得られます。各 i について、wj = x - wi となるような j を見つける必要があります。同時に、i が少なくとも x 単位の水容量を保持できること、vi ≥ x を保証する必要もあります。 

これにより、各水位の位置を保存し、補数を一致させるという問題が軽減されます。

 ## アルゴリズムのチュートリアル

1. すべてのリザーバーをスキャンし、wi が x に等しいかどうかを確認します。 そうであれば、そのインデックスを 0 で出力して停止します。 これは、操作が必要ない場合に対処します。 
2. 水量 wi からその値を持つインデックスのリストまでのハッシュ マップを構築します。 これにより、高速な補数検索が可能になります。 
3. 各リザーバ i を潜在的なターゲットとして反復します。 
4. vi が x より小さい場合、i を完全にスキップします。 注ぐも容量制限により×まで到達できません。 
5. j から必要な寄与を need = x - wi として計算します。 
6. need が負の場合、この i はすでに x を超えており、加算によって修正できないため、この i をスキップします。 
7. マップ内に値が必要な j が存在するかどうかを確認します。 
8. そのような j が存在する場合、複数の同一エントリが存在しない限り、j が同じインデックス i ではないことを確認し、i j を出力します。 
9. すべての i をスキャンしてもペアが機能しない場合は、-1 -1 を出力します。 

機能する理由: このアルゴリズムは、すべての有効な構成を直接ヒットまたは正確な補数和に分割します。 ハッシュ マップは、寄与する可能性のあるすべてのリザーバ j が一定の平均時間内に見つかることを保証します。 容量フィルター vi ≥ x により、最終値を合法的に保持できるターゲットのみが考慮されるようになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, x = map(int, input().split())
    v = list(map(int, input().split()))
    w = list(map(int, input().split()))

    pos = {}
    for i, val in enumerate(w):
        if val == x:
            print(i + 1, 0)
            return
        if val not in pos:
            pos[val] = []
        pos[val].append(i)

    for i in range(n):
        if v[i] < x:
            continue
        need = x - w[i]
        if need < 0:
            continue
        if need not in pos:
            continue

        for j in pos[need]:
            if j != i:
                print(i + 1, j + 1)
                return
            if len(pos[need]) > 1:
                print(i + 1, j + 1)
                return

    print(-1, -1)

if __name__ == "__main__":
    solve()
```このソリューションでは、まず、ある貯水池に既に正確に x 個の水が含まれている、即時に成功するケースを処理します。 この操作はオプションであり、これがその操作に有効な唯一の出力形式であるため、これが必要です。 

辞書は水位ごとにインデックスをグループ化し、補体の定時間検索を可能にします。 i に対するループにより、容量に基づいて x を合法的に収容できるリザーバーのみを試行することが強制されます。 

内部選択では、リザーバーからリザーバー自体に注入しても意味のある変化は何もないため、重複が存在しない限り同じインデックスを使用するという劣化したケースを慎重に回避します。

 ## 特殊なケース

 重要なエッジケースの 1 つは、複数の貯水池が補完として必要な同じ水の値を共有する場合です。 たとえば、x = 5 および wi = 2 で、wj = 3 のリザーバーが 2 つある場合、i とは異なる有効な j を選択できるか、別の同一のインデックスを再利用できることを確認する必要があります。 このアルゴリズムは、完全なリストをハッシュ マップに保存することでこれを処理し、必要に応じて個別のインデックスを選択できるようにします。 

wi ≤ vi および wi ≤ vi は wi が容量を超えることができないことを意味するため、wi がすでに x を超えることが不可能である場合、別のエッジ ケースが発生しますが、それでも wi が x より大きくなる可能性があります。 その場合、ニーズはマイナスになり、アルゴリズムはそのリザーバーを正しくスキップします。 

最後のエッジケースは、i と j が一致する場合です。 wi = x - wi の場合、j は i と等しくなります。 これは、別の同一のリザーバーが利用可能な場合、または問題により簡単な自己使用が許可される場合にのみ有効です。 この実装では、リスト サイズを明示的にチェックして、必要に応じて 2 回目の出現を許可し、無効な自己転送を防ぎます。
