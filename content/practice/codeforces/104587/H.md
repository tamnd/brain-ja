 ## 問題の理解

 私たちは、同じ個室のトイレに入れられる必要がある人々の流れを与えられ、そこでは各人が正確に 1 単位時間だけ個室を占有します。 がある`s`失速、つまり、いつでも`s`人は同時に中に入ることができます。 

人にはそれぞれ期限がある`d`、つまり、遅くとも時間までに 1 回の使用単位を完了する必要があります。`d`。 時間は離散的であり、各人が正確に 1 つのスロットを占有するため、誰かが時間に開始した場合`x`、時間通りに終わります`x + 1`。 

2 つ目の問題は、一部の人々が、共有の希少資源、つまり、マークが付いているトイレット ペーパー 1 ロールを必要とすることです。`t = 'y'`。 トイレットペーパーを必要とする人はいつでも 1 人だけが個室内に入れることができます。 持っている人`t = 'n'`このリソースは使用せず、ストール容量を超えて相互に干渉しないでください。 

課題は、全員が締め切りまでに作業を終え、「トイレット ペーパーの制約」に決して違反しないように、すべての人がブースに入るようにスケジュールを設定し、時間枠を設定することが可能かどうかを判断することです。 

主な制約は大きく、最大 100,000 人および 50,000 の屋台です。 これにより、時間内を順方向にスキャンしながら、個人を 1 つずつタイムスロットに貪欲に割り当てようとするシミュレーションは即座に排除されます。これは、期限が大きいか密集している場合、二次関数の動作に低下するためです。 

共有リソースの制限を無視すると、微妙な障害モードが発生します。 ストール容量のみを考慮すると、実現可能性を誤って仮定する可能性があります。 たとえば、多くの`'y'`ユーザーが全員同じ厳しい期限を持っている場合、ストール容量だけでもスケジュールは可能ですが、単一のロールによってシリアル化が強制されます。 

別の特殊なケースは、すべての締め切りが同じで、`'y'`ユーザーがその期限を超過した場合。 出店数が多くても時間自体がボトルネックになってしまいます。 

## アプローチ

 直接的なブルートフォース戦略は、からの時間をシミュレートしようとします。`1`トイレットペーパーが現在使用されているかどうかを尊重しながら、最大期限までに、空いている個室に人を割り当てます。 時間ステップごとに、利用可能なすべての人々の中から期限が過ぎていない人を選び、最大 2 人を割り当てます。`s`彼らのうち。 のために`'y'`また、時間単位ごとに 1 つだけが配置されるようにします。 

これは実際のスケジューリング プロセスを模倣しているため、概念的には機能しますが、遅すぎます。 最悪のケースは、締め切りが長い場合に発生します。`10^9`、一方、`10^5`人は存在する。 イベントによって時間を圧縮したとしても、利用可能な人材の動的なセットを維持し、有効な割り当てを繰り返し選択すると、タイム ステップごとに並べ替えとヒープ操作が発生し、事実上、`O(n log n)`イベント時間ごとのシミュレーションで最大`O(max d)`最悪の定式化での出来事。 

重要な観察は、時間を明示的にシミュレートする必要がないということです。 各人が必要とするユニット スロットは 1 つだけであるため、実際の制約は、各締め切りまでに何人が完了する必要があるかです。 これは古典的な累積容量の実現可能性の問題です。 

システムはいつでも次のように再解釈できます。`t`、せいぜい`s * t`人々は全体的に完了している可能性があります。 また、完成したもののうち、せいぜい`t`そのうちの`'y'`ユーザーは 1 人だけなので、`'y'`ユーザーは時間単位で処理できます。 

したがって、スケジュールを設定する代わりに、ソートされた期限に関するプレフィックスの実現可能性制約をチェックします。 締め切りごとに人を並べ替えることで、カウントを蓄積し、各締め切りまでに確実に人数を確保できるようになります。`d`、総容量を超えず、超えません。`'y'`容量。

 ## アルゴリズムのチュートリアル

 この問題を、人の接頭辞が時間容量とリソース容量の制約に適合するかどうかを確認することに変換します。 

1. 人々を概念的に 2 つのグループに分けます: トイレット ペーパーが必要な人 (`y`）とそうでない人（`n`）。 スケジューリングではそれらを個別に扱いませんが、それらの数は個別に追跡します。 
2. すべての人を期限の降順でない順に並べ替えます。 これにより、期限までにプレフィックスを処理することが保証されます。`d`、私たちは、遅くとも次の時間までに終了しなければならない人たちを正確に考慮しています。`d`。 
3. ソートされたリストをスキャンしている間、3 つのカウンターを維持します: これまでに見た人の合計、人数`'y'`これまでに目撃された人々、そして暗黙のうちにその数`'n'`人々。 
4. ソートされた順序で各人についてカウンタをインクリメントし、そのプレフィックスでの実現可能性をチェックします。 現在の方に期限がある場合`d`、それから時間までに`d`処理されるすべての人をスケジュールできなければなりません。 
5. 各ステップで 2 つの制約をチェックします。 まず、total_people_so_far を超えてはなりません`s * d`、それぞれの`d`時間単位は最大でも対応できます`s`並行して人々。 2番、`'y'_so_far must not exceed `d`、単位時間当たりトイレットペーパーを使用できるのは 1 人だけであるためです。 
6. いずれかの制約がいずれかの時点で違反された場合、スケジューリングは不可能であると直ちに結論付けることができます。 
7. 違反なくすべての人の処理を完了すると、スケジュールが存在します。 

重要な設計上の選択は、期限の境界でのみ制約を評価することです。 有効なスケジュールはこれらのプレフィックス容量を尊重する必要があるため、ある時点で違反が発生した場合、再配置しても修正できません。 

### なぜ効果があるのか

 このアルゴリズムは、単調な実現可能性プロパティに依存しています。 期限順に並べ替えると、すべてのプレフィックスが同じ期間内にスケジュールを設定する必要がある人々のグループに対応することが保証されます。 任意の時間枠内で`[1, d]`、システムは正確に`s * d`処理スロットの合計と正確な値`d`の特別なスロット`'y'`ユーザー。 プレフィックスがいずれかの境界を超える場合、各人は分割できず、正確に 1 単位の時間を消費するため、割り当てを並べ替えてもワークロードを十分に圧縮できません。 これにより、スケジューリングは、建設的な割り当ての問題ではなく、全体的なキャパシティ チェックに変わります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s, n = map(int, input().split())
    people = []
    for _ in range(n):
        d, t = input().split()
        d = int(d)
        people.append((d, t))

    people.sort()

    total = 0
    y_count = 0

    for d, t in people:
        total += 1
        if t == 'y':
            y_count += 1

        if total > s * d:
            print("No")
            return
        if y_count > d:
            print("No")
            return

    print("Yes")

if __name__ == "__main__":
    solve()
```実装は、プレフィックス実現可能性ロジックに直接に従います。 並べ替えることにより、期限を正しい順序で処理できるようになります。 2 つのカウンターは、実現可能性の境界を定義する数量を正確に追跡します。 

微妙な点は、比較では以下を使用することです。`s * d`、完全な整数精度で計算する必要があります。 Python はこれを安全に処理しますが、他の言語ではオーバーフローに注意が必要です。 もう 1 つの詳細は、集合的な実現可能性のみが重要であるため、実際のストール割り当てをシミュレートしようとしていないことです。

 ## 特殊なケース

 重要なエッジケースの 1 つは、すべての人が同じ締め切りを持っていて、`s`大きいですが`y`制約が厳しい。 プレフィックス チェックが行われるため、アルゴリズムがこれを処理します。`y_count ≤ d`ストール容量に関係なく、単一リソースの制約を即座に適用します。 

もう 1 つのエッジ ケースは、期限が非常に長いにもかかわらず、ストール数が少ない場合です。 それでも`s * d`巨大に見えるかもしれませんが、プレフィックスは大きくなります`n`このチェックにより、無限の並列処理が暗黙的に想定されないことが保証されます。 

最後の微妙なケースは、締め切りが短い人が入力順に遅れて現れる場合です。 並べ替えにより、それらが最初に処理されることが保証されるため、アルゴリズムは、実行不可能なプレフィックスに誤って厳しい期限を延期することはありません。
