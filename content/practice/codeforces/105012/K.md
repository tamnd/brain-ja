 ## 解決策
 ## 問題の理解

 無限の整数グリッド上を移動する人々のグループをシミュレートしています。 各人物は指定された時間に現れ、固定座標から開始し、最初は北を向いています。 時間は分単位で進み、活動的な人は 1 分ごとに 2 つのアクションを決まった順序で実行します。 

まず、各人は、自分が現在向いている方向と垂直な線上に横たわっており、自分の位置を通過しているすべての人々を観察します。 それらが北または南を向いている場合、この線は y 座標における水平行全体になります。 それらが東または西を向いている場合、この線はその x 座標の垂直柱になります。 彼らは、自分自身とセルを共有している他の人を含む、その回線上のすべての人をカウントします。 このカウントが奇数の場合、時計回りに 90 度回転します。 

第二に、すべてのローテーションが決定された後、各人は現在の方向に正確に一歩前進します。 

新しい人は特定の分の開始時に、最初の座標で常に北を向いて参加します。 このプロセスを m 分間続けた後、その分の行動の前に、m 分の開始時点でのすべての人々の位置を報告する必要があります。 

制約は、時間をかけて直接シミュレーションできるほど十分に小さいですが、各ステップ内で非効率な再計算を許容できるほど小さいわけではありません。 n と m が最大 1000 の場合、シミュレートされる人分数の合計は最大約 100 万人になります。これにより、1 人あたり 1 ステップあたり線形時間でグローバル情報を再計算しようとするアプローチは除外されます。これは、約 10^9 の操作が必要になるためです。 

微妙な難しさは、「ライン上のカウント」が現在アクティブなすべての人々に依存しており、これらの位置が毎分変化することです。 すべての人をスキャンしてこれらの数を再計算する単純な実装では、遅すぎます。 

よくある落とし穴は、更新が同時に行われることを忘れることです。 人を 1 人ずつ移動し、すぐにカウントを更新すると、同じ分内の後の人には部分的に更新された状態が表示されますが、これは正しくありません。 到着時に別の問題が発生します。時刻 t に入場する人々は、移動がすでに発生した後ではなく、その分の決定段階から参加しなければなりません。 

## アプローチ

 ブルートフォース シミュレーションでは、毎分、すべての人を反復処理し、1 人ごとに他のすべてのアクティブな人々をスキャンして、向きに応じて同じ行または列に何人が横たわっているかを計算します。 これにより、毎分のコストは O(k^2) になります (k はアクティブな人数)。 m 分を超えると、これは O(n^2 m) に縮退し、最悪の場合、約 10^9 の演算に達し、遅すぎます。 

重要な点は、これらのカウントを最初から再計算する必要がないということです。 各ユーザーが必要とする唯一の情報は、その行または列を現在何人が共有しているかということです。 これらの数は、ハッシュ マップを使用して段階的に維持できます。1 つは Y 座標をその行の人数にマッピングし、もう 1 つは X 座標をその列の人数にマッピングします。 

これらの構造により、各人は、O(1) 時間以内に、該当する行のカウントが奇数であるかどうかを判断できます。 残る唯一の課題は、人の移動に合わせてこれらのカウントを正確に保つことです。 決定が下された後はすべての動きが同時に発生するため、まず現在のカウントのスナップショットを使用してすべての方向の変化を計算し、次にすべての動きを適用し、それに応じてマップを更新します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2m) | O(n) | 遅すぎる |
 | ハッシュ マップを使用した増分カウント | O(nm) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべてのアクティブな人々の現在の状態を維持しながら、時間を分ごとにシミュレーションします。

1. 人ごとに現在位置、方向、活動中かどうかを保存します。 現在時刻が到着時刻に達すると、人はアクティブになります。 
2. 各分の開始時に、新しく到着したすべての人々をアクティブ セットに挿入します。 それらの方向は北に初期化され、すぐに行数と列数に影響します。 
3. 2 つの頻度マップを維持します。1 つは各 Y 座標に現在何人の人がいるかをカウントし、もう 1 つは各 X 座標に何人の人がいるかをカウントします。 
4. 活動的な人ごとに、ローテーションするかどうかを決定します。 それらが北または南を向いている場合、それらの y 座標で行マップをクエリします。 それらが東または西を向いている場合、その x 座標で列マップをクエリします。 値が奇数の場合は、時計回りに 90 度回転します。 

これが機能する理由は、ルールがその瞬間の開始時の状態のみに依存するため、方向を決定する際に地図を変更してはいけないためです。 

1. すべての方向が確定したら、マップから各人の古い位置を削除し、その方向に 1 単位移動して、新しい位置をマップに挿入し直します。 
2. m 分後、すべての最終座標を出力します。 

正確さは、毎分の開始時にシステムの一貫したスナップショットを維持するかどうかにかかっています。 すべての決定ではそのスナップショットのみが使用され、すべての更新はその後に適用されます。 これにより、同じ 1 分以内に他の人の決定に影響を与える人がいないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n, m = map(int, input().split())
    x = []
    y = []
    t = []
    for _ in range(n):
        xi, yi, ti = map(int, input().split())
        x.append(xi)
        y.append(yi)
        t.append(ti)

    # directions: 0=N,1=E,2=S,3=W
    dx = [0, 1, 0, -1]
    dy = [1, 0, -1, 0]

    dirc = [0] * n
    active = [False] * n

    row_cnt = {}
    col_cnt = {}

    def add(i):
        row_cnt[y[i]] = row_cnt.get(y[i], 0) + 1
        col_cnt[x[i]] = col_cnt.get(x[i], 0) + 1

    def remove(i):
        row_cnt[y[i]] -= 1
        if row_cnt[y[i]] == 0:
            del row_cnt[y[i]]
        col_cnt[x[i]] -= 1
        if col_cnt[x[i]] == 0:
            del col_cnt[x[i]]

    ptr = 0

    for _ in range(m):
        while ptr < n and t[ptr] == _:
            active[ptr] = True
            add(ptr)
            ptr += 1

        # decide directions using snapshot
        for i in range(n):
            if not active[i]:
                continue
            if dirc[i] % 2 == 0:
                cnt = row_cnt[y[i]]
            else:
                cnt = col_cnt[x[i]]
            if cnt % 2 == 1:
                dirc[i] = (dirc[i] + 1) % 4

        # move all
        for i in range(n):
            if not active[i]:
                continue
            remove(i)
            x[i] += dx[dirc[i]]
            y[i] += dy[dirc[i]]
            add(i)

    for i in range(n):
        print(x[i], y[i])

if __name__ == "__main__":
    main()
```この実装では、シミュレーションが 1 分ごとに厳密に同期されます。 の`row_cnt`そして`col_cnt`マップは移動前の状態を表し、すべての方向変更が計算された後にのみ更新されます。 

微妙な点は、決定フェーズと移動フェーズの分離です。 方向を変えるときにすぐに位置を更新すると、同じ 1 分間のその後の計算でカウントが矛盾することになります。 もう 1 つの重要な詳細は、並べ替えられたフィールド上のポインタを使用して到着を処理することです。`t`これにより、各人が正しい時間に 1 回だけアクティブ化されることが保証されます。 

## 実用的な例

 3 人が異なる時間に入場する最初のサンプルを考えてみましょう。 最初は最初の人だけが存在するので、干渉されずに移動します。 2 人目の人が現れると、両方が行数と列数に影響し、その後数分間の方向転換の動作が変化する可能性があります。 

| 分 | アクティブセット | キー数 | 方向転換 | 移動後の位置 |
 | --- | --- | --- | --- | --- |
 | 0 | 1 | 行=1、列=1 | 出番なし | (1,2) → (1,3) |
 | 1 | 1,2 | 共有行/列が更新されました | 両方の可能性のあるターン | 更新されたポジション |
 | 2 | 1、2、3 | 完全なインタラクション | パリティはターンに影響します | 最終座標は進化する |

 2 番目のサンプルは、複数の人々が座標を共有する繰り返しの相互作用に重点を置き、回転動作に影響を与えるパリティ フリップを頻繁に引き起こします。 

これらのトレースは、システムが幾何学的距離や順序ではなく、現在の行と列の占有のパリティのみに依存していることを確認します。

 ## 特殊なケース

 重要なエッジケースは、複数の人が同じセルを占有している場合です。 この状況では、行数と列数に重複が含まれるため、パリティに直接影響します。 カウントはポジションごとではなく人ごとに維持されるため、アルゴリズムはこれを自然に処理します。 

もう 1 つのケースは、到着がちょうど 1 分の境界で発生する場合です。 アクティベーションはその分の決定フェーズの前に行われるため、新しく到着した人々はすぐにカウントに貢献し、同じステップでターンに影響を与える可能性があります。 ポインターベースの挿入により、この順序が保証されます。 

最後の微妙なケースは、2 人の人が 1 回の動作で位置を交換する同時交差です。 すべての更新は方向を計算した後に適用されるため、両方の移動は同じ初期スナップショットに基づいており、順序付けによるアーティファクトが防止されます。
