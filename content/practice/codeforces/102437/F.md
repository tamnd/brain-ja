 ## 解決策
 ## 問題の理解

 これは対話型の問題です。 (n \le 10^{18}) を持つ非負の残高 (n) が隠されており、プログラムは (n) を通常の入力として受け取りません。 代わりに、次のコマンドを発行して、少なくとも (x) ドルが残っているかどうかを端末に尋ねることができます。`withdraw x`。 アン`accepted`答えは、(x) ドルが現在の残高から削除されることを意味します。`rejected`残高が (x) より小さく、変更されないことを意味します。 プログラムが残高がゼロであると判断すると、次のように出力します。`finish`。 

クエリ制限は未知数 (n) によって異なります。 (q) を (n \le 2^q) を満たす最小の整数とします。 端末では最大 (q+10) 回の出金試行が許可されます。 これにより、クエリの数が実際の複雑さの尺度になります。 (10^{18}<2^{60}) であるため、60 個の 2 のべき乗をすべて使用する固定戦略は正しいですが、(n) が小さい場合でも 60 個のクエリを実行する可能性があります。 たとえば、(n=0) の場合、制限は 10 クエリのみであるため、無条件の 60 クエリ スキャンは無効になります。 

単純な解決策は、受け入れられたクエリと、残高がゼロであることとの間の区別にも敏感です。 (n=5) の場合、クエリ`withdraw 4`返品`accepted`ですが、残高は1です。 印刷中`finish`すぐに間違っているでしょう。 出金が成功した場合は、要求された金額が利用可能であったことのみがわかります。 

ゼロ残高も別の境界ケースです。 (n=0) の場合、`withdraw 1`戻らなければなりません`rejected`、その後`finish`は正しいです。 If (n=1), the same query returns`accepted`、 そして`finish`その撤回後にのみ正しくなります。 

正確な 2 の累乗は、off-by-one エラーをチェックするのにも役立ちます。 (n=2^k) の場合、クエリは`withdraw 2^k`成功し、ちょうどゼロのままになります。 一般に、受け入れられたクエリによってアカウントが使い果たされるとは想定できないため、アルゴリズムは引き続き安全に続行できなければなりません。 可能な最大値 (10^{18}) は (2^{60}) よりも小さいですが (2^{59}) よりも大きいため、指数 59 はこれまでに要求できる最大の 2 の累乗になります。 値 (2^{60}) は、許可された引き出し金額を超えるため、不要です。 

もう 1 つ微妙な点があります。 最適化フェーズでは、クエリが受け入れられるたびにバランスが変化するため、回答は元の (n) に関する通常の単調な述語を形成しません。 たとえば、(n=100) の場合、8 のクエリが受け入れられ、残高が 92 に減ります。その後、元の残高が 100 であっても 64 のクエリが拒否される可能性があります。したがって、二分探索では、通常の二分探索とは異なる正当性引数が必要になります。 

## アプローチ

 ブルートフォース手法では、(2^{59}) から (2^0) までの 2 の累乗をすべて試行します。 引き出しが受け入れられると、そのビットは現在の残高から削除されます。 これが機能するのは、すべての非負の整数が一意のバイナリ表現を持つためです。 最後に、可能な限りすべてのビットが試行されたため、何も残りません。 

問題は試行回数です。 (2^0) から (2^{59}) までの 2 の累乗はちょうど 60 個あるため、最悪の場合は 60 個のクエリになります。 ただし、(n=0) の場合 (q=0)、端末は 10 回の試行のみを許可します。 ブルートフォースアルゴリズムは、可能な限り最小のバランスでもすでに失敗する可能性があります。 

重要な点は、実際には、設定された最上位ビットを正確に識別する必要がないということです。 短い検索の後、残りの残高が (2^{l+1}) 未満になる程度に十分小さい指数 (l) を見つける必要があるだけです。 その後、通常の降順 2 値分解を 59 ではなく (l) から開始できます。 

このような (l) は、60 個の可能な指数に対する二分探索で取得できます。 中間点 (m) については、(2^m) を引き出そうとします。 成功した場合は、(l=m) に設定します。 失敗した場合は、(r=m) と設定します。 残高はこのプロセス中に変更される可能性があるため、(l) は必ずしも元の残高または現在の残高のいずれかの最上位ビットであるとは限りません。 重要なのは、検索が (r=l+1) で終了すると、最終的に拒否されたクエリによって現在の残高に制限が与えられるということです。 最後に有効な受け入れられたクエリが確立された場合 (l)、(l) より大きい後続の指数はすべて拒否され、特に境界指数 (l+1) は現在の残高に対して大きすぎます。 したがって、現在の残高は (2^{l+1}) を下回ります。 

候補指数が 60 個しかなく、(60<2^6) であるため、検索には最大 6 つのクエリが含まれます。 その後、さらに多くても (l+1) 個のクエリが必要になりますが、(l) が元の残高の対数スケールを超えることはありません。 したがって、合計は最大でも (q+7) であり、許容される (q+10) を十分に下回ります。 これが意図した最適化です。

 ## アルゴリズムのチュートリアル

 1. 指数区間 ([l,r)=[0,60)] から開始します。 許容されるすべての残高が (2^{60}) 未満であるため、60 を使用します。つまり、関連するすべてのべき乗は (2^0,\ldots,2^{59}) になります。 
2. (r-l>1) の間、(m=(l+r)//2) を選択して発行します。`withdraw ⟦PROTECT_2⟧`。 端末が応答した場合`accepted`、（l=m）を設定します。 引き出しにより実際には残高は減少しましたが、(l) その時点で手頃な有用な指数がまだ記録されています。 もし答えが`rejected`現在の残高は確実に (2^m) を下回っているため、(r=m) と設定します。 
3. 二分探索の後、(l) からゼロまで指数を処理します。 すべての (i) に対して、次のコマンドを発行します。`withdraw ⟦PROTECT_3⟧`。 応答が受け入れられると、残りの残高からそのバイナリ ビットが削除されます。 拒否された応答は、単にそのビットが存在しないことを意味します。 
4. (l) からゼロまでのすべての指数が試行された後、次のように出力します。`finish`。 二分探索により、残りの残高が (2^{l+1}) 未満であることが保証されたため、考えられるすべての残りのビットが考慮されるようになりました。 

中心的な不変条件は、残高が決して増加せず、受け入れられたすべてのクエリによって要求された金額が正確に削除されることです。 二分検索の終了時、(2^{59}) の引き出しに成功した後、検索が (l=59) に到達した (この場合、残高は (2^{59}) を下回っている) か、検索に (2^r) の拒否されたクエリによって作成された境界 (r=l+1) があります。 後者の場合、現在の残高は (2^{l+1}) を下回ります。 したがって、(l) からゼロまでの最後の降順スキャンは、残りのすべてのドルを除去するのに十分です。 

クエリ境界は同じ構造から派生します。 二分探索では最大 6 回の試行が必要です。 最終スキャンでは最大で (l+1) 回の試行が行われます。 受け入れられた引き出しは残高を減らすだけであるため、(l) は元の残高の対数スケールを超えることはできません。 したがって、合計は最大でも (q+7) となり、必要な (q+10) 許容量のうち 3 回の試行は未使用のままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    def ask(x):
        print(f"withdraw {x}", flush=True)
        response = input().strip()
        if response == "fail":
            sys.exit(0)
        return response

    l, r = 0, 60

    while r - l > 1:
        m = (l + r) // 2
        response = ask(1 << m)

        if response == "accepted":
            l = m
        else:
            r = m

    for i in range(l, -1, -1):
        ask(1 << i)

    print("finish", flush=True)

if __name__ == "__main__":
    solve()
```の`ask`function は、インタラクターとの通信が行われる唯一の場所です。 引き出しコマンドを出力し、プロトコルの要求に応じて直ちにフラッシュし、応答を読み取ります。 の`fail`端末がロックされた後の続行は明示的に禁止されているため、応答は即時に終了します。 

二分探索では、金額そのものではなく指数が使用されます。 間隔には 0 ～ 59 の整数が含まれるため、要求される量は最大でも (2^{59}<10^{18}) になります。 Python の整数はオーバーフローしませんが、C++ での同じ実装は、実際のクエリごとに符号付き 64 ビット整数に快適に収まります。 

最後のループは意図的に次から始まります。`l`、 ない`l + 1`または 59. 一部の権限は二分探索中にすでに取り消されている可能性があるため、再度クエリすると拒否される可能性があります。 それは無害です。 残高は減少するだけなので、一度成功した引き出しが二度成功することはありません。 

プログラムは、ゼロを検出しようとしません。`accepted`応答。 正確に (x) を含むアカウントと、受け入れられた後に (x) を超える数を含むアカウントを区別する方法はありません。`withdraw x`。 あらかじめ決められた戦略を継続することで、その曖昧さを回避できます。

def strategy(ask, finish):
    l, r = 0, 60

    while r - l > 1:
        m = (l + r) // 2
        response = ask(1 << m)

        if response == "accepted":
            l = m
        elif response == "rejected":
            r = m
        else:
            raise RuntimeError("unexpected interactor response")

    for i in range(l, -1, -1):
        ask(1 << i)

    finish()

def run_hidden(n):
    balance = n
    commands = []

    def ask(x):
        nonlocal balance
        assert 1 <= x <= 10**18

        commands.append(f"withdraw {x}")

        if balance >= x:
            balance -= x
            return "accepted"
        return "rejected"

    def finish():
        commands.append("finish")
        assert balance == 0

    strategy(ask, finish)
    return commands, balance

        else:

 ## 特殊なケース

 ゼロ残高は検索によって自然に処理されます。 のために`withdraw 1`(n=0) の場合、答えは次のようになります。`rejected`、その後の出金もすべて拒否されます。 二分探索は最終的に (l=0) に達し、最後のスキャンでもう 1 回実行されます。`withdraw 1`、 そして`finish`有効です。 完全な対話では 6 回の試行のみが必要ですが、プロトコルでは 10 回の試行が可能です。 

(n=1) の場合、二分探索では 1 を超えるすべてのテストされた電力が拒否されます。 最終スキャンは指数 0 から開始されるため、`withdraw 1`成功し、ゼロのままになります。 その後、アルゴリズムは終了します。 重要な境界は、指数ゼロが最後のループに含まれることです。 1 から始めると、1 ドルだけを逃してしまいます。 

(n=2^5=32) のような正確な累乗の場合、二分探索クエリは 32​​ を正常に取り出し、ゼロを残すことができます。 それ以降のクエリはすべて拒否されます。 拒否された出金は何も起こらないため、最終スキャンは安全なままです。 これは、ソリューションが次のことを想定してはならない理由を示しています。`accepted`応答は、残高がゼロになったことを意味します。 

最大残高 (n=10^{18}) については、(2^{59}<10^{18}<2^{60}) となるため、(q=60) となります。 すべてのクエリでは 60 未満の指数が使用され、バイナリ検索には最大 6 回の試行が必要です。 たとえ (l=59) であっても、最終スキャンに必要な試行回数はあと 60 回だけで、正確な検索パスに応じて合計で最大 66 回または 67 回となり、許容される 70 回を下回ります。 

最も微妙なケースは、受け入れられたクエリによってバイナリ検索中にバランスが変化する場合です。 (n=100) と仮定します。 8 のクエリは成功し、残高は 92 に減ります。その後の 32 のクエリも成功して、残高が 60 に減りますが、64 のクエリは拒否されます。 応答は、元の 100 との比較として解釈できません。有効なままになるのは、アルゴリズムに必要な弱いステートメントです。最終的に拒否された境界は、現在の残高が上の次のべき乗 (l) よりも小さいことを証明します。 その後、最後の降順スキャンでは、元のバランスが変更されていないことに依存することなく、残りのバイナリ表現が削除されます。
