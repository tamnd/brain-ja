 ## 解決策
 ## 問題の理解

 文字行を表す文字列が与えられます。 チップは、この文字列内の選択された位置から始まります。 配置した後、繰り返し移動させ、そのたびにチップの現在の位置にキャラクターを記録します。 動きは厳密な構造になっており、チップは最初は右にのみ一定ステップ移動し、その後方向を切り替えて左にのみ一定ステップ移動する場合があります。 再び右に進むことには戻りません。 

これは、記録されたシーケンスが常に文字列の連続セグメントに沿って移動することによって生成され、最初にインデックスが増加し、次に場合によってはインデックスが減少し、方向が反転するターニング ポイントが 1 つだけあることを意味します。 

タスクは、ターゲット文字列を、特定の開始位置と特定の動きの選択に対して、そのような訪問文字のシーケンスとして生成できるかどうかを決定することです。 

制約は十分に小さいため、個々のテスト ケースに対する 2 次または 3 次の解さえも許容されます。 すべてのテストにわたる文字列長の合計は最大 500 であり、最悪の場合、およそ O(n³) を超える最適化の必要性は即座に排除されます。 テスト ケースあたり O(n²) であっても安全です。 

正確さには、いくつかの微妙な状況が重要です。 

問題の 1 つは、パスが左に移動しない場合です。 たとえば、位置 3 から開始して右のみに移動すると、生成される文字列は元の文字列の単純な部分文字列になります。 常に少なくとも 1 回方向転換する必要があると想定する単純なアプローチでは、そのようなケースは誤って拒否されてしまいます。 

もう 1 つの問題は、配置直後にパスが動かない場合です。 位置 i から開始してすぐに左に移動することも有効で、インデックスが厳密に減少するシーケンスが生成されます。 たとえば、s = "abcde" の場合、インデックス 4 から開始して左に 2 回移動すると、"edc" が生成されます。 最初の正しい動きを強制するソリューションでは、これが見逃されます。 

最後に、多くの間違ったアプローチは、答えが部分文字列または反転された部分文字列の一致のみに依存すると想定していますが、重要な問題は、シーケンスの方向が 1 回だけ変わる可能性があることです。これにより、「abcba」のような形状や「abcdc」のような部分的なバージョンが可能になります。 

## アプローチ

 直接的な強引な解釈は、あらゆる開始位置を試し、考えられるすべての動きのパターンをシミュレートすることです。 開始インデックス i から、右に移動するステップ数、次に左に移動するステップ数を選択し、結果の文字列を明示的に構築して t と比較できます。 これは、定義どおりのプロセスに従っているため、正しいです。 ただし、開始位置ごとに右と左の移動の長さの選択肢は O(n²) あり、結果として得られる各文字列の構築には O(n) のコストがかかり、開始ごとに O(n³)、最悪の概念形式では全体で O(n⁴) になります。 たとえnが小さくても、これは不要であり、構造に無駄が生じます。 

重要な観察は、左右にどのくらい移動するかを個別に決定する必要がないということです。 開始位置を固定すると、最大 1 方向の変化でインデックスに沿って移動するシーケンスによってパスが完全に記述されます。 これは折れ線グラフ上の制約されたウォークであり、文字列内の位置とターゲット内の位置に関する動的プログラミングの定式化を示唆しています。 

移動の長さを列挙する代わりに、現在右に移動しているか左に移動しているかを追跡し、方向が右から左に最大 1 回切り替えられるように強制します。 これにより、問題は、サイズ O(n) の小さな状態グラフ内のパスに t を位置合わせできるかどうかを確認することに集約されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべての動きのブルート フォース シミュレーション | O(n⁴) 最悪の概念的な | O(n) | 遅すぎる |
 | DP の位置、インデックス、方向 | O(n³) または O(n²) の最適化 | O(n²) または O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

ターゲット文字列の文字を照合しながら、文字列内のインデックスをウォークオーバーするプロセスとしてモデル化します。 

1. 文字列内のすべての可能な開始インデックスを初期チップ配置として試みます。 これが必要なのは、プロセスはどこからでも開始でき、t の最初の文字は選択した開始位置と一致する必要があるためです。 
2. 固定の開始位置から、文字列内の現在のインデックス、t 内のインデックス、および現在の移動方向で構成される状態を使用して、ターゲット文字列との一致を試みます。 方向は「右に移動」または「左に移動」のいずれかです。 
3. 最初は方向を強制されないため、最初の手が右に進むか、最初の手が左に進むかの 2 つの可能性に分岐します。 これは、歩行がすぐに方向転換する場合と、しばらく一方向に進む場合の両方のケースを捉えています。 
4. 「右に移動」状態にある場合、位置 i から i+1 に移動し、t の次の文字を消費する可能性があります。 また、いつでも「右への移動」から「左への移動」への 1 つの移行を許可し、歩行の転換点を表します。 
5. 「左に移動」状態にある場合、位置 i から i-1 に移動し、再び t の 1 文字を消費します。 このプロセスでは一方向の変更のみが許可されるため、右への移動に戻すことは許可されません。 
6. t のすべての文字を消費するか、すべての可能な状態が使い果たされるまで、このプロセスを続けます。 いずれかのパスが t を正確に消費する場合、答えは「はい」です。 

ステート マシンによって強制される重要な制約は、方向が右から左に 1 回だけ変更されるということです。 

### なぜ効果があるのか

 チップの動きの有効な構造はすべて、あるインデックスから始まり、文字列グラフ内の一連のエッジをたどるウォークに正確に対応し、最初にインデックスを増加させ、次にオプションでインデックスを減少させます。 私たちの DP は、現在位置、t の進行状況、および方向位相のみをエンコードすることにより、そのような歩行をすべて重複することなく列挙します。 すべての遷移はチップの有効な動きを反映しており、無効な方向変更は決して許可されないため、受け入れられた状態は有効なプロセスを再構築し、正当な遷移が決して除外されないため、有効なプロセスはすべて DP によって追跡されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(s, t):
    n, m = len(s), len(t)
    
    for start in range(n):
        if s[start] != t[0]:
            continue
        
        # dp[pos][dir][idx] is too large explicitly,
        # we compress by iterative BFS-style DP over states
        # state: (pos, idx, dir)
        # dir: 0 = right, 1 = left
        
        from collections import deque
        
        vis = set()
        q = deque()
        
        # initial state: at start, matched first character
        # we can choose next direction as right or left
        q.append((start, 0, 0))  # go right
        q.append((start, 0, 1))  # go left
        vis.add((start, 0, 0))
        vis.add((start, 0, 1))
        
        while q:
            pos, i, d = q.popleft()
            
            if i == m - 1:
                return True
            
            if d == 0:
                # move right
                if pos + 1 < n and s[pos + 1] == t[i + 1]:
                    nxt = (pos + 1, i + 1, 0)
                    if nxt not in vis:
                        vis.add(nxt)
                        q.append(nxt)
                # switch to left
                if pos - 1 >= 0 and s[pos - 1] == t[i + 1]:
                    nxt = (pos - 1, i + 1, 1)
                    if nxt not in vis:
                        vis.add(nxt)
                        q.append(nxt)
            else:
                # moving left only
                if pos - 1 >= 0 and s[pos - 1] == t[i + 1]:
                    nxt = (pos - 1, i + 1, 1)
                    if nxt not in vis:
                        vis.add(nxt)
                        q.append(nxt)
    
    return False

def main():
    q = int(input())
    for _ in range(q):
        s = input().strip()
        t = input().strip()
        print("YES" if solve_case(s, t) else "NO")

if __name__ == "__main__":
    main()
```このソリューションは、すべての開始位置を反復し、それぞれの開始位置から小規模な状態検索を開始します。 BFS 状態は、文字列内の現在位置、ターゲット文字列内の進行状況、および現在右に移動しているか左に移動しているかをエンコードします。 遷移ロジックは、許可されたチップの動きを直接反映しています。右に移動している状態からは右に進むか、左に一度切り替えることができますが、左に移動している状態からは左に進むことしかできません。 

訪問したセットは、異なる移動履歴を通じて同じ構成に到達する可能性があり、再訪問すると指数関数的な爆発を引き起こす可能性があるため重要です。 状態空間は開始ごとに最大でも n × m × 2 であるため、これは与えられた制約の下で効率的です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | 完全なソリューションごとに O(n³) のワーストケースが発生し、実際には実質的にはるかに小さくなります。 各開始では最大で O(n × m × 2) 個の状態が探索され、合計の n は小さい |
 | スペース | O(n × m) | 開始ごとの訪問状態のストレージにより再計算が防止される |

 この制約により、すべてのテストの合計 n が最大 500 であることが保証されるため、3 次探索であっても制限内に留まります。 BFS 状態のプルーニングにより、一般的なケースでは実際のランタイムが 2 次の動作に近づくことが保証されます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    def solve():
        q = int(input())
        out = []
        for _ in range(q):
            s = input().strip()
            t = input().strip()
            
            n, m = len(s), len(t)
            from collections import deque
            
            def ok():
                for start in range(n):
                    if s[start] != t[0]:
                        continue
                    
                    qd = deque()
                    vis = set()
                    qd.append((start, 0, 0))
                    qd.append((start, 0, 1))
                    vis.add((start, 0, 0))
                    vis.add((start, 0, 1))
                    
                    while qd:
                        pos, i, d = qd.popleft()
                        if i == m - 1:
                            return True
                        if d == 0:
                            if pos + 1 < n and s[pos+1] == t[i+1]:
                                st = (pos+1, i+1, 0)
                                if st not in vis:
                                    vis.add(st)
                                    qd.append(st)
                            if pos - 1 >= 0 and s[pos-1] == t[i+1]:
                                st = (pos-1, i+1, 1)
                                if st not in vis:
                                    vis.add(st)
                                    qd.append(st)
                        else:
                            if pos - 1 >= 0 and s[pos-1] == t[i+1]:
                                st = (pos-1, i+1, 1)
                                if st not in vis:
                                    vis.add(st)
                                    qd.append(st)
                    return False
            
            out.append("YES" if ok() else "NO")
        return "\n".join(out)
    
    return solve()

 ## 特殊なケース

 t が同じ文字の場合、長さ 1 の最小文字列が常に受け入れられます。 DP は唯一の位置から開始され、最初の文字と一致し、すぐに正常に終了します。 

t が s に等しい場合は、移動が必要ないシナリオをテストします。 初期状態はすでに最初の文字と一致しており、移動を強制せずに終了できるため、このアルゴリズムではゼロ遷移が許可されています。 

完全に反転した文字列は、配置後に左に移動するだけという極端なケースをテストします。 最後の文字から開始して段階的に左に移動すると、すべての文字と一致し、DP では最初の方向を左にすることが正しく許可されます。 

右に移動してから右に戻る 2 番目の独立した切り替えが必要なような「ジグザグ」パターンは、ステート マシンが複数の方向変更を禁止し、無効な再構築を防ぐため、拒否されます。
