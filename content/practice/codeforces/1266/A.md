 ## 問題の理解

 いくつかの文字列が与えられます。それぞれの文字列は、ボブの元の数値の桁を並べ替えるか、任意の何かに置き換えた後にアリスによって書かれた数値を表します。 各文字列について、純粋に組み合わせに関する質問が行われます。つまり、結果の数値が 60 で割り切れるようにその桁を並べ替えることはできますか。 

重要な点は、並べ替えられた数値では先頭のゼロが許可されるため、標準の整数ではなく複数の桁のセットを効果的に扱うことができるということです。 このタスクは、60 で割り切れる数値を形成するこれらの数字の順列が存在するかどうかをチェックすることに要約されます。 

制約は十分に小さいため、各テスト ケースは桁長にわたって線形時間で独立して処理できます。 最大 418 個の文字列とそれぞれ最大 100 桁の場合、テスト ケースごとに一定の回数だけ桁をスキャンするソリューションであれば十分です。 階乗または順列ベースのアプローチは、100 桁でさえ天文学的な数の並べ替えを意味するため、完全に実行不可能です。 

よくある落とし穴は、元の数値が重要であるかのように問題を扱うことから発生します。 たとえば、「060」と「600」は、順列で先行ゼロが許可されるため、どちらもこの問題では有効な表現です。 もう 1 つの微妙な問題は、元の 60 倍の数値を構築する必要があると仮定していることです。実際には、ボブの元の値を再構築するのではなく、60 で割り切れるかどうかだけが問題となります。 

いくつかの代表的なエッジ状況が落とし穴を浮き彫りにしています。 

すべての数字がゼロの場合、次のように`"0000"`の場合、どの配列も 0 を形成し、60 で割り切れるため、答えは明らかに有効です。 

数値にゼロがまったく含まれていない場合、次のようになります。`"1234"`、10 で割り切れないため、60 は不可能です。 

桁の合計は正しいがゼロがない場合、次のようになります。`"222"`、10 で割り切れないため、並べ替えは役に立ちません。 

## アプローチ

 ブルートフォース ソリューションでは、数字のすべての順列を生成し、結果の各数値が 60 で割り切れるかどうかをチェックしようとします。これは、検索空間全体を探索するため、原理的には正しいです。 ただし、最大 100 桁になると、順列の数は 100! と増加し、計算の限界をはるかに超えます。 10桁でも10！ すでにテスト ケースごとに 360 万の可能性があるため、このアプローチは使用できません。 

重要な観察は、60 で割り切れる可能性が独立した桁制約に分解されるということです。 60 は 3 × 4 × 5 に等しいため、代わりに標準の割り算ルールを使用して推論できます。 

数値は、最後の桁が 0 または 5 である場合にのみ 5 で割り切れます。2 で割り切れる必要もあるので、最後の桁は偶数である必要があり、したがって 0 でなければなりません。これにより、有効な配列の最後の桁がゼロに即座に修正されます。つまり、マルチセットには少なくとも 1 つのゼロが含まれている必要があります。 

3 で割り切れるかどうかは、桁の合計にのみ依存し、並べ替えの下では不変です。 したがって、入力文字列の桁の合計はすでに 3 で割り切れる必要があります。 

残りの条件は、末尾にゼロを強制した後でも有効な数値が存在するように数字を配置できる必要があることです。 少なくとも 1 つのゼロと 3 で割り切れることを確認したら、他のすべての桁を任意に配置できます。 

したがって、問題は 2 つのチェック、つまり少なくとも 1 つのゼロの存在と、数字の合計が 3 で割り切れるかという 2 つのチェックに集約されます。

 ## アルゴリズムのチュートリアル

 1. 文字列を読み取り、0 から 9 までの各桁の頻度を数えます。これにより、入力が、置換推論が単純になる形式に圧縮されます。 
2. 少なくとも 1 つのゼロが存在するかどうかを確認します。 これが必要なのは、10 で割り切れる数値、つまり 60 の最後の桁がゼロでなければならないためです。 ゼロがなければ、有効な再配置は存在しません。 
3. すべての桁の合計を計算します。 この値は置換下では不変であるため、3 で割り切れるかどうかが決まります。 
4. 桁の合計が 3 で割り切れない場合は、その文字列を直ちに拒否します。 順列では合計が変わらないため、再配置してもこれを解決できません。 
5. 両方の条件が当てはまる場合、末尾に常にゼロを配置し、残りの数字を任意に配置できるため、文字列を有効なものとして受け入れます。 

### なぜ効果があるのか

 このアルゴリズムは、桁の合計と桁の可用性という 2 つの不変条件に依存します。 順列も変化しないため、必要な割り算条件が入力マルチセットにすでに存在している必要があります。 60 で割り切れる数は、10 で割り切れる数と 3 で割り切れる数にきれいに分割され、どちらの条件も順序ではなくローカルな桁のプロパティによって完全に決定されます。 ゼロが存在し、桁の合計が 3 で割り切れると、末尾にゼロを置き、残りを自由に配置することで、いつでも有効な順序を構築できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
for _ in range(n):
    s = input().strip()
    
    cnt0 = 0
    digit_sum = 0
    
    for ch in s:
        digit = ord(ch) - 48
        cnt0 += (digit == 0)
        digit_sum += digit
    
    if cnt0 == 0:
        print("cyan")
    elif digit_sum % 3 != 0:
        print("cyan")
    else:
        print("red")
```この実装では、各文字列を 2 つの十分な統計 (ゼロが存在するかどうかと数字の合計) に圧縮します。 ゼロ チェックは 10 で割り切れることを強制し、サム チェックは 3 で割り切れることを強制します。60 = 3 × 4 × 5 であり、数値がゼロで終わり、残りの桁に十分な柔軟性がある場合、4 の条件は自動的に満たされるため、それ以上の構造的推論は必要ありません。 

チェックの順序は効率のためにのみ重要です。 欠落ゼロを早期に拒否することで、一部の実装では不必要な合計作業が回避されますが、ここではどちらも線形スキャンです。

 ## 特殊なケース

 特に微妙なケースは、次のように文字列がゼロのみで構成されている場合です。`"00000"`。 このアルゴリズムは、少なくとも 1 つのゼロを数え、3 で割り切れるゼロの桁の合計を計算します。アルゴリズムは正しく「赤」を出力します。これは、どの順列でも 0 (60 で割り切れる) が得られることを反映しています。 

もう一つのケースは、`"1110"`、ゼロがありますが、桁の合計は 3 であり、3 で割り切れます。アルゴリズムはそれを受け入れ、1101 → 1011 などの有効な配置が存在します。どちらも 3 で割り切れ、割り算の制約を維持しながらゼロで終わるように配置できます。 

みたいな失敗例`"222"`は、合計が 6 で 3 で割り切れるが、使用できるゼロがないため拒否されます。 アルゴリズムは正しく「シアン」を出力し、数字をゼロで終えることは不可能であることに一致します。
