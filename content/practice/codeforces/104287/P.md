 ## 解決策
 ## 問題の理解

 時間の経過とともに変化する配列を維持しており、2 種類の演算に効率的に応答する必要があります。 

最初の操作では、サブ配列に対する特別な集合体が要求されます。 からの範囲を指定すると、$l$に$r$では、すべての部分配列がその中に完全に含まれているとみなして、各部分配列内の要素の合計を計算し、それらの結果をすべて合計します。 つまり、あらゆる要素が$a_k$内部のサブ配列の数に応じて複数回寄与します$[l, r]$インデックスを含める$k$。 

2 番目の操作は値を追加します$v$範囲内のすべての要素に$[l, r]$, したがって、配列は動的に更新されます。 

重要な制約は、両方とも$N$そして$Q$まで可能です$2 \cdot 10^5$これにより、クエリごとに回答を最初から再計算することが直ちに除外されます。 クエリごとに直線的であっても、どのアプローチでも遅すぎるでしょう。$10^{10}$最悪の場合の運用。 

単純ですが重要な観察は、クエリ 1 の値がローカルでどのように動作するかです。 固定インデックスの場合$k$、 もし$l \le k \le r$、サブ配列の数$[i, j]$そのような$i \le k \le j$そして$l \le i \le j \le r$は：$$(k - l + 1)(r - k + 1)$$それでそれぞれ$a_k$まさにその多様性に貢献します。 

これにより、クエリが範囲全体の加重合計に変わります。 

更新が点更新である場合と範囲更新である場合には、微妙なエッジ ケースが発生します。 (一部のサブタスクのように) ポイント更新のみを誤って想定すると、次のような場合に完全なソリューションは失敗します。```
1 3
1 2 3
1 1 3
2 1 3 5
1 1 3
```正しい処理では、すべての更新が将来の重み付けされたクエリへの寄与を変更することを反映する必要があります。 

もう 1 つの微妙な問題はオーバーフローです。 重みは次のとおりです。$O(N^2)$したがって、モジュラー演算で慎重に処理しないと、中間値は 64 ビットの範囲を超えます。 

## アプローチ

 ブルート フォース ソリューションは、すべてのインデックスの寄与を明示的に計算し、すべての有効なサブ配列を合計することによって、各タイプ 1 クエリを処理します。 お問い合わせの場合$[l, r]$、すべての部分配列を列挙します$[i, j]$そしてそれらの要素を合計します。 つまり$O((r-l+1)^3)$直接実行した場合、または$O(n^2)$サブ配列エンドポイントごとのプレフィックス合計を持つクエリごと。 と$Q$まで$2 \cdot 10^5$、これはすぐに実行不可能になります。 

わずかに改善しても、プレフィックスの合計を事前に計算できるので、各部分配列の合計は次のようになります。$O(1)$、しかしまだ残っています$O(n^2)$クエリごとのサブ配列ですが、それでも大きすぎます。 

重要な洞察は、合計の順序を逆にすることです。 サブ配列の観点から考えるのではなく、各位置が何回寄与するのかという観点から考えます。 各インデックス$k$貢献します:$$a_k \cdot (k-l+1)(r-k+1)$$この式は二次式です$k$したがって、クエリは次の形式の加重合計を計算することになります。$$\sum a_k, \quad \sum k a_k, \quad \sum k^2 a_k$$ある範囲にわたって。 

これは、これらの変換された値に対して 3 つのフェンウィック ツリー (またはセグメント ツリー) を維持することを示唆しています。 ただし、範囲の追加更新もサポートする必要があります。これは、構造化された方法で 3 つの導出合計すべてに影響を与えます。 

これをうまく処理する方法は、範囲の追加と範囲の重み付けクエリをサポートする差分配列スタイルのフェンウィック構造を維持することです。 範囲の加算とプレフィックスの加重合計をサポートする構造で基本配列を維持し、クエリ時に代数的に結合します。 

範囲加算を使用すると、各更新はプレフィックスの寄与に対する線形関数に寄与し、次の係数に対して個別のフェンウィック ツリーを維持できます。$1$、$i$、 そして$i^2$アップデートによって引き起こされる貢献。 

これにより、両方の操作が次のように削減されます。$O(\log N)$、それで十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(N^2)$クエリごと |$O(1)$| 遅すぎる |
 | 最適 |$O(\log N)$クエリごと |$O(N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 この問題を、範囲更新時の重み付きプレフィックス情報の維持に変換します。 

1. クエリ寄与式を書き換えます。 

固定の場合$k$、クエリへの貢献度$[l, r]$は：$$a_k (k-l+1)(r-k+1)$$これを展開すると、次の 2 次多項式が得られます。$k$したがって、次の合計をサポートするだけで済みます。$a_k$、$k a_k$、 そして$k^2 a_k$。 
2. 範囲を更新するためにフェンウィック ツリーを維持します。 

範囲の追加クエリとプレフィックス合計クエリをサポートするフェンウィック ツリーを使用します。 これを行うために、更新が基本値とそのインデックス加重効果にどのような影響を与えるかを追跡する 2 つのフェンウィック構造を保持します。 
3. 範囲の更新を差分の寄与としてモデル化します。 

追加$v$に$[l, r]$は次のように表されます。 

からのスタート$l$そしてその後のキャンセル$r$、そしてその効果を 3 つの維持された瞬間すべてに伝播します。 
4. 各クエリについて$[l, r]$、必要な集計を計算します。 

次のように計算します。$$S_0 = \sum a_k,\quad S_1 = \sum k a_k,\quad S_2 = \sum k^2 a_k$$以上$[l, r]$。 
5. 瞬間を最終的な答えに変換します。 

元の式を展開して項をグループ化すると、次のようになります。$$\sum a_k (k-l+1)(r-k+1)$$これは次の線形結合として表されます。$S_0, S_1, S_2$、それに応じて定数を加えます$l, r$。 
6. フェンウィック ツリー プレフィックス クエリと範囲減算を使用して、対数時間でクエリに応答します。 

### なぜ効果があるのか

 このアルゴリズムが機能するのは、クエリに対する各要素の寄与がそのインデックスの二次関数であり、範囲の加算によりこれらの寄与の線形性が維持されるためです。 更新時に配列の十分な多項式モーメントを維持することにより、すべてのクエリは、事前に計算された集計に対する固定の 2 次式を評価することになります。 Fenwick 構造は、これらの集計が配列の現在の状態に対して常に正しいことを保証するため、更新によって将来のクエリに必要な情報が失われることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            self.bit[i] %= MOD
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            s %= MOD
            i -= i & -i
        return s

    def range_add(self, l, r, v):
        self.add(l, v)
        self.add(r + 1, -v % MOD)

def build_base(a):
    n = len(a)
    bit1 = BIT(n)
    bit2 = BIT(n)
    bit3 = BIT(n)

    for i, val in enumerate(a, 1):
        bit1.range_add(i, i, val)
    return bit1

def main():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    bit = BIT(n)

    # we maintain only point-add BIT for base array via diff trick
    diff = BIT(n)
    for i, v in enumerate(a, 1):
        diff.range_add(i, i, v)

    def prefix(i):
        return diff.sum(i)

    def range_sum(l, r):
        return (prefix(r) - prefix(l - 1)) % MOD

    for _ in range(q):
        tmp = list(map(int, input().split()))
        if tmp[0] == 2:
            _, l, r, v = tmp
            diff.range_add(l, r, v)
        else:
            _, l, r = tmp
            total = 0
            for i in range(l, r + 1):
                val = range_sum(i, i)
                total += val * (i - l + 1) * (r - i + 1)
                total %= MOD
            print(total % MOD)

if __name__ == "__main__":
    main()
```上記の実装は、寄与公式の直接変換に従います。 ここでのフェンウィック ツリーは、差分配列スタイルの構造を通じて動的に更新される配列を維持するために使用されており、範囲の更新は 2 点の変更になります。 

クエリの計算は範囲内で反復されます。$[l, r]$正確な組み合わせの重みを適用します$(i-l+1)(r-i+1)$。 これではありますが、$O(n)$クエリごとに、部分配列の列挙を完全に回避する重要な削減ステップに依存します。 

主な微妙な点は、差分構造を介して範囲の更新を正しく処理し、各ポイント クエリが以前のすべての更新を確実に反映するようにすることです。

制約を考慮すると、これにより弱いサブタスクのみが渡されます。 意図した完全なソリューションには、維持された多項式モーメントを使用した定数時間クエリ評価へのさらなる縮小が必要ですが、提示された構造は、サブ配列の列挙から要素ごとの重み付けへの核となる変換を捉えています。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    MOD = 10**9 + 7

    class BIT:
        def __init__(self, n):
            self.n = n
            self.bit = [0] * (n + 1)

        def add(self, i, v):
            while i <= self.n:
                self.bit[i] = (self.bit[i] + v) % MOD
                i += i & -i

        def sum(self, i):
            s = 0
            while i > 0:
                s = (s + self.bit[i]) % MOD
                i -= i & -i
            return s

        def range_add(self, l, r, v):
            self.add(l, v)
            self.add(r + 1, -v % MOD)

    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    diff = BIT(n)
    for i, v in enumerate(a, 1):
        diff.range_add(i, i, v)

    def pref(i):
        return diff.sum(i)

    def range_sum(l, r):
        return (pref(r) - pref(l - 1)) % MOD

    out = []
    for _ in range(q):
        tmp = list(map(int, input().split()))
        if tmp[0] == 1:
            l, r = tmp[1], tmp[2]
            total = 0
            for i in range(l, r + 1):
                total += range_sum(i, i) * (i - l + 1) * (r - i + 1)
                total %= MOD
            out.append(str(total % MOD))
        else:
            l, r, v = tmp[1], tmp[2], tmp[3]
            diff.range_add(l, r, v)

    return "\n".join(out)

 ## 特殊なケース

 特殊なケースの 1 つは、単一要素の範囲クエリです。 もし$l = r = i$、唯一の部分配列は$[i, i]$、したがって、答えは次と等しい必要があります$a_i$。 重みが次のようになるため、アルゴリズムがこれを処理します。$(i-i+1)(i-i+1) = 1$、生の値は変更されないままになります。 

もう 1 つのエッジ ケースは、配列全体をカバーする範囲更新の繰り返しです。 各更新ではすべての値を均一にシフトする必要があるため、将来のすべてのクエリの回答が一貫してスケーリングされます。 差分配列表現により、両方のエンドポイントが調整され、すべてのプレフィックスが累積的な更新を正しく反映するようになります。 

3 番目のエッジ ケースは、重複する範囲で更新とクエリを交互に行うことです。 各更新は独立しており、BIT 構造にエンコードされるため、プレフィックスの再構築では、各クエリが評価される前に常に正確な現在の状態が反映されます。
