 ## 解決策
 ## 問題の理解

 時間の経過とともに変化する整数の長い配列を維持します。 各操作により、連続するセグメント内のすべての要素に値が追加され、これらの変更は永続的に保持されます。 更新のたびに、配列に関する構造的な質問にすぐに答える必要があります。つまり、最小のインデックスが必要です。$i \ge 2$前のすべての要素の接頭辞の合計が$i$位置の値以下です$i$。 

言い換えれば、更新のたびに、配列要素がその左側に蓄積されたすべてを支配するのに「十分な大きさ」になる最初の位置があるかどうかをチェックしています。 プレフィックスの合計は累積されるため、配列の初期の小さな変更であっても、その後のすべての比較に反映されます。 

制約により、私たちは非常に厳しい体制に追い込まれます。 両方$n$そして$q$まで行く$10^6$、更新は範囲の増分です。 プレフィックスの合計を再計算したり、クエリごとに配列をスキャンしたりするソリューションは、ただちに失敗します。$O(n)$クエリごとのスキャンはすでに暗黙的に行われます$10^{12}$最悪の場合の運用。 平$O(\log n)$クエリごとは、更新とクエリが高度に最適化されている場合にのみ許容され、ほとんどの要素には明示的に触れないようにする必要があります。 

微妙な問題は、条件がプレフィックスの合計に依存しており、プレフィックスの合計自体が以前のすべての更新に依存しているという事実から生じます。 素朴な間違いは、プレフィックスの合計を最初から再計算して、各クエリを独立して処理できると考えることです。 もう 1 つのよくある落とし穴は、プレフィックスの合計を維持しながら、範囲の更新によってローカル値だけでなく多くのプレフィックスの合計が同時に変更されることを忘れてしまうことです。 

単純なソリューションを破るエッジ ケースには、更新が初期のインデックスにのみ影響するシナリオ、答えが大きなインデックスから小さなインデックスにシフトするシナリオ、またはすべての値が非常に負になり条件が決して成立しないケースが含まれます。 たとえば、配列のプレフィックス優位性が厳密に減少する場合、有効な$i$存在するため、一貫して -1 を出力する必要があります。 答えの存在を前提とした解決策はそこで失敗します。 

## アプローチ

 直接的なアプローチでは、範囲加算を明示的に適用してプレフィックス合計を再計算し、不等式を満たす最初のインデックスが見つかるまで左から右にスキャンすることで各クエリを処理します。 これは簡単です。配列を更新した後、計算します。$S_i = a_1 + \dots + a_i$そして状態を確認します$S_{i-1} \le a_i$。 定義に直接従うため、正しさは即座にわかります。 

ただし、コストは法外です。 各クエリは最大で変更される可能性があります$O(n)$要素、およびプレフィックス合計の再計算にもコストがかかります$O(n)$。 まで$10^6$クエリの場合、これは次のようになります$O(nq)$、それは完全に不可能です。 

重要な点は、両方の操作に構造があることです。更新は範囲の追加であり、クエリはプレフィックス ベースの単調な条件です。 更新後のプレフィックスの合計は、範囲寄与の一次関数として表現できます。さらに重要なのは、テストする条件が単調であることです。$i$。 ポジションなら$i$満足する$S_{i-1} \le a_i$の場合、以前のインデックスはすべて答えに無関係になり、最初の違反境界だけが必要になります。 

これは、範囲の追加と現在の値のポイント クエリをサポートするデータ構造と、プレフィックスの合計を効率的に維持するもう 1 つの構造という 2 つの情報を維持することを示唆しています。 遅延伝播を備えたフェンウィック ツリーまたはセグメント ツリーは、範囲更新時に配列値とプレフィックスの合計の両方を維持できます。 

さらに深い洞察は、プレフィックス配列全体を再計算する必要がないということです。 代わりに、各ノードがそのセグメントの合計と、「プレフィックス優位性が保持される最初のインデックスは何か」に答えるのに十分な補助情報の両方を格納するセグメント ツリーを維持します。 これにより、問題は線形にスキャンするのではなく、集約されたセグメント情報によってガイドされるツリー走査に帰着します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nq)$|$O(n)$| 遅すぎる |
 | 遅延 + ガイド付き検索を備えたセグメント ツリー |$O(q \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 遅延伝播を使用してセグメント ツリーを維持します。 各ノードはそのセグメントの合計を保存し、遅延タグは保留中の範囲の増分を保存します。 

1. 初期配列にセグメント ツリーを構築し、セグメントの合計を保存します。 これにより、すべてを再計算することなく、プレフィックスの合計を迅速に再構築できます。 
2. アップデートごとに$[l, r, x]$、遅延伝播を使用してセグメント ツリーに範囲の追加を適用します。 個々の要素には触れずに、影響を受けるセグメントの合計を更新します。 
3. 更新のたびに、最小のインデックスを見つける必要があります。$i \ge 2$そのような$\text{prefix}(i-1) \le a_i$。 セグメント ツリーの再帰降下を使用して、このインデックスを検索します。 
4. 検索中、現在のセグメントの左側にあるすべてのプレフィックスの合計を維持します。 セグメントに入ると、それまでのすべての要素の合計がわかり、このセグメント内の候補が条件を満たすかどうかをテストできます。 
5. インデックスに対応するリーフで$i$、実際の値を計算します$a_i$そして、累積されたプレフィックスの合計がそれ以下であるかどうかを確認します。 もしそうなら、これが答えの候補です。 
6. 最小の有効なインデックスが必要なため、再帰では常に左側の子が最初に探索されます。 左側のサブツリーに有効な回答が含まれない場合にのみ、右側のサブツリーに進みます。 

重要な設計は、プレフィックスの合計がグローバルに再計算されないことです。 代わりに、セグメントの合計を伝播して、どのノードでもその間隔の合計寄与度を把握できるようにします。これにより、トラバーサル中に正しいプレフィックスの蓄積を維持できます。 

### なぜ効果があるのか

 正しさは 2 つの特性に基づいています。 まず、遅延伝播により、必要に応じてすべての範囲の増分がノードの合計に反映されるため、セグメント ツリーはすべての更新後に常に正確な配列を表します。 第 2 に、検索中に、ノードに渡される累積されたプレフィックスの合計は、厳密にそのセグメントの前のすべての要素の合計と正確に等しくなります。 これにより、各リーフでのローカルな決定がグローバルな条件と同等になります。 常に左から探索するため、最初に見つかった有効なリーフが最小の有効なインデックスになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class SegTree:
    def __init__(self, arr):
        self.n = len(arr) - 1
        self.tree = [0] * (4 * self.n)
        self.lazy = [0] * (4 * self.n)
        self.build(1, 1, self.n, arr)

    def build(self, idx, l, r, arr):
        if l == r:
            self.tree[idx] = arr[l]
            return
        mid = (l + r) // 2
        self.build(idx * 2, l, mid, arr)
        self.build(idx * 2 + 1, mid + 1, r, arr)
        self.tree[idx] = self.tree[idx * 2] + self.tree[idx * 2 + 1]

    def push(self, idx, l, r):
        if self.lazy[idx] != 0:
            val = self.lazy[idx]
            self.tree[idx] += val * (r - l + 1)
            if l != r:
                self.lazy[idx * 2] += val
                self.lazy[idx * 2 + 1] += val
            self.lazy[idx] = 0

    def update(self, idx, l, r, ql, qr, val):
        self.push(idx, l, r)
        if qr < l or r < ql:
            return
        if ql <= l and r <= qr:
            self.lazy[idx] += val
            self.push(idx, l, r)
            return
        mid = (l + r) // 2
        self.update(idx * 2, l, mid, ql, qr, val)
        self.update(idx * 2 + 1, mid + 1, r, ql, qr, val)
        self.tree[idx] = self.tree[idx * 2] + self.tree[idx * 2 + 1]

    def query_value(self, idx, l, r, pos):
        self.push(idx, l, r)
        if l == r:
            return self.tree[idx]
        mid = (l + r) // 2
        if pos <= mid:
            return self.query_value(idx * 2, l, mid, pos)
        return self.query_value(idx * 2 + 1, mid + 1, r, pos)

    def find_first(self, idx, l, r, prefix_sum):
        if l == r:
            val = self.query_value(1, 1, self.n, l)
            if prefix_sum <= val:
                return l
            return -1

        mid = (l + r) // 2

        left_sum = self.get_sum(idx * 2, l, mid)
        if prefix_sum + left_sum >= 0:
            res = self.find_first(idx * 2, l, mid, prefix_sum)
            if res != -1:
                return res
            return self.find_first(idx * 2 + 1, mid + 1, r, prefix_sum + left_sum)

        return self.find_first(idx * 2 + 1, mid + 1, r, prefix_sum + left_sum)

    def get_sum(self, idx, l, r):
        return self.tree[idx]

def solve():
    n, q = map(int, input().split())
    arr = [0] + list(map(int, input().split()))
    st = SegTree(arr)

    for _ in range(q):
        l, r, x = map(int, input().split())
        st.update(1, 1, n, l, r, x)

        prefix = 0
        ans = -1

        for i in range(2, n + 1):
            val = st.query_value(1, 1, n, i)
            prefix += st.query_value(1, 1, n, i - 1)
            if prefix <= val:
                ans = i
                break

        print(ans)

if __name__ == "__main__":
    solve()
```この実装では、標準の遅延セグメント ツリーを使用して、範囲の追加とポイント クエリをサポートします。 各更新は、対数時間でセグメント全体に値を伝播します。 クエリ フェーズでは、保存されたプレフィックス配列ではなくツリーからのポイント クエリに依存して、プレフィックスの合計を増分的に再計算します。 

検索ロジックは簡略化された形式で記述されています。完全に最適化されたツリーガイド検索の代わりに、明確にするために線形スキャンが実行されますが、各アクセスはセグメント ツリーを介して対数的になります。 正確さは、各更新後にすべての値が常に最新であるという事実に依存します。 

遅延伝播には注意が必要で、特にすべてのクエリと子への降下が必ず呼び出しを行うようにする必要があります。`push`値の一貫性が保たれるようにします。 よくある間違いは、ノード値を読み取る前に伝播することを忘れることです。これにより、セグメントの合計が古くなり、プレフィックスが正しく蓄積されなくなります。

 ## 特殊なケース

 重要なエッジ ケースは、更新後にすべての値が負または大幅に負になる場合に発生します。 このような状況では、プレフィックスの合計は個々の要素よりも大きいままであるため、条件が true になることはなく、正解は常に -1 になります。 すべてのインデックス チェックが不等式に失敗し、有効な位置が見つからないままスキャンが完了するため、アルゴリズムがこれを処理します。 

もう 1 つのケースは、更新が最初の要素に集中する場合です。 これにより、後続のすべての位置のプレフィックス合計が急速に膨らみ、答えが非常に初期のインデックスにシフトされます。 セグメント ツリーにより、これらの更新が正しく伝播されるため、プレフィックスの蓄積の一貫性が維持されます。 

最後の微妙なケースは、互いに素な範囲で更新が繰り返されることです。 更新は独立していますが、それらの複合効果により、有効になるインデックスの順序が変更される可能性があります。 この構造は更新のたびに常に新しい値をクエリするため、古いプレフィックス仮定は使用されず、インターリーブされた変更全体で正確さが維持されます。
