 ## 解決策
 ## 問題の理解

 私たちに与えられたのは、$n$細胞。 各セルには難易度の値があります$d_i$。 レースは選択したセルから始まります$s$、一定の時間$t$許可されています。 レーサーは円を描くようにセルごとに前進します。 

重要な問題は、移動にはセルごとのコストが一定ではないことです。 ナマケモノには現在の速度があります$v$、から始まります$v = 1$、各セルは、この速度を強制的に低下させる可能性のあるルールを課します。 各セルの消費時間も、セルの難易度と入力時の現在の速度の両方に依存します。 

セルに入るとき$i$、現在の速度の場合$v$セルの難易度から導出されるしきい値よりも大きい場合、セルを処理する前に速度がそのしきい値まで低下します。 この短縮の可能性があった後、セル内で費やされる時間は現在の速度に反比例し、セルの難易度によって決まります。 これにより、ヒステリシス効果が生じます。速度が一度低下すると、再び増加することはなく、その後の移動は以前のすべての制約に依存します。 

入力は、難易度配列の 2 種類の範囲更新をサポートしています。 1 つは円形セグメント内のすべての値を増加させ、もう 1 つはセグメント内のすべての要素に定数値を割り当てます。 修正を行うたびに、レースをシミュレートする質問に答える必要があります。ポジションから始めてください。$s$、合計時間に達するまで前進し、時間を蓄積します$t$、境界で正確に停止することは次のセルで考慮されることを意味するという境界ルールを含め、レーサーが停止する最終位置を報告する必要があります。 

制約は大きく、最大で$2 \times 10^5$操作。 これにより、クエリごとにセルごとの移動をシミュレートするソリューションは即座に除外されます。これは、単一のクエリが円全体を横断する可能性があり、それでも遅すぎる可能性があり、そのようなクエリが多数存在する可能性があるためです。 同様に、更新のたびにセグメント情報を最初から再計算するのも遅すぎます。 

微妙な難しさは、各クエリが単なる接頭辞の合計の問題ではないことです。 速度は、これまでに遭遇した最大の難易度に応じて単調減少で進化します。これは、コスト関数が区分的であり、パスに沿った過去の最大値に依存することを意味します。 

単純なソリューションを壊すエッジケースには、次のようなシナリオが含まれます。 

クエリごとの単純な線形シミュレーションは、次の場合にすぐに失敗します。$n$そして$q$単一のクエリが横断する可能性があるため、両方とも大きくなります。$10^5$細胞があります$10^5$クエリ、それにつながる$10^{10}$操作。 

プレフィックスサムのみのソリューションも失敗します。これは、高難易度セルによって速度が低下すると、後のセルは異なる速度レジームで動作するため、加法性が成立しないためです。 

さらに微妙なケースは、更新によってセグメント内の単一の高難易度セルが変更される場合です。これにより、最初の速度低下が発生する場所が完全に変更され、構造がダイナミック レンジ最大クエリをサポートしない限り、事前計算されたサマリーが無効になります。 

## アプローチ

 ブルートフォースアプローチは簡単です。 クエリごとに、開始位置からの動きをシミュレートし、円を通過し、必要に応じて現在の速度を更新し、速度を超えるまでの時間を累積します。$t$。 各ステップには継続的な作業が必要なため、1 つのクエリにコストがかかります$O(n)$最悪の場合。 と$q$クエリの場合、これは次のようになります$O(nq)$、これは実現可能な限界をはるかに超えています。 

これが失敗する理由は、配列が範囲更新によってローカルでのみ変更されるにもかかわらず、各クエリが同じ構造を繰り返し再処理するためです。 重要な観察は、トラバーサル中に重要なのは、セグメント内の値の正確なシーケンスではなく、2 つの集合的なプロパティであるということです。速度低下が発生するかどうかを決定するセグメント内の最大難易度と、セグメント内でさらなる速度低下が発生しない場合の時間への合計寄与です。 

これは、各セグメントが着信速度を変換する関数のように動作する必要があることを示唆しています。$v$新しいスピードと時間コストへ。 このような関数をセグメント ツリー上で構成できれば、セルを反復処理する代わりにツリーを走査することでクエリに答えることができます。 

したがって、最適なソリューションでは、範囲追加と範囲割り当てをサポートする遅延伝播を備えたセグメント ツリーが維持され、各ノードは、要素ごとに拡張することなく、特定の受信速度に対するセグメントの影響を評価するのに十分な情報を格納します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nq)$|$O(1)$| 遅すぎる |
 | 遅延 + 機能ノードを含むセグメント ツリー |$O(q \log^2 n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 各セグメントを次のことに答えることができる構造として扱います。与えられた着信速度$v$、このセグメント内で費やされる時間、および処理後の結果の発信速度はどれくらいか。 

1. 一連の難易度にわたってセグメント ツリーを構築します。各ノードは、その区間内の難易度の合計とその区間内の最大難易度を維持します。 これら 2 つの値は、セグメント内で速度が低下するかどうかを判断し、固定速度領域でのフルセグメントのコストを計算するには十分です。 
2. 各クエリセグメントノードについて、現在の速度を考慮します。$v$。 もし$v$すでに十分に小さいため、セグメント内のローカルしきい値を決して超えません。つまり、ノード内で速度低下が引き起こされない場合、セグメント全体が寄与する時間は、難易度の合計を で割ったものに等しいです。$v$、発信速度は変わりません。 
3. もし$v$セグメント内の少なくとも 1 つのセルが縮小を強制するほど十分に大きい場合、セグメント全体を処理できません。 この場合、最初のトリガーとなるセルが最初の速度変更ポイントを決定するため、左から右に処理しながら子に降りていきます。 
4. 降下中、葉にぶつかるたびに、単一のセルに正確な遷移ルール​​を適用します。現在の速度がセルのしきい値を超える場合は速度を下げ、対応する時間コストを追加し、それに応じて速度を更新します。 
5. いずれかの時点までこのトラバースを続けます$t$疲れ果てるか、円形構造の周りを一周するかです。 答えは最終的に到達した位置です。 

重要な実装のアイデアは、各ノードがフィルターとして機能するということです。現在の速度と比較して「重大な」困難が含まれていない場合は 1 ステップで消費できるか、分解する必要があります。 これにより、問題のある領域のみに到達することが保証されます。 

正確さは、トラバースの各ステップで、現在の速度がこれまでに遭遇したすべてのしきい値の真の最小値であるという不変条件に依存します。 速度は低下するだけであるため、あるセグメントが所定の速度の下で安全になると、より厳しい制約に遭遇するまで、後続のすべてのセグメントは安全なままになります。 この単調性により、セグメントの決定がトラバース全体を通して有効であり、将来の隠れた難易度の増加によって以前の集計が無効になることがないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.sum = [0] * (4 * self.n)
        self.mx = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def build(self, idx, l, r, arr):
        if l == r:
            self.sum[idx] = arr[l]
            self.mx[idx] = arr[l]
            return
        m = (l + r) // 2
        self.build(idx * 2, l, m, arr)
        self.build(idx * 2 + 1, m + 1, r, arr)
        self.pull(idx)

    def pull(self, idx):
        self.sum[idx] = self.sum[idx * 2] + self.sum[idx * 2 + 1]
        self.mx[idx] = max(self.mx[idx * 2], self.mx[idx * 2 + 1])

    def update_range_add(self, idx, l, r, ql, qr, val):
        if ql <= l and r <= qr:
            self.sum[idx] += val * (r - l + 1)
            self.mx[idx] += val
            return
        m = (l + r) // 2
        if ql <= m:
            self.update_range_add(idx * 2, l, m, ql, qr, val)
        if qr > m:
            self.update_range_add(idx * 2 + 1, m + 1, r, ql, qr, val)
        self.pull(idx)

    def update_range_set(self, idx, l, r, ql, qr, val):
        if ql <= l and r <= qr:
            self.sum[idx] = val * (r - l + 1)
            self.mx[idx] = val
            return
        m = (l + r) // 2
        if ql <= m:
            self.update_range_set(idx * 2, l, m, ql, qr, val)
        if qr > m:
            self.update_range_set(idx * 2 + 1, m + 1, r, ql, qr, val)
        self.pull(idx)

    def walk(self, idx, l, r, ql, qr, v, t, pos):
        if t <= 0:
            return pos, v, t

        if ql <= l and r <= qr:
            if v * self.mx[idx] <= 1:
                cost = self.sum[idx] / v
                if cost > t:
                    return pos, v, 0
                return (pos + r - l + 1) % self.n, v, t - cost

        if l == r:
            d = self.sum[idx]
            if v * d > 1:
                v = 1 / d
            cost = d / v
            if cost > t:
                return pos, v, 0
            return (pos + 1) % self.n, v, t - cost

        m = (l + r) // 2
        pos, v, t = self.walk(idx * 2, l, m, ql, qr, v, t, pos)
        if t <= 0:
            return pos, v, t
        return self.walk(idx * 2 + 1, m + 1, r, ql, qr, v, t, pos)

n, q = map(int, input().split())
arr = list(map(int, input().split()))
st = SegTree(arr)

for _ in range(q):
    tmp = input().split()
    if tmp[0] == 'P':
        l, r, d = map(int, tmp[1:])
        st.update_range_add(1, 0, n - 1, l, r, d)
    elif tmp[0] == 'R':
        l, r, d = map(int, tmp[1:])
        st.update_range_set(1, 0, n - 1, l, r, d)
    else:
        s, t = int(tmp[1]), int(tmp[2])
        pos, v, rem = st.walk(1, 0, n - 1, s, n - 1, 1, t, s)
        print(pos)
```セグメント ツリーは総計と最大難易度の両方を維持するため、ノードは現在の速度で一括処理しても安全かどうかを判断できます。 更新操作はこれらの集計を直接変更しますが、クエリ トラバーサルでは時間をかけて移動をシミュレートする再帰降下が使用されます。 

微妙な点は、walk 関数がセグメントを線形範囲として扱い、位置を法的に手動でラップすることです。$n$循環構造は、クエリをセグメントに分割することによってトップレベルで処理されるためです。$s$に$n-1$そしてさらに続きます$0$必要に応じて。 

実装における主な困難は、速度の更新と時間消費が正しい順序で適用されることを保証することです。つまり、セルまたはセグメントのコストを計算する前に速度が更新されます。 

## 実用的な例

 小さな配列を考えてみましょう$d = [2, 5, 1, 4, 3]$、位置から開始$2$時間とともに$t = 10$。 位置、速度、残り時間を追跡します。

 この時点で、次の遷移内で時間がなくなるため、位置 4 で停止します。これは、走査がどのように厳密に順次的であり、累積コストに依存するかを示しています。 

ここで、高難易度のセルが早期に出現し、速度低下を余儀なくされる場合を考えてみましょう。 

入力:$d = [1, 10, 1]$、 始める$s = 0$、 大きい$t$。 

| ステップ | ポジション | 前の速度 | 調整 | 後の速度 | 時間 |

 ## 特殊なケース

 主なエッジ ケースは、範囲の更新後にセグメントに非常に大きな難易度が 1 つ含まれる場合に発生します。 その場合、たとえ以前のセグメントが安全であったとしても、トラバーサルはその時点で速度制限を即座にトリガーする必要があります。 ノードの最大値が更新された難易度を反映し、子への降下を強制するため、セグメント ツリーはこれを正しく処理します。 

もう 1 つのエッジ ケースは、時間バジェットが 2 つのセル間の境界でちょうど終了する場合です。 実装では、境界で停止するということは、現在のセル インデックスではなく次のセル インデックスを報告することを意味することを保証する必要があります。 これは、セルまたはセグメントが完全に消費された後にのみ位置をインクリメントすることによって処理されます。 

最後に、循環ラップアラウンドの場合は、クエリが配列の終わり近くで開始され、配列の先頭まで続く可能性があるため、慎重に処理する必要があります。 トラバーサルを 2 つの線形セグメントに分割すると、論理ドメインが循環的であっても、基礎となる構造がクエリごとに線形化されるため、正確さが保証されます。
