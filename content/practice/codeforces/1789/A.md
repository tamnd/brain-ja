 ## 解決策
 ## 問題の理解

 いくつかのテスト ケースが与えられ、それぞれのテスト ケースは小さな正の整数の配列で構成されます。 各配列について、その要素を任意に並べ替えることができます。 順序を選択した後、少なくとも 2 の長さのすべてのプレフィックスを検査し、そのプレフィックスの gcd を計算します。 要件は、そのようなすべてのプレフィックスがプレフィックス長を超えない gcd を持つ必要があることです。 この制約を満たす配列の順序が少なくとも 1 つ存在するかどうかを判断する必要があります。 

テスト ケースごとの制約は小さく、すべてのテストの要素の合計は最大でも数百です。 つまり、$O(n \log n)$あるいは$O(n^2)$テスト ケースごとのアプローチは許容されますが、階乗または指数再配置を伴うものは許容されません。 

単純な推論による微妙な失敗のケースは、隣接するペアのローカル チェックで十分であると仮定することです。 たとえば、次のような配列では、$[3, 6, 1]$、最初のペアを除くすべての隣接するペアは無害に見えるかもしれませんが、接頭辞は$[3,6]$その gcd は次のとおりであるため、すでに条件に違反しています。$3$、長さよりも大きい$2$。 これは、制約が基本的にペアベースではなくプレフィックスベースであることを示しています。 

もう 1 つのよくある落とし穴は、元の順序に意味があると思い込むことです。 この問題では明示的に並べ替えが許可されているため、順列を考慮せずに指定されたシーケンスのみを評価する解決策は、次のような場合に失敗します。$[15, 35, 21]$、入力順序が無効であっても、適切な順序が存在します。 

## アプローチ

 ブルートフォースアプローチは、配列のすべての順列を試し、それぞれの順序がプレフィックス gcd 条件を満たすかどうかを確認することです。 順列ごとに、プレフィックス gcds を計算し、制約を検証します。 これは正しいですが、順列の数が次のように増加するため、直ちに実行できなくなります。$n!$、それはたとえ限界をはるかに超えています$n = 20$。 

重要な観察は、実際にはすべての順列を探索する必要はないということです。 この条件はプレフィックス gcd 値のみに依存し、gcd は非常に強力な方法で単調に動作します。つまり、一度小さくなると、数値を追加しても再び増加することはありません。 これは、値が小さいほど初期に gcd が減少する傾向があり、後の制約を満たすことが容易になるため、要素を昇順に配置することが自然な候補であることを示唆しています。 

これにより、配列をソートし、このソートされた順序がすべてのプレフィックス制約をすでに満たしているかどうかを確認するという欲張りなアイデアが得られます。 最適に構造化された順序付け (昇順でソート) さえ失敗した場合、他の並べ替えでは早期の接頭辞 gcd の爆発を修正できません。これは、大きな gcd に寄与する要素をより前に配置する並べ替えは、接頭辞 gcd を大きくするか等しくするだけであるためです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (すべての順列) |$O(n!)$|$O(n)$| 遅すぎる |
 | ソート + 接頭辞チェック |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 次の方法でソリューションを構築します。 

1. テスト ケースごとに、配列を降順でない順序で並べ替えます。 これにより、gcd の増加に関して最も安定したプレフィックス構造が作成されます。 
2. 現在のプレフィックスの gcd を維持しながら、配列を左から右に走査します。 
3. 各ポジションで$i$で終わるプレフィックスの gcd を計算します。$i$。 もし$i \ge 1$、この gcd が以下より大きいかどうかを確認します。$i + 1$。 そうであれば、有効な順列が存在しないことがすぐにわかります。 
4. 条件に違反せずにスキャンを終了した場合、ソートされた配置は有効であるため、答えは「YES」です。 

ソートされた配列のみをチェックする理由は、不正なプレフィックスを「修正」しようとすると、より小さい数値をより早く挿入する必要があるためですが、それらの数値はソート順のできるだけ早い段階ですでに配置されています。 ソートされた順序で gcd を制御できない場合は、再配置しても制御できません。 

### なぜ効果があるのか

 プレフィックスの gcd は、現在の gcd の倍数ではない数値を含めた場合にのみ減少します。大きな gcd 値を早期に破るには、小さな数値が最も効果的です。 ソートにより、使用可能な最小の要素ができるだけ早く使用され、すべてのステップでプレフィックス gcd が最小限に抑えられます。 プレフィックスの長さが増加するにつれて条件は厳しくなるため、この最良のケースの貪欲な構築さえも満たさない順序付けは不可能であることを意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from math import gcd

t = int(input())
for _ in range(t):
    n = int(input())
    a = list(map(int, input().split()))
    
    a.sort()
    
    g = 0
    ok = True
    
    for i, x in enumerate(a):
        g = gcd(g, x)
        if i >= 1 and g > i + 1:
            ok = False
            break
    
    print("Yes" if ok else "No")
```ソート後、実行中の gcd を維持します。 重要な詳細はインデックスの比較です。プレフィックスの長さは$i+1$、gcd と比較します。$i+1$、 ない$i$。 この条件は長さが 2 以上のプレフィックスにのみ適用されるため、最初の要素はチェックされません。 

唯一の微妙な点は、gcd をゼロで初期化することです。これは中立要素として正しく機能するため、最初の更新では単純に最初の配列値に設定されます。 

## 実用的な例

 インプットを考慮する$[3, 6, 1]$。 並べ替えると、次のようになります$[1, 3, 6]$。 

各ステップで:

 | 私 | 値 | プレフィックス gcd |
 | --- | --- | --- |
 | 0 | 1 | 1 |
 | 1 | 3 | 1 |
 | 2 | 6 | 1 |

 すべてのプレフィックス gcd 値は、そのインデックスに 1 を加えた値より大きくなることはないため、これは有効です。 

ここで考えてみましょう$[15, 35, 21]$。 並べ替えると得られるもの$[15, 21, 35]$。 

| 私 | 値 | プレフィックス gcd |
 | --- | --- | --- |
 | 0 | 15 | 15 |
 | 1 | 21 | 3 |
 | 2 | 35 | 1 |

 で$i = 1$、プレフィックス長は 2、gcd は 3 で条件に違反するため、答えは NO です。 

これは、並べ替えられた構成で障害ができるだけ早く検出されることを示しており、並べ替えによって避けられない違反が明らかになることを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 | 時間 |$O(n \log n)$| ソートが優先され、gcd 更新は線形です。 
| スペース |$O(1)$番外編 | プレフィックス変数のみが保存されます。 

合計の入力サイズは十分小さいため、各テスト ケースの並べ替えは制限内で簡単に高速に実行でき、gcd 計算は要素ごとに一定の作業になります。

            g = gcd(g, x)

                ok = False
                break
        out.append("Yes" if ok else "No")
    return "\n".join(out)

 ## 特殊なケース

 サイズ 2 の最小配列は、チェックする唯一のプレフィックスが完全な配列自体であるため、条件全体を即座に公開します。 並べ替えられた順序が 1 回評価され、gcd が 2 と比較されるため、アルゴリズムはこれを正しく処理します。 

繰り返しの値を含む配列は、予測どおりに動作します。これは、繰り返しの gcd 強化によって gcd が安定した状態に保たれるか増加し、この増加が許容されるプレフィックスしきい値を超えたときにソートされたスキャンが即座に検出されるためです。
