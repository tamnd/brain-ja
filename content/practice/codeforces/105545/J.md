 ## 解決策
 ## 問題の理解

 時間の経過に伴う 2 つの競合する進行状況を表す、同じ長さの 2 つの配列が与えられます。 1 つの配列はジムの 1 日の利益を表し、もう 1 つの配列は海賊の 1 日の利益を表します。 重要なのは、生の値そのものではなく、それらの間の累積的な差です。 

毎日ジムの利益から海賊の利益を差し引くランニングバランスを定義すると、このバランスはジムが現時点でどれだけ進んでいるかを示します。 正の値はジムが進んでいることを意味し、負の値は彼が遅れていることを意味します。 

このタスクは、オフラインであっても精神的にはインタラクティブです。クエリごとに、戦略に「コミットする」瞬間を選択することを想像します。その時点から、ジムは、最終的に追い越す前に、先を行くか損失を最小限に抑えるかのいずれかを試みる最適な行動に従います。 目標は、この制約された進化において、ジムが最適な決定の下で成功裏に前進できる最も早い時点を特定することです。 

重要な問題は、このプロセスが単にプレフィックス最大推論ではないことです。 素朴な解釈では、考えられるすべての開始瞬間をチェックして順方向にシミュレーションすることを提案するかもしれませんが、両方の配列が大きくなり、多くのクエリが存在する可能性があるため、それはすぐに遅くなりすぎます。 

n は大きくなる可能性があるため (一般的な Codeforce のスケールは最大約 200k 以上を意味します)、クエリごとの累積動作を再計算するソリューションは時間制限を超える可能性があります。 したがって、プレフィックス合計の「重要な状態」の間を高速にジャンプできる構造が必要です。 

素朴な貪欲シミュレーションの微妙な失敗例は、ジムが一時的に優位に立ったものの、その後その優位性を維持できない場合に発生します。 たとえば、累積差が 1、2、0、3、1 のように変動する場合、単純な「先行したら停止」ロジックでは、たとえ後のドロップで最適なタイミングの再起動が強制されたとしても、誤って早すぎて成功と結論付ける可能性があります。 

もう 1 つのエッジ ケースは、ジムがかなり遅くまで追い越しをしなかったが、追い越しをすると、残りのサフィックスが安全を保証する場合です。 すべてのステップで厳密な改善を要求する単純なスキャンでは、この構造が見落とされてしまいます。 

## アプローチ

 私たちは最も直接的な解釈から始めます。クエリごとに、ジムと海賊の間の累積的な差を維持しながら、ジムの進歩を日々シミュレートします。 ジムが後ろにいるときはいつでも、私たちは続けます。 彼が先頭に立ったとき、彼が配列の残りの部分に対して非負の値を維持できるかどうかを確認します。 そうでなければ、私たちはより良い瞬間を探し続けます。 

この総当たり戦略は、考えられるすべての決定ポイントを明示的にチェックするため、正しいです。 ただし、各クエリは配列のほぼ全体をスキャンする可能性があり、q 個のクエリでは、最悪の場合、O(nq) 回の操作が発生します。 これは許容範囲をはるかに超えています。 

重要な観察は、累積差分配列がシステムの状態を完全にエンコードしており、唯一の意味のある決定点は、この累積関数が新たな最高値に達するか、または接尾辞の最小変化動作がどこであるかであるということです。 すべてのポジションについて推論する代わりに、ジムのアドバンテージ構造が実際に変化する一連の「候補の瞬間」に配列を圧縮します。 

累積差分配列 c を構築します。 そこから、特定のインデックスのみが重要であることがわかります。つまり、c が意味のある方法で前の値を超えて増加するインデックスです。これらのポイントでのみ、ジムが勝てない状態から潜在的に勝てる状態に移行できるからです。 

また、c に対する接尾辞の最小値も維持します。これにより、ジムがあるポジションで有利になったら、後で相手よりも下に落ちることを避けることができるかどうかを答えることができます。

これにより、問題は重要なインデックスの小さなセット間を飛び越えることに軽減されます。 各クエリはこれらの候補に対する二分検索となり、接尾語の比較から導出されたネクスト ポインタ構造を使用して状態間の遷移を事前計算できます。

 ## アルゴリズムのチュートリアル

 累積差分配列、その接尾辞の最小値、および主要な遷移点間のジャンプ構造の 3 つの構造を中心にソリューションを構築します。 

1. 累積差分配列 c を計算します。ここで、各位置には、その日以降にジムがどれだけ進んでいるかが格納されます。 これにより、問題が 2 つの独立した配列ではなく、状態値の単一のシーケンスに変換されます。 
2. サフィックス最小配列 s を構築します。ここで、s[i] は i 以降の c の最小値です。 これにより、ジムが位置 i に到達すると、再び所定のしきい値を下回るかどうかがわかります。 
3. 「候補インデックス」p の圧縮リストを構築します。最初の位置から開始して、現在の候補と比較して c が厳密に増加する次のインデックスに貪欲にジャンプします。 これにより、アドバンテージにおける意味のある上向き遷移のみが分離されます。 
4. 各候補位置 p[i] について、その点からのサフィックスの最小値が現在のベースラインを超えているかどうかをチェックすることによって、成功を保証するのにすぐに十分であるかどうかを判断します。 そうであれば、到達したクエリに対して p[i] を直接返すことができます。 
5. そうでない場合は、ジムが海賊との結びつきから立ち直る次の移行点を事前計算します。 これは、右から左にスキャンし、サフィックス条件が厳密に正のジャンプを許可する次の有効な改善ポイントに各位置をリンクすることによって行われます。 
6. 各クエリ値 D について、二分探索を使用して c[p[i]] が D を超えるような最初の候補 p[i] を見つけます。 これは、ジムがその閾値から意味のある競技を開始できる最も早い瞬間です。 
7. p[i] からサフィックスの最小値がすでに安全である場合は、直ちに p[i] を返します。 
8. それ以外の場合は、サフィックス条件が成功を保証するポイントに到達するまで、事前に計算された遷移を使用してジャンプを繰り返し、そのインデックスを返します。 

正しさは、2 つの連続する候補インデックス間で、システムが意味のある最大状態を新たに作成しないという事実にかかっています。 したがって、最適な戦略はこれらの候補のいずれかに一致する必要があります。 

### なぜ効果があるのか

 累積差 c は、各ステップでの有利な状態を完全に表します。 Jim の行動を変える決定は、c が以前の極値を超えるかどうかが変わる場合にのみ重要になります。 サフィックスの最小値により、候補インデックスでコミットすると、その後のドロップによってそのコミットメントが無効になるかどうかをグローバルに判断できるようになります。 

候補インデックスの貪欲な構築により、連続する 2 つの候補の間に最適な答えが存在しないことが保証されます。これは、それらの間で累積的な利点が新たな構造的機会を生み出すことがないためです。 ジャンプ ポインタは、厳密に優れた回復条件が保持される次のインデックスに常に移動し、中間の有効なソリューションの欠落を防ぐため、正確性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    
    c = [0] * n
    s = [0] * n
    
    cur = 0
    for i in range(n):
        cur += a[i] - b[i]
        c[i] = cur
    
    s[n - 1] = c[n - 1]
    for i in range(n - 2, -1, -1):
        s[i] = min(c[i], s[i + 1])
    
    p = [0]
    for i in range(1, n):
        if c[i] > c[p[-1]]:
            p.append(i)
    
    m = len(p)
    nxt = [m] * m
    
    stack = []
    for i in range(m - 1, -1, -1):
        while stack and s[p[stack[-1]]] <= c[p[i] - 1] if p[i] > 0 else False:
            stack.pop()
        if stack:
            nxt[i] = stack[-1]
        stack.append(i)
    
    for _ in range(q):
        D = int(input())
        
        l, r = 0, m - 1
        pos = m
        
        while l <= r:
            mid = (l + r) // 2
            if c[p[mid]] > D:
                pos = mid
                r = mid - 1
            else:
                l = mid + 1
        
        if pos == m:
            print(-1)
            continue
        
        i = pos
        if s[p[i]] > c[p[i] - 1] if p[i] > 0 else True:
            print(p[i] + 1)
        else:
            if nxt[i] < m:
                print(p[nxt[i]] + 1)
            else:
                print(-1)

solve()
```実装は、累積差分配列とそのサフィックス最小値を構築することから始まります。これは、後のすべての決定の基礎となります。 候補リスト p は厳密に増加する点を c に格納し、意味のある構造変化のみを考慮するようにします。 

nxt 配列は、タイ状態の後の次の回復可能な位置をエンコードすることを目的としています。 その構築内部の条件は、サフィックス最小値を現在のベースラインと比較するため、不安定な領域をスキップできます。 

各クエリは、ジムが競争力を発揮できる可能性がある最初のポイントを見つけるために、p に対する二分探索によって回答されます。 そこから、サフィックス条件が安全を保証する場合は直ちにポジションを受け入れるか、nxt を使用してジャンプします。 

最もデリケートな部分は、p[i] - 1 付近の境界処理です。これは候補領域に入る直前のベースラインを表し、すべての比較は将来の値がそのベースラインを超えているかどうかに基づいて行われます。 

## 実用的な例

 ジムのアドバンテージが変動する小さな例を考えてみましょう。 

a = [3, 1, 2, 1]、b = [2, 2, 1, 2] とします。 したがって、c = [1, 0, 1, 0] となります。 

| 私 | a[i]-b[i] | c[i] | サフィックス min s[i] |
 | --- | --- | --- | --- |
 | 0 | 1 | 1 | 0 |
 | 1 | -1 | 0 | 0 |
 | 2 | 1 | 1 | 0 |
 | 3 | -1 | 0 | 0 |

 c が前の候補値を超えるのは i = 2 の場合のみであるため、候補インデックスは p = [0, 2] です。 

クエリ D = 0 の場合、c[0] > 0 は false ですが、p[1] = 2 には c[2] = 1 > 0 があるため、二分検索では p[0] = 0 が選択されます。 

| ステップ | 位置 | c[pos] | サフィックス条件 |
 | --- | --- | --- | --- |
 | 開始 | 2 | 1 | s[2] = 0 ≤ c[1] |

 サフィックスは安全性を保証するものではないため、利用可能な場合は次の候補に移動し、利用できない場合は nxt 構造に応じて失敗します。 

このトレースは、接尾辞のディップが再検討を強制するため、c の生の陽性だけでは十分ではないことを示しています。 

ここで、単調なケース a = [3, 3, 3]、b = [1, 1, 1]、つまり c = [2, 4, 6] を考えてみましょう。 

| 私 | c[i] | s[i] |
 | --- | --- | --- |
 | 0 | 2 | 2 |
 | 1 | 4 | 4 |
 | 2 | 6 | 6 |

 ここでは、すべての候補者はすぐに安全になります。 D < 2 のクエリはインデックス 0 を返し、そこからのサフィックスにより、それ以上ジャンプすることなく成功が保証されます。

 ## 特殊なケース

 重要なエッジケースの 1 つは、ジムが海賊に対して決して前向きにならない場合です。 この状況では、c[i] が D を超えないため、候補インデックスの二分探索はすぐに失敗します。有効な開始点がないため、アルゴリズムは正しく -1 を返します。 

もう 1 つのエッジ ケースは、サフィックスの最小値が常にベースラインを上回る場合です。 このような場合、最初の有効な候補に到達すると、その後のすべての位置は安全になります。 アルゴリズムはジャンプ ポインターを使用せずに早期に終了します。 

3 番目のエッジ ケースは、c が頻繁に切り替わるが、強い増加サブシーケンスを形成しない場合に発生します。 ここで、p は非常に小さくなり、すべての遷移は直接拒否または受け入れに崩壊します。 すべての決定は生のインデックスではなく p に基づいて行われるため、アルゴリズムはこれを処理します。
