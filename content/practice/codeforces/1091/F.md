 ## 解決策
 ## 問題の理解

 連続したセグメントで構成される長い 1 次元のルートが与えられます。 各セグメントには長さと地形タイプ (草、水、溶岩のいずれか) があります。 ボブは最初のセグメントの直前に開始し、最後のセグメントの後に遠端に到達したいと考えています。 

ボブは、歩行、水泳、飛行の 3 つのモードで移動できます。 歩行は草の上のみ、水泳は水の上のみ、飛行はどこでも許可されます。 各モードにはメートルあたりの固定コストがあります。歩行は遅いですがスタミナを与え、水泳は歩くより速くスタミナを与え、飛行は速いですがスタミナを消費します。 スタミナはゼロから始まり、ゼロを下回ることはありません。 

最大の難点は、溶岩を渡る唯一の方法である飛行がスタミナを消費する唯一の方法でもあるということです。 したがって、決定はスピードによる最短経路だけではなく、スタミナを使い果たさずに溶岩セクションを飛行で横断できるように、安全な地形でいつスタミナを蓄積するかということによって決まります。 

入力は各セグメントの長さとそのタイプを記述し、地形の制約とスタミナのダイナミクスを考慮しながら、開始から終了までの最小合計時間を計算する必要があります。 

n が 10^5 まで、セグメント長が 10^12 までという制約により、メートルごとのシミュレーションが直ちに除外されます。 どのようなソリューションでも、各セグメントを集約された推論に圧縮し、線形時間でルートを処理する必要があります。 メーターを個別に扱うアプローチでは、最悪の場合、最大 10^17 の演算が必要になりますが、これは実行不可能です。 

溶岩セグメントが長く、十分なスタミナが構築される前に発生する場合、微妙なエッジケースが発生します。 たとえば、ボブが早い段階で溶岩に遭遇した場合、長距離飛行を試みる前に十分なスタミナを蓄積するために、前のセグメントを歩いたり泳いだりして迂回する必要がある可能性があります。 「十分なスタミナを蓄積してから飛行する」だけの単純な貪欲な戦略は失敗します。スタミナは局所的な蓄積だけではなく、以前の選択に依存するためです。 

草と水のセグメントが交互に存在する場合、別の明白ではない状況が発生します。 ウォーキングと水泳は両方ともスタミナを与えますが、速度と制約が異なるため、たとえ当面の移動コストが増加したとしても、純粋にスタミナのタイミングを操作するためにセグメントで低速モードを選択することが最適な場合があります。 

## アプローチ

 ブルートフォースの観点では、問題は位置とスタミナに関する状態グラフとして扱われます。 ボブはラインに沿った各ポイントから地形に応じて移動モードを選択し、それに応じてスタミナを更新できます。 スタミナの変化は以前のすべての決定に依存するため、飛行ではグローバル カップリングが導入されます。 直接の状態空間検索では、メートル単位の位置と現在のスタミナを追跡し、モードに応じてスタミナを増減する可能性のある遷移を考慮する必要があります。 セグメントごとに圧縮しても、総移動距離に応じて可能なスタミナ値の数は増加し、前後に歩いたり泳いだりする可能性があるため、移行は両方向に発生する可能性があります。 これにより、すぐに指数関数的または擬似多項式の動作が発生します。 

重要な観察は、最適な動きには恣意的なバックトラッキング構造が決して必要ないということです。 後退する唯一の理由は、必要な溶岩の上の飛行を試みる前に、安価な地形（草または水）を追加のスタミナに変換することです。 この後方移動は「スタミナを買うために時間を費やす」方法として理解でき、複数のセグメントを任意に混合するのではなく、スタミナを獲得できる最も安価な利用可能な地形セグメントで実行することが常に最適です。

これにより、飛行による即座のスタミナ消費を強制する溶岩セグメントを考慮しながら、セグメントを左から右に処理した後に現在利用可能なスタミナの量を維持するプロセスとして再解釈することができます。 溶岩に遭遇した場合は、十分なスタミナが蓄積されていることを確認する必要があります。 それ以外の場合は、最小限の時間コストで不足しているスタミナを生成するために、体系的な方法で以前の草/水の使用量を遡及的に「延長」する必要があります。 これにより、これまでに見られたスタミナを獲得するセグメントに対する貪欲な割り当て戦略が生まれます。 

位置とバックトラックの観点から考えるのではなく、草と水のセグメントを単位あたりの時間コストを伴うスタミナ獲得の貯蔵庫として扱い、溶岩セグメントを長さに比例してスタミナを消費する必須の支出ポイントとして扱います。 最適化は、以前に蓄積された安価なスタミナをどれだけ飛行の実現可能性に変換するかを決定することになります。

 ## アルゴリズムのチュートリアル

 1. セグメントを左から右に移動し、費やした合計時間と現在のスタミナという 2 つのアキュムレーターを維持します。 また、スタミナに貢献する、これまでに見られた草と水のセグメントを表す構造も維持します。 
2. 長さ L の草セグメントを処理する場合、歩行時間 5L を追加し、スタミナを L だけ増加します。このセグメントをスタミナ単位あたりの実効コスト 5 の「スタミナ バンク」として保存します。 
3. 長さ L の水セグメントを処理する場合、水泳時間 3L を追加し、スタミナを L だけ増加します。このセグメントをスタミナ単位あたりのコスト 3 で保存します。 
4. 長さ L の溶岩セグメントを処理する場合、L メートル飛行する必要があり、L 時間かかり、L スタミナが必要です。 現在のスタミナが十分であれば、スタミナから L を直接減算し、時間に L を加算します。 
5. スタミナが溶岩に不十分な場合、不足分 D = L - スタミナを計算します。 以前に保存された草/水の貢献から追加のスタミナ D を生成する必要があります。 
6. 追加時間を最小限に抑えるために、常に最も安価な入手可能なソースからスタミナを最初に「返金」します。つまり、草由来のスタミナ (ユニットあたりコスト 5) よりも水由来のスタミナ (ユニットあたりコスト 3) を優先します。 これは、常に最も高価なスタミナを最初に逆に取り消すことと同じです。 
7. スタミナの各単位について、以前のセグメントから飛行可能性に変換し、代わりに以前の歩行/水泳の寄与を飛行に置き換えます。 これにより、保存されている旅行コストの差が減り、純コストが変わりますが、柔軟性が向上します。 実際には、追加のアップグレード コスト (1 メートルあたりのモード コストの差) を支払うものとしてモデル化します。 
8. 不足分が満たされるまでスタミナの抽出を続け、それに応じて合計時間を更新し、スタミナがゼロを下回らないようにします。 
9. 溶岩を解決したら、スタミナ プールが更新された次のセグメントに進みます。 

### なぜ効果があるのか

 このアルゴリズムは単調な構造に依存しています。スタミナは溶岩セグメントでのみ必要であり、以前に処理された非溶岩セグメントのみがスタミナを生成できます。 すべてのスタミナ生成セグメントは、溶岩消費の決定が最終決定される前に追加される独立した貢献であるため、実現可能性に影響を与えることなくスタミナ ソースを「割り当てる」方法を並べ替えることができます。 まず、常に安価なスタミナ源を使用するという貪欲な選択により、過去の動きを追加のスタミナに変換する必要があるときはいつでも、最小限の時間増加で変換できるようになります。 これにより、部分的な後方移動戦略を混合する利点が防止されます。そのような戦略は、以前のセグメントに対するユニットのスタミナ調整に分解され、貪欲に最適に処理されるためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    l = list(map(int, input().split()))
    s = input().strip()

    # we store available stamina sources as [cost_per_stamina, remaining_amount]
    # cost per stamina: water=3, grass=5
    import heapq
    heap = []

    stamina = 0
    total_time = 0

    for i in range(n):
        length = l[i]
        t = s[i]

        if t == 'G':
            total_time += 5 * length
            stamina += length
            heapq.heappush(heap, (5, length))

        elif t == 'W':
            total_time += 3 * length
            stamina += length
            heapq.heappush(heap, (3, length))

        else:  # Lava
            need = length - stamina
            total_time += length  # flying cost
            stamina -= length

            if need > 0:
                # pull from cheapest stamina sources first
                temp = []
                while need > 0:
                    cost, amt = heapq.heappop(heap)
                    take = min(amt, need)
                    need -= take
                    amt -= take
                    total_time += (5 - cost) * take
                    if amt > 0:
                        heapq.heappush(temp, (cost, amt))

                for item in temp:
                    heapq.heappush(heap, item)

                stamina = 0

    print(total_time)

if __name__ == "__main__":
    solve()
```このコードは、基礎となる動きのコストをキーとして、スタミナ ソースの優先キューを維持します。 草は1メートルあたり5のコストでスタミナに貢献し、水は1メートルあたり3のコストでスタミナに貢献します。 溶岩に遭遇すると、飛行するとスタミナが直接消費されます。 スタミナが不十分な場合は、以前の歩行または水泳を遡って飛行に変換し、元のモードと飛行のコスト差のみを支払います。 ヒープにより、常に最も安価なスタミナ ソースが最初に調整されるため、追加コストが最小限に抑えられます。 

実装の微妙な詳細は、ヒープが分解された貢献を追跡する一方で、スタミナがグローバル カウンターとして扱われることです。 ヒープから消費する場合、セグメントは部分的に消費されるため、残りの部分を再挿入する必要があります。 これにより、欠損を補うためにセグメントが部分的にのみ必要な場合のエラーが回避されます。

 ## 特殊なケース

 溶岩セグメントが現在のスタミナよりも長いが、以前のセグメントが存在する場合、重大なエッジケースが発生します。 アルゴリズムは、以前のスタミナ貢献を部分的に消費することでこれを処理します。 たとえば、草 3、水 2、溶岩 10 がある場合、追加のスタミナ ユニットを 5 つアップグレードするだけで済みます。 ヒープにより、草よりも先に水由来のスタミナが変換されるため、コストの増加が最小限に抑えられます。 

もう 1 つの特殊なケースは、連続する溶岩セグメントです。 各溶岩セグメントは個別にスタミナを消費するため、アルゴリズムはスタミナを消費するたびにヒープのバランスを再調整することで繰り返し実行可能性を確保します。 これにより、スタミナの古い仮定を防ぐことができます。 

最後のエッジケースは、事前のスタミナが存在しない、長い初期溶岩セグメントです。 この場合、不足分は溶岩の全長に等しく、ヒープは未使用のままになります。これは、ソリューションが総距離に等しい純粋な飛行コストに正しく縮退することを意味します。
