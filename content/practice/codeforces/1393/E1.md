 ## 解決策
 ## 問題の理解

 元々ソートされたリストから取得されたと考えられる一連の単語が与えられます。元のリストは辞書順で減少していません。 ただし、元の各単語は、その中のどこかに 1 文字だけ余分な文字を挿入することによって変更されている可能性があるため、観察されるすべての単語は、真の元のバージョンよりも 1 文字だけ長くなります。 

私たちの仕事は、各単語から 1 文字を削除することで概念的に「修復」し、その結果得られるきれいになったシーケンスが辞書編集的に再び減少しないように、すべての単語にわたってそのような削除を選択するさまざまな方法が何通りあるかを数えることです。 最終的な答えは、観察された破損した単語と一致する有効な元のシーケンスの数を法でとったものです。$10^9+7$。 一貫した元のシーケンスが存在しない場合、答えはゼロになります。 

主な難点は、各単語には 1 文字を削除することで得られる複数の「親」が存在し、辞書編集上の順序がグローバルに保持される必要があるため、選択肢が単語間で相互作用することです。 

制約が非常に厳しいため、単語ごとにすべての削除を明示的に個別に試行しようとするアプローチは爆発的に増加します。 各単語の長さ$L$与える$L$最悪の場合、全長が 20,000 に達すると、単純な組み合わせは天文学的に大きくなります。 トランジションが極度に最適化されない限り、枝刈りを行わずにすべての単語を選択する動的プログラミングさえも実行できなくなります。 

いくつかの候補の削除により、異なる位置または単語にわたって同一の文字列が生成される場合、微妙なエッジ ケースが発生します。 もう 1 つの注意が必要な状況は、前の単語の選択肢の中に有効な先行単語がない場合であり、その場合はその分岐全体が直ちに削除されます。 最後に、たとえローカルな選択肢が存在しても、シーケンス全体に連鎖する辞書編集上の制約により、グローバルな一貫性が失われる可能性があります。 

## アプローチ

 直接的な総当りの解釈は簡単です。 各単語について、ちょうど 1 文字を削除して形成されたすべての文字列を考慮します。 これにより、ポジションごとに一連の候補者が得られます。 次に、単語ごとに 1 つの候補を選択するあらゆる方法を試し、結果のシーケンスがソートされているかどうかを確認します。 

これは、求められているものを正確に列挙するため、概念的に機能します。 ただし、組み合わせの数は、$\prod_i |s_i|$、最悪の場合は次のように動作します。$20^{1000}$-規模の拡大。 すべての候補を生成するだけでもすでにコストがかかります$O(\text{total length}^2)$、すべてのシーケンスをチェックすることは完全に不可能です。 

重要な観察は、完全なシーケンスを明示的に列挙する必要がまったくないということです。 「辞書編集的に減少しない」という条件は、連続する単語間の関係にのみ依存します。 これは当然、有効な選択肢の数を伝播するシーケンス内の位置に対する動的プログラミングを示唆しています。 

ただし、完全な文字列を繰り返し比較すると、やはりコストが高くなります。 2 番目の洞察は、すべての候補文字列が 1 文字を削除することによって形成されるため、すべての候補を効率的に生成し、ハッシュやサフィックス比較などの事前計算された構造を使用して比較できることです。 候補が利用可能になると、問題は層状グラフ内の非減少シーケンスをカウントすることになります。各単語は層であり、各候補はノードであり、単語からエッジが存在します。$i-1$に$i$候補の順序が有効な場合。 

これにより、問題は階層化された DP に変わり、遷移が辞書編集的な順序によって制限されます。 最後の最適化は、各レイヤー内の候補をソートし、プレフィックス集約を使用して遷移を効率的にカウントすることで、すべてのペアを明示的にチェックすることを回避することです。

 ## アルゴリズムのチュートリアル

 正確に 1 文字を削除することで、各単語の可能なすべての「親文字列」を構築します。 長い単語に対して$m$、私たちが生産します$m$候補者たち。 

次に、現在の単語の各候補に到達できる方法の数を維持しながら、単語を左から右に処理します。 

1. 単語ごとに 1 文字を削除して、すべての候補文字列を生成します。 このステップが必要なのは、すべての有効な解決策が単語ごとに正確に 1 つの削除を選択する必要があるため、状態空間を完全に具体化するためです。 
2. 最初の単語の候補を辞書順に並べ替え、それぞれに DP 値 1 を割り当てます。これは、これらのクリーン化された文字列のいずれかが有効なシーケンスの開始になる可能性があることを表します。 
3. 次の各単語についても、その候補を生成し、辞書順に並べ替えます。 前のレイヤーに基づいてこれらの候補の DP 値を計算します。 
4. 現在の単語の固定候補については、前の単語の候補が辞書編集的にその単語以下である候補がいくつあるかを数える必要があります。 各ペアを比較する代わりに、両方のソート済みリストをスイープし、前の層からの DP 値のプレフィックス合計を維持します。 これにより、レイヤーごとにすべての遷移を線形時間で計算できるようになります。 
5. 現在のレイヤー内のすべての候補の DP 値を計算した後、前のレイヤーを現在のレイヤーに置き換えて続行します。 
6. すべての単語を処理した後、最後の層のすべての DP 値を合計して答えを取得します。 

これが効率的に機能する主な理由は、辞書編集的な順序付けにより、ソートされた候補リスト全体に単調な構造が生じるためです。 両方の層がソートされると、有効な遷移は任意の 2 部グラフではなくプレフィックス構造を形成します。 

### なぜ効果があるのか

 各ステップで、DP[i][j] は、ソートされた順序を維持しながら単語 i の j 番目の候補に到達する方法の数を表します。 辞書編集順は合計であり、ソート時に保存されるため、候補のすべての有効な先行文字が、以前にソートされたリストのプレフィックスを形成します。 これにより、プレフィックス合計がすべての有効な遷移を二重にカウントしたり省略したりすることなく正しく集計されることが保証されます。 DP の不変条件は、単語 i を処理した後、すべてのカウントが i までの有効な部分再構成の数を正確に反映し、全体的な単調性を維持することです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

def gen_candidates(s):
    # generate all strings formed by deleting one character
    res = []
    n = len(s)
    for i in range(n):
        res.append(s[:i] + s[i+1:])
    return res

n = int(input())
words = [input().strip() for _ in range(n)]

# build first layer
prev = sorted(gen_candidates(words[0]))
dp = [1] * len(prev)

# precompute nothing else; we rely on lex ordering

for i in range(1, n):
    cur = sorted(gen_candidates(words[i]))

    # prefix DP over previous layer
    new_dp = [0] * len(cur)

    j = 0
    pref = 0

    for k in range(len(cur)):
        # advance j while prev[j] <= cur[k]
        while j < len(prev) and prev[j] <= cur[k]:
            pref = (pref + dp[j]) % MOD
            j += 1
        new_dp[k] = pref

    prev = cur
    dp = new_dp

print(sum(dp) % MOD)
```このコードは、1 文字を削除することによって各レイヤーを明示的に構築します。 各レイヤーを並べ替えることで、辞書編集順が単純なインデックス順として表現されるようになります。 DP 配列は、各候補で終了する有効なウェイの数を追跡します。 

遷移ループは古典的な 2 ポインター スイープです。両方のレイヤーがソートされているため、前のレイヤーへのポインターを維持し、現在の候補ごとにすべての有効な寄与を蓄積します。 

よくある微妙な問題は、ここでの文字列比較が文字ごとの手動チェックではなく、完全な文字列に対する辞書編集であることを忘れていることです。 Python の文字列比較は必要な順序とすでに一致しているため、それを直接信頼します。 

もう 1 つのデリケートな点は、内側ループ内のプレフィックス合計を誤ってリセットしないことです。 ソートされた候補を移動するにつれて、単調に蓄積する必要があります。

## テストケース```python
import sys, io

def solve():
    import sys
    input = sys.stdin.readline
    MOD = 10**9 + 7

    def gen(s):
        return [s[:i] + s[i+1:] for i in range(len(s))]

    n = int(input())
    w = [input().strip() for _ in range(n)]

    prev = sorted(gen(w[0]))
    dp = [1] * len(prev)

    for i in range(1, n):
        cur = sorted(gen(w[i]))
        new = [0] * len(cur)

        j = 0
        pref = 0
        for k in range(len(cur)):
            while j < len(prev) and prev[j] <= cur[k]:
                pref = (pref + dp[j]) % MOD
                j += 1
            new[k] = pref

        prev, dp = cur, new

    print(sum(dp) % MOD)

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return sys.stdout.getvalue().strip() if solve() is None else ""

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、複数の削除により同一の文字列が生成される場合に発生します。 たとえば、次のような言葉で`aaa`、任意の文字を削除すると、`aa`, そのため、並べ替え後、候補レイヤーは重複に折りたたまれます。 DP では各出現が独立して処理され、プレフィックス合計が同一の文字列を正しく集計するため、アルゴリズムはこれを自然に処理します。 

別のエッジ ケースは、ある単語が次の単語のすべての候補よりも辞書編集的に小さい候補を生成する場合に発生します。 その場合、前の DP 合計全体が次のすべての状態に流れ込み、プレフィックス スイープは特別なケースなしで正しくキャプチャします。 

失敗するケースは、`<=`注文する。 これにより、有効な厳密に増加する遷移が誤って破棄されてしまいます。
