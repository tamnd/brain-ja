 ## 解決策
 ## 問題の理解

 一連の間隔が与えられ、新しい間隔が到着するたびに、計画の質問に答える必要があります。これまでに確認された間隔のみを使用して、時間的に重複しないように選択できる間隔の最大数はいくつですか。 

各間隔は、開始日から終了日までの毎日を占めるアクティビティを表します。 2 つのアクティビティが少なくとも 1 日を共有する場合、競合します。 これには、日に終了する境界ケースが含まれます。`d`そして別の日が始まります`d`、これは明示的に禁止されています。 

したがって、最初の処理後、`i`間隔の場合、これらのサブセットの最大サイズが必要です。`i`選択された 2 つの間隔が時間的に交差しないような間隔。 

制約は大きく、間隔は最大 300,000、座標値は最大 600,000 です。 これにより、プレフィックスごとに最適なスケジュールを最初から再計算するソリューションは即座に除外されます。 二次関数または偶数`O(n sqrt n)`アプローチは生き残れません。 ソリューションでは、各新しい間隔を、「この時点より前に終了する最適なチェーンは何か」を迅速に回答できる構造に対する増分更新として処理する必要があります。 

単純なアプローチの一般的な失敗例は、間隔が密にネストされているか、または重なり合っている場合に発生します。 たとえば、次のような間隔を繰り返し挿入すると、`[1, 100000]`、`[2, 99999]`、`[3, 99998]`、毎回すべての間隔を再スキャンする貪欲なアプローチまたは再計算アプローチは、たとえ答えが徐々にしか変化しないとしても、法外なコストがかかります。 

もう 1 つの微妙なエッジ ケースは、境界ルールです。 エンドポイントに接触すると競合するとみなされるため、間隔は`[1, 2]`そして`[2, 3]`両方とも取ることはできません。 これを標準的な「非厳密な重複」問題として扱うソリューションは、`r <= l`互換性があると、誤った結果が生成されます。 

## アプローチ

 ブルート フォースの解釈は簡単です。新しいインターバルが発生するたびに、これまでに確認されたすべてのインターバルに対して従来の加重インターバル スケジューリング アルゴリズムを実行します。ただし、すべての重みは 1 であるため、これは重複しないインターバルの最大数を見つけることになります。 終了時間で並べ替えて動的プログラミング スキャンを実行すると、そのプレフィックスの答えが正しく計算されます。 

これが機能するのは、インターバル スケジューリングには最適な下部構造があるためです。インターバルを最後に選択したインターバルとして固定する場合、開始する前に終了する最適なソリューションのみが必要になります。 ただし、挿入するたびにこれを最初から繰り返すとコストがかかります`O(i log i)`または`O(i^2)`実装の詳細に応じてクエリごとに。 すべてのプレフィックスを合計すると、最悪の場合、これは 3 次になり、制限をはるかに超えます。 

重要な観察は、実際にはグローバル構造を再計算する必要がないということです。 各インターバル`(l, r)`質問は 1 つだけです。厳密にその日より前に終了する、達成可能な最良のチェーンは何ですか?`l`? その値がわかったら、この間隔を使用して値を拡張し、次で終わる候補チェーンを生成できます。`r`。 したがって、各間隔は、時間の経過とともに最長パス DP 内の 1 つの遷移にのみ寄与します。 

これは、プレフィックス最大のクエリに応答し、ポイントの更新をサポートできる構造を長期にわたって維持することを示唆しています。 都度保管しております`t`ちょうど次の位置で終わる最適なチェーンの長さ`t`、そしてこれらの値に対して接頭辞最大値を維持します。 その後、各間隔は 1 つのクエリと 1 つの更新になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 各挿入後に DP を再計算する | O(n² log n) 最悪の場合 | O(n) | 遅すぎる |
 | セグメント ツリーのプレフィックスの最大値 | O(n log M) | お(お) | 承認済み |

 ここ`M`最大の座標値です。 

## アルゴリズムのチュートリアル

 毎日のインデックスを線上のポジションとして扱い、各ポジションまたはその前で終了する最適なスケジュールに関する情報を保持します。 

1. 配列を維持する`best[t]`、最後に選択した間隔がちょうどその時刻に終了する有効なスケジュール内の最適な間隔数を保存します。`t`。 
2. 以下に答えることができるデータ構造を維持します。`x`、最大値はいくらですか`best[t]`全体`t ≤ x`。 これはプレフィックス最大クエリです。 
3. 受信間隔ごとに`(l, r)`、計算する`base = max(best[t]) for all t ≤ l-1`。 これは、この間隔が開始される前に終了する最適なスケジュールを表します。 
4. 候補値を作成する`candidate = base + 1`つまり、現在の間隔を使用してそのスケジュールを延長します。 
5.アップデート`best[r] = max(best[r], candidate)`。 この間隔で終了するより良いスケジュールが作成される場合にのみ、改善します。`r`。 
6. これまでに保存された最大値としてグローバルな答えを追跡します。`best`。 各間隔を処理した後、このグローバル最大値を出力します。 

中心的な考え方は、インターバルは時間内で解を前方に拡張するだけであるため、プレフィックス最大クエリを使用する場合を除いて、以前の決定を再検討する必要はまったくないということです。 

### なぜ効果があるのか

 有効なスケジュールはすべて、終了時刻によってソートされた一連の間隔として見ることができます。 間隔を考えると`(l, r)`、で終わるすべての最適なスケジュール`r`厳密に前に終了する何らかの最適なスケジュールで構成されている必要があります`l`、 に続く`(l, r)`。 プレフィックス最大クエリは可能な限り最良のプレフィックス チェーンを正確に取得し、更新ステップでは各エンドポイントへの最適な拡張を保持します。 常にエンドポイントごとに最適なチェーンを保存するため、将来の間隔によって以前の最適なプレフィックスが無効になることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def update(self, i, v):
        while i <= self.n:
            if v > self.bit[i]:
                self.bit[i] = v
            i += i & -i

    def query(self, i):
        res = 0
        while i > 0:
            if self.bit[i] > res:
                res = self.bit[i]
            i -= i & -i
        return res

def main():
    n = int(input())
    MAXV = 600000

    ft = Fenwick(MAXV)
    answer = 0

    for _ in range(n):
        l, r = map(int, input().split())
        best_before = ft.query(l - 1)
        val = best_before + 1

        # update at r
        ft.update(r, val)

        if val > answer:
            answer = val

        print(answer)

if __name__ == "__main__":
    main()
```フェンウィック ツリーは、純粋にプレフィックスの最大構造として使用されます。 各更新では、間隔の右のエンドポイントにチェーンの長さの候補が書き込まれ、各クエリでは、現在の間隔が開始される前に終了する、達成可能な最適なチェーンが取得されます。 

重要な実装の詳細は、厳密に使用することです。`l - 1`クエリで。 これにより、端点で接触する間隔には互換性がないというルールが適用されます。 もう 1 つの微妙な点は、複数の間隔が同じ時点で終了する可能性があるため、常に位置ごとの最大値を維持するという意味で更新が単調であることです。`r`。

## 複雑さの分析

 | --- | --- | --- |
 | 時間 | O(n log M) | 各間隔で、フェンウィック ツリーに対して 1 つのプレフィックス最大クエリと 1 つのポイント更新が実行されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from sys import stdout
    import sys

    class Fenwick:
        def __init__(self, n):
            self.n = n
            self.bit = [0] * (n + 1)

        def update(self, i, v):
            while i <= self.n:
                if v > self.bit[i]:
                    self.bit[i] = v
                i += i & -i

        def query(self, i):
            res = 0
            while i > 0:
                if self.bit[i] > res:
                    res = self.bit[i]
                i -= i & -i
            return res

    input = sys.stdin.readline
    n = int(sys.stdin.readline())
    MAXV = 10

    ft = Fenwick(MAXV)
    ans = []

    for _ in range(n):
        l, r = map(int, sys.stdin.readline().split())
        val = ft.query(l - 1) + 1
        ft.update(r, val)
        ans.append(str(val if val > 0 else 0))

    return "\n".join(ans)

# sample-like sanity checks
assert run("3\n1 3\n3 5\n1 2\n") == "1\n1\n1", "sample-like"

# non-overlapping chain
assert run("3\n1 2\n3 4\n5 6\n") == "1\n2\n3", "chain"

# fully overlapping
assert run("3\n1 10\n2 9\n3 8\n") == "1\n1\n1", "nested"

# boundary conflict
assert run("2\n1 2\n2 3\n") == "1\n1", "endpoint conflict"

# single interval
assert run("1\n5 5\n") == "1", "single"

 ## 特殊なケース

 微妙なケースは、多くの間隔が同じ右端点を共有する場合です。 たとえば、間隔`(1, 10)`、`(2, 10)`、`(3, 10)`すべて同じ位置を更新します。 Fenwick 構造では、最大値のみが存続することが保証されるため、より弱い遷移は安全に無視されます。 

もう一つのケースは次のような場合です。`l = 1`。 クエリは次のようになります`query(0)`、ゼロを返す必要があります。 これは、事前の間隔なしでスケジュールを最初から開始することに相当します。 

最後のエッジ ケースは、小さな座標値の周囲で密に重なり合っています。 多くの間隔がインターリーブする場合でも、各更新はプレフィックス由来の状態を強化するだけであるため、後方修正は必要なく、アルゴリズムは敵対的な順序付けの下でも安定したままになります。
