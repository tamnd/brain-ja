 ## 解決策
 ## 問題の理解

 私たちは、プログラミング コンテストの問題の小さなセットを与えられ、各問題について、3 人のチームメイトがその課題を割り当てられた場合、それぞれがその問題を実装するのにどれくらいの時間がかかるかを知っています。 の値`-1`これは、特定のチームメイトがその問題をまったく実装できないことを意味します。 

チームには共有コンピューターが 1 台しかないため、並行して作業することはできません。 また、コンテストの所要時間は 300 分に固定されています。 各問題が選択された場合、その問題は 1 人のチームメイトに割り当てられ、時間の貢献は、その問題に対するそのチームメイトの対応する実装時間になります。 目標は、選択した各問題を解決できるチームメイトに割り当て、選択したすべての実装時間の合計が 300 を超えないように、できるだけ多くの個別の問題を選択することです。 

入力の構造は基本的に最大 14 個の項目のコレクションであり、各項目は 3 つの「ナップザック」にわたるコストの 3 倍であり、各項目は有効なコストの 1 つで取得するか、完全にスキップできます。 私たちは合計値を最大化することを求められるのではなく、単一のグローバルな時間予算の下で選択される項目の数を最大化することを求められます。 

制約`n ≤ 14`は重要な信号です。 最大 14 個の問題であれば、問題のサブセットを調査するあらゆるソリューションが実行可能です。`2^14 = 16384`これは、すべてのサブセットを明示的にチェックできるほど十分に小さいです。 項目ごとに 3 つの選択肢という追加の次元は、単純な決定ルールによって各サブセット内で解決できるため、その実現可能性は変わりません。 

唯一の微妙なエッジケースは、`-1`価値観。 素朴な解釈では治療を受ける可能性があります`-1`ゼロとして指定するか、実行可能性を誤って無視すると、不可能な割り当てが可能になります。 

たとえば、次のような問題があるとします。```
A -1 20 10
```その場合、それを最初のチームメイトに割り当てることは不可能です。 間違った貪欲なアプローチでは、依然として「最小時間を選択」しようとして、それを誤ってゼロとして扱い、実行可能なセットの過大カウントにつながる可能性があります。 正しい処理は、このオプションを完全に除外することです。 

もう 1 つのエッジ ケースは、3 つの値がすべて次のような場合です。`-1`。 その場合、他の問題がすべて小さい場合でも、その問題を選択することはできず、常に無視する必要があります。 

## アプローチ

 この問題を直接考える方法は、問題を選択して割り当てるあらゆる方法を試してみることです。 問題のサブセットごとに、選択した各問題をどのチームメイトが解決するかを決定し、合計時間を計算します。 合計が 300 以下の場合は、そのサブセットのサイズに応じて最良の回答が更新されます。 

この強引な見方は正しいですが、組み合わせ論が 2 層あります。 まず、`2^n`問題のサブセット。 サブセットごとに、選択された問題ごとに最大 3 つの割り当ての選択肢があるため、単純な展開は次のようになります。`O(3^n)`。 たとえ`n = 14`、最適化されたコードでは技術的にはまだ実現可能ですが、注意せずに実装すると、これはすでに境界線に達します。 ただし、すべての割り当てを独立して検討する必要はありません。 

重要な単純化は、固定された問題のサブセットの場合、最適な割り当ては自明であるということです。サブセット内の各問題について、3 人のチームメイト間の最小有効時間のみを気にするだけです。 各問題は、誰が解くかに関係なく、同じ共有時間リソースを消費するため、割り当ての選択に関して問題間に相互作用はありません。 これにより、2 番目の組み合わせ層が完全に削除されます。 

したがって、問題は、各項目が有効な実装時間の最小値として定義される単一の有効コストを持つ項目のサブセットを選択することに集約されます。 次に、合計コストが 300 を超えないアイテムの最大数を求めます。これは、少ないアイテム数でカーディナリティを最大化することを目的とする、古典的なナップザックの変形です。 

ここで必要なのは、すべてのサブセットを評価し、それらの合計コストとサイズを計算し、実現可能な最適なサイズを追跡することだけです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 完全な割り当ての列挙 | O(3^n) | O(n) | 遅すぎる |
 | 最小コスト削減によるサブセット列挙 | O(2^n · n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、各問題の 3 つの時間値を 1 つの有効コストに変換することで、各問題を前処理します。 このコストは有効な値の中で最も小さく、値は無視されます。`-1`エントリ。 3 つの値がすべて一致する場合、`-1`、問題を使用不可としてマークします。 

次に、ビットマスクを使用して問題のすべてのサブセットを列挙します。 各サブセットは、解決しようとしている問題の候補セットを表します。 

1. 問題ごとに、有効コストをチームメイトの利用可能な最小時間として計算します。 全部そうだったら`-1`、それを無限のコストとして扱い、決して選択できないようにします。 
2. すべてのマスクを反復処理します。`0`に`2^n - 1`。 各マスクは問題のサブセットをエンコードします。 
3. 特定のマスクについて、選択した問題の数と所要時間の合計という 2 つの値を計算します。 
4. 合計時間を計算しているときに、300 を超えた場合は、継続しても改善できないため、そのサブセットについては早期に停止します。 
5. 合計時間が 300 以内の場合は、これまでに発生した問題の最大数で回答を更新します。 

各サブセット内で早期に停止することは、実行可能性がすでに失われている場合に不要な合計を回避し、Python であってもソリューションの効率を維持できるため、重要です。 

### なぜ効果があるのか

 各問題について、その問題をチームメイトに割り当てることは、個人ごとの処理能力の制約がなく、グローバルな時間予算が 1 つだけであるため、他のすべての問題から独立しています。 これにより、割り当ての決定間の結合が排除されます。 したがって、各問題を実現可能な最小の割り当てコストに置き換えることで、すべてのサブセットの実現可能性が維持され、有効な割り当てのコストが増加することはありません。 最適な解はいずれも何らかのサブセットに対応する必要があり、そのサブセット内で各問題に対する最小コストの割り当てを選択することが常に最適です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    cost = []

    for _ in range(n):
        parts = input().split()
        name = parts[0]
        t = list(map(int, parts[1:]))

        best = 10**9
        for x in t:
            if x != -1:
                best = min(best, x)

        cost.append(best)

    ans = 0

    for mask in range(1 << n):
        total = 0
        cnt = 0

        for i in range(n):
            if mask & (1 << i):
                if cost[i] == 10**9:
                    total = 10**9
                    break
                total += cost[i]
                cnt += 1
                if total > 300:
                    break

        if total <= 300:
            ans = max(ans, cnt)

    print(ans)

if __name__ == "__main__":
    solve()
```前処理ステップでは、各問題を単一のスカラー コストに圧縮します。これは、探索スペースを削減するために不可欠です。 次に、ビットマスク ループはすべてのサブセットを直接探索します。 サブセット ループ内の早期終了条件により、実現不可能であることが確実になった後にコストを蓄積する時間を無駄にすることがなくなります。 

実装の微妙な詳細は、不可能な問題をゼロではなく非常に大きな数で表現しています。 ゼロを使​​用すると、誤って解決できない問題を無料で選択することができ、答えが人為的に水増しされてしまいます。 センチネルのようなものを使用する`10**9`このようなサブセットが自動的に予算を超えることを保証します。 

## 実用的な例

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(2^n · n) | 各サブセットは、最大 n 項目をスキャンすることによって評価されます。 
| スペース | O(n) | 問題ごとのコストといくつかのカウンターのみを保存します。 

と`n ≤ 14`、`2^n`は最大でも 16384 であり、14 を乗算しても数十万回をはるかに下回る演算が得られ、制限時間内に問題なく収まります。

 ## 特殊なケース

 エッジケースの 1 つは、すべての問題が少なくとも 1 人のチームメイトには不可能でも、別のチームメイトならまだ実現可能な場合です。 たとえば、問題は次のようになります。`-1 10 200`。 アルゴリズムはコストとして 10 を正しく受け取り、`-1`、問題が引き続き使用可能であることを確認します。 

もう 1 つのエッジケースは、問題がチームメイト全員にとって不可能である場合です。 その場合、そのコストは無限になり、それを含むサブセットは自動的に拒否されます。 列挙では引き続きそのようなサブセットが考慮されますが、センチネル コストが検出されるとすぐにフィルターで除外されます。 

最後の微妙なケースは、低コストの問題が多数存在し、最適な解決策を得るには、予算がちょうど飽和するまでそれらのほとんどすべてを解決する必要がある場合です。 ビットマスク列挙により、これらの組み合わせが明示的にチェックされることが保証され、早期停止は、有効な組み合わせをスキップするのではなく、実行不可能なサブセットの枝刈りにのみ影響します。
