 ## 解決策
 ## 問題の理解

 ゲームの各ラウンドでは、現在の資本の状態と裁判官が選んだ整数が表示されます。 その整数は 1 から現在の資金までの範囲から均一に抽出されるため、残高が大きくなると、そのラウンドで考えられる結果の範囲が即座に増加します。 

この値を確認した後、ラウンドに参加するかスキップするかを選択します。 関与すると、ラウンドは対称的なギャンブルのように動作します。同じ確率で、選択した金額を正確に失うか、その金額の 2 倍を獲得します。 スキップすると、お金を変更せずに次のラウンドに進むだけですが、今後のランダムな選択の順序は現在の残高に依存します。 

ゲームは、10000 を厳密に超える非常に大きな目標残高に達するか、資金がゼロになる場合を除き、固定ラウンド数でプレイされます。 可能な値の範囲は現在の資本に依存するため、すべての決定が将来のすべてのラウンドの配分を変更するため、相互作用により状況はより微妙になります。 

制約 T は小さく、1000 に固定されており、考えられるすべての結果シーケンスにわたって決定木を探索する試みは除外されます。 分岐がない場合でも、状態に依存するランダム性を使用して、正確に 1000 ラウンドを超える確率をシミュレートすることは不可能です。 主な問題点は、プロセスが対話的かつ適応的であるため、マネー状態に対する単純な確率的動的プログラミングは、連続的な状態爆発により失敗することです。 

よくある落とし穴は、期待値を使って逐一推論しようとすることです。 ラウンドをプレイすることによる期待利益は、結果が等しい確率で +b と -b となり、期待変化 +b/2 となるため、固定 b の場合は正になります。 ただし、これは b と現在のお金の間の依存関係を無視しており、さらに重要なことに分散を無視しています。繰り返しプレイすると、ゼロになり、プロセスが早期に終了する可能性があります。 もう 1 つの間違いは、早い段階でスキップしすぎて、後で積極的にプレイしすぎることです。これにより、サンプルされた b 値が大きくなり、負ける可能性が高くなる高い分散状態に達する可能性があります。 

## アプローチ

 ブルートフォース解釈では、プレーの考えられるすべての結果をシミュレートし、1000 ラウンドにわたって決定をスキップしようとします。 プレイ中にコイン投げの結果に応じて分岐するだけだとしても、各ラウンドでは、状態が変化しない状態で、プレイの場合は 2 プラス、スキップの場合は 1 という分岐係数が導入され、同時に将来のランダム値の分布も変更されます。 これは T ですぐに指数関数的になり、同一の金額値をマージして状態を切り捨てても役に立ちません。これは、金額は潜在的に非常に大きな値までの連続整数であり、遷移ごとに将来のすべてのラウンドのサンプリング空間が変化するためです。 

重要な構造的観察は、合理的な戦略が中間のランダム性にきめ細かく適応する必要がないようにゲームが設計されていることです。 この相互作用は、分配においては敵対的ですが、隠された情報においては敵対的ではありません。裁判官の選択 b は、現在の資金に対して常に均一であるため、唯一の意味のある制御変数は、現在の状態が十分に安全であるときに参加するかどうかです。 

重要な単純化は、ラウンドごとのギャンブルには、現在の資本と比較してプラスのドリフトと限界のある下値があることに気づくことです。 負けの境界 (お金 0) から遠く離れている場合、プレイは常にスキップよりも期待値が厳密に優れており、スキップは変動の影響を軽減するだけで、期待される成長は向上しません。 勝利条件はしきい値ベースであるため、最適な戦略は、すぐに崩壊するリスクがないときは常にポジティブな期待を利用することです。

これにより、意思決定の問題が決定論的なポリシーに集約されます。つまり、資金がプラスである間は常にプレイするということです。 その後、相互作用は、対称的な乗法加算更新の繰り返しによってのみ駆動される単一の確率的プロセスとなり、意思決定ロジックから対話的な側面が消えます。 

実装は簡単です。システムがゲームを終了するまで常に PLAY を出力します。

 ## アルゴリズムのチュートリアル

 私たちはジャッジからの各質問に反応しながらラウンドを順番に処理します。 

1. 現在のお金 m とサンプル値 b からなる現在のラウンド状態を読み取ります。 値 b は、プレイすることを選択した場合にのみ重要です。 
2. ゲームが終了しない限り、常に PLAY で応答することを決定します。 その理由は、プレイするとプラスの期待利益が得られ、スキップすると期待ドリフトが改善されることなくエクスポージャが減少するだけであるということです。 
3. インタラクションには厳密な同期が必要なため、決定を即座に出力してフラッシュします。 
4. 各応答後、次の状態を待ちます。 ジャッジが勝敗を宣告した場合は、直ちに終了します。 

### なぜ効果があるのか

 各プレイのプロセスでは +b/2 の変化が期待され、b は常に負ではなく、現在の資金によって制限されます。 スキップしても、失われた正のドリフトを補う形で将来の b 値の分布は変更されません。 1000 ラウンドを超えて、一貫してプラスのドリフト機会を獲得することは、統一サンプリング ルールを超えた決定に基づいて結果を調整する外部敵が存在しないため、それらを選択的に回避する戦略を支配します。 唯一の吸収失敗状態はゼロに達することであり、更新の構造により、プレイを回避しても、プレイによって追加される期待される利益と比較して、ゼロに達する確率を減らすことができないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    T = input().strip()
    if not T:
        return
    T = int(T)

    for _ in range(T):
        line = input().strip()
        if not line:
            return

        if line == "WIN" or line == "LOSE":
            return

        # line format: "ROUND m b"
        print("PLAY", flush=True)

if __name__ == "__main__":
    main()
```このソリューションは、単純に PLAY を出力することで、すべてのラウンド プロンプトに反応します。 唯一の微妙な点は、早期終了シグナルの処理です。対話の非同期を避けるために、実行を直ちに停止する必要があります。 審査員はリアルタイムの応答を期待しているため、各出力後のフラッシュは必須です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(T) | ラウンドごとに 1 つのコンスタントタイム判定 |
 | スペース | お(1) | 入力を読み取る以上の状態はありません |

 T = 1000 に制限されているため、実行時間はわずかです。 インタラクティブなオーバーヘッドが計算の大部分を占めますが、十分に制限内に収まっています。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    out = io.StringIO()
    sys.stdout = out

    T = sys.stdin.readline().strip()
    if not T:
        return ""
    T = int(T)

    for _ in range(T):
        line = sys.stdin.readline().strip()
        if not line:
            break
        if line in ("WIN", "LOSE"):
            break
        print("PLAY")

    return out.getvalue().strip()

# sample-like test
assert run("2\nROUND 100 10\nROUND 90 20\n") == "PLAY\nPLAY"

# immediate loss
assert run("1\nLOSE\n") == ""

# immediate win signal midstream
assert run("3\nROUND 100 10\nWIN\nROUND 200 20\n") == "PLAY"

# minimal rounds
assert run("1\nROUND 1 1\n") == "PLAY"
```| テスト入力 | 期待される出力 | 検証内容 |

 | 1ラウンドノーマル | 遊ぶ | 基本的なインタラクション |
 | すぐに負けます | 空 | 早期終了 |

 ## 特殊なケース

 エッジケースの 1 つは、何らかの決定が下される前に即時終了されることです。 T の後の最初の行が WIN または LOSE の場合、プログラムは何も出力しようとしてはいけません。 このソリューションは、出力を発行する前に受信行をチェックすることでこれに対処します。 

もう 1 つのケースは、勝利条件の後、ジャッジが早期に終了する部分入力です。 ループは WIN を検出するとすぐに終了し、プロトコルの非同期化を引き起こす余分な出力を防ぎます。 

最後のケースは、インタラクションのバッファリングが原因で空行または不正な行が発生する場合です。 実装では、空の読み取りが発生した場合にブレークすることでこれを防ぎ、ブロックしたり未定義の出力を生成したりしないようにします。
