 ## 解決策
 ## 問題の理解

 私たちには、餃子、ジュース、パンケーキの 3 つの独立した備品が与えられます。 各訪問者は、2 つの制約付きで、これら 3 つのアイテムのサブセットを受け取ります。 まず、訪問者は各アイテム タイプを複数受け取ることはできません。 第 2 に、2 人の訪問者がまったく同じサブセットを受け取ることはできません。 すべての訪問者は少なくとも 1 つのアイテムを受け取る必要があるため、空のセットは許可されません。 

したがって、レストランは、各サブセットが選択された各リソースから 1 ユニットを消費することを尊重しながら、3 つのリソースのセットの空ではない個別のサブセットを効果的に割り当てようとしています。 問題は、各項目の数が限られている場合に、個別のサブセットをいくつ実現できるかということです。 

各テスト ケースは小さく、カウント a、b、c は最大 10 で、テスト ケースは最大 500 です。 これにより、大規模な入力の反復に依存する指数関数的な構築が即座に除外されますが、ここでより重要なのは、パフォーマンスを心配することなく、3 つの項目の 7 つの可能なサブセット タイプすべてについて安全に推論できることを示唆していることです。 

重要な点は、リソースの使用においてサブセットが重複していることです。 たとえば、誰かに「餃子 + ジュース」を与えると、餃子 1 個とジュース 1 個を消費しますが、後で餃子が不足した場合に「餃子のみ」を与える可能性も排除されます。 利用可能な最大のサブセットを繰り返し形成するだけの単純な貪欲な戦略は、サブセットがどのように相互作用するかを考慮していないため、失敗する可能性があります。 

エッジ ケースの 1 つは、アイテムのタイプが 1 つだけ存在する場合です。 a = 5、b = 0、c = 0 の場合、有効なのは「団子」のみであるため、答えは 5 ではなく 1 になります。もう 1 つは、リソースが非常にアンバランスである場合です。たとえば、a = 10、b = 0、c = 0、または a = 10、b = 10、c = 0 です。2 番目のケースでは、「団子」、「ジュース」、および「団子 + ジュース」を形成して、訪問者を 3 人にすることができます。 単純に合計品目を数えてみると、20 食分の可能性があることが示唆されます。 項目数とサブセットの組み合わせ間のこの不一致が、中核的な問題です。 

## アプローチ

 強引なアイデアは、可能なすべての訪問者の割り当てを明示的に構築することです。 {A、B、C} の空ではない有効なサブセットは 7 つだけです。 訪問者にサブセットを再帰的に割り当て、毎回リソースを減分して、これまでに使用されたサブセットの一意性を確保することを試みることもできます。 これは状態空間が小さいため機能しますが、一般化すると非効率になります。制約が大きい場合、サブセットの組み合わせの数は訪問者の割り当て数に応じて指数関数的に増加し、k 人の訪問者の最悪のケースではおよそ 7^k のオーダーになります。 ここで k が小さいとしても、このアプローチは問題の実際の構造を隠すので不必要です。 

重要な観察は、サブセットの実際のアイデンティティはその数を超えて重要ではないということです。 項目が 3 つしかないため、完全な解決策は、各項目がいくつあるか、および空ではない可能性のある 7 つのサブセットにそれらをどのように分散するかによってのみ決まります。 各サブセットは個別にリソースを消費し、最適な戦略は供給制限によってのみ制約されます。 

これを確認するより直接的な方法は、サブセットの可能なマルチセットをすべて列挙することですが、さらに簡単なのは組み合わせ論的に推論することです。 項目が 3 つある場合、空でない個別のサブセットの最大数は 7 です。したがって、答えは 7 を超えることはできません。同時に、十分なリソースがある場合は、各サブセットに 1 人の訪問者を割り当てることで、7 つのサブセットすべてを実現できます。 したがって、問題は、これら 7 つのサブセットのうち、利用可能な数で実際にサポートできる数を決定することに帰着します。

各サブセットには既知の需要ベクトルがあり、リソースが過剰に使用されないように、できるだけ多くの個別のサブセットを選択したいと考えています。 宇宙は非常に小さいため、制限要因は常に総リソースか、可能なサブセットが 7 つしかないという事実のいずれかであると直接推論できます。 最適な結果は、適切に分割された合計と構造的制約の両方によって制限されることがわかりますが、この問題については、既知の単純化により、答えは次のようになります。$$\min(a + b + c, a + b + c - \max(0, \text{overlap reduction})) \rightarrow \text{simplifies to a direct greedy evaluation of subsets}$$より具体的には、各訪問者は少なくとも 1 つのアイテムを消費し、サブセットはすべて異なるため、最初にすべての単一アイテムの訪問者を貪欲に形成し、次にペア、次にトリプルを形成して、利用可能な数を決して超えないようにすることができます。 数値が非常に小さいため、すべてのサブセットの使用パターンを暗黙的にシミュレートできますが、最もクリーンな既知の解決策は、答えが次と等しいというものです。$$\min(a + b + c, 7)$$リソースが大きく偏っている場合は修正が行われます。これは、7 つのサブセットのそれぞれが最大 1 つ存在できることを観察することで自動的に処理され、十分なリソースがあれば、その制限までは常に実現可能です。 

したがって、問題は、実現できるサブセットの数を確認することに帰着します。これは、7 つの可能性の単純な貪欲な計算によって完全に決定されます。

 ## アルゴリズムのチュートリアル

 可用性の制約を考慮しながら、3 つのリソースの空ではない個別のサブセットの最大数を明示的に構築します。 

1. 各訪問者のタイプを、{A、B、C} の 7 つの可能なサブセットの 1 つとして扱います。 これらは、A、B、C、AB、AC、BC、ABCに対応します。 
2. 各サブセットに 1 人の訪問者を割り当てるようにします。ただし、そのサブセットに十分なリソースが存在する場合に限ります。 
3. 必要なすべてのリソースに少なくとも 1 つの残りのユニットがある場合、サブセットは実現可能です。 
4. より多くのリソースを消費し、将来の割り当てをブロックする可能性があるため、大きなサブセットを最初に優先する順序でサブセットを貪欲に選択します。 
5. サブセットを割り当てるたびに、対応するリソース数が減算され、答えが増分されます。 
6. サブセットが形成できなくなるまで続行します。 

サイズによる順序付けが機能する理由は、サブセットが大きくなると厳密に制限が厳しくなるからです。 割り当てが遅れると、必要なリソースがより小さなサブセットで消費され、将来の柔軟性が低下する可能性があります。 

### なぜ効果があるのか

 すべての訪問者は、3 つの要素の一意のサブセットに対応します。 このアルゴリズムは、リソース制約の下で個別の実行可能なサブセットの最大セットを構築します。 各サブセットは最大 1 回検討され、可能な場合にのみ受け入れられるため、リソース制約に違反することはありません。 より大きなサブセットに貪欲な優先順位を付けることで、リソースの多い構成が可能な限り長く保持され、小さなサブセットによる時期尚早の消費が防止されます。 サブセットは 7 つしかなく、それぞれが 1 回評価されるため、構築されたソリューションを超える最適な配置はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(a, b, c):
    ans = 0

    # try largest subsets first
    # ABC
    if a > 0 and b > 0 and c > 0:
        ans += 1
        a -= 1
        b -= 1
        c -= 1

    # AB, AC, BC
    if a > 0 and b > 0:
        ans += 1
        a -= 1
        b -= 1

    if a > 0 and c > 0:
        ans += 1
        a -= 1
        c -= 1

    if b > 0 and c > 0:
        ans += 1
        b -= 1
        c -= 1

    # A, B, C
    if a > 0:
        ans += 1
        a -= 1

    if b > 0:
        ans += 1
        b -= 1

    if c > 0:
        ans += 1
        c -= 1

    return ans

t = int(input())
out = []
for _ in range(t):
    a, b, c = map(int, input().split())
    out.append(str(solve_case(a, b, c)))

print("\n".join(out))
```この実装は、サブセット構築戦略を直接反映しています。 最初のブロックはトリプル サブセットを処理します。これは、3 つのリソースすべてを一度に消費するため、最も制限が厳しくなります。 次に、それぞれが 2 つのリソースを消費するすべてのペアごとのサブセットを処理します。 最後に、単一項目の訪問者を割り当てます。 この順序により、より大きなサブセットをブロックする共有リソースの早期枯渇が防止されます。 

各条件では、リソースを消費する前に可用性がチェックされ、すべてのステップで実現可能性が保証されます。 答えは、正常に形成されたサブセットごとに 1 つずつ累積されます。
