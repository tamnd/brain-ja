 ## 解決策
 ## 問題の理解

 数字だけで構成される単一の長い文字列が与えられます。 この文字列は、次の形式の正しい算術同一性に由来することが知られています。`a + b = c`、しかし記号`+`そして`=`が削除され、数字が連結されました。 

タスクは、この数字列を 3 つの連続する部分に分割し、それらを非負の整数として解釈することです。`a`、`b`、 そして`c`を挿入してください`+`そして`=`式が再び有効になります。 各部分は空であってはならず、正確に一致する場合を除き、先行ゼロで始めてはなりません`"0"`、そして等価性`a + b = c`正確に保持する必要があります。 

入力の長さは最大 10^6 にすることができ、分割位置の考えられるすべてのトリプレットを個別にテストしようとするアプローチは即座に除外されます。 分割点に対する単純なトリプル ループでは、加算の検証方法に応じて O(n^2) または O(n^3) の構成を検査しますが、これは許容される 2 秒をはるかに超えています。 

実際に重要な特殊なケースがいくつかあります。 先頭のゼロは 1 桁の数字のゼロ自体に対してのみ有効であるため、次のような分割`"01|2|3"`たとえ算術が数値的に機能するとしても、拒否する必要があります。 もう 1 つの微妙なケースは、キャリーが長いセグメントにわたって伝播する場合です。これは、単純な部分文字列から整数への変換が、注意せずに繰り返し実行されるとオーバーフローしたり、遅くなりすぎたりする可能性があるためです。 3 番目の問題は、有効な解が存在することが保証されていますが、必ずしも一意であるとは限らないため、正しい再構築は許容されるということです。 

## アプローチ

 ブルートフォース戦略は、分割ポイントを選択することから始まります。`a`、次に分割ポイントを選択します`b`、残りを次のように扱います`c`。 分割位置の各ペアについて、次のことを確認します。`a + b == c`。 

選択する方法は O(n^2) 通りあります`(i, j)`どこ`i`の終わりです`a`そして`j`の終わりです`b`。 各ペアについて、単純チェックにより部分文字列が整数に変換され、加算が実行されます。 換算がO(長さ)でも最悪の場合合計は3次になってしまいます。 n が 10^6 までの場合、O(n^2) ですらすでに不可能です。 

重要な点は、3 つの部分すべてについて任意の長さを試す必要がないということです。 方程式の構造により、強い制約が課せられます。`a`始まりと終わり、そしてどこで`b`開始すると、の値が`c`は、次の多倍整数の加算によって完全に決定されます。`a`そして`b`。 これにより、3 番目の分割点を完全に繰り返す必要がなくなります。 

すべてのスプリットを列挙するのではなく、ポジションのみを列挙します。`a`そして`b`、手動加算を使用して対応する数字列の合計を計算し、結果の数字シーケンスが元の文字列の接尾辞と一致するかどうかを確認します。 これにより、検索スペースが大幅に削減されます。`c`は長さが線形になるため、同じサフィックスを繰り返し解析することがなくなります。 

これを効率的に行うために、桁上げを使用して加算が桁ごとに行われるようにし、部分文字列を整数に変換せずに元の文字列と直接比較します。 これにより、試行ごとに操作が線形に保たれ、繰り返しのオーバーヘッドが回避されます。 

残りの改善点は枝刈りです。先行ゼロ制約により、大きなクラスの分割を即座にスキップできるようになり、不一致チェックは桁の比較中に早期に終了できます。

 ## アルゴリズムのチュートリアル

 1. スプリット位置を固定する`i`それが終わりを決める`a`、確保する`a = s[0:i]`有効です。 どれもスキップします`i`どこ`s[0] == '0'`そして`i > 1`先頭にゼロの数字が作成されてしまうためです。 
2. 有効なそれぞれについて`i`、分割位置を修正します`j`終わりに向けて`b`、 それで`b = s[i:j]`。 次の場合も同様に拒否します。`b`先頭にゼロが付いています。 
3. それぞれについて`(i, j)`ペアにする、解釈する`a`そして`b`を数字シーケンスとして計算し、キャリーを使用して右から左へ手動で加算して合計を計算します。 
4. 合計を計算する際、同時に生成された各桁を図中の対応する位置と比較します。`c = s[j:]`。 不一致が発生した場合、このペアは直ちに破棄されます。 
5. 加算が終了した後、キャリーが残っていないこと、およびサフィックス全体が正確に消費されたことを確認します。 両方が成立する場合、有効な分解が見つかったことになります。 

これで十分である理由は、一度`a`そして`b`固定されており、`c`は算術によって一意に決定されます。 私たちは探しているわけではありません`c`、検証中です。 

### なぜ効果があるのか

 アルゴリズムは、考えられるすべての有効な配置を列挙します。`a`そして`b`そして、ペアごとに、次の値に等しくなければならない一意の数値を構築します。`c`。 正しい解はそのようなペアの 1 つに正確に対応し、加算チェックにより、部分文字列を整数として解釈することなく、桁ごとに正確さが保証されます。 基数 10 の算術加算は決定論的で位置を保持するため、不一致がある場合は、隠れた桁上げ構成が等価性を修正できないことを意味します。 したがって、実行可能なすべての分割がテストされるため、アルゴリズムは無効な分解を受け入れることができず、有効な分解を見逃すこともできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

s = input().strip()
n = len(s)

def valid_num(l, r):
    if l < r and s[l] == '0':
        return False
    return True

def add_check(i, j):
    # a = s[0:i], b = s[i:j], c = s[j:]
    a = i - 1
    b = j - 1
    c = n - 1
    carry = 0

    while a >= 0 or b >= i:
        x = ord(s[a]) - 48 if a >= 0 else 0
        y = ord(s[b]) - 48 if b >= i else 0

        total = x + y + carry
        digit = total % 10
        carry = total // 10

        if c < j:
            return False
        if ord(s[c]) - 48 != digit:
            return False

        a -= 1
        b -= 1
        c -= 1

    if carry:
        if c < j or ord(s[c]) - 48 != carry:
            return False
        c -= 1

    return c == j - 1

for i in range(1, n):
    if not valid_num(0, i):
        continue
    for j in range(i + 1, n):
        if not valid_num(i, j):
            continue
        if add_check(i, j):
            print(s[:i] + "+" + s[i:j] + "=" + s[j:])
            sys.exit(0)
```実装では文字列を生の数字として扱い、部分文字列を整数に変換することを回避します。 機能`add_check`最下位桁から加算を実行し、位置を揃えます`a`、`b`、 そして`c`右側に。 異なる長さの正しい処理を保証するのは位置合わせだけであるため、これは不可欠です。 

微妙な詳細は、一方のオペランドが他方のオペランドより先に使い果たされる場合の境界処理です。 スライスの代わりに、インデックス範囲とガード条件を使用して、部分文字列の割り当ての繰り返しを回避します。 最後のキャリーチェックにより、次のようなケースが確実に発生します。`999 + 1 = 1000`正しく検証されています。
