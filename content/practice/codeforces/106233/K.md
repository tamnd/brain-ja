 ## 解決策
 ## 問題の理解

 このプロセスは、ボード上に配置された 1 つの整数から始まります。 現在ボード上にある任意の数字を繰り返し取得し、それを消去し、合計が消去された値に等しい 2 つの正の整数に置き換えることができます。 このような各分割には、結果として得られる 2 つの数値の積に等しいコストがかかります。 

時間が経つにつれて、繰り返しの分割から派生した数値のマルチセットが構築されます。 各クエリの目標は、初期値から開始してターゲットの数値コレクションを取得できるかどうか、取得できる場合はすべての分割の最小合計コストがいくらになるかを判断することです。 

重要な点は、最終的なボードに必要な数字を正確に含める必要がないことです。 必要なすべての値が最終的なマルチセットのどこかに出現するだけで十分です。 追加の数値は許可されており、必要に応じてさらに分割することもできます。 

各クエリは、必要な値を表す配列のセグメントと開始値 S を与えます。 S をそのセグメント内のすべての値を含むマルチセットに分解できるかどうかを判断する必要があります。分解できる場合は、すべての分割操作の最小コストを計算します。 

この制約は、非常に多くのクエリと配列サイズを意味するため、クエリごとに何かを個別に再計算するソリューションは遅すぎます。 分割の単純なシミュレーションでは、分割するたびにノードの数が増加し、各ノードは再度分割される可能性があるため、指数関数的に増加します。 

隠れた構造は、分割が任意の分岐ではなく、常に合計を保持し、コスト関数が二分分解ツリー上で予測どおりに動作するということです。 

不注意なアプローチにより、すぐに失敗するケースがいくつか発生します。 

S が必要な値の合計より小さい場合、たとえば S = 5 で、必要な数が 2、3、4 である場合、分割は許可されても総和を増やす方法がないため、答えは不可能になります。 

S が合計に等しいが、分割の構造が無視される場合、実現可能性は常に維持されると仮定するかもしれません。 たとえば、S = 7 で必要な値 [2, 2, 3] は機能しますが、[3, 3, 3] は合計が 9 であっても機能しません。S が不十分であるためです。 

もう 1 つの微妙なケースはコスト行動です。 S = 4 の場合、(1,3) への分割のコストは 3 ですが、(2,2) への分割のコストは 4 です。複数のターゲット値を構築する場合、「バランスのとれた分割」の貪欲な選択は全体的に最適ではありません。中間値はさらに分割する必要がある可能性があるためです。 

## アプローチ

 直接的なブルート フォース アプローチでは、S をルートとするバイナリ ツリーとしてプロセスをモデル化します。各ノードは現在の数値を表し、ノード y を a と b に拡張すると、コスト a·b が追加されます。 必要な値がすべてマルチセットに存在するまで、考えられるすべての分割を再帰的に試行します。 

これは正しいです。すべての有効な操作シーケンスは、葉が最終的な数値である 2 分木に正確に対応するからです。 ただし、可能な木の数は爆発的に増加します。 中程度の S の場合でも、各値 y には O(y) 個の可能な分割があり、再帰は大きく分岐します。 これにより時間が急激に増加し、大規模な S クエリや多数のクエリには使用できなくなります。 

重要な観察は、数値 y を a と b に分割するコストは正確に a・b = (a+b)^2/4 - (a^2 + b^2)/4 構造であるということですが、より重要なのは、S をリーフに完全に分解する際の総コストは、分割の順序ではなく、最終的なリーフのペアごとの相互作用のみに依存することです。 

S をリーフ x1、x2、...、xk に展開すると、総コストは xi・xj の順序のないリーフのペアすべての合計になります。 これは、分割によってクロス項の寄与がマージされるという恒等式を繰り返し適用することで得られます。 これにより、問題は、固定合計 S の下でペアごとの相互作用コストを最小限に抑えながら、必要なすべての xi とおそらく追加の正の整数を含むリーフのマルチセットを選択することに変換されます。

追加の番号は無料ではありませんが、S の「ギャップを埋める」ために使用できます。最適な戦略は、最終的に、不足している合計をサイズ S - sum(required) の追加リーフとして扱い、選択したセグメントのプレフィックス合計の関数としてコストを計算することになります。 

これにより、各クエリは、セグメント全体にわたる 2 つの量 (値の合計とペアごとの積の合計) を計算することになります。これらは、プレフィックスの前処理で維持できます。

 ## アルゴリズムのチュートリアル

 1. 必要な値の配列のプレフィックス合計を事前計算します。 これにより、あらゆるクエリ範囲のセグメント合計を高速に計算できます。 
2. セグメント上のペアごとの交互作用項の計算を可能にするプレフィックス二乗和または同等の寄与を事前計算します。 これが必要なのは、コストが選択されたすべての値間の相互作用に依存するためです。 
3. クエリ (l、r、S) の場合、セグメントの必要な合計 T を計算します。 
4. T > S の場合は、分割しても総和を増やすことができないため、すぐに -1 を返します。したがって、実現可能性はありません。 
5. 残りの値 L = S - T を定義します。これは、必要なリーフを割り当てた後にどれだけの「余分な質量」が残るかを表します。 
6. ペアごとの展開から導出された公式を使用して、必要な要素によって寄与されるコストを計算します。すべてのペアの合計 xi・xj に、追加のリーフとして扱われる場合は L との相互作用を加えます。 
7. 計算されたコストを返します。 

自明ではないステップは、分割プロセス全体を最終リーフの閉じた形式の式に置き換えることです。 すべての分割は合計を保持するため、有効なプロセスは合計が S である最終的なマルチセットに対応します。各分割は、ツリー全体にわたって相互作用コストを子全体に分散するため、コストはリーフ間の外積として正確に蓄積されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# We assume preprocessing arrays exist after reading input:
# a is the array of values
# prefix sums and prefix square sums are computed

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    pref = [0] * (n + 1)
    pref2 = [0] * (n + 1)

    for i in range(n):
        pref[i + 1] = pref[i] + a[i]
        pref2[i + 1] = pref2[i] + a[i] * a[i]

    out = []

    for _ in range(q):
        l, r, S = map(int, input().split())
        l -= 1

        sum_seg = pref[r] - pref[l]

        if sum_seg > S:
            out.append("-1")
            continue

        # leftover mass
        L = S - sum_seg

        # total pairwise contribution among segment elements
        # using identity: sum_{i<j} a_i a_j = (sum^2 - sumsq)/2
        sumsq = pref2[r] - pref2[l]
        pair_cost = (sum_seg * sum_seg - sumsq) // 2

        # interaction with leftover treated as an extra leaf
        extra_cost = L * sum_seg

        out.append(str(pair_cost + extra_cost))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このコードは、コントリビューションを 2 つの独立した部分に分割することに依存しています。 1 つ目は、必須要素間の内部相互作用で、接頭辞の合計と接頭辞の二乗から導出されるペアごとの合計の標準恒等式を使用して計算されます。 2 つ目は、残りの値 L とすべての必須要素の間の相互作用です。これは、各必須要素が L・xi に寄与するため線形です。 

最もデリケートな部分は、葉の表現に切り替えた後は、分割プロセスのさらなる構造は重要ではないことを認識することです。 ここで、多くの誤った解決策がプロセスを過度に複雑にするか、貪欲な分割を試みますが、ローカルなバランスの選択では全体的な最適性が維持されないために失敗します。

 ## 特殊なケース

 セグメントの合計がすでに S を超えている場合、重大なエッジ ケースが発生します。この状況では、分割によって合計合計が正確に保持されるため、一連の分割で不足分を修正できません。 このアルゴリズムは、コスト計算の前にプレフィックス合計の比較を通じてこれを直ちに処理します。 

S がセグメントの合計と等しい場合、別のエッジ ケースが発生します。 ここで、L はゼロになり、残った相互作用項はすべて消えます。 このソリューションは、セグメント要素間の純粋なペアごとのコストを正確に削減し、コストの人為的なインフレを回避します。 

最後の微妙なケースは、セグメントに単一の要素がある場合です。 ペアごとの項はゼロであり、答えは単純にその要素の L 倍となり、すべての余分な質量が 1 つの葉と相互作用する必要があることを反映しています。
