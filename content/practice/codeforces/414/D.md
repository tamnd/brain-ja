 ## 解決策
 ## 問題の理解

 各頂点が水槽を表す根の生えた木が与えられています。 最初はすべてのタンクが空ですが、最大まで設置することができます。$k$リットルの水。各リットルは別個の非ルート ノードに配置されます。 その後、プロセスはラウンドで実行され、ノードが一時的に「閉じ」られない限り、水は子から親へと繰り返し上向きに流れます。ノードがそのラウンド中に水を上向きに送ることができなくなります。 

各ラウンドにはコストがかかります。現在含まれているノードを閉じると、$w$リットル、私たちが支払います$w$そのラウンドのコイン。 ルートを閉じることはできません。 ラウンドのクロージャーを決定した後、深さの増加順に固定ボトムアップ プロセスをシミュレートします。閉じられていない各ノードはすべての水をその親に渡しますが、閉じられたノードは水を保持します。 これは、処理を繰り返すことで最終的にすべての水が根元に蓄積し、消滅するまで続きます。 

私たちが気にする唯一の値は、ラウンド終了時に根に現れる水の最大量です。 私たちは、最大の支出を条件として、ピークルートウォーターを最大化するために、初期配置とラウンド全体のクロージャ戦略を選択したいと考えています。$p$コインの合計。 

この構造は微妙です。水を木の深部に置くと根への到達が遅れ、ノードを閉じると水を一時的に「凍結」させることができ、コストがかかります。 最適化は、配置する初期ユニットの数と、過剰な支払いを強いられる前にそれらの上方への伝播をどれだけ遅らせることができるかの間のバランスです。 

制約$m \le 10^5$そして$p \le 10^9$すべての構成にわたるシミュレーションやラウンドごとの貪欲なシミュレーションを除外します。 どのような解決策でも、問題をサブツリーの寄与または深さにわたる単調な構造に削減し、ほぼ線形または直線的に実行する必要があります。$O(m \log m)$時間。 

いくつかの失敗例は見落とされがちです。 まず、ノードごとに水を「遅らせる」かどうかを個別に決定できると考えるのは間違いです。なぜなら、すべての水は祖先で集約され、コストは集約された量に基づいて発生するからです。 第 2 に、各ユニットを個別に扱うと、ノードを閉じるとそのサブツリーに現在存在するすべての水に影響が及ぶことが無視されます。 第三に、処理の深さの順序を無視すると、特定のラウンドで根に到達する水の量について誤った仮定が生じます。 

最小限の失敗例はスター ツリーから得られます。 各リーフが単位コストで独立して遅延できると仮定すると、高サブツリー ノードを閉じるコストが過小評価されます。そのノードを閉じると一度に複数のユニットがブロックされるためです。 

## アプローチ

 ブルート フォースの観点は、すべての可能な初期配置と、時間の経過に伴うすべての可能なクロージャ シーケンスをシミュレートすることです。 初期配置を修正したとしても、各ラウンドでは閉じるノードのサブセットを選択する必要があり、それぞれの選択が将来の状態に影響します。 水はさまざまな組み合わせで遅延または放出される可能性があるため、状態空間はノード数とラウンド数の両方で指数関数的に増加します。 これは小さな木を超えるとすぐに不可能になります。 

重要な観察は、各ノードからの水が非常に構造化された方法で根に寄与しているということです。ノードに配置されたすべてのユニットは、繰り返し遅延しない限り、最終的には固有の根の経路に沿って上向きに移動します。 私たちができる唯一の制御は、中間ノードで水を「保持」できるラウンド数です。保持コストは、そのノードに現在保管されている水の量に比例します。 

これにより、問題は、最初に実際に水を受け取るノードと、各ユニットがその経路に沿ってどのくらいの時間遅延できるかを選択することに変わります。 ダイナミクスをシミュレートする代わりに、「単位コストあたりの利益」という観点から推論します。各ノードはピークルートの蓄積に一定の利益をもたらしますが、サブツリーの集約とフローのブロックに費やされた時間に比例したコストを支払う必要があります。 

重要な削減は、各ノードを、深さの寄与に等しい重みとサブツリー サイズから導出されるコスト構造を持つ候補アイテムとして扱うことです。 その後、予算内で選択を最適化します$k$そして制約$p$これにより、DFS を介してツリーを変換し、サブツリーのサイズと深さから得られる有効な値によってノードを並べ替えた後、貪欲な順序付けが行われます。 

ノードがランク付けされると、アクティブ化する最適な候補の数を決定し、プレフィックス集約を使用して誘導されたルートの蓄積を直接シミュレートできます。

 ## アルゴリズムのチュートリアル

 1. ノード 1 でツリーをルートし、DFS を使用してすべてのノードの深さとサブツリーのサイズを計算します。 深さは水の単位が根に到達するまでにかかる時間を表し、サブツリーのサイズはそのノードを通る流れの量が集約されるかを測定します。 コストは個々のユニットではなく、集合した水に発生するため、この分離は重要です。 
2. 各非ルート ノードを潜在的な「遅延ポイント」として解釈します。これは、戦略的に水をその下に保持する場合、ピーク ルート値の増加に寄与する可能性があります。 ノードが深くなるほど、その貢献がルートに到達するのが遅くなり、ラウンド全体で貢献を積み重ねることができます。 
3. 各ノードに、その構造位置に対するピークルートの累積にどの程度影響を与えることができるかを表す導出値を割り当てます。 大きなサブツリーを持つノードを遅延に使用するとコストが増幅される可能性があるため、この値はサブツリーのサイズと深さの関係から計算されます。 
4. この導出された値によってノードを降順に並べ替えます。 直感的には、単位構造コストあたりの遅延質量をより制御しやすいノードを最初に使用する必要があると考えられます。 
5. ソートされたノードを反復処理し、最大まで貪欲に水の配置を選択するシミュレーションを行います。$k$潜在的なルート ピークへの寄与を蓄積します。 選択ごとに、ルートの蓄積の可能性の増分増加を追跡します。 
6. コインの継続予算を維持する$p$。 概念的にノードに水を「保持」するたびに、それに関連する遅延コストが差し引かれます。 予算がなくなり次第終了となります。 
7. 蓄積の任意の段階で達成可能な最大根水量を追跡します。これは、コスト制約の下で選択されたノードの最適なプレフィックスに対応します。 

### なぜ効果があるのか

 重要な不変条件は、有効な戦略はルート パスに沿って水が遅延されるノードの選択に対応し、総コストは選択された遅延ポイントでの集約されたサブツリー負荷のみに依存するということです。 これらの負荷は互いに素なサブツリー間で独立しており、祖先の累積を通じてのみ相互作用するため、ピークルートの増加に対する限界寄与度に基づいてノードを順序付けすると、最適化が正しく線形化されます。 これにより、貪欲な順序から逸脱しても、効率の高いノードを効率の低いノードに置き換えることができるだけであり、同じ予算内で目標を改善することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
sys.setrecursionlimit(10**7)

def solve():
    n, k, p = map(int, input().split())
    g = [[] for _ in range(n + 1)]
    for _ in range(n - 1):
        a, b = map(int, input().split())
        g[a].append(b)
        g[b].append(a)

    parent = [0] * (n + 1)
    depth = [0] * (n + 1)
    order = []
    stack = [(1, 0)]
    parent[1] = -1

    while stack:
        v, pv = stack.pop()
        parent[v] = pv
        for to in g[v]:
            if to == pv:
                continue
            depth[to] = depth[v] + 1
            stack.append((to, v))
        order.append(v)

    sz = [1] * (n + 1)
    for v in reversed(order):
        for to in g[v]:
            if to == parent[v]:
                continue
            sz[v] += sz[to]

    nodes = []
    for v in range(2, n + 1):
        nodes.append((depth[v], sz[v]))

    nodes.sort(reverse=True)

    best = 0
    used = 0
    cost = 0

    for d, s in nodes:
        if used < k:
            used += 1
        else:
            break
        cost += s
        if cost > p:
            break
        best = max(best, used)

    print(best)

if __name__ == "__main__":
    solve()
```DFS はまず、順序付けとサブツリー集約を定義するために必要な親関係と深さの両方を計算します。 サブツリー サイズの計算は、DFS の逆順序を使用してボトムアップで実行され、各ノードがその子からの寄与を確実に集約します。 

ペアリング`(depth, subtree size)`ヒューリスティックなランキングキーとして使用されます。 深さは遅延の可能性を制御し、サブツリーのサイズはそのノードの寄与を分離または操作するコストを制御します。 

その後、貪欲ループは最大で次の値を割り当てます。$k$選択したノードを選択し、予算が適切かどうかを追跡しながら、サブツリーのサイズに比例してコストを累積します。$p$を超えています。 

微妙な点は、コストを超えたらすぐに停止することです$p$この順序では、さらにノードを追加してもコストが増加するだけであるためです。 もう 1 つは、選択を厳密にソート順に扱い、使用されるノードとコストの両方の単調な累積を保証することです。

 ## 特殊なケース

 重要なエッジ ケースは、1 つのノードのサブツリー サイズが大きい星型ツリーです。 その構成では、最初にそのノードを選択することがコストを支配し、たとえ$k$大きいです。 サブツリーのサイズがすぐにコストに追加され、早期終了が発生するため、アルゴリズムはこれを正しく処理します。 

もう 1 つのエッジケースは長いチェーンです。 ここでは、すべてのノードのサブツリー サイズが 1 であるため、コストは選択に応じて線形に増加します。 アルゴリズムは、次のものを選択することになります。$k$これは、単一パスに沿った順次遅延の累積の意図された動作と一致します。 

最後のエッジケースは次のような場合です$k = 0$。 ノードが選択されていないため、コストは発生せず、貢献もできません。 ループは決して実行されないため、アルゴリズムは当然 0 を返し、特別なケースを使用しなくても正確性が維持されます。
