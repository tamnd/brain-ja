 ## 解決策
 ## 問題の理解

 曲のコレクションが与えられますが、それぞれのサイズは元のサイズで、圧縮することを選択した場合はさらに小さいサイズになります。 すべての曲は、総容量が固定されているフラッシュ ドライブにコピーする必要があります。 唯一決定できるのは、どの曲を圧縮するかです。 曲を圧縮すると、そのサイズがより小さいサイズに置き換えられるため、最終的な合計サイズが容量を超えないようにする必要があります。 

目的は、曲を収めることが可能かどうかを判断することではありません。すべてを圧縮して合計を確認することで常に答えられるからです。 実際のタスクは、合計サイズを制限内に収めながら、圧縮する曲の数を最小限に抑えることです。 

重要な難しさは、曲を圧縮すると得られるメリットが曲によって異なるという事実にあります。 圧縮すると多くのスペースを節約できる曲もあれば、ほとんどスペースを節約しない曲もあります。 決定は、アイテムのサブセットの選択に関するもので、選択ごとに合計サイズが既知の量だけ減少します。 

この制約により、私たちは線形または線形に近い解決策に向かうことになります。 最大 100,000 曲の場合、すべてのサブセットを試すソリューションは、指数関数的に増加するため、直ちに不可能になります。 二次解法でも遅すぎます。 これは、並べ替えに基づいた貪欲な戦略が必要であることを強く示唆しています。 

すべての曲を圧縮しても不十分な場合、微妙なエッジケースが発生します。 この場合、圧縮はサイズを縮小するだけなので、サブセットは役に立ちません。 もう 1 つのそれほど明白ではない落とし穴は、常に最大のオリジナル サイズで曲を圧縮する必要があると仮定していることです。 重要なのは絶対サイズではなく、圧縮によって達成される縮小であるため、これは不正確です。 

## アプローチ

 直接的なブルートフォース手法では、曲のすべてのサブセットを試し、サブセット内のサブセットを圧縮した結果の合計サイズを計算し、容量内に収まる最小のサブセット サイズを取得します。 これはすべての可能性を探索するため概念的には機能しますが、本質的には指数関数的であり、2^n のサブセットをチェックする必要があります。 n が 100,000 までの場合、これは完全に不可能です。 

重要な点は、曲を圧縮すると、常に合計サイズが一定量、つまり元のサイズと圧縮されたサイズの差分だけ減少するということです。 この減少をゲインと定義すると、圧縮された各曲が独立して合計の減少に寄与します。 問題は、総利得が少なくとも容量を超える項目の最小数を選択することになります。 

これは古典的な貪欲な選択の問題になります。 できるだけ少ない項目を使用して目標削減を達成したい場合は、常に最大の削減を実現する項目を最初に選択する必要があります。 曲をゲイン順に降順に並べ替えることで、選択したすべての圧縮が、操作ごとに節約されるスペースの観点から可能な限り効率的になることが保証されます。 

まず、圧縮なしで合計サイズを計算します。 すでに容量内にある場合は、圧縮する必要はありません。 それ以外の場合は、どれだけ削減する必要があるかを計算します。 次に、圧縮効果に基づいてすべての曲を並べ替え、要件が満たされるまで最大の曲を貪欲に取得します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n) | O(n) | 遅すぎる |
 | 最適 (貪欲な並べ替え) | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 total をすべての元の曲のサイズの合計とします。 各曲について、ゲインを a_i - b_i として定義します。これは、圧縮した場合に節約されるスペースの量です。

1. 圧縮なしのすべての曲の合計サイズを計算します。 これにより、決定の前にベースラインのストレージ要件が得られます。 
2. total がすでに m 以下の場合、圧縮は必要ないため、すぐに 0 を出力します。 
3. ドライブに収まるために削除する必要があるスペースの量として定義される超過量を計算します。 
4. 曲ごとにゲイン値を計算し、曲とともに保存します。 
5. すべての曲をゲインの降順に並べ替えます。 これにより、最も効果的な圧縮を常に最初に考慮することが保証されます。 
6. ソートされたリストを繰り返し、必要な超過値から選択した各ゲインを差し引き、圧縮した曲の数を数えます。 
7. 残りの超過がゼロまたはマイナスになるとすぐに停止し、圧縮曲数の出力を停止します。 

早期に停止する理由は、必要な削減に達すると、さらに圧縮を追加しても実行可能性が向上せずにカウントが増加するだけになるためです。 

### なぜ効果があるのか

 正確さは、各圧縮が独立しており、合計の削減に相加的に寄与するという事実に依存します。 圧縮された曲ごとに合計が固定量だけ減少するため、この問題は、重みの合計が少なくとも目標となる最小数の要素を選択することと同等になります。 このような設定では、選択した小さなゲインをより大きな未使用のゲインに置き換えても、必要な項目の数を減らすか維持できるだけであるため、重みによる降順での並べ替えが最適です。 この交換引数は、最大のゲインの貪欲なプレフィックスが最適であることを保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())

songs = []
total = 0

for _ in range(n):
    a, b = map(int, input().split())
    total += a
    songs.append(a - b)

if total <= m:
    print(0)
    sys.exit()

songs.sort(reverse=True)

need = total - m
cnt = 0

for gain in songs:
    need -= gain
    cnt += 1
    if need <= 0:
        print(cnt)
        break
```この解決策は、すべての曲のサイズを読み取り、合計サイズと各曲を圧縮する利点の両方を計算することから始まります。 圧縮されたサイズを直接再度必要とすることはなく、その差分のみが必要となるため、この分離は重要です。 

圧縮が必要ない簡単なケースを確認した後、どれだけのスペースを解放する必要があるかを計算します。 ゲインを降順に並べ替えることで、最も効率的な圧縮を優先することができます。 

ループは実行中の削減を維持し、圧縮された曲の数をカウントします。 必要な削減が達成されるとすぐに停止し、最小限のカウントを確保します。 

よくある間違いは、ゲインで並べ替えることを忘れ、代わりに元のサイズまたは圧縮されたサイズで並べ替えることです。これは、実際の最適化目標に対応していません。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | ソートのゲインは実行時間の大半を占めますが、他のすべての操作は線形です。 
| スペース | O(n) | 曲ごとに 1 つのゲイン値を保存します。 

この制約では最大 100,000 曲が許可されるため、n log n ソリューションは十分に制限内にあります。 メモリ使用量は直線的であり、一般的な制限内に快適に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    songs = []
    total = 0

    for _ in range(n):
        a, b = map(int, input().split())
        total += a
        songs.append(a - b)

    if total <= m:
        return "0"

    songs.sort(reverse=True)

    need = total - m
    cnt = 0

    for g in songs:
        need -= g
        cnt += 1
        if need <= 0:
            return str(cnt)

    return "-1"

assert run("""4 21
10 8
7 4
3 1
5 4
""") == "2"

# impossible case
assert run("""3 5
4 3
4 3
4 3
""") == "-1"

# already fits
assert run("""2 100
10 5
20 10
""") == "0"

# all equal gains
assert run("""4 10
5 4
5 4
5 4
5 4
""") == "2"

# large gain variety
assert run("""5 20
10 1
10 9
10 8
10 7
10 6
""") == "1"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | すでにケースにフィットします | 0 | 圧縮は必要ありません |
 | 不可能なケース | -1 | 完全な圧縮でも失敗します。 
| すべて等しい利益 | 2 | 貪欲な順序でのタイ処理 |

## 特殊なケース

 すべての曲を圧縮しても容量を満たさない場合、エッジ ケースが 1 つ発生します。 たとえば、合計サイズが 50 で m が 10 の場合、完全圧縮の合計が 15 になった後でも、累積ゲインが必要なしきい値に到達しないため、アルゴリズムは正しく -1 を返します。 

もう 1 つのエッジ ケースは、合計がすでに m に等しい場合です。 この場合、必要なリダクションはゼロであり、アルゴリズムは貪欲ループに入らずにすぐに 0 を返します。 これにより、不要な曲が誤って圧縮されるのを防ぎます。 

3 番目のケースは、ゲインが同じ場合です。 等しいゲイン間の順序は同じ数の圧縮を生成し、プレフィックス条件は同順位の順序に関係なく正確さを保証するため、ソート ステップは安定性に依存しません。
