 ## 解決策
 ## 問題の理解

 小文字の上に変更可能な文字列が与えられます。 私たちが追跡するコア量は、文字の固定順序ペア、特に最初の文字が次のペアに対して定義されます。`'e'`そして2つ目は`'f'`。 何かが起こるたびに、`'e'`位置にある`i`そして`'f'`位置にある`j`と`i < j`、距離を加算します`j - i`。 タスクは、最初の文字列と、文字列の 1 つの位置が永続的に上書きされる各ポイントの更新後のこの合計を計算することです。 

別の言い方をすると、すべての有効なペアは、2 つの位置の距離に等しい重みを与えます。 文字列は一度に 1 文字ずつ変更され、変更のたびに更新された重み付きペアの合計が必要になります。 

制約は次のとおりです`5 × 10^5`長さと更新の両方について、変更のたびに合計を最初から再計算する必要がありません。 クエリごとに文字列全体をスキャンするソリューションでは、約`O(nm)`実行可能性をはるかに超えた操作です。 平`O(n log n)`ここでは実際には更新ごとに遅すぎます。 

重要な構造は、関係するペアのみが含まれることです。`'e'`そして`'f'`案件。 更新が発生したときにこれら 2 つの文字に移行したり、これらの 2 文字から移行したりする可能性がある場合を除き、アルファベットの他のすべては無関係です。 

更新によってキャラクターが反転したり反転したりするときに、微妙なエッジケースが発生します。`'e'`または`'f'`。 たとえば、`'e'`に`'f'`は、その位置に関係する寄与を削除するだけでなく、すべてのペアでの役割を逆転させるため、左右の相互作用の両方を調整する必要があります。 

もう 1 つの注意が必要な状況は、複数の場合です。`'e'`そして`'f'`インターリーブされています。 ローカル近傍のみを更新しようとする単純なアプローチは、各位置が両側の反対タイプの文字すべてと相互作用するため失敗します。 

## アプローチ

 ブルートフォースアプローチは簡単です。 クエリごとに、文字列の状態を再構築し、すべてのペアを反復して合計を計算します。`(i, j)`と`i < j`かどうかを確認します`s[i] = 'e'`そして`s[j] = 'f'`、そして追加`j - i`。 これは定義を直接実装しているため、これは正しいです。 

ただし、各計算にはコストがかかります`O(n)`、そして、あります`m`更新されるため、全体の複雑さはさらに大きくなります`O(nm)`、最悪の場合、`2.5 × 10^{11}`操作。 これはあまり受け入れられません。 

最適化するには、式を代数的に拡張します。 固定の場合`'e'`位置にある`i`、その貢献度は次の合計です。`(j - i)`全体`'f'`その右側に位置します。 これは 2 つの部分に分かれます。`'f'`ポジションマイナス`i`カウントされる回数にそれらのインデックスの合計を加えたものです。 これは、世界的な統計を維持することを示唆しています。`'f'`位置を確認し、サフィックス情報を効率的にクエリできるようになります。 

重要なアイデアは、2 つのフェンウィック ツリー (またはセグメント ツリー) を維持することです。1 つは、`'e'`そして`'f'`、もう 1 つはそれらのインデックスの合計を追跡します。 これにより、対数時間で寄与度を計算できるようになります。 文字が変更されると、その古い寄与が削除され、プレフィックス/サフィックス クエリを使用して既存のすべての反対文字に対する効果を再計算することにより、新しい寄与が追加されます。 

これにより、各更新が次のように削減されます。`O(log n)`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | O(n) | 遅すぎる |
 | フェンウィックベースのアップデート | O((n + m) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 2 つの関連するキャラクターごとに 2 つのフェンウィック ツリーを維持します`'e'`そして`'f'`。 1 つのツリーには、その位置に存在するオカレンスの数が格納され、もう 1 つはそれらのインデックスの合計が格納されます。 

また、現在の拠出総額も維持します。 

1. カウントとインデックス合計のフェンウィック構造体を初期化します。`'e'`そして`'f'`初期文字列に基づいて。 ポジションごとに、`'e'`または`'f'`に応じて挿入します。 
2. 位置を反復し、プレフィックス クエリを使用して、最初の答えを計算します。 それぞれについて`'e'`位置にある`i`、いくつあるかを問い合わせます`'f'`右側に存在するものとそれらのインデックスの合計。 貢献度は、`(sum of f indices to right) - i * (count of f to right)`。 
3. 位置の更新ごとに`p`、まず、グローバル回答から古い貢献を削除します。 これには、位置を古い文字セットから削除されたかのように扱う必要があります。 
4.フェンウィックツリーを更新して古いキャラクターをその位置から消去します`p`。 
5. 位置に新しい文字を挿入します`p`対応するフェンウィック構造に組み込まれます。 
6. ポジションの貢献効果を再計算する`p`新しい状態でグローバル回答に追加し直します。 

各更新はプレフィックス/サフィックス集合体のみに影響するため、無関係な位置のスキャンを回避します。 

### なぜ効果があるのか

 合計は、それぞれの独立した寄与に分解できます。`'e'`すべてに対する立場`'f'`その右側に位置します。 フェンウィック ツリーは、そのような各寄与を評価するために必要な 2 つの集計 (インデックスのカウントと合計) を正確に保存します。 更新では一度に 1 つのインデックスのみが変更されるため、グローバルな正確性を維持するには、これらの集計をローカルで調整するだけで十分です。 

不変条件は、フェンウィック ツリーが常に、次のインデックスのマルチセットを正しく表すことです。`'e'`そして`'f'`したがって、サフィックス範囲に対するすべてのクエリは、寄与式を再構築するために必要な正確なカウントと合計を返します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        if r < l:
            return 0
        return self.sum(r) - self.sum(l - 1)

def solve():
    n, m = map(int, input().split())
    s = list(input().strip())

    fe_cnt = Fenwick(n)
    fe_sum = Fenwick(n)
    ff_cnt = Fenwick(n)
    ff_sum = Fenwick(n)

    def add_char(ch, idx, delta):
        if ch == 'e':
            fe_cnt.add(idx, delta)
            fe_sum.add(idx, delta * idx)
        elif ch == 'f':
            ff_cnt.add(idx, delta)
            ff_sum.add(idx, delta * idx)

    for i, ch in enumerate(s, 1):
        add_char(ch, i, 1)

    def contribution_e(i):
        c = ff_cnt.range_sum(i + 1, n)
        sidx = ff_sum.range_sum(i + 1, n)
        return sidx - i * c

    ans = 0
    for i, ch in enumerate(s, 1):
        if ch == 'e':
            ans += contribution_e(i)

    out = []
    out.append(str(ans))

    for _ in range(m):
        p, c = input().split()
        p = int(p)
        old = s[p - 1]

        if old != c:
            if old == 'e':
                c_cnt = ff_cnt.range_sum(p + 1, n)
                c_sum = ff_sum.range_sum(p + 1, n)
                ans -= c_sum - p * c_cnt
            elif old == 'f':
                e_cnt = fe_cnt.range_sum(1, p - 1)
                e_sum = fe_sum.range_sum(1, p - 1)
                ans -= p * e_cnt - e_sum

            add_char(old, p, -1)

            if c == 'e':
                c_cnt = ff_cnt.range_sum(p + 1, n)
                c_sum = ff_sum.range_sum(p + 1, n)
                ans += c_sum - p * c_cnt
            elif c == 'f':
                e_cnt = fe_cnt.range_sum(1, p - 1)
                e_sum = fe_sum.range_sum(1, p - 1)
                ans += p * e_cnt - e_sum

            add_char(c, p, 1)
            s[p - 1] = c

        out.append(str(ans))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```数式は両方の量に独立して依存するため、フェンウィック構造はカウントとインデックスの合計に対して複製されます。 各更新では、変更された位置の古い寄与分がデータ構造から削除される前に慎重に減算され、構造の更新後に新しい寄与分が挿入され、正確性が維持されます。 

よくある実装の落とし穴は、キャラクターを削除するには、フェンウィック ツリーを更新する前にその寄与分を差し引く必要があることを忘れていることです。 逆の順序で実行すると、クエリにはすでに更新された状態が反映されており、減算が間違っています。 

## 実用的な例

 インタラクションが表示される小さな文字列を考えてみましょう。`e f e f`。 

それぞれからの貢献を追跡します`'e'`後で`'f'`。 

| ステップ | 文字列 | ポジションからの貢献 | 合計 |
 | --- | --- | --- | --- |
 | 初期化 | エフエフ| (1→2)=1、(1→4)=3、(3→4)=1 | 5 |

 ここで位置 2 を更新します`'f'`に`'e'`。 

| ステップ | 文字列 | 効果 | 合計 |
 | --- | --- | --- | --- |
 | 前 | エフエフ| ベース | 5 |
 | 2 | で f を削除します。 e_ef | f が正しいエンドポイントであるペアを削除します。 3 |
 | 2 に e を追加 | e e e f | 新しい投稿を追加します | 4 |

 このトレースは、単一の変更がローカルの隣接関係だけでなく、複数のペアにグローバルに影響を与えることを示しています。 

別のケース: すべての文字が`'e'`。 その場合、有効なものはありません`(e, f)`ペアなので、答えはゼロになります。 フェンウィックの構造はこれを正しく反映しています。`'f'`ツリーが空になり、すべてのサフィックス クエリがゼロになります。

 ## 特殊なケース

 重大なエッジケースは、アップデートによって関連性のないキャラクターが`'e'`または`'f'`。 立場を仮定してください`p`からの変更`'x'`に`'e'`。 変更前は何も貢献しません。 変更後、突然すべてのユーザーと対話します`'f'`その右側にあります。 このアルゴリズムは、挿入時にサフィックス統計をクエリすることでこれを処理し、すべての新しいペアが即座にカウントされるようにします。 

別のケースは、次のような役割を逆転することです。`'e'`なる`'f'`。 これには、フェンウィック ツリーを変更する前に古い寄与分を差し引く必要があります。 ツリーの更新後に実行すると、サフィックスおよびプレフィックスのクエリにはすでに新しい構成が反映されており、減算は無効になります。 この実装では、最初に減算が明示的に実行され、次に構造が更新され、次に新しい寄与が追加され、すべてのステップで一貫性が維持されます。
