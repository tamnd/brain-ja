 ## 解決策
 ## 問題の理解

 同じ長さの 2 つの整数配列が与えられています。 最初の配列は非常に制限された値で始まり、各位置は負の 1、0、または正の 1 のいずれかになります。 2 番目の配列には、大きさが非常に大きくなる可能性のある任意の整数を含めることができます。 ここでのタスクは、要素を繰り返し変更する特定の操作を使用して、最初の配列を 2 番目の配列に変換できるかどうかを判断することです。 

許可される操作では、最初のインデックスが 2 番目のインデックスよりも厳密に前にある 2 つのインデックスを選択し、前の位置の値を後の位置に追加します。 重要なのは、ソースの位置は変化せず、同じペアの再利用を含め、操作を何度でも繰り返すことができることです。 

重要な制約は、影響は左から右にのみ流れるということです。 前の要素が後の要素に影響を与えることはありますが、その逆は決してありません。 これにより、アレイ全体に指向性伝播システムが作成されます。 

入力サイズでは、すべてのテスト ケースにわたって合計最大 100,000 個の要素が許可されます。 これにより、ポジションごとに繰り返される更新をシミュレートする単純な試みが 1 回でも爆発的に制限時間を超えてしまうため、インデックスのペア間の演算の二次シミュレーションは即座に除外されます。 

繰り返しの操作によって実際に何が可能になるのかを理解するのは、微妙な難しさがあります。 同じペアを複数回選択できるため、単一の非ゼロ値を後の位置に繰り返し適用できます。これは、操作が 1 回限りの転送ではなく、再利用可能な影響源であることを意味します。 

素朴な推論を破る傾向があるエッジケースには、必要な増加が早期に現れるが、唯一のプラスのソースが後で発生する状況が含まれます。たとえば、次のような配列です。`[0, 1]`なろうとしている`[1, 0]`。 正の値は最初の位置を支援するには右すぎるため、これは不可能です。 もう 1 つの失敗例は、合計が重要であると仮定することです。 たとえば、操作には方向性があり、質量を後方に再配置することはできないため、合計の一致を実行することは実現可能性を保証しません。 

## アプローチ

 ブルートフォース解釈では、操作を直接シミュレートします。 すべてのペアを繰り返しスキャンします`(i, j)`そして、それ以上の変更が発生しなくなるか、配列がターゲットと一致するまで、役立つと思われるたびに更新を適用します。 このアプローチは、許可された操作を正確に模倣するため、原理的には正しいですが、各操作は無期限に適用でき、O(n^2) のペアが存在するため、反復回数が無制限または非常に多くなります。 妥当な上限に制限したとしても、n を 100,000 まで拡張することはできません。 

重要な観察点は、操作の構造が非常に粗雑であるということです。 初期配列内の各位置は、ポジティブな影響、ネガティブな影響、または中立性の永続的なソースになります。 値 1 は、後の任意の位置に繰り返し 1 を追加できることを意味します。 マイナス 1 の値は、後の任意の位置から繰り返し 1 を減算できることを意味します。 ゼロは何もしません。 

これにより、プロセス全体がシミュレーションの問題ではなく、到達可能性の条件に変わります。 ターゲット配列内の各位置について、その位置までのプレフィックス内に少なくとも 1 つの正のソースと少なくとも 1 つの負のソースが既に存在しているかどうかを知る必要があるだけです。 初期状態に比べて値を増やす必要がある場合は、左側の接頭辞の正のソースにアクセスする必要があります。 それを減らす必要がある場合は、左側のプレフィックスに負のソースが必要です。 このようなソースが存在すると、無限に何度も再利用できるため、複数のソースが必要になることはありません。 

これにより、問題は 1 回のリニア スキャンに軽減されます。

 ## アルゴリズムのチュートリアル

 各テスト ケースを独立して処理し、元の配列でこれまでに見つかった正の値か負の値かを追跡しながら、左から右にスキャンします。 

1. 2 つのブール フラグを初期化します。1 つはプレフィックスに正のフラグが現れたかどうかを示し、もう 1 つは負のフラグが現れたかどうかを示します。 
2. 各インデックスを左から右に繰り返します。 各位置で、最初に元の配列の値を使用してフラグを更新します。 現在の要素が 1 の場合、肯定フラグは true になります。 マイナス 1 の場合、否定フラグは true になります。 ゼロは何も変わりません。 
3. この位置で 2 つの配列の現在値を比較します。 ターゲット値が元の値より大きい場合は、1 を加算してこの位置を増やす必要があります。これには、プレフィックスに正のソースがすでに存在している必要があります。 そのようなソースが存在しない場合、変換は不可能です。 
4. ターゲット値が元の値より小さい場合は、マイナス 1 演算を使用して値を減らす必要があります。これには、プレフィックスに負のソースが存在する必要があります。 存在しない場合、変換は不可能です。 
5. どのインデックスでもどちらの条件にも違反しない場合、変換は可能です。 

重要な点は、ソースが使用された回数を追跡する必要はなく、到達可能なプレフィックスにそのソースが存在するかどうかだけを追跡する必要があるということです。 

### なぜ効果があるのか

 演算構造体により、元の配列内のゼロ以外の各エントリが、後のすべての位置に対する単位の増分または減分の再利用可能なジェネレータになります。 あるインデックス i に値 1 が現れると、i より大きいすべての位置 j は、操作を繰り返すことによって i から任意の数の増分を受け取ることができます。 無制限のデクリメントのソースとしてのマイナス 1 についても同じことが当てはまります。 ソースは消費されることはなく、プレフィックスに導入されるだけであるため、意味のある唯一の状態は、各側に少なくとも 1 つのソースが存在するかどうかです。 

これにより、すべての実現可能性に関する質問がプレフィックス存在チェックに減らされ、スキャン全体を通じて一貫性が保たれます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))
        
        has_pos = False
        has_neg = False
        ok = True
        
        for i in range(n):
            if a[i] == 1:
                has_pos = True
            elif a[i] == -1:
                has_neg = True
            
            if b[i] > a[i]:
                if not has_pos:
                    ok = False
                    break
            elif b[i] < a[i]:
                if not has_neg:
                    ok = False
                    break
        
        print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()
```実装は、アルゴリズムで説明されているスキャンに従います。 現在の位置自体がゼロ以外の場合、後のインデックスのソースとして機能するため、各インデックスでの実現可能性をチェックする前にフラグが更新されます。 

よくある微妙な間違いは、条件をチェックした後にフラグを更新することです。 これにより、許可されている場合でも、位置 i の値が位置 i 自体の制約を満たすために使用されることが誤って防止されてしまいます。 

## 実用的な例

 ### 例 1

 入力:```
n = 3
a = [1, -1, 0]
b = [1, 1, -2]
```プレフィックスのソースと実現可能性を段階的に追跡します。 

| 私 | a[i] | b[i] | 持っている位置 | ハッシュタグ | 状態 |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 1 | 1 | 本当 | 偽 | わかりました |
 | 1 | -1 | 1 | 本当 | 本当 | 増加は許可されます |

 インデックス 1 では、ターゲットが元の値より大きいため、インデックス 0 からすでに存在する正のソースが必要です。インデックス 2 では、ターゲットが小さいため、インデックス 1 に表示される負のソースが必要です。すべての要件が満たされています。 

### 例 2

 入力:```
n = 2
a = [1, 0]
b = [1, 41]
```| 私 | a[i] | b[i] | 持っている位置 | ハッシュタグ | 状態 |

 | 0 | 1 | 1 | 本当 | 偽 | わかりました |
 | 1 | 0 | 41 | 本当 | 偽 | 増加は許可されます |

 増加が大きい場合でも、2 番目の指数に繰り返し適用できるため、単一のプラスのソースが存在するだけで十分です。 

これは、大きさは重要ではなく、ソースの存在だけが重要であることを示しています。

 ## 特殊なケース

 一般的なエッジ ケースは、必要な操作が配列内で後から現れるソースに依存する場合です。 たとえば、最初の位置で減少が必要であるが、最初のマイナス 1 がその後にしか現れない場合、たとえグローバルなマイナスが存在していても、変換は失敗します。 評価時にプレフィックス フラグがまだ false であるため、アルゴリズムはこれを正しく拒否します。 

もう 1 つの微妙なケースは、初期配列のすべての要素が 0 である場合です。 ゼロでは変更を生成できないため、最初の配列とは異なるターゲット配列はすぐに失敗します。これは、スキャン全体で両方のフラグがないことによって正しくキャプチャされます。 

3 番目のケースは、ソースが 1 種類のみ存在する場合です。 配列に 1 のみが含まれている場合、将来の構造に関係なく、必要な減少は不可能であり、接頭辞の負なしで負の要件が出現すると、スキャンによってこれが即座に検出されます。
