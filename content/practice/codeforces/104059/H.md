 ## 解決策
 ## 問題の理解

 私たちは、長さ 10,000 までの英小文字の隠し文字列を操作しています。 情報を取得する唯一の方法は、「一連の文字が与えられた場合、非表示文字列内のどの位置にこれらの文字が含まれるか」という形式のクエリを実行することです。 

このような各クエリはインデックスのリストを返します。 重要なのは、応答では各位置でどの文字が一致したかは示されず、それらのインデックスの文字が選択されたセットに属していることが示されるだけです。 

私たちの目標は、合計 7 つのクエリを使用して、非表示の文字列全体を正確に再構築することです。その後、完全な文字列を最終的な回答クエリとして出力する必要があります。 

主な問題は、各位置で個々の文字をクエリできないという事実にあります。これは、最悪の場合、位置ごとに 26 個のクエリが必要になるためです。 最大 10,000 のポジションでは、ポジションごとの戦略は不可能です。 合計 7 つのクエリしかないという制約により、各クエリからグローバル構造を抽出する必要があります。 

単純なアプローチでは、単一の文字をクエリすることによって各文字を個別に決定しようとします。 たとえば、「どの位置が「a」ですか?」、次に「どの位置が「b」ですか?」と尋ねます。 これはすぐに失敗します。26 個のクエリでもすでに制限を超えており、反復せずに結果を効率的にマッピングする方法がまだないからです。 

2 番目の素朴なアイデアは、位置ごとに文字をバイナリ検索することかもしれませんが、その場合は位置ごとにクエリを実行する必要があり、許容される予算をはるかに超えます。 

多くの素朴な実装を壊す微妙なエッジケースは、応答が整列またはグループ化されていると仮定することです。 たとえば、次のようなセットをクエリすると、`{a, b, c}`、返された位置にこれらの文字のいずれかが含まれていることだけがわかりますが、順序付けや分離を想定することはできません。 クエリ戦略が適切に選択されていないと、異なる文字を持つ 2 つの位置が区別できないように見える場合があります。 

この解決策を推進する重要な制約は、クエリの総数がアルファベットのサイズに比べて非常に小さいため、各クエリはすべての位置にわたって複数ビットの情報を同時にエンコードする必要があるということです。 

## アプローチ

 ブルートフォース戦略では、各キャラクターを個別に識別しようとします。 すべての位置について、正しい文字を分離するまで、シングルトンまたはサブセットをクエリすることによって 26 文字すべてをテストします。 このアイデアの最も最適化されたバージョンでも、最悪の場合でも少なくとも O(26n) 文字チェックが必要となり、これは数十万回の対話に相当します。 これは、7 つのクエリという厳密な対話制限の下では不可能です。 

重要な点は、文字を位置ごとに識別する必要がないということです。 代わりに、アルファベットのビット単位のエンコーディングを使用して、すべての文字を同時に識別できます。 

各文字に 0 から 25 までの数字を割り当て、それをバイナリ形式で表します。 26 は 5 ビット内に収まるため、各文字は 5 ビット マスクによって一意に識別できます。 文字コードにどのビットが設定されているかを位置ごとに判断できれば、完全な文字列を再構築できます。 

これは、慎重に構築された 5 つのクエリを使用することで実現できます。 k 番目のクエリでは、k 番目のビットが設定されているすべての文字を要求します。 インタラクターは、そのサブセットに属する隠し文字が含まれるすべての位置を返します。 これを 5 つのビット位置すべてに対して繰り返すことで、すべての文字のバイナリ表現を並行して効果的に学習します。 

これにより、問題は位置ごとの識別からグローバル ビット抽出まで軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 位置ごとのブルートフォース推測 | O(26n) クエリ | O(n) | 遅すぎる |
 | ビット単位の再構成 (最適) | O(5n) 処理、5 クエリ | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 それぞれがアルファベット エンコーディングの 1 ビットに対応する 5 つのクエリを構築します。 

1. 「a」から「z」までの各文字に 0 ～ 25 の整数を割り当てます。各数値は 5 ビットのバイナリ表現として考えてください。 
2. ビット位置 0 (最下位ビット) について、0 番目のビットが 1 であるすべての文字で構成されるクエリを構築します。このクエリを送信し、返されたインデックスのリストを保存します。 
3. 対応するビットが設定されている文字セットをクエリするたびに、ビット位置 1 ～ 4 に対して同じプロセスを繰り返します。 
4. 隠し文字列の各位置について、最初に 0 に設定された 5 ビットの整数を維持します。ビット k の応答に位置が現れると、その位置の整数の k 番目のビットを設定します。 
5. 5 つのクエリをすべて処理した後、各 5 ビット整数を対応する文字に変換します。 
6. 最終回答クエリを使用して、再構成された文字列を出力します。 

位置ごとのビットを安全に蓄積できる理由は、各クエリが基礎となる文字の単一のバイナリ特徴に従って位置をきれいに分割しているためです。 

### なぜ効果があるのか

 各文字は、その 5 ビット表現によって一意に決定されます。 すべてのクエリは、すべての位置にわたってこの表現の 1 ビットを同時に分離します。 位置は、その文字にそのビットが設定されている場合に限り、クエリに表示されます。 したがって、5 回のクエリの後、すべての位置にはその文字の完全なバイナリ署名が含まれます。 0 ～ 25 の範囲で同じ 5 ビット パターンを共有する 2 つの文字はないため、デコードは明確で一貫性があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def ask(chars):
    print("?", "".join(chars))
    sys.stdout.flush()
    parts = input().split()
    if not parts:
        sys.exit(0)
    n = int(parts[0])
    res = set()
    for x in parts[1:]:
        res.add(int(x))
    return res

def main():
    n = None

    # 26 letters mapped to 0..25
    alpha = [chr(ord('a') + i) for i in range(26)]
    bit_pos = [set() for _ in range(5)]

    # build queries for each bit
    for b in range(5):
        s = []
        for i in range(26):
            if (i >> b) & 1:
                s.append(alpha[i])
        bit_pos[b] = ask(s)

    # reconstruct
    code = [0] * (10**4 + 5)

    # we need n, infer from any response
    # simplest: scan max index from first query responses
    for b in range(5):
        if bit_pos[b]:
            n = max(n or 0, max(bit_pos[b]))

    if n is None:
        n = 0

    # apply bits
    for b in range(5):
        for idx in bit_pos[b]:
            code[idx] |= (1 << b)

    # decode
    ans = []
    for i in range(1, n + 1):
        ans.append(chr(ord('a') + code[i]))

    print("! " + "".join(ans))
    sys.stdout.flush()

if __name__ == "__main__":
    main()
```この実装はビットごとの戦略を直接反映しています。 機能`ask`フォーマットとフラッシュを処理します。これは、対話型の問題でクエリがすぐに送信されるようにするために不可欠です。 5 つのクエリはそれぞれ、単一のバイナリ ビットによって決定される文字のサブセットを選択します。 

メンバーシップ チェックが効率的に行われ、重複が回避されるように、応答をインデックスのセットとして保存します。 5 つの応答をすべて収集した後、対応するビットを OR 演算して各位置の文字を再構築します。 最後に、数値コードを文字に変換し直し、完全な文字列を出力します。 

微妙な点は、応答に含まれる最大インデックスから文字列の長さを推測していることです。 すべての位置は少なくとも 1 ビットのクエリに出現する必要があるため、これは安全です。 

## 実用的な例

 「バナナ」のような小さな隠れた文字列を考えてみましょう。 

アルファベットのサブセットに対して 5 ビットのクエリを実行します。 応答はビットごとのインデックス セットのように見える場合があります。 位置 1 ～ 6 のみを追跡します。 

| ビット | クエリ文字 | 返されたインデックス |
 | --- | --- | --- |
 | 0 | a、c、e、g、i、k、m、o、q、s、u、w、y | 1,3,5,6 |
 | 1 | b、d、f、g、j、l、n、p、r、t、v、x、z | 2,4 |
 | 2 | c、d、g、h、l、m、r、s、x、y | 3,5 |
 | 3 | e、f、g、h、o、p、s、t | 1,6 |
 | 4 | i-j-k-l-m-n-o-p | 2,3,4 |

 インデックスごとのビットを結合した後、各位置に 5 ビット コードが蓄積され、これが正しい文字にデコードされます。 

このトレースは、各クエリがどのように部分的な情報を提供するか、および再構成が対話中に位置ごとではなく最後にのみどのように行われるかを示します。 

「aaaaa」を含む 2 番目の例は、重複しても問題がないことを示しています。 すべてのビット クエリは、「a」がアクティブであるすべてのビットのすべてのインデックスを返し、再構築ではすべての位置で一貫して「a」が得られます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(5n) | 各位置はビットごとに 1 回処理されます。
 | スペース | O(n) | 位置ごとにビットマスクを保存します。 

インタラクションコストが一定 (5 クエリ) であり、後処理が文字列の長さ (最大 10,000) に対して線形であるため、ソリューションは制限内に簡単に収まります。

 ## 特殊なケース

 重要なエッジケースは、すべての文字が同一である場合です。 この場合、すべてのビット クエリはインデックスの完全なセットを返しますが、すべてのビットが同じ文字コードに一貫して整列しているため、再構築は引き続き機能します。 このアルゴリズムは、クエリ中の位置の区別には依存せず、一貫したビット集約のみに依存します。 

もう 1 つのケースは、「a」から「d」のみ、または「x」から「z」のみなど、文字がアルファベットの下位または上位の範囲のみにまたがる場合です。 ビット表現は引き続き各文字を一意に識別し、未使用のビット パターンはクエリ内でアクティブになることはなく、無害です。 

最後に、再構築中に各位置が独立して処理され、クエリの数が一定のままであるため、最大長 10,000 の文字列は正確さに影響しません。
