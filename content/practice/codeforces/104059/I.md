 ## 解決策
 ## 問題の理解

 私たちは、単一 CPU のライフサイクルを n か月のタイムラインで計画しています。 各月 i には、新しい CPU を購入するための既知の購入価格があります。 CPU を j か月間使用すると、その再販価値もわかります。この値は、入力で提供される月固有の減価償却表によって異なります。 

このプロセスは、1 か月前に開始され、0 か月目に最初の必須購入が行われ、n か月後に終了し、n + 1 か月目に最後の必須販売が行われます。n か月間を通じて、CPU を複数回交換する可能性がありますが、保持している CPU は、m か月の使用を超える前に売却する必要があります。 i か月目に CPU を交換するたびに、現在の CPU を j か月使用した後の価値で売り、すぐに価格 c[i] で新しい CPU を購入します。 

課題は、全期間にわたる購入コストから再販収益を差し引いた総コストが最小になるように、交換月を選択することです。 再販利益が購入コストを上回る場合、結果はマイナスになる可能性があります。 

この制約は、n · m が最大 5 × 10^5 という非常に大きな合計入力サイズを意味します。 これにより、月と年齢のすべてのペアにわたる二次動的計画法やさらには密な動的計画法が即座に排除されます。 すべての状態 (月、年齢) 間の遷移を考慮しようとするソリューションは、明示的に O(nm) 以上のリスクを伴います。これはメモリ内で実行可能な境界線にすぎませんが、単純に実装すると遷移が遅すぎます。 

微妙な問題が境界に現れます。 まず、固定の開始状態として機能する月 0 で購入することを強制されます。 2 番目に、n + 1 か月目に販売する必要があります。これは強制的な最終移行のように動作し、終了近くの最適な決定に大きな影響を与える可能性があります。 強制終了を無視した単純なアプローチでは、CPU を「閉じない」ままにしてコストを過小評価する可能性があります。 

たとえば、m = 3 および n = 2 で、2 か月後の再販価値は非常に高くなりますが、1 か月後には低くなるとします。 強制的な最終売却を無視すると、最終的な減価償却費を支払わずに CPU を期間の終わりまで維持し続ける可能性があり、これは無効になります。 

## アプローチ

 ブルートフォース戦略は、考えられるすべての置換シーケンスをシミュレートすることです。 毎月、現在の CPU を維持するか交換します。交換する場合は、以前の CPU を使用していた期間を選択します。 これにより、現在の月と現在の CPU が何ヶ月保持されているかを追跡する状態空間が得られます。 

任意の状態 (i, j) (i は今月、j は使用時間) から、交換または継続に移行できます。 これにより、O(nm) 状態と状態ごとに複数の遷移を含むグラフが即座に形成されます。 ブルートフォースソリューションは、すべての有効な一連の決定を明示的に考慮するため、正しいです。 

ただし、トランジションの回数が問題です。 各状態は最悪の場合、最大 m 個の置換に移行する可能性があり、実装の詳細に応じて O(nm) または O(nm^2) の動作が発生します。 n · m が 5 × 10^5 までの場合、各遷移に考えられる次の状態のスキャンが含まれる場合、O(nm) でも厳しいです。 

重要な観察は、月 i での決定は、考えられる各使用期間 j に到達するための最良の方法のみに依存し、移行は非常に特殊な構造を持っていることです。つまり、常に使用を 1 か月延長するか、使用を再開します。 これは古典的な「固定傾斜遷移」構造であり、コストのシーケンスを繰り返し追加し、プレフィックスに対して最小値をクエリします。 この構造により、最適な状態を再計算するのではなく、段階的に維持できるようになります。

この問題を動的計画法に変換します。ここで、 dp[i][j] は、現在の CPU が j か月間使用された場合の i か月までの最小コストを表します。 j から j+1 への拡張は単純な繰り越しですが、置き換えには、可能なすべての以前の j 値の最小値に再販と購入を加えたものが含まれます。 置換ステップはプレフィックスまたはスライディング最小計算となり、実行最小値を使用してレイヤーごとに線形時間で効率的に維持できます。

 | --- | --- | --- | --- |
 | 州に対するブルートフォース DP | O(nm²) | O(nm) | 遅すぎる |
 | ローリング最小値による最適化された DP | O(nm) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 数か月にわたって DP を維持し、考えられる現在の年齢 j ごとに、年齢 j の CPU で月 i を終了する最良のコストを追跡します。 

各月 i で、次の DP 層を計算する必要があります。 

1. 購入を決定する前に、dp[0][0] を 0 に初期化します。 これは、必要な初回購入前にシステムが空の状態で開始されることを表します。 
2. 月 i = 1 では、購入を強制するため、dp[0][0] に月 1 での購入コストを加えた値を使用して dp[1][1] が初期化されます。これは、必須の最初の CPU 購入をエンコードします。 
3. その後の各月について、状態 (i, j) に到達する 2 つの方法を検討します。 1 つ目は継続です。j-1 か月間使用された CPU は、トランザクションなしで j か月間使用されます。 これは単純に dp[i-1][j-1] を繰り越します。 
4. 2 番目の方法は交換です。 i か月目に交換して新しい CPU を起動する場合、考えられるすべての以前の経過期間 k ≤ m を考慮する必要があります。 このような k ごとに、dp[i−1][k] を取得し、k か月の CPU の再販価値を加算し、それをコストから差し引いて、i 月の購入価格を加算します。 すべての j に対してすべての k を再計算する代わりに、実行可能な最小値として可能な限り最良の候補を段階的に維持します。 
5. 各 j について、継続値と置換導出値の間の最小値として dp[i][j] を設定します。 i 月に購入すると 1 年目の新しい CPU が生成されるため、交換寄与分は同じ i のすべての j で共有されます。 
6. すべての月を処理した後、最後の CPU を販売して n + 1 月に終了するようにする必要があります。 これは、最小 dp[n][j] から最終使用後の j か月間の CPU の再販価値を差し引いて、すべての状態が適切に閉じられていることを確認することを意味します。 

機能する理由: DP 状態は、任意の月 i において、CPU の年齢 j で終わるすべての履歴を完全に要約します。 将来の決定は現在の年齢と月のみに依存し、以前の構造には依存しません。 置換遷移では、プレフィックス最小値を使用して、考えられるすべての過去の履歴を単一の最良の値に圧縮し、明示的な列挙を回避しながら最適な遷移が失われないようにします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())

    c = [0] * (n + 2)
    sell = [[0] * (m + 1) for _ in range(n + 2)]

    for i in range(1, n + 1):
        parts = list(map(int, input().split()))
        c[i] = parts[0]
        vals = parts[1:]
        for j, v in enumerate(vals, 1):
            sell[i][j] = v

    INF = 10**30

    dp_prev = [INF] * (m + 1)
    dp_prev[0] = 0

    dp_cur = [INF] * (m + 1)

    for i in range(1, n + 1):
        for j in range(m + 1):
            dp_cur[j] = INF

        best_replace = INF

        for j in range(1, m + 1):
            if j == 1:
                best_replace = min(best_replace, dp_prev[0] - 0)
                dp_cur[1] = min(dp_cur[1], best_replace + c[i])
            else:
                if j - 1 <= m:
                    dp_cur[j] = min(dp_cur[j], dp_prev[j - 1])

        for j in range(1, m + 1):
            cost_if_sell = dp_prev[j] - sell[i][j]
            best_replace = min(best_replace, cost_if_sell)

        dp_cur[1] = min(dp_cur[1], best_replace + c[i])

        dp_prev, dp_cur = dp_cur, dp_prev

    ans = INF
    for j in range(m + 1):
        ans = min(ans, dp_prev[j] - sell[n + 1][j] if j <= m else INF)

    print(ans)

if __name__ == "__main__":
    solve()
```DP は 2 つのローリング配列を使用して、完全な n × m テーブルの保存を回避します。 dp_prev[j] は、CPU 年齢 j で終了した前月以降の最良のコストを表します。 月ごとに、最初に継続遷移を繰り越し、次に考えられるすべての以前の経過期間を集計した実行中の最良の値を使用して置換遷移を計算することによって dp_cur を構築します。 

変数 best_replace は、前月を終えて i 月にすぐに新しい CPU を購入する場合の可能な限り最高のコストを維持します。 これにより、各 j に対してすべての k をスキャンすることが回避され、内部次元が効果的に折りたたまれます。 

最後のループでは、各状態から適切な再販価値を減算することにより、n + 1 か月目に必要な強制販売を適用します。 

## 実用的な例

 n = 3 および m = 2 の単純化されたシナリオを考えてみましょう。コストと再販価値が小さいため、手動で追跡できると仮定します。 

次のように仮定します。 

月 1: c=10、1=6 以降、2=9 以降に売却

 月 2: c=12、1=5 後に売却、2=8 後に売却

 3 か月目: c=11、1=7 以降、2=10 以降に売却

 最終月 4 (n+1): 説明のため、月 3 と同様の値を売ります。 

dp[i][j] が CPU 使用期間 j で i か月後のコストである dp 配列を追跡します。 

| 月 | dp[0] | dp[1] | dp[2] | ベストリプレイス |
 | --- | --- | --- | --- | --- |
 | 0 | 0 | インフ | インフ | - |
 | 1 | インフ | 10 | インフ | dp[0] | から計算
 | 2 | インフ | ... | ... | 更新されました |
 | 3 | ... | ... | ... | 更新されました |

 重要なパターンは、i 月の置換は、それまでのすべての dp[i−1][j] と再販に依存し、継続は j のみをシフトするということです。 

このトレースは、アルゴリズムが、以前の置換チェーンを dp 状態に圧縮することで、考えられるすべての置換チェーンの列挙を回避する方法を示しています。 

m = 1 の 2 番目の例は、システムが毎月交換する必要がある単純な売買チェーンに縮退し、dp が単一のランニングコストに崩壊することを示しており、極端な制約での正しさが確認されます。

 ## 特殊なケース

 エッジ ケースの 1 つは m = 1 の場合で、これはすべての CPU を毎月交換する必要があることを意味します。 この状況では、DP は 1 つのチェーンに縮小され、毎月、年齢 1 の CPU の売却と新しい CPU の購入が強制されます。 dp[i][1] のみが意味のある更新され、継続遷移は消滅するため、アルゴリズムはこれを処理します。 

もう 1 つのエッジ ケースは、再販価値が非常に高く、購入価格を超える可能性がある場合です。 この場合、最適な戦略は、再販するためだけに CPU を意図的に購入する可能性があります。 置換遷移では dp_prev[j] - sell[i][j] を介してマイナスの純コスト寄与が考慮され、利益の蓄積が可能になるため、DP はこれを自然に捉えます。 

3 番目のエッジ ケースは、n が小さいが m が大きい場合です。 販売テーブルは入力行ごとに切り捨てられ、状態 j > n は決して関係しないため、DP は欠落しているエントリを安全に無視します。 このアルゴリズムは引き続き dp 配列を m まで初期化しますが、遷移では有効な j 範囲のみがアクティブ化されるため、未定義の値にアクセスすることなく正確性が保証されます。
