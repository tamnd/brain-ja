 ## 問題の理解

 バイナリ文字列が与えられています。これは、次の内容のみを含むセルの行と考えてください。`0`そして`1`。 この長い行から、固定サイズのウィンドウをスライドさせます`k`考えられるすべての開始位置にわたって。 各位置は、次の長さの部分文字列を生成します。`k`、各部分文字列自体はバイナリ文字列です。 

タスクは、これらの部分文字列をリストしたり、素朴な方法でペアごとに直接比較したりすることではなく、単に長さの異なるパターンがいくつあるかを数えることです。`k`文字列内のどこにでも現れます。 

したがって、出力は、サイズに応じた一意の「ウィンドウ」の数になります。`k`左から右にスキャンすると。 

この制約により、文字列の長さは最大 200,000 まで許可されます。 すべての部分文字列の単純な比較には最大 200,000 のウィンドウが含まれ、各比較のコストは O(k) となり、およそ O(nk) となり、最悪の場合は 4×10^10 の演算に達する可能性があります。 それは制限時間をはるかに超えています。 

重要な点は、各部分文字列が短い (バイナリ アルファベット) ため、前処理後に O(1) 内の部分文字列を比較する方法、またはそれらをコンパクトなハッシュ可能な形式で表現する方法が必要であるということです。 

すべての文字が同一である場合、微妙なエッジケースが発生します。 たとえば、次の場合`s = 00000`そして`k = 3`、すべての部分文字列は同一であるため、答えは次のようになります。`1`。 非ローリング再計算を誤って使用する単純なハッシュ手法では、再計算エラーや一貫性のない正規化により、誤って同一の部分文字列が異なるものとして扱われる可能性があります。 もう 1 つのエッジケースは次のような場合です`k = 1`、答えは単に個別の文字の数です、常に`1`または`2`。 

## アプローチ

 ブルートフォースソリューションでは、長さのすべての部分文字列が抽出されます。`k`、それを文字列として保存し、セットに挿入します。 セットは一意性を処理するため、これは論理的には正しいです。 ただし、各部分文字列のコピーには O(k) のコストがかかり、これを O(n) 個の位置で行うと合計コストは O(nk) となり、上限に対して遅すぎます。 

これを改善するために、部分文字列が重なり合っていることに気付きます。 あるウィンドウから次のウィンドウに移動すると、2 人の文字が変更されるだけです。1 人はウィンドウから出て、もう 1 人はウィンドウに入ります。 この構造はローリング表現を示唆しています。 

アルファベットはバイナリであるため、各部分文字列を基数 2 の数値として解釈できます。すると、各ウィンドウが整数に対応し、ビット演算を使用して O(1) でこの整数を更新できます。つまり、左にシフトし、新しいビットを追加し、長さを超えた古いビットをマスクします。`k`。 これにより、衝突のないローリング ハッシュが得られます。 

これにより、スライディング バイナリ値を維持し、各値をセットに挿入するという問題が軽減されます。

 ## アルゴリズムのチュートリアル

 1.最初のウィンドウのサイズを変換します。`k`2進数として解釈して整数に変換します。 これにより、部分文字列がコンパクトに表現されます。 
2. この整数をハッシュ セットに挿入します。 このセットには、これまでに確認されたすべての個別のウィンドウ値が格納されます。 
3. ポジションごとに`i`から`k`に`n - 1`、現在の値を更新します。 

1 ビット左にシフトし (2 を乗算するのと同じ)、新しいビットを追加します。`s[i]`でマスクして、ウィンドウから外れるビットの影響を除去します。`(1 << k) - 1`。 
4. 更新された各値をセットに挿入します。 各値は、長さの部分文字列を一意に識別します`k`。 
5. 答えは、すべてのウィンドウを処理した後のセットのサイズです。 

ステップ 3 の重要な考え方は、部分文字列を決して再構築しないということです。 以前の計算を再利用してローカルに調整することで、ランタイムを線形に保ちます。 

### なぜ効果があるのか

 長さの各部分文字列`k`基数 2 で解釈されると、一意の 2 進数に対応します。ローリング アップデートでは、整数表現と現在のウィンドウ コンテンツの間の正確な等価性が維持されます。 すべてのウィンドウが 1 回だけアクセスされ、決定論的に数値にマッピングされるため、部分文字列の等しいかどうかは、セットに格納されている整数の等しいかどうかに正確に対応します。 表現はハッシュ化されたものではなく正確であるため、衝突は発生しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    s = input().strip()

    if k == 0:
        print(0)
        return

    mask = (1 << k) - 1

    val = 0
    for i in range(k):
        val = (val << 1) | (ord(s[i]) - 48)

    seen = {val}

    for i in range(k, n):
        val = ((val << 1) & mask) | (ord(s[i]) - 48)
        seen.add(val)

    print(len(seen))

if __name__ == "__main__":
    solve()
```コードはローリング整数を維持します`val`それは常に最後を表します`k`文字列のビット。 マスクにより、古いビットがウィンドウの外に移動すると確実に削除されます。 セット`seen`遭遇したすべての個別の値を追跡します。 

よくある間違いは、マスク操作を忘れることです。これにより、ビットが長さを超えてしまいます。`k`ウィンドウ間の比較を蓄積して破損するため。 もう 1 つの微妙な問題は、最初のウィンドウを正しく初期化することです。 そうしないと、すべての比較が変更され、誤ったカウントが生成されます。

 ## 特殊なケース

 文字列がすべて同一の文字で構成されている場合、ローリング値は同一ビット内でシフトする場合を除いて決して変更されないため、すべてのウィンドウは同じ整数にマップされます。 入力用`s = 000000`そして`k = 3`、すべての計算値が残ります`0`、したがって、セットサイズは`1`。 

いつ`k = 1`、各ウィンドウは単一ビットにすぎません。 ローリング メカニズムは、各文字の整数値をセットに直接挿入するように退化します。 のために`s = 0101`、値が交互に表示されます。`0`そして`1`、正確に 2 つの異なる要素が生成されます。 

いつ`k = n`、ウィンドウが 1 つしかないため、初期エンコーディングはすでに完全な文字列を表しており、設定されたサイズは常に`1`。
