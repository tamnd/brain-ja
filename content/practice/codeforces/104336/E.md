 ## 問題の理解

 私たちは一連のマキシムの日々の問題解決を追跡しています。$n$日々。 毎日、彼は少なくとも 1 つの問題を解決するため、毎日に正確な正の整数を割り当てたいと考えています。 

毎日 2 つの量が観察されます$i$。 The first is the total number of problems solved in the last$k$で終わる日$i$、長さの合計のスライディング ウィンドウのように動作します。$k$。 2 番目は、次で終了する連続した日数です。$i$その間、彼は毎日問題を解決しており、これは単に現在の連続記録の長さに相当します。 

ルールは、毎日、過去のスライディング ウィンドウの合計です。$k$日は少なくとも現在の連続長と同じ長さである必要があります。 この条件はすでにすべての人に当てはまると言われています$n$すべての合計を最小限に抑えながら、制約を満たす日次値のシーケンスを再構築する必要があります。$n$日々。 

入力により得られるのは、$k$、ウィンドウのサイズ、および$n$、日数。 出力は、解決された問題の最小合計数です。 

制約は次のとおりです$10^6$したがって、どの解も線形または線形に近いものでなければなりません。$n$。 すべての有効なシーケンスの二次再構成やスライディング ウィンドウの繰り返しの再計算は不可能です。$O(nk)$届くだろう$10^{12}$最悪の場合の運用。 

単純な考えとしては、毎日可能な限り最小の値 (通常は 1) を割り当ててみて、制約に違反していないかどうかを確認することです。 失敗のケースは、スライディング ウィンドウがストリークの成長に比べて小さすぎる場合に発生します。 たとえば、次のようなとき$k = 2$、3 日目のウィンドウは最初の 2 日と部分的にしか重なりません。そのため、すべての値を 1 に維持するだけでは、連続増加を伴う不等式を満たすにはすぐに不十分になります。 単純なシミュレーションでは、以前の値を繰り返し調整することになり、カスケード更新が発生して速度が非常に遅くなります。 

もう 1 つの微妙な問題は、制約が移動合計とグローバル ストリークの両方に依存するため、ローカルで貪欲な選択を行うと、すぐに検出されずに後で実現可能性が損なわれる可能性があることです。 

## アプローチ

 ブルート フォース アプローチでは、完全な配列を維持し、日ごとにストリークの長さと最後の合計の両方を再計算して毎日シミュレーションします。$k$日々。 日時に制約に違反した場合$i$場合は、それを修正するために以前の値をいくつか増やしてみます。 最悪の場合、各調整が逆方向に伝播する可能性があります。$k$これが何日も繰り返される可能性があります。 これにより、最悪の場合、次のような複雑さが生じます。$O(nk)$、毎日スライディング ウィンドウの再計算と修復が必要になる可能性があるためです。 

重要な観察は、制約が 2 つの単調量にのみ依存するということです。ストリークは決定論的に増加します (常に増加します)。$i$)、スライディング ウィンドウの合計は、サイズが制限されたウィンドウによって制御されます。$k$。 この不平等により、ウィンドウ合計は線形の増加に「追いつく」ことになりますが、それは局所的な調整によってのみです。 これは、私たちが決定を再検討する必要が決してないことを示唆しています。$k$それよりも古いものは後退します。$k$日は制約に影響しなくなりました。 

これは、貪欲な構築につながります。つまり、現在のウィンドウの合計を維持し、ストリークが増加したときに、実行可能性を回復するためにウィンドウ内の値を最小限に増やすことを保証します。 最適な構造は最終的に周期的になります。毎日、最後の構造にちょうど十分な質量が存在することを確認します。$k$システムが安定すると、これにより繰り返しパターンが作成されます。

 ## アルゴリズムのチュートリアル

 最後のスライディング ウィンドウの合計を維持しながら、シーケンスを段階的に構築します。$k$値を調整し、それが常に少なくとも現在のストリーク長であることを確認します。 

1. 配列またはローリング構造を初期化して、最後のデータを保存します。$k$値はすべて 1 から始まります。毎日少なくとも 1 つの問題が発生するため、これは可能な最小の選択です。 
2. 前回の累計を維持します。$k$日々。 最初は、1 日目の合計は 1、連続数は 1 であるため、制約が当てはまります。 
3. 1 日目から次の日まで繰り返す$n$。 毎日のために$i$、現在のストリーク値を計算します。$i$シーケンスが連続しているためです。 
4. 最新のウィンドウの現在のウィンドウの合計を計算します。$k$要素。 もし$i \le k$、ウィンドウはプレフィックスの合計です。$i$; それ以外の場合は合計が終了します$i-k+1$に$i$。 
5. ウィンドウ合計がすでに少なくとも$i$では、現在の日に最小値 1 を割り当て、ウィンドウを更新して続行します。 
6. ウィンドウ合計が以下の場合$i$、ウィンドウ合計が正確になるように、当日の値を増やす必要があります。$i$。 以前の値を増やしても、将来の要件が減少することなく合計が増加するだけであるため、これは最適です。 
7. 日の値を割り当てた後$i$、新しい値を追加し、次の場合はウィンドウからはみ出した値を削除して、スライディング ウィンドウを更新します。$i > k$。 

重要な構造上の考え方は、制約内のすべての不足は現時点で貪欲に修正でき、過去への再分配は必要ないということです。 

### なぜ効果があるのか

 いつでも$i$、制約は最後の値の合計にのみ依存します。$k$要素と値$i$。 不等式に不足がある場合は、現在のウィンドウの合計が小さすぎて、必要なしきい値を満たすことができないことを意味します。 ウィンドウ外の以前の日はすべて制約に影響を与えないため、実現可能性を修復する唯一の方法は、現在のウィンドウ内の値を増やすことです。 

ウィンドウ内の以前のポジションまたは現在のポジションを増やすことは、実現可能性の点では同等ですが、既に満たされている前日の制約に違反するリスクがないため、当日​​を増やすことが最適です。 これにより、過去の正しさを決して無効にしない局所的に最適な修復ステップが作成され、安定した貪欲不変式が確立されます: 処理日後$i$までのすべての制約$i$が保持され、ウィンドウの合計は常に最小限で十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    k, n = map(int, input().split())
    
    from collections import deque
    window = deque()
    window_sum = 0
    
    total = 0
    
    for i in range(1, n + 1):
        # remove element leaving window
        if len(window) == k:
            window_sum -= window.popleft()
        
        # current streak requirement
        need = i
        
        # minimum value is 1
        val = 1
        
        # check window constraint
        if window_sum + val < need:
            val = need - window_sum
        
        window.append(val)
        window_sum += val
        total += val
    
    print(total)

if __name__ == "__main__":
    solve()
```実装は、最後のものを表す両端キューを維持します。$k$サポートする値と累計$O(1)$更新情報。 毎日、少なくとも 1 つの問題が割り当てられるようにします。 スライディング ウィンドウの合計が現在のストリーク要件を満たすのに不十分な場合は、同等を満たすのに十分なだけ当日の値を増やします。 

重要な詳細は、制約を評価する前にウィンドウが更新されるため、合計は常に最後の値を正確に反映することです。$k$日々。 これにより、スライディング範囲でのオフバイワンエラーが回避されます。

 ## 特殊なケース

 重要なエッジケースの 1 つは次のような場合です。$k = 1$。 ウィンドウには現在の日のみが含まれるため、制約はその日の値になります。$i$少なくとも$i$。 アルゴリズムは正確に割り当てます$i$、三角形の成長シーケンスを生成します$1,2,3,\dots,n$。 スライディング ウィンドウは常に要件に正確に一致するため、追加の調整は必要ありません。 

もう 1 つのエッジケースは次のような場合です$k \ge n$。 ウィンドウは古い値を決して破棄しないため、合計は常に累積されます。 この状況では、毎日に 1 を割り当てるのが最適です。$i$まさに$i$、これは常に必要なストリークと一致します。 

さらに微妙なケースが発生するのは、$k$小さいです、例えば$k = 2$。 初期の頃は次のように動作します$k \ge n$ただし、ウィンドウがいっぱいになると、古い小さい値は破棄されます。 サンプル 1 に見られるように、ここでアルゴリズムがより大きな値の注入を開始します。当日の貪欲な修正により、以前の割り当てを再検討することなく実現可能性が保証されます。
