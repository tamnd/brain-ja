 ## 解決策
 ## 問題の理解

 サイズの配列から始めます$n$ここで、各ポジションには最初にちょうど 1 つのボールが含まれており、そのボールは開始位置によって一意に識別されます。 だから骨壷$i$最初はボールを持っている$i$、そしてタスクは、一連のセグメント再配置操作の後に各元のボールがどこに終わるかを決定することです。 

各操作には連続した URN ブロックが必要です$[from_i, from_i + count_i - 1]$、それらの壺の中に現在入っているすべてのボールを抽出し、それらを別の連続したブロックに配置します。$[to_i, to_i + count_i - 1]$左から右への配置を維持しながら、順番に並べます。 つまり、ポジションからのボール$from_i + k$位置に移動します$to_i + k$あらゆる人にとって$k$セグメントの長さで。 

重要な点は、これらの操作は値の配列への独立した書き込みではなく、現在の内容の完全なセグメントの並べ替えであるということです。 後の操作はすでに変更された配置に作用するため、問題は事実上、ラベルの配列に対する区間順列のシーケンスを構成することになります。 

この制約により、操作ごとに要素に直接触れるシミュレーションから遠ざけられます。 と$n \le 10^5$そして$m \le 5 \cdot 10^4$、操作ごとに各要素を移動する単純なアプローチでは、パフォーマンスが低下する可能性があります。$O(nm)$のオーダーです。$5 \cdot 10^9$実現可能性をはるかに超えた、最悪の場合の作戦。 

微妙なエッジケースは、重複した動きや繰り返しの動きから発生します。 セグメントは複数回移動でき、後の移動で部分的に元に戻したり、以前の移動のルートを変更したりできます。 たとえば、$n = 3$:```
1 2 3
1 1 2
1 2 1
```最初の動きの後、ボールは次のようになります。`[2,3,1]`。 2回目の移動の後、移動します`[3]`位置 1 に戻り、譲ります`[3,2,1]`。 単純な「操作を通じて各ボールを独立して追跡する」アプローチでは、セグメントの独立性を前提としている可能性がありますが、各操作は元のインデックスではなく、現在のグローバルな配置に依存します。 

もう 1 つの注意が必要な状況は、ソースと宛先が重なっている場合で、暗黙的な一時バッファリング動作が発生する可能性があります。 移動は最初に持ち上げてから配置するように定義されているため、抽出中に値が上書きされないため、配列からの読み取り中に配列に直接書き込むインプレース シミュレーションでは、静かにデータが破損します。 

## アプローチ

 直接シミュレーションでは、ボール ラベルの配列が維持され、操作ごとに明示的にセグメントが抽出され、それが宛先に書き込まれます。 これは正しいですが、各操作にコストがかかるため遅すぎます。$O(\text{count}_i)$、合計移動量は次のように蓄積されます。$O(nm)$最悪の場合。 

重要な観察は、進化する配列の内容を実際に明示的に追跡する必要がないということです。 各ボールは常にその現在位置へのポインタを持ち、すべての操作は 2 つの間隔の間の全単射のみを記述します。 値を移動する代わりに、逆に考えることができます。最終的な配列内の各位置は、それがどの初期位置から来たのかを知りたいと考えています。 

これは、現在の位置から元の位置へのマッピングを維持することを示唆しています。 そもそも、これがアイデンティティなのです。 各演算では範囲間の置換が適用され、位置に対する関数合成として表すことができます。 私たちが必要とする構造は、内部の順序を維持しながらセグメントを切り取って別の場所に貼り付ける機能、そしてこれを多くの操作にわたって効率的に実行できる機能です。 

これをモデル化する標準的な方法は、分割と連結をサポートする動的シーケンス構造内のノードとして位置を扱うことです。 ただし、より単純で直接的なアプローチが存在します。配列を維持します。`src[i]`「どの初期位置が現在最終位置 i を占めているか」を意味します。 各操作でスライスがコピーされます。`src[from:from+len]`の中へ`to:to+len`。 コピーはまだなので、$O(n)$、各セグメントが全体として上書きされ、各操作に補助配列を使用できることを利用しない限り、再びボトルネックに直面します。 

重要な改良点は、単一ステップ内の複数の操作にわたる永続性が必要ないことです。 各操作は、現在の配列から読み取り、一時バッファーに書き込み、結果をコミットすることで適用できます。 要素の総数はたったの$n$、各要素は操作ごとに制限された回数だけ書き換えられますが、すべての操作にわたって操作ごとの合計作業量は線形のままであり、最悪の場合でも依然として大きすぎます。 したがって、より構造的な圧縮が必要です。 

代わりに、視点を完全に反転します。つまり、元の各ボールの現在の位置を維持します。 させて`pos[x]`ボールの位置になる`x`。 各操作では、影響を受けるすべてのボールを直接更新するのは簡単ではありませんが、配列をセグメントの順列として表すことができ、各セグメントの動きは 2 つの間隔割り当ての構成になります。 これは、範囲のアフィン「コピー元」操作を格納する遅延伝播を使用してセグメント ツリーを維持することと同等です。 それぞれの操作は、$O(\log n)$要素を個別に操作するのではなく、構造化された割り当てを使用して範囲を更新するためです。 

したがって、問題は、「このセグメントは、デルタによってシフトされた別のセグメントから値を取得します」を格納する遅延伝播を備えたセグメント ツリーを介して実装される、インデックスの動的マッピングに対する範囲割り当て + ポイント クエリに帰着します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション |$O(nm)$|$O(n)$| 遅すぎる |
 | 範囲コピー マッピングを使用したセグメント ツリー |$O((n + m)\log n)$|$O(n \log n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 ポジションごとにセグメントツリーを維持します$1 \ldots n$ここで、各ノードは連続した間隔を表します。 各ノードは、均一な「ソース間隔マッピング」を持っているかどうかを格納します。つまり、そのノード内のすべてのリーフが現在、シフトされている可能性がある初期インデックスの連続セグメントを指していることを意味します。 

1. 構造体を初期化して、次の位置に配置します。$i$ソースにマップする$i$。 これは、セグメント ツリーの葉の ID 割り当てとして表されます。 
2. 各操作ごとに$(count, from, to)$、間隔のマッピングをコピーすると解釈します。$[from, from+count-1]$の中へ$[to, to+count-1]$。 これは、スカラーではなく、構造化された値の範囲の割り当てです。 
3. まずセグメント ツリーにクエリを実行して、ソース インターバルの完全な構造を抽出します。$[from, from+count-1]$。 これにより、再利用できる表現が得られます。 
4. 次に、この抽出した構造を宛先区間に割り当てます。$[to, to+count-1]$。 割り当てにより、その宛先セグメント内の以前のマッピングが上書きされます。 
5. 遅延伝播により、必要な場合を除き、構造が個々のリーフに拡張されなくなります。 内部ノードにはセグメント全体のマッピングが保存され、クエリが部分的に影響を受けるノードに到達した場合にのみ、構造が下方にプッシュされます。 
6. すべての操作を処理した後、最終トラバースを実行して各位置を解決します$i$最終的な元のインデックスに追加されます。 これは、各位置でセグメント ツリーをクエリすることによって行われます。 

### なぜ効果があるのか

 すべての操作は 2 つの等しい長さの間隔間の全単射であり、位置の 1 対 1 のマッピングを定義することを意味します。 セグメント ツリーは、配列のセグメントへの分割を維持し、最終位置から最初の位置までの一貫した間隔のマッピングを常に表します。 ある区間から別の区間にセグメント マッピングをコピーするとき、内部順序が維持され、無関係なセグメントが混在しません。 遅延伝播により、必要な場合にのみ部分的な重複が解決され、一貫性のないマージが防止されます。 更新のたびに区間全体が構造的に同一のマッピングに置き換えられるため、どのポジションも有効な原点を失うことはなく、これらの区間マッピングを繰り返し合成することで、ボールの最終的な並べ替えが正しく表現されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("l", "r", "left", "right", "tag", "has_tag")
    def __init__(self, l, r):
        self.l = l
        self.r = r
        self.left = None
        self.right = None
        self.tag = 0
        self.has_tag = True  # initially identity mapping

def build(l, r):
    node = Node(l, r)
    if l == r:
        node.tag = l
        return node
    m = (l + r) // 2
    node.left = build(l, m)
    node.right = build(m + 1, r)
    return node

def push(node):
    if not node.has_tag or node.l == node.r:
        return
    mid = (node.l + node.r) // 2
    node.left.tag = node.tag
    node.left.has_tag = True
    node.right.tag = node.tag + (mid + 1 - node.l)
    node.right.has_tag = True
    node.has_tag = False

def update(node, l, r, src_l, delta):
    if node.r < l or node.l > r:
        return
    if l <= node.l and node.r <= r:
        node.tag = src_l + (node.l - l)
        node.has_tag = True
        return
    push(node)
    update(node.left, l, r, src_l, delta)
    update(node.right, l, r, src_l, delta)

def query(node, idx):
    if node.has_tag:
        return node.tag + (idx - node.l)
    push(node)
    if idx <= node.left.r:
        return query(node.left, idx)
    else:
        return query(node.right, idx)

n, m = map(int, input().split())
root = build(1, n)

for _ in range(m):
    cnt, frm, to = map(int, input().split())
    update(root, to, to + cnt - 1, frm, 0)

res = [0] * n
for i in range(1, n + 1):
    res[i - 1] = query(root, i)

print(*res)
```セグメント ツリーは、各ノードが最終位置の連続した間隔を表すように構築されます。 の`tag`フィールドは、連続マッピングの開始ソース インデックスをエンコードします。 ノードが でマークされている場合、`has_tag`、これは、その区間全体が初期インデックスからの単純な等差数列マッピングであることを意味するため、個々のリーフは明示的なストレージを必要としません。 

更新操作は、ソース間隔から宛先間隔への線形マッピングを割り当てます。 マッピングは常に連続していて位置合わせされているため、このコンパクトな形式ではデルタ パラメーターは使用されません。 オフセットは次から直接計算されます。`src_l`そして宛先インデックス。 プッシュ操作により、下降時にセグメントレベルのマッピングが一貫した子マッピングに正しく分割されることが保証されます。 

クエリは、タグ付けされたセグメントが見つかるまで降順で単一の位置を解決し、レベルごとに一定時間で元のインデックスを再構築します。

 ## 特殊なケース

 エッジ ケースの 1 つは、セグメントがそれ自体の上に移動される場合です。 入力の場合:```
3 1
2 1 1
```この操作により、位置 1-2 が 1-2 にコピーされます。 セグメント ツリーは、それ自体を指すタグでその間隔をマークするため、位置 1 と 2 に対するクエリは変更されていないインデックスを返しますが、位置 3 は変更されません。 更新により同じ間隔で ID の進行が割り当てられるため、マッピングの一貫性が保たれます。 

もう 1 つのケースは、後の操作が前の操作を部分的に上書きする重複書き込みです。 のために：```
4 2
3 1 2
2 2 3
```最初の操作はブロックを位置 2 ～ 4 にシフトし、次に 2 番目の操作で位置 2 ～ 3 を再度上書きします。 この構造により、2 番目の更新によってその間隔内で前のタグが完全に置き換えられるため、混合状態が存続することはありません。 各クエリは、最新のカバータグを通じて解決されます。 

最後のコーナーケースは単一要素の動きです。`count = 1`。 これらはポイント割り当てに縮退し、セグメント ツリーはそれらを直接リーフ更新に還元します。 範囲構造が壊れていないため、マッピングの一貫性が保たれ、標準の範囲更新ロジックを超える特別な処理は必要ありません。
