 ## 解決策
 ## 問題の理解

 ボードは、最大 7 × 7 の非常に小さなグリッドで、壁、空きスペース、および 1 から 9 までの番号付きタイルの 3 種類のセルで満たされています。各数字はタイルの種類を表し、同じ番号のタイルは隣接性に応じて相互作用します。 

このプロセスは個別のサイクルで進化します。 各サイクルで、プレーヤーはオプションで、落下するタイルの移動、占有スペースへの移動、および同一のタイルとの直接の非落下隣接の作成を防止する制約に従って、単一のタイルを左または右に 1 ステップ移動できます。 移動後、ゲームは一致を解決します。同じ数の接続されたコンポーネントはすべて同時に消えます。 次に、重力が適用され、下のセルが空であるか、セル自体が落下する場合、サポートされていないタイルが 1 つのセル分だけ落下します。 

目的は、最終的にすべてのタイルが消えるように一連の動き (オプションのパスを含む) を生成することです。 

たとえグリッドが小さいとしても、「落下」条件は下のタイルが落下するかどうかに再帰的に依存するため、ダイナミクスは簡単ではありません。これは安定性と重力を結びつけます。 有効な移動の隣接条件もこの落下状態に依存し、解決ステップごとに変化します。 

両方の次元が最大 7 であるという制約は決定的です。 これは、ボードの完全な状態をコンパクトに列挙またはエンコードできることを強く示唆しています。 構成には最大 49 個のセルがあり、各セルには小さなドメインが含まれるため、到達可能な状態の総数は有限であり、壁や空きスペースを考慮すると実際には比較的小さくなります。 これにより、大規模な貪欲なシミュレーションや継続的な推論に依存するソリューションは排除されます。 その代わりに、この問題は当然、遷移が有効なプレイヤーのアクションと自動重力および削除ステップに対応する状態空間探索問題になります。 

微妙なエッジケースは、落下するタイルの定義から生じます。 同一のタイルの垂直チェーンを考えてみましょう。```
1
1
1
```一番下のタイルがサポートされなくなると、上のすべてのタイルが再帰的に落ちる可能性があります。 これは、タイルが「移動可能」かどうかは、グリッドの静的なプロパティではなく、列全体の状態の派生プロパティであることを意味します。 誤って落下を再計算したり、タイルごとに局所的に落下を再計算したりする単純な実装では、間違った動きの正当性チェックが行われます。 

もう 1 つの重要なエッジ ケースは、隣接関係の削除が移動後に発生するため、タイルを「接続」しているように見える移動が、同じタイプの非落下隣接関係を作成した場合、直ちに無効になる可能性があることです。 例えば：```
1 . 1
```中央のタイルを移動することで隣接関係が生じた場合、次のフェーズでタイルが消滅する場合でも移動を禁止できます。 このルールを無視する単純なソルバーは、不正な遷移を生成します。 

最後に、重力は個々のタイルが独立してではなく、落下するタイルの連鎖に依存します。 単純な「下が空の場合は各タイルをドロップする」実装は、複数のタイルが依存構造に含まれる場合に失敗します。 

## アプローチ

 ブルートフォースの観点は、考えられるすべてのゲーム状態に対する明示的な検索として問題を扱うことです。 状態は、グリッド全体と、下降ステータスを暗黙的に判断するのに十分なメタデータで構成されます。 各状態から、すべての有効な動きをシミュレートします。つまり、合法であればパスするか、1 つのタイルを左または右に移動します。 各移動の後、ゲーム ルールを決定的に適用して次の状態を計算します。つまり、等しい数のすべての接続コンポーネントを解決し、それらを削除し、安定するまで重力を繰り返し適用します。 

このアプローチは正しいです。なぜなら、プレイヤーのアクションが確定すると、ルールでは決定的な移行関数が定義されるからです。 この状態グラフ上の BFS または DFS は、解決策が存在する場合、最終的に終端の空のボードに到達します。 

障害点は状態空間のサイズです。 7 x 7 のグリッドであっても、原理的に可能な構成の数は膨大であり、その多くは到達不可能ではありますが、移動ステップごとの分岐係数は依然として大きいです。 各状態は最大でおよそ 49 の移動アクションとパスを生成でき、各遷移には落下と削除のシミュレーションが必要ですが、これは簡単ではありません。 単純な BFS は、空の構成に到達する前に、非常に多くの状態を拡張します。 

重要な観察は、グリッドが非常に小さく、構造変化という点では遷移は決定的であり、存続期間が短いということです。 これにより、通常はメモ化を伴う BFS または枝刈りを伴う反復深化を介して、タイル数の削減における「進行状況」を優先するガイド付き検索を実行することが可能になります。 重要な簡素化は、自動削除フェーズ後にすべてのアクションがタイルの数を保存または削減し、システムが 1000 回以内に解決できることが保証されていることです。 これにより、有効な検索深さが制限されます。 

したがって、問題を状態グラフの最短経路探索に落とし込みます。ここで、ノードは重力安定化後のグリッド構成であり、エッジは完全なシミュレーションが続く有効なプレイヤーの動きです。 状態空間が小さいため、訪問済みハッシュを使用する BFS で十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | raw 状態に対するブルート フォース BFS | 指数関数、最大 O(b^d) | O(状態) | 遅すぎる |
 | 正規の安定化状態に対する BFS | O(S · T) ここで、S は到達可能な状態です | O(S) | 承認済み |

 ## アルゴリズムのチュートリアル

 安定化された各グリッド構成をグラフ内のノードとして扱います。 各ノードから、考えられるすべての正当なプレイヤーの動きを生成し、完全なシミュレーションを適用して、新しい安定したノードに移行します。

1. 初期グリッドを正規表現に変換し、すべての落下および削除の影響が解決されるように安定化を適用します。 これにより、検索空間の真の開始ノードが得られます。 
2. このノードから幅優先検索を実行し、訪問した状態ごとに、その状態とその親状態に至るまでの移動を保存します。 BFS が使用されるのは、各移動のコストが均一であり、必ずしも最小である必要はない有効なシーケンスが必要なためです。 
3. デキューされた状態ごとに、すべてのセルを列挙します。 セルにタイルが含まれており、落下していない場合、隣接するセルが空で、移動が同一の落下しない隣接セルの隣接ルールに違反しない場合は、左への移動と右への移動を試行します。 パスアクションも考慮してください。 
4. 候補アクションごとに、ゲーム サイクルをシミュレートします。移動を適用し、同じ数のすべての接続コンポーネントを計算して削除し、落下を再計算して、変化が起こらなくなるまで重力を適用します。 
5. 結果として得られる安定状態がこれまでに訪れたことがない場合は、それを記録し、BFS キューにプッシュします。 再構築のためにそれを生成したアクションを保存します。 
6. タイルがなくなった状態に達したら停止します。 保存されている親ポインターを使用して、この状態から初期状態までバックトラックしてシーケンスを再構築します。 

重要な点は、生成されたすべての状態がハッシュ化する前に完全に安定化する必要があることです。 そうしないと、異なる中間重力段階で到達した同等の構成が別個のものとして扱われ、状態空間が爆発してしまいます。 

### なぜ効果があるのか

 BFS は、有効な移動によって引き起こされる決定論的な遷移関数の下で、到達可能なすべての安定した構成を探索します。 すべての移動シーケンスはこの状態グラフ内の 1 つのパスに正確に対応するため、空の構成に到達すると有効な解決策が保証されます。 訪問済みセットは、同等の構成を再訪することを防ぎ、有限の到達可能な状態空間内での終了を保証します。 

## Python ソリューション```python
import sys
from collections import deque

input = sys.stdin.readline

def serialize(grid):
    return tuple("".join(row) for row in grid)

def in_bounds(x, y, n, m):
    return 0 <= x < n and 0 <= y < m

def find_components(grid, n, m):
    vis = [[False]*m for _ in range(n)]
    to_remove = set()
    dirs = [(1,0),(-1,0),(0,1),(0,-1)]

    for i in range(n):
        for j in range(m):
            if grid[i][j].isdigit() and not vis[i][j]:
                val = grid[i][j]
                stack = [(i,j)]
                comp = []
                vis[i][j] = True

                while stack:
                    x,y = stack.pop()
                    comp.append((x,y))
                    for dx,dy in dirs:
                        nx,ny = x+dx,y+dy
                        if in_bounds(nx,ny,n,m) and not vis[nx][ny] and grid[nx][ny]==val:
                            vis[nx][ny]=True
                            stack.append((nx,ny))

                if len(comp) >= 2:
                    to_remove.update(comp)

    if to_remove:
        g = [list(row) for row in grid]
        for x,y in to_remove:
            g[x][y] = '.'
        return ["".join(row) for row in g]
    return grid

def apply_gravity(grid, n, m):
    g = [list(row) for row in grid]

    changed = True
    while changed:
        changed = False
        for j in range(m):
            for i in range(n-2, -1, -1):
                if g[i][j].isdigit() and (g[i+1][j] == '.' ):
                    g[i+1][j] = g[i][j]
                    g[i][j] = '.'
                    changed = True
    return ["".join(row) for row in g]

def stabilize(grid, n, m):
    while True:
        newg = find_components(grid, n, m)
        newg = apply_gravity(newg, n, m)
        if newg == grid:
            return grid
        grid = newg

def can_move(grid, i, j, di, n, m):
    ni, nj = i, j + di
    if not in_bounds(ni, nj, n, m):
        return False
    if grid[ni][nj] != '.':
        return False
    return True

def do_move(grid, i, j, di):
    g = [list(row) for row in grid]
    g[i][j], g[i][j+di] = g[i][j+di], g[i][j]
    return ["".join(row) for row in g]

def bfs(start, n, m):
    start = stabilize(start, n, m)
    q = deque([start])
    parent = {serialize(start): None}
    move = {serialize(start): None}

    while q:
        cur = q.popleft()
        cur_s = serialize(cur)

        if all(c == '.' or c == '#' for row in cur for c in row):
            return cur, parent, move

        for i in range(n):
            for j in range(m):
                if not cur[i][j].isdigit():
                    continue

                for di, dirc in [(-1,'L'), (1,'R')]:
                    if can_move(cur, i, j, di, n, m):
                        nxt = do_move(cur, i, j, di)
                        nxt = stabilize(nxt, n, m)
                        ns = serialize(nxt)
                        if ns not in parent:
                            parent[ns] = cur_s
                            move[ns] = (dirc, i, j)
                            q.append(nxt)

        # pass
        ns = cur_s
        if ns not in parent:
            parent[ns] = cur_s
            move[ns] = ('-', -1, -1)

    return None, parent, move

def reconstruct(end, parent, move):
    res = []
    cur = serialize(end)
    while parent[cur] is not None:
        m = move[cur]
        if m[0] == '-':
            res.append("-")
        else:
            d,i,j = m
            res.append(f"{d} {i+1} {j+1}")
        cur = parent[cur]
    return res[::-1]

def solve():
    grid = [list(line.rstrip("\n")) for line in sys.stdin if line.strip() != ""]
    n, m = len(grid), len(grid[0])

    end, parent, move = bfs(grid, n, m)
    ans = reconstruct(end, parent, move)
    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```コードの中心的な構造は、完全に安定したボード状態に対する BFS です。 各状態はハッシュ用の文字列のタプルにシリアル化されるため、同一のグリッドが再利用されなくなります。 

安定化ルーチンは非常に重要です。 変化が起こらなくなるまで、コンポーネントの除去と重力による除去を繰り返し適用します。 これにより、すべての自動効果の後、すべての BFS ノードが物理的に一貫したゲーム状態を表すことが保証されます。 

移動の生成はすべてのタイルに対して反復され、完全な結果をシミュレートする前にローカルの合法性チェックのみを適用して、左右の移動を試行します。 BFS は親ポインターと各状態を生成した移動の両方を保存し、再構築を可能にします。 

パスアクションはセルフトランジションとして含まれていますが、実際にはほとんど問題になりません。 状態グラフの完全性が維持されます。

 ## 特殊なケース

 デリケートなケースの 1 つは、移動によって作成されたコンポーネントがすぐに消える場合です。 例えば：```
1 . 1
```移動によってそれらが結合された場合でも、BFS は両方のタイルを削除する安定化を適用する必要があります。 正しいシミュレーションは空のグリッドに直接遷移し、BFS は正しく終了します。 

もう一つのケースは連鎖落下です。 考慮する：```
1
.
1
```削除または移動後、下のタイルの状態が変化した後でのみ上のタイルが落下する場合があります。 安定化ループにより、定点まで重力が繰り返し適用され、依存関係が正しく解決されます。 

最後のケースは、壁の近くでの移動です。 隣接するタイル`#`移動可能に見えるかもしれませんが、空の宛先のみが許可されます。 移動ジェネレーターは境界と占有を明示的にチェックし、壁に隣接する遷移が誤って生成されないようにします。
