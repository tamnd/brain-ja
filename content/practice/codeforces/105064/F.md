 ## 解決策
 ## 問題の理解

 各兵士は数直線上の整数の位置に座っており、射撃の強さを持っています。 ある位置にモンスターが出現し、飛距離に応じて飛来する弾を弱めるシールドを装備している。 兵士が発砲した弾丸$i$力から始まる$p_i$、走行距離後$t$、その有効電力は$p_i - t$。 弾丸がモンスターに到達したときに、その残存パワーが少なくともシールド強度以上であれば、その弾丸はヒットとしてカウントされます。$s$。 

モンスターの位置を固定する場合$d$、距離条件が満たされている場合、兵士はヒットに貢献します。$|a_i - d| \le p_i - s$が成立する。 Each query does not ask for this value at a single point. Instead, it asks for the sum of this hit count over every monster position in an interval$[l, r]$。 したがって、セグメント内のすべてのポジションにわたる貢献を効果的に集計しています。各兵士は、そのクエリ内のパワーとシールドの強さによって決定されるポジションの範囲にわたって貢献しています。 

兵士とクエリの両方に関して制約は大きく、それぞれ最大 100 万人ですが、座標空間は小さいため、すべての位置が次の位置にあります。$[1, 2000]$, and shield strength is also bounded by 1000. This mismatch is the central hint. 入力サイズが大きくても、ドメインは小さいため、ソリューションではソルダーやクエリではなく位置を圧縮または事前計算する必要があります。 

A naive approach would try to evaluate each query by iterating over all positions in$[l, r]$そして兵士の皆さん。 それはおおよそ次のことにつながります$10^6 \times 2000 \times 10^6$最悪の場合の作戦は実行可能をはるかに超えています。 

この条件を無視すると、さらに微妙な落とし穴が発生します$p_i - s$。 兵士の力が盾の強さよりも低い場合、それはどこでも何の貢献もありません。 もう 1 つのよくある間違いは、距離が対称であるため、各兵士が中心となる間隔に影響を与えることを忘れていることです。$a_i$、一方的な範囲ではありません。 

## アプローチ

 重要な観察は、地位に貢献する兵士の条件は次のとおりであるということです。$d$範囲制約として書き換えることができます$d$。 から$$|a_i - d| \le p_i - s,$$私たちはその兵士を手に入れます$i$すべてのポジションに貢献する$d$合間に$$[a_i - (p_i - s),\; a_i + (p_i - s)].$$もし$p_i < s$、この間隔は空です。 

したがって、各兵士はその間隔内のすべての位置に +1 を貢献します。 次に、クエリは次のように尋ねます。$d \in [l, r]$、これらの間隔のうち何個がカバーされるか$d$、すべてを合計した$d$。 これは、セグメントにわたるカバレッジ関数を合計することに相当します。 

配列を定義する$cover[d]$間隔が含まれる兵士の数として$d$。 この場合、各クエリは単純に次のようになります。$$\sum_{d=l}^{r} cover[d].$$したがって、タスクはこのカバレッジ配列を効率的に構築することになります。 

位置は 2000 までしかないので、差分配列を使用できます。 各兵士について、左のエンドポイントに +1 を追加し、右のエンドポイントの後に -1 を追加します。 プレフィックスの合計後、すべての位置でカバレッジが得られます。 このカバレッジ配列の 2 番目のプレフィックス合計により、O(1) の各クエリに答えることができます。 

この総当り攻撃は、兵士と位置のすべてのペアを直接評価するため機能しますが、クエリ全体での反復が膨大であるため失敗します。 各兵士が連続した影響範囲を形成しているという観察により、構造全体を接頭辞の合計に圧縮することができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n \cdot q \cdot 2000)$|$O(2000)$| 遅すぎる |
 | 差分 + プレフィックスの合計 |$O(n + q + 2000)$|$O(2000)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 配列を作成する`diff`サイズは約 2005 で、ゼロに初期化されます。 これにより、個々の投稿ではなく間隔の更新が保存されます。 
2. 兵士ごとに$i$、その有効半径を計算します$r_i = p_i - s$。 もし$r_i < 0$、どの位置にも到達できないためスキップします。 
3. それ以外の場合は、カバレッジ間隔を計算します。$[L, R] = [a_i - r_i, a_i + r_i]$。 この間隔を有効な座標範囲に固定します$[1, 2000]$、この範囲外の位置は無関係であるためです。 
4. に 1 を追加して差分配列を更新します。$L$で 1 を減算します。$R + 1$。 これは、兵士がその間隔内のすべてのポジションを反復処理することなく貢献していることをエンコードします。 
5.変換`diff`に`cover`プレフィックスの合計を使用した配列。 それぞれのポジションで$d$、`cover[d]`は、そのポイントをカバーするアクティブな間隔の数になります。 
6. 2 番目のプレフィックス合計配列を構築する`pref`、 どこ`pref[d] = pref[d-1] + cover[d]`。 これにより、カバレッジにわたる範囲合計クエリが可能になります。 
7. 各クエリについて$(l, r, s)$、出力`pref[r] - pref[l-1]`。 

正確かどうかは、幾何学的距離の制約を間隔の適用範囲に置き換えることにかかっています。 各兵士は、有効な間隔内のすべての位置に 1 つのユニットを正確に提供し、プレフィックスの合計により、セグメントにわたるカウントと集計の両方が保持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    p = list(map(int, input().split()))

    MAX = 2000
    diff = [0] * (MAX + 3)

    for i in range(n):
        r = p[i]
        if r <= 0:
            continue
        L = a[i] - r
        R = a[i] + r

        if L > MAX or R < 1:
            continue

        if L < 1:
            L = 1
        if R > MAX:
            R = MAX

        if L <= R:
            diff[L] += 1
            diff[R + 1] -= 1

    cover = [0] * (MAX + 2)
    cur = 0
    for i in range(1, MAX + 1):
        cur += diff[i]
        cover[i] = cur

    pref = [0] * (MAX + 2)
    for i in range(1, MAX + 1):
        pref[i] = pref[i - 1] + cover[i]

    out = []
    for _ in range(q):
        l, r, s = map(int, input().split())
        if l > r:
            out.append("0")
        else:
            out.append(str(pref[r] - pref[l - 1]))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、前処理フェーズとクエリ応答が分離されます。 差分配列はすべての兵士の範囲を線形時間でエンコードし、プレフィックスの合計によりすべての座標でのカバレッジを回復します。 2 番目のプレフィックス合計により、カバレッジ配列が O(1) 範囲クエリをサポートする構造に変わります。 

微妙な点は、間隔を固定することです。$[1, 2000]$。 これがないと、負のインデックスまたは範囲外の更新により、プレフィックス構造が静か​​に破損します。 もう 1 つの詳細は、確実に使用することです。$R+1$これが、配列のサイズが 2000 よりわずかに大きい理由です。

 ## 特殊なケース

 主なエッジケースは次のような場合です$p_i < s$。 この場合、有効半径は負になり、兵士は何も貢献する必要はありません。 アルゴリズムは、そのようなソルジャーをスキップすることでこれを明示的に処理し、次のような無効な間隔を防ぎます。$[a_i + 1, a_i - 1]$。 

もう 1 つのケースは、間隔が座標範囲を超えて広がる場合です。 大きなパワーを持つ位置 1 のソルジャーは、1 未満の左エンドポイントを生成する可能性があります。クランプ ステップにより、寄与が有効なインデックス内にのみ適用されることが保証され、ドメインの外側にあるものはすべてクエリに無関係であるため、差分配列は一貫したままになります。 

最後に、同じ位置にいる多くの兵士の重複する間隔により、大きなカウントが生成される可能性があります。 プレフィックスベースの構築では、各ソルジャーが明示的に展開されるのではなく差分配列に一度エンコードされるため、オーバーフローや繰り返しを行わずにこれらの重複を自然に合計します。
