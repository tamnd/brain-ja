 ## 解決策
 ## 問題の理解

 メッセージを表す整数のシーケンスと、キーを表す別の短いシーケンスが与えられます。 どちらのシーケンスも 0 から c マイナス 1 までの固定モジュラー範囲にわたっており、すべての加算はモジュロ c をラップアラウンドします。 

暗号化は、繰り返されるスライディング プロセスとして定義されます。 左から右の各位置 i で、i から始まる長さ m のウィンドウを取得し、そのウィンドウに要素ごとにキーを追加します。 これはシングル パス更新ではありません。後のウィンドウにはすでに変更された値が表示されるため、各操作は将来のウィンドウにすぐに影響します。 

出力は、これらの重複するウィンドウ更新がすべて適用された後の配列の最終状態です。 

主な問題点は、各ポジションが複数のウィンドウに参加していることです。 寄与の観点から考えると、各キー値 b[j] は、そのインデックスをカバーするウィンドウの数に応じて多くの位置に追加されます。 

この制約により、私たちは単純なシミュレーションから遠ざけられます。 n が 100,000 までの場合、n マイナス m プラス 1 ステップのそれぞれが m 要素を更新する直接シミュレーションでは、最悪の場合でも約 10^10 の演算が発生し、これは Python の 2 秒の制限をはるかに超えます。 最適化された C++ であっても、これは限界に達します。 

オーバーラップ動作から微妙なエッジケースが発生します。 更新は順次適用されるため、単純な解釈では、元の配列に対して各ウィンドウを独立して計算できると想定する可能性があります。 それは間違いです。 

たとえば、次のことを考えてみましょう。```
n = 4, m = 2, c = 5
a = [0, 0, 0, 0]
b = [1, 2]
```元の配列にすべてのウィンドウを誤って適用すると、位置 2 は 2 番目のウィンドウからのみ寄与を受け取ることになります。 実際には、重複伝播により、以前の更新による間接的な影響も受けます。 この違いこそが、単純な畳み込みのような思考が慎重に扱われなければならない理由です。 

## アプローチ

 強引な解釈は簡単です。 0 から n から m を引いた値までの各ステップ i をシミュレートし、ステップごとに b[j] を a[i + j] に加算します。 これは定義を直接反映しているため、これは正しいです。 ただし、各ステップは m 個の要素に触れるので、合計作業量は最悪の場合でも n 倍になり、両方とも 100,000 回の場合は 10^10 回の操作に達します。 

重要な構造上の観察は、更新は重複しているものの、各更新は追加的で独立しているということです。 すべての演算は c を法とする固定値を加算するだけであるため、順序によって各位置の最終的な合計は変わりません。 これは、プロセスをシミュレートする代わりに、各 b[j] が各位置に何回寄与するかをカウントできることを意味します。 

配列内の位置 i を固定します。 これは、開始インデックス s が s ≤ i ≤ s + m − 1 を満たすすべてのウィンドウに含まれます。その不等式は、[i − m + 1, i] の s になります。 したがって、位置 i に b[j] を与える有効なウィンドウの数は、i − s = j の場合にそのような s がいくつ存在するかによってのみ決まります。 

i − s = j を書き直すと、s = i − j となります。 したがって、位置 i は、ウィンドウ開始 i − j が有効である場合、つまり 0 ≤ i − j ≤ n − m である場合に限り、寄与 b[j] を受け取ります。 これにより、プロセス全体が直接累積問題に変換され、これを使用して線形時間で計算できます。
