 ## 解決策
 ## 問題の理解

 私たちは、すべての天文台に対して 1 つの減少しないカウンターを維持します。 メンバーはある時点で参加し、最大 3 つの異なる天文台を選択し、合計少なくとも 3 つの観測点を要求します。`y`それらの天文台から数分です。 メンバーが参加した後に収集されたビデオのみが、そのメンバーの目標にカウントされます。 

アップデートで追加される場合`w`天文台まで数分`x`を使用しているすべてのまだアクティブなメンバー`x`取得します`w`その天文台からさらに数分。 この更新中に初めて合計が目標に達したメンバーを正確に報告する必要があります。 報告された ID はさらにソートする必要があります。 

入力は意図的にオンラインで行われます。 値`last`前のタイプ 2 イベントによって報告されたメンバーの数に等しいが、現在のイベントを XOR デコードするために使用されます。 最初のクエリでは、`last = 0`。 タイプ 1 イベントには、その目標とすべての観測点のインデックスがあり、XOR 演算されます。`last`一方、タイプ 2 イベントには、観測値と増分値の両方が XOR 演算されます。`last`。 イベントの値を使用する前に、イベントをデコードする必要があります。 

公式の問題には、`n,m <= 2 * 10^5`、最大でも目標値と更新値`10^6`、512 MB のメモリで 2 秒の時間制限。 これにより、更新のたびにすべてのメンバーをスキャンするアルゴリズムが直ちに排除されます。 と`2 * 10^5`イベント、二次作業が発生する可能性があります`4 * 10^10`最悪の場合の運用は現実的なものをはるかに超えています。 

また、各メンバーが使用する天文台は最大 3 つであるという便利な構造上の制限もあります。 この一定の境界が、より高速なソリューションへの鍵となります。 最大でも 3 つの天文台が存在するため、1 人のメンバーのアラームが目覚めるたびに、そのメンバーに属するすべての天文台を検査する余裕があります。 

いくつかの特殊なケースは、誤って処理されやすいものです。 まず、メンバーが参加する前に収集されたビデオはカウントされてはなりません。 考慮する：```
1 3
2 1 5
1 3 1 1
2 1 3
```最初の更新により、天文台 1 の所要時間は 5 分になりますが、まだメンバーがいないため、答えは次のようになります。`0`。 その後、メンバーはゴール 3 に加わります。その前の 5 分間はカウントされません。 最後の更新により、新しい 3 分が追加されるため、正しい出力は次のようになります。```
0
0
1 1
```すべてのメンバーの目標をグローバル天文台の合計と単純に比較するソリューションでは、メンバーが参加した直後に誤って完了してしまいます。 

第二に、完了したメンバーは永久に消滅しなければなりません。 例えば：```
1 3
1 2 1 1
2 1 2
2 0 0
```メンバーが参加した後の最初の更新にはちょうど 2 分かかるため、最初のクエリは次のように出力します。`1 1`。 以来`last = 1`、最後の暗号化された更新`2 0 0`実際には天文台を意味します`1`、増分`1`。 メンバーはすでに完了しているため、正しい出力は次のようになります。```
1 1
0
```メンバーのアラームをアクティブのままにする不注意な実装では、再度報告されることになります。 

第三に、XOR デコードは前の回答数に依存します。 例えば：```
1 4
1 1 1 1
2 1 1
1 0 1 0
2 0 0
```最初のメンバーは 2 番目のイベント後に完了するため、`last = 1`。 したがって、3 番目のイベントは次のようにデコードされます。`1 0 1 0`目標 1 と観測所 1 を持つ新しいメンバーに送信されます。4 番目のイベントは、観測所 1 の別の更新を 1 ずつデコードします。出力は次のとおりです。```
1 1
1 2
```間違った方法で XOR が適用された場合`last`、その後のイベントはすべて破損します。 

## アプローチ

 直接的な解決策は、メンバーごとに、選択した天文台、その目標、およびメンバーが参加して以来それらの天文台から収集されたビデオの量を保持することです。 天文台のアップデートについて`x`を使用するすべてのメンバーを検査できます。`x`、現在の合計を再計算し、目標に達したかどうかを確認します。 

更新によって変更されるのは次の寄与のみであるため、これは正解です。`x`。 問題はそのようなチェックの数です。 最悪の場合、イベントのおよそ半分がメンバーを作成し、残りの半分が同じ観測所を更新します。 メンバー全員がその天文台を使用すると、約

 [
 \frac m2 \cdot \frac m2 = \シータ(m^2)
 ]

 会員チェック。 のために`m = 2 * 10^5`、これは次の順序です。`10^10`小切手。 

有益な観察は、次のようなメンバーがいるということです。`k`天文台は残りの目標を達成できません`r`少なくとも 1 つの天文台が少なくとも

 [
 \left\lceil \frac r k \right\rceil
 ]

 さらに数分。 これは単なる鳩の巣の原則です。 もしすべてなら`k`天文台が受け取った金額はその金額よりも少なく、その合計増加額は厳密に以下よりも小さくなります。`r`。 

これにより、1 つの困難なグローバル状態をいくつかの単純なローカル アラームに置き換えることができます。 メンバーが現在必要としているものがあるとします。`r`さらに分がかかり、天文台を使用します`q1, ..., qk`。 私たちは毎回アラームを鳴らします`qi`、その天文台が別の場所を取得したときにこのメンバーを検査したいと述べています`ceil(r/k)`分。 

各観測所は、アラームが発生した絶対カウンター値によって順序付けされた最小ヒープ内にアラームを維持できます。 天文台のアップデート`x`に属するヒープを検査するだけで済みます`x`。 

興味深いのは、アラームが鳴ったがメンバーが実際には完了していない場合に何が起こるかということです。 メンバーの真の残りの目標を再計算します。 今だとしましょう`r' > 0`。 新しい警報器を設置します

 [
 \left\lceil \frac{r'}k \right\rceil。 
]

 古いアラームは少なくともその後に作動したため、`ceil(r/k)`1 つの天文台で新しい分が収集され、残りの目標は少なくとも減少します`ceil(r/k)`。 特に、

 [
 r' \le r-\left\lceil\frac rk\right\rceil
 \le \frac{k-1}{k}r.
 ]

以来`k <= 3`、アラームが失敗するたびに、残りの目標が一定の割合で減少します。 のために`k = 3`、せいぜい`2r/3`。 本来の目標はせいぜい`10^6`、1 つのメンバーのみ再構築できます`O(log 10^6)`回。 

This is the reason the heap approach works. ブルート フォースは更新のたびにすべてのメンバーをチェックしますが、アラーム構造は、残りの作業が大幅に縮小する必要があるほど十分な進捗が発生した後でのみメンバーをチェックします。 コンテストの公式編集では、頂点ごとに大量のアラームを使用して、まさにこの戦略を説明しています。 

There is one implementation issue in Python. 単純な遅延ヒープでは、再構築のたびに新しいアラームが挿入され、古いアラームがヒープ内に残ります。 これは書くのは簡単ですが、多くの古いヒープ エントリが作成される可能性があります。 代わりに、以下の実装ではインデックス付きバイナリ ヒープを使用します。 各メンバーには最大 3 つのアラーム ノードがあり、メンバーを再構築すると、新しいヒープ エントリが割り当てられるのではなく、それらの既存のノードのキーが変更されます。 メンバーが完了すると、そのすべてのアラーム ノードが直接削除されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |`O(m^2)`|`O(m)`| 遅すぎる |
 | ヒープアラーム |`O(m log m log V)`|`O(n + m)`| 承認済み |

 ここ`V <= 10^6`が最大の目標です。 要因`k <= 3`定数に吸収されます。 

## アルゴリズムのチュートリアル

 1. メンテナンス`value[x]`、天文台で収集された合計量`x`これまでのところ。 この値には、メンバーが参加する前に収集されたビデオが含まれるため、各メンバーは、参加した時点で選択されたすべての天文台の値も保存します。 これらの保存された値を減算すると、そのメンバーにとって重要な貢献度が正確に得られます。 
2. 目標を持った新メンバーの場合`y`そして`k`天文台が到着し、選択した天文台とその現在を保存します`value`カウンター。 選択した観測所ごとに、現在のカウンターと現在のカウンターをターゲットとするアラームを作成します。 

[
 \左\lceil\frac yk\右\rceil。 
]

 目標は絶対カウンター値であるため、アラームはイベント間で観測値がどの程度変化するかを記憶する必要はありません。 
3. 同じ観測所に属するすべてのアラームを最小ヒープに保存します。 最小のターゲットは、そこで発火する可能性のある次の警報です。 インデックス付きヒープはすべてのアラーム ノードの位置も記憶しているため、任意のアラームを変更または削除できます。`O(log m)`時間。 
4. タイプ 2 イベントの場合、まず観測所を XOR デコードし、前の値を使用してインクリメントします。`last`。 増加`value[x]`デコードされた増分によって。 
5.最小アラームが鳴っている間、`x`新しい目標を超えない目標を持っています`value[x]`、そのアラームを処理します。 アラームにアタッチされているメンバーは、このアップデートにより完成した可能性のあるメンバーの 1 つであることが保証されます。 
6. 合計してメンバーの実際の徴収金額を計算します。`value[q] - base[q]`最大でも 3 つの天文台上にあります。 この合計が少なくともメンバーの目標である場合は、メンバーに完了のマークを付け、そのアラーム ノードをすべて削除し、この更新の回答にその ID を追加します。 
7. メンバーが完了していない場合は、`r`残りの目標になります。 セット

 [
 d=\left\lceil\frac rk\right\rceil。 
]

 メンバーのアラーム ノードをすべて変更して、新しいターゲットが`value[q] + d`。 これらは将来の増分であるため、現在のカウンターが新しい開始点として使用されます。 
8. この更新中に発生したすべてのアラームが処理された後、この更新のために収集された ID を並べ替えて出力します。 セット`last`報告された ID の数まで。 この値は、次のイベントをデコードするために使用されます。 

### なぜ効果があるのか

 不変条件は、すべてのアクティブなメンバーが選択した各観測所に 1 つのアラームを持ち、各アラームが正確に配置されることです。`ceil(r/k)`将来のユニットが離れている場所、`r`メンバーの現在の残りの目標です。 メンバーが目標を達成した場合、少なくとも 1 つの選択された天文台が少なくとも 1 つの目標を達成している必要があります。`ceil(r/k)`前回の再構築以来なので、これらのアラームのいずれかは、メンバーが完了した瞬間までに起動する必要があります。 したがって、メンバーは検査されずに完了ポイントを黙って通過することはできません。 

アラームが発生すると、メンバーが参加してからの正確な累積貢献度が計算されます。 目標が達成された場合、メンバーを報告し、すべてのアラームを削除します。これにより、再び報告されることはなくなります。 それ以外の場合、残りの目標は最大でも`(k-1) / k`以前の残りの目標を達成し、アラームは新しい状態から再構築されます。 したがって、すべてのメンバーは対数的に何度のみ再構築できます。 

保存された基本値は、他の正確性条件を処理します。つまり、メンバーが参加する前に行われた観測は、その寄与度の計算には決して入りません。 最後に、各更新後に ID を並べ替えると、必要な昇順が正確に得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())

    # Current total collected at every observatory.
    value = [0] * n

    # Member data, indexed by member id.
    goals = [0]
    positions = [()]
    bases = [()]
    nodes_of_member = [()]
    active = [False]

    # Every alarm is represented by one node.
    # node_target[node] is its absolute firing target.
    # node_member[node] is the member owning it.
    # node_pos[node] is the observatory heap containing it.
    # node_index[node] is its current index inside that heap.
    node_target = []
    node_member = []
    node_pos = []
    node_index = []

    # One indexed binary min-heap per observatory.
    heaps = [[] for _ in range(n)]

    def less(a, b):
        ta = node_target[a]
        tb = node_target[b]
        if ta != tb:
            return ta < tb
        return a < b

    def sift_up(heap, i):
        node = heap[i]
        while i:
            p = (i - 1) >> 1
            parent = heap[p]
            if not less(node, parent):
                break
            heap[i] = parent
            node_index[parent] = i
            i = p
        heap[i] = node
        node_index[node] = i

    def sift_down(heap, i):
        node = heap[i]
        size = len(heap)
        while True:
            left = i * 2 + 1
            if left >= size:
                break
            right = left + 1
            child = left
            if right < size and less(heap[right], heap[left]):
                child = right
            if not less(heap[child], node):
                break
            heap[i] = heap[child]
            node_index[heap[i]] = i
            i = child
        heap[i] = node
        node_index[node] = i

    def insert_node(node, pos):
        heap = heaps[pos]
        node_pos[node] = pos
        heap.append(node)
        node_index[node] = len(heap) - 1
        sift_up(heap, len(heap) - 1)

    def remove_node(node):
        pos = node_pos[node]
        heap = heaps[pos]
        i = node_index[node]
        last_node = heap.pop()

        if i < len(heap):
            heap[i] = last_node
            node_index[last_node] = i

            if i and less(last_node, heap[(i - 1) >> 1]):
                sift_up(heap, i)
            else:
                sift_down(heap, i)

        node_index[node] = -1

    def change_key(node, new_target):
        node_target[node] = new_target
        pos = node_pos[node]
        heap = heaps[pos]
        i = node_index[node]

        if i and less(node, heap[(i - 1) >> 1]):
            sift_up(heap, i)
        else:
            sift_down(heap, i)

    last = 0
    member_count = 0
    output = []

    for _ in range(m):
        parts = list(map(int, input().split()))
        op = parts[0]

        if op == 1:
            enc_y = parts[1]
            k = parts[2]

            y = enc_y ^ last

            qs = []
            bs = []

            for j in range(k):
                q = parts[3 + j] ^ last
                q -= 1
                qs.append(q)
                bs.append(value[q])

            member_count += 1
            mid = member_count

            goals.append(y)
            positions.append(tuple(qs))
            bases.append(tuple(bs))
            nodes_of_member.append(())
            active.append(True)

            delta = (y + k - 1) // k
            member_nodes = []

            for q in qs:
                node = len(node_target)

                node_target.append(value[q] + delta)
                node_member.append(mid)
                node_pos.append(q)
                node_index.append(-1)

                member_nodes.append(node)
                insert_node(node, q)

            nodes_of_member[mid] = tuple(member_nodes)

        else:
            x = (parts[1] ^ last) - 1
            add = parts[2] ^ last

            value[x] += add
            answer = []

            heap = heaps[x]

            while heap:
                node = heap[0]
                if node_target[node] > value[x]:
                    break

                mid = node_member[node]

                if not active[mid]:
                    remove_node(node)
                    continue

                qs = positions[mid]
                bs = bases[mid]
                k = len(qs)

                collected = 0
                for j in range(k):
                    collected += value[qs[j]] - bs[j]

                if collected >= goals[mid]:
                    active[mid] = False
                    answer.append(mid)

                    for nd in nodes_of_member[mid]:
                        remove_node(nd)
                else:
                    remaining = goals[mid] - collected
                    delta = (remaining + k - 1) // k

                    for j, nd in enumerate(nodes_of_member[mid]):
                        q = qs[j]
                        change_key(nd, value[q] + delta)

            answer.sort()

            output.append(str(len(answer)) + (
                " " + " ".join(map(str, answer)) if answer else ""
            ))

            last = len(answer)

    sys.stdout.write("\n".join(output))

if __name__ == "__main__":
    solve()
```の`value`配列は各観測所の現在の累積量を表します。 メンバーが参加したときに意図的にリセットされません。 その代わり、`bases`各カメラの古い値が記録されるため、メンバーに関連する貢献度は次のようになります。`value[q] - bases[q]`。 

の`goals`、`positions`、`bases`、 そして`nodes_of_member`配列はすべてメンバー ID によってインデックス付けされます。 メンバーが使用する天文台は最大 3 つであるため、これらの各レコードのサイズは一定のままです。 

ヒープ実装は遅延ではなくインデックスが作成されます。 すべてのアラームには安定したノード ID があり、`node_index`そのノードが観測所のヒープ内のどこにあるかを正確に教えてくれます。`change_key`その結果、既存のアラームを変更できるようになります。`O(log m)`、 その間`remove_node`同じ複雑さ内の 1 つを削除できます。 これにより、再構築後に古いアラームが保持されることが回避されます。 

メンバーがチェックに失敗すると、コードは正確な残りの目標を計算し、現在の観測所カウンターを基準にしてすべてのアラーム目標を設定します。 天井の表現`(remaining + k - 1) // k`の整数形式です`ceil(remaining / k)`。 

メンバーが完了すると、そのすべてのアラーム ノードが直ちに削除されます。 このため、後で選択した別の天文台が更新されても、完了したメンバーを再度報告することはできません。 

入力は、状態が変更される前にデコードされます。 タイプ 1 イベントの場合、`last`目標とすべての観測指標に適用されます。 第 2 種イベントの場合は、観測値と増分値の両方に適用されます。 タイプ 2 イベントを処理した後、`last`そのイベントによって報告されたメンバーの数になります。 

Python の整数には任意の精度があるため、オーバーフローの問題はありません。 実際の最大カウンタは次を超える可能性があります`10^6`多くの更新が同じ観測所に蓄積される可能性があるため、これが説明や実装で固定幅の仮定を使用しないもう 1 つの理由です。 

## 実用的な例

 ### サンプル 1

 サンプルは次のとおりです。```
3 5
1 5 3 1 2 3
2 2 1
1 2 2 1 2
2 3 1
2 1 3
```最初のメンバーには目標 5 があり、観測点 1、2、および 3 にカメラがあります。その最初のアラーム増分は次のとおりです。`ceil(5 / 3) = 2`。 

| イベント |`last`前 | 操作 | 天文台の合計 | メンバーの状態 | 出力 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | メンバー 1、目標 5、を追加`{1,2,3}`|`(0,0,0)`| 残り 5、アラーム`2`| |
 | 2 | 0 | 天文台 2 に 1 を追加 |`(0,1,0)`| 残り 4 |`0`|
 | 3 | 0 | メンバー 2、ゴール 2 を追加、`{1,2}`|`(0,1,0)`| メンバー 2 は次の値から始まります。 |
 | 4 | 0 | 展望台 3 に 1 を追加 |`(0,1,1)`| アラームがターゲットに到達しない |`0`|
 | 5 | 0 | 展望台 1 に 3 を追加 |`(3,1,1)`| メンバー1は`3+1+1=5`; メンバー2は`3+0=3`|`2 1 2`|

 4 番目のイベントはメンバー 1 を完了しません。その貢献は次のとおりです。`0 + 1 + 1 = 2`。 最終更新では、観測所 1 が両方のメンバーに警報を発するのに十分なレベルまで上昇し、両方の正確なチェックが成功します。 ID は印刷前にソートされます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |`O(m log m log V)`| メンバーそれぞれが再構築される`O(log V)`各再構築は最大 3 つのヒープ ノードに影響し、各ヒープ操作コストが発生します。`O(log m)`|
 | スペース |`O(n + m)`| がある`n`ヒープとメンバーごとに最大 3 つのアラーム ノード |

 幾何学的減少の原因は次のとおりです。 

[
 r' \le \frac{k-1}{k}r.
 ]

 最も遅いケースは、`k = 3`、大まかに言うと`r' <= 2r/3`。 から始まる`10^6`、これには、1 つのメンバーに対して約 35 回の再構築の失敗だけが必要です。 各メンバーには最大 3 つのアラームがあるため、ライブ ヒープ ノードの総数は次のようになります。`O(m)`。 インデックス付きヒープは、アラームが何度も再構築された後でも、このメモリをバインドしたままにします。 

のために`n,m <= 2 * 10^5`ヒープ構成には対数係数が必要ですが、重要な改善点は、更新後に無関係なメンバーを決してスキャンしないことです。 定数`k <= 3`すべての再構成を、意図した複雑さに対して十分に小さく保ちます。

 ## 特殊なケース

 最初のエッジケースは、メンバーが参加する前に収集されたビデオです。 で```
1 3
2 1 5
1 3 1 1
2 1 3
```メンバーが存在する前に、グローバル カウンタは 5 になります。 メンバーが作成されると、実装は`base = 5`。 最終更新後、関連する投稿は次のとおりです。`value[1] - base = 8 - 5 = 3`、その時点でメンバーは正確に目標に到達します。 出力は`0`、`0`、`1 1`。 

2 番目のエッジ ケースは、メンバーが完了し、さらに更新を受信する場合です。 で```
1 3
1 2 1 1
2 1 2
2 0 0
```最初の更新でメンバーが完成します。 その`active`フラグが false になり、そのアラーム ノードがすべて削除されます。 以来`last = 1`、最後のエンコードされた更新は、天文台 1 への別の更新です。そのヒープは空であるため、何も報告されません。 出力は`1 1`、`0`。 

3 番目のエッジ ケースは、アラームは発生するが完了しない更新です。 考慮する：```
3 4
1 6 3 1 2 3
2 1 2
2 2 2
2 3 2
```当初、各アラームは 2 分後です。`ceil(6/3)=2`。 最初の更新では観測所 1 で警報が鳴りましたが、メンバーは 2 分しか収集していません。 残りの目標は 4 であるため、アラームは増分とともに再構築されます`ceil(4/3)=2`。 2 回目の更新では別のアラームが発生し、2 分間残ります。 その後、アラームは増分して再構築されます`ceil(2/3)=1`。 3 回目の更新で最後のアラームが発生し、正確な合計は 6 になります。出力は次のようになります。`0`、`0`、`1 1`。 

4 番目のエッジケースは大規模なアップデートです。 メンバーがゴール 10 と 3 台のカメラを持っていると仮定すると、1 台のカメラに突然 100 分の時間が与えられます。 アラームが 1 回鳴ると、正確なチェックにより、目標に到達したことがすぐにわかります。 100分をいちいちシミュレーションする必要はありません。 ヒープは、絶対的なアラーム目標を超えたかどうかのみを考慮します。 

最後のエッジケースは、同じ天文台を共有する複数のメンバーです。 それらはすべて、その天文台のヒープ内に個別の警報ノードを持っています。 更新では最初に最小のターゲットが処理され、そのメンバーが完了または再構築された後、ヒープが再度検査されます。 これは、最小ターゲットが現在の観測値より大きくなるまで繰り返されます。 その天文台に関係のないメンバーがこのアップデートに影響を受けることはありません。 

ご希望であれば、新しいバイナリアラーム手法を使用した社説の 2 番目のバージョンを提供することもできます。これにより、おおよその漸近限界が改善されます。`O(m log V)`ただし、実装はかなり複雑です。
