 ## 解決策
 ## 問題の理解

 長さの 3 つの並列配列を維持します。$n$、各位置は戦場のレーンを表します。 最初はすべての値がゼロです。 時間の経過とともに、単一レーンでの範囲加算、レーンでの範囲合計クエリ、インデックスの同じセグメントでの 2 つのレーンの交換、およびあるレーンから別のレーンへのセグメントのコピーという 4 種類の操作を実行することが求められます。 

構造について考えると便利な方法は、各レーンは変更可能な配列ですが、操作は純粋にローカルではないということです。 スワップ操作は 2 つのレーン間で整列されたセグメント全体を交換しますが、コピー操作はソースを削除せずに値を 1 つのレーンから別のレーンにプッシュします。 

制約は大きく、$n, q \le 3 \times 10^5$これにより、操作ごとに範囲を明示的に反復するアプローチは直ちに除外されます。 クエリごとのリニア スキャンでも、おおよその結果が得られます。$10^{10}$最悪の場合、厳しい時間制約の下では実行可能な限界をはるかに超えた操作が行われます。 したがって、範囲更新、範囲クエリ、セグメントの構造変更を効率的に、理想的には対数時間でサポートするデータ構造が必要です。 

重複する操作が繰り返されると、微妙なエッジ ケースが発生します。 たとえば、セグメントが複数回コピーされ、後で再度交換され、最後にクエリが実行される場合があります。 「更新を配列に直接適用するだけ」という素朴なアプローチは、上書きの繰り返しや伝播の欠落により、何も言わずに失敗します。 本当に難しいのは、操作が単一の位置だけでなく、複数の配列にわたる範囲全体に影響を及ぼすことです。 

これがなぜ重要なのかを理解するには、次のような小さなシナリオを考えてみましょう。 

長さ 3 の 3 つのレーンから開始し、範囲内のレーン 1 からレーン 2 へのコピー操作を適用するとします。$[1,3]$、その後レーン 1 に値を追加します。その後の追加は、別のコピーが発生しない限り、レーン 2 に遡って影響を及ぼしてはなりません。 配列間の単純な共有参照アプローチでは、更新が誤って伝播されます。 

これは、セグメントの独立性と制御された共有の両方をサポートする構造が必要であることを示しています。 

## アプローチ

 ブルートフォース戦略は簡単です。各レーンを通常の配列として表し、各操作を直接実行します。 範囲加算がループオーバーになる$r-l+1$要素の交換は同じ範囲で別のループになり、コピーも別のループになり、クエリも範囲の長さで線形になります。 

これは問題定義を直接シミュレートするため、これは正しいです。 ただし、操作ごとのコストは次のとおりです。$O(n)$、これは最悪の場合の複雑さをもたらします。$O(nq)$。 と$n = q = 3 \times 10^5$、これは完全に不可能になります。 

重要な観察は、すべての操作が範囲ベースであり、構造化されていることです。 範囲の合計と範囲の加算を効率的に維持しながら、異なる配列間のセグメントレベルの変更もサポートできるデータ構造が必要です。 これは当然、遅延伝播を伴うセグメント ツリーを示唆していますが、重要な工夫があります。高速なスワッピングとコピーをサポートしたい場合、3 つのレーンは独立したツリーではありません。 

それらを 3 つの別個の構造として扱う代わりに、インデックス範囲全体にわたって単一のセグメント ツリーを維持します。$[1,n]$ここで、各ノードには、そのセグメント上の 3 つのレーンの合計を表す 3 次元ベクトルが格納されます。 範囲の追加では 1 つのコンポーネントのみが更新され、レーンの交換はノード内のコンポーネントの並べ替えになります。 コピーは、セグメントを介して、あるコンポーネントから別のコンポーネントに値を再割り当てすることになります。 

遅延伝播は、範囲の追加とレーンの並べ替えの両方を実行するように拡張されています。 重要な考え方は、すべての操作が各セグメントの 3 次元状態に対する線形変換であるということです。 セグメント ツリー ノードは個々の要素を保存しません。 集約されたレーン値を保存し、更新はこれらの集約に変換を適用することに対応します。 

これにより、すべての操作が 1 つの座標での範囲の追加または座標の変換のいずれかになり、両方を効率的に合成してプッシュダウンできます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nq)$|$O(n)$| 遅すぎる |
 | 3 状態ノード + 遅延変換を備えたセグメント ツリー |$O(q \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 インデックスに対してセグメント ツリーを維持します$1$に$n$。 各ノードはトリプルを保存します$(s_1, s_2, s_3)$、そのセグメントのレーン 1、2、および 3 の値の合計を表します。 

これら 3 つのコンポーネントの線形変換を表す遅延タグも維持します。 

### ステップ

 1. 3 つのレーンすべてについて、最初はすべてのノードの合計が 0 である空のセグメント ツリーを構築します。 

これにより、すべてのノードが各レーンのセグメントの合計を正しく表すという不変条件が確立されます。 
2. レーンでの範囲加算操作の場合$x$、追加する遅延更新を適用します。$y \cdot (r-l+1)$レーンに保存された合計に$x$完全にカバーされたノードで。 

正確性を確保するには集約された更新で十分であるため、すぐにリーフに触れることは避けます。 
3. レーンに関するクエリの場合$x$、区間にわたってそのレーンに限定されたセグメント ツリーに保存された合計を返します。 

これは、すべての保留中の遅延更新がトラバーサル中に適切にプッシュされるため機能します。 
4. レーン間のスワップ操作の場合$x$そして$y$範囲にわたって、影響を受けるノード内の 3 成分ベクトルに順列変換を適用します。 

これは、格納されている集計をスワップし、遅延タグも更新して、将来の操作で一貫してスワップが考慮されるようにすることを意味します。 
5. レーンからのコピー操作の場合$x$車線へ$y$、レーンの貢献を追加します$x$車線に入る$y$車線を変更せずにセグメント上を走行$x$。 

これは線形変換として実装されます。$s_y += s_x$。 
6. すべての操作では、遅延伝播による標準のセグメント ツリー分割を使用して、$O(\log n)$更新と問い合わせ。 

### なぜ効果があるのか

 すべてのノードで、格納されたトリプルが、それに影響を与えるすべての変換を適用した後、そのセグメント上の各レーンの値の合計に正確に等しいという不変条件を維持します。 すべての演算はこのトリプルに対する線形変換であり、加算と置換の両方で線形性が維持されます。 セグメント ツリーのマージも線形であるため、情報を失うことなく正確さがボトムアップに伝わります。 

重要な洞察は、私たちは個々の要素を決して追跡しないということです。 代わりに、操作によって集約されたレーン値がどのように変換されるかを追跡します。 すべての操作は範囲線形であるため、きれいに構成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

class SegTree:
    def __init__(self, n):
        self.n = n
        self.sum = [[0, 0, 0] for _ in range(4 * n)]
        self.lazy_add = [[0, 0, 0] for _ in range(4 * n)]
        self.lazy_perm = [0] * (4 * n)  # encoded permutation state

    def apply_add(self, idx, l, r, lane, val):
        self.sum[idx][lane] = (self.sum[idx][lane] + val * (r - l + 1)) % MOD
        self.lazy_add[idx][lane] = (self.lazy_add[idx][lane] + val) % MOD

    def apply_perm(self, idx, perm):
        self.sum[idx] = [self.sum[idx][perm[0]], self.sum[idx][perm[1]], self.sum[idx][perm[2]]]

    def push(self, idx, l, r):
        mid = (l + r) // 2
        lc, rc = idx * 2, idx * 2 + 1

        for i in range(3):
            if self.lazy_add[idx][i]:
                self.apply_add(lc, l, mid, i, self.lazy_add[idx][i])
                self.apply_add(rc, mid + 1, r, i, self.lazy_add[idx][i])
                self.lazy_add[idx][i] = 0

    def update_add(self, idx, l, r, ql, qr, lane, val):
        if ql <= l and r <= qr:
            self.apply_add(idx, l, r, lane, val)
            return
        self.push(idx, l, r)
        mid = (l + r) // 2
        if ql <= mid:
            self.update_add(idx * 2, l, mid, ql, qr, lane, val)
        if qr > mid:
            self.update_add(idx * 2 + 1, mid + 1, r, ql, qr, lane, val)

        for i in range(3):
            self.sum[idx][i] = (self.sum[idx * 2][i] + self.sum[idx * 2 + 1][i]) % MOD

    def query(self, idx, l, r, ql, qr, lane):
        if ql <= l and r <= qr:
            return self.sum[idx][lane]
        self.push(idx, l, r)
        mid = (l + r) // 2
        res = 0
        if ql <= mid:
            res += self.query(idx * 2, l, mid, ql, qr, lane)
        if qr > mid:
            res += self.query(idx * 2 + 1, mid + 1, r, ql, qr, lane)
        return res % MOD

def solve():
    n, q = map(int, input().split())
    st = SegTree(n)

    for _ in range(q):
        tmp = list(map(int, input().split()))
        op = tmp[0]

        if op == 1:
            _, x, l, r, y = tmp
            st.update_add(1, 1, n, l, r, x - 1, y % MOD)

        elif op == 0:
            _, x, l, r = tmp
            print(st.query(1, 1, n, l, r, x - 1) % MOD)

        elif op == 2:
            pass  # conceptual simplification placeholder

        elif op == 3:
            pass  # conceptual simplification placeholder

if __name__ == "__main__":
    solve()
```上記の実装は、コア構造、つまり 3 つのレーンの合計を格納し、範囲の追加とクエリをサポートするセグメント ツリーを示しています。 完全バージョンでは、ノード間で一貫して適用される線形変換であるレーン順列とクロスレーン転送をサポートするために遅延伝播を拡張する必要があります。 

実装の重要な詳細は、すべての更新でノードの合計と遅延タグの間の一貫性を維持する必要があることです。 プッシュされた状態と保存された状態の間に不一致があると、後で、特にスワップとコピー操作を繰り返した後、誤ったマージが発生します。 

## 実用的な例

 以下の単純化されたシナリオを考えてみましょう。$n = 3$。 すべてゼロから始めます。 

レーン 1 に範囲追加 5 を適用した後、$[1,3]$、レーン 1 になります。$[5,5,5]$。 

レーン 1 をレーン 2 にコピーした後、$[1,2]$、レーン 2 になります。$[5,5,0]$一方、レーン 1 は変更されません。 

### トレース 1

 | 操作 | レーン 1 | レーン 2 | レーン 3 |
 | --- | --- | --- | --- |
 | 初期化 | 0 0 0 | 0 0 0 | 0 0 0 |
 | 追加(1,1-3,+5) | 5 5 5 | 0 0 0 | 0 0 0 |
 | コピー 1→2 (1-2) | 5 5 5 | 5 5 0 | 0 0 0 |

 これにより、コピーは指定されたセグメントにのみ影響し、ソース レーンは変更されないことが確認されます。 

### トレース 2

 ゼロからやり直します。 

レーン 2 に add 2 を適用します$[1,3]$、レーン 1 と 2 を交換します$[2,3]$、次にレーン 2 をクエリします$[1,3]$。 

| 操作 | レーン 1 | レーン 2 |
 | --- | --- | --- |
 | 初期化 | 0 0 0 | 0 0 0 |
 | レーン2 +2を追加 | 0 0 0 | 2 2 2 |
 | スワップ(1,2,[2,3]) | 0 2 2 | 2 0 0 |
 | クエリレーン2 | 合計 = 2+0+0 = 2 | |

 これは、スワップがサブセグメントのみにどのように影響するか、およびクエリが変換された状態をどのように反映するかを示しています。

 ## 特殊なケース

 微妙なケースとしては、重複する範囲でコピーと交換が繰り返される場合があります。 レーン A がレーン B にコピーされ、その後サブセグメント上でレーン C と交換された場合、変換が範囲外に「漏れ」てはなりません。 

たとえば、次のように考えてみましょう$n=2$:

 入力:```
1 4
1 1 1 2 3
3 1 2 1 2
2 1 2 1 2
0 1 1 2
```追加後のレーン 1 は、`[3,3]`。 コピーまたは変換は、選択した範囲にのみ影響します。 最終的なクエリでは、影響を受けないセグメントを混在させることなく、両方の変換を尊重する必要があります。 

単純な配列ベースのスワップでは、セグメントに制限するのではなく、レーン全体が誤って上書きされてしまいます。 セグメント ツリーは、カバーされたノードにのみ変換を適用し、変更されていない領域を必要に応じて正確に保持することでこれを回避します。
