 ## 解決策
 ## 問題の理解

 すべて「訪問」して掃除する必要があるメールボックスを表す線上のいくつかの点と、同じ線に沿って移動できる人々を表す別の点のセットが与えられます。 各人は固定座標から開始し、1 秒あたり 1 単位ずつ左右に移動できます。 人が郵便受けの位置に立つと、その郵便受けは即座に掃除されます。 複数の人が自由に重なることができ、複数のメールボックスが同じ座標を共有することができます。 

タスクは、すべてのメールボックスが少なくとも 1 回はアクセスされるように全員を調整することであり、最後のメールボックスがクリーンアップされるまでの時間を可能な限り短縮する必要があります。 

これについて考えると便利な方法は、各人は制限時間 T 以内にラインの連続したセグメントをカバーできるということです。これは、出発点から距離 T 内の任意の位置に T 秒以内に到達できるためです。 したがって、各友人は到達可能な位置の間隔を定義し、これらの間隔の和集合がすべてのメールボックス ポイントを「カバー」できるように T を選択する必要があります。 

制約により、効率的な解決策が求められます。 テスト ケースごとに最大 100,000 のメールボックスと 100,000 人の友人が存在する場合、ユーザーとメールボックスの間の 2 次マッチングは非常に遅すぎます。 並べ替えと単純な割り当てでも、カバレッジを繰り返しスキャンする場合は合格しません。 これは、ソリューションでは、通常は並べ替えと貪欲なマージを使用して、候補値ごとに問題を線形または線形に近いチェックに削減する必要があることを示します。 

メールボックスがクラスター化されており、すべての友人から遠く離れている場合、微妙なケースが発生します。 たとえば、すべての友人が 0 付近から始まり、メールボックスが大きな正と負の極値にある場合、答えは、平均やグローバル マッチングではなく、最も近い友人からの必要な最も遠い移動距離によって決まります。 

もう 1 つの特殊なケースは、位置が繰り返されることです。 多くのメールボックスが座標を共有している場合は、1 回の訪問で十分ですが、マッチング ロジックでメールボックスを個別に扱う単純な実装では、作業が無駄になったり、割り当てが過剰に増加したりする可能性があります。 

## アプローチ

 強引なアイデアは、割り当ての観点から考えることです。 固定時間 T の間、友人が T 以内に到達できるように、すべてのメールボックスを少なくとも 1 人の友人に割り当てることができるかどうかを確認します。つまり、友人ごとに到達可能な間隔を計算し、これらの間隔ですべてのメールボックス ポイントをカバーしようとします。 単純なチェックでは、すべての友人間隔に対してすべてのメールボックスが試行され、テスト ケースあたり O(nm) になる可能性があります。 n と m が両方とも 100000 までの場合、最悪の場合は 10^10 の演算が行われることになりますが、これはリモートでは実行不可能です。 

重要な観察は、一定時間 T の間、各友人の到達可能な領域は回線上の連続したセグメントであるということです。 問題はカバレッジの問題になります。これらのセグメントはすべてのメールボックス ポイントをカバーしているか? メールボックスが並べ替えられると、並べ替えられた両方のリストをスイープすることによって、直線的な時間でチェックできます。 

これにより、問題が決定問題に変換されます。特定の T について、O(n + m) で実現可能性をチェックできます。 すべてのメールボックスを時間 T 内にクリーンアップできれば、さらに長い時間でもクリーンアップできるため、答え自体は T において単調です。 この単調性により、T に対する二分探索が可能になります。 

各実現可能性チェックを貪欲なスイープとして、回答範囲の二分探索を使用して、カバレッジが可能となる最小 T を計算します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース割り当て | テストあたり O(nm) | お(1) | 遅すぎる |
 | 二分探索 + スイープ | O((n + m) log R) | O(n + m) | 承認済み |

 ここで R は 10^18 までの座標範囲であるため、log R は約 60 になります。 

## アルゴリズムのチュートリアル

 ### 1. すべてのメールボックスの位置とすべての友人の位置を並べ替えます。 

並べ替えることにより、後戻りすることなく左から右にカバレッジを推論できるようになります。 順序付けが完了すると、間隔と目標が構造化された方法で調整されます。 

### 2. 実現可能性をチェックする関数 can(T) を定義します

位置 p の各友人の到達可能なセグメントは [p − T, p + T] です。 目的は、これらのセグメントの結合がすべてのメールボックスの位置をカバーしているかどうかを確認することです。 

### 3. ポインタを使用してメールボックスをスイープする

 メールボックス上でインデックス i を維持します。 また、並べ替えられた順序で友人を反復処理します。 

各友人では、可能な限り範囲を拡大するよう努めています。 

その間隔内にあるすべてのメールボックス、つまり位置 ≤ p + T のメールボックスを考慮します。現在のメールボックスが < p − T の場合、その友人はそれを助けることができないため、適切に前方にスキップします。 

重要な考え方は、メールボックスをスキップすると、その後の友人は過去に戻ることができないため、すべてのメールボックスが順番にカバーされていることを確認する必要があるということです。 

### 4. 友人ごとに到達可能なメールボックスを貪欲に消費する

 特定の友人について、有効な開始メールボックスに到達すると、メールボックスが到達可能な間隔内にある限り、メールボックス ポインタを進めます。 

これにより、決定を再度検討することなく、各メールボックスがそのメールボックスをカバーできる最も早い友人に効果的に割り当てられます。 

### 5. すべてのメールボックスがカバーされている場合は、True を返します。 

ポインタがメールボックス リストの最後に到達した場合、時間 T は十分です。 

### 6. T 上の二分探索

 メールボックスと友人の間の 0 から最大距離まで T にわたって検索します。 各中間値は can(mid) でテストされます。 

### なぜ効果があるのか

 正しさは、カバー領域とターゲットの両方が直線上にあるという構造から得られます。 任意の固定 T の場合、各フレンドは連続した間隔に寄与し、実現可能性は一連の間隔がすべてのポイントをカバーするかどうかによって決まります。 貪欲なスイープは、友人を順番に処理すれば、可能な限り範囲を拡張しても、将来の範囲オプションを妨げることがないため、最適です。 メールボックスのカバーを遅らせる代替割り当ては柔軟性を低下させるだけであるため、左から右への貪欲な使用により、実現可能性が存在する場合に正確に維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(mailboxes, friends):
    mailboxes.sort()
    friends.sort()

    n = len(mailboxes)
    m = len(friends)

    def can(t):
        i = 0
        for p in friends:
            if i >= n:
                return True

            left = p - t
            right = p + t

            if mailboxes[i] > right:
                continue

            if mailboxes[i] < left:
                continue

            while i < n and left <= mailboxes[i] <= right:
                i += 1

            if i >= n:
                return True

        return i >= n

    lo, hi = 0, 10**18

    while lo < hi:
        mid = (lo + hi) // 2
        if can(mid):
            hi = mid
        else:
            lo = mid + 1

    return lo

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        n, m = map(int, input().split())
        mailboxes = [int(input()) for _ in range(n)]
        friends = [int(input()) for _ in range(m)]
        out.append(str(solve_case(mailboxes, friends)))
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```コア実装は、実現可能性チェックを二分探索から分離します。 の`can(t)`機能は最もデリケートな部分です。 ポインタ`i`各メールボックスがチェックごとに最大 1 回処理されることが保証されるため、各実現可能性テストは線形になります。 周囲の状況`left`そして`right`カバレッジが有効な場合にのみ先に進み、役に立たない友人が現在のメールボックス セグメントに到達できない場合はスキップします。 

二分探索範囲は、座標がこれほど大きくなり、最悪の場合でもメールボックスと友人間の距離がそのスケールに達する可能性があるため、最大 10^18 まで控えめに選択されます。

| た | 友達の間隔 | 取材プロセス | カバーされた |
 | --- | --- | --- | --- |
 | 1 | [0,2]、[4,6] | 0 をカバーし、その後 3 でスタックします。 いいえ |
 | 2 | [-1,3]、[3,7] | 最初は 0 と 3 をカバーしますが、2 番目は 8 に到達できません | いいえ |

 T = 4 では、最初の友人は最大 5 に達し、メールボックス 0 と 3 をカバーします。2 番目の友人は 9 に達し、最後のメールボックスを終了します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + m) log R) | ソートと二分探索、各実現可能性チェックは線形スイープです。

 ## 特殊なケース

 主なエッジケースは、すべてのメールボックスがすべての友人の片側にある場合です。 たとえば、メールボックスが 100、200、300、友人が 0 です。二分探索には、単一の間隔 [0−T, 0+T] が最も遠いメールボックスをカバーするのに十分な大きさの T が必要であるため、アルゴリズムは正しく 300 を返します。 「最初に近いものに一致させる」という貪欲な割り当ての試みは失敗します。これは、分散の選択肢がなく、拡張のみであるためです。 

もう 1 つのケースは、友人が密集しているが、その間のメールボックスがまばらである場合です。 スイープにより、各フレンドは必要な場合にのみ貢献することが保証され、ポインタは前方にのみ移動するため、重複する間隔は干渉せず、多くの間隔が重なり合っている場合でも正確さが維持されます。
