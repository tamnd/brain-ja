 ## 解決策
 ## 問題の理解

 スタックされたブロックが分散された 2 つの構成が与えられています。$T$塔。 各タワーは本質的には積み重ねであり、すべてのブロックには重みがあります。 各スタック内では、重みは下から上に非増加順序で配置されます。つまり、重いブロックまたは等しいブロックは常に軽いブロックの下に位置します。 この制約により、すべてのタワーがすでに安定した状態にあることが保証されます。 

1 つの操作は、空ではないタワーの最上部のブロックを取得し、それを別のタワーの上に配置することで構成されます。ただし、結果として得られるタワーが安定しているため、移動されたブロックは、移動先の現在の最上部のブロック (存在する場合) よりも重くてはなりません。 

課題は、そのような法的手段をいくらでも使用して、最初の取り決めを最終的な取り決めに変えることができるかどうかを判断することです。 

制約から観察される重要な点はスケールです。 まであります$2 \cdot 10^5$ブロックされるため、移動を 1 つずつシミュレートしたり、構成を探索しようとしたりする戦略はすぐに失敗します。 ブロックごとの直線的な移動数であっても、各移動が再計算または検証作業をトリガーする場合は大きすぎます。 

素朴な解釈では、これをスタック上の状態空間の到達可能性の問題として扱うことを提案しますが、状態空間は天文学的に大きいです。 唯一の希望は、問題を個々のブロックまたはスタックの構造特性にわたる何らかの不変式に圧縮することです。 

ブロックが同じ重みを共有する場合、微妙なエッジケースが発生します。 「非増加」ルールの下では等しい重みを自由に積み重ねることが許可されているため、順序付けによってブロックされているように見える多くの変換が実際には可能です。 たとえば、すべてのブロックの重みが 5 の場合、どのような再配置も有効です。 構成間の厳密な順序制約を誤って強制する単純なソリューションは、ここでは失敗します。 

もう 1 つのエッジ ケースは、初期構成と最終構成に同一のマルチセットのタワーがあり、配布順序のみが異なる場合です。 一時的なタワーを介した再配布が多くの場合可能である場合でも、単純なタワーごとの比較では、これらのケースが誤って拒否されてしまいます。 

## アプローチ

 ブルートフォースの観点は、すべての法的措置をシミュレートすることから始まります。 どの状態からでも、各タワーの最上部のブロックを他の互換性のあるタワーに移動して、新しい状態を生成できます。 各移動は最上位の要素にのみ影響するため、構成上の BFS を想像することができます。 

このアプローチは、法的な動きによって定義される到達可能空間全体を調査するため、原則として正しいです。 ただし、構成の数はブロックの数に応じて指数関数的に増加します。 各ブロックは複数回移動し、タワー間で組み合わせ分岐を作成できます。 30 ブロックの場合でも、これは実行不可能になります。ここでは、最大で$2 \cdot 10^5$。 

重要な洞察は、各タワー内の順序は重みによって完全に決定され、唯一の本当の自由は、同じまたは異なる重みのブロックを時間の経過とともにタワー間でどのように「再割り当て」できるかにあるということです。 一番上のブロックのみが移動するため、ブロックは、最初のタワーでその上にあるすべてのブロックが最初に削除された後にのみ移動できます。 これにより、依存関係構造が作成されます。各ブロックは、タワーのプレフィックスがクリアされるまで待機する必要があります。 

動きをシミュレートする代わりに、視点を逆転させます。 すべてのブロックが固定のアイデンティティを持ち、初期構成と最終構成の両方に現れることがわかります。 唯一の問題は、最終的な取り決めが、削除中にブロックにアクセスできるようになる方法によって課せられる制約を尊重しているかどうかです。 

これにより、問題は、（先頭のようなアクセシビリティ制約から）適切な順序でブロックを処理するときに、ブロックが最終スタックでどのようにグループ化されるかを一致させることができるかどうかをチェックするだけになります。 このシステムは、プレフィックスの削除のみが許可される制約付き再スタッキングのように動作します。これは、重みごとまたはタワーごとのスタックとカウンターを使用した貪欲な再構築を示唆しています。 

私たちは問題を、最終構成によって暗示されるブロック削除のシーケンスが、初期構成からのプレフィックス ポップの正当なシーケンスと一致しているかどうかを検証することに集約します。

 ## アルゴリズムのチュートリアル

 両方の構成をスタック順のブロックのシーケンスとして処理します。 

1. 各タワーを下から上の順序付きリストに平坦化し、それを反転して上から下への一連のポップとして扱います。 これにより、各タワーがスタック表現に変換されます。 
2. タワースタックを連結し、暗黙的にタワーの分離を維持することにより、初期構成のグローバルシーケンスを構築します。 
3. 最終構成に対しても同じことを行いますが、これを必要な削除のターゲット シーケンスとして解釈します。 
4. 単一のシミュレーション スタックを使用して、初期構成ブロックを消費しながら最終構成ブロックを徐々に一致させるプロセスをモデル化します。 どの時点でも、初期設定からブロックを順番にプッシュし、作業スタックの先頭が最終シーケンスで次に必要なブロックと一致するたびに、それをポップして先に進みます。 
5. 最初のブロックがすべて消費されるまで続行し、可能な限り一致の解決を繰り返します。 
6. 最後にすべての最終ブロックが順番に正確に一致していれば、変換は可能です。 

すべてを 1 つのプロセスにマージできる理由は、各タワー内では相対的な順序が固定されており、タワー間の移動は、ブロックがいつアクセス可能になるかという点でのみ重要であるためです。 スタック シミュレーションは、このアクセシビリティ制約を正確に捉えます。 

### なぜ効果があるのか

 各ブロックは、元のタワーでその上にあるすべてのブロックが削除された後でのみ移動できます。つまり、初期構成では、各タワーがチェーンである部分的な順序が定義されます。 有効な一連の動きは、最終的な配置を考慮したこの部分的な順序の線形拡張に対応します。 貪欲スタック シミュレーションは、ブロックがアクセス可能になったとき、および最終的な構成順序で必要になったときにブロックを一致させるだけで、まさにそのような線形拡張を構築します。 不一致が発生した場合、それはタワー構造によって引き起こされる不可能な順序制約に対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def read_towers(T):
    towers = []
    for _ in range(T):
        arr = list(map(int, input().split()))
        k = arr[0]
        if k == 0:
            towers.append([])
        else:
            towers.append(arr[1:])
    return towers

def flatten(towers):
    res = []
    for t in towers:
        for x in reversed(t):
            res.append(x)
    return res

def solve():
    T = int(input())
    init_towers = read_towers(T)
    final_towers = read_towers(T)

    init = flatten(init_towers)
    target = flatten(final_towers)

    if len(init) != len(target):
        print("N")
        return

    j = 0
    stack = []

    for x in init:
        stack.append(x)
        while stack and j < len(target) and stack[-1] == target[j]:
            stack.pop()
            j += 1

    print("S" if j == len(target) else "N")

if __name__ == "__main__":
    solve()
```実装では、まず両方の構成を読み取り、各タワーを上から下の順序で並べられた一連のブロックに変換します。 これは重要です。移動は常に一番上のブロックに影響するため、自然な処理順序は入力に対して逆になります。 

メイン ロジックはスタックを使用して遅延配置をシミュレートします。 初期構成からブロックをプッシュし、現在のトップが最終構成で次に必要なブロックと一致するたびに、それをすぐに消費します。 一致可能なブロックはできるだけ早く一致する必要があるため、この貪欲な一致は安全です。 遅らせることはブロックを増やすだけなので役に立ちません。 

よくある落とし穴は、タワーが独立したチェーンであることを忘れていることです。 それらを正しい順序で平坦化することが重要です。そうでないと、ブロックがスタック制約に違反して位置間を移動できると誤って想定されてしまいます。

 最終的には対象ブロックが順番に一致するので変形が可能となります。 これは、ブロックがスタック内で一時的に遅延しても、正しく再配置される仕組みを示しています。

 イニシャル =$[6,5,3,1]$最終 =$[6,3,5,1]$| ステップ | プッシュされました | スタック | 次のターゲットインデックス | アクション |

 ここでアルゴリズムは失敗します。ターゲットが 5 の前に 3 を要求しているのに、5 が 1 より上でスタックしているためです。これは、正当な一連の動きによっては解決できません。

 ## 特殊なケース

 重要なエッジケースは、すべてのブロックが同一である場合です。 アルゴリズムは可能な限り常に即座に一致するため、スタックがブロックされることはなく、最終的な答えは常に期待どおりに正になります。 

別のケースは、最初のシーケンスと最後のシーケンスの間の厳密な反転です。 スタック シミュレーションは、より大きなブロックが必要なより小さなブロックへのアクセスを間違った順序でブロックし、ターゲット インデックスが永続的に停止することを正しく検出します。 

3 番目のケースは空のタワーです。 これらはフラット化されたシーケンスにブロックを寄与しないため、シミュレーションには影響せず、特別な処理を行わずに正しく無視されます。
