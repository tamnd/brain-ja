 ## 解決策
 ## 問題の理解

 銀行は、入金額がしきい値に達するかそれを超えた場合にのみ開設できる特別な高金利預金を提供しています`b`。 フィリップは`a`ルーブルが利用可能であり、彼の目標は、この高金利の預金にどれだけの金額を預けることができるかを最大化することです。 

複雑な問題があります。メインの預金を開く前に、フィリップは任意の数の補助預金を開くことができます。 各補助預金は一定の金額を消費します`x`彼の現在の資金から、そのような操作のたびに必要な閾値が減ります`b`による`2x`, ただし、100,000を下回ることはありません。 補助預金に預けられた資金は永久に保管され、再利用することはできません。 このような一連の操作を実行した後、最終的に必要なしきい値条件が満たされている限り、フィリップは残りの資金を使用してメイン デポジットを開くことができます。 

課題は、補助預金の最適な使用のもとで、最終的にどれだけの金額を主預金に入れることができるかを決定することです。 

入力は 2 つの整数で構成されます: 利用可能な金額`a`、および初期しきい値`b`。 出力は主な預金の最大可能値です。 

制約は大きく、両方とも`a`そして`b`1e9まで。 これにより、資金を補助預金に分割する可能なすべての方法を列挙しようとするシミュレーションは除外されます。 すべてのサブセットまたはすべての可能な操作シーケンスを考慮しようとするソリューションは、非常に遅くなります。 

微妙な点は、補助預金のサイズが同じである必要も、数が制限されている必要もないことです。 これにより、整数割り当てに対する暗黙的な連続最適化問題が発生します。この問題では、資金を投じると要件が 100,000 で飽和するまで線形的に減少します。 

よくある落とし穴は、削減に費やした資金が最終要件を満たすのに十分な資本を残しているかどうかを確認せずに、「常にしきい値が十分小さくなるまで引き下げ、その後、残りの資金をメインの入金に使用する」などの貪欲な行動を想定することです。 

別の失敗例が現れるのは、`b`すでに10万人に近づいています。 そのような状況では、一定の点を超えた補助支出は削減に影響を与えません。`b`したがって、これ以上の出費は完全に有害です。 

最後に、もし`a < b`、減らすことでメインデポジットを開くことができる可能性があります。`b`十分。 ただし、`a`意味のある削減をするには小さすぎる`b`下に`a`、その場合、どの戦略も役に立ちません。 

## アプローチ

 強引な解釈は総額を分割しようとするでしょう`a`いくつかの部分に分割されます。一部の部分は補助堆積物として使用され、残りは最終堆積物として確保されます。 補助割り当ての選択ごとに最終しきい値が定義されます`b'`、次のように計算されます`b - 2 * (sum of auxiliary x)`、100,000でクリップされます。 次に、残りのお金が少なくともあるかどうかを確認します`b'`、最終的な入金サイズを最大化します。 

このアプローチは概念的には正しいですが、すぐに組み合わせ爆発に遭遇します。 分割方法の数`a`複数の整数成分への変換は最悪の場合指数関数的になります。 操作の数を制限しても役に立ちません。`a`最大 1e9 になる可能性があり、状態空間の探索は不可能になります。 

重要な観察は、補助預金に費やされる総額のみが重要であり、その分割方法は問題ではないということである。 補助支出の総額が`s`、その場合、しきい値は次のようになります`max(100000, b - 2s)`、残りのお金は`a - s`。 問題は単一の整数を選択することに帰着します`s`で`[0, a]`最終入金額を最大化するために`a - s`の対象となる`a - s ≥ max(100000, b - 2s)`。 

これにより、問題は区分的線形制約を伴う 1 次元の最適化に変換されます。 この構造は、最適点が制約が厳しくなる境界か、しきい値が 100,000 に達する飽和点のいずれかで発生することを示唆しています。 

2 つの体制を考えます。 まず、削減するのに十分な支出をしたとき`b`100,000まで下がります。 第二に、部分的にしか削減しない場合`b`となることによって`b - 2s > 100,000`。 最初の体制では、飽和点を超えて支出しても最終デポジットが減るだけなので、最善の戦略は 100,000 に達するのにちょうど十分な額を支出することです。 2 番目のレジームでは、残存資金としきい値の平等を強制するか、これ以上の支出が有益ではない境界で運用します。 

これは、すべての可能性を探索するのではなく、これらの方程式から導出される少数の候補値をチェックすることになります。

 ## アルゴリズムのチュートリアル

 1. 実現するために必要な支出を計算する`b`100,000まで下がります。 これは`s0 = max(0, (b - 100000 + 1) // 2)`整数で表しますが、より正確には、しきい値条件を考慮します。`b - 2s ≤ 100000`。 この時点を超えて支出しても、要件を削減する効果はありません。 
2. ちょうど飽和状態に達するのに十分な費用を費やした場合を考えてみましょう。`s = min(a, ceil((b - 100000) / 2))`。 これ以降、必要なしきい値は 100,000 になります。 残ったお金は、`a - s`、そして条件は次のことをチェックすることになります。`a - s ≥ 100000`。 その場合、入金サイズは次のようになります。`a - s`。 
3. しきい値が完全に飽和していない状況を考えてみましょう。 この場合、最終的な制約は次のようになります。`a - s ≥ b - 2s`、これを単純化すると、`a + s ≥ b`。 並べ替えると`s ≥ b - a`。 支出により最終デポジットが減少するため、可能な限り最小のデポジットが必要です`s`、つまり`max(0, b - a)`。 
4. 実行可能な候補を評価して両方の体制を結合します。`s`そして最大の結果をもたらすものを選択します`a - s`制約を満たし、超えない範囲で`a`。 

### なぜ効果があるのか

 実現可能条件は、次の観点から凸状の実現可能領域を定義します。`s`。 目的`a - s`で厳密に減少しています`s`したがって、最適解は実現可能な最小値で発生する必要があります。`s`。 実現可能性の境界は、2 つの線形制約によって定義されます。`s ≥ b - a`そして`s ≥ ceil((b - 100000)/2)`。 有効な最小値`s`したがって、これらの下限の最大値によって決定され、次のようにクリップされます。`[0, a]`。 それより大きいもの`s`実現可能性を向上させることなく目的を縮小するだけであるため、既に制約によって捕捉されている飽和によって強制されない限り、最適な内部点は存在しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    a, b = map(int, input().split())

    INF = 10**30

    # Need s such that:
    # 1) a - s >= max(100000, b - 2s)

    # Case split encoded via lower bounds:

    # From a - s >= b - 2s  => s >= b - a
    s1 = max(0, b - a)

    # From a - s >= 100000  => s <= a - 100000, but only relevant if threshold saturated
    # Saturation requirement: b - 2s <= 100000 => s >= (b - 100000 + 1)//2
    if b <= 100000:
        s2 = 0
    else:
        s2 = (b - 100000 + 1) // 2

    # If we choose saturation, s must be at least s2 and at most a - 100000
    if a >= 100000:
        s_sat = s2
        if s_sat <= a - 100000:
            best_sat = a - s_sat
        else:
            best_sat = 0
    else:
        best_sat = 0

    # Non-saturated regime: s = s1 works if it doesn't violate saturation dominance
    s_non = s1
    if s_non <= a:
        remaining = a - s_non
        if remaining >= max(100000, b - 2 * s_non):
            best_non = remaining
        else:
            best_non = 0
    else:
        best_non = 0

    print(max(best_sat, best_non))

if __name__ == "__main__":
    solve()
```コードはまず 2 つの構造レジームを分離します。1 つはしきい値が下限まで引き下げられるもので、もう 1 つはしきい値が下限まで引き下げられないものです。 各体制に必要な最小限の支出を計算し、残りの資本に対して実現可能性をチェックします。 答えは、両方のケースで達成可能な最大デポジットです。 

重要な実装の詳細は、プッシュするために必要な支出を計算する際に、整数の除算を慎重に処理することです。`b`100,000まで下がります。 ここでは、不等号には離散設定での厳密なカットオフが含まれるため、オフバイワンエラーがよく発生します。

 ## 特殊なケース

 いつ`b`がちょうど 100,000 である場合、補助支出に関係なく、このしきい値は変わりません。 最適な戦略は、いかなる補助的な操作も最終的な金額を減らすだけであるため、支出を避け、利用可能な資金をすべて入金することです。
