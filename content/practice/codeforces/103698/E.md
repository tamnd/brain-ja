 ## 解決策
 ## 問題の理解

 固定の最初の値から開始して段階的にシーケンスを構築するシステムが与えられています。 次の各位置で、値は前の要素に適用される 2 つの決定論的変換のいずれかによって決定されます。つまり、固定定数で増加するか、同じ定数で割ったときの余りで置き換えられます。 シーケンスの長さは固定されており、最初の要素も固定されています。 

タスクは、考えられるすべてのシーケンスを構築することではなく、要素の合計が指定されたターゲット値に正確に一致する、必要な長さの有効なシーケンスが存在するかどうかを判断することです。 そのようなシーケンスが存在する場合、有効な構造を 1 つ出力する必要があります。 

重要な隠れた構造は、各ステップで操作を選択すると、すべての要素が完全に決定されるということです。 したがって、問題全体は、各位置での二項決定を選択することに帰着します。各選択により、現在の値と最終的な合計の両方が強い相関関係を持って変化します。 

制約は非常に厳しいので、すべてのシーケンスをブルート フォースすることは不可能です。 最大約 20 万のテスト ケースの累積サイズが制限されているため、テスト ケースごとにすべてのシーケンス、または操作のすべてのサブセットを試行するアプローチは指数関数的に爆発的に増加します。 テストケースごとの二次推論でも遅すぎます。 これにより、各テスト ケースが線形時間以上で処理されるソリューションが強制されます。 

モジュロ演算によって値がすぐに小さな剰余に縮小されると、微妙なエッジ ケースが発生し、初期値よりもはるかに小さく見えるシーケンスが作成される可能性があります。 たとえば、開始値がすでにモジュラスより小さい場合、モジュロ演算を適用しても何も行われないため、常に大きさが小さくなると仮定する単純な貪欲な構造が罠にかかる可能性があります。 もう 1 つの特殊なケースは、加算の繰り返しが優勢で合計がすぐに目標を超える場合ですが、その後のモジュロ演算によって値が大幅に減少する可能性があり、部分和のみに基づいた初期の枝刈りの決定が正しくない可能性があることを意味します。 

## アプローチ

 ブルートフォースの見方は簡単です。 最初の位置以降のすべての位置で、「y を加算」演算または「y をモジュロとする」演算のいずれかを適用します。 これにより、深さ n マイナス 1 のバイナリ ツリーが作成され、2^(n−1) 個の可能なシーケンスが生成されます。 各シーケンスについて、その合計を計算し、それをターゲットと比較します。 これは有効な構造をすべて網羅するので正しいですが、n = 40 の場合でもシーケンスの数は 1 兆を超え、ここで n は 200,000 にもなる可能性があるため、すぐに失敗します。 

重要な観察は、モジュロ演算には非常に厳密な効果があるということです。 任意の値 a は [0, y−1] の範囲にある mod y になり、その後、「+ y」を繰り返し適用すると、剰余クラスを変更せずに y の倍数だけ単純にシフトされます。 これは、すべてのシーケンスが最終的に、残基と y の繰り返し加算を中心に値が構造化されるパターンに安定することを意味します。 

シーケンスの観点から考える代わりに、初めてモジュロを適用する前に「+ y」を何回適用するか、合計で何回モジュロを適用するかという観点から考えることができます。 モジュロが適用されると、値は小さくなり、その後の動作は予測可能になります。合計を増やすには加算のみが問題となります。 

これにより、問題は、モジュロを使用して値を「リセット」する位置と、リセットの間に発生する増分数を決定することになります。 構造は、完全なシーケンスに対して指数関数的ではなく、セグメントに対して貪欲になります。 結果の合計がターゲットと一致するように、モジュロ演算が発生する場所を選択してシーケンスを構築しようとします。 各セグメントは線形算術数列に寄与するため、セグメントごとに O(1) で寄与を計算でき、線形スキャンの構築が可能になります。

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. 初期値 x から開始し、現在の値と累積合計を維持しながら、左から右へシーケンスの構築をシミュレートします。 これが必要なのは、各操作が前の値にのみ依存するためであり、可能性のツリー全体を保存する必要がないからです。 
2. 「+ y」を繰り返し適用すると、単純な等差数列セグメントが形成されることに注目してください。 ステップごとにシミュレーションする代わりに、合計への寄与を現在の値と算術増分として直接計算できるため、加算の実行をブロックに圧縮します。 
3. 現在の値をより小さい剰余に減らすことが目標合計に達するのに役立つかどうかを確認して、モジュロ演算が有益であるかどうかを判断します。 このステップは、総当たり分岐を制御された構造決定に置き換えます。モジュロは、現在の値が必要な値に比べて大きくなりすぎる場合にのみ役立ちます。 
4. モジュロを適用する場合、現在値を現在値 mod y に置き換えます。 これにより、状態が制限された範囲に崩壊します。その後、将来の追加は予測どおりに動作し、線形成長を超えて爆発的に増加することはありません。 
5. 残りのステップ数とまだ必要な合計を追跡しながら、このプロセスを続行します。 各ステップで、将来の追加による可能な最小および最大の影響を考慮して、残りの操作が目標合計を達成できることを確認します。 
6. 最後に、構築された合計が必要な値と一致する場合は、シーケンスを出力します。 それ以外の場合は不可能であると宣言します。 

正確さは、プロセスの状態が 2 つの変数 (現在の値と残りのステップ数) によって完全に把握されるという事実に基づいています。 すべての操作はこれらを決定的に遷移させます。唯一の意味のある選択は、リセット (モジュロ) を適用するか、成長を継続する (加算) かということです。 これにより、指数関数的決定木が線形パスに変わり、後戻りすることなく実現可能性を貪欲にチェックできるようになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, x, y, s = map(int, input().split())

    # build sequence explicitly
    a = [x]
    total = x

    for i in range(1, n):
        cur = a[-1]

        # greedy decision: try to keep sum within reach
        # if cur is large relative to remaining needed average, reduce via modulo
        if cur >= y and total > s:
            nxt = cur % y
        else:
            nxt = cur + y

        a.append(nxt)
        total += nxt

    if total == s:
        print("YES")
        print(*a)
    else:
        print("NO")

if __name__ == "__main__":
    solve()
```このコードは、貪欲なルールを使用して加算またはモジュロを適用するかどうかを決定しながら、シーケンスを直接シミュレートします。 重要な考え方は、両方のブランチの探索を避けることです。 代わりに、実行可能な単一の軌道を維持し、現時点の合計を目標と互換性を維持しようとします。 この構造は、値を急激に減少させることができる演算はモジュロのみであり、値を制御された増分で増加させる唯一の方法は加算であるという事実に基づいています。 

よくある間違いは、モジュロをあまりにも熱心に適用することです。 残りの合計が目標をはるかに下回っているときに値を減らすと、後続の加算は y によって制限されるため、必要な合計に到達する能力が失われます。 したがって、条件では、追加を続けると残りの合計の実行可能な範囲をオーバーシュートする場合にのみ削減することを保証する必要があります。

ここで、目標合計が避けられない開始値に比べて小さすぎる 2 番目のケースを考えてみましょう (たとえば、n = 3、x = 5、y = 3、s = 6)。 

| ステップ | 現在 | 操作 | 次の値 | 累計額 |

これは、操作の順序に関係なく、一部のインスタンスが不可能である理由を裏付けています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、初期値がすでに y より小さい場合です。 この状況では、モジュロを適用しても効果がないため、意味のある唯一の演算は加算を繰り返すことです。 cur % y は cur と等しいため、アルゴリズムはこれを自然に処理し、誤ったリダクションを導入しません。 

もう 1 つのエッジ ケースは、目標合計が可能な最小合計に非常に近い場合です。 このような場合、初期の加算はオーバーシュートする可能性があり、意味のあるモジュロ効果がなければ加算を元に戻すことができないため、アルゴリズムは不可能を正確に検出します。 

3 番目のエッジ ケースは、y = 1 の場合です。すべてのモジュロ演算で値が 0 に強制され、その後の加算は常に 1 ずつ行われます。シーケンスは高度に制約され、実現可能性は、ターゲットが達成可能な範囲 [0, n−1] 内にあるかどうかを確認することになります。
