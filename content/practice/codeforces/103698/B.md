 ## 解決策
 ## 問題の理解

 このタスクでは、タイルに 1 から n までの番号が付けられ、それぞれの数字が任意の量で表示される、簡略化された麻雀のようなシステムについて説明します。 手全体はこれらの数字の単なる集合です。 また、何が有効なグループとしてカウントされるかを定義する 2 つのパラメーターも与えられます。 

グループは、同じ番号の正確に x 個の同一のタイルである「ポン」、またはそのグループ内にそれぞれ 1 回出現する y 個の連続する数字である「チョウ」のいずれかです。 すべてのタイルを残り物なくそのようなグループに分割できた場合、ハンドは有効であるとみなされます。 

したがって、問題は、指定された周波数配列をサイズ x のブロック (単一のインデックスで) とサイズ y のブロック (連続したインデックスにまたがる) に完全に分解できるかどうかを判断することに帰着します。ここで、Chow は、連続する y 位置のそれぞれから 1 ユニットを消費します。 

主な問題点は、Pong ブロックが 1 つのインデックスに対してローカルであるのに対し、Chow ブロックは隣接するインデックスを結合するため、1 つの値での決定が将来の可能性に影響を与えることです。 この相互作用により、貪欲なローカル決定は安全ではなくなります。 

制約は n が最大 1000、カウントが最大 10^9 ですが、x と y は非常に大きくなる場合もあります。 これにより、分解に対する指数関数的な検索や、ポンとチョウをさまざまな順序で貪欲に取得するすべての組み合わせを試行するシミュレーションが即座に除外されます。正確なカウントを追跡しようとすると、「残りのタイル」に対する単純な DP ですら大きすぎるためです。 

y が n に対して大きい場合、微妙なエッジ ケースが発生します。 たとえば、y > n の場合、Chow はまったく不可能であるため、問題はすべての a[i] が x で割り切れるかどうかを確認することになります。 もう 1 つの注意が必要な状況は、x が大きいが y = 1 の場合に発生します。その場合、チャウは単一の要素であり、x によって引き起こされる特定のパリティのような方法でカウントが一致しない限り、事実上すべてのタイルを常に消費できます。 

隠れた主な危険は、可能な限り貪欲に Pong を形成することが安全だと思い込むことです。 たとえば、x = 3 で、あるインデックスに 3 つのタイルがある場合、有効なグローバル パーティションが存在していても、Pong をすぐに消費すると、後で必要となる Chow の形成が妨げられる可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、左から右へグループを形成するあらゆる方法をシミュレートしようとします。 各インデックス i で、a[i] から取得するポンの数と、将来のポジションを消費する i で開始するチャウの数を決定できます。 各選択は残りのカウントに影響を与えるため、これは残りのサフィックス制約に応じて状態を伴う分岐検索になります。 最悪の場合、すべてのポジションでポンの選択肢が O(a[i]/x) あり、チャウの開始回数については追加の選択肢があり、n ポジション全体で指数関数的に爆発することになります。 メモ化を行ったとしても、状態空間は最大 y−1 個前の位置からの残りの部分的な寄与に依存するため、実行不可能になります。 

重要な洞察は、各ポジションで現在「アクティブ」になっているチョウの数を追跡する前方スイープとしてプロセスを扱うことです。 位置 i で開始されたチョウは、i から i+y-1 までのそれぞれから 1 つのタイルを消費します。 したがって、位置 i では、最後の y−1 位置で開始されたチャウがまだ i に影響を与えている数を知る必要があるだけです。 これにより、問題はスライディング ウィンドウ効果を伴う貪欲な実行可能性チェックに変換されます。 

各インデックスで、以前のチャウによってすでに予約されているタイルの数がわかったら、i にある残りの利用可能なタイルをいくつかのポンと、場合によっては i から始まる新しいチャウに分割する必要があります。 Pong は x 単位を消費し、Chow は正確に y 開始位置を消費するため、この構造では、必要な Chow の使用量を考慮した後、x を法として残りを処理する方法に割り算の制約が課せられます。 

これにより、問題はリニア スキャンに縮小され、アクティブな Chow に対してキューのような構造が維持され、ローカルで一貫性が強化されます。 各チョウには固定スパンとポジションごとの固定コストがあるため、以前の決定を再検討する必要はありません。

 ## アルゴリズムのチュートリアル

 1. 先に開始したチョウによって各位置ですでに消費されているタイルの数を維持しながら、インデックスを 1 から n までトラバースします。 これは、以前の決定によって課された強制的な使用を表しています。 
2. インデックス i で、アクティブなチョウによってすでに使用されている数を引いた後、残りの利用可能なタイルを計算します。 この値が負になると、以前の Chow 決定が位置 i を過剰に消費するため、設定は不可能になります。 
3. 位置 i にいて、アクティブなチョウを計算した後でもまだタイルが残っている場合は、i で開始する新しいチョウの数を決定します。 ここで開始されるそれぞれの新しい Chow は、i から 1 つのタイルを消費し、次の y-1 位置での使用も予約します。 
4. 必要なだけ、または可能な限り多くのチョウを割り当てた後、位置 i にある残りのタイルは x で割り切れなければなりません。 そうでない場合は、ポンを組み合わせても残りを修正できないため、答えは直ちに不可能になります。 
5. i にある残りのタイルを x で割ってポンに変換し、続行します。 
6. 前に進むときに効果が除去されるように、位置 i+y で終了するチョウの数を記録するスライド構造を維持します。 

### なぜ効果があるのか

 このアルゴリズムが機能するのは、すべての Chow が固定長の間隔制約であり、その範囲にわたる各位置で正確に 1 単位の需要に寄与するためです。 食事が開始されると、その効果は完全に決定され、後から調整することはできません。 これにより、左から右への一方向の依存関係が作成されます。 各指数では、以前の決定に関するすべての不確実性が、現在の「アクティブな需要」値にすでに圧縮されています。 Pong は純粋にローカルであり、位置を越えて相互作用しないため、唯一のグローバル カップリングは Chow から得られ、それらはスライディング ウィンドウの状態によって完全に表現されます。 これにより、ローカルで実行可能な割り当ては、後戻りすることなく一貫して前方に拡張されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, x, y = map(int, input().split())
    a = list(map(int, input().split()))

    # active_chows[i] will track how many chows start at i and affect future positions
    active = [0] * (n + 5)
    current_active = 0

    for i in range(n):
        current_active += active[i]

        # tiles available at i after consuming by active chows
        if current_active > a[i]:
            print("No")
            return

        remaining = a[i] - current_active

        # try to start new chows at i
        if y <= n:
            start = remaining  # start as many chows as possible
        else:
            start = 0  # cannot form any chow

        current_active += start

        # schedule removal after y positions
        if i + y < len(active):
            active[i + y] -= start

        remaining -= start

        if remaining % x != 0:
            print("No")
            return

        # remaining is handled by pongs, no need to track further

    print("Yes")

if __name__ == "__main__":
    solve()
```コードは、各位置でアクティブな Chow 制約の数の実行カウントを維持します。 利用可能なタイルからそれらを差し引き、以前の決定で存在するタイルよりも多くのタイルが必要なポジションは即座に拒否されます。 その後、各インデックスで可能な限り多くの Chow を貪欲に開始します。これは、Chow の開始を遅らせても、将来の制約が増えるだけで利益が得られないためです。 

残りのタイルは Pong で正確に埋めることができる必要があるため、x による割り算チェックが最終的なローカル整合性条件となります。 

よくある落とし穴は、チャウが現在のポジションだけでなく将来のポジションも消費することを忘れていることです。 の`active`配列はこの伝播をエンコードし、開始された各 Chow が時間内に自動的に圧力を加えます。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

        if rem % x != 0:

    return "Yes"

 ## 特殊なケース

 y > n の場合、アルゴリズムは当然 Chow の開始を妨げるため、すべての位置が x で正確に割り切れる必要があります。 たとえば、入力`n=5, x=2, y=10, a=[2,2,2,2,2]`すべてのポジションが有効なポンであるため、受け入れられます。 

x = 1 の場合、カウントは 1 で割り切れるため、Chow 処理後に残ったすべてのタイルが自動的に有効になります。アルゴリズムは、Chow の実現可能性をチェックするだけになります。 

貪欲さが疑わしいと思われるケースは、初期のチョウ形成が後で柔軟性を低下させる場合です。 たとえば、i で Chow を開始すると、将来の Chow に必要なリソースが消費される場合でも、遅延が発生しても中間位置での残りの圧力が増加するだけで、減少することはないため、アルゴリズムは引き続き機能します。そのため、Chow を延期しても、貪欲なアプローチが見逃す有効な構成を作成することはできません。
