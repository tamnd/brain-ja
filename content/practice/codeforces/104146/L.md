 ## 解決策
 ## 問題の理解

 私たちには、各セルが通常の地面、溶岩、または泥のいずれかであるグリッド世界が与えられています。 シンディは最初は南を向いた固定セルからスタートし、ターゲット セルに到達する必要があります。 動きは単なるグリッドウォーキングではなく、方向と環境との相互作用を制御する小さな命令セットによって駆動されます。 

重要な問題は泥です。 泥の独房に入るのは、その独房に木の板が置かれている場合にのみ安全です。 シンディが板なしで泥の上を踏んだ場合、彼女は即座に無効になります。 溶岩は常に禁止されています。 板は拾い上げ、（一度に最大 1 つずつ）運んで、再度配置することができ、最初の板の位置はグリッド上に点在しています。 

したがって、タスクは単なるパス検索ではなく、リソースを移動して再利用できるリソース制約の下でのパス検索です。 出力はパス自体ではなく、シンディの動きをシミュレートする一連のコマンドであり、シンディが危険な泥や溶岩に足を踏み入れることがなく、最終的にターゲットに到達することが保証されます。 

制約は、グリッド位置と少量の余分な状態から導出される状態空間に対するグラフベースのソリューションには十分小さいです。 R と C は最大 100 であるため、グリッドのセルは最大 10,000 個になります。 方向と在庫によって状態を拡張する素朴なアプローチはすでに実現可能ですが、それは板処理における不必要な組み合わせ爆発を回避した場合に限ります。 

明らかではない問題は、板が再利用可能で移動可能であること、つまりグリッドが静的ではないことです。 実現可能性はルートに沿って板を再配置できるかどうかに依存するため、板を固定障害物として扱う単純な BFS は失敗します。 もう 1 つの微妙な問題は、動きは向いている方向に依存するため、状態ベースの検索では方向を考慮する必要があり、そうでない場合は遷移が不正確になることです。 

3 番目の微妙なエッジ ケースは、泥セルがスタートとターゲットの間のカット パス上にあるが、最初に他の場所から板を取得した場合にのみ安全に横断できる場合に発生します。これにより、向きの制約と相互作用する迂回路が強制される可能性があります。 

## アプローチ

 最も直接的な考え方は、これを拡張された状態空間上の最短経路問題として扱うことです。 状態には、シンディの位置、方向、板を運んでいるかどうかが含まれます。 遷移は、L、R、F の操作に加え、該当する場合は G と P に対応します。 

このブルートフォース状態グラフは、ゲームのルールを正確にモデル化しているため、原理的には正しいです。 ただしグラフは大きいです。 セル数は最大 10,000、方向は 4、キャリー状態は 2 なので、約 80,000 状態と十分です。 本当の問題は状態数ではなく、板の配置が固定されていないことです。移動が有効かどうかは、泥セルに現在板があるかどうかによって決まり、それ自体が変更可能なグローバル構成です。 板の位置もエンコードしようとすると、状態空間は指数関数的になります。 

重要な洞察は、板の恣意的な再配置を考慮する必要がないということです。 有効なソリューションはどれも正規化できるため、各板が非常に局所的な方法で使用されます。板は泥タイルまで運ばれ、配置され、横断に使用され、オプションで後で別の横断に必要な場合にのみ回収されます。 グリッドが小さく、板が区別できないため、選択したルート上のすべての泥タイルが必要なときに少なくとも 1 つの板にアクセスできるようにするという問題に減らすことができます。 

これは削減につながります。任意のグローバルな板材の物流をシミュレートする代わりに、板材を固定の歩行経路に沿って輸送できる消耗品のトークンとして扱います。 移動自体にコストがかかるため、スタートからターゲットまでの経路を設計し、ぬかるみに入るときは必ず事前に板を配置します。

したがって、問題は、必要なすべての泥の侵入が到達可能な厚板源によってサポートされていることを確認しながら、グリッド上で実行可能な歩行を見つけることになります。 これは、ステップの前に明示的に板を配置しない限り、板のない泥タイルの上にいることは禁止されている拡張グラフ上で BFS によって処理できます。

 ## アルゴリズムのチュートリアル

 各状態がシンディのセル、向いている方向、板を持っているかどうかによって定義される状態グラフを作成します。 さらに、現在どの泥タイルが厚板で「覆われている」かを追跡しますが、完全な構成を明示的に保存するのではなく、パスの構築中に P コマンドを物理的に実行するときにのみカバレッジを導入します。 

アルゴリズムは次のように進行します。 

1. 開始状態から BFS を実行します。この状態では、Cindy が開始セルにいて、南を向いており、板を持っていません。 各 BFS ノードは有効な物理的状況に対応しています。これは、シンディが危険な泥や溶岩に入ったことがなく、これまでのすべての泥への侵入がサポートされていることを意味します。 
2. 各状態から、左折および右折するためのトランジションを生成します。 これらは有効性に影響しませんが、方向を変更します。これは、前進が方向に依存するため必要です。 これらのトランジションは、シンディをプランクや安全なルートに合わせるために必要になる場合があるため、常に含めます。 
3. 前進を生み出します。 前進は、次のセルが境界内にあり、溶岩ではなく、泥ではないか、現在その上に板が置かれている場合にのみ有効です。 泥で板がない場合は直接横断することはできません。 
4. ピックアップと配置の操作が含まれます。 シンディが板を含むセルに直面していて、現在板を持っていない場合、G トランジションを許可します。 シンディが板を持っていて、前のセルが有効で板が空の場合、P 遷移を許可します。 これらの操作により、将来の泥道を安全に通過できるように、道に沿って板を再配置することができます。 
5. BFS 中に、親ポインターと各状態に到達するために使用されるコマンドを保存します。 ターゲット セルに到達したら、バックトラッキングによってコマンド シーケンスを再構築します。 
6. 再構築後、コマンド文字列が制約を尊重し、一貫性のないプランクの仮定に依存していないことを確認するために、最終的な正規化パスが必要になる場合があります。 すべての有効性は BFS 中に適用されるため、このパスは構造の再構築のみです。 

重要な不変条件は、すべての BFS 状態が Cindy とプランク システムの物理的に実現可能な構成に対応していることです。 特に、泥セルに入るときは、シーケンスの早い段階で板が明示的にそこに配置されているか、最初から存在していた場合にのみ、その侵入が可能になります。 実行時に有効な P 操作のみを許可するため、不可能なプランク構成を作成することはありません。 したがって、BFS によって検出されたパスはすべて実際のコマンド システムで実行可能であり、再構築された文字列は成功することが保証されます。 

## Python ソリューション```python
import sys
from collections import deque

input = sys.stdin.readline

# Directions: 0=S, 1=W, 2=N, 3=E (arbitrary consistent choice)
dr = [1, 0, -1, 0]
dc = [0, -1, 0, 1]

def solve():
    R, C = map(int, input().split())
    rs, cs, rt, ct = map(int, input().split())
    rs -= 1; cs -= 1; rt -= 1; ct -= 1

    grid = [list(input().strip()) for _ in range(R)]

    k = int(input())
    plank = [[False] * C for _ in range(R)]
    for _ in range(k):
        i, j = map(int, input().split())
        plank[i - 1][j - 1] = True

    # state: (r, c, dir, carry)
    # visited is 4D
    vis = [[[[False] * 2 for _ in range(4)] for _ in range(C)] for _ in range(R)]
    parent = {}
    q = deque()

    start = (rs, cs, 0, 0)
    vis[rs][cs][0][0] = True
    q.append(start)
    parent[start] = None

    def ok_cell(r, c):
        if not (0 <= r < R and 0 <= c < C):
            return False
        if grid[r][c] == '#':
            return False
        return True

    end_state = None

    while q:
        r, c, d, carry = q.popleft()

        if (r, c) == (rt, ct):
            end_state = (r, c, d, carry)
            break

        # turn left
        nd = (d + 1) % 4
        ns = (r, c, nd, carry)
        if not vis[r][c][nd][carry]:
            vis[r][c][nd][carry] = True
            parent[ns] = (r, c, d, carry, 'L')
            q.append(ns)

        # turn right
        nd = (d + 3) % 4
        ns = (r, c, nd, carry)
        if not vis[r][c][nd][carry]:
            vis[r][c][nd][carry] = True
            parent[ns] = (r, c, d, carry, 'R')
            q.append(ns)

        # forward
        nr, nc = r + dr[d], c + dc[d]
        if ok_cell(nr, nc):
            if grid[nr][nc] == '~' and not plank[nr][nc]:
                pass
            else:
                ns = (nr, nc, d, carry)
                if not vis[nr][nc][d][carry]:
                    vis[nr][nc][d][carry] = True
                    parent[ns] = (r, c, d, carry, 'F')
                    q.append(ns)

        # pick up plank (G)
        if carry == 0 and plank[r][c]:
            ns = (r, c, d, 1)
            if not vis[r][c][d][1]:
                vis[r][c][d][1] = True
                parent[ns] = (r, c, d, carry, 'G')
                q.append(ns)

        # place plank (P)
        if carry == 1 and ok_cell(r + dr[d], c + dc[d]):
            nr, nc = r + dr[d], c + dc[d]
            if grid[nr][nc] != '#' and not plank[nr][nc]:
                ns = (r, c, d, 0)
                if not vis[r][c][d][0]:
                    vis[r][c][d][0] = True
                    parent[ns] = (r, c, d, carry, 'P')
                    q.append(ns)

    if end_state is None:
        print("NO")
        return

    # reconstruct
    cmd = []
    cur = end_state
    while parent[cur] is not None:
        pr, pc, pd, pcarry, act = parent[cur]
        cmd.append(act)
        cur = (pr, pc, pd, pcarry)

    cmd.reverse()
    print("YES")
    print("".join(cmd))

if __name__ == "__main__":
    solve()
```BFS はすべての合法的なマイクロアクションを明示的にエンコードするため、長い幾何学的な動きについての推論が回避されます。 訪問された構造により、同等の設定を再度訪問することができなくなり、親マップが有効なコマンド シーケンスを再構築します。 最もデリケートな部分は前方への移動条件です。泥は現在板が存在する場合にのみ許可されます。 これは、実現可能性の観点から地形タイプを区別する唯一のルールです。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、ターゲットへの唯一の経路が泥の中を通過するが、唯一の板が溶岩の後ろにあるか、迂回する必要がある場合です。 BFS はこれを自然に処理します。これは、泥のトラバースを開始する前に、到達可能なすべての板の相互作用を調査し、違法な前方移動が決して待ち行列に入れられないことを保証するためです。 

もう 1 つのエッジケースは、シンディが泥の近くからスタートしたが、利用できる板がまだない場合です。 このアルゴリズムでは、すぐに泥に足を踏み入れることはできませんが、最初に G または P 操作を実行して板の位置を変更する可能性があります。 これらは状態として明示的にモデル化されているため、BFS は有効な構成に達するまで移動を正確に遅延させるか、構成が存在しない場合は不可能と結論付けます。
