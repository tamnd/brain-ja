 ## 解決策
 ## 問題の理解

 私たちには数字のリストが与えられ、それぞれの数字は生徒が購入に応じるキャンディーの数を表しています。 お店では生徒を順番に処理していますが、生徒が満足する順序は私たちが自由に選ぶことができます。 すでに「コミット」または販売されているキャンディーの総量を決定すると、生徒は自分の要件が少なくともその量である場合にのみ満足できます。 私たちの仕事は、生徒にサービスを提供する最適な順序を選択することで、何人の生徒を満足させることができるかを最大化することです。 

重要な構造は、各生徒にはしきい値があり、生徒にサービスを提供すると、累積的な意味である程度の「容量」が消費されるということです。 私たちは、できる限り多くの制約を累積合計の増加に当てはめようと効果的に試みており、以前の選択が後の選択が実現可能かどうかに影響を与えます。 

生徒の数が多い場合 (たとえば最大 200,000 人)、異なるサブセットや並べ替えを繰り返し試行する O(n^2) シミュレーションでは遅すぎます。 およそ 10^5 または 2×10^5 の要素では、O(n log n) または O(n) の解が期待されます。 これは、ソートまたは貪欲な選択が唯一の実行可能な方向であることを直ちに示唆します。 

学生を元の順序または降順で処理しようとすると、微妙な失敗が発生します。 大きな要件を最初に取り上げると、累積合計が急激に膨らみすぎる可能性があり、以前に満たすことができた小さな要件を適合させることができなくなります。 

たとえば、要件が次のとおりであるとします。`[5, 1, 2]`。 加工すれば`5`まず、累積和がすぐに大きくなるため、解釈によってはスキップする可能性があります。`1`そして`2`または実現可能性を誤って評価します。 正解は奉仕することです`1`、 それから`2`、 それから`5`これにより、制御された累積的な進行で 3 つすべてを満たすことができます。 

最大の困難は、処理の順序によって累積制約が増大する速度が決まり、最適な戦略とは増大を可能な限り遅らせる戦略であることを認識することです。 

## アプローチ

 この強引なアイデアは、生徒の可能な順序をすべて試して、その順序で何人が満足できるかをシミュレーションすることです。 順列ごとに現在までの合計を維持し、満たされたしきい値の数を数えます。 これはプロセスを直接モデル化するため機能しますが、階乗的な複雑性があります。 n 人の生徒がいれば、n 人います！ 1 つの順列を評価するだけでも O(n) のコストがかかるため、非常に小さい n を超えるとこのアプローチは実行不可能になります。 

重要な観察は、満足した生徒の数を最大化する唯一の方法は、累積合計をできるだけ長くできるだけ小さく保つことであるということです。 大きな要件を持つ学生を早期に選択すると、累積合計が不必要に増加し、将来の参加が妨げられる危険があります。 これは、累計に対する制約が最も少ない要件であるため、常に小さな要件を最初に優先する必要があることを示唆しています。 

要件を昇順に並べ替えると、最小値から最大値まで貪欲に処理し、累計を維持できます。 現在の要件が少なくとも現在の合計額である場合は、その学生を含めて、それに応じて合計額を増やすことができます。 そうでない場合は、それらを含めても、より多くの制約を満たすことができずに合計がさらに増加するだけであるため、それらをスキップします。 

これにより、問題は順列にわたる組み合わせ検索からソート後の単一の線形スキャンに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (すべての順列) | O(n! · n) | O(n) | 遅すぎる |
 | ソート + 貪欲スキャン | O(n log n) | O(1) または O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは、常に最小の制約を最初に考慮するように、すべての学生の要件を降順でない順に並べ替えることから始めます。 これにより、現在の累積合計を考慮して、すべてのステップが実行可能である可能性が最大限に高まることが保証されます。 

実行中の変数を初期化します`cur = 0`、すでにコミットされたキャンディーの合計量を表し、カウンター`ans = 0`、何人の生徒が満足したかを追跡します。 

次に、ソートされたリストを繰り返し処理します。 それぞれの値について`x`, 現在の累計を考慮して、この生徒を満足させることが可能かどうかを確認します。 

もし`x >= cur`、この生徒を含めます、増分します`ans`1つずつ更新してください`cur += x`。 このアップデートが安全である理由は、現在の状態に対応できる十分な要件を持つ学生のみを対象としているためです。 

もし`x < cur`、この貪欲なフレームワークでは彼らを含めることは意味をなさないため、この学生をスキップします。 すべての将来の値は (ソートのため) 以上であるため、スキップすることで、実行不可能な移行で機会を無駄にしないことが保証されます。 

最後に出力します`ans`。 

### なぜ効果があるのか

 どの時点でも、アルゴリズムは次の不変条件を維持します。`cur`処理された要素のサブセットを選択することによって達成できる最小の累積合計です。 ソートされた順序で処理することにより、大きな要件の後に小さな要件が発生することがなくなります。 この単調性により、値が現在の合計を満たすことができなくなると、その後の構造ではその値を回復できないことが保証されます。 実現可能な最小の要素をすべて取得するという貪欲な選択により、将来の選択の最大限の拡張性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
a = list(map(int, input().split()))

a.sort()

cur = 0
ans = 0

for x in a:
    if x >= cur:
        ans += 1
        cur += x

print(ans)
```このソリューションは、要件のリストを読み取り、弱い制約が最初に処理されるように並べ替えることから始まります。 変数`cur`蓄積されたコミットメントを追跡し、`ans`正常にサービスを提供できた生徒の数を数えます。 各反復では、累積制約に違反せずに現在の学生を含めることができるかどうかが決定されます。 条件`x >= cur`これは、ソリューションが有効な場合にのみソリューションを拡張することを保証する重要な実現可能性チェックです。 

よくある間違いは、不等式を逆転させたり、更新したりすることです`cur`実現可能性を確認する前に、間違って判断してください。 順序は重要です。最初に確認し、次に更新する必要があります。 もう 1 つの微妙な問題は、生徒をスキップしてもリセットまたは変更されないことを忘れていることです。`cur`。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての値が同一である場合です。 インプットを考慮する`[3, 3, 3]`。 並べ替え後も変更されません。 アルゴリズムは次のように進行します。`cur = 0`、 初め`3 >= 0`だから取って、`cur = 3`。 次`3 >= 3`だから取って、`cur = 6`。 次`3 >= 6`は false なのでスキップします。 出力は`2`。 これは、累積合計が繰り返し値を超えると、均一な入力でも完全な包含を破る可能性があることを示しています。 

もう 1 つのエッジ ケースは、非常に小さい値の後に大きな値が続く場合です。`[1, 100, 100]`。 アルゴリズムが必要とするのは、`1`、 それから`100`、そして決勝`100`実行不可能になるため`cur`大きくなりすぎました。 この痕跡は、初期の小さな内包物がその後の同一の大きな内包物をブロックする可能性があることを裏付けています。これがまさに、成長を制御するために選別と貪欲な受け入れが必要な理由です。
