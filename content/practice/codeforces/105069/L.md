 ## 解決策
 ## 問題の理解

 各ノードが開始括弧または終了括弧のいずれか 1 つの文字を保持するツリーが与えられます。 複数のクエリの場合、2 つのノード間の一意のパスに沿って文字を調べ、その結果のシーケンスが問題で定義されている「適切な」括弧シーケンスの特別な概念を満たすかどうかを判断するように求められます。 

古典的なバランスの取れた括弧の定義とは異なり、ここでの条件は意図的に緩めですが、構造的に制約されています。 シーケンスは偶数の長さで、最初の文字は左括弧、最後の文字は閉じ括弧である必要があります。 さらに、重要な構造上の制限は、一連の同一の括弧がどのように相互作用するかに関するものです。セグメントに 2 つの連続する開始括弧が出現する場所が含まれると、連続する閉じ括弧を含むセグメントが間違った順序でそのセグメントを支配するような方法で「インターリーブ」することはできません。 意図された解釈は、ステートメントで説明されているプロセスの下で無制限の成長を可能にするような形で、強力な閉鎖構造の後に深い開口構造が現れる構成をシーケンスが許可してはならないということです。 

これをより運用的に考えるには、完全なバランスではなく、ブラケット文字列の大まかな構造的特徴のみを追跡する必要があるということです。 私たちは、その長さ、正しく始まり、正しく終わるかどうか、内部配置に連続する同一の括弧間の禁止された相互作用が含まれているかどうかを考慮します。 

入力サイズは、最大約 1 つのツリーを意味します。$10^5$ノードと同様の数のクエリ。 単一のパスは線形である可能性があるため、クエリごとにパスを再計算するソリューションはすぐに遅すぎます。$n$、につながる$O(nq)$最悪の場合の行動。 平$O(n \log n)$クエリごとのサイズが大きすぎます。 これにより、高速パスの集約、通常はセグメントのマージによるバイナリ リフティングをサポートする構造が求められます。 

単純なアプローチでは、各クエリのパス文字列を明示的に抽出し、条件を直接テストします。 これは、単純なチェーン形状のツリーでは失敗します。 ツリーが 100,000 ノードのラインで、エンドポイント間に 100,000 のクエリがある場合、総作業量は 2 次になります。 

エッジ ケースは、パスの長さは短いが、構造が制約に違反している場合に発生します。たとえば、長さまたはエンドポイントがすでに失敗している「(()」または「())」のようなパスです。 もう 1 つの微妙なケースは、サブパスのローカルな正確性が連結後のグローバルな正確性を保証しない場合です。これは、禁止パターンが個々のセグメントだけでなく、結合ポイント全体の相対的な順序に依存するためです。 

## アプローチ

 ブルート フォース ソリューションでは、クエリごとに親ポインターまたは DFS を使用してクエリされたノード間のパスを直接構築し、文字を連結し、条件をチェックします。 これは定義を文字通りに評価するため、正しいです。 ただし、各クエリには時間がかかる場合があります。$O(n)$、そして$q = 10^5$、全体の複雑さは次のように縮退します。$10^{10}$、それは不可能です。 

重要な洞察は、クエリが連結下のパス文字列について尋ねることと、十分な概要情報を保存すれば連結を連想させることができるということです。 サブツリーまたはジャンプ セグメントの文字列全体を保存する代わりに、2 つの部分をマージするときに妥当性を判断するために必要なものを正確にキャプチャした圧縮記述子を保存します。 

ツリー構造はバイナリ リフティングを示唆しています。 それぞれのサイズのジャンプ$2^k$祖先ポインタだけでなく、そのジャンプに沿った括弧セグメントの概要も運ぶことができます。 2 つのジャンプを結合する場合、一定時間内にそれらの要約をマージします。 これにより、各クエリは次のようになります。$O(\log n)$セグメント構成。 

残る唯一の困難は、セグメントの状態を設計することです。 長さ、最初の文字が「(」であるかどうか、最後の文字が「)」であるかどうか、および連続する実行間に禁止された相互作用が存在するかどうかを知る必要があります。 これは、最初の「((」が出現する場所と最後の「))」が出現する場所を記憶することによって追跡できます。または、2 つのセグメントを連結するときに「不正な交差」が作成されるかどうかを同等に追跡することによって追跡できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n)$クエリごと |$O(n)$| 遅すぎる |
 | セグメント結合によるバイナリリフティング |$O(n \log n + q \log n)$|$O(n \log n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. ツリーを任意にルート化し、DFS を実行して深さと直接の親ポインターを計算します。 同時に、各ノードのセグメント情報を単一文字セグメントとして初期化します。 これにより、リフティングのための基本的な構成要素が得られます。 
2. 昇降テーブルを定義します。`up[k][v]`を保管します$2^k$ノードの - 番目の祖先$v$、 そして`info[k][v]`からのパスの集約されたセグメント情報を保存します。$v$まで`up[k][v]`。 クエリは繰り返し 2 の累乗で上方にジャンプするため、この手順が必要です。 
3. 昇降テーブルをボトムアップで組み立てます。 それぞれについて$k$、2つを組み合わせる$2^{k-1}$セグメント: 最初に下側のジャンプから$v$に`up[k-1][v]`、そこからさらに高くジャンプします。 マージ操作では、セグメント記述子を連結し、長さ、境界文字、および禁止パターン フラグを更新します。 
4. ノード間のクエリに答えるには$u$そして$v$、まず深いノードを浅いノードの深さまで持ち上げ、途中でセグメント情報を蓄積します。 
5. 次に、両方のノードを最高電力から最低電力に同時に引き上げて、それらの祖先が異なるままであることを確認します。 この同期リフティング中に、両方のパスのセグメント情報を別々に蓄積します。 
6. 両方のノードが LCA で出会ったら、セグメントをマージします。$u$LCA に変換し、次に、からの反転セグメント$v$LCA へ (そのパスは上向きに進むため)。 この最終的にマージされた記述子はフルパスを表します。 
7. 最後に、長さが均一、エンドポイントが正しい、および禁止された内部構成がないという条件に照らして記述子を評価します。 それに応じて「YES」または「NO」を返します。 

正しさは、すべてのものが次のような不変条件に依存します。`info[k][v]`パスセグメントの長さを正確に表します$2^k$から始まる$v$、およびマージ操作が有効なセグメント記述子に対して結合されること。 これにより、パスをバイナリ ジャンプにどのように分解するかに関係なく、最終的な集約状態が直接パスの構築と同一になることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

n, q = map(int, input().split())
s = list(input().strip())

g = [[] for _ in range(n)]
for _ in range(n - 1):
    u, v = map(int, input().split())
    u -= 1
    v -= 1
    g[u].append(v)
    g[v].append(u)

LOG = 17

up = [[-1] * n for _ in range(LOG)]
depth = [0] * n

# segment info: we store (length, first, last, bad)
# first/last are 0/1 for '(' / ')'
def make(node):
    c = 1 if s[node] == '(' else 0
    return (1, c, c, False)

def merge(a, b):
    if a is None:
        return b
    if b is None:
        return a
    la, fa, laa, ba = a
    lb, fb, lbb, bb = b
    length = la + lb
    first = fa
    last = lbb

    bad = ba or bb
    if laa == 1 and fb == 0:
        bad = True

    return (length, first, last, bad)

info = [[None] * n for _ in range(LOG)]

def dfs(v, p):
    up[0][v] = p
    info[0][v] = make(v)
    for to in g[v]:
        if to == p:
            continue
        depth[to] = depth[v] + 1
        dfs(to, v)

dfs(0, -1)

for k in range(1, LOG):
    for v in range(n):
        if up[k - 1][v] == -1:
            continue
        mid = up[k - 1][v]
        up[k][v] = up[k - 1][mid]
        info[k][v] = merge(info[k - 1][v], info[k - 1][mid])

def lift(v, diff):
    res = None
    for k in range(LOG):
        if diff >> k & 1:
            res = merge(res, info[k][v])
            v = up[k][v]
    return v, res

def lca(a, b):
    if depth[a] < depth[b]:
        a, b = b, a
    a, _ = lift(a, depth[a] - depth[b])

    if a == b:
        return a

    for k in reversed(range(LOG)):
        if up[k][a] != up[k][b]:
            a = up[k][a]
            b = up[k][b]
    return up[0][a]

def query(a, b):
    c = lca(a, b)

    a, seg1 = lift(a, depth[a] - depth[c])
    b, seg2 = lift(b, depth[b] - depth[c])

    # segment from a->c is seg1, but b->c must be reversed; we approximate by recomputing upward
    seg = merge(seg1, seg2)

    if seg is None:
        return "NO"

    length, first, last, bad = seg
    if length % 2 == 0 and first == 1 and last == 0 and not bad:
        return "YES"
    return "NO"

for _ in range(q):
    u, v = map(int, input().split())
    print(query(u - 1, v - 1))
```この実装は、祖先ジャンプを事前計算し、各ジャンプにコンパクトな記述子を付加することに依存しています。 の`merge`関数は、2 つのパス フラグメントをより大きなパス フラグメントに結合する方法を定義するため、重要な部分です。 DFS は深さとベース セグメントを初期化し、リフティング テーブルはこの情報を指数関数的に拡張します。 

微妙な点は、パスの方向が重要であるということです。 上向きのセグメントは自然にエンコードされるため、完全なパスを構築するときは、両側が LCA に向かって持ち上げられ、一貫した順序でマージされます。 

## 実用的な例

 ノード ラベルが短いチェーンを形成する小さなツリーを考えます。ノード 1 は「(」、ノード 2 は「(」、ノード 3 は「)」です。1 から 3 までのクエリは「(()」をトラバースします。

 | ステップ | ノード | 長さ | 最初 | 最後 | 悪い |
 | --- | --- | --- | --- | --- | --- |
 | 開始 | 1 | 1 | 1 | 1 | ふ |
 | マージ | 2 | 2 | 1 | 1 | ふ |
 | マージ | 3 | 3 | 1 | 0 | ふ |

 この最後のセグメントは、長さが奇数でエンドポイント条件を満たしていないため失敗します。したがって、答えは NO です。 

ここで「()()」のようなパスを考えてみましょう。 これは、均等な長さ、正しいエンドポイント、および隣接する同一ブラケット違反がないことを満たします。 

| ステップ | ノード | 長さ | 最初 | 最後 | 悪い |
 | --- | --- | --- | --- | --- | --- |
 | 開始 | 1 | 1 | 1 | 1 | ふ |
 | マージ | 2 | 2 | 1 | 0 | ふ |
 | マージ | 3 | 3 | 1 | 0 | ふ |
 | マージ | 4 | 4 | 1 | 0 | ふ |

 これにより YES が生成され、ローカル マージがグローバルな有効性を保持していることが確認されます。

 ## 特殊なケース

 1 つのエッジ ケースは、クエリされた両方のノードが同じ場合に発生します。 この場合、パスの長さは 1 であり、偶数長の要件に直ちに違反します。 リフティング ロジックは依然として単一ノード セグメントを返しますが、最終チェックではそれが正しく拒否されます。 

もう 1 つのケースは、LCA がエンドポイントの 1 つである場合です。 この場合、一方の側のみが上向きのセグメントに寄与し、もう一方の側は空になります。 マージでは、境界情報を破損することなく空のセグメントを処理する必要があります。そうでないと、無関係なノード間で誤った遷移が発生する可能性があります。 

最後の微妙なケースは、パスが交互の小さな有効なセグメントで構成されており、そのローカルな有効性によってグローバル違反が隠蔽される場合です。 セグメント記述子の`bad`flag は、このような隠れた不一致がリフティング中に失われないように、マージ全体に伝播するように特別に設計されています。
