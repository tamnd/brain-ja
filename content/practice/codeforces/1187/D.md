 ## 解決策
 ## 問題の理解

 同じ長さの 2 つの配列が与えられ、最初の配列の連続するセグメントを繰り返し選択し、そのセグメントのみを非降順で並べ替えることができます。 このような操作を何度でも行った後、最初の配列をターゲットの配列に正確に変換できるかどうかを知りたいと考えます。 

重要な点は、各操作で要素が任意に移動されるのではなく、選択された間隔内でのローカルな並べ替えのみが可能であるということです。 ただし、間隔は重複して適応的に選択できるため、セグメントの並べ替えを繰り返すことで達成できることと一致している限り、このプロセスではかなり複雑な再配置をシミュレートできます。 

すべてのテスト ケースの合計長が最大 300,000 であるという制約は、すべての解がテストごとに線形または線形演算に近くなければならないことを意味します。 サイズ 200,000 のワーストケースの配列が 1 つでもすでに時間制限を超えているため、テストごとに 2 次関数を実行することは直ちに不可能になります。 

全体的な実現可能性を追跡せずに左から右へ貪欲に推論すると、微妙な失敗モードが現れます。 たとえば、位置を個別に一致させようとすると、不一致をローカルでいつでも「修正」できると誤って仮定する可能性があります。 

ターゲット配列の早い段階で必要な値が、ソース配列の後半でのみ現れるシナリオを考えてみましょう。 素朴な欲張りな人は、それをカバーするセグメントを並べ替えることができると言うかもしれませんが、そのセグメントの並べ替えは、以前に固定された位置を壊す可能性のある中間要素も引き込みます。 このカップリングが核心的な難しさです。 

## アプローチ

 ブルートフォースの観点は、プロセスをシミュレートすることです。すべての可能なシーケンスですべてのサブ配列の並べ替えを試し、ターゲットの配列に到達できるかどうかを確認します。 各操作によって配列の状態が変化し、最悪の場合、ステップごとに O(n²) 個の選択肢、場合によっては O(n) 個のステップという、組み合わせ爆発的な巨大な分岐要素を探索することになります。 

配列状態に対して BFS を試みる少し賢い総当たり攻撃でも、到達可能な順列の数が非常に急速に増加するため、すぐに失敗します。 この操作は多くの中間構成を生成するのに十分強力であるため、状態空間の爆発により直接シミュレーションが不可能になります。 

重要な洞察は、視点を逆転させることです。 a を b に変換できるかどうかを問うのではなく、セグメントの並べ替えでは要素の順序を段階的に変更することしかできないが、接頭辞に沿ったマルチセットの実現可能性を侵害することは決してないという制約の下で、a の要素を b の位置に「割り当てる」一貫した方法が存在するかどうかを尋ねます。 

これはプレフィックスの実現可能性条件につながります。左から右にスキャンするときに、b の位置 i にどの値が出現する必要があるかを決定するたびに、a のその時点までにそれをサポートするのに十分な要素がすでに見つかっていることを確認する必要があります。 ただし、セグメントの並べ替えは任意の間隔内で並べ替えることができるため、相対的な可用性の制約を尊重する限り、利用可能な要素を取得して並べ替えることができるというのが正しい抽象化です。 

これをエンコードするきれいな方法は、b との一致を強制される位置によって引き起こされる「アクティブ セグメント」のマルチセットを維持しながら、値の処理をシミュレートすることです。 古典的な解決策は、要素を遅延させることしかできず、要素を発明したり破棄したりできないことを尊重しながら、要素を貪欲に割り当てることができるかどうかをチェックすることに問題を落とし込みます。 

同様に、セグメントソートの構造によって強制される順序付け制約を使用して、配列を処理して一致しない要素の数を維持し、すべての接頭辞で a の要素のマルチセットが b で必要なマルチセットをその接頭辞までカバーするのに十分であることを確認できます。

より実装に優しい解釈は、左から右にスイープするときに、事前に固定された構造によって「ブロック」されていない a[j] の出現と b[i] を常に一致させることができる場合に限り、このプロセスが可能であるということです。この構造は、等しい制約のセグメントに対するスタックのような構造を使用して維持できます。 

これにより、動的に形成されたセグメント内の周波数に対する貪欲な一貫性チェックが行われ、テストごとに線形時間で実行できます。

 ## アルゴリズムのチュートリアル

 重要な観察は、唯一の本当の制約は、セグメントの並べ替えが連続する未解決の領域をどのようにマージし、並べ替えるかに由来するということです。 私たちは、見たことはあっても最終的な取り決めにはまだコミットされていない要素を表す構造を維持することによって、プロセスをシミュレートします。 

配列を左から右に処理し、a から利用可能な要素のマルチセットのような構造を維持し、各ステップで b が必要とするものと比較します。 ただし、要素がセグメント間で遅延する可能性があることも考慮する必要があります。これは、実現可能性が損なわれない限り、一時的なバッファリングを許可することと同じです。 

1. 位置を左から右に繰り返し、各位置を b によって課される要件として扱います。 
2. a の要素のうち、遭遇したがまだ b の固定位置に割り当てられていない要素を表す構造を維持します。 
3. a に進むたびに、将来の配置に使用できるようになるため、新しい要素をこのプールに追加します。 
4. b の位置 i に到達したら、必要な値 b[i] が現在プール内で利用可能かどうかを確認します。 
5. 利用可能な場合は、セグメントの並べ替え操作を使用して最終的に適切な位置に配置できるため、それを割り当ててプールから削除します。 
6. 利用できない場合は、それ以降の操作で欠損値が作成される可能性がないため、すぐに不可能であると結論付けます。 
7. すべてのポジションが処理されるまでこのプロセスを続けます。 

微妙な点は、この貪欲な割り当てがなぜ有効なのかです。 セグメントの並べ替えにより、現在の到達可能なプレフィックス プールに値が存在すると、未解決の領域を常に結合して並べ替えて内部順序を調整できるため、以前に修正された一致を妨げることなく、一定の間隔内でいつでも再配置して正しい位置に戻すことができます。 

### なぜ効果があるのか

 どのプレフィックスでも、アルゴリズムは、b に割り当てられたすべての値が、必要な時点までに出現した a 内の個別の出現と一致していることを維持します。 セグメントの並べ替えでは、選択した任意の間隔内で任意の順序を並べ替えることができるため、使用可能な要素のセットをアクティブな領域内で自由に並べ替えることができます。 これは、唯一の制約はプレフィックスの多重度であり、正確な位置構造ではないことを意味します。 いずれかの時点で必要な要素が使用可能なプールに存在しない場合、一連のセグメント ソートによってその要素が導入されることはできないため、失敗は避けられません。 逆に、すべての要件を順番に満たすことができれば、未解決の接尾語をカバーするセグメントを段階的にソートすることで、いつでも配置を実現できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import defaultdict, deque

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))

        # We use a multiset-like structure via deque lists per value
        pos = defaultdict(deque)
        for i, x in enumerate(a):
            pos[x].append(i)

        # We simulate consumption of positions in increasing order
        # using a pointer over "time" in a
        available = defaultdict(int)

        ptr = 0
        ok = True

        # We maintain a moving pointer and mark consumed occurrences
        used = [False] * n

        for i in range(n):
            need = b[i]

            # expand until we can satisfy need
            while ptr < n and available[need] == 0:
                x = a[ptr]
                available[x] += 1
                ptr += 1

            if available[need] == 0:
                ok = False
                break

            available[need] -= 1

        out.append("YES" if ok else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、配列 a に対するポインターを維持し、使用可能な要素のセットを徐々に拡大します。 辞書`available`各値のうち、まだ使用できるものがいくつあるかを数えます。 b の必要な値ごとに、その値が表示されるまで a のプレフィックスを拡張し、それを使用します。 

重要な実装の詳細は、a でポインタを決して巻き戻さないことです。 これは、プレフィックスを考慮して要素が公開されると、それらはセグメントソートによる将来の再配置に引き続き利用できるため、単調展開のみが必要になるという事実をエンコードしています。

 ## 特殊なケース

 重大なエッジ ケースは、b が a に現れるが長いプレフィックスの後にのみ現れる値を必要とする場合です。 アルゴリズムは、その値が使用可能になるまで ptr を正しく展開し、早期の失敗を防ぎます。 

もう 1 つのエッジ ケースは、複数の同一要素が順番に一致する必要がある繰り返し値です。 頻度ベースの消費により、重複が独立して処理されることが保証されるため、同じ値が複数回必要な場合でも誤った拒否は発生しません。 

最後のエッジ ケースは、 b がグローバルに並べ替え可能であるが、セグメント制約を介してローカルに構築できない置換である場合です。 貪欲なプレフィックス拡張は、必要な要素がまだ公開されていないことを正確に識別し、無効な初期の割り当てを防ぎます。
