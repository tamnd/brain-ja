 ## 解決策
 ## 問題の理解

 長方形のグリッドで表された講堂があります。 一部のセルは壁または空の床であり、一部のセルは椅子であり、一部のセルにはコンセントがあり、一部の椅子にはすでに競合他社が座っています。 各競技者は小文字で表されるチームに属します。 

5 分間のインターバル中に、各競技者は独立して隣の椅子に移動しようとします。 可能な目的地は空の椅子である必要があり、コンセントに十分近い場所にある必要があり、隣に敵チームのメンバーがいない必要があります。 複数の目的地が可能な場合、競技者は北、西、東、南という固定の優先順位に従います。 すべての競技者が目的地を選択した後、競合のない移動のみが実行されます。 2 人以上の競技者が同じ椅子を選択した場合、誰もそこに移動しません。 

このタスクは、指定された間隔数のプロセスをシミュレートし、最終的な講堂の状態を出力することです。 

マップの次元とシミュレーション ラウンド数はすべて最大 100 です。したがって、グリッドには最大 10000 個のセルが含まれ、直接シミュレーションが可能です。 1 回のラウンドですべてのセルとすべての競合相手を検査できるため、O(I * N * M) または O(I * N * M * 定数) 付近の解は問題なく制限内に収まります。 このプロセスは決定論的であるため、起こり得る将来の状態を探ろうとするアプローチは必要ありません。 

主な実装の罠は、移動の計算中に間違ったグリッド状態を使用することに起因します。 すべての競技者が同時に決定するため、同じインターバル内でどの手が他の競技者の決定に影響を与えることもできません。 例えば：```
3 3 1
...
.*.
.a#
...
```正しい出力は次のとおりです。```
...
.*.
.a#
...
```競技者は右側の椅子に移動できません。その椅子はコンセントに十分近くないため、マップは変更されません。 

もう 1 つの微妙なケースは、2 人の競合他社が同じ椅子を望んでいる場合です。```
3 5 1
.....
.a#b.
.*...
```両競技者は中央の椅子を検討する可能性がありますが、目的地に複数のリクエストがあるため、移動をキャンセルする必要があります。 競合他社を 1 台ずつ処理する不注意な実装では、誤ってそのうちの 1 台の移動を許可してしまいます。 

3 番目のエッジ ケースは、競合他社が複数の椅子に囲まれている場合です。 優先順位は正確に尊重される必要があります。```
5 5 1
.....
..#..
.*a#.
..#..
.....
```正しい移動は、東に別の有効な椅子が存在する場合でも、それが有効であれば北の椅子に移動することです。 任意の順序で最初の有効な方向を選択すると、間違った結果が生成されます。 

## アプローチ

 直接的な総当たりシミュレーションが自然な開始点です。 インターバルごとに、グリッド全体をスキャンし、すべての競合相手を見つけ、隣接する 4 つのセルをチェックし、最初の有効な目的地を選択して、すべての手をまとめて適用します。 ルールは現在の配置のみに依存し、各間隔は他の間隔から独立しているため、このアプローチは正しいです。 

高価な部分は、答えを見つけることではなく、不必要な作業を繰り返して答えを見つけることです。 グリッドに N * M セルがあり、I 個の間隔がある場合、シミュレーションではおよそ I * N * M チェックが実行されます。 最大値では約 1 億セル検査になりますが、すべての検査は単純で制限が小さいため、この問題ではまだ許容されます。 

有益な観察は、問題には隠れた検索がないことです。 すべての動きは現在のグリッドにのみ依存し、ラウンドごとにグリッドが 1 回変更されます。 決定フェーズを更新フェーズから分離することで、同時動作を維持できます。 最初のフェーズでは、グリッドを変更せずに、要求されたすべての動きを記録します。 第 2 フェーズでは、一度だけリクエストされた宛先のみを適用します。 

シミュレーション開始前に出口条件を簡略化することもできます。 移動ごとにすべての出口までの距離をチェックするのではなく、マルチソースの幅優先検索を使用して、どのセルが出口に十分近いかを一度計算します。 その後、各動きのチェックは定数時間の検索になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(I * N * M) | O(N * M) | 承認済み |
 | 最適 | O(N * M + I * N * M) | O(N * M) | 承認済み |

 受け入れられたソリューションは、最適化されたシミュレーションです。 前処理により距離計算の繰り返しが排除される一方、2 フェーズ更新により同時移動ルールが正確に維持されます。 

## アルゴリズムのチュートリアル

 1. 講堂を読み取り、すべてのアウトレットから開始してマルチソース BFS を実行します。 すべてのセルの最も近いコンセントまでの距離を保存します。 椅子は、保存された距離が最大 3 の場合に正確に目的地になることができます。 
2. 以下のプロセスを I 回繰り返します。 各反復中に、現在のグリッド上のすべての競合他社を検査し、選択した目的地を決定します。 すべての競技者が同時に行動するため、この段階ではグリッドを変更してはなりません。 
3. 各競合他社について、北、西、東、南の順に隣接するセルを調べます。 空の椅子で、コンセントに十分近く、隣に対戦相手がいない最初のセルを選択します。 
4. 選択した動きをリクエストのリストに保存します。 また、各宛先セルを選択した競合他社の数も数えます。 リクエストをカウントすると、すべての決定がわかった後で競合を特定できます。 
5. 次のグリッド状態を作成します。 記録されたすべての移動について、その宛先にリクエストが 1 つだけある場合にのみ適用します。 元の椅子は空になり、目的地は競技者を受け入れます。 

正確さは、各ラウンドの開始時のグリッドが、そのラウンドの競技者が移動する前の講堂を正確に表すという不変条件を維持することによって得られます。 決定フェーズではこの状態のみが読み取られるため、すべての競技者が同じ状況を確認します。 更新フェーズでは、競合ルールで許可されている移動が正確に適用され、ステートメントの同時移動動作と一致します。 

マルチソース BFS ではすべてのセルに最も近いアウトレットまでの最短パス距離が与えられるため、BFS の前処理も正確です。 グリッド内の移動はタクシーの距離の定義とまったく同じであるため、この距離が最大 3 であるかどうかを確認することは、3 移動以内に出口に到達できるかどうかを確認することと同じです。 

## Python ソリューション```python
import sys
from collections import deque

input = sys.stdin.readline

def solve():
    n, m, intervals = map(int, input().split())
    grid = [list(input().rstrip()) for _ in range(n)]

    dist = [[10**9] * m for _ in range(n)]
    q = deque()

    for i in range(n):
        for j in range(m):
            if grid[i][j] == '*':
                dist[i][j] = 0
                q.append((i, j))

    directions = [(-1, 0), (0, -1), (0, 1), (1, 0)]

    while q:
        r, c = q.popleft()
        for dr, dc in directions:
            nr, nc = r + dr, c + dc
            if 0 <= nr < n and 0 <= nc < m and dist[nr][nc] > dist[r][c] + 1:
                dist[nr][nc] = dist[r][c] + 1
                q.append((nr, nc))

    for _ in range(intervals):
        moves = []
        count = {}
        current = grid

        for r in range(n):
            for c in range(m):
                team = current[r][c]
                if not ('a' <= team <= 'z'):
                    continue

                chosen = None
                for dr, dc in directions:
                    nr, nc = r + dr, c + dc
                    if not (0 <= nr < n and 0 <= nc < m):
                        continue
                    if current[nr][nc] != '#':
                        continue
                    if dist[nr][nc] > 3:
                        continue

                    blocked = False
                    for ar, ac in directions:
                        rr, cc = nr + ar, nc + ac
                        if 0 <= rr < n and 0 <= cc < m:
                            other = current[rr][cc]
                            if 'a' <= other <= 'z' and other != team:
                                blocked = True
                                break

                    if not blocked:
                        chosen = (nr, nc)
                        break

                if chosen is not None:
                    moves.append((r, c, chosen[0], chosen[1], team))
                    count[chosen] = count.get(chosen, 0) + 1

        for r, c, nr, nc, team in moves:
            if count[(nr, nc)] == 1:
                grid[r][c] = '#'
                grid[nr][nc] = team

    print('\n'.join(''.join(row) for row in grid))

if __name__ == "__main__":
    solve()
```コードの最初の部分では、出口の距離を計算します。 最初にすべてのアウトレットがキューに挿入されるため、BFS はすべてのアウトレットから同時に外側に拡張されます。 

シミュレーション ループは、ウォークスルーの 2 フェーズのアイデアに従います。 コードレコードが移動します`moves`そして触れない`grid`決定が行われている間。 これにより、早期に処理された競合他社が、後の競合他社に表示されるオプションを変更するというよくある間違いを回避できます。 

方向配列は意図的に北、西、東、南の順序で並べられています。 この順序は、問題からの優先順位ルールを直接表します。 競合カウンターは宛先座標をキーとして使用するため、一意の宛先のみが適用されます。 

最終更新では両方のセルが同時に変更されます。古い位置は空の椅子になり、新しい位置は占有されます。 このため、すべての選択肢が収集された後にのみ更新を適用することが重要です。 

## 実用的な例

 サンプル入力を使用して、最初のラウンドは空の椅子の周りに配置されたいくつかのチームから始まります。 

| 競合他社 | ポジション | 選択した目的地 | 結果 |
 | --- | --- | --- | --- |
 | | (3,1) | 有効な椅子がありません | 滞在 |
 | b | (2,7) | (3,7) | 動く |
 | c | (1,9) | (1,9) | 滞在 |
 | d | (1,15) | 有効な椅子がありません | 滞在 |

 このトレースの重要な部分は、すべての選択肢が元のマップから計算されるということです。 競合他社が更新フェーズの後半に移動しても、それ以前の決定には影響しません。 

小さなカスタム例は競合処理を示しています。 

入力:```

.....
.a#b.
.*...
```| 競合他社 | ポジション | 目的地リクエスト | 適用済み |
 | --- | --- | --- | --- |
 | | (1,1) | (1,2) | いいえ |
 | b | (1,3) | (1,2) | いいえ |

 両方の競技者が同じ椅子を要求するため、その宛先のカウンターは 2 つになります。 一意のリクエストのみが適用されるという不変条件により、不正確なレース結果が防止されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N * M + I * N * M) | BFS は各セルを 1 回訪問し、各シミュレーション ラウンドでセルごとに一定の作業のみでグリッドを 1 回スキャンします。 |
 | スペース | O(N * M) | 距離配列と移動情報はグリッド サイズに比例します。 |

 最大でも 100 行、100 列、100 ラウンドの場合、合計作業量は約 1 億回の単純な操作になります。 前処理により、シミュレーションは指定された制限に対して十分に軽量に保たれます。

 ## 特殊なケース

 競合他社に合法的な目的地がない場合、アルゴリズムはその人物の移動を記録しません。 単一セルの場合:```
1 1 1
a
```競合他社には隣接するセルがないため、移動リストは空のままで、グリッドは変更されません。 

複数の競技者が同じ椅子を選択する場合、アルゴリズムはどの競技者が最初に到着したかを知る必要はありません。 で：```
3 5 1
.....
.a#b.
.*...
```両方のリクエストが保存され、宛先数は 2 になり、どちらの移動も適用されません。 これは、競合他社が同じ席をめぐって争うことを避けるというルールと一致します。 

競合他社にいくつかの有効な選択肢がある場合、順序付けられた方向スキャンによって決定が処理されます。 最初の有効な方向がすぐに選択されるため、後の方向で優先度の高いオプションが誤って上書きされることはありません。 

多くのラウンドが要求されると、前の最終グリッドを次の開始状態として使用して同じシミュレーションが繰り返されます。 すべてのラウンドは次のラウンドが始まる前に完全に完了するため、間隔の間に中間状態が漏れることはありません。
