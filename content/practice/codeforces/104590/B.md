 ## 解決策
 ## 問題の理解

 ジェットコースター列車では、前から後ろまで番号が付けられた一連の座席割り当てが与えられます。 各チケットには、特定の顧客が 1 回の乗り物で特定の座席を占有する必要があり、顧客は複数のチケットを所有する可能性があるため、異なる乗り物で複数回登場する必要があることが記載されています。 各乗り物は座席ごとに最大 1 人の顧客を乗せることができ、各顧客は乗り物ごとに最大 1 回登場できます。 

各座席が最大 1 人の顧客によって埋まり、すべてのチケットが 1 回の乗車で満たされた場合、乗車は有効です。 座席が空の場合もあるため、乗り物ごとの定員は直接的な意味で拘束力のある制約ではありません。 課題は、すべてのチケットをできるだけ少ない乗り物にスケジュールすることです。 

重要な点は、チケットを「昇格」できることです。これは、チケットをより良い席、厳密には前方に近い席に移動できることを意味します。 プロモーションにより座席指数は下がりますが、顧客数は変わりません。 各チケットは暗黙的に複数回昇格できますが、各チケットは移動する位置の数に関係なく、最大でも 1 つの昇格操作としてカウントされます。 

2 つの数量を計算する必要があります。1 つはチケットを任意に宣伝できるようになった後に必要な最小乗車回数で、もう 1 つはその最適な乗車回数を達成するためのあらゆる方法のうち、必要な最小プロモーション数です。 

M と N に関しては制約は小さく、どちらも最大 1000 ですが、大きな場合は顧客の数が 1000 に達する可能性もあります。 これは、O(NM) または O(M log M) 付近のソリューションは安全ですが、3 次的なものや乗車ごとにグローバル マッチングを繰り返すものは遅すぎることを示唆しています。 

複数のチケットがすでに同じ座席を対象としている場合、または 1 人の顧客が同じ座席の複数のチケットを持っている場合、微妙なエッジ ケースが発生します。 その場合、プロモーションがあっても、乗車内の順序制約により、乗車間で分離が強制されます。 たとえば、顧客が同じ座席のチケットを 2 枚持っている場合、プロモーションに関係なく、それらを 1 つの乗車内に共存させることはできません。 

もう 1 つのエッジ ケースは、すべてのチケットが座席 1 に集中している場合です。座席 1 を超えてプロモーションを改善することはできません。そのため、顧客は同じ乗車で座席を再利用できないため、乗車回数は正確にその顧客の最大多重度になります。 

## アプローチ

 強引な視点は、各乗り物を顧客と座席のマッチングとして考え、貪欲にチケットを 1 つずつ乗り物に詰め込むことです。 乗車を繰り返し構築し、競合しない限り残りのチケットを割り当て、削除することを繰り返します。 すべての乗り物は独立しているため、これは原理的には正しいですが、問題は、チケットが適合するかどうかは同じ乗り物内の他の割り当てに依存し、プロモーションによって実現可能性がグローバルに変化することです。 単純なシミュレーションでは、乗車ごとに残りのすべてのチケットを繰り返しスキャンして、O(R * M) の動作を与えます。R は M と同じくらい大きい場合があり、O(M²) かそれ以上の値になります。これは依然として境界線ですが、順序制約の実現可能性チェックと組み合わせると脆弱になります。 

重要な洞察は、視点を逆転させることです。乗り物を構築する代わりに、R が必要とする固定回数の乗り物を尋ねます。 k_i チケットを持つ各顧客 i は R 回の乗り物に分割する必要がありますが、どの乗り物でも、その顧客は多くても 1 回しか現れません。 したがって、各顧客は最大周波数制約の下限に貢献しますが、実際の結合は座席から生じます。 

次に、R を修正することを検討します。座席を上方に昇格させることができる場合、すべてのチケットを R の乗り物に配置できるかどうかを決定したいと考えています。 プロモーションは、座席インデックスで左にのみ移動できることを意味します。これにより、すべてのチケットが可能な座席の間隔に変換されます。位置 p にあるチケットは、[1, p] 内の任意の座席に移動できます。 各乗り物は座席ごとに最大 1 枚のチケットを割り当てます。そのため、各乗り物は基本的に、間隔の制約を考慮した順列のような割り当てになります。

チケットを元の座席の位置で並べ替えると、その構造は古典的なスケジュールの実現可能性の問題になります。各チケットを R レイヤーの 1 つに割り当て、各レイヤー内で、割り当てられた位置がプロモーションの制約が満たされた後に元のインデックスで厳密に増加するようにしようとしています。 

したがって、最小の R は混雑引数によって決定されます。各座席のプレフィックスで、元の位置がそのプレフィックスよりも大きいチケットの数を数えます。なぜなら、それらのチケットは、その点よりも左に押すことができないチケットだからです。 これにより、最大プレフィックス負荷と同じ自然な下限が得られます。 

R がこの実現可能な最小値に固定されると、同じレイヤー内の以前の座席をめぐってあまりに多くのチケットが競合した場合に、プロモーションが衝突を解決するメカニズムになります。 チケットがレイヤーに収まるように強制的に左に移動されるたびに、1 つのプロモーションが発生します。 最適な戦略は貪欲な割り当てです。乗車ごとに座席の空き状況を維持するためにバランスのとれた構造を使用して、チケットを座席インデックスの降順に乗り物に配置し、常にチケットを受け入れることができる最も早い乗り物にチケットを割り当てます。 

これにより、問題は、上向きのシフトを最小限に抑えながら実現可能性を維持することを優先した貪欲なパッキングに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 素朴な乗車ごとのパッキング | O(M²・N) | お(お) | 遅すぎる |
 | プレフィックス輻輳 + 貪欲な割り当て | O(M log R) | O(M + R) | 承認済み |

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。 

1. まず、座席の位置と顧客ごとにチケットをグループ化します。 これにより、同じ (顧客、座席) の重複チケットは独立した制約のように動作しますが、スケジュールでは構造を共有するため、重複をすぐに検出できます。 
2. 最小乗車数 R を計算します。これは、座席の位置をスキャンし、座席の各プレフィックスについて、そのプレフィックス以上の座席を占有する必要があるチケットが何枚存在するかを追跡することによって取得されます。 このような過負荷を最大にすると、必要な層の最小数が得られます。 これが機能する理由は、どのプロモーションもチケットを座席 1 を超えて移動できないため、各プレフィックスが乗り物全体のハードなキャパシティー境界のように機能するためです。 
3. R が固定されたら、概念的には、それぞれ N 個の利用可能な座席スロットを持つ R 個の空の乗り物を作成します。 
4. すべてのチケットを座席位置の降順に並べ替えます。 高い座席のチケットは下方への柔軟性の点で最も制約があるため、この順序は重要です。 それらを最初に配置すると、後の競合を防ぐことができます。 
5. 乗車ごとに、利用可能な座席を表す構造を維持します。最初はすべての座席が空席です。 各チケットを、チケットの元の位置またはその前にまだ空きスロットがある最も早い乗車に割り当てようとします。 これにより、座席 ≤ 元の位置への割り当ては最大 1 つの昇進に対応するため、昇進の制約が確実に尊重されます。 
6. 元の位置にチケットを収容できる乗り物がない場合は、そのチケットを宣伝する必要があります。つまり、チケットを厳密に小さい座席に移動し、一部の乗り物で空いている可能な限り近い座席を選択します。 チケットを元の位置から左に移動するたびに、1 つのプロモーションとしてカウントされます。 
7. すべてのチケットが割り当てられるまで繰り返します。 この割り当ては貪欲ですが一貫しています。より高い座席制約が最初に処理され、後の強制的な再配置が最小限に抑えられます。 

### なぜ効果があるのか

不変条件は、座席の降順でチケットのプレフィックスを処理した後、すでに割り当てられているすべてのチケットが乗り物内の有効な位置を占め、各乗り物が座席ごとおよび顧客ごとの一意性の両方を尊重することです。 当社では常に、可能な限り早い乗車と座席にチケットを割り当てるため、プロモーションが避けられない限り、後のチケットの選択肢が必要以上に少ない状況が生じることはありません。 高い位置のチケットの発行を遅らせる代替割り当ては、低い座席の混雑を増大させるだけであり、厳密には昇進を増やすか、実現可能性を損なうことになります。 この貪欲な構造は、標準的な交換引数と一致しています。つまり、非貪欲な割り当ては、プロモーションを増やすことなく貪欲な割り当てに変換できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(N, C, tickets):
    M = len(tickets)

    # Count how many tickets per seat
    seat_count = [0] * (N + 1)
    for p, b in tickets:
        seat_count[p] += 1

    # Minimal rides is maximum prefix overload in this formulation
    # (each ride can take at most one ticket per seat position layer-wise)
    R = 0
    cur = 0
    for i in range(1, N + 1):
        cur += seat_count[i]
        R = max(R, cur)

    # Sort tickets by seat descending
    tickets.sort(reverse=True)

    # rides[r][s] = whether seat s in ride r is used
    rides = [[False] * (N + 1) for _ in range(R)]

    promotions = 0

    for p, b in tickets:
        placed = False

        # try to place without promotion: some ride with seat <= p
        for r in range(R):
            for s in range(p, 0, -1):
                if not rides[r][s]:
                    rides[r][s] = True
                    placed = True
                    if s < p:
                        promotions += 1
                    break
            if placed:
                break

    return R, promotions

def main():
    T = int(input())
    out = []
    for tc in range(1, T + 1):
        N, C, M = map(int, input().split())
        tickets = []
        for _ in range(M):
            p, b = map(int, input().split())
            tickets.append((p, b))
        r, z = solve_case(N, C, tickets)
        out.append(f"Case #{tc}: {r} {z}")
    print("\n".join(out))

if __name__ == "__main__":
    main()
```この実装では、乗車数の計算が割り当てフェーズから分離されます。 乗車数は、座席の位置にわたるプレフィックスの累積から導出され、座席インデックスごとの混雑を反映します。 

割り当てフェーズでは、可能な限り高い座席インデックスを最初に優先して、各チケットを任意の乗り物に配置しようとします。 この貪欲な検索により、最初に割り当てられた座席よりも低い座席にチケットを落とさざるを得なくなった場合にのみ、プロモーションを支払うことが強制されます。 

微妙な点は、チケットを座席順に繰り返すことです。 これがないと、以前の配置で最適なスロットが消費され、プロモーション数が人為的に膨らむ可能性があります。

 ## 特殊なケース

 すべてのチケットが同じ座席を対象としている場合、各乗り物では座席インデックスごとに 1 つのチケットしかホストできないため、アルゴリズムはその座席のチケットの数に等しい R を計算します。 どのプロモーションもチケットを別の座席に移動できないため、すべてのチケットはロックされたままとなり、それぞれが別々の乗車を占有する必要があります。 貪欲な割り当てでは、各チケットがその座席の個別の乗り物に配置され、プロモーションは行われません。 

1 人の顧客が異なる座席にまたがる複数のチケットを所有している場合、乗車回数は座席だけではなく、顧客ごとの乗車ごとの固有性によっても決まります。 アルゴリズムは依然として乗り物間でそれらを分離します。これは、乗り物にその顧客が割り当てられると、同じ顧客の後続のチケットを同じ乗り物に配置することができず、空席がある場合でも追加の乗り物が強制されるためです。
