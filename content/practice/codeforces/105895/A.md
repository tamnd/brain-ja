 ## 解決策
 ## 問題の理解

 大学システムによって発行された学生 ID を表す 9 文字の単一の文字列が与えられます。 タスクは、この ID が非常に特殊な構造規則に従っているかどうかを判断することです。 

この形式は固定長であり、概念的なセグメントに分割されています。 最初の 2 文字は、一定の機関プレフィックスをエンコードする必要があります。 3 番目の文字は学術タイプを示し、有効な数字の少数のセットに制限されます。 中央の 2 文字は、この問題では構文的に制限のない年フィールドを表します。つまり、任意の数字が受け入れられることを意味します。 最後の 4 文字は、登録時に割り当てられるシリアル番号を表します。このシリアル番号は、単純なすべてゼロの場合であってはなりません。 

出力は単純な妥当性チェックです。すべての制約が満たされている場合は YES が出力され、そうでない場合は NO が出力されます。 

ID は「フォーマットされた数値」に似ていますが、これは基本的に、位置の制約とサフィックスの単一の禁止パターンによる文字列検証の問題です。 

入力が 9 文字の文字列 1 つだけであるという制約により、解は構築により線形時間になります。 複数のテスト ケースを解析したり、大きな入力を処理したりする必要がないため、文字列のスライスや直接インデックス作成による定数要素のオーバーヘッドでも十分です。 操作バジェットはわずかであり、テストごとに O(1) から O(9) までの値が同等です。 

主な失敗ケースは、位置ルールの見落としや接尾辞の条件の読み間違いに起因します。 代表的な落とし穴をいくつか挙げます。 

文字列が数値であることのみをチェックする場合、サフィックスがすべて 0 であるため無効であっても、219900000 のような入力は誤って合格します。 

プレフィックスと入力桁のみをチェックし、サフィックスの検証を忘れた場合、2132410000 が誤って受け入れられます。 

誰かがプレフィックスやタイプの数字が年フィールドに依存すると誤って仮定した場合、たとえ中間セグメントが制限されていないとしても、2132251234 などの有効な文字列を拒否する可能性があります。 

中心的な課題は計算ではなく、正確な位置チェックです。 

## アプローチ

 ブルートフォース解釈では、すべてのルールを生成された有効な ID のセットとして明示的にモデル化しようとします。 プレフィックス、タイプの数字、年の範囲、シリアル番号の有効な組み合わせをすべて列挙し、メンバーシップをチェックすることを想像することもできます。 これは概念的には正しいですが、年フィールドとシリアル範囲が制限されていないため、使用可能な ID のスペースが非常に大きいため、精神的には不必要で非効率的です。 有効な文字列をすべて生成または保存することは無駄であり、検証は純粋にローカルであるため、何のメリットもありません。 

重要な点は、すべての制約が固定長文字列内の固定位置に適用されるということです。 これにより、問題は組み合わせ生成から直接のインデックス作成チェックにまで軽減されます。 各ルールは、文字または部分文字列に対する定数時間の比較になります。 接尾辞の条件もローカルです。最後の 4 文字がすべて「0」であるかどうかを確認するだけで済みます。 

すべての制約が位置的で独立していることがわかると、問題は継続的な作業の 1 回のパスに崩壊します。

 ## アルゴリズムのチュートリアル

 文字列を段階的に検証し、適切な構造上の制約をそれぞれチェックします。

1. 入力文字列を単一の 9 文字の値として読み取ります。 形式が固定長であるため、前処理は必要ありません。 
2. 最初の 2 文字が正確に「21」であるかどうかを確認します。 これが失敗した場合、文字列は必要な教育機関のエンコーディングに属することができないため、すぐに拒否できます。 このチェックは純粋に位置的なものであり、変換は必要ありません。 
3. 3 番目の文字が「3」または「4」であるかどうかを確認します。 これは学生のタイプをエンコードします。 他の数字は形式ルールに違反するため、一致しない場合はすぐに拒否されます。 
4. 文字列の最後の 4 文字を抽出します。 これらは登録シリアル番号を表します。 
5. これらの最後の 4 文字がすべて「0」ではないことを確認します。 無効なケースは「0000」のみです。 「0001」のような先行ゼロを含むその他の組み合わせは有効です。 
6. すべてのチェックに合格した場合は、YES を出力します。 それ以外の場合は NO を出力します。 

### なぜ効果があるのか

 問題文の各ルールは文字列の互いに素なセグメントに適用され、他のセグメントからの計算値に依存する制約はありません。 この独立性により、各制約を個別にチェックするだけで十分かつ必要であることが保証されます。 ルールに違反すると、セグメント間の修正メカニズムがないため、ID は有効になりません。 逆に、すべてのローカル制約が満たされている場合、文字列は完全な仕様と正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

s = input().strip()

ok = True

if len(s) != 9:
    ok = False
else:
    if s[:2] != "21":
        ok = False
    if s[2] not in ("3", "4"):
        ok = False
    if s[5:] == "0000":
        ok = False

print("YES" if ok else "NO")
```実装はアルゴリズムの構造にほぼ直接に従います。 末尾の改行文字の削除を忘れることは、文字列等価性チェックにおける微妙なバグの一般的な原因となるため、改行の干渉を避けるために最初に入力を削除します。 

次に、一定時間のスライス操作を実行します。 プレフィックスチェックでは、`s[:2]`、最初の 2 文字が安全に抽出されます。 型チェックでは、位置 2 での直接インデックス付けが使用されます。サフィックス チェックでは、`s[5:]`、9 文字の文字列の最後の 4 文字に対応します。 

唯一の微妙な点は、オールゼロの状態です。 文字を反復処理する代わりに、部分文字列を次と直接比較します。`"0000"`これは、よりシンプルでエラーが発生しにくいものです。

 ## 特殊なケース

 最も重要なエッジ ケースは、プレフィックスとタイプ フィールドは正しいが、サフィックスが正確に「0000」である場合です。 たとえば、入力`213245000`最終比較まですべての構造チェックに合格します。 このアルゴリズムはプレフィックス「21」を評価し、タイプ「3」または「4」を受け入れ、その後、最後の 4 文字を分離して、それらを禁止されたパターンと直接比較します。 これらは正確に「0000」と一致するため、条件がトリガーされ、出力は NO になります。 

もう 1 つの微妙なケースは、次のように接尾辞の最初の桁だけがゼロ以外の場合です。`2132450001`。 部分文字列`s[5:]`は「0000」と等しくない「0001」になるため、ほとんどの桁がゼロであってもサフィックスチェックに正しく合格します。 これは、ルールが「1 桁を除いてすべてゼロが許可される」ではなく、厳密には「厳密にすべてゼロではない」ことを確認します。 

次のようなプレフィックス障害`223245123`最初のチェックで即座に拒否され、その後の条件は関係ありません。 これは、各ルールが独立しており、どのセグメントでの失敗も決定的なものであるため、短絡検証が正確さに影響を与えないことを示しています。
