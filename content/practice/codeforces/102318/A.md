 ## 解決策
 ## 問題の理解

 この問題は、電力消費量が正の整数である 2 つの世帯をモデル化します。 電力会社は累進料金を使用しています。最初の 100 CWh は 2 アメリカス、次の 9,900 CWh は 3 アメリカス、次の 990,000 CWh は 5 アメリカス、1,000,000 を超えるユニットは 7 です。元の問題では 2 つの数字が得られます。`A`そして`B`。`A`料金を適用する前に両世帯の消費量を合算した場合に生じる請求額です。`B`は、個々の請求額間の絶対的な差です。 正確に 1 組の消費でこれら 2 つの値が生成されることが保証されており、小規模な世帯の個別の請求書を出力する必要があります。 入力には複数のテスト ケースが含まれており、次で終わります。`0 0`。 

最初のタスクは、総消費量を回収することです。`A`。 これが可能なのは、関税機能が厳密に強化されているからです。 総消費量がわかったら、それを呼び出します`C`、2 つの個別の消費は次のとおりである必要があります。`x`そして`C - x`。 私たちの消費量は隣人の消費量を超えないことが約束されているので、考慮する必要があるのは、`1 <= x <= C / 2`。 

数値境界は`A <= 10^9`。 つまり、最も高い料金ではユニットあたり 7 が請求されるため、総消費量は 10^8 のオーダーになる可能性があります。 可能な限りのリニアスキャン`x`したがって、1 つのテスト ケースに対して数千万回の反復が必要になります。 1 秒という制限があると、特に Python では作業が多すぎます。 代わりに料金表の構造により単調関数が得られ、二分探索を使用して探索を約 30 回の反復に減らすことができます。 

直接実装が失敗する可能性がある境界ケースがいくつかあります。 1 つ目は、最小の有効な非終了ケースです。 のために```
6 2
```合計消費量は 3 です。`bill(3) = 6`。 唯一可能な分割は 1 と 2 で、その請求額は 2 と 4 であるため、答えは次のようになります。```
2
```すべてのテスト ケースが 2 番目の料金範囲に入るのに十分な量の消費があると想定する不注意な実装では、これが誤って計算される可能性があります。 

ちょうど 100 単位の料金境界も、オフバイワン エラーのもう 1 つの一般的な原因です。 考慮する```
200 4
```合計の消費量は 100 です。固有の分割は 49 と 51 です。請求額は 98 と 102 で、差は 4 です。したがって、答えは次のようになります。```
98
```使用する`100`ここでは、レート 2 で最初の 100 ユニットを正確に充電するのではなく、最初の範囲のサイズが必要です。 

最初の料金範囲の直後の境界も同様に重要です。 合計 201 ユニットの消費には請求があります`503`最初の 100 ユニットのコストは 200、次の 101 のコストは 303 であるため、誤って 100 番目のユニットに 2 番目のレートを使用したソリューションは、後の計算ごとにシフトします。 

最高料金の範囲も重要です。 例えば、```
4979977 4979968
```は消費量 1,000,010 と 1 に相当するため、小規模世帯は 2 を支払います。合計消費量は 1,000,000 単位の境界を越えるため、最終的な料金分岐は正しく実装される必要があります。 この境界ケースは、実装が通常の値では正しく見える一方で、消費量が 1,000,000 を超えるとすぐに失敗する可能性があるため便利です。 

ついに、`0 0`は普通のケースではありません。 入力ターミネータです。 特に、均等な請求書では次のような結果が得られますが、`B = 0`、定期的な検査ケースでは陽性反応が見られます`B`したがって、期待すべき唯一のゼロ差入力は終端ペアです。 

## アプローチ

 単純な解決策では、まず変換します。`A`総消費量に占める割合`C`次に、可能な限り少ない消費量を試してください。`x`1から`C / 2`。 候補者ごとに、次のように計算されます。`bill(x)`そして`bill(C - x)`、それらの違いを比較します`B`、必要な差分が見つかったら停止します。 これが機能するのは、考えられるすべての分割が明示的にチェックされ、ステートメントによって 1 つの分割が有効であることが保証されるためです。 

問題は探索空間のサイズです。 いつ`A`に近いです`10^9`、対応する総消費量は約 1 億 4,300 万ユニットです。 その半分はおよそ7,100万の候補者の分裂です。 各候補には少なくとも 2、3 の算術演算とタリフ評価が必要であるため、最悪のケースではテスト ケースごとに約 7,100 万回の反復が行われます。 これは 1 秒の制限と互換性がありません。 

重要な観察は、分割を移動すると 2 つの紙幣の差が単調に変化するということです。 させて`D(x) = bill(C - x) - bill(x)`のために`x <= C / 2`。 として`x`増加すると、小規模世帯では消費量が多くなり、大規模世帯では消費量が少なくなります。 なぜなら`bill`厳密に増加しています、`bill(x)`その間増加します`bill(C - x)`減少します。 その結果、`D(x)`厳密に減少します。 

これにより、総当たり検索が二分探索に変わります。 もし`D(x)`よりも大きいです`B`、私たちが選んだ世帯はまだ小さすぎるため、増加します`x`。 もし`D(x)`よりも小さいです`B`、小さい世帯を大きくしすぎたので、減少します`x`。 一意のソリューションが保証されるということは、正確なターゲットが最終的に見つかることを意味します。 

もう 1 つ便利な簡略化があります。 回復するために考えられる総消費量を調べる必要はありません`C`。 各範囲には固定価格があるため、料金関数は直接反転できます。 たとえば、29,900 を超えて最大 4,979,900 の請求書は、次のようになります。`10,000 + (A - 29,900) / 5`単位。 以来`A`実際の合計消費量から得られることが保証されており、分割は正確です。

 | ブルートフォース | O(C) | お(1) | 遅すぎる |
 | 最適 | O(log C) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.読む`A`そして`B`。 両方がゼロの場合、これは入力の終了をマークする番兵であるため、停止します。 
2.合算請求額を換算する`A`複合消費に`C`。 逆関税は、3 つの関税境界における累積コスト 200、29,900、および 4,979,900 を使用して区分的に計算されます。 
3. 二分探索範囲を次のように設定します。`lo = 1`そして`hi = C // 2`。 この問題により、私たちの世帯が隣の世帯と同じように消費していることが特定されるため、総消費量の半分までしか検索しません。 
4.選択します`mid = (lo + hi) // 2`2 つの消費量を次のようにします`mid`そして`C - mid`。 
5. 2 つの個別の請求書とその差額を計算します。`diff = bill(C - mid) - bill(mid)`。 2 番目の請求書は少なくとも最初の請求書です。`mid <= C - mid`, したがって、検索内では絶対値は不要です。 
6. もし`diff == B`、ユニークな分割を発見しました、そして`bill(mid)`は必須の答えです。 
7. もし`diff > B`、 増加`mid`移動することで`lo`に`mid + 1`。 小規模世帯の消費を増やすと、2 つの請求額が近くなり、消費額が減少します。`diff`。 
8. もし`diff < B`、 減少`mid`移動することで`hi`に`mid - 1`。 均等消費を目指しすぎたため、請求額の差が必要以上に小さくなってしまいました。 

不変条件は、正しいより小さい消費が内部に残ることです。`[lo, hi]`。 機能`D(x)`は厳密に減少しているため、比較するたびに、どの半分に答えが含まれないかがわかります。 いつ`D(mid) > B`、以下のすべての値`mid`少なくとも同程度の差が生じるため、答えは右側にあるはずです。 いつ`D(mid) < B`、以上のすべての値`mid`大きな差は生じないため、答えは左側にあるはずです。 有効な分割は一意であることが保証されているため、二分探索ではそれを破棄できません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def bill(energy):
    if energy <= 100:
        return energy * 2

    result = 200
    energy -= 100

    if energy <= 9900:
        return result + energy * 3

    result += 9900 * 3
    energy -= 9900

    if energy <= 990000:
        return result + energy * 5

    result += 990000 * 5
    energy -= 990000

    return result + energy * 7

def consumption_from_bill(amount):
    if amount <= 200:
        return amount // 2

    if amount <= 29900:
        return 100 + (amount - 200) // 3

    if amount <= 4979900:
        return 10000 + (amount - 29900) // 5

    return 1000000 + (amount - 4979900) // 7

def solve():
    while True:
        A, B = map(int, input().split())

        if A == 0 and B == 0:
            break

        total = consumption_from_bill(A)

        lo = 1
        hi = total // 2

        while lo <= hi:
            mid = (lo + hi) // 2

            smaller_bill = bill(mid)
            larger_bill = bill(total - mid)
            diff = larger_bill - smaller_bill

            if diff == B:
                print(smaller_bill)
                break

            if diff > B:
                lo = mid + 1
            else:
                hi = mid - 1

if __name__ == "__main__":
    solve()
```の`bill`関数は、累積コストを使用して累進料金を実装します。 最初の 100 ユニットの後、最初の 200 Americus はすでに請求されています。 次の 9,900 ユニット以降の累積コストは次のようになります。`200 + 9900 * 3 = 29,900`。 さらに99万台になると、`29,900 + 990000 * 5 = 4,979,900`。 これらの定数により、各請求書計算が一定時間で実行されます。 

の`consumption_from_bill`関数はそれらの同じ境界を反転します。 たとえば、次の場合`amount`が 29,901 ～ 4,979,900 の場合、最初の 10,000 ユニットはすでに 29,900 アメリカスを占めているため、残りの金額を 5 で割って 10,000 に加算します。 

二分探索では、お金ではなく消費を意図的に使用します。 料金は非線形であるため、最初に総消費量を回復せずに料金の差額を直接二分探索しようとすると、関係を表現することが難しくなります。 一度`total`がわかっている場合、2 つの消費量は常にその固定値に加算されます。 

検索で使用されるのは、`bill(total - mid) - bill(mid)`それよりも`abs(...)`。 なぜなら`mid <= total // 2`、2番目の世帯は少なくとも1番目の世帯と同じくらい消費しており、請求機能が増加しています。 したがって、高額な請求額は事前にわかります。 

Python の整数には任意の精度があるため、オーバーフローの心配はありません。 いずれにせよ、最大の中間値は Python の整数表現の範囲内に収まります。 の使用`sys.stdin.readline`また、テスト ケースが多い場合でも、不必要な入力オーバーヘッドが回避されます。

## テストケース```python
import sys
import io

def bill(energy):
    if energy <= 100:
        return energy * 2
    if energy <= 10000:
        return 200 + (energy - 100) * 3
    if energy <= 1000000:
        return 29900 + (energy - 10000) * 5
    return 4979900 + (energy - 1000000) * 7

def consumption_from_bill(amount):
    if amount <= 200:
        return amount // 2
    if amount <= 29900:
        return 100 + (amount - 200) // 3
    if amount <= 4979900:
        return 10000 + (amount - 29900) // 5
    return 1000000 + (amount - 4979900) // 7

def solve_data(data: str) -> str:
    inp = io.StringIO(data)
    out = []

    while True:
        line = inp.readline()
        if not line:
            break

        A, B = map(int, line.split())

        if A == 0 and B == 0:
            break

        total = consumption_from_bill(A)

        lo = 1
        hi = total // 2

        while lo <= hi:
            mid = (lo + hi) // 2

            small = bill(mid)
            large = bill(total - mid)
            diff = large - small

            if diff == B:
                out.append(str(small))
                break

            if diff > B:
                lo = mid + 1
            else:
                hi = mid - 1

    return "\n".join(out)

# Provided samples

    "1100 300\n35515 27615\n0 0\n"
) == "350\n2900", "provided samples"

# consumptions 1 and 2 -> bills 2 and 4.

    "6 2\n0 0\n"
) == "2", "minimum valid case"

) == "98", "first tariff boundary"

) == "2", "large input"

# The all-equal case is represented by the required sentinel 0 0.
assert solve_data(

) == "", "termination sentinel"

最初の関税境界については、次のことを考慮します。`200 4`。 最初の 100 ユニットのコストがちょうど 200 であるため、逆関数は 100 ユニットを返します。間隔が次のように表される場合、二分探索では、可能なより小さい消費量のみ 50 がテストされます。`1..50`、最終的に一意の分割 49 と 51 が見つかります。請求額は 98 と 102 で、必要な差額は 4 になります。計算では、ユニット 100 が最初の範囲の一部として扱われ、ユニット 101 がレート 3 で請求される最初のユニットとして扱われます。

大綴じの場合`999999996 999999987`、合計消費量は 143,145,728 です。 有効な分割は 1 と 143,145,727 です。 小さい請求書は 2 ですが、大きい請求書は 999,999,989 で、その差は 999,999,987 です。 総消費量は 1 億 4,300 万ユニットを超えていますが、二分探索では、考えられる分割を 1 つずつスキャンするのではなく、対数的に多くの反復を行うだけで済みます。 

の`0 0`入力は、関税変換または二分探索の前に処理されます。 ループは直ちに終了するため、誤って消費ゼロの世帯のペアとして解釈されることはありません。 通常のテストケースでは肯定的な結果が得られるため、この区別は重要です。`A`そして`B`、 その間`0 0`は終了マーカーとしてのみ予約されています。
