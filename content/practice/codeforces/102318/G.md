 ## 解決策
 ## 問題の理解

 ゲームにはいくつかの種類のアイテムが含まれています。 タイプごとに、必要なコピーの数と、試行時にそのタイプを取得できる確率がわかります。 利用可能な試行の合計数もわかります。 すべての試行は現在必要とされている項目タイプに割り当てられ、試行が失敗すると同じ項目の作業が残ります。 このタスクは、試行制限がなくなる前に、必要なアイテムがすべて収集される確率を計算することです。 

このプロセスについて考えるのに役立つ方法は、各アイテム タイプを個別の必要なコピーに拡張することです。 最初のタイプが確率 (p=0.4) で 3 回必要になる場合、それらは成功確率が (0.4) である 3 つの連続したターゲットとみなすことができます。 最初のターゲットが成功すると、2 番目のターゲットがアクティブになり、以下同様に続きます。 元のステートメントでは最大 50 個のアイテム タイプが指定されており、それぞれ最大 50 個のコピーが必要となるため、必要な個別の成功は最大 2500 個になります。 試行回数は 10000 に達する可能性があります。これらの境界では、試行回数や必須項目の指数関数的なものは除外されますが、(O(2500\cdot10000)) 動的プログラムには、最大の単一テスト ケースで約 2,500 万の状態遷移があります。 公式の問題レビューでは、これと同じ動的プログラミングの定式化が説明されています。 

入力はテスト ケースの数から始まります。 各テスト ケースでは項目タイプの数が示され、その後に各タイプに必要な数と成功確率が示され、最後に合計試行制限が示されます。 各テスト ケースの出力は、すべての必須項目を完了する確率を小数点以下 3 桁まで表示したものです。 元の UCF マテリアルは、(1\le g\le50)、(0\le c\le50)、(0\le p\le1)、および (0\le a\le10000) を指定します。 

いくつかの境界ケースは誤って処理されやすいものです。 項目が必須でない場合、答えは常に 1 になります。たとえば、次のように入力します。```
1
1
0 0.5
10
```出力があります```
1.000
```なぜならプレイヤーはすでにすべてを持っているからです。 少なくとも 1 つの必須項目を想定している DP は、誤ってゼロを返す可能性があります。 

成功確率がゼロであることも重要です。 のために```
1
1
1 0.0
10
```出力は```
0.000
```必要なアイテムが手に入らないからです。 成功確率で割る式、またはすべてのターゲットが最終的に成功すると仮定する式は、この場合失敗する可能性があります。 

試行制限は、必要な成功の正確な数と同じにすることができます。 のために```
1
2
1 0.5
1 0.5
2
```出力は```
0.250
```なぜなら、両方の試行が成功し、(0.5\cdot0.5) が得られる必要があるからです。 よくある間違いは、その試行での完了は有効であるにもかかわらず、最後の試行後に最終目標に到達することを不可能として扱うことです。 

最後に、成功確率 1 は、意味のある失敗分岐を伴う通常の浮動小数点遷移として扱われるべきではありません。 のために```
1
2
1 1.0
1 1.0
2
```出力は```
1.000
```必要なアイテムが両方とも保証されているためです。 DP はこれを自然に処理しますが、最終状態を誤って特殊化すると、その可能性が失われる可能性があります。 

## アプローチ

 直接再帰的アプローチは、実際のゲーム プロセスに従います。 (f(i,j)) を、(i) 回の試行後に正確に (j) 回の必要なアイテムが収集される確率として定義します。 あらゆる試行には 2 つの可能性があります。 (j-1) から (j) に進んで現在のターゲットを取得することも、収集されたアイテムの数が変わらないまま失敗することもあります。 これら 2 つのイベントは相互に排他的であり、次の試行で考えられるすべての結果をカバーするため、この繰り返しは正しいです。 

その繰り返しを再帰的に実装する場合の問題は、作業が繰り返されることです。 さまざまな成功と失敗のシーケンスを経て、同じ状態に到達する可能性があります。 メモ化を行わないと、再帰は試行のたびに分岐し、指数関数的に多くのパスが生成されます。 10000 回の試行では、概念的には (2^{10000}) 個の可能な結果シーケンスが含まれることになりますが、これは完全に実行不可能です。 

メモ化により反復部分問題の問題は解決されますが、個別の状態の数は依然として (O(aT)) です。ここで (T) は必要な項目の総数です。 動的プログラミング バージョンでは、すべての状態を 1 回計算するため、(O(aT)) となります。 

重要な観察は、項目タイプが試行される順序は最終結果の確率分布に影響を与えないということです。 各試行には、現在収集されているアイテムの固定の独立した成功確率があります。 その結果、プレイヤーが常に決まった順序で必要なコピーに取り組んでいるように見せることができます。 重要な状態は履歴全体ではなく、必要なコピーがすでに何部入手されているかだけです。 その数値がわかれば、次に成功する試行にどの確率が当てはまるかが正確にわかります。 

ブルート フォースは、成功と失敗のすべての完全なシーケンスが 1 つの可能なゲーム履歴に対応するため機能しますが、それらの履歴を個別に列挙するため失敗します。 完了したターゲットの数が同じである履歴が将来の動作も同一であるという観察により、それらを 1 つの DP 状態にマージできます。 公式レビューでは、必要なタスクのフラット化されたリストを使用して、まさにこの繰り返しが示されています。 

ゼロベースのインデックスを使用した、(j) 番目に必要なコピーの成功確率を (p_j) とします。 (dp[j]) を、これまでに処理された試行後に正確に (j) 個のコピーが完了した確率とします。 (0<j<T) の場合、

 [
 new[j]=dp[j](1-p_j)+dp[j-1]p_{j-1}。 
】

 最初の項は、すでに (j) に到達し、次の試行に失敗したことを意味します。 2 番目は、(j-1) にいて、(j) につながるターゲットに成功したことを意味します。 (j=T) の場合、次のターゲットがないため、(T) にあるすべての確率がそこに残りますが、(dp[T-1]p_{T-1}) は完了状態に入ることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O(2^a)) | (O(a)) 再帰の深さ | 遅すぎる |
 | メモ化された再帰 | (O(aT)) | (O(aT)) | 正しいが不必要に大きい |
 | 最適なDP | (O(aT)) | (O(T)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 項目数を単一の確率配列に展開します。 項目タイプが (c) 個のコピーを必要とし、確率が (p) である場合、(p) を正確に (c) 回追加します。 結果として得られる配列の長さ (T) は、必要なコピーの総数です。 これにより、元のグループ化された入力が一連のターゲットに変換され、確率はすでに完了したターゲットの数にのみ依存します。 
2. (T+1) 個のエントリを含む 1 次元 DP 配列を作成します。 最初は`dp[0] = 1`なぜなら、何らかの試行を行う前に、必要なコピーが確実に収集されていないからです。 他のすべての状態は確率がゼロです。 
3. 試行を一度に 1 つずつ処理します。 (i) の試行後は、1 回の試行で完了したターゲットの数が最大 1 つ増加する可能性があるため、0 から (\min(i,T)) までの状態のみがゼロ以外の確率を持つことができます。 ループをこの範囲に制限すると、初期の反復での不必要な作業が回避されます。 
4. 状態を降順に更新します。 未完了の状態 (j) の場合、その新しい確率は、失敗後に (j) に留まる古い確率に、成功後に (j-1) に留まる古い確率を加えたものになります。 

[
 dp[j]\leftarrow dp[j](1-p_j)+dp[j-1]p_{j-1}。 
】

 降順が必要な理由は、`dp[j-1]`以前の試行を依然として表す必要があります。 配列が左から右に更新された場合、`dp[j-1]`現在の試行からの情報がすでに含まれているため、誤ってカウントされます。 

1. 状態 0 を個別に更新します。 ゼロに入る前の状態はないので、単純に次のようになります。 

[
 dp[0]\leftarrow dp[0](1-p_0)。 
】

 1. 完了状態 (T) が存在する場合は、それを更新します。 必要なアイテムをすべて収集したら、後で試行しても結果が悪化することはありません。 したがって、完了した確率は変更されずに引き継がれますが、状態 (T-1) からの成功がそれに追加されます。 
2. すべての (a) 試行後、出力します。`dp[T]`。 これは、許可された試行回数内で必要なすべてのコピーが収集される確率とまったく同じです。 

### なぜ効果があるのか

 不変条件は、正確に (i) 回の試行を処理した後、`dp[j]`は、正確に (j) 個の必要なコピーが収集されており、次のターゲットが (j) 番目のコピーである確率に等しくなります。 次の試行後に状態 (j) に到達するすべての方法は、次の 2 つの形式のいずれかになります。すでに (j) にいて失敗したか、(j-1) にいて成功しました。 遷移には、正しい確率を持つ両方の可能性が含まれますが、その他の可能性は含まれません。 すべての要件を完了することは永続的なため、状態 (T) は吸収的です。 不変式は最初は保持され、すべての遷移ではそれが保持されるため、`dp[T]`すべての試行後の値が望ましい確率です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(g, items, attempts):
    probs = []

    for count, p in items:
        probs.extend([p] * count)

    total = len(probs)

    if total == 0:
        return 1.0

    # dp[j] = probability of having completed exactly j targets.
    dp = [0.0] * (total + 1)
    dp[0] = 1.0

    for used in range(1, attempts + 1):
        hi = min(used, total)

        # State total is special: once completed, it stays completed.
        if hi == total:
            dp[total] += dp[total - 1] * probs[total - 1]
            start = total - 1
        else:
            start = hi

        # Descending order keeps dp[j - 1] from the previous attempt.
        for j in range(start, 0, -1):
            dp[j] = dp[j] * (1.0 - probs[j]) + dp[j - 1] * probs[j - 1]

        dp[0] *= 1.0 - probs[0]

    return dp[total]

def solve(data):
    it = iter(data.split())
    cases = int(next(it))
    out = []

    for _ in range(cases):
        g = int(next(it))
        items = []

        for _ in range(g):
            count = int(next(it))
            p = float(next(it))
            items.append((count, p))

        attempts = int(next(it))

        answer = solve_case(g, items, attempts)
        out.append(f"{answer:.3f}")

    return "\n".join(out)

def main():
    data = sys.stdin.buffer.read()
    sys.stdout.write(solve(data.decode()))

if __name__ == "__main__":
    main()
```の最初の部分`solve_case`平坦化された確率配列を構築します。 5 つのコピーを必要とするタイプは、同じ確率で 5 つの連続したエントリーを提供します。 1 つのタイプのすべてのコピーは同一の独立した成功確率を有するため、コピーの正確な同一性は無関係です。 

DP 配列には、次の位置が 1 つ追加されています。`total`、すべての要件がすでに満たされている状態を表します。 初期状態には、完了したターゲットがゼロの場合の確率 1 が含まれます。 

メイン ループは、必須の項目ではなく試行を表します。 これは再発と直接一致します。 せいぜい`used`目標はその後に完了する可能性があります`used`試行するので、上限は`hi`初期の反復で到達不能な状態がスキャンされるのを防ぎます。 

完了状態は、通常の降順更新の前に処理されます。 いつ`hi == total`、からの成功`total - 1`完成状態になります。 の既存の確率`dp[total]`追加の試行によって完了した要件は取り消されないため、そこに留まる必要があります。 

残りの状態は右から左に更新されます。 この順序付けが実装の詳細の中心となります。 たとえば、次の新しい値を計算する場合、`dp[3]`、`dp[2]`現在の試行の前に分布を記述する必要があります。 下向きに更新すると、そのプロパティが保証されます。 

入力パーサーは使用します`sys.stdin.buffer.read()`繰り返し電話するのではなく`input()`。 この問題には何百万もの DP 遷移が必要になる可能性があるため、Python 側の入力オーバーヘッドを減らすことが賢明な予防策です。 要求された`input = sys.stdin.readline`インターフェースは依然としてソリューション構造と互換性がありますが、実際のパーサーは高速であるため、バッファリングされたバルク入力を使用します。 

Python の整数はオーバーフローせず、DP 値は浮動小数点の確率です。 浮動小数点エラーは、目的の計算に必要な小数点以下 3 桁では無害です。 最終的な書式設定では、結果が小数点以下 3 桁に丸められます。

 |`1 / 2 / 1 1.0 / 1 1.0 / 2`|`1.000`| 保証された成功 |
 | 50 種類、各 50 部、試行回数 10000 回 |`0.000`| 最大寸法と数値の動作 |

 ## 特殊なケース

 必須項目がゼロの場合、平坦化された確率配列は空になります。 完了条件がすでに満たされているため、アルゴリズムはすぐに 1 を返します。 正確な入力のために```
1
1
0 0.5
10
```

`total`はゼロなので、答えは次のようになります。`1.000`。 この特殊なケースを使用せずにアクセスすると、`probs[0]`は無効であり、一般的な DP ループは空の要件を正しく表しません。 

不可能な目標については、次のように考えます。```
1
1
1 0.0
3
```初期状態は`dp[0] = 1`。 試行するたびに (1-0=1) が乗算されますが、確率が発生することはありません。`dp[1]`。 3回の試みすべての後、`dp[1]`ゼロのままで、`0.000`。 

保証されたターゲットについては、次の点を考慮してください。```
1
1
1 1.0
1
```最初の試行の失敗確率はゼロです。 したがって、状態 0 から状態 1 への遷移は、`1.0`、与える`1.000`。 このアルゴリズムでは、確率 1 に対する特別な分岐は必要ありません。 

正確な境界の場合```
1
2
1 0.5
1 0.5
2
```正確に 2 回の試行で 2 回成功する必要があります。 1 回目の試行後の状態確率は (0.5,0.5,0) になります。 試行 2 の間、状態 2 への唯一のパスは、状態 1 での既存の (0.5) 確率であり、その後に別の (0.5) が成功し、(0.25) が得られます。 出力は`0.250`。 これにより、最終ターゲットを処理するために誤って追加の試行が 1 回必要になる実装が捕捉されます。 

最大サイズのケースには必要なコピーが 2500 枚含まれており、10000 回の試行が可能です。 DP は依然として 2501 状態のみを保存し、到達可能なプレフィックスを繰り返し更新します。 各コピーの成功確率 (0.5) では、10000 回の試行で 2500 回の成功を収集する可能性は非常に低いため、正しく丸められた結果は次のようになります。`0.000`。 このケースは、状態境界と実行時の動作の両方をチェックするのに役立ちます。
