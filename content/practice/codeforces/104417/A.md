 ## 解決策
 ## 問題の理解

 この問題の各注文は、締め切り日と必要な数量の製品とともに届きます。 工場では初日から毎日決まった数の製品が生産され、初期在庫はありません。 1 日が終了するたびに、その日の生産が在庫に追加され、その日が期限である注文はすべて、現在の在庫を使用して完全に満たされる必要があります。 

課題は、生産が均一であり、時間の経過とともに在庫が蓄積されることを前提として、すべての注文が期限までに履行されるようにすべての注文を処理する方法が存在するかどうかを判断することです。 

主な問題は、注文が入力順に自然に整列しないことです。 納期の異なる 2 つの注文は共有在庫を通じて相互作用するため、ローカルで実行可能な決定であっても、在庫が間違った順序で消費されると、後で実行可能性が損なわれる可能性があります。 

注文数という点では制約は少なく、テスト ケースごとに最大 100 件ですが、期限と要件の値は 10 億にも及ぶ可能性があります。 これにより、毎日のシミュレーションを明示的に行うことが直ちに除外されます。 正しいソリューションは、圧縮された時間イベント、具体的には実際に入力に現れる個別の締め切り日に対して機能する必要があります。 

単純だが誘惑に陥りやすい間違いは、時間差にわたる在庫の蓄積を慎重に処理せずに、入力順に、または締切順に増加する順序で注文を処理することです。 たとえば、同じまたはそれ以前の有効在庫レベルでの後の複合需要を考慮せずに、初期の大きな需要に貪欲に対応すると、在庫が時期尚早に枯渇する可能性があります。 

もう 1 つの微妙な失敗モードは、複数の注文が同じ期限を共有する場合に発生します。 在庫チェックがその期限の総需要に反していることを確認せずに、ソリューションがそれらを 1 つずつ処理すると、集約された要件を検証する代わりに、複数のステップにわたる部分的な満足を誤って受け入れる可能性があります。 

## アプローチ

 強引な解釈は、毎日シミュレーションすることです。 毎日、在庫を k ずつ増やし、その日期限のすべての注文を確認し、貪欲に履行しようとします。 これは、説明されているプロセスを直接反映しているため、原理的には正しいですが、期限が 10^9 に達すると完全に実行不可能になります。 注文が 100 件しかない場合でも、最大期限までシミュレーションするには、テスト ケースごとに最大 10^9 の反復が必要になります。 

重要な観察は、連続する 2 つの締め切り日の間に何も変化がないことです。 生産は直線的に蓄積され、注文は期限にのみ「アクティブ化」されます。 これにより、期限として表示される日数だけに時間を圧縮することができます。 

時間が短縮されると、締め切り日ごとに、その時点までに利用可能な在庫がその日の期限のすべての注文を満たすのに十分であることを確認する必要があります。 ただし、在庫は複数の日に渡って共有されるため、日ごとに個別にチェックするだけでは不十分です。 正しい観点は、締め切りを昇順に処理し、その日までに必要な需要の合計を維持することです。 

個別の期限ごとに、これまでに生産された在庫量を計算し、k にその日のインデックスを乗じて、その日またはそれ以前に期限があるすべての要件の合計と比較します。 どこかの時点で需要が供給を上回った場合、スケジュールは不可能になります。 

これにより、問題は、並べ替えられたイベントに対するプレフィックスの実行可能性チェックに変換されます。

 ## アルゴリズムのチュートリアル

 作業方法をステップごとに説明しましょう。

1. すべての注文を締め切り日ごとにグループ化します。 毎日、必要な数量をすべて合計します。 これにより、同じ期限の複数の注文を繰り返し処理することがなくなり、重要な時点ごとの総需要のみを追跡できるようになります。 
2. 個別の締切日を昇順に並べ替えます。 これが必要なのは、実現可能性が各時点までの累積生産量に依存するためです。 
3. 必要な製品の実行中のプレフィックス合計を維持します。`need`。 分類された日を繰り返しながら、その日の需要を`need`。 
4. 締め切り日ごとに`d`、利用可能な在庫を次のように計算します。`k * d`。 これは、1 日目から 2 日目までの総生産量を表します。 
5. いつでも`need > k * d`場合は、将来の生産がすべて完全に割り当てられたとしても、工場はすでにその期限までに不足しているため、すぐに「いいえ」を返します。 
6. すべての期限がこの条件を過ぎている場合は、「はい」を返します。 

重要な推論ステップは、期限を過ぎて履行を遅らせることは不可能であるため、最後に全体的に実行するのではなく、各期限の境界で実行可能性を正確にチェックする必要があるということです。 

### なぜ効果があるのか

 いつでも、在庫は時間によって完全に決定され、注文への割り当て方法とは無関係です。 唯一の制約は、期限までの累積需要が、同じ時点までの累積生産を超えてはいけないということです。 これがすべての期限の接頭語に当てはまれば、生産されたユニットを常に時間順に貪欲に割り当てることができます。これは、より早い期限を満たすためにより早い生産が常に利用可能であり、残った在庫は自然に繰り越されるためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        by_day = {}
        
        for _ in range(n):
            a, b = map(int, input().split())
            by_day[a] = by_day.get(a, 0) + b
        
        days = sorted(by_day.keys())
        
        need = 0
        ok = True
        
        for d in days:
            need += by_day[d]
            if need > k * d:
                ok = False
                break
        
        print("Yes" if ok else "No")

if __name__ == "__main__":
    solve()
```この実装では、ディクショナリを使用して注文を期限別にグループ化し、同じ日の複数の注文が単一の累積需要にマージされるようにします。 分割しても実現可能性は変わりませんが、追跡が複雑になるため、これは不可欠です。 

キーをソートすると、時系列の処理が確立されます。 変数`need`需要の実行中のプレフィックス合計として機能し、各ステップでそれを生産能力と比較します。`k * d`。 Python では任意精度の整数のため乗算は安全ですが、固定幅言語では 64 ビット算術を使用することが重要です。 

プレフィックスが容量を超えると、それ以上の処理では実現可能性を回復できないため、初期のブレークは正確性を維持する最適化です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import defaultdict

    def solve():
        t = int(input())
        out = []
        for _ in range(t):
            n, k = map(int, input().split())
            mp = defaultdict(int)
            for _ in range(n):
                a, b = map(int, input().split())
                mp[a] += b
            need = 0
            ok = True
            for d in sorted(mp):
                need += mp[d]
                if need > k * d:
                    ok = False
                    break
            out.append("Yes" if ok else "No")
        return "\n".join(out)

    return solve()

 ## 特殊なケース

 エッジケースの 1 つは、すべての注文が同じ期限を共有する場合です。 その状況では、アルゴリズムはすべての需要を 1 つの値にマージし、それをその日の k 回の値と 1 回比較します。 たとえば、入力`(2,1),(2,1),(2,1)`k = 2の場合、need = 3およびcapacity = 4が生成され、これは正しく受け入れられます。 

もう 1 つのエッジ ケースは、10^9 日目に 1 件の注文があるなど、締め切りがまばらな場合です。 このアルゴリズムは中間日をシミュレートせず、容量を k * 10^9 として直接計算し、正確に必要な境界で正確さをチェックしながら時間の爆発を回避します。 

最後の微妙なケースは、早い締め切りは厳しいが、後の締め切りは緩い場合です。 プレフィックスの比較により、早期の累積需要が実現可能になると、残りの生産能力が増加する生産関数を通じて暗黙的に繰り越されるため、後のスラックが正確さに影響を与えないことが保証されます。
