 ## 解決策
 ## 問題の理解

 私たちは、さまざまな職業の従業員でスタートする会社を与えられており、各職業の種類には現在利用可能な労働者の数があります。 この初期の労働力に加えて、複数の建設プロジェクトが利用可能です。 各プロジェクトには 2 つの部分があります。1 つは特定の職種にわたる一連の最低人員配置要件、もう 1 つはプロジェクトの完了後に一部の職種の従業員を追加することで労働力を増やす報酬です。 

重要なのは、単一の最適なプロジェクトや固定スケジュールを選択することではありません。 その代わりに、プロジェクトを試みる時点で、その人員配置要件がすべて現在の従業員によって満たされている限り、プロジェクトの任意のサブセットを選択し、任意の順序で実行することができます。 プロジェクトが完了すると、その報酬によって利用可能な従業員が永続的に増加し、後で他のプロジェクトのロックが解除される可能性があります。 

目標は、完了できるプロジェクトの最大数を決定することです。 

制約は大きく、初期職業タイプは最大 100,000、プロジェクトは最大 100,000 で、要件と報酬のエントリの総数も 100,000 で制限されます。 これにより、プロジェクトのオーダーのすべての順列をシミュレートするアプローチは即座に除外されます。1 つのオーダーの実現可能性をチェックするだけでもすでにコストがかかりすぎるためです。 

重要な構造は、システムの状態は時間の経過とともにのみ改善されるということです。 従業員数は決して減らないため、実現可能性は単調です。要件が一度満たされると、その要件は永久に満たされ続けます。 この単調性は、貪欲なアクティベーション プロセスを可能にする中心的な特性です。 

新しくロック解除されたプロジェクトを追跡せずに、固定された順序で貪欲にプロジェクトを選択しようとすると、微妙な失敗例が発生します。 たとえば、プロジェクト A が最初は実行可能ではなく、プロジェクト B の後でのみ実行可能になる場合、A を再訪しない単純なスキャンでは、プロジェクト A を完全に見逃してしまいます。 難易度は多次元であり、進化するリソースに依存するため、プロジェクトを難易度で分類しようとすると、別の問題が発生します。 

## アプローチ

 最も直接的なアイデアは、プロジェクトの可能な順序をすべて試して、実行をシミュレーションすることです。 各ステップで常に要件を確認し、報酬を適用できるため、これは概念的に機能します。 ただし、最悪の場合、順列の数は n 階乗となり、n = 100000 の場合でも完全に実行不可能になります。 

より構造化された強引な方法は、すべてのプロジェクトを繰り返しスキャンし、現在実行可能なものを選択し、進歩がなくなるまで繰り返すことです。 これは正しいプロセスに近いものですが、単純に実装すると遅すぎます。各フル スキャンのコストが O(n) であり、それを O(n) 回繰り返す可能性があるため、O(n^2) の動作が発生する可能性があります。 

重要な観察は、実現可能性は各職業タイプの各要件のしきい値に到達したかどうかによってのみ決まるということです。 カウントは増加するだけなので、要件が一度満たされると、再度無効になることはありません。 これは、現在実行可能なプロジェクトの動的なセットを維持し、従業員数が増加したときに効率的に更新する必要があることを示唆しています。 

視点を逆転させることができます。各プロジェクトを繰り返しチェックするのではなく、職種ごとにどのプロジェクト要件が依存しているかを追跡し、その職種の数が増加した場合にのみそれらのプロジェクトを更新します。 各要件は基本的にしきい値イベントであり、カウントがそのしきい値を超えると、永続的に満たされます。 

これにより、問題は、暗黙的な依存関係グラフ上の BFS と同様に、キュー内の現在実行可能なすべてのプロジェクトから開始し、それらを繰り返し実行し、その報酬を伝播してさらなるプロジェクトのロックを解除するプロセスに変換されます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 完全な順列検索 | お(ん!) | O(n) | 遅すぎる |
 | フルスキャンの繰り返し | O(n^2) | O(n) | 遅すぎる |
 | しきい値追跡による増分 BFS | O((n + m + k) log m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 各要件は、対応する職業数が十分に多くなると満たされる可能性がある条件として扱われます。 カウントは増加するだけなので、各要件は満たされていない状態から満たされた状態に 1 回だけ遷移します。 

### ステップ

 1. 各職種から現在の従業員数へのマッピングを作成します。 これが私たちの進化する状態です。 
2. すべてのプロジェクトについて、最初に満たされていない要件がいくつあるかを計算します。 プロジェクトに未満たな要件がない場合は、すぐに実行可能になります。 
3. 効率的に更新するには、すべての要件を職業タイプごとにグループ化します。 タイプごとに、すべての要件エントリをしきい値でソートして保存します。 各エントリはプロジェクトと最小必要数をリンクします。 
4. 現在実行可能なすべてのプロジェクトでキューを初期化します。 
5. キューが空でない間に、プロジェクトを 1 つ削除して実行します。 解答カウンターを増やします。 
6. このプロジェクトの報酬ごとに、対応する職業数を増やします。 
7. 職業数が増加するたびに、そのタイプのソートされた要件リストに目を通し、現在しきい値が満たされているすべての要件にマークを付けます。 新しく満たされた要件ごとに、そのプロジェクトの残りの未満たされている要件の数を減らします。 プロジェクトの未処理数がゼロになった場合は、そのプロジェクトをキューに追加します。 

重要な点は、各要件がしきい値を超えた瞬間に 1 回だけ処理されるということです。 

### なぜ効果があるのか

 アルゴリズムは常に、現在の従業員の下ですべての要件が満たされている場合にのみ、プロジェクトがキューにあるという不変条件を維持します。 従業員数は増加するだけであるため、満たされていない要件は一方向にしか満たされず、一度満たされると元に戻ることはありません。 したがって、すべてのプロジェクトは実行可能になると正確にキューに入り、遅延によって将来のプロジェクトの達成が困難になることはないため、すぐに実行しても安全です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    g = int(input())
    cnt = {}
    for _ in range(g):
        t, u = map(int, input().split())
        cnt[t] = cnt.get(t, 0) + u

    n = int(input())

    reqs = []
    proj_req = [[] for _ in range(n)]
    proj_unmet = [0] * n
    reward = [[] for _ in range(n)]

    type_reqs = {}

    for i in range(n):
        parts = list(map(int, input().split()))
        m = parts[0]
        idx = 1

        for _ in range(m):
            a = parts[idx]
            b = parts[idx + 1]
            idx += 2
            req_id = len(reqs)
            reqs.append((a, b, i))
            proj_req[i].append(req_id)
            if cnt.get(a, 0) < b:
                proj_unmet[i] += 1
            type_reqs.setdefault(a, []).append(req_id)

        parts = list(map(int, input().split()))
        k = parts[0]
        idx = 1
        for _ in range(k):
            c = parts[idx]
            d = parts[idx + 1]
            idx += 2
            reward[i].append((c, d))

    # sort requirements per type by threshold
    ptr = {}
    for t, lst in type_reqs.items():
        lst.sort(key=lambda x: reqs[x][1])
        ptr[t] = 0

    q = deque()
    visited = [False] * n

    for i in range(n):
        if proj_unmet[i] == 0:
            q.append(i)
            visited[i] = True

    ans = 0

    while q:
        i = q.popleft()
        ans += 1

        for c, d in reward[i]:
            old = cnt.get(c, 0)
            new = old + d
            cnt[c] = new

            if c in type_reqs:
                lst = type_reqs[c]
                p = ptr[c]
                while p < len(lst) and reqs[lst[p]][1] <= new:
                    req_id = lst[p]
                    proj = reqs[req_id][2]
                    # each requirement triggers exactly once
                    proj_unmet[proj] -= 1
                    if proj_unmet[proj] == 0 and not visited[proj]:
                        q.append(proj)
                        visited[proj] = True
                    p += 1
                ptr[c] = p

    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、職業タイプごとにグローバル カウンターが保持され、報酬が適用された場合にのみ更新されます。 各職業タイプには、要件のしきい値のソートされたリストと、各要件を 1 回だけ処理することを保証するポインターがあります。 しきい値を超えると、対応するプロジェクトの残りの要件数がすぐに更新されます。 

よくある落とし穴は、1 つの職業の更新で一度に複数の要件のロックが解除される可能性があることを忘れることです。そのため、しきい値を超える while ループが不可欠です。

 | 時間 | O(n + m + k) | 各要件は、しきい値を超えると 1 回処理され、各プロジェクトは 1 回キューに入れられます。

 ## 特殊なケース

 主なエッジケースは、プロジェクトに要件がない場合です。 このようなプロジェクトは、現在の従業員に関係なく、常にすぐに利用可能でなければなりません。 未処理カウントはゼロから始まるため、アルゴリズムはこれを自然に処理し、初期化中にキューに挿入されます。 

もう1つのケースは、報酬の大幅なジャンプにより、同じ職業の複数の要件が一度に満たされる場合です。 ポインタベースの処理により、1 回の更新で超えたすべてのしきい値が 1 回のスイープで適用され、各要件が 1 回だけカウントされることが保証されます。 

最後の微妙なケースは、ロック解除が繰り返されることです。プロジェクトは、時間の経過とともに、最後に満たされた要件をさまざまな報酬から受け取る可能性があります。 Unmet カウンタは、完全に満たされたときに 1 回だけキューに入るようにし、重複した処理を防ぎます。
