 ## 解決策
 ## 問題の理解

 最初は空のバイナリ ヒープ配列に 1 つずつ挿入される一連の値が与えられます。 各挿入では、標準の「シフトアップ」手順が使用されます。つまり、新しい要素が最後に追加され、その後、ヒープ プロパティに違反している間、その要素が親と繰り返し交換されます。 

問題は、ヒープのプロパティが固定されていないことです。 挿入ごとに、ヒープは、非表示のバイナリ文字列に応じて最小ヒープまたは最大ヒープとして処理されます。 ビットが 0 の場合、構造体は挿入中に最小ヒープのように動作します。つまり、親の値が子よりも大きくてはなりません。 ビットが 1 の場合、最大ヒープのように動作します。つまり、親の値が子よりも小さくてはなりません。 

すべての挿入の後、結果の配列が与えられます。これは、挿入された値の順列であることが保証されていますが、挿入ごとに異なるヒープ タイプが使用されている可能性があるため、どちらの解釈でもグローバルに有効なヒープであるとは限りません。 タスクは、最終的な配列が指定されたものとまったく同じになるように、各挿入がどのように実行されたかを説明するバイナリ文字列を再構築することです。 複数の文字列が機能する場合は、辞書順に最小の文字列を出力する必要があり、0 より前を優先します。 有効なシーケンスが存在しない場合は、不可能であることを報告する必要があります。 

この制約により、テスト ケース全体で最大合計 100 万回の挿入が許可されるため、ソリューションはテストごとに基本的に線形またはほぼ線形である必要があります。 バイナリ文字列のすべての選択肢をシミュレートしようとする試みは指数関数的であり、すぐには不可能です。 単純に挿入タイプをバックトラックしようとしても、すべてのステップで分岐が発生することになり、これは限界をはるかに超えています。 

単一の挿入タイプに対する貪欲な決定が後で実現可能性を妨げる場合、微妙な失敗のケースが発生します。 たとえば、値が早い段階で最大ヒープ挿入に強制されると、値が大きくなりすぎて、後で必要なヒープ構成が不可能になる可能性があります。 もう 1 つのエッジ ケースは、等しい値が出現する場合です。両方のヒープ タイプが等しい場合には同じように動作するため、複数の文字列が有効になる可能性があり、辞書編集上の最小性が主な制約になります。 

## アプローチ

 自然な開始点は、バイナリ文字列を推測しながらプロセスをシミュレートしてみることです。 挿入位置ごとに、最小ヒープと最大ヒープの両方の動作を試し、シフトアップ操作を実行して、最終配列にまだ到達できるかどうかを確認できます。 これは、現在のヒープ構成と位置で構成される状態に対するバックトラッキングまたは動的プログラミングを直ちに示唆します。 ただし、ヒープ自体は決定全体にわたって階乗的に多くの構成を持つことができ、挿入ごとに要素が対数ステップ上にシフトされる可能性があります。 2 つの異なる決定シーケンスが同じプレフィックス構造をもたらしても、後で分岐する可能性があるため、枝刈りさえも効果がありません。 これにより、ブルート フォースが n で指数関数的に近づきます。 

重要な観察は、視点を逆転させることです。 それぞれの挿入によってヒープがどのように変更されるかを考える代わりに、最終的な配列を決定論的なシフトアップ パスのエンドポイントとして解釈できます。 挿入された各値は、比較条件によって停止するまで、その挿入位置からいくつかの祖先位置までのパスをたどります。 停止条件は、そのステップで最小動作を強制するか最大動作を強制するかによってのみ決まります。 

したがって、各要素の動作は、挿入時にルートへのパスに沿った比較セグメントを制約します。 プロセスを逆方向に再構築することを考えると、最終的な配列構造によって引き起こされる祖先関係に沿った最終的な順序と一致する必要がある型を各挿入に事実上割り当てることになります。

重要な削減点は、中間ヒープを明示的に再構築する必要がないことです。 各挿入 i について、最小または最大の動作を選択できることを確認するだけで、最終配列内の v_i の最終配置が、挿入パスに沿った有効な上方比較シーケンスと互換性が保たれます。 これは、ヒープ インデックスによって引き起こされる固定の暗黙的なツリー構造上での実現可能性割り当て問題となり、各ノードは 2 つの可能な単調制約のうちの 1 つを満たさなければなりません。 

これにより、問題は、挿入パスに沿ったすべての比較が最終的な配列と一致するように、各 i に対して min タイプまたは max タイプの挿入を強制できるかどうかを決定することになります。 辞書編集上最小の文字列は、実現可能性を損なわない限り、最小タイプ (ゼロ) を貪欲に優先することによって取得されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (すべての文字列を試し + ヒープをシミュレート) | O(2^n · n log n) | O(n) | 遅すぎる |
 | 最適 (挿入ごとの貪欲な実現可能性) | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 前の要素のタイプの固定選択に従った場合に得られるヒープ構造を維持しながら、挿入を順番に処理します。 重要なのは、単純な方法でヒープを再構築するのではなく、最終的なヒープ構成をシミュレートし、型を割り当てるときに一貫性制約を適用することです。 

1. 空のヒープ構造から開始し、要素 v1 から vn を順番に処理します。 各要素はヒープ配列内の位置 i に配置され、そのシフトアップ パスを概念的にシミュレートします。 
2. 各挿入 i に対して、まずタイプ 0 (最小ヒープ動作) を割り当てようとします。 パスに沿ってのみシフトアップ比較をシミュレートします。ノードがルートではない間、スワップが最小ヒープ ルールと一致するかどうかを確認します。つまり、親は停止点で現在のノード以下である必要があります。 これらの比較の制約として、最終的な配列値を使用します。 
3. min-type の割り当てが最終的な配列構造と矛盾する場合、つまり最小ヒープ条件に違反するパスに沿った必要な比較が存在する場合、この選択を拒否します。 
4. min-type が有効でない場合は、タイプ 1 (最大ヒープ動作) を割り当てます。 同じ挿入パスに沿って同様に検証しますが、条件が逆になります。つまり、停止条件では親が子以上である必要があります。 
5. どちらの割り当ても有効でない場合は、この要素がどのようにその位置に到達したかを説明できる一貫したヒープ ルールがないため、バイナリ文字列は指定された最終配列を生成できないと結論付けます。 
6. 挿入ごとに選択されたビットを記録し、これが有効な挿入プロセスを定義することを概念的に受け入れます。 

重要な点は、各挿入パスがグローバルな再配置ではなく、ヒープ ツリー内の祖先インデックスのみに依存することです。 したがって、検証は、挿入ごとに最大 O(log n) 個の比較のチェーンをチェックすることになります。 

### なぜ効果があるのか

 いつでも、ヒープ構造は以前の挿入とその最終位置によってのみ決定されます。 要素 i の挿入は、その祖先チェーン上のノードとのみ対話します。 最後の配列は、発生したはずのスワップのシーケンスと一致する、そのような各チェーンに沿った全体の順序をエンコードします。 タイプの選択は、そのチェーンに沿って単調条件を強制することに対応します。 比較が修正されるとスワップは決定的になるため、型の有効な割り当てによってヒープの進化が一意に決まります。 min-type は max-type よりも弱い順序付け制約を課すため、可能な限り貪欲に min-type を選択すると、将来の実現可能性が維持されます。そのため、後の挿入に対して柔軟性が高くなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check(v, a, i, is_max):
    x = i
    val = v[i]
    while x > 1:
        p = x // 2
        if is_max:
            if a[p] < val:
                return False
            if a[p] == val:
                break
        else:
            if a[p] > val:
                return False
            if a[p] == val:
                break
        x = p
    return True

def solve():
    n = int(input())
    v = [0] + list(map(int, input().split()))
    a = [0] + list(map(int, input().split()))

    b = ['0'] * (n + 1)

    for i in range(1, n + 1):
        if check(v, a, i, False):
            b[i] = '0'
        elif check(v, a, i, True):
            b[i] = '1'
        else:
            print("Impossible")
            return

    print("".join(b[1:]))

t = int(input())
for _ in range(t):
    solve()
```コードは各挿入を独立して処理し、最初にそれを最小ヒープ挿入として検証しようとします。 の`check`関数は、挿入位置から親チェーンをたどって、パスに沿った比較がヒープ ルールと矛盾しないことを検証します。 矛盾が現れた瞬間、そのタイプは拒否されます。 等しい値が出現すると、どちらのヒープ タイプも、最終構成によって暗示される安定性を侵害することなく、その時点を超えてスワップを強制することができないため、等価性は停止条件として機能します。 

実装の微妙な詳細は、等価性の処理です。 一度`a[p] == val`、ヒープの種類に関係なく、シフトアップがそこで停止する可能性があるため、早めに中断します。 これにより、パスが過度に制約されるのを防ぎます。

 ## 特殊なケース

 最初のエッジケースは、すべての値が同一である場合です。 すべての挿入は、任意のパスに沿って最小ヒープ条件と最大ヒープ条件の両方を満たしているため、辞書編集上の最小の出力はすべてゼロの文字列になります。 等号が min 条件に違反することはなく、上向きの動きは直ちに停止されるため、アルゴリズムはすべてのステップで min-type を正しく受け入れます。 

もう 1 つのエッジ ケースは、最終配列が挿入順序と正確に一致する場合です。 その場合、すべての要素はスワップなしですでに正しいヒープ位置にあるため、すべての挿入は即時停止と一致している必要があります。 どちらのヒープ タイプでもこれが許可されているため、貪欲な選択では常に 0 が選択されます。 

最後のエッジ ケースは、グローバルでは 1 つの挿入タイプのみが実行可能であるが、ローカルではどちらも初期のステップに有効であると思われる場合です。 貪欲な戦略では、強制されない限り max-type へのコミットを回避します。また、max-type はより厳しい上方制約を導入するため、時期尚早に選択すると柔軟性が失われます。 このアルゴリズムは、可能な限り min-type を延期し、祖先チェーンに沿って検証が失敗した場合にのみ切り替えることで、これを回避します。
