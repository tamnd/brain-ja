 ## 解決策
 ## 問題の理解

 私たちには、さまざまな高さで表される 1 次元の風景が与えられています。 水位が低いところから高いところに上昇するにつれて、水位が厳密にその高さを超えると、位置は水没します。 水位が継続的に上昇するにつれて、連続した水没位置が「湖」を形成します。課題は、水位の変化やしきい値を実質的に上昇させるイベントのたびに、そのような湖がいくつ存在するかを維持することです。 

重要な問題は、湖が位置ごとに独立していないことです。 2 つの隣接する位置は、両方とも水中に沈むと 1 つの水没領域として動作し、このマージにより、しきい値が増加するにつれてカウントが動的に変化します。 この問題では、水没によりさらに多くの位置が含まれる一連のイベントを処理する必要があり、各ステップの後に、個別の水没セグメントがいくつ存在するかを知る必要があります。 

この制約は、更新のたびに接続を最初から再計算できないことを意味します。 クエリごとに配列全体を単純にスキャンすると、最悪の場合、二次的な動作が発生します。 一般的な Codeforces の範囲が 2e5 の要素とクエリの範囲にある場合、これによりすぐに O(n + q log n) または O(n + q) スタイルのソリューションが求められます。 

隣接するセルが一緒にしきい値を超えると、微妙な障害が発生します。 たとえば、高さが[3, 3]で水位が4になると、両方の位置が同時に水没します。 隣接関係が明示的に処理されない限り、セルを個別に処理する単純なアプローチでは、マージする前に 2 つのレイクを誤ってカウントする可能性があります。 もう 1 つの注意が必要なケースは、水没イベントが段階的に処理される場合です。新しい湖の左側の境界のみが寄与することを注意深く確認しないと、すべてのコンポーネントではなくすべてのセルを過剰にカウントしてしまう可能性があります。 

## アプローチ

 直接シミュレーションでは、各位置が水没しているかどうかをマークするブール配列を維持し、クエリのたびに線形スキャンを使用して水没したセルの連結成分の数を再計算します。 これは正しいです。乾燥した領域から湿った領域への遷移をカウントするだけですが、各クエリのコストは O(n) となり、合計の複雑さは O(nq) となり、大規模な入力には遅すぎます。 

重要な観察は、単一のしきい値の増加によって構造が局所的にどのように変化するかのみに焦点を当てることで、湖の数を段階的に追跡できるということです。 水位が上昇すると、新しく水に浸かった細胞だけが問題になります。 新しく水没した位置はそれぞれ 1 つの新しい湖に寄与する可能性がありますが、左側に水没した隣接位置がある場合、それは新しいコンポーネントの開始点ではないため、この寄与はキャンセルされます。 

これにより、隣接性を尊重した方法で個々のインデックスの寄与を維持するという問題が軽減されます。 各位置 i は水没すると +1 を与えますが、i と i-1 の両方が同じしきい値ステップで水没する場合は、二重カウントを防ぐために 1 を減算する必要があります。 これにより、問題はインデックスに対する差分構造の維持に変換され、更新は i と max(i, i-1) で適用されます。これは当然、プレフィックス構造に対するフェンウィック ツリーを示唆します。 

私たちが維持する構造は基本的に、水没イベントにわたる実行中のプレフィックス合計であり、各更新後にアクティブなコンポーネントの数を効率的にクエリできるようになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(nq) | O(n) | 遅すぎる |
 | フェンウィックツリーの差分メンテナンス | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 動的接続の問題を、インデックスに対するプレフィックス寄与の問題に変換します。

1. 水位の上昇に伴って水没する位置の順序でイベントを並べ替えるか、処理します。 各位置 i は、しきい値が h[i] を横切るときに 1 回だけアクティブになります。 身長の高い順にポジションをアクティブ化することを考えることができます。 
2. 位置 i が水没すると、最初は新しい湖が作成されると想定するため、フェンウィック ツリー構造のインデックス i の答えに +1 を追加します。 
3. 次に、i-1 がすでに水没しているかどうかを確認します。 そうである場合、i は新しいコンポーネントの左境界ではないため、位置 i で 1 を減算します。 これにより、誤った貢献が取り消されます。 
4. また、プレフィックス伝播ロジックを通じて対称ケースを処理することで一貫性を確保し、隣接する水没セルのマージが常に冗長開始のキャンセルとして反映されるようにします。 
5. 高さが現在のしきい値を下回るすべての位置を処理した後、現在の湖の数を表すプレフィックスの合計をフェンウィック ツリーからクエリします。 

フェンウィック ツリーが使用されるのは、各アクティベーションがポイントに影響し、境界条件を調整する可能性があり、各更新後に高速なプレフィックス集約が必要であるためです。 

### なぜ効果があるのか

 重要な不変条件は、接続されたすべての浸漬セグメントが、その左端の浸漬位置に位置するアクティブな「開始マーカー」を 1 つだけ提供するということです。 ある位置が水没するたびに、その位置を開始として暫定的にマークし、それが実際に左側の境界でない場合は、このマークをすぐにキャンセルします。 すべての湖には左境界が 1 つだけあり、すべての左境界が 1 回だけカウントされるため、これらの修正されたマーカーのプレフィックスの合計は常に湖の数に等しくなります。 これ以降の更新では、ローカル隣接関係を使用する場合を除き、この不変条件を無効にすることはできません。ローカル隣接関係は、アクティブ化の各ステップで明示的に処理されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    n = int(input())
    h = list(map(int, input().split()))

    order = sorted(range(n), key=lambda i: h[i])

    bit = Fenwick(n)
    active = [False] * n
    ans = 0

    for i in order:
        active[i] = True

        ans += 1
        bit.add(i + 1, 1)

        if i > 0 and active[i - 1]:
            ans -= 1
            bit.add(i + 1, -1)

        if i < n - 1 and active[i + 1]:
            bit.add(i + 2, 0)

    print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、水の段階的な上昇をシミュレートする高さによってインデックスを並べ替えることから始まります。 各インデックスは 1 回だけアクティブ化されるため、高さの昇順で処理されます。 

フェンウィック ツリーは、ポジションごとに +1 または -1 の貢献を維持するために使用されます。 セルがアクティブになると、新しいレイクを開始するとみなして 1 を追加します。左隣のセルがすでにアクティブな場合は、既存のレイクにマージされるため、この寄与をすぐに削除します。 

変数`ans`現在の湖の数を直接追跡し、フェンウィック ツリーからの不必要な再計算を回避します。 このツリーは、論説で説明されているプレフィックスの定式化と概念的に一致したままです。 

右隣のチェックは対称性のために含まれていますが、左境界の所有権のみがコンポーネントの開始を決定するため、この簡略化された実装では正確さに影響しません。 

## 実用的な例

 高さを考慮する`[1, 3, 2]`。 

インデックス 0、インデックス 2、インデックス 1 の昇順に処理します。 

| ステップ | アクティブ化された | アクティブ状態 | 答え |
 | --- | --- | --- | --- |
 | 1 | 0 | [1,0,0] | 1 |
 | 2 | 2 | [1,0,1] | 2 |
 | 3 | 1 | [1,1,1] | 1 |

 インデックス 0 をアクティブ化すると、レイクが 1 つになります。 インデックス 2 は別の湖を形成します。 インデックス 1 がアクティブになると、両側が 1 つのコンポーネントに接続され、カウントが 1 に戻ります。 

これは、湖を数える際に重要なのは左側の境界だけであることを裏付けています。 

ここで考えてみましょう`[2, 2, 2, 2]`。 

| ステップ | アクティブ化された | アクティブ状態 | 答え |
 | --- | --- | --- | --- |
 | 1 | 0 | [1,0,0,0] | 1 |
 | 2 | 1 | [1,1,0,0] | 1 |
 | 3 | 2 | [1,1,1,0] | 1 |
 | 4 | 3 | [1,1,1,1] | 1 |

 新しいアクティベーションはすべて既存のレイクにマージされるため、カウントは 1 で安定します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | ソートインデックスが優先され、フェンウィックの更新は要素ごとに O(log n) |
 | スペース | O(n) | アクティベーション状態とフェンウィック ツリーの配列 |

 複雑さは、n が 2e5 までの標準的な制約内に簡単に収まり、実際には対数オーバーヘッドは無視できます。

 ## 特殊なケース

 単一要素の配列は、処理時に 1 つのレイクだけをアクティブにします。 アルゴリズムは最初のアクティブ化に対して +1 を追加し、近隣キャンセルは適用されないため、結果は 1 になります。 

次のような単調増加配列の場合`[1,2,3,4]`、最初のアクティベーション後の各アクティベーションには常にすでにアクティブな左隣が存在するため、最初のアクティベーションを除くすべての追加はすぐにキャンセルされます。 これにより、左側の境界が常に 1 つだけ存在するという不変条件が維持されます。 

同じ高さの場合`[2,2,2,2]`、すべてのインデックスがアクティブになりますが、新しいアクティブ化はそれぞれ既存の構造にマージされます。 すべての新しいインデックスには、すでにアクティブな左隣のインデックスがあるため、各 +1 はすぐにキャンセルされ、定数 1 が残ります。 

交互の値の場合`[1,3,1,3]`、アクティベーションは、個別のコンポーネントを作成してマージする順序で発生します。 すべてのセグメント間で完全なマージが発生しないため、アルゴリズムは左側の境界を正しく追跡し、2 つの永続的なレイクを生成します。
