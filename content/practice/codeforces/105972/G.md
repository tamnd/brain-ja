 ## 解決策
 ## 問題の理解

 名前付きオブジェクトを徐々に構築および破棄する一連の操作が与えられます。 変数を表す名前もあれば、変数を指す参照を表す名前もあります。 各名前は、その存続期間を通じて一意です。 

アクションは4種類あります。 変数の作成、既存の変数への読み取り専用参照の作成、既存変数への書き込み可能参照の作成、または以前に作成した名前 (変数または参照のいずれか) の削除を行うことができます。 

システムは、すべての操作後に 2 つの制約が成立する場合にのみ有効であると見なされます。 まず、各変数は任意の数の読み取り専用参照または 1 つの書き込み可能な参照のいずれかをを持つことができますが、両方の型を同時に持つことはできません。 次に、すべての参照は常に、現在存在する変数、つまり削除されていない変数を指している必要があります。 

重要な点は、参照と変数は削除という意味では独立したオブジェクトですが、所有権ルールを通じて論理的にリンクされていることです。 単純なアプローチでは、作成時にのみ有効性をチェックする可能性がありますが、後で追加の参照が追加または削除されたときに違反が発生する可能性があります。 

この制約は、テスト全体の操作の総数が最大 100,000 に達するため、操作ごとにほぼ一定時間のブックキーピングが必要であることを意味します。操作ごとにすべての参照をスキャンするソリューションは、二次時間に縮退して失敗します。 

典型的な失敗例は、同じ変数への書き込み可能参照と読み取り専用参照が混在している場合に発生します。 

たとえば、次のシーケンスを考えてみましょう。 

入力:```
1
3
1 a
2 b a
3 c a
```作成後`a`、読み取り専用の参照を添付します。`b`、その後、書き込み可能な参照をアタッチしてみます`c`。 正しい答えは、`No`書き込み可能な参照は読み取り専用の参照と共存できないためです。 単純なアプローチでは、ローカル状態のみをチェックするか、既存の読み取り専用参照の追跡を忘れる可能性があります。 

もう 1 つの問題となるケースには、削除が含まれます。 

入力:```
1
3
1 a
2 b a
4 a
```ここで、削除すると、`a`その間`b`まだ存在します`b`ぶら下がっている参照。 ルールの作成時にのみ検証するソリューションでは、これが誤って受け入れられてしまいます。 

これらの例は、各操作を個別に検証するだけでなく、グローバルな状態の一貫性を継続的に維持する必要があることを示しています。 

## アプローチ

 この強引なアイデアは、完全な構造追跡を使用してすべてを明示的にシミュレートすることです。 すべての変数について、それを指すすべての参照のリストを維持できます。 新しい参照を作成するときは、その変数の既存の参照をすべてスキャンして、競合する型 (読み取り専用か書き込み可能か) がすでに存在するかどうかを確認します。 変数を削除するときは、すべての参照も調べて無効化します。 

このアプローチはルールを直接反映しているので正しいですが、遅すぎます。 最悪の場合、単一の変数に O(n) 個の参照が蓄積される可能性があり、各操作ですべての参照のスキャンまたは更新が必要になる可能性があります。 これにより、全体として O(n²) の動作が行われます。 

重要な点は、実際には個々の参照を検査する必要がないということです。 必要なのは、変数ごとに集計された情報 (現在書き込み可能な参照があるかどうか、および読み取り専用の参照がいくつ存在するか) だけです。 問題をこれらのカウンターの維持に縮小すると、各操作は O(1) になります。 

より深い構造的洞察は、参照が互いに直接相互作用しないということです。 これらは、それらが指す変数を通じてのみ対話します。 これにより、すべての参照状態を変数ごとのメタデータに圧縮できます。 

削除には依然として注意が必要です。変数が削除されるときは、その変数へのすべての参照が無効になるようにする必要があります。 明示的に削除する代わりに、単に変数をデッドとしてマークし、今後の使用を拒否することができます。

 ## アルゴリズムのチュートリアル

 私たちは 3 つのハッシュ マップを維持します。 名前が現在アクティブな変数または参照として存在するかどうかを追跡します。 各変数をアクティブな読み取り専用参照の数にマップします。 変数に現在書き込み可能な参照があるかどうかを追跡します。 

また、各参照名からそれが指す変数へのマッピングも維持するため、削除時に正しい変数を更新できます。 

アルゴリズムは次のように進みます。 

1. 各操作を読み取り、そのタイプを特定します。 必要なときにその名前が存在しない場合、システムはすでに矛盾しているため、プログラムは拒否されます。 
2. 変数を作成するとき、変数をアクティブとしてマークし、その参照カウンターをゼロに初期化します。 この変数は、制約が適用されていない状態で開始されます。 
3. 変数への読み取り専用参照を作成するときは、まずターゲット変数がまだアクティブであることを確認します。 次に、この変数に書き込み可能な参照がすでにあるかどうかを確認します。 その場合は、直ちに拒否します。 それ以外の場合は、読み取り専用カウンターをインクリメントし、参照名から変数へのマッピングを保存します。 
4. 書き込み可能な参照を作成するときは、ターゲット変数が存在することを再度確認します。 次に、読み取り専用の参照がすでに存在するか、または既存の書き込み可能な参照が存在するかを確認します。 どちらかが存在する場合、その操作は独占性に違反するため、拒否されます。 それ以外の場合は、この変数に書き込み可能な参照があることをマークし、マッピングを保存します。 
5. 名前を削除するときは、それが変数であるか参照であるかを確認します。 それが参照である場合、それが指す変数を取得し、適切なカウンターをデクリメントします。 変数の場合は、非アクティブとしてマークされます。 今後それを参照すると失敗します。 

実装上の重要な決定は、変数を削除するときにすべての依存参照を「クリーンアップ」しようとしないことです。 代わりに、これらの参照を含む将来の操作によって、ターゲットがアクティブでなくなったことを検出するという事実に依存します。 

### なぜ効果があるのか

各変数は、任意の数の読み取り専用参照によって読み取られているか、書き込み可能な参照によって排他的に所有されているかなど、外部制約の正確な概要を常に維持します。 これらの概要は、運用によって定義された法的移行を通じてのみ更新されます。 

すべての制約違反はこれらの要約のみに依存し、個々の参照の ID には依存しないため、すべての参照をカウンターに折りたたむことで正確さが維持されます。 不変条件は、カウンターが常にアクティブな参照の現在のセットを正確に表し、すべての操作がこの不変条件を保持するか、すぐに拒否されるかのいずれかであるということです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())

        is_var = {}
        is_ref = {}
        ref_to_var = {}

        read_cnt = {}
        has_write = {}

        ok = True

        for _ in range(n):
            if not ok:
                input()
                continue

            parts = input().split()
            tp = int(parts[0])

            if tp == 1:
                a = parts[1]
                is_var[a] = True
                read_cnt[a] = 0
                has_write[a] = False

            elif tp == 2:
                b, a = parts[1], parts[2]

                if a not in is_var or not is_var[a]:
                    ok = False
                    continue

                if has_write.get(a, False):
                    ok = False
                    continue

                is_ref[b] = True
                ref_to_var[b] = a
                read_cnt[a] = read_cnt.get(a, 0) + 1

            elif tp == 3:
                b, a = parts[1], parts[2]

                if a not in is_var or not is_var[a]:
                    ok = False
                    continue

                if has_write.get(a, False) or read_cnt.get(a, 0) > 0:
                    ok = False
                    continue

                is_ref[b] = True
                ref_to_var[b] = a
                has_write[a] = True

            else:
                a = parts[1]

                if a in is_ref:
                    v = ref_to_var[a]
                    if a in ref_to_var:
                        if has_write.get(v, False):
                            has_write[v] = False
                        else:
                            read_cnt[v] -= 1

                    del is_ref[a]
                    if a in ref_to_var:
                        del ref_to_var[a]

                elif a in is_var:
                    is_var[a] = False

                else:
                    ok = False

        out.append("Yes" if ok else "No")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装では、変数と参照が明示的に分離されます。 変数が追跡されるのは、`is_var`、参照はに保存されます。`is_ref`。 マッピング`ref_to_var`参照が削除されたときにどの変数が影響を受けるかを解決するために不可欠です。 

2 つの制約トラッカー、`read_cnt`そして`has_write`、すべてのアクティブな参照の圧縮表現です。 それらは、正しさを強制するために必要な唯一の状態です。 

微妙な点は削除処理です。参照を削除するときは、まずそれが読み取りまたは書き込みとして貢献していたかを判断する必要があります。 そのため、変数の現在の書き込みフラグをチェックし、それに応じてカウンターを調整します。 

設定によっても失敗を伝播します。`ok = False`これにより、不必要な処理が回避されますが、入力消費量の一貫性が維持されます。

 ## 特殊なケース

 厄介なケースは、参照がまだ存在している間に変数が削除された場合です。 アルゴリズムはそれらをすぐに消去しようとはしません。 代わりに、これらの参照は記録されたままになりますが、論理的には無効になります。`is_var[a]`偽になります。 これらが関与する今後の操作は失敗し、安全性が正しく確保されます。 

書き込み可能な参照が削除され、読み取り専用の参照が再度追加される場合にも、別のエッジ ケースが発生します。 カウンタは、読み取り専用状態に正しく移行できることを保証します。`has_write`削除するとクリアされ、`read_cnt`が唯一のアクティブな制約になります。 

最小限の例:```

5

3 b a
4 b

4 a
```削除後`b`にすると、変数は再び書き込み可能になります。 最終的な削除は、`a`すべての有効期限を終了します。 すべての変更が変数ごとのカウンターに即座に反映されるため、アルゴリズムはすべての状態をきれいに遷移します。 

これにより、状態圧縮によって将来の正当性チェックに必要な情報が失われないことが確認されます。
