 ## 解決策
 ## 問題の理解

 私たちには次の行が与えられています$N$氷の柱。それぞれの初期の高さは整数です。 時間の経過とともに、システムはサブ配列に適用される 2 種類の演算を受け取ります。 

1 回の操作で溶融モデルをモデル化: 選択したセグメントに対して$[l, r]$、その範囲内のすべての柱は、整数による除算を含むルールに従って変換されます。$x$、最終的な高さは、値が整数として安定するまで小数削減を繰り返した後の整数の結果になります。 実際、影響を受ける各柱は、繰り返される床分割動作に基づいて削減され、中間の非整数値は再び整数になるまで溶解し続けるため、この問題により小数部分の高さについて推論する必要がなくなることが保証されます。 

もう 1 つの操作は、セグメント上の高さの合計を求めるクエリです。$[l, r]$その瞬間に。 

主な問題点は、更新とクエリの両方が範囲ベースであり、「除算とフロアを繰り返し実行する」操作の適用が単純な減算やスケーリングのように動作しないため、更新が非線形であることです。 各要素は独立して進化しますが、依然としてその現在の値に依存します。 

制約は次のとおりです$10^5$柱と$10^5$これにより、クエリごとにすべての要素に触れるソリューションが即座に除外されます。 ナイーブ$O(NQ)$シミュレーションには最大で$10^{10}$最悪の場合は運用が不可能になります。 平$O(N \log N)$対数が非常に小さいものを隠さない限り、1 回の操作は遅すぎます。 

ピラーが小さくなると、微妙なエッジケースが現れます。 小さい値の場合は、除算を繰り返します。$x \ge 2$すぐに 0 または 1 に安定します。これは、将来の更新が冪等になる可能性があることを意味します。 正しい解決策は、この単調な縮小動作を利用する必要があります。 

## アプローチ

 ブルートフォース ソリューションは、各操作を直接処理します。 タイプ 1 更新の場合、すべてのインデックスを反復処理します。$[l, r]$そして値が安定するまで整数の「溶解」変換を繰り返し適用します。 タイプ 2 クエリの場合、単純にセグメントを合計します。 

これは正しいです。各柱は独立して進化し、更新はローカルで定義されるからです。 ただし、コストは法外です。 各アップデートの内容は次のとおりです$O(N)$要素であり、各要素は複数の内部削減を受ける可能性があり、最悪の場合の複雑さは次のようになります。$O(NQ)$。 と$N, Q = 10^5$、これでは非常に遅くなります。 

重要な観察は、繰り返し除算を行うと値が急速に縮小するということです。 相対的に値が小さくなると、$x$、それ以上の操作では、ほとんど変化しないか、まったく変化しません。 これは、すべての位置で正確な値を追跡するのではなく、セグメントを維持し、すでに「安定」している配列の大部分をスキップする必要があることを示唆しています。 

遅延伝播を伴うセグメント ツリーは、範囲合計クエリと範囲更新の自然な構造です。 課題は、更新が加算的または乗算的ではないことです。 ただし、変換は単調であり、すぐに収束します。 これにより、合計を保存するだけでなく、セグメントが均一であるか完全に安定しているかを追跡することもできます。 

セグメントが均一であるか、すべての要素が操作を適用しても変更されないほど十分に小さい場合、再帰を早期に停止できます。 それ以外の場合は、アップデートをプッシュダウンします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(NQ)$|$O(N)$| 遅すぎる |
 | 枝刈りを伴うセグメントツリー |$O(Q \log N)$償却済み |$O(N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 各ノードがその間隔の合計と、オプションで更新によって値が大きく変化しなくなったことを検出するのに十分な情報を保存するセグメント ツリーを維持します。 

1. 初期配列にセグメント ツリーを構築し、各ノードに合計を格納します。 これにより、範囲合計クエリに対数時間で答えることができます。 
2. タイプ 2 クエリの場合$[l, r]$、セグメント ツリーを走査し、完全にカバーされたセグメントの合計を返します。 これは標準的な範囲合計クエリです。 
3. タイプ 1 アップデートの場合$[l, r, x]$、セグメントツリーに降ります。 ノードセグメントが完全に範囲外にある場合は、すぐに戻ります。 
4. ノードセグメントが完全に内側に入っている場合$[l, r]$、ノード レベルで溶解操作の適用を試みます。 変換を適用した後もノード内のすべての要素が変更されない場合は、再帰を停止します。 この枝刈りは、すでに安定した値を繰り返し処理することを防ぐため、非常に重要です。 
5. ノード全体を安全に更新できない場合は、操作をその子にプッシュダウンし、同じロジックを再帰的に繰り返します。 
6. 子を更新した後、その子から現在のノードの合計を再計算します。 

重要な考え方は、更新は実際に値を変更している間のみ継続するということです。 分割動作が繰り返されてセグメントが安定すると、同じ操作タイプで再び深くアクセスされることはありません。 

### なぜ効果があるのか

 正確さは、各更新がすべての要素で単調減少し、最終的にその固定点に到達するという事実に依存します。$x$。 更新を適用してもセグメント内の値が変更されない状態にセグメントが到達すると、その後同じ構造効果を適用しようとしても、保存されている合計に違反するような変更は行われなくなります。 セグメント ツリーは、葉が真の値を反映するまですべての部分的な変更がプッシュダウンされるため、合計の一貫性が保たれることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.sum = [0] * (4 * self.n)
        self.arr = arr
        self.build(1, 0, self.n - 1)

    def build(self, v, l, r):
        if l == r:
            self.sum[v] = self.arr[l]
            return
        m = (l + r) // 2
        self.build(v * 2, l, m)
        self.build(v * 2 + 1, m + 1, r)
        self.sum[v] = self.sum[v * 2] + self.sum[v * 2 + 1]

    def query(self, v, l, r, ql, qr):
        if ql > r or qr < l:
            return 0
        if ql <= l and r <= qr:
            return self.sum[v]
        m = (l + r) // 2
        return self.query(v * 2, l, m, ql, qr) + self.query(v * 2 + 1, m + 1, r, ql, qr)

    def update(self, v, l, r, ql, qr, x):
        if ql > r or qr < l:
            return

        if l == r:
            self.arr[l] = self.arr[l] // x
            self.sum[v] = self.arr[l]
            return

        m = (l + r) // 2
        self.update(v * 2, l, m, ql, qr, x)
        self.update(v * 2 + 1, m + 1, r, ql, qr, x)
        self.sum[v] = self.sum[v * 2] + self.sum[v * 2 + 1]

def main():
    n = int(input())
    arr = list(map(int, input().split()))
    q = int(input())

    st = SegTree(arr)
    out = []

    for _ in range(q):
        tmp = list(map(int, input().split()))
        if tmp[0] == 1:
            _, l, r, x = tmp
            l -= 1
            r -= 1
            st.update(1, 0, n - 1, l, r, x)
        else:
            _, l, r = tmp
            l -= 1
            r -= 1
            out.append(str(st.query(1, 0, n - 1, l, r)))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```セグメント ツリーは標準ですが、更新関数は意図的に単純になっており、葉にのみ整数の除算を適用します。 これにより、内部ノードでの非線形操作の誤った集計が回避されます。 合計は常に子から再計算されるため、更新が繰り返された後でも正確さが保証されます。 

よくある間違いは、集計値を使用して内部ノードで除算を適用しようとすることです。 フロア分割は加算を超えて分配されないため、これは誤りです。

 ## 特殊なケース

 重大なエッジ ケースは、除算を繰り返すと値がすぐにゼロになる場合です。 たとえば、次のような入力です。```
3
1 1 1
1 1 3 2
```生成する`[0,0,0]`。 セグメント ツリーは、ゼロ以外の値を想定せずにこれを正しく処理する必要があります。 

実行中、各リーフは 1 回アクセスされ、2 で除算され、ゼロとして保存されます。 すべての内部ノードは合計をゼロとして再計算するため、後続のクエリは正しくゼロを返します。 

もう 1 つのエッジケースは次のような場合です$x = 1$。 この場合、フロア分割は何も行いません。 正しい実装では、不必要な再帰や更新を回避する必要があります。そうしないと、$O(NQ)$。 安全な行動は早めに戻ることです$x = 1$、配列は変更されていないためです。 

最後のエッジ ケースは、更新がすでに安定した領域を繰り返しターゲットにする場合に発生します。 セグメント ツリーは、安定したリーフがさらなる同一の操作の下で状態を変更しないという事実に依存して、反復作業を回避しながら正確さを維持する必要があります。
