 ## 解決策

 ## 問題の理解

 直線上に配置された一連のポジションが与えられますが、各ポジションにはプラットフォームが含まれる場合と含まれない場合があります。 プレイヤーは左端の位置から開始し、右端の位置に到達したいと考えます。 プレイヤーは右方向にのみ移動でき、現在の位置から前方にジャンプすることはできますが、固定された最大距離までしか移動できません。 

おもしろいのは、プレーヤーがすべての位置に着地する必要がないことです。 プラットフォームを含む位置に着地するだけでよく、すべてのジャンプはプラットフォームに正確に着地する必要があります。 プラットフォームのない位置は、距離の潜在的なギャップとして依然として存在しますが、着地点として事実上使用できません。 

タスクは、有効なジャンプのシーケンスを使用して最初の位置から最後の位置まで移動できるかどうかを判断し、可能であれば、着地点を表すプラットフォーム インデックスのシーケンスを 1 つ構築することです。 

入力は複数のテスト ケースを記述します。 各テスト ケースでは、ポジションの数と最大ジャンプ距離が示され、その後にどのポジションにプラットフォームが含まれているかを示す配列が続きます。 出力では、有効な着陸位置のシーケンスを印刷するか、不可能であることを示す必要があります。 

制約が十分に大きいため、プラットフォーム間のすべてのジャンプの二次シミュレーションは失敗します。 テスト ケースごとに最大 10^5 のポジションがあるため、プラットフォームのすべてのペアをチェックしたり、すべてのジャンプの組み合わせを試行したりするアプローチでは、最悪の場合、およそ 10^10 の操作が必要となり、時間制限内では実行不可能です。 

重要な微妙な点は、プラットフォームがまばらな場合に現れます。 たとえば、位置 1、2、および 100 にプラットフォームが存在し、最大ジャンプが 10 である場合、他の部分に中間プラットフォームが存在しても、位置 100 に到達することは不可能です。 常に最も遠くにある到達可能なプラットフォームにジャンプするという貪欲な選択が必要です。 そうしないと、単純なショートステップ戦略が早期に行き詰まり、誤って失敗と結論付けてしまう可能性があります。 

もう 1 つのエッジ ケースは、最初または最後のポジションにプラットフォームが含まれていない場合です。 このような場合、開始点と終了点は有効な着地点である必要があるため、すぐには解決策は存在しません。 

## アプローチ

 ブルートフォース手法では、各プラットフォームをグラフ内のノードとしてモデル化し、考えられるすべての遷移を試行します。つまり、各プラットフォームから距離 k 以内の後のすべてのプラットフォームにジャンプすることを試みます。 これにより、ジャンプ範囲内の任意の 2 つのプラットフォーム間にエッジが存在する有向非巡回グラフが効果的に構築されます。 次に、BFS または DFS を使用して、最初のプラットフォームから最後のプラットフォームまでのパスが検索されます。 

すべての有効な遷移を調査するため、正確性は簡単です。 ただし、エッジの数はプラットフォームの数の 2 次になる可能性があります。 n 個のプラットフォームが密にクラスター化されている場合、各プラットフォームは O(n) 個の他のプラットフォームに接続し、O(n^2) 個のエッジが生成される可能性があります。 このグラフを構築するだけでもメモリ制限を超えており、グラフを移動するのが遅すぎます。 

重要な観察は、特定のポイントから到達可能なすべてのプラットフォームを明示的に考慮する必要がないということです。 代わりに、各ステップで最も遠くに到達可能なプラットフォームのみを考慮します。 現在の位置と到達可能な最も遠いプラットフォームの間のすべてのプラットフォームは実現可能性の点で同等であるため (残りの範囲が減少するだけです)、常に最も遠い到達可能な有効なプラットフォームを選択することで、ジャンプの数を最小限に抑えながら到達可能性が維持されます。 

これにより、問題は貪欲スキャンに変わります。つまり、現在のプラットフォームへのポインターを維持し、距離 k 以内の最も遠いプラットフォームに繰り返し進みます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) | O(n^2) | 遅すぎる |
 | 最適な貪欲さ | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. プラットフォームが存在するすべてのインデックスを抽出し、リストに保存します。 これにより、問題は有効な着地点でのみ機能するように圧縮されます。 
2. 最初の位置にプラットフォームが含まれているかどうかを確認します。 そうしないと旅が始まらないので、即答は不可能です。 
3. 最初のプラットフォーム インデックスでポインタを初期化し、それを使用してパスの構築を開始します。 
4. 現在のプラットフォームから、プラットフォーム リストを前方にスキャンし、現在のプラットフォームからの距離が k 以下であるすべてのプラットフォームを特定します。 
5. これらの到達可能なプラットフォームの中で、最も遠いプラットフォームを選択します。 この選択により、進捗が最大化され、中間の選択によってブロックされることがなくなります。 
6. ポインタをこの選択したプラットフォームに移動し、回答パスに追加します。 
7. 最後のプラットフォームに到達するか、それ以上進めなくなるまで、このプロセスを繰り返します。 
8. いずれかのステップで前方プラットフォームに到達できない場合は、終了して出力が不可能になります。 

### なぜ効果があるのか

 正確さは、各ジャンプの後、アルゴリズムが常に現在の実現可能範囲内で最も遠い到達可能なプラットフォームに立つという不変条件に依存します。 有効なソリューションは、同じ到達可能な間隔から次の着地点も選択する必要があります。 より近いプラットフォームを選択すると、その後のジャンプに使用できる前方への残りの距離が減少するため、将来のリーチが制限されるだけであり、決して拡大することはできません。 したがって、解決策が存在する場合、各ステップで貪欲な選択に従う解決策が常に存在し、アルゴリズムが実行可能なパスを排除することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))

        if a[0] == 0 or a[-1] == 0:
            print(-1)
            continue

        # collect platform positions (1-indexed for output clarity)
        pos = [i + 1 for i, v in enumerate(a) if v == 1]

        res = []
        i = 0
        res.append(pos[i])

        possible = True

        while pos[i] != n:
            j = i
            # extend as far as possible within k
            while j + 1 < len(pos) and pos[j + 1] - pos[i] <= k:
                j += 1

            if j == i:
                possible = False
                break

            i = j
            res.append(pos[i])

        if not possible:
            print(-1)
        else:
            print(*res)

if __name__ == "__main__":
    solve()
```コードはまず、入力をフィルタリングして有効なプラットフォーム位置のリストを作成します。 これにより、無効なセルを繰り返しチェックすることが回避され、問題は有効なインデックスに対する単調スキャンに軽減されます。 

ポインタ`i`この圧縮リストで現在のプラットフォームを追跡します。 内側のループが進みます`j`距離の制約がある中で可能な限り遠くまで`pos[j + 1] - pos[i] <= k`が成立する。 これは、最も遠くに到達可能なプラットフォームを選択する貪欲なステップを直接実装します。 

もし`j`が動かない場合、ジャンプ範囲内に前方プラットフォームが存在しないため、即座に失敗が強制されます。

 ## 特殊なケース

 主要なエッジケースは、最初または最後のポジションにプラットフォームがない場合に発生します。 たとえば、入力`1 5 / 0 1 1 1 1`有効な開始点がないため、すぐに失敗します。 アルゴリズムは、処理および出力の前にこれをチェックします。`-1`、無駄な計算を防ぎます。 

別のケースは、プラットフォームが存在するものの、ジャンプ制限をわずかに超えた間隔にある場合に発生します。 例えば、`1 0 0 0 1`と`k = 2`有効な中間着地点がありません。 ポインタは最初のプラットフォームから開始され、内部スキャンで到達可能な次のプラットフォームが見つからず、障害状態がトリガーされます。`j == i`。 

3 番目のケースには、プラットフォームの高密度クラスターが含まれます。 ここでは、アルゴリズムの範囲内に多くの候補がある可能性がありますが、到達可能な最も遠い候補まではステップごとに 1 回だけ進みます。 これにより、最悪の場合の高密度セグメントでも、ポインタはプラットフォームを再度訪問することなく単調に前進し、線形動作が維持されます。
