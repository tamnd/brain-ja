 ## 解決策
 ## 問題の理解

 左から右にインデックスが付けられたニワトリの行が与えられます。 各鶏には容量制限があり、一定数までの穀物しか食べることができません。 これに加えて、いくつかのフィーダーがあり、各フィーダーは鶏の連続したセグメントをカバーし、一定数の穀物が含まれています。 

工夫は、鶏ごとにフィーダーをフィルタリングする方法にあります。 固定チキンインデックスの場合$i$、セグメントに含まれるフィーダのみを保持します。$i$。 他のすべてのフィーダーは完全に無視されます。 残りのフィーダーのうち、合計で何粒の穀物を使用できるかを検討しますが、それでも各鶏が自身の容量を超えることはできません。 

したがって、すべての鶏について$i$、フィーダーだけがカバーする世界を想像します。$i$存在する。 その世界では、これらの飼料供給者が提供する穀物の総数が必要ですが、鶏あたりの生産能力の制限によって制限されます。 

出力は次のリストです。$n$値 (鶏ごとに 1 つ)。このフィルタリング ルールの下でその鶏に使用可能な穀物の合計を記述します。 

制約が非常に厳しいため、ニワトリとフィーダーに対する二次アプローチでは遅すぎるでしょう。 と$n, m \le 10^5$テスト ケースごと、およびテスト全体で制限された総和では、どのソリューションも線形または$O((n + m)\log n)$。 すべてのフィーダーに対する単純な鶏ごとのスキャンでは、最大で次のような結果が得られます。$10^{10}$最悪の場合は運用が不可能になります。 

オーバーラップ動作から微妙な点が生じます。 フィーダーは複数の鶏に貢献しますが、フィーダーが含まれるかどうかは各鶏ごとに個別に決定されます。 これは、フィーダの貢献が「ローカルにグローバル」であることを意味します。つまり、インデックスがそのセグメント内に存在するかどうかのみに依存します。 

単純な間違いは、各ニワトリの合計を最初から再計算する必要があると想定することです。 もう 1 つの間違いは、あるインデックスで除外されたフィーダーが近くのインデックスに含まれている可能性があるため、フィーダーをグローバルに事前に削除できないことを忘れていることです。 

## アプローチ

 強引な解決策で問題を解決する$i$次に、すべてのフィーダーを反復処理して合計します。$c_j$間隔が空いている人のために$[l_j, r_j]$含まれています$i$。 これはルールに直接従うため、正しいです。 ただし、各クエリにはコストがかかります$O(m)$、そしてこれを全員のために行う$n$鶏が導くのは$O(nm)$に達する$10^{10}$最悪の場合の運用。 

重要な観察は、固定されたニワトリの場合です。$i$、フィーダーは次の場合にのみ貢献します。$l_j \le i \le r_j$。 これを次のように書き直すことができます: すべてのフィーダーがアクティブになります$i$まさにその間隔をカバーするものです$i$。 したがって、各フィーダーはその重みをインデックスの連続範囲に寄与します。$l_j$に$r_j$。 これは、古典的な「範囲の追加、ポイントのクエリ」の構造です。 

毎回再計算するのではなく、$i$、視点を逆転させます。 各フィーダーは追加します$c_j$その間隔内のすべてのインデックスに適用されます。 したがって、すべての位置について計算したいと考えます。$i$、すべての合計$c_j$それを覆うオーバーフィーダー。 これは、差分配列またはプレフィックス合計の累積問題になります。 

この総適用範囲合計の基本配列を計算したら、鶏肉の容量を考慮する必要があります。 各鶏はこれ以上の量を食べることはできません$a_i$したがって、最終的な答えは単純です。$\min(a_i, \text{coverage}[i])$。 

これにより、問題は差分配列上の 2 つの線形パスに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | お(1) | 遅すぎる |
 | 最適 (差分配列) | O(n + m) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべてのフィーダーを範囲追加として適用した場合に、各位置で利用可能な粒子の数を計算し、容量によってクランプします。 

1. 配列を初期化する`diff`サイズの$n+2$ゼロ付き。 この配列は、範囲の更新を圧縮形式で保存します。 このアイデアは、範囲内のすべての位置を更新する代わりに、寄与の開始位置と終了位置をマークするというものです。 
2. フィーダごとに$(l_j, r_j, c_j)$、 追加$c_j$で`diff[l_j]`そして引きます$c_j$で`diff[r_j + 1]`。 これは、コントリビューションが次の間でのみアクティブであることをエンコードします。$l_j$そして$r_j$。 減算により、範囲が終了した後に効果が確実に停止します。 
3. プレフィックスの合計を計算します`diff`実際のカバレッジ配列を回復するには`cover[i]`。 各インデックスで$i$、`cover[i]`その時点でのすべてのアクティブなフィーダの寄与の合計に等しくなります。 これが機能するのは、範囲の更新ごとに開始時に +c が寄与し、終了後に -c が寄与するためです。そのため、プレフィックスの累積により正しいオーバーラップ合計が再構築されます。 
4. 鶏ごとに$i$、最終的な答えを次のように計算します。$\min(a_i, cover[i])$。 これにより、チキンごとの容量制限が強制されます。 
5. テスト ケースのすべての回答を出力します。 

### なぜ効果があるのか

 各フィーダーが貢献します$c_j$その区間内のインデックスに正確に変換します。 差分配列により、プレフィックス合計中にそのようなすべての間隔が正確に 1 回カウントされることが保証されます。 インターバル終了後にすべての加算に一致するキャンセルがあるため、貢献が失われたり二重にカウントされることはありません。 結果の位置でのプレフィックスの合計$i$カバーするすべてのフィーダーの合計に等しい$i$、これはまさに容量制限を適用する前に必要な量です。 容量はインデックスごとに独立しているため、クランプが他の位置の正確さを妨げることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        a = list(map(int, input().split()))

        diff = [0] * (n + 2)

        for _ in range(m):
            l, r, c = map(int, input().split())
            diff[l] += c
            diff[r + 1] -= c

        cur = 0
        res = [0] * n

        for i in range(1, n + 1):
            cur += diff[i]
            res[i - 1] = min(a[i - 1], cur)

        print(*res)

if __name__ == "__main__":
    solve()
```実装はアルゴリズムを正確に反映しています。 の`diff`配列のサイズが指定されている$n+2$安全に取り扱うために$r+1$無制限のチェックを更新します。 プレフィックス累積変数`cur`プレフィックス合計を繰り返し再計算することを回避します。 各位置は 1 回処理されるため、テスト ケースごとの線形パフォーマンスが保証されます。 

よくある落とし穴は、インデックス付けが入力では 1 から始まりますが、Python 配列では 0 から始まることを忘れていることです。 このソリューションは、書き込み時にのみ一貫して移行します。`res`、維持`diff`わかりやすくするために、1 から始まるロジックに合わせています。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    out_lines = []
    for _ in range(t):
        n, m = map(int, input().split())

 ## 特殊なケース

 単一のフィーダーを備えた最小の単一鶏のケースでは、r+1 の減算が配列の境界を破るかどうかをテストします。 入力用$n=1$、$l=r=1$、更新は次の場所に書き込みます`diff[2]`、配列のサイズが決まっているため、これは有効です$n+2$。 プレフィックスの合計により正しいカバレッジが生成され、クランプにより最終値が次と等しいことが保証されます。$\min(a_1, c_1)$。 

フィーダがない場合は、プレフィックスの合計がどこでもゼロのままになります。 範囲の更新がアクティブ化されないため、アルゴリズムは容量に関係なく正しくゼロを出力します。 

フィーダの完全にオーバーラップしたセットにより、蓄積の正確性がテストされます。 すべてのインデックスはすべてのフィーダー値の合計を受け取り、最後の min 操作により、非常に大きなオーバーラップであっても位置ごとに独立してキャップされ、インデックスごとの独立性が維持されることが確認されます。
