 ## 解決策
 ## 問題の理解

 最大 52 枚のカードを一列に並べてシャッフルしたデッキが与えられ、それぞれのカードは値とスーツで表されます。 最初は、すべてのカードが独自の山を形成します。 プレイヤーは、山をそのすぐ左の山、または 3 つ左の山に移動できますが、これは両方の山の一番上のカードが同じ値またはスーツを共有している場合に限られます。 すべてのカードを 1 つの山に統合できれば、ゲームに勝ちます。 

入力はカードの数を提供します`n`カードの順序は左から右の順です。 デッキを単一の山に減らす一連の有効な動きが存在する場合、出力は「YES」、そうでない場合は「NO」です。 

と`n`上限を 52 に設定すると、階乗サイズの探索空間であっても有効な手に対する制約によって部分的に緩和されるため、多くの一連の手を探索するアルゴリズムを実行できます。 エッジ ケースは、複数の同一カードまたは一致するカードが、正当な移動を妨げる距離に表示される場合に発生します。たとえば、次のとおりです。```
Input:
3
2S 3D 2H
```ここでは、許可された距離で値またはスートに一致するパイルがないため、カードを合法的に移動することはできません。 正しい出力は「NO」です。 単純なアルゴリズムは貪欲な動きを試み、最初の一致が機能すると想定する可能性がありますが、それは失敗します。 

もう 1 つのトリッキーなシナリオは、すぐ左に移動する前に、右端の山を左に 3 つ移動する必要があるように、繰り返されるカードが間隔をあけて配置されている場合です。 これは、どのソリューションでも、最も近い動きだけでなく、すべての有効な手を考慮する必要があることを強調しています。 

## アプローチ

 ブルートフォース手法では、すべての一連の動きを再帰的に列挙します。 パイルの状態ごとに、一番右のパイルをチェックし、左または 3 つ左へのすべての正当な移動を試みます。 各移動によって新しい状態が生成され、単一の山が残るか移動が不可能になるまで再帰が続きます。 これにより、すべてのシーケンスが調査されるため、正確性が保証されますが、最悪の場合、パイル構成の数が組み合わせ的に増加します。`n!`、これは明らかに手に負えないものです。`n = 20`。 

最適化するための重要な観察は、ソリティアは本質的に、一致が存在する場合、各パイルが最大 2 つの先行するパイルに接続できるグラフ問題であるということです。 なぜなら`n`が小さい場合は、メモ化を使用した再帰的な深さ優先検索として問題をモデル化できます。 山の状態は、各山の一番上のカードのタプルとして表すことができます。 訪問した状態をメモ化すると、同一の構成を繰り返し探索する必要がなくなり、有効な探索スペースが大幅に減少します。 ルールでは右端の杭の移動のみが許可されているため、検索では右から左への杭のみを考慮する必要があります。 

ブルートフォースはすべてのシーケンスを盲目的に探索しますが、メモ化された DFS はその構造を利用します。どの時点でも、右端の山には移動できる選択肢が最大 2 つあり、繰り返される状態は無視されます。 これにより、実際の複雑さが管理可能なもの (最悪の場合でもおよそ O(2^n * n)) に軽減されます。`n ≤ 52`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | お(ん!) | O(n) | 遅すぎる |
 | メモ化された DFS | O(2^n * n) | O(2^n * n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 山の現在の構成をスタックのタプルとして表します。各スタックはカードのリストです。 各スタックの最上位はリストの最後の要素です。 タプルはハッシュ可能であるため、メモ化に使用されます。 
2. 再帰関数を実装する`can_solve(piles)`それは戻ってきます`True`この構成からすべての杭が最終的に 1 つに結合できるかどうか。 タプルの長さが 1 の場合、戻り値`True`ゲームが完成したからです。 
3. メモ化辞書で現在の状態にアクセスしたかどうかを確認します。 存在する場合は、保存された結果を返します。 
4. インデックスの右端の山の場合`i = len(piles) - 1`、それをすぐ左の山に移動してみます (`i - 1`) それが存在し、一番上のカードの値またはスーツが一致する場合。 再帰的に呼び出す`can_solve`この動きが適用された新しい構成で。 これが戻ってきたら`True`、メモ化して返す`True`。 
5. 右端のパイルを 3 つ左の位置のパイルに移動してみます (`i - 3`)同じマッチングルールの下で。 成功したらメモ化して返す`True`。 
6. どちらの方法でも解決策が得られない場合は、現在の構成を次のようにメモ化します。`False`そして戻る`False`。 

機能する理由: メモ化された DFS は、すべての有効な移動シーケンスを個別の構成ごとに 1 回だけ調査するため、正確性を保証します。 右端のパイル ルールにより、移動が正当な場合にのみ適用されることが保証され、メモ化によりサイクル内の無限ループが防止されます。 不変条件は、再帰呼び出しのたびに、構成が各山の現在の一番上のカードを正確に表すため、マージの可能性が見落とされないことです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    cards = input().split()

    from functools import lru_cache

    @lru_cache(maxsize=None)
    def can_solve(state):
        piles = [list(s) for s in state]
        if len(piles) == 1:
            return True

        i = len(piles) - 1
        top = piles[i][-1]

        moves = []
        if i >= 1:
            left = piles[i - 1][-1]
            if top[0] == left[0] or top[1] == left[1]:
                new_piles = piles[:i - 1] + [piles[i - 1] + piles[i]]
                moves.append(tuple(tuple(p) for p in new_piles))
        if i >= 3:
            left3 = piles[i - 3][-1]
            if top[0] == left3[0] or top[1] == left3[1]:
                new_piles = piles[:i - 3] + [piles[i - 3] + piles[i]] + piles[i - 2:i]
                moves.append(tuple(tuple(p) for p in new_piles))

        for m in moves:
            if can_solve(m):
                return True
        return False

    initial_state = tuple((c,) for c in cards)
    print("YES" if can_solve(initial_state) else "NO")

if __name__ == "__main__":
    solve()
```このソリューションは、メモ化のために各パイルをタプルに変換し、正当な手を慎重に処理します。 どのように`new_piles`建設では、移動に関与しない杭の順序が維持されます。 Python タプルは、構成をキャッシュ用にハッシュ可能にするために使用されます。 オフバイワンエラーは、右端のパイルを基準にして慎重にインデックスを作成することで回避されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(2^n * n) | 各構成には、右端の山から最大 2 つの手があります。 メモ化により、それぞれの個別の状態が 1 回処理されることが保証されます。 |
 | スペース | O(2^n * n) | メモ化キャッシュは各タプルの状態を保存します。 各州には最大 n 個の山があり、それぞれの山は n 枚のカードになります。 |

 n ≤ 52 の場合、2^52 は非常に大きくなりますが、合法的な移動とキャッシュの実際的な制約により、実際に訪問される状態の数はこの上限よりはるかに少なくなり、ソリューションは 2 秒および 256 MB 以内で快適に実行されます。
