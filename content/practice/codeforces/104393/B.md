 ## 解決策
 ## 問題の理解

 マイクロサービスのコレクションが与えられ、それぞれが初期数のユーザー リクエストを生成します。 これらのリクエストはすべて同一のホスティング マシンによって処理され、各マシンには固定の容量制限があります。 時間の経過とともに、トラフィックは非常に厳格に増加します。毎月、リクエストの総負荷は 2 倍になります。 

倍増ステップ後の総リクエスト負荷が、現在レンタルしているマシンで処理できる量を超えると、システムは追加のマシンをレンタルし、古いインフラストラクチャと新しいインフラストラクチャの間でトラフィックを分割することで対応します。 分割は任意ではなく、常に 2 倍になったトラフィックの半分を取得して既存のセットアップに割り当て、残りの半分を新しくレンタルしたホストに割り当てることによって実行されます。 分割は 1,000 分の 1 への四捨五入を使用して定義されるため、事実上、合計負荷を 2 つのほぼ等しい部分に整数で分割することになります。 

私たちが追跡する重要な数量は、倍増と場合によっては分割が繰り返された所定の月数の後に必要となるホストの数です。 複数のクエリ月にわたって、最大 54 ステップ先の将来まで、これに答えるように求められます。 

入力によりマイクロサービスごとの初期負荷が得られ、これらが合わせて初期の総リクエスト量を形成します。 各クエリは、特定の月数の成長プロセスをシミュレートした後、容量制約の下ですべてのリクエストに対応するために必要なホストの数を尋ねます。 

制約は構造的には小さいですが、成長挙動では大きくなります。 マイクロサービスは最大 1000 個あるため、初期の合計負荷を計算するのは簡単です。 月数は最大でも 54 と非常に小さいため、すべての月の状態を事前計算するソリューションは実行可能です。 重要な問題は、リクエスト値が指数関数的に増加するため、クエリごとに生の値を再計算する必要がなく、クエリごとに個別に実行すると無駄が生じることです。 

素朴な解釈では、各クエリを最初からシミュレートし、値を 2 倍にし、必要に応じて分割を繰り返します。 これにより、54 ステップのプロセスにクエリの数が乗算されますが、それでもわずかです。 単純なアプローチにおける本当のリスクは、時間の複雑さではなく、特に総負荷の総計ではなくマイクロサービスごとの観点から考える場合、分割プロセスのモデリングが間違っていることです。 

初期負荷がちょうど容量に達した場合、微妙なエッジケースが発生します。 単純なアプローチで、厳密に容量を超えた後にのみ分割が行われると想定している場合、ホストの作成が誤って遅れる可能性があります。 もう 1 つの問題は、丸めを誤って解釈することによって発生します。これは、この問題では 1000 分の 1 への丸めが定義されていますが、意図されている構造は単に決定論的な整数の分割であるためです。 これを誤解すると、配布時にオフバイワンエラーが発生する可能性があります。 

## アプローチ

 ブルートフォースの考え方は単純です。リクエストの総数を維持し、現在利用可能なホストの数を維持します。 毎月、負荷を 2 倍にします。 負荷が現在のホストの合計容量を超える場合は、「アクティブ ブロック」ごとの残りの負荷が容量内に収まるまで、ホストの追加と負荷の分割を繰り返します。 

ただし、文字通りホストごとまたはマイクロサービスごとに分割をシミュレートする必要はありません。 重要な観察は、分割イベントが発生するたびに、システムが総負荷を容量によって制限された独立したチャンクに分割したかのように動作し、各チャンクが倍増時に同様に進化することです。 これは、各セグメントがホストに対応するため、負荷の等しい「セグメント」がいくつ存在するかを追跡するだけでよいことを意味します。

総負荷が 2 倍になるたびに、各セグメントも 2 倍になります。 セグメントが容量を超えると、セグメントはほぼ同じサイズの 2 つのセグメントに分割され、そのセグメント系統内の分割イベントごとにホストの数が 1 つずつ増加します。 すべてのセグメントは同じように動作するため、システム全体が決定論的に進化します。各倍増ステップ後にセグメントの負荷を容量以下に保つために必要なホストの数を追跡するだけで済みます。 

これにより、問題は 1 つの代表セグメントにルールを繰り返し適用することになります。つまり、負荷を 2 倍にし、容量を超えると負荷を 2 つに分割し、すべてのセグメントが制約を満たすまで継続します。 

月数は最大 54 であるため、単純な反復シミュレーションを使用して、各月に必要なホストの数を事前計算できます。

 | 毎月の状態を事前計算する | お(54) | お(54) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、すべてのマイクロサービス リクエストを合計して、初期の合計負荷を計算します。 これがシステムの開始点となります。 

次に、ホスト グループごとの現在の実効負荷と必要なホストの数という 2 つの量を維持しながら、月ごとにシミュレーションを行います。 

1. すべてのマイクロサービスの合計として初期合計負荷を計算します。 これは、スケーリングまたは分割前のシステム負荷を表します。 
2. 最初はすべてのトラフィックが単一のホスティング構造によって処理されるため、ホストの数を 1 に初期化します。 
3. 1 から 54 までの月ごとに、現在の負荷を 2 倍にします。 これは問題における成長の仮定をモデル化します。 
4. 2 倍にした後、現在の負荷が容量 C を超えているかどうかを確認します。超えている場合は、複数のホストに負荷を分割する必要があります。 
5. 分割操作ごとにホストの数が 1 つずつ増加し、ホスト グループあたりの実効負荷が半分になります。 ホストごとの負荷が容量内になるまで分割を繰り返します。 これにより、再配布後にホストが過負荷になることがなくなります。 
6. クエリに一定時間内に応答できるように、月ごとにホストの数を保存します。 

重要な不変条件は、i 月の処理後、各ホストに C を超えない負荷が割り当てられ、合計負荷が丸め効果まですべてのホストに均等に分割されることです。 分割は違反した場合に常に実行可能性を回復し、倍増が増加の唯一の源であるため、このプロセスでは、構成が 1 か月間有効になると、その構成が翌月の更新の正しい開始点であり続けることが保証されます。 容量違反が発生したときにすべての分割が正確にトリガーされるため、代替の配布によって必要なホストの数を減らすことはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    C, N, M = map(int, input().split())
    total = 0
    for _ in range(N):
        total += int(input())

    queries = [int(input()) for _ in range(M)]
    max_month = 54

    # hosts[m] = number of hosts needed at month m
    hosts = [0] * (max_month + 1)

    cur_load = total
    cur_hosts = 1

    hosts[0] = 1

    for m in range(1, max_month + 1):
        cur_load *= 2

        # ensure each host has at most C load
        while cur_load > cur_hosts * C:
            cur_hosts += 1

        hosts[m] = cur_hosts

    out = []
    for q in queries:
        out.append(str(hosts[q]))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```スケーリング動作には合計のみが重要であるため、コードはすべてのマイクロサービスの負荷を 1 つの値に集約することから始まります。 その後、シミュレーションは月ごとに進行し、毎回合計負荷が 2 倍になります。 

重要な実装の詳細は条件です。`cur_load > cur_hosts * C`。 これにより、現在の分散が実現可能かどうかがチェックされます。合計容量はホスト数とホストごとの容量の積です。 負荷がこれを超える場合は、実行可能性が回復するまでホストの数を増やします。 各増分は、新しいホストの導入と負荷の再分散に対応します。 

最後に、事前計算された値を使用して各クエリに回答し、再計算を回避します。

    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    total = 0

        total += int(input())

        hosts[m] = cur_hosts

    return "\n".join(str(hosts[q]) for q in queries)

 ## 特殊なケース

 重要なケースの 1 つは、初期負荷が総容量と正確に等しい場合です。 たとえば、C = 1000、単一サービスが 1000 の場合、システムは完全にバランスの取れた状態で開始されます。 月 0 では、答えは 1 ホストです。 1 回 2 倍になると負荷が 2000 になり、容量を超えるため、2 台目のホストが必要になります。 アルゴリズムは厳密な不等式をチェックするため、これを正しく処理します。`cur_load > cur_hosts * C`、平等が依然として有効であることを意味します。 

もう 1 つのケースは、初期負荷が容量を大幅に下回る場合です。 たとえば、合計負荷が 10 の場合、C = 1000 となります。倍増を複数回行った後でも、システムは数か月間容量を下回る状態が続く可能性があります。 ループはしきい値を超えるまで何も行わないため、ホスト数を増やす必要が生じるまでホスト数は安定したままになります。 

3 番目のケースは、倍増の繰り返しにより、1 か月に複数のホストが追加される場合です。 負荷が C の倍数のすぐ下からそれをはるかに上回るまでジャンプした場合、`while`ループにより、1 回の増分ではなく、実行可能性を復元するのに十分なホストを正確に追加できるようになります。
