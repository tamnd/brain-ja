 ## 解決策
 ## 問題の理解

 プレフィックス演算を使用して左から右に配列を構築するプロセスが与えられています。 最初はすべての位置がゼロです。 利用可能な各操作はインデックスに関連付けられています`i`、その操作を実行すると、すべての要素が位置から増加します`1`に`i`いくつかのコインを消費しながら、ちょうど 1 つずつ`c[i]`。 持っている以上のコインを費やさない限り、各操作は何度でも使用できます。 

重要な出力は一連の操作ではなく、最初のコインを最適に消費した後の最終配列です。 実現可能なすべての配列の中で、辞書編集的に最大の配列が必要です。つまり、配列の最大化を優先します。`a1`、 それから`a2`、 等々。 

この制約により、テスト ケースごとに線形または線形に近い動作が求められます。 の合計`n`すべてのテスト ケースにわたる値は最大 2 × 10^5 であるため、テスト ケースごとに O(n log n) よりも悪いソリューションは、繰り返し適用するとタイムアウトになる危険性があります。 これは、各位置を 1 回のパスまたは償却カウントで決定できる、貪欲なソリューションまたはプレフィックス構造のソリューションを強く示唆しています。 

微妙な点は、操作がかなり重複していることです。 インデックスでの操作の使用`i`以前のすべてのポジションに影響を与えるため、`a[j]`で選択されたすべての演算の合計です`i ≥ j`。 この逆依存関係が問題の核心構造です。 

簡単な間違いの 1 つは、ポジションに直接コインを費やすという観点から貪欲に考えることですが、これではプレフィックスの結合が無視されます。 もう 1 つはインデックスを独立して処理する方法ですが、これは無効です。操作は単一のインデックスではなくプレフィックス全体に影響するためです。 

## アプローチ

 ブルートフォースアプローチでは、コインの支出をオペレーション全体に分散するためのあらゆる可能な方法をシミュレートしようとします。 それぞれの操作`i`は複数回選択でき、それぞれの選択がプレフィックスに影響します。 各操作が何回使用されるかを数えてみると、状態空間には制限がなく、コインの価値に応じて増加することがすぐにわかります。 

たとえ利用回数に上限を設けたとしても、`k`、単純な動的アプローチでは、依然としてすべての移行を考慮する必要があります。`n`考えられるコイン支出の決定ごとのインデックス。 最悪の場合、これは指数関数的、または少なくとも O(k · n) になりますが、これは実行不可能です。`k`最大 10^9 まで可能です。 

重要な観察は、辞書編集的な最大化によって以前のインデックスが強く優先されるということです。 増加中`a1`常に他の何よりも重要であり、一度は`a1`固定されているので最大化します`a2`、 等々。 これは、各操作が位置の各接尾辞に何回寄与するかという観点から考える必要があることを示唆しています。 

時間の経過とともにコインを配布するのではなく、視点を逆転させます。 それぞれの操作`i`すべてのポジションに +1 貢献します`1..i`。 したがって、固定位置については、`j`、少なくともインデックスを持つすべての操作`j`に貢献する`a[j]`。 これは、各操作が使用される回数を定義すると、次の値が得られることを意味します。`a[j]`全体の合計です`i ≥ j`。 

ここで重要な単純化: 辞書順では初期のインデックスが優先されるため、インデックスへの寄与を最大化したいと考えています。`a1`、 それから`a2`、 等々。 これは、可能な限り最大のプレフィックスに影響を与える、利用可能な最も安価な操作を繰り返し使用することに相当しますが、操作がどのように重複するかを慎重に考慮します。 

これをモデル化するきれいな方法は、利用可能な最良のコストを維持しながらインデックスを右から左に処理することです。 私たちが位置にいるとき`i`、インデックス ≥ i の操作はいずれも引き続き貢献できます。`a[i]`したがって、そのような最も安価な操作によって、以前のポジションによって引き起こされた予算の制約を考慮した後、このポジションにどれだけの増分を許容できるかが決まります。 

これにより、ランニングコストを最小限に抑え、残余予算を注意深く追跡することで、問題を 1 つのパスに軽減します。

 ## アルゴリズムのチュートリアル

 1. これまでに確認された最良のプレフィックス操作コストを維持しながら、配列を左から右に処理します。 位置で`i`、操作のみ`1..i`影響を与えるために使用できます`a[i]`したがって、次の中で最小コストを追跡します。`c[1..i]`。 この最小コストは、すべてのポジションを最大まで増やすための最も効率的な方法を表します。`i`。 
2. しましょう`best[i]`の中で最小コストとなる`c[1..i]`。 この値は、すべての増分が位置に影響を与えることを示しています。`i`少なくとも費用がかかる必要があります`best[i]`、これまでに確認された最良のインデックスを選択することで、いつでもそのコストを達成できます。 
3.今度は何回の位置を決定しますか`i`世界的な予算を尊重しながら増額可能`k`。 増加するたびに、`a[i]`事実上支出に相当する`best[i]`コイン、ポジションに影響を与える最大増分数`i`以前の決定に違反することなく、`k // best[i]`。 
4. ただし、辞書編集的には前の位置の方が重要であるため、インデックスごとにすべての予算をすぐに貪欲に消費するわけではありません。 代わりに、プロセスを再解釈します。増分レベルを決定するたびに、それが配列のサフィックスに影響します。 これにより、隣接する位置の差を使用して最終的な配列が構築されます。 
5. 配列を維持します`a`ゼロに初期化され、増分の累積をシミュレートします。 から移動するとき`i`に`i+1`、許容コストは同じままか改善することしかできないため、現在の最適コストを更新し、それを使用して現在のプレフィックス レベルに割り当てるべき増分数を決定します。 
6. 最終的な配列は、各位置が確実に一致するように構築されます。`i`あらゆる操作からのすべての増分を受け取ります`j ≥ i`、これはランニングベストコストロジックを使用して累積できます。 

### なぜ効果があるのか

 正確さは、すべての操作がプレフィックスに影響するため、寄与はインデックスの逆順で単調であるという事実に基づいています。 プレフィックスを修正するとき`[1..i]`、それに関連する唯一の操作は、少なくともインデックスを持つ操作です。`i`。 これらの中で、これまでに利用可能な最小コストを使用してあらゆる増分を実現できるため、最も安価な操作が優先されます。 辞書編集順では前の位置が優先されるため、後の位置を改善するために前の位置を犠牲にすることはありません。 実行最小コストにより、プレフィックス増分を拡張するための最も安価な方法が常にモデル化されることが保証され、その構造により、各位置が最も安価な適用可能な操作に含まれる増分の数が正確にカウントされることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        c = list(map(int, input().split()))
        k = int(input())

        best = [0] * n
        best[0] = c[0]
        for i in range(1, n):
            best[i] = min(best[i - 1], c[i])

        a = [0] * n

        # remaining increments we can still "place"
        # think of k as total budget for increments using best costs
        remaining = k

        for i in range(n):
            if remaining <= 0:
                break

            # max increments affecting position i
            take = remaining // best[i]
            a[i] = take

            remaining -= take * best[i]

        # propagate contributions: prefix structure means
        # each a[i] actually contributes to all j <= i,
        # so we convert from difference form to final array
        for i in range(n - 2, -1, -1):
            a[i] = max(a[i], a[i + 1])

        print(*a)

if __name__ == "__main__":
    solve()
```このソリューションでは、まずコスト構造をプレフィックス最小配列に圧縮します。 特定の時点で最も安価なプレフィックスを超える操作は、その時点またはそれ以前の位置での増分を最大化するのに決して最適ではないため、これは不可欠です。 

貪欲な予算消費ステップでは、各プレフィックス レベルで完全な増分を何回支払うことができるかを解釈します。 掛け算`take * best[i]`多くの増分の使用にかかる総コストが適切に差し引かれるようにします。 

最後の逆方向伝播では、プレフィックスに適用される増分は以前の位置にも反映される必要があるため、配列のプレフィックス モノトーン構造が強制されます。

 ## 特殊なケース

 重要なエッジケースの 1 つは、すべてのコストが等しい場合です。 この状況では、すべてのプレフィックス操作は同等に効率的であるため、最適な戦略は、最大のプレフィックス (インデックス 1) に影響を与える操作にすべてのコインを集中させます。プレフィックスの最小配列は一定のままであり、すべてのバジェットが最も早いインデックスで消費されるため、アルゴリズムはこれを自然に処理します。 

コストが厳密に削減される場合、別のエッジケースが発生します。 ここで、後のインデックスは常に安価ですが、小さなプレフィックスに影響を与えます。 プレフィックスの最小値により、より安価な操作が出現すると、以前のすべてのポジションがそのコストを継承し、増分が割り当てられる場所を正しくシフトすることが保証されます。 

最後の微妙なケースは次のような場合です。`k`非常に大きいです。 アルゴリズムはコイン単位ごとにループすることはありません。 コストで除算するだけなので、10^9 までの値でもオーバーフローやパフォーマンス低下のリスクなく安全に処理されます。
