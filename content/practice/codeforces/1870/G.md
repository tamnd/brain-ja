 ## 解決策
 ## 問題の理解

 配列が与えられ、そのプレフィックスを 1 つずつ調べます。 各プレフィックスについて、それを整数のマルチセットとして扱い、非常に珍しい操作を繰り返し実行することを想像します。つまり、空ではないサブマルチセットを選択し、それを削除し、その MEX を計算し、その MEX を挿入し直します。 これを任意に何度でも繰り返すことができます。 最終的には、数字が 1 つだけ残る状況に追い込まれ、この最後の数字が取り得る最大値を知りたいと考えます。 

主な難点は、この操作ではサイズが保持されず、小さな数値が破棄されたり作成されたりする可能性があることです。 サブセットを自由に選択できるため、プロセスは決定論的ではなく、考えられるすべての操作シーケンスにわたって最適化しています。 

各接頭辞は独立して同じ質問をします。最初の i 要素が与えられた場合、達成可能な最終的な最大値はいくらですか。 

制約は厳しく、テスト ケース全体の長さは 2e5 であるため、テストごとに本質的に線形または線形に近い動作が必要です。 操作のシミュレーションやサブセットの推論を明示的に行うことは、直ちに不可能になります。 

素朴な間違いは、貪欲なローカル MEX 動作で十分であると想定することです。 たとえば、常にすべてを結合する、または常に最小限の欠損値を個別に抽出すると考えると失敗します。これは、操作がステップ間で非自明な方法で相互作用する可能性があるためです。 

さらに微妙な落とし穴は、答えが最大プレフィックス MEX または最大要素だけであると仮定することです。 小さな例では、両方の直観がすでに打ち破られています。MEX 演算は、最初に存在していた値よりも大きな新しい値を生成できると同時に、小さな数値の重複を消費する繰り返しの再構成も可能にします。 

## アプローチ

 ブルート フォース解釈では、到達可能なすべてのマルチセット、またはサブセット削除のすべての可能なシーケンスをシミュレートしようとします。 状態を周波数ベクトルとしてエンコードした場合でも、各操作では任意のサブセットを選択でき、サブセットの数はプレフィックスのサイズで指数関数的に増加します。 分岐係数は実質的に 1 ステップあたり 2^n であるため、これは n = 30 の場合でも完全に実行不可能です。 

重要な構造的洞察は、任意のサブセットの観点から考えるのをやめ、代わりに MEX 変換を繰り返すことで最終的にどのような値が生成されるかを理解することです。 

この操作では基本的に、一連の値を単一の MEX 値と「交換」できます。 重要な点は、小さな整数の有無のみが重要であるということです。 十分な数値のコピーがあれば、制御された方法で 0、1、2、... の出現を繰り返し消費できます。 

変換は、すべての小さな整数が十分に「供給」されている限り、新しい整数を生成できるシステムのように動作します。 最終結果として値 x を生成するには、プロセス中のある時点で 0 から x-1 までのすべての整数を作成できなければなりません。 これは、問題が、欠損値の「連鎖」を何回完了できるかを追跡することに帰着することを示唆しています。 

プロセスを表示する便利な方法は、新しい数値を生成するたびに、一連の操作にわたって少なくとも 1 回、すべての小さい数値の出現を「消費」する必要があるということです。 これは、貪欲な蓄積条件につながります。つまり、カウントを追跡し、0、1、2、... の完全なレイヤーをいくつ維持できるかを決定します。 

操作をシミュレートする代わりに、周波数を維持し、プレフィックスが完全な連続構造をどの程度サポートできるかを段階的に計算します。 各プレフィックスは利用可能な供給量を拡張し、到達可能な連続セグメントを拡張できる場合にのみ、答えは大きくなります。 

これにより、問題は、オンラインで更新できる完全な「MEX 構造」をいくつ維持できるかということになります。

 ## アルゴリズムのチュートリアル

 頻度カウントと、構造化された意味で「利用可能」であることをすでに保証できる連続した小さな整数の数を記述するポインターを維持しながら、配列を左から右に処理します。 

1. 周波数配列を維持する`cnt[x]`これまでに確認された値について。 これにより、現在各整数の供給が十分であるかどうかがわかります。 
2. 変数を維持する`need`、最小の整数を表すため、MEX 構築の意味でこの整数まで構築することはまだ完全にサポートできません。 最初は`need = 0`。 
3. 新しい要素をそれぞれ読んだ後`a[i]`、その頻度を増やします。 
4. 前進しようとする`need`可能な限り:その間に`cnt[need] > 0`、次の 1 つの発生を治療できます。`need`より大きな値の構築を可能にする完全な「チェーン」の一部として、インクリメントします。`need`。 

その理由は、以下のすべての整数が存在する限り、`need`使用可能な方法で少なくとも 1 回出現した場合、より高い値をロック解除する MEX レイヤーを構築するプロセスをシミュレートできます。 
5. 現在のプレフィックスの答えは次のとおりです。`need`。 

この貪欲な拡張は、繰り返しの MEX 操作で「消費」できる整数の最大連続セグメントを取得します。そのセグメントの長さが、構築できる最終値の大きさを正確に決定します。 

### なぜ効果があるのか

 重要な不変条件は、プレフィックスを処理した後、すべての整数が`[0, need-1]`何らかの一連の操作を通じて生成可能であることが保証されていますが、`need`はまだ完全にはサポートされていません。 

私たちが新たな出来事を観察するたびに、`need`の障害物を除去します。`need`これは、必要な一連の小規模な MEX 構築ステップの完了に貢献するためです。 MEX は常に欠落している最小値のみに依存するため、プロセスは最初の欠落している整数境界を拡張するように線形化できます。 最初にすべての小さい値を入力しない限り、どの操作もこの境界をスキップすることはできません。`need`単調に進み、真の達成可能な最終値をオーバーシュートすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    MAXV = 200000 + 5

    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        cnt = [0] * (n + 5)
        need = 0
        res = []

        for x in a:
            if x < len(cnt):
                cnt[x] += 1

            while need < len(cnt) and cnt[need] > 0:
                need += 1

            res.append(str(need))

        print(" ".join(res))

if __name__ == "__main__":
    solve()
```このコードは、プレフィックスの頻度テーブルと単一のポインターを維持します。`need`まだ「完全にサポートされていない」最小の整数を追跡します。 挿入のたびに、可能な限りこのポインタを貪欲に進めます。 各プレフィックスの後の結果は、まさにこのポインターです。 

微妙な点としては、`need`決して減少しないため、実行全体にわたるすべての while ループの合計コストは、最大値の範囲内で線形になります。

## 特殊なケース

 One important edge case is when the array contains only large numbers. この場合、小さな整数は決して現れないので、`need`すべてのプレフィックスで 0 のままであり、MEX ベースの構築を開始できないという事実と一致します。 

もう 1 つのケースは、ゼロが繰り返されることです。 素朴な解釈では、複数のゼロが役立つと考えるかもしれませんが、構築境界を進めるには各整数の存在のみが重要です。 

最後の微妙なケースは、値が遅く表示される場合です。 たとえば、いくつかの大きな数字の後に 0 が現れると、突然プロセスが開始されます。`need`十分な連続値が存在すると、それに応じてジャンプします。
