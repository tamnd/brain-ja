 ## 解決策
 ## 問題の理解

 すべてのセルが最初はゼロを保持しているという意味で、完全に空から始まる長方形のグリッドを使用しています。 次に、一連の操作を実行します。 各操作では、行全体または列全体が選択され、その行のすべてのセルが指定された値で上書きされます。 

重要な点は、上書きは破壊的であるということです。 行に何らかの値が設定されると、列操作によって以前に書き込まれた可能性のある値を含め、その行内の以前の情報はすべて消去されます。 同様に、列を上書きすると、その列に以前に書き込まれた内容が消去されます。 すべての操作が順番に適用された後、現在グリッドに格納されているすべての値の合計が求められます。 

直接解釈すると、行全体または列全体を繰り返し更新することが示唆されますが、グリッドは非常に大きくなる可能性があります。 テストごとに最大 5e5 行と列、および最大 5e5 操作を行うと、操作ごとに個々のセルにアクセスするソリューションはすぐに失敗します。 行全体または列全体を明示的にタッチした場合でも、O(n) または O(m) のコストがかかる可能性があり、最悪の場合は 2 次の動作が発生します。 

主な問題点は、各操作が将来および過去の操作と相互作用することです。 後の行の割り当ては、交差するセルに対する以前の列の割り当てをオーバーライドします。また、その逆も同様です。 セルの最終値は、その行または列に影響を与える最新の操作によってのみ決定されます。 

いくつかの特殊なケースでは、よくある間違いが明らかになります。 すべての操作が列の更新である場合、列の寄与を個別に合計できると誤って仮定する可能性がありますが、後で初期化された行が以前の行を上書きする可能性があります。 たとえば、2x2 グリッドの場合、次の操作が行われます。`C 1 5`、`F 1 2`、最後のグリッドは`[[2,2],[0,5]]`、添加物ではありません。 

もう 1 つの落とし穴は、可換性を仮定することです。 セルの最終値はその行と列の間の最新の操作に依存するため、順序が非常に重要になります。 

最後に、行と列のタイムスタンプ間の相互作用を無視すると、過大なカウントが発生します。単純な解決策では、行の値と列の値の両方が同じセルに適用される可能性があります。 

## アプローチ

 ブルート フォース シミュレーションでは、グリッドが明示的に保持されます。 操作ごとに、選択した行または列のすべてのセルを上書きします。 各更新には O(n) または O(m) のコストがかかり、q 回の操作で総コストは O(q・max(n,m)) になります。 最悪の場合、寸法と q の両方が 5e5 である場合、これは実現可能な限界をはるかに超えています。 

グリッドを保存して影響を受ける部分のみを再計算することによって最適化しても、上書きするたびに線形の数のセルが影響を受けるため、役に立ちません。 

重要な点は、行または列に影響を与える最後の操作のみが値の決定に重要であるということです。 時刻 t で行が値 x で上書きされると、古い行操作はその行に対して無関係になります。 同じことが列にも当てはまります。 ただし、セルは、最新の行操作と最新の列操作の相互作用の影響を受けます。 

これは、各行について、その最終更新日時とその値を追跡し、同様に各列についても追跡することを示唆しています。 次に、グリッドを再計算する代わりに、操作ごとに、最終的な合計にどの程度の寄与が追加されるかを推論します。 

操作を逆の順序で処理します。 操作を処理する時点で、それ以降のすべての操作はすでに修正されており、残りの未設定の行または列に対しては「最終」とみなされます。 後の操作の観点から、まだ「割り当てられていない」行と列の数のカウントを維持します。 行操作が発生すると、その値に、後の列操作でまだ固定されていない列の数を乗算した値が与えられます。 対称的に、列演算は、後の行演算によってまだ固定されていない行数を乗算した値を提供します。 行または列が逆に処理されると、完了としてマークされ、以前の操作ですでにカバーされているセルが二重にカウントされないようにします。 

この逆転により、グローバルな依存関係の問題が、各ステップでまだ「空いている」行または列の数に関する単純な簿記タスクに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(q・(n+m)) | O(nm) | 遅すぎる |
 | 逆処理 | O(n + m + q) | O(n + m + q) | 承認済み |

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。 

1. すべての操作を読み取り、リストに保存します。 後の操作が以前の操作をオーバーライドするため、それらをすぐには適用しません。そのため、フォワード シミュレーションには高価な更新が必要になります。 
2. 逆処理中に行または列がすでに「消費」されているかどうかを追跡するために 2 つの配列またはセットを初期化します。 カウンターも整備`remaining_rows`そして`remaining_cols`、最初は n と m に等しくなります。 
3. 逆の順序で操作を実行します。 この順序により、操作を処理するときに、元のシーケンスでその操作の後に続くすべての操作がすでに考慮されることが保証されます。 
4. 各操作について:

 - 値 x を含む行 r に対する行操作の場合、行 r がすでにマークされているかどうかを確認します。 存在する場合は、後の操作でこの行の最終的な寄与がすでに決定されているため、スキップしてください。 
- マークされていない場合、この行は x にまだ割り当てられていない列の数を乗算した値になります。 追加`x * remaining_cols`答えに。 
- 行 r を処理済みとしてマークし、デクリメントします`remaining_rows`。 

その理由は、まだ割り当てられていないすべての列が、最終制御操作がこの行割り当てであるセルでこの行と交差するためです。 
5. 値 x を持つ列 c に対する列操作の場合:

 - 列 c がすでにマークされている場合は、スキップします。 
- それ以外の場合は追加します`x * remaining_rows`答えに。 
- 列 c をマークしてデクリメントします`remaining_cols`。 

これは対称的に機能します。割り当てられていない各行は、この列の 1 つのセルに寄与し、この操作が最新の影響を与える操作になります。 
6. すべての演算を逆に処理した後、累積和を出力します。 

### なぜ効果があるのか

 逆処理では常に、マークされていないすべての行と列が、最終的な定義操作がまだ考慮されていないものであるという不変条件を維持します。 行操作を処理する場合、後の列更新はすでに処理されているため、マークされていないすべての列は、最新の操作がまさにこの行更新であるセルに対応します。 したがって、マークされていない列の数を乗算すると、この行が最終値を決定するセルの数が正確にカウントされます。 同じ対称性が列にも当てはまります。 各行と列は、最初に逆方向に出現したときに 1 回だけカウントされるため、すべてのセルには最終的に寄与する操作が 1 つだけ割り当てられ、正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n, m, q = map(int, input().split())
        ops = []
        for _ in range(q):
            c, a, x = input().split()
            a = int(a)
            x = int(x)
            ops.append((c, a, x))

        used_row = set()
        used_col = set()

        rem_rows = n
        rem_cols = m

        ans = 0

        for c, a, x in reversed(ops):
            if c == 'F':
                if a in used_row:
                    continue
                ans += x * rem_cols
                used_row.add(a)
                rem_rows -= 1
            else:
                if a in used_col:
                    continue
                ans += x * rem_rows
                used_col.add(a)
                rem_cols -= 1

        out.append(str(ans))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装は、逆の処理ロジックを直接反映しています。 セット`used_row`そして`used_col`各行または列の最後に有効な更新のみを考慮するようにします。 カウンター`rem_rows`そして`rem_cols`逆の順序で後の操作によってまだ影響を受けていない行が何行あるかを追跡します。これは、現在の操作から値を取得する残りのセルの数に対応します。 

よくある間違いは、行または列が最初に逆に処理されるときにのみ、残りのカウンターをデクリメントするのを忘れることです。 操作の繰り返しにより複数回減分されると、寄与が過小評価される可能性があります。

トレースは、行が一度処理されると、その後のコントリビューションではその行を無視し、交差の二重カウントを防止していることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m + q) | 各操作は 1 回処理され、各行/列は最大 1 回マークされます。 
| スペース | O(n + m + q) | 業務および簿記セットの保管 |

 ## 特殊なケース

 行が複数回更新されると、微妙なエッジ ケースが発生します。 のような入力で`F 1 5`、`F 1 7`、最後の更新のみが重要です。 逆の処理では、最初に行 1 に遭遇したときに、それが最後の有効な更新であるため、これにマークを付けます。 後の遭遇はスキップされるため、以前の値は寄与しません。 

もう 1 つのケースは、すべての行が更新されるが、列がタッチされない場合です。 各行はその値に列の数を乗算したものになります。すべての行は独立しているため、最初に逆に見たときにそれぞれが 1 回だけカウントされます。 

最後に、次のように操作が行と列の間で頻繁に交互に行われる場合、`F C F C ...`、残りのカウンターは最初の遭遇時に正しく縮小し、各交差が正確に 1 回割り当てられるようにします。 小さな 2x2 グリッドを手動でトレースすると、4 つのセルがそれぞれ 1 回だけ考慮され、重複が発生していないことが確認されます。
