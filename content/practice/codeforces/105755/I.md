 ## 問題の理解

 私たちには一連の授業日と一連のニュースイベントが与えられており、各イベントは連続した範囲の日数にわたってアクティブになります。 毎日、数人の学生が発表する必要があり、各学生は、現在アクティブなイベントのどれだけを「準備」するかを制御する熱意値を持っています。 

クラスの日の開始時に、その日の時間間隔に含まれる、以前のクラスで提示されていないすべてのイベントを確認します。 この番号に電話してください$x$。 その日に到着した各学生は、独立して、正確に次のセットを選択します。$\min(x, e_i)$それらのアクティブなイベントの。 これらの選択は、そのサイズの有効なサブセットが選択できると仮定する必要があるという意味で敵対的です。 

すべての生徒がセットを選択した後、エズラは生徒が発表する順序を決定することができます。 学生が処理されるとき、学生は、そのクラスの前半でまだ使用されていない、準備されたセットから 1 つのイベントを提示する必要があります。 準備されたセット全体がすでに消費されている場合、失敗します。 

課題は、学生が許可されたサブセットをどのように選択するかに関係なく、どの学生も失敗しないように、すべてのクラスで学生の順序を選択できるかどうかを判断することです。 

最大の難点は、生徒がどのイベントを準備するかを私たちがコントロールできないことです。 私たちが知っているのは準備されたセットのサイズだけであり、その内容はわかりません。 これにより、単純な割り当て問題ではなく、最悪の場合の組み合わせ制約が作成されます。 

制約は大きく、テスト全体のイベントと生徒の総数は最大で$2 \cdot 10^5$。 サブセットのすべての選択肢を明示的にシミュレートしたり、完全な 2 部グラフでマッチングを実行しようとするソリューションは、クラスごとのイベントごとの線形作業でさえすでに制限を超えているため、遅すぎます。 

クラスのすべてのイベントがアクティブであるにもかかわらず、生徒の熱意値が小さい場合、微妙な特殊なケースが発生します。 イベントの総数が十分な場合でも、敵対的なサブセットの選択により、生徒がお互いの利用可能な選択肢から孤立してしまう可能性があります。 もう 1 つのエッジ ケースは、イベントが非常に短い間隔で発生し、利用可能なデータが急速に変化する場合に発生します。$x$、これは実現可能性にクラスごとに影響します。 

## アプローチ

 ブルート フォース ビューポイントでは、各クラスが独立して処理されます。 私たちは、学生が選択したサブセットを明示的に構築し、貪欲に、または二部マッチングによってイベントを割り当てようとすることを想像します。 これは概念的には正しいです。なぜなら、サブセットが修正されると、問題は生徒を選択したセット内の個別のイベントに一致させることになるからです。 

ただし、これは計算上すぐに破綻します。 各生徒は最大サイズのサブセットを選択できます$x$、そのような選択肢は指数関数的にたくさんあります。 単一の敵対的構成を修正したとしても、クラスごとのマッチングを解決するには少なくともコストがかかります$O(k_i \cdot x)$または$O(x^2)$一般的な実装では、制約の下では不可能です。 

重要な観察は、実際には正確なサブセットについて推論する必要がないということです。 最悪の場合のサブセット構造がどのような影響を与える可能性があるかを理解することだけが必要です。 学生は自分が選択した要素の数によってのみ制約されるため、敵対者はいつでも自分が選択した要素を他の学生に比べて最も不便な位置に配置することができます。 これは、私たちが信頼できる唯一の確実な情報は、各生徒が選択したセットのサイズであることを意味します。 

これにより、問題はスケジュールの実現可能性条件に変換されます。 各学生には実質的に「締め切りのような」制約があります。順番が遅すぎると、学生が選択した可能性のあるすべてのイベントが他の学生によってすでに消費されている可能性があります。 これにより、クラスは、これらのセット サイズから派生した制約を持つ貪欲な順序付け問題に変換されます。 

再定式化すると、各クラスは、次から導出される一連の整数に対する条件検査問題になります。$\min(e_i, x)$、そして解決策は、有効な順序付けが存在するかどうかを確認することに帰着します。

 ## アルゴリズムのチュートリアル

 各クラスを個別に処理します。 唯一のグローバル インタラクションは、毎日アクティブなイベントの数を計算することです。これは、各イベントが進行中で未使用の間のみプールに寄与するためです。 

### 1. 1 日あたりのアクティブなイベントを計算します。 

イベントの開始点と終了点にスイープ ラインを使用します。 毎日のために$i$、私たちは維持します$x$、現在アクティブで以前のクラスでまだ使用されていないイベントの数。 

この値は生徒を割り当てる前にクラスに対して固定されるため、その日の選択肢の範囲が決まります。 

### 2. 利用可能なイベントによって生徒の定員を制限する

 生徒一人ひとりの熱意を持って$e_i$で置き換えます。$e'_i = \min(e_i, x)$。 これは、学生が存在する以上に異なるイベントを準備できないことを反映しています。 

### 3. 順序制約を位置条件に変換する

 クラス内での生徒の有効な順序が考慮されます。 学生がそのポジションに配置されたとします。$p$(0 からインデックスが付けられます)。 まさにその瞬間、$p$イベントはすでに消費されています。 

学生は、準備したすべてのイベントがすでに使用されているセット内にある場合にのみ不合格になります。 攻撃者は任意のサイズのサブセットを選択できるため、$e'_i$、使用されるプールがサイズのサブセットを完全に含むのに十分な大きさである場合、失敗は避けられません。$e'_i$。 

これにより、学生を処理する前に、残りのイベントの数が次の条件を満たす必要があるという条件が生じます。$$x - p > x - e'_i$$これを単純化すると$$p < e'_i.$$したがって、各生徒は最初の時間内に登場する必要があります。$e'_i$注文の位置。 

### 4. 期限スケジュールの問題として実現可能性を確認する

 各ジョブには期限があるという古典的な制約ができました。$e'_i$そして、すべてのジョブをポジションに割り当てる必要があります$1..k_i$。 

すべて並べ替える$e'_i$降順ではない順に。 注文はすべてのポジションの場合にのみ実行可能です$j$、$$e'_j \ge j.$$この条件により、少なくとも次のことが保証されます。$j$学生は最初の枠内に配置できます$j$期限に違反することなくスロットを獲得できます。 

### 5. すべてのクラスに対して繰り返します。 

すべてのクラスが独立してこの条件を満たす場合、クラスごとに有効な順序付けを構築できます。 

### なぜ効果があるのか

 重要な不変条件は、敵対的なサブセットの選択は、構造ではなくセットのサイズを通じてのみ実現可能性に影響するということです。 攻撃者はいつでも、選択したサブセットをサイズの共有プールに埋め込むことができるため、$e'_i$、最悪の場合の動作を生き残る唯一の制約は、学生が十分に早く処理され、$e'_i$イベントは消費されました。 

これが期限の制約になったら、次の基準で並べ替えます。$e'_i$可能な限り厳密な順序を取得します。 あらゆる違反$e'_j \ge j$は、あまりにも多くの低キャパシティーの学生をあまりにも早くスケジュールしなければならず、確実に失敗する構成を強制するプレフィックスに直接対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def possible(e_list, x):
    # cap by available events
    e = [min(v, x) for v in e_list]
    e.sort()
    for i, v in enumerate(e, 1):
        if v < i:
            return False
    return True

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())

        classes = []
        total_k = 0
        for _ in range(n):
            tmp = list(map(int, input().split()))
            k = tmp[0]
            e = tmp[1:]
            classes.append(e)
            total_k += k

        events = []
        for _ in range(m):
            l, r = map(int, input().split())
            events.append((l, r))

        add = [[] for _ in range(n + 3)]
        rem = [[] for _ in range(n + 3)]

        for l, r in events:
            add[l].append(1)
            rem[r + 1].append(1)

        active = 0
        ptr = 0

        ok = True

        for day in range(1, n + 1):
            for _ in add[day]:
                active += 1
            for _ in rem[day]:
                active -= 1

            if not possible(classes[day - 1], active):
                ok = False
                break

        print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()

唯一の微妙な点は、実現可能性のチェックが現在の状況のみに依存していることです。$x$、イベント ID の構造ではありません。 これが、実際のイベントを保存したり割り当てたりしない理由です。 カウントだけが重要です。

| ステップ | ソート済み e' | チェック |

これは、十分な総イベント数があるだけでは十分ではないことを示しています。 配布の制約が重要です。 

### 例 2

| ステップ | ソート済み e' | チェック |

これは、敵対的なサブセット選択の下では、能力の高い生徒が複数の能力の低い生徒を補うことができないことを強調しています。

 ## 特殊なケース

 重要なケースの 1 つは、すべてのイベントが全日にわたる場合です。 それから$x$は一定で最大です。 このアルゴリズムでは、生徒の順序付け制約のみをチェックするようになり、失敗は純粋に熱意値の分布に起因します。 アクティブ カウントは安定しているため、スイープ ラインは正確さを妨げません。 

もう 1 つのケースは、イベントが非常にまばらで、$x$ほとんどのクラスでは小規模になります。 このような場合、すべての生徒に厳しい制限が適用され、多くの熱意値が同じ値に崩壊します。 並べ替えベースのチェックでは、すべての上限付きの値が均一に扱われるため、これは自然に処理されます。 

最後の微妙なケースは次のような場合です。$x = 0$。 それから全部$e'_i = 0$、最初の生徒が満足できないため、生徒がいるクラスはすぐに失敗します。$e'_1 \ge 1$。 これは、提示するイベントが存在せず、いかなるプレゼンテーションも不可能であるという現実と一致します。
