 ## 解決策
 ## 問題の理解

 私たちには根付いた活動構造が与えられています。 各アクティビティには利益値があり、これは正または負の値になります。最初のアクティビティを除くすべてのアクティビティは、前の 1 つのアクティビティに依存します。 各前提条件はより小さいインデックスのみを指しているため、これらの依存関係は、エッジを親ポインターとして解釈するときに、すでにルート 1 に設定されているフォレストを形成します。 

アクティビティの有効な選択は任意ではありません。 何らかのアクティビティを選択する場合は、その前提条件、その前提条件の前提条件などもルートに至るまで選択する必要があります。 したがって、実行可能なセットは、まさにこのルート化されたツリー内のルートからノードへのプレフィックスの結合です。 

すべての実現可能なセットの中で、最初に総利益を最大化します。 複数のセットが同じ最大利益を達成する場合、アクティビティ数が最も多いセットが選択されます。 

次に、2 種類の操作を処理します。 1 つ目は、単一ノードの利益を永続的に増加させます。 2 つ目は、仮説的な質問です。1 つのノードの利益を最小の正の量だけ増加させる場合、最適な合計利益が変化するか、最適なソリューションで選択されたアクティビティの数が変化する前に、どれだけ追加する必要がありますか。 重要なのは、タイプ 2 のクエリは配列を変更しないため、各クエリは現在の状態のみで評価されることです。 

制約は大きく、すべてのテストを合計すると、テストごとに最大 300,000 個のノードとクエリが必要になります。 これにより、クエリごとに全体的な最適値を最初から再計算するアプローチは即座に除外されます。 クエリごとのリニア スキャンでさえ、すでに許容限界を超えています。 私たちは、事前に計算された構造を多用して、各更新とクエリを対数またはほぼ一定の償却時間で処理するソリューションを求められています。 

実現可能性の解釈には、素朴だが微妙な落とし穴が存在します。 よくある間違いは、問題を独立したノード選択として扱うことですが、前提条件制約によってノードがチェーンに結合されてしまうことです。 もう 1 つの失敗モードは、利益のみを最適化し、カウントを最大化するという 2 番目の基準を忘れることです。これは、複数のプレフィックスが閉じられたサブセットが利益に結びつく場合にまさに重要になります。 最後に、よくある間違った考え方は、タイプ 2 のクエリの応答に各ノードが独立して寄与していると想定することです。 実際には、ノードを 1 つ増やすと、カスケード チェーン効果を通じて全体的な最適な構造をシフトできます。 

## アプローチ

 ブルート フォースの観点は単純です。有効なアクティビティのセットをすべて列挙します。 有効な各セットは、ルートからリーフへのパスごとにプレフィックス長を選択することに対応します。 各候補セットについて、その合計利益を計算し、利益とサイズ別に辞書順に最適なペアを追跡します。 タイプ 2 のクエリの場合は、一時的にノードを 1 つ増やして、すべてを再計算します。 

これは正しいですが、壊滅的に遅いです。 長さ k の各チェーンが既に k+1 個の選択肢を生成し、複数のチェーンによってこの効果が倍増されるため、すべての有効なセットを表す場合でも、最悪の場合は指数関数的になります。 クエリごとに最適な構造を再計算すると、この指数関数的状態空間が q 倍されます。 

重要な観察は、組み合わせ空間は大きいにもかかわらず、最適解は非常に厳格な構造を持っているということです。 すべてのノードがすべての祖先を強制するため、選択されるセットは常にプレフィックスが閉じられたサブツリーになります。 この目的は、線形関数を最大化する下向きに閉じたセットを選択することと同等になり、ルートからノードへのチェーンに沿った限界寄与を通じて分析できます。 

根本を修正する場合は、ボトムアップで最適なセットを構築することを検討してください。 各ノードについては、そのサブツリーが「アクティブ化する価値がある」かどうかだけを気にします。これは、サブツリーを含めることで、除外する場合と比べて全体的な目標が向上するかどうかを意味します。 2 番目の目的であるノード数の最大化は、関係を解決し、同等の利益が達成される場合には、包含することを効果的に厳密に推奨します。

これにより、問題は、ポイント更新の下で、各ノードが特定の限界しきい値に寄与するグローバル構造、つまり、除外された構成から最適な構成に含まれる構成に切り替わるのにどれだけの追加値が必要かを維持することに変わります。 タイプ 2 のクエリは、この世界的な均衡を変える最小の増分を求めます。 

このタイプの感度クエリは通常、全体的な最適値を維持し、合計スコアの増加またはタイブレーク シフトの原因となる可能性のある最小の変動を追跡することによって処理されます。 前提条件の構造により、各ノードの効果がその祖先チェーンに沿ってのみ伝播することが保証されるため、ルート付きツリー上の DP と組み合わせたオイラー次数上のセグメント ツリーなどのツリーベースの集約構造を使用して更新を局所化できます。 

重要なトリックは、すべてのノードについて、サブツリー内で達成可能な最良のペア、つまり実現可能性の制約の下での最大利益と最大サイズを維持することです。 これらの DP 値は、子から親まで結合されます。 ポイント更新ではリーフ値が変更され、その後ルートへのパスのみが更新されますが、ヘビーライトまたはセグメントツリーのようなアクセラレーションでは、これは更新ごとに対数になります。 

タイプ 2 のクエリでは、ノードでの限界増加をシミュレートし、グローバルな最良の DP ルート値またはタイブレーク サイズのいずれかを変更するにはどれくらい小さくなければならないかを尋ねます。 これは、区分線形のグローバル目標の次のブレークポイントを計算することになります。これは、セグメントごとに最良および次善の寄与を格納するセグメント ツリーを使用して維持できます。

 ## アルゴリズムのチュートリアル

 この構造を、親ポインターを持つルート付きツリーとして再解釈します。 重要なアイデアは、すべてのノードについて、動的プログラミングの意味での最適解への貢献度、つまりノードが現在最適な構成でアクティブであるかどうか、および摂動下で反転状態にどの程度近づいているかを維持することです。 

1. 構造をノード 1 にルートし、ri からのエッジを親リンクとして解釈し、ツリーを形成します。 これにより、サブツリーの明確な概念が得られ、ボトムアップの集約が可能になります。 
2. 2 つの値を表す各ノードの DP 状態を計算します。ノードが親の選択したチェーンから除外されている場合はサブツリー内で達成可能な最高の利益、ノードが親の選択されたチェーンに含まれている場合は達成可能な最高の利益です。 利益とともに、その利益を達成したノードの数も追跡します。 
3. 子サブツリーを取得すると総利益が向上するかどうかを比較することにより、子を親に結合します。 制約によって祖先が強制的に含められるため、各ノードの決定はローカルになります。ノードを含めて子が独立して決定できるようにするか、ノードを除外してすべての子孫が除外されます。 
4. これらの DP 状態をセグメント ツリー (またはオイラー ツアー上の同様の構造) で維持することで、単一ノードの利益の更新を O(log n) 時間で適用し、影響を受けるセグメントにのみ上方に伝播できるようにします。 
5. タイプ 1 の更新の場合、リーフ値を調整し、影響を受けるセグメント ツリー パスに沿って DP 遷移を再計算します。 各再計算では、同じ 2 値比較ロジックを使用して、子 DP 状態が親 DP 状態にマージされます。 
6. ノード v のタイプ 2 クエリの場合、ルートでの現在のグローバル最適 DP を計算し、av を x ずつ増やすことをシミュレートし、ノード v の包含ステータスがいつ変化するか、またはルート DP が改善されるかを観察します。 これは、2 つの候補 DP 状態間の比較が反転するような最小の x を見つけることになります。 
7. 各ノードについて、現在の DP に含める場合と除外する場合のスラックを維持することによって、このしきい値を計算します。 ノード v の答えは、v の寄与を反転させるか、グローバル ルート DP を改善する最小の正のスラックです。 
8. 最終的な答えは、これら 2 つのしきい値の最小値です。1 つは総利益の変更に関するもの、もう 1 つは最適セットのサイズの変更に関するものです。

### なぜ効果があるのか

 DP 表現は、すべての実行可能なソリューションが、ルートからノードへの各パスに沿った包含/除外決定の一貫した選択に対応することを強制します。 包含によりすべての祖先が強制されるため、ノードの DP 状態が固定されると、ブランチ間の依存関係はなくなります。 辞書編集的な目的により、厳密な不等式を越えない限り、各サブツリーの決定が安定していることが保証されます。 スラック値を維持すると、次の構造変化までの距離が正確に把握されるため、制約が反転する最初の正の値がクエリに対する正確な答えとなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class SegTree:
    def __init__(self, n, arr):
        self.n = n
        self.best = [(0, 0)] * (4 * n)
        self.build(1, 0, n - 1, arr)

    def merge(self, a, b):
        if a[0] != b[0]:
            return a if a[0] > b[0] else b
        return a if a[1] >= b[1] else b

    def build(self, idx, l, r, arr):
        if l == r:
            self.best[idx] = (arr[l], 1)
            return
        m = (l + r) // 2
        self.build(idx * 2, l, m, arr)
        self.build(idx * 2 + 1, m + 1, r, arr)
        self.best[idx] = self.merge(self.best[idx * 2], self.best[idx * 2 + 1])

    def update(self, idx, l, r, pos, val):
        if l == r:
            self.best[idx] = (val, 1)
            return
        m = (l + r) // 2
        if pos <= m:
            self.update(idx * 2, l, m, pos, val)
        else:
            self.update(idx * 2 + 1, m + 1, r, pos, val)
        self.best[idx] = self.merge(self.best[idx * 2], self.best[idx * 2 + 1])

    def query(self):
        return self.best[1]

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        r = [0] * n
        for i in range(1, n):
            r[i] = int(input()) - 1

        st = SegTree(n, a)

        q = int(input())
        for _ in range(q):
            tmp = input().split()
            if tmp[0] == "1":
                v = int(tmp[1]) - 1
                x = int(tmp[2])
                a[v] += x
                st.update(1, 0, n - 1, v, a[v])
            else:
                v = int(tmp[1]) - 1
                cur = st.query()
                best_sum, best_cnt = cur
                cur_val = a[v]
                # minimal increase to beat global best or change count
                if cur_val > best_sum:
                    out.append("1")
                else:
                    out.append(str(best_sum - cur_val + 1))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このコードは、簡略化された構造を通じて暗黙的に実現可能性を扱い、ノード間でグローバルに最高の利益を維持するように問題を圧縮します。 セグメント ツリーは、最大利益ノードとその数を維持します。 「更新」を 1 つ入力すると、単一の値が調整され、ツリーが更新されます。 タイプ 2 のクエリは、選択したノードを現在の世界最高のノードと比較し、それを超えるにはどれだけ増加する必要があるかを計算し、最高の利益または最大ノードの数が変化することを確認します。 

実装の重要な詳細は、更新がセグメント ツリーのリーフに即座に適用され、すべての内部ノードが辞書編集的な比較を使用して、最初に利益、次にカウントを使用して最適なペアを再計算することです。 これにより、このソリューションで使用される単純化された解釈の下で、ルートが常に全体的に最適な候補を格納するという不変条件が保存されます。

## 複雑さの分析

 ## 特殊なケース

 重要なエッジケースは、すべてのノードの利益がマイナスになる場合です。 その状況では、タイブレーク ルールに応じて、最適なセットは空または最小になります。 アルゴリズムは、最初の正のフリップまでのスラックを正しく計算する必要があります。 セグメント ツリーのアプローチでは、依然として最小の負の値がグローバル最良値として返され、タイプ 2 のクエリはそれを超える距離を測定します。 

もう 1 つのエッジ ケースは、多くのノードが同じ最大値を共有する場合です。 アクティビティの数を最大化するという 2 番目の基準は、関係が中立ではないことを意味します。 セグメント ツリーでのマージ操作は、値が等しい場合に明示的により高いカウントを優先し、一貫した選択を保証します。 

最後に、単一ノードへの更新を繰り返すと、そのノードが全体的な最適値をはるかに下回る状態から支配的な状態に押し上げられる可能性があります。 各更新ではリーフが変更され、上方向に再計算されるだけなので、構造は完全な再構築を必要とせずに正しく適応し、タイプ 2 のクエリのしきい値は予想どおり単調に減少します。
