 ## 解決策
 ## 問題の理解

 時間の経過とともに変化する整数の配列を維持しています。 更新とともに、非常に具体的なクエリが繰り返し求められます。配列のセグメントと数値 x が与えられると、そのセグメント内の要素がいくつ x を正確に分割するかを数えなければなりません。 

したがって、タイプ 2 の各クエリは範囲を指定し、通常の意味で頻度を合計したりカウントしたりすることはありません。 代わりに、範囲内の各要素 a[i] は、x mod a[i] が 0 に等しい場合にのみ寄与します。 

主な問題点は、更新とクエリの両方がオンラインで行われることです。 位置 i の値は任意に何度でも変更できるため、後のクエリでは現在の状態を反映する必要があります。 

この制約により、各クエリの全範囲をスキャンするソリューションは失敗するという状況に私たちは追い込まれます。 n と q が最大 100,000 の場合、クエリごとの単純な O(n) アプローチでは、最悪の場合、約 10^10 の操作が発生し、これは 1 秒では実現不可能です。 賢い定数係数を追加しても、そのような解決策は得られません。 

a[i] と x の値は両方とも 100000 によって制限されます。これは重要な構造上の制約です。 これは、約数の関係が完全に小さな整数の世界の中に存在するため、因数に関連した推論が可能であることを示唆しています。 

ここではいくつかの特殊なケースが重要です。 

すべての要素が 1 の場合、すべての要素がすべての x を除算するため、すべての範囲クエリは r − l + 1 を返します。約数が「まれ」であると誤って仮定したソリューションは、ここでは誤った動作をします。 

x がほとんどの a[i] よりも大きい素数の場合、1 と x 自体の出現のみが問題になります。 単純なスキャンは依然として機能しますが、最適化されたアプローチは 1 の特別な役割を見逃してはなりません。 

更新により値が 1 や 2 などの小さな数値に頻繁に変更される場合、寄与する位置の数が非常に多くなる可能性があるため、値ごとの重い構造は頻繁な増分と減分を適切に処理する必要があります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 タイプ 2 の各クエリについて、範囲 [l, r] を反復処理し、a[i] が x を除算するかどうかを確認します。 各チェックは O(1) であるため、最悪の場合でも各クエリのコストは O(n) になります。 更新は O(1) です。 これはクエリの定義を直接実装しているため、正解です。 

問題はスピードです。 最大 100,000 個のクエリと範囲が配列全体に及ぶ場合、これは約 10^10 の割り算チェックになります。 たとえ各チェックが非常に高速だったとしても、これでは遅すぎます。 

重要な観察は、視点を反転することによって得られます。 範囲内のすべての要素を反復処理して x を除算するかどうかを確認する代わりに、x のすべての約数を反復処理して、それらの値が範囲内にあるかどうかを確認できます。 すべての a[i] は最大でも 100000 であるため、x の可能な約数のセットは小さく、最大 100000 までの x に対して最大でも約 200 です。 

これにより、クエリが「セグメントをスキャンする」から「セグメント内の x の約数と合計頻度を列挙する」に変換されます。 値ごとに高速範囲頻度クエリを維持できる場合、各クエリはセグメントのサイズではなく、x の約数の数に比例します。 

更新と範囲頻度クエリの両方をサポートするために、値 v ごとに、a[i] が v に等しい位置の動的なセットを維持します。そのような各セットは、[l, r] に含まれる位置の数のカウントをサポートします。 これは、順序付けされた構造で実装できます。動的に圧縮する場合は、より簡単に値ごとのフェンウィック ツリーで実装できます。ただし、値には制限があるため、よりクリーンなアプローチは、位置全体にわたって値ごとの BIT を維持することです。 

考えられる値 v ごとにフェンウィック ツリーを維持します。ここで、tree[v] は現在 v を含むインデックスをマークします。位置 i を古い値から新しい値に更新するとき、古い BIT から i を削除し、新しい BIT に追加します。 固定 v に対する各範囲クエリは、プレフィックス合計の差になります。

各クエリは x の約数のみを反復し、各約数クエリは O(log n) であるため、最終的な複雑さは許容範囲内です。

 ## アルゴリズムのチュートリアル

 1 ～ 100000 のすべての可能な値に対して 1 つのフェンウィック ツリーを維持します。各ツリーは、その値が現在どの位置に格納されているかを追跡します。 

1. 初期配列を読み取り、各インデックス i を a[i] に対応するフェンウィック ツリーに挿入することにより、構造を初期化します。 これにより、すべての値の位置インデックスが構築されます。 
2. グローバルな約数については何も事前計算しません。 代わりに、クエリごとに x の約数をその場で生成します。 これによりメモリが小さく保たれ、すべての数値の因数リストを保存する必要がなくなります。 
3. 更新クエリ「set a[i] = x」を処理するには、まず古い値のフェンウィック ツリーからインデックス i を削除し、次に新しい値のフェンウィック ツリーに i を挿入します。 その後、a[i]を更新します。 これにより、表現が常に一貫した状態に保たれます。 
4. 範囲クエリ「x を除算する [l, r] 内の要素をカウントする」を処理するには、O(sqrt(x)) 内の x のすべての約数 d を列挙します。 各約数 d について、値 d のフェンウィック ツリーに格納されている [l, r] のインデックスの数を加算します。 d は a[i] に等しくなければならないため、これは有効な貢献を直接カウントします。 
5. タイプ 2 の各クエリの累積合計を出力します。 

重要な設計上の選択は、「価値の同一性」を「位置の集約」から分離することです。 それぞれの値はインデックスのバケツのように動作し、フェンウィック ツリーはバケツごとの範囲を高速にカウントします。 

### なぜ効果があるのか

 いつでも、すべてのインデックス i は、その現在の値 a[i] に対応する 1 つのフェンウィック ツリーに属します。 したがって、範囲内のいくつかの d に等しい a[i] がいくつあるかを数えるということは、その範囲内で Tree[d] に格納されているインデックスがいくつあるかを数えるということとまったく同じです。 x の約数はまさに貢献の対象となる値であるため、これらを合計すると漏れや重複がなく正しい答えが得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXV = 100000

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def divisors(x):
    res = []
    i = 1
    while i * i <= x:
        if x % i == 0:
            res.append(i)
            if i * i != x:
                res.append(x // i)
        i += 1
    return res

n, q = map(int, input().split())
a = [0] + list(map(int, input().split()))

trees = [Fenwick(n) for _ in range(MAXV + 1)]

for i in range(1, n + 1):
    trees[a[i]].add(i, 1)

out = []

for _ in range(q):
    tmp = input().split()
    if tmp[0] == '1':
        i = int(tmp[1])
        x = int(tmp[2])

        old = a[i]
        if old != x:
            trees[old].add(i, -1)
            trees[x].add(i, 1)
            a[i] = x

    else:
        l, r, x = map(int, tmp[1:])
        ans = 0
        for d in divisors(x):
            if d <= MAXV:
                ans += trees[d].range_sum(l, r)
        out.append(str(ans))

print("\n".join(out))
```フェンウィック ツリーの実装は標準であり、各値の位置のカウントを保存します。 重要な点は、Fenwick 操作と配列インデックスの両方がそれに依存しているため、1 からインデックスされた位置を一貫して維持することです。 

除数の列挙はクエリごとに再計算されます。 sqrt(100000) が約 316 であるため、最悪の場合のクエリでも小さいままであるため、これは効率的です。 

更新ステップでは、新しい値を挿入する前に古い値を慎重に削除し、バケット間でインデックスが二重にカウントされないようにします。

 | 時間 | O(q · sqrt(maxA) · log n) | 各クエリは約数を列挙し、フェンウィック範囲の合計を実行します。 
| スペース | O(maxA・n) | 位置に対する値ごとに 1 つのフェンウィック ツリー |

 ## 特殊なケース

 完全に均一な 1 の配列は、正確性にとって最も積極的なケースです。 入力用`a = [1,1,1,1]`そしてクエリ`x = 100`、約数には 1 が含まれるため、すべての要素が寄与します。 アルゴリズムは除数 1 をチェックし、セグメント全体の長さに等しい Fenwick Tree[1].range_sum(l,r) を返します。 特別なケースは必要ありません。これにより、1 を通常の値バケットとして扱うことが正しいことが確認されます。 

値がそれ自体で置き換えられる境界更新では、冗長な更新が安全かどうかをテストします。 いつ`a[i] = x`、コードは変更をスキップし、不必要なフェンウィック操作を防ぎます。 たとえそのガードが取り除かれたとしても、正確性は維持されますが、パフォーマンスは低下します。これは、最適化が論理的に必要ではなく、実際的に重要であることを示しています。 

n=1 および q=1 の最小限の入力で、インデックス付けの一貫性をテストします。 フェンウィック ツリーは依然として 1 ベースのインデックスを使用しており、すべての操作が単一点更新と [1,1] を超える範囲合計に削減されるため、更新とクエリの両方が正しく動作します。
