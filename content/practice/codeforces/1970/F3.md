 ## 解決策
 ## 問題の理解

 グリッド上でプレイされる非常に小さなイベント駆動型のゲームをシミュレートしています。 グリッドには 2 つのチームの選手、各チームの固定ゴール、および最大 3 種類のボールが含まれています。クアッフル (得点に使用)、ブラッジャー (接触した選手を排除)、ゴールデン スニッチ (捕らえられるとすぐにゲームを終了できる) です。 

入力により、オブジェクト上のすべてのエンティティの初期レイアウトが得られます。$N \times M$ボード、その後に続く一連の$T$アクション。 各アクションは、プレーヤーが移動したり、ボールを拾ったり、クアッフルを落としたりするなど、1 つのエンティティにのみ影響します。 移動はグリッド上で段階的に行われ、インタラクションは各アクションの直後に解決されます。 重要な問題は、得点、ボールのリセット、除去、ゲームの終了など、1 つの動きの「副作用として」多くのことが起こる可能性があることです。 

出力はボードの最終状態ではなく、シミュレーション中に発生するイベントのログです。 厳密な時間順にエリミネーションを出力し、次にスコアイベントを出力し、最後に最終スコアラインを出力する必要があります。 

制約は、直接シミュレーションが意図されているほど十分に小さいです。$T \leq 10^4$、$N, M \leq 99$、最大20人のプレイヤー。 これにより、より複雑なものは直ちに排除されます。$O(T)$または$O(T \log T)$。 ステップごとにボード全体の構造を再計算しようとするソリューションはすべて合格しますが、不必要なグローバル スキャンを繰り返し実行すると、簡単にパフォーマンスの罠になる可能性があります。 

微妙な部分は、複数のインタラクションが同じタイム ステップで発生する可能性があり、順序が重要であるということです。 

よくある失敗例の 1 つは、同時消去順序を無視することです。 たとえば、ブラッジャーとプレーヤーの両方が同じセルに配置される場合、エリミネーションはプレーヤー ID のアルファベット順に出力される必要があります。 

入力シナリオ:```
R0 and B0 collide with Bludger in same step
```正しい出力順序:```
B0 ELIMINATED
R0 ELIMINATED
```任意の辞書順でプレイヤーを処理する単純なシミュレーションでは、これが逆転する場合があります。 

もう 1 つの失敗例は、得点するとクッフルがすぐに中央にリセットされることを忘れていることです。 プレーヤーがゴール セルに移動し、その後同じステップでクアッフルを投げた場合、スコアはリセットされる前にその位置に基づいてそのステップの早い段階ですでに解決されている必要があります。 

最後に、スニッチを捕まえるとゲームは即座に終了する必要があります。つまり、アクションが後から入力されたとしても、それ以上のアクションは処理されません。 

## アプローチ

 直接シミュレーションが自然な出発点となります。 グリッド、すべてのエンティティの位置を保存し、クアッフルを持っているかどうかなどのプレイヤーごとの状態を維持します。 各コマンドは順番に実行され、位置が更新され、相互作用がチェックされます。 

ブルートフォースの考え方では、すべての動きの後にすべてのプレーヤーをスキャンしてブラッジャーとの衝突を検出し、すべてのセルをスキャンしてゴールと得点イベントを検出します。 これは正しいですが、原理的には非効率的です。ステップごとにすべてのプレイヤーをスキャンすると、$O(P \cdot T)$、グリッドをスキャンすると別のものが追加されます$O(NM \cdot T)$。 これでもここでの制約には適合しますが、不必要なオーバーヘッドが発生し、実装が複雑になるリスクがあります。 

重要な観察は、すべての対話がローカルであるということです。 すべてのイベントは、アクションの瞬間に同じセルを共有しているエンティティにのみ依存します。 これにより、位置からエンティティへの直接マッピングを維持し、各移動後に影響を受けるセルのみを更新することができます。 グローバルな再計算は必要ありません。 

したがって、最適な解決策は依然としてシミュレーションですが、構造化された状態を維持するものです。 

- 辞書内のプレーヤーのポジション
 - 素早い検索のためのセル占有追跡
 - クッフルの場所または運送業者の参照
 - ゴール位置は事前にマークされています
 - ブラジャーとスニッチのポジション

 各アクションの後、ボード全体ではなく、影響を受けたセルのみを検査します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース スキャン ボード/プレーヤーの各ステップ |$O(T(NM + P))$|$O(NM + P)$| 概念的には遅すぎる |
 | ローカル更新によるイベント駆動型シミュレーション |$O(T)$|$O(NM + P)$| 承認済み |

 ## アルゴリズムのチュートリアル

 すべてのエンティティの正確な状態を維持しながら、段階的にシミュレーションします。 

1. グリッドを解析して以下を保存します。 

各プレーヤー、クアッフル、ブラッジャー、スニッチ、および両チームのゴールの位置。 これにより、最初の解析が唯一のグローバル操作であるため、後でグリッドを再スキャンする必要がなくなります。 
2. プレイヤー ID からその位置および生存ステータスまでのマップを維持します。 死亡したプレイヤーは今後のアクションでは無視されます。 
3. 別のブール マップを使用して、プレーヤーがクアッフルを運んでいるかどうかを追跡します。 クアッフル自体は、位置が固定されているか、プレーヤーに取り付けられています。 
4. それぞれについて$T$アクションを順番に処理します。 

アクターがすでに排除されている場合は、処理を完全にスキップします。 
5. アクションが移動の場合、エンティティの位置を 1 セル分更新します。 プレイヤーの場合、クアッフルを運んでいる場合は、クッフルも移動させます。 動きは常にステップごとにアトミックであるため、中間状態は存在しません。 
6. 移動するたびに、ブラッジャーの衝突を確認します。 プレイヤーがブラッジャーとセルを共有している場合、それらを排除済みとしてマークします。 この動きによって引き起こされたすべての削除を直ちに登録する必要があります。 
7. このステップのすべてのエリミネーションが特定されたら、それらをプレイヤー ID 順にソートして出力します。 
8. 生き残ったプレイヤーがクアッフルを持っていて、敵チームのゴールセルにいる場合、得点を計算します。 

スコアを更新し、イベントを発行し、Quaaffle をすぐに中央にリセットします。 
9. アクションがキャッチ コマンドの場合、プレーヤーがセルを共有している場合は、指定されたボールをプレーヤーに取り付けます。 
10. アクションが投げコマンドの場合、クアッフルを切り離し、現在のセル上に残します。 
11. スニッチが捕らえられた場合は、ただちにイベントを出力し、スコアを 10 ずつ更新し、残りのすべてのアクションの処理を終了します。 

中心的な不変条件は、処理ステップ後の$i$、その後の世界の状態はゲームのルールと完全に一致します。$i$衝突やスコアリングによるすべてのカスケード効果を含むアトミック アクション。 すべての副作用は同じタイム ステップ内で即座に解決されるため、後のステップでは常に一貫した状態が観察されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    N, M = map(int, input().split())

    grid = []
    players = {}
    alive = {}
    carry = {}
    pos = {}

    bludger = None
    snitch = None
    quaffle = None

    red_goal = set()
    blue_goal = set()

    for i in range(N):
        row = input().split()
        for j, cell in enumerate(row):
            if cell == "..":
                continue
            if cell == ".Q":
                quaffle = (i, j)
            elif cell == ".B":
                bludger = (i, j)
            elif cell == ".S":
                snitch = (i, j)
            elif cell == "RG":
                red_goal.add((i, j))
            elif cell == "BG":
                blue_goal.add((i, j))
            else:
                team = cell[0]
                pid = cell
                players[pid] = (i, j)
                alive[pid] = True
                carry[pid] = False

    T = int(input())
    score_r = 0
    score_b = 0

    center = ((N // 2), (M // 2))

    def move(p, d):
        x, y = players[p]
        if d == "U":
            x -= 1
        elif d == "D":
            x += 1
        elif d == "L":
            y -= 1
        else:
            y += 1
        players[p] = (x, y)

    def check_elim():
        nonlocal bludger
        to_remove = []
        bx, by = bludger
        for p in players:
            if alive[p] and players[p] == (bx, by):
                to_remove.append(p)
        to_remove.sort()
        for p in to_remove:
            alive[p] = False
            carry[p] = False
            print(f"{t} {p} ELIMINATED")

    for t in range(T):
        parts = input().split()
        actor = parts[0]
        if actor not in players or not alive[actor]:
            continue

        cmd = parts[1]

        if cmd in "UDLR":
            move(actor, cmd)
            if carry[actor]:
                quaffle = players[actor]

            if bludger is not None:
                check_elim()

            # scoring after movement
            if carry[actor]:
                ppos = players[actor]
                if ppos in red_goal:
                    score_b += 1
                    print(f"{t} BLUE GOAL")
                    quaffle = center
                    carry[actor] = False
                elif ppos in blue_goal:
                    score_r += 1
                    print(f"{t} RED GOAL")
                    quaffle = center
                    carry[actor] = False

            # snitch check
            if snitch is not None and players[actor] == snitch:
                team = actor[0]
                if team == "R":
                    score_r += 10
                    print(f"{t} RED CATCH GOLDEN SNITCH")
                else:
                    score_b += 10
                    print(f"{t} BLUE CATCH GOLDEN SNITCH")
                return

        elif cmd == "C":
            ball = parts[2]
            if ball == ".Q":
                carry[actor] = True
                quaffle = None

        elif cmd == "T":
            carry[actor] = False
            quaffle = players[actor]

    print(f"FINAL SCORE: {score_r} {score_b}")

if __name__ == "__main__":
    solve()
```実装は、明示的な状態を再構築するのではなく、明示的な状態を維持することに依存しています。 プレーヤーの位置は直接更新され、クアッフルはプレーヤーにアタッチされるか、座標として保存されます。 消去チェックは、ブラッジャーのセルのみを検査するヘルパーに集中されており、グリッドの無関係な部分がスキャンされないようになっています。 

微妙な詳細はエリミネーションの順序です。プレイヤー ID をソートすることで、出力が確実に確定します。 もう 1 つは、移動直後、次のアクションまでの得点の処理です。 

スニッチ条件はゲームの残りの部分をオーバーライドするため、移動直後にチェックされます。 

## 実用的な例

 プレイヤーがクアッフルを持ってゴールに移動する最小限のインタラクションを考えてみましょう。 

| 時間 | アクション | プレーヤーの位置 | クアッフル | イベント |
 | --- | --- | --- | --- | --- |
 | 0 | R0D | (2,2) | 運ばれる | なし |
 | 1 | R0T | (2,2) | 落とした | なし |
 | 2 | R0D | (3,2) | (2,2) | ブルーゴール |

 これは、スコアが将来の動きではなく、クアッフルをリリースした瞬間の位置やキャリー状態に依存することを示しています。 

ここで Bludger 衝突を考えてみましょう。 

| 時間 | アクション | R0 位置 | B0 位置 | イベント |
 | --- | --- | --- | --- | --- |
 | 0 | R0R | (1,1) | (1,2) | なし |
 | 1 | B0L | (1,1) | (1,1) | R0 を排除、B0 を排除 |

 これは同時除去の順序を示しています。両方のプレイヤーが同じステップで除去されるため、ソートする必要があります。 

これらのトレースは、すべての対話がローカルであり、各アクションの直後に解決されることを確認します。

 ## 特殊なケース

 重要なエッジケースは、ブラッジャーの動きによって引き起こされる同時除去です。 複数のプレイヤーが同じステップで同じセルに着地する場合、最初にすべてを収集してから、ソートされた順序で出力する必要があります。 プレイヤーごとの単純な即時印刷では、誤った順序が発生する危険があります。 

もう 1 つのエッジ ケースは、同じタイムステップでスニッチ キャプチャ ロジックが直後に続くスコアリングです。 正しい動作では、スニッチ キャプチャは動作の処理後すぐにゲームを終了するため、同じステップ内にある保留中のスコアは終了前にすでに解決されている必要があります。 

最後の微妙なケースは、クアッフルがゴールに運ばれ、同じステップで落とされたことです。 スコアリングは移動後、スローアクション前の位置に基づいて評価されるため、コマンド処理の順序によって一貫性が保証されます。つまり、移動が状態を解決し、スコアリングがチェックされ、その後にのみスローが処理されます。
