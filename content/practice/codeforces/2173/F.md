 ## 解決策
 ## 問題の理解

 増加しない正の整数の配列が与えられ、「容量リセット」ルールに基づいてそのサブセグメントを繰り返し処理します。 

クエリごとに、インデックスから連続したスライスを選択します。`l`に`r`。 次に、それを左から右にスキャンして、現在の合計を維持します。 次の要素を追加すると、合計がしきい値に達するかそれを超えるたびに`x`、「クリアイベント」を 1 つカウントし、すぐに合計をゼロにリセットします。 スキャンの終了後、発生したクリアの数と、まだ保存されている残りの合計が報告されます。 

したがって、各クエリは基本的に、サブ配列に適用される、しきい値でリセットのルールを備えたストリーミング アキュムレータの決定論的なシミュレーションです。 

重要な問題はスケールです。 配列とクエリの数はどちらも大きく、すべてのテスト ケースにわたる合計要素とクエリの数は最大 150,000 です。 クエリごとの直接シミュレーションでは、最大でスキャンできます。`O(n)`要素、`O(nq)`最悪の場合、大きすぎる場合もあります。 

配列の非増加特性は、利用する必要がある構造上の制約です。 これは、任意の固定範囲内で、初期の要素が後のすべての要素を支配することを意味し、プレフィックスの合計と容量に収まる項目の数に対して強力な単調な動作が作成されます。 

大きな要素の後に多数の小さな要素が続く場合、微妙なエッジケースが発生します。 素朴な直観は、リセットが「めったに」発生しない、または貪欲なパッキングが均一であると仮定するかもしれませんが、実際には、単一の大きな要素が即座にリセットを強制し、後続の小さな要素が再び蓄積される可能性があります。 

たとえば、次のように考えてみましょう`a = [6, 5, 3, 2]`そしてクエリ`(l=1, r=4, x=7)`。 単純で不適切な最適化では、合計をグローバルに「パック」し、要素ごとのシミュレーションをスキップしようとする可能性がありますが、正しい動作は正確な順序に依存します。`6`(合計=6)、`5`リセット (1) をトリガーし、その後`3+2`独立して行動します。 順序を尊重せずに集約するアプローチは、正確さを失います。 

したがって、課題は、プレフィックスのようなプロセスで繰り返ししきい値の交差を計算するための構造化された方法が必要な、多くの範囲クエリに答えることです。 

## アプローチ

 ブルートフォースの方法は簡単です。 クエリごとに、以下を繰り返します。`l`に`r`、現在の合計を維持し、それが到達するかそれを超えるたびにカウンターをインクリメントします。`x`。 各クエリのコスト`O(r-l+1)`、したがって、最悪の場合の複雑さの合計は次のようになります。`O(nq)`、最悪の場合、約 2.25×10¹⁰ の操作に達します。 これはまったく実現不可能です。 

重要な観察は、配列の単調な構造から得られます。 以来`a[i] >= a[i+1]`、大きい値が最初に表示され、後の値はそれより小さいか等しい値になります。 これにより、リセットの発生方法に強いバイアスが生じます: 合計が交差した場合`x`、これは常に現在のスキャンの比較的小さいプレフィックスが原因であり、リセット後、プロセスは厳密に弱い残りの値で再起動されます。 

すべてのクエリを個別にシミュレートするのではなく、合計が到達するブロックを繰り返し「ジャンプ」するプロセスとして再解釈します。`x`。 リセットの数は、範囲内の互いに素なセグメントを容量以下に貪欲にパックできる数に相当します。`x`。 

これを効率的にサポートするために、事前に計算されたプレフィックス構造とポインター ジャンプのアイデアを組み合わせたクエリに対する分割統治を使用します。 中心的なツールは、開始位置と容量のしきい値ごとに、リセットをトリガーする前にどこまで移動できるかを計算し、直接スキップできることです。 これにより、前処理に応じて、線形スキャンから対数または償却定数移行へのクエリごとのコストが削減されます。 

これを実装する一般的な方法は、ポジションごとに、「しきい値未満のセグメント合計」がどこまで拡張できるかに関する情報を維持することです。 値が増加しないため、バイナリ リフティングまたはセグメント ツリーの累積は最大リーチの計算に適しています。 各クエリは、次からの繰り返しジャンプになります。`l`向かって`r`、完全な「ブロック」がいくつ収まるかを数えます。

 ## アルゴリズムのチュートリアル

 すべての範囲の合計はすぐに導出できるため、配列のプレフィックスの合計を前処理します。 主な課題は、「オーバーフローするまで充填してからリセットする」操作の繰り返しを処理することです。 

1. プレフィックス合計配列を構築する`pref`どこ`pref[i] = a[1] + ... + a[i]`。 これにより、一定時間の範囲合計クエリが可能になります。 これは、ジャンプの計算がセグメントがどこまで延長できるかを評価することに依存しているため、重要です。 
2. 各開始インデックスについて`i`、最も遠いインデックスを見つけることができる構造を計算します。`j`からの合計が`i`に`j`未満です`x`。 以来`x`はクエリごとに異なるため、これを直接事前計算することはできませんが、プレフィックス合計の二分探索を使用してサポートできます。 
3. お問い合わせの場合`(l, r, x)`、ジャンプでプロセスをシミュレートします。 から開始`pos = l`、 と`cnt = 0`そして`cur = 0`。 
4. 各ステップで、セグメントを可能な限り拡張しようとします。`[pos, r]`要素の追加が次を超えないようにします。`x`リセットを引き起こさない限り。 要素ごとにチェックする代わりに、最も遠いものを見つけます。`mid`どこ`cur + (pref[mid] - pref[pos-1]) < x`はまだ有効です。 これは二分探索で見つけることができます。 
5. 最大値を見つけたら`mid`を含めることができるかどうかを確認します。`mid + 1`。 「はい」の場合、リセットが次の時点で発生することを意味します`mid + 1`なので、インクリメントします`cnt`、リセット`cur = 0`、設定します`pos = mid + 1`。 そうでない場合は、残りの金額を追加して終了します。 
6. まで続けます`pos > r`。 

このプロセスでは、各クエリを範囲拡張の対数に減らし、それぞれを二分探索で解決します。 

### なぜ効果があるのか

 このアルゴリズムは、リセットされるたびにバッファーの合計が正確にゼロになり、次の未処理の要素に位置するという不変条件を保持します。 すべてのジャンプで次のリセットまでに消費できる最大プレフィックス セグメントが計算されるため、要素がスキップされたり二重にカウントされたりすることはありません。 プレフィックスの合計はすべてのセグメントの合計を完全に特徴付けるため、二分探索では次のリセット境界を正確に識別します。 配列の単調な順序付けは、プレフィックスの合計を正確にするために厳密には必要ありませんが、これにより数値の安定性が確保され、セグメントの動作における病的な振動パターンが防止されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n, q = map(int, input().split())
        a = list(map(int, input().split()))

        pref = [0] * (n + 1)
        for i in range(n):
            pref[i + 1] = pref[i] + a[i]

        for _ in range(q):
            l, r, x = map(int, input().split())

            cnt = 0
            cur = 0
            pos = l

            while pos <= r:
                lo, hi = pos, r
                best = pos - 1

                # find furthest we can extend without forcing a reset immediately
                while lo <= hi:
                    mid = (lo + hi) // 2
                    seg_sum = pref[mid] - pref[pos - 1]

                    if cur + seg_sum < x:
                        best = mid
                        lo = mid + 1
                    else:
                        hi = mid - 1

                if best >= r:
                    cur += pref[r] - pref[pos - 1]
                    break

                # we reach best, then next element triggers reset
                cur += pref[best] - pref[pos - 1]
                cnt += 1
                cur = 0
                pos = best + 1

            out.append(f"{cnt} {cur}")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションは、テスト ケースごとにプレフィックスの合計を構築します。 各クエリは貪欲な拡張ループを使用します。 ループ内では、バイナリ検索により、オーバーフローを引き起こすことなく到達可能な最も遠いインデックスが検索されます。 次の要素でオーバーフローが避けられない場合は、リセットを登録して次の位置から続行します。 

微妙な実装の詳細は、不等式です。`cur + seg_sum < x`。 厳密な比較により、しきい値に到達または超過した最初の瞬間のみが停止し、合計が少なくとも以上になるとすぐにリセットが発生するというルールに一致します。`x`。 

別の詳細はメンテナンス中です`best`として`pos - 1`。 これにより、単一の要素が即時リセットをトリガーする場合でも正しく処理されます。

 ## 特殊なケース

 重大なエッジケースは、単一の要素がすでにしきい値を超えているか、しきい値を満たしている場合です。 その状況では、すべての要素が即時リセットをトリガーします。 

入力用`a = [10, 9, 8]`そしてクエリ`(1, 3, 5)`, the correct behavior is three resets and zero final sum. アルゴリズムはこれを処理します。`best`になる`pos - 1`、単一の要素を即座に消費し、各ステップでリセットすることを強制します。 

もう 1 つのケースは、範囲の合計に比べてしきい値が極端に大きい場合です。 のために`a = [1, 1, 1, 1]`そして`x = 100`、ループがリセットをトリガーすることはなく、アルゴリズムは単一の範囲合計の累積に崩壊します。 二分探索で見つかるのは、`best = r`となり、プロセスは増分なしで終了し、正しい最終合計とゼロ リセットが生成されます。 

3 番目のケースでは、「ほぼリセットされた」境界が交互に発生し、部分和が繰り返し近づきますが、超えることはありません。`x`。 このアルゴリズムは、常に最大の安全な拡張を計算し、各リセットが誤って先にスキップするのではなく、最初の違反位置に正確に対応するようにするため、これを処理します。
