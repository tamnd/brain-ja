 ## 解決策
 ## 問題の理解

 10 進数で書かれた非常に大きな整数が与えられます。そのような数値ごとに、数字 4 と 7 だけで構成される、それを超えない正の整数がいくつあるかを数える必要があります。 

したがって、タスクは算術制約の下で数値を構築することではなく、指定された数値の上限までのすべての「幸運な」数字列について推論することです。 すべての桁が 4 または 7 の場合、その数値は有効であるとみなされ、1 から n までの範囲内にそのような有効な数値がいくつあるかを数えなければなりません。 

重要な問題は、n のサイズにあります。 最大 100 桁まで含めることができるため、組み込みの整数型には適合しません。 どのようなソリューションでも、それを文字列として扱い、桁ごとに推論する必要があります。 テスト ケースの数は最大 10^4 であるため、テスト ケースごとの効率は桁数において基本的に線形である必要があります。 

長さ 100 までのすべての幸運な数字を生成する単純なアプローチは、すでに実行不可能です。 長さによって制限したとしても、考えられるラッキー文字列は 2^100 あり、これは天文学的に膨大です。 たとえ n と同じ長さまでのそれらのみを生成したとしても、n と効率的に比較するための構造化された方法が必要です。 

微妙なエッジ ケースは、n 自体に 4 と 7 以外の数字が含まれる場合です。たとえば、n = 500 です。正解は、500 の数字パターンに一致するものだけでなく、すべてのラッキー ナンバー ≤ 500 です。n が 4 または 7 を持つ位置のみを考慮する不用意な数字マッチングのアプローチは、アンダーカウントになります。 

もう 1 つのエッジ ケースは、先行動作です。1、4、または 7 のような 1 桁の n です。n = 4 の場合、答えは 1 です。 n = 3 の場合、答えは 0 です。どの桁の DP も、「まだ番号が構築されていない」から「開始された番号」への移行を正しく処理する必要があります。 

## アプローチ

 ブルートフォースのアイデアは、数字 4 と 7 で構成されるすべての数値を昇順に生成し、≤ n である数値をカウントすることです。 これは、|n| までの長さのすべての文字列を再帰的に構築することで実現できます。 そしてそれぞれを文字列としての n と比較します。 すべての有効な数値が 1 回だけ列挙され、n との比較が簡単であるため、これは概念的には正しいです。 

ただし、そのような文字列の数は長さに応じて指数関数的に増加します。 n が 100 桁の場合、その長さだけでも 2^100 の候補文字列が存在します。 候補が n を超えたときに早期に停止しても、ほとんどの候補は大きすぎることがわかる前に生成されるため、漸近的には役に立ちません。 

重要な点は、すべての有効な数値を明示的に生成する必要がないということです。 数値として解釈された場合に、辞書編集上、指定された範囲以下の有効な数字列がいくつあるかを数えるだけで済みます。 これは古典的な数字の動的プログラミング設定です。数値を最上位桁から最下位桁までスキャンし、各位置で、n の接頭辞と一致するか、厳密に小さくなるかを決定します。 

桁セットが固定されており、2 桁のみと非常に小さいため、構造はさらに簡素化されます。 各位置での有効な継続の数は、n に厳密でなくなると、プレフィックス値とは無関係に純粋に 2 の累乗になります。 

2つの部分を組み合わせます。 まず、長さが len(n) より厳密に小さいラッキーナンバーをすべて数えます。 次に、厳密なプレフィックス トラバーサルを使用して、n を超えない同じ長さの幸運な数字を数えます。

 ## アルゴリズムのチュートリアル

 数値を長さ L の文字列 s として扱います。 

### ステップ

1. まず、長さが厳密に L より小さい幸運な数字がいくつ存在するかを計算します。固定長 k の場合、すべての位置には 2 つの選択肢があります: 4 または 7。したがって、そのような数字は 2^k 個あります。 これを 1 から L-1 までの k について合計します。 これにより、自動的に ≤ n となるすべての短い長さの候補が処理されます。 
2. 次に、正確に L の長さの数値を処理します。s を左から右にスキャンし、構築中のプレフィックスがまだ s のプレフィックスと正確に等しい (タイトな条件) か、またはすでに小さいかどうかを示す状態を維持します。 
3. 各位置 i で、タイトであれば、数字 s[i] を許可された数字 4 および 7 と比較します。許可された各数字 d について:

 - d < s[i] の場合、残りの位置の補完は有効であり、2^(L-i-1) に寄与します。 
- d == s[i] の場合、タイト モードで続行します。 
- d > s[i] の場合、プレフィックス制約を超えるためスキップします。 
4. いずれかの位置で 4 も 7 も s[i] に等しくないか、それ以下である場合は、プレフィックスに一致する有効な数値が存在しないため、早期に中断されます。 
5. すべての貢献を 998244353 を法として累積します。 

### なぜ効果があるのか

 このアルゴリズムは、接頭辞制約の不変を維持します。ステップ i では、最初の i 桁が辞書編集的に n の接頭辞以下である接頭辞を形成する数値のみをカウントします。 n の対応する桁よりも小さい桁を選択すると、4 と 7 をどの組み合わせでも数値が n より小さいままであるため、残りのサフィックスは完全に自由になります。 これにより、問題はグローバル比較から 2 のべき乗を使用した独立したサフィックス カウントに軽減されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

def solve():
    t = int(input())
    pow2 = [1] * 105  # enough for length up to 100
    for i in range(1, 105):
        pow2[i] = (pow2[i - 1] * 2) % MOD

    for _ in range(t):
        s = input().strip()
        L = len(s)

        # count all lucky numbers with length < L
        ans = 0
        for k in range(1, L):
            ans = (ans + pow2[k]) % MOD

        # count same-length numbers
        tight = True

        for i in range(L):
            cur = int(s[i])
            for d in (4, 7):
                if d < cur:
                    ans = (ans + pow2[L - i - 1]) % MOD
                elif d == cur:
                    # continue tight only if valid prefix
                    break
            else:
                # if neither 4 nor 7 matched, no tight continuation possible
                tight = False
                break

            if cur not in (4, 7):
                # once prefix mismatch occurs, we stop tight propagation
                pass

        # check if n itself is lucky
        ok = all(c in '47' for c in s)
        if ok:
            ans = (ans + 1) % MOD

        print(ans % MOD)

if __name__ == "__main__":
    solve()
```最初のループは、すべての空きサフィックス位置が 2 つの独立した選択肢に寄与するため、2 の累乗を事前計算します。 最初の合計では、n より短い有効なラッキーナンバーをすべて加算します。 

2 番目の部分では、前方一致の拡張を試みます。 内部ロジックは、数字 4 と 7 との比較を使用して、いつ小さなプレフィックスに分岐できるかを決定します。 選択した数字が厳密に s[i] より小さい場合、残りの接尾辞は完全に自由になり、2 のべき乗が与えられます。 

最後に、分岐時にカウント ロジックは厳密に小さいプレフィックスのみを考慮するため、n 自体が幸運な数字であるかどうかを明示的にチェックします。 

実装の微妙な詳細は、サフィックスの長さが残りの位置に依存するため、100 までの 2 のべき乗を事前に計算する必要があることです。 また、n は非常に大きくなる可能性があるため、整数解析よりも文字列比較の方が優先されます。

 ## 特殊なケース

 トリッキーなケースは、n = 500 など、文字列の最初の方で n に {4, 7} の外側の数字が含まれている場合です。n の対応する数字より小さい数字に達すると、それ以降の数字を必要とせずに、2 の累乗によるすべての接尾辞の組み合わせを直ちに追加するため、アルゴリズムはこれを正しく処理します。 

n = 500 の場合、最初の桁で 4 と 7 を 5 と比較します。桁 4 の方が小さいため、長さ 2 のすべての補完を追加します。これは 2^2 = 4 となります。桁 7 の方が大きく、何も寄与しません。 その後スキャンを続けますが、厳密な継続は正しく残っておらず、残りの数値はすべて分岐ステップですでに考慮されているため、過剰にカウントすることはありません。 

もう 1 つのエッジ ケースは、n 自体が 744 などの有効な幸運な数字である場合です。アルゴリズムは最後に明示的に +1 を追加する必要があります。 これがないと、カウントには厳密に n より小さい数値のみが含まれ、境界解が失われます。
