 ## 解決策
 ## 問題の理解

 私たちは、一連の命令からルート付きツリーを動的に構築し、そのツリー内のノード間の関係に関するクエリに答えるプロセスを効果的に扱っています。 各ノードは、通常は座標によって記述されるグリッド状の構造内の「位置」に対応し、各命令は新しい位置を決定論的な方法で接続することによって構造を拡張します。 

最終的な構造の観点から見ると、ルートを除くすべての位置に親が 1 つだけあるため、結果のグラフはツリーになります。 各クエリは、このツリー内の 2 つのノードの最も低い共通祖先を要求しますが、問題は、ノードが静的な頂点として直接与えられるのではなく、ノードを作成した一連の構築ステップによって暗黙的に定義されることです。 

中心的なタスクは、このツリーを段階的に構築する一連の操作を処理し、結果の構造に対する LCA クエリに答えることです。 

制約 (編集の進行によって暗示されるように) が十分に大きいため、二次構築やクエリごとの線形 LCA では不十分です。 ツリーの構築を明示的にシミュレートし、祖先を登ることによって各クエリに答えると、せいぜい O(nq) が得られますが、n、q が約 2e5 以上に達すると明らかに壊れます。 単純なツリー構築のための O(n²) 前処理であっても、非常に小さなサブタスクでのみ許容されます。 

微妙な問題は、ノードが固定インデックスだけではなく、作成の瞬間を通じて識別され、複数のノードが成長する構造のさまざまな状態に対応することです。 これは、単純な LCA アプローチでも、これらの状態をツリー内の実際の頂点に正しくマッピングする必要があることを意味します。 

いくつかの特殊なケースが自然に発生します。 

問題の 1 つは、クエリ対象の両方のノードが同じルートからリーフへのパス上にある場合です。 この場合、LCA は単にチェーン内の上位ノードです。 分岐構造を想定した単純なアプローチでは、両方のノードを対称的に上方に移動しようとして誤って正解を超えてしまう可能性があります。 

別のエッジケースは、ノードが異なる時間に作成された異なる「ブランチ」に属している場合に発生します。 この状況では、LCA は構築履歴の分岐点に近く、必ずしも最終的な空間位置のみに関連しているわけではありません。 構築順序を無視し、座標のみに依存するソリューションはここで失敗します。 

最後に、ノードは暗黙的な命令によって識別されるため、作成タイミングを追跡せずにツリー全体を再構築するソリューションでは、クエリ エンドポイントとツリー内の実際の位置との間に必要なマッピングが失われます。 

## アプローチ

 ツリーが明示的に構築されれば、総当たりアプローチは簡単です。 すべての命令をシミュレートし、すべてのノードの完全な親配列を構築し、両方のノードが一致するまで 1 つのノードを繰り返し持ち上げることで各 LCA クエリに答えます。 これが機能するのは、すべてのノードに一意の親があるため、上向きに登ると最終的に LCA に収束するためです。 正しさは、ルート付きツリーの祖先の定義からすぐにわかります。 

ただし、トラバースを繰り返すことでコストが発生します。 ツリーの構築には単純な表現では O(n²) がかかる可能性があり、ツリーが長いチェーンに縮退する最悪の場合、各 LCA クエリには O(n) がかかる可能性があります。 q クエリの場合、これは O(nq) になります。n と q の両方が大きい場合、これは遅すぎます。 

重要な洞察は、構築される構造が恣意的ではないということです。 各ノードは特定の命令インデックスに関連付けられており、祖先はこれらの命令シーケンスの共通のプレフィックスに対応します。 ツリーのエッジの観点から考える代わりに、ルートからノードまでのパスが一連の決定をどのようにエンコードするかという観点から考えることができます。 2 つのノードの LCA は、それらの命令履歴の最長の共有プレフィックスになります。

このように問題を再構成すると、ツリー トラバーサルを命令インデックスに対する範囲クエリに置き換えることができます。 LCA 深さは共通プレフィックスの長さに対応し、範囲最小クエリを使用して計算できます。 水平移動や座標コンポーネントなどの追加の属性は、同じ構造に対するプレフィックスの蓄積を使用して再構築できます。 

最後の改善は、命令インデックスをノードに割り当て、そのマッピングを動的に維持する方法を最適化することで実現します。 セグメント ツリーまたは命令レベルにわたるフェンウィック ベースのスイープを使用すると、各ノードがいつ有効になるかを追跡し、対数時間でクエリを効率的に解決できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq + n²) | O(n) | 遅すぎる |
 | 最適 | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各ノードを特定の命令ステップで作成されたものとして解釈し、ノードごとにそれを生成した命令インデックスを保存します。 これにより、問題は構造ツリーのナビゲーションから時間インデックス付きの再構成に変換されます。 
2. クエリ エンドポイントごとに、その作成にどの指示ステップが対応するかを判断するメカニズムを維持します。 これは、フェンウィック ツリーまたはアクティブ ノードのセグメント ベースのシミュレーションと組み合わせた並列二分探索を使用して行われます。 
3. すべてのノードについて、最終構造の一部になったときの命令インデックスを記録します。 これにより、各クエリ エンドポイントに命令タイムライン内の位置が与えられます。 
4. 2 つのノードの LCA を計算するには、それらの命令インデックスを比較し、問題を命令シーケンス内の最も長い共通プレフィックスを見つけることに落とし込みます。 LCA の深さは、このプレフィックスの長さに対応します。 
5. 命令配列に対して範囲最小クエリ構造を使用して、O(log n) の最長の共通プレフィックス長を計算します。 これが機能するのは、セグメントにわたる最小命令値が最も早い分岐点を特定するためです。 
6. LCA の深さがわかったら、そのプレフィックスまでに「右下」タイプの移動が何回発生したかを数えることによって、残りの座標コンポーネントを計算します。 これは、命令シーケンスに対するフェンウィック ツリーを使用して維持できます。 
7. プレフィックス長と累積方向カウントを組み合わせて各クエリに答え、正確な LCA ノードを再構築します。 

機能する理由: この構造により、すべてのノードが命令シーケンスの一意のプレフィックスに対応することが保証されます。 2 つのノードは、命令履歴が一致するプレフィックス上で正確に祖先を共有します。 最初の分岐点は、ツリー内の分岐点を定義します。 深さと横方向の位置は両方ともこの共有プレフィックスの関数であるため、LCA 計算をプレフィックス クエリに減らすことで、明示的なツリー トラバーサルを回避しながら正確さを維持します。

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

完全なソリューションで最もデリケートな部分は、ノードの作成時間がすべてのクエリにわたって一貫して計算されるようにすることです。 マッピング命令インデックスにおけるオフバイワンの間違いは、プレフィックス比較がシフトされるため、LCA の正確さに直接影響します。

 ## 特殊なケース

 連続した命令ステップで 2 つのノードが作成される場合、重大なエッジ ケースが発生します。 そのような状況では、LCA は非常に浅く、多くの場合、根元にあります。 命令インデックスが最初の位置で異なるため、アルゴリズムはこれを処理します。そのため、最長の共通プレフィックスはすぐに折りたたまれます。 

もう 1 つのエッジ ケースは、あるノードが別のノードの祖先である場合です。 この場合、祖先の命令シーケンスは子孫の完全なプレフィックスになります。 一定期間にわたる RMQ は祖先の完全な深さを返し、LCA が祖先自体として正しく識別されることを保証します。 

最後に、すべてのノードが単一のパス上にある場合、すべてのクエリは最小深さのエンドポイントを選択することになります。 プレフィックスベースの解釈は自然に単純な比較に退化し、追加の分岐ロジックなしで正確さを維持します。
