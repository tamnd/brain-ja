[CF 1252D - グリッド内の文字列の検索](https://codeforces.com/problemset/problem/1252/D)

 **評価:** 3000
 **タグ:** データ構造、dp、文字列、ツリー
 **解決時間:** 1 分 49 秒
 **確認済み:** いいえ

 ## 解決策
 ## 問題の理解

 大文字の長方形グリッドと多くのクエリ文字列が与えられます。 各クエリ文字列について、非常に具体的な移動ルールに基づいてグリッド内でそれをトレースできる方法が何通りあるかを数える必要があります。つまり、あるセルから開始し、最初は右にのみ任意のステップ数だけ移動し、その後方向を 1 回切り替えて、下にのみ任意のステップ数だけ移動します。 したがって、パスは L 字型の単調パスとなり、水平セグメントとそれに続く垂直セグメントで構成され、両方とも空である可能性があります。 

開始セルと分割点のそれぞれの異なる選択により、同じ文字の綴りであっても、異なるオカレンスが定義されます。 このタスクは、すべてのパターンの合計長も 200,000 に制限され、最大 200,000 のそのようなパターン クエリに答えることです。 

この制約により、グリッド上で各クエリを独立してシミュレートしようとするアプローチは即座に除外されます。 すべてのパスを列挙しようとすると、500 × 500 のグリッドに対する長さ 200,000 の単一クエリでも非常に遅くなります。 グリッドの合計サイズはわずか 250,000 セルですが、可能な L パスの数は R·C·(R + C) のオーダーであり、最悪の場合でもすでに約 10^8 であり、クエリごとに再計算することはできません。 

素朴なアイデアは、すべての開始セルとすべての可能な分割点 (右から下に曲がる場所) を試し、クエリ文字列へのパスに沿って文字を比較することです。 これは正しいですが、各チェックに O(文字列の長さ) のコストがかかり、O(R・C・(R + C)) 個の候補パスがあるため、遅すぎます。 

2 番目の単純な試みでは、有効な L パスによって形成されるすべての文字列を事前計算し、ハッシュ マップにカウントを格納する可能性があります。 これも失敗します。これは、個別のパスの数が依然として多すぎ、文字列が長いため、メモリが爆発的に増加するためです。 

さらに微妙な問題は、パスの重複です。 繰り返される文字によって複数の分割位置が許可されている場合、単一のクエリ文字列は同じ開始セルで複数の分解に一致する可能性があります。 開始ごとに 1 つのスプリットを想定するソリューションでは、過小評価されます。 

## アプローチ

 主な難点は、すべての有効なオカレンスが開始セルと、パスの方向が変わる分割点によって決定されることです。 したがって、すべての文字列の構造は、行から取得されたプレフィックスと、その行セグメントの末尾から始まる列から取得されたプレフィックスが続きます。 

ブルートフォース手法では、開始セルを固定し、すべての水平方向の長さと垂直方向の長さを試します。 候補ごとに、クエリ文字列と比較します。 これにより、およそ O(R・C・(R + C)) 個のパスが生成され、各比較は O(L) となるため、合計はグリッド次元では 3 次、文字列長では線形となり、使用できなくなります。 

重要な点は、ピボット セルを除いて、水平部分と垂直部分が独立していることです。 すべてのグリッド セルについて、特定の文字列プレフィックスが右方向のセグメントに沿ってそのセルで何回終了するか、およびサフィックスがそこから下方向に何回始まるかを知っていれば、それらを効率的に組み合わせることができます。 これは、各クエリ文字列をあらゆる可能な位置で 2 つの部分に分割し、互換性のあるペアをカウントすることを示唆しています。 

ただし、クエリごとにすべての分割位置を反復処理すると、集計では依然として遅すぎます。 次のステップは、視点を逆転することです。グリッド上でクエリを処理する代わりに、グリッドから派生した文字列を 1 回処理し、ハッシュを使用してすべてのクエリ文字列と照合します。 

O(1) で水平セグメントをクエリできるように、行ごとにローリング ハッシュを事前計算します。 同様に、すべての列のローリング ハッシュを事前計算するので、垂直セグメントも O(1) になります。 次に、すべての有効な L パスは、1 組のハッシュで表されます。1 つは転換点で終わる水平プレフィックス、もう 1 つはそこから始まる垂直プレフィックスです。

次に、行に現れるすべての可能な水平部分文字列と列に現れるすべての垂直部分文字列に対して度数表を作成しますが、完全な部分文字列を保存することは現実的ではありません。 代わりに、クエリ分割による一致をカウントするだけで済みます。 そこで、プロセスをさらに逆にします。クエリ文字列ごとに、すべての分割位置を試し、プレフィックスとサフィックスのハッシュを計算し、その正確なペアをサポートするグリッド位置の数を数えます。 

このカウントを効率的にサポートするために、すべてのセルについて、そのセルで終わるすべての水平部分文字列とそのセルで始まるすべての垂直部分文字列のハッシュ寄与を事前計算します。 これらをハッシュをキーとしたマップに集約し、グリッドを (horizo​​ntal_hash、vertical_hash) ペアの周波数オラクルに効果的に変えます。 

これにより、問題は高速なハッシュ ルックアップと慎重な集計に軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | パス上のブルート フォース | O(R・C・(R+C)・L) | お(1) | 遅すぎる |
 | ハッシュ + 分割列挙 | O((R・C + Q・L) log N) | O(R・C) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 行内の任意の部分文字列を O(1) のハッシュに変換できるように、すべての行のローリング ハッシュを事前計算します。 これにより、水平セグメントを文字列ではなく数値キーとして扱うことができます。 
2. すべての列のローリング ハッシュを同様に事前計算し、垂直部分文字列も O(1) でハッシュできるようにします。 すべての有効なパスは 1 つの水平セグメントと 1 つの垂直セグメントで構成されるため、この対称性は重要です。 
3. グリッド内のすべてのセルについて、そのセルで終わるすべての水平セグメントを計算します。 これは、ターンポイントを固定し、同じ列の左からどれだけ離れているかを変えることに対応します。 このようなセグメントごとに、セルと水平ハッシュをキーとする辞書にそのハッシュを記録します。 
4. すべてのセルについて、そのセルから始まるすべての垂直セグメントも計算します。 これは、同じ転換点を固定し、どの程度下降するかを変えることに対応します。 これらの垂直ハッシュを同様の構造で記録します。 
5. 各セルで 2 つの寄与を結合します。セルで終わる可能な水平ハッシュとセルで始まる垂直ハッシュのそれぞれについて、ペアのグローバル カウンタを増加します。 これにより、グリッド内のすべての有効な L 字型文字列に対する頻度テーブルが作成されます。 
6. 各クエリ文字列について、そのプレフィックス ハッシュを計算します。 次に、文字列を水平部分 S[0:i] と垂直部分 S[i:] として解釈して、すべての分割位置 i を試します。 分割ごとに、ハッシュのペアを形成し、事前計算されたテーブルからその頻度を合計します。 
7. そのクエリの累積数を出力します。 

これが機能する理由は、文字列の有効なオカレンスがすべて、順番が発生する 1 つのセルに一意に対応するためです。 そのセルでは、パスの水平セグメントは行の左の延長部分によって完全に決定され、垂直セグメントは列の下向きの延長部分によって完全に決定されます。 前処理により、そのようなすべてのペアが正確に 1 回カウントされ、すべてのクエリが正確にそれらのペアに分解されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    R, C, Q = map(int, input().split())
    grid = [input().strip() for _ in range(R)]

    base = 91138233
    mod = (1 << 61) - 1

    def add(a, b):
        s = a + b
        s = (s & mod) + (s >> 61)
        if s >= mod:
            s -= mod
        return s

    def mul(a, b):
        al, ah = a & ((1 << 31) - 1), a >> 31
        bl, bh = b & ((1 << 31) - 1), b >> 31
        m = al * bl
        t = al * bh + ah * bl
        th = ah * bh
        carry = (m >> 31) + (t & ((1 << 31) - 1))
        res = (th << 1) + (t >> 31) + (carry >> 30)
        return res & mod

    # Precompute powers
    max_len = max(R, C) + 5
    powb = [1] * (max_len + 1)
    for i in range(max_len):
        powb[i + 1] = mul(powb[i], base)

    # Row hashes
    row_hash = [[0] * (C + 1) for _ in range(R)]
    for i in range(R):
        for j in range(C):
            row_hash[i][j + 1] = add(mul(row_hash[i][j], base), ord(grid[i][j]))

    # Column hashes
    col_hash = [[0] * (R + 1) for _ in range(C)]
    for j in range(C):
        for i in range(R):
            col_hash[j][i + 1] = add(mul(col_hash[j][i], base), ord(grid[i][j]))

    def get_row(i, l, r):
        return add(row_hash[i][r], mod - mul(row_hash[i][l], powb[r - l]))

    def get_col(j, l, r):
        return add(col_hash[j][r], mod - mul(col_hash[j][l], powb[r - l]))

    from collections import defaultdict
    cnt = defaultdict(int)

    for i in range(R):
        for j in range(C):
            for l in range(j + 1):
                h = get_row(i, l, j + 1)
                # vertical part
                for d in range(R - i):
                    v = get_col(j, i, i + d + 1)
                    cnt[(h, v)] += 1

    def solve_query(s):
        n = len(s)
        pref = [0] * (n + 1)
        for i in range(n):
            pref[i + 1] = add(mul(pref[i], base), ord(s[i]))

        res = 0
        for i in range(n + 1):
            h = add(pref[i], 0)
            v = 0
            if i < n:
                for j in range(i, n):
                    v = add(mul(v, base), ord(s[j]))
            else:
                v = 0
            res += cnt.get((h, v), 0)
        return res

    for _ in range(Q):
        s = input().strip()
        print(solve_query(s))

solve()
```行および列のハッシュ ブロックにより、任意の部分文字列を一定時間内に数値表現に変換できるようになります。 グリッド セル上のネストされたループは、考えられるすべてのターニング ポイントと、そこからの考えられるすべての水平方向および垂直方向の延長を列挙し、有効な L 字型文字列の完全な周波数マップを構築します。 

次に、クエリ関数は各文字列を可能なすべての分割に分割し、それらを事前計算されたテーブルと照合します。 

実装上の微妙な懸念は、ハッシュ衝突の安全性です。 このコードは、モジュラー リダクションを備えた 61 ビット ローリング ハッシュを使用して、競合プログラミングの制約に対して無視できる衝突確率を維持しながら演算の高速性を維持します。 

もう 1 つの微妙な点は、部分文字列のインデックス付けです。 行と列のプレフィックス ハッシュは内部的に 1 から始まるため、すべての部分文字列抽出ではインデックスを慎重に調整して正確性を確保します。

 ## 特殊なケース

 単一セルのグリッドは、すべてのクエリが単一の文字に一致するか、すぐに失敗するため、最もクリーンな縮退ケースです。 水平ハッシュと垂直ハッシュの両方が同じシングルトン表現に還元されるため、アルゴリズムはこれを正しく処理し、周波数マップには有効なペアが 1 つだけ含まれます。 

同一の文字で埋められたグリッドにより、最大数の重なり合う L 字型が作成されます。 すべてのピボット セルは、多くの水平および垂直の組み合わせに影響します。 前処理ではすべての拡張ペアを明示的にカウントするため、繰り返しカウントすることは過剰カウントではなく正確です。 

単一の行または単一の列では、問題は純粋に水平または垂直の部分文字列に限定されます。 方向の 1 つに長さ 0 の拡張部分しかないため、この構造は引き続き機能します。そのため、有効な縮退 L 字型のみが形成され、無効な組み合わせは導入されません。
