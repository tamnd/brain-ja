 ## 解決策
 ## 問題の理解

 この問題は、一定期間動作中にエネルギーを消費するデバイスについて説明していますが、1 分あたりのコストは、料金プランがアクティブになっている時間帯によって異なります。 料金体系は 2 つあり、それぞれ 1 分あたりの料金と適用される日中の時間間隔によって定義されます。 その期間外では、他の料金が適用されます。 

デバイスの開始時間、合計実行時間 (分単位)、およびそれぞれの料金レートを含む 2 つの料金表が与えられます。 タスクは、デバイスの実行にかかる総コストを計算することであり、その特定の瞬間に有効な料金に従って、1 分ごとにリアルタイムで課金されます。 

重要な隠された構造は、すべてが 1440 分の円形のタイムラインで発生し、丸 1 日を表すということです。 時間が午前 0 時を過ぎると、時間が終了し、料金の適用は周期的に継続します。 

単純な間違いは、料金間隔が午前 0 時を超えるとすぐに現れます。 たとえば、料金表が 22:00 から 06:00 まで有効な場合、間隔が日の境界をまたがって分割されるため、「開始 ≤ t < 終了」のような直接比較は失敗します。 もう 1 つの微妙な障害モードは、特にデバイスが複数日にまたがって稼働する場合に、時間と分の計算とモジュラー ラップアラウンドを誤って混合することによって発生します。 

もう 1 つの問題は、最終コストのオーバーフローです。 中程度に見える境界でも 10^18 に近い値になる可能性があるため、中間計算は 64 ビット整数で格納する必要があります。 

## アプローチ

 この問題を考える最も簡単な方法は、デバイスを分ごとにシミュレートすることです。 動作が 1 分ごとに、現在の絶対時間を 1 日の分の値に変換し、それが安い料金プランまたは高い料金プランの範囲内にあるかどうかを確認します。 それに応じてコストを積み上げていきます。 

これが機能するのは、問題が本質的に離散的であり、時間が分単位で測定されるため、直接の反復が定義と正確に一致するためです。 ただし、デバイスが k 分間動作する場合、k 回のチェックと k 個のモジュラー算術演算が必要になります。 kが大きいと遅くなりすぎます。 

重要な点は、実際には毎分を個別に検査する必要はないということです。 料金は、料金間隔が何分に該当するかによってのみ決まります。 2 つの時間セグメント間の重複の合計を計算できれば、単純な加重合計から直接答えが得られます。 これにより、問題は分単位のシミュレーションから循環領域にわたる間隔演算に移行します。 

このように理解すると、タスクは、長さ k のセグメント内の整数点が 1440 分サイクルの周期間隔内にいくつ入るかをカウントするようになります。 これは、最大 2 つの部分的な日の断片と、その間の丸一日に分解できます。

 ## アルゴリズムのチュートリアル

 まず、すべての時間表現を単一の分単位の線形スケールに変換します。 時と分で指定された各時刻は、[0, 1440) の値になります。 これにより、時分計算を繰り返す必要がなくなり、比較が簡単になります。 

次に、料金間隔が一貫した形式で表現されていることを確認します。 間隔が午前 0 時を超えない場合、それはすでに標準セグメント [t1、t2) です。 真夜中をまたぐ場合は、2 つの料金表の役割を交換して、常に 1 つの線形日表現内に収まるきれいな間隔で作業できるようにします。 

正規化後、デバイスの実行時間が料金間隔内に何分含まれるかを計算します。 反復する代わりに、ランタイムを 3 つの部分に分割しました。開始時刻から午前 0 時までの最初の部分的な 1 日、数日間の丸一日、および最後の部分的な 1 日です。

部分日セグメントごとに、区間交差ロジックを使用して料金区間との重複を計算します。 任意のセグメント [b, e) について、[t1, t2) との重複は max(0, min(e, t2) − max(b, t1)) です。 これは、両方の間隔が線形で 1 日以内に制限されているため、機能します。 

丸 1 日は一定量を寄与します。つまり、1440 分のサイクルごとに、正確に (t2 − t1) 分の料金使用量が寄与します。 

最後に、最初の部分日、丸一日、および最後の部分日からの寄与を組み合わせて、合計料金分数 Tp を取得します。 次に、答えは Tp * p + (k − Tp) * q として計算され、重み係数 w が乗算されます。 

### なぜ効果があるのか

 常に 1 つのタリフがアクティブになり、コストは現在の分が固定された周期セット内にあるかどうかによってのみ決まります。 時間を日の境界に合わせて互いに素なセグメントに分解することにより、実行時間のすべての分が 1 回だけ計算され、各セグメントの寄与は純粋な間隔の重複によって計算されます。 セグメンテーションによりランタイム全体が分割されるため、分が二重にカウントされたり、取り逃されたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

D = 24 * 60

def intersect(b, e, l, r):
    left = max(b, l)
    right = min(e, r)
    return max(0, right - left)

def solve():
    h1, m1 = map(int, input().split())
    h2, m2 = map(int, input().split())
    s, u = map(int, input().split())
    k = int(input())
    p, q, w = map(int, input().split())

    t1 = h1 * 60 + m1
    t2 = h2 * 60 + m2
    ts = s * 60 + u
    tf = ts + k

    if t1 > t2:
        t1, t2 = t2, t1
        p, q = q, p

    Tp = 0

    if tf <= D:
        Tp = intersect(ts, tf, t1, t2)
    else:
        Tp += intersect(ts, D, t1, t2)

        rem = k - (D - ts)
        full = rem // D
        Tp += full * (t2 - t1)

        rem %= D
        Tp += intersect(0, rem, t1, t2)

    Tq = k - Tp
    ans = w * (Tp * p + Tq * q)
    print(ans)

if __name__ == "__main__":
    solve()
```解決策は、すべての時間を分に正規化することから始まります。 機能`intersect`は、中心となる幾何学的なアイデアをエンコードしています。つまり、直線上の 2 つのセグメント間の重なりは、端点の交差によって決まります。 

正規化ステップの交換`(t1, t2)`そして`(p, q)`料金間隔を常に単一の連続したブロックとして扱うことを保証します。 これにより、ラップアラウンド ケースを個別に処理する必要がなくなります。 

計算ではランタイムが最大 3 つの部分に分割され、各部分で同じ交差ロジックが使用されます。 1 日分の寄与分は 1440 分ごとに同じように繰り返されるため、個別に処理され、直接乗算することができます。 

丸一日経過すると残り時間がゼロになる場合があるので注意が必要です。 また、最大 10^6 の範囲の乗算は 32 ビットの制限を超える可能性があるため、すべての算術演算では 64 ビット整数を使用する必要があります。

 | 最後のセグメント | 0 | 160 | 交差 = 0 |

 最初のセグメントは 1000 から 1200 まで重複しており、200 分の料金プランが発生します。 残りは何も貢献しません。 これにより、アルゴリズムが 1 日以内のラップアラウンドを正しく処理していることが確認できます。 

次に、複数日の実行を考えます。1000 から開始、k = 2000、料金 [900, 1200)。 

| フェーズ | 開始 | 終わり | 貢献 |
 | --- | --- | --- | --- |
 | 最初のセグメント | 1000 | 1440 | 200 |
 | 丸一日 | 丸 1 日 | | 300 |
 | 最後のセグメント | 0 | 560 | 200 |

 最初の日は 200 を寄与し、全日は 300 を寄与し、最後の半日は 200 を寄与し、サイクル全体で一貫した蓄積が得られます。 これは、周期的な繰り返しが正しく処理されていることを示しています。

 ## 特殊なケース

 重要なエッジケースは、料金間隔が午前 0 時を超える場合です。 t1 = 22:00 (1320)、t2 = 06:00 (360) と仮定します。 t1 > t2 であるため、単純チェックは失敗します。 交換後、間隔を回転軸上の連続セグメントとして正しく再解釈し、オーバーラップ ロジックが有効なままであることを確認します。 

別のエッジ ケースは、デバイスが 1 日の終わり近くに起動したときに発生します。 ts = 1400 および k = 200 の場合、実行時間は午前 0 時まで続きます。 アルゴリズムはこれを [1400, 1440) に分割し、次に [0, 200 − 40)] に分割します。 各部分は独立して処理され、完全なサイクルは乗算によって処理されるため、重複や分単位の損失は発生しません。 

最後のエッジケースは、k が非常に大きい場合です。 直接シミュレーションは実行不可能ですが、分解により問題が一定数の算術演算に軽減されるため、規模に関係なくパフォーマンスが安定します。
