 ## 解決策
 ## 問題の理解

 2 人の学生が一連の問題を次々と解決します。 ケシャは問題ごとに一定の時間を費やします。$t_k$、そしてメレンティは費やします$t_m$。 両方とも同じ瞬間に開始し、「散歩に行く」と呼ばれる決定の瞬間まで継続的に作業します。 

この決定の瞬間が起こる可能性は 2 つあります。 1 つ目は、両方の生徒がたまたま同じ時間境界で問題を終了した場合です。 各完了は周期的に発生するため、それらの同時完了はステップ時間の公倍数で発生します。 2 つ目は、どちらかがすべてを完了したときです$n$問題が発生した後、対話が変化します。終了した生徒は、それぞれの終了時点で効果的に休憩を「呼びかけ」続けますが、もう一方の生徒は、自分の終了時間にのみ応答できます。 これにより、遅い生徒のスケジュールに合わせて次の瞬間まで遅れが生じます。 

タスクは、散歩が始まる最も早い瞬間を計算し、その時点までに各生徒が完了した問題の数を決定することです。$n$。 

入力は 3 つの整数で構成されます: 問題の数$n$、および問題ごとの時間$t_k$そして$t_m$。 出力は、散歩の開始時に Kesha と Melentiy が解決した問題の数を表す 2 つの整数です。 

このプロセスはダイナミックに聞こえますが、すべては周期構造によって完全に決定されます。 各生徒の進歩は時間の経過とともに線形であるため、有効な答えは、最小公倍数に基づく同期の瞬間、および 1 人の生徒が到達した時点の境界調整された瞬間など、少数の候補タイムスタンプのセットから導き出される必要があります。$n$問題が発生し、もう一方は次の互換性のある完了時に反応します。 

単純なシミュレーションでは、時間をかけてステップを実行し、停止条件が満たされるまで両方のカウンターを増加させます。 イベントの数が膨大になるため、このアプローチは遅すぎます。$n$到達できる$10^9$またはそれ以上。 

エッジケースは、同期が行われる前に 1 人の生徒がすべての問題を完了した場合に発生します。 たとえば、次の場合$t_k \ll t_m$、ケシャはすべてを終えるかもしれない$n$Melentiy が共有境界の十分な作業を完了するずっと前に、問題が発生しました。 単純な「第一公倍数」アプローチはこれを無視し、誤って答えをはるか先の未来に押し込んでしまいます。 もう 1 つのエッジケースは次のような場合です$t_k = t_m$、同期はすべてのステップで発生しますが、上限は$n$引き続き施行しなければなりません。 

## アプローチ

 直接シミュレーションでは時間を離散として扱い、どちらかの生徒の次の完了イベントに繰り返し進みます。 各ステップでは、時間が次の倍数に増加します。$t_k$または$t_m$を実行し、散歩に行くための両方の条件が満たされているかどうかを確認します。 これは実際のプロセスを反映しているため正しいですが、答えに到達するまでのイベントの数は次の値に比例する可能性があります。$n$、各遷移は一定の作業であるため、大きな制約に対しては遅すぎます。 

重要な構造観察は、システムが周期的であるということです。 制限を無視する$n$、両方の生徒が同時に問題を完了するのは、次の倍数だけです。$\mathrm{lcm}(t_k, t_m)$。 これにより、無限の相互作用が単純な等差数列に縮小されます。 ただし、有限の上限は、$n$切り捨ての導入: 時間の経過後$n \cdot t_k$または$n \cdot t_m$、生徒は進歩を停止し、純粋な周期性が壊れます。 

したがって、解決策は 2 つの体制の組み合わせになります。 どちらかの生徒がすべての問題を終える前に、答えは次の倍数でなければなりません。$\mathrm{lcm}(t_k, t_m)$。 1 人の生徒が終了した後、他の生徒の完了グリッドを早い生徒の終了時間に合わせることで、答えが決定されます。 私たちは両方の体制を評価し、最も早い有効な瞬間を採用します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | シミュレーション |$O(n)$|$O(1)$| 遅すぎる |
 | 算術 (LCM + 境界調整) |$O(\log \min(t_k,t_m))$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 2 つの独立したメカニズムから候補モーメントを構築し、最も早いものを選択します。 

1. 次の最小公倍数を計算します。$t_k$そして$t_m$。 これは、両方の生徒が無制限のプロセスで同時に問題を完了する基本サイクルを表します。 gcd 関係を使用して取得します。$\mathrm{lcm}(a,b) = a \cdot b / \gcd(a,b)$。 
2. ケシャがすべての問題を完了する時間を計算します。$T_k = n \cdot t_k$、同様に$T_m = n \cdot t_m$。 これらは、周期的な動作が変化する切り捨てポイントです。 
3. どちらかが終了する前に、同期イベントを検討します。 意味のある最も早い同期は、次の最小の倍数です。$\mathrm{lcm}(t_k, t_m)$これは少なくとも時間ゼロですが、純粋に周期的な動作が必要な場合は、両方の生徒が最終問題に到達する前に発生する瞬間のみを保持します。 実際には、最初の候補を lcm の最初の倍数とみなして、それが有効な解決ウィンドウ内にあるかどうかを推論します。 
4. ケシャが最初に終了した場合を処理します。つまり、$T_k \le T_m$。 時間に$T_k$, ケーシャはすでに待っているかもしれません。 Melentiy は自分の完了時間にのみ応答できるため、実際の会議は最小の倍数で行われます。$t_m$それは以上です$T_k$。 
5. Kesha の完了グリッドを$T_m$。 
6. すべての候補時間 (最良の同期時間と 2 つの境界駆動時間) を比較し、最小のものを選択します。 
7. 最後にもう一度$T$が決定されたら、各生徒が解いた問題の数を次のように計算します。$\min(n, T // t_k)$そして$\min(n, T // t_m)$。 

### なぜ効果があるのか

 状態は完了境界でのみ変化するため、歩行の可能性のあるすべての瞬間は、少なくとも 1 人の生徒が問題を完了する時間と一致する必要があります。 どちらかの生徒がすべてを終える前に$n$問題がある場合、同時完了は正確に LCM の倍数によって特徴付けられます。 1 人の生徒が進歩を止めると、システムは 1 つの算術グリッドに縮小され、次に実行可能な対話は終了時点の後のそのグリッド上の次の倍数になります。 これにより、構造的に異なるケースがすべて網羅されるため、他の候補時間は存在しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import math

def solve():
    n, tk, tm = map(int, input().split())

    def lcm(a, b):
        return a // math.gcd(a, b) * b

    L = lcm(tk, tm)

    Tk = n * tk
    Tm = n * tm

    # candidate 1: first synchronization after start, but capped by both still running
    t_sync = L

    # candidate 2: Kesha finishes first, align to tm
    t_k = ((Tk + tm - 1) // tm) * tm

    # candidate 3: Melentiy finishes first, align to tk
    t_m = ((Tm + tk - 1) // tk) * tk

    t = min(t_sync, t_k, t_m)

    print(min(n, t // tk), min(n, t // tm))

if __name__ == "__main__":
    solve()
```コードは、すべてのジョイント完了動作のバックボーンである LCM を計算することから始まります。 次に、両方の生徒が目標地点に到達したときの正確な終了時間を計算します。$n$- 番目の問題。 

表現`((Tk + tm - 1) // tm) * tm`そしてその対称的な対応者は、他の生徒の完了グリッドに天井分割を実装します。 これは、「次の解決可能な問題の境界まで待つ」ことをモデル化する個別の調整ステップです。 

最後に、応答時間は同期および境界調整の候補の最小値であり、解決された問題の数は整数除算によって導出され、上限は です。$n$。 

微妙な点は、完了前の同期が完了ベースのイベントよりも早く発生する可能性があるため、1 人の生徒の方が速い場合でも、すべての候補タイムを考慮する必要があることです。 

## 実用的な例

 ### 例 1

 しましょう$n = 3$、$t_k = 2$、$t_m = 3$。 

2 と 3 の最小公倍数は 6 です。したがって、結合完了は時間 6 で発生します。 

Kesha はタイム 6 で終了し、Melentiy はタイム 9 で終了します。 

次に、境界の位置合わせを計算します。 Kesha は 6 で終了しますが、6 は 3 で割り切れるため、Melentiy は 6 で応答できます。$t_k = 6$。 同様に、Melentiy は 9 で終了し、Kesha は 10 で応答しますか? 実際には、9 の次の 2 の倍数は 10 なので、$t_m = 10$。 

最低 6、6、10 を取得します。$T = 6$。 

| 時間候補 | 値 |
 | --- | --- |
 | LCM同期 | 6 |
 | ケシャはアライメントを終了します | 6 |
 | メレンティ仕上げ調整 | 10 |
 | 最終回 | 6 |

 時間6で、ケシャは解決しました$6 // 2 = 3$問題とMelentiが解決しました$6 // 3 = 2$。 

### 例 2

 しましょう$n = 4$、$t_k = 1$、$t_m = 5$。 

LCMは5です。同期候補は5です。 

ケシャは4位、メレンティは20位でフィニッシュ。 

ケシャが 4 で終了すると、次の 5 の倍数は 5 です。 

したがって、候補者は 5、5、20 となり、最終的には 5 となります。 

| 時間候補 | 値 |
 | --- | --- |
 | LCM同期 | 5 |
 | ケシャはアライメントを終了します | 5 |
 | メレンティ仕上げ調整 | 20 |
 | 最終回 | 5 |

 時間 5 で、Kesha は 4 つの問題 (n が上限) を解決し、Melentiy は 1 つの問題を解決しました。 

これらの例は、同期が早期に存在する場合でも、実現可能な会議時間が短縮されない限り、境界効果によって同期が無効にならないことを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(\log \min(t_k, t_m))$| gcd 計算が大部分を占める |
 | スペース |$O(1)$| 少数の整数のみが保存されます。 

このソリューションは線形シミュレーションを定数時間の算術演算に置き換えるため、制約に簡単に適合します。

 ## 特殊なケース

 いつ$t_k = t_m$、あらゆる瞬間が同期ポイントですが、答えは依然として次の制約を受けます。$n$。 LCM がステップ自体に等しいため、アルゴリズムはこれを処理します。また、両方の境界調整も自然な終了時間を超えない倍数に解決されるため、最小値は常に一貫しています。 

たとえば、ある生徒の方がはるかに速い場合、$t_k = 1$そして$t_m = 10^9$, ケーシャはすべての問題を非常に早く終わらせます。 このアルゴリズムは、遅すぎる LCM 同期に誤って依存するのではなく、Melentiy の次の倍数によって相互作用が決定される「フィニッシュファースト」方式に正しく切り替わります。 

いつ$n = 1$、両方の学生が最初のステップを効果的に完了し、すべての受験者が最小のステップに崩壊します。$t_k$、$t_m$、 そして$\mathrm{lcm}(t_k, t_m)$。 すべての式が特別なケースを使用せずに最初のステップの比較に明確に変換されるため、実装は引き続き正しく動作します。
