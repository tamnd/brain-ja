 ## 解決策
 ## 問題の理解

 私たちには、さまざまな現場から届く作業依頼を説明するイベントの時系列の流れと、現場間を移動し、訪問する各現場で一定の日数をかけて作業する 1 台の掘削機が与えられます。 

各リクエストは、サイト インデックスとそのリクエストが表示される日に関連付けられます。 また、掘削機は離散時間で動作し、現場を順番に前進し、現場に到着すると、正確に一定時間そこに留まり、その時点までにどのリクエストがすでに現れているかに応じてさらに移動する可能性があります。 

重要な相互作用は、リクエストが時間の経過とともに蓄積されることですが、掘削機の動きは、現在の作業間隔が終了するまでに表示される最新のリクエストに依存するということです。 これにより、時間の進行と空間の進行の間にカップリングが作成されます。各段階で、現在の時間枠ですでに「表示」されているすべてのリクエストの間で掘削機の位置を可能な限り拡張します。 

出力には、掘削機がサイト間で効果的に「ジャンプ」した距離を時間の経過とともに追跡し、これらのジャンプに関する統計、具体的にはジャンプの最大距離と、この最大値に達するジャンプに寄与した合計日数を蓄積する必要があります。 

複雑さの観点から見ると、入力は順序付けされているため、並べ替えは不要です。 この制約は、毎日多くのイベントを前方にスキャンする必要がある可能性があるため、タイムラインが大きい場合は日ごとにシミュレーションできないことを意味します。 単純なシミュレーションでは、最悪の場合、各サイトでイベント リストの再スキャンが繰り返され、二次的な動作に低下します。 

重要な点は、掘削機の 1 回のインターバル中に複数のリクエストが同時に関連する可能性があり、次の移動の決定が行われる前にそれらのリクエストをすべて吸収する必要があることです。 もう 1 つのエッジ ケースは、掘削機が現場を終了する境界日に正確にリクエストが到着する場合です。これは、そのリクエストが現在のセグメントに属するか次のセグメントに属するかに影響します。 

単純な処理による最小限の失敗シナリオは次のとおりです。 

入力:```
2 2
1 1
2 2
```2 番目のリクエストをサイト 1 の完了後の厳密に次のフェーズに属するものとして誤って処理すると、計算されたジャンプ タイミングが 1 日ずれてしまい、不正確な継続時間の累積が発生します。 

もう 1 つの微妙なケースは、移動が完了する前に複数のリクエストが発生した場合に発生します。```
3 5
1 1
2 2
3 3
```単純な 1 日あたりのシミュレーションでは、進行が遅すぎる可能性があり、すでに消費されたイベントを繰り返し再処理することになります。 

## アプローチ

 この強引なアイデアは、時間を明示的にシミュレートすることです。 毎日、新しいリクエストが表示されるかどうかを確認し、これまでに確認されたすべてのリクエストに基づいて最も遠い到達可能なサイトを更新し、サイト間で掘削機を段階的に移動させます。 移動するたびに、その瞬間までに発生したすべてのリクエストのスキャンがトリガーされ、現在のセグメントをどこまで拡張できるかを確認します。 

これは、問題で説明されているプロセスを直接模倣しているため、正しく機能します。 ただし、サイトが移行するたびに、増加するイベントのプレフィックスを再スキャンする必要がある場合があります。 n 個のイベントがあり、掘削機が O(n) 回移動する場合、合計の複雑さは O(n²) になり、大きな入力に対しては遅すぎます。 

重要な洞察は、リクエストがすでに時間によってソートされており、掘削機の作業間隔が固定されると、時間がその間隔内にあるすべてのリクエストを 1 回の前方スイープで消費できるということです。 各リクエストは、リスト内でポインターを進めるときに最大 1 回処理されます。 これは当然、2 ポインターまたは線形スイープ戦略につながります。1 つのポインターは現在のリクエスト インデックスを追跡し、もう 1 つは掘削機の現在のタイム ウィンドウ エンドポイントを追跡します。 

過去のリクエストを繰り返しスキャンするのではなく、リクエストを単調に進めて、各イベントが 1 回だけ処理されるようにします。 次に、空間的な移動は、次の遷移までに時間ウィンドウがどれだけ伸びるかから導出されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適な 2 つのポインタ | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちはリクエストに対するポインタを維持し、掘削機が現在の連続作業間隔をどこまで延長できるかをシミュレーションします。 

1. すべてのリクエストを配列に読み取ることから始めます。リクエストはすでに時系列で与えられているため、日ごとの順序を維持します。 また、各リクエストのサイト インデックスと到着日も追跡します。 
2. ポインタを初期化する`i`最初のリクエストで。 これは、現在の掘削機セグメントを拡張する可能性がある最も古い未処理のリクエストを表します。 
3. 各セグメントについて、まだ処理されていない最も早いリクエストに基づいて、掘削機の現在のサイトと開始時刻を設定します。 
4. 現在の作業間隔の終了を次のように定義します。`current_day + k - 1`、掘削機は各現場にちょうど k 日間滞在するためです。 この境界により、このセグメント中にどのリクエストが表示されるかが決まります。 
5. 次のリクエストの到着時間が現在の間隔終了時間以下である間に、ポインタを進め、これまでに到達した最も遠いサイト インデックスを更新します。 このようなすべてのリクエストは、個別ではなく 1 つのバッチで掘削機の動作をどこまで拡張できるかに影響を与えるため、このステップは非常に重要です。 
6. 現在の間隔内にリクエストが存在しなくなったら、最後に処理されたサイトと現在のサイトとの差として空間ジャンプを計算し、アラインメントに応じて次のリクエスト時間と現在のセグメントの開始または終了との差として時間寄与を計算します。 
7. 移動は継続するため、現在のサイトを最も遠い到達可能なサイトに 1 ステップ加えた値に更新します。 
8. 掘削機が次の現場に移行する瞬間を反映するように現在時刻を更新します。これは、現在の間隔の終わりに 1 を加えた時刻です。 
9. すべてのリクエストが消費されるまで、このプロセスを繰り返します。 

### なぜ効果があるのか

 正確さは、各セグメントの開始時に、現在のセグメントの終了よりも時間が短いすべてのリクエストがすでに 1 回だけ考慮されており、ポインターが決して後方に移動しないという不変条件に基づいています。 これにより、すべてのリクエストが正確に 1 つの最大到達可能間隔に寄与することが保証されます。 掘削機は、現在の時間枠内のすべての関連リクエストを使い果たした後にのみ位置を変更するため、到達可能なセグメントの貪欲な拡張は常に最大であり、説明したプロセスと一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    req = []
    for _ in range(n):
        t, x = map(int, input().split())
        req.append((t, x))

    i = 0
    cur_time = req[0][0]
    cur_site = req[0][1]

    ans_max_jump = 0
    ans_days = 0

    while i < n:
        start_time = cur_time
        end_time = cur_time + k - 1

        furthest_site = cur_site

        while i < n and req[i][0] <= end_time:
            # absorb all requests in current window
            furthest_site = max(furthest_site, req[i][1])
            i += 1

        jump = furthest_site - cur_site

        if jump > ans_max_jump:
            ans_max_jump = jump
            ans_days = 0

        if jump == ans_max_jump:
            ans_days += (end_time - start_time + 1)

        cur_site = furthest_site + 1
        cur_time = end_time + 1

    print(ans_max_jump, ans_days)

if __name__ == "__main__":
    solve()
```実装は 2 ポインター構造に直接に従います。 変数`i`各リクエストが 1 回処理されるようにします。 セグメント境界は包括的なエンドポイントで処理されるため、`end_time = cur_time + k - 1`日数を数える際の 1 つずつの誤差を回避します。 

アップデート`cur_site = furthest_site + 1`これは、到達可能な影響をすべて使い果たした後、掘削機が最も遠い影響を受けた現場を一歩越えて移動することを反映しています。 累積ロジックは、新しい最大ジャンプが見つかるたびに合計日カウンタを慎重にリセットします。これは、最大ジャンプ間隔についてのみ貢献を追跡するという要件に一致します。

 ## 特殊なケース

 エッジ ケースの 1 つは、複数のリクエストがセグメント終了時間の境界に正確に到着する場合に発生します。 この状況では、それらは現在の吸収フェーズに含める必要があります。 たとえば、次の場合`cur_time = 1`そして`k = 2`、 それから`end_time = 2`、時刻 2 のリクエストは移動前に処理する必要があります。 

もう 1 つのエッジ ケースは、セグメント内に新しいリクエストが到着しない場合であり、その場合、アルゴリズムはゼロ ジャンプを生成します。 ポインタは引き続き時間とともに進み、シミュレーションが停止しないようにします。 

最後の微妙なケースは、すべてのリクエストが単一の初期ウィンドウ内にある場合です。 内部の while ループがすべてのインデックスを吸収するため、アルゴリズムはこれらを 1 つの最大リーチ計算に正しく圧縮します。`i`満足のいく`req[i][0] <= end_time`、そのウィンドウに未処理のイベントが残らないようにします。
