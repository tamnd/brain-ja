 ## 解決策
 ## 問題の理解

 このタスクは、一連の文字として書かれた特定の数字に対する単純な「幸運の数字」チェックを中心に構築されています。 それぞれがテキスト形式の数字を表す 1 つ以上の入力を受け取り、数字の 7 を含む 1 つのルールに従って、その数字が「幸運」に該当するかどうかを決定する必要があります。 

各入力の出力は短い判定文字列です。 概念的には、数値の演算を実行しているのではなく、その表現をスキャンして、その数値内のどこかに特定の文字が出現するかどうかを判断します。 

計算は簡単に思えますが、重要な点は、数値が十分に大きいため、言語によっては整数として扱うことが不必要であるか、安全でさえない可能性があるということです。 正しいメンタル モデルは、入力が文字列であり、タスクが文字のパターン チェックであるということです。 

このタイプの問題における制約は通常、寛大です。 複数のテスト ケースにわたって各入力文字列の長さが最大 ​​10^5 に達した場合でも、テスト ケースごとの線形スキャンが依然として最適です。 繰り返しの変換、ネストされたスキャン、または算術分解を試みるアプローチはいずれも線形性を保ちますが、利点のない不要なオーバーヘッドが発生します。 

主なエッジケースは、数値の表現方法から発生します。 単純な実装では、単一の整数入力を想定し、それを直接変換する可能性がありますが、値が一般的な整数の制限を超えると、警告なしに中断されます。 たとえば、次のような入力`777777777777777777777`固定幅整数言語では、正しく解析されないとオーバーフローしますが、文字列としては完全に有効です。 もう 1 つの微妙なケースは、先行ゼロです。`00017`ここで、数字 7 はまだ存在しており、フォーマットにもかかわらず検出される必要があります。 

複数の配列やグラフのような複雑な構造はありません。 全体の問題は、正しい入力処理と正確な文字スキャンに帰着します。 

## アプローチ

 最も簡単な方法は、数値を文字列として扱い、文字が`7`どこにでも現れます。 これは、文字列を左から右にスキャンし、スキャンが完了したらすぐに停止することで実行できます。`7`に遭遇します。 条件は位置や周波数ではなく存在のみに依存するため、このアプローチは正しいです。 

ブルートフォースメンタルモデルは、数値を数値的に解釈し、モジュロ 10 算術を使用して繰り返し数字を抽出しようとする可能性があります。 これも機能しますが、除算演算と文字列形式から整数形式への変換を繰り返し行う必要があるため、不要です。 非常に大きな入力の場合、変換ステップ自体がボトルネックになったり、オーバーフローの問題の原因になったりします。 

重要な点は、入力がテキスト形式で提供される場合、数字ベースのプロパティは基本的に文字列プロパティであるということです。 これが受け入れられると、問題は文字に関する単純なメンバーシップ テストに帰着します。 これにより、入力の単一パスで最適なソリューションが得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース（数値抽出） | 一定のオーバーヘッドが大きい場合、数値ごとに O(d) | お(1) | 受け入れられるが不要 |
 | 最適 (文字列スキャン) | 数値ごとの O(d) | お(1) | 承認済み |

 ここで、d は入力表現の文字数です。 

## アルゴリズムのチュートリアル

 1. テスト ケースの数 (存在する場合) を読み取るか、入力行が枯渇するまで処理します。 各行は、文字列としてエンコードされた数値に対応します。 これにより、任意の大きな値を整数に解析することなく安全に処理できるようになります。 
2. 入力文字列ごとに、その文字を左から右に繰り返します。 目的は、いずれかの文字が以下に等しいかどうかを検出することです。`7`、それが出力を決定する唯一の条件であるためです。 
3. もし、`7`スキャン中にこの文字が検出された場合は、直ちにその数字を幸運なものとして分類し、それ以降の文字の処理を停止します。 長時間の入力による不必要な作業を避けるため、早期に終了することが重要です。 
4. スキャンが問題なく完了した場合`7`、その番号を幸運ではない番号として分類します。 
5. 対応する文字列を出力します。通常は`"Happy"`ラッキーナンバーと`"Sad"`さもないと。 

### なぜ効果があるのか

 正確さは、テストされるプロパティが数値の桁セット全体にわたって存在するという事実に基づいています。 アルゴリズムはスキャン中に単純な不変条件を維持します。つまり、最初の k 文字を処理した後、`7`そのプレフィックスに存在します。 いつでも`7`が見つかった場合、サフィックスは結果を無効にすることができないため、早期に終了することで正確さが保たれます。 スキャンが完了すると、不変条件により数字がないことが保証されます。`7`は文字列内のどこにでも存在するため、否定的な答えが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    if not s:
        return
    if '7' in s:
        print("Happy")
    else:
        print("Sad")

if __name__ == "__main__":
    solve()
```このソリューションでは、入力を生の文字列として読み取り、整数の解析を完全に回避します。 会員チェックは`'7' in s`Python で効率的に実装されており、早期終了による線形スキャンが内部で実行されます。 

ここでの主な実装選択は、整数変換を意図的に回避することです。 これにより、オーバーフローのリスクがすべて排除され、ロジックが問題の実際の構造と一致した状態が保たれます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(d) | 各文字は最大 1 回チェックされます。 
| スペース | お(1) | 入力サイズに比例する補助構造はありません |

 ランタイムは各入力の桁数に比例してスケールします。最悪の場合でもすべての文字を検査する必要があるため、これが最適です。 これは、大規模な入力であっても、一般的な Codeforces 制約内に簡単に適合します。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    output = []
    s = sys.stdin.readline().strip()
    if s:
        output.append("Happy" if '7' in s else "Sad")
    return "\n".join(output)

# provided samples (hypothetical since statement is minimal)
assert run("7") == "Happy"
assert run("123") == "Sad"

# custom cases
assert run("0000") == "Sad", "no lucky digit"
assert run("700000") == "Happy", "leading lucky digit"
assert run("123456789") == "Sad", "no 7 at all"
assert run("99999997") == "Happy", "lucky digit at end"

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、入力が 7 以外の繰り返し数字のみで構成されている場合です。`11111111`。 アルゴリズムは文字列全体をスキャンし、正しく返します。`"Sad"`一致する文字が表示されないため。 

もう 1 つのケースは、文字列が非常に長く、数字が`7`のように最後に表示されます。`99999999999999999997`。 このアルゴリズムは早期の成功を想定せず、最後の文字まで正しくスキャンし、最悪の場合の入力の正確性を保証します。 

3 番目のケースは、次のような先頭にゼロがある入力です。`0000070`。 すべての文字は同等に扱われるため、これらはロジックには影響しません。`7`は、位置やフォーマットに関係なく引き続き検出されます。
