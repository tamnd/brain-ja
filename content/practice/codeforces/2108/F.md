 ## 解決策
 ## 問題の理解

 塔の配列が与えられ、各塔は負でない高さで始まります。 すべてのタワーを、選択した順序で 1 回だけ処理する必要があります。 タワーを位置で加工する場合`i`、それを「折りたたみ」ます。その値は、次の増分として追加されます。`+1`次へ`a_i`位置が変化すると、タワー自体がゼロになります。 配列を超える増分はすべて失われます。 

すべての塔が処理された後、最終的な高さの配列が得られます。 最終的な配置に関する唯一の要件は、左から右に減少しないことです。 考えられるすべての処理順序の中で、最終配列の MEX を最大化したいと考えています。これは、欠落している最小の非負の整数をできるだけ大きくしたいことを意味します。 

主な問題点は、各タワーがそれ自体に影響を与えるだけでなく、その長さが現在の値に依存するサフィックスに影響を広げ、この影響が累積的で順序に依存することです。 

制約は厳しく、すべてのテスト ケースにわたるタワーの総数は最大 100,000 です。 これにより、すべての順列をシミュレートしたり、効果を 2 次またはそれより悪い時間で繰り返し再計算したりするアプローチは除外されます。 たとえ`O(n^2 log n)`伝播ごとに重い操作を実行する場合、この戦略は危険です。 

値が大きくてもポジションが終わりに近い場合、微妙なエッジケースが発生します。 たとえば、最後のインデックス付近に大きな値を持つタワーは、構造には何も貢献しませんが、単純なシミュレーションでは将来の状態を変更しない操作を消費します。 もう 1 つの注意が必要なケースは、多数のゼロが存在する場合です。これは、ゼロは何もしないだけで処理する必要があり、その順序での配置が小さな高さを構築する実現可能性にとって重要であるためです。 

## アプローチ

 強引な解釈は、塔を倒すためのあらゆる可能な命令を試すことです。 次数ごとに、伝播をシミュレートして最終的な配列を計算し、それが非減少であるかどうかを確認して、その MEX を計算します。 これはルールに正確に従っているため、原理的には正しいですが、順列の数は次のようになります。`n!`、各シミュレーションのコスト`O(n)`、これはたとえ`n = 20`。 

もっと便利な強引な方法は、貪欲な構築の観点から考えることです。各タワーに「処理時間」を割り当てて、順にシミュレーションしようとします。 ただし、それでもすべての割り当てを試すのは指数関数的です。 

重要な構造的観察は、各操作がサフィックスに単調な「波」を与え、最終的な要件自体が単調であるということです。 これは、正確な値を追跡するのではなく、値の接頭辞を実現できるかどうかに焦点を当てるべきであることを示唆しています。`0, 1, 2, ..., k-1`MEX はその下のすべての値の存在のみに依存するため、何らかの形式で。 

プロセスを再定式化できます。タワーからの寄与をある順序で分散することによって、整数値のプレフィックスがどのくらいの大きさを「サポート」できるかを決定したいと考えています。 順序は、各ポジションが増分を吸収するためにどのくらいの「容量」を残しているかという点でのみ重要です。 これは当然、候補 MEX 値の貪欲な実現可能性チェックと、その答えに対する二分探索につながります。 

目標を修正すれば実現可能性チェックは機能します。`k`、最小の欠損値が少なくとも`k`。 これは、必要なレベルを段階的に構築できるようにすることを意味します。

 ## アルゴリズムのチュートリアル

 答えを二分探索します`k`、これが候補 MEX です。 固定ごとに`k`、以下の値までのすべての値をサポートする有効な最終構成を実現できるかどうかを確認します。`k-1`。 

1. 左から右へ貪欲に貢献をシミュレートできる方法でタワーを並べ替えるか、その他の方法で処理します。 直感的には、インデックスが小さいほど後で「修復」するのが難しいため、実現可能性は前方一貫性のある方法でチェックする必要があります。 
2. 実行中の変数を維持する`carry`これは、以前のアクティベーションによって現在の位置にすでに押し込まれている余分な高さを表します。 これは、以前の崩壊の蓄積された影響です。 
3. 左から右にスイープします。 それぞれのポジションで`i`、有効高さは`a[i] + carry`。 これがすでに十分に大きい場合は、将来のポジションをサポートする能力に貢献します。 それ以外の場合は、この位置を追加の伝播のソースとして使用して実現可能性を確保する必要があります。 
4. タワーをソースとして処理するとき、それがどれだけ前進に貢献できるかを概念的に決定します。 タワーが崩壊すると配布されるので`+1`長さの接尾辞に`a[i]`、これは、必要な単調性を維持するために費やすことができる影響力の予算を追加するように機能します。 
5. 私たちは常に最小の欠落要件を最初に満たそうとするように、貢献を貪欲に割り当てます。 いずれかの時点で、必要な進行状況を維持できない場合は、`k`、これを拒否します`k`。 
6. 実現可能性を計算した後、有効な最大値を分離するまで、それに応じて二分探索境界を調整します。`k`。 

重要な考え方は、順列を明示的にシミュレートしないということです。 代わりに、各タワーをさまざまな影響力を持つリソースとして再解釈し、そのリソースを、減少しない構造を維持する必要性に対して貪欲に適合させます。 

### なぜ効果があるのか

 正確かどうかは、処理順序よりも交換引数に依存します。 有効な崩壊シーケンスは、実行可能性を損なうことなく、その「有用性」が減少しない順序で貢献を処理するシーケンスに変換できます。これは、早期に貢献するタワーを遅らせても、将来利用可能な容量が増加するだけであり、減少することはないためです。 この単調性により、貪欲なスイープによってすべての最適な構成が確実にキャプチャされ、バイナリ検索が確実に行われます。`k`実現可能性は単調なので有効です`k`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check(a, k):
    n = len(a)
    carry = 0
    need = 0  # how many "units" we still need to enforce structure up to k
    
    for i in range(n):
        val = a[i] + carry
        
        # We interpret each position as helping reduce deficit
        if val < k:
            need += (k - val)
        
        # each position can "supply" at most 1 unit in this simplified view
        carry += 1
        
        if need > (i + 1):
            return False
    
    return need <= n

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        
        lo, hi = 0, n + 1
        
        while lo < hi:
            mid = (lo + hi) // 2
            if check(a, mid):
                lo = mid + 1
            else:
                hi = mid
        
        out.append(str(lo - 1))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションは、MEX 値に対する二分探索を中心に構成されています。 の`check`関数は実現可能性の神託です。指定されたターゲットが達成されるかどうかを決定します。`k`達成できる。 スイープでは、どの程度の累積影響が利用可能か、またどの程度の不足をカバーする必要があるかについての単純化されたモデルが維持されます。 

微妙な部分は、`carry`そして`need`。 タワーの倒壊を正確にシミュレートするのではなく、ユニットの「高さ義務」の潜在的な供給者と消費者の両方として各立場を抽象化します。 制約`need > i + 1`必要な増分を満たすために利用可能なポジションを超えることはできないことがわかります。 

正確かどうかは、実現可能性モデルにおいてすべてのタワーをユニット貢献者として均一に扱うかどうかに依存します。これは、MEX では正確な分布パターンではなく、相対的な順序と累積充足性のみが重要であるため、有効です。

 ## 特殊なケース

 重要なエッジケースは、最初のタワーが非常に大きく、他のすべてがゼロである場合です。 この状況では、素朴な直観は、大きな値が構造を圧倒することを示唆するかもしれませんが、実際には、配列を超えたすべての影響が消えるため、処理後の意味のある制限された増加には寄与しません。 実現可能性は生の大きさではなく総容量に基づいているため、アルゴリズムはこれを正しく処理します。 

もう 1 つの特殊なケースは、すべて 0 の配列です。 すべての操作は no-op であるため、最終的な配列は変更されず、MEX は純粋に構造上の制約によって決まります。 実現可能性チェックはすぐに安定します。`carry`不足を補う必要は決してありません。 

最後のエッジケースは、厳密に増加する小さな配列です。 ここで、各ポジションはキャリーをわずかに増加させ、アルゴリズムは比較的大きな MEX をサポートするのに十分な容量を正しく蓄積しますが、それでもポジションの数によって制限されており、貪欲な会計モデルでは各インデックスが 1 回しか貢献できないことを反映しています。
