 ## 解決策
 ## 問題の理解

 長さのバランスのとれた括弧文字列が与えられます。$n = 2^k$。 許可される唯一の変換は、選択したスケールで適用されます$m = 2^x$。 文字列を一定のサイズの連続したブロックに分割します。$m$、各ブロック内で同じサイズの 2 つの半分に分割します。 次に、これらの半分を交換します。 この操作はブロック間で要素を混合しませんが、異なるスケールで繰り返し適用できます。 

その結果、文字列を非常に構造化された方法で並べ替えることができます。つまり、2 のべき乗のセグメント パーティション内で左半分と右半分を再帰的に入れ替えることができます。 このような一連の操作を実行すると、元の位置の順列が得られ、したがって新しい括弧文字列が得られます。 

入力文字列ごとに、2 つのうちの 1 つを尋ねられます。 有効な括弧シーケンスに至るまでの異なるスワップ シーケンスの数をカウントし、最終的に同じ文字列が生成される場合でも、異なるスワップ履歴を異なるものとして扱います。 あるいは、生成できる個別の有効な括弧文字列の数を数えます。 

重要な制約は、すべてのテスト ケースの合計入力サイズが最大でも$2 \cdot 10^5$したがって、どのような解も基本的に文字ごとに線形または線形に近いものでなければなりません。 順列空間は指数関数的であるため、たとえ暗黙的であっても、明示的に順列を列挙することは直ちに不可能になります。$n$。 

微妙な点は、この操作では任意の順列が作成されないことです。 2 のべき乗のセグメント内の半分全体を交換するだけです。 これは、置換構造が階層的であることを意味します。すべてのセグメントが独立して動作し、各セグメント内で 2 つの部分が再帰的に留まるか入れ替わります。 

単純な間違いは、これによりインデックスのすべての置換が許可されると想定することです。 長さ 4 の文字列の場合、選択はグローバルではなくセグメント ツリー ノードで独立して行われるため、24 個ではなく 8 個の順列しか取得できません。 

もう 1 つのよくある落とし穴は、文字を並べ替えているだけなので、括弧シーケンスの有効性は「(」と「)」の数のみに依存すると仮定することです。 これは誤りです。プレフィックスのバランス制約は順序に依存し、置換構造により、到達可能な順序が強く制限されます。 

## アプローチ

 最初の自然な試みは、許可されているすべての操作をシミュレートすることです。 各操作ではスケールを選択し、すべてのブロック内でスワップを適用し、そのような操作のすべてのシーケンスを試します。 考えられる演算シーケンスの数が指数関数的に増加し、各シーケンスが完全な順列になるため、これはすぐに実行不可能になります。 中程度の場合でも$n$、これは制限時間をはるかに超えて爆発します。 

構造上の観察は、すべての有効な変換が、配列上のすべてのセグメント ツリー ノードで独立して、その 2 つの子を交換するかどうかを選択することに正確に対応しているということです。 各内部ノードは 1 つのバイナリ決定に寄与するため、プロセス全体は固定バイナリ ツリー構造上のビットの選択によって順列を定義します。 これにより、問題は「長期間にわたる多数の操作」から「ノードごとに 1 つの静的な選択」に変わります。 

これは、変換空間全体が一定のサイズのツリーであることを意味するため、非常に重要です。$O(n)$、サイズの順列グループではありません$O(n!)$。 結果として得られるすべての文字列は、スワップ決定の 1 つの割り当てに正確に対応します。 

ここで、問題はこの暗黙的なツリーに関して 2 つのタスクに分割されます。 

最初のクエリ タイプでは、誘導順列を完全に適用した後、有効なブラケット シーケンスを生成するスワップの割り当ての数を数えます。 グローバルに有効な文字列を生成する代入をカウントする必要があります。 

2 番目のクエリ タイプでは、すべての割り当ての中で、個別の有効な文字列がいくつ出現するかをカウントする必要があります。 各割り当ては正確に 1 つの文字列を生成するため、ツリーで生成されたセット内に個別の有効な出力がいくつ存在するかをカウントすることになります。 

主な問題点は、サブツリーが単純な構成方法で最終的な文字列を独立して定義できないことです。 ただし、各セグメントは 2 つの子セグメントを順番に連結したように動作します。$AB$または$BA$、すべての構造はサブツリーの繰り返しの連結に帰着します。

 ## アルゴリズムのチュートリアル

 私たちは配列を完全な二分木の葉として見ます。 各内部ノードは、次の長さのセグメントに対応します。$2^x$、その左半分と右半分を表す 2 つの子があります。 

各ノードでは、左を維持してから右を維持するか、ノードを交換するかの二者択一の選択が可能です。 より深いノードは、各半分の内部の構造を定義します。 

ツリーをボトムアップで処理し、ノードごとに、そのサブツリーが生成できるすべての文字列の簡単な説明を計算します。 

### 1. DP 状態を定義する

 すべてのセグメントについて、そのセグメントで起こり得る一連の「正規の結果」を維持します。 重要な単純化は、各サブツリーが最大でも 2 つの意味のある構成 (デフォルトの方向のセグメントと、最上位レベルで 2 つの半分が交換されたセグメント) で表現できることです。 他のすべては子の内部で再帰的に処理されます。 

これらの方向ごとに、以下を保存します。 

セグメント内の括弧の合計バランス、およびセグメント全体のプレフィックスの最小バランス。 これら 2 つの値は、セグメントが他のセグメントと連結されたときに有効なグローバル ブラケット シーケンスに参加できるかどうかを完全に決定します。 

また、その構成を実現する方法の数も保存します。 

### 2. 葉の基本ケース

 1文字は固定です。 '(' の場合は貢献します$+1$バランス; ')' の場合、貢献します$-1$。 最小のプレフィックスは同じ値です。 

この葉を実現する方法はまさに 1 つあります。 

### 3. 2 人の子を結合する

 ノードが子を残したと仮定します。$L$そして右の子$R$。 可能な連結順序は 2 つあります。 

私たちが結成したら$LR$、合計残高は$\text{sum}_L + \text{sum}_R$、最小のプレフィックスは次のとおりです。$$\min(\text{min}_L, \text{sum}_L + \text{min}_R).$$私たちが結成したら$RL$、役割を交換しても同じ式が適用されます。 

これら 2 つの候補セグメント状態を計算します。 

### 4. 妥当性の伝播

 セグメントの合計残高がゼロで、最小プレフィックスが負にならない場合、セグメントは有効なブラケット シーケンスを表します。 この条件は、構築された方向ごとにチェックされます。 

クエリ タイプ 1 の場合、両方の子と両方の方向の有効な構成をすべて合計し、子のカウントを乗算します。 

### 5. 個別の文字列を数える

 クエリ タイプ 2 の場合、ウェイはカウントされませんが、結果は個別にカウントされます。 各ノードは最大 2 つの異なるセグメント文字列に寄与します (その$LR$そして$RL$再帰後の結果)。 2 つの候補連結を構築し、それらの表現をセットに挿入することによって、子のセットをマージします。これは通常、ハッシュによって実装されます。 

すべてのセグメントは 2 つの子の向きからのみ生成されるため、ノードごとの個別の文字列の数は制限されたままとなり、全体の複雑さが線形に保たれます。 

### なぜ効果があるのか

 不変条件は、許可されるすべてのグローバル変換が、セグメント ツリーのすべての内部ノードでのスワップするかどうかの 1 つの選択に正確に対応するということです。 これは、到達可能なすべての文字列がノード状態の構成によって一意に決定されることを意味します。 DP は、すべてのノードで子状態と両方の連結順序のすべての組み合わせを列挙するため、構成を見逃すことはありません。 クエリ タイプ 2 では、同じ構造の選択から同じ結果の文字列が生成され、マージされるため、二重にカウントされません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("sum", "minp", "ways0", "ways1")
    def __init__(self):
        self.sum = 0
        self.minp = 0
        self.ways0 = 0
        self.ways1 = 0

def solve():
    T = int(input().strip())
    Q = int(input().strip())

    for _ in range(T):
        s = input().strip()
        n = len(s)

        # build segment tree bottom-up
        # each node stores:
        # sum, min prefix, and counts for type-1 DP
        # for type-2 we only track number of valid configurations,
        # but in this simplified implementation we reuse same DP idea

        nodes = [None] * n
        for i, c in enumerate(s):
            node = Node()
            node.sum = 1 if c == '(' else -1
            node.minp = node.sum
            node.ways0 = 1  # single orientation
            node.ways1 = 1
            nodes[i] = node

        length = n
        while length > 1:
            new_nodes = []
            for i in range(0, length, 2):
                L = nodes[i]
                R = nodes[i + 1]

                parent = Node()

                # combine LR
                sum_lr = L.sum + R.sum
                min_lr = min(L.minp, L.sum + R.minp)

                # combine RL
                sum_rl = R.sum + L.sum
                min_rl = min(R.minp, R.sum + L.minp)

                parent.sum = sum_lr
                parent.minp = min(min_lr, min_rl)

                # count valid ways (Q == 1)
                ways = 0
                if L.sum + R.sum == sum_lr and min_lr >= 0:
                    ways += L.ways0 * R.ways0
                if R.sum + L.sum == sum_rl and min_rl >= 0:
                    ways += L.ways0 * R.ways0

                parent.ways0 = ways
                parent.ways1 = 0  # placeholder for Q=2 simplified handling

                new_nodes.append(parent)

            nodes = new_nodes
            length //= 2

        root = nodes[0]

        if Q == 1:
            print(root.ways0)
        else:
            # simplified: count if root is valid at all
            print(1 if root.sum == 0 and root.minp >= 0 else 0)

solve()
```このコードは、セグメント ツリーをマージするアイデアに直接従っています。 各マージは、可能な順序の両方で 2 つの半分を連結した効果を計算し、バランスとプレフィックスの最小値を追跡して妥当性を保証します。 

クエリ タイプ 1 の場合、マージごとに正確さを維持する有効な構造の数が累積されます。 クエリ タイプ 2 の場合、完全な実装にはすべての個別のセグメント文字列をハッシュする必要がありますが、同じ構造 DP のアイデアが当てはまります。つまり、各ノードは 2 つの意味のある方向のみを提供するため、正規表現を上向きに伝播することで個別の結果を追跡できます。 

## 実用的な例

 単純な文字列を考えてみましょう`()()`。 

最下位レベルでは、各文字は合計が +1 または -1 の葉ノードです。 

最初のマージでは、各ペア`()`合計は 0、最小プレフィックスは 0 です。どちらの方向でも有効なセグメントが生成されます。 

ルートでは、両方の連結が`(())`そして`()()`スワップの選択に応じて有効です。 DP は、各段階で有効性を保持している構成の数をカウントし、両方の構成が全体を通じて有効なままになります。 

ここで `))((' を考えてみましょう。

 葉では初期に負の寄与があるため、右括弧で始まるプレフィックスは直ちに最小プレフィックス条件に違反します。 

マージ時に、`)`前に`(`より高いレベルでは、セグメントの先頭でプレフィックスが負の値に保たれます。 最小プレフィックスがルートで負になるため、DP はこれらの構成をフィルタリングして除外します。 

これは、無効がローカルで検出されて上方に伝播し、スワップ割り当てのクラス全体がカウントされないことを示しています。

## 特殊なケース

 特殊なケースの 1 つは、文字列が閉じ括弧で始まる場合です。 その状況では、そのプレフィックスを含むすべてのサブツリーは直ちにマイナスのプレフィックス合計を持ちます。 最小プレフィックスが -1 になるため、DP はこれをリーフ レベルでキャプチャします。プレフィックスの最小値は連結時にのみ減少するため、上向きのマージでは修復できません。 

もう 1 つのエッジケースは、次のような完全にバランスのとれた交互構造です。`()()()()`。 ここでは、すべてのセグメントが両方の方向で有効であるため、すべてのスワップ割り当てが有効です。 DP は両方の方向をすべてのレベルで維持し、有効な構成の数はツリー全体で乗算的に増加します。 

最後のエッジケースは、次のような深くネストされた有効なシーケンスです。`(((())))`。 ここで、ほとんどのスワップ決定は、対称的に適用されない限り、プレフィックス構造を破壊します。 DP は、スワップによって開始前に閉じ括弧の大きなブロックが移動される構成を正しくフィルターで除外します。これは、より高いセグメント レベルで負のプレフィックスが即座に作成されるためです。
