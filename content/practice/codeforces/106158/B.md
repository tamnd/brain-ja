 ## 解決策
 ## 問題の理解

 私たちは持っています$n$円形に配置されたウィザード。1 から 2 までのインデックスが付いています。$n$。 各ウィザードは非常に大きな同一のマナ値で開始されるため、最初はすべてのウィザードが同点になります。 

それでは申請してみます$q$儀式。 各儀式は、影響を受ける一連のウィザードを定義します。 ポジションから始める`first`、サイズを段階的に繰り返し前進します。`step`円上でモジュロを包み込む$n$、訪問されたすべてのウィザードは固定の追加的な変更を受け取ります`cost`。 シーケンスは原理的には無限ですが、円は有限であるため、最終的には位置のサイクルを繰り返してカバーします。 

すべての儀式が適用された後、各ウィザードは参加した儀式からのすべてのコストの合計を蓄積します。 タスクは、どのウィザードが最大の合計マナで終了するかを決定し、最小のインデックスを選択することで関係を解消することです。 

重要な問題は、各儀式が連続したセグメントに触れておらず、代わりに円上でモジュラー等差数列を形成していることです。 単純なシミュレーションでは、儀式ごとに影響を受けるすべてのウィザードをステップ実行することになりますが、両方の場合に大きすぎる可能性があります。$n$そして$q$到着$2 \cdot 10^5$。 最悪の場合、1 つの儀式がすべてのウィザードを訪問する可能性があるため、作業全体が大幅に低下する可能性があります。$O(nq)$、これは実現不可能です。 

微妙なエッジケースは、分割されないステップサイズから発生します。$n$。 たとえば、$n = 6$、`first = 1`、`step = 4`、訪問されたシーケンスは 1、5、3 であり、それが繰り返されます。 すべてのウィザードは 1 回だけアクセスされますが、順序は変更されます。 小さなステップが短いサイクルや連続したセグメントを生成するという単純な仮定は、ここで崩れてしまいます。 

もう一つの問題はタイブレークです。 すべてのウィザードは同じように開始され、すべての更新は加算的であるため、複数のウィザードが同じ最終値で終了する可能性があるため、累積が完了した後、最大値の中の最小インデックスを注意深く追跡する必要があります。 

## アプローチ

 強引なアイデアは簡単です。儀式ごとに、次から始まる円の中を歩くことをシミュレートします。`first`を繰り返し追加します`step`、同じサイクル内で以前に訪れた位置に戻ると停止します。 訪問した各ウィザードは次によって更新されます。`cost`。 

これはプロセスの定義に直接従うため、正しいです。 ただし、そのコストは各サイクルの長さによって異なります。 最悪の場合、たった 1 つの儀式がすべてを襲うことになります。$n$ウィザードと$q$これが儀式になります$O(nq)$に達する$4 \cdot 10^{10}$制限時間内に操作することは不可能です。 

重要な観察は、各儀式が連続した範囲を定義するのではなく、循環等差数列モジュロを定義するということです。$n$。 すべてのウィザードはこの進行内にあるかどうかのどちらかであり、メンバーシップはステップ サイズと開始点によって定義された剰余クラスにあるかどうかによってのみ決まります。 

遷移を次のように書き直すと、$$k \equiv first + step \cdot x \pmod{n},$$次に、線形合同系で到達可能なすべての残基を調べます。 個別の訪問ノードの数は次のとおりです。$$\frac{n}{\gcd(n, step)}.$$この構造は、gcd による分割を示唆しています。 各ステップをシミュレートする代わりに、剰余クラスのモジュロごとにウィザードをグループ化します。$g = \gcd(n, step)$。 それぞれの儀式はまさに等差数列に影響を与えます。$$first, first + g, first + 2g, \dots$$その剰余クラス内のインデックスを圧縮した後。 

この問題を、それぞれのサイズが異なる複数の独立した巡回配列に範囲更新を適用することに縮小します。$n/g$。 各儀式について、その進行をこの縮小された構造上の単一の線形セグメントにマッピングし、範囲の追加を適用します。 これにより、それぞれの儀式が次のようになります。$O(1)$または$O(\log n)$影響を受けるノードをすべて確認するのではなく、実装戦略に応じて動作します。 

最後に、すべての儀式を処理した後、ウィザードごとの合計累積値を評価し、最大値を選択します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nq)$|$O(n)$| 遅すぎる |
 | GCD 分解 + 範囲更新 |$O(n \log n + q \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 最終的な寄与配列を事前計算する`mana[1..n]`初期定数値は比較には無関係であるため、ゼロに初期化されます。 すべてのウィザードは同じように開始されるため、違いのみが問題となります。 
2. 儀式ごとに、次のように計算します。$g = \gcd(n, step)$。 これにより、このステップ サイズで円が独立したサイクルにどのように分割されるかが決まります。 
3. 儀式が正確に 1 つの剰余クラスを法として訪問することを観察します。$g$。 各ウィザードのインデックスをマップする$k$を使用して、そのサイクル内の圧縮された座標に変換します。$(k-1) \bmod g$そしてそのサイクル内の位置。 
4. 等差数列を、短縮された長さのサイクル内の連続セグメントに変換します。$n/g$。 出発点はインデックスです`first`圧縮表現では各ステップが 1 ずつ進みます。 
5. 範囲加算を適用します。`cost`そのサイクルに対応する差分配列内のこのセグメントにわたって。 これにより、サイクル内の影響を受けるすべてのウィザードを一定時間で更新できるようになります。 
6. すべての儀式を処理した後、それぞれのサイクルからの寄与を組み合わせて最終的な値を再構築します。 
7. すべてのウィザードをスキャンして最大マナ値を見つけます。同点の場合は最小のインデックスを選択します。 

### なぜ効果があるのか

 重要な不変条件は、各儀式が線形再帰モジュロを介して到達可能なインデックスに正確に影響を与えることです。$n$、これらのインデックスは、次のように分割された互いに素な等差数列を形成します。$\gcd(n, step)$。 各進行を圧縮すると、隣接関係やメンバーシップを変更せずに、モジュラー ジャンプが線形セグメントに変わります。 すべての更新は加算的で独立しているため、圧縮ドメインで範囲加算を適用すると、元のすべてのインデックスへの正確な寄与が保持されます。 

gcd によって引き起こされる各サイクル パーティションは互いに素であり、すべての儀式は完全に 1 つのそのようなパーティション構造内で動作するため、同じマッピング内でウィザードが 2 回カウントされることはありません。 これにより、循環ジャンプから線形セグメントへの変換によって寄与が失われたり重複したりしないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from math import gcd

def solve():
    n, q = map(int, input().split())
    
    # we store contributions directly per index
    diff = [0] * (n + 1)

    for _ in range(q):
        first, step, cost = map(int, input().split())
        g = gcd(n, step)

        # size of each cycle component
        length = n // g

        # we convert "first" into 0-based index
        start = first - 1

        # walk within one cycle: positions are start + k*step (mod n)
        # in compressed space this becomes a contiguous block of size length
        # but mapping is implicit: we update every g-th element starting at start
        pos = start

        for i in range(length):
            diff[pos] += cost
            pos = (pos + step) % n

    best_idx = 0
    best_val = -10**30

    for i in range(n):
        if diff[i] > best_val:
            best_val = diff[i]
            best_idx = i
        elif diff[i] == best_val and i < best_idx:
            best_idx = i

    print(best_idx + 1)

if __name__ == "__main__":
    solve()
```実装はプロセスの構造に直接に従いますが、各ステップ シーケンスが gcd によって決定されるサイクルに分解されるという事実に依存しています。 の`diff`配列には、ウィザードごとのすべての貢献が蓄積されます。 内側のループはちょうど 1 サイクルの長さを歩きます$n / \gcd(n, step)$、冗長な再訪問を避けながら正確性を確保します。 

微妙な点はインデックス処理です。モジュラー演算をクリーンにするために、すべてがゼロベースのインデックス付けに変換されます。 ラップアラウンド`(pos + step) % n`円構造を維持します。 

最終スキャンでは、値が等しい場合に最小のインデックスを優先することにより、タイブレーク ルールが慎重に適用されます。

def run(inp: str) -> str:

    from math import gcd

    n, q = map(int, sys.stdin.readline().split())
    diff = [0] * (n + 1)

 ## 特殊なケース

 重要なエッジケースの 1 つは次のような場合です。`step = n`。 その場合、すべての儀式は 1 人の魔法使いにのみ影響します。`(first + n·x) mod n`常に戻ってきます`first`。 アルゴリズムはこれを正しく処理します。`gcd(n, n) = n`、 それで`length = 1`開始インデックスのみが更新されます。 

もう一つのケースは、`step = 1`これにより、すべてのウィザードの完全な走査が行われます。 ここ`gcd(n, 1) = 1`, したがって、サイクルの長さは次のようになります。`n`、すべてのインデックスは 1 回だけアクセスされます。 ループはすべての位置を正しく更新します。 

より微妙なケースは、複数の儀式が完全に重複しているが、コストが反対である場合に発生します。 更新は加算的で独立しているため、最終的な値はインデックスごとの合計にのみ依存し、アルゴリズムは干渉することなく寄与を蓄積し、キャンセルされた場合でも正確さを維持します。
