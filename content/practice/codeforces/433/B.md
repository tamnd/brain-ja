 ## 解決策
 ## 問題の理解

 一連の石があり、それぞれに数値コストが付いています。 栗山未来は 2 種類の質問を繰り返し尋ねたいと考えています。1 番目の種類では、元のシーケンスの連続したセグメント内の石のコストの合計を尋ねます。 2 番目のタイプでは、すべての石をコストの降順でない順に並べ替えた後、同じセグメント内の石のコストの合計を要求します。 

入力では、最初に石の数が与えられ、次に石の個々のコストが与えられ、次に質問の数と質問自体が続きます。 各質問には、タイプ (1 または 2) とセグメントの境界が示されます。 出力は、そのクエリに対応する合計です。 

最大 100,000 個のストーンと 100,000 個のクエリが存在する可能性があることを考えると、各クエリのセグメントを直接合計する単純なアプローチでは、最悪の場合でも O(n * m) の操作が必要になります。 これは 10^10 の操作に達する可能性があり、2 秒の制限時間の妥当な制限をはるかに超えています。 したがって、複数のクエリを効率的に、理想的には前処理後にクエリごとに O(1) で処理できるアプローチが必要です。 

明らかでないエッジ ケースには、長さ 1 (l が r に等しい) のセグメント、アレイ全体をカバーするセグメント、およびすべての石が等しい値を持つアレイが含まれます。 不注意な解決策では、1 ベースのインデックス付けと 0 ベースのインデックス付けが混在したり、合計が 32 ビット整数を超える可能性があることを忘れたりして、オーバーフローが発生する可能性があります。 たとえば、配列`v = [10^9, 10^9, 10^9]`そしてクエリ`1 1 3`は 3*10^9 を返す必要がありますが、これは 32 ビットの符号付き整数に収まりません。 

## アプローチ

 ブルート フォース アプローチは簡単です。クエリごとにセグメント インデックスを反復処理し、値を合計します。 これは問題のステートメントを直接実装しているため、正解です。 ただし、100,000 ストーンと 100,000 クエリという最悪のシナリオでは、O(n*m) 回の操作が必要となり、非常に遅すぎます。 

重要な洞察は、両方のタイプのクエリが連続したセグメントの合計を要求するということです。 任意の配列について、プレフィックス合計配列を事前計算すると、任意のセグメントの合計が計算されます。`[l, r]`次の式を使用して O(1) で計算できます。`prefix[r] - prefix[l-1]`。 タイプ 2 クエリの場合、最初に元の配列を並べ替えて、そのプレフィックスの合計を計算します。 これにより、クエリごとの時間が O(1) に短縮されますが、前処理にはソートに O(n log n)、プレフィックス合計に O(n) かかります。 

ブルート フォース アプローチは、要求された要素を直接合計するため機能しますが、入力が大きい場合は失敗します。 セグメントの合計がプレフィックスの合計に還元できるという観察により、各クエリに一定時間で答えることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n*m) | O(n) | 遅すぎる |
 | プレフィックスの合計 + 並べ替え | O(n log n + m) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 石の数を読み取る`n`そして石のコスト配列`v`。 
2. プレフィックス合計配列を構築する`prefix_original`のために`v`どこ`prefix_original[i] = v[0] + ... + v[i]`。 これにより、元の配列に対して O(1) の合計クエリが可能になります。 
3. コピーを作成します。`v`それを並べ替えて取得します`v_sorted`。 プレフィックス合計配列を構築する`prefix_sorted`ソートされた配列の場合。 
4. クエリ数を読み取る`m`。 
5. 各クエリについて`(type, l, r)`：

- もし`type`が 1 の場合、合計を次のように計算します。`prefix_original[r] - prefix_original[l-1]`。 
- もし`type`が 2 の場合、合計を次のように計算します。`prefix_sorted[r] - prefix_sorted[l-1]`。 
6. 各クエリの結果を出力します。 

これが機能するのは、プレフィックス合計配列が次の不変条件を維持しているためです。`prefix[i]`インデックス 1 から i までのすべての要素の合計に等しい。 2 つのプレフィックスの合計を減算すると、これらのインデックス間の要素の合計が正確に得られるため、セグメントの合計を誤って計算することができなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
v = list(map(int, input().split()))

# prefix sum for the original array
prefix_original = [0] * (n + 1)
for i in range(1, n + 1):
    prefix_original[i] = prefix_original[i - 1] + v[i - 1]

# prefix sum for the sorted array
v_sorted = sorted(v)
prefix_sorted = [0] * (n + 1)
for i in range(1, n + 1):
    prefix_sorted[i] = prefix_sorted[i - 1] + v_sorted[i - 1]

m = int(input())
for _ in range(m):
    t, l, r = map(int, input().split())
    if t == 1:
        print(prefix_original[r] - prefix_original[l - 1])
    else:
        print(prefix_sorted[r] - prefix_sorted[l - 1])
```このソリューションでは、最初にプレフィックス合計を構築して、合計の繰り返しを回避します。 使用する`n+1`先頭に 0 を付けた長さの配列を使用すると、境界処理が簡素化され、インデックス 1 で始まるセグメントの合計が特殊な場合を除いて正確になります。 並べ替えによりタイプ 2 クエリの配列が作成され、同じプレフィックス合計トリックが適用されます。 入力を効率的に読み取るために注意が必要です`sys.stdin.readline`。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 n、m ≤ 10^5 とすると、これは 2 秒以内に収まり、使用量は 256 MB 未満になります。
