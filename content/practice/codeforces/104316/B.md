 ## 解決策
 ## 問題の理解

 頂点 1 にルートが固定されたルート付きツリーが与えられます。各頂点には 2 つの属性が格納されます: ラベル`t[v]`、頂点をタイプにグループ化するもの、およびジャンプ パラメータ`d[v]`、トークンがルートへのパスに沿って上方向にどのくらい移動するかを定義します。 最初は、いくつかの頂点にトークンが含まれています。 

このプロセスは、一連のクエリによって駆動されます。 各クエリには値があります`c`。 そのクエリでは、現在トークンを含み、そのラベルが付けられているすべての頂点を考慮します。`t[v]`等しい`c`。 このようなトークンはすべて同時に移動します。 頂点のトークン`v`～からの道を見る`v`根元に到達し、上にジャンプします`d[v]`そのパスに沿った端。 ジャンプがルートを超えた場合、単に頂点 1 に到達します。各クエリの後、トークンは新しい位置に残ります。 

クエリを順番に処理するため、すべてのトークンがルートに配置される最初のクエリ インデックスを見つける必要があります。 これが起こらない場合は、次のように出力します。`-1`。 

ツリーには最大 200,000 個の頂点とクエリを含めることができるため、クエリごとに各トークンの動きを明示的にシミュレートするソリューションは直ちに遅すぎます。 主な問題は、トークンが相互ではなくクエリ タイプを通じてのみ相互作用することですが、それらの位置は時間の経過とともに変化するため、すべてのトークンがルートに収束するタイミングを検出する必要があることです。 

単純なアプローチでは、すべてのトークンを反復処理し、各トークンに対して親ポインターを使用して祖先ジャンプを計算することによって各クエリをシミュレートします。 最悪の場合、O(n) 個のトークンと O(q) 個のクエリが存在し、制限をはるかに超える O(nq) 個の操作が発生する可能性があります。 

2 番目の単純なアイデアは、ジャンプ d[v] ステップが O(1) になるように先祖を事前計算することですが、それでもクエリごとにトークンを繰り返し処理するため、依然として遅すぎます。 

複数のトークンが同じ頂点を共有する場合、またはトークンが異なるクエリ タイプによって繰り返し移動される場合、微妙なエッジ ケースが発生します。 「アクティブなトークンを一度だけ処理する」という貪欲なアイデアは、トークンが 1 つのクエリ内でルートに近づく可能性があるにもかかわらず、位置が変わるまでその後の異なるタイプのクエリでは考慮されない可能性があるため、失敗します。 

## アプローチ

 重要な観察は、各トークンの動きは決定的であり、現在の頂点と現在のクエリ タイプにのみ依存するということです。 ツリーの構造は、任意のトークンの宛先を O(log n) 時間で計算できるように、バイナリ リフティングを使用して上向きジャンプを前処理することを示唆しています。 

ただし、主なボトルネックは、単一のジャンプを計算するのではなく、クエリごとにすべてのトークンを繰り返しスキャンすることです。 トークンに作用するクエリを追跡する代わりに、視点を逆転させます。トークンごとに、一連の操作で最終的にいつルートに到達するかを知りたいと考えます。 

時間を順方向にシミュレートしますが、安定したトークンの再処理は避けます。 トークンがルートに到達すると、そのトークンは参加しなくなります。 各トークンは、現在の頂点がクエリ タイプと一致する場合にのみ移動されます。 それ以外の場合は影響を受けません。 

これを効率的に行うために、現在の頂点ごとにトークンをグループ化し、クエリに一致するタイプの頂点のみを処理します。 各頂点について、現在そこにあるトークンのリストを維持します。 次のタイプのクエリの場合`c`到着したので、頂点のみを処理します`v`と`t[v] = c`現在トークンが含まれているものを選択し、それらの頂点からすべてのトークンを一括で移動します。 

これにより、各トークンが移動する場合にのみ処理され、移動するたびにツリー内でその位置が厳密に変更されます。 移動するたびに深さが減少するため、各トークンは O(高さ) 回しか移動できませんが、ジャンプが大きくなり、複数のステップが崩壊する可能性があることも観察されています。 

宛先を効率的に計算するために、ジャンプできるようにバイナリ リフティング祖先を前処理します。`d[v]`ステップ数は O(log n) です。 各トークンの移動は厳密にルートに向かって深さを増すため、すべての移動にわたる合計作業量は管理可能なままになります。 

したがって、最終的な解決策はイベント駆動型のシミュレーションです。クエリを処理し、影響を受けるトークンのみを移動し、頂点バケットを更新します。

 | --- | --- | --- | --- |
 | ブルートフォース | O(nq · n) | O(n) | 遅すぎる |
 | 最適 (バケット + リフティング シミュレーション) | O((n + q) log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ツリー構造を維持し、対数時間で上にジャンプできるようにバイナリ リフティングを前処理します。 

また、各トークンが現在どこにあるかを追跡する動的構造も維持します。 

1. ルート ツリーを構築し、各ノードの深さとバイナリ リフティング祖先を計算します。 これにより、遠く離れた祖先を計算できるようになります。`k`O(log n)で。 
2. コンテナを初期化する`pos[v]`現在頂点にあるすべてのトークンを保持しています`v`。 最初に、入力配列に従ってトークンを挿入します。`a`。 
3. 各ノードのジャンプ先を事前計算する`v`から移動した結果を意味します。`v`上向きに`d[v]`ステップ。 もし`d[v]`深さを超えると、宛先はルートになります。 
4. クエリを 1 つずつ処理します。 クエリ値の場合`c`、頂点のみを考慮します`v`そのような`t[v] = c`そして`pos[v]`は空ではありません。 
5. このような頂点ごとに、現在存在するすべてのトークンを取得します。`v`、宛先を計算し、それらを一括して移動します。`pos[new_v]`。 
6. クエリの処理後、すべてのトークンがルートにあるかどうかを確認します。 「はい」の場合、現在のクエリ インデックスを返します。 
7. 条件に到達せずにすべてのクエリが終了した場合は、リターンします。`-1`。 

### なぜ効果があるのか

 重要な不変条件は次のとおりです`pos[v]`常に、現在頂点にあるトークンが正確に含まれます`v`以前のすべてのクエリを処理した後。 各トークンの移動は、頂点タイプがクエリ タイプと一致する場合にのみ、トリガー クエリごとに 1 回だけ適用されます。 動きは他のトークンには依存せず、頂点の状態とクエリ シーケンスにのみ依存するため、位置によってトークンをグループ化すると正確さが保たれます。 すべての操作は元のプロセスを忠実にシミュレートしますが、トークンごとの冗長なスキャンを回避します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

n, q = map(int, input().split())
parent = [0] * (n + 1)
par = list(map(int, input().split()))
for i in range(2, n + 1):
    parent[i] = par[i - 2]

t = [0] + list(map(int, input().split()))
d = [0] + list(map(int, input().split()))
a = [0] + list(map(int, input().split()))
queries = list(map(int, input().split()))

LOG = 20
up = [[0] * (n + 1) for _ in range(LOG)]

for v in range(1, n + 1):
    up[0][v] = parent[v]

for j in range(1, LOG):
    for v in range(1, n + 1):
        up[j][v] = up[j - 1][up[j - 1][v]] if up[j - 1][v] else 1

depth = [0] * (n + 1)

for v in range(2, n + 1):
    depth[v] = depth[parent[v]] + 1

def jump(v, k):
    for i in range(LOG):
        if k & (1 << i):
            v = up[i][v]
    return v

pos = [[] for _ in range(n + 1)]
active = 0

for i in range(1, n + 1):
    if a[i]:
        pos[i].append(i)
        active += 1

ans = -1

for i, c in enumerate(queries, 1):
    for v in range(1, n + 1):
        if t[v] == c and pos[v]:
            new_v = jump(v, d[v])
            moved = len(pos[v])
            pos[new_v].extend(pos[v])
            active -= moved
            pos[v].clear()

    if active == 0:
        ans = i
        break

print(ans)
```このソリューションでは、まずバイナリ リフティング テーブルを構築します。`up`これにより、祖先のクエリに効率的に答えることができます。 の`jump`関数は、次のように定義された上向きの動きを実行します。`d[v]`。 

の`pos`配列は現在の頂点ごとにトークンを格納します。 各クエリは、タイプがクエリ値と一致する頂点のみを処理します。 このような頂点を処理するとき、すべてのトークンが計算された祖先に一度に移動されます。 の`active`カウンタはルートにまだ存在していないトークンの数を追跡し、一定時間の終了チェックを可能にします。 

微妙な点は、宛先がルートを超えているかどうかを明示的にチェックしていないことです。これは、バイナリ リフティングは、頂点 1 へのフォールバックが繰り返されることで自動的に飽和するためです。`1`。

 ## 特殊なケース

 重要なエッジ ケースは、1 つのディープ トークンを除いて、すべてのトークンが既にルートで開始されている場合です。 ルート以外の位置のみにエントリがあるため、アルゴリズムは依然として正しく動作します。`pos`、そして`active`カウンタは、最後のトークンがルートに到達した後の早期終了を保証します。 

複数のトークンが頂点を共有し、一緒に移動する場合にも、微妙なケースが発生します。 それらを一括で移動するため、転送後に頂点リストを確実にクリアする必要があります。 そうしないと、将来のクエリ間でトークンが重複してしまいます。 各トークンが 1 つだけ出現するという不変式`pos[v]`リストは正確さを保証し、二重カウントを防ぎます。
