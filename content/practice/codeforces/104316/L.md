 ## 解決策
 ## 問題の理解

 キャレットとアンダースコアの 2 文字のみから構成される文字列が与えられます。 文字列内のどこにでも追加の文字を挿入することはできますが、既存の文字を削除したり並べ替えたりすることはできません。 すべての挿入の後、結果の文字列はカバレッジ ルールを満たす必要があります。つまり、最終文字列のすべての位置が、2 つの許可されたパターン (つまり、2 つのキャレットで構成される 2 文字のパターン、または 3 文字のパターン キャレット アンダースコア キャレット) のいずれかの少なくとも 1 つの出現に属している必要があります。 これらの発生は重複することが許可されます。 

目標は、追加する文字数をできるだけ少なくしながら、このルールの下で元の文字列を「安全」にすることです。 

これを解釈する便利な方法は、最終文字列がタイルで完全に覆われている必要があり、各タイルが「^^」または「^_^」であり、すべての文字位置が少なくとも 1 つのタイルに含まれるということです。 元の文字列が完全にタイルでカバー可能な文字列のサブシーケンスになるように文字を挿入しようとしています。 

制約は小さく、文字列の長さは最大 100、テスト ケースは最大 100 です。 これにより、ヘビー ステート展開と組み合わせた文字列に対する 3 次構造またはそれより悪い構造が即座に排除されます。 二次または三次の動的プログラムは安全ですが、部分文字列に対する指数関数は不要です。 

微妙な問題は、単一文字の修正という意味では挿入がローカルではないことです。 1 つのアンダースコアを修正すると周囲の構造が強制される可能性があり、キャレットは複数の方法で重複するタイルに参加する可能性があります。 文字列の一部に関する決定により、後で追加の挿入が強制される可能性があるため、ローカル違反の素朴な貪欲な修復は失敗します。 

よくある失敗例は、アンダースコアの間隔が空いているため、アンダースコアを局所的に修正すると他の場所に隙間ができる場合に発生します。 たとえば、「_^_」のような文字列では、各アンダースコアを個別に修復しようとする可能性がありますが、カバレッジに必要な共有キャレット構造は両端を結合するため、単純なローカル修正により過剰カウントまたは過小カウントの挿入が修正されます。 

## アプローチ

 強引なアイデアは、あらゆる方法で文字を挿入して最終的な文字列を構築し、その結果が有効なタイルで完全にカバーできるかどうかを確認することです。 最終文字列の候補ごとに、すべての位置をスキャンし、各位置が有効な「^^」または「^_^」の出現に属しているかどうかを確認することで、カバレッジ条件を検証します。 ただし、文字を挿入する方法の数は文字列の長さに応じて増加し、最終的な長さを適度な境界に制限したとしても、検索スペースは膨大になります。 

重要な観察は、タイルをグローバルに明示的に推論する必要がないということです。 代わりに、最終文字列の有効性をローカルで強制することができます。文字が「^_^」パターンの中心であると判断するたびに、その隣の文字が強制的にキャレットになる必要があり、連続するキャレットのペアは「^^」タイルをサポートできます。 これにより、ローカルの一貫性を確保しながら、問題を左から右への文字列の構築に還元できます。 

元の文字列をサブシーケンスとして埋め込みながら、最終的な文字列の構築をシミュレートします。 各ステップで、元の文字列から次の文字を取得するか、文字を挿入するかを決定します。 文字を追加するたびに、新しく形成された長さ 3 のウィンドウが、アンダースコアの両側に隣接するキャレットを持たなければならないというルールに違反しないことを確認します。 これにより、グローバル カバレッジ制約がローリング ローカル チェックに変換されます。 

これにより、問題は、元の文字列内の位置と構築された文字列の最後の 2 文字に関する動的プログラミング プロセスに変わります。これは、新しい文字を追加すると無効な中心が作成されるかどうかを検証するために必要なのは最後の 2 文字だけであるためです。

 ## アルゴリズムのチュートリアル

 最終的な文字列を段階的に構築し、元の文字列のうち既に消費した量を追跡します。 

1. 元の文字列のインデックスと構築された文字列の最後の 2 文字で構成される状態を定義します。 最後の 2 文字は、新しい文字を追加することによって 1 つ後ろの位置を中心とする禁止された構成が作成されるかどうかを検出するのに十分です。 
2. どの状態からでも、構築された文字列にキャレットまたはアンダースコアのいずれかを追加することを検討します。 この追加された文字は挿入であるか、元の文字列内の次の未使用の文字と一致します。この場合、元の文字列内のポインタを進めます。 このモデルでは両方とも統一された方法で操作が可能でした。 
3. 文字を追加すると、可能な唯一の新しい制約が直ちに検証されます。 2 つ前の文字がアンダースコアの場合、現在の文字と前の文字は両方ともキャレットである必要があります。これは、これらの文字がそのアンダースコアの周囲に必要な「^_^」パターンを形成するためです。 この条件に違反すると、遷移は破棄されます。 
4. 元の文字列から文字を消費せずに文字を追加することを選択するたびに、コストが 1 ずつ増加します。 元の文字列から消費すればコストはかかりません。 私たちは常にこのコストを最小限に抑えることを目指しています。 
5. 元の文字列全体を消費し、有効な最終構成を構築するまで続行します。 すべての有効な完了に対する最小コストが答えです。 

### なぜ効果があるのか

 核となる不変条件は、完全に決定された時点で潜在的な「^_^」パターンの完全な「中心位置」が違反されていない場合に限り、部分的に構築された文字列は有効な完全にカバーされた文字列に拡張可能であるということです。 問題内のすべての制約は長さ 3 のウィンドウに対してローカルであり、ある位置がそのようなウィンドウの中心になると、DP 遷移のその時点でその隣接する位置は両方ともすでに固定されています。 これは、すでに明らかになっている違反を今後挿入しても修復できないこと、およびこれらのウィンドウを超える隠れた長距離条件が存在しないことを意味します。 その結果、無効な遷移を削除しても、グローバルに有効な構造は削除されず、有効な最終文字列はすべて、遷移のシーケンスによって到達可能になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**9

def solve():
    t = int(input())
    
    for _ in range(t):
        s = input().strip()
        n = len(s)
        
        # dp[i][a][b] = minimum insertions after consuming i chars of s
        # and ending with last two characters (a, b)
        # encode: 0 = '^', 1 = '_'
        
        dp = [[[INF] * 2 for _ in range(2)] for _ in range(n + 1)]
        dp[0][0][0] = 0  # dummy start state
        
        for i in range(n + 1):
            for a in range(2):
                for b in range(2):
                    cur = dp[i][a][b]
                    if cur == INF:
                        continue
                    
                    for c in range(2):
                        # check constraint for window (prev2, prev1, c)
                        # prev2 is unknown here; we simulate by storing last two only,
                        # so we interpret (a,b) as last two, c new => window is (a,b,c)
                        
                        # if b is '_' (1), then a and c must be '^' (0)
                        if b == 1:
                            if not (a == 0 and c == 0):
                                continue
                        
                        # determine next state
                        ni = i
                        cost = cur + 1
                        
                        if i < n:
                            if s[i] == ('^' if c == 0 else '_') and i < n:
                                # match original character
                                ni = i + 1
                                cost = cur
                        
                        # if we didn't consume s[i], we still keep i unchanged
                        
                        if ni <= n:
                            dp[ni][b][c] = min(dp[ni][b][c], cost)
        
        ans = min(dp[n][a][b] for a in range(2) for b in range(2))
        print(ans)

if __name__ == "__main__":
    solve()
```この実装は、構築された文字列の最後の 2 文字を 2 ビットの状態として保存します。 制約が強制可能になるのは 3 番目の文字が追加され、長さ 3 のウィンドウが完成するときだけであるため、これで十分です。 

各トランジションでは、キャレットまたはアンダースコアのいずれかの追加が試行されます。 追加された文字が元の文字列の次の未使用の文字と一致する場合、その文字は元の文字列から消費されるものとして扱われます。 それ以外の場合は、答えを増やす挿入です。 

重要なチェックはウィンドウの検証です。最後の 3 文字の中央がアンダースコアの場合、隣接する文字は両方ともキャレットである必要があります。 これは、3 番目の文字が追加されるとすぐに適用されます。 

DP は、考えられるプレフィックスの消費と最後の 2 文字の構成ごとに最適なコストを追跡します。 

## 実用的な例

 文字列「^_」について考えてみましょう。 DP は空の構築状態から始まり、徐々にキャラクターを配置しようとします。 最適なパスの 1 つは、カバレッジ ルールを満たす「^_^」を完成させるために最後に追加のキャレットを挿入することです。 

| ステップ | 私はsです | 最後の 2 つ | アクション | コスト |
 | --- | --- | --- | --- | --- |
 | 0 | 0 | (開始) | '^'を挿入 | 1 |
 | 1 | 0 | ^ | s | の '^' に一致します 1 |
 | 2 | 1 | ^^ | '^'を挿入 | 2 |
 | 3 | 1 | ^^ | '_' に一致 | 2 |
 | 4 | 2 | ^_^ | 仕上げ | 2 |

 これは、アンダースコアが単独では機能せず、「^_^」構造に埋め込まれ、少なくとも 1 つの挿入が強制される必要があることを示しています。 

ここで「^^」を考えてみましょう。 2 つのキャレットで「^^」タイルを形成できるため、これはすでに互換性があります。 

| ステップ | 私はsです | 最後の 2 つ | アクション | コスト |
 | --- | --- | --- | --- | --- |
 | 0 | 0 | (開始) | '^' に一致 | 0 |
 | 1 | 1 | ^ | '^' に一致 | 0 |
 | 2 | 2 | ^^ | 仕上げ | 0 |

 これは、アルゴリズムが可能な場合には挿入を行わずにキャレットをペアリングすることを自然に好むことを裏付けています。

 ## 特殊なケース

 単一のアンダースコアを入力すると、最も強い制約が強調表示されます。 DP は、有効な「^_^」パターンを許可するために周囲の両方のキャレットの挿入を強制する必要があり、それをカバーしないままにしようとするソリューションは、ウィンドウ制約をチェックするときにすぐに失敗します。 

「^_^_^」などの長い交互文字列は、重複動作を強調します。 各アンダースコアにはすでに部分的な構造があり、DP により、不必要に挿入を複製するのではなく、隣接するパターン間でキャレットが効率的に再利用されるようになります。
