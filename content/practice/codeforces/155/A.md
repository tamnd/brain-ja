 **解決時間:** 4 分 24 秒

 ## 解決策
 ## 問題の理解

 あるプログラマーのコンテストスコアが時系列で与えられます。 現在のスコアが以前のすべてのスコアより厳密に大きい場合、または以前のすべてのスコアより厳密に小さい場合、そのパフォーマンスは「素晴らしい」と呼ばれます。 

比較する以前のコンテストがないため、最初のコンテストはカウントされません。 

タスクは、シーケンスを処理し、プログラマーが新しい自己ベストまたは新しい自己ワーストを設定した回数をカウントすることです。 

たとえば、次のことを考えてみましょう。```
100 50 200 150 200
```最初のスコアは、最良のレコードと最悪のレコードの両方を初期化します。 

２つ目のスコアは、`50`、これまでのすべてのスコアよりも低いため、ワースト記録を更新します。 

３点目は、`200`、これまでのすべてのスコアよりも高いため、最高記録を更新します。 

残りのスコアはどちらの記録も破ることはできません。 

答えは`2`。 

制約は非常に小さいです。 コンテストの数は最大で`1000`、したがって、`O(n²)`制限時間内に問題なく解決できるでしょう。 それでも、この問題には、2 つの値のみを維持しながら配列を 1 回スキャンする、非常にクリーンな線形解決策があります。 

難しいのは、等価性を正しく処理することです。 スコアは、現在の最大値より厳密に大きいか、現在の最小値より厳密に小さい場合にのみカウントされます。 

次の入力を考えてみましょう。```
4
10 10 10 10
```正しい答えは、`0`。 

を使用した不注意な実装`>=`または`<=`繰り返された値を誤って記録破りのパフォーマンスとしてカウントする可能性があります。 

もう 1 つの微妙なケースは、レコードが繰り返し交互に切り替わる場合です。```
5
100 50 200 25 300
```正しい答えは、`4`。 

新しいスコアはそれぞれ現在の最小値または最大値を破っており、両方のレコードはイベントをカウントした直後に更新する必要があります。 

## アプローチ

 直接的なブルートフォース ソリューションでは、すべてのコンテストを以前のすべてのコンテストと比較してチェックします。 

コンテスト用`i`、コンテストをスキャンできます`0`を通して`i-1`そして、現在のスコアが以前のすべてのスコアより厳密に大きいか、または以前のすべてのスコアより厳密に小さいかを判断します。 

これが機能するのは、素晴らしいパフォーマンスの定義が以前のコンテストにのみ依存するためです。 ロジックは単純ですが、各ポジションは最大で比較される可能性があります。`n-1`以前の要素により、`O(n²)`時間の複雑さ。 

と`n = 1000`、これでも制限内で簡単に実行できます。 最悪の場合、約 100 万件の比較が実行されますが、これは最新のハードウェアでは簡単なことではありません。 

より迅速なアプローチは、実際には以前のスコアがすべて必要ではないことを観察することから生まれます。 どの時点でも、重要なのは次の 2 つの値だけです。```
current maximum score
current minimum score
```次のスコアが現在の最大値よりも大きい場合、最高パフォーマンス記録が破られます。 

現在の最小値よりも小さい場合、最悪のパフォーマンス記録が破られます。 

スコアを処理した後、対応するレコードを更新します。 

これにより、問題は、一定の追加メモリを使用した 1 回の左から右へのスキャンに軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 承認済み |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. コンテストの数とスコアのリストを確認します。 
2.両方を初期化します`best`そして`worst`最初のスコアで。 

最初のコンテストは最初の記録を確立するものであり、決して素晴らしいものとして数えられることはありません。 
3.初期化`answer = 0`。 
4. 2 番目のコンテストからスコアを繰り返します。 
5. 各スコアについて:

 スコアが厳密に次の値よりも大きい場合`best`、増分`answer`そして更新します`best`。 

スコアが厳密に以下の場合`worst`、増分`answer`そして更新します`worst`。 
6. すべてのスコアを処理した後、印刷します。`answer`。 

### なぜ効果があるのか

 あらゆる段階で、`best`これまでに確認された最大スコアを保存し、`worst`これまでに確認された最小スコアを保存します。 

新しいスコアを処理する場合、考えられる可能性は 3 つだけです。```
score > best
score < worst
worst <= score <= best
```最初のケースは、プログラマーが新たな最高スコアを達成したことを意味します。 2 番目のケースは、新たな最低スコアを意味します。 3 番目のケースは、記録が破られなかったことを意味します。 

アルゴリズムは新しいレコードを数えた直後にレコードを更新するため、不変条件はスキャン全体を通じて正しいままです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    scores = list(map(int, input().split()))

    best = scores[0]
    worst = scores[0]
    answer = 0

    for score in scores[1:]:
        if score > best:
            answer += 1
            best = score
        elif score < worst:
            answer += 1
            worst = score

    print(answer)

solve()
```この解決策は、入力を読み取り、最初のコンテスト スコアを使用して両方のレコード値を初期化することから始まります。 

最初のコンテストでは以前の記録を破ることができないため、ループは 2 番目の要素から始まります。 

の`if`ステートメントは、現在のスコアがこれまでに確認された最高スコアを超えているかどうかを確認します。 そうであれば、素晴らしいパフォーマンスをカウントし、最高値を更新します。 

の`elif`逆方向を扱います。 使用する`elif`2番目の独立者の代わりに`if`数値は現在の最大値よりも大きく、同時に現在の最小値よりも小さいことはできないため、論理的にクリーンです。 

厳密な比較が不可欠です。 同じスコアは記録破りのパフォーマンスとしてカウントされません。 

このソリューションでは、入力配列を超えて 3 つの整数だけを格納するため、定数の追加メモリのみが使用されます。

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io

def solve():
    input = sys.stdin.readline

    n = int(input())
    scores = list(map(int, input().split()))

    best = scores[0]
    worst = scores[0]
    answer = 0

    for score in scores[1:]:
        if score > best:
            answer += 1
            best = score
        elif score < worst:
            answer += 1
            worst = score

    print(answer)

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    output = sys.stdout.getvalue()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return output

# provided samples
assert run("5\n100 50 200 150 200\n") == "2\n", "sample 1"

assert run("10\n1 2 3 4 5 4 3 2 1 0\n") == "5\n", "sample 2"

# minimum size
assert run("1\n100\n") == "0\n", "single contest"

# all equal values
assert run("4\n10 10 10 10\n") == "0\n", "equal scores are not amazing"

# alternating new records
assert run("5\n100 50 200 25 300\n") == "4\n", "multiple alternating records"

# decreasing sequence
assert run("5\n9 8 7 6 5\n") == "4\n", "every contest breaks worst record"

# off-by-one style check
assert run("3\n5 10 10\n") == "1\n", "equal maximum should not count twice"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1 / 100`|`0`| 最初のコンテストはカウントされません |
 |`10 10 10 10`|`0`| 同じスコアは無視されます。 
|`100 50 200 25 300`|`4`| レコードは繰り返し交互に使用できます。 
|`9 8 7 6 5`|`4`| スコアが低くなると最小値を超えます。 
|`5 10 10`|`1`| 等しい最大値は再度カウントされません。 

## 特殊なケース

 すべてのスコアが同一である場合を考えてみましょう。```
4
10 10 10 10
```アルゴリズムは以下から始まります。```
best = 10
worst = 10
answer = 0
```残りのスコアはすべて両方のレコードに等しいため、どちらの条件もトリガーされません。 

最終的な答えは残っています`0`厳密な改善または低下は発生しなかったので、これは正しいです。 

ここで、繰り返される最大値を考えてみましょう。```
3
5 10 10
```2 番目のスコアを処理した後:```
best = 10
answer = 1
```3 番目のスコアは以下に等しい`best`、ただしそれを超えません。 比較しているので、`>`それよりも`>=`、アルゴリズムはそれを再度カウントすることを正しく回避します。 

最後に、レコードを交互に変更することを検討します。```
5
100 50 200 25 300
```レコードの順序は次のようになります。```
100 -> new minimum 50 -> new maximum 200 -> new minimum 25 -> new maximum 300
```新しいスコアはそれぞれ現在の境界の 1 つを超えるため、答えは毎回増加します。 アルゴリズムは、驚くべきパフォーマンスの直後に走行記録を更新するため、これを自然に処理します。
