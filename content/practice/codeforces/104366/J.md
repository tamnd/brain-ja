 ## 解決策
 ## 問題の理解

 すべてのエッジに単位コストがあり、グラフが強く接続されていることが保証されている有向グラフが与えられます。 2 つのワーカーが頂点 1 から開始します。一連のリクエストが到着し、各リクエストは修復を実行するために訪問する必要がある頂点を指定します。 

すべてのリクエストに対して、2 人のワーカーのうち 1 人がそれを処理するために選択されます。 そのワーカーは、現在の場所からグラフ内の最短パスに沿って要求された頂点まで移動し、その後の要求に備えてその頂点に留まります。 他のワーカーは、そのリクエスト中に移動しません。 

各作業者は時間の経過とともに総移動距離を蓄積します。 目的は、総移動距離を最小限に抑えることではなく、負荷のバランスをとることです。すべてのリクエストが処理された後に、アリスとボブによって蓄積された 2 つの合計距離のうち、大きい方を最小限に抑えたいと考えています。 

重要な構造は、割り当てが順序的であり、位置に関して元に戻すことができないことです。リクエストが割り当てられると、そのワーカーの位置はそのリクエストの頂点に永久に変更されます。 将来の最短経路は現在の位置に依存するため、各ステップでの決定は将来の移動コストに影響します。 

グラフ サイズは小さく、頂点数は最大 80、リクエスト数は最大 80 です。 これにより、枝刈りを行わずに状態にわたる大規模な指数関数的分岐に依存するものは直ちに排除されますが、位置のペアに対する動的プログラミングが可能になります。 ユニット エッジの存在と強力な接続により、頂点のすべてのペア間に最短パスが確実に存在するため、すべてのペアの最短パスを安全に事前計算できます。 

現在のリクエストを常に近いワーカーに割り当てるような単純な貪欲な戦略は、将来の構造を無視するため失敗します。 従業員がグラフの「悪い」領域に早期に移動すると、たとえ当面の移動が安かったとしても、将来的に大きな移動が発生する可能性があります。 決定は一連の流れ全体を考慮する必要があります。 

さらに微妙な失敗は、累積コストを適切に追跡せずにポジションだけをバランスさせることによって発生します。 2 つの同一のポジション構成は、各従業員がすでに費やした予算に応じて、残りの実現可能性がまったく異なる可能性があります。 

## アプローチ

 直接的な総当たりのアイデアは、アリスまたはボブのいずれかへの各リクエストの可能なすべての割り当てを試みることです。 q 個のリクエストがあるため、2^q 個の可能性が得られます。 割り当てごとに、動きをシミュレートし、事前に計算された距離行列を使用して最短経路距離を計算します。 これにより、答えは正しく計算されますが、可能性の数は指数関数的に増加し、約 2^80 に達し、実行可能な制限をはるかに超えます。 

重要な観察は、いつでもシステムの状態が 3 つの情報によって完全に記述されるということです。つまり、リクエスト シーケンスでどこまで処理したか、アリスが現在どこにいるか、ボブが現在どこにいるかです。 これらが修正されると、累積コストを除いて、将来のすべての決定は、どのようにしてこの状態に到達したかとは無関係になります。 

これは、位置のペアに対する動的プログラミングの定式化を示唆しています。 ただし、目的は単純な合計ではなく、max(SA, SB) の可能な最小値です。SA​​ の部分的な最適性だけでは最大値の最適性が保証されないため、単純な最小化が複雑になります。 

解決策は、最終的な答えをしきい値の問題として扱うことです。 最大負荷を直接最小化する代わりに、どちらのワーカーも指定された制限 T を超えないようにすべてのリクエストを処理できるかどうかを尋ねます。固定 T の実現可能性をテストできれば、最小の有効な T を二分探索できます。

実現可能性をチェックするために、ステップと位置のペアにわたって DP を実行し、両方のワーカーの累積コストが T 以内に収まる到達可能なすべての構成を保存します。q と n が小さいため、DP セルごとに一連の状態を維持する余裕があります。 各状態は、現在のリクエストをアリスまたはボブに割り当て、対応する最短パス コストを追加し、しきい値を超える遷移を破棄することによって遷移します。 

これにより、この問題は、状態ごとにサイズ 2 の遷移を伴う、サイズ O(q · n²) の状態グラフにおける階層化された到達可能性の問題に変わります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース割り当て | O(2^q · q + n^3) | お(1) | 遅すぎる |
 | DP + 答えの二分探索 | O(log V · q · n² · n²) ≈ O(log V · q · n³) | O(n² · 状態) | 承認済み |

 ここで、V は最大 80 × 80 で制限される、可能な最大の旅行コストです。 

## アルゴリズムのチュートリアル

 ### すべてのペアの最短パス

 まず、Floyd-Warshall を使用して、頂点のすべてのペア間の最短経路距離を計算します。 これが必要なのは、すべての遷移がワーカーの現在位置と次のリクエスト頂点の間の最短距離に依存するためです。 

### 固定制限 T の実現可能性 DP

 ここで、両方の作業者の合計移動距離を T 以内に抑えることが可能かどうかを確認します。 

1. アリスとボブの両方が頂点 1 にあり、両者の消費距離が 0 であるステップ 0 の DP を初期化します。 これが唯一の有効な開始設定です。 
2. リクエストを 1 つずつ処理します。 ステップ i では、各 DP 状態はアリスとボブの現在の位置のペアを、T を決して超えない暗黙的な累積コストとともに表します。 
3. 各状態 (a、b) について、次の要求頂点 x をアリスに割り当てることを検討します。 アリスは a から x に移動し、コストを dist[a][x] だけ増加させますが、ボブは b に留まります。 これにより、アリスの新しいコストが T を超えない場合、新しい状態 (x, b) が作成されます。 
4. 同様に、リクエストを Bob に割り当てることを検討してください。 ボブは b から x に移動し、コストが増加しますが、アリスは a に留まります。 これにより、コスト制約が満たされた場合に状態 (a, x) が作成されます。 
5. 現在のリクエストのすべての状態を処理した後、到達不能な設定をすべて破棄し、次のリクエスト層に進みます。 
6. すべてのリクエストを処理した後、少なくとも 1 つの状態が到達可能な状態のままであれば、しきい値 T は実現可能です。 

### 答えの二分探索

 0 から可能な最大総移動量までの範囲で最小の T を二分探索します。 上限は、グラフ内の最大最短経路距離の q 倍とみなして問題ありません。 

各中間点 T に対して、上記の実現可能性 DP を実行します。 

### なぜ効果があるのか

 どのワーカーも現在の制限 T を超えないという制約の下で、リクエストのプレフィックスを処理した後、DP 状態は常に、到達可能なポジションの構成を正確に保存します。有効な完全な割り当ては、これらの状態を通る一意のパスを誘導します。 逆に、DP 内のすべての遷移は有効な割り当て決定に対応します。 制約を尊重しながら各ステップで可能なすべての割り当てを探索するため、DP は実行可能な空間全体をキャプチャします。 次に、二分探索により、最後のリクエスト後にこの実行可能なスペースが空ではない最小の T が見つかります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**9

def floyd(n, dist):
    for k in range(n):
        for i in range(n):
            dik = dist[i][k]
            if dik == INF:
                continue
            di = dist[i]
            dk = dist[k]
            for j in range(n):
                nd = dik + dk[j]
                if nd < di[j]:
                    di[j] = nd

def can(n, q, req, dist, T):
    cur = set()
    cur.add((0, 0, 0, 0))  # (a, b, sa, sb)

    for x in req:
        x -= 1
        nxt = set()
        for a, b, sa, sb in cur:
            # assign to Alice
            da = dist[a][x]
            nsa = sa + da
            if nsa <= T:
                nxt.add((x, b, nsa, sb))

            # assign to Bob
            db = dist[b][x]
            nsb = sb + db
            if nsb <= T:
                nxt.add((a, x, sa, nsb))

        if not nxt:
            return False
        cur = nxt

    return True

def solve():
    n, m = map(int, input().split())
    dist = [[INF] * n for _ in range(n)]
    for i in range(n):
        dist[i][i] = 0

    for _ in range(m):
        u, v = map(int, input().split())
        u -= 1
        v -= 1
        dist[u][v] = 1

    floyd(n, dist)

    q = int(input())
    req = list(map(int, input().split()))

    lo, hi = 0, 80 * 80
    ans = hi

    while lo <= hi:
        mid = (lo + hi) // 2
        if can(n, q, req, dist, mid):
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1

    print(ans)

if __name__ == "__main__":
    solve()
```フロイド-ウォーシャル ステップは完全な距離行列を構築するため、DP 移行中に一定時間内にすべての移動コストをクエリできます。 実行可能性関数は、到達可能なポジションの構成と累積コストをすべて明示的に追跡し、指定された制限内で有効な割り当てが失われないことを保証します。 

二分探索では、この実現可能性チェックがラップされ、可能な限り最小の値が見つかるまで、許容最大負荷が徐々に厳しくなります。 

実装の微妙な詳細は、状態が蓄積された SA と SB を含む完全なタプルとして保存されることです。 しきい値を超える状態はすべて排除され、T の下での実現可能性による場合を除いて、異なるコスト分布を比較する必要がないため、これで十分です。

 ## 特殊なケース

 頂点間に複数の最短パスが存在する場合、特殊なケースが発生します。 すべてのエッジには単位重みがあるため、パスが異なれば、コストは同じですが中間構造が異なる可能性があります。 ただし、重要なのは最終的な最短距離のみです。 Floyd-Warshall 前処理により、すべての遷移で真の最小コストが使用されることが保証されるため、DP はパス ID に依存しません。 

もう 1 つの重要な状況は、同じリクエスト頂点が繰り返し現れる場合です。 その場合、最適な戦略は、多くの場合、単一の位置から長く繰り返されるパスの蓄積を避けるために作業者を交代させます。 両方の割り当てが各ステップで利用可能なままであり、実現可能性フィルタリングが制限 T を尊重する分布のみを保存するため、DP はこれを自然に捕捉します。 

最後の微妙なケースは、1 人のワーカーが早期に遠くのリージョンに強制的に移動させられ、そのワーカーに割り当てられた場合、後のリクエストが高価になる場合です。 DP は、到達可能なポジションのペアをすべて維持することで早期のコミットを回避するため、後の決定でも将来のリクエストを他のワーカーに再割り当てでき、貪欲な戦略が失う可能性のある実現可能性を維持します。
