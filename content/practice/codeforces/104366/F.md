 ## 解決策
 ## 問題の理解

 時間の経過とともに変化するチャット グループをシミュレートしています。 ユーザーはグループに参加するかメッセージを送信しますが、グループにはメンバーを強制的に削除できる厳格なルールがあります。 

最初のルールは容量の制約です。 グループには最大 N 人を収容できます。 グループがすでにいっぱいのときに新しい人が参加しようとすると、スペースを空けるために現在参加している人が削除されます。 この問題は、削除されたユーザーが、現在のメンバーの中で最も最近のアクティビティが最も古いユーザーであることを示しています。これは、最も最近アクティブでなかったユーザーが削除されることを意味します。 

これに加えて、より攻撃的な 2 番目のルールがあります。 最終参加時刻から数えて、両方のエンドポイントを含めて、長さ T のスライディング タイム ウィンドウ内にいずれかのメンバーが K 個のメッセージを送信すると、そのメンバーはすぐに追い出されます。 重要なのは、最後に参加した後のメッセージのみが考慮されるため、参加するとその人のカウント ウィンドウがリセットされることです。 

参加するたびに「hello」と呼ばれるメッセージが自動的に生成されるため、新しく参加したメンバーには常に少なくとも 1 つのメッセージがすぐに表示されます。 

入力は、時間順に並べられたイベントのストリームです。 イベントごとに、参加者またはメッセージを送信している人が表示されます。 その人がイベント時間前に現在グループに参加している場合、イベントはメッセージです。 それ以外の場合は結合です。 タスクは、すべてのイベントを処理し、すべてのキックアウトを時系列で出力し、最後に残りのメンバーを出力することです。 

制約は最大 100 万のイベントと 100 万のユーザーに達し、時間値は最大 10 億に達します。 これにより、イベントごとにすべてのメンバーをスキャンしたり、単純なデータ構造でメンバーごとのスライディング ウィンドウを維持したりするアプローチは即座に除外されます。 アクティブなメンバーに対して繰り返し反復するソリューションは、最悪の場合、二次的な動作に低下し、失敗します。 

微妙な問題は、2 つの立ち退きルール間の相互作用にあります。 ユーザーは、他のユーザーと比較した非アクティブさ (容量ルール)、またはタイム ウィンドウ ルールのメッセージ スパムのいずれかの理由で削除される可能性があります。 もう 1 つの注意が必要な点は、参加するとメッセージ ウィンドウがリセットされるため、古いメッセージ履歴が無効になり、単純なプレフィックス カウントが正しくなくなることです。 

素朴な実装を壊すことが多い小さなエッジケースは、結合、キック、再結合の繰り返し動作です。 ユーザーが時間 1 に参加し、K 個のメッセージをすぐに送信し、キックされて、後で再参加したとします。 2 回目の結合以降のメッセージのみが重要であり、以前の履歴が漏洩してはなりません。 

## アプローチ

 ブルート フォース シミュレーションでは、グループ メンバーの完全なリストが維持され、削除が必要な場合は、イベントごとに、最も最近アクティブでなかったメンバーが再計算されます。 各メッセージ イベントについて、完全な履歴またはすべてのイベントをスキャンして、最後の T 時間枠内に各ユーザーが送信したメッセージの数も再計算します。 最悪の場合、M 個のイベントのそれぞれが N 人全員のユーザーのスキャンをトリガーし、各ユーザーが最大 M 個のメッセージを保持する可能性があります。 これにより、O(MN) のオーダーの複雑さが生じますが、これは 100 万件のイベントでは実現不可能です。 

重要な観察点は、どちらのルールも最近のアクティビティ、つまり容量のエビクションの場合は最新のメッセージ時間、スパムのエビクションの場合はスライディング ウィンドウ カウントのみに依存するということです。 これは、完全な履歴ではなく、ユーザーごとのコンパクトな状態を維持することを示唆しています。 

各ユーザーについて必要なのは、最後の参加時刻、その参加後のメッセージ タイムスタンプのデキュー、および最新のアクティビティ時間だけです。 この場合、キャパシティー ルールは、アクティブ ユーザーの中から最小の「最終アクティビティ時間」を常に抽出するという問題になります。 これは古典的な優先キューの使用例ですが、アクティビティ時間が変化するため、遅延更新が行われます。 

スライディング ウィンドウ制約の場合、すべてのメッセージを保存するのではなく、ユーザーごとにキューを維持し、現在時刻から T を引いたものより古いタイムスタンプを破棄します。これにより、各メッセージの挿入と削除が最大 1 回行われることが保証され、償却 O(1) メンテナンスが行われます。

これにより、ヒープの更新により各イベントが対数時間で処理され、ユーザーごとのキューが全体的に線形のままになるシステムが実現します。

 | 最適 | O(M log N) | お(お) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは3つの核となる構造を維持しています。 アクティブなメンバーの辞書、ユーザーごとのメッセージ タイムスタンプのデキュー、およびエビクション決定のための最終アクティビティ時間順に並べられたヒープ。 

各イベントは次のように処理されます。 

1. ユーザーが現在グループに属していない場合、イベントは参加として扱われます。 参加タイムスタンプを割り当て、自動「hello」メッセージを表す単一のエントリでメッセージ キューを初期化します。 また、最後のアクティビティ時刻を参加時刻に設定し、この値をキーとしたヒープにプッシュします。 これにより、それらは立ち退きの決定に対して即座にアクティブであるとみなされるようになります。 
2. 結合を処理する前にグループがいっぱいの場合は、アクティブ セット内でまだ有効なユーザーが見つかるまで、最終アクティビティ時間が最も短いユーザーをヒープから繰り返し削除します。 そのユーザーは追い出されます。 エビクション時間を記録し、非アクティブとしてマークします。 ヒープには古いエントリが含まれている可能性があるため、ポップされた要素を使用する前にメンバーシップを確認します。 
3. ユーザーがすでにグループに属している場合、イベントはメッセージです。 タイムスタンプをメッセージ デキューに追加し、最後のアクティビティ時刻を現在時刻に更新して、新しいエントリをヒープにプッシュします。 
4. メッセージを挿入するたびに、スライディング ウィンドウ ルールが適用されます。 間隔 [t - T, t] の外にあるタイムスタンプを両端キューの左側から削除します。 残りのメッセージ数が K 以上に達すると、ユーザーは直ちに追い出されます。 イベントを記録し、アクティブ セットから削除します。 
5. ユーザーが何らかの理由でキックアウトされると、そのユーザーは非アクティブとしてマークされます。 それらの将来のヒープ エントリは、抽出中に無視されます。 

重要な考え方は、ヒープ エントリは決して明示的に削除されないということです。 代わりに、エントリがポップされたときにユーザーがまだアクティブであるかどうかをチェックすることによる遅延削除に依存します。 

### なぜ効果があるのか

 このアルゴリズムは、すべてのアクティブ ユーザーが最新のアクティビティを反映する少なくとも 1 つのエントリを持ってヒープ内に表現され、メッセージ デキューには最後の参加以降のメッセージが正確に含まれるという不変条件を維持します。 どちらのエビクション ルールもこれら 2 つの情報のみに依存するため、履歴データは必要ありません。 レイジー ヒープ クリーンアップでは、エビクション候補を選択するときに各ユーザーの最新の有効な状態のみが考慮されるため、古いアクティビティ レコードが複数存在する場合でも正確さが保証されます。 

## Python ソリューション```python
import sys
import heapq
from collections import deque

input = sys.stdin.readline

def solve():
    N, M, T, K = map(int, input().split())

    active = set()
    last_join = {}
    last_activity = {}
    msgs = {}

    # (last_activity_time, user)
    heap = []
    events = []
    kicks = []

    def kick(user, t):
        if user in active:
            active.remove(user)
            kicks.append((t, user))

    for _ in range(M):
        t, p = map(int, input().split())

        if p not in active:
            # join
            if len(active) >= N:
                while heap:
                    time, u = heapq.heappop(heap)
                    if u in active and last_activity[u] == time:
                        kick(u, t)
                        break

            active.add(p)
            last_join[p] = t
            msgs[p] = deque([t])  # hello message
            last_activity[p] = t
            heapq.heappush(heap, (t, p))

        else:
            # message
            msgs[p].append(t)
            last_activity[p] = t
            heapq.heappush(heap, (t, p))

            # sliding window
            dq = msgs[p]
            while dq and dq[0] < t - T:
                dq.popleft()

            if len(dq) >= K:
                kick(p, t)

    print(len(kicks), len(active))
    for t, u in kicks:
        print(t, u)
    print(*sorted(active))

if __name__ == "__main__":
    solve()
```この実装は、メンバーシップの追跡を注文ロジックから分離することに重点を置いています。 の`active`set は O(1) メンバーシップ チェックを提供します。 ヒープには、最後のアクティビティごとに候補のエビクション順序が保存されますが、同じユーザーに対して複数の更新が存在するため、各ヒープ エントリを現在のアクティビティに対して検証します。`last_activity`。 

ユーザーごとの両端キューは、スライディング ウィンドウ制約にとって重要です。 これにより、関連するタイムスタンプのみが保存され、各タイムスタンプが正確に 1 回プッシュおよびポップされることが保証されます。 

キック機能は削除ロジックを一元化するため、キャパシティ ルールとスパム ルールの両方で同一の状態遷移が使用されます。 

微妙な点は、古いエントリが残っている場合でも、すべてのメッセージで常にヒープを更新することです。 これにより、遅延削除が可能になり、コストのかかるヒープ更新が回避されます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、結合とリセットの繰り返し動作です。 ユーザーは参加し、メッセージ履歴を蓄積し、キックされ、後で再参加します。 アルゴリズムは、結合のたびに両端キューをリセットすることでこれを処理し、古いメッセージが決して考慮されないようにします。 

もう 1 つの特殊なケースは、古いヒープ エントリです。 ユーザーのヒープ内に複数の古いアクティビティ タイムスタンプが存在する可能性があります。 遅延検証ステップにより、エントリの一致のみが保証されます。`last_activity`は有効であるため、正確さに影響を与えることなく、古いエントリは無視されます。 

最後の微妙なケースは、メッセージの後に両方のエビクション ルールが同時に満たされることです。 このアルゴリズムは、メッセージの更新直後に常にスライディング ウィンドウ ルールをチェックし、さらなる容量決定の前に削除が適用されるため、一貫した状態遷移が保証されます。
