 ## 解決策
 ## 問題の理解

 私たちには、あなたとあなたのフォロワーの 2 人で一定量の運搬能力が割り当てられています。 各テスト ケースは、小さな「戦利品の選択」問題を説明します。武器には剣と戦斧の 2 種類があり、各タイプにはアイテムごとの重量が固定されており、ショップの在庫には限りがあります。 目標は、それぞれの配送業者がそれぞれのキャパシティーを超えず、持ち込む商品の総数ができるだけ多くなるように、2 つの運送業者に分担して引き取る各タイプの商品の数を選択することです。 

重要なのは、同じアイテムプールを共有する 2 つの独立したナップザックのような制約の下で、重量や価値を最大化することではなく、単に数を最大化することです。 各アイテムの種類は同じなので、各人が持つ剣と斧の数だけが決まります。 

この制約により、テスト ソリューションごとに O(1) または O(log n) が求められます。 最大 10^4 のテスト ケースとテスト全体でアイテムの合計数が制限されているため、アイテムごとのシミュレーションや、大量の在庫を反復する貪欲な再構築を行う余裕はありません。 テストごとに一定時間で再計算するソリューションが期待されています。 

微妙な失敗例は、重量効率の違いを考慮せずに、最初に 1 人に貪欲にアイテムを割り当てる単純な戦略によって発生します。 たとえば、剣が斧よりもはるかに軽い場合、1 つの空母で最初に斧を取ると、交換によって実現可能性が向上したとしても、総数を減らすことができます。 もう 1 つの失敗は、最適な配分がローカルなフィルではなくグローバルなアイテム比率に依存することを無視して、両方のキャリアを独立して処理したことに起因します。 

中心となる問題は、アイテム タイプが 2 つだけで、境界のある 2 つのナップザックの数を最大化していることです。そのため、構造は単純化できますが、すぐには明らかではありません。 

## アプローチ

 強引な解釈では、2 人の間で可能な限りの剣と斧の分割が試みられます。 分割ごとに、あなたとあなたのフォロワーに渡す剣の数を決定し、斧についても同様に、容量の制限を確認します。 これはすぐに実行不可能になります。合計数だけを考慮したとしても、アイテムを 2 つのナップザックに分散する必要があり、O(cnt_s * cnt_w) またはさらに悪い組み合わせ動作が発生します。 

重要な観察は、各武器タイプ内で、重量を除いてすべての項目が同一であるということです。 これにより、問題は、剣と斧の合計数をグローバルに選択し、その合計数を 2 つのナップザックに分割できるかどうかを検証することに変わります。 持っていく剣の数を決めたら、常に最初に残りの 2 つの選択肢のうち軽い方を各人に貪欲に満たすのが最善の戦略です。そうすることでユニット容量あたりのアイテム数が最大化されるからです。 

したがって、問題は 1 つの次元に集約されます。重量によるアイテム タイプの特定の順序では、両方のナップザックにまたがってできるだけ多くの軽いアイテムを優先的に取り、その後、残りの容量を重いアイテムに使用する必要があります。 

これは、両方の可能な順序を考慮する貪欲な構造につながります。つまり、剣を軽いものとして扱い、斧を軽いものとして扱い、それぞれの仮定の下で最適な梱包をシミュレートし、最大値を取得します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 項目数の指数関数 | お(1) | 遅すぎる |
 | 注文による最適な貪欲さ | テストごとに O(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 2 ケースの貪欲評価を使用して、各テスト ケースを個別に解決します。

1. どの武器の種類が軽いかを特定します。 これにより、固定容量の制約の下で軽いアイテムを最初に取得することでカウントが最大化されるため、どのアイテムを優先する必要があるかが決まります。 
2. まず最初に 1 人目、次に 2 人目でできるだけ多くの軽い武器を取ることをシミュレートします。 これは、利用可能な在庫によって制限される、重量による容量の整数除算を使用して行われます。 
3. 軽い武器を割り当てた後、両方の人の残りの容量を計算します。 
4. 残りの容量を使用してより重い武器を取り、再び残りのスペースと利用可能なストックの順に両方の人々を貪欲に満たします。 
5. この注文で受け取ったアイテムの合計を計算します。 
6. 剣と斧の役割を交換して、プロセス全体を繰り返します。 
7. 2 つのシミュレーションの最大の結果を出力します。 

シミュレーションが 2 つだけ必要な理由は、最適な梱包はどの商品が「単位重量あたりより安く」扱われるかによってのみ決まるからです。 タイプが 2 つしかないため、意味のある順序は 2 つだけです。 

### なぜ効果があるのか

 正しさは単調な交換議論から得られます。 軽いアイテムがどちらかのナップザックにまだ収まる間に、より重いアイテムが取られた場合、重いアイテムをより軽いアイテムに置き換えても、実現可能性が低下することはなく、常にアイテムの数が増加または保存されます。 したがって、最適な解決策では、軽いアイテムが未使用のまま残されることはなく、代わりに重いアイテムが使用されます。 これにより、すべての最適解が 2 つの可能な重み順序のいずれかを尊重する順序構造が強制され、両方をチェックすることですべてのケースがカバーされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(p, f, cs, cw, s, w):
    def simulate(first_cap, second_cap, cnt1, cnt2, w1, w2):
        # ensure w1 is lighter or equal than w2 is not required here;
        # we just simulate fixed order: type1 then type2
        
        # take type1
        take1_first = min(cnt1, first_cap // w1)
        first_cap -= take1_first * w1
        
        take1_second = min(cnt1 - take1_first, second_cap // w1)
        second_cap -= take1_second * w1
        
        rem1 = cnt1 - take1_first - take1_second
        
        # take remaining type1 using leftover space greedily
        take1_second_extra = min(rem1, second_cap // w1)
        second_cap -= take1_second_extra * w1
        
        rem1 -= take1_second_extra
        
        # now type2
        take2_first = min(cnt2, first_cap // w2)
        first_cap -= take2_first * w2
        
        take2_second = min(cnt2 - take2_first, second_cap // w2)
        second_cap -= take2_second * w2
        
        rem2 = cnt2 - take2_first - take2_second
        
        take2_second_extra = min(rem2, second_cap // w2)
        second_cap -= take2_second_extra
        
        rem2 -= take2_second_extra
        
        return (cnt1 - rem1) + (cnt2 - rem2)

    # try both orders
    res1 = simulate(p, f, cs, cw, s, w)
    res2 = simulate(p, f, cw, cs, w, s)
    return max(res1, res2)

t = int(input())
for _ in range(t):
    p, f = map(int, input().split())
    cs, cw = map(int, input().split())
    s, w = map(int, input().split())
    print(solve_case(p, f, cs, cw, s, w))
```実装では、グリーディ パッキング ロジックを直接エンコードします。 シミュレーション機能は、まず 1 つの武器タイプを処理し、2 番目のタイプに移る前に、両方のナップザックにできるだけ多くの武器を収めようとします。 各ステップでは残りの容量を明示的に尊重し、過剰充填がないようにします。 

主要な実装の詳細は、タイプごとに 2 つのフェーズで 2 つのキャリア間の割り当てを分割することです。最初に各人を個別に満たし、次に残りのスペースを残りのアイテムに貪欲に使用します。 これにより、二重カウントが回避され、すべての容量がその注文に対して最適に使用されるようになります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    output = []
    t = int(input())
    
    def solve_case(p, f, cs, cw, s, w):
        def simulate(first_cap, second_cap, cnt1, cnt2, w1, w2):
            take1_first = min(cnt1, first_cap // w1)
            first_cap -= take1_first * w1
            
            take1_second = min(cnt1 - take1_first, second_cap // w1)
            second_cap -= take1_second * w1
            
            rem1 = cnt1 - take1_first - take1_second
            
            take1_second_extra = min(rem1, second_cap // w1)
            second_cap -= take1_second_extra * w1
            rem1 -= take1_second_extra
            
            take2_first = min(cnt2, first_cap // w2)
            first_cap -= take2_first * w2
            
            take2_second = min(cnt2 - take2_first, second_cap // w2)
            second_cap -= take2_second * w2
            
            rem2 = cnt2 - take2_first - take2_second
            
            take2_second_extra = min(rem2, second_cap // w2)
            second_cap -= take2_second_extra * w2
            rem2 -= take2_second_extra
            
            return (cnt1 - rem1) + (cnt2 - rem2)

        return max(simulate(p, f, cs, cw, s, w),
                   simulate(p, f, cw, cs, w, s))

    for _ in range(t):
        p, f = map(int, input().split())
        cs, cw = map(int, input().split())
        s, w = map(int, input().split())
        output.append(str(solve_case(p, f, cs, cw, s, w)))
    
    return "\n".join(output)

 ## 特殊なケース

 1 つのナップザックにはすべての軽いアイテムを入れるのに十分な大きさがあるが、もう 1 つはそうでない場合、重大なエッジ ケースが発生します。 たとえば、重量 1、p = 10、f = 1 の剣が 10 本ある場合、最適解は均等に分割されず、すべての剣が最初のキャリアに割り当てられます。 このアルゴリズムは、常に最初に 1 つのナップザックを満たしてから 2 番目のナップザックを使用することでこれに対処し、容量が途中で無駄にならないようにします。 

もう 1 つのケースは、重みが等しい場合です。 s = w の場合、どのような順序付けも有効であり、項目タイプ間の厳密な不平等を仮定しないため、シミュレーションは依然として正しい結果を生成します。
