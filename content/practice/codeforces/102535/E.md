 ## 解決策
 ## 問題の理解

 入力は、植物のいくつかのコレクションを記述します。 コレクションは大文字の文字列として記述され、各文字は 1 つの植物を表し、その重みはアルファベット内の位置によって決まります。 各テスト ケースの最初の値は、栽培エリアがサポートできる最大総重量です。 タスクは、コレクション内のすべての植物の重量の合計がその制限内にあるかどうかを判断することです。 

出力は単にコレクションが適合するかどうかです。 総重量が許容容量以下の場合、答えは次のようになります。`YES`; それ以外の場合はそうです`NO`。 

すべての文字列の合計の長さは最大 10 6 です。これは、ソリューションがすべての文字を一定の回数だけ処理する必要があることを意味します。 二次解法では、重みの再計算を繰り返したり、多くの組み合わせをチェックしたりすると、最大のケースでは 10 12 回の演算に近づく可能性があるため、遅すぎます。 10 6 文字の操作は指定された制限時間内で簡単に処理できるため、リニア スキャンで十分です。 

いくつかのケースでは、不注意な実装が壊れる可能性があります。 容量が総重量と正確に等しい場合でも、答えは次のようになります。`YES`。 例えば：```
1
3 ABC
```重みは 1+2+3=6 であるため、この例は実際には容量を超えており、出力は次のようになります。```
NO
```正しい境界の例は次のとおりです。```
1
6 ABC
```出力は次のとおりです。```
YES
```次のような厳密な比較を使用する実装`total < w`誤って拒否してしまうでしょう。 

もう 1 つのよくある間違いは、文字をインデックスが 0 の値として扱うことです。 例えば：```
1
1 A
```植物`A`重みは 1 なので、出力は次のようになります。```
YES
```もし`A`を使用して誤って変換されます`ord('A') = 65`間違ったオフセットを減算すると、結果が不正確になります。 

容量がゼロになることもあるため、正の重みのプラントは常に失敗する必要があります。```
1
0 A
```正しい出力は次のとおりです。```
NO
```## アプローチ

 直接的な解決策は、総重量の計算をシミュレートすることです。 文字列内のすべての文字をアルファベットの位置に変換し、その値を累計に加算します。 文字列全体を処理した後、合計を指定された容量と比較します。 すべての植物を少なくとも 1 回は検査する必要があるため、このアプローチはすでに最適です。 

より遅い総当り攻撃の考え方では、可能性のある合計を構築または検証しながら、コレクションを繰り返しスキャンすることになります。 たとえば、サブセットをチェックするには、最大 2 n 個の可能性を考慮する必要がありますが、文字列の長さが 10 6 に達する場合は不可能です。合計を繰り返し再計算するそれほど極端ではないアプローチでも、大きな入力に対して約 10 12 回の加算を実行できます。 

重要な観察は、植物間に相互作用がないことです。 合計の重みは独立した寄与の合計にすぎないため、問題全体は 1 回のパス中に値を蓄積することに帰着します。 並べ替え、動的プログラミング、検索は必要ありません。 

この総当り攻撃は、最終的に合計を計算するすべての可能な方法を調べるため機能しますが、可能性の数が急速に増加するため失敗します。 各プラントが固定の独立した値に寄与しているという観察により、プロセス全体を 1 つの線形累積に置き換えることができます。

 | ブルートフォース | 実装に応じて O(2 n ) またはそれ以上の状態になります。 O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 最大許容重量と植物ストリングを読み取ります。 すべての文字が 1 つの重みに直接マッピングされるため、文字列には合計を計算するために必要な情報が正確に含まれています。 
2. 文字列を 1 文字ずつ調べます。 次を使用して、各大文字をその重みに変換します。`ord(character) - ord('A') + 1`、それを累計に追加します。 の`+1`この問題ではアルファベットの位置が 0 ではなく 1 から始まるため、これが必要です。 
3. すべての文字が処理された後、累積重量と許容容量を比較します。 合計が制限を超えない場合は、印刷します。`YES`; それ以外の場合は印刷します`NO`。 

なぜ効果があるのか:

 スキャン中の不変条件は、文字列の接頭辞を処理した後、累計がその接頭辞内のすべての植物の正確な重みに等しいということです。 各ステップで次のプラントの正しい寄与が追加されるため、文字列全体が処理されるまで不変式は true のままになります。 スキャンの終了時に保存される合計は、すべての植物を組み合わせた正確な重量になります。 容量と比較することで正しい判断ができます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    ans = []

    for _ in range(t):
        w, s = input().split()
        w = int(w)

        total = 0
        for c in s:
            total += ord(c) - ord('A') + 1

        if total <= w:
            ans.append("YES")
        else:
            ans.append("NO")

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    solve()
```プログラムは、次を使用してすべてのテスト ケースを読み取ります。`sys.stdin.readline`、合計入力サイズが 100 万文字に達する可能性があるため、これが必要になります。 

変換式`ord(c) - ord('A') + 1`変換する`A`1と`Z`累積された値は Python の整数型で保存されるため、大きな文字が多数表示される場合でもオーバーフローの懸念が回避されます。 

比較には、`<=`重みが利用可能な容量と正確に一致するコレクションが許可されるためです。 文字列は単一の累計のみで処理されるため、文字列のサイズに比例する追加のメモリは必要ありません。

## テストケース```python

import io

def run(inp: str) -> str:
    old_stdin = sys.stdin
    sys.stdin = io.StringIO(inp)

    def solve():
        input = sys.stdin.readline
        t = int(input())
        out = []
        for _ in range(t):
            w, s = input().split()
            total = sum(ord(c) - ord('A') + 1 for c in s)
            out.append("YES" if total <= int(w) else "NO")
        return "\n".join(out)

    result = solve()
    sys.stdin = old_stdin

 ## 特殊なケース

 アルゴリズムは容量と正確に一致する合計を受け入れるため、等価境界は正しく処理されます。 のために：```
1
6 ABC
```スキャンでは 1+2+3=6 が計算されます。 比較`6 <= 6`成功すると、以下が生成されます。```
YES
```この場合、厳密な小なり比較は失敗します。 

可能な限り最小の植物コレクションは 1 つの文字です。 のために：```
1
1 A
```変換により得られるもの`1`、合計は正確に一致するため、出力は次のようになります。```
YES
```これにより、アルファベットの変換が 0 ではなく 1 から始まることが確認されます。 

ゼロ容量も有効な入力です。 のために：```
1
0 A
```合計は`1`よりも大きい`0`したがって、アルゴリズムは次を返します。```
NO
```最後に、非常に大規模なコレクションには特別な処理は必要ありません。 多数の文字列を含む文字列`Z`文字は単純に各文字に 26 を加算します。 すべての文字は独立して処理されるため、文字列の長さに関係なく同じ不変式が適用され、最終的な比較は正しいままになります。
