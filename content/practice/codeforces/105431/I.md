 ## 解決策
 ## 問題の理解

 私たちは、2 つの競合する勢力の下で、個人の現金残高を長期にわたって追跡しています。 毎日はお金の量から始まり、その人はすぐに現在持っているものの半分を使い、費やした金額を四捨五入します。 つまり、残高が$x$、支出後の次の残高は、$\lfloor x/2 \rfloor$。 したがって、収入がなければ毎日お金はゼロに向かって厳密に減少します。 

定期的な収入もあります。$d$- 3日目、その日の支出がすでに発生した後、固定金額$s$残高に追加されます。 プロセスは初期金額から始まります$m$そして、残高がゼロになるまで、つまりその人が支出ステップを実行することさえできない状態で一日が始まるまで、毎日シミュレーションします。 

タスクは、その日の開始時の残高がゼロになる最初の日を特定することです。 これが起こらなければ、このプロセスは事実上永久に持続可能であり、資金が枯渇することは決してないことを報告しなければなりません。 

入力はバイナリ表現で与えられますが、基礎となる値は非常に大きくなる可能性があり、最大で約$2^{100}$。 これにより、数値の生の大きさに対する小さなステップのシミュレーションの繰り返しに依存するソリューションは即座に排除されます。 同時に、ダイナミクスは強い意味で単調です。支出は常に残高を半分にしますが、収入は個別のチェックポイントでのみ到着します。 この構造は、状態が任意に振動することができないことを示唆しています。 それはゼロに崩壊するか、際限なく増大するかのどちらかです。 

日々の推移を単純にシミュレーションすることは概念的には安全ですが、実際の問題はその最悪のケースの長さです。 ゼロにならない程度にお金が補充され続けると、シミュレーション日数が非常に大きくなる可能性があります。 主な困難は、シミュレーションを無制限に継続するのではなく、システムが二度とゼロに到達しない領域に入ったことを認識することです。 

微妙なエッジケースは、繰り返される半減を補うのに十分な頻度で収入が得られる場合に現れます。 たとえば、次の場合$d = 1$、残高は半分になり、すぐに増額されます。$s$毎日。 たとえ残高が巨大化することがなかったとしても、残高は永久にゼロを超えて安定する可能性があります。 小さな値をチェックするだけ、または固定数のステップをシミュレートするだけの不注意な実装では、この無限領域を検出できません。 

別の特殊なケースが発生するのは、$s = 0$。 その場合、システムは純粋に減少しており、答えは単純に、繰り返される半減期がゼロに達する最初の日、つまり約$\lfloor \log_2 m \rfloor + 1$。 収入が常に重要であると仮定した最適化は、このケースを誤って複雑にしすぎたり誤って分類したりする可能性があります。 

## アプローチ

 単純に解釈すると、プロセスを毎日シミュレーションすることになります。 各反復では、現在の値を半分にして新しい残高を計算し、加算します。$s$日のインデックスが次の倍数の場合$d$。 一日の始まりに残高がゼロになった時点で終了となります。 これはプロセスのルールに正確に従っているため、これは正しいです。 

問題は、終了までの日数が入力サイズの小さな多項式によって制限されないことです。 半減すると収入がなくなるとすぐに価値が下がってしまいますが、定期的に注入すると$s$バランスを繰り返し回復し、終了が大幅に遅れる可能性があります。 システムが安定しているか成長している場合、シミュレーションは終了しません。 

重要な観察点は、システムが毎年更新される構造であることです。$d$日々。 2 つの収入イベント間のプロセスは純粋に決定的であり、厳密に縮小しています。つまり、変換が繰り返されます。$x \mapsto \lfloor x/2 \rfloor$。 各ブロックを圧縮できます$d$単一の機能に数日かかる$f(x)$、正確にシミュレーションした後のバランスを示します。$d$から始まる日々$x$。 

このブロック機能を取得すると、長期的な行動について推論できるようになります。 繰り返し申請する場合$f$最終的に値がゼロになると、答えは有限になります。 いつか$f(x) \ge x$の場合、各完全なサイクルで状態を減らすことができないため、システムは下向きに収束できなくなります。 半分にすることですでに構造が破壊されているため、サイクルを繰り返すと値が維持または増加するだけで、最終的な崩壊は防止されます。 

これにより、無限と有限の区別は、$d$-day 変換は、開始点を下回るかどうかにかかわらず安定します。

 ## アルゴリズムのチュートリアル

 1. 正確に 1 つのブロックをシミュレートする関数を定義します。$d$指定金額からの日数$x$。 それぞれについて、$d$日、支出ルールを適用する$x \leftarrow \lfloor x/2 \rfloor$、そしてその後$d$- 番目、$2d$-th などの日を追加します。$s$一日の終わりに。 この関数は、1 収益期間にわたるシステムの完全な進化を表します。 
2.初期金額からスタート$m$1 日目から今日のインデックスを追跡します。 
3. 一日の始まりに残高がゼロになるか、フル期間にわたって減少しない動作が検出されるまで、毎日繰り返しシミュレーションします。$d$-日周期。 
4. 各完全なサイクルの後、新しい値を計算します。$x' = f(x)$。 もし$x' = 0$、システムは最終的に残高ゼロで 1 日を開始し、その日のインデックスが答えになります。 
5. もし$x' \ge x$、さらなる進化はシステムをゼロに追い込むことはできないと結論付けています。 この時点から、各サイクルで残高が維持または増加しますが、支出は毎日半分になるだけなので、システムは永続的にプラスのままです。 この場合は「お金無限大！」と出力します。 
6. それ以外の場合は更新します$x \leftarrow x'$そして次のサイクルに進み、日カウンターを次のように進めます。$d$。 

### なぜ効果があるのか

 各ブロック内では、$d$数日間、変換は決定的であり、現在の残高のみに依存します。 支出は厳密に縮小的であり、収入が唯一の成長源です。 これは、サイクル境界で観察される一連の値が単調であることを意味します。非線形効果は半減を繰り返すことだけであるため、一度減少が停止すると、後で減少傾向を回復することはできません。 したがって、システムは最終的にゼロに達するか、サイクル間の値が縮小しない領域に入ります。これは永続的な生存を意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def simulate_cycle(x, s, d):
    for i in range(1, d + 1):
        x //= 2
        if i % d == 0:
            x += s
    return x

def solve():
    s = int(input().strip(), 2)
    d = int(input().strip(), 2)
    m = int(input().strip(), 2)

    day = 1
    x = m

    while True:
        # start of a day: if already zero, we are done
        if x == 0:
            print(bin(day)[2:])
            return

        # simulate one full cycle of d days
        nxt = x
        for i in range(1, d + 1):
            nxt //= 2
            if i % d == 0:
                nxt += s

        # check infinite regime
        if nxt >= x:
            print("Infinite money!")
            return

        x = nxt
        day += d

solve()
```この実装は、サイクル圧縮のアイデアを直接反映しています。 曜日カウンターはブロック単位で進みます。$d$、それらのポイントのみが非ローカルな方法でバランスを変更できるためです。 比較`nxt >= x`は、繰り返される半減に対抗するのに十分な収入がいつあるのかを検出する重要なガードです。 

よくある落とし穴は、間違ったタイミングで収入を適用することです。 このステートメントでは、すべての給与の最後に給与が配置されます。$d$- 日、支出後、ループは最初に半分を適用し、その後に追加します。$s$適切な場合。 この順序を逆にするとダイナミクスが完全に変化し、不正確な安定性検出が行われます。 

もう 1 つの微妙な点は、日インデックスのバイナリ出力です。 変換では、`0b`出力形式は純粋なバイナリ文字列を想定しているため、接頭辞が付けられます。

このトレースは、減少しないサイクル境界を検出するだけで無限の動作を分類するのに十分であることを確認します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(d log m) | 各サイクルは d 個の半減操作を実行し、終了または検出前のサイクル数は対数減衰または早期安定化によって制限されます。 
| スペース | お(1) | 少数の整変数のみが維持されます。 

制約により非常に大きな数値が許可されますが、半減操作により数値はすぐに小さくなります。 サイクル圧縮と組み合わせると、完全なシミュレーションの数が十分に少なくなり、制限時間内に簡単に収まるようになります。

 ## 特殊なケース

 初期値がすでにゼロの場合、正しい答えは 1 日です。アルゴリズムは、変換を適用する前に各反復の開始時に残高をチェックすることでこれを処理するため、シミュレーションに入らずにすぐに現在の日のカウンターを返します。 

収入がまったくない場合、システムは純粋に減少します。 半減を繰り返すと成長できないため、各サイクルで値が厳密に減少します。 各サイクルで厳密に小さい値が生成され、対数ステップの後に最終的にゼロに達するため、アルゴリズムはこれを検出します。 

収入が支出に比べて非常に大きい場合、サイクル関数は繰り返しを通じて増加する値を生成します。 その場合の比較は、`nxt >= x`を早期にトリガーし、不必要なシミュレーションを防ぎます。 これにより、プロセスが最終ゼロ状態に到達しない場合の無限ループが回避されます。
