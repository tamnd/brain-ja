 ## 解決策
 ## 問題の理解

 私たちは、毎日永遠に繰り返される決まったパターンの仕事を与えられています。 毎日には次のタイムラインがあります`k`何時間も、そして毎日の始まりにぴったり`n`タスクが表示されます。 タスク`i`一日の予定が既知の時間に表示されます`a_i`その日以内に必要な`b_i`数時間の中断のない処理時間。 到着時間`a_i`厳密に増加しているため、1 日内のタスクは固定された時系列順で発生します。 

タスクを処理する単一のワーカーがあります。 ワーカーは、一度開始されたタスクをプリエンプトすることはなく、空いているときはいつでも、常に最も早く到着した未完了のタスクを選択します。 タスクは毎日繰り返されるため、非常に規則的な構造を持つ無限のタスクの流れになります。 

各クエリは、タスクの特定の発生を参照します。`y`その日の - 番目のタスク`x`。 目標は、その特定のタスクが終了する正確な時刻を、その日の日付と時間で表して計算することです。 

重要な問題は、毎日`n`タスクを実行すると、システムは永久に実行され、異なる日のタスクがキューを通じて対話します。 その日のタスク`x`前の日では処理順序が後ろに遅れる可能性があるため、前の日とは独立していません。 

この制約により、私たちは一日中シミュレーションから遠ざかることになります。 まで`10^5`1 日あたりのタスク`5×10^5`クエリが何日も続くと、単純な 1 日あたりのシミュレーションでは約`5×10^10`操作。 キューの持ち越しによって日をまたぐ依存関係が生じるため、1 日を繰り返しシミュレートするだけでは十分ではありません。 

微妙なエッジケースは、システムの過負荷によって発生します。 1 日の合計作業量が利用可能な作業量を超えた場合`k`数時間経ってもキューが完全に解消されることはなく、遅延は数日にわたって蓄積されます。 ワークロードが十分に小さい場合は、毎日が独立してクリアされ、繰り越しは存在しません。 これら 2 つの体制は根本的に動作が異なるため、分離する必要があります。 

よくある間違いは、タスクが毎日リセットされると仮定して、毎日を個別にシミュレーションすることです。 日中のタスクが実行されるとすぐに失敗します`x`その日のやり残した仕事に依存する`x-1`。 もう 1 つの失敗モードは、日中の到着時間を無視し、タスクが同時に到着したかのように扱うことです。これは、一日の早い時間にアイドル状態のギャップが存在する場合に正確性を損ないます。 

## アプローチ

 直接シミュレーションでは、保留中のタスクのキューを一日中維持し、毎日新しいタスクをプッシュして 1 つずつ処理します。 これはシステムを正しくモデル化しますが、処理される作業の合計に応じて操作数が増加し、`O(nq)`最悪の場合は数日かかり、実現可能性をはるかに超えています。 

重要な観察は、1 日の合計ワークロードが利用可能な処理時間以下かどうかに応じて、システムが 2 つのモードのいずれかで動作するということです。`k`。 

すべてを合計すると`b_i`せいぜい`k`、その場合、毎日の負荷が低くなります。 ワーカーはその日が終わる前にすべてのタスクを完了し、キューは毎日空になります。 この場合、日は同じスケジュールの独立したコピーであるため、1 日内のタスクの完了時間を計算するだけで済みます。 

合計額を超える場合`k`、その後、毎日、完了できる以上の作業が発生します。 短い一時的な期間の後、ワーカーは永続的に忙しい状態になります。 それが実現すると、キューが空になることがないため、1 日内の正確な到着時刻が実際の注文に影響を与えることはなくなります。 システムは、総作業量のみが重要となる連続フローに変質します。 

これにより、無限プロセスを 1 日のシミュレーション (軽負荷) または定常状態のプレフィックス蓄積 (重負荷) に減らすことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | 数日間にわたる完全なシミュレーション | O(総作業量) | O(n) | 遅すぎる |
 | 1 日のシミュレーション + 定常状態の処理 | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1 日の合計ワークロードに基づいて、ソリューションを 2 つのケースに分割しました。 

### ケース 1: 1 日あたりの総作業量 ≤ k

 1. 時刻 0 から始まる 1 日のスケジュールを計算します。 

タスクを昇順にシミュレートします。`a_i`、現在の時間ポインタを維持します。 各タスクは次から始まります`max(current_time, a_i)`追加して終了します`b_i`。 これは、到着制約と FIFO 順序の両方を考慮します。 
2. その日のすべてのタスクの完了時間を記録します。 

総仕事量が収まるので、`k`、翌日に持ち越されるタスクはないため、これらの完了時間は最終的なものです。 
3. お問い合わせの場合`(x, y)`、1 日の結果を丸一日シフトします。 

答えは単純です`(x-1)*k + completion_time_within_day[y]`。 

これが機能するのは、システムが毎日リセットされ、タスクが残らないためです。 

### ケース 2: 1 日あたりの総作業量 > k

 1. システムが最終的に永続的にビジー状態になることを観察します。 

十分な日数が経過すると、毎日の始まりには常に保留中の作業があるため、ワーカーがアイドル状態になることはありません。 
2. 定常状態では、1 日内の到着時間が実行順序に影響しなくなりました。 

実行の順序を変更する可能性のあるギャップが発生しないため、タスクは厳密な日順で、毎日インデックス順で効果的に処理されます。 
3. 各タスクをその処理コストのみで置き換えます。 

システムは、毎日繰り返されるワークロードの単一の無限シーケンスになります。 
4. 1 日のプレフィックス合計を事前計算します。 

しましょう`pref[i] = b_1 + ... + b_i`、 そして`S = pref[n]`。 
5. グローバル完了時間を連続時間で計算します。 

タスクの完了時間`(x, y)`は次のようになります:`time = (x-1)*S + pref[y]`。 
6. 連続時間を次のように変換します。`(day, hour)`で割ることで`k`。 

これが機能するのは、システムが飽和状態になるとワーカーは決して待機しないためです。そのため、スケジュールはアイドル ギャップのない連続ストリームを処理するのと同等になります。 

### なぜ効果があるのか

 どちらの場合も、重要な不変条件は、ワーカーが常に FIFO の到着順にタスクを処理し、システムが飽和状態になると、順序を歪める可能性のあるアイドル間隔が存在しないことです。 キューは毎日リセットされるか、ある時点以降空にならないかのどちらかです。 これらは、毎日の一定の入力パターンの下で可能な安定した動作の 2 つだけであるため、プロセスを独立した日のシミュレーションまたは純粋なプレフィックス蓄積のいずれかに縮小することで、すべてのダイナミクスを正確に捉えることができます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k, q = map(int, input().split())
    a = []
    b = []
    
    for _ in range(n):
        ai, bi = map(int, input().split())
        a.append(ai)
        b.append(bi)

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + b[i]
    S = pref[n]

    # Case 1: light load, each day clears
    if S <= k:
        finish = [0] * n
        cur = 0
        for i in range(n):
            if cur < a[i]:
                cur = a[i]
            cur += b[i]
            finish[i] = cur

        out = []
        for _ in range(q):
            x, y = map(int, input().split())
            y -= 1
            day_start = (x - 1) * k
            t = day_start + finish[y]
            d = t // k + 1
            h = t % k + 1
            out.append(f"{d} {h}")

        print("\n".join(out))
        return

    # Case 2: heavy load, steady state prefix model
    out = []
    for _ in range(q):
        x, y = map(int, input().split())
        y -= 1
        t = (x - 1) * S + pref[y]
        d = t // k + 1
        h = t % k + 1
        out.append(f"{d} {h}")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装では、まず処理時間のプレフィックス合計が事前計算されます。これは、それらが過負荷状態で重要な唯一の量であるためです。 決定点は 1 日の総作業量です`S`。 

軽負荷ブランチでは、単一のタイム ポインターを使用して 1 日を明示的にシミュレートします。 重要な詳細は、`max(cur, a[i])`これにより、タスクのリリース時間と 1 日のアイドル期間が確実に尊重されます。 

高負荷ブランチでは、シミュレーションを完全に回避します。 各クエリは、プレフィックス合計に対する線形公式を使用して一定時間内に回答されます。 絶対時間からへの変換`(day, hour)`による整数除算を使用します`k`、1 ベースのインデックス調整付き。

次に、重い負荷の例を考えてみましょう。`k = 10`、タスク:

 ## 特殊なケース

 エッジ ケースの 1 つは、1 日の合計ワークロードが次とまったく同じである場合です。`k`。 この状況では、作業者は毎日の終わりにちょうど終了しますが、何も前に持ち越すことはありません。 たとえば、タスクが完全に埋まった場合、`k`時間後も、軽負荷ブランチは引き続き適用されます。 シミュレーションは時間通りに終了します`k`、したがって、次のようにシフトします`(x-1)*k`毎日、重複することなく連続して配置されます。 

もう 1 つのケースは、最初のタスクがその日の遅い時間に到着する場合です。 軽負荷システムであっても、ワーカーは次の時間までアイドル状態になります。`a_1`。 シミュレーションはこれを次のように処理します。`max(cur, a[i])`ステップ。 これがないと、初期のアイドル時間が無視され、すべての完了時間が誤って早くシフトされてしまいます。 

3 番目のケースは、負荷の高いシステムで、初期の段階では部分的にアイドル状態が続いているように見えます。 システムは最終的には飽和しますが、定常状態の公式は移行後にのみ適用されます。 1 日の合計作業負荷に基づいて決定することで、レジームの混合を回避し、すぐに飽和状態になると誤って想定することがなくなります。
