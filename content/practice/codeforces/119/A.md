 ## 解決策
 ## 問題の理解

 それぞれ固定整数を持つ 2 人のプレイヤー、サイモンとアンティシモンの間でターンベースのゲームをシミュレートするように求められています。`a`そして`b`それぞれ。 山盛りです`n`石。 プレイヤーはサイモンから順番に交互にターンを開始し、ターンでは、プレイヤーは固定数とヒープに残っている現在の石の数の最大公約数 (gcd) に等しい数の石を取らなければなりません。 ヒープにある石の数がプレイヤーが取る必要がある石よりも少ない場合、そのプレイヤーは負けます。 タスクは、誰が勝者かを決定することです。`0`サイモンと`1`アンティシモンのために。 

制約は小さく、すべての数値は最大 100 です。これは、ヒープには 100 個を超える石を含めることができないため、各手の直接シミュレーションさえも実行可能であることを意味します。 最悪の場合の総手数は約 100 にすぎないため、複雑な数学やメモ化を使用して最適化する必要はありません。 

エッジケースには、ヒープに最初にプレイヤーの番号の gcd よりも少ないストーンが含まれている状況が含まれます。`n`。 たとえば、次の場合`a = 7`、`b = 3`、 そして`n = 1`, サイモンは次の理由で先手を取ることができません。`gcd(7, 1) = 1`はヒープサイズに等しいため、ちょうど 1 つの石を取ることができ、アンティシモンは次のターンに負けます。 ヒープがゼロになったときに gcd を正しく処理することも重要です。`gcd(x, 0)`返すべきです`x`、すぐにヒープを超えてゲームが終了する可能性があります。 

## アプローチ

 ブルートフォースアプローチは、ゲームをターンごとにシミュレートすることです。 ターンごとに計算します`gcd(player_number, current_heap)`、山が十分であるかどうかを確認し、可能であれば石を減算し、ターンを切り替えます。 この方法はゲームのルールに忠実に従っているので正しいです。 その時間計算量は移動回数に比例し、最大でも`n`。 と`n <= 100`、これは許容範囲です。 

キャッシュする繰り返し状態や複雑な副問題がないため、ここでは最適化は必要ありません。 問題の構造は本質的に逐次的です。各手は残っている石の正確な数に依存するため、事前計算や貪欲なショートカットは必要ありません。 重要な洞察は、コンピューティングが`gcd`また、境界が狭いため、ターンごとにヒープを更新するのは簡単であるため、単純なシミュレーションはシンプルかつ効率的です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n * log(max(a,b))) | お(1) | 承認済み |
 | 最適 (総当たりと同じ) | O(n * log(max(a,b))) | お(1) | 承認済み |

 ここ、`log(max(a,b))`gcd のユークリッド アルゴリズムから来ています。 

## アルゴリズムのチュートリアル

 1. 整数を読み取る`a`、`b`、 そして`n`。 それらを Simon、Antisimon、および初期ヒープに割り当てます。 
2. フラグまたは変数を設定する`turn`誰の番かを示すために。 簡単にするために、`turn = 0`サイモンと`turn = 1`アンティシモンのために。 
3. ヒープに少なくとも 1 つの石がある間ループします。 

1. 現在のプレイヤーが取るべき石の数を計算します。`take = gcd(player_number, heap)`。 
2. もし`take > heap`、現在のプレイヤーが負けます。 印刷する`turn`そして出ます。 
3. それ以外の場合は減算します`take`から`heap`。 
4.設定によりスイッチが回転する`turn = 1 - turn`。 
4. ループは、プレイヤーがターン中に負けた場合にのみ自然に終了するため、常に正しい勝者で終了します。 

機能する理由: 不変条件は、減算のたびにヒープが残りの石を表し、次のプレイヤーの手がルールに従って正確に計算されることです。 ターンは厳密に交互に行われ、減算前に石が不足していないかチェックするため、シミュレーションは常に実際のゲームプレイを反映しています。 ターンごとにヒープが減少し、最終的に次の状態に達するため、ゲームは常に終了します。`take > heap`。 

## Python ソリューション```python
import sys
import math
input = sys.stdin.readline

a, b, n = map(int, input().split())
turn = 0  # 0 for Simon, 1 for Antisimon

while True:
    if turn == 0:
        take = math.gcd(a, n)
    else:
        take = math.gcd(b, n)
    
    if take > n:
        print(turn)
        break
    
    n -= take
    turn = 1 - turn
```ソリューションはまず入力を読み取り、`turn`変数。 ユークリッド アルゴリズムを使用します。`math.gcd`必要な石を計算します。 小切手`take > n`損失状態を即座に検出します。 移動するたびにヒープをデクリメントし、ターンを切り替えます。 使用する`1 - turn`0 と 1 を交互に切り替える簡単な方法です。

## テストケース```python
import sys, io
import math

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    a, b, n = map(int, input().split())
    turn = 0
    while True:
        take = math.gcd(a if turn == 0 else b, n)
        if take > n:
            return str(turn)
        n -= take
        turn = 1 - turn

# Provided samples
assert run("3 5 9\n") == "0", "sample 1"
assert run("2 1 1\n") == "0", "sample 2"

# Custom cases
assert run("1 1 1\n") == "0", "both take 1, Simon wins first"
assert run("100 100 100\n") == "0", "large numbers equal, Simon wins eventually"
assert run("2 2 3\n") == "1", "odd heap, Antisimon wins"
assert run("7 3 1\n") == "0", "Simon takes the only stone"
assert run("5 2 10\n") == "1", "multiple gcd reductions, Antisimon wins"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 1 1 | 0 | 最小ヒープ、最小数 |
 | 100 100 100 | 0 | a、b、n の最大値 |
 | 2 2 3 | 1 | 奇数ヒープがアンチシモンの勝利につながる |
 | 7 3 1 | 0 | Antisimon の gcd より小さいヒープ |
 | 5 2 10 | 1 | 異なる gcd 削減による複数の移動 |

 ## 特殊なケース

 いつ`n = 1`両方のプレイヤーが 1 より大きい数値を持っている場合、アルゴリズムは正しく計算します。`gcd(player_number, n)`そして、可能であればサイモンが単一の石を取ることを許可します。 のために`a = 7, b = 3, n = 1`、最初の gcd は`gcd(7,1)=1`したがって、Simon が石を受け取り、ヒープが 0 になり、Antisimon が移動できなくなり、出力が確認されます。`0`。 これは次のことを示しています`gcd(x,0)`交互の処理とターンは、ヒープが固定数よりも小さいエッジ条件を正確に捕捉します。
