 ## 解決策
 ## 問題の理解

 このシステムは、時間の経過とともにイベントを処理する非常に小さな「SMS センター」をシミュレートしています。 各イベントは、特定の秒にメッセージのバッチをキューに挿入するか、そのキューの先頭から 1 つのメッセージの処理をトリガーします。 時間は秒単位で進み、毎秒ちょうど 1 単位の処理能力が利用可能になります。 

各タスクは指定されたタイムスタンプに到着し、いくつかのメッセージを FIFO キューに送ります。 各整数タイム ステップで、システムはまず現在のキューから 1 つのメッセージを送信できるかどうかを決定します。 その決定の後のみ、新しいタスクが同時に到着すると、そのメッセージがキューに追加されます。 

目的は、このシステムをシミュレートし、最後のメッセージが最終的に送信される瞬間と、プロセス中にキューが到達する最大サイズの 2 つのことを決定することです。 

この制約は、タスクの数が最大約 1,000 である一方、メッセージの数はタスクごとに最大 100 万と大きくなる可能性があることを意味します。 これにより、バッチ処理やアイドル時間を効率的にスキップすることに注意しない場合、各メッセージを個別のユニットに拡張したり、素朴な方法で 1 つずつシミュレートしたりすることが直ちに排除されます。 ただし、時間はタスク境界またはキューの継続的な排出中にのみ進むため、直接のイベント駆動型シミュレーションは引き続き実行可能です。 

微妙なエッジケースは、同じタイムスタンプでの操作の順序から発生します。 メッセージの送信と同時にタスクが到着した場合、送信が先に行われ、その後新しいメッセージがキューに入れられます。 この順序を混在させると、キュー サイズが不正確になります。 

別の特殊なケースは、タスク間でキューが空になる場合に発生します。 時間を段階的に増加させる単純なシミュレーションは、到着間に大きなギャップがある場合、不必要に遅くなる可能性があります。 たとえば、時間 1 でキューが空で、次のタスクが時間 10^6 に到着する場合、システムは中間秒ご​​とに反復せずに単純に前にジャンプする必要があります。 

最後に、最後のタスクが到着した後も、すべてのメッセージが処理される可能性があります。 正しい実装では、新しいタスクがスケジュールされていない場合でも、キューを排出し続ける必要があります。 

## アプローチ

 ブルート フォース シミュレーションでは、時間を一連の整数ステップとして扱います。 毎秒、タスクが到着するかどうかを確認し、メッセージを追加し、キューから最大 1 つのメッセージを送信します。 このアプローチは概念的には単純で正しいですが、タスクがない状態が長時間続くと、著しく性能が低下する可能性があります。 最悪の場合、時間は約 10^6 以上に及ぶ可能性があり、1 秒ごとにステップ実行すると、わずか数回の操作しか発生しない場合でも、約 10^6 回の反復が行われることになります。 

重要な観察は、キューが空のアイドル期間には興味深いことは何も起こらないということです。 キューが空でない場合、システムは決定論的に動作します。つまり、キューが空になるか次のタスクが到着するまで、1 秒あたり 1 つのメッセージを継続的に処理できます。 これにより、秒ごとにシミュレーションするのではなく、次のイベントまでに排出できるメッセージの数を計算することで、時間間隔を「ジャンプ」することができます。 

これにより、問題はタスク上のポインタを維持し、イベント境界のみをシミュレートすることに軽減されます。 現在のキューのサイズと次回の到着時間がわかったら、次の処理を行うことができます。`min(queue_size, time_gap)`メッセージを一括して送信し、それに応じて時間を進めます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | ステップバイステップのシミュレーション | O(最大時間) | お(1) | 遅すぎる |
 | イベント駆動型バッチ シミュレーション | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在の時刻とキューで待機しているメッセージの数を維持しながら、タスクを時系列に処理します。 

1. 最初のタスクのタイムスタンプと同じ現在時刻から開始します。 キュー サイズをゼロに初期化し、最後の送信時刻と最大キュー サイズの応答を追跡します。 

2. タスクごとに、現在時刻とタスクの到着時刻の間の時間差を計算します。 このギャップの間、システムはキューにすでにあるメッセージのみを処理できます。 ギャップのサイズまで、できるだけ多くのメッセージをキューに入れて削減します。 ギャップが終了する前にキューがゼロになった場合は、キューが空になる瞬間まで現在の時間を進めます。 それ以外の場合は、タスクの到着時刻に移動します。 最終送信時刻は、この排出フェーズ中にメッセージが正常に処理されるたびに更新されます。 

3. タスクが到着すると、最初に 1 単位の時間を処理します。キューが空でない場合は、1 つのメッセージを送信し、それをデクリメントします。 これは、同じタイムスタンプでキューに入れる前に送信が行われるというルールに対応します。 メッセージが送信された場合は、最終送信時刻を更新します。 

4. 送信ステップの後、タスクのメッセージをキューに追加し、最大キュー サイズを更新します。 

5. すべてのタスクが処理されるまで続行します。 

6. 最後のタスクの後、メッセージが残っている場合は、キューが空になるまで 1 秒ごとに 1 つ送信してメッセージを完全に排出し、それに応じて最終送信時刻を更新します。 

正しさは、連続する 2 つのタスク到着の間に、システムが 1 秒あたり 1 つの割合でメッセージを送信して完全にビジー状態であるか、空のキューでアイドル状態であるかのいずれかであるという不変条件に依存します。 中間の動作はありません。キュー サイズは時間の経過とともに直線的かつ決定論的に変化するため、一定の時間間隔内ですべての送信をバッチ処理すると、正確な動作が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
tasks = [tuple(map(int, input().split())) for _ in range(n)]

t0, v0 = tasks[0]
cur_time = t0
q = 0
last_send = -1
max_q = 0

i = 0

for t, add in tasks:
    # drain until time t
    if cur_time < t:
        gap = t - cur_time

        # use up queue during gap
        used = min(q, gap)
        q -= used
        if used > 0:
            last_send = cur_time + used - 1

        cur_time += gap

    # at exact time t: send first if possible
    if q > 0:
        q -= 1
        last_send = cur_time

    # enqueue new messages
    q += add
    max_q = max(max_q, q)

    cur_time = t + 1

# final drain
if q > 0:
    last_send = cur_time + q - 1
    q = 0

print(last_send, max_q)
```この実装では、実行時間ポインターが保持され、明示的に毎秒反復処理されることが回避されます。 排出ステップでは、長いアイドル間隔が 1 つの算術更新に圧縮されます。 各タスク内の順序は重要です。送信操作は新しいメッセージを挿入する前に適用され、同じタイムスタンプで問題の優先順位の定義と一致します。 

よくある間違いは、送信前にキューを更新することです。`t`これにより、同一のタイムスタンプで意図した FIFO の動作が反転し、キュー サイズと最終送信時間の両方でオフバイワン エラーが発生します。 

もう 1 つの微妙な点は更新です`last_send`バッチ処理中。 ギャップ内に複数のメッセージが送信されると、最後のメッセージは次の時点で発生します。`cur_time + used - 1`、ギャップの終わりではありません。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import math
    from collections import deque

    # inline solution
    n = int(input())
    tasks = [tuple(map(int, input().split())) for _ in range(n)]

    cur_time = tasks[0][0]
    q = 0
    last_send = 0
    max_q = 0

    for t, add in tasks:
        if cur_time < t:
            gap = t - cur_time
            used = min(q, gap)
            q -= used
            if used:
                last_send = cur_time + used - 1
            cur_time += gap

        if q > 0:
            q -= 1
            last_send = cur_time

        q += add
        max_q = max(max_q, q)
        cur_time = t + 1

    if q > 0:
        last_send = cur_time + q - 1

    return str(last_send) + " " + str(max_q)

 ## 特殊なケース

 タスクが 1 つだけの場合でも、アルゴリズムはエンキュー前送信ルールと最終排出フェーズの両方を正しく処理する必要があります。 タスクが追加するメッセージがゼロの場合、キューは大きくならず、送信も行われないため、最終送信時刻は初期化に応じて未設定またはゼロのままにする必要があります。 

タスクと空ではないキューの間に長いギャップがある場合、バッチの排出ステップが不可欠になります。 システムは次の到着前にすべてのメッセージを終了する可能性があり、現在時刻はキューが空になる瞬間までのみ進む必要があり、必ずしも次のタスク時刻まで進む必要はありません。 

大量のメッセージ バーストを伴うタスクが連続して到着すると、キューが大幅に増大する可能性があります。 ピークは挿入直後に発生するため、アルゴリズムは、処理後ではなく、エンキューごとに最大キュー サイズを更新する必要があります。
