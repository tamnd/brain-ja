 ## 問題の理解

 川には陣地の長い列があり、各陣地には 1 種類の錬金術材料が含まれています。 ErvinX​​ie は、どこから開始するかを選択し、通過したすべての資料を収集しながら先に進みます。 収集したマテリアルは、収集したときと同じ順序で配置する必要はありません。 唯一の要件は、最終的なコレクションには、魔法陣に必要なすべてのマテリアル タイプの十分なコピーが含まれている必要があることです。 

フォーメーションは配列で記述されます`a`。 で複数回登場するマテリアル`a`また、複数回収集する必要があります。 川は別の配列で記述されます`b`, ここで、各要素はその位置で見つかったマテリアルです。 タスクは、地層から必要なすべてのカウントをカバーする材料カウントを持つ、川の最も短い連続部分を見つけることです。 答えはその部分の長さです。 そのような部分が存在しない場合、答えは次のようになります。`DragonXie`。 

入力サイズにより、ほぼ線形の解決策が求められます。 地層の長さは 100 万に達し、川の長さは 200 万に達することがあります。 すべての開始位置をチェックしてセグメントを拡張するソリューションには、次のようなものが必要になります。`s * len`最悪の場合、約 2 兆個のチェックがあり、完了できない場合もあります。 範囲内の材料を繰り返しカウントするアプローチですら遅すぎます。 各川の位置を一定の回数だけ処理する必要があります。 

材質の種類はたったの2種類だけです`5000`これは、低速な構造を使用する代わりに、周波数情報を配列に保存できることを意味します。 アルファベットのサイズが小さいことは役に立ちますが、シーケンスの長さが非常に大きいため、依然として`O(len)`アルゴリズム。 

いくつかの特殊なケースでは、より単純な実装が壊れる可能性があります。 繰り返し素材が必要な編成の場合、全種類出現するかどうかだけを確認するのは間違いです。 例えば：```

4

```正しい出力は次のとおりです`3`なぜならセグメントは`[1, 2, 1]`資料のコピーが 2 枚含まれています`1`および資料のコピー 1 部`2`。 型が出現したかどうかだけを記録する不用意な解決策では、より短い無効なセグメントが受け入れられてしまいます。 

もう 1 つのケースは、川全体では不十分な場合です。```

```正しい出力は次のとおりです`DragonXie`。 すべての要件を確認せずに、必要な材料を 1 つ見つけただけで解決策が停止すると、間違った答えが得られます。

```答えは`4`。 縮小が発生したときにのみ回答を更新する実装では、このケースを見逃す可能性があります。 

## アプローチ

 直接的なアプローチは、川で可能なすべての開始位置を試すことです。 開始するたびに、セグメントを右に拡張し、収集された材料を数え、必要な数量がすべて満たされたときに停止します。 これは正しいです。考えられるすべてのセグメントの開始点が考慮され、各開始点の最初の有効な終点が、そこから始まる最短のセグメントを与えるからです。 

問題は、多くのセグメントがほぼ同じ情報を共有していることです。 最悪の場合、形成には巨大な川の始まり近くに決して出現しない 1 つのマテリアルが必要になる可能性があります。 ブルート フォース スキャンでは、考えられる左右の境界のほぼすべてのペアを検査できます。 と`len = 2 * 10^6`に近づく可能性がある操作の数`4 * 10^12`、それは限界をはるかに超えています。 

重要な点は、必要な条件が現在のセグメント内のカウントのみに依存するということです。 セグメントにすべてのマテリアルがすでに十分に含まれている場合、その左側の境界を右に移動してもセグメントを短くすることしかできません。 セグメントに何かが欠けている場合、より多くのマテリアルを得るには、右側の境界を拡張することが唯一の方法です。 この単調な動作により、スライディング ウィンドウが可能になります。 

ウィンドウには 2 つの周波数配列が保持されます。1 つは必要な地層用で、もう 1 つは現在の河川セグメント用です。 変更のたびにすべてのマテリアル タイプを比較するのではなく、必要なマテリアル オカレンスがまだ不足している数を表す単一の値を維持します。 マテリアルを追加すると、そのオカレンスが以前に欠落していた場合にのみ、この値が減少します。 材料を除去すると、除去によってセグメントが再び不足した場合にのみ材料が増加します。 

すべてのセグメントを個別に検査するため、ブルート フォースが機能しますが、ほぼ同じカウント作業が繰り返されます。 スライディング ウィンドウは、隣接するセグメントからの情報を再利用しながら同じ正確さを維持し、問題を川を 1 回通過するだけで済みます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(len²) | O(k) | 遅すぎる |
 | 最適 | O(レン) | O(k) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. フォーメーション内に各マテリアルが何回出現するかを数えます。 させて`missing`必要な材料がまだ収集されていないため、最初は編隊の長さに等しくなります。 
2. 右ポインタを川の始まりから終わりまで移動します。 新しいマテリアルをそれぞれ現在のウィンドウのカウントに追加します。 この材料を追加する前にまだ必要だった場合は、値を減らします。`missing`。 

の値`missing`は、現在のウィンドウにまだ不足している、必要なマテリアルのコピーの正確な数を表します。 
3. いつでも`missing`ゼロになると、現在のウィンドウでフォーメーションを構築できます。 ウィンドウが有効なまま左ポインタを前方に移動し、より短い有効な長さが見つかるたびに答えを更新します。 

目標は最短の有効なセグメントであるため、不要なマテリアルの削除は常に安全です。 もう 1 つのマテリアルを削除すると有効性が失われ、現在の左側の境界はこの右側の境界に対して可能な最小になります。 
4. 川全体を処理した後、記録された最小の長さを出力します。 有効なウィンドウが見つからなかった場合は、次のように出力します。`DragonXie`。 

なぜ効果があるのか:

 スライディング ウィンドウによって維持される不変条件は次のとおりです。`missing`常に、現在のウィンドウに存在しない必要なマテリアルのコピーの数と等しくなります。 右ポインタは前方にのみ移動し、ウィンドウが有効になるたびに、左ポインタは有効性を失うことなくすべての削除可能なマテリアルを削除します。 考えられるすべての最短セグメントには、右側の境界に到達する瞬間があり、縮小プロセスによって最小の左側の境界が見つかります。 すべての最短ウィンドウ候補が検査されるため、最終的な最小値は正確です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    k_line = input().strip()
    if not k_line:
        return
    k = int(k_line)

    s = int(input())
    need = [0] * (k + 1)

    arr = list(map(int, input().split()))
    for x in arr:
        need[x] += 1

    length = int(input())
    river = list(map(int, input().split()))

    have = [0] * (k + 1)
    missing = s
    left = 0
    ans = length + 1

    for right, x in enumerate(river):
        have[x] += 1
        if have[x] <= need[x]:
            missing -= 1

        while missing == 0:
            cur = right - left + 1
            if cur < ans:
                ans = cur

            y = river[left]
            if have[y] <= need[y]:
                missing += 1
            have[y] -= 1
            left += 1

    if ans == length + 1:
        print("DragonXie")
    else:
        print(ans)

if __name__ == "__main__":
    solve()
```プログラムは最初に編成の頻度テーブルを構築します。 配列のサイズはマテリアル タイプの数のみに依存するため、シーケンスが大きくても小さいままです。 

変数`missing`に初期化されます`s`、必要な資料のコピーの合計数。 マテリアルがウィンドウに入った場合、以前にウィンドウに必要なコピー数より少ないコピーしかなかった場合にのみ役に立ちます。 追加コピーは新しいものを満たさないので変化しない`missing`。 

縮小ループは、ウィンドウが有効な場合にのみ実行されます。 一番左のマテリアルを削除する前に、コードはそのマテリアルが現在要件を満たすことに貢献しているかどうかをチェックします。 カウントがまだ必要な量の範囲内にある場合、それを削除すると欠落したコピーが作成されます。 チェックとデクリメントの順序は、削除されたコピーが有用かどうかを決定するため、重要です。 

2 つのポインターは、それぞれ最大 1 回だけ左から右に移動します。 河川のスキャンを繰り返す必要がないため、実装は必要な制限内に保たれます。
