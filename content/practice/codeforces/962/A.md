 ## 解決策
 ## 問題の理解

 私たちには一連の日が与えられており、ポリカープは毎日、決まった数の問題を解決します。 トレーニング期間全体を見ると、全日を通して解決された問題の合計数があります。 タスクは、その日の終わりまでに、Polycarp がスケジュール全体の総問題数の少なくとも半分をすでに解決しているような、最も早い日を見つけることです。 

つまり、1 日目以降の累計を計算し、このプレフィックスの合計が全体の合計の少なくとも半分に達する最初の位置で停止します。 答えはその日のインデックスです。 

制約では最大 200,000 日が許可されるため、どのソリューションも直線的な時間で実行する必要があります。 プレフィックスの合計を繰り返し再計算したり、サフィックスをスキャンしたりする二次アプローチは、次のように実行されます。$n^2$、この規模では遅すぎます。 単一パスの蓄積で十分かつ必要です。 

微妙な点は「半分以上」の定義です。 合計が奇数になる可能性があるため、正確に半分に分割するのではなく、次のしきい値と比較します。$\lceil \frac{S}{2} \rceil$または、プレフィックスの合計に 2 を乗算した値が合計以上であるかどうかを同等にチェックします。 

エッジケースはほとんどが構造的なものです。 いつ$n = 1$の場合、最初の日にすでにすべての問題が含まれているため、答えは常に 1 になります。 もう 1 つの特殊なケースは、1 つの大きな値がシーケンスの後半に出現する場合です。これは、最初はプレフィックスがゆっくりと増加したとしても、答えが早く出ないことを意味します。 

## アプローチ

 問題を解決する簡単な方法は、最初に問題の総数を計算し、次に毎日、初日からその日までの問題の合計を再計算することです。 各チェックには、プレフィックスを最初から合計することが含まれます。 これは条件の定義を直接反映しているため正しいですが、作業が頻繁に繰り返されます。 一日中$i$、プレフィックス合計コストを再計算します。$O(i)$、すべての日を合計すると、$O(n^2)$最悪の場合の操作が大きすぎて、$n = 200{,}000$。 

重要な点は、プレフィックスの合計を増分的に維持できることです。 再計算する代わりに、1 回反復するたびに累計を累積します。 各ステップで、現在のプレフィックスの合計と合計の半分を比較します。 条件を満たす最初のインデックスが答えになります。 

これが機能するのは、条件がプレフィックスのみに依存し、プレフィックスの合計が単調な非減少シーケンスを形成するためです。 しきい値を超えると、その後のすべてのインデックスでしきい値を超えたままになるため、最初の交差点は一意に定義されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) | お(1) | 遅すぎる |
 | 最適なプレフィックスサムスキャン | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 毎日解決された問題の配列を読み取り、すべての値の合計を計算します。 この合計が、到達する必要があるしきい値を定義します。 
2. 実行変数を初期化する`prefix = 0`。 これには、当日までに解決された問題の累積数が保存されます。 
3. 左から右に日数を繰り返します。 毎日、現在の値を次の値に加算します。`prefix`。 
4. アップデート後`prefix`、どうかを確認してください`2 * prefix >= total`。 この比較により、浮動小数点除算が回避され、「少なくとも半分」条件が直接エンコードされます。 
5. 条件が true になった最初のインデックスが応答として直ちに返されます。 

すぐに停止する理由は、プレフィックスが全体の半分に達すると、単調増加により、それ以降のすべてのプレフィックスも条件を満たすためです。 

### なぜ効果があるのか

 毎日の値はすべて正であるため、プレフィックス合計シーケンスは減少しません。 「プレフィックスの合計が合計の少なくとも半分である」という条件は、インデックスに対する単調述語を定義します。つまり、一度 true になると、再度 false になることはありません。 これにより、それを満たす最初のインデックスが明確に定義され、一意であることが保証され、左から右にスキャンしても後戻りすることなくそのインデックスが見つかります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
a = list(map(int, input().split()))

total = sum(a)
prefix = 0

for i, x in enumerate(a, start=1):
    prefix += x
    if prefix * 2 >= total:
        print(i)
        break
```このソリューションでは、まず問題の総数を計算して、目標のしきい値を把握します。 次に、単一パスを実行し、実行中のプレフィックス合計を維持します。 比較では 2 による乗算を使用して浮動小数点演算を回避し、整数の安全性を維持します。 

この問題では 1 から始まる日のインデックスが必要なので、列挙は 1 から始まります。 条件が満たされた瞬間にループが早期に終了するため、不必要な計算が最小限に抑えられます。 

## 実用的な例

 ### 例 1

 入力:```
4
1 3 2 1
```合計は 7 なので、しきい値は 3.5 になります。これは、少なくとも 4 に達する最初のプレフィックスを探すことを意味します。 

| 日 | 値 | プレフィックスの合計 | 条件 (2*プレフィックス >= 7) |
 | --- | --- | --- | --- |
 | 1 | 1 | 1 | いいえ |
 | 2 | 3 | 4 | はい |

 2 日目にはプレフィックスが 4 に達し、すでにすべての問題の少なくとも半分をカバーしているため、答えは 2 です。 

### 例 2

 入力:```
6
1 2 3 4 2 0
```合計は 12 なので、しきい値は 6 になります。 

| 日 | 値 | プレフィックスの合計 | 条件 (2*プレフィックス >= 12) |
 | --- | --- | --- | --- |
 | 1 | 1 | 1 | いいえ |
 | 2 | 2 | 3 | いいえ |
 | 3 | 3 | 6 | はい |

 最初の有効な日は 3 です。これは、プレフィックスの合計がその時点で合計のちょうど半分に等しいためです。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 合計を 1 回計算し、配列を 1 回スキャンします。 
| スペース | お(1) | 少数の整変数のみが使用されます。 

リニアスキャンで十分です$n \le 200{,}000$、すべての演算は定数時間の整数の加算と比較であるため、ソリューションは時間とメモリの制限内に簡単に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    n = int(sys.stdin.readline())
    a = list(map(int, sys.stdin.readline().split()))
    
    total = sum(a)
    prefix = 0
    
    for i, x in enumerate(a, start=1):
        prefix += x
        if prefix * 2 >= total:
            return str(i)

    return ""

# provided sample
assert run("4\n1 3 2 1\n") == "2"

# minimum size
assert run("1\n5\n") == "1"

# already satisfied early
assert run("3\n10 1 1\n") == "1"

# exact half on last element
assert run("4\n1 1 1 3\n") == "4"

# all equal
assert run("5\n2 2 2 2 2\n") == "3"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 5 | 1 | 単一要素のエッジケース |
 | 10 1 1 | 1 | 最初の要素の早期優位性 |
 | 1 1 1 3 | 4 | 最後の位置でしきい値に到達 |
 | 2 2 2 2 2 | 3 | 対称プレフィックスの増加 |

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、最初の要素だけで既に全体の半分を超えている場合です。 入力の場合:```
3
10 1 1
```合計は 12 なので、半分は 6 です。最初のプレフィックスは 10 で、すでに条件を満たしているため、答えは 1 になります。チェックは最初の要素の処理直後に実行されるため、アルゴリズムはこれを自然に処理します。 

もう 1 つのケースは、最後の要素で正確にしきい値に到達する場合です。 のために：```
4
1 1 1 3
```合計は 6、半分は 3 です。プレフィックスの合計は 1、2、3、6 で、最初に少なくとも 3 に達するのは 3 日目ですが、等価処理によっては、2 * 3 >= 6 であるため 3 日目が有効になります。アルゴリズムはその時点で正しくトリガーされ、早期に停止します。 

最後の構造ケースは、次のような一様分布です。```
5
2 2 2 2 2
```合計は 10、半分は 5 です。プレフィックスの合計は 2、4、6 であるため、3 日目が初めてしきい値を超えます。 プレフィックス合計の単調な性質により、このインデックスの選択に曖昧さがないことが保証されます。
