 # 問題の理解

 このシステムはユーザーのソーシャル ネットワークを維持します。 友情接続は 2 人のユーザーを同じ友達グループに参加させます。グループはグラフの接続されたコンポーネントです。 トーナメントのクエリごとに、正確な規模のチームが何チームあるかを尋ねられます。`s`形成することができる。 チームは完全に 1 つのフレンド グループから構成されている必要があり、ユーザーを共有しない限り、1 つのグループが複数のチームに貢献することができます。 したがって、答えは次の合計になります。`floor(size_of_group / s)`現在の友達グループ全体にわたって。 

入力には最大で次のものが含まれます`10^5`ユーザーと`10^5`操作。 フレンドシップ操作はエッジを追加するだけなので、接続されたコンポーネントは素の集合結合構造で維持できます。 ただし、クエリでは、任意のチーム サイズを要求できます。`1`に`n`つまり、クエリごとにすべてのコンポーネントを再計算することは不可能です。 と`10^5`操作、さらには`O(n)`クエリごとの回答は次のようになります`10^10`オペレーションのため、一般的なコンテストの制限内に収まりません。 

難しいのは、接続されたコンポーネントを維持しないことです。 難しいのは値を維持することです`sum floor(component_size / s)`あらゆる可能性のために`s`コンポーネントのサイズは変わります。 

よくある間違いは、マージ後に考えられるすべてのチーム サイズを更新することです。 たとえば、コンポーネントのサイズが大きくなった場合、`1`サイズに合わせて`50000`、すべてを直接変更します`s`まで`50000`1 回のマージでは機能しますが、数千回のマージではソリューションが遅くなりすぎます。 

もう 1 つのエッジケースはサイズの処理です`1`コンポーネント。 最初はすべてのユーザーが一人なので、チームの規模を問い合わせます`1`戻らなければなりません`n`、一方、それより大きなサイズのクエリは返される必要があります。`0`。 

例：```
5 3
2 1
2 2
1 1 2
```最初のクエリでは、チームの規模を尋ねます。`1`、したがって、答えは次のとおりです`5`。 ユーザーの後`1`そして`2`友達になる、グループにはサイズがある`2,1,1,1`、ので、サイズ`2`チームクエリの戻り値`1`、 ない`2`2 人のユーザーのグループは 1 つの完全なチームしか提供できないためです。 

もう 1 つのエッジ ケースは、すでに接続しているユーザーを結合することです。 同じグループ内の 2 人のユーザーが再び友達になった場合でも、友情グラフは変わりません。 不用意に実装すると、コンポーネントが 2 回削除され、保存されているカウントが破損する可能性があります。 

例：```
3 3
1 1 2
1 2 1
2 2
```最終的なコンポーネントのサイズは次のとおりです。`2,1`、したがって、答えは次のとおりです`1`。 2 番目の結合演算は無視する必要があります。 

## アプローチ

 簡単な解決策は、素の集合結合を使用してコンポーネントを維持することです。 タイプのすべてのクエリに対して`2`、現在のすべてのコンポーネント サイズを反復処理し、各コンポーネントが貢献するチームの数を計算できます。 各グループが独立して貢献しているため、これは正解です。`size // s`チーム。 

問題はクエリコストです。 あり得る`10^5`クエリ、また、`10^5`コンポーネント。 最悪の場合、このアプローチは次のように実行されます。`10^10`動作が遅すぎます。 

重要な観察は、サイズの構成要素であるということです。`x`貢献する`floor(x / s)`あらゆるチームサイズの答えへ`s`。 すべてを更新する必要はありません`s`個別に。 の値`floor(x / s)`についてのみ変更します`2 * sqrt(x)`回。 たとえば、すべて`s`特定の間隔内の値が同じ商を生成する場合があります。 

これにより、コンポーネントの追加または削除の効果を少数の範囲の追加として表すことができます。 クエリでは特定の 1 つが要求されるため、`s`、差分配列上のフェンウィック ツリーは、範囲の追加とポイント クエリをサポートできます。 

サイズの成分が 2 つある場合`a`そして`b`サイズに合わせてマージする`a+b`の投稿を削除します。`a`そして`b`の貢献を追加します`a+b`。 DSU が接続を処理し、フェンウィック ツリーが応答を維持します。

 ## アルゴリズムのチュートリアル

 1. すべてのユーザーを独自の DSU コンポーネントとして初期化します。 1 人のユーザーが貢献する`floor(1/s)`したがって、同じコンポーネント更新ルーチンを使用して最初の貢献を追加できます。 
2. 範囲の追加を保存するフェンウィック ツリーを維持します。 位置の値`s`現在の有効なサイズのチームの数を表します`s`。 
3. サイズのコンポーネントを追加する場合`x`、チームサイズのすべての区間を求めます。`floor(x/s)`同じ値を持ちます。 そのような間隔ごとに`[l,r]`、その商をその範囲のフェンウィックツリーに追加します。 
4. 部品を取り外す場合は、符号を逆にして同様の作業を行ってください。 これにより、考えられるすべてのチーム サイズの回答が現在のコンポーネント サイズと同期されます。 
5. フレンドシップ操作の場合、2 つの DSU ルートを見つけます。 すでに等しい場合は、何も変わりません。 それ以外の場合は、両方の古いコンポーネントの寄与を削除し、DSU セットをマージし、新しいコンポーネント サイズの寄与を追加します。 
6. チームサイズを含むトーナメントクエリの場合`s`、フェンウィックツリーに位置の値を問い合わせます`s`。 

商の間隔が小さい理由は次のとおりです。`floor(x/s)`最初はゆっくりと減少し、最後に近づくと急速に変化します。 個別の値の数は次のように制限されます。`O(sqrt(x))`なので、各コンポーネントの更新が効率的になります。 

なぜ効果があるのか:

 維持される不変条件は、すべての位置でのフェンウィック ツリーの値です。`s`の合計に等しい`floor(size/s)`現在接続されているすべてのコンポーネントにわたって。 すべてのコンポーネントが挿入されているため、最初はこれが当てはまります。 マージでは 2 つの古いコンポーネントが正確に削除され、新しいコンポーネントが正確に挿入されるため、友情操作が行われるたびに不変条件は true のままになります。 クエリは、要求されたチーム サイズの維持された値 (正確に必要なチーム数) を読み取るだけです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 2)

    def add(self, idx, val):
        while idx <= self.n:
            self.bit[idx] += val
            idx += idx & -idx

    def range_add(self, l, r, val):
        if l > r:
            return
        self.add(l, val)
        self.add(r + 1, -val)

    def query(self, idx):
        res = 0
        while idx:
            res += self.bit[idx]
            idx -= idx & -idx
        return res

def solve():
    n, q = map(int, input().split())

    parent = list(range(n + 1))
    size = [1] * (n + 1)

    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x

    fw = Fenwick(n)

    def update_component(x, delta):
        l = 1
        while l <= x:
            val = x // l
            r = x // val
            fw.range_add(l, r, val * delta)
            l = r + 1

    update_component(1, n)

    ans = []

    for _ in range(q):
        query = list(map(int, input().split()))
        if query[0] == 1:
            a, b = query[1], query[2]
            ra, rb = find(a), find(b)
            if ra != rb:
                update_component(size[ra], -1)
                update_component(size[rb], -1)
                if size[ra] < size[rb]:
                    ra, rb = rb, ra
                parent[rb] = ra
                size[ra] += size[rb]
                update_component(size[ra], 1)
        else:
            ans.append(str(fw.query(query[1])))

    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```フェンウィック ツリーは、答えを直接保存するのではなく、差分配列を保存します。 範囲の更新では、左側の境界で加算され、右側の境界の後で減算され、プレフィックスの合計により、特定のチーム サイズに対する現在の回答が再構築されます。 

の`update_component`関数は最適化の中核です。 間隔をあけて歩きます。`x // s`は一定です。 ライン`r = x // val`現在の間隔の終わりに直接ジャンプし、考えられるすべてのチーム サイズにわたるループを回避します。 

DSU は、サイズによるパス圧縮と結合を使用します。 格納されたコンポーネントのサイズはマージ後にルートに属するため、マージ順序は慎重に処理されます。 両方のユーザーがすでに同じルートを持っている場合、貢献度の変更は行われません。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |`O((n+q) sqrt(n) log n)`| マージごとに 3 つのコンポーネントが変更され、各コンポーネントの更新では次のものが使用されます。`O(sqrt(n))`フェンウィック演算による商区間。 |

 制約により、約`10^5`操作。 最適化された商分解により、すべてのマージのコストが高くなりすぎる線形更新コストが回避され、総作業量が必要な制限内に抑えられます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    old = sys.stdin
    sys.stdin = io.StringIO(inp)
    out = []
    n, q = map(int, input().split())

    parent = list(range(n + 1))
    size = [1] * (n + 1)

    class Fenwick:
        def __init__(self, n):
            self.n = n
            self.bit = [0] * (n + 2)
        def add(self, i, v):
            while i <= self.n:
                self.bit[i] += v
                i += i & -i
        def ra(self, l, r, v):
            self.add(l, v)
            self.add(r + 1, -v)
        def get(self, i):
            s = 0
            while i:
                s += self.bit[i]
                i -= i & -i
            return s

    fw = Fenwick(n)

    def add_comp(x, d):
        l = 1
        while l <= x:
            v = x // l
            r = x // v
            fw.ra(l, r, v * d)
            l = r + 1

    def find(x):
        if parent[x] != x:
            parent[x] = find(parent[x])
        return parent[x]

    add_comp(1, n)

    for _ in range(q):
        a = list(map(int, input().split()))
        if a[0] == 1:
            x, y = find(a[1]), find(a[2])
            if x != y:
                add_comp(size[x], -1)
                add_comp(size[y], -1)
                parent[y] = x
                size[x] += size[y]
                add_comp(size[x], 1)
        else:
            out.append(str(fw.get(a[1])))

    sys.stdin = old
    return "\n".join(out)

 ## 特殊なケース

 すべてのユーザーが一人のとき、アルゴリズムは`n`サイズのコピー`1`成分。 更新ルーチンは追加することでこれを処理します。`1`チームサイズのみ`1`、そのため、より大きなチームのサイズはゼロのままです。 

友人関係を繰り返すと、DSU は両方のユーザーが同じルートを持っていることを検出します。 コンポーネントのサイズは変更されないため、フェンウィック ツリーは変更されず、保存された回答は有効なままになります。 

サイズの大きなコンポーネントの場合`100000`、アルゴリズムは、考えられるすべてのチームサイズをループするわけではありません。 代わりに、等しい商の範囲間をジャンプします。 これにより、1 つの友人グループにすべてのユーザーが含まれる場合でも、更新コストが低く抑えられます。
