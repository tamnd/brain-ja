 ## 解決策
 ## 問題の理解

 私たちは一連の本を与えられており、次の本に移る前に各本を最初から最後まで読まなければなりません。 各本にはページ数と締め切り日が設定されています。 リーダーはすべての本に対して、1 日あたりのページ数で測定される単一の一定の読書速度を使用し、本を読み終えるまでにかかる日数は、その長さの上限を速度で割ったものに相当します。 書籍は順次処理されるため、各書籍の終了日はこれらの期間の累積合計になります。 

本が終了する日が締め切りを超える場合、その本は遅れているとみなされます。 タスクは、最大 m 冊の本が遅れるように、可能な限り最小の整数の読み取り速度を選択することです。 

この制約により、最大 100,000 冊の書籍が許可され、長さは最大 10^9、期限は最大 10^4 になります。 これにより、すべての速度を単純に試し、それぞれの速度を完全にシミュレートするアプローチは即座に除外されます。 1 つの完全なシミュレーションでも O(n) であるため、10^9 までのすべての速度を試すことは不可能です。 有効なソリューションでは、候補の数を大幅に削減しながら、各候補を効率的に評価する必要があります。 

微妙な問題は、遅刻の定義方法にあります。 遅刻は本ごとに独立したものではありません。 それは累積読書時間によって異なります。 素朴な間違いは、以前の長い本がその後のすべての本を遅らせることを無視して、各本を個別に比較することです。 

もう 1 つのよくある落とし穴は、天井分割の処理を誤ることです。 整数の除算を l // s として直接使用すると、l が s で割り切れない場合は常に時間を過小評価することになり、累積スケジュールが誤って削減され、実行可能なように見える無効な速度が生成される可能性があります。 

## アプローチ

 簡単な試みは、1 から本の最大の長さまで、あらゆる可能な読書速度を試すことです。 それぞれの速度について、すべての本を順番に読むことをシミュレートし、各本の読み終えた日を計算し、締め切りを超過した本の数を数え、その数が最大でも m であるかどうかを確認します。 これは問題で説明されているプロセスを直接反映しているため、これは正しいです。 ただし、コストは法外です。 S 個の可能な速度をテストし、それぞれに O(n) のシミュレーションが必要な場合、総コストは O(Sn) となり、最悪のケースでは 10^14 の演算程度になります。 

重要な構造的観察は、読書速度を上げることが唯一の助けになるということです。 特定の速度 s で最大 m 冊の遅れを防ぐのに十分な場合、それ以上の速度ではすべての本が速度 s までに完了するため、遅れている本の数を増やすことはできません。 この単調な動作により、問題をソートされた述語の検索として扱うことができます。実現可能な速度はすべての整数の接尾辞を形成します。 

単調性を認識したら、答えに二分探索を適用できます。 候補速度については、一度シミュレーションして、何冊が遅れているかを数えます。 これにより、シミュレーションの数が、回答範囲の線形から対数に減少します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | あらゆる速度でのブルートフォース | O(maxL・n) | お(1) | 遅すぎる |
 | 二分探索 + シミュレーション | O(n log maxL) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは、速度の実現可能性を独立してテストできるという事実を利用します。

1. 指定された速度が有効かどうかを確認する関数を定義します。 すべての本を順番に読むことをシミュレートし、費やした日数の累計を維持します。 各本について、読み終えるまでに必要な日数を加算し、(l + s − 1) // s として計算します。 累積時間を更新した後、終了日がその本の締め切りを超えているかどうかを確認します。 そうであれば、それは遅れた本としてカウントされます。 
2. 遅れた本の数が m 個以下の場合、チェック関数は true を返します。 これにより、速度に関する単調な述語が得られます。 
3. 答えの二分探索範囲を設定します。 可能な最小速度は 1 です。その速度ではどんな本でも 1 日で読み終えることができるため、必要な最大速度は本の最大の長さになります。 
4. この範囲に対して二分探索を実行します。 中間速度ごとに、実現可能性チェックを実行します。 
5. 速度が実現可能な場合は、右側の境界を下に移動して速度の低下を試みます。 それが不可能な場合は、左側の境界を上に移動して速度を上げます。 
6. 二分探索が収束した後、左側の境界が実現可能な最小速度になります。 

機能する理由: シミュレーションは、単調に増加しない速度に関する述語を定義します。 遅延を許容範囲内に抑えるのに十分な速度になると、それより大きな速度ではすべての完了時間を維持または改善するため、遅れた本の数を増やすことはできません。 これにより、実行可能領域が連続していることが保証されます。これはまさに、最小有効速度を見つけるための二分探索に必要な条件です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check(speed, books, m):
    time = 0
    late = 0
    for l, d in books:
        time += (l + speed - 1) // speed
        if time > d:
            late += 1
            if late > m:
                return False
    return True

def solve():
    n, m = map(int, input().split())
    books = [tuple(map(int, input().split())) for _ in range(n)]

    lo, hi = 1, max(l for l, _ in books)

    while lo < hi:
        mid = (lo + hi) // 2
        if check(mid, books, m):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```シミュレーションはソリューションの中核です。 変数`time`は、書籍ごとの期間ではなく、現在の書籍が終了する累積日を表します。 各本は前の本が完了した後にのみ開始されるため、この蓄積は不可欠です。 

天井分割`(l + speed - 1) // speed`日の一部が正しく考慮されるようにします。 この調整を行わないと、長さが速度で割り切れない書籍は、実際よりも速く誤って表示され、正確さが損なわれてしまいます。 

二分探索では、それ以下の速度であるという不変条件が維持されます。`lo`は無効ですが、それ以上の速度は`hi`有効です。 チェック機能は実行可能条件を一貫して強制し、検索を安全に収束させることができます。 

## 実用的な例

 次のサンプル入力を考えてみましょう。 

n = 3、m = 1

 書籍: (450, 9)、(500, 6)、(300, 4)

 二分探索を使用して候補の速度をテストします。 

| 速度 | 1冊目終了 | 2巻終了 | 3冊目終了 | 遅れたカウント | 実現可能 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 450 | 950 | 1250 | 3 | いいえ |
 | 2 | 225 | 475 | 625 | 2 | いいえ |
 | 3 | 150 | 317 | 417 | 1 | はい |

 スピード 2 の場合、2 冊目の本は 475 日目に終了し、すでに期限の 6 日を超えており、3 冊目も失敗します。 そのため、遅れた本が多すぎます。 速度 3 では、1 冊だけが遅れており、制約を満たしているため、答えは 3 になります。 

このトレースは、遅延が個々の本の所要時間ではなく累積終了時間にどのように依存するかを示しています。 速度が適度に上昇しただけでも、完了時間が大幅に遅くなります。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log L) | 各実現可能性チェックではすべての書籍がスキャンされ、速度を超えた二分探索では書籍の最大長 L | まで対数チェックが実行されます。 
| スペース | お(1) | 入力ストレージ以外に維持されるカウンタはわずかです。 

この制約では最大 100,000 冊の書籍が許可され、log(max L) は約 30 であるため、ソリューションはおよそ数百万回の操作を実行しますが、制限内に収まります。

 ## 特殊なケース

 重大なエッジケースは、1 冊の本だけが遅刻を許可される場合です。 このような場合、最適な速度は、1 冊の長い本が締め切りの連鎖を破らなくなるしきい値のすぐ上にあることがよくあります。 実現可能性関数が false から true に 1 回だけ反転するため、二分探索はこれを正しく捕捉します。 

もう 1 つの重要なケースは、すべての締め切りが本の長さに比べて非常に短い場合です。 たとえば、すべての締め切りが 1 の場合、本の最大の長さに等しい速度のみが、どの本でも 1 日以内に完了できることを保証します。 そうしないと、すべての本がすぐに遅れてしまいます。 実行可能性チェックでは累積時間に基づいて遅延がカウントされ、二分探索により必要な最大速度に直接到達するため、アルゴリズムはこれを自然に処理します。 

最後に、m が大きい (n − 1 に近い) 場合、ほぼすべての速度が許容可能になります。 チェック機能は、過剰な遅延書籍をカウントすることで正確性を確保し、二分探索はスケジュール内の単一の最悪の障害点を回避する最小速度に収束します。
