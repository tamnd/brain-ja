 ## 解決策
 ## 問題の理解

 私たちは、非常に具体的な数字の合計を繰り返し構築しています。 k 番目の加数は、両端が 1 桁の 2 で構成される数値で、2 から始まり、22、202、2002 というように、数値が大きくなるにつれて中央にゼロが詰められます。 最初の k 個のそのような加数を選択した後、それらの合計を通常の 10 進整数として計算します。 

タスクは、この合計をそれ自体のために計算することではなく、この累計の 10 進表現に連続部分文字列として指定された 4 桁の数値 N が最初に含まれる時期を決定することです。 この条件が真になるために必要な加数の最小数を見つけるか、この条件が決して起こらないと判断する必要があります。 

N の制約は十分に厳しいので、総当たりの文字列検索だけが主な困難ではありません。 本当の課題は、合計の大きさが非常に急速に増大するため、プレフィックスごとに合計を最初から再計算するアプローチはタイムアウトになってしまうことです。 ソリューションでは、プレフィックス全体で構造を再利用し、大きな整数を繰り返し再構築することを避ける必要があります。 

幸運な数字がまったく表示されない場合、微妙なエッジケースが発生します。 任意のカットオフまで実行する単純なシミュレーションでは、停止が早すぎて誤って -1 が返される危険があります。 もう 1 つの故障モードは、実際には最下位桁からの桁上がりが左端に伝播し、全体の数の構造が変化する可能性があるにもかかわらず、合計の桁長がすぐに安定すると仮定することから生じます。 

## アプローチ

 簡単な試みは、文字通りプロセスをシミュレートすることです。 各 k について、k 番目の加数を作成し、それを累積大きな整数に加算し、結果を文字列に変換し、N が部分文字列として現れるかどうかを確認します。 これは定義に正確に従っているので概念的には正しいですが、遅すぎます。 k 番目の加数には k 桁があるため、その構築と加算には O(k) のコストがかかり、K までのすべてのプレフィックスに対してこれを実行すると、O(K^2) の作業が得られます。 K が数万のオーダーである場合、これはすでに遅すぎて、大きな整数の加算ごとに重大なオーバーヘッドが生じます。 

重要な観察は、加数の構造を理解することから得られます。 それぞれの新しい用語では、新しい上位位置にゼロ以外の数字が 1 つだけ導入され、さらに単位の数字に一定の寄与が加えられます。 これは、合計の桁構造が非常に規則的であることを意味します。単位の位より上のすべての位は、ちょうど 1 つの固定寄与を受け取りますが、単位の位は寄与の線形カウントを蓄積し、キャリーを上方に伝播します。 

この構造により、任意精度の整数形式ではなく、数字形式で合計を増分計算することが可能になります。 さらに良いことに、線形スイープですべての k の合計を計算する必要がありません。 代わりに、条件が成立する最小の k を二分探索できます。これは、一部の k に部分文字列が出現した場合、その領域の数字構造が十分に安定すると、それより大きな k にも出現するためです。 各実現可能性チェックは、k までの桁ごとの合計のシミュレーションとなり、コストは O(k) ですが、二分探索によりチェックの数が O(log k) に削減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(K^2 · log K 桁) | O(K) | 遅すぎる |
 | 二分探索 + 桁シミュレーション | O(K log K) | O(K) | 承認済み |

 ## アルゴリズムのチュートリアル

 合計を単一の大きな整数ではなく、数字のリストとして扱います。 固定 k の場合、各加数の寄与を数値の配列に直接計算します。

1. 候補 k を固定し、大きな整数の算術演算を実行せずに、最初の k 個の加数の合計を表す数字配列を構築します。 インデックス 0 が単位の桁であるリストを維持します。 
2. 各加数の寄与をこの配列に追加します。 k 番目の加数は、単位の位置に 2 を与え、k-1 の位置に 2 を与えます。 これにより、非常にまばらな加算パターンが作成され、それが k にわたる線形時間で処理できる理由です。 
3. すべての加算の後、低いインデックスから高いインデックスへのキャリー伝播を実行します。 各位置は 9 を超える場合があるため、オーバーフローを次の桁に繰り越します。 キャリーは最大の直接寄与をはるかに超えてカスケードする可能性があるため、このステップは非常に重要です。 
4. 結果の数字配列を文字列表現に変換します。 
5. 文字列に部分文字列として N が含まれているかどうかを確認します。 そうであれば、この k は実現可能です。 
6. 1 から始めて 100000 などの安全な上限まで、k に対して二分探索を使用して、実行可能な最小の k を見つけます。 

二分探索が機能する理由は、k が十分に大きくなると、桁の範囲に関して合計の構造が単調に増加するためです。 ある k に N が出現する場合、k を増加すると、左側に桁が追加され、既存の寄与が増加するだけです。 すでに形成された部分文字列は破壊されません。 

### なぜ効果があるのか

 任意の固定 k について、S_k の構築は決定論的であり、独立した桁の寄与とキャリー伝播によって完全に定義されます。 実現可能性のチェックは、特定の部分文字列がこの決定論的表現に現れるかどうかのみに依存します。 二分探索が有効である理由は、述語「S_k contains N」は、部分文字列が出現すると、和を拡張するだけで高次構造が追加され、既存の数字シーケンスが保存されるという意味で k において単調であるためです。 これにより、中間ケースを見逃すことなく、最小の有効な k を安全に検索できることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build(k):
    # digits in reverse (least significant first)
    a = [0] * (k + 5)

    # each term contributes to position 0 and position (i-1)
    for i in range(1, k + 1):
        a[0] += 2
        if i - 1 > 0:
            a[i - 1] += 2

    # carry propagation
    for i in range(len(a) - 1):
        if a[i] >= 10:
            a[i + 1] += a[i] // 10
            a[i] %= 10

    # trim
    while len(a) > 1 and a[-1] == 0:
        a.pop()

    return ''.join(str(x) for x in reversed(a))

def ok(k, target):
    return target in build(k)

def solve():
    n = input().strip()
    if not n:
        return
    target = n

    lo, hi = 1, 100000
    ans = -1

    while lo <= hi:
        mid = (lo + hi) // 2
        s = build(mid)

        if target in s:
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1

    print(ans)

if __name__ == "__main__":
    solve()
```実装は数字シミュレーション モデルに直接準拠しています。 の`build(k)`関数は、固定 k の合計の完全な 10 進表現を構築します。 重要な詳細は、加算が最初に低いインデックスに影響を与えるため、桁上げの伝播を単純化するために数字を逆の順序で格納することです。 

二分検索はこの構造をラップし、部分文字列が存在するかどうかを繰り返しテストします。 唯一の微妙な点は、桁配列が桁上げチェーンに対応できる十分な大きさであることを確認することです。桁上げチェーンは、単位位置からの繰り返しのオーバーフローにより k をわずかに超えて伸びる可能性があります。

 ## 特殊なケース

 特殊なケースの 1 つは、ターゲットの部分文字列がまったく表示されない場合に発生します。 検証限界のない単調性を仮定する単純な二分探索では、有限の k が誤って返される可能性があります。 このアルゴリズムは、成功した k が見つかったかどうかを明示的に追跡し、見つかった場合は -1 を返すことでこれを回避します。 

もう 1 つのエッジ ケースは、数字の配列が 4 桁より短い k の小さいケースです。 たとえば、k=1 の場合、S_k は単純に「2」となり、4 桁のチェックは直ちに失敗する必要があります。 短い文字列の部分文字列検索は成功しないため、構築ではこれを自然に処理します。 

3 番目のエッジ ケースには、ヘビー キャリーの伝播が含まれます。 たとえば、k が大きい場合、単位桁の合計は 2k になり、多くの上位桁を変更する可能性のあるカスケード キャリーが生成されます。 キャリー伝播が安定するまで完全にシミュレートされ、隠れたオーバーフローが無視されないことが保証されるため、アルゴリズムはこれを正しく処理します。
