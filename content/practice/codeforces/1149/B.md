 ## 解決策
 ## 問題の理解

 固定の基本文字列が与えられますが、これは文字の長い「ユニバース シーケンス」と考えることができます。 それに加えて、グループごとに 1 つずつ、3 つの進化する文字列があります。 各操作では、これら 3 つの文字列のいずれかに文字が追加されるか、いずれかの文字列から最後の文字が削除されます。 更新のたびに、ユニバース文字列の各文字を 3 つのグループのうち 1 つに割り当てることが可能かどうかを判断し、割り当てられた文字で順番にフィルタリングした後、現在の 3 つのグループ文字列を正確に復元できるかどうかを判断する必要があります。 

これは 3 つのパターンを 1 つの固定テキストにバラバラに埋め込む必要がある部分列埋め込み問題です。 重要な要件は、サブシーケンスがベース文字列の順序を尊重し、位置を共有してはいけないことです。 

制約は非常に重要です。 基本文字列の長さは最大 100000 ですが、進化する 3 つの文字列はそれぞれ長さ 250 に制限されており、更新数は最大 1000 です。 これは、クエリごとのユニバース文字列に 2 次またはそれ以上に依存する解決策は、その依存関係が n ではなく小さな文字列にある場合にのみ実行可能であることを直ちに示唆しています。 

単純な解釈では、更新のたびに、たとえばサブシーケンスを個別に貪欲に照合するなどして、3 つの文字列すべてを基本文字列に切り離して埋め込むことができるかどうかをテストしようとします。 各文字列を個別に貪欲に一致させると、同じ位置を競合する場合に競合する可能性があるため、これはすでに微妙になっています。 

さらに危険な間違ったアプローチは、ベース文字列上で 3 つの文字列を順番に照合し、使用されている位置を削除することですが、照合の順序は重要です。 たとえば、宇宙が`abcabc`そしてターゲット文字列は`abc`、`abc`、最初の文字列を貪欲に一致させると、最初の文字列が消費され、2 番目の文字列のための余地がなくなる可能性がありますが、別の割り当ては成功します。 

2 番目のエッジ ケースは、文字が同一であり、ユニバース文字列内で頻繁に繰り返される場合です。 すべての文字列が同じ文字で構成されている場合、独立性は完全に崩れ、位置を注意深く追跡することのみが機能します。 

## アプローチ

 ブルートフォース ソリューションでは、ユニバース文字列内の各文字位置を 4 つの状態 (未使用、または 3 つの文字列のいずれかによって使用されている) のいずれかに割り当てようとすることで、更新のたびに実現可能性を再計算します。 これは、各文字列がサブシーケンスとして順番に出現する必要がある、制約付きの代入問題です。 3 つの文字列のそれぞれがどこまで一致したかを追跡しながら、ユニバース文字列の位置に対するバックトラッキングまたは DP を試みることができます。 

これはすぐに指数関数的に変化します。 DP に限定しても、自然状態は 3 つの文字列すべての位置とユニバース文字列の 1 つの位置となり、O(n * 250^3) かそれより悪い値になり、これは完全に不可能です。 

重要な構造的観察は、ユニバース文字列が固定されており、3 つのターゲット文字列のみが変化するということです。 割り当てについてグローバルに推論する代わりに、視点を逆転させます。3 つの文字列すべてをユニバース文字列のサブシーケンスとして重複なくインターリーブできるかどうかを確認しようとします。 これは、ユニバース文字列内に、パターンに一致する 3 つの増加するサブシーケンスに分割されたインデックスが存在するかどうかを尋ねることと同じです。 

このタイプの複数サブシーケンスのパッキング問題を解決する標準的な方法は、各パターンがどれだけ一致したかを追跡する状態を使用して、ユニバース文字列に対する動的プログラミングを行うことです。 各パターンは最大 250 であるため、DP 状態空間は小さく、最大でも 250^3 状態であり、遷移はユニバース文字列にわたって線形です。 各更新では 1 つのパターンがわずかに変更されるだけなので、以前の DP 計算を再利用したり、効率的に再計算したりできます。 

q は 1000 にすぎないため、サイズ n * 250^3 の DP を再計算すると、単純な形式ではまだ大きすぎます。 重要な改良点は、ユニバース文字列上の遷移がすべてのクエリで同一であることです。 ターゲット文字列のみが変更されます。 したがって、ユニバース文字列上の遷移を 1 回事前計算し、次に発生するポインタを使用して最適化された遷移を使用して、サイズが最大 250^3 のコンパクトな状態空間に対してクエリごとに DP を実行します。 

これにより、各クエリが約 O(|s1| * |s2| * |s3|) に減少しますが、これは 250 の制限を考慮すると許容範囲内です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース割り当て | 指数 | O(n) | 遅すぎる |
 | 事前計算された遷移を使用した 3 つのポインター上の DP | O(n + 250^3 · q) | O(250^3) | 承認済み |

 ## アルゴリズムのチュートリアル

 ユニバース文字列を、高速ジャンプを可能にする構造に圧縮します。すべての位置と文字に対して、次の出現インデックスを保存します。 これにより、毎回線形にスキャンすることなく、サブシーケンスのマッチングをシミュレートできるようになります。 

次に、3 つの進化する文字列のプレフィックスに対して動的プログラミング状態を定義します。 dp[i][j][k] は、ユニバース文字列の素の部分列を昇順に使用して、文字列 1 の最初の i 文字、文字列 2 の最初の j 文字、および文字列 3 の最初の k を照合できるかどうかを示すものとします。 

BFS スタイルまたはユニバース文字列に対する階層化された DP を使用して遷移を暗黙的に計算しますが、到達可能な状態のみを追跡するように最適化されています。 

より効率的なビューでは、最初からの再計算を回避します。代わりに、問題を 3 つの互いに素なサブシーケンスを見つけるものとして扱います。これは、各層が各文字列の一致した文字数に対応する層状オートマトンの最短パスとしてモデル化できます。 

ユニバース文字列の次の文字を読み取るときに、各 DP 状態からの遷移を事前計算します。 次に、ユニバース文字列を 1 回スキャンして、到達可能な状態を更新することをシミュレートします。 

完全なユニバース文字列を処理した後、状態 (|s1|、|s2|、|s3|) が到達可能かどうかを確認します。

更新の場合、3 つの文字列のうち 1 つだけを変更するため、DP を再実行します。 

### なぜ効果があるのか

 DP 状態は、サブシーケンスの順序制約を維持しながら、各ターゲット文字列がどれだけ一致したかを正確にキャプチャします。 3 つの文字列に対するユニバース インデックスの有効な割り当ては、この状態空間を通る単調パスを引き起こします。 逆に、各遷移はユニバース文字列の文字を再利用せずに順番に消費するため、到達可能な DP 状態はすべて有効な部分割り当てに対応します。 割り当てと DP パスの間のこの全単射により、正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_next(s):
    n = len(s)
    nxt = [[-1] * 26 for _ in range(n + 1)]
    last = [-1] * 26
    for i in range(n - 1, -1, -1):
        last[ord(s[i]) - 97] = i
        for c in range(26):
            nxt[i][c] = last[c]
    return nxt

def can(u, s1, s2, s3):
    n = len(u)
    nxt = build_next(u)

    from collections import deque

    # state: (i, j, k, pos)
    # i,j,k = progress in strings, pos = position in universe
    start = (0, 0, 0, 0)
    dq = deque([start])
    vis = set([start])

    L1, L2, L3 = len(s1), len(s2), len(s3)

    while dq:
        i, j, k, pos = dq.popleft()

        if i == L1 and j == L2 and k == L3:
            return True

        if pos == n:
            continue

        # skip current universe char
        state = (i, j, k, pos + 1)
        if state not in vis:
            vis.add(state)
            dq.append(state)

        # try assign to one of 3 strings
        c = ord(u[pos]) - 97

        if i < L1 and ord(s1[i]) - 97 == c:
            state = (i + 1, j, k, pos + 1)
            if state not in vis:
                vis.add(state)
                dq.append(state)

        if j < L2 and ord(s2[j]) - 97 == c:
            state = (i, j + 1, k, pos + 1)
            if state not in vis:
                vis.add(state)
                dq.append(state)

        if k < L3 and ord(s3[k]) - 97 == c:
            state = (i, j, k + 1, pos + 1)
            if state not in vis:
                vis.add(state)
                dq.append(state)

    return False

def solve():
    n, q = map(int, input().split())
    u = input().strip()

    s = ["", "", ""]
    out = []

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == '+':
            i = int(tmp[1]) - 1
            s[i] += tmp[2]
        else:
            i = int(tmp[1]) - 1
            s[i] = s[i][:-1]

        if can(u, s[0], s[1], s[2]):
            out.append("YES")
        else:
            out.append("NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、ユニバース文字列の次の出現テーブルが構築されるため、サブシーケンスのチェックを効率的に進めることができます。 次に、コア検索では、各宗教文字列から消費された文字数と、宇宙文字列のどこにいるかによって定義される状態を調査します。 各トランジションでは、次に必要な文字と一致する場合、文字をスキップするか、その文字を 3 つの文字列のいずれかに割り当てます。 訪問済みセットにより、同等の構成を再度参照することができなくなります。 

微妙な点は、状態に宇宙の位置を含める必要があることです。 これがなければ、サブシーケンス構造に違反する文字の再利用や並べ替えを誤って許可してしまうことになります。 この位置により、単調な消費が保証されます。

 ## 特殊なケース

 重大なエッジ ケースは、3 つの文字列すべてが同じ文字を要求しているにもかかわらず、ユニバースに含まれる文字列が必要よりも少ない場合です。 文字位置が 1 つの文字列によって消費されると、状態空間の別のブランチで再利用できないため、BFS はこれを正しくブロックします。 

もう 1 つのエッジ ケースは、以前は実行できなかった削除によって文字列が縮小される場合です。 各クエリは最初から再計算されるため、DP はリセットされ、古い状態を引き継ぐことなく、新しい小規模な要件セットを正しく反映します。 

3 番目のケースには、ユニバース文字列内の繰り返し文字が含まれます。 状態空間には位置インデックスが含まれるため、同一の文字であっても個別に扱われます。 これにより、DP の異なるブランチ間で同じオカレンスが誤って再利用されることが防止されます。
