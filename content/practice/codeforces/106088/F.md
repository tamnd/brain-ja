 ## 解決策
 ## 問題の理解

 レベルのシーケンスが与えられ、厳密に左から右の順序で処理されます。 各レベルには必要な数のアイテムがあり、挑戦する前にそれらを入手する必要があります。 プレイヤーが十分なアイテムを持っていればレベルに入ることができますが、クリア直後にアイテムを 1 つだけ永久に失います。 

入力は、各位置がそのレベルを開始するために必要な項目の最小数を表す配列で構成されます。 これに加えて、複数のクエリが与えられます。 各クエリは保存されたゲームの状態を記述します。プレーヤーは現在、あるレベルのインデックスにいます。$l$、そして彼らは現在所有しています$x$アイテム。 この状態から、プレイヤーは再びレベルごとに進み、現在のレベルの要件を満たすことができるかどうかを常にチェックし、正常に完了するたびにアイテムを 1 つ失います。 タスクは、プロセスが停止するまでに連続レベルを何段階まで完了できるかを計算することです。 

この制約により、ソリューションはクエリごとの非常に高速な処理による線形または線形に近い前処理を実現します。 両方$n$そして$q$まで可能です$5 \cdot 10^5$したがって、各クエリを段階的にシミュレートするアプローチは、すぐに遅すぎます。 平$O(nq)$または$O(\log n)$シミュレーション内のステップごとの費用は、大幅に償却しない限り受け入れられません。 

リソースが単調に減少することから、微妙な問題が発生します。 各レベルの後、利用可能なアイテムの数は 1 つずつ減少しますが、必要条件は任意に変化します。 この組み合わせでは、トラバーサル中に制約が動的に変化するため、単純なプレフィックス実行可能性チェックが妨げられます。 

各レベルの実現可能性を個別にチェックするだけで十分であると仮定すると、素朴な落とし穴が発生します。 たとえば、レベルに 10 個のアイテムが必要で、プレイヤーは最初に 10 個を持っていますが、前のレベルを通過した後、アイテム数が予想より早く要件を下回ったとします。 実現可能かどうかは、開始状態だけでなく、以前にクリアしたレベルの数によって決まります。 

もう 1 つの誤った直感は、貪欲なスキップを試みることです。つまり、最初のレベルを事前に計算します。$a_i > x$。 これは失敗します。$x$レベル間で一定ではありません。 進むにつれて減少します。 

## アプローチ

 ブルートフォースのアイデアは単純です。 各クエリについて、次のレベルから開始します$l$と$x$項目を選択して段階的にシミュレーションします。 レベルで$i$、現在の項目が少なくとも以下であるかどうかを確認します。$a_i$。 そうでない場合は、停止してください。 それ以外の場合は項目を減らして続行します。 これによりプロセスが正しくモデル化されますが、最悪の場合、各クエリが配列のサフィックスのほぼ全体を走査する可能性があり、$O(nq)$限界をはるかに超えた行動。 

重要な観察は、レベル間の唯一の相互作用はリソースの決定論的な線形減少であるということです。 レベルの前に現在のアイテム数を定義すると$i$として$x - (i - l)$、次にレベルを通過するための条件$i$は次のようになります:$$x - (i - l) \ge a_i$$並べ替えると次のようになります。$$x \ge a_i + (i - l)$$これにより、各レベルが固定のしきい値に変換されます。$x$ただし、クエリの開始位置から相対的な位置だけシフトされます。 

これを次のように書き換えることができます。$$x + l \ge a_i + i$$これは重要な単純化です。レベルを通過するための条件は値のみに依存します。$a_i + i$、クエリは一定のシフトに寄与します$x + l$。 さて、問題は次のとおりです。位置から開始します。$l$を維持したままどこまで右に進むことができるでしょうか。$$a_i + i \le x + l$$これで、すべてが静的になります。 各位置には事前に計算された値があります$b_i = a_i + i$。 クエリの場合はインデックスから開始します$l$そして、すべてのサフィックスの最も長いプレフィックスが必要です。$b_i \le x + l$。 これは古典的な範囲最大クエリの問題です。つまり、範囲の最大値が$b$セグメント上の値はしきい値内にあります。 セグメント ツリーまたはスパース テーブルを使用すると、到達可能な最も遠い位置までバイナリ サーチを繰り返し実行できます。 

エンドポイントを二分探索します$r$クエリごとに。 候補者にとって$r$かどうかを確認します。$\max(b_l, \dots, b_r) \le x + l$。 true の場合、さらに拡張できます。 そうでなければ、私たちは縮こまってしまいます。 これにより、$O(\log n)$クエリごとに$O(n)$前処理中。

 ## アルゴリズムのチュートリアル

 1. 配列を静的しきい値配列に変換します。$b_i = a_i + i$。 これにより、位置ベースのアイテム損失の要件と影響の両方が単一の値で取得されます。 
2. 範囲最大のクエリ構造を構築する$b$。 これにより、最大値が制限を超えているかどうかを確認することで、セグメント全体が実現可能かどうかを迅速にテストできます。 
3. クエリごとに$(l, x)$、有効なしきい値を計算します$T = x + l$。 これは、許容される最大値です。$b_i$私たちが試みるあらゆるレベルに対応します。 
4. 到達可能な最も遠いインデックスに対して二分検索を実行します。$r \in [l, n]$。 各チェックでは次のことが検証されます。$\max(b_l, \dots, b_r) \le T$。 true の場合、検索範囲を拡張します。 それ以外の場合は減らしてください。 
5. 最終エンドポイントを変換する$r$返すことで答えを導き出す$r - l + 1$。 

二分探索が機能するのは、実行可能性が単調であるためです。$r$。 セグメントの場合$[l, r]$が有効である場合は、制約を削除しても違反が発生しないため、より小さいセグメントも有効です。 

### なぜ効果があるのか

 変革$b_i = a_i + i$リソースの線形枯渇をレベルごとの固定しきい値に吸収します。 元のプロセスは減少する状態変数に依存しますが、再配置後は、各レベルがクエリに対して静的な制約を個別に課します。 セグメントの実現可能性は、そのセグメント内のすべての制約が単一の定数境界によって個別に満たされることと同等になります。$T$。 セグメントの有効性はセグメント内の最大値のみに依存するため、範囲最大クエリは実現可能性を正確に特徴付け、二分探索は拡張の単調性を利用します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        n = len(arr)
        self.n = 1
        while self.n < n:
            self.n *= 2
        self.seg = [-10**18] * (2 * self.n)
        for i in range(n):
            self.seg[self.n + i] = arr[i]
        for i in range(self.n - 1, 0, -1):
            self.seg[i] = max(self.seg[2 * i], self.seg[2 * i + 1])

    def query(self, l, r):
        l += self.n
        r += self.n
        res = -10**18
        while l <= r:
            if l % 2 == 1:
                res = max(res, self.seg[l])
                l += 1
            if r % 2 == 0:
                res = max(res, self.seg[r])
                r -= 1
            l //= 2
            r //= 2
        return res

n = int(input())
a = list(map(int, input().split()))

b = [a[i] + i + 1 for i in range(n)]

st = SegTree(b)

q = int(input())
out = []

for _ in range(q):
    l, x = map(int, input().split())
    l -= 1
    T = x + (l + 1)

    lo, hi = l, n - 1
    ans = l - 1

    while lo <= hi:
        mid = (lo + hi) // 2
        if st.query(l, mid) <= T:
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    out.append(str(ans - l + 1))

print("\n".join(out))
```セグメント ツリーには変換された値が保存されます$b_i$、任意の間隔にわたって高速かつ最大のクエリを可能にします。 各クエリは、その開始状態を単一のしきい値に変換します。$T$次に、バイナリ検索を使用して、到達可能なプレフィックスを可能な限り拡張します。 

よくある微妙な点は、インデックス作成の一貫性です。 変換では概念的に 1 から始まるインデックスを使用するため、$b_i = a_i + i$しきい値で使用されているのと同じインデックス付けと一致する必要があります$x + l$。 0 ベースのインデックス付けと 1 ベースのインデックス付けの間に不一致があると、実現可能性の境界が変化し、正確性が損なわれます。

 ## 特殊なケース

 重大なエッジ ケースは、セグメント内の最初のレベルがすでにしきい値に違反している場合です。 例えば：```
a = [100, 1, 1], l = 1, x = 0
```ここ$b_1$すでにはるか上を行っています$T$, したがって、答えはゼロです。 二分探索では、範囲の最大値がすぐにしきい値を超えるため、最小のセグメントでも失敗することが正確に識別されます。 

すべてのレベルが実現可能な場合、別の特殊なケースが発生します。 その状況では、二分探索は次のように拡張されます。$n$早期終了なしで、セグメント ツリーは常に以下の値またはそれに等しい値を返します。$T$、完全な走査が正しく報告されることを保証します。 

最後の微妙なケースは、インデックスの一貫性です。 以来$b_i$定義では 1 ベースのインデックスを使用しており、0 ベースのクエリしきい値を混合すると、実行可能性が 1 レベルだけシフトする可能性があり、境界クエリでのみ発生するオフバイ 1 エラーが発生します。$x$レベルを 1 つ追加するのに十分です。
