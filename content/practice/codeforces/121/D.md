 ## 解決策
 ## 問題の理解

 数字のセグメントを調整した後に表示できる「完全な幸運の数字」の最大数を見つけるように求められます。 ラッキー ナンバーとは、桁が 4 と 7 のみで構成される任意の正の整数です。各セグメントは、数直線上の範囲 [l_i, r_i] です。 番号がすべてのセグメントに同時に属している場合、その番号は完全であるとみなされます。 最大 _k_ 回の移動が許可されており、移動は数直線に沿って任意のセグメントを +1 または -1 シフトすることで構成されます。 

入力により、_n_ 個のセグメントと最大 _k_ 個の移動が得られます。 各セグメントの境界と _k_ は、最大 10^18 まで非常に大きくすることができ、セグメント数は最大 10^5 まで可能です。 これにより、数値自体が天文学的に大きくなる可能性があるため、セグメントの和集合または交差部分内のすべての数値を反復するソリューションは即座に排除されます。 各セグメント内のすべての整数を反復処理することさえ不可能です。 すべての整数を列挙することなく、セグメントと潜在的な幸運の数字を扱うアプローチが必要です。 

エッジケースは、セグメントがすでに遠く離れている場合に発生します。 たとえば、セグメント [1,1]、[100,100]、および k=1 の場合、交点が重なるほど十分にシフトできないため、ラッキー ナンバーがいっぱいになることはありません。 単純な解決策では、移動予算を考慮せずに交差点をやみくもに計算しようとし、ゼロ以外の幸運な数字が誤って報告される可能性があります。 

もう 1 つの微妙なエッジ ケースは、セグメントの幅が非常に広く、交差部分が自然に大きい場合です。 アルゴリズムは、複数のラッキーナンバーが同じ範囲内にある場合に、カウントしすぎないようにする必要があります。 

## アプローチ

 ブルートフォースアプローチを説明するのは簡単です。 考えられる最大のセグメント境界内のすべてのラッキー ナンバーを列挙し、各セグメントを左または右に移動して合計 _k_ 回以下の移動を使用して、各ラッキー ナンバーがすべてのセグメントに含まれるかどうかを確認することもできます。 これは論理的には正しいですが、計算的には実行不可能です。 10 ^ 18 未満のすべてのラッキー ナンバーを生成しても、メモリや時間で管理できる範囲をはるかに超える、10 ^ 10 のオーダーのラッキー ナンバーが生成されます。 

重要な洞察は、ラッキーナンバーはまばらであり、その数字のパターンによって完全に決定されるということです。 すべての整数を反復処理する代わりに、再帰または 4 と 7 のみを含む数字列の BFS を使用して、最大 10^18 までのすべてのラッキー ナンバーを生成します。ソートされたラッキー ナンバーのリストを取得したら、問題は一連の範囲クエリに縮小されます。各ラッキー ナンバーについて、セグメントをシフトして、それをカバーできるかどうか ≤ k の移動を使用できますか?

 次に、2 ポインターまたはスライディング ウィンドウ手法を使用できます。 数直線上の幸運な数字を想像してください。 潜在的なセンターとしてのラッキーナンバーごとに、それを埋めるための最小の手数を計算します。 ラッキー ナンバー全体にウィンドウを移動し、動きを追跡することで、動きの予算内でカバーできる完全なラッキー ナンバーの最大数を見つけます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(#数値 * n) | O(#数値) | 遅すぎる |
 | 最適 | O(n * log n + L) ここで、L はラッキーナンバーの数 ≤ 10^18 | O(L) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 10^18 までのすべてのラッキーナンバーを生成します。 空の数値から開始し、数字 4 と 7 を再帰的に追加して、数値を収集します。 結果のリストを昇順に並べ替えます。 ラッキーナンバーの桁の長さは指数関数的に増加するため、これにより管理しやすいリストが作成されます。 
2. 各セグメントについて、現在の左右の境界を維持します。 中心的な考え方は、任意のラッキーナンバー x の候補について、x をセグメント i でカバーするために必要な最小限の動きは次のとおりであるということです。`max(0, l_i - x)`x < l_i の場合、または`max(0, x - r_i)`x > r_i の場合、それ以外の場合、x がすでにセグメント内にある場合はゼロです。 
3. すべての幸運な数字を潜在的な完全な数字として繰り返し処理します。 それぞれについて、すべてのセグメントに必要な合計移動数を計算します。 合計移動数 ≤ k の場合、x はフルであるとみなします。 
4. 完全なラッキー ナンバーの数を最大化するには、セグメントをわずかに移動することで連続するラッキー ナンバーが一緒にカバーされる可能性があることに注意してください。 2 ポインタ手法を実装します。最初のラッキー ナンバーから開始し、合計移動数が k 以下のままで右ポインタを拡大し、ウィンドウの長さ (対象となるラッキー ナンバーの数) を追跡します。 左ポインタを移動して他のウィンドウを探索します。 見つかった最大長を維持します。 
5. 有効なウィンドウ内に含まれるラッキーナンバーの最大数を答えとして返します。 

機能する理由: 不変条件は、スライディング ウィンドウの各ステップで、計算された合計手数が、ウィンドウ内のすべてのラッキー ナンバーを含めるための最小手数を反映することです。 ラッキー ナンバーはまばらであり、連続するラッキー ナンバーのシーケンスは数直線上の連続したサブセットであるため、2 ポインタ アプローチにより、k 手以内でカバーできる最大の連続したラッキー ナンバーのセットが見つかることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def generate_lucky(limit):
    lucky = []

    def dfs(num):
        if num > limit:
            return
        if num > 0:
            lucky.append(num)
        dfs(num * 10 + 4)
        dfs(num * 10 + 7)

    dfs(0)
    lucky.sort()
    return lucky

def main():
    n, k = map(int, input().split())
    segments = [tuple(map(int, input().split())) for _ in range(n)]
    limit = 10**18
    lucky = generate_lucky(limit)

    max_full = 0
    left = 0
    total_moves = 0
    move_costs = [0]*n

    for right in range(len(lucky)):
        x = lucky[right]
        # compute moves to cover lucky[right]
        move_costs = [max(0, s[0]-x) if x < s[0] else max(0, x-s[1]) for s in segments]
        total_moves = sum(move_costs)

        while total_moves > k:
            left += 1
            if left > right:
                break
            x_left = lucky[left-1]
            # recalc moves for the reduced window
            move_costs = [max(0, s[0]-lucky[left]) if lucky[left] < s[0] else max(0, lucky[left]-s[1]) for s in segments]
            total_moves = sum(move_costs)

        if total_moves <= k:
            max_full = max(max_full, right-left+1)

    print(max_full)

if __name__ == "__main__":
    main()
```の`generate_lucky`関数はすべての幸運な数字を再帰的に生成します。 各セグメントの移動コストは、候補のラッキーナンバーに基づいて計算されます。 2 ポインター ウィンドウにより、ラッキー ナンバーのすべての最大シーケンスを効率的に探索できます。 このソリューションでは、不可能な範囲での反復処理を回避し、現実的に満たされる可能性のある数値のみを考慮します。 

## 実用的な例

 **サンプル 1:**

 | セグメント | 初期範囲 | 表紙 4 に移動 | 引越し費用 |
 | --- | --- | --- | --- |
 | [1,4] | 1-4 | すでに 4 をカバーしています | 0 |
 | [6,9] | 6-9 | 2 だけ左にシフト | 2 |
 | [4,7] | 4-7 | すでに 4 をカバーしています | 0 |
 | [3,5] | 3-5 | すでに 4 をカバーしています | 0 |

 合計手数 = 2 ≤ 7。幸運な数字 4 だけがいっぱいです。 最大フル = 1。 

**サンプル 2:**

 セグメント [42,44]、[41,47]、k=5。 ラッキーナンバー 44、47 は、k 個以下の手で完全にカバーできることがわかります。 スライディング ウィンドウは両方をキャプチャします (最大フル = 2)。 

これは、2 ポインター アプローチが最大の幸運の数を効率的にカウントする方法を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(L * n) | L = ラッキーナンバーの数 ≤ 10^18 (~200 万)。 それぞれについて、n 個のセグメントすべての移動コストを計算します。 |
 | スペース | O(L + n) | すべてのラッキーナンバーと n セグメントを保存します。 |

 n ≤ 10^5 および L ~ 2e6 の場合、最悪の場合の演算は ~2e11 になります。 最適化 (ウィンドウが変更されたときのみセグメントを移動したり、プレフィックス合計を計算したりするなど) により、実際の実行時間が短縮されます。
