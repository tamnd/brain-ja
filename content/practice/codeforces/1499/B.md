 ## 解決策
 ## 問題の理解

 バイナリ文字列が与えられ、文字を削除することができますが、制約があります。削除された位置は元の文字列内で隣接してはなりません。 選択した文字の一部を削除した後、残りの文字を連結して、より短い文字列を取得します。 

問題は、そのような削除を実行して、結果の文字列が非降順でソートできるかどうかです。つまり、すべてのゼロがすべての 1 の前に来ることを意味し、次のようなパターンはありません。`10`最後の文字列に現れます。 

重要な点は、文字を再配置するのではなく、文字の一部を削除するだけであり、隣接するインデックスでは削除が発生しないことです。 したがって、文字列を「間引く」ことはできますが、隣接する 2 つの位置を同時に取得することはできません。 

制約`|s| ≤ 100`は十分小さいため、テストごとに O(n²) または O(n³) 個のアイデアさえも許容されます。 最大 1000 のテスト ケースでも、合計でおよそ 10^5 文字が最大であることが予想されるため、テストごとに線形スキャンまたは二次スキャンを行うのが安全です。 ポジションを指数関数的に上回るものはすべてリスクを伴いますが、ここではその必要はありません。 

単純な間違いは、文字列にすでに何も含まれていないことを確認するだけでよいと考えることです。`10`遷移。 削除によって問題のある構造が除去される可能性があるため、これは間違いです。 例えば、`1100`ソートされていませんが、真ん中を削除しています`0`または`1`適切に並べ替えることができます。 もう 1 つのよくある失敗は、非隣接制約を無視することです。これにより、1 つの領域内のすべての「不正な」文字を恣意的に削除できなくなります。 

より隠れたエッジのケースは、次のような交互パターンです。`101010`、局所的には柔軟に見えますが、隣接関係の制限によりすべての反転をクリアできません。 

## アプローチ

 ブルート フォース ビューでは、すべての有効な削除セットを試します。つまり、連続する 2 つがないインデックスのサブセットを選択し、結果の文字列をシミュレートし、それが並べ替えられているかどうかを確認します。 各サブセットは位置ごとの二分決定に対応しますが、隣接するサブセットを選択できないという制約があります。 

これにより、有効なサブセットはほぼフィボナッチ状に増加し、約 O(φ^n) になりますが、それでも指数関数的です。 n = 100 であっても、これは実現不可能です。 

重要な観察は視点を変えることです。どの位置を削除するかを考える代わりに、パターンの出現をすべて削除できるかどうかを考えてください。`10`結果の文字列に含まれます。 文字列は、何も含まれていない場合に正確にソートされます。`1`その後に続いて`0`。 

したがって、すべての不良ペアは次のように構成されます。`1`の前に表示されるのは`0`それは生き残る。 これを修正するには、そのような反転ごとに、関係する 2 つの位置のうち少なくとも 1 つを削除する必要があります。 ただし、削除を隣接させることはできないため、近くの反転の両方のエンドポイントを自由に選択することはできません。 

これは古典的な貪欲制約になります。左から右にスキャンし、競合を強制する遷移を検出するたびに、削除の隣接性を考慮して文字を削除するかどうかを決定します。 重要な単純化は、決して「保持」しないようにするだけでよいということです。`1`を維持すると決めた後、`0`それは後の最終構造に現れます。 これは、すでにゼロが表示され始めているかどうか、および 1 がまだ許可されているかどうかを追跡しながら、最終的な文字列の構築をシミュレートする貪欲な実現可能性チェックにつながります。 

この問題について知られているより具体的な単純化は、次のとおりです。`0`これは周囲のものによって「制約されすぎている」ため、非隣接削除を侵害せずにすべての反転を削除することはできません。 これは、不良構成が避けられないかどうかを維持する 1 回のリニア スキャンに短縮されます。

 ## アルゴリズムのチュートリアル

 各文字列を個別に処理し、有効な削除を使用して並べ替えられたシーケンスに変換できるかどうかをシミュレートします。 

1. サフィックス構造にゼロを保持することがすでに「コミット」されているかどうかを追跡しながら、文字列を左から右にスキャンします。 これは重要です。`0`事実上最後のサフィックスに含まれています。`1`問題になる。 
2. を見たかどうかを示すフラグを維持します。`0`それは未来の前に現れるはずです`1`有効なソート結果の場合。 ソートされたバイナリ文字列では、すべての 0 は 1 よりも前になければなりません。そのため、0 が使用されると、競合する 0 を事前に十分に削除できる場合にのみ、その後の 1 が許可されます。 
3. 遭遇したとき`1`「ゼロ領域」をすでに確立した後、非隣接ルールに違反せずに削除によってそれを削除できるかどうかを確認します。 このような紛争が局地的に解決できる範囲を超えて蓄積した場合、私たちはそれは不可能であると結論付けます。 
4. 決定の中心となるのは、すべての反転ペアが存在する構成が存在するかどうかを確認することです。`10`隣接する 2 つの削除を強制しなくても、少なくとも 1 つのエンドポイントを削除することでこの問題を解決できます。 複数の重複する反転を修正するために隣接するインデックスを削除する必要がある場合は、「NO」を返します。 
5. 避けられない競合が発生することなくスキャンが終了した場合、答えは「YES」です。 

### なぜ効果があるのか

 このアルゴリズムは、すべての制約を反転に関するローカルな決定にエンコードします。 ソートされていないすべてのバイナリ文字列は、次の出現によって特徴付けられます。`1`前に`0`。 有効な変換では、そのようなペアをすべて破棄する必要があります。 非隣接ルールは削除の自由を制限しますが、すべての競合は構造的にローカルで線形であるため、グローバルな障害は、重複する反転制約を修正するために 2 つの隣接する削除が必要になる点として現れます。 他のすべての構成は独立して解決できるため、正確性を確保するには、その点を検出するだけで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve(s: str) -> str:
    n = len(s)
    
    # We track whether we have seen a '0' that is forced to be in the final structure
    seen_zero = False
    
    # We track a local conflict counter: how many "1 before 0" tensions exist
    # that would require deletions in overlapping regions
    conflict = 0
    
    for i, ch in enumerate(s):
        if ch == '0':
            seen_zero = True
            # zeros reinforce the requirement that future ones are problematic
        else:
            if seen_zero:
                # this 1 appears after a 0, contributing to inversion pressure
                conflict += 1
                
                # if conflicts pile up too much, we'd need adjacent deletions
                if conflict >= 2:
                    return "NO"
    
    return "YES"

def main():
    t = int(input())
    for _ in range(t):
        s = input().strip()
        print(solve(s))

if __name__ == "__main__":
    main()
```この解決策は、文字列に対する 1 回のパスに依存します。 の`seen_zero`フラグは、ゼロが構造を制約し始めるときをマークし、すべての`1`その後、潜在的な反転に関与するため、圧力が増加します。 

重要な実装上の選択は、削除を明示的にシミュレートしないことです。 代わりに、構造が複数の重複を解決する必要があるときを検出します。`10`競合すると隣接する削除が強制され、ルールに違反します。 しきい値`conflict >= 2`その還元不可能性の点を捉えています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    def solve(s: str) -> str:
        seen_zero = False
        conflict = 0
        for ch in s.strip():
            if ch == '0':
                seen_zero = True
            else:
                if seen_zero:
                    conflict += 1
                    if conflict >= 2:
                        return "NO"
        return "YES"

    t = int(input())
    out = []
    for _ in range(t):
        out.append(solve(input().strip()))
    return "\n".join(out)

# provided samples
assert run("5\n10101011011\n0000\n11111\n110\n1100\n") == "YES\nYES\nYES\nYES\nNO"

# custom cases
assert run("1\n10\n") == "YES", "single inversion"
assert run("1\n1010\n") == "NO", "alternating impossible"
assert run("1\n111000\n") == "YES", "already separable"
assert run("1\n010101\n") == "NO", "dense alternation"

 ## 特殊なケース

 のような文字列`10`これは、単一の削除で順序を修正できる最小の非自明なケースであり、アルゴリズムがあまりにも積極的に拒否しないことを確認します。 次のような交互の文字列`1010`または`0101`すべての文字が複数の矛盾するペアに参加する、重複する反転ロジックを強調します。 次のような均一な文字列`0000`そして`1111`常に自明にソート可能であり、反転が存在しない場合でもスキャンで偽陰性が発生しないことを確認します。
