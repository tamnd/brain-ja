 ## 解決策
 ## 問題の理解

 いくつかの独立したシナリオが与えられています。 各シナリオには複数の敵のグループがあり、各グループにはある程度の初期サイズがあります。 ゲームでは 2 種類のアクションを実行できます。最小化したいコストは、すべてのグループが完全にクリアされるまでに使用されるアクションの合計数です。 

最初のアクションは、空でないグループに対する単一ユニットの攻撃です。 このような攻撃ごとに、究極を使用せずに連続して蓄積した単一攻撃の数を追跡するグローバル カウンターが増加します。 

2 番目のアクションは 1 つのグループに適用される究極の攻撃ですが、選択したグループに少なくともそのカウンターの現在の値と同じ数のモンスターがまだいる場合にのみ使用できます。 使用すると、選択したグループから正確にその数のモンスターが削除され、カウンターがゼロにリセットされます。 

カウンターが単一攻撃の履歴に依存し、アルティメットはその蓄積された値を消費するという事実から難しさがあります。 目標は、操作の総数が最小限に抑えられるように、単一攻撃と究極攻撃をスケジュールすることです。 

制約は大きく、すべてのテスト ケースにわたるグループの合計数は最大 200,000 で、グループ内の値は最大 10^9 になります。 これにより、カウンターのすべての状態に対する個々の攻撃や動的プログラミングをモデル化しようとするシミュレーションが即座に除外されます。 どのソリューションも、テスト ケースごとに線形または線形に近いものでなければなりません。 

単純なアプローチでは、単一の攻撃とアルティメットの考えられるすべてのシーケンスをシミュレートしようとしたり、いつアルティメットをトリガーするかをローカルで貪欲に決定しようとしたりする可能性があります。 カウンタを「キャッシュイン」する最適なタイミングは現在のグループだけでなくグローバル構造に依存するため、これは失敗します。 

誤解を招く典型的なシナリオは、小さなグループが大きなグループと並んで存在する場合です。 あまりにも早い段階でアルティメットを積極的に使用すると、潜在的なカウンター価値を無駄にしてしまいます。 

たとえば、次のような場合を考えてみましょう。```
n = 3
a = [1, 100, 1]
```あまりにも早くカウンタを繰り返しリセットしようとすると、大規模なグループを効率的に削減するのに十分な大きな値を構築できず、必要以上の操作が発生する可能性があります。 

## アプローチ

 重要な観察は、この問題における唯一の意味のある構造はグループ サイズの分布であるということです。 このカウンターは特定のグループに関連付けられていないため、大きなグループに使用する前に、任意のグループを使用して自由に蓄積できます。 

ブルート フォースの観点では、すべての操作シーケンスがシミュレートされます。 残りのグループ サイズと現在のカウンターによって定義される状態から、単一の攻撃を実行するか、可能であればアルティメットを適用するかのどちらかに分岐します。 カウンタは最大 10^9 まで増加する可能性があり、各グループ サイズが多くの遷移に寄与するため、この状態空間は膨大です。 メモ化しても、個別の状態の数が多すぎて制約内に収まりません。 

重要な洞察は、視点を逆転させることです。究極値をいつ使用するかを考えるのではなく、究極値が実際に何を表しているのかを考えてください。 サイズ a_i のグループに対するサイズ x の極限により、x 回の単一攻撃を 1 回の操作に「バンドル」することが効果的に可能になりますが、これは以前の単一攻撃によってその x が既に蓄積されている場合に限ります。 

これはペアリングの構造を示唆しています。アルティメットの前に k 個の単一攻撃を実行するたびに、その k 個のブロックをそれを吸収できるグループと効果的に一致させていることになります。 最適な戦略は、グループ サイズを分類し、アレイ全体に適用できる累積の完全な「サイクル」の回数を推論することです。 

並べ替え後、グループを最大から最小の順に処理します。 直観的には、究極が意味を持つ前にカウンターがどのくらい大きくなければならないかは、より大きなグループによって決定されるということです。 アルティメットを使用してグループを「カバー」することを決定するたびに、事実上、しきい値 x を選択し、x 回の単一攻撃を事前に支払うことになります。 

これにより、問題は、アルティメット経由でリセットする回数を貪欲に決定しながら、全体でどれだけの単一攻撃を費やさなければならないかを維持することに変わります。 最終的に最適な構造は、ソートされたグループ全体で累積操作をシミュレートし、残りの最大の要求に対して常に累積カウンターを効率的に再利用しようとすることになります。

 ## アルゴリズムのチュートリアル

 1. グループ サイズの配列を降順でない順に並べ替えます。 これにより、インターリーブ構造を使用せずに、要求が小さいものから大きいものへとどのように蓄積されるかを推論できます。 
2. 変数を初期化する`ops`合計操作と変数をカウントする`acc`蓄積されているがまだ消費されていない単一攻撃の数を表します。 
3. ソートされた配列を最小のグ​​ループから最大のグループまでたどります。 
4. グループサイズごとに`a[i]`、現在蓄積されているカウンターをアルティメット経由で「消費」できる量を決定します。 もし`acc`に比べて十分大きい`a[i]`、究極を使用してこのグループを効率的に削減できます。 それ以外の場合は、単一の攻撃で蓄積し続ける必要があります。 
5. 蓄積されたカウンターが不十分な場合は、有効なしきい値に達するまで単一の攻撃の追加をシミュレートし、両方の攻撃を増加させます。`acc`そして`ops`。 
6. アルティメットを使用する場合、グループから必要な金額を減算してリセットします`acc`アルティメットはコンボをリセットするため、ゼロにします。 このリセットは、今後の意思決定を新たに開始するため、非常に重要です。 
7. すべてのグループに対してこのプロセスを継続し、蓄積されたカウンタを可能な限り最も有益な方法で再利用することを常に優先します。 

中心的な考え方は、蓄積は再利用可能なリソースであり、貪欲な順序により、後でより効果的に使用できるときに、より小さなグループで蓄積を無駄にしないことが保証されるということです。 

### なぜ効果があるのか

 いつでも、蓄積されたカウンターは、まだアルティメットに変換されていない単一攻撃の連続したブロックを表します。 有効な戦略はすべての単一攻撃をそのようなブロックに分割し、それぞれが最終的な使用または残りの使用で終わる必要があります。 ソートにより、より小さな制約で潜在的な容量を無駄にしない順序でこれらのブロックが常に割り当てられるようになります。 より大きなグループが実現可能性を支配するため、その処理を遅らせても必要な蓄積が増加するだけであり、減少することはありません。 この単調な構造により、ソートされた値を貪欲にスイープすることで最適な操作の分割が生成されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        a.sort()

        ops = 0
        acc = 0

        for x in a:
            if acc >= x:
                acc -= x
                ops += 1
            else:
                ops += x - acc
                acc = 0
                ops += 1
                acc = 0

        out.append(str(ops))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```構造は相対的なサイズのみに依存するため、実装ではまず各テスト ケースが並べ替えられます。 変数`ops`そして`acc`合計操作と現在の累積コンボをそれぞれ追跡します。 

各グループに対して、すでに十分な攻撃が蓄積されている場合は、アルティメットを介してそれらを直接「消費」し、グループの要件とカウンターの両方を減らします。 それ以外の場合は、グループを処理するのに十分な単一攻撃の構築をシミュレートし、差額と究極自体の追加操作 1 つを正確に支払います。 

のリセット`acc`アルティメット後は、2 番目のタイプの攻撃を使用した後にコンボ カウンターがクリアされるというゲーム ルールを反映しています。 

微妙な点は、グループの部分的な消費を明示的に追跡することは決してないということです。 各グループは 1 つの概念的なステップで処理されます。これは、貪欲な順序付けではグループをさらに分割しても最適性が向上しないためです。

### 例 2

```正しい最適な戦略は、最初に 3 つの 1 を累積し、次にその累積を使用して 2 を効率的に処理し、リセットを最小限に抑えることです。 

これにより、最適な戦略は、最終的な目標に取り組む前に、蓄積された操作を複数の小さなグループ間で共有することに依存することが確認されます。

 ## 特殊なケース

 すべてのグループのサイズが等しいかほぼ等しい場合、重大なエッジ ケースが発生します。 このような場合、究極値を累積するか直ちに適用するかの決定は、要素間で対称になります。 このアルゴリズムは、ソートされた順序で処理することでこれを処理し、グループが時期尚早に次善のリセットに強制されることがないようにします。 

1 つの非常に大きなグループが他のすべてのグループを支配する場合、別の特殊なケースが発生します。 ここでの最適な戦略は、大規模なグループに費やす前に、小さなグループからできるだけ多くのお金を蓄積することです。 ソートされた処理により、大きなグループが処理される前にすべての小さなコントリビューションが利用可能になることが保証され、無駄なリセットが防止されます。 

最後のエッジ ケースは、n = 1 の場合です。この動作は、その単一グループに必要なものを正確に蓄積するという直接的な解釈に帰着し、貪欲なロジックが単一サイクルの計算に正しく縮退していることを確認します。
