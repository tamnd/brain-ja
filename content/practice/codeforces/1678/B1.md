 ## 解決策
 ## 問題の理解

 バイナリ文字列が与えられ、単位コストで個々の文字を反転することができます。 すべての変更を行った後、文字列は同一文字の最大の連続に圧縮されることによって解釈されます。 ランは同じビットの連続したブロックにすぎず、これらのランの長さに注目します。 

すべてのランレングスが偶数である場合、文字列は有効であるとみなされます。 これにより、非常に厳格な構造が強制されます。ランは奇数のサイズにすることはできず、ランは 0 と 1 の間で交互に現れるため、文字列全体を交互のブロックに分割し、各ブロックが偶数の長さになるようにする必要があります。 

タスクは、入力文字列をこの制約を満たす任意の文字列に変換するために必要なフリップの最小数を計算することです。 

すべてのテスト ケースの全長が最大 2×10^5 であるという制約は、テスト ケースごとに線形または線形に近い解が必要であることを意味します。 各位置の可能性を個別に再計算しようとしたり、変換を明示的に調べたりするアプローチは、テスト全体で O(n^2) さえも直ちに不可能であるため、遅すぎます。 

いくつかの危険な状況については、覚えておく価値があります。 

すでに偶数の長さのランで構成されている文字列はすでに有効であるため、答えは 0 です。 たとえば、「1100」は長さ 2 と 2 の 2 つのランになるため有効です。 

単一のロングランは、その長さが偶数の場合にのみ有効です。 「1111」は有効ですが、「111」は有効ではありません。これを修正するには、パリティを解除または調整するために少なくとも 1 文字を変更する必要があります。 

もう 1 つの微妙なケースは、実行が交互に行われるが、1 つの境界だけが「間違っている」場合です。 たとえば、「1110011000」は、最初と最後を除いて多くの実行が偶数であっても無効であり、ローカルな正確性がグローバルな妥当性を意味しないことを示しています。 

## アプローチ

 ブルートフォース手法では、長さ n の可能な最終バイナリ文字列をすべて考慮し、そのラン分解を計算し、すべてのラン長が均等であるかどうかを確認しようとします。 各候補文字列について、入力との差を計算してフリップをカウントします。 バイナリ文字列の数は 2^n であり、各文字列を評価するだけでも O(n) かかるため、これはまったく実行不可能です。 

重要な観察は、「すべてのランの長さが均等である」という条件は、ラン内の隣接する位置のすべてのペアが一致する必要があることを要求することと同等であり、構造化された方法で考える場合、ランの境界は偶数のインデックスでのみ発生する可能性があるということです。 任意の実行という観点から考える代わりに、ペア構造を強制することができます。つまり、位置 (1,2)、(3,4)、(5,6) などは一貫して動作する必要があります。 

より具体的には、文字列を 2 文字のブロックで処理できます。 すべてのランの長さを均等にしたい場合は、各有効な最終構成内で、位置 i と i+1 が同じランに属している必要があります。つまり、それらは等しくなければなりません。 これにより、問題はペアごとに「00」になるか「11」になるか決定することになります。 この解釈を修正すると、各ペアのコストは独立します。これは、有効な最終文字列は各ペアのターゲット値の選択によって完全に決定されるためです。 

したがって、問題は次のようになります。各ペア (s[2k]、s[2k+1]) について、選択したターゲットにすでに一致する場合は 0 を支払い、そうでない場合は、選択したペアの値に応じて不一致の文字ごとに 1 を支払います。 各ペアはすべて 0 になるかすべて 1 になるかを個別に選択するため、ペアごとに安価なオプションを選択します。 

これにより、グローバルな実行パリティ制約がローカルなペアごとの最適化に変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n · n) | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列を左から右に 2 つの位置ずつ処理します。

1. 文字列を連続するペア (s[i]、s[i+1]) に分割します。 n は偶数であることが保証されているため、これは有効です。 
2. 各ペアについて、「00」にするために何回フリップする必要があるか、「11」にするために何回フリップする必要があるかを計算します。 

最初のコストはペア内の 1 の数、2 番目はペア内の 0 の数です。 
3. これら 2 つのコストのうち小さい方を答えに加えます。 
4. すべてのペアに対して繰り返し、累積合計を出力します。 

各ステップは、有効な最終構成では、ペアの両方の文字が同一でなければならないという事実によって正当化されます。 そうでない場合、ランはペア内で分割され、すぐに長さ 1 のランが作成されますが、すべてのランは偶数でなければならないため、これは無効です。 

### なぜ効果があるのか

 重要な特性は、有効な最終文字列では、インデックス (2k−1, 2k) が同じランに属していなければならないということです。 それらが異なる実行にある場合、実行の 1 つがペア内の奇数長の境界で開始または終了し、分解のどこかで奇数の実行が強制されます。 

すべての有効な解はペアごとの値を選択することによって完全に決定されることを受け入れると、コストは独立した部分問題に分解されます。 各ペアはフリップの総数に独立して寄与し、1 つのペアを変更しても別のペアの実行の有効性に影響を与えないため、ペア間の依存関係によって結果が改善されることはありません。 

この独立性により、ペアごとに局所的に最適な選択肢が全体的に最適なソリューションに結合されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n = int(input().strip())
    s = input().strip()

    ans = 0

    for i in range(0, n, 2):
        a = s[i]
        b = s[i + 1]

        ones = (a == '1') + (b == '1')
        zeros = 2 - ones

        ans += min(ones, zeros)

    print(ans)
```このソリューションは、素のペアを反復処理することに依存しているため、追加のデータ構造や状態追跡は必要ありません。 唯一の微妙な点は、インデックスを正しくグループ化することです。1 つの位置をシフトするとペアリング ロジックが完全に無効になるためです。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各テスト ケースは、文字列を 2 回ずつスキャンします。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        s = input().strip()

        ans = 0
        for i in range(0, n, 2):
            a = s[i]
            b = s[i+1]
            ones = (a == '1') + (b == '1')
            ans += min(ones, 2 - ones)

        out.append(str(ans))

    return "\n".join(out)

 ## 特殊なケース

 「1100」のような均一なペアですでに構成されている文字列の場合、アルゴリズムは (11) と (00) を処理し、どちらもコストはゼロです。 これは、文字列がすでに偶数長のランに分解されているという事実と一致します。 

「101010」のような完全に交互の文字列の場合、すべてのペアが混合されるため、それぞれが 1 回の反転に寄与します。 アルゴリズムは 3 を生成します。これは、各ペアを独立してすべて 0 またはすべて 1 に変換することに対応します。 

「01」のような単一のペアの場合、唯一の有効な修正は 1 ビットを反転することであり、どちらの方向のコストも同じであることを反映して、アルゴリズムは min(1,1) = 1 を正しく選択します。 

これらのケースは、1 つのペアの修正が別のペアの実現可能性に影響を与えないため、ペアリングの仮定が境界を越えた相互作用を見逃さないことを確認します。
