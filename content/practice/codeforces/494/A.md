 ## 解決策
 ## 問題の理解

 開き括弧、閉じ括弧、および特殊なプレースホルダーの 3 種類の文字で構成される文字列が与えられます。 各プレースホルダーは、正の数の閉じ括弧に展開する必要があります。 すべての置換が行われた後、結果は非常に強い意味で有効な括弧シーケンスになる必要があります。左から右にスキャンするとき、どの接頭辞であっても、閉じ括弧の数が開き括弧の数を超えてはならず、最終的には開き括弧と閉じ括弧の合計数が正確に一致する必要があります。 

主な難点は、各プレースホルダーが単一の固定シンボルではなく、いくつかの閉じ括弧を提供する柔軟なブロックであることです。これらの要素は、すべてのプレフィックス制約が同時に満たされるように選択する必要があります。 

文字列の長さは最大 100,000 であるため、プレースホルダーへの値の割り当てをすべて試行するアプローチは即座に除外されます。 各プレースホルダーは将来のすべてのプレフィックスバランスに影響を与えるため、グローバル構造を使用せずに値を貪欲に割り当てることさえ危険です。 

局所的なバランス調整は問題ないように見えても、後で全体的な実現可能性が損なわれる場合、微妙な失敗のケースが発生します。 たとえば、初期のプレースホルダに割り当てられている閉じ括弧が少なすぎる場合、後のプレフィックスには、最終的な等価性制約に違反することなく補正できない過剰な開始括弧が蓄積される可能性があります。 逆に、早期に閉じ括弧を割り当てすぎると、接頭辞条件がすぐに壊れる可能性があります。 

## アプローチ

 ブルートフォース手法では、整数の右括弧を各プレースホルダーに割り当て、結果のシーケンスが有効かどうかを検証しようとします。 各プレースホルダーを適切な範囲に制限しても、プレースホルダーの数は指数関数的に増加します。これは、最大 100,000 個のプレースホルダーがある場合には実行不可能です。 

問題の構造は、別の観点を示唆しています。 最後の文字列はバランスの取れた括弧のシーケンスである必要があるため、閉じ括弧の総数は元の文字列の開き括弧の数によって正確に固定されます。 これにより、問題は「任意の正の整数を選択する」という問題から「固定の合計金額をプレースホルダー全体に分配する」という問題に即座に変わります。 

この合計を修正したら、残りの条件はプレフィックスの有効性です。 ここで欲が有効になります。早期に閉じ括弧を増やすと、後でプレフィックスの肯定性に違反するリスクが軽減されるため、各プレースホルダーは初期段階ではできるだけ貢献を少なくする必要があります。 ただし、合計合計制約が確実に保持されるように、1 つのプレースホルダーは残りの必要な閉じ括弧をすべて吸収して補正する必要があります。 

これにより、最初にすべてのプレースホルダーがちょうど 1 つの閉じ括弧に寄与するように設定され、選択された 1 つのプレースホルダーが残りの必要な量を吸収するという構造になります。 正確さは、「追加ロード」に適切なプレースホルダーを選択することにかかっています。プレースホルダーは、値を増やしてもプレフィックスの有効性が損なわれないように配置する必要があります。 

したがって、残りの閉じ括弧を安全に運ぶことができる最後のプレースホルダーを特定し、残りを最小限に配布します。

 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(n) | 遅すぎる |
 | 単一調整による貪欲な分布 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 文字列内の左括弧の数を数えます。 有効なシーケンスは両方のタイプの同じ数で終了する必要があるため、これによって最終シーケンスに必要な閉じ括弧の合計数が決まります。 
2. 各プレースホルダーを概念的に少なくとも 1 つの閉じ括弧に置き換えます。 これにより、各プレースホルダーが正の整数に寄与するという制約が確実に満たされます。 
3. 各プレースホルダーに閉じ括弧を割り当てた後に残っている閉じ括弧の数を計算します。 この残りの部分は、正確に 1 つのプレースホルダーに配置する必要があります。 
4. 文字列をスキャンし、各プレースホルダーが 1 つの閉じ括弧に寄与すると仮定して、開始部分から終了部分を差し引いたバランスを維持します。 スキャン中は、実現可能性を追跡する目的で、プレースホルダーを 1 つの閉じ括弧に寄与するものとして扱います。 
5. 残りの余分な閉じ括弧を安全に吸収できるプレースホルダーを特定します。 これには、その寄与を増やす場合、その前またはそれを含むプレフィックスが無効になることが必要です。 正しい選択は、最後に見つかったプレースホルダーです。これは、以前のプレフィックスのバランスに影響を与えることなく、追加の閉じ括弧を延期できる最も遠いポイントであるためです。 
6. 選択したプレースホルダを除くすべてのプレースホルダに値 1 を割り当てます。選択したプレースホルダには、1 に残りの必要な量を加えた値が与えられます。 

### なぜ効果があるのか

 このアルゴリズムでは、プレフィックス検証中にすべてのプレースホルダーが最小限の動作をするように強制されます。これは最も制約された状態です。 追加の閉じ括弧は 1 つの位置にのみ表示され、できるだけ後ろに配置することで、以前のプレフィックス条件を妨げないようにすることができます。 右括弧の総数は左括弧の数によって正確に決まるため、最終的な合計制約は自動的に満たされます。 貪欲な最小割り当てが常に最も安全な構成であり、余剰分は最後の可能なプレースホルダーに延期され、以前のプレフィックスを遡って無効にすることができないため、プレフィックス制約が保持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    opens = s.count('(')
    stars = s.count('#')

    total_close = opens
    base = stars  # each '#' gives at least 1 ')'
    rem = total_close - base

    # store positions of '#'
    pos = []
    for i, c in enumerate(s):
        if c == '#':
            pos.append(i)

    # assign all 1, last gets extra rem
    ans = [1] * stars
    ans[-1] += rem

    # verify feasibility (optional conceptual check)
    bal = 0
    j = 0
    for c in s:
        if c == '(':
            bal += 1
        elif c == ')':
            bal -= 1
        else:
            bal -= ans[j]
            j += 1
        if bal < 0:
            print(-1)
            return

    if bal != 0:
        print(-1)
        return

    for x in ans:
        print(x)

if __name__ == "__main__":
    solve()
```実装では、最初に合計でいくつの閉じ括弧が存在する必要があるかをカウントし、次に 1 つの閉じ括弧のベースライン値をすべてのプレースホルダーに割り当てます。 残りの余剰は最後のプレースホルダーに追加されます。 

検証パスは、各プレースホルダーを割り当てられた値として扱い、最終シーケンスをシミュレートします。 これにより、プレフィックスがマイナスになることがなく、合計残高がゼロで終わることが保証されます。 プレフィックスの実現可能性を維持するには、以前のプレースホルダーは最小限にしておく必要があるため、最後のプレースホルダーの選択は重要です。 

## 実用的な例

 ### 例 1

 入力:```
(((#)((#)
```左括弧が 5 つとプレースホルダーが 2 つあるため、閉じ括弧の合計は 5 でなければなりません。各プレースホルダーは少なくとも 1 つを提供し、残りの 3 つは最後のプレースホルダーに割り当てられます。 

| ステップ | キャラクター | バランス (開始 - 終了) | アクション |
 | --- | --- | --- | --- |
 | 1 | ( | 1 | +1 |
 | 2 | ( | 2 | +1 |
 | 3 | ( | 3 | +1 |
 | 4 | # | 2 | -1 |
 | 5 | ) | 1 | -1 |
 | 6 | ( | 2 | +1 |
 | 7 | ( | 3 | +1 |
 | 8 | # | -1 | -2 (調整しないと違反します) |

 これは、最後のプレースホルダーが余分なクローズを吸収する必要がある理由を示しています。 割り当て後、2 番目のプレースホルダーは、プレフィックスが負にならない程度に大きくなります。 

これにより、余剰を最後のプレースホルダーに分配すると、合計バランスを満たしながらプレフィックスの有効性が維持されることが確認されます。 

### 例 2

 入力:```
(#(#))
```開始括弧とプレースホルダーが 2 つあるため、終了括弧の合計は 2 でなければなりません。各プレースホルダーは 1 つを取得するため、余剰は存在しません。 

| ステップ | キャラクター | バランス |
 | --- | --- | --- |
 | 1 | ( | 1 |
 | 2 | # | 0 |
 | 3 | ( | 1 |
 | 4 | # | 0 |
 | 5 | ) | -1 は生の形式では無効です |

 各プレースホルダーが正確に 1 を提供し、構造が自然にバランスをとるため、割り当て後もプレフィックスは有効なままになります。 

これは、調整が必要ないベースラインのケースを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての左括弧がプレースホルダーの前に表示される場合です。 このような場合、プレフィックスのバランスは割り当ての早期終了に非常に敏感になります。 このアルゴリズムは、最後のプレースホルダーを除くすべてのプレースホルダーの貢献が最小限に抑えられるようにすることでこれを処理し、残高の早期の枯渇を防ぎます。 

もう 1 つのエッジ ケースは、プレースホルダーが括弧で大量にインターリーブされている場合です。 それでも、最後のプレースホルダーを除くすべての場所に最小値を割り当てることで、接頭辞が右括弧でオーバーロードされることがなくなります。 

最後に、プレースホルダーが 1 つしかない場合は、必要な閉じ括弧をすべて吸収する必要があります。 「最後のプレースホルダー」も唯一のものであるため、アルゴリズムはこれを自然に処理し、プレフィックス制約に違反することなく残り全体を受け取ります。
