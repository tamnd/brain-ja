 ## 解決策
 ## 問題の理解

 長さ 8 の固定方程式形式が与えられ、常に 2 つの 2 桁の数値を加算して別の 2 桁の数値と等価として記述されます。 構造はいつも`??+??=??`、ここでそれぞれ`?`は数字です。 プラス記号と等号は同じ位置に固定されており、その他の位置はすべて数字です。 先頭のゼロは許可されるため、2 文字のブロックはそれぞれ 00 から 99 までの数値を表します。 

推測方程式`E`が送信され、システムはフィードバック文字列を返しました。`C`3色を同じ長さで使います。 各位置は、対応する文字がどのように配置されるかを説明します。`E`隠れた正しい方程式と一致します。 緑色は、文字が正しく、正しい位置にあることを意味します。 紫は、そのキャラクターが非表示の方程式のどこかに存在するが、その位置には存在しないことを意味します。 黒は、その文字が非表示の方程式に現れないか、または推測よりも出現回数が少ないため、余分な出現はクレジットされないことを意味します。 

タスクは、与えられた推測と比較したときに、まさにこのフィードバックを生成する可能性のあるすべての有効な方程式を再構築することです。`E`。 

重要な点は、有効な回答候補は任意ではないということです。 2 つの独立した条件を満たさなければなりません。 まず、構文的に有効な次の形式の方程式である必要があります。`??+??=??`。 第 2 に、これは算術的に正しくなければなりません。つまり、先頭のゼロを許可する整数として解釈される場合、左側の合計が右側と等しくなる必要があります。 

制約の構造は小さいですが、組み合わせは大きくなります。 3 つの数値ブロックのそれぞれの範囲は 00 から 99 までであるため、算術的正確さによってフィルタリングする前に、考えられる方程式は最大 100 万通りになります。 これは直接総当たり攻撃を実行できるほど小さいですが、候補者ごとのフィードバック チェックが効率的である場合に限ります。 

単純な誤解は、重複を正しく処理せずにフィードバックをキャラクターごとに独立したものとして扱うことから生じることがよくあります。 たとえば、推測に繰り返しの数字が含まれている場合、その数字に一致する紫色の数は、その数字が隠された答えに何回出現したかによって異なります。 単にメンバーシップをチェックするだけの不注意な実装では、一致が過剰にカウントされ、不正確なフィルタリングが生成されます。 

もう 1 つの微妙なケースは、回答候補で数字が繰り返される場合です。 次のような推測を考えてみましょう`11+11=22`。 本当の答えが一つしかないとしたら`1`、それらの位置のうち 1 つだけが緑または紫でなければならず、他の位置は黒でなければなりません。 この多重度の上限は不可欠であり、シミュレーションでは強制する必要があります。 

## アプローチ

 直接的な総当たりの解決策では、考えられるすべての方程式が考慮されます。`a + b = c`、ここでそれぞれ`a`、`b`、 そして`c`範囲は 00 から 99 です。トリプルごとに、それを文字列表現にフォーマットし、算術的正しさを検証します。 これにより生成される候補者は最大で 1000,000 人ですが、条件を満たすのはそのうちのほんの一部だけです`a + b == c`。 

有効な候補者ごとに、与えられた推測に対してナードル フィードバックをシミュレートします。`E`。 このシミュレーションでは、Wordle のようなカウントによるマッチングを再現する必要があります。 まず、文字の位置が正確に一致するすべての緑色の一致を割り当てます。 次に、候補内の未使用の文字の頻度を数え、それらを残りの推測文字と照合することで残りの文字を処理し、可用性に応じて紫または黒を生成します。 

この強引なアプローチは、検索スペースが小さいため機能します。 ただし、主なコストはフィードバック シミュレーションです。 慎重に実装した場合、各比較は O(8) であるため、合計の複雑さは約 800 万回の操作となり、これは十分に高速です。 

重要な点は、これ以上賢い剪定は必要ないということです。 この問題は、算術的に有効な方程式をすべて網羅的に列挙するだけで十分であるように設計されています。

 ## アルゴリズムのチュートリアル

 3 つの数値ブロックのすべての可能な値を反復し、算術的妥当性によってフィルターし、フィードバック文字列との一貫性をチェックします。 

1. 反復する`a`0から99まで、`b`0から99まで、計算します`c = a + b`。 もし`c > 99`、2桁に収まらないので飛ばしてください。 これにより、有効な方程式構造のみが生成されることが保証されます。 
2.変換`a`、`b`、 そして`c`先頭にゼロを付けた 2 文字の文字列に変換します。 完全な方程式文字列を構築する`S = format(a) + "+" + format(b) + "=" + format(c)`。 
3. 比較する`S`与えられた推測に反して`E`フィードバックを計算します。 まず、すべての位置にマークを付けます。`S[i] == E[i]`緑色として表示され、それらの文字は今後の検討から除外されます。 完全一致が常に優先される必要があるため、この手順が必要です。 
4. 残りの不一致位置については、隠れた候補の文字頻度をカウントします。`S`。 次に、一致しない位置をスキャンします。`E`。 残りの周波数プールに文字が存在する場合は、紫を割り当て、カウントをデクリメントします。 それ以外の場合は黒を割り当てます。 
5. 構築されたフィードバックが指定された文字列と正確に一致する場合`C`、方程式を有効なものとして保存します。 
6. すべての候補を処理した後、カウントとすべての有効な方程式を出力します。 

設計上の選択の中心は、制約を記号的に「解決」しようとしないことです。 代わりに、実行可能なすべての方程式を直接テストし、小さなドメイン サイズに依存します。 

### なぜ効果があるのか

 すべての有効な隠れた答えは列挙された算術解の 1 つである必要があるため、アルゴリズムは正しいです。 フィードバック関数は、推測と隠された答えが与えられた場合に決定的であり、私たちのシミュレーションは多重度制約を含めてその関数を正確に再現します。 したがって、フィードバックに一致する候補は観察された結果と一致し、一貫した方程式は列挙中に発見されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def feedback(guess, target):
    n = 8
    res = [""] * n
    used_guess = [False] * n
    used_target = [False] * n

    for i in range(n):
        if guess[i] == target[i]:
            res[i] = 'G'
            used_guess[i] = True
            used_target[i] = True

    freq = {}
    for i in range(n):
        if not used_target[i]:
            freq[target[i]] = freq.get(target[i], 0) + 1

    for i in range(n):
        if res[i]:
            continue
        if freq.get(guess[i], 0) > 0:
            res[i] = 'P'
            freq[guess[i]] -= 1
        else:
            res[i] = 'B'

    return "".join(res)

def solve():
    E = input().strip()
    C = input().strip()

    ans = []

    for a in range(100):
        for b in range(100):
            c = a + b
            if c >= 100:
                continue

            s = f"{a:02d}+{b:02d}={c:02d}"
            if feedback(E, s) == C:
                ans.append(s)

    print(len(ans))
    for x in ans:
        print(x)

if __name__ == "__main__":
    solve()
```解決策は、算術的に有効なすべての方程式を直接列挙することを中心に構成されています。 の`feedback`関数は厳密な 2 パス マッチング戦略を実装します。 最初のパスでは緑色の位置がロックされ、周波​​数のマッチングが開始される前に正確な一致が考慮から除外されるようになります。 2 番目のパスでは、頻度辞書を使用して、問題に必要な多重度の制約を強制します。 

よくある落とし穴は、最初のパスをスキップして周波数マッチングを直接実行することです。これにより、繰り返される数字が特定の位置に揃うと正確さが失われます。 

## 実用的な例

 推測が次のような小さな例として考えてみましょう。`E = 11+45=56`そして答えの候補は`11+45=56`。 

| ステップ | 推測 vs 候補者 | グリーン | 残りの周波数 | フィードバック |
 | --- | --- | --- | --- | --- |
 | イニシャル | 11+45=56 vs 11+45=56 | すべて | なし | ぐぐぐぐぐ |

 これにより、完全な一致が確認され、すべての緑色のタイルが生成されます。 

次に、次のような不一致の候補を考えてみましょう。`11+46=57`。 

| ステップ | 推測 vs 候補者 | グリーン | 残りの周波数 | フィードバック |
 | --- | --- | --- | --- | --- |
 | イニシャル | 11+45=56 vs 11+46=57 | 部分的 (プレフィックス一致) | 残りの桁 | 混合 |

 ここでは、位置が一致する数字は緑色になり、その他の数字は頻度によって評価されます。 これは、位置の正確さとマルチセットの正確さがどのように相互作用するかを示しています。 

トレースは、フィードバックが純粋な位置ベースでも純粋なセットベースでもなく、両方のハイブリッドであることを示しています。そのため、2 パス シミュレーションが必要です。

 ## 特殊なケース

 微妙なケースの 1 つは、推測には繰り返しの数字が含まれているが、回答候補には含まれる数字が少ない場合です。 たとえば、推測が次のような場合`11+11=22`そして候補者は`12+10=22`、そのうちの 1 つだけ`1`と一致させることができます。 頻度ベースの 2 番目のパスでは、1 つの一致を割り当てた後、残りの一致が自動的に強制的に黒に設定されます。 

もう 1 つのエッジ ケースは、算術的正確性によってほとんどの候補が除外される場合です。 例えば、`99+99=198`は結果が 2 桁を超えるため無効であり、考慮されることさえありません。 これにより、誤ったラップアラウンド動作が防止されます。 

最後のエッジ ケースは、フィードバックに黒のタイルのみが含まれる場合です。 この場合、許容される多重度を超える推測と文字を共有しない候補方程式はすべて合格します。 すべての緑の一致が最初に削除され、共有数字の過剰クレジットを自然に防ぐ頻度カウントが残るため、シミュレーションはこれを引き続き正しく処理します。
