 ## 解決策
 ## 問題の理解

 私たちには、種類ごとにラベルが付けられた食品パッケージのコレクションが与えられます。 もあります$n$遠征の参加者であり、時間は日数で測定されます。 毎日、参加者全員が 1 つのパッケージを正確に消費します。 重要な制約は、参加者が異なれば異なる種類を選択する場合もありますが、参加者は遠征全体を通じて単一の種類の食品を使用しなければならないことです。 

したがって、参加者ごとに 1 つの食品の種類を効果的に割り当て、利用可能なパッケージのみを使用して毎日全員に食事を提供し続けることができる時間を確認する必要があります。 参加者が割り当てたタイプ$x$タイプのパッケージを 1 つ消費します$x$1 日あたりなので、割り当てると$k$参加者が入力する$x$、そして私たちは毎日を過ごします$k$タイプのパッケージ$x$。 したがって、日数は各タイプのパッケージの合計数によって制限されます。 

入力により参加者の数が得られます$n$、利用可能なパッケージの数$m$、およびパッケージの種類のリスト。 出力は、そのような割り当てを維持できる最大丸日数です。 

制約は小さく、$n, m \le 100$, そのため、多くの候補の答えを試したり、カウントを繰り返し再計算したりするソリューションでも、快適に合格します。 これは、ソリューションの構造が大量の計算の最適化ではなく、周波数に関する推論に重点を置いていることを示しています。 

総供給量が極端に偏っている場合、微妙なエッジケースが現れます。 たとえば、すべてのパッケージが 1 つのタイプであるが、参加者が多い場合、答えはそのタイプに割り当てられる人数によって制限されます。 もう 1 つの特殊なケースは、すべての型が出現する回数が非常に少ない場合です。 参加者が多い場合でも、制限要因は参加者の数ではなく、タイプ間で使用可能な貢献の合計になります。 

よくある間違いは、より多くの参加者をタイプに割り当てると毎日の消費量が直線的に増加することを考慮せず、各参加者が頻度に基づいて個別に日数に貢献していると考えることです。これにより、単純な貪欲な割り当ての実現可能性が完全に失われる可能性があります。 

## アプローチ

 日数を固定するという単純な考え$d$次に、各参加者に食品の種類を割り当てることができるかどうかを確認します。割り当てられたすべての種類に少なくとも$d$参加者ごとのパッケージ。 タイプが出たら$c$最大でもサポートできるのは$\lfloor c / d \rfloor$の参加者$d$日々。 したがって、実現可能性は、すべてのタイプの合計が一致するかどうかを確認することになります。$\lfloor c_i / d \rfloor$少なくとも$n$。 

できる限りのことをやってみたら$d$、答えはせいぜい$m$ので、それぞれを確認してください$d$まで$m$周波数スキャンを使用すると、次のような解決策が得られます。$O(m \cdot 100)$、これは制約の下では自明です。 これはすでに機能しています。 

ただし、重要な洞察は、すべてを繰り返す必要はないということです。$d$。 「サポート参加者数」機能$d$days」は単調減少します。$d$。 もし$d$が実現可能であれば、より小さな値もすべて実現可能です。 この単調性により、答えに対する二分探索が可能になります。 

したがって、すべてを試すのではなく、$d$、最大値を二分探索します。$d$、各候補について、頻度カウントを使用してサポートされる参加者の合計を計算します。 それぞれのチェックは、$O(100)$、検索は$O(\log 100)$。

 ## アルゴリズムのチュートリアル

 1. 食品の種類ごとにいくつのパッケージが存在するかを数えます。 周波数をタイプごとにインデックスを付けた配列に保存します。 
2. 関数を定義する`can(d)`それは私たちが維持できるかどうかをチェックします$d$日々。 種類ごとに頻度付き$c$、サポートできる参加者の数を計算します。$d$日、つまり$c // d$。 これらの値を合計します。 
3. サポートされる参加者の合計が少なくとも$n$、 それから$d$供給を超過することなく参加者をタイプに割り当てることができるため、日数は実現可能です。 
4. 二分探索$d$1から$m$、実現可能な最大値を追跡します。 
5. 実現可能な最大値を出力する$d$。 たとえさえあれば$d = 1$失敗すると、0 が出力されます。 

ステップ 3 が有効である主な理由は、各タイプがリソース プールのように機能し、参加者を割り当てると 1 日あたり 1 ユニットが消費されるためです。 参加者をタイプごとにグループ化すると、同一の消費パターンを最大限に再利用できるため、常にできるだけ多くの参加者を高頻度のタイプに詰め込むことが最善の戦略となります。 

### なぜ効果があるのか

 任意の固定日数で$d$、を備えたタイプ$c$パッケージでサポートできるのは最大でも$\lfloor c / d \rfloor$参加者。 各参加者が正確に消費するため、この制限は厳しいです$d$遠征中のユニット。 タイプを合計すると、有効な食品タイプを同時に割り当てることができる参加者の総数が得られます。 この合計が少なくとも$n$、キャパシティのカウントを超えるタイプ間の相互作用がないため、参加者を貪欲に割り当てることができます。 これにより、実行可能性が計算された条件と正確に一致することが保証され、二分探索決定関数が正しくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    
    freq = [0] * 101
    for x in a:
        freq[x] += 1
    
    def can(d):
        total = 0
        for c in freq:
            total += c // d
        return total >= n
    
    lo, hi = 1, m
    ans = 0
    
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1
    
    print(ans)

if __name__ == "__main__":
    solve()
```値が 100 で制限されているため、頻度配列は問題を一定サイズの状態に圧縮します。実現可能性チェックでは、整数の除算を使用して、各食品タイプが指定された日数に維持できる完全な参加者の割り当ての数を直接モデル化します。 次に、二分探索によって候補の答えが繰り返し絞り込まれます。 

よくある落とし穴は、実行中に周波数配列ではなく生のリストを反復処理することです。`can`これにより、各パッケージが誤って個別に扱われ、分割を意味のあるものにするグループ化ロジックが壊れてしまいます。

 ## 特殊なケース

 参加者が 1 人だけの場合、その参加者は最も豊富な食物を選択できるため、答えは単一の種類の最大頻度に減ります。 アルゴリズムはこれを処理します。$d > \max c_i$、すべての寄与がゼロになり、実行可能性は直ちに失敗し、正しい最大値が残ります。 

全体としてパッケージが 1 つしかなく、参加者が多い場合、すべてのパッケージが$d \ge 1$割り当ての合計がゼロになるため、すべての割り当てについて実現可能性が失敗します。$d$、二分探索では正しく 0 が返されます。 

すべてのパッケージが同一であれば、実現可能性は単純になります。$\lfloor m / d \rfloor \ge n$、これはまさに周波数分割で計算されるものです。 1 つの周波数だけがゼロではないため、アルゴリズムは特別なケースを使用せずにこれを自然に捕捉します。 

分布がまばらな場合、下限値の合計により過剰カウントが防止されます。 パッケージ合計が超過しても$n \cdot d$、不均等な分布により割り当てが不可能になる可能性はありますが、タイプごとの分割によってその制約が正しく適用されます。
