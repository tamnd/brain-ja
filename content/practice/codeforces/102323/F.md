 ## 解決策
 ## 問題の理解

 電子レンジでの推奨調理時間は、`MM:SS`形式とパーセンテージ`p`。 Chris は、推奨時間からの距離が最大以下である整数の秒数を選択できます。`p`推奨時間のパーセント。 このようなすべての候補時刻の中で、数字の並びが最も速い時刻を入力したいと考えています。 

電子レンジでは、有効な秒数を形成するために最後の 2 桁は必要ありません。 押したら`190`、電子レンジはそれを次のように解釈します。`1:90`、合計時間は 2 分 30 秒と同じです。 したがって、候補は合計秒数を 10 進数で表すのが最も適切です。 たとえば、88 は、`0:88`、1分28秒です。 

数字の入力には 1 秒かかります。 ある数字から別の数字に移動するにはさらに時間がかかりますが、同じ数字をもう一度押すには移動は必要ありません。 したがって、数字列の場合、`d1 d2 ... dk`、そのコストは`k + number of positions i where di != d(i+1)`。 

入力には以下が含まれます`n`食料品。 各項目の推奨時間は次のとおりです。`00`を通して`20`、その秒は次のいずれかです。`00`、`15`、`30`、 または`45`。 推奨される時間は少なくとも 15 秒です。`p`これらの制限により、検索スペースが非常に小さくなります。 最大の推奨値である 20 分でさえ、10 パーセントの範囲はわずか 240 整数秒であるため、すべての候補を直接チェックするのは簡単に十分な速度です。 元のコンテスト ステートメントは、これらの正確な境界を指定し、実際にパーセンテージ条件を満たす整数秒を使用してパーセンテージ間隔が解釈されることを指定します。 

単純な実装が間違っている可能性がある詳細がいくつかあります。 

たとえば、次のことを考えてみましょう。```
1
01:30
4
```推奨時間は 90 秒であるため、許容範囲は 87 ～ 93 秒です。 答えは`88`、 ない`01:28`。 シーケンス`88`電子レンジ自体がこれらの数字を 1 分 28 秒に変換するのに対し、所要時間はわずか 2 秒です。 

パーセンテージのエンドポイントも正しい方向に四捨五入する必要があります。 のために：```
1
00:15
10
```数学的な間隔は 13.5 ～ 16.5 秒です。 整数の秒のみが許可されるため、有効な候補は 14、15、および 16 となり、答えは次のようになります。`15`。 13 または 17 を含めると、候補セットが誤って拡大されてしまいます。 

3 番目のエッジ ケースは、選択した時間が 60 秒未満である必要がないということです。```
1
00:30
10
```有効な範囲は 27 ～ 33 秒です。`33`同じ数字を 2 回押すと 2 秒しかかからないため、これが最適です。 マイクロ波が解釈する`33`通常は 33 秒ですが、同じ原理で次のような値も許可されます。`88`。 

最後に、最速のエントリーが必ずしも推奨に最も近い候補であるとは限りません。 のために：```
1
06:00
8
```有効な間隔は 331 ～ 388 秒です。 シーケンス`555`わずか 3 分しかかからないため、次のような候補を上回ります。`600`600 秒がまさに推奨時間であるにもかかわらずです。 実際の期間は、`555`5分55秒です。 

## アプローチ

 直接的なアプローチは、許可された間隔内のすべての整数の秒数を列挙することです。 候補ごとに、整数を 10 進表現に変換し、そのエントリ コストを計算します。 コストが最小の候補を保持し、2 つの候補のコストが等しい場合は、推奨秒数からの絶対距離が小さい方を保持します。 

制約により間隔が小さくなるため、この強引な方法ですでに十分です。 推奨される最大時間は 20 分、つまり 1200 秒です。 と`p = 10`、間隔には 1080 ～ 1320 の最大 241 個の整数値を含めることができます。各候補のコストの計算では最大 4 桁が検査されるため、1 つのテスト ケースに必要なプリミティブ操作は約 1000 回だけです。 入力に多数のテスト ケースが含まれている場合でも、これは十分に小さいです。 

コスト計算の背後には、有益な構造的観察もあります。 合計コストは、入力中に数字が何回変更されるかによってのみ決まります。 すべての数字は常に 1 回押す必要があり、別の数字に移行するたびに 1 回の操作が必要になります。 したがって、指の位置をシミュレートしたり、キーパッドの形状をモデル化したりする必要はありません。 コストは 10 進数の文字列から直接計算できます。 

候補の間隔が狭いため、総当たり検索が機能します。 より複雑な最適化は、これらの制約の下で実際的な利点を提供することなく、実装を困難にするだけです。 重要な削減は、推奨時間を秒に変換し、正確な整数間隔を計算し、その間隔内のすべての候補を検査するだけです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(R log R) | O(log R) | 承認済み |
 | 最適 | O(R log R) | O(log R) | 承認済み |

 ここ`R`は許可される間隔の整数の秒数であり、この問題では`R <= 241`。 すべての候補の 10 進数は最大 4 桁であるため、これは事実上、テスト ケースごとに一定の時間になります。 

## アルゴリズムのチュートリアル

 1. 推奨値を変換します。`MM:SS`値を単一の整数に変換する`target = 60 * MM + SS`。 完全に秒単位で作業できるため、分と秒の境界を個別に処理する必要がなくなります。 
2. 整数演算を使用して最小の有効な候補を計算します。 下限のエンドポイントは、`ceil(target * (100 - p) / 100)`。 

正の整数の場合、これは次のように計算できます。`(x + 99) // 100`、 どこ`x = target * (100 - p)`。 
3. 最大の有効な候補を次のように計算します。`floor(target * (100 + p) / 100)`。 

整数除算はこれを直接与えます。 
4. すべての整数を反復処理します。`t`下端点から上端点まで。 このループ内のすべての値は、提案された正当な調理時間であり、正当な時間がスキップされることはありません。 
5.変換`t`に`str(t)`そしてその参入コストを計算します。 各桁を 1 回押す必要があるため、桁数から始めます。 次に、異なる数字の隣接するペアごとに 1 つを追加します。これは、異なるボタン間を移動するときにさらに 1 秒かかるためです。 
6. 現在の候補と、これまでに見つかった最良の候補を比較します。 候補者は、エントリーコストが低いほど優れています。 コストが同じ場合は比較してください`abs(t - target)`そして、推薦に近い候補者を優先します。 
7. 選択した候補の 10 進数を出力します。 これらは Chris が押す必要があるボタンではないため、コロンや先頭のゼロを挿入せずに数値そのものを出力します。 

不変条件は、すべての候補を処理した後、`t`、保存された回答は、問題からの正確な 2 レベルの順序に従って、これまでに処理されたすべての候補の中で最良の候補です。最初に最小エントリコスト、次に推奨からの最小距離です。 ループは最終的にすべての有効な整数候補を処理するため、最終的に保存された回答が固有の必須の回答となります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def entry_cost(t):
    s = str(t)
    cost = len(s)

    for i in range(1, len(s)):
        if s[i] != s[i - 1]:
            cost += 1

    return cost

def solve():
    n = int(input())
    out = []

    for case in range(1, n + 1):
        time_str = input().strip()
        p = int(input())

        minutes = int(time_str[:2])
        seconds = int(time_str[3:])
        target = minutes * 60 + seconds

        low_num = target * (100 - p)
        high_num = target * (100 + p)

        low = (low_num + 99) // 100
        high = high_num // 100

        best_time = None
        best_cost = 10**9
        best_dist = 10**9

        for t in range(low, high + 1):
            cost = entry_cost(t)
            dist = abs(t - target)

            if cost < best_cost or (cost == best_cost and dist < best_dist):
                best_time = t
                best_cost = cost
                best_dist = dist

        out.append(f"Case #{case}: {best_time}")

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```の最初の部分`solve`5 文字を変換します`MM:SS`秒単位で表現します。 入力形式が固定されているため、`time_str[:2]`議事録を渡して、`time_str[3:]`秒を与えます。 

の表現`low`そして`high`浮動小数点演算を意図的に避けます。 たとえば、下限の数学的終点が 13.5 の場合、`(13 * 100 + 99) // 100`スタイルの整数上限演算では 14 が得られます。浮動小数点演算は不要であり、境界エラーが発生する可能性があります。`entry_cost`から始まる`len(s)`すべての数字を押す必要があるためです。 次に、隣接する数字を調べます。 次のような遷移`5 -> 5`動きを必要としない一方で、`5 -> 6`は 1 回の動作を必要とするため、等しくない隣接ペアはそれぞれ 1 つだけ寄与します。 

比較条件は、必要な優先度を直接エンコードします。 エントリーコストが最初に考慮されます。 推奨時間からの距離は、入場コストが等しい場合にのみ重要です。 使用する`<`このステートメントでは最終的な答えが一意であることが保証されているため、距離の比較だけで十分です。 

次のような候補を正規化する必要はありません。`88`の中へ`01:28`。 候補は押されたボタンの順序であるため、正しい出力は正確に`88`。 Python の整数では、オーバーフローの問題も当然回避されますが、ここでの実際の値はわずか数千程度です。

def best_time(time_str, p):
    minutes = int(time_str[:2])
    seconds = int(time_str[3:])
    target = minutes * 60 + seconds

    low = (target * (100 - p) + 99) // 100
    high = target * (100 + p) // 100

    def cost(t):
        s = str(t)
        ans = len(s)
        for i in range(1, len(s)):
            if s[i] != s[i - 1]:
                ans += 1
        return ans

    best = None
    best_key = None

    for t in range(low, high + 1):
        key = (cost(t), abs(t - target))
        if best_key is None or key < best_key:
            best = t
            best_key = key

    return str(best)
