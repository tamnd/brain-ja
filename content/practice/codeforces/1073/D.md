 ## 解決策
 ## 問題の理解

 さまざまなブース価格にわたって循環ウォークをシミュレートしています。 Polycarp は位置 1 から開始し、一定の周期で時計回りに動き続けます。 各ブースで、彼は自分の残りのお金が少なくともそのブースのキャンディー 1 個の価格であるかどうかを確認します。 そうであれば、彼はキャンディーを 1 つだけ購入し、その金額だけお金を減らします。 そうでない場合は、購入をスキップします。 彼はブースを処理した後、必ず次のブースに移動します。 このプロセスは、フルパスで購入が発生しなくなった場合にのみ停止します。実際には、現在の位置でキャンディーを買う余裕がなくなった場合にプロセスが停止し、最終的にすべての可能性を使い果たすまで継続します。 

課題は、シミュレーションが終了する前に、合計で何個のキャンディーを購入したかを数えるということです。 

制約は大きく、ブース数は最大 200,000、総金額は最大 10^18 です。 これにより、ステップごとにコストがかかるものを再計算する場合、すべての金額控除にわたる単純なステップバイステップのシミュレーションが即座に排除されます。 すべての訪問の直接シミュレーションはサイクルごとに線形ですが、サイクル数は T を最低価格で割ったものまで大きくなる可能性があり、最悪の場合、明示的にシミュレーションするには大きすぎます。 

すべての価格が 1 の場合、重要なエッジ ケースが現れます。その場合、Polycarp は T がゼロになるまで各ステップでキャンディーを購入し、正確に T の操作を生成します。 ステップバイステップでシミュレーションするアプローチは概念的には機能しますが、多くのサイクルが必要なより緊密な最悪の場合の構築では遅くなりすぎます。 

もう 1 つの問題となるケースは、1 つのブースだけが手頃な価格で、他のブースは常にスキップされる場合です。 単純な実装では、ほとんどのステップが無駄なチェックである場合でも、n 個のブースすべてを繰り返しスキャンする可能性があり、縮退解釈で不必要な O(nT) 動作が発生します。 

## アプローチ

 ブルートフォースのアイデアは単純です。 Polycarp が円の周りを移動し、各ブースをチェックし、可能であれば価格を減算し、カウンターを増分することをシミュレートします。 これはプロセスを正確に反映しているため、これは正しいです。 ただし、各フル サイクルのコストは O(n) であり、最悪の場合、Polycarp は T / min(a_i) サイクル程度で実行できます。 T は 10^18 になる可能性があるため、これは不可能になります。 

重要な観察は、このプロセスには強力な周期構造があるということです。 すべてのブースをフルラウンドするごとに、すべての価格の合計に等しい固定額だけ予算が減ります。 Polycarp が許容できる完全なラウンドの数がわかっていれば、各ステップをシミュレートする代わりに、それらを飛び越えることができます。 全ラウンドを使い果たした後は部分的なパスのみが残り、最後の 1 回のリニア スキャンでシミュレートできます。 

これにより、問題はバジェット内に収まる完全なサイクルの数をカウントし、残りの残りを 1 回のパスで処理するという問題に軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(T × n) 最悪の場合 | お(1) | 遅すぎる |
 | サイクルジャンプ + 残留スキャン | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

1. すべてのブースにわたる 1 つの完全なサイクルの合計コストを計算します。 これは、Polycarp が可能な限り購入を伴う n 回の訪問を 1 回完了した場合に費やされる金額を表します。 
2. 残りの金額をサイクル コストで整数除算して、完全なサイクルを何回完了できるかを計算します。 これは、同じ動作の保証された完全な繰り返しの回数を直接示します。 
3. サイクルごとの購入数にサイクル数を掛けて、全サイクル中に購入したキャンディーの数を加算します。 これにより、多数の反復シミュレーションが 1 つの算術演算に圧縮されます。 
4. すべての全サイクルの合計コストを差し引いて、残りの金額を減らします。 この後、残りのバジェットは 1 サイクル全体のコストよりも厳密に小さくなり、最大 1 回の部分走査が発生することが保証されます。 
5. ブースを順番に通過する 1 回のパスをシミュレートします。 各ブースで、現在のお金が価格以上であれば、答えを減算して増分します。 通過を終えてから停止してください。 
6. 累計を出力します。 

### なぜ効果があるのか

 重要な不変条件は、全サイクルを処理した後、Polycarp の状態は、お金を減らしてブース 1 から再開したのと同等であり、各サイクルの構造とコストの蓄積が同一であるため、以前のサイクル内の中間構成が異なることはできないということです。 すべての完全なサイクルがお金とカウントに均一に影響を与えるため、それらを圧縮しても順序や決定の正確さが失われることはありません。 残りのシミュレーションは 1 サイクルで区切られているため、すべての部分的な動作が正確にキャプチャされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, T = map(int, input().split())
    a = list(map(int, input().split()))

    total = sum(a)

    full_cycles = T // total
    if full_cycles:
        T -= full_cycles * total

    ans = full_cycles * n

    for x in a:
        if T >= x:
            T -= x
            ans += 1

    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、まず、算術演算を使用して、繰り返される完全なループを圧縮します。 すべてのブースの価格の合計が、1 回の完全な移動のコストを定義します。 この効果を乗算すると、繰り返しサイクルのシミュレーションが回避されます。 

残りのループは、配列に対する 1 回のパスです。 各ステップで手頃な価格がチェックされ、状態が更新されます。 圧縮後に最大 1 サイクルしかシミュレートしないため、モジュロ インデックスは必要ありません。 

微妙な点は、残りの予算を変更する前に整数除算を使用することです。 これにより、全サイクルが正確にカウントされ、浮動小数点エラーや減算ループの繰り返しが回避されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, T = map(int, input().split())
    a = list(map(int, input().split()))

    total = sum(a)
    full = T // total
    T -= full * total
    ans = full * n

    for x in a:
        if T >= x:
            T -= x
            ans += 1

    return str(ans)

# provided sample
assert run("3 38\n5 2 5\n") == "10"

# all equal, small
assert run("4 10\n2 2 2 2\n") == "4"

# cannot buy anything
assert run("3 1\n5 6 7\n") == "0"

# single booth
assert run("1 100\n3\n") == "33"

# exact one cycle
assert run("2 3\n1 2\n") == "2"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | すべて等しい小さい | 4 | 均一なサイクリング動作 |
 | 購入しない | 0 | ロジックをスキップする |
 | シングルブース | 33 | 縮退 n=1 の場合 |
 | 正確なサイクルフィット | 2 | 完全なサイクルと部分的なサイクルの間の境界 |

 ## 特殊なケース

 n = 1 の場合、処理は単一の値の繰り返し減算になります。 入力用`1 100`価格付き`3`の場合、アルゴリズムはサイクル合計を 3、全サイクルを 33、残り 1 を計算し、33 回の購入を生成します。これは、各サイクルが 1 つの購入機会にすぎないため、直接推論と一致します。 

すべての価格が T を超える場合、たとえば`3 5 6 7`、完全なサイクルカウントはゼロであり、残りのパスによる購入はゼロであり、いつでも単一のブースが手頃な価格ではないという事実と一致します。 

すべての価格が等しく、T に対して小さい場合、アルゴリズムは T を合計で除算し、その余りを線形に消費することで、非常に大きな T であってもすべてのステップのシミュレーションを必要としないようにします。
