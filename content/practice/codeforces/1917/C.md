 ## 解決策
 ## 問題の理解

 配列から始めます`a`長さの`n`。 

For each of the next`d`アクションを 1 つだけ選択しなければならない日があります。 

最初のアクションでプレフィックスが増加します`[1..b_i]`1 ずつ、シーケンスは`b`指定された配列を繰り返すことによって生成されます`v`永遠に。 

2 番目のアクションでポイントが獲得されます。 現在の配列に次の位置が含まれる場合、`a_j = j`、そのようなポジションごとに 1 ポイントを獲得します。 スコアリング後、配列全体がすべて 0 にリセットされます。 

目標は、正確な結果の合計スコアを最大化することです。`d`日々。 

最も重要な観察は、リセットによって以前の進行状況がすべて破壊されるということです。 リセット後は、以前に何が起こったかに関係なく、配列はすべて 0 に固定されます。 これは、タイムラインがスコアリング操作によって分離された独立したセグメントに自然に分割されることを意味します。 

制約により、何か異常なことが明らかになります。 日数は次のように大きくすることができます`10^9`したがって、全日をシミュレートするソリューションは不可能です。 一方、すべてを合計すると、`n`入力全体の値は`2000`。 これは、意図したソリューションにおおよその費用を費やす必要があることを強く示唆しています`O(n²)`テストケースごとに動作し、依存性を完全に回避します。`d`。 

微妙な点は、リセット後は配列がすべて 0 になることです。 ポジションには番号が付けられているため、`1`、すべてゼロの配列はスコアをゼロにします。 2 つ目のスコア操作はスコアが 0 で配列が変更されないままになるため、2 つの連続したスコア操作を実行しても常に役に立ちません。 

もう 1 つの簡単な間違いは、何日も重要であると考えることです。 考慮する：```
n = 3
a = [0,0,0]
v = [3]
d = 10^9
```ポジション後`j`すでに値を超えています`j`、追加の増分は決して等しくすることはできません`j`値が増加するだけなので、再び。 配列の有用な進化は非常に短いものですが、`d`巨大です。 

3 番目の罠は、スコア操作に 1 日かかることを忘れていることです。 仮定する：```
n = 1
a = [1]
v = [1]
d = 1
```答えは`1`、すぐに得点できるからです。 同じ日にインクリメントとスコアの両方を行うことはできません。 

## アプローチ

 強引な解釈は、毎日を意思決定ポイントとみなして、数日間にわたって動的プログラミングを実行することです。 将来のスコアはその正確な値に依存するため、状態は現在の配列全体を記憶する必要があります。 以来`d`届くかもしれない`10^9`、これは絶望的です。 

より小さなものを見つけるには、実際に何が変化するかに注目する必要があります。 

各インクリメント操作では、プレフィックスに 1 が追加されるだけです。 どのポジションでも`j`、その値は 2 つのリセット間のセグメント全体にわたって単調増加します。 一度`a_j`より大きくなる`j`、そのセグメント内の将来のスコアに寄与することはできません。 

リセットせずに最初の操作を実行するとします。`t`インクリメント操作。 させて```
good(t) = number of positions j with current value exactly j
```それらの後に`t`増加します。 

当日のスコア操作を選択することを想像してください`t + 1`。 

私たちは得をします`good(t)`すぐにポイントがつきます。 

残りの日数はどうなりますか？ スコアリング後、配列はすべて 0 になります。 ゼロからスタートして、残りの日数で取得できる最高のスコアは驚くほど簡単です。 

ゼロ配列から、その後`x`今後は、2 日ごとに最大 1 つのスコアを取得できます。1 日は役立つものを作成し、もう 1 日はそれをスコア付けします。 受け入れられた解決策で使用されている公式の観察では、最大の追加寄与は次のとおりです。```
floor((remaining_days) / 2)
```なぜなら位置が`1`いつでも繰り返し再作成して収穫することができます。 

したがって、正確に演奏した後に得点することを選択した場合、`t`元の配列からのインクリメント操作の場合、達成可能な合計スコアは次のようになります。```
good(t) + floor((d - t - 1) / 2)
```どこ`t + 1`得点計算に使用される日です。 

残りの問題は、次の値がいくつあるかです。`t`チェックする必要があります。 

ポジションについて`j`、その値が超えると`j`、それは永久に役に立ちません。 当初から`0 ≤ a_j ≤ n`、各位置は最初の実行中にのみそのインデックスと等しくなります。`O(n)`増加します。 おおよそ後`2n`オペレーションでは、すべてのポジションがすでに一致しているか、永続的にオーバーシュートしています。 

公式ソリューションはこれを利用し、チェックのみを行います。```
t = 0, 1, ..., min(d - 1, 2n)
```これらのプレフィックスの追加を明示的にシミュレートしながら。 

全部の合計だから`n`だけです`2000`、このシミュレーションは簡単に十分に高速です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 数日間にわたるブルートフォース | 指数関数的 / に依存`d`| 巨大な | 遅すぎる |
 | 最初の最適シミュレーション`2n`状態 |`O(n²)`テストケースごと |`O(n)`| 承認済み |

 ## アルゴリズムのチュートリアル

 1. しましょう`cur`初期配列のコピーになります。 
2. を満たす位置の数を計算します。`cur[i] = i + 1`。 この値を呼び出します`good`。 
3. 答えを次のように初期化します。```
good + floor((d - 1) / 2)
```これは、1 日目の即時のスコアに相当します。 
4. インクリメント操作を 1 つずつシミュレートします。 
5. しましょう`lim = min(d - 1, 2n)`。 最初のものだけを調べる必要があります`lim`インクリメント操作。 
6.ステップについて`t`から`1`に`lim`:

 1. 次のプレフィックス増分を適用します。`v[(t - 1) mod k]`。 
2. 現在満たしているポジションの数を再計算します。`cur[i] = i + 1`。 
3. スコア操作の実行までに少なくとも 1 日残っている場合は、更新します。```
answer = max(
    answer,
    good + floor((d - t - 1) / 2)
)
```ここ`t`増分日数はすでに使用されており、スコアリングにはさらに 1 日が使用されます。 
7. 見つかった最大の答えを出力します。 

### なぜ効果があるのか

 最適な戦略を検討してください。 実行される最初のスコア操作に注目してください。 

このスコアがちょうど後に発生したと仮定します`t`元の配列からのインクリメント演算。 その瞬間に得られたスコアはまさに`good(t)`。 

その日以降、配列はすべて 0 になり、過去は重要ではなくなります。 残りの最適化問題は、残りの日数のみに依存します。 ゼロから開始して、2 日ごとに最大 1 ポイントを貢献でき、この上限は達成可能です。 したがって、将来の最良の貢献は正確に次のようになります。`floor((remaining_days)/2)`。 

したがって、すべての戦略は、いくつかの選択に対応します。`t`そして入手```
good(t) + floor((d - t - 1)/2).
```アルゴリズムは、関連するすべての値を評価します。`t`。 

最初だけ`2n`すべてのポジションはそのインデックスを永続的にオーバーシュートする前にのみ貢献できるため、値が重要です。 その時点以降`good(t)`第 2 項は増加することはありませんが、第 2 項は次のように減少します。`t`成長します。 これ以上大きくない`t`答えを改善することができます。 

したがって、アルゴリズムによって検査される最大値は最適スコアと等しくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())

    for _ in range(t):
        n, k, d = map(int, input().split())
        a = list(map(int, input().split()))
        v = list(map(int, input().split()))

        def count_good(arr):
            cnt = 0
            for i, x in enumerate(arr, start=1):
                if x == i:
                    cnt += 1
            return cnt

        cur = a[:]

        ans = count_good(cur) + (d - 1) // 2

        lim = min(d - 1, 2 * n)

        for step in range(1, lim + 1):
            b = v[(step - 1) % k]

            for i in range(b):
                cur[i] += 1

            good = count_good(cur)
            ans = max(ans, good + (d - step - 1) // 2)

        print(ans)

if __name__ == "__main__":
    solve()
```配列`cur`元の構成から一定回数のインクリメント操作を行った後の状態を表します。 

実行されるすべての可能な増分に対して`t`では、最初のスコア操作が直後に発生するシナリオを評価します。 表現```
good + (d - step - 1) // 2
```証明で導出された式と一致します。 

バウンド```
lim = min(d - 1, 2 * n)
```重要な最適化です。 以上をシミュレートする`2n`それ以降は新たに有用な位置が存在しないため、インクリメント操作は不要です。 

頻繁にオフバイワンの間違いを引き起こす詳細の 1 つは、次の意味です。`step`。 後`step`日数を増やすと、スコア操作にさらに 1 日必要になります。 だから残り日数は等しい```
d - step - 1
```それよりも`d - step`。

 | 時間 |`O(n * min(2n, d))`| せいぜい`2n`シミュレートされた日々、それぞれがせいぜい触れ合うだけ`n`要素 |

 次のことを考慮してください。```

```配列にはすでに一致する位置が 1 つあります。 アルゴリズムが評価するのは、`t=0`そして取得します```

```後続のスコアを取得できる日が残っていないため、増分操作は実行できません。 出力は正しく行われています`1`。
