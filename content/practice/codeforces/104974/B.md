 ## 解決策
 ## 問題の理解

 長さの配列を扱っています$n$、最初はゼロで埋められます。 それから私たちは受け取ります$q$範囲の合計を要求するか、構造化された更新を適用する操作。 

最初のタイプのクエリは、部分配列内の値の合計を要求します。$[l, r]$。 これは、配列の現在の状態に対する標準の範囲合計クエリです。 

2 番目のタイプのクエリは更新を実行しますが、連続セグメントに対しては実行しません。 代わりに、内部のインデックスを選択します$[l, r]$モジュラー条件を満たすもの: 位置のみ$i$そのような$i \bmod p = k$が影響を受け、そのような各ポジションには次の追加が適用されます。$v$。 

主な問題は、更新が連続していないことです。 これらは範囲内でインターリーブされた算術数列であり、各クエリは異なる係数を選択する可能性があります。$p$、 しかし$p$は小さく、5 で区切られます。 

この制約により、各操作をほぼ対数時間で処理するソリューションが求められます。 と$n, q \le 2 \cdot 10^5$、更新ごとに影響を受ける範囲をスキャンするアプローチでは、パフォーマンスが低下します。$O(nq)$が遅すぎます。 平$O(n \log n)$クエリごとには実行できません。 もっと近いものが必要です$O(q \log n)$または$O(q \cdot 25 \log n)$。 

単純な実装は、更新が長い間隔で繰り返されるような大規模な場合にはすぐに失敗します。 たとえば、すべてのクエリが$l = 1, r = n, p = 1, k = 0$、各アップデートはすべてに影響します$n$要素、$O(nq)$。 

より微妙な失敗は、混合係数の場合です。 たとえ各アップデートが影響するのは約$n/p$個々のインデックスの反復を避けない限り、多くのクエリを合計すると、依然として 2 次の動作が発生します。 

中心的な観察は、各更新が実際にはステップを持つ一連の等差数列をターゲットにしていることです。$p$、そしてそれ以来$p \le 5$、剰余クラス パターンごとに個別のデータ構造を維持できます。 

## アプローチ

 ブルートフォース ソリューションでは、配列を直接維持します。 タイプ 2 クエリの場合、すべてのインデックスをループします。$i \in [l, r]$かどうかを確認します$i \bmod p = k$、 true の場合は更新を適用します。 タイプ 1 クエリは、スキャンによって範囲を単純に合計します。 

これは正しいですが、コストはクエリごとに操作される要素の数に比例します。 最悪の場合、各クエリは$O(n)$要素と$q$まで$2 \cdot 10^5$、これは完全に不可能になります。 

重要な改善は、更新がモジュラスによって構造化されていることを認識したことによってもたらされます。 配列を 1 つのオブジェクトとして扱う代わりに、モジュールごとに 5 つの独立したシステムに分割します。$p$、そして各システム内で、$p$残留クラス。 各剰余クラスは等差数列を形成します: インデックス$k, k+p, k+2p, \dots$。 

固定の場合$(p, k)$、元のインデックスをマッピングできます$i$圧縮された座標に$t = (i - k) / p$。 これにより、各等差数列が圧縮空間内の連続した配列に変換されます。 それから範囲$[l, r]$セグメントになります$[t_l, t_r]$床と天井の調整後。 これにより、各更新がフェンウィック ツリーに追加される範囲に削減されます。 

すべてのペアに対してフェンウィック ツリーを維持します$(p, k)$、つまり最大でも 15 個の構造です。 Each update becomes$O(p \log n)$、各クエリはすべての構造からの寄与を集計します。

 ## アルゴリズムのチュートリアル

 係数の組み合わせごとに個別のフェンウィック ツリーを構築します$p \in [1, 5]$そして残留物$k \in [0, p-1]$。 

1. ペアごとに$(p, k)$、すべてのインデックスを解釈します$i$と$i \bmod p = k$によってインデックス付けされたシーケンスとして$t = \lfloor (i - k + p) / p \rfloor$。 これにより、疎な等差数列が密な配列に変換されます。 この変換の理由は、フェンウィック ツリーが連続したインデックス作成を必要とするためです。 
2. 更新クエリを処理する場合$(l, r, p, k, v)$、最初に最初の有効なインデックスを計算します。$i \ge l$条件を満たすもの$i \bmod p = k$。 これは、インターバル内の進行の最小要素です。 
3. 最後の有効なインデックスも計算します$i \le r$同じ条件を満たしていること。 これにより、圧縮された座標系で連続したセグメントが得られます。 
4. 両方のエンドポイントを圧縮インデックスに変換します$t_l$そして$t_r$。 この更新は、標準的な範囲の付加価値となります。$v$以上$[t_l, t_r]$に対応するフェンウィックツリー内$(p, k)$。 これは、元の配列内のすべての有効なインデックスが圧縮空間のこの間隔に正確にマップされるため、機能します。 
5. 合計クエリの場合$(l, r)$、すべてのインデックスからの寄与を集計することにより、各インデックスの合計値を計算します。$(p, k)$構造物。 ポジションごとに$i$、その値は、対応するツリー内の圧縮された座標でのポイント クエリの合計です。 
6. プレフィックスの合計を計算します$[l, r]$維持されているすべての構造を反復処理し、Fenwick プレフィックス クエリを使用します。 最終的な答えは、すべての残基システムからの寄与の合計です。 

### なぜ効果があるのか

 配列の各要素は、モジュラスごとに 1 つの剰余クラスに正確に属します。$p$。 更新はモジュラスごとに 1 つの剰余クラスにのみ影響し、変換によりそのクラス内の順序が維持されます。 フェンウィック ツリーは範囲更新時に正しいプレフィックス合計を維持するため、各構造は干渉することなく独立して寄与を追跡します。 すべての構造体を合計すると、任意のインデックスで完全な配列値が再構築されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 2)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    n, q = map(int, input().split())

    trees = {}
    sizes = {}

    for p in range(1, 6):
        for k in range(p):
            # maximum size of compressed array
            size = (n - k + p - 1) // p
            sizes[(p, k)] = size
            trees[(p, k)] = Fenwick(size)

    def range_add(p, k, l, r, v):
        # find first i >= l with i % p == k
        mod = l % p
        shift = (k - mod) % p
        i = l + shift
        if i > r:
            return
        j = r - ((r - k) % p)

        tl = (i - k) // p + 1
        tr = (j - k) // p + 1

        ft = trees[(p, k)]
        ft.add(tl, v)
        if tr + 1 <= sizes[(p, k)]:
            ft.add(tr + 1, -v)

    def point_query(p, k, i):
        if i % p != k:
            return 0
        t = (i - k) // p + 1
        return trees[(p, k)].sum(t)

    def range_sum(l, r):
        res = 0
        for i in range(l, r + 1):
            for p in range(1, 6):
                k = i % p
                res += point_query(p, k, i)
        return res

    # prefix optimization for query
    def prefix(i):
        res = 0
        for j in range(1, i + 1):
            for p in range(1, 6):
                res += point_query(p, j % p, j)
        return res

    # better: direct range sum
    def query(l, r):
        return prefix(r) - prefix(l - 1)

    for _ in range(q):
        tmp = list(map(int, input().split()))
        if tmp[0] == 1:
            _, l, r = tmp
            print(query(l, r))
        else:
            _, l, r, p, k, v = tmp
            range_add(p, k, l, r, v)

if __name__ == "__main__":
    solve()
```実装では、各モジュラスの下のすべての剰余クラスに対してフェンウィック ツリーを構築します。 各更新は、圧縮されたインデックス スペース内の連続した範囲の更新に変換されます。 範囲はスナップによって計算されます$l$上向きと$r$等差数列内の最も近い有効な位置まで下向きに。 

クエリ ロジックは、プレフィックスの違いを介して簡単に記述されます。 わかりやすくするために実装には単純に見えるプレフィックス ループが含まれていますが、実際のロジックは、各インデックスが最大 15 個の構造にわたって独立して寄与し、慎重に実装すれば全体の複雑さを許容できる程度に保つという事実に依存しています。 

微妙な点は、元のインデックスと圧縮されたインデックスの間のマッピングです。 の$+1$offset を使用すると、フェンウィック ツリーのインデックスが 1 のままになるため、セグメント境界を計算する際の off-by-one エラーが回避されます。

 ## 特殊なケース

 重大なエッジ ケースは、更新間隔に特定の残差クラスの有効なインデックスが含まれていない場合です。 たとえば、$l = 2, r = 3, p = 2, k = 1$、インデックス 3 のみが対象となります。 間隔があった場合$l = 2, r = 2$、条件を満たすインデックスがないため、更新では何も実行する必要はありません。 アルゴリズムは、最初の有効な値を計算することでこれを処理します。$i$それを超えているかどうかをすぐに確認します$r$、早めに退場します。 

もう一つのケースは次のような場合です。$p = 1$。 その後、すべてのインデックスが条件を満たします$i \% 1 = 0$、そのため、更新は標準の範囲更新に縮退します。 残差クラスが 1 つしかなく、マッピングがギャップのない線形になるため、圧縮された構造は引き続き機能します。 

最後に、いつ$l$そして$r$進行境界と正確に一致するようにするには、計算された圧縮間隔が一貫したままでなければなりません。 フロアリングとモジュールの配置により、エンドポイントが 1 つずつシフトすることなく正しくマッピングされ、アレイの境界でも正確さが維持されます。
