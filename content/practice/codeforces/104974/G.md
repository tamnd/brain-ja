 ## 解決策
 ## 問題の理解

 各テスト ケースでは、すべての人が一意の名前と 8 桁の電話番号を持っている、人々の小さな電話帳が提供されます。 その後もたくさんのお問い合わせをいただいております。 各クエリでは完全な電話番号が明らかになることはありません。 代わりに、少数の桁のみが表示され、その順序は無関係です。 クエリ内に同じ数字が複数回出現する場合もあります。 

クエリごとに、電話帳のどの電話番号がこれらの観測された数字を生成した可能性があるかを判断する必要があります。 電話番号に少なくとも同じ多重度を持つすべてのクエリ数字が含まれており、順序は無視され、電話番号内の余分な数字は無視されている場合、その電話番号は互換性があるとみなされます。 

各クエリの出力は、一致する電話番号の数によって異なります。 一致するものがない場合、答えは「なし」になります。 1 人の人の番号が正確に一致する場合、その人の名前が出力されます。 複数の電話番号が一致する場合は、MANY が出力されます。 

重要な問題は、クエリの規模にあります。 最大 100 万件のクエリが存在する可能性がありますが、電話帳は最大でも 1 万件のエントリと比較的小規模です。 各電話番号は固定長 8 ですが、これが問題における最も重要な構造上の制約です。 

単純な考えでは、桁数を数えることによって、すべての電話番号をすべてのクエリに対してチェックすることになります。 これには、最大 10^6 のクエリに 10^4 の電話番号を乗算する必要があり、各チェックで最大 8 桁をスキャンする可能性があります。 これにより、約 8 × 10^10 の演算が行われ、1 秒で実行できる演算数をはるかに超えます。 

クエリの解釈には微妙な落とし穴もあります。 数字の順序は無関係であるため、クエリを文字列の接頭辞または部分文字列として扱うと、不正確な一致が発生します。 もう 1 つの間違いは、多重度を忘れることです。 「11」のようなクエリでは、電話番号に 1 が 1 つだけではなく少なくとも 2 つ必要です。 

## アプローチ

 ブルートフォースアプローチは簡単です。 クエリごとに、保存されているすべての電話番号を反復処理し、その番号にクエリで必要なすべての数字が含まれているかどうかを十分な頻度で検証します。 各電話番号をサイズ 10 の数字頻度配列として表し、クエリに対しても同じことを行います。 数字のアルファベットが固定されているため、単一の数字をチェックするには一定の時間がかかります。 ただし、クエリごとにこれを繰り返すと、およそ 10^6 × 10^4 のチェックが必要となり、遅すぎます。 

重要な観察は、各電話番号が非常に短いということです。 長さが 8 の場合、ポジションの個別のサブセットの数は 2^8 = 256 によって制限されます。すべての電話番号をスキャンしてクエリに答える代わりに、プロセスを逆にします。 すべての電話番号について、そこから派生したクエリとして表示される可能性のあるすべての数字のマルチセットを事前計算します。 各サブセットは、電話番号からいくつかの位置を選択することに対応しており、これにより、複数の桁のセットが生成されます。 このようなマルチセットごとに、どの電話番号がそれを生成できるかを記録します。 

この前処理が完了すると、各クエリはその桁マルチ​​セットの直接辞書検索になります。 辞書は、そのパターンを生成できる電話番号が 0、1、または複数であるかどうかを示します。 

ブルート フォースから最適なソリューションへの移行は、作業をクエリから前処理に移行することによって促進されます。 サブセットの関係を 100 万回再計算する代わりに、電話番号ごとにすべての可能性を 1 回計算します。

 ## アルゴリズムのチュートリアル

 各電話番号を 8 文字の配列として表します。 中心的なアイデアは、その数字のすべてのサブセットを列挙することです。

1. 各電話番号について、0 ～ 255 のビットマスクを使用して、その 8 つの位置のすべてのサブセットを考慮します。各ビットマスクは、電話番号の数字の選択またはスキップを表します。 これが機能するのは、すべてのクエリが完全な電話番号からの一部の数字の選択に対応し、余分な数字が無視されるためです。 
2. サブセットごとに、選択した数字の正規表現を構築します。 これを行うには、数字を収集し、それらを文字列に並べ替えます。 クエリでは順序が保持されないため、並べ替えが必要です。そのため、「123」と「321」は同じ表現にマップする必要があります。 
3. この正規の数字列から、生成できる異なる電話番号の数を格納する構造へのハッシュ マップを維持します。 すべての名前を保存する必要はありません。 ゼロ、1、または多数を区別する必要があるだけです。 したがって、各エントリには何も保存されないか、1 つの名前が保存されるか、複数の一致を示すマーカーが保存されます。 
4. 電話番号を処理するとき、各サブセットが電話番号ごとに最大 1 回だけ寄与することを保証します。 サブセットは番号ごとに独立して生成されるため、これは当然当てはまります。 
5. クエリごとに、その数字列を同じ正規の並べ替え表現に変換し、単一の辞書検索を実行します。 保存されている情報に基づいて、NONE、単一の名前、または MANY を出力します。 

### なぜ効果があるのか

 すべてのクエリは、複数の数字セットに正確に対応します。 電話番号は、クエリ マルチセットがその電話の数字マルチセットのサブセットである場合に限り、クエリと一致します。 このようなすべてのサブセットは、その電話番号の 8 つの位置の列挙されたサブセットの中に表示されます。 したがって、一致が存在する場合は、前処理中に記録されている必要があります。 すべての電話番号のカウントを追跡するため、最終的に保存された状態は、0、1、または複数の電話番号がクエリ パターンを生成できるかどうかを正確に反映します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import defaultdict

def normalize(s):
    return ''.join(sorted(s))

def solve():
    n = int(input().strip())
    
    phone_names = []
    phones = []
    
    for _ in range(n):
        parts = input().split()
        name = parts[0]
        phone = parts[1].strip()
        phone_names.append(name)
        phones.append(phone)

    mp = {}

    for idx in range(n):
        name = phone_names[idx]
        phone = phones[idx]
        digits = list(phone)

        seen = set()

        for mask in range(1 << 8):
            subset = []
            for i in range(8):
                if mask & (1 << i):
                    subset.append(digits[i])
            key = ''.join(sorted(subset))
            if key in seen:
                continue
            seen.add(key)

            if key not in mp:
                mp[key] = [1, name]
            else:
                if mp[key][0] == 1:
                    if mp[key][1] != name:
                        mp[key][0] = 2
                        mp[key][1] = ""
                elif mp[key][0] == 2:
                    pass

    q = int(input().strip())
    out = []

    for _ in range(q):
        parts = input().split()
        k = int(parts[0])
        s = parts[1].strip()
        key = ''.join(sorted(s))

        if key not in mp:
            out.append("NONE")
        else:
            cnt, name = mp[key]
            if cnt == 1:
                out.append(name)
            else:
                out.append("MANY")

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```前処理ループは実装の重要な部分です。 電話番号ごとに、ビットマスクを使用して 256 個のサブセットすべてを生成します。 各サブセットは数字を並べ替えることによって正規化され、順列が同じキーにマッピングされることが保証されます。 小規模な最適化はローカルで行われます。`seen`電話番号ごとに設定されます。これにより、電話番号で数字が繰り返され、異なるビットマスクで同じ数字のマルチセットが生成される場合の冗長な挿入が回避されます。 

辞書には、キーが 0、1、または複数の電話番号に対応するかどうかなど、クエリに答えるのに十分な情報のみが保存されます。 同じキーに対して 2 番目の個別の名前が表示されると、状態を MANY に折りたたみます。 

クエリ フェーズはクエリごとに一定時間であり、最大 8 桁の並べ替えと辞書検索のみが含まれます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n · 2^8 + q · 8 log 8) | 各電話機は 256 のサブセットを生成します。 各クエリは最大 8 桁でソートされます。 
| スペース | O(n · 2^8) | 各サブセット パターンは最大でも一定のメタデータとともに保存されます。 

前処理が優勢ですが、2^8 は 256 にすぎないため、小さいままです。n が 10^4 までの場合、サブセットの総生成は数百万回程度の操作にとどまりますが、これは十分に制限内です。 クエリ処理はクエリ数に関しては直線的ですが、クエリあたりのコストは非常に低くなります。

 ## 特殊なケース

 電話番号に繰り返しの数字が含まれる場合、微妙な特殊なケースが発生します。 たとえば、電話「11223344」は、異なるビットマスクから同一のサブセット表現を生成します。 電話番号ごとに重複を排除しないと、寄付金が誤って過大にカウントされてしまいます。 電話機ごと`seen`set は、各マルチセットが番号ごとに 1 回だけ記録されることを保証し、正確さを保ちます。 

もう 1 つのケースには、電話番号で使用できる数字を超える数字が繰り返されるクエリが含まれます。 たとえば、クエリ「111」は、1 が 2 つだけある電話番号と一致するべきではありません。 サブセットの生成は実際の位置に基づいているため、そのようなクエリ パターンはその電話番号から生成されることはなく、辞書には表示されず、正しく NONE が返されるか、他の番号に応じて別の一致が返されます。
