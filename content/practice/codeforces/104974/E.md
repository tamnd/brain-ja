 ## 解決策
 ## 問題の理解

 連続して適用される 3 つの操作をサポートする非常に小さなファイル システムをシミュレートしています。 各操作では、名前付きファイルを作成するか、名前付きファイルを削除するか、現在存在するファイルの数を尋ねます。 ファイルは名前によって一意に識別され、名前は正確な文字列のように動作します。`"abc"`そして`"ABC"`は異なり、スペースは名前の一部です。 

状態は空から始まります。 とき`touch name`コマンドが表示されると、その名前を現在のファイルセットに挿入しようとします。 すでに存在する場合は何も変わりません。 とき`rm name`コマンドが表示されると、その名前が存在する場合は削除します。 それが存在しない場合は、再び何も行いません。 とき`ask`コマンドが表示されると、現在保存されているファイルの数が出力されます。 

重要な問題はスケールです。 コマンドの数は最大 100 万個で、ファイル名は任意の文字列で、合計の長さは 200 万文字に達することがあります。 これにより、クエリごとに保存されているすべての名前をスキャンするソリューションは即座に除外されます。`ask`最悪の場合、二次関数の動作に変質する可能性があります。 

単純な実装では、文字列のリストを維持します。`ask`、リスト全体をスキャンし、メンバーシップを手動で確認することにより、存在する個別の文字列の数を再計算します。 これは、操作が多く、保存されているファイルが多い場合に問題が発生します。 

より微妙な障害モードは、重複の誤った処理によって発生します。 たとえば、私たちが治療すると、`touch`存在を確認せずに「リストに追加」として実行すると、同じ名前を繰り返しタッチすると、カウントが誤って増加します。 同様に、単にすべてのカウンタをデクリメントすると、`rm`、存在しないファイルを削除対象とする場合は、マイナスになる可能性があります。 

## アプローチ

 ブルートフォースのアイデアは簡単です。現在有効なすべてのファイル名のリストを維持します。 のために`touch`、名前がすでにリストにあるかどうかを確認します。 そうでない場合は追加します。 のために`rm`、リストを検索し、見つかった場合は削除します。 のために`ask`、リストのサイズを計算します。 

リストはアクティブ セットを正確に反映しているため、正確性は即座にわかります。 問題はパフォーマンスです。 両方`touch`存在チェックと`rm`ルックアップには最大 O(n) 文字列のスキャンが必要で、削除には要素のシフトも必要になる場合があります。 最大 10^6 の操作では、最悪の場合、およそ O(n^2) の動作が発生し、これは制限をはるかに超えています。 

重要な観察は、順序や構造ではなく、メンバーシップとカーディナリティのみが必要であるということです。 ハッシュベースのセットはまさにそれを目的として設計されています。 Python にファイル名を保存すると、`set`、3 つの操作はすべて平均 O(1) になります。挿入、削除、メンバーシップのチェックは平均して一定時間であり、セットのサイズによって答えが得られます。`ask`直接。 

また、再計算を完全に回避します。 セットは常に現在の状態を表すため、カウントは構造体によって内部的に保持されている格納された整数を読み取るだけです。

 ## アルゴリズムのチュートリアル

 一連のアクティブなファイル名を維持しながら、コマンドを 1 つずつ処理します。 

1. 空のセットを初期化する`files`。 これは、任意の時点での現在存在するすべてのファイル名を表します。 
2. 各コマンドラインを読み、部分に分割します。 最初のトークンによって操作の種類が決まります。 
3. コマンドが`touch name`、 入れる`name`セットに。 すでに存在する場合、セットは変更されずに残り、重複を無視するという要件に一致します。 
4. コマンドが`rm name`、 取り除く`name`存在する場合はセットから。 存在しない場合は何もしません。 これは次を使用して安全に実装できます`discard`したがって、エラーは発生しません。 
5. コマンドが`ask`、セットの現在のサイズを出力します。 

このロジックが機能するのは、すべてのファイル名がセット内で最大 1 回表され、すべての有効な状態遷移がその要素の追加または削除によってキャプチャされるためです。 

### なぜ効果があるのか

 あらゆるステップで、セットは`files`によって挿入された名前が正確に含まれます`touch`しかし、によって削除されませんでした`rm`。 これは帰納的に保存されます。`touch`不足している要素を重複せずに追加します。`rm`他の要素には影響を与えずに既存の要素のみを削除します。`ask`状態は変更されません。 したがって、セットのサイズは常にその時点でアクティブなファイルの数と等しくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n = int(input())
    files = set()
    out = []

    for _ in range(n):
        parts = input().strip().split()
        if parts[0] == "touch":
            files.add(parts[1])
        elif parts[0] == "rm":
            files.discard(parts[1])
        else:
            out.append(str(len(files)))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    main()
```このソリューションは、Python の組み込みハッシュ セットを利用してファイル名を保存します。 の使用`discard`の代わりに`remove`これは、存在しないファイルを削除するときの例外を回避し、問題ステートメントの「何もしない」動作と一致するため、意図的なものです。 

クエリの上限で顕著になる I/O オーバーヘッドを削減するために、回答をすぐに出力するのではなくリストに蓄積します。

 ## 特殊なケース

 1 つのエッジケースが繰り返される`touch`同じファイル名の。 セットは重複を無視するため、状態は安定したままになります。 たとえば:

 入力:```
touch a
touch a
ask
```セットはこうなります`{a}`両方の操作の後なので、出力は次のようになります`1`。 リストベースの実装では、明示的にチェックしない限り、誤って 2 つのコピーが保存されてしまいます。 

もう 1 つのエッジ ケースは、作成されていないファイルを削除することです。 使用する`discard`例外や状態変化がないことを保証します。 

入力:```
rm missing
ask
```セットは空のままで、出力は`0`。 ナイーブ`remove`コールはクラッシュする一方、手動のカウンターアプローチは否定的な結果になる可能性があります。 

最後のエッジケースは、ファイルが絶えず追加および削除される大規模なチャーンです。 各操作は O(1) で償却されるため、状態が大きく変動する場合でも、アルゴリズムは線形パフォーマンスを維持します。
