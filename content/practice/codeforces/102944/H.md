 ## 解決策
 ## 問題の理解

 1 つのカウンターに、時間の経過とともに次々とお客様が到着します。 各顧客には到着時間とチップの額があります。 顧客が受け入れられると、顧客は FIFO ラインに加わり、1 人ずつサービスが提供され、各サービスにはまったく同じ固定時間がかかります。 

このシステムには厳しい制約があります。待っている人、またはサービスを受けている人の総数は、常に一定の収容力 K を超えることはできません。システムがすでに満員であるときに新しい顧客が到着すると、その顧客はすぐに失われてしまいます。 ただし、将来のオーバーフロー状況を回避するために、たとえ適合する顧客であっても、事前に積極的に拒否することが許可されています。 目標は、オーバーフローが起こらず、提供された顧客からのチップの合計が最大化されるように、どの顧客を維持するかを選択することです。 

重要な問題は、顧客を受け入れることはその顧客だけに影響を与えるわけではないということです。 サービスは厳密に逐次的に行われ、受け入れられた各顧客は固定長のタイムスロットを占有し、後続のすべての顧客が遅れる可能性があるため、将来のスケジュール全体が変更されます。 

N は最大 1000 であるため、制約は十分に小さいため、O(N²) または O(N² log N) 戦略が受け入れられます。これにより、指数関数的なサブセット検索が即座に除外され、O(N³) アプローチさえも境界線になりますが、まだ考えられます。 この構造は、候補スケジュールをシミュレーションし、違反を貪欲に修正する必要があることを強く示唆しています。 

これを単純な並べ替えまたは独立した選択の問題として扱おうとすると、微妙な失敗例がいくつか発生します。 たとえば、到着順を考慮せずに最高額のチップを最初に選択すると、早い顧客が後の顧客をブロックするスケジュールが作成され、一連の拒否が発生して総利益が減少する可能性があります。 

単に溢れ出るまで全員を受け入れて、最後に到着した顧客をドロップするという単純な貪欲も間違っています。 後の顧客は非常に高額なチップを持っていても、依然としてオーバーフローを引き起こす顧客である可能性がありますが、時間の経過とともにシステムが大きくなりすぎた本当の理由は、以前の低額顧客にあります。 

## アプローチ

 この強引なアイデアは、顧客のすべてのサブセットを試し、各サブセットのキューをシミュレートし、スケジュールがキャパシティを超えない場合に合計チップを計算することです。 これは問題の制約を直接モデル化しているため、これは正しいです。 ただし、サブセットは 2ⁿ あり、1 つのサブセットをシミュレートするだけでも O(N) のコストがかかり、実行不可能な O(N・2ⁿ) かそれ以上の複雑さになります。 

重要な観察は、重要な構造は到着順序と誘導された FIFO サービス順序だけであるということです。 サブセットを決定すると、サービスのタイムラインは完全に決定されます。 これは、問題は順序の選択ではなく、時間の経過に伴うキュー占有の制約の下でどの要素が生き残るかを選択することであることを意味します。 

これは建設的なアプローチを示唆しています。つまり、到着順の昇順で顧客をシミュレートし、誘導されたサービス スケジュールを維持し、スケジュールがキャパシティの制約に違反するたびに、現在のセットから 1 人の顧客を削除します。 他の顧客を削除すると、実現可能性を必要以上に向上させることなく、より多くの利益を浪費するため、削除する最適な候補は、現在輻輳の原因となっている顧客の中でチップが最も少ない顧客です。 

N はわずか 1000 であるため、要素を削除するときにスケジュールを繰り返し再構築する余裕があります。 各再構築は線形であり、削除の数は最大 N であるため、ソリューションは制限内に保たれます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | サブセットに対するブルート フォース + シミュレーション | O(N・2^N) | O(N) | 遅すぎる |
 | 貪欲な削除と再計算による増分シミュレーション | O(N²) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 サービスの順序は最終的には受け入れられた顧客の到着順によって決定されるため、最初にすべての顧客を到着時間で並べ替えます。

当社では、受け入れられた顧客の最新リストを維持しています。 固定の受け入れセットの場合、サービス時間を正確に計算できます。各顧客は到着時刻と前回の完了時刻の最大時刻に開始し、S 時間単位後に終了します。 

1. 顧客を到着時間順に並べ替えます。 
2. 受け入れられた顧客の空のセットから開始します。 
3. 顧客をソート順に繰り返し、次の顧客を受け入れられたセットに暫定的に挿入します。 

この挿入により、その時点以降のスケジュールが変更されるため、受け入れられたすべての顧客の開始時刻と終了時刻が順番に再計算されます。 
4. 再計算後、イベント順に時間をスキャンし (計算された間隔によって暗示される到着と出発)、システム内に同時に何人の顧客がいるかを追跡します。 

いずれかの時点でアクティブな顧客の数が K を超えた場合、違反が特定されます。 
5. 違反を修正するには、現在受け入れられているセットから 1 人の顧客を削除します。 最良の選択は、現在の過負荷状況に寄与している顧客の中でチップが最も少ない顧客です。これは、その削除によってキャパシティが解放され、損失が最小限に抑えられるためです。 
6. 顧客を削除すると、その後のすべての開始時間が変更されるため、削除後、スケジュールを再計算します。 
7. 現在のセットで違反が発生しなくなるまでこのプロセスを繰り返し、その後、次の到着の処理を続けます。 

重要な点は、実行不可能性が検出されるたびに、顧客を 1 人だけ削除して修復し、問題のある領域の中で最も価値の低い顧客を常に削除することです。 

### なぜ効果があるのか

 いつでも、スケジュールは顧客が受け入れたプレフィックスによって完全に決定されます。 容量に違反した場合は、現在アクティブな顧客のうち少なくとも 1 人を削除する必要があります。 それらの中で、チップが最小のものを削除することは、システム サイズを 1 つ削減しながらも総利益の減少が最小限に抑えられるため、局所的に最適です。 サービスの順序は固定されており、FIFO であるため、他の顧客を削除しても、実現可能性を回復するのに同等の効果があるか、利益の点で厳密に悪くなるかのどちらかです。 この修復手順を繰り返し適用すると、削除するたびに過負荷が厳密に軽減され、顧客の数も有限であるため、最終的には実行可能なスケジュールが作成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_schedule(customers, S):
    # customers: list of (a, t)
    n = len(customers)
    start = [0] * n
    end = [0] * n

    cur_time = 0
    for i in range(n):
        a, _ = customers[i]
        if cur_time < a:
            cur_time = a
        start[i] = cur_time
        end[i] = cur_time + S
        cur_time = end[i]

    return start, end

def violates(customers, start, end, K):
    events = []
    for i in range(len(customers)):
        events.append((start[i], 1))
        events.append((end[i], -1))

    events.sort()
    cur = 0
    for _, delta in events:
        cur += delta
        if cur > K:
            return True
    return False

def solve():
    N, K, S = map(int, input().split())
    customers = []
    for _ in range(N):
        a, t = map(int, input().split())
        customers.append([a, t])

    customers.sort()

    accepted = list(range(N))
    active = customers[:]

    # we store indices into active list; easier to rebuild by filtering
    while True:
        active = [customers[i] for i in accepted]
        start, end = build_schedule(active, S)

        # check feasibility
        events = []
        for i in range(len(active)):
            events.append((start[i], active[i][1]))
            events.append((end[i], -active[i][1]))
        events.sort()

        cur = 0
        bad = False
        for i, delta in events:
            cur += 1 if delta > 0 else -1
            if cur > K:
                bad = True
                break

        if not bad:
            break

        # find candidate to remove: minimum tip among all accepted
        worst_idx = min(accepted, key=lambda i: customers[i][1])
        accepted.remove(worst_idx)

    ans = sum(customers[i][1] for i in accepted)
    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、顧客の候補セットを維持し、誘導された FIFO スケジュールがキューの容量を超えているかどうかを繰り返しチェックします。 そうなると、最も価値の低い顧客が削除され、スケジュールが最初から再構築されます。 単一サーバーの制約により、1 人の顧客を削除するとすべてのダウンストリーム開始時間が変更されるため、再構築手順が必要になります。 

実現可能性チェックでは、スケジュールを開始イベントと終了イベントに変換し、それらをスイープして同時顧客の最大数を検出します。 

重要な実装の詳細は、スケジュールが反復ごとに再計算され、サービス時間のカスケード依存性にもかかわらず正確性が保証されることです。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N²) | 各削除は完全な再構築をトリガーし、最大 N 個の削除があり、各再構築はスイープを含めて O(N) です。 
| スペース | O(N) | 顧客リストと現在受け入れられているサブセットを保存します。 

N ≤ 1000 という制約により、定数係数が小さく、すべての操作が線形スキャンまたは単純なソートであるため、O(N²) シミュレーションは 1 秒以内で快適に高速になります。

    S = int(next(it))

 ## 特殊なケース

 重大なエッジケースは、到着が集中し、サービス時間によりバックログが増大する場合に発生します。 このような状況では、アルゴリズムは最初にあまりにも多くの価値の低い顧客を受け入れ、後で集合的に違反を引き起こす可能性があります。 

たとえば、多くの少額チップの顧客が高額チップの顧客の直前に到着する場合、スケジュールは数回挿入した後でのみ K を超える可能性があります。 このアルゴリズムは、各挿入後に完全なスケジュールを再計算し、現在受け入れられているセット内の最も価値の低い顧客を削除することでこれを処理し、価値の低い輻輳ソースが最初に排除されるようにします。 

もう 1 つの特殊なケースは、到着客がまばらな場合です。 その場合、K に関係なくキューがいっぱいになることはなく、アルゴリズムが削除をトリガーすることはありません。 イベント時間にわたるスイープでは 1 を超える同時アクティブ間隔が決して観察されないため、シミュレーションによってこれが確認されます。 

どちらのケースも完全な再計算アプローチによって自然に処理され、将来の到着に関するローカルな仮定に依存することが回避されます。
