 ## 解決策
 ## 問題の理解

 私たちには、実際の量の水が入った 2 つの容器が与えられます。 1つは次から始まります`a`、もう一方は`b`。 最大で移せるカップもございます`c`1 回の操作での水の単位。 1 回の操作でソース容器を選択し、一定量の水を汲み上げます。`c`、もう一方の器に注ぎます。 

このプロセスでは 2 つの値が非対称に変化しますが、水の総量は一定のままです。 移動するたびに、一方の容器はある程度減少し、もう一方の容器は同じ量だけ増加します。 目標は、両方の容器にまったく同じ量を入れることです。 

総水量は固定されているため、唯一可能な最終状態は、各容器に次のものが含まれているということです。`(a + b) / 2`。 もし`a == b`、答えはすでにゼロ手です。 それ以外の場合は、事実上正確に転送しようとしています`|a - b| / 2`最大でもサイズの移動を使用して、大きな容器から小さな容器への水の単位`c`。 

制約は非常に小さいです。`a, b, c ≤ 100`、そして最大`1000`テストケース。 これにより、きめの細かい分数状態のシミュレーションや連続的な選択の検索が即座に除外されます。 正しい解決策は、プロセスをテスト ケースごとの直接の算術計算に減らす必要があります。 

微妙なエッジケースは次のような場合です`c`差分全体を 1 回の移動で転送できるほど十分に大きいです。 もう一つは、いつ`c`非常に小さいため、多くの部分転送が必要になります。 常に正確に転送する素朴な貪欲さ`c`ここでも引き続き機能しますが、必要な転送の残りを慎重に処理する場合に限ります。 

## アプローチ

 強引な解釈では、プロセスを段階的にシミュレートします。 各ステップで、より大きな容器を選択し、最大でいくらかの量を移します。`c`と貪欲に差を縮めていきます。 いつも乗り換えるなら`c`(または、少ない場合は残りの必要な量)、間の絶対的な差を減らします。`a`そして`b`。 

すべての操作が厳密に削減されるため、このシミュレーションは正しいです。`|a - b|`すでに等しい場合を除きます。 ただし、その複雑さは移動数に比例し、最悪の場合、`|a - b| / c`。 ここでは値が小さいため、これは技術的には実現可能ですが、実際の構造が隠蔽されてしまいます。各移動で差は最大で 1 つ減少します。`c`、差がゼロになることだけを気にします。 

重要な観察は、個々の状態を追跡する必要がないということです。 絶対的な差異のみを追跡します`d = |a - b|`。 それぞれの動きによって、この差は最大で 1 つずつ縮まる可能性があります`c`常に最適な方向 (大きい方向から小さい方向へ) を選択できるため、最適な戦略は常に差をできるだけ小さくすることです。 これにより、問題は単純な上限分割、つまりサイズのチャンクがいくつになるかという問題に変わります。`c`カバーする必要がある`d / 2`転送単位ですが、より明確に、移動ごとの差の減少という観点から推論します。 

それぞれの動きで最大でも差が縮まります`2c`不均衡解消の観点からですが、より直接的には、移転します。`x`大きいものから小さいものへ、差は次のように減少します`2x`したがって、最適な移動には常に時間がかかります`x = min(c, remaining_needed/2)`事実上。 これは、単純な貪欲なカウントに分解されます。最大まで繰り返し減算します。`c`アンバランスがなくなるまで。 

したがって、答えは次のとおりです`ceil(|a - b| / (2c))`縮小を対称的にモデル化し、標準的な CF ソリューションでより明確に導出すると、差がゼロになるまで繰り返し縮小することが単純化されます。`ceil(|a - b| / (2c))`。 実際には、受け入れられている公式は次のとおりです。`ceil(|a - b| / (2c))`これはそれぞれの動きが動くという事実と一致します`c`一方からもう一方へ。

 ## アルゴリズムのチュートリアル

 1. 絶対差を計算します`d = |a - b|`。 これは、移転を​​通じて解消する必要がある全体的な不均衡を表します。 
2. もし`d == 0`、出力`0`両方の容器がすでに等しいため、操作は必要ありません。 
3. 各操作で最大移動できるのは`c`これにより、一方向の不均衡が最適に低減されます。 
4. それぞれの動きによってアンバランスが正確に減少するため、`2 * x`どこ`x ≤ c`、移動ごとに可能な最大の削減は次のとおりです。`2c`。 
5. 移動回数を最小の整数として計算します。`k`そのような`k * 2c ≥ d`。 
6. 出力`ceil(d / (2c))`。 

### なぜ効果があるのか

 システムの状態は違いによって完全に説明されます`d`。 すべての動きは総質量を維持し、変化します`d`送金額の2倍を差し引いて。 私たちは常に大きな容器をソースとして選択するため、常に量を減らします。`d`増やすのではなく。 一連の移動の中で、常に最大許容転送量を使用すること以上に効果的なものはありません。`c`転送量が小さいと転送量が減少するため、`d`よりゆっくりと、そして決してそれを補う将来の利益を生み出すことはありません。 これにより、プロセスは繰り返し減算することと同等になります。`2c`から`d`最適なステップ数が得られるゼロに達するまで。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    a, b, c = map(int, input().split())
    d = abs(a - b)
    if d == 0:
        print(0)
    else:
        # each move can reduce difference by at most 2c
        print((d + 2 * c - 1) // (2 * c))
```実装は、各テスト ケースを読み取り、2 つの容器間の絶対的な差を計算することから始まります。 唯一重要なステップは、転送を明示的にシミュレートする必要がないことを認識することです。 プロセス全体がこの差を縮めることにつながります。 

整数の上限除算`(d + 2*c - 1) // (2*c)`不均衡をサイズの塊にグループ化しているという事実をエンコードします`2c`。 エッジケース`d == 0`式はゼロを返しますが、不必要な算術演算を避けるために個別に処理されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        a, b, c = map(int, input().split())
        d = abs(a - b)
        if d == 0:
            out.append("0")
        else:
            out.append(str((d + 2*c - 1) // (2*c)))
    return "\n".join(out)

 ## 特殊なケース

 重要なエッジケースの 1 つは、その差がカップの容量よりも小さい場合です。 例えば`a = 1, b = 4, c = 10`与える`d = 3`。 アルゴリズムは計算します`(3 + 19) // 20 = 1`これは、必要な水をすべて分割することなく一度に移送できるという事実と一致します。 

もう一つのケースは次のような場合です。`a == b`。 ここで、計算された差はゼロであり、早期終了は直ちにゼロ手を返します。 このチェックを行わない場合でも、数式はゼロを生成しますが、明示的な分岐により、演算が必要ないという解釈とロジックの一貫性が保たれます。 

3 番目のケースは次の場合です。`c = 1`、ユニットの転送を強制します。 のために`a = 1, b = 100`、その差は 99 で、手ごとに最大 2 ずつ減ります。式は次のようになります。`(99 + 1) // 2 = 50`、これは多くの小さな調整の必要性に一致し、正確に均等に収束するように最適に方向を切り替えます。
