 ## 解決策
 ## 問題の理解

 接続された無向グラフがあります。 一部の頂点にはトークンが含まれており、一部の頂点にはボーナスが含まれています。 移動は、1 つのトークンを取得し、それを隣接する頂点に移動することで構成されます。 最初の移動は常に許可されますが、その後の移動は、前に移動したトークンがボーナス頂点に着地した場合にのみ許可されます。 次の動きでは別のトークンを使用する必要があります。 目標は、いずれかのトークンが最終的に頂点 1 に到達できるかどうかを決定することです。 

難しいのは、トークンの動きだけが重要ではないということです。 ボーナス着地の連鎖を維持するのに十分なトークンが他にない場合、フィニッシュに近いトークンはまだ役に立たない可能性があります。 同時に、ボーナスの一部のグループは無制限の追加の動きを生成できます。 

この制約により、テスト ケース全体の頂点とエッジの合計数が約 200,000 に達することが許可されます。考えられる状態の数が指数関数的に増加するため、トークンの移動の考えられるすべてのシーケンスを探索することができなくなります。 ソリューションは、グラフのサイズが線形に近い必要があります。 

いくつかのケースは見落とされやすいものです。 トークンが頂点 1 から始まる場合、移動は必要ないため、答えはすぐに YES になります。 例えば：```
n = 3, m = 2
tokens = [1]
bonuses = [2]
edges = (1,2), (2,3)
```正しい出力は YES です。 トークンが頂点 1 に移動できるかどうかだけをチェックするソリューションでは、トークンが誤って拒否されてしまいます。 

もう 1 つの注意が必要なケースは、トークンがいくつかのボーナスを使用することによってのみ終了に到達できるが、チェーンを継続するのに十分な他のトークンがない場合です。```
n = 4, m = 3
tokens = [4]
bonuses = [3]
edges = (1,2), (2,3), (3,4)
```正しい出力は NO です。 トークンは 4 から 3 まで移動できますが、それ以降は同じトークンを再利用できないため、再度移動することはできません。 単純な最短パス チェックでは、トークンが継続できると誤って判断されてしまいます。 

最後のエッジケースは無限の動きの源です。 2 つのボーナスが隣接している場合、そのエリア近くのトークンは、ボーナス エッジの周りで異なるトークンを移動することによって、ボーナスを繰り返しアクティブ化し続けることができます。```
n = 5, m = 5
tokens = [5,4]
bonuses = [2,3]
edges = (1,2), (2,3), (3,4), (4,5), (2,5)
```ボーナス ペアは無制限のターンを提供できるため、正しい出力は YES です。 近くにあるトークンの数だけを数えるアプローチでは、これを見逃してしまいます。 

## アプローチ

 直接的なアプローチでは、考えられるすべてのゲームをシミュレートします。 トークンを選択して移動し、次に利用可能になったトークンをすべて再帰的に試すことができます。 これは、可能な一連の動きを正確に調査しているため、正しいです。 問題は、分岐要素が膨大になる可能性があることです。 トークンが多数ある場合、可能な手の順序の数はトークンの並べ替えの数に匹敵し、制限をはるかに超えています。 

重要な観察は、シーケンス全体について考えるのをやめ、選択した 1 つのトークンを終了に導くために必要な手数に焦点を当てることです。 最終的に頂点 1 に到達するトークンを選択するとします。最後の移動の前に、このトークンはチェーンの継続を可能にする頂点を通過する必要があります。 これらの有用な頂点は、フィニッシュに向かうパス上にあるボーナス頂点です。 

まず、頂点ごとに、そこにあるトークンがフィニッシュに到達するまでに必要なボーナス着地の最小数を見つけます。 これは頂点 1 から始まる BFS で実行できますが、ボーナス頂点を通じてのみ拡張します。 トークンが距離のある頂点にある場合`d`、必要です`d`サポートが完了する前に移動します。 

ここで必要なのは、他のトークンが十分なサポートを提供できるかどうかを知ることだけです。 トークンがボーナス頂点の隣にある場合、トークンは 1 つの追加の動きに貢献できます。 隣接するボーナスのペアの一部であるボーナス頂点の隣にある場合、それらのボーナスはトークンを交互に切り替えることで永久に再利用できるため、無制限の移動に貢献できます。 

ブルートフォースは、考えられるすべての順序をモデル化するため機能します。 可能な注文の数が爆発的に増えると失敗します。 利用可能なサポートの量のみが重要であるという観察により、シーケンスの検索をグラフの前処理に置き換えることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(n) | 遅すぎる |
 | 最適 | O(n + m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. グラフを読み取り、どの頂点にトークンが含まれ、どの頂点にボーナスが含まれるかを保存します。 いずれかのトークンが頂点 1 から始まる場合、ゲームはすでに終了しているため、答えは直ちに YES になります。 
2. 隣接するボーナスのペアに属するすべての頂点をマークします。 これらの頂点は、トークンが将来の無限の動きを生み出すのに役立つ場所を表します。 
3. 頂点 1 から BFS を実行します。拡張中はボーナス頂点のみを通過します。 結果として得られる距離から、ゲームを継続しながらフィニッシュに到達するためにその頂点から必要な最小移動数がわかります。 
4. すべてのトークンについて、必要なサポート量を計算します。 トークンは自身の初動を無料で使用できるため、必要な距離が`d`、必要です`d - 1`他のトークンからの追加の動き。 
5. すべてのトークンから利用可能なサポートをカウントします。 トークンがダブルボーナスエリアに隣接している場合、トークンは無制限のサポートを提供します。 それ以外の場合は、1 ステップでボーナスに到達できれば 1 つの移動に貢献します。 
6. すべてのトークンを最終的な勝利トークンとして試します。 自身の貢献をサポート数から一時的に削除します。 無制限のサポートがある場合、または 1 回の移動で十分なサポートがある場合、答えは「YES」です。 

機能する理由: 選択された勝利トークンは、フィニッシュへの最終移動の前に一連の移動のみを必要とします。 最終以外の動きはすべて、別のターンをアクティブにするためだけに存在するため、他のトークンに関する唯一の関連情報は、それらが提供できるターン数です。 再利用可能なボーナス構造に近いトークンは無限のターンを提供しますが、他のすべての有用なトークンは 1 つだけを提供します。 BFS 距離から必要なターンの正確な数が得られるため、最終的な比較で十分です。 

## Python ソリューション```python
import sys
from collections import deque

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    p, b = map(int, input().split())

    tokens = list(map(int, input().split()))
    bonuses = [0] * (n + 1)

    if b:
        for x in map(int, input().split()):
            bonuses[x] = 1
    else:
        input()

    graph = [[] for _ in range(n + 1)]

    edges = []
    for _ in range(m):
        u, v = map(int, input().split())
        graph[u].append(v)
        graph[v].append(u)

    has_pair = [0] * (n + 1)
    for i in range(1, n + 1):
        if bonuses[i]:
            for v in graph[i]:
                if bonuses[v]:
                    has_pair[i] = 1
                    break

    if 1 in tokens:
        print("YES")
        return

    support = [0] * (n + 1)

    for x in tokens:
        for v in graph[x]:
            if has_pair[v]:
                support[x] = 2
                break
            if bonuses[v]:
                support[x] = max(support[x], 1)

    dist = [-1] * (n + 1)
    q = deque([1])
    dist[1] = 0

    while q:
        u = q.popleft()
        for v in graph[u]:
            if bonuses[v] and dist[v] == -1:
                dist[v] = dist[u] + 1
                q.append(v)

    cnt_one = 0
    cnt_inf = 0

    for x in tokens:
        if support[x] == 1:
            cnt_one += 1
        elif support[x] == 2:
            cnt_inf += 1

    for x in tokens:
        if support[x] == 1:
            cnt_one -= 1
        elif support[x] == 2:
            cnt_inf -= 1

        need = 10**9

        if dist[x] != -1:
            need = dist[x]

        for v in graph[x]:
            if dist[v] != -1:
                need = min(need, dist[v] + 1)

        if need != 10**9:
            if cnt_inf > 0 or cnt_one >= need - 1:
                print("YES")
                return

        if support[x] == 1:
            cnt_one += 1
        elif support[x] == 2:
            cnt_inf += 1

    print("NO")

t = int(input())
for _ in range(t):
    solve()
```後のすべてのステップで近隣ノードへの高速アクセスが必要となるため、コードは最初に隣接関係リストを構築します。 の`has_pair`配列は、隣接するボーナス ペア内にある頂点を識別します。これはまさにサポートが無制限になる場所です。 

BFS は通常の最短パス検索とは少し異なります。 すべての中間移動はボーナスに到達する必要があるため、フィニッシュから開始し、ボーナス頂点にのみ拡張します。 ボーナス以外の頂点を準備パスの一部にすることはできません。 

最後のループでは、各トークンが最後に到達したものとしてテストされます。 それ自体は役に立たないため、それ自体の貢献はチェックする前に削除されます。 値`need - 1`これは、事前のボーナスのアクティベーションを必要とせずに、ゲームの最初の手が常に利用可能であるという事実から来ています。 

## 実用的な例

 次のことを考慮してください。```
n = 4, m = 3
tokens = [4,3]
bonuses = [3]
edges = (1,2), (2,3), (3,4)
```| ステップ | 現在のトークン | 距離 | 1 回の移動で | 無限のサポート | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | イニシャル | 4 | 3 | 1 | 0 | 続ける |
 | テストトークン 4 | 3 つ必要 | 1 | 0 | 十分ではありません | いいえ |

 4 のトークンはボーナスに入ることができますが、その後はシーケンスを継続するために利用できる他のトークンがありません。 トレースは、距離だけでは不十分な理由を示しています。 

別の例:```
n = 4, m = 4
tokens = [4,3]
bonuses = [2,3]
edges = (1,2), (2,3), (3,4), (1,4)
```| ステップ | 現在のトークン | 距離 | 1 回の移動で | 無限のサポート | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | BFS | 1 | 0 | | | |
 | ボーナス 2 | 1 | | | | |
 | ボーナス 3 | 2 | | | | |
 | テストトークン 4 | 2 | 0 | 1 | 0 | はい |

 4のトークンはボーナスチェーンを使用できます。 もう一方のトークンからのサポートは、最後の動きまでゲームを存続させるのに十分です。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m) | すべてのエッジは、BFS と前処理によって一定の回数処理されます。 
| スペース | O(n + m) | 隣接リストと補助配列にはグラフ情報が格納されます。 

すべてのテストにわたる合計入力サイズは線形解に適合します。 このアルゴリズムはゲーム状態の探索を回避するため、最大のグラフであっても高速なままです。 

## テストケース```python
import sys, io
from collections import deque

def run(inp: str) -> str:
    old = sys.stdin
    sys.stdin = io.StringIO(inp)
    t = int(sys.stdin.readline())
    out = []
    for _ in range(t):
        n, m = map(int, sys.stdin.readline().split())
        p, b = map(int, sys.stdin.readline().split())
        tokens = list(map(int, sys.stdin.readline().split()))
        bonuses = [0] * (n + 1)
        if b:
            for x in map(int, sys.stdin.readline().split()):
                bonuses[x] = 1
        else:
            sys.stdin.readline()

        g = [[] for _ in range(n + 1)]
        for _ in range(m):
            u, v = map(int, sys.stdin.readline().split())
            g[u].append(v)
            g[v].append(u)

        if 1 in tokens:
            out.append("YES")
            continue

        pair = [0] * (n + 1)
        for i in range(1, n + 1):
            if bonuses[i] and any(bonuses[x] for x in g[i]):
                pair[i] = 1

        typ = []
        one = inf = 0
        for x in tokens:
            val = 0
            for y in g[x]:
                if pair[y]:
                    val = 2
                    break
                if bonuses[y]:
                    val = 1
            typ.append(val)
            if val == 1:
                one += 1
            elif val == 2:
                inf += 1

        dist = [-1] * (n + 1)
        q = deque([1])
        dist[1] = 0
        while q:
            u = q.popleft()
            for v in g[u]:
                if bonuses[v] and dist[v] == -1:
                    dist[v] = dist[u] + 1
                    q.append(v)

        ok = False
        for idx, x in enumerate(tokens):
            if typ[idx] == 1:
                one -= 1
            elif typ[idx] == 2:
                inf -= 1

            need = 10**9
            if dist[x] != -1:
                need = dist[x]
            for y in g[x]:
                if dist[y] != -1:
                    need = min(need, dist[y] + 1)

            if need != 10**9 and (inf or one >= need - 1):
                ok = True

            if typ[idx] == 1:
                one += 1
            elif typ[idx] == 2:
                inf += 1

        out.append("YES" if ok else "NO")

    sys.stdin = old
    return "\n".join(out)

 ## 特殊なケース

 最初のエッジ ケースでは、答えがすぐに返されるため、頂点 1 のトークンはアルゴリズム チェックに入りません。 これは、移動する前にゲームがすでに終了している状態を処理します。 

単一トークンのボーナスの場合、BFS はトークンがフィニッシュに近づく可能性があることを正しく検出しますが、勝利トークンを削除した後のサポート カウントはゼロになります。 ターンを提供するのに十分な他のトークンがないため、この条件は失敗します。 

隣接するボーナスの場合、前処理によってボーナス ペアがマークされます。 そのエリアの隣にあるトークンは無限サポートとして分類されるため、個々の動きをカウントする必要がなく、最終チェックは成功します。 これは、隣接するボーナスの繰り返しの性質を捉えています。
