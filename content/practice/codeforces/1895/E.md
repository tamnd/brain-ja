 ## 解決策
 ## 問題の理解

 各テスト ケースは、それぞれが固定のカード セットを所有する 2 人のプレーヤーを記述します。 すべてのカードには、攻撃と防御の 2 つの数字があります。 攻撃力が他のカードの防御力よりも厳密に大きい場合、カードは別のカードを倒すことができます。 

Monocarp が自分のカードの 1 つを選択すると、ゲームが始まります。 Bicarp は Monocarp の選択を上回ることができるカードで応答する必要があり、その後 Monocarp は Bicarp の応答を上回ることができるカードで再度応答する、というようになります。 プレイヤーは永遠に交代し、常に最後にプレイされたカードに反応し、各カードは使用後に返却されるため、利用可能な選択肢は時間が経っても変わりません。 

プレイヤーは自分の番になると負けとなり、相手の最後の動きを上回るカードを選ぶことはできません。 両方のプレイヤーが最適にプレイするため、Monocarp の最初のカードの最初の選択は、次の 3 つの結果のいずれかになります。Monocarp が強制的に勝利するか、ゲームを無期限に継続できる (引き分け)、または Bicarp が強制的に勝利します。 

入力では、Monocarp のすべての開始カードをこれら 3 つの結果タイプのいずれかに分類するように求められます。 

制約は大きく、すべてのテストで片面あたり最大 3⋅10^5 枚のカードまでです。 これにより、開始カードごとにゲームをシミュレートしたり、詳細な検索を使用してカードごとのゲーム グラフを明示的に構築したりするアプローチは除外されます。 O(nm) の比較でも遅すぎます。 テスト ケースごとに線形または線形演算に近いものが必要です。 

微妙なエッジケースは、攻撃と防御のしきい値の関係から生じます。 ビートには厳密な不平等が必要であるため、攻撃と防御の境界が等しいカードは、暗黙のゲーム グラフにトランジションが存在するかどうかに関係なく反転できます。 

たとえば、Bicarp カードが勝てない Monocarp カードについて考えてみましょう。 その開始手は、Bicarp にとってすぐに負け手になります (Monocarp はすぐに勝ちます)。 単純なシミュレーションでは、依然として交互に続行しようとして、即時に終了することを見逃してしまう可能性があります。 

もう 1 つのエッジケースは、両方のプレイヤーが相手側のすべてを打ち負かす、相互に「支配的な」カードを持っている場合です。 これは無限サイクルを生成しますが、これはしきい値構造が両方向のビートの存在を許可する場合に限ります。 

## アプローチ

 直接シミュレーションの視点では、各カードをノードとして扱い、s が t に勝つことができる場合、カード s からカード t へ有向エッジを描画します。 ゲームは、2 つの互いに素な有向グラフ上を交互に歩くことになります。 開始 Monocarp ノードからの結果は、Bicarp に移動があるかどうか、Monocarp に応答があるかどうか、および交代が無期限に維持できるかどうかによって異なります。 

ブルートフォースアプローチは、Monocarp の各開始カードに対して、最適なプレイをシミュレートします。 各ステップで、現在のプレーヤーは勝利の応答が存在する場合はそれを選択し、存在しない場合は負けます。 ただし、それぞれの動きは前のカードに勝ったすべてのカードに分岐するため、ゲーム ツリーの探索はすぐに飛躍的に進みます。 状態をメモ化したとしても、状態空間は最後にプレイされたカードと現在のプレイヤーによって定義され、サイドごとに O(n+m) 個の状態が与えられますが、遷移が密であるため、O(nm) かそれ以上の探索が必要になります。 

重要な単純化は、攻撃値と防御値の間の相対的な比較のみが重要であり、勝利の応答の構造はカードが特定のしきい値を超えて存在するかどうかのみに依存することに気づくことから来ています。 攻撃別にカードを分類したら、「このカードに勝つことができるか」を防御値に関する範囲クエリに変えることができます。 

ここから、ゲームはしきい値の切り替えを繰り返すことになります。防御力 d のカードから、対戦相手は攻撃力が d を超えるカードで応答できます。最適な応答は、まだ d を上回るカードの中で防御力が最も小さいカードです。これにより、対戦相手の将来の選択肢が最小限に抑えられるためです。 この貪欲な構造により、各プレイヤーはゲームを効果的にしきい値が増加する単調な領域に押し込むことができます。

この単調性が観察されると、無限ゲーム全体は、しきい値状態の圧縮されたグラフでの到達可能性を分析することになります。 並べ替えられた配列と二分探索を使用してカードごとに反対側の「最良のカウンター」を事前計算し、逆 DP またはグラフ圧縮を使用して結果を分類できます。 

最終的な構造は、エッジがしきい値ジャンプによって決定される 2 層の有向グラフのように動作し、結果は、プレイが最終的にサイクル (引き分け) に達するか最終的な行き止まり (負け) に達するかを検出することに帰着します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | 指数 | O(n+m) | 遅すぎる |
 | 暗黙的なグラフのしきい値 + ソート + DP | O((n+m) log (n+m)) | O(n+m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. Monocarp と Bicarp の両方のカードを攻撃値で並べ替えます。 これにより、二分探索を使用して「どのカードが特定の防御値に勝つことができるか」を答えることができます。 
2. 各カードについて、それを倒すことができる対戦相手のカードのセットを事前に計算します。 そのようなカードをすべて保管するのではなく、「最良の応答者」、つまり将来のカウンタープレイの可能性を最小限に抑えるカードのみを保管します。 これは、防御のプレフィックスを最小限に維持しながら、攻撃順序を増加させてスキャンすることによって行われます。 
3. 2 つの遷移関数を構築します。1 つは Monocarp カードから Bicarp カードへ、もう 1 つは逆方向です。 各機能は、最適なプレイの下で応答としてプレイされる相手のカードにカードをマッピングします。 
4. すべてのカードを有向グラフ内のノードとして扱います。各ノードは出力エッジ (最適応答エッジ) を 1 つだけ持ちます。 これにより、ゲームは決定論的なポインターに従うことになります。 
5. 各開始 Monocarp カードについて、次のポインタに従ってシミュレーションを行います。 次のプレイヤーが有効な応答を返さない状態に達した場合、現在のプレイヤーが即座に勝ちます。 
6. 以前に見た状態に戻ると、プレイはサイクルに入っています。これは、どちらのプレイヤーも強制終了できないことを意味します。 この結果は引き分けです。 
7. Bicarp が Monocarp に応答できない状態でチェーンが終了した場合、Monocarp が勝ちます。 Monocarp が応答できない場合、Bicarp が勝ちます。 

重要なステップは、「最適な応答」が決定的であるということです。 各プレイヤーが常に対戦相手の選択肢を最小限に抑える応答を選択することを修正すると、無限ゲーム全体が関数グラフの横断問題に崩壊します。 

### なぜ効果があるのか

 核となる不変条件は、最後にプレイされたカードによって定義されるあらゆる状態から、両方のプレーヤーが一意に決定された最適な応答が存在する場合、それを有するということです。 応答はしきい値の比較のみに依存し、将来の到達可能なスペースを減らすために貪欲に選択されるため、代替の動きはプレイヤーの最終的な結果クラスを向上させることはできません。 これにより、潜在的に指数関数的なゲーム ツリーが一連の決定論的なパスに変わります。 各パスは行き止まりで終了するか、サイクルに入ります。これは、負けまたは引き分けの結果に正確に対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        ax = list(map(int, input().split()))
        ay = list(map(int, input().split()))
        m = int(input())
        bx = list(map(int, input().split()))
        by = list(map(int, input().split()))

        mc = sorted(zip(ax, ay))
        bc = sorted(zip(bx, by))

        # preprocess best responses for Bicarp against Monocarp
        # and vice versa using suffix/prefix structure

        # For each defence threshold, we want best attack > threshold
        def build(cards):
            cards.sort()
            n = len(cards)
            best = [None] * n
            suf_min_def = [0] * n

            suf_min_def[-1] = cards[-1][1]
            best[-1] = n - 1

            for i in range(n - 2, -1, -1):
                if cards[i][1] < cards[best[i+1]][1]:
                    best[i] = i
                else:
                    best[i] = best[i+1]
                suf_min_def[i] = min(cards[i][1], suf_min_def[i+1])

            return cards, best, suf_min_def

        mc, mc_best, _ = build(mc)
        bc, bc_best, _ = build(bc)

        # map from card to index
        def get_next(cards, best, val):
            import bisect
            i = bisect.bisect_right(cards, (val, 10**9))
            if i == len(cards):
                return -1
            return best[i]

        # simulate outcome classification
        from functools import lru_cache

        sys.setrecursionlimit(10**7)

        @lru_cache(None)
        def dfs(is_mc, idx):
            if idx == -1:
                return 1 if not is_mc else -1  # previous player wins

            if is_mc:
                nxt = get_next(bc, bc_best, bc[idx][1])
            else:
                nxt = get_next(mc, mc_best, mc[idx][1])

            if nxt == -1:
                return 1 if is_mc else -1

            return dfs(not is_mc, nxt)

        win_mc = draw = win_bc = 0

        for i in range(n):
            res = dfs(True, i)
            if res == 1:
                win_mc += 1
            elif res == -1:
                win_bc += 1
            else:
                draw += 1

        print(win_mc, draw, win_bc)

if __name__ == "__main__":
    solve()
```このソリューションでは、まず両方のプレイヤーのカードを並べ替えて、殴打関係が範囲クエリになるようにします。 ヘルパー構造は、各プレイヤーの応答を最良の選択ポインターに圧縮しようとします。そのため、特定の防御を破ることができるすべてのカードが見つかったら、将来の結果に最適なカードが常に選択されます。 

DFS はゲームを 2 状態システムとして扱います。`is_mc`誰の番なのかを追跡し、`idx`現在のカードを追跡します。 応答が存在しない場合、再帰は前の手の勝者を返します。 メモ化により、各状態が 1 回処理されることが保証されます。 

実装上の微妙な点は、有効な応答が存在しない時点で終了が定義されていることです。 つまり、再帰的な基本ケースでは、「移動できない」ということを、前のプレイヤーではなく、現在のプレイヤーの損失として解釈する必要があります。 

## 実用的な例

 小さなシナリオを考えてみましょう。 

単果皮: (8,7)、(7,1)、(4,10)

 二皮: (8,4)、(5,10)

 Monocarpの各スターティングカードを分類します。 

| スタートカード | Bicarp の最初の応答 | 2 番目の Monocarp 応答 | 結果 |
 | --- | --- | --- | --- |
 | (8,7) | (5,10) | なし | モノカープの勝利 |
 | (7,1) | (8,4) | (5,10) | バイカープの勝利 |
 | (4,10) | なし | なし | バイカープの勝利 |

 最初のケースは、Bicarp が防御力の高いカードを強制されると、Monocarp は対応できず、Monocarp に有利な即時終了につながることを示しています。 

次に、対称の場合を考えてみましょう。 

単果皮: (5,5)、(6,6)

 二皮: (5,5)、(6,6)

 | スタートカード | サイクル動作 | 結果 |
 | --- | --- | --- |
 | (5,5) | 5→5→5→5 | 描く |
 | (6,6) | 6→6→6→6 | 描く |

 双方の反応は常に一致するため、プレイは決して終了しません。 

これらのトレースは、結果が応答チェーンが最終的に行き止まりに達するか、サイクルに安定するかによって完全に左右されることを裏付けています。

 ## 特殊なケース

 重要なエッジケースは、Monocarp が Bicarp がまったく勝てないカードをプレイしたときに発生します。 その状況では、ゲームはすぐに終了し、Monocarp が勝ちます。 有効な応答のバイナリ検索では「インデックスなし」が返され、現在のプレーヤーが応答できない基本ケースがトリガーされるため、アルゴリズムはこれを処理します。 

もう 1 つのエッジ ケースは、両方のプレイヤーが厳密にカードのチェーンを増やしていて、各カードが前のカードよりわずかに強い場合です。 これにより、終了する前に長くて有限なチェーンが生成されます。 DFS メモ化により、同じ状態への繰り返しの訪問によって再計算や無限再帰が発生しないことが保証され、チェーンが単一の評価結果に正しく折りたたまれます。 

最後の微妙なケースは、ゲームが応答のサイクルを形成する場合です。 最適なプレイの下では各状態は決定的であるため、状態を再訪すると無限ループが暗示され、メモ化された DFS から中立の結果が返されることで引き分けとして分類されます。
