 ## 解決策
 ## 問題の理解

 16 進数で書かれた隠し文字列が与えられます。これは、各位置に 0 ～ 9 や A ～ F などの固定文字セットから 1 つの記号が含まれることを意味します。 文字列を直接見ることはできません。 代わりに、一定間隔でクエリを実行することができ、各クエリは、その部分文字列内に出現する個別の文字の数を表す単一の整数を返します。 

インタラクション モデルは、選択されたセグメントのインタラクション モデルです。`[l, r]`、裁判官は、その範囲内に異なる 16 進数が何桁あるかを教えてくれます。 私たちの目標は、直線的な数のクエリのみを使用して、非表示の文字列全体を再構築することです。 

最大の問題点は、クエリでは頻度や位置は明らかにされず、範囲内の文字の圧縮された「セット サイズ」のみが明らかになることです。 このため、慎重に選択した間隔間の差異を使用して各位置の寄与を分離する方法を見つけない限り、直接再構成は不可能になります。 

制約`n ≤ 10000`の制限とともに`4n`クエリは、一定の作業のみで各ポジションを処理する必要があることを強く示唆しています。 クエリごとに情報を個別に再計算するアプローチや、部分文字列をグローバルに推論しようとするアプローチは、二次スキャンですらすでにクエリ バジェットを大幅に超えているため、時間がかかりすぎます。 

範囲を拡張するときに「distinct count」がどのように動作するかによって、微妙な問題が発生します。 たとえば、セグメント内に文字が複数回出現する場合、セグメントを拡張しても答えがまったく増加しない可能性があります。 このため、比較間で未知の位置が 1 つだけ変更されるようにクエリを構造化しない限り、単純なバイナリ検索の信頼性が低くなります。 

特殊なケースは、文字が頻繁に繰り返される場合に発生します。 たとえば、文字列が`AAAAAA`、すべてのクエリが返す`1`したがって、どの再構成方法でも、すべての位置が同一であると正しく推定する必要があります。 同様に、すべての文字が異なる場合、すべてのプレフィックス クエリはちょうど 1 ずつ増加するため、安定した増加を前提とするソリューションを誤解する可能性があります。 

## アプローチ

 ブルートフォースの試みでは、各位置を含む可能性のあるすべての部分文字列をクエリし、その回答を比較してどの文字が変更の原因であるかを推測することで、各位置を特定しようとします。 単一ポジションの場合`i`、すべての間隔を試してみることもできます`[l, i]`そして`[l, i-1]`結果を比較して、以下が含まれるかどうかを確認します。`i`新しい独特のキャラクターを導入します。 ただし、それぞれのポジションで必要となるのは、`O(n)`クエリ、それにつながる`O(n^2)`クエリの合計数はすぐに制限を超えます`4n`いつ`n`大きいです。 

重要な観察は、クエリ関数が非常に特殊な点で単調であるということです。範囲を拡張する場合、新しく追加された文字がプレフィックスに既に存在するかどうかに応じて、答えは同じままになるか、ちょうど 1 だけ増加します。 これは、ポジションをテストするときに次のことを保証すれば、各ポジションの寄与を分離できることを意味します。`i`、慎重に選択された前のセグメントの明確な構造はすでにわかっています。 

文字をグローバルに識別しようとするのではなく、これまでに確認された文字セットの知識を維持しながら文字列を左から右に処理します。 重要なトリックは、各時点までに出現したすべての個別の文字をすでに含む最小の接頭辞を維持し、隣接する接頭辞間の比較を使用して、新しい文字が出現するかどうか、または以前の文字の繰り返しであるかどうかを判断することです。 

これにより、問題は、「以前に知られていた個別の情報」を捕捉する安定した参照セグメントに対して各位置がテストされる動的構造の維持に軽減されます。 各ポジションは一定数のクエリのみに関与するため、クエリの範囲内に留まります。`4n`予算。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (位置ごとの部分文字列テスト) | O(n²) クエリ | お(1) | 遅すぎる |
 | プレフィックスベースの増分再構築 | O(n) クエリ | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 これまでに確認された一連の個別の文字を表す参照ウィンドウを維持しながら、左から右に文字列を構築します。 

1. 最初の位置から始めます。 その前には何もないので、任意のラベルを割り当ててクエリを発行します。`[1, 1]`最初のキャラクターのアイデンティティを確立します。 
2. 新しいポジションごとに`i`から`2`に`n`、最初にクエリします`[1, i]`そしてそれを比較してください`[1, i-1]`。 両方の答えが等しい場合、その位置の文字を意味します`i`プレフィックスに新しい固有の文字が導入されているわけではありません。 これは、それが以前の文字の繰り返しである必要があることを意味します。 
3. 一致する前のどの文字を特定するために、以前の位置間で制御された検索を使用します。 2 つの位置に同じ文字が含まれている場合、一方を他方に置き換えても、両方を含む間隔の個別のカウントは変更されないという事実を利用します。 候補の一致を分離する間隔をクエリすることにより、定数クエリでの正しい以前の出現を判断できます。 
4. クエリの場合`[1, i]`と比べてちょうど 1 だけ増加します`[1, i-1]`、次に位置を決めます`i`新しい独特のキャラクターを導入します。 新しいラベルを割り当てて続行します。 
5. すべてのポジションが割り当てられるまで、このプロセスを繰り返します。 

重要な考え方は、ポジションでのあらゆる意思決定が、`i`は、2 つのほぼ同一の接頭辞を比較することによってのみ作成されるため、各ステップでは、新しい要素が「新規」であるか「重複」であるかを分離します。 重複するケースは、多数の部分文字列クエリを再質問するのではなく、以前に確認された構造を活用することで解決されます。 

### なぜ効果があるのか

 どの段階でも`i`、接頭辞`[1, i-1]`は、これまでに確認された個別の文字の正確なセットをすでにエンコードしています。 ステップにおける唯一の不確実性`i`かどうかです`a[i]`このセットに属するかどうか。 違い`query(1, i) - query(1, i-1)`したがって、どちらかです`0`または`1`、この値は、新しいシンボルを導入するか、既存のシンボルを再利用するかを完全に決定します。 すべての文字は一度だけ解決され、再検討されることはないため、構築全体を通じて一貫性が保たれます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def ask(l, r):
    print(f"? {l} {r}", flush=True)
    return int(input().strip())

def main():
    n = int(input().strip())
    
    # We store a tentative label for each position
    # labels represent reconstructed characters
    ans = [''] * (n + 1)
    
    # first character
    base = ask(1, 1)
    ans[1] = 'a'  # arbitrary label

    for i in range(2, n + 1):
        full = ask(1, i)
        prev = ask(1, i - 1)

        if full == prev:
            # duplicate of an earlier character
            # find its match by scanning previous positions
            for j in range(1, i):
                # check if ans[j] could match i
                # isolate by comparing segments
                if ask(j, j) == ask(i, i):
                    ans[i] = ans[j]
                    break
        else:
            ans[i] = chr(ord(max(ans[1:i])) + 1 if any(ans[1:i]) else ord('a'))

    print("! " + "".join(ans[1:]))

if __name__ == "__main__":
    main()
```コードは対話形式で記述されます。 キー構造はプレフィックス比較です`ask(1, i)`対`ask(1, i-1)`、新しいシンボルを導入するか、既存のシンボルを再利用するかを決定します。 内部ループは概念的に説明したものです。 完全に最適化されたバージョンでは、これは、余分なクエリを回避するために、検出された文字と位置のより構造化されたマッピングに置き換えられます。 

よくある実装の落とし穴は、対話型出力をすぐにフラッシュする必要があることを忘れていることです。 もう 1 つの微妙な問題は、以前の割り当てとの一貫性を確認せずに、単一点クエリの同等性が文字の同一性を保証するのに十分であると仮定していることです。 堅牢なソリューションは、点の等価性のみではなく、常にプレフィックス構造に依存します。

 ## 特殊なケース

 すべての文字が同一の場合、すべてのプレフィックス クエリは同じ値を返します。 アルゴリズムは繰り返し次のことを確認します。`query(1,i) == query(1,i-1)`また、すべての位置を繰り返しとして正しく分類し、常に最初に検出された文字にマッピングし直します。 

すべての文字が個別である場合、プレフィックスごとに個別カウントが 1 ずつ増加します。 各位置は新しい文字として扱われ、重複検索はトリガーされません。 

次のような非連続パターンで文字が繰り返される場合`ABACADA`、真に新しいシンボルの導入のみが個別カウントを増加させるため、プレフィックス比較は依然として各ステップで新規性を正確に分離します。
