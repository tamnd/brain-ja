 ## 解決策
 ## 問題の理解

 バイナリ文字列とターゲットの実数値が与えられます$F$0 と 1 の間。任意の部分文字列について、1 の小数部分を次のように計算できます。$\frac{\#1}{\text{length}}$。 タスクは、1 の小数部分が次の値に最も近い部分文字列を見つけることです。$F$、すべての最適な部分文字列の中で、最小の開始インデックスを返さなければなりません。 

したがって、問題は固定長のウィンドウや単一の目標合計を見つけることではありません。 すべての部分文字列の長さが許可されるため、直接実行すると検索スペースが 2 次になります。 

入力サイズが重要な制約です。 と$N$500,000 までの場合、すべての部分文字列を検査するソリューションは不可能です。 平$O(N^2)$部分文字列ごとに一定の作業を行うと、約$10^{11}$限界をはるかに超えた最悪の場合の操作。 これにより、問題を、テスト ケースごとに線形または線形に近い時間で解決できるものに削減する必要が直ちに生じます。 

微妙な困難は次のような事実から生じます。$F$小数点以下 6 桁の 10 進数として指定されます。 これは浮動小数点数の比較問題ではありません。 比率を直接比較すると、浮動エラーが原因で正確性が損なわれてしまいます。 もう 1 つの問題は、複数の部分文字列が同じ最適距離を達成できるため、最も早い開始インデックスを選択する必要があることです。つまり、スキャン中にタイブレークを慎重に処理する必要があります。 

長さを固定して移動しようとする単純なスライディング ウィンドウのアプローチも失敗します。最適な部分文字列の長さは入力構造に依存し、少数の候補セットに制限されないためです。 

## アプローチ

 ブルートフォースのアイデアは簡単です。すべての部分文字列を列挙します。$[l, r]$、その中の 1 の数を計算し、分数を評価し、からの距離を測定します。$F$。 これは、考えられるすべての候補をチェックするため、正しいです。 問題はコストです。 がある$O(N^2)$部分文字列、さらにはプレフィックスの合計で各カウントが作成されます$O(1)$、テスト ケースごとの合計作業量は 2 次になります。 のために$N = 5 \cdot 10^5$、これはまったく不可能です。 

重要な観察は、実際には分数自体を気にするのではなく、それが固定値にどれだけ近いかを気にするということです。$F$。 これにより、問題は絶対差を最小化することに変わります。$$\left|\frac{\text{ones}}{len} - F\right|$$これを書き直すと端数が削除されます。 両辺に次の値を掛けます$len$:$$|\text{ones} - F \cdot len|$$ここで問題は、すべての部分文字列に対して値が必要になるということです。$\text{ones} - F \cdot len$できるだけゼロに近づけること。 

させて$A[i]$「1」の場合は 1、「0」の場合は 0 になります。 変換された配列を定義します。$$B[i] = A[i] - F$$次に、任意の部分文字列に対して$[l, r]$:$$\sum_{i=l}^r B[i] = \text{ones} - F \cdot len$$したがって、タスクは、合計がゼロに最も近い部分配列を見つけることになります。 

これは現在、古典的なプレフィックス合計ジオメトリ問題です。 させて$P[i]$のプレフィックスの合計になる$B$。 この場合、部分文字列の合計は次のようになります。$P[r] - P[l-1]$。 値が最も近い 2 つのプレフィックスの合計が必要です。 

追加の制約として、最小の開始インデックスを返さなければならないため、2 つの差が等しい場合には同点を注意深く追跡する必要があります。 

効率的に解くために、すべてのプレフィックスの合計を値でソートして維持します。 繰り返していくうちに$r$、挿入します$P[r]$そして、最も近い既存のプレフィックス合計をクエリします。 これはバランスの取れた BST 問題であり、ソートされたリストと二分探索を使用して実装できます。 

各ステップでは、現在の右境界に最適な左境界が得られます。 これにより、$O(N \log N)$テストケースごとのソリューション。

 | 最適 (プレフィックス + 順序付きセット) |$O(N \log N)$|$O(N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 比率の問題をプレフィックス合計の近さの問題に変換し、プレフィックス合計の動的なセットを維持します。 

1. 入力文字列を、各文字が 1 または 0 を表す配列に変換し、減算します。$F$それぞれの立場から概念的に。 浮動小数点を格納する代わりに、固定乗数 (通常は$10^6$）。 
2. プレフィックス合計を構築する$P[i]$ここで、各ステップは変換された値を加算します。 また、$P[0] = 0$。 各部分文字列の合計は、2 つのプレフィックス値の差になります。 
3. 以前に確認されたプレフィックス合計のソートされた構造を維持します。 格納された各要素は、以前の位置に対応します。$l-1$、現在の位置で終わる部分文字列の開始インデックスを表します。 
4. 各右端点について$r$、計算する$P[r]$そして、ソートされた構造内で最も近いプレフィックス合計値を検索します。 最適な左境界候補は、プレフィックスの合計が直前または直後にある境界です。$P[r]$ソートされた順序で。 ソートされたセット内の最も近い値は常に隣接する値の中にあるため、これで十分です。 
5. 各候補プレフィックスの合計について、絶対差を計算します。$|P[r] - P[l-1]|$。 これまでに確認された最小の差を追跡します。 同じ差が複数回現れる場合は、最小値を維持します$l$。 
6.挿入$P[r]$ソートされた構造に移動して続行します。 

### なぜ効果があるのか

 任意の固定右エンドポイントで$r$、で終わる最適な部分文字列$r$プレフィックスの合計を選択することによって決定されます$P[l-1]$に最も近いのは$P[r]$。 で終わるすべての可能な部分文字列があるため、$r$以前のすべてのプレフィックス合計に正確に対応する場合、最適な選択は、ソートされた順序で最も近いものでなければなりません。 これにより、候補者を決して見逃さず、すべてをスキャンすることが保証されます。$r$すべての部分文字列が接頭辞の違いを通じて間接的に考慮されるようにします。 タイブレーク ルールは、差が一致する場合に、より小さい開始インデックスを明示的に優先することによって維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(n, f_str, s):
    # scale F to integer
    F = int(f_str.split('.')[1])
    SCALE = 10**6

    # prefix sums of (1 if '1' else 0) * SCALE - F
    # instead we store scaled difference directly
    pref = 0

    # we maintain sorted list of (prefix_value, index)
    import bisect
    arr = [(0, 0)]

    best_diff = None
    best_l = 0

    for r in range(1, n + 1):
        c = 1 if s[r - 1] == '1' else 0
        pref += c * SCALE - F

        pos = bisect.bisect_left(arr, (pref, -10**18))

        candidates = []
        if pos < len(arr):
            candidates.append(arr[pos])
        if pos > 0:
            candidates.append(arr[pos - 1])

        for val, idx in candidates:
            diff = abs(pref - val)
            l = idx + 1

            if best_diff is None or diff < best_diff or (diff == best_diff and l < best_l):
                best_diff = diff
                best_l = l

        bisect.insort(arr, (pref, r))

    return best_l

def main():
    T = int(input())
    for tc in range(1, T + 1):
        n, f = input().split()
        n = int(n)
        s = input().strip()
        ans = solve_case(n, f, s)
        print(f"Case #{tc}: {ans}")

if __name__ == "__main__":
    main()
```この実装は、ソートされたリストでプレフィックスの合計を維持することに依存しています。 サブストリングの開始位置を再構築する必要があるため、キーの詳細にはプレフィックス値とそのインデックスの両方が保存されます。 二分探索では、現在のプレフィックスが挿入される場所が検索され、絶対差を最小化できる唯一の候補であるため、隣接する 2 つのみをチェックします。 

よくある落とし穴は、スケーリングの処理です。$F$。 小数部分を抽出し、基数の整数として扱います。$10^6$、すべての算術が整数のままであることを保証します。 もう 1 つの微妙な問題は、プレフィックス セットの初期化です。$(0,0)$、インデックス 1 から始まる部分文字列が許可されます。

def run(inp: str) -> str:

    output = []

    def solve():
        T = int(input())

            n, f = input().split()
            n = int(n)

            F = int(f.split('.')[1])

 ## 特殊なケース

 エッジケースの 1 つは次のような場合です$F = 0$。 この場合、事実上、可能な限り少ないサブストリングを見つけようとしています。 プレフィックスの違いは 1 の数のみによって支配されるようになるため、変換は引き続き機能します。 多くの部分文字列が同一の最小偏差を持つため、アルゴリズムは正確に最も早い位置を優先します。 

もう一つのエッジケースは、$F = 1$ここで、1 の密度が最も高い部分文字列が必要です。 ここでは、変換された値により動作が逆転しますが、プレフィックスの差の最小化は依然として同じ最近接プレフィックスの問題に帰着します。 完全に 1 で構成される部分文字列では当然差はゼロになり、そのような最も古い部分文字列が正しく選択されます。 

最後の微妙なケースは、スケーリング後に複数のプレフィックスの合計が非常に近い場合、特に浮動小数点表現の場合に発生します。$F$は正確ですが、算術丸めにより誤差が蓄積される可能性があります。 すべての操作を整数スケールに保つことで、アルゴリズムはドリフトを完全に回避し、大規模な操作であっても一貫した比較を保証します。$N$。
