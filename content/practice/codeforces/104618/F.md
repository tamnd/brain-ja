 ## 解決策
 ## 問題の理解

 材料のコレクションが与えられていますが、各材料には 2 つの入手方法があります。 固定価格で直接購入することも、他の材料を組み合わせて製造することもでき、それら自体を購入または製造することもできます。 すべての生産ステップで必要な副成分が消費されるため、アイテムの生産コストはその依存関係の合計となり、異なる構造間での再利用や共有はありません。 

すべての成分の中には、必須ターゲットとしてマークされているものもあります。 このタスクは、直接購入と比較してコストを削減できる可能性のある組み合わせルールを利用して、必要な対象成分をすべて入手するために必要な最小総コストを計算することです。 

入力によって誘導される構造は、有向非循環依存関係グラフです。各成分は、それを構築するために必要な成分を指します。 直接的または間接的に、どの成分もそれ自体に依存できないという保証により、循環システムではなく DAG に取り組んでいることが保証されます。 

制約は大きく、最大 100,000 個のコンポーネントと合計 300,000 個の依存関係のサイズがあります。 これにより、メモ化せずに再帰的にコストを再計算したり、二次形式で更新を繰り返し伝播したりするアプローチは除外されます。 どのソリューションでも、基本的に各依存関係エッジを一定の回数処理する必要があります。 

微妙な失敗例は、コンポーネントを購入するよりも構築する方が安い場合に発生しますが、それは依存関係の連鎖によってのみ発生します。 直接の子だけを比較する単純なアプローチは失敗します。 もう 1 つの落とし穴は、共有サブツリーのコストを繰り返し再計算することです。これは、最悪の場合、簡単に爆発的に時間がかかる可能性があります。 

次の単純なシナリオを考えてみましょう。 

入力:```
2 3
A B
A 10 0
B 100 1 A
C 1 0
```正解は 110 です。 B を計算するときに A の最も安価な計算コストを使用することを忘れ、代わりに依存関係を独立して処理したり、A を複数回再計算したりすると、オーバーカウントまたはタイムアウトになります。 

もう 1 つのエッジ ケースは、購入が常に作成よりも悪い場合ですが、複数のレイヤーを経て初めて明らかになる場合です。 グローバルな伝播を伴わない各ノードでの貪欲なローカル決定は、ここでは失敗します。 

## アプローチ

 ブルートフォース解釈は簡単です。 各材料について、両方のオプションを試してコストを計算します。つまり、材料を直接購入するか、必要な材料のコストを再帰的に合計します。 次に、ターゲット成分ごとに、計算されたコストを合計します。 

すべての材料費の定義が正確に尊重されるため、これは原則として正しいです。 ただし、再帰では同じノードが何度も再訪されます。 長さ N のチェーン状の依存関係グラフでは、各呼び出しが別の完全な走査に拡張され、最悪の場合は指数関数的な再計算が発生します。 メモ化を行ったとしても、不注意な実装では、文字列の検索や解析の繰り返しにより、依存関係が繰り返し再検討される可能性があります。 

重要な観察は、依存構造が DAG であるため、各成分のコストはトポロジカルな順序で以前に計算可能な成分にのみ依存するということです。 材料の最小コストを計算したら、再計算する必要はありません。 

これにより、問題は DAG 上の最短パスのような伝播に変換され、各ノードの値はすでに最終化された隣接ノードから計算されます。 ノードをトポロジー順に処理するか、同様に、各ノードが 1 回評価されるようにするメモ化された DFS を使用します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(exp) 最悪の場合 | O(N) 再帰 | 遅すぎる |
 | 最適 (DAG DP / トポロジカル DP) | O(N + E) | O(N + E) | 承認済み |

 ## アルゴリズムのチュートリアル

 各成分をノードとしてモデル化します。 各ノードには基本コスト (購入価格) と依存関係のリストがあります。 目標は、各ノードの達成可能な最小コストを計算することです。 

1. すべての成分を解析し、それぞれに一意の識別子を割り当てます。 これにより、文字列比較を繰り返す代わりに、高速なインデックス作成が可能になります。 これが重要なのは、文字列ベースの辞書検索が大規模な実行時間の大半を占めることになるからです。 
2. 依存関係グラフを構築します。 材料ごとに、その構築に必要な材料のリストを保存します。 また、各ノードの入次数 (ノードが持つ依存関係の数) も計算します。 
3. 各ノードのコストを直接購入価格で初期化します。 これは、クラフトを完全に無視するベースライン オプションを表します。 
4. 依存関係がゼロのすべてのノードで処理キューを準備します。 これらは購入することしかできない食材なので、コストは最初から確定しています。 
5. キュー順にノードを処理します。 各ノード u について、その計算されたコストを固定として扱います。 次に、u に依存するすべての成分 v について、u の最終的なコスト寄与を使用して v のコストを緩和しようとします。 具体的には、各 v についてその依存関係コストの累計を維持し、すべての依存関係が処理されたら、この合計を直接購入価格と比較します。 
6. ノードのすべての依存関係が処理されたら、ノードの完全な作成コストを依存関係コストの合計として計算します。 最終コストは作成コストと購入コストの最小値に設定します。 
7. 依存関係が完全に解決されたノードをキューにプッシュし、すべてのノードが処理されるまで続行します。 
8. 最後に、必要なすべてのターゲット成分の計算されたコストを合計します。 

重要なアイデアは、すべてのコンポーネントはその依存関係がすべてわかった後でのみ評価され、計算された作成コストの正確性が保証されるということです。 

### なぜ効果があるのか

維持される不変条件は、ノードが処理されるときに、そのすべての依存関係で最終的な最小コストがすでに計算されていることです。 グラフは非巡回であるため、トポロジカルな順序付けが存在し、キューベースのプロセスはまさにそのような順序付けを強制します。 したがって、材料のコストを計算するとき、使用されるすべての副材料のコストはすでに最適になっており、今後の更新によってさらにコストを削減することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import defaultdict, deque

def solve():
    n, m = map(int, input().split())
    targets = input().split()

    idx = {}
    price = [0] * m
    indeg = [0] * m
    deps = [[] for _ in range(m)]
    rev = [[] for _ in range(m)]

    for i in range(m):
        parts = input().split()
        name = parts[0]
        p = int(parts[1])
        g = int(parts[2])

        idx[name] = i
        price[i] = p
        indeg[i] = g

        for j in range(g):
            child = parts[3 + j]
            deps[i].append(child)

    # convert deps to indices and build reverse graph
    for i in range(m):
        new_list = []
        for name in deps[i]:
            new_list.append(idx[name])
            rev[idx[name]].append(i)
        deps[i] = new_list

    sum_dep = [0] * m
    q = deque()

    for i in range(m):
        if indeg[i] == 0:
            q.append(i)

    # topological processing
    while q:
        u = q.popleft()

        for v in rev[u]:
            sum_dep[v] += price[u]
            indeg[v] -= 1
            if indeg[v] == 0:
                # v is ready: decide its final cost
                price[v] = min(price[v], sum_dep[v])
                q.append(v)

    ans = 0
    for t in targets:
        ans += price[idx[t]]

    print(ans)

if __name__ == "__main__":
    solve()
```実装は、グラフ操作を効率化するために、成分名をインデックスにマッピングすることから始まります。 依存関係リストは隣接形式に変換されるため、補完を上方に伝播できます。 の`sum_dep`配列は、すでに処理された依存関係のコスト寄与を累積します。 

微妙な点は、ノードの次数がゼロになった場合にのみノードのコストを最終決定するということです。 これにより、購入するよりも作成する方が安いかどうかを判断する前に、必要なコンポーネントをすべて確認できます。 

最後の合計ステップでは、すべてのターゲット成分の計算されたコストを取得するだけです。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N + E) | 各成分と依存関係はトポロジカルな順序で 1 回処理されます。 
| スペース | O(N + E) | グラフ ストレージに加えて、次数と累積のための補助配列 |

 ## 特殊なケース

 特殊なケースの 1 つは、作成が有効であるにもかかわらず、材料を作成するよりも購入した方が厳密に安い場合です。 たとえば、アイテムに高価な依存関係がある場合でも、最終ステップで両方のオプションを比較するため、アルゴリズムは購入コストを正しく選択します。 

もう 1 つのケースは、長い依存関係チェーンです。 このアルゴリズムは各ノードをトポロジー順に 1 回だけ処理するため、長さが 100,000 のチェーンであっても再帰や繰り返し作業が発生しません。 

最後のエッジケースは、複数の依存関係が 1 つのノードに収束することです。 以来`sum_dep`各依存関係が処理された後にのみ貢献度を集計するため、最終コストには依存関係ごとに 1 回だけ全額が反映され、二重カウントが回避されます。
