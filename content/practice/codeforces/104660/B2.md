 ## 解決策
 ## 問題の理解

 このタスクは 10 進数の文字列を扱います。各桁は、概念的な入れ子構造の「深さ」を表します。 単に数字を出力するのではなく、現在アクティブな開き括弧の数が各位置の数字の値と一致するように数字を括弧で囲みたいと考えてみましょう。 

それぞれの文字列が与えられます。`'0'`に`'9'`。 元の数字を含む別の文字列を作成する必要がありますが、追加の数字が含まれます。`'('`そして`')'`左から右にスキャンしたときに、各桁の直前にある一致しない開き括弧の数がその桁の値と等しくなるように挿入されます。 

したがって、出力は値の変換ではなく、構造的なエンコードです。括弧は、すべての位置で数字ストリームを正確に追跡する必要がある動的な深さを定義します。 

入力サイズは文字列の長さに対して線形であるため、実行可能な解決策は線形または線形に近いものだけです。 すべての文字のネストを最初から再計算する試みは、慎重に実装されていれば、漸近性の観点からすでに許容可能ですが、ループ内で文字列の再構築を繰り返すと、不変性と連結の繰り返しにより二次関数の動作に劣化します。 

桁数が急激に減少する場合、微妙なエッジケースが発生します。 たとえば、次のような入力を考えてみましょう。`321`。 単純なアプローチでは、必要なときにのみ括弧を開き、次の数字を出力する前に十分なレイヤーを閉じるのを忘れて、ある時点でアクティブな括弧が多すぎるなど、無効な中間ネストが発生する可能性があります。 もう 1 つの一般的な失敗は、次のような先頭のゼロで発生します。`0000`。 正しい出力には括弧がまったく含まれていない必要がありますが、不注意な実装では依然として空のペアまたは不一致のクロージャが出力されることがよくあります。 

## アプローチ

 この問題についての素朴な考え方は、それぞれの立場を独立して扱うことです。 数字ごとに、プレフィックスを再度スキャンし、ネストが「あるべき」ものを数えることにより、必要な括弧の数を再構築して、数字を出力する前に必要な開閉数を出力することができます。 要件はすべてのインデックスでのローカル整合性であるため、これは論理的に機能しますが、各ステップでプレフィックスを再スキャンしたり、シミュレートされたスタックを繰り返し調整したりする可能性があるため、コストがかかります。 最悪の場合、これは二次的な動作につながります。これは、各キャラクタについて、前の構造をトラバースすることによって深度を再計算する可能性があるためです。 

重要な観察は、望ましい構造が連続する数字間の違いによって完全に決定されるということです。 絶対深度を最初から再計算する必要はありません。 代わりに、左から右にスキャンしながら現在の深さを維持します。 次の数字が現在の深さよりも大きい場合は、開き括弧を追加するだけです。 小さい場合は括弧を閉じます。 等しい場合は何もしません。 これにより、グローバル制約が隣接する文字間のローカル遷移ルール​​に変換されます。 

これが機能するのは、括弧の構造がセグメント内で単調であるためです。一度深さを増やすと、減少によって強制的に閉じるまでそのレベルに留まります。 したがって、全体の構造は、単一の整数を追跡し、各ステップで最小限の調整を行うことになります。

 ## アルゴリズムのチュートリアル

 変数を維持しながら文字列を左から右に処理します。`depth`現在アクティブな開き括弧の数を表します。 

1.初期化`depth = 0`そして空の出力バッファー。 
2. キャラクターごとに`c`文字列内で整数に変換します`target`。 
3. もし`target > depth`、追加`target - depth`括弧を開けて増加`depth`に`target`。 これにより、数字を配置する前に十分なネストを構築できるようになります。 
4. もし`target < depth`、追加`depth - target`閉じ括弧と減少`depth`に`target`。 これにより、ネストが安全に削減され、現在の桁が必要な深さと一致します。 
5. 数字自体を追加します。 
6. すべての数字を処理した後、次の場合は`depth > 0`、残りの閉じ括弧を追加して、構造のバランスを完全に整えます。 

重要な考え方は、各桁を処理した後、開き括弧の数がその桁に等しいという不変条件を決して破らないということです。 

### なぜ効果があるのか

 どの位置でも、アルゴリズムはアクティブなネストの深さが書き込まれる数字と同じになるように強制します。 明示的に開き括弧または閉じ括弧を使用して深さを調整するだけであり、すべての調整が連続するターゲット間の差異に正確に一致するため、不必要な構造が導入されることはありません。 最後のクリーンアップ手順により、全体的なバランスが確保されます。 各遷移は 2 つの隣接する必要な状態間で最適に処理されるため、位置ごとの深さの制約を満たしながら括弧の数を減らすことのできる代替配置はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    res = []
    depth = 0

    for ch in s:
        target = ord(ch) - ord('0')

        while depth < target:
            res.append('(')
            depth += 1

        while depth > target:
            res.append(')')
            depth -= 1

        res.append(ch)

    while depth > 0:
        res.append(')')
        depth -= 1

    print(''.join(res))

if __name__ == "__main__":
    solve()
```実装は深度追跡戦略に直接従います。 2 つの while ループは、ネストの違いを明示的に照合することで、連続する数字間の遷移を処理します。 出力の蓄積にリストを使用すると、文字列の連結が繰り返されることによる二次的な動作が回避されます。 最後のループは、開いたすべての括弧が適切に閉じられていることを保証します。これは、最後の桁が 0 より大きい場合に必要です。

 ## 特殊なケース

 のような入力の場合`0`の場合、アルゴリズムはどちらのループにも入らず、出力はプレーンな数字ストリームのままになります。 これにより、深さゼロが中立状態として扱われることが確認されます。 

次のような減少シーケンスの場合、`210`、アルゴリズムはまず、一致するように深さを増やします。`2`、次に移動するとすぐに 1 つのレベルを閉じます。`1`に達すると残りのレベルをすべて閉じます。`0`。 これは、クロージャが隣接する数字間の差によって純粋に駆動され、遷移間でネストが残らないようにすることを示しています。
