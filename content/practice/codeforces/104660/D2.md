 ## 解決策
 ## 問題の理解

 私たちは隠されたバイナリ配列を操作しており、その内容を再構築する必要があります。 配列は固定長ですが、最初はその値がわかりません。 個々の位置をクエリし、そこに保存されているビットを受け取ることができます。 

この相互作用にはさらに複雑な問題があります。 10 個のクエリのブロックごとに、非表示配列は 4 つの方法のいずれかでジャッジによって変換されます。変更されないままにするか、反転するか、すべてのビットを反転するか、反転と反転の両方を行うことができます。 私たちは、いつ、どのような変化が起こるのかについては知りません。 唯一の保証は、10 回のクエリごとに、毎回独立してこの問題が発生する可能性があることです。 

目標は、限られた数のクエリを使用して配列全体を正しく回復することです。 すべてのクエリは高価であり、配列が大きくなる可能性があるため、変換を考慮せずに位置を繰り返し調査する単純な戦略は失敗します。これは、位置に関する以前の知識が、隠された変更後に無効になる可能性があるためです。 

固定クエリ間隔の後にのみ変換が発生するという制約が、重要な構造上の制限です。 これは、10 個のクエリのブロック内では配列が安定しており、不一致がブロック境界でのみ発生することを意味します。 これは、正確さが変換を迅速に検出し、内部ビューを再同期することに依存していることを示唆しています。 

単純なアプローチでは、左から右に位置を繰り返しクエリし、値が有効なままであると想定します。 これは単純なシナリオでは失敗します。 位置 1 が 0 であると学習したとします。10 回のクエリの後、配列が反転されるため、位置 1 は 1 になります。元の値を仮定し続けると、配列が誤って再構築されてしまいます。 逆転でも同じ問題が発生し、対称推論が壊れます。 

別の失敗ケースは、変更が発生していないにもかかわらず、変更があったと想定する場合に発生します。 10 回のクエリごとに配列をやみくもに「修正」すると、保存された状態が誤って反転または反転され、エラーが悪化する可能性があります。 

中心的な課題は、効率的にクエリを実行することではなく、未知のグローバル変換の下で配列の一貫したビューを維持することです。 

## アプローチ

 ブルートフォース戦略では、不確実性が現れるたびにすべてのポジションを繰り返しクエリします。 疑わしい変換が行われるたびに、配列全体を再読み取りして再構築を再開することを想像することもできます。 これはアレイの現在の状態を常に反映するため、原理的には正しいですが、遅すぎます。 配列の長さが N で、変換が頻繁に発生する可能性がある場合、配列を繰り返し再スキャンすると、最悪の場合、O(N^2) クエリが発生し、すぐに制限を超えます。 

重要な洞察は、変換のたびにすべてを再構築する必要はないということです。 代わりに、どの変換が発生したかを検出するだけで済みます。 可能性は 4 つしかないため、慎重に選択した一定数のプローブを使用して変化を特定できます。 

配列の左端と右端からのインデックスの対称ペアを維持します。 位置をクエリするとき、(i, n−i+1) のようなペアを保存します。 これらのペアのうち、等しいビットを含む 1 つのペアと、異なるビットを含む 1 つのペアを追跡します。 これら 2 つの参照ペアにより、考えられるすべての変換を検出できます。 

変換後にこれらの参照位置を再度クエリすると、新しい値と保存されている値を比較することで、反転が発生したか、反転が発生したか、両方が発生したか、または何も起こらなかったのかがわかります。 特定されたら、すべてを再計算するのではなく、それに応じて内部表現を更新します。 

これにより、完全な再構築の繰り返しの問題が、定期的な O(1) 修正オーバーヘッドによる増分メンテナンスに軽減されます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(N^2) | O(N) | 遅すぎる |
 | 最適 | O(N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

配列の長さは B で、最大 150 個のクエリが許可されると仮定します。 

1. 2 つのポインタを初期化します。左は 1、右は B です。これらは、両方をクエリすることで反転に関する不確実性が軽減されるため、一緒に埋める対称位置を表します。 
2. 私たちは 2 つの特別なトラッカーを維持します。1 つのペアは等しいビットが観察されたもので、もう 1 つのペアは異なるビットが観察されたものです。 これらは、後で変換を検出するのに役立ちます。 
3. クエリをバッチで実行し、現在の 10 個のブロック内で実行されたクエリの数を常に追跡します。 変換はまさにこれらの境界で発生する可能性があるため、これは重要です。 
4. 各ステップで、まだ解決されていない限り、左右の位置を照会します。 私たちは彼らの価値観を保存し、内側に向かって進みます。 等しいビットまたは異なるビットを持つペアを発見すると、それらのインデックスを潜在的なアンカーとして記録します。 
5. 10 個のクエリのセットごとに、検出フェーズを実行します。 保存されている等価ペア インデックスと異なるペア インデックスを再クエリします。 これらの値は、以前に保存した値と比較されます。 
6. 比較に基づいて、4 つの変換のうちどれが発生したかを判断します。 等しい関係と異なる関係の両方が一貫したままであれば、変化は発生しません。 両方が反転している場合、補数が検出されます。 ポジションが一貫して入れ替わる場合、反転が検出されます。 両方の効果が現れる場合、逆プラス補体を検出します。 
7. 変換が特定されたら、それに応じて保存されているすべての既知の値を更新します。 補数の場合は、保存されているすべてのビットを反転します。 反転するには、保存された構造内の対称位置を交換します。 これにより、内部モデルが非表示の配列と一致した状態に保たれます。 
8. すべての位置が埋まるまでこのプロセスを続け、その後、再構成された配列を出力します。 

### なぜ効果があるのか

 正しさは、裁判官によって適用された変換がグローバル操作の小さな閉じたセットに属しているという事実に依存します。 これらの操作はグループを形成し、各アクションは反転可能であり、対称および非対称の既知のペア間の比較を使用して検出可能です。 検出を少なくとも 1 つの等しいペアと 1 つの異なるペアに固定することで、すべての変換がこれらの参照上に一意の署名を生成することを保証します。 これによりあいまいさが防止され、配列の状態を誤って分類することがなくなり、プロセス全体で再構築の一貫性が保たれます。 

## Python ソリューション```python
import sys

input = sys.stdin.readline

def solve():
    B = 20  # in real interactive problems this is given; placeholder for structure

    a = [-1] * (B + 1)
    l, r = 1, B

    same_idx = None
    diff_idx = None

    qcount = 0

    def query(i):
        nonlocal qcount
        qcount += 1
        print(i)
        sys.stdout.flush()
        return int(input().strip())

    def apply_flip():
        for i in range(1, B + 1):
            if a[i] != -1:
                a[i] ^= 1

    def apply_reverse():
        nonlocal a
        na = a[:]
        for i in range(1, B + 1):
            if a[i] != -1:
                na[B - i + 1] = a[i]
        a = na

    while l <= r:
        if qcount > 0 and qcount % 10 == 0:
            x = query(1)
            y = query(1)

            if same_idx is not None:
                s = query(same_idx)
            else:
                s = 0
            if diff_idx is not None:
                d = query(diff_idx)
            else:
                d = 0

            if same_idx is not None and diff_idx is not None:
                old_s = a[same_idx]
                old_d = a[diff_idx]
                same_now = s
                diff_now = d

                if old_s == same_now and old_d == diff_now:
                    pass
                elif old_s != same_now and old_d != diff_now:
                    for i in range(1, B + 1):
                        if a[i] != -1:
                            a[i] ^= 1
                else:
                    a = a[::-1]

        if l > r:
            break

        lv = query(l)
        rv = query(r)

        a[l] = lv
        a[r] = rv

        if lv == rv and same_idx is None:
            same_idx = l
        if lv != rv and diff_idx is None:
            diff_idx = l

        l += 1
        r -= 1

    print("".join(str(a[i]) for i in range(1, B + 1)))
    sys.stdout.flush()

if __name__ == "__main__":
    solve()
```コードは、配列の対称位置を埋める 2 つのポインターを保持します。 この対称性により、すべてを最初から再計算することなく反転処理が可能になります。 

変換検出ロジックは、クエリ数が 10 の倍数に達するたびにトリガーされます。 その時点で、以前に保存された参照インデックスを再確認します。 現在の応答を保存された値と比較することで、補完または反転が発生したかどうかを推測できます。 

最も重要な実装の詳細は、一貫した参照ペアを維持することです。 少なくとも 1 つの等しいペアと 1 つの不等なペアを早い段階で記録できなかった場合、後で変換を区別する能力が失われます。 

もう 1 つの微妙な点は、内部配列の更新では反転と補完の両方を独立して考慮する必要があることです。 これらの操作を誤って組み合わせることが、バグの最も一般的な原因です。 

## 実用的な例

 長さ 6 の単純化された配列を考えてみましょう。`1 0 0 1 1 0`。 

対称的にクエリを実行します。 

| ステップ | クエリ | 応答 | 既知の状態 |
 | --- | --- | --- | --- |
 | 1 | 1 | 1 | [1, _, _, _, _, _] |
 | 2 | 6 | 0 | [1, _, _, _, _, 0] |
 | 3 | 2 | 0 | [1, 0, _, _, _, 0] |
 | 4 | 5 | 1 | [1, 0, _, _, 1, 0] |

 10 回のクエリの後、反転が発生したとします。 

| ステップ | リファレンスチェック | 保存済み | 新しい | 推論 |
 | --- | --- | --- | --- | --- |
 | 同じペア | 1 | 1 | 0 | 変更されました |
 | 差分ペア | 0 | 0 | 1 | 変更されました |

 両方が反転していることは、補数演算を意味します。 

これにより、変更がどこで発生したかが分からなくても、参照比較を通じてグローバルな一貫性を回復できることが確認されます。

 ## 特殊なケース

 エッジ ケースの 1 つは、アレイが完全に対称または完全に非対称である場合に発生します。 このような場合、「同じ」参照ペアと「異なる」参照ペアの両方を早期に見つけるのは難しい場合があります。 アルゴリズムは、両方のタイプが観察されるまで変換検出を遅らせることでこれを処理し、不完全な情報に基づいて正確さが決してないことを保証します。 

もう 1 つのエッジ ケースは、複数の変換が連続して発生する場合です。 検出は 10 クエリごとに実行されるため、各変換は段階的に吸収されます。 参照チェックは常に現在の状態を反映するため、蓄積された変更によって再構築プロセスが非同期になることはありません。
