 ## 解決策
 ## 問題の理解

 一連の時間間隔が与えられ、それぞれが 2 人のうちの 1 人に割り当てられるアクティビティを表します。 各アクティビティには開始時刻と終了時刻があり、割り当てでは、1 人に 2 つの重複するアクティビティが割り当てられないようにする必要があります。 2 つのアクティビティは、一方が開始する前に終了した場合にのみ、同じ人に対して互換性があります。 

ここでの課題は、すべての間隔を 2 人のうちの 1 人に割り当てることが可能かどうかを判断することです。 可能であれば、2 人に対して 2 つの異なるラベルを使用して、各文字が入力順序の間隔に対応する文字列を出力する必要があります。 それが不可能な場合は、有効な割り当てが存在しないことを出力します。 

入力構造は間隔のリストであり、出力は各間隔のラベル付けです。 重要な制約は、どの時点においても、各人が最大 1 つの進行中のインターバルを処理できるということです。 

制約の観点から見ると、区間の数が十分に大きいため、二次関数のアプローチは失敗します。 すべての間隔のペアをチェックしようとしたり、割り当てごとに競合を繰り返しスキャンしようとしたりするソリューションは O(n²) まで低下します。これは、n が 10⁵ 程度の場合には遅すぎます。 これにより、ソートと一定時間の割り当ての決定を伴う貪欲な戦略に向かうことになります。 

いくつかの特殊なケースは間違いやすいものです。 すべての区間が共通点で重なっている場合、たとえば [1,4]、[2,5]、[3,6] である場合、区間は 3 つありますが、人は 2 人しかいないため、答えは不可能になります。 空き状況を注意深く追跡しない単純な貪欲な人は、割り当てを誤って上書きしたり、1 人が重複する 2 つの間隔を取得できると想定したりする可能性があります。 

もう 1 つの微妙なケースは、間隔がエンドポイントで接触する場合に発生します。 たとえば、[1,3] と [3,5] は重複せず、同じ人に割り当てることができます。 終了時刻を包括的な重複として扱う不用意な実装は、有効なスケジュールを誤って拒否する可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、2 人に対する間隔の可能な割り当てをすべて試みます。 各間隔には 2 つの選択肢があるため、割り当ては 2ⁿ あります。 割り当てごとに、誰かが重複する間隔を持っているかどうかを確認しますが、これ自体で並べ替えまたはペアごとのチェックが必要です。 効率的なチェックを行ったとしても、検索スペースは指数関数的に増大し、非常に小さな入力を超えると実行不可能になります。 

重要な観察は、制約が時間的にローカルであるということです。 どの時点でも、現在アクティブなインターバルのみが重要であり、利用可能な人は 2 人しかいないため、一度に 2 つ以上のインターバルが重ならないようにすることだけが必要です。 これは、間隔を時系列で処理し、現在空いている人を維持することを示唆しています。 

間隔を開始時間で並べ替えることで、間隔を処理するときに、競合する可能性のある以前のすべての間隔がすでに割り当てられていることを確認します。 次に、可能な人にインターバルを貪欲に割り当てます。 どちらも利用できない場合は、すぐに割り当ては不可能であると結論付けます。 

これにより、問題は指数関数的な検索から、2 つの利用可能時間を記録する単一パスの割り当てに軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2ⁿ・n) | O(n) | 遅すぎる |
 | 最適な貪欲さ | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ステップ

1. 出力はソート順ではなく入力順に従う必要があるため、元のインデックスを維持しながらすべての間隔を読み取ります。 
2. 間隔を開始時間で並べ替えます。 並べ替えにより、常に早い開始間隔が最初に割り当てられるため、以前には見られなかった早い競合をブロックする決定を下すことはありません。 
3. 各人がいつ自由になるかを表す 2 つの変数を維持します。 最初は両方とも時間 0 で利用可能です。 
4. ソートされた順序で間隔を繰り返します。 インターバルごとに、開始時刻またはその前に最初の人が空いているかどうかを確認します。 「はい」の場合、その人にそれを割り当て、次の自由時間を間隔の終わりまで更新します。 
5. 1 人目の人が不在の場合は、2 人目の人にチェックを入れます。 利用可能な場合は、同様に割り当てます。 
6. どちらの担当者も対応できない場合は、この間隔がすでに割り当てられている 2 つの間隔と重複し、有効な割り当てが不可能になるため、すぐに終了します。 
7. すべての間隔を処理した後、保存された割り当てを元のインデックス順序で使用して応答文字列を再構築します。 

### なぜ効果があるのか

 重要な不変条件は、スイープの各ステップで、追跡された 2 つの対応可能時間が、すべての処理された間隔のうち各人に割り当てられた最後の間隔の終了時間を正確に表すということです。 開始時間を増やして処理するため、現在の間隔と競合する可能性のある間隔は、これら 2 つの状態にすでに反映されている必要があります。 間隔の開始時に両方の人が忙しい場合、その時間をカバーする重複する間隔がすでに 2 つあるため、制約に違反せずに 3 番目の間隔を割り当てることはできません。 これにより、貪欲な決定がローカルに最適化され、グローバルに安全になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    intervals = []
    for i in range(n):
        s, e = map(int, input().split())
        intervals.append((s, e, i))
    
    intervals.sort()
    
    freeC = 0
    freeJ = 0
    ans = [''] * n
    
    for s, e, i in intervals:
        if freeC <= s:
            ans[i] = 'C'
            freeC = e
        elif freeJ <= s:
            ans[i] = 'J'
            freeJ = e
        else:
            print("IMPOSSIBLE")
            return
    
    print("".join(ans))

if __name__ == "__main__":
    t = int(input())
    for _ in range(t):
        solve()
```この解決策は、開始時間によるソート後も必要な出力順序を再構築できるように、各間隔に元のインデックスを付加することから始まります。 並べ替えは、問題を時系列のスイープに変換し、間隔ごとに 1 回決定が行われるため、並べ替えが不可欠です。 

変数`freeC`そして`freeJ`各人が対応可能な最も早い時間を追跡します。 インターバルを処理するときは、インターバルの開始時刻以降に対応可能な最初の人にそのインターバルを割り当てます。 間隔の終わりまで可用性を更新すると、今後の間隔でこの割り当てが正しく尊重されるようになります。 

両方が利用できない場合の即時障害状態は非常に重要です。 このチェックを遅らせたり、後で再割り当てを試行したりすると、正確性が損なわれます。これは、並べ替えられた順序により、重複の競合が現在のステップですでに完全に露出していることが保証されるためです。

 ## 特殊なケース

 重要なエッジ ケースは、間隔がエンドポイントでのみ接触する場合です。 [1,2]、[2,3]、[3,4] のような入力の場合、アルゴリズムはこれらを重複しないものとして扱う必要があります。 私たちが使っているので、`<=`可用性を考慮して、直前の端から正確に開始する間隔が許可され、同じ人がすべての間隔を処理できます。 

もう 1 つのエッジ ケースは、すべての間隔が 1 つの点で重なる場合です。 たとえば、[1,10]、[2,9]、[3,8]などです。 最初の 2 つの間隔を別の人に割り当てた後、3 番目の間隔では時間 3 で両方の人が通話中であることがわかり、即時不可能がトリガーされます。 アルゴリズムはこれを正しく検出します。`freeC`そして`freeJ`開始時間を超過します。 

最後の微妙なケースは、間隔が任意の順序で与えられる、ソートされていない入力です。 並べ替えが不可欠なのは、並べ替えがないと可用性の追跡が意味を失い、貪欲な割り当てが順序に依存してしまい、有効なスケジュールが存在する場合でも誤った結果が生じるためです。
