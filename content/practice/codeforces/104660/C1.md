 ## 解決策
 ## 問題の理解

 2 つの同一のリソースに対してスケジュールする必要があるタスクを表す時間間隔のリストが与えられます。通常、2 人が交互に作業するものと考えられます。 各間隔には開始時刻と終了時刻があり、各タスクは 2 つのリソースのうちの 1 つに完全に割り当てられる必要があります。 リソースは一度に 1 つのタスクのみを処理できるため、割り当てられた間隔が時間的に重複してはなりません。 

目標は、競合することなく 2 つのリソース間ですべての間隔を割り当てることができるかどうかを判断することです。 可能であれば、どのリソースが各間隔を処理するかを示す有効な割り当てを出力する必要があります。 不可能な場合は、割り当てが存在しないことを出力します。 

入力サイズでは最大約 10 万の間隔が許容されるため、すべての代入を試行するソリューションは即座に除外されます。 ブルートフォース割り当てでは、間隔ごとに 2 つの選択肢が検査され、2^n 通りの可能性が生じますが、n が 20 付近を超えると実行不可能になります。各割り当て後に素朴に重複をチェックしても、さらに二次関数の動作に移行してしまい、これも遅すぎます。 

エンドポイントを共有する間隔では、微妙な問題が発生します。 たとえば、あるタスクが時刻 5 に終了し、別のタスクが時刻 5 に開始する場合、通常、それらは重複していないと見なされます。 接触間隔を重複として扱う不用意な実装は、有効なケースを誤って拒否する可能性があります。 

もう 1 つのエッジ ケースは、複数の間隔が同時に重なる場合です。 たとえば、3 つの間隔が 1 つの時点で重複する可能性があり、2 つのリソースでそれらの間隔をスケジュールすることができなくなります。 グローバルな重複構造を考慮せずに間隔を割り当てる貪欲なアプローチは、ここで失敗する可能性があります。 

## アプローチ

 強引なアイデアは、各間隔をリソース 1 またはリソース 2 のいずれかに割り当て、結果として得られる両方のスケジュールが有効かどうかを確認することです。 これは概念的には単純です。すべての 2^n 代入を試し、各グループ内での重複を回避する代入があるかどうかを確認します。 あらゆる可能性を徹底的に探索するので、正しさは明らかです。 失敗点はパフォーマンスです。 n が 100000 までの場合、割り当ての数は天文学的に多くなり、単一の割り当てを検証するだけでも O(n log n) または O(n) のコストがかかり、合計を検証するのは完全に不可能になります。 

重要な観察は、これは実際には組み合わせ検索の問題ではないということです。 構造は純粋に一時的なものです。 いつでも、アクティブなインターバルの数を知る必要があるだけです。 リソースが 2 つしかないため、3 つ以上の間隔が同時に重なると、システムはまさに失敗します。 これにより、問題は、割り当ての構築と組み合わせたスイープラインの実現可能性チェックに変換されます。 

割り当てを推測する代わりに、開始時間の昇順に間隔を処理します。 私たちは 2 つのリソースの現在の可用性を維持します。 間隔が開始されると、その時点で現在空いているリソースに間隔が割り当てられます。 両方が占有されている場合、3 つの間隔が重なっていることが検出され、不可能であると結論付けられます。 これが機能するのは、同時にアクティブな間隔が最大 2 つまで許可され、解放されたリソースが常に貪欲に再利用されるためです。 

したがって、最適な解決策は、開始時間による間隔の並べ替えと、どのリソースが最初に空きになるかを動的に追跡することに依存します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n · n) | O(n) | 遅すぎる |
 | 最適なスイープ + 貪欲な割り当て | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 競合は時間枠の重なりによって完全に決定されるため、時系列順を尊重する方法で間隔を処理します。

1. すべての間隔を読み取り、元のインデックスをアタッチして、後で出力割り当てを再構築できるようにします。 これが必要なのは、並べ替えによって元の順序が破壊されるためです。 
2. 間隔を開始時間で並べ替えます。 これにより、間隔を処理するときに、以前に開始されたすべての間隔がすでに考慮されるため、現在のオーバーラップ状態が正しく維持されます。 
3. 2 つのリソースがそれぞれいつ解放されるかを表す 2 つの変数を維持します。最初は両方とも 0 に設定されます。 
4. ソートされた順序で間隔を繰り返します。 間隔ごとに、間隔の開始時刻またはその前にリソース 1 が空いているかどうかを確認します。 その場合、この間隔をリソース 1 に割り当て、次の空き時間を間隔の終わりに更新します。 
5. リソース 1 が使用できない場合は、同様にリソース 2 を確認します。 空いている場合は、そこに間隔を割り当て、その空き状況を更新します。 
6. どちらのリソースも利用できない場合は、この間隔の開始時点で両方がまだビジーであることを意味するため、この時点では 3 つの間隔が重なっています。 その場合は日程調整が不可能となり早期終了とさせていただきます。 
7. 割り当てを元の位置でインデックス付けされた配列に保存して、入力順に出力できるようにします。 

正確さは、スイープのどの時点でも、追跡された 2 つの終了時刻が、現在アクティブな 2 つの間隔の最後の終了時刻を表すという不変条件から得られます。 新しい間隔がどちらのスロットにも収まらない場合は、3 番目の同時オーバーラップが存在することを意味し、容量制約に違反します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    intervals = []
    for i in range(n):
        s, e = map(int, input().split())
        intervals.append((s, e, i))

    intervals.sort()

    end1 = 0
    end2 = 0
    ans = [0] * n

    for s, e, i in intervals:
        if end1 <= s:
            ans[i] = 1
            end1 = e
        elif end2 <= s:
            ans[i] = 2
            end2 = e
        else:
            print("NO")
            return

    print("YES")
    print("".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```ソートのステップにより、開始時間を増やしながら常に間隔を処理することが保証され、貪欲な割り当てがリアルタイムの実現可能性と一致します。 2 つの変数`end1`そして`end2`各リソースの次に利用可能な時間を表します。 小切手`end <= s`は、等価性が許可されるという意味で厳密です。つまり、時間 t で終了する間隔は、正確に t でリソースを解放します。 

よくある実装上の間違いは、元のインデックスを保持することを忘れることで、出力の順序が正しくなくなります。 もう 1 つの微妙な問題は印刷形式です。割り当ては区切り文字を使用せずに連結する必要があります。

このトレースは、重複が 2 つの使用可能なスロット間で同時間隔を分割することによって処理されることを示しています。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

| スペース | O(n) | インターバルと出力割り当てのストレージ |

 この制約により、最大 10 万間隔までのソートが快適に可能になり、その後のリニア スキャンにより効率が保証されます。 メモリ使用量は間隔の数に直線的であり、最小限に抑えられます。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    data = inp.strip().split()
    n = int(data[0])
    arr = []
    idx = 1
    for i in range(n):
        s = int(data[idx]); e = int(data[idx+1]); idx += 2
        arr.append((s, e, i))
    arr.sort()

    end1 = 0
    end2 = 0
    ans = [0] * n

    for s, e, i in arr:
        if end1 <= s:
            ans[i] = 1
            end1 = e
        elif end2 <= s:
            ans[i] = 2
            end2 = e
        else:
            return "NO"

    return "YES\n" + "".join(map(str, ans))

 ## 特殊なケース

 主なエッジケースは、間隔がエンドポイントでのみ接触する場合です。 例えば、`(1,2)`そして`(2,3)`同じリソース上でスケジュール可能である必要があります。 アルゴリズムでは、最初の間隔が時刻 2 で終了すると、`end1 = 2`、2 番目の間隔は 2 から始まるため、`end1 <= s`が保持され、再利用が有効になります。 これにより、端の等価性を非オーバーラップとして扱うことが正しいことが確認されます。 

もう 1 つの重要なケースは、常に 2 つの間隔が最大で重なることです。たとえば、`(1,10), (2,9), (3,8), (4,7)`。 このアルゴリズムは、障害を引き起こすことなく 2 つのリソース間の割り当てを交互に行い、容量 2 で十分であることを示しています。 

最後に、前の 2 つの間隔のいずれかが終了する前に 3 番目の間隔が始まると、失敗パターンが発生します。 スイープ ラインはまさにこれを捉えています。`end1`そして`end2`現在の開始時間を超過すると、制約に違反した瞬間に強制的に拒否されます。
