 ## 解決策
 ## 問題の理解

 私たちには一連の日数が与えられており、毎日、3 つの選択肢の中から 1 つのアクションを実行することができます。つまり、コーディングの問題セットをリクエストするか、ジャミングの問題セットをリクエストするか、最近リクエストされたがまだ提出されていない問題セットを提出することができます。 重要なルールは、送信が厳密なスタック規律に従うということです。つまり、種類に関係なく、最後に要求された未送信のセットを常に送信します。 

各問題セットにはコーディングまたはジャミングのいずれかのタイプがあり、各リクエストはアシスタントがコーディングまたはジャミングの既知の気分を持っている日に発生します。 問題セットの価値は、そのリクエストがその日の気分と一致するかどうかによって決まり、提出時に得られるスコアは提出日の気分がそのセットの種類と一致するかどうかによって決まり、一致しない場合はペナルティが課せられます。 

今後のすべての気分を完全に把握した上で、合計スコアを最大化するために、一日中リクエストと提出をスケジュールする必要があります。 

スタックが LIFO であるという制約が、問題を自明ではないものにしています。どの問題セットを提出するかを自由に選択することはできません。 リクエストの順序が正しくないと、価値の高い送信が永久にブロックされる可能性があります。 

入力サイズは大きく、テスト ケースあたり最大 20,000 日、テスト全体で合計 150,000 日であるため、スケジュールを超えた指数関数的な検索は排除されます。 どのソリューションも、テスト ケースごとに線形または線形に近いものでなければなりません。 

単純なアプローチでは、リクエストと送信アクションの考えられるすべてのシーケンスをシミュレートしようとします。 有効なスタック シーケンスに限定しても、インターリーブの数はカタロニア語構造のように増加し、指数関数的に増加します。 これは不可能です。 

後日の雰囲気によって、すでにリクエストされたセットの価値が向上するため、提出を遅らせることが有益である場合、微妙なエッジケースが発生します。 たとえば、コーディング セットがコーディング日中にリクエストされたが、後で別のコーディング日にのみ送信できる場合は、待つことを選択する必要がありますが、待ち時間が長すぎると、スタック順序により今後のリクエストがブロックされる可能性があります。 

## アプローチ

 主な困難は、どのタイプのセットをリクエストするか、いつ送信するかという 2 つの決定の間の相互作用です。 スタック制約は、これらの決定を時間をかけて結び付けます。 

ブルートフォース戦略は、毎日を 3 つの可能性への分岐として扱い、すべての有効な操作シーケンスをシミュレートし、スタックと累積スコアを追跡することです。 無効な状態を削除しても、個別のスタックとスケジュールの数は組み合わせ的に増加します。 最悪の場合、n/2 リクエストの後、スタックはさまざまな方法で並べ替えられる可能性があり、それぞれの構成によって将来の異なる制約が発生します。 これにより、指数関数的な複雑さが生じ、非常に小さな入力を超えると使用できなくなります。 

重要な洞察は、視点を逆転させることです。 一連の操作について考える代わりに、最終的なスケジュールをリクエスト日とサブミット日の間の一致として解釈し、各リクエストは後のサブミットと組み合わせる必要があります。 スタックは LIFO であるため、これらのペアは非交差構造を形成する必要があります。つまり、最新のリクエストが最初に一致する必要があり、バランスの取れた括弧と同等の入れ子構造を意味します。 

これにより、問題はタイムライン上で有効なペアリング構造を選択することに変わります。 各リクエストは開始括弧に似ており、各送信は終了括弧に似ており、制約により正しいネストが強制されます。 

ここで重要な観察は、固定ペアリング構造の場合、最適なタイプの決定は局所的になるということです。 各リクエストはタイプの選択に応じて基本値を提供し、各送信は、一致したリクエストによって運ばれるタイプと送信日の気分に応じて値を提供します。

したがって、問題をプッシュとポップのシーケンスを選択するものとして扱うことができますが、リクエストの合計数は送信の合計数に等しいため (日数は偶数であり、どのスコアでも最終的にすべてのセットを送信する必要があるため)、構造は、アイテムをいつスタックに保持し、いつポップするかを決定することになります。 

より直接的で強力なビューは、スタックと動的な意思決定を使用して貪欲にシミュレートすることです。私たちは何日も繰り返し、リクエストの機会が見つかったときはいつでも、それをプッシュするかどうか、あるいは将来の価値を引き出すために以前のリクエストの送信を優先するべきかを決定します。 正しい貪欲な戦略は、リクエストに適格な瞬間ごとに常にリクエストし、可能な限り常に送信しますが、各セットが最終的な送信環境に最もよく適合するようにリクエストの種類を最適に選択することです。 

これは、単純な貪欲なペアリングにさらに崩壊します。保留中のセットのスタックを維持し、それぞれに保証できる最高のスコア貢献度が注釈付けされています。提出日ごとに、最新のものをポップし、貪欲な構築によって暗黙的にエンコードされた現在および将来の制約に基づいて、達成可能な最高の貢献度を追加します。 

さらに単純化すると、ソリューションが線形になるため、セットが存在する場合、最適な戦略では送信を遅らせる必要がありません。遅延しても、LIFO 制約の結果は改善されず、将来の柔軟性が低下するだけであるためです。 したがって、直接シミュレートします。送信しない場合は毎日リクエストし、有益な構造が指示するたびに送信します。これは、決定論的な貪欲なスタック プロセスに帰着します。

 ## アルゴリズムのチュートリアル

 1. アクティブな問題セットのスタックを維持しながら、左から右に数日を調べます。 各要素には、セットのタイプと、最終的に解決されたときに得られるスコアが格納されます。 これは、LIFO 制約を直接モデル化します。 
2. 「リクエスト」することに決めたら、新しいセットをスタックにプッシュします。 私たちが選択するタイプは、期待されるゲインの最大化に合わせて調整されますが、将来の気分は既知であるため、局所的な最適化に基づいてすぐに割り当てます。現在の気分が C の場合はコーディングを好み、それ以外の場合はジャミングを好みます。 これにより、即時のリクエスト値が最大化されます。 
3. 提出の決定点に達したら、スタックの一番上をポップします。 これは、LIFO に基づく唯一の合法的な提出の選択肢を表します。 
4. ポップされたセットのスコアは、提出日の気分と保存されているセットのタイプを使用して計算されます。 それらが一致する場合は、完全な値が採用されます。 それ以外の場合はペナルティが適用されます。 
5. すべての日数が処理されるまで続行し、入力によって偶数の日数が保証されるため、要求されたすべてのセットが最終的に送信されることが保証されます。 
6. 最終的な答えは、ポップされたすべてのセットからの累積スコアです。 

### なぜ効果があるのか

 不変条件は、スタックが常に未送信のリクエストのセットを正しい時間的順序で正確に表しており、将来の決定によって送信の相対的な順序が変更される可能性がないことです。 各セットの送信は、送信ステップでスタックの最上位になると強制されるため、唯一の自由度は作成時のそのタイプです。 タイプの選択は、ローカルのリクエスト値と最終的な送信評価に独立してのみ影響するため、リクエストごとに貪欲に最適化するだけで十分です。 送信の順序を変更しようとすると、LIFO 制約に違反するため、グローバルな再配置によって結果が改善されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for tc in range(1, T + 1):
        s = input().strip()
        stack = []
        score = 0

        for i, ch in enumerate(s):
            # If stack is non-empty, we choose to submit
            # otherwise we request
            if stack:
                t, base = stack.pop()
                # submission mood affects score
                if t == ch:
                    score += base
                else:
                    score += max(0, base - 5)
            else:
                # request a set matching current mood
                # to maximize request value
                if ch == 'C':
                    stack.append(('C', 10))
                else:
                    stack.append(('J', 10))

        print(f"Case #{tc}: {score}")

if __name__ == "__main__":
    solve()
```このコードは、保留中の問題セットのスタックを維持します。 各要素は、作成時に型とその基本値を格納します。 決定ルールは意図的にシンプルになっています。提出するものがあれば、すぐに提出します。 それ以外の場合は、現在の気分に合わせた新しいセットをリクエストします。 

重要な実装の詳細は、スタックが LIFO 送信順序を自動的にエンコードするため、明示的なスケジューリング構造が必要ないことです。 スコアの計算は、その日の気分を使用してポップタイムに行われます。

 ## 特殊なケース

 重要なエッジケースは、気分が交互に変化するものの、積み重ねることが有益に見える場合です。 入力用`CJCJ`、単純な戦略では、後でより適切に調整するために送信を遅らせようとする可能性がありますが、LIFO はペアの再配置を防ぎます。 このアルゴリズムは、リクエストと送信を即座にペアにすることでこれを処理し、古いスタックが蓄積されないようにします。 

もう 1 つの特殊なケースは、次のような同じムードが長期間続くことです。`CCCCCC`。 再度リクエストする前にすぐに送信するため、スタックが 1 つの有効な保留セットを超えることはありません。 これにより、不必要な蓄積が回避され、各リクエストが両端で最大限に評価されるようになります。
