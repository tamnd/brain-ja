 ## 解決策
 ## 問題の理解

 2 つの固定時刻表を使用して、2 つの停留所 A と B の間を往復する旅行者をシミュレートしています。 1 つの時刻表には A から B への出発時刻が記載されており、もう 1 つの時刻表には B から A への出発時刻が記載されています。旅行者がバスに乗車するたびに、移動には一定の時間がかかり、到着後すぐに次の逆方向のバスを待ち続けることができます。 

重要な点は、旅行者が任意にバスを選択しないことです。 いつでも、彼らは常に、現在行きたい方向にある次に利用可能なバスを選択します。これは、現在の到着時刻から出発時刻がまだ有効である最も早いバスを意味します。 また、スケジュール内の関連する最後の時刻に関連付けられたグローバル カットオフ条件もあり、最終許可時刻よりも遅れて到着するバスの乗車を防止します。 

入力は、一定の移動遅延とともに、各方向のバスの出発時刻を表す 2 つの並べ替えられた整数シーケンスで構成されます。 このプロセスは固定された駅と時刻で開始され、有効な移動が存在しなくなるまで、次の実行可能なバスへの乗車を繰り返しシミュレーションします。 出力は、成功したバス乗車の数です。 

この制約は、どちらのスケジュールも大きくなる可能性があり、通常は合計エントリ数が最大約 200,000 になる可能性があることを意味します。 各ステップでリスト全体をスキャンする単純なシミュレーションでは、配列を繰り返し走査することになり、最悪の場合は 2 次の動作が発生します。 このスケールでは、線形または線形に近い解のみが安全であるため、各バスが最大 1 回または対数的に考慮されるようにする必要があります。 

いくつかのエッジの状況が重要です。 1 つは、後のバスが存在するにもかかわらず、現在時刻以降に利用可能なバスがない場合です。 たとえば、A の時刻が 10 で、次の A-to-B バスが 5 の場合、それは無関係なのでスキップする必要があります。 もう 1 つの微妙なケースは、バスに乗った場合、世界的な締め切り時間に比べて到着が遅すぎる場合です。 たとえバスが利用可能であっても、バスは拒否されなければならず、さらなる進行を妨げる可能性があります。 最後に、移動が交互に行われるということは、ポインターの移動における 1 つの間違いが同じセグメントの繰り返しの再検討を引き起こし、無限ループや二重カウントにつながる可能性があることを意味します。 

## アプローチ

 ブルートフォースアプローチでは、文字通りプロセスをシミュレートしようとします。 各ステップで、関連する時刻表全体をスキャンして、現在の場所の時間条件を満たす最初のバスを見つけます。 これが機能するのは、ルールに直接従うためです。つまり、常に最も近い有効なバスを選択します。 ただし、各スキャンには直線的な時間がかかるため、これを乗車ごとに 1 回実行する場合があります。 n + m 個のバスがあり、O(n + m) 回の遷移が発生する可能性がある場合、最悪の場合、O((n + m)^2) の動作が発生し、これは非常に遅すぎます。 

重要な点は、どちらのスケジュールも整理されており、時間通りにバスを通過してしまえば、再度バスのことを考える必要がないということです。 「最も近い有効なバス」は常に、ソート順で次に未使用の候補になります。 これにより、前方にのみ移動する 2 つのポインター (配列ごとに 1 つ) を維持できるようになります。 方向を切り替えるたびに、最初の有効な出発点が見つかるまで、対応するポインタを進めます。 

これにより、繰り返される再スキャンが各アレイの 1 回のパスに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O((n + m)^2) | お(1) | 遅すぎる |
 | 2 ポインターのシミュレーション | O(n + m) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 2 つのスケジュールへの 2 つのポインターと、現在時刻と現在のステーションを追跡する変数を維持します。 それ以上移動できなくなるまで、次の有効なバスに乗ろうと繰り返し試みます。

1. A-to-B および B-to-A 配列の先頭で 2 つのインデックス i と j を初期化し、現在時刻を可能な限り最も早い開始時刻に合わせて現在位置を A に設定します。 これにより、移動が発生する前のシミュレーション状態が確立されます。 
2. 駅 A に着いたら、問題の待機状況によって調整された出発時刻より早く出発しない最初のバスが見つかるまでポインタ i を進めます。 これにより、実際に乗車可能なバスのみが考慮されるようになります。 
3. カットオフ制約の下でこのバスの乗車が許可されているかどうかを確認します。 過度の遅刻を防止する条件に違反する場合は、直ちにシミュレーションを停止してください。 
4. 有効な場合、乗車カウンタをインクリメントし、ステーション B に移動し、現在時刻を移動後の到着時刻に更新します。 これは、1 つの完全な移行が完了したことを反映しています。 
5. 駅 B に着いたら、ポインタ j を使用して対称プロセスを実行し、現在の時刻で乗車できる最初のバスまで処理を進めます。 
6. 有効性を確認するために、同じカットオフ条件を適用します。 失敗した場合は、これ以上有効な処理を進めることができないため、プロセスを終了します。 
7. 有効な場合は、乗車カウンターをインクリメントし、ステーション A に戻り、それに応じて時間を更新します。 プロセスを繰り返します。 

正確さは、各ポインタが前方にのみ移動し、現在時刻から取得される可能性がある最初の未使用の候補バスを常に指すという不変条件から得られます。 スケジュールは並べ替えられているため、以前のバスは一度スキップすると永久に使用できなくなり、後のバスはまだ到着できません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, d = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    i = j = 0
    ans = 0

    # start at A at time a[0] - d is a common interpretation anchor;
    # many formulations start at time 0, so we use 0 unless specified otherwise
    t = 0
    at_A = True

    while True:
        if at_A:
            while i < n and a[i] < t:
                i += 1
            if i >= n:
                break
            if a[i] < a[-1] - d:
                ans += 1
                t = a[i] + d
                at_A = False
                i += 1
            else:
                break
        else:
            while j < m and b[j] < t:
                j += 1
            if j >= m:
                break
            if b[j] < a[-1] - d:
                ans += 1
                t = b[j] + d
                at_A = True
                j += 1
            else:
                break

    print(ans)

if __name__ == "__main__":
    solve()
```中心となる構造は、2 つのスケジュールを交互に繰り返すループです。 各内側の while ループは、次の実行可能な出発点が見つかるまでポインターを進めます。 実装の重要な詳細は、ポインタが前方にのみ移動し、後方には決して移動しないことです。これにより、線形の複雑さが保証されます。 

カットオフ チェックでは、関連する最後の A 側時間から導出された最終しきい値が使用されます。 これにより、旅行者は到着が遅すぎてプロセスを有意義に続行できないバスに乗車することができなくなります。 

## 実用的な例

 A から B へのバスが時刻 [3、8、15] にあり、B から A へのバスが [5、10、20] にあり、d = 2 である単純なケースを考えてみましょう。 

開始時、私たちは時刻 0 に A にいます。最初に利用できる A のバスは 3 にあるので、それに乗って時刻 5 に到着し、B に移動します。 

| ステップ | 側面 | 時間 | ポインタ i | ポインタ j | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 1 | あ | 0 | 0 | 0 | a[0]=3 を取る |
 | 2 | B | 5 | 1 | 0 | bを待ちます |
 | 3 | B | 5 | 1 | 0 | b[0]=5 を取る |
 | 4 | あ | 7 | 1 | 1 | 続ける |

 このトレースは、ポインタが以前のバスに再びアクセスせず、常に前方に移動する様子を示しています。 

次に、A バス [2、4、6] で現在時刻が 5 など、バスは存在するが現在時刻に対して早すぎるケースを考えます。ポインタは 2 と 4 を自動的にスキップし、6 のみを考慮します。これにより、アルゴリズムが再スキャンせずに実行不可能なオプションを正しく無視していることが確認されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 | 時間 | O(n + m) | 各ポインターは配列全体を厳密に前方に 1 回だけ移動します。 
| スペース | お(1) | インデックスとカウンターのみが保存されます。 

リニア スキャンの動作は、イベントの合計が大きいものの、それぞれが 1 回処理される ICPC スタイルのスケジューリング シミュレーションに典型的な制約と一致します。 これにより、最大入力サイズであっても制限内で快適な実行が維持されます。

 ## 特殊なケース

 重大なエッジ ケースは、一方向のすべてのバスが現在時刻より早い場合に発生します。 たとえば、時刻 50 で B にいて、すべての B-to-A バスが [1, 2, 3] にある場合、ポインタは配列全体を超えて進み、正しく終了します。 内部の while ループが j を使い果たし、シミュレーションが即座に停止するため、アルゴリズムはこれを処理します。 

別のエッジ ケースは、有効なバスが存在するが、それを使用するとカットオフ制約に違反する場合に発生します。 このような場合、ポインタが実行可能な出発時刻を見つけたとしても、条件チェックによって進行がブロックされます。 シミュレーションは前方にスキップしようとするのではなくきれいに停止するため、誤った追加乗車が防止されます。 

最後の微妙なケースは、交互の移動が各方向で最後に残っている有効なバスを繰り返し消費する場合です。 ポインタは乗車が成功するたびにすぐにインクリメントされるため、同じバスが再検討されることはなく、一方の利用可能な出発便がなくなるとシミュレーションは自然に終了します。
