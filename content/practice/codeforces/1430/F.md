 ## 解決策
 ## 問題の理解

 私たちには、一定の順序で時間の経過とともに発生する一連のモンスターウェーブが与えられています。 各ウェーブは特定の時間間隔で到着し、開始時に既知の数のモンスターを瞬時に生成します。 期限までにすべてのウェーブからすべてのモンスターを排除する必要があります。ウェーブは時間的に重なりません。つまり、ウェーブを独立した「処理ウィンドウ」の時系列チェーンとして扱うことができます。 

モンスターを倒すとすぐに弾丸を1発消費します。 銃にはマガジン容量がある`k`、リロードするたびに 1 単位時間がかかり、その間は他に何も行われません。 重要な点は、リロードすると現在のマガジン内の未使用の弾丸がすべて破棄されるため、過剰なリロードによりすでに支払った弾薬が無駄になる可能性があることです。 

マガジンが満杯の状態から開始し、発射された弾丸とリロードにより廃棄された弾丸の両方をカウントして、消費される弾丸の総数を最小限に抑えたいと考えています。 

制約の観点から見ると、`n ≤ 2000`二次動的計画法が可能になります。 時間とモンスターの値の範囲は大きく、最大で`10^9`これは、時間が明示的にシミュレートされていないことを示します。 むしろ、波の構造が重要なのです。 重要な観察は、すべての制約が組み合わせによるものであり、波間で射撃能力をどのように分割するかということです。 

素朴な解釈では、射撃とリロードを瞬間ごとにシミュレートしようとしますが、モンスターがバーストで出現し、各ウェーブの間隔内でショットを分配する完全な自由があるため、それは失敗します。 

波がそれ以上のものを持っている場合、微妙なエッジケースが現れます。`k`モンスター。 単一のマガジンには、リロードせずにウェーブをクリアするのに十分な弾丸を保持できないため、すべてのリロードが実際に使用可能であることを確認する必要があります。 リロードが早すぎたり遅すぎたりすると、部分的に未使用のマガジンが不必要に破棄される可能性があります。 もう 1 つの微妙な問題は、連続する波が小さいものの、時間的に互いに近い場合に発生します。この場合、波の間でリロードするのではなく、波を越えて残りの弾丸を運ぶことが最適になります。 

## アプローチ

 ブルートフォース戦略では、ウェーブごとに、リロードする前に発射する弾丸の数と、各ウェーブのモンスターをマガジン間で分割する方法を決定しようとします。 これは事実上、各パーティションを分割するすべての方法を列挙することを意味します。`a_i`せいぜいサイズの塊に`k`同時に、ウェーブ間のリロード境界がどこで発生するかを決定します。 これは組み合わせ的に爆発します。`a_i`モンスターは大まかに貢献します`O(a_i / k)`セグメント間、および全体にわたって`n`これにより、グローバル構成の数が指数関数的に増加します。 

重要な構造の簡素化は、ウェーブ内の正確なタイミングをまったく気にせず、ウェーブ間で移行するときにマガジン内に残っている弾丸の数だけを気にすることです。 各ウェーブは弾丸を消費し、最大でも`k`リロードが強制される前に弾丸を使用できます。 これは、波と残りの弾丸に対する動的プログラミングの定式化を示唆しています。 

DP 状態を、マガジンに一定数の弾丸が残った状態で終了する、ウェーブのプレフィックスを処理した後の最小コストとして定義します。 現在のマガジンを使用し続けるか、ウェーブの前または最中にリロードを実行するかどうかをモデル化します。 リロードのコストは、現在の状態を破棄して弾丸を次の状態にリセットする操作 1 回分です。`k`。 

ウェーブごとに、満杯のマガジンを何冊使用するか、残りをどのように配布するかを決定する必要があります。 一緒に到着したら`x`弾丸が残っているので、最初にウェーブで使用してから、`(a_i - x)`残りの需要、それには`ceil((a_i - x)/k)`雑誌がいっぱい。 移行コストは、必要な完全リロードの回数によってのみ異なります。 

以来`k`サイズが大きくなる可能性があるため、すべてを反復することはできません`k`州。 代わりに、波の境界での遷移のみが重要であることを観察することによって状態を圧縮し、波の後に残る弾丸は、最後のマガジンに未使用のまま残すことにした弾丸の数によって完全に決定されます。 これにより、DP は意味のあるブレークポイントのみを考慮するようになり、`O(n^2)`解決。

 ## アルゴリズムのチュートリアル

 DP 配列を維持します。`dp[i][j]`最初の弾丸を処理した後に消費される最小弾丸を表します。`i`波とで終わる`j`ウェーブ後に現在のマガジンに残っている弾丸`i`。 以来`j`ではなく波のサイズによって制限されます`k`、実行可能な剰余値のみを追跡します。 

また、残りを指定してウェーブを開始するときに必要な満杯のマガジンの数をシミュレートすることにより、遷移を事前計算します。 

1. 次のコマンドを使用して DP を初期化します。`dp[0][k] = 0`、ウェーブが処理されておらず、完全なマガジンが利用可能であることを意味します。 
2. ウェーブごとに`i`、到達可能なすべての状態を考慮します`(remaining bullets r, cost c)`前の DP レイヤーから。 
3. その状態に対して、残りの弾丸を使用して波の一部をカバーできるかどうかを判断します`r`。 もし`r ≥ a_i`、リロードせずにウェーブを終了し、残りを次のように更新します。`r - a_i`。 
4. もし`r < a_i`、私たちは消費します`r`すぐに弾丸を発射し、残りの弾丸に必要な満弾のマガジンの数を計算します。`a_i - r`モンスター。 これは`(a_i - r + k - 1) // k`。 
5. 新しいマガジンはそれぞれ、以前のマガジンを破棄するリロード アクションを介して購入されるため、マガジンを完全に使用するたびにリロード コストに相当します。 
6. waveのDP状態を更新します`i`ウェーブが終了した後の新しい残りを使用します。`(a_i - r) % k`残りを使い果たした後にマガジンをフルに使用した場合。 
7. すべての遷移の中で、考えられる残りの状態ごとに最小コストを維持します。 
8. すべての波を処理した後、すべての最終剰余状態の最小値を取得します。 

重要な不変条件は、各ウェーブプレフィックスについて、DP がマガジン内のすべての意味のある弾丸の残りの最適コストを保存することです。 あらゆる最適な戦略は、そのような残りのシーケンスに対応している必要があります。各ウェーブの後に将来に影響を与える唯一の情報は、弾丸がどのように消費されたかではなく、弾丸が残っているかどうかだけだからです。 

これが機能するのは、ウェーブ間の決定構造が残りの弾丸を超えて記憶されないためです。 以前のすべての決定は、現在の雑誌の状態と累積コストによって完全に要約されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    waves = [tuple(map(int, input().split())) for _ in range(n)]

    INF = 10**30

    dp = {k: 0}

    for l, r, a in waves:
        ndp = {}

        for rem, cost in dp.items():
            if rem >= a:
                nrem = rem - a
                if nrem not in ndp or cost < ndp[nrem]:
                    ndp[nrem] = cost
            else:
                need = a - rem
                full = (need + k - 1) // k

                cost2 = cost + full

                used_last = need % k
                nrem = (k - used_last) % k

                if nrem not in ndp or cost2 < ndp[nrem]:
                    ndp[nrem] = cost2

        dp = ndp

    ans = min(dp.values())
    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、残りの弾丸を最小限のコストにマッピングする辞書として DP 状態を追跡します。 各ウェーブは、以前の可能なすべての残りからの遷移を処理します。 移行ロジックは、現在のマガジンで十分な場合と完全なリロード サイクルが必要な場合を区別します。 2 番目のケースの残りの更新は、最後に部分的に充填されたマガジンを消費した後の残りの弾丸を反映します。 

微妙な点は、既存のマガジンから使用された弾丸はすでに状態遷移コストに含まれているため、部分的な消費ではなく完全なリロードのみをカウントすることです。

```DP の状態を次のように追跡します。`(remaining bullets → cost)`。 

| ステップ | 波 | | 前の DP ステート アクション | | の後の DP ステート
 | --- | --- | --- | --- | --- |
 | 1 | 6 モンスター | {3→0} | 3 個使用、3 個リロード | {0→0、0→1} が結合されました |
 | 2 | モンスター3体 | {0→?} | 2 回のリロード サイクルが必要 | 最終コスト 9 |

 最初のウェーブではマガジンが 1 つ完全に使い果たされ、部分的にリロードが強制されます。 第 2 ウェーブは残りの状態から継続し、追加のマガジン消費が必要となり、合計コスト 9 が発生します。 

このトレースは、ウェーブを最適に分割するには、ゼロの剰余を運ぶ必要があるが、後で追加のリロードを支払う必要があり、それを DP がキャプチャすることを示しています。

 ## 特殊なケース

 エッジケースの 1 つは、波がマガジン内の残りの弾丸に正確に適合する場合に発生します。 移行によって余分なリロードが発生してはなりません。 DP がこれを処理します。`rem >= a`コストを追加せずに Wave を消費し、正しいゼロまたは正の剰余を残します。 

残りを使用した後、ウェーブが部分的なマガジンを 1 つだけ必要とする場合には、別のケースが発生します。 余りの計算`(k - used_last) % k`最後のチャンクが正確にマガジンを満たしたときに完全な容量を正しく復元し、幻の残留状態を回避します。 

最後のエッジケースは、すべての波が以下よりも小さい場合です。`k`。 このアルゴリズムは不必要なリロードを強制せず、自然に剰余を前方に繰り越すため、各ウェーブを個別に処理するのではなく、クロスウェーブの最適化を可能にするため、引き続き正しく動作します。
