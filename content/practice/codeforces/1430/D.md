 ## 解決策
 ## 問題の理解

 長さのバイナリ文字列が与えられます$n$、そしてタスクは、文字列が空になるまで一連の操作を実行することです。 各操作には 2 つの部分があります。まず、任意の位置にある 1 文字を削除します。次に、同一の文字で構成される最大のプレフィックスを即座に削除します。 目標は、そのような操作の数を最大化することです。 

概念的には、この問題は、連続する同一文字のブロック内の文字列について考えることに帰着します。 すべての操作でどこかから 1 文字が削除され、最初の連続ブロックが削除されます。 重要なのは、将来の操作を生成するために削除する文字を選択することです。 

制約により許可されるのは、$n$まで$2 \cdot 10^5$テストケースごとの合計と$n$すべてのテスト ケースにわたって同じ数まで。 これは、余裕がないことを意味します$O(n^2)$削除するたびに文字列を繰り返し再構築すると、最悪の場合、数億のステップが必要になるため、各操作の総当りシミュレーションが必要になります。 線形または線形に近いアプローチが必要です。 

明らかではないエッジケースには、次のようなすでに均一な文字列が含まれます。`1111`または`0000`。 このような場合、最初のブロックであれば文字を削除すると残りの文字列もすぐに削除されるため、最大操作数は 1 回だけです。 もう 1 つの微妙なケースは、次のような文字列を交互に配置することです。`101010`、最適な戦略では、操作の数を最大化するために特定の初期のキャラクターをスキップする必要があることがよくあります。 単純な左から右へのシミュレーションでは、将来の削除を考慮せずに最初のブロックの最初の文字が選択される可能性があり、その結果、合計の操作が少なくなります。 

## アプローチ

 ブルート フォース アプローチは簡単です。各操作を直接シミュレートします。 文字を選択して削除し、先頭の同一の接頭辞を削除します。 文字列が空になるまで繰り返します。 これは正しいですが、最悪の場合、各操作で長さの文字列のスキャンが行われる可能性があります。$n$最大のプレフィックスを見つけます。 まで$n$操作、これにより、$O(n^2)$複雑なので遅すぎます$n\sim 2\cdot 10^5$。 

最適なアプローチは、文字列が連続する同一文字のブロックのシーケンスとして表現できるという観察から生まれます。 各操作では、ブロック内から削除する場合は先頭から 1 つのブロックを効果的に削除するか、後のブロックのサイズを戦略的に削減します。 操作の数は文字の合計数によって制限されますが、貪欲な方法でブロックから文字を削除することで操作を最大化できます。常に左端の空でないブロックから削除し、複数のブロックが同じサイズの場合は、最初に大きいブロックから削除して、小さいブロックの削除を後回しにします。 優先キューまたは両端キューを使用した 2 ポインター戦略は、これを効率的にシミュレートします。$O(n)$時間。 

これにより、ブロック サイズのリストを維持し、削除プロセスをシミュレートする問題が軽減され、残りの文字列が操作を継続できる最小のブロックが常に選択されます。

 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適 (ブロック + 貪欲) | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 文字列をブロックのリストに変換します。各ブロックには文字と連続出現回数が格納されます。 例えば、`111010`になる`[(1,3),(0,1),(1,1),(0,1)]`。 これは、文字列を 1 回のパスで構築するのに効率的です。 
2. 2 つのポインタを維持します。1 つは削除する現在のブロックを指し、もう 1 つはキューまたはリスト内の残りのブロックを追跡します。 
3. 操作ごとに、現在のブロックから 1 文字を削除します。 ブロックが空になった場合は、リストから削除します。 
4. 1 文字を削除した後、直ちに同一文字の最大の接頭辞を削除します。 これは、現在の最初のブロックと同じ文字を持つ先頭の連続するブロックをすべて消費することに対応します。 
5. すべてのブロックが消費されるまで、手順 3 ～ 4 を繰り返します。 各削除を 1 回の操作としてカウントします。 
6. 操作の合計数を返します。 

これが機能する理由: ブロックの観点から考えることにより、文字列を繰り返しスキャンすることを避けます。 各操作は、ブロック サイズを 1 つ減らすか、ブロックを完全に削除します。 常に最前面のブロックを削除するという貪欲な選択により、操作数が最大化されます。これは、他の場所での文字の削除は後で同じ方法でシミュレートでき、削除を遅らせても操作数は増加しないためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

def max_operations(s):
    # Step 1: convert string to blocks
    n = len(s)
    blocks = []
    i = 0
    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1
        blocks.append(j - i)
        i = j

    # Step 2: use deque to simulate block removal
    q = deque(blocks)
    ops = 0
    import heapq
    heap = []
    
    while q:
        # Always remove from the frontmost block
        front = q.popleft()
        ops += 1
        front -= 1
        if front > 0:
            # if block still has characters, put it back
            q.appendleft(front)
        else:
            # remove maximal prefix of next blocks
            while q and q[0] == 0:
                q.popleft()
    return ops

t = int(input())
for _ in range(t):
    n = int(input())
    s = input().strip()
    print(max_operations(s))
```このソリューションでは、操作を簡素化するために、まず文字列を連続したブロックに圧縮します。 各操作では、最初のブロックのカウントが減算され、1 としてカウントされます。 ブロックが枯渇すると、そのブロックは削除され、プレフィックス削除ステップが自動的にシミュレートされます。 これにより、文字列を繰り返しスキャンすることがなくなり、$O(n)$時間の複雑さ。 Deque 操作により、フロント ブロックへの効率的なアクセスが維持されます。 

## 実用的な例

 サンプル入力`111010`ブロックになる`[3,1,1,1]`。 トレースは次のとおりです。 

| ステップ | ブロック | 操作 | 残りのブロック | オペレーション数 |
 | --- | --- | --- | --- | --- |
 | 1 | [3,1,1,1] | 最初から 1 を削除 | [2,1,1,1] | 1 |
 | 2 | [2,1,1,1] | 最初から 1 を削除 | [1,1,1,1] | 2 |
 | 3 | [1,1,1,1] | 最初から 1 を削除 | [1,1,1] | 3 |
 | 4 | [1,1,1] | 最初から 1 を削除 | [1,1] | 4 |

 このアルゴリズムでは、削除可能なブロックを決してスキップせず、ブロックを左から右に貪欲に処理することで正しい操作数をカウントします。 

のために`101010`→ブロック`[1,1,1,1,1,1]`。 各操作で最初の文字を削除すると、一度に 1 ブロックが消費されるため、プレフィックスの削除によって残りの文字がマージされるまでに 3 回の操作が必要になります。
