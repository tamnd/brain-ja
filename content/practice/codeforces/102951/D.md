 ## 解決策
 ## 問題の理解

 概念的に非常に大きい、0 から最大までのインデックスが付けられた配列から始めます。$10^9 - 1$ですが、最初はすべての位置にゼロが含まれます。 この配列を明示的に保存する代わりに、範囲を変更およびクエリする 2 種類の操作が提供されます。 

最初のタイプの操作では、セグメント全体に増分を適用します。 セグメントを指定すると$[l, r)$そして値$v$、その範囲内のすべてのポジションは$v$現在の値に追加されます。 これらの更新は重複して蓄積されるため、各ポジションの最終値は、そのポジションをカバーするすべての更新の合計となります。 

2 番目のタイプの操作では、範囲の合計を求めます。 セグメントを指定すると$[l, r)$、その間隔に現在保存されているすべての値の合計が必要です。 これは単に更新をカウントするだけではなく、すべての範囲の加算が適用された後の配列の実際の値を合計します。 

主な難点は、座標範囲が最大であることです。$10^9$したがって、配列を明示的に構築する解決策は不可能です。 座標圧縮された密な配列であっても、すべての位置での反復を慎重に避けた場合にのみ実行可能です。 

制約は以下を意味します$10^5$アップデートと$10^5$クエリ。 影響を受ける更新をスキャンして各クエリを処理するソリューションは次のように動作します。$O(NQ)$、これは実現可能な限界をはるかに超えています。 配列の長さはメモリや時間で使用できないため、位置ごとのシミュレーションさえも不可能です。 

更新とクエリが重なり合って境界点に接触すると、微妙なエッジ ケースが発生します。 たとえば、ある時点で一致する 2 つの更新について考えてみましょう。 

入力:```
1 1
0 5 2
0 5
```0 から 4 までのすべての要素が 2 になるため、正解は 10 です。 範囲を誤って両端を含むものとして扱う、または 1 つずつ不一致として扱う単純な実装$[l, r]$対$[l, r)$二重にカウントされるか、最後の要素が完全に欠落します。 この問題では一貫して半開区間が使用されており、規則が混在していると、データ構造自体が正しい場合でも集計が正しく行われなくなります。 

## アプローチ

 ブルートフォースの解釈は簡単です。各更新を適用した後、配列を明示的に維持し、範囲を合計して答えを再計算します。 各アップデートの内容は、$O(10^9)$最悪の場合は位置もスキャンされ、各クエリもスキャンされます。$O(10^9)$ポジション。 タッチされた領域のみが重要であると仮定した場合でも、更新が重複すると、実効コストはおよそ$O(N \cdot 10^9 + Q \cdot 10^9)$、これは使用できません。 

最初の構造上の観察は、座標空間は巨大であるにもかかわらず、重要なのは更新境界だけであるということです。 2 つの連続するイベント ポイントの間では、配列の値は定数です。 これは、配列をすべてのセグメントで定義されたセグメントに圧縮できることを意味します。$l$そして$r$エンドポイント。 多くてもあります$2N + 2Q$そのような位置にあるため、問題は巨大な暗黙的な配列から管理可能なブレークポイントのセットに減ります。 

座標を圧縮すると、各更新ははるかに小さいインデックス空間に範囲を追加することになります。 残りの課題は、範囲加算と範囲合計という 2 つの操作を効率的にサポートすることです。 これはまさに、フェンウィック ツリーまたは差分トリックを備えたセグメント ツリーの古典的な設定です。 

重要な洞察は、配列の差異構造を通じて配列を扱うことです。 範囲の追加をサポートする構造を維持する場合、それを差分配列のポイント更新に変換できます。 次に、プレフィックス合計によって実際の値が再構築されます。 範囲合計クエリに答えるには、プレフィックス合計のプレフィックス合計が必要です。これにより、係数用と重み付け係数用の 2 つのフェンウィック ツリーを維持することになります。 この標準的なトリックにより、両方の操作を対数時間で実行できます。 

したがって、移行は次のようになります。ブルート フォースは明示的なシミュレーションによって機能しますが、規模が原因で失敗します。 座標圧縮により、ユニバースのサイズが縮小します。 Fenwick ベースの範囲更新 + 範囲クエリは、問題をプレフィックス算術に変換します。

 ## アルゴリズムのチュートリアル

 まず、重要な座標をすべて抽出します。 これらはすべてです$l$そして$r$更新とクエリの両方から。 それらを並べ替えて重複を削除し、実際の座標からコンパクトな範囲への圧縮されたインデックス マッピングを構築します。$[0, M)$。 

それぞれのアップデート$[l, r), v$圧縮されたインデックスに変換されます$[l', r')$。 次に、フェンウィック ツリー トリックを使用して範囲の追加を適用します。 間隔内のすべての要素を更新するのではなく、プレフィックスに線形効果を追加できる構造を維持します。 

フェンウィックの木を2本使用しています。 1 つはポジションが何回影響を受けたかを追跡し、もう 1 つは累積された重み付けされた寄与を追跡します。 このペアリングにより、対数時間でのプレフィックス合計の再構築が可能になります。 

更新ごとに、エンドポイントのツリーごとに 2 つのポイント更新を実行し、範囲の追加の効果をエンコードします。 

クエリごとに$[l, r)$、プレフィックスの合計を計算します。$r-1$プレフィックスの合計を減算して、$l-1$。 これにより、間隔全体の合計が得られます。 

これが機能する理由は、範囲加算が差分信号になり、プレフィックス再構築がその信号を実際の値に変えるためです。 

### なぜ効果があるのか

 このアルゴリズムは、フェンウィック構造が配列の差分分解を表すという不変条件を維持します。 各範囲の更新は、ステップ関数を追加することと同じです。 プレフィックス合計クエリでは、これらのステップ関数の積分をある点まで評価します。 統合は線形であるため、重複する更新は干渉することなくその寄与を単純に加算し、プレフィックスの減算によりセグメントを正確に分離します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        i += 1
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        if i < 0:
            return 0
        i += 1
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def add_range(bit1, bit2, l, r, v):
    bit1.add(l, v)
    bit1.add(r, -v)
    bit2.add(l, v * (l - 1))
    bit2.add(r, -v * (r - 1))

def prefix_sum(bit1, bit2, i):
    return bit1.sum(i) * i - bit2.sum(i)

def range_sum(bit1, bit2, l, r):
    return prefix_sum(bit1, bit2, r - 1) - prefix_sum(bit1, bit2, l - 1)

def main():
    n, q = map(int, input().split())
    updates = []
    queries = []

    coords = []

    for _ in range(n):
        l, r, v = map(int, input().split())
        updates.append((l, r, v))
        coords.append(l)
        coords.append(r)

    for _ in range(q):
        l, r = map(int, input().split())
        queries.append((l, r))
        coords.append(l)
        coords.append(r)

    coords = sorted(set(coords))
    idx = {x: i for i, x in enumerate(coords)}

    m = len(coords)
    bit1 = Fenwick(m)
    bit2 = Fenwick(m)

    for l, r, v in updates:
        l = idx[l]
        r = idx[r]
        add_range(bit1, bit2, l, r, v)

    out = []
    for l, r in queries:
        l = idx[l]
        r = idx[r]
        out.append(str(range_sum(bit1, bit2, l, r)))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```コードは、すべての意味のある境界が連続したインデックス空間にマップされるように、座標を圧縮することから始まります。 フェンウィック ツリーには高密度のインデックス作成が必要なため、これが必要になります。 

の`add_range`関数は範囲の追加を 2 つのフェンウィック アップデートにエンコードし、エフェクトをプレフィックス調整可能なコンポーネントに分割します。 の`prefix_sum`関数は、標準の 2 ツリー トリックを使用して、生の累積項と補正項を組み合わせて、ある点での実際の値を再構築します。 

最後に、各クエリは 2 つのプレフィックスの合計を減算することによって回答され、これにより必要なセグメントが正確に分離されます。 

微妙な点は、すべての範囲がハーフオープンとして扱われることです。 減算では、$r - 1$そして$l - 1$隣接するセグメント間でオフバイワンの漏れが発生しないように注意してください。 

## 実用的な例

 小さなケースを考えてみましょう。 

入力:```
2 2
1 4 2
3 6 1
1 6
2 5
```座標を圧縮します。$[1, 2, 3, 4, 5, 6]$。 

最初の更新後の値は、$[1,4)$+2です。 2番目以降は、$[3,6)$+1を追加します。 

プレフィックス値を追跡できます。 

| ポジション | アップデート 1 後 | アップデート 2 後 | 最終回 |
 | --- | --- | --- | --- |
 | 1 | 2 | 0 | 2 |
 | 2 | 2 | 0 | 2 |
 | 3 | 2 | 1 | 3 |
 | 4 | 0 | 1 | 1 |
 | 5 | 0 | 1 | 1 |

 クエリ$[1,6)$合計は 2 + 2 + 3 + 1 + 1 = 9 となります。 

クエリ$[2,5)$合計は 2 + 3 + 1 = 6 になります。 

このトレースは、フェンウィックの再構成がプレフィックスの違いから計算したものと一致します。

 ## 特殊なケース

 エッジケースの 1 つは、更新がエンドポイントのみに接触する場合です。 たとえば、次のアップデート$[0, 1)$続いて次の質問が続きます$[1, 2)$。 範囲が重複していないため、正しい結果はゼロです。 差分配列は正確に境界で寄与をキャンセルするため、Fenwick 構造はこれを処理します。 

もう 1 つのケースは、次のような完全に重複する更新です。$[0, 10)$何度も繰り返しました。 値は更新の数に応じて線形にスケールされる必要があり、プレフィックスの再構築により、各重複が上書きされるのではなく蓄積されることが保証されます。 

最後のエッジケースは、クエリが更新境界に正確に一致する場合です。 実装では一貫して半開間隔が使用され、エンドポイントが圧縮されるため、境界で正確にクエリを実行しても、隣接するセグメントが誤って含まれることはありません。
