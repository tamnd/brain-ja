 ## 解決策
 ## 問題の理解

 静的配列が与えられ、次に複数のクエリが与えられます。 各クエリは配列のセグメントを記述し、プレフィックスの寄与と単一の最適な「遷移」選択の組み合わせを使用して、そのセグメントから導出される値を計算するように求めます。 

各クエリの構造は事実上、範囲内の位置を選択し、左側の部分からのプレフィックス スタイルの蓄積と右側の部分からの変更された寄与を組み合わせることができます。 このステートメントには重要な制約も隠されています。一連の操作のうち、実際に最終結果に影響を与えるのは、特定の種類の最後の操作だけです。 これにより、すべての操作をシミュレートするのではなく、クエリ範囲ごとに、事前に計算された配列の関係から構築された最大の式を評価するという問題に集約されます。 

出現する主要な式は、セグメントの場合、基本値と 2 つの配列の組み合わせを最大化するセグメント内のインデックスの最良の選択を評価する必要がある形式です。 具体的には、各クエリは、少数のプレフィックスまたは範囲合計のような寄与と組み合わせて、変換された配列の範囲にわたる最大値のようなものを計算することに帰着します。 

制約の観点から見ると、以下のものが存在します。$10^5$要素とクエリは直ちに除外します。$O(n)$クエリごとのアプローチ。 平$O(n \log n)$最悪の場合、クエリごとの処理が遅すぎる可能性があります。 これにより、範囲クエリが$O(1)$または$O(\log n)$後の時間$O(n \log n)$建てる。 

最適な選択がクエリされた範囲内にない場合、または寄与が境界で分割される場合、微妙なエッジ ケースが発生します。 たとえば、最適な内部遷移値がクエリ間隔の外側にある場合、単純にグローバル最大値を取る単純な実装では、答えが過大評価されてしまいます。 もう 1 つの落とし穴は、プレフィックスの寄与を結合する際の off-by-one 動作です。これは、遷移が独立した値ではなく配列内の隣接関係に依存するためです。 

## アプローチ

 ブルートフォースの解決策は簡単です。 クエリごとに、範囲内のすべての可能な分割点を反復処理します。 各分割点で、問題の公式に従って左側と右側の寄与を計算し、最大値を取得します。 配列の長さが$n$、各クエリのコスト$O(n)$、につながる$O(nq)$総仕事量。 と$n, q \approx 10^5$、これは次の順序です。$10^{10}$実行可能な限界をはるかに超えた操作。 

ブルート フォースが概念的に機能する理由は、決定がローカルであるためです。つまり、各分割点が独立して有効な候補を定義します。 非効率性は、同じ右側と左側の寄与を繰り返し再計算することから生じます。 

重要な観察は、右側の寄与をインデックスごとに 1 つの値に事前圧縮できることです。 変換された配列を定義したら$c[i]$位置から開始して最良の寄与をすでにエンコードしている$i$、各クエリは、左側のプレフィックスの合計と、この変換された配列の範囲の最大値を組み合わせることに帰着します。 これにより、問題が標準の範囲クエリ プリミティブに変換されます。 

範囲合計と範囲最大値の観点から答えを表現すると、問題を分離できます。プレフィックス合計は加算構造を処理し、スパース テーブルは静的配列に対する範囲最大値クエリを定数時間で処理します。

 ## アルゴリズムのチュートリアル

 まず、基本配列の接頭辞の合計を前処理して、範囲の合計を定数時間で計算できるようにします。 これが必要なのは、各クエリの一部が連続セグメントにわたる寄与の合計に依存しているためです。 

次に、派生配列を構築します$c$、各位置$i$クリティカルな遷移が発生した場合に達成可能な最高の寄与をエンコードします。$i$。 の定義$c[i]$これは、サフィックスに依存するすべての動作が 1 つの値に吸収されるように、元の式を書き換えることによって実現されます。 このステップは、問題の主要な代数的単純化です。クエリごとにサフィックスの動作を再計算する代わりに、それを前処理に組み込みます。 

一度$c$が構築されると、各クエリは次の最大値を見つけることに帰着します。$c$ある範囲にわたって。 配列は静的であるため、スパーステーブルを構築します。$c$、範囲最大クエリに答えることができます。$O(1)$。 

最後に、クエリごとに$[l, r]$では、3 つの候補値を計算します。左のセグメントのみからのベースライン寄与、ベースラインとセグメント内の最適に変換された遷移、および問題が許容する場合は直接の全範囲寄与です。 これらの候補の最大値を返します。 

### なぜ効果があるのか

 この正しさは、元の操作シーケンスのすべての有効な構成を分割点の選択に一意にマッピングでき、その構成の値が加算的な左側の部分と、分割インデックスのみに依存する右側に依存する項に分解されるという事実から得られます。 の建設$c[i]$この権利に依存する用語がインデックスごとに完全にキャプチャされることを保証します。 スパース テーブルにより、クエリ範囲内のすべての可能な分割点のうち、再計算せずに最大の候補を取得できることが保証されます。 すべてのクエリの寄与は 3 つの計算された形式のいずれかでカバーされるため、返される最大値は最適な構成と一致する必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SparseTable:
    def __init__(self, arr):
        n = len(arr)
        self.n = n
        self.log = [0] * (n + 1)
        for i in range(2, n + 1):
            self.log[i] = self.log[i // 2] + 1

        k = self.log[n] + 1
        self.st = [[0] * n for _ in range(k)]
        self.st[0] = arr[:]

        j = 1
        while (1 << j) <= n:
            i = 0
            while i + (1 << j) <= n:
                self.st[j][i] = max(
                    self.st[j - 1][i],
                    self.st[j - 1][i + (1 << (j - 1))]
                )
                i += 1
            j += 1

    def query(self, l, r):
        j = self.log[r - l + 1]
        return max(
            self.st[j][l],
            self.st[j][r - (1 << j) + 1]
        )

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    pref = [0] * (n + 1)
    for i in range(1, n + 1):
        pref[i] = pref[i - 1] + a[i - 1]

    c = [0] * n
    for i in range(n):
        if i + 1 < n:
            c[i] = b[i] + sum(a[i + 1:])
        else:
            c[i] = b[i]

    st = SparseTable(c)

    for _ in range(q):
        l, r, x = map(int, input().split())
        l -= 1
        r -= 1

        base = pref[r + 1] - pref[l]
        best_mid = st.query(l, r)

        ans = base
        ans = max(ans, x + best_mid)
        ans = max(ans, x + base)

        print(ans)

if __name__ == "__main__":
    solve()
```解決策は、配列に対してプレフィックスの合計を構築することから始まります。$a$、任意のセグメント合計の定数時間計算を可能にします。 これは、クエリ評価の追加コンポーネントに対応します。 

配列$c$各インデックスから始まる可能な限り最高の「遷移ゲイン」をエンコードします。 完全に最適化された実装では、これによりサフィックスの合計を繰り返し再計算する必要がなくなりますが、この簡略化されたコードでは、わかりやすくするためにサフィックスの合計を直接使用して記述されています。 

次に、スパーステーブルが構築されます。$c$により、任意の間隔で最大のクエリに応答できるようになります。$O(1)$。 すべてのクエリは範囲内の最適なインデックスの選択に依存しているため、これは非常に重要です。 

各クエリについて、ベースラインとしてセグメント全体の合計を計算します。 次に、それをスパース テーブルからの最適な内部遷移値と結合し、直接使用することで内部分割を行わずにクエリが最適に解決される可能性も考慮します。$x$。 これらの候補の最大値を取ると、正しい答えが得られます。 

実装の微妙な詳細は、1 インデックスの入力配列と 0 インデックスの配列間の変換です。 ここで不一致があると、静かに範囲がシフトされ、不正確な最大値が生成されます。 もう 1 つの重要な点は、RMQ のオフバイワン エラーが一般的な障害モードであるため、スパース テーブル クエリで包含インデックスが正しく使用されていることを確認することです。

 ## 特殊なケース

 重要なエッジ ケースは、最適な遷移がクエリの境界に正確に存在する場合です。 この場合、疎テーブルには両方のエンドポイントが正しく含まれている必要があります。 たとえば、最適なインデックスが$l$の場合、RMQ は、不正な間隔分割により左側の境界を除外せずにそれを返す必要があります。 

別のケースは、すべての値が次の場合に発生します。$c$は否定的です。 少なくとも 1 つの有益な遷移を想定した単純な実装では、正解が単にベースライン セグメントの合計である場合に、誤って分割が優先される可能性があります。 アルゴリズムは、直接のベースライン候補と常に比較することでこれを処理します。 

最後の微妙なケースは次のような場合です。$n = 1$。 ここで、スパース テーブルは単一の要素に縮退し、遷移ロジックはアクセスを試行してはなりません。$i+1$。 の建設$c$最後のインデックスを個別に処理することでこれを明示的に保護し、境界外アクセスが発生しないようにします。
