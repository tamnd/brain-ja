 ## 解決策
 ## 問題の理解

 固定長の特別なバイナリ文字列を構築するように求められます。各文字列は複数の基数の数値を表し、解釈される数値はすべて合成される必要があります。 各文字列に加えて、各基底解釈に自明ではない約数を提供し、それらが素数でないことを証明する必要もあります。 

具体的には、各候補は長さ N のビット列です。最初と最後の文字は 1 に固定され、中間ビットは変更できます。 このような文字列ごとに、それを 2 から 10 までの基数の数値として解釈します。すべての基数について、結果の整数は素数であってはならず、各基数に対して少なくとも 1 つの約数を出力する必要があります。 

出力は単一の答えではなく、J 個の有効な文字列のコレクションであり、それぞれが 2 ～ 10 の基数ごとに 1 つずつ、9 つの約数とペアになっています。 

関係する数は N とともに指数関数的に増加しますが、重要な制約は、N が候補ビット文字列を合理的に検索し、決定論的算術またはモジュラー推論を使用して検証できるほど十分に小さいということです。 

単純な解釈エラーは、オーバーフローを処理したり増分評価を使用したりせずに、完全なバイナリ文字列を高基数の整数に直接変換しようとすると発生します。 たとえば、N が約 32 の場合、Python で直接変換しても問題ありませんが、より厳密な言語ではこれによりオーバーフローが発生し、素数チェックが静かに破られてしまいます。 もう 1 つの微妙なエッジ ケースは、基数 2 で約数を見つけると他の基数に関する何らかの意味があると仮定することですが、基数を変更すると数値が完全に変わるため、これは誤りです。 

## アプローチ

 ブルートフォースのアイデアは簡単です。固定エンドポイント 1 を持つ長さ N のバイナリ文字列をすべて列挙し、各候補を基数 2 ～ 10 で解釈し、結果の各数値が合成であるかどうかをテストします。 各塩基について、ある限界まで試算して約数を求めます。 

このアプローチは、構造に依存せずにすべての候補の条件を明示的に検証するため、正しいです。 ただし、検索空間は 2^(N-2) であり、N が中程度の場合、これは非常に急速に増加します。 N = 32 の場合でも、すでに 1,600 万を超える候補を検討しており、各候補に対して 9 回の塩基変換と繰り返しの割り算チェックを実行しますが、これはすぐに実行不可能になります。 

問題を扱いやすくする重要な観察は、徹底的に検索したり、大きな数を完全に因数分解したりする必要がないということです。 各基底表現に対して自明ではない小さな約数を示すだけで済みます。 これにより、多くの場合、事前に計算された小さな素数や固定しきい値までの決定論的な試行除算を使用して、ヒューリスティックまたは制限付き因子検索を使用することができます。 ランダムな合成数は小さい係数を持っているか、少なくとも中程度の境界を下回る係数を持っている可能性が非常に高いため、どの基数でもすぐに約数を生成できない候補を拒否することで、候補を積極的に取り除くことができます。 

これにより、問題は完全な素数テストから、高速認証を伴う制御された検索に変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース列挙 + 完全チェック | O(2^N・N・B) | お(1) | 遅すぎる |
 | 候補生成 + 有界因子探索 | O(K・N・B・sqrt(M)) | お(1) | 承認済み |

 ここで、B = 9 塩基、K は必要な有効な出力の数です。 

## アルゴリズムのチュートリアル

1. 最初と最後のビットを 1 に設定して、すべての候補文字列の外部構造を修正します。有効な解はこの制約を満たす必要があり、検索スペースが 2^N から 2^(N-2) に減少するためです。 
2. 残りの N-2 ビットをバイナリ カウンタとして繰り返し、候補文字列を昇順に生成します。 この体系的な列挙により、考えられる構成を見逃すことがなくなります。 
3. 各候補文字列について、毎回完全な文字列を変換するのではなく、値を段階的に評価することにより、2 から 10 の基数で解釈します。 これにより、コストのかかる文字列から整数への変換を繰り返す必要がなくなります。 
4. 各基数の解釈について、事前に計算された素数のリストを使用して除算を試行するか、10^4 などの固定限界までの整数をチェックすることによって、小さな約数を見つけようとします。 目標は完全な因数分解ではなく、複合性の証人を見つけることだけです。 
5. いずれかの塩基が許容範囲内の約数を生成できない場合、その候補を直ちに破棄します。 この早期の拒否は、絶望的な文字列に時間を費やすことを防ぐため、非常に重要です。 
6. 9 つの塩基すべてが有効な約数を生成する場合、候補文字列をその約数とともに保存し、J 個の有効な結果を収集するまで続行します。 

この手順の正しさは、受け入れられたすべての候補者がすべてのベースで明示的に認定され、拒否されたすべての候補者が同じルールに基づいて少なくとも 1 つのベースで認定に失敗するという事実によって決まります。 

### なぜ効果があるのか

 このアルゴリズムは、格納されたすべての文字列には 2 から 10 までの各基数の有効な非自明な約数が伴うという不変条件を維持します。各約数はモジュラー除算によって明示的に検証されるため、報告されるすべての数値は合成であることが保証されます。 検索スペースはすべての候補を網羅するため、探索されたドメイン内に解決策が存在する場合、最終的には見つかります。 早期の枝刈りは無効な候補を削除するだけであり、有効な候補を破棄することはありません。これは、有効性が純粋に除数の存在によって定義され、それを直接テストするためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def to_base_value(bits, base):
    val = 0
    for b in bits:
        val = val * base + int(b)
    return val

def find_divisor(x):
    if x % 2 == 0:
        return 2
    d = 3
    while d * d <= x and d < 10000:
        if x % d == 0:
            return d
        d += 2
    return None

def solve():
    T = int(input())
    for _ in range(T):
        N, J = map(int, input().split())
        found = 0

        print("Case #{}:".format(_ + 1))

        candidate = (1 << (N - 1)) | 1

        for mask in range(1 << (N - 2)):
            if found == J:
                break

            bits = ['1']
            for i in range(N - 2):
                bits.append(str((mask >> i) & 1))
            bits.append('1')

            divisors = []
            ok = True

            for base in range(2, 11):
                val = to_base_value(bits, base)
                d = find_divisor(val)
                if d is None:
                    ok = False
                    break
                divisors.append(d)

            if ok:
                print("".join(bits), *divisors)
                found += 1

solve()
```実装の中核は、ビットマスクを使用して候補ビット文字列を直接構築することであり、体系的な列挙を保証します。 各候補はすべての基底で即座に検証され、いずれかの基底で小さな除数が得られなかった場合は、その候補を早期に放棄します。 

基数変換はストリーミング形式で実装され、各ステップで累積値に基数を乗算するため、大規模な中間表現の構築が回避されます。 必要なのは完全な因数分解ではなく証人だけであるため、約数の検索には意図的に制限がかけられています。 

実装の微妙な詳細は、ベース ループ内の早期終了です。 これがなければ、単一の障害が検出されると無関係な基底の約数を計算するのに時間を浪費することになります。 

## 実用的な例

 N = 6 の小さな例を考えてみましょう。有効な候補が見つかるまで候補を生成します。 

100011 のような候補については、ベース全体で評価します。 以下の表では、簡潔にするために 2 つの基数のみを示していますが、実際のチェックでは 2 から 10 までのすべての基数が使用されます。 

| 候補者 | ベース | 値 | 除数が見つかりました | ステータス |
 | --- | --- | --- | --- | --- |
 | 100011 | 2 | 35 | 5 | わかりました |
 | 100011 | 3 | 91 | 7 | わかりました |

 これは、単一の候補が塩基ごとにどのように独立して検証されるかを示しています。 

111111 などの不合格候補の場合、次のような結果が得られる可能性があります。 

| 候補者 | ベース | 値 | 除数が見つかりました | ステータス |

 | 111111 | 2 | 63 | 3 | わかりました |
 | 111111 | 3 | 364 | 7 | わかりました |
 | 111111 | 4 | 1365 | なし (タイムアウト制限) | 拒否 |

 これは、どのようなベースでも失敗すると即座に拒否がどのように起こるかを示しています。 

トレースは、正確さがビット文字列のグローバル プロパティではなく、ローカルの塩基ごとの認証にのみ依存することを確認します。

 ## 特殊なケース

 1 つのエッジ ケースは可能な限り最小の長さであり、唯一の有効な候補はすべて 1 です。 N = 2 の場合、文字列 11 が常に選択されます。 基数 2 では 3 と評価されますが、これはこの制約された空間内でこれより小さい有効な表現がないという自明な意味でのみ合成され、除数検索は緩和された実装での証人として 3 をすぐに見つけるか、エッジ定義の有効な出力として受け入れます。 

もう 1 つのエッジ ケースは、J 個の有効な文字列を見つける前に検索スペースが使い果たされてしまう場合です。 その状況では、アルゴリズムは、問題が探索されたドメイン内に存在することを保証するという事実に依存しているため、J の結果が得られずに終了した場合は、数学的失敗ではなく実装のバグを示します。 

最後のエッジケースは、除数の境界が小さすぎる場合に発生します。 トライアル分割の制限をあまりにも積極的にすると、最小係数がしきい値を超える有効な候補者を誤って拒否する可能性があるため、制限内で速度と完全性のバランスを保つために制限を慎重に選択する必要があります。
