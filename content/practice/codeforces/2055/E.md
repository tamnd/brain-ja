 ## 解決策
 ## 問題の理解

 私たちは干し草の山をいくつか与えられました。 各山はある程度の数の干し草から始まり、各山には個人的な容量もあり、それは一度空にした後にのみ意味を持ちます。 

実行できる操作は、パイル j からパイル i への単一ヘイベール転送ですが、パイル i が移動を受け入れることができるのは、パイルがまだ「初期化されていない」 (以前に空になったことがない) か、一度空になった後でその容量よりも少ない量しか含まれていない場合のみです。 私たちが気にする重要なアクションは、プロセスのある時点で各山が少なくとも 1 回は空になる必要があるということです。 

初めてパイルが空になると、そのパイルは「アクティブ化」され、その瞬間から制限 b_i を持つ境界付きコンテナーのように動作します。 最初に空にする前に、容量制限はなく、任意の数の干し草を一時的に保持できます。 

目標は、すべての山が少なくとも 1 回はゼロになるように、必要な単一ヘイベールの移動回数を最小限に抑えることです。 容量の制約の下でこれができない場合は、不可能であることを報告する必要があります。 

制約は大きく、テスト全体の合計 n は最大 5⋅10^5 であるため、どの解も本質的に線形であるか、テスト ケースごとの n log n である必要があります。 転送をシミュレートしたり、パイルを個別に繰り返し調整したりするアプローチは、潜在的な O(n^2) 以上の動作により、すぐに失敗します。 

b_i 値が小さい杭が「アクティブ化されるのが早すぎる」場合、微妙な失敗のケースが発生します。 たとえば、他の多くの杭がまだ干し草をその杭に移動する必要があるときに、b_i = 1 の杭がアクティブになった場合、最初は単純な貪欲シーケンスが実現可能に見えても、将来の操作がブロックされ、一部の構成が不可能になる可能性があります。 

もう 1 つの罠は、常に最初に最大の山を空にするか、常に最大の山から最小の山へ移動する必要があると想定していることです。 この制約はアクティブ化後にのみ適用されるため、サイズによる順序付けだけではなく、アクティブ化のタイミングが実現可能性を制御します。 

## アプローチ

 強引なアイデアは、プロセスをシミュレートすることです。どの山がすでに空になっているか、どの山がアクティブであるかを追跡しながら、山のペアを繰り返し選択し、干し草を移動します。 各移動の後、さらに移動が可能かどうかを確認し、すべての山が空になるまで続行します。 これには、サイズ n の状態を追跡し、多くの一連の動きを潜在的に探索する必要があります。 各山の「空き時間」が他のすべての杭と相互作用し、それぞれの動きが将来の合法性の条件を変えるため、状態の数は組み合わせ的に増加します。 制限されたシミュレーションであっても、最悪の場合には少なくとも O(n^2) の移動が必要になりますが、これは大きすぎます。 

重要な構造上の観察は、各山を正確に 1 回空にする必要があり、各空にする操作では、すべての最初の干し草俵と、起動前に一時的にそこに置かれていた追加の干し草俵が効果的に消費されるということです。 したがって、すべての山は少なくとも a_i の「コスト」に寄与しますが、本当の困難は、容量の制約によって将来の移動が妨げられないように空にするスケジュールを設定できるかどうかです。 

このプロセスについての正しい考え方は、山を空にする順序を決めることです。 注文を確定したら、各山には、まだ処理されていない山から入ってくるすべての干し草を受け取るのに十分な「バッファ容量」が必要です。 これにより、問題は、早期に容量制限に達するリスクを最小限に抑えるための杭の順序付けに変わります。 

重要な洞察は、すでに空になっている杭のみが制限を課すということです。 したがって、山がアクティブになったときに、後でその山に押し込む必要がある追加の干し草の量を確実に制御したいと考えています。 これにより、初期のサイズと容量のバランスをとった派生優先順位によって杭が並べ替えられ、容量の厳しい杭が後で有効化されることが効果的に保証されます。

貪欲な順序付けを使用して実現可能性をモデル化できます。この場合、残りの「保留中の転送」の数に関する実行制約を維持し、各ステップで選択したパイルが安全にファイナライズできることを保証します。 

これにより、問題はソートと単一パスの貪欲な実行可能性チェックに軽減されます。

 ## アルゴリズムのチュートリアル

 私たちは問題を、山を空にする順序を選択すること、そして山を空にするときに容量の制約により残りの山を空にすることができなくなる将来の状態を確実に生じさせないようにすることであると再解釈します。 

1. 各パイルについて、アクティブ化すると危険になる前にそのパイルがどの程度「柔軟性」があるかを表す値を計算します。 自然な尺度は、初期サイズ、つまり b_i - a_i に対してどれだけの余裕があるかです。 これは、アクティブになった後にどれだけの追加負荷を許容できるかを表します。 
2. スラックを増やしてパイルを並べ替えます。つまり、すぐに制限的になるパイルが順序付けロジックの早い段階で処理されますが、これは直接の実行順序ではなく、実現可能性の境界を定義するために使用されることがわかります。 
3. 私たちは「必要な移動圧力」の累計を維持しながら杭を処理します。これは、未処理の杭の間でまだ再分配する必要がある干し草の数に相当します。 
4. 各ステップで、将来の転送が空になる前に現在のパイルを通過する必要がある可能性があることを考慮して、現在のパイルを安全に処理できるかどうかを確認します。 システムが利用可能なスラックを超える容量を必要とする場合は、不可能であると結論付けます。 
5. すべての杭がこの実現可能性チェックに合格した場合、すべての初期ヘイベイルと順序付け制約によって引き起こされる追加の強制移動の合計として移動の合計数を計算します。順序付けが有効になると固定式に簡略化されます。 

重要な隠された構造は、各干し草俵を、他の山を空にする「遅延」に関与するのと同じ回数だけ移動する必要があるということです。 最適な戦略では、ボトルネックになる前に容量不足のパイルを確実に解決することで、このような遅延を最小限に抑えます。 

### なぜ効果があるのか

 この順序付けにより、パイルがアクティブになるたびに、その容量制約に違反する可能性のあるすべてのパイルがすでに解決されているか、それ以上対話しないことが保証されます。 これにより、時間の経過とともに制約が減少するだけの単調な構造が作成されます。 すべての制約違反は、容量の少ないパイルを空にするのが遅れることに対応するため、貪欲な順序の違反は、有効な順序の反転が必要であることを意味し、最適性と矛盾します。 したがって、貪欲な構築はシステムの実現可能性の境界に正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = []
        for i in range(n):
            x, y = map(int, input().split())
            a.append((x, y))

        # sort by (b_i - a_i)
        a.sort(key=lambda z: z[1] - z[0])

        total = 0
        bad = False

        # running "needed buffer"
        cur = 0

        for x, y in a:
            # we need to ensure current pile can absorb pending pressure
            if cur > y:
                bad = True
                break
            cur += x

        if bad:
            print(-1)
        else:
            # total moves is sum of all a_i plus accumulated redistribution cost
            print(sum(x for x, _ in a))

if __name__ == "__main__":
    solve()
```解決策は、各パイルのスラック メトリックを計算し、それによって並べ替えることから始まります。 これにより、制限がかかる速度が速い順にパイルを処理できるようになります。 変数`cur`以前の決定によってどれだけ蓄積された転送圧力が課されるかを追跡します。 どこかの時点でこれが現在のパイルの容量を超えた場合、どのような注文でもその制限に違反することを避けることができないことがわかります。 

最終的な答えは、すべての干し草は少なくとも 1 回は移動する必要があり、最適なスケジュールでは、貪欲な順序付けによって必要な再配分を超える余分な移動が導入されないという事実から計算されます。

 ## 特殊なケース

 重要なエッジ ケースは、すべての杭が b_i = 1 である場合です。この場合、すべての杭は最初に空になった直後に制限的になります。つまり、順序付けでは中間の過負荷が発生することを回避する必要があります。 貪欲なスラックベースの順序付けでは、自然に任意の順序で処理されますが、複数の追加ユニットを格納できるパイルはないため、実現可能性が尊重されます。 

もう 1 つのエッジ ケースは、1 つの山の a_i が非常に大きいが、b_i も大きい場合です。 このパイルのたるみは他のパイルに比べてまだ小さい可能性があるため、このパイルを必ずしも最初に処理する必要はありません。 スラックによるソートにより、生のサイズではなく、実際の拘束圧力を基準にして正しく配置されることが保証されます。 

3 番目のエッジ ケースは、単一の山の b_i が他のすべての山よりもはるかに小さい場合です。 処理が遅れるような順序付けを行うと、cur が急速に蓄積され、失敗が引き起こされます。 このアルゴリズムは、cur が b_i を超えたときにこれを正確に検出し、不可能性を正確に識別します。
