 ## 解決策
 ## 問題の理解

 1 から n までのラベルが付けられたお菓子が円形に配置されています。 それぞれのお菓子には「好き」か「嫌い」があります。 アーニャは、サークルからお菓子を 1 つずつ取り除く決定的なプロセスを実行します。 

このプロセスには、すべてのテスト ケースに 2 つのフェーズがあります。 まず、どこにでも好きな甘いものがあれば、好きかどうかに関係なく、すぐに1番の甘いものを食べます。 以降、同じ動作ルールを繰り返し、次に残ったお菓子から時計回りにk個ずつ数え、k番目に着いたお菓子を食べる。 取り除くたびに円は閉じられ、次のステップは常に、食べたばかりの甘いものから時計回りにすぐに始まります。 

このプロセスは、サークル内に好きなお菓子がなくなるまで続き、その時点ですぐに停止します。 出力は、途中で削除された気に入ったものと嫌いなものの両方を含む、合計で食べたお菓子の数です。 

すべてのテスト ケースの合計 n が最大 5000 であるという制約により、すべてが変わります。 すべてのテスト ケースの合計作業量が数千万回のオーダーにとどまるため、食べるスイーツごとに O(n) を費やすシミュレーションは許容されます。 ここでは、バランスのとれたツリーのような重いデータ構造に依存するソリューションは必要ありませんが、注意深くインデックスを作成せずにステップごとに配列の完全な再スキャンを単純に繰り返すと、依然として時間がかかりすぎたり、バグが発生しやすくなる可能性があります。 

いくつかの微妙なエッジケースが自然に現れます。 

気に入ったお菓子がまったくない場合、たとえルールに最初のチェックが記載されていたとしても、プロセスは実際に「適切に開始」されることはなく、答えはゼロになります。 

最初のお菓子が唯一気に入ったものであれば、それはすぐに食べられ、たとえサークル内でさらに多くのステップが可能であっても、プロセスはすぐに停止します。 

もう 1 つの注意が必要な状況は、残っているお菓子の数に対して k が大きい場合です。 カウントは円を一周するため、モジュラー演算を忘れたり、削除されたスイーツが除外されることを忘れたりする実装は、範囲外になるか、間違ったターゲットを選択することになります。 

3 番目のよくある失敗は、好きなお菓子だけを気にしていると仮定して配列をフィルタリングすることです。 異なるお菓子は引き続きカウントに参加し、将来のすべてのポジションに影響を与えるため、プロセスが中断されます。 

## アプローチ

 このプロセスについて考える最も直接的な方法は、文字通り円をシミュレートすることです。 私たちは生きているお菓子の現在のリストを維持し、ルールに従って要素を繰り返し削除します。 それぞれの削除では、残りの円を歩いて k 番目の次の要素を見つける必要があります。 円は時間の経過とともに縮小するため、削除ごとに最悪でも O(n) 回の作業になります。 

最悪の場合、ほぼすべてのお菓子が食べられるため、O(n) 回の削除を実行し、各削除に O(n) コストがかかり、テスト ケースあたりの総作業量は O(n²) になります。 テスト全体の合計 n が 5000 に制限されているため、これは依然として許容範囲内です。 

重要な観察は、プロセスにおいて線形よりも高速な選択を必要とするものは何もないということです。 範囲、合計、カウントをクエリする必要はありません。 縮小する循環リストを段階的に進めていくだけで済みます。 つまり、生きている要素の単純な配列で十分であり、それを循環インデックス構造として扱うことができます。 要素を削除した後、その後続の要素から続行し、現在のアライブ リストのその位置から k-1 ステップ進めることによって次のターゲットが見つかります。 

これにより、問題は動的なリスト上の制御されたシミュレーションに帰着され、正確性は生きているシーケンス内の現在位置を維持することのみに依存します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 慎重なインデックス作成を行わないブルート フォース シミュレーション | テストあたり O(n²) | O(n) | 危険 / TLE またはバグの可能性 |
 | 最適化されたリストベースの循環シミュレーション | O(n²) 合計 | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

生きているインデックスの配列を使用して円を明示的にシミュレートします。 

1. リストを作成する`alive = [1, 2, ..., n]`現在のサークルを表します。 ポインタも維持します`idx`このリスト内の現在位置を示します。 最初は`idx = 0`、スイート1に対応します。 
2. 最初に好きなお菓子がいくつあるか数えます。 これにより、プロセスが有意義に開始されるかどうかを判断できます。 
3. 少なくとも 1 つの好きな甘いものがあれば、すぐに甘い 1 を削除します。`idx = 0`、これはに対応します`alive[0]`。 sweet 1 がいいねされた場合、いいねされたカウンタをデクリメントします。 
4. 要素を削除した後は、後戻りしたり再起動したりしません。 私たちは保管します`idx`同じ位置にあり、縮小されたリストの次の要素を参照します。 
5. 気に入ったお菓子がまだ残っている間に、次のことを繰り返します。 

- 移動`k-1`モジュラー演算を使用して循環リストを前進させます。`idx = (idx + k - 1) % len(alive)`。 
- 要素を削除します`alive[idx]`必要に応じて、いいねカウンタを更新します。 
- 削除後、次の開始位置は自然に`idx`リストが左にシフトし、次の要素がこのインデックスを占めるためです。 
6.好きなお菓子がなくなったらすぐにやめてください。 

### なぜ効果があるのか

 重要な不変条件は次のとおりです`alive`常に、残りのお菓子の現在の時計回りの順序を正確に表します。`idx`は常に、その順序で次の開始位置を指します。 すべての操作は、現在の要素を削除するか、循環リスト内の固定ステップ数だけ進みます。これは、残りのスイーツを時計回りにカウントするという問題の定義と正確に一致します。 現在の構成を超えて過去の履歴に依存するステップはないため、この状態によって将来のすべての動きが完全に決定され、正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        s = input().strip()

        alive = list(range(1, n + 1))
        idx = 0

        liked = [c == '1' for c in s]
        liked_cnt = sum(liked)

        eaten = 0

        if liked_cnt == 0:
            print(0)
            continue

        # initial forced eat of 1
        eaten += 1
        if liked[0]:
            liked_cnt -= 1

        # remove index 0
        alive.pop(0)
        liked.pop(0)
        if not alive:
            print(eaten)
            continue

        idx = 0

        while liked_cnt > 0 and alive:
            idx = (idx + k - 1) % len(alive)

            if liked[idx]:
                liked_cnt -= 1

            alive.pop(idx)
            liked.pop(idx)
            eaten += 1

            if idx == len(alive):
                idx = 0

        print(eaten)

if __name__ == "__main__":
    solve()
```このソリューションは、縮小リストを使用して循環プロセスを直接エンコードします。 唯一の微妙な点は、削除後のポインターの処理です。要素が削除されると、次の候補は自然に同じインデックスに移動します。ただし、最後の要素を削除した場合はゼロに戻ります。 

また、どのお菓子が好かれているかのブール値リストを明示的に保持しているので、削除ごとに O(1) で残りの好まれているカウンターをデクリメントできます。

 ## 特殊なケース

 重要なエッジケースは、最初のスイーツが唯一好まれるものである場合です。 その状況では、アルゴリズムは位置 1 を即座に読み取り、like カウンタを 0 にデクリメントし、循環スキップが開始される前に停止します。 削除するたびに停止条件がチェックされるため、状態は正しく折りたたまれます。 

もう 1 つのエッジ ケースは、k が残りのお菓子の数よりも大きい場合に発生します。 インデックスの更新には剰余演算が使用されるため、`idx = (idx + k - 1) % len(alive)`の場合、リストを明示的に繰り返す必要がなく、選択内容が複数回正しく循環されます。 これにより、範囲外のアクセスが防止され、テーブルを物理的に複数回巡回するのと同じ動作が保証されます。 

すべてのスイーツが気に入らない場合、アルゴリズムは気に入った要素を数えた直後にゼロを返し、不必要なシミュレーションを回避します。
