 ## 解決策
 ## 問題の理解

 私たちは、方向性のない「隣人」関係によって接続された研究室の集合と協力しています。 各ラボには、最初はいくつかの机とモニターが含まれています。 個々のラボにデスクやモニターを追加するため、時間の経過とともにこれらの数値は変化します。 

重要な問題は、研究室を評価するときに、それを単独で見ていないことです。 ラボの「利用可能な」デスクとモニターは、そのラボ自体のリソースと、直接接続されている隣接するラボのすべてのリソースの合計として定義されます。 グラフの 1 つのエッジを超えるものは何も寄与しません。 

したがって、関心のあるすべてのクエリは、あるノードを取得し、その閉じた近傍 (それ自体とすべての隣接するノード) の値を集計した場合、デスクがモニターを超えているのか、モニターのほうが高いのか、それとも等しいのか、ということを問うことになります。 

入力制約により、3 つの次元すべてが最大 100000 に設定されます。グラフは疎または密になる可能性があります。 操作の数が十分に多いため、クエリごとに近傍合計を最初から再計算すると、最悪の場合、時間がかかりすぎます。 クエリごとの隣接リストのフル スキャンは、密なグラフでは二次的な動作に低下します。これは、Python の 5 秒制限の下では実行できません。 

更新に伴う微妙な問題が発生します。各「追加」操作で変更されるのは 1 つのノードのみですが、そのノードを集約に含むすべての近隣ノードの応答に影響します。 要求された場合にのみすべてを再計算する単純なソリューションでは、隣接リストを繰り返し再スキャンするか、構造を維持せずにオンデマンドで再計算するかのどちらかになり、どちらの場合も TLE の危険があります。 

明示する価値のあるエッジケースは、グラフ構造に由来します。 

グラフに多くの隣接ノードがある 1 つのノード (たとえば、中心が 1 の星) がある場合、葉に対するすべてのクエリで高次のノードによる合計が必要になります。 単純なクエリごとの隣接トラバーサルはリーフにはまだ問題ありませんが、センターへの更新は多くのリーフに間接的に影響します。 グラフが密な場合、対称性の問題が発生します。つまり、各クエリがほぼすべてのノードに触れます。 

もう 1 つのエッジ ケースは、孤立したノードです。 ノードに隣接ノードがない場合、その答えはそれ自体にのみ依存します。 少なくとも 1 つのネイバーが空の隣接リストに誤ってアクセスしたり、初期化を誤って処理する可能性があると想定する不用意な実装ですが、論理的には、これらのノードは定数時間の自明な答えになるはずです。 

最後に、更新を繰り返すことが重要です。 各更新の規模は小さいですが、最大 100,000 件存在する可能性があるため、更新ごとにすべてのノードに伝播することは許容できません。 

## アプローチ

 簡単なアプローチは、グラフを保存し、クエリごとに、クエリされたノードとそのすべての隣接ノードのデスクとモニターの合計を再計算することです。 これは、ノードの隣接リストを反復処理し、両方の値を累積することで機能します。 

可用性の定義は閉じた近傍に対して純粋にローカルであるため、これは正しいです。 ただし、この方法では、クエリごとにすべての近傍をスキャンするコストがかかります。 ノードの次数が N に近い最悪の場合のグラフでは、各クエリは線形になります。 最大 100,000 のクエリでは、最悪の場合、10^10 の演算に近い複雑さになりますが、これは現実的ではありません。 

実際の非効率性は、更新が実質的にローカライズされていないことです。1 つのノードを変更すると、その隣接ノードすべての将来のクエリ結果に影響します。 最初から再計算するのではなく、部分的に集約された情報を維持したいと考えています。 

重要な点は、隣接リストが低次と高次の 2 種類のノードに分割できることです。 次数の大きいノードを特別に扱うと、それらの事前計算された近傍合計を維持できます。 その後、更新は、更新されたノードに隣接する高次ノードに伝播するだけで済みます。 高次ノードの数が少ないため、総作業量が制限されます。

これにより、標準的な「グラフ次数に重点を置いた」最適化が行われます。つまり、低次数のノードについては安価に答えを再計算し、高次数のノードについてはキャッシュされた集計を維持します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとのブルート フォース再計算 | O(Q・度) 最悪 O(NQ) | O(N + M) | 遅すぎる |
 | 次数分解（重光） | O((N + Q)√M) | O(N + M) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは 2 つの並列システム (1 つはデスク用、もう 1 つはモニター用) を維持していますが、どちらも同じように動作します。 

√M 付近のしきい値 B を選択します。 次数が B より大きいノードはヘビー ノードと呼ばれ、残りはライト ノードと呼ばれます。 

### ステップ

 1. すべてのノードをその程度に基づいて重いまたは軽いとして分類します。 

これにより、重いノードの数が最大でも O(M / B) となり、小さいことが保証されます。 
2. すべてのノードの隣接リストを事前計算し、近隣ノードに対する反復を通じて暗黙的にのみ逆構造を構築します。 

逆エッジは明示的に必要ありません。 更新中に隣接リストをスキャンします。 
3. すべての重いノードについて、その閉じた近隣全体にわたるデスク (またはモニター) の合計を表す実行値を維持します。 

最初は、これは隣接リストに対する 1 回のパスによって計算できます。 
4. 次の方法で更新「ノード u に値を追加」を処理します。 

まず、u の生の値を更新します。 

次に、u のすべての近傍 v を反復処理します。 

v が重い場合は、キャッシュされた近傍合計を同じデルタだけ更新します。 

これは正しいです。なぜなら、v が u に隣接している場合、u は v の近傍に正確に寄与するからです。 
5. ノード u に対するクエリの場合:

 u が重い場合は、キャッシュされた値を直接返します。 

u が軽い場合、すべての近傍を反復処理し、それらの現在の値とそれ自体を合計することによって、その答えを計算します。 

ライト ノードの次数は最大でも B であるため、これは許容されます。 
6. 同じ構造をデスクとモニターに対して個別に繰り返し、クエリごとに 2 つの結果を比較します。 

### なぜ効果があるのか

 正確さは、すべてのヘビー ノードが常にその閉じた近傍全体の正確な合計を格納するという不変条件に基づいています。 ノードが変更されるたびに、そのデルタがそれに依存するすべての重い隣接ノードに直ちに伝播されるため、これは当てはまります。 ライト ノードはキャッシュされないため、必要なときに常に正確に再計算されます。 すべてのクエリは正しいキャッシュを使用するか、現在の基本値から直接再計算するため、古い情報は使用されません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class HeavyLight:
    def __init__(self, n, adj, vals, B):
        self.n = n
        self.adj = adj
        self.val = vals[:]  # base values
        self.B = B

        self.heavy = [False] * (n + 1)
        for i in range(1, n + 1):
            if len(adj[i]) > B:
                self.heavy[i] = True

        self.heavy_sum = [0] * (n + 1)

        for i in range(1, n + 1):
            if self.heavy[i]:
                s = self.val[i]
                for v in adj[i]:
                    s += self.val[v]
                self.heavy_sum[i] = s

    def add(self, u, delta):
        self.val[u] += delta
        for v in self.adj[u]:
            if self.heavy[v]:
                self.heavy_sum[v] += delta

    def query(self, u):
        if self.heavy[u]:
            return self.heavy_sum[u]
        res = self.val[u]
        for v in self.adj[u]:
            res += self.val[v]
        return res

def solve():
    n, m, q = map(int, input().split())
    d = list(map(int, input().split()))
    e = list(map(int, input().split()))

    adj = [[] for _ in range(n + 1)]
    for _ in range(m):
        a, b = map(int, input().split())
        adj[a].append(b)
        adj[b].append(a)

    B = int(m ** 0.5) + 1

    desks = HeavyLight(n, adj, [0] + d, B)
    mons = HeavyLight(n, adj, [0] + e, B)

    out = []

    for _ in range(q):
        parts = input().split()
        if parts[0] == "add":
            typ = parts[1]
            cnt = int(parts[2])
            u = int(parts[3])
            if typ == "desk":
                desks.add(u, cnt)
            else:
                mons.add(u, cnt)
        else:
            u = int(parts[1])
            ds = desks.query(u)
            ms = mons.query(u)
            if ds > ms:
                out.append("desks")
            elif ms > ds:
                out.append("monitors")
            else:
                out.append("same")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装では基本値が保持されます。`val`、そして使用します`heavy_sum`次数がしきい値を超えるノードのみ。 更新は、キャッシュされたノードにのみ伝播されます。 これにより、完全な再計算が回避されます。 

よくある落とし穴は、アップデートがデスクとモニターの両方に対称的に影響を与えることを忘れていることです。 両方の構造が同じグラフと独立した値レイヤーを受け取る必要があります。 もう 1 つの微妙な問題は、ノード自体がクエリ定義の一部であるため、近傍だけでなく閉じた近傍を使用して重い合計を初期化することです。 

## 実用的な例

 提供されたサンプルを使用して:

 ### トレース (1 つのクエリ フローの部分図)

 | 操作 | ノード | 影響を受けるデスクの値 | 影響を受けるモニター値 | 大量のキャッシュ変更 |
 | --- | --- | --- | --- | --- |
 | 初期化 | すべて | 基本配列 | 基本配列 | 重いノードが事前に計算される |
 | チェック2 | 2 | 合計(2 + 近傍) | 合計(2 + 近傍) | なし |
 | デスク 1 を追加 | 1 | d[1] += x | - | ヘビーネイバーを更新する |
 | チェック2 | 2 | 再計算またはキャッシュ | 再計算またはキャッシュ | なし |

 示されている重要な動作は、更新後、ノード 1 のヘビーネイバーのみがキャッシュされた合計を調整することです。 他のノードは、クエリされるまで影響を受けません。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((N + Q)√M) | 各更新は重度の隣接要素のみに影響を与えます。 ライト ノードの各クエリは、最大 √M の隣接サイズをスキャンします。 
| スペース | O(N + M) | グラフ ストレージとノードごとの値および大量のキャッシュ |

 しきい値を選択すると、すべての操作にわたる合計隣接スキャンが制限されたままになります。 密なグラフであっても、制御された数のノードのみが重いノードとして扱われるため、二次関数の爆発が防止されます。

## 特殊なケース

 単一の孤立したノードが最も単純な状況です。 隣接リストは空であるため、クエリはノード自身のデスクとモニターの値を比較することになります。 ライトノードのクエリ ループは空のリストを反復し、基本値のみを返すため、アルゴリズムはこれを自然に処理します。 

スター グラフでは、次数がしきい値を超えると中心ノードが重くなります。 リーフへの更新はすべてセンターのキャッシュされた合計に伝播され、センターでのクエリが O(1) のままになることが保証されます。 リーフは軽いままで、1 つの隣接ノード上で再計算されるため、頻繁な更新下でも動作が安定します。 

完全に密なグラフでは、ほぼすべてのノードが重くなりますが、しきい値によって重いノードの数が M に比べて小さいことが保証されるため、これは制御されます。更新は依然として隣接リストに沿ってのみ伝播し、総作業量はクエリごとのフル スキャンではなく、操作全体の度数の合計によって制限されたままになります。
