 ## 解決策
 ## 問題の理解

 固定文字列と多くの部分文字列クエリが与えられます。 クエリごとに、部分文字列を取得し、そのすべてのサフィックスに対して特定の集計を計算します。 

文字列の場合、位置の Z 関数`i`文字列のプレフィックスが、次の部分文字列と一致する長さを測定します。`i`。 文字列の「Ж 関数」は、各開始位置におけるこれらすべての Z 値の合計です。 したがって、部分文字列については、概念的にそれをそれ自体のすべての接尾辞と比較し、各接尾辞がその接頭辞と一致する長さを測定し、それらの長さを合計します。 

各クエリは、元の文字列の異なる部分文字列に対するこの合計を要求します。 

この難しさは、クエリの数と文字列の長さが両方とも 200,000 に達する可能性があるという事実から生じます。 クエリごとに Z 値を最初から再計算するソリューションでは、クエリごとに線形スキャンを行っても、最悪の場合は 2 次の動作が発生するため、速度が非常に遅くなります。 

単純なアプローチには 2 番目の罠も隠されています。Z 関数は部分文字列の内部構造のみに依存します。 元の文字列内の複数の位置で一致がどのように動作するかを慎重にモデル化しない限り、任意のスライスと直接互換性はありません。 

いくつかの危険な状況は、不注意なアプローチが失敗する例を示しています。 部分文字列が次のような定数の場合`"aaaaa"`、すべての接尾辞が完全に一致し、答えは二次関数的に増加します。 すべての文字が個別である場合、すべての Z 値は最大でも 1 となり、答えは線形になります。 「典型的な」小さな Z 値を仮定するソリューションは、すべてが等しい場合には失敗しますが、ペアをスキャンしてマッチングを再計算しようとするソリューションは、繰り返される大きなブロックでは失敗します。 

## アプローチ

 ブルート フォース ソリューションでは、各クエリ部分文字列の Z 関数が個別に再計算されます。 長さの部分文字列の場合`m`、これには費用がかかります`O(m)`標準の Z アルゴリズム以上を使用`q`これにより劣化する可能性があるクエリ`O(nq)`最悪の場合。 両方とも`n`そして`q`200,000 までは不可能です。 

重要な観察は、Z 関数は基本的に、文字列のサフィックスと文字列自体の間の最長の共通プレフィックスに関するものであるということです。 接尾辞の比較という観点から考えると、それぞれの値は`z[i]`サフィックス間の LCP に対応します`i`と接尾語`1`。 

固定部分文字列の場合、合計するのは次のとおりです。 

それぞれのポジション`i`で始まるサフィックス間の LCP に貢献します。`i`およびサブストリングのルートから始まるサフィックス。 

これにより、問題は元の文字列のサフィックスに対する LCP クエリの繰り返しに変換されます。 このように再フレーム化すると、自然な構造は LCP 前処理を備えたサフィックス配列になります。 サフィックス配列を使用すると、任意の 2 つのサフィックス間の LCP に応答できます。`O(1)`LCP 配列に対する範囲最小クエリを使用します。 

残りの課題は、クエリ部分文字列ごとに集計することです。`[l, r]`、全体の合計`i in [l, r]`の:

 LCP(suffix(l + i - 1), suffix(l)) ですが、部分文字列境界によって切り捨てられます。 

これは、サフィックス ランクに関する範囲の問題に帰着します。この問題では、寄与は、並べ替えられた順序で隣接するサフィックスを比較し、クエリ間隔内で一致がどこまで続くかを維持することに依存します。 

標準ソリューションでは、フェンウィック ツリーまたはセグメント ツリーと組み合わせたサフィックス配列順序のスイープを使用し、LCP を追跡しながらサフィックスの各ペアの寄与を処理し、これらの寄与を間隔に両方のサフィックスが含まれるすべてのクエリにマッピングします。 

これにより、問題は「部分文字列ごとの Z の計算」から「ペアごとの LCP 寄与を間隔にわたって分散」に変わり、これが重要な構造的変化です。

 | --- | --- | --- | --- |
 | クエリごとのブルート フォース Z | O(nq) | お(1) | 遅すぎる |
 | サフィックス配列 + LCP + オフライン集計 | O(n log n + q log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 文字列のサフィックス配列を構築します。 これにより、すべての接尾辞が辞書順に並べられ、比較を繰り返し再計算する代わりに、ローカルで LCP 構造を推論できるようになります。 
2. 隣接するサフィックスの LCP 配列をサフィックス配列の順序で計算します。 これにより、隣接するサフィックス間に最も長い共通プレフィックスが与えられ、RMQ を介してすべてのペアごとの LCP 情報が暗黙的にエンコードされます。 
3. 各サフィックスについて、サフィックス配列内の位置を記録します。 これにより、部分文字列の開始位置をサフィックスの順序付けにおけるランクに変換できるようになります。 
4. 部分文字列のクエリを再解釈する`[l, r]`位置から始まるサフィックスを操作する場合`l..r`。 各サフィックスは、次のサフィックスとどの程度一致するかに基づいて寄与します。`l`。 
5. 接尾辞のペアの寄与を観察します。`(i, j)`のみに依存する`LCP(i, j)`開始位置がクエリ間隔内にあるかどうか。 クエリごとに計算する代わりに、すべてのペアにわたる寄与を蓄積します。 
6. 単調スタックのアイデアを使用して、LCP 配列から導出された構造内のペアを並べ替えまたは処理します。各 LCP 値は、最小値となる範囲を定義し、そのペアの主要な一致長を定義します。 
7. サフィックス位置に対してフェンウィック ツリー (またはセグメント ツリー) を使用して、間隔のアクティブなエンドポイントを維持し、ペアを昇順にアクティブ化するときに LCP 値に比例する寄与を追加します。 
8. 各クエリについて、データ構造全体のプレフィックス合計を使用して、その間隔に制限された累積寄与を計算します。 

### なぜ効果があるのか

 部分文字列内のすべての Z 値は、開始位置がその部分文字列内にある 2 つの接尾辞間の LCP であり、接尾辞の 1 つが左側の境界になります。 したがって、Ž 関数の合計は、区間内の接尾辞のすべてのペアの合計であり、共通の接頭辞の長さによって重み付けされますが、部分文字列の境界によって切り捨てられます。 サフィックス配列は、繰り返された比較を構造に圧縮し、各 LCP 値がセグメント全体の最小値として 1 回だけ考慮され、二重カウントが発生しないようにします。 Fenwick の累積により、有効な各ペアが、その間隔に両方のエンドポイントが完全に含まれるクエリに正確に寄与し、正確さが維持されることが保証されます。

        self.n = n
        self.bit = [0] * (n + 5)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def build_sa(s):
    n = len(s)
    k = 1
    sa = list(range(n))
    rank = [ord(c) for c in s]
    tmp = [0] * n

    while True:
        sa.sort(key=lambda i: (rank[i], rank[i + k] if i + k < n else -1))
        tmp[sa[0]] = 0
        for i in range(1, n):
            tmp[sa[i]] = tmp[sa[i-1]] + (
                (rank[sa[i]] != rank[sa[i-1]] or
                 (rank[sa[i]+k] if sa[i]+k < n else -1) != (rank[sa[i-1]+k] if sa[i-1]+k < n else -1))
            )
        rank = tmp[:]
        k <<= 1
        if rank[sa[-1]] == n - 1:
            break
    return sa, rank

def build_lcp(s, sa, rank):
    n = len(s)
    lcp = [0] * (n - 1)
    h = 0
    pos = rank
    for i in range(n):
        if pos[i] == 0:
            continue
        j = sa[pos[i] - 1]
        while i + h < n and j + h < n and s[i + h] == s[j + h]:
            h += 1
        lcp[pos[i] - 1] = h
        if h:
            h -= 1
    return lcp

 ## 特殊なケース

 次のような完全に均一な文字列`"aaaaa"`すべての接尾辞が他の多くの接尾辞と深く一致するように強制します。 この場合、アルゴリズムは、重複するサフィックス ペア間で LCP 寄与が二重にカウントされないことを保証する必要があります。 サフィックス配列ベースのグループ化により、各セグメントは、定義された最小 LCP 間隔を通じて 1 回だけ寄与することが保証されます。 

次のような完全に異なる文字列`"abcdef"`すべての LCP 値がゼロであることを保証します。 アルゴリズムは、スタック構造内の隣接するサフィックス比較による人為的な寄与の作成を正しく回避する必要があります。これは、LCP 配列が完全にゼロであり、アクティブな範囲を生成しないため保証されます。
