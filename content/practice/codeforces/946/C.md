 ## 解決策
 ## 問題の理解

 英語の小文字で構成される文字列が与えられます。 アルファベットの文字を 1 段階増やすだけの操作を実行することができます。たとえば、回転などです。`c`の中へ`d`または`a`の中へ`b`。 キャラクターは減らないし、`z`端末です。 

個々の位置にこのような増分を任意の数だけ適用すると、新しい文字列が得られます。 この最後の文字列からは、何かを正確に一致させる必要はありませんが、固定文字列が必要です。`"abcdefghijklmnopqrstuvwxyz"`サブシーケンスとして表示されます。 つまり、アルファベットを綴れるように 26 個の位置を昇順に選択できる必要があります。 

タスクは、それが可能かどうかを判断し、可能であれば、これを達成する結果の変換された文字列を 1 つ出力することです。 複数の回答が存在する場合は、有効な回答をどれでも受け入れます。 

入力サイズは最大 100,000 文字に達するため、変換を明示的に調査したり、文字ごとに可能なすべての増分をシミュレートしようとするソリューションは即座に除外されます。 各文字は最大 25 回インクリメントできますが、それを位置ごとに総当たりで個別に実行しても、不必要にスキャンを繰り返すことになります。 

微妙な点は、サブシーケンス内の文字を完全に無視できるため、すべての文字を使用する必要がないことです。 ただし、使用するすべての文字は、必要なターゲット文字まで順番にインクリメントできる必要があります。 

単純なアプローチでは、実現可能性を注意深く追跡せずに、アルファベットの文字を位置に貪欲に割り当てようとする可能性がありますが、初期の割り当てで使用可能な文字がすべて消費されてしまう場合には失敗する可能性があります。 

たとえば、次のような文字列を考えてみましょう。`"abz..."`どこにたくさん`z`キャラクターの登場が早い。 単純な貪欲な人は、誤って初期の文字を次の文字と一致させようとする可能性があります。`z`、 しかし`z`増やすことはできないため、今後の割り当てがブロックされます。 

もう 1 つの失敗ケースは、文字列にグローバルに十分な文字が含まれているにもかかわらず、それらの文字が使用可能な増分構造位置にない場合です。 サブシーケンスは頻度だけではなく順序に依存するため、どのソリューションも左から右への一致制約を尊重する必要があります。 

## アプローチ

 強引なアイデアは、各文字を考慮して、それをターゲット文字に割り当てようとすることです。`"abcdefghijklmnopqrstuvwxyz"`、おそらくインクリメントした後。 アルファベットの各位置について、文字列内を前方にスキャンして適切な文字を見つけ、それを使用済みとしてマークして続行します。 これは本質的に貪欲なマッチングです。 

これは概念的に機能します。各文字は上方向にしか移動できないため、文字の再配置を考慮する必要はなく、後の文字が必要な文字を満たすかどうかだけを考慮する必要があります。 ただし、注意せずに実装すると、各アルファベット文字の文字列を繰り返しスキャンすると O(26n) になり、これはまだ問題ありませんが、文字ごとのすべての増分をより単純にシミュレーションすると、位置ごとに O(26n) かそれ以上になります。 

重要な点は、アルファベットの各文字が順番に一致するかどうかだけを気にしているということです。 各文字は、使用可能な文字の範囲に影響します。`c`～からのどんな文字にもなりえます`c`に`z`。 したがって、各ポジションをキャパシティ間隔を提供するものとして扱うことができます。 合わせたい`'a' → 'z'`可能な限り最も早い有効な位置を順番に使用します。 

したがって、文字列を 1 回スキャンし、アルファベット文字ごとに、現在の文字が到達できる最も古い未使用の位置を選択します。 一度使用するとその位置は固定され、再利用することはできません。 

この貪欲さは正しいです。なぜなら、最も早い有効な位置を取得すると、後の文字に対して最大限の柔軟性が常に残されるからです。 それ以降の選択は、残りの選択肢を減らすだけです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 文字ごとのブルート スキャン | O(26n) | O(n) | 承認済み |
 | 最適な貪欲なシングルパス | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列上にポインタを保持し、文字列の一致を試みます。`'a'`に`'z'`順番に。 

1. インデックスから始める`i = 0`そして目標の文字`cur = 'a'`。 サブシーケンス構築のために選択したインデックスのリストを作成します。 
2. 対象となる手紙ごとに、`'a'`に`'z'`、位置が見つかるまで現在のインデックスから前方にスキャンします。`j`そのような`s[j] <= cur`。 この条件により、増加できることが保証されます`s[j]`まで`cur`文字だけが増えるというルールを破ることなく。 
3. そのような位置が見つからずに文字列の末尾に到達した場合、構築は不可能となり、出力されます。`-1`。 これは、残りの文字が必要な文字に到達できないために発生します。 
4. 有効なポジションを見つけたとき`j`を表すために割り当てます。`cur`、 記録`j`、スキャン開始を に移動します。`j + 1`。 
5. 26 個の位置をすべて収集した後、元の文字列をコピーし、選択した各位置を置き換えることによって出力文字列を構築します。`j`必要なアルファベット文字を付けてください。 
6. 結果の文字列を出力します。 

### なぜ効果があるのか

 正確さは、単調な一致の不変式に依存します。つまり、アルファベットの最初の k 文字を一致させた後、それらを実現できる k 個の位置の最小のインデックス セットを選択しました。 選択された各位置は実行可能な最も早い位置であるため、その後の代替選択は一致を右にシフトするだけで、残りの文字に使用できるサフィックス スペースが減少します。 実現可能性は、以前の未使用の柔軟性には決して依存せず、後の互換性のある位置の存在のみに依存するため、貪欲な選択は安全で最適です。 

文字のみが増加するという制約により、割り当て間の独立性が確保されます。文字が文字として使用されると、それを再利用することはできませんが、以前の一致を妨げるために下方に変更することもできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = list(input().strip())
    n = len(s)
    
    pos = []
    i = 0
    
    for c in range(26):
        target = chr(ord('a') + c)
        found = -1
        
        while i < n:
            if s[i] <= target:
                found = i
                i += 1
                break
            i += 1
        
        if found == -1:
            print(-1)
            return
        
        pos.append(found)
    
    for idx, c in zip(pos, range(26)):
        s[idx] = chr(ord('a') + c)
    
    print("".join(s))

if __name__ == "__main__":
    solve()
```コードはまず文字列を変更可能なリストに変換するため、更新が効率的になります。 ポインタ`i`選択された各位置が厳密に増加することを強制します。これは、サブシーケンスの順序に必要です。 

各アルファベット文字について、その文字に対応する文字が見つかるまで前方にスキャンします。 比較`s[i] <= target`実現可能性をエンコードします。`s[i]`すでにより大きいです`target`、それに合わせて減らすことはできません。 

26 文字すべてが割り当てられたら、選択したインデックスをターゲット文字で上書きし、文字列を再構築します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return sys.stdout.getvalue() if False else solve_capture(inp)

def solve_capture(inp: str) -> str:
    import sys
    from io import StringIO
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout
    sys.stdin = StringIO(inp)
    out = StringIO()
    sys.stdout = out
    try:
        solve()
    finally:
        sys.stdin = backup_stdin
        sys.stdout = backup_stdout
    return out.getvalue().strip()

# provided sample
assert solve_capture("aacceeggiikkmmooqqssuuwwyy\n") == "abcdefghijklmnopqrstuvwxyz"

# all identical chars, impossible
assert solve_capture("zzzz\n") == "-1"

# already valid minimal case
assert solve_capture("abcdefghijklmnopqrstuvwxyz\n") == "abcdefghijklmnopqrstuvwxyz"

# mixed case with forced upgrades
assert solve_capture("abcz" + "z"*30 + "\n") != ""

# insufficient structure
assert solve_capture("abc\n") == "-1"

 ## 特殊なケース

 失敗モードの 1 つは、文字列に次のような大きな文字のみが含まれている場合です。`z`。 その場合、理論的にはすべてのターゲット文字に到達可能です。`z`, しかし、それでも 26 個の異なる位置が必要です。 文字列が短すぎる場合、未使用のインデックスが残っていないため、アルゴリズムはターゲット文字で失敗し、正しく返されます。`-1`。 

もう 1 つの特殊なケースは、小さな文字が存在するが順序が正しくない場合です。たとえば、`"cba..."`。 スキャンにより、引き続き有効な位置が順番に選択されることが保証されますが、以前の大きな文字はダウングレードできないため、正しくスキップされます。 

最後の微妙なケースは、有効な選択肢が存在するにもかかわらず、かなり右側に遅れてしまう場合です。 ポインタベースのスキャンでは、常に最も早い有効な位置が選択されることが保証されるため、将来の文字に必要になる可能性のある後のセグメントを誤って消費することはありません。
