 ## 解決策
 ## 問題の理解

 文字列として表現される大きな数値が与えられるため、クエリごとに、構造特性を満たす厳密に小さい数値を構築する必要があります。 

数字の桁数が偶数であり、その桁を並べ替えて回文を形成できる場合、その数値は有効であるとみなされます。 これは、各桁が偶数回出現するということと同じです。 長さが偶数である場合、この条件は回文順列が存在するために必要かつ十分です。 

入力番号ごとに`s`、より厳密に小さい最大数を見つけなければなりません。`s`この周波数条件を満たすものです。 

入力サイズは大きく、最大 100,000 のテスト ケース、合計桁数は 200,000 です。 これにより、桁の置換が指数関数的になるテストごとの構築や、すべての候補に対して完全な再計算が繰り返されることは直ちに排除されます。 どのようなソリューションも、テスト ケースごとの桁数が基本的に線形である必要があります。 

微妙な制約は、答えが常に存在することが保証されていることです。 これにより、有効な数値より小さい値がない場合の失敗ケースを処理する必要がなくなります。 

いくつかの特殊なケースは、誤って処理されやすいものです。 1つはそのときです`s`はすでに有効な「すべて偶数の頻度」の数値です。 例えば、`88`は構造的には有効ですが、答えは依然として厳密に小さい必要があるため、最も近い有効な構成にステップダウンする必要があります。`77`。 

別の失敗例は、デクリメントによって先行ゼロの状況が生じたり、局所的に修正できない方法で桁パリティが壊れたりした場合に発生します。 たとえば、`1000`、単純な減少は示唆するかもしれません`0999`ただし、先頭のゼロは無効であるため、正しい答えは有効な偶数長の数字のマルチセットに正規化する必要があります。これは次のようになります。`99`。 

最後に、局所的にのみ確認すると、貪欲な桁調整は失敗する可能性があります。 問題は基本的に、偶数のカウントを維持しながら、元の接頭語より小さい、辞書編集上最大の桁のマルチセットを選択することです。 

## アプローチ

 ブルートフォースアプローチでは、数値を減らして各候補をチェックしようとします。 各候補について、その数字を回文に再配置できるかどうかを検証します。これには、周波数パリティのチェックが必要です。 有効性のチェックが桁数において線形である場合でも、最悪の場合、最大 O(10^n) 個の候補をスキャンする可能性がありますが、これはまったく実行不可能です。 

重要な観察は、有効性は桁数が偶数であるかどうかのみに依存するということです。 つまり、有効な数値は、使用する各桁のペアの数を選択することによって完全に決定されます。 各桁数は偶数であるため、概念的には半分の長さのシーケンスを選択し、それらを 2 倍にするという観点から考えることができます。 

タスクは次のようになります。次の値より小さい最大の数を構築します。`s`その桁マルチ​​セットはペアに分割できます。 候補を反復する代わりに、残りの桁を有効な偶数に配置できることを維持しながら、左から右に貪欲に答えを構築します。 

私たちは構築を数字 DP のような貪欲なプロセスとして扱います。 各位置に、対応する数字より小さい可能な最大の数字を配置しようとします。`s`、残りのサフィックスを最大の有効な偶数周波数マルチセットで埋めます。 それが失敗した場合は、ポジションを 1 つ戻して、より小さい桁を試します。 

これにより、問題は、制御された貪欲なプレフィックス構築と、残りのパリティ制約に基づく実現可能性チェックに変換されます。

 ## アルゴリズムのチュートリアル

 数値を一連の数字として扱い、入力値よりも厳密に小さくなるようにしながら、左から右に答えを構築することを目指します。 

1. 文字列内の位置を反復処理し、最初の相違点で厳密に小さいプレフィックスを構築しようとします。 目標は、桁を減らす最初の位置を決定することです。 

その理由は、一度厳密な減少が発生すると、残りは実現可能性の制約の下で独立して最大化できるためです。 
2. 各位置で、以下の数字を試みます。`s[i]-1`まで`0`。 残りのサフィックスを有効な偶数周波数マルチセットに完成させることが不可能になるような選択はスキップします。 

これにより、番号を入力できる可能性が常に確保されます。 
3. 位置の数字を選択した後`i`、残りの桁バジェットを計算し、残りの桁数がすべて偶数である必要があることを強制します。 いずれかの桁の残りのパリティが奇数の場合は、前の選択を調整するか、この分岐を拒否することで修正します。 
4. 有効なプレフィックス数字が選択されたら、偶数のカウントを維持しながら、残りの位置を可能な限り最大の数字で埋めます。 これは、少なくとも 2 つの出現がまだ残っている最大の数字を常に配置することによって貪欲に行われます。 
5. ある位置に有効な数字を配置できない場合は、前の位置に戻り、そこで次に小さい数字を試します。 

中心的な考え方は、構築が単調であるということです。接頭辞を修正すると、数字のペアを貪欲に埋めることによって接尾辞が常に最適に完成します。 

### なぜ効果があるのか

 正確さは 2 つの結合されたプロパティから得られます。 まず、有効な数値はすべて、すべてのカウントが偶数である桁のマルチセットに正確に対応するため、問題は辞書編集上の制約の下でマルチセットを選択することになります。 第 2 に、固定マルチセットによる辞書編集上最大の構築は、数字を降順にソートすることによって実現されます。 

残りの数字マルチセットがまだペアリングできる場合にのみプレフィックスにコミットすることを保証することで、無効な状態になることはありません。 最初の異なる位置での貪欲な選択は最大性を保証します。これは、以前の改善は厳密な辞書編集上の順序付け要件に矛盾するためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_suffix(cnt, length):
    res = []
    for d in range(9, -1, -1):
        while cnt[d] >= 2:
            res.append(str(d))
            cnt[d] -= 2
    return "".join(res)

def solve_case(s):
    n = len(s)

    cnt = [0] * 10
    for ch in s:
        cnt[ord(ch) - 48] += 1

    # try decreasing one position
    for i in range(n - 1, -1, -1):
        for d in range(ord(s[i]) - 49, -1, -1):
            cnt2 = cnt[:]
            cnt2[ord(s[i]) - 48] -= 1
            cnt2[d] += 1

            # fix parity by removing odd counts
            bad = False
            for k in range(10):
                if cnt2[k] % 2 == 1:
                    bad = True
                    break
            if bad:
                continue

            # build result prefix
            prefix = list(s[:i])
            prefix.append(chr(d + 48))

            # build suffix greedily
            suffix = build_suffix(cnt2, n - i - 1)

            if len(prefix) + len(suffix) == n:
                return "".join(prefix) + suffix

    # fallback (guaranteed exists, but should not be reached in practice)
    return "9" * (n - 2)

t = int(input())
for _ in range(t):
    s = input().strip()
    print(solve_case(s))
```有効性はすべてのカウントが偶数であるかどうかのみに依存するため、コードは最初に桁の頻度を計算します。 次に、実現可能性を維持しながら桁を減らすことができる右端の位置を見つけようとします。 

候補の減少ごとに、新しい桁のマルチセットをシミュレートし、パリティをチェックします。 すべてのカウントが偶数のままの場合は、9 から下に数字をペアにして、可能な限り最良の補完を構築します。 

接尾辞の構築は最大性を強制するため重要です。有効な接頭辞が固定されると、最良の継続は常に残りのカウントと一致する辞書編集上最大の配置になります。 

問題は答えの存在を保証するため、フォールバックケースは理論的には不要です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    def build_suffix(cnt, length):
        res = []
        for d in range(9, -1, -1):
            while cnt[d] >= 2:
                res.append(str(d))
                cnt[d] -= 2
        return "".join(res)

    def solve_case(s):
        n = len(s)
        cnt = [0] * 10
        for ch in s:
            cnt[ord(ch) - 48] += 1

        for i in range(n - 1, -1, -1):
            for d in range(ord(s[i]) - 49, -1, -1):
                cnt2 = cnt[:]
                cnt2[ord(s[i]) - 48] -= 1
                cnt2[d] += 1

                if any(c % 2 for c in cnt2):
                    continue

                prefix = list(s[:i])
                prefix.append(chr(d + 48))
                suffix = build_suffix(cnt2, n - i - 1)

                if len(prefix) + len(suffix) == n:
                    return "".join(prefix) + suffix

        return "9" * (n - 2)

    t = int(input())
    out = []
    for _ in range(t):
        out.append(solve_case(input().strip()))
    return "\n".join(out)

 ## 特殊なケース

 次のような入力の場合`1000`、主なリスクは、デクリメント後に先頭にゼロが付いている候補が生成されることです。 このアルゴリズムは、中間文字列の完全な数値解釈に決してコミットせず、代わりに桁数から接尾辞を再構築することでこれを回避します。 

次のような入力の場合`88`、単純なアプローチでは、既に「有効」であるため同じ数値が返される可能性がありますが、厳密な不等式要件により、アルゴリズムは最も近い小さい構成を検索する必要があります。 

多くの繰り返し数字を含む入力の場合、次のようになります。`2222`、貪欲なプレフィックス変更はグローバル パリティを維持する必要があります。 桁数ベースの構造により、すべての桁がまだペアにできる状態のみを受け入れることが保証され、微妙な無効な補完が防止されます。
