 ## 解決策
 ## 問題の理解

 サイズが n × n の正方形のグリッドが与えられ、これを 0 と 1 で埋める必要があります。 各セルは、黒い四角形を配置するか (1)、白い四角形のままにするか (0) を表します。 制約は、隣接関係やパターンなどのローカル構造を記述せず、グローバルなカウントのみを記述します。つまり、各行 i には正確に Ri のものを含める必要があり、各列 i には正確に Ci のものを含める必要があります。 

タスクは、各テスト ケースにそのようなバイナリ行列が少なくとも 1 つ存在するかどうかを判断し、存在する場合は有効なバイナリ行列を構築することです。 すべての行と列の合計を同時に満たすことができる行列がない場合、出力は -1 でなければなりません。 

主な問題は、行の要件と列の要件が組み合わされていることです。 行で 1 を選択すると、列で使用可能な容量が減少し、ローカル カウントがまだ有効であるように見えても、貪欲な決定により将来の実現可能性が簡単に妨げられる可能性があります。 

制約により、テスト ケースごとに最大 2000 が許可され、すべてのテスト ケースにわたる n² の合計は 4 × 10⁶ によって制限されます。 これにより、すべてのテストの合計がおよそ O(n² log n) よりも悪いアプローチは直ちに排除されます。 効率的なブックキーピングを行わずに各配置の完全な行または列を繰り返しスキャンしようとすると、速度が非常に遅くなります。 

合計は一致するが、分布に互換性がない場合、微妙な失敗のケースが発生します。 たとえば、すべての行が列の小さなサブセットに集中して高い値を要求する場合、単純な戦略ではそれらの列が早期に使い果たされ、合計が正しくても後の行は満足できないままになる可能性があります。 もう 1 つの一般的な落とし穴は、カラム容量が早期にゼロになる可能性があることを無視していることです。 それらに代入し続けると、実行可能性が黙って損なわれます。 

## アプローチ

 ブルートフォースの観点は、すべての制約をチェックしながら、行列をセルごと、または行ごとに埋めることを考えることです。 バックトラックを試みることもできます。各セルで 1 を配置するかどうかを決定し、残りの行と列の合計を維持し、再帰します。 これはすべての有効な構成を調査するため論理的には正しいですが、分岐要素は膨大です。 各 n² セルは、最悪の場合、探索空間を 2 倍にし、指数関数的な複雑性をもたらし、n が 30 という小さい場合でも不可能になります。 

より構造化された大胆なアイデアは、各行を個別に処理し、まだ容量が必要な列に貪欲に行を割り当てることです。 問題は、行内での単純な選択が取り消せないことです。 任意の列を選択すると、大容量の列が早期に無駄になり、将来の行が取り残される可能性があります。 

重要な観察は、残存容量が多いカラムが最も貴重なリソースであるということです。 行に Ri の値が必要な場合は、現在最大の残り容量を持つ列にそれらの列を配置することが常に最も安全です。これは、それらの列が将来の制約に対応できる柔軟性を備えた唯一の列であるためです。 これにより、問題は、残りの容量によって列の動的順序付けを繰り返し維持することに変わります。 

これにより、列全体の最大ヒープを使用する貪欲なシミュレーションが行われ、各行が Ri の最も利用可能な列を消費し、残りの容量が減少します。 万が一、十分な柱が確保できなかったり、残存容量のない柱を使用せざるを得なくなったりした場合、建設は不可能となります。

 ## アルゴリズムのチュートリアル

 列を容量 Ci を持つリソースとして扱い、行を要求 Ri として扱います。 目標は、最初に最も柔軟な列を使用して各行を満たすことを繰り返し行うことです。

1. まず、行に必要な 1 の合計数が列に必要な 1 の合計数と等しいことを確認します。 これらの合計が異なる場合、建設は不可能です。 配置されたそれぞれが同時に 1 つの行と 1 つの列に寄与するため、これは必要な条件です。 
2. 各エントリが列インデックスとその残りの容量 Ci を格納する最大ヒープを初期化します。 このヒープにより、現在最も未使用の容量を持つ列を常に抽出できます。 
3. 行 1 から n までを繰り返します。 行 i には、Ri のものを正確に配置する必要があります。 
4. 各 Ri 配置について、最大の残り容量を持つ列をヒープから抽出します。 Ri 配置を実行する前にヒープが空になるか、抽出された容量がゼロになると、構築はただちに失敗します。 これは、行の需要を満たすのに十分な使用可能な列が残っていないことを反映しています。 
5. 現在の行と選択した列に 1 を配置し、その列の残りの容量を 1 つ減らします。 
6. デクリメント後も列にまだ容量が残っている場合は、それをヒープに戻して、後の行で使用できるようにします。 
7. すべての行を処理した後、矛盾が発生しなかった場合、記録された配置は有効な行列を定義します。 

重要な考え方は、各行が常にその時点で利用可能な最も「柔軟な」列に割り当てられ、使いにくい列を後の行に保存するということです。 

なぜそれが機能するのかは、単純な交換引数に関係しています。 最適解では、より大きな容量のカラムが利用できる一方で、残りの容量がより少ないカラムに 1 が配置されるとします。 より大きな容量の列のほうが将来の行にとってより有用であるため、これらの割り当てを交換しても実現可能性が低下することはありません。 このスワップ原則を繰り返し適用すると、有効なソリューションはすべて貪欲な選択に一致するものに変換されます。つまり、貪欲な構築では、実行可能なソリューションが存在する場合、それが削除されることはありません。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        C = list(map(int, input().split()))
        R = list(map(int, input().split()))

        if sum(C) != sum(R):
            out.append("-1")
            continue

        heap = []
        for j in range(n):
            heap.append((-C[j], j))
        heapq.heapify(heap)

        grid = [[0] * n for _ in range(n)]
        ok = True

        for i in range(n):
            need = R[i]
            used = []

            for _ in range(need):
                if not heap:
                    ok = False
                    break

                cap, col = heapq.heappop(heap)
                cap = -cap

                if cap == 0:
                    ok = False
                    break

                grid[i][col] = 1
                cap -= 1
                used.append((cap, col))

            if not ok:
                break

            for cap, col in used:
                if cap > 0:
                    heapq.heappush(heap, (-cap, col))

        if not ok:
            out.append("-1")
        else:
            for row in grid:
                out.append(" ".join(map(str, row)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、貪欲なプロセスが行ごとにミラーリングされます。 ヒープには負の容量が保存され、Python の最小ヒープを使用して最大ヒープをシミュレートします。 行ごとに、使用する列を一時的に削除します。これは、単一行内で、その行に対するすべての割り当てが完了する前に、更新された容量を誤って再利用したり再挿入したりすることがないようにするためです。 

の`used`すぐに再挿入すると単一行内で同じ列が複数回選択される可能性があり、正確性に違反するため、バッファは重要です。 行が終了した後でのみ、更新された容量を元に戻します。 

障害状態は、枯渇または残りの容量がゼロであるために、使用可能な列を抽出できないときに正確にトリガーされます。 

## 実用的な例

 n = 3 の小規模な有効なケースを考えてみましょう。 

入力:```
3
2 1 1
1 2 1
```列容量のヒープを構築します: 列 1、2、3 (2, 1, 1)。 行の要求は (1, 2, 1) です。 

行 1 については、最適な列 (容量 2) を選択し、1 を配置して 1 に減算します。行 2 については、容量 1 と 1 の列を取得し、2 つの 1 を配置して両方を 0 と 0 に減算します。 行 3 では、容量 1 で使用できる列が 1 つだけ残っているため、最後の列を配置します。 プロセスは矛盾なく完了します。 

失敗した場合の場合:

 入力:```
2
2 0
1 1
```行の合計は 2 になりますが、列の合計は最初の列に 2、2 番目の列に 0 しか提供されません。 行 2 には配置が必要ですが、行 1 を貪欲に割り当てた後、残っている唯一の使用可能な構造が不十分になり、最終的にヒープの容量がゼロの列が生成され、障害が発生します。 これは、合計が一致しているにもかかわらず、分散により完了が妨げられていることを反映しています。

 ## 特殊なケース

 多くの行が早期に行を要求し、少数の列だけが高容量を持っている場合、まれなケースが発生します。 グリーディ ヒープでは、常に最大の残りの容量が最初に優先されるため、これらの高容量の列は、低容量の選択によって早期に枯渇するのではなく、徐々に消費されます。 

n = 3、C = [3, 0, 0]、R = [1, 1, 1] のような場合、ヒープはその容量がなくなるまで常に列 1 を選択し、すべての行が正しく埋められます。 単純な行方向の左から右への塗りつぶしでは、列 2 と列 3 を誤って使用しようとし、すぐに失敗します。 

もう 1 つのエッジ ケースは、カラムの容量が早期にゼロに達する場合に発生します。 ヒープ削除条件により、そのような列が二度と選択されなくなり、後続の行のサイレント破損が防止され、実行可能性がなくなったまさにその瞬間に障害が検出されることが保証されます。
