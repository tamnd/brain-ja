 ## 解決策
 ## 問題の理解

 同じ長さの 2 つの文字列が与えられています。 すべての位置で、最初の文字列から 1 文字を取り出し、2 番目の文字列から 1 文字を取り出して形成された文字のペアを確認できます。 インデックスのどのセグメントでも、2 つの文字列内の文字を交換する操作を実行できますが、同じインデックスでのみ実行できます。つまり、ペアを垂直に交換します。 各スワップは A[i] を B[i] と交換します。これはセグメント内の任意の位置に対して独立して何度でも行うことができます。 

クエリ範囲については、一連の交換の後、結果として得られる両方の部分文字列を非降順で個別に並べ替えることができるように、これらの垂直ペアを再配置できるかどうかを決定したいと考えています。 

このステートメントに隠されている重要な観察は、文字列内の文字を恣意的に並べ替えているわけではないということです。 同じインデックスにある 2 つの文字を交換するアクセス権のみがあります。 これは、セグメント全体にわたって、文字が最初の文字列に行くか 2 番目の文字列に行くかを位置ごとに効果的に選択していることを意味しますが、位置を並べ替えることはできません。 

入力サイズは文字列長とクエリ数の両方で 100000 に達するため、セグメントに対するクエリごとの線形スキャンは遅すぎます。 各クエリを O(r - l + 1) で個別に検査するソリューションは O(nq) まで低下しますが、これは許容限界をはるかに超えています。 

また、単純なアプローチでは、微妙な構造上の制約を見落とす傾向があります。たとえ両方の文字列がソートされたとしても、各インデックスが最終的な各文字列に 1 文字だけ寄与するという事実を尊重する必要があります。 よくある間違いは、インデックスごとのスワップによって導入される結合を無視して、問題をセグメントごとに 2 つの独立したマルチセットとして扱うことです。 

問題のあるエッジケースは、文字が大量にインターリーブされているものの、全体的にバランスが取れている場合です。 たとえば、A = "ab"、B = "ba" の場合、どちらの文字列も最初は並べ替えられていませんが、全範囲に対して答えは YES になります。 もう 1 つのエッジ ケースは、カウントは一致するが、スワップがどのように行われたかに関係なく、配置によりソート順序の違反が強制される場合です。 

## アプローチ

 ブルート フォース アプローチでは、各クエリのプロセスをシミュレートしようとします。 特定のセグメントについて、各インデックスを交換するか交換しない 2^(長さ) の方法をすべて考慮します。 構成ごとに、結果として得られる 2 つの文字列を構築し、両方がソートされているかどうかを確認します。 これは、許可された操作の完全な状態空間を明示的に探索するため、正しいです。 ただし、長さ k の単一セグメントの場合でも、すでに O(2^k) 個の構成が必要であり、k が 100000 までになると、これは完全に不可能になります。 

より構造化されたブルート フォースでは、チェックを次のように簡素化します。A[i] または B[i] が最初の文字列に寄与するかどうかを位置ごとに選択し、もう一方が 2 番目の文字列に寄与することを確認してから、並べ替えを検証します。 これにより、問題が組み合わせ代入問題として再構成されます。 重要な洞察は、並べ替えによってインデックス全体に単調な制約が課されるということです。 最初の文字列の位置 i にどの文字を入れるかを決定すると、i+1 で許可される内容が制限されます。 

これは中心的な観察につながります。すべての割り当てを考慮する必要はなく、セグメント内で利用可能な各タイプの文字数を追跡し、結果として得られるソートされた両方の文字列が一貫して形成されることを確認するだけで済みます。 これはプレフィックス頻度の問題になり、範囲内の A と B の文字数を比較することと、文字の順序のみに依存する実現可能性条件によって各クエリに答えることができます。 

各クエリを、ペアのマルチセットを 2 つの非減少シーケンスに分割できるかどうかをチェックすることに縮小します。 これは、すべての文字しきい値について、A と B の間の累積的な不均衡が順序付けの制約に違反していないことを検証することと同じです。 文字頻度に対するプレフィックスの合計を使用すると、各クエリは O(26) で答えることができます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(クエリごとに 2^n) | O(n) | 遅すぎる |
 | プレフィックス頻度 + チェック | O(26・Q + 26・N) | O(26・N) | 承認済み |

 ## アルゴリズムのチュートリアル

 問題を両方の文字列のプレフィックス頻度配列 (文字ごとに 1 つの配列) に変換します。 

1. A と B のプレフィックス カウントを個別に構築します。ここで、prefA[c][i] には、文字 c がインデックス i まで A に出現する回数が格納されます。B についても同様です。これにより、文字ごとに O(1) で範囲頻度クエリに答えることができます。 
2. 各クエリ [l, r] について、そのセグメント内の A と B の間の各文字の頻度の差を計算します。 これにより、利用可能な各文字の合計数と、それらが 2 つの文字列にどのように分散されているかがわかります。 
3. 文字のアルファベット順に実行可能条件をシミュレートします。 考え方は、セグメントからの利用可能な数を尊重しながら、最初の文字列が減らないようにするには、最初の文字列に何文字を追加する必要があるかを維持することです。 いかなる時点でも、要件が利用可能な供給量を超えた場合、答えは「ノー」です。 
4. 「a」から「z」までの文字をチェックし、並べ替え順序の制約を破ることなく、いくつの要素を割り当てることができるかという実行能力を維持します。 必要に応じて、小さい文字が最初の文字列の先頭に配置されるように貪欲に保証します。 
5. 両方の文字列の単調構造を維持しながらすべての文字を正常に割り当てることができた場合は YES が出力され、それ以外の場合は NO が出力されます。 

### なぜ効果があるのか

 この操作では固定インデックス内での交換のみが許可されるため、各インデックスは固定の文字ペアを提供します。 唯一の自由は、どの文字列がどの文字を受け取るかを決定することです。 ソート条件は、最終的な配置では、各文字列内の文字がグローバルなアルファベット順に従う必要があることを意味します。 これにより、有効なソリューションはすべて、文字間を後戻りすることなく昇順で一貫した文字の割り当てに対応するようになります。 

文字を順番に処理し、カウントのみを追跡することで、並べ替えによって課せられる制約を正確に把握します。これは、違反があると、少なくとも 1 つの文字列内で小さな文字の前に大きな文字を配置する必要があり、ローカルで修復できないためです。 プレフィックス頻度表現により、各クエリに対して正しいマルチセットを常に推論することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_prefix(s):
    n = len(s)
    pref = [[0] * (n + 1) for _ in range(26)]
    for i, ch in enumerate(s, 1):
        for c in range(26):
            pref[c][i] = pref[c][i - 1]
        pref[ord(ch) - 97][i] += 1
    return pref

def get_range(pref, c, l, r):
    return pref[c][r] - pref[c][l - 1]

def solve():
    L, Q = map(int, input().split())
    A = input().strip()
    B = input().strip()

    prefA = build_prefix(A)
    prefB = build_prefix(B)

    for _ in range(Q):
        l, r = map(int, input().split())

        need = 0
        ok = True

        for c in range(26):
            cnt = (
                get_range(prefA, c, l, r)
                + get_range(prefB, c, l, r)
            )

            if need > cnt:
                ok = False
                break

            need = max(0, need - cnt)

        print("YES" if ok and need == 0 else "NO")

if __name__ == "__main__":
    solve()
```プレフィックス配列には累積文字数が格納されるため、各クエリは文字ごとに一定時間抽出されます。 26 文字にわたるループは、中核となる実現可能性チェックです。`need`結果として得られる 2 つの文字列にわたって辞書編集上の順序制約を維持するために、さらに小さい文字をいくつ配置する必要があるかを追跡します。 

微妙な点は、常に A と B の両方からのカウントを結合することです。これは、スワップにより、ある位置にある任意の文字が文字列間を移動できるため、セグメント内の合計マルチセットのみが問題となるためです。 最終条件`need == 0`制約が残されることなく、すべての順序付け要件が満たされていることを確認します。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    def build_prefix(s):
        n = len(s)
        pref = [[0] * (n + 1) for _ in range(26)]
        for i, ch in enumerate(s, 1):
            for c in range(26):
                pref[c][i] = pref[c][i - 1]
            pref[ord(ch) - 97][i] += 1
        return pref

    def get(pref, c, l, r):
        return pref[c][r] - pref[c][l - 1]

    L, Q = map(int, input().split())
    A = input().strip()
    B = input().strip()

    prefA = build_prefix(A)
    prefB = build_prefix(B)

    out = []
    for _ in range(Q):
        l, r = map(int, input().split())
        need = 0
        ok = True
        for c in range(26):
            cnt = get(prefA, c, l, r) + get(prefB, c, l, r)
            if need > cnt:
                ok = False
                break
            need = max(0, need - cnt)
        out.append("YES" if ok and need == 0 else "NO")

    return "\n".join(out)

 ## 特殊なケース

 厄介な状況の 1 つは、セグメントにインデックスが 1 つしか含まれていない場合です。 この場合、唯一の操作はその位置で 2 文字を交換することなので、各文字列は 2 文字のうちの 1 つを正確に受け取ります。 プレフィックスベースのカウントは、結果として得られる両方の単一文字列が自明にソートできるかどうかをチェックすることになるため、アルゴリズムはこれを正しく処理します。これは常に true です。 

もう 1 つの微妙なケースは、すべての文字が同一である場合です。 どの割り当てでも両方の文字列に対して同一のマルチセットが生成されるため、順序付けの制約は自動的に満たされます。 頻度ベースのメソッドは、これをすべての文字レベルでゼロ順序の競合として扱うため、一貫して YES を返します。 

さらに興味深いケースは、一方の文字列に多くの「a」文字があり、もう一方の文字列に多くの「z」が含まれているなど、セグメントに非常に不均衡な分布がある場合です。 ランニング`need`変数は、初期の文字が後の制約を満たすことができるかどうかをキャプチャします。 不均衡が解消できない場合、`need`利用可能な数を超えて増加すると、アルゴリズムはセグメントを正しく拒否します。
