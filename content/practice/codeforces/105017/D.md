 ## 解決策
 ## 問題の理解

 10 進数の長い文字列が与えられ、その連続する部分文字列のうち、整数として解釈された場合に 11 で割り切れる数値を表すものがいくつあるかを数える必要があります。 

各部分文字列は、開始位置と終了位置を選択し、その間のすべての数字を並べ替えることなく順番に取得することによって形成されます。 結果の数値が 11 で割り切れる場合、それは答えに寄与します。 

この制約により、入力がテスト ケースごとではなく全体として大きいことが明らかになります。 すべてのテスト ケースの合計の長さは最大 100 万であるため、どのソリューションも合計サイズが基本的に線形になる必要があります。 すべての部分文字列を直接検査しようとするアプローチでは、最悪の場合、テスト ケースごとにおよそ n² 個の部分文字列が必要になりますが、これは実現可能な制限をはるかに超えています。 

一般的な失敗モードは、各部分文字列の数値を直接計算したり、ローリング算術を使用して計算しようとしたときに発生します。 たとえ算術が 11 を法として実行されたとしても、依然として O(n²) 個の部分文字列が存在し、定数因数が大きすぎます。 

もう 1 つの微妙な問題は、11 で割り切れる解釈から発生します。たとえば、「0」、「11」、「121」、「1111」などの部分文字列は、単純な数字の合計ヒューリスティックでは異なる動作をします。 単純な試みでは、割り算が桁の合計 mod 11 のみに依存すると誤って仮定する可能性がありますが、これは誤りです。 たとえば、「121」は 11 で割り切れますが、「111」は、それらの桁の合計が近いにもかかわらず、11 で割り切れません。 

主な困難は、各部分文字列を個別に評価することを回避できる構造を認識しなければならないことです。 

## アプローチ

 直接的なアプローチでは、すべての部分文字列を列挙し、その値を計算し、11 で割り切れるかどうかをテストします。11 を法とするローリング値を維持したとしても、各部分文字列のコストは依然として O(1) ですが、部分文字列は O(n²) 個あるため、時間は O(n²) になります。 n が合計 10⁶ までの場合、これは実行不可能です。 

このブレークスルーは、11 の算術特性から来ています。数値は、その桁の交互の合計が 11 で割り切れる場合に限り、11 で割り切れます。より正確には、数字を左から右に取得して d₁ − d₂ + d₃ − d4 + … を計算すると、結果は 11 の倍数になります。 

これにより、問題は完全な数に関する推論から、桁上の線形関数に関する推論に変換されます。 線形関数が得られると、すべての部分文字列はプレフィックス値の差になります。 これが重要な単純化です。部分文字列を直接評価する代わりに、部分文字列の有効性がプレフィックス状態の等しいかどうかのみに依存するように、各プレフィックスを単一の整数値にマップします。 

プレフィックス交互合計を定義します。 各位置は、そのインデックス パリティに応じて + または - 符号を付けてその桁に寄与します。 どの部分文字列でも、交互構造により、部分文字列の寄与が 2 つのプレフィックス値の符号付きの差に崩壊します。 符号は開始位置に依存しますが、結果がゼロかどうかだけを気にするので、符号は無関係になります。 

したがって、問題は、等しいプレフィックス値のペアをカウントすることに帰着します。 等しいプレフィックス合計の各ペアは、交互の合計が 0 であるため、11 で割り切れる部分文字列に対応します。 

プレフィックス値の頻度マップを維持し、これまでに各値が出現した回数を蓄積します。

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。

1. ゼロに設定されたプレフィックス アキュムレータと、ゼロ値が 1 回出現する周波数マップを初期化します。 これは、数字が処理される前の空のプレフィックスを表します。 
2. 文字列を左から右に繰り返し、交互に合計を維持します。 位置 i では、i が偶数か奇数かに応じて数字を加算または減算します。 これにより、文字列がプレフィックス状態に一貫して変換されます。 
3. 各位置のプレフィックス状態を更新した後、このプレフィックス値が以前に何回出現したかを確認します。 以前に出現するたびに、現在の位置で終わる部分文字列が定義され、その変換された値はゼロにキャンセルされます。 
4. その頻度を答えに追加し、現在のプレフィックス値の頻度を増やします。 
5. すべての位置を処理した後、累積された応答にはすべての有効な部分文字列が含まれます。 

重要な推論ステップは、各プレフィックス値がその時点までの数字の交互構造をエンコードしているため、プレフィックス値が等しいということは、介在する部分文字列にわたってバランスのとれた交互の合計を意味するということです。 

### なぜ効果があるのか

 交互合計変換は、桁の連結を位置にわたる線形関数に変換します。 任意の部分文字列の場合、その交互の合計は 2 つのプレフィックスの合計の差に等しく、開始パリティに応じて -1 を乗算することもできます。 11 で割り切れるかどうかはゼロに一致するかどうかのみに依存するため、乗算の符号は影響しません。 したがって、部分文字列は、この変換の下で 2 つの対応する接頭辞の状態が等しい場合に正確に有効になります。 部分文字列をカウントすることは、プレフィックス状態の等しいペアをカウントすることと同じになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        s = input().strip()

        freq = {0: 1}
        pref = 0
        ans = 0

        for i, ch in enumerate(s):
            d = ord(ch) - 48

            if i % 2 == 0:
                pref += d
            else:
                pref -= d

            ans += freq.get(pref, 0)
            freq[pref] = freq.get(pref, 0) + 1

        print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは、単一の実行中のプレフィックス値と、以前に確認された値のハッシュ マップを維持します。 パリティベースの符号の選択は、交互の合計構造をエンコードするものです。 実装の重要な詳細は、部分文字列に対して何も再計算しないことです。 プレフィックスの状態を再確認すると、すべての部分文字列が暗黙的にカウントされます。 

よくある間違いの 1 つは、周波数を 0 から 1 に初期化するのを忘れることです。 これがないと、インデックス 0 から始まる部分文字列はカウントされません。

 ## 特殊なケース

 次のような最小限の 1 桁の入力`"0"`有効な部分文字列を 1 つだけ生成します。 プレフィックスは 0 で始まり、数字の処理後も 0 のままであるため、周波数ルックアップではすぐに有効なものとしてカウントされます。 

ゼロが繰り返される文字列は、同じプレフィックスが繰り返される場合と同様に動作します。 例えば、`"000"`これは、すべての位置のペアが有効な部分文字列に寄与することを意味します。 このアルゴリズムは、明示的に列挙することなく、すべての O(n²) 部分文字列を正確にカウントします。 

のような文字列`"1010"`プレフィックス値を予測可能なパターンで交互に配置します。 アルゴリズムは、同じプレフィックス状態を繰り返し再検討することによってこれを処理します。これにより、各位置で終わるバランスのとれた部分文字列の数と正確に一致する方法で頻度カウントが増加します。
