 ## 解決策
 ## 問題の理解

 私たちには、2 つの一方通行道路のどちらを通過できるかを交互に指定する信号機が与えられています。 光のパターンは周期的であり、事前に十分にわかっています。 この繰り返しパターンに応じて、すべての分がストリート 1 またはストリート 2 のいずれかに属します。 

時間の経過とともに車のセットが到着します。 各車は特定の分に到着し、2 つの道路のいずれかに割り当てられる必要があります。 割り当てが完了すると、車はその通りの FIFO キューに加わります。 車は 2 つの条件が満たされた場合にのみ通過できます。それは、車がすでに到着していること、および現在信号が通過できることです。 現在緑豊かな道路からは、1 分間に最大でも 1 台の車が通過できます。 

時刻 t に到着した車は、t + 1 分以降にのみ動き始めることができるため、信号がすぐに青になったとしても、少なくとも次の分までは待機することになります。 総コストは、すべての車両が通過するまでの待ち時間の合計です。 

このタスクは、固定された割り当てをシミュレートするだけではなく、合計の待ち時間が最小限になるように、各車両が道路 1 に行くべきか道路 2 に行くべきかを選択することです。 

この制約により、テスト ケースごとに線形に近い解決策または対数線形の解決策が求められます。 すべてのテストにわたる n と m の合計は最大 100000 であり、時間の経過や割り当てに関する二次戦略は除外されます。 2 つの道路へのすべての車の割り当てを試すという単純なアイデアは、すぐに指数関数的に変化します。 注意深い構造を持たずに両方のキューを独立してシミュレートした場合でも、イベントが密集している場合には O(mn) 動作が発生する危険があります。 

微妙なエッジケースは、同時に到着する車両から発生します。 その分以内の入力順序を保持する必要があり、これはキューの順序に影響します。 もう 1 つの注意が必要な状況は、一方の道路に光が非常に有利で、もう一方の道路が実質的に「遮断」され、すべての車が唯一の生産的な列に強制的に入れられる場合です。 現在の光の色のみに基づく素朴な貪欲な割り当ては、輻輳の蓄積を避けるために将来の光サイクルが必要な場合に失敗します。 

## アプローチ

 ブルートフォース戦略では、2 つの道路へのあらゆる可能な車の割り当てが考慮されます。 割り当てごとに、両方のキューを分ごとにシミュレートし、ライトを進めて 1 分あたり最大 1 台の車を処理します。 これは正しいですが、代入の数が 2^m であるため、直ちに実行できません。 m = 100000 であってもこれは不可能です。 

より構造化されたブルート フォースでは、車を 1 台ずつ割り当て、毎回完全なシミュレーションを再計算します。 各挿入は将来のすべてのキュー遅延に影響を与える可能性があるため、それでも O(m^2) かそれよりも悪い結果が生じます。 

重要な観察は、各車両がシステムと対話するのは待ち時間を通じてのみであり、待ち時間は、選択したキュー内でその車両の前に何台の車両があるか、およびそのキューが到着後に青信号で処理される頻度によって完全に決定されるということです。 割り当てを修正すると、合計待機時間の計算は線形になります。 

この最適化は、基本的にサービスの可用性が定期的に切り替わる 2 つのサーバーにジョブを分散していることに気づいたことから始まります。 各ストリートは、既知のサービス スロットを持つサービス プロセスのように動作します。 したがって、各車両の決定は、将来のサービスタイムラインが異なる 2 つのキューのどちらかを選択することになります。 この構造により、車両を到着順に処理し、2 つの進化するキューを維持し、現在のキューの状態を考慮して、挿入時の増分コストがより小さい側に車両を常に割り当てることができます。 

これにより、問題は貪欲なシミュレーションに縮小され、街路ごとに、そのキュー内の車が追加された場合に次に終了する時刻を維持します。 現在の車をいずれかの道路に割り当てることによって発生する待機コストの増分を常に計算し、より良い方を選択します。

 ## アルゴリズムのチュートリアル

 まず、サイクル内の 1 分ごとに、どの道路が緑であるかを事前計算します。 次に、街路ごとに 1 つずつ、2 つのキューを維持しながら時間の進みをシミュレートし、それぞれが次に利用可能なサービス スロットがいつ発生するかを追跡します。 

到着時間が早い順に車両を処理します。 

1. 到着時間を処理可能な最も早い分、つまり t + 1 に変換します。これが各車両の真の「準備完了時間」です。 
2. 時刻 0 から開始して、次に各道路で車が通行できる時刻を表す 2 つのポインタを維持します。これらのポインタは、周期的なパターンに従って進みます。 
3. 入ってくる車ごとに、道路 1 に割り当てられた場合と道路 2 に割り当てられた場合の終了時刻を計算します。これには、各キューの最後での挿入をシミュレートする必要があります。つまり、その道路の最後に予定されている出発時刻と次に利用可能なサービス スロットを比較します。 
4. 終了時間が短い道路に車を割り当てます。 両方が等しい場合は、どちらの選択も有効です。 
5. 割り当て後、車をキューのタイムラインに押し込んで、その通りの次に利用可能な出発時刻を更新します。 
6. 待機時間を終了時間から準備時間を引いたものとして累積します。 
7. 合計待ち時間と代入配列の両方を出力します。 

重要な考え方は、各ストリートがサービス スロットが時間内に固定される決定論的プロセッサのように動作するため、ジョブの追加は最後にスケジュールされた完了にのみ依存するということです。 

### なぜ効果があるのか

 どの瞬間でも、各街路には、繰り返される交通パターンによって引き起こされる単調なサービス機会の連続があります。 車は到着順に処理されるため、各キュー内の相対的な順序を再検討する必要はありません。 車が割り当てられると、その道路で前の車を追い越すことはできず、その車の完了時間は、その道路で最後に予定された完了時間によってのみ決まります。 これにより、貪欲な選択の特性が生まれます。より早く終了する通りに車を割り当てても、その通りの最後尾にのみ影響し、他のキューの構造には影響しないため、将来の実現可能性が悪化することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    k = int(input())
    out = []

    for _ in range(k):
        n, m = map(int, input().split())
        s = input().strip()
        t = list(map(int, input().split()))

        # precompute next green street at each cycle position
        # 0-based time modulo n
        green = [0] * n
        for i, ch in enumerate(s):
            green[i] = int(ch)

        # next available time for each street
        # we simulate service slots as time increases
        nxt = [0, 0]

        ans = [0] * m
        total = 0

        # pointers to next usable minute per street
        ptr = 0

        # we maintain current time progression implicitly
        # but we need to simulate service availability
        # so we track for each street the next time it can process a car
        import heapq

        # for each street, store next time it is free to process a car
        free = [0, 0]

        for i in range(m):
            ready = t[i] + 1

            best = None
            best_lane = 0

            for lane in (0, 1):
                cur = max(free[lane], ready)

                # simulate waiting until a green slot for that lane
                # advance until green matches lane
                while True:
                    if green[cur % n] == lane + 1:
                        finish = cur
                        break
                    cur += 1

                if best is None or finish < best:
                    best = finish
                    best_lane = lane

            ans[i] = best_lane + 1
            total += best - ready

            lane = best_lane
            start = max(free[lane], ready)

            while green[start % n] != lane + 1:
                start += 1

            free[lane] = start + 1

        out.append(str(total))
        out.append(" ".join(map(str, ans)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、レーンごとに単純な状態、つまり、以前の割り当て後に新しい車にサービスを提供できる最も早い時刻が維持されます。 各車について、両方の車線を試し、その車線が車を受け入れて青信号を出せる最も早い時間を計算します。 その時間は、到着準備状況と車線の利用可能性の最大値から開始して、定期信号によってその車線が許可されるまで順方向にスキャンすることによって求められます。 

より良い車線を選択した後、青の 1 分間に 1 台の車しか通過できないため、その車線の空き状況をサービス開始の 1 分後に更新します。 待ち時間の寄与は、サービス時間と準備完了の差です。

 ## 特殊なケース

 重大なエッジケースは、信号機が長時間にわたって一方向通行を許可しない場合に発生します。 このような場合、その方向に車両を割り当てると、列の長さに関係なくコストが高くなります。 次の有効な緑のスロットのスキャンにより常に終了時間が繰り上がり、そのレーンが魅力的ではなくなるため、アルゴリズムがこれを処理します。 

もう 1 つの特殊なケースは、多くの車が同時に到着することです。 準備が同じであるため、順序はインデックスによって保存され、各割り当てによってレーンの空き時間が単調に拡張されるため、FIFO キューは自然に維持されます。
