 ## 問題の理解

 現在のタイヤ セットの摩耗具合に応じて各ラップのコストが決まるレースをシミュレーションしています。 各タイヤ セットは初期摩耗値から始まり、そのセットでラップを走行するたびに、ラップは正確に現在の摩耗値を秒単位で取得し、その後摩耗が 1 ずつ増加します。

 タイヤセットは2本あります。 最初のものは摩耗とともに最初に取り付けられています`a`、2番目は摩耗から始まります`b`。 最初のラップを含め、すべてのラップの前にピットストップを行うことが許可されており、固定タイムペナルティと引き換えにアクティブなタイヤセットを交換します。`p`。 何度でも切り替えることができます。 

目標は正確に完了することです`n`最小合計時間で周回します。時間にはラップタイムとピットストップペナルティの両方が含まれます。 

重要な構造は、各タイヤ セットが決定論的に進化するということです。`k`摩耗から始まる連続周回`x`、合計コストは等差数列になります。 つまり、連続使用のセグメントには閉じた形式のコストがあり、これが大きな制約にもかかわらず問題を扱いやすくするものです。 

この制約により、ブルート シミュレーションは不可能になります。 以来`n`は 10^9 にもなる可能性があるため、ラップごとにシミュレーションしたり、ラップ全体で DP を維持したりすることさえできません。 ラップを直接繰り返すアプローチは直ちに除外されます。 解決策は、各タイヤの使用量の観点から推論する必要があります。 

切り替えが常にわずかに有益であるか、常にわずかに有害である場合、微妙なエッジケースが発生します。 ローカルでより良いと思われるたびに貪欲なポリシーを切り替えると、切り替えによって固定ペナルティが導入されますが、摩耗が異なる初期値にリセットされるため、失敗する可能性があります。これは、非ローカルで将来のコストに影響します。 たとえば、たとえ`b < a`、ピットストップのコストが、何周にもわたる節約に比べて大きすぎる場合、すぐに 2 番目のセットを使用することは依然として最適ではない可能性があります。 

## アプローチ

 素朴なアプローチは、どのタイヤを使用するかをラップごとに決定することです。 周回ごとに、現在のタイヤを使い続けるか、別のタイヤに切り替えるかを検討できます。 これにより、動的なプログラムオーバー状態が発生します`(i, current_tire)`、 どこ`i`完了した周回数です。 各遷移のコストは O(1) であるため、合計の複雑さは O(n) になります。 これはすでに失敗しています`n = 10^9`。 

もう少し良い視点は、一度スイッチを切り替えると、連続して複数周にわたってタイヤを装着したままになる可能性があることに気づくことです。 これは、ラップをセグメントにグループ化することを示唆しています。 セグメントのシーケンスを固定すると、各セグメントは決定的な等差数列コストに加えて、場合によってはスイッチ コストにも影響します。 ただし、すべてのセグメンテーションを列挙することは依然として指数関数的です。 

重要な観察は、どのような最適な戦略においても、各タイヤは常に連続したブロックで使用され、選択されたブロック長に対してコストが完全に決定されるということです。 これにより、交互のブロックで各タイヤに何周を割り当てるかを決定するという問題が軽減されます。

### なぜ効果があるのか

 各タイヤの限界コストは使用量に応じて直線的に増加するため、最適な戦略は一般性を失うことなく最大 1 つの切り替えポイントに減らすことができます。 複数回切り替える場合、コスト関数はセグメントの長さにおいて凸状であり、切り替えにより固定ペナルティが追加されるため、分割による利点はなく、2 つの隣接するセグメントを同じタイヤ上の 1 つのセグメントにマージすることができます。 これにより、最適な構造には最大でも 1 つの遷移点が必要となり、単一の分割に対する検索で十分になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def cost(x, k):
    return k * x + k * (k - 1) // 2

def solve():
    n, a, b, p = map(int, input().split())

    ans = float('inf')

    def eval_order(start, second):
        nonlocal ans

        def total(i):
            return cost(start, i) + (p if i > 0 and i < n else 0) + cost(second, n - i)

        # continuous minimization: derivative-based optimum
        # cost difference is convex, so check neighborhood around critical point
        # approximate optimal split
        # derivative balance gives i ≈ (second - start + n) / 2
        if n == 0:
            return

        i_opt = (second - start + n) / 2

        for di in range(-3, 4):
            i = int(i_opt + di)
            if 0 <= i <= n:
                ans = min(ans, total(i))

    # no switch
    ans = min(ans, cost(a, n), cost(b, n))

    # one switch A -> B or B -> A
    eval_order(a, b)
    eval_order(b, a)

    print(ans)

if __name__ == "__main__":
    solve()
