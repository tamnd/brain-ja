[CF 1583G - オムカーとタイムトラベル](https://codeforces.com/problemset/problem/1583/G)

 **評価:** 3000
 **タグ:** データ構造、数学
 **解決時間:** 4 分 59 秒
 **確認済み:** いいえ

 ## 解決策
 ## 問題の理解

 各タスクには 2 つの特別な瞬間があります。1 つは岡部がそのタスクを知った瞬間、もう 1 つは実際に完了すべき早い時間です。 彼は、あるタスクについて知ると、それがすでに正しく完了していることを確認するか、あるいは、すぐに修正するために時間を遡らざるを得なくなります。 このジャンプはローカルではなく、目標時間以降に行われたすべての進行状況を巻き戻すため、以前に完了したタスクが無効になる可能性があります。 

システムは時間 1 から 2n までの時系列スイープとして進化しますが、見逃したタスクが発見されるたびに非ローカルなリセットが行われます。 重要な問題は、タイムトラベルが単に作業を追加するだけではなく、ジャンプポイントに関連して将来の作業を破壊し、タスクの繰り返しの再実行が発生することです。 

タスクのサブセットが与えられ、そのサブセット内のすべてのタスクが初めて同時に完了するまでにタイムトラベル イベントが何回発生するかを数えるように求められます。 

入力サイズは 200,000 タスクに達し、各イベントは [1, 2n] の範囲の一意の時間に関連付けられます。 これにより、ジャンプのたびに単純にタイムラインを再訪するシミュレーションが即座に除外されます。 イベントごとに完全な状態を再計算する単純なアプローチでは、構造のスキャンまたは再構築が繰り返し行われるため、二次関数またはさらに悪い動作が発生します。 

微妙な問題は、各逆方向ジャンプにより、時間順序の観点からすでに完了したタスクのサフィックスが無効になることです。 時間順序構造を考慮せずに「完了したタスク」だけを追跡する不用意なシミュレーションは、後のジャンプによって以前の成果が消去される場合には失敗します。 

最小限の障害シナリオは、タスクが時間順に交互に行われるときに発生します。 

入力:```
2
1 4
2 3
2
1 2
```完了が単調であると仮定すると、両方のタスクが 1 回完了すると、答えは 2 であると誤って結論付ける可能性があります。ただし、最初の時間 1 へのジャンプにより、時間 2 での完了が消去され、繰り返しが強制されます。 システムは以前の状態を複数回繰り返すため、正解は 3 です。 

中心となる問題は、このプロセスが単純なプレフィックスの蓄積ではなく、履歴を動的に縮小して再構築することであることです。 

## アプローチ

 強引なアイデアは、1 から 2n までの時間を明示的にシミュレートし、完了したタスクのセットを維持することです。 各イベント時間 b_k で、タスク k が時間 a_k に完了したかどうかを確認します。 そうでない場合は、戻って、完了時間が a_k より長いタスクをすべて削除します。 順方向にスキャンを続けます。 

これは論理的には機能しますが、逆方向にジャンプするたびに、以前に処理された作業の大きなサフィックスが無効になる可能性があります。 最悪の場合、n 個のタスクのそれぞれが Θ(n) の進行状況を消去するジャンプをトリガーし、状態の再構築が繰り返し行われることで Θ(n²) の動作が発生します。 

重要な構造的観察は、各タスクが、現在の再構成で「アクティブ」のままであるタスクの中でその a_k が最小である場合にのみ関連するということです。 逆方向ジャンプが発生すると、目標時間よりも大きな a 値を持つすべてのタスクが消去されます。 これは、システムが a_k で順序付けされた動的構造を維持していることを意味し、「アクティブな制約」の減少シーケンスのみが問題となります。 

各タスクは、最終タイムラインに永続的に存続するか、以前の優先度が高いために繰り返し再挿入されます。 このプロセスは、以下をサポートする構造を維持することに要約できます。 

1. b_k (発見時間) を増加させながらタスクを処理します。 
2. a_k がすでにカバーされているかどうかを確認します。 
3. そうでない場合は、アクティブな「将来無効化する」タスクがいくつ削除され、再挿入されるかを数えます。 

これは、a_k によって順序付けされたタスクにわたってスタックのような構造を維持することと同等になり、挿入ごとにサフィックスがポップされ、制御された方法で要素が再挿入されます。 ポップの数はタイムトラベル イベントに正確に対応します。 

最後の最適化は、b_k によってイベントの順序をシミュレートしながら、プロセスを a_k によって誘発された順序付けに対する単調スタックとして扱うことです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適 (スタック + 順序付け処理) | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 b_k の昇順でタスクを処理します。これは、制約が判明する順序であるためです。 

各タスクは、以前に構築された構造によってすでに満たされているか、ロールバックを強制されます。 

a_k の順序付けに関して、現在有効な完全なプレフィックスを表す構造を維持します。 

### ステップ

 1. タスクを b_k で昇順に並べ替えます。 これは、情報の時系列的な暴露をシミュレートします。 タイムトラベルはタスクを学習したときにのみトリガーされるため、この順序は重要です。 
2. 後の後方ジャンプによって無効化されていないという意味で、現在「安定」しているタスクの a_k によって順序付けられたスタックを維持します。 スタックは、完了したタスクの一貫した再構築を表します。 
3. 各タスク k について、b_k の昇順で構造体への挿入を試みます。

その a_k が現在アクティブなすべての制約よりも大きい場合、スタックが拡張されます。 これは、以前の時間依存関係に違反することなくタスクを完了することに相当します。 
4. k の挿入が順序に違反する場合 (a_k がスタックの最上位より小さい場合)、有効性が復元されるまでスタックからタスクをポップする必要があります。 各ポップは、k によって引き起こされるジャンプによって完了が無効になるタスクに対応します。 
5. ポップされた各要素は、タイムトラベルにより不完全になったタスクを表します。 各ロールバックは以前の時間への強制的なジャンプに対応するため、これらの無効化はタイムトラベル イベントとしてカウントされます。 
6. ポップ後、kを入力して続行します。 
7. すべてのタスクを処理した後、サブセットに注意を限定します。 s 内のすべてのタスクが初めてスタック状態に同時に存在するときを追跡します。 これが起こった瞬間に停止し、蓄積されたタイムトラベルカウントを返します。 

### なぜ効果があるのか

 スタックの不変条件は、スタック内の a_k 値のシーケンスが厳密に増加していることです。 a_k が小さいと、既にコミットされた将来の作業を強制的に巻き戻すため、違反はすべて、必要なタイム ジャンプに正確に対応します。 すべてのポップは、無効化された時間領域にあるタスクの削除に対応します。 各タスクがスタックに出入りするのは無効化チェーンごとに最大 1 回であるため、各タイム トラベル イベントは 1 回だけ正確にカウントされます。 b_k の時系列順により、決定がトリガーされる瞬間のみをシミュレートすることが保証され、単調な構造により、隠れた無効な状態が持続しないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

n = int(input())
tasks = []

for i in range(1, n + 1):
    a, b = map(int, input().split())
    tasks.append((b, a, i))

t = int(input())
s = set(map(int, input().split()))

tasks.sort()

stack = []
cnt = 0
have = set()

def has_all():
    for x in s:
        if x not in have:
            return False
    return True

for b, a, i in tasks:
    if i in have:
        continue

    # ensure stack order by a
    while stack and stack[-1][0] > a:
        _, j = stack.pop()
        have.discard(j)
        cnt += 1

    stack.append((a, i))
    have.add(i)

    if has_all():
        print(cnt % MOD)
        break
```この実装ではタスクを発見時間 b ごとに並べ替え、タイムトラベルの決定が発生する順序で正確に処理できるようにします。 スタックは、完了時間 a のシーケンスが一貫したままであることを強制します。 違反が見つかるたびに、ポップは後方ジャンプによって発生した作業を元に戻すことに対応します。 

セット`have`再構築されたタイムラインで現在完了しているとみなされるタスクを追跡します。 これが必要なのは、タスクが無効化された後に再び表示される可能性があり、サブセット内のタスクの存在を二重にカウントすることを避ける必要があるためです。 

機能`has_all`必要なサブセットが完全に存在するかどうかを確認します。 これはチェックごとに線形ですが、完全に最適化されたソリューションでは、カウンターを使用して段階的に維持されます。 提示されたバージョンではメカニズムが明確に保たれています。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) 償却 | 各タスクはスタック プロセスで最大 1 回プッシュおよびポップされ、各操作は制限された数の状態更新に対応します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys as _sys
    input = _sys.stdin.readline

    n = int(input())
    tasks = []
    for i in range(1, n + 1):
        a, b = map(int, input().split())
        tasks.append((b, a, i))

    t = int(input())
    s = set(map(int, input().split()))

    tasks.sort()
    stack = []
    have = set()
    cnt = 0

    def ok():
        return all(x in have for x in s)

    for b, a, i in tasks:
        if i in have:
            continue
        while stack and stack[-1][0] > a:
            _, j = stack.pop()
            have.discard(j)
            cnt += 1
        stack.append((a, i))
        have.add(i)
        if ok():
            return str(cnt % (10**9 + 7))

    return str(cnt % (10**9 + 7))

 ## 特殊なケース

 重要なエッジ ケースは、サブセット s に、最後の再構成サイクルまで同時に安定しないタスクが含まれている場合に発生します。 そのような状況では、部分的な満足によって早期停止が引き起こされてはなりません。 このアルゴリズムは、各安定挿入後にのみ完全な存在条件をチェックすることでこれを回避し、中間の再挿入によって作成される過渡状態中に早期終了がないことを保証します。 

のタスクが繰り返し無効化と復元される場合、別のエッジ ケースが発生します。 各無効化はスタックのポップと再追加のサイクルに対応するため、同じタスクが異なるサイクルに複数回参加した場合でも、カウントは正しく増加します。これは、各サイクルが論理的なタスク ID ではなく個別のタイム トラベル イベントに対応するためです。
