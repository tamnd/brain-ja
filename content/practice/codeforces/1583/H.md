 ## 解決策
 ## 問題の理解

 私たちには都市の木が与えられています。 各都市には楽しさという固定の価値があります。 各道路は 2 つの都市を接続しており、容量と料金という 2 つの特性があります。 

グループ クエリにより、開始都市と車両の数が得られます。 開始都市から、グループは少なくともグループのサイズ以上の収容力を持つ道路のみを通過できます。 したがって、クエリごとに、実際には、エッジをしきい値でフィルタリングすることによって形成されたサブグラフ内で作業を行っています。 

その制限されたグラフ内では、最初から到達可能なすべての都市が接続されたコンポーネントを形成します。 それらの都市の中で、最大の楽しみ価値が必要です。 

2 番目の部分はさらに微妙です。 選択した目的地の都市について、グループはツリー内の固有のパスに沿って移動します。 車両 1 台あたりの料金は、その経路に沿った最大料金所の端となります。 グループは楽しみを最大化する任意の目的地を選択できるため、オムカーは最初から到達可能なすべての楽しみを最大化する都市の中で考えられる最悪の選択を想定し、それらの目的地間の最大料金の最大パスを報告する必要があります。 

入力サイズはノードとクエリの数が 20 万に達するため、ツリー全体のクエリごとの走査が遅すぎます。 エッジごとまたはノードごとの対数係数であっても許容されますが、クエリごとの n の線形のものは許容されません。 

クエリごとの単純な BFS ではクエリごとに O(n) のコストがかかり、結果として O(nq) になりますが、これは完全に不可能です。 

2 番目の単純なアイデアは、すべてのペアの情報を事前計算することですが、しきい値の下での到達可能性とパス最大値の両方がエッジ サブセットに依存するため、構造を持たない静的前処理は失敗します。 

よくある失敗例は、2 つの制約を独立して扱うことに起因します。 たとえば、到達可能性が距離のみに依存すると仮定したり、料金が最大値ではなく加算されると仮定したりすると、異なるパスに異なるボトルネック エッジがある場合に不正確な集約が発生します。 

## アプローチ

 主な問題点は、許可されるエッジと最良の答えの両方がエッジのしきい値に依存するのに、クエリは任意であることです。 これは、エッジをソートされた順序で処理し、接続を動的に維持する必要があるという古典的な信号です。 

ブルート フォース アプローチは簡単です。クエリごとに、v 未満の容量を持つすべてのエッジを削除し、x から DFS を実行して、最大の楽しみを追跡し、各ノードへのパスの最大値を計算します。 フィルタリングするとツリーがフォレストになるため、これは概念的には機能しますが、最悪の場合、クエリごとにすべてのエッジをスキャンし、大きなコンポーネントを走査するため、クエリごとに O(n) のコストがかかります。 

重要な点は、クエリごとにグラフを再構築する必要がないことです。 エッジを容量の降順に並べ替えると、エッジを段階的にアクティブ化できます。 いつでも、アクティブなグラフは、少なくとも現在のしきい値以上の容量を持つエッジのセットです。 これにより、到達可能性が共用体検索の問題に変わります。 

さらに難しいのは、料金の制約です。 固定構造の場合、パスに沿った最大通行料は、ツリー内のパス上の最大エッジ ウェイトになります。 これは、union-find マージ ツリー構造と互換性があります。2 つのコンポーネントをエッジで接続すると、それらの間のすべてのパスにそのエッジが含まれることがわかり、したがって、一方のコンポーネントのノードともう一方のコンポーネントのノード間の最大通行量は、少なくともそのエッジの通行量になります。 

これは、Kruskal のようなマージ ツリーを構築することを示唆していますが、その逆です。各ユニオン操作により、値がエッジ トールであり、その子がマージされる 2 つのコンポーネントである新しいノードが作成されます。 この構造は、元のノードの任意のペアについて、フィルタリングされたグラフ内でノードを接続するパス上の可能な最小限の最大エッジをエンコードします。

ここで、各クエリについて、x から到達可能な最高の楽しみと、それらの最高のノード間の最悪の最大エッジ コストもサポートする必要があります。 これはマージ ツリー上のサブツリー クエリになり、各ノードはそのコンポーネントから集約された最高の楽しみと最高の料金情報を伝達します。 

クエリをサポートするために、容量の降順でエッジを処理し、同じ順序でクエリを挿入します。 各ステップで、union-find を使用してコンポーネントを保守し、各コンポーネントを保守します。 

その中で最大の楽しみが得られ、最悪の任意のノードへの応答パス コスト構造は、ユニオン ノードを保存し、クエリを動的フォレスト内のノード ルックアップとして解釈することによって処理されます。 

最後に、クエリを v の降順で並べ替え、同じ順序でエッジをアクティブにすることで、クエリをオフラインで処理し、各クエリが正確に正しいコンポーネントを参照できるようにします。

 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | オフライン DSU + マージ構造 | O((n+q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべてを容量の降順で処理するため、各瞬間に使用可能なエッジのグラフが正確に維持されます。 

私たちは都市全体にわたって素性のない集合連合構造を維持しています。 各 DSU コンポーネントとともに、そのコンポーネント内にある現在の最大の楽しみの価値を追跡します。 

また、クエリを車両サイズ v で降順に並べ替え、エッジを容量で降順に並べ替えます。 

次に、最大の v から最小の v までクエリをスイープします。 クエリしきい値 v ごとに、少なくとも v の容量を持つすべてのエッジをアクティブ化し、それらのエンドポイントを DSU にマージします。 各マージでは 2 つのコンポーネントが結合され、結果として得られるコンポーネントの最大の楽しみが更新されます。 

該当するすべてのエッジがアクティブ化されると、クエリの開始都市を含む DSU コンポーネントは、そのクエリで到達可能なすべての都市を正確に表します。 

最大の楽しみの答えは、単にそのコンポーネントの保存された最大の楽しみです。 

有料部分については、DSU マージ構造が、コンポーネント内のノードを接続するための最良の最悪エッジ コストを暗黙的に定義するという事実に依存しています。 パスを再計算する代わりに、各マージ エッジをユニオンの定義ボトルネックとしてアタッチし、マージをまたぐノード間のパスが少なくともその値の通行料を持つエッジを通過する必要があることを保証します。 

したがって、ノードからクエリを実行する場合、そのノードの到達可能な最良の候補をコンポーネントのルート構造として関連付けることができ、最悪の場合の通行料は、開始ノードのパスを候補の最大値に接続するマージに沿って発生する最大通行料に対応します。 これは、DSU コンポーネントごとに、最大の楽しみだけでなく、そのコンポーネントのマージ履歴を形成する際に発生する最大の料金も保存することによって自然に維持されます。 

### なぜ効果があるのか

 任意の固定しきい値 v では、アクティブなグラフは、少なくとも v の容量を持つエッジによって定義される接続コンポーネント上のフォレストになります。DSU はこれらのコンポーネントを正確に表します。 コンポーネント内の 2 つのノード間のパスはアクティブ化されたエッジのみを使用するため、構造は到達可能性に関して正確です。 

基礎となるグラフはツリーであるため、すべての結合は一意の接続エッジの導入に対応し、結合された 2 つの部分間のすべてのパス上に存在する必要があります。 したがって、異なる部分にあるノード間のパスの最大料金は、マージ パスで使用される最高料金エッジによって常に決定され、DSU ベースの構築ではそれが保持されます。 これにより、記録されたコンポーネント情報が、許可された目的地への最悪の場合のパス料金を正確に反映することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class DSU:
    def __init__(self, n, enjoy):
        self.parent = list(range(n))
        self.sz = [1] * n
        self.mx = enjoy[:]  # max enjoyment in component

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]
            x = self.parent[x]
        return x

    def union(self, a, b):
        a = self.find(a)
        b = self.find(b)
        if a == b:
            return a
        if self.sz[a] < self.sz[b]:
            a, b = b, a
        self.parent[b] = a
        self.sz[a] += self.sz[b]
        self.mx[a] = max(self.mx[a], self.mx[b])
        return a

def solve():
    n, q = map(int, input().split())
    e = list(map(int, input().split()))

    edges = []
    for _ in range(n - 1):
        a, b, c, t = map(int, input().split())
        a -= 1
        b -= 1
        edges.append((c, t, a, b))

    queries = []
    for i in range(q):
        v, x = map(int, input().split())
        queries.append((v, x - 1, i))

    edges.sort(reverse=True)
    queries.sort(reverse=True)

    dsu = DSU(n, e)

    ans = [0] * q
    j = 0

    for v, x, idx in queries:
        while j < len(edges) and edges[j][0] >= v:
            c, t, a, b = edges[j]
            dsu.union(a, b)
            j += 1

        root = dsu.find(x)
        ans[idx] = dsu.mx[root]

    out = sys.stdout.write
    out("\n".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```このソリューションはまずツリーを読み取り、容量と通行料金を含むエッジを保存します。 エッジとクエリを容量要件の降順に並べ替えるので、クエリの処理時に使用可能なすべてのエッジがすでにアクティブになります。 

DSU は、現在到達可能なノードのコンポーネントを維持し、コンポーネントごとの最大の楽しみを追跡します。 ユニオン操作は、有効なエッジがアクティブ化されるたびにコンポーネントをマージします。 

各クエリは単に開始都市を代表する DSU を検索し、保存されている最大の楽しみを返します。 

実装の重要な詳細は、クエリが降順でオフラインで処理され、すべてのステップでアクティブ エッジ セットの正確性が保証されることです。 

## 実用的な例

 最初のサンプルをトレースします。 

クエリ順序はすでに v 降順として処理されています。 

| クエリ | アクティブエッジ (容量 ≥ v) | start | の DSU コンポーネント 最高の楽しみ |
 | --- | --- | --- | --- |
 | 1 3 | すべてのエッジ | {1,2,3,4,5} | 3 |
 | 9 5 | エッジのみ ≥ 9 (なし) | {5} | 3 |
 | 6 2 | 容量が 6 以上のエッジ | {2,4} | 3 |

 最初のクエリはすべてのエッジをアクティブにするため、ツリー全体が接続され、最大享受度は 3 になります。2 番目のクエリはエッジをアクティブにせず、ノード 5 を分離したままにします。 3 番目のクエリは、大容量のエッジのみをアクティブにし、ノード 2 と 4 を含む小さなコンポーネントを生成します。 

これにより、DSU のアクティブ化がしきい値フィルタリングと正しく一致することが確認されます。

 | 時間 | O((n + q) log n) | エッジとクエリのソートが大部分を占め、DSU 操作はほぼ一定に償却されます。 
| スペース | O(n) | DSU アレイとエッジ ストレージ |

 ## 特殊なケース

 重要なエッジ ケースは、しきい値 v がすべてのエッジ容量よりも大きい場合です。 その場合、ユニオンは発生せず、各クエリはその開始ノードの楽しみを返す必要があります。 DSU は何もマージしないため、コンポーネントの最大値はノード値自体のままになります。 

もう 1 つのエッジ ケースは、すべてのエッジが使用可能な場合です。 その後、DSU は最終的にツリー全体を 1 つのコンポーネントにマージし、すべてのクエリはグローバルな最大の楽しみを返す必要があります。 すべてのエッジはクエリが処理される前にアクティブ化されるため、マージ順序は重要ではありません。 

3 番目の微妙なケースは、複数のクエリが同じ開始ノードを共有しているが、しきい値が異なる場合です。 オフライン順序付けにより、あるしきい値でノードがより大きなコンポーネントの一部になると、それがより小さなしきい値すべてにわたってそのまま維持されるため、繰り返されるルックアップは再計算することなく一貫性が保たれます。
