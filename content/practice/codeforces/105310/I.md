 ## 解決策
 ## 問題の理解

 上部の 0 から下部の n までインデックスが付けられたレイヤーの垂直構造を維持しています。 一部のレイヤーには「つる」が含まれている場合があり、各つるは現在の整数の長さを持ちます。 このシステムは、つるの動的追加、選択したつるのグループの長さの増加、およびそれらのつるの長さを使用した下方向への繰り返しの移動をサポートします。 

つるがレイヤー i に長さ l で存在する場合、それはジャンプのように動作します。i から i + l に移動しますが、これが n を超えると、正確に n に到達します。 レイヤーにつるが存在しない場合、そのレイヤーはトラバース中の停止点のように動作します。 

操作は3つあります。 1 つは、長さ 1 の位置につるを作成またはリセットします。1 つは、インデックスが特定の合同クラスの法 c に該当するすべてのつるの長さを増加します。 最後の操作はトラバースをシミュレートします。指定されたレイヤーから開始して、つるのないレイヤーに到達するまでつるを使用して繰り返しジャンプし、その最終位置を出力します。 

重要な制約は、n と q の両方が最大 100000 であるため、クエリごとに走査または一括更新を線形時間で再計算するソリューションは失敗するということです。 ジャンプを繰り返したどるタイプ 3 の単純なシミュレーションは、最悪の場合、クエリあたり O(n) まで低下する可能性があり、q 回繰り返すと遅すぎます。 同様に、すべてのレイヤーをスキャンしてタイプ 2 を適用する場合も、更新ごとに O(n) となり、大きすぎます。 

連鎖によって微妙な問題が発生します。 つるが 0 → 5 → 9 → 12 → … のような長いチェーンを形成している場合、単純なトラバーサルでは同じセグメントが繰り返し再計算され、タイプ 2 の更新が繰り返されると多くのノードが一度に変更される可能性があります。 この組み合わせにより、単純なシミュレーションが不可能になります。 

単純な走査の具体的な失敗シナリオは、長いチェーンです。 

入力:```
n = 10
type 1: vines at 0,1,2,...,9 each length 1
type 3: start at 0
```単純なアプローチでは、0 → 1 → 2 → ... → 10 と進み、コストは O(n) です。 繰り返すとO(nq)となります。 

もう 1 つの問題のあるケースは、一括増分クエリです。```
c = 1
type 2 always affects every vine
```更新のたびにすべてのつるに影響があり、単純な O(nq) が作成されます。 

## アプローチ

 直接シミュレーションでは、つるの長さの配列を保存し、文字通りすべてを処理します。 タイプ 1 は値を設定するだけで、タイプ 2 はすべてのインデックスをループして i mod c = k に一致するものをインクリメントし、タイプ 3 は配列を使用して繰り返しジャンプします。 

これは正しいですが、遅すぎます。 タイプ 2 だけでは、クエリごとに O(n) のコストがかかり、O(nq) になります。 タイプ 3 は、つるの長さが短い場合、または更新が頻繁に構造をリセットする場合、クエリごとに O(n) に低下する可能性もあります。 

重要な観察は、タイプ 2 の演算が高度に構造化されていることです。これらの演算は、c を法とする 1 つの剰余クラスのインデックスにのみ影響します。 これにより、配列が c 個の独立したグループに分割されます。 各グループ内では、時間の経過とともに更新が均一に追加されます。 

すべての要素をすぐに更新する代わりに、残基クラスごとに、そのクラスがインクリメントされた回数を表すグローバルな「遅延成長カウンター」を保存できます。 各つるは作成時またはリセット時の最後のカウンタ値を記憶しており、必要に応じて実際の長さを計算します。 

これにより、O(n) の更新コストが完全に削除されます。 

残りの課題は、タイプ 3 のクエリに効率的に答えることです。 トラバースはインデックスが単調増加し、各ステップが前方にジャンプします。 これは、オンデマンドで現在の長さを読み取るだけで、「次にアクティブなつる」の動作を暗黙的に維持できることを示唆しています。 各ステップは厳密に位置を増やすため、各クエリは各レイヤーに最大 1 回しか触れません。 遅延評価を使用すると、これは制約内で許容されるようになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 遅延残差 + 直接シミュレーション | O(qn) 最悪 | O(n + c) | 遅すぎる |
 | 残余遅延 + オンデマンド評価 (最適化されたトラバーサル) | O(q log n) または償却された O(n + q) | O(n + c) | 承認済み |

 ## アルゴリズムのチュートリアル

 ベースのつるの長さを格納する配列、各インデックスにつるが存在するかどうかを示すフラグ、c を法とする各剰余クラスのグローバル インクリメント カウンターの 3 つの主な構造を維持します。 また、つるごとに、最後にリセットまたは作成された時点のカウンターの値も保存します。 

1. 配列を初期化する`base[i]`つるの長さの配列`active[i]`つるが存在するかどうかを示す、および配列`tag[i]`その残差クラスの最後に確認された増分カウンターを保存します。 メンテナンスも行います`add[k]`各剰余クラス k について、最初はゼロです。 これにより、すべての要素に触れることなく現在のつるの長さを再構築できるシステムがセットアップされます。 
2. インデックス i のタイプ 1 クエリの場合、i につるを作成または上書きします。 設定しました`active[i] = true`、`base[i] = 1`、そして記録する`tag[i] = add[i % c]`。 その理由は、この残余クラスに影響を与える将来の増分は、このスナップショットに関連して適用される必要があるためです。 
3. 残基 k を持つタイプ 2 クエリの場合、インクリメントします。`add[k] += 1`。 個々のブドウの木には触れません。 これは、この残基クラスのすべてのつるが事実上 1 成長したという考えを捉えていますが、適用を遅らせます。 
4. i で始まるタイプ 3 クエリの場合、ジャンプをシミュレートします。 i につるが存在しますが、その現在の長さを次のように計算します。`base[i] + (add[i % c] - tag[i])`。 これにより、作成以降の正しい有効長が得られます。 次にジャンプします`i + length`、必要に応じて n にクランプし、続行します。 現在のレイヤーにつるが存在しない場合は、停止して i を出力します。 
5. 横断ループは、非つる層に到達するまで続きます。 各反復ではインデックスが厳密に増加し、確実に終了します。 

### なぜ効果があるのか

 各つるは、初期化と残余クラスの増分という 2 種類の変更を経験します。 違い`add[k] - tag[i]`つるが作成されてから、関連するクラスの増分が何回発生したかを正確にカウントします。 タイプ 1 は両方をリセットするため、`base[i]`そして`tag[i]`現在のグローバル状態に応じて、式は常に真の現在の長さを再構築します。 タイプ 2 は 1 つの残基クラスにのみ影響し、クラス間で相互作用することはないため、この分解は正確で損失がありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q, c = map(int, input().split())

    base = [-1] * n
    active = [False] * n
    tag = [0] * n
    add = [0] * c

    out = []

    for _ in range(q):
        tmp = input().split()
        t = int(tmp[0])

        if t == 1:
            i = int(tmp[1])
            base[i] = 1
            active[i] = True
            tag[i] = add[i % c]

        elif t == 2:
            k = int(tmp[1])
            add[k] += 1

        else:
            i = int(tmp[1])

            while True:
                if not active[i]:
                    out.append(str(i))
                    break

                length = base[i] + (add[i % c] - tag[i])
                ni = i + length
                if ni > n:
                    ni = n

                i = ni

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、各蔓の基本長を累積成長とは別に保存します。 重要な詳細は、`tag[i]`スナップショット: これがないと、すべての残基クラスの増分が異なるつる全体に誤って蓄積されてしまいます。 ジャンプ ループはプロセスの定義に直接続きますが、O(1) の長さの計算に依存します。 

微妙な境界条件は、ジャンプを n にクランプすることです。 これがないと、インデックスが範囲外になったり、無効な遷移が作成されたりする可能性があります。 もう 1 つの重要な詳細は、レイヤー n は、そこに vine が存在しない場合でも常にターミナル シンクとして扱われることです。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、複数の残基更新後につるが作成される場合です。 に保存されているスナップショット`tag[i]`古い増分が遡って適用されないようにします。 たとえば、残差クラスに影響を与えるタイプ 2 の 2 回の更新後に i でつるが作成された場合、その初期の実効成長は 2 ではなく 0 になります。 

もう 1 つのエッジ ケースは、更新後に同じ領域を繰り返し走査することです。 トラバーサルは常に現在のグローバル カウンターを使用して長さを再計算するため、再処理を必要とせずに更新された構造が常に反映されます。 

最後のエッジケースは、つるのないレイヤーで開始すると即時に終了することです。 その場合、ジャンプは不可能であるため、アルゴリズムは開始インデックスを直接出力します。
