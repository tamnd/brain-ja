 ## 解決策
 ## 問題の理解

 いくつかのバイナリ文字列が与えられ、任意の文字列内の任意の 2 つの位置の間で文字を繰り返し交換することができます。 スワップは 1 つの文字列内または異なる文字列間で発生する可能性があるため、事実上、すべての文字は、すべての位置間で自由に再分配できる 1 つのグローバル プールの一部となります。 

目標は、すべての文字を再配置して、できるだけ多くの元の文字列が同時に回文になるようにすることです。 最初の文字が最後の文字と一致し、2 番目の文字が最後から 2 番目の文字と一致する場合、文字列は回文です。 

重要な点は、スワップ中に個々の文字列構造を保持しようとしていないということです。 スワップにより完全な再割り当てが可能になるため、各文字列内の最後の文字のマルチセットのみが重要になります。 

各テスト ケースには最大 50 個の文字列があり、それぞれの長さは最大 50 であるため、テスト ケースあたりの合計文字数は最大 2500 です。これは十分に小さいため、線形または線形に近い操作を超えるパフォーマンスのボトルネックを心配することなく、文字数と貪欲な割り当てについてグローバルに推論できます。 

単純な推論による微妙な失敗のケースは、各文字列を個別にチェックできると仮定した場合です。 たとえば、ある文字列の長さが奇数で内部的に不一致が多すぎる場合、その文字列を回文にすることはできないと結論付けるかもしれませんが、文字をインポートまたはエクスポートすることで他の文字列と交換することで問題を修正できます。 もう 1 つの失敗例は、最初に 1 つの文字列を貪欲に修正することが最適であると想定している場合です。 そうすると、他の場所で必要な不一致文字が多すぎる可能性があります。 

エッジ シナリオの例: 文字列を考慮する`01`、`01`、`11`。 貪欲に試みれば両方を解決できるかもしれません`01`最初にビットをペアリングすることで文字列を作成しますが、これでは最適なグローバル ペアリングを行うには不十分な構造が残る可能性があります。 正しい解決策は、グローバルなカウントのみに依存します。`0`そして`1`、現地手配ではありません。 

## アプローチ

 ブルートフォース解釈では、スワップをシミュレートし、文字列全体にわたる文字の可能な最終的な分布をすべて試行します。 これは、すべての文字を固定サイズの n 個のグループに分割し、どのグループが回文を形成できるかを確認することと同じです。 再配置を無視して代入のみを考慮したとしても、分割数は天文学的に多く、最大 2500 要素にわたって多項係数のように増加するため、実行不可能になります。 

重要な洞察は視点を反転することです。交換によりすべての文字がグローバルに交換可能になるため、回文にするために選択する文字列の数を決定するだけでよく、最初から文字列の正確な同一性を決める必要はありません。 文字列が対称的にペアにできる場合、文字列は回文です。これは、文字のペアの数にのみ依存します。`0`そして`1`奇数長の文字列には、さらに 1 つの残りの文字を割り当てることができます。 

単一の文字列の数がわかっている場合、`0`そして`1`内部的に十分なペアを形成できれば実現可能です。 あらゆる長さの回文`L`必要`L // 2`間で任意に分散されたペア`0-0`そして`1-1`、場合によっては 1 文字が残っている可能性があります。`L`奇数です。 したがって、各文字列は特定の数のペアと、場合によっては 1 つの単一文字を消費します。 

これにより、問題は貪欲な割り当てに集約されます。利用可能なペアの合計を計算します。`0`そして`1`入力全体から、これらのリソースを費やして満足できる文字列の数を最大化しようとします。 各文字列には固定の要件があるため、ソートするか、より安価な文字列を最初に満たそうと貪欲に試みますが、ここではすべての文字列のコスト構造が対称であるため、単調な方法で実現可能性を直接計算できます。 

最終的な構造は、組み合わせたペアの要件が利用可能なペアを超えないように文字列のサブセットを選択し、文字列ごとに最大 1 つの奇数長の中心が利用可能な単一の文字で処理されるようにします。

 ## アルゴリズムのチュートリアル

 まず、入力文字列のグローバル統計を計算します。 総数を数えます`0`文字数と総数`1`文字。 すべての回文は最終的に対称ペアの文字を消費するため、これらから、各タイプのペアをいくつ形成できるかを導き出します。 

次に、各文字列を個別に調べて、回文になるために必要なものを計算します。 ある長さの文字列の場合`L`、必要です`L // 2`キャラクターペア。 これらのペアは、次のいずれかを使用して埋めることができます。`0`または`1`グローバル リソースが許す限り、ペア。 文字列の長さが奇数の場合は、中心として機能する追加の 1 文字も必要になります。 

次に、文字列を任意の順序で処理しますが、概念的には、各文字列を利用可能なリソース プールに「適合」させようとします。 各文字列について、十分なペアを割り当てられるかどうかを確認し、必要に応じて中央の文字を割り当てます。 「はい」の場合、グローバル リソースを減分し、文字列が正常に回文化されたものとしてカウントします。 それ以外の場合はスキップします。 

1. すべての文字列の合計 0 と 1 を数えます。 
2. それらを利用可能なペア数に変換します: 0 からは 0 ペア、1 からは 1 ペア、残りのシングル。 
3. 各文字列について、必要なペアと中心が必要かどうかを計算します。 
4. 現在のグローバル プールで要件を満たすことができる場合は、文字列を受け入れてプールを更新します。 
5. それ以外の場合はスキップしてください。 
6. 受け入れられた文字列の数を返します。 

この貪欲なアプローチが機能する理由は、各文字列が集約リソースのみを消費し、共有の枯渇を超える相互作用がないためです。 すべての文字列には同一の構造上の制約があるため (順序ではなく長さのみが重要)、残りの容量内に収まるかどうかを除いて、一方を優先しても利点はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    Q = int(input())
    for _ in range(Q):
        n = int(input())
        strings = [input().strip() for _ in range(n)]

        total0 = sum(s.count('0') for s in strings)
        total1 = sum(len(s) - s.count('0') for s in strings)

        zero_pairs = total0
        one_pairs = total1

        ans = 0

        for s in strings:
            l = len(s)
            need_pairs = l // 2
            need_center = l % 2

            if need_pairs <= zero_pairs + one_pairs:
                # use pairs greedily
                take = need_pairs
                use0 = min(zero_pairs, take)
                take -= use0
                use1 = take

                if use1 <= one_pairs:
                    zero_pairs -= use0
                    one_pairs -= use1

                    if need_center == 0:
                        ans += 1
                    else:
                        # need a center character
                        if total0 + total1 > 0:
                            ans += 1
                            if total0 > 0:
                                total0 -= 1
                            else:
                                total1 -= 1

        print(ans)

if __name__ == "__main__":
    solve()
```コードは、すべての文字列の文字数を集計することから始まります。これは、スワップによって文字列ごとの所有権の概念が削除されるため、必要になります。 次に、文字列を反復処理して、各文字列が消費するペアの文字の数を計算します。 

貪欲な割り当てが利用可能`0`そして`1`ペアの要件を満たすプール。 微妙な部分は、奇数長の文字列が中心文字をグローバルに使用できる場合にのみ使用するようにすることです。 このセンター処理はペアリング構造と相互作用しないため、ペア割り当てとは分離されています。 

ここでよくある落とし穴は、文字列ごとの実現可能性とグローバルな実現可能性を早すぎる段階で混合してしまうことです。 正しい解釈は常にグローバルなリソース割り当てです。

 ## 特殊なケース

 重要なエッジ ケースは、多数の奇数長の文字列が 1 つの中央文字をめぐって競合する場合です。 例えば：```
3
1
1
1
```各文字列にはセンターが必要です。 奇数長の構造ごとにグローバルに中心が 1 つだけ存在するため、完全に満たされる文字列は最大でも 1 つだけでなければなりません。 貪欲なアルゴリズムにより、センターが消費されると、それを必要とする後続の文字列が確実に拒否されます。 

もう 1 つの特殊なケースは、ペアの電源が正確にバランスされている場合です。 例えば：```
2
01
10
```両方の文字列にはそれぞれ 1 つのペアが必要で、リソースの合計は正確に一致します。 このアルゴリズムは、リソース カウンターをオーバーシュートすることなく、両方を順番に受け入れます。 

最後のエッジケースは、次のような不均一な分布です。```
2
000
111
```ここでは、各文字列に 1 つのセンターと 1 つのペアが必要です。 シングルが不十分な場合は両方のセンターを同時に満たすことができないため、正しい数のストリングのみが通過する必要があります。 リソースベースのアカウンティングは、このグローバルな制約を正しく適用します。
