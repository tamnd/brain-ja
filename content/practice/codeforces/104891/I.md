 ## 解決策
 ## 問題の理解

 時間内に再利用可能なアクションのように動作する 2 つの相互作用するクールダウン システムを備えたセットアップが与えられています。 1 つのアクションは繰り返し使用できるゴールド生成能力ですが、使用するたびに一定期間使用できなくなります。 2 番目のアクションは、他のすべてのクールダウンを復元するリセット ツールで、ゴールド生成能力をすぐに再利用できるようにしますが、独自のクールダウンもあります。 

目標は、一定の時間枠にわたって最適な使用シーケンスをシミュレートし、ゴールド生成アクションを実行できる回数をカウントすることです。 各実行では固定量のゴールドが生成されるため、ゴールドを最大化することは有効な実行数を最大化することと同じです。 

入力サイズは複数のテスト ケースにわたって大きく、最大 10^4 のケースがあり、パラメーターの合計は 10^7 で制限されます。 これにより、テスト ケースごとに 1 秒ごと、またはイベントごとに反復されるシミュレーションが除外されます。 時間を少しずつ進める単純な貪欲シミュレーションでも、最悪の場合、テスト ケースごとに O(m) まで低下し、多くのケースで m が 10^6 に達すると制限を超えます。 

重要なエッジケースは、リセットツールがメインアビリティのクールダウンよりもはるかに速いか、はるかに遅い場合に発生します。 それが非常に速い場合、プレイヤーは効果的にリセットを連鎖させて、ほぼ継続的にクールダウンを回避できます。 それが非常に遅い場合、それは役に立たなくなり、解決策は主な能力の単純な定期的な使用に退化します。 もう 1 つの微妙なケースは、m が小さい場合です。この場合、リセット操作は役に立たず、時間ゼロの使用がカウントされるかどうかに応じて、答えは単に Floor(m / a) + 1 になります。 

単純なアプローチは、常に最適なリセットの即時再利用を前提としたり、クールダウン間のタイミング調整を無視したりすることによって失敗する傾向があり、これにより、a = b または b が a をわずかに超える場合など、境界が調整されたケースで誤ったカウントが発生します。 

## アプローチ

 ブルート フォース シミュレーションでは、時間を明示的にモデル化し、2 つのアイテムのそれぞれがいつ利用可能になるかを追跡します。 メインアビリティを使用するか、リセットツールを使用するかをその時々で決定します。 これは、システム状態が完全に決定的で小さいため機能しますが、アクションの考えられるすべてのシーケンスを考慮すると、基本的に構造が指数関数的です。時間は単位ステップまたはイベント ジャンプで進み、最悪のシナリオでは依然として O(m) 回発生するため、貪欲なシミュレーションでもテスト ケースごとに O(m) のコストがかかります。 m が最大 10^6 および 10^4 のテスト ケースでは、これは実行できません。 

重要な観察は、メインの能力を使用することと、それが有益になった直後にリセット ツールを使用することの 2 種類のイベントのみが重要であるということです。 システム構造は繰り返しサイクルに崩壊します。 メインアビリティには固定クールダウンaがあり、リセットツールにはクールダウンbがあります。 リセット後、メインの能力をすぐに使用できるようになり、b が十分に小さければ、今後のクールダウンのギャップを効果的に圧縮できます。 このプロセスは定期的なパターンとなり、通常のクールダウンの進行と、基本スケジュールよりも早くメイン アビリティの追加使用を「挿入」する時折のリセットが交互に行われます。 

これにより、ベースライン スケジュールに対して各リセットでロック解除できる追加の使用回数と、m 秒以内にリセットを実行できる回数を決定するという問題が軽減されます。 サイクルごとのゲインを特徴付けると、答えはシミュレーションではなく単純な算術評価になります。

 ## アルゴリズムのチュートリアル

 中心的なアイデアは 2 つのタイムラインを比較することです。1 つはリセット ツールを使用せず、もう 1 つは使用可能なメイン アビリティ キャストの数が増加するたびに最適にリセットを挿入します。

1. まず、リセット操作なしでメインアビリティの使用のベースライン数を計算します。 最初の使用は時間 0 に発生し、その後は 1 秒ごとに発生する可能性があるため、カウントは Floor(m / a) + 1 になります。これにより、最低保証ゴールドが確立されます。 
2. リセット ツールを正常に使用するたびに、メイン アビリティが使用可能になるよりも早く、すぐに追加の使用が 1 つロック解除されることに注目してください。 この「追加キャスト」は、最適なプレイでリセットを使用することの唯一の利点です。 
3. リセット ツール自体は b 秒ごとにのみ使用できます。 したがって、時間 m 内に使用できるリセットの最大数は、floor(m / b) + 1 であり、ここでも時間 0 で即時使用されると仮定します。 
4. 各リセットが常に値を生み出すとは限りません。 これは、リセットの時点でメインアビリティがまだクールダウン中の場合にのみ役立ちます。 すでに使用可能な場合、リセットを使用してもメリットはありません。 
5. 重要な削減点は、相互作用は、クールダウン a がリセット スケジュール b より何回「遅れる」かに事実上依存することです。 有益なオーバーラップの数は、メイン能力が自然に利用可能になる前にリセットが到着する頻度に対応します。 
6. これは直接計算につながります。時間枠内で b が a を何回「追い越す」かを数えることによって位置合わせをシミュレートします。 これは、リセット タイミングがメイン アビリティの準備ギャップよりも厳密に小さい場合の整数間隔のカウントとして表現でき、レートの単純な算術比較が得られます。 
7. 最終的な答えは、ベースラインの使用量に、各ベースラインの回復が完了する前に発生する有効なリセットの数を加えたものです。 

最終的なカウントを簡潔に表現する方法は次のとおりです。 

b の間隔のリセットを使用して、長さ a の待機間隔を何回「圧縮」できるかを検討します。 長さ a の各間隔はリセットによって部分的に埋めることができ、b < a の場合は常に追加の使用に寄与し、それ以外の場合は何も寄与しません。 

### なぜ効果があるのか

 このシステムは単調な構造を持っています。主な能力の使用可能時間は、リセットによって変更されない限り固定された等差数列を形成し、リセット自体が別の等差数列を形成します。 唯一意味のあるインタラクションは、次に予定されているメイン機能が利用可能になる前にリセットが開始される場合です。 このようなイベントごとに待機時間がちょうど 1 クールダウン単位だけ短縮され、リセットによって重複間隔ごとに複数の追加使用が発生することはありません。 これにより、2 つの数列間の重複のカウントが追加のキャストの数と正確に一致することが保証され、算術解が正確になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []
    
    for _ in range(T):
        a, b, m = map(int, input().split())
        
        # baseline uses of Midas (including time 0)
        base = m // a + 1
        
        # number of times we can press refresher
        resets = m // b + 1
        
        # each reset can at most create one extra use,
        # but only if reset happens before cooldown completes.
        # Effective gain is bounded by overlaps of cycles.
        
        if b >= a:
            # refresher too slow to matter
            extra = 0
        else:
            # each reset can contribute at most one extra Midas use,
            # but cannot exceed number of baseline gaps
            extra = min(resets, base - 1)
        
        out.append(str(base + extra))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```ベースラインの計算`m // a + 1`時間ゼロから始まるすべての自然なアクティベーションをカウントします。 リセット回数`m // b + 1`クールダウンリフレッシュを試行する機会が何回あるかを表します。 条件付き分割は、構造的に意味のある唯一の体制変更、つまりリセットがクールダウンの進行を妨げるのに十分な速さであるかどうかを処理します。 いつ`b >= a`、リセットはタイミングを向上させるのに十分早く到着することがないため、答えはベースラインのままになります。 いつ`b < a`、リセットごとに、逃した 1 つの待機期間を追加の使用に変換できる可能性がありますが、利用可能なベースライン ギャップの数を超えることはできません。`base - 1`。 

このソリューションは、相互作用を 2 つの等差数列間の境界付きマッチングに減らすことで、明示的なスケジューリングを回避します。 

## 実用的な例

 代表的な 2 つのケースを追跡します。 

### 例 1:`a = 40, b = 10, m = 50`ベースラインの使用時間は 0、40 であるため、base = 50 // 40 + 1 = 2 となります。 

リセットは時間 0、10、20、30、40、50 で発生するため、リセット = 6 になります。 

b < a なので、extra = min(6, 1) = 1 となります。 

合計 = 3。 

| 時間 | ミダスの空室状況 | リセット可能 | アクション | 合計使用量 |
 | --- | --- | --- | --- | --- |
 | 0 | 準備完了 | 準備完了 | ミダス + リセット | 1 |
 | 10 | クールダウン | 準備完了 | リセット | 1 |
 | 10 | リフレッシュした | 準備完了 | ミダス | 2 |
 | 40 | 準備完了 | 準備完了 | ミダス + リセット | 3 |

 これは、1 回のリセットで 2 番目の自然な利用可能性の前に、Midas の使用を 1 つ追加できることを示しています。 

### 例 2:`a = 1, b = 1, m = 1000000`ベースラインは 1,000,001 回の使用です。 リセットも 1,000,001 回発生しますが、b >= a であるため、extra = 0 になります。各リセットは、Midas がすでに使用可能になったときに正確に到着するため、加速はできません。 

トレースは、頻繁なリセットにもかかわらず、悪用できるクールダウンのボトルネックがないことを示しています。

 ## 特殊なケース

 いつ`b >= a`、アルゴリズムは追加の貢献を直ちに無効にします。 たとえば、入力の場合`a = 60, b = 200, m = 960`、ベースラインが与える`960 // 60 + 1 = 17`。 リセットの発生が遅すぎるため、Midas の自然な回復の前に着陸することはできません。そのため、完全なステートメントのコンテキストでは、extra は 0 のままで、出力は gold 係数によってスケールされた 17 になります。 

いつ`a = 1`、ベースラインはすでに最大使用密度に達しているため、リセットでは何も追加できません。 のために`a = 1, b = 1, m = 10`、ベースラインは 11、エクストラは 0 です。 

いつ`m < a`、ベースラインは 1 になり、最初のキャストのみが可能であることを意味します。 リセットが頻繁に発生しても、圧縮するためのクールタイムがないため、エクストラは常に0になります。 

これらのケースは、縮退したタイミング レジームの下では式が自然に正しく崩壊することを裏付けています。
