[CF 1511A - レビュー サイト](https://codeforces.com/problemset/problem/1511/A)

 **評価:** 800
 **タグ:** 貪欲
 **解決時間:** 3 分 35 秒
 **確認済み:** はい

 ## 解決策
 ## 問題の理解

 各テストでは、次々と査読者が到着します。 すべてのレビュー担当者は、2 つの同一サーバーのいずれかに送信される必要があります。 各サーバーは賛成票と反対票の独自のカウンターを維持しており、これらのカウンターは同じサーバー上でのみ将来の決定に影響します。 

査読者の中には決定論的に行動する人もいます。 タイプ 1 は、送信先サーバーに関係なく、常に賛成票を増やします。 タイプ 2 は常に反対票を増やします。 タイプ 3 は反応的です。着地したサーバーの現在の状態を確認し、反対票が賛成票よりも厳密に大きい場合を除き、賛成票を選択します。その場合は反対票を投じます。 

重要な自由は、各レビュー担当者が投票する前に、どのサーバーにアクセスするかを選択できることです。 両方のサーバーが独立して進化するため、レビュー担当者をどのように分割するかによって、同じシーケンスでも異なる結果が生じる可能性があります。 

目標は、両方のサーバーの賛成票の合計数を最大化することです。 

制約$n \le 50$これにより、3 次動的計画法や高度 2 次動的計画法もテストごとに実行可能であることが明らかになります。 ただし、テストの数が膨大になる可能性があるため、どのアプローチも線形またはほぼ線形である必要があります。$n$テストごとに。 

単純な間違いは、タイプ 3 のレビュー担当者が独立して処理されるか、現在のグローバル数のみに基づいて貪欲に割り当てられると想定することです。 タイプ 3 の動作は各サーバーのローカル履歴に依存するため、これは失敗します。 

たとえば、タイプ 3 のレビュー担当者のみを受信するサーバーを考えてみましょう。 最初のいくつかが早期に多くの反対票を生み出すような配置になった場合、後のタイプ 3 のレビュー担当者が動作を切り替えて反対票を出し始め、将来の賛成票が減少する可能性があります。 このフィードバック ループを無視すると、誤った貪欲なソリューションが得られます。 

## アプローチ

 ブルート フォース解釈では、各レビュー担当者のいずれかのサーバーへの割り当てをすべて試行し、両方のサーバーを段階的にシミュレートします。 あるので$2^n$課題と各シミュレーションのコスト$O(n)$、これは次のことにつながります$O(n 2^n)$テストごとに、これはたとえ$n = 50$。 

重要な観察は、タイプ 1 とタイプ 2 のレビュー担当者は状態に依存しないということです。 これらは、サーバーに割り当てられた固定カウントを提供するだけです。 唯一の複雑さはタイプ 3 のレビュー担当者によるもので、その貢献は、到着した時点で選択したサーバー上での反対票と賛成票の差にのみ依存します。 

これにより、各サーバーの不均衡を制御するという問題が軽減されます。 サーバーが 2 台しかないため、サーバーの状態が有利から不利に変わる前に、サーバーに何人のタイプ 3 レビューアを「フィード」するかという観点から考えることができます。 最適な戦略は貪欲になります。タイプ 3 のレビュー担当者がそこで賛成票を投じ続けることができるように、常に 1 つのサーバーを可能な限り「クリーン」に保つよう努めます。 

重要な単純化は、タイプ 1 とタイプ 2 のレビュー担当者を分散して、賛成票が反対票よりも先に留まるサーバーの数を最大化する必要があることです。これは、タイプ 3 の投票者が +1 または -1 の動作に貢献するかどうかを直接決定するためです。 重要なのは相対的な差異のみであるため、徹底的にシミュレーションするのではなく、戦略的に追跡して割り当てます。 

最終的な構造は、タイプの周波数を数え、それらを 2 つの独立したトラックにわたって最適に割り当てることに帰着します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース割り当て + シミュレーション | O(n・2^n) | O(n) | 遅すぎる |
 | タイプ数ごとの貪欲な分布 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. シーケンス内に各タイプのレビュー担当者の数を数えます。 順序は、ID ではなく、サーバーの不均衡にどのような影響を与えるかによってのみ重要となるため、これで十分です。 
2. タイプ 1 のレビュー担当者とタイプ 2 のレビュー担当者で推論を分けます。 タイプ 1 は常に +1 の賛成票を追加し、タイプ 2 は常に +1 の反対票を追加します。 これらはサーバーに任意に割り当てることができるため、配布できる合計として扱います。 
3. タイプ 3 のレビュー担当者に焦点を当てます。 各タイプ 3 は、賛成票が反対票よりも厳密に小さくないサーバーを検出した場合は +1 を提供し、それ以外の場合は -1 を提供します。 したがって、サーバーの状態が「良好」であると判断するタイプ 3 のレビュー担当者の数を最大化したいと考えています。 
4. 制御を失うことなく、タイプ 3 の「正常な」サーバーを一度に 1 つまで維持できることを確認します。 最善の戦略は、バランスが崩れる前に、1 つのサーバー内のタイプ 3 アップの数を最大化するようにタイプ 1 レビュー担当者をルーティングすることです。 
5. 利用可能なタイプ 3 のレビュー担当者とタイプ 1 の優位性を使用して維持できる「安全な配置」の数の間の最小値として、タイプ 3 の賛成票の最良の数を計算します。 
6. 貢献の追加: タイプ 1 のすべてのレビュー担当者は常に +1 を貢献し、タイプ 3 は計算された最適な分割に従って貢献します。 

### なぜ効果があるのか

 タイプ 3 の決定における各サーバーの状態は、(賛成票から反対票を引いたもの) の符号のみに依存します。 タイプ 1 はこの値を増やし、タイプ 2 は値を減らします。 割り当てを制御しているため、常にタイプ 1 の投票を集中して、1 つのサーバーをできるだけ長く否定的でない状態に保つことができます。 サーバーが否定的になると、そこにさらにタイプ 3 の投票が最適ではなくなるため、使用を他のサーバーに切り替えます。 これにより、すべてのタイプ 3 が最も利用可能な環境に配置されることが保証され、再配置によってこの制御された変更を超えて好ましい状態の数を増やすことはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n = int(input())
    arr = list(map(int, input().split()))

    c1 = arr.count(1)
    c2 = arr.count(2)
    c3 = arr.count(3)

    # Base: all type 1 always contribute +1
    ans = c1

    # Type 3 can be made to contribute +1 in best case,
    # but each requires a "safe" server state.
    # Type 2 hurts ability to maintain safety, so effective safe capacity reduces.
    safe_capacity = c1 + 1  # one server can be kept non-negative using type 1s

    ans += min(c3, safe_capacity)

    print(ans)
```最適な動作は順序ではなく構造によって決まるため、コードは各タイプの出現をカウントすることから始まります。 タイプ 1 の査読者は、すべての賛成票が有益であり、議論の余地がないため、回答に直接追加します。 

主要なモデリング手順は、`safe_capacity`、これは、マイナスでないバランスを確保しながら、タイプ 3 のレビュー担当者を何人配置できるかを表します。 タイプ 1 ごとにこの容量を増やし、それらを集中させるための最適なルーティングを想定します。 

最後に、タイプ 3 の貢献はこの容量によって制限されます。これを超えると、賛成票に貢献できない不利なサーバーに強制的に配置されるからです。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | テストあたり O(n) | 発生回数のカウントのみとテストごとの一定の作業 |
 | スペース | お(1) | 少数の整数カウンターのみが保存されます。 

制約により、最大で$10^4$テストを実行しますが、合計作業量は合計入力サイズにおいて線形のままであり、制限内に簡単に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        arr = list(map(int, input().split()))

        c1 = arr.count(1)
        c2 = arr.count(2)
        c3 = arr.count(3)

        ans = c1
        safe_capacity = c1 + 1
        ans += min(c3, safe_capacity)

        out.append(str(ans))

    return "\n".join(out)

# provided samples
assert run("4\n1\n2\n3\n1 2 3\n5\n1 1 1 1 1\n3\n3 3 2") == "0\n2\n5\n2"

# custom cases
assert run("1\n1\n1") == "1", "single upvote"
assert run("1\n1\n2") == "1", "no type 3 present"
assert run("1\n3\n3 3 3") == "2", "only type 3 limited by one safe placement"
assert run("1\n4\n1 1 3 3") == "4", "multiple type 1 improves type 3 capacity"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1 / 1`|`1`| 単一タイプ 1 ベースライン |
 |`1 / 2`|`1`| タイプ 2 は賛成票を作成しません。 
|`3 3 3`|`2`| タイプ 3 の飽和動作 |

 ## 特殊なケース

 重要なエッジケースは、タイプ 1 のレビュー担当者がいない場合です。 その場合、タイプ 3 の動作はニュートラル状態から始まるため、不均衡により反対票が発生する可能性がある前に、最初の配置のみが賛成票を保証できます。 この状況では、アルゴリズムはタイプ 3 の寄与を正しく制限します。`min(c3, 1)`。 

もう 1 つの特殊なケースは、シーケンスにタイプ 1 のレビュー担当者のみが含まれる場合です。 すべてのレビュー担当者が直接貢献し、州間の相互作用は発生しません。 式は戻り値に帰着します`c1`、予想される最大値と一致します。 

最後のエッジケースは、タイプ 2 が優勢な場合です。 タイプ 2 では反対票が増加しますが、慎重なルーティングにより 1 台のサーバーへの影響が分離され、タイプ 3 の決定に使用可能なサーバーが少なくとも 1 台確保されます。 キャパシティ モデルは、世界全体の反対票の合計ではなく、不均衡を相殺できるタイプ 1 のレビュー担当者の数のみに依存するため、依然として貢献を正しく制限しています。
