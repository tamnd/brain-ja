 ## 解決策
 ## 問題の理解

 私たちは、一次元の道路に沿って配置された飲食店の列を与えられます。 各ストップには開始点の右側に固定位置があり、消費するのに必要な時間が固定されています。 馬は時刻 0 に位置 0 から開始し、右にのみ移動し、以前の位置に戻ることはできません。 地点までの移動には移動距離と同じ時間がかかり、停車地に到着するとそこで食事の時間も費やします。 馬には合計時間予算 D があり、目標は完全に完了できる停留所の数を最大化することです。つまり、制限時間内に順番に停留所に到着し、食事を終えることを意味します。 

重要な点は、馬が自由にストップをスキップできることです。 この制約は、すべてのポイントを訪問することではなく、総時間コストを考慮して、位置の昇順で一連の立ち寄り先を選択することです。コストには、移動時間と食事時間の両方が含まれます。 

この制約は、典型的な競技プログラミングの構造を暗示しています。n はテスト ケース全体で大きくなり、合計で最大 10^5 になります。 位置と時間は最大 10^9 まで大きいため、すべてのサブセットまたはすべての順列を試行する解決策は不可能です。 最悪の場合は約 10^10 の操作になるため、テスト ケースあたり O(n^2) でも遅すぎます。 テスト ケースごとに O(n log n) または O(n) に向かって押し進められます。 

よくあるエッジケースは、最も近い、または最も安い地元の料理を食べるという貪欲な選択が世界的に失敗したときに発生します。 たとえば、少し遠い料理は食べる時間がはるかに短く、後でより多くの合計ピックを可能にする一方、近い料理は将来の実現可能性を妨げる状況を考えてみましょう。 単純な位置による貪欲戦略または時間による貪欲戦略は、実際の制約が位置と累積移動量の両方を結合するため、ここでは失敗する可能性があります。 

もう 1 つの微妙な問題は、移動時間が毎回原点からではなく、最後に選択した位置に基づいて累積されることです。 したがって、位置 2、10、および 11 の料理を選択した場合、コストは料理ごとに独立しません。 これは増分距離に依存しており、移動を常に 0 からのものとして誤って扱うと、誤って処理されやすくなります。 

## アプローチ

 ブルートフォース手法では、ディッシュのすべてのサブセットを試し、ポジションの昇順で実現可能性をチェックし、各サブセットの合計時間を計算します。 サブセットごとに旅行コストを計算するには、連続した差分と食事の時間を合計する必要があり、これはサブセットごとに O(n) になります。 部分集合が 2^n 個あるため、これは O(n・2^n) となり、n = 40 の場合でも実現不可能です。 

重要な観察は、位置の昇順で料理を選択することのみを考慮しており、固定数の料理については、総時間コストを最小限に抑える最善の方法を必要としているということです。 これは、選択した料理のセットを維持し、効率的な置き換えの決定を可能にするデータ構造を備えた貪欲な選択を示唆しています。 

古典的な洞察は、現在の最良の選択を維持しながら、位置が昇順にディッシュを処理することです。 料理を検討する際、前に選択した料理の後にそれを含めた場合の追加時間コストを計算します。 指定された数の選択した料理の合計時間を可能な限り最小に維持しようと常に努めると、D を超えるたびに、貢献の観点から最も「高価な」料理が削除されます。 これにより、問題は最大ヒープによる貪欲な選択に変換されます。暫定的に料理を順番に取り出し、合計時間を追跡し、D を超えた場合は、食事時間の寄与が最も大きい料理を破棄します。 

これが機能するのは、旅行代金は注文ごとに固定されており、変動はどの食事時間を含めるかによってのみ発生するためです。 料理をポジションごとに分類すると、追加の出張コストが固定されるため、柔軟性があるのはどの品目を予算内に抑えるかだけです。 この構造は、増分プレフィックス コストを伴う制約の下で重みの最大数を選択するのと似たものになります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース サブセット | O(n・2^n) | O(n) | 遅すぎる |
 | ソートされた位置のヒープに貪欲 | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### アルゴリズムのチュートリアル

 1. すべての料理を位置に従って昇順に並べ替えます。 これにより、馬は後戻りできないため、有効なルートがプレフィックス一貫性のある選択に対応することが保証されます。 
2. 現在の経過時間、last_position、および選択した料理の食事時間を保存する最大ヒープの 3 つの変数を維持します。 ヒープは、必要に応じて削除するのに最もコストがかかる選択したディッシュを特定するのに役立ちます。 
3. ソートされた順序で料理を繰り返します。 各料理について、last_position からこの料理までの移動時間を計算し、その食事時間を加算して、それが含まれている場合の暫定的な新しい合計時間を取得します。 
4. この料理の食事時間をヒープに追加し、累積時間を更新します。 last_position を現在のディッシュ位置に更新します。 
5. 合計時間が D を超える場合は、食べる時間が最も長い料理をヒープから削除し、その寄与を合計時間から差し引きます。 その理由は、最も高価な食事時間を削除すると、選択した料理 1 つだけを失いながら、実行可能性を回復する最良の機会が得られるということです。 
6. すべての料理を処理した後、山盛りのサイズが食べられる最大の料理数になります。 

### なぜ効果があるのか

 どのステップでも、料理の選択を位置の昇順で維持し、そのサイズに対して合計時間が最小限になるようにします。 移動コンポーネントは、位置が固定されると固定されるため、唯一調整可能な部分はどの食事時間が含まれるかです。 予算を超えた場合は、最大の食事時間を削除することが最適です。削除ごとの総コストを最大限に削減できるからです。 この欲張り交換引数により、同じサイズの実行可能なサブセットが存在する場合、このプロシージャの総コストがそれよりも大きくならないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    t = int(input())
    for _ in range(t):
        n, D = map(int, input().split())
        p = list(map(int, input().split()))
        ttime = list(map(int, input().split()))

        dishes = sorted(zip(p, ttime))
        
        heap = []
        total_time = 0
        last_pos = 0

        for pos, eat in dishes:
            travel = pos - last_pos
            last_pos = pos

            total_time += travel + eat
            heapq.heappush(heap, -eat)

            if total_time > D:
                removed = -heapq.heappop(heap)
                total_time -= removed

        print(len(heap))

if __name__ == "__main__":
    solve()
```コードは最初に料理を並べ替えるため、動作は常に前進します。 ヒープは、Python の最小ヒープを使用して最大ヒープをシミュレートするために、食事時間を負の値として保存します。 

変数 total_time は、移動コストと食事コストの両方を一貫して追跡します。 各反復では、現在の料理を使用すると仮定し、必要に応じて最もコストのかかる食事時間を削除することで実現可能性を修復します。 この修復ステップは、貪欲なメカニズムの中核となります。 

実装でよくある落とし穴は、連続して選択された料理間の移動のみを考慮することを忘れることです。 last_pos の更新により、移動が毎回出発地からではなく、増分的に行われることが保証されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | ソートが支配的であり、ディッシュごとのヒープ操作も必要です。 
| スペース | O(n) | ヒープには最大で n 個の要素が格納されます。 

テスト ケース全体の n の合計が 10^5 であるとすると、これは一般的な 1 ～ 2 秒の制限内に問題なく収まります。 

## テストケース```python
import sys, io
import heapq

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n, D = map(int, input().split())
        p = list(map(int, input().split()))
        ttime = list(map(int, input().split()))

        dishes = sorted(zip(p, ttime))

        heap = []
        total_time = 0
        last_pos = 0

        for pos, eat in dishes:
            total_time += (pos - last_pos) + eat
            last_pos = pos
            heapq.heappush(heap, -eat)

            if total_time > D:
                total_time += heapq.heappop(heap)  # subtracting negative

        out.append(str(len(heap)))

    return "\n".join(out)

1 2 3 4 5

1 1 1 1 1
""") == "4\n5"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 単品料理に合う | 1 | 最小限の選択 |
 | すべて高価で、きつい D | より小さいサブセット | ヒープ削除トリガー |
 | 等しい時間 | フルセレクション | 削除は必要ありません |
 | ポジションに大きな差がある | 正しい旅行の蓄積 | 間隔の正確さ |

 ## 特殊なケース

 エッジケースの 1 つは、非常に早い時間の料理に時間がかかり、後で削除せざるを得なくなる場合です。 例えば：```
n = 3, D = 5
p = [1, 2, 3]
t = [4, 1, 1]
```アルゴリズムは最初にすべてのディッシュを取得しますが、合計時間はすぐに D を超えます。最大ヒープは最初に 4 つを削除し、適合する 2 つの小さなディッシュを残します。 

もう 1 つのエッジ ケースは、ポジションがまばらな場合です。```
n = 3, D = 10
p = [1, 100, 200]
t = [1, 1, 1]
```ここでは旅行が主流です。 このアルゴリズムは、多額の交通費を正確に累積し、選択を自然に制限します。これは、実現可能性が食事時間だけではなく、プレフィックスの到達可能性に依存することを示しています。 

最後のエッジケースは、単独で D を超える単一の大きなジャンプです。 アルゴリズムは引き続きそれを処理しますが、ヒープを介してすぐに削除し、その結果、正しい空の選択または縮小された選択が得られます。
