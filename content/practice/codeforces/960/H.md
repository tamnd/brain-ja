 ## 問題の理解

 私たちは、各頂点に 1 つのキャンディーが正確に含まれ、各キャンディーにフレーバーがある根付きツリーに取り組んでいます。 ツリー構造は固定されていますが、アップデートにより時間の経過とともにフレーバーが変化します。 

固定フレーバーの場合$k$、頂点を均一にランダムに繰り返し選択すると想像してください。 次に、その頂点のサブツリー全体を取得し、フレーバーのすべてのキャンディーを置き換えるコストを計算しようとします。$k$その中に。 実際のコストは、そのサブツリー内で現在フレーバーを持つ頂点の数によって異なります。$k$、そのような各頂点は固定量に寄与します$c_k$。 ただし、パン屋は常に固定の定数を請求します$C$、サブツリーのサイズや構成に関係なく。 

選択した頂点に対して$x$、サブツリーに次のものが含まれる場合$S_x$風味の頂点$k$、その場合、実際の費用は次のようになります。$c_k \cdot S_x$、エラーは次のとおりです$$(c_k \cdot S_x - C)^2.$$すべての頂点は等しい確率で選択されるため、クエリではすべての頂点にわたるこの値の平均が求められます。 

頂点でのフレーバーの変更と、指定されたフレーバーに対するこの期待値の再計算という 2 つの操作をサポートする必要があります。 

制約が非常に厳しいため、クエリごとにサブツリー数を再計算することは不可能です。 まで$5 \cdot 10^4$ノードとクエリ、サブツリー統計を繰り返し再計算するソリューション$O(n)$クエリごとに、$O(nq)$、これは実現可能な限界をはるかに超えています。 

微妙な問題は、サブツリーのメンバーシップの変更がインデックス順でローカルではないため、ツリーを慎重に線形化しない限り、単純なセグメント表現は失敗することです。 

2 番目の微妙な問題は、期待値が単なる合計ではなく、サブツリー数の 2 乗に依存することです。 多くの誤った解は、サブツリーごとの合計数のみを維持し、重複するサブツリー間の二次相互作用を見逃しています。

すべてのサブツリーのサイズを事前に計算したとしても、すべての頂点について、そのサブツリー内で動的に変化する色の現在の数が必要になるという困難は依然として残ります。 重要な観察は、各クエリは単一色の頂点ごとのサブツリー集合体のみに依存し、更新は 1 つの頂点のみに影響するということです。 これは、各フレーバーについて、ツリーのオイラーツアーにわたって動的構造を維持することを示唆しています。

重要なステップは、$S_x$それ自体は、動的バイナリ配列にわたる範囲の合計です。 課題は、サブツリー間隔ごとに、ツリー構造によって引き起こされるプレフィックス サブツリーの合計の合計と二乗和を効率的に維持することになります。 これは問題を逆転させる典型的なケースです。クエリごとにサブツリーの合計を再計算する代わりに、オイラー次数上のフェンウィック ツリーとサブツリー間隔にわたる第 2 レベルの集計を組み合わせてノードごとの寄与を維持します。

 ## アルゴリズムのチュートリアル

 ツリーのルートを 1 に設定し、各サブツリーが連続した間隔に対応するようにオイラーの開始時刻と終了時刻を計算します。 

それぞれの味を維持します$k$、現在フレーバーを持つ各ノードに 1 を格納するオイラー次数上のフェンウィック ツリー$k$、それ以外の場合は 0。 これにより、フレーバーのノード数をクエリできるようになります。$k$の任意のサブツリーに存在します$O(\log n)$。 

頂点ごとに$x$、値$S_x$は、そのサブツリー間隔にわたる範囲の合計として取得されます。 すべてを保管することはありません$S_x$明示的に。 代わりに、線形性を利用し、プレフィックスの寄与を再利用することで、すべての頂点の合計を計算します。 

各フレーバーに対して 2 つのグローバル アキュムレータ (すべてのノードのサブツリー数の合計と二乗サブツリー数の合計) を維持します。 これらは、単一のノードがフレーバーを変更すると、そのノードを含むサブツリー クエリ、つまりオイラー階層内のすべての祖先に正確に影響を与えるという事実を使用して、間接的に更新されます。 オイラー ツアー上で 2 番目のフェンウィック ツリーを維持し、各サブツリー ルートに寄与するアクティブなノードの数を追跡します。 

フレーバーのタイプ 2 クエリを処理する場合$k$、次のように計算します。 

まずは合計額$S_x$Fenwick クエリによるサブツリー ルートの走査を使用してすべての頂点を探索し、次の合計を計算します。$S_x^2$同様の集計を使用します。 これらは、拡張された式を使用して最終的な期待値に結合されます。 

タイプ 1 の更新を処理するとき、古いフレーバー構造からノードを削除し、新しいフレーバー構造に挿入します。各操作には時間がかかります。$O(\log n)$。 

### なぜ効果があるのか

 各サブツリー クエリは、連続するオイラー間隔内のアクティブ ノードの数にのみ依存します。 フェンウィック ツリーは、ポイント更新時にこれらのカウントが常に正しいことを保証します。 すべてのノードはすべての祖先サブツリー間隔に独立して寄与するため、正確性を維持することは、フレーバー メンバーシップの一貫した点単位の表現を維持することになります。 期待式は、これらのサブツリー合計の線形および二次集計にのみ依存し、両方ともこれらの維持されたカウントによって完全に決定されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

n, m, q, C = map(int, input().split())
f = [0] + list(map(int, input().split()))
parent = [0] + list(map(int, input().split()))

children = [[] for _ in range(n + 1)]
for i in range(2, n + 1):
    children[parent[i - 1]].append(i)

tin = [0] * (n + 1)
tout = [0] * (n + 1)
euler = []
sys.setrecursionlimit(10**7)

def dfs(u):
    tin[u] = len(euler) + 1
    euler.append(u)
    for v in children[u]:
        dfs(v)
    tout[u] = len(euler)

dfs(1)

bits = [BIT(n) for _ in range(m + 1)]

for i in range(1, n + 1):
    bits[f[i]].add(tin[i], 1)

def query_k(k):
    ck = c[k]
    total_sum = 0
    total_sq = 0

    for x in range(1, n + 1):
        s = bits[k].range_sum(tin[x], tout[x])
        total_sum += s
        total_sq += s * s

    return (ck * ck * total_sq - 2 * C * ck * total_sum + C * C * n) / n

c = [0] + list(map(int, input().split()))

for _ in range(q):
    tmp = input().split()
    if tmp[0] == '1':
        x = int(tmp[1])
        w = int(tmp[2])
        old = f[x]
        if old != w:
            bits[old].add(tin[x], -1)
            bits[w].add(tin[x], 1)
            f[x] = w
    else:
        k = int(tmp[1])
        print(query_k(k))

期待値は、二乗誤差の代数展開から直接計算されます。

 ## 特殊なケース

 A critical edge case is when all nodes share the same flavour and multiple updates flip a single node back and forth. In this situation, every subtree query is maximally sensitive to that node because it lies in every ancestor subtree interval. Fenwick の更新では、正確に 1 つの位置を増減させることでこれを正しく反映し、影響を受けるすべてのサブツリーの合計が一貫して調整されるようにします。 

Another edge case occurs when the queried flavour does not exist in the tree. The BIT for that flavour remains empty, so every subtree count is zero, and the answer reduces to$C^2$、すべての頂点にわたって平均され、予想される一定の誤差と一致します。
