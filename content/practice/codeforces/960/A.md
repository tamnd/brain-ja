 ## 解決策
 ## 問題の理解

 文字だけからなる文字列が与えられます`a`、`b`、 そして`c`。 この文字列は非常に特殊な方法で構築されていると主張されており、1 つ以上の文字列で始まります。`a`キャラクター、その後いくつか`b`文字が追加され、最後にいくつかの文字が追加されます`c`文字は最後に追加されます。 これら 3 つのフェーズの後、文字列には少なくとも 1 つが含まれている必要があります。`a`そして少なくとも1つ`b`、 その間`c`構築ルールによっては存在する場合と存在しない場合があります。 

キーの制約は、数だけでなく構造にも関係します。 文字列は非減少位相順序である必要があります: all`a`最初に来て、それから全員`b`、それからすべて`c`。 その上、その数は、`c`文字は次のいずれかの数に等しくなければなりません`a`文字または数`b`文字 (または等しい場合は両方)。 

タスクは、指定された文字列がそのようなプロセスによって生成された可能性があるかどうかを判断することです。 

入力サイズは最大 5000 文字です。 これは十分に小さいため、ほぼ二次関数までの解は問題なく通過できますが、問題の構造は線形スキャンで十分であることを示唆しています。 パターンを検証しているだけで何も構築していないため、O(n) チェックが期待されるはずです。 

単純な誤解は、カウントだけに注目することです。 たとえば、次のような文字列`acbbc`の数が等しい`a`、`b`、 そして`c`しかし、順序が壊れているため無効です。 もう 1 つの微妙な失敗は、文字列を再配置できると想定しているにもかかわらず、再配置が許可されていないことです。 

不適切なソリューションを壊すことが多いエッジケースには、次のようなものがあります。 

- 混合注文など`aba...`どこ`b`皆の前に現れる`a`終わっています。 
- 必要なセグメントが欠落している (例: no)`b`全然。 
- 順序は正しいが間違っている`c`カウントなど`aabccc`どこ`a=2`、`b=1`、`c=3`、以降無効です`c`2 にも 1 にも一致しません。 
- 文字列のような`aaabbbccc`すべてがクリーンでカウントが一致している場所`a`または`b`。 

## アプローチ

 ブルートフォース解釈では、文字列を 3 つのセグメントに分割し、考えられるすべての分割点をチェックしようとします。 分割ごとに`(i, j)`、私たちは解釈します`S[0:i]`全員として`a`、`S[i:j]`全員として`b`、 そして`S[j:]`全員として`c`、次に順序とカウント条件の両方を確認します。 これには、O(n²) 回の分割を試行する必要があり、各検証のコストは O(n) であり、最悪の場合は O(n³) になります。これは、n = 5000 の場合でも不必要で無駄です。 

問題の構造により、分割点を推測する必要がありません。 文字列が有効な場合、その文字列は厳格な単調パターンを持ち、文字型が変更されると元に戻りません。 これは、左から右にスキャンして、遷移が確実に続くことを意味します。`a → b → c`のみ。 同時に、各文字の出現をカウントします。 

スキャンが終了したら、順序付け制約が満たされていることと、最終カウントが満たされていることの 2 つの条件を確認するだけで済みます。`c == a or c == b`、追加の暗黙の要件として、両方が`a > 0`そして`b > 0`なぜなら、構造はそれぞれの少なくとも 1 つを保証するからです。 

これにより、問題全体が一定のブックキーピングによる 1 回のパスに短縮されます。

 ## アルゴリズムのチュートリアル

 1. カウンタの初期化`ca`、`cb`、`cc`ゼロに。 また、現在どのブロックにいるかを表すステージ変数も追跡します。`0`のために`a`、`1`のために`b`、`2`のために`c`。 
2. 文字列を左から右にスキャンします。 
3. 各キャラクターについて:

 - そうだとしたら`a`、まだステージ中の場合にのみ有効です`0`。 インクリメント`ca`。 
- そうだとしたら`b`、私たちはステージにいるはずです`0`または`1`。 私たちがステージにいるなら`0`、ステージに切り替えます`1`。 インクリメント`cb`。 
- そうだとしたら`c`、私たちはステージにいるはずです`1`または`2`。 私たちがステージにいるなら`1`、ステージに切り替えます`2`。 インクリメント`cc`。 

許可された遷移に違反すると、文字列はただちに無効になります。 
4. スキャン後、両方のことを確認します。`ca > 0`そして`cb > 0`。 
5. 最後に次のことを確認します。`cc == ca`または`cc == cb`。 

スキャン中にトランジションが強制される理由は、決して許可しないようにするためです。`b`全てを終える前に`a`、または`c`全てを終える前に`b`。 

### なぜ効果があるのか

 建設プロセスは三相モノトーン構造を保証します。 有効な文字列には、連続したブロックへの一意のパーティションが必要です。`a`、 それから`b`、 それから`c`。 ステージ変数は、まさにこのパーティショニングを強制します。 すべての文字は厳密な遷移ルール​​に基づいて 1 回だけ処理されるため、必要な順序からの逸脱はすぐに検出されます。 構造が検証された後、残る自由度は次の数だけです。`c`、構造の定義により、以前のブロック サイズの 1 つと一致する必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

s = input().strip()

ca = cb = cc = 0
stage = 0  # 0 = a, 1 = b, 2 = c

valid = True

for ch in s:
    if ch == 'a':
        if stage != 0:
            valid = False
            break
        ca += 1
    elif ch == 'b':
        if stage == 2:
            valid = False
            break
        if stage == 0:
            stage = 1
        cb += 1
    else:  # 'c'
        if stage < 1:
            valid = False
            break
        if stage == 1:
            stage = 2
        cc += 1

if not valid or ca == 0 or cb == 0:
    print("NO")
else:
    print("YES" if (cc == ca or cc == cb) else "NO")
```コードは厳密な位相変数を維持します`stage`これは、現在拡張が許可されているセグメントをエンコードします。 これにより、不正な逆遷移（たとえば、`a`後`b`。 カウンタは、最終条件に必要な正確な周波数を追跡します。 

微妙な点の 1 つは、トランジションはステージに入ると前にのみ進むということです。`1`、私たちは決して戻りません。 これは建設プロセスの不可逆性と一致します。

 ## 特殊なケース

 重大なエッジ ケースは、文字列の順序は正しいが、カウント制約を満たさない場合です。 入力用`aaabbbcccc`、スキャンによって生成される`ca=3`、`cb=3`、`cc=4`。 ステージロジックは構造的にそれを受け入れますが、最終チェックはそれを拒否します。`cc`どちらとも一致しない`ca`または`cb`。 

もう 1 つのエッジ ケースは、移行が早すぎる場合です。 のために`baaa`、最初の文字`b`フォースステージ`1`、しかし遭遇`a`その後、直ちにルールに違反し、カウントが問題になる前に早期に拒否されます。 

最後のケースは、次のような最小限の有効な構造です。`abc`。 スキャンセットは`ca=1`、`cb=1`、`cc=1`、そしてそれ以来`cc == ca == cb`、これは受け入れられ、3 つのセグメントすべての等価性が最終条件によって自然に処理されることが確認されます。
