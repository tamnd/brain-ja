 ## 解決策

 ## 問題の理解

 私たちは、ノードが標準のヒープ順序でラベル付けされた無限の完全なバイナリ ツリーを操作しています。 ルートは 1 で、すべてのノード x には子 2x および 2x+1 があります。 これは、すべてのノードがルートからの一意のバイナリ表現パスに対応し、左に移動すると 0 ビットが追加され、右に移動すると 1 ビットが追加されることを意味します。 

おもしろいのは、ツリーが静的ではないことです。 特定のノード X と同じ深さのすべてのノードに作用する操作を実行できます。操作に応じて、そのレベルのノードのラベルを回転するか、それらのノードをルートとするサブツリー全体を回転します。これにより、内部構造を維持しながら無限ツリーのチャンク全体を効果的に水平方向に移動します。 

最後のクエリ タイプは、すべての変換後にノード X からルートまでのパスに沿った値を要求します。これらの変換では、レベル内で複雑な方法でノードが並べ替えられる場合があります。 

入力サイズは 10^5 操作に達し、ノード値は 10^18 に達するため、ツリーを明示的にシミュレートしたり、操作ごとに構造を再構築したりすることはできません。 個々のノードまたはレベル全体を明示的に追跡しようとするソリューションは、メモリと時間の両方で失敗します。 

素朴な考えは、深さごとに明示的な配列を維持することです。 ただし、2^60 はすでに 10^18 を超えているため、深さは約 60 に達する可能性があります。 深さが浅い場合でも、各レベルには概念的には指数関数的な数のノードが含まれる可能性があり、直接ストレージを不可能にします。 

2 番目の単純なアイデアは、シフトの下で各ノードの現在の ID を追跡することです。 ただし、サブツリーの移動は無限に多くの子孫に影響を与えるため、変更を下位に伝播することも不可能です。 

2 つの操作タイプを混合すると、微妙な落とし穴が発生します。 タイプ 1 はレベル内のラベルのみをシフトしますが、タイプ 2 はそのレベルのノードをルートとするサブツリー全体をシフトします。 これらは根本的に異なるアクションであり、これらを混同すると、誤った祖先の再構築につながります。 たとえば、サブツリーのシフト後、ノードの親は、元のラベル付けでは単純に x//2 ではなくなります。 

正しいアプローチでは、ノードを個別に追跡することを避け、代わりにレベルごとの変換を圧縮された形式で維持する必要があります。 

## アプローチ

 重要な観察は、すべてのノードが深さに属し、すべての操作が X によって決定される 1 つの深さレベルにのみ影響するということです。深さは約 log2(X) であるため、対話するのは約 60 レベルだけです。 

2 つの操作を概念的に分離します。 

タイプ 1 の操作は、レベル内のノード ラベルの循環シフトです。 これは、固定の深さ d でノードの順序が回転されることを意味します。 重要なのは、ツリーの構造は変わらないため、これは親子関係には影響しません。 そのレベルのラベルのみが並べ替えられます。 

タイプ 2 の操作はより巧妙です。 特定のレベルでノードを回転しますが、サブツリー全体も一緒に移動します。 これは、どのサブツリーがどの親の位置の下に位置するかが変わるため、ノードとその親の間のマッピングが変更されることを意味します。 

ブルート フォース シミュレーションでは、レベルごとにノードの明示的なリストを維持し、シフトごとにそれを更新し、さらにタイプ 2 の親子ポインタを更新する必要があります。これには O(N * レベルのサイズ) のコストがかかりますが、レベルには実質的に制限がないため、これは不可能です。 

重要な洞察は、完全な構造は必要ないということです。 任意のノード X について、長さ 60 までのチェーンを形成するその祖先だけを考慮します。レベルごとに上向きに歩き、各深さで発生したすべてのシフトを修正することで、このチェーンを再構築できます。

フルレベルを保存する代わりに、深さごとに 2 つの値を維持します。1 つはタイプ 1 操作の累積循環シフトを表し、もう 1 つはタイプ 2 操作の累積構造シフトを表します。 タイプ 2 は親マッピングに影響を与える追加のオフセットのように動作しますが、タイプ 1 はそのレベルでのラベル解釈にのみ影響します。 

クエリに答えるとき、現在の深さで両方の効果を元に戻すことによって、現在のノードをその親に繰り返しマッピングします。 これが機能するのは、バイナリ ツリー構造により、各ノードの親がそのレベル内の位置によってのみ決定され、両方の操作がレベル ローカルであることが保証されるためです。 

したがって、レベルごとに O(log X) の状態を維持し、クエリごとに O(log X) の上向きジャンプを実行することに問題を集約します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(N * レベル サイズ) | O(レベルサイズ) | 遅すぎる |
 | 最適 | O(N log A) | O(log A) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 1 に達するまで 2 で割ることを繰り返して、ノード X の深さを計算します。これにより、X に関係する各クエリでどのレベルを操作するかが定義されます。 
2. 2 つの配列shift1[d]とshift2[d]を維持します。ここで、dは深さです。 SHIFT1 は、タイプ 1 のクエリによって引き起こされるレベル d でのノード ラベルの循環回転を追跡し、一方、SHIFT2 はタイプ 2 のクエリによって引き起こされる構造回転を追跡します。 一方はラベル付けに影響し、もう一方は親マッピングに影響するため、この分離が必要です。 
3. 深さ d のタイプ 1 クエリの場合、その概念レベルのサイズを法とするshift1[d] に K を追加します。 レベルは無限であるため、絶対的なサイズではなく、トラバースに対する相対的なシフトのみを維持する必要があります。 
4. タイプ 2 クエリの場合は、同様に K を SHIFT2[D] に追加します。 これは、サブツリーのルートがそのレベルでどのように回転され、親子の配置が変化するかを表します。 
5. タイプ 3 のクエリに答えるには、ノード X から開始して、ルートに到達するまでその親を繰り返し計算します。 各ステップで、現在の深さ d を決定し、そのレベルで SHIFT1 と SHIFT2 から逆変換を適用し、元のシフトされていないツリー内の正しい親を計算します。 
6. この上向きの走査中に訪問したすべてのノードを収集し、それらを逆の順序で出力して、ルートから X へのパスを生成します。 

正確かどうかは、各レベルでの親の選択における唯一のあいまいさは、そのレベルでの巡回置換から生じるという事実にかかっています。 保存されたシフトを使用してこれらの順列を修正すると、標準のフロアを 2 で割ることで真の親が得られます。 

### なぜ効果があるのか

 すべての深さで、ノードはサブツリーとラベルのシフトの繰り返しによって引き起こされる概念的な循環順序を形成します。 どちらの操作でも、各レベルが元のレベルの順列であるという事実が保持されます。 このアルゴリズムは、正確な累積順列を明示的に保存するのではなく、暗黙的に保持します。 バイナリ ヒープ内の親関係はレベル内の相対位置にのみ依存するため、置換を元に戻すと正規構造が復元されます。 したがって、上向きのステップごとに、固有の正しい祖先チェーンが再構築されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXL = 61

shift1 = [0] * MAXL
shift2 = [0] * MAXL

def get_depth(x):
    return x.bit_length() - 1

def parent(x, d):
    return x // 2

def solve():
    q = int(input())
    res = []

    for _ in range(q):
        tmp = input().split()
        t = int(tmp[0])

        if t == 1 or t == 2:
            x = int(tmp[1])
            k = int(tmp[2])

            d = get_depth(x)
            k %= (1 << d)

            if t == 1:
                shift1[d] = (shift1[d] + k) % (1 << d)
            else:
                shift2[d] = (shift2[d] + k) % (1 << d)

        else:
            x = int(tmp[1])
            path = []

            cur = x
            d = get_depth(cur)

            while cur:
                path.append(cur)
                if cur == 1:
                    break
                d = get_depth(cur)

                # undo both shifts at level d
                mod = (1 << d)
                cur = ((cur - shift1[d] - shift2[d]) % mod) // 2

            res.append(" ".join(map(str, path)))

    print("\n".join(res))

if __name__ == "__main__":
    solve()
```この実装では、深さによってインデックス付けされた 2 つのグローバル シフト配列が維持されます。 各更新では、適切なレベルでモジュール式の増分が適用され、すべての変換がシミュレートされるのではなく集約されることが保証されます。 

クエリ処理中、標準の親操作を適用する前に、上向きトラバーサルによって累積シフトを差し引くことによって現在のノードが繰り返し修正されます。 減算ステップは、上に移動する前にレベル内のノードの正規の位置を復元するため、非常に重要です。 

よくある間違いは、2 で割った後にシフトを適用することです。これにより、レベルのインデックス作成とヒープ構造の間の対応が崩れます。 修正は、親レベルに移動する前に行う必要があります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、X が非常に小さい場合、特に X = 1 である場合です。この場合、深さはゼロであり、レベル サイズに関するモジュラー演算ではサイズ 0 のマスクを回避する必要があります。 (1 << 0) = 1 であるため、アルゴリズムは深さ 0 でのシフトの適用を自然に回避し、すべてのシフトを自明のゼロにし、無効な操作を防ぎます。 

大きな負の K 値が使用される場合、別のエッジ ケースが発生します。 シフトは累積されたモジュロ レベル サイズであるため、負の更新は適切に正規化する必要があります。 これがないと、減算を繰り返すと有効な範囲を逸脱し、不正確な親の再構築が行われる可能性があります。 実装におけるモジュロ演算により、正回転と負回転の両方で一貫性が保証されます。 

最後の微妙なケースは、同じ深さで更新が繰り返されることです。 タイプ 1 とタイプ 2 は両方とも独立して蓄積されるため、時期尚早にマージしないことが重要です。 それらを分離しておくことで、構造の変更がラベルの置換に干渉しないことが保証され、任意のインターリーブの下で正しい祖先の再構築が維持されます。
