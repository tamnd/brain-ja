 ## 解決策
 ## 問題の理解

 0 秒から 86399 秒までのタイムラインとして 1 日が表されます。このタイムラインに沿って、いくつかの互いに素な間隔があり、それぞれがスケジュールされたタスクを表します。 タスクが開始されたら、それを実行するか無視するかを即座に決定する必要があります。 それを実行すると、インターバル全体にわたって私たちはブロックされ、いくつかのカルマが与えられます。 それを無視することは、現在十分なカルマがある場合にのみ許可され、そうすることで間隔全体を解放しながらそのカルマを消費します。 

タスクの外では、できるだけ多くの固定長のゲーム セッションを挿入したいと考えています。 各セッションには連続して正確に M 秒かかり、セッションは重複できません。 

重要な相互作用は、タスクが互いに重ならないため、時間が自然に一連のタスク間隔に分割され、それらの間に空きギャップが生じることです。 ただし、タスク間隔がブロックされるか空きになるかは当社の決定に依存するため、実際の空きタイムラインは固定されていません。 

入力により N 個のタスクが与えられ、それぞれに開始時刻、終了時刻、カルマ値が指定されます。 タスクごとに、それを実行するか (可能であれば) スキップするかを決定し、その結果生じる自由時間にできるだけ多くの長さ M のゲーム セッションを配置する必要があります。 

カルマの合計が最大 20,000 であるという制約は、カルマが明示的に追跡する必要がある唯一の実際の「リソース」であるという主なシグナルです。 タスクの数は最大 10000 であるため、カルマを状態次元として扱うあらゆるソリューションが妥当です。 

タスクのすべてのサブセットを試す単純なアプローチは、2^N 個の構成をチェックする必要があるため、不可能です。 カルマによって以前の決定と後の決定の間に依存関係が生じるため、時間をかけて動的にプログラムするだけでは不十分です。 

微妙な失敗例は、後で大きな空きブロックを開くために初期のタスクをスキップする必要がある場合に発生しますが、スキップには初期のタスクを実行することによってのみ得られる蓄積されたカルマが必要です。 たとえば、カルマの高い​​タスクが早い段階で現れた場合、後のインターバルのスキップを解除するためだけに、将来の柔軟性が低下するとしても、それを実行せざるを得なくなる可能性があります。 この依存関係により、貪欲な決定は信頼できなくなります。 

2 つの異なる戦略が同じ合計空き時間を生成するが、セグメント構造が異なる場合、別のエッジ ケースが発生します。 ゲームには連続した M 長のブロックが必要であるため、合計の自由時間が同じであっても、自由時間を異なる方法で分割すると、答えが変わる可能性があります。 

## アプローチ

 ブルートフォースソリューションは、タスクに関するあらゆる有効な意思決定シーケンスをシミュレートします。 各タスクで、「実行」または「可能であればスキップ」に分岐し、それに応じてカルマを更新し、ブロックされた間隔の結果のセットを維持します。 すべてのタスクを処理した後、一日中スキャンして、ゲーム セッションを空きセグメントに貪欲に詰め込みました。 シミュレーション自体は線形ですが、分岐により指数関数的な数の状態が作成され、およそ 2^N の可能性に達し、実現可能性をはるかに超えています。 

重要な観察は、タスクが時間内にすでに順序付けられており、重複していないため、システムが順次進化するということです。 どの時点においても、将来の決定において重要なのは、現在のカルマと、現在ゲームのために「空いている」連続した自由時間がどれだけあるかということだけです。 

これは、国家がカルマと構築されている自由時間の現在の構造の両方を追跡するタスクに対する動的プログラミングのアプローチを示唆しています。 

主な問題は、スコアが自由時間を全体の長さだけではなく、セグメントにどのように分割するかによって決まることです。 これは、現在の空きセグメントのモジュロ M の残りを追跡することで処理できます。空き時間が増えると、1 つ以上の完全なゲーム セッションが完了する可能性があります。 

したがって、タイムラインを一連のブロックとして扱います。 タスク間では、自由時間が蓄積されるか (スキップされた場合)、リセットされます (タスクを実行している場合)。 各 DP 移行では、カルマと次の完全なゲーム セッションに向けた「部分的な進行状況」の両方が更新されます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 決定に対するブルートフォース | O(2^N・N) | O(N) | 遅すぎる |
 | タスク、カルマ、自由時間の残りに対する DP | O(N · K · M_state) を O(N · K) に簡略化 | O(N・K) | 承認済み |

 この単純化は、完全な履歴は必要なく、カルマと、完了した完全な M ブロックの数と現在の残りだけが必要であることを観察することによって得られます。 

## アルゴリズムのチュートリアル

 時間の増加順にタスクを処理します。 

正確に k カルマを持つタスクの現在のプレフィックスを処理した後に達成可能な最良の結果を dp[k] に格納する DP テーブルを維持します。 各 dp エントリには、完了したゲーム セッションの数と、まだ完全な M 長セッションを形成していない現在の残りの空き時間という 2 つの値が格納されます。 

1. dp[0] をゲーム数も残りの自由時間もゼロとして初期化します。 他のすべての状態は不可能です。 
2. タスクごとに、最初は空の新しい DP 配列 next_dp を構築します。 
3. 到達可能な各状態 (k、ゲーム、レム) から、タスク間隔の長さ L を考慮します。 
4. タスクを実行することを選択した場合、ブロックされた間隔で時間を進め、現在の空きセグメントが終了します。 残ったレムは、タスク後に新たな自由時間が蓄積されるまでそれ以上貢献しません。 カルマは k_i ずつ増加します。 更新された状態を next_dp[k + k_i] に保存し、ゲームを保存し、次の空きセグメントの開始に備えて rem を 0 にリセットします。 
5. タスクをスキップすることを選択し、十分なカルマがある場合は、カルマから k_i を減算します。 間隔が完全に空きになるので、現在の空きセグメントを L 秒だけ延長します。 rem + L を更新し、完全な M ブロックを完成したゲームに変換し、rem % M のみを新しい剰余として保持します。 ゲーム数は (rem + L) // M ずつ増加します。 
6. タスクのすべての遷移を処理した後、dp を next_dp に置き換え、各カルマの最大ゲームを維持し、同点の場合の最良の剰余を保存することによって状態をマージします。 
7. すべてのタスクの後、最後のタスク終了から 86400 までの最後の時間区間も、最終空きセグメントとして処理されます。 

正しさは、すべての決定がカルマと現在の無料セグメントの構造を通じて将来の可用性にのみ影響し、他の履歴情報が将来の選択に影響を及ぼさないという事実に依存します。 

不変条件は、各タスク プレフィックスと各可能なカルマ値について、dp[k] が完了したゲーム セッションの達成可能な最良の数と可能な限り最良の部分的な空きセグメント状態を表すということです。 同じ (karma、rem) ペアで終わる 2 つの歴史は交換可能です。将来の決定はこれら 2 つの値にのみ依存するためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def add_free(dp_entry, length, M):
    games, rem = dp_entry
    total = rem + length
    games += total // M
    rem = total % M
    return games, rem

def better(a, b):
    # compare (games, rem) lexicographically by games, then rem
    if a[0] != b[0]:
        return a if a[0] > b[0] else b
    return a if a[1] > b[1] else b

N, M = map(int, input().split())
tasks = []
for _ in range(N):
    l, r, k = map(int, input().split())
    tasks.append((l, r, k))

dp = {0: (0, 0)}  # karma -> (games, rem)

prev_end = 0

for l, r, k in tasks:
    length = r - l + 1
    new_dp = {}

    for karma, (games, rem) in dp.items():
        gap = l - prev_end
        base_games, base_rem = add_free((games, rem), gap, M)

        # do task
        nk = karma + k
        state = (base_games, 0)
        if nk not in new_dp:
            new_dp[nk] = state
        else:
            new_dp[nk] = better(new_dp[nk], state)

        # skip task if possible
        if karma >= k:
            nk = karma - k
            state = add_free((base_games, base_rem), length, M)
            if nk not in new_dp:
                new_dp[nk] = state
            else:
                new_dp[nk] = better(new_dp[nk], state)

    dp = new_dp
    prev_end = r + 1

# final tail
end_time = 86400
final_dp = {}

for karma, (games, rem) in dp.items():
    state = add_free((games, rem), end_time - prev_end, M)
    if karma not in final_dp:
        final_dp[karma] = state
    else:
        final_dp[karma] = better(final_dp[karma], state)

print(max(g for g, _ in final_dp.values()))
```カルマはスキップが許可されるかどうかを制御する唯一の制約であるため、DP 辞書は現在のカルマによってキー設定されます。 各遷移は、残余メカニズムを通じて空き時間構造を明示的に更新し、後で追加の空き時間と結合するときに部分セグメントが正しく考慮されるようにします。 

実装の微妙な詳細は、タスク間のギャップの処理です。 そのギャップは決定に関係なく常に完全に空いているため、次のタスクを処理する前に現在の空きセグメントに追加する必要があります。 

もう一つの微妙な点は、タスクの実行時に残りをリセットすることです。 タスクを実行すると連続性が失われるため、部分的に蓄積された空きセグメントを引き継ぐことはできません。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、カルマがゼロであるため、たとえタスクが長くて利用可能なゲーム時間が減少したとしても、初期のタスクを実行する必要がある場合です。 カルマが不十分な場合は「スキップ」遷移が生成されず、DP が有効な状態のみを伝播するよう強制されるため、アルゴリズムはこれを処理します。 

もう 1 つのケースは、小さなタスクが長く続くことで、実行とスキップを繰り返す機会が多くなる場合です。 DP は各タスクで両方のブランチを正しく探索し、後の大きなスキップのためにカルマが保存されている状態が失われないようにします。 

3 番目のケースは、タスク間の大きなギャップがスケジュールを支配する場合です。 ギャップ処理ステップにより、次のタスクでの決定の前にタスク外の空き時間が常に蓄積されるようになり、可能性のあるゲーム セッションの過小カウントが防止されます。
