## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

from functools import lru_cache

def solve_case(a, b, c):
    target = c - a
    if target < 0:
        return False

    @lru_cache(None)
    def dfs(x):
        if x == 0:
            return {0}

        res = set()
        nxt1 = x // 2
        nxt2 = x // 4

        for sub in dfs(nxt1):
            res.add(x + sub)
        for sub in dfs(nxt2):
            res.add(x + sub)

        return res

    return target in dfs(b)

def main():
    t = int(input())
    for _ in range(t):
        a, b, c = map(int, input().split())
        print("YES" if solve_case(a, b, c) else "NO")

if __name__ == "__main__":
    main()
```実装は状態の解釈に直接に従います。 再帰では、次から始まるすべての考えられる寄与合計が計算されます。`b`。 各状態は分岐する前に独自の値を追加します。 メモ化により、値が繰り返されることが保証されます。`b`は再計算されません。これは、フロア分割後に多くの異なるパスが同じ整数につながる可能性があるため、非常に重要です。 

小切手`target in dfs(b)`は最終的な到達可能条件です。

 ## 特殊なケース

 重要なエッジケースの 1 つは次のような場合です。`b = 0`。 この場合、プロセスでは追加がまったく実行されないため、考えられる唯一の結果は次のとおりです。`a`。 アルゴリズムはこれを正しく処理します。`dfs(0)`返品`{0}`、つまり貢献は追加されないため、次の場合にのみ受け入れられます。`c == a`。 

別のエッジケースが発生するのは次の場合です。`b = 1`。 ここから、2 または 4 で除算するとすぐにゼロが生成されますが、この順序では終了前に 1 つの最後の寄与が強制されます。 再帰はこれを次のように正しくキャプチャします`1 + dfs(0)`、正確に生産`{1}`。 

3 番目のエッジケースには、次のような急速な崩壊が含まれます。`b = 3`。 1つの枝が与えます`3 // 2 = 1`、もう一方は与えます`3 // 4 = 0`。 これにより 2 つの異なるパスが作成され、DP には両方の寄与が含まれます。 ここで貪欲な選択は失敗します。なぜなら、より小さい区分を早期に選択すると、あと 1 ステップで値を大きく保つことに依存する到達可能な合計が排除される可能性があるからです。
