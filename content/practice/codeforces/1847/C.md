 ## 解決策
 ## 問題の理解

 小さな整数の配列が与えられ、それを繰り返し拡張することができます。 各拡張機能は、ある位置から始まるサフィックスを選択し、その XOR を配列の末尾に追加します。 したがって、新しい値はプレフィックスとサフィックスの派生値になります。現在配列の長さである場合$m$、インデックスの選択$i$の XOR を追加します$a_i$を通して$a_m$。 

タスクはプロセスをシミュレートすることではなく、そのような操作を何度でも行った後に配列に現れる可能性のある最大値を決定することです。 

制約から観察される重要な点は、値が次の制限によって制限されるということです。$2^8$, したがって、各数値は 8 ビットに収まります。 配列の長さは最大で大きくなる可能性があります。$10^5$ただし、テスト全体の合計にも限界があるため、テストごとに線形または線形に近い値が期待されます。 二次関数以上のもの$n$すぐに遅すぎます。$10^{10}$最悪の場合の運用。 

素朴な解釈では、考えられるすべてのサフィックスの選択と新しく作成されたすべての配列をシミュレートしようとします。 新しい要素ごとに、後で使用できるサフィックス XOR のセットが変更されるため、分岐が大きくなります。 考えられるすべての XOR セグメントを計算しても、明示的に次のようになります。$O(n^2)$セグメントが増加し、成長が繰り返されると悪化します。 

すべての要素が同一である場合、微妙なエッジケースが発生します。 たとえば、次の場合$a = [5,5,5]$、サフィックス XOR は長さのパリティに応じて 5 または 0 のいずれかであり、単純に考えると、繰り返し増加が 5 を超えることはできないと思われるかもしれません。しかし、サフィックスを慎重に選択することで、0 を生成し、その後の操作を通じて間接的に結合することができます。 これは、単純な方法でプロセスが単調ではないことを示しています。 

もう 1 つのエッジ ケースは、プレフィックス XOR が繰り返される場合です。 XOR はキャンセルされるため、プレフィックスを繰り返すと多くのサフィックス XOR が等しくなります。これは、構造が明示的なセグメントではなくプレフィックス XOR 関係によって支配されていることを示唆しています。 

## アプローチ

 ブルートフォースアプローチはプロセスをシミュレートします。 配列の現在の状態ごとに、インデックスのすべての選択肢を試します。$i$、サフィックス XOR を計算し、追加して繰り返します。 それぞれの操作にかかる費用$O(n)$サフィックス XOR を再計算するか、プレフィックス構造を維持します。 配列は毎回 1 ずつ増加し、最大まで増加する可能性があるため、$O(n^2)$概念的な分岐が最悪の状態にある場合、これはすぐに実行不可能になります。 

重要な洞察は、動的配列の観点から考えるのをやめ、代わりに構造をプレフィックス XOR に圧縮することです。 定義する$p[i]$プレフィックス XOR として最大$i$。 次に、からの任意のサフィックス XOR$i$に$j$は$p[j] \oplus p[i-1]$。 これは、生成されるすべての値が 2 つのプレフィックス XOR 状態の XOR であることを意味します。 

したがって、プロセスは実際に次の形式の値を生成しています。$p[i] \oplus p[j]$さまざまな到達可能なプレフィックス状態に対応します。 これを理解すると、この操作は XOR 閉包の下でセットを構築するのと同等になります。 GF(2) 上の線形基底の意味で到達可能な最大要素が必要です。 

数値はわずか 8 ビットであるため、XOR 空間は小さく、すべてのプレフィックス XOR にわたって線形基底を貪欲に維持できます。 達成可能な最大値は、基底ベクトルのサブセットを使用して形成できる最大 XOR です。 生成をシミュレートする代わりに、各プレフィックス XOR を基底に挿入し、最も表現可能な値を追跡します。

 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | 指数関数 | O(n^2) の状態 | 遅すぎる |
 | 線形 XOR プレフィックス XOR に基づく | O(n · 8) | お(8) | 承認済み |

 ## アルゴリズムのチュートリアル

 プレフィックス XOR と 8 ビットにわたるバイナリ線形基底を維持しながら配列を処理します。 

1. プレフィックス XOR を次から順に計算します。$p[0] = 0$。 それぞれ$p[i]$開始位置から位置までの XOR を表します$i$。 これにより、セグメント XOR クエリが 2 つのプレフィックス状態の XOR に変換されます。 
2. 8 ビットにわたって線形基底を維持します。 各基底ベクトルは、XOR の組み合わせを生成するために使用できるビット パターンに対応します。 
3. 各プレフィックス XOR 値について、それを基底に挿入しようとします。 挿入中に、基底を削減したままにするために、最上位ビットから最下位ビットまで既存の基底要素によってそれを削減します。 
4. リダクション後の値がゼロ以外の場合、それは新しい基底ベクトルになります。 ゼロになった場合、それはすでに表現可能であり、基底サイズは増加しません。 
5. すべてのプレフィックスを処理した後、基底ベクトルを使用して最上位ビットから最下位ビットまで結果を貪欲に改善しようとすることにより、最大の XOR 値を構築します。 

機能する理由: サフィックス XOR 演算を繰り返して生成できるすべての値は、いくつかのプレフィックス XOR 値の XOR として書き換えることができます。 これらのプレフィックス XOR は、GF(2) 上のベクトル空間に存在します。 線形基底はまさにこの空間を捉えます。 すべての操作では既存のプレフィックス XOR の XOR の組み合わせのみが生成されるため、このスパンから離れることはなく、到達可能なすべての値がこのスパンに含まれます。 したがって、到達可能な最大強度は、スパンから取得できる最大 XOR となります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def insert_basis(basis, x):
    for b in range(7, -1, -1):
        if (x >> b) & 1:
            if basis[b] == 0:
                basis[b] = x
                return
            x ^= basis[b]

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        basis = [0] * 8
        px = 0

        insert_basis(basis, 0)

        for v in a:
            px ^= v
            insert_basis(basis, px)

        ans = 0
        for b in range(7, -1, -1):
            ans = max(ans, ans ^ basis[b])

        print(ans)

if __name__ == "__main__":
    solve()
```このソリューションでは、まずプレフィックス XOR 値を構築し、それらをバイナリ基底構造に入力します。 ヘルパー関数`insert_basis`新しいベクトルはそれぞれ、挿入前に上位ビットに対して削減され、独立性が維持されます。 

最後の貪欲な再構成ステップでは、利用可能な基底ベクトルを使用してビットを高値から低値に反転することを試みることにより、達成可能な最大の XOR を構築します。 

よくある実装の落とし穴は、最初のプレフィックス XOR のゼロを含め忘れることです。 この値は空のプレフィックスを表し、配列の先頭から始まるサフィックスを有効にするため、必須です。

 ## 特殊なケース

 次のような単一要素配列の場合`[0]`の場合、プレフィックス XOR セットにはゼロのみが含まれるため、基底は空のままで、答えはゼロになります。 アルゴリズムは最初のゼロを明示的に挿入するため、正しく 0 が返されます。 

次のような定数配列の場合`[5,5,5]`、プレフィックス XOR は 5 と 0 を交互に行います。基底には最終的に 0 以外のベクトルが 1 つだけ含まれるため、最大値は 5 のままです。挿入ステップにより、繰り返される XOR 値が新しい独立した方向として扱われることが正しく回避されます。 

のような独立性の高い集合の場合、`[1,2,4,8]`、プレフィックス XOR は 4 ビット空間全体に広がります。 基底はすべての独立したベクトルを収集し、貪欲な再構成は 15 に達し、完全な XOR 閉包が正しく捕捉されたことを確認します。
