 ## 解決策
 ## 問題の理解

 9 つのセルの直線トラックでプレイされる小さなボード ゲームをシミュレートしています。 最初は、3 つの異なるピースが固定位置に配置されています。紫色のピースはセル 2 から始まり、緑のピースはセル 3 に、黄色のピースはセル 4 に配置されます。 

ゲームは、テスト ケースごとに 12 個のコマンドのシーケンスを通じて進行します。 各コマンドは色と移動距離を指定します。 コマンドを実行すると、対応する色のピースがラインに沿って左右に移動します。 

重要な点は、ピースを積み重ねることができるということです。 移動中のピースがすでに他のピースによって占有されているセルに到着すると、そのピースは既存のスタックの上に配置されます。 さらに重要なのは、ピースがスタック内に単独で存在しない場合、そのピースを移動すると、その上にあるすべてのものが引きずられることです。 これにより、システムは、移動がどこに着地するか、スタック内のどのピースが選択されるかに応じて、時間の経過とともにマージおよび分割できる一連の動的なスタックのように動作します。 

12 個のコマンドすべてを処理した後、スタック内の内部順序に関係なく、3 つの部分すべてが同時にセル 9 に到達するかどうかを判断する必要があります。 

制約の構造は非常に厳密ですが、状態のサイズは小さいです。 各テスト ケースには、12 の演算の固定長シーケンスと最大 10^4 のテスト ケースがあります。 これにより、大規模な構造に対して操作ごとの大量のシミュレーションを実行するソリューションは即座に除外されます。 ただし、ピースの合計数はわずか 3 つであり、各操作が一定または一定に近い時間で処理される限り、注意深く状態を追跡した直接シミュレーションで十分であることが強く示唆されています。 

スタック移動ルールにより、微妙なエッジ ケースが発生します。 単純な実装では、各色の位置のみを追跡し、スタック構造を無視する可能性があります。 スタックの中央にあるピースが移動すると、その上のピースが誤って残されるため、これは失敗します。 

たとえば、紫がセルにあり、その上に緑が積み重ねられており、コマンドが紫を移動するとします。 次に、紫と緑の両方が一緒に移動する必要があります。 色ごとの座標のみを追跡する単純なモデルでは、紫だけが誤って移動してしまいます。 

複数のマージが発生すると、別の失敗ケースが発生します。 スタックがマージされると、その後の操作は複数の色に伝播する可能性があるため、各スタック内の順序を保持する必要があります。 

## アプローチ

 ブルートフォース解釈では、ボードとすべてのスタックを明示的にシミュレートします。 私たちは 9 つのリストを管理しており、それぞれがピースのスタックを表しています。 各移動では、現在のスタック内でターゲット ピースを見つけ、リストを分割し、サフィックスを別のスタックに移動する必要があります。 スタックが小さいため、これはすでに実現可能ですが、セグメントを見つけて切り取る方法を正確に行う必要があります。 

最悪の場合、各操作で最大 3 のサイズのスタックをスキャンして移動部分を特定し、リストをスライスする必要がある可能性があります。 実際にはこれは一定時間ですが、注意せずに実装すると、構造はまだ少しぎこちなくなります。 

重要な観察は、システム全体には最大でも 3 つのオブジェクトがあり、スタックの相互作用は 9 つの位置にわたるこれらのオブジェクトの単なる並べ替えであるということです。 高度なデータ構造は必要ありません。 セルごとのスタックの内容とスタック内の各部分の位置の両方を維持する限り、直接リストベースのシミュレーションで十分です。 

ブルートフォースアプローチは機能しますが、位置追跡のみで実装すると脆弱になります。 正しい洞察は、状態が十分小さいため、各位置で完全なスタックを明示的に維持し、各移動後に一貫して更新できるということです。

 ## アルゴリズムのチュートリアル

ボードを 9 つのスタックとして維持し、各スタックは下から上への色のリストになります。 また、色ごとに、その色が現在どのスタックに属しているかを維持します。 

1. 9 つの空のスタックを初期化し、位置 2、3、4 にそれぞれ紫、緑、黄色を配置します。 それぞれは単一要素のスタックです。 
2. 操作ごとに、指定された色を含むスタックを識別します。 スタックだけでなく、そのスタック内の色のインデックスも特定します。 このインデックスは、その位置から上のすべてが一緒に移動するため、不可欠です。 
3. スタックを 2 つの部分に分割します。選択したピースより下の部分は元のセルに残り、選択したピースより上の部分はブロックとして削除されます。 
4. 現在のインデックスに移動値を加算して、宛先セルを計算します。 
5. 移動されたブロックを、順序を維持して宛先スタックに追加します。 
6. セルが変更されているため、移動したブロック内の各色の記録位置を更新します。 
7. すべての操作を処理した後、3 色すべてがスタックのセル 9 に存在するかどうかを確認します。 

正確さは、各操作がスタックの連続したサフィックスのみを移動すること、およびスタックは各移動後に常に正しい順序で維持されるという事実にかかっています。 

### なぜ効果があるのか

 いつでも、各セルには、そこに到着したピースの正確な垂直方向の順序を反映するスタックが保存されます。 サフィックスのみが移動されるため、移動されたグループ内の相対的な順序は決して変更されません。 すべての操作では、各ピースが正確に 1 つのスタックに属し、スタック順序が履歴のスタック順序と一致するという不変条件が保持されます。 シミュレーションはルールを正確に反映しているため、最終的な構成は説明したプロセスに忠実です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        stacks = [[] for _ in range(10)]
        pos = {}

        # initial positions
        stacks[2] = [1]
        stacks[3] = [2]
        stacks[4] = [3]
        pos[1] = 2
        pos[2] = 3
        pos[3] = 4

        for _ in range(12):
            a, b = map(int, input().split())
            c = a
            cur = pos[c]
            stack = stacks[cur]

            idx = stack.index(c)
            moving = stack[idx:]
            stacks[cur] = stack[:idx]

            nxt = cur + b
            stacks[nxt].extend(moving)

            for x in moving:
                pos[x] = nxt

        if pos[1] == 9 and pos[2] == 9 and pos[3] == 9:
            print("Y")
        else:
            print("N")

if __name__ == "__main__":
    solve()
```このソリューションはスタック モデルを直接エンコードします。 各スタックは Python リストであり、スライスによって移動する部分と留まる部分がきれいに分離されます。 辞書`pos`これにより、任意の色の現在のセルを即座に見つけることができます。 

唯一の微妙な実装の詳細は、`index`スタック内のピースの位置を見つけます。 スタック サイズは最大 3 であるため、これは事実上一定時間です。

 ## 特殊なケース

 エッジ ケースの 1 つは、移動によってスタックの一番下の要素が選択される場合です。 その場合、スタック全体が移動され、元のセルは空になります。 インデックス 0 からスライスすると完全なリストが返され、空のプレフィックスが後に残るため、実装はこれを自然に処理します。 

もう 1 つの特殊なケースは、マージと分割を繰り返すことです。 スタックが形成され、途中で分割され、後で別の位置で再結合されることがあります。 常に明示的なリストを介してスタックを再構築するため、履歴的な依存関係が失われることはなく、各操作で正確な構造が再計算されます。 

最後の微妙なケースは、複数のピースが異なる順序で同じ目的地に着地する場合です。 このアルゴリズムでは、移動された各ブロックが宛先スタックの最後に追加されるため、到着順序が維持されます。これは、新しい到着ブロックが既存のブロックの上に配置されるという問題のルールと一致します。
