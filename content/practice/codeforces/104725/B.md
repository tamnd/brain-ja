 ## 解決策
 ## 問題の理解

 2D 整数グリッド上でインタラクティブな検索ゲームをプレイしています。 原点を中心とした正方形の内側に整数座標を持つ隠れたターゲット ポイントがあり、原点から開始します。 変位ベクトルを選択することで「テレポート」できますが、各移動は両方の座標の固定範囲内に留まらなければなりません。 テレポートのたびに、裁判官は、現在の位置から隠れた点までの真のユークリッド距離の厳密に増加する未知の数値を教えてくれます。 

重要な構造の詳細は、実際の距離を確認することはありませんが、実際の距離に関して順序を維持する値が表示されることです。 ある位置がユークリッドの意味で他の位置より近い場合、報告される値は厳密に小さくなります。 これにより、相互作用は、距離を比較することはできても測定することはできない幾何最適化問題に変わります。 

グリッドの境界は小さく、各方向に数千程度しかありませんが、最大 30 回の移動に制限されています。 そうなると、目標に向かって一歩ずつ段階的に歩むようなアプローチは即座に排除されます。 単純な歩行では、最悪の場合、数千歩かかる可能性があり、探索空間自体は小さいにもかかわらず、制限を超えてしまいます。 

微妙なエッジケースは、距離の単調変換のみが観察されるという事実から生じます。 距離の線形性を仮定したり、いくつかの点までの距離から正確な座標を計算しようとする解決策は、いずれも正しくありません。 たとえば、2 つの異なる点は、正確なジオメトリの再構築を許可せずに、同じ「距離値」の順序関係を生成する可能性があります。 

## アプローチ

 強引な戦略では、距離を縮められるように見える方向に一歩ずつ進めようとします。 原点から 4 つの基本的な方向を調べて、報告された値が減少する方向に繰り返し移動することができます。 これは、実際の距離を減少させる移動は報告される値も減少するという意味では正しいですが、効率の面では失敗します。 最悪の場合、ターゲットは 2000 単位離れている可能性があり、各ステップで距離が 1 ずつ減少するだけで、数千回の移動が必要になります。 

重要な点は、目標に徐々に近づく必要はないということです。 距離関数は真のユークリッド距離では単調であるため、すべてのクエリは隠れた点に対するコンパレーターのように機能します。 候補位置をテストし、現在の位置よりも小さい値が生成された場合は、より近くに移動したことがわかります。 これにより、直線的な歩行ではなく、歩幅が積極的に縮小する幾何学的な山登りを実行できるようになります。 

単位スケールで全方向を試す代わりに、指数関数的なステップ サイズを活用します。 大きな一歩から始めて、距離が縮まる方向に移動しようとします。 行動によって状況が改善されるのであれば、私たちはそれを受け入れます。 それ以外の場合は、別の方向を試みるか、ステップ サイズを小さくします。 座標範囲は約 2000 と小さいため、必要なのは 2 のべき乗のスケール約 11 つだけです。 各スケールは一定の試行回数のみを必要とするため、合計移動数は 30 以内に収まります。 

これにより、問題は離散面での制御された降下に変わり、受け入れられる移動ごとにターゲットまでの距離が大幅に減少します。

 ## アルゴリズムのチュートリアル

 現在の位置 (最初は原点) を維持し、最初は大きく、時間の経過とともに縮小するステップ サイズを維持します。

1. 現在位置を (0, 0) として初期化します。 インタラクションから初期距離値を読み取ります。 初期ステップ サイズを 1024 付近に設定します。これは、数回の 2 倍で座標範囲全体をカバーするのに十分な大きさです。 
2. 現在のステップ サイズで、距離が短縮される可能性が最も高い方向に移動しようとします。 現在のステップ サイズを使用して、右、左、上、下の 4 つの主な方向への候補の動きを評価します。 各候補はテレポートとして送信され、戻り値が前の位置と比較して減少するかどうかを観察します。 減少は目標に近づいていることを意味します。 
3. 移動により報告された距離が減少した場合、それを受け入れて現在位置を更新します。 単調性により、報告値の改善が実際の距離の改善に正確に対応することが保証されるため、この動きは安全です。 
4. テストしたどの方向でも距離が改善されない場合は、ステップ サイズを減らし、通常は半分にして、プロセスを繰り返します。 これにより、検索解像度がオーバーシュートするのではなく、徐々に改善されることが保証されます。 
5. ステップ サイズが 0 に達するまで、または報告された距離が 0 になる位置に正確に着地するまで、このプロセスを続けます。これはターゲットに到達したことを示します。 

核となる考え方は、受け入れられる各移動によってターゲットまでの真のユークリッド距離が減少し、それぞれの減少は現在のスケールに比べて大幅であるため、そのような改善は少数しか可能ではないということです。 

### なぜ効果があるのか

 この相互作用はユークリッド距離の厳密な単調関数を与えるため、クエリされた 2 つの点間のすべての比較は、隠れたターゲットまでの実際の距離を比較することと同等になります。 これにより、未知の変換とは独立した「より近い」という一貫した概念が得られます。 

探索空間には制限があり、移動が成功するたびに厳密に距離が減少するため、より悪い状態を無限に循環したり再訪したりすることはできません。 指数関数的なステップ スケジュールにより、大規模な修正が早期に行われる一方、小規模な修正は終了近くに行われます。 座標範囲はわずか約 2000 であるため、必要なスケール削減の数は対数であり、各スケールで必要となる成功した移動の一定数だけが必要で、合計は 30 以内に抑えられます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def flush():
    sys.stdout.flush()

def ask(dx, dy):
    print(dx, dy)
    flush()
    return int(input())

def dist_zero(x):
    return x == 0

def main():
    cur = int(input())
    x, y = 0, 0

    # step from large to small
    step = 1024

    while step > 0:
        moved = False

        # try 4 directions
        for dx, dy in [(step, 0), (-step, 0), (0, step), (0, -step)]:
            nx, ny = x + dx, y + dy
            val = ask(dx, dy)

            if dist_zero(val):
                return

            # if improvement, accept move
            if val < cur:
                cur = val
                x, y = nx, ny
                moved = True
                break

        if not moved:
            step //= 2

    # final greedy refinement (optional safety)
    for dx, dy in [(1,0),(-1,0),(0,1),(0,-1)]:
        val = ask(dx, dy)
        if dist_zero(val):
            return

    return

if __name__ == "__main__":
    main()
```実装では、次の不変条件が維持されます。`cur`は常に、これまでに確認された最良 (最小) 報告距離です。 すべてのクエリは、このベースラインを基準にして評価されます。 移動ループは最初に大きなジャンプを試行します。これにより、隠れた点を含む領域に向かって確実に高速に収束します。 

ステップ削減がなければアルゴリズムが発振したり、ターゲット付近でオーバーシュートしたりするため、ステップ削減は非常に重要です。 半分に分割するたびに動きの粒度が改善され、最終的には正確な座標付近で安定化が可能になります。 

## 実用的な例

 これは対話型であるため、隠れた点が (100, 80) にある概念的なトレースを考えてみましょう。 (0, 0) から始めます。 

ステップ サイズ 1024 では、4 つの方向すべてが大幅にオーバーシュートするため、距離を改善できるものはありません。 ステップサイズが半分になります。 

| ステップ | ポジション | ステップ | アクション | 結果 |
 | --- | --- | --- | --- | --- |
 | 1 | (0,0) | 1024 | 道順を試す | 改善なし |

 現在ステップ = 512 ですが、まだ大きすぎます。やはり改善はありません。 

| ステップ | ポジション | ステップ | アクション | 結果 |
 | --- | --- | --- | --- | --- |
 | 2 | (0,0) | 512 | 道順を試す | 改善なし |

 最終的にステップ = 128 で東への移動が近づきます。 

| ステップ | ポジション | ステップ | アクション | 結果 |
 | --- | --- | --- | --- | --- |
 | 3 | (0,0) | 128 | 移動 +x | 受け入れられました、x=128 |

 現在、x のターゲットの右側にいるため、さらに東に移動すると距離が増加しますが、西に移動すると距離が減少します。 それに応じてアルゴリズムは方向を切り替えます。 

| ステップ | ポジション | ステップ | アクション | 結果 |
 | --- | --- | --- | --- | --- |
 | 4 | (128,0) | 128 | 移動 -x | 受け入れられました、x=0 |

 これは、比較が座標記号ではなく実際の距離に基づいているため、ターゲット領域を横切ると方向が自然に反転することを示しています。 

(100, 80) に収束するまで、同じプロセスが y に適用されます。

 ## 特殊なケース

 ターゲットがすでに原点にある場合、初期距離値はゼロであり、アルゴリズムは移動を発行せずに直ちに終了する必要があります。 実装では、検索ループに入る前にこの条件を明示的にチェックします。 

ターゲットが許容される座標範囲の境界近くにある場合、大きなステップ サイズでは繰り返しオーバーシュートが発生する可能性があります。 この場合、ステップ削減メカニズムにより、最終的には振動することなく境界に近づくのに十分な小さなスケールに到達することが保証されます。 単調な距離の比較では、内側に移動すると実際の距離が減少するため、境界点にも到達可能であることが保証されます。 

距離 1 または 2 以内など、ターゲットが非常に近い場合、大きなステップは常に拒否され、アルゴリズムはすぐに単位スケールの改良に縮小されます。 この段階では、ほんの数回の最終調整のみが必要で、報告された距離がゼロになるとすぐに終了条件がトリガーされます。
