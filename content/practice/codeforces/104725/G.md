 ## 解決策
 ## 問題の理解

 私たちは、ポケモンのような戦闘機で構成される 2 つの順序付けされたチーム間のターンベースの決闘をシミュレートしています。 各チームはユニットの列であり、常に各チームの先頭のユニットのみがアクティブになります。 2 人のプレイヤーはアリスから順番に順番を変えます。 各ターンで、アクティブなユニットは、物理攻撃、魔法攻撃、またはエネルギー コストと固定ダメージを伴う究極のスキルのいずれかのアクションを 1 つだけ選択します。 

物理攻撃と魔法攻撃は、相手の対応する防御力によって減少するダメージを与えますが、アルティメットは固定の真のダメージを与えますが、エネルギーを蓄積する必要があります。 エネルギーはゼロから始まり、そのユニットが物理攻撃または魔法攻撃を使用するたびに 1 ずつ増加し、アルティメットが使用されると消費されます。 ユニットは攻撃後、チームの後方に移動します。 ユニットが対戦相手の HP をゼロ以下に減らすと、対戦相手の現在のユニットはすぐに次に生きているユニットに置き換えられます。 

戦いは、どちらかのチームがポケモンを使い果たすか、K ラウンドが完了するまで続きます。ラウンドは、アリスの動きとそれに続くボブの動きとして定義されます。 K ラウンド後にどちらのチームも勝てなかった場合、結果は引き分けとなります。 

入力サイズは片側あたり最大 100,000 匹のポケモン、K は最大 1,000,000 に達し、すべてのステータスは最大 10^8 まで大きくなります。 これにより、すべての K ラウンドにわたる個々のエネルギーまたはターンごとの状態遷移を処理するシミュレーションは直ちに除外されます。 O(K) であっても許容されますが、各ポケモンの内部戦闘状態のアクションごとのシミュレーションに依存するものは、単純に決定を再計算すると遅すぎます。 

重要な点は、各ユニットの行動の選択が現在のエネルギーと対戦相手の現在のステータスにのみ依存することです。 ただし、対戦相手も時間の経過とともに変化するため、両サイドのすべてのスキルに対する単純なターンごとの再計算は依然として O(K) であり、これは問題ありませんが、より深い状態遷移を再計算したり、アクションごとに明示的にエネルギーごとの増加をシミュレートしたりするのは不必要なオーバーヘッドです。 

一般的な障害ケースは、ユニット スイッチ間でのエネルギー蓄積の管理を誤ったことが原因で発生します。 たとえば、ポケモンがスイッチインすると、そのエネルギーはゼロにリセットされます。 これを忘れると、最終的な使用タイミングが間違ってしまいます。 

もう 1 つの微妙な問題はタイブレークです。 複数のアクションが同じダメージを与える場合、究極ではなく物理または魔法を選択する必要があります。 このルールが無視されると、実装によりエネルギーが誤って浪費されたり、異なる損傷シーケンスが発生したりする可能性があります。 

最後に、「ラウンド制限」条件を慎重に処理する必要があります。 ゲームは K 個の個別の動きではなく、K 個の完全なペアの動きの後に終了するため、半ラウンドの停止は間違った結果につながります。 

## アプローチ

 ブルートフォースのアイデアは単純です。説明どおりに各動きを正確にシミュレートします。 各ターンで、対戦相手の現在アクティブなユニットに対する物理的、魔法的、究極のダメージを評価することにより、アクティブなポケモンに最適なアクションを計算します。 ダメージを与え、HPを更新し、エネルギーを管理し、気絶したりアクションを終了した場合にポケモンを回転させます。 

これが機能するのは、ルールが完全に決定的でローカルであるためです。 それぞれの決定は現在の統計とエネルギーのみに依存します。 ただし、その代償として、ターンごとに 3 つのダメージ値を再計算し、潜在的に 2,000 ターンにわたって状態遷移を維持する必要があります。 K は最大 10^6 であるため、慎重に実行すれば Python でもこれは実現可能ですが、隠れた問題はターンごとの計算ではなく、リストや削除を単純に実装した場合にチームの移行や繰り返しのオブジェクト操作が非効率的に処理されることです。 

不必要な構造で「最適な攻撃」を再計算しようとしたり、キューを頻繁に再構築したりすると、さらに非効率が生じます。

重要な観察は、各ターンの構造が独立しているということです。必要なのは、各サイドの現在の先頭のポケモンと、残りのキューへのポインターだけです。 過去の状態を振り返る必要は決してありません。 したがって、高価なキュー操作を使用するのではなく、配列へのインデックスを維持できます。 

これにより、シミュレーションが定数時間遷移を伴う O(K) 個の単純な算術演算に削減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | リスト操作を使用したブルート フォース シミュレーション | O(K · n/a) | O(n + m) | 遅すぎる |
 | 最適化されたポインターベースのシミュレーション | O(K) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 各チームを表す 2 つの配列と、現在アクティブなポケモンを示すポインターを維持します。 各ポケモンは、残りの HP と現在のエネルギーも追跡します。 

毎ターン、アクティブなポケモンの最適な動きを計算します。 

1. アリスとボブのキューから先頭のポケモンと、現在の HP とエネルギーを読み取ります。 
2. 物理ダメージを最大(0, A − 相手の物理防御力)として計算します。 
3. 魔法ダメージを最大(0, B − 相手の魔法防御力)として計算します。 
4. 最終的なダメージを W として計算します。ただし、エネルギー ≥ E の場合に限ります。 それ以外の場合は、利用できないものとして扱います。 
5. 最大のダメージを与える技を選択します。 物理または魔法がアルティメットと関係がある場合は、必要に応じてアルティメットよりも物理または魔法を優先します。 
6. 相手の現在HPにダメージを与えます。 
7. 物理または魔法を使用した場合、エネルギーが 1 増加します。 アルティメットを使用する場合、エネルギーを E だけ減らします。 
8. 相手のHP ≤ 0の場合、相手のポインタを次のポケモンに進め、そのポケモンのHPとエネルギー状態をリセットします。 
9. ターンを切り替え、K ラウンドが完了するか、1 つのチームがなくなるまで繰り返します。 

この構造の背後にある理由は、エネルギーと HP の進化は現在の相互作用ペアにのみ依存するため、各ポケモンの現在の状態を超える履歴追跡は必要ないということです。 

これが機能する理由は、いつでもゲーム全体の状態が 2 匹のアクティブなポケモンとその残りのキューによって完全に記述されるためです。 すべての遷移はマルコフ関数です。将来の結果は現在の状態にのみ依存し、その状態にどのように到達したかには依存しません。 各アクションはこの状態を決定的に更新するため、段階的にシミュレーションすると正確さが保たれます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, K = map(int, input().split())

    A = []
    for _ in range(n):
        h, a, b, c, d, e, w = map(int, input().split())
        A.append([h, a, b, c, d, e, w])

    B = []
    for _ in range(m):
        h, a, b, c, d, e, w = map(int, input().split())
        B.append([h, a, b, c, d, e, w])

    i = j = 0
    a_hp, a_en = A[0][0], 0
    b_hp, b_en = B[0][0], 0

    def best(att, defn, en):
        Aatk, Batk, Cdef, Ddef, Ecost, W = att[1], att[2], att[3], att[4], att[5], att[6]
        phys = max(0, Aatk - defn[3])
        mag = max(0, Batk - defn[4])
        ult = W if en >= Ecost else -1
        if phys >= mag and phys >= ult:
            return phys, 0
        if mag >= phys and mag >= ult:
            return mag, 1
        return ult, 2

    for round_id in range(K):
        if i >= n or j >= m:
            break

        dmg, typ = best(A[i], B[j], a_en)
        b_hp -= dmg
        if typ == 0 or typ == 1:
            a_en += 1
        else:
            a_en -= A[i][5]

        if b_hp <= 0:
            j += 1
            if j < m:
                b_hp, b_en = B[j][0], 0
            else:
                break

        if i >= n or j >= m:
            break

        dmg, typ = best(B[j], A[i], b_en)
        a_hp -= dmg
        if typ == 0 or typ == 1:
            b_en += 1
        else:
            b_en -= B[j][5]

        if a_hp <= 0:
            i += 1
            if i < n:
                a_hp, a_en = A[i][0], 0
            else:
                break

    if i >= n and j >= m:
        print("Draw")
    elif j >= m:
        print("Alice")
    else:
        print("Bob")

if __name__ == "__main__":
    solve()
```この実装では、各チームの 2 つのポインターが維持され、アクティブな HP とエネルギーが明示的に維持されます。 の`best`関数は、現在の制約の下で 3 つの考えられるダメージ値をすべて比較する決定ルールをカプセル化します。 

微妙な点は、最終的な入手可能性はエネルギーに依存し、そうでない場合はマイナスのダメージで無効として扱われるため、決して選択されないことです。 タイブレークは、究極の比較の前に物理的および魔法的を順序付けることによって処理されます。 

シミュレーション ループは、K ラウンドのカットオフを尊重して、各ラウンド内でアリスとボブを交互に切り替えます。 

## 実用的な例

 両側に 1 匹のポケモンがいる小さなシナリオを考えてみましょう。 

アリスは、HP 10、物理 5、魔法 1、防御 0、エネルギーコスト 2、究極 10 のユニットを持っています。ボブは対称的なステータスを持っています。 

開始時には両方のエネルギーがゼロです。 

| ターン | 攻撃者 | 選択されたアクション | 前のエネルギー | ダメージ | その後のHP |
 | --- | --- | --- | --- | --- | --- |
 | 1 | アリス | 物理的な | 0 | 5 | ボブ5 |
 | 2 | ボブ | 物理的な | 0 | 5 | アリス5 |
 | 3 | アリス | 物理的な | 1 | 5 | ボブ0 |

 ボブが気を失った後、すぐにアリスが勝ちます。 

このトレースは、エネルギーの蓄積が後のターンに正しく影響を与えるが、初期の決定には影響を及ぼさないことを示しています。 

ここで、攻撃を繰り返した後にのみ究極が使用可能になり、最適な選択を強制的に切り替えるケースを考えてみましょう。 最終ダメージが高いがコストが高いユニットは、最初はエネルギー閾値に達するまで物理攻撃または魔法攻撃に依存します。その時点で、決定関数が支配的であれば決定関数が究極に移行します。

 ## 特殊なケース

 重大なエッジケースは、前のポケモンが気絶した後にポケモンが切り替わる場合です。 そのエネルギーはゼロにリセットされなければなりません。 エネルギーが誤って持ち越された場合、すぐにアルティメットを誤って使用し、ダメージが増大し、シミュレーションが中断される可能性があります。 

もう 1 つのエッジケースは、防御力が高いために物理と魔法の両方がダメージを与えない場合です。 この状況では、究極値が厳密にゼロより大きく、エネルギーによって許容される場合にのみ、依然として究極値が選択される可能性があります。 それ以外の場合、ゼロダメージターンを繰り返すとエネルギーが増加し、最終的には ult の使用が可能になります。 

最後のエッジケースは、ラウンドの途中で一方のチームがポケモンを使い果たした場合の早期終了です。 シミュレーションはボブのターンを続行するのではなく、ただちに停止する必要があります。そうしないと、無効なインデックスにアクセスし、結果が破損する可能性があります。
