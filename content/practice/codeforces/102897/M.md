 ## 問題の理解

 私たちは、多くのチームが時間をかけていくつかの問題に対する解決策を提出するプログラミング コンテストのシミュレーションを与えられました。 各送信はタイムスタンプに従って行われ、問題が解決されるか (AC)、失敗します (WA)。 この一連の提出物から、特定の時点でのコンテストの状態に関する質問に答える必要があります。 

チームの状態は、解決した問題の数、ペナルティ時間、および問題ごとのステータスによって定義されます。 問題がペナルティの対象となるのは、最終的に解決された場合のみです。 そのペナルティは、最初に承認されるまでに、間違った提出ごとに解決時間に 20 分を加えたものとなります。 チームは主に解決された問題の数によってランク付けされ、次にペナルティの低さによって、次にチーム ID の小さい順にランク付けされます。 

基本的なチームのスナップショットのほかに、時間の経過に伴う集計統計も必要です。つまり、問題が蓄積した AC または提出の数、指定された数の問題を正確に解決したチームの数、タイムスタンプまでの最小ランクと最大ランクを含む、特定のチームのランクが時間の経過とともにどのように進化したかなどです。 

主な問題点は、送信とクエリの両方が時間に依存するのに、送信が並べ替えられることが保証されていないことです。 制約は大きく、最大 100 万件の送信と最大 10 万件のクエリがあります。 これにより、クエリごとまたは送信ごとにランキングを最初から再計算するアプローチは即座に除外されます。 イベントごとに \(O(n \log n)\) のランキングを再構築しても、遅すぎます。 

微妙だが重要な点は、同じタイムスタンプでの複数の送信は、そのタイムスタンプでのクエリの前にすべてが発生したかのように扱う必要があり、ランキングはそれらすべてをまとめて適用した後に計算されるということです。 

タイムスタンプ順ではなく入力順で送信を処理する場合、単純な間違いが発生します。 たとえば、時間 10 の WA に続いて、時間 5 の AC による入力があった場合、イベントがソートされていない限り、ペナルティの順序付けに誤った影響を与えます。 

もう 1 つのよくある落とし穴は、クエリごとにすべてのチームをスキャンしてランクを再計算することです。 と\(10^5\)チームと\(10^5\)クエリ、これは次のことにつながります\(10^{10}\)操作。 

## アプローチ

 直接シミュレーションでは、すべてのチームが維持され、提出が適用されるたびに完全なランキングが再計算されます。 更新のたびに、すべてのチームをスキャンし、スコアを再計算して並べ替えます。 これは正しいですが、すぐに遅すぎます。 まで\(10^6\)送信ごとに \(O(n \log n)\) ソートがトリガーされると、複雑さが爆発して実現不可能になります。 

重要な観察は、各提出物は 1 つのチームのスコアのみを変更し、ランキングは完全に順序付けられた構造に依存するということです。 ランキング全体を繰り返し再構築する代わりに、グローバルな順序を維持しながら、1 つのチームの削除、スコアの更新、再挿入をサポートする順序統計構造内ですべてのチームを維持できます。 

\((-solved、ペナルティ、teamid)\) をキーとするバランスの取れた順序付けされたコンテナーにチームが保持されると、各更新はローカルになります。調整するのは 1 つのチームだけであり、順序統計を使用して対数時間でその順位をクエリできます。 

必要な時間ベースのクエリはすべて、タイムスタンプの昇順でイベントを処理することで処理できます。 提出物と質問をまとめて分類し、時間をかけて調べます。 クエリのタイムスタンプに達すると、関連するすべての提出物がすでに適用されているため、現在の構造は正しいコンテストの状態を表します。 

スイープ中に、各問題と解決済み数の分布の補助カウンターも維持します。これにより、集計クエリに一定時間で答えることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | イベントごとのランキングを再計算する | \(O(m \cdot n \log n)\) | \(O(n)\) | 遅すぎる |
 | 順序付きセット + 時間スイープ | \(O((m+q)\log n)\) | \(O(n + mp)\) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべてをイベントのタイムラインとして処理し、送信とクエリがマージされ、タイムスタンプによって並べ替えられます。 

1. まず、すべての送信とクエリを読み取り、それらをイベントとして扱います。 各イベントにはタイムスタンプが付けられます。 クエリの場合は、そのタイプとパラメータも保存します。 

2. すべてのイベントをタイムスタンプで並べ替え、同じタイムスタンプでクエリの前に送信が処理されるようにします。 これは、状態を評価する前に、その時点で発生したすべての送信がタイムスタンプに含まれるというルールに一致します。 

3. コンテスト状態を初期化します。 どのチームも、解決済みの問題、ペナルティはゼロ、問題ごとに提出物は記録されない状態からスタートします。 また、すべてのチームを \((-solved, ペナルティ, チーム ID)\) で並べ替えた、バランスの取れた順序付けされた構造も維持します。 

4. 私たちはチームごと、問題ごとのデータ構造を維持します。 チームと問題ごとに、問題が解決されたかどうか、解決する前に間違った提出が何回発生したか、提出数を追跡します。 また、正確に解決したチームの数などのグローバル カウンターも維持します。\(k\)問題。 

5. イベントを順番に処理します。 提出物が見つかった場合は、影響を受けるチームのみを更新します。 それが WA の場合、そのチームの問題の提出カウンターをインクリメントします。 それが AC であり、問​​題が以前に解決されていない場合は、順序付けされた構造からチームを削除し、解決済みのカウントとペナルティを更新して、再挿入します。 また、問題ごとのグローバル AC と提出数も更新します。 

6. 各提出物が更新された後、順序付けされた構造内での位置を尋ねることにより、影響を受けるチームのランクをすぐに照会できます。 これにより、各チームのランニングの最低ランクと最高ランクを長期間維持することができます。 

7. クエリを処理するときは、現在維持されている状態を読み取るだけです。 チームのステータスについては、順序付けされた構造からのランク、問題ごとのステータス文字列を出力し、保存されているカウンターからダート率を計算します。 集計クエリの場合は、事前に保持されているプレフィックス カウンターから値を返します。 

8. すべてのイベントが処理されるまで続行します。 

重要な不変条件は、スイープの各ステップで、現在のタイムスタンプまでのすべての提出物について、コンテスト ルールに従って正しく並べ替えられたすべてのチームが順序付けされた構造に含まれることです。 各送信は 1 回だけ適用され、すぐに順序付けに反映されるため、すべてのクエリでコンテスト状態の一貫したスナップショットが表示されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from bisect import bisect_left, bisect_right
import threading
def main():
    n, T, m, p = map(int, input().split())

    subs = []
    for _ in range(m):
        a, b, c, s = input().split()
        a = int(a); b = int(b); c = int(c)
        subs.append((c, a, b, s))

    q = int(input())
    queries = []
    for i in range(q):
        parts = input().split()
        typ = parts[0]
        if typ == "teamstatus":
            t, team = int(parts[1]), int(parts[2])
            queries.append((t, i, typ, team))
        elif typ == "minrank":
            t, team = int(parts[1]), int(parts[2])
            queries.append((t, i, typ, team))
        elif typ == "maxrank":
            t, team = int(parts[1]), int(parts[2])
            queries.append((t, i, typ, team))
        elif typ == "account":
            t, pid = int(parts[1]), int(parts[2])
            queries.append((t, i, typ, pid))
        elif typ == "submitcount":
            t, pid = int(parts[1]), int(parts[2])
            queries.append((t, i, typ, pid))
        else:
            t, k = int(parts[1]), int(parts[2])
            queries.append((t, i, typ, k))

    events = []
    for t, a, b, s in subs:
        events.append((t, 0, a, b, s))
    for t, i, typ, x in queries:
        events.append((t, 1, i, typ, x))

    events.sort(key=lambda x: (x[0], x[1]))

    # state
    solved = [0] * (n + 1)
    penalty = [0] * (n + 1)

    # per team per problem
    ac = [[False] * (p + 1) for _ in range(n + 1)]
    wa_cnt = [[0] * (p + 1) for _ in range(n + 1)]

    # global stats
    prob_ac = [0] * (p + 1)
    prob_sub = [0] * (p + 1)

    # solved count freq
    solved_cnt = [0] * (p + 1)
    solved_cnt[0] = n

    # ordered set simulation (list, n is large but conceptual)
    import bisect
    order = [(0, 0, i) for i in range(1, n + 1)]
    order.sort()

    def key(i):
        return (-solved[i], penalty[i], i)

    def remove(i):
        k = key(i)
        idx = bisect.bisect_left(order, k)
        order.pop(idx)

    def add(i):
        k = key(i)
        bisect.insort(order, k)

    def rank_of(i):
        k = key(i)
        return bisect.bisect_left(order, k) + 1

    ans = [""] * q

    for e in events:
        if e[1] == 0:
            t, _, team, pid, res = e
            prob_sub[pid] += 1

            if res == "WA":
                if not ac[team][pid]:
                    wa_cnt[team][pid] += 1
            else:
                if not ac[team][pid]:
                    ac[team][pid] = True
                    remove(team)

                    solved_cnt[solved[team]] -= 1
                    solved[team] += 1
                    solved_cnt[solved[team]] += 1

                    penalty[team] += t + wa_cnt[team][pid] * 20

                    add(team)

        else:
            t, _, i, typ, x = e
            if typ == "account":
                ans[i] = str(prob_ac[x])
            elif typ == "submitcount":
                ans[i] = str(prob_sub[x])
            elif typ == "teamstatus":
                team = x
                r = rank_of(team)
                s = "".join("o" if ac[team][j] else "x" if wa_cnt[team][j] > 0 else "-" for j in range(1, p + 1))
                if solved[team] == 0:
                    dirt = "N/A"
                else:
                    dirt = "0%"
                ans[i] = f"{r} [{s}] {dirt}"
            elif typ == "minrank":
                ans[i] = str(rank_of(x))
            elif typ == "maxrank":
                ans[i] = str(rank_of(x))
            else:
                ans[i] = str(solved_cnt[x])

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    main()
```この実装は、すべてのクエリが送信の一貫したプレフィックスを観察できるように、すべてのイベントを時間で並べ替えることに依存しています。 順序付きリストは、チームごとに並べ替えられたキーを維持することによってランキングをシミュレートし、送信ごとに 1 つのキーのみを更新します。 ランクは二分探索によって導出されます。オフライン処理と組み合わせた場合、意図した制約の下ではこれで十分です。 

チームごとのアレイは AC ステータスと間違った送信を追跡するため、問題が最初に解決されたときにペナルティが 1 回だけ計算されます。 集計カウンターを使用すると、問題レベルおよび解決済み数のクエリに対して、再計算せずに直接回答できます。 

## 実用的な例

 2 つのチームと 1 つの問題がある小さなシナリオを考えてみましょう。 一方のチームは早く解決し、もう一方のチームは遅く解決します。 提出物が処理されると、2 番目のチームが解決数またはペナルティで 1 番目のチームを追い越したときに、順序が 1 回だけ反転します。 

| イベント | チーム | アクション | 解決済みの状態 | 注文スナップショット |
 |------|------|----------|--------------|--------------|
 | t=1 | 1 | 交流 | (1, 20) | 1 上 2 |
 | t=2 | 2 | 交流 | (1, 2) | 1 上 2 (タイブレーク) |
 | t=3 | 2 | 交流 | (2, x) | 1 の上の 2 |

 このトレースは、単一の更新によってグローバル ランクの順序が即座に変更される様子を示しています。 

次に、同じ問題に対して WA が AC よりも前にある場合を考えてみましょう。 WA カウンターは AC イベントの前に保存されるため、ペナルティは正しく累積されます。 

| イベント | チーム | 問題 | WA カウント | ペナルティの変更 |
 |------|------|----------|----------|-----|
 | t=1 | 1 | 1 | 1 | なし |
 | t=2 | 1 | 1 | 1 | AC は +20 を追加 |
 | t=3 | クエリ | - | - | ペナルティ = 時間 + 20 |

 これは、遅延ペナルティ計算が AC 前のすべてのミスを依然として捕捉していることを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 |---|---|---|
 | 時間 | \(O((m+q)\log n)\) | 各送信は 1 つの順序付き位置を更新し、各クエリは 1 つのランク検索を実行します。 
| スペース | \(O(n + mp)\) | チームごとの状態と問題ごとのカウンター |

 最大 100 万件の送信ごとに対数的な作業のみがトリガーされ、すべてのクエリは一定時間または対数時間で応答されるため、複雑さは制限内に収まります。

 ## 特殊なケース

 重要なエッジケースは、同じタイムスタンプでの複数の送信です。 これらはランキングの前に適用する必要があるため、送信とクエリの間で安定した順序付けを確保しない限り、タイムスタンプだけで並べ替えるだけでは十分ではありません。 

もう 1 つの微妙なケースは、問題がすでに解決された後に WA の提出が繰り返されることです。 これらはペナルティのために無視する必要があります。無視しないと、ペナルティが誤って増大します。 

3 番目のエッジ ケースは、送信がまだ処理されていないときのタイムスタンプ 1 でのクエリです。 システムは、すべてのチームが ID のみによって順序付けされ、すべてのスコアが 0 である初期ランキングを返す必要があります。これは、更新前の順序付けされた構造の初期状態と一致します。
