 ## 解決策
 ## 問題の理解

 いくつかの独立した建物の説明が与えられます。 各建物は複数のフロアで構成されており、各フロアは文字列で表されます。 文字列内の文字は、位置にゴミが含まれているかどうか、およびゴミの種類を示します。 ドット文字は空の位置を表し、その他の文字はゴミ箱アイテムを表し、異なる文字は異なるゴミ箱タイプに対応します。 

フロアごとに、そのフロアに出現する個別のゴミの種類の数を数えるように求められます。 次に、建物内のすべてのフロアのこの値を合計します。 最後に、テスト ケースごとにこの合計を出力します。 

重要な点は、識別性がフロアごとに独立して測定されるということです。 同じ種類のゴミが複数のフロアに出現する場合、出現する各フロアに個別に寄与します。 フロアに同じキャラクターが複数存在する場合でも、そのフロアに寄与するのは 1 回だけです。 

この制約は、リニア スキャン ソリューションを意味します。 テスト ファイル内のすべてのフロアにわたる文字の合計数は、最大 10^7 です。 これにより、部分文字列の並べ替えや、クエリごとに大きなオーバーヘッドを伴うセットの再初期化の繰り返しなど、文字ごとに負荷のかかる構造が即座に除外されます。 一定時間の更新で各文字を基本的に 1 回処理するアプローチが必要です。 

微妙な失敗例は、ゴミの種類をフロアごとではなく建物全体で誤って集計した場合に発生します。 たとえば、次のことを考えてみましょう。 

1階:`a.a`2階:`aa.`正しい解釈:

 1階には`{a}`したがって、1に貢献します。 

2階にもあります`{a}`したがって、1に貢献します。 

答えは2です。 

間違ったグローバル セット アプローチでは、それを 1 つの型の合計として扱い、出力 1 を出力します。 

もう 1 つの微妙なケースは、同じフロアで文字が繰り返される場合です。 例えば：`####`これは 4 ではなく 1 に寄与するはずです。 

## アプローチ

 単純な解釈は、各フロアを独立して処理し、その文字列内のすべての非ドット文字のセットを構築し、そのサイズを答えに追加することです。 これは正しいです。セットにより、フロアごとのゴミのタイプの一意性が自然に強制されるからです。 

ただし、素朴な懸念はパフォーマンスです。 文字通り新しいセットを作成して各文字を挿入した場合でも、各文字に 1 回触れるだけなので、複雑さは合計入力サイズに比例します。 唯一の潜在的なオーバーヘッドはハッシュ セット操作ですが、Python では、これは合計 10^7 文字という制約の下ではまだ許容されます。 

繰り返しの割り当てや重いオブジェクトの作成を可能な限り回避することで、実装を改良できます。 各フロアの完全なセットを明示的に保存する代わりに、各文字タイプのブール マーカー配列または最後に表示されたタイムスタンプ配列を維持できます。 各フロアでは、使用したマーカーのみをリセットすることで、大きな建造物のクリアを回避します。 

重要な点は、キャラクターが「どのフロア」で使用されたかを知る必要はなく、そのキャラクターが現在のフロアに登場したかどうかだけを知る必要があるということです。 したがって、O(1) マーキング操作でフロアごとに表示された文字を追跡できます。

 ## アルゴリズムのチュートリアル

 1. テストケースの数を読み取ります。 各テスト ケースは独立しているため、それぞれのテスト ケースに対して累積された回答をリセットします。 
2. テスト ケースごとに、グローバル構造を初期化します。`seen`これは、キャラクターが現在のフロアですでにカウントされているかどうかを記録します。 これは、制約に応じて辞書または配列になります。 
3. 各フロア文字列を繰り返します。 新しいフロアを処理する前に、そのフロアに関連する状態のみをクリアまたはリセットしてください。 重要な要件は、前のフロアからの情報が現在のフロアに漏洩しないことです。 
4. 文字列を 1 文字ずつスキャンします。 文字がドットの場合は、ゴミを表すものではないので、すぐにスキップしてください。 
5. ドット以外の文字については、このフロアに対してすでにカウントされているかどうかを確認します。 そうでない場合は、それを既知としてマークし、フロアの貢献度を 1 増やします。これにより、各ゴミタイプがフロアごとに最大 1 回貢献することが保証されます。 
6. フロアを終了したら、そのフロアの貢献度を合計回答に追加します。 
7. 次の階に移動して繰り返します。 

### なぜ効果があるのか

 各フロアは独立したユニバースとして扱われ、ドット以外の文字の中で個別のシンボルがカウントされます。 マーキング構造により、各シンボルがフロアごとに 1 回カウントされることが保証され、フロア間のリセットにより独立性が保証されます。 すべての文字は 1 回だけ処理され、最大 1 つの増分に寄与するため、最終的な合計は「フロアごとの個別のゴミタイプの合計」の定義と正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        n = int(input())
        total = 0
        
        seen = set()
        
        for _ in range(n):
            s = input().strip()
            seen.clear()
            cnt = 0
            
            for ch in s:
                if ch == '.':
                    continue
                if ch not in seen:
                    seen.add(ch)
                    cnt += 1
            
            total += cnt
        
        print(total)

if __name__ == "__main__":
    solve()
```このソリューションは各テスト ケースを個別に処理し、フロアごとに回答を蓄積します。 の`seen`セットはフロアごとに片づけられるため、ゴミの種類がフロアを越えて汚染されることはありません。 各文字は 1 回チェックされ、Python セットへの挿入により、償却定数時間での一意性追跡が保証されます。 

よくある落とし穴はクリアを忘れることです`seen`これにより、異なるフロア間でゴミの種類が誤ってマージされ、カウントが増大します。

 ## 特殊なケース

 エッジ ケースの 1 つは、たとえば、ドットのみの床です。`"....."`。 アルゴリズムがクリアされる`seen`、各文字をスキャンし、有効なゴミを見つけず、貢献度は 0 です。セットは空のままで、貢献度は正確にゼロです。 

もう 1 つのエッジ ケースは、同じ文字で構成される非常に長い単一フロアの入力です。`"aaaaaaaa..."`。 最初のオカレンスが挿入されます`seen`、後続の文字はすべて無視され、長さに関係なく寄与度は 1 になります。 

3 番目のケースは、次のような重複するシンボルを持つ交互のフロアです。```
a.b
b.a
```1階には、`seen`になる`{a, b}`2階に、`seen`はクリアされ、次のように再計算されます`{a, b}`、再び2を貢献しました。 リセットによりキャリーオーバーがなく、フロア間で正確さが維持されます。
