 ## 解決策
 ## 問題の理解

 開始年と整数シフトが与えられます。 シフトは年に適用されますが、結果は直接使用されません。 代わりに、結果として得られる年の上限 9999 を超える部分は、問題で説明されている特定の方法で削除され、最終的に調整された年間隔が生成されます。 最後のタスクは、その間隔内に閏年が何年あるかをカウントすることです。 

うるう年は標準のグレゴリオ暦に従います。 年が 400 で割り切れる場合、または 4 で割り切れるが 100 では割り切れない場合、その年は閏となります。 

各テスト ケースは独立しています。 それぞれについて、「オーバーフロー折りたたみによる 9999 での上限」ルールを適用した後、最終間隔を再構築し、その間隔内の閏年をカウントする必要があります。 

制約は精神的には小さく、テスト ケースは最大でも約 100 件で、関係するすべての年は 1 ～ 9999 の範囲に戻されるまで最悪でも数万以内に収まります。 これにより、前処理を行わずにクエリごとに大きな範囲にわたって閏ステータスを年ごとに再計算するようなことは即座に除外されます。 ドメインが最大 9999 までしかないため、テスト ケースごとの単純な年ごとのスキャンはまだ問題ありませんが、O(100 × 10000) よりも漸近的に悪いものは依然として快適に通過しますが、構造のないダイナミック レンジにわたる繰り返しの再計算のようなものは不必要なオーバーヘッドになります。 

微妙な点は、オーバーフロー年の「折り畳み」です。 シフトされた年が 9999 を超える場合、9999 を超えた部分は単に無視されるわけではありません。 代わりに、9999 か​​ら減算されて最終エンドポイントが形成されます。 これにより、9999 付近に対称的な反射のような効果が作成され、単純なクリッピングと誤読されやすくなります。 

よくある間違いは、最終間隔を常に [Y, Y + A] が [1, 9999] にクリップされたものとして扱うことです。 加算が 9999 を超えると、オーバーフローがエンドポイントの削減に寄与するため、これは失敗します。 

もう 1 つのエッジ ケースは負の A です。間隔の方向が反転する可能性があるため、エンドポイントを慎重に正規化する必要があります。 たとえば、Y = 10 および A = -20 の場合、単純な終点は -10 となり、これは無効ですが、この問題により、調整後の最終建設年数が正になることが保証されます。 それでも、常にソートされた間隔でカウントするようにする必要があります。 

## アプローチ

 ブルート フォース ソリューションでは、最初に説明どおりに変換を正確にシミュレートして、最終的な間隔のエンドポイント L と R を取得します。間隔を取得したら、L から R まで毎年単純に反復し、割り算ルールを使用して各年が閏年であるかどうかを確認します。 

これは、リープ チェックが O(1) であり、最大間隔の長さが 9999 によって制限されているため機能します。最悪のケースでは、各クエリはほぼ 10000 年をスキャンし、すべてのテスト ケースにわたって約 10^6 のチェックが行われますが、これは簡単です。 

ただし、これでも、毎年独立してモジュール チェックが繰り返し実行されます。 問題の構造は、より良いアプローチを示唆しています。閏年は、周期 400 の周期的なパターンに従います。各年を個別にチェックする代わりに、9999 年までの閏年の接頭辞数を事前計算し、区間再構成後に O(1) で各クエリに答えることができます。 

重要なアイデアは、カウントの問題を、各位置が閏年かどうかを示す静的バイナリ配列に対する範囲合計クエリに変換できるということです。 プレフィックス合計配列を一度構築すると、各クエリは 2 つのプレフィックス値の減算に減ります。 

これにより、問題は単純な間隔の再構成と定数時間のクエリに変わります。

 ## アルゴリズムのチュートリアル

 まず、1 から 9999 までのすべての年を前処理し、閏年であることをマークします。 これから、プレフィックス合計配列を構築します。 

1. 配列を計算する`is_leap[i]`うるう年のルールを使用して、1 から 9999 までのすべての年を対象とします。 
2. 構築する`pref[i]`どこ`pref[i] = pref[i-1] + is_leap[i]`。 i 年までに閏年が何年存在するかを格納します。 
3. 各テスト ケースについて、Y と A を読み取り、生のエンドポイントを計算します。`X = Y + A`。 
4. X ≤ 9999 の場合、必要に応じてエンドポイントを並べ替えた後、間隔は単純に [Y, X] になります。 
5. X > 9999 の場合、オーバーフローを計算します`excess = X - 9999`エンドポイントを次のように設定します`R = 9999 - excess`。 
6. 最後の間隔は 2 つのエンドポイントの間であるため、次のように設定します。`L = min(Y, R)`そして`R = max(Y, R)`。 
7. 出力`pref[R] - pref[L-1]`。 

重要な推論ステップは、オーバーフローが発生した場合でも、変換によって常に [1, 9999] 内に有効なエンドポイントが生成されるため、正規化後の間隔は常に適切に定義されるということです。 

### なぜ効果があるのか

 プレフィックス合計配列は、固定の順序付けされたドメインにわたる加算測度をエンコードします。 うるう年の条件はクエリから独立しており、年の値のみに依存するため、安全に一度だけ事前計算することができます。 すべてのクエリは、ある期間にわたる関数の合計を求めることになり、プレフィックスの差がその合計を正確に表します。 この問題の唯一の動的な部分は、間隔のエンドポイントを決定することであり、それらが正しければ、カウントは純粋に算術的になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXY = 10000

def is_leap(y: int) -> int:
    if y % 400 == 0:
        return 1
    if y % 100 == 0:
        return 0
    if y % 4 == 0:
        return 1
    return 0

# precompute prefix of leap years
pref = [0] * (MAXY)
for i in range(1, 10000):
    pref[i] = pref[i - 1] + is_leap(i)

def solve():
    T = int(input())
    out = []
    for _ in range(T):
        Y, A = map(int, input().split())
        X = Y + A

        if X <= 9999:
            L, R = Y, X
        else:
            excess = X - 9999
            R = 9999 - excess
            L = Y

        if L > R:
            L, R = R, L

        if L < 1:
            L = 1
        if R > 9999:
            R = 9999

        out.append(str(pref[R] - pref[L - 1] if L > 1 else pref[R]))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```コードは、うるう年の直接インジケーターを構築することから始まり、次にその情報をプレフィックス合計配列に圧縮します。 各クエリは、カスタム オーバーフロー ルールからのエンドポイントの計算に還元され、その後、プレフィックス配列で定数時間の減算が行われます。 

順序の処理はデリケートな部分です。調整されたエンドポイントが開始年より大きいか小さいかに応じて、間隔のエンドポイントが入れ替わる可能性があります。 並べ替えると、ケースを分けなくても正確さが保証されます。 

もう 1 つの微妙な点は、プレフィックス配列のインデックス付けです。 1 ベースの年を使用するため、pref[0] はニュートラルベースとして機能するため、1 年から始まるクエリでは pref[-1] へのアクセスを回避する必要があります。 

## 実用的な例

 2 つの例を考えてみましょう。 

まず、Y = 9997 および A = 3 です。生のエンドポイントは 10000 で、9999 を超えています。オーバーフローは 1 であるため、反映されたエンドポイントは 9998 になります。間隔は [9997, 9998] です。 

| ステップ | や | あ | X | 過剰 | R | Ｌ |
 | --- | --- | --- | --- | --- | --- | --- |
 | イニシャル | 9997 | 3 | - | - | - | - |
 | 計算する | - | - | 10000 | 1 | 9998 | 9997 |
 | 最終間隔 | - | - | - | - | 9998 | 9997 |

 これにより、オーバーフローによって切り捨てられるのではなく、上限のエンドポイントが減少することが確認されます。 

2 番目は、Y = 9999 および A = -3 です。 生のエンドポイントは 9996 であり、範囲内に収まるため、間隔は [9999, 9996] となり、[9996, 9999] に並べ替えられます。 

| ステップ | や | あ | X | 過剰 | R | Ｌ |
 | --- | --- | --- | --- | --- | --- | --- |
 | イニシャル | 9999 | -3 | - | - | - | - |
 | 計算する | - | - | 9996 | 0 | 9996 | 9999 |
 | 最終間隔 | - | - | - | - | 9996 | 9999 |

 これは、オーバーフローが発生していない場合でも並べ替えが必要な理由を示しています。

 ## 特殊なケース

 エッジ ケースの 1 つは、オーバーフローにより変換後に間隔が崩壊する場合です。 たとえば、Y = 9999 および A = 1 の場合、X = 10000、超過 = 1 となるため、R = 9998 となります。間隔は [9999, 9998] となり、並べ替え後は [9998, 9999] になります。 このアルゴリズムは、L > R の場合にエンドポイントを明示的に交換することでこれを処理し、プレフィックス配列をクエリする前に有効性を保証します。 

もう 1 つのケースは、正規化後に下限が 1 になる場合です。 プレフィックス合計は pref[L-1] へのアクセスに依存しているため、実装では L = 1 を個別に扱い、負のインデックス付けを回避することでこれを保護しています。
