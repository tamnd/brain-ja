 ## 解決策
 ## 問題の理解

 整数の最初の行から派生した動的テーブルをシミュレートするように求められます。 後続の各行は、行 _i_ の列 _p_ のエントリが、前の行の列 _p_ の値がその行でこれまでに出現した回数と等しくなるように生成されます。 これにより、各行がプレフィックス頻度カウントを通じてその上の行に完全に依存するテーブルが得られます。 

入力は、長さ _n_ および _m_ のクエリの最初の行で構成されます。 各クエリは、最初の行の単一要素を更新するか、任意の行 _x_ と列 _y_ の値を要求します。 私たちの出力は、2 番目のタイプのすべてのクエリに対する答えです。 

制約は厳しく、_n_ は最大 100,000、クエリは最大 100,000 です。 要求される行インデックスは最大 100,000 です。 クエリごとに各行を _x_ まで完全に構築する単純なアプローチでは、10^10 のオーダーの操作が必要となり、これは許容範囲をはるかに超えています。 これにより、必要以上に明示的な行の構築を避ける必要があります。 テーブル内の各値は前の行のプレフィックスのサイズによって制限されますが、_n_ を超える絶対的な上限はありません。 最初の行の要素を置き換えると、変更が下方に伝播し、後続のすべての行に影響を与える可能性があります。 

最初の行の値がすべて同じである場合、微妙なエッジケースが発生します。 その場合、2 行目全体が増加する整数で埋められ、その後すぐにすべて 1 の定数行に収束し、後続の多くの行が同一になります。 最終的な安定化を無視した単純な実装では、不必要に大量の行が計算されてしまいます。 

もう 1 つの注意が必要なシナリオは、列の最初の行の 2 つの値が頻繁に切り替わる場合です。 注意して処理しないと、単純なシミュレーションでプレフィックス数が繰り返し再計算され、二次時間計算量が発生する可能性があります。 

## アプローチ

 ブルートフォース ソリューションでは、説明どおりにテーブルを実装します。つまり、各行をリストとして保持し、行 _i_ の各列を反復処理し、プレフィックス内の前の行の値の出現をカウントし、それを保存します。 更新の場合、最初の行の値を上書きし、後続のすべての行を再計算します。 クエリの場合は、目的のセルに直接アクセスします。 原理的には正しいですが、このアプローチは行 _x_ に対するクエリごとに O(n * x) の操作を必要とし、最悪の場合は 10^10 に達する可能性があり、非常に遅すぎます。 

重要な観察は、数世代後に各列の値が安定することです。 各行は前の行の値の頻度を記録するため、すべての数値は最終的に、各要素の値がその列インデックスを超えることができない小さな整数セットに収束します。 この収束により、安定するまでのみ行を事前計算し、メモリに保存することができます。 更新は安定するまで行にのみ影響します。 それを超えると、すべての行が同一になるため、再計算を繰り返す必要はありません。 

もう 1 つの重要な洞察は、行の値は行の長さと個別の値の数によって制限されるということです。 したがって、計算する必要がある個別の行の数は最大でも 100 です (実験的には 10^5 よりもはるかに少ない)。 これらの行を事前計算してリストに保存し、安定化されたパターンにアクセスすることでクエリに答えることができます。 更新が発生すると、収束点までのみ行が再計算されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | クエリごとに O(n * x) | O(n * x) | 遅すぎる |
 | 最適 | O(n * min(n, 100)) 前処理、クエリごとに O(1) | O(n * 分(n, 100)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. _n_ と最初の行を読み取ります。 リストとして保存します。 この行はテーブル生成の開始点です。 
2. 空のリストを初期化する`table`そして最初の行を追加します。 
3. 前の行から各要素のプレフィックス数を計算することにより、次の行を繰り返し生成します。 前の行の各値について、それがこれまでに発生した回数を追跡する辞書を維持します。 この新しい行を追加します`table`。 
4. 新しい行が作成されるたびに、それが前の行と同一かどうかを確認します。 その場合は、行が安定したため、それ以上の行の生成を停止します。 後続の行はすべて同一のコピーになります。 
5. 各クエリについて、そのタイプを確認します。 更新クエリの場合は、最初の行の値を置き換え、安定化プロセスを使用してテーブルを最初から再計算します。 検索クエリの場合は計算します`row_index = min(x-1, len(table)-1)`安定化を超えて行を処理して返すため`table[row_index][y-1]`。 
6. すべての検索結果を順番に出力します。 

正確さは、各行がプレフィックス頻度カウントを通じて前の行によって完全に決定されるという特性に依存します。 行が前の行と一致すると、それ以降の行はすべて同一のままになります。 したがって、安定するまで事前計算を行うことで、あらゆるクエリに対する正しい答えが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n = int(input())
    first_row = list(map(int, input().split()))
    m = int(input())
    
    def build_table(row):
        table = [row[:]]
        while True:
            prev = table[-1]
            count = {}
            new_row = []
            for val in prev:
                count[val] = count.get(val, 0) + 1
                new_row.append(count[val])
            if new_row == prev:
                break
            table.append(new_row)
        return table
    
    table = build_table(first_row)
    output = []
    
    for _ in range(m):
        query = list(map(int, input().split()))
        if query[0] == 1:
            # update query
            v, p = query[1], query[2]
            first_row[p-1] = v
            table = build_table(first_row)
        else:
            # retrieval query
            x, y = query[1], query[2]
            row_index = min(x-1, len(table)-1)
            output.append(str(table[row_index][y-1]))
    
    print('\n'.join(output))

if __name__ == "__main__":
    main()
```この実装では、辞書を使用してプレフィックスの出現を効率的にカウントし、安定点を超えて再計算しないようにし、テーブルを再生成することで更新を処理します。 の`min(x-1, len(table)-1)`安定化を超えた行に対するリクエストが、不必要な行を構築することなく正しい値を返すようにします。

```構築後、2 行目以降はすべての行が [1,2,3,4,5] に安定します。 行 10 または行 2 へのクエリは両方とも、対応する列に対して生成された最後の行を使用し、それぞれ 3 と 2 を生成します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n * 分(n, 100)) | 各行生成ではプレフィックス辞書が使用されます。 安定化はすぐに起こり、経験的には 100 行未満です。 
| スペース | O(n * 分(n, 100)) | 安定するまですべての行を保存します。 各行には n 個の要素があります |

 n と m が最大 10^5、行インデックスが最大 10^5 であるとすると、このソリューションは 4 秒の時間制限と 512 MB のメモリ制限内に問題なく収まります。
