 ## 解決策
 ## 問題の理解

 私たちにはスパルタ人のグループが与えられており、それぞれが忠誠心と呼ばれる一定の強さを持っています。 また、それぞれの強さの値を持ついくつかの敵の分隊も与えられます。 

2 つの条件が満たされる場合、単一のスパルタン分隊を使用して 1 つの敵分隊を倒すことができます。 まず、その分隊内のすべてのスパルタ人は、敵の強さを超える忠誠心を厳密に持たなければなりません。 第二に、その分隊に割り当てられるスパルタンの数は、少なくとも敵の戦力値と等しくなければなりません。 分隊が戦闘すると、その分隊内のすべてのスパルタンは消費され、再利用することはできません。 

課題は、一部またはすべてのスパルタンをばらばらの分隊に分割して、すべての敵分隊を 1 回だけ正確に倒すことができるかどうかを決定することです。 

重要な点は、各敵が 2 つの制約を同時に課すことです。つまり、必要な分隊の最小サイズと、その分隊の各メンバーに対する最小忠誠度のしきい値です。 

制約はテストごとに最大 100,000 人のスパルタンと 100,000 人の敵に達し、テスト全体の合計は 100,000 になります。 これにより、考えられるすべてのグループ化をシミュレートしたり、サブセットを繰り返し検索しようとするソリューションは直ちに除外されます。 合計入力サイズが 2 次のものは時間内に終了しません。 ソリューションは基本的に、順序付けられた構造をソートまたは維持し、操作ごとに対数時間で要素を処理する必要があります。 

よくある落とし穴は、グローバルなリソースの消費を考慮せずに、各敵を有効なサブセットと貪欲に一致させることができると想定することです。 もう 1 つの微妙な問題は、より厳しい忠誠度の基準を満たすために最初に必要になる可能性があるため、より強力なスパルタを早期に消費することが常に良いとは限らないことです。 

ナイーブな貪欲マッチングの具体的な失敗例は、高い強度のスパルタンが弱い敵に浪費され、後でより強力な制約に使用できる十分な強度のスパルタンが少なすぎる場合に現れます。 たとえば、最初に最も強力なスパルタンを小さな敵に割り当てた場合、有効なグローバル割り当てが存在していても、後で大きなしきい値の敵を満足させることができない可能性があります。 

## アプローチ

 強引な解釈では、分隊を明示的に構築しようとします。 敵ごとに、残っているすべてのスパルタ人をスキャンし、十分な忠誠心を持つ人たちをフィルタリングして、十分な人数を選びます。 すべての敵についてスパルタ リスト全体をスキャンする可能性があるため、これには最悪の場合でもすでに O(NM) のコストがかかります。 N と M が最大 100,000 であるため、これは実現可能な限界をはるかに超えています。 

重要な観察は、スパルタンの個々のアイデンティティは重要ではなく、忠誠度の値と、それらがまだ使用されているかどうかだけが重要であるということです。 各敵は、未使用のスパルタンがそのしきい値を超えた数だけを気にします。 これにより、問題は、しきい値制約の下でマルチセットの要素を繰り返しチェックして消費するという問題に軽減されます。 

これは当然、ロイヤルティ値に対する並べ替えまたは頻度構造を示唆しています。 すべてのスパルタンを秩序ある構造に維持し、強さの降順に敵を処理することができます。 最初に強い敵を処理する場合、弱い制約によって消費される前に、忠実度の高いスパルタを厳格な要件に合わせて確保します。 

敵を強さの降順に並べ替えると、各ステップで同様の質問が行われます。現在未使用のスパルタン全員の中で、現在の敵の強さよりも高い忠誠心を持っている人は何人いますか? そのうちの何人を削除できるでしょうか?

 カウントと削除の両方を効率的にサポートするために、圧縮されたロイヤルティ値に対してフェンウィック ツリーを使用します。 これにより、しきい値を超えている Spartan の数をクエリしたり、割り当てられた特定の Spartan を削除したりすることができます。 除去戦略は恣意的である必要はありませんが、最初に最小の有効な忠誠度を選択することで、後のステージのためにより強力なスパルタンを確実に保存することができます。ただし、カウントが一貫している限り、正確さはこの詳細には依存しません。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NM) | O(N) | 遅すぎる |
 | フェンウィック ツリー 貪欲 | O((N + M) log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### 1. すべての敵を強さの降順に並べ替えます

 高しきい値の要件に必要な Spartan を誤って消費しないように、最も強力な制約を最初に処理します。 

### 2. スパルタの忠誠心を調整圧縮する

 ロイヤルティ値は最大 10^9 になる可能性があるため、フェンウィック ツリーを使用できるように、それらをソートされたインデックス空間に圧縮します。 

### 3. Spartan カウント上にフェンウィック ツリーを構築する

 各ポジションには、その忠誠値を持つ未使用のスパルタンの数が保存されます。 

### 4. 降順で敵ごとに

 私たちは、敵の強さを厳密に上回る忠誠心を現在満たしているスパルタンの数を計算します。 これは、フェンウィック ツリーに対するサフィックス合計クエリです。 

この数値が敵の戦力より小さい場合、割り当ては不可能であると即座に結論付けます。 

### 5. 十分なスパルタンが存在する場合は、それらを割り当てます

 正確に B_i を削除するまで、有効なサフィックスから Spartan を繰り返し削除します。 

各削除は、しきい値を超える利用可能なロイヤルティ インデックスの最小値を見つけて、フェンウィック ツリー内のそのカウントを減らすことによって行われます。 

各ステップで利用可能な最小の有効な Spartan を選択すると、忠誠度の高い Spartan の無駄が回避されますが、有効なセット内の一貫した削除戦略により正確さが維持されます。 

### 6. すべての敵が正常に処理された場合

 要件を満たさない敵がいない場合、有効なパーティションが存在します。 

### なぜ効果があるのか

 降順で敵を処理することで、一度閾値を超えてしまえば、それ以降のステップでは、すでに処理したものよりも厳しい忠誠心が必要とされなくなります。 フェンウィック ツリーは、未使用の Spartan のセットを常に正確に表すという不変条件を維持します。 各ステップで、十分なロイヤルティを持つ現在利用可能な Spartan のみを使用して、現在の要件が満たされることを確認します。 すべての Spartan は最大 1 回削除され、すべての削除が構造内で考慮されるため、隠れた再利用や二重カウントが発生することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        if r < l:
            return 0
        return self.sum(r) - self.sum(l - 1)

    def find_first(self, l):
        lo, hi = l, self.n
        ans = -1
        while lo <= hi:
            mid = (lo + hi) // 2
            if self.range_sum(l, mid) > 0:
                ans = mid
                hi = mid - 1
            else:
                lo = mid + 1
        return ans

def solve():
    T = int(input())
    for _ in range(T):
        N = int(input())
        A = list(map(int, input().split()))
        M = int(input())
        B = list(map(int, input().split()))

        A.sort()
        B.sort(reverse=True)

        # coordinate compression
        vals = sorted(set(A))
        idx = {v: i + 1 for i, v in enumerate(vals)}

        fw = Fenwick(len(vals))

        for a in A:
            fw.add(idx[a], 1)

        ok = True

        for b in B:
            # count available A > b
            import bisect
            pos = bisect.bisect_right(vals, b)
            total = fw.range_sum(pos + 1, len(vals))

            if total < b:
                ok = False
                break

            need = b
            while need > 0:
                p = fw.find_first(pos + 1)
                fw.add(p, -1)
                need -= 1

        print("Yes" if ok else "No")

if __name__ == "__main__":
    solve()
```このソリューションでは、まずロイヤルティ値を圧縮して、フェンウィック ツリーで管理できるようにします。 ツリーは、未使用の Spartan の数を維持します。 敵ごとに、忠誠心が敵の強さを超える最初のインデックスを特定し、そのサフィックスに十分なスパルタンが残っているかどうかを確認します。 そうでない場合、構築は即座に失敗します。 

機能`find_first`は重要な部分です。Fenwick 構造に対してバイナリ検索を実行して、有効な範囲内で次に利用可能な Spartan を見つけます。 削除するたびにツリーが更新されるため、今後のクエリでは更新された状態が表示されます。 

微妙な点は、現在のフェンウィックの状態をキャッシュするのではなく、常に現在の状態から可用性を再計算することです。 これは、割り当てごとに Spartan が永久に削除され、将来の実現可能性が変化するため必要です。 

## 実用的な例

 ### 例 1

 入力:```
A = [1, 2, 4, 6, 9]
B = [3, 1]
```敵を降順に処理するため、最初は 3、次に 1 となります。 

| ステップ | 敵B | 対象となる A (>B) | 利用可能な数 | アクション | 残り |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 3 | [4、6、9] | 3 | 3を削除 | [1,2,4,6,9] → [1,2] |
 | 2 | 1 | [2,4,6,9] | 4 | 1を削除 | 有効 |

 すべての要件が満たされているため、出力は「はい」になります。 

このトレースは、強い要素を早期に消費しても、弱い制約に対して十分な容量が残っていることを示しています。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((N + M) log N) | 削除ごとのフェンウィック操作とバイナリ検索 |
 | スペース | O(N) | 圧縮値とフェンウィック ツリーのストレージ |

 フェンウィック作戦の総数はスパルタンの数と敵の要件に比例し、各作戦は個別の忠誠度の値の数において対数になります。 合計入力サイズの上限が 100,000 であるため、これは一般的な制限内に問題なく収まります。

 ## 特殊なケース

 重要なエッジケースは、すべてのスパルタ人がまったく同じ忠誠心を持っている場合です。 敵がその値と等しい厳密な不平等を要求する場合、スパルタンは資格を持ちません。 サフィックス クエリはそのしきい値に対して 0 を返すため、アルゴリズムはこれを正しく処理します。 

もう 1 つのケースは、小型の敵が処理される前に、1 人の非常に大きな敵がすべてのスパルタンを消費する場合です。 降順により、このようなことが起こったとしても、それが避けられないことが保証されます。なぜなら、有効な解決策であれば、最大の制約に対してもこれらの Spartan が必要になるからです。 

最後のケースは、十分な数のスパルタンが存在するものの、さまざまな忠誠値に分散している場合です。 フェンウィック ツリーでは、現在利用可能な有効な候補のみが常にカウントされるため、部分的な割り当てが誤って再利用されることはありません。
