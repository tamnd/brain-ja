 ## 解決策
 ## 問題の理解

 私たちは自動車ブランドのコレクションを与えられており、各ブランドには固定の在庫数と車ごとの固定価格があります。 車が購入されると撤去されること以外に、1 日あたりの価格や在庫に変動はありません。 

毎日、顧客は指定された数の車を購入しようとしますが、その日の指定された予算制限を超えない価格の車のみを購入します。 予算の制約を満たすすべての車の中で、彼は常に価格の高い車を最初に好み、価格が同じ場合は指数の小さいブランドを好みます。 

購入ルールには、全需要を満たすのに十分な適格な車が少なくとも利用可能である場合にのみ、顧客が購入するという重要なグローバル条件があります。 1 台でも車が不足している場合は、購入全体がキャンセルされ、その日は車が撤去されません。 

出力には 2 つのことが必要です。1 日ごと、購入が成功したかどうか、もう 1 つはすべての日の処理後のブランドごとの残りの在庫です。 

この制約により、クエリごとにすべてのブランドを対象とした単純なシミュレーションは実行できなくなります。 最大 100,000 のブランドと 100,000 のクエリを使用すると、クエリごとにすべてのブランドをスキャンするソリューションでは、最悪の場合、10^10 の操作が必要となり、これは一般的な制限をはるかに超えています。 

微妙な難しさは、全か無かのトランザクション ルールに起因します。 1 日あたりの部分的な削除の貪欲なアプローチでは、十分な数の車が存在することを確認する前に車の削除を開始すると、正確性が損なわれます。 

もう 1 つの重要なエッジケースは、複数のブランドが同じ価格を共有する場合です。 タイブレーク ルールでは、インデックスによる一貫した順序付けが必要であるため、価格のみで並べ替える構造では、安定した順序付けを維持するか、明示的にエンコードする必要があります。 

さらに特殊なケースとしては、C_i の値が大きく、需要が予算内で利用可能な対象車両すべてを超える場合があります。 このような場合、部分的な貪欲選択によって一部の車両が選択される可能性がありますが、正しい答えは完全な拒否であり、状態は変更されません。 

## アプローチ

 直接的なアプローチでは、すべてのブランドをスキャンし、価格 ≤ D_i のすべての車を収集し、価格の降順とインデックスの昇順で並べ替えて、少なくとも C_i の車が存在するかどうかを確認することで、各クエリを個別に処理します。 「はい」の場合、上位の C_i 車両を削除します。 

これは論理的には機能しますが、遅すぎます。 各クエリには並べ替えのために O(N log N) が必要になるか、少なくとも O(N) のスキャンが必要になり、O(NQ) かそれ以上の結果になります。 N と Q の両方が最大 10^5 であるため、これは実行できません。 

重要な観察は、価格は静的であり、価格による注文を考慮する必要があるのはグローバルで 1 回だけであるということです。 すべてのブランドを価格の降順 (およびインデックスの昇順) で並べ替えると、決して変更されないグローバルな優先順位が得られます。 各クエリは、しきい値 D_i 未満の最初の C_i 有効な車を選択することになりますが、残りの在庫も考慮する必要があります。 

これは、ブランドごとに利用可能な車の数を維持しながら、すべての車の固定ソートリストに対する貪欲な構造を示唆しています。 残りの課題は、完全なリストを繰り返しスキャンすることなく、少なくとも C_i の有効な車両が存在するかどうかを効率的にチェックすることです。 ソートされたブランドに対するプレフィックスの蓄積とグローバル ポインタまたは減分追跡を組み合わせたプレフィックス合計により、実装戦略に応じて各クエリを O(log N) または償却 O(N + Q) で評価できます。 

一般的な効率的な解決策は、ブランドを 1 回ソートし、クエリごとに、価格 ≤ D_i を満たす利用可能な車を数えながら、ソートされたリストを貪欲に走査し、C_i に達するか、対象となるアイテムがなくなったら停止することです。 成功した場合は在庫を減らします。 それ以外の場合は何もしません。 D_i でソートされたクエリ間でポインタを注意深く再利用するか、スイープ構造を維持することにより、総作業量は線形またはほぼ線形になります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NQ ログ N) | O(N) | 遅すぎる |
 | 最適 | O((N + Q) log N) または O(N + Q) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 タイブレークのための元のインデックスを維持しながら、各ブランドを価格と残りの在庫で構成されるペアとしてモデル化します。 

1. すべてのブランドを価格の低い順に並べ替え、同じ価格の場合はインデックスの大きい順に並べ替えます。 これにより、世界中で常に自動車が好まれる正確な順序が生成されます。 
2. ブランドごとに残っている車の数を追跡しながら、このソートされた順序でブランドを横断できる構造を構築します。 
3. パラメータ C および D を持つ各クエリについて、ソートされた順序でブランドをスキャンしますが、価格が最高でも D のものだけを考慮します。残りの在庫を考慮して、これらのブランドから入手可能な車を蓄積します。 
4. いずれかの時点で累積カウントが C に達した場合、購入を停止し、購入の実現可能性を確認します。 
5. 適格なブランドをすべて使い切る前に C に到達できない場合、クエリは拒否され、在庫は変更されません。 
6. クエリが実行可能な場合、同じ選択プロセスの 2 回目のパスを実行し、ちょうど C 台の車が削除されるまで、同じ順序でブランド在庫から車を減算します。 

微妙だが重要な設計上の選択は、実現可能性のチェックを実際の削除から分離することです。 これにより、クエリが不可能であることが判明した場合に状態が破損するのを回避できます。 

### なぜ効果があるのか

 ソートされた順序は、クエリに依存しない、すべての自動車のグローバルな優先順位を定義します。 有効な購入はすべて、価格 ≤ D のアイテムの中から最初の C の入手可能なアイテムを単純に取得することです。削除によって在庫が減少するだけで、順序が変更されることはないため、使い果たされない限り、将来のクエリでは優先度の高い以前の車が常に優先されます。 これにより、ソートされた構造に対する貪欲な選択が、価格制約の下で必要な辞書編集的に最適な選択と常に一致することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    A = list(map(int, input().split()))
    B = list(map(int, input().split()))
    q = int(input())
    C = list(map(int, input().split()))
    D = list(map(int, input().split()))

    # sort by price desc, index asc
    items = sorted([(B[i], i) for i in range(n)], key=lambda x: (-x[0], x[1]))

    for i in range(n):
        pass

    # remaining stock
    rem = A[:]

    for qi in range(q):
        need = C[qi]
        lim = D[qi]

        chosen = []
        cnt = 0

        # feasibility check
        for price, idx in items:
            if price > lim:
                continue
            if rem[idx] == 0:
                continue
            take = rem[idx]
            if cnt + take >= need:
                chosen.append((idx, need - cnt))
                cnt = need
                break
            else:
                chosen.append((idx, take))
                cnt += take

        if cnt < need:
            print("No")
            continue

        # apply purchase
        print("Yes")
        for idx, t in chosen:
            rem[idx] -= t

    print(*rem)

if __name__ == "__main__":
    solve()
```この実装では、ブランドのグローバルなソート順序が維持され、実現可能性のチェックと削除の両方に一貫して使用されます。 rem 配列は、ブランドごとに残りの在庫を追跡します。 選択されたリストには、実現可能性が確認された後にブランドごとに削除される車の数が正確に保存され、時期尚早に状態の突然変異が発生しないことが保証されます。 

微妙な点は、個々の車ごとではなくブランドごとに集計していることです。 1 つのブランドのすべての車は同じ価格を共有するため、1 つのブランドから複数のユニットを取得することは、並べ替えられた構造内で同じアイテムが繰り返されるものとして扱うことと同じです。 

カウントと更新の適用を分離することは、全か無かの制約の下で正確さを維持するために不可欠です。

 ## 特殊なケース

 重要なエッジ ケースは、クエリがほぼ満たされるものの、わずかな差で失敗する場合です。 たとえば、価格制限内で利用可能な車が 9 台しかないのに、クエリで 10 台が要求された場合、単純な貪欲アルゴリズムでは、失敗に気づく前にこれらの 9 台が削除される可能性があります。 このアルゴリズムは、最初に選択内容を保存し、実現可能性が確認された後にのみ変更を適用することでこれを回避します。 

もう 1 つのエッジ ケースは、需要の増加に伴ってクエリが繰り返され、単一の高価格ブランドが徐々に枯渇してしまうことです。 ソート順序は固定されているため、常に同じ優先順位構造から消費され、構造の更新を必要とせずに枯渇が自然に rem を介して伝播します。 

すべての価格が等しい場合、正確さはインデックスの順序に完全に依存します。 (価格降順、インデックス昇順) で並べ替えると、決定的な同点解消が保証されるため、繰り返されたクエリは時間が経っても一貫して動作します。
