 ## 解決策
 ## 問題の理解

 キャッシュは次の配列です`n`バイトアドレス。最初はゼロで埋められます。 私たちも持っています`m`独立したデータ部分。各部分はそれ自体がバイト配列です。 ロード操作では、部分全体がキャッシュの連続領域にコピーされ、そこにあったものはすべて置き換えられます。 インクリメント操作は、格納されたデータ部分内の連続する範囲を 256 を法として変更しますが、すでにキャッシュにロードされているコピーは変更されません。 印刷操作では、1 つのキャッシュ アドレスにある現在のバイトが要求されます。 元のステートメントでは、次のことが許可されます`5 * 10^5`キャッシュアドレス、データ部分、操作。すべてのデータ部分の合計の長さも最大です。`5 * 10^5`。 規定の制限時間は5秒です。 

これらの境界により、データ部分のすべてのバイトをコピーすることによる負荷のシミュレーションが除外されます。 一枚でも長さはあります`5 * 10^5`、ほぼすべてのデバイスに同じピースをロードできます。`5 * 10^5`操作。 それは最悪のケースを約`2.5 * 10^11`バイトの割り当て。 入力自体の読み取りとは別に、各操作が対数的に多くの構造ノードのみに触れることを必要とします。 

難しいのは、キャッシュ コピーがスナップショットであることです。 データピースの場合`[10, 20]`がロードされ、その後ピースが増分されても、キャッシュにはまだ次の内容が含まれています。`[10, 20]`、新しいバージョンではありません。 逆に、ロード前に実行されたインクリメントは、そのロード内で表示される必要があります。 データピース識別子のみをキャッシュ位置に格納する直接実装では、この区別が失われます。 

何かがロードされる前に、可能な限り最小のキャッシュを検討してください。```
1 1 2
1 0
2 1
2 1
```正しい出力は次のとおりです。```
0
0
```不注意な実装では、クエリされたすべての位置が最新のデータ部分に属していると想定し、結果を返す可能性があります。`0`間違った理由で、または初期化されていないデータ オフセットにアクセスしようとしました。 キャッシュは、以前のロードがないことを明示的に表す必要があります。 

2 番目のエッジ ケースは、ロード前の増分です。```
1 1 3
1 255
3 1 1 1
1 1 1
2 1
```出力は次のとおりです。```
0
```インクリメントにより、保存されているピースが次から変更されます。`255`に`0`、および後続のロード コピー`0`。 データを不変として扱うと、正しく印刷されません。`255`。 

逆の順序も同様に重要です。```
1 1 4
1 255
1 1 1
3 1 1 1
2 1
```出力は次のとおりです。```

```インクリメントはロード後に発生するため、キャッシュにすでに格納されているバイトを変更することはできません。 クエリに応答するときに現在のデータ部分を単に調べるだけのソリューションでは、誤って出力されます。`0`。 

最後に、重複する負荷はバイト単位で処理する必要があります。 例えば：```

## アプローチ

 ブルート フォース ソリューションは、キャッシュ アレイを直接維持します。 大量のピース`i`位置にある`p`すべてをループします`k_i`バイトを取得してキャッシュに書き込みます。 インクリメントは、要求された範囲をループし、データ部分の対応するバイトを変更します。 印刷は一定時間です。 これは、すべての操作のセマンティクスに正確に従っているため、正しいです。 

問題はロード操作です。 ある長さのデータが 1 つあるとします。`500000`、そしてもう一つは`499999`操作もその部分の負荷です。 ブルートフォース ソリューションのパフォーマンスは大まかです`500000 * 500000 = 2.5 * 10^11`バイト書き込み。 それは制限時間をはるかに超えています。 

最初の有益な観察は、キャッシュ クエリにはキャッシュ状態全体が必要ないということです。 必要なのは、どのロードがその特定のキャッシュ アドレスを最後に書き込んだのか、そしてロードされた部分のどのバイトがそのアドレスに対応するのかを知ることだけです。 すべての荷重をその操作番号を持つ範囲割り当てとして扱うことで、データをコピーせずにその荷重を見つけることができます。 

セグメント ツリーには、各キャッシュ位置に影響を与える最新のロード番号を保存できます。 範囲更新の場合、その負荷によって完全にカバーされるセグメント ツリー ノードに負荷番号を配置します。 ポイント クエリの場合は、リーフからルートまでをたどって、検出された最大の負荷数を取得します。 操作数は時間の経過とともに増加するため、最大数は正確にその位置をカバーした最後の荷重になります。 

増分を処理する 2 番目の観測があります。 クエリが特定のロードに関連付けられると、そのキャッシュ値はそのロードの実行時に固定されます。 その負荷が処理されるまで、値の計算を延期できます。 まずすべての操作をスキャンして、すべての印刷クエリを最後のロードに関連付けます。 次に、操作を再度スキャンします。 2 回目のスキャン中、データ部分には、元の実行の各時点でのバージョンが正確に含まれています。 負荷に達すると、その負荷に関連するすべてのクエリに即座に答えることができます。 

データ部分については、範囲増分とポイント クエリが必要です。 フェンウィックの木はまさにこの組み合わせを提供します。 差分配列をフェンウィック ツリーに保存し、次のように追加します。`+1`左側の端点と`-1`右エンドポイントの直後。 バイト位置のプレフィックスの合計は、そのバイトに影響を与える増分の数になります。 値はバイトであるため、これらのカウントはすべて 256 を法として減らすことができます。 

したがって、2 つの部分は独立しています。 セグメント ツリーは、「どのロードによってこのキャッシュ バイトが生成されたのか?」という時間的な質問に答えますが、フェンウィック ツリーは、「そのロードが発生したときのこのデータ バイトの値は何でしたか?」という歴史的な質問に答えます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(コピーされたバイトの合計) | O(n + 合計 k_i) | 遅すぎる、最大約 2.5 * 10^11 の書き込み |
 | 最適 | O(合計 k_i + q log n + q log S) | O(n + m + q + 合計 k_i) | 承認済み |

 ここ`S`はデータピースの最大長です。 最適なアプローチでは、ロードされたコピーがキャッシュ内に実体化されることはありません。 

## アルゴリズムのチュートリアル

 1. すべてのデータを読み取り、元のバイトを保持します。 1 つのグローバル バイト配列内の各部分にコンパクトな範囲を与えます。 また、すべての作品にフェンウィックの木の範囲を予約します。 すべてのピースの合計サイズは最大で`5 * 10^5`したがって、元のバイトをすべて保存するのは低コストです。 
2. すべて保存する`q`操作をすぐに実行するのではなく、 操作は 2 回必要です。1 回目は各キャッシュ クエリを所有するロードを検出するため、もう 1 回目はロード時にデータ部分のバージョンを再構築するためです。 
3. キャッシュ アドレス上にセグメント ツリーを作成します。 ロード操作ごとに`1 i p`、影響を受けるキャッシュ間隔は`[p, p + k_i - 1]`。 この間隔に完全に含まれるすべてのセグメント ツリー ノードに負荷の操作番号を保存します。 クエリではリーフのすべての祖先を単純に検査できるため、これらのタグを下にプッシュする必要はありません。 
4. 印刷操作ごとに`2 p`、キャッシュ位置から歩きます`p`セグメント ツリー ルートに向かって移動し、発生した最大のロード操作番号を見つけます。 そのような操作がない場合、キャッシュ アドレスは一度も書き込まれていないため、その答えは 0 です。 
5. ロード操作が見つかった場合は、そのデータ部分内の対応するオフセットを計算します。 ロードがキャッシュアドレスから開始される場合`s`、次にキャッシュアドレスをクエリします`p`データオフセットを指します`p - s + 1`。 この印刷クエリをそのロード操作にアタッチします。 そのバイト値はまだ計算していません。 
6. データごとに 1 つの概念的なフェンウィック ツリーを初期化します。 これらは、各部分に個別のベース オフセットを使用して、1 つのフラット バイト配列に格納されます。 増分のために`3 i l r`、 追加`1`で`l`そして`-1`で`r + 1`その立場が存在するとき。 位置のフェンウィック接頭辞の合計`x`影響を受けたバイトの増分数を返します`x`これまでのところ。 
7. 保存された操作を元の順序でスキャンします。 増加するには、適切なフェンウィック ツリーを更新します。 ロードの場合、フェンウィック ツリーには現在、このロードの前に発生した増分が正確に含まれているため、データ部分は現在、キャッシュにコピーされるバージョンと正確に一致しています。 
8. ロード時に、そのロードに関連付けられたすべての印刷クエリにアクセスします。 クエリごとに、保存されているオフセットで元のバイトを読み取り、そのオフセットのフェンウィック プレフィックス合計を加算し、結果を 256 を法として減算します。クエリの元の出力インデックスを使用して回答を保存します。 
9. 回答をクエリ順に出力します。 ロード前に発生したクエリのデフォルトの応答はすでにゼロですが、他のすべてのクエリは、それを所有するロードが処理されたときに応答されます。 

機能する理由: キャッシュ アドレスごとに、セグメント ツリーにはそのアドレスが含まれる範囲のすべてのロードが保存され、最大のロード番号が最新のロードになります。 したがって、すべての印刷クエリは、キャッシュ バイトを最後に決定した操作に正確に関連付けられます。 2 回目のスキャン中にそのロードに達すると、ロード前のすべての増分は対応するフェンウィック ツリーにすでに挿入されていますが、ロード後のすべての増分はまだ挿入されていません。 したがって、計算されたバイトは、キャッシュにコピーされたスナップショットとまったく同じになります。 データ部分に対する後からの変更は、必要なキャッシュ セマンティクスと一致する、保存された回答に影響を与えることはできません。 

## Python ソリューション```python
import sys
from array import array

input = sys.stdin.readline

def solve():
    n, m, q = map(int, input().split())

    lengths = array('i', [0]) * (m + 1)
    value_base = array('i', [0]) * (m + 1)
    fenwick_base = array('i', [0]) * (m + 1)

    values = bytearray()
    fenwick_total = 0

    for i in range(1, m + 1):
        tokens = input().split()
        k = int(tokens[0])

        lengths[i] = k
        value_base[i] = len(values)
        fenwick_base[i] = fenwick_total

        values.extend(int(x) for x in tokens[1:])
        fenwick_total += k + 1

    # Store operations compactly.
    typ = array('b', [0]) * q
    a = array('i', [0]) * q
    b = array('i', [0]) * q
    c = array('i', [0]) * q

    for t in range(q):
        op = list(map(int, input().split()))
        typ[t] = op[0]
        if op[0] == 1:
            a[t] = op[1]       # data piece
            b[t] = op[2]       # cache start
        elif op[0] == 2:
            a[t] = op[1]       # cache position
        else:
            a[t] = op[1]       # data piece
            b[t] = op[2]       # left
            c[t] = op[3]       # right

    # Segment tree for latest load covering a cache position.
    size = 1
    while size < n:
        size <<= 1

    tag = [0] * (2 * size)

    # For every load operation t, head[t] is the first query attached to it.
    head = array('i', [-1]) * q
    nxt = array('i', [-1]) * q
    query_offset = array('i', [0]) * q

    # Answers are bytes, so bytearray is enough.
    query_count = 0
    answers = bytearray()

    # First pass: resolve every cache query to its latest load.
    for t in range(q):
        if typ[t] == 1:
            data_id = a[t]
            start = b[t]
            end = start + lengths[data_id] - 1

            left = start - 1 + size
            right = end - 1 + size

            while left <= right:
                if left & 1:
                    tag[left] = t + 1
                    left += 1
                if not (right & 1):
                    tag[right] = t + 1
                    right -= 1
                left >>= 1
                right >>= 1

        elif typ[t] == 2:
            pos = a[t]
            node = pos - 1 + size
            load_id = 0

            while node:
                if tag[node] > load_id:
                    load_id = tag[node]
                node >>= 1

            answers.append(0)
            if load_id:
                load_idx = load_id - 1
                data_id = a[load_idx]
                offset = pos - b[load_idx] + 1

                query_offset[query_count] = offset
                nxt[query_count] = head[load_idx]
                head[load_idx] = query_count

            query_count += 1

    # Fenwick trees for range increment + point query.
    bit = bytearray(fenwick_total)

    def fenwick_add(base, length, pos, delta):
        while pos <= length:
            idx = base + pos
            bit[idx] = (bit[idx] + delta) & 255
            pos += pos & -pos

    def fenwick_sum(base, pos):
        result = 0
        while pos:
            result += bit[base + pos]
            pos -= pos & -pos
        return result & 255

    # Second pass: reconstruct each data piece exactly at each load time.
    for t in range(q):
        if typ[t] == 3:
            data_id = a[t]
            left = b[t]
            right = c[t]

            base = fenwick_base[data_id]
            length = lengths[data_id]

            fenwick_add(base, length, left, 1)

            after = right + 1
            if after <= length:
                fenwick_add(base, length, after, -1)

        elif typ[t] == 1:
            data_id = a[t]
            base = fenwick_base[data_id]
            original_base = value_base[data_id]

            query_id = head[t]

            while query_id != -1:
                offset = query_offset[query_id]
                increment = fenwick_sum(base, offset)

                value = values[original_base + offset - 1]
                answers[query_id] = (value + increment) & 255

                query_id = nxt[query_id]

    sys.stdout.write('\n'.join(map(str, answers)))

if __name__ == "__main__":
    solve()
```最初の配列セットには、データ部分がコンパクトに格納されます。`value_base[i]`部分の最初の元のバイトを指します`i`、 その間`fenwick_base[i]`フェンウィック ツリーの始まりを指します。 ピースごとにフェンウィック スロットを 1 つ追加すると、すべての木が`r + 1`データごとに個別の Python オブジェクトを割り当てることなく、差分を更新します。 

演算配列により、50 万の Python タプルの保存が回避されます。 各操作には型と最大 3 つの整数引数があるため、コンパクトです`array`オブジェクトはメモリ使用量を予測可能な状態に保ちます。 

セグメント ツリーは 1 から始まるオペレーション番号をタグとして使用します。ゼロは、ノードに負荷がかかっていないことを意味します。 更新間隔は、次を使用してキャッシュ アドレスからゼロベースのリーフに変換されます。`start - 1 + size`。 包括的な右エンドポイントは次のとおりです。`start + length - 1`、したがって、変換では使用する必要があります`end - 1 + size`。 これは、off-by-one エラーによってどのロードがクエリを所有するかが変わる可能性がある主な境界です。 

セグメント ツリーは、範囲の更新とポイントのクエリにのみ使用されます。 ロードは、完全にカバーされたノードにその操作番号を保存します。 クエリは、ルートからリーフへのパス上のすべてのノードを検査し、最大値を取得します。 セグメント全体の状態を具体化する必要がないため、遅延伝播は必要ありません。 

クエリのリンクされたリストは、別の大規模な Python リストのコレクションを回避します。`head[t]`最終キャッシュ値がロードから取得されたクエリを指します。`t`、 その間`nxt`同じロードに属するクエリをリンクします。 したがって、クエリは 2 回目のパス中に 1 回だけ処理されます。 

フェンウィック ツリーは差分を法 256 で保存します。通常のフェンウィック ツリーは通常、任意の整数の合計を保存しますが、バイト値は 256 を法とする合計にのみ依存するため、保存されたすべての値は安全に保存されます。`bytearray`。 プレフィックスの合計も、元のバイトに追加される前に 256 を法として減算されます。 

2 番目のパスは、後のロードの前に増分を処理し、元の操作の時系列順序と正確に一致します。 負荷に達したとき、それ以降の増分はまだフェンウィック ツリーに入力されていないため、その負荷に関連付けられたすべてのクエリに対して計算された値が、不変のキャッシュ スナップショットになります。 

Python の整数はオーバーフローしませんが、実装ではバイト値を 256 を法として明示的に削減します。これは問題の定義を反映しており、コンパクトなバイト配列を安全に使用できます。

 | 2 | 2 |`[1, 2, 1, 3]`| アドレス 4 → オフセット 3 |`1`|
 | 3 | 1 |`[255, 0, 15]`| アドレス 1 → オフセット 1 |`255`|
 | 8 | 1 |`[0, 1, 15]`| アドレス 2 → オフセット 1 |`0`|

 負荷が残る前のクエリ`0`、アドレス 5 の最後のクエリはロード 2 に属し、その 4 番目のバイトを返します。`3`。 最終的な出力は次のとおりです`0, 255, 1, 255, 0, 3`、サンプルと一致します。 

2 番目の例として、次のことを考えてみましょう。```
5 2 8
3 10 20 30
2 40 50
1 1 2
2 2
2 4
1 2 3
2 2
2 3
2 4
2 5
```最初のロードはアドレスを書き込みます`2..4`。 

| 操作 | アクション | クエリされたアドレスでの最新のロード | オフセット |
 | --- | --- | --- | --- |
 | 1 | ピース 1 を 2 にロード | なし | なし |
 | 2 | クエリアドレス 2 | ロード1 | 1 |
 | 3 | クエリアドレス 4 | ロード1 | 3 |
 | 4 | ピース 2 を 3 にロード | なし | なし |
 | 5 | クエリアドレス 2 | ロード1 | 1 |
 | 6 | クエリアドレス 3 | ロード4 | 1 |
 | 7 | クエリアドレス 4 | ロード4 | 2 |
 | 8 | クエリアドレス 5 | なし | なし |

 2 番目のロードはアドレスのみをカバーします`3`そして`4`。 住所変更は出来ない`2`、アドレスに届かない`5`。 結果の出力は次のとおりです。`10, 30, 10, 40, 50, 0`。 このトレースは、セグメント ツリーがキャッシュ位置ごとに最新のロードを個別に記憶する必要がある理由を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(合計 k_i + q log n + q log S) | データの読み取りは、合計データ サイズに比例します。 各ロード範囲の更新とキャッシュ クエリは O(log n) を使用しますが、各増分と各解決されたクエリは O(log S) を使用します。 |
 | スペース | O(n + m + q + 合計 k_i) | セグメント ツリーは O(n) を使用し、オペレーションとクエリ リンクは O(q) を使用し、ピース メタデータは O(m) を使用し、元のデータとフェンウィック ストレージは O(sum k_i + m) を使用します。 |

 関連するすべての境界を次のとおりに設定すると、`5 * 10^5`、対数係数は最大でも約 19 または 20 です。アルゴリズムは、ロードされたデータ部分の長さに比例した作業を実行することはありません。そのため、大きなデータ部分を繰り返しロードしても、大きなコピーが繰り返されることはありません。 5 秒という制限により、この対数構造が適切になり、コンパクトな配列により Python のメモリ使用量が制御されます。 

## テストケース

 次のハーネスは次のことを前提としています。`solve()`上記のソリューションの関数は、同じファイルで使用できるか、提出されたソリューションからインポートできます。```python
import sys
import io

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout
    old_input = globals()["input"]

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()
    globals()["input"] = sys.stdin.readline

    try:
        solve()
        return sys.stdout.getvalue()
    finally:
        sys.stdin = old_stdin
        sys.stdout = old_stdout
        globals()["input"] = old_input

 ## 特殊なケース

 ロード前のクエリの場合、セグメント ツリー パスにはタグが含まれていません。 アルゴリズムは、答えをデフォルトのバイト値のままにします。`0`。 たとえば、`1 1 2`、 データ`[7]`、そして2つ`2 1`クエリの場合、どちらの出力も`0`。 タッチされていないキャッシュ アドレスに対して、人為的なデータ部分の関連付けは作成されません。 

ロード前の増分の場合、2 番目のパスでロードが処理される前にフェンウィック ツリーが更新されます。 データあり`[255]`そして操作`3 1 1 1`、位置 1 のフェンウィック接頭辞の合計は次のようになります。`1`。 したがって、負荷は次のように計算されます。`(255 + 1) mod 256 = 0`、これが正しいスナップショットです。 

ロード後の増分の場合、クエリは以前のロードにアタッチされます。 ロードが 2 番目のパスで処理されるとき、後の増分はまだフェンウィック ツリーに到達していません。 データあり`[255]`、ロード、インクリメントが続き、保存された答えは残ります。`255`データ部分自体は最終的には`0`。 

重複するロードの場合、セグメント ツリーは、ポジションがロードされたかどうかを単に保存するのではなく、操作番号を比較します。 ピース 1 がアドレス 2 にロードされ、その後ピース 2 がアドレス 3 にロードされるとします。アドレス 2 のクエリは最初のロードのみを参照し、アドレス 3 と 4 のクエリは 2 番目のロードを参照します。 2 番目のロードの範囲にはアドレス 2 が含まれていないため、maximum-tag プロパティはまさにこの結果を返します。 

最後のキャッシュ アドレスで正確に終了するロードの場合、正しいエンドポイントは次のように計算されます。`start + length - 1`。 セグメント ツリーは、この包括的なエンドポイントを次のように変換します。`end - 1 + size`。 長さのある荷物`500000`から始まる`1`したがって、アドレス用のリーフをカバーします`500000`、これは最大サイズのテストによって実行されます。 

データ部分の最終バイトで終了する範囲増分の場合、差分は次の時点で更新されます。`r + 1`を実行してはなりません。 実装チェック`after <= length`その位置を更新する前に。 このチェックを行わないと、差分マーカーがフラットなフェンウィック ストレージ内の次の論理部分に漏れてしまいます。 

バイト オーバーフローの場合、フェンウィックの寄与と元のバイトの両方が次のように結合されます。`& 255`。 したがって`255 + 1`になる`0`、増分を繰り返すと、大きな整数表現を必要とせずに、256 バイト値すべてが自然に循環されます。
