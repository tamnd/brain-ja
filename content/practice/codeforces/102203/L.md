 ## 解決策
 ## 問題の理解

 不明な配列 (s_1,s_2,\ldots,s_n) があります。 配列はある位置までは厳密に増加し、その後は厳密に減少するため、ピークは 1 つになります。 すべての値は個別です。 (n) と目標値 (k) がわかっているので、インタラクティブなジャッジによって任意のインデックス (i) の値を尋ねることができます。 タスクは、値が正確に (k) であるインデックスを見つけることです。 

配列自体はプログラムでは使用できません。 すべての配列アクセスは対話型クエリであり、次のように記述されます。`? i`と答えると裁判官は(s_i)と答える。 必要なインデックスが特定されると、プログラムは次のように出力します。`! i`そして終了します。 

境界 (n\le 2\cdot10^5) により、配列のスキャンが直ちに除外されます。 通常の (O(n)) アルゴリズムは、多くの非対話型問題では十分小さいですが、ここではすべての配列アクセスが高価なクエリであり、使用できるクエリは 80 個のみです。 対数的な動作が必要です。 (\log_2(2\cdot10^5)<18) であるため、複数のバイナリ検索でもクエリ制限内に問題なく収まります。 

値自体は 0 ～ (10^9) の間であるため、通常の Python 整数で十分です。 ターゲットは必ず発生するため、増加部分と減少部分を正確に識別した後、2 つの二分探索のいずれかでそれを見つける必要があります。 

不注意な実装を破ってしまう可能性のある境界例がいくつかあります。 考慮する`n = 2`、値付き`[5, 3]`そして`k = 3`。 ピークは最初の位置にあるため、減少部分にはインデックス 2 の答えが含まれます。ピークが常に内部要素であると想定する実装では、このケースが失われ、2 番目の位置が正しく検索されない可能性があります。 

もう一つのケースは、`[1, 5, 3]`と`k = 1`。 答えは最初の要素で、増加部分の左側の境界に正確にあります。 二分探索で下限を誤って初期化すると、下限が破棄される可能性があります。 

同様に、`[1, 5, 3]`と`k = 3`減少部分の右側の境界をテストします。 答えはインデックス 3 なので、減少する二分探索では最終エンドポイントが許可される必要があります。 

元の問題ではすべての (s_i) が異なることが保証されているため、「すべてが等しい」配列をテストするという要求は文字通りには満たされません。 次のような配列`[5, 5, 5]`は法的な入力ではありません。 最も意味のあるテストは、厳密に単調な配列であり、ピークはエンドポイントの 1 つにあります。`[1, 2, 3, 4]`または`[4, 3, 2, 1]`。 

## アプローチ

 直接的なアプローチは、値 (k) が見つかるまで 1 から (n) までの位置をクエリすることです。 すべての位置が最終的に検査され、答えが存在することが保証されているため、これは正しいです。 問題はクエリの予算です。 最悪の場合、(n) 個のクエリが必要になり、その数は (200,000) にも達する可能性がありますが、裁判官は 80 個しか許可しません。問題は単に実行時間ではなく、対話型プロトコルの制限を超えていることです。 

配列の構造により、任意の配列よりもはるかに多くの情報が得られます。 増加部分では、(s_i<k) の場合、ターゲットは右側にのみ存在します。 (s_i>k) の場合は、左側のみになります。 減少部分では方向が逆になります。 したがって、ピークがどこにあるのかがわかったら、問題は 2 つの通常の二分探索になります。 

二分探索でもピークを見つけることができます。 中間位置 (m) をクエリし、(s_m) と (s_{m+1}) を比較するとします。 (s_m<s_{m+1}) の場合、まだ増加側にあるため、ピークは厳密に (m) の右側にあります。 (s_m>s_{m+1}) の場合、すでに減少側にあるため、ピークは (m) またはその左側のどこかにあります。 

これにより、ピークの対数検索が行われます。 その後、増加セグメントと減少セグメントを二分探索します。 クエリの総数は最大でもおおよそ (3\log_2 n) で、(n\le2\cdot10^5) の 80 をはるかに下回ります。 

この総当たりアプローチは、すべての位置が明示的にチェックされるため機能しますが、各チェックで 80 個のクエリのうちの 1 つしか消費されないため、失敗します。 山型の順序付けにより、これらの個々のチェックをバイナリ決定に置き換えることができ、検索を (O(n)) クエリから (O(\log n)) に減らすことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O(n)) クエリ | (O(1)) | 遅すぎる |
 | ピークの検索 + 2 つのバイナリ検索 | (O(\log n)) クエリ | (O(\log n)) 個のキャッシュされた値、または (O(1)) 個の補助スペース | 承認済み |

 ## アルゴリズムのチュートリアル

 1. (n) と (k) を読み取ります。 配列値はまだわかっていないため、アルゴリズムが必要とするすべての値は対話型クエリを通じて取得する必要があります。 
2. 出力するクエリ関数を定義します。`? i`、出力を直ちにフラッシュし、審査員の回答を読み取り、それを返します。 フラッシングは必須です。そうしないと、審査員が Python の出力バッファーに残っているクエリを待つ可能性があるからです。 
3. 二分探索でピークを見つけます。 範囲を維持する`[lo, hi]`ピークが含まれることが保証されています。 その間`lo < hi`、 取る`mid = (lo + hi) // 2`そしてクエリ`s[mid]`そして`s[mid + 1]`。 
4. もし`s[mid] < s[mid + 1]`、シーケンスはまだ増加しています`mid`したがって、ピークは厳密に右側にある必要があります。 セット`lo = mid + 1`。 
5. それ以外の場合は、`s[mid] > s[mid + 1]`なぜなら、すべての値は異なるからです。 シーケンスはすでに減少し始めているため、ピークは`mid`または左へ。 セット`hi = mid`。 
6. いつ`lo == hi`、そのインデックスがピークです。 配列は増加するセグメントに分割されました`[1, peak]`そして減少セグメント`[peak + 1, n]`。 
7. 二分探索`[1, peak]`増加する配列として。 位置で`mid`、その値がより小さい場合`k`、右に移動します。 それより大きい場合`k`、左に移動します。 等しい場合`k`、そのインデックスをすぐに出力します。 
8. 最初の検索が失敗した場合は、バイナリ検索を実行します。`[peak + 1, n]`減少する配列として。 ここでは比較の方向が逆になります。 もし`s[mid] > k`、右に行くほど値が小さくなるため、右に移動します。 もし`s[mid] < k`、左に移動します。 
9. ターゲットが見つかったら、印刷します。`! index`そして終了します。 (k) が発生するという保証は、最初の検索で見つからなかった場合でも、2 回目の検索で最終的にそれが見つかることを意味します。 

### なぜ効果があるのか

 ピーク検索の不変条件は、現在の間隔に常に最大要素が含まれるということです。 もし`s[mid] < s[mid+1]`、最大値をそれ以前にすることはできません`mid`、そこではシーケンスがまだ上昇しているため、次へ移動します。`[mid+1, hi]`不変式を保持します。 もし`s[mid] > s[mid+1]`、シーケンスが落ち始めました`mid+1`、したがって最大値は次の時点で発生します。`mid`またはそれより前に、不変条件を維持する`[lo, mid]`。 

ピークがわかった後は、その左側のすべてのインデックスは厳密に増加するシーケンスに属し、その右側のすべてのインデックスは厳密に減少するシーケンスに属します。 対応する二分探索では、(k) がまだ発生する可能性のあるインデックスが正確に保持されます。 ターゲットが存在することが保証されているため、これらの検索のいずれかがそのインデックスに到達します。 

## Python ソリューション```python
import sys

input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())

    cache = {}

    def ask(i):
        if i not in cache:
            print("?", i, flush=True)
            value = int(input())
            if value == -1:
                sys.exit(0)
            cache[i] = value
        return cache[i]

    # Find the peak.
    lo, hi = 1, n
    while lo < hi:
        mid = (lo + hi) // 2
        left = ask(mid)
        right = ask(mid + 1)

        if left < right:
            lo = mid + 1
        else:
            hi = mid

    peak = lo

    # Binary search on the increasing part [1, peak].
    lo, hi = 1, peak
    while lo <= hi:
        mid = (lo + hi) // 2
        value = ask(mid)

        if value == k:
            print("!", mid, flush=True)
            return
        if value < k:
            lo = mid + 1
        else:
            hi = mid - 1

    # Binary search on the decreasing part [peak + 1, n].
    lo, hi = peak + 1, n
    while lo <= hi:
        mid = (lo + hi) // 2
        value = ask(mid)

        if value == k:
            print("!", mid, flush=True)
            return
        if value > k:
            lo = mid + 1
        else:
            hi = mid - 1

if __name__ == "__main__":
    solve()
```の`ask`機能は裁判官とコミュニケーションをとる唯一の場所です。 ピーク検出により、後のバイナリ検索で再度必要となる位置がクエリされる可能性があるため、キャッシュは役立ちます。 回答を再利用すると、同じインデックスに対して別の対話型クエリを費やすことがなくなります。 

ピーク検索では次のように使用します。`lo = mid + 1`いつ`s[mid] < s[mid + 1]`、 なぜなら`mid`その状況では、それ自体がピークになることはできません。 他の支店では、`mid`依然としてピークの可能性があるため、正しい更新は次のとおりです。`hi = mid`、 ない`mid - 1`。 

増分二分探索では、通常の比較ルールが使用されます。 右に移動すると値が小さくなるため、減少する検索では方向が逆になります。 

Python には整数オーバーフローの問題はありません。`(lo + hi) // 2`指定された範囲内では安全です。 重要な実装の詳細は次のとおりです。`flush=True`すべての質問と最終的な答えについて。 フラッシュを行わないと、ジャッジがリクエストを受信しないため、他の点では正しい対話型アルゴリズムが失敗する可能性があります。 

の`-1`ハンドリングは、無効なクエリまたはプロトコルの失敗を通知するために否定的な応答を使用する、対話型ジャッジのための従来の防御手段です。 元のステートメントでは、有効な実行のためにそのような応答を使用する必要はありませんが、応答が表示されたときに終了することで、プログラムが無意味な入力を続行するのを防ぎます。 

このコードは、元の対話型審査員を対象としています。 ジャッジが回答する責任があるため、通常のバッチ ランナーは直接実行できません。`? i`。

## テストケース

 元のタスクは対話型であるため、通常は`run(input) -> output`単体テスト パターンを直接適用することはできません。 テスト ハーネスは、要求されたインデックスの値を指定して審査員をシミュレートする必要があります。 次のテストでは、同じアルゴリズムのバッチ バージョンを使用します。ここでは、テスト コードで非表示の配列を明示的に使用できます。 これにより、アサーションも決定的になります。```python
import io
import sys

def find_target(a, k):
    n = len(a)
    queries = 0

    def ask(i):
        nonlocal queries
        queries += 1
        return a[i - 1]

    lo, hi = 1, n

    while lo < hi:
        mid = (lo + hi) // 2
        left = ask(mid)
        right = ask(mid + 1)

        if left < right:
            lo = mid + 1
        else:
            hi = mid

    peak = lo

    lo, hi = 1, peak
    while lo <= hi:
        mid = (lo + hi) // 2
        value = ask(mid)

        if value == k:
            return mid, queries
        if value < k:
            lo = mid + 1
        else:
            hi = mid - 1

    lo, hi = peak + 1, n
    while lo <= hi:
        mid = (lo + hi) // 2
        value = ask(mid)

        if value == k:
            return mid, queries
        if value > k:
            lo = mid + 1
        else:
            hi = mid - 1

    raise AssertionError("Target is guaranteed to exist")

# Provided sample.
assert find_target([1, 3, 10, 8, 2], 3)[0] == 2

# Minimum-size input, peak at the first position.
assert find_target([5, 3], 3)[0] == 2

# Minimum-size input, peak at the second position.
assert find_target([3, 5], 3)[0] == 1

# Target is exactly the peak.
assert find_target([1, 4, 9, 7, 2], 9)[0] == 3

# Target is at the right boundary.
assert find_target([1, 5, 8, 6, 3], 3)[0] == 5

# Strictly increasing array, peak at the right boundary.
assert find_target([1, 2, 3, 4, 5], 1)[0] == 1

# Strictly decreasing array, peak at the left boundary.
assert find_target([5, 4, 3, 2, 1], 1)[0] == 5

# Large legal instance.
a = list(range(100000))
a += list(range(100000, 0, -1))
expected = 150000
assert find_target(a, a[expected - 1])[0] == expected

 |`[5, 3], k=3`|`2`| 最小サイズ、左境界のピーク |
 |`[3, 5], k=3`|`1`| 最小サイズ、右境界のピーク |
 |`[1, 4, 9, 7, 2], k=9`|`3`| ターゲットはピークに等しい |

 テスト仕様で要求されている「すべて等しい値」のケースは意図的に省略されています。 このような配列は、すべての (s_i) が異なるという元の条件に違反します。 これを厳密に単調な配列に置き換えると、不可能な状態をテストすることなく、対応する境界動作がテストされます。 

## 特殊なケース

 最初の位置のピークについては、次のことを考慮します。`n = 2`、`k = 3`、および隠し配列`[5, 3]`。 ピーク検出中に位置 1 と 2 を比較すると、次のようになります。`5 > 3`, したがって、ピーク範囲は次のようになります。`[1, 1]`。 増加する検索では位置 1 がチェックされ、その値が 5 であるため失敗します。次に、減少する検索では位置 2 がチェックされ、3 が見つかり、結果が生成されます。`! 2`。 このケースは、ピーク間隔が左側のエンドポイントに直接折りたたまれることが許可されているため機能します。 

最後の位置のピークについては、次のことを考慮します。`[3, 5]`と`k = 3`。 比較`3 < 5`ピーク検索を位置 2 に移動します。増加検索は両方の位置をカバーし、位置 1 でターゲットを見つけます。減少セグメントに要素を含める必要はありません。 これにより、次の使用が検証されます。`[peak + 1, n]`2 番目の検索では、無効な範囲を強制するのではなく。 

ピークに等しいターゲットの場合、次のように考慮します。`[1, 4, 9, 7, 2]`と`k = 9`。 ピーク検出により位置 3 が特定されます。増加バイナリ検索にはピーク自体が含まれ、位置 3 をクエリし、すぐにそれを返します。 最初の二分探索からピークを除外すると、不必要で不正確な境界変更が生じる可能性があります。 

一番右の位置にあるターゲットについては、次のように考えます。`[1, 5, 8, 6, 3]`と`k = 3`。 ピークは位置 3 なので、減少する検索でカバーされます。`[4, 5]`。 位置 5 をクエリすると 3 が返されます。検索では次を使用する必要があります。`hi = n`包括的に、そうでない場合は、最終インデックスのターゲットが黙って破棄されます。 

次のような完全に増加する配列の場合`[1, 2, 3, 4, 5]`、ピークは位置 5 です。ピーク検出中のすべての比較で次のことがわかります。`s[mid] < s[mid+1]`したがって、下限は 5 に達するまで右に移動します。その後、最初の二分探索で配列全体がカバーされます。 定義では転換点が (n) であることが許可されているため、これは正当です。 

次のような完全に減少する配列の場合、`[5, 4, 3, 2, 1]`、ピークは位置 1 です。すべてのピーク比較で次のことがわかります。`s[mid] > s[mid+1]`、したがって、上限は 1 に達するまで左に移動します。増加する部分には位置 1 のみが含まれ、減少する検索では位置 2 ～ 5 が処理されます。これは対称境界のケースです。 

最後に、重複した値を、それが可能であるかのように処理してはなりません。 例えば、`[1, 4, 4, 2]`位置 2 と位置 3 の比較は等しくなりますが、このような配列は問題により禁止されています。 ピーク検索は、すべての比較が厳密に増加または減少しているという事実に基づいています。 実装に等価性ブランチを追加すると別の問題が解決されるため、ここでは不要です。
