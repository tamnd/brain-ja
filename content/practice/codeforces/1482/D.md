 ## 解決策
 ## 問題の理解

 ジャンルごとにラベル付けされた曲を含むプレイリストをシミュレートするように求められます。Arkady は曲を順番に聴き、最後に到達すると最初に戻ります。 ルールは、Arkady が最後に聴いた曲のジャンルと前の曲のジャンルが互いに素である場合、最後の曲がプレイリストから削除されるというものです。 曲が削除されると、Arkady は前の曲を忘れてしまうため、削除をすぐに連鎖させることはできません。 タスクは、どの曲をどのような順序で削除するかを決定することです。 

入力では複数のテスト ケースが提供され、それぞれが曲数とジャンルのリストを指定します。 出力は、テスト ケースごとに、削除された曲の数と、削除順の 1 から始まる位置である必要があります。 制約により、ジャンル値が最大 100,000 曲までのすべてのテスト ケースが許可されます。$10^9$これにより、削除ごとにすべての曲のペアを繰り返すような単純なアプローチが排除されます。 配列の削除を使用した直接シミュレーションは次のようになります。$O(n^2)$最悪の場合、遅すぎます。 

明らかではないエッジ ケースには、プレイリストが複数回循環するシナリオ、削除により曲がスキップされるシナリオ、またはプレイリストに繰り返し要素があるシナリオが含まれます。 たとえば、プレイリスト`[2, 2, 2]`隣接するすべてのジャンルが 1 より大きい GCD を共有するため、何も削除されません。`[1, 2]`2 番目の曲を削除すると、アルゴリズムがリセットされて最初の曲が再度チェックされ、複数の削除が発生する可能性があるため、両方の曲を削除します。 

## アプローチ

 ブルートフォース手法では、プレイリストを反復処理し、最後の 2 曲をチェックして GCD が 1 になったときに削除し、削除した後の曲から再開します。 これはルールに正確に一致しますが、削除するたびに最大でスキャンが必要になる可能性があります。$O(n)$につながる曲$O(n^2)$複雑。 と$n$まで$10^5$、これは非現実的です。 

重要な洞察は、現在の曲とその前の曲が互いに素である場合にのみ曲を削除するということです。 これは、循環構造を維持し、すでにチェックした曲を繰り返しスキャンすることなく、次の削除候補を迅速に見つけることを示唆しています。 キューまたはリンク リスト構造により、O(1) の削除と効率的な循環が可能になります。 次の削除に対してどの曲が有効であるかを追跡するために、前の曲がまだ生きており、共素チェックが使い果たされていない曲インデックスのキューを維持できます。 削除後、次の曲から続行し、アルカディによってすでに「忘れられた」曲を効果的にスキップします。 これにより、各曲はチェック時に 1 回、場合によっては削除時に 1 回の合計 2 回アクセスされるため、テスト ケースごとの複雑さが O(n) に軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) | O(n) | 遅すぎる |
 | 最適 (キュー + GCD チェック) | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. テスト ケースの数を読み取ります。 テストケースごとに曲数を読み取ります。`n`そしてジャンルのリスト`a`。 簡単にするために、内部では 0 から始まるインデックスを使用して作業します。 
2. 配列を使用して、プレイリストの循環リンク表現を構築します。`next_song`どこ`next_song[i]`プレイリスト内の次の曲を指します。 当初は、`next_song[i] = (i + 1) % n`。 
3. 前の曲が互いに素である曲のインデックスを使用してキューを初期化します。 これは、すべての曲を反復してチェックすることで見つかります。`gcd(a[i], a[i-1]) == 1`。 
4. 空のリストを初期化する`deleted`削除の順序を保存します。 
5. キューを処理します: 曲のインデックスをポップします`i`。 もし`i`はすでに削除されているため（前の曲が削除されているため）、スキップします。 それ以外の場合は追加します`i+1`に`deleted`(1 から始まるインデックスに変換します)。 
6. を更新します。`next_song`前の曲の をクリックして、削除された曲をスキップし、プレイリストから事実上削除します。 
7. 次の曲が次の曲かどうかを確認します`i`は、新しい前の曲と互いに素の関係にあります。 その場合は、将来の削除に備えて次の曲のインデックスをキューに追加します。 
8. キューが空になるまで続行します。 の長さを出力します`deleted`そしてインデックスを順番に並べます。 

機能する理由: このアルゴリズムは、ライブ曲のみを表す循環構造を維持します。 削除候補のキューを維持することで、不必要に曲を再チェックすることがなくなり、各曲が最大でも 1 回削除されるようになります。 不変条件は、各削除の後、プレイリストとキューが次の潜在的な同一の削除を正確に表すということです。 循環リンクにより、プレイリスト内の適切な循環が保証されます。 

## Python ソリューション```python
import sys
import math
from collections import deque
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n = int(input())
    a = list(map(int, input().split()))
    next_song = [(i + 1) % n for i in range(n)]
    deleted = []
    alive = [True] * n
    q = deque()
    
    for i in range(n):
        if math.gcd(a[i], a[i-1]) == 1:
            q.append(i)
    
    while q:
        i = q.popleft()
        if not alive[i]:
            continue
        deleted.append(i + 1)
        alive[i] = False
        prev = (i - 1) % n
        while not alive[prev]:
            prev = (prev - 1) % n
        nxt = next_song[i]
        while not alive[nxt]:
            nxt = next_song[nxt]
        next_song[prev] = nxt
        if alive[nxt] and math.gcd(a[prev], a[nxt]) == 1:
            q.append(nxt)
    
    print(len(deleted), *deleted)
```ソリューションは、`next_song`循環リンク リストをエミュレートする配列。 最初は削除候補だった各曲はキューに入れられます。 次に、キューの先頭を繰り返し削除し、リンクを更新し、削除によって次の曲に新しい共素条件が作成されるかどうかを確認します。 プレイリストの終わりを超えて循環するような境界条件は、モジュロ演算によって処理されます。 すでに削除されている曲はスキップされ、重複した削除が回避されます。 

## 実用的な例

 トレースサンプル 1、最初のテストケース`[5, 9, 2, 10, 15]`:

 | ステップ | キュー | 削除済み | プレイリスト (生存中) | メモ |
 | --- | --- | --- | --- | --- |
 | 初期化 | [1、2] | [] | [5、9、2、10、15] | gcd(5,9)=1、gcd(9,2)=1 |
 | ポップ1 | [2] | [2] | [5,2,10,15] | 9 を削除、前 = 0、次 = 2 |
 | ポップ2 | [] | [2,3] | [5,10,15] | 2 を削除、前 = 0、次 = 3 |
 | 完了 | [] | [2,3] | [5,10,15] | キューが空です |

 トレース サンプル 1、2 番目のテスト ケース`[1,2,4,2,4,2]`:

 | ステップ | キュー | 削除済み | プレイリスト (生存中) | メモ |
 | --- | --- | --- | --- | --- |
 | 初期化 | [1,3] | [] | [1,2,4,2,4,2] | gcd(1,2)=1、gcd(2,4)=2 ... |
 | ポップ1 | [3] | [2] | [1,4,2,4,2] | 曲 2 を削除 |
 | ポップ3 | [] | [2,1] | [4,2,4,2] | 曲 1 を削除 |

 これらのトレースは、「前のことを忘れる」ルールと適切な循環を尊重して、削除が正しい順序で行われたことを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | テスト ケースあたり O(n) | 各曲は最大 2 回アクセスされます。1 回目は GCD の確認のため、1 回目は削除のためです。 キュー操作は O(1) です。 |
 | スペース | テスト ケースあたり O(n) | 配列`alive`、`next_song`、キューは最大 n 個の要素を保持します。 |

 の合計を考えると、`n`すべてのテスト ケース ≤ 10^5 で、これは 2 秒の制限内に問題なく収まります。
