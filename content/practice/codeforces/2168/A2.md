 ## 解決策
 ## 問題の理解

 整数の配列に対して 2 フェーズのエンコードとデコードのプロセスを実装するように求められます。 最初のフェーズでは、プログラムは配列を受け取ります。`a`サイズの`n`値は最大 10 億で、文字列を出力する必要があります`s`小文字で構成されます。 この文字列は、最初の実行のメモリを持たない状態でプログラムが再起動される第 2 フェーズまで保持される唯一の情報です。 この 2 回目の実行では、プログラムは次のメッセージを受け取ります。`s`そして両方を再構築する必要があります`n`そして元の配列`a`その通り。 制約は、文字列が`s`潜在的に大きな整数をエンコードしながら、適切な長さに収まるほど十分にコンパクトである必要があります。 

課題は 2 つあります。 まず、数値を直接保存したり送信したりすることはできません。 それらを文字にエンコードする必要があります。 第 2 に、エンコーディングは明確であり、許容される最大 100,000 文字の文字列長内でデコード可能である必要があります。`n`最大 10,000 で、値は次の値に達します`10^9`。 各整数を 1 つの文字にマッピングする単純なアプローチは失敗します。これは、アルファベットには 26 文字しかなく、数値の可能な範囲よりもはるかに少ないためです。 

エッジ ケースには、単一要素の配列、すべて同じ値を持つ配列、または最大値を含む配列が含まれます。`10^9`。 値を正規化しない、または値を明確に分離しない不用意なソリューションを使用すると、誤ってデコードされる可能性があります。 たとえば、エンコーディング`[1, 27]`として`'ab'`数値マッピングが区切り文字なしで再利用される場合、曖昧になる可能性があります。 

## アプローチ

 ブルートフォースアプローチは、各整数を文字に直接マッピングしようとすることです。 あなたは取ることができます`a_i % 26`手紙を作成します。 これは、小さい数値の場合は原則として正しいですが、複数の整数が同じ文字に折りたたまれるため、デコード時に失敗します。 操作数は微々たるものですが、方法があいまいなので受け入れられません。 

重要な洞察は、配列を基数 26 を使用した位置記数系の一連の数値として扱うことができるということです。各整数は、基数 26 の数字を表す複数の文字にエンコードできます。そうすることで、最大 26 進数までの任意の数値をマッピングできます。`10^9`一連の文字に変換します。 明確なデコードを保証するために、エンコードされた各整数はマーカーで区切られるか、各整数の長さを文字列の一部としてエンコードされます。 実際的な解決策は、1 文字あたり 5 ビットを使用し、26 文字を超える 32 個の個別のシンボルを提供することです。 次に、数値をバイナリにパックし、5 ビットのチャンクを文字にマッピングします。 これにより、デコードが正確であり、文字列長の制限内で動作することが保証されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n) | O(n) | あいまいで、数値が大きい場合は失敗します。 
| 最適 | O(n log(max(a))) | O(n log(max(a))) | 受け入れられ、正確なエンコード/デコード |

 ## アルゴリズムのチュートリアル

 1. 最初の実行で、以下を読み取ります。`n`そして配列`a`。 各整数を変換する`a_i`バイナリに。 すべてのバイナリ表現を順番に連結して、長いビット文字列を生成します。 
2. ビット文字列を 5 ビットのチャンクに分割します。 各 5 ビットのチャンクは、オフセットを追加することで小文字にマップされます。`'a'`。 これにより文字列が生成されます`s`小文字のみを含む。 
3.文字列を出力する`s`。 プログラムが終了し、すべての記憶が失われます`a`。 
4. 2 回目の実行では、文字列を読み取ります。`s`。 各文字を対応する 5 ビット値に変換し、長いビット文字列を再構築します。 
5. 元の整数ごとに既知のビット長を使用します (`10^9 < 2^30`、各数値には 30 ビットで十分です)、ビット文字列を連続した 30 ビットのセグメントにスライスします。 各セグメントを整数に変換し直します。 
6. 出力`n`デコードされた配列が続きます。 

これが機能する理由は、5 ビット エンコードによって文字をバイナリにマッピングし直すときにあいまいさがなくなることと、整数あたりの固定幅が 30 ビットであるため、元の数値がそれぞれ正確に再構築されるためです。 不変条件は、元の各数値がちょうど 30 ビットで完全に表現され、エンコード中にビットが失われないことです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def encode(a):
    bits = ""
    for x in a:
        bits += bin(x)[2:].rjust(30, '0')
    # pad to make length a multiple of 5
    if len(bits) % 5 != 0:
        bits += '0' * (5 - len(bits) % 5)
    s = ""
    for i in range(0, len(bits), 5):
        val = int(bits[i:i+5], 2)
        s += chr(ord('a') + val)
    return s

def decode(s, n):
    bits = ""
    for c in s:
        val = ord(c) - ord('a')
        bits += bin(val)[2:].rjust(5, '0')
    a = []
    for i in range(n):
        x = int(bits[i*30:(i+1)*30], 2)
        a.append(x)
    return a

mode = input().strip()
if mode == 'first':
    n = int(input())
    a = list(map(int, input().split()))
    print(encode(a))
else:
    s = input().strip()
    # estimate n by using length: each number is 30 bits, each letter 5 bits
    total_bits = len(s) * 5
    n = total_bits // 30
    a = decode(s, n)
    print(n, *a)
```エンコードでは、文字チャンクと一致するようにビット文字列が 5 の倍数にパディングされます。 デコード中、プログラムは元のビット文字列を再構築し、それを数値ごとに 30 ビットのセグメントにスライスします。 主な微妙な点は、ビット文字列の長さが 5 ビットの文字マッピングおよび 30 ビットの数値と一致していることを確認して、off-by-one エラーを回避することです。

 ## 特殊なケース

 単一要素配列の場合`[1]`、アルゴリズムは 30 ビット文字列を生成し、それを 6 文字にエンコードします。 デコード中に、ちょうど 30 ビットが抽出されて数値 1 が生成されます。`[10^9, 10^9]`、30 ビット表現により、情報が失われることはなく、両方の要素が正しくデコードされることが保証されます。 文字の境界を越える配列の場合:`[1, 27]`、各 5 ビット セグメントが個別であり、30 ビット スライスが元の整数と一致するため、5 ビット マッピングにより衝突が防止されます。
