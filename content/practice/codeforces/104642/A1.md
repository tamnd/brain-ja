 ## 解決策
 ## 問題の理解

 単純なロボットのようなシステムを制御する一連のコマンドが与えられます。 プログラムは2種類の文字からなる文字列です。 1 人のキャラクターはシステムの発射力を増加させ、もう 1 人のキャラクターはその時点の現在のパワーに等しいダメージを与えるショットを発射します。 

システムは、パワーが 1 に等しい状態で開始します。プログラムを左から右にスキャンすると、パワーが増加するコマンドに遭遇するたびに、パワーは 2 倍になります。 射撃コマンドに遭遇するたびに、現在のパワーが合計ダメージに追加されます。 

プログラムに加えて、最大許容ダメージも与えられます。 タスクは、プログラムがこの制限を超えない合計ダメージを生成するために必要な、隣接するコマンド間の隣接スワップの最小数を決定することです。 コマンドを並べ替えても不可能な場合は、その旨を報告しなければなりません。 

重要な問題は、スワップによってローカルな順序だけでなく、どのショットがどのパワー レベルで発生するかも変化することです。 パワーはショットの前にすでに出現した増加の数に依存するため、ショットを早く移動すると寄与が減少し、後で移動すると増加が増加します。 

通常、制約により、最大約 10^5 のプログラム長が許可されます。 これにより、考えられるすべてのスワップをシミュレートしたり、すべての順列を試行したりするアプローチは即座に除外されます。 局所的な改善を繰り返した O(n^2) シミュレーションでも、最悪の場合は遅すぎます。 スワップが総ダメージにどのように影響するかを直接推論するアプローチが必要です。 

すべてのショットがすでに最小限のパワーで行われている場合、微妙なエッジケースが発生します。 その場合、スワップは役に立たず、計算されたダメージを制限値と直接比較する必要があります。 もう 1 つのエッジ ケースは、プログラムに射撃コマンドが含まれていない場合に発生します。この場合、ダメージは配置に関係なく常にゼロになります。 

## アプローチ

 この強引なアイデアは、プログラムを文字列として扱い、隣接するすべてのスワップを繰り返し試行し、各スワップ後に合計ダメージを再計算し、最良の結果を維持することです。 これは、スワップによって到達可能な置換の完全な状態空間を探索するため、原理的には正しいです。 ただし、ダメージの各再計算には O(n) のコストがかかり、スワップ シーケンスの数は指数関数的に増加します。 貪欲な局所的な改善に限定しても、最悪の場合は O(n^3) の動作が発生し、これは大規模な入力の許容限界をはるかに超えています。 

重要な観察は、各射撃コマンドの寄与は、そのコマンドの前に出現するパワー増加コマンドの数にのみ依存するということです。 パワー増加コマンドと射撃コマンドの間の各スワップは、ポジション間でパワー寄与の 1 単位をシフトします。最も有益なスワップは常に、可能な最新のパワー増加コマンドを超えてより早く射撃コマンドを移動するものです。 これにより、問題のあるパターンの最も右側の出現を常にターゲットにすることができます。 

スワップを直接シミュレートする代わりに、現在のダメージを計算します。 すでに制限内にある場合は、スワップする必要はありません。 それ以外の場合は、射撃コマンドの前に表示される右端の威力増加コマンドを 1 つ右に移動することでダメージを軽減することを繰り返します。 このような各動きは、高威力のショットの寄与を減らし、制限に達するか、有用な交換がなくなるまで、動きごとにどれだけダメージが減少するかを追跡します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(2^n · n) | O(n) | 遅すぎる |
 | 貪欲な削減 | O(n^2) | O(n) | 遅すぎる |
 | 位置追跡による最適化された貪欲さ | O(n) または O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちはプログラムを、各射撃コマンドがその前に出現するパワー倍増コマンドの数によって決定されるパワー レベルに等しいダメージを蓄積するシーケンスとして考えます。

1. 現在のパワーを維持しながら、左から右にスキャンして初期の合計ダメージを計算します。 パワーコマンドを見るたびに、パワーが2倍になります。 射撃コマンドが表示されるたびに、合計ダメージにパワーが追加されます。 これにより、削減する必要があるベースラインが得られます。 
2. 初期ダメージがすでに許容限度以下である場合、スワップの必要がないため、直ちに停止します。 配置を変更しても、一部のショットのダメージが増加するリスクがあるだけです。 
3. それ以外の場合は、被害を減らす努力を繰り返します。 これを効率的に行うために、パワーコマンドが射撃コマンドの前に現れる右端の位置に配置します。 これら 2 人のキャラクターを交換すると、その射撃コマンドの寄与が、より高いパワーのコンテキストのちょうど半分に減ります。これは、1 回の交換で可能な最大の削減量です。 
4. スワップを実行し、最初から再計算するのではなく、それに応じて合計ダメージを更新します。 重要なのは、影響を受ける射撃コマンドの貢献だけが予測可能な方法で変化し、他のものは変化しないということです。 
5. 損傷が許容できるようになるか、有効なスワップが存在しなくなるまで、このプロセスを続けます。 制限を超えたままスワップ機会を使い果たした場合、答えは不可能です。 

これが機能する理由は、ダメージを軽減できる唯一のスワップは、パワー コマンドを横切って射撃コマンドを左に移動するスワップであるという不変条件に基づいています。 このようなスワップでは、そのショットが実行されるパワー レベルがちょうど 1 倍の係数だけ減少します。 より高いパワーショットは指数関数的に大きなダメージに寄与するため、常に可能な最新のパワーシュート境界にスワップを適用することで、スワップごとの最大の軽減が保証されます。 この貪欲な選択により、正確性が保たれます。非ローカル スワップは、同一またはより小さい効果を持つ一連の隣接スワップに分解でき、有益なスワップを遅らせても、必要な操作の数を減らすことはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def compute_damage(s):
    power = 1
    damage = 0
    for c in s:
        if c == 'C':
            power *= 2
        else:
            damage += power
    return damage

def solve():
    t = int(input())
    for _ in range(t):
        d, s = input().split()
        d = int(d)
        s = list(s.strip())

        if s.count('S') == 0:
            print(0)
            continue

        swaps = 0

        while True:
            damage = compute_damage(s)
            if damage <= d:
                print(swaps)
                break

            idx = -1
            for i in range(len(s) - 1):
                if s[i] == 'C' and s[i + 1] == 'S':
                    idx = i

            if idx == -1:
                print("IMPOSSIBLE")
                break

            s[idx], s[idx + 1] = s[idx + 1], s[idx]
            swaps += 1

if __name__ == "__main__":
    solve()
```この解決策は、プログラム セマンティクスの直接的なシミュレーションを使用してダメージを計算することから始まります。 機能`compute_damage`ストリング全体で電力がどのように進化するかの正確な定義を反映しています。 

次に、メイン ループは、現在の構成が有効かどうかを繰り返しチェックします。 そうでない場合は、パワー増加の直後にショットが発生する有利な隣接ペアを右端から検索します。 この選択は意図的なもので、後のパワー増加に比べてショットを早く移動することがダメージの軽減に最大の影響を与えるためです。 

スワップ操作はインプレースで実行され、適用したそのような操作の数を数えます。 アルゴリズムは、ダメージ条件が満たされるか、改善するスワップが存在しない場合に終了します。 

重要な微妙な点は、スワップのたびにダメージを再計算するのは概念的には単純ですが非効率であるということです。 ただし、実装は正しく、この A1 バリアントの典型的な小さな制約内に保たれます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n・k) | 各スワップでは、ダメージを再計算するためにフル スキャンが必要になる場合があり、これを最大 k 回繰り返すことができます。 
| スペース | O(n) | 文字列は変更可能なリストとして保存されます。 

n と総スワップの両方が小さいままである A1 バージョンの一般的な制約を考慮すると、これで十分です。 制約が大きい場合は、再計算の繰り返しを減らすために、最適化された貪欲戦略が必要になります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、プログラムに射撃コマンドが含まれていない場合です。 その状況では、ダメージ計算ループは値を加算しないため、スワップに関係なく結果は常にゼロになります。 アルゴリズムは、スワップ ループに入る前に射撃コマンドがないことをチェックすることで、このケースを正しく短絡します。 

すべての射撃コマンドがすでに可能な限り低い電力レベルにある場合、別の特殊なケースが発生します。 スワップは構文上引き続き可能ですが、被害がさらに軽減されるわけではありません。 このアルゴリズムは、各スワップ後にダメージを再計算し、改善が不可能な場合には終了することでこれを処理します。 

最後のエッジケースは、文字列に射撃コマンドのみが含まれている場合です。 ここでは、スワップによって構造を変更することはできないため、有益なペアの右端の検索はすぐに失敗し、アルゴリズムは正しく不可能を出力します。
