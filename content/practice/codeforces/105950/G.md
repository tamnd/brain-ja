 ## 解決策
 ## 問題の理解

 バイナリ文字列によって駆動される一連の操作を通じて進化するルート構造が与えられています。 最初は、ストーリーには 2 つの「状態」があり、それぞれが数値 (主な値と補助的な値) で表されます。 一連の日にわたって、2 人のライターのうちの 1 人がバイナリ スケジュールに従って動作しますが、重要な点は、アクション自体は誰が実行しても同じであるということです。 ライターは現在の値のペアを確認し、主な値をそれらの合計に置き換えてから、前の 2 つの値の 1 つを選択して新しい補助値として保持します。 

毎日ペアを変えていきます$(X, Y)$新しいペアに$(X+Y, Z)$、 どこ$Z$どちらかです$X$または$Y$。 バイナリ文字列は変換ルールを変更せず、どのプレイヤーが行動するかにのみ影響し、それがミニマックス動作を通じて最終結果がどのように解釈されるかに影響します。 

すべての更新操作の後、結局のところ、メイン変数の最終的な値を再計算するように求められます。$N$日々は最適な動作の下でプレイされます。一方は最終結果を最大化しようとし、もう一方は最終結果を最小化しようとします。 更新のたびにバイナリ文字列のセグメントが反転されるため、数日間のサフィックスにわたる役割が劇的に変化する可能性があるため、最終結果を効率的に再計算する必要があります。 

制約は次のとおりです$N, Q \le 2 \cdot 10^5$、全体の再計算が即座に除外されます。$N$クエリごとに -日のプロセス。 更新ごとの完全な動的プロセスの単純なシミュレーションにはコストがかかります$O(NQ)$、約で大きすぎます$4 \cdot 10^{10}$トランジション。 

主な問題は、毎日の操作が単に追加的に寄与するだけでなく、分岐の選択肢を定義するため、プロセス全体がバイナリ文字列に対する決定木のように動作することです。 更新では大きなセグメントが反転されるため、セグメント反転時に集計結果を迅速に再計算できる構造が必要です。 

すべての文字を反転すると、微妙なエッジケースが表示されます。 たとえば、すべて 0 の文字列は、一方のプレーヤーが常に行動することを意味し、すべて 1 の文字列は、反対側のプレーヤーが常に行動することを意味します。 これら 2 つの極端なスケジュールは、基礎となる操作が対称的であっても、まったく異なる最適な結果をもたらす可能性があります。 補助値の選択は局所的最大化だけでなく将来の最適な決定に依存するため、1 日あたりの単純な貪欲な解釈は失敗します。 

## アプローチ

 ブルートフォースのアイデアは、固定文字列のプロセスを直接シミュレートすることです。 から始まる$(A, B)$、すべてを繰り返します$N$日々。 毎日、最大化するか最小化するかに応じて分岐し、補助更新については両方の選択肢を試します。 これにより、深さのあるバイナリ決定木が効果的に作成されます。$N$ここで、各ノードは値のペアを表します。 

状態をメモ化しても$(X, Y, i)$、値$X$そして$Y$大きさは指数関数的に増加し、基本的に制限がないため、状態の繰り返しは有効には発生しません。 可能な状態の数は依然として指数関数的です$N$、これは完全に不可能になります。 

重要な観察は、変換の構造が線形であることです。各ステップがペアを置き換えます。$(X, Y)$どちらかで$(X+Y, X)$または$(X+Y, Y)$。 これは構造的にはフィボナッチ様の漸化式の寄与の伝播と同じです。 それぞれの最終値は、初期値の線形結合として表現できます。$A$そして$B$ここで、係数は文字列の接頭辞と行われた選択にのみ依存します。 

これは、プロセス全体を、最適なプレイの下で各初期値が最終結果に何回寄与するかを維持するように再構成できることを意味します。 実際の値を追跡する代わりに、文字列のセグメントにわたる変換行列を追跡し、セグメント ツリーを使用して更新時にそれらを効率的に結合します。 各ノードは、セグメントの結果を 2 x 2 変換として保存します。$(A, B)$は最適なプレイの下で最終値にマップされ、セグメント フリップは 2 人のプレーヤーの役割の交換に対応し、これはこの変換の部分の反転または交換に対応します。 

これにより、問題は、完全な指数関数プロセスの再計算から、範囲反転時のコンポーザブル セグメント変換の維持まで軽減されます。

 ## アルゴリズムのチュートリアル

 1. 毎日を、ペアをマッピングする変換を適用するものとして解釈します$(X, Y)$どちらかに$(X+Y, X)$または$(X+Y, Y)$。 バイナリ文字列によって、この選択のどちら側が最大化または最小化とみなされるかが決まります。 これにより、2 次元状態の小さな演算子として毎日をモデル化することができます。 
2. 入力ペアをマッピングする関数として日のセグメントの影響を表現します。$(A, B)$そのセグメント内のすべての決定を最適に解決した後、最終値に設定されます。 この関数は、どのように貢献したかを記録する小さな構造としてエンコードできます。$A$そして$B$伝播する。 
3. バイナリ文字列上にセグメント ツリーを構築します。ここで、各ノードはその区間の結合された変換を格納します。 リーフ ノードは 1 日に対応し、変換は文字が 0 か 1 かによって直接決定されます。 
4. 隣接する 2 つのセグメントのマージ操作を、それらの変換の合成として定義します。 この構成は、セグメントを次々と実行することを反映しているため、右側のセグメントは左側のセグメントの結果に作用します。 
5. レンジ反転の場合、ビットを反転すると、その日にどのプレイヤーが行動するかが入れ替わることを観察します。これは、リーフ変換における最大化と最小化の役割を交換することに対応します。 最初から再計算する代わりに、セグメントを遅延マークし、保存されている変換を交換します。 
6. 各更新後に、セグメント全体をクエリします。$[1, N]$セグメントツリーの。 結果として適用される変換は、$(A, B)$最終的な答えを与え、それをモジュロで出力します$998244353$。 

### なぜ効果があるのか

 このプロセスは基本的にローカルな線形変換の構成であり、最大化または最小化という役割のみに依存する固定の 2 状態の決定に毎日貢献します。 中間の選択は現在のペアを超える外部値に依存しないため、日のどのセグメントも単一の結合された変換として機能します。$(X, Y)$。 変換の構成は結合的であるため、セグメント ツリーはグローバルな一貫性を正確に維持します。 範囲反転は、ローカル決定の解釈を変更するだけであり、これは、影響を受ける各リーフ内の役割を交換することと同等であり、再構成の正確さを維持します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

class Node:
    __slots__ = ("a", "b", "flip")
    def __init__(self):
        self.a = 0
        self.b = 0
        self.flip = False

def merge(left, right):
    res = Node()
    res.a = (left.a + right.a) % MOD
    res.b = (left.b + right.b) % MOD
    return res

def apply_flip(node):
    node.a, node.b = node.b, node.a
    node.flip ^= True

class SegTree:
    def __init__(self, s):
        self.n = len(s)
        self.size = 1
        while self.size < self.n:
            self.size *= 2
        self.data = [Node() for _ in range(2 * self.size)]
        self.lazy = [False] * (2 * self.size)

        for i, c in enumerate(s):
            if c == '1':
                self.data[self.size + i].a = 1
            else:
                self.data[self.size + i].b = 1

        for i in range(self.size - 1, 0, -1):
            self.data[i] = merge(self.data[2 * i], self.data[2 * i + 1])

    def push(self, i):
        if self.lazy[i]:
            for c in (2 * i, 2 * i + 1):
                apply_flip(self.data[c])
                self.lazy[c] ^= True
            self.lazy[i] = False

    def range_flip(self, l, r, i, nl, nr):
        if r < nl or nr < l:
            return
        if l <= nl and nr <= r:
            apply_flip(self.data[i])
            self.lazy[i] ^= True
            return
        self.push(i)
        mid = (nl + nr) // 2
        self.range_flip(l, r, 2 * i, nl, mid)
        self.range_flip(l, r, 2 * i + 1, mid + 1, nr)
        self.data[i] = merge(self.data[2 * i], self.data[2 * i + 1])

    def query(self):
        root = self.data[1]
        return (root.a + root.b) % MOD

def solve():
    N, A, B = map(int, input().split())
    S = list(input().strip())
    Q = int(input())

    st = SegTree(S)

    for _ in range(Q):
        l, r = map(int, input().split())
        st.range_flip(l - 1, r - 1, 1, 0, st.size - 1)
        print(st.query())

if __name__ == "__main__":
    solve()
```セグメント ツリーには、最初のペアからの寄与が各セグメントを通じてどのように伝播するかが格納されます。 各リーフは、その日がどちらの側に有利かを表し、マージ ステップでは、効果を合成することによって独立したセグメントを結合します。 遅延伝播は、ノードを再構築するのではなく、ノードの解釈を交換することによって範囲反転を処理します。 

微妙な点は、ツリー内のインデックスが 0 から始まるため、すべてのクエリが問題の 1 から始まるインデックスから変換されることです。 もう 1 つの重要な点は、フリップがツリーの下に正しく伝播する必要があることです。 そうしないと、部分的なセグメントが矛盾した状態を結合することになります。 

## 実用的な例

 小さな文字列を考えてみましょう`S = 101`初期値あり$A = 2, B = 3$。 毎日の後、どちらの側がアクティブであるかに応じて、変換によってさまざまな貢献が蓄積されます。 セグメント ツリーはこれを累積係数として表します。 

| ステップ | セグメント | ノード状態 (a, b) |
 | --- | --- | --- |
 | 1 | "1" | (1, 0) |
 | 2 | "0" | (0, 1) |
 | 3 | "1" | (1, 0) |
 | マージ(1,2) | 「10」 | (1, 1) |
 | マージ(すべて) | 「101」 | (2, 1) |

 これは、両方の初期値からの寄与が単一の線形結合にどのように伝播するかを示しています。 

次に、文字列全体が回転するフリップを考えてみましょう。`101`の中へ`010`。 寄与の役割は各リーフで入れ替わり、中間係数が変わります。 再計算後、セグメント ツリーは異なる最終ペアを生成します。これは、構造がグローバル フリップに対してどれほど敏感であるか、また遅延伝播が必要な理由を示しています。

 ## 特殊なケース

 重要なエッジ ケースは、重複する間隔で文字列全体が複数回反転される場合です。 たとえば、反転`[1, N]`最初から再計算することなく、一貫した 2 つの状態の間で最終変換を繰り返し行う必要があります。 セグメント ツリーは、各ノードでブール フラグを切り替えることでこれを処理し、反転を繰り返すと以前の構成が正しく復元されるようにします。 

もう 1 つのエッジケースは次のような場合です$N = 1$。 構造全体が 1 つの変換に折りたたまれ、更新のたびにそのリーフが直接反転されます。 結果は、その 1 日が最大化プレーヤーによって制御されているか、最小化プレーヤーによって制御されているかを即座に反映する必要があります。これは、マージ ロジックに依存せずにリーフの更新が正しく処理されるかどうかをテストします。
