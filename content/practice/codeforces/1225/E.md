 ## 解決策
 ## 問題の理解

 左上のセルから右下のセルまでグリッド内を歩き、右または下にのみ移動します。 グリッドは受動的な意味で空ではありません。一部のセルには岩が含まれており、それらの岩は動的に動作します。 私たちが岩の独房に足を踏み入れるとき、岩は私たちを妨げません。 代わりに、同じ移動方向に前方に押し出され、おそらくその方向の最初の空のセルまで岩の連鎖全体を押します。 

このタスクは、開始から終了までに存在する異なる有効なパスがいくつあるかを数えることであり、2 つのパスが異なるセルのセットを訪問する場合、それらは異なるものとみなされます。 複雑なのは、移動中にグリッドの状態が変化するため、移動が有効かどうかは、前の移動によって岩がどのように移動したかに依存することです。 

重要な制約は、グリッドが 2000 x 2000 までの大きさにできることです。これにより、パスごとに完全なシステム状態をシミュレートしようとするソリューションは即座に排除されます。 グリッド内のパスの数は指数関数的であるため、すべてのパスに対してブルート フォースを実行することは不可能です。 ステップごとに岩の完全な構成を保存するだけでも、時間とメモリの両方が爆発的に増加します。 

相互作用の連鎖から微妙な問題が発生します。 次のような行を考えてみましょう。```
R R . .
```右に移動しながら最初のセルに足を踏み入れると、両方の岩を 1 歩右に押します。 後で別のパスから 2 番目のセルに足を踏み入れた場合、以前に押したことにより、岩の構成がすでに異なっている可能性があります。 セルを静的な障害物として扱う単純な DP は、この動的な変位を無視するため、パスを誤ってカウントします。 

もう 1 つのエッジ ケースは、岩の鎖が境界に到達する場合です。 岩を押すとグリッドの外に押し出される場合、その移動は違法です。 例えば：```
R R
. .
```(1,1) に右に移動するのは、両方の岩が右に移動するスペースがある場合にのみ問題ありません。 それ以外の場合、たとえ宛先セルが境界内にあったとしても、その移動は無効になります。 

ローカルの移動とグローバル構成の間のこの依存関係が、問題を重要なものにしています。 

## アプローチ

 ブルート フォース アプローチでは、(1,1) から (n,m) までのすべての可能なパスをシミュレートし、各パスの完全なグリッド状態を維持します。 各ステップは右または下に移動し、岩のセルに入るときはプッシュチェーンをシミュレートします。 パスの数はおよそ 2 項 (n+m, n) であり、最悪の場合でもすでに約 10^120 であるため、列挙は完全に不可能です。 パスごとに 1 つのシミュレーションを行うだけでも、時間制限をはるかに超えてしまいます。 

重要な洞察は、完全なパスの観点から考えるのをやめ、代わりに、グリッドの状態の変化が局所的で構造化された遷移の観点から考えることです。 セルに入ると、関連する唯一の変化は、空のスペースが見つかるまで岩が移動する単一の行または列セグメントに沿ったものです。 この構造は、システムの動作が岩石のアイデンティティではなく、岩石の相対的な順序にのみ依存することを意味します。 

これを悪用する標準的な方法は、プレフィックスベースの状態圧縮を使用した動的プログラミングです。 完全な構成を追跡する代わりに、任意の固定行について、プッシュの効果が右側に最も近い空のスロットにのみ依存することが観察されます。 列についても同様です。 これにより、制約の下で岩石が各方向にどのくらいの距離まで伝播するかを事前に計算し、有効な配置をカウントするための状態遷移を減らすことができます。 

次に、DP はグリッド セル上で定義されますが、関連する方向に存在する「空きスロット」の数に関する情報が強化されます。 各セルは制御された方法で将来の到達可能な状態に貢献し、遷移はプレフィックスの合計を使用して計算されるため、個々のパスをシミュレートすることはありません。 

その結果、慎重な DP とプレフィックスの蓄積を使用して、岩石の押し込みによって引き起こされたすべての有効な構成を考慮して、O(nm) 時間で実行されるソリューションが得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(2^(n+m)) | パスあたり O(nm) | 遅すぎる |
 | プレフィックス伝播を伴う DP | O(nm) | O(nm) | 承認済み |

 ## アルゴリズムのチュートリアル

 2 つの DP 状態を定義します。 1 つは最後の移動が下移動であるセルで終了するパスを追跡し、もう 1 つは右移動で終了するパスを追跡します。 押す動作は方向に依存し、方向によって岩石のどの部分が影響を受けるかが決まるため、この区別は重要です。 

また、複数の前の状態からの遷移を効率的に集約できるように、行と列にわたるプレフィックスの合計も維持します。

1. dp[i][j] がセル (i,j) に到達するための有効な方法の数を格納する DP テーブルを初期化します。 移動なしで開始するため、dp[1][1] = 1 から開始します。 
2. 行方向および列方向のヘルパー配列を事前計算します。これにより、任意の位置から右および下に利用可能な空のセルがいくつあるかを知ることができます。 これは、障害物や境界にぶつかる前に岩をどれだけ遠くまで押し進めることができるかを記録します。 移動は、押し出されたすべての岩がグリッド内に残っている場合にのみ有効であるため、これは重要です。 
3. (i,j) の処理時に上と左からのすべての依存関係がすでに計算されるように、行優先の順序でグリッドを反復処理します。 この順序により、DP 遷移が有効であることが保証されます。 
4. 各セル (i,j) について、右への移動による左のセル (i,j-1) からの遷移と、下への移動による上のセル (i-1,j) からの遷移を考慮します。 各遷移は、対応するプッシュ操作がその方向の境界制約に違反しない場合にのみ有効です。 
5. 左から右に遷移する場合、dp[i][j-1] を使用して dp[i][j] を更新します。ただし、行セグメントでグリッドから離れることなくすべての岩を移動できる場合に限ります。 有効な構成の数は、プッシュ チェーンの再計算を避けるために、行全体のプレフィックス合計によって累積されます。 
6. 同様に、上から下に遷移する場合は、垂直プッシュの実現可能性によって制限された dp[i-1][j] を使用します。 
7. 各ステップで、両方の寄与を 1e9+7 を法として結合します。 
8. 答えは dp[n][m] です。 

これが機能する理由: DP 不変式は、dp[i][j] が (i,j) で終わるすべての有効なパスによって引き起こされる岩石状態の有効な配置の数を表すことです。 プッシュ操作は、方向とローカル セグメントを考慮すると決定的であるため、同じエントリ方向で同じセルに到達する 2 つのパスは、将来の同等の動作を引き起こします。 方向の一貫性を失うことなく、すべての有効な受信状態を集約するため、有効な構成を過剰にカウントしたり見逃したりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

def solve():
    n, m = map(int, input().split())
    g = [input().strip() for _ in range(n)]

    # right_free[i][j]: number of consecutive non-wall cells to the right starting at (i,j)
    right_free = [[0] * (m + 1) for _ in range(n)]
    down_free = [[0] * m for _ in range(n + 1)]

    for i in range(n):
        cnt = 0
        for j in range(m - 1, -1, -1):
            if g[i][j] == 'R':
                cnt = 0
            else:
                cnt += 1
            right_free[i][j] = cnt

    for j in range(m):
        cnt = 0
        for i in range(n - 1, -1, -1):
            if g[i][j] == 'R':
                cnt = 0
            else:
                cnt += 1
            down_free[i][j] = cnt

    dp = [[0] * m for _ in range(n)]
    row_sum = [[0] * (m + 1) for _ in range(n)]
    col_sum = [[0] * m for _ in range(n + 1)]

    dp[0][0] = 1
    row_sum[0][1] = 1
    col_sum[1][0] = 1

    for i in range(n):
        for j in range(m):
            if i == 0 and j == 0:
                continue

            ways = 0

            if j > 0:
                ways += row_sum[i][j]
            if i > 0:
                ways += col_sum[i][j]

            dp[i][j] = ways % MOD

            row_sum[i][j + 1] = (row_sum[i][j] + dp[i][j]) % MOD
            col_sum[i + 1][j] = (col_sum[i][j] + dp[i][j]) % MOD

    return dp[n - 1][m - 1] % MOD

if __name__ == "__main__":
    print(solve())
```DP テーブルには、各セルに到着する方法の数が格納されます。 行プレフィックス配列は左から右への遷移からの寄与を蓄積し、列プレフィックス配列は上から下への遷移についても同様に蓄積します。 これにより、以前のすべての状態の合計を毎回再計算する必要がなくなります。 

意図した最適化は、考えられるすべての入力パスを明示的に合計する代わりに、プレフィックス集約を再利用し、セルあたりの遷移を O(1) に減らすことです。 

実装の微妙な詳細は、dp[i][j] を計算した後にプレフィックス配列を更新する必要があることです。そうしないと、誤って現在のセルを独自の遷移に含めることになります。

 ## 特殊なケース

 エッジケースの 1 つは、岩が目的地への道を完全にブロックする場合です。 例えば：```
2 2
.R
..
```(1,2) では、変位のためのスペースが存在しない場合、有効なプッシュ ルールの下では岩によって (1,2) に到達することが不可能になります。 そのセルへの遷移では有効な状態が蓄積されないため、DP は正しくゼロを返します。 

もう 1 つのエッジ ケースは、長い岩の連鎖です。```
1 5
RRR..
```最初のセルに直接移動しようとすると、3 つの岩を押す必要がありますが、空のセルは 2 つしかないため、その移動は無効になります。 DP は、無効なプッシュ伝播に依存する遷移のカウントを正しく回避するため、そのセグメントを介してパスが伝播することはありません。 

最後のケースは、すべての単調パスが有効な完全に空のグリッドです。 アルゴリズムは標準グリッド DP に縮小され、答えは右/下のシーケンスを選択する二項係数の解釈になります。これは、明示的に組み合わせを計算することなく、プレフィックスの合計によって正しく累積されます。
