 ## 解決策
 ## 問題の理解

 大文字と小文字の両方が表示されるラテン文字の文字列が与えられます。 タスクは、文字列がパングラムであるかどうかを判断することです。つまり、`'a'`に`'z'`大文字と小文字の違いを無視して、文字列内のどこかに少なくとも 1 回出現します。 

より具体的に言えば、単一の文字シーケンスをスキャンし、存在する一連の個別の文字が英語のアルファベットの 26 文字すべてをカバーしているかどうかを確認したいと考えています。 大文字と小文字は関係ないので、`'A'`そして`'a'`カバレッジを確認する目的で同じシンボルとして扱われます。 

入力サイズは小さく、最大 100 文字です。 これにより、文字列を 1 回通過する以上の最適化の必要性が即座に排除されます。 たとえ$O(n \cdot 26)$または$O(n^2)$このアプローチは技術的には問題ありませんが、自然な解決策は、一定の追加メモリを使用した線形時間です。 

主なエッジケースは、文字の正規化方法と完全性のチェック方法に由来します。 単純な間違いは、大文字と小文字を別の文字として扱うことであり、次のような文字列を誤ってマークしてしまいます。`"TheQuickBrownFoxJumpsOverTheLazyDog"`大文字と小文字が正規化されていない場合は、すべての文字が含まれていないことになります。 もう 1 つの微妙な問題は、文字列の長さによってカバレッジが保証されると誤って想定していることですが、繰り返しは多様性を意味しないため、これは誤りです。 

## アプローチ

 問題を解決する強引な方法は、からの手紙ごとに、`'a'`に`'z'`、文字列全体をスキャンして、その文字が小文字で表示されるか大文字で表示されるかを確認します。 これはパングラムの定義を直接検証するため、正しいです。 ただし、26 文字ごとに最大 100 文字をスキャンする可能性があり、最大 2600 文字のチェックが行われることになります。 これは実際にはすでに些細なことですが、その構造は必要なものに比べて非効率的です。 

より良いアプローチは、視点を逆転させることです。 「各文字が文字列に出現するか?」と尋ねる代わりに、文字列を 1 回処理して、どの文字が出現したかを記録します。 各文字は小文字に正規化され、セットに挿入されるか、サイズ 26 のブール配列でマークされます。最後に、26 の位置すべてがマークされているかどうかを確認するだけです。 これが機能するのは、関心のあるプロパティがサイズ 26 の固定ユニバースのメンバーシップであるため、繰り返しスキャンする必要がないからです。 

重要な観察は、アルファベットのサイズが一定であるということです。 関心のある領域が固定されており小さいことが認識されると、問題を単一パスの累積問題に減らすことができます。

 ## アルゴリズムのチュートリアル

 文字列を 1 文字ずつ処理し、どの文字が出現したかを追跡する構造を維持します。 

1. ブール配列を初期化する`seen`サイズは 26、すべて false に設定されます。 各インデックスはからの文字に対応します。`'a'`に`'z'`。 これにより、メンバーシップを継続的に追跡できるようになります。 
2. 入力文字列内のすべての文字を反復処理します。 各文字を小文字に変換して、大文字と小文字のバージョンが同じインデックス スペースにマップされるようにします。 この正規化により、大文字と小文字に基づいて文字を二重にカウントすることがなくなります。 
3. 文字のインデックスを次のように計算します。`ord(c) - ord('a')`。 このマップは`'a'`0まで、`'b'`1 まで、以下同様に最大`'z'`25時。マーク`seen[index] = true`。 これは、その手紙が少なくとも 1 回遭遇したことを記録します。 
4. すべての文字を処理した後、次のすべてのエントリが`seen`それは本当です。 いずれかの位置が false のままである場合、文字列から少なくとも 1 つの文字が欠落しているため、その文字列はパングラムではありません。 
5. 出力`"YES"`すべてのエントリが true の場合、そうでない場合は出力`"NO"`。 

正確さは、各文字が独立して扱われ、頻度ではなく、その存在のみが重要であるという事実にかかっています。 

### なぜ効果があるのか

 このアルゴリズムは、最初の k 文字を処理した後、次の不変条件を維持します。`seen[i]`インデックス i に対応する文字がそれらの k 文字に出現した場合にのみ true です。 この不変条件は、すべての文字が 1 つのインデックスだけを更新し、一度設定された値をクリアする操作は存在しないため成り立ちます。 スキャンの終了時点では、状態は文字列内のすべての文字のセットを正確に表しているため、すべてのエントリが true であるかどうかを確認することは、文字列に 26 文字すべてが少なくとも 1 回含まれているかどうかを確認することと同じです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    s = input().strip()

    seen = [False] * 26

    for c in s:
        if c.isalpha():
            idx = ord(c.lower()) - ord('a')
            seen[idx] = True

    if all(seen):
        print("YES")
    else:
        print("NO")

if __name__ == "__main__":
    solve()
```このソリューションは長さと文字列を読み取りますが、正確さのために長さは厳密には必要ありません。 コア ロジックは、レター カバレッジを追跡する固定サイズのブール配列です。 

への呼び出し`lower()`大文字と小文字を区別しない処理を保証します。 の`all(seen)`check は、すべてのアルファベット文字が少なくとも 1 回出現する必要があるという要件を直接翻訳したものです。 

微妙な点の 1 つは、周波数には決して依存せず、存在のみに依存しているということです。 これが、カウンター配列の代わりにブール配列で十分である理由です。

 ## 特殊なケース

 微妙なエッジケースは、大文字と小文字の区別です。 アルゴリズムが文字を正規化しない場合、`"AaBbCc...Zz"`大文字と小文字は異なるインデックスにマッピングされるため、多くの文字が欠落しているように誤って表示されます。 私たちのアプローチでは、`lower()`両方のフォームが同じスロットにマップされるようにするため、`"A"`そして`"a"`どちらもインデックス 0 を設定します。 

もう 1 つのエッジ ケースは、次のような重複の多い入力です。`"aaaaaaaaaaaaaaaaaa"`。 ここでは、1 つのインデックスのみがマークされます。 ブール配列は、更新を繰り返しても正確さが変わらないため、オーバーカウントがアルゴリズムを誤解させるのを防ぎます。 

最後のエッジケースは、次のような最小限のカバレッジ入力です。`"abcdefghijklmnopqrstuvwxyz"`などの 1 文字が欠けている場合と比較して、`"abcdefghijklmnopqrstuvwxy"`。 最初のケースでは、すべてのインデックスが 1 回だけ入力され、結果は次のようになります。`"YES"`。 2 番目では、インデックス 25 は false のままで、最終チェックでは正しく次の結果が得られます。`"NO"`。
