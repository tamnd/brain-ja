 ## 解決策
 ## 問題の理解

 ここでは、0 から 9 までのインデックスが付けられたちょうど 10 室の部屋がある非常に小さなホテルをシミュレートしています。各部屋は空であるか、ちょうど 1 人のゲストが占有している可能性があります。 時間の経過とともに、ゲストは 2 つの入り口のいずれかから到着するか、特定の部屋から退出します。 

到着時の行動が重要なルールです。ゲストが左側の入り口から入った場合、常に現在空いている一番左の部屋を利用します。 右の入り口から入った場合、彼らは常に現在空いている一番右の部屋を取る。 出発は明示的です。数字 x が表示されると、現在部屋 x を占有しているゲストが退去し、再び空になります。 

入力は、これらのイベントの時系列シーケンスです。 それらを順番にシミュレーションし、10部屋の占有状態を維持しなければなりません。 最終出力は 10 文字のバイナリ文字列で、各位置はその部屋が最後に占有されているかどうかを示します。 

イベント数の点では制約が大きく、最大 100,000 操作です。 これは、どのソリューションでも各イベントを一定時間で処理する必要があることをすぐに示します。 状態空間は小さい (わずか 10 部屋) ため、メモリや構造のサイズに制約されることはありません。10 × 100,000 程度に増加するイベントごとの繰り返しのスキャン作業を回避するだけで済みます。これはまだ問題ありませんが、より複雑または間接的なものは不要になります。 

単純な間違いは、複雑なデータ構造を使用して割り当てを再構築したり、「誰がどのポジションにいるのか」を動的に追跡したり、注意深く構造化せずにイベントごとにフルスキャンを使用して最も近い空き部屋を再計算しようとしたりすることから発生することがよくあります。 10 個の位置のスキャンが一定であっても、不必要なロジックを繰り返したり、出発時に状態更新を誤って管理したりすると、不正確な結果が生じる可能性があります。 

微妙なエッジケースの 1 つは、出発後に部屋を再利用することです。 たとえば、部屋が解放され、後で別の到着者が近接ルールに基づいてその部屋を再利用する必要がある場合、アルゴリズムはその部屋をすぐに利用可能であると正しく再再検討する必要があります。 

もう 1 つの潜在的な落とし穴は、出発が到着順ではなく部屋のインデックスに直接依存するという誤解です。 間違ったアプローチでは、入口ごとに列に並んでゲストを追跡しようとする可能性がありますが、それは不必要であり、間違いが発生しやすくなります。 

## アプローチ

 システムは非常に小さいため、単純なシミュレーションが機能します。 各部屋が占有されているかどうかを表すサイズ 10 の配列を維持します。 到着ごとに、左から右または右から左にスキャンして、最初の空のスロットを見つけて割り当てます。 出発のたびに、指定された部屋を空としてマークするだけです。 

10 個の要素のスキャンは一定時間であるため、この総当たりアプローチは実際にはすでに最適です。 100,000 回の操作があっても、実行するのはせいぜい 1,000,000 回程度の基本的なチェックであり、これは些細なことです。 

両側から最も近い空き部屋に対して個別の構造を維持することで「最適化」を試みることもできますが、10 を超える位置の再計算はすでに無視できるものであるため、複雑さが増すだけでメリットはありません。 

重要な洞察は、状態空間が固定されており小さいため、直接シミュレーションが意図された解決策であることを認識することです。 この問題は、アルゴリズムの最適化ではなく、慎重な実装をテストするように設計されています。

 ## アルゴリズムのチュートリアル

 私たちはリストを管理しています`rooms`サイズは 10、最初はすべてゼロ。 

### ステップ

 1. 配列を初期化する`rooms`長さ 10 で、すべての値が 0 に設定されます。 

これは、開始時にすべての部屋が空であることを表します。 
2. 入力シーケンス内の各文字を順番に処理します。 

正確かどうかは、正確な時系列順序を維持するかどうかにかかっています。 
3. キャラクターが`'L'`、最初の空の部屋が見つかるまで、部屋 0 から上に向かってスキャンします。 

占有として割り当てて、すぐに停止します。 

これが機能する理由は、ルールが左端の使用可能なスロットを明示的に優先するためです。 
4. キャラクターが`'R'`、最初の空の部屋が見つかるまで、部屋 9 から下に向かってスキャンします。 

占有として割り当てて、すぐに停止します。 

これにより、対称的な右端の選択ルールが適用されます。 
5. 文字が次の数字の場合`'0'`に`'9'`、それを整数 x に変換し、マークします。`rooms[x] = 0`。 

これは出発を直接モデル化し、前の状態に関係なく指定された部屋を解放します。 
6. すべてのイベントを処理した後、配列を 0 と 1 の文字列として出力します。 

### なぜ効果があるのか

 あらゆる段階で、`rooms[i]`部屋かどうかを正確に反映します`i`以前のすべてのイベントを処理した後、占有されます。 到着時は常に必要な方向で最初に利用可能な部屋を選択し、出発時は他のスロットに影響を与えることなく特定のスロットのみを空けます。 イベントは現在の占有状態以外には依存しないため、この不変条件を維持することで最終構成の正確性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n = int(input().strip())
    s = input().strip()

    rooms = [0] * 10

    for c in s:
        if c == 'L':
            for i in range(10):
                if rooms[i] == 0:
                    rooms[i] = 1
                    break
        elif c == 'R':
            for i in range(9, -1, -1):
                if rooms[i] == 0:
                    rooms[i] = 1
                    break
        else:
            idx = ord(c) - ord('0')
            rooms[idx] = 0

    print(''.join(map(str, rooms)))

if __name__ == "__main__":
    main()
```実装はシミュレーション モデルに直接に従います。 唯一の微妙な部分は、正しい方向のリニア スキャンで到着を処理することです。 配列サイズは 10 に固定されているため、イベントごとに一定時間になります。 

数字の処理は ASCII 変換に依存しているため、解析のオーバーヘッドが回避され、各出発点が部屋のインデックスに直接マッピングされることが保証されます。

## テストケース```python
import sys, io

def solve(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n = int(input().strip())
    s = input().strip()

    rooms = [0] * 10

    for c in s:
        if c == 'L':
            for i in range(10):
                if rooms[i] == 0:
                    rooms[i] = 1
                    break
        elif c == 'R':
            for i in range(9, -1, -1):
                if rooms[i] == 0:
                    rooms[i] = 1
                    break
        else:
            rooms[ord(c) - 48] = 0

    return ''.join(map(str, rooms))

 ## 特殊なケース

 重要なエッジケースの 1 つは、同じ部屋に人が入ったり空になったりを繰り返すことです。 インプットを考慮する`L0L`。 最初の到着後、部屋 0 は満室になります。 数字`0`再び解放し、最後に`L`ルーム 0 を左端の利用可能なスロットとして正しく再利用する必要があります。 すべての到着が常に配列の先頭からスキャンされ、解放されたスロットがすぐに表示されるため、アルゴリズムはこれを自然に処理します。 

もう 1 つのエッジ ケースは、交互に到着し、両端の占有率が常に反転する場合です。`LRLRLR...`。 システムは、状態が古いために空きルームを「スキップ」してはなりません。 各ステップで可用性が直接再計算されるため、`rooms`、履歴的な仮定は行われないため、再利用には常に現在の構成が反映されます。 

3 番目のケースは、満室の後に出発するケースです。 すべての部屋が満室になった場合でも、数字イベントによりすぐに 1 つの部屋が解放され、次の到着者は更新された状態に基づいて正しく選択する必要があります。 すべての操作で同じ共有配列が更新されるため、可用性の更新を遅らせる可能性のある隠れた状態はありません。
