 ## 解決策
 ## 問題の理解

 私たちは、ドルで表された一定の金額と、スーパーマーケットで買える砂糖のリストを与えられます。 各オプションにはドルとセントで書かれた価格が付いています。 Caisa は、砂糖を 1 種類だけ選択し、使えるお金で支払い、必要以上のお金がある場合はおつりを受け取ることができます。 異常な詳細は、店がセントではなくお菓子の釣銭の一部を返し、彼が受け取るお菓子の数が小銭のセント数と全く同じであることです。これは、セントが常に正規化されており、100 セントを 1 ドルに換算した後に最大でも 99 セントが残るという事実によって暗黙的に上限が設定されています。 

課題は、カイサが買える砂糖の種類を 1 つ選択し、お釣りで戻ってくるお菓子の数を最大にすることです。 手頃な価格の砂糖の種類がない場合、答えは -1 です。 

入力サイズは小さく、最大でも 100 個のオプションです。 これにより、パフォーマンスに関する懸念が即座に排除されます。 すべての項目に対する二重ループさえも簡単です。 リストの線形スキャンで十分です。 

すべてのアイテムが合計で高すぎる場合、微妙なエッジケースが現れます。 たとえば、カイサが 5 ドルを持っていて、すべての砂糖が少なくとも 6 ドルかかる場合、購入は不可能であり、答えは -1 でなければなりません。 もう 1 つのケースは、複数の商品が手頃な価格であるが、1 つの商品の価格が低く、別の商品の方がより多くの小銭が得られる場合です。 最適な選択は、最も安い商品ではなく、差し引いた残りをセント単位で最大化する商品です。 

単純なアプローチを混乱させる可能性のある具体例としては、変化を最大化する代わりに最小のコスト項目を選択することが挙げられます。 Caisa が 10 ドルを持っているとします。 1 つの商品の価格は 9 ドル 70 セント、もう 1 つの商品の価格は 7 ドル 0 セントです。 1 つ目では 30 セントのお釣りしか得られませんが、2 つ目では 300 セントのお釣りが得られます。これは 3 ドル 0 セントに相当するため、お菓子は 0 になります。 残りをセント単位で慎重に計算しないと、誤って比較してしまいがちです。 

## アプローチ

 制約から自然に総当たりの解決策が導き出されます。 各砂糖の種類を反復処理し、Caisa がそれを買う余裕があるかどうかを確認し、変化をセント単位で計算し、最大の残りを追跡します。 項目が最大 100 個あるため、算術チェックは最大 100 回であり、無視できる程度です。 

重要な観察は、問題は完全に各項目に局所的なものであるということです。 選択肢間の相互作用や組み合わせ構造はなく、複数の選択肢にわたって最適化する必要もありません。 各砂糖の種類は独立して候補値、つまり利用可能なお金からその価格を差し引いた後に何セント残るかを生成します。 

浮動小数点推論を避けるために、すべてをセントに変換します。 Caisa が s ドルを持っている場合、それは 100 セントになります。 各アイテムの価格は 100xᵢ + yᵢ セントです。 コストが利用可能な金額を超える場合はスキップします。 それ以外の場合は、剰余を計算し、最良の答えを更新します。 

入力サイズが一定の制限があり、小さいため、総当たりアプローチはすでに最適化されています。

 | --- | --- | --- | --- |
 | ブルートフォース | O(n) | お(1) | 承認済み |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 100 * s を計算して、利用可能なお金をセントに変換します。 これにより、すべての比較が単一の単位系で行われるようになり、ドルとセントの間のあいまいさがなくなります。 
2. 変数 best を -1 に初期化します。 これにより、すべての手頃なオプションの中で最大の小銭が保管されます。 
3. 砂糖の種類ごとに、100 * xᵢ + yᵢ を使用して価格をセントに変換します。 これにより、予算と同じ単位で同等の数量が得られます。 
4. 価格が利用可能金額を超える場合は購入できないため、このオプションをスキップしてください。 
5. それ以外の場合は、変更を (予算 - 価格) として計算します。 お菓子は正規化後の残りの変化のセントに相当するため、モジュロ 100 を使用してセントの部分を抽出します。 
6. この値が現在の最良値よりも大きい場合は、最良値を更新します。 
7. すべての項目を処理した後、最適なものを出力します。 有効な項目が見つからなかった場合、最適値は -1 のままです。 

### なぜ効果があるのか

 各砂糖の種類は、購入後に残ったセント数を表す独立した候補値を 1 つだけ生成します。 Caisa は正確に 1 つのアイテムを購入するため、問題は独立した評価の有限セットの中から最大値を選択することになります。 すべてをセントに変換すると、順序が維持され、精度が失われることはありません。 このアルゴリズムは、これまでに処理されたすべての手頃な価格の商品の中で見られる最大の小銭セントが常に最良であるという不変条件を維持するため、最終的な価値は全体的に最適になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n, s = map(int, input().split())
    budget = s * 100

    best = -1

    for _ in range(n):
        x, y = map(int, input().split())
        cost = x * 100 + y

        if cost <= budget:
            change = budget - cost
            sweets = change % 100
            if sweets > best:
                best = sweets

    print(best)

if __name__ == "__main__":
    main()
```このソリューションでは、比較の一貫性を保つために、まず予算をセント単位に正規化します。 また、各項目は計算が行われる前にセントに変換されるため、単位の混在による間違いが回避されます。 

重要な実装の詳細は、残りの変更でモジュロ 100 を使用することです。 お菓子はフルドル正規化後の残り額のセントに相当するので、100で割った余りだけが問題となります。 その値のみを追跡すると、不必要な計算が回避されます。 

エッジ処理は暗黙的です。コスト <= 予算を満たすアイテムがない場合は、-1 から更新しないのが最善です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各種類の砂糖は定数時間演算で 1 回処理されます。 
| スペース | お(1) | 少数の整変数のみが使用されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, s = map(int, input().split())
    budget = s * 100

    best = -1

    for _ in range(n):
        x, y = map(int, input().split())
        cost = x * 100 + y
        if cost <= budget:
            best = max(best, (budget - cost) % 100)

    return str(best)

# provided sample
assert run("5 10\n3 90\n12 0\n9 70\n5 50\n7 0\n") == "50"

# minimum case, no affordable item
assert run("1 1\n2 0\n") == "-1"

# exact budget match, zero change
assert run("2 5\n5 0\n3 0\n") == "0"

# multiple options, best is not cheapest
assert run("3 10\n9 99\n9 50\n8 0\n") == "50"

# all affordable, check modulo behavior
assert run("3 10\n1 10\n1 20\n1 30\n") == "90"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 手頃な価格のアイテムがない | -1 | 不可能に対する正しい対処 |
 | 完全一致 | 0 | 変更ゼロの場合 |
 | 混合価格 | 50 | コストではなく最大剰余による選択 |
 | すべて手頃な価格 | 90 | 正しいモジュロ抽出 |

 ## 特殊なケース

 エッジケースの 1 つは、すべてのアイテムが高すぎる場合です。 その状況では、ループは初期値 -1 を更新せず、出力は -1 のままになります。 たとえば、予算が 100 セントでアイテムのコストが 200 セントの場合、チェックは失敗し、変更の計算は実行されず、センチネルは正しく保存されます。 

もう 1 つのケースは、複数のアイテムが手頃な価格であるにもかかわらず、同じ残りが生じる場合です。 たとえば、2 つのアイテムが両方とも 30 セント残る場合があります。 アルゴリズムは最大値のみを追跡し、等しい値によって結果が変更されないため、これを自然に処理します。 

最後のケースは、お釣りが 100 セントの倍数である場合です。 その場合、モジュロ演算の結果は 0 であり、ゼロ スイーツを正しく表します。
