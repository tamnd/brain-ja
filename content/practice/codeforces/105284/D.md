 ## 解決策
 ## 問題の理解

 与えられた固定の外部データベースは、アニメ タイトルの長い順序リストと考えることができ、各タイトルは 1 から始まる特定の行番号にあります。実際のリストは入力の一部ではありません。 代わりに、受信したすべてのクエリ タイトルがその外部ファイルのどこかに表示されることが保証されます。 

各クエリ タイトルについて、そのファイル内の行番号を決定し、その行番号を指定された整数で割った値を出力する必要があります。$P$。 弾性率$P$は小さい場合もあれば大きい場合もありますが、キー操作は常に同じです。つまり、非表示の順序付きリストで正確な文字列を見つけ、そのインデックスを取得し、剰余を計算します。 

主な課題は算術ではなく、検索です。 プログラム内で最初から再構築するには大きすぎる静的データセットに対して、多くの正確な文字列からインデックスへのクエリをサポートすることが事実上求められています。 

制約により、どのような種類の解決策が期待されるかが明確になります。 まであります$2 \cdot 10^4$すべてのクエリ文字列の合計の長さは次のとおりです。$10^6$。 これにより、クエリごとに大規模なデータセットを繰り返しスキャンしようとするアプローチは即座に除外されます。 クエリごとに数千行にわたるリニア スキャンでも、すでにリスクが発生します。$10^4 \times 10^4 = 10^8$比較は困難ですが、非表示のデータベースの方が大きい場合はさらに悪いことになります。 

より微妙な制約は、タイトルにスペース、句読点、引用符、および大文字と小文字の混合を含めることができるということです。 これにより、トークン化または正規化に基づくショートカットが排除されます。 一致は文字ごとに正確に行う必要があります。 

潜在的な落とし穴の 1 つは、データセットがクエリごとにブルート フォース検索を実行できるほど小さいと想定していることです。 これは、関連するプレフィックスが数千行に制限されている一部のサブタスクでのみ機能しますが、完全バージョンでは明らかに永続的なマッピングが必要です。 

もう 1 つの問題は、行番号付けにおける 1 つずつの間違いです。 この問題では、行番号に 1 から始まるインデックスを明示的に使用し、剰余を取得します。$P$行番号がちょうど割り切れる場合を含め、正確な剰余を保持する必要があります。$P$。 

## アプローチ

 強引な解釈では、外部ファイルをリストとして扱い、クエリごとに、一致するタイトルが見つかるまで最初の行からスキャンします。 すべてのタイトルがデータベース内に 1 回だけ存在することが保証されているため、これは正しいことです。 ただし、データベースに次のものが含まれている場合、$N$行、各クエリのコスト$O(N)$、につながる$O(TN)$全体的な複雑さ。 と$T$まで$2 \cdot 10^4$、 平$N \approx 10^5$これは完全に不可能になります。 

重要な点は、データベースが静的であり、クエリは検索のみであるということです。 これは、ファイル全体を一度前処理して、タイトル文字列から行インデックスまでのハッシュ マップを構築できることを意味します。 その後、各クエリは予想される辞書検索に縮小されます。$O(1)$時間。 

ファイルの隠された性質が唯一の珍しい点ですが、意図されたソリューションでは、ファイルのコンテンツはダウンロード可能なテキスト ファイルまたはプリロードされたデータセットとして提供されます。 読み取られると、他の文字列配列と同様に動作します。 

したがって、変換は簡単です。ハッシュ マップを使用して線形探索問題を直接アドレス テーブルに変換します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとのブルート フォース スキャン |$O(T \cdot N)$|$O(1)$| 遅すぎる |
 | ハッシュマップの前処理 |$O(N + T)$|$O(N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 完全なデータベース ファイルが文字列のリストとして利用可能であると仮定します。 

1. 外部データセットからすべての行を読み取り、各タイトルに 1 から始まるインデックスを割り当てます。 すべてのクエリはこの固定された順序にマップされる必要があるため、このステップでは回答の世界を構築します。 
2. 各タイトルを行番号にマッピングする文字列を辞書に挿入します。 これが機能する理由は、タイトルがデータセット内で一意であるため、マッピングに曖昧さがなくなるからです。 
3. 各クエリ タイトルに対して、辞書検索を実行して行番号を直接取得します。 これにより、ハッシュを超えたスキャンや比較が回避されます。 
4. 答えを次のように計算します。$\text{line} \bmod P$。 Python のモジュロ演算子は既に正しい範囲の値を返しているため、これは直接操作ですが、1 ベースのモジュラー動作を期待している場合、結果が 0 の場合は注意が必要です。 ここでの問題は、明示的に標準モジュロ出力を必要としています。 
5. 結果をすぐに印刷するか、出力を蓄積して高速バッチ印刷を行います。 

### なぜ効果があるのか

 正確さは、前処理ステップが各タイトルとデータベース内のその位置との間の全単射マッピングを構築するという事実から得られます。 すべてのクエリ タイトルは 1 回だけ存在することが保証されているため、すべての検索で明確に定義された整数インデックスが取得されます。 モジュロ演算は検索プロセスとは独立して適用されるため、正確性は辞書構築の正確さと文字列の正確な一致に限定されます。 固定されたファイル順序を超える順序の仮定は必要ありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    T = int(input().strip())
    P = int(input().strip())

    queries = [input().rstrip('\n') for _ in range(T)]

    # Read full database from local file
    # (In the intended setting, this file is provided externally.)
    with open("database.txt", "r", encoding="utf-8") as f:
        titles = [line.rstrip('\n') for line in f]

    pos = {}
    for i, title in enumerate(titles, 1):
        pos[title] = i

    out = []
    for q in queries:
        idx = pos[q]
        out.append(str(idx % P))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    main()
```重要な実装上の決定は、完全なタイトル リストから一度構築されたハッシュ マップを使用することです。 これにより、各クエリが定数時間の辞書アクセスになることが保証されます。 

一緒に読む`rstrip('\n')`末尾の改行が一致しないと正確な一致が失われるため、これは重要です。 マッピングでは、1 から始まるインデックスが使用されます。`enumerate(..., 1)`問題の行番号の定義と一致します。 

モジュロは取得後にのみ適用され、インデックス作成ロジックへの干渉を回避します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(N + T)$| データベースから辞書を構築するための 1 つのパス、クエリごとに 1 つの検索 |
 | スペース |$O(N)$| 各タイトルをその行番号にマッピングするためのストレージ |

 前処理とクエリ処理の両方が線形であるため、ソリューションは制約内に快適に適合します。 辞書ベースのアプローチでは、データベースの繰り返しスキャンが完全に回避されます。これは、単純な検索に比べて重要な改善点です。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return main_capture()

def main_capture():
    import sys
    input = sys.stdin.readline

    T = int(input().strip())
    P = int(input().strip())
    queries = [input().rstrip('\n') for _ in range(T)]

    titles = [
        "A", "B", "C", "D", "E"
    ]

    pos = {t: i+1 for i, t in enumerate(titles)}

    out = []
    for q in queries:
        out.append(str(pos[q] % P))
    return "\n".join(out)

# sample-style test
assert run("3\n10\nA\nC\nE\n") == "1\n3\n0"

# edge: P = 2
assert run("2\n2\nB\nD\n") == "0\n0"

# edge: P larger than indices
assert run("2\n100\nA\nE\n") == "1\n5"

# boundary: first and last
assert run("2\n3\nA\nE\n") == "1\n2"
```| テスト入力 | 期待される出力 | 検証内容 |

 | 小規模な順次クエリ | 正しいマッピング | 基本的な正しさ |
 | P = 2 の場合 | 0/1 交互 | モジュロエッジ動作 |
 | 大きなP | 単位モジュロ | 意図しないラップはありません |

 ## 特殊なケース

 エッジ ケースの 1 つは、タイトルが正確に 1 行目にある場合です。辞書はそれをインデックス 1 にマップするため、出力は次のようになります。$1 \bmod P$。 たとえば、次の場合$P = 2$、これは 1 を生成し、モジュロの前に 1 ベースのインデックスが正しいことを確認します。 

もう 1 つのケースは、タイトルが次の値で正確に割り切れる行にある場合です。$P$。 たとえば、タイトルが 10 行目にある場合、$P = 10$1 ベースのモジュラー演算を強制しようとする単純な実装では、これを誤って 10 または 1 に変換する可能性がありますが、問題は生のモジュロ結果を期待しています。 

3 番目のケースは、句読点や間隔が異なる、繰り返しのように見える文字列です。 一致は正確であるため、前処理に一貫性がない場合は、引用符や余分なスペースが欠落している場合でも、辞書キーが欠落する可能性があります。 このため、改行のみを削除し、他のすべての文字を保持することが重要です。
