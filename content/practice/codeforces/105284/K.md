 ## 解決策
 ## 問題の理解

 私たちには、線分が並んだ一次元の宇宙が与えられています。 各セグメントには値があり、配列の左半分にあるか右半分にあるかに応じて、最初は +1 または -1 になります。 時間の経過とともに、この線は変化する可能性があります。隣接する等しいセグメントがより大きなマグニチュードのセグメントに結合したり、より大きなマグニチュードのセグメントが 2 つの等しいより小さなセグメントに分割されたりすることがあります。 これらの構造変化にもかかわらず、すべてのセグメントは常に符号付きの「質量単位」を表し、過去のマージまたは分割に応じて 1、-1、2、または -2 のいずれかになります。 

この進化するアレイの上で、アストラル エクスプレスと呼ばれる移動オブジェクトをシミュレートします。 それはセグメント上にあり、速度があります。 各ステップで、速度によって左に動くか右に動くかが決まります。 移動後、着地したセグメントの値を速度に加えて吸収します。 アレイから離れると、プロセスは停止します。 速度がゼロになると、方向は前の動きから記憶されます。 

タイプ 1 の各クエリでは、ルールで定義された特定の位置から初速度で開始し、オブジェクトが配列から出るまでにこのシミュレーションがどれくらいの時間実行されるのか、それとも永遠に継続されるのかが尋ねられます。 

タイプ 2 および 3 のクエリは、厳密な保証の下でマージまたは分割することによって隣接するセグメントをローカルに変更します。つまり、構造の変更は常に有効で元に戻すことができます。 

主な難点は、シミュレーションが 1 回だけ実行されるわけではないことです。 配列が動的に変化する間、最大 200,000 のクエリに応答する必要があるため、クエリごとにウォーク全体を最初から再計算することは不可能です。 

この制約は、ステップを明示的にシミュレートするソリューションが実行不可能であることを意味します。 1 つのクエリには、ウォークのステップ数として最大で 1 次または 2 次の時間が必要になる場合があり、その数は速度の蓄積とセグメントの繰り返しの再訪問により容易に大きくなる可能性があります。 したがって、各クエリが対数時間またはほぼ一定の時間で応答できるようにシステムを表現する方法を見つける必要があります。 

速度がゼロになると、微妙なエッジケースが発生します。 方向が持続するため、正しい動作では運動が継続するにもかかわらず、単純なシミュレーションではゼロ速度が誤って停滞として扱われる可能性があります。 もう 1 つの注意が必要なケースは振動です。値がループ内の速度変化をキャンセルすると、急行が 2 つのセグメント間で跳ね返り、無限の旅につながる可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、文字通り各ステップをシミュレートします。 配列を維持し、速度に応じて左または右に繰り返し移動し、現在のセル値で速度を更新します。 これはルールに直接従うため、正しいです。 ただし、各クエリは終了するまでに多くの手順を必要とする場合があります。 最悪の場合、速度は 1 ステップあたり ±1 しか変化せず、アレイ サイズに比例するかそれ以上の長さの長い歩行が発生します。 最大 200,000 のクエリがあるため、全体的に許容できないほど複雑になります。 

重要な観察は、システムが一定の傾きのセグメント上で区分線形ポテンシャル ウォークのように動作することです。 各セグメントは速度に一定の増分を与えるため、等しい値の連続したブロック内では、速度は予測どおりに変化します。 セルごとにステップ実行する代わりに、方向または速度構造が変化する「イベント」間をジャンプできます。 

配列を同じ値のブロックに圧縮し、分割と結合をサポートするバランスの取れた構造に維持できます。 この動きは、個々のインデックスではなくブロック間の遷移として解釈できます。 各ブロックは方向に応じて +k または -k の速度に寄与するため、歩行は一連のブロック間ジャンプになります。

重要な洞察は、実際にはすべての中間位置を知る必要はないということです。 知っておく必要があるのは、2 つのことのいずれかが起こるまでにどれくらいの時間がかかるかだけです。配列を終了するか、繰り返す構成に到達する (これは無限ループを意味します)。 これは、ブロック全体にわたる累積速度効果を追跡し、プレフィックスのような高速遷移をサポートする構造を使用することで処理できます。 

ブロック上のトリープ ツリーやスプレイ ツリーなどのバランスの取れたツリーを使用すると、セグメントの合計を維持し、ブロック遷移ごとの対数時間でのジャンプをシミュレートできます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(クエリごとの合計ステップ) | O(n) | 遅すぎる |
 | 最適 (バランスの取れたツリーを使用したブロック シミュレーション) | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 配列をバランスの取れた二分探索ツリーとして維持します。各ノードは値とサイズが暗黙的に 1 のブロックを表します (分割により小さい大きさが適用されるため)。 

各ノードはサブツリーの合計やサイズなどの集計情報を保存するため、間隔ごとに速度がどのように変化するかを効率的に計算できます。 

1. 2n 個のノードで初期バランス ツリーを構築します。最初の n の値は +1 で、次の n の値は -1 です。 これは初期の銀河を表します。 
2. タイプ 2 クエリの場合、値が等しいか ±1 であることが保証される 2 つの隣接するノードをマージします。 2 番目のノードを削除し、最初のノードの値を 2 倍にします。 これにより、構造サイズを縮小しながら、速度への全体的な寄与が維持されます。 
3. タイプ 3 クエリの場合、値 ±2 のノードを ±1 の 2 つのノードに分割します。 1 つのノードを 2 つの同一のノードに置き換えます。 これにより、より細かい粒度が復元されながら、ローカル合計が不変に保たれます。 
4. タイプ 1 クエリの場合、右端の正のセグメントとして定義された開始位置を見つけます。 これは、ツリーを走査して値 +1 を持つ最後のノードを見つけることによって行われます。 
5. そのノードから、初速度符号によって決定される方向への動きをシミュレートします。 段階的に移動するのではなく、現在の速度を維持しながら、連続するセグメントを飛び越えます。 
6. ノード内を移動するときは、ノードの値にノードの訪問回数を乗算して速度を更新し (通常、ブロック形式での走査ステップごとに 1 つ)、次のブロック境界までの位置を更新します。 
7. いずれかの時点でトラバースがツリー境界を出る場合、それまでに実行されたステップ数を返します。 
8. トラバース中に、同じ速度と方向の状態で以前に見たノードを繰り返していることが検出された場合、プロセスは無限であると結論付け、-1 を出力します。 

正確さは、各ノードが速度への均一な寄与を表し、速度の符号が変わらない限りノード間の移動はインデックスにおいて単調であるという不変条件に依存します。 速度は蓄積されたノード値によってのみ変化するため、ブロックレベルの遷移は考えられるすべての状態変化を完全に捕捉します。 

## なぜ機能するのか

 重要な不変条件は、どの瞬間においても、システムの状態は現在のノードの位置、現在の速度、最後の移動方向という 3 つの情報によって完全に決定されるということです。 すべての遷移は、隣接するノードに移動するか、構造から出ます。速度の更新は、ノード内の内部構造ではなく、ノードの値のみに依存します。 マージと分割では、隣接する領域全体の合計が保持されるため、領域内の一連の操作の最終的な効果は、ブロック遷移のレベルでは変わりません。 これにより、ブロック粒度でのシミュレーションによって、ステップバイステップ シミュレーションとまったく同じ速度変化が生成されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("val", "left", "right", "size", "prio")
    def __init__(self, val):
        import random
        self.val = val
        self.left = None
        self.right = None
        self.size = 1
        self.prio = random.randint(1, 10**9)

def sz(t):
    return t.size if t else 0

def upd(t):
    if t:
        t.size = 1 + sz(t.left) + sz(t.right)

def split(t, k):
    if not t:
        return (None, None)
    if sz(t.left) >= k:
        l, r = split(t.left, k)
        t.left = r
        upd(t)
        return (l, t)
    else:
        l, r = split(t.right, k - sz(t.left) - 1)
        t.right = l
        upd(t)
        return (t, r)

def merge(a, b):
    if not a or not b:
        return a or b
    if a.prio < b.prio:
        a.right = merge(a.right, b)
        upd(a)
        return a
    else:
        b.left = merge(a, b.left)
        upd(b)
        return b

def kth(t, k):
    if not t:
        return None
    lsz = sz(t.left)
    if k < lsz:
        return kth(t.left, k)
    if k == lsz:
        return t
    return kth(t.right, k - lsz - 1)

def build(n):
    root = None
    for i in range(n):
        root = merge(root, Node(1))
    for i in range(n):
        root = merge(root, Node(-1))
    return root

def inorder_rightmost_positive(t):
    res = None
    stack = []
    cur = t
    while stack or cur:
        while cur:
            stack.append(cur)
            cur = cur.right
        cur = stack.pop()
        if cur.val > 0:
            res = cur
        cur = cur.left
    return res

def solve():
    n, q = map(int, input().split())
    root = build(2*n)

    for _ in range(q):
        t, x = map(int, input().split())

        if t == 2:

            a, right = split(mid, 2)
            a.val += a.val  # merge guaranteed
            root = merge(merge(left, a), right)

        elif t == 3:
            left, mid = split(root, x-1)
            a, right = split(mid, 1)
            b = Node(a.val // 2)
            a.val //= 2
            root = merge(merge(left, a), merge(b, right))

        else:
            start = inorder_rightmost_positive(root)

重要な点は、タイプ 1 クエリ内の単純な走査では十分ではないことです。 実際に受け入れられている解決策は、保存されたサブツリー集合体を使用して、セグメント上の対数ジャンプでループを置き換えます。 

## 実用的な例

 n = 2 の単純化された初期構成を考えます。つまり、配列は [1, 1, -1, -1] になります。 

右端の正の位置、つまりインデックス 2 から開始します。 

初速度 x = 2 のクエリの場合:

 | ステップ | ポジション | 速度 | 付加価値 | メモ |
 | --- | --- | --- | --- | --- |
 | 1 | 2 | 2→3 | +1 | 右に移動すると速度が増加します |
 | 2 | 3 | 3→2 | -1 | 右に移動 |
 | 3 | 4 | 2→1 | -1 | 続く |

 最終的には出口まで速度が低下します。 

これは、交互の符号によって速度がどのように振動するかを示しています。 

ここで、配列が [1, 2, -1, -1] になるマージされたケースを考えてみましょう。 

| ステップ | ポジション | 速度 | 付加価値 |
 | --- | --- | --- | --- |
 | 1 | 2 | x → x+2 | +2 |
 | 2 | 3 | すぐに成長します | -1 減少 |

 ここでは速度が速くなり、片側の出口が早くなり、合流に対する感度が高くなります。 

これらのトレースは、局所的な構造の変化が全体的な軌道に劇的な影響を与えることを示しています。そのため、ステップ シミュレーションを集合推論に置き換える必要があります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、ノードに着地した直後に速度がゼロになる場合です。 この状況では、方向性を維持する必要があります。 単純なシミュレーションでは動作が停止する可能性がありますが、正しい動作は最後に知られた方向に継続し、Express が以前に訪問したノードに再入して実行時間を大幅に延長する可能性があります。 

別の特殊なケースでは、同じ場所でマージとその後の分割が繰り返されます。 マージによって大きさが増加し、分割によって大きさが逆転するため、構造は 2 つの同等の構成の間で振動する可能性があります。 アルゴリズムは、分割が重複したり質量を失ったりしないように、ノードのアイデンティティがトレプ内で正しく保存されることを保証する必要があります。 

3 番目のエッジ ケースは、エクスプレスが大きなマージされたブロックの境界で開始するときに発生します。 正しく集約しないと、単純なアプローチではブロックが単一のステップとして扱われ、中間の速度寄与がスキップされる可能性があります。 正しい解釈は、ブロック内の各ユニットは、構造的に圧縮されている場合でも、独立して速度の進化に寄与するということです。
