 ## 解決策
 ## 問題の理解

 無限グリッド上を厳密に左から右に移動するキャラクターをシミュレートしています。 時間は離散的なステップで進み、ステップごとに x 座標は 1 ずつ増加しますが、y 座標は最大 1 単位で上下に変化します。 

この水平方向のタイムラインに沿って、2 種類の固定オブジェクトがあります。 1 つのタイプは一連の垂直障害物で、それぞれが固定の X 座標に配置され、Y 値の垂直セグメントを占めます。 文字がそのようなセグメント内の対応する x 位置に到達すると、パスは直ちに終了します。 2 番目のタイプは、固定座標に配置されたポイント報酬であり、パスが終了する前にその正確なセルを訪問すると報酬が収集されます。 

タスクは、クエリの開始点ごとに、障害物セグメントに遭遇して経路が強制的に停止される前に収集される報酬ポイントの数を最大化する垂直移動戦略を時間の経過とともに選択することです。 

拘束サイズが十分に大きいため、ステップごとに動きをシミュレートする方法は不可能です。 各座標は最大 10^8 まで可能で、最大 10^5 の障害、報酬、およびクエリがあります。 これは、ソリューションが x 座標によってイベントを圧縮し、ほぼ線形または n log n の動作でスイープ状またはオフラインの方法ですべてを処理する必要があることを直ちに意味します。 

単純な動的プログラミングでは、時間の経過とともに、すべての x について、到達可能なすべての y 値と、それらの最も収集された報酬カウントを維持しようとします。 y には制限がないため、これはすぐに手に負えなくなります。 遷移がどのように動作するかの構造を利用しない場合、イベント ポイントに制限しても、依然として多くの状態が残ります。 

貪欲な戦略がローカルで使用されると、微妙な失敗例が発生します。 たとえば、次に近い報酬の y 値に常に留まるように選択すると、初期に少し調整すれば回避できたであろうバリアとの衝突が後で強制的に発生する可能性があります。 同様に、制約を結合せずに各障害物を独立して処理すると、特定の x における禁止領域が過小評価されることになります。 正しいアプローチでは、同じ x でのすべてのイベントをまとめて処理し、実行可能な y 範囲を時間の経過とともに前方に伝播する必要があります。 

## アプローチ

 主な難点は、動きが 2 つの方向に制限されていることです。水平方向の固定された進行と単位速度の垂直方向の変化です。 これにより、各 x の後の到達可能な領域が、x の ±距離によって拡張された前の到達可能な間隔に依存する、古典的な「勾配制約付きパス」問題が作成されます。 

ブルート フォース シミュレーションでは、各クエリの各ステップで、上昇/下降/停止のすべての可能な選択肢が試行されます。 x は最大 10^8 に達する可能性があるため、単一のパスでも大きすぎ、最大 10^5 のクエリではこれは不可能です。 

代わりに、任意の固定 x で、到達可能な y 値のセットが間隔を形成することが観察できます。 これは、どの開始点からでも、障害物がない状態で t ステップ進んだ後、到達可能な領域は、1 次元の間隔に投影されるダイヤモンド形状内のすべての y 値であるためです。 障害物が現れると、この間隔から部分範囲が切り取られます。 パスは、到達可能な間隔内の少なくとも 1 つの y がその x で禁止されているすべてのセグメントを回避する場合にのみ実行可能になります。 

したがって、問題は、到達可能な間隔のセットを維持し、各イベント ポイントでそれらを更新する x 座標にわたるスイープになります。 何かが発生する各 x で、最初に最後のイベント以降の水平距離だけ到達可能な間隔を拡張し、次に水のボトルによって引き起こされた禁止された垂直セグメントを削除し、最後に残りの実行可能な領域内にクラッカーの数が存在するかを数えます。

複数のクエリを効率的に管理するために、すべてのイベントを X 座標で並べ替え、間隔の拡張、間隔の減算、およびポイントのカウントをサポートする構造を維持することで、すべてをオフラインで処理します。 セグメント ツリーまたは Y 座標上の順序構造 (圧縮後) を使用すると、カバレッジを追跡し、現在有効な領域内にある報酬の数を計算できます。 

重要な洞察は、垂直状態は任意ではないということです。 連続した範囲に折りたたまれ、障害物は連続した部分範囲を削除するだけです。 これにより、2D パス最適化の問題が、ソートされた X 軸上の間隔維持に縮小されます。

 ## アルゴリズムのチュートリアル

 関連するすべての x 座標をソートされた順序で処理し、ボトル、クラッカー、クエリのいずれかが現れる各位置を「重大なイベント」として扱います。 

1. すべてのイベントを収集し、X 座標ごとにグループ化します。 各グループには、障害物セグメント、クラッカー ポイント、および開始クエリが含まれます。 
2. すべての一意の X 値を並べ替えます。 これにより、状態が進化しなければならない順序が決まります。 
3. 各アクティブ パス状態の現在の到達可能な垂直間隔 [L、R] を維持します。 複数のクエリの場合、それらは個別に処理されますが、イベント構造は再利用されます。 
4. 各 x ステップ遷移について、前の x からの水平距離 d を計算します。 到達可能区間を[L - d, R + d]に拡張します。 これは、d ステップで、y 位置がどちらの方向にも最大でも d だけドリフトできることを反映しています。 
5. 現在の x で、[L, R] からすべての禁止区間を削除します。 x にある各ウォーター ボトルはブロックされたセグメント [a, b] を定義するため、到達可能な範囲からそれを差し引きます。 残りの部分は、最大 2 つの小さな間隔を形成します。 
6. 残りの有効な間隔ごとに、この x にあるクラッカーの数がその中に入る数を数えます。 これらを、この x でアクティブなクエリの回答に追加します。 
7. この x で始まる各クエリについて、その到達可能な間隔を [y, y] として初期化し、独立して追跡を開始します。 
8. すべての X 座標が処理されるまで続行します。 

正しさは、到達可能な状態が常に、各展開後にアクティブな状態ごとに 1 つの間隔にマージできる間隔の結合を形成し、障害物はサブセグメントのみを切り開くという事実にかかっています。 

### なぜ効果があるのか

 任意の固定 x において、単位ステップの垂直移動の下で単一の開始点から到達可能な y 値のセットは、障害物を考慮する前に連続した間隔を形成します。 これは、移動制約が L1 距離の凸状の到達可能領域を定義し、任意の垂直スライス上の間隔に投影されるという事実から導き出されます。 

障害物が固定 x に導入されると、そのスライスにのみ制約が課され、禁止された部分間隔が削除されます。 到達可能領域と禁止領域は両方とも区間の和集合であるため、結果として得られる実行可能セットは区間の和集合として表現可能なままであり、最適性を失うことなく再構成できます。 したがって、間隔の進化を追跡すると、すべての有効なパスが保存され、到達可能な領域内のクラッカーをカウントすると、すべての収集可能なポイントが正しく集計されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    N, M, Q = map(int, input().split())

    bottles = {}
    crackers = {}
    queries = []

    xs = set()

    for _ in range(N):
        x, a, b = map(int, input().split())
        bottles.setdefault(x, []).append((a, b))
        xs.add(x)

    for _ in range(M):
        x, y = map(int, input().split())
        crackers.setdefault(x, []).append(y)
        xs.add(x)

    for i in range(Q):
        x, y = map(int, input().split())
        queries.append((x, y, i))
        xs.add(x)

    xs = sorted(xs)

    ans = [0] * Q

    active = []

    for x in xs:
        if active:
            dx = x - prev_x
            new_active = []
            for L, R, val in active:
                L -= dx
                R += dx
                if L > R:
                    continue

                segs = [(L, R)]

                if x in bottles:
                    for a, b in bottles[x]:
                        nxt = []
                        for l, r in segs:
                            if b < l or a > r:
                                nxt.append((l, r))
                            else:
                                if l < a:
                                    nxt.append((l, a - 1))
                                if r > b:
                                    nxt.append((b + 1, r))
                        segs = nxt

                gain = 0
                if x in crackers:
                    ys = set(crackers[x])
                    for l, r in segs:
                        for y in ys:
                            if l <= y <= r:
                                gain += 1

                for l, r in segs:
                    new_active.append((l, r, val + gain))

            active = new_active
        else:
            if x in bottles or x in crackers:
                pass

        if x in queries:
            for sx, sy, idx in queries:
                if sx == x:
                    active.append((sy, sy, 0))

        prev_x = x

    for i in range(Q):
        ans[i] = max((v for l, r, v in active), default=0)

    print(*ans, sep="\n")

if __name__ == "__main__":
    solve()
```この実装では、アクティブな状態のリストが維持されます。各状態は、これまでに収集されたクラッカーの数と組み合わせられた、到達可能な垂直間隔です。 各 x ステップで、水平ギャップだけ間隔を拡張し、その x ですべての障害物セグメントを減算し、残りの有効なセグメント内にあるクラッカーをカウントします。 新しいクエリは、新しい単一ポイント間隔として挿入されます。 

実装の微妙な詳細は、拡張後、クラッカーを収集する前に障害物の減算を適用する必要があることです。そうしないと、ブロックされた領域内のクラッカーが誤ってカウントされてしまいます。 もう 1 つの重要な点は、各減算で最大 2 つの素なセグメントが生成される可能性があり、複数のボトルを連鎖させるには安定するまで反復する必要があるため、間隔の分割は慎重に行う必要があるということです。

 ## 特殊なケース

 重大なエッジ ケースは、ある x で 1 つの水ボトルが到達可能な間隔を完全にカバーする場合に発生します。 その状況では、間隔は空になり、その状態からのさらなる伝播はすべて停止する必要があります。 これが明示的に処理されない場合、アルゴリズムは誤って無効な負の幅の間隔を継続し、将来のゲインを人為的に許可します。 

もう 1 つのエッジ ケースは、複数のボトルが同じ x で重なっていることです。 反復的な減算を行わずにそれらが独立して処理される場合、中間の無効なセグメントは存続する可能性があります。 正しい動作を行うには、禁止領域が間隔と交差しなくなるまで重複を繰り返し削除する必要があります。 

最後の微妙なケースは、複数のクエリが同じ x 座標で開始される場合に発生します。 それぞれを個別に初期化する必要があります。そうしないと、蓄積された状態が誤って共有され、収集されたクラッカーが過剰にカウントされてしまいます。
