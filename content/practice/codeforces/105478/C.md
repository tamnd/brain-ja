 ## 解決策
 ## 問題の理解

 各テスト ケースでは、アイテムのいくつかの独立したスタックとして構造化されたショップが得られます。 各スタックでは、アイテムは上から下に固定された順序で配置されており、スタック内の次のアイテムにアクセスできるのは、その上のすべてをすでに購入している場合のみです。 したがって、どのスタックからでも、選択できるのは任意のサブセットではなく、そのスタックのプレフィックスです。 

すべてのアイテムには価値があり、それを購入すると、その価値だけ攻撃の合計が増加します。 すべてのアイテムのコインのコストは同じであるため、制約は純粋に、どのアイテムを購入できるかということではなく、購入できるアイテムの数によって決まります。 

これにより、問題はすべてのスタックにわたるアイテムの合計数を選択することになりますが、各スタック内で何かを取得する場合はプレフィックスを取得する必要があります。 目的は、選択した値の合計が最大になる方法で、限られた購入数をスタック全体に分配することです。 

微妙な点は、負の値が許可されていることです。 これにより、容量がある場合でもスタックから取得するアイテムの数を減らすことが最適になる場合があります。アイテムの深さが深いほど合計スコアが低下する可能性があるためです。 これにより、「アイテムが多ければ多いほど良い」という貪欲な戦略は排除されます。 

制約から、スタック数は最大 250 であり、各スタックはかなり長くなる可能性があります。 コイン制限は最大 3000 ですが、各アイテムのコストは 15 コインです。つまり、実際に購入できるアイテムの数は最大 200 個です。この削減が重要な構造の簡素化です。入力が大きく見えても、ナップザックの有効容量は小さいです。 

素朴な解釈では、スタック全体にわたるプレフィックス長の有効な組み合わせをすべてシミュレートしようとします。 スタック i に mi オプションがある場合、組み合わせの合計は (mi + 1) の積として増加し、中程度の入力でも天文学的に大きくなります。 N スタックにわたる C 項目のすべての分布を試しても、組み合わせ爆発が発生します。 

不注意な解決策を破るエッジ ケースには、すべてが負の値を持つスタック (最適な選択はそのスタックからアイテムを 0 個取り出すことである) や、初期のアイテムが負であるが後のアイテムが正であるスタックが含まれ、慎重なプレフィックス推論が強制されます。 For example, a stack like`[-5, -2, 10]`プレフィックス合計があります`[-5, -7, 3]`, and the best choice is taking all three items even though the middle prefix is very bad. Any greedy “stop when it becomes negative” approach fails here.

 もう 1 つのエッジ ケースは、C が 15 で割り切れない場合です。すべての品目のコストは同じであるため、真の制約は品目の数であるため、効果的に作業します。`C // 15`。 

## アプローチ

 ブルート フォース ビューでは、各スタックにアイテム k_i の数を割り当て、各スタックのプレフィックス値を計算し、すべての k_i の合計が購入できるアイテムの数と等しくなるように強制します。 各スタック i について、0 から m_i までのすべての k_i を試し、スタック全体のすべての組み合わせをチェックできます。 

これは、問題のルールに直接従うため、概念的には機能しますが、分岐係数がスタック間で乗算されるため、計算的には失敗します。 たとえ各スタックの選択肢が 50 個しかなかったとしても、スタックが 250 個あると、状態空間は完全に実行不可能になります。 

重要な観察は、アイテム全体の予算の共有を除いて、スタックごとの決定が独立していることです。 スタックから正確に k 個の項目を取得する値 (単なる接頭辞の合計) を事前に計算すると、各スタックは多肢選択ナップザック問題のグループになります。 その後、合計 K 個のアイテムをグループ全体に配布するだけで済みます (K は最大 200)。 

これにより、問題は指数関数的な組み合わせ選択から、スタックと項目数に関する構造化された動的プログラミングに軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべてのプレフィックスの組み合わせに対するブルート フォース | 指数 | 指数 | 遅すぎる |
 | スタックとアイテム予算に関する動的プログラミング | O(N · K · 平均 m_i) | O(K) | 承認済み |

 ## アルゴリズムのチュートリアル

 K を、次のように計算して購入できるアイテムの数とします。`K = C // 15`。 

1. 各スタックについて、最初の k 項目を取得した場合に何が起こるかを O(1) で答えることができるようにプレフィックスの合計を計算します。 これにより、各スタックがリストに変換されます。インデックス k は、正確に k 個の項目を取得した値を表します。 
2. DP 配列を維持します。`dp[x]`は、合計でちょうど x 個のアイテムを取得しながらいくつかのスタックを処理した後に達成可能な最大の攻撃を表します。 Initially,`dp[0] = 0`他のすべての状態は負の無限大です。 
3. スタックを 1 つずつ処理します。 スタックごとに、新しい DP アレイを構築します`ndp`。 このスタックからのすべての可能な以前の合計 x とすべての可能な選択肢 k について、次のように遷移します。`x + k`項目を選択し、対応するプレフィックス値を追加します。 このステップは、総容量を考慮しながら現在のスタックから取得する項目の数を独立して決定するという考えを反映しています。 
4. すべてのスタックを処理した後、未使用の容量を残すことができるため、答えはすべての dp[x] の最大値になります (x ≤ K)。 

移行における重要な点は、プレフィックス制約によりスタックごとに 1 つの連続した選択が強制されるため、同じスタックからの部分的な決定を決して混合しないことです。 

### なぜ効果があるのか

 i 個のスタックを処理した後のあらゆる時点で、すべての dp 状態は、それらの i 個のスタックからのプレフィックスの有効な選択に対応します。 不変条件は、プレフィックス制約を考慮して、処理されたスタックの中から正確に x 項目を選択することによって達成可能な最良の攻撃値を dp[x] が格納するということです。 新しいスタックを処理するときは、そのスタックに対して 1 つのプレフィックス長を正確に選択することで、既存の各設定を拡張します。 すべての有効なソリューションはスタックごとにそのような選択を 1 つだけ行う必要があるため、有効な構成が失われることはなく、無効な構成が導入されることもありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

NEG = -10**30

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        N, C = map(int, input().split())
        K = C // 15
        
        stacks = []
        for _ in range(N):
            arr = list(map(int, input().split()))
            m = arr[0]
            vals = arr[1:]
            
            pref = [0]
            s = 0
            for v in vals:
                s += v
                pref.append(s)
            
            # truncate to K since we never need more than K items
            pref = pref[:min(len(pref), K + 1)]
            stacks.append(pref)
        
        dp = [NEG] * (K + 1)
        dp[0] = 0
        
        for pref in stacks:
            m = len(pref) - 1
            ndp = [NEG] * (K + 1)
            
            for used in range(K + 1):
                if dp[used] == NEG:
                    continue
                base = dp[used]
                for take in range(m + 1):
                    if used + take <= K:
                        val = base + pref[take]
                        if val > ndp[used + take]:
                            ndp[used + take] = val
            
            dp = ndp
        
        out.append(str(max(dp)))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装は DP 構造に直接に従います。 各スタックのプレフィックス配列は、「k 個の項目を取得」の各決定が O(1) になるように増分的に構築されます。 DP 配列のサイズは C ではなく K によって決まります。これは C 自体がコインであるため重要ですが、実際の制約は項目数です。 

ダブルループオーバー`used`そして`take`変換後の K は最大 200 であるため、変換は安全であり、最悪の場合でもスタックあたり約 40,000 の操作が行われ、これは快適に適合します。

| スタック | プレフィックスの合計 |

 | 1 | [0、-2、-1] |
 | 2 | [0、-1、-2、1] |

 DPの進化：

 | ステップ | dp[0] | dp[1] | dp[2] |
 | --- | --- | --- | --- |
 | 開始 | 0 | -inf | -inf |

 スタック 1 の後:

 | 中古 | 取る | 新しい状態 |
 | --- | --- | --- |
 | 0 | 0 | 0 |
 | 0 | 1 | -2 |
 | 0 | 2 | -1 |

 dp は次のようになります。`[0, -2, -1]`After stack 2, best combination is taking prefix 3 from stack 2 alone (value 1) or combining carefully, but capacity limits lead to optimal result 0.

 これは、負の中間値が依然としてピックのスキップまたは制限につながる可能性があることを示しています。 

### 例 2

 入力:```
1
1 90
3 5 1 10
```K = 6。 

プレフィックスの合計は次のとおりです。`[0, 5, 6, 16]`。 

最良の場合は、3 つのアイテムをすべて取得して 16 が得られ、余分な容量は使用されません。 DP は、すべての dp 状態の max を引き継ぐことにより、容量を未使用のままにすることを正しく許可します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N · K²) 最悪の場合 | 各スタックについて、以前に使用されたすべてのカウントとすべてのプレフィックス長を試します。 
| スペース | O(K) | 2 つの DP 配列のみが保存されます。 

コイン予算をアイテム予算に変換した後、K ≤ 200 であれば、N = 250 の場合でも効率的です。 

これが適合する主な理由は、元の大きな制約が欺瞞的であるということです。固定アイテムのコストにより、ナップザックの有効寸法が小さな一定規模の容量に縮小されます。

 ## 特殊なケース

 プレフィックス配列には常に空の選択肢が含まれるため、負の値のみを含むスタックは自然に処理されます。 DP は、非負のベースラインを維持して項目をゼロにするオプションを伝播します。 

のようなケース`[-5, -2, 10]`プレフィックス構造が重要な理由を示します。 DP はすべての k 値を考慮し、中間プレフィックスはさらに悪くなりますが、貪欲に推論されるのではなく明示的に評価されるため、k = 3 を取ることが最適になります。 

C が 15 より小さい場合、K は 0 になり、アイテムを購入できないため、DP はすぐに 0 を返します。
