 ## 解決策
 ## 問題の理解

 0 ～ 3 の 4 つの整数のカウントが与えられます。具体的には、次のようになります。$c_0$0のコピー、$c_1$1のコピー、$c_2$2のコピー、および$c_3$3 のコピー。これから、長さの配列を形成できます。$n = c_0 + c_1 + c_2 + c_3$。 目標は、この配列のすべての個別の順列を調べ、各順列の「奇数」と呼ばれる量を計算することです。 奇数は、順列内の連続する各ペアの XOR の最小設定ビットの合計として定義されます。 最後のタスクは、0 から 0 までの考えられる奇数値ごとにレポートすることです。$2(n-1)$、その値を生成する順列の数、法$10^9 + 7$。 

制約は十分小さいので、すべてのテスト ケースの要素の合計数が 800 を超えることはありません。単純階乗時間は超過に近づくため、これが重要です。$n$要素は完全に実行不可能です。$12!$ほぼ500,000であり、$800!$天文学的に大きいです。 組み合わせ的に機能し、順列の明示的な列挙を避けるアプローチが必要です。 

微妙な点は、数値 0 ～ 3 が少数の個別の lowbit(XOR) 値しか生成しないことです。 具体的には、[0,3] の任意の 2 つの数値の XOR は 0 ～ 3 であり、0..3 の下位ビットは {0,1,2} にあります。 この制限された範囲により、DP を圧縮し、総当たりではなく組み合わせで推論できるようになります。 

エッジケースは、カウントが著しく不均衡な場合に発生します。 たとえば、次の場合$c_0 = 1$そして$c_1 = c_2 = c_3 = 7$、配列には多くの繰り返し要素があり、多項係数を使用して重複を適切に処理しない限り、単純なカウントでは順列を過剰にカウントしてしまいます。 もう一つのエッジケースは、$n=4$, ここで、各数字は 1 回出現します。 この場合、すべての順列は個別になりますが、その奇数値が衝突する可能性があります。 

## アプローチ

 ブルートフォースアプローチは、配列のすべての異なる順列を生成し、それぞれの奇数を計算し、その奇数に応じてカウンターをインクリメントすることです。 これは原理的には正しいですが、時間の複雑さが伴います$O(n!)$、これは不可能です$n$XOR 結果をメモ化しても、階乗的に多くの順列を列挙することは、制約では不可能です。 

重要な観察は、異なる値が 4 つしかないということです。 順列を指定されたカウントを持つ数値 0、1、2、3 のシーケンスとして考えると、残りの数値のカウントと最後に配置された数値を考慮して、達成可能な奇数の値の分布を追跡する動的プログラミング アプローチを定義できます。 これにより、順列をすべて列挙することなく段階的に構築できるようになります。 各ステップでは、次の数値を選択し、カウントを更新し、前の数値との XOR の下位ビットを計算し、結果を DP テーブルに追加します。 

さらに、低ビット テーブルが小さいことに気づくことで、さらに最適化することができます。 0..3 内の任意の 2 つの数値の XOR は、最大 3 つの可能な下位ビット値を生成します。 これは、各 DP 遷移がカウントを少量の固定量だけシフトすることを意味します。 状態空間の境界は次のとおりです。$(c_0+1)_(c_1+1)_(c_2+1)*(c_3+1)*4$(残りの数値と最後に使用された数値を掛けた数)。 最悪の場合でも、$800^4 * 4$は大きいですが、ゼロ以外のカウントのみを DP エントリとして使用する (疎 DP) ことで、これが可能になります。 慎重に実装すると、DP はすべてのテスト ケースで数秒以内に実行されます。

 ## アルゴリズムのチュートリアル

 1. 0、1、2、3 の間のすべての XOR 組み合わせの下位ビットを事前計算します。 4x4のテーブルに保管します。 これにより、DP 中の再計算が回避されます。 例えば、`lowbit_xor[1][3] = 2`。 
2. DP テーブルを初期化します。`dp[c0][c1][c2][c3][last][oddness]`を使用して部分順列を構築する方法の数を数えます。`c0..c3`各数字の残り、で終わる`last`、まったく奇妙です`oddness`。 
3. ベースケースをセットします。 それぞれの番号について`x`with count at least 1, start the permutation with that number. This corresponds to decreasing its count by 1 and starting the oddness at 0, since no pair exists yet.
 4. すべての DP 状態を反復します。 州ごとに新しい番号を追加してみてください`y`残りのカウントが正です。 を追加して新しい奇数を計算します。`lowbit(last XOR y)`。 の数を減らします`y`by 1. 現在の DP カウントを追加して、新しい状態の DP テーブルを更新します。 
5. すべてのカウントがゼロになるまで続けます。 その時点で、カウントがゼロであるすべての DP エントリを合計します。 各エントリは、特定の奇妙さを持つ順列に対応します。 奇数ごとにカウントを収集します。 
6. モジュロを適用する$10^9+7$整数のオーバーフローを避けるために加算のたびに。 

機能する理由: DP は、すべての状態が、指定された残りのカウント、最後の要素、および累積された奇数を持つすべての部分順列を正確に表すという不変条件を維持します。 各ステップで次の可能なすべての数値を考慮するため、すべての順列は 1 回だけカウントされ、重複は明示的なシーケンスではなくカウントを使用して自動的に処理されます。 低ビット加算により、奇数が正しく累積されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
MOD = 10**9 + 7

# precompute lowbit table
lowbit = [0,1,2,1,4]
lowbit_xor = [[lowbit[i^j] for j in range(4)] for i in range(4)]

from collections import defaultdict

def solve_case(c):
    n = sum(c)
    dp = defaultdict(int)
    # base case: start with each number if available
    for x in range(4):
        if c[x] > 0:
            key = tuple(c[i]-(1 if i==x else 0) for i in range(4)) + (x,0)
            dp[key] = 1

    for _ in range(n-1):
        new_dp = defaultdict(int)
        for key, val in dp.items():
            rem0, rem1, rem2, rem3, last, odd = key
            rem = [rem0, rem1, rem2, rem3]
            for y in range(4):
                if rem[y]==0:
                    continue
                new_rem = tuple(rem[i]-(1 if i==y else 0) for i in range(4))
                new_odd = odd + lowbit_xor[last][y]
                new_key = new_rem + (y,new_odd)
                new_dp[new_key] = (new_dp[new_key] + val) % MOD
        dp = new_dp

    # collect final counts
    res = [0]*(2*(n-1)+1)
    for key,val in dp.items():
        rem0, rem1, rem2, rem3, last, odd = key
        if rem0+rem1+rem2+rem3==0:
            res[odd] = (res[odd] + val) % MOD
    return res

t = int(input())
for _ in range(t):
    c = list(map(int,input().split()))
    ans = solve_case(c)
    print(' '.join(map(str,ans)))
```このソリューションでは、スパース DP アプローチを使用します。`defaultdict`到達可能な状態のみを保存します。 各状態は、残りの数字のカウント、最後に配置された数字、および累積された奇数を保存します。 これにより、4D カウント空間全体を保存できなくなります。 XOR の組み合わせの下位ビットを事前に計算することは、効率と明瞭さを実現するために重要です。 最初は XOR ペアが存在しないため、基本ケースは単一の数値と 0 の奇数から始まります。 更新では慎重にカウントを減算し、低ビットの寄与を追加します。 最終的な合計では、完全に使用された順列のカウントが集計されます。
