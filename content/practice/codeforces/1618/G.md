 ## 解決策
 ## 問題の理解

 この問題では、Monocarp はそれぞれ整数の価格を持つアイテムのセットを持っており、これらのアイテムを別のキャラクターのアイテムと交換できます。 取引ごとに、価格のアイテムの 1 つを手放すことができます$x$他のキャラクターから、価格が最高以下のアイテムを受け取ります$x + k$、 どこ$k$クエリ固有の値です。 各クエリの目標は、指定された条件の下で一連の取引を行うことが許可されている場合に Monocarp が取得できるアイテムの最大合計値を決定することです。$k$。 各クエリは独立しているため、取引はクエリ間で引き継がれません。 

入力サイズは大きく、最大で$2 \cdot 10^5$両側にアイテムがあり、$2 \cdot 10^5$クエリ。 各取引には多くのオプションがあり、指数関数的な可能性をもたらすため、考えられるすべての取引シーケンスをシミュレートしようとする単純な強引なアプローチは直ちに実行不可能です。 問題の構造を使用して最大値を効率的に計算するアプローチが必要です。 

微妙なエッジケースには、Monocarp が最初は他のキャラクターよりも安いアイテムを持っているが、$k$取引を「サイクル」し、より高価なアイテムを間接的に取得するためのマージン。 もう 1 つのエッジ ケースは、Monocarp のすべてのアイテムが他のキャラクターのアイテムよりも既に高価であるため、トレードによって合計額が増加しない場合です。 たとえば、Monocarp が`[10, 20]`そしてもう一方は`[5, 6]`と`k = 0`の場合、合計が改善されることはなく、常に取引を試みるという単純なアプローチは、価格の制約を適切に考慮していないと失敗します。 

## アプローチ

 ブルートフォースソリューションでは、取引のすべてのシーケンスをシミュレートし、Monocarp アイテムごとに他のどのアイテムが合法的に取得できるかをチェックし、改善が不可能になるまで繰り返します。 最悪の場合、このアプローチでは、取引ごとに利用可能な取引のセットが変更されるため、項目数が階乗的に複雑になります。 と$n, m \le 2 \cdot 10^5$、これはまったく不可能です。 

重要な洞察は、この問題が「到達可能な」アイテムのグラフとしてモデル化できるということです。つまり、一連の取引を通じて一方を直接または間接的にもう一方と交換できる場合、2 つのアイテムは同じ連結要素の一部となり得るということです。 このようなコンポーネント内で、Monocarp は最終的に最も高価なアイテムを収集できます。これは、取引ルールにより、コンポーネント内のアイテムを、価格が範囲内の他のアイテムと交換できるためです。$k$取引されたアイテムの。 したがって、最適な合計値は、単純に最大値の合計になります。`n`彼が最初に所有していたコンポーネント内のすべてのアイテムにわたるアイテム。 

これは、ソートベースの戦略を示唆しています。Monocarp のアイテムと他のキャラクターのアイテムの両方をソートすると、最低価格から最高価格までスイープし、差が最大であるアイテムをグループ化することで、連結成分を効率的に見つけることができます。$k$。 Union-Find (DSU) 構造を使用すると、コンポーネントをマージし、各コンポーネントの合計を効率的に追跡できます。 次に、クエリごとに$k$、2 つのソートされたリストを処理し、コンポーネントを構築し、Monocarp の初期項目を含む各コンポーネント内の最大の項目を合計することができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O((n+m)!) | O(n+m) | 遅すぎる |
 | 最適 | O((n+m) log(n+m) + q log q) | O(n+m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.Monocarpのアイテムを並べ替える`a`そして他のキャラクターのアイテム`b`。 これにより、価格が上昇する順に効率的に取引を処理することができます。 
2. すべての項目を、所有権を示すフラグ付きの 1 つのリストに結合します。 各要素はタプルです`(price, owner_flag)`どこ`owner_flag`は`0`Monocarp と`1`他のキャラクターの場合。 
3. この結合リストを並べ替えます。 このリストを徹底的に調べると、価格差 ≤ k の連続したアイテムを同じコンポーネントにマージできます。 
4. Union-Find (DSU) 構造を使用してコンポーネントを追跡します。 各コンポーネントは、その中のすべての項目の合計を保持します。 最初は、各アイテムは独自のコンポーネントです。 
5. 並べ替えられた結合リストを調べます。 価格差 ≤ k の連続するアイテムの各ペアについて、DSU を使用してコンポーネントをマージし、合計を更新します。 
6. すべてのマージの後、Monocarp の初期項目ごとに、そのコンポーネントの合計を求めます。 Monocarp が取得できる最大合計額は、彼の元のアイテムを少なくとも 1 つ含むコンポーネント内のアイテムの合計です。 
7. クエリごとに手順 3 ～ 6 を繰り返します。$k$。 

なぜ機能するのか: 不変条件は、各コンポーネントには現在の取引チェーンを通じて相互に交換できるすべてのアイテムが含まれていることです。$k$。 価格差を除いて取引には制約がないため、Monocarp は最終的にコンポーネント内のすべてのアイテムを入手できます。 したがって、最初の項目を含むコンポーネントの合計を合計すると、最適な答えが得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class DSU:
    def __init__(self, n, vals):
        self.parent = list(range(n))
        self.size = [1]*n
        self.sum = vals[:]
        
    def find(self, x):
        while x != self.parent[x]:
            self.parent[x] = self.parent[self.parent[x]]
            x = self.parent[x]
        return x
    
    def union(self, x, y):
        xroot = self.find(x)
        yroot = self.find(y)
        if xroot == yroot:
            return
        if self.size[xroot] < self.size[yroot]:
            xroot, yroot = yroot, xroot
        self.parent[yroot] = xroot
        self.size[xroot] += self.size[yroot]
        self.sum[xroot] += self.sum[yroot]

def solve():
    n, m, q = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    ks = list(map(int, input().split()))
    
    all_items = [(val, 0) for val in a] + [(val, 1) for val in b]
    all_items.sort()
    vals = [val for val, _ in all_items]
    owners = [owner for _, owner in all_items]
    
    for k in ks:
        dsu = DSU(n+m, vals)
        for i in range(len(all_items)-1):
            if vals[i+1] - vals[i] <= k:
                dsu.union(i, i+1)
        ans = 0
        for i in range(n+m):
            if owners[i] == 0:
                root = dsu.find(i)
                ans += dsu.sum[root]
                # Mark as used so we don't double count
                dsu.sum[root] = 0
        print(ans)

if __name__ == "__main__":
    solve()
```この実装では、DSU の初期化がクエリ処理から分離されます。 各クエリは DSU を再構築し、クエリの独立性を確保します。 各コンポーネントの合計は DSU に保存され、複数の Monocarp 項目が同じコンポーネント内にある場合の二重カウントを避けるために、カウント後にゼロに設定されます。
