 ## 解決策
 ## 問題の理解

 システムは、名前付きタスクの動的なコレクションを維持します。 各タスクには一意の文字列識別子があり、存在する場合は整数の優先度があり、小さいほど重要であることを意味します。 時間の経過とともに、タスクが追加、削除されたり、優先順位が変更されたりします。 さらに、時間は厳密には線形ではありません。システムの状態は逆方向にジャンプし、1 回の操作で前日のサフィックス全体を元に戻す可能性があります。 

クエリはいつでも特定のタスク名を尋ね、そのタスクよりも厳密に優先度が低い現在アクティブなタスクがいくつあるかをカウントする必要があります。 タスクが現在の状態に存在しない場合、答えは未定義であるため、-1 として報告する必要があります。 

主な問題は、状態が更新されるだけでなく、以前のスナップショットから派生した可能性のある以前のバージョンにロールバックできることです。 このため、根本的に問題は、過去の状態に高速にアクセスして進化するセットの履歴を維持することになります。 

この制約により、1 日あたりの対数または対数に近い演算が行われます。 最大 100,000 回の操作では、カウントを最初から再計算したり、元に戻すたびにグローバル構造を再構築したりするソリューションは、すぐに失敗します。 すべてのアクティブなタスクに対するクエリごとの線形スキャンでさえ、最悪の場合、約 10^10 の操作が必要となるため、遅すぎます。 

いくつかの微妙なケースがすぐに現れます。 タスクは複数回更新される場合があり、元に戻すと、タスクがまったく存在しなかった状態に戻る場合があります。 たとえば、タスクが 1 日目に設定され、2 日目に削除され、0 日目に戻す場合、クエリを実行すると、古い値ではなく「見つかりません」が正しく返される必要があります。 もう 1 つの注意が必要な状況は、複数のレイヤーにジャンプして元に戻す操作を繰り返すことです。 シングルステップの取り消しのみをサポートする単純なスタック ロールバックは、タイム ジャンプが任意であるため、ここで機能しません。 

## アプローチ

 直接シミュレーションでは、タスク名から優先順位、およびすべての優先順位のセットまでの辞書が保持されます。 各クエリは、スキャンまたは並べ替えによって、クエリされたタスクの優先度より小さい優先度がいくつあるかをカウントします。 これは概念的には機能しますが、制約の下ではすぐに壊れます。頻繁な挿入と削除でソートされた構造を維持することはバランスのとれた BST では問題ありませんが、元に戻す操作は線形タイムラインの前提を破壊します。 操作を最初から再実行して文字通り元に戻すと、各取り消しに O(q) のコストがかかり、二次的な動作が発生する可能性があります。 

中心的な観察は、システム全体が一連のバージョンとして進化し、毎日が完全な状態を定義するということです。 元に戻すでは過去の状態は変更されません。 現在のポインタを以前のバージョンにリダイレクトするだけです。 これにより、問題は永続的なデータ構造管理に変わります。 

すべてのバージョンで 2 種類の情報が必要です。 1 つの構造では、タスクが存在するかどうか、およびその現在の優先順位が何であるかを伝える必要があります。 別の構造では、「x より小さいものはいくつあるか」を効率的に回答できるように、すべてのアクティブな優先順位のマルチセットを維持する必要があります。 

これを実現する標準的な方法は、2 つのセグメント ツリーを永続的な形式で維持することです。 1 つのセグメント ツリーは、タスク名ごとに、その現在の優先順位 (または不在) を追跡します。 もう 1 つのセグメント ツリーは優先順位の頻度を追跡し、プレフィックスの合計からしきい値を下回るタスクの数を示します。 

毎日、前のバージョンから新しいバージョンが派生します。 操作が設定または削除された場合、最初に名前セグメント ツリー内のタスクの現在の優先度を確認し、古い値が存在する場合は削除してマルチセットを更新し、次に必要に応じて新しい値を挿入し、最後に名前セグメント ツリーを更新します。 操作が元に戻す場合は、古いバージョンのポインターを再利用するだけです。 

永続性により、元に戻す操作は構造的な再計算ではなく、単なるポインターの再割り当てであることが保証されます。

 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション | O(q²) | O(q) | 遅すぎる |
 | 永続セグメントツリー | O(q log q) | O(q log q) | 承認済み |

 ## アルゴリズムのチュートリアル

 集合演算に現れるすべての優先順位をソートされた配列に圧縮して、セグメント ツリーのインデックスとして使用できるようにします。 これが必要なのは、優先順位は 10^9 までですが、個別の値は最大 q 個しか存在しないためです。 

2 つの永続的なセグメント ツリーを維持します。1 つは現在の優先順位 (または存在しない場合は 0) を格納するタスク ID で、もう 1 つは頻度カウントを格納する圧縮優先順位です。 

また、文字列操作が配列インデックス付き操作になるように、タスク名から整数 ID へのマッピングも維持します。 

各日は次のように処理されます。 

1. 基本バージョンを決定します。 正常に動作している場合は前日のバージョンがベースとなります。 undo d の場合、ベースは i - d - 1 日目のバージョンになります。これにより、構築中の完全な状態が定義されます。 
2. 操作がクエリの場合、まずベース バージョンの名前セグメント ツリーからタスクの優先度を取得します。 存在しない場合は、-1 を出力します。 それ以外の場合は、この値より厳密に小さい優先順位の数をマルチセット セグメント ツリーに問い合わせます。 
3. 操作が設定されている場合は、ベース バージョンからタスクの古い優先度を再度取得します。 存在する場合は、その優先順位の 1 つの出現をマルチセット ツリーから削除します。 次に、新しい優先度をマルチセット ツリーに挿入します。 最後に、名前ツリーを更新して新しい優先度を保存します。 
4. 操作が削除の場合、古い優先度を取得します。 存在する場合は、マルチセット ツリーから削除し、名前エントリを「存在しない」に設定します。 
5. 結果として得られるセグメント ツリーのルートが、当日のバージョンになります。 

重要な不変条件は、すべてのアンドゥ ジャンプを含む最初の i 操作を正確に実行した後のシステム状態を各バージョンが完全に表すということです。 両方のセグメント ツリーは、すべてのバージョンで相互に一貫しています。マルチセット ツリーは、そのバージョンの名前ツリーに保存されている優先順位のセットを正確に反映します。 

すべてのクエリは部分的に更新された構造ではなく、完全なスナップショットから応答されるため、この一貫性によって正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, n):
        self.n = n
        self.sum = [0]
        self.ls = [0]
        self.rs = [0]

    def _new(self, v):
        self.sum.append(self.sum[v])
        self.ls.append(self.ls[v])
        self.rs.append(self.rs[v])
        return len(self.sum) - 1

    def update(self, v, l, r, idx, val):
        nv = self._new(v)
        if l == r:
            self.sum[nv] += val
            return nv
        m = (l + r) // 2
        if idx <= m:
            self.ls[nv] = self.update(self.ls[v], l, m, idx, val)
        else:
            self.rs[nv] = self.update(self.rs[v], m + 1, r, idx, val)
        self.sum[nv] = self.sum[self.ls[nv]] + self.sum[self.rs[nv]]
        return nv

    def query(self, v, l, r, ql, qr):
        if v == 0 or ql > r or qr < l:
            return 0
        if ql <= l and r <= qr:
            return self.sum[v]
        m = (l + r) // 2
        return self.query(self.ls[v], l, m, ql, qr) + self.query(self.rs[v], m + 1, r, ql, qr)

def solve():
    q = int(input())
    ops = []
    vals = []

    for _ in range(q):
        tmp = input().split()
        ops.append(tmp)
        if tmp[0] == "set":
            vals.append(int(tmp[2]))

    vals = sorted(set(vals))
    comp = {v: i + 1 for i, v in enumerate(vals)}
    m = len(vals)

    name_tree = SegTree(q + 5)
    freq_tree = SegTree(m + 5)

    name_root = [0] * (q + 1)
    freq_root = [0] * (q + 1)

    name_id = {}
    nxt_id = 1

    def get_name_id(s):
        nonlocal nxt_id
        if s not in name_id:
            name_id[s] = nxt_id
            nxt_id += 1
        return name_id[s]

    def get_val(root, idx):
        def _get(v, l, r):
            if v == 0:
                return 0
            if l == r:
                return name_tree.sum[v]
            mid = (l + r) // 2
            if idx <= mid:
                return _get(name_tree.ls[v], l, mid)
            else:
                return _get(name_tree.rs[v], mid + 1, r)
        return _get(root, 1, q + 5)

    for i in range(1, q + 1):
        op = ops[i - 1]
        typ = op[0]
        base = i - 1

        if typ == "undo":
            d = int(op[1])
            base = i - d - 1

        name_root[i] = name_root[base]
        freq_root[i] = freq_root[base]

        if typ == "set":
            s = op[1]
            x = comp[int(op[2])]
            nid = get_name_id(s)

            old = name_tree.query(name_root[base], 1, q + 5, nid, nid)
            if old:
                freq_root[i] = freq_tree.update(freq_root[i], 1, m, old, -1)

            freq_root[i] = freq_tree.update(freq_root[i], 1, m, x, 1)
            name_root[i] = name_tree.update(name_root[i], 1, q + 5, nid, x)

        elif typ == "remove":
            s = op[1]
            if s in name_id:
                nid = name_id[s]
                old = name_tree.query(name_root[base], 1, q + 5, nid, nid)
                if old:
                    freq_root[i] = freq_tree.update(freq_root[i], 1, m, old, -1)
                    name_root[i] = name_tree.update(name_root[i], 1, q + 5, nid, 0)

        elif typ == "query":
            s = op[1]
            if s not in name_id:
                print(-1)
                continue
            nid = name_id[s]
            px = name_tree.query(name_root[base], 1, q + 5, nid, nid)
            if px == 0:
                print(-1)
            else:
                res = freq_tree.query(freq_root[base], 1, m, 1, comp[px] - 1)
                print(res)
        else:
            pass

if __name__ == "__main__":
    solve()
```このソリューションは 2 つの独立した永続セグメント ツリーを構築します。1 つはタスク識別子によってインデックス付けされ、もう 1 つは圧縮優先度値によってインデックス付けされます。 各バージョンでは両方のツリーのルートが保存され、元に戻す操作は単純に以前のルートを再利用します。 クエリは常に完全に一貫性のあるスナップショットで動作します。 

実装の微妙な点は、毎日分離されたスナップショットを作成する必要があるため、更新は変更を連鎖させるのではなく、常にベース バージョンのルートから開始されることです。 もう 1 つの重要な点は、削除では周波数を減分する前に存在を確認する必要があるということです。そうしないと、削除を繰り返すとマルチセット ツリーが破損します。 

## 実用的な例

 サンプル入力を使用して、システムが時間の経過とともにどのように進化するかを追跡します。

 ## 特殊なケース

 タスクがバージョン間で複数回更新されると、古い状態のバグが簡単に露呈する可能性があります。 たとえば、タスクが設定されてから削除され、両方の操作の前にシステムが元に戻された場合、単純な実装で最後の変更が取り消されただけであっても、クエリを実行すると「not found」が返される必要があります。 永続バージョン ポインターは、タスクが存在しなかった以前の完全なスナップショットを復元することでこれを回避します。 

もう 1 つの障害モードは、元に戻す操作で複数のレベルにジャンプした場合に発生します。 一度に 1 つの操作のみをポップするスタックベースのロールバックでは、i 日目から i - d - 1 日目へのジャンプを正しく処理できません。 バージョン ルートを使用すると、履歴を再生することなく、任意の後方ジャンプで正しいスナップショットが選択されるだけになります。 

最後の微妙な問題は、存在しないタスクの削除の処理です。 周波数ツリーを更新する前に現在のバージョンでの存在を確認しないと、マルチセットが誤った負のカウントを蓄積する可能性があります。 スナップショットベースの古い値の取得では、すべての変更を実際に保存された状態に条件付けることでこれを防ぎます。
