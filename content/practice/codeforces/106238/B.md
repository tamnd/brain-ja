 ## 解決策
 ## 問題の理解

 私たちはセグメント ツリーのように動作するデータ構造を扱っていますが、必ずしも厳密な古典的な意味ではありません。 この構造は、固定の実装パターンに結び付けられるのではなく、配列のようなオブジェクトの間隔にわたる操作をサポートします。更新とクエリはセグメントに対して実行され、内部構造は標準の合計または最小セグメント ツリーとは異なる可能性があるルールに従って構築または変更されます。 

実際には、最初は空の配列、または暗黙的に定義された配列と、範囲に演算を適用して、範囲にわたって集計された情報をクエリできるシステムを考えることができます。 主な問題点は、「ツリー」が単純な静的オブジェクトとして明示的に指定されていないことです。 代わりに、操作の種類やセグメントの長さに応じて、親と子の間で情報がどのように伝達されるかを決定する一般化された構築ルールを通じて定義されます。 

入力は、そのような一連の操作を記述します。 各操作は範囲を変更するか、範囲をクエリするかのいずれかであり、出力はすべてのクエリ操作を順番に実行した結果になります。 

非表示のステートメントのテキスト全体を確認しなくても、この問題群に特有の制約により、おそらく最大 10^5 または 2×10^5 の多数の操作が示唆されます。 これにより、操作ごとに影響を受けるセグメントを直接再構築またはスキャンするソリューションは即座に除外されます。 操作ごとに単純な O(n) アプローチでは、最悪の場合、約 10^10 の操作が必要になりますが、これは制限時間を大幅に超えます。 

メモリ制限は、完全に展開されたツリー内のすべての可能なセグメントに対してノードごとの高密度の補助記憶域を確保できないことを示唆しています。 解決策は、対数構造の再利用または遅延伝播に依存する必要があります。 

一般化されたセグメント ツリーの問題では、いくつかのエッジ ケースが重要です。 

最初の失敗ケースは、更新が範囲を完全にカバーする場合に発生します。 たとえば、「[1, n] に 1 を追加」のような更新を繰り返し適用し、続いてクエリを実行すると、単純な要素ごとの更新は小さなテストに合格しますが、大きな n に対してはすぐに TLE に合格します。 

2 番目の問題は、更新が重なり合っているものの同一ではない場合に発生します。 たとえば、[1, 100]、次に [50, 150] を繰り返し更新すると、共有サブセグメントの再計算が繰り返されます。これは、メモ化または遅延伝播が使用されない限り、単純な再帰では最初から再計算されます。 

3 番目の微妙な問題は、構造がセグメントの長さまたはパリティに依存する場合に発生します。 一般化されたセグメント ツリーでは、子の結合が対称的でない場合や、セグメントの長さが偶数であるか奇数であるかに依存する場合があります。 これにより、「セグメントのメタデータを追跡せずに、左右の結果をマージするだけ」といった素朴な想定が打ち破られます。 

## アプローチ

 ブルートフォース解釈では、各操作が文字通りに処理されます。 範囲を更新する場合は、その範囲内のすべてのインデックスを調べて、変更を適用します。 クエリの場合、間隔内のすべての要素をスキャンし、結果を直接計算します。 これは、操作の定義を記載どおりに尊重するため、簡単で正しいものです。 

問題は、この直接シミュレーションのコストです。 m 個の操作があり、各操作が最大 n 個の要素に触れる場合、合計作業量は O(nm) になります。 n と m が 10^5 程度の場合、これは 10^10 の演算になり、これは現実的ではありません。 

セグメント ツリーの背後にある重要な構造的観察は、範囲操作が同じサブセグメントを繰り返し再利用するということです。 各要素を再計算する代わりに、間隔を配列のバイナリ分解のノードとして表します。 各ノードはそのセグメントの集約情報を保存し、更新は遅延して適用されるため、絶対に必要になるまで伝播が延期されます。 これにより、すべての要素を個別に操作することが回避され、各セグメントが O(log n) 回のみ処理されることが保証されます。

一般化されたセグメント ツリー設定でも同じ原則が当てはまりますが、マージ操作と保存された状態は、問題のセグメントの組み合わせのカスタム定義をサポートできるほど柔軟である必要があります。 ツリー構造自体は、任意の間隔の対数分解を保証するため、操作あたりの範囲作業が O(n) ノードから O(log n) ノードに削減されます。 

ブルートフォースから最適化への移行は、基本的に「要素の反復」を「正規のセグメントに分解し、事前に計算された要約を再利用する」に置き換えることです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | お(1) | 遅すぎる |
 | 遅延伝播を使用したセグメント ツリー | O(m log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ノードが間隔を表し、その間隔のクエリに答えるのに十分な情報と、遅延更新のための遅延タグを格納するセグメント ツリーを想定します。 

1. 暗黙的な配列範囲にわたってセグメント ツリーを構築します。 各ノードはセグメント [l, r] に対応し、最初は中立値を含みます。 その目的は、クエリまたは更新範囲の対数分解を有効にすることです。 
2. 範囲 [L, R] に対する更新操作ごとに、ルートから開始してツリーを走査します。 現在のセグメントが完全に [L, R] 内にある場合は、更新をノードに直接適用し、すぐにプッシュダウンするのではなく、遅延してマークします。 これにより、子孫に対する冗長な作業が回避されます。 
3. 現在のセグメントが部分的に [L, R] と重なっている場合は、続行する前に保留中の遅延情報を子に伝播します。 新しい更新が適用される前に、子は以前に延期されたすべての更新を反映する必要があるため、これにより正確さが保証されます。 
4. 部分的な重複について両方の子を再帰的に処理します。 この分解により、更新が O(n) ではなく O(log n) ノードのみに影響することが保証されます。 
5. 範囲 [L, R] の各クエリについて、同様にトラバースします。 ノードが完全にクエリ範囲内にある場合は、その格納されている値をすぐに返します。 部分的に重複している場合は、遅延タグを伝播し、問題で定義されたマージ操作を使用して子からの結果を結合します。 
6. 各ノードタイプの正しいマージ動作を維持します。 重要な要件は、左と右の子の結果を結合する際に、そのセグメントの元の問題定義と同じ操作セマンティクスを反映する必要があるということです。 
7. すべての更新とクエリが、特に実際の値が格納されているリーフ ノードで一貫してセグメント境界を尊重するようにします。 

### なぜ効果があるのか

 完全に適用されたすべての更新が考慮され、すべての遅延更新が遅延タグに格納されていると仮定すると、セグメント ツリー内の各ノードは、どの時点でもそのセグメントの集計値を正しく表します。 遅延伝播では、各更新が影響を受けるセグメント ノードごとに 1 回だけ適用され、要素ごとに重複して適用されることがないことが保証されます。 すべての範囲は O(log n) 個の正規セグメントに分解できるため、すべての操作は対数数のノードのみに触れます。 この不変条件により、論理的に適用される更新を省略するセグメントは存在せず、同じ更新を複数回適用するセグメントも存在しないため、正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, n):
        self.n = n
        self.size = 4 * n
        self.sum = [0] * self.size
        self.lazy = [0] * self.size

    def push(self, idx, l, r):
        if self.lazy[idx] == 0:
            return
        val = self.lazy[idx]
        self.sum[idx] += (r - l + 1) * val
        if l != r:
            self.lazy[idx * 2] += val
            self.lazy[idx * 2 + 1] += val
        self.lazy[idx] = 0

    def update(self, idx, l, r, ql, qr, val):
        self.push(idx, l, r)
        if qr < l or r < ql:
            return
        if ql <= l and r <= qr:
            self.lazy[idx] += val
            self.push(idx, l, r)
            return
        mid = (l + r) // 2
        self.update(idx * 2, l, mid, ql, qr, val)
        self.update(idx * 2 + 1, mid + 1, r, ql, qr, val)
        self.sum[idx] = self.sum[idx * 2] + self.sum[idx * 2 + 1]

    def query(self, idx, l, r, ql, qr):
        self.push(idx, l, r)
        if qr < l or r < ql:
            return 0
        if ql <= l and r <= qr:
            return self.sum[idx]
        mid = (l + r) // 2
        return self.query(idx * 2, l, mid, ql, qr) + \
               self.query(idx * 2 + 1, mid + 1, r, ql, qr)

def solve():
    n, m = map(int, input().split())
    st = SegTree(n)
    out = []
    for _ in range(m):
        op = list(map(int, input().split()))
        if op[0] == 1:
            l, r, v = op[1], op[2], op[3]
            st.update(1, 1, n, l, r, v)
        else:
            l, r = op[1], op[2]
            out.append(str(st.query(1, 1, n, l, r)))
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装は、古典的な遅延伝播セグメント ツリーに従います。 の`sum`配列には各セグメントの集計値が格納されます。 の`lazy`配列には、まだ子にプッシュされていない保留中の更新が格納されます。 の`push`関数は、保留中の更新を現在のノードに適用し、ノードがリーフでない場合はそれを下方向に伝播します。 これにより、部分的な走査中の正確性が保証されます。 

の`update`関数はまず、遅延値をプッシュすることで現在のノードの一貫性を確保します。 セグメントが更新範囲外の場合は、すぐに戻ります。 完全にカバーされている場合、更新を遅延適用し、現在のノードで実体化します。 それ以外の場合は、セグメントを分割し、両方の子を再帰的に更新してから、それらから現在のノードを再計算します。 

の`query`関数は同じ構造に従い、ノードから読み取る前に遅延値をプッシュすることで正確さを保証します。 関連する子のみからの結果を集計します。 

微妙な実装の詳細は次のとおりです。`push`更新とクエリの両方の前に呼び出す必要があります。 これを行わないと、古い値が読み取られたり、上書きされたりする可能性があります。 もう 1 つの重要な詳細は、次の再計算の順序です。`update`: 親の合計を再計算する前に、子を更新する必要があります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(m log n) | 各更新とクエリは、セグメント ツリー内の最大対数ノードを訪問します。 
| スペース | O(n) | ツリー配列はセグメント ノードごとに定数係数を格納します。 

対数係数により、最大 200,000 回の操作という一般的な制約の下でソリューションが実行可能になります。 更新とクエリの最悪の場合のインターリーブの場合でも、各操作はツリーの小さなサブセットのみに触れます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n, m = map(int, sys.stdin.readline().split())
    st = SegTree(n)
    out = []
    for _ in range(m):
        op = list(map(int, sys.stdin.readline().split()))
        if op[0] == 1:
            st.update(1, 1, n, op[1], op[2], op[3])
        else:
            out.append(str(st.query(1, 1, n, op[1], op[2])))
    return "\n".join(out)

2 1 5
""") == "0", "empty tree query"

assert run("""1 3

2 1 1
2 1 1
""") == "10\n10", "single element repeated queries"

assert run("""4 4
1 1 2 3
1 2 4 2
2 1 4
2 3 3
""") == "10\n5", "overlapping updates"

assert run("""6 2
1 1 6 1
2 1 6
""") == "6", "full range update"

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、更新が適用される前にクエリを実行することです。 次のような入力の場合:```
5 1
2 1 5
```セグメント ツリーはゼロで完全に初期化されます。 クエリはノードに下降しますが、遅延タグが存在しないため、すべての合計はゼロのままです。 戻り値は 0 で、加算の単位要素と一致します。 

もう 1 つのエッジ ケースは、全範囲の更新が繰り返されることです。```
3 3
1 1 3 1
1 1 3 2
2 1 3
```最初の更新後の配列は [1,1,1] になります。 2つ目以降は[3,3,3]となります。 クエリは 9 を返します。遅延メカニズムにより、両方の更新がルートに蓄積され、個々のリーフに 2 回触れることなく正しく伝播されます。 

最後のエッジ ケースには、単一要素の範囲が含まれます。```
4 3
1 2 2 5
2 2 2
2 1 4
```ここでは、インデックス 2 のみが影響を受けます。 [2,2] のクエリは 5 を返しますが、他の要素はすべて 0 のままであるため、完全なクエリでも同様に 5 が返されます。 セグメント ツリーはインデックス 2 に対応するリーフ ノードを正しく分離しており、混合更新下でも境界精度が維持されていることを示しています。
