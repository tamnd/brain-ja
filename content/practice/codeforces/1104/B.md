 ## 解決策
 ## 問題の理解

 小文字で構成される単一の文字列が与えられます。 2 人のプレイヤーが交互にターンを行い、移動は、現在の文字列内で隣り合った同一の文字のペアを選択し、両方を削除することで構成されます。 削除後は文字列が閉じられるため、新しい隣接ペアが形成され、再生可能になる場合があります。 

プレーヤーが削除できる有効な隣接する等しいペアを持たない場合、ゲームは終了し、そのプレーヤーは負けます。 両方のプレイヤーは最適なプレイを行うと想定されます。つまり、常に勝つ可能性を最大化する手を選択します。 

文字列の長さは最大 100,000 です。 これにより、移動ごとに文字列の大部分を再スキャンまたはコピーするという単純な方法で削除を繰り返しシミュレートする戦略は即座に除外されます。 移動ごとに線形であっても、最悪の場合、解が二次関数に劣化する可能性があり、これは非常に遅すぎます。 

複数の素なペアが存在する場合、微妙な問題が発生します。 素朴なアプローチでは、ペアの削除は文字列の残りの部分から独立していると想定するかもしれませんが、削除により境界を越えて新しい隣接するペアが作成され、利用可能な動きが変更される可能性があります。 たとえば、次のような文字列では`"abba"`、真ん中を削除`"bb"`生成する`"aa"`、最初は存在しなかった新しい動きを作成します。 正しい推論では、ペアを孤立したものとして扱うのではなく、これらの連鎖反応を説明する必要があります。 

もう 1 つの明らかではない点は、最適な移動とは特定のペアを選択することではなく、現在の構成に少なくとも 1 つの移動が存在するかどうかであるということです。 構造を理解すると、削除の正確な位置ではなく、考えられる削除の数の同等性のみが重要であることがわかります。 

## アプローチ

 直接的な総当たりシミュレーションでは、文字列が維持され、各ターンで隣接する等しいペアをスキャンして削除し、これを繰り返します。 削除のたびに文字列のサフィックス全体が移動する可能性があり、新たなスキャンが必要になる場合があります。 最悪の場合、例えば、`"aaaaaa...."`、各除去には線形時間がかかり、線形除去が存在するため、二次の複雑さが生じます。 これは 100,000 文字では合格しません。 

重要な観察は、このゲームは、戦略に関係なく、隣接する等しいペアが出現する場所で繰り返し崩壊するのと同じであるということです。 スタックを使用した処理を考えると、スタックのトップに等しいキャラクターが現れるたびに、そのキャラクターは全滅します。 そうでなければ、私たちはそれを押します。 これは、文字列キャンセル問題で使用されるものと同じ削減プロセスです。 

重要な構造的洞察は、すべての有効な移動によって、生き残る一致しない文字の数が決定論的な方法で減少し、最終的な縮小形式は削除の順序に関係なく一意であるということです。 最終的なスタック削減文字列を計算すると、プロセス中に実行される移動数が固定されます。 

プレーヤーは交互に手を動かすため、勝者は純粋にこの完全な削減における合計の手数が奇数か偶数かによって決まります。 削除の合計数がゼロの場合、最初のプレイヤーは何も動かず、すぐに負けます。 

これにより、ゲームは短縮された文字列長のシングルパス計算に変換されます。

 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n²) | O(n) | 遅すぎる |
 | スタック削減 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 文字列の現在の縮小状態を表すために空のスタックを初期化します。 

スタックには、隣接する一致によってまだキャンセルされていない文字のみが保持されます。 
2. 文字列を左から右に繰り返します。 

各文字で、現在のスタックの最上位と比較します。 
3. スタックが空でなく、先頭が現在の文字と等しい場合は、スタックをポップします。 

これは、隣接する等しい文字のペアを削除することに正確に対応します。 
4. それ以外の場合は、現在の文字をスタックにプッシュします。 

これは、キャラクターには現時点で即時キャンセルの機会がないことを意味します。 
5. 文字列全体を処理した後、次のように削除数を計算します。$$\text{moves} = \frac{n - |\text{stack}|}{2}$$それぞれの削除により、正確に 2 文字が削除されます。 
6. もし`moves`これは奇妙で、最初のプレイヤーが最後の動きをして勝ちます。 それ以外の場合は、2 番目のプレーヤーが勝ちます。 

### なぜ効果があるのか

 スタック プロシージャは、有効な一連の正当な手の場合と同じ最終的な縮小文字列を生成する、決定的な順序ですべての可能な隣接キャンセルをシミュレートします。 すべての移動により、隣接する等しいペアが 1 つだけ削除され、展開中の文字列内で現在隣接していない文字には影響を与えることはできません。 不変条件は、各プレフィックスを処理した後、考えられるすべての有効な削除順序の下で、そのプレフィックスの縮小された形式がスタックに正確に含まれるということです。 この縮小形式は独特であるため、削除の総数は固定されており、ゲームは単純なパリティ チェックになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    st = []

    for c in s:
        if st and st[-1] == c:
            st.pop()
        else:
            st.append(c)

    moves = (len(s) - len(st)) // 2
    print("Yes" if moves % 2 == 1 else "No")

if __name__ == "__main__":
    solve()
```実装では標準のスタック シミュレーションを使用します。 唯一の微妙な点は、各キャンセルでちょうど 2 文字が削除されるため、移動数は元の長さと最終的なスタック サイズの差から計算されることです。 

最後のパリティ チェックでは、ゲーム結果全体がエンコードされます。 これ以上のターンのシミュレーションは必要ありません。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    s = input().strip()
    st = []

    for c in s:
        if st and st[-1] == c:
            st.pop()

# provided sample
assert run("abacaba\n") == "No"

# all equal pairs
assert run("aaaa\n") == "Yes"

# no moves possible
assert run("abcde\n") == "No"

# alternating pairs
assert run("aabb\n") == "Yes"

# nested chain reactions
assert run("abba\n") == "Yes"

 ## 特殊なケース

 のような文字列の場合`"abcde"`、スタックは決してポップを実行しません。 スタックは元の文字列と同じで終了するため、移動 = 0 となり、最初のプレイヤーはすぐに負けます。 

のために`"aaaa"`、各ステップでプッシュとポップが交互に行われ、空のスタックが残ります。 計算された手数は 2 であり、これは偶数であり、2 番目のプレーヤーが勝つことを意味します。 スタックの動作は、2 つの独立した削除を直接反映します。 

のために`"abba"`、最初の 2 文字がキャンセルされ、残りの文字がキャンセルされます。`"ba"`逆の順序で隣接すると、別のキャンセルが発生します。 スタックは空で終了し、2 つの移動をもたらし、奇数パリティによる先手の勝利を正しく識別します。
