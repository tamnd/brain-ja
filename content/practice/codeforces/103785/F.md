 ## 解決策
 ## 問題の理解

 私たちは、固定数の「パッチ ケーブル」が限られたリソースとして機能し、増加するコンピューター セット全体にアップデートを配布する伝播プロセスをシミュレートしています。 このプロセスは、すでにアップデートされている 1 台のコンピュータから始まり、各ステップで、利用可能なケーブルを使用してアップデートされるコンピュータの数を拡大しようとします。 各ケーブルにより、1 ステップで 1 つの追加接続が効果的に可能になりますが、有効な接続の数は、現在すでに更新されているコンピュータの数によっても制限されます。 

状態は 2 つの整数で完全に記述されます。 1 つは現在の更新されたコンピューターの数で、最初は 1 です。もう 1 つはパッチ ケーブルの数で、プロセス全体を通じて一定のままです。 各反復では、更新されたマシンの現在のフロンティアを完全に利用するのに十分なケーブルがあるかどうかに応じて、更新されるコンピューターの数を増やし、n 台のコンピューターすべてが更新されるまで繰り返します。 

出力は、少なくとも n 個の更新されたコンピューターに到達するために必要なステップ数です。 

複雑さの観点から見ると、n は十分に大きいため、1 ずつ増加するシミュレーションや各コンピューターを個別に処理するシミュレーションは遅すぎる可能性があります。 重要な観察は、リソースが十分である場合、現在の状態の値が少なくとも幾何学的に増加するため、最良の状況では反復回数が n で対数になるということです。 これにより、ソリューションは O(log n) または O(log n) の償却時間予想内にしっかりと配置され、ステップごとの O(n) の拡張が除外されます。 

パッチ ケーブルが非常に小さい場合、特にパッチ = 0 の場合、微妙なエッジ ケースが発生します。その状況では、プロセスは最初のコンピューターを超えて拡張できません。そのため、n > 1 の場合、素朴な仮定の下では答えに到達することは不可能です。 もう 1 つのエッジ ケースは、パッチが n に比べて極端に大きい場合に発生し、各ステップで成長が直ちに 2 倍になります。 

不用意に実装すると、線形成長を誤って仮定したり、成長の上限を n に設定できなかったりして、不必要な反復やオーバーフローが発生する可能性があります。 

## アプローチ

 プロセスのブルート フォース解釈は簡単です。更新されたコンピューターの数を維持し、1 ステップで到達できる新しいコンピューターの数に関するルールを繰り返し適用し、カウントが n に達したら停止します。 各反復では、現在の更新されたマシンの数とケーブルの数の間の最小値として寄与分が計算されます。 これは正しいです。更新された各マシンは、ステップごとに最大 1 つの発信接続に寄与でき、各ケーブルはステップごとに 1 回しか使用できないためです。 

ただし、n が大きい場合、このシミュレーションは非効率になります。 最悪の場合、patch が n に匹敵する場合、反復回数は少なくなりますが、patch が n に比べて小さい場合、依然として多くのステップが必要となり、各ステップで追加される増分はわずかです。 ブルート フォース アプローチでは、反復ごとに O(1) の処理が行われますが、O(n) 回の反復が必要になる場合があり、n が大きい場合は遅すぎます。 

重要な洞察は、プロセスが、アクティブなコンピューターの数とケーブルの数の 2 つの量の小さい方によって完全に制御されるということです。 アクティブなコンピュータの数がケーブルの数以下の場合、増加は倍増して、実質的に現在の状態の 2 倍になります。 アクティブなコンピュータの数がケーブルの数を超えると、増加は線形になり、各ステップでケーブルの数に等しい固定量ずつ増加します。 これにより、指数関数的フェーズとそれに続く線形フェーズという 2 つのフェーズのシステムが生成されます。 各ステップは現在の値のみに依存するため、アルゴリズムは、ノードごとの作業を行わずにこれらの遷移をシミュレートすることになります。

 | ブルートフォースシミュレーション | O(n) 最悪の場合 | お(1) | 遅すぎる |
 | 位相ベースのシミュレーション | O(log n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 更新されたコンピュータの数を 1 に、ステップ カウンタを 0 に初期化します。これは、システムが 1 台の感染済みマシンから開始することを表します。 
2. 更新されたコンピュータの数が n 未満である場合、現在のステップで到達できる新しいコンピュータの数を決定します。 
3. 現在の更新されたコンピュータの数とケーブルの数の間の最小値として増分を計算します。 これは、更新された各コンピュータが提供できる発信接続は最大 1 つですが、利用可能なケーブルの数にも制限があるという事実を反映しています。 
4. この増分を、現在の更新されたコンピューターの数に追加します。 これにより、1 つの伝播ステップの後に到達可能なセットが更新されます。 
5. ステップ カウンタを 1 つ増やして、1 単位時間が経過したことを記録します。 
6. 更新されたコンピュータの数が n に達するか、それを超えるまで繰り返します。 

なぜ機能するのか: 重要な不変条件は、各反復後に値が`curr`は、そのステップ数のプロセスの制約を考慮して、到達できるコンピューターの最大数を正確に表します。 更新ルールは、供給 (現在更新されているコンピューター) と容量 (パッチ ケーブル) の間のボトルネックを正確にモデル化します。 各ステップでは 2 つの制限のうち小さい方を完全に使い果たすため、隠れた容量が未使用のまま残されることはなく、シミュレーションで到達可能なノードが過小評価されたり過大評価されたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, patch = map(int, input().split())
    
    curr = 1
    hours = 0
    
    while curr < n:
        curr += min(curr, patch)
        hours += 1
    
    print(hours)

if __name__ == "__main__":
    solve()
```この実装は、前述の状態遷移を直接反映しています。 変数`curr`すでに更新されているコンピューターの数を追跡します。`patch`固定されています。 各ループ反復では、次を使用して正しい増分が計算されます。`min(curr, patch)`、利用可能なソースと利用可能なケーブルの間のボトルネックをエンコードします。 

よくある間違いは、誤って使用することです`curr += patch`無条件に成長を過大評価する`curr < patch`。 もう1つは、次の点に止まらないことです。`n`これにより、ターゲットを超えて不必要に増加したり、他の言語でオーバーフローが発生したりする可能性があります。 ループ条件により、必要な数に達したときに確実に終了します。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    hours = 0
    
    while curr < n:
        curr += min(curr, patch)
        hours += 1
    
    return str(hours)

 ## 特殊なケース

 エッジ ケースの 1 つは、n が 1 に等しい場合です。条件が次のとおりであるため、アルゴリズムは正しく 0 を返します。`curr < n`は最初は false であるため、伝播は必要ありません。 

もう 1 つの特殊なケースは、パッチが非常に大きい場合です。 入力用`n = 8, patch = 100`最初の繰り返しでは、curr が 1 から 2、次に 2 から 4、次に 4 から 8 に設定されます。ループは 3 つのステップで終了し、大きなパッチ値は関係なくなります。 これにより、`min(curr, patch)`過剰な容量を安全に処理するための処方です。 

3 番目のエッジ ケースは、パッチが 1 の場合です。`n = 6, patch = 1`、進行は 1 → 2 → 3 → 4 → 5 → 6 で、5 つのステップが必要です。 各ステップは、線形レジームの動作に一致する新しいノードを 1 つだけ提供し、しきい値に達するとループは正常に終了します。
