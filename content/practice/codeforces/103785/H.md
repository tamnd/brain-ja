 ## 解決策
 ## 問題の理解

 行に配置された要素を表す一連の整数が与えられます。 許可される操作は位置によって異なります。要素が現在その位置にある場合$k$(1-インデックス付き) 値が正確にあります$k$の場合、その要素は削除の対象になります。 

このプロセスは任意ではありません。 複数の削除可能な要素が存在する場合は、それらの中で最も右の要素を強制的に削除する必要があります。 削除するたびに残りの要素のインデックスが変更されるため、削除可能な位置のセットは時間の経過とともに進化します。 ここでのタスクは、このルールを繰り返し適用してすべての要素を完全に削除できるかどうかを判断することです。 可能であれば、要素が削除される順序も出力する必要がありますが、削除プロセスの逆に報告されます。 

重要な点は、除去が独立していないことです。 要素を早期に削除すると、位置が移動するため、他の要素の削除可能性が露出したり破壊されたりする可能性があります。 インデックスは静的ではなく動的であるため、「a[i] = i である任意のインデックス i」を独立してチェックする単純な解釈は失敗します。 

制約は十分小さいので、$O(n^2)$シミュレーションは許容されます。 これは、各ステップでアレイ全体の線形スキャンが可能であり、最大で次のステップを実行できることを示唆しています。$n$除去、せいぜい与える$O(n^2)$total operations. グローバルな再計算の繰り返しに依存するソリューションは、依然として安全です。 

いくつかの失敗例は、不用意なアプローチから自然に発生します。 1 つは、左端の有効な要素を常に削除できると仮定することです。 たとえば、次のように考えてみましょう$[1, 2, 3]$。 最初に 1 を削除すると、配列がシフトされ、「右端の必須削除」ルールに基づいて、後の削除に必要な構造が破壊されます。 正しいプロセスは順序に依存しており、貪欲な方向性が重要です。 

もう 1 つの落とし穴は、削除のたびにインデックスが変更されることを忘れていることです。 値を元のインデックスを参照しているかのように扱うと、次のような場合に誤った削除が発生します。$[2, 1, 3]$、有効な削除のみが動的な再インデックスに依存します。 

## アプローチ

 この強引なアイデアは、文字通りプロセスをシミュレートすることです。 各ステップで、配列をスキャンし、次のすべての位置を見つけます。$a[i] = i$、そのような位置の右端を選択し、削除して続行します。 各スキャンにかかる費用$O(n)$、そして私たちは最大で行うことができます$n$引っ越し、寄付$O(n^2)$複雑。 これは制限内で機能しますが、スキャンとシフトを繰り返すと非効率になります。 

重要な観察は、このプロセスが、現在「正しい」右端の位置を繰り返し削除するのと同じであるということです。 ポジションが削除可能になり、それが最右候補であるときに削除しないことを選択すると、後で削除することはできません。 これは、右側にあるものを削除してもインデックスの状態には影響しませんが、左側にあるものを削除するとインデックスの状態がシフトされ、等価性が永久に損なわれるという事実から来ています。 したがって、有効な右端の除去を延期すると、取り返しのつかない損害が生じます。 

これにより、右端のインデックスを繰り返し見つけるというクリーンな貪欲戦略が生まれます。$i$そのような$a[i] = i+1$、すぐに削除して続行してください。 正確さはインデックス シフトの単調性に左右されます。左側の削除のみが位置のインデックスに影響するため、右端の有効な要素は安全にコミットできます。

 ## アルゴリズムのチュートリアル

 配列を維持し、すべてが削除されるか、有効な削除が存在しなくなるまで要素を繰り返し削除します。 

1. 現在の配列と空のリストから開始します`ans`削除された要素を削除順に記録します。 目標は、完全な有効な削除シーケンスを再構築することです。 
2. 配列を右から左にスキャンして、最大のインデックスを見つけます。$i$そのような$a[i] = i+1$。 これにより、常に右端の取り外し可能な要素を選択するというルールが尊重されます。 
3. そのようなインデックスが存在しない場合、プロセスは停止します。 操作が許可されていないため続行できないため、NOを出力して終了します。 
4. そのようなインデックスが見つかった場合は、その要素を配列から削除し、その値を配列に追加します。`ans`。 削除すると、インデックスの後のすべての要素がシフトされます$i$1 つの位置を残して、将来のチェックのためにインデックスを変更します。 
5. 配列が空になるまでこのプロセスを繰り返します。 
6. 最後に反転します`ans`そしてそれを出力します。 要素を削除順序で記録しましたが、問題では逆の順序が求められているため、逆転が必要です。 

なぜ効果があるのか

 重要な不変条件は、特定のステップで右端の有効な位置にない要素は、スキップした場合に後で安全に削除できないことです。 要素を厳密に左側に削除すると、そのインデックスがシフトされ、等価条件が永久に破壊されます。 右側の要素を削除しても影響はありません。 したがって、取り外し可能な要素が存在する場合、安全で元に戻せない唯一の選択肢は右端の要素です。 これにより、貪欲な選択が必要かつ十分となり、完全な削除命令が存在する場合に限り、繰り返し適用すると最終的にすべての有効な削除が使い果たされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    ans = []

    for _ in range(n):
        idx = -1

        for i in range(len(a) - 1, -1, -1):
            if a[i] == i + 1:
                idx = i
                break

        if idx == -1:
            print("NO")
            return

        ans.append(a[idx])
        a.pop(idx)

    print("YES")
    print(*ans[::-1])

if __name__ == "__main__":
    solve()
```実装は貪欲なプロセスに直接続きます。 内側のループは最後から検索して、右端の有効な位置を選択します。 の`pop`操作ではその要素が削除され、配列がシフトされ、後続の反復で正しいインデックスが自然に維持されます。 最後の逆転は、`ans`出力を必要な順序に揃えます。 

微妙な点は、`i + 1`比較では。 これは、条件内の 1 から始まるインデックス付けを反映していますが、Python 配列は 0 から始まります。 慎重に位置合わせを行うことで、検証中の off-by-one エラーを回避できます。 

## 実用的な例

 配列を考慮してください$[1, 2, 3]$。 

### トレース 1

 | ステップ | 配列 | 見つかったインデックス | 削除されました |
 | --- | --- | --- | --- |
 | 1 | [1、2、3] | 2 (3=3) | 3 |
 | 2 | [1、2] | 1 (2=2) | 2 |
 | 3 | [1] | 0 (1=1) | 1 |

 撤去命令は、$[3, 2, 1]$、そして逆にすると、$[1, 2, 3]$。 これにより、完全に一貫性のある配列がルールに従ってきれいに折りたたまれることが確認されます。 

### トレース 2

 検討してください$[2, 1, 3]$。 

| ステップ | 配列 | 見つかったインデックス | 削除されました |
 | --- | --- | --- | --- |
 | 1 | [2、1、3] | 2 (3=3) | 3 |
 | 2 | [2、1] | なし | 失敗 |

 ここでは、条件を満たすポジションがないため、プロセスが早期に停止します。 これは、一部の要素が最初にそのインデックスと一致したとしても、すべての順列が解決できるわけではないことを示しています。 

トレースは、アルゴリズムが右端の有効な削除の必要性を正しく強制し、有効な状態が残っていない場合に失敗を検出することを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、最初は最後の要素のみが有効である場合です。 たとえば、$[2, 3, 1]$、最後の位置のみが条件を満たします。 アルゴリズムはそれを即座に選択し、正確さを保証します。 除去後、残った構造は小さくなり、不変条件を維持しながらきれいに再評価されます。 

もう 1 つのケースは、複数の有効な位置が存在するが、右端のみが安全である場合です。 で$[1, 3, 2]$、最初は位置 1 と位置 3 の両方が有効です。 アルゴリズムは最初に位置 3 を選択します。 代わりに位置 1 を削除すると、後の要素がシフトされ、将来の有効性が破壊され、デッド状態につながります。 一番右のルールは、この障害パスを防ぎます。 

最後の微妙なケースは、シフトにより有効性が後で現れる場合です。 で$[2, 1, 3, 4]$、右端が有効であるため、最初に 4 を削除する必要があります。 そうして初めて、次の正しい構造が現れます。 アルゴリズムは、古い位置に依存するのではなく、削除のたびに有効性を再計算するため、これを自然に処理します。
