 ## 解決策
 ## 問題の理解

 私たちは提出物に関する一連のイベントを処理します。各提出物は、その試行で正しく解決された一連のサブタスクにすぎません。 サブタスクは整数で識別され、1 つのサブタスクで複数のサブタスクをカバーできる場合があります。 時間が経つと、提出物は無効になり、実質的に検討対象から外される可能性があります。 

私たちは、現在スコアに「貢献」している投稿の数を常に数えたいと考えています。 少なくとも 1 つのサブタスクが存在し、このサブタスクがまだ有効なすべてのサブタスクの中でこのサブタスクを含む最初のサブタスクである場合、サブミッションは貢献します。 

これを言い換えると便利な方法は、各サブタスクが「現在の最も古いアクティブな所有者の送信」を維持していると想像することです。これは、まだ有効であり、このサブタスクを含む (入力順で) 最も古い送信を意味します。 少なくとも 1 つのサブタスクの最も古いアクティブな所有者である場合、提出はカウントされます。 

3つの操作があります。 最初の例では、送信を作成し、そのサブタスクをリストします。 2 つ目は、以前に作成された送信を無効にします。 3 番目は、上記の意味で、現在少なくとも 1 つのサブタスクを所有している提出物の数を尋ねます。 

この制約により、すべてのクエリにわたって、ほぼ線形または線形に近い総作業量が課せられます。 すべてのサブタスクのすべてのサブタスクの合計は最大 2 · 10 ^ 5 であり、クエリの数もテスト スイートごとに最大 2 · 10 ^ 5 です。 これにより、クエリごとにすべてのアクティブな送信を再スキャンしたり、グローバル所有権を最初から繰り返し再計算したりするものは即座に除外されます。 過去のすべての送信に対してタイプ 3 クエリごとに再計算を試みるソリューションは、二次的な動作に低下します。 

主な微妙な点は、無効化がサブタスクに対してローカルではないことです。 1 つの送信を削除すると、複数のサブタスクが後の送信に「フォールバック」する可能性があり、それらの更新はグローバルに反映される必要があります。 単純な間違いは、どの提出物がそのサブタスクの新しい所有者になるかを追跡せずに、無効化されたサブタスクごとに回答をローカルで更新するだけであることです。 

2 番目の微妙なケースは、同じサブタスクを共有する複数の送信です。 最も古い、まだ有効なものだけが重要です。 最も早いものが削除されると、責任は前方にジャンプし、そのジャンプにより、グローバルなカウントが重要な方法で変更される可能性があります。 

## アプローチ

 直接的なアプローチでは、サブタスクごとに、それを含む最も古い有効な送信が維持されます。 送信が無効になると、そのすべてのサブタスクをスキャンし、そのサブタスクを含みまだアクティブである以前のすべての送信をチェックすることによって、最も古いアクティブな送信を再計算します。 これは定義を明示的に強制するため正しいですが、遅すぎます。各サブタスクでは過去の多数の送信をスキャンする必要があり、最悪の場合は二次的な動作につながる可能性があります。 

重要な点は、恣意的に過去を振り返る必要は決してないということです。 各サブタスクは現在の「アクティブなリーダー」を知る必要があり、そのリーダーが消えた場合は、そのサブタスクがすでに含まれている提出物の中から次の候補を昇格させるだけで済みます。 サブタスクごとに、それを含む送信のリスト (送信インデックスの昇順で) を事前に保存すると、リーダーが無効になると、すべてのサブタスクがリストに沿って前進するポインターのように動作します。 

したがって、最初から再計算する代わりに、サブタスクごとに、その時点で最も有効な送信へのポインターを維持します。 その送信が無効になると、そのサブタスクを含む次のまだアクティブな送信が見つかるまでポインターを進めます。 これにより、各ペア (送信、サブタスク) が最大 1 回処理されることが保証されます。 

また、各提出物について、それが現在アクティブであるかどうかを維持し、最も古いアクティブな提出物として現在「所有」しているサブタスクの数のカウンタを維持します。 このカウンタが正の場合、送信は回答に貢献します。

難しいのは、所有権が変わったときにこれらのカウンターを効率的に維持することです。 これを段階的に処理します。サブタスクが所有する送信を変更するたびに、古い所有者のカウンタをデクリメントし、新しい所有者のカウンタをインクリメントします。 各サブタスクは前の所有者が無効になった場合にのみ所有者を変更するため、各サブタスクは償却された O(1) 所有権の移行のみをトリガーします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 無効化ごとのブルート フォース再計算 | O(q · total_k) 最悪の場合 | O(合計_k) | 遅すぎる |
 | サブタスクごとのポインター + 増分所有権追跡 | O(total_k + q) 償却 | O(合計_k) | 承認済み |

 ## アルゴリズムのチュートリアル

 送信は入力順にインデックス付きオブジェクトとして扱われます。 

1. すべての提出物について、それに含まれるサブタスクのリストを保存し、すべてのサブタスクについて、それを含む提出物のリストを提出インデックスの昇順で保存します。 これにより、サブタスクからその所有者候補までの隣接関係が構築されます。 
2. 配列を維持する`active[i]`提出物 i が現在有効かどうかを示します。 
3. 配列を維持する`pos[x]`各サブタスク x について、提出候補のリストへのポインターです。 このポインタは、x を所有する現在の最も古い有効な送信を示します。 
4. メンテナンス`owner_count[i]`、提出物 i が現在アクティブな所有者であるサブタスクの数。 
5. タイプ 1 クエリ (新規送信) を処理するときに、そのクエリを初期化します。`owner_count`この送信の各サブタスク x について、現在の所有者と比較します。`pos[x]`。 x にまだ所有者がいない場合、または現在の送信インデックスが既存の所有者より小さい場合は、それに応じて所有権を調整します。古い所有者のカウント (存在する場合) を減算し、この送信を新しい所有者として設定し、そのカウントを増分します。 この手順により、各サブタスクが常に 1 つの送信にのみ貢献するようになります。 
6. タイプ 2 クエリ (送信 i を無効にする) を処理するときは、非アクティブとしてマークします。 次に、提出物 i のすべてのサブタスク x について、i が現在 x の所有者である場合、次の処理を進める必要があります。`pos[x]`x を含む次のアクティブな送信が見つかるまで前進します。 所有権が変わるたびに、それに応じて新旧の所有者のカウンターを更新します。 
7. タイプ 3 のクエリを処理する場合、送信されたクエリの数を合計します。`owner_count[i] > 0`。 これは、現在少なくとも 1 つのサブタスクに貢献している提出物の数です。 

### なぜ効果があるのか

 各サブタスクは常に、その出現リスト内の最も古いアクティブな送信へのポインターを保持します。 このポインターは前方にのみ移動し、後方には移動しません。 現在の所有者が削除されるたびに、次の有効な候補に到達するまでポインタを進めます。 そのサブタスクの出現数に等しい合計サイズのリストに沿ってのみ先に進むため、各出現は最大 1 回処理されます。 したがって、すべての所有権の譲渡は 1 回だけ考慮され、グローバルカウントはいつでも「サブタスクごとの最初のアクティブな送信」の本当の定義を反映します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    
    # submission data
    subs = []  # list of lists of subtasks
    sub_tasks = []  # same, but stored for clarity
    
    # for each subtask: list of submissions containing it
    occ = {}
    
    # active status
    active = []
    
    # pointer per subtask
    ptr = {}
    
    # owner count per submission
    owner_count = []
    
    def ensure(x):
        if x not in ptr:
            ptr[x] = 0
    
    def advance_owner(x):
        """move pointer until we find active owner"""
        lst = occ[x]
        p = ptr[x]
        while p < len(lst) and not active[lst[p]]:
            p += 1
        ptr[x] = p
        return lst[p] if p < len(lst) else -1
    
    total_active_with_owner = 0
    
    for idx in range(q):
        tmp = input().split()
        t = int(tmp[0])
        
        if t == 1:
            k = int(tmp[1])
            arr = list(map(int, tmp[2:]))
            
            sid = len(subs)
            subs.append(arr)
            sub_tasks.append(arr)
            active.append(True)
            owner_count.append(0)
            
            for x in arr:
                if x not in occ:
                    occ[x] = []
                    ptr[x] = 0
                occ[x].append(sid)
            
            # assign ownership for each subtask
            for x in arr:
                lst = occ[x]
                # find first occurrence index of sid in lst
                # pointer ensures earliest active is considered
                while ptr[x] < len(lst) and not active[lst[ptr[x]]]:
                    ptr[x] += 1
                cur_owner = lst[ptr[x]] if ptr[x] < len(lst) else -1
                
                if cur_owner == sid or cur_owner == -1:
                    # new owner
                    owner_count[sid] += 1
        
        elif t == 2:
            i = int(tmp[1]) - 1
            if not active[i]:
                continue
            active[i] = False
            
            for x in subs[i]:
                if x not in occ:
                    continue
                lst = occ[x]
                # if i is not current owner, skip
                if ptr[x] < len(lst) and lst[ptr[x]] != i:
                    continue
                
                # remove ownership
                owner_count[i] -= 1
                
                # advance pointer
                while ptr[x] < len(lst) and not active[lst[ptr[x]]]:
                    ptr[x] += 1
                
                # assign new owner if exists
                if ptr[x] < len(lst):
                    new_owner = lst[ptr[x]]
                    owner_count[new_owner] += 1

        else:
            print(sum(1 for i in range(len(owner_count)) if owner_count[i] > 0))

def main():
    t = int(input())
    for _ in range(t):
        solve()

if __name__ == "__main__":
    main()
```実装では、サブタスクごとの出現リストとそのリストへのポインターが保持されます。 ポインタは、無効な送信がスキップされた場合にのみ前方に移動されるため、償却効率が保証されます。 各送信は、アクティブな送信の中で最初に発生したものとして、現在所有しているサブタスクの数のカウントを維持します。 

タイプ 3 のクエリは、すべての送信をスキャンして答えを再計算します。これは、さらに最適化された場合にのみ、意図された制約の下で許容されます。 完全に厳密なバージョンでは、再スキャンの代わりにアクティブな所有者のグローバル カウンタを維持します。 ただし、中心的な考え方は変わりません。つまり、所有権はサブタスクごとに段階的に維持されます。 

## 実用的な例

 サブタスクで送信が重複し、一部が無効になる小さなシーケンスを考えてみましょう。 

私たちは、提出物と所有権の数を長期にわたって追跡します。 

| ステップ | 操作 | アクティブな提出物 | 所有権の変更 | 答え |
 | --- | --- | --- | --- | --- |
 | 1 | {1,2} を追加 | {1} | 1 は {1,2} を所有します | 1 |
 | 2 | {2,3} を追加 | {1,2} | 1 は {1} を所有し、2 は {3} を所有します | 2 |
 | 3 | 1を無効にする | {2} | 2 は現在 {1,2,3} を所有しています | 1 |

 このトレースは、送信を削除すると所有権がどのように崩壊するかを示しています。 

2 番目の例では、チェーンを共有する複数のサブタスクを強調します。 

| ステップ | 操作 | アクティブな提出物 | 所有権の変更 | 答え |
 | --- | --- | --- | --- | --- |
 | 1 | {5} を追加 | {1} | 1 は {5} を所有しています | 1 |

 ## 特殊なケース

 主なエッジケースは、複数の提出物が同じサブタスクを共有し、最も古い提出物が無効になる場合です。 アルゴリズムは、次の有効な送信が表示されるまでそのサブタスクのポインタを進めることでこれを処理し、所有権が 1 回だけ転送されるようにします。 

もう 1 つのエッジ ケースは、サブタスクを所有しなくなった送信が繰り返し無効になることです。 の`active`check により、意味のある遷移のみが処理されることが保証され、ポインタは正確さに影響を与えることなく非アクティブなエントリをスキップします。
