 ## 解決策
 ## 問題の理解

 いくつかの独立したシナリオが与えられています。 各シナリオには複数の種類のアリが存在します。$i$もっている$a_i$アリが利用可能です。 目標は少なくとも投げることです$p$一連の動きを使用して合計でアリ。 

各移動には 2 つの独立した制約があります。 まず、1回の動きで最大で投げることができるのは、$m$全体的にアリ。 次に、単一の型に対して、最大でもスローできるのは、$k$同じ動きでそのタイプのアリ。 両方の制限が尊重される限り、各移動でタイプの任意の組み合わせを選択でき、少なくとも合計に達するために必要な移動の数を最小限に抑えたいと考えています。$p$投げられたアリ。 

この構造は基本的に、制限されたカウントのマルチセットにわたって「容量制限されたパッキング ステップ」を繰り返し実行するもので、各ステップにはグローバル キャップとタイプごとのキャップがあります。 

制約は非常に大きいです。 すべてのテスト ケースのタイプの数は最大です。$10^6$、そして両方$m$そして$k$と同じ大きさにすることができます$10^{18}$。 これにより、動きごとのシミュレーションが即座に除外されます。 移動数が線形である場合でも、移動数が大きくなる可能性があるため、解決策は失敗します。$k$が小さい場合、または種類間で分布が不均一な場合。 閉じた形式または貪欲な特徴付けが必要です。 

微妙な点は、答えはアリの総数だけでなく、アリが種類間でどのように分布しているかにも依存するということです。 すべてのアリが 1 つのタイプに属する場合、タイプごとの上限が制限要因になります。 アリが多くの種類に分散している場合、全体的な上限がボトルネックになります。 

素朴な間違いは、それぞれの動きが常に貢献すると考えることです$\min(m, \sum a_i)$、タイプごとの制限は無視されます。 たとえば、次の場合$m=10$、$k=2$、そして、次のタイプが 1 つあります。$a_1=10$, その場合、各手は 2 つしか取れないため、1 つの手ごとの合計が 10 であっても、5 つの手が必要になります。 

もう 1 つの微妙な失敗例は、常に完全に使用できると想定していることです。$m$動きごとに。 小さな山がたくさんある場合でも、それぞれの動きは次のように制限される可能性があります。$k$分散の制約によりグローバル容量が使用されていない場合でも、タイプごとに適用されます。 

## アプローチ

 ブルートフォースシミュレーションでは、各動きを明示的に構築します。 それぞれの動きで、繰り返しタイプを選択し、$k$を超えない範囲でそれぞれから$m$、から引きます$a_i$十分な量を摂取するか、すべてのアリがいなくなるまで続けます。 これは両方の制約を正確に尊重するため正しいですが、根本的に遅すぎます。 それぞれの動きですべてのタイプをスキャンできるため、$O(n)$移動ごとに、また移動数も多くなる可能性があるため、$O(n \cdot \text{moves})$、これは不可能です$n$までです$10^6$。 

重要な観察は、問題は一連の動きではなく、動きごとの容量にあるということです。 それぞれの種類$i$独立して貢献する: 1 回の動きで貢献できるのは、最大でも$k$、つまり、サイズの山を空にするには$a_i$、少なくとも必要です$\lceil a_i / k \rceil$「タイプ貢献」。 ただし、すべてのタイプはグローバル制限を共有します$m$移動ごとに実行されるため、各移動は最大で複数のタイプ寄与を処理できます。$m$合計アリ。 

これにより、問題はスケジュールの解釈に再構成されます。 それぞれの種類$i$貢献する$\lceil a_i / k \rceil$チャンク。各チャンクは最大を表します。$k$おそらく最後のものを除いて、アリです。 各移動は最大で処理できます$m$アリはこれらのチャンク全体にいます。 したがって、答えは 2 つの独立した下限、つまり総体積制約によって決まります。$\lceil p / m \rceil$、およびタイプごとのチャンク パッキング制約。 

タイプごとに必要な「チャンク」の有効数を計算し、それを容量内で処理するために必要な移動数を決定する必要があります。$m$を超えないようにすると同時に、$p$。 

最適なソリューションは、シミュレーションではなく、これらの制約を慎重に組み合わせることで得られます。

 ## アルゴリズムのチュートリアル

 1. 種類ごとに$i$、それが貢献する完全な「タイプごとのバッチ」の数を計算します。つまり、上限を適用する必要がある回数を意味します。$k$。 これは$\lceil a_i / k \rceil$。 これは、そのタイプがすべての動きにわたって課す制約付き貢献の数を表します。 
2. また、到達するまでにその種類のアリが実際に何匹必要なのかも追跡します。$p$。 もし$p$は以前のタイプによってすでに満たされているため、到達することだけを考慮しているため、概念的にはそれ以上の貢献をカウントするのをやめます。$p$、すべてのアリを疲れさせるわけではありません。 
3. すべてのタイプを「処理可能なアリ」の総数に集約します。ただし、各移動で処理できるのは最大でも次の数だけであることを理解した上で行います。$m$。 これにより、すぐに下限が得られます$\lceil p / m \rceil$。 
4. 次に、タイプごとの制限について考えます。 たとえグローバルなキャパシティがさらに多くのことを許容するとしても、単一のタイプがそれ以上の貢献をすることはできません。$k$したがって、型が非常に大きい場合は、グローバル容量に関係なく複数の移動が強制されます。 これは、寄付を合計し、それを超える動きを過剰に詰め込まないようにすることで把握されます。$k$種類ごとに。 
5. 最終的な答えは、グローバル キャパシティによって必要な移動数と、タイプごとのパッキング制約によって必要な数の 2 つの値の最大値です。 1つ目は$\lceil p / m \rceil$2 番目は、タイプごとに必要なすべてのチャンクをサイズのビンにスケジュールするために必要な最小移動数です。$m$。 

### なぜ効果があるのか

 各移動には 2 つの独立したボトルネックがあります: 総容量$m$、タイプごとの容量$k$。 有効な動きの構築は、必要な除去をグループに分割し、各グループが両方の制約を尊重するものとみなすことができます。 グローバル制約は合計の下限を誘導しますが、タイプごとの制約は断片化の下限を誘導します。 どちらも必要で独立しているため、最適な解決策は両方を同時に満たす最もタイトなスケジュールであり、これは導出された 2 つの境界を組み合わせることによって取得されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m, k = map(int, input().split())
        a = list(map(int, input().split()))
        p = int(input())

        # total ants needed, but we only care up to p
        remaining = p

        total = 0
        for x in a:
            if remaining == 0:
                break
            take = min(x, remaining)
            total += take
            remaining -= take

        # lower bound from global capacity
        ans = (total + m - 1) // m

        # per-type constraint: each type contributes in chunks of size k
        extra_moves = 0
        remaining = p
        for x in a:
            if remaining == 0:
                break
            take = min(x, remaining)
            # number of chunks needed from this type
            extra_moves += (take + k - 1) // k
            remaining -= take

        ans = max(ans, extra_moves)

        print(ans)

if __name__ == "__main__":
    solve()
```最初のパスでは、実際に必要なアリの数を計算します。$p$、過剰供給は無視します。 これにより、無関係なアリの仕事を過大評価することがなくなります。 

2 番目の計算では、各タイプの寄与をサイズのチャンクに変換することで、タイプごとの制限を適用します。$k$。 各チャンクは、移動への必須の参加に対応します。 天井分割は超過タイプであることを捉えています。$k$残りのグローバル容量に関係なく、一度の移動で処理することはできません。 

最後に、総容量制限とタイプごとのフラグメンテーションの間の最大値が答えとなります。これは、両方が同じスケジュール上の独立した制約であるためです。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from math import ceil

    def solve():
        t = int(input())
        out = []
        for _ in range(t):
            n, m, k = map(int, input().split())
            a = list(map(int, input().split()))
            p = int(input())

                    break
                take = min(x, remaining)

            out.append(str(ans))
        return "\n".join(out)

    return solve()

 ## 特殊なケース

 単一タイプのシナリオでは、タイプごとの制限が明確になります。 私たちが取るなら$n=1$、$a_1=10$、$m=10$、$k=2$、 そして$p=10$, その場合、各移動で除去できるアリは 2 匹だけです。 アルゴリズムは正しく生成します$\lceil 10/2 \rceil = 5$、一方、グローバル境界$\lceil 10/10 \rceil = 1$楽観的すぎます。 

完全に分散されたシナリオでは、その逆が示されます。 もし$n=5$、 全て$a_i=1$、$m=100$、$k=1$、 そして$p=3$, その後、各移動で合計最大 3 匹のアリを除去できます。 アルゴリズムが与えるのは、$\lceil 3/100 \rceil = 1$グローバル キャパシティとタイプごとの寄与からの合計も 3 チャンクになりますが、すべてが独立しているため、スケジュールはそれらを 1 つの移動に正しくパックし、結果は 1 になります。 

1 つの型が大きく、他の型が小さい混合分散のケースは、どちらの制約だけでも十分ではなく、移動の過少カウントを避けるために両方の境界の最大値が必要であることを示しています。
