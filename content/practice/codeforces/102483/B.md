 ## 解決策
 ## 問題の理解

 交渉トピックの有向非循環グラフがあります。 各トピックには基本的なディスカッション時間があります`e[i]`、また、一部のトピックは、他の特定のトピックが終了した後でのみ議論できます。 有効なスケジュールは、このグラフのトポロジー的な順序です。 

トピックが位置に配置されている場合`p`スケジュールでは、最初の会議がポジションを持っています`0`、会議には時間がかかります`e[i] + p`分。 余分な`p`議事録は、これまでのすべての会議をレビューして作成されます。 目標は、1 回の会議の最長時間を最小限に抑える有効な順序を選択することです。 

入力によりトピックの数が与えられ、次に各トピックの基準時間と前提条件トピックのリストが与えられます。 出力は最大値の可能な最小値です。`e[i] + p`すべての有効なスケジュールにわたって。 

の制約`n`まで`400000`異なる順序を繰り返し試行したり、サブセットに対して動的プログラミングを使用したりするアルゴリズムを除外します。 グラフには最大で次のものを含めることができます`400000`したがって、意図した解決策は線形時間に近いものでなければなりません。 優先キューを使用した通常のトポロジー ソートは、各トピックとエッジを対数回のみ処理するため、適切です。 

いくつかのケースでは、誤って処理されやすいものがあります。 いくつかのトピックに依存関係がない場合は、最大の基準時間を最初にスケジュールする必要があります。 例えば：```
3
10 0
1 0
1 0
```答えは、`12`。 最適な順序は時間の経過とともに話題になります`10`まず長さを与える`10`、`2`、 そして`3`。 最初に小さなトピックを選択すると、大きなトピックに不必要な遅延が生じます。 

2 番目のケースは、長いトピックが最初は利用できない場合です。```
2
1 1 2
100 0
```答えは、`101`。 最初のトピックが依存しているため、2 番目のトピックが最初に発生する必要があります。 依存関係を無視して単純に並べ替える貪欲な実装`e`無効なスケジュールが作成されます。 

最後のコーナーケースは 1 つのトピックです。```
1
500 0
```答えは、`500`。 以前の会議が存在しないため、要約時間はありません。 

## アプローチ

 直接的なアプローチでは、現在利用可能なすべてのトピックを繰り返し検索しながらスケジュールを構築しようとします。 すべての位置で、すべてのトピックをスキャンし、それが利用可能かどうかを確認し、最大のトピックを選択できます。`e`。 これは正しいです。なぜなら、各時点での最善の選択は、遅延によって最も影響を受けるトピックであるからです。 ただし、`400000`トピック、すべての位置のすべてのトピックをスキャンするには、おおよその必要があります`400000^2`、 または`1.6 * 10^11`、最悪の場合にチェックが行われますが、これでは遅すぎます。 

有益な観察は、次のトピックを選択するときに必要な情報は、前提条件がすでに完了している一連のトピックだけであるということです。 これはまさに、カーンのトポロジカル ソート アルゴリズムによって維持される状態です。 すべてのトピックをスキャンする代わりに、利用可能なトピックを次の順序で最大ヒープに保持します。`e`。 トピックが使用可能になると、そのトピックはヒープに挿入されます。 次の会議は常に、基本期間が最長の利用可能なトピックとなります。 

この貪欲な選択が機能する理由は、議題を 1 つ遅らせると、会議の長さがちょうど 1 分増えるからです。 現在利用可能なトピックが 2 つある場合、`a`そして`b`、 と`e[a] > e[b]`、配置`b`前に`a`依存関係を助けずに、より大きなトピックの最終期間を長くします。 それらを交換しても、会議の最大時間を改善または維持することしかできません。 この交換議論を繰り返すことは、最適なスケジュールを常に、利用可能な最大のスケジュールを選択するスケジュールに変換できることを意味します。`e`あらゆる段階で。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適 | O((n + m) log n) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 依存関係グラフを構築します。 すべての前提条件の関係について`a -> b`、 店`b`後に利用可能になるトピックとして`a`完成しました。 各トピックの未完了の前提条件の数も保存します。 
2. 未完了の前提条件がゼロのすべてのトピックを、基本時間順に並べられた最大ヒープに置きます。 これらのトピックは、最初に法的に議論できる唯一のトピックです。 
3. ベース時間が最大のトピックをヒープから繰り返し削除します。 現在の位置はすでに完了した会議の数であるため、次のように答えを更新します。`e[i] + position`。 
4. トピックを完了したら、それに応じて各トピックの前提条件の数を減らします。 これらのカウントのいずれかが 0 になった場合は、そのトピックが使用可能になるため、そのトピックをヒープに挿入します。 
5. すべてのトピックがスケジュールされるまで続行します。 保存される最大値は、可能な最小の最長会議です。 

これが機能する理由: どの時点でも、ヒープには次に合法的に選択できるトピックが正確に含まれています。 これらの選択肢のうち、最大のものを選択すると、`e`この値は、依存関係に違反せずに、使用可能なトピックを選択したトピックと交換でき、より大きなトピックを移動できるため、最適です。`e`後のトピックでは最大値を増やすことしかできません。 すべての決定はこの交換引数によって正当化できるため、全体の順序付けが最適になります。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n = int(input())
    e = [0] * n
    graph = [[] for _ in range(n)]
    indeg = [0] * n

    for i in range(n):
        data = list(map(int, input().split()))
        e[i] = data[0]
        d = data[1]
        indeg[i] = d
        for x in data[2:]:
            graph[x - 1].append(i)

    heap = []
    for i in range(n):
        if indeg[i] == 0:
            heapq.heappush(heap, (-e[i], i))

    ans = 0
    done = 0

    while heap:
        neg_e, u = heapq.heappop(heap)
        ans = max(ans, -neg_e + done)
        done += 1

        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                heapq.heappush(heap, (-e[v], v))

    print(ans)

if __name__ == "__main__":
    solve()
```グラフには、前提条件から依存トピックへの発信エッジが格納されます。 この方向では、利用可能になる可能性のあるトピックにアクセスするだけで済むため、トピックの終了後の更新が簡単になります。 

ヒープは Python の標準ライブラリの min-heap として実装されるため、格納される値は次のようになります。`-e[i]`最大ヒープをシミュレートします。 変数`done`スケジュール内の現在のゼロから始まる位置です。 この位置での会議には長さがあります`e[i] + done`。 

すべての期間は Python 整数内に収まります。 考えられる最大の答えは以下の通りです`1,400,000`, しかし、Python の任意精度により、オーバーフローの懸念も解消されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + m) log n) | すべてのトピックはヒープに 1 回出入りし、すべての依存関係エッジは 1 回処理されます。 |
 | スペース | O(n + m) | グラフにはすべての依存関係エッジが保存され、ヒープには利用可能なトピックが保存されます。 |

 ここ`m`依存関係の総数です。 以来`m`せいぜい`400000`、ソリューションは必要な制限内に留まります。 

## テストケース```python
import sys
import io
import heapq

def run(inp: str) -> str:
    old = sys.stdin
    sys.stdin = io.StringIO(inp)
    n = int(input())
    e = [0] * n
    graph = [[] for _ in range(n)]
    indeg = [0] * n

    for i in range(n):
        data = list(map(int, input().split()))
        e[i] = data[0]
        indeg[i] = data[1]
        for x in data[2:]:
            graph[x - 1].append(i)

    heap = []
    for i in range(n):
        if indeg[i] == 0:
            heapq.heappush(heap, (-e[i], i))

    ans = done = 0
    while heap:
        x, u = heapq.heappop(heap)
        ans = max(ans, -x + done)
        done += 1
        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                heapq.heappush(heap, (-e[v], v))

    sys.stdin = old
    return str(ans) + "\n"

 ## 特殊なケース

 独立したトピックの場合:```
3
5 0
1 0
2 0
```すべてのトピックはすぐにヒープに入ります。 アルゴリズムが選択するのは、`5`、 それから`2`、 それから`1`、会議の長さを生み出す`5`、`3`、 そして`3`。 答えは、`5`一方、小さい順に並べると、最大値が不必要に増加します。 

強制的な依存関係の場合:```
2
1 1 2
100 0
```最初はトピック 2 のみが使用可能であるため、ヒープには選択肢がありません。 トピック 2 が終了すると、トピック 1 が使用可能になります。 アルゴリズムは計算します`100 + 0`そして`1 + 1`、与える`101`。 

値が等しい場合:```
3
10 0
10 0
10 0
```優先順位が同じであるため、ヒープは 3 つのトピックのいずれかを最初に返す可能性があります。 考えられるすべての順序で同じ結果が得られ、最後のトピックには 2 分間の要約時間が与えられます。`12`。
