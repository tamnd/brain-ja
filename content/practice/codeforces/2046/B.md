 ## 解決策
 ## 問題の理解

 一連の整数が与えられると、非常に特殊な変換を繰り返し実行することができます。つまり、任意の要素を選択し、それを 1 つ増やし、それを配列の末尾に移動します。 これを行うたびに、選択した要素がその位置から消え、わずかに成長し、再び背面に表示されます。 

タスクは、辞書編集上可能な限り最小の最終配列を生成するために、この操作を任意の回数 (場合によっては 0 回) 適用することです。 

主な難点は、この操作により値と位置の両方が同時に変更されることです。 要素を時間の経過とともに前方 (最後まで) に移動すると、辞書編集上の比較順序が遅れるためコストがかかりますが、前の位置を小さくできるのであれば、それだけの価値はあるかもしれません。 

すべてのテスト ケースの合計の長さが最大 ​​100000 であるという制約は、O(n log n) または O(n) 戦略が必要であることを強く示唆しています。 すべての操作シーケンスを試行したり、要素ごとに繰り返し調整をシミュレートしたりするソリューションは失敗します。最悪の場合、1 つの要素であっても何度も移動し、2 次またはさらに悪い動作が発生する可能性があるためです。 

素朴な間違いは、ローカルの貪欲な選択が常に安全であると仮定することです。 たとえば、小さいプレフィックスをブロックするときに大きい要素を常にすぐに移動すると、要素を増やすとその後の比較が微妙な方法で変更されるため、失敗する可能性があります。 

この微妙な失敗パターンを考えてみましょう。次の要素より大きい要素を常にすぐに後ろに押し込むと、他の削除後に問題がなかった要素を過剰に変更してしまう可能性があります。 もう 1 つの間違いは、要素を並べ替えるだけであるかのように操作を扱うことです。 この増分は純粋な順列の直感を打ち破ります。 

主な重要なエッジ ケースは、初期の要素は小さいが、後の要素はわずかに小さいが、移動した場合に競争力を維持するには複数の増分が必要になる場合です。 たとえば、数回移動された 1 のような要素は 1 + k になり、最終的には他の未処理の要素を超える可能性があるため、遅延させると実際に辞書編集上の順序が損なわれる可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、考えられるすべての操作シーケンスをシミュレートします。 各ステップではインデックスを選択し、それをインクリメントし、最後に押し込みます。 各要素は複数回選択でき、位置が変化し続けるため、状態空間は指数関数的に増加します。 各要素を n 回の操作で制限した場合でも、O(n^2) 以上の動作が発生し、制限をはるかに超えています。 

重要な観察は、決して移動されない要素の最終的な相対順序が保持され、移動された要素は常に、安定するまでに押し戻された回数に等しいコストを蓄積するということです。 一連の操作の観点から考える代わりに、各要素は所定の位置に留まるか、ある時点で「最後まで押し込まれ」、その後は二度と戻らないと考えることができます。 

変更されない要素のプレフィックスを修正したら、残りのすべての要素は最終的にそのプレフィックスの後ろに移動する必要があり、その最終的な値は、処理時にその前に未変更の要素がいくつあるかによってのみ決まります。 これにより、問題は左から右の順に、要素を今保持するべきか、それとも最後まで延期すべきかを決定することになります。その一方で、延期された要素はコストの増加順に戻ってくるという事実を考慮します。 

貪欲な構造は、要素を処理し、サフィックスを形成する「移動された保留中の要素」の構造を維持するときに現れます。 各ステップで、現在の要素を、増分を考慮した後で保留中のプールから繰り出すことができる最小の利用可能な候補と比較します。 これは、延期されたすべての要素を追跡するマルチセット (またはヒープ) を使用して効率的に処理できます。

 ## アルゴリズムのチュートリアル

 配列を左から右に処理し、2 つのコンポーネントを維持します。1 つは増加する応答プレフィックス、もう 1 つは「後ろに移動」したが最終構造にはまだ出力されていない要素のプールです。 

1. 延期された要素の空の構造から始めます。 最小の調整値を繰り返し抽出する必要があるため、これをマルチセットとして扱います。 
2. 配列を最初の要素から最後の要素まで繰り返します。 各インデックスで、現在の要素を回答に直接配置するか、延期されたプールに移動するかを決定します。 
3. 各要素 a[i] について、延期されたプール内に現在ある最小の要素と比較しますが、プール内の要素は以前の移動ごとに 1 回インクリメントされていることを覚えておく必要があります。 これにより、延期された要素の価値が時間の経過とともに効果的に「上昇」するダイナミクスが生まれます。 
4. 現在の要素が利用可能な最良の延期オプション以下である場合、現在の要素を直ちに回答に組み込みます。 それ以外の場合は、より小さい辞書編集プレフィックスが得られるため、最初に延期されたプールから何かを取得することを好みます。 
5. 延期されたプールから取得するときは常に、利用可能な最小の調整済み要素を出力し、必要に応じて別の動きを考慮して増分された値を使用して要素を再挿入するか、確定済みの場合は削除します。 
6. 延期されたプールから取得しないことを選択した場合は、現在の要素をプールに追加します。これは、要素が最後にプッシュされ、一度インクリメントされたことを表します。 
7. スキャンの終了後、残りの延期された要素が順番に抽出され、そのたびに累積された増分が適用されます。 

微妙な点は、延期されたすべての要素が循環されるたびに 1 ずつ増加する値のように動作するため、要素ごとに複数の動きを明示的にシミュレートすることは決してないことです。 現在の実効値のみを保存します。 

### なぜ効果があるのか

 どのステップでも、アルゴリズムは、次に出力される要素が、何らかの有効な操作シーケンスのその位置に合法的に出現できる最小値であることを保証します。 不変条件は、延期されたプールには常に、現在のプレフィックスを超えて遅延された要素が正確に含まれており、それぞれが正しい累積増分状態で表されるということです。 辞書編集的な順序は最も早い異なる位置にのみ依存するため、常に利用可能な最小の候補を出力することにより、局所的に最適性が維持され、したがって全体的に最適性が維持されます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        # min-heap of postponed elements
        heap = []

        res = []

        for x in a:
            if not heap or x <= heap[0]:
                # take current element
                res.append(x)
            else:
                # move current element to back (it gets incremented once)
                heapq.heappush(heap, x + 1)

                # take smallest postponed element
                smallest = heapq.heappop(heap)
                res.append(smallest)

        # flush remaining
        while heap:
            res.append(heapq.heappop(heap))

        print(*res)

if __name__ == "__main__":
    solve()
```この実装は、最小ヒープに依存して、O(log n) 内の最小の延期された要素に常にアクセスします。 決定点では、現在の要素とヒープの最小値が比較されます。これは、以前に遅延された要素から可能な限り最良の候補を表します。 

よくある落とし穴は、要素を延期するとすぐに 1 ずつ増加し、それ以上の延期はヒープの順序付けによる再処理によって暗黙的に表されることを忘れていることです。 ヒープには生の値が格納されることはありません。 最初の動きに対してすでに調整された値が保存されます。 

残りの延期された要素は有効な値の昇順で出力に配置する必要があるため、最後のフラッシュ ステップが必要です。

 ## 特殊なケース

 重要なエッジケースは、配列が厳密に減少している場合です。 その場合、最初の要素を除くすべての要素がヒープにプッシュされ、値が繰り返しインクリメントされます。 各要素の遅延増分はヒープによって自然に順序付けされ、後の要素が以前に延期された要素を誤って追い越すことを防ぐため、アルゴリズムは引き続き滑らかな増加シーケンスを生成します。 

もう 1 つの特殊なケースは、すべての要素が等しい場合です。 保持する場合と比較して延期によって厳密に改善される要素はないため、ヒープが比較で優勢になることはなく、配列は変更されません。 

3 番目のケースは、非常に小さな要素が遅れて現れる場合です。 ヒープは、辞書編集的に最適なプレフィックスを保持しながら、必要に応じて常に最小有効値として表示されるため、より大きな延期された要素の背後にヒープが失われないことを保証します。
