 ## 解決策
 ## 問題の理解

 この問題では、3 つのドアと 3 つの鍵があり、それぞれが赤、緑、青で色分けされている狭い廊下について説明しています。 騎士は廊下の左端からスタートし、王女は右端で待ちます。 廊下は 6 文字の文字列で表されます。大文字はドア (R、G、B) を示し、小文字はキー (r、g、b) を示します。 各色は、ドアとして 1 回、鍵として 1 回ずつ表示されます。 

目標は、騎士が各ドアを順番に開けながら廊下を左から右に横断できるかどうかを判断することです。 騎士は移動中に鍵を拾い、対応するドアに遭遇したときにすぐに使用できます。 すべてのドアが開くことができる場合、出力は「YES」、そうでない場合は「NO」になります。 

制約があるため、廊下の長さは常に 6 文字になります。 テスト ケースの数は最大 720 ですが、これはテスト ケースごとの線形時間アプローチが効率的であるほど十分に小さいです。 ドアと鍵は3つしかないので、鍵を拾って順番にドアを開けるという総当りチェックも可能ですが、鍵よりも先に出現したドアが進行を妨げるため注意が必要です。 

エッジケースには、鍵の直前にドアが現れることが含まれます。 たとえば、地図で言えば、`RgbrBG`、赤いドア`R`が最初で、赤いキーです`r`後で登場します。 騎士は最初のドアを開けることができないため、出力は「NO」でなければなりません。 順序を考慮せずに単に鍵とドアを数える単純なアプローチでは、誤って「YES」と答えてしまいます。 

## アプローチ

 ブルート フォース手法では、文字列を左から右に反復して、セット内に収集されたキーを追跡します。 騎士がドアに遭遇するたびに、対応する鍵がすでに収集されているかどうかを確認します。 そうであれば、彼はドアを開けます。 そうでない場合、廊下を横断することはできず、答えは「いいえ」です。 このアプローチが機能するのは、廊下の長さが 6 に固定されており、反復が簡単になるためです。 最悪のケースでは、テスト ケースごとに 6 文字すべてを検査する必要があり、結果として 6 × 720 = 4320 回の操作が発生しますが、これは無視できる程度です。 

最適なアプローチは、同じ線形スキャンに従います。 重要な洞察は、各ドアには固有の鍵があり、どちらも 1 回だけ現れるため、進行を妨げる唯一の状況は、鍵を取得する前にドアに遭遇することであるということです。 したがって、収集した鍵のセットを管理し、それに対してドアをチェックするだけで済みます。 複雑なデータ構造やバックトラッキングは必要ありません。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(6 * t) = O(t) | O(3) = O(1) | 承認済み |
 | 最適なリニアスキャン | O(t) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. テストケースの数を読み取る`t`。 
2. 各テスト ケースについて、廊下を表す 6 文字の文字列を読み取ります。 
3. これまでに収集したキーを格納するために空のセットを初期化します。 
4. 文字列内の各文字を左から右に繰り返します。 
5. 文字がキーの場合 (`r`、`g`、`b`)、収集されたキーのセットに追加します。 
6. キャラクターがドアの場合 (`R`、`G`、`B`)、対応する小文字キーがセット内にあるかどうかを確認します。 そうでない場合は、「NO」を出力し、このテスト ケースの処理を中止します。 
7. ブロックされたドアに遭遇せずに文字列の終わりに到達した場合は、「YES」と出力します。 

これが機能する理由: いつでも、セットには騎士が渡したすべてのキーが含まれています。 ドアは、そのキーがセット内にある場合にのみ開くことができます。 各鍵とドアは一意であり、一度だけ出現するため、収集された鍵を追跡することで正確性が保証されます。 サイクルや再訪問はないため、左から右への 1 回のパスで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    hallway = input().strip()
    keys_collected = set()
    possible = True
    for ch in hallway:
        if ch.islower():
            keys_collected.add(ch)
        else:  # door
            if ch.lower() not in keys_collected:
                possible = False
                break
    print("YES" if possible else "NO")
```コードはまずテスト ケースの数を読み取り、それらを反復処理します。 廊下文字列ごとに、キーを追跡するためのセットを初期化します。 各文字が処理されます。キーがセットに追加され、ドアがセットに対してチェックされます。 ドアを開けることができない場合、ループは早期に中断されます。 結果はすぐに印刷されます。 微妙な点としては、キーをチェックするときにドアを小文字に変換したり、入力文字列から改行を削除したりすることが含まれます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    output = []
    t = int(input())
    for _ in range(t):
        hallway = input().strip()
        keys_collected = set()
        possible = True
        for ch in hallway:
            if ch.islower():
                keys_collected.add(ch)
            else:
                if ch.lower() not in keys_collected:
                    possible = False
                    break
        output.append("YES" if possible else "NO")
    return "\n".join(output)

# Provided samples
assert run("4\nrgbBRG\nRgbrBG\nbBrRgG\nrgRGBb\n") == "YES\nNO\nYES\nNO", "Sample 1"

# Custom test cases
assert run("1\nrbgRGB\n") == "YES", "all keys first"
assert run("1\nRGBrgb\n") == "NO", "all doors first"
assert run("1\nrGBgRb\n") == "NO", "blocked by first door"
assert run("1\nrgBGRb\n") == "YES", "keys before doors but mixed"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | RGBRGB | はい | 最初にすべてのキーを収集します |
 | RGBrgb | いいえ | ドアは鍵の前に表示されます。 
| rGBgRb | いいえ | 最初のドアが進行を妨げます。 
| rgBGRb | はい | 順序が混在していますが、すべてのドアを開けることができます。 

## 特殊なケース

 重大なエッジケースは、ドアが鍵の前に現れたときに発生します。 のために`RGBrgb`、騎士はすぐに赤い扉に遭遇し、鍵を持っていないため、横断は不可能です。 私たちのアルゴリズムは最初のステップでこれを検出し、「NO」を出力します。 もう 1 つの微妙なケースは、すべてのキーが最初に出現する場合です。たとえば、`rbgRGB`、ドアを即座に開くことができ、アルゴリズムは正しく「YES」と出力します。 これらのテストにより、解決可能性に影響を与える唯一の要因は、ブロックされていないドアや鍵の相対的な位置ではなく、順序であることが確認されています。
