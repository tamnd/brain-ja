 ## 解決策
 ## 問題の理解

 利用可能なブレスレット タイルは 3 種類あります。1 つのタイプは 0 のペアを表し、別のタイプは混合ペアを表し、最後のタイプは 1 のペアを表します。 各タイル タイプには在庫が限られており、それぞれ n、m、k で指定されます。 さらに、バイナリ文字列 S で記述されるターゲットの円形ブレスレット パターンが与えられます。 

私たちは円形のブレスレット全体を作るように求められているわけではありません。 代わりに、S の連続セグメントを選択し、それを線形部分文字列として扱い、利用可能なタイルを使用してできるだけ長いセグメントを構築したいと考えています。 S の各文字は最終構成の単一ビットに対応し、隣接するビットによってどのタイルが必要かが決まります。 ツイストは、混合タイルの方向を反転できることです。つまり、通常は 01 となるタイルを 10 としても使用できます。他の 2 つのタイル タイプは対称であり、反転の影響を受けません。 

タスクは、各タイル タイプの利用可能な数を超えずに形成できる S の連続した部分文字列の最大長を決定することです。 

タイル数と文字列の長さの両方について、制約は最大 1e6 になります。 これにより、部分文字列に対する二次解は即座に排除されます。 どのソリューションでも文字列を線形または線形に近い時間で処理する必要があり、部分文字列ごとの再計算はコストがかかりすぎます。 

すべての開始位置を考慮せずに文字列の先頭から貪欲に問題を解決できると想定すると、微妙な失敗のケースが発生します。 たとえば、S が 0 と 1 の間で頻繁に切り替わる場合、混合タイルの需要は変動し、異なるオフセットで開始すると、特定のタイル タイプが最初になくなるかどうかが変わります。 インデックス 0 からの単純な左から右への構築では、後から始まる最適な部分文字列を見逃してしまいます。 

## アプローチ

 ブルートフォース手法では、すべての開始インデックス i を試し、必要な 00、01/10、および 11 遷移の数を追跡しながら部分文字列を右に展開します。 展開ごとに、部分文字列によって引き起こされた隣接ペアの数を維持します。 部分文字列を拡張するたびに、必要なタイル数を更新し、n、m、k に対して実現可能性をチェックします。 

すべての部分文字列がリソース制約に対して明示的にテストされるため、これは正しく機能しますが、遅すぎます。 O(N^2) 個の部分文字列があり、カウントを段階的に更新すると、各拡張は O(1) ですが O(N^2) 回実行されるため、最悪の場合でも 2 次の動作が発生します。 

重要な観察は、部分文字列の実現可能性は、隣接する文字間の遷移の数のみに依存するということです。 各部分文字列は要求を課します。すべての等しい隣接ペアは値に応じて 00 または 11 タイルを消費し、反転が許可されているため、方向に関係なくすべての異なるペアは 01 タイルを消費します。 

これにより、遷移用の 3 つのカウンターを維持しながら、S 上のスライディング ウィンドウを追跡するという問題が軽減されます。 左のエンドポイントを修正したら、リソースの 1 つを超えるまで右のエンドポイントを貪欲に拡張できます。 次に、ステップあたりのカウントを O(1) に維持しながら、左のエンドポイントを前方に移動します。 これは、ウィンドウ拡張に関して制約が単調である、古典的な 2 ポインターまたはスライディング ウィンドウの実現可能性問題です。

 | ブルートフォース | O(N^2) | お(1) | 遅すぎる |

 ## アルゴリズムのチュートリアル

 各部分文字列に含まれる各タイプの遷移の数を数えることによって、各部分文字列を処理します。 部分文字列の場合、隣接するすべてのペアが 1 つのリソース カテゴリにのみ寄与します。 

ウィンドウ [l, r) と、ウィンドウ内の隣接する遷移の数を反映するカウンター cnt00、cnt01、cnt11 を維持します。

1. l = 0、r = 0、およびすべてのカウンターをゼロに初期化します。 この時点では、ウィンドウは空であり、自明のことながら有効です。 
2. r を一度に 1 文字ずつ展開します。 S[r] を追加するとき、r > l の場合、S[r-1] と S[r] の間に形成される新しいエッジを考慮します。 このエッジが 00、11、または混合であるかどうかに基づいて、対応するカウンターを更新します。 このステップは、絶対的な位置ではなく、隣接する関係のみが重要であるという事実をエンコードします。 
3. カウンタ更新後、cnt00 <= n、cnt01 <= m、および cnt11 <= k が成立するかどうかを確認します。 それが成立する場合、現在のウィンドウは実行可能であるため、その長さで答えを更新します。 
4. ウィンドウが実行不可能になった場合は、左側からウィンドウを縮小する必要があります。 l を前方に移動する前に、エッジ (S[l]、S[l+1]) がウィンドウ内に存在する場合はその寄与を除去し、適切なカウンターをデクリメントします。 次に、l をインクリメントし、ウィンドウが再び有効になるまで縮小を続けます。 このステップは、要素を削除してもカウントが減るだけなので機能し、最終的には実現可能性が回復します。 
5. r が文字列の終わりに達するまで続けます。 

重要な点は、各エッジの追加と削除が最大 1 回であるため、全体の作業が線形のままであることです。 

それが機能する理由は、単調な実現可能性の特性に基づいています。 ウィンドウが実行不可能な場合、すべてのカウンターが r に関して減少しないため、ウィンドウをさらに拡張しても違反を修正できません。 同様に、左から縮小するとカウンターが厳密に削減され、状態を再検討することなくプロセスが常に実行可能に向かって進むことが保証されます。 これにより、すべての有効な部分文字列がある時点でウィンドウ境界構成として考慮され、実現可能な最大長が記録されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    S = input().strip()
    if len(S) <= 1:
        print(len(S))
        return

    def classify(a, b):
        if a == b == '0':
            return 0
        if a == b == '1':
            return 2
        return 1

    cnt = [0, 0, 0]  # 00, 01, 11
    l = 0
    ans = 0

    for r in range(len(S)):
        if r > l:
            c = classify(S[r-1], S[r])
            cnt[c] += 1

        while cnt[0] > n or cnt[1] > m or cnt[2] > k:
            if l + 1 <= r:
                c = classify(S[l], S[l+1])
                cnt[c] -= 1
            l += 1

        ans = max(ans, r - l + 1)

    print(ans)

if __name__ == "__main__":
    solve()
```コア実装は、部分文字列ごとに遷移カウントを再計算するのではなく、遷移カウントを維持します。 関数分類は 3 つのエッジ タイプをエンコードし、隣接する各ペアが 1 回だけ寄与することを保証します。 

左ポインタの更新では、l をシフトする前に、出ていくエッジの寄与を慎重に削除します。 l + 1 <= r という条件は、単一の文字には遷移がないため、ウィンドウのサイズが 1 になったときの無効なアクセスを防止します。 

よくある落とし穴は、制約が生の文字数ではなくトランジションに適用されることを忘れていることです。 もう 1 つは、ウィンドウを縮小するときにカウンタを誤って更新することで、不変条件が崩れ、過剰カウントにつながります。 

## 実用的な例

 S = 0101、n = 0、m = 3、k = 0 を考えてみましょう。混合タイルのみが許可されます。 

ウィンドウの拡大を追跡します。 

| r | S[r] | ウィンドウ | cnt00 | cnt01 | cnt11 | 有効 |
 | --- | --- | --- | --- | --- | --- | --- |
 | 0 | 0 | 0 | 0 | 0 | 0 | はい |
 | 1 | 1 | 01 | 0 | 1 | 0 | はい |
 | 2 | 0 | 010 | 0 | 2 | 0 | はい |
 | 3 | 1 | 0101 | 0 | 3 | 0 | はい |

 完全な文字列は実行可能であるため、答えは 4 です。これにより、交互構造が混合タイルのみを消費することが確認されます。 

ここで、S = 00110、n = 1、m = 1、k = 0 について考えてみましょう。混合タイルは許可されないため、遷移は禁止されます。 

| r | S[r] | ウィンドウ | cnt00 | cnt01 | cnt11 | 有効 |
 | --- | --- | --- | --- | --- | --- | --- |
 | 0 | 0 | 0 | 0 | 0 | 0 | はい |
 | 1 | 0 | 00 | 1 | 0 | 0 | はい |
 | 2 | 1 | 001 | 1 | 1 | 0 | はい |
 | 3 | 1 | 0011 | 1 | 1 | 1 | はい |
 | 4 | 0 | 00110 | 2 | 1 | 1 | 収縮なし |

 r = 4 では、cnt00 が n を超えるため、ウィンドウは無効になります。 アルゴリズムは実現可能性が回復するまで l をシフトし、最適な有効なサフィックスが確実に見つかるようにします。 

これらのトレースは、実現可能性が全体的な数ではなく、隣接する構造によって完全に左右されることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N) | 各ポインタは最大 N 回移動し、各エッジは 1 回追加および削除されます。 
| スペース | お(1) | 3 つのカウンタとポインタのみが保存されます。 

文字列の長さは 1e6 に達する可能性があるため、線形時間が必要です。 スライディング ウィンドウにより、各文字ペアが一定回数処理され、制約内に快適に収まるようになります。

 ## 特殊なケース

 単一文字の文字列が最も単純な境界です。 隣接するペアがないため、リソースは消費されません。 r = 0 の場合、アルゴリズムは ans を少なくとも 1 で正しく初期化し、カウンターの更新は行われません。 

完全に交互の文字列は、m への依存を強調します。 すべてのステップで cnt01 が増加し、m を超えない限りアルゴリズムは縮小しません。 これにより、混合エッジが正しく分類され、持続的な成長が正しく処理されることが検証されます。 

00000 のような文字列は、00 タイルの蓄積を強調します。 各拡張では cnt00 が 1 つ追加され、n を超えると、左ポインタが前に進み、古い 00 の寄与が削除されます。 正確性は対称的な追加と削除の動作に依存しており、縮小操作中に二重カウントが発生しないことが保証されます。
