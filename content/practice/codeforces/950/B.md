 ## 解決策
 ## 問題の理解

 正の整数の 2 つのシーケンスが与えられます。各シーケンスは、長いバイト ストリームがどのようにチャンクで送信されたかを表します。 各シーケンスは同じ全長のセグメント化ですが、セグメント化ポイントは異なります。 

私たちが再構築したい隠れた構造は、次々に書き込まれた複数のファイルで構成されるアーカイブです。 各ファイルにはある程度の合計サイズがありますが、送信中に各ファイルが複数の連続したブロックに分割される場合があります。 重要なのは、各メッセージ内では、元のファイルの境界ではなく、これらの小さなブロックのみが表示されることです。 私たちのタスクは、両方のメッセージが同じファイル サイズのシーケンスから送信され、分割方法が異なるだけであるように、元のファイルの可能な最大数を決定することです。 

したがって、合計が等しい 2 つの配列が与えられ、セグメントの合計が順番に一致するように、両方の配列を連続したセグメントに分割する必要があります。 目標は、作成できる一致するセグメントの数を最大化することです。 

制約が十分に大きいため、合計入力サイズが線形より悪い解は遅すぎるでしょう。 どちらの配列にも最大 100,000 個の要素を含めることができるため、それらを 1 回のパスまたはほぼ 1 回のパス時間で処理するメソッドが必要です。 ネストされたスキャンやプレフィックス合計の繰り返しの再計算を伴うものはすべて失敗します。 

単純な間違いは、両方の配列ですべての可能なパーティション ポイントを独立して試行することです。 たとえば、入力が小さい場合でも、最初の配列のプレフィックスの合計を 2 番目の配列のすべてのプレフィックスの合計と揃えようとする場合があります。 これはすぐに壊れます。次のような配列の場合`1 1 1 1 ...`パーティションの組み合わせの数は二次関数的に増加します。 

もう 1 つの微妙な失敗例は、貪欲なマッチングが同期なしで行われた場合に発生します。 一方のプレフィックスの合計が他方のプレフィックスの合計よりも小さい場合にファイルを貪欲に切り取り、同時に両方の配列で完全なファイル境界を等しくすることを忘れると、不一致のパーティションが生成される可能性があります。 

正しい構造は、双方の合計が同じ合計に達した場合にのみ「ファイルをカット」するように、累積合計を同期することに依存します。 

## アプローチ

 ブルートフォース手法では、両方の配列内のパーティション ポイントを選択し、セグメントの合計を照合しようとします。 すべてのプレフィックスの合計を生成し、選択した各ペアがファイル境界を形成するように、それらを昇順にペアにしようとすることを想像することもできます。 これは概念的には単純ですが、分割ポイントの組み合わせを調べる必要があり、実装に応じて指数関数的または少なくとも二次関数的な動作が発生します。 要素が 10^5 の場合、これは不可能です。 

重要な洞察は、両方の配列が同じファイル サイズの合計シーケンスを、異なる方法で断片化しただけで表しているということです。 両方の配列を同時に調べて合計を累積すると、累積された合計が一致したときに完全なファイル境界に到達したことを検出できます。 その時点で、1 つのファイルが完了したことを安全に宣言し、両方のアキュムレータをリセットできます。 

これが機能するのは、ファイル境界が両方の累積合計が一致する点に正確に対応しているためです。 秩序は保たれるので、以前の決定を再考する必要はありません。

 ## アルゴリズムのチュートリアル

 各配列に 1 つずつ、合計 2 つのポインターと、各メッセージからの現在の部分的に蓄積されたファイルを表す 2 つの累計を維持します。 

1. 2 つのインデックスを初期化する`i = 0`、`j = 0`、および 2 つのアキュムレータ`a_sum = 0`、`b_sum = 0`。 初期化もする`files = 0`。 
2. どちらも使い果たされないうちに、両方のアレイを移動します。 各ステップで、次のブロックを小さい方のアキュムレータまたは両方のアキュムレータに追加します。 
3. もし`a_sum`よりも小さいです`b_sum`、最初の配列から次のブロックを取得し、それを追加します。`a_sum`。 私たちは前進します`i`。 
4. もし`b_sum`よりも小さいです`a_sum`、2 番目の配列から次のブロックを取得し、それを次の配列に追加します。`b_sum`。 私たちは前進します`j`。 
5. もし`a_sum == b_sum`両方ともゼロ以外の場合、両方の表現で共有される完全なファイル境界が見つかりました。 インクリメントします`files`そして両方の合計をゼロにリセットします。 
6. 両方のアレイが完全に消費されるまで続行します。 最終的な答えは、`files`。 

このステッピング ルールが機能する理由は、一方が他方からの補償なしにオーバーシュートを決して許さないためです。 両方のアキュムレータが同じ現在のファイル候補の部分和を表すという不変条件を常に保持します。 等しい場合、両方の部分構造が元のアーカイブ内の完全なファイルに対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    x = list(map(int, input().split()))
    y = list(map(int, input().split()))
    
    i = j = 0
    sx = sy = 0
    ans = 0
    
    while i < n or j < m:
        if sx <= sy:
            if i < n:
                sx += x[i]
                i += 1
        else:
            if j < m:
                sy += y[j]
                j += 1
        
        if sx == sy:
            if sx != 0:
                ans += 1
            sx = sy = 0
    
    print(ans)

if __name__ == "__main__":
    solve()
```この実装は、2 ポインター同期のアイデアに直接従っています。 重要な繊細さは、`sx <= sy`条件: 合計が等しい場合、最初の配列を最初に拡張することを好みますが、進行状況を維持する限り、どちらの側が進んでも問題ではありません。 直後の等価性チェックにより、両方の部分和が一致するたびに、ファイル境界がコミットされることが保証されます。 

よくある落とし穴の 1 つは、ファイルをカウントした後に両方のアキュムレーターをリセットするのを忘れることです。 もう 1 つは、1 つの配列が先に終了したときに終了を保証せずに 1 つのポインターだけを進め続けることです。 の`while i < n or j < m`この条件により、残りのブロックが引き続き処理されることが保証されます。

            sx = sy = 0

 ## 特殊なケース

 エッジ ケースの 1 つは、一方の配列が他方よりも早く蓄積を完了する場合です。 たとえば、1 つのシーケンスの最後に大きなブロックがある場合、アルゴリズムは、合計が一致するまで、もう 1 つの配列の残りのブロックを消費し続ける必要があります。 ループ条件`i < n or j < m`早期に停止しないようにします。 

もう 1 つのケースは、カット後のゼロ調整により、等価性が短期間に複数回連続して発生する場合です。 リセット ステップでは、両方のアキュムレータが一致するたびに正常に再起動されるため、連続するファイルが個別にカウントされることが保証されます。 

最後の微妙なケースは、最後のファイルが両方の配列の最後のブロックで正確に終了する場合です。 等価性により終了時でもカットがトリガーされ、その後は未処理の要素が存在しないため、アルゴリズムは依然としてそれをカウントします。
