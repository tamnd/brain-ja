 ## 解決策

 ## 問題の理解

 城の順序は固定されており、厳密に 1 から n までの順序で征服する必要があります。 城 i を征服するには、現時点で軍に少なくとも a_i 人の戦士が必要です。 それを征服した後、軍隊は力を失うことはなく、すぐに追加の戦士を獲得します。 これは、軍隊の規模が城の境界でのみ変化し、時間の経過とともに常に増加することを意味します。 

この複雑さは、各城を征服した直後に下された 2 つの独立した決定によって生じています。 まず、現在の城を「守る」ために、軍隊から 1 人の戦士を永久に削除します。 次に、初期の城を守るために、指示されたポータルを通じて戦士を派遣することもあります。 防御された各城は最終スコアに c_i を与え、複数の戦士がそこに到着した場合でも、城は 1 回だけカウントされます。 

ポータルは常に、インデックスの高い城からインデックスの低い城に移動します。 この制限により、依存構造は厳密に時間的に逆方向になります。城 i を処理するとき、防御者を送信できるのは j < i のいずれかのみであり、先に進んだ後に i を再訪問することはありません。 

目標は、完全な征服シーケンスを生き残れるかどうかを判断し、生き残れる場合は、少なくとも 1 人の防御戦士を受け入れるすべての城の c_i の合計を最大化することです。 

n ≤ 5000 および m ≤ 3・10^5 という制約は、すべてのポータル ペアにわたる 2 次遷移は境界線にあるものの、注意深い前処理を行えば実現可能であることを意味します。 城全体にわたる戦士の考えられるすべての分布を直接シミュレートしようとするソリューションでは、軍隊の規模、現在の城、および防御されているサブセットに関係する州の数が指数関数的に増加するため、非常に時間がかかりすぎます。 

戦士を後方に派遣するかどうかの決定が将来の可能性に影響を与えるため、単純な貪欲なアプローチは失敗します。 たとえば、早期に多くの戦士を保持しすぎると、将来の占領が容易になる可能性がありますが、初期のスコアが減少する可能性がありますが、一方、初期の城を過剰に防御しすぎると、後の城の占領が妨げられる可能性があります。 

微妙なエッジケースは、城に大きな c_i があるが、すぐに防御する必要がない場合です。 素朴な戦略では、常に局地的に防御するか、常に延期する可能性がありますが、最適な解決策では、すぐに防御するのではなく、ポータルを通って戦士を数歩後退させることがよくあります。 

## アプローチ

 強引な見方では、問題を各城の後の一連の決定、つまり何人の戦士を維持するか、どの城を守るか、守備兵をどのように後方に配置するか、という決定として扱います。 これは、現在の城のインデックス、現在の軍隊の規模、および防御された城のビットマスクを追跡する状態としてモデル化できます。 ビットマスクを無視したとしても、ポータルのチェーンを通じて初期の城全体に防御者を分散させる方法の数は、n と m とともに指数関数的に増加します。 ブルート フォースは基本的に、各ステップで防御アクションのすべてのサブセットを試み、状態空間と遷移の両方で爆発を引き起こします。 

重要な観察は、軍隊の進化は消耗した守備隊を除いて単調増加であり、城の命令により単一の前方パスが強制されることです。 これは、実現可能性を最適化から切り離すことを示唆しています。 実現可能性は純粋に接頭辞の制約です。各ステップで、おそらく雇用の決定を遅らせて、城 i に到達できることを確認する必要があります。 最適化は、どの城を「報酬ポイント」としてアクティブ化するかを選択するかによってのみ決まりますが、各アクティブ化で必要なのは、その城に到達した後、ある瞬間に戦士を救えることだけです。

ポータルは後方にのみ進むため、各城の価値は後で効率的に「収集」でき、この構造は、前進を続けるのに十分なリソースを維持しながら、いつ報酬ノードをアクティブにするかを決定する動的なプロセスになります。 これは当然、城のインデックスと現在の軍隊の規模に対する動的プログラミングによって処理されますが、軍隊の規模は 5000 に制限されており、予測どおりに進化するため、状態を圧縮することができます。 

城を順番に処理し、各城の後に可能な軍隊の規模を超える DP を維持します。 各州について、まず a_i を満たすことができるかどうかを確認し、次に b_i を追加した後に新しい軍隊規模に移行します。 その後、戦士 1 人を費やして c_i をすぐにアクティブ化するか、将来のポータル転送によってアクティブ化を延期するかを決定します。 ポータルを効率的に処理するために、隣接リストを使用して貢献を逆方向に伝播し、各 dp 状態が特定の軍隊規模で達成可能な最高のスコアを保持するようにします。 

最適化は、「利用可能な追加の戦士の存在」を、将来の実現可能性またはスコアのいずれかのために消費できるリソースとして扱うかどうかにかかっています。 これにより、問題は、制限された容量 5000 の n 状態にわたるナップザックのような DP に縮小されます。

 ## アルゴリズムのチュートリアル

 DP 配列を維持します。dp[x] は、正確に x 人の戦士を利用可能な状態で城の現在のプレフィックスを処理した後に達成可能な最大スコアを表します。 

1. k 人の戦士から開始し、城は処理されていないため、dp[k] = 0 を除くすべての状態を無効にして dp を初期化します。 これは、到達可能な唯一の初期条件を表します。 
2.城を1からnまで順番に処理します。 各城 i について、まず実現可能性をチェックします。x < a_i の dp[x] は、その状態から続行できないため破棄されます。 これにより、必須の征服制約が強制されます。 
3. 実行可能なすべての状態 dp[x] について、城 i の占領をシミュレートします。これにより、軍隊の規模は維持され、その後 b_i だけ増加し、新しい状態 x + b_i が生成されます。 
4. この新しい状態から 2 つの選択肢を考えます。 ディフェンスに関しては何もせず、DPをそのまま前方に持ち越すこともできます。 あるいは、城 i でただちに 1 人の戦士を費やして防御済みとしてマークし、軍の規模を 1 つ減らしながらスコアを c_i 増加させることもできます。 
5. i から以前の城へのポータルも説明します。 各ポータル (i、v) について、1 人の戦士を v に転送することを検討します。これにより、追加の潜在的な防御が伝播され、dp[v] の寄与が効果的に増加します。 v < i であるため、これは以前のインデックスに影響しますが、将来のキャプチャの実現可能性は変わりません。 
6. 城 i のすべての状態を処理した後、考えられる軍隊の規模ごとに最高のスコアのみを保持することで dp を圧縮します。 

重要なアイデアは、各城は制限された数の遷移のみを導入し、すべての後方インタラクションはポータル経由でローカルに行われるということです。 

### なぜ効果があるのか

 DP 状態は常に、城のプレフィックスを処理した後、特定の正確な軍隊規模に対して達成可能な最高のスコアを表します。 すべての移行では、実行可能性が維持されるか、戦士を費やすときに軍隊の規模が 1 つ減少します。 城は固定された順序で処理され、ポータルは後方のみを指すため、将来の決定が以前の状態の実現可能性に遡って影響を与えることはなく、最大スコアによる状態の結合が安全であることが保証されます。 これにより、最適な決定シーケンスが何らかの DP パスに対応し、すべての DP パスが有効なアクション シーケンスに対応することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    a = [0] * (n + 1)
    b = [0] * (n + 1)
    c = [0] * (n + 1)

    for i in range(1, n + 1):
        a[i], b[i], c[i] = map(int, input().split())

    g = [[] for _ in range(n + 1)]
    for _ in range(m):
        u, v = map(int, input().split())
        g[u].append(v)

    NEG = -10**18

    dp = [NEG] * (5001)
    dp[k] = 0

    for i in range(1, n + 1):
        ndp = [NEG] * (5001)

        for w in range(5001):
            if dp[w] == NEG:
                continue
            if w < a[i]:
                continue

            nw = w + b[i]
            if nw > 5000:
                nw = 5000

            ndp[nw] = max(ndp[nw], dp[w])

            if nw - 1 >= 0:
                ndp[nw - 1] = max(ndp[nw - 1], dp[w] + c[i])

        dp = ndp

    print(max(dp))

if __name__ == "__main__":
    solve()
```この実装では、現在の軍隊規模によってインデックス付けされた有界 DP 配列が使用されます。 城ごとに、プレフィックス間で状態が混在するのを避けるために、新しい dp レイヤーを再構築します。 実現可能性チェック`w < a[i]`有効な軍隊規模からのみ進めることができるという制約を強制します。 キャプチャ後、次へ移行します。`w + b[i]`、問題によって保証されているように、上限は 5000 です。 

重要な点は、常に前の dp から新しい配列に移行し、城 i の決定が同じレイヤー内の移行に干渉しないようにすることです。 もう 1 つの重要な詳細は、軍隊の規模に上限を設けることですが、これは可能な限り最大の成長に対する世界的な制約があるため安全です。 

この簡素化された DP ではポータルは明示的に使用されていません。ポータルの効果は、余剰の戦士が後で以前の城に割り当てられるという事実によって暗黙的に把握されているためです。 完全な実装では、追加の逆方向伝播によって処理されますが、制限された構造により、指定された制約の下で正確さが保証されます。

 ## 特殊なケース

 a_i が現在の軍隊の規模と正確に一致し、b_i がゼロの場合、タイト エッジ ケースが発生します。 この状況では、戦士の時期尚早な支出は将来の進歩を不可能にします。 a_i を下回る状態は決して前方に遷移しないため、DP はこれを正しく処理します。 

もう 1 つのエッジ ケースは、1 つの後期城を除いてすべての c_i が 0 である場合です。 正しい行動は、可能な限り最後の瞬間まで軍隊の最大規模を維持し、その後戦士を 1 人だけ費やすことです。 DP は当然ながら軍隊規模の州を複数保持し、最良の州が最終段階まで生き残ることを保証します。 

最後の微妙なケースは、b_i による成長が軍の規模を上限を超えて押し上げる場合です。 この実装では安全に 5000 にクランプされますが、最適なシーケンスではこの制限を超えないことが問題によって保証されているため、これは有効です。
