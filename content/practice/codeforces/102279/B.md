 ## 解決策
 ## 問題の理解

 最大 200,000 個の頂点を持つツリーがあり、1 つの未知の頂点には隠された秘密が含まれています。 プログラムは 2 つのクエリを使用してインタラクターと通信できます。 タイプ 1 のクエリは、選択した頂点から非表示の頂点までの距離を要求します。 タイプ 2 のクエリは、非表示の頂点に向かうパス上にある、選択した頂点の近傍を求めます。 選択した頂点がすでに非表示の頂点である場合、タイプ 2 はゼロを返します。 目標は、最大 36 個のクエリを使用して隠れた頂点を特定することです。 この問題は完全に対話型であるため、入力にはツリーのみが含まれますが、クエリに対する回答は実行中に到着します。 

ツリーには 200,000 個の頂点があるため、クエリの制限が 36 である場合、クエリですべての頂点をスキャンすることは直ちに不可能になります。 ツリー全体にわたる線形前処理パスは完全に合理的ですが、頂点ごとに 1 つのクエリを要求すると、最悪の場合、200,000 のクエリが必要になります。 意図したソリューションでは、クエリのたびに、隠れている可能性のある頂点のセットを幾何学的に縮小させる必要があります。 

特に誤って対処しやすいエッジケースが 3 つあります。 1 つ目は 1 頂点のツリーです。```
1
```唯一の頂点が必然的に答えとなるため、正しい出力は次のようになります。`1`。 すべてのタイプ 2 の応答が有効な近傍であると想定する不用意な実装は失敗します。これは、非表示の頂点自体をクエリするときにインタラクターがゼロを返すためです。 

2 番目のケースは 2 頂点ツリーです。```
2
1 2
```非表示の頂点が 2 の場合、タイプ 2 で頂点 1 をクエリすると 2 が返されます。その後、アルゴリズムは 2 を含む 1 つの頂点コンポーネント内で続行し、再度クエリを実行して、0 を受け取る必要があります。 最初の非ゼロ応答の後に停止すると、非表示の頂点ではなく近傍が出力されます。 

3 番目のケースはスターです。```
5
1 2
1 3
1 4
1 5
```非表示の頂点が 5 の場合、頂点 1 が重心になります。 1 のタイプ 2 クエリは、唯一の関連コンポーネント、つまり 5 を含むシングルトンを即座に識別します。アルゴリズムは、返された近傍をグローバルに破棄したり、応答を最終応答として扱うのではなく、残りのツリーから重心を切り取る必要があります。 

公式社説では、LCA、DFS、および二分探索ソリューションが示されており、代替案として重心分解についても言及されています。 以下のアプローチではセントロイドのアイデアを直接使用しており、これによりクエリ バインドが特に透過的になります。 

## アプローチ

 簡単な戦略は、返される距離がゼロになるまで、すべての頂点に対してタイプ 1 クエリを実行することです。 これは正しいです。なぜなら、ちょうど 1 つの頂点が隠れた頂点からの距離が 0 であるからです。 問題はクエリの制限です。 最悪の場合、非表示の頂点がテストされた最後の頂点となり、200,000 のクエリが必要になりますが、インタラクターが許可するのは 36 クエリのみです。 

距離クエリによって、テストされた頂点が答えであるかどうかに関する完全な情報が得られるため、総当たりアプローチが機能します。 1 つの候補を区別するために 1 つのクエリが費やされるため、失敗します。 一度に大部分の候補を排除できる答えが必要なクエリが必要です。 

重要な観察は、木の重心の定義です。 すべてのツリーには頂点があり、その頂点を削除した後に得られるすべての接続コンポーネントには元の頂点の最大半分が含まれます。 考えられる隠れた頂点の現在のセットが接続コンポーネントを形成し、その重心を選択すると仮定します。`c`。 

タイプ 2 クエリ`c`からのパス上の最初のエッジを正確に与えます`c`隠れた頂点へ。 答えがゼロの場合、`c`それ自体は非表示になり、完了です。 それ以外の場合、答えは次のようになるとします。`v`。 隠れた頂点はその向こうにあるから`v`を含むコンポーネントに属している必要があります。`v`後`c`が削除されます。 他のコンポーネントはすべて完全に破棄できます。 

重要な部分は、残りのコンポーネントの頂点の数が前のコンポーネントの最大半分であることです。 そのコンポーネントに対して同じ操作を繰り返します。 これはまさに重心分解の背後にあるクエリ パターンであり、クエリごとに可能な頂点の数がおよそ 2 分の 1 に減少します。 この問題に対する重心ベースの解決策は、タスクを解決する自然な方法として外部のコンテスト資料にも記載されています。 

200,000 頂点の場合、18 等分で十分です。`2^18 = 262144`。 したがって、アルゴリズムは最大 18 個のタイプ 2 クエリを使用しますが、制限の 36 個を余裕で下回ります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n) 個のクエリと O(n) 個のローカル作業 | O(n) | 遅すぎる |
 | 重心検索 | O(n log n) 個のローカル作業と O(log n) 個のクエリ | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ツリーの隣接リストを作成します。 以前に選択した重心を切断して得られた接続コンポーネントを繰り返し検査するため、元のツリー自体を変更する必要はありません。 
2. ブール値を維持する`blocked`配列。 ブロックされた頂点は、現在の検索空間からすでに削除されている重心を表します。 非表示の頂点を含むコンポーネントは、常に 1 つのブロックされていない開始頂点によって表されます。 
3. 現在の頂点から開始して、ブロックされていない頂点のみをトラバースし、現在のコンポーネント全体を収集します。 この走査中に、訪問した頂点ごとに親を保存します。 ツリーは長さ 200,000 のパスになる可能性があり、通常の再帰制限を超える可能性があるため、Python では反復走査が推奨されます。 
4. 走査順序を逆に処理して、収集されたコンポーネント内のサブツリー サイズを計算します。 すべての頂点について、その親側のコンポーネントのサイズは次のようになります。`total_size - subtree_size[v]`、すべての子は独自のサブツリー サイズを提供します。 
5. 頂点を見つける`c`結果として得られるすべてのコンポーネントのサイズは最大でも`total_size / 2`。 このような頂点が重心です。 現在のコンポーネント内のすべての頂点を単純にスキャンし、サブツリーのサイズを使用してこの状態をテストできます。 
6. 対話者に質問する`? 2 c`。 答えが 0 の場合、重心自体が隠れた頂点であるため、次のように出力します。`! c`そして終了します。 
7. 答えが頂点の場合`v`、 ブロック`c`そして作ります`v`次の反復の開始頂点。 からのエッジ`c`向かって`v`効果的にカットされるようになりました。 なぜなら`v`～からの道沿いにある`c`非表示の頂点に対して、非表示の頂点はこの新しいコンポーネントの内部にあることが保証されます。 
8. タイプ 2 クエリがゼロを返すまで繰り返します。 各反復では、可能な頂点の数が少なくとも半分に減少するため、最大 18 個のクエリが必要になります。`n <= 200000`。 

### なぜ効果があるのか

 現在のブロックされていないコンポーネントに非表示の頂点が含まれるという不変条件を維持します。 最初はツリー全体が現在のコンポーネントであるため、不変条件は true です。 その重心が`c`が尋ねられ、ゼロ以外の答えが返される`v`の隣人です`c`～からのユニークなパスで`c`隠れた頂点へ。 削除中`c`したがって、隠れた頂点は、次の要素を含むコンポーネント内にそのまま残ります。`v`。 アルゴリズムはそのコンポーネントを正確に保持するため、不変式は true のままになります。 クエリがゼロを返した場合、インタラクターは次のことを確立しました。`c`は隠れた頂点なので、アルゴリズムは安全に出力できます。 

重心プロパティにより、保持されるコンポーネントに前のコンポーネントの最大半分が含まれることが保証されます。 最大 200,000 頂点から開始し、このような削減を 18 回行った後、残る頂点は 1 つ未満になるため、36 クエリ制限を超える前に隠れた頂点が特定されている必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(1_000_000)

def find_centroid(start, graph, blocked, parent, size):
    order = [start]
    parent[start] = 0

    for v in order:
        pv = parent[v]
        for to in graph[v]:
            if blocked[to] or to == pv:
                continue
            parent[to] = v
            order.append(to)

    total = len(order)

    for v in reversed(order):
        size[v] = 1
        pv = parent[v]
        for to in graph[v]:
            if blocked[to] or parent[to] != v:
                continue
            size[v] += size[to]

    for v in order:
        largest = total - size[v]

        for to in graph[v]:
            if blocked[to] or parent[to] != v:
                continue
            if size[to] > largest:
                largest = size[to]

        if largest * 2 <= total:
            return v

    return start

def ask(t, v):
    print("?", t, v, flush=True)
    ans = int(input())
    if ans == -1:
        sys.exit(0)
    return ans

def main():
    n = int(input())

    graph = [[] for _ in range(n + 1)]

    for _ in range(n - 1):
        u, v = map(int, input().split())
        graph[u].append(v)
        graph[v].append(u)

    blocked = [False] * (n + 1)
    parent = [0] * (n + 1)
    size = [0] * (n + 1)

    current = 1
    queries = 0

    while True:
        centroid = find_centroid(
            current,
            graph,
            blocked,
            parent,
            size
        )

        queries += 1
        if queries > 36:
            sys.exit(0)

        nxt = ask(2, centroid)

        if nxt == 0:
            print("!", centroid, flush=True)
            return

        blocked[centroid] = True
        current = nxt

if __name__ == "__main__":
    main()
```隣接リストには元のツリーが保存されます。 エッジは物理的に削除されません。削除するには、複数の隣接リストを更新する必要があるためです。 その代わり、`blocked[v]`以前に選択した重心を、今後のすべてのコンポーネントの走査に対して非表示にします。`find_centroid`最初に現在の接続コンポーネントを横断します。 の`order`リストには、親、子の順序で頂点が含まれます。 このリストを逆方向に処理すると、再帰なしですべてのサブツリーのサイズが得られます。 パス形状のツリーには 200,000 のネストされた頂点を含めることができるため、これは Python で特に役立ちます。 

頂点の場合`v`、`size[v]`一時的なルートに対するサブツリーのサイズです。`start`。 削除中`v`サイズを指定して親側に可能なコンポーネントを 1 つ作成します`total - size[v]`、サイズを持つ子ごとに 1 つのコンポーネントを追加`size[child]`。 これらの値の最大値が最大でも半分である場合、頂点は重心になります。`total`。 

の`ask`関数はクエリを出力し、すぐに標準出力をフラッシュします。 インタラクティブな問題では、バッファされたままのクエリにはインタラクターが応答できないため、フラッシュは必須です。 インタラクターが戻った場合`-1`、プロトコルはプログラムを終了する必要があると述べています。 

タイプ 2 のクエリのみが必要です。 ゼロ以外の答え自体は隠れた頂点ではありません。 これは、非表示の頂点へのパス上で現在の重心の後の最初の頂点であるため、どの半分のサイズのコンポーネントを保持するかを示します。 

最大入力サイズに対して最大 18 個のクエリが作成されることが centroid 引数によってすでに証明されているため、クエリ カウンタは正確性を保つために技術的には不要です。 これを実装内に保持すると、偶発的なプロトコル違反が安全に失敗します。 

コンポーネントの走査や重心の計算には再帰はありません。 これにより、パス形状のツリーでの Python スタックのオーバーフローが回避されます。 Python 整数では、サブツリー サイズのオーバーフローの問題も発生しませんが、関連するすべてのサイズはいずれにせよ最大でも 200,000 しかありません。

3 5
6 2
1 3

```そして転写により、隠れた頂点が 3 であることが明らかになります。 

完全な 7 頂点ツリーの重心は頂点 2 です。2 を削除すると、サイズ 1、1、1、および 3 のコンポーネントが残るため、すべてのコンポーネントのサイズは最大 3 になります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | 各重心検索反復では、現在のコンポーネントがスキャンされ、そのサイズは幾何学的に減少します。 
| スペース | O(n) | 隣接リストと補助配列にはそれぞれ線形空間が必要です。 
| クエリ | O(log n) | すべてのクエリにより、候補コンポーネントは最大でも前のサイズの半分に縮小されます。 

のために`n = 200000`、セントロイド クエリは最大 18 個存在する可能性があります。`2^18 = 262144`。 ローカル ツリー処理は、以下の範囲で幾何学的シーケンスのスキャンを実行します。`O(n log n)`これは、コンパイルされた実装での 2 秒および 256 MB の制限と容易に互換性があり、反復トラバーサルを使用する Python でも実用的です。 

## テストケース

 これはインタラクティブな問題であるため、公開されたサンプルは、通常の決定的な入出力ペアではなく、インタラクションの記録です。 普通の`run(input)`ヘルパーはインタラクターを再現できません。 次のテスト ハーネスは、固定の非表示頂点を使用し、タイプ 2 の回答をシミュレートします。 オフライン ソルバーは、送信された重心アルゴリズムをミラーリングしますが、シミュレーターは、クエリされた頂点の親がインタラクターのタイプ 2 応答とまったく同じになるように、ツリーを非表示の頂点にルートします。```python
import io
import sys

def solve_offline(inp: str, hidden: int):
    data = list(map(int, inp.split()))
    it = iter(data)

    n = next(it)
    graph = [[] for _ in range(n + 1)]

    for _ in range(n - 1):
        u = next(it)
        v = next(it)
        graph[u].append(v)
        graph[v].append(u)

    # Simulate the interactor's type-2 answers.
    parent_hidden = [0] * (n + 1)
    order = [hidden]

    for v in order:
        for to in graph[v]:
            if to == parent_hidden[v]:
                continue
            parent_hidden[to] = v
            order.append(to)

    blocked = [False] * (n + 1)
    parent = [0] * (n + 1)
    size = [0] * (n + 1)

    def find_centroid(start):
        order = [start]
        parent[start] = 0

        for v in order:
            for to in graph[v]:
                if blocked[to] or to == parent[v]:
                    continue
                parent[to] = v
                order.append(to)

        total = len(order)

        for v in reversed(order):
            size[v] = 1
            for to in graph[v]:
                if blocked[to] or parent[to] != v:
                    continue
                size[v] += size[to]

        for v in order:
            largest = total - size[v]

            for to in graph[v]:
                if blocked[to] or parent[to] != v:
                    continue
                largest = max(largest, size[to])

            if largest * 2 <= total:
                return v

        return start

    current = 1
    queries = 0

    while True:
        centroid = find_centroid(current)
        queries += 1

        if centroid == hidden:
            return centroid, queries

        nxt = parent_hidden[centroid]
        blocked[centroid] = True
        current = nxt

# Provided sample tree. The interaction transcript establishes hidden = 3.
sample = """\
7
2 1
2 4
3 5
6 2
1 3
2 7
"""
assert solve_offline(sample, 3) == (3, 2), "sample"

# Minimum-size tree.
case_min = """\
1
"""
assert solve_offline(case_min, 1) == (1, 1), "minimum tree"

# Two vertices, hidden at the second vertex.
case_two = """\
2
1 2
"""
assert solve_offline(case_two, 2) == (2, 2), "two-vertex boundary"

# Star, testing a highly branching tree and an immediate singleton component.
case_star = """\
5
1 2
1 3
1 4
1 5
"""
assert solve_offline(case_star, 5) == (5, 2), "star"

# Maximum-size path, hidden at the final vertex.
n = 200000
case_max = str(n) + "\n" + "\n".join(
    f"{i} {i + 1}" for i in range(1, n)
) + "\n"

answer, queries = solve_offline(case_max, n)
assert answer == n, "maximum-size path answer"
assert queries <= 18, "centroid query bound"

 最大サイズのテストでは、再帰ツリー アルゴリズムにとって最悪の形状であるパスを意図的に使用します。 送信されたソリューションはパスを再帰することはなく、セントロイド プロセスによりクエリごとに残りの長さの約半分に短縮されます。 

## 特殊なケース

 頂点が 1 つのツリーの場合、```
1
```唯一可能な現在のコンポーネントは`{1}`、その重心は 1 です。タイプ 2 のクエリ`? 2 1`頂点 1 が非表示の頂点であるため、ゼロを返します。 プログラムはすぐに印刷します`! 1`。 ゼロを近傍として解釈する試みはないため、境界の場合は正しく処理されます。 

2頂点ツリーの場合```
2
1 2
```非表示の頂点 2 では、初期重心は 1 です。1 でのタイプ 2 クエリは 2 を返します。その後、頂点 1 がブロックされ、シングルトン コンポーネントが残ります。`{2}`。 その重心は 2 で、次のタイプ 2 クエリはゼロを返します。 アルゴリズムは、正確に 2 つのクエリの後に 2 を出力します。 これは、非ゼロのタイプ 2 応答が「この頂点に応答する」ではなく「この方向に継続する」ことを意味する理由を示す最小の例です。 

五頂点星の場合```
5
1 2
1 3
1 4
1 5
```非表示の頂点 5 では、頂点 1 が重心になります。 これをクエリすると 5 が返されるため、他のすべてのリーフはすぐに破棄できます。 次のコンポーネントには頂点 5 のみが含まれており、そのクエリはゼロを返します。 このアルゴリズムは 2 つのクエリを使用し、距離情報を必要としません。 

最大サイズのパスの場合、最初の重心は中央付近にあります。 非表示の頂点が 1 つの端点にある場合、タイプ 2 の答えは、その端点を含む半分を選択します。 次の重心は再びその半分の中央近くにあり、同じプロセスが続きます。 したがって、200,000 頂点のパスでは、深さが 199,999 であるにもかかわらず、最大 18 個のクエリが必要になります。 反復走査は、パスの深さが原因で Python 再帰エラーが発生するのを防ぎます。 

これらすべての例の中央のエッジ ケースは、残りのコンポーネントに 1 つの頂点がある瞬間です。 重心は必ずその頂点であり、タイプ 2 はゼロを返します。 実装では重心をブロックする前にこの応答をチェックするため、検索スペースから誤って正解が削除されることはありません。
