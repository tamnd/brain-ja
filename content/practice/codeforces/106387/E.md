 ## 解決策
 ## 問題の理解

 複数の建物のシステムが与えられ、それぞれが生産率に関連付けられています。 時間は日単位で進み、時間が経つにつれて、各建物はそれぞれの割合に応じて「食料箱」の需要を蓄積します。 

一定の日数の間$t$、すべての建物$i$蓄積された量によって決定される特定の数のボックスが必要です$t$日々。 食品は固定サイズの単位で梱包されるため、累積量から箱への換算は直線的ではありません。そのため、各建物の要件は一定の梱包サイズで割った後に切り上げられます。 すべての建物で必要なボックスの総数は、所定の世界的な供給制限を超えてはなりません。 

タスクは最大日数を見つけることです$t$すべての建物で必要なボックスの総数が利用可能な供給量の範囲内に収まるようにします。 

各建物はより多くの需要に貢献します$t$が増加し、供給制限を超えると、それより大きいすべての値で供給制限を超えたままになります。$t$。 この単調な動作により、問題は答えに対する二分探索に適したものになります。 

入力は、建物の数、それぞれの料金、梱包パラメータ、および利用可能なボックスの合計に対するグローバル制限で構成されます。 出力は、実行可能な最大日数を表す単一の整数です。 

制約により許可されるのは、$t$と同じくらい大きくなる$10^{12}$、日々の成長をシミュレートするソリューションは即座に除外されます。 一日中一度の線形チェックさえ不可能です。 代わりに、ソリューションでは候補の実現可能性を評価する必要があります。$t$で$O(n)$、そして検索してください$t$対数のチェックを使用します。 

1 日あたりの累積を再計算するという単純な解釈は完全に失敗します。 たとえば、次の場合$t = 10^{12}$、毎日繰り返すのは不可能です。 1 日あたりの増分を計算し、浮動小数点除算の結果を蓄積しようとすると、切り上げを正確に処理する必要があり、整数の精度が必要になるため、別の微妙な障害モードが発生します。 

## アプローチ

 ブルートフォースアプローチは、可能な限りの日数を試すことから始まります。$t$、ゼロから始まり、上向きに増加します。 候補者ごとに$t$、各建物に必要な食料の量を計算し、天井分割を使用してそれをボックスに変換し、すべての建物の合計を計算し、その合計が利用可能な制限内に収まるかどうかを確認します。 

このアプローチは、要件の定義を直接モデル化するため、正しいです。 ただし、実行時間は可能な最大値に応じて直線的に増加します。$t$、そしてそれ以来$t$到達できる$10^{12}$、1日に1回の評価さえ不可能になります。 ボトルネックはチェックごとのコストではなく、候補値の数です。 

重要な観察は、実現可能条件が単調であるということです。 一定の日数が経過すると$t$が実現可能である場合、すべての建物の需要は減少するか変わらないため、さらに短い日数も実現可能である必要があります。 これにより、問題は実行可能な値と実行不可能な値の間の境界を見つけることに変換されます。これがまさに二分探索の目的です。 

この構造が認識されると、タスクは候補を効率的にチェックすることになります。$t$大きな数値範囲に対して二分探索を使用します。

 ## アルゴリズムのチュートリアル

 私たちは問題を決定関数として扱います。$t$: 与えられた日数で、供給制限内ですべての建物を満たすことが可能かどうかを判断します。 

### ステップ

 1. 関数を定義する`can(t)`かどうかを計算します$t$日は可能です。 建物ごとに$i$、累積需要の天井分割を使用して、必要なボックスを計算します。$t$梱包サイズによります。 これらすべての値を合計し、グローバル制限と比較します。 いずれかの時点で合計が制限を超えた場合は、すでにわかっています$t$は無効であり、早期に停止する可能性があります。 
2. 二分探索範囲を次から設定します。$0$に$10^{12}$。 上限が選択されるのは、実行可能な答えは問題の制約内に存在する必要があり、しきい値を超えると実現可能性関数が false になるためです。 
3. この範囲に対して二分探索を実行します。 それぞれの中間点で$mid$、 評価する`can(mid)`。 
4. もし`can(mid)`それは本当です、保管してください$mid$潜在的な答えとして検索を右半分に移動します。最大化しようとしているためです。$t$。 false の場合は、右半分を破棄して、左半分に進みます。 
5. 二分探索が完了すると、保存された最良の値が実行可能な最大日数になります。 

実装の重要な詳細は、整数演算を使用して上限除算を正しく計算することです。 表現$\lceil \frac{x}{y} \rceil$次のように実装する必要があります$(x + y - 1) // y$浮動小数点エラーを避けるため。 

### なぜ効果があるのか

 正しさは単調性にかかっています。 として$t$が増加すると、各建物の累積需要は直線的に増加し、個別のボックスに切り上げた後は、同じままか増加するしかありません。 したがって、必要なボックスの合計は、減少しない関数です。$t$。 これにより、実現可能性述語が true から false に 1 回だけ遷移し、有効な値の連続したプレフィックスが形成されることが保証されます。 二分検索はこのプレフィックスの境界を正確に識別し、有効な最大値を保証します。$t$が見つかりました。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(t, a, x, b):
    total = 0
    for ai in a:
        total += (ai * t + x - 1) // x
        if total > b:
            return False
    return True

def solve():
    n, x, b = map(int, input().split())
    a = list(map(int, input().split()))

    lo, hi = 0, 10**12
    ans = 0

    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid, a, x, b):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションでは、実現可能性のチェックを検索ロジックから分離します。 の`can`関数は、問題の物理的解釈全体、つまり需要が時間の経過とともにどのように拡大するか、および需要がどのようにボックスに離散化されるかをエンコードします。 

二分探索では、すべての値が残っているという不変式が維持されます。`lo`以前に観測され、すべての値が以下の場合にのみ実行可能な候補となります。`hi`実行不可能です。 更新ステップでは、単調チェックに基づいてこれらの境界を移動します。 

内側で早めに停止`can`合計が大きくなり、超過する可能性があるため、これは重要です`b`さらなる計算が不要になります。

        total = 0
        for ai in a:
            total += (ai * t + x - 1) // x
            if total > b:
                return False
        return True

        n, x, b = map(int, input().split())
        a = list(map(int, input().split()))

        lo, hi = 0, 10**12
        ans = 0

        while lo <= hi:
            mid = (lo + hi) // 2
            if can(mid, a, x, b):
                ans = mid
                lo = mid + 1
            else:
                hi = mid - 1

        print(ans)

    solve()
    return sys.stdout.getvalue().strip()

# small case
assert run("2 3 10\n2 5\n") == "4"

# all equal rates
assert run("3 2 5\n1 1 1\n") == "2"

# minimal case
assert run("1 1 10\n5\n") == "10"

 ## 特殊なケース

 制限が非常に小さい場合、微妙なエッジ ケースが 1 つ発生します。 たとえば、許可されるボックスの合計が 1 で、最小の建物であってもすでに 1 つ以上のボックスが必要な場合、$t = 0$、正解は 0 です。二分探索では、次のことを想定せずにこれを正しく処理する必要があります。$t = 1$最初は常に実現可能です。 

もう 1 つのケースは、すべてのレートがゼロの場合です。 その状況では、すべての建物は、$t$したがって、実現可能性関数は最大限界まで常に真です。 二分検索は正しく返されるはずです$10^{12}$オーバーフローや早期停止がありません。 

3 番目のケースには大規模な問題が含まれます。$t$小さなパッケージサイズと組み合わせると、次の中間値が得られます。$ai \cdot t$32 ビット整数はオーバーフローする可能性があります。 Python を使用するとこの問題は自然に回避されますが、他の言語では、不正な上限計算を防ぐために 64 ビット演算が必要になります。 

このアルゴリズムは時間の経過による増分更新に依存せず、常に各状態を定義から直接再計算するため、これらのケースはすべて正しく処理されます。$t$。
