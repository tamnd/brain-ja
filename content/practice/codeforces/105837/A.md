 ## 解決策
 ## 問題の理解

 ゴミ箱のコレクションが与えられました。 各ビンは一定数のボールから始まり、最大容量があります。 このプロセスにおける重要な操作は、ビンがいっぱいになるたびに、そのビンがアクティブな検討対象から削除され、その内容全体が共有リザーブに転送されることです。 リザーブ内のボールは後で他のビンに分配することができ、同様にフル容量に達するのに役立ちます。 

根本的な問題は、初期構成から始めて、最初に利用可能なボールまたはリザーブに蓄積されたボールのみを使用してすべてのビンを完全に処理できる方法で、最終的にこのカスケード プロセスをトリガーできるかどうかです。 

システムを理解するもう 1 つの方法は、各ビンには、アクティブ化する前に必要な追加量のボールがあるということです。 アクティブ化されると、その全容量がグローバル プールに提供され、他のビンがアクティブ化しきい値に達することが可能になる場合があります。 現在利用可能な予約を使用して一部のビンを完了できる限り、プロセスは続行されます。 

この制約は、ビンの数が多い場合、ビンをアクティブにする可能なすべての順序の直接シミュレーションが実行できないことを意味します。 活性化シーケンスのすべての順列を探索しようとすると、可能性の数は階乗的に増加しますが、これは数十のビンであっても完全に不可能です。 これは、問題が、考えられるすべての選択肢にわたる分岐を回避できる貪欲な構造または順序ベースの構造を持っている必要があることを直ちに示唆しています。 

微妙な失敗のケースは、複数のビンがいっぱいになりそうになるときに発生しますが、最初に間違ったビンを選択すると、プロセスが停止します。 

たとえば、2 つのビンがあるとします。 

入力:

 3 5

 4 6

 ビン 1 にはさらに 2 個のボールが必要で、ビン 2 にも同様にさらに 2 個のボールが必要ですが、完了するとビン 2 の方が多くの容量が得られます。 誤って大きいビンまたは任意のビンを最初に優先すると、有効なシーケンスが存在するにもかかわらず、予約が不十分で残りのビンを完了できない状態になる可能性があります。 これは、どのビンを最初にアクティブにするかについてのローカルの決定が非常に重要であることを示しています。 

最大の難点は、ビンの完了が単なるローカル イベントではなく、グローバル リソース プールを変更するため、将来の実現可能性に関するすべての決定に影響を与えることです。 

## アプローチ

 ブルートフォースアプローチでは、ビンが完了するすべての可能な順序をシミュレートしようとします。 各ステップで、残りの必要なスペースが現在の予約で満たされるビンを選択し、すべての選択肢を再帰的に調べます。 最悪のケースでは、すべてのビンが最終的に複数の方法で完了できる場合、N ビンにわたる階乗分岐が発生し、O(N!) 状態になります。 無効なパスを削除しても、多くの中間状態が有効なままであり、さらなる分岐につながるため、この最悪の場合の動作は根本的に改善されません。 

重要な構造的洞察は、ビンの唯一の意味のあるプロパティは、ビンをアクティブ化する前にどれだけの追加スペースが必要かであるということです。 正確な配布プロセスを抽象化すると、必要なスペースが小さいビンの方がアクティブ化が厳密に簡単であり、要件が大きいビンを優先して延期すべきではないことがわかります。 

ソリューションのロックを解除する変換は、各ビンを残りの容量として定義される要件値に寄与するものとして扱うことです。 任意のアクティベーション順序について推論する代わりに、この要件に従ってビンを並べ替え、現在実行可能な最も制限されたビンの処理を常に試みます。 これが機能するのは、要件の小さいビンを遅らせて要件の大きいビンを優先するソリューションが存在する場合、プロセスを難しくすることなくいつでも順序を入れ替えることができるためです。 ステートメントで指定された予備引数は、この交換引数を形式化したものです。つまり、より狭いビンを優先しても実現可能性が低下することはなく、実現可能性を改善または維持することしかできません。

これにより、問題は、複数の残りの容量を維持し、それらを昇順に貪欲に消費することになります。

 | 最適 (スペースに貪欲) | O(N log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ビンの残りの必要なスペースを、容量と現在のコンテンツの差として定義します。 この値は、そのビンをアクティブにするのがどれだけ難しいかを表します。 

### ステップ

 1. 各ビンの残りのスペースを、容量から現在のボールを引いたものとして計算します。 これにより、アクティブ化するために必要な追加リソースが正確に取得されます。 
2. すべてのビンを残りのスペースに基づいて降順でない順に並べ替えます。 遅延すると進行がブロックされる可能性が最も高いため、最も制限されたビンを常に最初に検討するという考え方です。 
3. 使用可能な保留球を表す変数を初期化します。 最初は、ビンがまだアクティブ化されていないため、これはゼロです。 
4. ソートされた順序でビンを反復処理します。 各ビンについて、現在の予備容量が必要なスペースをカバーするのに十分であるかどうかを確認します。 そうでない場合、同等以上の要件を持つビンをさらに完了することはできないため、プロセスは停止します。 
5. リザーブが十分な場合は、ビンをアクティブにして、その全容量をリザーブに追加します。 これは、ビンが完成すると、そのすべてのボールが再配布に利用可能になるという事実をモデル化しています。 
6. すべてのビンが処理されるか、ビンがアクティブ化できなくなるまで、このプロセスを続けます。 

### なぜ効果があるのか

 正しさは、アクティベーション順序よりも交換引数に依存します。 より少ない要件を持つビンの前に、より大きな残り要件を持つビンをアクティブ化する有効なシーケンスが存在すると仮定します。 小さいビンの方が満足しやすいため、大きいビンがまだ実行可能な段階では、注文を交換しても利用可能なリザーブが減少することはありません。 したがって、有効なソリューションはどれも、必要なスペースが減少しない順序でビンが処理されるソリューションに変換できます。 これは、何らかの解決策が存在する場合、貪欲な並べ替え順序も成功し、貪欲なプロセスがどこかのビンで失敗した場合、代替の順序付けも成功しない可能性があることを意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    bins = []
    for _ in range(n):
        a, s = map(int, input().split())
        bins.append((s - a, s))
    
    bins.sort()
    
    reserve = 0
    
    for need, cap in bins:
        if reserve < need:
            print("NO")
            return
        reserve += cap
    
    print("YES")

if __name__ == "__main__":
    solve()
```実装は貪欲な順序付けに直接従います。 各ビンは、必要な追加スペースとその容量寄与から構成されるペアで表されます。 並べ替えにより、常に最も厳しい制約が最初に処理されるようになります。 予約チェックは、現在利用可能なリソースでビンをアクティブ化できない無効な遷移を防ぎます。 

よくある実装の落とし穴は、アクティベーション後に追加される貢献が単なる差ではなく全容量であることを忘れることです。 もう 1 つの微妙な点は、代わりに容量でソートするとロジックが壊れてしまうため、ソート キーが正確に残りのスペースであることを確認することです。
