 ## 解決策
 ## 問題の理解

 入力は、出発空港、出発時刻、到着空港、到着時刻を含むフライトのコレクションを記述します。 各フライトに沿って時間は常に進み、乗り継ぎは瞬時に行われるため、時間どおりに空港に到着しても`t`、定刻に出発するフライトにすぐに乗ることができます。`t`またはそれ以降。 

このフライト ネットワークに加えて、出発地から最終目的地までたどる一連のフライト インデックスである 1 つの固定旅程が与えられます。 通常の状況では、この旅程は実現可能です。次のフライトは、前のフライトの到着より早く出発することはありません。 

問題は、旅程に含まれる 1 つのフライトが、搭乗予定のまさにその瞬間にキャンセルされる可能性があることです。 それがポジションで起こった場合`i`、あなたはまだ飛行機の到着空港にいます`i-1`元の到着時刻ではありましたが、完全なフライト システムを使用して、その空港から最終目的地までの可能な最速ルートと時間を再計算する必要があります。 

このタスクは、旅程内のキャンセルの可能性をすべて評価し、当初の計画と比較して到着がどのくらい遅れるかを計算することです。 私たちはそのような最悪の遅延を考慮します。 1回でもキャンセルで目的地に到着できなくなったら、答えは`stranded`。 すべてのルート変更が当初の計画と同じかそれより速い場合、答えは次のようになります。`0`。 

入力サイズは最大 100 万便に達するため、キャンセルごとに最短経路を最初から再計算するアプローチは排除されます。 クエリごとのリニア スキャンでさえ、すでに遅すぎます。 ソリューションでは、飛行システムのグローバル構造を再利用し、グラフ検索の繰り返しを回避する必要があります。 

旅程自体に冗長な選択肢や次善の選択肢が含まれている場合、微妙なエッジ ケースが発生します。 素朴なアプローチでは、唯一可能な継続は残りの旅程のサフィックスであると想定するかもしれませんが、この問題により、キャンセル後にシステム内の任意のフライトに切り替えることが明示的に許可されます。 

もう 1 つの失敗モードは、時間を単純な重みとして扱い、クエリごとにダイクストラを試行することによって発生します。 クエリが 100 万件に達すると、これは不可能になります。 

さらに特殊なケースは、旅程が早めに最終空港に到着するか、複数の等時間経路を経由して最終空港に到着する場合です。 キャンセルが遅れて発生した場合でも、ルート変更により厳密に早く到着する可能性があるため、代替ルートが存在する場合でも答えがゼロになる可能性があります。 

## アプローチ

 直接的なアプローチでは、各キャンセルを個別にシミュレートします。 インデックスごとに`i`旅程では、空港から出発し、フライト後の時間となります。`i-1`目的地までのフライト グラフ全体にわたって最短経路検索を実行します。 フライトには時間の制約があるため、すべてのフライトに対するダイクストラが自然なモデルです。 各実行にかかるおおよその費用`O(n log n)`最悪の場合、これを繰り返すことになる`m`旅程のフライトが導くのは`O(m n log n)`、これは実現可能な限界をはるかに超えています。`n, m`100万まで。 

重要な観察は、すべてのクエリが同じ基礎となる状態空間を共有しているということです。つまり、私たちは常に「指定された時間における指定された空港から目的地への最も早い到着」を解決しているのです。 クエリ間の唯一の違いは開始状態です。 これは、考えられるあらゆるフライトの到着状態について、目的地までの最良の完了とは何かを事前に計算することを示唆しています。 

各フライトを状態として再解釈します。 飛行中の場合`i`の到着空港時刻`a_i`、可能な限り残りの移動距離は、次の時刻までに出発する将来のフライトによってのみ決まります。`a_i`。 知っていたら、フライトごとに`j`、到着状態から開始してキャンセルに応答するまでの最適な完了時間は一定の時間になります。 

これにより、出発時刻によって並べ替えられたフライトに対するリバース ダイナミック プログラミングが可能になります。 フライトを最新のフライトから最も早いフライトの順に処理するため、フライトを評価するときに、後に出発する次のフライトの候補がすべてすでに解決されています。 フライトごとに、同じ空港から出発する互換性のあるすべての後のフライトに移行し、最良の結果が得られます。 

これを効率的に行うために、各空港は、出発時刻をキーにして処理済みの出発便を保存する構造を維持し、「出発時刻 ≥ 現在時刻」に対する範囲最小クエリをサポートしています。

 ## アルゴリズムのチュートリアル

 順序が一貫しているように、すべての時間を分単位で同等の整数に圧縮します。 

次に、各フライトを DP システム内のノードとして扱います。`dp[i]`現在飛行中の場合、最終目的地への可能な限り最も早い到着時刻を表します`i`の到着の様子。 

### ステップ

 1. すべてのタイムスタンプを、固定起点からの分を表す単一の整数に変換します。 これにより、計算中に文字列を解析することなく、高速な比較と並べ替えが可能になります。 
2. 最終目的地を、指定された旅程の最終便の到着空港として特定します。 成功したルートは最終的にこの空港に到達する必要があります。 
3. すべてのフライトを出発時刻の降順に並べ替えます。 この順序により、フライトを処理するときに、後で利用できるすべてのフライトがすでに構造内で処理されていることが保証されます。 
4. 空港ごとに、処理された出発便を保存するデータ構造を維持します。 各エントリは出発時刻によってキー付けされており、最もよく知られている時刻が保存されます。`dp`そのフライトの価値。 
5. 基本ケースを暗黙的に初期化します。最終目的地にすでに到着しているフライトは、`dp[i] = arrival_time[i]`、それ以上の移動が必要ないためです。 
6. 出発時刻の降順にフライトを処理します。 フライトの場合`i`、その値を次のように計算します。 目的地の空港に到着したら、`dp[i]`単に到着時間です。 それ以外の場合は、すべてのフライトの到着空港の構造をクエリします。`j`そのような`departure_time[j] ≥ arrival_time[i]`、そして最小限のものを取ります`dp[j]`。 

これは、次の最適なフライトを選択することを表します。`i`。 
7. 計算後`dp[i]`、フライトを挿入`i`出発空港の構造に、出発時刻によってインデックスが付けられ、早い便が継続して空港を利用できるようにします。 
8. もう一度`dp`値が計算され、各旅程の位置が評価されます`i`。 フライト後の本来の到着時刻`i`旅程シミュレーションからわかります。 フライトの場合`i`キャンセルされた場合は入荷状態からスタートしますので、新規入荷となります。`dp[i]`。 遅延は、`dp[i] - original_time[i]`。 
9. すべての旅程のフライトの最大遅延を計算します。 もしあれば`dp[i]`は無限です、答えは`stranded`。 最大遅延が負またはゼロの場合、出力`0`。 

### なぜ効果があるのか

 重要な不変条件は、出発時刻の降順でフライトを処理する場合、ルート変更で合法的にそのフライトを追跡できるすべてのフライトがすでに完全に評価され、空港構造に保存されていることです。 したがって、クエリ時の構造では、現在の状態からのあらゆる継続が表現されます。 これにより、`dp[i]`旅程の一貫性のある継続だけでなく、その状態から始まるグローバルに最適な完了を常に反映します。 

すべての有効なリルートはそのような遷移のシーケンスであり、すべての遷移は利用可能になったときに正確に考慮されるため、最適なパスが見逃されることはありません。

def parse_time(s):
    d = int(s[:-9])
    hh = int(s[-8:-6])
    mm = int(s[-5:])
    return d * 24 * 60 + hh * 60 + mm

class SegTree:
    def __init__(self, arr):
        self.n = 1
        while self.n < len(arr):
            self.n <<= 1
        self.seg = [INF] * (2 * self.n)
        self.arr = arr

    def update(self, i, val):
        i += self.n
        self.seg[i] = min(self.seg[i], val)
        i //= 2
        while i:
            self.seg[i] = min(self.seg[2 * i], self.seg[2 * i + 1])
            i //= 2

    def query(self, l):
        # minimum on [l, n)
        l += self.n
        r = self.n + self.n
        res = INF
        while l < r:
            if l & 1:
                res = min(res, self.seg[l])
                l += 1
            if r & 1:
                r -= 1
                res = min(res, self.seg[r])
            l //= 2
            r //= 2
        return res

 ## 特殊なケース

 重要なエッジケースは、旅程の最初のフライトでキャンセルが発生した場合に発生します。 この場合、開始状態は元の出発空港と時刻です。 アルゴリズムはこれを他の飛行状態と同様に扱います。`dp[i]`まさにその時点からの到達可能性をすでにエンコードしています。 DP は旅程の位置には依存せず、フライトの到着状態のみに依存するため、結果は正しいです。 

別の特殊なケースは、複数のフライトが同じ空港から同じ出発時間を共有する場合に発生します。 遷移は「出発時刻 ≥ 現在時刻」に依存するため、すべての遷移が同時に考慮され、サフィックス クエリによってスキップされるものがないことが保証されます。 

最後のエッジケースは、中間便から目的地の空港にすぐに到着できる場合です。 そのような状況では、`dp[i]`アルゴリズムは常に可能な最小の完了時間を選択するため、たとえより長い代替ルートが存在する場合でも、計算された遅延はゼロになります。
