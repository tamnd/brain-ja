 ## 解決策
 ## 問題の理解

 私たちは、各乗客が番号付きの旅行カードを使用するタップイン タップアウト交通システムをシミュレートしています。 すべてのイベントは桟橋とカード ID を記録し、イベントは時系列に到着します。 各カードは独立して動作するため、すべてのイベントを処理した後、各カードに蓄積された合計料金を計算する必要があります。 

トリップは、同じカードの 2 つの連続するイベントをペアにすることによって形成されます。最初のイベントは開始 (タップイン) で、同じカードの次のイベントは終了 (タップアウト) です。 コストは、これら 2 つの橋脚の関係によって異なります。 開始ピアと終了ピアが異なる場合、コストはそれらのインデックスの絶対的な差になります。 それらが同じ桟橋である場合、またはカードが旅行を開始しても終了しない場合、コストは 100 の固定ペナルティです。 

主な課題は、イベントが多くのカードにわたってインターリーブされるため、各カードが独自の「現在オープンしているトリップ」状態を維持することです。 最大 100,000 件のイベントを処理する必要があるため、グローバルにスキャンまたは照合しようとするアプローチは遅すぎます。 カードごとの状態を維持し、イベントごとに一定時間で回答を更新する必要があります。 

微妙な失敗例は、カードの最後に比類のないタップインがある場合に発生します。 たとえば、カードに 1 つのイベントがある場合、`(pier 3, card 7)`それ以上のイベントがない場合、正しいコストは 100 です。完全なペアに対してのみ課金する単純な解決策では、誤って 0 が出力されます。もう 1 つの特殊なケースは、グローバルに変更が適用されずにタップが繰り返されることです。 たとえば、カードは桟橋 1 でタップインし、桟橋 2 でタップアウトし、その後再び桟橋 2 でタップインし、桟橋 2 でタップアウトすることができます。同じ桟橋での移動には常にペナルティが課されるため、最後の移動は距離ゼロの移動に「見える」場合でも 100 コストがかかります。 

この制約は、イベントごとに O(1) の処理が必要であることを意味します。 最大 100,000 イベントの場合、O(k log k) であっても許容されますが、その必要はありません。 n の小さな境界 (橋脚の数は最大 50) は複雑さとは無関係で、距離の座標空間を定義するだけです。 

## アプローチ

 強引な解釈では、カードごとにすべてのイベントを保存し、タップアウトが発生するたびに、繰り返し逆方向にスキャンして、以前の一致しないタップインを見つけます。 各トリップは 2 つのイベントのペアによって定義されるため、これは論理的に機能しますが、単純に実装すると非効率になります。各イベントがそのカードの以前のすべてのイベントのスキャンをトリガーする可能性があり、すべてのイベントが 1 つのカードに属し、オープンとクローズが交互に行われる場合、最悪のケースでは O(k^2) になります。 

重要な点は、各カードが記憶する必要があるのは 1 つの状態だけであるということです。つまり、現在オープンなトリップがあるかどうか、また、オープンしている場合はその開始地点の桟橋です。 タップアウトが発生すると、すぐにコストを解決して状態をクリアします。 旅行が開いていないときに新しいタップインが発生した場合は、単にそれを保存します。 

これにより、問題はイベント ストリームを通過する 1 回のパスに軽減され、アクティブな旅行用にサイズ m の辞書または配列が維持され、累積コスト用に別の配列が維持されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (イベントごとのスキャン履歴) | O(k²) | O(k) | 遅すぎる |
 | 最適 (カードごとの状態) | O(k) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 カード ID によってインデックス付けされた 2 つの配列を維持します。 1 つは各カードの現在のオープン ピアを保存し、もう 1 つは累積コストを保存します。 

1. 配列を初期化する`open_pier`「アクティブな旅行はありません」を意味するセンチネル値と配列を含むサイズ m`cost`サイズ m のゼロで埋められたもの。 センチネルにより、アクティブな状態と非アクティブな状態を曖昧さなく区別できるようになります。 
2. 各イベントの処理`(p, c)`順番に。 時系列順により、ペアリングがカードごとに順番に行われることが保証されます。 
3. カードの場合`c`アクティブな旅行や店舗がありません`p`で`open_pier[c]`。 これは旅の始まりを表します。 旅行はまだ完了していないため、費用は発生しません。 
4. カードの場合`c`に始まるアクティブな旅行がすでにあります`open_pier[c]`, 旅費は次のように計算します。 もし`p == open_pier[c]`に 100 を加えます`cost[c]`。 それ以外の場合は追加します`abs(p - open_pier[c])`。 
5. 完了したトリップを処理した後、リセットします`open_pier[c]`センチネル値に戻り、カードが新しい旅行の準備ができていることを示します。 
6. すべてのイベントが処理された後、センチネル以外のカードが残っているカードは、`open_pier`値は不完全な旅行を表します。 そのようなカード1枚につき、コストに100を加えます。 

ステップ 6 の背後にある理由は、システムは、不完全な移動がどこから開始されたかに関係なく、常にペナルティが課されると定義しているためです。 

### なぜ効果があるのか

 各カードの一連のイベントは、おそらく末尾の開始を除いて、(開始、終了) の連続する素のペアに自然に分割されます。 アルゴリズムは、このペアリングを到着順に貪欲に強制します。これは、システムの唯一の有効な解釈と一致します。 カードは重複したトリップを持つことができないため、現在のコンテキストを完全に表現するには、アクティブな開始状態を 1 つだけ保存するだけで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    
    open_pier = [-1] * (m + 1)
    cost = [0] * (m + 1)
    
    for _ in range(k):
        p, c = map(int, input().split())
        
        if open_pier[c] == -1:
            open_pier[c] = p
        else:
            start = open_pier[c]
            if p == start:
                cost[c] += 100
            else:
                cost[c] += abs(p - start)
            open_pier[c] = -1
    
    for c in range(1, m + 1):
        if open_pier[c] != -1:
            cost[c] += 100
    
    print(*cost[1:])

if __name__ == "__main__":
    solve()
```このソリューションでは、カード ID によってインデックス付けされた 2 つの配列を使用します。`open_pier`カードに現在未完了の旅程があるかどうかを追跡し、その開始地点を保存します。 そのカードに 2 番目のイベントが到着すると、すぐにコストを計算し、状態をリセットします。 すべてのイベントを処理した後、最終スイープを実行して、未完了の旅行を請求します。 

よくある実装上の間違いは、最後のスイープを忘れることで、タップアウトしないカードのチャージが過少になってしまいます。 もう 1 つの微妙な問題は、状態のリセットが誤って早すぎるか遅すぎることです。 次のイベントが新しい旅行として扱われるように、コストを計算した直後にリセットを行う必要があります。

```私たちは追跡します`open_pier`そして`cost`ステップごとに。 

| イベント | カード | アクション | オープンピアの状態 | コストの状態 |
 | --- | --- | --- | --- | --- |
 | (1,1) | 1 | 開始 | [1,-1,-1] | [0,0,0] |
 | (1,2) | 2 | 開始 | [1,1,-1] | [0,0,0] |
 | (1,2) | 2 | 同じ桟橋の端 → +100 | [1,-1,-1] | [0,100,0] |
 | (3,1) | 1 | 終了差分 → +2 | [-1、-1、-1] | [2,100,0] |
 | (2,3) | 3 | 開始 | [-1、-1、2] | [2,100,0] |

最終コスト:`[2, 100, 100]`。 

このトレースは、ペアリングがカードごとに厳密にローカルであり、未完了のトリップがストリーム終了後にのみ処理されることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(k) | 各イベントは O(1) 更新で 1 回処理されます。 
| スペース | O(m) | カードごとに 1 つの状態と 1 つのコストを保存します。 

この制約では最大 100,000 のイベントとカードが許可されるため、線形処理は容易に制限内に収まります。 サイズ m の配列を 2 つだけ保持するため、メモリ使用量は最小限です。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    n, m, k = map(int, sys.stdin.readline().split())
    
    open_pier = [-1] * (m + 1)
    cost = [0] * (m + 1)
    
    for _ in range(k):
        p, c = map(int, sys.stdin.readline().split())
        if open_pier[c] == -1:
            open_pier[c] = p
        else:
            start = open_pier[c]
            if p == start:
                cost[c] += 100
            else:
                cost[c] += abs(p - start)
            open_pier[c] = -1
    
    for c in range(1, m + 1):
        if open_pier[c] != -1:
            cost[c] += 100
    
    return " ".join(map(str, cost[1:]))

# provided sample
assert run("3 3 5\n1 1\n1 2\n1 2\n3 1\n2 3\n") == "2 100 100"

# single card simple pair
assert run("2 1 2\n1 1\n3 1\n") == "2"

# same-pier penalty
assert run("2 1 2\n1 1\n1 1\n") == "100"

# unmatched open trip
assert run("5 2 1\n3 2\n") == "0 100"

# alternating multiple cards
assert run("3 2 4\n1 1\n2 2\n3 1\n3 2\n") == "3 3"

 ## 特殊なケース

 エッジケースの 1 つは、決してタップアウトされないカードです。 たとえば、次のように入力します。```
2 1 1
1 1
```アルゴリズムストア`open_pier[1] = 1`。 すべてのイベントを処理した後、最後のスイープで 100 が加算され、出力が生成されます。`100`。 このステップを行わないと、完成したペアが形成されないため、結果は誤って 0 のままになります。 

もう 1 つのケースは、同じ桟橋を繰り返し航行する場合です。 例えば：```
2 1 2
1 1
1 1
```最初のイベントで旅が始まります。 2 番目のイベントによって同じ桟橋が閉鎖され、固定ペナルティ 100 がトリガーされます。リセットにより、別のイベントが続いた場合でも、過去の状態と誤って結合するのではなく、新しい旅行が開始されることが保証されます。 

最後の微妙なケースは、複数のカードをインターリーブすることです。```
3 2 4
1 1
2 2
3 1
3 2
```カード 1 はコスト 2 の 1 から 3 への旅行を形成します。カード 2 はコスト 1 の 2 から 3 への旅行を形成します。`open_pier`カードごとに、状態間の相互汚染がないことが保証されます。
