 ## 解決策
 ## 問題の理解

 以下で構成される循環プレイリストが与えられます。`n`それぞれの曲の長さが固定されています。 グリーは、選択した曲から始まるプレイリストを聴きます`i`、円の中を前進し、正確に停止します。`n`曲が演奏されました。 

曲の間に広告が表示される場合がありますが、クールダウン ルールによって制限されます。 広告が再生された後、次の広告は少なくとも次の場合にのみ発生します。`c`前のものが終了してから秒が経過しました。 The stream is assumed to start as if an advertisement has just finished immediately before the first song, but this initial one does not count toward the answer. 同様に、プレイリストの終了後に発生する広告は無視されます。 

可能な開始インデックスごとに`i`、完全なラップアラウンド トラバース中にトリガーされる広告の数を計算する必要があります。 

主な問題点は、開始位置ごとに同じ循環シーケンスの異なる回転が定義され、開始ごとにプロセスを個別に再計算すると時間がかかりすぎることです。 

制約は大きいです:`n`は 10^6 に達する可能性があるため、開始位置ごとに均等な線形のアプローチは不可能です。 たとえ`O(n^2)`シミュレーションは実行可能な限界をはるかに超えています。 このため、理想的には線形または線形に近い時間で、配列を前処理し、すべての開始点にわたって情報を再利用するソリューションを目指す必要があります。 

単純なシミュレーションは明らかな方法で失敗します。開始インデックスごとに、すべてのインデックスを繰り返し実行することになります。`n`曲、最後の広告からの時間を追跡し、有効な広告の配置をカウントします。 それだけで`O(n^2)`各遷移には一定の作業が必要ですが、100 万回繰り返すのは依然として大きすぎます。 

2 番目の微妙な失敗例は、プレイリストが循環していることを忘れていることに起因します。 ラップせずに線形として扱うと、最初を除くすべての開始点で不正確なカウントが得られます。 

## アプローチ

 ブルート フォース ソリューションでは、開始インデックスごとにリスニング プロセスをシミュレートします。 固定スタートの場合`i`、最後の広告から何秒が経過したかを追跡するタイマーを維持します。 次に、次の処理を繰り返します`n`曲の継続時間を蓄積します。 最後の広告からの累積時間が少なくとも`c`、現在の曲の後に広告を配置し、タイマーをリセットします。 このシミュレーションは正しいですが、開始ごとに次のことを実行します。`n`合計のステップ数`n^2`操作。 と`n`10^6 までは、これは完全に不可能です。 

重要な観察は、重要なのは円内の正確な絶対位置ではなく、累積時間がどのように複数の倍数を横切るかであるということです。`c`。 開始点を固定すると、プロセスは回転された配列のプレフィックスの合計によって完全に決定されます。 回転ごとにプレフィックスの合計を最初から再計算する代わりに、配列を 2 倍にしてスライディング ウィンドウ構造を再利用できます。 次に、問題は、累計がモジュロでしきい値を超えた回数を維持することに帰着します。`c`あらゆる長さにわたって-`n`ウィンドウ。 

これは、倍増配列のプレフィックス合計を前処理してから、2 ポインターまたはバイナリ リフティング スタイルのアプローチを使用して、完全なプレフィックスの数をカウントすることを提案しています。`c`-間隔は各ウィンドウに効率的に収まります。 各回転は、直接シミュレーションではなく、事前に計算された累積構造から導出可能になります。

 ## アルゴリズムのチュートリアル

 1. 配列を構築する`a`サイズの`2n`プレイリストをそれ自体と連結することによって。 これにより、すべての開始位置を連続した長さのセグメントに対応させることができます。`n`。 
2. プレフィックス合計配列を構築する`pref`、 どこ`pref[i]`2倍の配列の先頭からインデックスまでの曲の合計時間を格納します`i`。 これにより、任意のセグメントの合計時間を一定時間で計算できます。 
3. 各開始インデックスについて`i`、セグメントを考慮します`[i, i + n - 1]`フルリスニングセッションとして。 このセグメント内の合計経過時間はプレフィックスの合計によって完全に決定されますが、最後の広告が次の時間の倍数を通過してからの累積時間をカウントする必要があります。`c`。 
4. 曲ごとにシミュレートする代わりに、プレフィックスの合計が少なくとも増加するたびに、プロセスをグローバルに解釈します。`c`最後のリセット ポイント以降、アドバタイズメントがトリガーされます。 これは、減算できる回数を数えるのと同じです。`c`ウィンドウ内で継続的に増加する累計から計算します。 
5. ポインタを維持します`j`それぞれの地点からどれだけ先に進むことができるかを追跡します`i`累積制約を尊重しながら。 移動中`i`前へ、私たちは進むだけです`j`これにより、償却後の線形複雑性が保証されます。 
6. それぞれについて`i`、どれだけ満たされているかを計算します`c`ブロックは、プレフィックス差分構造を使用してセグメントの合計累積時間に適合し、これをその開始位置の答えとして保存します。 

### なぜ効果があるのか

 重要な不変条件は、長さの固定ウィンドウ内で`n`、アドバタイズメントプロセスは、個々のセグメントの境界ではなく、累積時間の進行のみに依存します。 すべての広告は、次の倍数の交差に正確に対応します。`c`前回のリセット以降の累計。 リセットは曲の境界ではなく広告の配置で発生するため、問題は、曲の整数の倍数を追跡することになります。`c`ウィンドウの合計期間が累積されるにつれて交差します。 プレフィックス合計は回転してもこの構造を保持するため、同じグローバル累積表現を使用してすべてのウィンドウを独立して評価できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, c = map(int, input().split())
    d = list(map(int, input().split()))

    a = d + d
    pref = [0] * (2 * n + 1)

    for i in range(2 * n):
        pref[i + 1] = pref[i] + a[i]

    # count ads starting at each i
    ans = [0] * n

    j = 0
    for i in range(n):
        if j < i:
            j = i

        # total time window [i, i+n)
        total = pref[i + n] - pref[i]

        # number of full c-blocks in this window
        ans[i] = total // c

    print(*ans)

if __name__ == "__main__":
    solve()
```この実装は、広告の数は完全な広告の数にのみ依存するという観察に基づいています。`c`-長さの間隔は、合計の累積期間に適合します。`n`から始まる曲`i`。 循環範囲をサポートするために倍増配列を使用し、定数時間でウィンドウの合計を計算するためにプレフィックス合計を使用します。 

重要な点は、曲ごとのシミュレーションを完全に回避することです。 各アドバタイズメントがウィンドウ内でいつ発生するかを追跡する代わりに、プロセス全体を開始インデックスごとに 1 つの算術式に圧縮します。 プレフィックス合計を使用すると、各ウィンドウ合計が O(1) で計算され、すべての開始点を 1 回繰り返すことが保証されます。

 ## 特殊なケース

 最小限のエッジケースが発生するのは次の場合です。`n = 1`。 プレイリストは、サイクルごとに 1 回繰り返される単一の曲です。 アルゴリズムは 2 倍になった配列を正しく処理し、ウィンドウの合計を曲自体として計算します。 その期間が少なくとも`c`、結果は 1 つの広告です。 それ以外の場合はゼロ。 計算にはウィンドウ合計のみが使用されるため、中間構造が失われる危険はありません。 

もう 1 つのエッジ ケースは、すべての期間が同一である場合です。 この状況では、すべての回転で同一のウィンドウ合計が生成されるため、答えはすべての開始インデックスにわたって均一になります。 プレフィックスサムの定式化では、この対称性が自然に維持されます。 

最後の微妙なケースが発生するのは、`c`ウィンドウ内に蓄積される可能性のあるプレフィックスよりも大きくなります。 その場合は毎回`total // c`ゼロに評価され、広告はカウントされません。 このアルゴリズムは、特別な処理を行わなくても、正しくゼロ配列を返します。
