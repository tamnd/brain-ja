 ## 解決策
 ## 問題の理解

 私たちには、DNA 文字列の隠されたデータベースへのバイナリ インターフェイスが与えられています。 私たちができる唯一のことは、クエリ文字列の選択した部分文字列がそのデータベースのどこかに出現するかどうかをクエリすることです。 保存されている DNA 鎖の部分文字列として一度でも出現する場合、答えは「存在」、そうでない場合は「不在」になります。 重要な構造特性は、文字列がデータベースに存在する場合、そのすべての部分文字列も存在するとみなされることです。 

私たちのタスクは、長さ n の単一のクエリ文字列を取得し、すべてのセグメントが「新しい」、つまりデータベースに表示されないように、それをできるだけ多くの連続したセグメントに分割することです。 これらのセグメントは互いに素であり、文字列全体を順番にカバーする必要があります。 このようなセグメントの最大数が必要です。 

相互作用の制約は厳しく、最大 2n 個の部分文字列クエリを実行できるため、O(n²) 個の部分文字列をすべて探索することなく、非常に制御された方法で「存在する部分文字列と存在しない部分文字列」のグローバル構造を抽出する必要があります。 

重要な制約の意味は、n が 10⁴ まで大きくなり得るため、すべての部分文字列をチェックしたり、完全な部分文字列テーブルを構築したりするアプローチは不可能であるということです。 O(n²) クエリでもすでに n 倍大きすぎるため、ソリューションでは慎重に O(n) クエリのみを使用する必要があります。 

たとえ小さな部分が存在しなくても、長い部分文字列が存在する場合、微妙なエッジケースが発生します。 「現在」は部分文字列までは下向きに遺伝しますが、超文字列までは上向きに遺伝しないため、順方向の単調性を仮定することはできません。 適切なプレフィックスがすべて存在するにもかかわらず、文字列が存在しないことも、その逆の場合も同様です。 例えば、「ABC」があれば「AB」「BC」も存在しますが、「A」「B」「D」がそれぞれ独立して存在していても「ABD」が存在しない場合があります。 これにより、各セグメントを明示的に検証しない限り、貪欲な部分文字列の分割が妨げられます。 

重要な問題は、セグメントの有効性が、ローカルの文字構造ではなく、その正確な部分文字列がどこかに存在するかどうかによって決まることです。 

## アプローチ

 素朴なアプローチは、文字列の考えられるすべてのセグメントを考慮し、各セグメントがデータベースに存在しないかどうかをテストすることです。 セグメントごとに、部分文字列クエリを使用してすべてのセグメントを検証する必要があります。 パーティション ポイントを修正したとしても、セグメントの検証には少なくとも 1 つのクエリが必要であり、パーティションの数は指数関数的に増加します。 これはすぐに実行不可能になります。 

より構造化されたブルートフォースの改善は、セグメントを左から右に貪欲に拡張し、セグメントがなくなったときに停止することです。 開始位置 i ごとに、部分文字列 i..j がなくなるまで j を増やしていき、そこでカットします。 ただし、最悪の場合、開始ごとに O(n) クエリが必要になる可能性があり、全体で O(n²) クエリが発生し、2n 制限に違反します。 

重要な点は、実際には、存在しない部分文字列をすべて知る必要はないということです。 位置ごとに、セグメントを有効なままにしながらどこまで延長できるかを知る必要があるだけで、カット数を最大化したいと考えています。 データベースは部分文字列の下で閉じられているため、「存在する」部分文字列のセットは、部分文字列が存在しないと、拡張子も存在しないか、その正確な位置に無関係になるという構造を形成しますが、これだけでは十分ではありません。 本当のトリックは、次の意味で単調性を利用することです。固定された左端点 i の場合、j が増加するにつれて、部分文字列 i..j は、データベース内で最も長く一致するプレフィックスを渡した場合にのみ存在から不在に移行できます。 これによりバイナリ検索や増分拡張が可能になりますが、合計クエリ数は 2n 以内に抑える必要があります。

これは、線形償却戦略につながります。つまり、現在のセグメント開始点のポインターを維持し、「存在」したままの状態で正しい境界を拡張します。 1 文字分伸びると部分文字列が「存在しなくなる」ので、その文字の前のセグメントを切り取ります。 これにより、各位置が最大 2 つのクエリで使用されることが保証されます。1 つは拡張のテストに、もう 1 つは境界動作の確認に使用されます。 

基本的には左から右にスキャンし、有効なセグメントを最大限に維持します。

 ## アルゴリズムのチュートリアル

 ポインタを維持します`i`現在のセグメントの開始をマークします。 2 番目のポインタを拡張しようとします`j`可能な限り、部分文字列が`i..j`データベースに存在したままになります。 それがなくなった瞬間にセグメントを終了します。 

1.初期化`i = 0`そして`answer = 0`。 私たちは文字列の先頭にいますが、まだセグメントを形成していません。 
2. ポジションごとに`i`、 セット`j = i + 1`そして最初に単一文字の部分文字列かどうかをクエリします。`i..i+1`が存在します。 これにより、次から始まるセグメントがあるかどうかのベースラインが得られます。`i`全然延長できます。 長さ 1 の部分文字列さえ存在しない場合、セグメントは長さ 1 でなければなりません。 
3. 拡張する`j`右に、部分文字列`i..j`存在したままです。 Each extension is checked with a single query. 最初はやめておきます`j`where the substring becomes absent.
 4. 最初の存在しない拡張子が見つかると、有効なセグメントの最大長が次のとおりであることがわかります。`i`は`i..j-1`。 インクリメントします`answer`1とセットで`i = j`。 で始まる長いセグメントは存在しないため、これは安全です。`i`は無効なので、セグメント数を最大化するにはここをカットする必要があります。 
5. までプロセスを繰り返します。`i = n`。 

重要な制約は、`j`失敗したクエリまたは成功したクエリに 1 回だけ対応します。 各文字境界は最大 2 つのクエリ (存在の確認と不在の検出の 1 つ) に関与し、クエリの合計は 2n 以内に抑えられます。 

### なぜ効果があるのか

 正確さは、各位置における貪欲な最適な下部構造に依存します。`i`、無効な内線境界を強制する最短のプレフィックスを選択します。 最初の「存在しない」遷移を超えてセグメントを延長しても、そのセグメントを再び有効にすることはできないため、すぐに切断しても、後で達成できるセグメントの総数が減少することはありません。 データベース プロパティにより、部分文字列が存在しなくなると、それ以降の拡張はすべてその開始位置とは無関係になることが保証されるため、貪欲なカットは局所的に最適であり、グローバルに一貫性があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def ask(i, j):
    print("?", i, j)
    sys.stdout.flush()
    return input().strip()

def main():
    n = int(input())
    
    i = 0
    ans = 0
    
    while i < n:
        j = i + 1
        
        # try to extend at least one character if possible
        if j > n:
            ans += 1
            break
        
        # if single char already absent, cut immediately
        res = ask(i, j)
        if res == "absent":
            ans += 1
            i += 1
            continue
        
        # extend while possible
        while j < n:
            res = ask(i, j + 1)
            if res == "absent":
                break
            j += 1
        
        ans += 1
        i = j + 1
    
    print("!", ans)
    sys.stdout.flush()

if __name__ == "__main__":
    main()
```コードは貪欲スキャン戦略に従っています。 機能`ask(i, j)`インタラクティブなクエリをラップし、リクエストごとに確実にフラッシュします。 メインループは左側の境界を維持します`i`そして正しい境界線を押し広げようとします`j`部分文字列が存在する間、可能な限り。 

各セグメントの最初のクエリでは、最小限の拡張子でも有効かどうかがチェックされます。 これにより、最適なセグメントの長さが 1 に強制される場合に不必要なスキャンが防止されます。内側のループはインクリメントされます。`j`そして常にテストします`i..j+1`、最初の障害点を確実に検出します。 障害が発生すると、セグメントは次の時点で終了します。`j`。 

一般的な実装の落とし穴は、off-by-one の処理です。`j`。 クエリはハーフオープンインデックスを使用します`[i, j)`したがって、すべての拡張子は、「不在」を検出した瞬間に注意深く調整する必要があります。

 ## 特殊なケース

 長さ 1 の文字列の場合、アルゴリズムはただちに単一の部分文字列をクエリし、それをスタンドアロン セグメントとして切り取るか、それが唯一の有効なセグメントであることを確認します。 ポインタが誤って移動する可能性はありません。`i`そして`j`一致する。 

すべての部分文字列が存在しない場合、長さ 1 のすべてのクエリは「存在しない」を返すため、各文字はすぐに切り取られます。 アルゴリズムは n 個のセグメントを生成し、反復ごとに増分します。`i`正確に 1 だけ増やすことで、無限ループやインデックスのスキップを防ぎます。 

すべての部分文字列が存在する場合、拡張ループは文字列の終わりまで実行され、セグメントが 1 つだけ生成されます。 「欠席」の応答は出ないので、`j`到達する`n`そして最後のカットは終了境界で発生し、文字列全体を 1 つのセグメントでカバーします。
