 ## 解決策
 ## 問題の理解

 以下から構成される固定長プログラムの入力を完了しようとしています。`c`文字。 各文字の入力にはちょうど 1 単位の時間がかかります。 問題は、すべての文字を入力した後、確率でマシンがクラッシュする可能性があることです。`p`。 クラッシュが発生すると、最後のセーブポイント以降のすべての進行状況が失われ、時間を費やす必要があります。`r`時間単位で回復し、その後最後に保存された状態から再開します。 

いつでも保存操作を実行できます。 コストの削減`t`時間単位を設定し、後でクラッシュが発生した場合でも、最初からのすべての進行状況を失うのではなく、保存された位置から再開することを保証します。 最後の文字も保存する必要があります。つまり、最適な戦略では、完成したソリューションが最後に確実に保護される必要があります。 

タスクは、すべての入力を完了するまでに予想される合計時間を計算することです。`c`これには、入力時間、保存時間、クラッシュによる予想される回復時間が含まれます。 ランダム性はクラッシュによってのみ発生し、それ以外はすべて決定的です。 

制約によって次のことが明らかになります。`c`最大でも 2000 ですが、`t`そして`r`最大 10^9 までの非常に大きなサイズになる可能性があります。 これは、衝突シーケンスを直接シミュレートしたり、詳細な履歴にわたって戦略を列挙したりすることはできないことを直ちに示唆しています。 合理的に利用できる唯一の構造は、プロセスの状態が履歴全体ではなく、最後の保存以降に入力した距離のみに依存するということです。 

素朴な解釈では、セーブ ポイントのあらゆる可能なスケジュールを考慮し、クラッシュ時の予想コストを計算することになります。 位置のすべてのサブセットがセーブ ポイントになる可能性があるため、これは本質的に指数関数的です。 小さいものでも`c`、これは手に負えなくなります。 

より微妙な障害モードは、「最後の保存から再開」ルールを無視することで発生します。 たとえば、次の場合`c = 3`、`t = 5`、`r = 2`、 そして`p = 0.5`、決して保存しない単純な戦略は魅力的に見えるかもしれませんが、ファーストクラッシュの後はすべての進行状況が失われ、再入力される文字の予想数が大幅に増加します。 逆に、すべての文字の後に保存すると、再入力のコストはなくなりますが、決定論的なオーバーヘッドが大きくなり、最適な解決策はこれらの両極端の間にあります。 

もう 1 つのエッジケースは次のような場合です`p`この状況では、ほとんどの場合、進行状況がすぐに失われるため、早めに節約しないと、予想されるコストが爆発的に増加します。 一方、次のようなときは、`p`が 0 に近い場合、保存はほとんど無駄なオーバーヘッドです。 

## アプローチ

 ブルートフォース戦略では、セーブを配置するポジションのサブセットを選択しようとします。 一連の保存位置を修正するとします。 次に、各セグメントが独立した「試行」のように動作し、クラッシュすることなく成功するまで繰り返されるため、セグメントごとに予想時間を計算できます。 セグメントの予想される再試行回数は、セグメントの長さと、クラッシュせずに存続する確率によって異なります。 ただし、セーブ ポイントの考えられるすべてのサブセットを列挙することは、次の点で指数関数的になります。`c`、 2^(c−1) 個の可能な選択肢があるためです。 

重要な観察は、最適な戦略は常に構造化された方法で保存されるということです。つまり、一度その位置で保存すると決めたら、`i`、残りの決定は以下にのみ依存します。`i`、完全な履歴ではありません。 これにより、プレフィックスに対する自然な動的プログラミングの定式化が作成されます。 州は「ポジションからフィニッシュするのに最も期待されるコスト」`i`現在セーブポイントにいるとき」で十分です。 

位置から`i`、次の保存位置を選択してみます`j > i`。 から文字を入力します`i+1`に`j`、そのセグメント中にクラッシュする可能性があります。 このセグメントを正常に完了するために予想されるコストは、幾何学的繰り返しによって異なります。各試行にはコストがかかります。`(j - i)`入力時間に失敗した場合に予想される回復時間を加え、確率で成功するまで繰り返します。`(1 - p)^(j - i)`。 

したがって、各遷移はセグメントの長さにのみ依存するコストに寄与し、節約コストを追加します。`j`そして再帰的に続行します。 これにより、セグメント エンドポイントに対する O(c^2) 動的プログラミングが生成されます。

 ## アルゴリズムのチュートリアル

 動的プログラミング配列を定義します`dp[i]`位置から始まる文字の入力を完了するのに必要な最小予想時間として`i`、現在、位置で安全に保存された状態にあると仮定します。`i`。 

事前に計算された電力配列も使用します`pow_bad[k] = p^k`そして`pow_good[k] = (1 - p)^k`、セグメントの生存確率はこれらの値に依存するためです。 

1.初期化する`dp[c] = 0`すべての文字を入力してしまえば、それ以上時間はかかりません。 
2. ポジションごとに`i`から`c-1`まで`0`、次の保存位置を選択してみます`j`どこ`i < j ≤ c`。 

アイデアは、入力するということです`len = j - i`1回の試行で文字数を増やすことができます。 そのセグメントでクラッシュせずに成功する確率は次のとおりです。`(1 - p)^len`。 失敗した場合はセグメント内のどこかにクラッシュし、復旧コストを支払います`r`から再試行してください`i`。 

成功するまでの予想試行回数は次のとおりです。`1 / (1 - (1 - p)^len)`。 試行が失敗するたびに、予想される内部クラッシュ コストと回復コストがかかりますが、それを直接拡張する代わりに、標準的な更新引数を使用します。 

一定の長さのセグメントを完了するために予想されるコスト`len`は:

 予想される試行回数に試行あたりのコストを乗算したもので、試行の失敗は予想される部分的な型付けと回復に寄与し、試行の成功は回復なしの完全な型付けに寄与します。 

これは、のみに依存する閉じた形式の予想セグメントコストに単純化されます。`len`、`p`、 そして`r`。 
3. 各候補者について`j`、次のように計算します。 

セグメントを完了するためのコスト`[i+1, j]`プラス節約コスト`t`、プラス`dp[j]`。 

すべてにおいて最低限のものを採用します`j`。 
4. アウトプットする`dp[0]`。 

重要な計算ステップは、セグメントの予想コストを計算することです。 クラッシュをシミュレートする代わりに、セグメントを幾何学的プロセスとして扱い、各試行は確率的に独立して成功します。`(1 - p)^len`。 それぞれの障害により、セグメント内の予想されるクラッシュ位置と復旧コストに比例して、予想される作業損失が発生します。`r`。 

### なぜ効果があるのか

 正確性は、セーブ ポイントが固定されると、セグメント内のすべてのランダム性が前のセグメントから独立しているという事実に依存します。 すべての戦略は、保存間で一連の独立したセグメントに分解されます。 したがって、最適な戦略とはセグメント境界を最適に選択することであり、DP はすべてのプレフィックスが拡張される前に最適に解決されることを保証します。 すべてのコストは独立したセグメント間で加算されるため、将来の決定によって以前は最適だったサフィックスを改善することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    c, t, r = map(int, input().split())
    p = float(input().strip())
    
    q = 1.0 - p
    
    # precompute powers
    qpow = [1.0] * (c + 1)
    for i in range(1, c + 1):
        qpow[i] = qpow[i - 1] * q
    
    # expected time spent typing a segment once (including crashes)
    # expected successful typing attempts structure:
    # success prob = q^len
    # expected attempts = 1 / (q^len)
    # but we must include failures properly:
    # each failed attempt expected crash position = len/2
    # (uniform over positions in expectation due to memoryless step-by-step process)
    
    def seg_cost(length):
        if length == 0:
            return 0.0
        
        success = qpow[length]
        fail = 1.0 - success
        
        # expected typing per full attempt (conditional step process approximation)
        # expected work per attempt = sum over positions i of q^(i-1)*p*(i + r)
        # normalized over cycles leads to:
        # we compute expected cost per success cycle:
        
        # expected time until success (geometric on attempts)
        exp_attempts = 1.0 / success
        
        # expected cost of a failed attempt:
        # expected crash position in [1..len]
        expected_crash_pos = 0.0
        prob_alive = 1.0
        for i in range(1, length + 1):
            expected_crash_pos += prob_alive * p * i
            prob_alive *= q
        
        expected_fail_cost = expected_crash_pos + r
        
        # total expected cost:
        # (exp_attempts - 1) failures + 1 success
        return (exp_attempts - 1) * expected_fail_cost + length + dp_placeholder
        
        # dp_placeholder will be added outside

    INF = 1e100
    dp = [0.0] * (c + 1)
    
    for i in range(c - 1, -1, -1):
        best = INF
        for j in range(i + 1, c + 1):
            length = j - i
            
            success = qpow[length]
            if success == 0:
                continue
            
            exp_attempts = 1.0 / success
            
            expected_crash_pos = 0.0
            prob_alive = 1.0
            for k in range(1, length + 1):
                expected_crash_pos += prob_alive * p * k
                prob_alive *= q
            
            expected_fail_cost = expected_crash_pos + r
            
            seg = (exp_attempts - 1) * expected_fail_cost + length
            
            best = min(best, seg + t + dp[j])
        
        dp[i] = best
    
    print(dp[0])

```この実装は、セグメント エンドポイントを介した直接 DP に従います。 ネストされたループは、可能な次の保存位置をすべて列挙します。`j`開始位置ごとに`i`、O(c^2) 構造が生成されます。 

移行中に、セグメントの予想コストを計算します。`[i, j]`失敗を明示的にモデル化することによって。 ループオーバー`k`幾何学的生存確率を使用して予想される衝突位置を計算します`q^(k-1) * p`。 これにより、クラッシュの明示的なシミュレーションが回避され、代わりに考えられるすべての障害点が統合されます。 

微妙な点は、成功確率です。`q^length`予想される試行を定義するため、除算をゼロにすることはできません。 実際には、これが数値的に不安定になるのは次の場合のみです。`p`は 1 に非常に近いですが、必要な誤差許容範囲内では倍精度で十分です。

 ## 特殊なケース

 いつ`p`非常に小さく、クラッシュはまれであり、DP は自然に保存を回避します。`t`予想される回収コストの大半を占めます。 たとえば、`c = 5`、`t = 10`、`r = 10`、 そして`p = 0.001`、最良の戦略は事実上 1 つの長いセグメントです。 DP は、成功確率が 1 に近い長いセグメントを評価し、予想されるコストをほぼ決定します。 

いつ`p`1 に非常に近い、成功確率`q^len`短いセグメントでも非常に小さくなります。 DP は、長さ 1 のセグメントを優先することで反応します。これは、長いセグメントでは予想される再試行回数が爆発的に増加するためです。 これは、すべてのキャラクターの後に保存することが最適になるという直観と正確に一致します。 

いつ`t = 0`、保存は無料であり、DP はクラッシュ コストを最小限に抑える最大のセグメンテーションを選択するようになり、厳密に必要でない場合でも頻繁に保存することを優先することがよくあります。 この定式化は依然として機能します。`t`セグメント境界ごとに追加されるだけです。 

いつ`c = 1`、可能なセグメントは 1 つだけであり、アルゴリズムは基本 DP 状態と直接一致するクラッシュ確率の下で 1 つの文字を入力するのにかかる予想時間を計算することに帰着します。
