 ## 問題の理解

 文字列として書かれた 2 つの風向きが与えられ、各文字列は円形コンパス上の方向を表し、方向は粗いものから細かいものへと再帰的に調整されます。 タスクは、両方の文字列を度単位の正確な角度に変換し、円上のそれらの間の最小角度差を計算することです。 

重要な問題は、指示が度として直接与えられないことです。 代わりに、階層構造が存在します。1 文字の方向は 4 つの基点に対応し、2 文字の方向は基点間の点に対応し、より長い文字列は、すでに定義された方向間のますます細かい中間点を再帰的に定義します。 最終的に、すべての有効な文字列は円上の固有の方向をエンコードします。 

出力は、時計回りまたは反時計回りの選択とは無関係に、X 方向から Y 方向に移動するのに必要な最小限の回転であるため、単純に 360 を法とする絶対角度差を最大 180 にクリップしたものになります。 

この制約により、各文字列の長さは最大 1000 になることが許可されているため、完全な円のパーティションを再計算することによって、あらゆるレベルで幾何学的構造を単純にシミュレートしようとするソリューションは、非常に遅すぎます。 ただし、各文字列は 1 回だけ処理されるため、文字列ごとの線形再構成で十分です。 

微妙なエッジ ケースは、再帰的定義が「前の方向で定義された円弧間の中間点」を使用することです。これは、円弧の幾何学的細分割を繰り返す必要があると誤解される可能性があります。 たとえば、単純なアプローチでは、すべての中間コンパス ノードを明示的に構築しようとする可能性があり、その深さは指数関数的に増加します。 代わりに、この構造により、各文字列が円上の決定論的なバイナリ サブディビジョン パスに対応することが保証されるため、そのパスを数値角度にデコードするだけで済みます。 

## アプローチ

 強引な解釈では、定義によって暗示される完全なコンパス グラフの再構築が試みられます。 8 つの基本方向から始めて、長い文字列ごとに、コンテキストに応じて既存の方向の間に新しい中間点が挿入されます。 新しい文字列ごとに、グラフの構築またはその深さまでのすべての可能な方向の循環順序付けをシミュレートし、文字列に対応する方向を特定します。 潜在的なノードの数は文字列の長さに応じて指数関数的に増加し、そのような構造を格納または走査するだけでも時間とメモリの両方の制限を超えるため、このアプローチはすぐに実行不可能になります。 

重要な洞察は、すべての文字列が円上の二者択一のシーケンスを記述しているということです。 各ステップで、方向は以前の文字によって決定された 2 つの既知の方向の中点として定義されます。 これは、円上の間隔を維持し、一方の端点に向かうか他方の端点に向かうかに応じて円を繰り返し二等分することに相当します。

 ## アルゴリズムのチュートリアル

 まず、4 つの基本方向と 4 つの基本方向の角度を度単位で事前定義します。 これらは、各文字列の最後の 2 文字をデコードするためのアンカーとして機能します。 

1. 各方向文字列を個別に解析し、その角度を計算します。

最後の 2 文字から開始します。これらは既知の角度に直接マッピングされます。 これにより、円上の基本セグメントが得られます。 
2. 文字列を右から左に、位置 k-3 から開始して 0 まで処理します。 

各文字は、方向をより小さな円弧に移動する絞り込みの選択肢を表します。 現在の既知の間隔を、2 つの暗黙的な境界方向間にまたがるものとして扱います。 
3. 円上の現在の角度間隔 [a, b] を維持します。 

最初は、この間隔は最後の 2 文字によって決まります。 最終的な方向はこの間隔のちょうど中間点にあると解釈されます。 
4. 前の各文字について、間隔の左の終点に向かって移動するか右の終点に向かって移動するかを決定します。 

各文字は最後の 2 文字のサフィックスの 2 文字のいずれかである必要があるため、暗黙的に二分決定をエンコードします。つまり、現在のセグメントの 2 つの「半分」のいずれかに属します。 それに応じて間隔を縮めます。 
5. すべての文字を処理した後、最終間隔の中点を結果の方向角度として取得します。 
6. X と Y の両方が角度に変換されたら、それらの差の絶対値を計算します。 

この差が 180 度を超える場合は、360 度からその差を引いて、小さい方の回転を取得します。 

### なぜ効果があるのか

 有効な各文字列は、方向の固定循環順序に対する再帰的な中点構造を定義します。 すべてのステップで、定義は既存のアークを、以前に確立されたエンドポイントによって定義された 2 つの同等の概念的なサブアークに分割するだけです。 これは、このプロセスが、バイナリ洗練ツリー内の円上のパスを選択することと同等であることを意味します。 最終方向は常に最後に残っている間隔の中点であるため、プロセスを繰り返し間隔の半分として表現すると、完全なツリーを明示的に構築する必要がなく、正確な構造が保存されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

base = {
    "N": 0.0,
    "E": 90.0,
    "S": 180.0,
    "W": 270.0,
    "NE": 45.0,
    "SE": 135.0,
    "SW": 225.0,
    "NW": 315.0
}

def normalize(angle):
    angle %= 360.0
    return angle

def angle_of(s):
    if len(s) == 1:
        return base[s]

    if len(s) == 2:
        return base[s]

    a = base[s[-2:]]
    b = base[s[-2]]  # direction formed by first of the last two letters' axis is not directly used meaningfully

    lo, hi = 0.0, 360.0
    lo = base[s[-2:]]
    hi = (base[s[-2:]] + 180.0) % 360.0

    for i in range(len(s) - 3, -1, -1):
        c = s[i]
        mid = (lo + hi) / 2.0

        if c == s[-2]:
            hi = mid
        else:
            lo = mid

    return (lo + hi) / 2.0

def circular_diff(a, b):
    d = abs(a - b)
    return min(d, 360.0 - d)

x, y = input().split()
ax = angle_of(x)
ay = angle_of(y)

print(f"{circular_diff(ax, ay):.10f}")
```機能`angle_of`記号的な風向を数値の角度に変換します。 ロジックは、既知の 45 度のセクター内で方向を固定する 2 文字の接尾辞から始まります。 次に、先行する各文字は、角度間隔を繰り返し半分にすることによって位置を調整し、問題で説明されている再帰的中点構成を効果的にシミュレートします。 

ついに、`circular_diff`直線距離と 0 度を通る回り込み距離を比較することにより、円上の最小回転を計算します。 

一般的な微妙な点は、間隔を維持するときにラップアラウンドを正しく処理することです。 このソリューションは、中間点リファインメント中に概念的なアンラップ空間で作業し、最後にのみ循環正規化を適用することにより、明示的なモジュラー区間演算を回避します。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import math

    base = {
        "N": 0.0,
        "E": 90.0,
        "S": 180.0,
        "W": 270.0,

        d = abs(a - b)

    x, y = input().split()
    return f"{diff(angle_of(x), angle_of(y)):.10f}"

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、両方の文字列が同一であるが、長さが 2 より大きい場合です。その状況では、中間点リファインメントを繰り返すと、2 つの計算間の浮動小数点ドリフトが蓄積してはなりません。 どちらのパスも同じシーケンスの半分化演算を適用するため、同じ値に収束し、最終的な差は正しくゼロになります。 

もう 1 つのケースは、北と南、または北東と南西など、正確に 180 度離れた反対方向です。 循環差分ロジックでは、直接距離とラップアラウンド距離の間の最小値を取得することで、180 を超える値が返されないようにします。 これにより、270 などの誤った大きな角度が報告されるのを防ぎます。 

さらにエッジ ケースとして、長さ 1000 までの非常に長い文字列があります。アルゴリズムは依然として各文字を 1 回だけ処理するため、最大入力サイズでもパフォーマンスは線形で安定しています。
