 ## 解決策
 ## 問題の理解

 ターゲットの小文字文字列と、最初は空のワークスペースが与えられます。 目標は、非常に特殊なツールセットの下で可能な限り少ない操作を使用して文字列を構築することです。現在のテキストの末尾に 1 文字を追加したり、現在のテキスト全体をクリップボードにコピーしたり (そこにあったものはすべて置き換えたり)、クリップボードの内容を現在のテキストの末尾に貼り付けることができます。 

主な難点は、コピーは常に部分文字列ではなく現在のテキストの「完全なスナップショット」であり、貼り付けは常にクリップボード全体を追加することです。 つまり、繰り返しを利用する唯一の方法は、最初にプレフィックスを作成し、それをコピーし、次に同じプレフィックスを繰り返し貼り付けることです。 

出力は、空の文字列を指定されたターゲット文字列に変換するために必要な最小限の操作数にすぎません。 

文字列の長さが最大 ​​100,000 に達する可能性があるという制約により、考えられるすべての操作シーケンスをシミュレートしようとするソリューションは即座に除外されます。 両方の次元が直線的に増加し、分岐が一定であるため、「現在の文字列 + クリップボード」に対する単純な状態検索は爆発的に発生します。 最適化を行わずにすべての部分文字列を比較する動的プログラミングであっても、部分文字列のチェックが繰り返されるため、二次または三次の動作に低下します。 

単純な貪欲な思考による微妙な失敗例は、繰り返しが 1 文字の拡張と一致していない場合に現れます。 

たとえば、次のような文字列を考えてみましょう。`ababab`。 貪欲なビルダーは、次の条件まで文字を挿入する可能性があります。`abab`をコピーし、一度貼り付けて取得します`ababab`、比較的少ない操作を使用します。 しかし、次のような文字列の場合`aaabaaa`、不安定なプレフィックスをコピーすると、後でより良い繰り返し構造を再利用できなくなるため、早期に貪欲にコピーすることは有害です。 

もう 1 つの落とし穴は、常にできるだけ早くコピーする必要があると想定していることです。 のために`aaaaa`、ビルド後にコピー`a`魅力的に見えますが、ビルド後にコピーする必要があります`aaa`後の操作が減るため、厳密にはこの方が優れています。 

これらの相互作用は、最適な戦略は、プレフィックスがより大きなプレフィックスを正確にタイリングできる時期を認識することに依存していることを示しています。 

## アプローチ

 ブルートフォースの考え方は、各状態を、現在構築されている文字列とクリップボードの内容から構成されるペアとして扱うことです。 各状態から 3 つの操作をすべて試します。 これにより、ノードが文字列であるグラフの最短経路問題が形成されます。 ターゲット文字列のプレフィックスに限定したとしても、クリップボードには指数関数的に多くの可能性があり、状態間の遷移では依然として長い文字列を比較する必要があります。 到達可能な状態の数は、長さの実際の制限をはるかに超えて 100,000 まで増加します。 

問題点は、状態空間が文字列の長さが線形であるだけでなく、以前にコピーされたすべてのセグメントにも依存していることです。 

重要な点は、クリップボードが役立つのは、コピー時の現在のプレフィックス全体に等しい文字列がクリップボードに含まれている場合のみであるということです。 長さ j のプレフィックスをコピーした後、ペーストするたびに文字列がちょうど j 文字分拡張されます。つまり、その時点からは j の倍数の長さまでしか到達できません。 

これにより、問題は文字列のブロックへの構造化された分解に変わります。 長さ i のプレフィックスを長さ j の k 個の同一ブロックに分割できる場合、最初に長さ j のプレフィックスを構築し、それを 1 回コピーし、k−1 回ペーストすることでそれを構築できます。 これには、dp[j] に加えて、そのセグメントに対する k 個の合計操作がかかります。 

これに加えて、文字を 1 つずつ挿入するという代替手段も常に用意されています。 

したがって、最適な解決策は、可分性チェックと高速な部分文字列の等価性テストを強化した、プレフィックス長に対する動的プログラミングです。

 ## アルゴリズムのチュートリアル

 dp[i] を、ターゲット文字列の最初の i 文字を構築するために必要な操作の最小数として定義します。 

### ステップ

 1. 空の文字列には操作が必要ないため、dp[0] = 0 を初期化します。 
2. 1 から n までの各位置 i について、ベースライン遷移 dp[i] = dp[i − 1] + 1 から開始します。これは、i 番目の文字を直接挿入することに対応します。 これは構造に関係なく常に有効です。 
3. 各 i について、j が i を除算するようなすべての可能なブロック サイズ j を考慮します。 長さ i のプレフィックスが長さ j のプレフィックスの繰り返しコピーで構成されているかどうかをテストします。 
4. 繰り返しを効率的に検証するために、すべての k について s[0:j] が s[k・j:(k+1)・j] に等しいことを確認します。 これはローリング ハッシュを使用して実装されているため、各チェックは O(1) となり、部分文字列スキャンの繰り返しが回避されます。 
5. プレフィックスが長さ j の有効な繰り返しであり、k = i / j 回繰り返される場合、次のようにして長さ i に到達できます。 

dp[j]を構築し、

 コピーは 1 回 (1 回の操作)、

 k − 1 回貼り付けます。 

これにより、候補値 dp[j] + k が得られます。 
6. すべての有効な j と挿入ベースラインの最小値を取得します。 

重要な決定点は、最終プレフィックスに正確な周期構造を生成する境界でのコピー操作のみを許可するということです。 これにより、無効なクリップボード状態を考慮する必要がなくなります。 

### なぜ効果があるのか

 最適な構築は、一連のフェーズとして見ることができます。 各フェーズでは、単一の文字を追加するか、すでに構築されているプレフィックスをコピーして、ペーストによって繰り返します。 コピーが使用されるたびに、クリップボードの内容はその時点で完全に構築されたプレフィックスと等しくなり、後続のすべての操作はその正確なブロックを繰り返すことによって文字列を拡張します。 したがって、貼り付け操作を使用して作成されたセグメントは、すでに構築されたプレフィックスの完全な繰り返しである必要があります。 DP はこれらの可能性を正確に列挙し、すべての有効な構造が表現可能であることを保証すると同時に、挿入遷移により非反復的な成長を決して見逃さないようにします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

def build_hash(s):
    n = len(s)
    base = 91138233
    mod = 972663749
    pref = [0] * (n + 1)
    p = [1] * (n + 1)

    for i, c in enumerate(s):
        pref[i + 1] = (pref[i] * base + (ord(c) - 96)) % mod
        p[i + 1] = (p[i] * base) % mod

    return pref, p, mod

def get_hash(pref, p, mod, l, r):
    return (pref[r] - pref[l] * p[r - l]) % mod

def solve():
    s = input().strip()
    n = len(s)

    pref, p, mod = build_hash(s)

    def equal(a, b, length):
        return get_hash(pref, p, mod, a, a + length) == get_hash(pref, p, mod, b, b + length)

    dp = [10**18] * (n + 1)
    dp[0] = 0

    for i in range(1, n + 1):
        dp[i] = dp[i - 1] + 1

        j = 1
        while j * j <= i:
            if i % j == 0:
                for d in (j, i // j):
                    if d == i:
                        continue
                    k = i // d
                    ok = True
                    for t in range(k):
                        if not equal(0, t * d, d):
                            ok = False
                            break
                    if ok:
                        dp[i] = min(dp[i], dp[d] + k)
            j += 1

    print(dp[n])

if __name__ == "__main__":
    solve()
```このソリューションは、プレフィックス動的プログラミングを中心に構築されています。 挿入のための DP 遷移は簡単で、常に有効なフォールバックが確保されます。 

より繊細な部分は繰り返しチェックです。 候補ブロック サイズごとに、プレフィックスが完全に周期的であることを確認します。 これにより、ローカルな一致がグローバルな繰り返しを意味するという誤った仮定が回避されます。 ハッシュを使用すると、部分文字列の比較が定数時間になることが保証されます。これは、直接比較するとチェックごとに解が 2 次になるため、不可欠です。 

除算ループでは i の因数のみが考慮されるため、候補の数は制限時間内に収まる程度に抑えられます。

 ## 特殊なケース

 次のような単一文字列`a`dp[1] は dp[0] + 1 から初期化され、コピー トランジションは適用されないため、正しく処理されます。 

次のような完全に均一な文字列`aaaaaa`複数の有効な除数チェックをトリガーします。 i = 6 では、アルゴリズムは長さ 3、2、または 1 がプレフィックスをタイル化できることを正しく認識し、dp[j] + i/j の中から最適なものを選択し、純粋な挿入よりも大幅な削減をもたらします。 

次のような非反復文字列`abcdef`1 より大きい約数 j の定期チェックを決して満たさないため、DP は純粋な挿入に縮退します。これは、コピー＆ペーストでは何のメリットもないため、正しい動作です。 

のような境界例`ababab`は、フルプレフィックスの定期的な検証の重要性を示しています。 ローカル一致をチェックするだけでは無効な遷移が誤って許可されますが、完全なハッシュ検証では、すべてのブロックが正確に一致することが強制されるため、正確さが保証されます。
