 ## 解決策
 ## 問題の理解

 固定数のスロットを持つハッシュ テーブルを維持しており、各スロットは最大 1 つのオブジェクトを保持できます。 各オブジェクトには一意の識別子と、そのハッシュ値によって指定される優先開始位置があります。 オブジェクトを挿入するときは、まずそのハッシュ位置を試します。 そのスロットがすでに占有されている場合は、停止しません。 代わりに、サイズを固定したジャンプでテーブル内を歩きます。`m`、モジュロをラップアラウンド`h`空のスロットが見つかるまで。 

スロットを試行し、この調査プロセス中にスロットが占有されていることが判明するたびに、その試行はダミー呼び出しとしてカウントされます。 タスクは、一連の挿入と削除を処理し、すべての挿入にわたってそのような失敗したプローブの総数を計算することです。 

削除は以前に占有されていたスロットを解放するだけであり、プローブのコストには影響しません。 

制約は最大 200,000 のオペレーションと最大 200,000 のテーブル サイズに達します。 これにより、最悪の場合、前方にステップごとにスキャンして各挿入をシミュレートすることが直ちに排除されます。これは、単一の挿入がほぼテーブル全体を横断する可能性があり、多くの操作にわたって繰り返されると二次的な動作が発生する可能性があるためです。 

微妙な点は、プローブは決定論的であり、オブジェクトのアイデンティティではなく、占有された位置のみに依存することです。 もう 1 つの重要な点は、削除によって再編成が引き起こされるわけではないということです。 セルを解放するだけなので、将来の挿入は過去の削除に応じて異なる動作をする可能性があります。 

長いチェーンが形成されると、単純な実装の失敗が発生します。 

たとえば、次の場合`h = 10, m = 1`そして、ほぼ完全なテーブルに挿入します。```
+ a 0
+ b 0
+ c 0
+ d 0
...
```挿入ごとに多くの占有セルがスキャンされ、総作業量はすべてのプローブの長さの合計に比例し、約$O(nh)$密度の高いシナリオで。 これでは遅すぎます。 

もう 1 つの失敗例は、削除が繰り返され、プローブ パスに「穴」ができることです。 構造が動的で再利用できる場合でも、毎回最初からプローブを再開する素朴な実装では、依然として全額のスキャン コストが発生します。 

## アプローチ

 ブルート フォース シミュレーションは定義に直接に従います。 挿入ごとに、次から開始します。`t`、無料かどうかを確認し、無料でない場合は繰り返し追加します`m (mod h)`空のスロットが見つかるまで。 失敗した各チェックを 1 つのダミー呼び出しとしてマークします。 削除は対応するスロットをクリアするだけです。 

これはプロセスを正確に反映しているため、これは正しいです。 問題はコストです。テーブルが高密度になると、各挿入でほぼすべてのテーブルがスキャンされる可能性があります。`h`ポジション。 以上`n`操作では、これは次のように縮退します。$O(nh)$、それは限界をはるかに超えています。 

重要な観察は、すべての挿入は現在占有されている位置にのみ依存し、プローブは常に固定された等差数列モジュロに沿って移動することです。`h`。 これにより、スロットごとに、そのスロットが現在占有されているかどうかを維持することができ、挿入ごとに、空きセルに到達するとすぐに停止できます。 重要な改善点は、最初に利用可能な位置を超えて何もシミュレートする必要がないことです。 実行されるチェックの数はカウントする必要がある正確な数であるため、最初の空のスロットまでしか進みませんが、余分なオーバーヘッドを発生させずに直接配列検索を使用して効率的に実行します。 

この構造は本質的に動的な占有配列であり、プローブ シーケンスはそれを決定論的にウォークします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n・h) | O(h) | 遅すぎる |
 | 最適 | O(n・k) 最悪の場合でも償却済み O(n) | O(h + n) | 承認済み |

 ここ`k`は挿入ごとのプローブの数ですが、すべての挿入にわたるプローブの総数はダミー コールの総数に等しく、これはまさに計算したものです。 

## アルゴリズムのチュートリアル

 配列を維持します`occupied`サイズの`h`、最初はすべて false、および辞書`pos`オブジェクト ID を最後のスロットにマッピングします。 

操作を順番に処理していきます。 

1. 操作が挿入の場合`(id, t)`、インデックスから調査を開始します`t`。 

チェックします`occupied[t]`。 空いている場合は、そこにオブジェクトを配置し、この挿入に対するダミー呼び出しを記録しません。 
2. もし`occupied[t]`それは本当です、私たちは次へ進みます`(t + m) % h`、 それから`(t + 2m) % h`、空きスロットが見つかるまで続けます。 

占有スロットに遭遇するたびに、グローバル ダミー カウンタを 1 ずつインクリメントします。 
3. 空きスロットが見つかると、そのスロットが占有されているとマークされ、その位置にオブジェクト ID が保存されます。 
4. 操作が削除の場合`id`、保存された位置を検索し、そのスロットを空きとしてマークします。 

プローブ パスは常に決定的であるため、削除中にハッシュ マップの検索以外にオブジェクトを検索する必要はありません。 

### なぜ効果があるのか

 いつでも、各挿入は候補セルの 1 つの決定的なシーケンスに従います。 このアルゴリズムは、最初の空きセルの前に出現した占有セルごとに 1 ユニットをカウントします。 このパスを正確にシミュレートし、テーブルの正確な占有状態を維持するため、カウントされるすべての衝突は、元のプロセスで実際に失敗した試行に対応します。 挿入または削除によってプローブの順序が変更されることはありません。 変更されるのはポジションがフリーかどうかだけであり、それがまさにシミュレーションで追跡されるものです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    h, m, n = map(int, input().split())
    occupied = [False] * h
    where = {}  # id -> position
    ans = 0

    for _ in range(n):
        parts = input().split()
        if parts[0] == '+':
            _, sid, sh = parts
            sid = int(sid)
            sh = int(sh)

            cur = sh
            while occupied[cur]:
                ans += 1
                cur = (cur + m) % h

            occupied[cur] = True
            where[sid] = cur

        else:
            _, sid = parts
            sid = int(sid)
            pos = where.pop(sid)
            occupied[pos] = False

    print(ans)

if __name__ == "__main__":
    solve()
```ソリューションの中核は、プローブ シーケンスの直接シミュレーションです。 の`occupied`配列は現在のテーブルの状態をエンコードします。 挿入の場合、空のスロットが見つかるまで文字通りプローブ チェーンに沿って歩き、試行が失敗するたびに答えをインクリメントします。 辞書`where`テーブル内のオブジェクトを検索しないため、削除は O(1) になります。 

微妙な実装の詳細は、プローブ ループを更新する必要があることです。`cur = (cur + m) % h`衝突を数えた直後。 これらのステップを交換すると、成功したスロットが誤って衝突としてカウントされたり、最終的な配置を逃したりする可能性があります。

 ## 特殊なケース

 テーブル サイズが 1 の場合、最初の挿入後のすべての挿入では、唯一のセルを見つける前に、占有されている 1 つのスロットを正確にプローブする必要があります。 while ループは 1 つのスロットが空くまで実行されるため、アルゴリズムは挿入が失敗するたびにダミー カウンタを 1 回正しくインクリメントします。 

密集したクラスターの中央で欠失が発生すると、それまで長かったプローブ チェーンは、後の操作のために直ちに縮小します。 占有配列はすぐに更新されるため、後続の挿入はより早く停止し、実際のプローブ動作と正確に一致します。 

いつ`m`と互いに素ではない`h`、プローブ シーケンスはインデックスのサブセットを循環します。 シミュレーションは実際のプロセスと同じ決定論的なサイクルに従うため引き続き機能し、問題ステートメントによって終了が保証されるため、そのサイクル内に空きスロットが存在する必要があります。
