 ## 解決策
 ## 問題の理解

 次の長さの文字列を構築するように求められます$3n$アルファベットの上に$\{a,b,c\}$、各文字が正確に表示される場所$n$回。 このバランス制約に加えて、それぞれ長さ 2 の文字列である 2 つの禁止パターンが与えられます。 構築された文字列の内部には、これら 2 つのペアのいずれも隣接する文字として含まれていてはなりません。 

したがって、このタスクは、大まかな意味でのサブシーケンスや再配置に関するものではなく、連続する文字間に禁止された有向エッジが表示されないように複数の文字セットを順序付けることに関するものです。 長さ 2 の各禁止文字列は、有向制約のように動作します。`"ab"`入力ペアリストに、を配置することはできません。`a`すぐに続いて`b`最終的な取り決めで。 

制約は大きいです:$n$まで可能です$10^5$したがって、最終的な文字列の長さは次のようになります。$3 \cdot 10^5$。 状態空間が階乗的に増加するため、置換や配置のバックトラックを試行しようとするソリューションはすぐに失敗します。 二次構成でさえ境界線に達するでしょう。 意図したソリューションは線形またはほぼ線形でなければなりません。 

微妙な問題は、制約間の相互作用から発生します。 禁止された各ペアを個別にローカルで回避するだけでは十分ではありません。1 つの文字を早めに配置すると、カウントや制約に違反せずに残りの文字を配置できない状況が生じた場合、今後の配置がブロックされる可能性があるからです。 

現在の最後の文字のみに基づいて安全な文字を常に追加する単純な貪欲は失敗する可能性があります。 たとえば、辞書編集的に最小の有効な次の文字を常に選択すると、後で禁止された遷移だけが利用可能になったときに行き詰まってしまう可能性があります。 

もう 1 つの明白ではない落とし穴は、両方の禁止されたペアが同じ文字を共有していると仮定することです。`"ab"`そして`"ac"`であれば、単純に配置を避けることができます。`a`両方の前に`b`そして`c`それ以上の構造は必要ありません。 すべてのカウントを正確に配置する必要があり、順序によっては文字を完全に分離する可能性があるため、これは誤解を招きます。 

## アプローチ

 ブルート フォース ビューでは、文字列を段階的に構築しようとし、各位置で残りの可能性のあるすべての文字を試し、追加によって禁止されたペアが作成されたり、不可能なサフィックスが生成されたりするかどうかを確認します。 これは事実上、深さのある最大 3 の分岐係数にわたるバックトラッキング検索になります。$3n$。 枝刈りを行ったとしても、多くの部分文字列はローカルでは有効なままですが、グローバルでは回復できないため、最悪の場合の動作は指数関数的に爆発的に増加します。 

重要な構造上の観察は、登場人物が 3 人だけであるということです。 禁止されたペアは、3 ノードの有向グラフで最大 1 つの有向エッジを削除します。 これは、正確な頂点訪問数を尊重しながら、本質的に小さな有向グラフ上のウォークを構築していることを意味します。 グラフのサイズは一定であるため、検索の代わりに事例分析を活用できます。 

問題はノード上にシーケンスを構築することであると解釈します$a,b,c$ここで、エッジは許可された遷移に対応します。 各禁止ペアは、6 つの可能な遷移の完全な有向グラフから 1 つの有向エッジを削除します。 禁止されているエッジは 2 つだけなので、少なくとも 4 つの遷移が許可されたままになります。 

重要なアイデアは、文字の「基本順序」を選択し、禁止された遷移を決して使用しないように、ブロック内に 3 番目の文字を慎重に挿入することです。 1 つの文字を「セパレータ」または「アンカー」として扱う場合、多くの場合、残りの 2 文字を安全な交互構造に配置し、3 番目の文字をチャンクに分割して挿入するという問題に減らすことができます。 

古典的なトリックは、3 つの文字の順序を固定することです。$x, y, z$、そして最初にどのようにするかを決定する場所で文字列を構築しようとします$x$そして$y$インタラクションしてから配布する$z$禁止されたペアを作成せずに。 禁止されている遷移は 2 つだけなので、少なくとも 1 つの順列が必要です。$(a,b,c)$構造を破壊することを避けます。 

無作為に推測するのではなく、すべてを試します$6$文字の順列を作成し、それぞれについて決定論的な構築を試みます。 固定順序の場合、カウントを維持し、禁止された隣接ペアが決して配置されないようにしながら、貪欲に文字列を構築します。 アルファベットは小さいので、この決定論的な構造で十分です。 

貪欲な戦略は、最後に配置されたキャラクターの後に常に禁止されていないキャラクターを配置しようとする場合に機能し、カウントが残っているキャラクターを優先します。 構築が失敗した場合は、順序に互換性がないことを意味するため、順列を切り替えます。 

これにより、問題は指数関数的な検索から線形貪欲構築の継続的な試行へと軽減されます。

 ## アルゴリズムのチュートリアル

 文字のすべての順列を試して答えを構築しようとします`a`、`b`、`c`。 

それぞれの順列について:

 1. 残りのカウントを初期化します:`a`、`b`、`c`は$n$。 また、空の結果文字列を開始します。 
2. 追加する次の文字を繰り返し選択します。 

現在の順列順序で文字を考慮し、まだカウントが残っており、最後の文字との禁止された隣接ペアを作成しない最初の文字を選択します。 

順列順にスキャンする理由は、構築を決定論的に保ち、振動を避けるためです。 
3. 選択した文字を追加し、残りの数を減らし、最後の文字トラッカーを更新します。 
4. ある時点で、カウントが残っている間に文字を配置できない場合は、この順列を中止し、次の順列から再開します。 
5. すべてを正常に配置できたら$3n$文字を入力すると、結果がすぐに出力されます。 

なぜこの欲張りなことが機能するのかは、状態空間が極めて小さいという事実に関係しています。 すべてのステップで、現在のキャラクターから最大 2 つの禁止された外向きエッジを回避するだけで済みます。 合計 3 つのオプションがあるため、有効な置換では少なくとも 1 つの候補が常に構造的に安全です。 すべての順列を試すと、最終的には禁止された遷移と一致する順序が選択されることが保証されます。 

### なぜ効果があるのか

 この構造では、文字列のすべてのプレフィックスに禁止された隣接ペアが含まれないという不変条件が維持されます。 アルゴリズムが失敗する唯一の方法は、残りの文字がすべて現在の最後の文字からの禁止された遷移につながる場合です。 これが発生した場合、選択されたグローバル順序によって行き止まりが強制され、その順列の下では完了が存在しないことを意味します。 正しい解決策は、制約と一致するアルファベットの順序に対応している必要があるため、6 つの順列のうち 1 つがそのような行き止まりを回避し、成功します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build(order, n, bad):
    cnt = {c: n for c in "abc"}
    res = []
    
    for _ in range(3 * n):
        placed = False
        last = res[-1] if res else None
        
        for ch in order:
            if cnt[ch] == 0:
                continue
            if last is not None and last + ch in bad:
                continue
            cnt[ch] -= 1
            res.append(ch)
            placed = True
            break
        
        if not placed:
            return None
    
    return "".join(res)

def solve():
    n = int(input())
    s = input().strip()
    t = input().strip()
    bad = {s, t}
    
    chars = "abc"
    
    from itertools import permutations
    
    for order in permutations(chars):
        ans = build(order, n, bad)
        if ans is not None:
            print("YES")
            print(ans)
            return
    
    print("NO")

if __name__ == "__main__":
    solve()
```このソリューションでは、まず禁止された遷移を O(1) ルックアップ用のセットにエンコードします。 次に、潜在的な構造優先度としてアルファベットの 6 つの順列すべてを試行します。 

の`build`関数は、固定された順序の下で有効なシーケンスを貪欲に構築します。 重要な詳細は、候補を追加する前に、最後に配置された文字を禁止されたセットに対して常にチェックすることです。 あるステップで機能する候補がない場合は、現在の順列を完全に放棄します。 

よくある実装の間違いは、順列間の状態をきれいに再起動できないことです。 もう 1 つの微妙な問題は、空のプレフィックスには最後の文字がないことを忘れていることです。これは個別に処理する必要があります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n = int(input())
    s = input().strip()
    t = input().strip()

    bad = {s, t}

    from itertools import permutations

    def build(order):
        cnt = {c: n for c in "abc"}
        res = []
        for _ in range(3 * n):
            last = res[-1] if res else None
            ok = False
            for ch in order:
                if cnt[ch] and (last is None or last + ch not in bad):
                    cnt[ch] -= 1
                    res.append(ch)
                    ok = True
                    break
            if not ok:
                return None
        return "".join(res)

    for order in permutations("abc"):
        ans = build(order)
        if ans is not None:
            return "YES\n" + ans + "\n"

    return "NO\n"

# provided sample
assert run("2\nab\nbc\n").startswith("YES")

# all equal forbidden pair
assert run("1\naa\nbb\n") == "YES\nabc\n"

# self-loop constraints
assert run("2\naa\naa\n") != ""

# maximum trivial case
assert "YES" in run("1\nab\nac\n")

 ## 特殊なケース

 1 つのエッジ ケースは、両方の禁止ペアが同じ文字からの遷移を排除するときに発生します。 たとえば、次の場合`s = ab`そして`t = ac`、 それから`a`どちらにも行けません`b`または`c`。 アルゴリズムはこれを処理します。`a`早期に強制すると、すぐに文字列の拡張に失敗し、その順列は破棄されます。 成功した置換の場所`a`後で、またはボトルネック状態になるのを回避します。 

もう 1 つのケースは、禁止されたペアが次のようなサイクルを形成する場合です。`ab`そして`ba`。 ここ`a`そして`b`どちらの方向にも隣接することはできません。 構造上、自然にそれらを分離します。`c`、および配置される任意の順列`c`彼らの間では成功します。 貪欲なプロセスは決して違法な隣接関係を試みることはありません。そのため、セパレータの役割は`c`自動的に出てきます。 

3 番目のケースは、両方の禁止ペアに、同一の入力など、概念的に繰り返される同じ順序ペアが含まれる場合です。 これは事実上 1 つの制約に減りますが、少なくとも 1 つの順序付けが 1 つの禁止エッジを回避するため、アルゴリズムは依然としてすべての置換を試行し、自明に成功します。
