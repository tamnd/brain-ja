 ## 解決策
 ## 問題の理解

 ここでは、それぞれの顧客が一定数のピザのスライスを要求する一連の顧客にサービスを提供するピザ店をシミュレートしています。 当店の収納力は、`m`、各テスト ケースの開始時には完全にいっぱいになります。 

各顧客にサービスが提供された後、ショップはしきい値に基づいてルールを適用します。`d`。 ストレージ内の残りのスライス数が以下になった場合`d`、店はすぐに補充されます`m`。 

顧客満足度は、現在の在庫で需要をすべて満たせるかどうかにかかっています。 十分なスライスが存在する場合、ショップは要求された金額を正確に差し引きます。 それ以外の場合は、残ったものはすべて引き渡され、顧客は不満とみなされ、プロセスが続行されます。 

タスクは可能な限り小さいしきい値を選択することです`d`すべての顧客に完全なサービスが提供され、欠品が発生することはありません。 

制約が意味するのは、`n`そして`m`テスト ケースごとに最大約 200,000 まで大きくなる可能性があり、テスト全体にわたるすべての顧客の要求の合計は 200,000 に制限されます。 これにより、考えられるすべての候補値をシミュレートするアプローチは即座に除外されます。`d`全体にわたる単純なスキャンのため、完全な再計算を使用して独立して実行されます。`d`値は次のように乗算されます`m`、大きすぎます。 

ローカルの補充動作について貪欲に推論すると、微妙な失敗例が発生します。 たとえば、「次の顧客を満足させるために必要なときにいつでも補充する」と仮定すると、注文後まで補充を遅らせると永続的な失敗の原因となる可能性があるという事実を見落とす可能性があります。 

次のようなケースを考えてみましょう。 

入力:`n = 2, m = 5, a = [4, 4]`もし`d = 2`、5個から始めて4個出し、残りが1個になったので5個に補充します。次のお客さんも無事4個もらいました。 これは機能します。 

しかし、各顧客の前に補充が行われると誤って仮定したり、「提供後」の条件を誤って処理したりすると、誤ったシミュレーションを行って、異なる実現可能性を結論付ける可能性があります。 

主な問題点は、補充ルールが、ローカルな決定だけでなく、プレフィックス全体の残り在庫のグローバル最小値に依存する形で消費プロセスと相互作用することです。 

## アプローチ

 強引なアイデアは、可能なすべての値を試してみることです。`d`1から`m`、顧客シーケンス全体をシミュレートし、在庫切れになる顧客がいるかどうかを確認します。 候補者ごとに`d`、すべてをシミュレートします`n`顧客に在庫を更新し、必要に応じて補充します。 

これはルールに正確に従っているため、これは正しいです。 ただし、各シミュレーションは O(n) であり、最大 O(m) 回繰り返します。 最悪の場合、これは O(nm) となり、非常に大きすぎます。`n, m`最大 2×10^5。 

重要な点は、実際にはすべてのしきい値を個別にテストする必要はないということです。 代わりに、株価がどのように推移するかを追跡しながらプロセスを一度シミュレートし、最小値を決定することができます。`d`それが失敗を防ぐことになるでしょう。 

重要な洞察は、残りの在庫が需要を下回った瞬間にのみ顧客が失敗するということです。 在庫が下がるたびに補充が行われるため、`d`、の値`d`早期に補充がどのように発生するかを制御します。 小さめの`d`つまり、補充する前に在庫が少なくなることが許されており、失敗のリスクが高まります。 より大きな`d`早めに補充してください。これは役に立ちます。 

この単調な動作は、実現可能性が単調であることを意味します。`d`: 値の場合`d`機能する場合は、より大きな値も機能します。 これにより、問題を特定の条件が true になるしきい値を見つけることとして解釈できるようになります。 

完全なシミュレーションを繰り返して二分探索を行う代わりに、視点を逆転させることができます。 一定のルールに基づいてプロセスを一度シミュレーションしますが、これまでに見たことのない最小在庫レベルを追跡します。 有効な最小値`d`顧客の負担を避けるために、詰め替えが必要になるまでにどれだけの温度まで下げることができるかによって決まります。 

実際、このプロセスは、実行中の在庫を維持することとみなすことができます。 在庫が下がるたびに`d`にリセットされます。`m`ただし、このリセットは将来の障害を防ぐ場合にのみ重要です。 重要な点は、答えが各トランザクション後の最小プレフィックス ストックに依存し、これを 1 回のパスで計算できることです。 

したがって、最適なアプローチは、テスト ケースごとに 1 回のリニア スキャンに減ります。

 ## アルゴリズムのチュートリアル

 現在の在庫を維持し、処理中に発生した最低在庫価格を追跡しながら、顧客シーケンスを一度シミュレーションします。 

1.初期化`stock = m`。 これは、現在利用可能なピザのスライスの数を表します。 
2. 変数を維持する`min_stock`最初は等しい`m`、顧客にサービスを提供した後に確認される最小在庫を追跡します。 
3. 顧客の要望ごとに`x`、それらにサービスを提供してみます。 

もし`stock >= x`、 減らす`stock -= x`。 

それ以外の場合は、設定します`stock = 0`なぜなら、顧客は利用可能なものはすべて消費するからです。 

これを明示的にゼロに設定する理由は、部分的なフルフィルメントによっても、将来の可用性の観点からストアが完全に枯渇してしまうためです。 
4. 配信後に更新する`min_stock = min(min_stock, stock)`。 これにより、最悪の消耗点が捕捉されます。 
5. 在庫が候補しきい値を下回るたびに、補充ロジックを概念的に適用します。`d`にリセットされます。`m`。 これを直接シミュレーションするのではなく、実現可能性とは、次の顧客にサービスを提供するために許容できる在庫を下回る状態にプロセスが強制的にならないようにする必要があると解釈します。 
6. 最終的な答えは、最も深い消耗点、つまり最小の劣化点から導き出されます。`d`有害な枯渇を防ぐ最大の不足深さは、まさに故障を回避するために必要な最大の不足深さであり、観測された最悪の在庫低下を上回る最小の安全なバッファーに相当します。 

### なぜ効果があるのか

 このプロセスは以下に関して単調です`d`。 増加中`d`補充を早期にトリガーできるだけで、在庫が増加しますが、減少することはありません。 したがって、しきい値によってすべての障害が防止されると、それより大きなしきい値でも障害が防止されます。 

障害が発生する唯一の方法は、累積消費量が、暗示される効果的な安全な補充スケジュールを超えるプレフィックスに達した場合です。`d`。 この失敗は、人為的に早期に補充を行わずにフルパス中にストックがどの程度低下するかによって完全に特徴付けられます。 到達した最小在庫は、必要なバッファーの量を正確にエンコードします。 どれでも`d`その臨界深度を超えると、システムが危険な最低点に到達することがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        a = list(map(int, input().split()))

        stock = m
        min_stock = m

        for x in a:
            if stock >= x:
                stock -= x
            else:
                stock = 0

            if stock < min_stock:
                min_stock = stock

        # The smallest d that guarantees no "unsafe dip"
        # corresponds to how far we fell from full capacity.
        # If we ever reached min_stock, we need d to be at least that far from m.
        ans = m - min_stock
        print(ans)

if __name__ == "__main__":
    solve()
```実装の中核はシングルパス シミュレーションです。 異なるものを明示的にシミュレートすることはありません`d`価値観。 代わりに、補充を無視した場合にシステムがどの程度消耗するかを計算します。 答えは、容量に対して観測された最悪の消耗から導き出されます。 

重要な点は、顧客に「部分的なサービス」を決して提供しないことです。 在庫が不足している場合はすぐにゼロになり、失敗した場合には残りのピザが完全に消費されるという問題のルールに一致します。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    input = sys.stdin.readline

    out = []
    for _ in range(t):
        n, m = map(int, input().split())

 ## 特殊なケース

 重要なエッジケースは、単一の顧客の需要が正確に等しい場合です。`m`。 入力用`n = 1, m = 10, a = [10]`、在庫は 10 から 0 にすぐに低下するため、`min_stock = 0`これは、システムが 1 ステップで使い果たされるため、大きなしきい値がなければ、いかなる補充ポリシーも無関係であるという直観と一致します。 

もう 1 つのケースは、すぐに失敗を引き起こすことなく、在庫をゆっくりと消耗させる小さな要求が繰り返される場合です。 のために`m = 6, a = [2, 2, 2]`、在庫は 6 → 4 → 2 → 0 となり、計算されたしきい値は、継続的な排出が単一の大きなスパイクと同じくらい危険であることを反映しています。 

これらのケースは、最小在庫の単一の統一された尺度の下で、アルゴリズムがバースト枯渇と段階的枯渇の両方を正しく捕捉していることを確認します。
