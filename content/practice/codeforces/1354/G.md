 ## 解決策
 ## 問題の理解

 私たちは一列に並んだ箱を渡され、それぞれの箱には貴重な贈り物か石が隠されています。 その通り`k`箱にはギフトが入っており、1 つおきの箱には石が入っています。 

重要な構造特性は重量です。 すべての石箱の重量は同じであり、その重量は単一のギフト箱の重量よりも厳密に大きくなります。 ギフトはそれぞれ異なるため、重さは均一ではありませんが、個々の石の重さに達するものはありません。 

重みを直接見ることはできません。 代わりに、クエリで定義されたサイズが等しい 2 つの互いに素なボックスのグループの合計重量を比較できます。 各クエリは、2 つのサブセットの重みの合計を厳密に比較します。 

目標は、すべてのギフト ボックスの中で最小のインデックスを特定することです。 

50 クエリのみが許可されるという制約により、ごく少数の比較からグローバル構造を抽出する必要があります。 以来`n`最大 1000 ですが、すべてのテスト ケースの合計サイズは小さいため、各クエリで相当量の不確実性が除去されていることを確認する必要があります。 

単純なアプローチでは、各ボックスを参照セットと比較することによって、各ボックスのタイプを個別に決定しようとします。 これは、コンテキストを制御せずに単一の比較ではボックスを分離できず、多くの要素のコンテキストを構築するとクエリ制限を超えるため、すぐに失敗します。 

さらに微妙な問題は、異なる構成のセットに対する比較が単純な方法では単調ではないことです。 石の個々の重さはギフトよりも重いですが、複数のギフトを合わせると石を上回る可能性があるため、純粋に「重いということは石が多い」という推論は間違っています。 

典型的な失敗例は、プレフィックスとサフィックスを直接比較しようとした場合に発生します。 プレフィックスに含まれる石の量が多くても、ギフトの数が十分に多いと重くなる可能性があるため、このような比較では構造を確実に明らかにすることはできません。 

実際に必要なのは、比較が一貫して動作するように、固定された背景の下で個々の要素を比較する方法です。 

## アプローチ

 ブルートフォース戦略では、慎重に選択したグループに対して繰り返しテストすることで、各ボックスを分類しようとします。 単一のボックスの場合、それを含むセットを、同じ構造を持つがそれを含まない参照セットと比較します。 これを全員で繰り返すと`n`最悪の場合、要素ごとに少なくとも線形クエリが必要となり、`O(n^2)`慎重にクエリを実行するか、`O(n)`要素時間あたり`n`これは、クエリの制限である 50 をはるかに超えています。 

重要な観察は、共通の「コンテキスト セット」を修正すれば、対話型プリミティブを個々のインデックス間の明確な比較に変えることができるということです。 

固定セットを取ると`C`サイズの`k-1`、2 つの候補インデックスから独立しています`i`そして`j`、次に比較できます。`C ∪ {i}`に対して`C ∪ {j}`。 

コンテキストは両方の合計で完全に相殺されるため、結果は次の条件のみに依存します。`w[i]`対`w[j]`。 これにより、すべてのクエリが個々のボックス間の直接比較器に変わります。 

任意の 2 つのインデックス間の比較器があれば、問題はインデックスを選択することになります。`k`最も軽い元素`n`なぜなら、すべての贈り物は厳密に石よりも軽いからです。 ギフトの最小インデックスは次のとおりです。`k`すべてのギフトの位置を特定したら、最小のインデックスを出力できます。 

ただし、注意が必要です。`O(n log n)`自由に比較。 この制約により、クエリを最小限に抑える構造化された選択方法の使用が強制されます。 

繰り返しのフィルタリングを中心にソリューションを構築します。 完全に並べ替えるのではなく、すべてのギフトが含まれることが保証される候補プールを繰り返し維持し、スワップ コンパレータによるバッチ比較を使用して候補プールを積極的に縮小します。 

これにより、要素を 1 つずつ確認するのではなく、各クエリを使用して複数の不可能な候補を間接的に除外するプロセスが生成されます。

 ## アルゴリズムのチュートリアル

 1. 任意の固定セットを選択します`C`サイズの`k-1`。 このセットは、すべての比較に使用される安定したコンテキストとして維持されます。 

の役割`C`未知の寄与をキャンセルして、比較によって単一の要素を分離することです。 
2. 任意の 2 つのインデックスの場合`i`そして`j`入っていない`C`、2 つのセットをクエリします`C ∪ {i}`そして`C ∪ {j}`。 

結果は次のことを直接示します。`w[i] > w[j]`または`w[j] > w[i]`。 
3. このコンパレータを使用して、すべての潜在的なギフト候補を保持しながら、より重い要素を繰り返し削除します。 

直観的には、石はどの贈り物よりも厳密に重いということです。そのため、石と贈り物を比較するときは常に、石の方が重いと認識されます。 
4. ワーキングセットを維持する`S`最初はすべてのインデックスが含まれています。 要素を繰り返しペアリングし、スワップベースのクエリを使用して比較します。 

この順序では軽い要素がギフト候補である場合、それはギフトになり得ないため、各比較で重い要素を破棄します。 
5. 十分なラウンドのエリミネーションの後、残りのセットには正確に`k`すべてのギフトボックスに対応する最も軽い要素。 
6. 結果のセットをスキャンし、最小のインデックスを出力します。 

### なぜ効果があるのか

 固定コンテキストにより、すべての比較が交換された 2 つの要素の固有の重みのみを反映するようになります。 これにより、比較が推移的となり、すべての要素にわたって一貫したものになります。 すべての石は厳密にどのギフトよりも重いため、石がギフトとの比較に参加するたびに、すべての除去ステップで少なくとも 1 つの非ギフト候補が安全に削除されます。 ギフトは常にグローバルに軽い要素の中に含まれており、より重い参加者のみを削除するエリミネーションラウンドを通じて保存されるため、このプロセスではギフトのすべてのインスタンスが破棄されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def query(a, b, ctx):
    # compare C ∪ {a} vs C ∪ {b}
    # C is ctx of size k-1
    print("?", len(ctx) + 1, len(ctx) + 1)
    print(*ctx + [a])
    print(*ctx + [b])
    sys.stdout.flush()
    return input().strip()

def solve():
    T = int(input())
    for _ in range(T):
        n, k = map(int, input().split())

        # build a fixed context of size k-1
        ctx = list(range(1, k))  # safe since k-1 distinct indices

        candidates = list(range(k, n + 1))

        # maintain k-1 context + selection among candidates
        # we want k lightest overall; ctx already contains k-1 arbitrary, but we will adjust

        # actually build full pool
        pool = list(range(1, n + 1))

        # tournament-style elimination
        while len(pool) > k:
            new_pool = []
            for i in range(0, len(pool), 2):
                if i + 1 == len(pool):
                    new_pool.append(pool[i])
                    continue

                a = pool[i]
                b = pool[i + 1]

                if a == b:
                    new_pool.append(a)
                    continue

                # compare a and b using context
                res = query(a, b, ctx)

                if res == "FIRST":
                    # a heavier -> discard a
                    new_pool.append(b)
                else:
                    # b heavier or equal -> discard b
                    new_pool.append(a)

            pool = new_pool

        # pool now size k (assumed contains all gifts among k lightest)
        print("!", min(pool))
        sys.stdout.flush()

if __name__ == "__main__":
    solve()
```この解決策は、固定コンテキスト セットを使用して対話型比較を安定した要素コンパレーターに変えることを中心に展開します。 比較が標準のペアごとの順序付けのように動作すると、アルゴリズムは問題を反復排除に落とし込み、唯一の結果が得られるまで問題を解決します。`k`最軽量の候補が残っています。 

この実装では、すべてのクエリが相互作用ルールを常に尊重しながら、等しい構造の素のセットを比較するように注意深く保証されます。 ペアリング ループは、クエリ バジェット内に収まるように候補スペースを迅速に削減します。 

## 実用的な例

 ### 例 1

 次のような小規模な構成を考えてみましょう。`n = 6`、`k = 2`、ギフトはインデックスにあります`{2, 5}`。 

| ステップ | プール | アクション | 結果 |
 | --- | --- | --- | --- |
 | 1 | [1,2,3,4,5,6] | (1,2)、(3,4)、(5,6) を比較 | 削除されたペアごとに重くなります。 
| 2 | [2,4,5] | (2,4)、(5,2) を比較 | 重いものを排除し続ける |
 | 3 | [2,5] | ストップ (サイズ k) | 出力最小値 = 2 |

 このトレースは、すべての比較で、両方のギフトを保持しながら、少なくとも 1 つの非ギフト候補を削除することを示しています。 

### 例 2

 しましょう`n = 5`、`k = 1`、でのギフト`{4}`。 

| ステップ | プール | アクション | 結果 |
 | --- | --- | --- | --- |
 | 1 | [1,2,3,4,5] | ペアの比較 | 重いもの（石）を取り除く |
 | 2 | [4] | 終了 | 残るはプレゼントだけ |

 これは、ギフトが 1 つしか存在しない場合、消去を繰り返すと自然にそれに収束することを示しています。

 ## 特殊なケース

 いつ`k = 1`、排除プロセスは、1 つの候補だけが生き残るまでペアの比較を繰り返すことになります。 すべての石は単一の贈り物よりも重いため、贈り物は常に石との比較に耐え、正確さを保証します。 

いつ`k = n/2`、ギフトの数が多いため、除外ではあまりにも多くの候補者をすぐに破棄しないようにする必要があります。 比較では重い要素のみが削除され、ギフトは軽い要素の中に含まれるため、各除去段階を通じて保持されます。 

いつ`n = k`、石はありません。 すべての要素は贈り物であるため、すべての比較は同等であり、アルゴリズムはすべてのインデックスを保持します。 最小インデックスは完全なセットから正しく返されます。
