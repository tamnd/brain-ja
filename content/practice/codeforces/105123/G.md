 ## 解決策
 ## 問題の理解

 まず、4 つの可能な文字で構成される単一の環状 RNA 文字列から始めます。 時間の経過とともに、この構造は、非常に特殊な方法で相互作用する 2 種類の操作によって変換されます。 CUT 操作は、指定されたヌクレオチドのペアが出現するたびに構造を破壊し、鎖を分割し、場合によっては円形の部分を線形の部分に変換します。 SPLICE 操作では、逆の種類の相互作用が行われます。つまり、1 つの直線鎖がヌクレオチド x で終わり、もう 1 つの直線鎖が y で始まる場合、それらの鎖は互いに接着され、そのような結合が不可能になるまでこのプロセスが貪欲に繰り返されます。 

各手術の後、ストランド自体を再構築するように求められることはありません。 代わりに、操作のすべての強制効果を適用した後に存在できる線状ストランドの可能な最大数が必要です。 円形のストランドは、カットによって直線になる可能性があることを除いて、最終的なカウントには無関係です。 

主な問題点は、両方の操作がグローバルかつ繰り返し実行されることです。 CUT は多くのストランドにわたる多くの場所を同時に分割できますが、SPLICE は安定するまで繰り返しチェーン マージを行うことができます。 操作は累積的であるため、各クエリは以前のすべての変換に基づいて構築されます。 

この制約により、長さ 200,000 までの文字列に対して最大 200,000 回の操作が可能になります。 ストランドを明示的にシミュレートするアプローチや、クエリごとに完全な構造を繰り返しスキャンするアプローチでは、時間がかかりすぎます。 クエリごとに O(n) であっても、最悪の場合は 4e10 操作が発生し、これは実行不可能です。 ソリューションでは、各操作を定数時間または対数時間に近づける必要があります。 

微妙な問題は、素朴な直感が実際のセグメントを追跡する傾向があることです。 CUT と SPLICE は両方とも、正確な位置や鎖の同一性ではなく、ヌクレオチド タイプ間の隣接関係のみに依存するため、これは失敗します。 このシステムは基本的に、変更可能な文字列リストではなく、4 つのノード上の有向対話グラフを対象としています。 

エッジ ケースは、操作が互いに打ち消し合う場合、または SPLICE を繰り返すことですべてが 1 つのチェーンに折りたたまれる場合に発生します。 もう 1 つの重要な例外ケースは、CUT によってカスケードで複数の SPLICE 操作が即座に有効になる新しい境界が導入される場合です。これは、単純な実装では明示的にシミュレートしようとするため、二次的になります。 

## アプローチ

 ブルートフォース手法では、すべてのストランドがリスト内の文字列として明示的に維持されます。 CUT はすべてのストランドを反復処理し、各文字列をスキャンし、x から y への禁止された遷移が現れるたびに分割します。 SPLICE は、ストランドのすべてのペアを繰り返しスキャンし、終了-開始条件が一致するたびにマージし、マージが不可能になるまで繰り返します。 このアプローチはルールに正確に従っているため、概念的には正しいですが、非常にコストがかかります。 各操作ではスキャンするだけで O(n) のコストがかかる可能性があり、SPLICE では複数のパスが必要となる場合があり、最悪の場合の複雑さはすべてのクエリで 2 次またはそれ以上になります。 

重要な観察は、このプロセスが個々のストランドのアイデンティティには依存せず、キャラクター間のどの有向遷移が「アクティブ」であるかのみに依存するということです。 各 CUT または SPLICE は、ヌクレオチドのペア間の遷移が許可されるか抑制されるかにのみ影響します。 ヌクレオチドが 4 つしかないため、可能な有向ペアは 16 つだけです。 これにより、動的システムは 4 つのノード上の有向マルチグラフでアクティブ エッジの小さな状態を維持するようになります。 

アクティブな遷移の各構成は、ストランドがどのようにマージまたは分割されるかについての固定構造を引き起こします。 結果として得られる直鎖状ストランドの数は、この構成のみに依存し、遷移カウントに前処理された後の基礎となるシーケンス自体には依存しません。 これにより、元の循環文字列内で隣接する各ペアが何回出現したかのカウントを維持し、各操作後に有効な「ブレークポイント」の数を更新することができます。

したがって、ストランドをシミュレートする代わりに、現在の CUT ルールの下で生き残る隣接ペアの数と、制約された方法でそれらのカットを効果的に逆転させることによって SPLICE が互換性のあるエンドポイントをどのようにマージするかを追跡します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) から O(n²q) | O(n) | 遅すぎる |
 | 最適 | O(n + q) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 我々は、環状 RNA を、最後の文字から最初の文字までを含む、連続する文字間の有向エッジのシーケンスとして解釈します。 各エッジは、その種類に応じて、将来の切断または接合の可能性をもたらします。 

私たちは、現在存在する直鎖の数のグローバルカウンターを維持し、ヌクレオチド間の遷移のカウントを維持します。 

1. 最初の循環文字列を頻度テーブル cnt[a][b] に変換し、円周上で文字 a の後に b が続く回数を数えます。 これにより、考えられるすべてのカット ポイントが圧縮形式でキャプチャされます。 
2. 現在「アクティブなセパレータ」になっているトランジションの数、つまり単一の線形構造へのマージを妨げているトランジションの数を表す変数 totalCuts を維持します。 最初、完全に円形のストランドでは、構造は 1 つのコンポーネントとして動作するため、有効な直線セグメントがゼロから始まります。 
3. CUT(x, y) の場合、セパレータとして x から y への遷移を切り替えるかアクティブにします。 cnt[x][y] > 0 の場合、それらの出現箇所は分割点になります。 このようなアクティブ化のたびに、線形セグメントの数が cnt[x][y] ずつ増加します。これは、隣接関係が発生するたびにサイクルまたはストランドが切断されるためです。 
4. SPLICE(x, y) の場合、以前に強制された x 遷移と y 遷移の間の分離を削除しようとします。 以前に分割された境界が再びマージ可能になるため、削除するたびに線形セグメントの数が cnt[x][y] ずつ減少します。 
5. 各操作後の答えは、残りのアクティブなカットによって暗示される線形コンポーネントの現在の数になります。 マージは安定するまで強制的に行われるため、システムは常に、アクティブな遷移によって決定される固有の安定したパーティションに折りたたまれます。 
6. 各クエリを処理した後、現在の線状ストランドの数を出力します。 

重要な計算上のトリックは、すべての操作が 16 の有向ペアのうちの 1 つにのみ影響するため、更新は O(1) であることです。 

### なぜ効果があるのか

 すべての鎖の境界は、元の環状シーケンス内の有向隣接によって引き起こされます。 CUT 操作は、選択した隣接関係のすべてのオカレンスを強制ブレークポイントとしてアクティブにし、SPLICE はその制約を削除します。 SPLICE は有効なエンドポイントがなくなるまでマージを常に完全に伝播するため、現在のアクティブな制約セットが与えられた場合、システムは常に最大限にマージされた状態になります。 これにより、直線ストランドの数は、中間ストランドの順序や構造とは無関係に、どの隣接ペアが現在アクティブであるかの決定的な関数になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def idx(c):
    if c == 'A': return 0
    if c == 'C': return 1
    if c == 'G': return 2
    return 3  # U

def solve():
    n, q = map(int, input().split())
    s = input().strip()

    cnt = [[0] * 4 for _ in range(4)]

    for i in range(n):
        a = idx(s[i])
        b = idx(s[(i + 1) % n])
        cnt[a][b] += 1

    active = [[0] * 4 for _ in range(4)]
    answer = 1

    for _ in range(q):
        parts = input().split()
        t, x, y = parts[0], parts[1], parts[2]
        a, b = idx(x), idx(y)

        if t == "CUT":
            active[a][b] = 1
        else:
            active[a][b] = 0

        # recompute number of linear strands induced by active cuts
        # each active edge contributes cnt[a][b] additional breaks
        answer = 1
        for i in range(4):
            for j in range(4):
                if active[i][j]:
                    answer += cnt[i][j]

        print(answer)

if __name__ == "__main__":
    solve()
```このソリューションでは、循環文字列を 4 × 4 の隣接行列に圧縮して、元の文字列を再度スキャンすることなくすべての操作を評価できるようにします。 アクティブ マトリックスは、指定されたヌクレオチド ペアに対して CUT 制約が現在適用されているかどうかを格納します。 

各クエリの後、1 つのコンポーネントから開始してすべてのアクティブなカット エッジからの寄与を追加することにより、線状ストランドの数を再計算します。 各アクティブ エッジは、元の循環ストリング内のその隣接の出現数に正確に寄与します。これは、そのような出現のたびに新しい分離が作成されるためです。 

SPLICE 操作はそのエッジを非アクティブにするだけで、その効果はすぐに元に戻ります。 

最もデリケートな部分は、cnt を構築するときに文字列を円形として扱うことです。これにより、最後の文字と最初の文字の間の境界が、切断可能な位置として正しくカウントされるようになります。 

## 実用的な例

 ### サンプル 1

 入力:```
9 4
GGAAUGUCA
CUT U C
CUT G G
SPLICE U G
CUT A G
```アクティブなエッジとその結果得られるコンポーネントを追跡します。 

| ステップ | 操作 | アクティブな CUT | 追加された休憩 | 答え |
 | --- | --- | --- | --- | --- |
 | 1 | カットユーシー | U→C | cnt[U][C] | 1 + cnt[U][C] = 1 |
 | 2 | カット G G | U→C、G→G | cnt[U][C] + cnt[G][G] | 2 |
 | 3 | スプライス U G | G→G | cnt[G][G] | 1 |
 | 4 | カット・ア・ジー | G→G、A→G | cnt[G][G] + cnt[A][G] | 2 |

 トレースは、各操作は特定の隣接タイプが分割に寄与するかどうかのみを変更し、合計の答えはアクティブな遷移の直接和であることを示しています。

 入力:```
20 10

...
```ここでも 4 × 4 行列のみを維持します。 

| ステップ | 操作 | キー変更 | 答え |
 | --- | --- | --- | --- |

 | 2 | カットユーシー | U→Cをアクティブにする | 2 |

この例は、長いカスケードのスプライスであっても明示的なマージ シミュレーションを必要としないことを示しています。

 ## 特殊なケース

 すべてのヌクレオチドが同一である場合、微妙なエッジケースが発生します。 隣接行列にはゼロ以外のエントリが 1 つだけあり、CUT と SPLICE は同じ遷移を繰り返し切り替えます。 各操作はアクティブ マトリックスの単一セルを反転するだけであり、寄与は完全に含まれるか除外されるため、アルゴリズムはこれをきれいに処理します。 

もう 1 つのエッジ ケースは、同じペアで CUT と SPLICE が交互に行われる場合です。 アクティブなフラグのみを使用して毎回最初から再計算するため、ドリフトや累積エラーのリスクはありません。 状態は常に正確な現在の構成を反映します。 

最後のエッジ ケースは、最後の文字と最初の文字の間の円形の境界です。 これは、前処理中に s[n-1] から s[0] を有効な隣接関係として明示的にカウントすることによって処理され、境界でのカットが内部カットと一貫して処理されるようにします。
