 ## 解決策
 ## 問題の理解

 最初から最後まで優先順位に従って順序付けされた一連のタスクが与えられ、各タスクを完了するには一定量の ATP が消費されます。 ジャスミンの 1 日あたりの ATP 予算は$m$、そして彼女はタスクを繰り返すことができません。 問題は、彼女が常にすべてのタスクを考慮しているわけではないということです。 代わりに、プレフィックス長ごとに$k$、彼女は最初のものだけに注意を制限します$k$優先順位に従ってタスクを実行し、その制限されたセットの中で、ATP 予算を超過することなくできるだけ多くのタスクを完了したいと考えています。 

それぞれについて$k$、私たちは事実上、「タスクだけを取るかどうか」を尋ねていることになります。$1$を通して$k$、合計が最大となる、選択できるタスク コストの最大数はいくらですか$m$。 

重要な点は、タスクは常にプレフィックス順に実行されるが、そのプレフィックス内では任意のサブセットを自由に選択できるということです。 したがって、これはスケジューリングや順序付けの問題ではなく、増加するプレフィックスに対して繰り返される「合計制約の下での最適なサブセット」の問題です。 

制約は大きく、$n$まで$2 \cdot 10^5$。 これにより、すべてのオブジェクトに対して最適なサブセットを最初から再計算する必要が直ちに排除されます。$k$。 ナイーブ$O(n^2 \log n)$または$O(n^2)$プレフィックスを再ソートまたは再スキャンするアプローチは遅すぎます。 各ステップが対数または一定の償却時間で前の答えを更新する増分構造が必要です。 

コストのバランスが著しく不均衡な場合、微妙な問題が発生します。 たとえば、次の場合$m = 10$そしてタスクは$[1, 1, 1, 100, 1]$、その後、初期のプレフィックスでは多くの小さな選択が可能ですが、一度大きなコストが現れると、それは最適なサブセットに属さず、それでもプレフィックスセットを変更します。 世界中で利用可能な最も安価なタスクを常に選択することを前提とする誤った貪欲なアプローチは、プレフィックスの増大下で実行可能性を慎重に維持しない限り失敗します。 

## アプローチ

 各プレフィックスについて考える直接的な方法は、その要素をソートし、合計が次の値を超えるまで最小のコストを取ることです。$m$。 それは正しいことです。合計制約の下でカウントを最大化するには、より小さいコストを選択することが常に最適だからです。 ただし、すべてのプレフィックスに対してこれを再計算するということは、構造を繰り返しソートまたは再構築することを意味します。$O(n)$要素、$O(n^2 \log n)$最悪の場合の動作。 

重要な構造上の観察は、プレフィックスから移動するときに$k-1$に$k$、新しい要素を 1 つだけ追加しています。 プレフィックスの最適なセット$k$プレフィックスとは異なります$k-1$この新しい要素を含めることができ、同じ予算内でカウントを増やすのに役立つ場合は、より大きな選択された要素を削除する可能性があるためです。 

これは、選択されたタスクの動的なマルチセットを維持し、常に現在のプレフィックスに対して可能な限り最適なサブセットを表すことを示唆しています。 このための標準構造は最大ヒープです。現在選択されているすべてのタスクを保持し、それらの合計が以下の範囲内に収まるようにします。$m$。 新しいタスクを追加する場合は、それを挿入し、合計が超えた場合は、$m$、最大の要素を削除します。 最大のものを削除すると、削除ごとに合計が最も多く削減され、できるだけ多くの小さな要素が保持されるため、最適です。 

したがって、各プレフィックスは次のように更新できます。$O(\log n)$、現在の合計と選択されたタスクの数の両方を維持します。

 ## アルゴリズムのチュートリアル

 タスクは左から右に処理され、常に ATP 予算内に収まるように選択されたタスクの構造が維持されます。 

1. 空の最大ヒープと変数を初期化します。`total = 0`。 ヒープには選択されたタスクのコストが保存され、`total`それらの合計を追跡します。 
2. タスクごとに$a_k$、それをヒープに挿入し、そのコストを`total`。 これは、すべての新しいタスクを暫定的に受け入れることに相当します。これは、それがこのプレフィックスの最終的な最適なサブセットの一部であるかどうかがまだわからないためです。 
3. もし`total > m`、ヒープから最大の要素を削除し、それを次から引きます。`total`。 このステップにより実現可能性が回復します。 最大の要素を削除することは、選択したタスクの数を必要以上に減らすことができない唯一の選択肢です。これは、可能な限り多くの項目を保持しながら、最もコストのかかるタスクを犠牲にするためです。 
4. 調整後のヒープ サイズは、現在のプレフィックスに対して完了できるタスクの最大数となります。 このサイズで出力します。 
5. すべてに対してこのプロセスを繰り返します$k$1から$n$、プレフィックスごとに 1 つの回答が生成されます。 

なぜこれが機能するのかは、貪欲な交換の議論に関係しています。 どのプレフィックスでも、サイズが最適ではない実行可能なサブセットがあると仮定します。 小さい要素を除外しながら大きい要素が含まれている場合、それらを交換しても実現可能性が悪化することはなく、カウントが減少することもありません。 したがって、最適なソリューションでは常に小さい要素が優先され、新しい要素が到着すると、ヒープ不変条件によってその構造が動的に適用されます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    
    heap = []
    total = 0
    out = []
    
    for x in a:
        heapq.heappush(heap, -x)
        total += x
        
        if total > m:
            largest = -heapq.heappop(heap)
            total -= largest
        
        out.append(str(len(heap)))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```主要な実装の詳細は、負の値を通じてシミュレートされた最大ヒープの使用です。`heapq`最小ヒープのみを提供します。 保守します`total`ヒープ合計の再計算が遅すぎるためです。 

微妙な点は、オーバーフローが発生したときに常に最大の要素を 1 つだけ削除することです。 たとえ`total`はるかに上です`m`の場合、挿入ごとに 1 回の削除で十分です。最大の要素を削除した後は、残りの要素はすべてそれより小さいか等しいため、ヒープ不変条件により、新しく追加された要素の寄与分だけが容量を超過するだけであることが保証されます。

import heapq

    import sys

 ## 特殊なケース

 重要なエッジケースは、最初の要素がすでに予算を超えている場合です。 入力用`n = 3, m = 5, a = [10, 1, 1]`、ヒープは最初に次のようになります`[10]`、合計が予算を超えているため、すぐに削除し、空のヒープを残します。 の答えは、$k=1$したがって、 は 0 となり、後続の小さな要素はソリューションを最初から再構築します。 すべての挿入の後に修正ステップが続くため、アルゴリズムはこれを自然に処理します。 

もう 1 つのエッジ ケースは、多数の小さな要素が蓄積し、大きな要素が遅れて現れる場合です。 のために`m = 6, a = [1, 1, 1, 1, 1, 10]`、ヒープはサイズ 5 まで着実に増加し、その後 10 により小さな要素ではなくヒープ自体が強制的に削除され、最適な数が維持されます。 これは、ヒープには常にプレフィックスの実現可能な最小コストのサブセットが含まれるという不変条件を示しています。
