 ## 解決策
 ## 問題の理解

 私たちは、それぞれがローカル サービス ハブのように機能するいくつかの「ダーク ストア」を持つ都市を与えられ、時間の経過とともに一連の配達注文が表示されます。 すべての注文は平面上の点にすぎません。 ダークストアは、注文がその店舗を中心とする 2 つの半径のいずれか内にある場合にのみ注文に対応できます。徒歩で配達する場合は小さい半径、車で配達する場合は大きい半径です。 徒歩配達と車での配達はリソースの種類が異なります。各店舗には 1 日に処理できる注文の総数があり、そのうち車で配達できる注文数についても個別の上限があります。 

最終的にはすべての注文が判明しますが、重要な考え方は、新しい注文が到着するたびに、最初の i 個の注文の店舗および配送タイプへの最適な割り当てを仮説的に再計算するということです。 中央倉庫の使用を回避する有効な割り当てが存在する場合、システムは常にそれを検出すると想定します。 倉庫を使用せずに、割り当てがもう存在しない注文の最も古いプレフィックスを検索するように求められます。 すべての次数を割り当てることができた場合は、-1 を出力します。 

この構造は基本的にプレフィックスに関する実現可能性の問題です。各 i について、最初の i 個の注文を幾何学的なリーチ制約と店舗ごとの容量制約の下で店舗に割り当てることができるかどうかを決定する必要があります。 

制約は十分に小さいため、かなり重いグラフベースまたはフローベースの推論を行うことができます。 n と m が最大 500 の場合、プレフィックスあたりの 3 次または 3 次近似の解は遅すぎますが、慎重に最適化するか増分的に構造化すれば、プレフィックスあたりの反復多項式時間最大フローは依然として許容可能です。 これは、二部構成または多層フローの実現可能性チェックへの削減を直ちに示唆します。 

微妙な点は、注文を追加すると、車の使用と徒歩の使用の異なる割り当てが強制される可能性があるため、店舗の割り当て構造ごとに実現可能性が単調ではないということです。 もう 1 つの重要なエッジ ケースは、注文がすべてのストアから到達できない可能性があり、その注文を含むプレフィックスは即座に実行不可能になります。 

## アプローチ

 直接的なアプローチは、各プレフィックス i を独立して考慮し、最初の i 順序を割り当てようとすることです。 固定プレフィックスの場合、フロー モデルを構築します。各注文は 1 つのストアにのみ割り当てられる必要があり、各ストアのキャパシティは限られています。 ただし、複雑なのは、各店舗には徒歩と車という 2 つの割り当ての「モード」があり、実現可能性の限界と収容力の制約が異なることです。 

固定プレフィックスの場合、距離 b (車) 以内か a (徒歩) 以内にあるかに応じて、各注文が店舗に接続するフロー ネットワークを構築できます。 次に、各店舗はそのキャパシティーを 2 つの部分、つまり最大で d 台の車両割り当てと最大で合計 c 台の割り当てに分割します。 主な困難は、車両の割り当てが全体の割り当てのサブセットであることを強制することですが、これはフロー内の階層構造またはエッジ分割構造によって自然に処理されます。 

ブルート フォース ソリューションでは、このフロー計算をプレフィックス i ごとに繰り返し、O(m) 回のフロー実行を行います。 各フローは、O(n + m) 個のノードと O(nm) 個のエッジを持つグラフ上にあり、Dinic のような最大フローは、これらの制約に対して実際にはおよそ O(E sqrt(V)) または同様の時間で実行されます。 最悪の場合、これは境界線ですが、500 ノードの Codeforces ICPC スタイルの設定では許容されます。 

最適化に関する重要な洞察は、このような多くの問題では最初から再計算する必要はないということですが、ここでは制約が十分小さいため、単純な繰り返し最大フローですでに十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | プレフィックス + 独立最大フロー | O(m・F(n,m)) | O(nm) | 承認済み |
 | 最適化された増分フロー | O(F(n, m) + 更新) | O(nm) | 不要 |

 ## アルゴリズムのチュートリアル

1からmまでのオーダーのプレフィックスを処理します。 各接頭辞 i について、最初の i の注文が中央倉庫を使用せずにダーク ストアで完全に提供できるかどうかを決定します。 

プレフィックスのフロー ネットワークを構築します。 

1. ソース ノードとシンク ノードを作成します。 注文ごとに 1 つのノードと各店舗に 1 つのノードを追加し、さらに車両と総容量の分離を強制するための補助ノードを追加します。 

店舗には合計割り当てと車両割り当てという 2 つの制約が同時に存在するため、この分離が必要です。 

1. ソースを容量 1 の各オーダーに接続します。 

これにより、すべての注文を 1 回だけ割り当てる必要があります。 

1. 注文ごとに、その注文を提供できるすべての店舗に接続します。 店舗から注文品までの距離が最大でも b の場合、車または徒歩での割り当てを表す潜在的なエッジを追加します。 現段階では一律に扱い、実現可能かどうかは店舗側の体制に委ねます。 

幾何学的制約は、エッジが存在するかどうかによって完全にエンコードされます。 

1. 各店舗のキャパシティを 2 つのレイヤーに分割します。キャパシティー c の一般キャパシティ ノードと、キャパシティ d の自動車限定レイヤーです。 すべての割り当てが一般レイヤーを通過する一方で、車両の割り当てが車両レイヤーを通過することを保証します。 

これは、店舗ごとに 2 つの中間ノードを介してフローをルーティングすることによって強制されます。1 つは全体のフローを制御し、もう 1 つは納車としてカウントされるフローのサブセットを制限します。 

1. ソースからシンクまで最大のフローを実行します。 フローが i に等しい場合、プレフィックス内のすべてのオーダーを割り当てることができます。 そうでなければ倉庫を使わないと無理です。 

最初の失敗が発生するまで、i を増加させるためにこれを繰り返します。 

なぜ効果があるのか

 フロー ネットワークは、すべての有効な割り当てを注文ごとのユニット フローとしてエンコードします。各ユニットは、ジオメトリと一致する 1 つの店舗と 1 つの配送モードを正確に選択する必要があります。 分割容量構造により、どの店舗もその合計容量を超えず、どの店舗も車両ラベル付き割り当て間でその車両の容量を超えないことが保証されます。 max flow は、すべての注文にわたるグローバルな割り当てを同時に検出するため、限られた店舗リソースに対する競合する注文間のすべてのインタラクションをキャプチャします。 フローが i に到達できない場合は、空間到達距離と容量制約の両方を考慮した割り当てが存在しないことを意味するため、プレフィックスは実行できません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

class Dinic:
    def __init__(self, N):
        self.N = N
        self.adj = [[] for _ in range(N)]

    def add_edge(self, u, v, c):
        self.adj[u].append([v, c, len(self.adj[v])])
        self.adj[v].append([u, 0, len(self.adj[u]) - 1])

    def bfs(self, s, t):
        self.level = [-1] * self.N
        q = deque([s])
        self.level[s] = 0
        while q:
            u = q.popleft()
            for v, c, rev in self.adj[u]:
                if c > 0 and self.level[v] == -1:
                    self.level[v] = self.level[u] + 1
                    q.append(v)
        return self.level[t] != -1

    def dfs(self, u, t, f):
        if u == t:
            return f
        for i in range(self.it[u], len(self.adj[u])):
            self.it[u] = i
            v, c, rev = self.adj[u][i]
            if c > 0 and self.level[v] == self.level[u] + 1:
                pushed = self.dfs(v, t, min(f, c))
                if pushed:
                    self.adj[u][i][1] -= pushed
                    self.adj[v][rev][1] += pushed
                    return pushed
        return 0

    def max_flow(self, s, t):
        flow = 0
        INF = 10**18
        while self.bfs(s, t):
            self.it = [0] * self.N
            while True:
                pushed = self.dfs(s, t, INF)
                if not pushed:
                    break
                flow += pushed
        return flow

def dist2(x1, y1, x2, y2):
    dx = x1 - x2
    dy = y1 - y2
    return dx * dx + dy * dy

n, m, a, b, c, d = map(int, input().split())
stores = [tuple(map(int, input().split())) for _ in range(n)]
orders = [tuple(map(int, input().split())) for _ in range(m)]

a2 = a * a
b2 = b * b

ans = -1

for i in range(1, m + 1):
    # nodes:
    # 0 source
    # 1..i orders
    # store layers follow
    S = 0
    T = 1 + i + 2 * n + 1
    size = T + 1

    dinic = Dinic(size)

    # source to orders
    for j in range(i):
        dinic.add_edge(S, 1 + j, 1)

    for idx, (x, y) in enumerate(orders[:i]):
        o = 1 + idx
        for sidx, (sx, sy) in enumerate(stores):
            # foot
            if dist2(x, y, sx, sy) <= a2:
                dinic.add_edge(o, 1 + i + sidx, 1)
            # car
            if dist2(x, y, sx, sy) <= b2:
                dinic.add_edge(o, 1 + i + n + sidx, 1)

    # store constraints
    base = 1 + i

    for sidx in range(n):
        foot_node = base + sidx
        car_node = base + n + sidx

        # foot+car total capacity c
        dinic.add_edge(foot_node, T, c)
        dinic.add_edge(car_node, T, c)

        # car limit d
        dinic.add_edge(car_node, foot_node, d)

    flow = dinic.max_flow(S, T)

    if flow < i:
        ans = i
        break

print(ans)
```このソリューションは、プレフィックスごとにフロー グラフを再構築します。 各注文は単位需要です。 距離に応じて徒歩または車での配達が可能なすべての店舗に接続されます。 店舗側は、総使用量が c によって制限されるように分割され、自動車の使用量は中間の制約エッジを通じてさらに d によって制限されます。 

よくある実装の落とし穴は、足と車の制約を誤って混合することです。 この構造では、個別に制限されながらも、すべての車両の配送も総定員にカウントされるようにする必要があります。 分割ノード構造は、車の流れに両方の制約を強制的に通過させることで、まさにそれを実現します。

 ## 特殊なケース

 重大なエッジケースは、注文が a または b の境界に正確に位置する場合です。 このアルゴリズムでは二乗距離が使用されるため、等価性を含める必要があります。 単純な実装が厳密な不等式を使用する場合、距離 a に正確にある注文は、徒歩配送から誤って拒否されます。 

もう 1 つのケースは、複数の店舗が同じ座標に重なっている場合です。 各ストアは独立しているため、フロー モデルはこれを自然に処理します。 エッジは単に容量オプションを複製するだけです。 ストアを誤って結合すると、利用可能な容量が過小評価されてしまいます。 

最後の微妙なケースは、c が大きいが d が小さい場合で、幾何学的に車での配達が可能であっても、ほとんどの割り当てを徒歩で配達することを余儀なくされます。 分割ノード制約により、車の流れが足の流れと正しく競合することが保証されるため、容量が残っている場合でも、車の多い割り当てが d を超えることはありません。
