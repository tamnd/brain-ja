 ## 解決策
 ## 問題の理解

 各プロジェクトは、Polycarp の現在の評価が十分に高い場合にのみ利用可能になるアクションと考えることができます。 プロジェクトを開始すると、彼の評価は上がったり下がったりすることがありますが、いかなる時点でもマイナスになることは決して許されません。 目標は、評価を最大化することではなく、できるだけ多くのプロジェクトを選択し、それらの有効な実行順序を見つけて、要件が満たされたときに選択したすべてのプロジェクトを開始できるようにすることです。 

困難は、プロジェクトが独立していないという事実から生じます。 1 つのプロジェクトを完了すると評価が変更されるため、後で実行可能になる他のプロジェクトも変わります。 要件は低いが、マイナスの報酬が大きいプロジェクトでも、他の多くのプロジェクトが可能になる場合は、足がかりとして役立つ可能性があります。 逆に、より優れたシーケンスへのアクセスをブロックする場合、高報酬のプロジェクトは使用できなくなる可能性があります。 

制約は十分に小さいため、サブセットに対する直接的な指数関数的検索は理論的には可能ですが、完全に非現実的です。 最大 100 のプロジェクトでは、サブセットベースのアプローチですでに効果が得られます。$2^{100}$可能性があり、それぞれが有効な順序をチェックする必要がありますが、これは実行可能な計算をはるかに超えています。 

要件や報酬による分類のみに基づいた貪欲な戦略も失敗します。 ローカルで問題があると思われるプロジェクトは、後で他のプロジェクトのロックを解除する必要がある場合があります。 同様に、常に最小の要件を最初に採用すると、たとえ別の早期注文が機能したとしても、残りのプロジェクトが使用できない状態に評価が閉じ込められる可能性があります。 

要件が低いプロジェクトが大きなマイナスの影響を与える場合、微妙な失敗のケースが発生します。 早すぎると、スキップすると合計セットが大きくなる可能性があっても、将来のプロジェクトに到達できなくなる可能性があります。 別の障害モードは、要件の高いポジティブ プロジェクトが不必要に延期され、早期に使用できたにもかかわらずアクセスできなくなる場合に発生します。 

## アプローチ

 ブルートフォースの観点は、プロジェクトのすべてのサブセットを試し、全体を通して評価をマイナスにしない順序が存在するかどうかを確認することです。 各サブセットについて、すべての順列をシミュレートすることもできますが、順列を無視しても、実行可能性をチェックするだけですでに順序付けの決定に依存します。 と$n = 100$、サブセットの数は$2^{100}$、サブセットごとの一定時間の実現可能性チェックさえ不可能です。 

重要な観察は、完全な注文をグローバルに修正する必要がないということです。 その代わりに、実現可能性を維持しながら、部分的な順序を貪欲に構築できます。 現時点では、現在の評価によって要件が満たされている利用可能なすべてのプロジェクトの中から、システムを「最も柔軟な」状態にするプロジェクトを選択したいと考えています。 

これにより、効果に基づいてプロジェクトを 2 つのタイプに分割するという標準的な変換が行われます。 評価を高めるプロジェクトは、将来の実現可能性を向上させるだけであるため、一度利用可能になった後は本質的に安全です。 評価を下げるプロジェクトは将来の選択肢を減らすため危険であり、慎重に扱う必要があります。 

この構造は、優先順位を付けた貪欲な戦略を示唆しています。つまり、可能な限り常に安全な (マイナスの利益がない) プロジェクトをすべて採用し、リスクのあるプロジェクトの中から、将来の実現可能性に最も悪影響を及ぼさないものを慎重に選択します。 これを正式化するために、使用可能なプロジェクトに対する優先キューを維持しながら、要件の昇順にプロジェクトを処理します。 ポジティブなプロジェクトはすぐに採用されますが、ネガティブなプロジェクトは、将来の困難なプロジェクトにアクセスできるように保存された方法で選択されます。 

本質的な削減は、すでに選択したプロジェクトを再検討する必要がなくなることです。 プロジェクトが適格になり、最適に採用されると、その効果は現在の評価に完全に吸収され、二度と競争することはありません。

 ## アルゴリズムのチュートリアル

 要件に応じてプロジェクトを分類します$a_i$。 これにより、評価が上がるにつれて、新しいプロジェクトが制御された単調な方法で利用可能になることが保証されます。 

現在要件は満たされているがまだ採用されていないすべてのプロジェクトに対して最大ヒープ (優先キュー) を維持します。 ヒープの順序は次のとおりです。$b_i$、即時に最大の利益をもたらすプロジェクトを優先します。 

また、ソートされたプロジェクトのリストに対するポインターも維持し、新しくロック解除されたプロジェクトが実行可能になるとすぐにヒープに継続的に追加します。 

アルゴリズムは次のように進行します。 

1. 電流定格を次のように初期化します。$r$、答えをゼロに設定し、プロジェクトを次の基準で並べ替えます。$a_i$。 

並べ替えにより、プロジェクトの可用性と評価の成長が調整されるため、段階的にロックを解除できます。 
2. プロジェクトを昇順にスキャンします。$a_i$、要件が最大でも現在の評価であるすべてのプロジェクトを、 によってキー設定された最大ヒープにプッシュします。$b_i$。 

このヒープは、現在試行が許可されているすべてのプロジェクトを表します。 
3. ヒープが空で新しいプロジェクトを追加できない場合は、プロセスを停止します。 

この時点で、現在の評価状態では残りのプロジェクトに到達できません。 
4. 最も高いプロジェクトを抽出します$b_i$ヒープから取り出して実行します。 評価を上げる$b_i$そして答えを増やします。 

最良の即時利益を選択することで、より良いオプションが存在する場合に、将来の柔軟性を不必要に低下させることがなくなります。 
5. 評価を上げると新しいプロジェクトのロックが解除される可能性があるため、プロジェクトの実行後、スキャン手順を繰り返します。 

たとえプロジェクトにマイナスの影響があったとしても、順序付け効果は非常に重要です。$b_i$、それが利用可能な最良のオプションである場合は、引き続き選択される可能性があります。 ただし、ヒープは、有益な選択を優先して、そのような有害な選択を可能な限り遅らせることを保証します。 

維持される不変条件は、すべての段階で、現在実行可能なすべてのプロジェクトの中で、要件制約に決して違反せず、即時の評価への影響という点で最も制限の少ないプロジェクトを常に選択するということです。 これにより、プロジェクトが最適なソリューションの一部である場合、より悪い選択を強いることなく、時期尚早に除外されないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, r = map(int, input().split())
    projects = []
    for _ in range(n):
        a, b = map(int, input().split())
        projects.append((a, b))
    
    projects.sort()
    
    import heapq
    
    i = 0
    cur = r
    heap = []
    ans = 0
    
    while True:
        while i < n and projects[i][0] <= cur:
            heapq.heappush(heap, -projects[i][1])
            i += 1
        
        if not heap:
            break
        
        b = -heapq.heappop(heap)
        
        if cur + b < 0:
            continue
        
        cur += b
        ans += 1
    
    print(ans)

if __name__ == "__main__":
    solve()
```実現可能性が段階的に処理されるように、実装は要件による並べ替えに依存しています。 ヒープストアが否定されました$b_i$値を指定して最大ヒープをシミュレートし、最も有益なプロジェクトを常に最初に考慮するようにします。 

小切手`cur + b < 0`評価がゼロ未満になるような無効な実行を防ぎます。 プロジェクトが要件の点で実行可能であっても、その効果が依然としてグローバル制約に違反する可能性があるため、この保護手段が必要です。

## テストケース```python
import sys, io

def solve():
    input = sys.stdin.readline
    n, r = map(int, input().split())
    projects = []
    for _ in range(n):
        a, b = map(int, input().split())
        projects.append((a, b))
    projects.sort()

    import heapq
    i = 0
    cur = r
    heap = []
    ans = 0

    while True:
        while i < n and projects[i][0] <= cur:
            heapq.heappush(heap, -projects[i][1])
            i += 1
        if not heap:
            break
        b = -heapq.heappop(heap)
        if cur + b < 0:
            continue
        cur += b
        ans += 1

    return ans

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return str(solve())

# provided sample
assert run("3 4\n4 6\n10 -2\n8 -1\n") == "3"

# all positive chain
assert run("3 1\n1 2\n2 3\n3 4\n") == "3"

# negative forcing skip
assert run("3 5\n5 -10\n5 1\n5 1\n") == "2"

# tight ordering requirement
assert run("4 1\n1 2\n2 -2\n2 2\n3 1\n") == "3"

# no reachable project
assert run("2 1\n5 1\n6 1\n") == "0"

 ## 特殊なケース

 一般的な失敗ケースは、初期のネガティブ プロジェクトが利用可能であるものの、必要ではない場合に発生します。 単純な貪欲な人は、すぐにそれらを受け入れてしまい、評価を下げ、その後の有益なプロジェクトへのアクセスをブロックする可能性があります。 ヒープベースの順序付けは、より良い代替手段が存在しないまで、そのような決定を遅らせます。 

もう 1 つのエッジ ケースは、悪影響を与えるプロジェクトを除いて、最初は実行可能なプロジェクトがない場合です。 アルゴリズムは、そのプロジェクトが唯一の選択肢である場合にのみそのプロジェクトを採用することを保証する必要があります。これは、評価が更新されるたびに利用可能かどうかを繰り返し確認することで保証されます。
