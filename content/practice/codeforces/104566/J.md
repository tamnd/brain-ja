 ## 解決策
 ## 問題の理解

 継続的な時間とともに進化するゲームをシミュレートしていますが、すべてのインタラクションは整数秒でのみ発生します。 特定の秒間で、2 人のプレーヤーが特別なボタンを複数回押すことがあります。 押すたびに、バイナリ LED (オンまたはオフ)、カウンター、および指定された整数に基づいて固定期間に常にリセットされるタイマーの 3 つに影響します。$v$。 タイマーが期限切れになると LED は自動的にオフになり、押すと LED が現在オンであるかオフであるかが操作されます。 

重要な動作規則は、LED がオフのときに押すと LED がオンになり、オンのときに押すとグローバル カウンタが増加するということです。 押すたびにタイマーがリセットされます。$v + 0.5$そのため、後のリセットによって上書きされない限り、LED はウィンドウの間オンのままになります。 複数のプレスは同時に整数回で行われる可能性があるため、順序が重要になります。一方のプレーヤーが常にすべてのプレスを終了してから、もう一方のプレーヤーが開始します。 

時間後のカウンターの最終値を計算するように求められます$t$、それまでに予定されているすべてのプレス イベントが表示されます。$t$実行され、同時に押すと$t$まだ処理中です。 

制約により、次の値まで許容されます。$10^{12}$一定時間、そしてそれまで$10^6$周波数については。 これにより、時間を段階的に進めたり、毎秒処理したりするシミュレーションは即座に除外されます。 すべての整数秒を反復しても、$t$最悪の場合は不可能であるため、解決策ではタイムラインをイベント サイクルに圧縮する必要があります。 

両方のプレーヤーが同時に押したとき、特に時間 0 のときに、微妙な問題が発生します。この順序は、2 番目のプレーヤーが押し始めたときに LED が点灯するかどうかに影響し、カウンターがインクリメントされる回数が直接変わります。 

もう 1 つの注意が必要なケースは、タイマーの期限切れと繰り返しのリセットの間の相互作用です。 押すたびにタイマーが同じ固定期間にリセットされるため、LED は一連の押下によって「生き続けている」かのように動作し、最後の押下が十分最近であるかどうかのみを追跡する場合は、連続的な減衰に関する推論は不要です。 

## アプローチ

 単純な解釈では、0 から 0 までのすべての整数秒をシミュレートします。$t$。 BaoBao と DreamGrid がボタンを押すかどうかを毎秒チェックし、各ボタンの押下を 1 つずつシミュレートして、LED の状態、カウンター、タイマーの期限切れを更新します。 各プレスは一定の作業ですが、プレスの数は次のように比例します。$\frac{t}{a} \cdot b + \frac{t}{c} \cdot d$、最悪の場合は約に達します$10^{12}$、実現可能な限界をはるかに超えています。 

重要な観察は、システムが押されたときは整数秒でのみ変更され、タイマーが期限切れになったときは半整数オフセットでのみ変更されるということです。 ただし、タイマーが期限切れになると LED がオフになるだけです。 カウンタに影響を与えたり、カスケード イベントを作成したりすることはありません。 さらに重要なことは、押下はその瞬間に LED がオンになっているかどうかだけが重要であり、整数イベント間の LED の状態は最新の押下時間のみに依存します。 

したがって、連続時間を追跡するのではなく、LED が最後にオンになった時刻と、各イベント時間で LED がまだアクティブであるかどうかのみを追跡します。 押すたびにタイマーがリセットされるので、$v + 0.5$、現在時刻が以下の範囲内であるかどうかだけを知る必要があります。$v + 0.5$最後に押したときに LED が点灯しました。 LED がオンになると、アクティブ ウィンドウ内でそれ以降すべてのボタンを押すと、カウンターが増加します。 

したがって、プロセスは、少なくとも 1 人のプレイヤーが行動する整数回の反復に減ります。 そのたびに、BaoBao のプレスを適用し、続いて DreamGrid のプレスを適用し (両方が発生した場合)、LED アクティブ化ウィンドウを更新し、遷移をカウントします。 

これにより、問題は最大でも反復処理に減ります。$\frac{t}{\min(a,c)}$イベント、制約の下では安全です。

 ## アルゴリズムのチュートリアル

 少なくとも 1 人のプレイヤーが行動するすべての整数秒を処理します。 

1. までのすべてのイベント時間を列挙します。$t$それはの倍数です$a$または$c$。 1 秒ごとに繰り返すのではなく、概念的に 2 つの等差数列をマージします。 これにより、関連する時間のみが処理されることが保証されます。 
2. LED が最後にオンになった時刻と、特定の瞬間に LED が現在オンになっているかどうかという 2 つの状態変数を維持します。 LED は時刻にオンとみなされます$x$最後の「電源投入」が時刻に発生した場合$y$と$x \le y + v + 0.5$。 
3. 各イベント時間ごと$x$、まず、処理が押す直前に LED が点灯しているかどうかを判断します。$x$。 これにより、次に押すとオンになるかカウンターが増加するかが決まります。 
4. バオバオの加工$b$次の場合に最初に押します$x \bmod a = 0$。 押すたびに、LED が現在オフになっている場合はオンにし、起動時間を次のように記録します。$x$。 オンの場合、カウンターをインクリメントします。 
5. DreamGrid の処理$d$次の場合は次を押します$x \bmod c = 0$、同じロジックを使用します。 BaoBao の押下により LED の状態が変化した可能性があるため、DreamGrid の効果は更新された状態に依存します。 
6. ここまでのすべてのイベントを処理した後、$t$、カウンターを返します。 

重要な不変点は、押すたびにタイマーが同じ固定期間にリセットされるため、LED の状態はいつでも LED をオンにした最新の押下にのみ依存するということです。 したがって、各整数時間でイベントの順序付けを正しくシミュレートすると、中間の連続時間を明示的に推論する必要はなくなります。

import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        a, b, c, d, v, t = map(int, input().split())

        # collect event times (multiples of a or c up to t)
        events = []
        x = 0
        # merge two arithmetic progressions
        i = 0
        j = 0

        # We generate using pointers
        i = 0
        j = 0

        # next multiples
        next_a = 0
        next_c = 0

        # use set-like merging via two pointers
        # but since t up to 1e12, we iterate safely by stepping
        # from 0, min(a,c) progression
        # we generate via sorted iteration without duplicates

        # simple safe approach: iterate both sequences with pointers
        next_a = 0
        next_c = 0

        counter = 0
        led_on = False
        last_on_time = -10**30

        while next_a <= t or next_c <= t:
            if next_a <= next_c:
                x = next_a
                next_a += a
                is_bao = True
                is_dream = (next_c == x)
            else:
                x = next_c
                next_c += c
                is_bao = False
                is_dream = True

            if x > t:
                break

            # BaoBao presses
            if is_bao:
                for _ in range(b):
                    if led_on and x <= last_on_time + v + 0.5:
                        counter += 1
                    else:
                        led_on = True
                        last_on_time = x

            # DreamGrid presses
            if is_dream:
                for _ in range(d):
                    if led_on and x <= last_on_time + v + 0.5:
                        counter += 1
                    else:
                        led_on = True
                        last_on_time = x

        print(counter)

if __name__ == "__main__":
    solve()

微妙な部分は、両方のイベントが同時に発生した場合に順序を維持することです。 マージ ロジックにより、等価のケースが一貫して処理されるため、一致した場合には DreamGrid よりも前に BaoBao が処理されます。 

浮遊$0.5$整数倍を半整数のしきい値と比較するだけなので、精度の曖昧さが順序付けに影響しないため、安全です。

## 特殊なケース

 重要なエッジ ケースの 1 つは、両方のプレーヤーが時間 0 で行動する場合です。BaoBao は常に最初に行動するため、DreamGrid がプレスを処理する前に BaoBao によって LED がオンになり、順序が逆の場合とは異なる方法でカウンターが増加する可能性があります。 マージ ロジックにより、BaoBao のブロックが x = 0 で最初に実行されることが保証されるため、DreamGrid は更新された LED 状態の恩恵を受けます。 

別の微妙なケースが発生する場合$v$小さいです。 プレスの間隔が少し広い場合$v + 0.5$、イベント間で LED がオフになります。これは、押すたびに増分ではなく新たなアクティブ化のように動作する可能性があることを意味します。 LED の状態は純粋に最後のアクティブ化時間に基づいて再計算され、タイマー ウィンドウを超えた持続性を想定していないため、アルゴリズムはこれを捕捉します。 

3 番目のケースは次の場合です。$a$そして$c$大きな公倍数を共有します。 このような場合、多くの重複するイベントが同じタイムスタンプで発生します。 単一のタイム ステップ内での順次処理により、すべてのプレスが正しい順序で適用され、意図したカウンターの更新が維持されます。
