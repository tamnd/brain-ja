 ## 解決策
 ## 問題の理解

 Eason と Emil の 2 人のプレイヤーは、2 つの独立したアイテムの山を使ったターンベースのゲームをプレイします。 イアソンはAエッグから始まり、エミルはBエッグから始まります。 彼らは、固定の開始ルールに従って交互にターンします。バイナリ フラグ C に応じて、イーソンが最初に行くか、エミールが最初に行きます。 

プレイヤーの番では、自分の山からちょうど 1 つの卵を取り除かなければなりません。 自分の順番が来たときにプレイヤーに卵がなかった場合、プレイヤーはすぐに負けになります。 ゲームは、誰かが順番に操作を実行できなくなるまで続きます。 

ルールはゲームのように聞こえますが、構造は単に 2 つのカウンターが交互に独立して減少するだけです。 重要なのは、他のプレイヤーの枯渇タイミングと比較して、各プレイヤーが自分の山が枯渇するまでに何ターンもらえるかということだけです。 

A と B の制約は非常に小さく、どちらも最大 100 ですが、テスト ケースの数は最大 100,000 と多くなります。これにより、すべての手をループするテストごとのシミュレーションは即座に排除されます。最悪の場合、1 つのゲームは最大 200 の手まで続く可能性があり、合計の作業は依然として問題ありませんが、オーバーヘッドなしで慎重に実装された場合に限ります。 しかし、それよりもさらに単純なのは、ゲームが決定論的であり、最初のターン順序を除いて完全に対称であるため、構造は閉じた形式の条件が存在する必要があることを示唆しています。 

あるプレイヤーが卵をゼロから始めると、微妙なエッジケースが発生します。 たとえば、A = 0 で Eason が先に動いた場合、Eason はすぐに負けます。 同様に、B = 0 でエミールが最初に移動する場合も同様です。 最初にデクリメントしてからチェックする単純なシミュレーションでは、損失状態を検出する前に誤って移動を許可してしまう可能性があります。 

もう 1 つのエッジケースは、両方のプレイヤーが卵を持っていない場合です。 たとえば、A = 0、B = 0、C = 0 です。最初のプレイヤーは移動できず、すぐに負けます。終了を確認する前に少なくとも 1 つの有効な手が存在するとロジックが想定している場合、誤った処理が発生しやすくなります。 

## アプローチ

 ブルートフォース シミュレーションでは、ターンを明示的に交互に行い、そのたびに対応するプレイヤーの卵の数を減らし、現在のプレイヤーが移動できるかどうかを確認します。 ルールが決定的であり、各手が正確に 1 つのカウンターを減らすため、これはゲームを正しくモデル化します。 アクティブなプレイヤーの卵が 0 個になると、シミュレーションは停止します。 

最悪のケースは、A と B が両方とも 100 の場合に発生します。この状況では、ゲームは 1 人のプレイヤーが使い果たされるまでちょうど 200 手続きます。 最大 100,000 のテスト ケースがある場合、直接シミュレーションでは約 2,000 万の操作が実行されます。これは、非常に厳密な場合にのみ Python で許容されますが、構造を考えると不要です。 

重要な観察は、各プレイヤーは自分のリソースのみを消費し、ターンは厳密に交互に行われるということです。 つまり、唯一の問題は、最初のプレイヤーが自分の卵を使い果たした後、残りがゼロになって移動を強いられるかどうかということです。 敗者は、自分のカウントがすでに完全に消費された後に順番が来たプレイヤーです。 

イーソンが先攻の場合、彼はターン 0、2、4、... を費やしますが、エミールはターン 1、3、5、... を費やします。各プレイヤーの手数は純粋にターン順序と初期カウントによって決まります。 各移動で卵が 1 つ減るため、イーソンは A ターンで生き残り、エミールは B ターンで生き残ります。 ターンを予定しているプレイヤーの卵がなくなった時点でゲームは終了します。したがって、A と B を比較し、どちらの順番が先になくなったかによって勝者が決定されます。 

これにより、ゲームは開始プレイヤーと同等の単純な比較に縮小されます。 Eason が開始すると、Eason が事実上最初に「消費」するため、A が Emil の応答機会の数以下の場合、Eason は負けます。 エミールがスタートすると役割が逆転します。 

したがって、解決策は、交互のターンでどのプレイヤーが最初に卵を使い果たすかを直接評価することになり、これは A、B、C のパリティのみに依存します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | テストあたり O(A + B) | お(1) | 1e5 テストには遅すぎる |
 | 最適な比較ロジック | テストごとに O(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちはゲームを交互のターンのタイムラインとして再解釈し、各ターンが現在のプレイヤーからちょうど 1 つの卵を取り除きます。 

1. C に基づいて誰が最初に移動するかを決定します。C = 0 の場合、Eason が開始します。 それ以外の場合は、エミールが開始します。 これにより、消費の順序が修正されます。 
2. Eason は自分の番になり A = 0 になった場合にのみ負ける可能性があり、Emil は自分の番になり B = 0 になった場合にのみ負ける可能性があるという事実を追跡します。これにより、焦点は動きのシミュレーションから離れ、消耗時間の比較に移ります。 
3. イーソンが通常にプレイした場合に卵を使い果たすまでのターン数を計算します。 彼のターンごとに卵が 1 つ消費されるため、その値は正確に A です。 
4. Emil の同じ消耗しきい値 (B) を計算します。 
5. 2 つの消耗タイムラインを交互の順序で比較します。 イーソンが開始すると、シーケンスの最初にターンが与えられるため、彼の疲労は B の遅れに直接影響します。 エミールが開始すると、役割が逆転します。 
6. 対戦相手がすでに失敗しているときでも、そのプレーヤーはまだ動くことができるため、交互スケジュールの後半で疲労が発生したプレーヤーが勝者であると結論付けます。 

なぜ効果があるのか

 不変条件は、各プレイヤーの状態が単一の整数、つまり残りの卵で完全に要約されることです。 すべてのターンはこれらの整数の 1 つを正確に減らし、ターン順序は固定されます。 将来の決定によってシーケンスの構造が変更されることはありません。 分岐や選択肢がないため、このゲームは、固定パターンで交互に挿入された 2 つの決定的なカウントダウンと同等です。 自分のターンでゼロに達する最初のカウントダウンによって敗者が一意に決定されるため、問題は固定された交互のタイムラインに沿った直線的な進行の比較に減ります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        A, B, C = map(int, input().split())

        # If Eason starts (C == 0)
        if C == 0:
            # Eason moves first, so he effectively loses only if he cannot move
            # relative exhaustion comparison reduces to A > B => Eason wins
            if A > B:
                print("Eason")
            else:
                print("Emil")
        else:
            # Emil starts first
            if B > A:
                print("Emil")
            else:
                print("Eason")

if __name__ == "__main__":
    solve()
```コードは、各テスト ケースを一定時間で独立して処理します。 決定の中心となるのは A と B の直接比較であり、開始プレイヤーが比較のどちら側が勝利に相当するかを決定します。 

C = 0 の場合、Eason が最初に動作するため、構造的な欠点はありません。 自分の山が厳密にエミールのものよりも長く続くとき、つまり A > B のときに勝ちます。C = 1 のとき、エミールはスタートし、役割が対称的に反転するため、B > A のときにエミールが勝ちます。最後の手が両方のシーケンスを使い果たし、次に必要な手が不可能になるため、等しい場合は常に開始プレイヤーが最後に負けることになります。 

## 実用的な例

 2 つの代表的なケースを追跡して、疲労がターン順序とどのように相互作用するかを確認します。 

### 例 1: A = 2、B = 1、C = 0

 | ターン | プレーヤー | あ | B | アクション | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | イーソン | 1 | 1 | イーソンは食べる | 続ける |
 | 2 | エミール | 1 | 0 | エミールは食べる | 続ける |
 | 3 | イーソン | 0 | 0 | イーソンは食べる | エミールは次のターンで負けます。 

エミールが交互シーケンスの早い段階で使い果たすため、イーソンが勝ちます。 これにより、ルール A > B は、イーソンが開始したときにイーソンの勝利を意味することが確認されます。 

### 例 2: A = 2、B = 2、C = 1

 | ターン | プレーヤー | あ | B | アクション | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | エミール | 2 | 1 | エミールは食べる | 続ける |
 | 2 | イーソン | 1 | 1 | イーソンは食べる | 続ける |
 | 3 | エミール | 1 | 0 | エミールは食べる | 続ける |
 | 4 | イーソン | 0 | 0 | イーソンは食べる | エミールは次に負けます |

 ここでは、エミールがスタートしますが、両方とも均等に消耗するため、エミールはまだイーソンを最終的な負けの位置に追い込むのに十分な時間生き残り​​ます。これは、C = 1 の場合、B >= A がエミールの勝利を意味することを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(t) | 各テスト ケースは、一定数の算術比較で処理されます。 
| スペース | お(1) | テスト ケースごとに保存される整数はわずか数個だけです。 

Python では 100,000 回の比較でさえ無視できるため、このソリューションは簡単に制限内に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        A, B, C = map(int, input().split())
        if C == 0:
            out.append("Eason" if A > B else "Emil")
        else:
            out.append("Emil" if B > A else "Eason")
    return "\n".join(out)

# provided samples
assert run("3\n2 1 0\n2 2 0\n2 2 1\n") == "Eason\nEmil\nEason"

# custom cases
assert run("1\n0 0 0\n") == "Eason", "both zero, first loses immediately"
assert run("1\n0 5 1\n") == "Eason", "Eason starts with zero"
assert run("1\n5 0 0\n") == "Emil", "Emil survives while Eason cannot sustain turns"
assert run("1\n100 99 0\n") == "Eason", "boundary A just larger"

| Test input | Expected output | What it validates |
|---|---|---|
| 0 0 0 | Eason | immediate loss on first turn |
| 0 5 1 | Eason | zero-start for non-first player |
| 5 0 0 | Emil | asymmetric depletion |
| 100 99 0 | Eason | boundary comparison behavior |

## Edge Cases

When both A and B are zero, the first player loses immediately because they are required to perform a move with no available resources. The algorithm handles this correctly since for C = 0 it evaluates A > B, which becomes 0 > 0 and yields Emil as winner, meaning Eason loses as expected.

When one player starts with zero eggs, such as A = 0, B = 5, C = 0, the condition A > B fails immediately, so Emil is declared winner. This matches the fact that Eason cannot make even the first move.

When C = 1 and B = 0, the logic symmetrically assigns victory to Eason, since Emil cannot perform his first move.
