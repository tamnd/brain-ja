 ## 解決策
 ## 問題の理解

 いくつかの独立した正の整数のペアが与えられます。 各ペアに対して、決定論的変換を繰り返し適用します。つまり、2 つの数値のうち大きい方を特定し、そこから小さい方を減算します。 両方の数値が等しい場合は、一方から他方を減算すると、すぐにゼロが生成されます。 

各操作は数値の少なくとも 1 つを厳密に減少させ、少なくとも 1 つの成分がゼロになるまで継続します。 タスクは、入力ペアごとに、終了までにそのような減算演算が何回発生するかを計算することです。 

この制約では、各値が 10^9 までの最大 1000 個のペアが許可されます。 各減算を 1 つずつシミュレートするソリューションは、ステップごとの線形作業に低下する可能性があります。 連続するフィボナッチ数のペアなどの最悪の場合、演算の数は数値自体の大きさに比例するため、直接シミュレーションは完全に不可能になります。 

数値が等しい場合、微妙なエッジケースが発生します。 たとえば、(5, 5) から開始して、プロセスは 1 つの操作を実行し、すぐに (0, 5) に到達します。 比率が厳密に減少することを前提とする推論、または不均等な減少のみを考慮する推論では、この終了動作を明示的に考慮する必要があります。そうしないと、最終ステップ数で 1 つずれたエラーが発生する危険があります。 

## アプローチ

 直接シミュレーションはプロセスを正確に模倣します。 各ステップで、大きい値から小さい値を減算し、カウンターをインクリメントします。 これはルールに忠実に従っているので正しいですが、そのコストは必要な減算ステップの数によって異なります。 

重要な問題は、このプロセスには非常に多くの手順が必要になる可能性があることです。 最悪の場合、一方の数値が他方の数値よりわずかに大きいだけの場合、各演算により大きい方の値がわずかに減ります。 これにより、より大きな数値に比例した更新の連鎖が発生しますが、これは 10^9 までの値の許容範囲をはるかに超えています。 

重要な観察は、減算を繰り返しても小さい数値は変更されず、大きい数値は大幅に大きいままであるということです。 代わりに、大きい数値がその値を下回るまで、同じ値を繰り返し減算します。 これはまさに整数の除算の動作です。 a が b よりはるかに大きい場合は、1 つの概念ブロックで Floor(a / b) の減算を実行し、a を a % b に削減します。 これはユークリッド アルゴリズムで使用されるのと同じ変換ですが、圧縮した減算の数も累積する点が異なります。 

大きい値を小さい値に対する剰余で繰り返し置き換え、その商を答えに加算します。 このプロセスは、1 つの値がゼロになるまで継続します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ユークリッドジャンプ (除算最適化) | ペアあたり O(log max(a, b)) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

1. 最初の値が常に大きい値になるようにペアを処理します。 スワッピングにより、常に一貫した方向でリダクションが実行されるため、減算する回数の推論が簡素化されます。 
2. 小さい方の値がゼロの場合は、直ちに停止します。 それ以上の操作はできないため、累積されたカウントはすでに最終的なものになります。 
3. 整数除算を使用して、小さい値が大きい値に何倍適合するかを計算します。 この商は、大きい値が小さい値を下回るまでに単純なプロセスが実行する減算演算の回数を正確に表します。 
4. この商を操作の累計に加算します。 これにより、最終状態を変えることなく、繰り返される多数の単一減算が 1 つの算術ステップに圧縮されます。 
5. 大きい値を小さい値を法とした剰余で置き換えます。 これは、これらの減算をすべて一度に実行した後の状態を反映しています。 
6. 必要に応じて、大きい値が常に最初になるように役割を再度交換し、プロセスを繰り返します。 

この反復リダクションはユークリッド アルゴリズムを反映していますが、gcd の進行状況を追跡するだけでなく、各リダクション ステージで実行された商ステップの合計数も累積している点が異なります。 

### なぜ効果があるのか

 a が b より大きい場合、減算プロセスは、a が b より小さくなるまで、(a, b) を (a - b, b)、次に (a - 2b, b) に繰り返し変換します。 このようなステップの数は正確にfloor(a / b)であり、結果の値はa mod bとなります。 すべての減算では、この段階では小さい数が変化しないという不変条件が維持されるため、シーケンス全体を除算に圧縮しても、異なる構造状態が誤ってスキップされたりマージされたりすることはありません。 したがって、このプロセスは、ユークリッド還元中に発生するすべての商を合計することと同等です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_pair(a, b):
    ops = 0
    while b:
        if a < b:
            a, b = b, a
        ops += a // b
        a %= b
    return ops

def main():
    n = int(input())
    out = []
    for _ in range(n):
        a, b = map(int, input().split())
        out.append(str(solve_pair(a, b)))
    print("\n".join(out))

if __name__ == "__main__":
    main()
```この解決策は、常に大きい値から小さい値を減算することを繰り返し強制することを中心に構成されています。 ループの不変条件は次のとおりです`b`は、各除算ステップの前の小さい要素です。 表現`a // b`その前に単純な減算演算が何回発生するかを正確にカウントします。`a`以下に低下します`b`、 そして`a %= b`これらすべての減算後の残りに状態を更新します。 

終了条件`while b:`元の停止ルールと一致して、1 つの数値がゼロになったときにプロセスが停止するようにします。 モジュロを取得した後、数値の役割が逆転する可能性があるため、交換ステップは不可欠です。 

## 実用的な例

 ### 例 1: (24, 17)

 圧縮されたユークリッド ステップをトレースします。 

| | b | a // b | オペレーションが追加されました | % b |
 | --- | --- | --- | --- | --- |
 | 24 | 17 | 1 | 1 | 7 |
 | 17 | 7 | 2 | 2 | 3 |
 | 7 | 3 | 2 | 2 | 1 |
 | 3 | 1 | 3 | 3 | 0 |

 最終的な答えは 1 + 2 + 2 + 3 = 8 です。 

このトレースは、各行が元のプロセスで繰り返された減算のブロック全体にどのように対応するかを示しています。 各剰余ステップは、現在のペアで可能な減算をすべて実行した後の状態を反映します。 

### 例 2: (10, 4)

 | | b | a // b | オペレーションが追加されました | % b |
 | --- | --- | --- | --- | --- |
 | 10 | 4 | 2 | 2 | 2 |
 | 4 | 2 | 2 | 2 | 0 |

 合計操作 = 4。 

これは、小さな入力であっても、反復された減算の複数の層がすでに含まれている可能性があり、アルゴリズムがそれらを除算ステップにきれいに圧縮することを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

| スペース | お(1) | ペアごとに一定数の変数のみが維持されます。

 ## 特殊なケース

 両方の数値が等しい場合、アルゴリズムは終了する前に操作を 1 回だけ実行します。 入力 (5, 5) の場合、スワップは無関係で、最初の除算では 5 // 5 = 1 が得られ、その後、剰余は 0 になります。ループはすぐに停止し、等号が 1 つの減算ステップにつながるというルールに一致します。 

(100, 1) のように、一方の数値が他方の数値よりはるかに大きい場合、アルゴリズムは商 100 と剰余 0 で 1 つの除算ステップを実行します。これは、単純なプロセスでは大きい方が消えるまで繰り返し 1 を減算するという事実と一致します。 

数値が (21, 13) などの連続したフィボナッチ数である場合、モジュロ ステップごとにペアが前のフィボナッチ ペアに減算され、プロセスに複数のユークリッド層がかかることが保証されます。 このアルゴリズムは、ブルート フォース シミュレーションで明示的に表れる長い減算チェーンを反映して、各商を正確に累積します。
