 ## 解決策
 ## 問題の理解

 この問題には 2 種類の可変状態があり、それらを分離することが全体の解決の鍵となります。 

キャッシュには、`n`バイト位置は完全にゼロから始まります。 別途、`m`ソース配列。 ロード操作では、1 つの完全なソース配列がキャッシュの連続部分にコピーされます。 コピーされると、それらのキャッシュ バイトはソース配列から独立します。 ソースに対する後からの変更は、将来のロードにのみ影響します。 

ソース更新では、256 を法とする 1 つのソース配列の連続部分がインクリメントされます。印刷操作では、1 つのキャッシュ アドレスにある現在のバイトが要求されます。 出力は、印刷操作ごとに 1 バイトの値です。 公式声明によると、`n, m, q <= 5 * 10^5`、すべてのソース配列の合計の長さも最大です。`5 * 10^5`; 制限時間は5秒です。 

大きな`q`ロードごとに、ロードされた配列の長さに比例する作業を実行することを直ちに除外します。 単一のソース配列には長さがある場合があります`5 * 10^5`何十万回もロードできるため、`O(s_i)`ロード操作により、約`2.5 * 10^11`バイトの割り当て。 同じソースが繰り返しロードされる可能性があるため、制限されているソース配列の合計サイズはこれには役に立ちません。 

また、直接シミュレーションを驚くほど間違いやすくする時間的な問題もあります。 ソースに次のものが含まれているとします。`[10, 20]`、それをロードし、ソースを次のようにインクリメントします。`[11, 21]`。 キャッシュにはまだ次のものが含まれている必要があります`[10, 20]`。 ソースへの参照を保持し、印刷時にそれを評価するソリューションでは、新しい値が誤って生成されます。 

もう 1 つの特殊なケースは、負荷の重複です。 考慮する：```
3 1 3
2 5 6
1 1 1
1 1 2
2 2
```最初の負荷は`[5, 6]`2 番目の荷重により、位置 1 と 2 に荷重がかかります。`[5, 6]`2 番目と 3 番目の位置にあります。最終的な答えは次のとおりです。`5`位置 2 が 2 回目のロードによって上書きされたためです。 各位置をカバーする最初の負荷のみを記憶するソリューションでは、間違ったスナップショットが返されます。 

アンロードされたキャッシュ位置もゼロのままでなければなりません。 例えば：```
2 1 2
1 7
2 2
2 1
```出力は次のとおりです。```
0
0
```どちらのポジションもロードされたことはありません。 すべての出力が何らかのソース配列に対応すると仮定するソリューションでは、値が存在しない場合に値を作成することになります。 

最後に、増分は 256 を中心にラップすることができ、ラップはバイトごとに独立して発生します。 例えば：```
1 1 4
1 255
3 1 1 1
1 1 1
2 1
```出力は`0`。 最初のロードは最終的なクエリとは無関係です。 2 番目のロードは増分後に発生するため、次のようになります。`255 + 1 = 0`。 適切な時点でモジュロ 256 を減算せずに通常の整数の合計を維持すると、最終的には不正なバイトが生成されます。 

## アプローチ

 直接的なアプローチは、キャッシュを明示的に表すことです。 たっぷりのソース`i`位置で`p`すべてコピーします`s_i`バイト、ソース更新ループから`l`を通して`r`、印刷は 1 つのキャッシュ セルを読み取ります。 これは操作に正確に従っているので、これは正しいです。 

問題はロード操作です。 ソースに長さがある場合`5 * 10^5`、1 つのロードにはすでに 50 万の割り当てがかかります。 と`5 * 10^5`このような負荷がかかると、最悪のケースが発生します`2.5 * 10^11`課題。 この作業量には 5 秒では決して十分ではありません。 

最初の有益な観察は、印刷クエリにはキャッシュ全体が必要ないということです。 **その 1 つのアドレスをカバーする最新の負荷**を知る必要があるだけです。 その負荷がわかると、キャッシュ値はその負荷時に取得されたソース スナップショットのちょうど 1 バイトになります。 

これにより、キャッシュの問題は、唯一のクエリがポイント クエリである範囲割り当ての問題に変わります。 この場合には、特に単純なセグメント ツリー表現があります。 負荷が間隔をカバーする場合、その間隔を通常の正規セグメント ツリー ノードに分解し、そのようなノードごとに負荷の操作番号を入れます。 キャッシュ位置については、そのリーフからルートまでをたどり、発生した最大操作数を取得します。 この最大値は、まさにその位置をカバーする最新の荷重です。 

2 番目の観察は、ソース スナップショットに関するものです。 キャッシュ位置で印刷すると仮定します`p`動作時の負荷を指します`t`。 そのロードがソースを開始した場合`i`キャッシュ位置で`start`の場合、出力されたバイトはソース位置になります。`p - start + 1`ソースが操作を調べたとき`t`。 

これらを発見できます`(load time, source offset)`最初のパス中のリクエスト。 次に、操作を 2 回目の時系列順に実行します。 時間に負荷に達したとき`t`、そのロード前のすべてのソース更新はすでに適用されているため、ソースはロードがコピーした状態とまったく同じになります。 その時点で、その負荷を参照するすべての印刷クエリに答えることができます。 

ソース更新の場合、更新が 1 つのソースから別のソースにクロスすることがないため、ソース配列を 1 つの概念配列に連結できます。 範囲の追加とポイント クエリをサポートするセグメント ツリーは、すべてのソースの増分を維持できます。 すべてのノードで遅延伝播や完全な値を必要としません。 各範囲の追加はその正規セグメント ツリー ノードに保存され、ポイント クエリによってリーフへのパス上のタグが合計されます。 

結果として、2 つのパスにより 2 つの独立した問題が解決されます。 最初のセグメント ツリーは、「どのロードがこのキャッシュ位置を所有しているか?」という質問に答えます。 2 番目のセグメント ツリーは、「その負荷が発生したときのこのソース位置の値は何でしたか?」に答えます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |`O(q * max(s_i) + q * max(s_i))`最悪の場合 |`O(n + sum s_i)`| 遅すぎる |
 | 最適 |`O((q + sum s_i) log(max(n, sum s_i)))`|`O(n + q + sum s_i)`| 承認済み |

 ブルート フォース バウンドは、より具体的には次のように見ることができます。`2.5 * 10^11`ロードのみから割り当てをキャッシュします。 最適な方法では、ロード、印刷、ソース更新ごとに対数作業のみが実行されます。 

## アルゴリズムのチュートリアル

 1. すべてのソース配列を 1 バイト配列に連結します。 すべてのソースの開始グローバル位置を記録します。 ソースの合計長は最大でも`5 * 10^5`、これは線形空間を使用します。 
2. キャッシュ アドレス上にセグメント ツリーを構築します。 最初はすべてのツリー タグがゼロです。これは、キャッシュのその部分をカバーする負荷がなかったことを意味します。 
3. 最初のパスでは、操作を時系列に処理します。 運転時の負荷に対して`t`、キャッシュ間隔を決定し、書き込みます`t`その間隔をカバーする正規のセグメント ツリー ノードに変換します。 後続のポイント クエリではそのリーフのすべての祖先を単純に検査できるため、これらの値を下方向に伝播しません。 
4. キャッシュ位置での印刷の場合`p`、リーフからルートまで歩いて、そのパス上の最大のロード操作数を見つけます。 最大値がゼロの場合、キャッシュ位置は一度もロードされていないため、答えはゼロになります。 
5. 印刷物が動作時の負荷に属する場合`t`、そのロードのソースと開始キャッシュ位置をデコードします。 対応するソース オフセットは次のとおりです。`p - start + 1`。 このオフセットをオペレーションに添付されたリクエスト リストに保存します。`t`。 出力スロットも記録されるため、後で元の出力順序を変更せずにリクエストに応答できます。 
6. 最初のパスの実行中に操作をコンパクトに保存します。 2 番目のパスでは、ロード操作とソース更新操作のみが必要なため、実装では大きな Python タプルを保持するのではなく、各操作を 64 ビット整数にパックします。 
7. セグメント ツリーをクリアし、ソース配列に再利用します。 概念的にソースを 1 つの座標系に連結します。 ソースのソース更新`i`、ポジション`l`を通して`r`、グローバル間隔での範囲加算になります。`[base[i] + l - 1, base[i] + r - 1]`。 
8. 操作を時系列に再生します。 ソース更新の場合は、そのグローバル範囲に 1 つを追加します。 運転時の負荷に対して`t`、以前に行われたすべてのソース更新`t`現在は適用されています。 に添付されているリクエスト リストを調べます。`t`、要求されたソース オフセットごとに、元のバイトとその位置で累積された増分を加算した、256 を法とする減算値を読み取ります。 
9. 再生が終了すると、すべての印刷結果が元の順序で入力されます。 回答のバイト配列を最終出力として書き込みます。 

### なぜ効果があるのか

 すべてのキャッシュ位置について、最初のセグメント ツリーは、ルートからリーフへのパス上の最大ロード タイムスタンプがその位置を含む間隔の最新ロードであるという不変条件を維持します。 したがって、すべての印刷は、現在そこにバイトが存在するロードに正確に関連付けられます。 

負荷に関連するリクエストの場合`t`、2 番目のパスが動作に達します`t`すべてのソース更新を処理した後でのみ、`t`その後何かを処理する前に`t`。 したがって、その時点で読み取られるソース値は、ロードによってコピーされた値とまったく同じになります。 後でソースを更新しても、すでにロードされているキャッシュ バイトを変更することはできないため、ロードのタイムスタンプでリクエストに応答することは、元の印刷操作でリクエストに応答することと同じです。 

2 つの不変条件を組み合わせると、すべての印刷クエリの正確なキャッシュ値が得られます。 

## Python ソリューション```python
import sys
from array import array

input = sys.stdin.readline

def solve():
    input = sys.stdin.readline

    n, m, q = map(int, input().split())

    # base[i] is the 1-based global position of the first byte of source i.
    base = [0] * (m + 2)
    data = bytearray()

    pos = 1
    for i in range(1, m + 1):
        parts = input().split()
        s = int(parts[0])
        base[i] = pos
        data.extend(int(x) for x in parts[1:])
        pos += s

    total = pos - 1
    base[m + 1] = pos

    # One tree size is enough for both the cache and the concatenated sources.
    limit = max(n, total)
    size = 1
    while size < limit:
        size <<= 1

    # First pass: tree[node] stores the latest load timestamp covering
    # the interval represented by this node.
    tree = [0] * (2 * size)

    # Operations are packed into 64-bit integers.
    # Bits 60..61: type
    # Bits 40..59: first argument
    # Bits 20..39: second argument
    # Bits 0..19 : third argument
    ops = array('Q', [0]) * (q + 1)

    # Requests belonging to load time t form a linked list.
    head = array('i', [-1]) * (q + 1)
    req_offset = array('i')
    req_next = array('i')

    # One byte per print query, in original query order.
    answers = bytearray()

    MASK = (1 << 20) - 1

    for t in range(1, q + 1):
        parts = input().split()
        typ = int(parts[0])

        if typ == 1:
            src = int(parts[1])
            start = int(parts[2])

            ops[t] = (1 << 60) | (src << 40) | start

            if src < m:
                length = base[src + 1] - base[src]
            else:
                length = total - base[src] + 1

            left = size + start - 1
            right = size + start + length - 1  # exclusive

            # Range assignment of timestamp t.
            while left < right:
                if left & 1:
                    tree[left] = t
                    left += 1
                if right & 1:
                    right -= 1
                    tree[right] = t
                left >>= 1
                right >>= 1

        elif typ == 2:
            p = int(parts[1])

            node = size + p - 1
            load_time = 0

            while node:
                value = tree[node]
                if value > load_time:
                    load_time = value
                node >>= 1

            query_id = len(answers)
            answers.append(0)

            if load_time != 0:
                load_code = ops[load_time]
                src = (load_code >> 40) & MASK
                start = load_code & MASK

                offset = p - start + 1

                req_offset.append(offset)
                req_next.append(head[load_time])
                head[load_time] = query_id

        else:
            src = int(parts[1])
            left_pos = int(parts[2])
            right_pos = int(parts[3])

            ops[t] = (
                (3 << 60)
                | (src << 40)
                | (left_pos << 20)
                | right_pos
            )

    # Reuse the tree for range-add / point-query operations on source data.
    tree = [0] * (2 * size)

    for t in range(1, q + 1):
        code = ops[t]
        if code == 0:
            continue

        typ = code >> 60

        if typ == 3:
            src = (code >> 40) & MASK
            left_pos = (code >> 20) & MASK
            right_pos = code & MASK

            left = size + base[src] + left_pos - 2
            right = size + base[src] + right_pos - 1  # exclusive

            while left < right:
                if left & 1:
                    tree[left] += 1
                    left += 1
                if right & 1:
                    right -= 1
                    tree[right] += 1
                left >>= 1
                right >>= 1

        elif typ == 1:
            load_code = code
            src = (load_code >> 40) & MASK

            request = head[t]
            if request == -1:
                continue

            source_base = base[src]

            while request != -1:
                offset = req_offset[request]
                global_pos = source_base + offset - 1

                node = size + global_pos - 1
                added = 0

                while node:
                    added += tree[node]
                    node >>= 1

                answers[request] = (data[global_pos - 1] + added) & 255
                request = req_next[request]

    return ''.join(chr(x + 48) if x < 10 else str(x) + '\n'
                   for x in answers)

if __name__ == "__main__":
    sys.stdout.write(solve())
```ソース配列は第 2 フェーズでのみフラット化されます。`base[i]`ソースの最初のグローバル位置を与える`i`、つまりソースの位置`k`に対応する`base[i] + k - 1`。 

最初のセグメント ツリーは、意図的に通常の遅延伝播ツリーではありません。 そのエントリはタイムスタンプであり、実際のキャッシュ バイトではありません。 範囲ロードはタイムスタンプを書き込みます。`O(log n)`正規ノード。 ポイント クエリはすべての祖先をチェックし、それらの最大値を取得します。 タイムスタンプは操作が処理されるにつれて増加するため、最大のタイムスタンプが正確に最新の対象負荷になります。 

操作番号は操作引数と一緒にパックされます。 関連する座標はすべて以下にあります`5 * 10^5`したがって、各座標には 20 ビットで十分です。 これにより、かなり多くのメモリを消費することになる数十万の Python タプルの保存が回避されます。 

リクエスト リストも整数配列を使用して保存されます。 リクエストはその出力位置によって識別され、`head[t]`負荷に依存するすべての印刷クエリを指します`t`。 これにより、2 番目のパスは、対応する負荷に達するとすぐにクエリのグループ全体に応答できるようになります。 

2 番目のツリーには範囲の追加のみが保存されます。 範囲の増分は正規ノードに分解され、そのタグが 1 つずつ増加します。 ポイント クエリは、ルートからリーフへのパス上のタグを合計します。 その合計は、バイトに影響を与えるソース増分の数です。 

表現`(original + added) & 255`どちらの値も負ではなく、256 は 2 のべき乗であるため、 はモジュロ 256 と同等です。 操作性もコンパクトに保てます。 

問題内のすべての間隔は 1 から始まり、両端を含みます。 反復セグメント ツリー表現は内部で半開区間を使用するため、右端点が排他的座標に変換されます。 ソースオフセットも明示的に指定されます。`p - start + 1`これにより、キャッシュ アドレスをソース インデックスに変換するときによくある 1 位置エラーが回避されます。 

## 実用的な例

 ### サンプル 1

 公式サンプルには 2 つのソースがあります。`[255, 0, 15]`そして`[1, 2, 1, 3]`、ロードが重複し、その後のソース更新が行われます。 その出力は`0, 255, 1, 255, 0, 3`。

 |`2 3`| 負荷`2`、オフセット`2`|`(2,2)`|`[5,6,7]`|`6`|
 |`1 1 1`| 新しいロード カバー ポジション 1..3 | なし |`[5,7,8]`| |
 |`2 2`| 負荷`5`、オフセット`2`|`(5,2)`|`[5,7,8]`|`7`|
 |`2 4`| 負荷`2`、オフセット`3`|`(2,3)`|`[5,6,7]`|`7`|

 ソース更新後の最初のクエリは引き続き返されます。`6`、 ない`7`更新前にロードが発生したためです。 後のロードでは更新が確認され、生成されます。`7`。 これは、まさに 2 パス アルゴリズムがキャプチャする時間的分離です。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |`O((q + S) log(max(n, S)))`| 各ロードと印刷では対数キャッシュ ツリー操作が使用され、各ソース更新と依存リクエストでは対数ソース ツリー操作が使用されます。 ここ`S = sum s_i <= 5 * 10^5`。 |
 | スペース |`O(n + q + S)`| 2 つのセグメント ツリーは次を使用します。`O(max(n,S))`スペース、ソース データ、パックされた操作、およびリクエスト リストは線形スペースを使用します。 |

 と`n`、`q`、 そして`S`すべては～によって制限されている`5 * 10^5`、対数係数は最大約 19 です。この実装では、操作ログとリクエスト リストにコンパクトな整数配列も使用されますが、ソース バイトはそれぞれ 1 バイトを占めます。 これにより、メモリはすべてのロードによってコピーされる合計バイト数ではなく、入力サイズに比例した状態に保たれます。

 ## 特殊なケース

 ### キャッシュ位置がロードされたことがありません

 のために```
2 1 2
1 7
2 2
2 1
```最初のパスでは範囲の割り当てはまったく実行されません。 どちらの印刷クエリもルートからリーフへのパスをたどり、タイムスタンプ 0 を見つけます。 彼らの回答スロットはゼロのままで、`0`そして`0`。 

この場合、アルゴリズムには特別なキャッシュ配列は必要ありません。 タイムスタンプ 0 は当然、初期のオール 0 キャッシュを表します。 

### 後のソース更新では古いキャッシュ コピーを変更してはなりません

 次のことを考慮してください。```
1 1 6
1 42
2 1
3 1 1 1
1 1 1
2 1
3 1 1 1
2 1
```操作 4 のロードは 1 つのソース増分後に発生するため、キャッシュにコピーされるソース値は次のようになります。`43`。 操作 6 での後のインクリメントにより、ソースが次のように変更されます。`44`、しかしキャッシュは残ります`43`。 

最初のパスでは、最終印刷がロード 4 に関連付けられます。2 番目のパスでは、操作 6 が適用される前に、操作 4 に到達したときにその要求が応答されます。 結果は`43`。 

### 重複するロードでは最新のタイムスタンプを選択する必要があります

 対象:```
5 2 8
2 10 10
3 7 8 9
1 1 1
1 2 2
2 2
3 2 1 3
2 4
1 2 3
2 3
2 5
```最初のロードは位置 1 と 2 をカバーし、2 番目のロードは位置 2 ～ 4 をカバーします。したがって、位置 2 の印刷では、ロード 1 ではなくロード 2 が認識されます。 

キャッシュ セグメント ツリーでは、ロード 1 がその間隔で正規ノードにタイムスタンプ 1 を書き込みます。 その後、ロード 2 は、その間隔の間、タイムスタンプ 2 を正規ノードに書き込みます。 位置 2 のクエリは、ルートからリーフへのパスに沿って両方のタイムスタンプを確認し、最大値、つまり 2 を取得します。 

### ロードは、後の更新の前にソースをキャプチャする必要があります

 テイク：```
4 1 7
3 5 6 7
2 1
1 1 2
3 1 2 3
2 3
1 1 1
2 2
2 4
```動作2キャプチャ時の負荷`[5,6,7]`。 操作 3 での更新により、ソースが次のように変更されます。`[5,7,8]`ただし、操作 4 の print はロード 2 に関連付けられているため、戻り値が返されます。`6`。 

2 番目のパスが操作 2 に到達した時点では、ソース更新はまだ処理されていません。 ソースオフセット 2 のリクエストは元の値を読み取ります`6`。 後の更新はその後にのみ処理されるため、そのリクエストに影響を与えることはできません。 

### 後のロードでは、以前のすべてのソース更新が表示されます

 同じ例では、操作 5 は操作 3 からの更新後にソースをロードします。その時点でソースは次のようになります。`[5,7,8]`、したがって、位置 2 の出力が返されます。`7`。 

2 番目のパスは、操作 5 に到達する前にすでに操作 3 を適用しています。したがって、ロード 5 にアタッチされたリクエストは、更新されたソース状態を読み取ります。 したがって、同じソースがキャッシュ内に複数の独立したスナップショットを持つことができます。 

### モジュロ 256 を結果のバイトに適用する必要があります

 対象:```
3 1 10
2 250 250
1 1 1
3 1 1 2
3 1 1 2
3 1 1 2
3 1 1 2
3 1 1 2
3 1 1 2
1 1 1
2 1
2 2
```6 段階ずつ回転します`250`の中へ`0`なぜなら`250 + 6 = 256`。 したがって、2 番目のロードではコピーが行われます。`[0,0]`、両方の出力はゼロを返します。 

ソース セグメント ツリーには、増分の数が通常の整数として格納されます。 合計は最大で次のとおりであるため、これは安全です`q`, これは Python の整数に簡単に適合します。 モジュロ演算は、実際のバイト値が再構築されるときに適用されます。 

### ロードはキャッシュ境界で正確に終了します

 最大サイズのテストでは、ソース 1 の長さは`500000`、および操作`1 1 1`キャッシュ位置にロードします`1`を通して`500000`。 所定の位置にプリント`500000`ソースオフセットにマップする必要があります`500000`。 

範囲変換では排他的な右エンドポイントが使用されるため、内部間隔は次のようになります。`[1, 500001)`。 ポイントクエリで使用されるのは、`size + p - 1`、キャッシュ位置をマッピングします`500000`まさにその葉に。 余分なキャッシュ位置は含まれず、最終バイトは正しく処理されます。
