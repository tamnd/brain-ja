 ## 解決策
 ## 問題の理解

 「マイナス」と「プラス」という 2 つの記号のみで構成される 2 つの文字列が与えられます。 唯一許可される移動は、隣接する 2 つのマイナス記号を取得し、それらを 1 つのプラス記号に置き換えることで、文字列を 1 文字短縮します。 この操作は任意の順序で何度でも繰り返すことができます。 

タスクは、これらの置換を使用して開始文字列をターゲット文字列に変換できるかどうかを判断することです。 

この制約により、合計入力サイズが最大 200,000 文字で最大 100,000 のテスト ケースを処理する必要があります。 これにより、文字列を繰り返し書き換える二次関数やシミュレーションが即座に除外されます。 正しいアプローチでは、各文字を一定の回数処理する必要があります。 

微妙な点は、操作では長さとローカル構造の両方が変更されるため、操作の順序が重要ではないと仮定した場合、単純な「すべてのリダクションをシミュレートする」アプローチはパフォーマンスだけでなく正確性においても失敗するということです。 

単純な考え方を打ち破るエッジケースの 1 つは、マイナス記号の長いブロック内で複数のリダクションが相互作用する場合です。 たとえば、「----」のような文字列には有効なリダクション パスがいくつかあり、選択肢によってプラス記号が表示される場所が変わります。 もう 1 つは、ソース内の元のプラス記号に明らかに対応しない位置にターゲットのプラス記号がある場合です。プラス記号はマイナスのペアを結合することで作成できるためです。 

## アプローチ

 強引なアイデアは、文字列を繰り返しスキャンして、出現する「--」を「+」に置き換え、残りの手がなくなるまで続行することです。 これは、有効な削減プロセスを探索するという意味では正しいですが、置換のたびに文字列がシフトされ、単一のテスト ケースが二次時間に低下する可能性があるため、遅すぎます。 

重要な点は、この操作は隣接するマイナス文字にのみ影響し、プラス記号とは挿入する場合を除いて決して相互作用しないということです。 これにより、構造が最大の連続したマイナス記号のブロックに分離されます。 このようなブロック内では、プラス記号が区切り文字として機能するため、操作がその境界を越えることはありません。 

したがって、問題は、任意のリダクションを実行した後に、連続するマイナス記号の単一ブロックがどのようになるかを理解することに帰着します。 各演算では 2 つのマイナス記号が削除され、1 つのプラス記号が導入されるため、長さ L のブロック内で、変換する素のペアの数を効果的に選択することになります。 ブロック内で p 個の演算を実行すると、2p 個のマイナス符号が消費され、p 個のプラス符号が生成され、L − 2p 個のマイナス符号が残ります。 

これは、ブロックから派生した最終構成が 2 つの制約を満たす必要があることを意味します。1 つは、そのブロックから生成されるシンボルの総数は、選択されるペアの数によって決まり、残りのマイナス符号のパリティは、使用されるペアの数によって決まります。 

重要な単純化は、ブロック内ではカウントのみ、つまりマイナス記号がいくつ残っているか、プラス記号がいくつ作成されたかのみを考慮することです。 異なるペアリングの選択により、それらのカウントと一致する順序を実現できるため、それらの正確なインターリーブは到達可能性とは無関係です。 

したがって、ソース内の長さ L の各ブロックは、そのセグメントを L = m + 2p に対応するいくつかのマイナス文字とプラス文字に分割できれば、ターゲットのセグメントと一致します。ここで、m は保持するマイナス記号の数、p は生成されるプラス記号の数です。

 ## アルゴリズムのチュートリアル

 両方の文字列を、連続する同一文字の交互のブロックに分割して処理します。 これにより、文字列ごとに、「++++」、「----」、「++」、「---」などの一連のセグメントが生成されます。

次にアルゴリズムは、ターゲット文字列のセグメントをソース文字列のセグメントと順番に照合しますが、消費可能なリソースとしてマイナス ブロックのみを扱います。 

1. 両方の文字列を連続する同一文字のランに分割します。 
2. ターゲット ランを左から右にトラバースします。 ターゲット内で一連のプラス記号が発生する場合は、既存のプラス記号によって生成されるか、ソースのマイナス ブロック内のマイナス記号のペアを変換することによって生成される必要があります。 したがって、構造的にプラスの実行を一致させる必要はなく、利用可能なマイナスのペアによってそれらが説明できることを確認するだけです。 
3. ソース実行に対するポインタを維持し、リソースとしてのマイナス実行に焦点を当てます。 ソース内の長さ L のマイナスのランごとに、隣接するマイナス文字をペアにすることで、いくつかのプラス記号を生成できます。 各ペアは 2 つのマイナス記号を消費し、1 つのプラス記号を生成します。 
4. 長さ m のターゲットでマイナス ランを処理する場合、利用可能なソースから容量を引いたものからマイナス ランを形成できることを確認します。 残りのマイナス記号と、この部分で作成する必要があるプラス記号の数の 2 倍というターゲット要件をカバーするのに十分な総容量が得られるまで、ソース マイナスの実行を集計します。 
5. いずれかの時点で、対応するソース領域で利用可能なマイナス容量よりも多くのマイナス容量が必要な場合、変換は不可能です。 
6. すべての実行が処理されるまで続行し、一致しない構造が残らないようにします。 

### なぜ効果があるのか

 ソース内で実行される各マイナスは、トークンの貯蔵庫として機能します。 ターゲットに保持されるすべてのマイナスは 1 つのトークンを消費しますが、ターゲット内のすべてのプラスはマージされたペアから取得する必要があるため、2 つのトークンを消費します。 操作では、ソース内の既存のプラス実行によって作成された構造境界を越えて情報を移動することは決してないため、唯一の意味のある制約は、必要な各セグメントに、対応する利用可能な領域からの十分な数のマイナス トークンで資金を供給できるかどうかです。 貪欲な消費により、ソース ブロックを過剰に使用することがなくなり、ペアリングの不可逆的な性質が尊重されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def compress(s):
    runs = []
    i = 0
    n = len(s)
    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1
        runs.append((s[i], j - i))
        i = j
    return runs

def solve():
    k = int(input())
    out = []
    
    for _ in range(k):
        s = input().strip()
        t = input().strip()

        rs = compress(s)
        rt = compress(t)

        i = j = 0
        ok = True

        while i < len(rs) or j < len(rt):
            if i == len(rs):
                ok = False
                break
            if j == len(rt):
                ok = False
                break

            cs, ls = rs[i]
            ct, lt = rt[j]

            if cs == '+':
                if ct != '+':
                    ok = False
                    break
                if ls != lt:
                    ok = False
                    break
                i += 1
                j += 1
                continue

            if cs == '-' and ct == '+':
                need_pairs = lt
                if ls < 2 * need_pairs:
                    ok = False
                    break
                ls -= 2 * need_pairs
                rs[i] = (cs, ls)
                j += 1
                continue

            if cs == '-' and ct == '-':
                take = min(ls, lt)
                ls -= take
                lt -= take
                rs[i] = (cs, ls)
                rt[j] = (ct, lt)
                if ls == 0:
                    i += 1
                if lt == 0:
                    j += 1
                continue

            ok = False
            break

        out.append("YES" if ok else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```コードは最初に両方の文字列をランに圧縮するため、文字ごとに操作することはありません。 次に、2 つのポインターを使用して両方の実行リストを調べます。 ソース内のプラス記号は消えたり、再配置されたりできないため、プラス記号は正確に一致する必要があります。 マイナスランは柔軟に扱われます。マイナス文字はそのままにすることも、ペアで使用してターゲットにプラス記号を生成することもできます。 ランレングスを慎重に減少させることにより、利用可能な容量を 1 回だけ使用し、異なる一致間で文字を再利用しないことが保証されます。 

よくある落とし穴は、部分的に消費した後にその場で実行を減らすことができないことです。 単一のソース実行が複数のターゲット実行に分割される可能性があるため、これはここでは不可欠です。

 ## 特殊なケース

 重要なエッジ ケースは、マイナスのランが短すぎて、ターゲットが必要とするプラス記号の数をサポートできない場合です。 たとえば、ソースには「--」が含まれているが、ターゲットには「+++」が必要な場合、各プラスには 2 つのマイナス符号が必要であるため、アルゴリズムはペアリング容量の不足を直ちに検出します。 

もう 1 つのエッジ ケースは、プラス構造の不一致です。 ソースに長さ 3 のプラスの連続が含まれており、ターゲットが同じ構造位置で長さ 2 を必要とする場合、既存のプラス記号は削除またはマージできないため、アルゴリズムはそれを拒否します。 

3 番目のケースは、すべてのターゲット実行を処理した後に残ったマイナス記号です。 これが許可されるのは、操作がオプションであり、アルゴリズムがソース実行の完全な消費を強制することはなく、ターゲットの需要に対する実現可能性のみをチェックするためです。
