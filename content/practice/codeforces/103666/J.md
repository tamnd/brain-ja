 ## 解決策
 ## 問題の理解

 線に沿って配置された一連のタワーの高さが与えられ、各位置は一意の高さの値を持ちます。 タスクはインデックスのトリプルが何個あるかを数えることです$i < j < k$位置と高さの両方において厳密に増加するシーケンスを形成します。つまり、$h_i < h_j < h_k$。 

言い換えれば、順列のような配列内の長さ 3 の増加する部分列の数を数えています。 

制約$n \le 8000$定数を超える 3 次または 2 次の解はすでに除外されています。 全体にわたる素朴なトリプルループ$(i, j, k)$について調べるだろう$n^3 / 6$これは 8 \times 10^3^3 \およそ 5 \times 10^{11} 操作のオーダーであり、2 秒に収まる量をはるかに超えています。 平$O(n^2)$メソッドは慎重に設計する必要がありますが、ここではまだ許容されます。 

微妙な点は、高さは次の順列であるということです。$1 \dots n$したがって、比較は厳密に意味があり、重複は存在しません。 これにより、等しい値に関する曖昧さがなくなり、増加するすべてのペアまたはトリプルが明確に定義されます。 

順序縮退に関連するトリッキーなエッジ ケースはありませんが、単純な実装では、ローカル カウントの再計算が非効率的である場合、目立たない形で失敗する可能性があります。 たとえば、各中間インデックスのサフィックスを繰り返しスキャンすると、隠れた 2 次または 3 次の動作が発生します。 

最小限の例は、正確さの要件を明確にするのに役立ちます。 入力の場合:```
3
1 2 3
```有効なトリプルが 1 つだけあります$(1,2,3)$。 正しい方法であれば、この単一の増加チェーンを検出する必要があります。 

減少する配列の場合:```
3
3 2 1
```どのペアも 3 番目の増加要素に拡張できないため、答えはゼロです。 この場合、多くの場合、部分的な順序付けが間違っていると想定している実装が明らかになります。 

## アプローチ

 ブルートフォース手法では、すべてのトリプルを直接試行します。$i < j < k$値が増加しているかどうかを確認します。 これは、すべての候補を明示的に列挙し、有効な候補をフィルタリングするため、正しいです。 ただし、そのコストは次のように増加します$O(n^3)$、これはたとえ$n = 8000$なぜなら、それは何千億もの比較につながるからです。 

中間要素を修正することで改善できます$j$。 それぞれについて$j$、有効なペアの数を知りたいです。$(i, k)$そのように存在する$i < j < k$、$h_i < h_j < h_k$。 これにより、条件が 2 つの独立したカウント (前の要素の数) に分割されます。$j$よりも小さい$h_j$、その後の要素の数$j$よりも大きい$h_j$。 これら 2 つを乗算すると、中間点を持つ有効なトリプルの数が得られます。$j$。 

この変換により、プレフィックスとサフィックスの統計を効率的に計算するという問題が軽減されます。 毎回カウントを最初から再計算するのではなく、$j$、事前計算します:

 より小さい値がいくつあるか$h_j$接頭辞に表示される$[1, j-1]$、およびそれより大きい値がいくつあるか$h_j$接尾辞に表示されます$[j+1, n]$。 

高さは順列だから$1 \dots n$、フェンウィック ツリーを使用して、周波数構造を維持し、線形または対数時間で段階的に更新できます。 

重要な洞察は、トリプル カウントが中間インデックス付近できれいに分解され、グローバルな組み合わせ問題が位置ごとに 2 つのローカルなカウント クエリに変わるということです。

 | --- | --- | --- | --- |
 | ブルートフォース |$O(n^3)$|$O(1)$| 遅すぎる |
 | スプリットミドル + フェンウィックツリー |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 フェンウィック ツリー (バイナリ インデックス ツリー) を使用して、表示された値のカウントを維持します。 

1. 配列を左から右に走査し、プレフィックス数の配列を計算します。`left_smaller[j]`、各位置はどこですか$j$、位置にある要素の数を数えます$< j$より小さい値を持つ$h_j$。 私たちは、観測された高さの頻度を保存するフェンウィック ツリーを維持しています。 各ステップで、値の数をクエリします。$< h_j$これまでに挿入されました。 
2. 配列を右から左に走査し、サフィックス数の配列を計算します。`right_greater[j]`、各位置はどこですか$j$、位置にある要素の数を数えます$> j$より大きい値を持っています$h_j$。 ここでもフェンウィック ツリーを使用しますが、ここでは要素を右から左に処理し、値を挿入し、ツリー内に現在より大きい値がいくつ存在するかをクエリします。 これは、表示された合計からプレフィックスの合計を引いたものとして計算されます。$h_j$。 
3. インデックスごとに$j$、トリプルの中間要素として解釈します。 2 つの量を掛け合わせます。`left_smaller[j] * right_greater[j]`。 これは、すべての有効なトリプルをカウントします。$j$が中心です。 
4. これらの積を合計します。$j$。 結果は、増加するトリプルの合計数です。 

各ステップは、動的なプレフィックスまたはサフィックス上で正確な周波数構造を維持することに依存します。 フェンウィック ツリーは、更新とプレフィックス クエリの両方が対数時間で実行されることを保証します。 

### なぜ効果があるのか

 すべての有効なトリプル$i < j < k$中間インデックスによって一意に決定されます$j$。 固定の場合$j$、の選択$i$前の要素のみに依存します$j$より小さい$h_j$、そして次の選択$k$後の要素にのみ依存します$j$より大きい$h_j$。 これらの選択肢は独立しているため、組み合わせの数は 2 つのカウントの積になります。 すべての有効なトリプルは中間インデックスで 1 回だけカウントされるため、すべてを合計すると、$j$正しい合計が生成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

n = int(input())
h = list(map(int, input().split()))

# left_smaller
bit = Fenwick(n)
left_smaller = [0] * n

for i in range(n):
    x = h[i]
    left_smaller[i] = bit.sum(x - 1)
    bit.add(x, 1)

# right_greater
bit = Fenwick(n)
right_greater = [0] * n

total = 0
for i in range(n - 1, -1, -1):
    x = h[i]
    right_greater[i] = bit.sum(n) - bit.sum(x)
    bit.add(x, 1)

for j in range(n):
    total += left_smaller[j] * right_greater[j]

print(total)
```この実装では、ポイントの更新と高さの値に対するプレフィックスの合計をサポートするフェンウィック ツリーが定義されています。 最初のパスのビルド`left_smaller`左から右にスキャンしながら値を挿入することで、構造が常に現在のインデックスの左側にある要素を厳密に表すようにします。 

2 番目のパスでは、構造をリセットして右から左に処理し、各位置の右側に大きな要素がいくつ存在するかを計算します。 表現`bit.sum(n) - bit.sum(x)`プレフィックスのカウントをサフィックスのカウントに変換するため、これは非常に重要です。 

最後に、積の集計ステップは、中間インデックス付近のトリプルの組み合わせ分解を直接反映します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    class Fenwick:
        def __init__(self, n):
            self.n = n
            self.bit = [0] * (n + 1)

        def add(self, i, v):
            while i <= self.n:
                self.bit[i] += v
                i += i & -i

        def sum(self, i):
            s = 0
            while i > 0:
                s += self.bit[i]
                i -= i & -i
            return s

    n = int(input())
    h = list(map(int, input().split()))

    bit = Fenwick(n)
    left = [0] * n
    for i in range(n):
        left[i] = bit.sum(h[i] - 1)
        bit.add(h[i], 1)

    bit = Fenwick(n)
    right = [0] * n
    for i in range(n - 1, -1, -1):
        right[i] = bit.sum(n) - bit.sum(h[i])
        bit.add(h[i], 1)

    ans = 0
    for i in range(n):
        ans += left[i] * right[i]

    return str(ans)

 ## 特殊なケース

 最小の入力サイズは、Fenwick ロジックが無効なインデックスにアクセスしてはならない境界動作をテストします。 のために$n = 1$、プレフィックスとサフィックスの計算は集計では決して使用されず、中間インデックスが存在しないため、アルゴリズムは正しくゼロを返します。 

次のような厳密に増加するシーケンスの場合$1,2,3,4$、すべてのインデックスが貢献します$(j)\cdot(n-j-1)$、アルゴリズムは隣接関係に依存せずにフェンウィック カウントを通じてこれをキャプチャします。 これにより、考えられるすべてのトリプルが有効な場合でも正確さが保証されます。 

厳密に減少するシーケンスの場合、すべてのプレフィックスの小さいカウントはゼロになるため、すべての積が消滅します。 また、以前のどの要素よりも大きい要素がないため、サフィックスの計算でも正しくゼロが得られ、分解の両方の半分が反転の下で対称的に動作することが確認されます。
