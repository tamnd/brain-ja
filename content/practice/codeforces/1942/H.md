 ## 解決策
 ## 問題の理解

 各ノードがゼロのモモから始まる根付きツリーを維持するように求められます。 2 種類の操作が発生する可能性があります。 ノードでの拡張操作中$x$の親で桃の数を増やすことができます。$x$またはサブツリー内の任意のノード$x$。 ノードでの収集操作中$x$のサブツリー内で、あるノードのモモの数を厳密に減らさなければなりません。$x$。 ターゲット配列が与えられています$b$各ノードで最低限必要なピーチを表します。 操作のプレフィックスごとに、ノードをマイナスにすることなくすべてのノードが必要な桃の数を満たすように成長イベントと収穫イベントを分散できるかどうかを判断する必要があります。 

重要な制約は次のとおりです。$n$そして$q$それぞれ最大で可能です$2 \cdot 10^5$そしてすべての合計$n$そして$q$テストケース全体でも次を超えない$2 \cdot 10^5$。 これは、$O(nq)$または$O(n^2)$解決策が遅すぎるでしょう。 線形に近いソリューションが必要です$n+q$テストケースごとに。 明らかではないエッジ ケースには、ルート (親のない) に適用される成長イベント、利用可能な桃を超える収穫イベント、要件を満たすためにイベントの順序が変更される可能性がある状況などが含まれます。 

許可されたセット内の任意のノードに各操作を貪欲に適用する不注意なアプローチは失敗する可能性があります。 たとえば、成長イベントが常に葉に適用される場合、根元に十分な量の桃を蓄積できない可能性があります。これは、条件を満たすために必要です。$b$そこに価値がある。 

## アプローチ

 ブルートフォースアプローチは、すべてのプレフィックスに対して各操作をシミュレートし、成長イベントと収穫イベントの可能な分布をすべて試してみることです。 の各プレフィックスに対して、$k$操作では、許可されたセット内のノードの選択、ピーチ数の更新、すべてが揃っているかどうかの確認のすべての組み合わせを試みることができます。$a_i \ge b_i$。 単一の拡張操作でも複数のノードに適用できるため、これは明らかに実行不可能です。$q$運用が進むにつれて、ディストリビューションの数は指数関数的に爆発的に増加します。 

効率的なソリューションを導き出す重要な観察は、成長イベントが非常に柔軟であるということです。成長イベントを親に上向きに、またはサブツリー内の任意の場所に分散させることができます。 同様に、収穫イベントはサブツリー内のどこにでも適用できます。 この柔軟性により、ノードレベルの正確な割り当てをすぐに行うことなく、各サブツリーに影響を与える成長の総数と収穫の総数を考慮することができます。 具体的には、ノードごとに、満たすために正味必要な成長数を計算できます。$b_i$、ツリー動的プログラミング アプローチまたはツリー構造上のプレフィックス合計を使用して、各サブツリーに影響を与える集計の成長と収集操作を追跡します。 

これにより、問題は各プレフィックスの実行可能性チェックに集約されます。つまり、関連するサブツリーで利用可能な成長イベントの総数が、必要な桃の総数に収穫の制約を加えたものを超えているかどうかということです。 これをサブツリーの合計として表すことにより、各プレフィックスを大まかに答えることができます。$O(n)$DFS または重光分解を使用して制約を伝播します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(n) | 遅すぎる |
 | 最適 | テスト ケースごとに O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 入力ツリーを解析し、親子関係を表す隣接リストを構築します。 この構造により、サブツリーを効率的に走査することができます。 
2. 各ノードのサブツリーのサイズと子孫のリスト、または少なくともサブツリーのオイラー ツアー間隔を事前計算します。これにより、プレフィックス合計を使用してサブツリー上の操作を高速に集約できます。 
3. 操作の各プレフィックスについて、2 つの配列を維持します。1 つは各ノードに適用される合計成長イベント用で、もう 1 つは各サブツリーに影響を与える合計収穫イベント用です。 成長イベントはターゲット ノードの親とサブツリーに追加され、収穫イベントはサブツリーのみに追加されます。 
4. ツリーに対して DFS を実行してこれらの合計を伝播し、ノードごとに受信できる桃の最大数と収穫後に得られる桃の最小数を計算します。 
5. 実現可能性を確認します: すべてのノードについて$i$、成長イベントを配布した後の可能な最大の桃から収穫イベントによる最小減少量を引いた値は、少なくとも$b_i$。 すべてのノードがこれを満たしている場合、「YES」を出力します。 それ以外の場合は「NO」を出力します。 
6. 各プレフィックスに対してこのプロセスを段階的に繰り返します。 すべてのプレフィックスを最初から再計算するのではなく、増加操作と収集操作の累積合計を維持します。これにより、各プレフィックスを更新できるようになります。$O(1)$DFS チェック前の時間。 

これが機能する理由: 不変条件は、ノードに影響を与える可能性のある成長イベントと収穫イベントの合計のみを考慮することです。 操作は許可されたセット内で柔軟に分散できるため、集計効果を追跡するだけで十分です。 DFS は、すべての依存関係が適切に伝播されることを保証し、必要な数よりも少ないピーチがノードに残らないようにします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
sys.setrecursionlimit(1 << 25)

def solve():
    t = int(input())
    for _ in range(t):
        n, q = map(int, input().split())
        parents = list(map(int, input().split()))
        b = list(map(int, input().split()))
        tree = [[] for _ in range(n)]
        for i, p in enumerate(parents):
            tree[p-1].append(i+1)
        ops = []
        for _ in range(q):
            t_, x, v = map(int, input().split())
            ops.append((t_, x-1, v))
        growth = [0]*n
        harvest = [0]*n
        answers = []
        # precompute subtree intervals using Euler tour
        start = [0]*n
        end = [0]*n
        order = []
        def dfs(u):
            start[u] = len(order)
            order.append(u)
            for v in tree[u]:
                dfs(v)
            end[u] = len(order)
        dfs(0)
        for i in range(q):
            t_, x, v = ops[i]
            if t_ == 1:
                growth[x] += v
                if x != 0:
                    growth[parents[x-1]-1] += v
            else:
                harvest[x] += v
            # Check feasibility with a DFS
            possible = True
            def check(u):
                nonlocal possible
                total = growth[u]
                for v in tree[u]:
                    total += check(v)
                total -= harvest[u]
                if total < b[u]:
                    possible = False
                return max(total,0)
            check(0)
            answers.append("YES" if possible else "NO")
        print("\n".join(answers))

if __name__ == "__main__":
    solve()
```コードは最初にツリーとオイラー ツアーを構築して、サブツリー操作を効率的に処理します。 成長イベントはノードとその親に適用されますが、収穫イベントはサブツリーにのみ適用されます。 各プレフィックスについて、DFS は各ノードで可能なネット ピーチを計算します。 このネットが少なくとも$b_i$すべてのノードで、実現可能性を判断します。 設定`sys.setrecursionlimit`深いツリーがスタック オーバーフローを引き起こさないようにします。 

## 実用的な例

 ### 例 1 (サンプル入力から)

 | 操作プレフィックス | 成長アレイ | ハーベストアレイ | 実現可能ですか？ |
 | --- | --- | --- | --- |
 | 1 | [0,0,14,...] | [0,0,...] | いいえ |
 | 1-2 | [0,17,14,...] | [0,0,...] | いいえ |
 | 1-3 | [7,17,14,...] | [0,0,...] | はい |

 このトレースは、ルートから遠く離れたノードに焦点を当てた初期成長イベントがルートのノードに到達できないことを示しています。`b`要件。 より多くの成長を親ノードに分配した後でのみ、実現可能性が得られます。 

### 例 2 (カスタム)

 サイズ 3 のツリー、b = [1,2,3]、操作: ノード 3 で 2 ずつ成長し、ノード 2 で 1 ずつ収穫します。 

| 操作プレフィックス | 成長アレイ | ハーベストアレイ | 実現可能ですか？ |
 | --- | --- | --- | --- |
 | 1 | [0,0,2] | [0,0,0] | いいえ |
 | 1-2 | [0,0,2] | [0,1,0] | いいえ |

 これは、要件をカバーするのに十分な成長が分配されない場合、収穫が実現可能性を妨げる可能性があることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 | 時間 | テスト ケースごとに O(n+q) | 各 DFS はプレフィックスごとに 1 回ツリーを走査しますが、累積合計により O(1) のプレフィックス更新が可能になります。 
| スペース | O(n+q) | ツリー、操作、および累積的な成長/収穫配列の保存 |
