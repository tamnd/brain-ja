 ## 解決策
 ## 問題の理解

 各参加者はピザのスライスの数をリクエストし、リクエストされたすべてのスライスには指定されたトッピングが付いています。 ピザ店では、1 枚のピザにつき 1 つのトッピングのみでピザを販売し、各ピザは常に正確に 8 等分にカットされます。 

タスクは、要求されたすべてのスライスが正確に満たされ、未使用のスライスが残らないように、トッピングごとに一定数のピザを購入できるかどうかを判断することです。 重要な制限は、スライスの残りは許可されていないため、購入したスライスはすべて誰かが消費する必要があることです。 

これにより、各ピザには 1 つのトッピングの同一のスライスが正確に 8 枚含まれるため、問題は各トッピングの需要をサイズ 8 のグループに正確に詰めることができるかどうかという問題に変わります。 

入力は複数のテスト ケースで構成されます。 それぞれのケースに、人数と利用可能なトッピングの数が与えられます。 次に、各人に希望するスライスの数が与えられ、続いてそれらのスライスのトッピングのリストが与えられます。 各ケースの出力は、完璧な購入計画が存在するかどうかの決定です。 

この制約により、テスト ケースごとに最大 1000 人が許可され、ケースごとに合計 100,000 のスライス リクエストが許可されます。 これは、スライス リクエストの総数において線形または線形に近い解が必要であることを意味します。 人物やスライスに関する二次関数は遅すぎます。 

微妙なエッジケースは、配分が「一人当たりのバランスがとれている」ように見えるが、トッピングごとに全体的に分割できない場合です。 たとえば、ある人がトッピング 0 の 3 スライスをリクエストし、別の人がトッピング 0 の 5 スライスをリクエストした場合、局所的にはすべて問題ないように見えますが、合計は 8 なので機能します。 ただし、異なる人の間で合計が 10 と 6 だった場合、正しい決定はトッピングごとの合計金額のみに依存するにもかかわらず、単純な個人ごとのチェックでは、実装に応じて誤って承認または拒否される可能性があります。 

入力にトッピングがまばらな場合、別の特殊なケースが発生します。 単純な解決策では、リクエストがゼロのトッピングは無視される可能性がありますが、実現可能性に影響を与えないため、それらは無関係です。 

## アプローチ

 直接的なアプローチは、割り当ての観点から考えることです。 各スライスのリクエストはピザに割り当てる必要があり、各ピザは正確に 8 つの同一のスライスを提供します。 スライスをトッピングごとに 8 個のセットにグループ化するシミュレーションを試みることもできますが、それはすぐに不必要な簿記になります。 

重要な観察は、ピザがトッピング全体にわたって独立しているということです。 トッピング t のピザは、トッピング t のスライスのみを提供でき、常に正確に 8 スライスを提供します。 したがって、トッピングごとに、そのトッピングのリクエストされたスライスの総数は 8 で割り切れる必要があります。これが当てはまる場合、トッピング t の total_sum[t] / 8 枚のピザを購入するだけで済みます。 

これにより、問題全体がトッピングごとの合計の計算と、割り算条件のチェックに集約されます。 入力の構造により、クロストップ相互作用や順序制約がないため、カウントだけで十分であることが保証されます。 

ブルートフォース解釈では、ピザの具材をスライスごとにシミュレートしようとしますが、これにはトッピングごとに部分的に具材が入ったピザの複数セットを維持する必要があります。 最悪の場合、最大 100,000 のスライスでは、シミュレーションは挿入ごとに線形ですが、特に部分的なフィルを処理する場合、不必要に複雑になり、エラーが発生しやすくなります。 

簡素化された合計ベースの方法では、すべての状態追跡が削除され、単一パスの集計に置き換えられます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | 最適 (トッピングごとの合計) | O(スライスの合計) | お(お) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 配列を初期化する`cnt`トッピングごとに要求されたスライスの合計を保存するためのゼロを含むサイズ M 。 この配列は、各トッピングに提供する必要があるスライスの数を表します。 
2. 各人について、リクエストされたトッピングのリストを読み、対応するエントリを増やします。`cnt`。 この配列の各エントリは、個人ごとの構造ではなく、世界的な需要を蓄積します。 
3. すべての人を処理した後、0 から M − 1 までのすべてのトッピングを反復処理し、`cnt[t]`この条件により、需要をそのトッピングの完全なピザに正確に分割できることが保証されます。 
4. 8で割って余りがあるトッピングがある場合は、すべてのリクエストを無駄なく満たすことは不可能であると即座に判断します。 
5. すべてのトッピングが可算条件を満たしている場合、有効なピザの選択が存在すると結論付けます。 

重要な推論ステップは、各ピザが正確に 8 枚の同一のスライスを提供するため、実現可能性はトッピングごとの総需要をサイズ 8 のグループに分割することになります。 

### なぜ効果があるのか

 各トッピングでは、同一のユニット、つまり同じフレーバーのスライスのみを操作します。 各グループは購入した 1 枚のピザに正確に対応するため、有効な解決策では、これらのスライスを 8 つの互いに素なグループに割り当てる必要があります。 合計数が 8 で割り切れない場合、少なくとも 1 つのスライスがグループ化されないままになるか、不完全なピザが強制されることになります。これは禁止されています。 逆に、割り切れる場合は、各トッピングの正確に cnt[t] / 8 枚のピザを取得し、それらのスライスをリクエストに一致するように任意に割り当てることで、ソリューションを構築するのは簡単です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(n, m):
    cnt = [0] * m

    for _ in range(n):
        data = list(map(int, input().split()))
        p = data[0]
        toppings = data[1:]
        for t in toppings:
            cnt[t] += 1

    for x in cnt:
        if x % 8 != 0:
            return "NO"
    return "SI"

def main():
    out = []
    data = sys.stdin.read().strip().split()
    it = iter(data)

    while True:
        try:
            n = int(next(it))
            m = int(next(it))
        except StopIteration:
            break

        cnt = [0] * m
        for _ in range(n):
            p = int(next(it))
            for _ in range(p):
                t = int(next(it))
                cnt[t] += 1

        ok = True
        for x in cnt:
            if x % 8 != 0:
                ok = False
                break

        out.append("SI" if ok else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    main()
```整数の合計数が大きくなる可能性があるため、ソリューションはストリーミング方式で入力を読み取ります。 各スライス要求は 1 回だけ処理され、対応するトッピング カウンタがインクリメントされます。 

唯一の微妙な点は、すべてのトークンが複数のテスト ケースにわたって正しく消費されるようにすることです。 完全な入力に対して反復子を使用すると、繰り返しの I/O オーバーヘッドが回避され、解析が簡素化されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(合計スライス + M) | 各スライスが 1 回処理され、各トッピングが 1 回チェックされます。 
| スペース | お(お) | トッピングごとの count 配列のみが保存されます。 

この制約により、テスト ケースごとに合計 100,000 件のスライス リクエストが許可されるため、すべてのリクエストに対する線形パスは容易に十分に高速になります。 M は最大 100 であるため、メモリ使用量は少なくなります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    data = sys.stdin.read().strip().split()
    it = iter(data)

    out = []
    while True:
        try:
            n = int(next(it))
            m = int(next(it))
        except StopIteration:
            break

        cnt = [0] * m
        for _ in range(n):
            p = int(next(it))
            for _ in range(p):
                cnt[int(next(it))] += 1

        out.append("SI" if all(x % 8 == 0 for x in cnt) else "NO")

    return "\n".join(out)

 ## 特殊なケース

 単一のトッピングと単一のスライスのリクエストの場合、割り算ルールが直接公開されます。 入力が`1 1`に続く`1 0`、0 をトッピングするためのカウンタは 1 になり、1 % 8 はゼロではないため、アルゴリズムは正しく直ちにそれを拒否します。 

すべての需要がトッピングごとに正確に 8 の倍数である場合は、肯定的なシナリオが確認されます。 トッピング 0 に 16 件のリクエストがあり、トッピング 1 に 8 件のリクエストがある場合、どちらも 8 で割り切れるため、アルゴリズムは受け入れ、トッピング 0 のピザ 2 枚とトッピング 1 のピザ 1 枚を購入できるという事実と一致します。 

人数は多いが 1 人あたりのリクエストが少ないケースでは、1 人あたりの構造が無関係であることがわかります。 たとえ各人がトッピングの組み合わせを要求したとしても、最終的な合計のみが問題となり、アルゴリズムは割り切れるかどうかをチェックする前にすべてを正しく集計します。
