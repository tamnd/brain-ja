 ## 解決策
 ## 問題の理解

 小文字で構成される単一の文字列から始めます。 各文字は静的ではありません。サイズ 26 の固定置換テーブルに従って別の文字列に展開されます。`x`、文字列に置き換えられます`p_x`。 操作を 1 回適用すると、現在の文字列内のすべての文字が同時に置換されます。 

この変化を繰り返した結果、`k`場合によっては、文字列が非常に大きくなる可能性があります。 それを構築する代わりに、より具体的な質問が行われます: 位置にある文字は何ですか`i`最終的に展開された文字列には (1 からインデックスが付けられています)?

 重要な問題は、両方とも`k`そして`i`大きくなる可能性があります。 インデックスは 10^18 まで大きくなる可能性があるため、文字列を明示的に構築するアプローチは不可能になります。 文字列全体の長さを追跡することさえ、変換ステップごとに指数関数的に増加する可能性があるため、現実的ではありません。 

各展開を完全にシミュレートする単純なアプローチは、すぐに失敗します。 各文字が最大 10 文字に拡張されたとしても、20 ステップを経ると、文字列のサイズはすでに 10^20 を超える可能性があり、その文字列へのインデックス作成は構築なしでは不可能になります。 

展開によって空の文字列または短い文字列が生成される場合、微妙なエッジ ケースが発生します。 文字ごとに均一な増加を仮定したり、構造を注意深く伝播させずにプレフィックスの合計を維持しようとする不注意なアプローチは、単一の文字に繰り返しマッピングされる文字などの場合に失敗し、分岐のない長いチェーンが作成されます。 

たとえば、次の場合`a -> b`、`b -> c`、`c -> c`、その後、多くのステップを経て、文字列全体が単一の繰り返される文字に折りたたまれます。 単純な拡張ベースのシミュレーションでは、たとえ答えが単一の依存関係チェーンによって決定されるとしても、完全な中間文字列を不必要に再構築しようとする可能性があります。 

## アプローチ

 中心的な問題は、変換によって文字に対する有向書き換えシステムが定義されることです。 各文字は文字列になり、その文字列がインデックスが前方にどのように伝播するかを定義します。 

ブルートフォースメソッドは、各メソッドの後に完全な文字列を直接構築します。`k`変化。 各ステップでは、すべての文字が展開によって置き換えられます。 k ステップ後の全長が N の場合、各変換のコストは O(N) となり、N 自体は乗算的に増加します。 たとえ最小の制約下であっても、これはすぐに爆発的に実現可能性を超えてしまいます。 主な理由は、クエリに必要な位置は 1 つだけであるにもかかわらず、文字列全体を繰り返し再計算することです。 

重要な点は、完全な文字列は決して必要ないということです。 変換を通じて位置がどのように逆方向にマッピングされるかを知る必要があるだけです。 前方に拡張する代わりに、最終文字列のインデックスが以前の文字列からどのように由来するかを追跡します。 

わかっていれば、各キャラクターごとに`c`、t ステップ後の展開の長さによって、どの文字が i 番目の位置に寄与するかを決定できます。 どの文字から来たのかを特定したら、プレフィックス オフセットを減算し、前のステップを再帰的に続行します。 

これは、逆シミュレーションを示唆しています。文字列を構築する代わりに、関数を維持します。`len[c][t]`キャラクターの成長の長さを説明する`c`後になる`t`ステップ。 次に、クエリに答えるために、次のステップに進みます。`k`0 まで減少し、そのたびに正しい子セグメントが選択されます。 

計算するには`len[c][t]`、動的プログラミングを使用します。 ステップ 0 では、各文字の長さは 1 です。トランジションの場合、`c`ステップ t では、次の文字の長さの合計です。`p_c`ステップt-1で。 以来`k`最大 10^4 までの値を指定できるため、これらの値を繰り返し計算します。 

長さがわかったら、クエリへの応答は決定論的な降下になります。各ステップで、展開内のどの文字に位置が含まれているかを特定します。`i`、更新します`i`それに応じて。

 ## アルゴリズムのチュートリアル

 このソリューションを、展開長の前処理とクエリの走査に分割しました。 

1. テーブルを事前計算する`len[c][t]`、 どこ`len[c][t]`文字を展開して得られる文字列の長さです`c`その通り`t`回。 初期化する`len[c][0] = 1`なぜなら、ステップ0では各文字はそれ自体であるからです。 これが再帰の基本ケースを形成します。 
2. 各ステップごとに`t`1から`k`、計算する`len[c][t]`の文字を反復処理することで、`p_c`。 キャラクターごとに`x`で`p_c`、追加します`len[x][t-1]`。 これは、1 つの変換で置き換えられるため機能します。`c`と`p_c`、その文字列内の各シンボルは、前のステップの長さに応じて独立して展開されます。 
3. 質問に答えるため`(s, k, i)`、まず概念的にステップから開始します`k`そして位置`i`初期文字列の展開内で`s`。 
4. 次の文字を反復処理します。`s`、それぞれをサイズが次のブロックとして扱います。`len[c][k]`。 最初のブロックが見つかります。`i`落ちる。 特定されたら、以前のブロックのサイズを差し引いて、その文字に焦点を当てます。 これにより、問題は 1 つの文字の展開内で答えを見つけることになります。 
5. ここで、ステップからの 1 人のキャラクターの降下を繰り返しシミュレートします。`k`ステップ0へ。ステップ時`t`、私たちは見ます`p_c`どの文字の展開に位置が含まれるかを決定します`i`レベルで事前に計算された長さを使用する`t-1`。 正しい子が見つかるまでプレフィックスの合計を減算し、その子を次のステップで続行します。`t-1`。 
6. いつ`t`0 に達すると、基本文字に到達し、これが答えになります。 

### なぜ効果があるのか

 再帰のあらゆるレベルで、次の不変条件を維持します。`i`は、特定の深さでの特定の文字の展開内の有効な位置を指します。 DP テーブルは各ステップのセグメント長が正しいことを保証するため、プレフィックスの減算によって常に正しいサブツリーが選択されます。 各変換は展開を互いに素に連結したものであるため、位置マッピングは明確に定義されており、決して曖昧ではありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    while True:
        line = input().strip()
        if not line:
            return
        parts = line.split()
        if not parts:
            continue

        s = parts[0]
        k = int(parts[1])
        i = int(parts[2])

        p = [input().strip() for _ in range(26)]

        # dp[c][t] = length after t expansions
        dp = [[0] * (k + 1) for _ in range(26)]

        for c in range(26):
            dp[c][0] = 1

        for t in range(1, k + 1):
            for c in range(26):
                total = 0
                for ch in p[c]:
                    total += dp[ord(ch) - 97][t - 1]
                    if total > 10**18:
                        total = 10**18
                dp[c][t] = total

        # find starting character at level k
        cur_i = i
        cur_t = k

        # reduce from initial string s
        for ch in s:
            c = ord(ch) - 97
            if cur_i > dp[c][cur_t]:
                cur_i -= dp[c][cur_t]
            else:
                cur = c
                break

        # descend
        while cur_t > 0:
            for ch in p[cur]:
                nxt = ord(ch) - 97
                if cur_i > dp[nxt][cur_t - 1]:
                    cur_i -= dp[nxt][cur_t - 1]
                else:
                    cur = nxt
                    cur_t -= 1
                    break

        print(chr(cur + 97))

if __name__ == "__main__":
    solve()
```最初のフェーズでは、各行が文字に対応し、各列が適用される変換の数に対応する DP テーブルを構築します。 10^18 での飽和は、正確な巨大な値ではなく、i との比較のみが必要なため、オーバーフローに対する実用的な保護手段となります。 

最初のループオーバー`s`調整されたインデックスを使用して、問題を複数文字の文字列から単一の開始文字に折りたたみます。 2 番目のループは、プレフィックスの減算を使用して、どのブランチにターゲット位置が含まれているかを決定し、変換ツリーの実際の逆走査を実行します。 

重要な実装の詳細は一貫して正しい深さを使用しています`cur_t - 1`子供の検査をするとき。 DP レベルとトラバース レベルの間に不一致があると、正確性は直ちに損なわれます。

 ## 特殊なケース

 脆弱な状況の 1 つは、クエリ インデックスが最初の文字列内の 2 つの展開された文字間の境界に正確に位置する場合です。 仮定する`s = "ab"`、 と`a`長さ 3 に拡張し、`b`最終ステップで長さ 2 になり、`i = 3`。 アルゴリズムは最初にチェックします`a`、それがわかります`i`はそのブロック内にあり、それ以降は正しく減算されません。 代わりに`i = 4`の全長を減算します。`a`そして内部に続きます`b`。 この境界処理は完全に厳密な条件に依存します。`>`プレフィックス減算での比較。 

もう 1 つのケースは、次のような深い単一文字チェーンです。`a -> b -> c -> c`。 大きくなってからも`k`、DP テーブルが安定し、トラバーサルは単に決定的なポインター チェーンに従います。 このアルゴリズムでは文字列を展開する必要はなく、レベルを下げながら単一のインデックスを繰り返し解決するだけです。
