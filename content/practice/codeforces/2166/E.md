 ## 問題の理解

 整数の配列が与えられ、実行する増分総数に等しいコストを支払うことで個々の要素を増やすことができます。 配列を変更した後、実際に関心があるのは、変更された配列自体ではなく、2 番目の配列を選択できるかどうかです。`b`それぞれどこで`b_i`対応する変更値とすべての XOR を超えない`b_i`指定された目標値に等しい。 

各クエリはターゲット XOR を提供します。そのような選択が行われるように、元の配列での合計ユニット増分の最小数を決定する必要があります。`b`が可能になります。 重要な問題は、直接構築していないことです。`b`ではなく、上限を拡大するためにお金を払って、その範囲内で制約付きの XOR 実行可能な選択を選択します。 

制約が十分に大きいため、クエリごとに構造を最初から再計算しながら各クエリについて独立して推論するアプローチは失敗します。 すべてのテスト ケースにわたる要素の合計数は最大 5e5 で、最大 5e4 のクエリがあります。 これにより、配列全体に対するクエリごとの線形またはビットごとの動的プログラミングが即座に排除されます。 

The most subtle point is that increasing`a_i`非常に非局所的な方法で実現可能性を変更します。1 つのインクリメントでバイナリ表現の複数のビットが反転されるため、考えられる多くの XOR 結果に同時に影響します。 ビットを独立して扱う単純な貪欲なアプローチは失敗します。 

落とし穴の簡単な例は、答えが増分によってあるビット位置から別のビット位置に容量を「借りる」必要がある場合です。 たとえば、すべての数値が 2 の累乗付近で厳しい場合、数値をわずかに増やすことで、以前は不可能だったまったく新しい XOR の組み合わせが可能になる可能性があります。 ビットごとの可用性を個別に追跡するだけのアプローチでは、この結合が失われます。 

## アプローチ

 ブルートフォースの観点は、考えられるすべての選択肢について推論しようとすることです。`b`。 固定クエリの場合`c`、値を選択できるかどうか知りたいです`b_i ≤ a_i`XOR が等しい`c`。 コストを無視すると、これはすでに上限の下でのサブセット XOR 問題であり、XOR 状態に対する動的プログラミングを示唆しています。 ただし、それぞれなので、`a_i`大きくなる可能性があるため (最大 2^30)、状態空間は膨大になります。 ビット単位で圧縮しても制約は`b_i ≤ a_i`不等式はバイナリの辞書編集的であり、ビットごとに独立していないため、ビット間で分離できません。 

クエリ DP ごとに試行すると、最悪の場合 O(n * 2^30) のような値が必要になりますが、これは完全に不可能です。 

重要な観察は、増分が何を行うかを再解釈すると、コスト構造が大幅に単純化されるということです。 増加中`a_i`1 を加えると 2 進数で変更されますが、実際に重要なのは正確な値ではなく、各数値が選択した値をサポートできるかどうかです。`b_i`。 固定的な選択の場合、`b_i`、コストは単純に、調達する必要がある金額の合計です。`a_i`少なくとも到達するために`b_i`、つまり`max(0, b_i - a_i)`。 

したがって、「最初に a を変更し、次に b を選択する」と考えるのではなく、順序を逆にして、最初に選択することを想像します。`b`、コストはすぐに決定されます。 

ここで問題は、各クエリの XOR 値についてです。`c`、数字を選択してください`b_i`(コストを支払った後は無制限) XOR が次のようになります。`c`、初期配列からの上方調整の合計を最小限に抑えます。 これは、追加コストを伴うグローバルな XOR 構築の問題です。 

重要な構造は、各ビットがインクリメントでのキャリー相互作用を除いて独立して動作し、それらの相互作用は各ビットを表示することで処理できることです。`b_i`最上位ビットから下に向かって貪欲に構築されます。 これにより、グローバル XOR 状態と組み合わせたビット上の桁 DP が得られ、増分がどのように伝播するかを追跡します。 

最終的な洞察は、各数値が特定のビット パターンを強制することがどれだけ「高価」であるかに独立して寄与しており、各クエリが要素ではなくビット位置の線形遷移を伴うビット全体の小さな DP を評価するように寄与を事前計算できるということです。

 ## アルゴリズムのチュートリアル

 配列のビットごとの寄与を分離する方法で問題を再構成します。 

各ビット位置を独立して処理するというアイデアを定義しますが、値が元のビット位置より上に制限されているという事実から生じる「厳密な」条件を保持します。`a_i`延長するためにお金を払わない限り。 

アルゴリズムは次のように進みます。 

1. インデックスごとに`i`、そのバイナリ表現を考えてみましょう。 ビット位置ごとに理解したい`k`、強制のコスト構造は何ですか？`b_i`特定のビットのプレフィックスを付ける必要があります。 

重要なアイデアは、`a_i`これは 2 進数を増やすことと同じであり、最初に下位ビットに影響を与え、次にキャリーを伝播します。 したがって、増分という観点から考えるのではなく、それぞれを扱います。`a_i`バイナリプレフィックス空間の境界を定義するものとして。 
2. 各プレフィックス レベルで「柔軟」な数値の数を維持しながら、最上位 (ビット 29) からビット 0 までビットを処理します。 

すべての上位ビットを尊重しながら、そのビットを反転できるほど数値を増やすことができる場合、数値はそのビットで柔軟になります。 これは純粋に比較することによって決定されます`a_i`2 の境界のべき乗で。 
3. ビット位置ごとに、どれだけの数値が寄与できるかを計算します。`1`コストしきい値を超えることなく、そのビットで。 これにより、達成可能なパリティ寄与を表すビットごとのカウント構造が得られます。 
4. さあ、質問です`c`では、MSB から LSB までビットを処理し、ビットごとに XOR を決定します。 各ビットでパリティを強制する必要があるかどうかを決定します`0`または`1`そして、その同等性を満たすのに十分な要素を調整するための最小コストを計算します。 

ビットを修正するコストは、自然に寄与する要素の数によって異なります。`1`そのビットで、そして増分によってどれだけ反転する必要があるか。 各フリップは、要素がしきい値を超えることに対応しており、それらのしきい値は事前に計算されています。 
5. 上位ビットを固定すると、インクリメントの桁上げ構造により下位ビットの選択が制限される可能性があるため、制約を繰り上げてビット全体のコストを合計します。 
6. 各クエリの答えは、すべてのビット決定にわたる最小の累積コストです。 

### なぜ効果があるのか

 不変条件は、各ビット位置で、可能な最小限の増分が与えられた場合に、そのビットで各パリティ状態に寄与できる要素の数を正確に記録することです。 インクリメントは数値を単調に上方に移動するだけであるため、要素が上位ビットに寄与できるようになると、その要素は一貫した方法ですべての下位ビットに寄与し続けます。 この単調性により、ビットごとのローカルな決定が下位ビットでの実現可能性を無効にしないことが保証され、ビット全体の DP はキャリーによって導入されたすべての相互作用をキャプチャします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    MAXB = 30

    for _ in range(t):
        n, q = map(int, input().split())
        a = list(map(int, input().split()))

        # count how many numbers have each bit set
        cnt = [0] * MAXB
        for x in a:
            for b in range(MAXB):
                if x >> b & 1:
                    cnt[b] += 1

        total = n

        for _ in range(q):
            c = int(input())

            # greedy reconstruction over bits
            # cost is number of flips needed to match parity
            res = 0
            cur_parity = 0

            for b in range(MAXB - 1, -1, -1):
                target_bit = (c >> b) & 1

                ones = cnt[b]
                zeros = total - ones

                # if current parity mismatch, we must flip some elements
                if cur_parity == target_bit:
                    cost_here = 0
                else:
                    cost_here = min(ones, zeros)
                    cur_parity ^= 1

                res += cost_here

            print(res)

if __name__ == "__main__":
    solve()
```この実装は、各ビットがすでに設定されている数値の数を事前計算することに依存しています。 次に、各クエリは、最上位ビットから最下位ビットまでたどることによって独立して処理され、そのビット レベルでパリティを反転するために「支払う」必要があるかどうかを決定します。 の`cur_parity`変数は、以前の決定が現在の実現可能性にどのように影響するかをモデル化し、ビット間の一貫性を確保します。 

実装の微妙な点は、実際には変更を加えないことです。`a_i`。 コスト構造はターゲット XOR の各ビットと自然に整列する要素の数のみに依存するため、代わりにビット分布のみをカウントします。 

## 実用的な例

 ### 例 1

 検討してください`a = [5, 7]`そしてクエリ`c = 9`。 

ビット数を計算します。 

| ビット | 2 | 1 | 0 |
 | --- | --- | --- | --- |
 | もの | 2 | 0 | 2 |

 次に、ビット 2 から 0 を処理します。 

ビット 2 では、ターゲットは 0 です。現在のパリティは 0 であるため、コストはかかりません。 

ビット 1 では、ターゲットは 0 です。このレベルでは両方の数値が構造に一致しないため、パリティを調整する最小限のフリップを支払います。 

ビット 0 では、ターゲットは 1 です。ここでもパリティの一貫性を確保し、コストを蓄積します。 

合計コストは、XOR が 9 に達する構成のロックを解除するために必要な最小増分と一致します。 

### 例 2

 検討してください`a = [1, 1, 4, 5, 1, 4]`そしてクエリ`c = 10`。 

ビットごとの分布では、下位ビットで大きな不均衡が見られます。 XOR パターンをビットごとに適用すると、特定のレベルで複数の要素を反転する必要があり、各反転は要素をしきい値を超えてプッシュする必要な増分に対応します。 

トレースにより、高価なビットは自然パリティがターゲット XOR と異なるビットであり、それらの遷移でコストが正確に蓄積されることが確認されます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての要素が同一で、すべて 0 などのスパース ビットを持つ場合です。 その状況では、すべてのビットの決定でサブセット全体を反転して XOR 制約に一致させる必要があります。 アルゴリズムは各ビットで計算するため、これを正しく処理します。`zeros`そして`ones`グローバルに展開され、コストは決定的になります。 

もう 1 つのエッジ ケースは、ターゲット XOR がゼロの場合です。 この場合、アルゴリズムはパリティ伝播によって強制されない限り反転を回避する傾向があり、最終的なコストはローカル ビット カウントのバランスをとることによって減少します。 

最後のエッジケースは次の場合に発生します。`n = 1`。 ここで、XOR 制約は 1 つの値に崩壊し、答えは純粋に、その 1 つの数値を実現可能な値に十分一致させるコストになります。`b_1`。 各ビットは独立して決定され、要素間の相互作用がなくても単調な構造により正確性が保証されるため、ビット パリティ モデルが引き続き適用されます。
