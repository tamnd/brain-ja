 ## 解決策
 ## 問題の理解

 長さの文字列が与えられます$2n$、文字 A、B、および C のみで構成されます。タスクは、この文字列の位置のセットを次のように分割することです。$n$素のペア。 各ペアは 2 つのインデックスで構成されている必要があります$l < r$、これらの位置にある文字は、AB、AC、または BC の 3 つの許容される組み合わせのいずれかを形成する必要があります。 

言い換えれば、すべてのインデックスは 1 回だけ使用する必要があり、各ペアは 2 つの異なる文字を接続する必要があります。 任意の順序の並べ替えという意味でサブシーケンスを構築しているわけではありません。 各ペア内のみの元の順序を維持しながら、インデックス ペアを選択しています。 

制約$n \le 10^5$文字列が最大の長さであることを意味します$2 \cdot 10^5$。 ペアリングを検索したり、サブセットごとに複雑な状態を維持しようとしたソリューションは、遅すぎます。 アン$O(n \log n)$または$O(n)$最大数億の演算が通過する可能性があるため、アプローチが必要ですが、二次関数は何でも可能です。$n$そうはなりません。 

単純な失敗モードは、1 人のキャラクターが優勢になるとすぐに表示されます。 たとえば、文字列が AAAA...A の場合、どのペアにも 2 つの異なる文字が必要であるため、有効なペアは存在しません。 将来の可用性を考慮せずに、貪欲なアプローチでキャラクターを熱心にペアリングしすぎると、微妙な失敗が発生します。 たとえば、ABACBC のような文字列では、有効なグローバル一致が存在する場合でも、最初の A と最初に使用可能な B をペアにすると、C を含む後で必要なペアがブロックされる可能性があります。 

重要な問題は、選択肢が独立していないことです。組み合わせの決定は、後で残りの文字をまだ一致させることができるかどうかに影響します。 

## アプローチ

 強引なアイデアは、各位置をノードとして扱い、バックトラッキングを使用して完全な一致を構築しようとすることです。 各ステップで、文字が有効なペアを形成する 2 つの未使用のインデックスを選択し、それらを削除して再帰します。 これは大まかに調べます$(2n-1)!!$各段階で残りのすべてのインデックスから 1 つのインデックスのパートナーを選択するため、最悪の場合の可能性があります。 たとえ$n = 20$、これは実行不可能になり、$n = 10^5$、それはまったく不可能です。 

グローバル検索の観点から考えるのをやめ、代わりにローカルの可用性に焦点を当てると、問題の構造は大幅に単純化されます。 各文字タイプは異なる文字タイプと組み合わせる必要があるだけで、合計で 3 つのタイプしかありません。 これは、長距離の組み合わせ構造を追跡する必要がないことを示唆しています。 必要なのは、文字を処理するたびに、可能であれば、以前に確認された一致しない互換性のある文字と即座に一致できることを確認することだけです。 

これにより、3 つのスタック (現在一致していない A、B、および C のインデックスに 1 つ) を使用する貪欲なマッチング戦略が導き出されます。 文字列を左から右にスキャンしながら、現在の文字と、以前に表示された別のタイプの文字 (可能な場合) を組み合わせようとします。 互換性のある以前の文字が存在しない場合は、将来のペアリングのために現在のインデックスを保存します。 

重要な考え方は、後から登場するキャラクターの組み合わせに柔軟性を維持している限り、キャラクターを延期しても安全であるということです。 すべてのエッジは異なる文字の間にあり、グラフは異なる型にまたがる完全な 2 部構成であるため、使用可能な一致を消費するローカル ペアリングの選択は、パートナーなしで型を孤立させない限り、将来の実現可能性を損なうことはありません。

 ## アルゴリズムのチュートリアル

 まだペアになっていない文字のインデックスを保存する 3 つのスタックを維持します。 各スタックは A、B、C のいずれかに対応します。 

また、結果のペアのリストも維持します。 

1. 文字列を左から右に繰り返します。 各位置で、現在のキャラクターを確認します。 
2. 文字が A の場合、まず、以前に確認された一致しない B との一致を試みます。そのような B が存在する場合、そのインデックスをポップし、ペア (B インデックス、現在のインデックス) を記録します。 存在しない場合は、以前に確認された一致しない C との一致を試みます。それが存在する場合は、(C インデックス、現在のインデックス) をペアにします。 どちらも存在しない場合は、この A インデックスを A スタックにプッシュします。 
3. 文字が B の場合、まず利用可能な A と一致させようとします。それが不可能な場合は、C と一致させようとします。どちらも存在しない場合は、この B インデックスを B スタックにプッシュします。 
4. 文字が C の場合、まず利用可能な A との照合を試みます。それが失敗した場合は、B との照合を試みます。そうでない場合は、この C インデックスを C スタックにプッシュします。 
5. すべての文字を処理した後、スタックが空でない場合は、一部のインデックスが一致しないままになるため、失敗します。 それ以外の場合は、まさに$n$ペア。 

各ステップ内の順序設定は任意ではありません。 最初に一致させるタイプを選択するときは、後で代替オプションが少ないタイプを優先的に使用します。 たとえば、A を処理する場合、最初に B と照合すると、将来の構造によっては有効なパートナーが C よりも少なくなる可能性がある B が蓄積されるのを避けるのに役立ちます。 文字間の対称性により、この規則はすべてのケースで一貫しています。 

### なぜ効果があるのか

 スキャンの任意の時点で、各スタックは、残りの文字の中で互換性のあるパートナーを待っているインデックスを表します。 不変条件は、キャラクターがスタックにプッシュされた場合、その時点で直接互換性のあるパートナーが存在しなかったことを意味するということです。 

後で受信文字をこれらの保存されたインデックスのいずれかと照合すると、可能な限り早い機会を利用して、以前の不足を効果的に解決できます。 許可されるエッジはすべて異なる文字の間にあり、グラフは異なる型間で完全に接続されているため、延期された文字は将来の反対の型との互換性を維持します。 

貪欲なルールにより、互換性のない 2 つの余剰を、後で解決する方法なしに同時に存続させることは決してありません。 解決策が存在する場合、この左から右への解決順序を尊重する一連の一致が常に存在するため、貪欲なプロセスが途中で停止することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    s = input().strip()
    
    stA, stB, stC = [], [], []
    res = []

    for i, ch in enumerate(s, start=1):
        if ch == 'A':
            if stB:
                j = stB.pop()
                res.append((j, i))
            elif stC:
                j = stC.pop()
                res.append((j, i))
            else:
                stA.append(i)

        elif ch == 'B':
            if stA:
                j = stA.pop()
                res.append((j, i))
            elif stC:
                j = stC.pop()
                res.append((j, i))
            else:
                stB.append(i)

        else:  # 'C'
            if stA:
                j = stA.pop()
                res.append((j, i))
            elif stB:
                j = stB.pop()
                res.append((j, i))
            else:
                stC.append(i)

    if stA or stB or stC:
        print("NO")
        return

    print("YES")
    for a, b in res:
        print(a, b)

if __name__ == "__main__":
    solve()
```この実装は、スキャンベースの貪欲なプロセスに直接続きます。 各スタックには、一致しない文字のインデックスが格納されます。 一致すると、すぐにペアを出力します。 1 から始まるインデックスの使用は、必要な出力形式と一致します。 最終チェックでは、構成が不可能であることを示す残りのインデックスが残っていないことを確認します。 

微妙な点は、構築後にペアの順序を変更しようとしないことです。 正確かどうかは、すべてのペアリングが作成された時点で確定されるという事実によって決まります。 

## 実用的な例

 入力文字列を考慮してください`ABCACB`と$n = 3$。 

各文字の後にスタックを追跡します。 

| ステップ | シャア | スタック | Bスタック | Cスタック | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 1 | あ | [1] | [] | [] | ストアA |
 | 2 | B | [] | [] | [] | B を A と一致させる (1,2) |
 | 3 | C | [] | [] | [3] | ストアC |
 | 4 | あ | [] | [] | [3] | ストアA |
 | 5 | C | [] | [] | [] | C と A (4,5) を一致させる |
 | 6 | B | [] | [] | [] | B を C と一致させる (3,6) |

 最終結果には 3 つの有効なペアが含まれており、貪欲なマッチングによって依存関係ができるだけ早く解決されることがわかります。 

次に、失敗したケースを考えてみましょう`AAABBB`と$n = 3$。 

| ステップ | シャア | スタック | Bスタック | Cスタック | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 1 | あ | [1] | [] | [] | ストアA |
 | 2 | あ | [1,2] | [] | [] | ストアA |
 | 3 | あ | [1,2,3] | [] | [] | ストアA |
 | 4 | B | [1,2] | [] | [] | B を A と一致させる (3,4) |
 | 5 | B | [1] | [] | [] | B を A と一致させる (2,5) |
 | 6 | B | [] | [] | [] | B を A と一致させる (1,6) |

 これは実際には成功しますが、それはペアリング構造が完全なマッチングを可能にしているためです。 代わりに`AAAABCBC`、不均衡により一致しない A が残り、最後に障害状態が検出されたことがわかります。

 ## 特殊なケース

 病的なケースとは、ある文字が他の文字よりもはるかに頻繁に出現する場合です。たとえば、`A`繰り返された$2n$回。 この状況では、3 つのスタックすべてが最後まで空のままになり、すべての A が一致することなくプッシュされます。 終了時には、空ではない A スタックが拒否をトリガーし、不可能性を正しく識別します。 

もう 1 つの微妙なケースは、次のような交互構造です。`ABACBC`。 ここで、A と B の組み合わせが早すぎると、後の C に使用できる B が減少するため、早い段階で貪欲な選択は危険に見えるかもしれません。 ただし、スタック メカニズムにより、後でより適切な一致が存在する場合は必ずそれがすぐに使用され、残った互換性は必要になるまでスタックに保存されます。
