[CF 2052J - 賢明な監視](https://codeforces.com/problemset/problem/2052/J)

 **評価:** 2000
 **タグ:** 二分探索、貪欲、ソート
 **解決時間:** 2 分 10 秒
 **確認済み:** いいえ

 ## 解決策
 ## 問題の理解

 時間を競う 2 つの独立したアクティビティによるスケジュールのような状況が与えられます。 

片側には宿題があります。 各タスクには中断されずに一定の時間がかかり、それぞれに期限があり、それまでに完全に完了する必要があります。 ジルは、これらのタスクに取り組む順序を自由に選択できます。 

反対側には一連のテレビエピソードがあります。 それらは順番に視聴する必要があり、ジルがエピソードを開始したら、次に進む前にそれを終了する必要があります。 エピソードはプレフィックス構造を形成します。最初の k 個のエピソードを視聴するということは、常にそれらの長さの合計を正確に消費することを意味します。 

クエリ時間ごとに$t_k$、ジルが時間までに視聴できるエピソードの最大数を知りたいです。$t_k$、すべての締め切りが守られるようにすべての宿題タスクをスケジュールすることができます。 通話時間は単なるチェックポイントです。 仕事や視聴を妨げません。 

重要な相互作用は、エピソードの視聴により宿題に費やすことができる時間が消費されるということですが、宿題の実現可能性は、視聴に費やした時間後も期限に間に合うようにタスクを手配できるかどうかにのみ依存します。 

制約は大きく、テスト ケースごとに最大 200,000 のタスク、エピソード、クエリがあり、テスト ケース全体の合計も 200,000 に制限されます。 これにより、クエリごとに実現可能性を最初から再計算するアプローチは即座に除外されます。 平$O(nm)$または$O(n \log n)$クエリごとの速度が遅すぎます。 対数または定数のクエリ時間を持つ線形または線形前処理に近いものが必要です。 

締め切りが非常に緩い、または非常に厳しい場合、微妙なエッジケースが発生します。 

たとえば、何も監視していなくてもタスクがすでに不可能である場合、問題ステートメントはそのようなことが起こらないことを保証します。 これにより、重大な失敗のケースがなくなり、実行不可能な初期スケジュールに対処する必要がなくなりました。 

もう 1 つの注意が必要なケースは、エピソードのプレフィックスが大きいにもかかわらず、締め切りにより余裕がほとんどない場合です。 素朴なアプローチでは、「合計時間が収まれば大丈夫」と考えるかもしれませんが、締め切りによって順序付けの制約が課されるため、これは誤りです。 たとえば:

 入力:

 n = 2

 タスク: (5、d=5)、(5、d=6)

 総作業量が少なくても、最初のタスクを誤って遅らせると、実現可能性が損なわれる可能性があります。 したがって、実現可能性は単に合計に基づくものではありません。 それは期限の注文構造によって異なります。 

## アプローチ

 クエリのブルートフォース解釈は簡単です: 一定の時間$t$、エピソードの考えられるすべてのプレフィックスを試し、その合計の長さを計算し、それを利用可能な時間から差し引き、期限までにすべてのタスクをスケジュールできるかどうかを確認します。 

宿題の実行可能性の中核となるチェックは、単独では古典的です。タスクを期限で並べ替え、その順序で貪欲にスケジュールし、累積時間が現在の期限を超えないことを確認します。 これは$O(n \log n)$小切手ごとに。 

これをエピソードのすべてのプレフィックスとすべてのクエリに対して再計算すると、複雑さは次のようになります。$O(q \cdot m \cdot n \log n)$、これは与えられた制約ではまったく実現不可能です。 

重要な観察は、宿題の実現可能性は、エピソード時間の特定の配置ではなく、利用可能な合計時間のみに依存するということです。 エピソードの視聴によって「消費」される時間が決まると、残りの利用可能時間という 1 つの数字が残ります。 

したがって、問題は次のようになります。エピソードの長さのプレフィックスの合計ごとに、その残り時間内にすべてのタスクをスケジュールできるかどうかを判断します。 

これにより、構造がエピソードのプレフィックス全体で単調な状態に変わります。エピソードを視聴すればするほど、残り時間が減り、実現可能性はさらに難しくなります。 実現可能性を効率的に評価できれば、この単調性によりクエリごとの二分探索が可能になります。 

最後のステップでは、ソートの負荷が高いロジックを再計算することなくクエリ間で再利用できるように、実現可能性チェックを最適化します。 

一度、期限ごとにタスクを事前に分類します。 その場合、特定の時間制限の実現可能性は、時間を蓄積し、決して期限を超えないようにしながら、期限の増加順にタスクを貪欲に処理できるかどうかを確認することに帰着します。 

これは$O(n)$チェックごとに、各クエリのエピソード プレフィックスの合計に対する二分検索と組み合わせて、次のようにします。$O(q \log m \cdot n)$。 これでも最悪の場合は遅すぎます。 

本当の最適化は、宿題の重要な構造を事前に計算することです。残り時間ごとに貪欲に再チェックする代わりに、最小限のスラック要件を計算します。 

利用可能な時間を指定して関数を定義します。$T$、すべてのタスクをスケジュールできますか?

 この機能は単調です$T$, そのため、最大プレフィックス負荷制約を追跡する貪欲スイープを使用して、期限内にタスクを完了するために必要な最小時間を事前計算できます。 この値がわかると、各クエリは残り時間がこのしきい値以上であるかどうかを確認することになります。 

したがって、宿題を完全に単一のスカラー要件に分離します。 

ここで、各クエリは次のようになります。残り時間が宿題の要件を満たすのに十分な長さのエピソードの最大のプレフィックスを見つけます。 プレフィックス合計により二分検索が可能になります。

 ## アルゴリズムのチュートリアル

 私たちは問題を宿題の前処理とエピソードのクエリへの回答に分割しました。 

1. 期限を延ばして宿題タスクを並べ替えます。 これにより、有効なスケジュールは後の期限よりも前に期限を満たさなければならないため、常に最も厳しい制約を最初に考慮することが保証されます。 
2. 累積作業時間を維持しながらタスクを処理します。 各タスクでは、これまでに費やした合計時間が現在の期限を超えないようにします。 そうなった場合、概念的には、より早いスケジュールの柔軟性によって余分なスラックを除去する必要があることがわかります。 この問題では実現可能性が保証されているため、このスイープによって宿題時間の最小「必要な処理エンベロープ」が定義されます。 
3. 単一の値を計算する`need`、これは、期限を守ってすべての宿題を完了するために必要な有効な最小時間予算を表します。 これにより、スケジューリング制約が 1 つのスカラーに折りたたまれます。 
4. エピソードの長さのプレフィックスの合計を作成します。 これにより、任意のプレフィックスの合計視聴時間を定数時間で計算できます。 
5. クエリ時間ごとに$t$、残りの利用可能時間を次のように解釈します。$t - need$。 これがマイナスの場合、エピソードは視聴できません。 
6. それ以外の場合は、最大のインデックスを見つけます$k$prefix_sum[k] ≤ となるように$t - need$。 これは二分探索によって行われます。 
7. 出力$k$クエリごとに。 

### なぜ効果があるのか

 締め切りを貪欲に越えることで、宿題の可能な限りタイトなスケジュールのプレッシャーを捉えます。 有効な順序付けは、累積的な制約構造を尊重する必要があります。 この最小限必要な作業範囲がわかったら、エピソードの視聴は利用可能な合計時間から単純に減算されます。エピソードは厳密に連続しており追加コストがかかるため、最良の戦略は常に実行可能な最長のプレフィックスを取得することです。 単調性により、プレフィックス合計に対する二分探索の正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def compute_need(tasks):
    tasks.sort(key=lambda x: x[1])
    t = 0
    need = 0
    for a, d in tasks:
        t += a
        if t > d:
            need = max(need, t - d)
    return t  # total work is sufficient baseline

def feasible(tasks, limit):
    tasks.sort(key=lambda x: x[1])
    t = 0
    for a, d in tasks:
        t += a
        if t > d:
            return False
    return t <= limit

def solve():
    T = int(input())
    for _ in range(T):
        n, m, q = map(int, input().split())
        a = list(map(int, input().split()))
        d = list(map(int, input().split()))
        tasks = list(zip(a, d))
        l = list(map(int, input().split()))
        t = list(map(int, input().split()))

        tasks.sort(key=lambda x: x[1])

        prefix_need = 0
        cur = 0
        for a_i, d_i in tasks:
            cur += a_i
            if cur > d_i:
                prefix_need = max(prefix_need, cur - d_i)

        eps = [0] * (m + 1)
        for i in range(m):
            eps[i + 1] = eps[i] + l[i]

        res = []
        for tk in t:
            remain = tk - prefix_need
            if remain <= 0:
                res.append(0)
                continue

            lo, hi = 0, m
            while lo < hi:
                mid = (lo + hi + 1) // 2
                if eps[mid] <= remain:
                    lo = mid
                else:
                    hi = mid - 1
            res.append(lo)

        print(*res)

if __name__ == "__main__":
    solve()
```このソリューションは、タスクを期限ごとに分類し、期限内にスケジュールを実行可能にするために必要な最小有効スラックを計算することから始まります。 これは次のように保存されます`prefix_need`、これは時間の経過とともに固定間接費として機能します。 

次に、エピソードの長さにわたるプレフィックスの合計を構築して、プレフィックスの総再生時間を O(1) で計算できるようにします。 

各クエリは、利用可能な時間から宿題のオーバーヘッドを差し引き、エピソードのプレフィックスに対して二分検索を実行します。 エピソードの長さが正であるため、プレフィックスの合計は厳密に増加しているため、二分探索は安全です。 

よくある落とし穴は、タスクを一度グローバルに並べ替える必要があることを忘れていることです。 クエリ内で再計算するとすぐに TLE になります。 もう 1 つは、実現可能性がタスクの合計にのみ依存するという誤った仮定であり、厳しい中間期限では失敗します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O((n + m) \log m + q \log m)$| タスクを 1 回ソート、プレフィックス合計、クエリごとのバイナリ検索 |

 すべてのテスト ケースにわたる合計入力サイズが 200,000 に制限されており、すべての演算が要素ごとに線形または対数であるため、アルゴリズムは制約内に快適に適合します。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    T = int(input())
    out = []
    for _ in range(T):
        n, m, q = map(int, input().split())
        a = list(map(int, input().split()))
        d = list(map(int, input().split()))
        l = list(map(int, input().split()))
        t = list(map(int, input().split()))

        tasks = list(zip(a, d))
        tasks.sort(key=lambda x: x[1])

        cur = 0
        need = 0
        for ai, di in tasks:
            cur += ai
            if cur > di:
                need = max(need, cur - di)

        eps = [0]
        for x in l:
            eps.append(eps[-1] + x)

        res = []
        for tk in t:
            rem = tk - need
            if rem <= 0:
                res.append(0)
                continue
            lo, hi = 0, m
            while lo < hi:
                mid = (lo + hi + 1) // 2
                if eps[mid] <= rem:
                    lo = mid
                else:
                    hi = mid - 1
            res.append(lo)

        out.append(" ".join(map(str, res)))

    return "\n".join(out)

 ## 特殊なケース

 微妙なエッジケースは、すべてのタスクが余裕なく期限内に正確に収まる場合です。 その状況で`prefix_need`はゼロのままであり、解は純粋なプレフィックス和二分探索に帰着します。 減算は発生せず、すべてのエピソードの決定は次の要素のみに依存するため、アルゴリズムはこれを自然に処理します。`t`。 

もう 1 つのケースは、単一のタスクが蓄積中に期限をわずかに超過する場合です。 たとえば:

 入力:

 n = 2

 タスク: (5, 5)、(5, 9)

 2段階目で累積時間が10となり、期限の9を超えてしまうので、`prefix_need = 1`。 これにより、エピソードを考慮する前に、すべてのクエリが有効時間の 1 単位だけ正しく短縮されます。 その後、バイナリ検索が短縮された時間で実行され、小さな違反であってもローカルではなくグローバルに考慮されるようになります。 

最後に、クエリが次の値よりも小さい場合、`prefix_need`の場合、アルゴリズムは二分探索を呼び出さずに正しくゼロを返します。 これにより、不必要な計算が回避され、プレフィックス合計への誤った負のインデックス付けが防止されます。
