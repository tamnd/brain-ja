 ## 解決策
 ## 問題の理解

 各セルが塗りつぶされるか空になるグリッドで作業しており、各クエリから長方形のサブグリッドが得られます。 すべてのクエリについて、その四角形内の塗りつぶされたセルがスネークと呼ばれる有効な構造を形成しているかどうかを判断する必要があります。 

ここでのヘビは、単なる接続された形状ではありません。 一貫してジグザグにセルを訪問する 1 次元のパスのように動作する必要があります。 領域内のすべての塗りつぶされたセルは、単一の接続されたコンポーネントに属している必要があり、そのコンポーネントはステップごとに曲がるパスのように見える必要がありますが、分岐したりサイクルを形成したりすることはありません。 非公式には、曲がる線のように動作する必要がありますが、ブロックを分割したり埋めたりすることはありません。 

入力は、グリッドと多くの長方形のクエリで構成されます。 各クエリは、その四角形に限定された塗りつぶされたセルの誘導されたサブグラフが有効なスネーク構造を形成するかどうかを尋ねます。 

制約が大きいため、クエリごとに連結成分を再計算することは不可能です。 すべてのクエリ四角形内のすべてのセルに触れるアプローチは、グリッド サイズとクエリ数の積のオーダーで最悪のケースに直接つながり、これは許容範囲をはるかに超えています。 単一のグリッド スキャンはすでに N 倍 M で線形であり、クエリの数が大きくなる可能性があるため、クエリごとの BFS または DSU の再構築でも一般的な制限を超えます。 

単純にクエリごとにフラッド フィルを実行し、コンポーネントがパスを形成するかどうかを検証するという単純な考えは、失敗することがよくあります。 これは、クエリが重なり合う場合やグリッドが大きい場合には、各セルが何度も再訪される可能性があるため、すでに問題が発生しています。 

2 番目の微妙な失敗例は、接続のみをチェックすることで発生します。 接続された領域がスネークにならない場合もあります。 たとえば、2 x 2 の完全に塗りつぶされたブロックは接続されていますが、複数の方向に分岐しているため、無効です。 同様に、T 字型の構成は接続されていますが、単純なパスではありません。 

もう 1 つの微妙な問題は、程度をチェックするだけで十分であると想定していることです。 すべてのセルの次数が最大 2 であっても、サイクルが出現する可能性はありますが、ヘビではサイクルは許可されません。 

## アプローチ

 ブルート フォース戦略により、各クエリの全体像が構築されます。 特定の四角形について、すべての塗りつぶされたセルを収集し、グラフの走査を実行して接続されたコンポーネントを抽出し、各コンポーネントを検証します。 検証ステップでは、コンポーネントが分岐や循環のない単純なパスであることを確認しようとします。 

コンポーネントを検証する 1 つの方法は、セルを並べ替えて線形順序を再構築してみることです。 コンポーネントが有効なスネークの場合、一貫した座標順序が 2 つあります。1 つは増加方向、もう 1 つは逆ジグザグ方向です。 ソート後、連続した差異がユニットの動きのように動作するかどうか、および移動パターンが一貫して交互に行われるかどうかを確認します。 これが機能するのは、スネークは基本的に、方向が決まれば曖昧さのないグリッドに埋め込まれたパスであるためです。 

この強引なアプローチは、クエリごとに構造を最初から直接再構築するため、正しいものです。 障害点は実行時です。 最悪の場合、1 つのクエリがグリッド全体をカバーし、多数のクエリが存在する可能性があるため、同じデータに対して繰り返しグラフの走査を行うことになります。 これにより、最悪のシナリオではおよそ O(QNM) の動作が発生しますが、これは大きすぎます。 

重要な洞察は、実際にはクエリごとにコンポーネントを再構築する必要がないということです。 グリッドはグローバルに前処理できます。 クエリがスネークを誘発するかどうかを尋ねる代わりに、視点を反転して、グリッド内の任意の場所のスネークと互換性のないローカル パターンは何かを尋ねます。 すべての禁止されたローカル パターンを特徴付けると、各クエリは、禁止されたパターンがその中に完全に出現するかどうかをチェックすることになります。

この移行は、クエリごとの動的なグラフ推論から、グリッド上の静的なパターン検出への移行です。 ヘビの構造は非常に堅固であるため、小さな一定サイズの構成で障害が発生するはずです。 これにより、接続の再構築への依存が解消されます。

 ## アルゴリズムのチュートリアル

 私たちは、すべての無効なヘビには、局所的に検出できる小さな禁止パターンが含まれているという事実を信頼しています。 

1. グリッドを 1 回スキャンし、3 つのブール プレフィックス合計テーブルを事前計算します。 1 つは水平方向に 3 つの連続した塗りつぶされたセルの発生を追跡し、もう 1 つは垂直方向に同じ追跡を追跡し、もう 1 つは 2 x 2 の正方形の塗りつぶしを追跡します。 この前処理により、長方形の存在クエリに一定時間で答えることができます。 
2. これらのテーブルを作成する際、禁止されたパターンごとに特別なアンカー セルをマークします。 水平トリプルの場合、すべての出現箇所の中央のセルにマークを付けます。 垂直トリプルの場合は、中央のセルにもマークを付けます。 2 x 2 ブロックの場合は、左上のセルにマークを付けます。 この正規化により、すべての禁止構造が正規の代表セルを持つことが保証されます。 
3. これらのマークされたセルに対して 2D プレフィックス合計を構築します。 各プレフィックスの合計は、1 つの禁止パターン タイプに対応します。 これにより、そのタイプのマークされたセルがクエリ四角形内にあるかどうかをカウントできるようになります。 
4. 各クエリ四角形について、3 つのプレフィックスの合計をすべてチェックします。 それらのいずれかがゼロ以外のカウントを報告する場合、その四角形には禁止された構成が含まれており、ヘビであることはできません。 
5. どのプレフィックス合計でも禁止パターンが検出されない場合、その領域は有効であると結論付けます。 

### なぜ効果があるのか

 有効なスネークは、グリッドに埋め込まれた単純なパスです。 パス構造から逸脱すると、分岐点、サイクル、またはトラバースのあいまいさを強制する 2 x 2 の塗りつぶされたブロックのいずれかを導入する必要があります。 これらの障害はすべて、行または列に並んだ 3 つの連続したセル、または 2 × 2 の完全に塗りつぶされた正方形という 3 つのローカル パターンのうちの少なくとも 1 つとして現れます。 これらのパターンは、非ヘビ構造の最小限の証明書です。 すべての違反にはこれらのパターンのいずれかが含まれるため、その存在を検出することは、無効なスネークを検出することと同じです。 プレフィックスの合計により、そのようなパターンがクエリ四角形の完全に内側のどこかに存在する場合、その正規のマーク付きセルを通じて検出されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_prefix(mark):
    n = len(mark)
    m = len(mark[0])
    ps = [[0] * (m + 1) for _ in range(n + 1)]
    for i in range(n):
        row_sum = 0
        for j in range(m):
            row_sum += mark[i][j]
            ps[i + 1][j + 1] = ps[i][j + 1] + row_sum
    return ps

def rect_sum(ps, r1, c1, r2, c2):
    return ps[r2][c2] - ps[r1][c2] - ps[r2][c1] + ps[r1][c1]

def solve():
    n, m, q = map(int, input().split())
    grid = [list(map(int, input().split())) for _ in range(n)]

    hor = [[0] * m for _ in range(n)]
    ver = [[0] * m for _ in range(n)]
    sq = [[0] * m for _ in range(n)]

    for i in range(n):
        for j in range(m - 2):
            if grid[i][j] and grid[i][j + 1] and grid[i][j + 2]:
                hor[i][j + 1] = 1

    for i in range(n - 2):
        for j in range(m):
            if grid[i][j] and grid[i + 1][j] and grid[i + 2][j]:
                ver[i + 1][j] = 1

    for i in range(n - 1):
        for j in range(m - 1):
            if grid[i][j] and grid[i][j + 1] and grid[i + 1][j] and grid[i + 1][j + 1]:
                sq[i][j] = 1

    ps_h = build_prefix(hor)
    ps_v = build_prefix(ver)
    ps_s = build_prefix(sq)

    out = []
    for _ in range(q):
        r1, c1, r2, c2 = map(int, input().split())
        r1 -= 1
        c1 -= 1

        bad = 0
        bad |= rect_sum(ps_h, r1, c1, r2, c2)
        bad |= rect_sum(ps_v, r1, c1, r2, c2)
        bad |= rect_sum(ps_s, r1, c1, r2, c2)

        out.append("YES" if bad == 0 else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションでは、3 つの個別のパターン グリッドを前処理します。 水平配列と垂直配列には、3 行構成の標準マーカーが格納され、重複するパターンが二重にカウントされないようにします。 正方形配列には、2 x 2 ブロックの左上のアンカーが格納されます。 

プレフィックス合計の構築は標準の 2D 累積であり、定数時間の四角形クエリをサポートするための追加の行と列が含まれています。 各クエリは、3 つの定数時間範囲合計チェックになります。 

よくある実装上の間違いは、アンカー セルの位置がずれていることです。 トリプルの中央ではなく左端または右端のセルにマークを付けると、重複するパターンが二重にカウントされたり、クエリ四角形の境界付近で見逃されたりする可能性があります。 一貫した正規中心を使用することで、この曖昧さを回避できます。 

もう 1 つの微妙な問題は、プレフィックス合計の境界が半分開いていることを忘れていることです。 この実装では、入力の変換後に内部的に [r1, r2) スタイルのインデックス付けを一貫して使用します。 

## 実用的な例

 中央に 2 × 2 のブロックが表示される小さなグリッドを考えてみましょう。 

入力グリッド:```
1 1 0
1 1 0
0 0 0
```クエリ: フルグリッド。 

| ステップ | ホル | バージョン | 平方 | 四角形チェック |
 | --- | --- | --- | --- | --- |
 | 前処理 | なし | なし | マーク (0,0) | - |
 | クエリ | - | - | 見つかりました | 悪い=1 |

 正方形のマーカーはクエリ四角形の内側で検出されるため、答えは「いいえ」です。 これは、すべてのセルが接続されているにもかかわらず、その構造がスネーク ルールに違反していることを示しています。 

次に、有効な真っ直ぐなヘビを考えてみましょう。```
1 1 1 0
0 0 0 0
```クエリ: フルグリッド。 

| ステップ | ホル | バージョン | 平方 | 四角形チェック |
 | --- | --- | --- | --- | --- |
 | 前処理 | 真ん中のマーク | なし | なし | - |
 | クエリ | 検出されました | - | - | 悪い=1 |

 これは最初は驚くかもしれませんが、長さ 3 の直線は​​、厳密な交互回転の定義の下では有効なヘビではありません。これは、移動の方向が交互でなければならず、連続する 3 つのステップの間同一線上に留まらないという要件に違反するためです。 

直線トリプルのない長さ 4 のジグザグは禁止パターンを生成せず、すべてのチェックに合格します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(NM + Q) | グリッド スキャンはパターン マーカーを 1 回構築し、各クエリは定数時間のプレフィックス合計を使用します。 
| スペース | O(NM) | 3 つの補助グリッドとプレフィックスの合計 |

 前処理はグリッド サイズに比例して拡張され、各クエリは数回の算術演算に削減されます。 これは、最大 2000 x 2000 のグリッドと大量のクエリ数の一般的な制約内に快適に適合します。

 ## 特殊なケース

 重要なエッジ ケースは、ちょうど 3 つのセルからなる直線を形成する領域です。 前処理では、このようなすべてのトリプルの中央のセルにマークが付けられるため、3 つのセルすべてをカバーするクエリによって、水平または垂直のプレフィックス合計がトリガーされます。 これにより、既にスネーク交互ルールに違反している短い同一線上のセグメントが誤って受け入れられるのを防ぎます。 

もう 1 つのケースは、クエリ境界付近で 2 x 2 のブロックが重なっている場合です。 マークされたセルは左上隅にあるため、正方形が部分的に含まれていても完全には含まれていないクエリではカウントされませんが、完全に含まれているクエリには常にそのアンカー セルが含まれます。 これにより、部分的なオーバーラップの下でも正確さが保たれます。 

最後の微妙なケースは、グリッド全体が 1 で満たされている場合です。 2 x 2 のサブスクエアごとにマークされたセルが作成されるため、十分に大きなクエリはすぐに失敗します。これは、そのような領域には多くの分岐構成が含まれており、単一のスネークにはなり得ないという事実を反映しています。
