 ## 解決策
 ## 問題の理解

 ゲームは概念的なグリッド上で行われ、各位置は行インデックスと列インデックスによって識別されます。 各行には配列の固定値が含まれます`a`、各列は配列の固定値を持ちます。`b`。 ゲームがセルで終了した場合`(r, c)`、スコアは単に合計です`a[r] + b[c]`。 

ルークは次から始まります`(1, 1)`。 各移動で、プレイヤーはルークを現在の行または現在の列に沿って他のセルにテレポートするか、ゲームを直ちに停止して現在の位置のスコアを取得することができます。 追加の制約が 1 つあります。各セルは最大 1000 回訪問でき、開始セルは既に 1 回訪問したものとしてカウントされます。 

アリスは最終的に選択したスコアを最小化したいと考えており、ボブはそれを最大化したいと考えており、彼らはアリスから開始して交互に手を動かします。 

重要な観察は、移動が非常に寛容であるということです。ルークはどのセルからでも、同じ行または列内の他のセルにジャンプできます。 これにより、グリッドは、到達可能性がローカルではなく「行または列がグローバル」になる構造に効果的に変わります。 無限のプレイを妨げる唯一の制限はセルごとの訪問制限です。これは構造的な制限ではなく、有界な繰り返し制約のように機能します。 

の制約`n`そして`m`まで`2 * 10^5`グリッドまたは状態グラフ上のシミュレーションを除外します。 各セルをノードとして扱い、ゲーム状態をシミュレートする単純なアプローチでは、到達可能な位置さえも多すぎて分岐要素が膨大になるため、爆発してしまいます。 

微妙なエッジ ケースは、ほとんどの場合、1000 アクセス ルールが最適なプレイを意味のある制限にしないことを理解することから生まれます。 不用意に解釈すると、サイクルをシミュレートしたり、訪問数を明示的に追跡しようとしたりする可能性がありますが、最適な戦略は、しきい値 1000 をすべて使い果たすかどうかに依存することはありません。 それは、対戦相手をグリッドの徐々に悪い領域に追い込むかどうかにかかっています。 

素朴な推論による小さな失敗例としては、1000 キャップのせいでゲームが「短い」と考えることが挙げられます。 実際には、2 細胞周期でさえ何度も繰り返すことができます。 

入力:```
2 1
3 2
2
```プロセスは次の間を行き来する可能性があります。`(1,1)`そして`(2,1)`何度も繰り返して終了を遅らせ、強制されたポジションが使用できなくなった場合にのみゲームが終了します。 限られた数の移動を想定するソリューションでは、この動作が見逃されます。 

## アプローチ

 ゲームを直接シミュレートしようとすると、各状態はペアになります`(r, c)`そして訪問回数。 プレイヤーは各状態から次のいずれかに移動できます。`n + m - 2`同じ行または列の他の状態、または終了します。 訪問の制約を無視しても、ゲーム ツリーは巨大です。 訪問制限により、状態の繰り返しの数は技術的に制限されますが、その制限は非常に大きいため、計算上意味がありません。 

本当の構造はゲームを再解釈することから生まれます。 すべての動きで行または列を自由に切り替えることができるため、ゲームはパスのジオメトリではなく、繰り返し使用しても「安全に」行および列のインデックスの選択を制御することが重要です。 

各行は固定されたものを提供すると考えることができます。`a[r]`、各列は固定値を提供します`b[c]`。 最終スコアは常に 1 つの行の値と 1 つの列の値の合計です。 移動ルールにより、訪問制約下でまだ利用可能である限り、プレイヤーはゲームを強制的にどの行または列に移動させるかを効果的に選択できます。 

これにより、問題はゲームオーバーの値に帰着します。プレイヤーは繰り返し行または列を選択し、対戦相手をより良いまたは悪い組み合わせに押し込もうとしますが、最終的には一方が有利な構成のための安全な繰り返しがなくなる「強制境界」で終了が発生します。 

重要な洞察は、最適な結果は合計の相対的な順序にのみ依存するということです。`a[i] + b[j]`。 グリッドを探索する代わりに、最適なプレイの下で最終的にどのセルが避けられなくなるかを推論します。 この構造は、最終位置が交互の強制訪問下で最も長​​く存続するセルに対応することを意味しており、これは行と列からのソートされた寄与によって定義されるボトルネックに相当します。 

解決策は最大しきい値を見つけることになります。`x`ゲームが合計を超えるすべてのセルを回避できるようにする`x`相手が早期に終了を強制できないほど十分な長さ。 これにより、当然のことながら、プレイヤーがルークを「許可された」セルのサブグラフ内に保持できるかどうかをモデル化する実現可能性チェックと組み合わせて、答えの二分探索が行われます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション | O(非常に大きな、指数関数的な状態) | O(nm) | 遅すぎる |
 | 最適 (二分探索 + 実現可能性推論) | O((n + m) log A) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 答えが次の形式の値であることを観察します。`a[i] + b[j]`, したがって、最終スコアを二分探索できます。 これは有効です。なぜなら、スコアが`x`最終的な強制結果として達成可能であるため、より大きなしきい値は独立して実現可能性をチェックできます。 
2. 候補値の場合`x`、各セルを分類します`(i, j)`もし「良い」として`a[i] + b[j] <= x`、そうでない場合は「悪い」。 ゲームは現在、強制的に悪い領域に足を踏み入れるか終了するまで、良いセル内に留まるものとして解釈されます。 
3. 移動を 2 部構成の到達可能性構造としてモデル化します。セルから、ルークはその行または列内の他のセルに移動できます。つまり、行内にあると、到達可能な良好なセル間で列を自由に切り替えることができ、またその逆も可能です。 これにより、どの行と列に少なくとも 1 つの正常なセルが含まれているかによって接続性が決まります。 
4. どの行と列がまだ「アクティブ」であるかを維持します。これは、以前の強制制約によって削除されていない正常なセルが少なくとも 1 つあることを意味します。 行または列で正常なセルがすべて失われると、終了を回避するために使用できなくなります。 
5. 実現可能性チェックは、枝刈りプロセスに要約されます。つまり、適切なセルが含まれなくなった行と列を繰り返し削除し、カウントを動的に更新します。 最後に、アクティブな行と列の両方でまだサポートされているセルが少なくとも 1 つ残っている場合、ゲームは強制的に超過することなく続行できます。`x`早すぎる。 
6. 最小限の二分探索`x`このプルーニング プロセスでは構成が不安定になります。 それ`x`が答えです。 

正確性は、行または列がしきい値未満の有効なセルを少なくとも 1 つ保持している限り、不変式に依存します。`x`、ルークはいつでも安全領域内に留まるように位置を変更することができ、すべてのサポートがなくなると強制終了されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(x, a, b):
    n, m = len(a), len(b)

    row = [0] * n
    col = [0] * m

    for i in range(n):
        for j in range(m):
            if a[i] + b[j] <= x:
                row[i] += 1
                col[j] += 1

    from collections import deque

    rq = deque(i for i in range(n) if row[i] == 0)
    cq = deque(j for j in range(m) if col[j] == 0)

    bad_row = [False] * n
    bad_col = [False] * m

    while rq or cq:
        while rq:
            i = rq.popleft()
            if bad_row[i]:
                continue
            bad_row[i] = True
        while cq:
            j = cq.popleft()
            if bad_col[j]:
                continue
            bad_col[j] = True

    for i in range(n):
        if bad_row[i]:
            continue
        for j in range(m):
            if not bad_col[j] and a[i] + b[j] <= x:
                return True
    return False

n, m = map(int, input().split())
a = list(map(int, input().split()))
b = list(map(int, input().split()))

lo = min(a) + min(b)
hi = max(a) + max(b)

ans = hi
while lo <= hi:
    mid = (lo + hi) // 2
    if can(mid, a, b):
        ans = mid
        hi = mid - 1
    else:
        lo = mid + 1

print(ans)
```この実装では、考えられる答えに対して二分探索を実行し、各中間点に対して実現可能性関数を呼び出します。 実現可能性チェックでは、しきい値以下に「有効な」セルがいくつ存在するかをカウントします。 有効なセルがゼロの行と列は非アクティブとしてマークされ、ルークがそれらを安全に操作できないという考えをシミュレートします。 最終スキャンでは、有効なセルがアクティブな行と列の構造によってサポートされているかどうかを確認します。 

微妙な点は、動きを明示的にシミュレートしていないことです。 代わりに、しきい値によって引き起こされる二部発生グラフの構造的生存可能性にゲームを還元します。`x`。

 ## 特殊なケース

 重要なエッジ ケースは、1 つの次元がサイズ 1 の場合です。グリッドは線に縮退しますが、訪問制限によって強制終了されるまで、ゲームは依然として繰り返しバウンスを許可します。 

例えば：```
2 1
3 2
2
```アルゴリズムは、これを 1 つの列のみが存在する 2 部構成として扱います。 単一セルがしきい値以下で有効かどうかに基づいて行がプルーニングされるため、実現可能性チェックは引き続き機能します。 正解はこうなります`min(a) + b[1]`、対戦相手は、より小さい行の値にゲームを強制的に解決させることができるためです。 

もう 1 つのエッジ ケースは、すべての合計が等しい場合です。`a[i] = A`そしてすべて`b[j] = B`。 すべてのセルは同一であるため、しきい値を超えると`A + B`自明に実現可能です。 二分探索はすぐに折りたたまれます。`A + B`すべての行と列が同時に有効なままであるため、プルーニングによって構造が削除されることはありません。
