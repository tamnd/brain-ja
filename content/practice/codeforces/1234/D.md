 ## 解決策
 ## 問題の理解

 2 種類の操作で小文字の文字列を維持しています。 1 回の操作で文字列内の 1 つの位置が変更され、その文字が変更されます。 もう 1 つの操作では、文字列のセグメントについて質問し、そのセグメント内に出現する異なる文字の数を数える必要があります。 

主な問題は、更新と範囲クエリの両方がインターリーブされることです。 すべてのクエリに対して回答を最初から再計算する静的なソリ​​ューションでは、最大 100,000 の長さの部分文字列を繰り返しスキャンすることになりますが、最大 100,000 のクエリがある場合、これでは遅すぎます。 

この制約は、最大 100,000 のサイズの構造体に対する合計入力サイズが 200,000 操作程度であることを意味します。 クエリごとに線形作業を実行するソリューションでは、最悪の場合でも文字検査が約 10¹⁰ に達しますが、これは 2 秒の制限では実行不可能です。 これにより、単純な部分文字列スキャンが即座に排除されます。 

2 番目の微妙な問題は、更新が将来のクエリに影響を与えることです。 クエリは、文字列の初期バージョンではなく、現在のバージョンに依存します。 どのアプローチでも、固定スナップショットから再計算するのではなく、動的な構造を維持する必要があります。 

微妙なエッジ ケースの 1 つは、同じ位置への繰り返しの更新によって発生します。 たとえば、単一のインデックスを繰り返し前後に変更してクエリを実行する場合、正しいソリューションは単調な動作を想定するのではなく、常に最新の文字を反映する必要があります。 

素朴なソリューションを壊すもう 1 つのケースは、更新後のクエリの重複です。 たとえば、以前にクエリした範囲内の文字を変更した場合、応答にはキャッシュされた結果ではなく、新しい文字列の状態が反映される必要があります。 

## アプローチ

 ブルート フォース ソリューションは、各クエリを個別に処理します。 範囲に関するタイプ 2 クエリの場合`[l, r]`、部分文字列をスキャンし、26 文字のうちどの文字が出現するかをマークします。 次に、何人が見られたかを数えます。 答えの定義は部分文字列に対して純粋にローカルであるため、これは正しいです。 

ただし、このアプローチではクエリごとに O(r - l + 1) のコストがかかります。 最悪の場合、1 つのクエリで 100,000 文字がスキャンされ、クエリが 100,000 個になると、総作業量は 2 次になります。 これはすぐに失敗します。 

重要な観察は、アルファベットのサイズが一定で小さいことです。 完全な部分文字列を追跡する代わりに、文字ごとに、それが出現する一連の位置を維持できます。 この場合、範囲クエリは次のようになります。この文字は間隔内に少なくとも 1 回出現しますか?

 動的更新を効率的にサポートするには、インデックスのメンバーシップをソートされた順序で維持し、高速な挿入、削除、および範囲カウントをサポートする構造が必要です。 フェンウィック ツリー (バイナリ インデックス付きツリー) は、文字ごとに 1 つずつ、26 個の個別の BIT を維持する場合に適切に機能します。 各ビットには、その文字が現在表示されている位置に 1 が格納され、それ以外の位置には 0 が格納されます。 

ポイントの更新により、その位置の古い文字が削除されます`pos`BIT から削除し、新しいビットを挿入します。 クエリは 26 ビットのそれぞれをチェックし、合計がゼロでないビットがいくつあるかを数えます。`[l, r]`。 

26 は定数であるため、各クエリは O(26 log n) となり、実質的には O(log n) になります。

 | 26ビット | クエリごとに O(26 log n) | O(26n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは 26 本のフェンウィック ツリーを維持しており、それぞれが 1 つのキャラクターを表しています。 また、現在の文字列も維持するので、各位置に現在どの文字が格納されているかが分かります。 

1. サイズ n の 26 個のフェンウィック ツリーを初期化し、初期文字列を使用して構築します。 ポジションごとに`i`に対応する BIT に 1 を加えます。`s[i]`。 これにより、各ツリーがそのキャラクターが現れる場所を確実に反映します。 
2. タイプ 1 クエリの場合`pos c`、まず前の文字を次の位置で見つけます。`pos`。 そのインデックスで 1 を減算することで、対応する BIT からそれを削除します。 次に、同じ位置に 1 を追加して、新しい文字を BIT に挿入します。 最後に、保存されている文字列を更新します。 
3. タイプ 2 クエリの場合`l r`、26 文字すべてを繰り返します。 各文字について、範囲内のビットの合計を計算します。`[l, r]`。 合計がゼロより大きい場合、その文字は部分文字列内に少なくとも 1 回出現するため、それをカウントします。 
4. タイプ 2 の各クエリの累積数を出力します。 

明らかではない部分は、ゼロより大きい合計が存在を正しく表す理由です。 各 BIT には、文字が出現する位置のインジケーター関数が正確に格納されるため、範囲内の合計は正確にそのセグメント内の出現数となります。 

### なぜ効果があるのか

 常に、文字列内の各位置は 26 ビット全体で 1 回だけ表されます。 更新では、新しい文字を挿入する前に古い文字を削除することで、この不変条件が保持されます。 したがって、各 BIT には常にその文字の正しいインジケーター配列が含まれています。 このインジケーター配列の範囲合計は存在チェックに直接対応し、すべての文字を合計すると、セグメント内の個別の文字の数が得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def main():
    s = list(input().strip())
    n = len(s)

    bits = [Fenwick(n) for _ in range(26)]

    for i, ch in enumerate(s, 1):
        bits[ord(ch) - 97].add(i, 1)

    q = int(input())
    out = []

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == '1':
            pos = int(tmp[1])
            c = tmp[2]
            old = s[pos - 1]
            if old != c:
                bits[ord(old) - 97].add(pos, -1)
                bits[ord(c) - 97].add(pos, 1)
                s[pos - 1] = c
        else:
            l, r = int(tmp[1]), int(tmp[2])
            ans = 0
            for i in range(26):
                if bits[i].range_sum(l, r) > 0:
                    ans += 1
            out.append(str(ans))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    main()
```このソリューションでは文字列を変更可能なリストに保持するため、配列レベルでの更新は O(1) になります。 各フェンウィック ツリーは、親のナビゲーションを簡素化するために 1 から始まるインデックスを使用します。 更新操作では、新しい文字を挿入する前に古い文字が慎重に削除されるため、二重カウントが防止されます。 

範囲クエリが依存するもの`range_sum(l, r)`プレフィックスの差を計算します。 26 文字にわたる最後のループは、アルファベットのサイズが固定されているため安全です。

 ## 特殊なケース

 密な更新のケースは、同じ位置が繰り返し変更される場合に発生します。 たとえば、次のように始めます。`"aaaaa"`、位置 3 を次のように更新します`'b'`、次に戻ります`'a'`、その後に`'c'`構造が古いカウントの蓄積を回避するかどうかをテストします。 Fenwick 更新ロジックは、新しい文字を挿入する前に前の文字を削除するため、各状態遷移では、正確に 1 つのツリー内のインデックスごとにクリーンな単一の存在が維持されます。 

クエリのような最小範囲クエリのケース`[1,1]`単一文字の部分文字列が正しくカウントされているかどうかをチェックします。 各 BIT は正確な位置を表すため、単一インデックスの範囲合計は 0 または 1 のいずれかになり、アルゴリズムはこれを 0 または 1 つの個別の文字に正しくマップします。 

複数の更新後の全範囲クエリにより、26 ツリーすべてにわたる集計の一貫性が確保されます。 各ツリーは独立しており、対称的に更新されるため、文字が二重にカウントされたり失われたりすることはありません。
