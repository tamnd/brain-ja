 ## 解決策
 ## 問題の理解

 私たちは、一度に表示できる会話の数に厳しい制限を設けて、「画面に表示された最新性」によって並べられた会話の動的なリストをシミュレートしています。 各受信メッセージは 1 つの友人 ID に関連付けられており、すべての ID は 1 つの会話に正確に対応します。 

メッセージが到着すると、その友人の会話がすでに画面に表示されているかどうかを確認します。 そうでない場合は、合計数を制限内に保つために、最も最近表示されていない会話を削除し、新しい会話を先頭に挿入する必要がある場合があります。 すでに表示されている場合は、表示される会話の順序もセットもまったく変更されません。 

最終的な状態は、すべてのメッセージを処理した後に表示される会話のリストを上から下の順に並べたものになります。 

この制約により、最大 200,000 のメッセージと最大 200,000 の画面サイズが許可されます。 これにより、配列をシフトしたり、メッセージごとに線形に検索したりするソリューションは即座に排除されます。 現在の画面リストをスキャンしてメンバーシップを確認し、Python リスト内で挿入と削除を実行する単純なシミュレーションでは、最悪の場合、時間制限をはるかに超える二次時間まで低下します。 

いくつかの特殊なケースについては、明示する価値があります。 

たとえば、すべてのメッセージが同じ友人から来た場合、`1 1 1 1`、最初の挿入後、画面は再び変更されません。 この場合、正しい解決策としては、再挿入または並べ替えを回避する必要があります。そうしないと、同じ ID が誤って繰り返しプッシュされてしまいます。 

すべてのメッセージが別の友人から来た場合、`k = 1`、最新の一意のメッセージのみが存続する必要があります。 入力用`1 2 3 4`と`k = 1`、答えは`[4]`。 適切に削除することを忘れたり、容量を厳密に強制しないために古いアイテムを保持したりするアプローチは失敗します。 

もう一つの微妙なケースは、次のような交互の繰り返しです。`1 2 1 2 1 2`と`k = 2`。 構造は振動しており、正確さは現在の画面状態のメンバーシップを一定時間内に正しく検出できるかどうかに依存します。 

## アプローチ

 直接シミュレーションでは、画面をリストとして維持し、ID がすでに存在するかどうかを確認するためにスキャンすることで各メッセージを処理します。 存在しない場合は、必要に応じて最後の要素を削除し、先頭に挿入します。 

このアプローチはルールを正確に反映しているので正しいですが、現在の画面サイズでは各ステップに直線的な時間がかかる可能性があります。 以上`n`メッセージでは、これは O(nk) になり、最悪の場合、k は O(n) となり、O(n²) になります。 n が 200,000 までの場合、これでは遅すぎます。 

重要な点は、高速化するには 2 つの操作が必要であるということです。メンバーシップ テスト (「この ID は現在表示されていますか?」) と、要素を頻繁に前に移動し、場合によっては最後の要素を削除する、最大 k 個の要素の順序付きリストを維持することです。 

これはまさに LRU キャッシュの構造です。 私たちは以下を維持します:

 - 二重リンクされた注文 (または Python`OrderedDict`) 最新 (前) から最も新しい (後) までの画面順序を表します。 
- O(1) メンバーシップ チェック用のハッシュ セットまたは辞書。 

新しいメッセージが到着したとき:

 - 存在する場合は何もしません。 
- 存在しない場合は先頭に挿入し、サイズが k を超える場合は最後の要素を削除します。 

これにより、選択されたデータ構造ではメンバーシップ チェックと並べ替えの両方が定数時間の操作となるため、すべての操作が償却 O(1) に減ります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nk) | O(k) | 遅すぎる |
 | 最適 (LRU スタイルの構造) | O(n) | O(k) | 承認済み |

 ## アルゴリズムのチュートリアル

 順序を維持し、メンバーシップの高速チェックを可能にする構造を使用して画面をシミュレートします。 Python では、`OrderedDict`は、一定時間での挿入、削除、並べ替えをサポートしているため、理想的です。 

1. 画面を表す空の順序構造を初期化します。 

この構造には、友人 ID が新しいものから最も新しいものへの順序で格納されます。 
2. 各受信メッセージ ID を順番に繰り返します。 

各ステップにより、表示されている会話の現在の状態が更新されます。 
3. 現在の ID が構造内にすでに存在するかどうかを確認します。 

存在する場合は、表示を繰り返しても順序が変わらないという問題があるため、何もしません。 
4. 存在しない場合は、構造体の先頭に挿入します。 

これは、会話が最近アクティブになったことを表します。 
5. 構造体のサイズが k を超える場合は、最も新しい要素を後ろから削除します。 

これにより、画面容量の制約が強制されます。 
6. すべてのメッセージを処理した後、構造を前から後ろの順に出力します。 

重要な部分は、並べ替えのステップです。 新しい ID が挿入されると、その ID は常に先頭に配置されます。これは、頻度や過去の平均ではなく、最新のメッセージが最新の順序を定義するためです。 

### なぜ効果があるのか

 この構造は、どの時点でも、現在のメッセージのプレフィックスを処理した後に画面に表示される一連の会話を正確に維持します。 順序の不変条件は、表示されているすべての会話の中で、最も最近挿入または更新された会話が常に先頭にあり、最も最近の会話が最後にあることです。 新しい未確認の ID だけが構造に影響を与え、繰り返される ID は何もしないため、既存の要素間の相対的な順序は、新しい要素が先頭に追加されたときにのみ変更され、最新の順序の正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import OrderedDict

def solve():
    n, k = map(int, input().split())
    arr = list(map(int, input().split()))

    screen = OrderedDict()

    for x in arr:
        if x in screen:
            continue
        screen[x] = None
        screen.move_to_end(x, last=False)

        if len(screen) > k:
            screen.popitem(last=True)

    res = list(screen.keys())
    print(len(res))
    print(*res)

if __name__ == "__main__":
    solve()
```実装の中核となるのは、`OrderedDict`。 メンバーシップの確認、注文、効率的な更新を同時に処理します。 の`move_to_end(x, last=False)`call は確実に先頭に挿入します。これは、新しい会話が常に最新のものになる必要があるため必要です。 

立ち退きのステップ`popitem(last=True)`容量を超えると、最も古い会話が削除されます。 

よくある間違いは、要素がすでに存在する場合でも、要素を先頭に挿入することです。 これにより、最新の順序が誤って変更されてしまいますが、問題は、メッセージが繰り返されても画面の状態がまったく変更されないことを明確に示しています。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各メッセージは最大 1 回の辞書検索、1 回の挿入、場合によっては 1 回の削除をトリガーし、すべて O(1) が償却されます。 
| スペース | O(k) | この構造体には、常に最大 k 個のアクティブな会話が保存されます。 

この制約により、最大 200,000 の操作が許可されるため、一定時間の更新を伴う線形時間ソリューションは、時間とメモリの制限内に快適に収まります。 

## テストケース```python
import sys, io
from collections import OrderedDict

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import OrderedDict

    n, k = map(int, input().split())
    arr = list(map(int, input().split()))

    screen = OrderedDict()

    for x in arr:
        if x in screen:
            continue
        screen[x] = None
        screen.move_to_end(x, last=False)
        if len(screen) > k:
            screen.popitem(last=True)

    res = list(screen.keys())
    return str(len(res)) + "\n" + " ".join(map(str, res))

# provided sample
assert run("7 2\n1 2 3 2 1 3 2\n") == "2\n2 1"

# all same values
assert run("5 3\n7 7 7 7 7\n") == "1\n7"

# k = 1
assert run("4 1\n1 2 3 4\n") == "1\n4"

# k equals n
assert run("3 3\n1 2 3\n") == "3\n3 2 1"

# alternating pattern
assert run("6 2\n1 2 1 2 1 2\n") == "2\n1 2"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | すべて同じ値 | 1 要素 | 繰り返されるメッセージは並べ替えられません。 
| k = 1 | 最後の要素 | 厳格な立ち退き動作 |
 | k = n | 完全に逆の順序 | 全容量保持 |
 | 交互パターン | 安定した 2 ステート LRU | メンバーシップと注文の正確性 |

 ## 特殊なケース

 すべてのメッセージが同一である入力の場合、次のようになります。`5 3 / 7 7 7 7 7`、最初の挿入により作成される`[7]`、ID がすでに存在しているため、後続のメッセージはすべて無視されます。 この構造はサイズ 1 を超えて大きくなることはなく、メッセージが繰り返されても再挿入や不要な削除が発生しないことが確認されています。 

のために`k = 1`、 のような`4 1 / 1 2 3 4`、新しい未確認の ID はそれぞれ、以前の ID に置き換わります。 処理後は、最後のメッセージのみが残ります。 このアルゴリズムは、新しい挿入が発生するたびに常に最後の要素をポップすることでこれを強制します。 

次のような交互入力の場合`1 2 1 2 1 2`と`k = 2`、最初の 2 つの固有の挿入の後、画面が安定します。 後続の繰り返しは順序を妨げません。これは、メンバーシップ チェックが、すでに表示されている会話の構造更新を正しく防止していることを示しています。
