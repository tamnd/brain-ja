 ## 解決策
 ## 問題の理解

 この問題は、隠されたバイナリ文字列を発見することに関するものです。 私たちはその長さだけを教えられます。 利用可能な唯一の情報はクエリから得られます。私たちは別のバイナリ文字列を提出し、審査員は私たちが提出した文字列がサブシーケンスとして隠し文字列内に現れるかどうかを教えてくれます。 

課題は、非表示文字列の長さが最大 ​​1000 であるのに対し、各クエリはその長さの約半分に制限されることです。 既知のプレフィックス全体について尋ねる直接再構成方法では、最終的に長すぎるクエリが生成されます。 ソリューションでは、クエリの長​​さ制限をガイドとして使用する必要があります。 

クエリが最大 1024 個あるため、`n`が最大 1000 である場合、文字ごとにおよそ 1 つのクエリを使用するアプローチが許容されます。 ただし、可能なバイナリ文字列の数は指数関数的に増加するため、可能な文字列の二次探索を必要とする解決策は不可能です。 

難しいケースは、値が大きいことが原因ではなく、再構築の方向によって引き起こされます。 たとえば、非表示の文字列が次の場合:```
1
```唯一の有効な答えは次のとおりです。```
1
```常に最初にゼロをテストし、それを盲目的に追加できると想定したソリューションは失敗します。 

小規模な分割ケースの場合:```
n = 4
hidden = 0110
```現在の答えと新しい文字がサブシーケンスであるかどうかを尋ねて、左から 4 文字すべてを再構築しようとすると、3 文字が見つかった後、クエリの長​​さは 4 になり、許可されているクエリの長​​さの 3 より大きくなります。 大きな文字列ごとに同じ問題が発生します。 正しいアプローチでは、すべてのクエリが制限内に収まるように両端から再構築する必要があります。 

## アプローチ

 当然の強引なアイデアは、左から右に答えを構築することです。 プレフィックスがすでにわかっていると仮定します`p`。 かどうか尋ねることができます`p + "0"`はサブシーケンスです。 そうでない場合、次の文字は次の文字でなければなりません。`1`。 これが機能するのは、実際の文字列のすべてのプレフィックス自体が非表示の文字列の部分列であるためです。 

問題はクエリのサイズです。 文字列の約半分が検出された後、次のクエリには既知のプレフィックスともう 1 文字が含まれ、許容される長さを超えます。 のために`n = 1000`、完全な左から右への再構成には 1000 に近い長さのクエリが必要ですが、制限はわずか 501 です。 

重要な観察は、制限が長さのちょうど半分であるということです。 前半を左から、後半を右から再構成できます。 右から再構築する場合、クエリの最後に既知のサフィックスを保持し、候補文字を先頭に追加します。 クエリの長​​さが文字列の半分に 1 を加えた値を超えることはありません。 

2 つの部分を合わせてすべてのポジションをカバーし、クエリの数は最大で`n`、制限内に簡単に収まります。

 | ブルートフォース | 指数 | O(n) | 遅すぎる |
 | 左から右への再構築 | O(n) 個のクエリが無効なクエリ サイズ | O(n) | 許可されません |
 | 両面再構成 | O(n) クエリ | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. しましょう`half = n // 2`。 最初のものを再構築する`half`文字は左から右へ。 すでに見つかったプレフィックスを維持します。 プレフィックスの後に続くかどうかを尋ねます`0`はサブシーケンスです。 答えが「はい」の場合、次の文字は`0`; それ以外の場合はそうする必要があります`1`。 

このフェーズで最も長いクエリには長さがあります`half`, したがって、クエリ制限が尊重されます。 

1. 残りの文字を右から左に再構築します。 すでに見つかったサフィックスを維持します。 どうか尋ねてください`0`現在のサフィックスが後に続くのがサブシーケンスです。 そうであれば、新しいキャラクターは`0`; それ以外の場合はそうです`1`。 

新しい文字を追加する前のサフィックスの長さは、次の値を超えることはありません。`n - half - 1`したがって、クエリの長​​さは最大でも`half + 1`。 

1. 再構築されたサフィックスを反転し、前半の後に配置します。 2 つの部分を合わせて元の文字列を形成します。 

なぜ効果があるのか:

 最初のフェーズにおける不変条件は、保存されたプレフィックスが、非表示文字列の対応するプレフィックスと正確に一致することです。 どちらかを追加すると`0`または`1`隠し文字列の候補プレフィックスを作成し、正しいものだけがサブシーケンスとして残ります。 

第 2 フェーズでは、同じアイデアを逆の方向から使用します。 非表示文字列の正しいサフィックスは、その前に次の実際の文字が配置されたときにサブシーケンスのままになります。 テスト`0 + suffix`次の文字が 0 か 1 かを区別します。 すべての位置は 2 つの再構築された部分のうちの 1 つに正確に属するため、最終的な文字列は正しいものになります。 

## Python ソリューション```python
import sys

input = sys.stdin.readline

def ask(s):
    print("? " + s, flush=True)
    return int(input())

n = int(input())

half = n // 2

left = ""
for _ in range(half):
    if ask(left + "0"):
        left += "0"
    else:
        left += "1"

right = ""
for _ in range(n - half):
    if ask("0" + right):
        right = "0" + right
    else:
        right = "1" + right

print("! " + left + right, flush=True)
```機能`ask`インタラクティブなコミュニケーションを扱います。 インタラクティブなジャッジはプログラムの出力を待ってから応答するため、すべてのクエリは即座にフラッシュされます。 

最初のループは左側の部分を構築します。 あらゆる時点で、現在のプレフィックスが正しいことがすでにわかっているため、次のゼロをチェックするだけで十分です。 非表示文字列のその位置にはちょうど 1 文字があるため、逆のケースは 1 である必要があります。 

2 番目のループでは同じロジックが使用されますが、答えは逆方向に拡大されます。 課題`right = "0" + right`文字を右から左に追加するときにサフィックスを正しい順序に保ちます。 

分割点を超える整数計算は必要ないため、オーバーフローの心配はありません。 重要な境界はクエリの長​​さであり、両方のループは最大クエリ サイズが`floor(n/2)+1`。

 ## 特殊なケース

 1文字の文字列の場合`1`、最初のフェーズには再構築するキャラクターがありません。`n // 2`はゼロです。 接尾語フェーズでは、次のことを尋ねます。`0`可能です。 答えは偽なので、アルゴリズムは`1`サフィックスに を追加すると、正しい文字列が返されます。 

次のような偶数長の文字列の場合`0110`、分割により同じサイズの 2 つの部分が作成されます。 左フェーズはハンドルのみ`01`、および適切な位相ハンドル`10`。 どちらの側でも、この長さの許容制限である 3 文字を超えるクエリは必要ありません。 

次のような奇数長の文字列の場合`10101`、左側の部分の長さは 2、右側の部分は長さ 3 です。 各文字を追加する前に保存されているサフィックスが十分に短く、先頭に 1 文字を追加することでクエリが制限内に収まるため、適切な再構築は引き続き機能します。 最後の連結では元の順序が維持されます。
