 ## 解決策
 ## 問題の理解

 この問題は、一列に配置された一連のプレイヤーを記述しており、各プレイヤーは自分のデッキを表す文字列を所有しています。 これらのデッキは分離されていません。各プレイヤーの有効な「ハンド」は、そのプレイヤーに関連付けられた整数で示されるように、左側の固定数のプレイヤーのデッキで自分のデッキを拡張することによって形成されます。 言い換えれば、プレーヤー i は自分の文字列だけでなく、i で終わる前の文字列の連結されたウィンドウも気にします。 

この構造に加えて、それぞれ文字列とスコアで構成されるいくつかのパターンが与えられます。 パターンがプレイヤーの有効なハンド内の部分文字列として現れ、その出現がそのプレイヤー自身の元のデッキ境界内で終了するたびに、そのプレイヤーは対応するスコアを獲得します。 タスクは、すべてのプレーヤーについて、有効な領域に一致するすべてのパターンから取得できる最高のスコアを計算することです。 

この難しさは、プレイヤーの伸ばした手が重なっていることと、多くの部分文字列の出現を効率的に検出する必要があることに起因します。 直接読み取ると、複数のクエリを含む大規模な連結構造での文字列マッチングが示唆されます。テキスト長とパターン長の両方が 10^5 のオーダーで大きくなる可能性があります。 これにより、プレーヤーごとのパターンごとの単純な部分文字列検索が即座に除外されます。これは、最悪の場合 O(N * M * L) のように動作し、標準の Codeforce 制限の下では失敗します。 

この構造には重要な制約も隠されています。すべての入力文字列の合計の長さは制限されているため、各文字を一定の回数だけ処理するソリューションは実行可能ですが、部分文字列を繰り返しスキャンしたり、プレーヤーごとに一致を再計算したりするものは実行できません。 

パターンが重なり合い、複数のパターンが同じ終了位置で一致する場合、微妙なエッジ ケースが発生します。 たとえば、テキストに「aaaaa」が含まれており、パターンが「a」、「aa」、「aaa」である場合、一致が位置ごとにグループ化されていない限り、単純なパターンごとのスキャンでは二重にカウントされたり、正しいベストスコアの集計が失敗したりする可能性があります。 

もう 1 つの特殊なケースは、境界の調整から発生します。 パターンがちょうどプレイヤーが伸ばした手と次のプレイヤーの山札との境界で終わると仮定します。 そのパターンが貢献するかどうかは、そのパターンの終わりが現在のプレイヤーの元のデッキ内にあるかどうかに厳密に依存します。 エンドポイントの位置を検証せずに、拡張ウィンドウ内での発生のみをチェックする不注意な実装では、プレイヤー間でスコアが誤って割り当てられてしまいます。 

## アプローチ

 ブルートフォース手法では、各パターンを個別に処理し、すべてのプレーヤーの有効な文字列内のすべての可能な終了位置をスキャンします。 具体的には、各プレイヤーの完全な拡張文字列を構築し、パターンごとに、ナイーブ マッチングや KMP などの部分文字列検索を実行します。 テキストの合計長が N 程度、パターンの合計長が M 程度であると仮定すると、最悪の解釈ではプレイヤーあたりおよそ O(N * M) となり、最適化されたマッチングでも依然として O(N * パターンの数) となり、N と M が両方とも 10^5 までの場合、これは大きすぎます。 

この非効率性は、すべてのパターンが同じ基礎となるアルファベットを共有し、常に同じグローバル テキスト構造をスキャンしているにもかかわらず、すべてのパターンおよびすべての位置に対してパターン マッチングを繰り返し再開することから生じます。 

重要な観察点は、これは独立した部分文字列問題の集合ではなく、共有テキストに対する単一のマルチパターン マッチング問題であるということです。 各パターンを個別に検索する代わりに、すべてのプレイヤーのデッキの連結表現をスキャンしながら、すべてのパターンを同時に処理するオートマトンを構築できます。 これはまさに Aho-Corasick オートマトンが役立つ設定です。これにより、すべてのパターン遷移が 1 つの構造に圧縮され、テキスト全体にわたって線形時間ですべてのパターンの一致を検出できるようになります。

すべての出現が判明したら、連結された文字列内の位置追跡を使用して、各出現をプレーヤーにマッピングできます。 残りの困難は、一致が正しいプレイヤーの元のセグメント内で終了した場合にのみ寄与するという条件を強制することです。 これは、各プレーヤーのセグメント境界を事前計算し、各試合の終了インデックスがその区間内にあるかどうかを確認することによって処理されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (パターン検索ごと) | O(N・M) | O(N) | 遅すぎる |
 | 連結テキスト上の Aho-Corasick | O(N + パターンの合計長 + 一致) | O(N + 合計パターン) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべてのプレーヤーのデッキ文字列を 1 つのグローバル文字列に連結し、ポジションごとにどのプレーヤーに属するかを保存します。 これにより、セグメント化された構造が、サイド マッピングを備えた単一の線形テキストに変換されます。 
2. 各プレーヤーについて、連結された文字列内の元のデッキに対応するインデックスの間隔を計算します。 この間隔は、試合が正しいプレイヤーで終了したかどうかを確認するために必要です。 
3. すべてのパターン文字列から Aho-Corasick オートマトンを構築します。 各終端状態にはそのパターンに関連付けられたスコアが保存されるため、同じノードで終わる複数のパターンを自然に処理できます。 
4. トランジションとフォールバック リンクに従って、連結されたテキストをオートマトンで 1 文字ずつたどります。 状態に出力パターンがある場合は常に、現在の位置で終わる一致を記録します。 
5. 位置 i で終わる検出されたすべての一致について、その長さを決定し、したがってその開始点を決定します。 どのプレイヤーが終了位置 i を所有しているかを確認し、i がそのプレイヤーの元のデッキ間隔内にあることを確認します。 
6. 試合がそのプレーヤーにとって有効な場合、パターンの値を使用してプレーヤーのスコアを更新します。通常は、複数の試合の解釈に応じて最大値または合計を取ることによって行われます。 
7. テキスト全体を処理した後、各プレーヤーの計算されたスコアを出力します。 

### なぜ効果があるのか

 オートマトンは、連結されたテキストのすべての部分文字列がトライ構造内の遷移パスとして 1 回だけアクセスされることを保証します。 サフィックス リンクは部分一致を伝播するため、有効なパターンの出現がスキップされることはありません。 ポジションから選手へのマッピングでは、テキストが互いに素なセグメントに分割されるため、すべての一致はエンドポイントに基づいて 1 人の候補選手にのみ帰属されます。 エンドポイントがプレーヤーの元の間隔内にある一致のみを受け入れるため、部分文字列の境界を再計算する必要なく、問題の制限が適用されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

class AhoCorasick:
    def __init__(self):
        self.next = [{}]
        self.link = [-1]
        self.out = [[]]

    def add(self, s, value):
        v = 0
        for c in s:
            if c not in self.next[v]:
                self.next[v][c] = len(self.next)
                self.next.append({})
                self.link.append(-1)
                self.out.append([])
            v = self.next[v][c]
        self.out[v].append(value)

    def build(self):
        q = deque()
        self.link[0] = 0
        for c, v in self.next[0].items():
            self.link[v] = 0
            q.append(v)

        while q:
            v = q.popleft()
            for c, u in self.next[v].items():
                q.append(u)
                j = self.link[v]
                while j and c not in self.next[j]:
                    j = self.link[j]
                self.link[u] = self.next[j].get(c, 0)

                self.out[u].extend(self.out[self.link[u]])

    def run(self, text, belong, lbound, rbound):
        res = [0] * len(lbound)
        v = 0

        for i, c in enumerate(text):
            while v and c not in self.next[v]:
                v = self.link[v]
            v = self.next[v].get(c, 0)

            for val in self.out[v]:
                p = belong[i]
                if lbound[p] <= i <= rbound[p]:
                    res[p] = max(res[p], val)

        return res

def solve():
    n = int(input())
    s = []
    lbound = []
    rbound = []
    belong = []
    idx = 0

    for i in range(n):
        a = input().strip()
        s.append(a)
        lbound.append(idx)
        for _ in a:
            belong.append(i)
        idx += len(a)
        rbound.append(idx - 1)

    text = "".join(s)

    m = int(input())
    ac = AhoCorasick()

    for _ in range(m):
        t, x = input().split()
        x = int(x)
        ac.add(t, x)

    ac.build()
    ans = ac.run(text, belong, lbound, rbound)

    print(*ans)

if __name__ == "__main__":
    solve()
```この実装では、すべてのパターンに基づいてオートマトンを構築し、連結されたテキストを 1 回処理します。 の`belong`配列は、すべてのデッキを結合した後も各キャラクターの所有権を保持するため、重要です。 間隔配列`lbound`そして`rbound`パターンエンドポイントの有効性を定義し、プレイヤー自身のデッキ内で終了する一致のみが寄与するようにします。 

よくある間違いは、サフィックス リンクの伝播によって複数のパターンが同じ状態でトリガーされる可能性があることを忘れることです。`out[v]`到達可能なすべての終了状態からの値を集約する必要があります。 もう 1 つの微妙な点は、開始インデックスではなく終了ポイント インデックスを使用して有効性をチェックすることです。これは、この問題では一致が終了する場所に基づいて寄与度が定義されるためです。

 ## 特殊なケース

 エッジ ケースの 1 つは、複数のパターンが同じ位置で終了するが、異なるサフィックスリンク チェーンに属している場合です。 のようなテキストで`"aaaa"`、位置 3、パターン`"a"`、`"aa"`、 そして`"aaa"`すべて終了します。 オートマトンは、3 つすべてが存在することを確認します。`out[v]`サフィックス リンクの伝播を通じて、最大集約によって正しい最適値が選択されます。 

もう 1 つのエッジ ケースは、パターンがプレーヤーの境界を越える場合です。 たとえば、プレイヤーAが持っている場合、`"ab"`そしてプレイヤーBは`"cd"`、連結は`"abcd"`。 パターン`"bc"`位置 2 の境界を越えて一致します。グローバル テキスト内に存在しますが、エンドポイントはプレーヤー B のインターバル内にあるため、B のみに帰属します。インターバル チェックはこれを正確に適用します。 

最後の微妙なケースは、パターンがプレイヤーのデッキの最後の文字でちょうど終了する場合です。 境界は右側に含まれるため、チェック`lbound[p] <= i <= rbound[p]`にはこの一致が正しく含まれており、エッジが揃った出現箇所が失われないことが保証されます。
