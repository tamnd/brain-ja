 ## 解決策
 ## 問題の理解

 私たちは正の整数の動的なコレクションを維持しています。各整数はカフェに新しく到着する食材の量を表します。 コレクションは時間の経過とともに変化します。新しい値が追加され、場合によっては最新の値のブロックが削除されます。 これらの更新の間に、現在利用可能なすべての材料から一定数の同一のドリンクを同時に製造できるかどうかを確認するクエリが尋ねられます。 

この声明の重要な所見は、すべての飲み物にはすべての材料が使用されなければならず、各材料はすべての飲み物に均等に分割されなければならないということです。 現在材料の数量がある場合$a_1, a_2, \dots, a_k$、その後、生産します$x$飲み物は次の場合にのみ可能です$a_i$で割り切れます$x$。 これにより、実現可能性チェック全体が、すべてのアクティブな数値にわたる割り切れる条件に縮小されます。 

制約は以下を意味します$10^5$までの値の演算$10^9$。 Any solution that recomputes a property from scratch per query leads to$O(nq)$が遅すぎます。 各操作を償却して処理するアプローチが必要です。$O(1)$または$O(\log n)$つまり、現在のマルチセットのコンパクトな概要を維持する必要があります。 

削除によって最新の要素が削除される場合、微妙なエッジ ケースが発生します。 たとえば、材料から始めることを検討してください。$[6, 10, 15]$、次に追加します$4$, then removing the last two elements. 履歴を正しく維持しない単純な実装では、古い要素が誤って削除されたり、正しい状態の復元に失敗したりする可能性があります。 Another issue is repeated queries: a solution that recomputes divisibility by scanning all elements per query would pass small cases but fail under maximum constraints due to time limits.

 ## アプローチ

 強引なアイデアは単純明快です。有効成分の完全なリストを維持することです。 タイプ 3 の各クエリについて、すべての現在の値を反復処理し、各値が次の値で割り切れるかどうかを確認します。$x$。 これは問題の状態を直接エンコードしているため、これは正しいです。 ただし、各クエリでは最大でスキャンが必要になる場合があります。$10^5$要素と$10^5$クエリ、これは次のことにつながります$10^{10}$実行可能な限界をはるかに超えた最悪の場合の操作。 

重要な洞察は、私たちは実際には個々の値を気にするのではなく、それらの共通の可分性構造だけを気にするということです。 数字$x$最大公約数を分割する場合に限り、マルチセット内のすべての要素を分割します。 これにより、問題は一連の数値を維持することから、単一の集計値、つまりすべてのアクティブな要素の gcd を維持することに変わります。 

この減少が見られると、構造はスタックの問題になります。 要素はバッチで最後に追加され、最後から削除されるだけなので、各エントリがその位置までのすべての要素の gcd を格納するスタックを維持できます。 これにより、更新とロールバックの両方を効率的に処理できるようになります。

 ## アルゴリズムのチュートリアル

 現在のアクティブなシーケンス内のその時点までのすべての値の gcd を各位置に格納するスタックを維持します。 

1. 初期成分の接頭辞 gcd を含む初期スタックから開始します。 新しい値ごとに、その前のすべての gcd が更新されるため、スタックのトップは常に、これまでのすべての有効成分の gcd を表します。 
2. タイプ 1 クエリの場合、新しい成分が追加されます。 現在のスタックトップを使用してこの値の gcd を計算し、プッシュします。 これが機能するのは、gcd が結合型であるため、拡張後もプレフィックス構造が有効なままであるためです。 
3. タイプ 2 クエリの場合、最後のクエリを削除します。$K$スタックからポップして材料を取得する$K$回。 各ポップは、以前のプレフィックス gcd 値の正確さを維持しながら、最新の成分の寄与を削除します。 
4. タイプ 3 のクエリの場合、要求された番号が$X$スタックの先頭に格納されている現在の gcd を分割します。 そうであれば、すべての要素は次のように割り切れます。$X$そうでない場合、少なくとも 1 つの要素に互換性がなく、注文を満たすことができません。 

### なぜ効果があるのか

 いつでもスタックの最上位は$\gcd(a_1, a_2, \dots, a_k)$すべての有効成分に渡って。 数値は、gcd を除算する場合に限り、セット内のすべての要素を除算するため、この 1 つの値に対して割り算をチェックすることは、すべての要素を個別にチェックすることと同じです。 gcd 更新は結合的であり、削除すると以前のプレフィックス状態が正確に復元されるため、スタック不変条件は保持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from math import gcd

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    # stack stores prefix gcds
    st = [0]
    for x in a:
        st.append(gcd(st[-1], x))

    for _ in range(q):
        tmp = input().split()
        t = int(tmp[0])

        if t == 1:
            g = int(tmp[1])
            st.append(gcd(st[-1], g))

        elif t == 2:
            k = int(tmp[1])
            # pop k elements
            for _ in range(k):
                st.pop()

        else:
            x = int(tmp[1])
            if st[-1] % x == 0:
                print("SIM")
            else:
                print("NAO")

if __name__ == "__main__":
    solve()
```この実装は、生の値ではなくプレフィックス gcd を保存するスタックに依存します。 これにより、クエリ中に配列全体に対して gcd を再計算することが回避されます。 唯一の微妙な部分は、削除によって最新のプレフィックス状態が正しく削除されるかどうかを確認することです。 各スタック エントリは前のスタック エントリにのみ依存するため、ポップすると以前の有効な gcd が自動的に復元されます。 

注目に値する詳細の 1 つは、初期スタックが 0 から始まり、これが gcd の中立要素として機能することです。 これにより、最初の実際の成分が構造を正しく初期化することが保証されます。

 ## 特殊なケース

 単一の成分の入力は、gcd の初期化が 1 つの意味のある要素を含むスタックを正しく処理するかどうかをテストします。 単一の数値の gcd がそれ自体であり、割り算チェックが正しく行われるため、アルゴリズムは引き続き機能します。 

以前の状態を復元する大規模な削除では、スタックが以前のプレフィックス gcd 値に正しく戻るかどうかをテストします。 各スタック エントリは完全なプレフィックスをエンコードするため、複数回ポップすると、再計算せずに常に有効な履歴 gcd が復元されます。 

すべて等しい数値などの均一な配列により、更新後も gcd が安定した状態に保たれ、gcd 計算の繰り返しで意図しない副作用が発生しないことが確認されます。 

スタックを初期状態のままにする境界の削除により、センチネルのゼロ値が正しく動作し、可分性チェックに干渉しないことが確認されます。
