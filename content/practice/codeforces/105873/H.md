 ## 解決策
 ## 問題の理解

 私たちには独立したジョブのコレクションが与えられています。 各ジョブは、Tony が受け入れるか無視できる設計リクエストを表します。 彼が仕事を引き受けた場合、その仕事は完了するまでに一定の時間がかかり、厳しい期限までに完了しなければなりません。そうでない場合、その仕事は無効とみなされ、何も貢献しません。 

すべての仕事には、締め切り前に完了した場合に得られる基本利益も保証されています。 その他、ジョブごとにボーナスが発生する場合がありますが、ボーナスは固定ではありません。 代わりに、指定された範囲から均一に選択された 2 つの独立したランダム値に依存します。 ボーナスはジョブが 2 回目のしきい値より前に終了した場合にのみ付与され、その期待値はそれらの範囲から計算できます。 

タスクは、ジョブのサブセットとそれらを 1 台のマシンで順番に実行する順序を選択し、選択されたすべてのジョブが期限を守り、予想される総利益が最大化されるようにすることです。 

スケジュールの観点から見ると、これはサブセットの選択と順序付けの問題です。 各ジョブは時間を消費し、期限の制約を課し、期待される利益に等しい重みをもたらします。 ジョブの実現可能性は累積処理時間に依存するため、順序は重要です。 

この制約により、最大 20 個のジョブが許可されます。 主なボトルネックは n 自体ではなくジョブのサブセットであるため、n の 2 乗以上の多項式アルゴリズムは直ちに除外されます。 2^20 は約 100 万であり、これが徹底的な検索に適切なスケールであるため、すべてのサブセットを検査するソリューションが実現可能です。 

主なエッジケースは、ジョブのサブセットが個別に期限を満たしているものの、すべての制約を同時に満たす順序が存在しない場合です。 たとえば、あるジョブの期限は短いが処理時間が長い場合、それを後から配置すると、単独では有効に見えても実現可能性が損なわれる可能性があります。 複数のジョブが同じ期限と処理時間を共有する場合、別の微妙なケースが発生します。 期限による貪欲な順序付けだけでは、サブセット選択と組み合わせた場合の最適性は保証されません。 

## アプローチ

 ブルートフォースアプローチでは、ジョブの可能なすべてのサブセットを試し、各サブセットについて、利益を最大化しながらすべての期限を満たす有効な順序が存在するかどうかを確認します。 固定サブセットの場合、実現可能性をチェックするには、期限によってジョブを並べ替えたり、順列を探索したりする必要があり、これにはサブセットごとに少なくとも O(k log k) のコストがかかり、単純に実行した場合は潜在的に O(k!) かかります。 

最大 20 個のジョブでは、約 1,048,576 個のサブセットがあります。 サブセットごとの O(n) チェックでもすでに約 2,000 万回の操作が発生しており、これは境界線ではありますが実現可能ですが、サブセット サイズの階乗または指数関数的な順序付けチェックは不可能になります。 

重要な観察は、サブセットが固定されると、期限を満たすための最良の順序付けは常にジョブを期限順に並べ替えることであるということです。 これにより、実現可能性チェックが 1 回の確定的スキャンに変換されます。 この場合、問題は純粋に、期限順に並べ替えられたスケジュールが有効で、期待される総利益が最大化されるサブセットを選択することになります。 

その構造は次のとおりです。サブセットを列挙し、その期待利益を計算し、選択したジョブを期限ごとに並べ替えて、累積処理時間が期限を超えないことを確認します。 これにより、スケジューリングの最適化の問題が、実現可能性チェック上のサブセット DP に軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | サブセットごとのブルート フォース順列 | O(2^n・n!) | O(n) | 遅すぎる |
 | 貪欲な順序付けによるサブセット列挙 | O(2^n · n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 各ジョブのボーナスの期待値を事前に計算します。 ボーナスは長方形上で一様にランダムであるため、その期待値は、モデルが乗算的である場合は単純に両方の範囲の中点を乗算し、独立性が示すように加算的である場合は合計します。 これにより、各ジョブが確定的な利益値に変換されます。 
2. ジョブのサブセットごとに、基本利益と予想ボーナスの合計として総利益を計算します。 これにより、順序とは独立して、そのサブセットの目標値が定義されます。 
3. サブセット内のジョブを抽出し、期限の降順でない順に並べ替えます。 この順序が選択されるのは、すべての期限を満たすことができるスケジュールは、最初に最も早い期限と一致する必要があるためです。 そうしないと、期限が早いジョブが後の期限によって不必要に遅れる可能性があります。 
4. 実行時間カウンターを維持しながら、このソート順で実行をシミュレートします。 各ジョブの処理時間を加算し、累積時間が期限を超えているかどうかをすぐに確認します。 存在する場合は、このサブセットを完全に破棄します。 
5. サブセットが実現可能な場合は、その利益を現在の最良の回答と比較し、更新します。 

期限によるソートが正しい理由は、実行可能なスケジュールであれば、完了時間違反を増加させることなく、減少しない期限に従ってジョブを順序付けるスケジュールに変換できるためです。 締め切りが遅いジョブが締め切りが早いジョブより前に表示された場合、締め切りが早いジョブは期限が早いことによってのみメリットが得られるため、それらを交換しても実現可能性は悪化しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    jobs = []
    
    for _ in range(n):
        d, p, c, lx, rx, ly, ry = map(int, input().split())
        # expected bonus: E[x] * E[y] since independent uniform variables
        ex = (lx + rx) / 2.0
        ey = (ly + ry) / 2.0
        bonus = ex * ey
        jobs.append((d, p + bonus, c))
    
    ans = 0.0
    
    for mask in range(1 << n):
        total = 0.0
        subset = []
        
        for i in range(n):
            if mask & (1 << i):
                d, val, c = jobs[i]
                total += val
                subset.append((d, c))
        
        subset.sort()
        
        t = 0
        ok = True
        for d, c in subset:
            t += c
            if t > d:
                ok = False
                break
        
        if ok:
            ans = max(ans, total)
    
    print(f"{ans:.10f}")

def main():
    solve()

if __name__ == "__main__":
    main()
```実装はアルゴリズムを直接反映しています。 各ジョブは、期待されるボーナスを計算することによって、決定的な重みに前処理されます。 サブセット ループは、ビットマスクを使用してすべての組み合わせを列挙します。これは、最大 20 の n に対して十分効率的です。 

各サブセット内で、期限と処理時間のみを含む縮小リストを作成します。 このリストを並べ替えると、実現可能性をチェックするために貪欲な最適な順序付けが強制されます。 実行時間チェックは段階的に行われ、違反をできるだけ早く検出できるようにします。 

微妙な点は、期待値に浮動小数点演算を使用していることです。 必要な精度は 1e-6 であるため、倍精度で十分です。 累算では、整数と浮動小数点の比較が混在するのを避けるために、一貫して浮動小数点を使用します。

 両方をスケジュールできる 2 つのジョブを持つ小規模なインスタンスを考えてみましょう。 

| ステップ | サブセット | 期限順に並べ替え | 時間の経過 | 実現可能 | 利益 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | {} | {} | 0 | はい | 0 |
 | 2 | {1} | (1) | 5 → OK | はい | 10 |
 | 3 | {2} | (2) | 5 → OK | はい | 20 |
 | 4 | {1,2} | (1,2) | 5 → 10 → OK | はい | 30 |

 このトレースは、実現可能性が元の順序ではなく、並べ替え後の累積時間のみに依存する様子を示しています。 

次に、順序が重要な場合を考えてみましょう。 

| ステップ | サブセット | 期限順に並べ替え | 時間の経過 | 実現可能 | 利益 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | {A、B} | A(3)、B(5) | 4 → 7 (失敗) | いいえ | - |
 | 2 | {A} | あ | 4 | はい | 8 |
 | 3 | {B} | B | 3 | はい | 6 |

 両方のジョブが個別に期限を満たしていても、有効なスケジュール内で共存させることはできません。 

これは、サブセットの選択を実現可能性のチェックから切り離せない理由を示しています。

 ## 特殊なケース

 まれなケースは、サブセットが利益を上げているにもかかわらず、注文だけが原因で実行不可能になる場合に発生します。 2 つのジョブの期限が非常に近く、処理時間が類似している場合、それらを交換することで実現可能性が決まる可能性があります。 期限で並べ替えると、早い期限が常に最初に処理されるため、隠れた違反が防止されます。 

もう 1 つのケースは、すべてのジョブの期限が同じである場合です。 このアルゴリズムは、プレフィックスの合計処理時間がその共有制限内にあるかどうかをチェックすることに帰着します。 サブセットの列挙は引き続き機能し、並べ替えは無関係になりますが、無害になります。 

最後の微妙なケースは、期待されるボーナスが基本利益を上回る場合です。 期待値は小数であるため、浮動小数点累算はサブセット間で一貫性を保つ必要があります。 倍精度を使用すると、必要な公差内での安定性が保証されます。
