 ## 解決策
 ## 問題の理解

 企業の SMS センターに届く一連のタスクが与えられます。 各タスクは時間で構成されます`t_i`到着日と番号`c_i`送信するテキストメッセージの数。 SMS センターは 1 秒あたり最大 1 つのメッセージを送信でき、メッセージは到着順にキューに入れられます。 どの時点でも、キューが空でない場合、センターは最初に 1 つのメッセージを送信し、その秒に到着する新しいメッセージをキューの末尾に追加します。 

目標は、最後のメッセージが送信された時刻と、常にキュー内のメッセージの最大数という 2 つの量を計算することです。 

制約は小さいです。`n`最大でも 1000 倍です`t_i`そして数えます`c_i`は 10^6 までです。 以来`n`が小さいため、時間を気にせずにタスクを線形に繰り返すことができますが、1 秒あたりの単純なシミュレーションでは最大`10^6`秒では遅すぎます。 

明らかではないエッジ ケースとしては、時間的に大きく離れて到着するタスクがアイドル期間を生み出し、キューが完全に空になる場合や、タスクが一度に多数のメッセージとともに到着するため、最大キュー サイズが急増する可能性があります。 たとえば、タスクが 5 つのメッセージで 1 秒目に到着し、次のタスクが 1 つのメッセージで 10 秒目に到着した場合、キューは 6 秒目までに空になり、その後 10 秒目に新しいメッセージが到着するため、最後のメッセージは 10 秒目に送信されます。不注意な実装では、これらのアイドル ギャップを考慮することを忘れる可能性があります。 

## アプローチ

 ブルートフォース手法では、最初の到着からすべてのメッセージが送信されるまで、キューを秒ごとにシミュレートします。 キューが空でない場合は毎秒メッセージを送信し、その秒に到着するメッセージを追加します。 それは正しいのですが、これは最悪の場合、最大 10^6 秒の反復を必要とし、不必要かつ非効率的です。 

重要な観察は、SMS センターが常に 1 秒あたり最大 1 つのメッセージを処理し、すべてのタスクの到着時間を把握していることです。 したがって、毎秒明示的に繰り返す必要はありません。 代わりに、キューのサイズと現在の時間を追跡し、キューが空の場合は次のタスクに時間をインテリジェントに進めたり、次のタスクが到着するまでメッセージを継続的に送信したりできます。 これにより、アイドル秒数を個別にシミュレートすることなく、キューと最大キュー サイズを更新しながら、タスク全体を線形スイープできます。 最終的な最終メッセージ時間は、残りのキューを考慮した、すべてのメッセージが送信された後の時間です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (1 秒あたりのシミュレーション) | O(max(t_i + sum(c_i))) | お(1) | タスク間のギャップが大きいと遅すぎる |
 | 最適 (タスクベースのシミュレーション) | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.初期化`queue = 0`送信を待機しているメッセージの数を表すには、`max_queue = 0`最大キュー サイズを追跡するため、および`current_time = 0`処理した最後の秒を表します。 
2. 時系列順にタスクを繰り返します。 タスクごとに`(t, c)`、到着までの時間を早めます`t`。 最後に処理されてから何秒が経過したかを計算します。`delta = t - current_time`。 この間隔中に、SMS センターは次のメッセージを送信します。`sent = min(queue, delta)`メッセージ。 減らす`queue`による`sent`そして増加します`current_time`による`delta`。 
3. 新しいメッセージを追加します`c`に`queue`経過した間隔でメッセージを送信した後。 アップデート`max_queue`として`max(max_queue, queue)`新しいメッセージを考慮して。 セット`current_time = t`タスク到着まで処理済みなので。 
4. すべてのタスクが処理された後も、キューにメッセージが残っている可能性があります。 最後のメッセージは次の後に送信されます`queue`秒。 インクリメント`current_time`による`queue`最後のメッセージが送信された最終時刻を取得します。 
5. 戻る`current_time`最後のメッセージの時刻として、`max_queue`観測された最大キュー サイズとして。 

アルゴリズム全体を通じて維持される不変条件は次のとおりです。`queue`は常に、現在時刻の処理直後に送信を待機しているメッセージの数を表します。 これにより、最大キュー サイズと最後のメッセージ時刻の計算が正確になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
tasks = [tuple(map(int, input().split())) for _ in range(n)]

queue = 0
max_queue = 0
current_time = 0

for t, c in tasks:
    # Time passed since last task
    delta = t - current_time
    # Send as many messages as possible in that interval
    sent = min(queue, delta)
    queue -= sent
    current_time += delta
    # Add new messages
    queue += c
    max_queue = max(max_queue, queue)

# Process remaining messages
current_time += queue

print(current_time, max_queue)
```このソリューションは、最初にすべてのタスクを読み取り、次にタスクの到着と残りのメッセージのみを処理することでキューを効率的にシミュレートします。 の`delta`計算により、アイドル秒数が反復処理されることなく暗黙的に考慮されるようになります。 更新中`max_queue`メッセージを追加すると、最大キュー サイズが正しく追跡されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    queue = 0
    max_queue = 0
    current_time = 0
    n = int(input())
    tasks = [tuple(map(int, input().split())) for _ in range(n)]
    for t, c in tasks:
        delta = t - current_time
        sent = min(queue, delta)
        queue -= sent
        current_time += delta
        queue += c
        max_queue = max(max_queue, queue)
    current_time += queue
    return f"{current_time} {max_queue}"

# provided samples
assert run("2\n1 1\n2 1\n") == "3 1", "sample 1"

# minimum input
assert run("1\n1 1\n") == "2 1", "single task"

# multiple messages arriving before queue empties
assert run("3\n1 2\n2 2\n3 1\n") == "6 3", "messages overlap"

# large gap between tasks
assert run("2\n1 1\n10 2\n") == "12 2", "idle period"

# all tasks have 1 message, consecutive seconds
assert run("5\n1 1\n2 1\n3 1\n4 1\n5 1\n") == "6 1", "consecutive single messages"
```| テスト入力 | 期待される出力 | 検証内容 |

 | 1 1 | 2 1 | シングルタスクのエッジケース |
 | 3\n1 2\n2 2\n3 1 | 6 3 | 到着者間でキューが重複している |
 | 2\n1 1\n10 2 | 12 2 | 大きなアイドルギャップの処理 |
 | 5\n1 1\n2 1\n3 1\n4 1\n5 1 | 6 1 | 連続到着、行列増加なし |
