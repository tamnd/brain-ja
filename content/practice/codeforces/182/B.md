 ## 解決策
 ## 問題の理解

 私たちは、独特の種類のカレンダーをシミュレートするように求められます。 Vasya は 1 日から 1 日までを示す時計を持っています。`d`。 各月には一定の日数があり、時計はそれが何月であるかを知りません。 月が変わるとき、時計の日番号が新しい月の実際の日と一致しない場合、Vasya は一致するまで手動で日を増やします。 1 年間に手動による増加が何回発生したかを数えるように求められます。 

入力は次のもので構成されます`d`、時計が表示できる最大日、`n`、月数、および配列`n`各月の日数を表す整数。 出力は、Vasya が実行する手動増分の合計数です。 

制約は小規模から中程度です。`n`最大でも 2000 であり、`d`まで可能です`10^6`。 これは、大規模な環境にわたって可能なすべての日をシミュレートすることはできないことを示唆しています。`d`素朴なアプローチを使用した場合ですが、パフォーマンスの問題なく、数か月にわたってループし、月ごとに単純な算術計算を実行できます。 

トリッキーなエッジケースには、月の合計日数が次の月に等しい場合が含まれます。`d`、または、連続する月がすでに進んでいるまたは遅れている時計の日番号から始まる場合。 たとえば、最初の月が 3 日で、2 番目の月が 1 日の場合、`d=3`の場合、時計は月 1 の終わりに 1、2、3 を表示し、月 2 の初めに 1 にリセットされる可能性があります。モジュロ演算を不注意に扱うと、ここでオフバイ 1 エラーが発生する可能性があります。 

## アプローチ

 強引なアプローチは、1 年中毎日をシミュレートすることです。 時計の1日目から始めます。 現在の月の各日について、時計が現在の日付と一致しているかどうかを確認します。 そうでない場合は、一致するまで手動でクロックを増やします。 その後、翌日に移ります。 これは Vasya の動作を正確にモデル化しているため機能しますが、最悪の場合、`sum(a_i)`に達する可能性のある操作`2*10^9`もし`n=2000`そして`a_i`すべてです`d=10^6`。 これでは遅すぎます。 

重要な点は、1 か月の手動増分回数は、月の初めに時計が示す日番号とその月の日数のみに依存するということです。 現在の時計の日付が`c`そしてその月は`m`日の場合、月初めに必要な手動増分数は次のようになります。`(c + m - 1) // d`または、より直感的に、数えた後`m-1`数日、時計がオーバーフローして過ぎても`d`、各オーバーフローは、追いつくために必要な手動増分を表します。 これはモジュロ演算で処理できます。 これにより、シミュレーションが数か月にわたる単純なループに削減され、O(1) 時間で月ごとの増分数が追加されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(合計(a_i)) | お(1) | 大きい d | には遅すぎます。 
| 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 2 つの変数を初期化します。`current_day`時計の場合は 1 に設定し、`manual_count`手動増加の合計を保存するには 0 にします。 
2. 各月を順番にループします。 
3. 当月の場合`days_in_month`:

 ａ． 必要な手動増加の数を次のように計算します。`(current_day + days_in_month - 1) // d * d - (current_day + days_in_month - 1) % d`。 より単純な同等のアプローチは次のとおりです: 時計が経過する余分な日数`d`数えるとき`days_in_month - 1`日々。 

b. その数字を加えます`manual_count`。 

c. アップデート`current_day`に`(current_day + days_in_month - 1) % d + 1`。 これにより、次の月が正しい日に始まるようにしながら、24 時間正しくラップされます。 
4. すべての月を処理した後、印刷します。`manual_count`。 

機能する理由: アルゴリズムは、次の不変条件を維持します。`current_day`毎月初めの時計の日です。 この計算により、クロックが「オーバーフロー」するたびに、`d`、手動増分をカウントします。 ラッピングすることで`current_day`モジュロ`d`、時計のリセットを正しくモデル化し、次の月が正確な開始時計日から始まることを保証します。 各月は独立して処理され、手動増加の合計は正しく合計されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

d = int(input())
n = int(input())
a = list(map(int, input().split()))

manual_count = 0
current_day = 1

for days_in_month in a:
    # Number of manual increments before the month ends
    manual_count += max(0, current_day + days_in_month - d - 1)
    # Update clock day for next month
    current_day = (current_day + days_in_month - 1) % d + 1

print(manual_count)
```ループは各月を順番に処理します。 私たちは計算します`max(0, current_day + days_in_month - d - 1)`正の増分のみをカウントするようにするため。 月が現在のクロック範囲内に完全に収まる場合は、手動で増やす必要はありません。 モジュロ演算によりクロックが正しくラップされ、off-by-one エラーが回避されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各月を 1 回だけループし、1 か月あたり O(1) の演算を実行します。 |
 | スペース | O(n) | 月の長さの入力配列のみを保存します。 他のすべての変数は定数です。 |

 n ≤ 2000 という制約を考慮すると、これは 1 秒未満で快適に実行されます。 メモリ使用量は最小限です。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    d = int(input())
    n = int(input())
    a = list(map(int, input().split()))
    manual_count = 0
    current_day = 1
    for days_in_month in a:
        manual_count += max(0, current_day + days_in_month - d - 1)
        current_day = (current_day + days_in_month - 1) % d + 1
    return str(manual_count)

# provided sample
assert run("4\n2\n2 2\n") == "2", "sample 1"

# custom cases
assert run("1\n1\n1\n") == "0", "minimum input"
assert run("5\n3\n3 5 2\n") == "4", "overflow across multiple months"
assert run("6\n2\n6 6\n") == "5", "full months equal to d"
assert run("10\n4\n1 2 3 4\n") == "0", "all months fit in clock"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1\n1\n1 | 0 | 最小入力サイズ |
 | 5\n3\n3 5 2 | 4 | 複数の月にわたるオーバーフロー |
 | 6\n2\n6 6 | 5 | 月は d に等しく、エッジ オーバーフローをテストします。 
| 10\n4\n1 2 3 4 | 0 | すべての月が時計に適合し、手動で増やす必要はありません。 

## 特殊なケース

 時計が1日しかないとしたら、`d=1`、最初を除く新しい日ごとに手動で増分する必要があります。 例えば、`d=1`、`n=3`、`a=[1,1,1]`手動で 2 回増分することになります。 アルゴリズムはこれを処理します。`(current_day + days_in_month - d - 1)`次の場合でもオーバーフローを正しく計算します。`d=1`。 

月が残りのクロック範囲に完全に適合する場合、手動による増分は発生しません。 のために`d=6`、時計 4 から始まる 3 日のある月、`(4 + 3 - 6 - 1)`0 と評価され、増分は生成されません。これは、期待される動作と一致します。
