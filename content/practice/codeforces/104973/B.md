 ## 解決策
 ## 問題の理解

 私たちは帽子の束を与えられ、それぞれの帽子には固有のラベルが付けられており、いつでも束の一番上にのみアクセスできます。 人は1人からn人まで決まった順番で一人ずつ到着します。 各人が到着したら、現在のシルクハットを渡すか（山積みから取り出して）、スキップして何も渡さないかのどちらかです。 

人は、ラベルが自分の指数と正確に一致する帽子を受け取った場合にのみ幸せとみなされます。 違う帽子をもらったり、何ももらえなかったりすると、彼らは不幸になります。 また、どの人々が幸せでなければならないか (S[i] = 1)、どの人々が不幸でなければならない (S[i] = 0) かを記述するバイナリ文字列 S も与えられます。 課題は、まさにそれらの人々を幸せにする一連の「シルクハットを取る」と「スキップ」操作が存在するかどうかを判断することです。 

重要な構造は、ハットがスタック順に厳密に消費されるため、恣意的に割り当てているわけではありません。 私たちはいつポップするかを決めているだけです。 

この制約により、テスト ケース全体で n は最大 10^5 まで許可され、すべての選択をシミュレートしたり、アクションのサブセットをバックトラックしようとするアプローチは即座に除外されます。 テスト ケースごとの動作が O(n^2) であっても遅すぎるため、解は線形または線形に近いものでなければなりません。 

微妙なエッジケースは、S が多数の帽子を持っているにもかかわらず、一致する帽子に適切なタイミングでアクセスできない場合です。 たとえば、人 i は幸せなはずなのに、帽子 i がスタックの奥深くに現れて、i に到達する前に追い越されてしまうと、回復することは不可能になります。 もう 1 つの失敗例は、試合が必要なポジションをスキップせざるを得なくなった後、誤って必要な帽子をあまりにも早く消費してしまった場合です。 

最も難しいのは、タイミングの管理です。インデックス i のハットを選択できる場合、i を提供することを選択した時点で、i というラベルの付いたハットが正確に先頭になければなりません。そうしないと、後の強制ポップによって消費されてしまう可能性があります。 

## アプローチ

 強引な戦略では、各人に対して考えられるすべての一連の決定 (スキップするか帽子をかぶるか) が試行されます。 最悪のケースでは 2^n 通りの可能性があり、各シミュレーションのコストは O(n) となるため、完全に実行不可能になります。 

ただし、スタック構造には強い制約が導入されます。つまり、ハットは固定された順序で消費されるため、次にどのハットが表示されるかを選択することはなく、今ポップするか後でポップするかだけを選択します。 これにより、問題は、S によって指示された強制一致を満たそうとしながら、順列 H を制御されたウォークに変換されます。 

重要な洞察は、視点を逆転させることです。 各人が決定することについて考えるのではなく、次に必要な「正しい帽子」をその位置に合わせられるかどうかを追跡します。 S[i] = 1 の場合は必ず、将来の実現可能性を損なわない方法でのみ i を現在の先頭または遅延と一致させることができるようにしつつ、スタックがどのように進化するかをシミュレーションします。 

これにより、H に対するスタック ポインタと people に対するポインタを使用した貪欲な検証が行われます。 私たちは人々を順番に処理し、必要な場合にのみ帽子スタックを進めますが、必要な一致を誤ってスキップしないようにします。 

問題は、スタック順序の制約を尊重した方法で一致をスケジュールできるかどうかを確認することに帰着します。

 ## アルゴリズムのチュートリアル

 帽子スタック上にポインタを保持し、1 人から n 人まで順番に処理することをシミュレートします。 

1. ポインタを初期化する`p = 1`帽子のスタックの一番上に。 私たちはまた、人々に対する指針を維持します`i = 1`nに。 
2. 1 から n までの各人 i について、S[i] の要求に応じて彼らを幸せにできるかどうかを決定しようとします。 
3. S[i] = 1 の場合、ある時点でハット i を確実に与える必要があります。 ハットはスタック順でのみ利用できるため、ハット i が見つかるかスタックを使い果たすまで、スタックからハットを繰り返し消費します。 消費された帽子はすべて、すぐに誰かに割り当てられます (必ずしも正しく割り当てられるとは限りません)。 
4. このプロセス中に帽子 i が一番上の位置にある場合は、それを人 i に割り当てて続行します。 
5. S[i] = 0 の場合、自由に割り当てたりスキップしたりできますが、ハットを慎重に消費する必要があります。あまりに積極的に消費すると、将来必要な一致が破壊される可能性があるためです。 この配合では、強制一致を満たすために必要な場合にのみ消費します。 
6. どこかの時点でハット i (S[i] = 1) が必要であるが、スタックが使い果たされているか、間違って渡されたため、ハット i (S[i] = 1) に到達できない場合は、NO を返します。 
7. すべての制約が満たされた状態ですべての i の処理が終了すると、YES が返されます。 

重要な考え方は、必要な一致に達するために必要な以上に消費を遅らせないということです。遅らせても、将来利用できる選択肢が減るだけだからです。 スタックの性質により、一度ハットを通過すると回復できないことが保証されているため、正しさは必要なハットを決してスキップしないことに依存します。 

### なぜ効果があるのか

 このアルゴリズムはスタックの単調な消費を維持します。 どの時点でも、残りのハットのセットは正確に元のスタックのサフィックスになります。 必要なインデックス i を処理するときに、ハット i がまだそのサフィックスにある場合、順番に 1 回だけ遭遇します。 サフィックスの境界から消える前にそれに遭遇できなかった場合、その後の一連のスキップやテイクによってそれを回復することはできません。 これにより、必要十分条件が確立されます。処理順序で i に到達した時点で、必要なすべての i が残りのサフィックスに出現する必要があり、貪欲な消費により、将来の実現可能性が時期尚早に無効になることがないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        H = list(map(int, input().split()))
        S = input().strip()

        pos = {H[i]: i for i in range(n)}

        # we simulate a pointer over the stack
        i = 0
        ok = True

        # we track the furthest we have consumed
        # stack is H[0..i-1] consumed, H[i..] remaining
        for person in range(1, n + 1):
            if S[person - 1] == '0':
                continue

            # we need to find person in remaining stack
            if pos[person] < i:
                ok = False
                break

            # advance i until we reach pos[person]
            i = pos[person] + 1

        print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()
```コードはまず、各ハット ラベルをスタック内の位置にマップします。これにより、必要なハットがどこにあるかを常にチェックできるようになります。 変数`i`スタックのどのくらい下まですでに消費したかを表します。 幸せそうな人に出会ったとき、私たちはその人の帽子がまだ消費されていないかを確認します。 すでに遅れている場合`i`、これは、不可逆的にそれを通過し、構成が不可能になったことを意味します。 

前進`i`に`pos[person] + 1`必要なハットに到達するまで、モデルはすべての中間ハットを消費します。 これは、要件を満たすために必要な場合にのみ「強制消費」するという考えと一致します。

 ## 特殊なケース

 重要なエッジ ケースは、必要なハットがスタックの奥深くにあるにもかかわらず、以前に必要な一致がそれを超えて消費することを強制される場合に発生します。 たとえば、S が後のラベルを最初に一致させることを強制する場合、必要な前のラベルを暗黙的にスキップする可能性があります。 アルゴリズムはこれを検出します。`pos[i] < i`は、必要な位置を超えてすでに消費していることを示します。 

もう 1 つの特殊なケースは、S がすべて 1 である場合です。 その場合、アルゴリズムは効果的にすべてのラベルを昇順に照合しようとしますが、スタック順序は依然として尊重されます。 スタックの置換が ID の順序と一致しない場合、必要な要素が消費ポインターの後ろにあるときにエラーが発生します。 

3 番目のエッジ ケースは、S がすべて 0 の場合です。 アルゴリズムは強制的な消費を実行しないため、`i`は全体を通してゼロのままであり、答えは常に YES であり、制約が存在しないことを正しく反映しています。
