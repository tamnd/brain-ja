 ## 解決策
 ## 問題の理解

 私たちは一列に並べられたデータベースのコレクションを与えられています。 各データベースは、固定容量のキューのように動作します。 また、一連の操作もあり、各操作は値を取得し、インデックスが指定された間隔内にあるすべてのデータベースにその値をプッシュします。 この挿入後にデータベースがその容量を超えた場合、先頭から最も古い要素がすぐに削除されます。 

すべての操作を処理した後、各データベースには一連の値が含まれますが、値が繰り返されても問題ありません。 タスクは、データベースごとに、データベース内に残っているさまざまな値の数を計算することです。 

主な問題点は、各操作がデータベースのセグメント全体に影響を及ぼし、各データベースは時間の経過とともに受信する更新の数に応じて独自のキューの進化を伴うことです。 直接シミュレーションを行うには、操作ごとに最大 200,000 のデータベースにプッシュする必要がありますが、これはすでに大きすぎ、各データベースには最大 200,000 の操作が蓄積される可能性があるため、単純なキュー シミュレーションは実行不可能になります。 

プロセスを再解釈する有効な方法は、最後に残るものに焦点を当てることです。 各データベースは、それに影響を与える最新の c[i] 挿入のみを保持します。 キューがオーバーフローすると、古い挿入は順番に削除されます。 これは、実際には中間状態は考慮せず、データベースごとの関連する更新の最終的なサフィックスのみを考慮することを意味します。 

各データベースを個別にシミュレートしようとしているにもかかわらず、すべての操作が単純に処理されている場合、微妙な失敗のケースが発生します。 たとえば、すべての操作がすべてのデータベースに影響し、容量が大きい場合、単純なデータベースごとのキュー実装では依然として O(nq) プッシュが実行されますが、これは制限をはるかに超えています。 もう 1 つの落とし穴は、削除が厳密に前面から行われることを忘れていることです。これにより、構造が単なる複数の適用された操作ではなく、時間の経過とともにスライディング ウィンドウになってしまいます。 

## アプローチ

 ブルート フォース アプローチでは、間隔内ですべてのデータベースを反復処理し、値をキューにプッシュすることで、各操作を明示的にシミュレートします。 各データベースは両端キューを維持し、容量を超えると先頭からポップします。 これはステートメントを直接反映しているため、正しいです。 ただし、各操作は O(n) データベースに影響する可能性があるため、合計の複雑さは O(nq) になり、2⋅10^5 スケールではまったく実行不可能です。 

重要な観察は、視点を逆転させることです。 時間の経過とともにキューがどのように進化するかを追跡する代わりに、固定データベースを考慮してください。 すべての操作は i に影響を与えるか、影響しないかのどちらかです。 存在する場合、1 つの要素がキューに追加されます。 キューはオーバーフロー時に常に先頭から削除するため、データベース i の最終状態は、i を含む最後の c[i] 操作 (時間順) で正確に構成されます。 

したがって、問題は次のようになります。インデックス i ごとに、その間隔が i をカバーするすべての操作を収集し、それらを時間で並べ替え、最後の c[i] を取得し、それらの x[i] の中の個別の値をカウントします。 

課題は、時間の経過とともに多くの範囲からポイントへのクエリに効率的に応答することになりますが、データを集約するのではなく収集するだけです。 

データベース インデックスに対するセグメント ツリーを使用して、これをモデル化できます。 各操作 (l、r、x) は、その間隔を完全にカバーするすべてのセグメント ツリー ノードに保存されます。 これにより、固定インデックス i について、そのルートからリーフへのパス上のノードに、それに影響を与える操作が正確に含まれることが保証されます。 各ノードは操作を時間の増加順に保存します。 

単一の i について答えるために、その O(log n) ノードからリストをマージし、k-way マージを使用して最新の c[i] 操作のみを抽出します。 k が小さいため、すべてのインデックスを合計しても十分効率的です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション | O(nq) | O(n) | 遅すぎる |
 | セグメント ツリー + インデックスごとのマージ | O((n + q) log n + ∑c[i] log log n) | O((n + q) log n) | 承認済み |

## アルゴリズムのチュートリアル

 1. インデックス 1 から n までのセグメント ツリーを構築します。 各ノードは、そのノードのセグメントを完全にカバーする操作のリストを保存します。 これにより、すべてのデータベースに明示的に触れることなく、範囲の更新を表すことができます。 
2. 時間インデックス i の各操作 (l[i]、r[i]、x[i]) について、[l[i], r[i]] によって完全にカバーされるセグメント ツリー ノードに i を挿入します。 この分解により、各操作が O(log n) 回のみ保存されることが保証されます。 
3. セグメント ツリー内の各ノードについて、追加された順序で操作を維持します。これは時間の増加に対応します。 これにより、各ノード内でリストがすでに時系列順に準拠していることが保証されます。 
4. データベース位置 i ごとに、セグメント ツリー パスをルートからリーフまでたどり、そのパス上のノードに格納されているすべてのリストへのポインタを収集します。 これらのリストは、i に影響を与えるすべての操作をまとめて表します。 
5. データベース i について、これらの O(log n) 個のソート済みリストの k-way マージを実行し、常に最新の残りの操作を最初に選択します。 古い操作は最終的なキューの状態に影響を与えることができないため、 c[i] 操作を収集したら停止します。 
6. 収集された操作インデックスから、その x 値を抽出し、それらをセットに挿入して、データベース i の個別の値をカウントします。 
7. セットのサイズをデータベース i の答えとして出力します。 

### なぜ効果があるのか

 データベースに影響を与える各操作は、そのデータベースのルートからリーフへのパス上の 1 つ以上のセグメント ツリー ノードの 1 つの発生に正確に対応します。 各ノードは操作を時間順に格納するため、これらのリストをマージして最新の c[i] 要素を取得すると、関連するすべての操作の長さ c[i] のサフィックスが正確に再構築されます。 すべてのオーバーフローが最も古い要素を削除するため、そのサフィックスはキューの最終的な内容と同じになります。これは、最後の c[i] 挿入を除くすべてを破棄するのと同じです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    c = list(map(int, input().split()))

    ops = []
    for _ in range(q):
        l, r, x = map(int, input().split())
        ops.append((l - 1, r - 1, x))

    size = 1
    while size < n:
        size *= 2

    tree = [[] for _ in range(2 * size)]

    def add(node, nl, nr, l, r, idx):
        if l <= nl and nr <= r:
            tree[node].append(idx)
            return
        mid = (nl + nr) // 2
        if l <= mid:
            add(node * 2, nl, mid, l, r, idx)
        if r > mid:
            add(node * 2 + 1, mid + 1, nr, l, r, idx)

    for i, (l, r, _) in enumerate(ops):
        add(1, 0, size - 1, l, r, i)

    for i in range(2 * size):
        tree[i].reverse()

    def collect(i):
        i += size
        res_lists = []
        while i:
            res_lists.append(tree[i])
            i //= 2
        return res_lists

    import heapq

    ans = [0] * n

    for i in range(n):
        lists = collect(i)

        heap = []
        ptrs = [len(lst) - 1 for lst in lists]

        for j, lst in enumerate(lists):
            if ptrs[j] >= 0:
                op_idx = lst[ptrs[j]]
                heapq.heappush(heap, (op_idx, j))

        taken = 0
        seen_ops = []
        k = c[i]

        while heap and taken < k:
            op_idx, j = heapq.heappop(heap)
            seen_ops.append(op_idx)
            ptrs[j] -= 1
            if ptrs[j] >= 0:
                heapq.heappush(heap, (lists[j][ptrs[j]], j))
            taken += 1

        seen = set()
        for op_idx in seen_ops:
            seen.add(ops[op_idx][2])

        ans[i] = len(seen)

    print(*ans)

if __name__ == "__main__":
    solve()
```セグメント ツリーは各操作を O(log n) ノードに格納するため、すべてのデータベースは無関係な操作をスキャンすることなく、関連する操作を正確に取得できます。 各ノード内のリバース ポインターを使用すると、最初に最新の操作にアクセスできます。これは、長さ c[i] の接尾辞のみを考慮するため必要です。 ヒープはセグメント ツリー ノード間で k-way マージを実行し、常に次に新しい操作を効率的に選択します。 

よくある実装上の落とし穴は、すべてのセグメント ツリー ノードにわたってグローバル時間順に操作を実行する必要があることを忘れていることです。 ノードからのリストを単純に連結すると、無関係な順序が混在し、正確さが損なわれます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n + ∑ c[i] log log n) | セグメント ツリー分解とインデックスごとの K ウェイ マージ |
 | スペース | O((n + q) log n) | 各操作は O(log n) ノードに保存されます。 

この構造は、各操作が対数的にのみ複製され、各データベースが O(log n) リストにわたる小規模なマージのみを処理するため、効率的です。 これは、2⋅10^5 までの n、q の制約内に問題なく適合します。

 ## 特殊なケース

 微妙なエッジ ケースは、データベースが受信する更新が合計で c[i] 未満である場合です。 この状況では、削除は発生せず、答えには適用されたすべての値の完全なセットが反映されるはずです。 k-way マージは、c[i] に到達する前に利用可能な操作がすべて使い尽くされたときに停止するだけなので、アルゴリズムはこれを自然に処理します。 

すべての操作が単一のデータベースに適用される場合、別の特殊なケースが発生します。 セグメント ツリーはすべての操作を単一のパスに沿って配置し、ヒープは 1 つのリストの単純な逆走査に縮退します。 マージ ロジックは時間順序を保持しているため、出力は正しいままです。 

最後のケースは、c[i] が 1 に等しい場合です。この場合、最新の操作のみが問題になり、ヒープはマージされたリストから単一の最大時間エントリを即座に抽出します。 これにより、問題は純粋な「最終カバー更新」クエリに集約され、構造は変更せずに処理されます。
