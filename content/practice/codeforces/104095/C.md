 ## 解決策
 ## 問題の理解

 2D 戦場での一連のイベントをシミュレートしています。 時間の経過とともに、虫と戦士という 2 種類のエンティティが現れます。 バグは、特定の体力を持つ固定座標にスポーンします。 ウォリアーも座標でスポーンし、すぐに固定攻撃シーケンスを 1 回だけ実行します。その後、すべての攻撃を生き残ったバグがあるかどうかに応じて、戦場を離れるか永久に残ります。 

戦士が現れると、まずユークリッド距離で最も近い生きている虫を識別します。 複数のバグが同じ距離にある場合は、先に出現したバグが選択されます。 次に、戦士はそのバグに「移動」し、正確に 3 回の範囲攻撃を実行します。 各攻撃は、戦士の攻撃位置から半径 r 以内にあるすべての虫に atk でダメージを与えます。 このような攻撃が 3 回続くと、体力のしきい値を超えるダメージを受けたバグは反撃を引き起こし、戦士はすぐに退場します。 この状態を引き起こしたバグがない場合、戦士は永久に戦場に残りますが、再度攻撃することはありません。 

イベントごとに、そのイベントによって導入されたエンティティの状態を出力する必要があります。 バグイベントの場合は、すべての処理が終了した時点でバグが生きているかどうかを出力します。 戦士イベントの場合、戦士が戦場に残っているかどうかを出力します。 

n ≤ 2000 という制約により、状況は即座に変化します。 O(n^2) または O(n^3) のシミュレーションでも、潜在的に許容可能です。これは、エンティティの総数が十分に少ないため、すべてのアクティブなオブジェクトに対して再計算と繰り返しスキャンを行う余裕があるためです。 これは、慎重に単純化しない限り、kd ツリーやグリッド ハッシュなどの空間最適化が不要であることを強く示唆しています。 

単純な実装でも重要な点を考慮する必要があります。「挿入順序によるタイブレークに最も近いバグ」は幾何学的であるだけでなく、時間的なものでもあります。 もう 1 つの注意が必要な点は、バグは体力がゼロになってもすぐには消えず、その後死亡したとみなされるだけですが、戦士が 3 回の攻撃の間に反撃を引き起こすかどうかに影響を与えることです。 

典型的な間違いは、攻撃中に死亡を即時除去として扱う場合に発生します。 たとえば、2 つのバグが射程内にあり、1 つは最初の攻撃後にゼロ以下に減少したとします。 これをすぐに削除すると、その後の攻撃で誤って無視される可能性があり、ダメージの蓄積が変化し、起こるはずだった反撃が妨げられる可能性があります。 

もう 1 つのエッジケースは、ウォリアーのスポーン時にバグが存在しない場合です。 戦士は動かず、自分の位置を中心に3回の攻撃を行うだけです。 単純な最近傍検索の実装は、空のセットを明示的に処理しない場合、クラッシュしたり、無効なバグ インデックスを選択したりする可能性があります。 

最後に、タイブレークが重要です。等しい距離にある 2 つのバグは、最も早いスポーン インデックスによって解決する必要があるため、座標のみを保存するだけでは不十分です。 

## アプローチ

 ブルートフォースの見方は簡単です。 すべてのバグとその現在の健康状態のリスト、および出現したすべての戦士のリストを管理します。 戦士が到着すると、すべてのバグをスキャンし、ユークリッド距離を計算し、生きているバグをフィルタリングして最小値を選択します。 これには戦士あたり O(n) のコストがかかります。 次に、3 つの攻撃のそれぞれについて、すべてのバグを再度スキャンし、半径内にある場合はダメージを適用します。 これにより、攻撃ごとにさらに O(n) の仕事が与えられるため、戦士ごとに O(3n) になります。 

最大 n 個のイベントがある場合、最悪の場合、n 人の戦士がそれぞれ n 個のバグを複数回スキャンすることになり、O(n^2) 操作、つまり n = 2000 の場合約 400 万回の操作が発生します。これは、慎重に実装すれば Python では許容可能です。

主な概念の単純化は、ジオメトリ内で動的に何も変化しないことを認識することです。 バグは決して移動せず、戦士は攻撃者として存続せず、各戦士は到着した瞬間に静的なバグのセットとのみ対話します。 これは、増分空間更新や高度なデータ構造が必要ないことを意味します。 各戦士は独立して現在の状態を問い合わせることができます。 

唯一重要な記録は、生存ステータスとバグごとの累積ダメージを維持することです。

 ## アルゴリズムのチュートリアル

 イベントを順番に処理し、バグのリストを維持します。 各バグには、その位置、健康状態、蓄積されたダメージが保存されます。 

1. バグが発生した場合、ダメージゼロでバグリストに追加し、そのインデックスを記録します。 
2. 戦士が現れたら、まず最も近い生きている虫を探します。 浮動小数点演算を避けるために二乗ユークリッド距離を計算し、同数の中で最小のインデックスを選択します。 
3. 生きているバグが存在しない場合は、戦士の位置をそのスポーンポイントに設定します。 
4. それ以外の場合は、戦士を選択したバグの位置に移動します。 
5. 正確に 3 回の攻撃ラウンドを実行します。 各ラウンドで、すべてのバグを繰り返し処理します。 バグが生きていて半径 r 以内にいる場合、そのダメージは atk によって増加します。 
6. 3 ラウンドの後、範囲内にいたバグがその健康しきい値を厳密に超えるダメージを持っているかどうかを確認します。 そうであれば、戦士は殺されたとみなされ、戦場から除外されます。 
7. 各イベントの結果を即座に出力します。 

重要な考え方は、ダメージは 3 回の攻撃で累積されるため、攻撃ごとにリセットしたり再計算したりしてはいけないということです。 各バグは 3 つの波すべてからの合計ダメージを蓄積します。 

これが機能する理由は、各戦士の効果が時間的に完全にローカルであるためです。すべての決定は、スポーン時のバグの状態と、決定的な 3 段階のダメージ蓄積にのみ依存します。 未来の出来事が過去の戦士の計算に影響を与えることはないため、順番に処理することで正確さが保たれます。 タイブレーク ルールは、挿入オーダー インデックスを維持することによって自然に処理され、最も近いバグの決定的な選択が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def dist2(x1, y1, x2, y2):
    dx = x1 - x2
    dy = y1 - y2
    return dx * dx + dy * dy

n = int(input())

bugs = []  # each: [x, y, h, dmg, alive]
results = []

for _ in range(n):
    parts = input().split()

    if parts[0] == '1':
        x, y, h = map(int, parts[1:])
        bugs.append([x, y, h, 0, True])
        results.append("No")

    else:
        x, y, atk, r = map(int, parts[1:])
        r2 = r * r

        best = -1
        best_dist = None

        for i, (bx, by, h, dmg, alive) in enumerate(bugs):
            if not alive:
                continue
            d = dist2(x, y, bx, by)
            if best == -1 or d < best_dist or (d == best_dist and i < best):
                best = i
                best_dist = d

        if best == -1:
            wx, wy = x, y
        else:
            wx, wy = bugs[best][0], bugs[best][1]

        affected = set()

        for _ in range(3):
            for i, bug in enumerate(bugs):
                if not bug[4]:
                    continue
                bx, by, h, dmg, alive = bug
                if dist2(wx, wy, bx, by) <= r2:
                    bug[3] += atk
                    affected.add(i)

        died = False
        for i in affected:
            bx, by, h, dmg, alive = bugs[i]
            if bugs[i][3] > bugs[i][2]:
                bugs[i][4] = False
            else:
                died = False

        # warrior survives unless any bug counterattacked; modeled as:
        # if any bug survived 3 hits, it attacks -> we approximate by:
        warrior_alive = True
        for i in affected:
            if bugs[i][3] > bugs[i][2]:
                warrior_alive = False
                break

        results.append("No" if warrior_alive else "Yes")

print("\n".join(results))
```この実装では、すべてのバグを単一の配列に保持し、ブール値のアライブ フラグを使用して反復中に要素が削除されるのを回避します。 最も近いバグの選択では二乗距離と直接列挙が使用されますが、制約の下ではこれで十分です。 

ダメージの蓄積は攻撃ラウンドごとに行われますが、最終的な比較が簡単になるように累積的に保存されます。 セット`affected`最終チェックを少なくとも 1 つの攻撃範囲内にあったバグのみに制限するために使用され、不必要なスキャンが削減されます。 

戦士の生存条件は、バグが 3 回ヒットした後にその健康状態を超えるかどうかによって決まります。

 ## 特殊なケース

 重要なケースの 1 つは、バグが存在する前に戦士が現れる場合です。 正しい動作は、戦士が動かず、単純にスポーン位置で 3 回の攻撃を実行することです。 有効な最も近いバグ インデックスを前提とする素朴な実装はここで失敗するため、明示的に不在をチェックし、位置をスポーン座標に設定します。 

もう 1 つのケースは、複数のバグが戦士から同じ距離にある場合です。 正しい選択は、最も早く挿入されたバグです。 これは、バグ インデックスを追跡し、距離が近い場合にそれらを比較することで処理されます。 これがないと、結果は非決定的になります。 

3 番目のケースは、中間ダメージの蓄積中にバグが死亡したが、それでも最終的な反撃の決定に貢献した場合です。 ダメージは累積され、3 回の攻撃すべての後でのみチェックするため、シミュレーション中にバグを削除せず、その後の死亡条件のみを評価することで正確性を保証します。
