 ## 解決策
 ## 問題の理解

 コンテストの各提出物は 1 人の出場者に属し、各出場者は受け取ることができる評決に関して個人的な制限があります。 すべての送信に対して、システムは決定的な結果を生成しません。 代わりに、その提出を行った出場者に許可された評決の中から均一にランダムに選択されます。 

タスクは、このランダム性をシミュレートすることではなく、すべての提出物が審査された後に各評決が現れると予想される回数を計算することです。 

プロセスを再構成する有効な方法は、提出物ごとに考えることです。 すべての提出物は、評決のサブセットに確率質量を与えます。 出場者が持っている場合$t$許可された評決の場合、それらの評決のそれぞれに確率が与えられます$1/t$その提出から、他のすべての評決は貢献を受け取りません。 最終的な答えは、すべての提出物に対するこれらの貢献の合計にすぎません。 

提出数が上限に達する可能性があるため、制約は重要です。$10^5$一方、判定タイプの数は非常に少なく、最大でも 10 です。これは、大量のペアごとの計算や提出に対する状態追跡を伴うものではなく、どのようなソリューションも提出数が線形であり、出場者ごとの評決数に比例する必要があることをすぐに示唆しています。 

素朴だが間違った方向性は、ランダム性をシミュレートしたり、結果を繰り返しサンプリングして結果を平均したりすることです。 これでは分散が生じて正確に収束せず、何度繰り返しても遅すぎて近似値にすぎません。 

さらに微妙な間違いは、出場者ごとに集計せずに、提出物を独立して処理しようとすることです。 高価な構造を使用して、すべての提出に対して許可セットを最初から再計算した場合でも、制約を通過する可能性がありますが、重要な洞察は、同じ出場者が何度も出現するため、その確率分布を事前に計算することが不可欠であるということです。 

確率モデル自体にはトリッキーな例外ケースはありませんが、微妙な例外ケースの 1 つは、許可された評決が 1 つしかない出場者です。 その場合、その出場者によるすべての投稿は、確率 1 で決定論的にその評決に寄与します。もう 1 つは、どの出場者にも評決が許可されない場合であり、この場合、期待される頻度は正確にゼロになります。 

## アプローチ

 1 つの提出物を個別に見ると、計算は簡単です。 出場者を仮定します$c$許可されたサイズのセットがある$t_c$。 次に、許可された各評決に対して$v$、この投稿は貢献します$1/t_c$予想される数まで$v$。 すべての提出物を合計すると、最終的な期待値が得られます。 

ブルートフォースアプローチでは、各提出物を個別に処理し、それぞれに対してすべての提出物を反復処理します。$K$評決、その出場者に許可されているかどうかを確認します。 それにより得られるのは$O(NK)$時間、これはすでに許容できる時間です$K \le 10$, しかし、これは最もきれいな構造ではありません。 さらに悪い総当り攻撃の亜種では、出場者の分布を事前計算せずに、提出ごとに動的に確率を計算しようとし、入力サイズと判定セットのサイズの積に比例して作業が繰り返されることになります。 

重要な観察は、配分は提出物ではなく、出場者のみに依存するということです。 したがって、各出場者について、確率ベクトルを事前に計算できます。$K$判決。 これが完了すると、各送信は単純なルックアップとベクトル加算になります。 

これにより、問題が構築に変換されます$M$小さな確率ベクトル、その後の合計$N$提出物の所有権に応じてそれらのコピーを作成します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 送信ごとの再計算 | O(NK) | O(K) | 受け入れられますが冗長です |
 | 出場者ごとに事前計算 | O(MK + N) | O(MK) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 提出数を読む$N$、出場者数$M$、および判定タイプの数$K$。 さまざまなサイズを維持します$K$期待されるカウントを蓄積します。 
2. 各出場者について、許可された判定リストを読み取って保存します。 サイズも計算します$t$。 このサイズは、この出場者の提出物から各評決が受け取る確率の質量を直接決定します。 
3. 各出場者の確率ベクトルを構築します。 許可されたすべての評決に対して$v$、確率を割り当てる$1/t$。 このベクトルは、その出場者からの単一の提出物の予想される貢献を表します。 
4. 一連の提出物を読みます。 各提出物は、どの出場者がそれを作成したかを示すだけなので、そのインデックスを使用して事前計算された確率ベクトルを取得します。 
5. 提出物ごとに、出場者の確率ベクトルをグローバル回答配列に追加します。 これは、独立した試験全体で期待される寄与を合計することに相当します。 
6. 最終的に蓄積されたベクトルを十分な精度で出力します。 

これが有効である理由は、期待値が線形であるためです。 各提出物は各評決の期待数に独立して寄与するため、共同分布をモデル化する必要がなく、提出物ごとの期待値を合計すると、正しい全体的な期待値が得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    N, M, K = map(int, input().split())
    
    allowed = [[] for _ in range(M)]
    prob = [[0.0] * K for _ in range(M)]
    
    for i in range(M):
        qt = int(input())
        arr = list(map(int, input().split()))
        allowed[i] = arr
        p = 1.0 / qt
        for v in arr:
            prob[i][v - 1] = p
    
    ans = [0.0] * K
    
    for _ in range(N):
        c = int(input()) - 1
        pc = prob[c]
        for i in range(K):
            ans[i] += pc[i]
    
    print(" ".join(f"{x:.6f}" for x in ans))

if __name__ == "__main__":
    main()
```コア構造は、前処理を集計から分離します。 前処理ステップでは、出場者ごとに固定の確率ベクトルを構築します。これにより、提出ループ中の繰り返しの分割や繰り返しのリスト処理が回避されます。 

実装の微妙な詳細の 1 つはインデックス付けです。 判定は 1 ベースの入力として与えられるため、確率ベクトルに格納する前に 0 ベースのインデックスにシフトする必要があります。 もう 1 つの詳細は、浮動小数点の累算が倍精度で確実に行われるようにすることです。これは Python の float によって自然に提供されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(MK + N K) | 確率ベクトルの構築には MK が必要で、送信ごとに長さ K のベクトルが追加されます。 
| スペース | O(MK + K) | 出場者ごとの配布と最終解答のストレージ |

 境界は十分に小さいため、最悪の場合でも$10^5 \times 10$Python では蓄積は簡単です。 メモリも安全なので、$M \le N$そして$K \le 10$したがって、完全な確率テーブルを保存するのはごくわずかです。

 ## 特殊なケース

 重要なエッジケースは、出場者が許可された評決を 1 つだけ持っている場合です。 この状況では、確率ベクトルには 1 が 1 つ含まれ、残りは 0 になります。 たとえば、出場者 0 が評決 2 のみを許可する場合、すべての提出物は評決 2 にちょうど 1 を与えます。アルゴリズムはこれを自然に処理します。$1/t = 1$したがって、特別な分岐は必要ありません。 

もう 1 つのエッジ ケースは、異なる出場者が互いに素な許可セットを持っている場合です。 各送信は独自のローカル ディストリビューション内でのみ貢献するため、アルゴリズムは引き続き正しく動作します。 蓄積は純粋に加算されるため、出場者間の干渉はありません。 

最後のエッジケースは、どの出場者の許可されたセットにも評決がまったく表示されない場合です。 その場合、すべての確率ベクトル内のその列はゼロのままであるため、集計中に寄与を受け取ることはありません。
