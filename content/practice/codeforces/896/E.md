 ## 解決策

 ## 問題の理解

 2 種類の範囲演算の下で、時間の経過とともに変化する正の整数の配列を維持しています。 各要素は残りの「ベーキング時間」を表し、操作では一部の値を減らすか、正確なターゲット値に一致する要素がいくつあるかを尋ねます。 

最初の操作ではセグメントとしきい値 x を取り、そのセグメント内のすべての位置について、現在の値が x より大きい場合は、そこから正確に x を減算します。 すでに x 以下の値は変更されません。 2 番目の操作では、再びセグメントに対して、その時点で x と正確に等しい値がいくつあるかを尋ねます。 

難しさは、両方の操作が範囲ベースであり、それらの操作が最大 100,000 個あり、値と配列サイズも最大 100,000 であるという事実から来ています。クエリごとにセグメント全体をスキャンする単純なシミュレーションでは O(nm) に低下しますが、これは許容範囲をはるかに超えており、約 10^10 の操作が必要になる可能性があります。 

さらに微妙な問題は、値が構造的に減少することです。 値が増加することはなく、更新のたびに値が同じ x だけ減少しますが、それは値が x より大きい場合に限られます。 これにより、均一な減算ではない「クリッピング」動作が繰り返され、加算のための典型的なセグメント ツリーの遅延伝播が役に立たなくなります。 

素朴な推論を打ち破るエッジケースには、次のようなものがあります。 

すべての値が x よりわずかに大きいセグメント。 たとえば、a = [10, 11, 12]、x = 5 の演算 1 は、[5, 6, 7] に変換します。 単純な間違いは、すべてから x を引いて、ここでは [5, 6, 7] を正しく生成することです。しかし、[3, 11, 12] など、一部の要素がすでに x 未満である場合、すべてから間違って引くと、[3, 6, 7] ではなく [−2, 6, 7] のような負の値または間違った値が生成されます。 

もう 1 つの微妙なケースは、値が複数のしきい値を超える更新が繰り返されることです。 たとえば、減算を繰り返すと、1 回の操作後に値が x を下回ってしまい、その後の操作では値が変更されないままになる可能性があり、セグメント全体で単調な均一な変化を仮定するアプローチが無効になります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 更新またはクエリごとに、範囲 [l, r] を反復処理します。 タイプ 1 の演算では、各値をチェックし、x より大きい場合は x を減算します。 タイプ 2 の場合、x に等しい値の数を数えます。 

これは定義に直接従うため、正しいです。 ただし、各操作のコストは最悪の場合 O(n) となり、O(nm) になります。 n と m が最大 10^5 の場合、これは数桁遅すぎます。 

重要な観察は、値が更新時に任意に動作しないことです。 それらは減少するだけであり、さらに重要なことは、値 a[i] が x より大きい場合は常に、同様の操作を繰り返し適用すると、実質的に a[i] mod x になります。 「x より大きい間に x を減算する」という操作は、値を [1, x] の範囲に減らすため、1 回適用すると正確に a[i] = a[i] % x になります。 

これにより、問題は、値が変更されないか、より小さな同値クラスに削減されるセグメントの追跡に変換されます。 素のセット共用体構造を使用すると、特定の操作で変更されなくなる位置をスキップできます。 位置の値 ≤ x が設定されると、それ以降、より大きな x を使用した操作がその位置に影響することはありません。 これにより、インデックスが安定するにつれて、積極的な検討からインデックスを「削除」することができます。 

インデックスに対して DSU のようなネクスト ポインター構造を維持します。 インデックス i が処理され、その値が今後の操作で安定すると、それを前方マージして、同様の更新のために再度アクセスすることがなくなります。 これにより、すべての操作にわたって各インデックスが効果的に対数回のみアクセスされることが保証されます。

タイプ 2 クエリの場合、セグメントをスキャンできません。 代わりに、範囲内の正確な値の出現をカウントできる値ベースの構造を維持します。 標準ソリューションでは、値バケットごとにフェンウィック ツリーまたは順序構造を使用しますが、この DSU ベースのアプローチでは、値を変更してプレフィックス合計をクエリするときにカウントを更新します。 

すでに安定したインデックスをスキップし、周波数構造を維持することを組み合わせることで、複雑さが O((n + m) log n) 近くまで軽減されます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | お(1) | 遅すぎる |
 | DSU + 周波数トラッキング | O((n + m) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは、DSU の「ネクスト アライブ インデックス」構造、現在値配列、および発生回数をカウントするための頻度構造という 3 つの核となるアイデアを維持しています。 

1. 配列の親を初期化します。ここで、parent[i] = i + 1 になります。これにより、完全に処理されたインデックスをスキップできます。 DSU は、範囲内の次の候補インデックスに常にジャンプすることを保証します。 
2. 値に対する頻度構造を構築します。通常は、値によってインデックス付けされたフェンウィック ツリーで、各値が出現する回数を保存します。 これにより、正確な値の範囲を効率的にカウントできるようになります。 
3. パラメーター x を使用した [l, r] のタイプ 1 演算の場合、DSU ジャンプを使用して find(l) から開始して i を反復し、i が r を超えたときに停止します。 これにより、この範囲外ですでに処理されたインデックスに触れることを回避できます。 
4. 訪問した各インデックス i について、a[i] ≤ x の場合、変更しないままにして次のインデックスに移動します。 理由は減額条件を満たしていないためです。 
5. a[i] > x の場合、周波数構造から古い値を削除し、a[i] − x に更新して、新しい値を挿入し直します。 それから私たちは前に進みます。 
6. 更新後に値が十分に小さくなり、今後の同様の操作によって影響を受けない場合は、DSU で i と i + 1 を結合し、今後のスキャンではその値をスキップします。 これが償却効率を保証するメカニズムです。 
7. タイプ 2 の演算では、[l, r] 内の x に等しい要素の数について周波数構造をクエリします。 これはプレフィックス数によって行われます。 

### なぜ効果があるのか

 各インデックスは「アクティブ」であるだけですが、将来の操作によってまだ削減される可能性があります。 DSU スキップ ルールの下で安定すると、再度処理されることはありません。 すべての更新では厳密に値が減少し、各インデックスは安定するまでに限られた回数しか遷移できないため、インデックスに触れる合計回数には制限があります。 すべての変更が削除と挿入と組み合わされ、全体的な一貫性が維持されるため、周波数構造は正確なままです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    n, m = map(int, input().split())
    a = [0] + list(map(int, input().split()))
    MAXV = 100000

    bit = Fenwick(MAXV)

    for i in range(1, n + 1):
        bit.add(a[i], 1)

    parent = list(range(n + 2))

    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x

    def union(x, y):
        x = find(x)
        y = find(y)
        if x != y:
            parent[x] = y

    def process(l, r, x):
        i = find(l)
        while i <= r:
            if a[i] <= x:
                i = find(i + 1)
                continue
            bit.add(a[i], -1)
            a[i] -= x
            bit.add(a[i], 1)
            if i < n:
                union(i, i + 1)
            i = find(i + 1)

    for _ in range(m):
        tmp = input().split()
        if tmp[0] == '1':
            _, l, r, x = map(int, tmp)
            process(l, r, x)
        else:
            _, l, r, x = map(int, tmp)
            ans = bit.range_sum(x, x)
            print(ans)

solve()
```フェンウィック ツリーは、値のグローバルな頻度を追跡します。タイプ 2 のクエリは正確な値の数を要求するため、これで十分です。 更新のたびに古い値が削除され、新しい値が挿入され、一貫性が保たれます。 

DSU 構造により、範囲の更新中に、処理の必要がなくなったインデックスが確実にスキップされます。これが、クエリごとの O(n) を回避する鍵となります。 

微妙な点は、値を更新した後に結合が行われることです。 これが重要なのは、インデックスが十分に小さくなると、すぐにスキップの対象となる必要があり、そうしないと繰り返しアクセスが発生するためです。

 ## 特殊なケース

 主なエッジケースは、値が繰り返し正確に割り切れて小さな値になる場合です。 たとえば、10 から始めて x = 3 を繰り返し適用すると、7、4、1 が生成され、その後は変更されません。 単純なアプローチでは、同じインデックスを繰り返し再利用する可能性がありますが、DSU では、ある条件下でインデックスが安定すると、その後の走査では完全にスキップされます。 

もう 1 つのケースは、一連のリダクションの後にのみ表示される値をクエリで要求する場合です。 Fenwick の更新では、すべての中間値の遷移が即座に反映されることが保証されるため、値が範囲内で「移動」した場合でも、カウントは正確に保たれます。
