 ## 問題の理解

 時間の経過とともに一連の本のリクエストが与えられ、各リクエストでは特定の本が求められます。 最大でも置ける小さな机があります$k$いつでも異なる本を。 最初は机は空です。 

本がリクエストされると、2 つのことが起こります。 本がすでに机の上にある場合は、棚から何も取得されません。 本が机の上にない場合は、棚から持ってくる必要があり、これは取り出し操作とみなされます。 新しい本を取り出す必要があるときに机がすでにいっぱいの場合は、まず既存の本を 1 冊取り除く必要があります。ルールとしては、最も最近使用されていない本、つまり最終アクセス時間が過去で最も古い本を常に削除します。 

あらゆる可能なデスク容量を計算するように求められます$k = 1 \ldots n$、この LRU ルールの下で BaoBao が棚から本を何回取り出すか。 

入力サイズについては慎重に考える必要があります。 各テスト ケースには最大で次のものを含めることができます。$10^5$すべてのテスト ケースの合計は次のとおりです。$10^6$。 LRU を個別にシミュレートするソリューション$k$各シミュレーションにコストがかかるため、すぐに遅すぎます$O(n)$、につながる$O(n^2)$テストケースごとの全体的な作業。 

単純な間違いは、より大きな問題に対する答えを考えることです$k$シミュレーションをわずかに変更することで段階的に導出できます。$k-1$。 容量を増やすとエビクション履歴がローカルではなくグローバルに変更されるため、これは失敗します。 

もう 1 つの微妙なエッジ ケースは、すべてのリクエストが同一である場合です。 たとえば、入力$[1,1,1,1]$。 どれについても$k$、最初のアクセスのみがフェッチであるため、答えは定数でなければなりません$1$すべての容量にわたって。 繰り返しのエビクションを誤ってカウントしたり、キャッシュミスを誤って処理したりするシミュレーションは、オーバーカウントします。 

2 番目のエッジ ケースは、次のような厳密な交互アクセスです。$[1,2,1,2,1,2]$ここで、LRU の動作は小さい容量間で急激に変化します。 のために$k=1$、最初のアクセス以降はすべてミスですが、$k \ge 2$、最初の 2 つだけがミスです。 これは、答えが容量のしきい値に非常に敏感であることを強調しています。 

## アプローチ

 固定の直接シミュレーション$k$は簡単です。 キャッシュを表す順序付けされた構造を維持し、アクセスごとに最新性を常に更新します。 ミスが発生してキャッシュがいっぱいになると、最も最近使用されていない要素が削除されます。 それぞれの操作は、$O(1)$リンクされた構造または順序付き辞書で償却されるため、1 回のシミュレーションにコストがかかります$O(n)$。 

ブルートフォース ソリューションでは、これをすべてのユーザーに対して繰り返します。$k$、与える$O(n^2)$テストケースごとの合計作業量。 と$n = 10^5$、これは実現可能な限界をはるかに超えています。 

重要な観察は、実際にはさまざまなキャッシュを個別にシミュレートしていないということです。 容量の唯一の違いは、アイテムが追い出されるまでにどれくらいの時間存続できるかです。 LRU の用語では、書籍は「最新ランク」が次の値を超えると削除されます。$k$、ランクはアクセス履歴によって動的に決定されます。 

立ち退きをシミュレートする代わりに、視点を反転します。 アクセスごとに、新しい個別の要素がアクティブな最新のウィンドウに導入されるか、既存の要素が更新されます。 これを支配する構造は、「最後の出来事」の順序です。 ポジションごとに$i$、 定義する$p_i$前回の出来事として$a_i$、 または$0$以前に表示されていない場合。 各リクエストは効果的に間隔を作成します$(p_i, i]$この出来事がその本への最新の言及である。 

容量に対するキャッシュミス$k$まさにいつ、その時に起こる$i$、少なくともあります$k$最後に出現するのが次の個別の本$p_i$。 同様に、個別のアクティブな「ライブ間隔」の数が重複する場合、$i$を超える$k$。 これにより、問題はそれぞれの計算に変換されます。$k$、「アクティブな個別の履歴サイズ」が次のポジションよりも大きいポジションはいくつありますか。$k$。 

したがって、位置ごとに計算します。$i$、値$d_i$、前回の出現境界以降に接尾辞に出現する個別の本の数として定義されます。$i$。 これ$d_i$時点の LRU スタック距離またはワーキング セット サイズを表します$i$。 次に、固定容量の場合$k$、フェッチはまさにそのときに発生します。$d_i > k$。

私たちは計算します$d_i$フェンウィック ツリーを長期にわたって使用し、最後の出現を追跡します。 値が見つかったら、その前の寄与を削除し、新しい値を追加します。 各位置は逆時間での範囲更新効果に寄与し、効率的に蓄積することができます。 

すべて計算した後$d_i$、周波数配列を構築し、それをプレフィックス合計してすべてに答えます$k$。

 ## アルゴリズムのチュートリアル

 シーケンスを 1 回処理し、各値の最後の出現と各位置の現在の「アクティブな寄与」を維持できる構造を維持します。 

1. 配列を左から右にトラバースして、各書籍が出現した最後のインデックスを追跡します。 これにより、現在のアクセスが最初のアクセスであるか、繰り返しであるかがわかります。 
2. ポジションごとに$i$、 識別する$p_i$、前回の発生$a_i$。 既往歴がない場合には治療を行います$p_i = 0$。 これは、この出現がその書籍の最新の代表である間隔を定義します。 
3. 当社は、各ポジションに影響を与える個別のアクティブな貢献の数を追跡する差分形式の構造を長期にわたって維持します。 繰り返し発生した場合は、前の投稿を事実上「終了」し、次の時点で新しい投稿を開始します。$i$。 これにより、LRU の意味で現在関連する個別の書籍の数を毎回維持できるようになります。 
4. この構造から、次のように計算します。$d_i$、最後の出現ウィンドウがカバーされる個別の本の数$i$。 これは、その時点での LRU ワーキング セット サイズです。$i$、最新の順序で「生きている」個別の本の数を意味します。 
5. もう一度$d_i$が計算されたら、それらを周波数配列に変換します。$\text{freq}[x]$ワーキングセットサイズを持つポジションの数を正確に数えます$x$。 
6. すべての容量の答えを接尾辞の合計によって作成します。$k$、ミスの数は、次の位置の数です。$d_i > k$、これは周波数配列のサフィックスの合計です。 

### なぜ効果があるのか

 いつでも$i$、サイズの LRU キャッシュ$k$正確に含まれています$k$アクセス履歴内の最新の個別の要素。 現在の本がこれらの中にない場合、ミスが発生します$k$を超えるワーキング セット サイズに相当します。$k$。 ワーキングセットのサイズ$d_i$その時点で LRU の順序付けに関連する個別の要素の数を正確に取得します。 これにより、問題は事前計算されたシーケンスのしきい値超過をカウントすることと同等になり、複数のキャッシュ サイズをシミュレートする必要がなくなります。

import sys

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    last = {}
    d = [0] * n
    
    active = set()
    # We will compute LRU working set size via a sliding structure
    # using last occurrences and a Fenwick-like accounting
    
    import bisect
    
    positions = {}
    arr = []
    
    # We maintain a sorted list of "active last occurrences"
    for i, x in enumerate(a):
        if x in positions:
            arr.remove(positions[x])
        positions[x] = i
        arr.append(i)
        arr.sort()
        d[i] = len(arr)
    
    freq = [0] * (n + 1)

        freq[x] += 1
