 ## 解決策
 ## 問題の理解

 私たちは時間が完全に規則的な架空の暦システムに取り組んでいます。 各年はちょうど 12 か月で、各月はちょうど 30 日で、週は月曜日から金曜日までの固定サイクルで 5 日ごとに繰り返されます。 

このカレンダーには、テスト ケースごとに 2 つの日付が与えられています。 最初の日付には既知の平日が含まれます。 2 番目の日付には曜日が付加されていません。タスクは、最初の日付の情報を参照点として使用して、2 番目の日付がどの平日に該当するかを判断することです。 

したがって、概念的には、これは 1 次元の日のタイムライン上の相対オフセットの問題です。 すべての日付は絶対日インデックスに変換でき、平日の進行は 2 つの時点が何日離れているかによってのみ決まります。 

この制約により、年の値を 10^9 まで大きくすることができますが、カレンダーの構造は完全に均一です。 これにより、数年または数か月にわたるシミュレーションの必要がなくなります。 1 つのテスト ケースで最大 10^9 の操作が必要になる可能性があるため、年の差が数十億に達する可能性がある場合、日付間を毎日繰り返すアプローチは直ちに実行不可能になります。 

意味のあるエッジ ケースは、符号処理とモジュラー演算からのみ発生します。 よくある間違いは、2 番目の日付が最初の日付より前の場合に、日付間の負のオフセットを誤って計算することです。 もう 1 つは、特に差がマイナスであるか、ちょうど 5 で割り切れる場合に、5 日間の平日サイクルでラップアラウンドを誤って処理することです。 

たとえば、今日が 2019 年 5 月 12 日の月曜日で、2019 年 5 月 11 日を求める場合、現実世界に喩えると答えは日曜日になるはずですが、ここではサイクルが 5 日しかないため、その制限されたセット内でラップされます。 負の値を正規化せずにモジュロを誤って計算すると、平日リストから外れてしまったり、誤ってインデックスが付けられたりする可能性があります。 

もう 1 つの微妙なケースは、両方の日付が同一である場合です。 この場合、オフセットはゼロとなり、計算パスに関係なく、答えは指定された曜日と正確に一致する必要があります。 

## アプローチ

 ブルートフォース手法では、月と年の推移を更新しながら 1 日を繰り返し加算することで、両方の日付を日数に変換します。 各増分により、曜日も周期的に更新されます。 これは、定義どおりにカレンダーをシミュレートするため、実装と修正が簡単です。 

ただし、最悪の場合、日付間の差異が非常に大きくなり、最大約 10^9 年の差になる可能性があります。 各年は 360 日であるため、最悪の場合、最大約 3.6 × 10^11 日になります。 したがって、一度に 1 日ずつシミュレーションを実行することは完全に不可能です。 

重要な観察は、カレンダーが完全に直線的で周期的であるということです。 すべての月と年の構造は一定であるため、算術演算を使用して任意の日付の絶対的な日数を直接計算できます。 両方の日付が整数の日インデックスとして表現されると、それらの差によって、サイズ 5 のサイクルで移動する平日のステップ数が直接決まります。 

これにより、問題は線形変換とそれに続くモジュロ演算の計算に軽減されます。 この構造は、日付を 1 次元の数直線にマッピングするのと同じであり、毎日が 1 単位であり、曜日は絶対位置に関係なく繰り返しサイクルを形成します。

 ## アルゴリズムのチュートリアル

 固定参照 (年 0、月 1、日 1 など) から始まる絶対日インデックスに任意の日付をマップする関数を定義します。 

1. 次の式を使用して、各日付を絶対的な日数に変換します。`(year * 12 * 30) + (month * 30) + day`。 これが機能するのは、各年と月のサイズが固定されており、不規則なオフセットが存在しないためです。 
2. 差を計算します`delta = index2 - index1`。 これにより、何日前進するか (マイナスの場合は後退するか) がわかります。 
3. 指定された曜日文字列を整数に変換します。`[0, 4]`、月曜日を 0 から金曜日を 4 にマッピングします。 
4. 日の差を平日インデックスに追加します。`new_index = (start_index + delta) % 5`。 
5. 結果が次の範囲内に収まるように正規化します。`[0, 4]`、Python は整数に対するモジュロ動作をすでに保証しています。 
6. 結果のインデックスを対応する曜日文字列に変換して出力します。 

### なぜ効果があるのか

 重要な不変条件は、平日の進行は絶対的なカレンダーの位置ではなく、2 つのポイント間の日数のみに依存するということです。 サイズ 5 のサイクルでは、毎日曜日がちょうど 1 ステップずつシフトされるため、既知の平日に日の差を追加することで正確さが保たれます。 絶対日付変換により、日付のペアが一貫した整数の差に換算され、固定サイクルでのモジュラー演算により、負のオフセットでも正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

days = ["Monday", "Tuesday", "Wednesday", "Thursday", "Friday"]
idx = {d: i for i, d in enumerate(days)}

def to_day_number(y, m, d):
    return y * 12 * 30 + (m - 1) * 30 + (d - 1)

T = int(input())
for _ in range(T):
    y1, m1, d1, s = input().split()
    y1 = int(y1); m1 = int(m1); d1 = int(d1)

    y2, m2, d2 = map(int, input().split())

    base = to_day_number(y1, m1, d1)
    target = to_day_number(y2, m2, d2)

    delta = target - base
    start = idx[s]

    ans = (start + delta) % 5
    print(days[ans])
```変換機能`to_day_number`カレンダーをフラットなタイムラインにエンコードします。 各年は 360 日、各月は 30 日であるため、計算は一貫しており、ループが回避されます。 

曜日インデックスは、辞書検索を使用して計算されます。 次に、絶対日数の差によってそれをシフトします。 モジュロ演算は、5 日サイクルのラップアラウンドを直接処理します。 

微妙な点の 1 つは、負の数を使用した Python のモジュロは、このコンテキストでも正しい非負の剰余を生成するため、追加の調整が必要ないことです。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys as _sys
    from math import *
    input = _sys.stdin.readline

    days = ["Monday", "Tuesday", "Wednesday", "Thursday", "Friday"]
    idx = {d: i for i, d in enumerate(days)}

    def to_day_number(y, m, d):
        return y * 12 * 30 + (m - 1) * 30 + (d - 1)

    T = int(input())
    out = []
    for _ in range(T):
        y1, m1, d1, s = input().split()
        y2, m2, d2 = map(int, input().split())

        base = to_day_number(int(y1), int(m1), int(d1))
        target = to_day_number(y2, int(m2), int(d2))

        delta = target - base
        ans = (idx[s] + delta) % 5
        out.append(days[ans])

    return "\n".join(out)

 ## 特殊なケース

 次のような同一の日付の場合、`2000 1 1 Monday → 2000 1 1`、計算されたデルタはゼロです。 アルゴリズムが生成するのは、`(start + 0) % 5`、元の平日インデックスを直接返し、特別な処理を行わずに正確さを保ちます。 

などの後進移動に`2000 1 2 Monday → 2000 1 1`、デルタは -1 です。 計算`(0 + (-1)) % 5`Python では金曜日に対応する 4 に正しく評価されます。 これにより、負のモジュロが周期的な平日インデックス付けと一貫して動作することが確認されます。 

前方への大きなジャンプの場合`2000 1 1 Monday → 999999999 12 30`、絶対的な差は非常に大きいですが、答えに影響を与えるのはその剰余のみです。 変換では範囲全体が 1 つの整数の差に圧縮され、サイクルによって大きさに関係なく正確さが保証されます。
