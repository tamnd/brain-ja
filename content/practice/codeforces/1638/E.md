 ## 解決策
 ## 問題の理解

 私たちは完全に均一に始まる長さ n の配列を維持しています。すべての位置が値 0 を保持し、色 1 に属します。時間の経過とともに、配列は 2 種類の更新を通じて進化します。 1 つのタイプは、間隔全体の色を変更し、そこにあった色を新しい色に置き換えます。 もう 1 つのタイプは、特定の色のすべての位置に固定値を追加します。 最後に、単一のインデックスの現在値を要求するポイント クエリが実行されます。 

主な問題点は、更新が色を介して相互作用することです。値は単純な加算構造でインデックスごとに直接保存されるのではなく、色ごとに蓄積され、色自体は範囲の割り当てを通じて時間の経過とともに変化します。 

この制約により、n と q の両方が 100 万に達する可能性がある状況に追い込まれます。 操作ごとにセグメントに触れるようなソリューションは、直ちに不可能になります。 クエリごとに 1 回のリニア スキャンでも、最悪の場合は 10^12 の操作が発生し、制限時間をはるかに超えます。 これにより、再色付けと追加の両方を操作ごとにほぼ一定時間で処理する必要があり、配列全体をスキャンすることなくクエリに応答できる必要がある設計が強制されます。 

素朴な考えは、各インデックスの現在の色と現在の値を維持することです。 次に、Color 操作によって範囲が更新され、Add によって指定された色のすべてのインデックスが更新され、Query によって保存された値が単純に出力されます。 問題は、カラー クラスに配列の大部分が含まれる可能性があるため、Add のコストが高くなるということです。 同様に、Color は多くのインデックスに影響を与えるため、コストが高くなります。 

「アップデートをすぐにプッシュ」しようとすると、微妙な失敗例が発生します。 たとえば、範囲 [1, n] の色を繰り返し変更し、そのたびに配列を物理的に更新しようとすると、すぐに 2 次の動作に低下します。 さらに悪いことに、色ごとのインデックスのリストのような色ベースの構造は、色が繰り返し変更されると壊れます。これは、色を変更するたびに要素をセット間で移動する必要があり、これも操作ごとに線形になるためです。 

本当の障害は、インデックスとカラーの両方の次元が動的であることです。インデックスはカラー間を移動し、カラーはグローバルな加法的シフトを蓄積します。 

## アプローチ

 ブルートフォースシミュレーションは簡単です。 色の配列と値の配列を保存します。 Color l r c の場合、l から r までループして色を更新します。 「Add c x」では、すべてのインデックスをループし、色が c のインデックスに x を追加します。 クエリは O(1) です。 

これは正しいですが、すぐに遅すぎます。 最悪の場合、1 回の Add が n 個の要素に影響し、そのような操作が q 回存在し、O(nq) 動作が発生する可能性があります。 

重要な観察点は、値の更新は位置ではなく色のみに依存するということです。 色が変化するときに何らかの方法で個々の要素に触れないようにすることができれば、代わりに色ごとの累積寄与を追跡することができます。 主な問題は、インデックスの色が時間の経過とともに変化するため、インデックスが 1 つのグループに永続的に属さないことです。 

画期的な点は、視点を逆転させることです。各インデックスを色に属するものとして考えるのではなく、各色を実行中の「タイムスタンプ付き値履歴」を維持するものとして扱います。各インデックスは、最後に色が変化したのがいつなのか、その変化の前に何が「欠落」したかを知るだけで済みます。 

追加操作に対してグローバル タイム カウンターを維持します。 各色 c は、それに適用されるすべての加算操作の合計を表す累計 add[c] を保持します。 インデックスの色が変わるときは、古い色からこれまでに蓄積された値を「凍結」し、履歴を再計算せずに新しい色に付加する必要があります。 

これを効率的に達成するために、インデックスごとに以下を維持します。 

- 現在の色
 - 現在の値
 - 色から最後に確認された寄与ベースライン

インデックスごとの更新を保存する代わりに、インデックスごとに、最後に色が変化した瞬間の合計色の寄与に等しい遅延「調整」を維持します。 クエリを実行するときに、現在の色の寄与と保存されているベースラインの差を計算します。 

色の更新は依然として範囲の割り当てであるため、すべての要素に触れることができません。 したがって、色に対する遅延伝播を備えたセグメント ツリーを使用し、各セグメントは均一または混合されます。 各ノードは、色が均一であるかどうかを保存します。 そうであれば、セグメント全体を O(1) の新しい色に直接割り当てることができます。 これにより、要素ごとの再着色が防止されます。 

加算部分は純粋にカラー レベルで処理されるため、O(1) のままです。 

したがって、最終的なシステムは、色の割り当てのためのセグメント ツリーと、色ごとの加法和のためのハッシュまたは配列、さらに値デルタのためのリーフごとのブックキーピングを組み合わせます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | セグメント ツリー + カラー遅延 + カラーごとの合計 | O((n + q) log n) | O(n + q) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各ノードがセグメントに均一な色があるかどうか、およびその色が何であるかを格納する配列上にセグメント ツリーを構築します。 最初はツリー全体がカラー 1 です。これにより、すべてのインデックスを変更することなく、セグメント全体にカラーを割り当てることができます。 
2. これまでにカラー c に追加された合計値を格納する配列 add[c] を維持します。 これは、追加クエリごとに O(1) で更新されます。 
3. Color l r c 操作の場合は、セグメント ツリーをトラバースします。 ノードが完全に範囲内にあり、すでに均一になっている場合は常に、その色を直接上書きします。 部分的に覆われているか混合されている場合は、それを押し下げて再帰します。 これにより、典型的な遅延伝播方式では O(log n) ノードのみが訪問されることが保証されます。 
4. セグメントが新たに色 c に割り当てられると、概念的には add[c] に一致するように「ベースラインをリセット」します。 これにより、今後の追加操作が正しいカラー履歴に基づいて測定されることが保証されます。 
5. クエリ i の場合、セグメント ツリーのルートからリーフまでをたどり、位置 i の色を決定します。 その色 c がわかったら、add[c] にその葉の保存されているオフセットを加えた値を返します。 

微妙な点は、各インデックスがその完全な値の履歴を保存していないことです。 代わりに、最後のリセットと現在のグローバル カラー累積の差のみを保存します。 これにより、繰り返しの再計算が回避されます。 

### なぜ効果があるのか

 不変条件は、すべてのインデックス i について、その格納された値が、最後に色が変更されてから現在の色に適用されたすべての加算操作の合計寄与度に等しいということです。 色の割り当てが発生するたびにその境界がリセットされるため、過去の貢献が二重にカウントされなくなります。 追加操作は色にのみ影響し、インデックスには直接影響しないため、すべての寄与は 1 回だけ考慮され、更新が失われたり 2 回適用されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class SegTree:
    def __init__(self, n):
        self.n = n
        self.color = [1] * (4 * n)
        self.lazy = [0] * (4 * n)
        self.is_uniform = [True] * (4 * n)

    def push(self, v):
        if self.lazy[v]:
            c = self.lazy[v]
            self.color[v*2] = c
            self.color[v*2+1] = c
            self.lazy[v*2] = c
            self.lazy[v*2+1] = c
            self.is_uniform[v*2] = True
            self.is_uniform[v*2+1] = True
            self.lazy[v] = 0

    def update(self, v, l, r, ql, qr, c):
        if ql <= l and r <= qr:
            self.color[v] = c
            self.lazy[v] = c
            self.is_uniform[v] = True
            return
        if r < ql or qr < l:
            return
        self.push(v)
        mid = (l + r) // 2
        self.update(v*2, l, mid, ql, qr, c)
        self.update(v*2+1, mid+1, r, ql, qr, c)
        if self.color[v*2] == self.color[v*2+1] and self.is_uniform[v*2] and self.is_uniform[v*2+1]:
            self.color[v] = self.color[v*2]
            self.is_uniform[v] = True
        else:
            self.is_uniform[v] = False

    def query(self, v, l, r, idx):
        if l == r:
            return self.color[v]
        self.push(v)
        mid = (l + r) // 2
        if idx <= mid:
            return self.query(v*2, l, mid, idx)
        else:
            return self.query(v*2+1, mid+1, r, idx)

def main():
    n, q = map(int, input().split())
    st = SegTree(n)
    add = [0] * (n + 5)

    out = []

    for _ in range(q):
        parts = input().split()
        if parts[0] == "Color":
            l, r, c = map(int, parts[1:])
            st.update(1, 1, n, l, r, c)
        elif parts[0] == "Add":
            c, x = int(parts[1]), int(parts[2])
            add[c] += x
        else:
            i = int(parts[1])
            c = st.query(1, 1, n, i)
            out.append(str(add[c]))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```セグメント ツリーは、範囲の割り当てに基づいて現在のカラーを追跡することのみを担当します。 値を保存することはありません。 値は構造ではなく色の履歴にのみ依存するため、この分離は不可欠です。 

add 配列は色ごとの累積増分を格納し、クエリは単にインデックスをその色にマップし、対応する累積合計を読み取ります。 

微妙な実装の詳細は、遅延伝播がカラーの上書きのみを処理することです。 ツリー内で数値をマージすることはありません。これにより、ツリーがクリーンに保たれ、二重カウントが回避されます。 

## 実用的な例

 サンプル入力をトレースします。 

初期状態では、すべての位置が色 1、値 0 で、add[1] = 0 です。 

[2,4] を 2 に色付けすると、インデックス 2 ～ 4 が色 2 になります。 

加算 2 2 の後、add[2] は 2 になります。 

クエリ 3 は色 2 をチェックするため、値は 2 になります。 

[4,5] を 3 に、[2,2] を 3 に色付けした後、該当する場合、位置 2、4、5 が色 3 になります。 

加算 3 3 の後、add[3] は 3 になります。 

クエリ 2 は色 3 を認識するため、出力は 3 になります。 

クエリ 5 もカラー 3 を認識し、出力は 3 になります。 

| 操作 | 追加[1] | 追加[2] | 追加[3] | 影響を受ける色 | クエリ結果 |
 | --- | --- | --- | --- | --- | --- |
 | 開始 | 0 | 0 | 0 | すべて 1 | - |
 | カラー 2-4 → 2 | 0 | 0 | 0 | 2-4=2 | - |
 | 2 2 を追加 | 0 | 2 | 0 | - | - |
 | クエリ 3 | 0 | 2 | 0 | - | 2 |
 | カラー 4-5 → 3 | 0 | 2 | 0 | 4-5=3 | - |
 | カラー2-2→3 | 0 | 2 | 0 | 2=3 | - |
 | 3 3 を追加 | 0 | 2 | 3 | - | - |
 | クエリ 2 | 0 | 2 | 3 | - | 3 |
 | クエリ 5 | 0 | 2 | 3 | - | 3 |

 このトレースは、インデックスを介して値を伝播する必要はなく、色のみを伝播する必要があることを示しています。

 ## 特殊なケース

 重大なエッジ ケースは、セグメントの色が繰り返し再設定される場合です。 たとえば、Color 1 n 2 に続いて Color 1 n 3 を繰り返し適用する場合、最後の割り当てのみが問題になります。 遅延割り当てにより以前の色の状態が上書きされるため、セグメント ツリーによってこれが保証されます。 

もう 1 つのケースは、再色付けする前に同じ色に対して Add が何度も呼び出される場合です。 追加配列は正しく蓄積され、クエリはリーフの色のみを解決するため、発生した追加操作の数に関係なく、値は一貫したままになります。 

最後のエッジケースは、明示的に色が変更されていない位置をクエリすることです。 これらは色 1 のままで、add[1] は 0 から始まり、他の色と同様に更新されるため、特別な処理をしなくても自然に正しい値が返されます。
