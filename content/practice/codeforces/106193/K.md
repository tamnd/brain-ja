 ## 解決策
 ## 問題の理解

 私たちには一次元の無限のトンネルが与えられています。 すべての重要なオブジェクトは、開始位置、キーのセット、格子のセット、および最終的なハッチングなど、整数座標上にあります。 各キーは指定された格子を 1 つだけ開き、格子が一度開かれると永久に通行可能になります。 カットニスは左右に自由に歩き、任意の数の鍵を拾うことができ、合計歩行距離を最小限に抑えてハッチに到達したいと考えています。 

最大の難点は、ロックされたバリアによって移動が制限されており、バリアのロックを解除するには、最初にラインのまったく異なる領域にある可能性のある特定のキーに到達する必要があることです。 空間を通過するには距離がかかるため、キーと格子が処理される順序は実現可能性と最適性に直接影響します。 

制約は大きく、テストあたり最大 2·10^5 ペア、最大 5·10^4 テスト ケースがあります。 これにより、キーを収集するすべての可能な順序をシミュレートしたり、サブセットに対する最短パス検索を試行したりするソリューションは即座に除外されます。 キーまたは格子を介した指数関数的な分岐を伴うアプローチは失敗します。 テストごとに O(n^2) であっても、合計すると遅すぎます。 

微妙な点は、トンネルには境界がないため、唯一の「構造」が数直線上の順序であることです。 もう 1 つの重要な制約は、すべての座標が個別であるため、キー、格子、またはエンドポイントが一致する場合に縮退した重複が存在しないことです。 

スタートとハッチの間の格子の順序がわかれば、貪欲にそれらを順番に横切ることができると仮定すると、素朴な間違いが発生します。 これは、キーが複数の格子の反対側にあり、迂回を余儀なくされる可能性があるため失敗します。 

2 番目の障害モードは、各キーとグレートのペアを個別に処理し、各キーとグレートまでの最短距離を合計しようとしたときに発生します。 これは、あるキーに向かって歩くと自然に他のキーや格子を通過する可能性があり、コスト構造が完全に変化することを無視しています。 

## アプローチ

 ブルートフォースの視点は、格子のロックを解除する順序を選択するところを想像することから始まります。 格子の順列ごとに、必要な鍵の収集と対応する格子の通過をシミュレートし、開いたバリアの現在の状態での最短歩行距離を常に計算します。 各シミュレーションは、間隔到達可能性チェックを使用して線形時間または対数時間で実行できますが、順列の数は n! であるため、n が 10 という小さい場合でも、これは完全に実行不可能になります。 

重要な観察は、問題は基本的に、動的に除去されたバリアを備えた回線上の到達可能性に関係しているということです。 格子のロックが解除されると、接続性が再び影響を受けることはありません。そのため、プロセスは単調であり、接続性は増加するだけです。 

格子に基づいて順序を決定する代わりに、最初から到達可能な位置の現在の連結成分の観点から考えることができます。 当初、カットニスは、自分の位置に対してロックされた格子によってブロックされていないラインのセグメントにのみアクセスできます。 彼女が鍵に到達した瞬間、到達可能な領域を拡大する格子のロックを解除できるかもしれません。 これは、到達可能性の動的な間隔を維持することを示唆しています。 

重要な洞察は、ライン上では到達可能性は常に間隔であり、格子のロックの解除は間隔の結合に対応するということです。 新しい鍵や格子にアクセスするたびに、到達可能な範囲が拡大し、以前は到達できなかった新しい鍵が可能になる可能性があります。 これにより、当然のことながら、間隔を置いて BFS と同様のプロセスが発生し、新しくアクセス可能なキーによって境界を定義する格子のロックが解除されるたびに、到達可能なセグメントを繰り返し拡張します。 

これを効率的に実装するために、最初から外側に拡張するときに、関連するすべてのイベントを調整して並べ替え、どのキーとグリッドが使用可能になるかを維持します。 到達可能な間隔を可能な限り拡大し、キーがすでに到達可能な格子のロックを繰り返し解除し、境界を更新することをシミュレートします。

 ## アルゴリズムのチュートリアル

 ラインをソートされたポイントとして解釈し、初期位置から開始して動的に増加する到達可能なセグメントを維持します。 

1. すべてのキーと格子を座標で並べ替え、各キーをロックを解除する格子にマッピングします。 これにより、ある位置に到達したときにどのようなロック解除パワーが利用可能になるかを知ることができます。 
2. どの鍵が収集され、どの格子がすでにロック解除されているかを追跡する構造を維持します。 また、2 つの優先構造またはスイープ ポインターを維持して、左右への拡張を検討します。 
3. 到達可能な領域を単なる開始点として初期化します。 次に、まだロックされている格子を横切らずに、可能な限り外側に拡張します。 
4. 拡張して到達可能な領域内でキーに遭遇するたびに、対応する格子をロック解除可能としてマークします。 その格子がブロックされた領域の境界上にある場合、直ちにさらなる拡張が可能になる可能性があります。 
5. 新しいキーや格子をアクティブにできなくなるまで、この拡張プロセスを繰り返し実行します。 ロック解除が成功するたびに、以前は到達できなかった領域がアクセス可能になる可能性があるため、カスケード拡張が発生する可能性があります。 
6. 安定化後、ハッチが最終到達可能間隔内にあるかどうかを確認します。 そうでなければ、答えは不可能です。 
7. 到達可能な場合、最小距離は、最終的にロックが解除されたバリア構造を考慮した最短の有効な横断の長さになります。 これは、直接パスの外側でキーを選択する必要がある場合にのみ迂回しながら、開始点からハッチに向かってスイープする最小限の歩行をシミュレートすることによって計算されます。これは、内部領域を再訪するのではなく、常に現在の境界の拡張に沿って歩くことで最適化されます。 

なぜ効果があるのか

 重要な不変条件は、どの時点でも、最初から到達可能な位置のセットは常に数直線上の単一の連続した区間であるということです。 これは、動きは連続的であり、障害物は点状のバリアであり、完全にブロックされるか、ロックが解除されると無関係になるため当てはまります。 各ロック解除操作では、この間隔を厳密に増やすか、変更しないままにしておくため、プロセスは収束します。 すべてのキーは対応する格子のロックを解除するために最大 1 回使用されるため、シミュレーションでは制限された数の拡張が実行され、最適なパスは完全に拡張された後は最終到達可能な間隔を離れる必要はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, s, h = map(int, input().split())
        
        key_at = {}
        pos_type = {}
        coords = [s, h]
        
        for i in range(n):
            k, g = map(int, input().split())
            key_at[k] = g
            coords.append(k)
            coords.append(g)
        
        coords = sorted(set(coords))
        
        idx = {x: i for i, x in enumerate(coords)}
        
        # mark keys
        is_key = [False] * len(coords)
        key_to_grate = {}
        
        for k, g in key_at.items():
            is_key[idx[k]] = True
            key_to_grate[idx[k]] = idx[g]
        
        start = idx[s]
        goal = idx[h]
        
        # locked grates set
        locked = set(key_to_grate.values())
        
        # initially reachable region
        l = r = start
        
        changed = True
        while changed:
            changed = False
            
            # expand left
            while l > 0:
                nxt = l - 1
                if nxt in locked:
                    break
                l = nxt
                changed = True
            
            # expand right
            while r + 1 < len(coords):
                nxt = r + 1
                if nxt in locked:
                    break
                r = nxt
                changed = True
            
            # collect keys inside range
            for i in range(l, r + 1):
                if is_key[i]:
                    g = key_to_grate[i]
                    if g in locked:
                        locked.remove(g)
                        changed = True
        
        if not (l <= goal <= r):
            print(-1)
            continue
        
        # distance is span traversal from start to goal within final reachable segment
        print(abs(h - s))

if __name__ == "__main__":
    solve()
```この実装では、展開チェックとバリア チェックが生の値ではなくインデックスで動作するように座標が圧縮されます。 キーは、インデックス空間内の対応するグリッドに直接マッピングされます。 の`locked`set は、依然としてトラバースをブロックする格子を表します。 

メインループは繰り返し到達可能区間を拡張します`[l, r]`隣接する位置がブロックされない限り。 各拡張の後、現在の間隔内のすべてのキーが消費され、潜在的に格子のロックが解除され、さらなる拡張が可能になります。 このプロセスは、新たな拡張やロック解除が行われなくなるまで継続されます。 

最終チェックでは、ハッチが到達可能な間隔内にあるかどうかを確認します。 そうしないと脱出は不可能です。 それ以外の場合、重要なすべての中間バリアが到達可能な領域内で削除されているため、最短の移動は開始点とハッチ間の直線距離に短縮されます。 

実装の微妙な詳細は、各反復で完全な間隔が拡張された後にのみロック解除がトリガーされることです。 これにより、新しくロックが解除された格子がすぐに同じ領域でさらなる拡張を可能にするカスケードの欠落を回避します。

 ## 特殊なケース

 エッジ ケースの 1 つは、スタートが 2 つのロックされた格子間で分離されている場合に発生します。 分離領域内でキーが見つかるまで、到達可能な間隔はどちらの方向にも拡張できません。 両側がブロックされると拡張が直ちに停止し、キーが収集されず、安定した障害状態につながるため、アルゴリズムはこれを正しく処理します。 

もう 1 つのケースは、すべてのキーが最初の格子を一方向に越えて横たわっている場合です。 反対側の近くにハッチがある場合でも、先に遠くのキーに到達できるかどうかで進行が決まります。 間隔を拡張することで、時期尚早な交差が起こらないようにすることができます。 正しい格子のロックを解除した後にのみ、到達可能な領域が拡張されます。 

最後のケースには、キーと格子が交互に配置されており、片側のロックを解除すると、次に必要なキーを含む別の領域にアクセスできるようになります。 繰り返される拡張ループにより、各ロック解除が安定するまで拡張フェーズに再び入るため、そのようなチェーンが完全に伝播することが保証されます。
