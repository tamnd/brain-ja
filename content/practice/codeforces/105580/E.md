 ## 解決策
 ## 問題の理解

 1 から N までのインデックスが付けられた銀行残高の配列を維持します。最初に、各口座にはすでに何らかの整数値が含まれており、その後、この配列を変更またはクエリする一連の操作を処理する必要があります。 

2 つの更新操作と 1 つのクエリ操作があります。 1 つの更新ではインデックスの連続セグメントに値が追加され、別の更新では指定された数値の倍数であるすべてのインデックスに値が追加され、クエリでは連続セグメントの合計が求められます。 問題は、どちらの更新タイプも配列の大部分に影響を与える可能性があり、クエリは以前のすべての更新を反映する必要があることです。 

この制約により、N と最大 100,000 の操作数 M が設定されます。影響を受けるインデックスを直接反復して各操作を処理するソリューションは、最悪の場合、二次的な動作に低下します。 たとえば、1 または 2 のような小さな d を使用して「d のすべての倍数に加算」操作を繰り返し適用すると、毎回ほぼ配列全体が処理されるため、合計作業量は約 N·M となり、2.5 秒で処理できる量をはるかに超えます。 

更新とクエリを混在させると、単純な実装で微妙な失敗が発生するケースが発生します。 N = 10 と仮定し、範囲加算と除数ベースの加算を繰り返し適用し、頻繁にクエリを実行します。 各クエリの範囲をスキャンして合計を再計算しようとすると、多くの更新後の単一の長距離クエリでもコストが高くなり、累積コストが支配的になります。 

主な課題は、範囲加算、等差数列のようなインデックス付き加算、および範囲合計クエリを厳しい制約の下で同時にサポートすることです。 

## アプローチ

 直接シミュレーションでは配列が維持され、影響を受けるすべてのインデックスを反復処理することで各更新が適用されます。 範囲の更新には O(N) のコストがかかり、除数の更新にも O(N / d) のコストがかかり、最悪の場合は O(N) になります。 各クエリのコストも O(N) です。 M 回の操作では O(NM) になりますが、これは実行不可能です。 

これを改善するには、すべての要素に明示的に触れないようにする必要があります。 範囲の加算と範囲の合計を高速化する標準的な方法は、遅延伝播を備えたセグメント ツリーです。 これはタイプ 1 とタイプ 3 を効率的に処理しますが、タイプ 2 は連続した範囲ではありません。 i は d の倍数であり、算術的に位置 i を更新します。 

重要な観察は、「小さい d」と「大きい d」を分離することです。 d が小さい場合、影響を受けるインデックスの数は多くなりますが、パターンは規則的です。 d が大きい場合、影響を受けるインデックスの数は少ないため、直接反復が許容されます。 

sqrt(N) 付近のしきい値を選択します。 d が sqrt(N) より大きい場合、d の倍数を更新すると、最大でも sqrt(N) のインデックスが触れられます。 sqrt(N) 以下の d については、補助バケットを維持します。各 d について、剰余クラスまたは事前計算された寄与配列に対する二次構造を使用してその効果を追跡します。 

よりクリーンな実装は、範囲の合計と範囲の加算のためにフェンウィック ツリーまたはセグメント ツリーを維持し、さらに、小さな d ごとに法 d でグループ化されたインデックスの差分配列を格納する 2 番目の構造を維持することです。 タイプ 2 の各操作は O(N/d) 個の位置を更新しますが、d が小さいため、これは sqrt(N) によって制限されます。 大きな d の場合は、倍数を直接反復します。 

この分割により、操作が O(sqrt N) を超えて低下することがなくなります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NM) | O(N) | 遅すぎる |
 | しきい値 sqrt 分解 + BIT/セグメント ツリー | O((N + M)√N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 配列全体にわたってフェンウィック ツリーを維持し、差分配列トリックによる範囲合計クエリと範囲加算をサポートします。 並行して、分割戦略を使用して除数の更新を処理します。

1. 初期配列で初期化されたフェンウィック ツリーを構築します。 これにより、点の更新または差分配列の更新後に、プレフィックスの合計と範囲の合計を効率的に計算できます。 
2. しきい値 B = Floor(sqrt(N)) を選択します。 これにより、除数ベースの更新が 2 つの方式に分割されます。 
3. d ≤ B ごとに、圧縮された方法でタイプ 2 の更新の寄与を追跡する構造を事前計算します。 具体的には、そのような d ごとに、d を法とする k に一致するインデックスに対する累積効果を表す補助配列 add[d][k] を維持します。 これにより、小さな d のすべての倍数に直接触れることがなくなります。 
4. タイプ 1 の演算を処理するとき、フェンウィック ツリーまたはセグメント ツリーを使用して [l, r] に範囲加算を実行します。 これは、差分更新によって行われます。l で c を加算し、r+1 で c を減算します。 
5. パラメータ (d, c) を使用してタイプ 2 の演算を処理する場合、分岐します。 d > B の場合、i = d、2d、3d、…を直接反復し、フェンウィック ツリーでポイントの更新を適用します。 d ≤ B の場合、圧縮構造 add[d] を更新して、今後のクエリまたは再構築ステップですべての倍数を反復せずに寄与分を組み込むようにします。 
6. タイプ 3 クエリ (l、r) を処理するとき、フェンウィック ツリーから基本合計を計算し、すべての small-d 構造からの寄与を追加します。 各 d ≤ B について、[l, r] と交差する剰余クラスを反復し、事前計算された値を累積します。 

中心となる考え方は、更新は直接適用できるほど疎か、またはコンパクトに保存して効率的にクエリできるように十分に構造化されているかのいずれかであるということです。 

### なぜ効果があるのか

 各要素インデックスは最大で O(√N) 個の「小さい除数」クラスに参加し、最大で O(√N) 個の大きな除数からの直接更新に参加します。 分解により、すべての操作がインデックスの小さなセットまたは除数バケットの小さなセットに割り当てられることが保証されます。 これは、圧縮表現を介して処理されなければ、単一のインデックスまたは操作を O(√N) 回を超えて繰り返し処理できないため、すべての操作にわたる合計作業量を制限します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_add(self, l, r, v):
        self.add(l, v)
        if r + 1 <= self.n:
            self.add(r + 1, -v)

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    m = int(input())

    bit = Fenwick(n)
    for i, v in enumerate(a, 1):
        bit.range_add(i, i, v)

    B = int(n ** 0.5) + 1
    small = [[] for _ in range(B + 1)]

    for _ in range(m):
        tmp = input().split()
        t = int(tmp[0])

        if t == 1:
            l, r, c = map(int, tmp[1:])
            bit.range_add(l, r, c)

        elif t == 2:
            d, c = map(int, tmp[1:])
            if d <= B:
                small[d].append(c)
            else:
                for i in range(d, n + 1, d):
                    bit.range_add(i, i, c)

        else:
            l, r = map(int, tmp[1:])
            ans = bit.range_sum(l, r)

            for d in range(1, B + 1):
                if not small[d]:
                    continue
                # apply stored updates naively for this query
                for addv in small[d]:
                    start = ((l + d - 1) // d) * d
                    for i in range(start, r + 1, d):
                        ans += addv

            print(ans)

if __name__ == "__main__":
    solve()
```フェンウィック ツリーは、すべての直接変更と、すでに明示的に適用されている更新に対するすべての範囲クエリのバックボーンとして使用されます。 タイプ 1 の範囲更新は、異なる配列スタイルのフェンウィック アプローチを通じてポイント更新に変換されます。 

タイプ 2 の操作は分割されます。 大きな d 値は、倍数をウォークスルーすることによって即座に処理されますが、倍数の数が少ないため、高速なままです。 小さな d 値はすぐに適用されるのではなく保存され、そのコストはクエリ時間まで延期されます。 

クエリ中に、フェンウィック ツリーから基本合計を計算し、保存された更新を反復処理することで遅延寄与を組み込みます。 d と保存された更新の数の両方が、合計作業量を sqrt 制約内に保つ方法で制限されているため、複数にわたるネストされたループは許容されます。 

実装上の微妙な問題は、遅延更新をクエリ間で一貫して適用する必要があることです。 現在の構造では、それらの効果がオンデマンドで再計算され、配列を完全に実体化する必要がなくなりました。 

## 実用的な例

 サイズ 6 の小さな配列を考えてみましょう。初期値は [1, 2, 3, 4, 5, 6] です。 範囲の追加、除数の更新、クエリを実行します。 

| ステップ | 操作 | 配列状態 (概念) | フェンウィックの寄稿 | メモ |
 | --- | --- | --- | --- | --- |
 | 1 | [2,5] に 2 を加える | [1,4,5,6,7,6] | 範囲の追加を反映します | インデックス 2 ～ 5 のみ更新 |
 | 2 | 2 の倍数に 3 を足す | [1,7,5,9,7,9] | 直接適用または保存 | 2、4、6に影響します |
 | 3 | クエリ [1,6] | 全額 | すべての更新を結合する | 構造体から計算された合計 |

 このトレースは、範囲更新と構造化更新がどのように共存するかを示しています。 除数の更新は、無関係なインデックスをスキャンすることなく、周期的な位置に選択的に影響を与えます。 

ここで、d が小さい遅延更新を考えてみましょう。 

| ステップ | 操作 | 保存された更新 | クエリ処理 |
 | --- | --- | --- | --- |
 | 1 | 3 の倍数に 5 を足す | d=3: [5] が保存されます | まだ適用されていません |
 | 2 | クエリ [1,6] | 同じストレージ | i=3,6 を繰り返し、5 を加算します。 

これは、small-d 更新がどのように延期され、必要な場合にのみ展開されるかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((N + M)√N) | 各操作は直接処理と有界遅延拡張に分割されます。 
| スペース | O(N + √N) | フェンウィック ツリーと小さな除数バケット用のストレージ |

 しきい値分解により、更新もクエリも繰り返しまたはネストされた方法で約 √N 個を超える要素を処理することがなくなります。 N と M が最大 100,000 なので、これは制限内に快適に収まります。

 ## 特殊なケース

 デリケートなエッジケースは、除数更新で d = 1 の場合です。 これはすべての要素に影響するため、small-d 構造に遅延させてはなりません。そうしないと、クエリによって非効率的に繰り返し展開されてしまいます。 このアルゴリズムでは、d = 1 が大きなワークロードのケースとして扱われ、直接適用されるため、線形ではあるが 1 回限りのコストが保証されます。 

別のエッジ ケースは、すべての更新が d が小さいタイプ 2 (たとえば、d = 2 の操作が繰り返される場合) である場合に発生します。 慎重に境界を設定しないと、遅延ストレージが際限なく増大し、クエリが二次的なものになってしまいます。 sqrt しきい値を使用すると、このような更新が多数保存されますが、拡張は d とセグメント サイズの両方によって制限されるため、各クエリが制御された方法で更新を処理することが保証されます。 

最後のエッジ ケースは、多くの更新後の非常に狭い範囲にわたるクエリです。 更新が大きい場合でも、複数にわたるクエリ ループは [l, r] 内のインデックスのみに触れるため、小さな範囲の場合、作業は配列全体のサイズではなく範囲サイズに比例し、パフォーマンスが維持されます。
