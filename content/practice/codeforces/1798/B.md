 ## 解決策
 ## 問題の理解

 私たちには一連の日数が与えられています。 毎日、何人かのグループが抽選に参加し、そのうちの 1 人がその日の勝者として選ばれます。 重要な制限は、その日に誰かが勝った場合、`i`、後日出現することは禁止されています。`i+1`を通して`m`。 

課題は、固有の履歴を再構築することではなく、参加リストを説明できる、またはそのような割り当てが存在しないことを判断できる、毎日の勝者の有効なシーケンスを構築することです。 

より具体的に言い換えると、毎日、利用可能な候補者のセットが提供されます。 各セットから順番に 1 つの要素を選択する必要がありますが、要素が一度選択されると、それ以降のセットには表示されなくなります。 難しいのは、早期の選択が後の実現可能性を制約するため、貪欲な選択は将来の可用性を考慮する必要があることです。 

制約は厳しく、全日の参加者数の合計は最大 50,000 人で、テスト ケースは最大 50,000 件まで可能です。 これにより、1 日あたりの二次比較またはペアごとの比較戦略が即座に除外されます。 どのソリューションでも、通常は数日間スキャンして小さな補助構造を更新することにより、各参加者を一定回数処理する必要があります。 

貪欲なアプローチにより参加者が選ばれ、その参加者が後で再び現れることが判明した場合、微妙な失敗例が発生します。 たとえば、1 日目に 3 日目にも出演する人を選択した場合、2 日目に代替案があったとしても、その選択は実現可能性を無効にします。 もう 1 つの注意が必要な状況は、その日の唯一の有効な候補がすでに以前に使用されており、以前の貪欲な手順が局所的には正しいように見えても、構築が不可能になる場合です。 

中心的な課題は、当日の勝者を選択する際に、`i`、今後それらが表示されないことを保証します。 私たちは将来の参加リストをすべて知っているので、これはローカルな制約ではなくグローバルな制約になります。 

## アプローチ

 単純な戦略では、毎日考えられるすべての選択肢を再帰的に試し、選択した勝者が後で現れるたびにバックトラックします。 最悪の場合、毎日多くの候補が存在する可能性があり、前処理しない限り、将来の日に候補が表示されるかどうかを確認するには直線的な時間がかかります。 前処理を行ったとしても、すべての組み合わせを探索すると指数関数的な分岐が発生します。 最大 50,000 日なので、これは完全に不可能です。 

重要な点は、すべての候補者を考慮する必要はないということです。 候補者が当日有効であるためには`i`、それらは日に現れる必要があります`i`そして後日現れてはなりません。 つまり、すべての日にわたって、すべての人の最後の出現を事前計算できるということです。 各人が最後に出現した日がわかれば、問題は毎日、最後に出現した日が当日またはそれ以前である参加者を選択することになりますが、より正確には、今安全に割り当てたい場合は、最後の出現が正確にその日である参加者が必要です。 

欲張りなアイデアは、正確さを保証する方法で、最後の日から最初の日まで処理することです。 勝者を逆方向に割り当てる場合、その日を迎えた時点で、以降のすべての決定はすでに修正されており、最後に出現したのが当日かそれ以前で、構築されたサフィックスでまだ使用されていない参加者を選択するだけで済みます。 

ただし、より単純で標準的な解決策が登場します。つまり、最後に出現する日が当日と一致するかそれを超える一連の利用可能な候補を維持しながら、最後の日から最初の日まで処理し、将来の制約に決して違反しないように貪欲に選択します。 より直接的で一般的な CF ソリューションは、「最終出現」配列を使用し、可能な最後の日に人を割り当てることが安全な場合にのみ選択肢を構築します。 

これにより、問題は何日にもわたる貪欲な割り当てに変わり、各人は最終登場時またはその前に 1 回だけ割り当てられなければならず、競合は常に最も早い安全なスロットを消費することで解決されます。

 | 最適 (最後の出現 + 貪欲な割り当て) | O(合計 n) | O(最大値) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、すべての参加者の値について、参加者が最後に出現した日を計算します。 これは、「i 日目にこの人を選択した場合、後で登場することはできないため、i 日がシーケンスの最後の日でなければならない」という制約をエンコードするため、重要な前処理ステップです。 

次に、逆の順序で日をスキャンし、最後の日から最初の日まで答えを構築します。 私たちは、当日どの候補者が空いているか、安全に割り当てられるかどうかを把握できる体制を維持しています。 

1. すべての参加リストをスキャンして、各値の最後の発生日を計算します。 

これにより、各人を選択した場合、それまでに各人を割り当てなければならない最終期限がわかります。 
2. 毎日どの参加者が参加するかを追跡する構造 (通常はリストの配列) を作成します。 
3. からの日数を横断する`m`まで`1`、その日に現れる候補者のセットまたは優先順位の構造を維持する`i`。 

現時点では、将来のすべての制約がすでに解決されているサフィックスの割り当てを決定しています。 
4. その日のために`i`、その日にリストされているすべての参加者を検討し、候補者のプールに追加します。 

参加者は、最後の出現が正確に一致する場合にのみ資格があります。`i`、つまり、これが最後の割り当て可能日であることを意味します。 
5. その日そのような候補者が存在しない場合`i`の場合、有効な割り当ては不可能なので、失敗して終了します。 

これは、毎日少なくとも 1 人の利用可能性がそこで終了する人を消費する必要があるという事実を反映しています。 
6. それ以外の場合は、有効な候補を選択します (最後の出現が等しい場合はすべてが安全であるため、どれでも構いません)`i`) そして彼らをその日の勝者として割り当てます`i`。 
7. その候補を使用済みとしてマークし、以前の状態に進みます。 

この構造により、選択された各勝者は最終的な出現時に正確に削除されるため、以前の割り当てと競合することはありません。 

### なぜ効果があるのか

 不変条件は、日を処理するときです。`i`、一日中`i+1 ... m`すでに勝者が割り当てられており、今後処理する予定の日にはそれらの勝者が再び表示されることはありません。 したがって、最後の出現が正確に一致する候補はすべて、`i`今それらを選択することで違反する可能性のある将来の制約がないため、安全に割り当てることができます。 逆に、そのような候補が 1 日存在しない場合は、その日の参加者全員が後でどこかに現れることになり、どの選択も「勝利後は再出現しない」ルールに違反することになり、構築は不可能になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        m = int(input())
        days = []
        last = {}
        
        for i in range(m):
            n = int(input())
            arr = list(map(int, input().split()))
            days.append(arr)
            for x in arr:
                last[x] = i
        
        ans = [-1] * m
        used = set()
        
        ok = True
        
        for i in range(m - 1, -1, -1):
            pick = -1
            for x in days[i]:
                if last[x] == i and x not in used:
                    pick = x
                    break
            
            if pick == -1:
                ok = False
                break
            
            ans[i] = pick
            used.add(pick)
        
        if not ok:
            print(-1)
        else:
            print(*ans)

if __name__ == "__main__":
    solve()
```解決策は、一日中読んで、`last`各数字が出現する最終日を記録した辞典。 これは、グローバルな制約を 1 日あたりのローカルな条件に変換するため、不可欠です。 

次に、何日も遡って繰り返します。 毎日、参加者リストをスキャンして、その日が最後に出現し、まだ使用されていない人を見つけようとします。 このような人は、以前に処理されたサフィックスには表示されないため、その日の勝者として安全に割り当てることができます。 

の`used`set により、同じ人が 2 回割り当てられることがなくなります。 各勝者は割り当てに関して一意である必要があるため、これにより、日をまたいで再利用することができなくなります。 

有効な候補者が 1 日も存在しない場合、直ちに不可能と判断します。

 毎日少なくとも 1 人の参加者がいて、その最終的な外観が処理される日と一致するため、構築は成功します。 

これは、割り当てられたすべての勝者が最後に出現した時点で正確に消費されるという不変条件を裏付けます。 

### 例 2

 入力:```
2
1 2
2 1
```最後に発生した出来事:

 | 値 | 最終日 |
 | --- | --- |
 | 1 | 1 |
 | 2 | 0 |

 処理 1 日目:

 候補は [1, 2] のみですが、last[x] == 1 を満たすのは 1 つだけです。1 を選択します。 

処理 2 日目:

 候補 [2, 1] ですが、1 はすでに使用されており、2 の最後の出現は 0 であるため、有効な選択は存在しません。 

このプロセスは失敗し、将来の日数が再利用された参加者に依存する場合、初期の構造が行き詰まりを強いられる可能性があることを示しています。

 ## 特殊なケース

 重大なエッジ ケースは、すべての参加者が今後数日にわたって現れる場合です。 このシナリオでは、最後の出現が固有の日の境界に一致しないため、以前の日に割り当てられる資格のある人は誰もいません。 アルゴリズムは正しく失敗します。`i`、 いいえ`x`満足する`last[x] == i`。 

もう 1 つのエッジ ケースは、毎日の参加者が 1 人だけである場合です。 このアルゴリズムが成功するか失敗するかは、これらの参加者が最後に出現したものの重複しないシーケンスを形成しているかどうかに基づいて決まります。 毎日 1 つの候補のみが提供されるため、チェックは最後の出現位置の一貫性を検証することになります。 

3 番目のケースは、多くの参加者が連続して参加する重度の重複です。 逆方向スキャンにより、常に可用性の境界で割り当てが行われるため、時期尚早な消費が防止されます。 値が何日も前に出現したとしても、その値は 1 回だけ、つまり最後の出現時に割り当てられるだけで、シーケンス全体にわたって正確さが維持されます。
