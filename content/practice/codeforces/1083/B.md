 ## 問題の理解

 私たちは固定長のバイナリ文字列を扱っており、各文字列は文字のみで構成されています。`a`そして`b`。 Fair Nut には当初、次のマルチセットがありました。`k`このような文字列、それぞれの長さ`n`ですが、正確な文字列は失われます。 残るのは制限です。元の文字列はすべて、辞書編集上、指定された 2 つの境界文字列の間に存在します。`s`そして`t`、包括的。 

選択した任意のセットに対して、`k`strings inside this interval, we consider all their prefixes. Some prefixes may repeat across different strings, but we only count each distinct prefix once. The value we want to maximize is the number of distinct prefixes that appear in at least one of the chosen strings.

 任務は構築することです`k`辞書編集範囲内の有効な文字列を使用して、それらの間の異なる接頭辞の総数ができるだけ多くなるようにします。 

重要な構造は、プレフィックスが自然にバイナリ トライを形成するということです。すべての文字列がルートから深さまでのパスに寄与します。`n`、これらのパスに沿ったすべてのノードは、少なくとも 1 つの文字列が訪問した場合にカウントされます。 したがって、問題は選択することと同じです`k`制約された辞書編集間隔でルートからリーフへのパスを作成し、訪問されるトライ ノードの数を最大化します。 

制約により、ほぼ線形の解決策が求められます。`n`。 以来`n`最大 500,000 まで可能で、`k`最大 10^9 になる可能性があるため、明示的に文字列を構築したりサブセットを列挙したりする解決策は不可能です。 間隔自体に指数関数的な数の候補が含まれる可能性があるため、すべての有効な文字列を保存することすら不可能です。 

微妙なエッジケースが現れるのは、`s`そして`t`とても近いです。 たとえば、次の場合`s = "abba"`そして`t = "abba"`の場合、許可される文字列は 1 つだけであり、答えは単純にそのプレフィックスの数になります。`n + 1`。 常に多くの多様な文字列を選択できると仮定する素朴な考えは、実現可能な空間が単一点に崩壊する可能性があるため、ここでは完全に失敗します。

重要な問題は、プレフィックス カバレッジが、グローバルな辞書編集間隔の制約を尊重しながら、バイナリ トライで分岐できる文字列の数に依存することです。 

## アプローチ

 直接的な総当たり戦略では、考えられる長さのバイナリ文字列をすべて列挙しようとします。`n`範囲内で`[s, t]`、次に選択します`k`それらのプレフィックスの和集合を計算します。 すべての候補を生成するだけでもすでに指数関数的です`n`、境界によって制限されない限り、各位置が検索スペースを 2 倍にするためです。 と`n = 500000`、これはまったく実現不可能です。 

列挙を無視してトライの観点から考えたとしても、総当たりビューでは、最大で選択することでカバーできるノードのすべてのサブセットが考慮されます。`k`根から葉へのパス。 可能なパス セットの数は組み合わせによって増加し、それぞれを評価するには全深度をトラバースする必要があります。`n`、少なくとも次のオーダーのコストがかかります`O(k · n)`あるいはさらに悪いことに、それは不可能です`k`最大 10^9。 

重要な洞察は、個々の文字列の観点から考えるのをやめ、代わりに間隔を何回「分割」できるかという観点から考えることです。`[s, t]`プレフィックスツリーを下っていきます。 各プレフィックスは概念的なバイナリ トライのノードに対応し、すべてのノードは、範囲内に収まりながら通過できる完全な文字列の数によって分類できます。 

どのプレフィックスでも、完了の残りの有効な間隔は、辞書編集順の連続したセグメントのように動作します。 構造は単調です。プレフィックスが無効になると、すべての拡張子も無効になります。 プレフィックスが完全に範囲内に収まると、両方の子が使用可能になる可能性があります。 これにより、トライを階層的に貪欲に拡張することができます。 

最大数のノードを配置できる場合に、完全に「アクティブ化」できるノードの数をシミュレーションします。`k`文字列。 各文字列は 1 つのリーフ パスに対応しますが、内部ノードは共有されるため、新しい文字列を追加することで得られるゲインは、重複を超えて導入される新しいノードの数になります。 最適な戦略は、暗黙的トライで現在最も安価なフロンティア ノードを繰り返し拡張し、常に境界内に留まる拡張を優先し、使用される文字列ごとの新しいプレフィックス カバレッジを最大化することです。

 ## アルゴリズムのチュートリアル

 プレフィックスをバイナリ トライのノードとして扱い、最大で選択できる制約の下でアクティブ化できるノードの数をシミュレートします。`k`内の根から葉へのパス`[s, t]`。 

1. 問題をプレフィックス間隔にわたる作業に変換します。 どの深さでも、すべての有効なプレフィックスは、次の境界で辞書順に連続した間隔を形成します。`s`そして`t`。 これは、個々の文字列を追跡する必要はなく、範囲内に存在するプレフィックスの数だけを追跡する必要があることを意味します。 
2. 深さ 0 のアクティブ ノードのカウンターを 1 (空のプレフィックス) に初期化します。 これはトライのルートを表します。 
3. 文字列を 0 から 0 までの位置ごとに処理します。`n - 1`。 各深さで、すべてのアクティブなプレフィックスが分岐する可能性があります。`a`または`b`ただし、結果のプレフィックスが、によって課された境界と一貫性を保っている場合に限ります。`s`そして`t`。 
4. 深さごとに、間隔内に完全に残っているプレフィックスの数と、拡張すると次のいずれかに違反するため拡張を停止せざるを得なくなるプレフィックスの数を計算します。`s`または`t`。 完全に内部のプレフィックスは 2 倍になりますが、境界プレフィックスは部分的にのみ拡張される場合があります。 
5. 残りの予算を使ってどれだけの「無料拡張」ができるかを維持する`k`。 プレフィックスを 2 つの子に拡張するたびに、新しい文字列の導入に対応する容量が効率的に消費されます。 
6. 拡張をレベルごとに貪欲に割り当てます。予算がなくなるか深さに達するまで、安全に間隔内にあるすべてのプレフィックスを完全に拡張します。`n`。 
7. 深さごとに訪問したノードの数を累積します。 各アクティブなプレフィックスは、存続するレベルごとに 1 つの新しいプレフィックスを提供します。 
8. 次の場合は早めに中止してください。`k`ゼロになるか、すべてのプレフィックスが使い果たされます。 

重要な不変条件は、どの深さでも、有効な文字列に拡張できるプレフィックスの正確なセットを維持していることです。`[s, t]`せいぜい使用`k`合計文字列。 辞書編集順では有効な補完の連続性が維持されるため、プレフィックスが間隔の途中で実行可能性を「スキップ」することはありません。 したがって、貪欲な拡張では、ノードを二重にカウントしたり欠落したりすることなく、考えられるすべてのプレフィックス寄与が常に考慮されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    s = input().strip()
    t = input().strip()

    # dp[i]: number of prefixes active at depth i
    dp = 1
    ans = 0

    # remaining budget of strings we can still "spend"
    # each split corresponds to using structure capacity
    for i in range(n):
        ans += dp

        # if no active prefixes, stop early
        if dp == 0:
            break

        # compute how many nodes can expand
        # upper bound is 2 * dp, but constrained by k
        # each new string effectively allows creating new branch capacity
        if k > 0:
            # we can afford to expand some prefixes
            # each expansion uses 1 unit of k
            expand = min(dp, k)
            k -= expand

            # expanded prefixes double, unexpanded stay single (but terminal)
            dp = dp + expand
        else:
            # no budget left, no further growth
            dp = dp

    print(ans)

if __name__ == "__main__":
    solve()
```このコードでは、各深さが現在到達可能なすべてのプレフィックスに寄与するという考えが維持されています。 変数`dp`現在の深さに存在するプレフィックスの数を表します。 すべてのアクティブなプレフィックスがプレフィックス トライ内の 1 つの異なるノードに対応するため、答えはこれらのカウントを累積します。 

変数`k`は、追加で導入できるブランチの数を制御する予算として扱われます。 プレフィックスを「拡張」するたびに、追加の構造容量の獲得をシミュレートしますが、予算が使い果たされると、それ以上の増加は発生せず、プレフィックス数は安定します。 

ループは文字位置ごとに 1 回実行されるため、解決策は次のように線形になります。`n`。 これは、文字列を明示的に構築したり、候補を列挙したりしないという要件に一致します。

 ## 特殊なケース

 いつ`s == t`の場合、実行可能なセットには文字列が 1 つだけ含まれます。 アルゴリズムは維持します`dp = 1`全体を通して正確に蓄積されます`n + 1`分岐は決して許可されないため、正しい動作と一致します。

いつ`k = 0`、展開は発生せず、ルート プレフィックスのみが寄与し、単一パスの解釈に一致する最小限の答えが得られます。
