 ## 解決策
 ## 問題の理解

 バイナリ文字列、つまり次のものだけで構成されるシーケンスから始めます。`0`そして`1`。 2 種類のローカル編集操作が許可されており、各操作では 2 つの隣接する位置の間に 1 つの余分な文字が挿入されます。 

最初の操作は、等しい隣接ペアのペアでのみ使用できます。 見たら`00`を挿入することができます。`1`彼らの間で、そして私たちが見れば`11`を挿入できます。`0`。 この操作は「均一な」境界があることに依存しており、常に反対の文字を導入して、新しい代替点を作成します。 

2 番目の操作はより寛容です。 見たら`01`または`10`、どちらかを挿入してもよい`0`または`1`それらの間にあるため、挿入された文字は制約されません。 

正確に実行することが求められます`a`最初のタイプの操作と`b`2 番目のタイプの操作は、適用可能な任意の順序および位置で実行できます。 その後、位置と挿入ビットの選択に応じて、さまざまな最終文字列が生成される可能性があります。 タスクは、得られる個別の最終文字列の数を数えることです (剰余)`10^9 + 7`。 ある時点で、必要な数の操作を実行できなくなった場合、答えはゼロになります。 

入力サイズは最大 100 万に達するため、挿入や動的な文字列構築のシミュレーションは直ちに除外されます。 各操作では文字列の長さが変化するため、単純な分岐は指数関数的に爆発的に増加します。 どのソリューションも、圧縮された構造情報を使用してのみ機能する必要があり、ほぼ確実に、明示的な文字列ではなく実行または隣接構造に基づいています。 

微妙な失敗例は、操作が常に独立して適用できると想定していることから発生します。 たとえば、から始めて、`00`最初の操作を適用すると、次の結果が得られます。`010`。 その後、オリジナルの`00`隣接関係が失われるため、別の第 1 タイプの操作を同じ場所に適用することはできません。 これは、実現可能性は初期の数だけではなく、進化する構造に依存することを意味します。 

もう 1 つのエッジ ケースは、次のように文字列が交互になる場合です。`0101`。 ここでは、最初は等しい隣接ペアが存在しないため、2 番目のタイプの挿入によって間接的に新しい等しい隣接関係が作成されない限り、1 番目のタイプの操作をゼロにすることは不可能です。 操作を独立したものとして扱う単純なカウントでは、誤って許可されてしまいます。`a > 0`そのような場合に。 

## アプローチ

 ブルートフォース解釈では、プロセスを状態グラフとして扱います。 各状態はバイナリ文字列であり、各エッジは許可された位置の 1 つに文字を挿入することに対応します。 考えられるすべてのシーケンスを再帰的に試します。`a + b`操作を実行し、結果の文字列をセットに収集します。 これは、定義された遷移システムを正確に調査するため、概念的には正しいです。 

ただし分岐要素は大きい。 それぞれの操作は多くの局面で適用でき、適用ごとに今後利用できる手が変わります。 州の数は指数関数的に増加します`n + a + b`、最悪の場合、最大 200 万操作になります。 たとえ小さな例であっても実行不可能です。 

重要な観察点は、このプロセスは実際には正確な文字列ジオメトリには依存せず、隣接タイプ (等しいペアと不等なペア) のみに依存するということです。 挿入はローカル隣接構造にのみ影響し、唯一意味のあるグローバル状態情報は、各タイプの位置がいくつ存在するか、およびそれらがどのように変化するかということです。 

さらに単純化すると、文字列内の「ブロック」の数を追跡することができます。ここで、ブロックとは、同一文字の最大の連続です。 すべての文字列は、そのブロック構造によって完全に記述されます。 最初の操作ではブロックを分割し、ブロック数を 1 つ増やします。 2 番目の操作は境界を調整しますが、基本的に独立した方法でブロック数を変更しません。戦略的に配置された場合にのみ新しいブロックを作成できますが、その組み合わせ効果は境界をまたがって対称的です。 

これにより、問題は、作成される新しい境界の数を追跡しながら、進化する境界上で操作を分散できる方法が何通りあるかを数えることに減ります。 最終的なカウントは、各操作タイプが導入する有効な「選択肢」の数にのみ依存します。これは、動的に増加するポジションに関する組み合わせカウントの問題になります。

 ## アルゴリズムのチュートリアル

 実行の観点からプロセスを再定式化します。 初期文字列を等しい文字の最大ブロックに分解します。 させて`k`そのようなブロックの数になります。 

重要な構造上の事実は、すべての操作はブロック間またはブロック内の境界上でローカルに動作しますが、存在する境界の数を超えるグローバルな認識を必要としないということです。 

有効な挿入ポイントの数が、単一の集約パラメーター (最初は「アクティブな位置」の数) を通じて暗黙的にどのように変化するかを追跡します。`n - 1`。 

### ステップ

 1. 文字列内の遷移の数、つまりインデックスの数を計算します。`i`そのような`S[i] != S[i+1]`。 この値を呼び出します`t`。 

これにより、異なる文字間の境界の初期数が得られます。これは、まさに第 2 タイプの操作をすぐに適用できる場所です。 
2. 隣接する等しいペアの数を計算します。`(n - 1 - t)`。 これに電話してください`e`。 

これらは、第 1 タイプの操作が適用できる初期位置に対応します。 
3. 第 1 タイプの操作を境界の数を増やすものとして解釈します。 それぞれの挿入`00 -> 010`または`11 -> 101`新しい遷移境界が 1 つだけ導入されるため、最初のタイプの操作ごとに、利用可能な異種位置の数が 1 つずつ増加します。 

つまり、演奏した後、`a`最初のタイプの操作では、利用可能な境界位置の数は次のようになります。`t + a`。 
4. 2 番目のタイプの操作では、任意のタイプの境界を選択し、文字を自由に挿入します。 このような操作を行うたびに長さが増加し、文字の選択に関係なく、潜在的な挿入ポイントの数が 1 つずつ増加します。 したがって、各 2 番目のタイプの操作は、現在の挿入位置の数に基づいた組み合わせ係数に寄与します。 

挿入位置の数は次のように直線的に変化します。 

初期位置 =`n - 1`、 k 回の操作後 =`n - 1 + k`。 
5. 重要な組み合わせ構造は、各操作が成長集合の中から位置を選択することと同等であるということです。 

最初の操作:`n - 1`選択肢

 2番目の操作:`n`選択肢

 3 番目の操作:`n + 1`選択肢

 などですが、妥当性制約は実現可能性によってのみ適用されます。`a`初期の等しいペアに関して。 
6. 実現可能性の条件: 等しいペアが存在しない場合に、最初のタイプの操作が決して要求されないことを保証する必要があります。 最初のタイプの操作は等しい隣接関係が存在する場合にのみ適用でき、そのような操作ごとに新しい操作が作成されるため、唯一の要件は次のとおりです。`a`初期の等しい隣接関係の数に、以前の最初のタイプの操作で作成された数を加えた数を超えてはなりません。この数は常に満たされます。 唯一の本当の制限は、次の場合に少なくとも 1 つの有効な初期等価ペアが存在する必要があることです。`a > 0`。 
7. ウェイの総数は線形係数の積になります。 

それぞれについて`a + b`操作では、その時点で利用可能な挿入位置の数を掛けます。 
8. したがって、答えは次のようになります。$$\prod_{i=0}^{a+b-1} (n - 1 + i)$$演算タイプによって引き起こされる区別できない選択を考慮した調整を乗算し、最初の演算と 2 番目の演算の間で分割される二項係数に解決されます。$$\binom{a+b}{a}$$### なぜ効果があるのか

 不変条件は、一連の操作の後、文字列の組み合わせの自由度はその長さのみに依存し、文字の正確な配置には依存しないということです。 挿入ごとに長さが 1 つ増加し、次のステップで 1 つの新しい潜在的な挿入位置が提供されます。 等しい隣接関係と等しくない隣接関係の区別は、最初のタイプの操作を開始する実現可能性についてのみ重要ですが、最初のタイプの操作が可能になると、新しい等しい隣接関係が伝播され、純粋に構造から将来デッドロックが発生しないことが保証されます。 

これにより、システムは、すべての有効なシーケンスが順序付けに一意に対応するプロセスに折りたたまれます。`a`区別できない「タイプ 1 トリガー」と`b`区別できない「自由挿入」。それぞれが着実に増加する間隔にわたって乗法的な選択肢に寄与します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

def modinv(x):
    return pow(x, MOD - 2, MOD)

def solve():
    n, a, b = map(int, input().split())
    s = input().strip()

    t = 0
    for i in range(n - 1):
        if s[i] != s[i + 1]:
            t += 1

    # feasibility: if no equal adjacency exists and we need first-type ops
    if a > 0 and (n - 1 - t) == 0:
        print(0)
        return

    total = a + b

    # product (n-1)(n)...(n+total-2)
    ans = 1
    for i in range(total):
        ans = ans * (n - 1 + i) % MOD

    # divide by ordering of a identical type-1 choices within total operations
    # combinatorial adjustment: C(a+b, a)
    # compute C(n, k) via factorials
    N = a + b
    fact = [1] * (N + 1)
    for i in range(1, N + 1):
        fact[i] = fact[i - 1] * i % MOD

    inv_fact = [1] * (N + 1)
    inv_fact[N] = modinv(fact[N])
    for i in range(N, 0, -1):
        inv_fact[i - 1] = inv_fact[i] * i % MOD

    comb = fact[N] * inv_fact[a] % MOD * inv_fact[b] % MOD

    ans = ans * comb % MOD

    print(ans)

if __name__ == "__main__":
    solve()
```実装ではまず、遷移をカウントすることで文字列がどの程度混合されているかを抽出します。 これは、等しい隣接関係が存在しないが、最初のタイプの操作が必要な場合の実現可能性チェックにのみ使用されます。 

乗算コアは、挿入位置の増加に対応する上昇階乗を構築します。 階乗ブロックは、2 つの演算タイプのインターリーブを考慮した二項係数を計算するために使用されます。 

微妙な点は、階乗がローカルで再計算されることです。これは複数のテスト ケース設定では不要ですが、単一入力の制約があるため、ここでは安全です。 プロダクション コンテスト ソリューションでは、最大 100 万個の階乗を事前計算する必要があります。

 ## 特殊なケース

 重要なエッジケースは、文字列が完全に交互になっている場合です。`010101`。 この場合、等しい隣接ペアは存在しないため、最初のタイプの操作は最初は使用できないように見えます。 アルゴリズムは、次のことを要求することでこれを処理します。`a > 0`、少なくとも 1 つの等しい隣接関係が最初に存在する必要があります。 それ以外の場合、答えはゼロです。 これにより、有効な開始トリガーなしで構造の作成が想定される無効な導出が防止されます。 

もう 1 つのエッジ ケースは、次のような完全に均一な文字列です。`00000`。 ここではすべての隣接関係が等しいため、最初のタイプの操作が常に適用されます。 アプリケーションごとに潜在的な挿入ポイントの数が増加するため、乗算の増加は単調であり、崩壊することはありません。 

最後の微妙なケースは次のような場合です。`a = 0`。 次に、問題は純粋に第 2 タイプの演算に帰着し、答えは純粋な階乗の上昇になります。`n - 1`文字列構造に依存しない選択肢。
