 ## 解決策
 ## 問題の理解

 根を張ったツリーが与えられ、各エッジには非常に大きなアルファベットのラベルが付いています。 ルートから任意のノードまで歩くと、そのパスに沿った一連のエッジ ラベルが文字列を形成します。 この文字列をノードのパス文字列と呼びます。 

ツリーと一緒にシーケンスもあります`t`。 それを段階的に処理します: ステップで`j`、接頭辞を考慮します`t[1..j]`。 ツリーノードごとに`i`、そのパス文字列とこのプレフィックスを連結し、新しい文字列を取得します。 

ここで、このように構築された文字列ごとに、その接尾辞として表示されるツリー内のすべての文字列を検索します。 それらの一致するノード パス文字列の中で、深さが最大のものを取得します。その深さは次のように定義されます。`f(i, j)`。 私たちは直感的に、ルートからノードへの文字列にいくつかの文字を追加した後、ツリーのどこまでをサフィックスとして「後方一致」できるかを尋ねています。 

最後に、各プレフィックス長について`j`を合計します`f(i, j)`すべてのノードにわたって`i`。 その合計が答えです`g_j`。 

制約は大きく、ツリーのサイズと長さの両方です。`t`すべてのテスト ケースで最大 200,000 まで可能です。 ノードとタイム ステップに対する二次アプローチは直ちに不可能です。 すべての一致を再計算するようなものでも、`(i, j)`ペアを明示的に指定すると、最悪の場合、最大 4e10 の操作が必要になりますが、これは制限をはるかに超えています。 

正しいソリューションでは、状態間で構造を再利用する必要があります。 重要な構造は、比較するすべての文字列がプレフィックス文字列のツリーから来ているということです。これはトライのようなビューまたはオートマトン ベースのビューを強く示唆しており、サフィックスの一致は視点を逆転するか、障害リンクの使用を示唆しています。 

素朴な推論を打ち破るエッジケースには、次のようなケースが含まれます。 

ノードのパス文字列はすでに別のノードのパス文字列のサフィックスであるため、文字を追加しても最適一致は変更されません。 

たとえば、ツリーに文字列が含まれている場合、`("a")`、`("ba")`を追加します`"a"`に`"b"`、最適なサフィックス一致は、構造に応じて、より深いノードからより短いノードに移動する可能性があります。 単純な「常に現在の一致を拡張する」という考えは、ツリー内でサフィックスの位置合わせが単調ではないため失敗します。 

もう 1 つの特殊なケースは、空の文字列の動作です。 空の文字列は常に有効なサフィックスであるため、すべてのノードは常に少なくとも深さ 0 を提供するため、アルゴリズムはこのベースラインを正しく初期化する必要があります。 

## アプローチ

 強引な解釈は簡単です。 各ノードについて`i`そしてそれぞれのプレフィックス`j`、文字列を明示的に形成します`s_i + t[1..j]`。 次に、すべてのツリー ノードを列挙します。`x`、どうかを確認してください`s_x`は、この構築された文字列の接尾辞であり、有効な一致の中で最大の深さを取得します。 これには、チェックごとに最大 2e5 の長さの文字列を比較する必要があり、最悪の解釈ではおよそ O(n * m * n * L) になります。`L`文字列の長さです。 比較を最適化したとしても、依然として O(n * m * L) の動作が発生しますが、これは実行不可能です。 

重要な観察は、ルートからノードへのパスから派生した文字列の固定セットに対して常に照合しているということです。 これはまさにトライ構造です。 文字列を逆にすると、接尾辞クエリは接頭辞クエリになり、一連の文字列に対する接頭辞クエリは、失敗リンクを含むトライのようにオートマトンによって自然に処理されます。 

ここでプロセスを再解釈してみましょう。 の接尾辞について考える代わりに、`s_i + t[1..j]`, この連結文字列の末尾からトライの中でどこまで逆方向にマッチできるかを考えます。 これは、ルートからノードまでのすべての文字列から構築された Aho-Corasick オートマトンの中を歩くのと同じです。 

オートマトンの各ノードはトライの状態に対応し、各遷移は文字の追加に対応します。 機能`f(i, j)`になります: 状態から開始`i`、加工後`j`文字の場合、何らかの接尾辞の一致に対応する、到達できる最も深いノードは何ですか。 答えはオートマトンの遷移のみに依存します。 

主な問題は、すべてのノードのすべてのノードを集約することです。`j`。 それぞれを更新するのではなく、`(i, j)`独立して、オートマトンの状態全体にカウントを伝播します。 それぞれのステップで`j`、現在各状態にある開始ノードの数を維持します。 次に、次を使用してトランジションを適用します。`t[j]`、その後に障害リンクの伝播が続き、サフィックスが閉じられることを保証します。 各ノードはその深さの重みに寄与し、ステップごとに寄与を蓄積します。 

これにより、問題は、ペアごとのマッチングから、線形遷移を伴う固定オートマトンにわたる繰り返しの質量分布へと軽減されます。

 ## アルゴリズムのチュートリアル

 まずツリーからトライ構造を構築します。 ツリー内の各ノードは、ルートからノードへのパス文字列を表すトライ状態に対応します。 親ポインタが与えられているため、ツリーをトラバースするときに各ノードに一意のトライ ノードを割り当てることができます。 

次に、Aho-Corasick とまったく同じように、BFS を使用してこのトライの障害リンクを構築します。 これらのリンクにより、ノードから有効なトライ状態でもある最長の適切なサフィックスに移動することができます。 

次に、トライ状態にわたる周波数配列を維持します。 最初に、すべてのツリー ノードは、対応するトライ状態で 1 単位の質量に寄与します。 

配列も維持します`depth[state]`、これはそのツリー ノードの深さです。 

の各キャラクターごとに、`t`、すべての状態にわたってグローバル遷移を実行します。 各ノードを個別に移動する代わりに、新しい周波数配列を計算します。`nf`。 州ごとに`v`周波数付き`f[v]`では、現在のキャラクターのオートマトン エッジを使用して遷移します。 エッジが存在しない場合は、有効な遷移またはルートに到達するまで失敗リンクをたどります。 結果の周波数を新しい配列に蓄積します。 

新しい位置を計算した後、各状態はその周波数とその深さを乗算した値を現在の答えに寄与します。`g_j`。 これが機能するのは、各アクティブ状態が、処理後に最もよく一致するサフィックスを持つすべての開始ノードを表すためです。`j`その状態で文字は終了します。 

最後に、次のすべての文字について繰り返します。`t`。 

### なぜ効果があるのか

 どのステップでも、すべての開始ノードで`i`は、正確に 1 つのアクティブなオートマトン状態によって表されます。これは、`s_i + t[1..j]`トライで。 障害リンク構造により、考えられるすべてのサフィックス対応が何らかの到達可能な状態によって表現されることが保証されます。 遷移では常にサフィックスの一貫性が維持されるため、有効な一致はスキップされません。また、失敗したリンクを常にたどるため、無効な一致はカウントされません。 深さにわたる合計を直接集計します`f(i, j)`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, m = map(int, input().split())
    p = list(map(int, input().split()))
    c = list(map(int, input().split()))
    t = list(map(int, input().split()))

    adj = [[] for _ in range(n + 1)]
    for i in range(1, n + 1):
        adj[p[i - 1]].append((i, c[i - 1]))

    nxt = [{} for _ in range(n + 1)]
    depth = [0] * (n + 1)

    q = deque([0])
    order = [0]

    while q:
        u = q.popleft()
        for v, ch in adj[u]:
            depth[v] = depth[u] + 1
            nxt[u][ch] = v
            q.append(v)
            order.append(v)

    fail = [0] * (n + 1)
    q = deque()

    for ch, v in nxt[0].items():
        fail[v] = 0
        q.append(v)

    while q:
        v = q.popleft()
        for ch, u in nxt[v].items():
            f = fail[v]
            while f and ch not in nxt[f]:
                f = fail[f]
            if ch in nxt[f]:
                fail[u] = nxt[f][ch]
            else:
                fail[u] = 0
            q.append(u)

    freq = [0] * (n + 1)
    for i in range(1, n + 1):
        freq[i] = 1

    def step(freq, ch):
        nf = [0] * (n + 1)
        for v in range(n + 1):
            if freq[v] == 0:
                continue
            u = v
            while u and ch not in nxt[u]:
                u = fail[u]
            if ch in nxt[u]:
                u = nxt[u][ch]
            else:
                u = 0
            nf[u] += freq[v]
        return nf

    res = []
    for ch in t:
        freq = step(freq, ch)
        ans = 0
        for i in range(n + 1):
            ans += freq[i] * depth[i]
        res.append(str(ans))

    print(" ".join(res))

if __name__ == "__main__":
    solve()
```この実装では、親ポインターからトライを構築し、BFS 順序で障害リンクを計算します。 の`step`関数は、すべてのアクティブな状態にわたって 1 つの完全なオートマトン遷移を実行します。 重要な点は、有効な遷移が見つかるまで障害リンクを繰り返し登ることです。これにより、現在のパスが直接延長できない場合でもサフィックスの正確さが保証されます。 

深さ配列は重要です。値をエンコードします。`d(x)`の定義で必須`f(i, j)`。 合計する`freq[state] * depth[state]`各ステップで必要な集計が生成されます。 

よくある落とし穴は、その状態を忘れてしまうことです`0`は空の文字列を表し、常に含める必要があります。含めないと、短い文字列の接尾辞の一致が失われます。 

## 実用的な例

 ルートがノードに接続して文字列を形成する小さなツリーを考えてみましょう。`"a"`、`"ab"`、`"b"`、 そして`t = "ba"`。 

開始時に、各ノードは 1 回アクティブになります。 加工後`'b'`、サフィックスと一致するノード`"b"`に対応する状態に集中する`"b"`そしてルートフォールバック。 加工後`'a'`、遷移によって再び質量が移動し、現在の状態の深さが蓄積されます。 

| ステップ | 処理された文字 | アクティブな状態 (概念) | 貢献 |
 | --- | --- | --- | --- |
 | 0 | - | 初期状態のすべてのノード | すべてのノードの深さの合計 |
 | 1 | b | b で終わるサフィックスに一致するノード | 更新された深さの合計 |
 | 2 | | ba で終わるサフィックスに一致するノード | 更新された深さの合計 |

 このトレースは、一致を最初から再計算するのではなく、質量がどのようにトライ状態間を移動するかを示しています。 

ここで、縮退したチェーン ツリーを考えてみましょう。`0 -> 1 -> 2 -> 3`ラベル形成中`"aab"`、 そして`t = "b"`。 読んだ後`"b"`、すべての接尾辞の一致は、表すノードに折りたたまれます。`"b"`存在する場合は、root にフォールバックします。 これにより、障害リンクが欠落している遷移を正しく処理することが確認されます。

 ## 特殊なケース

 重要なエッジケースは、すべてのノードがプレフィックスを共有する深いチェーンである場合です。 このような場合、障害リンクは繰り返しルートにリダイレクトされるため、適切なフォールバック処理がなければ、遷移によってコントリビューションが誤って削除されてしまいます。 このアルゴリズムは、有効なエッジが見つかるまで障害リンクを明示的にたどり、すべてのサフィックスの可能性が考慮されるようにすることでこれを処理します。 

もう一つのケースは次のような場合です。`t`トライには決して登場しない文字が含まれています。 その後、すべての遷移は状態にフォールバックする必要があります`0`。 周波数の塊が根元まで崩れると、答えは次のようになります。`n * depth[0] = 0`空の文字列のみが一致するため、これは正しいです。
