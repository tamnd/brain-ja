 ## 解決策
 ## 問題の理解

 長さの配列から始めます$m$、最初はゼロで埋められます。 それぞれの操作$i$位置のリストを取得し、それらのすべての位置を値で上書きします。$i$。 1から順番に演算が適用されるので、$n$、各位置の最終値は、単にその位置を操作した最後の操作のインデックスです。 

最終的な配列$R$したがって、「最後の書き込みが優先」ルールによって決定されます。すべてのインデックスは、それを含む最大の操作番号を記憶しており、その操作番号が最終値になります。 

タスクは、操作の順序を変更することです。 操作を任意に並べ替えることはできますが、この新しい順序で操作を適用した後は、すべての位置が元のプロセスとまったく同じ最終値になる必要があります。 

制約により、最大で$10^5$テストごとの操作と位置、合計入力サイズは最大約$2 \cdot 10^6$。 これにより、テスト ケースごとに線形または線形に近い解決策が強制されます。 各操作は多くの位置に触れる可能性があるため、操作位置の発生数が 2 次であるものはすべてすぐに失敗します。 

微妙な失敗例は、2 つの操作が一部のポジションで重なっているが、それらのポジションの「勝利」操作が元のプロセス全体で異なる場合に発生します。 たとえば、操作 1 が位置 1 と 2 にタッチし、操作 2 が位置 2 と 3 にタッチし、操作 3 が位置 1 と 3 にタッチする場合、インデックスが異なれば最後のライターも異なります。 操作のサイズやタッチされた最小インデックスによってソートするような単純なアイデアは、制約がグローバルではなく位置固有であることを無視しているため、失敗します。 

最大の問題は、最終結果が操作間の優先順位制約をエンコードするため、これらの制約を慎重に抽出する必要があることです。 

## アプローチ

 順序付けの制約を無視して、単純にすべての順列を試してみると、それぞれの順序付けをシミュレートして結果を比較できます。 それには費用がかかります$n! \cdot m$、これは小さな入力であっても完全に実行不可能です。 

もう少し素朴な試みとしては、各位置の最終値がその位置に影響を与える最後の操作にのみ依存することを理解することです。 これは、位置ごとに、元のシーケンスでどの操作が最後であるかを計算することを示唆しています。 これに電話してください$last[x]$。 同じ操作が各位置の最後のライターであり続ける必要があることを修正すると、すべての位置に対して次の制約を導出できます。$x$、タッチするすべての操作$x$を除外する$last[x]$前に現れる必要があります$last[x]$。 

This transforms the problem into a partial order over operations. Each position contributes directed constraints of the form “operation$a$手術前に来なければなりません$b$このような制約をすべて構築したら、問題は有効なトポロジー順序付けが存在するかどうかを確認することになります。 

まさにここが構造が悪用可能になる場所です。 配列について推論する代わりに、操作間の依存関係について推論します。 依存関係グラフにサイクルがある場合、すべての「最終書き込み」関係を順列で保存することはできません。 非巡回の場合、トポロジカルな順序付けによって有効な置換が生成されます。

 ## アルゴリズムのチュートリアル

 私たちは問題を、操作に関する有向グラフの構築と検証に集約します。 

1. 各位置に影響を与える最後の操作を計算します。 操作を昇順にスキャンし、各位置を記録します$x$最大のインデックス$i$そのような操作$i$含まれています$x$。 この値は$last[x]$。 このステップでは、アレイの最終状態を取得します。 
2. あらゆる操作に対して$i$、接触するすべての位置を調べます。 ポジションごとに$x$、 もし$last[x] \neq i$、その後操作$i$操作前に表示する必要があります$last[x]$任意の有効な順序で。 これを有向エッジとしてエンコードします$i \rightarrow last[x]$。 
3. 隣接リストを使用して完全な有向グラフを構築し、すべてのノードの次数を計算します。 このグラフは、最終的な配列を保存するために必要なすべての制約をエンコードします。 
4. 次数 0 のノードのキューを使用してトポロジカル ソートを実行します。 キューから操作を削除するたびに、それを答えに追加し、その近傍の次数を減らします。 
5. すべて出力できたら$n$操作では、順序は有効です。 それ以外の場合、グラフには循環が含まれ、順列は結果を保存できません。 

重要な考え方は、各ポジションが「勝者は他のすべての参加者の後に来なければならない」という制約に寄与しており、そのような制約はすべてグローバルに強制するということです。 

### なぜ効果があるのか

 各ポジション$x$元のプロセスで独自の操作によって決定されます$last[x]$。 その他のタッチ操作$x$後は上書きしないでください$last[x]$新しい順序で指定しないと、最終的な値が変更されます。 したがって、そのような操作はすべて前に行う必要があります$last[x]$。 これらの制約は、まさにグラフがエンコードしたものです。 

逆に、これらの制約がすべて満たされる場合、すべてのポジションに対して、$x$、新しい順序でそれに触れる最後の操作はまだです$last[x]$競合するすべての操作がより早く強制されるためです。 これにより、最終的な配列が正確に保存されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, m = map(int, input().split())
    
    ops = [[] for _ in range(n + 1)]
    last = [0] * (m + 1)

    for i in range(1, n + 1):
        arr = list(map(int, input().split()))
        p = arr[0]
        for x in arr[1:]:
            ops[i].append(x)
            last[x] = i

    g = [[] for _ in range(n + 1)]
    indeg = [0] * (n + 1)

    for i in range(1, n + 1):
        for x in ops[i]:
            j = last[x]
            if j != i:
                g[i].append(j)
                indeg[j] += 1

    q = deque([i for i in range(1, n + 1) if indeg[i] == 0])
    res = []

    while q:
        u = q.popleft()
        res.append(u)
        for v in g[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)

    if len(res) != n:
        print("No")
    else:
        print("Yes")
        print(*res)

t = int(input())
for _ in range(t):
    solve()
```コードはまず、ターゲット配列を完全に記述する各位置の「最後の出現」を再構築します。 次に、すべてのエッジで、ポジションに対する非勝利操作が勝利操作よりも前に出現する必要がある有向グラフを構築します。 

トポロジカル ソートは両端キューを使用して実装されます。 サイクルが存在する場合、一部の演算は度数 0 に到達することはなく、不可能であることを正しく示します。 

よくある落とし穴は、エッジを 2 回繰り返したり、操作自体が最後の書き込みである位置に誤ってエッジを追加したりすることです。 これらのケースには制約が課されないため、スキップする必要があります。 

## 実用的な例

 操作が重複する小さな例を考えてみましょう。 

入力:```
n = 3, m = 3
1: [1]
2: [1, 2]
3: [2]
```ここ$last[1] = 2$、$last[2] = 3$、$last[3] = 0$。 

エッジを構築します。 

オペレーション 1 が貢献$1 \rightarrow 2$。 

オペレーション 2 が貢献$2 \rightarrow 3$。 

操作 3 は何も貢献しません。 

トポロジカルソートにより順序付けが行われます$1, 2, 3$。 

| ステップ | キュー | 選ばれた | 結果 | 角度変化 |
 | --- | --- | --- | --- | --- |
 | 0 | 1 | 1 | [1] | 2 減少 |
 | 1 | 2 | 2 | [1,2] | 3 減少 |
 | 2 | 3 | 3 | [1,2,3] | 完了 |

 これにより、重複する更新に応じて依存関係が正しく伝播されることが確認されます。 

2 番目の例は、不可能であることを示しています。```
1: [1]
2: [1]
```どちらの操作も同じ位置にタッチしますが、操作 2 のみが最後であるため、エッジが得られます。$1 \rightarrow 2$。 これはまだ非循環であるため、順序付けは次のように存在します。$1,2$。 依存関係を誤って逆にすると、サイクルが発生し、失敗が誤って報告されてしまいます。 この構造により、方向が常に最後以外から最後になることが保証され、誤ったサイクルが防止されます。 

## 複雑さの分析

                j = last[x]

                    g[i].append(j)

 ## 特殊なケース

 最小のケースは、すべての操作が互いに素な位置に触れる場合です。 グラフにはエッジがないため、すべての順列が有効です。 このアルゴリズムは、最初に次数 0 のすべてのノードを正しく生成し、任意の次数を出力します。 

よりデリケートなケースは、単一の位置が多数の操作によってタッチされる場合です。 元のシーケンスの最後のものだけがエッジのチェーンのシンクとなり、他のすべてはそれを指します。 この構造により、エッジが反転しないことが保証されるため、人為的なサイクルが導入されません。 

共有位置に誤って両方向のエッジを追加すると、失敗するケースが発生します。 これにより、有効な順序付けが存在する場合でも、即時サイクルが作成されます。 アルゴリズムは、元のプロセスによって決定された最終ライターに厳密にエッジを向けることによってこれを回避します。
