 ## 解決策
 ## 問題の理解

 私たちは、プレイヤーが最初の手札と山札という 2 つの順序付けられた構造を持つ、非常に制約のあるカード ゲームをシミュレートしています。 手札には特別な勝ちカードが含まれており、山札にはカードを引くことで一時的に手札のサイズを増やすことができるユーティリティ カードが含まれています。 プレイヤーはカードを順番にプレイすることしかできず、プレイされたすべてのカードは次のカードが選択される前に完全に解決されます。 

キー制限は手のサイズ制限です`k`。 カードが山から引かれるたびに、現在の手のサイズが厳密に以下の場合にのみ手札に追加されます。`k`。 手札がすでに上限に達している場合、引かれたカードは単純に捨てられます。 ドローパイルは厳密に上から下に消費されます。 

勝利に重要なカードは 1 枚だけです。`G`カード。 山札が完全に空の場合にのみプレイできます。 したがって、プロセス全体は、有用なドロー効果がブロックされた状態に陥らないように、手札のサイズを管理しながら山を使い果たせるかどうかを判断することになります。 

入力により 2 つの文字列が得られます。 1 つ目は、最初のハンドを説明します。これには 1 つだけが含まれます。`G`。 2 つ目は、ドローパイルを上から下まで説明します。 各パイル カードは、シングル ドロー カード、ダブル ドロー カード、またはプレイできないデッド カードのいずれかです。 

出力では最小の整数が要求されます`k`（少なくとも初期の手札のサイズ）山札が完全に使い果たされることを保証する何らかの一連のトランプが存在し、`G`遊ばれること。 そうでない場合`k`存在する場合、不可能を出力します。 

すべてのテスト ケースにわたる制約の合計は、テスト ケースごとにほぼ線形またはほぼ線形の解を得るには十分小さいです。 以来`n, m ≤ 2500`、`O((n+m)^2)`または`O(nm)`アプローチは許容されますが、状態を超える三次または指数関数は許容されません。 

手札の容量がすべてのドローに共通のグローバルな制約であることを考慮せずに、ドロー カードを貪欲に消費すると、素朴な失敗例が発生します。 たとえば、常に「できるだけ多くのカードをすぐに取る」場合、たとえプレイの順序を変えれば飽和が避けられるとしても、早い段階で役に立たないカードで手札を埋めてしまい、後で必要なドローチェーンをブロックしてしまう可能性があります。 

別の微妙な失敗が発生します`W`カード。 これらはプレイできないため、手札のスペースを占有しますが、進歩には寄与しません。 これらを無視したり、自由にスキップできると想定した単純なシミュレーションは、必要な容量を過小評価したり、実現可能性を誤って判断したりすることになります。 

## アプローチ

 直接シミュレーションのアプローチでは、ゲーム状態全体、つまり現在手元にあるカード、山のどの位置、およびカードがプレイされる正確な順序をモデル化しようとします。 手札にある使用可能なカードをプレイすることを検討するたびに、その効果をシミュレートして再帰します。 ハンドは単なるセットではなく、パイルの相互作用に順序制約のあるマルチセットであり、ハンドがいっぱいかどうかに応じて各ドローが分岐するため、これはすぐに実行不可能になります。 

分岐を無視して貪欲にシミュレーションしたとしても、本当の問題は残ります。唯一の意味のあるリソースは、潜在的なドローを決して無駄にしないために、時間の経過とともにハンドにどれだけのスロットを予約しなければならないかということです。 各ドロー カードは、新しいカードを手札に挿入することで、将来のキャパシティ プレッシャーを効果的に高めようとします。 

重要な点は、実際には正確なプレイのシーケンスは必要ないということです。 を除くすべてのプレイ可能な手札のカード`G`は、存在する限りいつでも使用できる「描画ソース」とみなすことができます。 実行可能性に関しては、再生順序は関係ありません。 重要なのは、山を上から下に処理するときに、有用なドローを破棄せずに受け入れるのに十分な空きスロットを常に確保できるかどうかです。 

これにより、問題は、指定された容量が適切であるかどうかを判断することになります。`k`これにより、必要なカードを失わないよう十分な「利用可能なスペースの予算」を維持しながらパイルを処理できます。 修正の可能性を確認できれば`k`、最小限の二分探索ができます`k`。 しかし、実現可能性が単調であることを理解すれば、二分探索さえも不要であり、ドローカードを可能な限り最大限に使用することによって生成される最大同時圧力を追跡することによって最小値を直接計算できます。 

重要な削減は、山をシミュレートすることです。`Q`または`B`、それを将来のワークロードの生成として扱います。`Q`潜在的なスロット消費イベントを 1 つ生成します。`B`2つ生成します。 問題は、キャパシティを超過することなく、生成されたすべての需要に対応できるように初期手札の使用をスケジュールできるかどうかです。 これは、最悪のプレフィックス過負荷を追跡することと同じです。

 ## アルゴリズムのチュートリアル

 山を上から下に処理し、ハンドの容量を尊重しながら満たさなければならない「アクティブなドロー リクエスト」の数を維持します。 手には最初からサイズがあります`n`、容量は`k`したがって、最初は次のようになります。`k - n`無料のスロット。 

このプロセスを次のように解釈します。 

1. から始める`used = n`、すべての初期手札がスロットを占有することを意味します。`G`そして全部使えない`W`カード。 フリースペースは、`free = k - n`。 
2. 山札を順番に移動します。 
3. 遭遇したとき`Q`、カードを 1 枚引く必要があることをシミュレートします。 空き容量がある場合はデクリメントします`free`そして増加します`used`カードが手札に入るからです。 空き領域がない場合、カードは破棄され、何も行われません。 
4. 遭遇したとき`B`では、2 つの描画を連続して試行するため、同じロジックを 2 回繰り返します。 2 番目の描画では、最初の描画の後に更新された状態が表示されます。 
5. 遭遇したとき`W`、ドロー効果ではないので何もしません。 
6. いつでも、`free`電流がマイナスになると、`k`は無効です。 
7. 制約に違反することなく杭の処理を完了すると、次のようになります。`k`で十分です。 

重要なのは、手札からトランプを明示的にシミュレートする必要がないということです。 ハンドの唯一の役割は、入ってくるドローが受け入れられるか破棄されるかを決定することです。 

最終的な答えは最小です`k`上記のシミュレーションは成功します。 実現可能性は単調なので、`k`、間の二分探索で見つけることができます。`n`そして`n + m`。 

### なぜ効果があるのか

 いつでも、システムが不可能になる唯一の方法は、利用可能な容量を超えるカードを受け入れることを余儀なくされた場合です。 なぜなら`Q`そして`B`効果は順番に行われ、手札のどの特定のカードが効果をトリガーするかに関係なく、ドロー イベントの総数に影響を与えることなく、すべてのハンド プレイの順序を変更できます。 したがって、パイルプロセスは一度で完全に決定されます`k`は固定されており、有効な戦略は総需要を変更しない描画トリガーのスケジュールに対応します。 このアルゴリズムは、容量がゼロ未満に低下したかどうかを正確に追跡します。これが、空の山に到達することを防ぐ唯一の条件です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(k, n, pile):
    free = k - n
    if free < 0:
        return False

    for c in pile:
        if c == 'Q':
            if free > 0:
                free -= 1
            else:
                return False
        elif c == 'B':
            for _ in range(2):
                if free > 0:
                    free -= 1
                else:
                    return False
        else:
            continue

    return True

def solve():
    T = int(input())
    for _ in range(T):
        n, m = map(int, input().split())
        SH = input().strip()
        SP = input().strip()

        # k must be at least n
        lo, hi = n, n + m

        ans = None
        while lo <= hi:
            mid = (lo + hi) // 2
            if can(mid, n, SP):
                ans = mid
                hi = mid - 1
            else:
                lo = mid + 1

        if ans is None:
            print("IMPOSSIBLE")
        else:
            print(ans)

if __name__ == "__main__":
    solve()
```このソリューションでは、実現可能性チェックを単調な述語に分離します。 ヘルパー関数は、固定容量の下で杭をシミュレートします。`k`。 最悪の場合、すべてのカードを手札に保持する必要があるため、二分探索範囲は安全です。`n + m`。 

微妙な実装の詳細が処理されています`B`2 つの連続したものとして`Q`容量が不足している場合は順序が重要になるためです。 もう 1 つは、実際にシミュレーションを行っていないことです。`G`なぜなら、成功は、手札の順序ではなく、山を空にすることだけに依存するからです。

 ## 特殊なケース

 重要なエッジケースは、手がすでにいっぱいになっている場合です。`W`カード。 この状況では、たとえドローしようとしたカードがすぐに破棄されるため、容量が小さすぎると、たとえ有用なドローカードが大量に山積みされていても役に立ちません。 アルゴリズムはこれを正しく処理します。`free`として始まります`k - n`、だから、もし`n`すでにほとんどの容量を消費しているため、引き分けは受け付けられません。 

別のエッジケースが連続している`B`山の早い段階にあるカード。 それぞれなので`B`2 つの連続した描画試行に拡張される場合、順序はマイクロステップ レベルで重要になります。 シミュレーションは 2 つの描画を即座に処理することでこれを処理し、部分的な承認が両方とも成功したと誤って想定しないようにします。 

最後に、次のようなケース`k = n`重要です。 ここでは新しいカードを追加することはできないため、すべてのドローは破棄されます。 このアルゴリズムは、パイルが終了に到達することに無関係であり、ゲーム ルールに一致する場合にのみ、実現可能性を正しく識別します。
