 ## 解決策
 ## 問題の理解

 n 頂点の有向グラフを扱っていますが、グラフは明示的に与えられていません。 代わりに、順序付けられた個別の頂点のペアの間に有向エッジが存在するかどうかを尋ねることによってのみ調べることができます。 私たちのタスクは、他のすべての頂点からの入力エッジを持ち、出力エッジをまったく持たない特別な頂点が存在するかどうかを判断することです。 そのような頂点が存在する場合は、それらのいずれかを出力する必要があり、存在しない場合は -1 を出力します。 インタラクションにより、テスト ケースあたり最大 3n クエリに制限されます。 

重要な問題は、答えがクエリに依存する可能性のある隠れたグラフと一致するという意味で、グラフが適応的であることです。 これにより、固定構造の仮定に基づく確率的ショートカットの可能性が排除されるため、過去の回答と一致するグラフの下ですべての決定が有効なままでなければなりません。 

テスト ケースごとに n が最大 1000、合計が 1000 という制約は、O(n^2) クエリが限界に達しているものの、テストごとに慎重に制御されれば許容できる可能性があることを示唆しています。 ただし、3n クエリでは線形クエリ戦略が強制されるため、すべてのペアを比較するアプローチは直ちに不可能になります。 

複数の頂点が候補に近い場合、微妙なエッジ ケースが発生します。 たとえば、3 つのノード上の有向サイクルでは、すべての頂点に次数 1 と次数 1 があるため、答えは存在しません。 「次数の高い頂点が候補である可能性が高い」という単純な考えは失敗します。頂点ごとに O(n) クエリを実行しないと次数を直接計算できないためです。 

別の故障モードは、1 つの頂点がほぼシンクであるものの、1 つの出力エッジを持つ星形のグラフに表示されます。 非候補を体系的に排除しない限り、エッジの部分的なサンプリングは、それが候補であると誤って示唆する可能性があります。 

## アプローチ

 ブルート フォース戦略では、n(n−1) クエリを使用して完全な隣接行列を計算し、次にすべての頂点の入次数と出力次数を計算します。 これは、グラフを完全に再構築し、条件を直接検証するため、正しいです。 ただし、テスト ケースごとに Θ(n^2) クエリを使用します。これは、許容される 3n 制限をはるかに超えています。 n = 1000 の場合、テストごとに約 100 万クエリになりますが、これは現実的ではありません。 

重要な観察は、グラフの構造に関する完全な知識は必要ないということです。 必要なのは、ユニバーサル シンクが存在するかどうかを特定し、存在する場合はそれを見つけることだけです。 このタイプの問題では、多くの場合、線形消去プロセスが認められます。つまり、すべての次数を決定する代わりに、単一の候補を維持し、ペアごとの比較を使用して不可能な頂点を破棄します。 

決定的な特性は、頂点 u がシンクではない場合、その頂点 u がどこかの頂点への出ていくエッジを持っているか、または u から入ってくるエッジを見逃しているためシンクになれない別の頂点が存在するかのどちらかであるということです。 これにより、トーナメントのような方法で頂点を比較し、クエリごとに少なくとも 1 つの候補を排除することができます。 

候補頂点を維持できます。 他の各頂点について、候補とその頂点の間のエッジを一方向でクエリします。 答えに応じて、候補または他の頂点のいずれかを安全に削除できます。 線形スイープの後、残る候補は最大 1 つです。 2 番目の検証パスでは、最大 2(n-1) 個のクエリを使用してシンク条件を本当に満たしているかどうかをチェックし、合計を 3n 以内に保ちます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) クエリ | お(1) | 遅すぎる |
 | 候補者の排除 | O(n) クエリ | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

1. まず、頂点 1 がシンク候補であると仮定します。 エッジを検査する前に任意の頂点が条件を満たす可能性があるため、これは任意です。 
2. 頂点 2 から n までを繰り返します。 各頂点 i について、候補から i までのエッジがあるかどうかをクエリします。 
3. エッジ候補 → i がある場合、シンクには出力エッジがないため、その候補はシンクになることはできません。 候補を i に置き換えます。 
4. エッジ候補 → i が存在しない場合、頂点 i はシンク候補になりえなくなります。 これは、シンクは他のすべての頂点からエッジを受け取る必要があるが、候補には i へのエッジがないため、i が失格になっている間も候補はまだ有効である可能性があるためです。 
5. このパスの後、すべての排除を生き残る潜在的な候補者が 1 人います。 
6. 検証パスを実行します。すべての頂点 i ≠ 候補について、クエリを使用して 2 つの条件をチェックします。 まず、候補者→iは偽でなければなりません。 次に、i → 候補が true でなければなりません。 いずれかのチェックが失敗した場合、候補は無効になります。 
7. すべてのチェックに合格した場合、候補を出力します。 それ以外の場合は -1 を出力します。 

これが機能する理由は、削除中のすべてのクエリがシンクになり得ない少なくとも 1 つの頂点を削除するためです。 最終候補は、シンク プロパティとの矛盾によって削除されなかった唯一の頂点であり、検証パスにより、適応的な矛盾が残らないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    def ask(u, v):
        print("?", u, v)
        sys.stdout.flush()
        return int(input())
    
    cand = 1
    
    for i in range(2, n + 1):
        res = ask(cand, i)
        if res == 1:
            cand = i
    
    for i in range(1, n + 1):
        if i == cand:
            continue
        if ask(cand, i) == 1:
            print("! -1")
            sys.stdout.flush()
            return
        if ask(i, cand) == 0:
            print("! -1")
            sys.stdout.flush()
            return
    
    print("! {}".format(cand))
    sys.stdout.flush()

t = int(input())
for _ in range(t):
    solve()
```実装は削除戦略に直接に従います。 機能`ask`インタラクションとフラッシュをカプセル化します。これは、アイドル状態エラーを回避するためにインタラクティブな問題で必須です。 

最初のループでは、単一の候補が維持されます。 現在の候補に別の頂点へ向かうエッジがあるかどうかを判断するだけで十分であるため、各比較に必要なクエリは 1 つだけです。 そうなるとシンクではないのですぐに切り替えます。 

検証フェーズはより厳格になります。 私たちは、候補者が誰に対しても外向きのエッジを持たず、全員が候補者に対してエッジを持っていることを保証します。 どちらの条件もターゲット頂点にとって必要十分です。 

## 実用的な例

 頂点 3 がシンクである n = 4 の小さなグラフを考えてみましょう。 エッジが 3 を除くすべての頂点が 3 を指しており、3 には外に出るエッジがないものとします。 

### 排除フェーズ

 | ステップ | 候補者 | 私 | クエリ cand → i | アクション |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 2 | 1 | can は 2 になります |
 | 2 | 2 | 3 | 0 | キャンドステイ2 |
 | 3 | 2 | 4 | 1 | can は 4 になります |

 消去後の候補は 4 ですが、これはこの構築されたシナリオでは正しくなく、検証が必要な理由を示しています。 

### 検証フェーズ

 | 私 | キャン→私 | 私 → できます | 結果 |
 | --- | --- | --- | --- |
 | 1 | 1 | 1 | わかりました |
 | 2 | 1 | 1 | わかりました |
 | 3 | 1 | 1 | わかりました |

 ここで、条件に違反すると検証は失敗します。 有効なシンクの場合、すべてが合格し、正しい頂点が確認されます。 

このトレースは、任意のグラフでは消去だけでは不十分であり、正確さのためには第 2 フェーズが不可欠であることを示しています。

 ## 特殊なケース

 主なエッジ ケースは、複数の頂点がニアシンク構造を形成しているが、有効な頂点がどれも存在しない場合です。 たとえば、サイズ n の有向サイクルでは、すべての頂点に入力エッジと出力エッジの両方があるため、アルゴリズムは削除中に候補を継続的に置き換えます。 最終候補は、出ていくエッジがあるか、ある頂点から入ってくるエッジがないため、検証に失敗し、正しい -1 出力がトリガーされます。 

もう 1 つのエッジ ケースは、真のシンクが存在するが、それを排除する方法で直接比較されることがない場合です。 シンクには出力エッジがないため、削除ステップによってこれが保証されます。そのため、頂点と比較したときにシンクが破棄されることはありません。 常にすべての比較に耐え、変更されずに検証に達します。
