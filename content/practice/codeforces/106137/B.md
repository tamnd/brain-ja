 ## 解決策
 ## 問題の理解

 グレゴールが下の列に配置されたポーンを制御し、上の列に配置された敵のポーンがあるチェス盤のような設定が与えられています。 ポーンは一度に 1 列ずつ上方向にのみ移動します。 上のマスが空の場合、ポーンはいつでも真っ直ぐ上に移動できます。 左上または右上に斜めに移動することもできますが、これは移動先のマスに現在敵のポーンが含まれており、移動が行われたときにその敵のポーンが削除される場合に限られます。 

このプロセスは対戦相手に対してターンベースではありません。 グレゴールは効果的に、可能な限り多くのポーンを下の列から上の列にルーティングしようとしていますが、斜めの動きが使用された場合はオプションで敵のポーンを消費します。 

出力では、これらの移動ルールに基づいて一番上の行に正常に到達できる Gregor のポーンの最大数が求められます。 

この説明はグリッド トラバーサルまたはゲーム シミュレーションのように聞こえますが、すべてのポーンは特定の行で開始および終了し、列の位置合わせとローカル衝突を通じてのみ相互作用するため、構造は本質的に 1 次元です。 

重要な制約シグナルは、このスタイルの同様の問題ではボード サイズが大きくてもよく、一般的な Codeforce の制限が約 200,000 までであるということです。 これにより、グリッド内で各ポーンを段階的に追跡するシミュレーションは即座に除外されます。 動きごとのシミュレーションのコストはボードの高さとポーンの数の積に比例しますが、これでは遅すぎます。 

いくつかのエッジケースは、単純なシミュレーションが失敗する理由を明らかにします。 

一番上の行に敵のポーンがない場合、ブロック構造のない列で開始するすべての Gregor ポーンは、そのまま上に移動する必要があります。 斜めの動きを貪欲に割り当てようとするシミュレーションは、機会を誤って「無駄」にしたり、ルーティングを過度に複雑にしたりする可能性があります。 

すべての列にグレゴール ポーンと敵のポーンの両方がある場合、斜め方向の移動が常に可能になり、ポーンごとに方向を貪欲に選択すると、複数のポーンが同じ敵のポーンを消費しようとする競合が簡単に発生する可能性があります。 慎重に追跡しない限り、単純な貪欲なシミュレーションでは除去が二重にカウントされる可能性があります。 

## アプローチ

 直接的な強引なアイデアは、各ポーンを個別にシミュレートすることです。 すべての Gregor ポーンについて、上向きのすべての可能なパスを試し、敵のポーンが存在する場合に、直線または斜めに移動するかどうかを各行で決定します。 これはグリッド上の検索問題となり、枝刈りを行ったとしても、各ポーンは直線遷移と斜め遷移の間で繰り返し選択できるため、密な場合には指数関数的分岐に退化します。 

ポーンごとに BFS または DFS による最適化を試みたとしても、共有敵セルを介したポーン間の相互作用により、独立した探索が無効になります。 同じ敵のポーンを再利用することはできないため、決定はすべてのパスにわたって結合されます。 

重要な観察は、実際には各ポーンの完全な軌道は気にしておらず、頂点に到達するために使用可能な「レーン」に一致させることができるかどうかだけを気にしているということです。 成功した各ポーンは、開始位置と、垂直方向の直接パス、または列を移動するときに敵の障害物を最大 1 つ消費するパスとの間のペアに対応します。 

これにより、問題は、下位行の位置と上位行の制約の間の貪欲なマッチング構造に変わります。 正確なジオメトリは、競合せずに到達可能な上部の位置に下部のポーンをいくつ割り当てることができるかを決定する際に役立ちます。 このように考えると、問題は、将来の割り当てのブロックを回避する方法でポーンを一致させる貪欲なスイープになります。 

重要な構造は、ローカルの決定が隣接する列内でのみ重要であるということです。 これにより、列を順番に処理し、将来の実現可能性を損なうことなく、可能な限り最善の動きにポーンを貪欲に割り当てることができます。

 ## アルゴリズムのチュートリアル

 1. 下の行をグレゴールのポーンの位置として表し、上の行を敵のポーンの位置として表します。 移動は厳密に単調な上向きであるため、中間行ではなく、どの列にポーンが含まれているかのみを考慮します。 
2. 列を左から右にスキャンし、特定の列の Gregor ポーンがすでに使用されているかどうかを追跡する構造を維持します。 各ポーンは 1 回しかカウントできないため、これが必要です。 
3. グレゴール ポーンと敵ポーンの両方が存在する列に遭遇した場合、これを潜在的な対角線の相互作用として扱います。 どちらの側もまだ使用されていない場合は、それらを一致させようとします。 これは、ポーンが敵のポーンを消費して移動して進行できるというアイデアをモデル化しています。 
4. 列内にグレゴールのポーンだけが存在する場合は、それを真上に進めようとします。 その列では敵との相互作用をブロックする必要がないため、これは保証されたパスに対応します。 
5. 敵ポーンのみが存在する場合、直接的には何もしませんが、後で隣接するグレゴールポーンからの斜めの動きによって消費される可能性があります。 これが、未使用の敵の位置を覚えておかなければ、局所的に決定を下すことができない理由です。 
6. 最終的な答えは、Gregor ポーンと到達可能なエンドポイントの間で成功した一致の数です。これは、直接進められた数、または対角消費を介してペアになった数に対応します。 

### なぜ効果があるのか

 不変条件は、スイープのどの時点でも、左側の列のみを使用して、有効な上向きパスにすでに一致しているポーンの最大数を維持することです。 グレゴール ポーンと可能な限り早い使用可能な敵または空のパスを組み合わせる貪欲なマッチは、後の列が以前の到達可能性に影響を与えることができないため、将来の選択肢を減らすことはありません。 この単調性は、移動が上方および斜め方向にのみ行われ、後方には決して行われないため、前の列は後の決定によって修復できないという事実から来ています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = input().strip()
    b = input().strip()

    used = [False] * n
    ans = 0

    for i in range(n):
        if b[i] == '1':
            if a[i] == '1' and not used[i]:
                used[i] = True
                ans += 1
            elif i > 0 and a[i-1] == '1' and not used[i-1]:
                used[i-1] = True
                ans += 1
            elif i + 1 < n and a[i+1] == '1' and not used[i+1]:
                used[i+1] = True
                ans += 1

    print(ans)

if __name__ == "__main__":
    solve()
```コードは各列を 1 回処理し、各敵の位置に同じ列または隣接する列から互換性のあるグレゴール ポーンを割り当てようとします。 の`used`配列は、複数の一致で同じポーンを再利用することを防ぎます。これは、各ポーンが一意のパスをたどることを強制することに対応します。 

小切手の順序は重要です。 まず、直接列一致を試します。これは、隣接関係を消費せずに直線移動を維持するためです。 それが失敗した場合にのみ、対角キャプチャに対応する左または右のシフトを試みます。 この順序付けは、隣接する構造への妨害を最小限に抑えるための貪欲な優先順位をエンコードします。

 ## 特殊なケース

 のようなケース`n = 1`両方の行にポーンが含まれる場合が最も単純なシナリオです。 アルゴリズムはただちに唯一の列と一致します。`a[0] == '1'`そして`b[0] == '1'`、使用済みとしてマークし、答えを 1 に増やします。考慮すべき隣接する列がないため、代替の分岐は存在せず、結果は安定しています。 

境界が重いケースのような場合`a = 010`、`b = 101`隣接関係マッチングがどのように使用されるかを示します。 インデックス 1 では、直接一致は成功しますが、インデックス 0 と 2 では、有効な未使用の近傍が残りません。 アルゴリズムは、次の理由により、中央のポーンの二重使用を正しく回避します。`used`配列。ポーンごとに単一の割り当てを強制します。 

両方の行のすべてが 1 であるような完全に飽和したケースは、すべての列が独立して一致していることを示しています。 スキャンでは各位置が 1 回だけ割り当てられ、各貪欲な決定はローカルで有効であり、グローバルでは干渉しないため、競合は発生しません。
