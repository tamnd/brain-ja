 ## 解決策
 ## 問題の理解

 5 文字のみからなる文字列が与えられます`t, u, r, l, e`。 文字列のセグメントを繰り返し削除しますが、セグメントは最初の文字が次の場合にのみ削除できます。`t`、その最後の文字は`e`、厳密にセグメント内のどこかに少なくとも 1 つあります。`l`。 セグメントを削除すると、エンドポイント間のすべてが消えます。 

削除するたびに、残りの文字列全体が逆になります。 この反転は、位置がミラーリングされるため、将来のセグメントの形成方法に影響しますが、どの文字が残るかは変わりません。 

タスクは、文字列全体を削除するような一連の削除が存在するかどうかを判断することです。 

すべてのテスト ケースにわたる合計の長さの制約は最大 200,000 であるため、ソリューションはテスト ケースごとに線形に近い必要があり、操作ごとに二次関数や、文字列を最初から繰り返しスキャンするようなものではない必要があります。 

考えられるすべてのセグメントを試すブルート フォース シミュレーションでは、直ちに遅すぎます。各削除には、有効なエンドポイントの検索に直線的な時間がかかる可能性があり、直線的に多数の削除が発生する可能性があり、最悪の場合は三次的な動作が発生する可能性があります。 

さらに微妙な問題は、反転ステップで発生します。 単純な実装では、削除のたびに文字列を物理的に反転して処理を続行しようとする可能性があります。 これは隠れた落とし穴につながります。同じ論理構成が異なる方向に現れる可能性があるため、反転パリティを考慮せずに固定インデックスに依存するソリューションは一貫性のない動作をします。 

たとえば、次のような文字列について考えてみましょう。`tleelt`。 セグメントを一度削除して、残りを反転することもできますが、実装によっては、同じ残りの構造が異なって解釈され、方向が適切に追跡されていない場合に誤った拒否が発生する可能性があります。 

重要な問題は、有効なセグメントを選択するだけではなく、必要な文字の構造がすべてを削除するまでプロセスを続行できるかどうかを理解することです。 

## アプローチ

 ブルートフォースの解釈は簡単です。各ステップで、可能なすべてのポジションのペアを試します。`l`そして`r`エンドポイントが`t`そして`e`があるかどうかを確認します。`l`内部では、セグメントを削除し、文字列を反転して再帰します。 これは、すべての有効な操作シーケンスを調査するため、原則として正しいです。 

問題は分岐要素です。 最悪の場合、セグメントは O(n²) 個存在し、削除されるたびに文字列が変更されます。 枝刈りを行ったとしても、削除順序が異なると構成も異なるため、状態空間は指数関数的に増大します。 これは、実行可能な制限時間をすぐに超えてしまいます。 

重要な観察点は、取り外し可能なセグメント内の構造的制約を強制する唯一の文字は、`l`。 文字`u`そして`r`選択したセグメント内にある場合は削除されることを除き、無関係です。 基本的に各操作で 1 つ消費されます。`t`左側の境界に 1 つ`e`右側の境界で少なくとも 1 つ`l`中のどこかに。 

この角度から見てみると、反転はそれほど重要ではなくなります。 削除するたびに文字列全体を反転しても、残りの文字のマルチセットは変更されません。また、現在の文字列のどこからでも任意のセグメントを選択できるため、方向は左右の読み取り方法にのみ影響し、有効なペアが存在するかどうかには影響しません。 

したがって、問題は、各グループに少なくとも 1 つが含まれるグループを繰り返し形成できるかどうかということになります。`t`、少なくとも 1 つ`e`、少なくとも 1 つ`l`、各グループはちょうど 1 つを消費します。`t`そして1つ`e`少なくとも 1 つは必要ですが、`l`。 可能な限り最善の使用法`l`再利用するため、操作ごとに 1 つを専用にすることです。`l`削除すると、内部で複数の操作を行うことはできなくなります。 

させて`cnt_t`、`cnt_e`、 そして`cnt_l`これらの文字の数を数えてください。 すべての操作で 1 つ消費されます`t`そして1つ`e`したがって、操作の数は最大で`min(cnt_t, cnt_e)`。 各操作には個別の操作も必要です`l`削除されたセグメント内のどこかにあるので、少なくとも同じ数も必要です`l`。 したがって、操作の最大数は次のように制限されます。`min(cnt_t, cnt_e, cnt_l)`。 

文字列が空でないときにこの数値が 0 の場合、操作を開始することさえできません。 それが正の場合、問題の構造により、常に利用可能な削除を選択することで有効な削除を構築できます。`l`そしてそれを`t`そして`e`現在の構成でその周囲に配置できます。 

これにより、直接計数ベースのソリューションが得られます。

 ## アルゴリズムのチュートリアル

 1. 次の出現を数える`t`、`e`、 そして`l`文字列の中で。 これらの文字は、削除が可能かどうかに影響を与える唯一の文字です。 
2. 削除の制限数を次のように計算します。`k = min(cnt_t, cnt_e, cnt_l)`。 すべての操作が必要なリソースをそれぞれ 1 つ消費するため、これは可能な有効な操作の最大数を表します。 
3. 文字列が空ではなく、`k == 0`、削除はできないと即結論するので、回答は不可能です。 
4. それ以外の場合は、完全な削除シーケンスが存在すると結論付けます。 

根底にある理由は、すべての有効な操作で必要なリソースのトリプルが 1 つだけ削除され、可用性以外の構造的な制約は存在しないということです。 操作は新しいキャラクターを導入せず、カウントを減らすだけであるため、実現可能性は完全に十分な量であるかどうかによって決まります。`l`すべてのペアリングをサポートするために存在します`t`と`e`。 

### なぜ効果があるのか

 各操作は、`t`、`e`、少なくとも 1 つ`l`。 反転ステップは、将来の有効なセグメントの形成を妨げる方法で可用性や隣接の可能性を変更せずに文字列をミラーリングするだけであるため、将来の選択を制限しません。 十分な限り`l`各ペアを固定するために存在するため、文字列のある方向でその周囲の端点をいつでも選択できます。 これにより、次の数が計算されます。`l`一致する数を超えた唯一の構造的ボトルネック`t`そして`e`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    
    cnt_t = cnt_e = cnt_l = 0
    
    for ch in s:
        if ch == 't':
            cnt_t += 1
        elif ch == 'e':
            cnt_e += 1
        elif ch == 'l':
            cnt_l += 1
    
    if len(s) == 0:
        print("YES")
        return
    
    k = min(cnt_t, cnt_e, cnt_l)
    
    if k == 0:
        print("NO")
    else:
        print("YES")

if __name__ == "__main__":
    t = int(input())
    for _ in range(t):
        solve()
```このコードは、テスト ケースごとに 1 回の線形スキャンを実行し、重要なカウントのみを抽出します。 その後、決定は一定時間の比較に縮小されます。 削除や取り消しをシミュレートする必要はありません。 

ここでよくある間違いは、反転操作を考えすぎて、方向を反転してデックを維持しようとすることです。 実現可能性の条件は、中間構成の正確な順序ではなく、十分な構造リソースが存在するかどうかのみに依存するため、これは不要です。

 ## 特殊なケース

 文字列に次のものが含まれる場合、微妙なエッジ ケースが発生します。`t`そして`e`でもいいえ`l`。 例えば、`tteee`。 アルゴリズムは正しく計算します`cnt_l = 0`、作る`k = 0`、すぐに戻ります`NO`。 これは、すべての操作に内部的な削除が必要なため、有効な削除を開始できないという事実と一致します。`l`。 

もう 1 つのケースは、次のもののみで構成される文字列です。`l`キャラクターなど`llll`。 潜在的な内部アンカーは多数ありますが、`t`または`e`境界線を形成するために。 カウンターが与えるのは、`cnt_t = cnt_e = 0`、それではまたまた`k = 0`、正しく生成`NO`。 

最後のケースは、次のような最小限の有効なトリプルです。`tle`。 ここではすべてのカウントが正確に 1 であるため、`k = 1`、アルゴリズムは受け入れます。 これは、1 回の操作で 1 ステップで文字列全体が削除されるという、唯一の意味のある基本ケースを反映しています。
