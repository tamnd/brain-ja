 ## 解決策
 ## 問題の理解

 一連のページが与えられ、各ページには表と数式という 2 種類の項目が固定数含まれています。 唯一の自由は、各ページ内でこれらの項目をどのように配置するかです。つまり、ページ内で表や数式を任意に挿入できますが、ページ間で項目を移動することはできません。 

すべてのページを連結して形成された単一の長いシーケンスを読み取っているかのように、すべてのページが順番に処理されます。 キーの制限はグローバルです。どの時点でも、それ以上の制限がある場合、`k`連続したテーブル以上`k`この連結シーケンス内に連続した数式がある場合、その配置は無効です。 重要なのは、ストリークはページ間でリセットされないため、ページの境界を越えて実行を継続できることです。 

タスクは、連結されたシーケンス全体が両方のシンボルの最大ランレングス制約を遵守するように各ページを内部的に配置する方法が存在するかどうかを判断することです。 

制約は大きく、最大で`3 * 10^5`ページと最大値`10^6`。 これにより、完全なシーケンスをシミュレートしたり、ページ内のすべての順列を試行したりするアプローチは即座に除外されます。 項目ごとに意思決定を繰り返す必要がある場合、配置ごとの線形シミュレーションでも時間がかかりすぎます。 

ページの境界に微妙な困難が現れます。 各ページを個別に最適化する貪欲な戦略は、次のページへの不可能な継続を強制するサフィックスを生成する可能性があるため、失敗します。 たとえば、あるページが表の長いブロックで終わっている場合、それぞれに交互に十分な数式があったとしても、次のページで制約を破らざるを得なくなる可能性があります。 

もう 1 つの失敗例は、ローカルでバランスのとれたページに起因します。 ページは、最適に再配置されていれば個別に「安全」である可能性がありますが、そのページが表で終わるか数式で終わるかの選択は、将来の実現可能性に影響します。 このページ間の相互依存性が問題の核心です。 

## アプローチ

 強引な解釈では、現在の一連の表と数式を追跡しながら、ページごとに有効な配置を構築しようとします。 各ページについて、カウントを尊重する可能なすべての内部調整を試みてから、終了状態を前方に伝播します。 各ページには次の内容が含まれているため、`10^6`すべての要素を列挙することは不可能であり、状態を圧縮しても、ページの開始と終了の方法が指数関数的に分岐します。 

重要な観察点は、ページ内での正確な順序は問題ではなく、テーブルと数式を最大でもサイズの塊で「使用」できるかどうかだけが重要であるということです。`k`ページ間の接続方法を制御しながら。 これにより、問題は、境界実行の拡張を強制されるテーブルまたは式の数を追跡するだけになります。 

各ページ内で、リスクを最小限に抑えたい場合は、長く連続するセグメントの作成を避ける必要があることがわかります。 最善の戦略は常に、各タイプを最大でも同じサイズのブロックに分割することです。`k`なぜなら、有効な取り決めはリスクを増大させることなくそのようなブロック分解に変換できるからです。 

次に、ページから移動するときに何が重要かを考えてみましょう`i`ページへ`i+1`。 唯一関連する状態は、現在の終了ストリークの長さとタイプです。 正確な構成を追跡する代わりに、境界を超えないようにページ内に十分な区切りを割り当てることができるかどうかだけを知る必要があります。`k`。 

これは、貪欲な実現可能性条件につながります。どの時点でも、ストリークの現在の残り容量を追跡し、オーバーフローを強制しないように次のページを配置できるかどうかをチェックします。 唯一の危険な状況は、一方のタイプが連続するページにわたって大量の質量を蓄積し、反対のタイプの十分な中断の可能性がない場合です。 

問題は、テーブルも式も、「持ち運び可能な」合計容量を決して超えないようにすることです。`k`ページ境界を越えたアクティブなセグメントごとに。 現在のストリークをどれだけ延長できるか、いつそれを破らなければならないかを維持する貪欲なスキャンで十分です。

 ## アルゴリズムのチュートリアル

 現在のストリーク タイプと、ヒットする前にそのタイプのアイテムがまだ許可されている数を維持しながら、ページを順番に処理します。`k`。 

1. 現在のストリークを空として初期化します。 概念的には、長さがゼロで固定型がないものとして扱います。 
2. 各ページについて、2 つの可能性を検討します。現在の境界で許容される内容に応じて、テーブル ストリークまたは数式ストリークのいずれかを継続します。 
3. 現在のストリーク タイプがページの主要な寄与と一致する場合、制限を超えない範囲で、そのページから可能な限り多くのアイテムを使用してストリーク タイプを拡張しようとします。`k`。 ページの残りの部分は切り替えの機会として扱われます。 
4. ページが現在のストリークとは異なるタイプを強制する場合、現在のストリークが超えないことを確認して、遷移に対して「支払う」ことができるかどうかを確認する必要があります。`k`。 存在する場合、構成は直ちに無効になります。 
5. 各ページについて、どのブロックも超過しないように、テーブルと数式のブロックの数を効果的に決定します。`k`そして、これらのブロックを整列させて、強制的な長いストリークの伝播を最小限に抑えます。 
6. ページの最後のブロックがテーブルであるか数式であるか、およびその長さに基づいて現在のストリークを更新します。 
7. 内部制約と境界制約の両方を満たすためにページを合法的に分割できない場合は、失敗を返します。 

重要な不変条件は、各ページの処理後に、構築されたシーケンスのサフィックスの有効な表現、つまり長さが最大で表または式のいずれかの単一のアクティブなストリークを維持することです。`k`。 以前のページの内部構造は、この圧縮状態を超えると無関係になります。 

正しさは、ページ内の最適な配置は、最大でも同じサイズの交互のブロックに再配置できるという事実から来ています。`k`実現可能性に影響を与えることなく。 したがって、各ページをその境界動作まで削減しても、有効な解決策は失われません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    x = list(map(int, input().split()))
    y = list(map(int, input().split()))

    # We track how many "extra" capacity remains in current streak type.
    # We store current type: 0 = none, 1 = tables, 2 = formulas
    cur_type = 0
    cur_len = 0

    for i in range(n):
        tx, ty = x[i], y[i]

        # If no active streak, we choose the larger block to start with
        if cur_type == 0:
            if tx >= ty:
                cur_type = 1
                cur_len = tx
            else:
                cur_type = 2
                cur_len = ty

            # We must ensure we can split within page
            if cur_len > k:
                # We can break into chunks, but only if opposite exists
                # If only one type exists, we must split across boundary
                cur_len = cur_len % (k + k)
                if cur_len > k:
                    cur_len = k  # we cap it conceptually
            continue

        # Try to extend current streak
        if cur_type == 1:
            # tables continue
            if tx >= ty:
                cur_len += tx
                if cur_len > k:
                    # must insert formulas to break
                    if ty == 0:
                        print("NO")
                        return
                    cur_len = ty
                    cur_type = 2
            else:
                # switch to formulas first
                if ty > k:
                    print("NO")
                    return
                cur_type = 2
                cur_len = ty

        else:
            # formulas continue
            if ty >= tx:
                cur_len += ty
                if cur_len > k:
                    if tx == 0:
                        print("NO")
                        return
                    cur_len = tx
                    cur_type = 1
            else:
                if tx > k:
                    print("NO")
                    return
                cur_type = 1
                cur_len = tx

    print("YES")

if __name__ == "__main__":
    solve()
```実装では、各ページを圧縮して、どのタイプが継続を支配するかを決定します。 の`cur_type`そして`cur_len`変数は、各ページを完全に処理した後のアクティブなストリークを表します。 

重要な考え方は、シーケンスを明示的に構築しないということです。 代わりに、可能な限り最長の実行がどのように進化するかをシミュレートするだけです。 ランが超過するたびに`k`、ページ上で利用可能な他のタイプを使用して強制的に切り替えを試みます。 ストリークを解消するのに十分な反対のタイプがページに含まれていない場合、構成は不可能になります。 

微妙な点は、アルゴリズムがページ内の正確な順序に依存していないことです。 両方の数が十分である限り、必要な「破壊ブロック」を必要な場所に配置するためにいつでも再配置できることを前提としています。

 ## 特殊なケース

 重大なエッジ ケースは、ページに 1 種類の要素しか含まれていない場合です。 その数を超えると`k`、ページ自体は、前のページまたは次のページを使用して境界を越えて分割できる場合にのみ有効です。 アルゴリズムは、ストリークを破る反対のタイプが存在しない場合、そのようなケースを正しく拒否します。 

もう 1 つのケースは、各ページが個別に安全であるが、全体としてオーバーフローを形成するページ間で繰り返し蓄積される場合です。 貪欲な追跡`cur_len`この累積が最初の違反ポイントで正確に検出されることを保証し、遅延した障害の伝播を防ぎます。
