 ## 解決策
 ## 問題の理解

 私たちには指示された構造が与えられています$N$村々。 すべての村からは、ちょうど 2 本の下り道路があります。1 つは左のラベルが付けられ、もう 1 つは右のラベルが付けられ、それぞれが何らかの (おそらく同じまたは異なる) 村を指しています。 

トレーニングセッションは開始村と整数によって定義されます$K$。 その開始点から、バルトは一定の長さのパターンに従って移動します。$4K$: 彼は左エッジを取る$K$回、右端$K$何度か、そしてまた出発$K$何度も、そしてついにまた正しくなりました$K$回。 各移動は現在の村に適用されるため、パスは出力エッジを繰り返したどることによって完全に決定されます。 

課題は以下に答えることです$10^5$このようなクエリを効率的に実行できます。各クエリには$K$と同じくらい大きい$10^9$。 

この制約により、各クエリを段階的にシミュレートすることが直ちに除外されます。 1 つのクエリには最大で次のものが必要になる場合があります$4K$移行、最悪の場合は$4 \cdot 10^9$ステップ。 それに掛けると$10^5$クエリを使用すると、直接的なシミュレーションが不可能になります。 

この構造は任意のグラフ走査ではありません。 各ノードにはちょうど 2 つの出力エッジがあるため、各クエリは左右の 2 つの決定論的関数を繰り返し適用するだけです。 

いくつかの微妙なケースが重要です。 

問題の 1 つは、左右のトランジションが短いサイクルを形成する場合です。 たとえば、ノードは両方のエッジでそれ自体にループする可能性があります。 このような場合、単純なシミュレーションは時間を無駄にしますが、それでも正しい結果が得られます。 

もう 1 つの問題は、交互パターンが固定されており、対称であることです。 セグメント間の独立性を前提とした不用意な最適化は、左右のパスが異なる方法でサイクルと交差するときに機能しなくなる可能性があります。 たとえば、左と右の両方が同じサイクルにマップされているが、エントリ ポイントが異なる場合、同期せずにそれらを個別に扱うと、状態の位置がずれる可能性があります。 

最後に、なぜなら、$K$大きいため、どのソリューションでも反復を避ける必要があります$K$直接何度も。 に線形的に依存するアプローチ$K$クエリごとに実行することは直ちに不可能です。 

## アプローチ

 直接的な総当たりアプローチは、文字通り定義に従います。 クエリごとに、シミュレーションを行います。$K$左に移動すると、$K$右に移動して、もう一度$K$左が動き、最後に$K$右に動きます。 各移動は、保存された隣接関係を使用した単一のポインター ジャンプです。 

これは問題で説明されているプロセスを正確に反映しているため、これは正しいです。 ただし、そのコストは法外です。 各クエリが実行するのは、$4K$トランジションと$K$まで$10^9$、単一のクエリでも時間制限を数桁超える可能性があります。 

重要な観察点は、順序が任意ではないということです。 それは、左右の 2 つの決定的な関数の繰り返しです。 重要なのは、段階的な軌跡ではなく、これらの関数を何度も組み合わせた結果です。 

個々の動きの観点から考えるのではなく、左と右を関数グラフとして見ます。 これらの関数を素早く繰り返し適用する必要があります。 これはバイナリ リフティングの古典的な設定です。 

すべてのノードについて、その後どこで終了するかを事前計算します。$2^j$左のアプリケーションと、その後で終了する部分を個別に$2^j$権利の申請。 これが構築されると、大量に繰り返される左または右の動きに次のように答えることができます。$O(\log K)$時間。 

各クエリは次の 4 つのブロックで構成されます。$K$左右交互に動きます。 バイナリ リフティングを使用して各ブロックの結果を計算し、ブロックを順番に連鎖させます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(QK)$|$O(1)$| 遅すぎる |
 | 最適 (バイナリ リフティング) |$O(N \log K + Q \log K)$|$O(N \log K)$| 承認済み |

 ## アルゴリズムのチュートリアル

 左と右の移動を、同じグラフ上の 2 つの独立したジャンプ関数として扱います。 

1. 左右の遷移に対するバイナリ リフティング テーブルを事前計算します。 

すべてのノードについて$v$、 店$upL[j][v]$= 後に到達したノード$2^j$左から移動します$v$、同様に$upR[j][v]$正しい動きのために。 
2. ベースレベルの初期化$j = 0$指定されたエッジを使用します。 

これにより、直接遷移が 1 ステップでエンコードされます。 
3. 合成を使用してより高いレベルを構築します。 

それぞれについて$j > 0$、 定義する$upL[j][v] = upL[j-1][ upL[j-1][v] ]$、右も同様です。 

これは適用されるため機能します$2^j$移動は 2 つの連続したブロックに等しい$2^{j-1}$動く。 
4. 各クエリについて、指定された村から開始します。 
5. 申請する$K$left は、左遷移用のバイナリ リフティング テーブルを使用して移動します。 

分解する$K$2 の累乗になり、それに応じてジャンプします。 
6. 申請する$K$right は、right テーブルを使用して結果のノードから移動します。 
7. 完全なパターンは左、右、左、右であるため、ステップ 5 と 6 をもう一度繰り返します。 

1 つのセグメントの後の状態が次のセグメントの入力になるため、各ブロックは独立しています。 

### なぜ効果があるのか

 各移動タイプは、ノードからノードへの決定論的な関数を定義します。 バイナリ リフティングでは、大きな指数を 2 のべき乗に分解することで繰り返し関数の合成を効率的に計算します。 構成プロパティにより正確性が保証されます: 適用$2^a + 2^b$ステップは適用することと同じです$2^a$その後の手順$2^b$したがって、事前計算されたジャンプは、考えられるすべてのステップ数を正確に表します。 クエリは 4 つの関数の累乗を順番に適用したものにすぎないため、これらの結果を連鎖させると、元のプロセスとの正確な同等性が保たれます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

LOG = 31  # enough for K up to 1e9

def build_up(n, nxt):
    up = [[0] * (n + 1) for _ in range(LOG)]
    for v in range(1, n + 1):
        up[0][v] = nxt[v]
    for j in range(1, LOG):
        for v in range(1, n + 1):
            up[j][v] = up[j - 1][up[j - 1][v]]
    return up

def lift(up, v, k):
    bit = 0
    while k:
        if k & 1:
            v = up[bit][v]
        k >>= 1
        bit += 1
    return v

def main():
    n = int(input())
    left = [0] * (n + 1)
    right = [0] * (n + 1)

    for i in range(1, n + 1):
        l, r = map(int, input().split())
        left[i] = l
        right[i] = r

    upL = build_up(n, left)
    upR = build_up(n, right)

    q = int(input())
    out = []

    for _ in range(q):
        v, k = map(int, input().split())
        v = lift(upL, v, k)
        v = lift(upR, v, k)
        v = lift(upL, v, k)
        v = lift(upR, v, k)
        out.append(str(v))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```この実装では、前処理とクエリ処理が明確に分離されています。 の`build_up`関数は、指定された遷移配列のバイナリ リフティング テーブルを構築します。 左端と右端の両方で再利用されるため、ロジックがコンパクトに保たれ、重複が回避されます。 

の`lift`関数は、事前計算されたテーブルに対して 2 の累乗分解を適用します。 ビットを反復処理します$k$、対応するビットが設定されている場合にのみジャンプを適用します。 これにより、バイナリ表現を明示的に構築することが回避されます。 

各クエリは 4 つのリフトされた遷移を順番に適用します。 各セグメントは前のセグメントの結果から始まるため、順序は厳密に重要です。 

よくある落とし穴は、左右を 1 つの構造に統合しようとすることです。 セグメント間で遷移関数が変化するため、これは破綻します。 それらは交換可能ではありません。

 ## 特殊なケース

 すべてのノードが左と右の両方で自分自身を指す自己ループがどこにでもあり、自明なシステムが生成されます。 どこから開始しても、何回移動しても状態は変化しません。 バイナリ リフティング テーブルはすべてのレベルでアイデンティティ マッピングに折りたたまれるため、アルゴリズムはこれを処理します。そのため、リフトされたクエリはすべて元のノードを返します。 

2 ノードのスワップ サイクルでは、左右両方のノードがスワップされ、構成の繰り返しが強調されます。 各関数は単純ですが、累乗を繰り返すとパリティ動作が正しく維持される必要があります。 繰り返しの二乗によりサイクル パリティが自然にエンコードされ、各クエリがビットのチェックに減らされるため、リフティング テーブルはこれを捉えます。$K$。 

左と右の遷移が同じノードから始まる異なるサイクルを形成する場合は、順次適用が維持されるかどうかをテストします。 各セグメントの後に現在のノードを再計算するため、状態は遷移を混合することなく、さまざまな関数グラフを通じて正しく展開されます。
