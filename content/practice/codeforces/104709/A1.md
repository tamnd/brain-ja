 ## 解決策
 ## 問題の理解

 ソース文字列とターゲット文字列が与えられます。 ソース文字列は、左から右に処理することによってターゲットに変換できます。この場合、ソース内の各文字は、それ自体の 1 つのコピー、またはそれ自体の連続する 2 つのコピーに展開されます。 文字の順序は保持され、並べ替えや削除は許可されず、複製のみが制御されます。 

タスクは、このルールに従ってソース文字列からターゲット文字列を生成できるかどうかを判断することです。 言い換えれば、ターゲットを連続したブロックに分割できるかどうかをチェックしています。各ブロックはソースの 1 文字に対応し、各ブロックの長さは 1 または 2 で、ブロック内のすべての文字は同一です。 

入力サイズは十分小さいため、リニア スキャン ソリューションで十分です。 テスト ケース全体で文字列の合計の長さが 10^5 に達した場合でも、テストごとに O(n) または全体で O(n) 戦略は安全ですが、二次関数は遅すぎます。 すべての文字で「シングル」展開と「ダブル」展開の両方を試行する単純なバックトラッキング アプローチでは、最悪の場合は指数関数的に分岐することになり、文字列の長さが数十を超えるとすぐに実行できなくなります。 

ここではいくつかの特殊なケースが重要です。 ターゲットがソースより短い場合、すべてのソース文字が少なくとも 1 つの文字を生成するため、それは不可能です。 たとえば、ソース`abc`そしてターゲット`ab`最小限の拡張でもすでに長さ 3 が生成されるため、機能しません。 もう 1 つの失敗例は、想定されるブロック内で文字が一致しない場合です。 たとえば、ソース`ab`そしてターゲット`aab`消費した後なので失敗します`a`、次のソース文字は`b`、しかし残りのターゲットはから始まります`a`。 最後に、ターゲット内のランが 2 つの同一の文字より長い場合、微妙なケースが発生します。 たとえば、ソース`a`そしてターゲット`aaa`1 つの文字は最大 2 つのコピーに展開できるため、無効です。 

## アプローチ

 ブルートフォースアプローチでは、考えられるあらゆる拡張の選択肢をシミュレートしようとします。 ソース文字列内の文字ごとに、それをターゲット内の 1 文字にマップするか 2 文字にマップするかを再帰的に決定します。 これにより、各ステップで最大 2 の分岐係数が作成され、最悪の場合は 2^n 通りの可能性が検討されます。 n が約 40 の場合でも、これはすでに遅すぎるため、実際の制約はさらに大きくなります。 

重要な観察は、構造が剛であるということです。 ソース文字列内の位置とターゲット文字列内の位置を固定すると、マッチングに曖昧さはなくなります。ターゲット内で 1 つまたは 2 つの同一の文字を使用する必要があります。 これにより、後戻りの必要がなくなります。 2 つのポインターを使用して両方の文字列を貪欲に調べ、各ソース文字をターゲット内のブロックと照合し、各ブロックの長さが 1 または 2 であることを検証できます。 

ブルート フォースはすべての長さの割り当てを探索するため機能しますが、その探索のほとんどが冗長であるため失敗します。 各ステップが局所的に制約されているという観察により、検索全体を単一の線形パスに折りたたむことができます。

 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ソース文字列用とターゲット文字列用の 2 つのポインタを維持し、展開ルールを適用しながらそれらを前方に移動します。 

1. 両方のポインタをそれぞれの文字列の先頭から開始します。 並べ替えは許可されないため、これによりソースの最初の文字がターゲットの先頭に揃えられます。 
2. ソース内の現在の文字がターゲット内の現在の文字と一致することを確認します。 一致しない場合、キャラクタのアイデンティティを変更する展開ルールがないため、変換は直ちに不可能になります。 
3. 現在のソース文字がターゲット ポインタから開始してターゲット内に連続して出現する回数を数えます。 このランレングスによって、このソース キャラクターが消費する必要がある文字数が決まります。 
4. ランレングスが 2 より大きいか 0 に等しい場合、構成は無効です。 ランが 0 の場合は不一致を意味し、ランが 2 を超える場合は、各ソース文字が最大 2 つのコピーに展開されるというルールに違反します。 
5. ソース文字を完全に処理したので、消費したランレングスだけターゲット ポインタを前方に移動し、ソース ポインタを 1 ステップだけ移動します。 
6. すべてのソース文字が処理されるまで、このプロセスを繰り返します。 最後には、ターゲットも完全に消費されなければなりません。 そうしないと、残った文字が余分な不一致の拡張を意味します。 

正確かどうかは、各ソース文字がターゲット内の連続ブロックを個別に定義し、ブロック サイズが厳密に制限されているという事実にかかっています。 

### なぜ効果があるのか

 アルゴリズムは常に、現在のソース ポインタより前のすべての文字が、サイズ 1 または 2 のターゲット文字列内の互いに素な有効なブロックに一致するという不変条件を維持します。 変換ルールにより、展開が重複せず順序が維持されることが強制されるため、次の有効なブロックは現在のターゲット位置によって一意に決定されます。 割り当てが長くても短くても、隣接関係またはブロック長の制約にすぐに違反するため、別の分割を選択することが後で有効な解決策につながる可能性はありません。 これにより、検索の必要性がなくなり、ブロックを貪欲に消費することが必要かつ十分であることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can_transform(s, t):
    i = j = 0
    n, m = len(s), len(t)

    while i < n and j < m:
        if s[i] != t[j]:
            return False

        j_start = j
        while j < m and t[j] == s[i]:
            j += 1

        run_len = j - j_start
        if run_len == 0 or run_len > 2:
            return False

        i += 1

    return i == n and j == m

def solve():
    tcs = int(input())
    for _ in range(tcs):
        s = input().strip()
        t = input().strip()
        print("YES" if can_transform(s, t) else "NO")

if __name__ == "__main__":
    solve()
```実装の中核は 2 ポインター スキャンです。 内側のループは、現在のソース キャラクタと一致しながらターゲットがどこまで拡張できるかを測定し、拡張ブロックのサイズを効果的に計算します。 ランレングスのチェックでは、各ソース文字が最大 2 つのコピーに寄与するというルールが適用されます。 

よくある落とし穴は、最後に両方の文字列が完全に消費されていることを確認するのを忘れることです。 すべての文字がローカルで一致する場合でも、ターゲット内の残りの文字は無効な追加拡張を示します。

            t = input().strip()

    solve()
    sys.stdout.seek(0)

 ## 特殊なケース

 両方の文字列の長さが 1 である最小の入力は、ベース遷移をチェックします。 もし`s = "a"`そして`t = "a"`の場合、アルゴリズムはランレングス 1 に一致し、正常に終了し、単一文字の展開が有効であることを確認します。 

ターゲットが許容範囲を超えている場合`s = "a"`そして`t = "aaa"`、早期拒絶反応を示します。 ランレングスは 3 になり、すぐに制約に違反し、アルゴリズムは続行する必要がなく false を返します。 

などの厳密な交代を伴うケース`s = "ab"`そして`t = "abab"`、実行が連続していないため失敗します。 アルゴリズムはランレングス 1 を認識します。`a`、その後、期待したときにすぐに不一致が発生します`b`しかし見つけました`a`再度、インターリーブ拡張を正しく拒否します。
