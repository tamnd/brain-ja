 ## 解決策
 ## 問題の理解

 から始めます`T`カラオケシステムがロックされる数秒前。 曲は一定時間継続して再生する必要があります`0`, そのため、アイドル時間が存在することはありません。 通常の曲が 3 曲あり、長さは異なります`A`、`B`、 そして`C`、それぞれを何度でも選択できます。 長さが固定されている特別な曲、Golden Songs もあります。`768`秒。 

ロックは正確な時間に行われます`T`。 新しい曲はロックの直前でいつでも開始できますが、クロックが到達すると`T`、それ以上曲を選択することはできません。 現在再生中の曲は終了できるため、最後の曲は他の曲よりもはるかに長いため、通常はゴールデン ソングにする必要があります。 

課題は、歌唱時間を最大化することです。 つまり、ゴールデン ソングの前に通常の曲を配置して、ゴールデン ソングの開始時間ができるだけ遅くなるようにしながらも、ゴールデン ソングの開始時間を厳密に短くする必要があることを意味します。`T`。 

の最大値`T`だけです`18000`、それぞれの普通の曲が間にありますが、`180`そして`300`秒の長さ。 シーケンスの数は再生される曲の数に応じて指数関数的に増加するため、これにより、考えられるすべての曲のシーケンスを試すことが直ちに除外されます。 一方で、制限時間は十分に小さいため、どのアルゴリズムも次の値に比例します。`T`簡単に十分に高速です。 

簡単な間違いの 1 つは、ゴールデン ソングが時間に開始される可能性があることを忘れることです。`0`。 考慮する```
3 200 190 180
```ロックの前には普通の曲は合いません。 正しい答えは、`768`, Golden Songsはすぐに始められるからです。 

もう 1 つの微妙なケースは、残り時間を正確に埋めることができない場合です。 例えば、```
400 180 200 300
```最良の通常のプレフィックスが持続する`200`秒。 ゴールデンソングは時間に始まります`200`、合計を与えます`968`。 時間まで待っています`399`アイドルタイムは禁止されているので不可能です。 

off-by-one エラーの 3 番目の原因は、ロック ルールです。 仮定する```
600 300 200 180
```二`300`- 2 番目の曲は時間通りに終了します`600`。 画面がすでにロックされているため、Golden Songs を開始できません。 最も有効な選択肢は、`200`-2番目の曲に続いて2曲目`180`・2曲目、到達時間`560`、それからゴールデンソングを始めます。 答えは`1328`、 ない`1368`。 

## アプローチ

 直接のブルート フォース検索により、合計時間が以下の通常の曲の考えられるすべてのシーケンスが生成されます。`T`。 これ以上曲を追加できない場合は、現在の継続時間がゴールデン ソングの開始時間として扱われます。 すべての位置には 3 つの選択肢があるため、シーケンスの数はおおよそ次のように増加します。`3^k`、 どこ`k`通常の再生曲数です。 曲の長さについて`180`秒、`k`およそに到達できる`100`、検索が完全に不可能になります。 

重要な観察は、累積時間のみが重要であるということです。 同じ経過時間につながる曲の順序は、その後の選択には影響しません。 これは、問題が実際にどの時刻を下回るかを尋ねていることを意味します`T`繰り返し追加することで到達可能です`A`、`B`、 または`C`。 

これは、経過時間に対する動的プログラミングを即座に示唆します。 させて`dp[t]`正確に支出できるかどうかを示す`t`普通の曲だけを使った秒数。 まずは`dp[0] = True`。 到達可能な時間になると、3 つの曲の長さのいずれかを加算すると、到達可能な時間がさらに短くなります。`T`。 

すべての到達可能な時間を計算した後、厳密に以下の到達可能な最大値を見つけるだけです。`T`。 ゴールデンソングはそこから始まる、答えはその時間プラス`768`。

 ## アルゴリズムのチュートリアル

 1. 4 つの整数を読み取ります`T`、`A`、`B`、 そして`C`。 
2. ブール配列を作成する`dp`長さの`T`。 索引`i`正確かどうかを表します`i`ロック前に通常の曲を数秒間再生できます。 
3.セット`dp[0] = True`普通の曲を使わないことはいつでも可能だからです。 
4. から到達可能な時間ごとにスキャンします。`0`に`T - 1`。 いつでも`dp[i]`が正しい場合は、通常の 3 つの曲の長さをそれぞれ追加してみてください。 もし`i + song < T`、その新しい時刻を到達可能としてマークします。 
5. 到達可能なすべての状態を処理した後、アレイをもう一度スキャンし、到達可能な最大時間を記録します。 
6. 最大到達可能時間を加えた時間を出力します。`768`、ゴールデンソングは通常の曲の直後に始まり、常に完全に再生されるためです。 

### なぜ効果があるのか

 動的プログラミングの不変条件は、処理後の到達可能な時間です。`x`、通常の曲を 1 つ追加してそのスケジュールを延長することで取得できるたびに、到達可能とマークされます。 すべてのシーケンスは時間とともに始まるので、`0`すべてのシーケンスは、以下の有効な経過時間ごとに 1 つの曲を繰り返し追加することによって構築されます。`T`ついに発見される。 

逆に、状態は、すでに有効な状態に 1 つの正当な曲の長さを追加することによってのみ作成されるため、マークされたすべての状態は実際の曲のシーケンスに対応します。 到達可能な最大時間は、ゴールデン ソングが合法的に開始される可能性のある最も遅い瞬間であるため、その固定期間を追加すると、最大合計歌唱時間が生成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

T, A, B, C = map(int, input().split())

dp = [False] * T
dp[0] = True

songs = (A, B, C)

for t in range(T):
    if not dp[t]:
        continue
    for s in songs:
        nt = t + s
        if nt < T:
            dp[nt] = True

best = 0
for t in range(T):
    if dp[t]:
        best = t

print(best + 768)
```動的プログラミング配列には、ロックまでの到達可能な経過時間が正確に保存されます。 遷移ごとに少なくとも時間が増加するため、`180`秒間、サイクルは不可能であり、単純な左から右へのスキャンで十分です。 

比較には、`nt < T`、 ない`<= T`。 ゴールデンソングを時間通りに開始`T`その瞬間に画面がロックされるため禁止されています。 これは、この問題で最もよくある 1 つ違いの間違いです。 

最終スキャンでは、到達可能な最大値が維持されるだけです。 普通の曲が全く合わない場合は、`dp[0]`は true なので、答えは自然に次のようになります。`768`。

## テストケース```python
import sys, io

def solve():
    input = sys.stdin.readline

    T, A, B, C = map(int, input().split())

    dp = [False] * T
    dp[0] = True

    for t in range(T):
        if not dp[t]:
            continue
        for s in (A, B, C):
            if t + s < T:
                dp[t + s] = True

    best = 0
    for t in range(T):
        if dp[t]:
            best = t

    print(best + 768)

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    out = io.StringIO()
    old = sys.stdout
    sys.stdout = out
    solve()
    sys.stdout = old
    return out.getvalue().strip()

# provided samples
assert run("601 180 210 300\n") == "1368", "sample 1"
assert run("3 200 190 180\n") == "768", "sample 2"

# custom cases
assert run("180 180 180 180\n") == "768", "cannot start ordinary song at T"
assert run("181 180 180 180\n") == "948", "ordinary song fits once"
assert run("540 180 180 180\n") == "1128", "exactly reaches T, not allowed"
assert run("18000 300 300 300\n") == "18768", "maximum input"
```| テスト入力 | 期待される出力 | 検証内容 |

 ## 特殊なケース

```ダイナミック プログラミング テーブルのマークのみ`0`通常の曲はすべて利用可能な時間を超えるため、到達可能となります。 アルゴリズムは戻ります`0 + 768 = 768`、ゴールデンソングをすぐに開始する必要があることを正しく認識しています。

```到達可能な時間は、`0`、`180`、`200`、`300`、 そして`380`。 時間`400`厳密には以下ではないため、到達できません`T`。 アルゴリズムが選択するのは、`380`、生産`1148`、または、`200`はさまざまな曲の長さで到達可能ですが、代わりにそれを正しく選択します。 到達可能なすべての状態が中断のない再生に対応するため、アイドル待機が発生することはありません。
