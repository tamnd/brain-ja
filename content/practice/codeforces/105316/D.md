 ## 解決策
 ## 問題の理解

 ラベル付き文字列のコレクションを維持します。 各文字列はクエリによって導入され、その瞬間から、挿入された時点と同じ識別子を持つオブジェクトのように動作します。 各文字列と一緒に数値を保存します。 時間の経過とともに、文字列が削除され、これらの挿入識別子の範囲の値が上書きまたは増加される可能性があります。 

最も難しい操作は、パターン文字列 S に対するクエリです。値が指定された数値範囲内にある、現在アクティブなデータベース文字列と一致する S の部分文字列がいくつあるかを数えなければなりません。 部分文字列は出現ごとに 1 回カウントされるため、重複した出現や繰り返しの出現がすべて影響します。 

この構造は 2 つの独立した次元で動的です。 1 つの次元は時間であり、広告掲載オーダーによってインデックスが付けられます。 もう 1 つは値であり、範囲の割り当てと範囲の追加によって継続的に変更されます。 クエリは両方の次元を組み合わせて、時間制約によるアクティブな文字列の選択と値制約によるフィルタリングを行うと同時に、それらをクエリ文字列の部分文字列として照合します。 

この制約により、すべてのアクティブな文字列に対するクエリごとのスキャンが強制的に行われなくなります。 最大 200,000 の操作と合計文字列長も 200,000 で制限されるため、クエリごとに部分文字列の一致を再計算するソリューションはすぐに時間制限を超えてしまいます。 同様に、文字列ごとの部分文字列の直接リストを維持することは、二次関数の爆発により実行不可能になります。 

部分文字列の重複や挿入の繰り返しによって、微妙なエッジ ケースが発生します。 

たとえば、文字列を挿入すると、`"a"`、`"a"`、 そして`"aa"`、次にクエリ`"aa"`完全な値の範囲では、両方の出現が`"a"`部分文字列と単一の`"aa"`貢献する。 部分文字列または文字列の単純な重複排除では、不正確なカウントが生成されます。 

もう 1 つの落とし穴は、インデックスの挿入による削除です。 削除は現在の位置ではなく i 番目の挿入操作を参照するため、削除後に配列を圧縮する実装ではインデックスの位置がずれ、将来の範囲の更新が暗黙的に中断されます。 

## アプローチ

 強引な解釈は簡単です。 すべてのアクティブな文字列をその挿入インデックスと値とともに保存します。 タイプ 5 クエリの場合、すべてのアクティブな文字列を反復処理し、その値が範囲内にあるかどうかを確認し、範囲内にある場合は、その文字列が S の部分文字列として出現するかどうかをテストします。部分文字列のチェックは、単純なスキャンまたはパターンごとの文字列一致アルゴリズムを使用して実行できます。 

これは正しく動作しますが、遅すぎます。 格納された文字列ごとに KMP のような効率的な部分文字列マッチングを使用したとしても、各クエリは依然としてすべてのアクティブな文字列に影響します。 最大 200,000 回の挿入では、最悪の場合、約 200,000 × 200,000 回の操作にまで縮退しますが、これは不可能です。 

重要な観察点は、格納された文字列のセットは、挿入後の内容が静的であるということです。 値とアクティブなステータスのみが変化します。 これは、文字列のマッチングを動的フィルタリングから分離することを示唆しています。 

クエリごとにデータベース文字列を反復処理する代わりに、プロセスを逆にします。S の部分文字列を考慮し、それらがデータベースに存在するかどうかを尋ねます。 長さの合計は小さいため、S のすべての部分文字列を列挙し、それらを辞書エントリにマッピングできます。 

部分文字列のアイデンティティが修正されると、問題は、文字列ごとに、範囲の割り当てと追加の下でアクティブな値の動的なマルチセットを維持し、範囲内に含まれる値の数を数えることができるようになります。 これは、範囲の追加、範囲の割り当て、および範囲カウントのクエリをサポートする遅延伝播を備えた古典的なセグメント ツリーです。 

最後のソリューションは、文字列のハッシュ化または部分文字列のトライベースのインデックス付けを、文字列 ID によってグループ化された値に対するダイナミック レンジ データ構造と組み合わせます。

 | ブルートフォース | O(Q × アクティブな文字列の合計 × | S | ) |
 | 最適 | O((Σ | S | + Q) log Q) |

 ## アルゴリズムのチュートリアル

 1. 挿入された各文字列に、その挿入時間に等しい一意の識別子を割り当てます。 その内容と、現在のアクティブなステータスへのポインタを保存します。 
2. 開始位置と終了位置を列挙することにより、挿入されたすべての文字列のすべての部分文字列を合計 O(2 × 10^5) 時間かけて事前計算します。 各部分文字列をハッシュ テーブル マッピングの部分文字列→それを含む文字列 ID のリストに挿入します。 これにより、部分文字列から候補文字列への逆インデックスが構築されます。 
3. 各文字列 ID について、その現在の値を維持します。 また、範囲追加、範囲割り当て、および範囲カウントをサポートする挿入インデックス上のグローバル セグメント ツリーを維持します。 各ノードは、その範囲内の特定の値分布を持つアクティブな文字列の数に関する集約情報を保存します。 
4. タイプ 1 クエリの場合、文字列をアクティブ セットに挿入し、その値をセグメント ツリーの挿入位置に配置します。 
5. タイプ 2 クエリの場合は、セグメント ツリー内の文字列の位置を削除またはマークすることによって文字列を非アクティブ化し、クエリに寄与しなくなるようにします。 
6. タイプ 3 クエリの場合、セグメント ツリー内のインデックス L ～ R に範囲割り当てを適用し、遅延伝播を使用してその範囲内のすべての値を x に設定します。 
7. タイプ 4 クエリの場合、セグメント ツリー内のインデックス L から R に範囲加算を適用し、格納されている値をそれに応じて更新します。 
8. パターン S および範囲 [L, R] を持つタイプ 5 クエリの場合、S のすべての部分文字列を列挙します。各部分文字列について、ハッシュ マップから候補文字列 ID を取得し、各候補について、それが現在アクティブであるかどうか、およびその値が [L, R] にあるかどうかを確認します。 すべての有効な出現回数を累積します。 

これが機能する理由は、パターンの部分文字列と格納された文字列の間の高価なマッチングが事前計算された構造を通じてのみ行われ、値のフィルター処理が対数更新とクエリをサポートする構造に委任されるためです。

正確性が不変であるということは、セグメント ツリーはいつでも、すべてのアクティブな文字列の正確な現在値をその挿入インデックスに格納するということです。 遅延操作では、範囲の割り当てによって以前の追加が上書きされ、保留中の割り当てがない場合には範囲の追加が正しく構成されるため、一貫性が維持されます。 したがって、すべてのクエリで値の正確なスナップショットが表示されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    ops = []
    strings = []
    values = []
    alive = []

    for _ in range(q):
        parts = input().split()
        ops.append(parts)
        if parts[0] == '1':
            strings.append(parts[1])
            values.append(int(parts[2]))
            alive.append(True)

    n = len(strings)

    # Build substring index (naive but total length small)
    substr_map = {}
    for i, s in enumerate(strings):
        seen = set()
        for a in range(len(s)):
            cur = []
            for b in range(a, len(s)):
                cur.append(s[b])
                sub = ''.join(cur)
                if sub not in seen:
                    seen.add(sub)
                    if sub not in substr_map:
                        substr_map[sub] = []
                    substr_map[sub].append(i)

    import bisect

    # active set values
    active = [False] * n

    def get_active_values(ids):
        res = []
        for i in ids:
            if active[i]:
                res.append(values[i])
        return res

    for op in ops:
        if op[0] == '1':
            pass
        elif op[0] == '2':
            idx = int(op[1]) - 1
            active[idx] = False
        elif op[0] == '3':
            L, R, x = map(int, op[1:])
            for i in range(L-1, R):
                if i < n and active[i]:
                    values[i] = x
        elif op[0] == '4':
            L, R, x = map(int, op[1:])
            for i in range(L-1, R):
                if i < n and active[i]:
                    values[i] += x
        else:
            S, L, R = op[1], int(op[2]), int(op[3])
            ans = 0
            seen_sub = set()
            for a in range(len(S)):
                cur = []
                for b in range(a, len(S)):
                    cur.append(S[b])
                    sub = ''.join(cur)
                    if sub in seen_sub:
                        continue
                    seen_sub.add(sub)
                    if sub in substr_map:
                        for i in substr_map[sub]:
                            if active[i] and L <= values[i] <= R:
                                ans += 1
            print(ans)

if __name__ == "__main__":
    solve()
```実装は反転のアイデアに直接準拠しています。 挿入された各文字列のすべての部分文字列を構築し、ハッシュ マップでインデックスを付けます。 これにより、クエリ タイプ 5 はすべてのデータベース文字列のスキャンを回避し、代わりに関連する候補に直接ジャンプできます。 

アクティブなステータスは個別に追跡されるため、削除では部分文字列インデックスを変更せずにコントリビューションを無効にするだけです。 

ここではわかりやすくするために範囲更新を単純に処理しますが、完全に受け入れられたソリューションでは、これをセグメント ツリーまたはバランスのとれた構造に置き換えて対数更新をサポートします。 

部分文字列列挙では、文字列ごとにローカル重複排除セットを使用して、同じソース文字列から重複した部分文字列が複数回挿入されることを回避します。 

## 実用的な例

 3 つの挿入を含む単純化されたシーケンスを考えてみましょう。`"a"`値が 5 の場合、`"aa"`値が 3 の場合、および`"b"`値は 7 です。すべてがアクティブであると仮定します。 

に関する質問`"aa"`値の範囲が [3, 5] の場合、部分文字列が生成されます`"a"`、`"a"`、 そして`"aa"`。 

| 部分文字列 | マッチ | 値のチェック | 貢献 |
 | --- | --- | --- | --- |
 | "a" | 文字列 0、文字列 1 | 5、3 | 2 |
 | "ああ" | 文字列 1 | 3 | 1 |

 結果は 3 です。 

ここで、最初の文字列を削除し、すべての文字列の値を 2 ずつ増やすとします。状態は次のようになります。`"aa" → 5`、`"b" → 9`。 

に関する質問`"aa"`[4, 6] ではカウントのみが行われるようになりました`"aa"`一度、部分文字列のインデックス付けを変更せずに、削除と更新が将来のクエリに正しく影響することを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(Σ | S |
 | スペース | O(Σ | S |

 これは非常に小さな定数の場合にのみ許容され、実際に意図された解決策は、単純な部分文字列の列挙と線形スキャンを最適化された構造に置き換え、複雑さをおよそ O((Σ|S| + Q) log Q) まで下げます。 この制約により、文字列の合計の長さが小さくなり、部分文字列の前処理が可能になりますが、動的更新には対数処理が必要になります。 

小さい合計文字列サイズと多数の操作の組み合わせが中心的な設計機能です。前処理は文字列構造を処理し、オンライン構造は値のダイナミクスを処理します。

 ## 特殊なケース

 重要なエッジ ケースは、単一の文字列内で繰り返される部分文字列です。 たとえば、`"aaa"`トリプルカウントしてはいけません`"a"`部分文字列の出現ごとに一意の文字列 ID のみを考慮する場合は、同じ文字列から。 このアルゴリズムは、前処理中に部分文字列を重複排除することで、文字列ごとの二重カウントを回避します。 

もう 1 つの特殊なケースは、インデックスの挿入による削除です。 挿入すると`"a"`、`"b"`、`"c"`次に、2 番目の挿入のみを削除します。`"b"`そのうちに消えるはずだ`"a"`そして`"c"`影響を受けません。 これは、ストレージを圧縮するのではなく、挿入インデックスごとに直接アクティブなフラグを保持することで処理されます。 

範囲の更新が複数回重複することも混乱を引き起こす可能性があります。 加算中に単純に値を上書きすると、以前の増分が失われます。 対象のモデルには蓄積が必要なため、更新を正しい順序で適用する必要があります。 これが、適切なソリューションが遅延伝播またはバランスの取れた構造を使用して、操作の構成可能性を維持する理由です。
