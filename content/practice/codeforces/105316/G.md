 ## 解決策
 ## 問題の理解

 複数の独立したテスト ケースが与えられます。 各テストケースには、$n$ロッカーと$q$レンタルリクエスト。 リクエストごとに 1 つのロッカーが修正されます$x$そして時間間隔$[l, r]$、そのロッカーを意味します$x$その間隔全体を通して占有されます。 

2 つのリクエストが同じロッカーを参照し、時間間隔がいずれかの時点で重なっている場合、2 つのリクエストは競合します。 目的は、各ロッカーについて、そのロッカーに割り当てられた残りのすべての間隔がペアごとに素になるように、最大​​ 1 つのリクエストを削除できるかどうかを確認することです。 

したがって、問題は実際にはロッカーごとのローカルな一貫性に関するものです。すべてのロッカーにわたって 1 つのグローバル インターバルをオプションで削除した後、各ロッカーには個別に重複するインターバルが含まれていてはなりません。 

制約は小さく、$n, q \le 1000$テスト ケースごとの値とテスト全体の合計も 1000 で制限されます。これは、$O(q^2)$あるいは$O(q \log q)$テストケースごとのソリューションで十分です。 立体的以上のものは不要です。 

素朴な誤解は、問題をグローバルに間隔を選択するものとして扱うことです。しかし、全体で 1 つのリクエストしか削除できないという事実を除いて、ロッカーは独立しています。 この結合が重要な難点です。 

競合が複数のロッカーに分散している場合、微妙なエッジケースが発生します。 たとえば、ロッカー 1 に 2 つの重複する間隔があり、ロッカー 2 にも 2 つの重複する間隔がある場合、1 つのリクエストを削除すると 1 つのロッカーは修正されますが、別の状況が中断されるか、別の競合が未解決のままになる可能性があります。 もう 1 つの注意が必要なケースは、単一のリクエストがそのロッカー内の複数の競合に関与している場合です。つまり、リクエストを削除すると複数の重複が同時に解決されることになります。 

小さな説明的な例:

 入力:```
1
2 3
1 1 5
1 2 6
2 1 10
```ここでは、ロッカー 1 には重複する間隔がありますが、ロッカー 2 はすでに有効です。 最初の 2 つのリクエストのいずれかを削除するとすべての競合が解決されるため、出力は YES になります。 

別の例:```
1
1 3
1 1 3
1 2 4
1 3 5
```ここで、単一の間隔を削除しても、残りの 2 つの間隔の間に重複が残るため、答えは NO です。 

## アプローチ

 「削除リクエストは 1 つまで」という条件を無視すると、問題は単純になります。ロッカーごとに、間隔を開始時間で並べ替え、重複が存在するかどうかを確認します。 これはで動作します$O(q \log q)$。 

問題は、単一の削除をグローバルに許可することに起因します。 強引なアイデアは、各リクエストを 1 つずつ削除して、残りのシステムが有効かどうかを確認することです。 候補者を削除するたびに、すべてのロッカーの重複がないか再チェックします。 各小切手にかかる費用$O(q \log q)$したがって、全体的な複雑さは次のようになります。$O(q^2 \log q)$、それは周りにあります$10^6 \cdot 10^3$テスト全体で最悪の場合、まだ境界線にありますが、概念的には不要です。 

もっと鋭い観察が必要です。問題の構造はロッカーごとにローカルであり、各ロッカーは独立して一連の競合するペアを生成します。 ロッカーごとにすべての間隔をマージして並べ替えると、すべての競合を特定できます。 重要な洞察は、解決策が存在する場合、1 つの間隔を削除した後、すべてのロッカーで競合がなくなる必要があるということです。 つまり、すべてのロッカーにわたるすべての競合は、1 回の間隔で削除することで「カバー」する必要があります。 

したがって、問題をロッカーごとにすべての競合ペアを特定し、削除によってすべての競合が解消される間隔が最大 1 つ存在するかどうかを確認することに集約します。 ペアを明示的に列挙する代わりに、並べ替えられたリスト内の各重複が 2 つの区間のいずれかへの依存関係を生成することを観察します。 すべての競合を「カバー」するために 2 つ以上の個別の間隔が必要な場合、答えは不可能です。 

これは古典的な削減につながります。各ロッカーは独立して一連の競合するペアに寄与し、各インターバルがオーバーラップの解消に関与した回数を追跡します。 競合がゼロであれば完了です。 多数の競合がある場合は、削除によってすべての競合が解決される単一の間隔が存在するかどうかを確認します。 

効率的な方法は、各ロッカーを処理し、その間隔を並べ替え、競合に関係する「悪い」間隔を記録しながら重複を検出することです。 各間隔が参加する競合エッジの数のグローバル頻度カウントを維持します。最後に、単一の間隔を削除することですべての競合が解消されるかどうかを確認します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ブルート フォース (各リクエストを削除してみてください) |$O(q^2 \log q)$|$O(q)$| 遅すぎる |
 | ロッカーごとにグループ化 + シングルパスのオーバーラップ追跡 |$O(q \log q)$|$O(q)$| 承認済み |

 ## アルゴリズムのチュートリアル

 私たちはロッカーごとにグループ化されたインターバルのリストを管理しています。 次に、ソート後に各グループを個別に処理します。 

1. すべてのリクエストをロッカー インデックスごとにグループ化します。 重複は同じロッカー内でのみ問題となるため、これにより競合が独立したリストに分離されます。 
2. ロッカーごとに、開始時間で間隔を並べ替えます。 並べ替えにより、連続する間隔の間に重複が必ずこの順序で現れることが保証されるため、競合を見逃すことはありません。 
3. ソートされたリストをスキャンし、現在「アクティブ」なエンドポイントの中で最も右のエンドポイントとの間隔を維持します。 開始位置がアクティブ範囲内にある間隔が見つかると、重複が検出されます。 
4. 2 つの間隔の間に重複が見つかった場合は常に、インデックスのグローバル カウンタをインクリメントすることによって、両方の間隔を「競合中」として記録します。 これは、どちらかの間隔を削除すると、その特定の競合が解決される可能性があるという事実をモデル化しています。 
5. すべてのロッカーに対してこのプロセスを継続し、間隔ごとの競合参加数を蓄積します。 
6. すべてのロッカーを処理した後、競合カウントがゼロ以外の間隔がいくつあるかを数えます。 この数値がゼロの場合、システムはすでに有効です。 正確に 1 つの場合、その間隔を削除するとすべてが解決されます。 複数ある場合、1 回の削除ですべての競合を修正することはできないため、回答は不可能です。 

このチェックの背後にある理由は、すべての競合は削除された間隔で「カバー」される必要があるということです。 すべての競合エッジをカバーするために複数の間隔が必要な場合、単一の削除は成功しません。 

### なぜ効果があるのか

 各競合は、同じロッカー内の 2 つの間隔間の重複に対応します。 有効な解決策では、そのような重複ペアごとに少なくとも 1 つのエンドポイントを削除する必要があります。 これにより、各間隔が参加する競合をカバーするセットカバー問題が発生します。選択できる間隔は最大 1 つであるため、実現可能性は、すべての競合ペアが共通のエンドポイント間隔を共有しているかどうかを確認することになります。 そうでない場合は、少なくとも 2 つの異なる間隔が必要となり、回答は不可能になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, q = map(int, input().split())
        by_lock = [[] for _ in range(n + 1)]
        
        for i in range(q):
            x, l, r = map(int, input().split())
            by_lock[x].append((l, r, i))
        
        bad = [0] * q
        total_conflicts = 0
        
        for x in range(1, n + 1):
            arr = by_lock[x]
            if not arr:
                continue
            arr.sort()
            
            # track current rightmost interval in active overlap
            cur_l, cur_r, cur_i = arr[0]
            
            for j in range(1, len(arr)):
                l, r, i = arr[j]
                if l <= cur_r:
                    # overlap detected between cur_i and i
                    bad[cur_i] += 1
                    bad[i] += 1
                    total_conflicts += 1
                    if r > cur_r:
                        cur_l, cur_r, cur_i = l, r, i
                else:
                    cur_l, cur_r, cur_i = l, r, i
        
        cnt = sum(1 for x in bad if x > 0)
        print("YES" if cnt <= 1 else "NO")

if __name__ == "__main__":
    solve()
```競合がロッカーをまたがることは決してないため、コードは最初にリクエストをロッカーごとにグループ化します。 各ロッカー内で開始時間で並べ替えることにより、リニア スキャンで重複を効率的に検出できます。 変数`cur_r`現在のアクティブな間隔の右端を追跡します。 前または後に始まる任意の間隔`cur_r`重なり合う。 

重複が見つかるたびに、参加している両方の間隔が「不良」としてマークされます。これは、これらの間隔を削除すると、少なくとも 1 つの競合が解決される可能性がある候補であることを意味します。 すべてのロッカーを処理した後、少なくとも 1 つの競合に含まれる個別の間隔がいくつあるかを数えます。 このような間隔が複数存在する場合、単一の削除ではすべての重複を除去することはできません。 

微妙な点は、複数の間隔が競合に関係しているかどうかだけを知る必要があるということです。 残りの競合では少なくとも 1 つのエンドポイントを削除する必要があるため、それ以上の正確なオーバーラップ構造は必要ありません。

 ## 特殊なケース

 主なエッジケースは、競合が異なるロッカーに分散しているにもかかわらず、唯一の共通の「解決手段」として単一の間隔を共有する場合です。 このアルゴリズムは、競合への参加をロッカーごとではなくグローバルに集約するため、これを処理します。 

もう 1 つのケースは、重複がまったくない場合です。 不良カウンタはゼロのままで、アルゴリズムは削除を必要とせずに正しく YES を出力します。 

3 番目のケースは、1 つのロッカー内で重複するインターバルの長いチェーンであり、すべてのインターバルが少なくとも 1 つの競合に関与します。 これにより、複数の不正な間隔が生成され、単一の削除ではすべての重複を解消できないため、正しく NO が強制されます。
