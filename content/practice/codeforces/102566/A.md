 ## 解決策
 ## 問題の理解

 私たちには一連の列車が与えられており、各列車は連続した時間間隔で駅で利用できます。 物乞いは、時刻 0 から時刻 d までの勤務期間全体を電車内で過ごさなければなりません。 一人の乞食は、ある列車が出発し、別の列車が到着すると、瞬時に別の列車に移動できるため、乞食のスケジュールは、ある列車間隔の終わりが次の列車の始まりと一致する一連の列車間隔です。 

目標は、同時に働ける乞食の数を最大化することです。 物乞いの二人が同じ電車に乗ることはできませんし、同時に乗り換えることもできません。ホームで出会うことになるからです。 これは、すべての列車は最大でも 1 人の乞食に属することができ、異なる乞食は完全に別の列車チェーンを使用する必要があることを意味します。 

入力には複数のテスト ケースが含まれています。 各テスト ケースでは、稼働日の長さ d と n 個の列車間隔のリストが提供されます。 出力は、時刻 0 から時刻 d までの、競合せずに形成できる完全なスケジュールの最大数です。 

d の小さな値が、解決策を形作る重要な制限となります。 異なる時点は最大 200 ありますが、列車の数は 20,000 に達する可能性があります。組み合わせの数が指数関数的に増加するため、考えられるすべての列車グループを試行するアプローチは不可能です。 n が大きい場合、多くの可能なスケジュールを個別にチェックするだけでも時間がかかりすぎます。 時間の次元は十分に小さいため、時点にわたるグラフを構築するのが実用的です。 

いくつかの詳細により、単純な実装が壊れる可能性があります。 0 から 5 までの 1 つの列車を考えてみましょう。```
1
5 1
0 5
```答えは 1 です。なぜなら、1 人の乞食がその列車を全期間利用できるからです。 トレイン間の遷移のみをカウントするアプローチでは、スイッチがないため、誤って 0 が返される可能性があります。 

もう 1 つの重要なケースは、複数の同一の列車です。```
1
3 3
0 3
0 3
0 3
```答えは 3 です。3 人の物乞いはそれぞれ 1 つの異なる列車に泊まることができます。 同一の間隔を重複として扱い、1 つだけを保持すると、有効なスケジュールが失われます。 

3 番目のケースは、中間時点での大きなオーバーラップです。```
1
4 4
0 2
0 2
2 4
2 4
```答えは 2 です。2 人の物乞いは、独立して 2 つの完全な道をたどることができます。 最も長く見えるトレインを常に選択する貪欲なアプローチでは、別の有効なパスが必要とするトレインを誤って消費してしまう可能性があります。 

## アプローチ

 直接的なアプローチは、あらゆる可能な乞食スケジュールを構築しようとすることです。 スケジュールは、時刻 0 に始まる列車から始まり、時刻 d に終了する列車で終わる、列車を通る経路です。 1 つのスケジュールを見つけたら、その列車を削除して再度検索します。 有効なソリューションの定義はまさに重複しないパスの集合であるため、考えられるすべての選択肢を検討した場合、これは正しいことになります。 問題は、可能なパスの数が膨大であることです。 列車が 20,000 ある場合、可能な組み合わせの数は指数関数的に増加する可能性があり、このアプローチは使用できなくなります。 

問題の構造は、個々の乞食ではなく時点に注目することを示唆しています。 すべての列車間隔は、開始時刻から終了時刻までの有向エッジとして見ることができます。 物乞いの完全な旅は、ノード 0 からノード d までのパスになります。 2 人の物乞いが同じ列車を利用することはできないため、各端の定員は 1 人です。 切り替え中に合流できないため、複数のパスは中間時点を共有できません。 これはまさに最大流量の問題であり、列車の使用と切り替え場所の両方を制限する必要があります。 

スイッチング制限をモデル化するには、ノードが 2 つのノードに分割されるたびに行います。 時点に入るエッジとそこから出るエッジは、容量 1 の接続を通過する必要があります。 これにより、交換のためにそのステーションに居るのは 1 人の物乞いだけになります。 例外は時間 0 と時間 d で、任意の数のベガーが開始または終了する可能性があるため、これらのノードにはこの制限は必要ありません。 

d が最大 200 であるため、結果のグラフにはノードが約 400 しかありません。ディニックのアルゴリズムは、トレイン エッジが多くても十分に高速です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 列車本数の指数関数的増加 | O(n) | 遅すぎる |
 | 時間ごとの最大流量グラフ | O(V²E) とディニック | O(V + E) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 瞬間を表すグラフを作成します。 0 から d までの各時間値がグラフの位置になります。 すべての列車間隔 [x, y] に対して、時刻 x から時刻 y までの容量 1 の有向エッジを追加します。 この端は、この列車を一人の乞食が利用できるという事実を表しています。 
2. すべての中間時点 t (0 < t < d) を入力ノードと出力ノードに分割します。 容量 1 の入力側から出力側にエッジを追加します。 このエッジはその瞬間のプラットフォームを表しており、2 人の物乞いが同時にそこに切り替えることを防ぎます。 
3. トレインのエッジを分割ノードに正しく接続します。 時刻 t に出発する列車は t の下り側から出発し、時刻 t に到着する列車は t の上り側で終了します。 任意の数の物乞いが時間 0 に開始し、時間 d に終了する可能性があるため、開始と終了の瞬間は無制限に保たれます。 
4. 時間 0 を表すソースから時間 d を表すシンクまで、最大流量アルゴリズムを実行します。 フローの量は、独立した乞食スケジュールの最大数です。 

これが機能する理由は、流れのすべての単位が列車を通過する 1 つの完全なパスに対応しているためです。 定員 1 の列車エッジにより、2 つのフロー ユニットが同じ列車に乗車することが防止され、定員 1 の中間時間エッジにより、列車の乗り換え中に 2 つのフロー ユニットが合流することが防止されます。 すべての有効な物乞いのセットはまさにそのようなフローを作成し、すべての有効なフローは有効な物乞いのセットを記述します。 

不変条件は、フロー アルゴリズムの各拡張後に、フローのすべての単位がすでに競合のないスケジュールの部分的な集合を表すということです。 パスの増強は利用可能な残存容量のみを使用するため、最終的な最大流量に無効なオーバーラップを含めることはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Dinic:
    def __init__(self, n):
        self.n = n
        self.g = [[] for _ in range(n)]

    def add_edge(self, u, v, c):
        self.g[u].append([v, c, len(self.g[v])])
        self.g[v].append([u, 0, len(self.g[u]) - 1])

    def bfs(self, s, t):
        self.level = [-1] * self.n
        q = [s]
        self.level[s] = 0
        for u in q:
            for v, c, _ in self.g[u]:
                if c and self.level[v] == -1:
                    self.level[v] = self.level[u] + 1
                    q.append(v)
        return self.level[t] != -1

    def dfs(self, u, t, f):
        if u == t:
            return f
        while self.it[u] < len(self.g[u]):
            e = self.g[u][self.it[u]]
            v, c, rev = e
            if c and self.level[v] == self.level[u] + 1:
                pushed = self.dfs(v, t, min(f, c))
                if pushed:
                    e[1] -= pushed
                    self.g[v][rev][1] += pushed
                    return pushed
            self.it[u] += 1
        return 0

    def flow(self, s, t):
        ans = 0
        while self.bfs(s, t):
            self.it = [0] * self.n
            while True:
                pushed = self.dfs(s, t, 10**9)
                if not pushed:
                    break
                ans += pushed
        return ans

def solve():
    out = []
    T = int(input())
    for _ in range(T):
        d, n = map(int, input().split())

        def inn(x):
            return x * 2

        def outn(x):
            return x * 2 + 1

        size = 2 * (d + 1)
        dinic = Dinic(size)

        for t in range(1, d):
            dinic.add_edge(inn(t), outn(t), 1)

        for _ in range(n):
            x, y = map(int, input().split())
            start = outn(x) if x != d else inn(x)
            end = inn(y) if y != 0 else outn(y)
            dinic.add_edge(start, end, 1)

        source = outn(0)
        sink = inn(d)
        out.append(str(dinic.flow(source, sink)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```グラフが小さくてまばらであるため、実装では Dinic を使用します。 各グラフのエッジには、その宛先、残りの容量、および逆エッジのインデックスが格納されます。 逆エッジは残差グラフに必要であり、アルゴリズムが以前の選択を再検討できるようになります。 

ノードの分割は、時間値ごとに 2 つのインデックスを割り当てることによって処理されます。 中間時間 t、からのエッジ`inn(t)`に`outn(t)`容量は1です。 列車の端は、開始時刻の下り側から出発し、終了時刻の上り側に入ります。 

物乞いは制限なく開始瞬間から離れることができるため、ソースは時間 0 の発信側になります。 乞食は無制限に終了できるため、シンクは時間 d の流入側です。 トレイン エッジは問題で必要とされる完全な閉区間の動作をすでに表しているため、区間に対する特別な off-by-one 処理はありません。 

Python の整数はオーバーフローしないため、可能な最大フローが 1 よりもはるかに大きい場合でも、容量と答えは安全です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(V²E) | Dinic は、最大約 400 のノードと約 20000 のトレイン エッジを持つグラフ上で実行されます。 
| スペース | O(V + E) | グラフには、すべてのトレイン エッジとその残りのエッジが保存されます。 

時間範囲が狭いため、列車の数が多くてもフロー グラフが小さくなります。 高価な部分は可能なスケジュールの数ではなく時間ノードの数に依存するため、アルゴリズムは制限を快適に満たします。 

## テストケース```python
import sys
import io

def run(inp: str) -> str:
    old = sys.stdin
    sys.stdin = io.StringIO(inp)
    data = sys.stdin.read().split()
    sys.stdin = old

    it = iter(data)
    t = int(next(it))
    ans = []

    class Dinic:
        def __init__(self, n):
            self.g = [[] for _ in range(n)]

        def add(self, u, v, c):
            self.g[u].append([v, c, len(self.g[v])])
            self.g[v].append([u, 0, len(self.g[u]) - 1])

        def dfs(self, u, t, f):
            if u == t:
                return f
            while self.ptr[u] < len(self.g[u]):
                e = self.g[u][self.ptr[u]]
                if e[1] and self.level[e[0]] == self.level[u] + 1:
                    r = self.dfs(e[0], t, min(f, e[1]))
                    if r:
                        e[1] -= r
                        self.g[e[0]][e[2]][1] += r
                        return r
                self.ptr[u] += 1
            return 0

        def flow(self, s, t):
            res = 0
            while True:
                self.level = [-1] * len(self.g)
                q = [s]
                self.level[s] = 0
                for u in q:
                    for v, c, _ in self.g[u]:
                        if c and self.level[v] == -1:
                            self.level[v] = self.level[u] + 1
                            q.append(v)
                if self.level[t] == -1:
                    return res
                self.ptr = [0] * len(self.g)
                while True:
                    x = self.dfs(s, t, 10**9)
                    if not x:
                        break
                    res += x

    for _ in range(t):
        d = int(next(it))
        n = int(next(it))
        din = Dinic(2 * (d + 1))

        for x in range(1, d):
            din.add(2*x, 2*x+1, 1)

        for _ in range(n):
            x = int(next(it))
            y = int(next(it))
            din.add(2*x+1, 2*y, 1)

        ans.append(str(din.flow(1, 2*d)))

    return "\n".join(ans)

 ## 特殊なケース

 フロー グラフにはソースからシンクへの直接のエッジが含まれているため、1 日全体をカバーする 1 つのトレインが処理されます。 最大フローは、1 つの完全なスケジュールとして正しくカウントされます。 

多くの列車の間隔がまったく同じである場合、各列車は個別の定員 1 つのエッジになります。 このアルゴリズムは等間隔を組み合わせていないため、利用可能なすべての列車がさらに 1 つの乞食に貢献する可能性があります。 

多くのスケジュールを同時に切り替える必要がある場合、分割ノード容量により無効なソリューションが防止されます。 たとえば、trains を使用した入力では`[0,2]`そして`[2,4]`、時間 2 を通過できるフロー ユニットは 1 つだけであり、切り替え中に物乞いに会えないというルールに一致します。 

このアルゴリズムは、完全なルートが存在しない場合も処理します。 時刻 0 と時刻 d を接続するパスがない場合、フローの単位がシンクに到達できないため、最大フローはゼロになります。
