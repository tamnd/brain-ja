 ## 解決策
 ## 問題の理解

 複数の企業が直線に沿って配置されており、1 から n までのインデックスが付けられています。 多数の投資パッケージが存在し、各パッケージは最初はどこかの会社に「属しています」。 ただし、そこに留まることが強制されるわけではありません。 

各パッケージには、値 l によって決定される柔軟性の範囲があります。 会社 c から発信されたパッケージは、x が c から遠すぎない限り、具体的には距離 |c − x| である限り、任意の会社 x に割り当てることができます。 最大でも l です。 有効な宛先を選択した後、パッケージは 1 つの会社にのみ割り当てられる必要があります。 

すべてのパッケージを有効な企業間で自由に配布できます。 私たちが気にする制約は、最終的な配布のバランスがどの程度であるかということです。企業ごとに、受け取った荷物の数をカウントし、これらのカウントの最大値をできるだけ小さくしたいと考えています。 タスクは、この最小可能な最大負荷を計算することです。 

入力は複数の独立したシナリオを記述します。 各シナリオでは、企業の数 n、パッケージの数 m、そして 2 つの配列が与えられます。1 つは各パッケージの元の所有者、もう 1 つはその柔軟性半径です。 各シナリオの出力は、最適な再割り当て後に任意の会社に割り当てられたパッケージの最大数のうちの最小値を表す単一の整数です。 

重要な隠された構造は、各パッケージが任意の宛先のセットを持たないことです。 代わりに、各パッケージ i は、範囲 [1, n] にクリップされた、c_i − l_i から c_i + l_i までの有効な企業の連続した間隔を定義します。 したがって、すべてのパッケージは間隔リクエストであり、その間隔内の 1 つの整数点に正確に割り当てる必要があります。 

複雑さの観点から、n と m は両方とも、テスト合計ごとに最大 2⋅10^5 まで大きくなる可能性があります。 単純な方法で Z の値ごとに独立して割り当てをシミュレートしたり、実現可能性をチェックしようとしたソリューションは遅すぎます。 各パッケージを何らかの有効な会社に割り当てるという直接的な貪欲なシミュレーションも失敗します。ローカルな選択により、他の場所での輻輳が増大する形で後の割り当てが簡単にブロックされる可能性があるためです。 

すべてのパッケージが柔軟性が高く、ほぼすべての場所で重複している場合、微妙なエッジ ケースが発生します。 このような場合、貪欲な「現在負荷が最も少ない有効な企業を埋める」戦略は、不正確な配分を生み出す可能性があります。これは、よりグローバルにバランスのとれた割り当てが存在する場合でも、初期の決定により人為的にピーク負荷を増加させる方法で間隔が集中する可能性があるためです。 

間隔が非常に狭い場合、たとえばすべての i に対して l_i = 0 など、別のエッジ ケースが発生します。 次に、各パッケージは元の会社に強制的に送信され、答えは単純に任意の c_i の最大頻度になります。 この縮退を無視し、再分配が可能であると仮定する解決策は、実現可能性を過大評価することになります。 

## アプローチ

 直接的な総当たりアプローチでは、各パッケージを 1 つずつ割り当てて、すべての有効な選択肢を調べようとします。 これはすべての制約を尊重するので正しいですが、分岐係数が大きくなります。 各パッケージは最悪の場合、最大 O(n) 社にマッピングされる可能性があるため、状態空間が指数関数的に爆発的に増大し、小さな入力でも実行不可能になります。 

もう少し構造化されたブルート フォースでは、候補値 Z を固定し、企業が Z を超える値を受け取らないようにパッケージを割り当てることが可能かどうかをチェックします。これは、フローのような実現可能性の問題になります。各パッケージはその間隔内の位置の 1 つに割り当てられなければならず、各位置には容量 Z があります。単純な最大フローの構築は機能しますが、O(n + m) ノードと O(mn) エッジを持つ完全なフロー グラフを構築するのは大きすぎ、最適化されたフローでさえ、すべての Z にわたって繰り返しチェックするには遅すぎます。

重要な点は、実際には割り当てを明示的にシミュレートする必要がないということです。 容量を超えずにすべての間隔を整数ポイントにパックできるように、最小容量 Z を決定するだけで済みます。 これは古典的な「キャパシティ制約のあるインターバル割り当て」の問題であり、ポジションを順番に処理し、可用性を考慮しながら常に可能な限り遅いインターバルを割り当てれば、貪欲にチェックできます。 この構造により、左から右にスイープし、現在アクティブなインターバルを維持するという観点から考えることができます。 

固定 Z を繰り返し試行する代わりに、最適な配置の任意の点で強制的に重複する間隔の数を追跡することで、問題を最小 Z を直接計算することに変換できます。 各パッケージは範囲に寄与し、その答えは、すべての間隔が最適に割り当てられた場合に、任意の位置によって引き起こされる最大負荷になります。 最適な戦略は、各パッケージを常にその範囲内で可能な限り右に配置することと同等であり、これにより不必要な初期の輻輳が防止されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース割り当て検索 | 指数関数 | O(m) | 遅すぎる |
 | Z ごとのフローベースの実現可能性チェック | チェックごとの O(フロー) | O(n + m) | 遅すぎる |
 | 貪欲な間隔配置 + スイープ | O((n + m) log m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各パッケージを区間 [L_i, R_i] に変換します。ここで、L_i = max(1, c_i − l_i) および R_i = min(n, c_i + l_i) です。 これにより、整数点上に間隔を配置するという問題が再定式化されます。 
2. すべての間隔を左のエンドポイントで並べ替えます。 この順序により、配置対象となる順序で間隔が考慮されるようになります。これは、一貫したスイープを維持するために必要です。 
3. 左端が現在の位置以下であるがまだ割り当てられていないすべての間隔のデータ構造を維持しながら、1 から n までの位置をスイープします。 
4. 各位置 x で、x から始まるすべての間隔を、右端点をキーとする優先順位構造に挿入します。 適切なエンドポイントによって緊急性が決まります。後で実現可能性が失われないように、より早く終了する間隔はより早く割り当てる必要があります。 
5. 位置 x に現在割り当てられている間隔の数がターゲット容量 Z より少ない間、x ≤ その右境界である限り、アクティブな構造から右端が最小の間隔を繰り返し取得し、それを x に割り当てます。 そのような間隔が存在しない場合は、次に進みます。 
6. すべての位置を処理した後、すべての間隔が割り当てられたかどうかを確認します。 「はい」の場合、Z は実行可能です。 それ以外の場合はそうではありません。 
7. 最小 Z を見つけるには、1 から m までの回答範囲で二分探索を使用し、上記のスイープを使用して実現可能性をテストします。 

常に最も早い終了時刻のインターバルを割り当てるという貪欲な選択により、より長く存続できるインターバルで初期のポジションを「無駄にする」ことがなくなり、後でより狭いインターバルに対応できる柔軟性が維持されます。 

### なぜ効果があるのか

 任意の位置 x において、重要な唯一の制約は、x をカバーする間隔をそこにいくつ割り当てることができるかということです。 x に配置できるすべての間隔の中で、最小の右端点を持つ間隔を選択することは、将来の柔軟性が最も低いため安全です。 代わりに遅い終了間隔を割り当てる最適なソリューションは、実現可能性を悪化させることなく、それをより早い終了間隔と交換する最適なソリューションに変換できます。 この交換引数により有効性が維持され、貪欲な割り当てによって同じかそれ以下の最大負荷を達成できるソリューションがブロックされないことが保証されます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def can(Z, intervals, n):
    intervals = sorted(intervals)
    i = 0
    active = []
    used = 0

    for x in range(1, n + 1):
        while i < len(intervals) and intervals[i][0] == x:
            heapq.heappush(active, intervals[i][1])
            i += 1

        count = 0
        while active and count < Z:
            r = heapq.heappop(active)
            if r < x:
                continue
            count += 1
            used += 1

        # remove expired intervals
        while active and active[0] < x:
            heapq.heappop(active)

    return used == len(intervals)

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        c = list(map(int, input().split()))
        l = list(map(int, input().split()))

        intervals = []
        for i in range(m):
            L = max(1, c[i] - l[i])
            R = min(n, c[i] + l[i])
            intervals.append((L, R))

        lo, hi = 1, m
        ans = m

        while lo <= hi:
            mid = (lo + hi) // 2
            if can(mid, intervals, n):
                ans = mid
                hi = mid - 1
            else:
                lo = mid + 1

        print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは、各パッケージを有効な企業の限定された間隔に変換することから始まります。 実現可能性チェック関数は、スイープ ラインと正しいエンドポイント順に並べられた最小ヒープを使用して、位置ごとに最大 Z 間隔の割り当てをシミュレートします。 ヒープにより、現在使用可能なすべての間隔のうち、すぐに配置しないと最初に期限切れになる間隔が常に割り当てられるようになります。 

二分探索はこの実現可能性チェックをラップして、機能する最小の Z を見つけます。 実装の重要な詳細は、期限切れの間隔が削除され、決して割り当てにカウントされないことを保証することです。そうしないと、スイープで無効な配置や容量の超過が誤って許可されてしまいます。 

## 実用的な例

 ### 例 1

 入力:```
n = 3
packages: (1,0), (1,1), (2,1)
```間隔:

 変換後 (1,1)、(1,2)、(1,3)

 Z = 1 をテストします。 

x = 1 では、3 つの間隔がすべてアクティブになります。 最小の右端点 (1,1) を持つものを割り当てます。 x = 1 および x = 2 で容量を超えるため、残りの 2 つをすべて、位置 1 ～ 3 にわたって容量 1 で配置することはできません。 

| × | アクティブな間隔 | x に割り当てられます | 残り |
 | --- | --- | --- | --- |
 | 1 | (1,1)、(1,2)、(1,3) | (1,1) | 2 |
 | 2 | (1,2),(1,3) | (1,2) | 1 |
 | 3 | (1,3) | (1,3) | 0 |

 ここでは Z = 1 が機能し、最小負荷が 1 であることを確認します。 

### 例 2

 入力:```
n = 4
(1,3), (2,3), (2,2), (3,1)
```間隔:

 (1,3)、(1,4)、(2,2)、(2,4)

 Z = 2 のテスト:

 x = 2 では、重複する間隔が 3 つありますが、位置ごとに 2 つしか割り当てることができません。 

| × | アクティブ | 割り当てられた | 残り |
 | --- | --- | --- | --- |
 | 1 | (1,3),(1,4) | 0 | 2 |
 | 2 | (1,3)、(1,4)、(2,2)、(2,4) | 2 インターバル | 0 |
 | 3 | ... | 残りを埋める | 0 |

 これは、Z = 2 で十分である一方、Z = 1 では x = 2 で失敗することを示しています。

 ## 特殊なケース

 すべてのパッケージが l_i = 0 の場合、各間隔は 1 つの点に折りたたまれます。 このアルゴリズムは、企業ごとの頻度をカウントすることに帰着します。 各間隔は 1 つの位置にのみ入力され、容量が許せばすぐに割り当てられるため、スイープは引き続き機能します。 

すべての間隔が [1, n] の全範囲をカバーする場合、すべての位置ですべての m 間隔が表示されます。 ヒープには常にすべてのパッケージが含まれており、貪欲なプロセスによりそれらのパッケージが位置全体に均等に分散され、Z = ⌈m / n⌉ が生成されます。 各位置は前進する前に Z まで埋められるため、アルゴリズムはこれを自然に処理します。 

[1,n]、[2,n]、[3,n] のように間隔がネストされている場合、貪欲な選択により、一貫して先に終了する間隔が最初に割り当てられ、後の輻輳が防止されます。 これにより、実現可能性が維持され、あまりにも早い間隔で長い間隔を割り当てると、配置オプションが少ない短い間隔がブロックされるという罠が回避されます。
