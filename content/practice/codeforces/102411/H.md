 ## 問題の理解

 トランザクションの配列 (a_1,a_2,\ldots,a_n) があり、トランザクション (i) には (a_i) 個のクエリが含まれています。 この配列を連続したグループに分割する必要があります。 グループには 1 つのトランザクションまたは複数の隣接するトランザクションを含めることができますが、クエリの総数は選択した制限 (t) 以下である必要があります。 

(t) の要求された値ごとに、可能な最小限のグループ数が必要です。 トランザクションの順序は変更できないため、これは連続パーティションの問題です。 1 つのトランザクションに (t) を超えるクエリが含まれている場合でも、そのトランザクションは有効なグループに収まらないため、答えは次のようになります。`Impossible`。 

2 つの入力サイズは異なる役割を果たします。 (200,000) 個のトランザクションと (100,000) 個のクエリが存在する可能性があるため、すべてのクエリに対して (O(n)) スキャンを実行すると、最大 (20,000,000,000) 個のトランザクション操作が実行されることになり、これは 2 秒の制限をはるかに超えています。 同時に、すべてのトランザクション内のクエリの総数は最大でも (10^6) であり、(nq) よりもはるかに小さくなります。 この境界は、この問題で役立つリソースです。 これにより、個々のクエリ位置によってインデックスが付けられた構造を構築し、すべての貪欲なジャンプを一定時間にすることができます。 

値 (a_i) は正です。 プレフィックスの合計が厳密に増加しているため、これは重要です。 また、バッチに次のトランザクションを含めることができなくなると、その後のすべてのトランザクションはプレフィックスと合計の順序でさらに遠くになるため、最も遠い実行可能なエンドポイントを明確に見つけることができることも意味します。 

実装を静かに破壊する可能性のある境界ケースがいくつかあります。 1 つのクエリを持つ 1 つのトランザクションを考えてみましょう。```

## アプローチ

 直接的な解決策は、(t) のすべての値を貪欲にスキャンすることです。 最初のトランザクションから開始して、合計が最大 (t) になるまで連続したトランザクションを追加し続けます。 次のトランザクションが (t) を超える場合、現在のバッチを閉じて、新しいバッチを開始します。 可能な限り遠いエンドポイントを取得しても、残りのサフィックスの分割が困難になることはないため、この貪欲な選択は正しいです。 他の最初のバッチは右端では終了しないため、貪欲な選択により、残りのトランザクションに対して少なくとも同程度の余地が残されます。 

問題はコストです。 1 回の貪欲スキャンですべて (n) のトランザクションを検査でき、(q=100,000) のクエリが存在する可能性があります。 最悪の場合、これは (nq=20,000,000,000) 回の操作になります。 多くのクエリ値が繰り返される場合でも、最悪の場合の入力には多くの個別の値が含まれる可能性があるため、線形スキャンを単にメモ化するだけでは十分ではありません。 

有益な観察は、すべての (a_i) の合計が最大でも (10^6) であるということです。 しましょう

 [
 S=\sum_{i=1}^{n}a_i。 
]

 どのトランザクションに各クエリが含まれているかを覚えながら、個々のクエリに (1) から (S) までの番号を付けることを想像してください。 バッチがトランザクション (i) で開始される場合、バッチが開始されるまでのクエリの数

 [
 p_{i-1}=a_1+a_2+\cdots+a_{i-1}。 
]

 制限 (t) を使用すると、バッチは最大でクエリ位置 (p_{i-1}+t) に到達できます。 その位置がトランザクション (j) 内にある場合、バッチはトランザクション (j) で終了し、次のバッチは (j+1) で開始します。 

したがって、配列を前処理できます`owner`、 どこ`owner[x]`は、(x) 番目の個別のクエリを含むトランザクションです。 次に、1 つの貪欲なバッチ遷移が単一の配列検索になります。```
next_start = owner[prefix[start - 1] + t] + 1
```ただし、ターゲットのクエリ位置が (S) より小さい場合に限ります。 これにより、トランザクションをスキャンしたり、バッチごとにバイナリ検索を実行したりする必要がなくなります。 

もう 1 つ重要な複雑さの観察があります。 固定 (t) の場合、貪欲シミュレーションは定数係数まで (O(S/t)) ステップのみを実行します。 1 つのバッチがトランザクション (R) で終了し、トランザクション (R+1) が存在するとします。 最初のバッチの合計は最大 (t) ですが、(a_{R+1}) を追加すると (t) を超えます。 インスタンス全体が実行可能であるため、(a_{R+1}\le t)。 したがって、次のバッチはトランザクション (R+1) を受け取る可能性があり、これら 2 つのバッチ全体で (t) を超えるクエリが消費されます。 したがって、2 つのバッチごとに (t) 個を超えるクエリが消費され、最大で (2S/t) 個のバッチが生成されます。 

(t) のすべての実現可能な値に対する答えを計算すると、シミュレーション ステップの総数は次のように制限されます。 

[
 \sum_{t=1}^{S} O\left(\frac{S}{t}\right)
 =O(S\log S)。 
]

 (S\le10^6) なので、これは実用的です。 繰り返されるクエリ値は 1 回だけ計算されます。 

したがって、アプローチ間の関係は単純です。 貪欲が正しいため、ブルート フォース ソリューションは機能しますが、同じトランザクション配列を繰り返しウォークスルーします。 個々のクエリの総数が少ないという観察結果から、貪欲なジャンプをクエリの位置で表すことができ、各ジャンプを定数時間にして、総作業量を調和和に減らすことができます。 公式コンテストのチュートリアルでは、同じ (O(S\log S)) 限界について説明しています。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O(nq)) | (O(1)) 入力以外にも | 遅すぎる |
 | プレフィックス位置 + 貪欲なジャンプ | (O(n+S+S\log S+q)) | (O(n+S+q)) | 承認済み |

 ここで、(S=\sum a_i)、および (S\log S) 項は、(t) の個別の実現可能な値に対する総コストです。 

## アルゴリズムのチュートリアル

 1. トランザクション配列を読み取り、プレフィックスの合計を計算します。 させて`prefix[i]`トランザクション (1) ～ (i) のクエリの合計数になります。 すべての (a_i) が正であるため、これらのプレフィックスの合計は厳密に増加しています。 
2. 探す`mx`、最大のトランザクション サイズ。 クエリで (t<mx) が要求された場合は、応答します。`Impossible`すぐに。 すべてのトランザクションは一部のバッチ内に完全に存在する必要があるため、容量を超えるトランザクションはパーティション全体を構成することを不可能にします。 
3. すべての個々のクエリに (1) から (S) までの番号を付けます。 建てる`owner[x]`、クエリ (x) を含むトランザクションを保存します。 たとえば、(a=[2,3,1]) の場合、クエリ (1,2) はトランザクション (1) に属し、クエリ (3,4,5) はトランザクション (2) に属し、クエリ (6) はトランザクション (3) に属します。 
4. (t) の特定の実現可能な値については、トランザクションから開始します。`start = 1`そしてバッチ数をゼロに設定します。 未処理のトランザクションがまだ存在するため、反復ごとにさらに 1 つのバッチが必要になります。 
5. コンピューティング

 [
 x=\text{prefix[start-1]}+t。 
]

 これは、トランザクション境界が存在しない場合に現在のバッチが到達できる可能性がある最も遠い個々のクエリ位置です。 
6. (x\ge S) の場合、現在のバッチは配列全体の最後に到達できるため、答えをインクリメントして停止します。 さもないと、`owner[x]`バッチが到達できる最後のクエリ位置を含むトランザクションです。 現在のバッチはそのトランザクションで終了するため、次のように設定します。 

[
 \text{開始}=\テキスト{所有者}[x]+1。 
]

 これにより、(x) がトランザクションの途中に陥った場合が自動的に処理されます。 そのトランザクションを分割することはできないため、トランザクション全体が現在のバッチに属し、その後に次のバッチが開始されます。 
7. この値 (t) に対して計算された答えをキャッシュします。 入力で同じ (t) が再び発生した場合は、パーティションを再度シミュレートせずに、キャッシュされた値を返します。 
8. すべてのクエリに対するキャッシュされた回答を元の順序で出力します。 不可能なクエリは、有効な数値回答と混同されないように、個別に表されます。 

### なぜ効果があるのか

 固定 (t) の場合、最初の未処理のトランザクション (i) を考慮します。 このアルゴリズムは、(i) から (j) までの合計が最大でも (t) になるように、最も遠いトランザクション (j) を選択します。 有効なパーティションは、制限を超えるため、(j) 以降に最初のバッチを終了することはできません。 したがって、最初のバッチが (j) で終了する最適解が常に存在します。 そのバッチを修正した後、同じ議論が残りのサフィックスに適用されます。 帰納法により、すべての貪欲なバッチ エンドポイントを最適なパーティションの一部にすることができるため、最終的なバッチ数は最小限になります。 

の`owner`lookup は貪欲な決定を変更しません。`prefix[i-1]+t`合計サイズに適合する最後の個々のクエリを特定し、`owner`そのクエリ位置を、エンドポイントを含む必要があるトランザクションに変換します。 したがって、シミュレートされたすべてのジャンプは、直接の貪欲スキャンによるジャンプとまったく同じになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    prefix = [0] * (n + 1)
    mx = 0

    for i, x in enumerate(a, 1):
        prefix[i] = prefix[i - 1] + x
        if x > mx:
            mx = x

    total = prefix[n]

    # owner[x] = transaction containing the x-th query.
    owner = [0] * (total + 1)
    transaction = 1

    for x in range(1, total + 1):
        while x > prefix[transaction]:
            transaction += 1
        owner[x] = transaction

    q = int(input())
    queries = list(map(int, input().split()))

    cache = {}
    out = []

    for t in queries:
        if t < mx:
            out.append("Impossible")
            continue

        if t in cache:
            out.append(str(cache[t]))
            continue

        start = 1
        batches = 0

        while start <= n:
            batches += 1

            reachable_query = prefix[start - 1] + t

            if reachable_query >= total:
                break

            end_transaction = owner[reachable_query]
            start = end_transaction + 1

        cache[t] = batches
        out.append(str(batches))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```すべてのバッチ境界はトランザクション前のクエリ数で自然に表現されるため、プレフィックス配列が最初に構築されます。`prefix[i - 1]`トランザクション時に以前のバッチにすでに割り当てられていたクエリの正確な数です。`i`次の出発点になります。 

の`owner`配列には、個々のクエリ位置ごとに 1 つのエントリがあります。 この構造では、クエリ位置を左から右にたどって、位置がプレフィックスの合計を超えた場合にのみ現在のトランザクションを進めます。 トランザクション ポインタは前方にのみ移動するため、構築全体には (O(S+n)) 時間がかかります。 

メインのシミュレーションは、番号付きアルゴリズムを反映しています。`reachable_query`容量のみに基づいて現在のバッチに適合する最後のクエリ位置です。 到達または通過した場合`total`、現在のバッチはスクリプト全体を終了します。 

厳密な比較`total`意図的です。 いつ`reachable_query == total`、残りのクエリはすべて正確に適合するため、現在のバッチは有効であり、シミュレーションを停止する必要があります。 代わりにコードが必要な場合`reachable_query > total`を実行すると、不必要な追加の反復が実行され、off-by-one エラーが発生します。 

いつ`reachable_query < total`、`owner[reachable_query]`そのクエリを含むトランザクションを識別します。 トランザクションは分割できないため、バッチにはそのトランザクション全体が含まれている必要があります。 したがって、次に開始されるトランザクションは`owner[reachable_query] + 1`。 

Python の整数はオーバーフローしないため、プレフィックスの合計は最大合計 (10^6) であっても安全です。 キャッシュはパフォーマンス以外にも役立ちます。サンプル内で (t=8) が 2 回出現するなど、重複する値が 1 回だけ評価されることが保証されます。 

## 実用的な例

 最初のサンプルには以下が含まれます```
a = [4, 2, 3, 1, 3, 4]
```プレフィックス合計あり```
[0, 4, 6, 9, 10, 13, 17].
```(t=5) を考えてみましょう。 最大トランザクション サイズは (4) であるため、この値は実現可能です。 

| バッチ | トランザクションを開始する | 開始前のクエリ | 到達可能なクエリ |`owner`| 次の開始 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 1 | 0 | 5 | 2 | 3 |
 | 2 | 3 | 6 | 11 | 5 | 6 |
 | 3 | 6 | 13 | 18 | 終わり | 停止 |

 最初のバッチにはトランザクション (1) と (2) が含まれており、合計は (6) です。 これは (t=5) であるため矛盾しているように見えますが、テーブルの`reachable query`はクエリ位置であり、許可されたトランザクション エンドポイントではありません。 クエリ (5) はトランザクション (2) 内にあるため、`owner[5]=2`。 プレフィックスの合計が (6) である場合、トランザクション全体 (2) を実際には含めることはできません。 これは、の素朴な解釈における微妙な誤りを明らかにします。`owner[x]`。 

正しい遷移では、禁止されたトランザクション境界の直前のクエリ位置を使用する必要があります。 より直接的には、ターゲット位置が (x) の場合、エンドポイントはクエリ (x) を含むトランザクションになりますが、これはそのトランザクションのプレフィックス合計が制限値以下である場合に限ります。 (x) はトランザクション内に存在する可能性があるため、プレフィックスの合計が完全に一致する場合にのみ、エンドポイントは実際にそのトランザクションになります。 公式の定式化では、有効な開始境界から正確に (t) クエリ単位後に到達したトランザクション インデックスを、その事前計算された状態に基づく遷移とともに保存することで、この曖昧さを回避しています。 

よりシンプルで安全な実装のために、代わりに各ジャンプのプレフィックス合計に対して二分検索を使用できますが、これでは Python で意図された (O(S\log S)) 境界が失われます。 定数時間の正しい定式化は、クエリ数 (x) ごとに、プレフィックスの合計が (x) 以上である最初のトランザクションを保存し、その後のトランザクションに進むことです。 これはまさに、`owner`上記の配列はそうしますが、エンドポイントは、到達可能なクエリ数以上の最初のプレフィックスを使用して解釈される必要があります。 

サンプル (t=5) では、トランザクション (1) から開始し、少なくとも (5) の最初のプレフィックス合計は (6) で、トランザクション (2) に対応します。 トランザクション (2) はバッチの合計 (6>5) を作成するため、現在のバッチはトランザクション (1) で終了し、次のバッチは (2) から開始する必要があります。 このため、実装では`lower_bound`-style マッピングではなく`owner[x]`直接。 

次の修正された実装では、`next_transaction[x]`、プレフィックスの合計が少なくとも (x) である最初のトランザクションとして定義されます。 そのプレフィックスが目標を超えた場合、エンドポイントから 1 つのトランザクションが減算されます。```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    prefix = [0] * (n + 1)
    mx = 0

    for i, x in enumerate(a, 1):
        prefix[i] = prefix[i - 1] + x
        mx = max(mx, x)

    total = prefix[n]

    # at_least[x] = first transaction i with prefix[i] >= x.
    at_least = [0] * (total + 1)
    i = 1
    for x in range(1, total + 1):
        while prefix[i] < x:
            i += 1
        at_least[x] = i

    q = int(input())
    queries = list(map(int, input().split()))

    cache = {}
    out = []

    for t in queries:
        if t < mx:
            out.append("Impossible")
            continue

        if t in cache:
            out.append(str(cache[t]))
            continue

        start = 1
        batches = 0

        while start <= n:
            batches += 1

            target = prefix[start - 1] + t

            if target >= total:
                break

            first_too_large = at_least[target + 1]
            start = first_too_large

        cache[t] = batches
        out.append(str(batches))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```重要な修正点は、`target`は、容量によって許容される最大のクエリ位置を表します。 プレフィックスの合計が超過する最初のトランザクション`target`を使用して見つかります`target + 1`。 そのトランザクションは現在のバッチに属することはできないため、まさに次のバッチの開始トランザクションになります。 

サンプルの (t=5) の場合、最初のバッチはトランザクション (1) で開始されるため、`target=5`。 (5) より大きい最初のプレフィックスは (6) で、トランザクション (2) に属します。 したがって、次のバッチはトランザクション (2) から開始され、正しいパーティションが与えられます。 

2 番目の例として、次のことを考えてみましょう。```
4

```プレフィックスの合計は次のとおりです。```
[0, 2, 3, 6, 8].
```(t=3) の場合、貪欲なプロセスは次のようになります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | (O(n+S+S\log S+q)) | プレフィックスとクエリ位置の前処理は線形です。 すべての個別の (t) にわたって、貪欲なシミュレーションには合計 (O(S\log S)) のステップがかかります。 |
 | スペース | (O(n+S+q)) | プレフィックス合計は (O(n)) を使用し、クエリ位置マッピングは (O(S)) を使用し、クエリ キャッシュは (O(q)) を使用します。 |

 ここでは (S=\sum a_i\le10^6) です。 シミュレーションの背後にある調和和は次のとおりです。 

[
 S\left(\frac1{1}+\frac1{2}+\cdots+\frac1S\right)=O(S\log S),
 ]

 これは直接解の (nq) 仕事よりも十分に小さいです。 メモリ使用量も 512 MB 制限内で安全です。 

## テストケース

 次のテスト ハーネスは、コンテスト ソリューションを呼び出し可能な形式に保ちます。`solve`関数を使用して、標準入力をメモリ内ストリームに置き換えます。 最大サイズのケースは明示的に書き出すのではなく生成されるため、(200,000) トランザクションを構築しながらテストを読み取り可能な状態に保ちます。```python
import sys
import io

def solve():
    input = sys.stdin.readline

    n = int(input())
    a = list(map(int, input().split()))

    prefix = [0] * (n + 1)
    mx = 0

    for i, x in enumerate(a, 1):
        prefix[i] = prefix[i - 1] + x
        mx = max(mx, x)

    total = prefix[n]

    # first transaction whose prefix sum is strictly greater than x
    greater = [0] * (total + 1)
    i = 1

    for x in range(total):
        while i <= n and prefix[i] <= x:
            i += 1
        greater[x] = i

    q = int(input())
    queries = list(map(int, input().split()))

    cache = {}
    out = []

    for t in queries:
        if t < mx:
            out.append("Impossible")
            continue

        if t in cache:
            out.append(str(cache[t]))
            continue

        start = 1
        batches = 0

        while start <= n:
            batches += 1
            target = prefix[start - 1] + t

            if target >= total:
                break

            start = greater[target]

        cache[t] = batches
        out.append(str(batches))

    sys.stdout.write("\n".join(out))

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    try:
        solve()
        return sys.stdout.getvalue().strip()
    finally:
        sys.stdin = old_stdin
        sys.stdout = old_stdout

 ## 特殊なケース

 (t) が最大トランザクションより小さい場合、アルゴリズムはシミュレーションを実行する前に終了します。 例えば、```
3

```答えがあります`Impossible`トランザクション (2) だけでも 5 つのクエリが必要なためです。 隣接するトランザクションを組み合わせても、そのトランザクションを小さくすることはできません。 

(t) が最大のトランザクションに等しい場合、インスタンスは実行可能になります。 のために```
3
2 5 1
1
5
```貪欲なアルゴリズムはトランザクション (1) から始まります。 その容量はクエリ位置 (5) に達しますが、(5) より大きい最初のプレフィックス合計は (6) であり、トランザクション (3) に対応します。 最初のバッチはトランザクション (1) と (2) で、合計は (7) であるため、この例は、ルックアップで許可されたターゲットより厳密に大きい最初のプレフィックスを使用する必要がある理由を実際に示しています。 正しい最初のバッチはトランザクション (1) のみで、次にトランザクション (2)、その後にトランザクション (3) が続きます。`3`。 

ターゲットがトランザクション境界に正確に到達すると、次のトランザクションは次のバッチを開始する必要があります。 のために```
4
2 1 3 2
1
6
```最初の 6 つのクエリは正確にトランザクション (1)、(2)、および (3) です。 最初のバッチには合計 (6) があり、トランザクション (4) によって 2 番目のバッチが開始されます。 答えは`2`。

4

1
4
```最初のバッチにはトランザクション (1) と (2) を含めることができ、合計は (3) になりますが、トランザクション (3) を含めることはできません。トランザクション (3) のフルサイズは合計が (6) になります。 答えは`3`、パーティション (2+1\mid3\mid2) あり。 

(t) が少なくともクエリの総数である場合、配列全体が 1 つのバッチに収まります。 のために```
4

8
```ターゲットはすぐに最後に到達するため、アルゴリズムは 1 回だけ反復を実行して出力します。`1`。 

(t) の繰り返し値はキャッシュによって処理されます。 入力が (8) を 10 万回要求した場合、パーティションは 1 回シミュレートされ、その後の発生ごとに同じ結果が返されます。 複雑さの引数はクエリの生の数ではなく、(t) の個別の値に基づいているため、これは重要です。 

シミュレーション全体にわたる中心的な不変条件は次のとおりです。`start`常に、前のバッチに割り当てられていない最初のトランザクションです。 選択された次の開始は、現在のバッチに完全に適合しない最初のトランザクションです。 したがって、以前のすべてのトランザクション`start`は現在または以前の有効なバッチに属しますが、`start`それ以降は未処理のままです。 したがって、貪欲なプロセスは、配列全体が分割されるまで単調に進行します。
