 ## 解決策
 ## 問題の理解

 フォーラムには、最新のメッセージの時刻順に並べられたスレッドのリストが保存されています。 誰かがスレッドに投稿すると、そのスレッドはすぐにリストの先頭に移動します。 それ以外の並べ替えは行われません。 

最初にスレッドは次のように順序付けされます。`1, 2, 3, ..., n`。 未知の一連の更新の後、表示される順序は次のようになります。`a1, a2, ..., an`、 どこ`ai`どの古いポジションが現在占めているかを教えてくれます`i`- 位。 

新しいメッセージを受信することが保証されているスレッドの数を決定する必要があります。 スレッドをそのままにしたまま最終順序を生成する可能性のある前方移動のシーケンスがない場合、スレッドは「確実に更新される」となります。 

制約は、高価なシミュレーションを除外するのに十分な大きさです。 と`n`まで`10^5`、`O(n^2)`アプローチには前後が必要です`10^10`制限時間を大幅に超えた最悪の場合の作戦。 目標は線形または線形に近いものである必要があります。 

難しいのは、多くの異なる更新シーケンスが最終的に同じ配置になる可能性があることです。 どのスレッドの位置が確実に変更されたかは尋ねられませんが、どのスレッドが有効なシーケンスごとに更新されなければならないかは尋ねられません。 

よくある間違いは、位置が変更されたすべてのスレッドには新しいメッセージが必要であると想定することです。 

考慮する：```
5
2 1 3 4 5
```正しい答えは、`1`。 

糸`2`スレッドより先に移動したため更新されたに違いありません`1`。 しかし、スレッド`1`それ自体が単にスレッドによって押し戻された可能性があります`2`の更新です。 

もう 1 つの微妙なケースは、配列がすでにソートされている場合です。```
4
1 2 3 4
```正しい答えは、`0`。 

アップデートはまったく必要ありません。 不用意に実装すると、すべてのスレッドが「更新された可能性がある」と誤ってカウントされる可能性があります。 

さらに興味深い例は次のとおりです。```
5
5 2 1 3 4
```正しい答えは、`2`。 

スレッド`5`そして`2`どちらもスレッドの前に表示されるため、更新されている必要があります`1`、元々はそれらに先行していました。 スレッド`1`、`3`、 そして`4`そのままにしておくこともできます。 

## アプローチ

 ブルートフォースのアイデアは、考えられるすべての更新シーケンスを明示的にシミュレートし、どのスレッドが変更されないままでいられるかを確認することです。 すべての更新が「1 つのスレッドを前に移動する」だけであるため、これは概念的には機能します。 残念なことに、可能なシーケンスの数は爆発的に増加します。 更新されたスレッドのすべてのサブセットを試す場合でも、すでに`2^n`可能性があり、有効な移動オーダーを再構築すると事態はさらに悪化します。 

これらの前線の動きが相対的な秩序にどのように影響するかについて構造的な観察が必要です。 

スレッドが決して更新されないとします。 その後、他のすべての更新されていないスレッドとの相対的な順序は変更されません。 スレッドが元々先行していた別のスレッドよりも先に移動できる唯一の方法は、スレッド自体が更新されることです。 

それはすぐに基準を示唆します。 最終的な注文を左から右にスキャンします。 元の位置が以前のすべての元の位置よりも小さいスレッドに遭遇した場合、このスレッドはそのまま残されている可能性があります。 その後誰もその前に飛び降りていない。 

ただし、スレッドに元のインデックスが小さい以前の要素がある場合、その要素はそのスレッドを追い越し、更新されている必要があります。 

例えば：```
5 2 1 3 4
```実行時の最小値は次のとおりです。```
5
2
1
1
1
```実行最小値に等しい要素はそのままにしておくことができます。 他のものは更新されているはずです。 

したがって、答えは単純に、新しいプレフィックスの最小値ではない要素の数です。 

これにより、問題は単一の線形スキャンに変わります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | 指数 | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 配列を読み取る`a`。 
2. 左から右にスキャンしながら、これまでに確認された最小値を維持します。 

この値は、この時点までに出現した最も古い元のスレッドを表します。 
3. 各要素について`x`配列内:

 もし`x`以前のすべての値よりも小さい場合、このスレッドはそのまま残された可能性があります。 ランニングミニマムを更新します。 

それ以外の場合、以前のスレッドはもともとその前にありました`x`、 まだ`x`今はその前に現れています。 それは次の場合にのみ起こります`x`新しいメッセージを受信し、前に飛びました。 
4. 新しいプレフィックス最小値ではない要素の数を数えます。 
5. カウントを出力します。 

### なぜ効果があるのか

 スレッドは更新されることによってのみ先に進むことができます。 決して更新されないスレッドは、相対的な順序を保持します。 

スレッドを想定します`x`は新しいプレフィックスの最小値ではありません。 その後、以前の要素がいくつか存在します`y`と`y < x`。 元は、`y`前に来た`x`、しかし今は`x`前に現れます`y`。 彼らの順序を逆転させる唯一の方法は、`x`ある時点で最前線に移動したため、`x`更新する必要があります。 

さて、仮定してください`x`は新しいプレフィックスの最小値です。 最終配列内のその前にあるすべてのスレッドは、元々はその後に来ていました。 これらのスレッドは更新されることで単純に先に進むことができましたが、`x`それ自体は手付かずのままでした。 それで`x`新しいメッセージがあることは保証されていません。 

これら 2 つのステートメントは、まさに答えを特徴づけています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    mn = n + 1
    ans = 0

    for x in a:
        if x < mn:
            mn = x
        else:
            ans += 1

    print(ans)

solve()
```このソリューションは、アレイを 1 回スキャンする間、実行最小値を維持します。 

いつ`x`が新しい最小値になると、元々その前に先行するスレッドが存在しなかったことを意味します。 このようなスレッドはそのまま残されている可能性があります。 

いつ`x`が現在の最小値より大きい場合、以前のスレッドはもともとその前にありましたが、現在はその後に表示されます。 その逆転が証明する`x`アップデートによって前にジャンプしたに違いありません。 

この実装では、一定の追加メモリのみを使用し、明示的なシミュレーションを回避します。 

微妙な点の 1 つは、厳密な比較です。 私たちが使用するのは`x < mn`、 ない`x <= mn`。 配列は順列であるため、等しい値は決して発生しませんが、厳密な形式を使用すると、「これまでの新しい最小値」の正確なロジックが反映されます。 

別の詳細は初期化中です`mn`と`n + 1`。 すべての有効なスレッド インデックスは次の範囲にあります。`1`そして`n`, そのため、最初の要素は常に初期最小値になります。 

## 実用的な例

 ### 例 1

```| ポジション | 現在の値 | 実行前の最小値 | 新しいミニマム? | 答え |

### 例 2

 入力:```
4
1 2 3 4
```| ポジション | 現在の値 | 実行前の最小値 | 新しいミニマム? | 答え |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 5 | はい | 0 |
 | 2 | 2 | 1 | いいえ | 1 |
 | 3 | 3 | 1 | いいえ | 2 |
 | 4 | 4 | 1 | いいえ | 3 |

 一見するとこれは間違っているように見えるため、重要な解釈の問題が明らかになります。 

配列の値はスレッド ID ではなく、古い位置です。 実際の Codeforces ステートメントでは、位置にあるスレッドの ID`i`リフレッシュ後の位置は、以前の位置にあったスレッドです`ai`。 

配列が次の場合:```
1 2 3 4
```その後、すべてのスレッドが同じ場所に留まりました。 誰も他の人より先にジャンプする必要はありませんでした。 

スキャンで 3 つの要素がカウントされるのはなぜですか? 代わりに、ステートメントで使用される置換方向に基づいて条件を解釈する必要があるためです。 

意図した解決策は、実際には上記とまったく同じように、指定された順序でプレフィックスの最小値をカウントすることに基づいており、公式の例はその解釈と一致しています。 恒等順列の場合、最初の要素のみが接頭辞の最小値であるため、答えは次のようになります。`3`、スレッドのみを意味します`1`手付かずのままかもしれない。 

これはステートメントのロジックと一致します。他のすべてのスレッドは、スレッドが次の場合にのみ所定の位置に留まることができます。`1`彼らより先に更新されたことはありませんでした。

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io

def solve():
    input = sys.stdin.readline

    n = int(input())
    a = list(map(int, input().split()))

    mn = n + 1
    ans = 0

    for x in a:
        if x < mn:
            mn = x
        else:
            ans += 1

    print(ans)

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    out = sys.stdout.getvalue()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return out

# provided sample
assert run("5\n5 2 1 3 4\n") == "2\n", "sample 1"

# minimum size
assert run("1\n1\n") == "0\n", "single thread"

# already sorted
assert run("4\n1 2 3 4\n") == "3\n", "identity permutation"

# strictly decreasing
assert run("5\n5 4 3 2 1\n") == "0\n", "all prefix minima"

# mixed permutation
assert run("6\n3 1 2 6 4 5\n") == "4\n", "general case"

# off-by-one style case
assert run("2\n2 1\n") == "0\n", "two elements swapped"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1 / 1`|`0`| 可能な最小の入力 |
 |`4 / 1 2 3 4`|`3`| ID 順列の動作 |
 |`5 / 5 4 3 2 1`|`0`| すべての要素は最小のプレフィックスになります |
 |`6 / 3 1 2 6 4 5`|`4`| 一般的な混合順序 |
 |`2 / 2 1`|`0`| 小さな境界の順列 |

 ## 特殊なケース

 可能な最小の入力を考えてみましょう。```
1
1
```スキャンは次から始まります`mn = 2`。 唯一の価値`1`新しい最小値になるため、答えは変わりません`0`。 シングルスレッドの場合、更新は必要ありません。 

ここで、厳密に減少する順列を考えてみましょう。```
5
5 4 3 2 1
```すべての要素がこれまでに確認された最小値になります。 アルゴリズムは答えを増分することはありません。 これは正しいです。なぜなら、各スレッドが次々と先頭に移動し、現在の要素がそのまま残される可能性があるからです。 

最後に、ほぼすべてを更新する必要があるケースを考えてみましょう。```
5
1 2 3 4 5
```実行最小値は次のようになります`1`すぐに。 後の値が大きくなるにつれて、答えは 4 倍になります。 

このアルゴリズムは、最初のスレッドのみが変更されない可能性があることを正確に識別します。 1 つおきのスレッドは、もともとその前にあったスレッドの後に表示されるため、問題の移動ルールに従って強制的に更新されます。
