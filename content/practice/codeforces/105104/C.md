 ## 解決策
 ## 問題の理解

 各テスト ケースに配列が与えられ、特定のパリティ条件を満たすサブ配列の数をカウントする必要があります。選択したサブ配列内で、少なくとも 1 つの値が奇数回出現します。 

同様に、サブ配列の頻度分布がすべて均一でない場合、そのサブ配列は有効であると見なされます。 部分配列が失敗する唯一の方法は、その内部のすべての個別の値が偶数回出現する場合です。 

出力は、すべてのテスト ケースにわたるそのようなサブ配列の数です。 

制約は非常に特殊な意味で大きいです。 すべてのテスト ケースの合計の長さは最大 10^6 で、テスト ケースの数も大きくなる可能性があります。 これにより、部分配列の O(n^2) 列挙が除外されます。 非常に軽量でない限り、テスト ケースごとに O(n log n) であっても境界線に達します。 

各サブ配列をチェックして頻度をカウントする単純なアプローチでは、O(n^2) 個のサブ配列と、サブ配列ごとに最大 O(n) 個の作業が必要になりますが、これは限界をはるかに超えています。 周波数維持を最適化しても、依然として O(n^2) 個のサブ配列が残ります。 

すべての要素が同一である場合、微妙なエッジケースが発生します。 たとえば、配列が [1, 1, 1, 1] の場合、カウントが奇数になるのはその場合のみであるため、奇数長のすべての部分配列が有効になります。 不注意なアプローチを行うと、すべてのサブ配列が有効であると誤って仮定したり、グローバル パリティに基づいて誤ってショートカットを試みたりする可能性があります。 

もう 1 つの特殊なケースは、[1、2、1、2] のような交互のパターンです。 ここで、多くのサブ配列の周波数カウントはすべて偶数であり、有効なサブ配列の構造は、ローカル チェックだけでなく、セグメント間のパリティ キャンセルに依存します。 

重要な問題は、この条件が要素全体でローカルではなく、周波数全体でグローバルであることです。 

## アプローチ

 ブルート フォース ソリューションでは、すべてのサブ配列 [l, r] を列挙し、周波数マップを維持し、すべての周波数が偶数であるかどうかをチェックします。 各サブ配列について、周波数を段階的に更新しますが、パリティ状態を再計算または維持します。 増分更新の場合でも、O(n^2) 個の部分配列があり、各更新は O(1) 状態に影響しますが、有効性をチェックするには、すべてのカウントが偶数であるかどうかを理解する必要があり、これは依然として潜在的にすべての個別の値のパリティの追跡に依存します。 

これにより、最悪の場合、テストごとにおよそ O(n^2) の操作が発生し、合計規模では 10^12 の操作となり、明らかに不可能です。 

重要な観察は、実際には完全な周波数を追跡する必要はないということです。 周波数のパリティのみを考慮します。 各値は、サブ配列内の偶数または奇数のカウントに寄与します。 少なくとも 1 つの値が奇数パリティを持つ部分配列をカウントしたいと考えています。 

これは、すべての値が偶数の頻度を持つ、合計サブ配列からサブ配列を引いたものと同等です。 そこで問題を裏返します。すべて偶数の周波数を持つ部分配列を数えます。 

ここで、これをプレフィックス パリティの観点に変換します。 各プレフィックスについて、これまでにどの値が奇数回出現したかを記述するパリティ状態を維持します。 サブ配列の 2 つのプレフィックス状態が同一である場合、そのサブ配列の周波数は正確にすべて偶数になります。 これは、等しいパリティ状態を XOR するとすべてがキャンセルされるためです。 

したがって、問題は、等しいプレフィックス XOR 状態のペアをカウントすることに帰着します。 プレフィックス パリティをハッシュ可能な状態として表すと、良好な部分配列 (すべて偶数) の数は、出現の組み合わせの状態の合計になります。 したがって、答えはサブ配列の合計からその値を引いたものになります。 

パリティ更新のローリング XOR のような署名を維持します。 値が大きいため (最大 10^6)、完全なビットセットを保存できません。 代わりに、値ごとにランダム化されたハッシュを使用し、それらを実行中のプレフィックス ハッシュに XOR します。 これにより、高い確率で等価比較が維持されながら、パリティ状態が 1 つの整数に圧縮されます。 

したがって、問題を等しいプレフィックス ハッシュをカウントすることに縮小します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) | O(n) | 遅すぎる |
 | プレフィックスパリティハッシュ | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各テスト ケースについて、実行中のプレフィックス XOR ハッシュを 0 に初期化します。これは、値が出現していない空のプレフィックスのパリティ状態を表します。 
2. それぞれの個別の値にランダムな 64 ビット整数を割り当てます。 この値は、パリティ トグルへの寄与を表します。 
3. 配列を左から右に走査し、現在の要素に割り当てられたランダム値を XOR 演算することでプレフィックス ハッシュを更新します。 これはパリティの切り替えをシミュレートします。最初にパリティが発生するとオンになり、2 番目にパリティがオフになるというようになります。 
4. 各プレフィックス ハッシュがこれまでに出現した回数をカウントする頻度辞書を維持します。 
5. プレフィックス ハッシュ値に到達するたびに、そのハッシュの現在の数を「不良」サブ配列 (すべての周波数が偶数であるサブ配列) の累計に加算します。 これが機能するのは、2 つの同一のプレフィックス状態が偶数のカウントを持つサブ配列を定義するためです。 
6. すべてのプレフィックスを処理した後、サブ配列の合計を n(n+1)/2 として計算します。 
7. サブアレイの合計からすべて偶数周波数のサブアレイの数を減算します。 結果は、少なくとも 1 つの値が奇数回出現する部分配列の数になります。 

中心的な考え方は、プレフィックスの等価性が、区間内のすべてのパリティ寄与のキャンセルをエンコードするということです。 

### なぜ効果があるのか

 各プレフィックス ハッシュは、そのインデックスまでのすべての要素のパリティ ベクトルを表します。 r のパリティ状態が l − 1 のパリティ状態と等しい場合、部分配列 [l, r] はすべて偶数の周波数を持ちます。XOR エンコードにより、同一のトグルのマルチセットが同一のハッシュを生成することが保証されます。 したがって、等しいプレフィックス状態をカウントすることは、パリティ ゼロのサブ配列をカウントすることと同等であり、補うことにより必要な答えが得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    rng = 10**6 + 5

    # deterministic pseudo-random using splitmix64 style
    def splitmix64(x):
        x += 0x9e3779b97f4a7c15
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9
        x &= (1 << 64) - 1
        x = (x ^ (x >> 27)) * 0x94d049bb133111eb
        x &= (1 << 64) - 1
        return x ^ (x >> 31)

    # precompute random hashes for values
    h = [0] * (rng)
    seed = 123456789
    for i in range(rng):
        seed = splitmix64(seed + i)
        h[i] = seed

    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        pref = 0
        freq = {0: 1}
        total_even = 0

        for x in a:
            pref ^= h[x]
            total_even += freq.get(pref, 0)
            freq[pref] = freq.get(pref, 0) + 1

        total_subarrays = n * (n + 1) // 2
        print(total_subarrays - total_even)

if __name__ == "__main__":
    solve()
```この解決策は、考えられる値ごとに安定したハッシュを構築することから始まります。 Splitmix64 関数は、実際の衝突を回避するために使用され、高速な決定論的ハッシュのための競技プログラミングの標準です。 

各テスト ケースについて、これらのハッシュに対する XOR を使用してプレフィックス パリティ状態を計算します。 辞書`freq`各プレフィックス状態が出現する頻度を追跡します。 繰り返される各プレフィックス状態は有効な「全偶数周波数」サブ配列を形成するため、それらのカウントを累積します。 

最後に、サブ配列の合計から減算します。 

実装でよくある落とし穴は、初期化を忘れることです。`freq[0] = 1`これは、インデックス 0 から始まるサブ配列を考慮します。もう 1 つは、プロセスごとにランダム化され、実行間で安定しない Python の組み込みハッシュを使用する方法です。 

## 実用的な例

 ### 例 1

 入力:```
n = 3
a = [1, 2, 3]
```プレフィックスの状態を計算します。 

| 私 | a[i] | プレフィックスハッシュ | 前の頻度 | 偶数部分配列を追加しました |
 | --- | --- | --- | --- | --- |
 | 0 | 1 | h1 | {0:1} | 0 |
 | 1 | 2 | h1^h2 | {0:1,h1:1} | 0 |
 | 2 | 3 | h1^h2^h3 | ... | 0 |

 プレフィックスの繰り返しがないため、`total_even = 0`。 サブ配列の合計は 6 です。答えは 6 です。 

これは、すべての要素が異なる場合、すべての部分配列に奇数の出現が含まれることを示しています。 

### 例 2

 入力:```
n = 4
a = [1, 1, 2, 2]
```プレフィックスの進化:

 | 私 | a[i] | 接頭語 | 頻度の更新 | 偶数部分配列を追加 |
 | --- | --- | --- | --- | --- |
 | 0 | 1 | h1 | +0 | 0 |
 | 1 | 1 | 0 | +0 | 1 (h1 の繰り返し) |
 | 2 | 2 | h2 | +0 | 1 |
 | 3 | 2 | 0 | +1 | 2 |

 ここでは、プレフィックス 0 が 2 回繰り返され、[1,1,2,2] のようなバランスのとれたセグメントに対応します。 これらはまさに、すべてのカウントが偶数である部分配列です。

 ## 特殊なケース

 [7] のような単一要素配列の場合、接頭辞の状態は {0, h7} です。 接頭辞の繰り返しがないため、すべて偶数の部分配列はありません。 サブ配列の合計は 1 なので、答えは 1 です。プレフィックス ハッシュはすぐに変更され、繰り返されないため、アルゴリズムは正しくカウントします。 

[5, 5, 5, 5] のような完全に同一の配列の場合、プレフィックス ハッシュは 0 と h5 の間で交互に使用されます。 状態 0 はインデックス 0、2、4 に現れ、複数のプレフィックス一致が繰り返されます。 これらは、[1,2] スタイルのペア キャンセルなど、カウントが偶数であるサブ配列に正確に対応します。 減算ステップではこれらの間隔が正確に削除され、少なくとも 1 つの奇数カウントを持つ間隔だけが残ります。
