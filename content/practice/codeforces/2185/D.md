 ## 解決策
 ## 問題の理解

 配列と一連の更新操作から始めます。 各操作により 1 つの位置に何らかの値が追加されます。 

珍しいのはクラッシュルールです。 更新のたびに、現在の配列のいずれかの要素が次の値よりも大きくなった場合、`h`、コンピュータはすぐにクラッシュします。 これが発生すると、アレイ全体が最後の操作前の状態ではなく、元の状態にリセットされます。 

すべての操作を順番に処理し、クラッシュとリセットが適用されるたびに最終的な配列を出力する必要があります。 

制約は、ソリューションを形作る最初のものです。 すべてのテスト ケースにわたって、配列要素と演算の合計数は最大でも`2·10^5`。 つまり、`O(n + m)`または`O((n+m) log n)`ソリューションは簡単に十分に高速です。 一方、各操作の後に配列全体をスキャンするアプローチでは、最大で`O(nm)`仕事、それは約になります`4·10^10`最悪の場合、操作が不可能になり、完全に実行不可能になります。 

この問題の最も危険な部分は、リセット動作です。 クラッシュしても、最後の操作だけが元に戻されるわけではありません。 テスト ケースの先頭から元の配列を復元します。 

考慮する：```
n = 2, h = 5
a = [1, 1]

operations:
(1, 3)
(1, 3)
```最初の更新後に得られるのは、`[4,1]`。 

2 回目の更新後に得られるのは、`[7,1]`、クラッシュします。 

正しい状態はこうなります`[1,1]`、 ない`[4,1]`。 

最後の操作のみを元に戻すソリューションでは、間違った答えが生成されます。 

もう 1 つの微妙なケースは、最新のリセット以降、いくつかの更新が蓄積されている場合です。```
a = [0]
h = 5

operations:
+2
+2
+2
```状態は次のとおりです。```
[2]
[4]
[6] -> crash -> [0]
```最終的な答えは、`[0]`。 

オーバーフロー チェックは、単一の操作に対してではなく、最後のリセット以降の累積値に対して実行する必要があります。 

3 番目のエッジケースは、次のような更新です。`c = 0`。```
a = [5]
h = 5

operation:
+0
```値はそのまま残ります`5`値が厳密に よりも大きくなった場合にのみクラッシュが発生するため、これは許可されます。`h`。 

正しい出力が残る`[5]`。 

## アプローチ

 最も直接的なシミュレーションでは、現在の配列を明示的に保持します。 すべての操作で 1 つの位置を変更し、要素が次の値を超えているかどうかを確認します。`h`。 クラッシュが発生した場合は、元のアレイを復元します。 

これは文字通りステートメントに従うため、正しいです。 

問題はクラッシュの検出です。 各操作の後、すべてをスキャンする必要があります`n`値が超過しているかどうかを確認する要素`h`。 まで`2·10^5`操作と`2·10^5`要素、これは次のようになります`O(nm)`最悪の場合。 

重要な観察は、操作中に変化する位置は 1 つだけであるということです。 

インデックスごとに、最新のリセット以降に追加された合計量を保存するとします。 させて```
delta[i] = additions applied to position i since the last crash
```位置の現在値`i`は```
a[i] + delta[i]
```操作が追加されるとき`c`位置を決める`b`、位置のみ`b`変化します。 1 つおきの位置は以前と同じ値を維持します。 

つまり、クラッシュは更新された位置によってのみ引き起こされます。 アレイ全体を検査する必要はありません。 

アップデート後`delta[b]`かどうかを確認するだけです。```
a[b] + delta[b] > h
```そうでない場合、操作は成功します。 

それより大きい場合`h`、クラッシュが発生し、前回のリセット以降に蓄積されたすべての変更が消えます。 概念的にはすべて`delta`値がゼロになります。 

全体の長さをリセットする-`n`毎回配列を実行すると、再びコストが高くなります。 蓄積されたすべての更新を一定時間内にクリアする方法が必要です。 

重要なのは、クラッシュ間の更新を「世代」に属するものとして扱うことです。 各位置は、格納されているデルタが最後に更新された世代を記憶しています。 クラッシュが発生すると、生成カウンターがインクリメントされます。 古いデルタは、その世代が現在のものと一致しなくなるため、自動的に無関係になります。 

これは標準的な遅延リセット手法です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | O(n) | 遅すぎる |
 | 最適 | O(n + m) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 元の配列を保存する`a`。 
2. 配列を作成する`delta`長さの`n`、最初はすべてゼロです。 
3. 配列を作成する`stamp`長さの`n`、最初はすべてゼロです。 
4. 現在の世代番号を維持する`cur`、最初は`1`。 
5.手術について`(b, c)`、 変換する`b`ゼロベースのインデックス作成に。 
6. もし`stamp[b] != cur`の場合、保存されたデルタは古い世代に属します。 セット`delta[b] = 0`そして`stamp[b] = cur`。 
7.追加`c`に`delta[b]`。 
8.次のことを確認します。`a[b] + delta[b] > h`。 
9. 条件が false の場合は、次の操作に進みます。 
10. 条件が true の場合、クラッシュが発生します。 インクリメント`cur`1つずつ。 既存のスタンプはすべて古い世代に属するため、これにより、蓄積されたすべてのデルタが論理的にクリアされます。 
11. すべての操作が完了したら、最終的な配列を再構築します。 各ポジションについて:

 - もし`stamp[i] == cur`、その値は`a[i] + delta[i]`。 
- それ以外の場合、その値は単に`a[i]`。 

### なぜ効果があるのか

 どの時点においても、現在の配列は、最新のクラッシュ以降に実行された更新によってのみ元の配列と異なります。 すべてのインデックスについて、`delta[i]`それらの生き残った更新の正確な合計を保存します。 

生成カウンターは、以前のクラッシュからのすべての更新が無視されることを保証します。 世代をインクリメントすることは、すべてのデルタをゼロに設定することと同じですが、配列全体には影響しません。 

操作は 1 つの位置のみを変更するため、その位置のみが新たに超えることができます`h`。 チェック中`a[b] + delta[b]`クラッシュが発生したかどうかを判断するにはこれで十分です。 アルゴリズムは常に問題ステートメントに記述されている正確な状態を維持するため、最終的に再構築された配列は正確になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())

    out = []

    for _ in range(t):
        n, m, h = map(int, input().split())
        a = list(map(int, input().split()))

        delta = [0] * n
        stamp = [0] * n
        cur = 1

        for _ in range(m):
            b, c = map(int, input().split())
            b -= 1

            if stamp[b] != cur:
                delta[b] = 0
                stamp[b] = cur

            delta[b] += c

            if a[b] + delta[b] > h:
                cur += 1

        ans = []
        for i in range(n):
            if stamp[i] == cur:
                ans.append(str(a[i] + delta[i]))
            else:
                ans.append(str(a[i]))

        out.append(" ".join(ans))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```配列`a`これは、すべてのクラッシュがリセットされる元の状態を表すため、決して変更されません。 

ペア`(delta, stamp)`現在の世代からの更新のみを保存します。 クラッシュ後にインデックスが操作されるたびに、その古い情報はスタンプをチェックすることによって遅延して破棄されます。 

最もデリケートな部分はクラッシュハンドリングです。 クラッシュが発生した場合、どの要素も変更しません。`delta`または`stamp`。 増加するだけです`cur`。 これが機能するのは、保存されたすべての更新がすぐに古い世代の一部となり、その時点以降は無視されるためです。 

もう 1 つの微妙な点は、操作の順序です。 まずアップデートを適用し、次に値が次を超えるかどうかをテストします。`h`。 これは、操作の実行後にクラッシュが発生するステートメントと一致します。 

Python の整数には任意の精度があるため、おおよその値までの値が得られます。`2·10^14`オーバーフローの問題は発生しません。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m) | 各操作と各最終再構成ステップは定数時間です。 
| スペース | O(n) | 配列`delta`そして`stamp`位置ごとに保存されます |
