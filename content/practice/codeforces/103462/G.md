 ## 解決策
 ## 問題の理解

 長さ最大 100 の非表示の文字列を操作しています。文字列には 2 つの異なる小文字が使用されていますが、どの文字であるかは示されません。 それを知る唯一の方法は、選択したパターンが隠し文字列の連続した部分文字列として現れるかどうかを尋ねることです。 このようなクエリは最大 200 件発行でき、その後は正確な非表示文字列を出力する必要があります。 

各クエリは、提案された文字列が未知のターゲット内のどこかに出現するかどうかについての「はい」または「いいえ」の質問です。 十分な情報を収集したら、完全な文字列を出力する必要があります。 

アルファベットのサイズがちょうど 2 つであるという制約が、重要な構造上の制限です。 これがなければ、このような厳しいクエリ バジェットでは部分文字列クエリだけでは不十分になります。 記号が 2 つだけあるため、隠された文字列には十分な規則性があり、アルファベットと正確な配列の両方を突き止めることができます。 

最大 100 という小さな長さの制限も同様に重要です。 これは、二次推論は境界線にあるものの可能であること、および増分位置情報を収集するのではなく、多数の可能性を排除するように各クエリを選択する必要があることを示唆しています。 

素朴だが自然な考え方は、部分的に構築された文字列のすべての部分文字列をチェックして候補をテストし、文字列を 1 文字ずつ再構築しようとすることです。 これはすぐに概念的な問題に遭遇します。部分再構成の一貫性を検証するには、そのすべての部分文字列をチェックする必要があり、これは長さが二次関数的に増加します。 長さが最大 ​​100 であるため、分岐を考慮する前でもすでにクエリ制限を超えています。 

隠れた主な問題は、部分文字列クエリでは位置情報が提供されないことです。 肯定的な答えは、パターンがどこに現れるかではなく、どこかに存在することを示しているだけです。 これは、グローバルな部分文字列情報をローカルな制約に変換しない限り、文字を直接「検索」しようとするアプローチは失敗することを意味します。 

## アプローチ

 ブルートフォース再構築では、一度に 1 文字ずつ拡張して文字列を構築しようとします。 すでにプレフィックスを構築しており、次の文字を決定したいとします。 可能な 2 つの文字をそれぞれ暫定的に追加し、結果の部分文字列が非表示の文字列と互換性があるかどうかを確認します。 互換性とは、候補のすべての部分文字列が非表示の文字列にも出現する必要があることを意味します。 これをチェックするには、候補のすべての部分文字列をテストする必要があります。これは合計 O(n^2) 回のチェックであり、それぞれにクエリのコストがかかります。 これは、中程度の長さであっても、すでに 200 クエリの制限を超えています。 

重要な観察は、正確さを検証するために完全な部分文字列を閉じる必要はないということです。 必要なのは、禁止された部分文字列を含む文字列を決して構築しないようにすることだけです。 非表示の文字列はちょうど 2 文字で完全に固定されているため、正しいプレフィックスは常にその部分文字列のままである必要があり、有効な拡張子はすべてこのプロパティを保持する必要があります。 これにより、検証の問題は、候補拡張子が依然として隠し文字列内のどこかに埋め込まれる可能性があるかどうかをチェックすることに軽減されます。 

すべての部分文字列を検証する代わりに、現在の候補文字列自体が非表示文字列の部分文字列であるという不変条件を維持します。 これは非常に強力で使いやすい状態です。 候補拡張子がこのプロパティを破った場合、単一の部分文字列クエリによって即座に検出できます。 これがソリューションを実現可能にするものです。グローバルな一貫性条件を、決定ごとの単一のオラクル呼び出しに変換します。 

ソリューションの最終的な構造は貪欲な再構築になります。 まず文字列内で使用されている 2 文字を特定し、次に既知の有効な部分文字列を一度に 1 文字ずつ拡張して、部分文字列の有効性を常に維持しながら答えを構築します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース部分文字列一貫性チェック | O(n³) クエリ | O(n) | 遅すぎる |
 | 部分文字列検証を備えた貪欲な拡張機能 | O(n) クエリ | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ステップ 1: 非表示の文字列で使用されている 2 つの文字を特定する

 26 個すべての小文字を 1 文字のクエリでテストします。 クエリが true を返した場合にのみ、非表示文字列に文字が表示されます。 ちょうど 2 つの文字が正の値を返します。文字列で使用される記号はこれらだけです。 

このステップでは、問題を 26 の可能性から 2 進数のアルファベットに減らします。 

### ステップ 2: 非表示の文字列の長さを決定する

 長すぎる候補文字列に対する部分文字列クエリは失敗するが、実際の長さ以下の文字列は構造によっては表示される可能性があるという事実を利用します。 これを利用して、最大長 L をバイナリ検索して、慎重に選択された長さ L のパターンが隠し文字列に表示されるようにします。 一般的な選択は、検出された 2 つの文字を交互に配置するパターンです。これにより、ランへのバイアスが回避され、実際の部分文字列が存在する場合は一致する可能性が高まります。 

これにより、正確な長さ n が得られます。 

### ステップ 3: 文字列を貪欲に構築する

 答えを左から右に構築します。 いつでも、隠し文字列の部分文字列であることが保証されている現在の文字列 S を維持します。 

各位置 i に対して、可能な 2 つの文字 c をそれぞれ追加してみます。 候補 S + c を作成し、単一の部分文字列クエリを使用して、この新しい文字列が非表示文字列のどこかにまだ存在するかどうかを確認します。 

true が返された場合は、c を受け入れて先に進みます。 そうでない場合は、それを拒否し、他の文字を試します。 真の文字列が存在するため、2 つのオプションのうちの 1 つが常に有効になります。 

### ステップ 4: 再構築された文字列を出力する

 n 文字を構築したら、その結果を最終的な答えとして出力します。 

### なぜ効果があるのか

 不変条件は、i 文字を処理した後、構築された文字列 S が常に非表示文字列の部分文字列になるということです。 最初は、これは有効な開始文字であればどれでも当てはまります。 

実際の文字列自体には再構築している完全なプレフィックスが含まれているため、各拡張ステップで真の次の文字はこのプロパティを保持する必要があります。 したがって、2 つの候補をテストすると、少なくとも 1 つが成功する必要があります。 どちらも失敗した場合は、隠し文字列のどの部分文字列も、次の正しい文字によって拡張された真のプレフィックスと一致しないことを意味し、これは隠し文字列自体の存在と矛盾します。 

これにより、実際の文字列から逸脱することがなくなり、最終的には正確な再構築が保証されます。 

## Python ソリューション```python
import sys

input = sys.stdin.readline
flush = sys.stdout.flush

def ask(s: str) -> bool:
    print("ASK", s)
    flush()
    return int(input().strip()) == 1

def main():
    letters = []
    for c in "abcdefghijklmnopqrstuvwxyz":
        if ask(c):
            letters.append(c)

    a, b = letters[0], letters[1]

    # determine length (simple safe approach: grow until failure pattern-based probing)
    # since n <= 100, we can safely probe increasing lengths with a stable pattern
    # using alternating string ensures we detect a valid upper bound
    pattern = (a + b) * 100

    # binary search for max L such that pattern[:L] is substring
    lo, hi = 1, 100
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if ask(pattern[:mid]):
            lo = mid
        else:
            hi = mid - 1

    n = lo

    # reconstruct greedily
    # start from a valid single character
    cur = a if ask(a) else b

    while len(cur) < n:
        for c in (a, b):
            if ask(cur + c):
                cur += c
                break

    print("ANSWER", cur)
    flush()

if __name__ == "__main__":
    main()
```この解決策は、単一文字の部分文字列クエリを通じてアルファベットを識別することから始まります。 その後、交互パターンに対する二分検索を使用して長さを推定します。これは、誤って部分文字列の一致に偏りをもたらす可能性のある長時間の実行を回避するために選択されています。 最後に、現在のプレフィックスが非表示の文字列の部分文字列として存在する必要があるという不変条件を常に維持しながら、文字列を貪欲に再構築します。 

実装の微妙な詳細は、各クエリの後の即時フラッシュです。 インタラクティブな問題では、フラッシュを見逃すと同期が中断され、正確さに関係なく未定義の動作が発生します。

 ## 特殊なケース

 最小のエッジ ケースは、文字列の長さが 2 の場合です。この場合、再構成ステップはアルファベット検出直後に開始され、各文字が部分文字列チェックによって個別に検証されるため、貪欲な拡張機能は引き続き機能します。 オラクルは、正しい完全な文字列プレフィックスに対してのみ true を返します。 

2 番目のエッジ ケースは、文字列が次のような繰り返し文字で構成されている場合です。`aaaaa`。 ここで、正しい文字が識別されると、その文字を含む拡張子はすべて有効のままですが、他の文字はすぐに失敗します。 貪欲なプロセスは決定論的になり、常に曖昧さのない有効な拡張子を選択します。 

もう 1 つの特殊なケースは、両方の文字が頻繁に交互に現れる場合です。`ababab`。 どちらの文字も局所的には優勢ではありませんが、正しいプレフィックスはすべて有効な部分文字列のままであるため、オラクルは各ステップで真の拡張子を受け入れ続けます。 このアルゴリズムは部分文字列の存在以外の頻度や構造に依存しないため、変更は正確さに影響しません。
