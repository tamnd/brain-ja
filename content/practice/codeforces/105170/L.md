 ## 解決策
 ## 問題の理解

 固定容量でアクティブ化されたアイテムの充電システムをシミュレートしています。 各テスト ケースには容量が与えられます`k`そして部屋のコレクション:`x`小さな部屋と`y`広い部屋。 プレイヤーはこれらの部屋を任意の順序でクリアでき、クリアされた各部屋はチャージに貢献します。小さな部屋では 1 ユニットが与えられ、大きな部屋では 2 ユニットが与えられます。 蓄積された電荷が一定以上になるたびに`k`、アイテムは一度使用され、料金はゼロにリセットされます。 

目標は、アイテムをアクティブ化できる回数を最大化することです。 

最大の難点は、部屋の順番が固定されていないことです。 広い部屋はより価値がありますが、使用をトリガーするのに必要なユニットが 1 つだけである状況では「過充電」のリスクもあり、到達するとすぐにバーがリセットされるため、追加のユニットは事実上無駄になります。`k`。 

制約は大きく、最大で`2 × 10^5`テストケースと値`k, x, y`まで`10^9`。 これにより、部屋全体のシミュレーションや、部屋ごとに反復される貪欲な構築が即座に排除されます。 各テスト ケースは一定時間内に処理される必要があります。 

微妙なエッジケースは、大きな部屋の動作が残りの容量に応じて異なるという事実から生じます。 現在の料金が`k-1`、小さな部屋と大きな部屋の両方で使用が完了しますが、大きな部屋では 1 ユニットが無駄になります。 常に大きな部屋を最初に使用したり、常に値に応じて貪欲に詰め込むような素朴な貪欲なアプローチは、残りの容量を埋めるために小さな部屋を保持する方が効率的であるシナリオでは失敗します。 

たとえば、次のように考えてみましょう`k = 5, x = 4, y = 2`。 最初に大きな部屋を選択すると、しきい値を繰り返しオーバーシュートして容量が無駄になる可能性がありますが、混合戦略では、小さな部屋を慎重に使用して正確なギャップを埋めることで、より多くのアクティベーションを達成します。 

本当の問題は部屋を注文することではなく、サイズの完全なサイクルが何回あるかを数えることです。`k`のマルチセットから形成できます`1`と`2`s.

 ## アプローチ

 ブルートフォースアプローチでは、部屋のあらゆる可能な順序を明示的にシミュレートします。 注文ごとに、現在の料金を維持し、部屋を 1 つずつ消費し、アクティベーションをカウントします。 これは正しいですが、まったく実行不可能です。 順列の数は`(x + y)! / (x! y!)`、これは、次のような小さな入力であっても天文学的に大きくなります。`x = y = 50`。 

より構造化されたブルートフォースの改善は、各ステップで両方の部屋タイプを試しながら貪欲にシミュレーションすることです。 この決定は将来の剰余に依存するため、依然として指数関数的に分岐しており、依然として扱いにくいものです。 

重要な観察は、順序はフル充電に近づいた瞬間の局所的にのみ重要であるということです。 ほとんどのプロセスでは、蓄積された電荷の合計のみを考慮し、電荷がどのように構築されたかは気にしません。 すべての部屋が固定額を寄付するため、問題は、何倍に到達できるかを最大化することに帰着します。`k`のマルチセットを使用して`1`そして`2`。 

総和で考えることができる`S = x + 2y`。 順序を無視した場合、答えの上限は次のようになります。`S // k`。 ただし、大きな部屋では避けられない無駄が発生する可能性があるため、順序はこの制限を実現できるかどうかに影響します。`k`が奇数であるか、強制的に剰余状態になっている場合です。 

推論するための正しい方法は、完全なサイクルを残りの動作から分離することです。 正確に到達するたびに`k`、部屋のいくつかの組み合わせを消費し、合計すると少なくとも`k`。 あらゆる形成方法の中で`k`、後でさらに悪い残余パターンが発生しない限り、大きな部屋を使用することが常に最適です。 これにより、標準的な最適化が行われます。つまり、大きな部屋は貪欲に処理しますが、必要に応じて小さな部屋を使用してパリティのような残留物を修正します。 

最終的なソリューションは、テスト ケースごとの定数時間の算術計算になります。`k`チャンクは利用可能なものから形成できます`2`最初に s を追加し、次に次のように補足します。`1`s.

 ## アルゴリズムのチュートリアル

 最低でも何回チャージできるか数えたい`k`を使用して`x`ものと`y`2 つで、アクティブ化するたびにすぐにリセットされます。 

1. 広い部屋を一括して優先順位を付けることで、何回完全に使用できるかを計算します。 各大きな部屋は 2 に寄与するため、最初に、形成する際に完全に活用できる大きな部屋の数を検討します。`k`-サイズの合計。 自然な最初のステップは、満杯の数を計算することです。`k`広い部屋だけを使ってブロックを構築できます。`y * 2 // k`。 これによりベースラインが得られますが、混合使用法を完全には把握できません。 
2.完全なブロックをゼロから構築するという観点から考えるのではなく、プロセスを総エネルギーを消費するものとして再解釈します。`S = x + 2y`。 可能な最大使用量は次のように制限されます。`S // k`。 これにより、食べ残しを適切に管理すれば、いつでも近づくことができる上限が得られます。 
3. 唯一の障害は、広い部屋を貪欲に使用した後の残りの容量です。 できるだけ多くの大きな部屋を使用すると、効率的に埋めることができない残りの部屋が発生する可能性があります。`k`小さな部屋だけではギャップを繰り返し埋めるには不十分な場合があるため、小さな部屋のみを使用します。 
4. 大部屋の残りの寄与を剰余として計算する`k`。 させて`large_sum = 2 * y`。 そこから可能な限り多くの完全な用途を抽出します。`full_from_large = large_sum // k`、および残り`rem = large_sum % k`。 
5. 今度は小さな部屋を組み込みます。 大部屋後の残りの容量は`rem + x`。 追加のアクティベーションごとに必要となるのは、`k`単位なので計算します`(rem + x) // k`追加の用途。 
6. 最終的な答えは次のとおりです。`full_from_large + (rem + x) // k`。 

各ステップは、保証された完全なサイクルを残りのマージから分離するように設計されています。 重要な決定は、大きな部屋が梱包の不連続の唯一の原因であるため、最初に大きな部屋を処理することです。 一度縮小されたモジュロ`k`、小さな部屋は、残りのギャップのユニットフィラーのように動作します。 

### なぜ効果があるのか

 このアルゴリズムは、できるだけ多くの完全なデータを抽出した後、`k`大部屋の合計貢献度からグループを構成する場合、残りの大部屋の貢献度は厳密に以下になります。`k`そして、独立して別のアクティベーションを形成することはできなくなります。 この時点で、残りの柔軟性はすべて小さな部屋にあり、構造を変更せずに残りの合計を増やすことしかできません。 すべてのアクティベーションには正確な要求があるため、`k`単位を増やすと、残りの問題は、結合された残りのプールに対する純粋な整数の除算になります。 これにより、注文によって完全な数が増加することはありません。`k`計算された式を超えるしきい値。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        k, x, y = map(int, input().split())

        large_sum = 2 * y
        full_from_large = large_sum // k
        rem = large_sum % k

        total_rem = rem + x
        ans = full_from_large + total_rem // k

        print(ans)

if __name__ == "__main__":
    solve()
```このコードは、大きな部屋の寄与と小さな部屋との残りの結合への分解を直接実装します。 最初のブロックは、大きな部屋だけの合計値から完全なアクティベーションをいくつ抽出できるかを計算します。 小さな部屋は、次のアクティブ化に向けて部分的な進行を完了できる唯一の柔軟なフィラーであるため、大きな部屋の残りはすべての小さな部屋と結合されます。 

ここでよくある間違いは、順序をシミュレートしようとしたり、大小の部屋を貪欲に交互に配置しようとしたりすることです。 このソリューションは、プロセスを総寄与と剰余の算術演算に集約することで、これを完全に回避します。

 ## 特殊なケース

 エッジケースの 1 つは次の場合に発生します。`k = 1`。 どの部屋もすぐにアクティベーションをトリガーするため、答えは次のようになります。`x + 2y`。 数式はこれを正しく処理します。`large_sum // 1 = 2y`そして残りは何も貢献しません。 

もう 1 つの特殊なケースは、部屋が小さい場合です。 アルゴリズムは次のようになります。`x // k`、 以来`large_sum = 0`。 これは直接的な直感と一致します。 

広い部屋のみが存在する場合、結果は次のようになります。`(2y) // k`、2 を同じサイズのブロックにグループ化することに一致します`k`。 

最も微妙なケースが発生するのは、`k`よりもわずかに大きいです`2y`、大きな部屋だけでは単一のアクティベーションを形成できません。 その状況では、大きな部屋の残りは完全に保存され、小さな部屋と結合されるため、順序付けによって潜在的なアクティブ化が失われることはありません。
