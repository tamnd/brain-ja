 ## 解決策
 ## 問題の理解

 左から右にインデックスが付けられた穴の列があります。 各ホールにはジャンプ長が含まれます。 ボールが穴に落ちた場合`i`、すぐに移動します`i + a[i]`。 そこから、新しいホールの値を使用して再度ジャンプし、次のジャンプが配列から出るまでこれが続きます。 

2 種類の操作をオンラインで処理する必要があります。 

最初の操作は 1 つのホールのジャンプ長を変更します。 

2 番目の操作では、ある穴からボールを開始し、2 つの値を要求します。 

1. ボールがアレイから出る前に訪れた最後のホール。 
2. 実行されたジャンプの総数。 

この構造は実際には有向グラフであり、すべてのノードが別のホールまたは配列の外側への出力エッジを 1 つだけ持ちます。 すべてのジャンプは厳密に右に移動するため、サイクルは不可能です。 すべてのパスは最終的にアレイから出ます。 

制約が大きいため、単純なシミュレーションでは遅すぎます。 ホール数とクエリ数の両方が達成可能`10^5`。 すべてのクエリの単純なシミュレーションでは、毎回ほぼ配列全体を処理する可能性があります。 最悪の場合、すべての穴に価値があると想像してください`1`。 穴からのスタート`1`必要`10^5`ジャンプします。 これを行うのは、`10^5`クエリは次のような結果につながります`10^10`1秒に収まる範囲をはるかに超えた操作。 

更新操作が問題を厄介にします。 1 つのジャンプ長を変更すると多くのパスに影響を与える可能性があるため、すべての答えを 1 回事前計算するだけでは十分ではありません。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

次の入力を考えてみましょう。```
3 1
3 1 1
1 1
```穴からのスタート`1`、ボールはすぐに出ます。`1 + 3 = 4`。 正しい答えは次のとおりです。```
1 1
```不注意に実装すると穴が印刷される可能性があります`4`問題が終了する前に最後の有効なホールを要求しているにもかかわらず、最後の位置として。 

もう 1 つの微妙なケースは、更新の変更が 1 つのローカル領域内でのみジャンプする場合に発生します。```
5 3
1 1 1 1 1
0 3 5
1 1
```更新後のパスは次のようになります。`1 -> 2 -> 3 -> outside`正しい答えは次のとおりです。```
3 3
```更新後に前処理が正しく再構築されない場合、古いチェーンからの古い情報が残り、より長いパスが生成される可能性があります。 

最後によくある間違いは、ブロックの境界にあります。```
6 1
2 2 2 2 2 2
1 1
```ジャンプは次のとおりです。`1 -> 3 -> 5 -> outside`答えは次のとおりです。```
5 3
```平方根分解を使用すると、多くの実装では、ブロックの外への最初のジャンプではなく、ブロックの最後のインデックスで誤って停止してしまいます。 これにより、チェーン圧縮ロジックが壊れます。 

## アプローチ

 ブルートフォース ソリューションは、ボールの動きを直接シミュレートします。 

ホールから始まるクエリの場合`x`、繰り返しジャンプします`x + a[x]`位置が配列から外れるまで。 ジャンプが何回行われたかを数え、最後の有効なホールを覚えてください。 配列値を 1 つ変更するだけなので、更新は簡単です。 

これが機能するのは、グラフが非周期的であり、すべてのシミュレーションが最終的に終了するためです。 問題は走行時間です。 最悪の場合、すべてのジャンプは右に 1 ステップしか移動しません。 単一のクエリにコストがかかる`O(n)`。 と`10^5`クエリの場合、全体の複雑さは次のようになります。`O(nm)`、それは約です`10^10`操作。 

重要な観察は、ジャンプは右にのみ移動するということです。 そのため、インデックスをブロックにグループ化し、同じブロック内にあるすべてのジャンプを圧縮できます。 

配列を約サイズのブロックに分割するとします。`sqrt(n)`。 あらゆるインデックスに対して`i`、私たちは以下を保管します:

 1. 現在のブロックの外側で到達可能な次の位置`i`。 
2. そこに到達するために必要なジャンプの数。 
3. ブロックを離れる前に訪れた最後のホール。 

現在、クエリはジャンプごとに実行されなくなりました。 代わりに、ブロックごとにジャンプします。 くらいしかないので`sqrt(n)`ブロックを使用すると、各クエリがはるかに高速になります。 

更新も管理可能です。 変化`a[i]`すべてのジャンプは右方向に移動するため、同じブロック内のパスにのみ影響します。 1 つのブロックを再構築できます`O(sqrt(n))`すべてを再計算するのではなく、時間を計算します。 

これは、ブロック内のパス圧縮を伴う古典的な平方根分解です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |`O(nm)`|`O(1)`| 遅すぎる |
 | 最適 |`O((n + m)\sqrt{n})`|`O(n)`| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 配列をおよそのサイズのブロックに分割します。`sqrt(n)`。 

もし`n = 10^5`、ブロックサイズは約`320`。 これにより、おおよその結果が得られます`320`ブロックにより、クエリと更新の両方の効率が維持されます。 
2. ポジションごとに`i`、3 つのヘルパー値を計算します。`nxt[i]`現在のブロックの外側で到達した最初の位置を格納します。`cnt[i]`到達するまでに何回ジャンプする必要があるかを保存します`nxt[i]`。`last[i]`ブロックを離れる前に訪問した最後の有効なホールを保存します。 
3. 各ブロック内のインデックスを右から左に処理します。 

ジャンプは常により大きなインデックスに向かうため、宛先情報は処理時にすでに計算されています。`i`。 
4. しましょう`j = i + a[i]`。 

もし`j`配列を離れるか、別のブロックに属します。 

-`nxt[i] = j`-`cnt[i] = 1`-`last[i] = i`さもないと：

-`nxt[i] = nxt[j]`-`cnt[i] = cnt[j] + 1`-`last[i] = last[j]`これにより、ブロック内のすべてのジャンプが 1 つのトランジションに圧縮されます。 
5. から始まる質問に答えるには`x`、繰り返し：

 - 追加`cnt[x]`答えに。 
- 記録`last[x]`最新の有効なホールとして。 
- に移動します`nxt[x]`。 

まで続ける`x > n`。 

各反復では、ブロック全体に相当するジャンプがスキップされます。 
6. 位置で更新を処理するには`x`、 変化`a[x]`を含むブロックのみを再構築します。`x`。 

ジャンプは厳密に右に移動するため、以前のブロックはこのブロックに依存しません。 

### なぜ効果があるのか

 あらゆるインデックスに対して`i`、タプル`(nxt[i], cnt[i], last[i])`現在のブロック内のジャンプのシーケンス全体を要約します。 

次のジャンプがすでにブロックから出ている場合、要約は即座に行われます。 

それ以外の場合は、からのパス`i`最初にジャンプするのは`j`同じブロック内にあり、パスの残りの部分は正確に事前計算された要約です。`j`。 インデックスは右から左に処理されるため、この情報はすでに正確です。 

クエリ中に繰り返し次のように実行します`nxt`オリジナルのジャンプ シーケンスを正確に再現しますが、ブロック トランジションに圧縮されます。 ジャンプ数は保持されるため、`cnt[i]`スキップされたジャンプの正確な数を保存します。 最後に訪れたホールは保存されます。`last[i]`ブロック境界を越えたり、配列から出る前に、最後の有効な位置を追跡します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = [0] + list(map(int, input().split()))

    B = int(n ** 0.5) + 1

    nxt = [0] * (n + 1)
    cnt = [0] * (n + 1)
    last = [0] * (n + 1)

    def rebuild(block):
        l = block * B + 1
        r = min(n, (block + 1) * B)

        for i in range(r, l - 1, -1):
            j = i + a[i]

            if j > n or (j - 1) // B != block:
                nxt[i] = j
                cnt[i] = 1
                last[i] = i
            else:
                nxt[i] = nxt[j]
                cnt[i] = cnt[j] + 1
                last[i] = last[j]

    num_blocks = (n + B - 1) // B

    for b in range(num_blocks - 1, -1, -1):
        rebuild(b)

    out = []

    for _ in range(m):
        query = list(map(int, input().split()))

        if query[0] == 0:
            x, y = query[1], query[2]
            a[x] = y
            rebuild((x - 1) // B)
        else:
            x = query[1]

            total = 0
            ans_last = x

            while x <= n:
                total += cnt[x]
                ans_last = last[x]
                x = nxt[x]

            out.append(f"{ans_last} {total}")

    sys.stdout.write("\n".join(out))

solve()
```問題のステートメントは当然 1 から始まるため、配列は 1 から始まるインデックスを使用して保存されます。 これにより、ジャンプ中にインデックス調整を繰り返す必要がなくなります。 

の`rebuild`この関数は、1 つのブロックのすべての圧縮情報を再計算します。 インデックスを右から左に処理することが重要です。 取り扱い時`i`、目的地`j`常により大きい`i`なので、その圧縮された情報はすでに利用可能です。 

条件```
if j > n or (j - 1) // B != block:
```次のジャンプが現在のブロックから出るかどうかを確認します。 の`(j - 1) // B`式は、1 から始まるインデックスを 0 から始まるブロック番号に変換します。 が足りない`-1`これは一般的なオフバイワンバグです。 

クエリ中に、ループはすべてのジャンプを個別にシミュレートしません。 代わりに、各反復は次を使用して別のブロックに直接スキップします。`nxt[x]`。 スキップされたジャンプの総数は、次のように累積されます。`cnt[x]`。 

変数`ans_last`次のブロックに移動する前に更新されます。 これにより、配列を終了する前に、最後の有効なホールが常に保存されることが保証されます。 

更新では 1 つのブロックのみが再構築されます。 更新のたびに構造全体を再計算すると、時間がかかりすぎます。
