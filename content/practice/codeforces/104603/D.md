 ## 問題の理解

 コンテストには固定の構造が与えられています。各コンテストには次のようなものがあります。$K$難易度やレベルなど$i$正確に必要です$C_i$問題。 最低限使えるレベルごとに問題を分類：級の問題$d$レベルにのみ割り当てることができます$d, d+1, \dots, K$。 各問題は全体で最大 1 回使用でき、コンテスト内では 1 つのレベルのみを使用できます。 

サプライズもございます$P_i$学年の問題の$i$。 タスクは、形成できる完全なコンテストの数を最大化することです。各コンテストは、次の条件に従って完全に満たされる必要があります。$C_i$要件を満たし、利用可能な問題を再利用せずに使用します。 

主な問題点は、高グレードの問題は柔軟性があり、より高いレベルにも対応できるのに対し、低グレードの問題は制限されていることです。 これにより、レベル間でフローのような依存関係が生じ、早期の決定が後の実現可能性に影響を与えます。 

制約は以下に達します$K \le 10^5$および最大値$10^9$、コンテストごとのシミュレーションは即座に除外されます。 コンテストを 1 つずつ貪欲に構築しようとしても、考えられるコンテストの数が膨大になる可能性があるため、非常に時間がかかりすぎます。 

素朴な貪欲な割り当ての微妙な失敗例は、低グレードの問題を熱心に割り当てすぎると発生します。 

例：```
K = 2
C = [1, 1]
P = [1, 1]
```不注意な戦略により、グレード 1 の問題がレベル 1 に割り当てられ、グレード 2 の問題がレベル 2 に割り当てられ、コンテストが 1 つ生成される可能性がありますが、これは正しいことです。 しかし、これをスケールすると次のようになります。```
K = 2
C = [1, 1]
P = [100, 1]
```レベル 1 のグレード 1 の問題を貪欲に消費し、その柔軟性を無視した場合でも、正しい答えが得られる可能性がありますが、より複雑なディストリビューションでは、低グレードの問題は、それを使用できる最も制限されたレベルに保存される必要があるため、より高いレベルでの枯渇につながります。 

主な困難は、低学年の不足によって生じたギャップを埋めるために、柔軟な高学年の問題を常に利用できるようにすることです。 

## アプローチ

 強引な視点は、コンテストを一つずつ構築してみることです。 各コンテストでは、レベル 1 からレベルまでを満たすように努めます。$K$、常に、割り当てが可能な最小グレードの実行可能な利用可能な問題を選択します。 これは制約を直接尊重するため正しいですが、計算上実行不可能です。 

各コンテストでは複数のレベルをスキャンする必要があり、各レベルで使用可能な問題のグレードを検索する必要がある場合があります。 最悪の場合、最大で$10^5$レベルと潜在的に$10^9$コンテストでは、このアプローチは不可能になります。 

構造的な洞察は視点を反転することです。コンテストを構築する代わりに、与えられた数値の実現可能性をテストします。$x$。 構築したい場合$x$コンテスト、その後レベルアップ$i$必要$x \cdot C_i$レベルに割り当てられた問題$i$、これらはすべての問題グレードから取得する必要があります$d \le i$。 

これにより、問題は累積制約の下での実現可能性チェックに変わります。 私たちは、使用可能なポジションの下限を設けて供給を効果的に配分しています。これは当然、処理レベルが昇順であり、柔軟で高グレードの余剰能力を維持していることを示唆しています。 

重要な観察は、高グレードの問題はいつでも下方に「遅らせる」ことができるが、低グレードの問題は上に進むことができないということです。 したがって、低レベルから高レベルまで処理し、各レベルを満たした後に使用可能な問題がどれだけ残っているかを追跡します。 

次に、実現可能な最大値を二分探索します。$x$、実現可能性は単調なので、構築できれば$x$コンテスト、あらゆるものを構築することもできます$x' < x$。

### なぜ効果があるのか

 実現可能性チェックでは、あらゆるレベルでプレフィックスの一貫性条件が強制されます。$i$、グレードまでの使用可能な総供給量$i$レベルまでの総需要に十分でなければなりません$i$。 高グレードの問題は下位にのみ移動できるため、有効な割り当てはこれらのプレフィックス制約を満たさなければなりません。 

これにより、低位から高位への貪欲な累積が必要かつ十分になります。これは、柔軟性が存在する唯一の方向に一致するため、将来の再割り当てでは違反したプレフィックスを修復できません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(x, K, C, P):
    # current available pool of usable problems
    pool = 0
    
    for i in range(K):
        pool += P[i]
        need = x * C[i]
        
        if pool < need:
            return False
        
        pool -= need
    
    return True

def main():
    K = int(input())
    C = list(map(int, input().split()))
    P = list(map(int, input().split()))
    
    lo, hi = 0, 10**18
    ans = 0
    
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid, K, C, P):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1
    
    print(ans)

if __name__ == "__main__":
    main()
```このソリューションは、すべての問題グレードを累積的に処理する単一の実現可能性関数を中心に構築されています。 重要な実装の詳細は、実行中です。`pool`、現在の学年の境界までに利用可能なすべての問題を表します。 

減算ステップ`pool -= need`これは重要です。各問題が 1 回だけ使用されることが強制されます。 この手順を省略すると、レベル間で容量が誤って再利用されてしまいます。 

実行可能性が単調であるため、二分探索が適用されます。$x$。 一定数のコンテストを形成できなくなると、需要の線形スケーリングにより、それ以上の数のコンテストも失敗します。
