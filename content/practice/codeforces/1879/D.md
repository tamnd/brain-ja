 ## 解決策
 ## 問題の理解

 負ではない整数の配列が与えられます。 すべてのサブ配列について$[l,r]$、その部分配列内のすべての要素の XOR を計算します。 その XOR 値を次のようにします$f(l,r)$。 

サブ配列の寄与は XOR だけではありません。 これに部分配列の長さが乗算されます。$$f(l,r)\cdot(r-l+1)$$タスクは、すべての部分配列にわたってこの値を合計し、結果のモジュロを出力することです。$998244353$。 

直接実装すると、すべてが検査されます。$O(n^2)$サブアレイ。 と$n\le 3\cdot10^5$、それはおおよその意味になります$4.5\times10^{10}$サブ配列の場合、2 秒以内ではまったく不可能です。 たとえ$O(n^2)$サブ配列ごとに少数の演算のみを実行するアルゴリズムは、制限をはるかに超えています。 

配列の値は最大でも$10^9$, したがって、すべての数値は 30 ビットに収まります。 問題で XOR 値の合計が必要な場合は常に、XOR がすべてのビット位置で独立して動作するため、通常は各ビットを個別に処理する方が有益です。 

微妙な特殊なケースは、長さの乗数が両方のエンドポイントに依存することです。 例えば：```
2
1 1
```サブアレイ:```
[1] -> 1 * 1 = 1
[1,1] -> 0 * 2 = 0
[1] -> 1 * 1 = 1
```答え = 2。 

XOR ビットを持つサブ配列の数をカウントするだけのソリューション$1$長さの重み付けを見逃して、間違った結果を生成します。 

もう 1 つの簡単な間違いは、サブ配列 XOR がプレフィックス XOR によって表されることを忘れていることです。```
1
5
```XOR を持つ唯一のサブ配列$5$、 長さ$1$、 答え$5$。 

この場合、配列を開始する前にプレフィックス XOR が必要です。$pref_0=0$。 このプレフィックスを省略すると、すべてのサブ配列が位置から始まります。$1$カウントから消えること。 

3 番目のバグの原因はモジュラー演算です。 加重合計は非常に大きくなる可能性があります。 Python の整数はオーバーフローしませんが、この問題では最終結果のモジュロが必要です$998244353$、中間累積もこの値を法として削減する必要があります。 

## アプローチ

 ブルートフォースソリューションはすべてのペアを列挙します$(l,r)$。 プレフィックス XOR を使用すると、各サブ配列 XOR を次のように計算できます。$O(1)$:$$f(l,r)=pref_r\oplus pref_{l-1}$$次に追加します$$(pref_r\oplus pref_{l-1})(r-l+1)$$答えに。 

これは問題の定義に直接従うため、正しいです。 問題はサブアレイの数です。 がある$$\frac{n(n+1)}2$$そのうち、約に達します$4.5\times10^{10}$いつ$n=3\cdot10^5$。 

重要な観察は、XOR はビットごとに分解できるということです。 

1 つのビット位置を考慮します$b$。 最終的な答えへの貢献度は次のとおりです。$$2^b \times \sum_{\text{subarrays whose XOR has bit }b=1} (r-l+1)$$したがって、実際のタスクは次のようになります。 

各ビットについて、そのビットの XOR が次と等しいすべての部分配列の合計長を見つけます。$1$。 

このビットにプレフィックス XOR パリティを導入します。 させて$$p_i = \text{bit } b \text{ of } pref_i.$$サブアレイの場合$[l,r]$、$$\text{bit } b \text{ of } f(l,r) = p_r \oplus p_{l-1}.$$これら 2 つのパリティが異なる場合、ビットは正確に影響します。 

ここで、プレフィックス インデックスを使用してサブ配列を書き換えます。$$j=l-1,\qquad i=r.$$部分配列の長さは次のようになります。$$r-l+1=i-j.$$したがって、固定ビットの場合、次のようにする必要があります。$$\sum_{0\le j<i\le n,\ p_i\ne p_j} (i-j).$$これは、プレフィックス XOR パリティのペアカウントの問題です。 

プレフィックスの位置を左から右に処理するとします。 ポジションに到着したら$i$、以前のすべてのポジションが必要です$j$パリティが異なるのは$p_i$。 

彼らの貢献は、$$\sum (i-j) = (\text{count})\cdot i - \sum j.$$したがって、パリティごとに$0$そして$1$、必要なのは次のものだけです。 

- そのパリティを持つ以前のプレフィックスの数、
 - それらのインデックスの合計。 

その後、すべてのプレフィックス位置を次のように処理できます。$O(1)$、与える$O(n)$ビットごとの仕事量。 

関連するビットは 30 個だけなので、全体の複雑さは次のようになります。$O(30n)$。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 |---|------|---|

 | ブルートフォース |$O(n^2)$|$O(n)$| 遅すぎる |

 | 最適 |$O(30n)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 ### 1. プレフィックス XOR を構築する

 作成$$pref_0=0, \qquad pref_i=pref_{i-1}\oplus a_i.$$この場合、すべての部分配列の XOR は次のようになります。$$pref_r\oplus pref_{l-1}.$$### 2. 各ビットを個別に処理する

 あらゆるビットについて$b$から$0$に$29$、XOR がビットを持つ部分配列の重み付き長さの合計を計算します。$b=1$。 

最終的な答えは、この数量を乗算したものを受け取ります。$2^b$。 

### 3. 以前のプレフィックス パリティの統計を維持する

 現在のビットについては、次のように定義します。$$parity_i = (pref_i>>b)\&1.$$維持する：```
cnt[0], cnt[1]
sumPos[0], sumPos[1]
```どこ`cnt[t]`パリティのある以前のプレフィックス位置の数です`t`、 そして`sumPos[t]`はそれらのインデックスの合計です。 

最初はプレフィックス位置のみ$0$存在します:```
cnt[0] = 1
sumPos[0] = 0
```### 4. プレフィックスを左から右に処理します

 位置で$i$、現在のパリティを次のようにします。$p$。 

以前のすべてのポジションが同等である必要があります$p\oplus1$。 

もし```
opp = p ^ 1
```彼らの貢献度の合計は$$cnt[opp]\cdot i - sumPos[opp].$$この量は以下に等しい$$\sum(i-j)$$すべての有効な以前のポジションにわたって$j$。 

このビットの実行中の寄与にそれを追加します。 

### 5. 現在のプレフィックスを挿入します。 

ポジション使用後$i$右のエンドポイントとして、データ構造に追加します。$$cnt[p] += 1$$

$$sumPos[p] += i$$### 6. ビット寄与を追加します。 

ビットの累積加重長が$b$は$cur$、 追加$$cur\cdot 2^b$$答えのモジュロ$998244353$。 

### なぜ効果があるのか

 固定ビットの場合、サブ配列は、その両端の対応するプレフィックス パリティが異なる場合に正確に寄与します。 すべてのサブアレイ$[l,r]$プレフィックスインデックスのペアに一意に対応します$(l-1,r)$。 プレフィックス位置の処理中$r$の場合、アルゴリズムは、以前のすべてのプレフィックス位置を反対のパリティで考慮します。 表現$$cnt\cdot r-\sum j$$正確に長さの合計です$r-j$そのようなすべてのサブ配列の。 すべての有効なサブ配列は、その右端が処理されるときに 1 回カウントされます。無効なサブ配列は、パリティが等しいためカウントされません。 すべてのビットを個別に合計すると、元の XOR 値が再構築されるため、最終的な答えは必要な加重合計と等しくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] ^ a[i]

    ans = 0

    for b in range(30):
        cnt = [1, 0]          # prefix 0 already exists
        sum_pos = [0, 0]

        cur = 0

        for i in range(1, n + 1):
            p = (pref[i] >> b) & 1
            opp = p ^ 1

            cur += cnt[opp] * i - sum_pos[opp]

            cnt[p] += 1
            sum_pos[p] += i

        ans = (ans + (cur % MOD) * ((1 << b) % MOD)) % MOD

    print(ans)

if __name__ == "__main__":
    solve()
```プレフィックス XOR 配列は、すべてのサブ配列 XOR を 2 つのプレフィックスの XOR に変換します。 その後、各ビットを独立して処理できます。 

1 つのビットについて重要な唯一の情報は、そのビットのプレフィックス XOR が次のとおりであるかどうかです。$0$または$1$。 配列`cnt`そして`sum_pos`評価に必要な統計を正確に保存する$$\sum(i-j)$$逆パリティを持つ以前のすべてのプレフィックス。 

操作の順序が重要です。 現在のプレフィックス位置は、データ構造に挿入される前に寄与する必要があります。 そうしないと、プレフィックスがそれ自体と誤ってペアになり、長さ 0 のサブ配列が作成されてしまいます。 

値```
cnt[opp] * i - sum_pos[opp]
```はすでに、新しく発見されたすべての有効な部分配列の合計長と等しく、 で終了します。`i`。 追加の長さの計算は必要ありません。

 ## 特殊なケース

 次のことを考慮してください。```
1
5
```プレフィックス XOR 配列は次のとおりです。```
[0,5]
```5 の設定ビットごとに、位置 1 は位置 0 と反対のパリティを持ち、長さ 1 が生成されます。答えは正確に 5 になります。これにより、最初のプレフィックス XOR を含める必要があることが確認されます。 

考慮する：```
2
1 1
```XOR が 1 に等しいサブ配列は、2 つの単一要素サブ配列のみです。 長いサブ配列の XOR は 0 です。処理中、配列全体に対応するプレフィックスのペアは等しいパリティを持ち、決してカウントされません。 アルゴリズムは正しく 2 を出力します。 

次のことを考慮してください。```
3
0 0 0
```すべてのプレフィックス XOR はゼロです。 すべてのビット パリティは常に 0 です。反対のパリティ プレフィックスは存在しないため、すべての寄与は 0 になります。 答えは 0 のままで、すべての部分配列の XOR が 0 であるという事実と一致します。 

考慮する：```
2
1 0
```サブ配列は次のとおりです。```
[1]   -> 1 * 1 = 1
[1,0] -> 1 * 2 = 2
[0]   -> 0 * 1 = 0
```合計：```
3
```最初のプレフィックス位置 0 がパリティ マッチング プロセスに参加するため、アルゴリズムは両方のサブ配列をインデックス 1 から数えます。 これはまさに、空のプレフィックスを忘れた実装を破壊する状況です。
