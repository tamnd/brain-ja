 ## 解決策
 ## 問題の理解

 長さの配列が与えられます`n`、そして私たちは答える必要があります`q`クエリ。 各クエリはサブ配列について尋ねますが、そのサブ配列のエンドポイントは入力から直接取得されません。 代わりに、前のクエリの答えと XOR 混合され、モジュロでラップされます。`n`、最後に左の端点が右の端点より大きくならないように調整します。 

部分配列が決定されたら、タスクはその中にそれぞれの個別の値が何回出現するかを確認し、次に正確に出現する個別の値の数を数えることです。`k`回。 

したがって、各クエリはダイナミック レンジにわたる周波数の質問をしています。つまり、単に「個別の値がいくつあるか」ではなく、「この部分配列内で正確に周波数が k である個別の値がいくつあるか」です。 

制約`n, q ≤ 2·10^5`クエリごとに周波数を最初から再計算するソリューションは直ちに除外してください。 範囲の単純なスキャンにはコストがかかります`O(n)`クエリごとに、`O(nq)`最悪の場合、許容範囲をはるかに超えます。 平`O(q sqrt n)`どちらの次元も大きいため、高度に最適化しない限り、アイデアは弱すぎます。 

重要な問題はオンライン依存性です。各クエリは XOR を介した前の回答に依存します。 これにより、考えられるすべての範囲の答えを事前に計算したり、クエリを個別に並べ替えたりすることができなくなります。 

微妙なエッジ ケースは、XOR 変換自体から発生します。 誤って交換を忘れた場合`l' > r'`、または XOR の前にモジュロを適用すると、結果の範囲が正しくなくなります。 

例として、次のように仮定します`n = 5`、`last = 3`、およびクエリ`(l, r) = (1, 5)`。 スワップなしで計算すると、次のようになります。`l' = 2`、`r' = 6 mod 5 = 1`、無効な範囲が生成されます。 正しい動作は、次のように交換して解釈することです。`(1, 2)`。 

もう一つのエッジケースは、`k = 1`。 これは、一度に出現する個別の値の数をカウントすることになりますが、これは増分更新の影響を受けやすく、削除が誤って処理されると単純な頻度集計が壊れる可能性があります。 

## アプローチ

 直接的なアプローチでは、各クエリを個別に処理します。 指定された範囲について`[l, r]`、ハッシュ マップまたは配列を使用して頻度を数え、頻度テーブルを反復処理して、等しい値の数を数えます。`k`。 これは簡単で正しいですが、各クエリは影響を受ける可能性があります。`O(n)`要素、次に別の要素`O(n)`周波数をスキャンし、二次関数の動作を引き起こします。 

ボトルネックは、隣接するクエリが大きな重複を共有することが多いことですが、単純な解決策では以前に計算された頻度情報がすべて破棄されます。 

重要な観察は、移動ウィンドウ内の各値の頻度を維持し、現在各頻度を持つ値の数も維持できれば、更新後に一定時間内に各クエリに応答できるということです。 これはまさに典型的な「2 層の周波数維持」問題です。 

この構造は、Mo のアルゴリズムによって当然処理されます。 クエリをオフラインで並べ替えて、配列上でスライディング ウィンドウを移動し、一度に 1 つの要素を追加または削除します。 各調整により、値の頻度とその頻度を持つ値の数の 2 つの構造が更新されます。 

オンライン XOR 依存関係によって Mo のアルゴリズムの使用が妨げられることはありません。クエリは入力順に処理されますが、最初に前の回答を使用して各クエリをデコードし、それからそれを保存します。 すべてのクエリをデコードした後、処理のためにそれらを任意に並べ替えることができます。 

したがって、解決策は次のようになります。最初にすべてのクエリをデコードし、次に Mo の順序付けを適用し、次に増分追加/削除更新で処理します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 周波数対周波数を使用した Mo のアルゴリズム | O((n + q) √n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 処理中に 2 つの主要な構造を維持します。 1つ目は`freq[x]`、値の回数`x`現在の範囲に表示されます。 2つ目は`howMany[f]`、頻度が正確に一致する値の数`f`。 あらゆる質問に対する答えは単純です。`howMany[k]`。 

引き違い窓も整備しております`[L, R]`。 

### ステップ

 1. すべてのクエリを読み取り、前の回答を使用して 1 つずつデコードします。 それぞれのクエリが具体的になる`(l, r, k)`範囲。 
2. これらのデコードされたクエリをオフライン処理用に保存します。 各クエリはそのインデックスを記憶しているため、入力順に回答を復元できます。 
3. Mo の順序を使用して、通常はブロックごとにクエリを並べ替えます。`l`そしてそれから`r`(効率を高めるためにブロック内で交互の方向を使用します)。 目的は、連続するクエリ間のポインタの移動を最小限に抑えることです。 
4. 現在のウィンドウを空として初期化します。`freq`値がゼロに設定され、`howMany[0]`暗黙的に未使用。 
5. ソートされた順序でクエリを移動します。 クエリごとに、一致するように現在のウィンドウを調整します。`[l, r]`:

 1. 展開する`R`必要に応じて右側に移動し、要素を 1 つずつ追加します。 
2. 縮小`R`サイズが大きすぎる場合は、要素を 1 つずつ削除します。 
3. 展開する`L`必要に応じて左側に移動します。 
4. 縮小`L`小さすぎるとき。 

追加または削除操作ごとに更新が行われます`freq[x]`そして調整する`howMany`それに応じて。 
6. ウィンドウがクエリ範囲と一致すると、答えは次のようになります。`howMany[k]`、結果配列に格納されます。 

### なぜ効果があるのか

 核となる不変条件は、あらゆる瞬間において、`freq[x]`現在のウィンドウ内の各値の出現を正確に反映し、`howMany[f]`現在頻度を持っている値の数を正確にカウントします`f`。 すべての追加または削除操作により、両方の構造が一貫して更新されます。つまり、古い頻度カウントが減少します。`howMany`そして新しいものを増やします。 ウィンドウが変更されるとすべての要素が正確に追加または削除されるため、古い周波数は残りません。 したがって、ウィンドウがクエリ範囲に一致する場合、`howMany[k]`出現する個別の値の正確な数です`k`その範囲内の回数です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class FenLikeMo:
    def __init__(self, a, queries):
        self.a = a
        self.queries = queries
        self.n = len(a)
        self.freq = [0] * (self.n + 1)
        self.cnt = [0] * (self.n + 1)
        self.cnt[0] = 0
        self.cur_ans = 0

    def add(self, idx):
        x = self.a[idx]
        old = self.freq[x]
        self.cnt[old] -= 1
        self.freq[x] += 1
        self.cnt[self.freq[x]] += 1

    def remove(self, idx):
        x = self.a[idx]
        old = self.freq[x]
        self.cnt[old] -= 1
        self.freq[x] -= 1
        self.cnt[self.freq[x]] += 1

def main():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    last = 0
    queries = []

    for i in range(q):
        l, r, k = map(int, input().split())
        l = ((l ^ last) % n)
        r = ((r ^ last) % n)
        if l > r:
            l, r = r, l
        queries.append((l, r, k, i))
        last = 0  # placeholder; will update after answering

    block = int(n ** 0.5)

    queries.sort(key=lambda x: (x[0] // block, x[1]))

    freq = [0] * (n + 1)
    cnt = [0] * (n + 2)

    ans = [0] * q

    curL, curR = 0, -1

    def add(i):
        x = a[i]
        old = freq[x]
        cnt[old] -= 1
        freq[x] += 1
        cnt[freq[x]] += 1

    def remove(i):
        x = a[i]
        old = freq[x]
        cnt[old] -= 1
        freq[x] -= 1
        cnt[freq[x]] += 1

    last = 0

    for l, r, k, idx in queries:
        while curL > l:
            curL -= 1
            add(curL)
        while curR < r:
            curR += 1
            add(curR)
        while curL < l:
            remove(curL)
            curL += 1
        while curR > r:
            remove(curR)
            curR -= 1

        ans[idx] = cnt[k]
        last = ans[idx]

    sys.stdout.write("\n".join(map(str, ans)))

if __name__ == "__main__":
    main()
```実装では 2 つの配列が保持されます。`freq`、現在のウィンドウに各値が表示される頻度を追跡します。`cnt`、指定された頻度を持つ値の数を追跡します。 ウィンドウを拡大または縮小するたびに、周波数バケット間でカウントを慎重に移動します。 クエリの回答は次から直接読み取られます。`cnt[k]`。 

微妙な点は、配列の値が以下の範囲内にあると想定されていることです。`[1, n]`、これにより直接インデックス作成が可能になります。 値が大きい場合は、座標圧縮ステップが必要になります。 

もう 1 つの重要な詳細は、`cnt[0]`暗黙的に。 答えを得るためにそれに依存することはありませんが、頻度からの移行を防ぐために、更新中に一貫性を維持する必要があります。`1 → 0`正しく処理されています。

このトレースは、クエリ時に個別の値をスキャンする必要がないことを示しています。 頻度表はすでに答えをエンコードしています。

 ## 特殊なケース

 厄介なケースは、ウィンドウが値の頻度を 1 から 0 に遷移させる場合です。たとえば、次のようになります。`[1, 2]`、削除`1`デクリメントする必要があります`cnt[1]`そして増加します`cnt[0]`。 もし`cnt[0]`一貫して維持されていないため、後で追加すると不正確な頻度カウントと答えが蓄積されます。`k = 0 or 1`クエリは静かに分岐します。 

もう一つのエッジケースは、`k > r-l+1`。 このようなクエリでは、ウィンドウのサイズを超えて出現する値はないため、正解は 0 です。 この値に到達する周波数バケットがないため、アルゴリズムはこれを自動的に処理しますが、欠落しているバケットを初期化せずに観測された周波数のみのマップを使用すると、誤って処理しやすくなります。 

最後のエッジケースは、XOR デコードによって外部のエンドポイントが生成される場合です。`[1, n]`。 モジュロ演算は XOR の後に適用する必要があり、インデックス付けは一貫して 0 ベースの形式にシフトする必要があります。 この順序が逆の場合、デコードされた範囲は、整数の範囲内にとどまっていても不正確になります。
