 ## 解決策
 ## 問題の理解

 N 個の文字列のシーケンスが与えられ、各文字列は小文字で書かれた「スクロール」を表します。 各スクロールから、回文であるすべての部分文字列に注目し、文字シーケンスが同一であれば、出現する場所に関係なく、2 つの部分文字列を同じものとして扱います。 

各クエリはスクロール インデックス [L, R] の範囲を指定し、その範囲内の少なくとも 1 つのスクロールに部分文字列として表示される個別の回文文字列の数を求めます。 

したがって、概念的には、すべての巻物は回文文字列のセットに寄与します。 クエリでは、インデックスの間隔にわたるこれらのセットの和集合のサイズが求められます。 

難しいのは、N とクエリ数 M が両方とも大きく、すべての文字列の長さの合計が 5 · 10^5 までになることです。 これは、各文字列を効率的に前処理し、ダイナミック レンジにわたる高速なユニオン クエリをサポートする必要があることを強く示唆しています。 

素朴な解釈では、[L, R] 内のすべての文字列をスキャンし、すべての回文部分文字列を収集することによって、クエリごとに回文を再計算しようとします。 各文字列が線形回文構造であると仮定した場合でも、これをクエリごとに再計算すると、およそ O(M · total_length) となり、非常に遅すぎます。 

2 番目の単純なアイデアは、各文字列のすべての回文部分文字列を事前計算してセットに格納することですが、クエリごとにセットをマージするのは依然としてコストが高すぎます。これは、最悪の場合の結合では大きな重複が繰り返し再処理されるためです。 

本当の問題は、一定の間隔で繰り返しセットの結合を行っていることであり、そのたびに結合を最初から再構築することを避ける方法が必要です。 

文字列が同一であるか、または繰り返しが多い場合、微妙なエッジケースが発生します。 たとえば、すべての文字列が「aaaaa」の場合、すべての部分文字列「a」、「aa」、「aaa」などが多くのスクロールにわたって繰り返されますが、それでもカウントされるのはクエリごとに 1 回だけです。 個別の値ではなく出現回数をカウントするソリューションでは、オーバーカウントが行われます。 

もう 1 つの特殊なケースは、回文が長く、単一の文字列内で重なり合う場合です。 たとえば、「ababa」は「aba」、「bab」、「ababa」のような複数の回文を生成します。 すべてのポジションで重複を確実に排除する必要があります。 

## アプローチ

 ブルートフォース手法では、通常、回文ツリーまたは中心展開を使用して、文字列ごとにすべての回文部分文字列のセットを計算します。 合計の長さがわずか 5 · 10^5 であるため、この部分は管理可能であり、すべての文字列にわたる全体的な抽出は線形または線形に近い時間で実行できます。 

本当の障害は、範囲結合クエリに応答することです。 各文字列の回文セットを保存すると、クエリは R−L+1 セットの和集合になります。 各セットが平均して小さい場合でも、「aaaaa...」のような最悪の場合の文字列では、文字列ごとに O(n) 個の回文が生成され、クエリ全体で O(n^2) 個の動作が発生します。 

重要な観察は、ある範囲にわたるすべての異なる回文部分文字列のセットは、どの文字列が含まれるかのみに依存し、それぞれの異なる回文を特定の位置 (文字列) に現れる「項目」として扱うことができるということです。 次に、各クエリは、[L, R] の少なくとも 1 つのインデックスに出現する個別の項目がいくつあるかを尋ねます。 

これは、古典的なオフライン範囲結合カウントの問題になります。 各回文の出現を、最初に出現する文字列インデックスのセットに割り当てると、各回文を 1 つの右端の出現間隔に減らすことができます。 より具体的には、個別の回文文字列ごとに、それが出現する文字列のインデックスをすべて検索し、左から右にスイープするときに最初に出現する文字列のみを考慮します。 

次に、現在「アクティブ」、つまり現在のインデックスまでに少なくとも 1 回出現している回文のグローバルな頻度を維持しながら、文字列を順番に処理します。 各クエリは、プレフィックス状態の違いによって答えることができ、これは回文のインデックスに対する BIT またはセグメント ツリーを示唆します。

より明確な再定式化は、各回文に文字列配列内の最初の出現位置を割り当てることです。 次に、各回文は、L がその位置以上、R がその位置以上であるすべてのクエリに正確に寄与し、これがイベントの 2D 範囲カウント問題になります。 

これにより、右エンドポイントのスイープと左エンドポイントの範囲合計クエリをサポートするデータ構造を使用したオフライン処理で問題が軽減されます。

 | 最適 | O(合計長 log N + M log N) | O(総回文 + N) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべての文字列を個別の回文部分文字列のセットに変換し、その後、全体的な問題を文字列のシーケンス全体で各回文が最初に出現するときの追跡に落とし込みます。 

1. 各文字列について、回文ツリーを使用してすべての個別の回文部分文字列を効率的に計算します。 ツリー内の各ノードは一意の回文に対応し、その文字列形式またはハッシュ表現を抽出します。 このステップが必要なのは、内部の重複を二重にカウントせずにすべての個別の回文を列挙する必要があるためです。 
2. ハッシュ マップを使用して、すべての回文をグローバル識別子にマッピングします。 文字列を左から右に処理する際、各回文について、以前の文字列ですでにその回文が見られたかどうかを維持します。 
3. 各回文について、それが出現する文字列の最初のインデックスを記録します。 これにより、各回文が [1, N] の位置 i に位置する単一のイベントに変わります。 これが機能する理由は、回文が文字列に出現すると、その最初の出現を含むクエリ間隔ごとに回文がカウントされる必要があるためです。 
4. ここで問題を次のように解釈します。位置 i にイベントがあり、各イベントは別個の回文を表します。 クエリ [L, R] は、インデックス範囲 [L, R] に含まれるイベントの数を尋ねます。 ただし、文字列ごとに複数の回文が存在する可能性があり、それぞれを個別にカウントする必要があるため、これではまだ十分ではありません。 
5. 位置 1 から N までフェンウィック ツリーを構築します。文字列を左から右にスイープします。 文字列 i を処理するとき、新しく見つかった回文ごとに位置 i のフェンウィック ツリーを +1 更新することにより、最初に出現する回文が i にあるすべての回文がアクティブになります。 
6. 各クエリ [L, R] は、フェンウィック接頭辞の合計 (sum(R) − sum(L − 1)) を使用して範囲 [L, R] 内のアクティブ化された回文の数を計算することによって答えることができます。 

重要なアイデアは、回文の出現をその最初の出現インデックスに関連付けられた独立した寄与に変換し、その後クエリを静的な範囲合計問題に還元するということです。 

### なぜ効果があるのか

 それぞれの個別の回文は、文字列のシーケンス内で最初に出現した時点で 1 回だけカウントされます。 それ以降は、以降のすべてのクエリに対してアクティブなままになります。 したがって、フェンウィック ツリーは常に、最初の出現インデックスが処理されたプレフィックス内にある回文のセットを正確に表します。 クエリ [L, R] は、その間隔内に最初に出現する回文を正確にカウントし、[L, R] 内の少なくとも 1 つの文字列に出現するという要件に一致します。

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    res = set()
    n = len(s)
    for c in range(n):
        l = r = c
        while l >= 0 and r < n and s[l] == s[r]:

            l -= 1
            r += 1

def solve():
    N, M = map(int, input().split())
    s = [input().strip() for _ in range(N)]

    first_pos = {}
    for i in range(N):
        pals = palindromes_set(s[i])
        for p in pals:
            if p not in first_pos:
                first_pos[p] = i + 1

    events = [[] for _ in range(N + 1)]
    for p, idx in first_pos.items():
        events[idx].append(p)

    bit = Fenwick(N)
    active = 0

    queries = [tuple(map(int, input().split())) + (i,) for i in range(M)]
    queries.sort(key=lambda x: x[1])

    ans = [0] * M
    qptr = 0

        for _ in events[i]:

            active += 1

辞書`first_pos`それぞれの回文に正確に 1 つの位置が割り当てられるようにし、異なる文字列で複数出現する場合の過剰カウントを防ぎます。 

フェンウィック ツリーは、指定されたインデックスまたはその前に最初に出現した個別の回文がいくつあるかを維持します。 クエリは、正しいエンドポイントで並べ替えることによってオフラインで回答されるため、位置 R に到達した時点で、関連するすべての回文がすでにアクティブになっています。 

微妙な点は、同じ回文の複数の出現を決して数えようとしていないことです。 ハッシュ マップは冪等性を保証します。つまり、回文が記録されると、以降の文字列では無視されます。 

## 実用的な例

 ### 例 1

 文字列を考えてみましょう。 

「あば」、「ああ」、「あば」

 クエリ:

 [1,2]、[2,3]、[1,3]

 | ステップ | 文字列 | 新しい回文 | アクティブな数 |
 | --- | --- | --- | --- |
 | 1 | アバ | a、b、aba | 3 |
 | 2 | ああ | ああ | 4 |
 | 3 | アバ | なし | 4 |

 クエリ [1,2] は、3 で最初に出現したものを除く {a,b,aba,aa} をカウントするため、結果は 4 になります。 

クエリ [2,3] も {aa, a, b, aba} を 4 とカウントします。 

クエリ [1,3] は 4 です。 

これは、文字列間の重複によってカウントが増大しないことを示しています。

 | 2 | b | b | 2 |
 | 3 | | なし | 2 |

 クエリ [2,3] には b と a のみが含まれるため、結果は 2 になります。 

これは、繰り返される単一文字の回文を正しく処理する方法を示しています。

 ## 特殊なケース

 「aaaa」のような同一の文字列のシーケンスの場合、すべての部分文字列は回文であり、すべてのインデックスにわたって繰り返されます。 このアルゴリズムは、各回文文字列の最初の出現のみを記録することによって正確性を保証するため、後の文字列が同一の回文を生成しても、カウントは増加しません。 

交互の単一文字列の場合、すべての回文は簡単であり、複数の位置に現れます。 フェンウィック ツリー モデルでは、アクティベーションは回文ごとに 1 回だけ行われるため、各文字がグローバルに 1 回だけカウントされることが保証されます。 

「abc」などの繰り返し文字を含まない文字列の場合、各回文は 1 文字になります。 各文字は独立しており、独自の位置にのみ表示され、クエリは文字列間の干渉なしに共用体のサイズを正確にカウントします。
