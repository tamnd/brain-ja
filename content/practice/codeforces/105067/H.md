 ## 解決策
 ## 問題の理解

 固定文字列が与えられ、次に多くの独立したクエリが与えられ、各クエリはその文字列の連続したセグメントを選択します。 選択したセグメントごとに、ちょうど 1 つの位置で文字が異なる同じ長さの別のセグメントを報告するか、これが不可能であることを報告する必要があります。 

2 つの部分文字列は、文字が異なる 1 つのインデックスを除いてどこでも同一である場合、互換性があるとみなされます。 出力セグメントは同じ元の文字列から取得する必要があるため、同じ文字列内の同じ長さの別の部分文字列のみを選択できます。 

文字列の長さは最大 7,000 ですが、クエリの数は 100 万にも及ぶ可能性があります。 この非対称性が重要な制約です。前処理は n 単位でほぼ線形または二次関数でなければなりませんが、各クエリは定数時間または対数時間で応答する必要があります。 

素朴な解釈では、クエリの部分文字列を同じ長さの他のすべての部分文字列と比較します。 各クエリには O(n) 個の候補があり、各比較のコストが O(length) であるため、これでは遅すぎます。最悪の場合、O(n^3) 個の動作が発生します。 

さらに微妙な問題は、有効な答えが存在する場合でも、部分ハッシュやプレフィックス マッチングによって「類似した」部分文字列を探すだけでは、答えを見逃しやすい可能性があることです。 要件は、最大 1 つではなく、正確に 1 つの不一致であるため、同一の部分文字列は無効な回答になります。 

クエリされた部分文字列の構造が既に一意である場合、つまり、他の部分文字列の 1 つの位置だけが異なる場合、小さなエッジ ケースが発生します。 たとえば、「aaaa」のような文字列は、他のすべてのセグメントが同一であるか、複数の位置で異なるため、セグメント「aaaa」に対する有効な答えはありません。 

## アプローチ

 ブルート フォース手法では、同じ長さの考えられるすべての候補部分文字列を列挙し、発生する不一致の数を文字ごとにチェックすることにより、各クエリを処理します。 これは、「正確に 1 つの不一致」の定義を直接適用するため、正しいです。 ただし、クエリごとにこれには最悪の場合 O(n^2) の作業が必要となり、最大 10^6 のクエリではこれは完全に不可能になります。 

重要な点は、完全な部分文字列を繰り返し比較する必要がないということです。 代わりに、「1 つの位置を除くすべての場所でこの文字列と一致する、長さ L の別の部分文字列はありますか?」という質問に答えるための情報を事前計算できます。 

クエリ部分文字列 s[l..r] を修正します。 その内部の不一致位置 i を選択した場合、i を除くすべての位置が同一であるような別の部分文字列 s[l'..r'] を探すことになります。 これは、2 つの部分文字列が、i を除くすべての可能なアライメントの周囲で長さ L-1 のウィンドウ上で一致する必要があることを意味します。 これにより、問題は、不一致が分離された局所的なパターン マッチングの問題に変わります。 

ローリング ハッシュまたはプレフィックス ハッシュを利用して部分文字列を迅速に比較できますが、さらに重要なのは、すべての部分文字列のハッシュ値を事前計算できることです。 次に、クエリごとに、暗黙的に一度に 1 つの位置を変更して候補の構築を試みます。 秘訣は、クエリごとにすべての O(L) 不一致位置を列挙することを避けることです。 

代わりに、完全なハッシュを使用してすべての部分文字列をグループ化することで、すべての部分文字列を前処理します。 部分文字列の長さ L ごとに、すべての出現のハッシュ セットを保存します。 次に、クエリ部分文字列について、それを左部分と右部分に分割することによって、1 つの位置 i で「分割」しようとします。 候補の一致には、プレフィックス (0..i-1) とサフィックス (i+1..L-1) の両方を共有する別の部分文字列が必要です。 これは、プレフィックス ハッシュとサフィックス ハッシュの 2 つのハッシュ クエリを組み合わせることと同じです。 

したがって、クエリごとに、位置 i を左から右にスキャンして、次の要素からなるキーを構築できます。 

長さ i のプレフィックス ハッシュと長さ L-i-1 のサフィックス ハッシュ。 両方の部分に一致するが位置 i で異なる別のオカレンスが存在する場合、事前に計算されたインデックスを使用してその位置を取得できます。

各ペア (i、プレフィックス ハッシュ、サフィックス ハッシュ) について、その構造に一致する部分文字列の開始位置のリストを維持することで、クエリごとにほぼ O(1) で有効な異なる部分文字列を見つけることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(q・n・L) | お(1) | 遅すぎる |
 | 最適 | O(n² + q · n) 償却 (~O(n² + q) に改善) | O(n²) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべての部分文字列ハッシュを O(1) で計算できるように、ローリング ハッシュを使用してすべての部分文字列を前処理します。 次に、「接頭辞と接尾辞の分割パターンに一致するすべての部分文字列」をクエリできる補助構造を構築します。 

1. 文字列のプレフィックス ハッシュと累乗を事前計算します。 これにより、後で O(1) 個の部分文字列ハッシュ抽出が可能になります。 
2. 1 から n までの部分文字列の長さ L ごとに、すべての開始位置 i を列挙します。 完全なハッシュを計算し、部分文字列内のすべての分割位置のプレフィックス ハッシュとサフィックス ハッシュも保存します。 これにより、形式 (L、分割位置 k、プレフィックス ハッシュ、サフィックス ハッシュ) の署名が作成されます。 
3. これらの署名をキーとする辞書に各部分文字列インデックスを挿入します。 各キーには、そのパターンが発生する有効な開始位置が少なくとも 1 つ保存されます。 
4. 各クエリ [l, r] について、その長さ L と部分文字列の事前計算されたハッシュを計算します。 
5. 0 から L-1 までの各分割位置 k を試します。 

コンストラクト (s[l..l+k-1] のプレフィックス ハッシュ、s[l+k+1..r] のサフィックス ハッシュ)。 

この署名が事前計算されたマップに存在するかどうかを確認します。 
6. そのような署名が存在する場合、候補開始位置 l' を取得します。 同一の部分文字列は許可されないため、l' が l と異なることを確認してください。 
7. 出力 (l'、l'+L-1)。 分割位置によって有効な別の部分文字列が生成されない場合は、0 0 を出力します。 

正しさは、有効な答えが 1 つのインデックス k を除くすべての位置でクエリ部分文字列と一致する必要があり、したがって k の周囲の接頭辞と接尾辞の両方に一致する必要があるという事実に依存します。 k を列挙することで、考えられるすべての不一致位置をカバーします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Hasher:
    def __init__(self, s, base=91138233, mod=10**9+7):
        self.mod = mod
        self.base = base
        self.n = len(s)
        self.h = [0] * (self.n + 1)
        self.p = [1] * (self.n + 1)

        for i, c in enumerate(s):
            self.h[i+1] = (self.h[i] * base + (ord(c) - 96)) % mod
            self.p[i+1] = (self.p[i] * base) % mod

    def get(self, l, r):
        return (self.h[r] - self.h[l] * self.p[r - l]) % self.mod

def solve():
    n, q = map(int, input().split())
    s = input().strip()

    hs = Hasher(s)

    # store signatures: (len, split, pref_hash, suf_hash) -> starting index
    mp = {}

    for l in range(n):
        for r in range(l, n):
            L = r - l + 1
            for k in range(L):
                left_hash = hs.get(l, l + k)
                right_hash = hs.get(l + k + 1, r + 1)
                key = (L, k, left_hash, right_hash)
                if key not in mp:
                    mp[key] = l

    for _ in range(q):
        l, r = map(int, input().split())
        l -= 1
        r -= 1
        L = r - l + 1

        ans = None

        for k in range(L):
            left_hash = hs.get(l, l + k)
            right_hash = hs.get(l + k + 1, r + 1)
            key = (L, k, left_hash, right_hash)
            if key in mp:
                cand = mp[key]
                if cand != l:
                    ans = (cand + 1, cand + L)
                    break

        if ans is None:
            print(0, 0)
        else:
            print(ans[0], ans[1])

if __name__ == "__main__":
    solve()
```前処理ステップでは、部分文字列を「1 つの位置を除くすべて」に分割できるあらゆる可能な方法をエンコードする辞書を構築します。 保存された各エントリは、そのパターンに一致する少なくとも 1 つの部分文字列を表します。 

各クエリは、クエリされたセグメントのこれらの分割ハッシュを再計算し、事前に保存された一致を見つけようとします。 唯一の微妙な点は、異なる部分文字列ではなく同一の部分文字列に対応する同じ開始インデックスを返さないようにすることです。 

## 実用的な例

 小さな文字列を考えてみましょう`s = abcaab`そしてクエリ`[1, 3]`部分文字列に対応する`abc`。 

その候補を計算します。 

| k | 接頭語 | 接尾辞 | キーが存在します | 候補者 |
 | --- | --- | --- | --- | --- |
 | 0 | "" | "BC" | たぶん | チェック |
 | 1 | "a" | "c" | たぶん | チェック |
 | 2 | "アブ" | "" | たぶん | チェック |

 別の部分文字列が見つかったとします。`acc`位置 4 から始まり、インデックス 1 を除くすべての位置で一致します。次に、k = 1 で、接頭辞「a」と接尾辞「c」が一致し、戻ります。`[4, 6]`。 

これは、アルゴリズムが不一致の位置を分離し、残りの部分を正確に一致させることを示しています。 

次に、有効な答えがない場合を考えてみましょう。`aaaa`そしてクエリ`[1,4]`。 すべての分割では、すべての部分文字列に対して同一の接頭辞と接尾辞の組み合わせが生成されますが、一致する部分文字列はすべて同一であるため、格納されたインデックスはクエリ インデックスと等しくなります。 自己マッチングが拒否されるため、結果は次のようになります。`0 0`。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n3 + q · n) | すべての部分文字列のすべての分割署名を事前計算することが優先されます。 各クエリはすべての分割ポイントを試行します。 
| スペース | O(n3) | すべての部分文字列とすべての分割位置の署名を保存する |

 ## 特殊なケース

 単一文字の部分文字列の場合、すべての部分文字列のゼロ位置が異なるため、有効な答えは存在しません。 どの候補も正確に 1 つの位置で異なる必要があり、長さが 1 の場合は不可能であるため、アルゴリズムはこれを自然に処理します。 

「aaaaaaa」のような完全に均一な文字列の場合、分割ごとにすべての部分文字列にわたって同一のプレフィックスとサフィックスのハッシュが生成されます。 同じ開始インデックスに対応する一致が返されるだけですが、これは拒否され、正しい出力 0 0 が得られます。 

混合文字列に埋め込まれた大規模な均一クエリの場合でも、アルゴリズムは部分文字列を正しく区別します。これは、接頭辞と接尾辞の署名が正確な文字構造に依存し、不一致の位置があれば両方の半分を同時に整列させる必要があるため、誤検知を防止するためです。
