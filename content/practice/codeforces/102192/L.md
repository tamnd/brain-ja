 ## 解決策
 ## 問題の理解

 私たちは (k) か月間稼働する工場を持っています。 月 (i) では、1 台あたりの原材料費 (c_i)、1 台のコンピューターの生産には別のコンピューター (m_i) のコストがかかり、生産は (p_i) に制限され、正確に (d_i) 台のコンピューターを納品する必要があります。 原材料は容量制限なく保管できますが、完成したコンピュータは月 (i) から月 (i+1) までの境界を越えて (e_i) までの量しか持ち運ぶことができません。 

2 つの独立したストレージ コストがあります。 1 単位の原材料を 1 か月にわたって維持するにはコスト (R_i)、完成した 1 台のコンピューターを同じ境界にわたって維持するにはコスト (E_i) がかかります。 同じ月に製造および販売されたコンピューターには、どちらのストレージ コストもかかりません。 最初は両方のインベントリが空です。 

目標は、原材料をいつ購入するか、いつコンピュータを製造するか、および各月の需要に応じてどの製造コンピュータを使用するかを選択して、すべての需要が最小限の総コストで満たされるようにすることです。 生産能力や完成品の保管が不十分なために一部の需要を満たすことができない場合、答えは (-1) になります。 

入力には 1 つのテスト ケースに最大 (50,000) 月が含まれており、すべてのテスト ケースの (k) の合計は最大で (300,000) です。 (50,000^2/2) は約 (1.25\times10^9) であるため、月のペアごとに考慮する方法はすでに大きすぎます。 さらに深刻なことに、(p_i) と (d_i) は両方とも (10^4) である可能性があるため、ユニットごとの実装では 1 つのテスト ケースで (50,000\times10^4=5\times10^8) ものコンピューターを処理できる可能性があります。 解決策は、コンピューターの総数ではなく、月数に依存する必要があります。 

最初の微妙な点は、月 (i) の生産に最も安価な原材料を必ずしも月 (i) に購入する必要はないということです。 例えば、```
1
2
1 0 0 0
100 1 0 1
1 1 0
```答えは(2)です。 2 か月目に使用した原材料は 1 か月目に 1 元で購入し、さらに 1 元で保管できます。 材料価格として常に (c_i) を使用するソリューションでは、(100) が支払われます。 

2 番目の微妙な点は、完成品のストレージ容量は、当月に一時的に製造されたコンピューターの数ではなく、月の間に適用されることです。 例えば、```
1
2
0 0 0 2
0 2 0 0
1 0 0
```答えは (-1) です。 最初の月は 2 台のコンピューターを作成できますが、2 番目の月に移行できるのは 1 台だけです。 2ヶ月目は何も作れないので、2個という要求は不可能です。 境界容量を適用せずに、未使用のすべてのプロダクションをデータ構造内に保持する不注意な実装では、実行可能な計画が誤って検出されてしまいます。 

3 番目の微妙な点は、境界を越えるたびにストレージ コストが課金される必要があることです。 例えば、```
1
2
1 0 0 1
100 1 0 1
1 1 2
```答えは(3)です。 1 か月目に製造されたコンピューターには (1) のコストがかかり、保管中に別の (2) のコストがかかるため、2 か月目に販売されるときには (3) のコストがかかります。コンピューターが実際に境界を越えたときではなく、コンピューターが挿入されたときにストレージ料金が請求されると、オフバイワン エラーが発生しやすくなります。 

## アプローチ

 直接的なアプローチは、個々のコンピューターについて推論することです。 毎月、最大 (p_i) 個の候補コンピューターを作成し、その現在のコストを保存し、現在の需要に応じて最も安価な (d_i) コンピューターを採用し、倉庫の容量を超えるたびに最も高価なコンピューターを削除することができます。 これは概念的には正しいです。なぜなら、すべてのコンピューターは、実稼働容量とストレージ容量を除いて独立しているからです。 

問題は候補者の数だ。 1 つのテスト ケースには (p_i=10,000) の (50,000) 月を含めることができ、(5\times10^8) 個の候補コンピューターが得られます。 たとえヒープがすべての挿入を対数時間で処理したとしても、これには数億回のヒープ操作が必要になります。 需要のすべての単位を個別にシミュレートしようとすると、同じ問題が発生します。 

最初の観察では、原材料の在庫が完全に削除されます。 (q_i) を、月 (i) にすぐに使用できる原材料 1 単位を入手するための可能な最も安いコストとします。 月 (i) に (c_i) で購入するか、月 (i-1) に入手可能になり、それを保管するために (R_{i-1}) を支払います。 したがって、

 [
 q_1=c_1
 】

 (i>1) の場合、

 [
 q_i=\min(c_i,q_{i-1}+R_{i-1})。 
】

 原材料の容量は無制限であるため、異なるユニット間の相互作用はありません。 月 (i) に製造されたすべてのコンピューターは原価 (q_i) で原材料を使用していると独自に仮定できます。 その場合の製造コストは、

 [
 w_i=q_i+m_i。 
】

 残る問題は、完成したコンピュータに関するものだけです。 月 (i) に製造されたコンピューターには、現在のコスト (w_i) があります。 さらに 1 か月間倉庫に保管されると、コストは (E_i) だけ増加します。 したがって、現在ストレージ内にあるすべてのコンピュータは、時間が 1 か月進むと、まったく同じ追加コストがかかります。 

この一般的な追加コストが、貪欲なソリューションの鍵となります。 月の初めに、今月製造できるコンピューターを、現在の総コストの順に並べたコレクションに入れます。 次に、入手可能な最も安価なコンピューターを使用して現在の需要を満たします。 需要を満たした後は、(e_i) 個のコンピューターだけが翌月まで生き残ることができるため、最も安価な (e_i) コンピューターを保持し、最も高価なコンピューターを破棄します。 

概念的には、すべての (p_i) 個の可能なコンピューターを挿入できるという事実には、ある程度の注意が必要です。 これらは候補であり、必ずしも物理的に製造されたコンピューターである必要はありません。 高価すぎて維持できないという理由で候補が破棄された場合、私たちはそれをそのコンピューターを決して製造しないものと単純に解釈します。 最終的に販売される候補のみが、製造コストと材料コストを答えに反映します。 

現在の需要に応じて最も安価なコンピューターを使用する必要があるのはなぜでしょうか? 利用可能な 2 台のコンピュータの現在のコスト (a<b) があるが、主張される最適化により、現在のコスト (b) のコンピュータが売却され、コンピュータのコスト (a) が維持されるとします。 安価なコンピュータを今後使用しない場合は、すぐに交換すると解決策が改善されます。 後で安価なコンピュータを使用する場合は、役割を交換します。つまり、安価なコンピュータを今すぐ売却し、より高価なコンピュータを将来の同じ期間保持します。 どちらのコンピュータも将来同じストレージ コストを受け取ることになるため、(a) と (b) の差は、安価な方を維持しても決して回収されません。 安価なコンピューターを今販売することは、少なくとも同じくらい良いことです。 

同じ支配引数が倉庫の境界を処理します。 需要を満たした後に 2 台のコンピューターが残り、1 台のコストがもう 1 台よりも低い場合、高価な方を維持し、安い方を廃棄しても、その後の月ごとに同じストレージ コストが両方に追加されるため、何の解決にもなりません。 高価なコンピューターが主流です。

これはまさにコンテストの資料に記載されている貪欲なシミュレーションです。つまり、最も安い有効原材料価格を計算し、完成したコンピューターを現在のコストで維持し、最も安いコンピューターを販売し、倉庫の境界に達したら最も高価なコンピューターを廃棄します。 

実装に関する残りの課題は、多くのコンピュータが同じコストになる可能性があることです。 したがって、コンピューターごとに 1 つのヒープ要素を挿入するのではなく、各生産月をコストと数量を含む 1 つのバッチとして保存します。 最小ヒープは販売用に最も安価なバッチを提供し、最大ヒープは容量トリミング用に最も高価なバッチを提供します。 各バッチには、その量に関係なく、各ヒープに最大 1 つのヒープ エントリが含まれます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O((\sum p_i)\log(\sum p_i))) | (O(\sum p_i)) | 遅すぎる |
 | 最適 | (O(k\log k)) | (O(k)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. (k) 月次の生産および需要データを読み取り、続いて (k-1) 倉庫の推移を読み取ります。 入力ではすべての月次データが最初に配置されるため、月をシミュレーションする前に遷移データが必要です。 
2. メンテナンス`raw_cost`、当月に 1 単位の原材料を入手できる最も安い価格。 最初の月は (c_1) です。 その後計算します
 [
 \text{raw_cost}=\min(c_i,\text{raw_cost}+R_{i-1})。 
】
 これが機能するのは、原材料の保管場所に容量制限がないため、2 つの原材料ユニットがスペースをめぐって競合する理由がまったくないためです。 
3. グローバルな環境を維持する`offset`前月の境界を越えたすべてのコンピュータによって累積された、完成したコンピュータのストレージ コストを表します。 コンピュータの実際のコストは、保存されているヒープ キーに加えて`offset`。 (i) 月から (i+1) 月に移動する場合、増加します`offset`by (E_i) すべてのコンピュータに同じ値を追加しても、その順序は変わりません。 
4. 月 (i) に、最大 (p_i) 台の候補コンピュータを含む 1 つのバッチを作成します。 実際の生産コストは、
 [
 \text{生のコスト}+m_i。 
】
 正規化されたキーを保存する
 [
 \text{キー}=\text{raw_cost}+m_i-\text{オフセット}。 
]
それから`key + offset`は常にコンピュータの現在の実際のコストです。 
5. 使用可能な候補コンピュータの数が (d_i) 以上であるかどうかを確認します。 そうでない場合は、現在の需要を満たすことができない可能性があるため、(-1) を返します。 
6. 正確に (d_i) 台のコンピュータを最小コスト ヒープから削除します。 バッチごとに、必要な数のコンピュータを削除し、その数量に次の値を掛けます。`key + offset`、結果を答えに追加します。 バッチの一部のみが販売された場合は、減った数量をヒープに戻します。 
7. 最終月ではない場合は、残りの在庫を (e_i) と比較します。 (e_i) 個を超えるコンピューターが残っている場合は、ちょうど (e_i) 個が残るまで、最大コスト ヒープからコンピューターを削除します。 これらの廃棄された候補は、決して製造されなかったコンピューターとして解釈されます。 
8.増加`offset`翌月の処理前に (E_i) によって。 この境界を越えるすべてのコンピューターは、まさにこのストレージ コストを支払います。 

### なぜ効果があるのか

 不変条件は、月 (i) の処理後、ヒープは、現在のウェアハウスの境界を越えて最大でも許可された数だけ残っており、将来の月でもまだ使用できる完成品コンピューター候補の最も安価なセットを正確に表しているということです。 現在の需要の場合、選択した高価なコンピューターをより安価な入手可能なコンピューターに置き換えることで、将来のストレージが両方に同額追加されるため、将来の計画が悪化することはありません。 倉庫の境界では、より高価なコンピューターの代わりにより安価なコンピューターを保持することも、常に少なくとも同じくらい良いことです。 無制限の原材料保管により、すべてのユニットが生産月までの最も安価な経路を選択するため、原材料の繰り返しは独立して最適化されます。 これら 3 つの優位性特性を合わせると、あらゆる貪欲な選択を、コストを増加させることなく最適なソリューションに変換できることを意味します。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        k = int(input())

        c = [0] * k
        d = [0] * k
        m = [0] * k
        p = [0] * k

        for i in range(k):
            c[i], d[i], m[i], p[i] = map(int, input().split())

        e = [0] * (k - 1)
        R = [0] * (k - 1)
        E = [0] * (k - 1)

        for i in range(k - 1):
            e[i], R[i], E[i] = map(int, input().split())

        min_heap = []
        max_heap = []

        # remaining[id] is the number of computers left in batch id.
        remaining = []

        raw_cost = 0
        offset = 0
        total_inventory = 0
        answer = 0
        possible = True

        for i in range(k):
            # Computers carried from the previous month have just paid
            # the storage cost on the boundary before month i.
            if i > 0:
                offset += E[i - 1]

                raw_cost = min(c[i], raw_cost + R[i - 1])
            else:
                raw_cost = c[i]

            # This is a candidate batch, not necessarily an actually
            # manufactured batch. Discarding it later means we never
            # needed to manufacture those computers.
            if p[i] > 0:
                batch_id = len(remaining)
                remaining.append(p[i])

                key = raw_cost + m[i] - offset

                heapq.heappush(min_heap, (key, batch_id))
                heapq.heappush(max_heap, (-key, batch_id))

                total_inventory += p[i]

            if total_inventory < d[i]:
                possible = False
                break

            need = d[i]

            # Sell the cheapest available computers.
            while need > 0:
                while min_heap and remaining[min_heap[0][1]] == 0:
                    heapq.heappop(min_heap)

                key, batch_id = heapq.heappop(min_heap)

                take = min(need, remaining[batch_id])
                answer += take * (key + offset)

                remaining[batch_id] -= take
                total_inventory -= take
                need -= take

                if remaining[batch_id] > 0:
                    heapq.heappush(min_heap, (key, batch_id))

            # Only computers crossing to the next month occupy the
            # finished-goods warehouse.
            if i < k - 1 and total_inventory > e[i]:
                remove = total_inventory - e[i]

                # Discard the most expensive computers.
                while remove > 0:
                    while max_heap and remaining[max_heap[0][1]] == 0:
                        heapq.heappop(max_heap)

                    neg_key, batch_id = heapq.heappop(max_heap)
                    key = -neg_key

                    take = min(remove, remaining[batch_id])
                    remaining[batch_id] -= take
                    total_inventory -= take
                    remove -= take

                    if remaining[batch_id] > 0:
                        heapq.heappush(max_heap, (neg_key, batch_id))

        out.append(str(answer) if possible else "-1")

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```ウェアハウスの遷移は入力内のすべての月次レコードの後に​​表示されるため、月次配列が最初に読み取られます。 その後、シミュレーションは月を左から右に処理できます。`raw_cost`現在の運用バッチを作成する前に更新されます。 表現`raw_cost + R[i - 1]`原材料をより早く購入し、以前の境界を越えて運ぶことを表します。 直接的な代替手段は、`c[i]`、したがって、それらを最小限に抑えると、可能な限り安価な材料コストが得られます。 

の`offset`規則により、ストレージ料金が追加された場合にすべてのヒープ要素を変更することが回避されます。 正規化されたキーを使用してバッチが挿入されたとします。`key`。 当月の実際のコストは常に`key + offset`。 増加中`offset`すべての実際のコストが同じ量だけ変更されるため、両方のヒープ順序が有効なままになります。 

生産月ごとに最大 1 つのバッチが作成されます。 バッチ ID を使用すると、数量自体を複製することなく、2 つのヒープが同じ数量を参照できるようになります。 最小ヒープには次のものが含まれます`(key, id)`、最大ヒープには次のものが含まれます`(-key, id)`。 キーを否定すると、Python の最小ヒープが最大ヒープに変換されます。 

バッチは、需要または容量トリミングによって部分的に消費される可能性があります。 その場合、減少した量は、削除されたヒープに押し戻されます。 もう一方のヒープには依然として同じバッチ ID が含まれており、現在の数量を次のヒープから読み取ります。`remaining`したがって、古いエントリは、数量がゼロになった場合は常に無視できます。 

実現可能性チェックは、現在の生産能力を追加した直後に行われます。 もし`total_inventory < d[i]`、将来の月は今月の需要をサポートできないため、戻ります`-1`安全です。 

すべてのコスト計算では Python 整数が使用されるため、オーバーフローの問題はありません。 固定幅の整数を使用する言語では、答えは 64 ビット整数に格納される必要があります。 考えられる最大の答えは、32 ビット範囲を余裕で超えるものです。 

## 実用的な例

 公式サンプルは 2 つのテスト ケースで構成されています。 最初の月には 2 か月があり、最初の月は 6 台のコンピューターを生産でき、2 番目の月は 8 台のコンピューターを生産できます。 最初の 1 か月分の安価な原材料は保管する価値があり、完成品倉庫は境界を越えて 2 台のコンピューターを運ぶことができます。 公式の出力は (170) です。 

### サンプル 1

 最初のテスト ケースの入力は次のとおりです。```
2
10 5 3 6
15 7 2 8
2 3 2
```1 か月目の有効原材料費は (10) です。 2 か月目では、(\min(15,10+3)=13) になります。 したがって、生産コストは (13) と (15) になります。 

| 月 | 原材料費 | オフセット | 制作費 | 候補者数 | 販売済み | 販売後の在庫 | 容量 | 答え |
 | --- | --- | --- | --- | --- | --- | --- | --- | --- |
 | 1 | 10 | 0 | 13 | 6 | 5 | 1 | 2 | 65 |
 | 2 | 13 | 2 | 15 | 9 | 7 | 2 | 最終 | 170 |

 1 か月目の終わりには、1 台のコンピューターがストレージ内に残ります。 境界を越えると (E_1=2) が加算され、コンピュータのコストは (15) になります。 2 か月目では、新しく製造されたコンピューターのコストも (15) になるため、必要な 7 台のコンピューターすべてをそれぞれコスト (15) で取得できます。 合計は (5\times13+7\times15=170) となります。 

このトレースは、月の間にストレージ コストを適用する必要がある理由も示しています。 最初の月に残ったコンピューターの生産コストは (13) ですが、2 か月目に使用した場合のコストは (13+2=15) です。

 2 番目のテスト ケースは、```

0 0 0

 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | 7 | 8 | 7 | 不可能 |
 | 2 | 0 | 0 | 0 | 到達していません | 未処理 |

 アルゴリズムが検出するのは、`total_inventory < d[0]`すぐに (-1) を返します。 不足している 8 台のコンピューターは最初の月に必要となるため、2 か月目を待っても解決できません。 これは、公式サンプルで示されているまさに実現不可能性です。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | (O(k\log k)) | 月に最大 1 つの実稼働バッチが挿入され、バッチは 2 つのヒープから削除されます。 各バッチは最大 1 回完全に削除されますが、毎月、現在の削除が停止するバッチのみを部分的に処理できます。 |
 | スペース | (O(k)) | 2 つのヒープとバッチ数量配列には月あたり最大 1 つの論理バッチが含まれますが、月次入力配列も (O(k)) メモリを使用します。 |

 すべてのテスト ケースにわたって、合計 (k) は最大 (300,000) であるため、(O(k\log k)) が実用的です。 このアルゴリズムは、潜在的に膨大な数のコンピューターに依存することはありません。これが、アルゴリズムが意図された制限に適合する理由です。 

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io
import heapq

def solve_stream(stream):
    input = stream.readline
    t = int(input())
    out = []

    for _ in range(t):
        k = int(input())

        c = [0] * k
        d = [0] * k
        m = [0] * k
        p = [0] * k

        for i in range(k):
            c[i], d[i], m[i], p[i] = map(int, input().split())

        e = [0] * (k - 1)
        R = [0] * (k - 1)
        E = [0] * (k - 1)

        for i in range(k - 1):
            e[i], R[i], E[i] = map(int, input().split())

        min_heap = []
        max_heap = []
        remaining = []

        raw_cost = 0
        offset = 0
        total = 0
        ans = 0
        possible = True

        for i in range(k):
            if i > 0:
                offset += E[i - 1]
                raw_cost = min(c[i], raw_cost + R[i - 1])
            else:
                raw_cost = c[i]

            if p[i]:
                batch = len(remaining)
                remaining.append(p[i])
                key = raw_cost + m[i] - offset
                heapq.heappush(min_heap, (key, batch))
                heapq.heappush(max_heap, (-key, batch))
                total += p[i]

            if total < d[i]:
                possible = False
                break

            need = d[i]
            while need:
                while remaining[min_heap[0][1]] == 0:
                    heapq.heappop(min_heap)

                key, batch = heapq.heappop(min_heap)
                take = min(need, remaining[batch])

                ans += take * (key + offset)
                remaining[batch] -= take
                total -= take
                need -= take

                if remaining[batch]:
                    heapq.heappush(min_heap, (key, batch))

            if i < k - 1 and total > e[i]:
                remove = total - e[i]

                while remove:
                    while remaining[max_heap[0][1]] == 0:
                        heapq.heappop(max_heap)

                    neg_key, batch = heapq.heappop(max_heap)
                    take = min(remove, remaining[batch])

                    remaining[batch] -= take
                    total -= take
                    remove -= take

                    if remaining[batch]:
                        heapq.heappush(max_heap, (neg_key, batch))

        out.append(str(ans) if possible else "-1")

    return "\n".join(out)

def run(inp: str) -> str:
    old_stdin = sys.stdin
    sys.stdin = io.StringIO(inp)
    try:
        return solve_stream(sys.stdin)
    finally:
        sys.stdin = old_stdin

 ## 特殊なケース

 倉庫の容量がゼロということは、完成したコンピューターがその境界を越えることができないことを意味します。 考慮する```
1
2
0 0 0 2
0 2 0 0
1 0 0
```月 1 では、2 人の候補者が利用可能ですが、需要はゼロです。 需要が処理された後、インベントリには 2 台のコンピューターが含まれますが (e_1=1)、最大コスト ヒープによって 1 台が削除されます。 残りの在庫はサイズ 1 です。 月 2 には需要が 2 で生産能力が 0 であるため、使用可能なコンピューターは 1 台だけであり、アルゴリズムは (-1) を返します。 容量は、現在の販売後に、境界制約が属する場所に正確に適用されます。 

原材料は製造月のかなり前から購入できる場合があります。 考慮する```
1
2
1 0 0 0
100 1 0 1
1 1 0
```最初の月の実質的な直接コストは (1) です。 2 か月目の有効な直接コストは (\min(100,1+1)=2) です。 したがって、2 か月目はコスト (2) で必要なコンピューターを生産し、答えは (2) になります。 このアルゴリズムでは、明示的な原材料在庫は必要ありません。`raw_cost`これは、1 単位の原材料を当月に移動する最も安価な方法をすでに示しています。 

完成品の保管にも同様の累積効果があります。 考慮する```
1
2
1 0 0 1
100 1 0 1
1 1 2
```最初の月のコンピュータには製造コスト (1) がかかります。 (e_1=1) ため、容量チェックを通過します。 アルゴリズムが 2 か月目に進むと、`offset`は (2) だけ増加するため、格納されているコンピュータの現在のコストは (1+2=3) になります。 新しい月 2 のコンピューターのコストは (100) となるため、最小ヒープで保管されているコンピューターが販売され、答えは (3) になります。 

ゼロ需要も、最小限のヒープに触れることなく処理する必要があります。 例えば、```
1
2
0 0 0 1
0 1 0 1
0 0 0
```答えは(0)です。 最初の月には生産候補が 1 つある可能性がありますが、その需要はゼロであり、ストレージ容量もゼロであるため、候補は境界で破棄されます。 次に、月 2 は、独自に必要なコンピューターをコストなしで製造します。 すべての製品候補が最終的に販売される必要があると想定するユニットレベルの実装では、廃棄されたコンピュータに対して誤って請求される可能性があります。 

最後に、バッチは部分的にのみ販売または部分的に破棄できます。 最初のサンプルの最初の月を考えてみましょう。この場合、候補は 6 つありますが、販売されるのは 5 つだけです。 バッチ数量が 6 から 1 に変更され、残りの 1 は両方のヒープ構造に残ります。 後で、そのバッチが最も高価な生き残ったバッチになった場合、最大ヒープによって削除できるのはその 1 台のコンピューターだけです。 各バッチで数量を保存することで、この操作をバッチ内のコンピューターの数に依存せずに維持できます。
