 ## 解決策
 ## 問題の理解

 スタックの列が与えられ、各スタックにはいくつかのブロックが保持されます。 ブロックを移動できるのは隣接するスタック間でのみであり、テーブルからブロックを押し出すことでラインの両端からブロックを削除することもできます。 目標は、そのような単位移動の最小数を使用して、スタック高さの初期構成をターゲット構成に変換することです。ここで、単位移動とは、1 ブロックを左または右に 1 位置ずつシフトするか、境界でブロックを破棄することです。 

各ブロックは、最終的に最終スタックに配置されるか、システムから削除される必要がある質量単位と考えることができ、隣接するスタック間の移動単位ごとに、交差するエッジごとに正確に 1 ステップのコストがかかります。 これにより、線形コストの経路に沿って過剰な質量を輸送することが根本的に問題となります。 

制約は大きく、スタックは最大 100,000 個、スタックあたりの値は最大 10^12 です。 これにより、個々のブロックを追跡したり、動きを明示的にシミュレートしたりするアプローチは即座に除外されます。 有効なソリューションはすべて、スタック間のフローを集約し、直線または直線に近い時間で実行する必要があります。 

重要な微妙な点は、実現可能性が保証されていないことです。 ブロックの総数が一致していても、境界にマスを正しく配線できない場合、または境界からマスを正しく配線できない場合は、局所的な不均衡により変換が不可能になる可能性があります。 

合計だけが重要であると仮定すると、素朴な間違いが生じます。 たとえば、sum(a) が sum(b) と等しいことのみをチェックする場合、質量が中央に閉じ込められているが、境界がそれを吸収または供給できないケースを受け入れる可能性があります。 

考慮する：```
n = 3
a = [0, 10, 0]
b = [5, 0, 5]
```合計は一致しますが、中央のスタックを両端に分割する必要があります。 移動は隣接性を介してのみ行われるため、これは可能ですが、問題により厳密な方向制約や境界制限がある場合、単純な推論は失敗する可能性があります。 この例は、実現可能性が合計だけではなく累積フローに依存することを強調しています。 

長距離輸送コストを考慮せずに、地元の余剰分を貪欲に移動すると、別の失敗例が発生します。 集約せずにブロックを 1 つずつ移動すると、二次的な動作が発生します。 

## アプローチ

 重要な観察は、各スタックの違いがブロックの供給または需要として解釈できることです。 差分配列を次のように定義します。$$d_i = a_i - b_i$$左から右に見てみると、ランニング余剰を運ぶことが考えられます。 スタックに余分なブロックがある場合は常に、その余剰ブロックを右に渡す必要があります。 赤字がある場合は、左からの流入または以前の送金によって補わなければなりません。 

エッジを越えて運ばれる余剰の各ユニットは、ステップごとに 1 つの移動に正確に寄与します。 これは、総コストは、ブロックがグローバルにどこに到達するかではなく、隣接するスタック間の各境界をどれだけの量のフローが横切るかによって決まることを意味します。 

ブルートフォース解釈では、各ブロックの移動を個別にシミュレートします。 各ブロックは O(n) 個の位置を横断する可能性があり、最悪の場合は O(n^2) 個の動作が発生しますが、これは n が 100,000 までの場合には不可能です。 

重要な洞察は、個々のブロックを追跡する必要がないということです。 配列全体をスイープする際に、累積的な不均衡を追跡する必要があるだけです。 実行中のプレフィックスの合計により、各境界を通過する必要があるフローの量が正確にわかり、総コストは絶対プレフィックス値の合計になります。 

最終的に差の総和がゼロにならなければ、全体としては過不足があることになります。 端部では境界の削除のみが許可されているため、この不均衡は建設によって局所的にすでに解決されている必要があります。 そうしないと変換が不可能になります。

 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n^2) | O(n) | 遅すぎる |
 | プレフィックスフロー集約 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. スタックを反復処理し、実行残高を追跡することにより、差分配列を暗黙的に計算します。`cur = cur + (a[i] - b[i])`。 

この値は、i で終わるプレフィックスから右に追加ブロックをどれだけプッシュする必要があるかを表します。 
2. いずれかの時点で最終的な合計残高がゼロ以外の場合は、-1 を返します。 

これにより、すべてのブロックがターゲットと一致するか、境界でのみ削除可能である必要があるため、グローバルな実現可能性が保証されます。 
3.初期化`cur = 0`そして`ans = 0`。 
4. すべてのスタックを左から右に繰り返します。 各位置 i について、更新します`cur += a[i] - b[i]`。 
5. アップデート後、追加`abs(cur)`答えに。 

これは、ゼロ以外のプレフィックス余剰を繰り越す必要があるため、i と i+1 の間の境界を越える必要があるブロックの数を表します。 
6. 戻る`ans`すべてのスタックを処理した後。 

### なぜ効果があるのか

 i と i+1 の間の各境界で、プレフィックスの合計`cur`i までのすべてのスタックをターゲットと一致させるために、その境界を越える必要があるブロックの正味の数を表します。 正の値は、余分なブロックが右に移動する必要があることを意味します。 負の場合は、右側から赤字を埋める必要があることを意味します。 不均衡の各単位は、その境界を越える移動の 1 単位に正確に対応するため、絶対的なプレフィックスの不均衡を合計すると、隣接する各移動が 1 回だけカウントされます。 フローは境界を除いて保存されるため、移動が二重にカウントされたり、取り逃されたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    cur = 0
    ans = 0

    for i in range(n):
        cur += a[i] - b[i]
        ans += abs(cur)

    if cur != 0:
        print(-1)
    else:
        print(ans)

if __name__ == "__main__":
    solve()
```この実装は単一の線形パスに依存します。 変数`cur`現在の境界を越えて輸送する必要があるブロックの実行余剰を維持します。 の蓄積`abs(cur)`重要なステップです。最適なフローで各エッジを通過する必要があるブロックの数をカウントします。 

最終チェック`cur != 0`すべてのスタックを処理した後に、比類のない余剰が残らないようにします。 残留質量がある場合、境界以外で吸収または作成することはできません。また、両端は流れモデルで暗黙的にすでに考慮されているため、ゼロ以外の剰余は不一致を示します。 

よくある実装上の間違いは、`abs(cur)`更新する前に更新してください`cur`。 正しい順序が重要です。`cur`境界での交差コストを測定する前に、現在位置までの不均衡を反映する必要があります。

 ## 特殊なケース

 エッジ ケースの 1 つは、初期構成とターゲット構成の間ですべてのスタックが同一である場合です。 この場合、すべての差はゼロであるため、ランニングバランスは全体を通してゼロのままであり、累積コストはゼロのままです。 アルゴリズムは特別な処理を行わなくても当然 0 を返します。 

もう 1 つの特殊なケースは、すべての過剰が 1 つのエンドポイントに集中している場合です。 たとえば、次の場合`a = [10,0,0]`そして`b = [0,0,10]`、プレフィックスの合計は大きくなり、最後のステップまで正の値を維持します。 余剰全体がすべての境界を正確に 1 回通過する必要があるため、コストは正しく累積されます。 

実装が最終的な実現可能性チェックを忘れた場合、障害モードが表示されます。 総余剰がゼロ以外の場合、実行中のプレフィックスは依然として数値コストを生成する可能性がありますが、それは有効な変換に対応しません。 決勝戦`cur == 0`条件がそのようなケースを受け入れることを妨げているものです。
