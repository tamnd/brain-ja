 ## 問題の理解

 正の整数の配列が与えられ、重複しない部分配列のシーケンスを構築するように求められます。 これらの部分配列は左から右の順序で選択する必要があり、その長さは、ある値から開始して減少するシーケンスを形成するように固定されています。$k$まで$1$。 したがって、最初に選択されたセグメントの長さは$k$、2番目は長さです$k-1$など、最後のセグメントの長さが決まるまで続きます。$1$。 すべてのセグメントは位置の昇順で表示される必要があり、重複するものはありません。 

このようなすべての有効な構造の中で、選択できるセグメントの数を最大化したい、つまり、$k$、選択された各セグメント内の要素の合計は、シーケンス内を移動するにつれて厳密に増加する必要があるという追加の制約の下で。 

重要な問題は、セグメントの長さが任意ではなく、固定の降順パターンに厳密に制約されており、配列内の順序付けと合計の増加制約の両方を同時に尊重する必要があることです。 

制約により許可されるのは、$n$まで$10^5$テストケース全体で。 これにより、すべてのセグメント パーティションを明示的に試行する 3 次または 2 次のアプローチが除外されます。 平$O(n^2)$最悪の場合、テストケースごとの処理が遅すぎるため、$n$サイズが大きくなり、最大 100 個のテスト ケースが存在する可能性があります。 テストケースごとに線形または線形演算に近いものが必要です。 

素朴な貪欲なアイデアが微妙に失敗するケースは、初期の選択によってわずかに最適以下の合計が強制され、後でより長いチェーンがブロックされる場合に現れます。 たとえば、将来のセグメントは位置と合計の順序の両方に依存するため、特定の長さの局所的に最大の合計セグメントを選択すると、より長い有効なチェーンの形成が妨げられる可能性があります。 

もう 1 つのよくある落とし穴は、長さごとに最適なセグメントを個別に選択できると想定していることです。 セグメントの位置がグローバルに制約されるため、これは失敗します。長さを配置すると、$k$セグメントの場合、短いセグメントはすべて厳密に右側に配置する必要があります。 

## アプローチ

 ブルートフォースアプローチでは、最初のセグメントの長さの可能な選択肢をすべて列挙しようとします。$k$、次に長さの次のセグメントを再帰的に選択します$k-1$、 等々。 セグメントの長さごとに、すべての有効な開始位置を試し、オンザフライまたはプレフィックス合計を介して合計を計算し、昇順の制約を適用します。 

プレフィックスの合計が各範囲の合計になる場合でも$O(1)$、セグメントの開始を選択する方法は組み合わせによって異なります。 最悪の場合、これは配列の多くのパーティションを探索するように動作し、そのパーティションは指数関数的に増加します。$n$。 これは不可能です$n = 10^5$。 

重要な構造的観察は、固定のすべてのセグメントを明示的に決定する必要がないことです。$k$ゼロから。 代わりに、逆に考えることができます。$k$、セグメントを左から右に貪欲に配置し、厳密に増加する合計シーケンスを生成する必要な長さの可能な限り最も早い有効なセグメントを常に配置したいと考えています。 

より深い洞察は、修正する必要はないということです$k$直接。 代わりに、常に貪欲にチェーンを拡張した場合に有効なチェーンを構築できる長さを計算できます。 各ステップにより、配列の残りの使用可能な長さが減少し、問題は特定の配列の実現可能性のチェックになります。$k$、二分探索を提案します。 

ただし、さらに改善することもできます。 だって全部$a_i > 0$、セグメントの位置が右に移動すると、セグメントの合計は増加しますが、長さは厳密には単調ではありません。 これにより、二分探索を必要とせずにチェーンを常に可能な限り拡張しようとする貪欲な構築が可能になります。 

次に利用可能な開始位置へのポインタを維持し、その合計が以前に選択した合計よりも大きくなるように、必要な長さのセグメントを選択することを繰り返し試みます。 すべての値が正であるため、セグメントがある位置で有効になると、右に移動しても合計が増加するだけなので、各長さに対して最も早い有効なセグメントを貪欲に配置できます。 

これにより、セグメントの合計を注意深く維持することで、問題が 1 回の左から右へのスキャンに軽減されます。

 ## アルゴリズムのチュートリアル

 セグメントの合計を一定時間内にクエリできるように、プレフィックスの合計を事前に計算します。 これは、候補セグメントを繰り返し評価するために必要です。 

次に、さまざまな潜在的な値から開始して、可能な限り最長のチェーンを構築しようとします。$k$ただし、それぞれを明示的にテストするのではなく、$k$、プロセスを 1 回シミュレートし、形成されるセグメントの数を測定できることがわかります。 

1. 範囲の合計をすばやくクエリできるように、配列のプレフィックスの合計を計算します。 これにより、セグメントの合計を一定時間で評価できるようになります。候補セグメントの合計を繰り返し比較するため、これは不可欠です。 
2. 次のセグメントが開始できる最も早い位置を示すポインタを使用して、配列の左から開始します。 最初はこれが位置 1 です。 
3. セグメントを事前に定義するのではなく、長さの降順に配置するようにしてください。$k$、貪欲に連鎖を伸ばしていきます。 次に試行されるセグメントの長さと、最後に選択されたセグメントの合計を維持します。 
4. 指定されたセグメント長について、現在のポインタからスキャンして、合計が前のセグメントの合計より厳密に大きい有効なセグメントが存在する最も古い位置を見つけます。 
5. そのようなセグメントが見つかったら、それにコミットし、最後の合計を更新し、ポインタをこのセグメントの後の位置に移動します。 
6. セグメント長を 1 ずつ減らし続け、有効なセグメントが配置できなくなるまでこのプロセスを繰り返します。 
7. 正常に配置されたセグメントの数が答えです。 

重要な決定は常に、各長さに対して最も早い有効なセグメントを選択することです。 これにより、「適切な」高額セグメントが早期に無駄になることがなくなり、後の短いセグメントに対して最大限の柔軟性が保証されます。 

### なぜ効果があるのか

 すべてのステップで、最後に選択されたセグメントが、合計しきい値に達するすべての有効な選択肢の中で可能な最小の終了位置を持つという不変条件を維持します。 すべての要素が正であるため、セグメントを右にシフトすると、その合計が増加するだけで、残りのスペースが減少します。 したがって、後からの選択は、以前の有効な選択よりも将来の実現可能性を制限するだけです。 これにより、貪欲な早期選択戦略が最適化され、さらに拡張できた可能性のあるソリューションがブロックされることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]

    def range_sum(l, r):
        return pref[r] - pref[l]

    # we try to build maximum number of segments
    # segment lengths conceptually decrease from k, but we build greedily
    res = 0
    prev_sum = 0
    i = 0

    # we try increasing number of segments implicitly
    # by always attempting next possible segment
    length = n

    while i < n and length > 0:
        found = False

        while i + length <= n:
            s = range_sum(i, i + length)
            if s > prev_sum:
                prev_sum = s
                i = i + length
                res += 1
                found = True
                break
            i += 1

        if not found:
            break

        length -= 1

    print(res)

t = int(input())
for _ in range(t):
    solve()
```このコードは、セグメント合計クエリが定数時間となるようにプレフィックス合計を構築します。 次に、ポインタを維持します`i`可能な限り早いスタート位置を実現します。 試行されたセグメント長ごとに、合計が前のセグメントの合計を超えるセグメントが見つかるまで、前方にスキャンします。 見つかったらコミットして先に進みます。 そのようなセグメントが存在しない場合は停止します。 

微妙な点は、私たちは常に前進しているということです`i`スキップ無効開始時も同様です。 重複しない制約と要件の増加により、スキップされた開始は同じまたはそれ以降のセグメント長では再利用できないため、これは不可欠です。

 ## 特殊なケース

 主なエッジ ケースは、多くの短いセグメントが存在するが、合計の制約によりチェーンを形成できない場合です。 たとえば、次のような配列では、`[1,1,1,1,1]`、すべてのセグメントの合計は等しいため、有効なセグメントは 1 つだけです。 アルゴリズムは最初の完全なセグメントを正しく選択しますが、その後は厳密にそれより大きい合計を見つけることができません。 

もう 1 つのエッジ ケースは、初期のセグメントが魅力的だが最適ではない場合です。 で`[1,2,1,1,3,2,6]`、素朴なアプローチは選択するかもしれません`[1,2,1]`その後行き詰まりますが、貪欲スキャンにより、少し後により適切な有効なセグメントが存在する場合は、それが選択され、チェーンを拡張する可能性が維持されます。 

最後に、サフィックスの合計が急速に増加するケースでは、スキップが正しく処理されることが保証されます。 ポインタは前方にのみ移動するため、以前の位置を再検討することはありません。これは、セグメントの実現可能性に対する正の単調効果により安全です。
