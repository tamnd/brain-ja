 ## 解決策
 ## 問題の理解

 私たちは 2 の累乗の動的な集合を維持しています。 ADD 操作を受け取るたびに、次の形式の値を挿入します。$2^x$マルチセットに入れます。 各 GET 操作では、到達可能性に関する質問が行われます。現在利用可能な数値のうち、合計がターゲットに等しいサブセットを選択できるかどうかです。$w$。 

重要な特徴は、すべての要素が純粋な 2 の累乗であり、マルチセットには同じ累乗の繰り返し挿入を含めることができるため、重複が許可されることです。 これにより、その構造はバイナリ表現システムに近いものになりますが、同じ価値の複数の「コイン」が存在する可能性があるというひねりが加えられています。 

制約により、以下の処理が強制されます。$10^5$オンラインでの操作。 各 GET クエリには、最大で次のターゲットが含まれる場合があります。$10^9$したがって、すべてのサブセットを試したり、クエリごとの指数推論を行うことさえできません。 サブセットを列挙しようとしたり、クエリごとにナップサック スタイルの DP を実行しようとしたソリューションは、すぐに失敗します。$2^{30}$クエリごとのサブセットの組み合わせはすでに制限をはるかに超えています。 

複数の同一のパワーが累積すると、微妙な問題が発生します。 たとえば、3 つ挿入すると、$2^0$要素がある場合、それらのみを使用して 1、2、または 3 のような合計を形成できます。 カウントを考慮せずに各パワーを独立して扱う単純なアプローチは、ここでは失敗します。 正しい解釈は、各指数が制限された数の同一のコインのように動作し、ビット間のキャリーが可能になるということです。 

もう 1 つの失敗例は、新しい貪欲分解で各 GET を独立して処理しますが、以前の ADD 操作によって状態が蓄積されていることを忘れている場合です。 マルチセットが進化するため、クエリごとに最初から再計算するのは遅すぎます。 

## アプローチ

 ブルート フォースの解釈は簡単です。GET クエリごとに、マルチセットのすべてのサブセットを考慮し、サブセットの合計が次の値になるかどうかを確認します。$w$。 あれば$k$現在マルチセット内にある要素、これを確認する必要があります$2^k$サブセットは指数関数的に増加します。 たとえ$k = 40$、これは実行不可能になります、そしてここで$k$到達できる$10^5$。 

2 番目の単純な改善は、動的プログラミング セットを介してすべてのサブセットの合計を維持することです。 各 ADD の後、新しい累乗を既存のすべての合計に加算することにより、新しい合計をマージします。 これにより、最悪の場合でも挿入ごとに到達可能な合計数が 2 倍になり、再び指数関数的な増加につながります。 

重要な観察は、すべての値が 2 のべき乗であるということです。 つまり、すべての数値が正確に 1 つの 2 進位置に寄与し、それらを組み合わせるとキャリーが発生する可能性がある 2 進加算のように動作します。 サブセットを追跡する代わりに、各指数のコピーがいくつ存在するかを追跡するだけで済みます。 

させて$c[i]$要素の数が次と等しいこと$2^i$。 形成できるかどうかを答えるには$w$、私たちは解釈しようとします$w$バイナリで、利用可能なカウントを使用して剰余を上に繰り上げて、ビットを最低位から最高位まで貪欲に一致させます。 これにより、問題はバイナリの重みに関する有界コイン システムに帰着します。ここでは、各重みが前の重みのちょうど 2 倍であるため、貪欲なキャリー伝播が有効になります。 

これにより、各 GET クエリが最大 31 ビットにわたる小さなループに変換されます。

 ## アルゴリズムのチュートリアル

 配列を維持します`cnt`どこ`cnt[i]`何回保存するか$2^i$が挿入されました。 

1.追加の場合$x$、増分`cnt[x]`1つずつ。 これは、その電力の利用可能性を直接記録します。 
2. GETの場合$w$、建物のシミュレーション$w$最低電力から最高電力まで少しずつ。 
3. 各ビット位置について$i$、現在次の単位が必要かどうかを計算します。$2^i$から$w$。 
4. 利用可能なコインを追加する`cnt[i]`そのレベルで実行中の「供給」に移行します。 この供給量は、何ユニットかを表します。$2^i$私たちは使えます。 
5. 現在のビットが$w$が 1 の場合、1 単位を消費する必要があります。$2^i$。 供給がゼロの場合、このビットを満たすことができないため、答えは直ちに NO になります。 
6. 要件を満たした後、レベルに残っている供給は$i$として上に運ばれます$2^{i+1}$、2時から$2^i$一つを形成できる$2^{i+1}$。 
7. このプロセスを最大ビットまで続けます。$w$, そして最後に、残ったキャリーが無関係か吸収できるかを確認します。 

重要な考え方は、余分なものを決して捨てないということです。 リソース プーリングを使用したバイナリ加算とまったく同じように、すべてが上方に伝播します。 

### なぜ効果があるのか

 すべてのビット位置で$i$、その価値へのすべての貢献は区別できません。それらはすべてです。$2^i$。 ペアリングや残り物は自然に次のビットに変換されます。$2 \cdot 2^i = 2^{i+1}$。 これにより、下位ビットでの決定が後戻りすることなく実現可能性を完全に決定する厳密な階層が強制されます。 必要なビットを満たさない場合は上位ビットで修正できないため、各ビットでの貪欲な消費は安全ですが、余剰分はキャリーを介して常に最適に再利用できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    m = int(input())
    cnt = [0] * 31

    for _ in range(m):
        t, v = map(int, input().split())

        if t == 1:
            cnt[v] += 1
        else:
            w = v
            carry = 0
            ok = True

            for i in range(31):
                carry += cnt[i]

                if (w >> i) & 1:
                    if carry == 0:
                        ok = False
                        break
                    carry -= 1

                carry //= 2

            if ok:
                print("YES")
            else:
                print("NO")

if __name__ == "__main__":
    solve()
```この実装では、サイズ 31 の固定周波数配列が維持されます。$2^{30}$以下のすべての値をカバーするには十分です$10^9$。 各 GET クエリは、実行中のキャリーを使用してターゲットのバイナリ構築をシミュレートします。 

重要な点は、ビットを昇順に処理することです。 集計を次の 2 のべき乗に反映するために、各レベルの後にキャリーを常に 2 で割る必要があります。 この分割を正しく適用できないと、より高いレベルでリソースを過剰にカウントすることになります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    m = int(input())
    cnt = [0] * 31
    out = []

    for _ in range(m):
        t, v = map(int, input().split())
        if t == 1:
            cnt[v] += 1
        else:
            w = v
            carry = 0
            ok = True
            for i in range(31):
                carry += cnt[i]
                if (w >> i) & 1:
                    if carry == 0:
                        ok = False
                        break
                    carry -= 1
                carry //= 2
            out.append("YES" if ok else "NO")

    return "\n".join(out)

 ## 特殊なケース

 エッジ ケースの 1 つは、多くの小さな電力が蓄積され、複数のキャリーを介してカスケードする必要がある場合に発生します。 たとえば、次のコピーを 8 つ挿入すると、$2^0$すぐにシングルのように振る舞うべきです$2^3$。 各レベルが 2 による整数除算を実行し、安定するまで剰余を繰り返し上方に伝播するため、アルゴリズムはこれを処理します。 

もう 1 つのケースは、GET クエリが単一の格納された指数よりも大きい値を要求する場合です。 単一の一致するパワーが存在しない場合でも、組み合わせは機能する可能性があります。 たとえば、2$2^3$エントリは満たすことができます$2^4$。 キャリー メカニズムにより、上位ビットを評価する前にこれらのマージが常に考慮されるため、アルゴリズムが有効な構造を誤って拒否することはありません。
