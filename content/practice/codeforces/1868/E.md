 ## 解決策
 ## 問題の理解

 整数配列が与えられ、それをいくつかの連続したブロックに分割することができます。 各ブロックには合計があり、これらのブロックの合計を新しい配列と呼びます。 

制約は個々のブロックではなく、連続するブロックのグループごとに適用されます。 ブロックの連続セグメントを取得する場合、それらのブロック合計の合計は、そのセグメント内の最小ブロック合計と最大ブロック合計の間になければなりません。 言い換えれば、ブロック合計のウィンドウを見ると、そのウィンドウの合計はその最小要素と最大要素によって形成される範囲を「脱出」することはできません。 

目標は、このグローバルな一貫性条件を満たしながら、元の配列をできるだけ多くのブロックに分割することです。 

テストごとに n ≤ 300、合計 n ≤ 1000 という制約は、テストごとに O(n3) または O(n² log n) が合格する可能性があることを示唆していますが、枝刈りを行わないテスト ケースごとの 3 次関数はすでに境界線に達しています。 これは、間隔にわたる DP または事前に計算された実現可能性チェックによる貪欲なセグメンテーションを直ちに示唆します。 

微妙な問題は、この条件が隣接するペアだけでなく、ブロックのすべてのサブセグメントにわたってグローバルであることです。 隣接するブロックの相互作用のみをチェックする単純な試みは失敗します。 たとえば、ブロックサムを考えてみましょう。`[1, 10, -8]`。 隣接するチェックは問題ないように見えますが、セグメントは`[1, 10, -8]`合計があります`3`、一方、min は`-8`そしてマックスは`10`、それで合格します。 ただし、構造がより複雑な場合は、他の組み合わせが壊れる可能性があります。 本当の問題は、複数回の分割後にのみ違反が現れることが多いということです。 

もう 1 つの障害モードは、局所的な状態が安全であると思われる場合の貪欲な切断です。 プレフィックス決定における制約は単調ではないため、ローカルで有効なカットは将来の有効なパーティションをブロックする可能性があります。 

## アプローチ

 ブルート フォースのアイデアは、配列を連続セグメントに分割するすべての可能な方法を試し、セグメントの合計を計算し、考えられるすべてのセグメント グループの条件を検証することです。 指数関数的に多くのパーティションがあり、各パーティションに対してすべてのセグメント部分配列をチェックすると、セグメントに別の二次係数が追加されるため、n = 30 の場合でも完全に実行不可能になります。 

重要な点は、この条件がグループ化されたときにセグメントの合計がどのように動作するかを制限していることです。 パーティションを修正する場合、実際にはシーケンスを要求することになります。`s1, s2, ..., sm`すべての連続するサブシーケンスが「最小/最大を超えたオーバーシュートがない」特性を満たすようにします。 条件を拡張すると、ブロックの部分和が極値に対して一方向に大きくずれた場合に違反が発生することが代数的に示されます。 

制約を再解釈するより便利な方法は、それが累積的に「連続ブロックにわたる厳密な単調ドリフト」を禁止することと同等であることに気づくことです。 これは、構造的な特性を暗示していることがわかります。有効なパーティションは、前のパーティションを拡張することで、累積合計が個々のブロックの合計の範囲から外れるブロックのプレフィックスが導入されないように、すべての新しいブロックを選択する必要があるシーケンスに対応します。 

これにより DP が有効になります。`dp[i]`プレフィックスの最大ブロック数になります`[1..i]`。 遷移を計算するには、最後のブロックを試します`[j+1..i]`で終わる有効なパーティションにそれを追加するかどうかを確認します。`j`有効性を保持します。 重要なのは、パーティションの有効性はセグメントの合計にのみ依存するため、O(1) で合計を事前計算し、ブロック合計の実行スキャンを使用してマージ候補を検証できることです。 

より詳細な最適化は、パーティションを拡張するときに、ブロックのプレフィックスの合計がその範囲に対して極端になった場合にのみ危険な違反が発生することに気づいたことから生まれています。 これにより、拡張機能のテスト中にセグメントの合計と累積合計の増分最小/最大を維持できるようになり、パーティションあたりの検証が O(m²) から O(m) に削減されます。

 ## アルゴリズムのチュートリアル

 各セグメントの終了位置を決定し、結果として得られるセグメント合計のシーケンスが有効なままであることを確認することで、ソリューションを構築します。 

1. O(1) で部分配列の合計を取得できるように、プレフィックスの合計を事前計算します。 これは、候補セグメントの境界を繰り返しテストするため必要です。 
2. DP 配列を定義します。`dp[i]`インデックスで終わるプレフィックスをカバーする有効なセグメントの最大数を格納します`i`。 これは、プレフィックスの最適なソリューションが最適に拡張されるという考えをエンコードしています。 
3. 各エンドポイントについて`i`、すべての可能な以前のカット位置を反復します。`j < i`。 最後のセグメントは、`[j+1, i]`、その合計は直接計算できます。 
4. かどうかを決定する`dp[j]`に移行できます`i`で終わるセグメントのシーケンスにこの新しいセグメントを追加することをシミュレートします。`j`。 すべてを最初から再計算するのではなく、最小セグメント合計、最大セグメント合計、および累積セグメント合計の動作を増分的に追跡します。 
5. 新しいセグメントを追加することで、セグメント合計のすべての連続ブロックの合計がその最小要素と最大要素の間にあるという不変条件が維持される場合、遷移と更新を許可します。`dp[i]`。 

これが機能する主な理由は、条件違反は、新しく追加されたセグメントで終わるセグメントの連続ブロックに現れる必要があるためです。 つまり、トランジションをテストするときは、最後のセグメントに関係する構造のみを検証する必要があります。 それ以前の部分は、すでに DP によって有効であることが保証されています。 

維持される不変条件は次のとおりです`dp[i]`は常に次のパーティションを表します`a[1..i]`そのセグメント合計シーケンスは制約の下で有効です。 すべての拡張機能は、最後のセグメントによって導入されたすべての新しい違反を明示的にチェックするため、無効な構成は決して認められません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]

    dp = [1] * (n + 1)
    dp[0] = 0

    # we will store segment sums for reconstruction checking
    seg_sums = [[] for _ in range(n + 1)]
    seg_sums[0] = []

    def valid_extend(prev_sums, new_sum):
        # simulate appending and check condition on all suffix windows ending at last
        cur = []
        for x in prev_sums:
            cur.append(x)

        cur.append(new_sum)

        m = len(cur)
        total = 0
        for i in range(m - 1, -1, -1):
            total += cur[i]
            mn = min(cur[i:])
            mx = max(cur[i:])
            if not (mn <= total <= mx):
                return False
        return True

    for i in range(1, n + 1):
        best = 1
        best_sums = [pref[i] - pref[0]]

        for j in range(i):
            new_sum = pref[i] - pref[j]

            if j == 0:
                candidate = [new_sum]
            else:
                if dp[j] == 0:
                    continue
                if valid_extend(seg_sums[j], new_sum):
                    candidate = seg_sums[j] + [new_sum]
                else:
                    continue

            if dp[j] + 1 > best:
                best = dp[j] + 1
                best_sums = candidate

        dp[i] = best
        seg_sums[i] = best_sums

    print(dp[n])

t = int(input())
for _ in range(t):
    solve()
```この実装では、プレフィックスごとに、最適な有効なパーティションを実現するセグメント合計の実際のリストが維持されます。 これは最悪の場合コストが高くなりますが、n が小さいため制約には適合します。 

機能`valid_extend`新しいセグメントを追加した後、セグメント合計配列のすべてのサフィックスの定義条件を明示的にチェックします。 これにより、すべての連続するセグメント グループが正しく動作するという要件が直接強制されます。 チェックはサフィックスをスキャンし、最小値と最大値を再計算することによって行われます。これは単純ですが、意図した制約構造に対して正確です。 

DP トランジションはすべてのカット位置を試行し、すべてのパーティションが考慮されるようにします。 正確性は、新しいセグメントが追加されるたびに完全な構造状態を明示的に検証することに依存します。 

## 実用的な例

 最初のサンプル配列を考えてみましょう`[-1, 5, 4]`。 

We compute prefix sums:`0, -1, 4, 8`。 インデックス 1 にはセグメントが 1 つだけ存在するため、`dp[1] = 1`セグメント合計あり`[-1]`。 

インデックス 2 で、2 で終わるパーティションをテストします。`[-1, 5]`セグメントの合計を与える`[-1, 5]`。 これは、ウィンドウの合計がその 2 要素シーケンスの最小値と最大値の間にあるため有効です。 それで`dp[2] = 2`。 

インデックス 3 では、以下の拡張を考慮します。`dp[2]`。 追加`[4]`セグメントの合計を算出します`[-1, 5, 4]`。 サフィックスウィンドウをチェックすることで有効性が確認されるため、`dp[3] = 2`。 

| 私 | 選択された分割 | セグメント合計 | dp[i] |
 | --- | --- | --- | --- |
 | 1 | [ -1 ] | [-1] | 1 |
 | 2 | [-1][5] | [-1、5] | 2 |
 | 3 | [-1][5][4] | [-1、5、4] | 2 |

 このトレースは、すべての拡張子が隣接するペアだけではなく完全なセグメント構造に対してどのように検証されるかを示します。 

2番目の例は`[1, 4, 7, -1, 5, -4]`。 最適な戦略は、新しいセグメントの合計がサフィックス ウィンドウ全体の既存の最小/最大の一貫性を破らない場合にのみ、セグメントを拡大し続けます。 DP は、無効な拡張機能は即座に拒否されるため、後で違反を強制する早期の分割を自然に回避します。`valid_extend`。

 ## 特殊なケース

 重要なエッジケースは、すべての要素が同一である場合です。 のような配列の場合`[2,2,2,2]`、すべてのセグメントの合計は長さに比例し、積極的に分割しても条件に違反することはありません。 新しいセグメントの合計は以前の合計の最小値と最大値の範囲と一致するため、アルゴリズムはすべてのカットを繰り返し受け入れます。 

別の特殊なケースは、次のような交互の符号で発生します。`[5, -5, 5, -5]`。 ここでは、初期の分割は有望に見えますが、拡張パーティションによりサフィックス ウィンドウが作成され、累積合計が相殺され、最小-最大制約に違反します。 検証ステップでは、サフィックスの累積合計が許容範囲を超えた場合に、これらの拡張子が正確に拒否されます。 

3 番目のエッジ ケースは、厳密に増加する配列です。 で`[1,2,3,4]`を分割しようとすると、単調に増加するセグメント合計が作成され、セグメントの累積合計がすぐに中間値を超えるため、複数セグメントの分割ができなくなります。 すべての分割試行がフル ウィンドウ検証に失敗するため、DP は単一のセグメントに正しく折りたたまれます。
