 ## 解決策
 ## 問題の理解

 私たちには、開始日と期間が固定された旅行の小さなコレクションが与えられ、旅行ごとにビザの手続き時間が決定され、申請後にパスポートが拘束される期間が決まります。 グレブは最大 2 つのパスポートを所有しており、各ビザはそのうちの 1 つに割り当てられる必要があります。 パスポートを使用してビザ申請を提出すると、ビザが処理されるまでそのパスポートは利用できなくなります。 課題は、パスポートへの旅行の割り当てと、各旅行のビザ申請が行われる正確な日の両方を決定し、グレブが在宅中にのみ申請ができることを尊重しながら、すべての旅行が出発前にビザを準備できるようにすることです。 

時間は日単位で進み、各旅行は数日という閉じた間隔を占めます。 これらの日の間、グレブは不在のためビザを申請できません。 重要な制約は時間的一貫性です。あるパスポートを 1 つのビザに使用した場合、そのパスポートを使用する次のビザは、前のパスポートが完全に返還された後にのみ申請できます。 

入力サイズは少量で、最大 22 回の旅行と最大 2 つのパスポートです。 これは、サブセットに対する指数関数的な探索が妥当であることを直ちに示唆していますが、それは各状態遷移が効率的で慎重に構造化されている場合に限ります。 各ビザには連続決定変数 (申請日) があり、単純に列挙すると 10^9 までの大きな日数範囲にわたって爆発的に増加するため、すべてのスケジュールを完全に総当たりで実行することは不可能です。 

主な微妙な点は、旅行間の相互作用に起因します。 たとえ旅行が重なっていなくても、旅行の間隔には禁じられた時間的ギャップが生じるため、ビザの申請が妨げられる可能性があります。 グレブが物理的にイノポリスにいるかどうかを考慮せずに「パスポートの利用可能性」のみを強制する単純なアプローチでは、理論的にはビザの準備ができていても申請が間に合わないスケジュールが作成されます。 

2 番目の微妙な問題は、同時実現可能性です。同じパスポートに割り当てられた 2 つのビザを注文し、後の申請が前のビザの返却時期とすべての旅行ギャップの両方が厳密に経過した後に行われるようにする必要があります。 どちらかの制約を無視すると、実際のカレンダー制約に対して検証された場合にのみスケジュールが失敗します。 

## アプローチ

 ブルートフォースの観点では、各旅行を最大 2 つのパスポートのいずれかに割り当てることから始まります。 それはすでに次のものを作成します$2^N$パーティション。 パーティションごとに、各パスポート内のビザ申請の順序を決定し、すべての制約を満たす申請日を選択する必要があります。 固定順序を想定したとしても、曜日の割り当ては依存関係によるスケジュールの問題となり、単純にすべての配置を試してみると、大きな曜日範囲にわたって組み合わせ爆発が発生します。 

重要な構造上の観察は、各パスポート内で重要なのはビザの絶対的な配置ではなく、ビザの順序だけであるということです。 注文が決まると、可能な限り最も早いスケジュールが貪欲に決定されます。グレブが自宅にいてパスポートが空く最も早い日に各ビザを申請してください。 旅行のギャップにより申請可能な日数が​​なくなるため、遅延が発生すると将来の制約を満たすことが難しくなるだけです。 

これにより、問題は、旅行を最大 2 つのシーケンスに分割する方法と、各シーケンスをどの順序で処理するかを決定することになります。 N は 22 にすぎないため、パスポート 1 に割り当てられたすべてのサブセットを列挙し、パスポート 2 の補数を導出し、その後、それぞれの側で有効な順序付けスケジュールを見つけようとします。 

パスポート内の固定順序の場合、旅行によって課される制約により、時間が経つにつれて実現可能性がシミュレーションの問題になります。 開始時間によって旅行を事前に並べ替え、ブロックされた間隔を常に飛び越えて、申請日を前向きに割り当てることができます。 

残りの微妙な点は、順序が重要であるということです。すべての順列が有効であるわけではありません。 ただし、N が小さいため、サブセットに対する動的プログラミングに依存できます。この場合、状態は、どの旅行がすでにスケジュールされているか、および各パスポートの現在の「時間位置」をエンコードします。 

DP は、最後に選択した特定の旅行で終わるサブセットをスケジュールできるかどうかを追跡し、出発前にビザ申請ができる場合にのみ、実行可能な次の旅行を更新します。

 ## アルゴリズムのチュートリアル

 各パスポートを独立してモデル化しますが、旅行のグローバルな割り当てを通じてそれらを結合します。 

1. パスポート 1 に割り当てられた旅行のすべてのサブセットを繰り返します。残りの旅行は自動的にパスポート 2 に属します。パスポートが 2 つしかないため、これが可能です。 
2. パスポートごとに、割り当てられた旅行を開始時刻で並べ替えます。 これは任意ではありません。旅行が早いほど、利用可能な申請日がより厳しく制限されるため、時系列順に処理することで貪欲なスケジュール設定が可能になります。 
3. パスポートごとに、その固定された順序でビザのスケジュールをシミュレーションします。 私たちは、Gleb が次のビザを申請できる最も早い日を表す現在の日ポインタを保持します。 
4. 旅行のスケジュールを立てるときは、選択した申請日が旅行間隔内にないことを確認する必要があります。 現在のポインタが旅行間隔内にある場合は、その旅行が終了した後の最初の日にジャンプします。 このステップでは、「Innopolis に存在する必要がある」という制約が適用されます。 
5. 申請日を選択したら、以前のビザの処理によりパスポートが忙しくなっていないことを確認します。 有効な場合は、パスポートの有効期限までその日を繰り上げます。 
6. 次に、この日を割り当て、申請日と処理時間にパスポートの空き時間を更新します。 
7. 両方のパスポートをシミュレートした後、すべての旅行のビザ完了時刻が出発日の厳密に前であることを確認します。 いずれかのトリップがこの条件を満たさない場合、そのサブセットは無効になります。 
8. すべての有効なサブセットのうち、最初のサブセットを出力し、保存された決定からスケジュールを再構築します。 

正しさは、解決策が存在する場合、固定割り当て内で各ビザの可能な限り早い有効な申請日を選択することが将来の実現可能性を決して妨げないという事実にかかっています。 それ以降の選択は、次の移動までに利用可能なスラックを減らすだけであり、制約は時間的に単調であるため、貪欲にアプリケーションを前進させるのは安全です。 

維持される不変条件は、パスポートに k 件のビザをスケジュールした後、旅行や処理の制約に違反することなく (k+1) 番目のビザを申請できる最も早い時刻をポインタが反映するということです。 これにより、有効なスケジュールが存在する場合、貪欲な構築によってスキップされることがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, p = map(int, input().split())
    trips = [tuple(map(int, input().split())) for _ in range(n)]

    # sort trips internally for stable processing, but we keep original indices
    indexed = [(i, s, l, t) for i, (s, l, t) in enumerate(trips)]

    # precompute travel intervals
    intervals = [(s, s + l - 1) for _, s, l, _ in indexed]

    def can_schedule(mask):
        # returns schedule if passport 1 gets subset mask, else None

        def simulate(group):
            # group: list of indices
            if not group:
                return True, [], 1, 1  # ok, schedule, time pointer, passport free time

            items = sorted(group, key=lambda x: trips[x][0])

            cur_time = 1
            free_time = 1
            schedule = {}

            for i in items:
                s, l, t = trips[i]
                # move time to be outside travel if needed
                if cur_time >= s and cur_time <= s + l - 1:
                    cur_time = s + l

                # passport must be free
                if cur_time < free_time:
                    cur_time = free_time

                # still must ensure not in trip
                if cur_time >= s and cur_time <= s + l - 1:
                    cur_time = s + l

                # assign
                schedule[i] = cur_time

                # update passport availability
                free_time = cur_time + t

            # verify feasibility: all visas ready before trip start
            for i in group:
                s, l, t = trips[i]
                if schedule[i] + t > s:
                    return False, None, None, None

            return True, schedule, cur_time, free_time

        group1 = [i for i in range(n) if (mask >> i) & 1]
        group2 = [i for i in range(n) if not ((mask >> i) & 1)]

        ok1, sch1, _, _ = simulate(group1)
        if not ok1:
            return None
        ok2, sch2, _, _ = simulate(group2)
        if not ok2:
            return None

        res = [None] * n
        for i in group1:
            res[i] = (1, sch1[i])
        for i in group2:
            res[i] = (2 if p == 2 else 1, sch2[i])

        return res

    for mask in range(1 << n):
        res = can_schedule(mask)
        if res is not None:
            print("YES")
            for i in range(n):
                print(res[i][0], res[i][1])
            return

    print("NO")

if __name__ == "__main__":
    solve()
```この実装は、ビットマスクを介したパスポートの割り当ての列挙に依存しています。 各マスクは個別にテストされ、各面が時系列に貪欲にシミュレートされます。 重要な実装の詳細は、繰り返される「タイム ジャンプ」ロジックです。つまり、現在の適用日が旅行間隔に入るたびに、旅行後の最初の日に繰り上げられます。 これにより、違法なアプリケーションの試みが行われないことが保証されます。 

もう 1 つの微妙な点は、パスポートの入手可能性と物理的な入手可能性を区別することです。 アルゴリズムは両方を独立して追跡し、2 つのうちの後者が常に次回の適用時間を支配します。 この分離がないと、スケジュール上、ビザの処理が重複して許可されてしまう可能性があります。

 ## 特殊なケース

 微妙な失敗例は、2 つの旅行が近づき、次の旅行が始まって初めてパスポートが無料になる場合に発生します。 その状況では、アルゴリズムは移動間隔内にアプリケーションをスケジュールしようとしてはなりません。 代わりに、直接ジャンプして通過する必要があります。 シミュレートされたポインター ロジックは、現在の日を最初の有効な非旅行日まで進めることで、これを明示的に強制します。 

もう 1 つの特殊なケースは、ビザの処理が旅行開始日ちょうどに終了する場合に発生します。 パスポートは午前中に入手可能でなければならないため、モデルが一日が始まる前の完了をノンブロッキングとして扱う場合にのみ平等が受け入れられます。 実装はチェックすることでこれを尊重します`schedule[i] + t <= s`実現可能条件として、出発前に厳密な準備を整えます。
