 ## 解決策
 ## 問題の理解

 奇数長の単一の配列が与えられます。 このプロセスは長さのちょうど半分を切り捨てて実行され、各ラウンドでは、配列内のどこかで 1 つの隣接するスワップを許可した後、常に最初の 2 つの要素が削除されます。 

スワップは位置に制限はありませんが、ラウンドごとに 1 つの隣接する交換に制限されます。 その後、最初の 2 つの要素は完全に削除され、残りのサフィックスが次のラウンドの新しい配列になります。 これは、要素が 1 つだけ残るまで続きます。タスクは、スワップを最適に選択して、最後の生き残りを最大化することです。 

主な問題点は、スワップの選択はグローバルですが、実際にはローカルであり、削除は常に先頭で固定されることです。 これにより、削除が繰り返されることで要素がどれだけ早く前面に向かってドリフトするかということと、ラウンドごとに最大 1 回のスワップを使用してそのドリフトをどれだけ遅らせるか加速できるかの間に緊張が生じます。 

この制約により、n は 2 × 10^5 まで許可され、考えられるすべてのスワップ決定を試行したり、配列の考えられるすべての状態を追跡したりするシミュレーションは除外されます。 ラウンドごとまたはポジションごとの選択肢に応じて分岐するソリューションは、指数関数的または少なくとも二次関数的に爆発します。 

単純な推論による微妙な失敗例は、最大の要素を常に前面に向かって泡立てることが最善の戦略であると仮定した場合に現れます。 フロントはまさにスワップ直後に削除が発生する場所であるため、その直感は崩れます。 たとえば、[1, 100, 2, 3, 4] のような小さな配列では、削除が無条件であるため、最初の 2 つの位置に早く引っかかった場合、繰り返し 100 を前方に押し出すと失敗する可能性があります。 

誤解を招きやすいもう 1 つのケースは、答えが常にグローバル最大値であると想定していることです。 [10, 6, 2, 1, 5, 3, 4] では、最大値は 10 ですが、スワップに関係なく、削除プロセスの早い段階で削除されるため、これが存続することは不可能です。 

## アプローチ

 ブルート フォース ビューでは、すべてのラウンドをシミュレートし、各ラウンドで最初の 2 つの要素を削除する前に、可能な隣接するスワップをすべて試行します。 1 つの配列のみを追跡する場合でも、スワップ位置の選択によりラウンドごとに O(n) 個の分岐が作成され、O(n) 個のラウンドが存在するため、可能なシーケンスの数は指数関数的に増加します。 ラウンドごとにすべてのスワップ ポジションを試す単純なシミュレーションでも、最適な決定論的解釈ではすでに O(n^2) 回の演算が必要ですが、これは n が 2 × 10^5 までの場合には遅すぎます。 

重要な洞察は、このプロセスは実際にはローカルの再配置能力に関するものではなく、固定された削除スケジュールに抗して生き残るためのものであるということです。 各ラウンドでは、先頭からちょうど 2 つの要素が削除されるため、各要素の運命は、削除される前に最初の 2 つの位置にどれだけ長く流れ込むことを回避できるかによって決まります。 ラウンドごとに 1 回のスワップでは、要素の有効位置はラウンドごとに最大 1 ステップしか移動できませんが、削除ではすべてがラウンドごとに 2 ステップ左に移動します。 

これにより線形ドリフト モデルが作成されます。各要素は削除圧力により 2 つずつ左に移動しますが、スワップを使用するとラウンドごとに最大 1 つだけ右に移動できます。 最終的な効果は、各要素がその死を制限された量だけ「遅らせる」ことができ、この制限はその初期位置のみに依存し、他の要素の値には依存しないということです。 これにより、問題はどのインデックスが最終ラウンドまで存続できるかを特定することに分解されます。 

この視点が確立されると、問題はすべてのラウンドで生き残ることができるポジションのサフィックスを特定し、それらの中で最大値を取得することに帰着します。

 | ポジション生存分析 | O(n) | O(1) おまけ | 承認済み |

 ## アルゴリズムのチュートリアル

 ここで、生存推論を直接計算に変換します。 

### アルゴリズムのチュートリアル

1. (n − 1) / 2 ラウンドがあり、各ラウンドで先頭からちょうど 2 つの要素が削除されるため、プロセスでは 1 つを除くすべての要素が削除されることに注目してください。 
2. 最初に位置 i で要素を追跡します。 スワップなしで k 回ラウンドした後、削除により 2k 位置だけ左にシフトするため、その有効位置は i − 2k になります。 
3. 修正メカニズムとしてラウンドごとに 1 つのスワップを使用します。 各ラウンドで最大 1 つの隣接スワップが許可されるため、k ラウンドにわたって、要素は削除ドリフトに対して最大 k 位置だけ右にプッシュされます。 
4. 両方の効果を組み合わせます。 k 回のラウンドの後、最初に i にある要素の最良の有効位置は i − 2k + k となり、これは i − k に単純化されます。 
5. 要素が最終ラウンド k = (n − 1) / 2 まで存続するには、その時点での有効位置が正のままでなければなりません。 これにより、条件 i − (n − 1) / 2 > 0 が得られます。 
6. これは i > (n − 1) / 2 に単純化されます。つまり、配列の後半の要素のみが最後まで生き残ることができることを意味します。 
したがって、最終的な答えは、1 から始まるインデックスの (n + 1) / 2 から n までのインデックスの最大値になります。 

### なぜ効果があるのか

 削除プロセスでは、ラウンドごとに 2 つの要素が前方から決定的に削除され、すべての要素に対して厳格な左方向のドリフトが作成されます。 このアルゴリズムによって提供される唯一の制御は、単一の隣接スワップを介した、ラウンドごとに最大 1 つのポジションの限定された右方向の修正です。 どちらの効果もラウンド数に応じて線形にスケールするため、要素の正味変位も線形であり、その開始インデックスによって完全に決定されます。 

これは、生存は、配列の奥深くにある要素の任意のペア間の相対的な順序の変更には影響されず、最終ラウンドの前に要素が削除ゾーンに入ることを回避できるかどうかによってのみ影響されることを意味します。 要素が前半で開始されると、その要素を可能な限り右方向に修正しても、繰り返しの削除に対抗するには不十分であるため、最終的には削除する必要があります。 後半の要素には、最後まで生き残るために十分な期間、削除ウィンドウの外に留まるのに十分な余裕があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    start = n // 2  # 0-based index of (n+1)/2 in 1-based
    print(max(a[start:]))

if __name__ == "__main__":
    solve()
```実装では、派生した生存境界を直接適用します。 唯一の微妙な点はインデックス付けです。0 ベースのインデックス付けでは、生き残ったセグメントは n // 2 から始まります。 

残りは接尾辞に対する単純な最大値です。 スワップのすべての動的な動作はすでに生存格差に吸収されているため、シミュレーションは必要ありません。 

## 実用的な例

 ### 例 1

 入力:```

```私たちは生き残った領域を追跡します。

 これは、最適な戦略ではグローバル最大値は考慮せず、構造的にどの要素が削除プロセスでも存続できるかのみを考慮していることが確認されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 接尾辞の最大値を計算する単一パス |
 | スペース | お(1) | 入力配列ストレージのみが使用されます。 

この解は、線形スキャンを 1 回だけ実行し、スワップ削除プロセスのシミュレーションを実行しないため、n が 2 × 10^5 までの制限内に簡単に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n = int(input())
    a = list(map(int, input().split()))
    start = n // 2
    return str(max(a[start:]))

# provided sample
assert run("7\n10 6 2 1 5 3 4\n") == "5"

# minimum size
assert run("1\n42\n") == "42"

# simple increasing
assert run("5\n1 2 3 4 5\n") == "5"

# all equal
assert run("5\n7 7 7 7 7\n") == "7"

# maximum at front but not reachable
assert run("5\n100 1 1 1 1\n") == "1"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | n=1 の単一要素 | 42 | 自明な基本ケース |
 | 配列を増加する | 5 | 接尾辞の優位性 |
 | すべて等しい | 7 | 構造的な偏りがない |
 | 大きなフロント最大値 | 1 | 初期の要素は生き残ることができません。 

## 特殊なケース

 重要なエッジ ケースは、最大の要素が配列の前半に位置する場合です。 このような状況では、スワップでいつでも救済できると考えたくなりますが、繰り返しの削除によって生じるドリフトが、限られたスワップ予算を圧倒してしまいます。 

入力の場合:```
5
100 1 2 3 4
```アルゴリズムはサフィックス [2, 3, 4] を選択し、4 を返します。要素 100 は位置 1 から始まりますが、ラウンドごとに先頭から 2 つの要素が削除され、ラウンドごとに 1 回のスワップでは、プロセスの初期段階で一貫して削除ゾーン内にあることを補償できません。 

もう 1 つの特殊なケースは、次のような均一な配列です。```
5
7 7 7 7 7
```ここでは、どの戦略でも同じ最終値が得られます。 接尾辞ルールは引き続き適用され、アルゴリズムは最後の 3 つの要素の最大値を取得して 7 を正しく返します。
