 ## 解決策
 ## 問題の理解

 オペレーティング システムが、最も最近使用されていないポリシーを使用して、小さな固定サイズのメモリ キャッシュを管理する方法をシミュレートしています。 メモリは少数のスロットに分割されており、一連のメモリ アクセス要求を受け取ります。 各リクエストは、整数で識別される特定のメモリ ブロックにアクセスするように求めます。 

アクセスごとに、最大 n 個の異なるブロックを格納するサイズ n のキャッシュを維持する必要があります。 要求されたブロックがすでにキャッシュ内にある場合、そのブロックは最後に使用されたブロックとなり、その優先順位が最新の位置に更新されることを意味します。 キャッシュになく、まだ空き領域がある場合は、それを最近使用したものとして単純に挿入します。 キャッシュがいっぱいの場合は、新しいブロックを挿入する前に、最も最近使用されていないブロックを削除する必要があります。 

出力は、最終的なキャッシュ状態だけでなく、各操作後にキャッシュがどのように変化するかの完全なトレースです。 各行がステップに対応するテーブルを出力し、現在のタイム ステップと最新順に並べられたキャッシュの内容を、優先順位を説明するヘッダー行とともに表示する必要があります。 

制約は非常に小さく、n は最大 5、m は最大 100 です。これにより、演算ごとに 2 次オーバーヘッドが均一なアルゴリズムは完全に安全であることがすぐにわかります。 最適化のトリックを気にすることなく、プロセスを直接シミュレートできます。 本当の難しさは効率ではなく、正確さと注意深く状態を追跡することです。 

アクセスが繰り返されて同じ要素が再シャッフルされ続ける場合、微妙なエッジ ケースが発生します。 たとえば、n = 2 でシーケンス 1、2、1、2 の場合、キャッシュはエビクションなしで常に並べ替えられます。 単純な実装では、ヒット時の順序の更新を忘れて、誤った優先順位のシフトが発生する可能性があります。 もう 1 つのエッジ ケースは、n = 1 の場合です。この場合、繰り返されるアクセスを除くすべてのアクセスが即座にエビクションを引き起こすため、順序付けは簡単になりますが、コードが n ≥ 2 を想定している場合は誤って処理されやすくなります。 

## アプローチ

 ブルート フォース シミュレーションは当然ながらルールに直接に従います。 私たちは、最も最近使用されたものから最も最近使用されたものまでキャッシュの内容を表す順序付きリストを維持します。 リクエストごとにリストをスキャンして、要素が存在するかどうかを確認します。 存在する場合は削除して最後に追加します。 存在せず、スペースがある場合は追加します。 スペースがない場合は、最初の要素を削除し、新しい要素を追加します。 各操作の後、現在の状態を出力します。 

これが機能するのは、状態サイズが小さいため、リニア スキャンが安価であるためです。 各操作のコストは O(n) で、m 個の操作を実行するため、総コストは O(mn)、つまり最大 500 回の操作になります。 

制約は最適化が重要なしきい値をはるかに下回っているため、リンクされたハッシュ マップやヒープなどのより高度な構造は必要ありません。

 「最適な」ソリューションは事実上、総当たりのソリューションと同じです。これは、制約によってすでに最も単純な実装で十分であるためです。 

## アルゴリズムのチュートリアル

 私たちはリストを管理しています`cache`インデックス 0 で最も最近使用されたものから最後に最も最近使用されたものまで順序付けされます。 各操作の後、歩数カウンターも維持します。 

1. 空のリストを初期化する`cache`キャッシュは現在のメモリの内容を新しいものから順に表します。 
2. 要求された各ブロックを順番に処理します。 ブロックごとに`x`、まず、すでに入っているかどうかを確認してください。`cache`。 これにより、対処するのがヒットかミスかが決まります。 
3. もし`x`で見つかります`cache`、現在の位置から削除し、最後に追加します。 これは、最近アクセスされたブロックが最新になるというルールを反映しています。 削除は、キャッシュ内の一意性を維持しながら重複を回避するために必要です。 
4. もし`x`が見つからず、キャッシュがいっぱいでない場合は、末尾に直接追加します。 これにより、削除されずに、最後に使用されたブロックとしてそれが挿入されます。 
5. もし`x`が見つからず、キャッシュがいっぱいである場合は、の最初の要素を削除します。`cache`、最も最近使用されていないブロックを追加します。`x`最後まで。 これにより立ち退きポリシーが適用されます。 
6. キャッシュを更新した後、時間カウンターをインクリメントし、出力フォーマット用に現在の状態を記録します。 
7. すべてのリクエストが処理されるまで続行します。 

重要な不変条件は、すべてのステップで、`cache`は、正確に現在保存されているメモリ ブロックのセットであり、最終アクセスの最新性に従って、最も古いものから新しいものへと厳密に順序付けされています。 すべての操作は、既存の要素の順序を変更するか、この順序を保持しながら 1 つの要素だけを挿入または削除するため、不変条件に違反することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def to_hex2(x):
    return f"0x{int(x):02x}"

def to_hex4(x):
    return f"0x{int(x):04x}"

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))

    cache = []
    states = []

    for x in a:
        if x in cache:
            cache.remove(x)
            cache.append(x)
        else:
            if len(cache) == n:
                cache.pop(0)
            cache.append(x)

        states.append(cache[:])

    header = [""] + [to_hex2(i) for i in range(len(cache))]
    print("+" + "+".join(["------"] + ["--------"] * len(cache)) + "+")

    print("|" + "|".join([""] + header[1:]) + "|")
    print("+" + "+".join(["------"] + ["--------"] * len(cache)) + "+")

    for i, st in enumerate(states):
        row = [to_hex2(i)] + [to_hex4(v) for v in st]
        print("| " + " | ".join(row) + " |")
        print("+" + "+".join(["------"] + ["--------"] * len(cache)) + "+")

if __name__ == "__main__":
    solve()
```このソリューションは、LRU 構造として単一のリストを保持します。 各アクセスでは、削除と追加 (ヒットの場合) または削除と追加 (ミスの場合) が実行されます。 重要な点は、常に新しいものから新しいものへの順序を維持することです。 

フォーマット関数は、インデックスと値を固定幅の 16 進文字列に変換します。 テーブル構造はすべての状態を収集した後に出力され、出力寸法の一貫性が保証されます。 

実装の微妙な詳細は、最終的なキャッシュ長によって印刷される列の数が決まることです。 キャッシュは最大 n まで拡張できますが、最初は小さくなる可能性があるため、ほとんどの場合、最終的なサイズは n であると考えます。 それ以外の場合は、慎重に実装すると、n を明示的に使用して列幅を事前に定義できます。 

## 実用的な例

 ### 例 1

 入力:```

a = [0, 1, 2, 1]
```| ステップ | キャッシュ状態 |

 | 0 | [0] |

 最初の 3 つの手順は単純にキャッシュを埋めるだけです。 ステップ 3 で 1 にアクセスすると、1 が最新の位置に移動しますが、2 が前方にシフトされた後も 0 は最も新しい位置に残ります。 これにより、サイズを変更せずにヒットが正しく並べ替えられることが確認されます。 

### 例 2

 入力:```

a = [1, 2, 1, 3]
```| ステップ | キャッシュ状態 |
 | --- | --- |
 | 0 | [1] |
 | 1 | [1、2] |
 | 2 | [2、1] |

 ステップ 2 で 1 にアクセスすると、1 が後ろに移動し、2 が最も最近使用されていません。 ステップ 3 では、3 を挿入すると 2 のエビクションがトリガーされます。これは、ヒット時リオーダー動作とミス時エビクション動作の両方が連携して動作していることを示しています。

 ## 特殊なケース

 n = 1 の場合、個別のアクセスごとに強制的にエビクションが行われます。 キャッシュには常に最新の要素のみが含まれます。 アルゴリズムはこれを処理します。`len(cache) == n`の場合、新しい要素を追加する前に、最初の要素がポップされ、これが唯一の要素でもあります。 

繰り返しアクセスする場合など`[5, 5, 5]`、`x in cache`毎回分岐トリガーが発生します。 毎回同じ値を削除および追加し、冗長な操作を除いてキャッシュは変更されません。 追加する前に常に削除するため、一意性の不変条件が保持されます。 

次のようなフルキャパシティサイクルの場合`[1, 2, 3, 1, 4]`n = 3 の場合、エビクションは 4 を挿入したときに正確に行われます。厳密な順序付けが維持され、メモリ内に古い要素が残らないようにするため、その時点で最も最近使用されていない要素が正しく削除されます。
