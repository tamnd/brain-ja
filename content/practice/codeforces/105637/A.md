 ## 解決策
 ## 問題の理解

 価格が時間の経過とともにどのように変化するかを示す簡単なモデルが与えられています。 初日の価格を表す初期値があり、その後毎日、前日と比較して価格がどれだけ変化したかが与えられます。 各変更は累積的に適用されるため、i 日目の値は、i-1 日目の値に i-1 番目の変更を加えたものになります。 

タスクは、毎日の変更がすべて適用された後の最終値、つまり最終日の値を計算することです。 

この言い方は「時間プロセス」のように聞こえますが、その構造は純粋に線形の蓄積です。 すべての更新は追加的で独立しているため、実際には変更配列に対するプレフィックスの合計を再構築しているだけです。 

入力サイズは小さく、最大でも 1000 日です。 このことから、一般的な制限の下では 10^3 の演算は無視できるため、単純な O(n) スキャンでも十分すぎることがすぐにわかります。 線形時間を超えるソリューションは不必要なオーバーヘッドになります。 

いくつかの特殊なケースについては、覚えておく価値があります。 

1 日しかない場合は、変更を適用する必要がないため、答えは単なる初期値になります。 常に少なくとも 1 つの変更を読み取ろうとする単純な実装は、ここで失敗します。 

すべての変更がマイナスの場合でも、最終価格は問題の保証に従ってプラスのままである可​​能性がありますが、中間実装で誤って値をゼロに固定してしまうと (シミュレーション スタイルの考え方でよくある間違いです)、誤った結果が生成されます。 

変更にゼロが含まれている場合、数学的には特別なことは何も起こりませんが、無関係であるという仮定の下でゼロのエントリをスキップする実装は、正確性を損なうことになります。 

## アプローチ

 強引な解釈では、プロセスを毎日シミュレートすることになります。 最初の価格から開始して各変更を繰り返し、毎回現在の値を更新します。 毎日一定時間の更新が行われるため、これはすでに O(n) 時間です。 隠れた状態、分岐、組み合わせ爆発はありません。 

さらに「最適化」しようとすると、構造の要点を逸脱してしまいます。 重要な観察は、最終的な値はすべての変更の合計にのみ依存し、順序や中間状態には依存しないということです。 繰り返される更新は、初期値とすべての日次差の合計という 1 つの算術式にまとめられます。 

したがって、最適なアプローチとは、異なるアルゴリズム手法ではなく、ここではシミュレーションと直接加算が同一であるという認識です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ステップバイステップのシミュレーション | O(n) | お(1) | 承認済み |
 | 変更の合計を直接 | O(n) | お(1) | 承認済み |

 実際にはどちらも事実上同じ実装です。 

## アルゴリズムのチュートリアル

 1. 日数 n を読み取ります。 これにより、適用される更新の数が決まります。 
2. 初値を読み取ります。 これは変更前の開始状態です。 
3. この初期価格で可変電流を初期化します。 
4. 次の n-1 行ごとに、毎日の変化を読み取​​り、それを現在の値に追加します。 それぞれの追加は、時間を 1 日進めることに正確に対応します。 
5. すべての変更を処理した後、現在の価格を最終価格として出力します。 

重要な決定は、値の完全なシーケンスを保存する必要がないということです。 各中間価格は一時的な状態としてのみ存在し、すべての遷移は加算的なものであるため、現在の値のみを維持することで、必要な情報がすべて保持されます。 

### なぜ効果があるのか

 このプロセスは、value[i] = value[i−1] + delta[i] という形式の繰り返しを定義します。 この繰り返しを繰り返し展開すると、value[n] が初期値とすべてのデルタの合計に等しいことがわかります。 加算は結合であるため、演算のグループ化は重要ではなく、一度値を提供する以外に中間ステップが最終結果に影響を与えることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    cur = int(input())
    
    for _ in range(n - 1):
        cur += int(input())
    
    print(cur)

if __name__ == "__main__":
    solve()
```このコードは、ウォークスルーで説明されている繰り返しを直接実装します。 変数`cur`は進化する価格を表します。 各入力行はすぐに適用されるため、配列全体の不必要な格納が回避されます。 

よくある実装上の間違いは、すべての値をリストに保存し、後で再計算しようとすることです。 それは不必要ですが、ここではまだ安全です。 さらに深刻な間違いは、アキュムレータの初期化が間違っていることです。たとえば、指定された初期価格ではなくゼロから開始し、結果全体がシフトします。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 毎日の変更は 1 回ずつ処理されます。 
| スペース | お(1) | アキュムレータ変数は 1 つだけ維持されます。 

制約では最大 1000 日が許容されるため、単一の線形パスは十分に制限内に収まります。 境界がはるかに大きい場合でも、同じアプローチはネストされた計算を回避するため、効率的に拡張できます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    n = int(input())
    cur = int(input())
    for _ in range(n - 1):
        cur += int(input())
    return str(cur)

# provided samples
assert run("2\n11\n68\n") == "79"
assert run("4\n110\n-5\n0\n27\n") == "132"

# custom cases
assert run("1\n5\n") == "5", "single day no changes"
assert run("3\n10\n-3\n-7\n") == "0", "all negative changes"
assert run("5\n1\n1\n1\n1\n1\n") == "5", "uniform increments"
assert run("2\n1000000\n-1\n") == "999999", "boundary decrement"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1日限定 | 初期値 | 変更処理なし |
 | すべて否定的 | 0 | 正確性が低下します。 
| 繰り返し +1 | 線形累積 | 繰り返しの追加 |
 | 大きな値 | 999999 | 境界算術の正確性 |

 ## 特殊なケース

 1 日分の入力の場合、アルゴリズムは初期値を読み取り、ループに入らないため、出力はまさにその値になります。 アキュムレータは入力からすぐに設定されるため、初期化されていない更新が発生するリスクはありません。 

負のみのシーケンスの場合、各減算は累計に直接適用されます。 このアルゴリズムはどの時点でも正であることを想定していないため、クランプやオーバーフローの問題を引き起こすことなく、自然に減少を追跡します。 

変更がゼロの場合、各反復で実行されます。`cur += 0`の状態をそのまま残します。 ゼロ値を除外する条件はないため、ゼロ値は均一累積プロセスに正しく含まれます。
