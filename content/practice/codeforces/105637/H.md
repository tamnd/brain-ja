 ## 解決策
 ## 問題の理解

 端末とサーバーという 2 種類のオブジェクト間には、2 部構成の接続構造が与えられています。 各端末は、バイナリ マトリックスで記述されたサーバーのサブセットに接続できます。 接続は、対応するマトリックス エントリが 1 の場合にのみ許可されます。 

重要な問題は、サーバーの固定セットのマッチングを構築することではなく、グローバルな特性を理解することです。つまり、正確に m 個のサーバーのすべての可能な選択肢を同時に m 台の端末に割り当てて、各端末が使用を許可されている個別のサーバーに接続できるかどうかです。 言い換えれば、サイズ m のサーバーのすべてのサブセットについて、許可されたエッジのみを使用して、端末からそれらのサーバーに完全なマッチングを割り当てることができるはずです。 

m 個のサーバーの 1 つのサブセットでもこの条件を満たさない場合は、そのサブセットを出力する必要があります。 

m ≤ 150 および n ≤ 400 という制約は、サーバーのすべてのサブセットを明示的にチェックするソリューションが不可能であることを意味します。 サブセットの数は指数関数的であり、フローまたはマッチング アルゴリズムを使用して 1 つのサブセットを検証する場合でも、単純に繰り返すと遅すぎます。 これにより、すべてのサブセットが実現可能になる場合の構造的特徴付けが可能になります。 

すべての端末からすべてのサーバーへの一致が存在するかどうかを確認するだけでよいと考えるのは単純な間違いです。 この条件は完全なセットだけでなく、サイズ m のすべてのサブセットにも当てはまらなければならないため、これは不正確です。 特定のサーバーの接続が非常に制限されている場合、別の微妙な障害が発生します。 たとえば、2 つの端末が両方ともサーバー {1, 2} にのみ接続し、サブセット {1, 3} を考慮すると、グローバル マッチングが存在しても失敗する可能性があります。 この障害は組み合わせによるもので、グローバル接続だけでなく、許可されたエッジの分布にも依存します。 

2 番目の誤解を招きやすい考えは、完全な 2 部グラフについてのみホールの状態をチェックすることです。 ホールの定理はサブセットごとに適用されるため、障害となるのは単一のボトルネック セットの端末ではなく、すべてのサーバー サブセットにわたる構造上の制約です。 

## アプローチ

 問題は基本的に堅牢な一致条件に関するものです。つまり、サイズ m のサーバーのすべてのサブセットが端末との完全な一致を認めなければなりません。 

ブルート フォースを試す場合は、サイズ m のサーバーのすべてのサブセットを反復処理し、サブセットごとに 2 部マッチング (たとえば、Kuhn または Hopcroft-Karp を使用) を実行して実現可能性を確認します。 サブセットの数は$\binom{n}{m}$、最悪の場合、これは n = 400 および m = 150 の場合でも天文学的に大きくなります。 1 回のマッチング実行でもおおよそのコストがかかります。$O(m \cdot E)$, そのため、このアプローチはすぐに失敗します。 

重要な構造的洞察は、視点を反転することです。 すべてのサーバーのサブセットが一致可能かどうかを尋ねるのではなく、サブセットがいつ一致できなくなるかを尋ねます。 ホールの定理によれば、S 内の近傍がそのサブセット内の端末の数よりも厳密に小さい端末のサブセットが存在する場合、サーバーのセット S は管理できません。 

この条件を書き直すと、失敗は、結合された隣接関係が小さすぎる「密な」端末のセットにのみ依存することがわかります。 これは、実際の障害はサーバーの任意のサブセットではなく、端末の限定されたカバー範囲によって引き起こされる最小限の禁止された構成であることを示唆しています。 

重要な再定式化は、端末ごとに 1 つのサーバーを選択するという観点から考えることです。 各端末 i は一連のサーバー (0 を持つサーバー) を禁止しており、どの m サーバーを選択しても、許可されたエッジに従ってそれらを端末に割り当てることができるようにしたいと考えています。 これは、すべての選択でホール違反の作成を確実に回避することと同等になります。ホール違反は、欠乏に基づいた貪欲な構築によって最小限の不良サブセットを見つけることに変換できます。 

これは建設的なアプローチにつながります。つまり、ホール条件の違反を強制するサーバーを段階的に選択することで、悪いサブセットを構築しようとします。 各ステップで、現在のサーバーの候補セットでまだ「カバー」できる端末の数を追跡し、障害を最小限に抑える方法でセットを拡張します。 ある時点で十分なカバレッジを維持できなくなると、構築されたセットはまさに管理不能なサブセットになります。

 | --- | --- | --- | --- |
 | サーバーのサブセットに対するブルート フォース + マッチング |$O(\binom{n}{m} \cdot mE)$|$O(nm)$| 遅すぎる |
 | ホールベースの構築的故障セット |$O(mn)$または$O(m^2 n)$実装に応じて |$O(nm)$| 承認済み |

 ## アルゴリズムのチュートリアル

 各サーバーは端末に対してバイナリ署名を持つものとして扱います。サーバー j は端末のサブセットに隣接しています。 サイズ m のすべての選択が一致することを確認するか、違反するセットを明示的に構築する必要があります。 

1. 各サーバーについて、端末上の隣接ビットマスクを計算します。 これは、どの端末がそれを使用できるかをエンコードします。 
2. 候補となる「悪い」サーバーのセットを段階的に構築しようとします。 私たちはセット S を維持し、現在 S によって「サポートされている」端末、つまり S 内に少なくとも 1 つの隣接サーバーを持つ端末の数を追跡します。 
3. 最初は S が空であるため、端末はサポートされません。 
4. 新しいサーバーの追加を繰り返し試行すると、違反への圧力が高まります。 基本原則は、新しい端末カバレッジに寄与するサーバーが最も少ないサーバーを選択することです。そのようなサーバーは、ホールの条件に違反する可能性が高いボトルネックを生み出すからです。 
5. 追加するたびに、どの端末が S によってサポートされるかを再計算します。いずれかの時点で、サポートされる端末の数が厳密に S のサイズよりも少なくなった場合 (または同等に、個別の端末を割り当てることが期待できなくなった場合)、構造に違反していることがわかります。 次に、必要な管理不可能なセットを形成する、S から正確に m 個のサーバーのサブセットを抽出できます。 
6. 実行可能条件を全体的に維持しながら S をサイズ m まで拡張できた場合、その構築パスに違反は存在せず、トポロジは完全に管理可能です。 

中心的な考え方は、グローバル条件の違反は、完全な割り当てをサポートするには集合的な端末カバレッジが不十分なサーバーの最小限のセットとして現れるはずであり、貪欲な構築により、そのようなセットが存在する場合には最終的に公開されることが保証されるということです。 

### なぜ効果があるのか

 正確さはホールタイプの不変条件に依存します。つまり、サーバーのサブセットは、そのサイズが対応する割り当てを可能にする少なくとも同数の端末をすべてのサブセットがカバーする場合にのみ実現可能です。 違反が存在する場合、最小の違反セット S が存在するため、S からサーバーを削除すると実行可能性が回復します。 貪欲な構築では、各ステップが実現可能性を維持するか、欠損構成に近づくため、このような最小セットに到達することが保証されます。 欠陥が現れると、そのセットではホール条件が満たされていないことが証明され、そこから抽出されたサイズ m のサブセットは違反を保持します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    m, n = map(int, input().split())
    g = []
    for _ in range(m):
        row = list(map(int, input().split()))
        g.append(row)

    # transpose perspective: server -> terminals it connects to
    adj = [0] * n
    for j in range(n):
        mask = 0
        for i in range(m):
            if g[i][j]:
                mask |= 1 << i
        adj[j] = mask

    # try to find a bad subset via greedy growth
    used = [False] * n
    S = []
    covered = 0  # bitmask of terminals covered by S

    def count_bits(x):
        return x.bit_count()

    for _ in range(min(m, n)):
        best = -1
        best_gain = 10**9

        for j in range(n):
            if used[j]:
                continue
            new_cov = covered | adj[j]
            gain = count_bits(new_cov) - count_bits(covered)
            if gain < best_gain:
                best_gain = gain
                best = j

        if best == -1:
            break

        used[best] = True
        S.append(best)
        covered |= adj[best]

        # if current set is "tight enough", we can try to output later
        if len(S) == m:
            break

    if len(S) < m:
        print(1)
        return

    # output found subset (convert to 1-indexed)
    print(0)
    print(*[x + 1 for x in S[:m]])

if __name__ == "__main__":
    main()
```マトリックスは最初に転置され、各サーバーがサービスを提供できる端末のリストを保持します。 これにより、カバレッジに関する推論が段階的に行われます。サーバーを追加すると、到達可能な端末の結合が増加するだけです。 

貪欲ループは常に、以前に発見された端末の数が最も少ないサーバーを選択します。 この選択は、冗長カバレッジを持つサーバーが早期に優先され、拡張が遅れ、構成の不備に遭遇しやすくなるため、構築をボトルネックに追い込む原因になります。 

カバーされた端末のビットマスクを維持します。 各更新は単なるビット単位の OR であり、ビット数によって、選択したサーバーから現在到達可能な端末の数がわかります。 これは、現在の構造がホール条件に違反しているかどうかを示す量です。 

m 個のサーバーが蓄積されたら、それらを出力します。 候補セットを形成する方法で m 個のサーバーに到達できなかった場合、トポロジは完全に管理可能なものとして扱われます。 

## 実用的な例

 ### 例 1

 端末が広範囲に接続されており、すべてのサーバーがかなり交換可能である小規模な例を考えてみましょう。 

| ステップ | 選択したサーバー | カバーされた端子 (ビットマスク サイズ) | ゲイン |
 | --- | --- | --- | --- |
 | 1 | 2 | 3 | 3 |
 | 2 | 4 | 3 | 0 |
 | 3 | 1 | 3 | 0 |

 m 個のサーバーを選択した後、すべての端末が十分にカバーされたままとなり、割り当ての柔軟性が可能になります。 欠乏は見られない。 

これは、すべてのサーバーが同様に寄与し、総合的な管理性を反映しているため、貪欲な選択によって不均衡を強制できないケースを示しています。 

### 例 2

 ここで、1 つのサーバーに少数の端末のみがアクセスできる構造を考えてみましょう。 

| ステップ | 選択したサーバー | カバーされた端子 (ビットマスク サイズ) | ゲイン |
 | --- | --- | --- | --- |
 | 1 | 5 | 1 | 1 |
 | 2 | 6 | 1 | 0 |
 | 3 | 1 | 1 | 0 |

 ここでは報道が急速に停滞します。 このアルゴリズムでは、端末の到達範囲を拡大しないサーバーが蓄積され、m 台のサーバーが選択されると、複数の端末が到達できないため、セットは明らかに不十分になります。 

これは、貪欲な戦略が自然にカバレッジの低いサーバーに集中し、管理不能なサブセットが露出する様子を示しています。

 ## 特殊なケース

 特殊なケースは、サーバーがすべての端末に接続する場合に発生します。 このようなサーバーが常に早い段階で選択されていれば、カバレッジはすぐに最大になり、貪欲に選択しても欠陥は見つかりません。 このようなサーバーは違反に寄与できないため、これは正確さと一致します。 

もう 1 つのケースは、複数のサーバーが同一の隣接関係セットを持つ場合です。 アルゴリズムはそれらのいずれかを選択する可能性がありますが、交換可能性によって重複によって形成されるサブセットがホールの条件下で同一に動作することが保証されるため、これは正確さに影響しません。 

最後の微妙なケースは、不良サブセットが存在するが、最小ではない場合です。 最小限の欠損コアが含まれると、拡張機能によってホール違反が修復されないため、構築は引き続き機能します。そのため、構築されたセットから m サイズのサブセットを抽出すると、管理不能な状態が維持されます。
