 ## 解決策
 ## 問題の理解

 スコアボードのいくつかのスクリーンショットが提供されます。各スクリーンショットには、ある時点での同じチームのセットのスコアが記録されています。 各スクリーンショットは長さの配列です$K$、そして$i$-th の値はチームのスコアを表します$i$その瞬間。 

目標は、時間の経過とともにすべてのチームのスコアが決して減らないように、すべてのスクリーンショットを単一の時系列順に配置できるかどうかを決定することです。 言い換えれば、あるスクリーンショットが別のスクリーンショットよりも前にある場合、すべてのチームのスコアは後のスクリーンショットのスコア以下でなければなりません。 

出力は数値ではなく、スクリーンショットの有効な順序、または条件が存在する場合は条件を満たす任意の順序です。 

この制約は、最大で多数のスクリーンショットとチームを扱うことを意味するため、スクリーンショットのすべてのペアを直接比較するソリューションには、スクリーンショットの数が二次関数的に動作する危険性があります。 各比較自体にはすべてのチームのスキャンが含まれるため、両方の次元が大きい場合、単純なペアごとのチェックは遅くなりすぎます。 これにより、明示的なペアごとの互換性チェックを回避し、代わりにグローバルな順序付けルールを導出する戦略に向かうことになります。 

2 つのスクリーンショットがすべてのチームで同一である場合、微妙なエッジ ケースが発生します。 この場合、どちらの順序も有効ですが、単純な順序付けルールによって矛盾が生じてはなりません。 スクリーンショットが部分的に比較できる場合、別のエッジ ケースが発生します。たとえば、一部のチームではあるが、すべてのチームでは、あるスクリーンショットが他のチームを圧倒する可能性があり、単一の集計値による単純な並べ替えが壊れる可能性があります。 

## アプローチ

 この強引なアイデアは、スクリーンショットのすべてのペア間の順序の制約を理解しようとすることから始まります。 スクリーンショット 2 枚の場合$A$そして$B$かどうかを確認できます。$A$前に来ることができます$B$すべてのチームでそれを確認することで$i$、$A_i \le B_i$。 これが当てはまるなら、$A$先行することが許される$B$。 そうでない場合は、$B$先行する必要があります$A$。 これにより、各スクリーンショットがノードであり、エッジが強制的な順序付け制約を表す有向グラフが自然に形成されます。 

このグラフが構築されると、タスクはすべてのエッジと一致する有効なノードの順序を見つけることになります。これはまさにトポロジカルなソート問題です。 すべての制約が有向エッジとして強制されるため、正確さは明らかです。 

ボトルネックは建設だ。 スクリーンショットのすべてのペアを確認するには、$O(N^2)$比較、および各比較スキャン$K$価値観につながる$O(N^2 K)$。 これはすぐに不可能になります$N$is large.

 重要な観察は、ペアごとの制約「$A$先行できる$B$もし、そしてその場合に限り$A_i \le B_i$みんなのために$i$” は、座標方向の順序付けのように動作する部分順序を定義します。グラフを構築する代わりに、有効な順序付けは、スコア ベクトルによってスクリーンショットを辞書編集的に並べ替えることとすでに一致している必要があることを認識できます。1 つのベクトルが座標方向で小さいか等しい場合、並べ替え後の辞書編集順でも前に表示されるか同じになります。

 これにより、問題は並べ替えに限定されます$N$次元のベクトル$K$、すべてのペアをチェックするよりもはるかに安価です。 ソート後は、隣接する要素が単調条件を満たしていることを確認するだけで済みます。これは、違反があれば、制約と一致するグローバルな順序付けが存在できないことを示すためです。 

辞書編集的な比較は厳密には必要ではないことに気づくと、さらに単純化されます。 必要なのは座標上の優位性と一致する全体の順序だけであるため、スコアの合計などの単純な集計キーによる並べ替えも、この問題の制約下で機能します。 これが機能するのは、すべての座標において 1 つのベクトルが他のベクトルよりも優勢である場合、その合計も大きいか等しい必要があり、順序付けの一貫性が保たれるためです。

 ## アルゴリズムのチュートリアル

 1. すべてのスクリーンショットを読み取り、それぞれを長さの配列として保存します$K$。 この表現により、構造グラフの構築ではなく、座標操作に対してすべての比較がローカルに保たれます。 
2. 各スクリーンショットにインデックスを割り当てて、並べ替え後に元の順序を復元できるようにします。 これが必要なのは、出力が変換されたデータではなく、入力スクリーンショットの並べ替えであるためです。 
3. スクリーンショット ベクトルから派生したコンパレータを使用してインデックスを並べ替えます。 有効な選択肢の 1 つは、完全なベクトルにわたる辞書編集的な比較であり、差が現れるまでチームのスコアを左から右に比較します。 これは、座標上の優位性が存在する場合にはそれを尊重するため機能します。 
4. 必要に応じて、代わりに、各スクリーンショットのスコアの合計など、単一の集計値で並べ替えることができます。 有効な遷移はすべての座標を同時に保存する必要があり、したがって全体の順序も保存するため、問題の単調制約の下ではこれで十分です。 
5. ソートされたインデックスを最終的な順序として出力します。 

ソート後、順序付けは、すべての制約と互換性のある合計順序に従ってスコア ベクトルの一貫した非減少の進行を強制するため、候補タイムラインとして受け入れられます。 

### なぜ効果があるのか

 基礎となる構造は、座標方向の比較によって定義される半順序です。どの座標においてもスクリーンショットが大きくない場合にのみ、あるスクリーンショットが別のスクリーンショットに先行します。 有効な解決策は、この部分順序を全体順序に拡張する必要があります。 辞書編集順 (またはこの制約構造に基づく合計などの一貫した単調キー) による並べ替えでは、すべての座標において厳密に大きいベクトルが厳密に小さいベクトルの前に配置されることがないため、このような拡張が生成されます。 これにより、問題によって暗示されるすべての強制順序付け制約が尊重されることが保証されるため、最終シーケンスに無効な遷移が現れることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = [list(map(int, input().split())) for _ in range(n)]

    # store indices
    idx = list(range(n))

    # lexicographic sort of vectors
    idx.sort(key=lambda i: a[i])

    # output 1-based indices
    print(*[i + 1 for i in idx])

if __name__ == "__main__":
    solve()
```このソリューションは、すべてのスクリーンショットをメモリに読み取り、順列を表すインデックス配列を保持します。 ソートのステップは中核であり、リストに対する Python のタプルのような比較により、辞書編集的な順序付けが実行され、意図した部分順序の拡張に一致します。 

微妙な点は、要素ごとに比較する、Python の安定した正しいリストの辞書編集比較に依存していることです。 これにより、タイブレークや早期終了で間違いが発生する可能性があるコンパレータを手動で実装することが回避されます。 最後に、印刷時に 1 から始まるインデックスに変換し直します。

    import sys as _sys
    from io import StringIO
    out = StringIO()
    _stdout = sys.stdout
    sys.stdout = out

 ## 特殊なケース

 重要なエッジケースは、すべてのスクリーンショットが同一である場合です。 例えば：```
3 2
1 1
1 1
1 1
```どの座標においても厳密に他のスクリーンショットより優れている、または劣っているスクリーンショットはないため、すべての順序は有効です。 アルゴリズムはこれらを何らかの順列に並べ替えますが、それらを区別する制約がないため、これは許容されます。 

もう 1 つの重要なケースは、次のようなベクトルが座標の意味で比較できない場合です。```
2 2
1 5
5 1
```どちらのスクリーンショットも他方を支配するものではないため、理論的にはどちらの順序も有効です。 辞書編集的ソートでは、たとえば (5,1) の前に (1,5) というように 1 つの決定的な順序が選択されますが、逆の順序を強制する制約がないため、それでも問題は解決されます。 

最後に、チェーンを厳密に増やすことを検討します。```
3 2
1 1
2 2
3 3
```アルゴリズムにより、それらは自然に昇順に配置されます。 これにより、厳密なチェーンが存在する場合、並べ替えではそれが尊重され、明示的なグラフ構築を必要とせずに一貫したタイムラインが生成されることが確認されます。
