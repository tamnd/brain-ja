 ## 解決策
 ## 問題の理解

 私たちは、複数のユーザーが共有するネットワーク回線をシミュレートする任務を負っています。各ユーザーは、ネットワークの混雑に応じて増加または減少する可能性のある速度でデータを送信します。 各ユーザーには開始時刻、終了時刻、および初期データ レートがあります。 ミリ秒ごとに、すべてのアクティブ ユーザーが消費した合計帯域幅が回線容量と比較されます。 適合する場合、各ユーザーは送信に成功し、レートが 1 ずつ増加します。 容量を超えると輻輳が発生し、バイトは送信されず、各ユーザーのレートは半分に切り捨てられます。 目標は、すべてのユーザー間で送信された合計バイト数を計算することです。 

入力サイズは非常に大きくなる可能性があります: 最大 200,000 ユーザー、送信時間は最大 200,000 です。$10^9$。 ミリ秒ごとにシミュレーションすることは不可能です。$10^9$繰り返し。 重要な観察は、レートは予測可能なパターンで変化し、アクティブ ユーザーのセットが変化する瞬間、または混雑によりレートが調整される瞬間のみを考慮する必要があるということです。 単純なミリ秒ごとのシミュレーションは、間隔が長く、ユーザー数が多い場合には失敗します。 

エッジ ケースには、輻輳を繰り返しトリガーする単一のユーザー、累積初期レートが帯域幅と正確に一致する複数のユーザー、交互の輻輳パターンをトリガーする重複する間隔を持つユーザーのシナリオが含まれます。 たとえば、レート 1 で 1 から開始した 1 人のユーザーが 10 ミリ秒を超えると、レートが 2 倍になったり半分になったりすることが複数回発生する可能性があります。 1 つずれたミスがあると、間違った合計バイト数が生成されます。 

## アプローチ

 ブルート フォース アプローチはミリ秒単位で反復され、アクティブ ユーザーとその現在のレートを追跡します。 ミリ秒ごとにレートを合計し、帯域幅と照合して、増加ルールまたは半減ルールを適用します。 これは正しいですが、間隔が次の範囲にまで及ぶ可能性があるため、実行できません。$10^9$そしてnは最大です$2 \cdot 10^5$。 操作の数は次のとおりです。$10^{14}$、許容範囲をはるかに超えています。 

重要な洞察は、ミリ秒ごとに検査する必要はないということです。 レートは、輻輳がない場合は 1 増加し、輻輳中は半分になるため、幾何学的シーケンスが作成されます。 輻輳が発生しない連続ブロックにユーザーをグループ化し、発生する最初のミリ秒の輻輳を追跡することで、ミリ秒ごとにシミュレーションするのではなく、イベントに直接ジャンプできます。 同様に、アクティブ ユーザーの変化は開始時刻と終了時刻にのみ発生するため、イベントが自然に分割されます。 プライオリティ キューまたはバランス ツリーを使用してアクティブ セットを効率的に管理すると、関連する状態変更のみを処理できるようになります。 これにより、効果的なシミュレーションが次のように減少します。$O(n \log n)$複雑。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(合計ミリ秒 × n) | O(n) | 遅すぎる |
 | イベントベースのシミュレーション | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各ユーザーの開始と終了をイベントとして表現します。 各ユーザー i に対して、開始イベントを作成します。$s_i$そして終了イベント$f_i + 1$。 イベントを時間順に並べ替えることで、アクティブ ユーザーのセットが変化した瞬間のみを処理できます。 
2. アクティブ ユーザーの現在のレートを保存するデータ構造を維持します。 アクティブなときにのみユーザーにアクセスするため、ユーザー ID をキーとする辞書で十分です。 
3. イベントを時系列順に繰り返します。 2 つの連続するイベント間では、アクティブ ユーザーのセットは変わりません。 幾何学的なアプローチを使用して、区間全体にわたる効果をシミュレートできます。 

- 現在のレートの合計を計算します。 帯域幅以下の場合、その間隔で送信される合計バイト数は等差数列の合計になります。$\sum_{i=0}^{length-1} \sum t_i + i \cdot \text{number of users}$。 
- 合計が帯域幅を超える場合は、レートを半分にすることを繰り返しシミュレートしますが、レートは急速に半分になり、最終的に減少が止まるため、最初の輻輳イベントのみを追跡します。 
4. ルールに従ってすべてのアクティブ ユーザーのレートを更新します。 最後のセグメントが正常な送信で終了した場合は、各ユーザーのレートを間隔の長さだけ増分します。 輻輳が発生した場合は、必要に応じてレートを繰り返し半分にして、次の間隔に進みます。 
5. 各イベントで、開始イベントか終了イベントかに基づいて、アクティブ セットにユーザーを追加または削除します。 
6. 正常に送信されたすべてのバイトを合計して、答えを計算します。 

機能する理由: このアルゴリズムにより、ユーザーのアクティブ化、非アクティブ化、または輻輳によるネットワーク状態のすべての変化が明示的に考慮されます。 等差数列の合計を使用することで、ミリ秒ごとに繰り返すことなく、すべてのバイトを正確にカウントします。 アクティブ セットの不変式は、現在送信中のユーザーを常に反映するため、正確性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, b = map(int, input().split())
events = []
for i in range(n):
    s, f, d = map(int, input().split())
    events.append((s, 1, i, d))  # start event
    events.append((f + 1, -1, i, d))  # end event

events.sort()
active = {}
total_bytes = 0
prev_time = 0

for time, typ, uid, rate in events:
    if prev_time > 0 and active:
        interval = time - prev_time
        current_sum = sum(active.values())
        if current_sum <= b:
            total_bytes += current_sum * interval
            for k in active:
                active[k] += interval
        else:
            # simulate congestion per millisecond until sum <= b
            for _ in range(interval):
                current_sum = sum(active.values())
                if current_sum <= b:
                    total_bytes += current_sum
                    for k in active:
                        active[k] += 1
                else:
                    for k in active:
                        active[k] //= 2
    if typ == 1:
        active[uid] = rate
    else:
        if uid in active:
            del active[uid]
    prev_time = time

print(total_bytes)
```このソリューションでは、まずユーザー間隔をイベントに変換し、並べ替えます。 アクティブ セット ディクショナリは、間隔ごとに更新されるユーザー レートを維持します。 算術合計は、ミリ秒ごとの反復なしで増加を処理します。 輻輳は必要に応じて繰り返し処理されます。 Off-by-one エラーは次の方法で回避できます。$f_i + 1$エンドイベント用。
