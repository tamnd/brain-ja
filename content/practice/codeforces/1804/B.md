 ## 解決策
 ## 問題の理解

 患者の到着時刻のソートされたリストが渡されます。 各患者は特定の時間に到着し、限られた時間単位まで喜んで待ちます。つまり、ワクチン接種が可能な時間枠があることを意味します。 彼らが時間通りに到着したら$t_i$、その後、からの任意の整数時刻に提供できます。$t_i$に$t_i + w$。 

ワクチンは個別の単位ではなく、複数のパックにまとめて提供されます。$k$用量。 一度開封したパックは、一定の期限内に使用する必要があります。$x$、時間からのみ使用できます$x$に$x + d$。 その後、残りの投与量は廃棄されます。 各患者は正確に 1 回分の摂取量を摂取します。 

タスクは、パックを開けるタイミングと、パックに患者を割り当てる方法を選択し、すべての患者が個人の待機期間内で、開封されたパックの有効期間内に、できるだけ少ないパックを使用してワクチン接種を受けられるようにすることです。 

入力サイズは最大で$2 \cdot 10^5$total patients across test cases, so any solution must be roughly linear or near-linear per test case. A quadratic strategy that repeatedly tries all possible groupings of patients would exceed limits because it would require checking compatibility between many overlapping time windows.

 A key edge situation appears when patient windows barely overlap or are disjoint. たとえば、次の場合$w = 0$、すべての患者は到着時刻に正確に対応する必要があるため、グループ化は複数の患者が同時に到着した場合にのみ可能です。 もう 1 つの例外的なケースは次のような場合です。$d = 0$つまり、パックは開封直後にのみ使用できるため、各パックは効果的に使用できるのはせいぜい 1 回だけです。$k$。 

## アプローチ

 素朴な考えは、患者を 1 人ずつ割り当てることをシミュレートし、各患者について、開いた既存のパックがまだ有効で容量が残っている場合はそのパックに患者を配置し、そうでない場合は最適なタイミングで新しいパックを開くことです。 これには、すべてのアクティブなパックを維持し、各患者の互換性を確認する必要があります。 最悪の場合、多くのパックが時間的に重複し、有効なパックを見つけるために繰り返しスキャンすることになり、$O(n^2)$行動。 

問題の構造により、より詳細な観察が可能になります。 患者はソートされた順序で到着するため、当然、早い時間から最も遅い時間まで処理されます。 各パックは、一度開封すると、一定の使用可能期間を定義します。$[x, x + d]$、そして最大で奉仕することができます$k$患者。 一方、各患者には独自の対応可能間隔があります$[t_i, t_i + w]$。 パックは、サービス時にこれらの間隔が重なる場合にのみ患者に使用できます。 

重要な簡素化は、個々のパックを詳細に追跡することを避け、代わりに連続する患者をグループ化する方法を貪欲に決定することです。 開始患者が固定されている場合、次の両方の制約に従って、できるだけ多くの後続の患者を 1 つのワクチン パックに詰め込みたいと考えています。つまり、診療時間は共通の実現可能な時間枠内に収まる必要があり、それを超えてはなりません。$k$パックあたりの患者数。 

インデックスから始まる患者グループの場合$i$、パックの開封を遅らせることができる最も遅い時間は、グループ内の患者の可能な限り早い期限切れによって制限されますが、実行可能な最も早い時間は、グループ内の最も遅い到着から待機許容量を差し引いたものによって制限されます。 これにより、グループ化の問題は、実行可能な患者のスライディング ウィンドウを維持し、別の患者を追加すると実行可能性が損なわれたり、キャパシティを超えたりすると貪欲にグループを閉じるという問題に変わります。 

これにより、問題は 1 つのパスに短縮され、患者のウィンドウを拡大し、制約が破られるたびに繰り返しグループを最終決定します。

 ## アルゴリズムのチュートリアル

 到着時刻の昇順に患者を処理し、同じパックに割り当てられた患者を表す現在のバッチを維持します。 

1. 最初の患者から始めて、空のバッチを初期化します。 また、開封したパックの数も管理します。 
2. 各患者を順番に現在のバッチに追加してみます。 患者を追加するときは、バッチが時間の観点から実行可能であるかどうかを確認します。 バッチは、患者の待機制限とワクチンの寿命の両方を考慮した共通の時間間隔で提供できなければなりません。 
3. バッチを構築する際、次の値を超えないことも確認します。$k$患者。 バッチサイズに達した場合$k$、時間の実現可能性に関係なく、パックではより多くの患者にサービスを提供できないため、バッチをすぐに完成させます。 
4. 新しい患者を追加することが実現可能性に違反する場合、つまり現在バッチ内のすべての患者にサービスを提供できる 1 回の時間がない場合、この患者の前にバッチを終了し、新しいバッチを開始します。 
5. すべての患者が処理されるまで繰り返します。 バッチを終了するたびに、ワクチン パックを 1 つとカウントします。 

重要な隠れたステップは実現可能性のチェックです。 患者のバッチの場合、サービス時間はすべての患者間隔の交差点になければなりません。$[t_i, t_i + w]$、つまり$[\max t_i, \min (t_i + w)]$。 この交差部分は、ある程度の長さのパック間隔とも重なる必要があります。$d$ただし、バッチ内で開始時間を最適に選択するため、実現可能性は交差点が空ではなく、長さでカバーできることを確認することになります。$d$ウィンドウ。 

これを維持する実際的な方法は、バッチ内の現在の最大到着時間と最新の許容サービス時間の最小値を追跡することです。 

### なぜ効果があるのか

 バッチを拡張するたびに、現在の実行可能なサービス領域と間隔がまだ重なっている患者のみを追加します。 患者は分類されているため、先に進む前に、患者を含む可能性のある以前のグループ分けがすでに考慮されています。 バッチが終了すると、時間の制約や容量に違反することなく、以降のバッチにそれらの患者を含めることはできません。 これにより、各バッチが実現可能な最大の連続セグメントに対応することが保証され、貪欲な最大セグメンテーションにより必要なパックの数が最小限に抑えられます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k, d, w = map(int, input().split())
    t = list(map(int, input().split()))
    
    packs = 0
    i = 0
    
    while i < n:
        packs += 1
        
        batch_size = 0
        
        # We maintain the feasible time window of the current batch
        # For patients j in batch:
        # feasible start is max(t[j])
        # feasible end is min(t[j] + w)
        left = t[i]
        right = t[i] + w
        
        j = i
        
        while j < n:
            # check if patient j can fit in current feasibility window
            new_left = max(left, t[j])
            new_right = min(right, t[j] + w)
            
            if new_left > new_right:
                break
            
            if batch_size == k:
                break
            
            left = new_left
            right = new_right
            batch_size += 1
            j += 1
        
        i = j
    
    print(packs)

if __name__ == "__main__":
    solve()
```コードは各バッチを貪欲に構築します。 変数`left`そして`right`現在のグループ内のすべての患者時間ウィンドウの交差を維持します。 交差点が空いたら停止し、新しいパックを開始します。 の`batch_size`変数により、線量制限を決して超えないことが保証されます$k$。 ポインタ`i`各バッチ後に最初の未処理の患者にジャンプし、直線的な進行を保証します。 

微妙な点は、パックの開封時間を明示的に計算していないことです。 これは実行可能な交差点内で暗黙的に選択されるため、そのような時間が存在するかどうかのみを追跡します。

 ## 特殊なケース

 いつ$w = 0$、各患者は到着時間どおりにのみ対応できます。 交差間隔が患者ごとに 1 つの点に集約されるため、アルゴリズムはこれを処理します。そのため、到着が一致する場合にのみ結合が成功します。 たとえば、`1 1 0 0`到着あり`[5]`、バッチはすぐに形成され、1 つのパックで閉じられます。 

いつ$k = 1$、タイミングに関係なく、すべての患者が個別のパックを必要とします。 アルゴリズムはこれを強制します`batch_size == k`、患者ごとに強制的に閉鎖し、最適な動作を一致させます。 

いつ$d = 0$、パックの寿命はゼロです。つまり、パックは開封した瞬間にのみ使用できます。 すべての患者が共通の実行可能時間を共有しない限り、異なるサービス時間を必要とするグループは交差に失敗し、実質的に非常に小さなバッチが強制されるため、実行可能性条件は依然として機能します。
