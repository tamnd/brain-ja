 ## 解決策
 ## 問題の理解

 URL のストリームが 1 日あたり 1 つ与えられ、毎日の後にサーバーが維持する必要がある「確認プレフィックス」の数を決定する必要があります。 

確認プレフィックスは空ではない文字列です。 これらの保存されたプレフィックスの少なくとも 1 つが URL の先頭と一致する場合、URL は有効であると見なされます (つまり、サーバーはゲーム データを返します)。 それ以外の場合、サーバーは「見つかりません」を返します。 目的は、未リリースのゲームのデータ漏洩を防ぐことです。つまり、意図しない限り、未リリースの URL が誤ってサーバーの受け入れ条件と一致してはなりません。 

新しい URL が導入されるたびに、これまでに確認されたすべての URL が、ルールが暗示する意味での任意の推測と「区別できる」ように、プレフィックスの最小数を計算する必要があります。既知の URL はすべて、少なくとも 1 つの保存されたプレフィックスでカバーされている必要がありますが、不必要な重複によってカウントが膨らむことはありません。 

状況を再解釈する便利な方法は、文字列のセットを維持しており、できるだけ少ない共有プレフィックス代表を使用してそれらすべてをカバーしたいということです。 複数の URL が共通の始まりを共有している場合、単一のプレフィックスでそれらの URL に対応できます。 問題は、これまでに確認されたすべての URL にどれだけのプレフィックス共有構造が存在するかを追跡し、それを動的に更新することに帰着します。 

制約は厳しく、URL は最大 5 × 10⁴、それぞれの長さは最大 50 です。これにより、挿入ごとにペアごとのプレフィックス関係を 2 次またはそれより悪い時間で再計算するソリューションは即座に除外されます。 O(n²) アプローチでは、最悪の場合、10⁹ 程度の比較が必要になりますが、これでは遅すぎます。 

エッジケースは、時間の経過とともにプレフィックスがどのように相互作用するかによって発生します。 たとえば、次のことを考えてみましょう。 

入力:```
a
ab
abc
```単純なアプローチでは、新しい文字列ごとに常に答えが増え、1、2、3 が生成されると考えるかもしれません。しかし、実際には、それらはすべて単一の接頭辞「a」でカバーできるため、正解は 1、1、1 のままです。これは、文字列を数えているのではなく、独立した「接頭辞ブランチ」がいくつ存在するかを数えていることを示しています。 

もう 1 つの特殊なケースは、URL が早期に分岐する場合です。 

入力:```
a
b
c
```ここではプレフィックスが共有されていないため、答えは 1、2、3 のように毎回増加する必要があります。 

これらの例は、対象の構造が文字列のトライのような分割であり、共有プレフィックスによって必要な代表の数が減少することを示唆しています。 

## アプローチ

 直接的なブルート フォース解釈では、これまでに確認されたすべての URL のセットが維持され、挿入のたびに、セット内に表示されるすべての可能なプレフィックス文字列が試行されます。 各プレフィックス候補について、少なくとも 1 つの URL をカバーしているかどうか、および冗長なプレフィックスを削除できるかどうかを確認できます。 最適なプレフィックス セットは個々の文字列ではなくグローバル構造に依存するため、これはすぐに複雑になります。 

より単純な総当り攻撃のアイデアは、これまでに確認されたすべての文字列に対してトライを構築し、ノードをマージするか、ルートからリーフまでのパスごとに最小限の代表をカウントすることを繰り返し試行することです。 ただし、挿入のたびにこれを最初から再計算することは、合計サイズが最大 2.5 × 10⁶ 文字の構造を再構築または再処理することを意味します。 これを n 回実行すると、O(n · L) の再構築コストが発生します。これは境界線ですが、それでも厳しい制約の下で Python では遅すぎ、更新は増分であるため不要です。 

重要な観察は、答えが、文字列が挿入されるときの「新しい分岐寄与」を表すトライ ノードの数であるということです。 より正確には、新しい文字列が以前に存在しなかったプレフィックスを導入するたびに、既存のすべての文字列から最初に分岐するポイントに追加の代表プレフィックスが強制的に存在します。 これは、トライを段階的に構築し、すべての挿入で新しく作成されたノードの数をカウントすることと同じです。 新しく作成された各ノードは、以前には存在しなかったプレフィックスに対応するため、それをカバーする追加の確認プレフィックスが必要になります。 

したがって、問題は動的にトライを維持し、新しいノードをカウントすることに帰着します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | プレフィックス構造のブルート フォース再計算 | O(n · L²) | O(n・L) | 遅すぎる |
 | インクリメンタルトライ構築 | O(n・L) | O(n・L) | 承認済み |

 ## アルゴリズムのチュートリアル

 各エッジが小文字、ドット、スラッシュを含む URL アルファベットの 1 文字に対応するトライを維持します。 各ノードは、これまでに出現したプレフィックスを表します。 

新しく挿入された URL ごとに、トライを 1 文字ずつ調べます。 

1. トライのルートから開始します。 
2. URL 内の各文字について、その文字の子ノードが存在するかどうかを確認します。 
3. 存在する場合は、答えを変更せずにそのノードに移動します。 
4. 存在しない場合は、新しいノードを作成し、グローバル カウンタをインクリメントします。 
5. 文字列の終わりまで続けます。 

各 URL を処理した後のカウンターの現在の値がその日の答えになります。 

直感的には、新しいトライ ノードを作成するたびに、以前のすべての URL の中でこれまでに出現したことのないプレフィックスが見つかるということです。 このようなプレフィックスは既存の確認プレフィックスではカバーできないため、「プレフィックス カバレッジの複雑さ」の追加単位が必要になります。 

### なぜ効果があるのか

 このトライは、すべてのノードが少なくとも 1 つの挿入された URL に出現するプレフィックスに正確に対応するという不変条件を維持します。 新しい文字列を処理するとき、欠落しているエッジは、この挿入前に存在しなかったプレフィックスを表します。 確認プレフィックスはすべての URL を確実にカバーする必要があるため、新しく導入されたプレフィックスは、プレフィックス空間における新しい構造要件を表す可能性があります。 新しく作成された各ノードは、システム内で以前に表現されていなかった個別のプレフィックス セグメントに対応し、これらのセグメントは、各ステップの後に、必要な確認プレフィックスの最小数に正確に蓄積されます。 

ノードを削除することはなく、必要な場合にのみ追加するため、作成されたノードの数は個別のプレフィックス構造の増加を単調に追跡し、各挿入後に必要な応答と一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class TrieNode:
    __slots__ = ("next",)
    def __init__(self):
        self.next = {}

def solve():
    n = int(input())
    root = TrieNode()
    nodes = 0
    out = []

    for _ in range(n):
        s = input().strip()
        cur = root

        for ch in s:
            if ch not in cur.next:
                cur.next[ch] = TrieNode()
                nodes += 1
            cur = cur.next[ch]

        out.append(str(nodes))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションはトライを段階的に構築します。 の`nodes`カウンタは、導入された新しいプレフィックス状態の数を追跡します。 欠落している各遷移は、以前に存在しなかったプレフィックスに対応するため、新しいノードを割り当ててカウンターを増やします。 

すべての文字列にわたる合計遷移は長さの合計 (最大 2.5 × 10⁶) によって制限されるため、ノードごとの辞書の使用は許容されます。 

微妙な点は、端末情報を保存したり、後処理を実行したりする必要がないことです。 答えはプレフィックス構造のみに依存し、ノードが完全な URL に対応するかどうかには依存しません。
