 ## 解決策
 ## 問題の理解

 いくつかの種類のスナックが与えられますが、それぞれの種類のスナックが複数回出現する可能性があり、個々のスナックにはある程度の量のカフェインが含まれています。 重要な単純化は、生の質量と割合で考えるのではなく、各スナックを固定のカフェイン値に寄与するものとして直接扱うことです。 したがって、入力内のすべてのアイテムは、一定量のカフェインを追加する「パケット」として見ることができます。 

課題は、選択したスナックの種類を最小限に抑えて、少なくとも必要なカフェイン閾値に達することです。 重要な詳細は、ある種類のスナックを 1 つ選択すると、カフェインを蓄積する目的で同じ種類のすべてのスナックを効果的に使用できるため、個々の品目ではなく種類のレベルで決定が行われるということです。 

出力は、選択したすべてのスナックの合計カフェインが少なくとも目標値に達するために摂取する必要がある個別のスナックの種類の最小数です。すべてのスナックを摂取しても不十分な場合は -1 になります。 

この制約は、入力サイズが大きくなる可能性があることを暗示しているため、型のすべてのサブセットを試行したり合計を繰り返し計算したりするソリューションは遅すぎる可能性があります。 テストごとにソートまたは線形パスを使用するソリューションが期待されるため、テストごとにおおよそ O(n log n) または O(n) が許容されますが、指数関数または二次関数の動作は許容されません。 

スナックを種類ごとにグループ化するのではなく、個別に扱う場合、微妙な失敗例が発生します。 タイプごとに集計せずに個々のスナックを貪欲に選択すると、より早く高収量タイプに完全にコミットしたほうがよい場合に、低収量タイプから複数のスナックを選択する可能性があります。 

たとえば、スナックが多くの品目で合計 100 のカフェインをもたらしているタイプ A と、2 つのスナックがそれぞれ 51 カフェインをもたらし、合計 102 を備えているタイプ B があるとします。個々の値に基づいて貪欲に選択する場合、最初に両方の 51 秒を取得し、タイプ A の選択を遅らせる可能性がありますが、正しい推論は品目ごとの選択ではなく、種類の貢献によるグループ化に依存します。 

## アプローチ

 ブルートフォースの観点は、スナックの種類の考えられるすべてのサブセットを検討することから始まります。 各サブセットについて、それらのタイプに属するすべてのスナックからのカフェイン寄与を合計し、その合計が目標に達しているかどうかを確認します。 すべての有効なサブセットの中で、タイプの数が最も少ないサブセットを選択します。 これは、考えられるすべての決定を直接評価するため、正しいです。 ただし、q 個のタイプがある場合、2^q 個のサブセットを調べる必要があり、各サブセットの合計を計算するには項目の数に応じて直線的な時間がかかる可能性があります。 これは、中程度のサイズの入力であってもすぐに実行不可能になります。 

重要な観察点は、各タイプ内でその寄与を部分的に使用する理由がないということです。 あるタイプを含めることを決定したら、そのスナックをすべて摂取します。それぞれが合計にプラスの影響を及ぼし、そうすることによるペナルティはないからです。 これにより、問題は品目レベルの決定から種類レベルの重みに分解され、各種類が総カフェインに等しい単一の集計値を持ちます。 

型レベルの重みに削減されると、目標は、合計の重みが少なくとも x に達する最小数の型を選択することになります。 これは古典的な貪欲な構造です。私たちはできるだけ少ない種類のカフェインを使用してできるだけ多くのカフェインを蓄積したいので、常に最も「価値のある」種類を最初に選択します。 

これにより、タスクは種類ごとのカフェインの総量を計算し、この合計によって種類を降順に並べ替え、目標に達するまで貪欲に蓄積することに減ります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | タイプのサブセットに対するブルート フォース | O(2^q · n) | O(n) | 遅すぎる |
 | グループ化 + 貪欲な並べ替え | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. すべてのスナックを読み、タイプごとにグループ化し、タイプごとのカフェインの総寄与量を累計します。 このステップでは、項目レベルのデータを、各タイプが単一の意味のある重みを持つコンパクトな表現に変換します。 
2. 種類ごとに、カフェインの総寄与量を計算します。 これが必要なのは、そのタイプの選択を決定する際に重要となるのは集計のみであるためです。 
3. すべてのタイプの合計をリストに保存し、降順に並べ替えます。 並べ替えにより、最も影響力のあるタイプが常に最初に考慮されるようになります。これは、選択されるタイプの数を最小限に抑えるために不可欠です。 
4. 現在の合計をゼロに初期化し、選択したタイプのカウンターを初期化します。 
5. ソートされたタイプの合計を反復処理し、それぞれを累計に加算し、タイプ カウンタをインクリメントします。 追加するたびに、現在の合計が目標カフェイン値に達したか、それを超えたかどうかを確認します。 
6. 目標を達成した場合は、これまでに使用した種類の数を出力します。 目標に到達せずにループが終了した場合は、-1 を出力します。 

並べ替えが安全な理由は、すべてのタイプが一度選択されると独立して完全に寄与するため、選択順序を並べ替えても、常に最大の残りの寄与を最初に取得する以上に、必要なタイプの数を増やすことはできないためです。 

### なぜ効果があるのか

 プロセスのどの時点でも、関連する状態は、カフェインの蓄積量と、選択されたカフェインの種類だけです。 各タイプの貢献量は固定の正の量であるため、より少ない貢献度をより大きな貢献度に置き換えても、同じ合計に達するために必要なタイプの数を増やすことはできません。 これにより、総カフェインの非増加順にタイプを選択する最適なソリューションが常に存在することが確立されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, x = map(int, input().split())
    
    from collections import defaultdict
    tot = defaultdict(int)

    for _ in range(n):
        t, c = map(int, input().split())
        tot[t] += c

    vals = sorted(tot.values(), reverse=True)

    cur = 0
    cnt = 0

    for v in vals:
        cur += v
        cnt += 1
        if cur >= x:
            print(cnt)
            return

    print(-1)

if __name__ == "__main__":
    solve()
```実装はアルゴリズムを直接反映しています。 このディクショナリは、単一パスでタイプごとにカフェインを集計し、スナックの数の直線的な複雑さを保証します。 集計値を並べ替えると、次に利用可能な最適なタイプが常に選択されます。 

唯一の微妙な点は、並べ替えの前にグループ化の手順を実行する必要があることです。 型集計ではなく生の項目を並べ替えると、同じ型の複数の項目が選択範囲全体で不必要に分割される可能性があるため、誤った貪欲な決定につながります。 

## 実用的な例

 次の 3 つのタイプの入力を考えてみましょう。 

入力:```
5 150
1 50
1 30
2 60
3 40
3 20
```ここでは、タイプ 1 の合計は 80、タイプ 2 の合計は 60、タイプ 3 の合計は 60 です。 

| ステップ | 選択されたタイプ | 現在の合計 | アクション |
 | --- | --- | --- | --- |
 | 1 | [] | 0 | 開始 |
 | 2 | [1] | 80 | 最大の型を取得します |
 | 3 | [1、2] | 140 | 次に大きい | を追加します。 
| 4 | [1、2、3] | 200 | 目標達成 |

 3種類選択したら終了です。 

このトレースは、タイプ 2 と 3 が等しい場合でも、それらの間の順序は重要ではないことを示しています。 重要なのは、常により大きな貢献を最初に優先することです。 

ここで、目標に到達することが不可能な場合を考えてみましょう。 

入力:```
3 200
1 50
2 60
3 40
```合計は 50、60、40 となります。すべての種類を選択しても 150 までしか到達しないため、答えは -1 になります。 

| ステップ | 選択されたタイプ | 現在の合計 | アクション |
 | --- | --- | --- | --- |
 | 1 | [2] | 60 | 最大値を取る |
 | 2 | [2,1] | 110 | 続ける |
 | 3 | [2,1,3] | 150 | 全てを出し切る |
 | 4 | - | 150 | 失敗 |

 これにより、アルゴリズムが実行不可能なターゲットを正しく処理していることが確認されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | グループ化は O(n)、ソート タイプの合計が優勢です |
 | スペース | O(n) | タイプごとに合計を保存する |

 このソリューションは、並べ替えが優先され、その他はすべて線形であるため、最大 2e5 項目の Codeforces 問題の一般的な制約内に問題なく適合します。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return sys.stdout.getvalue() if False else solve_capture(inp)

def solve_capture(inp: str) -> str:
    import sys
    from collections import defaultdict
    input = sys.stdin.readline

    it = iter(inp.strip().split())
    n = int(next(it))
    x = int(next(it))

    tot = defaultdict(int)
    for _ in range(n):
        t = int(next(it))
        c = int(next(it))
        tot[t] += c

    vals = sorted(tot.values(), reverse=True)

    cur = 0
    cnt = 0

    for v in vals:
        cur += v
        cnt += 1
        if cur >= x:
            return str(cnt)

    return str(-1)

# already satisfied by one type
assert solve_capture("4 50 1 10 1 20 1 30 2 100") == "1"

 ## 特殊なケース

 最初のエッジケースは、単一のタイプがすでに目標を超えている場合です。 並べ替え後、最大の型が最​​初に処理され、1 ステップで終了がトリガーされるため、アルゴリズムはこれを即座に処理します。 

もう 1 つのケースは、すべてのタイプの寄与が非常に小さく、答えはそれらの多くを組み合わせることで決まる場合です。 アルゴリズムはソートされた順序で蓄積するため、特別な処理を必要とせずに、しきい値に達するか枯渇するまで自然に追加を続けます。 

最後のケースは、どの組み合わせもターゲットに到達しない場合です。 ループはすべての集約型値を処理した後に終了し、合計がしきい値を超えることはないため、アルゴリズムは途中で終了することなく、正しく -1 を返します。
