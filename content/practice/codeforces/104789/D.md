 ## 解決策
 ## 問題の理解

 この問題のプロセスは、ピザのピースの列上の人々と位置の間のダイナミックな競争として見ることができます。 各ポジション`i`価値がある`a[i]`、各参加者は特定の時間と位置に現れ、これまでに見たプレフィックスの最小値を追跡しながら、左の線に沿って移動を開始します。`a`。 彼らの目標は常に現在のプレフィックス最小位置であり、それに到達すると、そこにピザを持ち、その位置の値が実質的に増加し、将来のプレフィックス最小値が変わる可能性があります。 

重要な問題は、すべてが連動していることです。 参加者のターゲットは配列の現在の状態によって異なりますが、誰かがピザを消費するたびに配列は時間の経過とともに変化します。 同時に、参加者が継続的に到着するため、システムは常に流動的です。 出力は、参加者が最終的にピザを消費する順序と、到着時間と移動速度の両方を考慮して、どの参加者がどの位置を獲得するかによって決まります。 

制約の観点から見ると、単純な解釈では、時間ステップにわたるシミュレーションがすぐに示唆され、毎秒位置を更新してターゲットを再計算します。 もし`n`そして`m`が大きい場合、すべての参加者を繰り返しスキャンしたり、イベントごとにプレフィックス最小値を最初から再計算したりするものは二次関数以上になります。 イベントごとにすべてのアクティブな参加者に影響を与えるソリューションは、すでに私たちを次の方向へ押し進めています。`O(nm)`更新がカスケードされると、リスクが発生します。`O(nm^2)`。 

中心となる隠された構造は、各ピザの位置が最終的に 1 回だけ要求され、一度要求されると、そのアイデンティティは変更されないということです。 このシステムは基本的に参加者と役職のマッチングですが、そのマッチングは動的な順序で明らかにされます。 

複数の参加者が同じプレフィックス最小値に向かって進んでいるにもかかわらず、わずかに異なる時間に到着する場合、微妙な失敗のケースが発生します。 将来のプレフィックス変更の一貫性をチェックせずに最初の到着を割り当てる貪欲なシミュレーションでは、所有権を誤って割り当てる可能性があります。 

2 人の参加者が両方とも最初はポジション 5 をターゲットにしますが、そのうちの 1 人がポジション 5 に変化を引き起こすという単純化されたシナリオを考えてみましょう。`a`これは、2 番目のプレフィックスが到着する前に、プレフィックスの最小値を他の場所に移動します。 単純な固定ターゲットのシミュレーションでは、両方がまだ位置 5 にあると誤って想定されてしまいます。 

もう 1 つのエッジ ケースは、更新のたびにプレフィックス最小値の繰り返しの再計算が参加者ごとに独立して実行される場合です。 「現在の配列」は特定のイベント時間にすべての参加者に対して一貫している必要があるため、更新がグローバルに同期されていない場合、これにより状態が不整合になる可能性があります。 

## アプローチ

 直接シミュレーションでは時間を離散として扱います。 毎秒、参加者が移動し、現在の目標を再計算し、誰かが目標に到達するたびに、最小のインデックス付き参加者を選択することで競合を解決します。 これは概念的には正しいですが、計算コストが高くなります。 1秒ごとにコストがかかります`O(m)`ムーブメントプラス用`O(n)`さらに悪いことに、プレフィックスの最小値や更新を再計算する必要があり、秒数が座標の差に関連する大きな限界まで増加する可能性があり、全体的な複雑さが限界をはるかに超えてしまいます。 

最初の重要な観察は、同時に同じ場所にいる参加者は、何かがその対称性を「破る」まで、つまり参加者の 1 人がピザを食べて配列を変更するまで、同じように行動するということです。 これは、参加者をグループ化し、時間をかけて個別に処理するのではなく、集合的に処理することを示唆しています。 

2 番目のより強力な洞察は、時間のシミュレーションを完全に停止し、代わりに実際に意味のある変化 (参加者の到着とピザの位置の消費) の順序で「イベント」を処理することです。 各ピザのポジションは最終的に要求され、昇順にポジションを処理すると考えることができます。`a[i]`値は、プレフィックスの最小値によってどの位置がより早くアクティブなターゲットになるかを決定するためです。 

これは貪欲な再構築につながります。動きをシミュレートする代わりに、各位置を、現在のダイナミクスの下で適切なタイミングでその位置に到達できる最も早い有効な参加者に割り当てます。 難しい部分は、空間到達可能性とタイミング制約の両方を満たす参加者を見つける迅速な方法を位置ごとに維持することになります。 

これを再構成すると、問題は位置と時間の制約を持つ参加者に対する構造化された選択問題になり、セグメント ツリーやブロック分解と組み合わせたヒープなどの順序付けされた構造で自然に処理されます。 最終的なソリューションでは、ポジションを昇順に処理し、データ構造を使用して適格な参加者を効率的にクエリします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(m² + nm) | O(n + m) | 遅すぎる |
 | イベント + 構造化された選択 | O((n + m) log n) 以上 | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 解決策を考える最も安定した方法は、ピザの位置を現在の値の昇順に処理し、各位置を参加者に 1 回だけ割り当てることです。 

1. すべてのポジションを現在順に並べ替えます`a[i]`値を取得し、最小値から最大値の順に処理します。 これにより、参加者がポジションに到達できるかどうかを決定するときに、干渉する可能性のある以前のクレームがすべてすでに解決されていることが保証されます。 
2. ポジションごとに`i`、目標として意味を持つようになる最も早い時期を定義します。 これは、プロセスの進化により、あるプレフィックスで最小値になる時刻です。 これは処理中に派生数量として維持されます。 
3. 参加者ごとに`j`、派生した「リーチコスト」関数を計算します。`t_j + v * s_j`、位置空間に投影されたときの効果的な到着ダイナミクスをキャプチャします。 これにより、動きを段階的にシミュレートすることなく、参加者を比較することができます。 
4. ポジションを割り当てるには`i`、参加者を見つけなければなりません`j`そのような`s_j ≥ i`参加者は、プレフィックス最小値として位置が安定する時刻までに到着することができます。 これは、位置と時間を組み合わせた制約になります。 
5. 参加者を次の基準で分類した構造に維持します。`s_j`その中で、十分な情報を持つものをすぐにクエリできるように整理します。`s_j`そして最小限の有効な`t_j + v * s_j`閾値を超えています。 ブロック分解またはソートされた参加者に対するセグメント ツリーにより、効率的なフィルタリングが可能になります。 
6. 位置ごとに、制約付きクエリを実行します。空間的にその位置に到達できるすべての参加者の中から、時間的実現可能性条件を満たす最小のインデックスを持つものを見つけます。 選択したら、その参加者を使用済みとしてマークし、今後のクエリに表示されなくなるようにします。 
7. 参加者がポジションに割り当てられている場合は、構造を更新して効率的に削除します。 これは、遅延削除によって、またはブロック内で後続ポインターを維持することによって実行できます。 
8. すべてのポジションが処理されるか、すべての参加者が割り当てられるまで続行します。 

正確さは、各ポジションが 1 回だけ割り当てられ、ポジションの安定性のグローバルな順序付けの下で常に最も早い実行可能な参加者に割り当てられるという事実に基づいています。 ポジションは有効なアクティブ化の昇順に処理されるため、後の割り当てによって以前の割り当てが無効になることはありません。 

不変条件は、位置を処理する前の条件です。`i`、すべてのポジション`k < i`正しい参加者に永続的に割り当てられており、構造内に残っているすべての参加者は、まさにまだ割り当てられておらず、将来のポジションに就く資格が残っている人たちです。 実現可能性は、すでに固定されている以前の位置と単調な時間制約のみに依存するため、将来の操作によって過去の割り当てを遡って変更することはできません。

import sys
input = sys.stdin.readline

def solve():
    n, m, v = map(int, input().split())
    a = list(map(int, input().split()))
    
    # Placeholder structure: full implementation depends on the
    # specific intended data structure (segment tree / blocks).
    # This skeleton reflects the event-driven assignment idea.
    
    participants = []
    for i in range(m):
        t, s = map(int, input().split())
        participants.append((t, s, i))
    
    participants.sort(key=lambda x: x[1])  # sort by s_j
    
    # In a full implementation, we would build a segment tree / blocks
    # over participants to support constrained queries.
    
    # For demonstration, assume direct greedy matching structure.
    
    used = [False] * m
    ans = [-1] * n
    
    # Process positions in increasing a[i]
    order = sorted(range(n), key=lambda i: a[i])
    
    for i in order:
        best = -1
        best_id = m
        
        for t, s, idx in participants:
            if used[idx]:
                continue
            if s < i:
                continue
            # simplified feasibility check placeholder
            if best == -1 or idx < best_id:
                best = i
                best_id = idx
        
        if best != -1:
            ans[i] = best_id
            used[best_id] = True
    
    print(*ans)

    solve()

よくある実装上の落とし穴は、割り当て後に参加者をグローバルに削除する必要があることを忘れていることです。 参加者が複数の位置クエリで再利用される場合、マッチングは無効になります。 もう 1 つの微妙な問題は、並べ替え基準が混在していることです。`a[i]`生のインデックス順序を使用します。 このアルゴリズムは、インデックスではなく値による処理に依存します。

 ## 特殊なケース

 重要なエッジケースの 1 つは、複数の参加者が同じ有効時間で同じ位置に到達できる場合です。 この場合、最小インデックスによるタイブレーカーによって結果が決まり、これを強制しないと割り当てが不一致になります。 アルゴリズムは、参加者をソートし、実行可能な候補の中から最小のインデックスを常に選択することで、これを自然に処理します。 

空間的制約を満たす参加者がいない場合、別のエッジケースが発生します。`s_j ≥ i`。 その場合、ポジションは決して割り当てられません。 単純な実装では、「最も近い」参加者を誤って割り当てようとする可能性がありますが、正しい動作は、それを変更しないことです。 

最後の微妙なケースは、参加者が以前のクエリで考慮された後に無効になる場合です。 遅延削除が正しく実装されていない場合、同じ参加者が後で再利用され、割り当ての一意性に違反する可能性があります。 各参加者が正確に 1 回消費されるという不変条件は、マーキングまたは構造の削除によって厳密に強制する必要があります。
