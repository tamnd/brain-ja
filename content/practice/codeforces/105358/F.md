 ## 解決策
 ## 問題の理解

 私たちは、進化する単一の値、つまりユーザーの評価を追跡しています。 評価は固定の初期値 1500 で始まり、n 回の今後のコンテストごとに変更されます。 i 番目のコンテストでは、レーティングの変更は ci として与えられ、更新ルールは加算的です。つまり、新しいレーティングは以前のレーティングに ci を加えたものになります。 

タスクは、最終的なレーティングを計算することではなく、コンテストの変更を適用した後、実行中のレーティングが最初に 4000 に達するかそれを超える最も早い時点を検出することです。 どのプレフィックスでも評価が 4000 に達しない場合は、-1 を返します。 

したがって、この構造は、しきい値チェックを伴うプレフィックス蓄積問題となります。 各プレフィックスの合計は、初期値 1500 だけシフトされた、その数のコンテスト後の評価を表します。 

n が 100000 までの制約は、どのソリューションでも各コンテストを一定時間で処理する必要があることを意味します。 各プレフィックスの合計を繰り返し再計算する 2 次アプローチでは、最悪の場合でもおよそ 10^10 の演算が必要になりますが、これは Python の 1 秒の制限をはるかに超えています。 これにより、すぐにシングルパス蓄積戦略に進むことになります。 

微妙なエッジケースは、ネガティブなアップデートから発生します。 ci は負の値になる可能性があるため、定格はしきい値を超えたり下回ったりする可能性があります。 最後のインデックスではなく、しきい値に達した最初のインデックスを返すようにする必要があります。 

もう 1 つのエッジ ケースは、初期評価がすでに 4000 以上である場合です。この問題では 1500 であるため、そのような状況は発生しませんが、堅牢な推論アプローチにより、処理前のプレフィックス チェックとして自然に処理されるはずです。 

## アプローチ

 最も直接的なアイデアは、文字通りプロセスをシミュレートすることです。 現在のレーティングを 1500 から開始して維持し、コンテストごとに ci を追加してレーティングを再計算します。 更新のたびに、評価が 4000 以上であるかどうかを確認します。4000 以上である場合は、現在のインデックスを返します。 

このアプローチはプロセスを正確に反映しているため、正しいです。 ただし、構造的にはすでに最適化されています。 唯一の非効率性は、最初から合計を再計算してすべてのプレフィックスをチェックするような単純な定式化を試みた場合、プレフィックス合計を繰り返し再計算することによって発生します。 このバリアントでは、各プレフィックス合計のコストが O(n) になり、プレフィックスが n 個あるため、O(n^2) の操作が必要になります。 

重要な観察は、評価の更新が純粋に累積的であるということです。 分岐やリセットはなく、将来の値への依存もありません。 これは、ステップ i の状態がステップ i - 1 の状態によって完全に決定されることを意味するため、何も再計算することなく現在までの合計を維持できます。 

更新ごとにしきい値をチェックし、累計を使用した 1 回のスキャンで問題を解決します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | プレフィックスの合計を最初から再計算する | O(n^2) | お(1) | 遅すぎる |
 | 累計累計額 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在の評価を表す変数を維持し、それを順次更新します。 

1. これはコンテストが適用される前の開始状態であるため、レーティングを 1500 に初期化します。 
2. i = 1 から n までのコンテストを順番に繰り返し、各 ci を読み取り、現在の評価に追加します。 このステップは、i 番目のコンテストの予測された変更を適用することを表します。 
3. インデックス i での評価を更新した後、評価が 4000 以上であるかどうかを確認します。4000 である場合は、しきい値に達した最初の瞬間として直ちに i を返します。 最初の発生が必要なため、早期の終了が非常に重要です。 
4. 評価が 4000 に達しないままループが終了した場合は、-1 を返します。 

重要な設計上の選択は、しきい値チェックを延期するのではなく、各更新の直後に実行することです。 これにより、条件がまだ保持されている後のインデックスではなく、最も早いインデックスが確実に取得されます。 

### なぜ効果があるのか

このアルゴリズムは、i 個の要素を処理した後、保存された評価が 1500 に c1 から ci までの合計を加えたものに正確に等しいという不変条件を維持します。 これは、順次適用される更新ルールに直接従うものです。 

各ステップで ci が 1 回追加されるだけで、過去の値が再検討されることはないため、プレフィックスの状態をスキップしたり、後で変更したりすることはできません。 したがって、あるインデックス i で評価が最初に 4000 を超えるか到達すると、アルゴリズムはそのステップで即座にそれを検出します。 即座に戻るため、後のインデックスでこの回答をオーバーライドすることはできず、最小性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    arr = list(map(int, input().split()))
    
    rating = 1500
    
    for i, c in enumerate(arr, 1):
        rating += c
        if rating >= 4000:
            print(i)
            return
    
    print(-1)

if __name__ == "__main__":
    solve()
```このソリューションは、評価と呼ばれる単一の整数アキュムレータを保持します。 1500 から始まり、その場で更新されます。 列挙には 1 から始まるインデックスが付けられ、コンテストの番号付けと直接一致するため、1 つずつの間違いが回避されます。 

条件チェックは各更新の直後に実行されます。 即座に返すことで、後で有効なインデックスを誤って報告することがなくなります。 

入力配列以外にはデータ構造がないため、メモリ使用量は最小限に抑えられます。

 ## 特殊なケース

 重要なエッジ ケースは、評価がプレフィックスでしきい値を正確に超え、その後低下する場合です。 たとえば:

 入力:```
4
1000 1000 -500 2000
```段階的に:

 1:2500以降

 2以降：3500

 3時以降：3000

 4時以降：5000

 ステップ 3 で評価が 4000 を下回ったとしても、ステップ 4 で発生する最初の 4000 に到達または超えたときのみを考慮するため、正解は依然として 4 です。 

アルゴリズムは、各更新後にのみ条件をチェックし、最初の成功時にすぐに戻るため、これを自然に処理します。 以前の成功は上書きされないため、有効なインデックスが見つかると、その後の振動は無関係になります。
