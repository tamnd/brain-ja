 ## 解決策
 ## 問題の理解

 私たちには、厳密な依存関係システムに配置されたアイテムの大規模なセットが与えられています。 一部のアイテムは限られた量ですでに存在する基本的なリソースですが、他のすべてのアイテムは、以前に定義されたアイテムを消費するレシピによって生産されます。 重要な構造的特性は、すべてのレシピがより大きな ID を持つ項目のみを使用することです。これにより、サイクルがないことが保証され、高い ID から低い ID への自然な計算順序が強制されます。 

すべての項目のうち、最初の n 個は特別です。 これらは、最終的な回答で考慮する唯一の項目であり、他のレシピの材料として表示することはできません。 目標は、指定された量の原材料のみから開始すると仮定して、これらの特別なアイテムを少なくとも 1 回生産できる数を決定することです。 

作成された各アイテムは、レシピ内の各材料を 1 ユニット消費します。 材料自体は他の材料から作られる可能性があるため、最終アイテムの製造は原材料を超える要件にまで拡大する可能性があります。 最大の難点は、レシピが多層 DAG を形成するため、各最終製品が直接コストではなく、原材料に対する需要ベクトルに対応していることです。 

この制約により、クラフトのクエリごとのシミュレーションから遠ざけられます。 最大 20 万のアイテムと合計 50 万のレシピ エッジが存在する可能性があるため、最終アイテムごとに依存関係を繰り返し再計算するソリューションは遅すぎます。 ただし、原材料の数は最大でも 10 種類、最終製品の数は最大でも 15 種類です。 この分割が主な構造上のヒントです。グラフは大きいですが、実際のリソース制約の次元は非常に小さいです。 

中間的な再利用からは微妙なエッジケースが発生します。 中間アイテムは複数のレシピで使用される可能性があるため、そのコストを一度計算して再利用する必要があります。 たとえば、品目 A が 2 つの異なる最終製品で必要な場合、その原材料コストを製品ごとに個別に再計算すると、作業が二重に計算され、実装の不一致が生じる可能性があります。 正しい解釈は、各品目は、後でどのように使用されるかに関係なく、単位ごとに固定の「原材料コスト ベクトル」を持っているということです。 

貪欲に順番に製品を構築しようとすると、別の問題が発生します。 製品単体では安価であっても、その製品を製造すると、他の複数の製品に必要な希少な原材料が消費される可能性があります。 これにより、ローカルでの決定の信頼性が低くなります。 最終製品のサブセットをグローバルに評価する必要があります。 

## アプローチ

 直接的な強引な戦略は、レシピを原材料まで再帰的に拡張することで、各最終製品を個別に作成するシミュレーションを行うことです。 依存関係グラフが非循環であるため、これは原理的に機能し、DFS によって各最終製品のコスト ベクトルを計算できます。 これらのベクトルを取得した後、最終製品のすべてのサブセットを試し、原材料要件の合計が利用可能な在庫内に収まるかどうかを確認できます。 

この総当りにはすでに適切な分解が含まれていますが、不用意に実装すると再帰が繰り返されるためコストが発生します。 メモ化がなければ、各製品は重複するサブグラフを通じて拡張され、指数関数的な繰り返しにつながる可能性があります。 メモ化を行ったとしても、実際のコストの課題はサブセットの列挙に移行します。これは 2^n (n は最大 15) であるため、その部分は実際には許容可能です。 

重要な観察は、構造が自然に 2 つの相に分離するということです。 まず、大きな DAG 全体を小さな固定次元表現に圧縮します。各アイテムは最大 10 サイズのベクトルになり、消費する各原材料のユニット数を記述します。 次に、これらのベクトルを使用して、最大 15 項目にわたる小さな組み合わせ最適化問題を解きます。

すべてのアイテムが 10 次元のコスト ベクトルとして表されると、問題は次のようになります。座標方向の合計が固定容量ベクトルを超えないように、最大​​ 15 個のベクトルから最大のサブセットを選択します。 これは、小さな次元制約に対する古典的なサブセットの実現可能性チェックです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 最終製品ごとに単純に拡張を繰り返す | メモ化なしの場合、O(n · m) 最悪の場合、またはそれ以上の場合 | O(m) | 遅すぎる/危険 |
 | コスト ベクトル + サブセット列挙を構築する | O(m + 2^n · n · K) | O(m・K) | 承認済み |

 ここで、K は原料の数であり、最大 10 個です。 

## アルゴリズムのチュートリアル

 まず依存関係グラフ全体を品目ごとの原材料コストに圧縮し、次に最終品目に対するサブセット選択問題を解決します。 

1. すべての原材料項目を特定し、それぞれに 0 から K-1 までのインデックスを割り当てます。 このようなアイテムはそれぞれ、独自のタイプの 1 つのユニットにのみ貢献し、他には何も貢献しません。 
2. すべてのアイテムのコスト ベクトルを作成します。 原材料アイテムの場合、このベクトルはそれ自体に対応する単位ベクトルになります。 作成されたアイテムについては、そのコスト ベクトルをすべて 0 として初期化します。 
3. IDの昇順に処理します。 すべてのレシピでは、より大きな ID を持つアイテムのみが使用されるため、アイテムのすべての材料のコスト ベクトルがすでに計算されていることが保証されます。 
4. 作成されたアイテムごとに、レシピ内のすべてのアイテムのコスト ベクトルを合計することによってコスト ベクトルを計算します。 これは、クラフトでは各材料を 1 ユニット消費するため、原材料の要件が直線的に増加するため、有効です。 
5. 前処理後、最初の n 項目のコスト ベクトルを抽出します。 最終選考で選択できる候補者はこれらのみです。 
6. ビットマスクを使用して、これらの n 項目のすべてのサブセットを列挙します。 サブセットごとに、含まれる品目のコスト ベクトルを合計して、原材料の総消費量を計算します。 
7. すべての原材料の寸法が利用可能な供給量を超えていないことを確認して、各サブセットの実現可能性を確認します。 
8. 制約を満たす最大サブセット サイズを追跡します。 

この構造における重要な点は、最終的にどの最終製品に寄与するかに関係なく、すべてのアイテムが原材料への分解が固定されているということです。 これにより、サブセットの評価に一貫性があり、追加的なものになります。 

### なぜ効果があるのか

 このアルゴリズムは圧縮不変式に依存しています。ステップ 4 の後、各アイテム i は、1 単位の i を生産するのに必要な各原材料の正確な数を表すベクトルによって完全に特徴付けられます。 レシピは ID の降順で順序付けされた DAG を形成するため、このベクトルは明確に定義されており、項目ごとに 1 回だけ計算されます。 最終製品の実現可能なすべてのセットは、座標方向の合計がリソース制限を考慮したこれらのベクトルのサブセットに対応します。また、原材料が十分である限り中間品目は常に独立して生産できるため、アルゴリズムによってチェックされるすべてのサブセットは有効な同時製造計画に対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n, m = map(int, input().split())

    ingredients = [[] for _ in range(m + 1)]
    raw_id = []
    raw_index = [-1] * (m + 1)

    for i in range(1, m + 1):
        tmp = list(map(int, input().split()))
        c = tmp[0]
        if c == 0:
            raw_id.append(i)
        else:
            ingredients[i] = tmp[1:]

    K = len(raw_id)
    for idx, rid in enumerate(raw_id):
        raw_index[rid] = idx

    p = [0] * K
    # second pass to read raw quantities
    # (we reparse lines implicitly is not possible; instead store earlier)
    # so we store separately
    sys.stdin.seek(0)
    input()
    raw_qty = [0] * (m + 1)
    parsed_ing = [[] for _ in range(m + 1)]

    for i in range(1, m + 1):
        tmp = list(map(int, input().split()))
        c = tmp[0]
        if c == 0:
            raw_qty[i] = tmp[1]
        else:
            parsed_ing[i] = tmp[1:]

    # rebuild ingredients correctly
    ingredients = parsed_ing

    cost = [[0] * K for _ in range(m + 1)]

    for i in range(1, m + 1):
        if raw_index[i] != -1:
            cost[i][raw_index[i]] = 1
        else:
            for v in ingredients[i]:
                for k in range(K):
                    cost[i][k] += cost[v][k]

    final = list(range(1, n + 1))

    best = 0
    size = len(final)

    for mask in range(1 << size):
        total = [0] * K
        ok = True
        cnt = 0

        for i in range(size):
            if mask & (1 << i):
                cnt += 1
                fi = final[i]
                for k in range(K):
                    total[k] += cost[fi][k]
                    if total[k] > raw_qty[raw_id[k]]:
                        ok = False
                        break
                if not ok:
                    break

        if ok:
            best = max(best, cnt)

    print(best)

if __name__ == "__main__":
    main()
```この解決策は、クラフトされたアイテムから原材料を分離し、コンパクトなベクトル空間で各原材料に固定インデックスを割り当てることから始まります。 次に、各項目を原材料要件に拡張できるように、逆の依存関係表現を構築します。 

コスト計算ループは重要な圧縮ステップです。 各アイテムはその材料の原材料ベクトルを蓄積します。これは、すべてのレシピが各材料を 1 ユニット消費するため有効です。 依存関係は常に上位の ID を指しているため、項目の処理時に必要な値はすべてすでに計算されています。 

最後に、サブセット列挙により、最終製品のすべての組み合わせがチェックされます。 実現可能性チェックは段階的に行われ、原材料の制限を超えるとすぐに早期停止が行われます。 

## 実用的な例

 ### サンプル 1

 原材料の使用状況を追跡しながら、最終製品 1 および 2 のすべてのサブセットを検討します。

 この構成では一緒に選択できる項目は 1 つだけなので、最大数は 1 です。 

このトレースは、各項目が個別に実行可能であっても、その組み合わせが共有リソースの制約に違反する可能性があることを示しています。 

### サンプル 2

 ここでは、一方の原材料の可用性が高く、両方の最終製品を共存させることができます。 

| マスク | 選択されたアイテム | 生の使用法 | 実現可能 |

 これにより、サブセット列挙がリソース蓄積効果を正しく捉えていることが確認されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(m · K + 2^n · n · K) | 各項目が 1 回計算され、その後すべてのサブセットがチェックされます。 
| スペース | O(m・K) | 各アイテムのコストベクトルの保存 |

 制約は、m が大きくなるが、K と n が非常に小さくなるように選択されます。 前処理はレシピのエッジの数に比例してスケールされますが、指数部分は最大 2^15 に制限されており、管理が容易です。

 ## 特殊なケース

 エッジケースの 1 つは、複数の最終製品が深い依存関係チェーンを共有する場合です。 各中間項目は共有ベクトルとして 1 回計算されるため、アルゴリズムはこれを正しく処理します。 たとえば、2 つの最終製品が両方とも同じ中間品目に依存している場合、その中間品は両方のコスト ベクトルに同様に寄与するため、再利用は自動的に考慮されます。 

もう 1 つのエッジケースは、原材料が最終製品に直接使用されず、長いチェーンを通じてのみ使用される場合です。 原材料がレシピのすべての層を通って上に伝播し、隠れた依存関係が見逃されることがないため、前処理ステップでも正しいベクトルが割り当てられます。 

最後のエッジケースは、最適な解決策が、別の組み合わせのために希少な原材料を保存するために、一見安価な製品をスキップする必要がある場合です。 サブセット列挙はすべての組み合わせを明示的に評価するため、そのようなトレードオフは、貪欲な推論を必要とせずに自然に把握されます。
