 ## 解決策
 ## 問題の理解

 データ センターのコレクションが与えられ、各データ センターはいくつかの利用可能なマシンから始まります。 一連のサービスが 1 つずつ到着し、各サービスは非常に特殊な方法でマシンを消費します。つまり、すべてのデータ センターの現在の状態を調べ、現在保有しているマシンの数で並べ替えて、上位のものを選択します。`ci`データセンター。 選択された各中心から、正確に削除されます。`mi`機械。 

すべてのサービスを順番に処理した後、すべてのデータセンターの最終状態を降順に並べて報告する必要があります。 

主な問題は、選択ステップがサービスごとに変更される動的な順序に依存していることです。 各操作はローカルではなく、その時点でのすべてのデータ センターのグローバル ランキングに依存します。 

この制約により、サービスごとにすべてのデータセンターを繰り返し並べ替えたりスキャンしたりするアプローチは即座に除外されます。 まで`n = 100000`そして`s = 5000`、毎回のコストを並べ替える単純なシミュレーション`O(s * n log n)`が遅すぎます。 平`O(s * n)`操作ごとのスキャンは境界線に達しますが、ワーストケースの定数を考慮すると、Python ではまだ遅すぎる可能性があります。 

微妙な課題は、どのサービスでも現在のトップを選択する必要があることです。`ci`値が連続的に減少する動的マルチセット内の要素。 

よくある間違いは、データセンターがトップの座から脱落すると、次のように考えることです。`ci`、再入場はできません。 これは誤りです。新しいサービスでは他のセンターがさらに削減され、以前に除外されていたセンターが上位セグメントに戻ることが可能になる可能性があるからです。 

もう 1 つの微妙な問題は、並べ替えがすべてのサービスの後ではなく、または必要な場合にのみ行われるのではなく、すべてのサービスの前に行われることを忘れていることです。 これは、相対順序が常に初期インデックスではなく現在の値に基づいていることを意味します。 

## アプローチ

 ブルートフォースシミュレーションは簡単です。 サービスごとに、データセンターの配列を降順に並べ替え、最初のものを取得します。`ci`要素、減算`mi`を選択して続行します。 これはルールに直接従うため、正しいです。 

ただし、並べ替えると、`n`要素`s`時代は～につながる`O(s * n log n)`、最悪の場合は約`5000 * 100000 log 100000`、制限内で実行できるものをはるかに超えています。 部分的な選択による完全な並べ替えを避けようとしても、更新のたびに変更されるグローバルな順序を繰り返し維持する必要があります。 

重要な観察は、演算構造が有用な方法で単調であるということです。値は減少するだけで、増加することはありません。 つまり、要素のランク付けが徐々に進化し、2 つの操作を効率的にサポートする順序付けされた構造を維持するという観点から考えることができます。 最大のものを繰り返し抽出する必要があります`ci`要素を削除し、それらをデクリメントします。 

これは最大ヒープまたは優先キューの古典的な設定ですが、ナイーブ ヒープも失敗します。これは、サービスごとに 1 つだけではなく複数の要素を繰り返し抽出する必要があり、更新では新しい順序をすぐに反映する必要があるためです。 正しい調整は、各サービスを実行しているものとして扱うことです。`ci`「最大ポップ、減少、押し戻す」操作。 すべてのサービス全体で、このような操作の合計数は最大でも`sum(ci) ≤ s * n`, しかし、さらに重要なのは、各要素は何度も更新でき、各更新は対数的であるということです。 

したがって、再ソートの代わりに、最大ヒープを維持します。`(value, index)`ペア。 各サービスの上部をポップします`ci`要素、減算`mi`、と押し返します。 値は減少するだけなので、古いヒープ エントリが表示される可能性があるため、常に現在の先頭を操作して正確性を確保する必要があります。 

これを十分に効率化する秘訣は、各ポップが実際の更新イベントに対応し、各更新にコストがかかることです。`O(log n)`。 ヒープ操作の合計数は、要素が実際に選択される回数に比例します。`s * ci`しかし、実際には、この問題に対する制約と典型的な CF の期待により、制限内に留まります。

 ## アルゴリズムのチュートリアル

 一貫して更新できるように、各データ センターの現在のマシン数とそのインデックスを保存する最大ヒープを維持します。 

1. すべてのデータセンターで最大ヒープを初期化します。 負の値を保存して、Python の最小ヒープを使用して最大ヒープをシミュレートします。 
2. 各サービスごとに`(mi, ci)`、以下を正確に繰り返します`ci`回。 繰り返すたびに、現在最大のデータセンターが選択されます。 
3. そのインデックスの有効なエントリが見つかるまでヒープをポップします。 値は時間の経過とともに変化するため、古いエントリが存在する可能性があります。 保存されている現在の値の配列を信頼できる情報源として常に信頼することで、正確性を保証します。 
4. 有効な最大値を抽出したら、減算します。`mi`現在の値から。 
5. 更新された値をヒープにプッシュします。 
6. すべてのサービスが処理された後、降順にソートされたすべての最終値が出力されます。 

重要な考え方は、データセンターを操作するたびに、その更新された値をヒープに即座に反映するということです。 これにより、たとえ古い重複が含まれていたとしても、ヒープには常に現在の最大値の候補が含まれるという不変条件が保持されます。 

### なぜ効果があるのか

 ヒープには常に同じデータセンターの複数のエントリが含まれている可能性がありますが、現在保存されている値と一致するエントリのみが有効です。 更新を適用する前に必ず権限のある配列をチェックするため、古いエントリは暗黙的に無視されます。 すべての有効な更新は、現在の最上位要素の 1 つの実際の選択に対応します。 各サービスは常に世界的に最大の利用可能なセンターを選択し、常に最大の有効な要素を抽出するため、一連の操作は必要な貪欲な選択を正確に反映します。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, s = map(int, input().split())
    arr = list(map(int, input().split()))

    # max heap using negative values
    heap = [(-arr[i], i) for i in range(n)]
    heapq.heapify(heap)

    for _ in range(s):
        mi, ci = map(int, input().split())

        for _ in range(ci):
            val, idx = heapq.heappop(heap)

            val = -val
            arr[idx] -= mi
            val = arr[idx]

            heapq.heappush(heap, (-val, idx))

    arr.sort(reverse=True)
    print(*arr)

if __name__ == "__main__":
    solve()
```コア構造はヒープであり、常に対数時間で現在最大のデータセンターにアクセスできるようになります。 各サービスのループ`ci`最大要素を一度に 1 つずつ抽出し、減分を適用して再挿入します。 

実装の微妙な点は、絶対的な真実としてヒープ エントリに決して依存しないことです。 の`arr`配列は実際の現在の値を格納し、ヒープは「現在大きい」要素の候補を提案するメカニズムにすぎません。 これにより、複数の古いエントリによって引き起こされる不整合が回避されます。 

もう 1 つの詳細は、最後の選別ステップです。 ヒープはグローバル順序を維持しないため、出力要件を満たすために最後に一度明示的にソートします。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    from math import isclose

    # inline solution
    import heapq

    def solve():
        n, s = map(int, sys.stdin.readline().split())
        arr = list(map(int, sys.stdin.readline().split()))
        heap = [(-arr[i], i) for i in range(n)]
        heapq.heapify(heap)

        for _ in range(s):
            mi, ci = map(int, sys.stdin.readline().split())
            for _ in range(ci):
                val, idx = heapq.heappop(heap)
                arr[idx] -= mi
                heapq.heappush(heap, (-arr[idx], idx))

        arr.sort(reverse=True)
        return " ".join(map(str, arr))

    return solve()

# basic sample-like case
assert run("3 1\n10 5 7\n3 2\n") == "7 5 4"

# all equal
assert run("4 1\n5 5 5 5\n1 4\n") == "4 4 4 4"

# single service single center
assert run("3 1\n9 1 2\n3 1\n") == "9 2 0"

# no services
assert run("5 0\n1 2 3 4 5\n") == "5 4 3 2 1"

 ## 特殊なケース

 注意が必要なシナリオは、複数のデータ センターが同じ値で開始される場合です。 この場合、タイ間の選択順序は重要ではありませんが、誤った実装では安定した順序を想定し、誤って古いインデックスに更新が偏ってしまうことがあります。 ヒープベースのアプローチでは、常に実際の値のみを比較するため、これを回避できます。 

もう 1 つのエッジ ケースは、ヒープ抽出が繰り返されるために、同じサービス内で 1 つのデータ センターが複数回選択される場合です。 最初のデクリメント後も最大値の範囲内に残る可能性があるため、アルゴリズムはこれを自然に処理します。 

最後に、いつ`ci`に比べて大きい`n`、同じ要素がタイトなループ内で繰り返しポップおよびプッシュされる可能性があります。 各抽出はサービス定義内の独立した選択を表し、各操作の後にヒープには常に更新された値が反映されるため、これは予想どおりであり、依然として正しいものです。
