 ## 解決策
 ## 問題の理解

 隠された無向グラフが与えられます。$n$ラベル付きノード。 このグラフの構造はデザイン 0 と呼ばれますが、そのエッジが直接表示されることはありません。 代わりに、2 つのノードが何らかのパスで接続されているかどうかをクエリできます。つまり、エッジ情報ではなく接続情報のみが得られます。 

重要な点は、クエリしているグラフの現在のバージョンで接続されていない 2 つのノードをクエリするたびに、システムがそれら 2 つのノード間に直接エッジを追加することでそのバージョンを永続的に変更し、この変更されたグラフの新しい設計インデックスを返すことです。 ノードがすでに接続されている場合、システムは応答するだけで何も変更しません。 

したがって、各クエリは同時に情報を提供し、その設計バージョンに対する将来のクエリを変更する可能性があります。 元のデザイン 0 を含む、以前に作成されたデザイン バージョンをクエリできますが、新しいデザインの構造は、以前に失敗した接続クエリに依存します。 

目標は、正確な元のエッジ セットを再構築することではありません。 代わりに、すべてのノードのペア間の接続関係がデザイン 0 と一致するグラフを出力する必要があります。言い換えれば、隠れたグラフの内部配線ではなく、隠れたグラフの接続されたコンポーネントを再現するだけで済みます。 

制約$n \le 200$サブタスクに応じて最大約 2000 ～ 20000 のクエリが、$O(n^2)$程度の余裕があるため、おそらく意図された戦略であると考えられます。$10^4$合計クエリ数。 これは、多くの進化する設計にわたって同じノードのペアを繰り返し探索する戦略は避けるべきであることも示唆しています。これは、クエリが失敗するたびに構造が変化し、制御されないと推論が不安定になる可能性があるためです。 

微妙な落とし穴は、クエリが静的であると仮定していることです。 そうではありません。 以前に余分なエッジを強制した設計で接続性をテストすると、コンポーネントを誤って折りたたんで、将来の答えの意味を破壊してしまう可能性があります。 たとえば、デザイン 0 で 1 と 2 が切断されていることを最初に発見し、それらが接続される新しいデザイン 1 が作成された場合、後でデザイン 1 をクエリすると、デザイン 0 では切断されているにもかかわらず、それらが誤って接続されていると報告されます。これは、すべての意味のある推論がデザイン 0 のみに固定されている必要があり、構造の発見に突然変異したデザインを使用することは避けなければならないことを意味します。 

## アプローチ

 すべてのペアをチェックするという強引なアイデア$(i, j)$設計 0 で、出力グラフにそれらの間のエッジを含めるかどうかを直接決定します。 ただし、実際には直接エッジ クエリにアクセスすることはできません。 私たちが持っているのは、切断されたペアに遭遇したときに状態を変化させる可能性がある接続性オラクルだけです。 このため、慎重に制御しないと、単純なペアワイズ プローブの信頼性が低くなります。 

一時的に突然変異を無視し、クエリが純粋な接続チェックであると仮定すると、ルート ノードを選択し、BFS スタイルの探索によって接続されているすべてのコンポーネントを計算できます。新しいノードごとに、コンポーネントの既知の代表に接続されているかどうかをテストします。 それには必要になります$O(n^2)$クエリで十分です。 

本当に難しいのは、デザイン 0 に対するクエリは安全ですが、作成されたデザインに対するクエリはそのデザインを永久に変更する可能性があることです。 したがって、重要な観察は、デザイン 0 以外は決してクエリすべきではないということです。すべての接続性チェックをデザイン 0 に制限すると、システムは新しいエッジを作成せず、対話は標準の接続性オラクルになります。 

デザイン 0 で安定した接続が得られると、タスクは接続された各コンポーネントのスパニング フォレストを識別することに減ります。 すべてのエッジは必要ありません。各コンポーネント内の接続を維持するのに十分なエッジだけが必要です。 最も簡単な方法は、各コンポーネント上に BFS または DFS ツリーを構築することです。 現在のコンポーネントに接続されているがまだアクセスされていない新しいノードを検出するたびに、出力グラフの検出エッジを介してそのノードを接続します。 ただし、隣接リストは与えられないため、ペアをテストすることによって到達可能性をシミュレートします。 

したがって、ノード 1 を開始点として扱い、すべてのノードを反復処理し、デザイン 0 での接続チェックを使用してそれらをコンポーネントにグループ化します。未訪問のノードごとに、接続されている場合は既知のコンポーネントの代表に接続します。 それ以外の場合は、新しいコンポーネントが開始されます。 コンポーネントが識別されたら、コンポーネント内のすべてのノードをそのコンポーネント内の最初のノードに接続することによって、各コンポーネント内にスパニング ツリーを出力します。 これが有効なのは、デザイン 0 では同じコンポーネント内のすべてのノードが相互に到達可能であるため、スター構造を追加すると接続の等価性が維持されます。 

これにより、非表示グラフのエッジへの依存が回避され、変更されない設計 0 の接続述語のみが使用されます。

 ## アルゴリズムのチュートリアル

 1. ノード 1 を参照として固定し、それが最初のコンポーネントに属していると仮定します。 コンポーネント代表のリストと、各ノードがコンポーネントに割り当てられているかどうかをマークする配列を維持します。 これにより、接続グループ化のための安定したアンカーが得られます。 
2. 各ノードについて$i$2から$n$、ノード 1 とノード間の接続をクエリします。$i$デザイン 0 を使用します。結果が接続されている場合は、代入します。$i$それ以外の場合は、次のコマンドで新しいコンポーネントを開始します。$i$その代表として。 これが機能する理由は、接続性が等価関係であるため、同じ接続コンポーネント内のメンバーシップは、単一の代表からの到達可能性によって完全に決定されるためです。 
3. 代表者のリストを維持することで、このアイデアをすべてのコンポーネントに拡張します。 新しいノードごとに$i$、一致するものが見つかるか存在しないまで、既存の各代表と比較します。 これにより、すべてのノードが曖昧さなく正確に 1 つのコンポーネントに配置されることが保証されます。 
4. すべてのコンポーネントを特定したら、各コンポーネント内に星形を形成して出力グラフを作成します。 すべてのコンポーネントについて、その代表ノードを選択します$r$、1つおきのノードに接続します$v$そのコンポーネントで$r$。 これにより、$|C| - 1$コンポーネントごとにエッジがあり、接続には十分です。 
5. 収集されたすべてのエッジを次のように出力します。`DescribeDesign`。 

重要な設計上の選択は、設計 0 以外は決してクエリしないということです。これにより、対話型システムが突然変異状態に入ることを防ぎ、すべての応答が元の非表示グラフに対応することが保証されます。 

### なぜ効果があるのか

 無向グラフの接続性は、ノードを素の同値クラスに分割します。 これらのクラスを正しく識別すると、各クラス内のスパニング ツリーはまったく同じ到達可能性関係を保持します。つまり、ノードのすべてのペアは、それらが同じ元のコンポーネント内にある場合に限り、接続されたままになります。 この構築ではコンポーネントごとに接続されたツリーを明示的に構築し、異なるコンポーネントを接続しないため、デザイン 0 の正確な接続構造が再現されます。

def ToyDesign(n, max_ops):
    comp = [-1] * (n + 1)
    reps = []
    comps = []
    
    def get_comp(i):
        return Connected(0, 1, i)  # placeholder usage in explanation; real solution assumes design 0 queries only
    
    # We will actually assume pairwise check with design 0 only
    # Component detection
    for i in range(1, n + 1):
        assigned = False
        for idx, r in enumerate(reps):
            if Connected(0, r, i) == 0:
                comp[i] = idx
                comps[idx].append(i)
                assigned = True
                break
        if not assigned:
            comp[i] = len(reps)
            reps.append(i)
            comps.append([i])
    
    # Build spanning forest
    edges = []
    for group in comps:
        root = group[0]
        for v in group[1:]:
            edges.append((root, v))
    
    DescribeDesign(edges)

## 実用的な例

 ノードが次のような単純なケースを考えてみましょう。$\{1,2,3\}$すべて接続されており、ノード$4$孤立している。 

空のコンポーネントから始めて、ノードを順番に処理します。 

| ノード | 代表的な小切手 | 結果 | コンポーネントの割り当て |
 | --- | --- | --- | --- |
 | 1 | なし | 新しいコンポーネント | C0 = {1} |
 | 2 | 接続済み(1,2)=1 | 1と同じ | C0 = {1,2} |
 | 3 | 接続済み(1,3)=1 | 1と同じ | C0 = {1,2,3} |
 | 4 | 接続済み(1,4)=0 | 新しいコンポーネント | C1 = {4} |

 次にエッジを構築します。 C0 の場合、(1,2) と (1,3) を接続します。 C1 にはエッジがありません。 結果として得られるグラフでは、接続性が正確に維持されます。 

次に、{1,2} と {3,4,5} の 2 つのコンポーネントを含むグラフを考えます。 3 が 2 番目のコンポーネントを表す最初に発見されたものであると仮定します。 

| ノード | チェックと担当者 | 結果 |
 | --- | --- | --- |
 | 1 | 新しい | C0 = {1} |
 | 2 | 接続済み(1,2)=1 | C0 = {1,2} |
 | 3 | 接続済み(1,3)=0 | 新しいC1 |
 | 4 | 接続(1,4)=0、接続(3,4)=1 | C1 = {3,4} |
 | 5 | 接続済み(1,5)=0、接続済み(3,5)=1 | C1 = {3,4,5} |

 このトレースは、ノードが最初の代表に接続されていない場合でも、他の代表を介して正しくグループ化できることを示しています。

 ## 特殊なケース

 エッジケースの 1 つは、すべてのノードが分離されている場合です。 その状況では、個別のノード間のすべての接続クエリは切断状態を返すため、すべてのノードがそれ自体の代表になります。 その後、アルゴリズムはエッジを出力しません。これは、ペアが接続されていないため、正しい等価性と一致します。 

もう 1 つのエッジ ケースは、完全に接続されたグラフです。 すべてのノードは最初の代表と一致するため、コンポーネントが 1 つだけ形成され、出力はスターになります。 元のグラフには多くのエッジがある場合でも、スターは完全な接続性の等価性を維持します。 

最後の微妙なケースは、コンポーネントが二次代表者経由で遅れて発見される場合です。 ノードが最初の代表に接続されていない場合でも、接続は推移的であるため、最終的には同じコンポーネント内の別の代表と一致します。 これにより、隣接関係の知識がなくても正しいグループ化が保証されます。
