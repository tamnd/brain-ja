 ## 解決策
 ## 問題の理解

 2 つのコマンドのみをサポートする小さなシェルをシミュレートする必要があります。 

コマンド`cd path`現在のディレクトリを変更します。 パスはルートから始まることを意味する絶対パスにすることができます`/`、または相対、つまり現在のディレクトリから開始することを意味します。 パス内のトークン`..`「親ディレクトリに移動する」という意味です。 

コマンド`pwd`現在のディレクトリの完全な絶対パスを出力します。末尾は常にスラッシュで終わります。 

ファイルシステム自体をツリーとして構築する必要はありません。 この問題により、参照されるディレクトリがすべて存在し、ディレクトリ名が単なるラベルであることが保証されます。 実際に重要なのは、ルートから現在の場所までのディレクトリ名の順序です。 

コマンドの数は最大 50 個、各パスの長さは最大 200 文字です。 これらの制限は非常に小さいです。 パスを繰り返し再構築したり、文字列を何度も分割したりしても、完全に安全です。 合計入力サイズが線形に近い解はすべて快適に通過します。 

難しいのは、パスのセマンティクスを正しく処理することです。 

次の入力を考えてみましょう。```
3
cd /a/b
cd ..
pwd
```正しい出力は次のとおりです。```
/a/
```不用意に実装すると、最後のディレクトリではなく最後の文字が削除され、誤って次の文字が生成される可能性があります。`/a/b`。 

もう 1 つのよくある間違いは、絶対パスで発生します。```
3
cd /a/b
cd /x
pwd
```正しい出力は次のとおりです。```
/x/
```パスが次で始まる場合`/`、古い現在のディレクトリを完全に破棄する必要があります。 新しいパスを既存のパスに誤って追加すると、次のようになります。`/a/b/x/`。 

ディレクトリ名が混在する相対パスと`..`バグの原因にもなります:```
2
cd a/b/../c
pwd
```正しい出力は次のとおりです。```
/a/c/
```パスはコンポーネントごとに順番に処理する必要があります。 すべてを単純に削除することはできません`..`それぞれが直前のディレクトリにのみ影響するため、盲目的に実行します。 

ルート ディレクトリは、もう 1 つの特殊なケースです。```
3
cd /
pwd
cd ..
```出力は次のとおりです。```text`

/

```このステートメントは、ルートより上に移動しないことを保証しますが、実装ではルートを空のパス スタックまたは同等の構造として正しく表現しておく必要があります。 

## アプローチ

 最も直接的なアイデアは、現在のディレクトリを文字列として扱い、コマンドが表示されるたびにそれを文字通り操作することです。 

のために`cd`、文字列を連結し、スラッシュを繰り返し検索し、表示されたときに親ディレクトリを手動で消去することができます。`..`、結果を再構築します。 パスが短いため、これは機能します。 すべてのコマンドが 200 文字の文字列を数回処理したとしても、合計の作業量はわずかです。 

このアプローチの弱点はパフォーマンスではなく、複雑さです。 文字列のスライスと手動解析では、すぐにエラーが発生しやすくなります。 のようなケースの処理`/`、末尾のスラッシュ、または連続した親操作は扱いにくくなります。 

より明確な観察は、ファイルシステムのパスが自然にスタックのように動作するということです。 

例えば：```text
/home/vasya/docs
```は次のように表すことができます。```
["home", "vasya", "docs"]
```ディレクトリに入るということは、スタックにプッシュすることを意味します。 親ディレクトリに移動するということは、スタックからポップすることを意味します。 現在のパスを出力するということは、スタックをスラッシュで結合することを意味します。 

これはシェルのセマンティクスと正確に一致します。 

を処理するとき、`cd`コマンド:

 パスが次で始まる場合`/`, we reset the stack because absolute paths begin from the root.

 次に、パスを次のように分割します。`/`各コンポーネントを処理します。 

コンポーネントが空の場合は無視されます。 これは主に、絶対パスが次で始まるために発生します。`/`。 

コンポーネントが`..`、ディレクトリを 1 つポップします。 

それ以外の場合は、ディレクトリ名をプッシュします。 

これらの制約の下では、総当たりの文字列操作ソリューションも許容されますが、スタック表現はよりシンプルかつ安全で、実際のファイルシステムのロジックを直接反映しています。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース文字列操作 | O(n × L²) | O(L) | 承認済み |
 | スタックベースのシミュレーション | O(n × L) | O(L) | 承認済み |

 ここ、`L`は最大パス長です。 

## アルゴリズムのチュートリアル

 1. 現在のディレクトリをディレクトリ名のリストとして保存します。 

例えば、`/home/vasya/`になる`["home", "vasya"]`。 
2. 各コマンドを 1 つずつ読み取ります。 

シェルの状態は順番に変化するため、コマンドを順番に処理することは問題の動作と正確に一致します。 
3. コマンドが`pwd`、現在のパスを出力します。 

すべてのディレクトリ名を次のように結合します`/`、先頭にスラッシュを追加し、末尾にスラッシュを追加します。 

スタックが空の場合、結果は単純に次のようになります。`/`。 
4. コマンドが`cd path`, まず、パスが絶対パスであるか相対パスであるかを判断します。 

パスが次で始まる場合`/`、絶対パスはルートから始まるため、現在のスタックをクリアします。 
5. 次を使用してパスを分割します。`/`セパレータとして。 

これは次のように変換されます`vasya/../petya`独立して処理できるコンポーネントに分割します。 
6. 各コンポーネントを左から右に処理します。 

コンポーネントが空の場合は無視してください。 

これは、絶対パスの先頭のスラッシュで発生します。 
7. コンポーネントが`..`、スタックから最後のディレクトリを削除します。 

これは、親ディレクトリへの移動をシミュレートします。 
8. それ以外の場合は、コンポーネントをスタックに追加します。 

これは、子ディレクトリへの入力をシミュレートします。 

### なぜ効果があるのか

 スタックには、ルートから現在の場所までのディレクトリの正確なシーケンスが常に保存されます。 

有効なファイルシステムの移動はすべて、このシーケンスの終わりのみを変更します。 ディレクトリに入ると 1 つの要素が追加され、親に移動すると 1 つの要素が削除されます。 絶対パスでは、ルートからシーケンスが再開されます。 

各パス コンポーネントはシェルが解釈するのと同じ順序で処理されるため、コマンド処理後のスタックは常に実際の現在のディレクトリと一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    current = []
    
    for _ in range(n):
        parts = input().strip().split()
        
        if parts[0] == "pwd":
            print("/" + "/".join(current) + "/")
        else:
            path = parts[1]
            
            if path[0] == "/":
                current = []
            
            components = path.split("/")
            
            for comp in components:
                if comp == "" or comp == ".":
                    continue
                
                if comp == "..":
                    current.pop()
                else:
                    current.append(comp)

solve()
```このソリューションは、現在のパスを次の名前のリストとして保存します。`current`。 各要素は 1 つのディレクトリ名です。 

のために`pwd`の場合、実装はディレクトリ名を で結合して絶対パスを再構築します。`/`。 表現:```
"/" + "/".join(current) + "/"
```ルートディレクトリでも機能します。 もし`current`空です、`"".join(current)`は空の文字列になるため、最終的な結果は次のようになります。`//`。 形式には先頭と末尾のスラッシュがすでに含まれているため、実際には次のようになります。`//`、これは root にとっては正しくありません。 

この微妙なバグを回避するために、多くの人は条件付きアプローチを好みます。 ただし、この特定の実装では、空の結合により空の中間セクションが生成され、正確に次のようになります。`//`。 これを修正する必要があります。 

適切な実装は次のとおりです。```python
if not current:
    print("/")
else:
    print("/" + "/".join(current) + "/")
```修正された最終バージョンは次のとおりです。```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    current = []
    
    for _ in range(n):
        parts = input().strip().split()
        
        if parts[0] == "pwd":
            if not current:
                print("/")
            else:
                print("/" + "/".join(current) + "/")
        else:
            path = parts[1]
            
            if path[0] == "/":
                current = []
            
            for comp in path.split("/"):
                if comp == "":
                    continue
                
                if comp == "..":
                    current.pop()
                else:
                    current.append(comp)

solve()
```絶対パスのリセットも微妙な点です。 コンポーネントを処理する前にスタックをクリアする必要があります。 後でこれをクリアすると、同じパス内の相対ナビゲーションが正しく動作しなくなります。 

この問題により、ルートより上には移動しないことが保証されるため、`current.pop()`常に安全です。

 ## 特殊なケース

 現在のディレクトリが絶対パスに置き換えられる場合を考えてみましょう。 

入力：```
4
cd /a/b
cd /x/y
pwd
pwd
```実行:

 後`cd /a/b`、スタックは次のようになります`[a, b]`。 

次のコマンドは次で始まります`/`したがって、アルゴリズムはコンポーネントを処理する前にスタックをクリアします。 それから追加します`x`そして`y`。 

最終的なスタックは、`[x, y]`、生産:```
/x/y/
```スタックをクリアするのを忘れた場合、誤って次のエラーが発生します。`/a/b/x/y/`。 

ここで、親ナビゲーションを繰り返すことを考えてみましょう。 

入力：```
3
cd /a/b/c
cd ../..
pwd
```最初のコマンドの後のスタックは次のとおりです。`[a, b, c]`。 

処理`..`ポップス`c`。 

2番目を処理中`..`ポップス`b`。 

残りのスタックは`[a]`したがって、出力は次のようになります。```
/a/
```これにより、それぞれの`..`直前のディレクトリにのみ影響します。 

最後に、混合相対運動について考えます。 

入力：```
2
cd a/b/../c
pwd
```アルゴリズムはコンポーネントを次の順序で処理します。`a`→`[a]`

`b`→`[a, b]`

`..`→`[a]`

`c`→`[a, c]`出力されるパスは次のようになります。```
/a/c/
```これは、コンポーネントごとのシミュレーションがなぜ必要なのかを示しています。 ショートカット文字列置換アプローチでは、ネストされた親参照を簡単に誤って処理する可能性があります。
