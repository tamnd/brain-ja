 ## 解決策
 ## 問題の理解

 この問題は一連の日を記述しており、毎日がコストのような値と要件に関連付けられています。 時間の経過とともに、ある種の能力が蓄積され、毎日、必要なしきい値を満たすか、それを超える必要があると解釈されます。 あなたの初期能力は与えられており、毎日オプションでこの能力を永続的に高めるアクションを実行できます。 このようなアクションにはそれぞれコストがかかり、それが表示された日にのみ実行できます。 

具体的に言い換えると、基本強度値から始めます。 毎日、その日に少なくとも一致しなければならない必要な強さがあります。 また、i 日目には、アップグレード オプションが 1 つ提供されます。これを選択すると、強さが一定量だけ永続的に増加しますが、そのためにコストを支払います。 総コストを最小限に抑えながら 1 日の要件をすべて満たせるように、これらのアップグレード日のサブセットを選択するか、それが不可能であると判断したいと考えています。 

入力サイズは最大約 100,000 日になります。 これまでに確認されたすべてのアップグレード オプションを毎日再検討しようとするソリューションは二次的であり、制限時間内に完了することはできません。 これにより、すべてのサブセットを試したり、毎日の選択肢を再計算したりする単純な動的プログラミングは直ちに排除されます。 

微妙な問題は、アップグレードが永続的であり、将来のすべての日に影響を与えることです。 より高価なアップグレードを避けたものの、要件の急増に対応するために後から必要になった場合、早い段階で貪欲な決定を行った場合、最適ではないことが判明する可能性があります。 

いくつかの特殊なケースは分離する価値があります。 

失敗モードの 1 つは、初期強度が早い日にすでに不十分で、その日までアップグレードできない場合です。 たとえば、初期強度が 5 で、1 日目には 10 が必要だが、アップグレードが 2 日目以降にしか現れない場合、後のアップグレードが安価であっても、答えはすぐに不可能になります。 

もう 1 つのケースは、アップグレードが個別には小さいものの、累積的に必要になる場合です。 たとえば、要件が徐々に増加する可能性があり、初期の安価なアップグレードをスキップすると、後の高価なアップグレードの使用が強制されるため、局所的に貪欲な「現在失敗した場合にのみ購入する」戦略は崩れます。 

3 番目のケースは、ピーク後に要件が減少する場合です。 単純な戦略では、将来の制約によりアップグレードが必要なくなった後でもアップグレードを購入し続け、コストが不必要に超過する可能性があります。 

## アプローチ

 ブルート フォース ビューでは、アップグレードの選択肢のすべてのサブセットをシミュレートします。 サブセットごとに、最終的な強度を計算し、毎日の要件がすべて満たされているかどうかを確認し、有効であればコストを合計します。 n 日の場合、これは 2^n 個の可能性があり、非常に小さい n を超えると直ちに実行不可能になります。 

より構造化されたブルート フォースは、数日間にわたる動的プログラミングと現在の強度ですが、繰り返しの追加により強度が 1e14 以上に成長する可能性があるため、状態空間が爆発的に増加します。 状態を圧縮したとしても、遷移には各ステップで利用可能なすべてのアップグレードが考慮されるため、O(n^2) になります。 

重要な観察点は、数日を順番に処理し、利用可能なアップグレードの最も安価な組み合わせを使用して現在の要件を常に満たしていることを確認すれば、過去の決定を複雑な方法で再検討する必要がないということです。 どの日 i においても、日 ≤ i からのアップグレードのみが使用可能です。 この中で重要なのは、どのアップグレードをすでに実施しており、どのアップグレードを今後も実施する可能性があるかということです。 

これを考えると便利な方法は、利用可能なアップグレードのプールを維持しながら、日を順番に処理することです。 各アップグレードにはコストがあり、すべてのアップグレードには同じ量だけ強度を高めるという点で同じ利点があります。 目標は、現在の強度が現在の要件に対して十分であるように、各ポイントまでに何回アップグレードするかを決定することです。

これにより、問題はコストをめぐる貪欲な選択プロセスに変わります。必要な強度が不足する場合は常に、入手可能な最も安価なアップグレードを最初に選択する必要があります。各アップグレードは同じ利点をもたらしますが、コストが異なるためです。 私たちは、必要に応じて最小のコストを繰り返し選択できる構造で、目に見えるすべてのアップグレード コストを維持します。 

これは、プライオリティ キュー ベースの貪欲なソリューションにつながります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | サブセットに対するブルート フォース | O(2^n) | お(1) | 遅すぎる |
 | 利用可能なアップグレードを最小ヒープ内に維持する | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 1 日から n 日まで繰り返し、現在の強度と費やした総コストを追跡します。 また、現在までに利用可能なアップグレード コストの最小値も維持しています。 
2. 毎日 i に、アップグレード コスト C[i] をヒープに挿入します。これは、この時点から使用できるようになるためです。 
3. 現在の強さが X[i] 以上であるかどうかを確認します。 すでに存在している場合は、何もせずに続行します。 
4. 現在の強度が不十分な場合は、アップグレードを適用する必要があります。 各アップグレードは固定量 A だけ強度を増加させるため、X[i] に到達するために必要なアップグレードの数を計算します。 この数値は (X[i] - 強度 + A - 1) // A です。 
5. ヒープから最小コストのアップグレードを繰り返し抽出して適用し、強度と総コストを更新します。 必要な強度に達する前に山がなくなってしまうと、作業は不可能になります。 
6. このプロセスを一日中続け、先に進む前に必ず要件が満たされていることを確認します。 

中心となる考え方は、強度を高める必要があるときは常に、入手可能な最も安価なアップグレードを最初に選択する必要があるということです。なぜなら、すべてのアップグレードは将来の制約を満たすことに等しく貢献するからです。 

### なぜ効果があるのか

 いつでも、重要な唯一の決定は、利用可能なアップグレードのプレフィックスからいくつのアップグレードを取得するかということです。 各アップグレードでは同じ値 A が追加されるため、問題は、十分なサイズのアップグレードの最小コストのマルチセットを選択することになります。 利用可能な最小のコストを常に選択するという貪欲な選択により、同じ数のアップグレードを持つ他の選択のコストが低くなることはありません。選択したより高価なアップグレードを、より安価な未使用のアップグレードと交換することは決して実現可能性に違反することはないからです。 この交換引数は、ヒープ ベースの選択によってすべてのプレフィックス制約に対して最適なコストが生成されることを保証します。また、制約は時系列で処理されるため、初期の最適性がその後も有効であり続けます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    req = list(map(int, input().split()))
    A = int(input())
    cost = list(map(int, input().split()))

    cur = k
    ans = 0
    pq = []

    for i in range(n):
        heapq.heappush(pq, cost[i])

        if cur >= req[i]:
            continue

        need = req[i] - cur
        cnt = (need + A - 1) // A

        for _ in range(cnt):
            if not pq:
                print(-1)
                return
            c = heapq.heappop(pq)
            ans += c
            cur += A

    print(ans)

if __name__ == "__main__":
    solve()
```実装はウォークスルーを直接反映しています。 ヒープには、現在までに利用可能になったすべてのアップグレード コストが保存されます。 現状の戦力が足りない場合は、どれだけの強化が必要かを計算し、最も安価なものを抽出することを繰り返します。 

重要な詳細は、各アップグレードによって永続的に能力が向上し、必要な残りのアップグレードの数が減る可能性があるため、選択した各アップグレードの直後に強度が更新されるということです。 ループは、実行可能性を増加させることによって暗黙的に再計算します。`cur`。 

ここでよくある間違いは、必要なすべてのアップグレードを一度に計算し、抽出中にヒープの枯渇を確認せずに多くの要素を盲目的に取得することです。 コードはポップごとにヒープをチェックすることでこれを回避します。 

## 実用的な例

 ### 例 1

 入力:```
n = 5, k = 10000
req = [10000, 30000, 30000, 40000, 20000]
A = 20000
cost = [5, 2, 8, 3, 6]
```ヒープ、強度、コストを追跡します。 

| 日 | 挿入後のヒープ | 現在の強さ | 必須 | アクション | 総コスト |
 | --- | --- | --- | --- | --- | --- |
 | 1 | [5] | 10000 | 10000 | なし | 0 |
 | 2 | [2,5] | 10000 | 30000 | テイク 1 (コスト 2) | 2 |
 | 3 | [2,5,8] | 30000 | 30000 | なし | 2 |
 | 4 | [2,5,8,3] | 30000 | 40000 | テイク 1 (コスト 3) | 5 |
 | 5 | [2,5,8,3,6] | 50000 | 20000 | なし | 5 |

 4 日目以降、強度は十分に増加するため、後の制約が自動的に満たされます。 トレースは、アルゴリズムが高価なオプションの使用を遅らせ、常に最も安価な入手可能なアップグレードを選択することを示しています。 

### 例 2

 入力:```
n = 3, k = 10000
req = [10000, 40000, 30000]
A = 10000
cost = [5, 2, 8]
```| 日 | ヒープ | 強さ | 必須 | アクション | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | [5] | 10000 | 10000 | なし | わかりました |

 2 日目では、利用可能な両方のアップグレードを使用した後でも、強度は 30000 であり、まだ 40000 を下回っています。将来のアップグレードはまだ利用できないため、今後の情報は役に立ちません。 アルゴリズムは正しく -1 を出力します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | 毎日 1 つのコストがヒープに挿入され、各アップグレードは最大 1 回ポップされます。 
| スペース | O(n) | ヒープには利用可能なすべてのアップグレードが保存されます。 

ヒープ操作は対数のままであるため、ソリューションは n が 100,000 まで快適に拡張できます。

 ## 特殊なケース

 最初の要件がすでに初期強度よりも高いにもかかわらず、利用可能なアップグレードがまだない場合は、不足分を満たそうとするとヒープが空になるため処理され、即座に失敗が引き起こされます。 

初期に大きな要件があり、後で多くの安価なアップグレードが必要なケースは、アルゴリズムが将来のアップグレードを待たないため、正しく処理されます。 現在までにすでに明らかになっているもののみを使用するため、将来の可用性を誤って推測することはできません。 

ピーク後に要件が減少するケースは、強度が一度増加すると減少することはないため、自然に処理されます。そのため、将来のより小さな要件には追加の作業は必要なく、過去の決定に影響を与えることはありません。
