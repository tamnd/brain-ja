 ## 解決策
 ## 問題の理解

 各入力行は 1 つの日付を記述しますが、その構成要素の順序は区切り文字によって異なります。 ドットはヨーロッパ風の順序を意味します`day.month.year`、スラッシュはアメリカ式の順序を意味します`month/day/year`。 タスクは、その日付が実際の暦日であるかどうかを判断することではありません。 のようなものでも`31.02.2001`それでも変換して印刷する必要があります。 

すべての日付について、両方の表現を生成する必要があります。 最初のものは常に日、月、年の順序を持​​ち、ドットを使用します。 2 番目には常に月、日、年が含まれ、スラッシュが使用されます。 日と月はちょうど 2 桁である必要があり、年はちょうど 4 桁である必要があります。 入力の先頭のゼロは解析中に削除され、出力で必要な幅に復元されます。 

入力される日付は最大 20,000 件です。 各日付には 3 つの小さな数値フィールドしか含まれていないため、1 行に数個の文字列または整数を含むよりも複雑なデータ構造を使用する理由はありません。 各日付を 1 回処理するアルゴリズムは、十分に高速です。 この規模では、1 日あたりの追加作業が一定量であっても無視できます。 入力全体を保存せずに日付を個別に処理できるため、512 MB のメモリ制限も必要な量をはるかに超えています。 

最初の微妙なケースは、1 桁の年です。 例えば、```
1
1.2.1
```にならなければなりません```
01.02.0001 02/01/0001
```入力文字列を直接使用して不注意に実装すると、次のように出力される可能性があります。`01.02.1`入力では短い年が許可されますが、出力では常に 4 桁が必要になるためです。 

2 番目のエッジ ケースは、すでに埋め込まれている日付です。```
1
01.02.0001
```出力はまだです```
01.02.0001 02/01/0001
```変換では、誤って先頭のゼロを数値の一部として扱ったり、一貫性のない幅を生成したりしてはなりません。 

3 番目のケースは、無効な暦日です。```
1
29.02.2001
```必要な出力は次のとおりです```
29.02.2001 02/29/2001
```2001 年はうるう年ではありませんが、有効かどうかはタスクとは無関係です。 カレンダーの検証を追加すると、これまで尋ねられなかった問題が解決されます。 

4 番目のケースでは、通常の最大値が適用されます。```
1
31/12/9999
```結果は```
31.12.9999 12/31/9999
```ここで、区切り文字は元の順序を正しく決定する必要があり、年は特別な処理を行わずに 4 桁のままでなければなりません。 

## アプローチ

 意図的にブルートフォース解釈を行うと、3 つの解析されたコンポーネントが順序付けされていないコレクションとして扱われ、必要な形式に一致するまで可能な順序付けがすべて試行されます。 あるのは`3! = 6`したがって、20,000 の日付ごとに、最大 120,000 回の置換試行と書式設定作業が実行されます。 これらの制約に対してはまだ十分高速ですが、必要以上に難しい問題を解決することになり、コードがより複雑になります。 さらに重要なのは、区切り記号によって順序がすでに直接示されているため、検索するものが何もありません。 

3 つのフィールドの可能な配置が 6 つしかないため、総当たりアプローチは機能しますが、6 つの可能性すべてが不要であるため、エンジニアリングの選択としては失敗します。 入力セパレーターがフォーマットを一意に識別するという観察により、問題は 1 つの決定論的な分割と 1 つのスワップに縮小されます。 

ドット区切りの日付の場合、フィールドはすでに日、月、年の順序になっています。 スラッシュで区切られた日付の場合、最初の 2 つのフィールドは月と日なので、これらを交換するだけで済みます。 3 つのフィールドが日、月、年の順序になったら、書式設定は機械的に行われます。日と月は 2 文字に、年は 4 文字に埋められます。 

月の長さ、閏年、さらには結果の組み合わせが実際の日付であるかどうかを検証する必要もありません。 入力は、各コンポーネントが指定された数値範囲内にあることを保証し、出力は単にそれらのコンポーネントの正規化された表現です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(6n) = O(n) | お(1) | 受け入れられたが、不必要な作業 |
 | 最適 | O(n) | O(1) 補助スペース | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 1 つの日付文字列を読み取り、その区切り文字を検査します。 ドットはフィールドが日、月、年の順に並べられていることを意味し、スラッシュはフィールドが月、日、年の順に並べられていることを意味します。 区切り文字により、曖昧さのない形式が得られます。 
2. 文字列を 3 つのコンポーネントに分割します。 必要な変換はパディングだけであり、文字列は不必要な整数変換を避けるため、コンポーネントを文字列として保持します。 
3. 区切り文字がドットの場合、3 つのフィールドを直接割り当てます。`day`、`month`、 そして`year`。 区切り文字がスラッシュの場合、最初のフィールドを次のように割り当てます。`month`、2番目に`day`、そして3番目に`year`。 
4.パッド`day`そして`month`ちょうど 2 文字まで`year`ちょうど 4 文字まで。 桁数を手動でチェックするのではなくパディングすると、すでにパディングされた入力とパディングされていない入力の両方が均一に処理されます。 
5. ヨーロッパ表現を次のように構築します。`DD.MM.YYYY`。 
6. アメリカの表現を次のように構築します。`MM/DD/YYYY`。 
7. 2 つの表現を 1 つのスペースで区切って出力します。 各入力行は独立しているため、次の日付に対して同じ手順をすぐに繰り返すことができます。 

### なぜ効果があるのか

 ステップ 3 の後、3 つの変数は常に正規の順序で同じ論理日付を表します。`day`、`month`、`year`入力がどのように書かれたかに関係なく。 区切り記号によってどの割り当てが正しいかが決まるため、他の解釈はできません。 パディングは各コンポーネントのテキストの幅のみを変更し、その値は変更しません。 したがって、最初に構築された文字列では、常に正規コンポーネントが必要な幅で日-月-年の順序で配置され、2 番目の文字列では同じコンポーネントが月-日-年の順序で配置されます。 カレンダーの検証は必要ないため、許可された入力はすべて正しく処理されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    for _ in range(n):
        s = input().strip()

        if '.' in s:
            day, month, year = s.split('.')
        else:
            month, day, year = s.split('/')

        day = day.zfill(2)
        month = month.zfill(2)
        year = year.zfill(4)

        european = f"{day}.{month}.{year}"
        american = f"{month}/{day}/{year}"

        print(european, american)

if __name__ == "__main__":
    solve()
```セパレータ チェックは、アルゴリズムの最初の決定を実装します。 入力には許可されている 2 つの区切り文字のうちの 1 つが正確​​に含まれているため、`'.'`で十分です。 代替の大文字と小文字はスラッシュで区切る必要があります。 

2 つのブランチでの割り当て順序が、ソリューションの重要な部分です。 のために`11.12.2000`、分割すると生成される`["11", "12", "2000"]`、これはすでに日、月、年を意味します。 のために`1/29/3000`、分割すると生成される`["1", "29", "3000"]`、これは月、日、年を意味するため、最初の 2 つの変数は意図的に逆の順序で割り当てられます。`zfill`演算を行わずに、許可されたすべての幅を処理します。`zfill(2)`葉`"11"`変更されずに変換される`"1"`に`"01"`。 同様に、`zfill(4)`改宗する`"1"`に`"0001"`そして`"2100"`残る`"2100"`。 これにより、年は入力幅のままで、日と月だけがパディングされるという簡単な間違いも回避できます。 

実装では日付コンポーネントの算術演算が実行されないため、整数オーバーフローは発生しません。 また、日付が有効かどうかもチェックしませんが、無効な日付はフォーマットする必要があるため、これは正しいことです。

import sys
import io

def solve():
    input = sys.stdin.readline
    n = int(input())

    out = []

    for _ in range(n):
        s = input().strip()

        if '.' in s:
            day, month, year = s.split('.')
        else:
            month, day, year = s.split('/')

        day = day.zfill(2)
        month = month.zfill(2)
        year = year.zfill(4)

        out.append(f"{day}.{month}.{year} {month}/{day}/{year}")

    sys.stdout.write("\n".join(out))

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    try:
        sys.stdin = io.StringIO(inp)
        sys.stdout = io.StringIO()
        solve()
        return sys.stdout.getvalue()
    finally:
        sys.stdin = old_stdin
        sys.stdout = old_stdout

 ## 特殊なケース

 ### 1桁の年

 入力用```
1
1.2.1
```区切り文字はドットなので、コンポーネントは次のようになります。`day = "1"`、`month = "2"`、 そして`year = "1"`。 パディングにより生成される`01`、`02`、 そして`0001`。 したがって、2 つの出力は次のようになります。`01.02.0001`そして`02/01/0001`。 このアルゴリズムでは、入力された年にすでに 4 つの文字が含まれているとは想定されません。 

### すでに値が埋め込まれています

 のために```
1
01.02.0001
```分割により、すでに必要な幅を持つフィールドが生成されます。 電話をかける`zfill`何も追加しないので、`zfill`要求された幅以上の文字列を変更せずに残します。 出力は```
01.02.0001 02/01/0001
```これにより、正規化は正しくフォーマットされた入力に対して冪等になります。 

### カレンダーの日付が無効です

 のために```
1
29.02.2001
```アルゴリズムは 2 月の日数を検査しません。 単に解析するだけです`29`、`02`、 そして`2001`、それらを埋め込み、両方の表現を構築します。 結果は```
29.02.2001 02/29/2001
```日付が有効なグレゴリオ暦の日付ではない場合でも、これはまさに問題が必要とするものです。 

### スラッシュ区切りの入力

 のために```
1
1/29/3000
```区切り文字は`/`, したがって、パーサーは次のように割り当てます`month = "1"`、`day = "29"`、 そして`year = "3000"`。 パディング後の値は次のようになります。`01`、`29`、 そして`3000`。 ヨーロッパの形式は次のようになります。`29.01.3000`、一方、アメリカ式は次のようになります。`01/29/3000`。 このケースでは、スラッシュで区切られた入力が既に日-月-年の順序であるかのように処理される、最も可能性の高い解析エラーが検出されます。
