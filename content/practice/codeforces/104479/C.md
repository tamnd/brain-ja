 ## 解決策
 ## 問題の理解

 2 つのシーケンスが与えられ、畳み込みのように動作する新しいシーケンスを定義します。各位置`k`結果は、インデックスの合計が次の要素のペアの積をすべて合計することによって形成されます。`k`。 このタスクでは、この畳み込み全体を出力するように求められるのではなく、その畳み込みシーケンス内のすべての値の合計のみを出力するように求められます。 

したがって、インデックスの合計によってグループ化されたすべてのペアごとの寄与を計算する代わりに、すべてのポジションにわたるすべてのペアの合計寄与のみが必要になります。 

制約は大きく、各配列の要素は最大 100,000 個であり、ペアの二次列挙は即座に除外されます。 単純な二重ループでは、最悪の場合、最大 10^10 の乗算が生成されますが、これは時間制限をはるかに超えています。 

微妙なエッジ ケースは、値がゼロになる可能性があり、これは何も寄与せず、すべての寄与は独立していて加算的です。つまり、並べ替えやグループ化によって最終的な答えは変わりません。 

## アプローチ

 ブルートフォース解釈では、すべての値が計算されます。`c[k]`有効なすべてを反復処理することで明示的に`(i, j)`そのようなペア`i + j = k`。 これはすでにすべてのペアにわたる入れ子構造を暗示しています`(i, j)`2 つの配列で。 ごとに合計しても`k`、すべてのペア`(i, j)`は依然として 1 回だけ訪問されており、`O(nm)`プロセス。 これは大規模になると不可能になります。 

重要な観察は、最終的に必要な数量は、用語がどのようにグループ化されるかには依存しないということです。`k`。 すべての製品`a[i] * b[j]`全体で 1 回だけ表示されます`c[k]`、各ペアは 1 つのインデックスにのみ寄与するため、`k = i + j`。 したがって、すべての合計は、`c[k]`は、すべてのペアごとの積の単純な合計です。 

これにより、畳み込み構造が完全に崩壊します。 インデックスの合計について推論する代わりに、すべてのペアの積の合計を計算するだけで済みます。 式は因数分解するため、さらに単純化されます。 

の各要素`a`のすべての要素の合計を乗算します。`b`、その逆も同様です。 

したがって、最終的な答えは次のようになります。```
(sum of a) * (sum of b)
```これにより、問題は線形時間に短縮されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース ペアの列挙 | O(nm) | お(1) | 遅すぎる |
 | 和因数分解 | O(n + m) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 最初のシーケンスの合計を計算し、次に 2 番目のシーケンスの合計を計算します。 最後に、それらを掛け合わせます。 

1. 2 つの整数を読み取ります`n`そして`m`、配列の長さを示します。 
2. 配列の読み取り`a`そして計算する`sum_a`すべての要素を蓄積することによって。 
3. 配列の読み取り`b`そして計算する`sum_b`同様に。 
4. 出力`sum_a * sum_b`。 

重要な推論ステップは、畳み込みが合計に対して分散するため、畳み込みの総質量は入力シーケンスの総質量の積にすぎないことを認識することです。 

### なぜ効果があるのか

 すべてのペア`(i, j)`まさに貢献する`a[i] * b[j]`ちょうど 1 学期まで`c[i+j]`。 すべてを合計しているので、`c[k]`、最終的な答えでは、すべてのペアが 1 回だけカウントされます。 したがって、結果はすべてのペアの合計となり、これを独立した合計の積に因数分解します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    sum_a = sum(a)
    sum_b = sum(b)

    print(sum_a * sum_b)

if __name__ == "__main__":
    solve()
```このソリューションは両方の配列を線形時間で読み取り、それらの合計を累積します。 乗算は 1 回だけ行われるため、Python では通常の大きな整数の処理を超えてオーバーフローの問題が発生するリスクはありません。 重要な点は、畳み込みを明示的に構築しようとしないことです。これでは時間がかかりすぎます。 

## 実用的な例

 小さな例を考えてみましょう。 

入力:```
n = 3, m = 2
a = [1, 2, 3]
b = [4, 5]
```次のように計算します。 

| ステップ | 合計 | 合計_b | 実行状態 |
 | --- | --- | --- | --- |
 | |を読む 1 → 6 | - | 蓄積する |
 | bを読む | 6 | 4→9 | 蓄積する |
 | 最終 | 6 | 9 | 54 |

 畳み込み自体は複数の中間生成物を生成します。`c[k]`, しかし、それらを合計すると、すべてが 54 になります。 

2 番目の例:```
a = [0, 1, 2], b = [3, 0, 4]
```| ステップ | 合計 | 合計_b | 結果 |
 | --- | --- | --- | --- |
 | 合計を計算する | 3 | 7 | 21 |

 多くの畳み込み項がゼロまたは分布しているにもかかわらず、合計は 21 のままであり、ゼロと分布が全体和に影響を与えないことが確認されています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys as _sys
    from io import StringIO
    backup = _sys.stdin
    _sys.stdin = StringIO(inp)

    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    ans = sum(a) * sum(b)
    _sys.stdin = backup
    return str(ans)

 ## 特殊なケース

 1 つの配列にゼロのみが含まれている場合、すべての畳み込み項はゼロになり、その配列の合計がゼロになるため、アルゴリズムは正しくゼロを生成します。 両方の配列に単一の要素が含まれている場合、畳み込みは単一の積に折りたたまれ、定義と簡略化された式の両方に一致します。 配列が大きくても疎な場合、分布や疎性パターンではなく合計のみが重要となるため、計算は線形のままです。
