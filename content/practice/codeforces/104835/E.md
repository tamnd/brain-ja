 ## 解決策
 ## 問題の理解

 私たちの歯は円形に配置されており、一部の間隔は保定装置で覆われています。 これらの保持器は、円をいくつかの自由な円弧に分割します。 各フリー アークは、洗浄する必要がある歯の連続したセグメントです。 

それぞれの長さの円弧$L$は均一ではありません。概念的には 2 つの等しい層に分割されています。 1 つの層はつまようじの紐の端を使用して掃除する必要があり、もう 1 つの層は爪楊枝の端を使用して掃除する必要があります。 したがって、すべてのアークに対して、事実上 2 つの独立したクリーニング要件があります。$L/2$文字列容量の単位と$L/2$ピック容量の単位。 

1 本のつまようじを一連の連続する円弧 (時計回りまたは反時計回りに移動) に沿って使用できますが、リソースが限られた「セグメント クリーナー」のように動作します。 セグメント中に累積された文字列使用量が超過した場合$s$、または累計ピック使用量が超過$p$、つまようじは続行できないため、交換する必要があります。 重要なのは、セグメントが円弧の順序で連続している必要があり、つまようじでギャップの掃除を開始したら、切り替える前に完全に終了する必要があります。 

タスクは、円上の開始点を選択し、方向を選択し、各セグメントが両方の容量内に収まるように、一連の円弧を最小数の連続セグメントに分割することです。$s$そして$p$。 

制約$t, n \le 1000$ということを暗示します$O(n^2)$ソリューションは許容されますが、3 次のものは遅すぎます。 この構造は、すべての円弧を前処理し、線形化された円に対して貪欲または DP を使用する必要があることも示唆しています。 

いくつかの特殊なケースが重要です。 

単一の円弧がすでに超過している可能性があります$s$または$p$、素朴な定式化では答えを得ることが不可能になります。 たとえば、1 つの円弧の長さが 10 である場合、$s = p = 3$、そうすると爪楊枝では絶対に掃除できません。 正しいソリューションは、暗黙のうちに実現可能性を想定するか、差し迫った大きな要件として処理する必要があります。 

もう 1 つの微妙なケースは、最適解が円を「包み込む」場合です。 単純な線形ソリューションでは、最適なカット ポイントを見逃してしまいます。 たとえば、最適なセグメントが最後の円弧と最初の円弧の間の境界にまたがる場合、開始位置をインデックス 0 に固定すると、必要なつまようじの数が過大評価される可能性があります。 

## アプローチ

 この強引なアイデアは、開始アークを修正し、貪欲スキャンを使用してシミュレーションすることです。つまり、弦またはピックの容量を超えるまで現在のつまようじをできるだけ長く伸ばし、その後、新しいつまようじを開始します。 どちらのリソース使用量もセグメントを拡張するにつれて増加するだけであるため、これは固定線形順序で機能します。 各シミュレーションの費用$O(n)$、そしてすべてを試してみます$n$スターティングポジションのコスト$O(n^2)$、これは境界線にありますが、まだ実現可能です。 

ただし、循環的な性質が事態を複雑にします。 正しいカット ポイントは、自然なインデックス 0 ではない可能性があります。そのため、サイクル内のすべての可能な開始位置に対して同じ貪欲なプロセスをシミュレートする必要があります。 

重要な観察は単調性です。 開始インデックスを固定すると、1 本のつまようじを使用して到達可能な最も遠い終了インデックスは、開始を進めるにつれて前方にのみ移動します。 これにより、倍増配列上の 2 つのポインターを使用して「次のブレーク ポイント」を事前計算できます。 すべてのポジションについて、1 本のつまようじでどこまで移動できるかがわかったら、問題はこれらのインターバルをジャンプして、全サイクルをカバーするために何回ジャンプする必要があるかを数えることになります。 最後に、すべての開始位置を試して最小値を取得します。

 ## アルゴリズムのチュートリアル

 まず円を線形構造に変換します。 各自由弧$i$長さがある$L_i$、そして 2 つの重みを定義します。$a_i = L_i/2$文字列の使用と$b_i = L_i/2$ピックの使用に。 この配列を長さまで複製します$2n$したがって、円形セグメントを直線セグメントとしてシミュレートできます。 

1. 両方のプレフィックスの合計を計算します。$a_i$そして$b_i$。 これにより、任意のセグメントに対して定数時間の範囲クエリが可能になります。 
2. インデックスごとに$i$、最も遠いインデックスを計算します$r_i$セグメントが$[i, r_i]$両方の制約を満たします。$$\sum a \le s,\quad \sum b \le p$$これは 2 ポインタ手法を使用して行われます。有効なセグメントを拡張しても合計使用量が増加するだけであるため、前方にのみ移動するポインタを保持します。 
3. 各ポジションの治療$i$ジャンプ先のノードとして$r_i + 1$、つまようじ 1 本でカバーできることを意味します。$i$まで$r_i$両端を含むと、次のセグメントが始まります。 
4. 可能な開始位置ごとに$st \in [0, n-1]$、到達するまでに何回ジャンプする必要があるかをシミュレートします。$st + n$。 これは、その円弧から開始して前方にトラバースする場合に必要なつまようじの数を数えます。 
5. すべての開始位置で最小値を取得します。 

ステップ 4 のシミュレーションは、事前計算されたアルゴリズムを使用してジャンプを繰り返すことで効率的に実行できます。$r_i$、またはバイナリリフティングによって、ただし$n \le 1000$、単純な直線ジャンプで十分です。 

### なぜ効果があるのか

 各爪楊枝は、指定された位置から開始して掃除できる最大の連続する円弧ブロックを定義します。 どちらのリソース使用量も拡張に対して単調に増加するため、その開始点には貪欲な拡張が最適です。早期に停止しても役に立たず、容量を超えて拡張することは無効です。 したがって$r_i$明確かつ最大です。 

これらの最大範囲が固定されると、問題は事前に計算された間隔を使用してラインの最短カバーになります。 最適な円形ソリューションは、カット ポイントを選択し、円を線形化し、最大の有効な間隔で貪欲にカバーすることに対応します。 すべてのカットポイントで最小値を取ることで、最適なラップアラウンド構成を見逃さないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t, n = map(int, input().split())
    seg = []
    
    for _ in range(n):
        a, b = map(int, input().split())
        seg.append(b - a + 1)
    
    s = int(input())
    p = int(input())
    
    # each arc has equal split
    a = [x / 2 for x in seg]
    b = [x / 2 for x in seg]
    
    a = a + a
    b = b + b
    
    n2 = 2 * n
    
    # prefix sums
    pa = [0] * (n2 + 1)
    pb = [0] * (n2 + 1)
    
    for i in range(n2):
        pa[i+1] = pa[i] + a[i]
        pb[i+1] = pb[i] + b[i]
    
    r = [0] * n2
    j = 0
    
    for i in range(n2):
        if j < i:
            j = i
        while j < n2 and pa[j+1] - pa[i] <= s and pb[j+1] - pb[i] <= p:
            j += 1
        r[i] = j - 1
    
    INF = 10**9
    ans = INF
    
    for st in range(n):
        cnt = 0
        i = st
        limit = st + n
        
        while i < limit:
            cnt += 1
            i = r[i] + 1
            if i <= r[i-1]:  # safety, though usually unnecessary
                break
        
        ans = min(ans, cnt)
    
    print(ans)

if __name__ == "__main__":
    solve()
```コードはまず、各円弧を文字列とピックの使用法に分割された均一なコストに変換します。 次に、シーケンスを複製して、複雑なモジュラー演算を行わずに循環トラバーサルをシミュレートします。 プレフィックス合計を使用すると、候補セグメントが制約内に収まるかどうかを一定時間チェックできます。 

2 ポインター ループは、すべての開始インデックスに対して、両方の制約の下で同時に到達可能な最も遠いエンドポイントを構築します。 結果の配列$r[i]$最大の有効なセグメントをエンコードします。 

最後に、元の円内で考えられるすべての開始位置を試し、完全に 1 回転するまでこれらの事前計算された範囲を使用して貪欲にジャンプします。 

微妙な点は、配列を 2 倍にするとラップアラウンド条件を明示的に管理する必要がなくなることです。 重複がなければ、セグメントの有効性チェックにはモジュール式のプレフィックス合計が必要となり、正確性と実装の両方が複雑になります。 

## 実用的な例

 一定の長さの円弧を持つ小さな円を考えてみましょう$[4, 2, 6]$、および容量$s = p = 6$。 各アークは各リソースの半分を占めるため、重みは次のようになります。$[2,1,3]$。 

| ステップ | 開始 | 現在の i | r[i] | 次は | 使用されるセグメント |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | 2 | 3 | 1 |
 | 2 | 0 | 3 | 5 | 6 | 2 |

 0 から開始して、1 本のつまようじで円弧 0 ～ 2 をカバーし、次のつまようじで残りをカバーするため、答えは 2 です。 

ここで、貪欲な調整が悪化するシフトスタートについて考えてみましょう。 

| ステップ | 開始 | 現在の i | r[i] | 次は | 使用されるセグメント |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 1 | 1 | 3 | 4 | 1 |
 | 2 | 1 | 4 | 5 | 6 | 2 |

 これにより、開始点が異なるとセグメント数も異なる可能性があることが確認されており、すべての開始点を試行する必要があるのはこのためです。

 ## 特殊なケース

 重要なエッジ ケースは、最適なセグメンテーションが線形化されたアレイ内の人工的なカットと交差するときに発生します。 倍加戦略により、そのような構成が拡張配列内で連続した間隔として表示されることが保証されます。 すべての開始位置をテストすると、$[0, n)$、少なくとも 1 つの開始点が最適なカットと一致するため、貪欲なジャンプ シーケンスは真の最小セグメンテーションを再構築します。 

もう 1 つのエッジ ケースは、単一のアークが容量を使い果たしそうになる場合です。 その状況では、貪欲な拡張はその円弧ですぐに停止し、長さ 1 のセグメントが生成されます。 なぜなら$r[i]$は純粋に実現可能性によって計算されるため、アルゴリズムは特別な処理を行わずにそのようなアークを自然に分離します。
