 ## 解決策
 ## 問題の理解

 与えられたグリッドには、各セルが限られた回数の踏み込みに耐えられるバクラヴァの一部が表されています。 すべての友達は左上隅から開始し、一度に 1 つのセルを 4 つの基本方向に移動して右下隅に到達しようとします。 友達がセルを踏むたびに、そのセルの耐久性が 1 つ減少します。 2 つのセルは特別です。開始部分と終了部分は破壊できないため、制限なく何度でも使用できます。 

問題は単一のパスを見つけることではなく、同じグリッドを繰り返し使用することです。 各フレンドは独立して歩きますが、全員が共有セルの耐久性を集合的に消費します。 グリッドを横切ることができなくなる前に、最初から最後まで成功する横断の最大数が必要です。 

重要な制約は、両方のディメンションが最大 100 であるのに対し、耐久性の値は 100000 までであるということです。パスあたり 100000 のパスに最大 10000 のセルを掛けても制限をはるかに超えているため、これにより、友人ごとのシミュレーションは即座に除外されます。 有効なソリューションでは、パスを 1 つずつシミュレートするのではなく、暗黙的に処理する必要があります。 

多くの場合失敗する素朴な解釈は、各友人が常に同じ最短経路をたどると仮定することです。 代替のより長いルートがまだ存在する可能性があるにもかかわらず、数回の横断の後、その最短パスがブロックされるため、この問題はすぐに壊れます。 たとえば、単一の狭い廊下が始点と終点を接続している場合、グリッドの残りの部分が触れられていない場合でも、それを繰り返し使用すると消耗しますが、構造によっては再ルートが可能な場合と不可能な場合があります。 したがって、貪欲な「常に最短パスを再利用する」アプローチは、結合構造に応じて過小評価または過大評価されます。 

もう 1 つの微妙な失敗例は、複数の独立したパスが存在する場合に発生します。 1 つのパスのみを追跡する単純な方法では、グリッド全体のフローの再配分が無視されるため、共有エッジの使用状況を正しく考慮できません。 

## アプローチ

 重要な観察は、これは最短経路の問題ではなく、グリッド上の流量の問題であるということです。 各セル (開始と終了を除く) は、その耐久性に等しい容量を持つノードのように動作し、各走査は選択されたルートに沿って 1 単位の容量を消費します。 容量がなくなる前に送信できる開始から終了までのパスの数を最大化したいと考えています。 

これはまさに最大フローの問題ですが、エッジ容量ではなくノード容量が問題になります。 標準的な変換では、各セルを 2 つのノードに分割することにより、ノード容量をエッジ容量に変換します。つまり、容量がセルの耐久性に等しいエッジによって接続された「イン」ノードと「アウト」ノードです。 隣接するセル間の移動は、1 つのセルの「アウト」ノードから、無限の容量を持つ隣接セルの「イン」ノードまでのエッジになります。 

変換すると、問題はソース (開始セル) からシンク (終了セル) までの最大フローを計算することになります。 フローの各ユニットは、グリッドを正常に横断する 1 人の友人に対応し、各フロー ユニットは、使用するすべての中間ノードに沿って正確に 1 ユニットの耐久性を消費します。 

ブルートフォースアプローチでは、各友人のパスをシミュレートし、残りのグリッドで有効なパスを繰り返し見つけて、容量を減らします。 最悪の場合、各パス検索は O(NM) であり、これをすべての容量の合計 (場合によっては 100000) まで繰り返す可能性があり、約 10^9 ～ 10^10 の操作が必要になります。 それは遅すぎます。 

フローの定式化は、繰り返しのパス検索を、残余ネットワーク内の拡張パスを使用して効率的にフローを推進するグローバル最適化に置き換えます。 Dinic のアルゴリズムは、グラフが比較的小さく (分割後のノード数が約 10,000 まで)、エッジ構造が格子状であるため、適しています。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(F · NM) ただし、F ≤ 100000 | O(NM) | 遅すぎる |
 | マックスフロー (ディニック) | O(E √V) は、グリッド状のグラフに一般的 | お(え) | 承認済み |

 ## アルゴリズムのチュートリアル

 グリッドをフロー ネットワークに変換し、ソースからシンクまでの最大フローを計算します。 

1. 各セル (i, j) を 2 つのノード (入口ノードと出口ノード) に分割します。 入口→出口を K[i][j] に等しい容量で接続します。 これは、セルを踏むと耐久性が消費され、フローの各単位がその容量の 1 単位を消費するという事実をモデル化しています。 開始セルと終了セルは無限の容量を持つものとして扱われるため、それらの内部エッジには非常に大きな値が与えられます。 
2. グリッド内の隣接するセルのペアごとに、1 つのセルの出口ノードから無限の容量を持つ隣接セルの入口ノードまで有向エッジを追加します。 これにより、ノードの容量を除いて制限なく移動できます。 
3. ソースを (0, 0) の入口ノードとして定義し、シンクを (N-1, M-1) の出口ノードとして定義します。 ソースからシンクへの流れは、1 人の友人がトラバースを正常に完了することに対応します。 
4. Dinic のアルゴリズムを実行して、このネットワーク内の最大フローを計算します。 各拡張は、残りの耐久性を考慮したグリッドを通る 1 つの実行可能な完全なパスに対応します。 
5. 総流量を答えとして返します。 

機能する理由: すべての有効なウォークは、一連のノード容量エッジを通過するフローの単位に対応します。 各セルの容量はその分割エッジで強制されるため、そのセルを通過できる合計フロー ユニットは K[i][j] 個を超えません。 逆に、実行可能なフローはすべて、ソースからシンクまでのパスに分解でき、それぞれが有効なフレンド トラバーサルを表します。 これにより、有効な行程とフロー単位の間に 1 対 1 の対応が確立されるため、フローを最大化すると友人の数が正確に最大化されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

class Dinic:
    def __init__(self, n):
        self.n = n
        self.adj = [[] for _ in range(n)]

    def add_edge(self, u, v, c):
        self.adj[u].append([v, c, len(self.adj[v])])
        self.adj[v].append([u, 0, len(self.adj[u]) - 1])

    def bfs(self, s, t):
        self.level = [-1] * self.n
        q = deque([s])
        self.level[s] = 0
        while q:
            u = q.popleft()
            for v, c, rev in self.adj[u]:
                if c > 0 and self.level[v] < 0:
                    self.level[v] = self.level[u] + 1
                    q.append(v)
        return self.level[t] >= 0

    def dfs(self, u, t, f):
        if u == t:
            return f
        for i in range(self.it[u], len(self.adj[u])):
            self.it[u] = i
            v, c, rev = self.adj[u][i]
            if c > 0 and self.level[v] == self.level[u] + 1:
                pushed = self.dfs(v, t, min(f, c))
                if pushed:
                    self.adj[u][i][1] -= pushed
                    self.adj[v][rev][1] += pushed
                    return pushed
        return 0

    def max_flow(self, s, t):
        flow = 0
        INF = 10**18
        while self.bfs(s, t):
            self.it = [0] * self.n
            while True:
                pushed = self.dfs(s, t, INF)
                if not pushed:
                    break
                flow += pushed
        return flow

def node_id(i, j, m):
    return i * m + j

def solve():
    n, m = map(int, input().split())
    grid = [list(map(int, input().split())) for _ in range(n)]

    N = n * m * 2 + 5
    dinic = Dinic(N)

    INF = 10**18

    def in_id(i, j):
        return node_id(i, j, m)

    def out_id(i, j):
        return node_id(i, j, m) + n * m

    for i in range(n):
        for j in range(m):
            cap = grid[i][j]
            u = in_id(i, j)
            v = out_id(i, j)
            if (i, j) in [(0, 0), (n - 1, m - 1)]:
                dinic.add_edge(u, v, INF)
            else:
                dinic.add_edge(u, v, cap)

    for i in range(n):
        for j in range(m):
            for di, dj in [(1, 0), (-1, 0), (0, 1), (0, -1)]:
                ni, nj = i + di, j + dj
                if 0 <= ni < n and 0 <= nj < m:
                    dinic.add_edge(out_id(i, j), in_id(ni, nj), INF)

    s = in_id(0, 0)
    t = out_id(n - 1, m - 1)

    print(dinic.max_flow(s, t))

if __name__ == "__main__":
    solve()
```実装は分割ノード構造に直接続きます。 各セルは 2 つのインデックスで表され、内部エッジにより耐久性が強化されます。 移動エッジは方向付けされていますが、隣接関係の列挙によって両方向が追加されるため、効果的には双方向に動作します。 

よくある実装の落とし穴は、開始セルと終了セルに無限の容量を割り当てるのを忘れることです。 それらが制約されている場合、たとえ問題によって耐久性の制約が明示的に取り除かれていたとしても、流れは人為的に制限されます。 

もう 1 つの微妙な点は、ノードのインデックス付けです。 各グリッド セルは 2 つのノードに拡張されるため、合計ノード数は 2 倍になります。 ノード内インデックスとノード外インデックスを誤って混合することが、この変換における誤った答えの最も一般的な原因です。

 入力:```
2 2

```グリッドを解釈すると、開始と終了が自由であるため、中央の 2 つのセルのみが重要であることがわかります。 

フロー ネットワークには次のような能力があります。 

- (0,1) は 1000
 - (1,0) は 2000 です

 移動エッジは無制限です。 

ボトルネックの 1 つが飽和するまで、両方のパスに流れを押し込みます。 制限要因は、開始と終了を分けるカット全体の利用可能な容量の合計であり、その合計は 3000 になります。 

| ステップ | アクティブパス | ボトルネック | 総フロー |
 | --- | --- | --- | --- |
 | 1 | (0,0)->(0,1)->(1,1) | 1000 | 1000 |
 | 2 | (0,0)->(1,0)->(1,1) | 2000年 | 3000 |

 この表は、両方の利用可能なコリドーが枯渇するまでフローが両方のコリドーに分散されることを示しています。

 ## 特殊なケース

 重要なエッジ ケースは、唯一の有効なルートが異なるパスでセルを複数回再訪問する必要がある場合です。 キャパシティは単一のパスではなく全体の使用量に関連付けられるため、フロー モデルはこれを自然に処理します。 

考慮する：```
2 3
0 1 1
1 1 0
```中央のセルは共有構造を形成します。 単純な、友人ごとの最短パスのアプローチでは、同じルートが繰り返し使用され、数回の反復後に失敗します。 代わりに、フロー ソリューションは、各セルの容量が完全に消費されるまで使用量を分散し、考えられるすべての走査を正確にカウントします。 

もう 1 つのエッジ ケースは、同様に最適なコリドーが複数存在する場合です。 貪欲なパス選択は 1 つのコリドーを早期に飽和させる可能性がありますが、フローの定式化により、パスを増強することで単一のルートにコミットするのではなく、残りのキャパシティを動的に探索するため、両方が最適に使用されることが保証されます。
