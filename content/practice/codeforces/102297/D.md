 ## 解決策
 ## 問題の理解

 一連の販売日を設けております。 日 (i) には、ちょうど (c_i) 個のカップがリクエストされます。 カップごとにレモン x 個と砂糖 s オンスが消費されます。 レモンは個別に購入できますが、砂糖は 5 ポンドの袋でのみ販売されています。 1 ポンドには 16 オンスが含まれるため、1 つの砂糖袋にはちょうど 80 オンスが含まれます。 

どちらの食材も、その日の顧客が到着する前の午前中に購入でき、未使用の在庫は後日入手可能です。 レモンの価格と砂糖袋の価格は日々変化する可能性があります。 私たちは全体の流れを事前に知っており、資本も無限にあるので、唯一の問題は、いつ、いくらで購入するかです。 

各テスト ケースの出力は、毎日の需要に十分な量のレモンと砂糖を購入するために必要な最小合計セント数です。 

(d\le1000) であるため、制約は (O(d^2)) であっても問題なく適合するほど十分に小さいですが、構造により (O(d)) の解が可能になります。 テスト ケースは最大 100 個あるため、(O(d^2)) アプローチは、理論上の最大値で約 (100\times1000^2=10^8) 回の内部ループ反復を実行できますが、これは Python の制限に不必要に近い値です。 リニアスキャンの方がはるかに安全です。 公式 Codeforces アーカイブには、1 秒の時間制限と 256 MB のメモリ制限が記載されています。 

最初の微妙なケースは、砂糖が袋単位で販売されていることです。 考慮する```
1
1 1 10
1 1 7
```1 カップには 10 オンスの砂糖が必要なので、80 オンスの袋が 1 つ必要になります。 レモンの価格は 1 セント、砂糖袋のコストは 7 セントなので、答えは 8 になります。必要な 10 オンスに袋の価格を掛ける不注意な解決策では 71 セントが生成されますが、変換後に毎日の需要を個別に四捨五入する解決策では、未使用の 70 オンスを誤って処理する可能性もあります。 

2 つ目のエッジケースは、数日が一緒になっても 1 つの砂糖袋に収まる場合に発生します。 考慮する```
1
2 1 10
1 10 100
7 20 99
```1 日目には 10 オンス、2 日目には 70 オンスが必要なので、合計でちょうど 80 オンスが必要になります。 1日目に買った1袋で両日使えて、レモンが10セント、砂糖が100セント、合計110セントになります。 毎日の砂糖必要量を個別に四捨五入するソリューションでは、2 つの袋を購入すると、代わりに 209 セントが得られます。 

3つ目は、後から安い価格が現れた場合です。 考慮する```
1
2 1 1
1 50 500
80 1 1
```初日は、レモン 1 袋と砂糖 1 袋を初日の価格で購入することを強制されます。 2 日目には、追加の要件に対してより安価な料金を使用できます。 答えは631セントです。 将来に比べて初日が安いという理由だけで早めに複数のバッグを購入する戦略は、待つことが許可され、後の価格はさらに安くなる可能性があるという事実を見逃してしまいます。 

## アプローチ

 直接的なブルートフォース ソリューションでは、考えられるすべての購入スケジュールを列挙できます。 砂糖の場合、(B) を 1 日を通して必要な袋の合計数とします。 すべての袋は原則として (d) 購入日の 1 つに割り当てることができ、その後、結果として得られたスケジュールに毎日十分な砂糖が含まれているかどうかを確認し、そのコストを計算します。 割り当ての総数は最大で (d^B) です。 総需要は (1000\cdot1000\cdot10=10^7) オンスに達する可能性があるため、(B) は (\lceil10^7/80\rceil=125000) に達する可能性があります。 (d=1000) の場合、砂糖だけに対して最大 (1000^{125000}) の割り当てが行われます。 この総当り攻撃は、すべての法的スケジュールを明示的に考慮するため、正しいのですが、最大の制約が適用されるずっと前に役に立たなくなります。 

有益な観察は、同じ成分の供給品は交換可能であるということです。 レモンに関しては、包装制限は全くありません。 日 (i) に (q_i=c_i x) 個の新しいレモンが必要だとします。 これらの特定の (q_i) レモンは、遅くとも (i) 日までに購入されている必要があるため、それぞれの可能な限り最も安い価格は、単純に (1) から (i) 日までのレモンの最小価格になります。 その最低価格が設定されている早い日に購入できます。 

砂糖は袋の容量が 80 であることを除いてほぼ同じです。(S_i) を 1 日 (i) までに必要な総オンス数とします。 一日（i）の始まりまでに、少なくとも

 [
 B_i=\left\lceil\frac{S_i}{80}\right\rceil
 】

 バッグは購入済みである必要があります。 前日には、(B_{i-1}) 個のバッグだけが強制されました。 したがって、正確に (B_i-B_{i-1}) 個の追加のバッグが (i) 日に必要になります。 これらの袋はいずれも 1 から (i) までの任意の日に購入できるため、最も安い価格がこれまでに確認された砂糖袋の最低価格となります。 

重要な点は、毎日の砂糖需要を個別に四捨五入しないことです。 累積需要を四捨五入します。 これは、バッグの未使用のオンスが後の日に持ち越されるという事実を捉えています。 

2 つの成分は独立しているため、1 回のスキャンで同時に処理できます。 レモンの場合は、その日に必要なレモンの数に、これまでに確認された最も安いレモンの価格を掛けたものを加算します。 砂糖の場合、累積オンスを更新し、新しく必要な袋数を計算し、これまでに確認された最も安い砂糖価格で新しく必要な袋のみに請求します。

 | ブルートフォース | (O(d^B)) 砂糖の場合 | (O(B)) | 遅すぎる |
 | 最適 | (O(d)) | (O(1)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. レモンの最小価格とシュガーバッグの最小価格を、考えられるすべての入力価格よりも大きい値に初期化します。 また、累積砂糖需要とすでに必要な砂糖袋の数をゼロに初期化します。 
2. 一度に 1 日ずつ読みます。 日 (i) では、レモンの最低価格を日 (1) から (i) までの中で最も安いレモンの価格に更新し、砂糖袋についても同じことを行います。 (i) 日に必要な供給品は、それより前の日に購入されている可能性があるため、これらの接頭辞の最小値は、法定の最低購入価格を表します。 
3. この日に必要な新しいレモンの数を (c_i x) として計算します。 その量に現在のレモンの最低価格を掛けて、答えに加えます。 レモンは個別の単位であるため、四捨五入や在庫状態の複雑さはありません。 
4. 累積糖需要量に (c_i s) を加算します。 その累積量を次を使用してバッグの最小数に変換します。 
[
 B_i=\left\lceil\frac{S_i}{80}\right\rceil。 
】
 整数演算ではこれは`(S_i + 79) // 80`。 
5. コンピューティング`new_bags = B_i - B_previous`。 これらの新たに必要なバッグだけがコストを増加させます。 これらにこれまでに確認された砂糖袋の最安値を掛けて、その金額を答えに加えます。 
6. (B_i) を前のバッグ数として保存し、翌日に継続します。 最終日以降、累積された答えがテスト ケース全体の最小コストとなります。 

### なぜ効果があるのか

 レモンの場合、(i) 日に新しく必要になったレモンはすべて、(i) 日までに購入する必要があり、それより前の購入日はすべて数量に制限がありません。 したがって、その最小可能価格は、まさに (i) で終わる接頭語の最小レモン価格です。 必要な数をその価格で購入するのが実現可能かつ最適です。 

砂糖の場合、(i) 日目以降の総需要は (S_i) オンスであるため、実行可能なすべてのスケジュールでは少なくとも (\lceil S_i/80\rceil) 個の袋を所有する必要があります。 差 (B_i-B_{i-1}) は、実行可能なスケジュールが日 (i) までに取得する必要がある追加の手荷物の数とまったく同じです。 このような袋はそれぞれ、プレフィックス内のいつでも購入できるため、可能な限り最も安いコストはプレフィックスの最低砂糖価格となります。 供給は繰り越され、保管は無制限であるため、その最小限に達する日にこれらのバッグを購入することは実現可能です。 その結果、すべての有料手荷物には法的に利用可能な最低価格が適用されますが、必要なすべての手荷物には 1 回だけ料金が請求されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**30
BAG_OUNCES = 80

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        d, x, s = map(int, input().split())

        min_lemon_price = INF
        min_sugar_price = INF

        cumulative_sugar = 0
        previous_bags = 0
        answer = 0

        for _ in range(d):
            c, pl, ps = map(int, input().split())

            min_lemon_price = min(min_lemon_price, pl)
            min_sugar_price = min(min_sugar_price, ps)

            lemons_needed = c * x
            answer += lemons_needed * min_lemon_price

            cumulative_sugar += c * s
            required_bags = (cumulative_sugar + BAG_OUNCES - 1) // BAG_OUNCES

            new_bags = required_bags - previous_bags
            answer += new_bags * min_sugar_price

            previous_bags = required_bags

        out.append(str(answer))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```入力ループは反復ごとにちょうど 1 日処理するため、アルゴリズムがシーケンス全体を保存する必要はありません。`min_lemon_price`そして`min_sugar_price`現在利用可能な最も安い購入機会を表します。 

レモンの計算では、`c * x`すべてのカップが正確に消費されるため、`x`個々のレモン。 残ったレモンを個別に追跡する理由はありません。 前日に安く購入されたレモンはそのまま入手可能であり、プレフィックス最小の議論はすでにそれを説明しています。 

砂糖に関しては、`cumulative_sugar`重大な状態です。 表現`(cumulative_sugar + 79) // 80`80 による上限除算を実行します。`c * s`部分的に使用されたバッグは後の需要を満たすことができるため、四捨五入計算に直接使用するのは不正確です。`new_bags`現在の累積要件と以前の累積要件の差です。 これにより、未使用の砂糖がすでに入手可能な袋に対して再度料金を請求することがなくなります。 80 の倍数も正確に処理します。 累積需要が 79 オンスから 80 オンスに変化しても、必要な袋の数は 1 つにとどまるため、新しい袋は購入されません。 

Python の整数には任意の精度があるため、可能な限り最大の総コストであってもオーバーフローすることなく処理されます。 最大値は実際のメモリ問題をはるかに下回っており、アルゴリズムは一定数の整変数のみを保持します。
