 ## 解決策
 ## 問題の理解

 バス停の固定された順序リストを持つバス ルートが与えられます。 乗客はバスの乗車中に観察した一連の停車場所を報告しますが、問題が発生します。バスがルートの順方向に走行している場合もあれば、逆方向に走行している場合もあるということです。 

タスクは、観察された停止シーケンスがルートに沿った前進、ルートに沿った後進、またはその両方と一致するかどうか、またはどちらでもないかを判断することです。 両方の方向でまったく同じ観測シーケンスが生成される場合、方向を決定することはできず、答えは曖昧であると考えられます。 

より具体的に言うと、ルートを配列として考えます。`route[0..n-1]`。 観測されたシーケンスは別の配列です`obs[0..k-1]`。 かどうかを確認しています。`obs`順方向の連続した走査としてルートを正確に照合するか、逆方向の連続した走査として正確にルートを照合します。 

出力は、これら 2 つの可能性に基づいた観測の分類です。 

問題文は非常に短いですが、重要な隠された構造は、パスやグラフのような複雑なものを再構築していないということです。 1 つのシーケンスを 2 つの決定的な参照シーケンス (ルート自体とその逆バージョン) に対して比較しているだけです。 

比較は線形であるため、制約は暗黙的に次のことを示唆しています。`n`そして`k`十分に大きいため、二次スキャンまたは繰り返しスキャンのアプローチでは遅すぎる可能性があります。 したがって、どのソリューションでもシーケンスを線形時間で比較する必要があります。 

いくつかの特殊なケースを強調する価値があります。 

観察されたシーケンスが順方向ルートと逆方向ルートの両方と同一である場合、これはルートの長さが 0 または 1 であるか、すべての要素が同一である場合にのみ発生します。 その場合、正解は「わからない」です。 

観察されたシーケンスが部分的であってもどちらの方向にも一致しない場合、完全なシーケンスの同一性ではなくプレフィックスの同一性のみをチェックする単純な部分文字列チェックでは、誤って一致が結論付けられる可能性があります。 たとえば、ルート`[1,2,3,4]`そして観察`[1,2,4]`は、ルートの初期部分と一致しても、どちらの方向にも無効です。 

もう 1 つの微妙なケースは、逆ルートは正確に一致するが、順方向ルートは一致しない場合です。 一方向のみをチェックする、または対称性を前提とする不注意な実装は、これを誤って分類する可能性があります。 

## アプローチ

 ブルート フォースのアイデアは簡単です。ルートの可能な両方の通過 (順方向と逆順) を生成し、それぞれを観察されたシーケンスと比較します。 

各方向について、両方の配列を要素ごとにスキャンします。 すべての要素が一致し、長さが等しい場合、その方向は有効です。 これは正しいです。有効な走査では順序と値の両方が正確に保持される必要があるからです。 

ただし、それぞれの比較が線形であっても、単純な実装では逆配列を繰り返し再計算したり、複数のテスト ケースに対して冗長スキャンを実行したりする可能性があります。 多くのテスト ケースまたは大きな入力がある場合、メモリ割り当ての繰り返しや不必要な作業により非効率になる可能性があります。 

重要な点は、反転配列を明示的に構築する必要がないということです。 比較中に逆の順序で元の配列に直接インデックスを付けることができます。 これによりオーバーヘッドが削減され、時間とメモリの両方においてソリューションが純粋に線形に保たれます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (両方の配列の構築と比較) | O(n + k) | O(n) | 受け入れられるが非効率的 |
 | 最適 (インデックスベースの比較) | O(n + k) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ルートと観測されたシーケンスがすでにわかっていると仮定して、プロセスを説明します。 

### 1. ルートと観察されたシーケンスを読む

 ルートを配列に保存し、観測されたシーケンスを別の配列に保存します。 これが必要なのは、前方比較と逆比較の両方でインデックスによる直接アクセスが必要なためです。 

### 2. 順方向の有効性を確認する

 まず、観測されたシーケンスが順方向にルートと一致するかどうかを確認します。 不一致があると直ちに等価性が排除されるため、最初に長さを比較します。 次に、インデックスごとにスキャンして同等性を検証します。 

順方向トラバーサルは変更を加えずにルート配列に正確に対応するため、この手順は正しいです。 

### 3. 逆方向の有効性を確認する

 同じ比較を繰り返しますが、比較するのではなく、`route[i]`、比較します`route[n - 1 - i]`。 これは、反転配列を構築せずに、ルートを逆方向に歩くことをシミュレートします。 

これにより、正確性を維持しながら、余分なメモリ割り当てが回避されます。 

### 4. 結果を結合する

 順方向比較と逆方向比較の両方が有効な場合、次のように出力されます。`Unsure`。 forward のみが有効な場合は、次のように出力します。`Forward`。 reverse のみが有効な場合は、次のように出力します。`Reverse`。 それ以外の場合、シーケンスは無効です。 

### なぜ効果があるのか

 この正しさは、ルートが方向に応じて 2 つの可能な決定的な停留所のシーケンスを正確に定義しているという事実から得られます。 有効な観測値は、これら 2 つのシーケンスのいずれかに正確に一致する必要があります。 要素ごとに両方向で比較するため、考えられる両方のグランドトゥルースに対して等価性をチェックしています。 両方向が同一のシーケンスを生成する対称の場合以外には、曖昧さはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check_equal(a, b):
    if len(a) != len(b):
        return False
    for i in range(len(a)):
        if a[i] != b[i]:
            return False
    return True

def check_reverse(route, obs):
    n = len(route)
    k = len(obs)
    if n != k:
        return False
    for i in range(n):
        if route[n - 1 - i] != obs[i]:
            return False
    return True

def solve():
    data = list(map(int, input().split()))
    n = data[0]
    route = data[1:1+n]

    k = int(input())
    obs = list(map(int, input().split()))

    forward = check_equal(route, obs)
    backward = check_reverse(route, obs)

    if forward and backward:
        print("Unsure")
    elif forward:
        print("Forward")
    elif backward:
        print("Reverse")
    else:
        print("Impossible")

if __name__ == "__main__":
    solve()
```この実装では、順方向チェックと逆方向チェックが明確なヘルパー関数に分離されます。 前方チェックは直接等価スキャンです。 逆方向チェックでは、逆方向の配列の構築が回避され、代わりにルートの末尾からインデックスが作成されます。これにより、クリーンかつメモリ効率が向上します。 

微妙な点は、常に最初に長さを確認することです。 これにより、プレフィックスは一致するが完全なシーケンスは一致しないという偶発的な部分比較が防止されます。 

## 実用的な例

 ### 例 1

 ルートは`[1, 2, 3, 4]`、観察されたのは`[1, 2, 3, 4]`。 

| 私 | ルート[i] | 観測[i] | 一致 |
 | --- | --- | --- | --- |
 | 0 | 1 | 1 | はい |
 | 1 | 2 | 2 | はい |
 | 2 | 3 | 3 | はい |
 | 3 | 4 | 4 | はい |

 前方チェックはパスします。 逆方向チェックは失敗します。 出力は`Forward`。 

これにより、アルゴリズムがルートとの直接の位置合わせを正しく識別していることが確認されます。 

### 例 2

 ルートは`[1, 2, 3, 4]`、観察されたのは`[4, 3, 2, 1]`。 

| 私 | ルート[n-1-i] | 観測[i] | 一致 |
 | --- | --- | --- | --- |
 | 0 | 4 | 4 | はい |
 | 1 | 3 | 3 | はい |
 | 2 | 2 | 2 | はい |
 | 3 | 1 | 1 | はい |

 リバースチェックパス。 前方チェックが失敗します。 出力は`Reverse`。 

これは、逆方向のトラバースが正しく検出されたことを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべてのルート要素が同一である場合です。 たとえば、ルート`[5,5,5,5]`そして観察`[5,5,5,5]`順方向チェックと逆方向チェックの両方を同時に通過させます。 アルゴリズムは正しく出力します`Unsure`なぜなら、方向情報は本質的に失われるからです。 

もう 1 つの特殊なケースは、長さの不一致です。 観察されたシーケンスの長さがルートと異なる場合、前方比較も逆比較も成功しません。 アルゴリズムは両方のチェックの早い段階で拒否し、偶発的な部分一致を防ぎます。 

最後のエッジケースは、最小入力サイズです。 ルートに要素が 1 つだけある場合、両方の方向は定義上同一です。 このアルゴリズムは、一致する単一要素の観測値を次のように正しく分類します。`Unsure`一致する場合、または`Impossible`さもないと。
