 ## 問題の理解

 アランは決められたスケジュールに従ってジムに通います$N$日々。 当日$i$、彼は正確に持ち上げなければなりません$X[i]$グラム、そして彼は基本的な強さから始めます$K$。 彼はジムを訪れた日にトレーニング前のドリンクを購入することで、永久的に筋力を増強することができます。 飲み物を飲むたびに体力が一定量増加します$A$、料金はその日のジムによって異なります。$C[i]$。 彼は複数の飲み物を購入するかもしれませんが、それぞれの購入はその日のジムに関連付けられており、同じ筋力向上に貢献します。 

制約は一時的なものです。日によっては飲み物を買った場合、その日以降はその増大した体力に頼ることしかできません。 タスクは、毎日飲み物を購入する日を選択することです。$i$、彼の蓄積された強さは少なくとも$X[i]$総コストを最小限に抑えながら。 全部飲んでも無理なら答えは-1。 

制約は次のとおりです$N = 10^5$これにより、購入決定のサブセットに対する二次列挙が即座に除外されます。 有効なソリューションでは、通常、ヒープまたは並べ替えベースの構造による貪欲な選択を使用して、日を線形または線形に近い時間で処理する必要があります。 

微妙な失敗例は、初期には高い強度が必要であるが、高価な飲み物が初期に存在し、安価な飲み物が後に存在する場合に発生します。 現在の体力が不十分なときにいつでも貪欲に購入するという単純な戦略は、将来のより安価な機会を待つ代わりに、高価な初期購入に固定される可能性があるため、失敗する可能性があります。 

毎日飲み物を買うだけでも不十分な場合、別の特殊なケースが発生します。 たとえば、次の場合$K + N \cdot A < \max X[i]$の場合、どの戦略も要件を満たすことはできませんが、不注意な実装は依然としてシミュレーションを試みてオーバーフローしたり、誤った動作をしたりする可能性があります。 

## アプローチ

 直接的な強引なアプローチでは、飲み物を買うか買わないかを毎日検討します。 購入するたびに強度が永続的に増加するため、これはサブセットの選択の問題になります。$N$日々、与える$2^N$可能性。 実現可能性による枝刈りでも、それぞれの決定が将来のすべての制約に影響を与えるため、依然として指数関数的な分岐が残ります。 

重要な観察は、飲み物を買うのは、いつか失敗しないようにするためにのみ重要であるということです。 当日なら$i$、現在の強さでは不十分です。$X[i]$であれば、その前かその時に十分な飲み物を買ったはずです。$i$。 問題はスケジュールの問題になります。できるだけ安い飲み物の時間を選択しながら、毎日までに十分な「筋力予算」を確実に蓄えるようにする必要があります。 

問題を再構成する便利な方法は、これまでに必要な飲み物の数を維持しながら、日を順番に処理することです。 昼間なら$i$、現在の戦力が低すぎるため、ドリンクを追加する必要があります。 問題はその飲み物をどこから持ってくるかです。 各飲み物の効果は同じですが、価格が異なるため、経過した日の中で最も安いものを選択したいと常に考えています。 これは当然、候補コストのデータ構造を維持し、必要に応じて最小コストの飲み物を選択することにつながります。 

これにより、問題は、以前に確認された日数のコストを超える最小ヒープを伴う貪欲な蓄積プロセスに変換されます。

 ## アルゴリズムのチュートリアル

 日を左から右にスキャンし、すでに購入した飲み物の数と、選択できる利用可能なジムの費用のプールを維持します。 

1. 現在の強さを次のように初期化します。$K$、合計コストは 0、そしてこれまでに処理されたすべての日のコストを保存する最小ヒープ。 
2. 毎日について$i$、 入れる$C[i]$なぜなら、この日までにドリンクを購入できるオプションが追加されたからです。 
3. 現在の強度を確認します$K + (\text{drinks bought so far}) \cdot A$会う$X[i]$。 「はい」の場合は、何も買わずに続行します。 
4.満たさない場合$X[i]$、到達するまでに追加の飲み物が何杯必要かを計算します。$X[i]$。 ドリンクごとに追加されます$A$, そこで最低限必要なドリンク数を決めます。 
5. ヒープから最小のコストを繰り返し抽出し、必要な飲み物の数が満たされるまで飲み物の購入をシミュレートします。 各抽出は、この日以前に利用可能な最も安いジムを選択することに対応します。 
6. 要件を満たす前にヒープが空になった場合、将来のオプションでは以前の障害を修正できないため、-1 が出力されます。 
7. このプロセスを一日中続けて、総コストを累積します。 

重要なメカニズムは、飲み物を早めに購入するという事前約束を決してしないことです。 代わりに、過去のすべてのオプションを利用可能な状態に保ち、制約違反によって強制された場合に最も安価なオプションのみをアクティブにします。 

### なぜ効果があるのか

 いつでも$i$追加の強度が必要な場合は、有効なソリューションには、数日間購入した少なくとも一定数の飲み物が含まれている必要があります。$1$に$i$。 そのようなすべての有効な解決策の中で、選択した飲み物を同じ接頭辞からより安価に入手可能なものに置き換えることは、実現可能性を向上または維持することしかできません。 この交換の議論により、購入を迫られたときはいつでも、入手可能な最も安価なコストを貪欲に選択することが最適であることが保証され、決定を延期しても、より良い選択肢が検討から除外されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import heapq

def solve():
    n, k = map(int, input().split())
    x = list(map(int, input().split()))
    a = int(input())
    c = list(map(int, input().split()))

    heap = []
    total_cost = 0
    drinks = 0  # number of drinks bought so far

    for i in range(n):
        heapq.heappush(heap, c[i])

        current_strength = k + drinks * a

        if current_strength >= x[i]:
            continue

        # need more drinks
        needed = (x[i] - current_strength + a - 1) // a

        while needed > 0:
            if not heap:
                print(-1)
                return
            total_cost += heapq.heappop(heap)
            drinks += 1
            needed -= 1

    print(total_cost)

if __name__ == "__main__":
    solve()
```ヒープには、日数から現在のインデックスまでの考えられるすべての飲み物代が保存されます。 これにより、筋力を強化する必要がある場合、常にこれまでで最も安価で有効なジムを選択することが保証されます。 

の`drinks`カウンターは、すでにコミットした永続的なブーストの数を追跡します。 必要な体力差から飲み物の数への変換には、各飲み物が正確に寄与するため、天井分割が使用されます。$A$。 

正しさは、決してコストを考慮から外さないこと、そして強制された場合には常に最小コストを選択することにかかっています。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

    sys.stdin = io.StringIO(inp)
    import heapq

    n, k = map(int, input().split())
    x = list(map(int, input().split()))
    a = int(input())
    c = list(map(int, input().split()))

    return str(total_cost)

 ## 特殊なケース

 重大なエッジケースは、いくつかの安価な機会の後に強度要件が急激に上昇したときに発生します。 過去のすべてのジムのコストがヒープ内に残っているため、アルゴリズムは正確性を保証します。そのため、遅い日に複数のブーストが必要な場合でも、高価な遅いオプションを強制されるのではなく、以前の安価なオプションを選択できます。 

もう 1 つのエッジケースは、飲み物を必要としない日がない場合です。$X[i] \le K$。 ヒープはまだいっぱいになりますが、ポップは発生せず、答えはゼロのままです。 これにより、不必要な購入が決して引き起こされないことが確認されます。 

最後のエッジケースは、必要なドリンク数を超えた場合です。$N$。 その場合、需要を満たす前にヒープが空になり、アルゴリズムは正しく -1 を出力します。これは、最大ブースティングでも必要な強度プロファイルに到達できないことを反映しています。
