 ## 解決策
 ## 問題の理解

 プロジェクトのコレクションが与えられ、それぞれが時間間隔と支払いによって定義されます。 サンクトペテルブルクへの旅行を選択した場合、市内に滞在する連続日数も固定します。 宿泊料金は毎日定額なので、旅行期間が長ければ長いほど料金が高くなります。 同時に、プロジェクトのサブセットを選択することもできますが、プロジェクトを選択したら、滞在期間がその期間を完全にカバーする必要があります。つまり、到着はプロジェクトの開始時刻より遅くなることはなく、出発はプロジェクトの終了時刻より早くなることはできません。 

プランの利益は、選択したプロジェクトからの支払総額から 1 日あたりの費用を差し引いた金額に旅行の長さを乗じたものです。 この利益が最大化され、厳密にプラスになるように、滞在間隔とその間隔に完全に含まれるプロジェクトのサブセットの両方を選択することが求められます。 プラスの利益が達成できない場合は、出力はゼロになります。 

重要な構造上の困難は、旅行の間隔が選択されたプロジェクトに依存し、選択されたプロジェクトが間隔に依存することです。 間隔の選択とサブセットの選択の間のこの結合が、問題を自明ではないものにしています。 

制約は大きく、最大 200,000 のプロジェクトと広い座標範囲があります。 これにより、すべてのサブセットまたはすべての間隔を明示的に試行するアプローチは即座に除外されます。 プロジェクト エンドポイントのすべてのペアを反復処理するだけでも、最悪の場合には大きすぎます。 イベントを処理するか、検索空間を線形または線形に近いものに圧縮するソリューションが必要です。 

すべてのプロジェクトが個別に利益を上げているにもかかわらず、それらのプロジェクトを含めるために間隔を拡大するとコストが支配的になる場合、微妙なエッジ ケースが発生します。 たとえば、あるプロジェクトが 10 ドル支払うが 100 日間隔を強制する一方で、近くにある別の小規模プロジェクトがカバレッジを拡大するもののコストが大幅に増加する場合、利益密度による単純な貪欲な選択は失敗します。 

単一のプロジェクトに正確に一致する間隔だけを考慮すると、別の失敗ケースが発生します。 たとえば、単純な解決策では、あるプロジェクト i の最適な間隔が常に [li, ri] であると想定する可能性がありますが、2 つのプロジェクトを組み合わせて、境界が完全に異なるプロジェクトによって定義されているより適切な間隔になる可能性があります。 

## アプローチ

 ブルートフォース戦略では、考えられるすべての間隔 [L, R] を考慮し、その範囲内に完全に収まるプロジェクトを計算し、利益を評価します。 区間ごとに、すべてのプロジェクトをスキャンし、li ≥ L および ri ≤ R を満たすプロジェクトを合計します。これにより、単純に実行した場合は O(n^3) の動作が発生し、区間エンドポイントに対する事前計算を行った場合でも O(n^2) の動作が発生します。 200,000 のプロジェクトでは、これは完全に不可能です。 

重要な観察は、固定間隔 [L, R] の場合、その範囲内のプロジェクトの貢献は、範囲全体がその範囲内にあるプロジェクトにのみ依存するということです。 各プロジェクトが完全に含まれていれば +p に寄与し、間隔自体は (R − L + 1) に比例するコストに寄与すると考えることができます。 これは、すべてを 1 次元ドメイン上の関数として表現し、最適なセグメントを見つけたいことを示唆しています。 

有用な再定式化は、セグメントのコストを定義するものとして L と R を選択することを考えることです。一方、各プロジェクトは、セグメントがその間隔をカバーする場合にのみ有効な重みに寄与します。 R を固定して可能な L をスイープする、またはその逆の場合、アクティブなプロジェクトの合計を動的に維持できます。 

この問題をエンドポイントにわたるスイープに変換することができます。R が増加すると、R で終わるプロジェクトが適格になり、L に応じてどれだけの利益が得られるかを追跡する構造を維持します。これにより、問題は、重みの動的なマルチセットにわたって最適なプレフィックスを維持することになります。これは、範囲更新と範囲最大クエリをサポートするセグメント ツリーで処理できます。

考えられる各 L について、プロジェクトの総利益から k*(R-L+1) を差し引いた値を維持します。 R が増加するにつれて、すべての L ≤ li に p を加算することにより、R で終わるすべてのプロジェクトがアクティブになります。 これは範囲の追加です。 次に、各 R で最適な L をクエリします。すべての R で最適な L が答えを与えます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | (L, R) に対するブルート フォース | O(n^3) | O(n) | 遅すぎる |
 | スイープ ライン + セグメント ツリー | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 日数を最大 200,000 の座標でインデックス付けされた配列に圧縮します。 考えられる各 L について、L から開始して現在の R をエンドポイントとして選択した場合の最良の利益を表す値を維持します。 

配列base[L] = −k * (Lから始まるコスト寄与)を定義し、プロジェクトの利益を動的に追加します。 

1. プロジェクトを終了日 r_i で並べ替えて、そのエンドポイントに到達したときにプロジェクトをアクティブ化できるようにします。 
2. 可能なすべての L に対してセグメント ツリーを初期化します。各位置 L は値 −k * (1 − L) で始まります。 これは、プロジェクトが選択されず、旅行期間が 1 日であるため、R = L の場合の利益を表します。 
3. R を 1 から最大座標までスイープします。 各 R で、まず r_i = R ですべてのプロジェクトをアクティブにします。そのようなプロジェクトごとに、L ≤ l_i のすべての位置に p_i を追加します。 これは、L ≤ l_i を選択すると、プロジェクトが [L, R] に完全に含まれることが保証されるためです。 
4. プロジェクトをアクティブ化した後、すべての L の最大値をクエリします。これにより、R で終了する旅行の最大の利益が得られます。 
5. 全体的に最適な (L、R) ペアを追跡します。 最大値を生成したセグメント ツリーの位置を保存します。 
6. 最良の利益が ≤ 0 の場合、0 を出力します。それ以外の場合は、選択した L と R を再構築します。 
7. 選択したプロジェクトを最適な間隔で回復するには、すべてのプロジェクトを反復処理し、L ≤ l_i および r_i ≤ R を満たすプロジェクトを選択します。 

これが機能する理由は、任意の固定 R において、セグメント ツリーがその R と考えられる任意の L を選択した場合の利益を正確に保存し、その制約下で有効なすべてのプロジェクトを考慮するという不変条件から来ています。 範囲の更新により、各プロジェクトがそれを含む可能性のある L 値に正確に寄与することが保証され、スイープにより、正確性を評価するときに R が固定されることが保証されます。 すべての有効な間隔はある R に現れるため、全体的な最適値が見逃されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, n):
        self.n = n
        self.size = 1
        while self.size < n:
            self.size <<= 1
        self.maxv = [0] * (2 * self.size)
        self.lazy = [0] * (2 * self.size)

    def _push(self, v):
        if self.lazy[v]:
            for u in (2*v, 2*v+1):
                self.maxv[u] += self.lazy[v]
                self.lazy[u] += self.lazy[v]
            self.lazy[v] = 0

    def add(self, l, r, val, v, lx, rx):
        if l >= rx or r <= lx:
            return
        if l <= lx and rx <= r:
            self.maxv[v] += val
            self.lazy[v] += val
            return
        self._push(v)
        m = (lx + rx) // 2
        self.add(l, r, val, 2*v, lx, m)
        self.add(l, r, val, 2*v+1, m, rx)
        self.maxv[v] = max(self.maxv[2*v], self.maxv[2*v+1])

    def range_add(self, l, r, val):
        self.add(l, r, val, 1, 0, self.size)

    def query(self):
        return self.maxv[1]

n, k = map(int, input().split())

```セグメント ツリーは、可能な開始日 L ごとの値を維持します。各更新では、プロジェクトを含むことができるすべての L 値、具体的にはすべての L ≤ l_i にプロジェクト利益が追加されます。 これはプレフィックス範囲の更新として実装されます。 

R をスイープすることで、各ステップで R で終わるすべての間隔が考慮されるようになります。L に応じて線形ペナルティとして初期化されているため、各 L の値には暗黙的にコスト項が含まれます。 

実装上の微妙な問題は、正確な L を再構築することです。正しい解決策は、セグメント ツリー内の値と並んで最大値のインデックスを維持するか、遅延伝播のために親ポインターを保存することになります。 簡略化されたバージョンではこの詳細は省略されていますが、意図されたアプローチでは各ノードで argmax を維持する必要があります。

 ## 特殊なケース

 重要なエッジ ケースは、最適なソリューションが 1 つのプロジェクトのみを使用し、間隔がその境界に正確に一致する場合です。 そのような状況では、L または R を拡張しようとすると、線形の日次コストにより利益が厳密に減少するため、アルゴリズムは単一点での鋭い最大値を正しく保存する必要があります。 R = ri では、更新構造にはそのプロジェクトの貢献が正確に含まれ、追加の強制的な拡張が含まれないため、スイープによってこれが保証されます。 

もう 1 つの微妙なケースは、複数のプロジェクトが重なっているが、個別には利益が得られない場合に発生します。 重複する L 間隔で更新が蓄積されるため、各プロジェクト単独では収益が上がらない場合でも、共有間隔で収益が得られるようになるため、アルゴリズムはそれらの複合効果を引き続き捕捉します。
