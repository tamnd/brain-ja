 ## 解決策
 ## 問題の理解

 従業員のコレクションが与えられ、各従業員は 1 つのチームにのみ属します。 同じチームの従業員は常に一緒に移動する必要があるため、入力内の唯一の意味のある構造は各チームの頻度です。 

交通規則では、グループ分けに厳格な制約が課されています。各バスに乗車できるのは 1 チームまたは 2 チームのいずれかですが、それ以上は乗車できません。 チームを複数の乗り物に分割することはできません。 バス容量の値を選択できます`s`、乗車ごとに料金がかかります`s`なので、実行すると`r`乗車料金の合計は`s × r`。 私たちは選択するかもしれません`s`自由ですが、乗り物に割り当てられた最大のグループを収容できる十分な大きさでなければなりません。 

重要な決定は、乗り物の数と最大乗車負荷の積を最小限に抑えながら、チームを 1 つまたは 2 つのチームのサイズの乗り物に分割する方法です。 

この制約は、最大 500,000 人の従業員を処理する必要がある一方で、個別のチームの数は最大 8000 であることを意味します。チームのパーティションを列挙したり、すべてのサブセットに対して直接グループ化の選択肢をシミュレートしようとするソリューションは、組み合わせ的に爆発的に増加します。 チーム間のすべてのペアリングを反復処理しても、最悪の場合は 2 次関数になります。`k`大きいです。 

単純な貪欲な戦略による微妙な失敗例は、チームの規模がアンバランスな場合に現れます。 たとえば、1 つのチームが非常に大きく、多くのチームが小さい場合、組み合わせの決定は、目に見えない形で乗り物の数と最大定員の両方に影響を与えます。 

単純な間違いは、キャパシティの増加が最小限に抑えられると想定して、常に残りの最小チームをペアにすることです。 乗車定員の増加は、そうでなければ小規模のままであるものも含め、すべての乗り物に全体的に影響を与えるため、これは失敗する可能性があります。 

もう 1 つの失敗モードは、最初にキャパシティを最大チーム サイズとして固定し、その後、乗車を貪欲に最小化することです。 これは、乗車回数を大幅に減らすことができれば、戦略的に定員を増やすことができるということを無視しています。 

## アプローチ

 ペアリングの制限を無視すると、問題は些細なものになります。従業員全員が 1 回の乗り物に乗り、コストは単純に従業員の合計になります。 この難しさは完全に「1 回のライドにつき最大 2 チーム」という制約に起因しています。 

ブルートフォースアプローチでは、各チームをアイテムとして扱い、あらゆる方法でチームをサイズ 1 または 2 のグループに分割しようとします。 パーティションごとに、各ペア内の最大チーム サイズを計算します。これにより、必要な容量が決まります。 このようなパーティションの数は、サイズのセットで一致する数になります。`k`、おおよそ次のように成長します`(k/e)^(k/2)`、たとえ実現可能性をはるかに超えています`k = 8000`。 単一のパーティションの評価に限定することは問題ありませんが、それらを列挙することは不可能です。 

重要な観察は、乗車回数を固定すると、`r`、少なくとも形成できるかどうかだけを気にします。`r`サイズ 1 または 2 のグループ、およびそのようなグループ化の下での最小可能な最大ペア合計はいくらになるか。 これにより、問題は組み合わせ列挙から単一パラメータの最適化に移ります。 

パーティションを明示的に構築する代わりに、逆の推論も可能です。乗車回数を推測すると仮定します。`r`。 チームを割り当てることができるかどうかを確認したい`r`各グループに 1 つまたは 2 つのチームがあるようなグループ。 チームのサイズを分類する場合、必要なキャパシティを最小限に抑えるための最良のペアリング戦略は、常に、残りの最大のチームと残りの最小のチームをペアにすることです。 これは、ペアの最大合計を最小化する古典的な貪欲な構造です。 

固定の場合`r`を形成することで実現可能性をテストできます。`r`この最適な方法でグループを作成し、選択したペア間の最大負荷を計算します。 必要な容量がわかったら`s(r)`、費用は`r × s(r)`。 次に、すべての意味のある値を試します。`r`1から`k`。 

最適なペアリングはソートされたチーム サイズのみに依存し、プレフィックス サイズごとに誘発コストを効率的に評価できるため、構造はさらに簡素化されます。

 ## アルゴリズムのチュートリアル

 従業員をチームのサイズに分割し、分類します。 

1. 各チームのメンバーの数を数えます。 従業員の内部順序は無関係であるため、問題はさまざまなチームサイズに変わります。 
2. チームのサイズを昇順に並べ替えます。 これにより、極限ペアリングを使用して最適なペアリング戦略を推論することができます。 
3. 乗車回数の候補を検討する`r`。 正確に割り当ててみます`r`各グループには 1 つまたは 2 つのチームが含まれます。 
4. 固定の必要容量を最小限に抑えるため`r`、割り当てられていない残りの最大のチームと残りの最小のチームを組み合わせます。 チームがペアになっていないままの場合、シングルトン グループが形成されます。 これにより、グループの最大合計が最小化されます。これは、偏差があると、大-小のペアが大-大または小-小のいずれかに置き換えられ、どちらも最大負荷を増加させるか、改善できない可能性があるためです。 
5. 容量を計算する`s(r)`形成されたすべてのグループの最大値 (単一またはペアの合計)。 
6. 計算コスト`r × s(r)`有効なすべての最小値を維持します`r`。 

### なぜ効果があるのか

 正確さは、グループの数が固定されている場合、グループの最大重みを最小化することは最大のペアの合計を最小化することと同等であるという事実に基づいています。 ソートにより、目的を悪化させることなく、最適なソリューションを確実にモノトーンの組み合わせに変換できます。 交換引数は、2 つのペアが「交差」している場合、エンドポイントを交換してもペアの最大合計が増加しないため、貪欲なペアリングが最適であることを示しています。 

所定の乗り物数に対して可能な限り最適なキャパシティが決まると、コスト関数が完全に決定され、すべての項目がチェックされます。`r`あらゆる実現可能な構造をカバーします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    t = list(map(int, input().split()))

    cnt = [0] * (k + 1)
    for x in t:
        cnt[x] += 1

    sizes = [c for c in cnt if c > 0]
    sizes.sort()

    m = len(sizes)
    ans = float('inf')

    for r in range(1, m + 1):
        i, j = 0, m - 1
        groups = []
        used = 0

        while i <= j and used < r:
            if i == j:
                groups.append(sizes[i])
                i += 1
            else:
                groups.append(sizes[i] + sizes[j])
                i += 1
                j -= 1
            used += 1

        if used < r:
            break

        while i <= j:
            groups.append(sizes[i])
            i += 1

        capacity = max(groups)
        ans = min(ans, capacity * r)

    print(ans)

if __name__ == "__main__":
    solve()
```導入は、従業員をチームのサイズに圧縮することから始まります。 ソートにより、残りの最小チームと最大チームを繰り返し組み合わせる 2 ポインター ペア戦略が可能になります。 

候補となる乗車回数ごとに`r`、成形をシミュレーションします`r`グループ。 このループにより、許可されたグループ数を決して超えないことが保証され、残ったチームは実行可能性に影響を与えないため、単一チーム グループとして扱われます。`r`。 容量は最大グループ負荷として導出され、それに応じてグローバル最小コストを更新します。 

ブレーク条件は重要です。十分なグループを形成できない場合は、より大きなグループを形成する必要があります。`r`さらに多くのグループが必要となるため、値を指定することも不可能です。

 ## 特殊なケース

 特殊なケースは、あるチームが他のチームよりも大幅に大きい場合に発生します。 のような入力の場合`1 1000000`その後に多くのサイズ 1 のチームが続く場合、大規模なチームを含むグループは可能な限り最小限のチームを決定するため、ペアリングによってキャパシティが大幅に削減されることはありません。`s`。 最大の要素が常にグループに入り、どのペアもその寄与を減らすことができないため、アルゴリズムはこれを正しく処理します。 

もう 1 つのエッジ ケースは、チームの数は少ないが従業員の数が極端に多い場合に発生します。 例えば、`[1,1,1,100]`。 大規模なチームが関与するペアリングでは少なくとも 101 のキャパシティが生成されるため、最適なグループ化によりその影響が正しく分離され、残りのシングルトンによって結果が歪むことはありません。 

3 番目のケースは、すべてのチームが同等の場合です。 Then pairing does not change maximum sums, and the algorithm reduces correctly to evaluating linear cost scaling with the number of rides.
