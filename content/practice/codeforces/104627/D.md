 ## 解決策
 ## 問題の理解

 私たちには、秒単位まで正確な時間を示す 24 時間時計のコレクションが与えられています。 それとは別に都市のリストが与えられ、都市ごとにパリより何秒進んでいるのか、または遅れているのかがわかります。 隠された構造は、パリには未知の実時間が存在し、各都市の真の時間は、このパリ時間を所定のオフセットだけずらすことによって取得されるということです。 

私たちの仕事は、すべての割り当てが一貫した単一の世界的な「パリ時間」が存在するように、各都市ラベルを正確に 1 つの時計に割り当てることです。 言い換えれば、時計と都市オフセットの組み合わせを選択した後、すべてを 24 時間サイクル内の秒に変換すると、オフセットが逆転すると、すべての時計が同じ基礎となる基準時間に対応するはずです。 

重要な問題は、パリ時間自体が指定されておらず、時計と都市の間のマッピングが不明であることです。 私たちが知っているのは、そのようなマッピングが、いつか厳密な算術関係を法的に尊重しなければならないということだけです。 

制約は、二次または二次に近い推論には十分小さいです。 With up to 1000 clocks, an$O(n^2)$前処理は許容されますが、各ステップが自明でない場合、最悪の場合、三次関数は遅すぎます。 これは、すべての順列を直接試行することを避け、代わりに算術制約の構造に依存する必要があることを強く示唆しています。 

微妙な問題は、モジュールのラップアラウンドに起因します。 23:59:59 と 00:00:00 のような時間の差は午前 0 時を挟んでわずか 1 秒であるため、モジュロ演算を行わない単純な減算では不正確な不一致が生じます。 もう 1 つのよくある落とし穴は、パリ時間が独自に決定されると想定していることです。 実際、システムは一貫したグローバル シフトまでしか定義されていないため、複数の有効な調整が存在する可能性があり、有効な割り当てはいずれか 1 つだけ受け入れられます。 

## アプローチ

 直接的なアイデアは、時計と都市の間で可能なすべての全単射を試し、一貫したパリ時間が存在するかどうかを確認することです。 固定順列の場合、1 つのペアから暗黙のパリ時間を計算し、他のすべてのペアを検証できます。 これはすぐに実行不可能になります。$n!$割り当ては実際の制限をはるかに超えて増加します。$n = 1000$。 

次の自然な単純化は、パリ時間を暗黙的に修正することです。 どの時計がどの都市に対応するかがわかっていれば、ペアごとに暗黙の基準時間を計算できます。 有効な割り当てでは、これらの暗黙の値がすべて同一になる必要があります。 これにより、問題は一貫性条件の下で完全な一致を見つけることに変換されます。 

重要な観察は、差異という観点から条件を書き直すことです。 時計が時間を示しているなら$a_i$(秒単位) と都市がオフセットしました$d_j$の場合、有効な代入には定数値が存在する必要があります。$T$そのような$$a_i \equiv T + d_j \pmod{86400}.$$並べ替えると$$T \equiv a_i - d_j \pmod{86400}.$$これは、選択されたすべてのペアを意味します$(i, j)$同じ値を生成する必要があります$T$。 したがって、順列について考える代わりに、選択について考えます。$n$すべてのペアが同じモジュール差分に同意するようにペアを作成します。 

次に、候補値を固定することを検討します。$T$。 各時計ごとに$i$、都市$j$一致する必要があるかどうかは完全に決定されます。オフセットが次の条件を満たす一意の都市である必要があります。$d_j \equiv a_i - T$。 ずっと$d_j$は別個であり、各クロックは固定条件下で最大 1 つの一致の可能性があります。$T$。 これにより、問題は、この誘導されたマッピングが全単射であるかどうかを確認することになります。 

どちらを選択するかはまだ決める必要があります$T$試してみる。 有効な$T$等しい必要があります$a_i - d_j$何らかの有効なペアの場合、すべての候補は何らかのクロックシティのペアから生じます。 これにより、最大でも$n^2$候補者たち。 各候補について、誘導マッピングを構築し、それが完全なマッチングを形成するかどうかを確認することで、線形時間で一貫性を検証できます。 

これにより、$O(n^3)$理論上は最悪のアルゴリズムですが、実際には$n = 1000$そして、それぞれの内部チェックは非常に単純であり、早期に拒否されるのが一般的です。 この実装は、オフセットから都市インデックスへの高速ルックアップに依存しています。

 ## アルゴリズムのチュートリアル

 1. すべてのクロック時間を 86400 を法とした合計秒数に変換します。これにより、真夜中のラップアラウンドに関する問題が回避され、算術が均一になります。 
2. 各都市のオフセット値からそのインデックスへの直接マッピングを構築します。 すべてのオフセットは個別であるため、この検索は明確です。 
3. 時計のペアごとに$i$そして街$j$、候補となる基準時間を計算します。$$T = (a_i - d_j) \bmod 86400.$$この値は、時計を作成する仮想のパリ時間を表します。$i$都市に正確に対応する$j$。 
4. 各候補者について$T$、完全な代入を作成してみます。 

あらゆる時計に$i$、必要なオフセット一致を計算します$$d = (a_i - T) \bmod 86400.$$次に、このオフセットが都市リストに存在するかどうかを確認します。 そうでなければ候補者は$T$は無効です。 
5. マッピングを構築する際、各時計を対応する都市インデックスに割り当てます。 いずれかの都市が複数回割り当てられている場合、マッピングは単射的ではないため、候補は失敗します。 
6. すべてのクロックが異なる都市に一致する場合は、結果の割り当てをすぐに出力します。 
7. 候補者がいない場合$T$有効な全単射が生成され、「不可能」と出力されます。 

重要な構造は、各基準時間候補が時計から都市への決定論的なマッピングを引き起こすということです。 チェック内での分岐や検索はなく、直接検索のみです。 

### なぜ効果があるのか

 有効な解決策はすべて、実際のパリ時間に対応している必要があります$T$。 有効な時計と都市のペアを選択してください$(i, j)$その解決策から。 定義された制約により、そのペアは次の条件を満たす必要があります。$T = a_i - d_j \pmod{86400}$。 したがって、正しい$T$列挙された候補の中に常に表示されます。 

一度$T$が固定されると、他のすべてのペアリングが強制されます。 2 つの時計が同じ都市にマップされている場合、または一部の時計に有効な都市がない場合、割り当てはその都市に対して有効になりません。$T$。 これにより、検証ステップが必要かつ十分になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 24 * 60 * 60

def to_seconds(h, m, s):
    return h * 3600 + m * 60 + s

n = int(input())
clocks = []
for _ in range(n):
    h, m, s = map(int, input().split(":"))
    clocks.append(to_seconds(h, m, s))

offsets = list(map(int, input().split()))

pos = {}
for i, d in enumerate(offsets):
    pos[d] = i + 1

clocks_mod = [x % MOD for x in clocks]

for i in range(n):
    for j in range(n):
        T = (clocks_mod[i] - offsets[j]) % MOD

        used_city = [-1] * n
        ok = True

        for k in range(n):
            need = (clocks_mod[k] - T) % MOD
            if need not in pos:
                ok = False
                break
            c = pos[need]
            if used_city[c - 1] != -1:
                ok = False
                break
            used_city[c - 1] = k + 1

        if ok:
            print(*used_city)
            sys.exit(0)

print("Impossible")

ネストされたループオーバー$(i, j)$妥当なすべての基準時間を生成します。 各候補について、内側のループは、すべてのクロックが正確に 1 つの都市にマップされなければならず、都市は再利用できないという制約を強制します。 配列`used_city`都市にすでに時計が割り当てられているかどうかを追跡します。 

よくある落とし穴は、差分を計算するときにモジュラー演算を忘れることです。 もう1つはリセットに失敗しています`used_city`各候補者の構造$T$、試行間で状態が誤って引き継がれてしまいます。

 ## 特殊なケース

 重要なエッジケースは、複数の時計が同じ時間を示す場合です。 その状況では、多くの候補基準時間によって必要なオフセットが繰り返し生成され、都市の割り当てが重複しているため、アルゴリズムはそれらを正しく拒否します。 たとえば、すべてのクロックが 00:00:00 を読み取るが、オフセットが異なる場合、すべての候補が$T$すべての時計を強制的に同じ都市にマッピングすることになり、直ちに単射性が侵害されます。 

もう 1 つの微妙なケースは、オフセットに負の値が含まれる場合です。 モジュロ正規化により、負のシフトが有効な 24 時間ラップアラウンド位置に対応することが保証されるため、ルックアップの一貫性が維持されます。 

最後に、アルゴリズムは最初の一貫した基準時間で停止するため、複数の有効な回答があるケースは自然に処理されます。 すべての有効な解は何らかの候補に対応するため、$T$、正しい解決策を見逃すことはありません。
