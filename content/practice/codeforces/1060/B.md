 ## 解決策
 ## 問題の理解

 単一の大きな整数が与えられます$n$そして、それを 2 つの非負の整数に分割したいと考えています。$a$そして$b$それらの合計が正確に維持されるように$n$。 考えられるすべての分割の中で、2 つの部分の桁の合計の合計を最大化するように求められます。これは、最大化したいことを意味します。$S(a) + S(b)$、 どこ$S(x)$は 10 進数の合計です$x$。 

したがって、問題は任意の数値を選択することではなく、その桁を分配することです。$n$桁の合計をできるだけ大きくしながら、正しく合計される 2 つの数値に変換します。 

制約$n \le 10^{12}$手段$n$最大 12 桁です。 すべてのスプリットの直接の列挙$a \in [0, n]$まで繰り返す必要があるため不可能です$10^{12}$この値は実現可能な限界をはるかに超えています。 各分割をチェックして桁の合計を計算するだけでも、$O(n \cdot \log n)$、それは完全に不可能です。 

これにより、桁上げを伴う加算の下で桁の合計がどのように動作するかについての構造的特性を探す必要がすぐに生じます。 

素朴な直観は、両方を作ることを示唆するかもしれません$a$そして$b$「バランス」は役に立ちますが、桁上げの伝播下では桁の合計が奇妙に動作します。 本当の複雑さは、キャリーがどのように桁の合計を減らすかにあります。2 つの桁の合計が 10 以上になるたびに、キャリーはその位置で桁の合計を 9 減らします。 

微妙なエッジケースが現れるのは、$n$たとえば、これは 10 のべき乗です$n = 1000$。 みたいな素朴な分裂$500 + 500$バランスが取れているように感じますが、桁の合計は次のような構造に比べて比較的小さいです。$999 + 1$、キャリーをより効果的に活用します。 これは、最適な構造が対称分割ではなく 10 進桁上げに密接に関連していることを示唆しています。 

## アプローチ

 ブルートフォースアプローチでは、あらゆる可能な分割が試行されます。$a$0から$n$、計算します$b = n - a$、評価します$S(a) + S(b)$。 すべての有効な構成がチェックされるため、これは正しいです。 ただし、必要なのは$n$反復回数と各桁の合計の計算コスト$O(\log n)$したがって、全体の複雑さは次のようになります。$O(n \log n)$。 のために$n \approx 10^{12}$、これは実行可能なランタイムをはるかに超えています。 

重要な観察は、桁の和がキャリーを通じて加算と相互作用するということです。 任意の分割を選択することを考えるのではなく、構造を桁ごとに調べます。 各小数点は桁上げを除いて独立して動作します。 重要な考え方は、桁の合計を最大化する最善の方法は、破壊的なキャリーを最小限に抑え、代わりに両方の数値の桁をできるだけ大きくすることであるということです。 

これは、標準的な貪欲な洞察につながります。$a$そして$b$合計が次のようになりながらも、その桁ができるだけ大きくなるようにします。$n$。 よく知られている単純化は、最大の数字 9 と 0 の構造を作成する方法で「借用」すると、最適な分割が発生するということです。 具体的には、一方の数字が低下する前に 9 に飽和する先頭の数字で構成され、もう一方の数字が残りを吸収するという分割を試みることで、答えが得られることがわかりました。 

これを捉える実際的な方法は、分割してみることです。$n$異なる桁境界で。 プレフィックスの分割位置ごとに、次のようなプレフィックスで構成される 1 つの数値をシミュレートします。$10^k - 1$-スタイルの貢献。局所的に桁の合計を最大化します。 以来$n$最大 12 桁なので、テストするだけで済みます$O(\log n)$プレフィックス調整から導出された候補構造。 

したがって、全体にわたる完全な検索から問題を軽減します。$a$数字構造から構築された貪欲な候補の小さなセットに。

 ## アルゴリズムのチュートリアル

 1.変換$n$文字列に変換すると、その 10 進数を直接推論できるようになります。 桁の合計の動作はポジション間のキャリーに依存するため、桁ごとの作業が不可欠です。 
2. 可能な各位置を反復して、接頭辞を減らすことで分割候補を構築してみます。$n$サフィックスを、元の数値を超えない最大の数字構成に置き換えます。 これは、数字を 9 に近づけると数字の合計が増加するという考えを表しています。 
3. 各候補構成について、暗黙のペアを計算します。$(a, b)$の残りがどのように変化するかをシミュレートすることで、$n$1 つのコンポーネントを修正してから配布されます。 
4. コンピューティング$S(a) + S(b)$候補者ごとに。 12 桁の数値では桁の合計が低コストであるため、このステップは実際には候補ごとに一定時間です。 
5. すべての候補にわたる最大値を追跡し、出力します。 

これらの構造化された候補だけが必要な理由は、目的を損なうことなく、最適解を少なくとも 1 つの数字が接頭辞とその後にすべて 9 が続く数字パターンを持つものに変換できるためです。 この変換引数は、無限の検索空間を小さな有限セットに縮小します。 

### なぜ効果があるのか

 重要な不変条件は、どちらの場合でも桁位置が 9 に完全に飽和していない場合です。$a$または$b$, キャリー制約によってブロックされない限り、合計制約に違反することなく、分割をローカルに調整してその桁を上に押し上げることができます。 そのブロッキング ポイントは、まさにプレフィックス境界で発生します。$n$。 したがって、最適な構成はキャリー遷移が発生する境界に対応しており、それらの境界はまさに私たちが列挙したものです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def digit_sum(x: int) -> int:
    s = 0
    while x:
        s += x % 10
        x //= 10
    return s

def solve():
    n = int(input().strip())

    best = digit_sum(n)  # (a=n, b=0) baseline

    # Try splitting by forcing a prefix boundary in b
    # We construct candidates of form:
    # b = 10^k - 1, a = n - b
    p = 1
    while p <= n:
        b = p - 1
        a = n - b
        best = max(best, digit_sum(a) + digit_sum(b))
        p *= 10

    print(best)

if __name__ == "__main__":
    solve()
```この実装は、ある数値が次の形式の数値に近い場合に最も生産的な分割が発生するという観察に基づいて構築されています。$10^k - 1$、これは 10 進数の 9 の連続です。 このようなすべての境界を次の大きさまでテストします。$n$。 

基本的なケース$(n, 0)$が含まれているのは、常に有効であり、場合によっては最適であるためです。$n$それ自体の桁数の合計が大きくなります。 

10 のべき乗のループでは、プレフィックスで揃えられたすべての可能な「すべて 9」の候補が生成されます。 そうした候補者ごとに$b$、計算します$a = n - b$、制約を確保する$a + b = n$常に保持されます。

## テストケース```python
import sys, io

def digit_sum(x):
    return sum(map(int, str(x)))

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    n = int(input().strip())

    best = digit_sum(n)
    p = 1
    while p <= n:
        b = p - 1
        a = n - b
        best = max(best, digit_sum(a) + digit_sum(b))
        p *= 10

    return str(best)

# provided sample
assert run("35\n") == "17"

# minimum case
assert run("1\n") == "1"

# power of ten case
assert run("100\n") == "19"

# all digits 9
assert run("99\n") == "18"

# large case
assert run("1000000000000\n") == str(max(digit_sum(1000000000000 - (10**k - 1)) + digit_sum(10**k - 1) for k in range(13)))

# symmetric case
assert run("50\n") == str(run("50\n"))

# edge carry-heavy case
assert run("19\n") == "10"

 ## 特殊なケース

 のために$n = 1$、唯一の有効な分割は$(1, 0)$。 アルゴリズムが試行する$b = 0$そして戻ってきます$S(1) = 1$、それは正しいです。 

のために$n = 1000$、アルゴリズムは次のように評価します$b = 9, 99, 999$。 最良のものは通常、$b = 999$、降伏$a = 1$、桁の合計を与える$1 + 27 = 28$。 ループは 10 の累乗すべてを繰り返すため、このケースに正しく到達します。 

のために$n = 19$、最良の分割は$10 + 9$、桁の合計を与える$1 + 0 + 9 = 10$。 候補者$b = 9$は明示的にテストされており、アルゴリズムはこの最適なキャリーベースの分解を正確に捕捉します。 

これらの各ケースは、アルゴリズムが一様分布に依存するのではなく、キャリーアライメントされた境界を体系的に探索することを示しており、まさに単純な分割よりも改善が見られる箇所です。
