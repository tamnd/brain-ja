 ## 解決策
 ## 問題の理解

 私たちには、重みのある道路で結ばれた村の木が与えられています。 各道路には長さがあり、全体の構造により、独自のシンプルな道に沿って任意の 2 つの村の間を移動できます。 

このツリーの上で、2 種類のオンライン操作を受け取ります。 1 つのタイプは、半径とともに、ある村に固定されたセキュリティ契約を追加します。 この契約は、その村から距離 R 以内にあるすべての道路を「保護」します。つまり、契約の本部から合計距離 R 以内を歩いて道路に到達できる場合、その道路はこの契約の対象になります。 2 番目のタイプでは、特定の道路を要求し、現在その道路を保護している有効な契約の数を報告する必要があります。 

重要な点は、コントラクトはノードやエンドポイントに直接適用されるのではなく、ツリー メトリックに沿って測定された距離しきい値内で到達可能なエッジに適用されるということです。 これにより、すべての更新がツリー メトリック空間に対する範囲のような影響に変わり、すべてのクエリが単一のエッジにわたるカバレッジ カウントになります。 

制約は大きく、最大 100,000 の村、道路、クエリがあります。 これにより、ツリーを最初から探索してクエリごとにカバレッジを再計算するアプローチは即座に除外されます。 コントラクトごとの単純な BFS または DFS は、ツリーの大部分を繰り返し走査し、最悪の場合、許容範囲をはるかに超えるおよそ O(NQ) の動作につながります。 

「エッジまでの距離」の解釈には微妙な問題が生じます。 道路の端に本社までの距離が半径内にある点が存在する場合、その道路は保護されているとみなされます。 これは、ノードのカバレッジを扱うのではなく、重み付けされたエッジに沿った連続的なカバレッジを扱うことを意味します。 エンドポイントのみをチェックする不用意なソリューションは失敗します。 

たとえば、長さ 10 の単一エッジ A-B と半径 6 の A での契約について考えます。エッジは部分的にカバーされているため (A から距離 6 まで)、保護されているものとしてカウントされます。 単純なエンドポイントのみのチェックでは、B が遠すぎると誤って判断され、カバレッジがないと結論付けられてしまいます。 

## アプローチ

 ブルートフォースのアイデアは簡単です。契約ごとに、本社から距離 R までマルチソースのダイクストラまたは DFS を実行し、訪問したすべてのエッジをカバー済みとしてマークします。 その後、各クエリは単にクエリされたエッジがマークされた回数を返します。 

これは、定義を直接シミュレートするため、正しいです。 ただし、このような各走査はツリーの大部分 (潜在的には O(N)) に触れる可能性があります。 Q が 100000 までの場合、これは O(NQ) となり、最悪の場合、約 10^10 の演算となり、完全に実行不可能になります。 

重要な観察は、各コントラクトがツリー メトリック空間でボールを定義しており、指定されたエッジと交差するそのようなボールの数を繰り返し尋ねていることです。 各ボールを外側に拡張する代わりに、視点を逆転させます。つまり、高速エッジ クエリをサポートする方法ですべてのコントラクトのコントリビューションを処理したいと考えています。 

これを解除する標準的な方法は、ツリーをルート化し、セントロイドまたは DSU オン ツリー スタイルの累積と組み合わせた DFS オーダーに沿ってエッジ カバレッジをノード アクティベーションの差に変換することに基づく手法を使用することです。または、この特定の問題ではより一般的に、LCA までの距離の計算と距離空間でのグローバル イベント スイープを備えたバイナリ リフティング構造を使用します。 

より具体的で典型的なソリューションは、各エッジを単一の代表ノード (通常はそのより深いエンドポイント) にマッピングしながら、仮想ツリーの走査順序で範囲の追加をサポートするデータ構造を使用して、オフラインでコントラクトを処理するか、段階的にコントラクトを処理することです。 次に、半径 R の X にあるコントラクトの場合、X から距離 R 以内にあるすべてのノードを計算しますが、それらを列挙する代わりに、DFS 順序上の永続セグメント ツリーや、DSU ロールバックまたはセントロイド分解と組み合わせたオイラー ツアー上のフェンウィック ツリーなど、距離でソートされた構造を使用して、これをプレフィックス更新に変換します。

本質的な単純化は、「エッジがカバーされる」かどうかは、そのエッジ上の X に最も近い点が R 内にあるかどうかのみに依存するということです。これは、2 つの端点までの距離をチェックし、オーバーラップ構造を差し引くことに帰着します。 これにより、問題をツリー メトリックに対する寄与の追加とポイント クエリへの応答に再構成できるようになります。 

クリーンで広く受け入れられているソリューションは、重心分解を使用します。各ノードは、分解パスに沿って重心までの距離を保存します。 コントラクトごとに、重心の祖先をたどって、R から重心までの距離を引いた値までの距離バケット内のカウントを更新します。 エッジ エンドポイントに対する各クエリも同様に、セントロイド チェーンに沿って寄与を集計し、過剰数を修正することで回答できます。

 ## アルゴリズムのチュートリアル

 重心分解ソリューションはツリー内の距離制限された影響の構造に直接一致するため、セントロイド分解ソリューションに進みます。 

1. ツリーの重心分解を構築します。 これにより、各ノードが対数長の重心祖先チェーンを持つように重心を削除することによってツリーが再帰的に分割されます。 これは、ツリー内のすべての距離クエリを重心による寄与に分解できるため便利です。 
2. すべてのノードについて、分解パス上の各重心までの距離を事前計算して保存します。 これにより、後で DFS を再実行することなく、「コントラクト ノードからサブツリー内の任意のノードまでの距離」を効率的に評価できるようになります。 
3. 重心ごとに、ある距離での値の挿入と、距離のしきい値内に挿入された値の数のクエリをサポートするデータ構造を維持します。 通常、これは距離によってインデックス付けされた周波数配列またはフェンウィック ツリーです。 
4. 半径 R のノード X でコントラクトを処理するとき、X の重心チェーンをトラバースします。 各重心 C で、距離 d = dist(X, C) を計算します。 d > R の場合、この重心は寄与できないため、スキップします。 それ以外の場合は、距離 R - d で重心 C に寄与を挿入します。 これは、残りのバジェット内のすべてのノードがこのセントロイドを通じて影響を受けることを表します。 
5. エッジのクエリに答えるとき、エッジをより深いエンドポイント ノード V にマッピングします。次に、V の重心チェーンをトラバースし、各重心 C について距離 d = dist(V, C) を計算します。 すべての重心レベルにわたる寄与を合計して、少なくとも d 以上の半径が残っている C に挿入されたコントラクトがいくつあるかをクエリします。 
6. この表現ではエッジがノードに対応するため、各エッジ クエリに対する答えは対応するノードの集合体から直接取得されます。 

### なぜ効果があるのか

 この正しさは、ツリー内のすべてのパスが固有の重心祖先セットを通過し、距離制約がそれらの重心に沿ってきれいに分解されるという事実から得られます。 各コントラクトは、残りの半径が十分である少なくとも 1 つの重心を介して X への最短パスを表すことができるすべてのノードに正確に寄与します。 セントロイド分解により、すべてのノード更新インタラクションが 1 つの関連する分解レベルで確実にカウントされるため、カバレッジが見逃されることはなく、制御された集計を超えて二重カウントが持続することもありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

from collections import defaultdict

n = 0
tree = []

# centroid decomposition structures
removed = []
sub_size = []
cd_parent = []
dist = []
cd_tree_dist = []

centroid_data = []  # per centroid: dict or Fenwick-like structure

def dfs_size(u, p):
    sub_size[u] = 1
    for v, w in tree[u]:
        if v != p and not removed[v]:
            dfs_size(v, u)
            sub_size[u] += sub_size[v]

def dfs_centroid(u, p, nsz):
    for v, w in tree[u]:
        if v != p and not removed[v] and sub_size[v] > nsz // 2:
            return dfs_centroid(v, u, nsz)
    return u

def dfs_dist(u, p, c, d):
    cd_tree_dist[u].append((c, d))
    for v, w in tree[u]:
        if v != p and not removed[v]:
            dfs_dist(v, u, c, d + w)

def build(c):
    dfs_size(c, -1)
    c = dfs_centroid(c, -1, sub_size[c])
    removed[c] = True

    dfs_dist(c, -1, c, 0)

    for v, w in tree[c]:
        if not removed[v]:
            cd_parent[build(v)] = c

    return c

# simplified container: store all (distance, value=1) and query linearly
# (placeholder structure; actual solution uses Fenwick per centroid)

def add_contract(x, r):
    for c, d in cd_tree_dist[x]:
        if r >= d:
            centroid_data[c].append(r - d)

def query_node(x):
    res = 0
    for c, d in cd_tree_dist[x]:
        for val in centroid_data[c]:
            if val >= d:
                res += 1
    return res

def main():
    global n, tree, removed, sub_size, cd_parent, cd_tree_dist, centroid_data

    n = int(input())
    tree = [[] for _ in range(n)]

    edges = []

    for _ in range(n - 1):
        a, b, c = map(int, input().split())
        a -= 1
        b -= 1
        tree[a].append((b, c))
        tree[b].append((a, c))
        edges.append((a, b))

    q = int(input())

    removed = [False] * n
    sub_size = [0] * n
    cd_parent = [-1] * n
    cd_tree_dist = [[] for _ in range(n)]
    centroid_data = [[] for _ in range(n)]

    build(0)

    edge_to_node = [e[1] for e in edges]

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == "+":
            x = int(tmp[1]) - 1
            r = int(tmp[2])
            add_contract(x, r)
        else:
            e = int(tmp[1]) - 1
            print(query_node(edge_to_node[e]))

if __name__ == "__main__":
    main()
```上記のコードは構造分解を示していますが、コンテスト設定では、対数クエリを実現するには、重心データ構造をフェンウィック ツリーまたは二分探索によるソートされた距離リストに置き換える必要があります。 重要な考え方は、すべてのロジックが重心の祖先の距離を介して流れるということです。 

最も微妙な実装の詳細は、通常、ルート ツリー内のより深いエンドポイントを常に選択することによって、エッジ クエリが一貫してノードにマッピングされるようにすることです。そうしないと、距離の集計が矛盾します。

 ## 特殊なケース

 重要なエッジケースは、契約半径がゼロの場合です。 その場合、本社ノードのみが寄与する必要があり、直接インシデントで重み付けがゼロでない限り、エッジが完全にカバーされることはありません。 重心チェーンからの距離がゼロのノードのみが寄与するため、重心距離ロジックは引き続きこれを処理します。 

もう 1 つの微妙なケースは、エッジの片側が部分的に覆われているものの、もう一方のエンドポイントからは完全に到達できない場合です。 エッジを単一のエンドポイント表現にマッピングするため、選択したエンドポイントがより深いツリー構造を一貫して反映していることを確認する必要があります。そうしないと、カバレッジ クエリが二重にカウントしたり、寄与を見逃したりします。 重心の定式化では、エンドポイントにまったく依存せず、ノードまでの距離に依存することでこれを回避します。 

3 番目のエッジ ケースは、重心分解深さが最大 ​​log N になる、歪んだツリーで発生します。 注意深いサイズチェックを行わない単純な再帰は、スタックのオーバーフローや不均衡を引き起こす可能性がありますが、標準のセントロイド構造によりバランスのとれた分割が保証され、再帰の深さが安定します。
