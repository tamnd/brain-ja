 ## 解決策
 ## 問題の理解

 私たちは、マフィアと呼ばれる、すべての頂点に色が割り当てられたツリーに取り組んでいます。 これらの色は時間の経過とともに変化します。 重要な問題は、色が頂点を単に「占有する」わけではないことです。 代わりに、それ自体の頂点を接続するパス上にある追加の頂点も占有します。 

より正確には、色を固定します。 現在その色を持っているすべての頂点を確認します。 このような頂点のペアごとに、ツリー内の頂点間の固有の単純なパスを考慮します。 これらすべてのパスを結合すると、接続された構造が形成されます。 頂点がこれらのパスの少なくとも 1 つにある場合、その頂点はその色のコントロール領域に属します。 したがって、各色は、まさにその色のすべての頂点にまたがる最小の接続されたサブツリーであるサブツリーのような領域を生成します。 

各クエリは、2 つの頂点 v と u の間のパスについて尋ねます。 このパス上のどこかにあるコントロール領域の少なくとも 1 つの頂点を持つ個別の色の数を数える必要があります。 言い換えれば、v から u へのパス上のすべての頂点のセットを取得し、このパスと交差するすべてのコントロール領域を調べ、この結合内に出現する個別の色の数を数えます。 

この制約により、色の変更更新とパス クエリの両方で、最大 200,000 個の頂点と 200,000 回の操作が可能になります。 すべての色を検査したり、クエリごとに構造を再計算したりするソリューションは、非常に遅すぎます。 パスは n で線形になる可能性があり、q 回繰り返すと二次的な動作につながるため、パスを明示的に反復しても、最悪の場合はコストがかかりすぎます。 

微妙な特殊なケースは、色が 1 回しか現れない場合です。 その場合、その制御領域はその 1 つの頂点だけです。 後で 2 番目のオカレンスが追加されると、制御領域が突然拡大して接続パス上のすべての頂点が含まれるようになり、一度に多くのノードに影響を与える可能性があります。 もう 1 つの特殊なケースは、頂点の色の変更です。これにより、2 つの異なる色のコントロール領域を分割または結合できます。この変更はツリー構造全体でグローバルです。 

## アプローチ

 ブルートフォースアプローチは簡単です。 クエリごとに、v と u の間のパス上のすべての頂点を計算し、色ごとに、その色のコントロール領域の頂点がパスと交差するかどうかを確認します。 ただし、制御領域を明示的に維持するには、更新のたびに各色のシュタイナー ツリーを再計算する必要があります。 k 頂点にわたるシュタイナー ツリーの構築には、少なくとも O(k log k) または LCA 前処理による O(k) のコストがかかり、最悪のケースでは k は O(n) になります。 これを更新ごとに実行するのはすでに遅すぎます。また、これを q クエリと組み合わせると、全体の複雑さは O(nq) にまで膨れ上がります。 

重要な構造上の観察は、各色の制御領域が動的なシュタイナー ツリーであるということです。 明示的に維持するのではなく、指定されたパスと交差するかどうかを知るだけで済みます。 これにより、問題は完全なサブツリーの構築からプロパティの維持、つまり特定のパス セグメントを横切る色に影響があるかどうかに移ります。 

ツリー上の動的なサブツリーのようなオブジェクトを処理する強力な方法は、重心分解です。 このアイデアは、ツリーを階層に分解し、各ノードが O(log n) 個の重心コンポーネントに属するようにすることです。 各重心について、各色がその子サブツリー全体にどのように分布しているかに関する概要情報を維持できます。 これにより、色が重心の複数の枝に「広がる」かどうかを検出できるようになり、これがまさにその色がシュタイナー パスに現れることになります。 

ある色が、ある重心の少なくとも 2 つの異なる子ブランチに表示される場合、その重心はその色のシュタイナー ツリー内にあります。 これにより、制御領域を明示的に構築せずに暗黙的に表現する方法が提供されます。 

次に、この重心ベースの表現をパス分解と組み合わせます。 各クエリ パスは O(log n) 個の重心関連セグメントに分割でき、事前に計算された構造を使用してそのパスに沿ってアクティブな色を集計します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォースによるシュタイナー ツリーの再計算 | O(nq) | O(n) | 遅すぎる |
 | 色分布追跡による重心分解 | O((n + q) log² n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ツリーを任意にルート化し、ツリーの重心分解を構築します。 

私たちは、すべての重心ノードについて、その直接の重心で分割されたサブツリー全体に色がどのように分布しているかの記録を維持します。 概念的には、重心 c ごとに、そのコンポーネントを子部分に分割します。 各色 x について、各部分に表示される色 x の頂点の数を維持します。 

ある色が重心 c の少なくとも 2 つの異なる部分に出現する場合、c はその色のコントロール領域の「関連する証人」になります。 これは、明示的なシュタイナー ツリーに代わる重要な抽象化です。 

また、色ごとに、現在その色を持つ頂点のセットも維持されるため、更新を段階的に処理できます。 

処理は次のように動作します。 

## アルゴリズムのチュートリアル

 1. ツリーの重心分解を構築し、各ノードの重心祖先と各レベルの対応するサブツリー識別子を保存します。 これにより、任意の頂点が O(log n) 重心構造を効率的に更新できるようになります。 
2. 各重心 c について、その分解された子コンポーネントにわたる色から周波数配列へのマップを維持します。 この構造は、重心のパーティション内で色がどのように分布しているかを追跡します。 
3. 各色 x についても、更新によって出現箇所を効率的に削除および挿入できるように、現在の頂点セットを維持します。 
4. 頂点 v を色 a から色 b に再色するとき、v のすべての重心の祖先を更新します。そのような重心 c ごとに、v を含むコンポーネント内の色 a の寄与を減分し、色 b の寄与を増分します。 
5. 各更新の後、影響を受ける重心ごとに、その重心で色が現在「アクティブ」かどうか、つまり少なくとも 2 つの異なるコンポーネントに色が表示されているかどうかを維持します。 
6. v と u の間のクエリの場合、LCA と重心祖先追跡を使用して、パスを O(log n) 重心関連セグメントに分解します。 
7. パスと交差する重心セグメントごとに、その重心でアクティブなすべての色を収集します。 分解されたパス上でこれらのセットを結合すると、制御領域がパスと交差するすべての色が得られます。 

正確かどうかは、そのシュタイナー ツリーにそのパス上に少なくとも 1 つの頂点が含まれている場合に限り、色がパスと交差するかどうかにかかっています。 すべてのシュタイナー ツリーは、色が複数の枝にまたがる重心のセットによって完全にキャプチャされるため、パスとの交差はパス分解に沿って少なくとも 1 つのそのような重心を通過する必要があります。 

### なぜ効果があるのか

 色のコントロール領域は、まさにツリー メトリックにおけるシュタイナー ツリーです。 頂点は、色の出現を接続する必要があるときに正確にこのシュタイナー ツリーに存在します。これは、色がサブツリー パーティション内で少なくとも 2 つの異なる方向に現れるときに発生します。 重心分解により、すべての頂点が、あるレベルでのそのような状況の「分割証人」となることが保証されます。 すべてのパスは重心祖先を通じて分解できるため、パスとシュタイナー ツリー間の交差はこれらの重心監視の 1 つで検出される必要があります。 これにより、関連する重心セグメント全体でアクティブなカラーをカウントすると、パスが通過する個別の制御領域の数が正確に一致することが保証されます。

input = sys.stdin.readline

# and careful centroid bookkeeping.

sys.setrecursionlimit(10**7)

n, q = map(int, input().split())
color = list(map(int, input().split()))

g = [[] for _ in range(n)]
for _ in range(n - 1):
    u, v = map(int, input().split())
    u -= 1
    v -= 1
    g[u].append(v)
    g[v].append(u)

parent = [-1] * n
depth = [0] * n

def dfs(u, p):
    for v in g[u]:
        if v == p:
            continue
        parent[v] = u
        depth[v] = depth[u] + 1
        dfs(v, u)

dfs(0, -1)

# LCA via binary lifting
LOG = 20
up = [[-1] * n for _ in range(LOG)]
for i in range(n):
    up[0][i] = parent[i]

for k in range(1, LOG):
    for i in range(n):
        if up[k - 1][i] != -1:
            up[k][i] = up[k - 1][up[k - 1][i]]

def lca(a, b):
    if depth[a] < depth[b]:
        a, b = b, a
    diff = depth[a] - depth[b]
    for k in range(LOG):
        if diff & (1 << k):
            a = up[k][a]
    if a == b:
        return a
    for k in range(LOG - 1, -1, -1):
        if up[k][a] != up[k][b]:
            a = up[k][a]
            b = up[k][b]
    return parent[a]

実装の重要な詳細は、色を変更するたびに重心祖先全体で O(log n) 個の更新がトリガーされ、すべてのクエリが完全なパスをスキャンするのではなく、O(log n) 個の重心関連の要約のみを検査することです。

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log² n) | 各更新は O(log n) セントロイド レベルに影響し、内部の各操作は log n マップまたはカウンターを使用します。

 ## 特殊なケース

 単一の頂点カラーは、その制御領域がその頂点を超えて拡大することがないため、安定しています。 複数の再カラー操作を行った後でも、重心の更新はその頂点の寄与にのみ影響し、無関係なパスに誤った交差が発生することはありません。 

すべての頂点が同じ色を共有すると、すべての重心がその色に対してすぐに完全にアクティブになります。 制御領域は 1 つしかないため、パス クエリは常に 1 を返す必要があります。 色が複数の「状態」にまたがることはなく、すべてのノードが一貫した寄与者のままであるため、重心構造はこれを正しく維持します。 

再カラーによって単一の頂点が繰り返し振動する場合、各更新は O(log n) 個の重心祖先にのみ影響します。 データ構造はグローバルなシュタイナー情報を再構築しないため、切り替えを繰り返しても正確性やパフォーマンスが低下することはありません。
