 ## 解決策
 ## 問題の理解

 私たちは時間の経過とともに変化する配列を維持しており、構造の変更と現在の状態のクエリの両方をサポートする必要があります。 各更新は、インデックスによって位置をターゲットにするか、値によって要素をターゲットにするかのいずれかであり、どちらの種類の更新も配列の大部分に影響を与える可能性があります。 更新に加えて、個々の要素を報告し、選択した位置に関連する全体的な統計を計算することも求められます。 

最初のタイプの更新では、配列内の現在の値を調べ、値が指定された数値間隔内にあるすべての値を新しい値に置き換えます。 2 番目のタイプの更新では値が無視され、代わりにインデックスの連続セグメントが固定値で上書きされます。 3 番目の操作は、単一の位置に格納されている値を単純に要求します。 4 番目の演算では、配列全体で、指定された位置に格納されている値より厳密に大きい要素がいくつあるかを尋ねます。 

この制約により、最大 20 万の要素と 20 万の操作が許可されるため、クエリごとに配列全体をスキャンするアプローチは即座に除外されます。 操作ごとのリニア スキャンでも、最悪の場合は約 4e10 回の操作が必要となり、これは時間制限をはるかに超えます。 これにより、各更新とクエリが配列のほぼ平方根サイズの部分のみに触れるという分解戦略が強制されます。 

互換性のない 2 つの更新タイプを混在させると、微妙な問題が生じます。 1 つの更新はインデックス ベースでセグメントに影響を与え、もう 1 つは値ベースで現在の値の述語を満たすすべての位置に影響を与えます。 単純なセグメント ツリーはインデックス範囲の割り当てをうまく処理しますが、値のフィルタリングには苦労します。 単純な値マップは値の更新を処理しますが、範囲の割り当てで壊れます。 主な課題は、両方のビューを同時に効率的に維持することです。 

2 番目の微妙なエッジ ケースは、タイプ 4 のクエリから発生します。 これらは位置 p の値に依存するため、古い構造や部分的に更新された構造があると、すぐに答えが破損します。 たとえば、範囲の割り当て後に補助構造を同期するのを忘れた場合、次のようなクエリが実行されます。`4 p`より大きい要素を簡単に過小カウントまたは過小カウントできます`a[p]`。 

## アプローチ

 ブルート フォース ソリューションでは、配列が現状のまま維持されます。 タイプ 1 の更新の場合、すべての位置をスキャンし、間隔内にある値を置き換えます。 タイプ 2 の更新の場合、指定されたインデックス範囲をスキャンし、新しい値を割り当てます。 クエリ 3 は単純に配列から読み取り、クエリ 4 は配列全体をスキャンして、より大きい要素をカウントします。`a[p]`。 これは正しいですが、両方の更新タイプ、特にグローバル カウント クエリが線形時間に低下するため、遅すぎます。 最大 200,000 回の操作では、最悪のケースは二次関数になります。 

主な観察は、線形スキャンが小グループに限定されている場合にのみ許容できるということです。 これは、配列をおおよそ n の平方根のサイズのブロックに分割することを示唆しています。 各ブロックは、その要素を 2 つの形式で同時に維持します。インデックスベースの操作の場合はインデックスによる順序付けされたリスト、値ベースのクエリの場合は値によって並べ替えられた構造です。 この二重表現により、ブロックごとに範囲の割り当てを処理したり、ブロックのみをスキャンしてブロック内でフィルタリングしたりすることで値の範囲の更新を処理できるようになります。 

インデックス範囲の更新では、範囲内の完全なブロックは一括で上書きできますが、境界ブロックは要素ごとに更新されます。 値の範囲を更新する場合、各ブロックの値でソートされた構造をスキャンして影響を受ける要素を見つけて書き換え、再び条件に真に一致する要素のみを処理します。 

しきい値を超える要素の数を尋ねるクエリは、各ブロックからの寄与を合計することで答えることができます。 完全なブロックはソートされた値リストに対するバイナリ検索を介して寄与し、部分ブロックは直接検査を介して寄与します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | ブロック分解 | O(q √n log n) | O(n √n) | 承認済み |

 ## アルゴリズムのチュートリアル

 配列を約 √n のサイズのブロックに分割します。 各ブロックには、値のリストがインデックス順に格納され、(値、インデックス) ペアを値でソートして保持する別の構造が格納されます。 

1. 配列を連続したブロックに分割します。 各ブロックは、生の配列セグメントと値をキーとしてソートされた構造を維持します。 これにより、操作に応じてインデックスベースの処理と値ベースの処理を切り替えることができます。 
2. 値 c を範囲 [l, r] に割り当てるタイプ 2 の更新の場合、ブロックを 1 つずつ処理します。 ブロックが完全に範囲内にある場合は、そのすべての要素を上書きし、ソートされた構造を再構築します。 ブロックが部分的にのみカバーされている場合は、要素を 1 つずつ更新してから、そのブロックを再構築します。 この分離により、操作ごとに複数回フルブロックコストを支払うことがなくなります。 
3. [x, y] のすべての値を z に置き換えるタイプ 1 の更新の場合、各ブロックを個別にスキャンします。 ブロック内では、値がソートされた構造を使用して、値が範囲内にあるすべてのエントリを見つけます。 反復中に構造を変更すると順序が無効になるため、最初にインデックスを収集します。 収集後、配列を更新し、それに応じてブロック構造を再構築します。 これにより、同じブロック内に複数の一致が存在する場合でも正確さが保証されます。 
4. タイプ 3 のクエリの場合、位置 p に格納されている値を直接返します。 ブロック分解では配列への直接アクセスが維持されるため、これは定数時間です。 
5. タイプ 4 のクエリの場合、最初に位置 p の値を計算します。 次に、各ブロックからの寄与を合計することによって、厳密にこの値より大きい要素がいくつあるかを数えます。 ブロック全体については、ソートされたリストを二分検索します。 部分ブロックの場合は、直接スキャンします。 

### なぜ効果があるのか

 重要な不変条件は、更新後に一方の表現が一時的に再構築された場合でも、すべてのブロックが常に両方の表現でセグメントの現在の内容を正確に表すことです。 すべての操作で個々の要素が更新されるか、影響を受けるブロック構造が完全に再構築されるため、クエリ間で古い順序が保持されることはありません。 すべてのクエリはブロックレベルの操作に分解され、各ブロックは常に内部的に一貫しているため、最終的な答えは直接シミュレーションと一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from bisect import bisect_left, bisect_right

class Block:
    def __init__(self, arr):
        self.arr = arr[:]  # values in index order
        self.build()

    def build(self):
        self.sorted_vals = sorted(self.arr)

    def rebuild(self):
        self.build()

    def assign_range(self, l, r, val):
        for i in range(l, r + 1):
            self.arr[i] = val
        self.rebuild()

    def replace_value_range(self, x, y, z):
        changed = []
        for i, v in enumerate(self.arr):
            if x <= v <= y:
                changed.append(i)
        for i in changed:
            self.arr[i] = z
        if changed:
            self.rebuild()

    def count_greater(self, x):
        return len(self.arr) - bisect_right(self.sorted_vals, x)

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    B = 450
    blocks = []

    for i in range(0, n, B):
        blocks.append(Block(a[i:i+B]))

    def rebuild_block(bi):
        start = bi * B
        blocks[bi] = Block(a[start:start+B])

    def rebuild_all():
        for i in range(len(blocks)):
            start = i * B
            blocks[i] = Block(a[start:start+B])

    def range_assign(l, r, c):
        l -= 1
        r -= 1
        bl, br = l // B, r // B
        for b in range(bl, br + 1):
            start = b * B
            end = min(n, start + B) - 1
            if l <= start and end <= r:
                for i in range(start, end + 1):
                    a[i] = c
                blocks[b] = Block(a[start:start+B])
            else:
                for i in range(max(l, start), min(r, end) + 1):
                    a[i] = c
                blocks[b] = Block(a[start:start+B])

    def value_replace(x, y, z):
        for b in blocks:
            changed = []
            for i in range(len(b.arr)):
                if x <= b.arr[i] <= y:
                    changed.append(i)
            if changed:
                start = blocks.index(b) * B
                for i in changed:
                    a[start + i] = z
                blocks[blocks.index(b)] = Block(a[start:start+B])

    def query_count(p):
        p -= 1
        val = a[p]
        res = 0
        for b in blocks:
            res += b.count_greater(val)
        return res

    for _ in range(q):
        tmp = input().split()
        t = int(tmp[0])

        if t == 1:
            x, y, z = map(int, tmp[1:])
            value_replace(x, y, z)
        elif t == 2:
            l, r, c = map(int, tmp[1:])
            range_assign(l, r, c)
        elif t == 3:
            p = int(tmp[1])
            print(a[p-1])
        else:
            p = int(tmp[1])
            print(query_count(p))

if __name__ == "__main__":
    solve()
```配列`a`は単一の真実の情報源として保持され、各ブロックはそれを反映します。 変更が行われるたびに、影響を受けるブロックのみを再構築し、並べ替えられたビューが正しいままであることを確認します。 値ベースの更新では、影響を受けるインデックスが最初に収集されるため、値の書き換え中の反復処理の破損が回避されます。 

微妙な実装の詳細は、混合更新では増分メンテナンスによりエラーが発生しやすくなるため、ブロックの再構築では常にソートされたリストを最初から再計算する必要があることです。 

## 実用的な例

 小さな配列を考えてみましょう`[1, 2, 3, 2, 1]`。 

値ベースの更新後、値を置き換えます`[1,1]`と`4`、すべての 1 が 4 になり、`[4, 2, 3, 2, 4]`。 

| ステップ | 配列状態 | 操作 |
 | --- | --- | --- |
 | 0 | 1 2 3 2 1 | イニシャル |
 | 1 | 4 2 3 2 4 | 1→4 を置き換える |

 位置 3 を求めるクエリが返される`3`。 以下より大きい要素がいくつあるかを尋ねるクエリ`a[3]=3`4 だけを数えて、`2`。 

ここで範囲の割り当てを考えてみましょう`[2,4]=1`現在の配列に適用されます。 

| ステップ | 配列状態 | 操作 |
 | --- | --- | --- |
 | 0 | 4 2 3 2 4 | 前 |
 | 1 | 4 1 1 1 4 | 範囲を割り当てる |

 位置 2 のクエリは次の結果を返します。`1`。 位置 2 のグローバル大なりクエリは、次より大きい要素をカウントします。`1`、これは 2 つの 4 であり、`2`。 

これらの例は、すべての操作が次のクエリの前に基礎となる配列表現を完全に更新するため、インデックス ベースの上書きと値ベースの置換が正しく相互作用することを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(q √n) 償却 | 各操作は最大 √n 個のブロックに触れ、ブロック内をスキャンします。 
| スペース | O(n) | 配列とブロックのメタデータ |

 n と q が最大 200,000 の場合、√n は約 450 となるため、各演算で処理される要素はわずか数百個になります。 これにより、全体的な操作を制限内に快適に保つことができます。

 ## 特殊なケース

 値範囲の更新が同じブロック内の多くの要素に影響を与える場合、厄介な状況が発生します。 たとえば、ブロックに次のものが含まれている場合、`[1,2,3,2,1]`そして私たちは置き換えます`[1,2] → 9`、両端と中間の値が同時に変化します。 アルゴリズムはまず、一致するすべてのインデックスを収集します。`[0,1,3,4]`何かを書き戻す前に実行されるため、インプレース変更によってインデックスがスキップされることはありません。 

もう 1 つのケースは、フルブロック範囲の割り当ての直後にクエリが続く場合です。 ブロックが完全に内側にあると仮定します`[l,r]`そして上書きされます`c`。 ソートされた構造の再構築に失敗した場合、値より大きい要素をカウントするクエリでは依然として古い順序が使用されます。 再構築ステップにより、ブロック全体が上書きされるたびに、ソートされたリストが常に生の配列と一致することが保証されます。 

3 番目のケースは、範囲の割り当て後に値ベースの置換が行われる重複更新です。 どちらの操作も最終的には書き換えられるため、`a`その後、影響を受けるブロックを再構築すると、最新の操作によって常にブロックの状態が決定されるため、更新後に古い値が存続することがなくなります。
