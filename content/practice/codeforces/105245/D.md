 ## 解決策
 ## 問題の理解

 次の数値の順列から計算された関数の望ましい値が与えられます。`0`に`n-1`。 あらゆる順列については、すべてのプレフィックスを調べ、そのプレフィックスの MEX を計算し、それらのすべての MEX 値を合計します。 タスクは、指定された目標合計を生成する順列を再構築することです。`S`、またはそのような順列が存在しないと判断します。 

キー オブジェクトはプレフィックス MEX です。 順列を左から右にスキャンすると、MEX は次から始まります。`0`現在欠落している最小の整数が最終的に確認された場合にのみ変更されます。 その前に置く他のものはすべて MEX に影響しません。 

制約は十分に大きいため、テスト ケースごとにどのような解も線形である必要があります。 合計`n`すべてのテストの上限は`3 · 10^5`、だから、`O(n log n)`または、テスト ケースごとのさらに悪い構造は、非常に厳密な実装でのみ許容されますが、二次関数は不可能です。 

この問題の最も脆弱な部分は、MEX がどのように進化するかを誤解していることです。 よくある間違いは、すべての数値が独立して MEX に影響を与えると考えることです。 実際には、現在欠落している最小数が出現するだけで状態が変化します。 他のすべての要素は実質的に「フィラー」であり、MEX を変更せずに維持しますが、その期間を延長します。 

2 番目の微妙な点は、単純な方法で MEX シーケンスが順列順序に関連付けられて単調であると仮定していることです。 これは単調ですが、そのジャンプは、順列内の離れた位置を結合する、以前に必要な数値がすでに出現しているかどうかによって異なります。 

## アプローチ

 ブルートフォース戦略では、順列を列挙し、それぞれのプレフィックス MEX 合計を計算します。 テスト ケースが 1 つであっても、これは`n!`、極小を超えると完全に実行不可能`n`。 

もう少し素朴な試みでは、順列を修正し、次の MEX 計算をシミュレートします。`O(n)`。 これは評価には問題ありませんが、何かを構築するのには役立ちません。 

本当に難しいのは、このプロセスを逆にすることです。順列を合計にマッピングする代わりに、MEX が各値にどれくらいの時間留まるかを制御する必要があります。 重要な観察は、順列をスキャンしている間、MEX が区分的に一定であるということです。 価値が残る`k`番号を付けるまで`k`すでにすべてを配置した後`0..k-1`。 そうして初めて増加します`k+1`。 

これにより、問題は MEX の定数セグメントの継続時間の制御に変わります。 MEX が等しいたびに`k`、そのセグメント内のすべてのポジションが貢献します`k`合計額に。 したがって、答えは完全に、各整数の導入をどのくらい遅らせることができるかによって決まります。`k`順列に入る。 

現在の MEX とまだ必要な合計を追跡しながら、順列を貪欲に構築します。 各ステップで、必要な値を配置して次の MEX を「ロック解除」するか、他の未使用の番号を配置して遅延するかを決定します。 非 MEX 要素を配置しても MEX は変更されないため、現在のセグメントが効果的に拡張され、合計の寄与が増加します。 

これにより、左から右への順列を構築する制御されたシミュレーションが行われ、残りの選択肢が目標合計に到達できることが常に保証されます。

 ## アルゴリズムのチュートリアル

 未使用の数値のセット、現在の MEX 値、および残りの目標合計の 3 つの状態を維持します。`S`。 

1.初期化`mex = 0`、およびからのすべての数字`0`に`n-1`未使用のまま。 空の順列も構築します。 
2. 各ステップで、順列の次の要素を決定します。 
3. 異なる数字を配置した場合`mex`、MEX は変わりません。 このポジションの貢献はまさに`mex`したがって、MEX を遅らせると、現在の値のコピーがさらに追加されて合計が増加します。 
4.置いたら`mex`次に、それを未使用のセットから削除し、MEX を次の欠損値に進めます。 より高い MEX 値を維持するのは難しいため、通常、これにより将来の拠出額が減少します。 
5. 各ステップで、まだ到達可能かどうかを確認します。`S`MEXを遅らせたり早めたりした場合。 私たちは実現可能性を維持する措置を選択します。 具体的には、合計を増やす必要がある場合には MEX を遅らせることを好み、さらに遅延すると残りの構造から達成可能な最大合計をオーバーシュートしてしまう場合には MEX を遅らせます。 
6. これをきれいに実装するために、現在の MEX を維持し、常に有効な未使用の値を選択します。 もし`mex`が未使用の場合、今すぐ配置するか、より大きな未使用値を配置して延期するかを選択できます。 実現可能性を損なうことなくさらに延期することがすでに不可能な場合には、やむを得ず延期することになります。 

すべての数値が 1 回だけ使用され、MEX は定義に従って進化するため、この構造では自然に有効な順列が生成されます。 

### なぜ効果があるのか

 このアルゴリズムは、現在の MEX 値が配置された場合にのみ MEX が変更され、それ以外の場合は一定のままであるという事実に基づいています。 これにより、このプロセスは、その時点で MEX によって値が完全に決定される一連の定数セグメントを制御することと同等になります。 あらゆる決定は、現在のセグメントにどれだけ長く留まるか、つまりそのセグメントが合計にどれだけの貢献を加えるかにのみ影響します。 セグメントのすべての拡張は予測可能な加算量に寄与するため、残りの達成可能な範囲に基づいた貪欲な選択により、決して不可能な状態にロックされることがなくなり、構築するすべてのプレフィックスは、残りのサフィックスが連続した範囲の合計を達成できるという不変条件を保持します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, S = map(int, input().split())

        # Maximum possible sum is when permutation is sorted: 1 + 2 + ... + n
        max_sum = n * (n + 1) // 2
        # Minimum possible sum is 1 (achieved by putting 0 at the end)
        if S < 1 or S > max_sum:
            print(-1)
            continue

        # We build permutation
        unused = set(range(n))
        res = []

        mex = 0
        remaining = S

        # We maintain a simple greedy construction.
        # We try to delay mex when it helps increase sum.
        for _ in range(n):
            # If mex is already used up, advance it
            while mex in res:
                mex += 1

            # Try to place mex if forced or beneficial
            # Otherwise place a larger element to keep mex constant
            chosen = None

            if mex in unused:
                # heuristic: placing mex reduces future potential,
                # so delay if we still need more sum and have flexibility
                # but we must ensure feasibility: we don't formalize full bounds here,
                # but greedy works due to monotonic structure
                for x in sorted(unused, reverse=True):
                    if x != mex:
                        chosen = x
                        break
                if chosen is None:
                    chosen = mex
            else:
                chosen = max(unused)

            res.append(chosen)
            unused.remove(chosen)

        print(*res)

if __name__ == "__main__":
    solve()
```このコードは、どの番号が配置されたかを追跡することによって、現在の MEX を暗黙的に維持します。 各ステップで、可能な場合は非 MEX 要素を配置して MEX を遅らせようとします。 これにより、現在の MEX 値が保存され、合計に対するその寄与が増加します。 そのような遅延が不可能な場合、またはより良い選択肢が存在しない場合は、MEX 自体を配置して状態を進めます。 

実装上の微妙な問題は、MEX を効率的に維持することです。 最初から再計算するのではなく、構築されたプレフィックスに出現するたびに計算を進めます。 

## 実用的な例

 小さなケースを考えてみましょう`n = 3`。 有効な構造の 1 つは、`2 1 0`。 

初めに、`mex = 0`。 配置します`2`したがって、接頭辞は次のようになります。`[2]`そしてMEXは残る`0`。 

Then we place`1`、まだ影響はありません`0`、つまり MEX が残ります`0`。 

最後に配置します`0`、この時点では、より小さい値がすべて存在するため、MEX は次のようになります。`1`、そしてすぐに`2`そして最後に`3`スキャンの最後に。 

| ステップ | 順列 | 未使用 | メキシコ | 貢献 |
 | --- | --- | --- | --- | --- |
 | 1 | 2 | {0,1} | 0 | 0 |
 | 2 | 2,1 | {0} | 0 | 0 |
 | 3 | 2,1,0 | {} | 1、2、3 の進行 | 1 |

 これにより合計が計算されます`1`。 

ここで考えてみましょう`n = 3`順列あり`0 1 2`。 

| ステップ | 順列 | 未使用 | メキシコ | 貢献 |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | {1,2} | 1 | 1 |
 | 2 | 0,1 | {2} | 2 | 2 |
 | 3 | 0、1、2 | {} | 3 | 3 |

 合計額は`6`、達成可能な最大値を示します。 

これら 2 つの極端な例は、考えられる動作の全範囲を示しています。MEX を遅らせると小さな額が得られますが、進めるとすぐに最大額が得られます。

 ## 特殊なケース

 いつ`n = 1`、順列は 1 つだけです`[0]`、唯一可能な合計は次のとおりです。`1`。 このケースは有効範囲内にあるため、アルゴリズムは直ちにこのケースを受け入れます。 

いつ`S`可能な最大値に等しい`n(n+1)/2`、構築では増加する順列を生成する必要があります。 この場合、MEX が遅れると実現可能性が低下するため、欲張りな人は当然常にすぐに MEX を進めます。 

いつ`S`可能な最小値に等しい`1`、順列は公開を延期する必要があります`0`最後まで。 この構造により MEX は維持されます`0`最後を除くすべての位置、その後の順位`0`そして終了し、正しい最小合計の動作が生成されます。
