 ## 解決策
 ## 問題の理解

 時間の経過とともに変化する括弧文字列が与えられます。 更新のたびに、現在の文字列の部分文字列がいくつあるかを計算して、正確で完全にバランスの取れたブラケット シーケンスを形成する必要があります。 

部分文字列が括弧として解釈された場合、残高が決してマイナスにならず、合計残高が 0 で終わる場合、その部分文字列は答えに寄与します。 部分文字列自体を出力するように求められるのではなく、隣接する文字が交換されるたびにそのような部分文字列がいくつ存在するかだけを求められます。 

主な難しさは、すべての操作で隣接する 2 つの文字が交換され、最大 200,000 の操作があることです。 文字列も大きいため、交換のたびに答えを最初から再計算するのは遅すぎます。 

単純な再計算では、すべての O(n^2) 個の部分文字列をスキャンし、それぞれを O(n) で検証しますが、これはまったく実行不可能です。 プレフィックスバランスとスタックベースのチェックを使用したクエリごとの 1 回の再計算でも O(n) のコストがかかり、最悪の場合は O(nq) になります。 

この制約により、各スワップが非常に小さなローカル領域にのみ影響を及ぼし、高速更新をサポートするデータ構造でグローバル情報を維持するという解決策が求められます。 

微妙なエッジ ケースの 1 つは、スワップにより、スワップされた位置をはるかに超えた正しい部分文字列が作成または破壊される場合です。 たとえば、次のような長い交互パターン内で交換します。```
()()()()()
```スワップされたペアに関係する部分文字列だけでなく、多くの有効な部分文字列を変更できます。 これにより、固定ウィンドウのみを更新するソリューションは除外されます。 

## アプローチ

 ブルートフォース手法では、各スワップ後にすべての部分文字列をチェックしてスコアを再計算します。 各部分文字列について、バランス カウンターを使用して、それが通常のブラケット シーケンスであるかどうかを検証します。 これは、部分文字列ごとに O(n) と O(n^2) 個の部分文字列を必要とし、クエリごとに O(n^3) を与えますが、これはすでに不可能です。 プレフィックス合計を使用して検証を O(1) に改善しても、これはクエリあたり O(n^2) に減少しますが、それでも大きすぎます。 

より合理的なベースラインは、スタックまたはプレフィックスのバランスと動的プログラミング スタイルのカウントを使用して、クエリごとに O(n) で答えを再計算することです。 これはまだ O(nq) であり、最悪の場合でも約 4e10 回の演算に相当します。 

重要な洞察は、その答えは、ローカルな貢献を通じて表現できるグローバルな構造に依存するということです。 有効な各部分文字列は、一致する括弧の構造に対応し、各文字は、シーケンスをプリミティブなバランスの取れたセグメントに正規に分解する際に、最大 1 つの構造単位に参加します。 

これは、セグメント内に有効な部分文字列がいくつ存在するかを追跡すると同時に、開き括弧と閉じ括弧がセグメント境界を越えてどのように「流れる」かを追跡するセグメント構造を維持することを示唆しています。 正しいツールは、区間ごとに、その中に存在するバランスの取れた部分文字列の数と、2 つの半分をマージするのに十分な情報を格納するセグメント ツリーです。 

スワップは 2 つの隣接する位置にのみ影響するため、一定数のセグメント ツリーの葉のみが変更されます。 これらの葉を更新した後、O(log n) でツリーをプルアップして答えを再計算します。 各ノードのマージでは、境界を越えて新しく形成された有効な部分文字列を考慮しながら、左と右の子を結合する既知のブラケット シーケンス DP が使用されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | クエリあたり O(n^2) | O(n) | 遅すぎる |
 | セグメント ツリー マージ DP | クエリあたり O(log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列上のセグメント ツリーを維持します。 各ノードは間隔を表し、その間隔内およびマージ全体にわたる有効な部分文字列の数を計算するのに十分な情報を保存します。 

各ノードには以下が保存されます。 

セグメントに完全に含まれる有効な部分文字列の数に加えて、マージ時に左側の開き括弧と右側の閉じ括弧を一致させることを可能にするバランス プロファイル。 

各セグメントに対して次のように定義します。 

1. 内部的に形成された一致したペアの数。 
2. マージをサポートする方法で、一致しない「(」と「)」がいくつ残っているかを追跡する構造。 

わかりやすく考えると、各セグメントは一致しない括弧の複数セットのように動作し、マージによって一致が貪欲にキャンセルされ、同時に新しく形成されたバランスの取れた部分文字列が蓄積されるということです。 

### ステップ

 1. 各葉が 1 つの文字に対応するセグメント ツリーを構築します。 リーフには、それが開始括弧であるか終了括弧であるか、およびゼロの内部一致が格納されます。 
2. 内部ノードごとに、左側の子 A と右側の子 B の間のマージ操作を定義します。マージ中に、A のできるだけ多くの '(' と B の ')' が一致します。 このような各一致は、境界をまたがる有効な部分文字列の形成に役立ちます。 
3. マージ時に以下を計算します。 

貪欲な方法で、左からの不一致の開始と右からの不一致の終了をペアにすることによって作成された、新しい境界を越えた有効な部分文字列の数。 これは、利用可能な一致しないカウント間の最小操作を使用して行われます。 
4. ノードの合計答えは、両方の子からの答えの合計に、マージ中に計算された境界を越えた寄与を加えたものです。 
5. 各交換操作では、位置 p と p+1 の文字が交換されます。 セグメント ツリーの両方のリーフを更新し、影響を受けるノードをルートまで再計算します。 
6. 各更新の後、ルートは完全な文字列の合計スコアを保存し、それを出力します。 

### なぜ効果があるのか

すべての有効な部分文字列は、括弧のペア構造に対応します。 セグメント ツリーは、そのようなすべての構造が、それを完全に含む最小の間隔で 1 回だけカウントされることを保証します。 内部の部分文字列は子ノードでカウントされますが、境界を越える部分文字列は、マージ中に 2 つの部分が出会うときに正確にカウントされます。 2 つの独立したセグメント間の最適なマッチングは交差しない方法でペアにする必要があり、セグメント境界によって内部構造の独立性が強制されるため、一致しないオープンとクローズの間の貪欲なペアリングは有効です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("ans", "open", "close")
    def __init__(self, ans=0, open_=0, close_=0):
        self.ans = ans
        self.open = open_
        self.close = close_

def merge(a, b):
    res = Node()
    res.ans = a.ans + b.ans
    match = min(a.open, b.close)
    res.ans += match

    res.open = a.open + b.open - match
    res.close = a.close + b.close - match
    return res

class SegTree:
    def __init__(self, s):
        self.n = len(s)
        self.t = [Node() for _ in range(4 * self.n)]
        self.s = s
        self.build(1, 0, self.n - 1)

    def build(self, v, l, r):
        if l == r:
            if self.s[l] == '(':
                self.t[v] = Node(0, 1, 0)
            else:
                self.t[v] = Node(0, 0, 1)
            return
        m = (l + r) // 2
        self.build(v * 2, l, m)
        self.build(v * 2 + 1, m + 1, r)
        self.t[v] = merge(self.t[v * 2], self.t[v * 2 + 1])

    def update(self, v, l, r, pos):
        if l == r:
            if self.s[pos] == '(':
                self.t[v] = Node(0, 1, 0)
            else:
                self.t[v] = Node(0, 0, 1)
            return
        m = (l + r) // 2
        if pos <= m:
            self.update(v * 2, l, m, pos)
        else:
            self.update(v * 2 + 1, m + 1, r, pos)
        self.t[v] = merge(self.t[v * 2], self.t[v * 2 + 1])

    def query_all(self):
        return self.t[1]

def solve():
    n, q = map(int, input().split())
    s = list(input().strip())

    st = SegTree(s)
    arr = s

    for _ in range(q):
        p = int(input()) - 1
        arr[p], arr[p + 1] = arr[p + 1], arr[p]

        st.s = arr
        st.update(1, 0, n - 1, p)
        st.update(1, 0, n - 1, p + 1)

        print(st.query_all().ans, end=' ')

if __name__ == "__main__":
    solve()
```この実装は、各ノードが一致しない開き括弧と閉じ括弧、およびその間隔内で形成された一致するペアの数を追跡する標準セグメント ツリーに依存しています。 The merge function is the critical part, since it ensures that any new valid structure formed across a boundary is counted exactly once.

 The update step touches only the two swapped positions, and each update propagates in O(log n), keeping the solution efficient.

 ## 特殊なケース

 重要なエッジ ケースは、スワップによって、以前は不可能だったセグメント境界を越えた新しいバランスが作成される場合です。 たとえば、ほぼ交互の文字列では、単一のスワップで開始と終了を整列させることができるため、多数の新しい部分文字列が有効になります。 セグメント ツリーのマージでは、すべての境界の再計算で一致しない括弧間の最大の一致が再評価されるため、これが正しく処理されます。 

もう 1 つのエッジ ケースは、同じ位置でスワップが繰り返されることで、数ステップにわたってグローバル バランスを変更せずにローカル構造を切り替えることができます。 更新はローカルで完全に再計算されるため、ツリーに古い情報が残らず、スコアの一貫性が保たれます。
