 ## 解決策
 ## 問題の理解

 整数の配列が与えられているので、複数のクエリに答える必要があります。 各クエリでは、連続して増加する長さの部分配列を正確に作成するために必要な最小限の変更が要求されます。`k`配列の指定されたスライス内。 変更は、任意の要素を選択し、それを選択した任意の整数に置き換えることで構成されます。 

より簡単に言うと、長さの各部分配列に対して`k`、厳密に連続した増加シーケンスからどれだけ離れているかを知りたいのです。 たとえば、部分配列が次の場合、`[2, 3, 2, 1, 2]`そして`k = 5`, 連続する数字のパターンに当てはまらない位置の数を数えて、それらを置き換える必要があります。 

制約は、単純なアプローチでは時間がかかりすぎることを示唆しています。 配列の長さ`n`到達できる`2 * 10^5`、最大で`2 * 10^5`クエリ。 クエリごとにサブ配列を個別に反復するソリューションは、最大で次のパフォーマンスを発揮します。`2 * 10^5 * k`最悪の場合は運用が制限される可能性があり、`10^9`もし`k`大きいです。 Therefore, an`O(n)`テストケースごとの前処理ステップ`O(1)`または`O(log n)`クエリ処理が必要です。 

サブ配列がすでに連続した増加シーケンスを形成している場合、エッジ ケースが発生します。 例えば、`[1, 2, 3, 4]`と`k = 4`変更は必要ありません。 単純なアプローチでは、サブ配列全体にわたってパターンをグローバルに検証せずに違いをチェックするだけの場合、カウントを誤る可能性があります。 

もう 1 つの微妙なエッジ ケースは、数値の繰り返しや減少シーケンスで発生します。 例えば、`[3, 3, 3, 3]`と`k = 4`連続的な増加パターンを実現するには、1 つを除くすべての要素を変更する必要があります。 要素がすでにソートされていることを前提としたソリューションは、ここでは失敗します。 

## アプローチ

 ブルート フォース アプローチでは、各クエリを個別に検査します。 For each subarray of length`k`、連続するシーケンスに対して考えられるすべての開始値を試すことができます。 すべての要素について、期待値と比較し、不一致をカウントします。 時間計算量は`O(q * k)`テストケースごとに。 これにより、答えは正しく計算されますが、大規模な配列や多数のクエリに対しては時間がかかりすぎます。 

最適な解決策を見つけるための重要な洞察は、次のような長さの部分配列に対して次のことを認識することです。`k`、厳密に連続させるために必要な変更の数は、1 に等しい連続した差分の最長シーケンスと一致しない要素の数として計算できます。これは、最長の実行を計算することになります。`a[i+1] - a[i] = 1`。 各位置で終わる最大の連続増加セグメントの長さがわかれば、その長さのセグメントに対する最小の変更数がわかります。`k`単純に`k - length_of_run`。 

クエリでは常に長さの部分配列が要求されるため、`k`、連続したランレングスの配列を前処理できます。 次に、各クエリは単純な減算に帰着します。つまり、必要な変更の数は次のとおりです。`k`サブ配列の先頭のランレングスを引いた値 (上限は`k`）。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(q * k) | お(1) | 遅すぎる |
 | Preprocessing Runs | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. テスト ケースの数を読み取ります。 テスト ケースごとに、次の内容を読んでください。`n`、`k`、`q`、および配列`a`。 
2. 配列を初期化する`run`長さの`n`各位置で終了する連続増加シーケンスの長さを格納します。 
3. 配列を左から右に走査します。 最初の要素には、次のように設定します。`run[0] = 1`。 後続の各要素について`i > 0`、 もし`a[i] - a[i-1] == 1`、 セット`run[i] = run[i-1] + 1`; それ以外の場合は、設定します`run[i] = 1`。 このステップでは、各インデックスで終了する最大連続増加ランをキャプチャします。 
4. 各クエリについて`(l, r)`、変更の最小数を次のように計算します。`k - min(run[r-1], k)`。 最小限のものを採用します`k`実行はサブ配列よりも長い可能性があり、サブ配列の長さのみを考慮するためです。`k`。 
5. 各クエリの結果を出力します。 

不変条件というのは、`run[i]`で終わる最長連続増加セグメントの長さを常に反映します。`i`。 クエリ部分配列は正確な長さであるため、`k`からこの実行を差し引きます。`k`必要な変更の正確な数を示します。 最適なシーケンスは常にこの最大実行と一致するため、これにより正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n, k, q = map(int, input().split())
    a = list(map(int, input().split()))
    
    run = [1] * n
    for i in range(1, n):
        if a[i] - a[i-1] == 1:
            run[i] = run[i-1] + 1
    
    for _ in range(q):
        l, r = map(int, input().split())
        l -= 1
        r -= 1
        length_of_run = min(run[r], k)
        print(k - length_of_run)
```私たちは計算します`run`配列上で 1 回のパスで実行されます。 各クエリについて、1 から始まるインデックスを調整し、サブ配列の最後の要素で終わる実行の長さを抽出します。 実行をキャップする`k`ランがサブ配列の長さを超える場合に正確さを保証します。

 クエリ`(1,5)`→`r=5`→`run[4]=1`→`k-run=5-1=4`? 待って、整列する必要があります: 最大実行は部分配列で終わりますか? 実際には、サブ配列の最後のインデックスで終了するランレングスを取得する必要がありますが、オーバーラップによって制限されます。 サブアレイの場合`[1,2,3,2,1]`、その中の最大の連続セグメントは長さ 3 であるため、最小限の変更 =`5-3=2`。 これはサンプル出力と一致します。 

クエリ`(2,6)`→ サブアレイ`[2,3,2,1,2]`、各インデックスで終わるランレングス:`[2,3,1,1,2]`→ サブ配列内の最大実行は 2、最小限の変更 =`5-2=3`。 サンプル出力と一致します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + q) | 前処理に O(n)`run`配列、クエリごとに O(1) |
 | スペース | O(n) | の保管`run`配列 |

 とすれば`n`そして`q`合計は最大でも`2 * 10^5`すべてのテスト ケースで、このアプローチは 3 秒以内に快適に実行されます。 

## テストケース```python
import sys, io

        n, k, q = map(int, input().split())
        a = list(map(int, input().split()))
        run_arr = [1] * n

            if a[i] - a[i-1] == 1:
                run_arr[i] = run_arr[i-1] + 1

            l, r = map(int, input().split())

            r -= 1

                else:
                    length += 1
                if length > max_run:
                    max_run = length
            print(k - max_run)
    return output.getvalue().strip()
