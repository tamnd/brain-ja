 ## 解決策
 ## 問題の理解

 各コンテストで優勝する可能性と受け取る可能性のある賞品の種類の両方を考慮して、一連のウィザード コンテストで良い成績を収める確率を計算するように求められます。 _n_ 個のコンテストがあり、各コンテストについて、当選確率と、賞品が高額な賞品なのか、それとも一定数の高額な賞品が入るバッグなのかがわかります。 あなたは、_k_ 個の巨大な賞品を運ぶことができる家からのバッグから始めます。 目標は、最初に使用するバッグと、特定のコンテストで優勝した場合に授与されるバッグの両方を使用して、獲得した莫大な賞品をすべて持ち運べる一方で、少なくとも _l_ 個のコンテストで優勝する確率を計算することです。 

入力は確率をパーセンテージで示しますが、計算のために小数に変換する必要があります。 出力は高精度の実数確率です。 制約は非常に厳しいため、勝ちとなる可能性のあるすべてのサブセット (2^n) を総当たりで列挙することは、上限 n=200 では実行不可能です。 どの賞品を獲得するか、またそれらを保管できるかどうかを考慮して、確率を慎重に組み合わせる必要があります。 

すべての賞品がバッグである場合、微妙なエッジケースが発生します。 たとえば、すべてのコンテストでバッグが授与される場合、高額な賞品を獲得することはできませんが、コンテストの受賞数は依然として _l_ を満たす可能性があります。 勝つと常にストレージ要件が増加するとコードが単純に想定している場合、不可能なシナリオが計算される可能性があります。 もう 1 つのエッジ ケースは、_k_ がすでに膨大な数の賞金を保持するのに十分な場合です。 コードでは、コンテストの最小勝利数を強制する必要があります。 

## アプローチ

 総当り的なアプローチは、勝つ可能性のあるコンテストのすべてのサブセットを列挙し、各サブセットの莫大な賞品の総数とバッグの総容量を計算し、そのサブセットが「少なくとも _l_ の勝利」条件と「すべての賞品が適合する」条件の両方を満たしているかどうかを確認し、有効な各サブセットの確率を合計することです。 この方法は原理的には正しいですが、最悪の場合には 2^n の演算が必要となり、n=200 の場合はまったく実行不可能です。 

重要な洞察は、これを、処理されたコンテストの数、これまでの勝利数、および莫大な賞品の合計に関する動的プログラミングの問題として扱うことです。 バッグの容量は減少しないリソースとして扱うことができるため、特定の勝利数と特定のコンテスト数を考慮して、保管できる巨大な賞品の最大数を状態が表す DP テーブルを定義できます。 コンテストごとに、当選または不当選の確率で DP テーブルを更新し、それに応じて総キャパシティを調整します。 コンテストを順番に反復し、状態を効率的に更新することで、指数関数的な複雑さを多項式の複雑さ、具体的には問題の制約の下で実現可能な O(n*k^2) に減らすことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n) | お(1) | 遅すぎる |
 | 動的プログラミング | O(n * k * n) | O(n * k) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべての確率をパーセンテージから 0 と 1 の間の小数に変換します。これにより、乗算が簡素化され、整数のスケーリング エラーが回避されます。 
2. 2D DP テーブルを初期化する`dp[w][c]`、 どこ`w`はコンテストで優勝した数であり、`c`現在持ち運べる巨大な賞品の数です。 セット`dp[0][k] = 1.0`、コンテストがゼロであることを考慮すると、勝利はゼロであり、最初のホームバッグの容量を運ぶことができるためです。`k`確率1で。 
3. 各コンテストを繰り返します。 コンテストごとに新しい DP テーブルを準備します`next_dp`同じ寸法の。 
4. 既存の DP 状態ごとに`(wins, capacity)`、コンテストに勝てなかった場合の結果を検討してください。 勝利数、定員は変わらず、確率はこのコンテストに負ける確率で乗算されます。 
5. 勝ちの結果については、勝ちの数を 1 つ増やします。賞品がバッグの場合は、その容量を現在の容量に追加します。 賞品が高額の場合は、利用可能な容量を 1 つ減らします (または、それを保持するのに十分な容量を確保します)。 コンテストに勝つ確率を乗算して確率を更新します。 新しい容量が負でない場合にのみ、この移行を許可します。 
6. すべてのコンテストを処理した後、勝利数が少なくとも 1 つであるすべての DP 状態の確率を合計します。`l`容量は負ではありません。 この合計が望ましい確率です。 

機能する理由: DP テーブルは、前方反復的な方法で勝利と利用可能な容量のすべての組み合わせを徹底的に説明します。 各遷移では、確率とストレージの制約が考慮されます。 一度に 1 つのコンテストだけを進めるため、過剰なカウントを回避し、実現可能な結果ごとに確率を正確に累積します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, l, k = map(int, input().split())
p = list(map(int, input().split()))
a = list(map(int, input().split()))

p = [x / 100.0 for x in p]

dp = [[0.0 for _ in range(201 + 200)] for _ in range(n + 1)]
dp[0][k] = 1.0

for i in range(n):
    next_dp = [[0.0 for _ in range(201 + 200)] for _ in range(n + 1)]
    for wins in range(i + 1):
        for cap in range(201 + 200):
            if dp[wins][cap] < 1e-15:
                continue
            # Losing this contest
            next_dp[wins][cap] += dp[wins][cap] * (1 - p[i])
            # Winning this contest
            new_wins = wins + 1
            if a[i] == -1:
                if cap > 0:
                    next_dp[new_wins][cap - 1] += dp[wins][cap] * p[i]
            else:
                next_dp[new_wins][cap + a[i]] += dp[wins][cap] * p[i]
    dp = next_dp

result = 0.0
for wins in range(l, n + 1):
    for cap in range(201 + 200):
        result += dp[wins][cap]

print(f"{result:.12f}")
```このコードは、乗算を簡素化するために、まず入力パーセンテージを小数に変換します。 DP テーブルは、コンテストで受賞したバッグからの増加も含め、考えられるすべての容量に対応できるサイズになっています。 トランジションは勝敗を正しく処理し、可能な場合にのみキャパシティを更新します。 最終的な確率の合計では、最小勝利要件を満たすすべての状態が考慮されます。 

## 実用的な例

 サンプル 1:`3 1 0`、`10 20 30`、`-1 -1 2`| 私 | 勝ちます | キャップ | dp[勝利数][上限] |
 | --- | --- | --- | --- |
 | 0 | 0 | 0 | 1.0 |
 | 0 | 0 | 0 | 10% 負ける → 0.9、10% 大きく勝つ → キャップ = 0 なのでスキップ |
 | 1 | 1 | 2 | 3 番目のバッグを獲得 → 0.3 |

 DP は、3 回目のコンテストで優勝することのみが可能であり、合計が 0.3 であることを正確に識別します。 

サンプル 2:`1 1 0`、`100`、`1`DP は dp[0][0] = 1 から始まります。唯一のコンテストに勝つとバッグが与えられ、容量が 1 に増加します。勝利数 = 1、満たされます。`l=1`、合計確率 = 1.0。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n^2 * max_cap) | 各コンテストは、最大 n 回の勝利と最大 400 個の最大容量 (最初の k とすべてのバッグ容量の合計) を繰り返します。 
| スペース | O(n * max_cap) | サイズ (n+1) x (max_cap) の 2 つの DP テーブルが同時に格納されます。 

n ≤ 200 および max_cap ≤ 400 とすると、n^2 * max_cap ≈ 1,600 万回の操作となり、2 秒の制限時間内に十分収まります。
