 ## 解決策
 ## 問題の理解

 各テスト ケースでは、Polycarp が π の数字を記憶しようとして書き留めた数字の文字列が与えられます。 タスクは、π の先頭の何桁がこの文字列の接頭辞と一致するかを判断することです。 

π を再構成したり、エラーを修正したりするわけではありません。 与えられた数字列を既知の参照シーケンスの π 数字と比較し、最初の不一致で停止するだけです。 テスト ケースの答えは、完全に一致する最長のプレフィックスの長さです。 

制約は小さく、各文字列は最大 30 文字で、テスト ケースは最大 1000 個です。 これは、保存されている参照文字列との単純な文字ごとの比較でも十分に高速であることを意味します。 総作業量は約 30,000 文字の比較に制限されています。 

主な微妙な点は、先頭のゼロと初期の不一致にあります。 よくある間違いは、数値比較を想定したり、π の先頭の数字「3」を無視したりすることです。 

いくつかの危険な状況が重要になります。 

「000」のような文字列は、π が「3」で始まるため、すぐに 0 を返すはずで、最初の文字はすでに失敗しています。 

「31420」など、「3」で始まり後で分岐する文字列は、正しいプレフィックス「314」のみをカウントする必要があります。 

「3141592653」のような完全に正しいプレフィックスは、π の始まりと一致する場合、その完全な長さを返す必要があります。 

## アプローチ

 最も直接的なアイデアは、入力文字列を事前に計算された接頭辞 π と比較することです。 π 桁は、考えられるすべての入力をカバーするのに十分な長さの文字列 (たとえば、「314159265358979323846264338327...」) として保存します。 

各テスト ケースでは、左から右にスキャンして、不一致が見つかるか入力文字列の末尾に到達するまで文字を比較します。 停止するインデックスが答えです。 

最大入力長が小さいため、この総当り手法はこの問題ではすでに最適です。 比較を繰り返し再計算したり、スライスを使用したりしても、複雑さは合計入力サイズにおいて線形のままです。 

これを理解するためのより抽象的な方法は、2 つの文字列 (指定された数値と固定参照文字列) 間の最長の共通プレフィックスを計算していることです。 1 つの文字列は定数であるため、ハッシュやサフィックス構造などの高度な前処理は必要ありません。

 ## アルゴリズムのチュートリアル

 1. π の桁を、先頭の 3 を含む小数点以下の最初の桁から始まる固定の文字列として格納します。 
2. 各テスト ケースについて、Polycarp の記憶された数字を表す入力文字列を読み取ります。 
3. カウンタをゼロに初期化します。 このカウンタは、入力文字列と π の間で一致する連続した数字の数を追跡します。 
4. 入力文字列の文字を左から右に繰り返します。 各位置 i について、input[i] と pi_digitals[i] を比較します。 
5. 文字が等しい場合は、カウンタをインクリメントして続行します。 
6. 不一致が発生した場合は、それ以上の数字は正しいプレフィックスに含まれないため、すぐに停止します。 
7. カウンタを出力します。 

重要な考え方は、プレフィックスの正確性は単調であるということです。 不一致が発生すると、比較を拡張しても正確さを回復することはできません。 

### なぜ効果があるのか

 すべての位置 i で、アルゴリズムは i より前のすべての位置が π と正確に一致することを保証します。 最初の不一致は、正しい記憶と誤った記憶の境界を定義します。 再配置や部分一致ではなく、前置一致のみを考慮するため、停止条件は正確性のために十分かつ必要です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

PI = "314159265358979323846264338327950288419716939937510"

t = int(input())
for _ in range(t):
    s = input().strip()
    ans = 0
    for i in range(len(s)):
        if i < len(PI) and s[i] == PI[i]:
            ans += 1
        else:
            break
    print(ans)
```この解決策は、事前に計算された π 桁の文字列に依存します。 ループは各文字を位置的に比較し、不一致の場合はすぐに停止します。 境界チェック`i < len(PI)`は安全対策ですが、この定数はすべての制約に対して十分な長さです。 

よくある実装上の間違いは、改行文字を削除するのを忘れることです。これにより、誤った比較が発生します。 もう 1 つは、文字列を不必要に整数に変換することです。これにより、メリットがなく比較が複雑になります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 ## 特殊なケース

 「000」のような入力の場合、アルゴリズムは最初の文字を π の「3」と比較し、すぐに停止し、0 を返します。これにより、先頭の無効な数字がそれ以上スキャンすることなく正しく処理されることが確認されます。 

「314159」などの完全に一致するプレフィックスの場合、各文字は順番に一致し、カウンタは 6 に達します。ループは文字列を使い尽くした後にのみ自然に終了し、完全一致が正しく処理されていることを確認します。 

「31420」のような混合ケースの場合、最初の 3 文字までは一致が続行され、4 文字目で失敗し、結果は 3 で安定し、最初の不一致で正しい早期終了が示されます。
