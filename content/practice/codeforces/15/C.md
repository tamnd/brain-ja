 ## 解決策
 ## 問題の理解

 各採石場は、標準的な Nim ゲームに連続した範囲のヒープ サイズを提供します。 

採石場が私たちに価値を与えてくれるなら`(x, m)`、そのダンパーには以下が含まれます。$$x,\ x+1,\ x+2,\ \dots,\ x+m-1$$すべての採石場からのすべてのダンプが一緒になって、1 つの大きなニム陣地を形成します。 通常の Nim がプレイされるため、勝者はすべてのヒープ サイズの xor のみに依存します。 xor の合計がゼロ以外の場合、最初のプレーヤーが勝ちます。 それ以外の場合は、2 番目のプレイヤーが勝ちます。 

このタスクの直接の解釈は次のとおりです。$$(x) \oplus (x+1) \oplus \dots \oplus (x+m-1)$$すべての採石場について、それらすべての結果を XOR します。 

この制約により、ヒープを個別に反復処理することが完全に排除されます。 1 つの採石場には最大で次のものを含めることができます。$10^{16}$ダンパー、あるかもしれない$10^5$採石場。 すべてのヒープを格納することさえ不可能であり、ましてやそれらを 1 つずつ処理することは不可能です。 

このため、連続する整数に対する xor の数学的ショートカットを探す必要があります。 

厄介な点は、多くのプログラマは範囲の合計の式を覚えているにもかかわらず、xor の動作が異なることです。 単純な適応は境界条件で失敗することがよくあります。 

次の入力を考えてみましょう。```
1
1 4
```ヒープは次のとおりです。```
1 2 3 4
```それらの xor は次のとおりです。$$1 \oplus 2 \oplus 3 \oplus 4 = 4$$手動でパターンを導出しようとする不注意な実装により、簡単に次のような問題が発生する可能性があります。`0`ここ。 

もう 1 つの簡単な間違いは、ゼロから始まる範囲の処理を誤ることです。 標準の prefix-xor 式では次のものが使用されます。$$0 \oplus 1 \oplus 2 \oplus \dots \oplus n$$次のように処理するとします。```
1
2 1
```答えは単純です`2`、ヒープが 1 つしかないためです。 計算すると:$$f(r) \oplus f(l)$$の代わりに：$$f(r) \oplus f(l-1)$$すぐに間違った結果が得られます。 

大きな値も重要です。 までの数字で$10^{16}$、固定幅の 32 ビット整数ロジックは多くの言語でオーバーフローします。 Python はこれを自動的に処理しますが、アルゴリズムは依然として採石場ごとに対数または定数時間を維持する必要があります。 

## アプローチ

 ブルートフォースのアイデアは完全に単純です。 採石場ごとに、次の間隔ですべてのヒープ サイズを生成します。$$[x,\ x+m-1]$$そしてそれらを一緒に XOR します。 

これは、Nim の位置が xor を通じて結合されるため機能します。 最後の xor がゼロ以外の場合、最初のプレーヤーが勝ちます。 そうしないと、2 番目のプレイヤーが負けます。 

問題は規模だ。 単一の採石場に含まれるもの$10^{16}$山盛り。 1 秒あたり 10 億のオペレーションを処理しても、依然として絶望的に遅いでしょう。 最悪の場合、総当たり攻撃にはおおよそ次のものが必要になります。$$10^5 \times 10^{16} = 10^{21}$$操作。 

重要な観察は、連続する整数に対する xor には繰り返し構造があるということです。 

定義する：$$pref(n)=0 \oplus 1 \oplus 2 \oplus \dots \oplus n$$この場合、任意の間隔での xor は次のようになります。$$l \oplus (l+1) \oplus \dots \oplus r = pref(r)\oplus pref(l-1)$$なぜなら、以前のすべての値は`l`は 2 回表示され、自動的にキャンセルされます。 

今必要なのは、高速に計算する方法だけです`pref(n)`。 

いくつかの値を書き出すと次のようになります。 

| n | 優先度(n) |
 | --- | --- |
 | 0 | 0 |
 | 1 | 1 |
 | 2 | 3 |
 | 3 | 0 |
 | 4 | 4 |
 | 5 | 1 |
 | 6 | 7 |
 | 7 | 0 |

 長さ 4 のサイクルが表示されます。$$pref(n)= \begin{cases} n & n \bmod 4 = 0 \\ 1 & n \bmod 4 = 1 \\ n+1 & n \bmod 4 = 2 \\ 0 & n \bmod 4 = 3 \end{cases}$$これにより、各採石場は最大で$10^{16}$一定時間までの操作。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(\sum m_i)$|$O(1)$| 遅すぎる |
 | 最適 |$O(n)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 採石場の数を読み取ります。 
2. 変数を維持する`nim_sum`、最初は`0`。 

これは、すべての採石場のすべてのヒープの xor を保存します。 
3. 採石場ごとに、次を計算します。$$l = x$$

$$r = x+m-1$$採石場は区間内のすべての整数を提供します`[l, r]`。 

1. プレフィックス xor を使用して間隔の xor を計算します。$$range\_xor = pref(r) \oplus pref(l-1)$$以下のすべての数字`l`両方のプレフィックス xor に表示され、相殺されます。 

1. この間隔の寄与を XOR します。`nim_sum`。 
2.すべての採石場を処理した後、チェックを入れます`nim_sum`。 

ゼロ以外の場合、最初のプレイヤーが Nim のポジションを獲得しているため、次のように出力します。`"tolik"`。 

それ以外の場合は印刷します`"bolik"`。 

### なぜ効果があるのか

 正確さは 2 つの標準 Nim プロパティから得られます。 

まず、独立したヒープが XOR によって結合されます。 すべてのヒープ サイズの XOR が 0 以外の場合、ゲーム全体が最初のプレイヤーの勝利となります。 

2 番目に、xor は自動的にキャンセルされます。$$a \oplus a = 0$$それで：$$pref(r)\oplus pref(l-1)$$以下のすべての数字を削除します`l`、区間の xor だけを残します`[l, r]`。 

の`pref(n)`連続する整数に対する xor は 4 つの数値ごとに繰り返されるため、式は正しいです。 4 つの連続する整数を追加すると、常に同じパターンが復元され、以下に基づいて閉じた形式のケースが生成されます。`n % 4`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def pref_xor(n):
    if n % 4 == 0:
        return n
    if n % 4 == 1:
        return 1
    if n % 4 == 2:
        return n + 1
    return 0

n = int(input())
nim_sum = 0

for _ in range(n):
    x, m = map(int, input().split())

    l = x
    r = x + m - 1

    nim_sum ^= pref_xor(r) ^ pref_xor(l - 1)

print("tolik" if nim_sum else "bolik")
```ヘルパー関数`pref_xor(n)`計算します:$$0 \oplus 1 \oplus \dots \oplus n$$反復モジュロ 4 パターンを使用して一定時間で実行します。 

採石場ごとに、コードは次のように変換されます。`(x, m)`実際の間隔に`[x, x+m-1]`。 の`-1`重要です。 それを忘れると範囲が変わり、すべての答えが壊れてしまいます。 

表現:```
pref_xor(r) ^ pref_xor(l - 1)
```接頭辞合計が算術合計を抽出するのとまったく同じ方法で、区間全体で xor を抽出します。 

Python 整数は上記の値を自動的に処理します$2^{63}$、それで、$10^{16}$制限は完全に安全です。 

最終的な決定は標準的な Nim 理論と一致します。 ゼロ XOR は、すべての手が別のゼロ XOR 状態に反映される可能性があることを意味するため、最適なプレイでは最初のプレイヤーが負けます。

## テストケース```python
# helper: run solution on input string, return output string
import sys, io

def solve():
    input = sys.stdin.readline

    def pref_xor(n):
        if n % 4 == 0:
            return n
        if n % 4 == 1:
            return 1
        if n % 4 == 2:
            return n + 1
        return 0

    n = int(input())
    nim_sum = 0

    for _ in range(n):
        x, m = map(int, input().split())

        l = x
        r = x + m - 1

        nim_sum ^= pref_xor(r) ^ pref_xor(l - 1)

    print("tolik" if nim_sum else "bolik")

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    out = sys.stdout.getvalue()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return out.strip()

# provided sample
assert run(
"""2
2 1
3 2
""") == "tolik", "sample 1"

# minimum-size input
assert run(
"""1
1 1
""") == "tolik", "single heap"

# xor becomes zero
assert run(
"""1
1 3
""") == "bolik", "1 xor 2 xor 3 = 0"

# catches off-by-one in interval end
assert run(
"""1
5 1
""") == "tolik", "single-value interval"

# large values
assert run(
"""1
10000000000000000 2
""") == "tolik", "large integers"

# multiple ranges cancelling each other
assert run(
"""2
1 1
1 1
""") == "bolik", "same heaps cancel"

 | --- | --- | --- |

 ## 特殊なケース

 よくある間違いは、ちょうど 1 つの山を含む採石場の取り扱いを誤ることです。 

入力：```
1
5 1
```間隔は`[5,5]`。 

アルゴリズムは以下を計算します。$$pref(5)\oplus pref(4)$$モジュロ 4 ルールを使用すると、次のようになります。$$pref(5)=1$$

$$pref(4)=4$$それで：$$1 \oplus 4 = 5$$最後の xor はゼロではないので、答えは次のようになります。`"tolik"`。 

誤って使用した場合`r = x + m`の代わりに`x + m - 1`、処理します`[5,6]`代わりに、間違った答えが得られます。 

もう 1 つの微妙なケースは、合計 xor が完全にキャンセルされる場合です。 

入力：```
1
1 3
```ヒープは次のとおりです。```
1 2 3
```アルゴリズムは以下を計算します。$$pref(3)\oplus pref(0) = 0 \oplus 0 = 0$$したがって、出力は次のとおりです`"bolik"`。 

これにより、prefix-xor キャンセル ロジックが検証されます。 モジュロ 4 パターンのバグのある実装は通常、この正確な範囲で失敗します。 

値が大きい場合も危険な点があります。 

入力：```
1
10000000000000000 1
```間隔には値を含む単一のヒープが含まれます$10^{16}$。 

このアルゴリズムは依然として定数時間演算のみを実行します。$$pref(10^{16}) \oplus pref(10^{16}-1)$$ヒープの大きさに依存する反復がないため、ソリューションは最大制限でも効率的です。
