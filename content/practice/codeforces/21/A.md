 ## 解決策
 ## 問題の理解

 文字列が Jabber ID の構文に正確に従っているかどうかを検証する必要があります。 

有効な ID には次の 3 つの要素が考えられます。`username@hostname`または`username@hostname/resource`ユーザー名とリソースは同じルールに従います。 英文字、数字、アンダースコアのみを含めることができます。 その長さは 1 ～ 16 でなければなりません。 

ホスト名が少し異なります。 ドットで区切られた部分に分割されます。 すべての部分はユーザー名と同じルールを満たす必要があります。つまり、各部分には文字、数字、アンダースコアのみが含まれ、長さは 1 ～ 16 でなければなりません。ホスト名全体の長さは 1 ～ 32 である必要があります。 

入力は単一の文字列なので、出力する必要があります。`YES`すべてのルールが満たされている場合、そうでない場合`NO`。 

入力の長さは最大 100 であるため、パフォーマンスは問題になりません。 二次解析でも簡単に適合します。 課題は正確さです。 間違った送信のほとんどは、区切り文字を正しく解析しなかったり、長さの条件の 1 つを忘れたりするために失敗します。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

ホスト名には、ドットで区切られた複数の単語が含まれる場合があります。```
a@b.c.d
```各セグメントは空ではなく、正当であるため、これは有効です。 

空のセグメントを含むホスト名は無効です。```
a@b..c
```正しい答えは、`NO`2 つのドット間の部分文字列が空であるためです。 不注意な分割ベースの実装では、空の部分を拒否することを忘れることがあります。 

リソース部分はオプションですが、`/`存在する場合、リソースを空にすることはできません。```
a@b/
```答えは`NO`。 

同じことがユーザー名にも当てはまります。```
@abc
```ユーザー名の長さは少なくとも 1 でなければならないため、これは無効です。 

よくある解析ミスは、複数のエラーが発生することです。`@`記号:```
a@b@c
```この構造では 1 つのユーザー名と 1 つのホスト名のみが許可されるため、これは拒否する必要があります。 

もう 1 つの微妙なケースは、ホスト名の長さです。 すべてのセグメントが個別に有効であっても、ホスト名全体は最大 32 文字である必要があります。```
a@abcdefghij.abcdefghij.abcdefghijx
```それぞれの部分の長さは問題ありませんが、ホスト名の合計が 32 を超えるため、答えは次のようになります。`NO`。 

## アプローチ

 最も直接的な総当たりの解決策は、可能なすべての分割位置を試してみることです。`@`そして`/`、結果の部分文字列がすべてのルールを満たしているかどうかを確認します。 

たとえば、可能な限りすべての処理を繰り返すことができます。`@`位置、それから可能な限りの`/`その後の位置を確認し、すべての部分を手動で確認します。 文字列の長さは最大でも 100 であるため、これは即座に実行されます。 最悪のケースは、およそ数千回の部分文字列チェックです。 

このアプローチの弱点は速度ではなく、実装の複雑さです。 複数のセパレータが関与すると、総当たり解析ではエラーが発生しやすくなります。 複数の構造などの不正な構造を誤って受け入れてしまう可能性があります。`@`文字または空のホスト名セグメント。 

よりクリーンなアプローチは、文法に従って文字列を解析することです。 

構造は厳格です:

 1. 必ず 1 つ存在する必要があります`@`。 
2. 以前のすべて`@`はユーザー名です。 
3. その後のすべて`@`次のいずれかです:

 - 単なるホスト名
 - またはホスト名/リソース

 文字列がこれらの論理コンポーネントに分割されると、検証はローカルになります。 各部分を個別に確認できます。 

重要な観察は、すべてのアトミック ワードが同じ検証ルールを共有していることです。つまり、長さが 1 ～ 16 の文字、数字、アンダースコアのみです。つまり、再利用可能なバリデーター関数を 1 つ作成して、どこにでも適用できるということです。 

ホスト名については、さらにドットで分割し、すべてのセグメントを個別に検証します。

 ## アルゴリズムのチュートリアル

 1. 入力文字列を読み取ります。 
2. 文字列に 1 つだけが含まれていることを確認します。`@`。 

この制限がないと、次のような不正な入力が行われてしまいます。`a@b@c`曖昧に解析される可能性があります。 
3. 文字列を次のように分割します。`username`そして`rest`を使用して`@`。 
4. ユーザー名を検証します。 

ユーザー名は次のとおりである必要があります。 

- 長さは 1 ～ 16 です
 - 文字、数字、またはアンダースコアのみを含む
 5. かどうかを確認します。`rest`が含まれています`/`。 

そうなった場合は、次のように分割します。`hostname`そして`resource`。 

そうでない場合は、全体`rest`はホスト名ですが、リソースがありません。 
6. リソースが存在する場合は、ユーザー名と同じルールを使用してそれを検証します。 

空のリソースは無効です。 
7. ホスト名の長さを検証します。 

ホスト名全体の長さは 1 ～ 32 でなければなりません。 
8. ホスト名をドットで分割します。 
9. すべてのホスト名セグメントを検証します。 

すべてのセグメントは次のことを行う必要があります。 

- 空でないこと
 - 長さは 1 ～ 16 です
 - 文字、数字、またはアンダースコアのみを含む
 10. すべてのチェックが成功したら、印刷します。`YES`。 それ以外の場合は印刷します`NO`。 

### なぜ効果があるのか

 このアルゴリズムは、有効な Jabber ID の正確な形式構造を反映しています。 

の`@`Split は、ユーザー名セクションとホスト名セクションが 1 つだけ存在することを保証します。 オプションの`/`リソースが存在する場合、split はリソースを分離します。 残りのすべてのアトミック コンポーネントは、文字と長さのルールに照らしてチェックされます。 

ドットによる分割により、仕様に記載されているホスト名の単語が正確に生成されるため、ホスト名の検証は正しいです。 空のセグメントを拒否すると、連続したドットや先頭/末尾のドットなどの無効な形式が防止されます。 

仕様のすべてのルールが直接かつ独立してチェックされるため、アルゴリズムはすべての有効な ID を受け入れ、すべての無効な ID を拒否します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def valid_word(s):
    if not (1 <= len(s) <= 16):
        return False

    for ch in s:
        if not (ch.isalnum() or ch == '_'):
            return False

    return True

def solve():
    s = input().strip()

    if s.count('@') != 1:
        print("NO")
        return

    username, rest = s.split('@')

    if not valid_word(username):
        print("NO")
        return

    if rest.count('/') > 1:
        print("NO")
        return

    if '/' in rest:
        hostname, resource = rest.split('/')

        if not valid_word(resource):
            print("NO")
            return
    else:
        hostname = rest

    if not (1 <= len(hostname) <= 32):
        print("NO")
        return

    parts = hostname.split('.')

    for part in parts:
        if not valid_word(part):
            print("NO")
            return

    print("YES")

solve()
```このソリューションは 1 つの再利用可能なヘルパーを中心に展開します。`valid_word`。 この関数は、ユーザー名、リソース、およびホスト名セグメントによって使用される共有検証ロジックを実装します。 

最初の構造チェックは重要です`@`。 使用する`count('@') != 1`より深い解析が行われる前に、不正な入力を即座に拒否します。 

リソースの解析には注意が必要です。 まず、複数あるかどうかを確認します`/`hostname-resource セクション内に存在します。 次のような入力:```
a@b/c/d
```拒否されなければなりません。 

ホスト名の検証は 2 つの層で行われます。 このステートメントでは 32 文字という個別の制限が課されているため、最初にホスト名の合計の長さを検証します。 次に、ドットで分割し、各セグメントを個別に検証します。 

分割動作により、空のコンポーネントが自然に捕捉されます。 例えば：```
"ab..cd".split('.')
```生成されるもの:```
["ab", "", "cd"]
```空の文字列は失敗します`valid_word`、ホスト名を正しく拒否します。

import io

def solve():
    s = input().strip()

    def valid_word(x):
        if not (1 <= len(x) <= 16):
            return False

        for ch in x:
            if not (ch.isalnum() or ch == '_'):
                return False

        return True

    if s.count('@') != 1:
        print("NO")
        return

    username, rest = s.split('@')

    if not valid_word(username):
        print("NO")
        return

    if rest.count('/') > 1:
        print("NO")
        return

    if '/' in rest:
        hostname, resource = rest.split('/')

        if not valid_word(resource):
            print("NO")
            return
    else:
        hostname = rest

    if not (1 <= len(hostname) <= 32):
        print("NO")
        return

    for part in hostname.split('.'):
        if not valid_word(part):
            print("NO")
            return

    print("YES")

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    global input
    input = sys.stdin.readline

    solve()

    return sys.stdout.getvalue().strip()

 ## 特殊なケース

 次の入力を考えてみましょう。```
a@b..c
```このアルゴリズムはホスト名を次のように分割します。```
["b", "", "c"]
```空の中間セグメントは失敗します`valid_word`長さが 0 であるため、アルゴリズムは正しく出力します。`NO`。 

次に、次のことを考えてみましょう。```
a@b/
```パーサーが検出するのは、`/`そして次のように分割されます。```
hostname = "b"
resource = ""
```空のリソースは検証にすぐに失敗するため、答えは次のようになります。`NO`。 

複数の場合`@`記号:```
a@b@c
```最初のチェックでは、次の数をカウントします。`@`文字。 カウントは正確に 1 ではないため、文字列はさらに解析される前に拒否されます。 

32 文字を超えるホスト名の場合:```

```ホスト名の合計の長さは 33 になります。個々のセグメントがすべて有効であっても、個別のホスト名の長さの条件は失敗するため、アルゴリズムは次のように出力します。`NO`。 

最後に、有効な複雑な例を考えてみましょう。```
abc_DEF@host_1.server_2/resource_3
```ユーザー名、すべてのホスト名セグメント、およびリソースはすべて、共有検証ルールを満たしています。 ホスト名の長さは 32 以内です。アルゴリズムは拒否をトリガーすることなく最後に到達し、出力します。`YES`。
