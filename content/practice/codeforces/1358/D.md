 ## 解決策
 ## 問題の理解

 順番に並べられた一連の月が与えられます。各月の長さは日数で固定されています。 カレンダーを平坦化すると、毎日が 1 つの直線的なタイムラインになりますが、各ポジションは、1 日目から 1 日目まで、その月内の位置を引き続き認識します。$d_i$。 

日の値は、単にその月内のインデックスです。 1 日に訪れるとそれだけ多くの「ハグ」が得られるため、月の早い日は安く、遅い日はより価値があります。 正確に次の連続ブロックを選択する必要があります。$x$この無限に繰り返される年のどこかで連続した日を計算し、これらの日インデックス値の合計を最大化します。 

主な問題点は、シーケンスが年の境界によって周期的であるにもかかわらず、選択したセグメントは、年の境界を越える場合も含めて、どこからでも開始および終了できることです。 概念的には、長さを選択しています。$x$月と日のパターンを無限に連結した部分配列。 

制約は大きく、最大で$2 \cdot 10^5$月と合計日数$10^6$。 すべての開始位置を明示的に試すアプローチは、非常に大きくなる可能性がある線形化された配列をスキャンして評価する必要があるため、遅すぎます。$O(n)$が始まり、最悪の場合には二次関数の動作が発生します。 

微妙なエッジケースは、最適なセグメントが年末に重なる場合です。 月の境界から始まるセグメントのみを考慮する素朴なアプローチでは、月末近くの月内で始まるようなケースを見逃します。この場合、その月の末尾と次の月全体を取得すると、整列されたセグメントよりも大きな合計が得られます。 

もう 1 つの落とし穴は、月の一部を計算するときに二重に数えたり、数え間違えたりすることです。 毎月三角和額を拠出するので、$1 + 2 + \dots + d_i$、サフィックスを取得するには、プレフィックスを慎重に処理する必要があります。そうしないと、部分的な寄与を減算するときに off-by-one エラーが表示されます。 

## アプローチ

 ブルート フォース ソリューションでは、まずカレンダーを、各月が値を提供する完全な配列に拡張します。$1, 2, \dots, d_i$、次にサイズのウィンドウをスライドさせます$x$それを調べて合計を計算します。 これは、考えられるすべての休暇間隔を直接評価するため、正しいです。 ただし、構造を拡張すると、次のような問題が発生する可能性があります。$10^6$要素とその上でウィンドウをスライドさせます。$O(n)$、単純に合計を再計算すると、$O(x)$、諦める$10^{11}$最悪の場合は操作が不可能になります。 

プレフィックス合計を使用してウィンドウ合計を最適化したとしても、依然として概念的な非効率性に直面します。つまり、各月には予測可能な算術構造があるにもかかわらず、毎日を個別に処理していることになります。 重要な観察は、1 か月以内の寄与は線形かつ累積的であるため、日ごとの推移をシミュレーションする必要がないことです。 

カレンダーを拡張する代わりに、月の合計のプレフィックスの合計を事前計算し、月内の完全な「ハグ」のプレフィックスの合計も計算できます。 これにより、特定の月に始まり、その後に続くセグメントの合計を計算できます。$O(1)$。 次に、考えられるすべての開始点を試しますが、毎日繰り返すのではなく、月ごとにジャンプし、二分探索またはスライディング ウィンドウ ロジックを使用して、開始点がどこにあるかを判断します。$x$-日のセグメントが終了します。 

よりクリーンな観点は、ラップアラウンド セグメントが線形になるように月の配列を複製し、次に 2 ポインター手法を使用することです。つまり、累計を維持しながら右のエンドポイントを拡張し、セグメントが超過したときに左から縮小します。$x$日々。 ウィンドウが有効になるたびに、算術合計を使用して部分的な月を調整して、その境界で終了する可能な最良の値を計算します。 

これにより、問題は一定時間範囲評価による線形時間スキャンに軽減されます。

 ## アルゴリズムのチュートリアル

 毎月を長さのブロックとしてモデル化します$d_i$、ここで、その合計寄与率は単純な算術合計です。 目標は、すべての長さを評価することです。$x$月の回覧版のセグメント。 

1. ラップアラウンド間隔が連続するように、月の 2 倍の配列を作成します。 これにより、有効なセグメントが完全に含まれるようになるため、年の境界を個別に処理する必要がなくなります。 
2. 日数のプレフィックス合計と「丸月によって寄与されたハグ」のプレフィックス合計を事前計算します。 丸一ヶ月のハグ貢献$i$は$d_i(d_i+1)/2$これにより、月全体の拠出金を効率的に集計できます。 
3. 2 つのポインターを使用する$l$そして$r$数ヶ月にわたって。 ウィンドウは、合計の長さを明示的に追跡する連続した日のセグメントを表します。 
4. 展開する$r$ウィンドウ内の合計日数が少なくとも$x$。 私たちは、完全に含まれた月によって寄与された合計日数と合計ハグの両方を維持します。 
5. ウィンドウを超える場合$x$日の場合は、左から月を削除します。 月が部分的にのみ使用されている場合は、その月のサフィックス寄与分のみが差し引かれます。 これには、最初の値の合計を計算する必要があります。$k$または最後$k$等差数列の用語。 
6. ウィンドウが少なくとも$x$数日かけて、次で終わる最良のセグメントを計算します。$r$。 それを超えて余分な日数がある場合$x$の場合、部分的に含まれている月の左端にある最小値のプレフィックスを削除して調整します。 
7. すべての有効なウィンドウにわたる最大値を追跡します。 

重要な部分は、月の一部の拠出金を計算することです。 最初を取ると$k$月の日数、合計は$k(k+1)/2$。 最後を取ると$k$月の長さの日数$d$、プレフィックスを減算します: 合計マイナス$(d-k)(d-k+1)/2$。 この定数時間演算により、反復せずにウィンドウを調整できます。 

### なぜ効果があるのか

 すべての有効な休暇は、2 倍の月配列内の連続したセグメントに対応します。 2 ポインター プロセスでは、少なくとも長さの有効なセグメントが含まれるすべての最小右端点を列挙します。$x$終わります。 このようなエンドポイントごとに、寄与関数は数か月にわたって加算され、各月内で厳密に増加するため、左側の境界を貪欲に調整することで、正確性を維持しながら実行可能性が維持されます。 これにより、最適なセグメントがスキップされず、すべての候補が 1 回だけ評価されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def month_sum(d):
    return d * (d + 1) // 2

def prefix_sum(k):
    return k * (k + 1) // 2

n, x = map(int, input().split())
d = list(map(int, input().split()))

# duplicate to handle wrap-around
d = d + d

pref_days = [0] * (2 * n + 1)
pref_hugs = [0] * (2 * n + 1)

for i in range(2 * n):
    pref_days[i + 1] = pref_days[i] + d[i]
    pref_hugs[i + 1] = pref_hugs[i] + month_sum(d[i])

def calc_suffix_hugs(days, length):
    start = days - length
    return month_sum(days) - month_sum(start)

ans = 0
l = 0

for r in range(2 * n):
    while l <= r and pref_days[r + 1] - pref_days[l] > x:
        l += 1

    total_days = pref_days[r + 1] - pref_days[l]
    total_hugs = pref_hugs[r + 1] - pref_hugs[l]

    if total_days >= x:
        extra = total_days - x
        # remove extra from the left
        i = l
        while extra > 0:
            take = min(extra, d[i] - 0)
            total_hugs -= calc_suffix_hugs(d[i], take)
            extra -= take
            i += 1

        ans = max(ans, total_hugs)

print(ans)
```この実装は、円形のセグメントが直線になるように構造を 2 倍の配列に平坦化することに依存しています。 プレフィックス配列を使用すると、月全体の拠出額を定数時間で計算できます。 スライディング ウィンドウにより、各右エンドポイントが 1 回処理され、左ポインタは前方にのみ移動するため、複雑さが線形に保たれます。 

調整ステップでは、ウィンドウの左端の部分から超過日数が減算されます。 最も早い日を削除すると、月内の最小の寄与が削除され、残りのセグメントの最適性が維持されるため、これは安全です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, x = map(int, input().split())
    d = list(map(int, input().split()))

    d = d + d
    pref_days = [0] * (2 * n + 1)
    pref_hugs = [0] * (2 * n + 1)

    def ms(d): return d * (d + 1) // 2

    for i in range(2 * n):
        pref_days[i+1] = pref_days[i] + d[i]
        pref_hugs[i+1] = pref_hugs[i] + ms(d[i])

    ans = 0
    l = 0

    for r in range(2 * n):
        while l <= r and pref_days[r+1] - pref_days[l] > x:
            l += 1
        if pref_days[r+1] - pref_days[l] < x:
            continue
        ans = max(ans, pref_hugs[r+1] - pref_hugs[l])

    return str(ans)

 ## 特殊なケース

 主なエッジケースは、最適なセグメントが月末近くに始まる場合です。 たとえば、月の長さが 10 で、9 日目から始まる場合、次のようになります。$x=3$days は、翌月の 9 日、10 日、1 日を意味します。 セグメントが 1 か月以内に収まるか、境界に一致する必要があると想定する単純なアプローチでは、これを完全に見逃してしまいます。 

もう 1 つのエッジ ケースは、すべての月の長さが 1 である場合です。値は定数になり、どのセグメントでも同じ結果が得られますが、部分算術和に依存する不適切な実装では、接尾辞を処理するときに誤って減算しすぎてしまう可能性があります。 

3 番目のケースは次の場合です。$x$合計日数に等しい。 正解は固定されており、すべての月の拠出金の全額と等しくなります。 スライディング ウィンドウの実装では、境界での過度の縮小が原因で全範囲が破棄されないようにする必要があります。
