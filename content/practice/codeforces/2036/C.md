 ## 解決策
 ## 問題の理解

 時間の経過とともに変化するバイナリ文字列が与えられます。 各クエリは 1 つの位置を更新し、その文字を 0 または 1 に反転します。更新のたびに、非常に具体的な質問に答える必要があります。現在の文字列のどこかに連続ブロックとしてパターン「1100」が含まれていますか?

 したがって、各操作は 1 文字を変更し、各変更の後、長さ 4 の部分文字列が 1100 に等しいかどうかを概念的にスキャンします。 

この制約により、クエリごとの文字列全体の再計算が即座に除外されます。 すべての文字列の長さの合計は最大 2×10^5 であり、更新の合計数も最大 2×10^5 です。 クエリごとの文字列のフル スキャンは O(nq) となり、実行可能な制限をはるかに超える 4×10^10 演算に達する可能性があります。 更新ごとにすべての部分文字列のローリング ハッシュを再計算しても、単純に実行すると依然として時間がかかりすぎます。 

重要な観察は、各更新が非常に小さなローカル近傍にのみ影響を与えるということです。 単一の文字反転では、更新されたインデックスから遠く離れた「1100」の出現を作成または破棄することはできません。 更新された位置と重複する部分文字列にのみ影響します。 

微妙なエッジケースは境界処理から発生します。 文字列の長さが 4 未満の場合、答えは常に NO です。 もう 1 つのケースは、更新によって小さな領域内の文字が繰り返し切り替わり、次のような重複するオカレンスが作成および削除される可能性がある場合です。```
11100
```ここでは、「1100」が位置 2 から表示されます。更新されたインデックスの周囲の 1 つのウィンドウだけをチェックし、隣接するウィンドウを見逃す単純なアプローチは、次のような重複するパターンで失敗します。```
111100
```これには、位置 2 と位置 3 から始まる「1100」が含まれています。 

したがって、長さ 4 のすべての可能なウィンドウを正しく維持していることを確認する必要があります。 

## アプローチ

 簡単な方法は、長さ 4 のすべての部分文字列をスキャンすることによって、更新のたびに「1100」が存在するかどうかを再計算することです。これは、可能なすべてのウィンドウを明示的にチェックするため正しいですが、クエリごとに O(n) のコストがかかります。 最大 2×10^5 のクエリでは、これでは遅すぎます。 

重要な構造上の洞察は、更新されたインデックスを含む長さ 4 の部分文字列のみがその値を変更できるということです。 各更新は、最大 4 つの候補部分文字列 (i-3、i-2、i-1、および i で始まる候補部分文字列) にのみ影響します。 これにより、問題はグローバルな再計算からローカルなメンテナンスまで軽減されます。 

私たちは、現在「1100」が何回存在するかを示すグローバルカウンターを維持しています。 最初に O(n) で 1 回計算します。 クエリごとに、影響を受けるすべてのウィンドウのコントリビューションを削除し、更新を適用して、コントリビューションを再度追加します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | 最適 (ローカル ウィンドウの更新) | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列を配列として扱い、s[i:i+4] = "1100" を満たすインデックスの数の実行カウントを維持します。 

1. 文字列を初期化し、「1100」に等しい長さ 4 の部分文字列がいくつあるかを計算します。 これにより、最初の応答状態が得られます。 
2. 位置 i での更新ごとに、まず、このインデックスによって影響を受ける可能性のあるすべての部分文字列の寄与を削除します。 これらは開始位置 i-3、i-2、i-1、および i です。 
3. s[i] を新しい値に設定して、更新を適用します。 
4. 更新後に同じ 4 つの開始位置候補の貢献度を再計算します。 
5. 処理後、カウントが 0 より大きい場合は YES を出力し、それ以外の場合は NO を出力します。 

更新前に削除する理由は、古い文字値を含む古い部分文字列が二重にカウントされるのを避けるためです。 

### なぜ効果があるのか

 「1100」の出現はすべて、連続する 4 文字によって完全に決定されます。 1 つの文字を変更すると、その文字を含む部分文字列にのみ影響します。 [i−3, i+3] の範囲外に完全にある部分文字列は変更されないため、カウントへの寄与は不変です。 影響を受ける可能性のある一定サイズのウィンドウのセットへの更新を制限することで、文字列全体をスキャンせずに正確なグローバル数を保存します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check(s, i):
    if i < 0 or i + 3 >= len(s):
        return False
    return s[i] == '1' and s[i+1] == '1' and s[i+2] == '0' and s[i+3] == '0'

t = int(input())
for _ in range(t):
    s = list(input().strip())
    q = int(input())

    n = len(s)
    cnt = 0

    for i in range(n - 3):
        if s[i:i+4] == ['1', '1', '0', '0']:
            cnt += 1

    for _ in range(q):
        i, v = input().split()
        i = int(i) - 1
        v = v

        for j in range(i - 3, i + 1):
            if check(s, j):
                cnt -= 1

        s[i] = v

        for j in range(i - 3, i + 1):
            if check(s, j):
                cnt += 1

        if cnt > 0:
            print("YES")
        else:
            print("NO")
```実装では、効率的な更新のために文字列をリストとして保持します。 ヘルパー チェック関数は、インデックス j で始まるウィンドウが「1100」を形成するかどうかを安全に検証し、範囲外の場合は False を返します。 各クエリは更新の前後に最大 4 つのウィンドウを処理するため、操作ごとに一定の作業が保証されます。 

よくある間違いは、更新を適用する前に古い寄与分を差し引くのを忘れることです。 これにより、ウィンドウが一致から不一致に、またはその逆に移行するときにカウントが増大します。 

もう 1 つの微妙な点は、文字列の端近くのウィンドウをチェックするときにインデックス境界が確実に尊重されるようにすることです。

 ## 特殊なケース

 長さが 4 未満の短い文字列に「1100」が含まれることはありません。 最初のループは負の n−3 までしか実行されないため、アルゴリズムはこれを自然に処理します。したがって、一致はカウントされず、すべてのチェックは安全に false を返します。 

文字列の最初または最後での更新は、チェック関数の境界クリッピングにより 4 つ未満のウィンドウにのみ影響します。 たとえば、i = 1 の場合、インデックス −2 ～ 1 で始まるウィンドウのみが考慮され、無効なインデックスはすべて無視されます。 

各ウィンドウは独立して処理されるため、重複する発生は正しく処理されます。 2 つの出現が文字を共有している場合でも、それぞれは個別にカウントされ、各クエリの減算および加算中に一貫して更新されます。
