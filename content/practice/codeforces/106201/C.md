 ## 問題の理解

 ゲームでは、固定された一連のステージが与えられています。$i$のロック解除または取得に対応します。$i$-回目のエンディング。 ステージからの移動$i$ステージへ$i+1$既知の時間がかかる$d_{i+1}$したがって、進行時間は累積され、一時停止を選択しない限り厳密に増加します。 

それぞれの段階で$i$、絶対時間で開始されるストリームという単一のイベントもあります。$a_i$。 まさにその時点にいる場合 (またはまだその時点を過ぎていない場合)、進行を停止し、必要に応じて待機し、それを監視することを選択できます。 視聴にかかる時間はゼロですが、視聴後はすぐに次のステージに進みます。 それをスキップすると、それは永久に失われ、後で戻ることはできません。 さらに、ステージを越えると$i$、以前のストリームに戻って視聴することはできません。 

したがって、プロセスはステージを通過する単一の前方パスであり、各ステージで次のいずれかを実行します。 

1. ストリームを失ってすぐに続行する、または
 2. 時間に間に合うようにしてください$a_i$、ストリームを見てから続行します。 

目標は、視聴できるストリームの数を最大化することです。 

ステージ終了後の時間$i$一時停止は前方への遅延のみであり、後方への遅延は発生しないため、どの以前のストリームに参加することを選択したかによって完全に決まります。 

制約は次のとおりです$n \le 2 \cdot 10^5$したがって、どの解も線形または線形に近い必要があります。$n \log n$。 決定の二次シミュレーションは、各状態が以前のすべての選択に依存するため、すぐに遅すぎます。 

微妙な問題は、待つことが役立つのは十分に早い場合のみであるということです。 ステージなら$i$私たちはすでに通り過ぎました$a_i$、そうするとその流れは永遠に不可能です。 もう 1 つの失敗例は、可能であれば常にストリームを貪欲に取得する場合に発生します。そうすることにより、遅延が大きくなり、実際にはより価値のあるその後のストリームを多く失う可能性があります。 

たとえば、早いストリームを選択したために、そうでなければ視聴できたであろう後の 2 つのストリームに到着するのに遅すぎるとします。 利用可能なストリームを常に取得する単純な貪欲な戦略は、将来の時間への影響を考慮していないため、ここでは失敗します。

 ## アルゴリズムのチュートリアル

 現在時刻を維持します$t$、選択したスケジュールで現在のステージを終了した瞬間を表し、正常に視聴したストリームの数を示します。 

ステージという事実も利用します。$1$時間に始まります$0$、そしてステージから移動$i$に$i+1$常に追加します$d_{i+1}$。 

### ステップ

 1. 現在時刻を初期化する$t = 0$そして答える$ans = 0$。 

これは、ゲームプレイの前に開始し、何も見ていないことを表します。 
2. ステージを反復処理する$i = 1$に$n$。 

各段階で、概念的には時間に到達します$t$前のステージを終えた後。 
3. もし$t > a_i$、このストリームを完全にスキップしてください。 

これは強制です。すでに開始の瞬間を逃しており、さらに遅らせても時間が増えるだけです。 
4. それ以外の場合は、ストリームを視聴することを選択します$i$、 セット$t = a_i$、増加します$ans$。 

ストリーム時間に同期しますが、これには待機が含まれる場合があり、この選択をコミットします。 
5. もし$i < n$、時間を進める$d_{i+1}$。 

これは、現在のステージを終了した直後に次のステージを完了するモデルです。 

### なぜ効果があるのか

 重要な不変条件は、処理段階の後に$i$、変数$t$私たちがステージに到着できる最も早い時間です$i+1$これまでに行われた決定を考慮し、それらの決定に従ってすべてのスケジュールの中で視聴されるストリームの数を最大化します。 

それぞれのステップでストリームに参加できれば$i$そうすることで、将来の実行可能な決定の数が増加する効果を超えて減少することはありません。$t$に$a_i$。 ストリームをスキップする代替スケジュール$i$ストリームは固定時間に縛られているため、後で参加することはできますが、それは不可能です。 したがって、唯一意味のある決定は、まだ到達できるかどうかであり、到達できる場合はそれを実行します。 

これにより、すべてのストリームが実行可能な場合、または永久に到達不能な場合に取得されることが保証され、選択肢を再配置しても時間の制約に違反することなくカウントを改善できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    d = list(map(int, input().split()))

    t = 0
    ans = 0

    for i in range(n):
        if t <= a[i]:
            t = a[i]
            ans += 1

        if i < n - 1:
            t += d[i]

    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは単一のタイムライン変数を維持します`t`これは、検討されている最新のステージを終了した後の現在の完了時間を表します。 比較`t <= a[i]`ストリームがまだ到達可能かどうかをエンコードします。 そうである場合、設定によってモデル化される正確な時刻まで「待機」します。`t = a[i]`、視聴済みとしてカウントします。 

の追加`d[i]`各ステージの終了後は、次のエンディングに移動するための固定コストに応じて時間が常に進行することが保証されるため、非常に重要です。 よくある間違いは、次のように追加することです`d[i+1]`の代わりに`d[i]`、これによりインデックスの位置がずれます。`d`ステージ2への移行から始まります。

 ## 特殊なケース

 重要なエッジケースは、現在時刻が正確に等しい場合です。$a_i$。 この場合、ストリームの取得を許可する条件が必要です。 小切手`t <= a[i]`平等が受け入れられることを保証します。 のように書かれた場合`t < a[i]`の場合、現時点で発生するストリームが誤ってスキップされてしまいます。 

もう 1 つのエッジ ケースは、ストリームの待機によって時間が大幅に進み、残りのストリームがすべて到達できなくなる場合です。 後続の比較はすべて一度失敗するため、アルゴリズムはこれを自然に処理します。`t`未来を超える`a[i]`値を変更し、スキップを強制し、正確さを維持します。 

最終的なエッジケースが非常に小さい、または非常に大きい`d[i]`。 アルゴリズムはこれらの値を累積するだけなので、`t`Python ではオーバーフローは問題になりませんが、固定幅の整数言語ではこれには 64 ビットのストレージが必要になります。
