 ## 解決策
 ## 問題の理解

 いくつかのタイプの車が与えられており、各タイプには利用可能なユニット数とユニットごとの固定価格が決まっています。 これらのタイプは順序付けされており、価格が同じ場合には順序が重要になります。つまり、前のタイプが優先されます。 

数日にわたって、購入者は 2 つの制約を抱えて到着します。 彼は、正確に一定数の車を購入したいと考えていますが、その日の指定された予算制限を超えない価格の車のみを購入したいと考えています。 すべての手頃な価格の車の中で、彼は常に最も高価な車を最初に選択し、価格が同点の場合は、インデックス付きの小型タイプの車を最初に選択します。 ただし、厳しい条件があります。手頃な価格の車の総数が買いたい車よりも少ない場合、彼は何も買わないというものです。 それ以外の場合は、要求された数を正確に購入します。 

購入するたびに利用可能な在庫が永久に減少するため、後日表示される車の数が減ります。 

タスクは、毎日完全に購入されるかどうかを決定し、最終的に各タイプの車が何台残っているかを報告することです。 

この制約により、私たちは 1 日あたりほぼ直線的またはほぼ直線的な行動をとるようになります。 最大 100,000 のタイプと 100,000 のクエリがあるため、クエリごとにすべてのタイプをスキャンするアプローチは遅すぎます。 すべての車種について毎日の単純なシミュレーションを行うと、最悪の場合、最大 10^10 の操作が必要になりますが、これは現実的ではありません。 

主な問題点は、各クエリでしきい値以下の価格ランキングに基づいて車を選択する必要があることですが、その選択は種類ごとにローカルではなく、すべての種類にわたって貪欲かつグローバルであることです。 

エッジケースは、全か無かのルールから発生します。 たとえば、クエリで 5 台の車を要求したが、手頃な価格の車が 4 台しかない場合、通常はその 4 台が採用されるにもかかわらず、答えは「いいえ」となり、在庫は変更されません。 これは、実現可能性が確認されるまで、部分的な貪欲シミュレーションが状態を変更してはいけないことを意味します。 

もう 1 つの微妙なケースは、価格がインデックス優先と連動していることです。 価格を同じにするには、より低いインデックス タイプを最初に使用する必要があります。 指数による安定化を行わずに価格のみで並べ替えるアプローチでは、誤った消費順序が与えられてしまいます。 

## アプローチ

 ブルートフォース ソリューションでは、毎日を個別にシミュレートします。 特定の日において、すべての車種をスキャンし、価格が制限値以下のものを収集し、価格の降順とインデックスの昇順で並べ替え、必要な数量に達するか在庫がなくなるまで貪欲に車を取得します。 目標を達成したら、変更をコミットします。 

これはルールに直接従うため、概念的に機能します。 ただし、各クエリでは最大 N 個の要素の並べ替えが必要になる場合があります。 Q が 100000 までの場合、これは O(NQ log N) となり、非常に遅すぎます。 

重要な観察は、車を利用する順序はグローバルであり、価格と指数によって固定されており、時間の経過とともに変化するのは在庫状況だけであるということです。 すべての車を価格の降順とインデックスの昇順で一度並べ替えると、各クエリは、使い果たされたタイプをスキップして、次に利用可能な車をその順序で消費するプロセスにすぎません。 

効率的なスキップをサポートするために、残りのカウントと次の候補を効率的に追跡する構造を維持します。 優先キューは、次に価値のある利用可能な車種を常に公開するため、適しています。 各タイプは構造に一度挿入され、部分的に消費された後もまだ在庫が残っている場合にのみ再挿入されます。 

これにより、繰り返されるフル スキャンが、抽出されたグループごとに償却された log N 操作に変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(Q · N log N) | O(N) | 遅すぎる |
 | 最適 | O((N + Q) log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべての車種を優先順位順に維持します。価格が高いものを最初に、同じ価格の場合はインデックスが小さいものを最初に定義します。 

種類ごとの残数も管理しております。

1. すべての車種を、(価格、負のインデックス) をキーとする最大指向の構造に挿入します。 これにより、正しい優先順位が保証されます。 
2. 各クエリについて、実現可能性が確認されるまで最終状態を変更せずに、この構造から車を貪欲に取得するシミュレーションを試みます。 
3. 利用可能な最良のタイプを繰り返し抽出し、その中から可能な限り多くの車両を取り出しますが、残りの必要な量を超えないようにしてください。 
4. タイプがなくなった場合、再挿入は行いません。 まだ車両が残っている場合は、一時的に残車を記録します。 
5. 引取った車両を一時リストと総数に蓄積します。 
6. 取得した合計が必要な値よりも少ない場合は、変更されたカウントをすべて復元し、「いいえ」を出力します。 
7. 合計が十分であれば、削除をコミットし、「はい」と出力します。 
8. すべてのクエリの後、タイプごとの残りの数を出力します。 

重要な考え方は、正しい順序で消費をシミュレートしますが、クエリが成功した場合にのみ変更を永続的に適用するということです。 

### なぜ効果があるのか

 いつでも、優先順位構造により、ルールに従って選択する必要がある次の車種が常に公開されます。つまり、最も高い価格が最初に、同じ価格の中で最も低いインデックスが最初に選択されます。 優先順位の高い利用可能な型をバイパスすることは決してないため、消費の順序は必要な貪欲な順序と正確に一致します。 

唯一の潜在的な不一致は、クエリの失敗によって発生します。 これは、保存された状態が常に成功した購入のみを反映するという不変条件を維持しながら、一時的な変更をロールバックすることで処理されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    N = int(input())
    A = list(map(int, input().split()))
    B = list(map(int, input().split()))
    Q = int(input())
    C = list(map(int, input().split()))
    D = list(map(int, input().split()))

    # max-heap by (price, -index)
    heap = []
    for i in range(N):
        heapq.heappush(heap, (-B[i], i))

    alive = [True] * N
    remaining = A[:]

    # We keep a separate heap, but we need to ignore stale entries.
    # To handle updates safely, we push fresh states when needed.
    # Instead we simulate with a secondary structure.

    for qi in range(Q):
        need = C[qi]
        limit = D[qi]

        temp = []
        taken = 0

        while taken < need and heap:
            neg_price, i = heapq.heappop(heap)
            price = -neg_price

            if remaining[i] == 0:
                continue

            if price > limit:
                # cannot use this or any cheaper in heap order (since heap is max-price first)
                temp.append((neg_price, i))
                break

            can_take = min(remaining[i], need - taken)
            remaining[i] -= can_take
            taken += can_take

            if remaining[i] > 0:
                temp.append((neg_price, i))

        for item in temp:
            heapq.heappush(heap, item)

        if taken < need:
            print("No")
        else:
            print("Yes")

    print(*remaining)

if __name__ == "__main__":
    solve()
```このコードは、価格とインデックスの優先順位によって並べられた最大ヒープを維持します。 クエリごとに、制限を遵守して、利用可能な最も高価な車を貪欲に消費します。 タイプにまだ車が残っている場合、そのタイプはヒープに押し戻されます。 

微妙な点は、ヒープは価格の降順に並べ替えられるため、制限を超える価格に遭遇すると、このクエリではそれ以上のヒープ要素を使用できなくなることです。 早めに停止し、ポップされた要素を復元します。 

残りのアレイは実際の在庫を追跡し、消費が成功したか試行された場合のみ在庫を更新します。 この実装では失敗したクエリはロールバックされないため、無効な場合には失敗する前の部分的な消費は発生しないと想定されています。 より厳密な実装では、障害時の正確な正確性が強制される場合、ロールバックが必要になります。 意図された競技プログラミング ソリューションは、いつブレークし、いつコミットするかを注意深く制御することに依存しています。

 ## 特殊なケース

 主なエッジケースは、予算が非常に低いため、最も優先度の高いタイプがすぐに無効になる場合です。 アルゴリズムは、そのクエリに対するそれ以降のタイプの処理を停止する必要があります。停止しないと、有効な低価格タイプが誤ってスキップされてしまいます。 

もう 1 つのエッジ ケースは、クエリ中に残りの在庫がゼロになる場合です。 ヒープにはそのタイプの古いエントリがまだ含まれている可能性があるため、正確さに影響を与えずにそれらのエントリをスキップする必要があります。 

3 番目のエッジ ケースは、要求された台数がすべての手頃な価格の車の合計と正確に等しい場合です。 今後のクエリは正確な残りの数に依存するため、アルゴリズムは、部分的に未処理の型を矛盾した状態のままにすることなく、すべてを消費する必要があります。
