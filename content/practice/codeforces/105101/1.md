 ## 解決策
 ## 問題の理解

 私たちには、忠誠心と呼ばれる強さの値を持つ戦士のセットと、必要な強さをそれぞれ持つ敵グループのセットが与えられます。 分隊と呼ばれる単一の戦士グループは、1 つの敵グループとのみ戦うために使用されます。 

2 つの条件が同時に満たされた場合、分隊は敵グループを倒します。 分隊に選ばれたすべての戦士は、厳密に敵の強さを超える忠誠心を持っていなければならず、分隊の規模は少なくとも敵の強さでなければなりません。 分隊が戦うと、その中のすべての戦士が死ぬため、各戦士はすべての分隊で最大 1 回しか使用できません。 

課題は、すべての敵グループがこれらの制約を満たす 1 つの分隊に正確に割り当てられるように、一部またはすべての戦士をばらばらの分隊に分割できるかどうかを決定することです。 

重要な難点は、各敵には戦士の最小数と選択した各戦士の最小しきい値の両方が必要であり、より強い敵を早期に選択すると弱い敵の柔軟性が低下するため、両方の制約が相互作用することです。 

制約はすべてのテストを通じて最大 10 万人の戦士と敵に及ぶため、明示的に分隊を構築したり、すべての割り当てをチェックしたりするソリューションは遅すぎます。 入力サイズに二次関数が含まれる場合は、直ちに除外されます。 敵ごとにアレイ全体を繰り返しスキャンする貪欲な構築でも、制限を超えるでしょう。 

素朴な貪欲なアプローチでは、いくつかの失敗シナリオが発生します。 

よくある間違いの 1 つは、敵を任意の順序で処理することです。 たとえば、より強力な敵を最初に処理すると、忠誠度の高い戦士が多すぎるため、別の順序が成功したとしても、弱い敵を満足させることが不可能になる可能性があります。 もう一つの間違いは、敵の強さと同等の戦士を使用することが誤って許可されている、忠誠心に関する厳格な不平等を無視していることです。 

さらに微妙な問題は、グローバルな再利用を考慮せずに分隊編成を敵ごとに独立して扱うことです。 各戦士は一度消費されるため、ローカルな実現可能性はグローバルな実現可能性を意味しません。 

## アプローチ

 ブルートフォース戦略では、適格な戦士のサブセットを各敵に 1 人ずつ割り当てようとします。 敵ごとに、敵の強さを超える忠誠心を持つ未使用の戦士をすべてスキャンし、十分な数が残っているかどうかを確認します。 これにはすでに敵ごとに線形時間がかかり、最悪のケース O(NM) が発生します。これは 10^5 スケールの入力ではまったく実行不可能です。 

重要な構造的洞察は、アイデンティティではなく物質のみを考慮するということです。 要件 b を持つ敵の場合、唯一有益な情報は、現在 b よりも厳密に高い忠誠心を持っている未使用の戦士が何人いるかということです。 その数が少なくとも b であれば、サイズ b の分隊を編成できます。 現時点では、追加の適格な戦士は無視してかまいません。 

これにより、問題は複数の戦士の強みを管理し、利用可能性のしきい値を繰り返し確認することに変わります。 戦士と敵の両方を分類することで、貪欲な戦略が可能になります。 大きな要件が最初に満たされるように、敵を最も難しいものから最も簡単なものまで処理し、利用可能な戦士のマルチセット (ヒープまたはポインタを含むソートされたリストを介して実装) を維持します。 

それぞれの敵に対して、十分に強い戦士をすべて集め、そのうち b 人を確保できるようにします。 そうでなければ、即答は不可能です。 

これにより、問題はソートと線形処理に限定されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NM) | O(N) | 遅すぎる |
 | ソートによる最適な貪欲さ | O((N + M) log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

まず戦士を忠誠度の昇順で並べ替え、敵を必要な強さの降順で並べ替えます。 現在の敵に適格なすべての戦士と、後で適格になるすべての弱い戦士を追跡するデータ構造を維持します。 

最大ヒープを使用して、現在の敵に対して十分に強い、利用可能な戦士を保管します。 

1. 戦士の忠誠度を昇順に並べ替えて、敵の要件が減少するにつれて適格な戦士を段階的に追加できるようにします。 これにより、資格を最初から再計算するのではなく、増分アクティベーションが可能になります。 
2. 最も制限的な制約が最初に処理されるように、敵の要件を降順に並べ替えます。 これにより、弱い敵がより強い敵に必要な構造を消費するのを防ぎます。 
3. ウォリアー配列と空の最大ヒープへのポインターを初期化します。 
4. ソートされた順序で敵を繰り返します。 要件 b を持つ敵ごとに、厳密に b を超える忠誠度を持つすべての戦士をヒープに挿入します。 これらの戦士を追加しながらポインターを進めます。 
5. 挿入後、ヒープに少なくとも b 人の戦士が含まれているかどうかを確認します。 そうしないと有効な部隊を編成できないため、即時に失敗を返します。 
6. それ以外の場合は、ちょうど b 人の戦士をヒープからポップし、この敵の分隊を形成することを表します。 これらの戦士はシステムから削除され、再利用することはできません。 
7. すべての敵が正常に処理された場合は、成功を返します。 

### なぜ効果があるのか

 いつでも、ヒープは、現在または後で処理される弱い敵に対して忠誠心が十分である、まだ使用されていない戦士のセットを正確に表します。 敵を降順に処理することで、一度強い敵に戦士を投入すれば、弱い敵には戦士が必要なくなる。 現在の敵に対して利用可能な適格な戦士を常に消費するという貪欲な選択は、そのような戦士は残りのすべての敵に対しても適格であるため、安全です。これらの戦士を未使用のままにしておくのは、将来の実現可能性に役立ちません。 したがって、実現可能性は各ステップに十分な供給があるかどうかのみに依存し、どの戦士が選択されるかには依存しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    T = int(input())
    for _ in range(T):
        N = int(input())
        A = list(map(int, input().split()))
        M = int(input())
        B = list(map(int, input().split()))

        A.sort()
        B.sort(reverse=True)

        heap = []
        i = N - 1

        ok = True

        for b in B:
            while i >= 0 and A[i] > b:
                heapq.heappush(heap, A[i])
                i -= 1

            if len(heap) < b:
                ok = False
                break

            for _ in range(b):
                heapq.heappop(heap)

        print("Yes" if ok else "No")

if __name__ == "__main__":
    solve()
```このソリューションでは両方の配列をソートし、ポインターを使用して適格な戦士を最大ヒープに徐々に挿入します。 各敵は、まず十分な忠誠心を持つすべての可能な戦士が利用可能であることを確認し、次に十分な忠誠心が残っているかどうかを確認することによって処理されます。 ヒープには現在使用可能な戦士のみが保存されます。 正確に b 個の要素をポップすると、分隊の割り当てがシミュレートされます。 

微妙な点は厳密な不等式です`A[i] > b`、気を緩めてはいけません。 使用する`>=`境界線の戦士を誤って許可し、有効性を損なう可能性があります。 

もう 1 つの重要な実装の詳細は、敵を常に降順で処理することです。 この順序を逆にすると、制約が弱くなるのに忠誠度の高い戦士が早くに消費されてしまう可能性があるため、正当性が損なわれます。

 ## 特殊なケース

 重要なエッジケースは、すべての戦士が敵の要件をぎりぎり上回っている場合です。 たとえば、すべての A 値が b に等しい場合、条件が厳しいため、適格な戦士は存在しません。 アルゴリズムは、A[i] > b の戦士のみをプッシュするため、これを正しく処理します。 

もう 1 つのケースは、非常に大きな敵がほとんどすべての強力な戦士を消費する必要がある場合です。 貪欲な順序付けにより、この敵が最初に処理されることが保証されるため、以前の弱い割り当てによってブロックされることはありません。 

最後のエッジケースは、複数の敵が同じ強さを持つ場合です。 並べ替えるとそれらは隣接した状態に保たれ、各ステップで同じプールから b 人の戦士が独立して消費されます。 消費は明示的であるため、再利用が偶然に発生することはありません。
