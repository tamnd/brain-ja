 ## 解決策
 ## 問題の理解

 同じ長さの 2 つのバイナリ文字列が与えられています。 どちらの文字列も常に a で始まります`0`そして、で終わります`1`。 1 つの文字列内のセグメントを取得する操作を繰り返し適用することができます。ただし、そのセグメントのエンドポイントに同じ文字が含まれている場合に限り、それらのエンドポイント間のすべての文字が同じエンドポイント値になるように強制します。 

この操作の効果は、選択した間隔にわたって値を「拡散」することとして最もよく理解されますが、これは両端がすでに一致している場合に限られます。 2つ選ぶなら`0`s、それらの間のすべてを次のように変えることができます`0`。 2つ選ぶなら`1`s の場合も、同様に間隔を埋めることができます。`1`s. どちらの文字列でもこれを任意に何度でも実行できるため、各文字列は、より粗いブロック構造に安定するまで、同じ値の領域をマージすることによって進化します。 

問題は、これらの操作を使用して 2 つの文字列を個別に変換して、ある時点で同一になるようにできるかどうかです。 

制約は全体としては小さく、テスト ケース全体の長さの合計は最大 5000 です。これにより、テスト ケースごとに 3 次以上のものは即座に排除されますが、より重要なのは、おそらく操作のシミュレーションではなく構造的特徴付けを使用して、解が文字列ごとに線形またはほぼ線形になるはずであることを示唆しています。 

微妙な点は、この操作ではエンドポイントの変更が許可されず、同一のエンドポイント間で既存の値を伝播するだけであるということです。 したがって、ビットを恣意的に反転することはできず、ビット間で新しい遷移を作成することもできません。`0`そして`1`すでに制御された方法で存在している場合を除きます。 

単純な間違いは、セグメントをいつでも自由に再配置できると考えることです。 たとえば、次のようになります。```
a = 0101
b = 0011
```両方を次のように「平滑化」できるように見えるかもしれません`0001`、しかし実際には、到達可能な状態は実行の元の構造によって制限されます。 

本当の課題は、文字列のどの側面が操作下で不変であるかを理解することです。 

## アプローチ

 重要な観察は、この操作では、ギャップを挟んで同じ値の隣接する領域のみをマージできるということです。つまり、領域間に新たな変更が導入されることはありません。`0`そして`1`。 代わりに、中間セグメントを平坦化することによって一部の交互を削除するだけです。 

したがって、各文字列は基本的に交互のブロックのシーケンスに還元できますが、ブロックは同じタイプのエンドポイントを共有する場合にのみマージできます。 時間の経過とともに、これは、任意のセグメントを 2 つのセグメントの間で変換できることを意味します。`0`すべてに含まれています`0`、同様に`1`s、すでに存在するエンドポイントを選択する限り。 重要な結果は、同じ文字間の内部「ノイズ」を除去できることですが、最初に出現する文字の順序を変更することはできないということです。`0`そして`1`基本的な方法で移行します。 

これをより正確に見る方法は、連続する等しい文字の連続という観点から考えることです。 この操作により、エンドポイントが一致する場合に限り、間にある反対の文字のラン全体で同一の文字のランをマージできます。 これは、各文字列内で、各最大ブロックがソリッドである正規形式に文字列を効果的に「圧縮」でき、さらに、ブロックが同一の文字で囲まれている場合は、中間位置をカバーするために任意のブロックを拡張できることを意味します。 

等価性に関して重要なのは、両方の文字列を共通の「ブロック互換性構造」に変換できるかどうかです。 重要な不変条件は、次の位置のシーケンスであることがわかります。`0`そして`1`各文字列から達成可能な最終構成で交互に配置する必要があります。 

画期的な簡素化は、実際に操作をシミュレートする必要がないことです。 代わりに、貪欲なスイープで最初に遷移が発生する位置の相対的な順序を尊重して、各文字列を任意の文字列に変換できることがわかります。 これにより、各文字列が各インデックスで割り当てをどのように「サポート」できるかについて貪欲な比較が行われます。 

標準的な解決策は、強制変更の可能な最古および最新の位置を追跡することによって、両方の文字列を同じ正規表現に帰着できるかどうかをチェックすることに帰着します。 実際には、これは交互の実行によって定義されたセグメントの一貫性チェックになります。 

より単純な同等の定式化が現れます。各文字列を、どこにあるかに関する制約を誘導するものとして扱います。`0`-セグメントと`1`-セグメントは嘘をつき、共通の改良点が存在するかどうかを検証する必要があります。 これは、文字列の値が切り替わるインデックスのシーケンスを比較し、それらが実行可能なマージの下で位置合わせされていることを確認することになります。 

より直接的で実装可能な特徴付けは次のとおりです。 

両方の文字列をスキャンすると、各位置でプレフィックスが達成可能なマージで矛盾を強制したかどうかを維持できます。 この条件は、一方の文字列がマージによって他方の文字列がシミュレートできない遷移構造を強制する場合は必ず拒否することを検証することになります。 これは、有効性ウィンドウを注意深く追跡する線形スキャンになります。

 ## アルゴリズムのチュートリアル

 1. 両方の文字列を連続した等しい文字のランに圧縮します。 各ランは、その文字と長さによって表されます。 これにより、遷移が発生する場所の構造的なビューが得られます。 
2. 各文字列について、実行境界の順序を考慮します。 操作では同一のエンドポイントの実行をマージできるため、事実上、特定の境界を削除できますが、順序を変更することはできません。 
3. 唯一意味のある不変式は、次の間の遷移の相対的なパターンです。`0`そして`1`。 各文字列を、指定されたフリップのサブシーケンスと一致する任意のパターンに還元できるかどうかを追跡します。 
4. 両方の実行シーケンスを貪欲に比較し、両方の文字列からの実行を整列させようとするマッチング プロセスをシミュレートします。 
5. いずれかの時点で、一方の文字列の互換性のある実行では一致できない遷移が必要な場合、それは不可能であると結論付けます。 
6. これらのマージ ルールに基づいてすべての実行が一致する場合、両方の文字列を共通の形式に変換することが可能であると結論付けられます。 

### なぜ効果があるのか

 この操作では新しい変更が導入されることはありません。 同一のエンドポイントで囲まれたセグメント上に文字を拡張することによってのみ削除されます。 したがって、強制遷移の相対的な順序は削除されるまで保持され、両方の文字列で安定した遷移の共通のサブシーケンスが認められる必要があります。 このアルゴリズムは、内部境界の削除下での実行構造が共通の改良を許容するかどうかを効果的にチェックします。これはまさに変換可能性の条件です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def compress(s):
    runs = []
    n = len(s)
    i = 0
    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1
        runs.append((s[i], j - i))
        i = j
    return runs

def solve_case(a, b):
    ra = compress(a)
    rb = compress(b)

    # We compare run structures in a greedy aligned way.
    i = j = 0

    while i < len(ra) and j < len(rb):
        ca, la = ra[i]
        cb, lb = rb[j]

        if ca != cb:
            return False

        # We can match min length and reduce both
        take = min(la, lb)
        la -= take
        lb -= take

        ra[i] = (ca, la)
        rb[j] = (cb, lb)

        if la == 0:
            i += 1
        if lb == 0:
            j += 1

    return i == len(ra) and j == len(rb)

t = int(input())
for _ in range(t):
    a = input().strip()
    b = input().strip()
    print("YES" if solve_case(a, b) else "NO")
```どの操作においても等しいブロック間の遷移のみが重要であるため、実装は各文字列をランに圧縮することから始まります。 次に、貪欲なマッチング ステップでは、同じ文字の実行を順番に整列させようとし、マージ プロセスのように長さを消費します。 いずれかの段階で文字が異なる場合は、一方の文字列が、許可された操作ではもう一方の文字列が再現できない構造遷移を必要とすることを意味します。 

微妙な点は、新しい実行を「作成」しようとしないことです。 マージ ロジックはランレングスを短縮するだけであり、これは操作によって境界が削除されるだけで、新しい境界が導入されるわけではないという事実を反映しています。

 ## 特殊なケース

 厄介なケースは、両方の文字列が頻繁に交互しているにもかかわらず、同じエンドポイントを共有している場合です。 例えば、`010101`対`011111`。 単純なアプローチでは、0 と 1 の数を比較する可能性がありますが、それは合計よりも初期の構造が重要であるという事実を無視しています。 貪欲なアライメント中に実行の不一致がすぐに現れるため、アルゴリズムはこれを処理します。 

もう 1 つのケースは、1 つの弦がすでに大きなセグメントで完全に平らになっているのに、もう 1 つの弦が頻繁に交互になる場合です。 どちらにも同じ複数の文字セットが含まれていますが、順序付けの制約に違反しないと調整できないほど、実行構造が異なります。 圧縮と照合のステップにより、この不一致が早期に明らかになり、正確さが保証されます。
