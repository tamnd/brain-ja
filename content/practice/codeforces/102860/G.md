 ## 解決策
 # 問題の理解

 アイスクリームコーンがいくつかあります。 の`i`- 番目のコーンには最初に含まれています`a[i]`アイスクリームのグラム数。 時間が経つにつれて、コーンは一定の速度で溶けるため、アイスクリームが失われます`v`毎秒グラム数。 同時に、一定の合計レートでアイスクリームを食べることができます`u`毎秒グラム数、どのコーンから食べるかを選択し、いつでもコーンを切り替えることができます。 

課題は、すべてのアイスクリームを完全に食べ終えるのに必要な最小限の時間を見つけることです。 出力はこの最小時間です。 

制約によって、意図された複雑さが明確になります。 あたりまでで`10^5`コーンでは、可能なアクションの数が非常に多くなる可能性があるため、食事の小さな切り替えをすべてシミュレートすることは不可能です。 次のような、すべてのコーンを少数回だけ処理するソリューションが必要です。`O(n log n)`または`O(n)`。 

よくある間違いは、アイスクリームの総量だけを考えることです。 コーンは食べる前に消えてしまう可能性があるため、溶けると答えが変わります。 たとえば、重みのある 2 つの円錐がある場合、`100`そして`1`、融解速度が非常に大きいため、最初の円錐の作業中に 2 番目の円錐が溶けてなくなる可能性があります。 答えは単純ではありません`(101 / (u + v))`。 

もう 1 つのエッジ ケースは、すべてのコーンが同じサイズである場合です。 同じサイズのコーンが 3 つある入力の場合`5`、アルゴリズムは、3 つすべてが同時にアクティブになり、食事を共有する必要があることを認識する必要があります。 常に 1 つのコーンのみを選択する貪欲なソリューションでは、誤って終了が遅れてしまいます。 

例えば：```
3 1 1
5 5 5
```正しい答えは、`5`, なぜなら、5秒後にはすべてのコーンが食べられるか溶けてしまうからです。 食べた量のみが重要であると仮定したソリューションでは、より大きな値が計算される可能性があります。 

## アプローチ

 直接的なアプローチでは、プロセスをシミュレートしようとします。 常に残量が最も多いコーンを選択し、それを繰り返し食べることができました。 この戦略は直感的です。なぜなら、最大のコーンに時間を費やすことで、いずれにしても溶けそうなコーンに時間を浪費することが避けられるからです。 問題は、スイッチの数に制限がないことです。`n`。 いくつかのコーンが同じ残りのサイズに達すると、それらを継続的に切り替える必要があり、正確なシミュレーションが遅くなりすぎる場合があります。 

重要な観察は、咬傷の正確な順序を知る必要がないということです。 必要なのはできるだけ早い終了時間だけです。 

答えが次のようになったとします。`t`秒。 この間に`t`数秒間、すべてのコーンが正確に失われます`v * t`自然にグラム。 コーンがあれば`a[i]`グラムの場合、まだ食べる必要がある量は次のようになります。```
max(0, a[i] - v * t)
```私たちが食べなければならない総量は、これらの値の合計です。 きっちり食べられるので`u * t`グラム単位`t`秒、時間`t`次の場合に可能です。```
sum(max(0, a[i] - v*t)) <= u*t
```この条件は単調です。 ある程度の時間が機能する場合は、より長い時間ごとに機能します。 これにより、答えの二分探索が可能になります。 

ブルート フォース シミュレーションは、最適な貪欲な動作に従うため機能しますが、コーン間の変更の数が多すぎる可能性があるため、失敗します。 二分探索アプローチでは、スケジュールを作成する必要がなくなり、指定された終了時間が実現可能かどうかだけをチェックします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 最悪の場合大きすぎる | お(1) | 遅すぎる |
 | 二分探索 | O(n log C) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. コーンのサイズと、食べる速度と溶ける速度を読み取ります。 
2. 応答時間の二分探索。 下限は`0`上限は、すべてのアイスクリームが確実になくなる程度に大きく選択できます。 
3. 中間の時間`t`、溶けた後にまだ食べる必要があるアイスクリームの量を計算します。```
need = sum(max(0, a[i] - v*t))
```これは、溶けても生き残る唯一のアイスクリームを表します。 
4. 比較する`need`私たちが食べられる量は次のとおりです。```
can_eat = u*t
```もし`need <= can_eat`、選択した時間で十分なので、より短い答えを検索してください。 それ以外の場合は、時間を増やしてください。 
5. バイナリ検索の精度が十分になるまで続行し、結果の時間を出力します。 

機能する理由: 一定期間`t`、自然溶解後のすべてのコーンの残りの量が強制されます。 溶けて食べられる以上に多くのアイスクリームを消滅させる戦略はありません。 残りの量が私たちの食事の許容範囲内に収まる場合、一部のスケジュールはその時間までに終了する可能性があります。 実現可能性は false から true に 1 回だけ変化するため、二分探索では最小の有効時間を見つけます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, u, v = map(int, input().split())
    a = list(map(int, input().split()))

    def ok(t):
        need = 0
        melted = v * t
        for x in a:
            if x > melted:
                need += x - melted
        return need <= u * t

    lo, hi = 0.0, max(a) / v if v else 1e18

    if v == 0:
        hi = sum(a) / u

    else:
        hi = max(hi, sum(a) / u)

    for _ in range(100):
        mid = (lo + hi) / 2
        if ok(mid):
            hi = mid
        else:
            lo = mid

    print("{:.10f}".format(hi))

if __name__ == "__main__":
    solve()
```実現可能性機能はソリューションの中核です。 食べる順番をシミュレートするものではありません。 後に残っているものだけをチェックします`t`秒数と、食べる人がその量を除去できるかどうか。 

答えが実数であるため、二分探索では浮動小数点が使用されます。 誤差が必要な精度をはるかに下回るには、100 回の反復で十分です。 この境界は、溶融が存在しない特殊なケースもカバーします。 いつ`v = 0`, 答えは単純に総量を食べる速度で割ったものなので、上限は別途設定されています。 

掛け算`v * t`は大きくなる可能性があるため、ここでは Python の浮動小数点演算が役立ちます。 整数オーバーフローの問題はありません。

 ## 特殊なケース

 すべてのコーンが同一の場合でも、実現可能性チェックではそれらを一緒に扱うため、二分探索は機能します。 のために：```
3 1 1
5 5 5
```で`t = 5`, すべてのコーンが完全に溶けているので、必要な食べる量はゼロです。 答えは`5`。 

融解がゼロの場合、アイスクリームが自然に消えることはありません。 のために：```
1 5 0
20
```全部食べなければなりません`20`グラムで`5`グラム/秒、正確に与える`4`秒。 

1 つの円錐が他の円錐よりもはるかに大きい場合、小さな円錐はそこに到達する前に消えてしまう可能性があります。 表現`max(0, a[i] - v*t)`自動的にそれらを削除するため、アルゴリズムはすでに溶けたアイスクリームを食べる能力を無駄にすることはありません。
