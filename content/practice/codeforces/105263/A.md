 ## 解決策
 ## 問題の理解

 ネットワーク イベントのライブ ストリームを処理しています。 各イベントは、構成の更新またはパケットの到着のいずれかです。 パケットには、送信者 IP アドレス、タイムスタンプ、パケット内のバイト数という 3 つの情報が含まれます。 システムは、最後に受け入れられたトラフィックに応じたルールに基づいて、各パケットを受け入れるか無視するかを決定します。 

常に、現在のパケット時刻 t で終了する幅 δ のスライディング タイム ウィンドウを維持します。これは、タイムスタンプが [t − δ + 1, t] の範囲内にある受け入れられたパケットのみを考慮することを意味します。 このウィンドウ内で、各 IP アドレスの統計 (その IP からのパケットが何個受け入れられたか、および合計バイト数が受け入れられたか) を個別に追跡します。 

パケットを仮定して検討した結果、ウィンドウ内でその IP から受け入れられたパケットの数が α に達するかそれを超えるか、またはウィンドウ内でその IP から受け入れられる総バイト数が β に達するかそれを超える場合、そのパケットは拒否されます。 それ以外の場合、それは受け入れられ、将来の決定に貢献します。 

課題は、ウィンドウとしきい値の両方が動的に変化し、タイムスタンプを厳密に増加させながら最大 100,000 件のイベントを順番に処理する必要があることです。 最後の条件は、時間内に任意に検索するのではなく、単調な方法で古いパケットを削除できるため、非常に重要です。 

クエリごとに以前のすべてのパケットを再スキャンする単純な実装では、パケットごとに最大 O(n) 個の履歴を繰り返し走査することになり、O(n²) 個の動作が発生しますが、これは 105 回の操作では実行不可能です。 古いイベントの増分挿入と効率的な削除をサポートする構造が必要です。 

微妙なエッジ ケースの 1 つは、δ が非常に大きく、すべてのタイムスタンプよりも大きくなる可能性がある場合です。 この場合、期限切れになるものは何もなく、ウィンドウは「これまでのすべて」になりますが、オーバーフローやスキャンの速度が低下することなく処理する必要があります。 もう 1 つの問題はパラメータの変更です。α、β、δ はいつでも変更される可能性があります。これは、以前は受け入れられていたパケットが同じ履歴に基づいて拒否される可能性があることを意味します。 

最も重要な隠れた問題は、受け入れられたパケットは将来の状態に影響を与えますが、無視されたパケットは影響を受けないことです。 これは、「認識されたパケット」と「カウントされたパケット」を慎重に分離し、受け入れられたパケットのみがスライディング ウィンドウ統計に寄与するようにする必要があることを意味します。 

## アプローチ

 ブルート フォース ソリューションでは、以前に受け入れられたすべてのパケットをスキャンし、現在の時間枠でフィルタリングし、IP ごとのカウントとバイト数を合計することによって各パケットを処理します。 これは正しいですが、コストがかかります。各クエリは O(n) 個の履歴に影響を与える可能性があり、最大 10⁵ クエリでは、最悪の場合 10¹⁰ の操作が必要になります。 

重要な観察は、タイムスタンプが厳密に増加していることです。 これにより、スライディング ウィンドウがキューの問題に変換されます。 パケットが古くなりすぎると、再び関連性がなくなるため、受け入れられたパケットを FIFO 構造に保存し、古くなったパケットを前から追い出すことができます。 

IP ごとの制約をサポートするために、IP ごとに集計カウンタを維持し、パケットがウィンドウに出入りするたびにそれらを段階的に更新します。 パケットが受け入れられると、それをキューにプッシュし、その IP のカウンターを更新します。 新しい各パケットを処理する前に、まず期限切れのパケットをキューの先頭から追い出し、対応する IP 状態からその影響を差し引きます。 

これにより、各パケットが O(1) の償却作業に削減されます。受け入れられた各パケットは 1 回挿入され、1 回削除されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適 (キュー + ハッシュ マップ) | O(n) 償却 | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

受け入れられたパケットのキューを維持します。 各エントリには、タイムスタンプ、IP、およびサイズが保存されます。 同時に、2 つのハッシュ マップも保持します。1 つは現在のウィンドウ内の IP ごとのパケット数、もう 1 つは IP ごとの合計バイトです。 

また、いつでも変更できる現在のパラメーター α、β、δ も維持します。 

### ステップ

 1. 次のイベントを読み取ります。 構成更新の場合は、α、β、δを置き換えます。 古いパケットは将来のパケットを処理するときに遅延検証されるため、すぐに構造を変更する必要はありません。 
2. 時刻 t のパケットの場合、まず期限切れのパケットを削除します。 キューが空ではなく、フロント パケットのタイムスタンプが t − δ + 1 である間に、キューからパケットをポップし、その IP のカウンターからその寄与を差し引きます。 これにより、ウィンドウの不変条件が評価前に確実に復元されます。 
3. クリーンアップ後、パケットの IP の現在の状態 (ハッシュ マップから current_count と current_bytes) を計算します。 
4. 新しいパケットの追加が制約に違反するかどうかを確認します。 具体的には、current_count + 1 ≥ α または current_bytes + size ≥ β であるかどうかをテストします。 
5. いずれかの条件が成立する場合は、"ig" を出力し、パケットを完全に破棄します。 
6. それ以外の場合は、「ac」を出力し、パケットをキューにプッシュし、その IP のカウンターを更新します。 
7. 次のイベントに進みます。 

### なぜ効果があるのか

 重要な不変条件は、各パケットを処理する前に、タイムスタンプが有効ウィンドウ [t − δ + 1, t − 1] 内にある受け入れられたパケットがキューに正確に含まれていることです。 期限切れのパケットはすべて削除されており、残っているパケットはすべて現在の決定に関連していることが保証されています。 

受け入れられたパケットのみを追加し、パケットがウィンドウから外れた場合にのみ削除するため、IP ごとのカウンターは、スライディング ウィンドウ内の受け入れられたトラフィックの実際の状態を常に反映します。 拒否によって挿入が妨げられるため、拒否されたパケットによって将来の状態が汚染されることはなく、正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque, defaultdict

def solve():
    T = int(input())
    for _ in range(T):
        Q = int(input())

        q = deque()
        cnt = defaultdict(int)
        byt = defaultdict(int)

        alpha = beta = delta = 0

        for i in range(Q):
            parts = input().split()
            typ = int(parts[0])

            if typ == 2:
                alpha = int(parts[1])
                beta = int(parts[2])
                delta = int(parts[3])
            else:
                ip = parts[1]
                t = int(parts[2])
                sz = int(parts[3])

                # remove expired
                left_bound = t - delta + 1
                while q and q[0][0] < left_bound:
                    tt, ip0, sz0 = q.popleft()
                    cnt[ip0] -= 1
                    byt[ip0] -= sz0

                c = cnt[ip]
                b = byt[ip]

                if c + 1 >= alpha or b + sz >= beta:
                    print("ig")
                else:
                    print("ac")
                    q.append((t, ip, sz))
                    cnt[ip] += 1
                    byt[ip] += sz

        print("--")

if __name__ == "__main__":
    solve()
```キューには受け入れられたパケットのみが保存されるため、カウンタへのすべての更新は有効な送信に正確に対応します。 追い出しステップは、ウィンドウが常に現在のタイムスタンプと一致するように、新しいパケットをチェックする前に実行されます。 

実装の微妙な詳細は、左境界を t − δ + 1 として計算することです。これは包括的ウィンドウの定義と一致し、現在のタイムスタンプのみが有効なδ = 1 の場合に正しい処理が保証されます。 

しきい値に達すること自体がすでにルールに違反しているため、決定チェックでは > ではなく ≥ が使用されます。

 ## 特殊なケース

 重要なエッジ ケースは、δ が十分に大きく、パケットが期限切れにならない場合に発生します。 この状況では、キューは単調に増加しますが、エビクション条件がトリガーされないため、正確性は保たれます。 カウンタは受け入れられたすべての履歴を常に反映するため、アルゴリズムは引き続き機能します。 

もう 1 つのケースは、α または β が 1 に等しい場合です。α = 1 の場合、スライディング ウィンドウには少なくとも現在のパケットが常に含まれるため、同じ IP からの 2 番目に受け入れられたパケットは、それが後で発生したとしても直ちに制約に違反します。 アルゴリズムは挿入前に c + 1 ≥ α をチェックするため、これを正しく処理します。 

3 番目のケースは、パラメータの急速な変更です。 緩い制約の下でパケットを受け入れ、αとβを厳しくするとします。 過去に遡ってパケットを削除することはありません。 代わりに、次のパケット評価では更新された制約が使用されますが、キューには有効なウィンドウ履歴のみが反映されます。 この分離により、過去に受け入れられたパケットは状態のまま残りますが、新しいルールの下で将来の決定に正しく影響を与えることが保証されます。
