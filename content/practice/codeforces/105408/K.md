 ## 解決策
 ## 問題の理解

 私たちには、いくつかの食材がストックされたキッチンが与えられています。 各成分はある程度の量から始まります。 料理のメニューがあり、どの料理も調理時に一定量のこれらの食材を消費します。 最後に、一連の顧客の注文があり、それぞれの注文はすべて一緒に準備する必要がある料理のリストです。 

注文は指定された順序で厳密に処理される必要があります。 注文ごとに、現在の食材の在庫がその注文で要求されたすべての料理を準備するのに十分であるかどうかを確認します。 そうであれば、使用した材料を差し引いて次に進みます。 完全に準備できない注文に初めて遭遇すると、キッチンはすぐに停止し、この失敗が発生する前に正常に完了した注文の数を報告します。 

制約は小さく、最大でも 100 種類の食材、100 種類の料理、および 100 件の注文です。 各料理には最大 100 の食材を使用でき、各注文には最大 100 の料理を含めることができます。 このサイズは、注文ごとに材料の使用量を最初から再計算することが可能であることをすぐに示唆しています。 最悪の場合でも、数百万回程度のプリミティブ操作を実行していますが、これは Python の 1 秒のソリューションの制限内に十分収まります。 

素朴な推論による微妙な失敗例は、同じ注文内および以前の注文にまたがる料理全体で食材の使用量が累積されることを忘れていることから生じます。 たとえば、材料 1 の数量が 5 で、最初の注文で 3 単位を使用し、2 番目の注文でさらに 3 単位を使用した場合、個々の料理を単独で見れば手頃な価格に見えても、2 番目の注文は失敗するはずです。 もう 1 つのよくある間違いは、不足を発見する前に注文を部分的に適用することです。 注文全体がアトミックに成功するか失敗する必要があります。 

## アプローチ

 これに対処する直接的な方法は、説明どおりにプロセスを正確にシミュレートすることです。 現在の食材の在庫を保管しております。 注文ごとに、その注文内のすべての料理の寄与を合計することで、必要な材料の総消費量を計算します。 その注文の合計要件がわかったら、すべての材料が十分な量入手可能かどうかを確認します。 「はい」の場合は、在庫からそれらを差し引きます。 そうでない場合は停止します。 

この強引なアプローチは、問題ステートメントで定義されたプロセスを反映しているため、正しいです。 非効率性の懸念は、材料の使用量を繰り返し再計算することから生じます。 すべての注文をすべての料理に拡張し、各料理をその材料要件に拡張すると、注文ごとに最大 100 の料理、各料理に最大 100 の材料を加えることになり、合計でおよそ 1e6 の操作が行われますが、これはすでに小さいです。 各注文を 1 回だけ処理し、最初の失敗で停​​止するため、制限を超えるようなタイム ステップ間での再計算が繰り返されることはありません。 

重要な観察は、集約以外には動的構造や最適化は必要ないということです。 各注文は共有の可変在庫を除いて独立しているため、注文ごとに簡単な蓄積ステップのみが必要です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション | O(O × 平均的な料理 × 料理ごとの材料) | O(M×N) | 承認済み |
 | ディッシュごとの事前計算された使用量 + シミュレーション | O(O × 平均的な料理 × N) | O(M×N) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、料理の説明を、必要な材料にすぐにアクセスできる構造に変換します。 その後、すべての注文が完了するか失敗するまで、各注文の処理を繰り返します。

1. すべての材料の初​​期量を読み取り、配列に保存します。 これはキッチンの在庫の現在の状態を表します。 
2. 各料理について、各材料の必要量を表すサイズ N のリストまたは配列を保存します。 これにより、注文処理中の繰り返しの解析が回避され、各料理が直接ベクトルのようなオブジェクトに変換されます。 
3. 注文ごとに、一時的な配列を作成します`need`サイズ N はゼロに初期化されます。 この配列は、その注文に対する材料需要の合計を集計します。 
4. 注文するすべての料理について、その材料の要件を`need`。 このステップでは、料理のリストを単一の統合された要件ベクトルに変換します。 
5. 注文されたすべての料理を処理した後、比較します`need`現在の在庫と照らし合わせて。 材料の要件が利用可能な在庫を超えた場合は、直ちに停止し、これまでに正常に処理された注文の数を返します。 
6. 注文が実行可能な場合は、減算します。`need`在庫から取り出して次の注文に進みます。 

重要な考え方は、各注文が分割できないトランザクションとして扱われるということです。最初にその全額のコストを計算し、それから初めてそれを適用します。 

### なぜ効果があるのか

 どの時点でも、在庫は、以前に成功したすべての注文を処理した後に残っているものを正確に表します。 各注文は、要件の完全な集約を使用して、この状態に対して評価されます。 オーダーを部分的に適用することはなく、料理の要件は固定され独立しているため、各オーダーの決定は現在の状態に関して正しいものです。 これにより、在庫には完全に完了した注文のみが常に反映されるという不変条件が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    N, M, O = map(int, input().split())
    stock = list(map(int, input().split()))

    dishes = [None] * M
    for i in range(M):
        k = int(input())
        req = [0] * N
        for _ in range(k):
            ing, amt = map(int, input().split())
            req[ing - 1] = amt
        dishes[i] = req

    done = 0

    for _ in range(O):
        parts = list(map(int, input().split()))
        o = parts[0]
        order_dishes = parts[1:]

        need = [0] * N

        for d in order_dishes:
            req = dishes[d - 1]
            for i in range(N):
                if req[i]:
                    need[i] += req[i]

        ok = True
        for i in range(N):
            if need[i] > stock[i]:
                ok = False
                break

        if not ok:
            break

        for i in range(N):
            stock[i] -= need[i]

        done += 1

    print(done)

if __name__ == "__main__":
    solve()
```このソリューションでは、順序評価が単純な累積ステップになるように、各料理を固定長の食材ベクトルとして事前計算します。 重要な実装の詳細は、実現可能性をチェックする際にインベントリの変更を避けることです。 注文全体が満足できることを確認した後にのみ減算します。 

もう 1 つの微妙な点はインデックス付けです。料理と食材は入力時に 1 から始まるため、どちらも内部的に 0 から始まるものに変換されます。 実現可能性チェックは、在庫配列の変更の前に実行する必要があります。そうしないと、失敗した注文によってリソースが誤って消費されてしまいます。 

## 実用的な例

 1 つの材料と 3 つの注文がある単純化されたシナリオを考えてみましょう。 

### サンプルトレース

 在庫を追跡し、注文処理を行います。 

| ステップ | 在庫 | 注文 | 必須 | 実現可能 | 新しい在庫 |
 | --- | --- | --- | --- | --- | --- |

 | 2 | [3] | [1] | [3] | はい | [0] |
 | 3 | [0] | [1] | [3] | いいえ | 停止 |

 このプロセスは、在庫が不足するまで注文全体で消費がどのように蓄積されるかを示しています。 

これにより、アルゴリズムが注文ごとの実現可能性だけでなく、累積的な枯渇を正しく処理していることが確認されます。 

### 初期障害が発生した別のトレース

 | ステップ | 在庫 | 注文 | 必須 | 実現可能 | 新しい在庫 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | [2, 2] | [1] | [3,1] | いいえ | 停止 |

 ここでは、最初の注文はすぐに失敗するため、在庫の変更は発生せず、答えはゼロになります。 これにより、注文処理のアトミックな性質が検証されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

| スペース | O(M × N + N) | 皿の要件と現在の在庫の保管 |

 すべての制限が最大 100 であるとすると、合計作業量は 1e6 オペレーション程度となり、時間とメモリの制約内に十分収まります。

 ## 特殊なケース

 最初のエッジケースは、最初の注文がすでに利用可能な在庫を超えている場合です。 この状況では、アルゴリズムは実現可能性チェックを実行し、不足を検出し、在庫を変更せずにゼロを返します。 在庫には完了した注文のみが反映されるという不変条件により、部分的な控除が発生しないため、正確性が保証されます。 

個々の料理は手頃な価格に見えても、単一の注文内の複数の料理がまとめて在庫を超える場合、別の特殊なケースが発生します。 アルゴリズムはチェックする前にすべての寄与を集計するため、料理ごとではなく注文レベルで障害が検出されます。 これにより、誤った早期減算が防止されます。 

最後のケースは、注文によって材料が完全になくなってしまった場合です。 比較が厳密なので(`need[i] > stock[i]`）、平等が認められ、その後在庫はゼロになります。 これにより、その材料を必要とする後続の注文の正確性が維持され、材料をまったく必要としない限り、正しく失敗します。
