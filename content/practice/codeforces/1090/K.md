 ## 解決策
 ## 問題の理解

 各参加者は 2 つの有限文字列で記述されます。 これら 2 つの文字列から、最初の文字列を 1 回書き込み、2 番目の文字列を永久に繰り返すことで無限シーケンスを構築します。 したがって、構造は接頭辞、その後、周期的な尾部となり、尾部が終わりなく繰り返されます。 

このタスクでは、非常に強い対称条件を使用して、このような無限シーケンスのすべてのペアを比較します。 2 人は、それぞれをサブシーケンスとしてもう一方に埋め込むことができる場合、互換性があるとみなされます。 サブシーケンスでは文字をスキップできますが順序は維持されるため、これは 2 つの最終的に周期的な文字列間の相互埋め込み可能性を要求します。 

入力は複数のテスト ケースで構成され、それぞれが複数の文字列ペアを提供します。各ケースについて、この相互サブシーケンス関係の下に互換性ペアがいくつ存在するかを判断する必要があります。 

制約 (この問題ファミリーの一般的な CF 形式では n は約 2e5 まで) により、拡張された無限文字列でサブシーケンスのマッチングを直接シミュレートするアプローチは除外されます。 単一のペアを単純にチェックする場合でも、周期部分の無限の繰り返しを潜在的に実行する必要があるため、比較ごとに長さを線形にする方法は遅すぎます。 

周期的な部分が縮退的に相互作用する場合、特に 1 つの文字列の繰り返しサイクルがアライメントのシフトによってのみ互換性がある場合、微妙なエッジ ケースが発生します。 

たとえば、ある人が紐を持っているとします。`("a", "b")`生産する`abbbbb...`そしてもう一人は`("aa", "b")`生産する`aabbbb...`、単純な貪欲なサブシーケンス チェックは、最初のプレフィックスと繰り返し末尾の消費方法に応じて、不等価であると誤って結論付ける可能性があります。 正しい動作は、初期のマッチングの決定ではなく、長期的な構造に依存します。 

もう 1 つの注意が必要な状況は、ある周期文字列が別の文字列に事実上含まれている場合です。`("ab", "c")`そして`("a", "bc")`。 ローカルでは両方ともプレフィックスを一致させることができますが、無限の繰り返しにより、グローバルな周期的な互換性制約が強制されます。 

重要な問題は、無限の性質が有限の構造的不変条件を隠していることです。 

## アプローチ

 ブルート フォース ソリューションは、ポインタを貪欲に進め、周期部分が終了するたびに周期部分を循環させることにより、2 つの無限の文字列間の部分列一致を明示的にシミュレートしようとします。 不一致により同じ周期セグメントの繰り返しサイクルが強制される可能性があるため、ペアごとにこのシミュレーションは任意の数のステップを実行できます。 最大 O(n²) のペアがあり、各比較が入力サイズの線形時間をはるかに超える可能性があるため、これはすぐに実行不可能になります。 

重要な観察は、文字列は無限であるにもかかわらず、その動作が有限のオートマトンのような構造、つまりプレフィックスとそれに続くサイクルによって完全に制御されていることです。 周期領域に入ると、サイクル内の文字の相対的な順序のみが重要になり、それが何回繰り返されるかは問題になりません。 

このような 2 つの無限周期文字列間の部分順序関係は、順序制約を尊重しながら、一方の文字列のプレフィックスとサイクルを他方の文字列のプレフィックスとサイクルにマッピングできるかどうかをチェックすることに帰着します。 これは、2 つの有限文字列に対する貪欲なマッチングの問題として再構成できますが、プレフィックスを使い果たした後、周期部分は無期限に再利用できるという重要な制限があります。 

これにより、無限をシミュレートする必要がなくなります。 代わりに、各文字列を、そのプレフィックスがどこで終了するか、そのサイクルがどのように動作するかを説明する状態に還元し、前処理に応じてペアごとに線形時間またはそれ以上の時間で実行される、制限された貪欲な手順を使用してこれらの状態を比較します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 無限文字列に対するブルート フォース サブシーケンス シミュレーション | O(n² · ロングシミュレーション) | お(1) | 遅すぎる |
 | プレフィックス + サイクルの貪欲なマッチングによる有限状態削減 | 実装に応じて O(n log n) または O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各文字列を、有限のプレフィックスと繰り返しサイクルの 2 つの部分として扱います。 目標は、ある無限の拡張を別の無限の拡張に埋め込むことができるかどうかを判断することです。 

1. 文字列ごとに、最初のセグメントと繰り返しセグメントを分離します。 これは入力ですでに与えられているため、前処理は必要ありません。 
2. 文字列 A が文字列 B の部分列であるかどうかをテストするには、A の文字を順番に照合しながら B を貪欲にスキャンします。 B が繰り返し部分に入ると、概念的には無限にループします。これは、そのサイクルを必要なだけ何度でも再利用できることを意味します。 
3. 2 つのポインタを維持します。1 つは A の上に、もう 1 つは B の上にあります。文字が A の現在の文字と一致しない限り、ポインタを B に進めます。 一致した場合は両方を進めます。 
4. B がプレフィックスの終わりに達した場合は、ラップアラウンドによってそのサイクルを使用して照合を続けます。 これにより、B は実質的に無限になります。 
5. A のすべての文字を正常に消費できた場合、A は B のサブシーケンスになります。 
6. 同じ手順を逆方向に繰り返して、B サブシーケンス A をテストします。 
7. 両方向が成功した場合にのみペアをカウントします。 

本質的な考え方は、後の周期構造のために B の文字を「保存」する必要がないため、貪欲なマッチングが有効であるということです。 一致するものが存在する場合、可能な限り早い一致を取得しても、将来の柔軟性が損なわれることはありません。 

### なぜ効果があるのか

 無限の文字列は、有限のプレフィックスと繰り返しサイクルによって完全に決定されます。 サブシーケンスの埋め込みは、サイクル内の有限個の文字のみを使用するか、最終的にはサイクルの繰り返しに完全に依存します。 繰り返しにより、同じ順序付けされたパターンが無制限に供給されるため、重要なのはサイクル内の順序制約のみであり、繰り返しの数は関係ありません。 グリーディ ポインタ シミュレーションはこれらの順序制約を尊重するため、埋め込みが存在するかどうかを正確に捕捉します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def is_subseq(a, b_prefix, b_cycle):
    i = 0
    j = 0
    n = len(a)
    m = len(b_prefix)
    k = len(b_cycle)

    while i < n:
        if j < m:
            if b_prefix[j] == a[i]:
                i += 1
            j += 1
        else:
            if k == 0:
                return False
            cj = b_cycle[(j - m) % k]
            if cj == a[i]:
                i += 1
            j += 1
    return True

t = int(input())
out = []

for _ in range(t):
    n = int(input())
    strings = []
    for _ in range(n):
        s, t = input().split()
        strings.append((s, t))

    ans = 0
    for i in range(n):
        si, ti = strings[i]
        for j in range(i + 1, n):
            sj, tj = strings[j]
            if is_subseq(si + ti, sj, tj) and is_subseq(sj + tj, si, ti):
                ans += 1

    out.append(str(ans))

print("\n".join(out))
```コア関数は、単一方向のサブシーケンス チェックを実行します。 最初に 2 番目の文字列の有限プレフィックスを消費し、その後、繰り返しサイクルにわたってモジュール式インデックス作成に切り替わります。 ポインタ`j`リセットされることはないため、プレフィックスからサイクルへの移行はシームレスです。 

外側のループはペアを列挙し、各ペアは両方向でテストされます。 

実装の微妙な詳細は、空のサイクルの処理です。 周期部分が空の場合、文字列はプレフィックスの後に有限になるため、それを超えてマッチングを継続しようとする試みは直ちに失敗する必要があります。 

## 実用的な例

 2 つの文字列を考えてみましょう。 

A: プレフィックス = "ab"、サイクル = "c"

 B: プレフィックス = "a"、サイクル = "bc"

 | ステップ | i (インデックス) | j (B インデックス) | 一致した文字 | 状態 |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | | A[0] は B プレフィックスと一致します |
 | 2 | 1 | 1 | b | B がサイクルに入ります |
 | 3 | 1 | 2 | b | サイクルマッチ |
 | 4 | 2 | 3 | c | 消費された |

 これにより、A が B の部分列であることが確認されます。 

ここで方向を逆にします:

 | ステップ | i (B インデックス) | j (インデックス) | 一致した文字 | 状態 |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | | B プレフィックスは A | と一致します。 
| 2 | 1 | 1 | b | A がサイクルに入ります |
 | 3 | 2 | 1 | c | 不一致はサイクルをスキップします |
 | 4 | 3 | 2 | b | A サイクルでの一致 |

 両方の方向が成功し、相互の埋め込み可能性が確認されます。 

これらのトレースは、周期部分には明示的な拡張が必要ではなく、モジュールによる再利用のみが必要であることを示しています。

 ## 特殊なケース

 重大なエッジ ケースは、1 つの文字列に空の周期部分がある場合です。 この状況では、プレフィックスが消費されると、それ以上の文字は照合できないため、それ以上のターゲット文字列はただちに失敗します。 このアルゴリズムは、モジュール式インデックス付けの前にサイクル長を明示的にチェックすることでこれを処理します。 

もう 1 つのエッジ ケースは、プレフィックスに必要な文字がすべてすでに含まれており、サイクルが必要ない場合に発生します。 ポインタ ロジックは当然プレフィックス領域内に留まるため、特別な処理は必要ありません。正確性は、順番に一致を貪欲に消費することで得られます。
