 ## 問題の理解

 私たちには、Sagar が忙しい時期を説明するスケジュールが与えられており、Jagjeet が選択した瞬間がそれらの忙しい時間帯に該当するかどうかを判断する必要があります。 

サーガルの多忙なパターンは時間とともに始まります`a`。 その後、彼の可用性は構造化された方法で交互に切り替わります。すべてのサイクルは以下に基づいています。`b`。 各サイクルには、ビジーな瞬間が 2 回あります。1 回目はサイクルの開始時、2 回目はその 1 秒後です。 具体的には、忙しい時間帯は次のペアを形成します。`a, a+1`、 それから`a+b, a+b+1`、 それから`a+2b, a+2b+1`、 等々。 

したがって、タスクは単純です。クエリごとに、指定された時間があるかどうかを確認します。`c`これらのビジー タイムスタンプのいずれかと同じです。 

入力サイズは小さく、最大 1000 のテスト ケースと最大 10^9 の値が含まれます。 これにより、時間の経過に伴うシミュレーションやスケジュールの反復的な拡張が即座に除外されます。 正しいソリューションは、テスト ケースごとに一定時間内にメンバーシップを決定する必要があります。 

よくある間違いは、パターンを連続した間隔として解釈することです。たとえば、Sagar が次のような範囲でビジーであると考えることです。`[a, a+1]`、`[a+b, a+b+1]`などとなりますが、誤って重複または延長された間隔として処理されてしまいます。 間隔は分離されており、重なり合わないため（なぜなら、`b ≥ 1`)、オーバーラップは次の場合にのみ発生します。`b = 1`この場合、連続するペアは連続するビジー セグメントにマージされます。 その場合でも、直接のメンバーシップ チェックは引き続き機能しますが、不注意な間隔マージ ロジックによりエッジ処理が機能しなくなる可能性があります。 

もう 1 つの微妙なエッジケースは次のような場合です。`c < a`。 この場合、Sagar はまったく忙しくなり始めていないため、答えは「NO」でなければなりません。 同様に、`b = 1`、忙しい時間は次から始まるすべての整数になります。`a`、 以来`(a, a+1), (a+1, a+2), ...`～からのすべての整数をカバーします`a`これからも。 

## アプローチ

 ブルートフォースアプローチでは、ペアを生成することで、Sagar の忙しい時間をシミュレートします。`(a + k*b, a + k*b + 1)`増やすための`k`を超えると停止します`c`。 生成された各ペアについて、次のことを確認します。`c`いずれかのエンドポイントと一致します。 これは、記述されたパターンを直接構築するため、正しいです。 

ただし、これは次の場合には非効率になります。`c`に比べて大きい`a`そして`b`。 最悪の場合、`b = 1`、反復回数は次まで直線的に増加します。`c - a`、最大 10^9 まで大きくすることができます。 いつでも`b`が大きい場合でも、複数のテスト ケースにわたって多くの反復を行うリスクが依然としてあります。 

重要な観察は、構造が完全に周期的であり、列挙する必要がないということです。 代わりに、次のことを判断できます。`c`サイクルインデックスとオフセットに合わせます。 

一定の時間`c`, 混雑している時間帯の場合は、次の 2 つの条件のいずれかを満たしている必要があります。 

まず、これはサイクルの始まりである可能性があります。`c = a + k*b`ある整数に対して`k ≥ 0`。 これは以下と同等です`(c - a) % b == 0`。 

次に、サイクル内で 2 番目に忙しい瞬間である可能性があります。`c = a + k*b + 1`。 これは以下と同等です`(c - a - 1) % b == 0`。 

両方の条件も満たさなければなりません`c ≥ a`、スタート地点より前に混雑する時間帯が発生することはありません。 

これにより、問題はテスト ケースごとの定数時間の算術チェックに縮小されます。

 ## アルゴリズムのチュートリアル

 各テスト ケースを個別に処理し、算術チェックを適用して、忙しいスケジュールのメンバーを決定します。 

1. 値を読み取る`a`、`b`、 そして`c`現在のテストケースの場合。 これらは、開始点、サイクル長、およびクエリ時間を定義します。 
2. もし`c < a`、Sagar は時間的に忙しくないとすぐに結論付けます`c`。 スケジュールは にのみ開始されるため、これは定義から導き出されます。`a`。 
3. かどうかを確認します。`c`かどうかをテストすることで、あるサイクルの最初のビジー位置と一致します。`(c - a) % b == 0`。 これが当てはまるなら、`c`と正確に一致します`a + k*b`ある整数に対して`k`。 
4. 前の条件が失敗した場合は、次のことを確認します。`c`かどうかをテストすることにより、サイクル内の 2 番目のビジー位置と一致します。`(c - a - 1) % b == 0`。 これは以下に対応します`a + k*b + 1`。 
5. いずれかの条件が真の場合、「YES」を出力します。 それ以外の場合は「NO」を出力します。 

### なぜ効果があるのか

 すべての忙しい時間は、2 つの等差数列のうちの 1 つに正確に属している必要があります。`a`ステップ付き`b`、そして で始まるもの`a+1`同じステップで`b`。 これら 2 つのシーケンスはスケジュールを完全に記述しており、それぞれの有効な時間が一意のサイクル インデックスにマップされる必要があるため、誤検知は生成されません。`k`。 モジュロ条件により、整数ステップによってのみ到達可能な時間のみが保証されます。`a`または`a+1`の増分で`b`構造に正確に一致するものは受け入れられます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    for _ in range(n):
        a, b, c = map(int, input().split())

        if c < a:
            print("NO")
            continue

        if (c - a) % b == 0 or (c - a - 1) % b == 0:
            print("YES")
        else:
            print("NO")

if __name__ == "__main__":
    solve()
```コードは、派生した条件に直接に従います。 最初のガードは、スケジュールが開始される前にクエリが存在する場合の簡単な除外を処理します。 2 つのモジュロ チェックは、ビジー パターンを定義する 2 つの等差数列に正確に対応します。 ループは必要ないため、各テスト ケースは一定時間で処理されます。 

微妙な実装の詳細は次のとおりです。`(c - a - 1)`次の場合はマイナスになる可能性があります`c = a`ただし、Python のモジュロはこのコンテキストで負のオペランドを正しく処理し、前の条件によってすでに正確さが保証されています。 初期の`c < a`チェックにより、不必要なあいまいさが防止されます。

 ## 特殊なケース

 重要なエッジケースの 1 つは次のような場合です。`c = a`。 この状況では、最初の忙しい瞬間はまさに に始まるため、答えは常に「YES」でなければなりません。`a`。 アルゴリズムはこれを正しく処理します。`(c - a) % b = 0`と評価される`0 % b = 0`、肯定的な結果を引き起こします。 

もう一つのケースは次のような場合です。`b = 1`。 忙しい時期は、`(a, a+1), (a+1, a+2), ...`からのすべての整数を効果的にカバーします。`a`これからも。 小切手`(c - a) % 1 == 0`については常に真です`c ≥ a`したがって、アルゴリズムはそのようなすべてのケースに対して正しく「YES」を返しますが、`c < a`はすでに除外されています。 

最後に、いつ`c < a`どちらのモジュラー チェックでも、負の算術演算により誤解を招く値が生成される可能性がありますが、早期のガードによりこのシナリオは完全に防止されます。 たとえば、次の場合`a = 10, c = 3`、 それから`(c - a) = -7`Python ではモジュロ演算でも有効な剰余を返すことができますが、スケジュールがまだ開始されていないため、それらは無関係であり、正しい出力は常に「NO」になります。
