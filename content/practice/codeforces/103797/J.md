 ## 解決策
 ## 問題の理解

 問題ごとに参加者のグリッドが与えられます。各ペアは$(c, p)$1 人の出場者が 1 つの問題を解決していることを表します。 時間が経つにつれて、私たちは提出物の時系列の流れを受け取ります。各提出物はそのようなセルの 1 つに属し、評決が行われます。 

重要なルールは、同じ問題に対して最初に承認されたソリューションの前に発生した誤った送信のみを考慮するということです。$(c, p)$。 セルが最初の AC を受信すると、そのセルは非アクティブになり、その後のセルへの送信は完全に無視されなければなりません。 

すべての提出物を処理した後、多くの質問に答える必要があります。 各クエリは、さまざまな出場者とさまざまな問題によって定義された長方形のサブグリッドを提供します。 その四角形については、その中のすべてのセルにわたってカウントされた不正な送信 (AC の前に発生したもの) の合計数を計算する必要があります。 

制約はすでに解決策の形状を示唆しています。 グリッド サイズは最大です$500 \times 500$、つまり約 250,000 個のセルです。 送信数とクエリ数は両方とも次の数に達する可能性があります$2 \times 10^5$。 これにより、クエリごとに送信をスキャンしたり、クエリごとにセルごとに再計算したりするソリューションは即座に除外されます。 この構造は、すべての送信情報を静的な 2D 配列に圧縮し、高速な部分行列合計クエリをサポートする必要があることを強く示唆しています。 

微妙な点は「AC前のみ」という条件です。 単純な間違いは、AC 以外の提出物をすべてグローバルにカウントし、後で AC 後の提出物を減算しようとすることです。 AC 後の送信はセルにまったく影響を与えてはいけないため、これは失敗しますが、それでも入力ストリームに表示され、セルごとに慎重にフィルタリングしないとカウントが誤って増大する可能性があります。 

セルが AC をまったく受信しない場合、別のエッジ ケースが発生します。 その場合、たとえ多くの WA または TLE エントリがあっても、その送信はまったくカウントされません。 最終的に AC に達するセルのみが何らかの寄与をします。 

## アプローチ

 直接的なアプローチは、各クエリを個別にシミュレートすることです。 特定の四角形について、すべての送信を反復処理して、それらが四角形内のセルに属しており、そのセルの最初の AC より前に発生したかどうかを確認できます。 これには、最大でスキャンする必要があります。$2 \times 10^5$クエリごとの送信数が増加し、最悪の場合の複雑さが発生します。$4 \times 10^{10}$実行可能な限界をはるかに超えた操作。 

重要な観察は、各セルが他のセルから独立して動作するということです。 提出物はそれ自体にのみ影響します$(c, p)$そして、そのセルに属する有効な誤った送信の数を決定すると、それは再び変更されることはありません。 これは、動的プロセス全体を、グリッド セルごとに 1 つの整数を計算することに縮小できることを意味します。 

各セルに固定値が設定されると、問題は古典的な 2D 範囲合計クエリの問題になります。 2D プレフィックス合計により、一定時間内に各クエリに答えることができます。 

残っている唯一のタスクは、すべてのセルについて、最初の AC までに何回の送信が間違っているかを計算することです。 送信ログを順番に処理して、セルごとにすでに AC を検出したかどうかを維持し、そうでない場合は、非 AC 判定が表示されるたびにカウンターをインクリメントします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとのブルート フォース |$O(S \cdot Q)$|$O(1)$| 遅すぎる |
 | セルごとの累積 + 2D プレフィックスの合計 |$O(S + NM + Q)$|$O(NM)$| 承認済み |

 ## アルゴリズムのチュートリアル

 グリッドを、各エントリが有効な間違った送信のカウンターを保存するテーブルとして扱います。 

1. 2 つ作成します$N \times M$配列: セルがすでに AC を受信したかどうかをマークする 1 つのブール配列と、AC の前に誤った送信をカウントするための 1 つの整数配列。 この分離が必要なのは、AC の後にそのセルの状態を凍結する必要があるためです。 
2. 時系列順に提出を処理します。 提出物ごとに$(c, p, v)$, まず、このセルに既に AC があるかどうかを確認します。 含まれている場合は、AC 以降は定義上無関係であるため、送信を完全にスキップしてください。 
3. 判定が AC で、セルがまだマークされていない場合は、解決済みとしてマークします。 この瞬間以降、今後の送信はこのセルに影響を与えなくなります。 
4. 判定が AC でなく、セルがまだ解決されていない場合は、そのカウンタをインクリメントします。 これにより、最初の送信が成功する前に発生したミスのみがカウントされるようになります。 
5. すべての送信を処理した後、カウンター グリッド上で 2D プレフィックス合計を構築します。 各プレフィックス セルには、長方形内のすべての値の合計が格納されます。$(1,1)$に$(i,j)$。 
6. 各クエリ四角形について、プレフィックス グリッドの包含/除外を使用して一定時間で合計を計算します。 

### なぜ効果があるのか

 送信は自身の座標のみを変更するため、各セルは独立しています。 セルが AC を受信した瞬間に、その最終的な寄与が完全に決定され、その後のイベントによってそれが変更されることはありません。 したがって、問題はセルごとの固定値の計算に分解されます。 プレフィックス合計変換では、部分四角形全体にわたる正確な合計が保存されるため、送信ログを再度確認することなく、事前に計算された情報のみを使用してすべてのクエリに回答されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    N, M = map(int, input().split())
    S = int(input())

    solved = [[False] * (M + 1) for _ in range(N + 1)]
    bad = [[0] * (M + 1) for _ in range(N + 1)]

    for _ in range(S):
        c, p, v = input().split()
        c = int(c)
        p = int(p)

        if solved[c][p]:
            continue

        if v == "AC":
            solved[c][p] = True
        else:
            bad[c][p] += 1

    pref = [[0] * (M + 1) for _ in range(N + 1)]

    for i in range(1, N + 1):
        row_sum = 0
        for j in range(1, M + 1):
            row_sum += bad[i][j]
            pref[i][j] = pref[i - 1][j] + row_sum

    Q = int(input())
    out = []

    for _ in range(Q):
        c1, p1, c2, p2 = map(int, input().split())

        res = pref[c2][p2]
        if c1 > 1:
            res -= pref[c1 - 1][p2]
        if p1 > 1:
            res -= pref[c2][p1 - 1]
        if c1 > 1 and p1 > 1:
            res += pref[c1 - 1][p1 - 1]

        out.append(str(res))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```コア実装はセルごとのステート マシンを維持します。 の`solved`テーブルは、AC に達すると、それ以降の送信は無視されることを保証します。 の`bad`テーブルには、AC 前の有効な誤った試行のみが蓄積されます。 

ネストされた再計算を避けるために、プレフィックス合計の構築は行ごとに行われます。 クエリ応答では、部分行列に対して標準の包含/除外式が使用され、事前に計算されたプレフィックス テーブルに完全に依存します。 

## 実用的な例

 ### 例 1

 2 人の出場者と 2 つの問題がある小さなシステムを考えてみましょう。 送信を処理し、最終的に AC の前に有効な間違った送信のセルごとの数が次のようになったとします。 

| セル | 悪いカウント |
 | --- | --- |
 | (1,1) | 0 |
 | (1,2) | 1 |
 | (2,1) | 3 |
 | (2,2) | 0 |

 次に、プレフィックスの合計を構築します。 

| i\j | 1 | 2 |
 | --- | --- | --- |
 | 1 | 0 | 1 |
 | 2 | 3 | 4 |

 グリッド全体をカバーするクエリの場合、4 が返されます。これは、(2,1) では 3 回のみ、(1,2) では 1 回の誤った送信が発生したという事実と一致します。 

### 例 2

 セルに複数の誤った送信があるが AC を受信しない場合 ((1,1) に 10 WA があるが AC がない場合など)、その寄与は 0 のままです。プレフィックス グリッドはそれを完全に無視します。 

(1,1) を含む領域に対するクエリにはこれら 10 回の試行は含まれず、最終的に AC を持つセルのみが寄与することが確認されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(S + NM + Q)$| 送信に 1 回のパス、プレフィックス合計のグリッドに 1 回のパス、クエリごとの一定時間 |
 | スペース |$O(NM)$| 状態とプレフィックスの合計を格納する 2 つのグリッド |

 境界$N, M \le 500$を作る$NM$ストレージは簡単ですが、$S, Q \le 2 \times 10^5$送信とクエリの線形時間処理のみが受け入れられるようにします。 このソリューションは制限内に問題なく適合します。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from sys import stdout
    import sys

    input = sys.stdin.readline

    N, M = map(int, input().split())
    S = int(input())

    solved = [[False] * (M + 1) for _ in range(N + 1)]
    bad = [[0] * (M + 1) for _ in range(N + 1)]

    for _ in range(S):
        c, p, v = input().split()
        c = int(c)
        p = int(p)
        if solved[c][p]:
            continue
        if v == "AC":
            solved[c][p] = True
        else:
            bad[c][p] += 1

    pref = [[0] * (M + 1) for _ in range(N + 1)]
    for i in range(1, N + 1):
        for j in range(1, M + 1):
            pref[i][j] = pref[i-1][j] + pref[i][j-1] - pref[i-1][j-1] + bad[i][j]

    Q = int(input())
    out = []
    for _ in range(Q):
        c1, p1, c2, p2 = map(int, input().split())
        res = pref[c2][p2] - pref[c1-1][p2] - pref[c2][p1-1] + pref[c1-1][p1-1]
        out.append(str(res))
    return "\n".join(out)

 ## 特殊なケース

 よくある落とし穴は、AC のタイミングに関係なく、間違った送信をすべてカウントしてしまうことです。 例えば：```
1 1
3
1 1 WA
1 1 AC
1 1 WA
1
1 1 1 1
```ここでの正解は 2 ではなく 1 です。AC がすでに発生しているため、3 番目の送信は無視する必要があります。 アルゴリズムは、セルを解決済みとしてマークし、その後のすべての更新をスキップすることでこれを処理します。 

もう 1 つのエッジ ケースは、AC がまったく得られないセルです。```
1 1
2
1 1 WA
1 1 TLE
1
1 1 1 1
```正しい出力は 0 です。`solved`フラグは決して設定されませんが、AC がないため、ルールはこれらの送信をまったくカウントすべきではないと明示的に示しています。 実装では、インクリメントするだけでこれが強制されます。`bad`AC の前に、AC が発生しない限り、最終合計に加算することはありません。
