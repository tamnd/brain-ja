 ## 解決策
 ## 問題の理解

 スペースを含まない小文字の文字列が与えられます。 タスクは、この文字列を正確に分割することです。`k`連続した作品。 すべてのピースは次の間の長さを持たなければなりません`a`そして`b`、包括的。 

文字の順序は変更できません。 弦をどこで切るかを決めるだけです。 

入力が次のとおりであるとします。```
k = 3
a = 2
b = 5
s = "abrakadabra"
```有効な分割の 1 つは次のとおりです。```
ab
rakad
abra
```長さは`2`、`5`、 そして`4`、すべて許容範囲内です。 

制約は小さいです。 文字列の長さは最大でも`200`、 そして`k`、`a`、 そして`b`もせいぜい`200`。 これは、二次または三次動的計画法の解法であっても完全に安全であることをすぐに示します。 カットを配置する方法の数は指数関数的に増加するため、考えられるすべてのパーティションを総当たりで検索することは依然として危険です。 たとえば、長さの文字列であっても、`200`膨大な数の可能なセグメンテーションがあります。 

重要な観察点は、文字列のプレフィックスがいくつかの有効な部分に分割できるかどうかのみを考慮しているということです。 その構造は自然に動的プログラミングにつながります。 

不正な実装をサイレントに破壊する可能性のあるエッジケースがいくつかあります。 

よくある間違いの 1 つは、文字列全体を使用する必要があることを忘れることです。 考慮する：```
2 2 3
abcde
```文字列の長さは`5`。 有効な分割が存在します。```
ab
cde
```不用意に貪欲なアプローチを行うと、可能な限り最大の最初のセグメントが必要になる可能性があります`"abc"`そして失敗します。`"de"`長さがある`2`、これは実際にはまだ機能しますが、剰余が短すぎる場合、同様の入力が失敗する可能性があります。 

もう 1 つの注意が必要なケースは、全長を分配することが不可能なために解決策が存在しない場合です。```
3 2 2
abcde
```正確に 3 つの長さのセグメントが必要です`2`、したがって、必要な合計の長さは次のようになります。`6`ですが、文字列の長さは`5`。 正しい出力は次のとおりです。```
No solution
```グローバル合計を検証せずにローカル セグメントの長さだけをチェックする実装では、部分的な結果が誤って出力される可能性があります。 

3 番目の微妙なケースが現れるのは、`a = b`。 その後、すべてのセグメントの長さが固定されます。```
2 3 3
abcdef
```唯一の有効な答えは次のとおりです。```
abc
def
```これは、柔軟な分割ではなく、正確な分割に似た動作をします。 

## アプローチ

 ブルートフォースアプローチでは、あらゆる可能な方法で配置を試みます。`k - 1`弦の内側をカットします。 各パーティションについて、すべてのセグメントの長さが次の範囲内にあるかどうかを確認します。`a`そして`b`。 

これが機能するのは、すべての有効な回答がカットの配置に対応しているためです。 問題は可能性の数です。 長さの文字列`n`もっている`n - 1`可能なカット位置を選択しています`k - 1`彼らのうち。 パーティションの数は組み合わせになります。$$\binom{n-1}{k-1}$$と`n = 200`、これはまったく不可能です。 

重要な構造上の観察は、分割の有効性はプレフィックスのみに依存するということです。 最初かどうかがすでにわかっている場合は、`i`文字は次のように分けることができます`j`有効なセグメントがある場合は、その状態をもう 1 つのセグメントで拡張してみることができます。 

これにより、動的プログラミングへの移行が自然に形成されます。 

定義する：$$dp[i][j]$$最初かどうかのように`i`文字を正確に分割できる`j`有効な部分。 

州から`(i, j)`、次のセグメントの長さを取得してみます`len`間`a`そして`b`。 もし`i + len`文字列の長さを超えない場合、次のようになります。$$dp[i + len][j + 1] = True$$これにより、問題は指数関数的な探索から小さな多項式時間 DP に軽減されます。 すべての制限が最大なので、`200`、単純な実装でも十分高速です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(k) | 遅すぎる |
 | 最適なDP | O(n × k × (b - a + 1)) | O(n × k) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 値を読み取る`k`、`a`、`b`そして文字列`s`。 
2. しましょう`n`文字列の長さになります。 
3. DP テーブルを作成します。`dp[i][j]`最初かどうかを教えてくれます`i`文字を正確に分割できる`j`有効なセグメント。 
4.初期化`dp[0][0] = True`。 

これは、空のプレフィックスがゼロ部分に分割される可能性があることを意味します。 
5. ポジションごとに`i`から`0`に`n`:

 セグメント数ごとに`j`から`0`に`k - 1`：

もし`dp[i][j]`true の場合、すべてのセグメント長を試してください`len`から`a`に`b`。 
6. もし`i + len <= n`そうすると、現在のパーティションを 1 つの有効なセグメントだけ拡張できます。 

マーク：$$dp[i + len][j + 1] = True$$7. 答えを再構築するには、遷移が成功するたびに前の状態を保存します。 

たとえば、次のように保存します。```
parent[next_i][next_j] = (i, j)
```8. 表に記入したら、チェックを入れます。`dp[n][k]`。 

falseの場合は出力します`"No solution"`。 
9. それ以外の場合は、親ポインタを使用してバックトラックします。 

から始まる`(n, k)`、前の状態を繰り返し復元し、対応する部分文字列を抽出します。 
10. 再構築は逆方向に行われるため、収集されたセグメントを逆にします。 
11. セグメントを 1 行ずつ印刷します。 

### なぜ効果があるのか

 DP の不変式は次のとおりです。`dp[i][j]`最初の場合にのみ true です`i`文字を正確に分割できる`j`有効なセグメント。 

空の文字列にはセグメントが必要ないため、基本ケースは正しいです。 

間の長さのセグメントのみを追加するため、各トランジションは正確さを維持します。`a`そして`b`。 到達可能なすべての状態は、プレフィックスの有効なパーティションに対応します。 

保存されたすべての親ポインターが DP 状態の構築に使用される実際の遷移を記録するため、再構成は有効です。 

到達可能なすべての状態から、考えられるすべての有効なセグメント長が探索されるため、有効な解決策が見逃されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    k, a, b = map(int, input().split())
    s = input().strip()

    n = len(s)

    dp = [[False] * (k + 1) for _ in range(n + 1)]
    parent = [[None] * (k + 1) for _ in range(n + 1)]

    dp[0][0] = True

    for i in range(n + 1):
        for j in range(k):
            if not dp[i][j]:
                continue

            for length in range(a, b + 1):
                ni = i + length

                if ni > n:
                    continue

                if not dp[ni][j + 1]:
                    dp[ni][j + 1] = True
                    parent[ni][j + 1] = (i, j)

    if not dp[n][k]:
        print("No solution")
        return

    parts = []

    cur_i = n
    cur_j = k

    while cur_j > 0:
        prev_i, prev_j = parent[cur_i][cur_j]

        parts.append(s[prev_i:cur_i])

        cur_i = prev_i
        cur_j = prev_j

    parts.reverse()

    print("\n".join(parts))

solve()
```この解決策は、ブール値 DP テーブルを作成することから始まります。 寸法は`(n + 1) × (k + 1)`なぜなら、考えられるすべてのプレフィックス長と、構築されたセグメントのすべての数を追跡しているからです。 

ネストされたループは、到達可能なすべての状態を反復します。 いつでも`dp[i][j]`が true の場合、長さが間にある別のセグメントを追加しようとします。`a`そして`b`。 

行:```
ni = i + length
```次のセグメントを取得した後、新しいプレフィックス サイズを計算します。 

条件:```
if ni > n:
```文字列の末尾を越える文字にアクセスできないようにします。 この境界チェックは必須です。そうしないと、最後のセグメントが文字列からオーバーフローする可能性があるからです。 

親テーブルには、最初に状態に到達可能になったときのみ、再構成情報が格納されます。 有効な再構築はどれでも受け入れられるため、以前の親を上書きする必要はありません。 

再構築中、部分文字列は次のようになります。```
s[prev_i:cur_i]
```は、まさに、からの移行中に追加されたセグメントです。`(prev_i, prev_j)`に`(cur_i, cur_j)`。 

バックトラックは完全な文字列から開始され、空のプレフィックスに向かって逆方向に進むため、収集されたセグメントは逆の順序で表示されます。 リストを逆にすると、正しい順序が復元されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n × k × (b - a + 1)) | すべての DP 状態はすべてのセグメント長を試行します。 
| スペース | O(n × k) | DP テーブルと親テーブル |

 すべての値が最大であるため、`200`、トランジションの最大数はおおよそ次のとおりです。$$200 \times 200 \times 200 = 8 \times 10^6$$これは Python の制限時間内に簡単に収まります。

 ## 特殊なケース

 全長が不可能な場合を考えてみましょう。```
3 2 2
abcde
```すべてのセグメントは正確な長さでなければなりません`2`、したがって 3 つのセグメントには長さが必要です`6`。 DP が各州に到達`(2,1)`そして`(4,2)`ですが、別のセグメントを追加すると文字列の長さを超えるため、これ以上拡張することはできません。 以来`dp[5][3]`false のままの場合、アルゴリズムは正しく出力します。```
No solution
```次に、固定長のシナリオを考えてみましょう。```
2 3 3
abcdef
```許可される唯一のセグメント サイズは、`3`。 遷移は決定的になります。```
(0,0) -> (3,1) -> (6,2)
```再構成された答えは次のとおりです。```
abc
def
```セグメント長にわたる内部ループには値が 1 つだけ含まれるため、アルゴリズムはこれを自然に処理します。 

最後に、貪欲な選択が失敗する可能性があるケースを考えてみましょう。```
2 2 4
abcdefg
```貪欲に最大の最初のセグメントを取ると`"abcd"`長さの`4`、残り`"efg"`長さがある`3`、まだ機能します。 しかし、同様の入力に対して、貪欲な決定が私たちを罠にはめる可能性があります。 

DP は、到達可能なすべての状態からすべての有効なセグメント長を探索するため、この問題を完全に回避します。 有効なパーティションが存在する場合、一部の DP パスが到達します。`(n,k)`。
