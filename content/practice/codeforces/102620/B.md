 ## 解決策
 ## 問題の理解

 この問題は、座標グリッド上に部分的に書かれたルートをすでにたどっているオウムについて説明しています。 ルートは、右、左、上、下の 4 つの移動コマンドで構成されます。 既存のコマンドを実行した後、オウムは特定の位置にいます。 目標は、オウムが指定された目的地に到達するために、ルートの最後に追加する必要がある追加コマンドの最小数を見つけることです。 

入力により、現在のルート、その長さ、およびオウムが到達する必要がある最終座標が得られます。 出力されるのは、実際の一連の動きではなく、必要な追加の動きの数だけです。 

制約により、意図したアイデアが検索問題よりもはるかに単純になります。 ルートの長さが最大でも数百文字の場合、移動を直接シミュレートするのにかかる時間は直線的なものだけです。 たとえルートの長さがはるかに長かったとしても、すべてのコマンドが最終位置に独立して影響を与えるため、単一パスが依然として正しいアプローチとなります。 オウムは指定された接頭辞の後に任意のコマンドを選択できるため、可能なパスを探索したり、方向転換をシミュレートしたりするソリューションは不要です。 

主なエッジケースは、最終位置を正しく処理することで発生します。 不用意に実装すると、ターゲットが常に右上にあると想定し、残りの距離を左または下に移動する必要があることを忘れてしまう可能性があります。 たとえば、次の入力を使用します。```
1
R
0 0
```オウムは次で終わります`(1, 0)`。 正しい出力は次のとおりです。```
1
```左一手で十分だからです。 正の座標差を加算するだけの実装では、誤ってゼロが生成されます。 

もう 1 つのケースは、現在のルートがすでに目的地に到着している場合です。 例えば：```
2
RU
1 1
```正しい出力は次のとおりです。```
0
```追加のコマンドが必要ないためです。 常に少なくとも 1 つの手を追加するコードは、ここでは失敗します。 

3 番目のよくある間違いは、現在位置と目的地の座標を混同することです。 のために：```
3
DDD
0 -5
```現在の位置は`(0, -3)`, したがって、残りの距離は下に2手移動します。 正しい出力は次のとおりです。```
2
```ターゲットの座標をルートの長さと直接比較したり、シミュレートされた位置を無視したりするソリューションでは、これを正しく処理できません。 

## アプローチ

 簡単なアプローチは、追加される可能性のあるすべてのコマンド シーケンスを考慮して問題を解決しようとすることです。 新しい動きはそれぞれ 4 つの方向のいずれかになる可能性があるため、深さの総当たり検索が行われます。`k`調べるだろう`4^k`～の可能性`k`コマンドを追加しました。 これは、考えられるすべてのルート拡張をチェックするため正しいですが、指数関数的に増加し、すぐに不可能になります。 

グリッドには便利な特性があるため、強引な方法は不要です。つまり、最終位置のみを考慮する場合、移動の順序は重要ではありません。 既存のコマンドは、オウムが目的地からどのくらい離れているかを判断するだけです。 水平方向と垂直方向の違いがわかれば、最短経路が強制されます。 すべての水平方向の違いには 1 回の水平方向の移動が必要であり、すべての垂直方向の違いには 1 回の垂直方向の移動が必要です。 

2 つのグリッド点間のマンハッタン距離によって、軸に沿った移動の最小数が得られるという観察により、問題全体が 1 つのシミュレーション パスとそれに続く単純な計算に軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(4^k) | O(k) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 既存のルートを読み取り、原点からシミュレートします。 右に移動するたびに X 座標が増加し、左に移動するたびに減少し、上に移動するたびに Y 座標が増加し、下に移動するたびに減少します。 これにより、ルートの既知の部分の後の正確な位置が得られます。 
2. 目的地と現在の x 座標の間の水平方向の差を計算します。 目的地と現在の y 座標の間の垂直方向の差を計算します。 これらの値は、オウムが各方向にどのくらいの距離を移動する必要があるかを表します。 
3. 2 つの差の絶対値を加算します。 各移動は正確に 1 つの座標を 1 単位ずつ変更できるため、結果として余分な移動の数が最小限になります。 

これが機能する理由: 不変条件は、指定されたルートのプレフィックスを処理した後、保存された座標がそのプレフィックス以降のオウムの実際の位置と正確に一致することです。 ルート全体が処理されると、目的地までの残りの変位がわかります。 有効な継続は、水平および垂直の差のすべての単位を修正する必要があり、少なくとも`abs(dx) + abs(dy)`動く。 これらの差に沿って直接移動すると、正確にその数の移動が達成されるため、値は下限であり、達成可能です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    s = input().strip()
    x, y = map(int, input().split())

    cx = 0
    cy = 0

    for c in s:
        if c == 'R':
            cx += 1
        elif c == 'L':
            cx -= 1
        elif c == 'U':
            cy += 1
        elif c == 'D':
            cy -= 1

    print(abs(x - cx) + abs(y - cy))

if __name__ == "__main__":
    solve()
```コードの最初の部分は、ルート情報を読み取り、原点におけるオウムの位置を初期化します。 シミュレーション ループは、アルゴリズムのウォークスルーで説明したのと同じ遷移に従うため、座標は常に、処理されたプレフィックスの後の実際の位置を表します。 

オウムはどちらかの方向に位置を修正する必要があるため、最終的な式では絶対的な差分が使用されます。 コマンドの最小数のみが要求されるため、コマンド自体を構築する必要はありません。 

この実装では、配列や追加のデータ構造は使用されません。 また、ルートを一度スキャンすることで、不要な文字列操作を回避します。 Python の整数には、これらの座標計算におけるオーバーフローの問題はありません。

6

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |

 このアルゴリズムは、移動コマンドごとに一定量の作業を実行するため、非常に大規模なルートであっても、一般的な競技プログラミングの制限内に簡単に収まります。 

## テストケース```python
import sys
import io

def solve_data(inp: str) -> str:
    old_stdin = sys.stdin
    sys.stdin = io.StringIO(inp)

    import sys
    input = sys.stdin.readline

    n = int(input())
    s = input().strip()
    x, y = map(int, input().split())

    cx = 0
    cy = 0

    for c in s:
        if c == 'R':
            cx += 1
        elif c == 'L':
            cx -= 1
        elif c == 'U':
            cy += 1
        else:
            cy -= 1

    ans = abs(x - cx) + abs(y - cy)

    sys.stdin = old_stdin
    return str(ans)

assert solve_data("6\nUUDLRR\n5 3\n") == "6", "sample 1"
assert solve_data("3\nDDD\n0 -5\n") == "2", "sample 2"

assert solve_data("1\nR\n0 0\n") == "1", "opposite horizontal direction"
assert solve_data("2\nRU\n1 1\n") == "0", "already at destination"
assert solve_data("5\nLLLLL\n3 2\n") == "8", "large correction after negative movement"
assert solve_data("4\nUUUU\n0 100\n") == "96", "vertical boundary movement"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1\nR\n0 0`|`1`| ハンドルが反対方向に戻ります。 |
 |`2\nRU\n1 1`|`0`| 追加の移動が必要ない場合に対処します。 |
 |`5\nLLLLL\n3 2`|`8`| 負の電流座標をチェックします。 |
 |`4\nUUUU\n0 100`|`96`| 大きな残距離を確認します。 |

 ## 特殊なケース

 目的地が現在のルートとは反対方向に移動する必要がある場合、アルゴリズムは方向を想定しないため機能します。 で：```
1
R
0 0
```シミュレーションが与える`(1, 0)`。 違いは次のとおりです。`-1`水平方向と`0`垂直にすると、答えは次のようになります`abs(-1) + abs(0) = 1`。 

ルートがすでに目標に到達している場合、残りの変位は`(0, 0)`。 のために：```
2
RU
1 1
```シミュレーションは次で終了します`(1, 1)`、答えを作る`0`。 アルゴリズムは不必要な動きを追加しません。 

負の座標を作成するパスの場合でも、シミュレーションは同じルールに従います。 で：```
3
DDD
0 -5
```オウムが届く`(0, -3)`。 残りの垂直距離は`-2`、絶対値から正しい答えが得られます。`2`。 座標の符号は方向のみを決定し、必要な移動数は決定しません。
