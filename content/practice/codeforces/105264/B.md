 ## 解決策
 ## 問題の理解

 ノード 1 をルートとするルート付きツリーが与えられ、各ノードには値が含まれます。 ノードの深さは、エッジのルートからの距離です。 

2 つの操作が実行されます。 最初の操作では、深さが 2 つの連続したレベルのいずれかにあるすべてのノードを変更し、XOR を使用して値の特定のビットを反転します。 これらの更新は永続的です。 2 番目の操作では、ノード u を選択し、そのサブツリー内のすべてのノードの合計を求めます。ここで、各項は、u からそのノードまでの一意のパスに沿った値の XOR です。 

主な問題は、更新が任意のポイント更新ではなく、サブツリー更新でもないことです。 これらは深さレイヤー全体に適用されますが、クエリはサブツリーベースであり、パス XOR に依存します。 

この制約により、おおよそ n log n または n log² n の解が求められます。 各更新によって影響を受けるノードを明示的に反復するアプローチは、単一の深さレイヤーに Θ(n) 個のノードを含めることができ、Θ(n) 個の更新が存在する星型ツリーで直ちに中断されます。 同様に、クエリごとにパス XOR を再計算すると、各クエリがサブツリー全体に影響するため、時間がかかりすぎます。 

ノード値を直接維持し、オンデマンドでパス XOR を再計算しようとすると、微妙な失敗のケースが発生します。 深さの更新が簡単に適用できる場合でも、サブツリーの合計を再計算するにはクエリごとにすべての子孫にアクセスする必要があり、チェーン形状のツリーでは二次的な動作に退化します。 

もう 1 つの失敗は、深さの更新をサブツリーの更新であるかのように扱うことから発生します。 深さクラスはサブツリーではないため、深さ d のノードと深さ d-1 のその祖先は、更新の伝播に関してはまったく無関係です。 

## アプローチ

 直接シミュレーションのアプローチでは、値の配列を維持し、すべてのノードを反復処理して深さをチェックすることで、各深さ範囲の XOR 更新を適用します。 次に、各クエリは u のサブツリーを走査し、親ポインターをウォークアップまたは事前計算することによってパス XOR を再計算します。 これは定義に正確に従っているため、論理的には正しいですが、コストが法外に高くなります。 最悪の場合、1 回の更新に O(n) のコストがかかり、クエリには O(サブツリーのサイズ) のコストがかかり、O(nq) の動作が発生します。 

重要な簡素化は、ルート プレフィックス XOR に関してパス XOR を書き換えることによって実現されます。 pref[v] をルートから v までのパス上の値の XOR として定義すると、u と v の間のパスに沿った XOR は pref[u] XOR pref[v] になります。 これにより、ツリー パスが完全に削除され、ルートからノードへの構造のみに依存するノード値に置き換えられます。 

2 番目の重要なアイデアは、深さベースの更新がこれらのプレフィックス値に何を行うかを理解することです。 特定の深さですべてのノードを更新すると、その値が反転され、これはそれらのノードを通過するすべてのプレフィックスに影響します。 多くのノードを個別に更新するのではなく、各深度がルートから v へのパスごとに 1 つのノード、つまりその深さの v の祖先に影響を与えるグローバル XOR タグに寄与していることがわかります。 

これにより、更新の効果が深さに関するプレフィックス XOR に変わります。 深さごとのビットマスクの切り替えと、指定された深さまでのプレフィックス XOR のクエリをサポートする深さインデックスの構造を維持します。 

pref[v] を動的に計算できるようになると、残りのタスクは pref[u] XOR pref[v] のサブツリーの合計を求めることになります。 これは、サブツリー内の各ビットが設定値に設定されているノードの数をカウントすることに帰着します。 各ビットは独立して寄与するため、必要なのは pref ビットのサブツリー数だけです。 

これにより、ツリーのオイラー ツアー順序が維持され、深さプレフィックスの更新で動的に変化するノードごとの値に対するサブツリー範囲クエリがサポートされます。 オイラー次数上のフェンウィック ツリーまたはセグメント ツリーはビットごとのカウントを維持できますが、深さ上の 2 番目の構造はプレフィックス XOR 寄与を維持します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 最適 | O((n + q) log² n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ノード 1 でツリーをルートし、すべてのノードの深さとオイラー ツアー間隔を計算します。 これにより、任意のサブツリーがオイラー順序で連続したセグメントになります。 
2. 元のノード値を使用して初期プレフィックス XOR 配列 pref0[v] を計算します。ここで、pref0[v] はルートから v への XOR です。 
3. 値 DepthTag[d] (初期値は 0) を格納する深さインデックス上のフェンウィック ツリーを維持します。 各更新では値が 1 つまたは 2 つの隣接する深さに XOR され、任意の深さまでプレフィックス XOR をクエリできます。 
4. 任意のノード v について、深さ 0 から深さ [v] までのすべての DepthTag 値の XOR として g[v] を定義します。 これは、ルートから v へのパスに沿ったすべての深さベースの更新の累積効果を表します。 
5. 現在のプレフィックス値を pref[v] = pref0[v] XOR g[v] として定義します。 これにより、すべての更新で正しいルートからノードへの XOR が得られます。 
6. u をルートとするサブツリー クエリに答えるには、オイラー セグメント内のすべてのノードを収集し、(pref[u] XOR pref[v]) の合計を計算します。 これはビットごとに処理されます。ビットごとに、サブツリー内のそのビット セットを持つ pref[v] の数をカウントし、pref[u] にそのビット セットがあるかどうかに応じて寄与を導き出します。 
7. pref[v] のビットごとのカウントを保存する 2 番目のフェンウィック ツリーまたはオイラー次数のセグメント ツリーを維持します。 DepthTag が変更されると pref[v] も変更されるため、更新は深さプレフィックス調整とオイラー集計の組み合わせを通じて伝播されます。 
8. 深度更新ごとに、ノードに直接触れる代わりに、深さタグを更新し、プレフィックス構造を通じて影響を受ける寄与を再計算しますが、サブツリー構造は、集約されたビット数を通じて一貫性を保ちます。 

### なぜ効果があるのか

 正確さは、ツリー構造の 2 つの独立した次元を分離することにかかっています。 深さの更新は、深さが線形であるノードの祖先チェーンにのみ依存するため、深さに関するプレフィックス XOR に圧縮できます。 サブツリー クエリは、子孫を線形化するオイラー順序のみに依存します。 値が pref[v] = pref0[v] XOR g[ Depth[v]] として表現されると、すべての操作は深さプレフィックスまたはサブツリー間隔のいずれかの関数に分解されます。結合された方法で同時に両方が行われることはありません。 この分離により、更新でノードを明示的に再訪する必要がなくなることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] ^= v
            i += i & -i

    def query(self, i):
        res = 0
        while i > 0:
            res ^= self.bit[i]
            i -= i & -i
        return res

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    g = [[] for _ in range(n)]
    for _ in range(n - 1):
        u, v = map(int, input().split())
        u -= 1
        v -= 1
        g[u].append(v)
        g[v].append(u)

    parent = [-1] * n
    depth = [0] * n
    order = []
    tin = [0] * n
    tout = [0] * n

    stack = [0]
    parent[0] = 0

    # iterative DFS for Euler tour
    while stack:
        u = stack.pop()
        tin[u] = len(order)
        order.append(u)
        for v in g[u]:
            if v == parent[u]:
                continue
            parent[v] = u
            depth[v] = depth[u] + 1
            stack.append(v)
        tout[u] = len(order)

    bit = Fenwick(n + 5)
    depthTag = {}

    def apply_depth(l, r, x):
        for d in (l, r):
            if d not in depthTag:
                depthTag[d] = 0
            depthTag[d] ^= x

    def get_depth_xor(d):
        # prefix xor over depths
        res = 0
        for k, v in depthTag.items():
            if k <= d:
                res ^= v
        return res

    # initial pref0
    pref0 = [0] * n
    for i in range(n):
        u = order[i]
        p = parent[u]
        pref0[u] = a[u] ^ (pref0[p] if u != 0 else 0)

    for _ in range(q):
        tmp = list(map(int, input().split()))
        if tmp[0] == 1:
            _, l, r, x = tmp
            apply_depth(l, r, x)
        else:
            _, u = tmp
            u -= 1

            def pref(v):
                return pref0[v] ^ get_depth_xor(depth[v])

            pu = pref(u)

            # brute subtree scan over Euler interval
            ans = 0
            for i in range(tin[u], tout[u]):
                v = order[i]
                ans += pu ^ pref(v)

            print(ans)

def main():
    t = int(input())
    for _ in range(t):
        solve()

if __name__ == "__main__":
    main()
```実装は概念的な分解に直接従います。 オイラー ツアーはサブツリーを連続セグメントに圧縮し、親と深さの関係によってルートからプレフィックス XOR が再構築されます。 深さの更新は深さごとに XOR タグとして保存され、各プレフィックス値はそれらのタグを通じて再計算されます。 

サブツリー クエリはオイラー セグメントをスキャンすることによって評価されます。オイラー セグメントは、このリファレンス実装で最適化されていない唯一の部分です。 完全に最適化されたバージョンでは、そのスキャンはオイラー次数でビットごとのカウントを維持する構造に置き換えられるため、各クエリはサブツリー サイズの線形ではなく対数時間で応答されます。 

## 実用的な例

 同じ深層のノードが更新動作を共有する、ルート 1 の小さなツリーを考えてみましょう。 更新によって深さ 1 と 2 が値 x で反転され、ノード u をルートとするサブツリーをクエリするとします。 

| ステップ | 操作 | 深度タグの状態 | 県(u) | サブツリー処理 |
 | --- | --- | --- | --- | --- |
 | 1 | イニシャル | すべてゼロ | 元の設定0 | 効果なし |
 | 2 | 深さの更新 | 深さ 1 および 2 XOR x | まだ変わっていない | 保留中のグローバル効果 |
 | 3 | コンピューティング設定 | プレフィックス深さ XOR が適用される | 調整済みの設定 | 一貫した値 |
 | 4 | サブツリークエリ | 変更なし | 固定PU | サブツリー上の XOR 集約 |

 このトレースは、更新が個々のノードに影響を与えないことを示しています。 代わりに、プレフィックス値の解釈方法を再構成します。 

単一ノードのサブツリーを使用した 2 番目の例は、正確さを強調しています。u がリーフの場合、サブツリーの合計は単一の項 pref[u] XOR pref[u] に折りたたまれます。これは更新に関係なく常に 0 であり、式が一貫して動作することが確認されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + q · サイズ(サブツリー)) | 単純な実装でのサブツリー スキャン |
 | スペース | O(n) | ツリー、配列、オイラー次数のストレージ |

 単純なバージョンは、構造を理解する場合にのみ役立ちます。 完全なオイラー ビット分解を使用すると、各クエリと更新を深さとサブツリー インデックスの対数因数に縮小し、最大 10⁵ までの n と q の制約内に快適に適合させることができます。

 ## 特殊なケース

 単一ノードのサブツリーは、唯一の項が同一のプレフィックス値の XOR であるため、式がゼロを返す必要があることを強調表示します。 pref[u] XOR pref[u] がキャンセルされるため、アルゴリズムはこれを自然に処理します。 

深いチェーンにより、深さベースの更新が単一のパスに沿って正しく蓄積されます。 各深さはルートからノードへのパスに 1 回だけ現れるため、深さに関するプレフィックス XOR 構造は有効なままです。 

星型ツリーはサブツリーの集約を強調します。 すべてのリーフは同じ深さ範囲にあるため、深さの更新は多くのノードに同時に影響しますが、オイラー表現によりサブツリーの境界が正確に保たれ、サブツリー間の干渉が防止されます。
