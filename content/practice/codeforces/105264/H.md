 ## 解決策
 ## 問題の理解

 正の整数の配列が与えられます。 要素間で 2 の累乗を再分配する特別な操作を繰り返し実行できます。つまり、値が偶数のインデックスを選択し、それを半分に減らし、同時に別の要素を 2 倍にします。 

言い換えれば、すべての演算は、配列全体の奇数部分と 2 の合計指数に関する合計の積構造を変更することなく、2 の 1 つの因数を 1 つの位置から別の位置に移動します。 奇数のコンポーネントはその要素に付加されたままですが、2 の累乗は位置間で任意にシフトできますが、演算ごとに指数は 1 単位のみです。 

このような一連の操作の後、最終的な配列の少なくとも x 要素が少なくとも x になるように、値 x を最大化する必要があります。 これは、2 のべき乗を最適に再配分した後に適用される標準の「H インデックス スタイル」条件です。 

この制約は、操作を直接シミュレートできないことを意味します。 テスト ケースあたり最大 2·10^5 の要素と最大 10^4 のテスト ケースを使用すると、どのソリューションもテスト ケースあたりほぼ線形または n log n で実行する必要があります。 これにより、転送を繰り返しシミュレートしたり、操作ごとの状態変更を維持したりする戦略は即座に排除されます。 

微妙な特殊なケースは、大きな偶数がいくつかの位置に集中している場合です。 たとえば、1 つの要素が 2 という大きな累乗を持ち、他の要素が奇数で小さい場合、この操作によりその累乗を多くの要素に「分散」することができます。 最大の要素だけを増やす単純な貪欲なやり方は失敗します。最適解は力を集中させるのではなく分散させることが多いためです。 

もう 1 つの特殊なケースは、すべての数値が奇数である場合です。 この場合、演算はまったく不可能になるため、答えは配列の古典的な H インデックスになります。 

## アプローチ

 強引な解釈では、各操作を 2 の個別の累乗の再分配として扱います。 安定した構成に達するまで、偶数の要素を選択し係数を 2 にシフトすることを繰り返し、その後 H インデックスを計算してすべての可能性を試すことができます。 これは、各操作で 2 つの要素が変更され、テスト ケースごとに O (ビットの合計) の操作が存在する可能性があるため、すぐに実行不可能になります。最悪の場合、これは n log A に比例し、依然として膨大な分布の状態空間を探索する必要があります。 

重要な観察は、転送可能なリソースは 2 の累乗のみであるのに対し、奇数部分はベースライン値を決定する固定アンカーであるということです。 各要素は ai = od_i · 2^{cnt_i} と考えることができます。 この操作により、cnt_i から cnt_j に 1 つのユニットが移動します。 したがって、グローバルに、奇数部分のマルチセットは固定され、すべての cnt_i の合計も同様に固定されます。 

これにより、問題は、H インデックス条件を最大化するためにポジション間で固定数の「ダブリング」を分散することに変換されます。 シミュレーションする代わりに、少なくとも x 個の要素が値 ≥ x に達するかどうかだけを考慮します。 固定 x の場合、各要素 i は、odd_i · 2^{cnt_i} ≥ x となるように十分な 2 倍化を必要とします。 これにより、要素ごとに最低限必要な cnt_i が得られ、少なくとも x 要素を満たすために利用可能な 2 倍化を割り当てることができるかどうかを確認する必要があります。 

これは、貪欲な実現可能性チェックに帰着します。つまり、x に到達するために必要な倍加の数によって要素を並べ替え、利用可能なリソースが使い果たされるまで最も簡単なものを選択します。

 ## アルゴリズムのチュートリアル

 各値 ai をその奇数成分とそれに含まれる 2 の因数の数に再定式化します。 ci を ai の 2 の指数とし、oi を ai を 2^{ci} で割ったものとします。 

次に、すべての ci の合計である、利用可能な「電力バジェット」の合計を計算します。 これは、配列全体で要素を何倍にできるかを表します。

候補 x が達成可能かどうかを確認するには、各要素について、oi から開始して少なくとも x に到達するために何回の 2 倍化が必要かを決定します。 oi がすでに ≥ x である場合は、ゼロ倍加が必要です。 それ以外の場合は、oi · 2^k ≥ x となる最小の k を計算します。 

これらの要件をすべて収集し、分類します。 私たちは、可能な限り多くの要素を満たすために利用可能な総予算を貪欲に割り当て、倍増の少ない要素を優先します。 

固定 x の場合、この割り当ての下で少なくとも x 要素を満たすことができれば、x は実現可能です。 

x を 0 から n まで二分探索して答えを求めます。 

### なぜ効果があるのか

 重要な不変条件は、利用可能な 2 倍化の総数が固定され、完全に転送可能である一方、x が固定されると各要素の要件は独立するということです。 2 倍化の各単位は同一の値を持ち、カウントを超える位置制限がないため、最適な戦略は常に最小の要件を最初に満たすことです。 これにより、問題は標準的なリソース割り当ての実行可能性チェックに集約され、操作を再配置しなくても、固定しきい値に対する貪欲な割り当てよりも良い結果が得られることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def count_twos(x):
    c = 0
    while x % 2 == 0:
        x //= 2
        c += 1
    return c, x

def can(x, odd, cnt, total_twos):
    req = []
    for o, c in zip(odd, cnt):
        if o >= x:
            req.append(0)
        else:
            need = 0
            val = o
            while val < x:
                val *= 2
                need += 1
            req.append(need)
    req.sort()
    used = 0
    take = 0
    for r in req:
        if used + r <= total_twos:
            used += r
            take += 1
        else:
            break
    return take >= x

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        odd = []
        cnt = []
        total_twos = 0

        for v in a:
            c, o = count_twos(v)
            odd.append(o)
            cnt.append(c)
            total_twos += c

        lo, hi = 0, n
        ans = 0

        while lo <= hi:
            mid = (lo + hi) // 2
            if can(mid, odd, cnt, total_twos):
                ans = mid
                lo = mid + 1
            else:
                hi = mid - 1

        print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、まず各数値を奇数の底と 2 のべき乗の指数に分解します。 演算を通じて転送できるのは指数部分のみであるため、この分離は不可欠です。 

実現可能性チェック関数は、ターゲット x に到達するために各要素が何回倍加する必要があるかを計算し、利用可能な合計指数予算を貪欲に割り当てます。 ソートのステップは、常に最も安価な要素に最初にリソースを費やすことができるため、重要です。 

二分探索では、この実現可能性チェックをラップして、有効な最大の x を見つけます。 

実装の微妙な詳細は、対数ではなく乗算を繰り返すことで必要な 2 倍を計算することです。 これにより、精度の問題が回避され、値が指数関数的に増加するため、十分な速度が維持されます。 

## 実用的な例

 ### 例 1

 配列を考えてみましょう`[8, 3, 1]`。 

分解します:

 | 要素 | 奇数 | 2 |
 | --- | --- | --- |
 | 8 | 1 | 3 |
 | 3 | 3 | 0 |
 | 1 | 1 | 0 |

 2 の合計 = 3。 

ここで x = 2 をテストします。 

要件:

 | 要素 | 値 | 必要な倍加 |
 | --- | --- | --- |
 | 8 | 8 | 0 |
 | 3 | 3 | 0 |
 | 1 | 1→2 | 1 |

 予算 1 単位のみを使用して 3 つすべてを満たすことができるため、x = 2 が実現可能です。 

x = 3 の場合:

 要件:

 | 要素 | 必要な |
 | --- | --- |
 | 8 | 0 |
 | 3 | 0 |
 | 1 | 2 |

 予算内で満足できる要素は最大 2 つであるため、x = 3 は失敗します。 

したがって、答えは 2 です。 

このトレースは、単一の大きな要素から残った 2 のべき乗をどのように再分配して、より小さな要素を持ち上げるかを示しています。 

### 例 2

 配列`[1, 1, 1, 1]`。 

すべての要素は奇数で、2 の合計 = 0。 

x = 1 の場合、すべてがすでに ≥ 1 であるため、実行可能です。 

x = 2 の場合、それぞれ 1 回の 2 倍化が必要ですが、予算が 0 なので不可能です。 

したがって、答えは 1 です。 

これにより、アルゴリズムが転送なしのエッジ ケースを正しく処理していることが確認されます。

 ## 特殊なケース

 重要なエッジ ケースは、1 つの要素に利用可能な 2 のべき乗がすべて含まれる場合です。 のような入力の場合`[2^k, 1, 1, ..., 1]`、アルゴリズムはこれを大きな予算と多くの小さな要件に正しく変換します。 貪欲なステップにより、この予算が最初に最も安価な要素に費やされ、単一の大きなソースが多くのターゲットに効果的に分散されます。 

もう 1 つのエッジ ケースは、x が n に近い場合です。 実現可能性チェックは、満たせる要素の数を直接カウントするため、引き続き正しく動作し、ソートされた要件が早い段階で予算を超えると、不必要な計算を行わずにループが終了します。 

3 番目のエッジ ケースは、転送を使用しなくても値がすでに十分に大きい場合です。 このような場合、必要な 2 倍化はすべて 0 であり、アルゴリズムはすべての要素を満たしたものとして即座にカウントし、可能な場合には x = n を正確に求めます。
