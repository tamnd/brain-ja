 ## 解決策
 ## 問題の理解

 時間の経過とともに変化するバイナリ文字列が与えられます。 1 つの文字を反転する操作と、部分文字列に対するクエリに応答する操作の 2 種類の操作が発生します。 任意の部分文字列について、形式の隣接するパターンを繰り返し削除することができます。`01`、完全に削除し、任意の順序で何度でも削除した後、最小限の長さが必要になります。 

キー オブジェクトは、「消去」ルールに基づくバイナリ文字列の縮小形式です。`01`各クエリは、現在のバージョンの文字列内の指定された部分文字列のこの短縮形式の最終的な長さを要求します。 

文字列は動的であるため、ポイント フリップによって構造が変化し、最大 200k の操作に効率的に応答する必要があります。 クエリごとにリダクションを最初から再計算するソリューションでは、クエリごとに最大 200,000 文字のスキャンが必要になり、最悪の場合は約 4e10 回の操作が発生し、これは 1 秒をはるかに超えます。 

微妙な問題は、削除が隣接する等しい文字を削除するような局所的な単純化ではないことです。 削除中`01`以前に分離されたリージョン間でキャンセルの新たな機会が生まれる可能性があるため、最終的な結果はローカルの隣接関係だけでなくグローバル構造に依存します。 

よくある失敗例は、キャンセルを注意深く追跡せずに、部分文字列に対する貪欲なシミュレーションまたはスタック シミュレーションから発生します。 たとえば、`0101`、繰り返し削除します`01`は空の文字列になりますが、素の出現を一度だけ削除しようとすると、誤って残りの文字が残る可能性があります。 

もう 1 つのエッジ ケースは、部分文字列に`01`全然。 例えば、`111000`操作によって減らすことはできないため、答えは 6 です。単純な実装では、パターンの存在に関係なく何らかのバランスが発生すると誤って仮定する可能性があります。 

## アプローチ

 操作「削除」`01`」との間のキャンセル手続きを示唆しています。`0`そして`1`ただし、一方向のみです。`0`続いて`1`消えます。 これは非対称であるため、標準のブラケット マッチングとは動作が異なります。 

文字列でプロセスをシミュレートすると、構造的なものに気づきます。`0`の前に表示されるのは`1`一致させて削除することはできますが、`1`の前に表示されるのは`0`操作で直接キャンセルすることはできません。 これは、最終的な縮小形式が次のブロックで構成されることを意味します。`1`sの後に次のブロックが続きます`0`s. その間のすべては可能な限りキャンセルされます。 

より正確には、すべての`01`削除により、次の間の遷移の数が減少します。`0`そして`1`、そしてそれは、「ローカルペアリングの意味で0の後に1が続く」形式の1つの反転を効果的にキャンセルします。 より有用な観点は、プロセスを繰り返しペアリングするものとして扱うことです。`0`と`1`右側にあるので、両方を削除します。 

これは古典的な解釈につながります。最終的な答えは、次の数にのみ依存します。`0`と`1`およびキャンセルできる回数。 キャンセルごとに 1 つだけ削除されます`0`そして1つ`1`。 したがって、ペアリングが順序を尊重するという制約の下で、可能な限り最良の方法で形成できるペアの数がわかっている場合、結果は次のようになります。 

最終的な長さ = 最大ペアリング後の不一致文字の数`0`後で`1`。 

これは、各ペアが順序付けされている 0 と 1 の間の最大一致を計算することと同じです (`0`前に`1`）、スキャンすることで貪欲に計算できます。一致しないカウンターを維持します。`0`そして、私たちが見るたびに、`1`、以前の不一致でキャンセルします`0`もし可能なら。 

静的文字列の場合、これは O(n) です。 フリップを伴う動的部分文字列クエリの場合、発生したキャンセルの数を追跡しながらセグメントを結合できるデータ構造が必要です。 

重要な観察は、各セグメントが 2 つの数字で要約できることです。一致しないものがいくつあるかということです。`0`内部キャンセル後に残っている s と一致しない数`1`が残っています。 2 つのセグメント A と B を結合する場合、それらの間のキャンセルの数は次の数によって制限されます。`0`はAに残りますか？`1`s は B に存在します。境界を越えて貪欲に一致させることができます。 

したがって、各セグメントはペアを格納します`(zeros, ones)`内部縮小後。 合併する場合はキャンセルします`t = min(zeros_left, ones_right)`ペアの場合:

 new_zeros = ゼロス左 + ゼロス右 - t

 new_ones = 左のもの + 右のもの - t

 この構造はセグメント ツリーの下で完全に維持され、ポイントの更新と範囲クエリの両方をサポートします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | クエリごとのブルート フォース シミュレーション | O(nq) | お(1) | 遅すぎる |
 | マージ状態を含むセグメント ツリー | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列上でセグメント ツリーを維持し、各ノードにペアが格納されます。`(z, o)`そのセグメントを内部的に完全に削減した後の、一致しない 0 と 1 の数を表します。 

1. 次のようにリーフ ノードを構築します。`0`貢献する`(1, 0)`そして`1`貢献する`(0, 1)`。 各文字は、その単一要素セグメント内では自明に縮小されません。 
2. 2 つの隣接するセグメント A、次に B を結合する場合、境界を越えて何回キャンセルが発生する可能性があるかを計算します。 A の 0 と B の 1 を照合します。そのような照合の数は次のとおりです。`t = min(A.z, B.o)`。 
3. マージされた状態を次のように更新します。 

A.z + B.z - t ゼロは残ります。 

A.o + B.o - t のものが残ります。 

このステップが機能するのは、結合セグメント内の最適なキャンセルでは、左側の部分の 0 と右側の部分の 1 を組み合わせる必要があるためです。 注文の関係上、他の方向でのペアリングは不可能です。 
4. 範囲クエリは、クエリされた間隔にわたってマージされたペアを返します。 最終的な答えは単純に、`z + o`。 
5. ポイント更新では、キャラクタを反転してリーフ ノードを更新し、ルートへのパスに沿って再計算します。 

機能する理由: 各ノードは、内部ルールに基づいて完全に縮小されたセグメントを表します。`01`削除。 2 つのセグメントを連結する場合、新しく削除される可能性があるのは境界を越える削除のみであり、これらは境界を越える必要があります。`0`左のセグメントとペアになっているものから`1`右セグメントから。 各セグメントはすでにその不一致の残基に圧縮されているため、それ以上の内部構造は問題になりません。 これにより、将来のマージのために、セグメント表現が完全でロスレスであることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, s):
        self.n = len(s)
        self.t = [(0, 0)] * (4 * self.n)
        self.s = s
        self.build(1, 0, self.n - 1)

    def merge(self, a, b):
        z1, o1 = a
        z2, o2 = b
        t = min(z1, o2)
        return (z1 + z2 - t, o1 + o2 - t)

    def build(self, v, l, r):
        if l == r:
            if self.s[l] == '0':
                self.t[v] = (1, 0)
            else:
                self.t[v] = (0, 1)
            return
        m = (l + r) // 2
        self.build(v * 2, l, m)
        self.build(v * 2 + 1, m + 1, r)
        self.t[v] = self.merge(self.t[v * 2], self.t[v * 2 + 1])

    def update(self, v, l, r, idx):
        if l == r:
            self.s = self.s[:idx] + ('1' if self.s[idx] == '0' else '0') + self.s[idx+1:]
            if self.s[l] == '0':
                self.t[v] = (1, 0)
            else:
                self.t[v] = (0, 1)
            return
        m = (l + r) // 2
        if idx <= m:
            self.update(v * 2, l, m, idx)
        else:
            self.update(v * 2 + 1, m + 1, r, idx)
        self.t[v] = self.merge(self.t[v * 2], self.t[v * 2 + 1])

    def query(self, v, l, r, ql, qr):
        if ql <= l and r <= qr:
            return self.t[v]
        m = (l + r) // 2
        if qr <= m:
            return self.query(v * 2, l, m, ql, qr)
        if ql > m:
            return self.query(v * 2 + 1, m + 1, r, ql, qr)
        left = self.query(v * 2, l, m, ql, qr)
        right = self.query(v * 2 + 1, m + 1, r, ql, qr)
        return self.merge(left, right)

def solve():
    s = input().strip()
    q = int(input())
    st = SegTree(s)

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == '1':
            idx = int(tmp[1]) - 1
            st.update(1, 0, st.n - 1, idx)
        else:
            l, r = int(tmp[1]) - 1, int(tmp[2]) - 1
            z, o = st.query(1, 0, st.n - 1, l, r)
            print(z + o)

if __name__ == "__main__":
    solve()
```セグメント ツリーには、正しいマージに必要な不変式が正確に保存されます。 各更新ではリーフのみが変更され、内部ノードは同じキャンセル ルールを介して再計算され、一貫性が確保されます。 

実装上の微妙な問題の 1 つはインデックス付けです。クエリは 1 から始まるため、更新とクエリの両方に一貫して変換を適用する必要があります。 もう 1 つは、ノードごとに保存される状態が意図的に最小限であることです。 完全な文字列や遷移構造を追跡しようとすることは不要であり、メモリと時間の制約を超えてしまいます。

| 操作 | 考慮されるセグメント | (0、1) | 答え |

 トレースは、フリップがローカルでリーフ ノードをどのように変更するか、およびグローバル リダクションが再計算下でどのように安定しているかを示します。 

### サンプル 2

 初期文字列:`1011000110101010010`完全なテーブルは大きくなりますが、代表的なクエリを検査します。 

のために`[1,10]`、セグメントは次のように減少します。`(4,4)`したがって、答えは 4 です。 

のために`[4,9]`、キャンセル後の部分文字列には 1 よりも 0 の方が多くなり、最終的に一致しないカウントは 5 になります。 

のために`[4,9]`内部マージ後の構造では、ローカルな隣接関係ではなく、境界を越えたキャンセルが支配的であることが確認されています。 

主なパターンは、同様のカウントを持つ異なる部分文字列でも、その順序によってキャンセルの機会が変化した場合に、異なる結果が生成される可能性があり、セグメント ツリーはその順序の影響を正しく捕捉するというものです。

| スペース | O(n) | セグメント ツリーはノードごとに一定サイズの状態を保存します。 

n と q が 2e5 までの場合、log n は約 18 となるため、合計操作は約数百万回のマージとなり、制限内に十分収まります。

 ## 特殊なケース

 次のような単一文字列`0`または`1`常にどちらかのノード状態を生成します`(1,0)`または`(0,1)`、クエリは 1 を返します。リーフはマージせずに直接初期化されるため、セグメント ツリーがこれを処理します。 

次のようなゼロのみの文字列`000000`決してキャンセルを引き起こしません。 各ノードはゼロを蓄積し、マージではゼロが生成されません。`t > 0`構造体のどこにも人がいないからです。 

次のような交互の文字列`010101`境界を越えた最大のキャンセルを示します。 各マージ ステップでは 1 つのペアだけがキャンセルされ、セグメント ツリーは範囲全体をパリティに応じて小さな残差またはゼロに圧縮します。 

中心人物をから変えるフリップ`0`に`1`大規模なセグメント全体でキャンセル容量が大幅に変化する可能性があります。 ツリーは、リーフのみを更新して上方向に再計算することでこれを処理し、影響を受けるすべてのマージが無関係なセグメントに影響を与えることなく一貫して更新されるようにします。
