 ## 解決策
 ## 問題の理解

 私たちには家の木が与えられています。 各家には、最初は一定数の友達が住んでいます。 時間の経過とともに、2 種類のイベントが発生します。 うまるは 2 つの家の間で旅行クエリを実行するか、特定の家の友人の数を何らかの係数で乗算して増やす更新を実行します。 

旅行クエリごとに、うまるはツリー内の指定された 2 つのノード間の一意の単純なパスに沿って歩きます。 そのパス上の各家は、現在の友人の数に貢献します。 彼女は、その道のあらゆる値で割り切れる数のお菓子を持っていきたいと考えています。 つまり、その時点でそのパス上の値の最小公倍数が必要であり、それを 10^9 + 7 を法として出力します。 

ツリー構造では、任意の 2 つのノード間にパスが 1 つだけ存在することが保証されるため、各クエリはツリー上で定義された動的配列上のパスの処理に減ります。 

制約は小さく、N と Q は最大 1000 です。これにより、パス上の値を直接再計算したり、情報を繰り返し再構築したりするソリューションが可能になるため、これは重要です。 クエリごとに N^2 が含まれるものはまだ境界線にありますが、許容されます。一方、すべてのクエリにわたる 3 次のものは、厳密に実装されていれば Python で快適に通過します。 

微妙な点は、乗算更新により値が時間の経過とともに増加することです。 LCM を使用しているため、クエリごとの単純な因数分解はこれらの制限下でも機能する可能性がありますが、再計算のオーバーヘッドを避けるために慎重に構造化する必要があります。 

典型的なエッジ ケースは、更新がクエリされたパス上にないノードに影響を与える場合に発生します。 たとえば、ノード 5 に 10 を乗算し、後でノード 5 を含まないパスをクエリした場合、結果は影響を受けません。 もう 1 つのエッジ ケースは、同じノード上で更新が繰り返されることで、値が急速に増加する可能性があります。 たとえば、2 で始まるノードは係数 3、5、および 7 によって更新されて 210 になり、後のパス計算に完全に反映される必要があります。 

## アプローチ

 直接的な総当たりアプローチは、各クエリを個別に処理します。 u と v の間の移動クエリの場合、最初に DFS または BFS 親再構成を使用してそれらの間の一意のパスを見つけます。 パスを取得したら、その上のすべてのノードを反復処理し、現在の値の最小公倍数を計算します。 更新の場合は、ノードに保存されている値を単純に乗算します。 

これは正しいです。ツリー構造によって単一のパスが保証され、セットに対する LCM は結合的であり、増分的に計算できるためです。 問題は、クエリを繰り返す場合の効率です。 

最悪の場合のパス長は O(N) で、O(Q) 個のクエリが存在する可能性があります。 各クエリは最大 O(N) ノードにわたる LCM を再計算するため、合計の複雑さは O(NQ) になり、これは約 10^6 の演算に相当し、すでに問題ありません。 ただし、LCM 計算内で単純な因数分解を使用して実装すると、各数値が最大 10^7 倍の乗算になり、因数爆発や gcd 計算の繰り返しが発生してパフォーマンスが低下する可能性があります。 

より明確な観察は、実際には毎回完全な LCM を最初から再計算する必要はないということです。 LCM は素指数に依存するため、問題は各ノード値の素因数分解を維持し、パスに沿って最大の指数を取得することになります。 各更新は 1 つのノードにのみ影響するため、その因数分解を段階的に更新します。 各クエリは素数指数の「最大パス」問題になります。 

N が小さいため、LCA または親ポインターを介してパスを事前計算し、素数指数のマップを維持しながらクエリごとにパスをたどることができます。 各クエリはパス長が線形になり、更新は O(log 値) 因数分解になります。 

したがって、解決策は本質的に次のとおりです。値を因数分解し、ノードごとの素数指数マップを維持し、クエリごとにパスをたどり、素数ごとの最大指数を計算します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとのブルート フォース LCM 再計算 | O(NQ + Q log A) | O(N) | 承認済み |
 | 因数分解されたパスの集約 | O(Q * N * sqrt(A)) | O(N log A) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ツリーを構築し、任意のルートから DFS を使用して親配列と深さ配列を前処理します。 これにより、最下位の共通祖先に到達するまで両方のノードをリフトすることで、任意の 2 つのノード間のパスを再構築できます。 
2. 配列を維持する`fact[i]`ノード i での現在の値の素因数分解を、素数から指数への辞書またはカウンターとして保存します。 すべての a[i] を因数分解してこれを初期化します。 
3. ノード w と f を乗算し、f を因数分解してその指数を加算する形式の更新クエリごとに、`fact[w]`。 これにより、ノードの値が素指数形式で正しく表現されたままになります。 
4. u と v の間の各トラベル クエリについて、最初に u と v を LCA まで登ってセグメントを連結することによって完全なパス ノードを再構築します。 これにより、単純なパス上のすべてのノードが順番に表示されます。 
5. 空の辞書を初期化する`res`パス全体の最大指数を保存します。 
6. パス上の各ノードを走査し、因数分解内の素数ごとに更新します。`res[p] = max(res[p], fact[node][p])`。 このステップでは、LCM に必要な指数構造を集約します。 
7. パス上のすべてのノードを処理した後、乗算して答えを計算します。`p^res[p] mod MOD`内のすべての素数に対して`res`。 
8. この値を出力し、次のクエリに進みます。 

これが効率的である主な理由は、因数分解が更新時にのみ行われ、パスの走査が N で線形であるためです。N と Q は両方とも小さいため、総コストは問題なく制限内に収まります。 

### なぜ効果があるのか

 一連の数値の最小公倍数は、各素数について、すべての数値にわたるその素数の最大指数を取ることによって決定されます。 各ノードの値を素因数分解で表すと、必要な情報がすべて保存されます。 更新では指数が増加するだけで、減少することはないため、因数分解は時間が経っても一貫したままになります。 パスを横断するとき、素数ごとの最大指数を収集すると、そのパスの最小公倍数が正確に再構築されます。 素数間に相互作用は存在しないため、素数を独立して処理することは常に有効です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

from collections import defaultdict

def factorize(x):
    res = defaultdict(int)
    d = 2
    while d * d <= x:
        while x % d == 0:
            res[d] += 1
            x //= d
        d += 1
    if x > 1:
        res[x] += 1
    return res

def lca(u, v, parent, depth):
    visited = set()
    while u != v:
        if depth[u] > depth[v]:
            visited.add(u)
            u = parent[u]
        else:
            visited.add(v)
            v = parent[v]
    visited.add(u)
    return visited

def build_path(u, v, parent, depth):
    path_u = []
    path_v = []
    a, b = u, v
    while depth[a] > depth[b]:
        path_u.append(a)
        a = parent[a]
    while depth[b] > depth[a]:
        path_v.append(b)
        b = parent[b]
    while a != b:
        path_u.append(a)
        path_v.append(b)
        a = parent[a]
        b = parent[b]
    path_u.append(a)
    return path_u + path_v[::-1]

def dfs(root, g, parent, depth):
    stack = [(root, -1)]
    parent[root] = -1
    depth[root] = 0
    order = []
    while stack:
        u, p = stack.pop()
        for v in g[u]:
            if v == p:
                continue
            parent[v] = u
            depth[v] = depth[u] + 1
            stack.append((v, u))
    return

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    g = [[] for _ in range(n)]
    for _ in range(n - 1):
        u, v = map(int, input().split())
        u -= 1
        v -= 1
        g[u].append(v)
        g[v].append(u)

    parent = [-1] * n
    depth = [0] * n
    dfs(0, g, parent, depth)

    fact = [factorize(x) for x in a]

    for _ in range(q):
        tmp = list(map(int, input().split()))
        if tmp[0] == 1:
            u, v = tmp[1] - 1, tmp[2] - 1
            path = build_path(u, v, parent, depth)
            cur = defaultdict(int)
            for node in path:
                for p, e in fact[node].items():
                    if e > cur[p]:
                        cur[p] = e
            ans = 1
            for p, e in cur.items():
                ans = (ans * pow(p, e, MOD)) % MOD
            print(ans)
        else:
            w, f = tmp[1] - 1, tmp[2]
            add = factorize(f)
            for p, e in add.items():
                fact[w][p] += e

if __name__ == "__main__":
    solve()
```DFS は親情報と深さ情報を確立するため、あらゆるパスを線形時間で再構築できます。 因数分解表`fact`は乗算更新の下で常に更新され続けるため、常に各ノード値を忠実に表現したままになります。 

の`build_path`関数は、両方の端点が出会うまで持ち上げることによって単純なパスを再構築します。構造はツリーであるため安全です。 これにより、親ポインターを超えた LCA 前処理の必要がなくなります。 

次に、各クエリは、最大素指数を蓄積する辞書を使用してパス全体をスイープすることになります。これは、LCM の計算に直接対応します。 

## 実用的な例

 サンプル入力を考えてみましょう。 最初のクエリは、初期ツリー内のパスに沿って LCM を計算します。 走査では、そのパス上のすべてのノードから値を収集し、それらの素因数を結合して 12 を生成します。 

| ステップ | ノード | 現在値の因数分解 | 集約された最大指数 |
 | --- | --- | --- | --- |
 | 開始 | - | - | {} |
 | 訪問 1 | 1 | {1} | {1:1} |
 | 訪問 2 | 2 | {2,3} | {1:1、2:1、3:1} |
 | 訪問 5 | 5 | {2,2} | {1:1、2:2、3:1} |

 結果の積は 2^2 * 3 = 12 となり、正しいことが確認されます。 

更新後、ノード 2 は 4 で乗算され、2 の指数が 2 ずつ増加します。これにより、因数分解が 6 から 24 に変更されます。 

| ステップ | ノード | 因数分解 | 最大更新 |

 2 番目のクエリにはパスにノード 2 が含まれているため、LCM は増加した 2 の累乗を反映する必要があります。結果は 24 になります。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(Q * N * sqrt(A)) | 各クエリは O(N) ノードを横断する可能性があり、因数分解コストは更新時のみ O(sqrt(A)) です。 
| スペース | O(N log A) | 各ノードは、現在の値の素因数分解を保存します。 

この制約により、N と Q は最大 1000 に保たれるため、因数分解のオーバーヘッドと組み合わせたクエリごとの完全な走査であっても、時間制限内に十分収まります。 このソリューションは、2 秒と 512 MB の両方に快適に収まります。

 ## 特殊なケース

 重要なエッジケースは、単一ノード上で更新が繰り返されることです。 ノードが何度も乗算される場合、その因数分解は前の値を上書きするのではなく、正しく累積する必要があります。 たとえば、2 から始めて乗算器 3 と 5 を適用すると、因数分解 {2:1,3:1,5:1} が生成されます。 更新ロジックは指数を直接追加するため、以前の寄与が保存されます。 

もう 1 つのエッジ ケースは、u が v に等しいクエリです。パスには 1 つのノードが含まれているため、答えは単純にそのノードの現在の値になります。 この場合、パス構築ロジックは単一要素リストを返し、LCM 累積はそのノードの因数分解に正しく還元されます。 

最後のエッジ ケースは、まったくクエリされないノードの更新です。 これらは出力には影響しませんが、今後のクエリにはシーケンスの後半でこれらのノードが含まれる可能性があるため、正しく適用する必要があります。 因数分解ストレージにより、クエリの順序に関係なく、更新がグローバルかつ永続的になることが保証されます。
