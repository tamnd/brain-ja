 ## 解決策
 ## 問題の理解

 絶対的なコンパスの方向で書かれたルートが与えられます。各ステップは、北、東、南、西の 4 つの値のいずれかになります。 ルートを実行するプラットフォームは、最初は北を向いた固定の向きで開始します。 ルートが実行されると、新しいコマンドはそれぞれグローバル座標系で与えられますが、私たちが望んでいるのは、移動するプラットフォームの観点から同じ動きを相対的なコマンドのシーケンスとして書き直すことです。 

重要な変換は、各ステップで、方向を絶対ベクトルとして解釈するのではなく、プラットフォームの現在の方向を基準にして解釈することです。 各移動の後、プラットフォームの向きは、移動したばかりの方向と一致するように更新され、次のコマンドはこの更新された向きを基準にして表現する必要があります。 

したがって、出力は同じ長さのシーケンスになりますが、絶対的な方向ではなく、現在の機首方位に対してプラットフォームが前進し続けるか、右折するか、方向転換するか、または左折するかをエンコードします。 

制約は十分小さいため、文字列に対する 1 回の線形スキャンで十分です。 各位置の相対方向を最初から再計算しようとするソリューションはいずれも線形ですが、ペアごとの再計算やすべての遷移の事前計算を伴うものは不要なオーバーヘッドです。 本来のターゲットの複雑さは O(n) です。 

微妙なエッジ ケースは、方向演算でのラップアラウンドの処理から発生します。 方向はサイズ 4 のサイクルを形成するため、単純な減算では負の値が生成される可能性があります。 たとえば、北から西に移動すると、生の差は -1 になりますが、これは有効な範囲 [0, 3] に正規化する必要があります。 モジュール正規化を忘れた実装では、ラップアラウンド遷移で不正な相対コマンドが暗黙的に生成されます。 

もう 1 つのよくある落とし穴は、ステップごとにプラットフォームの向きが変わるという誤解です。 たとえば、固定の基準方向 (常に北) を誤って仮定した場合、最初の移動後の相対方向の計算は一貫して間違ったものになります。 

## アプローチ

 ブルートフォース解釈では、プラットフォームを段階的にシミュレートし、各段階で現在のコマンドの絶対方向と現在の方向を比較することによって相対方向を再計算します。 これはすでに最適に近い状態ですが、不注意に実装すると、ペアを繰り返しスキャンまたはマッピングすることで差分が再計算され、冗長な作業が発生する可能性があります。 

明確な観察は、絶対方向と相対遷移の両方がサイズ 4 の同じ周期グループ内に存在するということです。 方向を 0、1、2、3 にマッピングされた北、東、南、西の整数としてエンコードすると、相対コマンドは単にターゲットの方向と現在の方向の間のモジュール式の差になります。 ステップの実行後、現在の方向を同じターゲット方向に更新します。 

これにより、問題は単一の整数状態の維持と文字ごとの定数時間演算の実行に軽減されます。 ブルートフォースのアイデアは、すでにシミュレーション構造に従っているため機能しますが、幾何学的なベクトルや文字列ベースの変換で考えると、不必要に複雑になります。 循環構造を認識すると、すべてが単純なモジュラー演算に分解されます。

 | 最適なモジュール式エンコーディング | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 各方向文字をサイクル内の整数に変換します。北は 0、東は 1、南は 2、西は 3 になります。これにより、算術演算で回転を表すことができます。 
2. プラットフォームは北を向き始めるため、現在の向きを 0 として初期化します。 
3. 入力シーケンス内の各コマンドについて、減算を使用してコマンドの方向と現在の方向の差を計算します。 
4. モジュロ 4 を使用してこの差を正規化します。結果が負の場合は、モジュロ演算によって暗黙的に 4 を加算します。 これにより、常に有効な方向状態内に留まることが保証されます。 
5. 結果の値を相対コマンドに変換します。0 は前進を続けることを意味し、1 は右折を意味し、2 は方向転換を意味し、3 は左折を意味します。 
6. プラットフォームは移動方向を向くように回転するため、現在の方向を実行したばかりの絶対方向に更新します。 
7. 出力シーケンスに相対コマンドを追加し、次の入力文字に進みます。 

中心的な考え方は、各ステップで絶対方向を現在の進行方向に対する回転として表現し、進行方向をその方向に更新するということです。 状態の発展は単一の整数によって完全に捕捉されます。 

### なぜ効果があるのか

 このアルゴリズムは、保存された方向が最後に実行された絶対方向と常に等しいという不変条件を維持します。 すべての相対コマンドは、次の絶対方向とこの保存された方向の差としてモジュロ 4 サイクルで計算されるため、ある方向を別の方向に変換するために必要な回転を正確にエンコードします。 4 方向の回転は加算法 4 の下で閉じた循環グループを形成するため、各変換は一意に表現され、ステップ間で曖昧さやドリフトが蓄積することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()

    mp = {
        'N': 0,
        'E': 1,
        'S': 2,
        'W': 3
    }

    rmp = {
        0: 'N',
        1: 'E',
        2: 'S',
        3: 'W'
    }

    cur = 0
    out = []

    for ch in s:
        nxt = mp[ch]
        diff = (nxt - cur) % 4
        out.append(rmp[diff])
        cur = nxt

    sys.stdout.write(''.join(out))

if __name__ == "__main__":
    solve()
```この解決策は単一の変数を維持することに依存しています`cur`、これはプラットフォームの現在の絶対方向を表します。 文字ごとに、それを数値エンコーディングに変換し、モジュラー差を計算します。 モジュロ演算は、順方向ラップアラウンドと負の減算の両方のケースを均一に処理するため、追加の条件ロジックは必要ありません。 

アップデート`cur = nxt`は、各移動の実行後のプラットフォームの物理的な回転を反映するため、重要です。 この更新がなければ、後続のすべての相対計算は誤って固定方向を仮定することになります。

 ## 特殊なケース

 エッジ ケースの 1 つは、北から西への移行など、サイクル内で方向が逆方向にジャンプする場合です。 入力用`NW`の場合、計算は cur = 0 から nxt = 3 に進み、(3 - 0) % 4 = 3 が生成され、左折に正しくマッピングされます。 モジュロ処理を行わない単純な減算では -1 が生成され、有効なコマンドへのマッピングに失敗します。 

もう 1 つのケースは、方向の変化を蓄積する回転の繰り返しです。 入力用`NESW`、現在の方向性は 4 つの状態すべてを通じて進化します。 アルゴリズムが正しく更新される`cur`各ステップで各差が正しいフレームに対して計算されるため、ドリフトが防止されます。 

最後の微妙なケースは、次のような長く均一なシーケンスです。`SSSSSS`。 各ステップで方向が南に繰り返し更新されるため、最初の移動後のすべての差はゼロとなり、一貫した前進コマンドが生成されます。 これにより、指示が繰り返される場合、状態の更新が冪等であることが確認されます。
