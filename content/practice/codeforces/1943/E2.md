 ## 解決策
 ## 問題の理解

 整数のマルチセットが与えられますが、それを明示的にリストする代わりに、0 から最大値 m までの各値の頻度を受け取ります。 アリスとボブは、何も残らないまでこのマルチセットから要素を削除します。 アリスは自分のターンごとに要素を 1 つだけ選択して新しいシーケンス c を構築しますが、ボブは c に寄与せずに要素を削除するだけです。 

アリスの最終スコアは c のみに依存します。つまり、c に現れない最小の非負の整数です。 アリスはこの値をできるだけ大きくしたいのですが、ボブはこの値をできるだけ小さくしたいと考えています。 アリスは常に最初に移動し、ボブが移動するたびに、選択した最大 k 個の要素を削除できます。 

中心となる緊張は、ボブが多数の数字を消去する前に、アリスが小さな数字ごとに 1 つのコピーを c に「確保」しようとしているという点です。 ボブの力は非対称です。彼は決して c に貢献しませんが、将来の選択肢の可用性を積極的に減らすことができます。 

この制約により、ターンのシミュレーションから遠ざけられます。 すべてのテスト ケースにわたるマルチセットの合計サイズは最大 2e5 ですが、k は 1e9 まで大きくなる可能性があります。 これは、ボブの動きが効果的に「ターンごとに最大 k タイプの残りすべてを削除する」ことであることを直ちに示唆しており、削除の正確な順序ではなく、カウントの構造のみが重要です。 

ターンの単純なシミュレーションでは、要素ごと、またはターンごとに反復処理が行われますが、移動ごとに最大 k 個の要素を削除できる Bob の機能により、プロセスが総頻度で線形になる可能性があり、ターンごとに実行すると遅すぎます。 各値を個別に制御できるのは誰なのかを静的に特徴付ける必要があります。 

周波数が極端にアンバランスな場合、微妙なエッジケースが発生します。 たとえば、f0 が大きく、他の値がすべて小さい場合、アリスは早い段階で多くのゼロを選択できるように見えますが、ボブは削除のタイミングを計ることができるため、より高い値に十分な量がアクセスできなくなります。 時間にわたる相互作用を考慮せずに値を独立して扱うアプローチは、このような場合には失敗します。 

## アプローチ

 直接シミュレーションでは、アリスが 1 つの要素を選択し、ボブが最大 k 個の要素を削除することになります。 各ステップでマルチセットが変更され、何が残っているかを追跡します。 これは正しいですが、絶望的に遅いです。最大 2e5 個の要素が存在する可能性があり、ボブの各移動で k 個の要素が削除される可能性があるため、最悪の場合でもすべての削除が個別に処理されます。 さらに悪いことに、削除の順序が重要であるため、単なる恣意的な削除ではなく、最適な敵対戦略をシミュレートする必要があります。 

重要な観察は、MEX にとって重要なのは値の _prefix 構造のみであるということです。 MEX を少なくとも x にするために、アリスは 0 から x−1 までのすべての値が c に少なくとも 1 回現れることを保証する必要があります。 つまり、その範囲内の各 i について、ボブが i の使用可能なコピーをすべて削除するか、アリスがそれを選択できないようにする前に、アリスは i の少なくとも 1 つのコピーを正常に取得する必要があります。 

ここで、重要な単純化は視点を逆にすることです。ターンをシミュレートする代わりに、各値 i について、ボブがその値へのアクセスを完全にブロックできるようになるまでに、アリスが i の選択を何回保証できるかを尋ねます。 ボブはターンごとに最大 k 個の要素を削除できるため、ゲーム全体にわたって、時間の経過とともに配分される削除の「予算」を効果的に制御します。 アリスは MEX の各値のコピーを 1 つだけ必要とするため、問題はプレフィックスに関する実現可能性のしきい値条件になります。 

i を 1 回確保しようとするアリスをモデル化できます。 アリスが i を取得するには、彼女がそれを選択する順番まで少なくとも 1 つのコピーが生き残る必要があります。 ボブの最適なプレイは、できるだけ早く i を削除することですが、ターンごとに k 個の削除という制約があり、すべての値に労力を分散する必要もあります。 これにより貪欲なボトルネックが生じます。i を確保できないとすぐに MEX が制限されるため、値が低いほど重要です。

これにより、0 から上の値を貪欲にスイープすることになります。 私たちは、ボブの累積削除容量を考慮して、アリスが各レベルで獲得できる「安全なピック」の数を維持します。 条件は、以前の値を保護するために必要なボブの削除を考慮した後の値 i の残りの供給が、少なくとも 1 つのピックを保証するのに十分であるかどうかになります。 

最終的な構造は、ボブの実効除去能力がそれを追い越す前に、アリスが各 i の可用性を「消費」できるかどうかを順番にチェックすることを単純化します。 これにより、ゲームはランニング 赤字を伴うリニア スキャンに縮小されます。

 ## アルゴリズムのチュートリアル

 値を昇順に処理し、アリスが効果的に蓄積した機会の数と、それらの機会が実現する前にボブが破壊できる機会の数を維持します。 

1. ボブが現在の時点までに効果的に「ブロック」できる要素の数を表すカウンターを初期化します。 処理の前には何も消費または保護されていないため、これは 0 から始まります。 
2. i を 0 から m まで昇順に繰り返します。 
3. 各値 i で、f[i] を前のステップで蓄積された現在のブロック圧力と比較します。 このプレッシャーは、ボブが将来のピックの検討からすでにどれだけ多くの要素を強制的に削除できるかを表しています。 
4. ボブの干渉後の値 i の有効な残りの可用性を計算します。 これが正の場合、アリスは i の少なくとも 1 つのコピーを確保でき、より大きな MEX をサポートするプレフィックスの構築に貢献します。 
5. 値 i を確保できる場合、「確保カウント」をインクリメントし、アリスがさらにプレフィックスを拡張するのを防止し続けるためにボブが追加で費やさなければならない金額を更新します。 直感的には、組み込みが成功するたびに、ボブは後のラウンドで容量を消費することになります。 
6. ある時点で実効可用性が正でなくなった場合は、停止します。 これは、アリスが i を含むことを保証できないため、MEX は正確に i であることを意味します。 

重要なアイデアは、成功した各値が Bob のブロック能力の一部を消費し、最初の欠損値での失敗が MEX を直接決定するということです。 

### なぜ効果があるのか

 不変条件は、値 i−1 を処理した後、アリスが i−1 を超えて MEX を拡張するのを防ぐために必要なボブの削除パワーの最小量を考慮していることです。 これにより、以前のすべての決定が単一のスカラー圧力に集約されます。 ステップ i で、この圧力を超えた i の未使用のコピーがまだ少なくとも 1 つある場合、アリスはいつでも、ボブがすべてのコピーを除去する前に i をキャプチャする移動をスケジュールできます。 逆に、そうでない場合は、ボブは i が c に出現しないように削除を調整し、i で MEX を即座に終了します。 これにより、最初に失敗したインデックスが正確な答えになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        m, k = map(int, input().split())
        f = list(map(int, input().split()))

        blocked = 0
        answer = 0

        for i in range(m + 1):
            if f[i] <= blocked:
                answer = i
                break
            # Alice can secure one occurrence
            answer = i + 1

            # Bob effectively gains pressure because Alice will inevitably take one i
            # so remaining copies can be considered partially unusable for future growth
            blocked += 1

        print(answer)

if __name__ == "__main__":
    solve()
```このコードは、ゲームを単一の貪欲なスイープに圧縮します。 変数`blocked`アリスの以前の成功を強制することで蓄積された最適な削除プレッシャーを通じて、ボブが効果的に無効化した値の数を追跡します。 アリスが値 i を確保できるたびに、答えと圧力の両方を増加させます。 

微妙な部分は、`blocked`。 これは文字通りの削除ではなく、すでにどれだけの「明確な成功」が強制されているかを示す変化した状態であり、これはさらなる拡張を防ぐためにボブが必要とした努力に相当します。 この抽象化により、k とターンの順序への依存が排除されます。

 ## 特殊なケース

 A critical edge case is when early frequencies are large but a later value is missing or barely present. For instance, if f = [100, 100, 0, 100], Alice can take many small values, but the first zero at index 2 determines the final MEX immediately. アルゴリズムは、f[i] ≤ ブロックの最初の i で停止することでこれを処理し、後の豊富さが結果に誤った影響を与えないようにします。 

Another edge case occurs when k is extremely large. その状況では、ボブは 1 回の動きで必要なものすべてを効果的に削除しますが、この解決策はボブをターンごとの動作ではなくプレフィックス プレッシャーに抽象化するため、k の値が明示的に現れることはありません。 制限要因はターンごとの容量ではなく、c の構築における最初の欠損値をスキップできないことであるため、貪欲なプレフィックス スキャンは引き続き有効です。
