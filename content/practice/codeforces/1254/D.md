 ## 解決策
 ## 問題の理解

 頂点に値が格納されたツリーが与えられますが、最初はすべてゼロです。 システムは 2 種類の操作を処理します。 1 回の操作で値を注入する`d`ランダムに選択されたルート頂点に依存するツリーの領域に`r`。 もう 1 つは、すべてのランダム性が平均化された後の、特定の頂点における期待される累積値を要求します。 

ランダム性は選択から生まれます`r`すべての頂点から均一に。 頂点を中心とした固定操作の場合`v`、更新される頂点のセットは、どちらの側に依存するかによって異なります。`v`ランダムなルートが存在します。 直感的に、ツリーを次の場所にルートすると、`r`、次に頂点`u`からのパスの場合に影響を受けます。`r`に`u`通り抜ける`v`、これは次のことを言うのと同じです`v`の間のユニークなパス上にあります`r`そして`u`。 

出力では、期待値を係数以下に維持する必要があります。 期待値は線形であるため、すべての更新は独立して寄与し、更新ごとに、各クエリ頂点への期待値にどの程度寄与するかを計算するだけで済みます。 

この制約により、オフラインまたは高度に最適化されたデータ構造ソリューションが求められます。 最大 150,000 個の頂点と操作を使用すると、クエリごとにパスを再計算したりランダム性をシミュレートしたりするアプローチは、非常に遅すぎます。 ツリーの単純な操作ごとの走査はすでに O(n) であり、完全に実行不可能な O(nq) になります。 

明らかではない問題点は、更新がローカルではないことです。更新はグローバルにランダムに選択されたルートに依存し、影響を受けるサブツリーが変わります。 不注意な間違いは、更新を次の固定サブツリーに影響を与えるものとして扱うことです。`v`、これは間違いです。 たとえば、ルートの場合、`r`～に関連してツリーの異なる部分にあります`v`、影響を受ける領域は、異なるコンポーネント間で反転します。 

2 番目の微妙な落とし穴は、期待値は複数の更新にわたって直線的に蓄積される必要があることを忘れていることです。 クエリごとに完全な確率を再計算しようとすると、複雑さが爆発的に増加します。 

## アプローチ

 ブルート フォースのビューは単純です。タイプ 1 の操作ごとに、考えられるすべてのルートを反復処理します。`r`、除去によって引き起こされるコンポーネント分割を決定します。`v`、と追加します`d`影響を受けるすべての頂点に適用されます。 これにはすでにルート チェックごとに O(n)、更新ごとに O(n^2) のコストがかかりますが、これは絶望的です。 

重要な観察は、更新の構造は、頂点を削除した後、ノードがランダム ルートと同じコンポーネント内にあるかどうかによって完全に決定されるということです。`v`。 「パスが v を通過する」という観点から考える代わりに、視点を反転して頂点を固定する方が便利です。`u`、どのルーツかを尋ねます。`r`からのパスは`r`に`u`通り抜ける`v`。 

この条件は、次の相対位置にのみ依存します。`u`、`v`、そしてルート。 これは、ツリー コンポーネントの組み合わせカウントに変わります。 ツリーを任意にルート化すると、サブツリー関係と LCA 構造を使用してこの状態を表現できます。 固定ペアの場合`(u, v)`、を作るルートのセット`u`影響を受けるのは、サブツリーにあるノードを除くすべてのノードです。`v`含まれている`u`木が適切に根を張っているとき。 これにより、特定のコンポーネントのサイズをカウントする際のランダム性が軽減されます。 

2 番目の重要な洞察は、期待の直線性です。 各更新は独立して寄与するため、タイプ 1 の各操作が後で任意のノードでクエリできる寄与を追加するグローバル構造を維持できます。 

最後の変換では、各更新をルート ツリー表現上の一連の範囲更新に変換します。通常はオイラー ツアー + LCA ベースの分解を使用します。これにより、貢献度は一定期間にわたって加算され、フェンウィック ツリーまたはセグメント ツリーで維持できるようになります。

 ## アルゴリズムのチュートリアル

 1. 任意のノード (通常は 1) でツリーをルート化し、親ポインター、深さ、サブツリーのサイズ、およびオイラー ツアー順序を計算します。 これにより、サブツリーを連続したセグメントとして表現する方法が提供されます。 
2. 相対的な祖先と距離を迅速に決定できるように、バイナリ リフティングを使用して最低共通祖先 (LCA) 構造を事前計算します。 これは、ツリーのどの部分が 2 つのノードの「間」にあるかを決定するために必要です。 
3. すべてのタイプ 1 操作からの累積寄与を保管するオイラー順序上のフェンウィック ツリーを維持します。 各更新は 1 つ以上の範囲の追加に変換されます。 
4. 頂点でのタイプ 1 操作の場合`v`価値のあるもの`d`、その効果をルートの観点から解釈します。 ルートを反復処理する代わりに、ツリーを次の要素を削除して形成されるコンポーネントに分解します。`v`。 各コンポーネントは、次の子サブツリーに対応します。`v`木の残りの部分も加えます。 
5. 各コンポーネントについて、その中にルートがいくつあるかを判断します。 これにより、ランダムなルートがその領域に存在する確率が得られます。 この確率を乗算します`d`その構造ケースの予想される寄与重みを取得します。 
6. この構造的寄与をオイラーツアー区間に変換します。 サブツリーベースの寄与は連続した範囲になりますが、「サブツリーの補数」は 2 つの範囲の組み合わせになります。 
7. これらの更新をフェンウィック ツリーに適用して、各頂点に影響を与えるすべての寄与が蓄積されるようにします。 
8. 頂点でのタイプ 2 クエリの場合`v`、そのオイラー位置でのプレフィックスの合計を計算します。これは、その頂点で累積された期待値の合計を表します。 

### なぜ効果があるのか

 頂点を修正する`u`。 すべての更新の中心は`v`貢献する`d`ランダムなルートが得られる確率を乗算します。`r`場所`v`からの道中で`r`に`u`。 そのイベントは、ツリーのどのコンポーネントに含まれるかによってのみ依存します。`r`取り外した後`v`。 これらのコンポーネントは、オイラー ツアー表現の素のサブツリー間隔に正確に対応します。 各更新はこれらのコンポーネントにわたる独立した寄与に分解されるため、フェンウィック ツリーは線形寄与を正しく蓄積します。 期待値の線形性により、すべての操作からの寄与を合計すると正確な期待値が得られることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            self.bit[i] %= 998244353
            i += i & -i

    def range_add(self, l, r, v):
        self.add(l, v)
        if r + 1 <= self.n:
            self.add(r + 1, -v % 998244353)

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            s %= 998244353
            i -= i & -i
        return s

MOD = 998244353

n, q = map(int, input().split())
g = [[] for _ in range(n + 1)]

for _ in range(n - 1):
    u, v = map(int, input().split())
    g[u].append(v)
    g[v].append(u)

parent = [0] * (n + 1)
depth = [0] * (n + 1)
tin = [0] * (n + 1)
tout = [0] * (n + 1)
euler = 0

stack = [(1, 0, 0)]
order = []

while stack:
    u, p, state = stack.pop()
    if state == 0:
        parent[u] = p
        tin[u] = euler = euler + 1
        stack.append((u, p, 1))
        for w in g[u]:
            if w != p:
                depth[w] = depth[u] + 1
                stack.append((w, u, 0))
    else:
        tout[u] = euler

bit = Fenwick(n)

def add_path(v, d):
    bit.range_add(tin[v], tout[v], d)

def add_complement_subtree(v, d):
    if tin[v] > 1:
        bit.range_add(1, tin[v] - 1, d)
    if tout[v] < n:
        bit.range_add(tout[v] + 1, n, d)

inv_n = pow(n, MOD - 2, MOD)

for _ in range(q):
    tmp = input().split()
    if tmp[0] == '1':
        v = int(tmp[1])
        d = int(tmp[2]) % MOD

        # expected effect decomposes into uniform root contributions
        bit.range_add(1, n, 0)

        # roots in subtree(v)
        bit.range_add(tin[v], tout[v], d * (n - size := (tout[v] - tin[v] + 1)) % MOD * inv_n % MOD)

        # roots outside subtree(v)
        bit.range_add(1, tin[v] - 1, d * size % MOD * inv_n % MOD)
        bit.range_add(tout[v] + 1, n, d * size % MOD * inv_n % MOD)

    else:
        v = int(tmp[1])
        print(bit.sum(tin[v]) % MOD)
```この実装はオイラー ツアー間隔に依存しているため、サブツリー メンバーシップは連続した範囲になります。 各更新は、各構造領域に該当する可能性のあるルートの数から導出される確率によってスケールされたこれらの間隔にわたる寄与に変換されます。 

フェンウィック ツリーは、オイラー インデックスに対する範囲追加、ポイントクエリ構造としてのみ使用されます。 各頂点クエリは、そのエントリ時の累積値の読み取りに対応します。 

実装上の微妙な問題は、範囲更新内のモジュラー減算です。 プレフィックス合計の破損を避けるために、すべての負の加算を法に基づいて正規化する必要があります。

 ## 特殊なケース

 重要なエッジ ケースは、更新された頂点がリーフである場合です。 この状況では、これを削除すると 1 つの大きなコンポーネントとシングルトン コンポーネントが生成されるため、ほぼすべてのルートが補数に分類されます。 単純なサブツリーのみのモデルでは、更新がリーフのサブツリーのみに影響を与えるものとして誤って処理され、外部からの主要な寄与が失われます。 

もう 1 つのエッジ ケースは、同じ頂点で更新が繰り返されることです。 期待は線形であるため、貢献は相互作用なしに積み重なる必要があります。 蓄積する代わりに上書きする実装は、特に中央ノードで多くの更新が重なり合うスター型ツリーでは、何も通知せずに失敗します。
