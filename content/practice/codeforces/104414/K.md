 ## 解決策
 ## 問題の理解

 私たちに与えられた一次元のストリートは、$n$ポジション、それぞれのポジション$i$計画された最終的な高さがある$h_i$。 これを、各インデックスが建設現場と番号であるスカイライン プロジェクトと考えてください。$h_i$そのサイトで必要な「建設層」の数です。 

弊社では工事を行うことを許可されております。 各操作でセグメントが選択されます$[l, r]$そして毎に増加します$h_i$そのセグメントでは、完了に向けて 1 単位の進行度で進みます。 解釈としては、各単位の増加は、その間隔内のすべての建物に同時に 1 層の高さを与える作業の 1 つのバッチを表します。 

プロジェクト定義は動的です。 操作には 2 種類あります。 1 回の操作で値を追加することで計画された高さを変更します。$k$範囲内のすべての位置に$[l, r]$、それらの建物が最終的に必要とする建築層の数を効果的に増加させます。 もう 1 つの操作では、制限された計画に関する質問をします。つまり、外側のすべてを無視するかどうかです。$[l, r]$これらの位置を目標高さ 0 であるものとして扱うことにより、すべての建物を完成させるために必要な建設間隔操作の最小回数は何回になりますか?$[l, r]$?

 主要な出力は、タイプ 2 の各クエリに対する答えです。 

制約$n, m \le 10^5$までの高さ$10^6$クエリごとに回答を最初から再計算するソリューションは直ちに除外してください。 構築ステップの単純なシミュレーションや、クエリごとのフル スキャンの繰り返しでは生き残れません。 更新とクエリの両方が対数またはそれに近い値になる必要があります。 

微妙な問題は、高さが更新によって増加し、サブセグメントに対して個別にクエリされることです。 単純な間違いは、問題が単なるプレフィックス合計または範囲加算クエリであると考えることです。 2 番目の操作は合計や最大値を要求するのではなく、高さプロファイルを実現するために必要な間隔を「カバーする」操作の最小数を要求します。 

エッジ ケースは、更新が重度に重複する場合、またはクエリが間接的に何度もインクリメントされた領域を分離する場合に発生します。 たとえば、増やすと$[1, 5]$1 を繰り返し計算してサブセグメントをクエリすると、答えは合計だけではなく高さの構造によって決まります。 

罠を明らかにする小さな例:

 入力:```
3 3
1 2 3
1 1 3 1
2 1 3
2 2 2
```アップデート後、高さは$[2,3,4]$。 クエリを実行する$[2,2]$1 を返す必要がありますが、$[1,3]$4 つのグローバル単位操作が必要なので、 は 4 です。 素朴な解釈では、sum または max を単独で使用しようとしますが、コストは隣接する差分の構造に依存するため、失敗します。 

## アプローチ

 ブルートフォースの方法は、各クエリの構築を個別にシミュレートすることです。 一定間隔で$[l, r]$、各位置が目標の高さに達するために必要な間隔の増分数を知りたいと考えています。 各操作は連続セグメントを均一に増加させるため、セグメント全体に水平の「レイヤー」を積み重ねることによって高さプロファイルを構築することと同等です。 

レイヤーの観点から考えると、各操作は連続するブロックの高さの 1 単位に寄与します。 最小操作数は、配列を左から右にスキャンするときに新しい層を開始する必要がある合計回数に等しくなります。 具体的には、前の位置と比べて高さが何倍になったかを数えるということになります。 

したがって、固定配列の場合、次の答えは$[l, r]$は：$$h[l] + \sum_{i=l+1}^{r} \max(0, h[i] - h[i-1])$$これは既知の特徴であり、各増加は新しい「スタックの開始」を表します。 

ブルート フォースはクエリごとにこの合計を再計算します。$O(n)$、更新には時間がかかります$O(n)$直接適用された場合。 と$m = 10^5$、最悪の場合の複雑さは次のようになります。$10^{10}$が遅すぎます。 

重要な洞察は、答えは隣接する違いのみに依存するということです$d_i = \max(0, h_i - h_{i-1})$。 範囲の更新$h$これらの違いを構造化した最新情報に変換します。 各更新は、制御された方法で境界位置のみに影響します。 これにより、問題は、範囲加算および合計クエリを使用して差分の動的な配列を維持することに変わります。 

私たちは以下を維持します:$$d_i = \max(0, h_i - h_{i-1})$$クエリの答えに注意してください$[l, r]$は次のようになります:$$h[l] + \sum_{i=l+1}^{r} d_i$$したがって、次のものが必要です。 

1. 範囲の追加$h$2. メンテナンス$d$3. クエリプレフィックス調整後の合計$d$これは、範囲の追加とポイント クエリをサポートするセグメント ツリーまたはフェンウィック ツリーで処理されます。$h$、さらに維持のための 2 番目の構造$d$、変更の境界でのみ更新されます。 

各範囲の加算$[l, r, k]$2 つの比較のみを変更します。 

- で$l$:$h_l$増加し、影響を与える$d_l$- で$r+1$:$h_{r+1}$～に対する比較の変化$h_r$したがって、更新は$O(\log n)$、クエリも$O(\log n)$。

 ## アルゴリズムのチュートリアル

 2 つのセグメント ツリー (または BIT 構造) を維持します。 1 つは配列を格納する$h$範囲の追加とポイントのクエリで。 2 番目は派生構造を格納します$d_i = \max(0, h_i - h_{i-1})$ポイント更新経由。 

### ステップ

 1. 範囲の追加とポイントのクエリをサポートする構造を構築します。$h_i$。 

これにより、現在の高さを即座に取得できます。これは、更新後にローカルの差を再計算するために必要です。 
2. アレイを構築する$d$ここで最初は:$d_i = \max(0, h_i - h_{i-1})$。 

また、プレフィックス合計構造も維持します。$d$。 

これは、クエリの回答がプレフィックスの合計に減少するためです。$d$。 
3. タイプ 1 アップデートの場合$[l, r, k]$、範囲加算を適用します$h$。 

の高さ$[l, r]$変化しますが、重要なのは隣接境界のみです$d$。 
4. 影響を受けた差異を再計算します。 

ポジションのみ$l$そして$r+1$比較結果を変更することができます。 

更新します:$d_l = \max(0, h_l - h_{l-1})$

$d_{r+1} = \max(0, h_{r+1} - h_r)$もし$r+1 \le n$これが機能するのは、すべての内部差異が均一にシフトし、相対的な順序が維持されるためです。 
5. タイプ 2 クエリの場合$[l, r]$、次を計算します。$h[l] + \sum_{i=l+1}^{r} d_i$。 

これは、ポイント クエリによって取得されます。$h[l]$とプレフィックス範囲の合計$d$。 

### なぜ効果があるのか

 建設コストの解釈は、左から右に移動するときに高さの順序がどこで増加するかによってのみ決まります。 増加するたびに、有効な建設スケジュールに新しいレイヤーが強制的に追加されます。 範囲加算では境界を除いて相対的な差が保持されるため、増加の構造は更新エッジを除いて安定しています。 これにより、グローバルな問題は、隣接する比較における局所的な変化の小さなセットを追跡することに軽減されます。 不変条件とは、$d_i$は常に現在の隣接する差の正の部分に等しいため、プレフィックスの合計は次のようになります。$d$レイヤーの開始数を正確に数えます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 2)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

class RangeAddPointQuery:
    def __init__(self, n):
        self.n = n
        self.bit = BIT(n)

    def range_add(self, l, r, v):
        self.bit.add(l, v)
        if r + 1 <= self.n:
            self.bit.add(r + 1, -v)

    def get(self, i):
        return self.bit.sum(i)

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 2)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

n, m = map(int, input().split())
h0 = list(map(int, input().split()))

rapq = RangeAddPointQuery(n)
for i, v in enumerate(h0, 1):
    rapq.range_add(i, i, v)

d = Fenwick(n)

def get(i):
    if i == 1:
        return rapq.get(1)
    return max(0, rapq.get(i) - rapq.get(i - 1))

for i in range(1, n + 1):
    d.add(i, get(i))

def update(i):
    if 1 <= i <= n:
        if i == 1:
            new = rapq.get(1)
            prev = 0
        else:
            new = rapq.get(i)
            prev = rapq.get(i - 1)
        val = max(0, new - prev)
        cur = d.sum(i) - d.sum(i - 1)
        d.add(i, val - cur)

for _ in range(m):
    tmp = input().split()
    if tmp[0] == '1':
        _, l, r, k = map(int, tmp)
        rapq.range_add(l, r, k)
        update(l)
        update(r + 1)
    else:
        _, l, r = map(int, tmp)
        res = rapq.get(l)
        res += d.sum(r) - d.sum(l)
        print(res)
```実装では、高さの維持と差の維持が分離されます。 最初の構造は、高速範囲インクリメントとポイント クエリをサポートしており、配列全体の再構築を回避します。 2 番目の構造は、クエリの回答を駆動する圧縮された「ポイントの増加」表現を維持します。 

更新関数は、境界位置の再計算のみに慎重に制限されています。 よくある間違いは、すべてのインデックスを更新しようとすることです。$[l, r]$が鈍くなるにもほどがあります。 正確さは、各内部エッジの両方の端点が等しくシフトするため、内部差分の値が変化しないという事実に依存します。 

クエリではポイント値が使用されます。$l$との差分のプレフィックス和を加えたもの$l+1$に$r$、再構成式と一致します。

 ## 特殊なケース

 微妙なエッジ ケースは、更新が配列の境界に触れる場合です。 たとえば、私たちが適用すると、$[1, n, k]$、 のみ$d_1$がないので意味のある変化をする$d_{n+1}$、アルゴリズムは範囲外のインデックスへのアクセスを回避する必要があります。 実装は更新時に境界を明示的にチェックします。$r+1$、フェンウィックツリーの破損を防ぎます。 

もう 1 つは、重複した更新が繰り返される場合です。 高さ構造は差分ベースのフェンウィック ツリーを通じて維持されるため、重複する加算は再計算を必要とせずに正しく蓄積されます。 各更新は内部 BIT 状態に線形的に寄与し、境界の再計算により派生した差分の正確性が保証されます。 

最後のケースは、単一ポイントに対するクエリです。$[l, l]$。 式は戻り値に帰着します$h[l]$隣接関係が寄与しないため。 プレフィックスの差の合計がゼロになるため、実装ではこれを自然に処理します。
