 ## 解決策
 ## 問題の理解

 私たちには木箱が 2 段積み与えられました。 各クレートには 1 から n までの一意のラベルが付いています。ただし、0 というラベルが付いた 1 つの特別なクレートは除きます。これは「私たちのもの」であり、読み込み順序の一部ではありません。 初期構成は固定されています。各スタックの下から上の順序が通知されます。 

造船所は常に、1 から n までラベルの昇順で木枠を積み込みます。 クレート i をロードするには、システムはまず現在のスタック内でその上のすべてを一時的に削除し、それらのクレートを 1 つずつ他のスタックに移動し、転送順序を維持することによってクレート i を公開します。 アクセス可能になると、永久に削除されます。 

削除するたびに短い間隔があり、その間にクレート 0 がたまたまどちらかのスタックの一番上にあった場合、それを回復できます。 プロセス全体でこれが何回発生するかを数えるように求められます。 

主な問題点は、すべての操作で潜在的に大きなクレートのブロックがスタック間で再配置される可能性があり、これらの再配置は次の各クレート i が現在どこに存在するかによって決まることです。 n は大きくなる可能性があるため、スタックを繰り返しスキャンしたり、各移動をクレートごとに物理的にシミュレートしたりするアプローチは、時間内に終了しません。 構造は本質的に動的であり、ある位置でスタックを切断し、サフィックスを別のスタックに効率的に移動することをサポートする表現が必要です。 

微妙なエッジ ケースとして、クレート 0 はロードされないため削除されることはありませんが、他のクレートがその上に移動されるとスタック間を移動します。 答えは、スタック内の深い位置ではなく、各削除ステップの後に 0 が最上部で露出するかどうかによってのみ決まります。 

## アプローチ

 直接シミュレーションでは、文字通り 2 つのスタックが配列またはリストとして維持されます。 各 i について、その位置を検索し、その上にあるものをすべてポップし、それらのクレートを他のスタックにプッシュし、i を削除して、0 が一番上にあるかどうかを確認します。 i の検索がハッシュ マップを使用して最適化されたとしても、多くのクレートが繰り返し移動するため、最悪の場合、このアプローチは 2 次になります。 底部近くの 1 つのクレートでは、残りのほぼすべてのクレートを繰り返し移動させることができ、合計操作量は約 n² になります。 

構造上の観察は、各スタックが単なる山ではなく、順序付けられたシーケンスであり、すべての操作が 1 つのシーケンスを 2 つの部分に分割し、その後別のシーケンスにマージすることです。 これはまさに、暗黙的な treap など、暗黙的な順序を維持するバランスのとれたバイナリ構造によって処理できる種類の操作です。 

各スタックを下から上の順序でシーケンスとして表します。 各ノードはサブツリーのサイズを保存するので、インデックスによって位置を特定できます。 すべての操作で、現在のシーケンス内の i の位置を見つけ、シーケンスを 3 つの部分 (i より下の要素、i 自体、および i より上の要素) に分割します。 i より上のセグメントは、先頭でマージすることによってブロックとして他のスタックに移動されます。 クレート i は完全に削除され、残りの部分は元のスタックの新しい状態として残ります。 

これにより、各操作が一定数の分割とマージに変換され、それぞれの構造のサイズで対数時間がかかります。 重要な考え方は、個々のクレートの動きを決してシミュレートしないということです。 連続したセグメントのみを操作します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 直接シミュレーション | O(n²) | O(n) | 遅すぎる |
 | スタックごとの暗黙的トレプ | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 スタックごとに 1 つずつ、2 つの暗黙的トリープを維持します。 各 treap はクレートを下から上の順序で保存し、右端の要素がスタックの最上部を表します。 また、クレート 0 を表すノードへのポインタも保持しているので、それが公開されるかどうかをすぐに確認できます。

1. 初期スタックから 2 つのトレプを構築します。 各クレートはノードになり、順序どおりの走査は下から上の順序に対応します。 注文統計のためにサブツリーのサイズも保存します。 
2. 1 から n までの各 i について、現在 i を含むトリープを見つけます。 これは、各ノードからその treap ノードへの参照を保存し、親ポインタをルートまでたどることによって行われます。 
3. サブツリーのサイズを使用して、そのトリープ内の i のインデックスを計算します。 これにより、下から上の順序で正確な位置がわかります。 
4. トレプを i の位置で分割し、i までのすべてを含む左側の部分と、i より上のすべてを含む右側の部分に分割します。 右側の部分は、他のスタックに移動する必要があるすべてのクレートを表します。 
5. 左側の部分を再度分割して、i を単一のノードとして分離します。 これにより、システムから i が永久に削除され、下位セグメントのみが残ります。 
6. 下のセグメントをマージして、更新された元のスタックとして戻します。 
7. 上部のセグメントを取得し、ブロックとしての内部順序を維持しながら、その上部の他のスタックにマージします。 
8. すべての構造更新後、クレート 0 がいずれかの treap の右端のノードであるかどうかを確認します。 そうであれば、答えをインクリメントします。 

正確さは、各トリープが常に下から上の順序で 1 つの物理スタックを正確に表すという不変条件に依存します。 すべての操作は、i より上のサフィックスを切り取り、それを他のシーケンスに転送することに正確に対応します。 treap の分割とマージでは順序どおりの構造が維持されるため、クレートの相対的な順序が壊れることはありません。 クレート 0 は常にこれらのシーケンス内で追跡されるため、それが右端の位置にあるかどうかをチェックすることで、スタックの一番上にあるかどうかが正しくキャプチャされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("val", "prio", "left", "right", "parent", "size")
    def __init__(self, val, prio):
        self.val = val
        self.prio = prio
        self.left = None
        self.right = None
        self.parent = None
        self.size = 1

import random

def sz(t):
    return t.size if t else 0

def upd(t):
    if not t:
        return
    t.size = 1 + sz(t.left) + sz(t.right)
    if t.left:
        t.left.parent = t
    if t.right:
        t.right.parent = t

def split(t, k):
    if not t:
        return (None, None)
    if sz(t.left) >= k:
        l, r = split(t.left, k)
        t.left = r
        if r:
            r.parent = t
        upd(t)
        if l:
            l.parent = None
        return (l, t)
    else:
        l, r = split(t.right, k - sz(t.left) - 1)
        t.right = l
        if l:
            l.parent = t
        upd(t)
        if r:
            r.parent = None
        return (t, r)

def merge(a, b):
    if not a or not b:
        return a or b
    if a.prio < b.prio:
        a.right = merge(a.right, b)
        upd(a)
        return a
    else:
        b.left = merge(a, b.left)
        upd(b)
        return b

def get_root(x):
    while x.parent:
        x = x.parent
    return x

def get_index(x):
    res = sz(x.left)
    while x.parent:
        if x == x.parent.right:
            res += sz(x.parent.left) + 1
        x = x.parent
    return res

def get_rightmost(t):
    if not t:
        return None
    while t.right:
        t = t.right
    return t

def solve():
    n, s1, s2 = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    nodes = [None] * (n + 1)

    def build(arr):
        root = None
        for v in arr:
            node = Node(v, random.randint(1, 10**9))
            nodes[v] = node
            root = merge(root, node)
        return root

    root1 = build(a)
    root2 = build(b)

    ans = 0

    for i in range(1, n + 1):
        node = nodes[i]
        root = get_root(node)
        pos = get_index(node)

        left, right = split(root, pos)
        left_left, _ = split(left, pos - 1)

        new_root = merge(left_left, None)

        other_root = root2 if root == root1 else root1

        if root == root1:
            root1 = new_root
            root2 = merge(root2, right)
        else:
            root2 = new_root
            root1 = merge(root1, right)

        if get_rightmost(root1) and get_rightmost(root1).val == 0:
            ans += 1
        if get_rightmost(root2) and get_rightmost(root2).val == 0:
            ans += 1

    print(ans)

if __name__ == "__main__":
    solve()
```この実装は、暗黙的な treap に依存して、各スタックを順序付けられたシーケンスとして表現します。 Split 関数は位置によってプレフィックスを分離しますが、merge は順序を維持しながらスタックを連結します。 親ポインタは更新中に維持されるため、現在のスタックの検索とノードのインデックスの計算を対数時間で行うことができます。 

メインループはロード順にクレートを処理します。 各クレートについて、その位置を特定し、スタックをその上と下の部分に分割し、クレート自体を削除して、上部を他のスタックに移動します。 最後に、クレート 0 が現在どちらかのスタックの最上位にあるかどうかを確認します。 

よくある実装の落とし穴は、マージと分割後に親ポインターを維持するのを忘れることです。 親が正しく更新されないと、インデックス クエリが無効になり、構造全体が警告なしに壊れます。 

## 実用的な例

 最初のサンプル構成を考えてみましょう。 

2 つのスタックから開始し、昇順に木箱を処理します。 次の表は、各削除後にどのスタックが上部にクレート 0 を含むかという重要な状態のみを追跡します。 

| ステップ 1 | 作戦結果 | 0を含むスタックトップ | カウント |
 | --- | --- | --- | --- |
 | 1 | セグメントを 1 より上に移動、1 を削除 | なし | 0 |
 | 2 | 0 がスタックトップで公開される | スタック 1 | 1 |
 | 3 | 0 は断続的に露出したままになります。 スタック 1 | 2 |
 | 4 | 0 再配置後に再び露出 | スタック 2 | 3 |

 このトレースは、構造的変化の後に 0 がシーケンスの最後の要素になる時点によって答えが完全に決定されることを示しています。 

2 番目のサンプルでは、​​混合スタックの中で 0 がより深い位置から始まるため、動きがより頻繁になります。 削除するたびに異なる再配分パターンがトリガーされ、0 が交互のスタックの最上位に繰り返し出現し、複数のカウントに寄与します。 

ここで示されている重要な観察は、正確な完全な構成は決して必要ではなく、各操作の後にいずれかのシーケンスの右端で 0 が公開されるかどうかだけが必要であるということです。

 ## 特殊なケース

 クレート 0 が 1 つのスタックの奥深くに埋め込まれており、削除を繰り返すとスタック全体で大きなプレフィックスが継続的にシャッフルされる場合、重大なエッジ ケースが発生します。 このような場合、単純なシミュレーションでは要素を 1 つずつ繰り返し移動させると二次時間まで劣化してしまいますが、トレプベースのソリューションはそれぞれの大きな動きを単一の構造操作として処理します。 

もう 1 つのエッジ ケースは、削除直後の時点ですでに 0 がスタックの先頭にある場合です。 アルゴリズムは、すべての構造更新前ではなく、すべての構造更新後にチェックが行われるようにする必要があります。そうしないと、有効なエクスポージャーを見逃してしまう可能性があります。 

最後に、残りのすべての要素が 1 つのスタック内にあり、i がたまたま先頭かその近くにある場合、分割により非常に小さなセグメントが生成されます。 正確さは、空の分割結果を正しく処理できるかどうかに依存します。これは、None を ID として扱うマージによって保証されます。
