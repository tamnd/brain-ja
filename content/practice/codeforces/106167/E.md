 ## 解決策
 ## 問題の理解

 私たちには、都市 1 から都市 n まで、常に決まった順序で都市を通過するルートが与えられています。 都市 i と i+1 の連続するすべてのペアの間には、いくつかの代替道路があり、それぞれに 2 つの特性 (移動時間と最大サポート車両重量) があります。 

開始から終了までの 1 つの旅行は、i から i+1 までの各セグメントに対して 1 つの道路を正確に選択することで構成されます。 ただし、選択した道路は、車の重量がその道路の重量制限を超えない場合にのみ使用できます。 合計移動時間は、すべてのセグメントにわたって選択された道路時間を合計したものです。 

マップが修正されると、さまざまな重みを持つ多くの車が与えられます。 各車について、都市 1 から都市 n までの可能な最小合計移動時間を計算するか、有効な一連の道路が存在しないことを報告する必要があります。 

グラフの構造は重要です。それは階層化されています。 各層は固定遷移 i から i+1 に対応し、層間の選択は、各層が実行可能なエッジを 1 つだけ選択しなければならないというグローバル制約を除いて独立しています。 

制約が非常に厳しいため、クエリごとに応答を最初から再計算するソリューションは遅すぎます。 最大 100,000 のセグメント、100,000 の道路、および 100,000 のクエリがある場合、セグメントに対するクエリごとの線形スキャンでは約 10^10 の操作が必要となり、これは実行可能な制限をはるかに超えています。 セグメントごとのクエリごとのバイナリ検索でも、依然として遅すぎます。 

素朴な貪欲な考え方では、より微妙な問題が発生します。固定重みの場合、セグメントごとに最も安価なエッジを選択するのは正しいですが、これをクエリごとに個別に再計算すると、ほぼ同じ作業が繰り返されます。 重要なのは、クエリはエッジの重みに関するしきい値条件だけが異なるということです。 

エッジケースは、セグメントに重い車を支える道路がない場合に発生します。 このような場合、他のすべてのセグメントが問題なくても、答えは「不可能」でなければなりません。 もう 1 つの特殊なケースは、全体的に最も安い道路が重い車には使用できず、より高価ではあるが有効な道路にジャンプせざるを得なくなる場合です。 最後に、セグメントごとに複数の道路が容量範囲で重複する可能性があるため、慎重に扱わないと最適な選択は非単調に変化します。 

## アプローチ

 直接的なアプローチでは、各クエリを個別に評価します。 特定の車両重量に対して、すべてのセグメント i をスキャンし、少なくともその重量以上の容量を持つ道路の中から最小移動時間を選択します。 これらを合計すると答えが得られます。 これは正しいです。実現可能性が決まればセグメントは独立しているからです。 問題は実行時です。クエリごとに最大 100,000 のセグメントをスキャンする可能性があり、各セグメントでは複数の道路のスキャンが必要になる場合があります。 最悪の場合、これは 10^10 の演算になります。 

重要な観察は、実現可能性の重みが単調であるということです。 道路が重量 w に耐えられる場合は、それより小さな重量に耐えることができます。 これは、容量に基づいて並べ替えまたはスイープすることを示唆しています。 各クエリに個別に答える代わりに、関連するすべての変更を 1 回のパスで処理できます。 

セグメントごとに、利用可能な最適な道路はしきい値によって決まります。少なくとも w 以上の容量を持つすべての道路の中で、最小の時間が必要です。 w が減少すると、より多くの道路が利用可能になるため、各セグメントの最適値は時間の経過とともに向上するだけです。 

これにより、すべての道路をグローバルに検索し、容量や重量でソートされたクエリが実行されます。 容量の降順に道路をアクティブ化し、各セグメントでこれまでに記録された最高の時間を維持します。 クエリ重み w を処理するとき、容量 ≥ w のすべての道路はすでにアクティブであるため、維持された値により、維持された合計を介してセグメントごとに O(1) 時間で正しい答えが得られます。

 | 容量による最適なスイープ | O((n + m + q) log(n + q)) または O(n + m + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

私たちはすべての道路を、車両重量のしきい値がその許容量を下回ると使用可能になるイベントとして扱います。 また、各クエリを現在の最適な総移動時間を求めるイベントとして扱います。 

1. 各道路をその容量に関連付けられたイベントに変換します。 c. セグメント i からの時間 d の道路の場合、現在の重みしきい値が最大 c になったら、セグメント i の最もよく知られているオプションを改善するためにそれを使用する可能性があります。 これにより、実行可能な道路のみを考慮することが保証されます。 
2. 各クエリ重み w を、少なくとも w の容量を持つすべての道路が処理された後の現在の状態を尋ねるイベントに変換します。 そのときの答えが、まさにそのクルマにとっての最適なルートに相当します。 
3. 道路容量 c とクエリ重み w を均一に扱い、すべてのイベントをキーの降順に並べ替えます。 大から小への処理により、しきい値 w に達したときに、容量 ≥ w のすべての道路がすでに考慮されていることが保証されます。 
4. アクティブ化されたすべての道路のうち、セグメント i について現在わかっている最小移動時間を表す配列 best[i] を維持します。 最初は使用可能な道路がないため、すべてのエントリを無限大に初期化します。 
5. すべてのベスト [i] の現在の合計を維持します。 この合計は、現在アクティブ化されている道路セットでの最適なルートの合計移動時間を表します。 セグメントの最高値が向上すると、それに応じて合計を更新します。 
6. イベントを徹底的に調べます。 道路 (i, d, c) に遭遇したとき、d が改善する場合は best[i] を更新します。 クエリ w に遭遇したとき、すべてのセグメントが実行可能である場合は現在の合計を記録し、そうでない場合は、いずれかの best[i] がまだ無限である場合は不可能であると記録します。 

それが機能する理由は、単調な活性化特性に由来します。 スイープのどの時点でも、アクティブ化された道路のセットは、少なくとも現在のしきい値以上の容量を持つ道路です。 各セグメントについて、そのセグメントでアクティブ化されたすべての道路の最小時間を常に維持します。 実現可能性が決まれば、各セグメントの選択は独立しているため、これらの最小値の合計が制約の下での最適なパス コストとなります。 スイープにより、すべてのクエリで再計算なしで正しいアクティブ化されたセットが表示されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    edges = []
    for _ in range(m):
        i, d, c = map(int, input().split())
        edges.append((c, i - 1, d))  # 0-index segments
    
    q = int(input())
    queries = []
    for idx in range(q):
        w = int(input())
        queries.append((w, idx))
    
    events = []
    
    for c, i, d in edges:
        events.append((c, 0, i, d))  # road event
    
    for w, idx in queries:
        events.append((w, 1, idx, 0))  # query event
    
    events.sort(reverse=True)
    
    INF = 10**30
    best = [INF] * (n - 1)
    total = 0
    inf_count = n - 1
    
    res = ["" for _ in range(q)]
    
    for val, typ, x, d in events:
        if typ == 0:
            i = x
            if d < best[i]:
                if best[i] == INF:
                    inf_count -= 1
                    total += d
                else:
                    total += d - best[i]
                best[i] = d
        else:
            idx = x
            if inf_count > 0:
                res[idx] = "impossible"
            else:
                res[idx] = str(total)
    
    print("\n".join(res))

if __name__ == "__main__":
    solve()
```このコードは、すべての道路をアクティベーション イベントとしてエンコードし、すべてのクエリをスナップショット イベントとしてエンコードします。 容量を減らしてイベントを並べ替えることで、各クエリ時間におけるアクティブ セットの正確性が保証されます。 配列`best[i]`セグメントごとに最も安価な有効な道路を追跡しますが、`total`クエリごとに合計を再計算することを避けるために、合計を増分的に維持します。 

実装の微妙な詳細は、到​​達不能セグメントの処理です。 変数`inf_count`まだ有効な道路がないセグメントがいくつあるかを追跡します。 これにより、クエリごとに配列をスキャンすることがなくなり、各クエリが O(1) に保たれます。 もう 1 つの重要な詳細は、厳密に優れた道路が見つかった場合にのみ合計を更新することです。 そうしないと、改善を誤って二重にカウントしてしまうことになります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + m + q) log(n + q)) | すべてのエッジとクエリを一度ソートしてから、線形スイープ |
 | スペース | O(n + m + q) | セグメントおよびイベント リストごとに最適なデータを保存する |

 すべてのデータが単一のグローバル スイープで処理され、クエリごとの再計算が完全に回避されるため、このソリューションは制限内に問題なく収まります。

 ## 特殊なケース

 重大なエッジ ケースは、セグメントに最初から大型車が通行できる道路がない場合です。 スイープでは、十分に大容量のエッジが処理されるまで、best[i] が無限に留まるように見えます。 たとえば、互換性のあるエッジがアクティブ化される前にクエリが到着した場合、inf_count は正のままであり、答えは正確に「不可能」になります。 

もう 1 つのケースは、セグメントに多くの道路があり、時間は減少しますが、容量も減少する場合です。 このアルゴリズムにより、正しいしきい値で有効になる改善のみが適用されることが保証されるため、低容量の安価な道路が誤って高容量の要件を無効にすることはありません。 

最後の微妙なケースは、複数のクエリが同じ重みを共有する場合です。 イベントはまとめて並べ替えられるため、このようなクエリはすべてアクティブ化された道路の同じスナップショットを観察し、再計算なしで一貫した出力が保証されます。
