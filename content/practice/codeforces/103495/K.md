 ## 解決策
 ## 問題の理解

 整数のバイナリ表現を繰り返し追加することで、非常に大きなバイナリ文字列を構築しています。 

構築は単一の文字列「0」から始まります。 次に、すべての整数に対して$i \ge 1$のバイナリ表現を追加します。$i$現在の文字列の先頭にゼロを付けません。 したがって、グローバル文字列は長い連結のように見えます。$0, 1, 10, 11, 100, 101, \dots$完全な無限文字列には興味がありません。 代わりに、クエリごとに長さが与えられます。$k$、長さの接頭辞のみを考慮します$k$この無限の構造。 タスクは、そのプレフィックス内の文字「1」の最長連続ブロックの長さを計算することです。 

重要な点は、文字列が非常に速く成長するということです。 追加される各部分は短い場合でも、最大長のプレフィックスに達するには、追加される数字の数が必要です。$10^9$まだ数千万のオーダーです。 文字列全体を単純に構築することは、時間的にもメモリ的にも不可能です。 

この制約は、最大でも約$10^7$に$10^8$2 進数を 1 回のパスで処理し、理想的には各演算が非常に安価でなければなりません$O(1)$または$O(\log i)$。 

微妙な難しさは、答えが、ある数値のバイナリ表現内に到達する可能性があるプレフィックス カットに依存するという事実から生じます。$i$。 つまり、完全なブロック情報 (完全に含まれる数値) と部分ブロック情報 (最後の数値の内側) の両方をサポートする必要があります。 

よくある失敗例は、完全な文字列を構築しようとしたり、明示的に保存しようとしたりすることです。 たとえば、数字に到達することさえ$3 \times 10^7$はすでに 10 億近くの文字を生成しているため、文字列のリテラル構築はすぐにメモリ制限を超えます。 

もう 1 つの罠は、境界を越えた 1 の実行を無視することです。 たとえば、1 つのバイナリ ブロックのサフィックスが複数の 1 で終わり、次のブロックが 1 で始まる場合、最長ランは境界を越えて広がり、各ブロック内で独立して表示されるものを超える可能性があります。 

## アプローチ

 ブルートフォース手法では、バイナリ表現を 1 つずつ追加して文字列を明示的に構築し、次のプレフィックスをスキャンします。$k$最長の実行を計算します。 これは正しいですが、すぐには実行できません。 生成される合計の長さは次のとおりです。$10^9$文字列を保存することが不可能になり、複数のクエリに対して文字列を繰り返しスキャンするだけでも時間がかかりすぎます。 

重要な観察点は、文字列が増分的に構築され、連続するバイナリ表現間のローカルな遷移にのみ依存するということです。 完全な文字列は必要ありません。成長に応じて 3 種類の情報だけが必要になります。現在のプレフィックス内の 1 の最長の連続、1 の最長のサフィックス、およびプレフィックス全体が 1 で構成されているかどうかです。 

これにより、整数に対するストリーミング動的プログラミング アプローチが可能になります。 各整数について$i$、そのバイナリ表現を考慮し、以前の状態からグローバル統計を更新します。 各数値は最大でも約 30 ビットなので、それぞれを処理する$i$安いです。 

ただし、クエリは状況を複雑にします。$k$バイナリブロック内でカットされる場合があります。 これに対処するために、クエリを次の基準で並べ替えます。$k$そして累積長を維持しながら整数をスイープします。 クエリが現在のブロック内にある場合、次のバイナリ表現の部分統計を計算します。$i$必要なプレフィックス長までのみ。 

これにより、ローリング グローバル DP と一時的な番号ごとのプレフィックス分析の維持に問題が軽減されます。

 ## アルゴリズムのチュートリアル

 クエリは昇順に処理されます。$k$そして、整数に対して段階的に連結を構築します。$i = 1, 2, 3, \dots$。 

1. すべてのクエリを値で並べ替えます。$k$、出力再構築のために元のインデックスを保持します。 これにより、構築された文字列を 1 回だけスキャンすることが保証されます。 
2. 連結のすでに構築されているプレフィックスのグローバル状態を初期化します。 これまでの全長、構築されたプレフィックス全体での 1 の最長連続、1 の最長サフィックス、およびこれまでの文字列全体が完全に 1 で構成されているかどうかを示すフラグを維持します。 
3. 各整数について$i$、そのバイナリ表現をビットのリストとして計算します。 これは小さく、最大でも約 30 ビットなので、オンザフライで生成できます。 
4. このバイナリ文字列の 3 つのローカル プロパティを計算します。つまり、その中にある 1 の最長の連続、1 の最長のプレフィックスの連続、および 1 の最長のサフィックスの連続です。 これらは、ビットに対する 1 回の線形スキャンで計算できます。 
5. このバイナリ ブロックを追加して、グローバル状態を更新します。 新しい最良のランは、以前のベスト、現在のブロック内の最良、および前の文字列のサフィックスと現在のブロックのプレフィックスによって形成される可能な境界を越えたランの最大値です。 
6. グローバル プレフィックスおよびサフィックス情報を更新します。 新しい接頭辞の実行は、前の文字列全体がすべて 1 でない限り変更されず、その場合は現在のブロックに拡張されます。 新しいサフィックス run は、現在のブロックのサフィックス、または現在のブロックが完全に 1 の場合は前のサフィックスの拡張子のいずれかになります。 
7. 各整数を処理しながら$i$、このブロックを追加することでカバーされる範囲内にクエリが含まれているかどうかを確認します。 クエリがこのブロック内で終了する場合は、前のブロック内で完全に実行された最適な実行、カットオフまでの現在のバイナリ表現のプレフィックス内で実行された最適な実行、および可能な境界を越えた実行の 3 つの部分を組み合わせてその答えを計算します。 
8. バイナリ ブロック内の部分評価の場合、必要な位置までのプレフィックス統計を計算します。$t$のビット配列から直接$i$。 

### なぜ効果があるのか

 いつでも、文字列は完全なバイナリ ブロックと、場合によっては 1 つの部分ブロックを連結したものになります。 連続する 1 は、完全に 1 つのブロック内にあるか、完全に前の完全なブロック内にあるか、または 2 つの隣接するブロック間の 1 つの境界を正確に横切っています。 DP 状態は、内部最大値、プレフィックス動作、サフィックス動作という 3 つのケースすべてを評価するために必要な唯一の情報を正確に追跡します。 すべての更新では正しいプレフィックスとサフィックスの構造が保持されるため、更新が見逃されたり二重にカウントされたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def bits(x):
    return list(map(int, bin(x)[2:]))

def solve():
    T = int(input())
    queries = []
    for idx in range(T):
        k = int(input())
        queries.append((k, idx))

    queries.sort()

    ans = [0] * T

    best_global = 0
    pref_all = 0
    suff_all = 0
    all_ones = True
    total_len = 1  # s0 = "0"

    ptr = 0
    qn = len(queries)

    i = 1

    # handle initial string "0"
    while ptr < qn and queries[ptr][0] == 1:
        ans[queries[ptr][1]] = 0
        ptr += 1

    while ptr < qn:
        b = bits(i)
        m = len(b)

        # compute local stats
        local_best = 0
        local_pref = 0
        local_suff = 0

        cur = 0
        for x in b:
            if x == 1:
                cur += 1
                local_best = max(local_best, cur)
            else:
                cur = 0
        local_pref = 0
        for x in b:
            if x == 1:
                local_pref += 1
            else:
                break

        cur = 0
        for x in reversed(b):
            if x == 1:
                cur += 1
            else:
                break
        local_suff = cur

        # answer queries falling in this block
        while ptr < qn:
            k, idx = queries[ptr]
            if k <= total_len:
                ans[idx] = 0
                ptr += 1
                continue

            if k > total_len + m:
                break

            t = k - total_len

            best_inside_prefix = 0
            cur = 0
            for j in range(t):
                if b[j] == 1:
                    cur += 1
                    best_inside_prefix = max(best_inside_prefix, cur)
                else:
                    cur = 0

            pref_prefix = 0
            for j in range(t):
                if b[j] == 1:
                    pref_prefix += 1
                else:
                    break

            suff_prev = suff_all
            cross = suff_prev + pref_prefix if pref_prev := (pref_all == total_len and all_ones) else 0

            ans[idx] = max(best_global, best_inside_prefix, cross)
            ptr += 1

        # update global state
        cross_full = suff_all + local_pref
        best_global = max(best_global, local_best, cross_full)

        if all_ones:
            pref_all += m
        else:
            pref_all = pref_all

        if local_suff == m:
            suff_all += m
        else:
            suff_all = local_suff

        all_ones = all_ones and (local_suff == m and local_pref == m)

        total_len += m
        i += 1

    for x in ans:
        print(x)

if __name__ == "__main__":
    solve()
```このソリューションは、並べ替えられたクエリを同時に使用しながら、整数に対する単一のスイープを中心に構成されています。 バイナリ表現は整数ごとに生成され、すべての実行計算はその小さなローカル構造から派生します。 

重要な実装の詳細は、完全な文字列の保存を避けることです。 すべての計算は、小さなバイナリ リストまたは一定サイズのグローバル状態のいずれかで実行されます。 

最もデリケートな部分は、ブロック内のプレフィックスカットクエリを正しく処理することであり、再計算が必要になるのはカット位置までのみです。

 ## 特殊なケース

 重要なエッジ ケースは、プレフィックスのカットがブロック境界で正確に発生する場合です。 たとえば、カットがバイナリ表現の最後で正確に終了する場合、アルゴリズムは部分的な統計の再計算を回避し、代わりに純粋にグローバル DP 状態に依存する必要があります。 遷移ロジックはこれを保証します。$k = \text{total\_len}$部分処理に入る前に解決されます。 

もう 1 つのエッジ ケースは、次の形式の数値など、バイナリ ブロックが完全に 1 である場合です。$2^m - 1$。 この場合、プレフィックスとサフィックスのランは両方ともブロック長と等しく、境界を越えたマージが特に重要になります。 このアルゴリズムは、ローカルのプレフィックスとサフィックスの同等性を通じてフルワン ブロックを明示的にチェックし、グローバル状態への正しい伝播を保証します。 

最後のエッジケースは非常に小さなプレフィックスです$k \le 1$ここで、唯一の有効な部分文字列は最初の「0」です。 これらはバイナリ追加操作を処理する前に直接処理され、空または自明な状態に偶発的に伝播することがないようになっています。
