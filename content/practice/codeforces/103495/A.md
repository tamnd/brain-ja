 ## 解決策
 ## 問題の理解

 いくつかの独立したテスト ケースが与えられます。各テスト ケースは、2 つの同じ長さの「文字」行で構成されます。 各文字は、そのトーンをエンコードする数字で終わる短い文字列として表されます。 この数字によって、その文字がレベル トーン クラスに属するかオブリーク トーン クラスに属するかが決まります。 

タスクは、純粋にこれらのトーン クラスに基づいて 2 つのラインが非常に厳密な構造的関係を満たしているかどうかを確認することです。 まず、最初の行の各位置には 2 行目の相補的なトーン クラスが必要です。レベルはオブリークと一致し、オブリークはレベルと一致する必要があります。 次に、追加の境界制約があります。最初の行の最後の文字は斜めでなければなりません。これにより、位置ごとのルールが満たされると、2 行目の最後の文字が直ちに強制的に水平になります。 

制約は小さく、テスト ケースの数は最大 100、行の長さは最大 20 です。これにより、文字比較の合計数は最悪でも数千に制限されるため、単純な入れ子ループを使用したソリューションでも十分に高速であることがすぐにわかります。 

主なエッジ ケースは、トーン マッピングの誤解、または両方の条件が同時に成立する必要があることを忘れていることから発生します。 よくある間違いは、位置の反転のみをチェックして最後の文字の制約を忘れること、またはその逆です。 

具体的な失敗例としては、すべての位置が反転を満たしているが、最後の文字がルールに違反している場合があります。 たとえば、最初のラインの最後のトーンがレベルの場合、たとえ他のすべての位置が完全に一致していても、正しい出力は NO になります。 もう 1 つの微妙なケースは、行の長さが一致しないことですが、この問題は等しい長さを保証するため、追加の処理は必要ありません。 

## アプローチ

 単純なアプローチは、問題を文字通りに解釈することです。テスト ケースごとに、対応する文字のペアをすべて比較し、それらのトーン クラスを決定し、それらが反対であることを確認します。 その後、最後の文字の状態を個別に確認します。 これはルールを直接シミュレートしており、隠れた構造を見逃していないので正しいです。 

このアプローチのコストは、処理される文字の総数に比例します。 最大 100 個のテスト ケースと 1 行あたり 20 文字の場合、最大 2000 回の比較が実行されますが、これは無視できる程度です。 

分類ステップを簡素化する以外に意味のある最適化はありません。 重要な洞察は、問題全体が文字ごとの定数時間マッピングとテスト ケースごとの線形スキャンに帰着するということです。 トーンを 2 つのブール値クラスにマッピングしたら、残りは直接の整合性チェックです。

 ## アルゴリズムのチュートリアル

1. 各テスト ケースは独立しており、個別に検証する必要があるため、各テスト ケースについて、整数 n と 2 行のトークンを読み取ります。 
2. 各トークンの最後の文字を、トーン クラスを表すブール値に変換します。 数字 1 と 2 をレベル トーンとして扱い、数字 3 と 4 をオブリーク トーンとして扱います。 この正規化ステップは、問題を文字列処理から単純なブール比較に減らすため、重要です。 
3. 0 から n − 1 までのすべての位置を反復し、各位置について 1 行目と 2 行目のトーン クラスを比較します。 ルールでは、すべての位置でそれらが反対であることが要求されるため、ブール値の等価性はすべてのペアで失敗する必要があります。 
4. すべてのインデックス i について、toneA[i] がtoneB[i] と等しくないことを特に確認します。 これに違反するインデックスがある場合、その対は無効であると直ちに結論付けることができます。 
5. 1 行目の最後の文字が斜めであるという境界条件を別途検証します。 そうでない場合、他のすべての一致に関係なく、その対は無効になります。 
6. 位置ごとの条件と最後の文字の条件が両方とも成立する場合は YES を出力し、そうでない場合は NO を出力します。 

### なぜ効果があるのか

 このアルゴリズムは、各文字をレベルまたはオブリークのバイナリ状態に変換し、2 番目の行がすべてのインデックスで最初の行のビット単位の補数になるように強制します。 正確さは、問題の制約が純粋にローカルであるという事実から得られます。つまり、明示的にチェックされる最後の文字ルールを除いて、各位置は独立しています。 グローバルな依存関係がないため、すべてのローカル制約を満たすことで妥当性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def tone_is_level(token: str) -> bool:
    # last character is digit 1-4
    d = token[-1]
    return d == '1' or d == '2'

def solve():
    T = int(input())
    out = []

    for _ in range(T):
        n = int(input().strip())
        a = input().split()
        b = input().split()

        ok = True

        # check inversion condition
        for i in range(n):
            if tone_is_level(a[i]) == tone_is_level(b[i]):
                ok = False
                break

        # check last character constraint
        if tone_is_level(a[-1]):
            ok = False

        out.append("YES" if ok else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装ではまず、比較内で暗黙的に各トークンをバイナリ分類に変換します。 機能`tone_is_level`解析ロジックを分離し、文字列解析と条件チェックを決して混合しないようにします。 

不一致が見つかった場合、ループは早期に中断されます。これはオプションですが、実装をクリーンに保ち、不必要なチェックを回避します。 最後の文字ルールは位置ごとの検証とは独立しているため、ループの後に適用されます。 

微妙な点は、2 行目の最後の文字を明示的にチェックする必要がないことです。 1 行目の最後の文字が斜めで、すべての位置が正しく反転されている場合、2 行目の最後の文字は自動的に水平になるため、片側のみをチェックするだけで制約が完全に適用されます。

 ## 特殊なケース

 エッジ ケースの 1 つは、すべての位置が反転を満たしているが、最後の文字規則に違反している場合です。 このアルゴリズムは、最初の行の最後のトークンを明示的にチェックし、すぐに拒否して、正確さを保証します。 

もう 1 つのエッジ ケースは n = 1 です。この場合、両方の条件が 1 つのチェックにまとめられます。1 つのペアはトーンが反対であり、最初のペアは斜めである必要があります。 ループが 1 回実行され、最終チェックが無条件に適用されるため、アルゴリズムはこれを自然に処理します。 

最後の微妙なケースは、トーン解析が誤って解釈される場合です。 最後の文字のみを抽出してブール値にマッピングすることにより、アルゴリズムは、長さが任意に変化する可能性があるスペル接頭語への依存を回避します。
