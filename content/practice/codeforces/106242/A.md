 ## 解決策
 ## 問題の理解

 説明されているプロセスは、固定数の靴下から始めて、1 日に 1 足を履く人についてのものです。 毎日 1 ペアを永久に消費します。 特定の日、具体的には一定間隔ごとに新しい靴下が追加されますが、入手できるのは翌日からです。 問題は、最終的に使用可能な靴下がなくなるまでに、この 1 足の靴下を使用するこの日課を何日間続けることができるかを尋ねます。 

入力には 2 つの整数が与えられます。 1 つ目は、初日に利用できる靴下の初期数です。 2 番目の期間は、新しい靴下が追加される頻度を決定する期間で、常に特定の日の終わりに行われます。 出力は、翌日使用できる靴下がなくなるまでプロセスが継続する合計日数を表す単一の整数です。 

制約は小さく、値は最大約 100 です。 このことから、数日の線形シミュレーションで十分であることがすぐに分かります。なぜなら、数千ステップにわたる単純なループでさえ、時間制限の点では些細なことだからです。 O(n^2) を超えても安全ですが、プロセスの構造から重いものは必要ないことがわかります。 

微妙なエッジケースは、補充のタイミングによって発生します。 生理日の倍数日に購入した靴下はその日は使えず、翌朝からしか使えません。 これにより、誰かが誤って早めに新しい靴下を追加してしまうという、シミュレーションで 1 つずつずれたエラーが発生します。 

2 番目のエッジケースは、期間が初期在庫よりも大きい場合です。 この状況では、最初の補充は最初の靴下がすべて消費された後に行われるため、答えは完全に最初の補充が使用延長に間に合うかどうかによって決まります。 

## アプローチ

 この問題を考える素朴な方法は、毎日シミュレーションすることです。 最初の靴下の数から始めます。 1 つのペアが使用されるため、毎日カウントが減ります。 現在の日が指定された間隔の倍数である場合は常に靴下の数を増やしますが、購入は夕方遅くに行われるため、その日の靴下を消費した後でのみ行われます。 

このシミュレーションは実際のプロセスを正確に反映しているため、正確です。 ただし、両方のパラメータが小さい制約では、枯渇するまで実行したとしても、日数は大きくなりません。 最悪のケースは、補充によってプロセスが延長され続け、蓄積された在庫が消費されるまでループが続く場合です。 長さ m の各サイクルで靴下が 1 つ増えるため、成長は直線的で予測可能です。 

重要な観察は、靴下は 1 日あたり 1 枚という一定の割合で消費され、新しい靴下は定期的に到着するということです。 m 日ごとに、純利益は 1 靴下になります (m 靴下を消費し、1 足余分に受け取ります)。そのため、システムは定期的な補償を伴う線形減少プロセスのように動作します。 これにより、問題は、どれだけの完全なサイクルを維持できるか、そして最後の部分サイクルで何が起こるかを追跡することになります。 

毎日シミュレーションする代わりに、m 日単位でジャンプすることができます。 完全なブロックごとに m 個の靴下が消費されますが、次のサイクルでさらに 1 つの靴下が追加されます。 したがって、完全なブロックが完成するたびに、ストックは m - 1 ずつ減少します。残りのストックが別の完全なブロックを完了するのに十分でなくなるまでこれを繰り返し、その後、残りの日数を直接終了します。

 ## アルゴリズムのチュートリアル

1. 靴下の初期数と日数カウンターを 0 から開始します。 これは、消費が発生する前の最初のシステム状態をモデル化します。 
2. 次の補充日に到達するのに十分な靴下がある間に、長さ m の 1 つの完全なサイクルをシミュレートします。 各サイクルは m 日分の摂取に相当します。 
3. 完全なサイクルごとに、m 日間の使用が完了したため、日カウンタを m ずつ増やします。 
4. その日の使用量を考慮して靴下の数を m 減らし、サイクル日の終わりに新しい靴下を購入するため、すぐに靴下を 1 つ追加します。 これにより、遅延した補充効果が正確に把握されます。 
5. 残りの靴下が m 未満になったら、サイクル ループを終了し、残りの靴下を毎日消費し、日カウンターに直接追加します。 

正確さは、サイクルが完了するたびに、靴下の数が翌日の開始時に利用可能な未使用の靴下の数を正確に反映するという不変条件を維持することで得られます。 各完全なサイクルは一貫した方法で状態を変換します。m 回の消費と最大 1 回の補充が常に組み合わされるため、正味の変化は決定的です。 部分的なサイクルでは追加の補充を生成できないため、残りを個別に処理してタイムラインを正確に完了します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    days = 0
    
    while n >= m:
        cycles = n // m
        days += cycles * m
        n -= cycles * m
        n += cycles
    
    days += n
    print(days)

if __name__ == "__main__":
    solve()
```コードはサイクルベースの解釈に直接従います。 このループは、複数の完全な m 日ブロックを 1 つずつシミュレートするのではなく、一度に圧縮します。 表現`n // m`一度に抽出できる完全なサイクルの数を計算します。 各サイクルでは、靴下数が m ずつ減りますが、1 つ追加されます。これが理由です。`n += cycles`消費後に適用されます。 

よくある実装上の間違いは、全サイクル効果を考慮する前に靴下を更新することです。これにより、消費と補充のタイミングの関係が崩れてしまいます。 もう 1 つの微妙な問題は、補充が m 日目の消費後に行われることを忘れていることです。そのため、正味の効果は m を引いた後に処理されます。 

## 実用的な例

 ### 例 1

 入力:

 n = 2、m = 2

 | ステップ | n（ソックス）｜ 追加された日数 | アクション |
 | --- | --- | --- | --- |
 | 開始 | 2 | 0 | 初期状態 |
 | サイクル | 2 → 0 + 1 = 1 | +2 | 靴下を2枚消費し、1枚追加します。 
| 仕上げ | 1 | +1 | 残った靴下を使う |

 最終的な回答は 3 日です。 

このトレースは、靴下が 2 日後に完全に使い果たされても、補充により使用期間がさらに 1 日延長されることを示しています。 

### 例 2

 入力:

 n = 9、m = 3

 | ステップ | n（ソックス）｜ 追加された日数 | アクション |
 | --- | --- | --- | --- |
 | 開始 | 9 | 0 | 初期状態 |
 | サイクル 1 | 9 → 6 + 1 = 7 | +3 | 最初の 3 日間ブロック |
 | サイクル 2 | 7 → 4 + 1 = 5 | +3 | 2番目のブロック |
 | サイクル 3 | 5 → 2 + 1 = 3 | +3 | 3番目のブロック |
 | 仕上げ | 3 | +3 | 最終部分消費 |

 最終的な回答は 12 日です。 

この例は、各完全なサイクルで在庫が 2 ネットソックスずつ減少し、残りの在庫が別の完全なブロックに不十分になるまでプロセスが継続する定常状態の動作を示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n, m = map(int, input().split())
    
    days = 0
    while n >= m:
        cycles = n // m
        days += cycles * m
        n -= cycles * m
        n += cycles
    days += n
    return str(days)

# provided samples
assert run("2 2") == "3", "sample 1"
assert run("9 3") == "12", "sample 2"

# custom cases
assert run("1 2") == "1", "single sock, no refill before depletion"
assert run("10 1") == "10", "daily refill every day"
assert run("5 5") == "6", "exact one cycle boundary"
assert run("100 100") == "101", "single large boundary cycle"

 ## 特殊なケース

 初期在庫が補充間隔よりも小さい場合、ループは実行されません。 このアルゴリズムはすぐに毎日靴下をすべて消費することになりますが、使い果たされるまで新しい靴下が到着しないため、これは現実と一致します。 

間隔が 1 の場合、毎日、消費後に新しい靴下が生成されます。 このループでは、1 日あたり 1 つのネット ソックスが継続的に追加されるため、消費が常に最初に発生するため、シミュレーションは事実上、非減少システムに縮小され、依然として正しく進行します。 

初期在庫が間隔で正確に割り切れる場合、最後の完全なサイクルでは、単純な予想を超えて使用量をさらに 1 日延長する補充が生成され、サイクルベースの更新は特別なケースなしでこれをキャプチャします。
