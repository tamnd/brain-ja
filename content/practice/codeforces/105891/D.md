 ## 解決策
 ## 問題の理解

 初期値から始めます$v$、そして私たちに与えられるのは$n$操作。 各演算は実数による加算のいずれかです$x_i$、または何らかの係数による乗算$x_i$。 これらの操作の順序を任意に変更することができます。 順序を選択した後、次から順に適用します。$v$、一連の値を生成します$v_1, v_2, \dots, v_n$、ここでそれぞれ$v_i$を適用した後の値です。$i$- 番目に選択された操作。 

目的は、最終値を最大化することだけではなく、すべての中間値の合計を最大化することです。 演算を早期に適用するたびに、現在の値が引き継がれるため、後の多くのプレフィックス合計に影響を与えます。 このため、順序付けが重要になります。操作を先に配置すると、最終目標のより多くの項に寄与します。 

制約は小さく、$n \le 30$これは、あらゆる指数関数またはサブセットベースの推論が潜在的に実行可能であることを即座に示唆していますが、同時に、重い DP ではなくクリーンな構造的貪欲なソリューションが期待される可能性が高いことも示唆しています。 価値観$x_i$は浮動小数点数であり、乗算係数は常に 1 よりわずかに大きく、加算は正ですが大きくなる可能性があります。 弱い乗数と潜在的に大きな加算の間のこの非対称性が、繊細さの重要な原因です。 

素朴なアプローチでは、演算のすべての順列を試みることになりますが、$30!$は大きすぎます。 すべてのインターリーブまたはサブセットをシミュレートしようとしても、構造がなければ実行できません。 

加算と乗算を混合すると、微妙な特殊なケースが発生します。 たとえば、大きな加算と小さな乗算がある場合、乗算を先に配置すると、後のすべての値がわずかに増加する可能性があり、大きな加算を遅らせるよりも重要になる可能性があります。 逆に、たとえ乗数が小さくても、早期に大きな加算が優勢になる可能性があります。 この結合により、一貫したグローバルな順序付け原則を特定しない限り、単純なローカル推論は危険になります。 

## アプローチ

 ブルートフォースのアイデアは単純です。つまり、$n$操作を実行し、プロセスをシミュレートし、結果として得られるプレフィックス値の合計を計算します。 これは問題の定義に直接従うため、正しいです。 ただし、順列の数は増加します。$n!$でさえ天文学的な大きさです。$n = 30$、これは完全に使用できなくなります。 

重要な観察は、最終値を最適化しているのではなく、プレフィックス状態の合計を最適化しているということです。 各操作は、それが適用された瞬間だけでなく、将来のすべてのプレフィックスに影響します。 これにより、問題は、以前の位置の比重が厳密に高くなるという問題に変わります。 その構造を認識すると、演算を 2 つの動作クラスに分けることができます。加算は値を一定量増加させ、乗算はこれまでに蓄積されたすべてをスケールします。 

乗算は、将来のすべての加算と初期値を増幅するため、より早く出現するほど価値が高くなります。 加算は、それをさらにスケールできる乗算器が後からある場合、より早く出現するほど価値が高くなります。 これにより一貫した方向性が生まれます。乗算は「将来の質量」をできる限り増幅するために使用する必要があり、加算はできるだけ多くの乗算器から恩恵を受ける場所に配置する必要があります。 

乗数はすべて 1 より大きく、比較的 1 に近いため、その効果は単調で安定しています。 これは貪欲な構造につながります。最初に乗算を優先し、より強力な乗算が後続の構造をより多く増幅するように係数を減少させる順序で配置し、その後に加算を配置します。また、より大きな加算が初期の増幅フェーズからより多くの恩恵を受けるように、値が減少する順序で加算を配置します。 

これにより、問題はグローバルなスケジューリングの最適化から決定論的な順序付けルールに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n! \cdot n)$|$O(1)$| 遅すぎる |
 | 最適な貪欲な注文 |$O(n \log n)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 操作をそのタイプに基づいて 2 つのグループに分類します。 乗算演算では現在の値がスケーリングされ、加算演算では現在の値がシフトされます。 

次に、乗算演算を係数の降順に並べ替えます。 これにより、最も強力なスケーリング効果ができるだけ早く発生し、後続のすべての操作に対する影響が最大化されます。 

また、加算演算を値の降順に並べ替えます。 これにより、最大の加算ゲインが早期に現れ、その後の乗算の恩恵を受けることができます。 

最初にすべての乗算をソート順に配置し、次にすべての加算をソート順に配置して、最終的なシーケンスを構築します。 次に、初期値からプロセスをシミュレートします。$v$、すべての中間値の合計を累積します。 

なぜこれが機能するのかは、影響力がどのように伝播するかに根ざしています。 乗算はその後のすべてに影響し、将来の加算と累積されたベースの両方をスケーリングします。 したがって、乗算を遅延させると、増幅できる構造の量が厳密に減少します。 加算は、現在の値への寄与を除いて将来の演算に影響を与えないため、加算を先に配置すると、後続の乗数への影響が増大するだけです。 最終的な順序付けにより、両方の効果が同じ方向に整列され、隣接する要素が入れ替わることなく合計が向上することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, v = input().split()
    n = int(n)
    v = float(v)

    adds = []
    mults = []

    for _ in range(n):
        op, x = input().split()
        x = float(x)
        if op == '+':
            adds.append(x)
        else:
            mults.append(x)

    mults.sort(reverse=True)
    adds.sort(reverse=True)

    ops = [('m', x) for x in mults] + [('a', x) for x in adds]

    cur = v
    ans = 0.0

    for t, x in ops:
        if t == 'm':
            cur *= x
        else:
            cur += x
        ans += cur

    print(f"{ans:.10f}")

if __name__ == "__main__":
    solve()
```実装では、まず入力操作を 2 つのリストに分割します。 並べ替えは、前に導出した貪欲ルールに従って、各タイプ内で独立して行われます。 シミュレーションは簡単です。現在の値を維持し、すべてのプレフィックス結果を最終的な答えに累積します。 この順序により、すべての乗算が最大限の影響を及ぼし、すべての加算が将来のスケーリングから可能な限り利益を得るように配置されることが保証されます。

 ## 特殊なケース

 まれなケースは、追加のみがある場合です。 この場合、値による並べ替えは依然として正しいですが、すべての順列が累積増加の差の同じ構造を生成するため、無関係です。 アルゴリズムは乗算器 (存在しない) の後でも一貫してそれらを処理し、シミュレーションはプレフィックスの合計を正しく累積します。 

乗算のみがある場合は、係数を減少させる順序で順序付けることが重要です。 たとえば、$1.1$そして$1.05$、配置$1.05$まず、より強力な乗算器の増幅を低減し、その後のすべてのプレフィックス値を永続的に下げます。 並べ替えられた順序により、より強力な乗数がより早く適用されるようにすることで、この損失を回避します。 

1 つの大きな加算と多数の小さな乗算器を混合する場合、アルゴリズムはすべての乗算器を最初に配置するため、中程度の加算であっても複合スケーリングの恩恵を受けることができます。 逆にすると、加算は十分に増幅されず、後続のすべてのプレフィックス合計への寄与が減少します。
