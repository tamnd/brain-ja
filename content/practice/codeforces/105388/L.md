 ## 解決策
 ## 問題の理解

 私たちは、次々と届く一連の食事と対話しています。それぞれの食事にはマイナスではないカロリー値が含まれています。 私たちはいつでも食事を無視するか摂取するかのどちらかですが、摂取すると現在の「プレートセット」に恒久的に追加され、その総カロリー合計は決して1000を超えてはなりません。また、以前に摂取した食事を廃棄することもできますが、廃棄することを選択した時点ですでに皿に乗っていたものに限ります。 

次のように定義される隠れたベンチマーク値があります。 私たちが全知であり、同じ容量制約である 1000 を尊重しながら一連の食事の任意の部分を選択できる場合、蓄積できる最大の合計は、ある値 x になります。 私たちの目標は、自分自身の合計を最大化することではなく、オンラインでアイテムが表示され、入力が以前の決定に依存する可能性があるにもかかわらず、最終的に得られる合計が x の少なくとも 60 パーセントであることを保証することです。 

インタラクションの側面は、受信アイテムごとに即座に決定する必要があるという点でのみ重要であり、現在のセットの実現可能性を維持できるのは 1000 制限以下だけです。 

主な困難は、x がシーケンスを完全に知った状態でオフラインで定義されるのに対し、オンラインでは削除と容量の制約を伴う操作であることです。 

テスト ケースごとに n を最大 10^4 にできるという制約は、どの戦略も基本的に項目数が線形であり、項目ごとに一定または償却された一定の更新を行う必要があることを意味します。 ナップザックのような決定をステップごとにゼロから再最適化することを伴うものは、遅すぎます。 

大きなアイテムが遅れて表示される場合、微妙な特殊なケースが発生します。 たとえば、初期のアイテムが小さいものの多数ある場合、貪欲な戦略によりそれらが蓄積され、後で 1 つの大きなアイテムのために多くのアイテムを削除する必要が生じ、全体的な保持率が低下する可能性があります。 もう 1 つの障害モードは、オーバーフローまで常に受け入れ、その後最大の項目を任意に破棄することです。これにより、初期の構造が敵対的である場合、最適値の 40% 以上が失われる可能性があります。 

## アプローチ

 この問題のオフライン バージョンは、容量 1000 の古典的な 0-1 ナップザックです。ここで、x は選択したアイテムの達成可能な最良の合計です。 事前に配列全体を確認できれば、n の約 1000 倍の容量を超える動的計画法を使用してそれを解決することになりますが、これは実現可能です。 ただし、この設定では、x を計算する必要はありません。 オンラインで定数因数近似を保証することだけが必要です。 

単純なオンライン戦略は、現在のアイテムが適合する場合は常にそれを取得し、そうでない場合はスペースを空けるために何かを破棄することです。 これはすぐに悪化します。常に初期のアイテムを保持すると、将来の高価値の組み合わせがブロックされる可能性があります。 代わりに常に最大の項目を破棄すると、後から考えると最適な構造が破壊される可能性があります。 

重要な観察は、容量が小さく 1000 に固定されており、アイテムの値も 1000 によって制限されているということです。これは、密度タイプの制御を示唆しています。正確な構成を最適化する必要はなく、定数係数近似の下で最適なナップザックの動作に近い構造を維持するだけです。 

重要なアイデアは、選択された項目の管理されたマルチセットを維持することであり、容量を超えるたびに、可能な限り最良のサブセットと比較して保持される合計価値の証明可能な下限を維持する方法で、最も有用性の低い要素を破棄します。 削除を伴う境界付きナップザックで定数因数近似を実現する標準的な方法は、境界付きの「無駄」の不変条件を強制しながら、アイテムのサイズに貪欲に一致する構造を維持することです。

この問題では、すべての重みが値と同一であり、容量が小さいという事実を利用します。 テーブル上の項目の数は常に制限されていることを維持し、オーバーフローが発生した場合は、制約が復元されるまで最初に最小の項目を削除します。 容量 1000 未満の最適解では、すべてが 1 以上であればアイテムの総数は最大 1000 であり、当然大きなアイテムが値を支配するため、これで十分です。 最初に小さなアイテムを削除することで、解放された容量の単位当たりの損失を最小限に抑えることができます。 

戦略は決定論的であり、維持する不変式を除いて将来の目に見えない値に依存しないため、インタラクターの適応的な性質はこの推論を破ることはありません。

 ## アルゴリズムのチュートリアル

 現在取得されているアイテムのマルチセットを、挿入時間とその値によってインデックス付けして維持します。 また、現在の総額も維持いたします。 

入荷するアイテムごとに、次のように処理を進めます。 

1. 新しい項目の値を読み取り、それを暫定的に取得して構造に追加すると仮定します。 これは、項目を完全に無視すると、将来の高価値の組み合わせを見逃す可能性があるという事実を反映しています。 
2. アイテムをコンテナに挿入します。これにより、合計金額を追跡しながら、価値の低いアイテムを効率的に識別して削除できます。 
3. 合計が 1000 を超える場合は、合計が 1000 以下になるまで最小値の項目を繰り返し削除します。最小の項目を選択する理由は、それらが目的への貢献が最も少なく、実現可能性を回復する際の有害な犠牲が最も少ないためです。 
4. 対話型プロトコルでは現在テーブル上にある項目を明示的に削除する必要があるため、削除された項目に対応する破棄操作を出力します。 
5. 最後に、現在の項目をテーブル状態に含める場合は TAKE を出力します。現在の構造を維持することと比較して明らかに非効率である場合に含めない場合は IGNORE を出力します。 

これをより明確に見る方法は、ナップザックのような貪欲なパッキングの実行可能なプレフィックスを常に維持し、オーバーフロー修正が高密度構造を維持する枝刈りステップとして機能するということです。 

### なぜ効果があるのか

 維持される不変条件は、常に、現在選択されているアイテムの中で、より大きな値の構造を除外するという犠牲を払って、小さな合計値のサブセットが保存されないということです。 オーバーフローが発生するたびに、最も価値の低い項目が最初に削除され、解放された容量の単位当たりに失われる合計値が最小限に抑えられます。 最適なソリューションも容量 1000 によって制約されるため、システム的にこの戦略を一定の係数以上で上回ることはできません。大幅に異なる最適な梱包では、多くの小さなアイテムを大きなアイテムに置き換える必要がありますが、それらの大きなアイテム自体が同じルールの下で包含をトリガーすることになります。 これにより、維持されたソリューションがオフライン最適値の一定係数内に維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# We simulate a simple greedy structure:
# maintain all taken items in a list, and a running sum.
# when sum exceeds 1000, remove smallest items.

def solve():
    t = int(input())
    CAP = 1000
    
    for _ in range(t):
        n_line = input().strip()
        if not n_line:
            n_line = input().strip()
        n = int(n_line)
        
        items = []  # (value, id)
        total = 0
        alive = set()
        next_id = 1
        
        for i in range(1, n + 1):
            ai_line = input().strip()
            while ai_line == "":
                ai_line = input().strip()
            a = int(ai_line)
            
            # tentatively take item
            items.append([a, i])
            alive.add(i)
            total += a
            
            removed = []
            
            # fix overflow
            if total > CAP:
                # sort by value ascending for removal
                items.sort()
                idx = 0
                while total > CAP and idx < len(items):
                    v, j = items[idx]
                    if j in alive:
                        alive.remove(j)
                        total -= v
                        removed.append(j)
                    idx += 1
            
            # output removals
            if removed:
                print(len(removed), *removed)
            else:
                print(0)
            
            # always take current item in this construction
            print("TAKE")
        
        sys.stdout.flush()

t = int(input())
solve()
```この実装は、選択された項目の現在のセットをリストに保持し、それらの合計を追跡します。 新しいアイテムが到着すると、すぐに追加されます。 これにより合計が 1000 を超える場合は、値で並べ替え、実行可能性が回復するまで最小の項目を削除します。 

廃棄リストは、対話型プロトコルの要求どおりに正確に出力されます。 重要な点は、除去は現在保持されているアイテムに対応している必要があるため、生きているインデックスのセットを維持することです。 

この戦略では、修理後に常に現在のアイテムを受け入れます。 これにより、高額な遅延品を見逃すことがなくなり、修理手順の実行可能性が保証されます。 

## 実用的な例

 400、300、350、500 という短いアイテムのシーケンスを考えてみましょう。 

400以降はそれを受け取ります。 合計は400です。 

300以降はそれを受け取ります。 合計は700です。 

350以降はそれを受け取ります。 合計は1050となり容量を超えます。 最初に最小の項目を削除するため、300 が削除され、400 + 350 = 750 が残ります。 

500 の後にそれを取り、合計は 1250 になります。ここでも最小の項目を削除し、最初に 350 を削除し、次に 400 を削除して、500 を残します。

ここで、小さなアイテムが早い段階でフラッドするケースを考えてみましょう。1 が何度も繰り返され、その後に 1000 が 1 つ続きます。 

アルゴリズムは初期の値を蓄積しますが、それらは最小値であるため、大きなアイテムが到着するとすぐに削除されます。 最終状態は大きなアイテムによって支配され、オフラインの最適状態と一致します。

 ## 特殊なケース

 最初のエッジケースは、大きな値が現れるずっと前に、累積的に容量を超える小さな値が繰り返されることです。 たとえば、各 250 個のアイテムが 5 つあれば、容量が正確に満たされます。 アルゴリズムはそれらを順番に受け入れ、削除をトリガーしないため、制約に厳密に一致します。 

2 番目のエッジ ケースは、多数の小さなアイテムの後に到着する大きなアイテムです。 たとえば、1、1、1、1、1000 です。1000 に達すると、合計が容量を超え、すべての小さなアイテムが最初に削除されます。 このアルゴリズムにより、最終状態が 1000 値のアイテムになることが保証され、オンラインとオフラインの両方で最適になります。 

3 番目のエッジ ケースは、600、600、600 など、チャーンを繰り返し引き起こす中間値が交互に現れることです。最初の 2 つを取得した後、容量を超えて小さい方を破棄します。 3 番目の後は、再び 1000 未満の最良のサブセットのみを保持します。オーバーロードが発生するとすぐに値の低い要素が削除されるため、不変式により、構造的に悪い組み合わせが蓄積されることがなくなります。
