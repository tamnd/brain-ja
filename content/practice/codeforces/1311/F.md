 ## 解決策

 ## 問題の理解

 数直線上の点の集合が与えられます。 各点は、ある整数の位置から始まり、それぞれが独自の一定の速度で時間とともに永遠に移動します。 任意の 2 点を選択すると、位置が線形に変化するため、それらの距離は時間の経過とともに変化します。 

固定された点のペアの場合、特定の瞬間におけるそれらの距離ではなく、リアルタイムで到達する最小距離に興味があります。 2 つの点が交わる場合、その最小距離はゼロになります。 それ以外の場合、それらはある瞬間まで互いに接近し、その後再び離れ、相対的な距離が最小になる瞬間に最小値が発生します。 

タスクは、すべてのペアについてこの最小可能距離を計算し、すべてのペアを合計することです。 

この制約により、最大 200,000 ポイントが許可されるため、すべてのペアを明示的にチェックしたり、時間の経過とともに相互作用をシミュレートしたりするアプローチは即座に除外されます。 二次解には最悪の場合でも約 400 億ペアが含まれることになりますが、これは 2 秒での実行可能限界をはるかに超えています。 これにより、通常はソートとプレフィックス処理を使用して、各ポイントが構造化された方法で多くのペアに寄与するアプローチが推進されます。 

動きについて素朴に考えると、微妙な問題が現れます。 衝突をシミュレートしたり、初期位置でソートして局所的に推論したくなる誘惑に駆られますが、最小距離は位置と速度の両方に依存します。 最初は遠く離れていた 2 つの点は、後続の点の方が速い場合には後で出会う可能性がありますが、先頭の点が速い場合には近い 2 点は決して交わらない可能性があります。 

いくつかのエッジケースは、単純な推論が失敗する理由を明らかにします。 速度が等しい 2 点を考えます。 相対距離は決して変化しないため、最小値は単に初期ギャップになります。 時間の経過とともに彼らが出会ったり、再注文したりする可能性があると誤って仮定すると、彼らの貢献度を誤ってゼロに設定してしまうことになります。 

もう 1 つのケースは、速いポイントが遅いポイントより先に始まる場合です。 それらはすぐに発散するため、最小値は再び初期距離になります。 より速いポイントが常に「追いつく」と仮定するロジックは、ここでは失敗します。 

最後に、より速いポイントがより遅いポイントの後ろから始まる場合、それらはちょうど 1 回だけ出会う可能性があり、最小距離はゼロになります。 この動作を効率的に捉えることが最も難しい点です。 

## アプローチ

 ブルートフォース ソリューションでは、ポイントのすべてのペアが個別にチェックされます。 各ペアについて、距離が最小になる時間を計算します。 時刻 t における点 i と点 j の間の距離は次のとおりです。 

|x_i - x_j + t(v_i - v_j)|

 これは t の V 字型関数であり、最小値は t = 0 で発生するか、それらが満たされた場合に式がゼロになるときに発生します。 速度が異なる場合の集合時間を導き出し、それに応じて評価できます。 

ただし、すべてのペアについてこれを計算するには、O(n^2) の演算が必要です。 n = 200,000 の場合、これは完全に不可能です。 

重要な観察は、実際には時間を明示的に追跡する必要がないということです。 2 つの移動点間の最小距離は、それらの相対的な動きがそれらを近づけるかどうかによってのみ決まります。 位置によってポイントを分類すると、速度順序が「揃っている」ペアと「反対している」ペアに分けることができます。 

x_i < x_j の任意のペア (i, j) に対して、相対速度 v_i と v_j を定義します。 v_i <= v_j の場合、左の点が右の点を捉えていないため、距離は増加するか一定のままです。 最小値は単純に x_j - x_i です。 

v_i > v_j の場合、左の点のほうが速く、最終的には追いつきます。つまり、ある瞬間に距離がゼロに減少するため、寄与はゼロになります。 

したがって、問題は、v_i > v_j の「キャッチ ペア」を差し引いたすべてのペアにわたる初期距離の合計に帰着します。 これらの貢献を数えて蓄積する効率的な方法が必要です。

これは、古典的な反転スタイルの集計問題になります。位置によってソートされたポイントを処理し、速度に関するデータ構造を維持します。これにより、前のポイントの速度が大きいか小さいかを数えることができ、位置の差を効率的に蓄積できます。 

速度に関するフェンウィック ツリーと位置のプレフィックス合計を組み合わせることで、ポイントごとの対数時間での寄与を計算できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 遅すぎる |
 | 最適 (フェンウィック + ソート) | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、点を初期位置で並べ替えます。 これにより、すべてのペアが固定された左から右の順序で考慮されるため、寄与を一貫して解釈できます。 

次に、以前に確認されたポイントの速度にわたって構造を維持しながら、ポイントを左から右に処理します。 

1. すべての点を位置 x で並べ替えます。 

ソートにより順序が修正され、スイープでは任意のペア (i, j) について i が常に j の左側に配置されます。 
2. 各速度値とそれらの位置の合計について確認されたポイントの数を追跡するフェンウィック ツリーを維持します。 

広い範囲を処理するために速度を圧縮します。 
3. 位置の昇順に各点 j について、以前のすべての点 i < j に対する寄与を計算します。 

動きが存在しない場合のベースライン寄与は合計距離です。 

x_j * count_left - sum_left_positions。 
4. これらのペアのうち、左の点が追いつく場合 (v_i > v_j) を差し引きます。 

フェンウィック ツリーを使用して、v_j より大きい速度を持つ以前のポイントの数をクエリし、それに応じて寄与を調整します。 
5. 点 j を処理した後、それを Fenwick 構造に挿入します。 

重要な点は、すべてのペアごとの寄与が、位置と速度しきい値で分割されたカウントのプレフィックス合計に分解できることです。 

### なぜ効果があるのか

 点jを固定します。 以前のすべての点 i はペア (i, j) を形成します。 位置はソートされるため、常に x_i < x_j が成り立ちます。 このような各ペアの最小距離は、x_j - x_i (それらが決して交わらない場合) または 0 (i が j をキャッチした場合) です。 

成立条件は v_i > v_j です。 したがって、以前のすべての点のうち、v_j に対する相対速度によってそれらを分離するだけで済みます。 この分割が判明すると、時間をシミュレーションすることなく、すべての寄与が決定されます。 

フェンウィック ツリーは、正確にこのパーティション情報を増分的に維持し、各クエリが対話ポイントの正しいセットを反映していることを保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    n = int(input())
    x = list(map(int, input().split()))
    v = list(map(int, input().split()))

    pts = list(zip(x, v))
    pts.sort()

    vals = sorted(set(v))
    comp = {val: i + 1 for i, val in enumerate(vals)}

    fw_cnt = Fenwick(len(vals))
    fw_sum = Fenwick(len(vals))

    total = 0

    sum_x = 0
    cnt = 0

    for xi, vi in pts:
        idx = comp[vi]

        left_sum = sum_x
        left_cnt = cnt

        total += xi * left_cnt - left_sum

        cnt_leq = fw_cnt.sum(idx)
        sum_leq = fw_sum.sum(idx)

        cnt_gt = cnt - cnt_leq
        sum_gt = sum_x - sum_leq

        total -= cnt_gt * xi - sum_gt

        fw_cnt.add(idx, 1)
        fw_sum.add(idx, xi)

        sum_x += xi
        cnt += 1

    print(total)

if __name__ == "__main__":
    solve()
```このソリューションは、単一の左から右へのスイープを中心に構築されています。 変数`sum_x`そして`cnt`位置全体にわたるプレフィックス情報を維持し、会議がないと仮定してペアごとの合計距離を高速に計算できます。 

フェンウィック ツリーは、現在のポイントに対する速度に基づいて前のポイントを分割し、動きがマージを引き起こすペアを正確に減算できるようにします。 

よくある間違いは、両方の寄与がカウントだけではなくポジションの合計に依存することを忘れていることです。 もう 1 つは、現在のポイントを処理した後にフェンウィック構造を更新することです。これを含めるのが早すぎると、厳密な左から右への分割が壊れてしまうためです。

 ## 特殊なケース

 重要なエッジケースは、すべての速度が等しい場合です。 この状況では、どのペアも相対距離を変更しないため、答えは単にペアごとの位置の差の合計になります。 フェンウィック ツリーでは「キャッチ」ペアがまったく識別されず、減算も発生しないため、アルゴリズムはこれを正しく処理します。 

もう 1 つのエッジ ケースは、位置の順序が増加するにつれて速度が厳密に減少することです。 左側のすべての点は右側のすべての点よりも速いため、すべてのペアが一致します。 正解は 0 で、すべてのペアがキャッチ グループに分類され、完全に減算されるため、アルゴリズムはこれを達成します。 

3 番目のエッジ ケースは、速度が交互に変化する場合で、一部のペアは一致し、他のペアは一致しません。 フェンウィック ツリーの速度ベースの分割の構造により、各ペアが相対速度に基づいて独立して分類されるため、ペア間で干渉することなく混合動作が処理されます。
