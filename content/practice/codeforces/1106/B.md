 ## 解決策

 ## 問題の理解

 私たちは数種類の料理を提供するレストランを与えられました。 各タイプには現在の在庫があり、料理ごとに固定価格が設定されています。 客は次々に到着し、それぞれの客は特定の種類の料理を複数回要求します。 

レストランは、リクエストされた料理ごとに、在庫がある場合はリクエストされた種類を提供しようとします。 そのタイプが空の場合、レストランはすぐには失敗しません。 代わりに、まだ在庫が残っている世界的に最も安価な種類の料理を提供することに戻り、より小さな指数での関係を解消します。 何も利用できない場合、たとえいくつかの料理がすでに提供されていたとしても、顧客はすぐに去り、その顧客の費用全体はゼロになります。 

出力は、一連のリクエスト全体を処理した後、または在庫が完全になくなった場合は早期に停止した後、各顧客が支払った合計コストです。 

主な難点は、それぞれのリクエストが最大 1,000 万食分と大規模になる可能性があり、個々の料理を 1 つずつシミュレートすることができないことです。 最大 10 万人の顧客と 10 万の料理タイプがある場合、入手可能な最も安価な料理を繰り返し検索する単純なシミュレーションでは、時間がかかりすぎます。 

単純なアプローチでは、要求されたタイプがなくなるたびに、最小コストで利用可能な料理を繰り返しスキャンすることになります。 最悪の場合、各フォールバック クエリがすべてのタイプをスキャンし、二次的な動作が発生する可能性があります。 

顧客の注文中に在庫が完全になくなった場合、微妙なエッジケースが発生します。 たとえ飽きる前にいくつかの料理が提供されたとしても、合計コストは破棄されなければなりません。 たとえば、顧客が大量のアイテムを要求し、最後の数ステップで残りの在庫がすべて使い果たされた場合、最終的な答えは部分合計ではなくゼロになります。 

もう 1 つの注意が必要なケースは、要求されたタイプが空になり、最も安価なフォールバック タイプも提供のたびに動的に変更される場合です。 単純なアプローチでは、最小値が誤って再計算されたり、再計算の頻度が高すぎたりする可能性があります。 

## アプローチ

 ブルート フォース シミュレーションでは、顧客のリクエストを一度に 1 品ずつ処理します。 ユニットごとに、リクエストされたタイプに在庫があるかどうかを確認します。 そうでない場合は、すべてのタイプをスキャンして、最も安価な入手可能なタイプを見つけます。 これは正しいですが、非常に遅いです。 各顧客は最大 1,000 万件の料理をリクエストでき、毎回全種類をスキャンすると、およそ$O(m \cdot d_j \cdot n)$、それは完全に不可能です。 

重要な点は、実際にはすべての料理を個別に処理する必要はないということです。 重要なのは、何かが変化する前に、つまり要求された種類がなくなるか、残っている在庫がすべてなくなるまで、顧客が固定ソースから継続的にどれくらいの期間摂取できるかということです。 

これは、同じ種類の連続したサービングをグループ化し、常に現在最も安価な種類を提供するデータ構造を使用することを示唆しています。 コスト (およびタイブレーク用のインデックス) で順序付けされた最小ヒープにより、常に対数時間で次のフォールバック タイプを取得できます。 また、配列内の残りのカウントを維持し、古いヒープ エントリを無視します。 

顧客ごとに、要求されたタイプまたは世界で最も安価な入手可能なタイプのいずれかを繰り返し消費しますが、単一のステップではなく、一括して消費します。制限条件の 1 つが変更されるまで、ブロック内で可能な限り多くの消費を行います。 

主な改善点は、型が空になるたびにその型が再度使用されなくなり、各型が事実上 1 回削除されることです。 これにより、ヒープ操作が次の制限を受けるようになります。$O(n \log n)$全体。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(m \cdot n \cdot \max d_j)$|$O(n)$| 遅すぎる |
 | 最適 |$O((n + m)\log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 残り在庫を確保しております`r[i]`、費用`c[i]`、およびキーが付けられた現在使用可能なすべての型を含む最小ヒープ`(cost, index)`。 

顧客ごとに、要求をシミュレートしながら、完全に使い果たされてすでに「失敗」したかどうかを追跡します。 

1. 現在の顧客の回答を 0 とフラグとして初期化します。`dead = False`。 フラグは、顧客が完全枯渇イベントに遭遇したかどうかを記録します。 
2. それぞれについて`d_j`リクエストした料理：

 1. 要求されたタイプの場合`t_j`まだ在庫がある場合は、直接提供し、から 1 単位を減算します。`r[t_j]`。 通常はコストが加算されます。 
2. 空の場合は、入手可能な最も安価なタイプを見つける必要があります。 在庫のあるタイプが見つかるまで、繰り返しヒープからポップします。 この遅延削除により、厳密なヒープ構造の維持が回避されます。 
3. 有効なタイプが存在しない場合は、次のように設定します。`dead = True`それ以上提供しても何も貢献しないため、この顧客の処理を完全に停止します。 
4. それ以外の場合は、選択したフォールバック タイプの 1 ユニットを提供し、その在庫を減らします。 
5. そのタイプがゼロになっても、すぐには削除されません。 代わりに、将来のヒープポップでは無視されます。 
3. 終了後または早休憩後、`dead`が true の場合、最終的な答えは 0 です。 それ以外の場合は、累積コストを出力します。 

ヒープ クリーンアップの動作が遅い理由は、どのタイプもプラスのストックからゼロに一度しか移行しないため、各タイプが考慮から削除されるのは最大でも 1 回だけであるためです。 

### なぜ効果があるのか

 すべてのステップで、アルゴリズムは、使用可能なすべての型がヒープ内で正しく表現されるか、古いエントリとして安全に無視されるかのいずれかであるという不変条件を保持します。 ヒープは常に、正の残存在庫を持つタイプの中で現在有効な最も安価なタイプを生成します。 サービングごとに在庫が 1 単位ずつ減り、型は一度空になると再導入されないため、無効なヒープ ポップの数は型の総数によって制限されます。 これにより、合計操作を対数に保ちながら正確性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    c = list(map(int, input().split()))
    
    r = a[:]
    
    heap = []
    for i in range(n):
        heapq.heappush(heap, (c[i], i))
    
    for _ in range(m):
        t, d = map(int, input().split())
        t -= 1
        
        cost = 0
        dead = False
        
        for _ in range(d):
            if r[t] > 0:
                r[t] -= 1
                cost += c[t]
            else:
                while heap and r[heap[0][1]] == 0:
                    heapq.heappop(heap)
                
                if not heap:
                    dead = True
                    break
                
                price, idx = heap[0]
                r[idx] -= 1
                cost += price
        
        if dead:
            print(0)
        else:
            print(cost)

if __name__ == "__main__":
    solve()
```このコードは、コスト順に並べられたディッシュタイプのグローバル最小ヒープを保持します。 要求された型が使用できない場合、有効な型が見つかるまでヒープから空の型を繰り返し削除することでフォールバックを解決します。 

微妙な点は遅延削除条件です`r[heap[0][1]] == 0`。 項目がゼロになったときに項目を明示的に削除することはありません。 代わりに、それらが最上位に表示される場合にのみそれらをクリーンアップし、コストのかかるヒープ更新を回避します。 

顧客ごとのループは単純です。システムが完全に使い果たされない限り、コストが累積されます。完全に使い果たされた場合は、すぐにゼロが出力されます。

## 特殊なケース

 重大なケースは、要求されたタイプが最後のユニットまで常に利用可能であり、その後システムが完全に空になる場合です。 アルゴリズムは、フォールバックを試行した直後に枯渇をチェックするため、これを正しく処理します。 ヒープが空になると停止し、蓄積されたコストを破棄します。 

もう 1 つのケースは、前の最も安いタイプがなくなったため、最も安いタイプが動的に変更される場合です。 遅延ヒープ クリーンアップにより、古いエントリはアクセスされた場合にのみ削除されるため、アルゴリズムは、デクリメントのたびに明示的な更新を必要とせずに、常に現在の有効な最小値を取得します。
