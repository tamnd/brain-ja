 ## 解決策

 ## 問題の理解

 小文字で構成される文字列が与えられ、そこから文字を正確に削除することを繰り返します。$k$回。 各削除は固定ルールに従います。「a」から「z」までアルファベット順に文字をスキャンし、各文字について現在の文字列の左端にある文字を削除しようとします。 文字列内に存在する最初の文字によって、その操作でどの文字が削除されるかが決まります。 

これは、すべての操作で 1 文字だけが削除され、その時点で利用可能な最小のアルファベット文字の中で常に最も早い文字が削除されることを意味します。 この処理を行った後、$k$回、残りの文字列を出力します。 

重要な制約は、文字列の長さが最大であることです。$4 \cdot 10^5$そのため、各削除ステップ内で単純に文字列のスキャンや再構築を繰り返し行う方法では、速度が非常に遅くなります。 簡単なシミュレーション$k$最大でフルスキャン$n$文字がつながる$O(nk)$、到達できる$10^{11}$最悪の場合、操作が失敗し、通過できなくなります。 

初期の文字が複数出現する場合、微妙なエッジケースが現れます。 たとえば、次のような文字列では、`"babababa"`、各削除は更新された文字列に依存するため、3 文字の削除は、単に最初の 3 文字を削除したり、最小の 3 文字を個別に削除したりすることを意味するわけではありません。 削除するたびに構造が変化し、単純な事前計算では見逃すような方法で「左端の出現箇所」が移動します。 

## アプローチ

 ブルートフォース手法では、プロセスを直接シミュレートします。 それぞれについて、$k$操作では、文字列を左から右にスキャンして各文字をチェックし、各位置について、それが残りの文字列内で使用可能な最小の文字であるかどうかを判断します。 正しい文字が見つかったら、それを削除して文字列を再構築します。 

これはプロセスに正確に従っているため、これは正しいです。 ただし、削除するたびに現在の文字列全体をスキャンする必要がある場合があり、文字列の削除自体は$O(n)$注意深く管理しない限り。 横切って$k$ステップ、これは次のことにつながります$O(nk)$あるいはさらに悪いことに、両方が大きい場合には限界をはるかに超えてしまいます。 

重要な観察は、実際には完全な削除を段階的にシミュレートする必要がないということです。 代わりに、重要なのは、どの文字が削除され、どのような順序で選択されるかです。 各操作では常に左端の利用可能な「a」が選択され、それ以外の場合は「b」が選択されるなど、元のインデックスを保持しながら削除対象の文字を貪欲にマークすると考えることができます。 すべての正確なインデックスを特定したら、$k$文字が削除され、最終的な文字列の構築はそれらをフィルタリングする単一パスになります。 

これを効率的に行うために、26 のキュー (またはインデックスのリスト) を使用して各文字の位置を維持します。 各ステップで、キューが空ではない最小の文字を選択し、その最も古いインデックスを削除して続行します。 これは意思決定プロセスを直接シミュレートしますが、$O(1)$文字列を再スキャンしないため、削除ごとに償却されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nk)$|$O(n)$| 遅すぎる |
 | 最適 |$O(n + k)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 文字列自体を変更するのではなく、順序付けられた構造からインデックスを繰り返し選択して削除するという問題として再構成します。 

1. すべての文字のインデックスを、文字ごとに 1 つずつ、26 個の個別のリストに保存します。 これにより、元の順序が維持されます。 
2. それぞれについて$k$削除では、「a」から「z」までの文字を繰り返します。 空ではないリストが見つかるとすぐに、その最初の要素を削除します。 これは、「最初に使用可能なアルファベット文字の左端の出現」に正確に対応します。 
3. ブール配列でそのインデックスを削除済みとしてマークします。 
4. すべての操作が完了したら$k$削除の場合は、元の文字列をスキャンし、削除された位置をスキップして、最終的な文字列を再構築します。 

ステップ 2 が機能する理由は、各リストがすでにインデックスによってソートされているため、最初の要素は常に現在の状態でその文字の左端に出現するためです。 

### なぜ効果があるのか

 いかなる瞬間においても、アルゴリズムの選択は、まだ存在する最小の文字とその左端にある文字のみに依存します。 文字ごとのインデックス キューを維持すると、両方の順序制約が維持されます。つまり、各文字内ではインデックスが増加し、文字間では常にアルファベット順に検索されます。 したがって、この構造化スキャンで見つかった最初の利用可能なインデックスは、完全な文字列シミュレーションで生成されるものと正確に一致します。 インデックスは一度削除されると再表示されないため、今後の決定は進化する文字列と一致したままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    s = input().strip()

    pos = [[] for _ in range(26)]
    for i, ch in enumerate(s):
        pos[ord(ch) - 97].append(i)

    from collections import deque
    pos = [deque(p) for p in pos]

    removed = [False] * n

    for _ in range(k):
        for c in range(26):
            if pos[c]:
                idx = pos[c].popleft()
                removed[idx] = True
                break

    res = []
    for i, ch in enumerate(s):
        if not removed[i]:
            res.append(ch)

    print("".join(res))

if __name__ == "__main__":
    solve()
```コードは最初に 26 個のキューを構築し、各文字の出現がインデックスの昇順で格納されるようにします。 各削除ステップでは、「a」から「z」までスキャンし、最も古い有効な箇所を削除します。 の`removed`array を使用すると、元の構造を変更することなく、最終的な文字列を線形時間で再構築できることが保証されます。 

一般的な実装の落とし穴は、シミュレーション中に文字列から物理的に文字を削除しようとすることであり、これによりコストの繰り返しが発生します。 もう 1 つの微妙な問題は、「左端の出現箇所」が元の文字列ではなく現在の状態を基準にして定義されなければならないことを忘れていることです。 キュー構造はこれをきれいに解決します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(n + k)$| 各インデックスは 1 回挿入され、最大 1 回削除され、各削除では最大 26 文字がスキャンされます。 
| スペース |$O(n)$| 位置と削除マーカーを保存します |

 制約により、最大で次のことが許可されます。$4 \cdot 10^5$したがって、小さな定数係数による線形時間は制限内に問題なく収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    n, k = map(int, sys.stdin.readline().split())
    s = sys.stdin.readline().strip()

    pos = [[] for _ in range(26)]
    for i, ch in enumerate(s):
        pos[ord(ch) - 97].append(i)

    pos = [deque(p) for p in pos]
    removed = [False] * n

    for _ in range(k):
        for c in range(26):
            if pos[c]:
                removed[pos[c].popleft()] = True
                break

    return "".join(s[i] for i in range(n) if not removed[i])

# provided sample
assert run("15 3\ncccaabababaccbc\n") == "cccbbabaccbc"

# custom cases
assert run("1 1\na\n") == ""                      # single char removal
assert run("5 0\nabcde\n") == "abcde"            # no deletions
assert run("5 5\nddddd\n") == ""                 # all same char
assert run("6 2\nbbbaaa\n") == "bbaa"           # tie-breaking behavior
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1 1 a`| 空 | 最小限の削除 |
 |`5 0 abcde`|`abcde`| 何もしない場合 |
 |`5 5 ddddd`| 空 | ユニフォームキャラクター |
 |`6 2 bbbaaa`|`bbaa`| 左端の選択を修正 |

 ## 特殊なケース

 主なエッジケースは、初期のアルファベット文字が大量にインターリーブされている場合です。 次のことを考慮してください。 

入力:```
s = "ababab", k = 3
```段階的な動作:

 | ステップ | 選ばれた文字 | 削除されたインデックス | 残り |
 | --- | --- | --- | --- |
 | 1 | | 0 | ババブ |
 | 2 | | 2 | ババブ |
 | 3 | | 4 | BBB |

 各文字のキューは文字列の突然変異とは無関係に残りの出現を追跡するため、アルゴリズムは構造的変化の後でも「a」の削除を正しく続行します。 

もう 1 つの特殊なケースは、小さい文字がすべてプロセスの途中で使い果たされる場合です。 スキャンは再計算を必要とせずに自然に次の利用可能な文字に進み、初期の文字が完全に消えた場合でも正確性を保証します。
