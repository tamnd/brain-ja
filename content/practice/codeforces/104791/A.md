 ## 解決策
 ## 問題の理解

 私たちは、それぞれに一定量の水が入った同一のバケツから水が供給されるウォーター ディスペンサーを使用して、人々の列をシミュレートしています。 列に並んでいる人は皆、一定のリットル数を望んでいます。 ディスペンサーは満杯のバケツから始まり、次々と人々にサービスが提供されます。 サービス中に現在のバケットがなくなると、たとえ現在の担当者が要求量の受け取りを完了していなかったとしても、バケットは直ちに交換され、その交換は使用された追加のバケットとしてカウントされます。 このプロセスは、すべての人が処理されるまで続きます。 

課題は、物理的な意味で各人が実際に受け取る水の量を計算することではなく、このルールに従って全員に水を提供する際に消費されるバケツの数を数えるだけです。 

この制約により、テスト ケース全体で合計 100 万人までの人数が許可され、単純に実行した場合、各シミュレーション ステップの人数は線形になります。 各人のリクエストは最大 1000 リットル、バケツの容量は最大 1000 リットルであるため、総水流量は大きくなる可能性がありますが、重要な制限は、ユニットごとの消費量をシミュレートできないことです。 ソリューションは各ユーザーを一定時間内に処理する必要があります。 

素朴なアプローチでは、バケットの残り容量が一度に 1 リットルずつ減っていきます。 これは、1 つのテスト ケースに最大 10^6 人が必要となり、各人が最大 10^3 リットルを必要とし、最大 10^9 の操作が生成される可能性があるため、これはすぐに失敗します。これは時間制限をはるかに超えています。 

さらに微妙な間違いは、交代が途中で行われることを忘れることによって起こります。 たとえば、ある人が現在のバケツに残っている以上の水を必要とする場合、その人が継続してもバケツは交換され、カウントされます。 人を終えた後にのみチェックすると、バケットの数が過小評価されてしまいます。 

具体的な失敗シナリオとしては、容量 5 のバケツが 1 つあり、1 人が 6 リットルを必要とする場合です。 正解はバケツ 2 つです。最初のバケツは 5 リットルでなくなり、2 つ目のバケツは残りの 1 リットルに使用されます。 ユーザーが終了したときにのみバケット数を増加させる実装では、誤って 1 が出力されます。 

## アプローチ

 ブルートフォース シミュレーションでは、現在のバケツにどれだけの水が残っているかを追跡し、各人に必要なリットルを繰り返し減算します。 残量がゼロになるたびに、バケット数をインクリメントし、残量を C にリセットします。これはプロセスを正確に反映しており、正しいですが、リットルごとに実装すると遅くなりすぎます。 1 人ごとに実装し、段階的に減少量を確認したとしても、最悪のケースは O(水の合計単位) で、10^9 に達する可能性があります。 

重要な点は、個々のリットルをシミュレートする必要がないということです。 各人にとって、私たちは自分の需要が残りのバケツに収まるかどうかだけを気にします。 そうなった場合は、残りの容量を減らすだけです。 そうでない場合は、要求を満たすまでにバケット全体を何回交換する必要があるかを計算します。 

これにより、問題は 1 つの実行値、つまり現在のバケットの残りの容量を維持することに変わります。 各リクエストは直接適合するか、残りといくつかの完全なバケットを消費します。 これにより、各人を O(1) で処理できるようになります。

 ## アルゴリズムのチュートリアル

 これまでに使用されたバケットの数と現在のバケットの残りの容量という 2 つの変数を維持します。

1. すでにインストールされている完全なバケット 1 つから開始するため、バケット数を 1 に、残りの容量を C に初期化します。 これは、最初の使用で常に少なくとも 1 つのバケットが消費されるという事実を反映しています。 
2. 各人を順番に処理します。 それぞれの必要量 cᵢ について、残りの容量と比較します。 
3. cᵢ が残容量以下の場合は、残容量から cᵢ を引いて次の人に進みます。 現在のバケツにはこの要求を完全に満たすのに十分な水がまだあるため、これが機能します。 
4. cᵢ が残りの容量より大きい場合、現在のバケットがこの人のサービス中に使い果たされることに初めて気づきます。 したがって、このバケットを使用済みとしてカウントし、現在のバケットを終了した後にどれだけの需要が残っているかを計算します。 
5. cᵢ から残りの容量を減算し、バケット数を増やして、新しいバケットを補充します。 次に、整数除算 cᵢ // C を使用して、残りの需要を満たすために必要な追加バケットの数を計算します。そのような各バケットは完全に消費されているため、その商をバケット数に追加します。 
6. バケットをすべて使用した後に残り cᵢ % C がある場合は、もう 1 つのバケットを消費し、それに応じて残りの容量を設定します。 それ以外の場合、正確に分割した場合、最後のバケットは残り容量がちょうど 0 で終了します。 

重要なアイデアは、ユーザーの途中でバケットを切り替えると、残りの需要は、一連のバケット全体の消費と、場合によっては 1 つの部分的なバケットとして表現できるということです。 

すべての人々を処理した後、枯渇によりバケットが新たにインストールされるたびに、バケット数が反映されます。 

### なぜ効果があるのか

 すべてのステップで、アルゴリズムは、現在のバケットが部分的に使用されており、その残りの容量が前のユーザーにまだ割り当てられていないものであるという不変条件を維持します。 リクエストを処理するたびに、この残りの容量を減らすか、不足になった場合にのみ新しいバケットに置き換えます。 需要の各リットルは 1 回だけ計算され、バケットの境界を越えるたびにカウントが増加するため、バケットの総数はプロセス中にディスペンサーに補充される回数と正確に一致します。 各人が順番に処理され、バケットの枯渇が発生した時点ですぐに処理されるため、順序付けに曖昧さはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, C = map(int, input().split())
        c = list(map(int, input().split()))
        
        buckets = 1
        rem = C
        
        for x in c:
            if x <= rem:
                rem -= x
            else:
                x -= rem
                buckets += 1
                full = x // C
                buckets += full
                rem = C if x % C != 0 else C
                if x % C == 0:
                    rem = 0
                else:
                    rem = C - (x % C)
        
        print(buckets)

if __name__ == "__main__":
    solve()
```このソリューションは各テスト ケースを読み取り、1 つのバケットを初期化し、残りの容量を追跡します。 

条件分岐は、現在のリクエストが残りの水に適合するかどうかを処理します。 そうなった場合は、残りの容量を減らすだけです。 それ以外の場合は、現在のバケットの残りを消費し、残りの需要をバケット全体の使用量と、場合によっては部分的なバケットの使用量に変換します。 

微妙な部分も更新中`rem`部分的に消費した後は正しく使用してください。 需要がちょうどバケットの境界で終了した場合、残りの容量はゼロになります。つまり、次の人がすぐに補充をトリガーします。 それ以外の場合は、最後に部分的に使用されたバケットに残りのスペースを保存します。

 ## 特殊なケース

 重要なエッジケースは、個人の需要がバケットの境界と正確に一致する場合です。 たとえば、C = 3 でリクエスト シーケンス [3, 3] の場合、最初の人はちょうど 1 つのバケットを消費し、rem = 0 のままになります。2 人目はすぐに新しいバケットをトリガーする必要があります。 x % C == 0 の場合は常に剰余チェックによって rem が 0 に設定され、次の反復でシステムを空として扱うことが強制されるため、アルゴリズムはこれを処理します。 

リクエストが開始される前に残りの容量がすでにゼロになっている場合、別のエッジ ケースが発生します。 この場合、x > rem は即時置換ロジックをトリガーし、除算ロジックを続行する前にバケット数をインクリメントするため、アルゴリズムはあたかも新しいバケットが必要であるかのように正しく動作します。
