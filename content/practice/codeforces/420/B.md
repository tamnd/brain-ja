 ## 解決策
 ## 問題の理解

 開発者チームの会議ログがあり、各ログ エントリにユーザーのログインまたはログアウトが記録されています。 ログは会議の途中で開始または終了する可能性があるため、最初に録音されたメッセージの前に誰がオンラインであったかはわかりません。 私たちの目標は、チームリーダーの候補者をすべて見つけることです。 定義上、参加者がチャットに参加しているときは必ずリーダーが存在しなければなりませんが、ログは部分的なものであるため、記録されたセグメントの外に人が現れたり消えたりする可能性があります。 

正式には、各メッセージは「+ id」（番号を持つユーザー）のいずれかです。`id`ログイン済み）または「- ID」（ユーザーがログアウト済み）。 入力により得られるのは、`n`総ユーザー数と`m`メッセージ。 最初のメッセージでは最初にオンラインだったすべてのユーザーがキャプチャされない可能性があることを考慮して、他のユーザーがオンラインだったときにオンラインになっていた可能性のあるすべてのユーザーを特定したいと考えています。 出力は、このリーダー条件を満たす可能性のあるユーザーのリストです。 

制約は最大 10^5 のユーザーとメッセージです。 これは、O(n + m) よりも複雑なアルゴリズムは遅すぎる可能性があることを意味します。 すべてのユーザーとメッセージに対するネストされた反復では、最悪の場合、およそ 10^10 の操作が行われますが、これは実行不可能です。 したがって、理想的には単一の線形パスでログを効率的に処理する必要があります。 

ログが開始される前にログインしていた可能性があるユーザーのログアウトからログが始まる場合、微妙なエッジ ケースが発生します。 たとえば、最初のエントリが`- 2`、ユーザー 2 はログが開始される前から存在していた可能性があると想定する必要があります。 もう 1 つのエッジ ケースは、ユーザーがログアウトしない場合、または複数のユーザーがログアウトせずに連続してログインする場合です。 ログ内のメッセージをチェックするだけの単純なアプローチでは、これらのシナリオが見逃され、有効なリーダー候補が誤って除外される可能性があります。 

## アプローチ

 ブルートフォース手法では、すべてのユーザーを潜在的なリーダーとして試し、ログを最初から最後までシミュレートし、他のユーザーがオンラインであるときは必ずそのユーザーが常にオンラインであるかどうかを確認します。 毎回「オンライン」ユーザーのセットを維持し、リーダーの状態を確認できるため、これは原理的に機能します。 ただし、これには O(n * m) の操作が必要で、最悪の場合の入力では最大 10^10 に達し、明らかに遅すぎます。 

最適なアプローチを実現するための重要な洞察は、各ユーザーの制約を段階的に追跡することです。 具体的には、対応する以前のログインがないログアウトに気付いた場合、そのユーザーはログが開始される前にオンラインになっていたはずです。 同様に、ログ内ではアクティブではないが、ログアウトしているのが見られないユーザーもリーダーである可能性があります。 明らかにリーダーではないユーザーのセットを維持し、メッセージがリーダー条件に違反するたびにそれを更新することで、候補リストを O(n + m) 時間で効率的に絞り込むことができます。 候補の可能性を更新するには、メッセージと定数時間の集合演算を 1 回通過するだけでよいため、問題の構造によりこれが可能になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n * m) | O(n) | 遅すぎる |
 | 最適 | O(n + m) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 現在オンラインのユーザーを追跡するために空のセットを初期化します。 また、不可能なリーダー候補をマークするための配列を作成します。 当初、私たちはすべてのユーザーが潜在的なリーダーであると考えています。 
2. 最初のメッセージをスキャンします。 ログアウトの場合`- id`、 仮定する`id`ログが開始される前にオンラインだったので、それらをオンライン セットに追加します。 これにより、会議の途中でログが開始されるというエッジケースに確実に対処できます。 
3. 各メッセージを時系列順に繰り返します。 ログインの場合`+ id`、 マーク`id`オンラインとして。 ログアウトの場合`- id`、 取り除く`id`オンラインセットから。 
4. ユーザーがログインするときは常に、現在オンラインではない他のすべてのユーザーは、このログインが行われたときにリーダーが存在していなければならないため、この時点より前にリーダーになることはできません。 それに応じて不可能なリーダー配列を更新します。 
5. すべてのメッセージを処理した後、不可能とマークされていないユーザーが有効なリーダー候補となります。 それらを並べ替えて結果を出力します。 

機能する理由: 不変条件は、誰かがオンラインにいるときは常に、リーダー (存在する場合) がオンライン セットに存在している必要があるということです。 他のユーザーと同時にオンラインになっていないユーザーは、この不変条件を満たすことができないため、除外されます。 このロジックを段階的に適用し、最初のメッセージの前にオンラインだったユーザーを考慮することで、考えられるすべてのリーダー候補を捕捉します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
messages = [input().strip().split() for _ in range(m)]

online = set()
cannot_be_leader = [False] * (n + 1)
first_online = set()

# Handle initial logouts
for op, uid in messages:
    uid = int(uid)
    if op == '-':
        online.add(uid)

# Now we scan and mark impossible leaders
current_online = set(online)
for op, uid in messages:
    uid = int(uid)
    if op == '+':
        for user in range(1, n + 1):
            if user != uid and user not in current_online:
                cannot_be_leader[user] = True
        current_online.add(uid)
    else:
        current_online.remove(uid)

# Collect candidates
candidates = [i for i in range(1, n + 1) if not cannot_be_leader[i]]
print(len(candidates))
print(' '.join(map(str, candidates)))
```最初のループは、最初のイベントがログアウトであるというエッジ ケースを処理します。 2 番目のループは不変条件を維持します。リーダーは、他の誰かがオンラインであるときは常にオンラインでなければなりません。 現在オンラインではない他のユーザーをチェックすることで、不可能なリーダーを確実に除外します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m) | 各メッセージは 1 回処理されます。 オンラインのセット操作は平均 O(1) であり、不可能なリーダーのマーク付けは、ログインごとに最大でも n 人のユーザーに対して反復されます。 |
 | スペース | O(n + m) | メッセージの保存には O(m) が必要で、オンライン ユーザーと候補者の配列/セットには O(n) が必要です。 |

 n と m が最大 10^5 の場合、アルゴリズムは 1 秒以内に適切に実行され、O(n + m) のスペース使用量は 256 MB の制限を大幅に下回ります。

```最初のオンライン セットは {3} です。 ユーザー 1 がログインすると、ユーザー 2 はオフラインになるため、リーダーになることはできません。
