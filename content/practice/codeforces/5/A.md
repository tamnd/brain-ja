 ## 解決策
 ## 問題の理解

 一連のチャット サーバー イベントが与えられます。 ユーザーはチャットに参加したり、チャットから退出したり、メッセージを送信したりできます。 誰かがメッセージを送信するたびに、サーバーは送信者を含む現在チャット内にいるすべてのユーザーにそのメッセージを配信します。 

1 回のメッセージ配信のコストは、メッセージ テキストの長さになります。 あれば`k`チャット内のユーザー数とメッセージの長さは`l`、その後、サーバーが生成します`k * l`そのイベントの送信トラフィックのバイト数。 

タスクは、すべてのコマンドを処理し、生成される合計トラフィックを計算することです。 

入力は小さいです。 行数は最大 100 行で、各行の長さは最大 100 文字です。 単純なシミュレーションでも簡単に制限内に収まります。 高度なデータ構造や最適化のテクニックは必要ありません。 入力全体の線形スキャンで十分です。 

主な課題は、コマンドを正しく解析することです。 次の 3 つの形式があります。```
+name
-name
sender:message
```最初の文字は、これが追加操作であるか、削除操作であるか、メッセージであるかをすぐに示します。 

微妙な点は、送信者はトラフィックの計算には関係ないということです。 サーバーは、誰がメッセージを書いたかに関係なく、現在オンラインになっている全員にメッセージを送信します。 重要なのは 2 つの値だけです。```
current number of users
message length
```もう 1 つの簡単な間違いは、メッセージの長さを間違って計算することです。 長さにはコロンの後のテキストのみが含まれ、送信者名やコロン自体は含まれません。 

次の例を考えてみましょう。```
+Mike
Mike:hello
```メッセージの長さは`5`、 ない`10`。 

もう 1 つのエッジ ケースは、空のメッセージです。```
+Mike
Mike:
```メッセージの長さは`0`したがって、追加されるトラフィックも`0`たとえ1人のユーザーがそれを受け取ったとしても。 

不用意に実装すると、誤って分割されたり、すべてのメッセージにコロンの後に少なくとも 1 文字が含まれていると想定されたりする可能性があります。 

バグを引き起こすもう 1 つの状況は、ユーザー数が間違った順序で更新されることです。```
+Mike
-Mike
Mike:hello
```マイクはチャットに参加していないため、この入力は保証によれば無効です。 このステートメントは、そのようなケースが決して起こらないことを保証するため、検証ではなく純粋にシミュレーションに集中できます。 

## アプローチ

 この強引なアイデアは、セット内のすべてのオンライン ユーザーを明示的に追跡することです。 メッセージが表示されるたびに、現在オンラインのすべてのユーザーを反復処理し、ユーザーごとに 1 回メッセージの長さを追加できます。 

サーバーは実際にすべての参加者に 1 つのコピーを送信するため、このアプローチは正しいです。 あれば`k`ユーザー、すべてを反復する`k`ユーザーは実際のプロセスを正確にシミュレートします。 

問題は、私たちが不必要な仕事をしていることです。 この問題では、誰が受信したかではなく、送信されたバイトの総数のみが求められます。 ユーザーを数えるためにすべてのユーザーを反復処理すると、すでに知っている情報が繰り返されます。 

重要な観察は、すべての受信者がまったく同じメッセージを受信するということです。 各配信を個別にシミュレートする代わりに、以下を掛け合わせることができます。```
traffic added = online_users * message_length
```これにより、各メッセージ操作がすべてのユーザーに対する反復処理から定数時間の計算に減ります。 

最大 100 個のコマンドであれば、ブルートフォース ソリューションでも問題なく通過できます。 それでも、最適化されたバージョンはよりクリーンで、問題の実際の構造を直接表現しています。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 承認済み |
 | 最適 | O(n) | お(1) | 承認済み |

 ここ、`n`コマンドの数です。 

## アルゴリズムのチュートリアル

 1. 2 つの変数を初期化します。`users = 0`現在のチャット参加者数、および`answer = 0`送信トラフィックの合計。 
2. EOF まで入力を 1 行ずつ読み取ります。 
3. 行が次で始まる場合`'+'`、 増加`users`による`1`。 

新しい人がチャットに参加したため、今後のメッセージはさらに 1 人の受信者に配信されます。 
4. 行が次で始まる場合`'-'`、 減少`users`による`1`。 

そのユーザーはチャットから退出したため、今後メッセージが届く人は 1 人減ります。 
5. それ以外の場合、その線はメッセージを表します。 

結腸の位置を調べる`':'`。 それ以降はすべてメッセージ テキストです。 
6. メッセージの長さを次のように計算します。`len(line_after_colon)`7. 以下を追加します。`users * message_length`に`answer`。 

すべてのオンライン ユーザーはメッセージのコピーを 1 つ受信するため、送信される合計バイト数はまさにこの積となります。 
8. すべての行を処理した後、印刷します。`answer`。 

### なぜ効果があるのか

 このアルゴリズムは、実行を通じて 1 つの不変式を維持します。```
users = number of people currently inside the chat
```追加および削除操作では、コマンドに従って正確にこの値が更新されます。 メッセージが表示されるたびに、現在の参加者全員がメッセージのコピーを 1 つだけ受け取ります。 メッセージの長さは`l`そしてそこにあります`users`参加者、そのイベントによって追加されたトラフィックは正確に`users * l`。 

すべてのコマンドが順番に処理され、すべてのメッセージの寄与が 1 回だけカウントされるため、最終的な合計が正しい合計送信トラフィックになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

users = 0
answer = 0

for line in sys.stdin:
    line = line.rstrip('\n')

    if line[0] == '+':
        users += 1

    elif line[0] == '-':
        users -= 1

    else:
        colon = line.find(':')
        message = line[colon + 1:]
        answer += users * len(message)

print(answer)
```この解決策は、前述のシミュレーションに直接従います。 

変数`users`現在オンラインになっている人の数を保存します。 追加コマンドと削除コマンドは常に有効な順序で実行されるため、このカウンターを増減するだけで十分です。 実際にはユーザー名を保存する必要はありません。 

メッセージ行の場合、重要な部分はメッセージ テキストのみを抽出することです。 送信者名がバイト数に影響しないようにしてください。 使用する`find(':')`セパレータの位置とスライス位置を指定します。`colon + 1`実際のメッセージを抽出します。 

使用する`rstrip('\n')`入力読み取りによって追加された末尾の改行を削除します。 これがないと、改行文字によってメッセージの長さが誤って 1 つ増加します。 

このアルゴリズムは各行を 1 回だけ処理し、コマンドごとに定数時間の作業のみを実行します。

## テストケース```python
# helper: run solution on input string, return output string
import sys, io

def solve():
    users = 0
    answer = 0

    for line in sys.stdin:
        line = line.rstrip('\n')

        if line[0] == '+':
            users += 1

        elif line[0] == '-':
            users -= 1

        else:
            colon = line.find(':')
            message = line[colon + 1:]
            answer += users * len(message)

    print(answer)

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    output = sys.stdout.getvalue().strip()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return output

# provided sample
assert run(
"""+Mike
Mike:hello
+Kate
+Dmitry
-Dmitry
Kate:hi
-Kate
"""
) == "9", "sample 1"

# single user, single message
assert run(
"""+A
A:test
"""
) == "4", "basic case"

# empty message
assert run(
"""+Ann
+Bob
Ann:
"""
) == "0", "empty message"

# multiple users receive same message
assert run(
"""+A
+B
+C
A:abc
"""
) == "9", "3 users * length 3"

# user leaves before next message
assert run(
"""+A
+B
-B
A:hello
"""
) == "5", "correct user count after removal"
```| テスト入力 | 期待される出力 | 検証内容 |

 | 1 人のユーザーが 1 つのメッセージを送信します | 4 | 基本的なメッセージの計算 |
 | 空のメッセージ テキスト | 0 | 長さゼロのメッセージの正しい処理 |

 ## 特殊なケース

 空のメッセージの場合を考えてみましょう。```
+Ann
+Bob
Ann:
```最初の 2 つのコマンドの後、`users = 2`。 コロンの後のメッセージ テキストは空の文字列であるため、その長さは次のようになります。`0`。 

アルゴリズムは以下を計算します。```
2 * 0 = 0
```最終的な答えは残っています`0`、それは正しいです。 

次に、メッセージの解析を慎重に検討してください。```
+Mike
Mike:hello
```行全体の長さが次より長いです`5`、ただし後の部分文字列のみ`:`カウントします。 アルゴリズムはコロンの位置を見つけて抽出します。`"hello"`のみ。 

貢献度は次のようになります。```
1 * 5 = 5
```行全体の長さを使用して不注意に実装すると、間違った答えが生成されます。 

最後に、参加と脱退による受信者の数の変更について考えてみましょう。```
+A
+B
-B
A:abc
```後`+A`、ユーザーは`1`。 

後`+B`、ユーザーは`2`。 

後`-B`、ユーザーはに戻ります`1`。 

いつ`"abc"`が送信されると、参加者は 1 人だけがオンラインになるため、追加されるトラフィックは次のようになります。```
1 * 3 = 3
```ユーザー カウンターは各コマンドの直後に更新されるため、アルゴリズムはこれを正しく処理します。
