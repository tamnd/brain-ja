 ## 解決策
 ## 問題の理解

 電卓の表示は 3 行のテキスト描画であり、すべての文字が 3 x 3 の固定領域を占めます。 画面には数字、プラス記号またはマイナス記号、最後の等号が含まれています。 隣接するシンボルは 1 つの空白列で区切られます。 タスクは、書き込まれた算術式を復元し、表示された演算を使用して左から右に評価し、式を通常のテキスト形式で出力し、等号の後に結果を出力することです。 

入力サイズは 3 つの表示行の幅によって測定され、1000 文字に達する場合があります。 これは、画面全体に数百個のタイルしか含まれていないことを意味するため、アルゴリズムはすべての文字を一定の回数だけ処理する必要があります。 各タイルの多くの解釈を試みたり、式全体を繰り返しスキャンしたりするアプローチは不要です。 

個々の数値の値は十分小さいため、通常の整数演算で十分です。 主な困難は計算ではなく、7 セグメント形式の記号を正しく認識することです。 

いくつかの詳細により、単純な実装が損なわれる可能性があります。 先頭のマイナス記号は実数演算子であり、最初の数値の一部ではありません。 たとえば、次のような表示が表示されます。`-10-7=`にならなければなりません`-10-7=-17`、 ない`10-7=-3`。 もう 1 つの問題は等号です。 その後に式がないため、見つかったらすぐに解析を停止する必要があります。 3 番目の問題は、数値に複数の桁が含まれる場合があるため、演算または等号が表示されるまで、認識されたすべての桁を現在の数値に追加する必要があることです。 

## アプローチ

 直接的なアプローチでは、考えられるすべての 3 列ブロックをすべての既知のシンボルと比較しようとします。 数字が 10 個しかなく、演算子が数個しかないため、このブルート フォース パーサーはすでに正確です。 考えられる記号が非常に少ないため、問題は比較の数ではありませんが、不注意な実装では、式を分割しようとしながら画面全体を繰り返し検索するという間違いを犯すことがよくあります。 幅が 1000 の場合でも高速に作成できますが、入力の構造は使用されません。 

有益な観察は、表示がすでに独立したタイルに分割されていることです。 各タイルの幅は固定されており、区切り列は常に空白です。 これは、問題全体がタイルを 1 回通過するだけで済むことを意味します。 タイルはすぐにシンボルに変換でき、結果の文字列は構築中に評価できます。 

算術部分はさらに単純化されています。 式には加算と減算のみが含まれるため、優先順位の処理はありません。 トークンが回復されると、その値は、後続の各数値に現在の符号が適用された単なる累積合計になります。

 ここで、W は 3 つの入力行の幅です。 最適なソリューションは、クリーンなタイルごとのパーサーです。 

## アルゴリズムのチュートリアル

 1. 3 つの表示行を読み取り、同じ長さになるように埋め込みます。 入力はすでに完全な画面を表しているため、行を整列させておくと、すべてのタイルが列の位置によって抽出されます。 
2. 画面を左から右に移動し、完全に空の列をスキップします。 これらの列は、シンボル間の区切り文字にすぎません。 
3. 空ではないすべてのタイルについて、3 行すべてから次の 3 列を取り出し、結果として得られる 3 x 3 パターンを既知の数字および演算子のパターンと比較します。 これにより、グラフィック表現が通常の文字に変換されます。 
4. 認識された文字から式文字列を構築します。 等号に達したら、それ以降のすべてが存在しないため停止します。 
5. 文字をスキャンして、復元された式を評価します。 現在読み取られている現在の符号と数値を維持します。 演算子が表示されたら、前の数値とその符号を加算し、次の数値の符号を更新します。 
6. 復元された式を出力し、等号の後の最終値を出力します。 

正確さは、すべてのシンボルが 1 つの独立したタイルを正確に占有するという事実から得られます。 区切り文字がすべての境界を定義するため、パーサーは数字の終わりを推測することはありません。 タイル辞書には考えられるすべての記号が含まれているため、抽出されたすべてのタイルは最初に表示された文字とまったく同じに変換されます。 評価フェーズでは、現在の符号が次の項を記述する一方で、累積値が完全に処理されたすべての項の値に等しいという不変条件が保持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

patterns = {
    "0": (" _ ", "| |", "|_|"),
    "1": ("   ", "  |", "  |"),
    "2": (" _ ", " _|", "|_ "),
    "3": (" _ ", " _|", " _|"),
    "4": ("   ", "|_|", "  |"),
    "5": (" _ ", "|_ ", " _|"),
    "6": (" _ ", "|_ ", "|_|"),
    "7": (" _ ", "  |", "  |"),
    "8": (" _ ", "|_|", "|_|"),
    "9": (" _ ", "|_|", " _|"),
    "+": ("   ", " _ ", "|_|"),
    "-": ("   ", "___", "   "),
    "=": ("   ", "___", "___"),
}

decode = {v: k for k, v in patterns.items()}

def solve():
    rows = [input().rstrip("\n") for _ in range(3)]
    width = max(map(len, rows))
    rows = [row.ljust(width) for row in rows]

    expr = []
    col = 0
    while col < width:
        if all(rows[r][col] == " " for r in range(3)):
            col += 1
            continue

        tile = tuple(row[col:col + 3].ljust(3) for row in rows)
        expr.append(decode[tile])
        col += 3

    expr = "".join(expr)

    value = 0
    current = 0
    sign = 1
    for ch in expr:
        if ch.isdigit():
            current = current * 10 + int(ch)
        else:
            value += sign * current
            current = 0
            sign = 1 if ch == "+" else -1
    value += sign * current

    print(expr + "=" + str(value))

if __name__ == "__main__":
    solve()
```辞書には、考えられるすべてのシンボルの正確な 3 行の描画が保存されます。 これにより、解析中に手動でセグメントを再構築しようとすることが回避されます。 入力がパディングされるのは、最終タイルが正確に最後の文字で終了する可能性があり、現在の行の長さを超えてスライスすると一貫性のないタプルが生成されるためです。 

パーサーはシンボルを読み取った後、3 列ずつ進みます。 空白区切り文字は別個に処理されるため、ギャップを別の文字として扱う危険はありません。 加算と減算のみが存在するため、評価器にはスタックや優先順位ルールは必要ありません。 現在の数値は桁ごとに累積され、演算または式の終わりに達した場合にのみコミットされます。 

## 実用的な例

 最初のサンプルでは、復元されたタイルが次の式を形成します。`1+2`。 

| ステップ | タイル | デコードされた式 | 現在値の状態 |
 | --- | --- | --- | --- |

 | 3 | 2 桁目 |`1+2`| 現在の数値 = 2 |

 トレースは、オペレーターが前の数値を即座に確定したことを示しています。 パーサーは数値の長さを事前に知る必要はありません。 

2 番目のサンプルでは、​​式に減算と 2 桁の数値が含まれています。 

| ステップ | タイル | デコードされた式 | 現在値の状態 |
 | --- | --- | --- | --- |
 | 1 | 数字 3 |`3`| 現在の数 = 3 |

 これは、評価者が数値を適用する前に演算子が現れるまで待機する理由を示しています。 隣り合う数字は同じオペランドに属します。

 ## 特殊なケース

 否定的な結果には特別な解析は必要ありません。 次のような式の場合`3-10=`、パーサーは最初に文字を回復します`3-10`、その後、評価者が保存します`3`、マイナスタイルの後の符号を変更し、減算します。`10`。 出力は次のようになります`3-10=-7`。 

複数の桁の数値を別々のオペランドに分割してはなりません。 表現の中で`2+10=`、数字タイル`1`そして`0`は連続して読み取られるため、現在の数値は次のように変化します。`1`に`10`追加される前に。 すべてのタイルを個別の数値として扱うと、誤って生成されます。`2+1+0=3`。 

等号は解析を終了する必要があります。 最後のタイルが演算子またはオペランドと間違われた場合、評価者は等号の後に存在しない値を処理しようとする可能性があります。 このアルゴリズムは、タイル シーケンス全体をデコードし、等号記号を表示された式の終了マーカーとしてのみ使用することでこれを回避します。 

入力の末尾にある空白の区切り列によって空の記号が作成されてはなりません。 パーサーは、タイルの抽出を試行する前に完全に空の列をスキップします。これにより、入力行にスペースが埋め込まれている場合でも、タイルの境界は整列された状態に保たれます。
