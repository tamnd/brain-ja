 ## 解決策
 ## 問題の理解

 1 から N までの位置の行が与えられ、各位置に 0 から K までの値を割り当てる必要があります。この配列の上に、M 個の制約があります。 各制約はセグメント [l, r] を指定し、そのセグメント内の値の合計が正確に K であることを要求します。 

タスクは、そのような配列の数を計算することではなく、有効な配列を構築するか、存在しないことを報告することです。 

制約は、セグメント間のグローバルな結合を意味します。 各位置は同時に多くのセグメントの合計に寄与するため、セグメントを個別に扱うことはできません。 代わりに、1 つのインデックスでのすべての選択が、そのインデックスをカバーするすべてのセグメントに反映されます。 

最も重要な構造観察は、K が非常に小さく、最大でも 20 であるという事実から得られます。これは、各位置が、重複する間隔に分散する必要がある限られたリソースのように動作することを強く示唆しています。 

入力サイズは大きく、テスト ケース全体で合計 N と M はそれぞれ最大 4e5 と 2e5 になります。 これにより、セグメント上の二次関数や単純なセグメントごとのスキャンが排除されます。 どのソリューションも、テスト ケースごとにほぼ線形またはほぼ線形である必要があります。 

素朴な解釈では、貪欲に値を割り当て、すべてのセグメントを繰り返しチェックしようとします。 それは 2 つの点で失敗します。 まず、セグメント合計の再計算が非常に遅くなります。 第二に、重複を理解せずに貪欲に割り当てを行うと、簡単に実現可能性が損なわれます。 

セグメントが入れ子状に重なっている場合、微妙な失敗例が発生します。 たとえば、K = 1 のセグメント [1,3] と [2,4] がある場合、最初のセグメントを満たすために位置 2 の値を選択すると、2 番目のセグメントを満たすことができなくなる可能性があります。 制約が非ローカルで相互作用するため、ローカルでの貪欲な決定は安全ではありません。 

もう 1 つの問題となるシナリオは、矛盾した報道です。 1 つのセグメントが領域に過剰な値の蓄積を強制するが、重複するセグメントが同じ領域を異なる方法で制限する場合、単純な割り当てでは遅くなるまで、またはまったく不可能を検出できない可能性があります。 

## アプローチ

 ブルートフォース手法では、N 個の位置すべてに値を割り当て、M 個のセグメントすべてをチェックしようとします。 各チェックでは範囲にわたる合計が必要であり、最悪の場合は O(NM) になります。 チェックを高速化するためにプレフィックス合計を使用したとしても、割り当てを繰り返し調整する必要があり、検索スペースが (K+1)^N であるため、これは完全に不可能になります。 

重要な観察は、K が非常に小さく、すべてのセグメントが正確な合計を強制することです。 任意の実数値の制約という観点から考える代わりに、K 個のユニットを区間全体に分散するという観点から考えることができます。 各セグメントは固定の総質量を必要とし、各位置は全体で最大 K までしか貢献できません。 

これは、各位置が、そこを通過するすべてのセグメントを満たす必要があるある程度の「容量消費」を運ぶものと見なすことを示唆しています。 本当の画期的な点は、構造化された順序で制約を処理し、各セグメントが処理されるときに以前のセグメントに違反することなく正確に満たされるように段階的に制約を適用することです。 

この問題は、すべてのセグメントがフロー要件を課す配列を維持していると解釈できます。 セグメントを一貫した順序で処理し、必要な質量をセグメント内の最も右側の利用可能な位置に常にプッシュすれば、将来の競合を回避できます。 これは、間隔処理に基づいた古典的な貪欲な構造です。 

現在割り当てられている値を追跡する構造を維持し、セグメントを処理するときにその内部に K ユニットを割り当てることができることを保証します。 そうでない場合、インスタンスは不可能です。 K が小さいため、実現可能性を維持しながらユニットを明示的に分配できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O((K+1)^N・M) | O(N) | 遅すぎる |
 | 最適 | O((N + M) log N) または O(N + M) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

重要な考え方は、各セグメントを、現在利用可能な容量に配置する必要がある K ユニットの需要として扱うことです。 

正しいエンドポイントの昇順にセグメントを処理します。 この順序により、セグメントを満たすと、将来のセグメントがさらに拡張されるか、後で開始されるため、すでに処理された制約の実現可能性を誤って破壊することがなくなります。 

1. すべてのセグメントを右端点 r で並べ替えます。 2 つのセグメントが r を共有する場合、左端点の増加順に並べます。 
2. 0 に初期化された長さ N の配列 a を維持します。セグメントを満たすにつれてエントリをインクリメントします。 
3. ソートされた順序で各セグメント [l, r] について、このセグメントにすでに割り当てられている合計の量を計算します。 これはフェンウィック ツリーまたはセグメント ツリーを使用して維持できるため、範囲の合計を効率的にクエリできます。 
4. [l, r] の現在の合計が K を超える場合、前のセグメントを壊さずに後で値を減らすことはできないため、この構成が無効であることがすぐにわかります。 
5. 現在の合計が K 未満の場合、[l, r] 内に (K から現在の合計を引いた) 単位を追加する必要があります。 これらのユニットを位置 r から開始して左に向かって貪欲に配置し、常に K までの位置を埋めます。 
6. ユニットを追加するときは、常に a[i] ≤ K という上限を尊重します。K 個の追加ユニットに達する前に [l, r] 内のスペースが不足すると、インスタンスは不可能になります。 
7. すべてのセグメントを処理した後、構築された配列を出力します。 

右から左への貪欲な配置が機能する理由は、以前のセグメントがより小さい右端点に固定されているためです。 右から埋めると、より早く終了するセグメントに必要な潜在的なスペースの消費が回避されます。 

### なぜ効果があるのか

 すべてのステップで、処理されたすべてのセグメントが正確に満たされていることを確認します。 値を減らすことは決してないので、以前に満たされたセグメントは有効なままになります。 右端点を増加させることによって処理するため、オーバーラップする可能性のあるセグメントは、制御された方法でその右境界を共有します。セグメントを終了すると、以降の操作では、少なくとも右端まで広がるセグメント内で考慮されずに、その間隔の外側の位置に過剰な質量が導入されることはありません。 

不変条件は、指定された右端点 R までのセグメントを処理した後、r ≤ R のすべてのセグメントが正確に満たされ、K を超える位置がないということです。貪欲な充填により、セグメントに残っている不足分が常に最新の可能な位置に配置され、将来の制約に対する柔軟性が確保されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    n, m, k = map(int, input().split())
    segs = []
    for _ in range(m):
        l, r = map(int, input().split())
        segs.append((r, l))
    segs.sort()

    bit = Fenwick(n)
    a = [0] * (n + 1)

    for r, l in segs:
        cur = bit.range_sum(l, r)
        if cur > k:
            print(-1)
            return
        need = k - cur
        i = r
        while need > 0 and i >= l:
            if a[i] < k:
                add = min(k - a[i], need)
                a[i] += add
                bit.add(i, add)
                need -= add
            i -= 1
        if need > 0:
            print(-1)
            return

    print(*a[1:])

t = int(input())
for _ in range(t):
    solve()
```フェンウィック ツリーは、各セグメントを効率的にクエリできるようにプレフィックスの合計を維持します。 これがないと範囲を繰り返しスキャンすることになり、上限に達すると速度が非常に遅くなります。 

貪欲な内部ループは、ソリューションの建設的な部分です。 私たちは常に、残りの必要な合計をセグメント内の可能な限り右に配置しようとします。 これにより、必要に応じて、以前のセグメントがすでに左側の位置を埋めているため、より早く終了する以前のセグメントとの干渉が回避されます。 

配列`a`値が K を超えることはできないという位置ごとの制約が適用されます。フェンウィック ツリーはこれらの更新をミラーリングするため、将来のセグメント クエリにはすべての割り当てが反映されます。 

よくある微妙な間違いは、セグメントを埋めるときに左から右に繰り返すことです。 これは、低インデックスの消費が早すぎるため、正確性が損なわれます。これは、将来の処理順序で先に終了するセグメントで必要になる可能性があります。 

## 実用的な例

 N = 4、K = 2、セグメント [1,2]、[2,4] の小さなインスタンスを考えてみましょう。 

右のエンドポイントで並べ替えます: [1,2]、次に [2,4]。 

| セグメント | 範囲 | 現在の合計 | 必要 | アクション |
 | --- | --- | --- | --- | --- |
 | [1,2] | 1-2 | 0 | 2 | 2 で塗りつぶしてから 1 |
 | [2,4] | 2-4 | 0 | 2 | 4 で塗りつぶしてから 3 |

 最初のセグメントの後は、= [1,1,0,0] になる可能性があります。 2 番目以降は = [1,1,1,1] を取得します。 

これは、初期のセグメントが右側に向かって質量を集中させ、後のセグメントに柔軟性を残していることを示しています。 

次に、不可能なケース、つまりセグメント [1,2]、[2,3]、[1,3] を持つ N = 3、K = 2 を考えてみましょう。 

[1,2] を処理すると、2 つのユニットが最初に位置 2、次に 1 に配置され、= [1,1,0] が得られます。 処理 [2,3] では 2 つのユニットを配置しますが、位置 2 はすでにいっぱいであるため、位置 3 を使用し、最終セグメント [1,3] の合計で最初のセグメント制約を満たせません。 最終的に、容量を超えずに [1,3] のバランスを取ることができないときに、不可能であることがわかります。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((N + M) log N) | 各セグメントのクエリと更新では Fenwick 操作が使用され、各位置は最大で K 回増加します。 
| スペース | O(N) | アレイとフェンウィック ツリー ストレージ |

 この制約では、合計 N が 4e5 まで、セグメントが合計 2e5 まで許可されるため、対数係数は安全です。 K が小さいため、内側の充填ループは全体的に境界のあるままになります。

 ## 特殊なケース

 重大なエッジ ケースは、以前のセグメントによってすでに飽和されている領域内にセグメントが完全に含まれている場合です。 [1,4] がそのリージョン内の利用可能な容量をすべて消費した後に、セグメント [2,3] が到着するとします。 [2,3] を処理するとき、アルゴリズムはすでに K 以上に等しい現在の合計を計算します。 Kを超える場合は直ちに拒否します。 それが K に等しい場合、アクションは実行されず、正確さが保たれます。 

もう 1 つの微妙なケースは、長さ 1 のセグメントです。たとえば、[i,i] は a[i] = K を強制します。別のセグメントも i をカバーする場合、不一致はフェンウィックの合計チェックを通じてすぐにわかります。 これにより矛盾が早期に発見されます。 

3 番目のケースには、重複するセグメントの長いチェーンが含まれており、新しいセグメントごとに需要がわずかに右にシフトします。 右から左への充填により、ソートされた処理順序では常に前のセグメントが前のインデックスよりも優先されるため、前のセグメントで必要な容量が不足することがなくなります。
