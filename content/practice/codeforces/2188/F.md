 ## 解決策
 ## 問題の理解

 文字で構成される文字列が与えられます`0`、`1`、 そして`?`。 この文字列の各完全バージョンは、一連の値を生成する数値プロセスを定義します。 

から始めます`c0 = 0`。 次に、文字列を左から右にスキャンします。 すべての文字は現在の値を次の値に変換します。 あ`0`値を増やす`x`、一方、`1`看板をひっくり返す`y`、生産`y - current value`。 文字列全体を処理した後、すべての中間値を合計します。`c1 + c2 + ... + cn`、完成した文字列に関連付けられた単一の数値が得られます。 

タスクは 1 つの完了を評価することではありません。 代わりに、すべての`?`どちらでも置き換えることができます`0`または`1`、多くの可能な最終合計を生成します。 このような合計は「クール」と呼ばれ、すべての個別のクール値の合計を計算する必要があります。 

主な難点は、割り当てが異なることです。`?`最終的な合計が同じになる可能性があるため、構成をカウントするのではなく、その結果の値を集計します。 

この制約により、すべての補完を強引に列挙することが直ちに排除されます。 全体で最大 100,000 のポジションがあり、各ポジションごとに指数関数的な選択肢が用意されています。`?`, すべての文字列を試すのは不可能です。 サブセットに対するテストごとの指数関数的な DP さえ爆発的に増加します。 

さらに微妙な問題は、繰り返しによって動作が交互になることです。`0`直線的な成長を維持しながら、`1`反省を導入する`y - c_{i-1}`これにより、値は前の操作のパリティに依存します。 この交互構造を無視する単純なプレフィックス シミュレーションでは、寄与が誤って計算されます。`1`は加算的ではなく、状態を反転します。 

よくある失敗例は、複数の場合に発生します。`?`長い交互パターンで存在します。 貪欲な置換またはローカル推論は、初期の選択が符号反転を通じて将来のすべての値に影響を与えるため、失敗します。 

## アプローチ

 ブルートフォースアプローチでは、あらゆる方法でそれぞれを置き換えようとします。`?`と`0`または`1`。 完成した文字列ごとに、繰り返しをシミュレートして計算します。`f(s)`。 これは定義に直接従うため、正しいです。 ただし、ある場合は、`m`疑問符、これは次のことにつながります`2^m`構成と各評価コスト`O(n)`。 中程度の場合でも`m`、これは不可能になります。 

再発の構造は、別の観点を示唆しています。 各ステップは前の値で線形です。`0`当てはまる`c -> c + x`、一方、`1`当てはまる`c -> -c + y`。 これがアフィン変換です。 したがって、プロセス全体はアフィン関数の組み合わせであり、すべてのプレフィックス状態は次のように記述できることを意味します。```
c_i = a_i * c_0 + b_i
```以来`c0 = 0`、私たちは追跡するだけです`b_i`、しかし重要な洞察は、各ステップが将来の貢献の兆候を切り替えるということです。 したがって、各プレフィックスの状態は、パリティの数によって異なります。`1`これまでに適用されました。 

すべての割り当ての正確な値を追跡する代わりに、寄与度を 2 つの部分に分けます。すべての選択肢が固定されていると仮定した基本寄与度と、それぞれの選択肢によって引き起こされる追加効果です。`?`2 つの直線的な動作を切り替えます。 これは、問題を、現在のプレフィックスが「通常」パリティであるか「反転」パリティであるかを記述する小さな状態空間にわたる DP に変換し、各状態に至る割り当ての数をカウントすることを組み合わせます。 

本質的な削減は、各位置が固定増分 (`0`) または将来の蓄積を反転する変換 (`1`）。 これにより、プレフィックスごとに値の合計と、各パリティ状態でそのプレフィックスに到達する方法の数の両方を維持し、文字ごとに O(1) で更新することができます。 

最終的な答えは、これらの DP 状態を通じてすべての有効な完了の貢献を集約することによって得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^k · n) | O(n) | 遅すぎる |
 | DP over パリティ状態 | O(n) | O(1) または O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 このプロセスを、文字列のスキャン中に 2 種類の情報 (特定の符号状態に至る経路の数と、その状態にあるすべてのプレフィックスの累積寄与) を維持するものとして再解釈します。 

各ポジションでのトランジションは、私たちが選択するかどうかによってのみ決まります。`0`、`1`、または強制値を持ちます。 

私たちは 4 つの集約を維持します。 

1. 正の方向性で現在位置に到達する方法の数。 
2. 負の方向で現在位置に到達する方法の数。 
3. ポジティブ指向に対するプレフィックス寄与の合計。 
4. 否定的な方向性に対するプレフィックスの寄与の合計。 

向きは、現在の値が正常に動作するか、または奇数の値により無効になるかを追跡します。`1`-type 変換。 

文字を左から右に処理します。 

1. 初期化: 文字列を読み取る前に、合計を使用して正の方向を指定する方法が 1 つあります。`0`。 
2. キャラクターごとに、トランジションを計算します。 

- キャラクターの場合`0`、変換により追加されます`x`向きを反転せずに現在の値に戻します。 
- キャラクターの場合`1`、反転を適用します。次の値は次のようになります。`y - c`、方向が変更され、固定オフセットも追加されます。 
- キャラクターの場合`?`、両方のトランジションに分岐し、それらの貢献を組み合わせます。 
3. 最初にカウントを更新し、次に合計貢献度を更新します。 ウェイの数は固定増分が合計にどの程度寄与するかに影響を与えるため、この順序は非常に重要です。 
4. 最後に、両方の方向からの寄与を組み合わせて、すべての完了の合計を算出します。 

重要な不変条件は、処理後の位置です。`i`、DP はプレフィックスのすべての部分的な割り当てを正しく表します。`s[1..i]`、現在の繰り返し状態が反転されているかどうかによってグループ化されます。 各 DP エントリには、そのようなすべての割り当ての集計された寄与が正確に保存されるため、後で再結合や二重カウントが発生することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

def solve():
    n, x, y = map(int, input().split())
    s = input().strip()

    # dp0, dp1: number of ways in state 0/1
    # sum0, sum1: sum of c_i contributions aggregated over all ways
    dp0 = 1
    dp1 = 0
    sum0 = 0
    sum1 = 0

    for ch in s:
        n0 = n1 = 0
        ns0 = ns1 = 0

        if ch == '0' or ch == '?':
            # 0: c -> c + x, no flip
            n0 += dp0
            ns0 += sum0 + dp0 * x

            n1 += dp1
            ns1 += sum1 + dp1 * x

        if ch == '1' or ch == '?':
            # 1: c -> y - c (flip orientation)
            n1 += dp0
            ns1 += dp0 * y - sum0

            n0 += dp1
            ns0 += dp1 * y - sum1

        dp0, dp1 = n0 % MOD, n1 % MOD
        sum0, sum1 = ns0 % MOD, ns1 % MOD

    ans = (sum0 + sum1) % MOD
    print(ans % MOD)

def main():
    t = int(input())
    for _ in range(t):
        solve()

if __name__ == "__main__":
    main()
```DP はカウントと累積合計を同時に維持します。 の移行`0`すべてのアクティブな構成の現在の値を増加させます`x`, したがって、合計は によって増加します`dp * x`以前の金額を繰り越すことに加えて。 

のために`1`、変換を適用します`y - c`。 これにより寄与の方向が逆転するため、固定されたまま以前の合計が減算されます。`y`用語はアクティブな構成ごとに追加されます。 

モジュロを取得する前に、状態数と寄与の合計の両方を常に更新するように注意する必要があります。 減算の早い段階でモジュロを混合すると、負の値が後の遷移を破壊する可能性があるため、減算は最初に完全な精度で実行され、代入時にのみ減算されます。

 ## 特殊なケース

 弦が頻繁に交互に使用される場合、微妙なエッジケースが発生します。`1`そして`?`。 このような場合、向きは繰り返し反転し、単調な累積を前提とした単純な実装は失敗します。 

たとえば、次のように考えてみましょう`s = "?1"`。 最初の文字は両方の方向を作成し、2 番目の文字はそれらを反転します。 正しい DP は両方のブランチを別々に保存する必要があります。 結合するのが早すぎると、区別しておくべき用語がキャンセルされてしまいます。 

トレース`?1`:

 から始める`(dp0, dp1) = (1, 0)`。 

後`?`、 両方`0`そして`1`状態はアクティブです。 加工後`1`、遷移は状態を交換し、前の合計を減算しますが、DP 構造は両方の寄与を別々に保ちます。 最終的な集計では、両方の補完を明示的に列挙するという一貫性が維持されます。 

これは、不変のオーバーオリエンテーション状態が、反転を繰り返す際の情報の損失を防ぐのに十分であることを裏付けています。
