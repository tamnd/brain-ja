 ## 解決策
 ## 問題の理解

 私たちは、一連の操作を通じて進化する非常に小さな「プレイリスト システム」をシミュレートしています。 いつでも演奏を待つ曲の行列ができています。 2 種類の操作が順番に実行されます。 

1 回の操作で、キューの先頭から 1 つの曲が削除され、実行されます (存在する場合)。 もう 1 つの操作では、新しい曲をキューの最後に追加します。 重要な点は、追加がバッチ単位で行われることです。初めて曲を追加するときは 1 曲だけ追加します。 2 回目に曲を追加するときは、ちょうど 2 つ追加します。 3回目は3回、というように。 

すべての操作を実行した後、いくつかの曲が演奏されずにキューに残ります。 合計で何回の操作が実行されたか、そして最後に何曲が残っているかがわかります。 タスクは、プロセス全体で実際に何曲演奏されたかを判断することです。 

入力サイズは非常に小さく、操作の数は最大でも 10 程度であるため、指数推論またはすべての有効な操作パターンの直接列挙までのアプローチは概念的には問題ありません。 ただし、「バッチ サイズの増加」により、追加された曲の数と削除された曲の数の間に隠れた算術関係が作成されるため、構造は依然として重要です。 

微妙な点は、追加が連続して発生する可能性があることです。つまり、間に曲が演奏されずに複数の「バッチの追加」が発生する可能性があります。 これにより、交互パターンを想定することができなくなります。 

単純な間違いは、すべての操作が独立していると仮定し、増大する追加サイズのシーケンスを追跡せずにシミュレーションを試みることです。 もう 1 つのよくある間違いは、追加された曲の数を単に「追加操作」の数として扱うことです。これは、三角形の増加パターンを無視します。 

たとえば、2 つの追加操作と 1 つの削除操作があるように操作が配置されている場合、追加操作は合計 1 + 2 = 3 曲に寄与します。 1 曲が演奏されて 2 曲が残っている場合、それは一貫した状態と一致します。 各加算が一定量寄与すると仮定する推論は、そのような入力では失敗します。 

最も難しいのは、各操作タイプが何回発生したかを再構築し、それを追加された曲の三角和と組み合わせることです。 

## アプローチ

 この強引なアイデアは、操作シーケンスを再構築しようとすることです。 各操作は「k 曲を追加する」（k はすでに追加された曲の数に応じて異なります）または「可能であれば 1 曲削除する」のいずれかであるため、最終状態と一致するすべての有効なシーケンスをシミュレートできます。 候補シーケンスごとに、キューを追跡し、操作を適用して、ちょうど m 曲の残りで終了するかどうかを確認します。 これはプロセス定義を直接反映しているため、これは正しいです。 

ただし、分岐は、n 個の操作のうちどれが「追加」操作でどれが「削除」操作であるかを決定することから始まります。 最悪の場合、これは演算のすべてのサブセット (O(2^n)) を探索することを意味し、n が約 10 であってもこれは境界線ですが、より単純な構造が存在することを考えると不要です。 

重要な観察は、システムが 2 つの数値 (追加操作の数と削除操作の数) によって完全に決定されるということです。 a を追加操作の数、b を削除操作の数とすると、a + b = n となります。 追加される曲の合計数は a では線形ではなく、1 + 2 + … + a = a(a+1)/2 と等しくなります。 削除される曲の合計数は b ですが、キューが負にならない限り、有効な解決策が存在することが問題ステートメントによって保証されます。 

したがって、最後に残った曲は次の条件を満たします。 

初期値 + 追加 - 削除 = m

 初期値がゼロであると仮定すると (このモデルでは一般的)、次のようになります。 

a(a+1)/2 − b = m

 b = n − a なので、すべてを 1 つの変数にまとめます。 

a(a+1)/2 − (n − a) = m

これは a の単純な 2 次方程式になります。 n は小さいので、0 から n までのすべての a を試して、どれが方程式を満たすかを確認することができます。

 | ブルート フォース シーケンス シミュレーション | O(2^n · n) | O(n) | 遅すぎる/不必要 |
 | すべての追加カウントを試す | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. n 個の操作のうち「追加操作」である操作の数を選択するプロセスとして解釈し、この値を a と呼びます。 残りの n − a 操作は「削除操作」です。 
2. 固定 a について、追加によって導入された曲が何曲あるかを計算します。 追加するたびに 1 ずつ増加するため、追加される曲の合計は三角形の数 a(a+1)/2 になります。 これにより、バッチの増加ルールが正確に捕捉されます。 
3. 削除された曲の数を計算します。追加以外の操作ではそれぞれ 1 曲だけ削除されるため、単純に n − a となります。 
4. 追加された曲から削除されたものを差し引いた最終的な残りの曲数を計算します。 
5. これが m と等しいかどうかを確認します。 そうであれば、操作の一貫した分解が見つかったので、演奏された曲の数は正確に n − a になります。 
6. 制約は小さいため、0 から n までの可能なすべての a を反復し、一意の有効な結果を返します。 

### なぜ効果があるのか

 プロセスには、各操作タイプを実行した回数を超える隠れた状態はありません。 増加する追加ルールは、削除間の位置ではなく、以前の追加の数にのみ依存します。 したがって、追加を含む有効なスケジュールは、順序に関係なく、同じ追加合計を生成します。 これにより、シーケンス問題全体が単一のパラメータ a に折りたたまれます。 最終的なキューのサイズは、追加の合計と削除の合計にのみ依存するため、m の一致によって正しい分割が一意に決定されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    for a in range(n + 1):
        added = a * (a + 1) // 2
        removed = n - a
        remaining = added - removed
        if remaining == m:
            print(removed)
            return

if __name__ == "__main__":
    solve()
```実装では、リダクションを単一の変数に直接エンコードします。 n が最大 10 であるため、a に対するループは安全です。そのため、演算タイプの考えられるすべての分割を効果的に列挙していることになります。 

三角関数の計算`a * (a + 1) // 2`Python は大きな整数を自然に処理しますが、浮動小数点の問題を避けるために、整数演算を使用して慎重に実行する必要があります。 

印刷します`removed`実行された曲の数は、発生した削除操作の数に正確に対応するためです。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys as _sys
    from contextlib import redirect_stdout
    out = io.StringIO()
    
    def solve():
        n, m = map(int, _sys.stdin.readline().split())
        for a in range(n + 1):
            added = a * (a + 1) // 2
            removed = n - a
            if added - removed == m:
                print(removed)
                return

    with redirect_stdout(out):
        solve()
    return out.getvalue().strip()

# provided sample

# all removes
assert run("3 -3") == "3"

assert run("1 0") in {"0", "1"}  # depending on valid construction

 ## 特殊なケース

 最小の自明でないエッジは、n = 0 の場合です。この場合、操作はないため、曲は実行できず、曲も追加されません。 唯一の一貫した状態は m = 0 であり、アルゴリズムは a = 0、added = 0、removed = 0 を正しく評価します。 

もう 1 つの微妙なケースは、すべての操作が 1 つのタイプである場合です。 すべてが加算される場合、a = n となり、最終状態は純粋な三角形になります。 すべてが削除された場合、代数モデルでは a = 0 となり、最終状態は負になりますが、これは有効な入力では起こり得ないため、そのようなケースは「解の保証」条件によって当然除外されます。 

最後に、追加と削除を交互に行うような混合ケースでも、三角和は削除が発生した場所ではなく、追加カウンタをインクリメントした回数のみに依存するため、正しく折りたたまれます。 の列挙は、明示的にシミュレートすることなく、そのようなすべてのインターリーブを暗黙的にカバーします。
