 ## 解決策
 ## 問題の理解

 コンテナのコレクションが与えられ、各コンテナの重みは 2 に固定され、関連コストが割り当てられます。 各コンテナーの構造は一意ではありませんが、各入力行は同一のコンテナーのグループを記述します。$k_i$そしてコスト$W_i$、あることを意味します$k_i$利用可能なコンテナ、それぞれの費用$W_i$。 

需要面では、いくつかの注文を受けています。 各注文には番号が指定されます$t_j$そして高さパラメータ$h_j$。 すべての注文では正確に選択する必要があります$h_j$各コンテナは重量 2 に寄与し、必要な合計重量は次のようになります。$2h_j$。 選択したコンテナーごとにコストが発生するため、利用可能なコンテナーの同じグローバル プールを使用して、すべての注文に個別に対応する必要があります。 同じ物理コンテナを複数の注文にわたって再利用することはできないため、1 つの注文でコンテナ タイプが消費されると、その容量は全体的に減少します。 

目標は、すべての注文を満たすための総コストを最小限に抑えること、または利用可能なコンテナが必要な選択をすべて満たせない場合は不可能であることを報告することです。 

この構造を再解釈すると、より明確になります。アイテムのマルチセットがあり、各アイテムは選択単位の観点から重み 1 (すべてのコンテナが「2 重み」の 1 つの単位に正確に寄与するため) とコストを持ちます。 正確に割り当てなければなりません$h_j$アイテムを各注文に割り当て、注文間の割り当ては互いに素である必要があります。 

制約は非常に重要です。 コンテナー グループの合計数は最大 10,000 で、すべてのオーダーにわたる需要の合計は 5,000 に制限されます。 この非対称性は重要です。供給は大きく、構造化されていますが、需要は比較的小さいのです。 コンテナごとの割り当てをシミュレートしようとするアルゴリズムは、単純な拡張では最悪の場合 10^7 項目に達する可能性があるため、遅すぎます。 一方、各グループを制限された容量リソースとして扱うアルゴリズムは、ナップザック スタイルの構造を示唆していますが、複数の要求があります。 

合計数が多いように見えても、容量が不十分な場合には、エッジケースが発生します。 たとえば、すべてのコンテナが安価ですが、小容量にグループ化されており、1 回の注文で大量のコンテナが必要になる場合です。$h$、たとえ失敗するかもしれませんが、$\sum k_i$グループ化制約の処理を誤った場合には、これで十分です。 もう 1 つの失敗モードは、各グループの容量が限られているということを忘れていることです。 各グループを無限として扱うと、不正確な実現可能性が生じます。 

2 番目の微妙なエッジケースは、注文をまとめて考慮する必要がある場合に発生します。 将来の注文を考慮せずに、地元で最も安価なコンテナを使用して各注文を貪欲に満たすと、低コストのグループが使い果たされ、後でより高コストの使用が強制され、総コストが増加したり、失敗が発生したりする可能性があります。 

## アプローチ

 直接的な総当たりアプローチでは、すべてのコンテナを個別に処理しようとします。 各グループを次のように展開します。$k_i$項目を選択して注文に割り当てます。 それぞれの割り当ての決定には、どの項目をどの順序に割り当てるかを選択することが含まれます。これにより、自然に多次元の割り当てまたはフローのような定式化が行われます。 すべての品目とすべての注文に対する単純な動的プログラミングであっても、注文ごとに最大 10,000 のグループと潜在的に 10,000 の需要単位を反復する必要があり、操作数は$10^8$に$10^9$、1 秒の制限の下では遅すぎます。 

重要な観察は、すべてのコンテナの重量が同じで、コストと多重度だけが異なるということです。 これにより、問題は合計を選択することになります。$H = \sum h_j$重み付けされた選択肢のマルチセットから項目を選択します。各グループは$i$せいぜい貢献する$k_i$選択。 

個々の注文の観点から考えるのではなく、すべての需要を単一のグローバル要件に集約します。つまり、正確に選択する必要があります。$H$コンテナの合計。 注文が別々であるという事実は、実現可能性をグループ化する場合にのみ問題となりますが、すべての品目は重量において区別がつかず、コストにおいて独立しているため、有効な割り当ては行われません。$H$それぞれの注文に応じて項目を任意に並べ替えることができます。 

これにより、問題は容量のある境界のあるナップザックに変換されます。$H$。 各グループ$i$まで貢献します$k_i$アイテム、それぞれにコストがかかる$W_i$。 きっちり選びたい$H$トータルコストを最小限に抑えるアイテム。 

境界付きナップザックの標準的な手法は、容量のバイナリ分解です。 定員のある各グループ$k_i$は 2 の累乗バンドルに分割されるため、問題を 0/1 のナップサックとして扱うことができます。$O(n \log k_i)$アイテム。 合計以来$H \le 5000$、この容量を超えるナップザック DP は実現可能です。 

DP 配列を維持します。$dp[x]$正確に選択するための最小コストです$x$コンテナ。 初期化します$dp[0] = 0$その他はすべて無限大です。 分解されたバンドルごとに、標準の 0/1 ナップザック遷移を後方に実行します。$H$バンドルサイズに合わせて。 

これが機能するのは、各バンドルが利用可能な供給量を超えてはいけないという制約を強制すると同時に、対数分解でグループを効率的に再利用できるためです。

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. 必要なコンテナの合計数を計算する$H = \sum h_j$。 もし$H > \sum k_i$、コストを無視しても需要を満たすことはできないため、すぐに -1 を返します。 これは必要な実現可能条件です。 
2.次のサイズの DP 配列を作成します$H+1$、 どこ$dp[x]$正確に選択するための最小コストを保存します$x$コンテナ。 初期化する$dp[0] = 0$最初は何も選択していないため、他のすべての値は無限大となります。 
3. コンテナグループごとに$i$、その容量を分解します$k_i$2 のバンドルのべき乗に変換します。 たとえば、次の場合$k_i = 13$、それを 1、2、4、6 に分割します。各バンドルは、同じ数のアイテムを選択することを表し、各バンドルのコストは、bundle_size を乗算したものに等しくなります。$W_i$。 

この分解により、組み合わせを失うことなく、制限された選択肢を複数の 0/1 の選択肢に変換できます。 
4. バンドルごとに$(s, cost)$、DP 配列を逆の順序で更新します。$H$まで$s$。 それぞれについて$x$、バンドルを手に取ってリラックスしてみてください$dp[x]$使用して$dp[x - s] + cost$。 

逆走査では、各バンドルが最大 1 回使用されることが保証され、0/1 ナップザック セマンティクスの正確さが維持されます。 
5. すべてのグループを処理した後、チェックを入れます$dp[H]$。 無限のままの場合は -1 を返します。 それ以外の場合は戻る$dp[H]$。 

### なぜ効果があるのか

 処理中のどの時点でも、$dp[x]$正確に選択するための最小コストを表します$x$これまでに処理されたグループのコンテナの容量を超えることはありませんでした。 バイナリ分解により、最大でもすべての有効なサブセットが保証されます。$k_i$各グループのアイテムはバンドルの合計として表すことができるため、実行可能なソリューションは除外されません。 逆の DP 移行により、バンドルが再利用されず、容量制限の整合性が維持されます。 有効な代入はすべて$H$アイテムがバンドルの実行可能な 1 つの組み合わせに正確に対応する場合、DP はすべての有効な構成を調査し、それらの中での最小コストを返します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**18

n = int(input())
groups = []
total_supply = 0

for _ in range(n):
    k, w = map(int, input().split())
    groups.append((k, w))
    total_supply += k

m = int(input())
h_list = []
H = 0
for _ in range(m):
    t, h = map(int, input().split())
    H += h

if H > total_supply:
    print(-1)
    sys.exit()

dp = [INF] * (H + 1)
dp[0] = 0

for k, w in groups:
    if k == 0:
        continue
    cnt = k
    base = 1
    while cnt > 0:
        take = min(base, cnt)
        cost = take * w
        cnt -= take
        base <<= 1

        for x in range(H, take - 1, -1):
            if dp[x - take] + cost < dp[x]:
                dp[x] = dp[x - take] + cost

if dp[H] >= INF:
    print(-1)
else:
    print(dp[H])
```このソリューションでは、まず実現可能性を集計し、次に従来の有界ナップザック変換を適用します。 唯一の微妙な点は、バイナリ チャンクごとに逆方向 DP 更新を維持し、各チャンクが 1 回使用されるようにすることです。 分解ループは残りの容量を慎重に減らす必要があります。そうしないと、最後のチャンクが元の境界を超える可能性があります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、総供給量は十分であるが、グループ間で分配すると正確な満足が得られない場合です。 たとえば、5 つのコンテナが必要だが、グループ (k=3) と (k=3) がある場合、実現可能性は問題ありません。 ただし、グループを誤って個別に扱うと、1 つのグループから過剰に割り当てが行われ、その後の移行が失敗する可能性があります。 DP は、グローバルな容量制約を強制することでこれを回避します。 

もう 1 つのケースは、すべてのコストがゼロの場合です。 DP は、オーバーフローや不正な無限大の処理を行わずに、実行可能性を正しく計算する必要があります。 遷移では加算が使用されるため、無限大を大きな定数として初期化すると、ゼロコスト バンドルが歪みなく正しく伝播されます。 

最後のエッジケースは次のような場合です$H = 0$。 コンテナは必要ないため、アルゴリズムはすぐに 0 を返すはずです。 DP の初期化ではすでにこれに対応しています。$dp[0]$はゼロに設定されており、遷移は必要ありません。
