 ## 解決策
 ## 問題の理解

 私たちは、企業の従業員が時間の経過とともにどのように変化するかについて、一定のスケジュールを与えられています。 毎日、既知の数の労働者が解雇され、既知の数の雇用が行われます。システムは、解雇の数が現在雇用されている労働者の数を決して超えないことを保証します。 これは、ワーカー プールがワーカー 0 の暗黙的な初期状態から決定論的に進化することを意味します。 

この運用スケジュールに加えて、人事スタッフに関する別の要件があります。 毎日、ちょうど 1 人の人事担当者が、その日の解雇と採用の両方のイベントを処理する責任を負います。 ただし、構造を生み出す制限があります。つまり、ある人事担当者によって解雇された従業員は、その職歴の以前に同じ人事担当者に雇用されてはなりません。 言い換えれば、従業員の採用イベントと解雇イベントは、別の人事担当者が処理する必要があります。 

目標は、使用される個別の HR 従業員の総数を最小限に抑えながら、すべてのイベントが処理され制約が満たされるように、毎日 1 人の HR 従業員に割り当てることです。 

入力により、毎日、削除および追加されたワーカーの数がわかります。 出力では毎日 HR ID を割り当て、使用される ID の数を最小限に抑える必要があります。 

重要な制約は、解雇が従業員に対する後入れ先出しの方針に従って行われること、つまり、会社が雇用順序に従って従業員の束のように振る舞うことを意味します。 これが構造を作成するものです。ワーカーは、任意のマッチングではなく、ネストされた方法または連続した方法で、ライフタイムによってペアにできます。 

問題のサイズは最大 100,000 日で、1 日あたり最大 10^6 の操作が発生します。 これにより、個々の労働者を追跡したり、労働者ごとに簿記を試みたりするシミュレーションは即座に除外されます。 1 日あたりの線形または線形に近い複雑さを超えるものは遅すぎます。 

微妙な失敗例は、複数の HR ワーカーが交換可能であるように見えても、制約によりネストされたライフタイム全体で分離が強制される場合に発生します。 たとえば、ある人事担当者がある日の採用を担当し、その後、深くネストされた従業員が別の日に解雇された場合、同じ人事担当者を再利用すると、たとえ局所的には問題がないように見えても制限に違反する可能性があります。 これにより、グローバル構造を持たない貪欲な割り当てが排除されます。 

## アプローチ

 直接解釈すると、従業員を個別にシミュレートし、従業員 ID のスタックを維持し、どの人事が各採用を担当したかを記録します。 従業員が解雇されるたびに、私たちはその雇用記録を取得し、別の人事担当者が使用されるようにします。 これにはすでに各従業員の ID を明示的に追跡する必要があり、これは線形合計操作で実現可能ですが、本当の問題は HR ID を日数に割り当てることです。 

さらに深刻な問題は、従業員の生涯を通して業務のペアを結び付ける制約の下で、イベント (日) に色 (人事担当者) を割り当てていることです。 各労働者は雇用日と解雇日の関係を定義し、これら 2 つの日には異なる色が割り当てられる必要があります。 これにより、問題は、ネストされた間隔によって引き起こされる構造の色付けに変わります。 

LIFO に基づくワーカーのライフサイクルを見ると、雇用されたすべてのワーカーはスタックへのプッシュに対応し、解雇されるたびに先頭から削除されます。 したがって、各労働者は雇用日から解雇日までの間隔に対応し、これらの間隔は適切にネストまたは素になっています。 これは古典的な構造であり、バランスのとれた括弧の間隔のセットです。 

ここで制約を再解釈します。すべての間隔には、その終点に異なる色が割り当てられている必要があります。 つまり、各間隔によって 2 日の間に制約が生じます。つまり、これらの 2 日は同じ HR ID を共有できません。 間隔は入れ子になっているため、結果として得られる競合グラフは任意のものではありません。 スタックのネストによってツリー状の構造が形成されます。

重要な洞察は、この構造に沿って割り当てを交互に行うには最大 2 人の人事担当者で十分であるということです。 ワーカーが作成され、後で削除されると、スタックの深さに沿った変更を確実に行うことができます。つまり、暗黙的なスタック フォレスト内の深さのパリティに基づいて HR ID を割り当てます。 プッシュするたびに深さが増加し、ポップするたびに深さが減少します。各間隔のエンドポイントが異なることを確認するだけで済みます。これは、スタックの深さの遷移に沿って交互の役割を割り当てれば保証されます。 

したがって、問題は、スタックの現在の状態に応じて毎日 2 つのラベルのいずれかを割り当て、複数のワーカーを起動するときの一貫性を確保するスタックの維持に帰着します。 したがって、人事担当者の最適な数は、1 日の責任の重複により 2 つ以上の役割を同時に割り当てる必要があるかどうかによって決まりますが、1 日に担当する人事担当者は 1 人だけであるため、真のボトルネックは、重複する間隔によって引き起こされる同時アクティブな制約になります。 これは、ネストされたアクティブなワーカーの最大数によって制限されます。これは、時間の経過に伴うスタック深さの動作です。 

したがって、解決策は、現在アクティブな「競合チェーン」を追跡し、制約が許せばそれらを再利用しながら、貪欲に HR ID を割り当てることになります。

 ## アルゴリズムのチュートリアル

 1. 現在生存している従業員を表すスタックを維持します。各従業員には、雇用日に対応した人事担当者の注釈が付けられます。 このスタックは解雇の LIFO の性質を反映しており、毎日どの労働者が解雇されるかが正確であることを保証します。 
2. 新しい採用イベントに現在安全に使用できる、利用可能な HR ID のプールを維持します。 HR がすでにその従業員の雇用を処理している場合、その従業員にとってその HR は安全ではなくなります。そのため、解雇日を割り当てる際には、その従業員の雇用日に同じ HR を決して再利用しないようにしています。 
3. 毎日、まずスタックからポップしてすべての起動を処理します。 ポップされた各従業員は、どの HR が採用を処理したかを明らかにし、その HR がルールに抵触する場合、その日の割り当てが一時的に制限されているとマークされます。 
4. 解雇を処理した後、新しい従業員をスタックにプッシュして雇用を処理します。 各新しい従業員に、その日の解雇制限によって現時点で制限されていない、使用可能な最小の HR ID を割り当てます。 
5. これまでに使用された個別の HR ID の数を追跡します。 既存のすべての HR ID が一時的に制限されているために新しい HR ID の導入を余儀なくされた場合は、カウンタをインクリメントします。 
6. 毎日 1 人の人事担当者が担当するため、選択した同じ HR ID を 1 日全体に割り当て、その日に処理されたすべての採用と解雇との一貫性を確保します。 

各ステップにおける中心的な決定は、1 日に 1 つの HR を割り当てる必要があるということですが、ライフサイクルが複数日にまたがる従業員によって制約が生じます。 現在の解雇によりどの人事が禁止されているかを常に尊重することで、従業員を雇用した同じ人事によって従業員が解雇されることがないようにします。 

### なぜ効果があるのか

 スタックは、すべての従業員の解雇が、以前の 1 つの雇用イベントと正確に一致することを保証します。 各ワーカーは、2 日の間に制約エッジを 1 つだけ定義します。 LIFO 構造は任意の交差ではなくネストを保証するため、これらの制約によって、アクティブなオーバーラップ深度を超えて制限された数を超える色を必要とするサイクルが形成されることはありません。 貪欲な割り当てでは、アクティブな制約によってすべてが一時的にブロックされない限り、常に有効な HR が選択されます。この場合、新しい HR の導入は避けられません。 これにより、HR の数が最小限になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    # stack of (remaining_life, hire_day_index)
    stack = []
    
    # we assign one HR per day
    # we maintain current assignment pool
    hr_count = 0
    ans = [0] * n
    
    # track active HR restrictions due to "cannot reuse same HR for hire/fire"
    # we model this as HR used in currently "open" worker lifetimes
    active_hr = set()
    
    for day in range(n):
        f, h = map(int, input().split())
        
        # fire f workers (LIFO)
        for _ in range(f):
            hr_used = stack.pop()
            active_hr.add(hr_used)
        
        chosen = None
        
        # try reuse existing HR if not blocked today
        for hr in range(1, hr_count + 1):
            if hr not in active_hr:
                chosen = hr
                break
        
        if chosen is None:
            hr_count += 1
            chosen = hr_count
        
        ans[day] = chosen
        
        # hire h workers, all handled by chosen HR
        for _ in range(h):
            stack.append(chosen)
        
        # clear restrictions after day processed
        active_hr.clear()
    
    print(hr_count)
    print(*ans)

if __name__ == "__main__":
    solve()
```解雇の対象となるのは常に最後に雇用された従業員であるため、スタックには各従業員の雇用を担当する HR のみが保存されます。 私たちが解雇を求めに行くとき、その人事担当者をその日の任務に参加できないものとして一時的にマークし、雇用する人事担当者によって労働者を解雇できないというルールを強制します。 

貪欲な選択では、既存の HR ID をスキャンし、ブロックされていないものを再利用し、必要な場合にのみ新しい ID を作成します。 重要な点は、毎日の後に設定された制限をクリアすることです。これは、制約が無関係な日には適用されず、同じワーカーのライフサイクル関係内にのみ適用されるためです。

 ## 特殊なケース

 重要なエッジケースは、その日に解雇されたすべての労働者が同じ人事部に雇用されていた場合です。 その場合、その HR はその日の割り当てに対して完全にブロックされ、他の HR が存在する場合でも新しい HR を強制的に作成することになります。 

入力：```
2
0 2
2 0
```1 日目には、HR 1 が割り当てられ、すべての雇用者に 1 のラベルが付けられます。2 日目には、解雇された従業員は両方とも HR 1 から発生しているため、その日は HR 1 が無効になります。 アルゴリズムは、アクティブな制限セットを通じてこれを正しく検出し、HR 2 を作成します。 

もう 1 つの特殊なケースは、何日間も発砲が行われない場合です。 スタックは増加しますが、制約がトリガーされないため、同じ HR が繰り返し再利用され、HR カウントが最小限に抑えられ、安定した状態に保たれます。
