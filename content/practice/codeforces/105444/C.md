 ## 解決策
 ## 問題の理解

 私たちにはコインの束がいくつか与えられました。 1 回の移動で、2 人のプレイヤーが共同で 2 つの異なるスタックを選択し、それらのスタックのそれぞれからちょうど 1 枚のコインを取り除きます。 どこにもコインがなくなるまでこれを続けます。 課題は、これが可能かどうかを判断し、可能であれば有効な一連の動きを構築することです。 

入力はスタックの高さのリストだけです。 それぞれの高さは、すべての動きにわたってそのスタックを何回選択する必要があるかを示します。これは、スタック内のすべてのコインを正確に 1 回削除する必要があり、各選択でそのスタックからちょうど 1 枚のコインが削除されるためです。 

主要な構造上の制約は、すべての移動が 2 つの異なるスタックを消費することです。 これにより、直ちにグローバル カップリングが作成されます。各移動で 2 枚のコインが削除されるため、削除の総数は偶数でなければなりません。 また、スタックは異なる動きでのみ他のスタックと組み合わせることができるため、他のスタックと比較して「大きすぎる」スタックはあってはならないことも意味します。 

n ≤ 50 および合計コイン ≤ 1000 という制約は、操作を明示的にシミュレートまたは構築できることを意味します。 O(合計コイン · n) 個の作業を実行するソリューションで十分であり、繰り返しスキャンする貪欲な方法でも問題ありません。 

素朴な推論による微妙な失敗例は、1 つのスタックが残りのスタックを支配する場合に現れます。 たとえば、入力について考えてみましょう。`[5, 1, 1]`。 単純な試みでは、最大のスタックが空になるまで常に他の空でないスタックとペアにしようとする可能性があります。 しかし、2 回移動した後、小さいスタックはすでに使い果たされていますが、大きいスタックにはまだコインがあるため、続行できなくなります。 1 つのスタックが他のすべてのスタックの合計を超えているため、正しい出力は「no」です。 

もう 1 つのエッジ ケースは、合計が奇数である場合です。たとえば、`[1, 1, 1]`。 1手ごとに合計コインが2つ減るため、ゼロにすることは不可能です。 

## アプローチ

 ブルートフォースの観点では、考えられるすべてのペアリングのシーケンスをシミュレートしようとします。 各状態はスタック サイズのベクトルであり、各遷移は 2 つの非ゼロ スタックを選択します。 分岐係数はおよそ O(n²) で、深さはコインの総数に達するため、探索空間は n = 10 の場合でも実現可能性をはるかに超えて爆発的に増加します。 

シーケンスについて考えるのをやめ、代わりにペアリングの実現可能条件について考えれば、この問題は対処可能になります。 各スタック i は、他のスタックのスタブと一致する必要がある「スタブ」を提供します。 私たちは事実上、頂点 i の次数 ai があり、各エッジが 2 つの頂点間の 1 つの移動に対応する n 個の頂点上にマルチグラフを構築できるかどうかを尋ねています。 

これは、同じスタックを 2 回選択できないためループが禁止されていることを除けば、与えられた次数シーケンスを持つ単純な無向グラフを実現する古典的な条件とまったく同じです。 したがって、単純なグラフが必要です (同じペア間での複数の移動が許可されるため、自己ループやマルチエッジの制限は実際には問題になりません。つまり、これはマルチグラフ実現の問題です)。 

必要十分条件とは、次数の合計が偶数であるかどうか、および最大の次数が他のすべての次数の合計を超えていないかどうかをチェックすることになります。 これらが当てはまる場合、建設的な貪欲なプロセスが常に機能し、現在残っている最大の 2 つの次数を繰り返し接続します。 

これはハベル・ハキミと同じ直感ですが、ここではエッジを動きとして明示的に記録します。

 ## アルゴリズムのチュートリアル

 残りのコイン数をマルチセットのような構造として維持し、最大の残り数を持つ 2 つのスタックを繰り返しペアにします。 

1. すべてのコインの合計を計算します。 奇数の場合は「no」を出力します。 これが必要なのは、各手でちょうど 2 枚のコインが削除されるため、パリティが一致する必要があるためです。 
2. 現在のスタック数とそのインデックスのリストを管理します。 
3. すべてのカウントがゼロになるまで、次の操作を繰り返し実行します。 

1. まだ正の残りカウントが最大の 2 つのスタックを選択します。 
2. プラスのスタックが 2 つ未満しか残っていないが、コインがまだ残っている場合は、「いいえ」を出力します。 
3. 選択した両方のカウントを 1 ずつ減らし、このペアを移動として記録します。 

常に最大の 2 つを選択する理由は、大量の残りのスタックにパートナーが残っていない状況を避けるためです。 大規模なスタックの使用を遅らせると、後でスタックが分離される危険があります。 
4. 記録されたすべての動きを出力します。 

シーケンスを構築した後、各移動が合計コイン数を正確に 2 つ減らし、無効なセルフペアリングを決して試行しないという事実から妥当性が得られます。 

### なぜ効果があるのか

 このアルゴリズムは、各ステップの後でも、残りの次数のマルチセットを残りの頂点間の一連のペアとして実現できるという不変条件を維持します。 最大の 2 つの要素を選択すると、一致できない「支配的な残差度」の形成が防止されます。 これは、プロセスのすべてのプレフィックスで、単一のスタックが他のスタックの残りの容量の合計を超えないことを保証することに相当します。これは、完全なペアリング システムにおける唯一の構造的な障害です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    if sum(a) % 2:
        print("no")
        return

    moves = []

    while True:
        # collect positive stacks
        pos = [(a[i], i) for i in range(n) if a[i] > 0]
        if not pos:
            break

        if len(pos) == 1:
            print("no")
            return

        pos.sort(reverse=True)
        (c1, i), (c2, j) = pos[0], pos[1]

        if c1 == 0 or c2 == 0:
            print("no")
            return

        a[i] -= 1
        a[j] -= 1
        moves.append((i + 1, j + 1))

    print("yes")
    for u, v in moves:
        print(u, v)

if __name__ == "__main__":
    solve()
```この実装では、アクティブなスタックのリストを繰り返し再構築し、それを並べ替えて最大の 2 つを見つけます。 n ≤ 50 で合計操作数 ≤ 1000 の場合、移動ごとにこの O(n log n) で十分です。 

最もデリケートな部分は、ポジティブ スタックが 1 つだけ残っている場合の処理​​です。 すべての移動が 2 つの異なるスタックを消費するため、そのような状況は直ちに不可能になります。 

## 実用的な例

 ### 例 1

 入力:`n = 4, a = [1, 4, 3, 0]`プロセスを追跡します。 

| ステップ | 残りのカウント | 選択されたペア | 更新された数 |
 | --- | --- | --- | --- |
 | 1 | [1,4,3,0] | (2,3) | [1,3,2,0] |
 | 2 | [1,3,2,0] | (2,3) | [1,2,1,0] |
 | 3 | [1,2,1,0] | (2,1) | [0,1,1,0] |
 | 4 | [0,1,1,0] | (2,3) | [0,0,0,0] |

 これは、常に最大の 2 つを取得することで、より小さいスタックの早期枯渇を防ぎながら、依然として支配的なスタックを着実に減らしていく方法を示しています。 

### 例 2

 入力:`n = 3, a = [1, 1, 1]`| ステップ | 残りのカウント | 選択されたペア | 更新された数 |
 | --- | --- | --- | --- |
 | 1 | [1,1,1] | (1,2) | [0,0,1] |

 これで、正のカウントを持つスタックが 1 つだけ残りますが、2 番目のスタックは存在しません。 アルゴリズムはこれを検出し、「いいえ」を返します。 

これは、たとえ合計が偶数であっても、ペアリングには各ステップで少なくとも 2 つのアクティブなスタックが必要であるため、実現可能性が失敗することを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n · 移動 · log n) | 各移動は最大 n スタックまでスキャンおよびソートされ、最大 1000 の移動が存在します。 
| スペース | O(n) | 現在のカウントと出力シーケンスを保存します。 

境界は十分に小さいため、並べ替えを繰り返しても簡単です。 制限要因はペアリング ロジックの正確さだけであり、パフォーマンスではありません。

            a[j] -= 1

    with redirect_stdout(out):

 ## 特殊なケース

 すべてのコインが取り除かれる前に、ちょうど 1 つのスタックがゼロ以外のままになると、アルゴリズムは停止し、「いいえ」と出力されます。 入力用`[3, 0, 0]`の場合、最初の反復では正のスタックが 1 つだけ見つかり、すぐに失敗がトリガーされます。 これは正しいです。どの手も 2 つの異なるスタックを選択できないため、残ったコインは消費できません。 

合計値が奇数の場合など`[1, 1, 1]`、アルゴリズムはシミュレーション前に拒否します。 貪欲なペアリングの試みが開始されたとしても、最終的には 1 つの残りのコインに達するため、パリティを早期に検出することで不必要な作業を回避できます。 

1 つのスタックが他のスタックよりもはるかに大きい場合、たとえば、`[5, 1, 1, 1, 1]`、最大の 2 つのスタックを繰り返し選択すると、利用可能な小さいスタックと常にペアになった状態で、大きいスタックが徐々に削減されます。 初期の最大の戦略を無視する戦略は、最後にはマッチしないままになる危険性がありますが、貪欲なペアリングは継続的に消耗させることでそれを回避します。
