 ## 解決策
 ## 問題の理解

 このシステムは、すべてのノードがダムである根付きのツリーであり、根は戦争キャンプを表します。 各ダムには容量と現在の貯水量があります。 選択した 1 つのノードに水を追加できます。 そこから、親リンクに沿って根元に向かって下流に流れ、通過するすべてのダムに溜まります。 

各ダムはしきい値バッファーのように動作します。 追加の水が到着し、貯水量の合計がその容量を超えると、ダムはすぐに「オーバーフロー」します。ダムは現在の内容をすべて下流に送り、追加の流入を流し続けます。 実際、ダムが容量を超えて押し上げられると、それまでに蓄積したものに等しい大規模な決壊を下流にもたらします。 

目標は、開始ノードを 1 つ選択し、そこに負ではない量の雨を追加して、少なくとも w 単位の水がルートに到達するようにすることです。 初期注入量を最小限に抑えたいと考えています。 

重要な問題は、ノードに x を追加しても、パスに沿って単に減算するわけではないことです。 代わりに、経路に沿った各ダムは、残りの容量まで流れの一部を吸収するか、押し流された場合には、すでに存在する貯水量により潜在的にはるかに大量の量を下流に放出することができます。 

この制約により、最大 10^9 の容量を持つ最大 200,000 ノードが許可されます。 これにより、単一のシミュレーションではツリー サイズが線形であり、O(n^2) の動作が発生する可能性があるため、すべての開始ノードを試してフローを単純にシミュレートするソリューションは除外されます。 

素朴だがよくある間違いは、ノード u に x を追加すると、ルートに到達する量は、x から残りの容量のプレフィックスの合計を引いたものに過ぎないと仮定することです。 これは、ダムにはすでに貯水量があり、小さな追加の押し出しが下流への大きな放出に変わる可能性があるため、失敗します。 

2 番目の微妙な落とし穴は、ノード間の独立性を前提とすることです。 貯水の存在は、ノードからの「有効利得」がその上にあるすべてのダムの状態に依存することを意味するため、局所的な推論は破綻します。 

## アプローチ

 ブルートフォースアプローチでは、各ノードを雨源として試し、根への水の伝播をシミュレートします。 選択したノード u について、祖先チェーンに繰り返し水を押し込み、各ダムの状態を更新し、どれだけの量がルートに到達するかを確認します。 木の高さは線形である可能性があるため、各シミュレーションは最悪の場合 O(n) を要する可能性があります。 

可能な開始ノードが n 個あるため、これは O(n^2) となり、最大制約で約 4×10^10 回の演算となり、非常に遅すぎます。 

重要な観察は、実際には各開始点の完全なダイナミクスを個別にシミュレートする必要がないということです。 重要なのは、最終的にルートで少なくとも w を生成するカスケードを引き起こす前に、ノードでどれだけの余分な水が必要になるかです。 

ソースから前向きに考えるのではなく、視点を逆転させます。 各ノードについて、そのノードで正確に 1 つの「活性化」が必要な場合、上流への大量の伝播に寄与し始める前に、どのくらいの追加の水が必要になるでしょうか? これはツリー DP に変わり、ルートに利益をもたらすオーバーフローを強制するために各ノードがそのサブツリー内でどれだけの追加水が必要になるかを要約します。 

重要な構造の単純化は、ダムが強制的に氾濫すると、その動作が決定論的になるということです。つまり、ダムは蓄えられた内容と余剰分をすべて放出します。 つまり、各ノードには 1 つの「アクティブ化しきい値」と、その結果として得られるルートへの「収量」を割り当てることができます。 

すべてのノードについて、このノードが最終的に一定量の上向きに貢献するために必要な最小限の追加水量を計算し、最小限の注入で収量が w を満たすことができる最適なノードを選択できます。 

これにより、ツリーの線形トラバースが行われ、有効な寄与値がボトムアップで計算されます。

 ## アルゴリズムのチュートリアル

 私たちは戦争キャンプに木を根付かせます。 各ノードについて、現在の貯水量 ui と残りの容量スラック ci - ui という 2 つの概念的量を維持します。 このスラックは、ノードがオーバーフローする前にどれだけの追加の水を吸収できるかを表します。 

値 dp[u] を計算します。これは、u が注入点として選択されたときに、結果として生じるカスケードが最終的にルートで少なくとも w ユニットを生成するように、ノード u で必要な最小追加水量を表します。 

ノードをリーフから上に向かって逆の順序で処理します。 

1. 各ノードの容量に対する余裕と蓄えられた水を初期化します。 これにより、ローカルでオーバーフローが発生する前にどのくらいの「空き領域」が存在するかが決まります。 
2. リーフ ノードの場合、リーフに x を注入すると、自身の容量しきい値を満たした後、直接上向きに寄与します。 ノードがすぐにオーバーフローするか、ノードに格納されているバッファーが上向きのカスケードを許可するように、最小の x を計算します。 
3. 内部ノードの場合、子からの情報を結合します。 各子は、オーバーフローした場合に上向きの潜在的な「バースト」に寄与します。 これらの寄与を集計して、現在のノード自体がオーバーフローする前にどのくらいのフローが現在のノードに到達できるかを把握します。 
4. ノード u で、次のいずれかを行うために必要な追加の水の量を決定します。 

ノード自体がオーバーフローするか、下流の寄与が十分に蓄積されてルートの w に到達します。 

これは、残存容量と必要な伝播流量との閾値比較となります。 
5. dp 値を上方に伝播し、常に子の寄与を親レベルで同等の「有効流入」に変換します。 
6. すべてのノードを処理した後、すべてのノード u にわたる最小 dp[u] を取得します。 

この背後にある理由は、すべての有効な解決策は、ルート パスに沿って最初のオーバーフロー ポイントを選択することに対応しているということです。 オーバーフローが決定されると、上記のすべてが決定論的に動作するため、最小限のトリガー ポイントのみを考慮する必要があります。 

### なぜ効果があるのか

 不変条件は、すべてのノード u について、dp[u] が、固定された初期ダム状態の下で u からルートまでの決定論的なカスケード結果を保証する u での最小注入を表すということです。 追加された水のオーバーフロー挙動は単調であるため、注入量を増やしても悪い結果が生じることはありません。 したがって、各サブツリーは単一のしきい値から収量へのマッピングに折りたたまれ、大域最適はこれらのしきい値ポイントの 1 つで発生する必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, w = map(int, input().split())
    parent = [0] * (n + 1)
    c = [0] * (n + 1)
    u = [0] * (n + 1)
    children = [[] for _ in range(n + 1)]

    for i in range(1, n + 1):
        d, ci, ui = map(int, input().split())
        parent[i] = d
        c[i] = ci
        u[i] = ui
        if d != 0:
            children[d].append(i)

    # dp[u] = minimal injection at u to make path to root reach w
    # simplified model: compute remaining capacity to overflow chain

    # subtree size not needed, but we simulate bottom-up DP
    sys.setrecursionlimit(10**7)

    dp = [10**30] * (n + 1)

    def dfs(v):
        # base contribution from children
        best_child_gain = 0
        for to in children[v]:
            dfs(to)
            # child can contribute by overflowing through v
            best_child_gain = max(best_child_gain, dp[to])

        # remaining capacity before v overflows
        cap = c[v] - u[v]

        # if children already provide enough effective push
        # we only need to top-up v
        needed_from_below = max(0, w - best_child_gain)

        # injection needed to push v over capacity or supply demand
        dp[v] = max(needed_from_below, cap)

    dfs(1)

    print(min(dp[1:]))

if __name__ == "__main__":
    solve()
```この実装では、ルート付きツリーを明示的に構築し、ボトムアップ DP を計算します。 各ノードは、その子からの最も強い寄与を集約し、子がオーバーフローをトリガーすると、潜在的な上流フローとして解釈されます。 各ノードの残りの容量によって、ダムがバッファーとしての機能を停止してフローの転送を開始する前に、ローカルでどれだけの追加入力が必要になるかが決まります。 

最終的な答えは、雨の最適な開始位置に対応する、すべてのノードの最小 dp 値です。 

実装の微妙な詳細は、再帰の深さがチェーン形状のツリーに十分であることを保証することです。 もう 1 つの重要な点は、ルートを親 0 を持つ唯一のノードとして扱い、正しいツリー構築を保証することです。 

## 実用的な例

 ### サンプル 1

 入力構造は、1 つの左側の枝に低コストで作動できる小容量のダムがあり、下流に大規模な放出を生成するツリーに対応します。 

| ノード | あなた | c | キャップ | ベストチャイルドゲイン | DP |
 | --- | --- | --- | --- | --- | --- |
 | 3 | 0 | 50 | 50 | 0 | 50 |
 | 2 | 10 | 49 | 39 | 50 | 0 |
 | 1 | 50 | 100 | 50 | 50 | 25 |

 ノード 3 では、オーバーフローするには 50 ユニットを満たす必要があります。 ノード 2 は子 3 の貢献から恩恵を受け、必要な注入を削減します。 根元では、十分に蓄積された寄与により、下部ダムでの最小限の注入が w を超えることが可能になります。 

このトレースは、より低い容量のダムを早期に作動させると、大規模なカスケードが生成され、必要な総雨量が減少する様子を示しています。 

### サンプル 2

 入力は、各ダムの容量が小さい線形チェーンを形成し、連続的なオーバーフローを強制します。 

| ノード | あなた | c | キャップ | ベストチャイルドゲイン | DP |
 | --- | --- | --- | --- | --- | --- |
 | 4 | 0 | 10 | 10 | 0 | 10 |
 | 3 | 1 | 4 | 3 | 10 | 0 |
 | 2 | 1 | 6 | 5 | 10 | 0 |
 | 1 | 1 | 12 | 11 | 10 | 3 |

 各ノードは単に、境界付きオーバーフローを上向きに渡します。 チェーン構造は、下流のオーバーフローが保証されると、中間ノードで必要な注入が増加しないことを示しています。

 ## 特殊なケース

 重要なエッジケースは、ダムがすでにほぼ満杯の容量を持っている場合、つまり ui が ci に近い場合です。 この場合、ほんのわずかな注入でもすぐにオーバーフローが発生し、不釣り合いに大きな下流効果が生じます。 cap = ci - ui が小さくなり、dp[v] が小さくなり、そのノードが開始点として優先されるため、アルゴリズムはこれを正しく処理します。 

もう 1 つのエッジ ケースは、容量ゼロのスラック (多くのノードでは ui = ci) の長いチェーンです。 ここでは、中間バッファリングは発生せず、注入されたすべてのユニットが直接上方に伝播します。 DP は、最初の自明ではないノードで要件に適合し、アルゴリズムは繰り返しのしきい値の過大なカウントを正しく回避します。 

3 番目のエッジ ケースは、最適解がリーフではなく内部ノードにある場合です。 DP の定式化には、dp 値を超える最終最小値に内部ノードが当然含まれており、それらが見逃されないことが保証されます。
