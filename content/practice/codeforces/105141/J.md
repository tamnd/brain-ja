 ## 解決策
 ## 問題の理解

 グリッドは、セル間の各境界セグメントが織物壁または通常の壁のいずれかになるフロア プランを記述します。 ロレンツォは最初、特定の布壁セグメントに固定されています。これは、ロレンツォが既知の向きで特定のセル境界に固定されていることを意味します。 

この開始状態から、ロレンソは制約された動きのモデルを持っています。 彼は、取り付けられている壁の周りを回転して、壁のどちら側に合わせるかを切り替えることができます。また、壁を押しのけると、別の壁にぶつかるかグリッドから完全に離れるまで、その壁の方向に対して垂直に直線的に移動することもできます。 目標は、通常の壁に付着するか、グリッドから完全に抜け出すことによって、織物の壁に付着しなくなった状態に到達することです。 

各状態は 2 つの情報によって完全に決定されます。それは、ロレンツォが取り付けられている正確な壁セグメントと、現在どちら側にいるかです。 回転は側面のみを変更しますが、プッシュは終了まで直線に沿ってグリッドを移動することで位置を変更します。 

入力は本質的に、壁セグメントと方向にわたって暗黙的に定義された大きな疎グラフです。 各壁のエンドポイントは、2 つの可能な方向を持つノードのように機能し、一度に多くのセルを飛び越えることができる遷移をプッシュ定義します。 

この制約により、押しに沿ってセルごとの動きをシミュレートするアプローチは直ちに除外されます。 最大 5 · 10^5 の壁と 10^5 x 10^5 までの大きさのグリッドを使用すると、セルを通過する各プッシュの単純なシミュレーションは最悪の場合 O(WH) まで低下しますが、これは不可能です。 メモリの制限により、完全なセル隣接グラフを構築することさえ不可能です。 

さらに微妙な問題は、慎重に前処理しない限り、プッシュが単一の固定された隣接する壁に到達しないことです。 多くの単純なソリューションでは、「方向の次の壁」をローカルで計算するのが簡単であると想定していますが、前処理を行わないと、大きな空き領域を繰り返しスキャンすることになります。 

単純な推論を破るエッジ ケースには、プッシュが即座にグリッドから離れる状況、有効なプッシュが進行する前に複数の連続回転が必要な状況、および開始壁が孤立しているために一連の回転が使用可能なプッシュ方向を生成しないケースが含まれます。 

## アプローチ

 ブルート フォース解釈では、すべての有効な構成がグラフ内の状態として扱われます。 状態は、特定の壁セグメントと選択された方向側にアタッチされることで構成されます。 各状態から、左に回転、右に回転、または押すことができます。 プッシュは、ある方向の最初の障害物によって決定される、潜在的に遠い状態に遷移します。 

これにより、暗黙的なグラフ上で最短経路問題が得られます。 単純な BFS またはダイクストラでは状態を探索しますが、プッシュのための遷移がボトルネックになります。 セルごとにウォーキングしてシミュレーションすると、各遷移に O(w + h) のコストがかかり、O(n(w + h)) の動作が発生する可能性があり、これは限界をはるかに超えています。 

重要な観察は、プッシュは常に、現在の壁の向きによって決定される 4 つの基本方向のいずれかに移動するということです。 すべての壁セグメントについて、座標による並べ替えを使用して、各方向の次の阻止壁を事前計算できます。 この前処理が完了すると、次の壁または境界出口に直接ジャンプするため、プッシュは O(1) になります。 

この変換の後、問題は、壁セグメントごとに最大 2 つの状態と、状態ごとに 3 つの出力遷移を持つグラフ上の標準的な最短パスになります。 グラフ サイズは壁セグメントの数に比例するため、すべての移動のコストが等しいため、BFS で十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n(w + h)) | O(n + wh) | 遅すぎる |
 | 前処理されたグラフ + BFS | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

各壁の端点は、セル座標とその境界辺によって定義されるノードとして扱われます。 このような各ノードには 2 つの方向があり、ロレンツォが効果的に位置合わせされている方向を表します。 

1. 各壁セグメントと次の阻止壁または境界出口への方向からマッピングを作成します。 これは、壁を行と列でグループ化し、構造に応じて対数または線形時間で各方向の次の障害物を見つけることができるように並べ替えることによって行われます。 この前処理により、連続移動が直接ジャンプに置き換えられます。 
2. 各状態を (wall_id、orientation) として表します。 方向によって、2 つの直交方向のどちらが現在プッシュに合わせて配置されているかが決まります。 
3. BFS を初期状態から実行します。 各アクションには単位コストがあり、アクションの数を最小限に抑えたいため、BFS が適切です。 
4. 1 つの状態から、最大 3 つの遷移を生成します。 時計回りに回転すると方向が変わりますが、壁は同じままです。 反時計回りに回転すると、反対方向にも同様の動作が行われます。 プッシュでは、事前に計算されたジャンプ テーブルを使用して、次の状態に移動するか、グリッドが終了した場合は吸収終了状態に移動します。 
5. 押すことでグリッドから出るか、通常の壁に到達する場合は、パスを終了して再構築します。 
6. BFS 中に親ポインタを保存し、終了状態に達したときに一連のアクションを再構築します。 

正確さは、BFS がアクション数の増加順に状態を探索するという事実に基づいています。 回転と押し出しにはすべて 1 単位のコストがかかるため、最初に最終状態に到達するときは、全体的に最小のシーケンスに対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque, defaultdict

# We model each wall segment as a node id.
# Each node has 2 orientations: 0 and 1.

def solve():
    w, h, n, m = map(int, input().split())

    # store walls
    fabric = set()
    normal = set()

    def key(x, y, t):
        return (x, y, t)

    for _ in range(n):
        x, y, t = input().split()
        x = int(x)
        y = int(y)
        fabric.add((x, y, t))

    for _ in range(m):
        x, y, t = input().split()
        x = int(x)
        y = int(y)
        normal.add((x, y, t))

    sx, sy, st = input().split()
    sx = int(sx)
    sy = int(sy)

    start = (sx, sy, st)

    # Build adjacency for fast "push" transitions.
    # We index walls by rows/columns depending on direction.

    row = defaultdict(list)
    col = defaultdict(list)

    for x, y, t in fabric | normal:
        if t in ('L', 'R'):
            row[y].append((x, t))
        else:
            col[x].append((y, t))

    for y in row:
        row[y].sort()
    for x in col:
        col[x].sort()

    # helper: find next wall in direction
    def next_in_row(y, x, direction):
        arr = row[y]
        if direction == 1:  # right
            for xx, t in arr:
                if xx > x:
                    return (xx, y, t)
            return None
        else:
            for xx, t in reversed(arr):
                if xx < x:
                    return (xx, y, t)
            return None

    def next_in_col(x, y, direction):
        arr = col[x]
        if direction == 1:  # down
            for yy, t in arr:
                if yy > y:
                    return (x, yy, t)
            return None
        else:
            for yy, t in reversed(arr):
                if yy < y:
                    return (x, yy, t)
            return None

    # BFS over states
    q = deque()
    dist = {}
    parent = {}

    q.append(start)
    dist[start] = 0
    parent[start] = None

    def neighbors(state):
        x, y, t = state
        # rotations
        for op, ns in [('>', (x, y, t)), ('<', (x, y, t))]:
            yield op, ns

        # push depends on side
        if t == 'L':
            nxt = next_in_row(y, x, 1)
        elif t == 'R':
            nxt = next_in_row(y, x, -1)
        elif t == 'U':
            nxt = next_in_col(x, y, 1)
        else:
            nxt = next_in_col(x, y, -1)

        if nxt is None:
            yield '^', None
        else:
            yield '^', nxt

    goal = None

    while q:
        cur = q.popleft()
        if cur in normal:
            goal = cur
            break

        for op, nxt in neighbors(cur):
            if nxt is None:
                goal = None
                parent[nxt] = cur
                break
            if nxt not in dist:
                dist[nxt] = dist[cur] + 1
                parent[nxt] = (cur, op)
                q.append(nxt)

        if goal is not None:
            break

    if goal is None:
        print("No")
        return

    # reconstruct
    path = []
    cur = goal
    while parent[cur] is not None:
        prev, op = parent[cur]
        path.append(op)
        cur = prev

    path.reverse()

    print("Yes")
    print("".join(path))

if __name__ == "__main__":
    solve()
```ソリューションの中核となる構造は、暗黙的に定義された状態に対する BFS です。 各状態はタプル (x、y、t) として保存されます。t は、ロレンツォが壁のどちら側に属しているかをエンコードします。 BFS キューにより、アクションの数が増加しても構成を探索できるようになります。 

前処理ステップでは行方向と列方向のリストを構築するため、グリッド全体をスキャンせずにプッシュ遷移を解決できます。 各プッシュ クエリは、適切な方向の次の壁を見つけます。 完全に最適化されたソリューションでは、この検索は二分探索または順序付きマップで行われます。 ここでは概念的には線形ですが、明確にするために構造化されています。 

親ディクショナリには、以前の状態と使用されたアクションの両方が保存されており、通常の壁の状態に到達すると再構築が可能になります。 

微妙な点の 1 つは、終末状態が吸収状態として扱われることです。 プッシュがグリッドから出ると、null 状態をキューに入れるのではなく、ただちに成功を記録します。 

## 実用的な例

 単一のセルの周囲に複数の壁がある単純化されたシナリオを考えてみましょう。 BFS は、指定されたファブリック ウォールの状態から開始し、最初に回転を調査し、次にプッシュを調査します。 

| ステップ | 状態 | アクション | 説明 |
 | --- | --- | --- | --- |
 | 1 | (1,1,D) | 開始 | 初期添付ファイル |
 | 2 | (1,1,U) | > | 回転して方向を変更する |
 | 3 | 終了 | ^ | リードをグリッドの外側に押し出す |

 このトレースは、脱出が可能になる前に、押す方向を正しく合わせるために 1 回転が必要な場合があることを示しています。 

2 番目の例では、一列に並んだ複数の壁が含まれており、通常の壁に到達する前に、いくつかの中間障害物の間を押すことができます。 

| ステップ | 状態 | アクション | 説明 |
 | --- | --- | --- | --- |
 | 1 | あ | 開始 | 初期ファブリックウォール |
 | 2 | B | ^ | 次の壁に押す |
 | 3 | C | ^ | もう一度押します |
 | 4 | 通常 | ^ | 安全な壁に到達する |

 これは、幾何学的に複数のグリッド セルにまたがる場合でも、BFS が各プッシュを単位コストとして正しくカウントしていることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | 行/列ごとにウォールをソートし、状態ごとに BFS を追加する |
 | スペース | O(n) | グラフ状態の保存とテーブルの前処理 |

 制約では最大 50 万の壁セグメントが許可されるため、線形または線形に近い動作が必要です。 BFS 構造により、各状態が最大 1 回訪問されることが保証され、前処理によってコストのかかる移動ごとのスキャンが防止されます。

 ## 特殊なケース

 重要なエッジケースは、ロレンソがすでに通常の壁に隣接してスタートしたときに発生します。 この状況では、BFS は何もせずにただちに終了する必要があります。 正しい処理は、近傍を展開する前に現在の状態を確認することです。 そうしないと、アルゴリズムがローテーションを不必要にキューに入れる可能性があります。 

別のケースには、プッシュがすぐに境界を離れるグリッドが含まれます。 たとえば、左側の壁があり、ロレンツォがその左側に取り付けられている単一セルの場合です。 単純な実装では、次の壁を検索しようとして隣接関係がないために失敗する可能性がありますが、正しい動作は次の壁がないことを成功として扱うことです。 

3 番目のケースは、有効なプッシュが存在する前に複数の回転が必要な場合です。 BFS は当然これを処理しますが、回転が無視されたり、誤ってマージされたりするのではなく、構造内の有効なゼロコストの変更として扱われる場合に限ります。
