 ## 解決策
 ## 問題の理解

 私たちには、洗濯アイテムの固定されたコレクションが与えられており、各アイテムには物理的な幅と乾燥プロファイルがあります。 複数の週にわたって、ハリーは同じ長さの 2 本の平行な物干し竿を持っていますが、利用できる長さは週ごとに変わります。 すべてのアイテムは週の初めにすぐに吊るす必要があり、通常どおり吊るす場合は 1 行のスペースを占有します。または、両方の行に分割することもできます。その場合、両方の行のスペースが同時に使用されますが、乾燥が速くなります。 

したがって、各アイテムには 2 つの「モード」があります。 通常モードでは、一定の長さの連続したセグメントを占有します。$d_i$一行で終了$t^{slow}_i$。 アクセラレーション モードでは、同じ幅を占めますが、両方の行にまたがって拡張され、両方のスペースを同時に消費し、後で終了します。$t^{fast}_i$、 どこ$t^{fast}_i \le t^{slow}_i$。 特定の週の目標は、各アイテムを 2 つのモードのいずれかに割り当て、すべてのアイテムの最大乾燥時間を最小限に抑えるために、すべてのアイテムを 2 つのラインに重ならないように配置することです。 線の長さの制約内に収まる配置が存在しない場合は、不可能を出力する必要があります。 

入力により得られるのは、$N$アイテムを一度。 各クエリは行の長さを示します$L_j$。 クエリごとに、達成可能な最適な終了時間を計算する必要があります。 

制約が十分に大きいため、クエリごとの貪欲な配置やすべての項目にわたるシミュレーションは不可能です。 と$N \le 3 \cdot 10^4$そして$Q \le 3 \cdot 10^5$、 平$O(N)$クエリごとにすでにプッシュされています$10^9$操作。 これにより、クエリごとに割り当てを最初から再計算することが直ちに排除されます。 

主な問題点は、高速モードを使用できるかどうかが回線容量に依存し、アイテムのさまざまなサブセットが回線容量に応じてモードを切り替える必要がある場合があることです。$L$これにより、構造が本質的にグローバルになります。 

素朴な推論による微妙な失敗例は、アイテムを幅でソートし、貪欲に配置することで最適性が得られると仮定することです。 たとえば、常に高速に処理するために最大のアイテムを選択すると、小さくても多数のアイテムがブロックされてライン容量が無駄になる可能性があります。 もう 1 つの失敗モードは、実現可能性を 1 行につき 1 つのナップザックとして扱うことです。 これは、高速モード項目が両方の行を同時に消費することを無視します。 

## アプローチ

 直接的な総当たりアプローチでは、各項目のすべての割り当てを低速モードまたは高速モードで試行し、割り当てごとに項目が 2 行の長さにパックできるかどうかを確認します。$L$。 貪欲なビン パッキング戦略を使用してパッキングが最適に行われたとしても、モード割り当ての数だけでも$2^N$、それは不可能です。 

閾値時間を固定しても$T$を含むアイテムのみを許可します$t^{fast}_i \le T$高速モードは空間リソースを 2 倍消費するため、潜在的に高速になるためには、これらの項目のどのサブセットを実際に高速モードに割り当てるかを決定する必要があります。 重要な観察は、問題は項目の順序付けではなく、高価な「2 行」リソースと単一行リソースに割り当てる項目の数の選択にあるということです。 

この問題は、「広範囲に消費される」アイテムのサブセットを選択するという観点から再解釈できます (高速モード)。 アイテムが高速モードの場合、消費します$d_i$両方のラインから同時にユニットを取得します。そうでない場合は、ユニットが消費されます。$d_i$たった一行で。 利用可能なリソースの合計は 2 行の長さです$L$ただし、低速モードに割り当てられた項目は 2 つの行に分割されるため、実際の制約は合計幅の配分のバランスを取ることです。 

重要な簡素化は、固定時間しきい値の実現可能性を確認することで実現します。$T$。 以下の項目のみを考慮します。$t^{fast}_i > T$強制スローモードの候補と項目として$t^{fast}_i \le T$柔軟です。 柔軟な項目のうち、高速モードを選択すると、1 つの行の負荷は軽減されますが、両方の行の負荷が増加します。そのため、項目を幅でソートし、高速に処理する数を貪欲に決定することでトレードオフを特徴付けることができます。 

これにより、各実現可能性チェックが前処理して効率的に回答できる構造化された計算に変換され、回答時間の経過とともに二分探索が可能になります。

 ## アルゴリズムのチュートリアル

 ### 重要なアイデア: 答えの二分探索

 クエリごとの最終回答を値として扱います$T$。 固定の場合$T$、すべての項目が時間までに完了できるかどうかを確認します$T$最適な配置で。 

### ステップ 1: 高速時間で項目を前処理する

 項目ごとにグループ化します$t^{fast}_i$。 候補者にとって$T$、の付いたアイテム$t^{fast}_i > T$強制的に低速モードになります。 残りは低速モードと高速モードのどちらかを選択できます。 

これにより、「必須の低速」項目と「オプションの高速」項目が分離されます。 

### ステップ 2: 幅要件を計算する

 固定の場合$T$、すべてのアイテムが幅要件に影響します。 

アイテムが遅い場合は消費します$d_i$ちょうど 1 行で。 速いと消費する$d_i$両方の線で。 

したがって、高速アイテムは共有容量の点でより高価ですが、低速アイテムはより柔軟です。 

問題は、すべてを 2 行の長さに詰め込むために、どのオプション項目を高速にするかを決定することです。$L$。 

### ステップ 3: 負荷分散の実現可能性を下げる

 2 つの行を 2 つの容量の配列として解釈します。$L$。 遅い項目は行間で任意に分割できるため、単一ユニットの読み込みのように動作します。 高速アイテムは両方の行を均等に消費するため、同期されたロードのように動作します。 

重要な観察は、実現可能性は全幅と、どの程度の「2人占有」を導入するかによってのみ決まるということです。 

すべてのオプション項目を遅くすると、実現可能性が最も簡単になります。 項目を高速モードにすると柔軟性が低下するため、時間の制約を満たすために必要な場合にのみ実行します。 

### ステップ 4: ソート後の貪欲な構造

 オプションの項目を幅の降順で並べ替えます。 高速に割り当てる最適な候補は最大のアイテムです。これは、大きなアイテムを高速に割り当てると、構造上の制約に従って単一行の混雑が最も効果的に軽減されるためです。 この順序により、必要な高速割り当ての数をテストできます。 

高速モードに強制的に移行する最大のアイテムの数を繰り返し、梱包が可能になるかどうかを確認します。 

### ステップ 5: 固定構成の実現可能性チェック

 遅い項目と速い項目に分割すると、次のようになります。 

両方のラインがすべての低速アイテムに対応できること、および高速アイテムが共有容量を超えないことを確認する必要があります。 これは、各ラインに割り当てられた合計負荷が以下を超えていないかどうかをチェックすることになります。$L$、速いアイテムが両方を同時に占めることを考慮してください。 

両方の制約が満たされる場合、構成は実行可能です。 

### ステップ 6: クエリごとのバイナリ検索

 クエリの長さごとに$L_j$、最小限の二分探索を行います$T$実現可能性が保たれるように。 

### なぜ効果があるのか

 正しさは時間の経過に伴う実現可能性の単調性に依存する$T$。 時間内に全ての項目を終えることができれば$T$, その後、制約が緩和されるだけなので、より長い時間までに終了することもできます。より多くのアイテムが高速モードの対象になります。 この単調な構造により二分探索が可能になります。 

固定の範囲内で$T$、幅が意思決定の影響を支配し、高速モードでは行ごとの柔軟性が低下する一方で共有消費量が均一に増加するため、どのオプション項目を高速にするかを貪欲に選択することが最適です。 幅で並べ替えることにより、常に最も「配置にコストがかかる」アイテムを最初に変換することが優先されるため、実現可能性を損なう断片化を防ぐことができます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def feasible(items, L, T):
    slow = []
    fast = []

    for d, tf, ts in items:
        if ts <= T:
            # already finished even in slow mode
            continue
        if tf <= T:
            fast.append(d)
        else:
            slow.append(d)

    slow.sort(reverse=True)
    fast.sort(reverse=True)

    # try assign greedily to two lines
    left1 = L
    left2 = L

    # place fast items first (they occupy both)
    for d in fast:
        if left1 >= d and left2 >= d:
            left1 -= d
            left2 -= d
        else:
            return False

    # place slow items greedily on better-fitting line
    for d in slow:
        if left1 >= d:
            left1 -= d
        elif left2 >= d:
            left2 -= d
        else:
            return False

    return True

def solve():
    N, Q = map(int, input().split())
    items = [tuple(map(int, input().split())) for _ in range(N)]
    queries = [int(input()) for _ in range(Q)]

    # candidate times are all tf and ts values
    cand = sorted({x[1] for x in items} | {x[2] for x in items})

    def check(L):
        lo, hi = 0, len(cand) - 1
        ans = -1
        while lo <= hi:
            mid = (lo + hi) // 2
            if feasible(items, L, cand[mid]):
                ans = cand[mid]
                hi = mid - 1
            else:
                lo = mid + 1
        return ans

    out = []
    for L in queries:
        if not feasible(items, L, float('inf')):
            out.append("-1")
        else:
            out.append(str(check(L)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、まず実行可能性チェックを分離します。これは、特定の時間しきい値の下で項目が 2 行をどのように占めるかをシミュレートします。 高速モード項目は両方の行を同時に消費するように強制されますが、低速モード項目はスペースのある行に貪欲に詰め込まれます。 この貪欲な割り当ては、固定されているため機能します。$T$、重要なのは配置が存在するかどうかだけであり、正確な配置ではありません。 

次に、最適な答えは既存の情報から得られる必要があるため、ソルバーは関連するすべての時間候補を並べ替えられたリストに圧縮します。$t^{fast}_i$または$t^{slow}_i$。 各クエリについて、まず取り決めが存在するかどうかを確認します。 そうでない場合は、すぐに -1 を返します。 それ以外の場合は、候補時間を二分探索します。 

実装の微妙な詳細は、高速項目が両方の行を同時に制約するため、高速項目が低速項目の前に配置されるようにすることです。 この順序を逆にすると、誤って 1 行がオーバーフィルされ、実行可能な構成が誤って拒否されます。

 ## 特殊なケース

 重要なエッジケースは、条件を満たす項目がないためにすべての項目を低速モードにする必要がある場合です。$t^{fast}_i \le T$。 この場合、アルゴリズムは純粋な 2 行のビン パッキング問題に帰着します。 実行可能性関数は、スペースのある行に各項目を貪欲に配置しようとするため、引き続き機能します。 これにより、合計幅が超過した場合でも正しく拒否されることが保証されます。$2L$。 

もう 1 つのエッジ ケースは、1 つの大きな低速アイテムを除いて、ほとんどすべてのアイテムが高速である場合に発生します。 その 1 つの遅いアイテムにより、残りのアイテムの特定の分配が強制される可能性があり、最初に速いアイテムを注文することで、以前の配置によってブロックされないようにすることができます。 

最後に、いつ$L$非常に大きいので、すべてのアイテムが簡単に収まります。 高速配置は常に成功し、低速アイテムは競合することなく配布できるため、アルゴリズムがこれを処理します。その結果、即時に実行可能になり、可能な限り最小限の時間を返すバイナリ検索が行われます。
