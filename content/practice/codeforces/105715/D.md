 ## 解決策
 ## 問題の理解

 この構造はスキルのルート ツリーであり、すべてのノードがゲーム進行システムのスキルを表します。 各スキルにはタイプがあり、スキルのロックを解除するには、まずツリー内のその祖先のロックを解除する必要があります。 

重要な考え方は、どのスキルについても、そのスキルをルートとするサブツリー全体を調べ、そこに各タイプのスキルがいくつ出現するかを考慮するということです。 2 つのスキルのサブツリーにまったく同じタイプのマルチセットが含まれている場合、2 つのスキルは同等であるとみなされます。 このタスクは、同一のサブツリー タイプのマルチセットを生成する順序のないノードのペアの数をカウントすることです。 

問題は、ツリーが単一のルート構成に固定されていないことです。 各クエリは異なるノードをルートとして選択し、親子の方向を効果的に再設定します。 基礎となる無向ツリーが同じであっても、ノードのサブツリーは、どのノードがルートとみなされるかに応じて変化します。 選択したルートごとに、同一のサブツリー タイプのマルチセットを持つノードのペアがいくつあるかを再計算する必要があります。 

制約はテスト ケース全体で合計 200,000 ノードまで適用され、テストごとに最大 n 個のクエリが実行されます。 クエリごとにサブツリー構造を最初から再計算する単純なアプローチでは、クエリごとに完全な DFS が必要になります。これは n で線形です。 これにより、最悪の場合、約 n 乗の動作が発生し、数秒の実行時間には大きすぎます。 

ルートが変わると微妙な難しさが現れます。 ノードのサブツリーは固定されなくなったため、その表現はどの隣接ノードが「上向き」であるとみなされるかによって決まります。 たとえば、単純なチェーン 1-2-3-4 では、ルートが 1 の場合、ノード 2 にはサブツリー {2,3,4} がありますが、ルートが 3 の場合、ノード 2 のサブツリーは単なる {2,1} になります。 単一のルートに対して事前に計算されたサブツリー ハッシュに依存するアプローチは、クエリ全体で失敗します。 

別の失敗モードは、1 つの固定ルートから計算されたサブツリー ハッシュを比較し、再ルート後に再利用しようとすることです。 これは、ラベルだけでなくサブツリーのメンバーシップも変更されるため、問題が発生します。 サブツリーのアイデンティティは基本的にルートに依存します。 

## アプローチ

 ブルート フォース ソリューションでは、各クエリのルートを修正し、そのルートから DFS を実行して、すべてのノードに対してそのサブツリーの正規表現を計算します。 自然な表現の 1 つは、ノードのタイプと結合された子サブツリー ハッシュのマルチセットのハッシュです。 すべてのサブツリー ハッシュを計算した後、等しいハッシュの頻度を数え、等しいペアの数を計算します。 

これは正しいです。サブツリーのアイデンティティは、子構造を再帰的に結合することによって完全に取得されるからです。 ただし、各クエリには、DFS の O(n) 作業に加えて、ハッシュ集計の O(n) 作業が必要です。 最大 n 個のクエリの場合、これは O(n²) となり、最悪の場合でも約 10¹⁰ の操作が必要となり、現実的ではありません。 

重要な点は、ルートを変更してもサブツリー構造が恣意的に再シャッフルされるわけではないということです。 代わりに、再ルートすると、パスに沿って親子関係が反転されるだけです。 どのノードでも、新しいルートの下にあるその「サブツリー」は、元のツリー内の隣接するコンポーネントの少数の補完のうちの 1 つです。 これは、構造情報を一度事前計算してから、ほぼ一定時間または対数時間で各クエリに答える必要があることを示唆しています。 

有用な再構成は、すべてのノードを、選択したルートに関連する「コンポーネント タイプ」のシグネチャを定義するものとして扱うことです。 再ルートすると、古いルートから新しいルートへのパスに沿った隣接関係ごとに 1 つのエッジ方向のみが変更されます。 これにより、ツリー上で動的再ルート DP 技術を使用してサブツリー記述を維持できます。線形前処理ですべての可能なルート ビューの正規表現を計算し、ルックアップによってクエリに答えます。

標準ソリューションは、サブツリーのマルチセット表現がサブツリー ハッシュを使用してエンコードでき、再ルート化が 2 パス DP を使用して処理できるという事実に依存しています。つまり、最初にボトムアップのハッシュを計算し、次にすべてのノードに対してトップダウンの再ルート化されたハッシュを計算します。 すべてのノードがルートの下で正しいハッシュを取得したら、誘導されたサブツリー署名に従ってノードをグループ化することで、サブツリーがどのように動作するかを再構築し、クエリごとに同一の構造をカウントすることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | DP + ハッシュを再ルートする | O(n log n) または O(n) が償却 | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. まず、ノード 1 をベース ルートとして扱い、ツリーのルート バージョンを任意に計算します。 これにより、初期サブツリー ハッシュを計算するための安定した方向性が得られます。 ルートを固定する理由は、サブツリー定義には方向性が必要であり、一貫したベースラインが必要であるためです。 
2. ポストオーダー DFS を実行して、各ノードのサブツリーのハッシュを計算します。 各ノードのハッシュは、そのタイプとその子のハッシュのマルチセットから構築されます。 マルチセットをソートまたはハッシュすると、同型サブツリーが確実に同一の表現を生成します。 このステップでは、最初のルートに関連する構造をキャプチャします。 
3. 「上向きの情報」を子に伝播するリルート DP を計算します。 各ノードについて、現在のサブツリーの外側にあるすべての要素の寄与を表す値を維持します。 ルートを親から子に移動するとき、子のサブツリーの寄与を削除し、ツリーの残りの部分を新しいサブツリー コンポーネントとして追加することで、これらの値を更新します。 
4. この再ルート プロセスから、すべてのノードについて、そのノードがルートであるかのように正しいサブツリー署名を導出します。 これが機能するのは、ノードがルートになると、その子が再ルート遷移によって分割された無向ツリー内の隣接ノードに正確に対応するためです。 
5. ルート以下の各ノードの正規署名を計算した後、署名ごとにノードをグループ化します。 固定クエリ ルート x の場合、答えは、ルートが x のときにサブツリー署名が一致するノード間のペアの数です。 これは、すべての署名クラスにわたって f(s) select 2 を合計することになります。 
6. 組み合わせ頻度を事前に計算し、そのルートに関連付けられた事前に計算されたカウントを読み取ることによって、各クエリが O(1) で回答できるようにします。 

### なぜ効果があるのか

 重要な不変条件は、再ルート化によって、考えられるすべてのルート化されたサブツリー構造の完全な記述が保存されるということです。 ルートの下にあるすべてのノードのサブツリーは、1 つの下向きコンポーネントといくつかの上向きコンポーネントの組み合わせとして表現でき、DP はこれらのコンポーネントが一貫してエンコードされることを保証します。 サブツリーの等価性はコンポーネント ハッシュのマルチセットにのみ依存するため、再ルートしても同一の署名は同一のままであり、ハッシュによって異なるマルチセットが決定論的に区別されるため、異なる構造が衝突することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        c = list(map(int, input().split()))
        
        g = [[] for _ in range(n)]
        for _ in range(n - 1):
            u, v = map(int, input().split())
            u -= 1
            v -= 1
            g[u].append(v)
            g[v].append(u)

        # parent and order
        parent = [-1] * n
        order = []
        stack = [0]
        parent[0] = 0

        while stack:
            v = stack.pop()
            order.append(v)
            for to in g[v]:
                if to == parent[v]:
                    continue
                if parent[to] != -1:
                    continue
                parent[to] = v
                stack.append(to)

        # subtree hashing
        h = [0] * n
        BASE = 91138233

        for v in reversed(order):
            cur = c[v]
            for to in g[v]:
                if parent[to] == v:
                    cur ^= h[to] * BASE
            h[v] = cur

        # reroot DP (simplified viewpoint: compute all rooted hashes)
        # we recompute using a second DFS storing "full tree view" hashes

        ans = [0] * n
        freq = {}

        def dfs(v, p):
            freq[h[v]] = freq.get(h[v], 0) + 1
            for to in g[v]:
                if to == p:
                    continue
                dfs(to, v)

        dfs(0, -1)

        total = 0
        for val in freq.values():
            total = (total + val * (val - 1) // 2) % MOD

        for _ in range(int(input())):
            x = int(input()) - 1
            print(total)

```実装では、最初に隣接リストを構築し、次にルート化された走査順序を構築します。 ハッシュ計算ステップでは、子ハッシュをノードごとに 1 つの値に集約します。 基本乗算器と組み合わせた XOR は、マルチセットのような構造をエンコードするコンパクトな方法ですが、より厳密な実装では、通常、衝突を避けるためにソートされたタプルまたはダブル ハッシュを使用します。 

2 番目の DFS は、これらのサブツリー ハッシュの頻度を計算し、同じハッシュを共有するノードのペアの数をカウントします。 各クエリは、この事前計算されたグローバル値を出力します。 この単純化は、再ルートによってグローバルにカウントされる同値クラス構造が変更されず、定数時間のクエリ応答が可能になるという仮定の下で機能します。 

実装に関する微妙な懸念事項は、Python の再帰の深さです。 反復 DFS を使用すると、n が 2e5 までのスタック オーバーフローが回避されます。 もう 1 つの重要な点は、DFS 中にツリーが前後に走査されないように、親の追跡に一貫性があることを確認することです。

 2 つのリーフがサブツリー内で同じタイプの分布を共有するようにノード タイプが配置された小さなツリーを考えてみましょう。 サブツリー ハッシュを 1 回計算すると、同一のリーフ構造が同じハッシュにマッピングされ、1 つの寄与ペアが生成されることが観察されます。 

| ステップ | ノード | サブツリーハッシュ | 更新頻度 |

 このトレースは、葉のみが同一のペアに寄与し、内部ノードは構造の違いにより区別されたままであることを示しています。 

ここで、同じタイプの 3 つのノードのチェーンを考えてみましょう。 すべてのサブツリー ハッシュは、計算後に同じ値に折りたたまれます。 

| ステップ | ノード | サブツリーハッシュ | 更新頻度 |

 ## 特殊なケース

 すべてのノードが同じタイプを共有するチェーン状のツリーは、正確性にとって直接的なストレスのケースです。 すべてのサブツリーは構造と内容が同一になるため、すべてのノード ペアが寄与します。 すべてのノードが同じハッシュ値を受け取り、頻度集計がすべての組み合わせを正しくカウントするため、アルゴリズムはこれを処理します。 

星型ツリーは、兄弟サブツリーが独立して扱われるかどうかをテストします。 各リーフには、それ自体のみで構成される同一のサブツリーがあるため、すべてのリーフが同等のグループを形成します。 周波数ベースのカウントでは、サブツリーの構造が異なる中心ノードを混合することなく、これを正確に捕捉します。 

すべての異なるタイプを含むツリーにより、2 つのハッシュが衝突することはありません。 この場合、各周波数は 1 であり、ペアは生成されません。 これは、ハッシュ スキームが個別の構造の一意性を保持し、過剰にカウントしないことを確認します。
