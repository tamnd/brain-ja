 ## 解決策
 ## 問題の理解

 それぞれのタイプが前のタイプよりも価値のある一連のコイン タイプが与えられています。 交換レートはチェーンに沿って乗算されます。つまり、タイプ i の一定数のコインをタイプ i+1 の 1 枚のコインと交換できます。 これは隣接するすべてのペアに当てはまるため、パスに沿って乗算または除算することにより、任意のコイン タイプを他のタイプで表現できます。 

プレイヤーはいくつかのマルチセットのコインを持って開始します。各タイプにはカウントがあります。 時間の経過とともに、コインがコレクションに追加されます。 更新のたびに、次のような形式の質問が行われます。現在保持されているすべてのコインの合計価値は、タイプ y の x コインで構成されるターゲット バンドルの価値と少なくとも同じくらい大きいですか?

 したがって、各クエリは、カウントのベクトルの 1 つの座標でのポイント更新、またはすべてのコインの現在の加重合計と単一の加重バンドルとの比較のいずれかになります。 

重要な問題は、重みがタイプごとに独立していないことです。 タイプ i の値は、それを超えるすべての為替レートの積に依存するため、直接の数値変換はすぐに爆発的に増加します。 n が 200,000 まで、q が 100,000 までの場合、クエリごとにグローバル値を再計算するのは遅すぎ、中間値の大きさが指数関数的に増大するため、明示的な巨大な整数を維持することさえ不可能になります。 

単純な間違いは、プレフィックス積を使用してすべてをタイプ 1 の値に変換し、単一の大きな整数を維持することです。 これは、10^9 のような乗算チェーンを 200,000 回繰り返すと数十万桁の数値が生成され、各演算が遅すぎるため失敗します。 

もう 1 つの微妙な失敗例は、浮動小数点または上限付き整数を使用した巨大な値の比較から発生します。 大きな値を早く切り捨てると、2 つの異なる大きさが区別できなくなり、両側が上限を超えても等しくない場合、比較が不正確になる可能性があります。 

## アプローチ

 簡単なアイデアは、各コイン タイプに、タイプ 1 コインの価値に等しい固定重みを割り当てることです。 この場合、合計値はカウントと重みの内積にすぎません。 更新は簡単ですが、クエリでは繰り返しインクリメントされる大きな整数を維持する必要があり、加算には非常に大きな乗算が必要です。 これにより、重くて大きな整数の演算が行われ、値がチェーン全体に沿って繰り返し増加する最悪の場合には遅くなりすぎます。 

構造的な洞察は、実際には正確な値は必要ないということです。 すべてのクエリは 2 つの数量間の比較のみを要求します。 正確な巨大な整数を維持する代わりに、順序を決定するのに十分な情報のみを維持する必要があります。 

これは、飽和した数値システムで値を維持することを示唆しています。値が十分に大きくなると、入力制約で表現できるクエリよりもその値が常に優先されるため、特定のしきい値を超えるものはすべて「無限」として扱われます。 これに加えて、交換構造を使用して貢献を上方に伝播し、更新がグローバルではなく実質的にローカルかつ対数に保たれるようにします。 

現在のマルチセットをコイン タイプのセグメント ツリーに保存します。各ノードはタイプ 1 単位で表現されるセグメントの値を保持しますが、固定の飽和制限に制限されます。 更新では単一のリーフを調整し、上方に再計算します。 クエリは、同じ上限システムの下で現在の値とターゲット値の両方を計算し、それらを比較します。 

重要な考え方は、飽和によってクエリのしきい値と比べてすでに大きすぎて問題にならない値間の区別が除去される限り、比較は正しいままであるということです。

 | --- | --- | --- | --- |
 | クエリごとのブルート フォース変換 | クエリあたり O(n) | O(n) | 遅すぎる |
 | 飽和セグメントツリー | 操作ごとに O(log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各タイプからタイプ 1 へのプレフィックス変換係数を事前計算します。正確な積を保存する代わりに、早期に飽和してそれらを維持します。 製品が選択された大きな境界を超える場合、それをクランプします。 
2. コインの種類に基づいてセグメント ツリーを構築します。 各リーフには、合計値に対するそのコイン タイプの寄与が格納されており、すでにタイプ 1 単位にスケールされ、飽和されています。 
3. 更新クエリの場合、単一のコイン タイプの数を増やします。 この増分をタイプ 1 の寄与に変換し、対応するリーフに追加して、親ノードを再計算します。 いずれかのノードが飽和限界を超えた場合、それをクランプします。 
4. 比較クエリの場合、同じプレフィックス変換ロジックを使用して、再度飽和を使用して、タイプ y の x コインの値を計算します。 
5. 最後に、現在のマルチセットの飽和合計値とクエリ バンドルの飽和値を比較し、前者が少なくとも後者であるかどうかを出力します。 

これが機能する理由は、実際の比較はすべて、ある値が最終的に別の値を支配するかどうかのみに依存するためです。 値が、同じ飽和ルールの下でクエリから導出された数値によって到達可能な最大意味範囲を超えると、その正確な大きさは無関係になります。 システム状態とクエリ値はどちらも同じ切り捨ての下で対称的に扱われ、順序が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**30

n = int(input())
a = list(map(int, input().split()))
b = list(map(int, input().split()))
q = int(input())

# prefix conversion to type 1 with saturation
pref = [1] * (n + 1)
for i in range(1, n + 1):
    if i == 1:
        pref[i] = 1
    else:
        val = pref[i - 1] * a[i - 2]
        if val > INF:
            val = INF
        pref[i] = val

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.t = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def cap(self, x):
        return INF if x > INF else x

    def build(self, v, l, r, arr):
        if l == r:
            self.t[v] = self.cap(arr[l] * pref[l + 1])
        else:
            m = (l + r) // 2
            self.build(v * 2, l, m, arr)
            self.build(v * 2 + 1, m + 1, r, arr)
            self.t[v] = self.cap(self.t[v * 2] + self.t[v * 2 + 1])

    def add(self, v, l, r, idx, val):
        if l == r:
            self.t[v] = self.cap(self.t[v] + val * pref[idx + 1])
        else:
            m = (l + r) // 2
            if idx <= m:
                self.add(v * 2, l, m, idx, val)
            else:
                self.add(v * 2 + 1, m + 1, r, idx, val)
            self.t[v] = self.cap(self.t[v * 2] + self.t[v * 2 + 1])

    def query_sum(self):
        return self.t[1]

st = SegTree(b)

for _ in range(q):
    t, x, y = map(int, input().split())
    y -= 1
    if t == 1:
        st.add(1, 0, n - 1, y, x)
    else:
        # compute value of x type-y coins in type 1 units
        need = x * pref[y + 1]
        need = INF if need > INF else need
        print(1 if st.query_sum() >= need else 0)
```セグメント ツリーには、タイプ 1 ユニットにすでに正規化された各タイプの寄与が格納されます。 更新は 1 つのリーフにのみ影響し、上向きに伝播し、グローバル合計の一貫性を保ちます。 

唯一微妙なデザインの選択は彩度です。 INF しきい値を使用すると、比較に影響を与える可能性のある数値の表現に時間を費やすことがなくなります。 

## 実用的な例

 ### 例 1

 3 つのコイン タイプと為替レート 2 および 3 を持つ小規模なシステムを考えます。つまり、タイプ 2 はタイプ 1 の 2 と等しく、タイプ 3 はタイプ 1 の 6 と等しくなります。最初に各タイプのコインが 1 つあると仮定します。 

タイプ 2 のコインを 2 枚追加するクエリを処理してから、タイプ 3 のコインを 1 枚購入できるかどうかを尋ねます。 

| ステップ | b1 | b2 | b3 | 合計 (タイプ 1) | クエリ値 |
 | --- | --- | --- | --- | --- | --- |
 | イニシャル | 1 | 1 | 1 | 1 + 2 + 6 = 9 | - |
 | 追加 2 タイプ 2 | 1 | 3 | 1 | 1 + 6 + 6 = 13 | - |
 | クエリ | - | - | - | 13 | 6 |

 13 ≥ 6 なので、答えは 1 です。これは、すべてのタイプが単一のスケールにどのように一貫してマッピングされるかを示しています。 

### 例 2

 次に、彩度が重要な場合を考えてみましょう。 為替レートが大きく、更新が繰り返されることで値が上限を超えると仮定します。 システムは、現在の合計とクエリしきい値が境界を超えると両方を INF として保存しますが、両方とも同一の飽和ルールに基づいて計算されるため、比較は安定したままになります。 

これは、アルゴリズムがすでに順序付けに無関係な値を決して区別しないことを示しています。 

## 複雑さの分析

| スペース | O(n) | セグメント ツリー ストレージとプレフィックス配列 |

 この制約により、合計 300,000 回の操作が可能になり、対数更新は時間制限内に快適に収まります。

 ## 特殊なケース

 エッジ ケースの 1 つは、更新が繰り返されることで、単一の型の寄与がクエリ値をはるかに超えてしまう場合です。 飽和がないと、整数のオーバーフローや過剰な計算が発生します。 飽和では、値が INF を超えると均一に扱われ、それ以上増加しても比較には影響しません。 

もう 1 つのエッジ ケースは、クエリで非常に高い種類のコインが要求され、変換乗数が非常に大きい場合に発生します。 プレフィックス積はすぐに飽和します。これは、必要な値が INF になることを意味します。 飽和する現在の合計は正しく比較され、正確な大きさが追跡されない場合でも、意図した順序が維持されます。
