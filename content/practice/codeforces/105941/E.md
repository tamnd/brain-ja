 ## 解決策
 ## 問題の理解

 小文字で構成される 2n 個の文字列が与えられます。 それらを同じサイズの 2 つのグループに分割し、一方のグループを「プレフィックス側」文字列として、もう一方のグループを「サフィックス側」文字列として考える必要があります。 その後、1 対 1 のマッチングで 2 つのグループを任意に組み合わせます。 

各ペアは、2 つの文字列の最も長い共通プレフィックスの長さに等しいスコアを提供します。 パーティションとマッチングの両方を自由に決定でき、目標はすべてのペアの合計スコアを最大化することです。 

重要な問題は、パーティションとペアリングが結合していることです。 「プレフィックス側」に配置された文字列は、反対側の 1 つの文字列と厳密に一致するように強制されるため、ペアを独立して扱うことはできません。 この構造は、長いプレフィックスを共有する文字列は、最終的に互換性のある文字列とペアになるように慎重に配置する必要があることを示唆しています。 

この制約により、最大 10^5 の文字列と最大 2・10^5 の合計長が許可されます。 これにより、すべてのペアを比較したり、明示的な n^2 コスト行列を構築したりするソリューションは即座に除外されます。 O(合計長対合計長) ソリューションでさえ境界線にあるため、共有プレフィックスを効率的に処理するトライベースまたは貪欲な構造を期待する必要があります。 

多くの文字列が部分的なプレフィックスを共有しているが、異なる深さで分岐している場合、微妙な失敗のケースが発生します。 たとえば、「aab」、「aac」、「abx」、「aby」などの文字列は、異なるトライ レベルでの決定を強制します。 グローバルな一致を考慮せずにローカルで類似した文字列をペアにする単純な貪欲な場合、より優れたより深いペアを見逃す可能性があります。 

もう 1 つの落とし穴は、最初に同じプレフィックスを持つ文字列を個別にペアにできると仮定していることです。 カウントが均等でない場合、これは失敗します。文字列をペアリングに早く押し込みすぎると、後で別のサブツリーでより適切な一致がブロックされる可能性があるためです。 

## アプローチ

 ブルートフォースの見方は簡単です。 2n 個の文字列のすべてのパーティションをサイズ n の 2 つのセットに分けて試行し、各パーティションについて 2 つのセット間の最良の一致を計算します。 パーティションを修正する場合でも、最適なマッチングを計算するには、LCP 値に等しいエッジの重みを使用して最大重みの 2 部マッチング問題を解く必要があります。 それだけでもすでに O(n^3) 以上です。 すべてのパーティションを考慮すると、それは指数関数的に不可能になります。 

重要な観察は、LCP 構造が階層的であるということです。 2 つの文字列は、トライ表現のルートから少なくとも k 文字を共有する場合、答えに k を与えます。 これは、ペアごとではなくトライノードごとに貢献を処理する必要があることを示唆しています。 

個々のペアリングについて考える代わりに、各トライ ノードを「通過」するペアの数を考えます。 2 つの文字列が反対側にあり、両方ともノードを通過する場合、それらは少なくとも深さ(ノード) を合計スコアに寄与します。 目標は、トライのできるだけ高い位置でできるだけ多くのクロスペアが形成されるように、各サブツリー内のストリングの数を左側と右側に割り当てることを決定することです。 

これはトライ上のツリー DP につながります。 各ノードで子を集約し、「内部でペアになっていない」文字列の数と上に押し上げられる文字列の数を決定し、このノードで形成された一致したペアの寄与を蓄積します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースパーティション + マッチング | 指数 / O(n^3) | O(n^2) | 遅すぎる |
 | トライ+ツリーDP | O(全長) | O(全長) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、すべての文字列のトライを構築します。 各ノードはプレフィックスを表し、各文字列はルートから終端ノードまでのパスに対応します。 

次に、ポストオーダー トラバーサルを実行します。 各ノードでは、マルチセットのようなカウント構造を維持しますが、このサブツリーからの「ペアになっていない文字列」の数が、現在左側から右側を引いた部分に割り当てられている数のカウントのみを保存し、単一の整数残高として表します。

ステップ 1 はトライを構築することです。 これにより、すべてのプレフィックス関係が圧縮されるため、LCP はノードの深さに正確に対応します。 

ステップ 2 では、DP 状態を定義します。 各ノードについて、このノードより上の寄与を最大化するために、サブツリー内の文字列の数をサブツリー外の文字列と一致させる必要があるかを計算します。 これは片方の剰余を表すバランス値で捉えられます。 

ステップ 3 では、子を結合します。 私たちは子供から戻ってくると、その余剰を受け取ります。 現在のノードですべての子の余剰を結合します。 結合中に、異なる子から反対の余剰がある場合は常に、現在のノードの深さに正確に寄与する一致を形成できます。 

ステップ 4 では、現在のノードを考慮します。 文字列がこのノードで終了する場合、どちらかの側に割り当てる必要がある余剰の 1 単位に寄与します。 これらも同じバランシング プロセスにマージされます。 

ステップ 5 は最終的な集計です。 ルートでは、片側あたり正確に n 個の文字列で終了する必要があるため、すべての余剰がキャンセルされなければなりません。 より高いノードでのペアリングはより多くの寄与を与えるため、可能な限り低い深さでの貪欲なキャンセルが最適です。 

これが機能する理由は、すべての一致が両方の文字列がまだ共存する最上位のトライ ノードに割り当てられるためです。 2 つの文字列が異なる子に分岐すると、そのノードより上位には寄与できなくなるため、どのペアも最も低い共通の祖先で考慮する必要があります。 DP は、LCP 領域内で可能な限り早期に余剰を常に一致させることを保証し、貢献を最大化します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class Node:
    __slots__ = ("ch", "cnt")
    def __init__(self):
        self.ch = {}
        self.cnt = 0

def solve():
    n = int(input())
    strings = [input().strip() for _ in range(2 * n)]

    nodes = [Node()]

    def new_node():
        nodes.append(Node())
        return len(nodes) - 1

    root = 0

    def add(s):
        v = root
        for c in s:
            if c not in nodes[v].ch:
                nodes[v].ch[c] = new_node()
            v = nodes[v].ch[c]
        nodes[v].cnt += 1

    for s in strings:
        add(s)

    ans = 0

    def dfs(v, depth):
        nonlocal ans
        balance = 0

        for c, u in nodes[v].ch.items():
            b = dfs(u, depth + 1)
            balance += b

        balance += nodes[v].cnt

        # greedy pairing inside this node
        # we can match opposite sides implicitly; since we do not explicitly split,
        # we interpret pairing as canceling surplus in a global sense
        # contribution equals number of matched pairs at this depth
        pairs = balance // 2
        ans += pairs * depth
        balance %= 2

        return balance

    dfs(root, 0)
    print(ans)

if __name__ == "__main__":
    solve()
```トライ構造は標準であり、すべての文字列が 1 文字ずつ挿入されます。 複数の同一の文字列が許可され、独立して処理する必要があるため、各終端ノードはそこで終了する文字列の数をカウントします。 

DFS は最初に子を集約するため、常に浅いプレフィックスよりも前に深いプレフィックスを処理します。 重要な変数は`balance`、サブツリーから可能な限り一致を試みた後、このノードに残るペアになっていない文字列の数を表します。 

子を結合するときは、サブツリー内のすべての文字列がこのプレフィックス レベルではまだ区別できないため、それらの残高を合計します。 次に追加します`cnt`、ちょうどここで終わる文字列の数。 

この時点で、残りの 2 つの一致しない文字列をペアにすることができ、両方の文字列がこのプレフィックスを共有するため、そのような各ペアは現在の深さに正確に寄与します。 これが私たちが計算する理由です`pairs = balance // 2`そしてすぐに追加します`pairs * depth`。 

残り`balance % 2`単一の残りの文字列がこのサブツリーの外側で一致を見つける可能性があるため、上向きに伝播されます。 

微妙な点は、左セットと右セットを明示的に区別していないことです。 パリティ構造は、可能な限り最良の割り当てを暗黙的にエンコードします。ペアリングは、2 つの互換性のある文字列が可能な限り最も深いノードで出会うとすぐに常に行われます。

 ## 特殊なケース

 特殊なケースの 1 つは、すべての文字列が同一である場合です。 すべての文字列は完全な深さを共有するため、アルゴリズムはそれらを任意にペアにする必要がありますが、常に終端ノードで最大の深さの寄与を蓄積します。 最深ノードの DFS はすべてのカウントを収集し、正確にそこに n 個のペアを形成し、n・|s| を生成します。 

もう 1 つのエッジ ケースは、文字列が最初の文字までのプレフィックスのみを共有する場合です。 この場合、すべてのペアリングは深さ 1 で行われ、それ以上深くなることはありません。 トライ ルートの子はそれぞれ独立して寄与を生成し、それ以上のキャンセルは発生しません。 

最後のエッジ ケースは、1 つの長いチェーンと多数の短い分岐など、非常にアンバランスな分岐です。 DFS は、より深いノードからの不一致の余剰が上向きに正しく伝播することを保証し、より深い一致が存在する場合に浅い深さでの早すぎるペアリングを防ぎます。
