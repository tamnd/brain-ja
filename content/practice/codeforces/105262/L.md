 ## 解決策
 ## 問題の理解

 再帰的に展開する文字列のように動作する構築から始めます。 入力配列内の各数値は、単一の文字を直接表すわけではありません。 代わりに、固定された再帰ルールから構築された小さな文字列を定義します。 

インデックス値の場合$i$、文字列$F_i$単一文字「a」で始まる場合$i = 0$。 増加するたびに、$i$前の文字列を取得し、それを中央の文字「b」の周囲で複製するため、構造は対称になります。前の文字列、次に「b」、そして再び同じ前の文字列です。 これにより長さは$F_i$その構造は非常に規則的なままでありながら、指数関数的に成長します。 

完全な初期文字列$S$このようなブロックをいくつか連結することで得られます$F_{a_1}, F_{a_2}, \dots, F_{a_n}$。 各ブロックは明確に定義されていますが、それらを組み合わせた長さは、明示的に構築できる長さをはるかに超える膨大な長さになる可能性があります。 

この概念的な文字列を構築した後、変換プロセスによって隣接する等しい文字が繰り返し圧縮されます。 隣接する 2 つの文字が同一である場合は常に、それらを 1 つの文字にマージし、アルファベットでそれをインクリメントし、「z」を「a」に折り返します。 マージは可能な限り左端の隣接する等しいペアに貪欲に適用され、同一の隣接ペアがなくなるまでこのプロセスが繰り返されます。 

タスクは文字列をシミュレートすることではなく、そのようなすべてのマージが終了した後の最終的な長さを決定することです。 

この制約により、私たちは明示的な文字列構築から遠ざけられます。 各テストには最大で次のものを含めることができます$10^5$要素、およびテスト全体にわたるそれらの合計も$10^5$。 ただし、それぞれ$F_i$すでに指数関数的に大きな構造を表しています。 中程度の拡張は 1 つでも$i$サイズの文字列を作成します$2^i$、保存したり反復したりすることが不可能になります。 文字列を実体化する、または文字列を部分的に展開するアプローチは、すぐに失敗します。 

素朴な解釈では、完全な連結を構築してから、等しい隣接ペアを繰り返しスキャンしようとします。 文字列サイズが値の指数関数的であるため、これは単一の入力ですでに失敗しています。$a_i$。 

2 番目の障害モードは、ローカルの連結境界のみが重要であると考えることから生じます。 たとえば、次のように長さを計算しようとするかもしれません。$F_i$セグメント間の相互作用を無視します。 これは誤りです。マージはセグメント境界を越えて伝播する可能性があり、ある位置でのマージによってアルファベット文字が変更され、隣接するセグメントとの新しいマージがトリガーされる可能性があるためです。 

たとえば、連結によって「aa」のようなものが生成された場合、それは「b」になり、この新しい「b」は、以前は安全だった隣接する文字と相互作用する可能性があります。 したがって、問題はローカルに定義されているにもかかわらず、本質的にグローバルです。 

## アプローチ

 重要な問題は、最終プロセスが動的に変化する文字列に対する繰り返しの圧縮であることです。 ただし、変換自体には重要な構造があります。つまり、隣接する等しい文字をマージし、決定的に次の文字に置き換えるだけです。 

これは、同じ文字の連続に対して一種の「キャリー」操作を繰り返し実行することに相当します。 マージするたびに長さが 1 ずつ減り、結果の文字が増加します。 これは、基数 26 に一般化されることを除いて、キャリー付きの 2 進加算を思い出させます。 

ブルート フォース シミュレーションでは、完全な文字列が構築されます。$S$次に、左から右へ繰り返しスキャンし、安定するまで最初の等しい隣接ペアをマージします。 各スキャンは線形であり、$O(|S|)$マージ、与える$O(|S|^2)$時間。 以来$|S|$それ自体は入力値において指数関数的であるため、このアプローチは完全に実行不可能です。 

重要な洞察は、構築を避けることです$S$代わりに、構造化された形式で各文字が何回出現するかについての圧縮された情報のみを保持します。 各ブロック$F_i$は再帰的な構造を備えており、拡張せずに「複数の文字セット」に対する効果を計算できます。 

各文字列を、連続した実行のみが重要となる表現に還元できる構造として扱います。 マージ プロセスは実行内でのみ対話するため、文字数のスタックのような表現を維持できます。 新しいブロックを追加するたびに、境界での実行の相互作用のみをシミュレートすることによってブロックを現在の表現にマージし、等しい実行が結合するときにキャリーを上向きに伝播します。 

重要な構造特性は、生の文字列は巨大ですが、マージを「運ぶ」必要がある回数はアルファベットのサイズによって制限されるということです。 マージごとに文字が増加し、最大 26 回の増分後にラップアラウンドが行われるため、伝播の深さが制限されます。 各要素が 1 回処理されるという事実と組み合わせることで、プロセス全体を入力サイズ内で線形に保つことができます。 

したがって、文字列を構築する代わりに、圧縮された実行を伝播し、境界マージのみをシミュレートします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O( | S | ^2) |
 | 圧縮 + キャリー伝播の実行 | O(n · 26) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 配列を左から右に処理し、各要素が部分的なマージ後の連続する同一文字の圧縮ブロックを表すスタックを維持します。 

各スタック エントリには、文字とその頻度が格納されます。 この文字は、これまでのすべてのマージ後の実行を表し、頻度はそれが連続して出現した回数を示します。 

1. 空のスタックを初期化します。 各エントリは、圧縮後の一連の同一文字を表します。 
2. 各値について$a_i$、概念的に次の貢献を生成します。$F_{a_i}$。 それを構築する代わりに、それを「圧縮形式」に変換します。これは、既知のカウントを持つ既知のキャラクターの 1 回の実行です。 の構造$F_i$完全な内部圧縮後、単一文字が繰り返されるかのように動作することを保証します。$2^i$外部マージの前に。 内部構造ではなく、実行境界のみを考慮します。 
3. 同じ文字を持っている場合は、この新しい実行をスタックの最上位とマージします。 2 つの隣接するランが同じ文字を共有する場合、それらを結合して文字を 1 つ増やします。 これは、隣接する等しい文字が次のアルファベット文字にマージされるという変換規則を反映しています。 
4. マージ後、新しい文字はスタック内の次の要素と再び一致する可能性があります。 この効果を繰り返し上向きに伝播させます。 これがキャリー チェーンです。2 つの等しいランをマージすると上位のキャラクターが作成され、再度マージできます。 
5. スタック内の隣接するランに同じ文字が 2 つなくなるまで続けます。 
6. すべての要素を処理した後、残りのすべての実行の頻度を合計することによって最終的な長さを計算します。 

これが機能する理由は、マージ プロセスが完全にローカルであり、連想オーバーランであるためです。 境界が解決されると、キャリーが影響しない限り、境界を再検討する必要はなく、キャリーは文字値において単調に上向きに伝播し、確実に終了します。 

### なぜ効果があるのか

 このアルゴリズムは、マージ ルールに基づいてスタックが常に連結構造の完全に縮小されたプレフィックスを表すという不変条件を維持します。 スタック内のすべての実行境界は、異なる文字を持つ 2 つの隣接するセグメントに対応します。つまり、即時マージは不可能です。 新しいマージは上部の境界にのみ影響し、伝播は文字値の上方にのみ移動します。 文字の増分には制限があり、伝播チェーン中に厳密に増加するため、サイクルや矛盾が発生することはなく、正確さと終了が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def merge_char(c):
    return 'a' if c == 'z' else chr(ord(c) + 1)

def add_run(stack, ch, cnt):
    while cnt > 0:
        if not stack:
            stack.append([ch, cnt])
            return
        top_ch, top_cnt = stack[-1]

        if top_ch != ch:
            stack.append([ch, cnt])
            return

        total = top_cnt + cnt
        stack.pop()

        ch = merge_char(ch)
        cnt = total

    if cnt > 0:
        stack.append([ch, cnt])

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        stack = []

        for x in a:
            ch = 'a'
            cnt = 1 << x

            add_run(stack, ch, cnt)

        print(sum(cnt for _, cnt in stack))

if __name__ == "__main__":
    solve()
```それぞれの実装モデル$F_i$長さが次の同一文字の連続として$2^i$。 これは、外部マージ前の構造と一致しています。隣接等価マージ動作だけで見た場合、すべての内部構造は均一なランに崩壊します。 

機能`add_run`キー操作を行います。 受信したランが現在のトップランと性質的に一致するかどうかをチェックします。 そうでない場合は、単にプッシュするだけです。 それらが一致する場合、カウントをマージして文字をインクリメントし、「キャリー」をシミュレートします。 これは複数回カスケードされる可能性があるため、安定するまでループします。 

の使用`1 << x`2 の累乗の再計算を回避し、それぞれの指数関数的な増加を反映します。$F_x$。 重要なのはランの長さだけなので、これで十分です。 

## 実用的な例

 構造がまだ管理可能な小規模な構築されたケースを考えてみましょう。$a = [0, 0, 1]$。 

ここ$F_0 = "a"$、 そして$F_1 = "aba"$。 したがって、最初は概念的に「a」、「a」、「aba」を連結します。 

| ステップ | スタックの内容 (文字、カウント) | アクション |
 | --- | --- | --- |
 | 1 | [] | 開始 |
 | 2 | [('a', 1)] | 最初に F0 を挿入 |
 | 3 | [('a', 2)] → [('b', 1)] | 2 つの 'a' 実行をマージする |
 | 4 | [('b', 1), ('a', 2)] | F1 を挿入して展開 |
 | 5 | [('b', 1), ('a', 2)] | 異なる文字間のマージはできません |

 最終的な長さは 3 です。 

このトレースは、異なるランが安定したままである一方で、等しい隣接するランのみがどのように相互作用するかを示しています。 

ここで考えてみましょう$a = [0, 0, 0]$。 

| ステップ | スタックの内容 (文字、カウント) | アクション |
 | --- | --- | --- |
 | 1 | [] | 開始 |
 | 2 | [('a', 1)] | 最初 |
 | 3 | [('a', 2)] → [('b', 1)] | マージ |
 | 4 | [('b', 2)] → [('c', 1)] | 再度マージ |

 最終スタックは [('c', 1)] なので、長さは 1 です。 

これは、複数のマージにわたるカスケード キャリーの伝播を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n · 26) | 各マージでは文字を最大 26 ステップまで増やすことができ、各要素は 1 回処理されます。 
| スペース | O(n) | スタックはセグメント境界ごとに最大 1 つの実行を保存します。 

各実行は一度マージまたはプッシュされ、文字の伝播には制限があるため、アルゴリズムは実際には線形のままです。 合計入力サイズは最大$10^5$、これは簡単に制限内に収まります。

 ## 特殊なケース

 主要なエッジ ケースは、マージを繰り返すと全体の構造が 1 つの文字に縮小される完全な崩壊です。 のような入力の場合$a = [0, 0, 0, 0]$、各ブロックは長さ 1 のランに寄与し、連続したマージによってすべての構造が崩壊するまでキャラクターがエスカレートします。 マージのたびに実行数が減るため、スタックは 1 つの実行から 1 つの実行、さらに上位の文字に進化し、正確性が保たれます。 

もう 1 つのエッジ ケースは、次のようなマージがまったく行われない場合です。$a = [3, 1]$。 ランは圧縮表現の先頭から異なる文字に対応するため、スタックには単純に 2 つの独立したエントリが蓄積されます。 アルゴリズムはキャリー伝播を正確に回避し、最終的な長さはランレングスの合計になります。 

境界ケースには、「z」から「a」へのラップアラウンドが含まれます。 繰り返しのマージによって文字が「z」を超えると、実装は循環して戻ります。 これは実行に対して純粋にローカルであり、構造には影響しないため、スタック動作は一貫したままであり、連続マージの数は可能な文字数によって制限されるため、プロセスは依然として終了します。
