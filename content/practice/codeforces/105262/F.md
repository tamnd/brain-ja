 ## 問題の理解

 2 つの基本文字列が与えられています。$F_1$そして$F_2$、そして、後のすべての文字列が前の 2 つを順番に連結することによって形成される文字列のシーケンスを定義します。 それで$F_3 = F_2 + F_1$、$F_4 = F_3 + F_2$、 等々。 これはフィボナッチ数と同じ構造規則ですが、値を加算する代わりに文字列を連結する点が異なります。 

テスト ケースごとに、インデックスが与えられた単一のクエリが尋ねられます。$x$そしてポジション$k$、どの文字がその位置に表示されるかを決定する必要があります$k$(1 からインデックス付き) 文字列内$F_x$。 難しいのは、$F_x$は急速に天文学的に大きくなる可能性があるため、明示的に構築することは不可能です。 

制約はこれを強化します。$10^4$テストケース、入力文字列の長さの合計は$10^5$これは、前処理が全体的に線形である必要があることを意味します。 インデックス$x$まで上がります$1000$したがって、連結の深い再帰を通じて推論する必要があるかもしれませんが、文字列を構築したり、文字列の長さを追跡する以上に明示的に保存することさえできません。 位置$k$と同じ大きさにすることができます$10^{18}$これにより、長さに基づいた推論のみが実行可能であることが明らかになります。 

単純なアプローチでは、次の値に達するまでフィボナッチ文字列を繰り返し構築します。$F_x$、しかし保管さえも$F_{40}$ほとんどの場合、すでにメモリ制限を超えており、$F_{100}$全く実現不可能です。 もう 1 つの素朴なアイデアは、その場で文字列を構築する再帰ですが、これも指数関数的に爆発的に増加します。 

両方の初期文字列のすべての文字が同一である場合、微妙なエッジ ケースが発生します。 その場合は毎回$F_x$は均一であり、クエリはその 1 文字を返すだけになります。 それでも再帰を試みる不用意な実装は、オーバーフローしたり、不必要に時間を浪費したりする可能性があります。 

もう 1 つのエッジケースは次のような場合です$k$間の境界の長さに正確に等しい$F_{i-1}$そして$F_{i-2}$分解中。 ここでの off-by-one エラーは、連結によって文字列が 2 つの部分に分割され、正しいインデックス付けによって再帰で左に移動するか右に移動するかが決まるため、よく発生します。 

## アプローチ

 ブルートフォースのアイデアは単純です。 各文字列を構築します$F_i$到達するまで繰り返し連結を使用します。$F_x$、その後、それに直接インデックスを付けます。 これは定義に正確に従っているため、正しいです。 ただし、各連結の結果のサイズは線形であり、フィボナッチの増加により長さが指数関数的に増加します。 到達さえ$F_{40}$すでに数十億の文字を含む文字列を構築する必要がありますが、これは時間とメモリの両方で不可能です。 

重要な点は、実際には完全な文字列が必要ないということです。 それぞれの長さを知る必要があるだけです$F_i$と、連結によって位置がどのように分割されるかについて説明します。 以来$F_i = F_{i-1} + F_{i-2}$、同じ繰り返しを使用して長さを事前計算できますが、それらの上限を大きな値に設定します (例:$10^{18}$) オーバーフローを避けるため。 長さが分かると、クエリに答えることは、長さから後退するプロセスになります。$F_x$、位置を決定する$k$左側の部分にあります$F_{x-1}$または右側の部分$F_{x-2}$。 これにより、問題は次の対数降下に​​変換されます。$x$、バイナリ分解ツリーをナビゲートするのと似ています。

 ## アルゴリズムのチュートリアル

 まず、必要な最大インデックスまでのすべてのフィボナッチ文字列の長さの配列を構築します。 

1.初期化$len[1] = |F_1|$そして$len[2] = |F_2|$。 これらは入力文字列から直接わかります。 
2. それぞれについて$i \ge 3$、計算する$len[i] = len[i-1] + len[i-2]$ただし、合計がそれを超える場合は、$10^{18}$にクランプします。$10^{18}$。 これにより、インデックス作成の正確性を維持しながら、オーバーフローが防止されます。 
3. 長さテーブルが構築されたら、クエリを処理します。$(x, k)$。 インデックスから開始$x$そして位置$k$。 
4. ながら$x > 2$、 比較する$k$と$len[x-1]$。 もし$k \le len[x-1]$に移動します$x-1$そして保管してください$k$位置が左側の部分文字列にあるため、変更されません。 それ以外の場合は減算します$len[x-1]$から$k$そしてに移動します$x-2$、今は正しい部分文字列の内側にいるからです。 
5. いつ$x$1 または 2 になった場合は、直接返します$k$の - 番目の文字$F_1$または$F_2$。 

各決定ステップでは、連結の構造を拡張するのではなく、それに従うことで問題のサイズを縮小します。 

### なぜ効果があるのか

 構造はあらゆることを保証します。$F_x$は、2 つの連続する部分に正確に分割されます: プレフィックス$F_{x-1}$接尾辞が続く$F_{x-2}$。 長さの配列は、このパーティションを正確にエンコードします。 すべてのステップで、アルゴリズムは現在のペアの不変条件を保持します。$(x, k)$原作と同じキャラクターを指します$F_x$、より小さな部分問題にマッピングされただけです。 各遷移は厳密に減少するため、$x$、プロセスは終了する必要があり、最後の基本ケースは明示的な文字列に直接インデックスを付けます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAX = 10**18

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        f1 = input().strip()
        f2 = input().strip()
        x, k = map(int, input().split())

        # build length table up to x
        mx = x
        ln = [0] * (mx + 1)
        ln[1] = len(f1)
        if mx >= 2:
            ln[2] = len(f2)

        for i in range(3, mx + 1):
            val = ln[i - 1] + ln[i - 2]
            if val > MAX:
                val = MAX
            ln[i] = val

        cur_x = x
        cur_k = k

        while cur_x > 2:
            if cur_k <= ln[cur_x - 1]:
                cur_x -= 1
            else:
                cur_k -= ln[cur_x - 1]
                cur_x -= 2

        if cur_x == 1:
            print(f1[cur_k - 1])
        else:
            print(f2[cur_k - 1])

if __name__ == "__main__":
    solve()
```このソリューションは、長さの計算とナビゲーションという 2 つの問題を分離します。 長さの配列は反復的に構築されるため、各値は前の 2 つの値のみに依存し、フィボナッチ構造に一致します。 クランプは、到達可能なすべての比較の有効性を維持しながら、オーバーフローを防止します。$k$。 

降下ループはコア ロジックです。 反復ごとに、クエリ位置が連結の最初のコンポーネントにあるか、2 番目のコンポーネントにあるかが決定されます。 2 番目のコンポーネントに移動するときは、減算します。$len[x-1]$インデックスは新しい部分文字列に対して相対的にシフトするため、これは必須です。 

よくある実装上の間違いは、次のことを忘れることです。$F_x = F_{x-1} + F_{x-2}$(反転されません)。 この順序を逆にすると、一貫して間違った分岐が発生します。 もう 1 つの微妙な問題は、クランプ長ではありません。これにより、他の言語の Python リストがオーバーフローして比較が中断される可能性があります。

 ## 特殊なケース

 ### 統一文字列

 もし$F_1 = F_2 = "n"$、その後は毎回$F_x$同じ文字の繰り返しです。 アルゴリズムは引き続き長さを計算して下降しますが、基本ケースではパスに関係なく同じ文字を返します。 たとえば、$x = 1000$そして$k = 10^{18}$、降下は多くの州を訪問する可能性がありますが、最終的な結果は常に`"n"`。 

### 正確なプレフィックス長での境界分割

 次のステップを考えてみましょう。$k = len[x-1]$。 条件では、これを左側に属するものとして扱う必要があります。 ルール`if cur_k <= ln[cur_x - 1]`正確性を保証します。 厳密な不等式として記述された場合、アルゴリズムが誤って正しいセグメントにシフトし、off-by-one エラーが発生します。 

### 非常に大きな k 値

 いつ$k$実際の長さを超えている場合、クランプにより比較が有効なままになります。 たとえ$len[x]$上限は$10^{18}$の場合でも、到達不能なサフィックスはすべて右側のブランチに完全に含まれているものとして扱われるため、ロジックは引き続きクエリを一貫してルーティングします。
