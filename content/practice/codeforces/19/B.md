 ## 解決策
 ## 問題の理解

 各項目には 2 つのプロパティがあります。 ボブがその商品の代金を支払う場合、レジ係は`t[i]`それを処理するのに数秒かかり、ボブもそれに費やします`c[i]`お金。 その間`t[i]`秒間、ボブは他のアイテムを 1 秒ごとに 1 つずつ盗むことができます。 

注文はボブによって完全に制御されます。つまり、重要なのはどの商品の代金が支払われるかだけです。 有料アイテムを決定したら、その合計処理時間によって、他のアイテムがどれだけ盗まれるかが決まります。 

ボブがお金を払ったと仮定します`k`レジ係の合計時間が`T`。 それらの`k`有料アイテムはすでに合法的に取得されており、`T`ボブが盗める最大秒数`T`追加のアイテム。 したがって、取得したアイテムの合計数は次のようになります。```
k + T
```全部取るには`n`アイテムには次のものが必要です。```
k + T >= n
```タスクは次のようになります。```
Choose a subset of items minimizing total cost,
such that sum(t[i]) + number_of_chosen_items >= n.
```この再定式化こそが問題のすべてである。 

制約が次の手がかりになります。 最大 2000 個のアイテムがあり、それぞれ`t[i]`また、最大でも 2000 です。ブルートフォースのサブセット列挙ではチェックが必要になります。`2^n`不可能な可能性`n = 2000`。 平`O(n^3)`Python では 1 秒の制限を超えると不快になり始めます。 

この構造は動的プログラミングを強く示唆しています。 状態は、すでに入手を保証できるアイテムの数によって決まり、その値が超えることはありません。`n`。 アン`O(n^2)`ここではDPが完全に実現可能です。 

見落としやすいエッジケースがいくつかあります。 

処理時間がゼロのアイテムを考えてみましょう。```
1
0 5
```答えは`5`。 

このアイテムの代金を支払っても盗む時間はありませんが、アイテム自体は取得したものとしてカウントされます。 間違った解釈をすると、ゼロタイム項目は役に立たないと考える可能性があります。 

もう 1 つの注意が必要な状況は、高価なアイテムが 1 つだけあれば十分な場合です。```
3
10 100
0 1
0 1
```正しい答えは、`1`。 

どちらの安いアイテムを支払っても、入手できるアイテムは 1 つであり、時間を盗むことはないので、さらに多くの有料アイテムが必要になります。 ただし、最初のアイテムの代金を支払うと、次のものが得られます。```
1 paid item + 10 stealable items >= 3
```だから払ってる`100`両方の安いアイテムを支払うだけなので、実際には不要です`2`。 

待って、注意深く確認しましょう。 両方の安価なアイテムを支払うと、次のことが得られます。```
2 paid items + 0 stealing time = 2 items
```まだ十分ではありません。 したがって、実際の最小値は`100`。 

この例は、合計盗み時間だけをカウントすることがなぜ間違っているのかを示しています。 The paid items themselves must also be counted.

 もう 1 つの危険なケースは、小さな時間が多数重なった場合です。```
4
1 5
1 5
1 5
1 5
```答えは`10`。 

2 つのアイテムを支払うと次のものが得られます。```
2 paid + 2 stealable = 4
```すべての項目が対称であるため、「常に最大の時間を購入する」などの欲張りな戦略はここでは存在しません。 最適化は基本的に組み合わせで行われます。 

## アプローチ

 ブルートフォースの解決策は簡単です。 項目のサブセットごとに、次を計算します。```
paid_count
total_time
total_cost
```もし：```
paid_count + total_time >= n
```その場合、このサブセットは有効であり、コストが最小限に抑えられます。 

考えられるすべての有料アイテムのセットが 1 回だけ検査されるため、総当り攻撃は正しいです。 問題は探索空間のサイズです。 と`n = 2000`、 がある：```
2^2000
```サブセットは天文学的に不可能です。 

重要な観察は、すべての有料アイテムが正確に貢献しているということです。```
t[i] + 1
```最終要件に向けて。 

の`+1`アイテム自体が合法的に入手されたものであり、`t[i]`チェックアウト中に盗むことができる追加アイテムの数に基づいて計算されます。 

したがって、選択された各項目は次のオブジェクトのように動作します。```
value = t[i] + 1
cost = c[i]
```少なくとも合計値が必要です`n`コストを最小限に抑えながら。 

クラシックなナップサックスタイルのDPです。 

定義する：```
dp[x] = minimum cost to achieve total contribution exactly x
```ここで、貢献とは次のことを意味します。```
sum(t[i] + 1)
```より大きい値`n`到達したら不要なので`n`、すべてのアイテムを入手できます。 

各項目について、それを取得するかスキップします。 これは標準の 0/1 ナップザック移行になります。 

問題は基本的にサブセットに関するものであるため、総当り攻撃が機能します。 DP が機能するのは、サブセットに関して重要な唯一の情報が項目の正確な順序ではなく、その合計の寄与であるためです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n) | お(1) | 遅すぎる |
 | 最適なDP | O(n^2) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべての項目を読みます。 
2. 各項目について、その寄与度を計算します。```
gain = t[i] + 1
```これは、このアイテムの代金を支払った場合に入手できるアイテムの合計数を表します。 

1.次のサイズの DP 配列を作成します`n + 1`。```
dp[x] = minimum cost to achieve contribution x
```以下を除くすべての値を無限大に初期化します。```
dp[0] = 0
```貢献を達成しているので`0`費用はかかりません。 

1. 項目を 1 つずつ処理します。 

各アイテムについて:```
gain = t[i] + 1
cost = c[i]
```から寄与値を逆方向に反復します。`n`に`0`。 

逆方向反復により、同じ項目を複数回使用することができなくなります。 

1. 以前の投稿から`x`、次のように遷移します。```
nx = min(n, x + gain)
```上限は`n`より大きな値は同等であるためです。 寄付金が到達したら`n`、すでにすべてのアイテムを入手できます。 

1. アップデート:```
dp[nx] = min(dp[nx], dp[x] + cost)
```これは、達成するための以前の最良の方法を維持するかどうかを意味します`nx`、または現行品を使用いたします。 

1. すべての項目を処理した後、次のように出力します。```
dp[n]
```貢献だから`n`手段：```
paid_items + stealable_items >= n
```これにより、すべてのアイテムが取得されることが保証されます。 

### なぜ効果があるのか

 DP の不変条件は次のとおりです。```
After processing the first i items,
dp[x] stores the minimum possible cost
to achieve total contribution x.
```各項目には、選択するか選択しないかの 2 つの選択肢があり、トランジションでは両方が考慮されます。 すべてのサブセットは 1 つの固有の選択肢シーケンスに対応するため、DP はすべての有効なサブセットを暗黙的に探索します。 

サブセットの貢献は次のとおりです。```
sum(t[i] + 1)
```これは以下に等しい:```
number_of_paid_items + total_stealing_time
```サブセットは、この量が少なくとも次の値に達したときに有効になります。`n`。 DP はそのようなすべてのサブセット間のコストを最小化するため、最終的な答えは最適になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**18

n = int(input())
items = [tuple(map(int, input().split())) for _ in range(n)]

dp = [INF] * (n + 1)
dp[0] = 0

for t, c in items:
    gain = t + 1

    for x in range(n, -1, -1):
        if dp[x] == INF:
            continue

        nx = min(n, x + gain)
        dp[nx] = min(dp[nx], dp[x] + c)

print(dp[n])
```DP 配列には、達成可能な貢献レベルごとの最小コストが格納されます。 配列のサイズは`n + 1`値がより大きいため`n`は不要です。 

逆方向の反復は最も重要な実装の詳細です。 前方に反復すると、1 つのアイテムが状態を更新し、すぐに同じ反復で再度再利用され、問題が誤って制限のないナップザックになってしまう可能性があります。 

キャップ:```
nx = min(n, x + gain)
```境界外のアクセスを回避し、すべての「十分な」状態を 1 つの最終的なターゲット状態に圧縮します。 

コストが以下に達する可能性があるため、無限値は大きくする必要があります。```
2000 * 10^9
```それで`10^18`安全な選択です。 

## 実用的な例

 ### 例 1

 入力:```
4
2 10
0 20
1 5
1 3
```利点は次のとおりです。```
3, 1, 2, 2
```DP を追跡します。 

| アイテム | ゲイン | コスト | 更新された状態 |
 | --- | --- | --- | --- |
 | 開始 | - | - | dp[0] = 0 |
 | (2,10) | 3 | 10 | dp[3] = 10 |
 | (0,20) | 1 | 20 | dp[1] = 20、dp[4] = 30 |
 | (1,5) | 2 | 5 | dp[2] = 5、dp[4] = 15 |
 | (1,3) | 2 | 3 | dp[2] = 3、dp[4] = 8 |

 最終的な答え:```
8
```最適な選択は、最後の 2 つの項目に対して支払いを行うことです。 彼らの貢献度の合計は次のとおりです。```
2 + 2 = 4
```これですべての項目に十分です。 

### 例 2

 入力:```
3
0 5
0 6
0 7
```各アイテムにはゲインがあります`1`。 

| アイテム | ゲイン | コスト | 到達可能な最良の州 |
 | --- | --- | --- | --- |
 | 開始 | - | - | dp[0] = 0 |
 | 最初 | 1 | 5 | dp[1] = 5 |
 | 2番目 | 1 | 6 | dp[2] = 11 |
 | 3番目 | 1 | 7 | dp[3] = 18 |

 最終的な答え:```
18
```すべての処理時間はゼロであるため、盗用は不可能です。 ボブはすべてのアイテムに対して支払いをしなければなりません。 

この例では、`+1`有料アイテムそのものからの貢献が必須となります。

 | 測定 | 複雑さ | 説明 |

## テストケース```python
# helper: run solution on input string, return output string
import sys, io

def solve():
    input = sys.stdin.readline

    INF = 10**18

    n = int(input())
    items = [tuple(map(int, input().split())) for _ in range(n)]

    dp = [INF] * (n + 1)
    dp[0] = 0

    for t, c in items:
        gain = t + 1

        for x in range(n, -1, -1):
            if dp[x] == INF:
                continue

            nx = min(n, x + gain)
            dp[nx] = min(dp[nx], dp[x] + c)

    print(dp[n])

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    out = io.StringIO()

    backup = sys.stdout
    sys.stdout = out

    solve()

    sys.stdout = backup
    return out.getvalue().strip()

# provided sample
assert run(
"""4
2 10
0 20
1 5
1 3
""") == "8", "sample 1"

# minimum size
assert run(
"""1
0 7
""") == "7", "single item"

# all zero times
assert run(
"""3
0 5
0 6
0 7
""") == "18", "must pay for all"

# one large time dominates
assert run(
"""5
10 4
0 100
0 100
0 100
0 100
""") == "4", "single item covers everything"

# equal values
assert run(
"""4
1 5
1 5
1 5
1 5
""") == "10", "choose any two"

# off-by-one contribution check
assert run(
"""2
0 3
1 10
""") == "10", "gain includes paid item itself"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 時間ゼロの単品 | 7 | 有料アイテム自体が 1 つ貢献します |
 | すべてゼロ回 | 18 | 盗むことはできません |
 | 1 つの巨大なタイムアイテム | 4 | 多額の寄付で全項目をカバー可能 |
 | すべて等しい値 | 10 | DP は貢献を正しく結合します |

 ## 特殊なケース

 可能な最小の入力を考えてみましょう。```
1
0 5
```アイテムの貢献度は次のとおりです。```
0 + 1 = 1
```DP は次から移行します。```
dp[0] = 0
```に：```
dp[1] = 5
```以来`n = 1`、答えは次のようになります`5`。 

この事例は、盗み時間が存在しない場合でも、有料アイテムが最終的な合計にカウントされることを証明しています。 

次に、次のことを考えてみましょう。```
3
0 5
0 6
0 7
```すべての項目が正確に貢献します`1`。 貢献を達成する唯一の方法`3`3 つの項目をすべて選択しています。 DP は徐々に構築されます。```
dp[1] = 5
dp[2] = 11
dp[3] = 18
```合計盗む時間は常にゼロであるため、近道は存在しません。 

別の微妙なケースは次のとおりです。```
5
10 4
0 100
0 100
0 100
0 100
```最初の項目は以下に貢献します。```
10 + 1 = 11
```すでに超えている`n = 5`。 

DP は直ちに更新します。```
dp[5] = 4
```キャップのせいで：```
nx = min(n, x + gain)
```この上限がないと、実装はメモリを無駄にするか、インデックス作成エラーの危険性があります。 

最後に、次のことを考慮してください。```
2
0 3
1 10
```最初の項目が貢献します`1`、2番目は貢献します`2`。 

2 番目のアイテムのみを支払うと、すでに次の条件が満たされます。```
2 >= n
```だから答えは`10`。 

貢献を使用した間違った実装`t`の代わりに`t+1`両方の項目が必要であると誤って判断し、返されます。`13`。
