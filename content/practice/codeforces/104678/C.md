 ## 解決策
 ## 問題の理解

 それぞれのストーリーが固定のページ数を持つ、一連の長さのストーリーが与えられます。 これに加えて、ページ容量のある本が数冊与えられます。 すべての本について、物語のサブセットを自由に選択できる場合、その中にいくつの異なる物語を配置できるかを知りたいと考えていますが、そのサブセット内の総ページ数が本の容量を超えてはなりません。 

重要な詳細は、各ストーリーは書籍間で再利用できるが、再利用によってクエリ間に結合が作成されないことです。 すべての本は、同じストーリー群に対して個別に評価されます。 

したがって、タスクは、容量値ごとに、合計ページ合計がその制限内に収まるストーリーの最大数を見つけることになります。 

この制約により、ほぼ線形または対数線形の解決策が求められます。 最大 200,000 のストーリーと 200,000 のクエリを扱う場合、クエリごとにサブセットを再計算するアプローチは非常に遅すぎます。 すべてのストーリーに対する単純なクエリごとの貪欲な選択では O(nk) のコストがかかりますが、これは最悪の場合でも 4e10 操作程度であり、2 秒の制限の下では実行できません。 クエリごとに並べ替えることさえ完全に不可能です。 

微妙な落とし穴は、問題を任意のサブセットが必要であると誤解することから発生します。 さまざまな組み合わせが重要であると考える人もいるかもしれませんが、すべてのストーリーは独立しており、加算的にのみ寄与するため、最適な選択は常に、利用可能な最小のストーリーを最初に選択することです。 小さいストーリーを除外しながら、より大きなストーリーを含めようとすると、同じ合計制約の下で達成可能なストーリーの数が減るだけです。 

2 番目のエッジ ケースは、容量が非常に小さい場合に発生します。 本の容量が最小のストーリーよりも小さい場合、答えはゼロでなければなりません。 もう 1 つの特殊なケースは、容量が最大 10^18 と非常に大きい場合で、合計が適合する場合にはすべてのストーリーを常に含めることができます。 

## アプローチ

 この強引なアイデアは簡単です。本ごとに、ストーリーのすべてのサブセットを試すか、少なくともストーリーをある順序で選択することをシミュレートし、容量を超える前に何件まで収まるかを追跡します。 ストーリーを一度ソートして貪欲に追加することでわずかに最適化したとしても、これをクエリごとに個別に実行すると、各書籍がすべてのストーリーをスキャンする可能性があるため、依然として O(nk) 動作が発生します。 

重要な構造的洞察は、特定のストーリーではなく、制限を超える前に最小のストーリーをいくつ詰め込めるかだけを気にするということです。 ストーリーがサイズ別にソートされたら、合計制約の下でカウントを最大化するための最良の戦略は、常にストーリーを昇順に取得することです。 これにより、各クエリがソートされた配列に対するプレフィックス問題に変換されます。 

ソートされたストーリーの長さにわたってプレフィックスの合計を事前計算すると、各クエリは次のようになります。合計が本の容量を超えない最大のプレフィックスを見つけます。 これは古典的な単調条件であり、二分探索で解決できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nk) | お(1) | 遅すぎる |
 | ソート + プレフィックス + 二分検索 | O(n log n + k log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべてのストーリーの長さを降順でない順に並べ替えます。 これにより、ストーリーを順番に取得すると、固定数のストーリーに対して常に最小の累積合計が得られます。 
2. ソートされたストーリーに対してプレフィックス合計配列を構築します。 各位置には、すべてのストーリーをそのインデックスまで取得するのに必要な合計ページが格納されます。 
3. 各本の容量について、プレフィックスの合計が容量以下になるような最大プレフィックス長を見つけたいと考えています。 
4. プレフィックス合計配列に対して二分検索を使用して、合計が本の制限を超えない右端の位置を見つけます。 その位置の指標がその本の答えです。 
5. すべての回答を入力クエリと同じ順序で出力します。

ここで二分探索が機能する理由は、すべてのストーリーの長さが正であるため、プレフィックス合計配列が厳密に増加しているためです。 これにより、単調な述語が保証されます。プレフィックスの合計が容量を超えると、長いプレフィックスもすべてその容量を超えます。 

### なぜ効果があるのか

 合計制約の下でカウントを最大化するための最適なサブセットは、常に最小の利用可能な要素で構成されている必要があります。 小さなストーリーをより大きなストーリーに置き換える逸脱は、実現可能性を向上させることなく、適合できる要素の数を減らします。 これにより、ソートされたプレフィックス構造が十分であるだけでなく最適なものになり、プレフィックス合計の単調性により、二分探索で正確なカットオフ ポイントが見つかることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    
    a.sort()
    
    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]
    
    import bisect
    
    res = []
    for cap in b:
        ans = bisect.bisect_right(pref, cap) - 1
        res.append(str(ans))
    
    print(" ".join(res))

if __name__ == "__main__":
    solve()
```この解決策は、まずストーリーの長さを並べ替えて、短いストーリーが最初に考慮されるようにすることから始まります。 プレフィックス合計配列は、「合計制約の下に収まる項目の数」の問題を、単一の配列に対する範囲クエリに変換します。 の使用`bisect_right`容量よりも厳密に大きい最初のプレフィックスの合計を直接検索し、1 を引くと最後の有効なプレフィックス長が得られます。 

実装の微妙な詳細は、プレフィックス配列がインデックス 0 のゼロで始まり、ストーリーが選択されていないことを表します。 これにより、非常に小さな容量であっても、特別なケースを使用せずにゼロ階に正しくマッピングされることが保証されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n + k log n) | 並べ替えが優先され、各クエリは二分検索を使用します。 
| スペース | O(n) | プレフィックス合計配列とソートされたリスト |

 この制約では最大 200,000 個の要素が許可されており、この複雑さは一般的な制限内に問題なく収まります。 一度ソートし、対数時間で各クエリに応答することで、最悪の場合でもソリューションの効率性が維持されます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, k = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    a.sort()
    pref = [0]
    for x in a:
        pref.append(pref[-1] + x)

    import bisect
    res = []
    for cap in b:
        res.append(str(bisect.bisect_right(pref, cap) - 1))
    return " ".join(res)

# minimum size
assert run("1 1\n5\n5\n") == "1"

# cannot take anything
assert run("3 2\n10 20 30\n1 5\n") == "0 0"

# all equal
assert run("4 2\n3 3 3 3\n6 12\n") == "2 4"

# large increasing capacities
assert run("5 3\n1 2 3 4 5\n3 6 15\n") == "2 3 5"

 ## 特殊なケース

 すべてのストーリーが所定の本の容量より大きい場合、ソートによって最小のストーリーが依然として大きすぎることが確認されます。 この場合、最初の要素のプレフィックスの合計がすでに容量を超えており、バイナリ検索ではインデックス 0 が返され、正しくゼロ ストーリーが得られます。 

10^18 に近い値など、非常に大きな容量の場合でも、合計が 64 ビットの範囲内にあるため、プレフィックス合計配列はそれらを正しく処理します。 二分検索では単純に完全なプレフィックス長が返されるため、すべてのストーリーを含めることができます。 

ストーリーが 1 つだけの場合、プレフィックス配列は次のようになります。`[0, a1]`。 以上の容量`a1`1 つのストーリーが生成され、それ以外の場合は 0 のストーリーが生成され、二分探索では特別な処理を行わずにこの動作が自然に再現されます。
