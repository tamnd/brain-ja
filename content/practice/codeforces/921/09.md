 ## 解決策
 ## 問題の理解

 ロボットは格子状の迷路に配置され、各セルは隣接する 4 つのセルに接続されますが、隣接するセル間の移動は通行できない壁またはロックされたドアによってブロックされる可能性があります。 一部のセルにはキーが含まれており、一部のセルは出口です。 ロボットは固定セルから開始し、小さな命令言語で書かれたプログラムを実行して出口に到達する必要があります。 

命令セットは意図的に制限されています。 ロボットは、4 方向に移動したり、ある方向にドアを開けたり、鍵を拾ったり、実行を終了したりすることができます。 制御フローは、境界付きループと、前のアクションが成功したかどうかに応じた条件によって提供されます。 重要な微妙な点は、アクションが「操作なし」になる可能性があることです。たとえば、壁を通り抜けようとしても何もしませんし、ドア以外のドアを開けようとしても何もしませんが、それでもコマンドの実行としてカウントされます。 

タスクは、通常の意味でのパスを見つけることではなく、これらの命令のセマンティクスを尊重しながら、ロボットが最終的に出口に到達することを保証するプログラムを出力することです。 

この制約は、最大 100,000 個のドアとキーを備えた最大 1000 x 1000 のグリッドという非常に大規模な環境を意味します。 クエリごとの直接シミュレーション、またはグリッド全体で到達可能性をゼロから繰り返し再計算する戦略は、グリッド サイズが 2 次またはそれより悪い場合、遅すぎます。 10^6 ノードを複数回完全に再処理するとすでに限界が押し上げられるため、許容可能なソリューションではグリッドをグラフとして扱い、大きな領域を不必要に再訪することを避ける必要があります。 

単純なアプローチでよくある失敗例は、「キーが消費される」ルールを考慮せずに、ドアを永続的にブロックまたは永続的に開いたものとして扱うことです。 たとえば、最短パスが早い段階でキーを使用するが、後の迂回でも同じキーが必要な場合、最初に遭遇したドアをグローバルに開く貪欲な BFS は正確性を損ないます。 

もう 1 つの微妙な落とし穴は、ドアの使いやすさが時間の経過とともに対称的ではないことを無視していることです。 2 つの通路が 1 つのドアを共有しており、ドアを開けると他の場所で必要な鍵が消費される状況を考えてみましょう。 目に見えるものすべてを開く単純なフラッド フィルでは、将来のアクセシビリティを誤って想定してしまいます。 

## アプローチ

 ブルートフォース解釈では、考えられるすべてのロボット プログラムをシミュレートしたり、パスを探索してすべての決定をネストされたループや条件に直接エンコードすることによってプログラムを構築したりすることもあります。 これではすぐに 2 つの問題が発生します。 まず、ドアとキーを使用して 1000 x 1000 のグリッドでパスを列挙すると、各キーが状態空間を変更するため、状態に依存する動作が指数関数的に増加します。 第 2 に、位置と収集されたキーの拡張状態空間にわたる単一の完全な BFS でさえ、キーが最大 100,000 個になる可能性があり、状態表現が膨大になるため、実行不可能です。 

問題を扱いやすくする主な観察は、キーが区別できないことです。 どの鍵でもどのドアを開けることができ、ドアを開けると鍵は消費されます。 つまり、キーは単なるリソース数であり、ID ではありません。 この構造は、エッジ (ドア) が 1 ユニットのグローバル消耗品リソースを必要とし、キーが補充ポイントとなるグラフになります。 

これにより、この問題は単位コストの消耗品エッジを含むグラフにおける到達可能性の問題に帰着します。ここで唯一意味のある問題は、必要なときに利用可能なキーを常に貪欲に使用するポリシーの下で出口に到達できるかどうかです。 これにより、迷路を「ブロックされているがロック解除可能なエッジ」のキューで強化された BFS トラバースとして扱うことができ、出現したキーを収集しながら最初から到達可能性をシミュレートできます。

「どのキーがどこで使用されているか」の状態を探索する代わりに、セルを一度探索し、使用可能なキーのグローバル プールを維持します。 ドアに遭遇すると、鍵を入手するまでドアを通過するのを延期し、鍵が見つかるとすぐに保留中のドアのロックを解除します。 これにより、指数関数的な状態の爆発が、エッジごとに償却された一定の処理を伴う線形走査に折りたたまれます。

 ## アルゴリズムのチュートリアル

 1. 迷路をセルのグラフとして扱います。隣接関係は 4 つの方向によって与えられますが、各隣接関係は壁またはドアによってブロックされる可能性があります。 これらの接続を高速ルックアップ構造に前処理して、一定時間内に遷移をテストできるようにします。 
2. 最初のセルから開始して BFS または DFS を実行します。 目的は、キーが収集されるにつれて徐々にドアのロックを解除しながら、現在の使用可能なキーの数でどのセルに到達できるかを判断することです。 
3. 到達可能なセルのキュー、ブール値の訪問済みグリッド、および使用可能なキーのグローバル カウンタを維持します。 キーを含むセルに入力すると、すぐにキー数が増加します。 これは、どのブロックされたエッジを通過できるようになるかが変わるため、重要です。 
4. 訪問済みのセルに隣接しているが現在鍵がないために開けることができないドアの二次構造、通常はキューまたはリストを維持します。 各エントリには、ドアの 2 つのエンドポイントが格納されます。 
5. キーの数が増加するたびに、保留中のドアを繰り返し処理します。少なくとも 1 つのキーがある場合は、保存されているドアを開いて 1 つのキーを消費し、そのエッジを通行可能として扱います。 新しく到達可能なセルはすべて BFS キューにプッシュされます。 1 つのドアのロックを解除すると、他の鍵やドアへのアクセスがロック解除される可能性があるため、この伝播は非常に重要です。 
6. これらのルールに基づいて到達可能なすべてのセルが使い果たされるまで、BFS を続行します。 いずれかの時点で出口セルに到達した場合、経路の存在が確認されるため、早期に停止できます。 
7. 出力の構造は、到達可能性に直接従うものです。概念的には、開始から終了までの有効なパスを与える BFS 親ポインターと一致する走査順序を想定しています。 出口から開始までバックトラックし、方向指示を出すことで動きを再構築します。 

### なぜ効果があるのか

 維持される不変条件は、BFS キュー内のすべてのセルはいつでも、一連の移動と最大で現在消費されるキーの数を使用して到達可能であり、すべての保留中のドアは、十分なキーが存在するときに正確に使用可能になるフロンティア エッジを表すということです。 キーは区別できず、消耗品としてのみ機能するため、アルゴリズムはドアを開ける順序の違いを区別する必要はありません。 作動できるドアの数を追跡するだけです。 これにより、元の迷路にパスが存在する場合、BFS は最終的にキーの可用性と一致する順序で必要なすべてのドアのロックを解除し、到達可能なすべての出口に到達することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque, defaultdict

def solve():
    n, m = map(int, input().split())
    sx, sy = map(int, input().split())

    # adjacency structures
    walls = set()
    doors = defaultdict(list)
    keys = set()
    exits = set()

    c = int(input())
    for _ in range(c):
        x1, y1, x2, y2 = map(int, input().split())
        walls.add((x1, y1, x2, y2))
        walls.add((x2, y2, x1, y1))

    d = int(input())
    for _ in range(d):
        x1, y1, x2, y2 = map(int, input().split())
        doors[(x1, y1)].append((x2, y2))
        doors[(x2, y2)].append((x1, y1))

    k = int(input())
    for _ in range(k):
        x, y = map(int, input().split())
        keys.add((x, y))

    e = int(input())
    for _ in range(e):
        x, y = map(int, input().split())
        exits.add((x, y))

    q = deque()
    q.append((sx, sy))

    vis = set()
    vis.add((sx, sy))

    key_count = 0
    pending = deque()

    parent = {}

    def try_add(nx, ny, px, py):
        if (nx, ny) not in vis and (px, py, nx, ny) not in walls:
            vis.add((nx, ny))
            parent[(nx, ny)] = (px, py)
            q.append((nx, ny))

    while q:
        x, y = q.popleft()

        if (x, y) in keys:
            key_count += 1

        if (x, y) in exits:
            target = (x, y)
            break

        for dx, dy in [(1,0), (-1,0), (0,1), (0,-1)]:
            nx, ny = x + dx, y + dy
            if (x, y, nx, ny) in doors[(x, y)]:
                if key_count > 0:
                    key_count -= 1
                    try_add(nx, ny, x, y)
                else:
                    pending.append((x, y, nx, ny))
            else:
                try_add(nx, ny, x, y)

        # try open pending doors if keys available
        new_pending = deque()
        while pending and key_count > 0:
            x1, y1, x2, y2 = pending.popleft()
            if (x2, y2) not in vis:
                key_count -= 1
                try_add(x2, y2, x1, y1)
            else:
                new_pending.append((x1, y1, x2, y2))
        pending = new_pending

    # reconstruct path
    path = []
    cur = target
    while cur in parent:
        px, py = parent[cur]
        path.append((cur[0] - px, cur[1] - py))
        cur = (px, py)

    path.reverse()

    # convert to commands
    mp = {(1,0):"move-down", (-1,0):"move-up",
          (0,1):"move-right", (0,-1):"move-left"}

    out = []
    for d in path:
        out.append(mp[d])
    print(" ".join(out))

if __name__ == "__main__":
    solve()
```このコードは、明示的な壁とドアの構造を使用して隣接関係を構築し、開始セルから BFS を実行します。 親マップは、出口が見つかったときに有効なパスを再構築するために使用されます。 キーの処理は BFS 拡張に統合されています。キー セルに入るとグローバル カウンタが増加し、キーが存在する場合はドアがすぐに通過されるか、後の処理のために保存されます。 

最も脆弱な部分は、ドアが 1 回だけ消費されるようにすることです。 この実装では、ドアが発見されたときではなく、ドアが実際に使用されたときにキー カウンタをデクリメントすることでこれを強制します。 もう 1 つの微妙な点は、再構築が親ポインターに依存しているため、すべてのエンキュー操作で一意の親エッジを保存する必要があることです。

 ## 特殊なケース

 問題となるのは、鍵を回収する前にドアが発見された場合です。 アルゴリズムはそれを破棄せずに保存します。 キーが表示されると、保留中のキューが処理され、ドアが使用可能になります。 これにより、一時的にのみブロックされているパスの欠落を回避できます。 

もう 1 つのケースは、単一のキー リソースを共有する複数のドアです。 この実装により、各ドアが通過時に正確に 1 単位のキー数を消費することが保証され、過度の使用や時期尚早のロック解除が防止されます。
