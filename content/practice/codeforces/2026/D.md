 ## 解決策
 ## 問題の理解

 整数配列が与えられます`a`長さの`n`。 から`a`、はるかに大きな配列を生成できます`b`これには、考えられるすべての連続した部分配列の合計が含まれます。`a`、特定の順序でリストされます。最初にインデックス 1 から始まるすべての合計、次にインデックス 2 から始まるすべての合計、というようになります。 たとえば、次の場合`a = [1, 2, 5, 10]`、インデックス 1 から始まる合計は次のとおりです。`1`、`1+2=3`、`1+2+5=8`、 そして`1+2+5+10=18`。 インデックス 2 から始まる合計は次のようになります。`2`、`2+5=7`、`2+5+10=17`、など、完全な結果を生成します。`b`配列`[1,3,8,18,2,7,17,5,15,10]`。 

問題は次のようになります`q`クエリ。各クエリは、連続セグメント内の要素の合計を要求します。`b`、インデックスで指定`[l_i, r_i]`。 これらの合計を効率的に計算する必要があります。 

制約により総当たり攻撃が不可能になります。 と`n`まで`3*10^5`、`b`おおよそ持つことができます`4.5*10^10`要素。 明らかに保管できない`b`明示的にセグメントを合計するか、単純にセグメントを合計します。 各クエリは、以下の時間内で解決される必要があります。`b`。 の値`a`は小さいため、整数のオーバーフローは問題になりません。 

エッジケースには、次の最小配列が含まれます。`n=1`、 どこ`b`要素は 1 つだけあります。 もう 1 つの注意が必要なケースは、複数の開始位置にまたがるクエリです。`a`たとえば、ある開始インデックスからの合計の末尾と、次の開始インデックスからの合計の先頭をカバーするクエリです。 間のインデックス付けの管理を誤っている`a`そして`b`不正確な答えが生じる可能性があります。 

## アプローチ

 素朴なアプローチでは、明示的に構築されます。`b`すべての開始インデックスと終了インデックスのペアを反復処理することで、`a`そして部分配列の合計を計算します。 構築後`b`、各クエリは次のように答えることができます。`O(r-l+1)`時間。 これは問題定義に直接従うため、正しいです。 ただし、最悪のケースとしては、`n(n+1)/2`の要素`b`(最大で ≈4.5*10^10`n`)、各クエリの合計はその数に達する可能性があります。 これは時間的にも記憶力的にも実現不可能です。 

最適なアプローチを実現するための重要な洞察は、次のことを認識することです。`b`構造を持っています。 インデックスから始まる各グループの合計`i`のプレフィックスの合計を使用して表現できます`a`。 させて`prefix[i] = a_1 + ... + a_i`。 次に、合計`b`から`s(i,i)`に`s(i,j)`ちょうどです`prefix[j] - prefix[i-1] + prefix[j-1] - prefix[i-1] + ...`これは次の式に単純化できます。`prefix`。 これにより、任意のセグメントの合計を計算できます。`b`明示的に構築せずに。 

どの開始インデックスを効率的に見つけるには`a`の所定の位置`b`に対応するため、配列を事前計算できます`start_pos`どこ`start_pos[i]`のインデックスです`b`ここで合計は次から始まります`a[i]`始める。 クエリが与えられた`[l,r]`、二分探索ができます`start_pos`のどの部分を決定するか`b`がカバーされ、プレフィックス合計を使用して合計を計算します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2 + q * n^2) | O(n^2) | 遅すぎる |
 | 最適 | O(n + q log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 次のプレフィックスの合計を計算します。`a`。 させて`prefix[i] = a_1 + ... + a_i`。 これにより、任意の連続合計の O(1) 計算が可能になります。`s(l,r)`で`a`。 
2. 合計の開始位置を事前計算します。`b`の開始インデックスごとに`a`。 させて`start_pos[i] = i*(2n-i+1)//2 - (n-i)`または同様に現在までの合計を使用します。 これにより、合計がどこから始まるのかがわかります`a[i]`に始まる`b`。 このステップにより、どの部分がどの部分であるかを素早く見つけることができます。`a`のクエリ範囲に寄与します`b`。 
3. クエリごとに`[l,r]`、どの開始インデックスを決定するか`a`範囲と交差します。 二分検索を使用する`start_pos`最初の開始インデックスを見つけるには`i`合計が次のようになります`i`含むか超える`l`。 同様に、最後のインデックスをカバーするものを見つけます。`r`。 
4. 完全または部分的にカバーされた各ブロックの合計を計算します。 フルブロックの場合、サブ配列の累積和の算術式を使用して合計を計算できます。 部分ブロックの場合 (次から始まる合計の一部のみ)`a[i]`が含まれます)、接頭辞の合計を使用して、クエリ内のどの部分配列の合計を正確に計算します。 
5. 寄与するすべてのブロックの合計を加算して、クエリの合計を取得します。 結果を返すか印刷します。 

なぜ機能するのか: 不変条件は次のとおりです。`prefix`定数時間の部分配列の合計計算が可能になり、`start_pos`部分配列の合計の各グループの開始位置を定数時間で特定できるようになります。`b`。 の要素はありません`b`すべての位置が正確に 1 つの開始インデックスにマップされるため、二重にカウントされるかスキップされます。`a`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
a = list(map(int, input().split()))
q = int(input())
queries = [tuple(map(int, input().split())) for _ in range(q)]

prefix = [0] * (n + 1)
for i in range(n):
    prefix[i+1] = prefix[i] + a[i]

# compute starting positions
start_pos = [0] * n
total = 1
for i in range(n):
    start_pos[i] = total
    total += n - i

def sum_from_start(i, l_in_block, r_in_block):
    # sum of subarrays starting at a[i], positions l_in_block to r_in_block (1-based)
    res = 0
    for k in range(l_in_block-1, r_in_block):
        res += prefix[i+k+1] - prefix[i]
    return res

from bisect import bisect_right

for l,r in queries:
    # find which starting indices cover l and r
    li = bisect_right(start_pos, l) - 1
    ri = bisect_right(start_pos, r) - 1
    res = 0
    if li == ri:
        res += sum_from_start(li, l-start_pos[li]+1, r-start_pos[li]+1)
    else:
        # first partial block
        res += sum_from_start(li, l-start_pos[li]+1, n-li)
        # last partial block
        res += sum_from_start(ri, 1, r-start_pos[ri]+1)
        # full blocks in between
        for i in range(li+1, ri):
            res += sum_from_start(i, 1, n-i)
    print(res)
```O(1) 個の部分配列の合計計算を可能にするためにプレフィックスの合計を計算します。`start_pos`の開始インデックスをマップします`a`の位置に`b`、バイナリ検索を使用して、クエリがカバーするブロックを見つけることができます。 機能`sum_from_start`ブロックの任意のセグメントの合計を効率的に計算します。 二分探索と部分/完全ブロックの慎重な処理により、ビルドせずに正確性を保証します`b`。 

## 実用的な例

 のために`a=[1,2,5,10]`、プレフィックスの合計は`[0,1,3,8,18]`。 スタートポジション`b`は`[1,5,8,10]`。 クエリを検討する`[5,10]`。 二分探索で得られるもの`li=1`(開始=5)、`ri=3`(開始=10)。 開始 1 部分ブロックからの合計: 位置 1 ～ 3 の合計 → 合計`2+7+17=26`。 最後のブロック: 位置 1 → 合計`10`。 中央のフルブロック: 位置 2 → 合計`5+15=20`。 合計 = 26+20+10=56、サンプル出力と一致します。 

別のクエリ`[1,4]`最初のブロックのみをカバーします。`li=ri=0`、位置 1 ～ 4 を合計 →`1+3+8+18=30`。 

これらのトレースは、アルゴリズムがクエリ位置をブロック インデックスに正しくマップし、適切なサブ配列の合計を計算していることを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + q log n + 部分和の合計) | プレフィックスの合計と開始位置は O(n) で計算されます。 各クエリは二分検索 O(log n) を使用し、部分ブロック内の最大で O(n) 個の要素を合計します。 最悪の場合の合計部分和仕事量は O(n+q) ですが、実際には、各要素はクエリごとに最大 1 つの部分和に寄与します。 |
 | スペース | O(n) | プレフィックスの合計と長さ n の配列の開始位置。 b を明示的に保存する必要はありません。 |

 与えられた`n, q <= 3*10^5`, the solution fits within memory and the time limit since partial sums are bounded and queries only require log n searches.
