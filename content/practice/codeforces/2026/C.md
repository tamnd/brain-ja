 ## 解決策
 ## 問題の理解

 1 から n までの番号が付けられた一連のアクション フィギュアが与えられます。 図 i は i コインかかりますが、1 日目にすぐに購入することはできません。 i 日目からのみ利用可能になります。 n 日目以降は、すべてが利用可能になります。 

n 日間にわたり、毎日が Monocarp が店を訪問できる営業日か、来店できない休業日のいずれかになります。 訪問日に、彼は現在入手可能なフィギュアのサブセットを購入することができます。 一度の訪問で少なくとも 2 つのフィギュアを購入した場合、そのバッチの中で最も高価なフィギュアが無料になります。 

目標は、支出総額を最小限に抑えながら、すべてのフィギュアを 1 回だけ購入することです。 

主な問題点は、購入の決定が時間によって制限されることです。以前の数値はいつでも入手できますが、後の数値は特定の日まで待つ必要があり、割引ルールにより購入のグループ化が重要になります。 

制約は大きく、テスト ケース全体の n の合計は 4·10^5 に達するため、日数や数値にわたる二次戦略は不可能です。 重いデータ構造を繰り返し実装すると、テスト ケースあたり O(n log n) であっても、最悪の場合には遅すぎるため、線形または線形に近い動作を目指す必要があります。 

訪問日が早い時間にはまばらであるが、遅い時間には集中する場合、微妙な特殊なケースが現れます。 たとえば、最終日のみが利用可能な場合は、すべてのフィギュアを一緒に購入する必要があり、最大値のみが無料になります。 これにより、コストは 1 + 2 + ... + (n−1) になります。 在庫状況を考慮せずに購入を遅らせようとする単純な貪欲な人は、遅い日のグループ分けを多用することでコストを簡単に過小評価する可能性があります。 

もう 1 つの注意が必要なケースは、訪問日が連続する場合です。 たとえば、s = "11111" です。 その後、隣接する日の購入をすべてペアにして割引を最大化できます。 訪問ごとに常に 1 つの商品を購入するという単純な戦略では、購入を組み合わせてコストを削減する機会が失われます。 

本当の緊張は、後でペアリングできるようにフィギュアの購入を遅らせるか、ペアリングの機会を失わないようすぐに購入するかを決めることです。 

## アプローチ

 強引な解釈では、意思決定をシミュレートします。フィギュアごとに、それが購入される日を選択し、グループ化する利用可能なフィギュアを毎日選択します。 その日に購入されるアイテムのすべてのサブセットが将来の在庫状況と割引に影響を与えるため、これは指数関数的分岐の割り当ての問題になります。 サブセットの DP または数日および「未購入のマスク」の DP に限定したとしても、状態空間は 2^n であり、これは n が 4・10^5 までの場合には直ちに不可能です。 

重要な点は、割引構造が非常に厳格であることです。どの日でも、その日の購入で最も高価な商品のみが無料になります。 これは、すべての「無料アイテム」は、同じ日に購入されたより高価なアイテムと厳密に組み合わせる必要があり、毎日最大 1 つの無料アイテムを提供できることを意味します。 

したがって、問題全体は、各アイテム i を何らかの j > i (j は両方が利用可能になる日) とペアにするか、ペアにしないままにするかに帰着します。 各ペア (i, j) はコスト i を削除します。 コスト j は、それ自体がより大きなものとペアになっていない限り、常に支払われます。 

ここで視点が変わります。日数について考えるのではなく、どのインデックスをグループ化できるかのみを考慮し、グループ化は、選択した日に両方のアイテムが利用可能でなければならないという条件によってのみ制約されます。 アイテム j は j 日に入手可能になるため、j を含むペアはすべて j 日以降に発生する必要があります。つまり、アイテム i < j は両方とも j 日までに入手可能になります。 

したがって、すべてのペアリングは、前の項目 i < j を 1 つ吸収できる「後のアンカー」 j を選択するだけです。 

各 j が最大 1 つの i < j を保存でき、各 i は最大 1 回使用できる、合計の節約量を最大化したいと考えています。 問題は、より小さなインデックスをより大きなインデックスに貪欲に割り当てる方法になります。

インデックスを左から右に処理し、「訪問可能な日数」のプールを維持します。そこでは、より小さな項目を将来のより大きな項目と組み合わせるために割り当てることができます。 s[i] = 1 の日が発生するたびに、その日は潜在的なペアリングのエンドポイントとして機能しますが、それは可用性の制約で実現可能性を確認した場合に限られます。 

正しい貪欲さは次のようになります。位置 i に到達したら、i を無料アイテムとして後で訪問する日と組み合わせるか、料金を支払うかを決定します。 当社は訪問日ごとに作成されたアクティブな「スロット」のマルチセットを維持し、使用率を最大化するために可能な限り早いスロットに小さなインデックスを割り当てます。 

より具体的な単純化が現れます。利用可能な訪問容量のカウンターを維持しながら、左から右にシミュレーションします。 「1」ごとに容量が増加します。 アイテムに遭遇するたびに、可能であればそれを無料で割り当てるように努めますが、そうでない場合は料金を支払います。 この貪欲さが機能するのは、小さい項目を可能な限り早い訪問に割り当てることで、可用性の制約により選択肢が少ない大きい項目の柔軟性が保たれるためです。 

これは、「無料でペアリングできる」アイテムの数を追跡する単純な構造のリニア スキャンに帰着します。

 ## アルゴリズムのチュートリアル

 1. カウンタを維持しながら、インデックスを 1 から n まで走査します。`free_slots`割引ペアリングのために今後の訪問に割り当てることができる以前のアイテムの数を表します。 訪問日が見つかるたびに、ペアリングをホストできる可能性があるため、この容量を増やします。 
2. 位置 i に到達したら、まず空き状況を考慮します。i 日が訪問日であれば、将来の割引グループを形成する可能性が高まるため、増分します。`free_slots`。 
3. 空きスロットがある場合 (`free_slots > 0`)、項目 i を「将来のペアリング内で自由」に割り当てます。これは、デクリメントすることを意味します。`free_slots`そして私にお金を払わないでください。 
4. 利用可能なスロットがない場合は、答えに i を加えて、直ちに i を支払わなければなりません。 
5. n まで続行し、すべてのアイテムが支払われるか、将来の有効なペアリングの機会に割り当てられるようにします。 

重要な点は、訪問日がペアリングの時点で直接使用されないことです。 代わりに、以前に割り当てられていない項目によって消費される容量が作成されます。 この逆転が貪欲な働きを生むのです。 

### なぜ効果があるのか

 いつでも、`free_slots`延期して、後で訪問した日に照合できるアイテムの数を表します。 訪問ごとに割引できるのはバッチ内の最も高価なアイテム 1 つだけであるため、訪問日ごとに 1 つの潜在的な「無料アイテムの機会」が提供されます。 最初に小さいインデックスを割り当てると、残りのコストが最小限で解放されるため、訪問が使用されるたびに最大の節約が保証されます。 利用可能な訪問容量と最小の未解決項目の間のこの貪欲なマッチングにより、最適性が維持されます。これは、より大きな項目を優先して小さな項目を延期するような逸脱は、総コストを増加させるだけであるためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        s = input().strip()

        free_slots = 0
        ans = 0

        for i in range(n):
            if s[i] == '1':
                free_slots += 1

            # try to use a slot for item i+1
            if free_slots > 0:
                free_slots -= 1
            else:
                ans += (i + 1)

        print(ans)

if __name__ == "__main__":
    solve()
```実装は貪欲な解釈に直接従います。 ループインデックス i は数字 i+1 に対応します。 「1」が表示されるたびに、将来のペアリングの機会の数が増えます。 フィギュアを処理するときは、そのフィギュアをこれらの機会の 1 つに割り当てるか (スロットを消費)、そのコストを支払います。 

微妙な点は、使用するとすぐにスロットが消費されてしまうことです。 これは、各訪問で 1 つのアイテムのみを「保存」できることを反映しているため、スロットを複数回再利用することはできません。 正確さは、可能な限り早いアイテムのために常にスロットを貪欲に消費することに依存します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        s = input().strip()

        free_slots = 0
        ans = 0

        for i in range(n):
            if s[i] == '1':
                free_slots += 1
            if free_slots > 0:
                free_slots -= 1
            else:
                ans += i + 1

        out.append(str(ans))
    return "\n".join(out)

 ## 特殊なケース

 n 日目を除いて最後の瞬間まで訪問日数がない場合、アルゴリズムは蓄積しません。`free_slots`最終日までにペアリングできるアイテムを除き、それ以前のすべてのアイテムが支払われます。 これは、すべてのアイテムを最後に 1 回だけグループ化できるという事実と一致しており、最大限の割引を利用できますが、それでも訪問バッチごとに 1 つの無料アイテムに制限されます。 

全日が見学日の場合は、`free_slots`なくなることはないので、すべてのアイテムは出現するとすぐに一致します。 このアルゴリズムはスロットを即座に消費し、すべての数値を将来のバッチに吸収できることを反映して、コストを最小限に抑えます。 

訪問日がまばらで早い時期に集中している場合、スロットは蓄積されますが、大きなインデックスが表示される前に消費される可能性があります。 貪欲な消費により、小さなインデックスが常に最初に割り当てられ、後の必須支払いのために大きなインデックスが保存されます。これは、ペアリング容量が利用可能になると小さな項目を遅らせても役に立たないため、最適な構造と一致します。
