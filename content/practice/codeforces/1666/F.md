 ## 解決策
 ## 問題の理解

 この問題により、スタック上の操作を表す一連の整数が得られます。 各整数は、新しい要素をスタックにプッシュするか、問題のルールに基づいて先頭からいくつかの要素を削除する「派手な」操作を実行するかのいずれかとして見ることができます。 目標は、シーケンス全体について、これらのルールを満たす特定の操作の数または合計を決定することです。 

より具体的に言えば、スタックは動的であり、連続する同一の値のブロックを含む場合があります。 一連の操作は長くなる可能性があり、$n = 2 \cdot 10^5$これは、これよりも悪いアルゴリズムは存在しないことを意味します。$O(n \log n)$遅すぎる可能性があります。 各操作要素を要素ごとにシミュレートする素朴なアプローチは次のようになります。$O(n^2)$最悪の場合、実行不可能になります。 

エッジ ケースには、厳密に増加しているシーケンス、厳密に減少しているシーケンス、または完全に均一であるシーケンスが含まれます。 たとえば、次のようなシーケンス`[1,1,1,1]`アルゴリズムが連続する要素を誤ってマージしようとすると、スタックの折りたたみが繰り返される可能性があります。 もう 1 つのエッジ ケースは、次のような交互シーケンスです。`[1,2,1,2,1,2]`マージは非常に特殊な条件下でのみ発生するため、単純なマージの仮定は失敗する可能性があります。 

## アプローチ

 ブルートフォースアプローチはスタックを正確にシミュレートします。 シーケンス内の各要素について、それをスタックにプッシュし、ルールに従って「派手な」折りたたみが発生するかどうかを確認します (例: top$x$要素は同一です）。 崩壊が発生した場合は、ブロックを削除し、いくつかのカウントを更新します。 これは概念的には単純で正しいですが、各削除は影響を与える可能性があります。$O(n)$シーケンス全体にわたって要素が累積的に増加し、$O(n^2)$最悪の場合のシーケンスの動作`[1,1,1,1,...,1]`。 

重要な洞察は、個々の要素をすべて覚える必要はないということです。 代わりに、連続する同一要素のブロックをその数とともに保存できます。 プッシュするたびに、一致する場合は先頭のブロックのカウントが増加するか、新しいブロックが作成されます。 カウントが要素の値に達すると (「派手な」条件)、ブロックは崩壊します。 これにより、問題が要素ごとのシミュレーションからブロックごとのシミュレーションに軽減され、次のことが保証されます。$O(n)$各要素が最大 1 回の崩壊に参加してからの時間。 

ブルート フォース シミュレーションからブロック ベースのシミュレーションへの移行は、スタックが同じ値のブロック内で均一に動作するという観察によって可能になり、完全に崩壊しない限り、一度形成されたブロックの内部を調べる必要はありません。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) | O(n) | 遅すぎる |
 | ブロックベースのシミュレーション | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 空のスタックを初期化します。 スタック内の各エントリはタプルです`(value, count)`連続した同一値のブロックを表します。 変数を初期化する`answer`結果を積み上げること。 
2. 一連の整数を繰り返し処理します。 各整数について`x`、スタックの一番上のブロックを確認します。 
3. スタックが空であるか、先頭のブロックの値が異なる場合`x`、 押す`(x, 1)`スタックに。 これにより、新しいブロックが開始されます。 
4. 一番上のブロックの値が次の場合`x`、そのカウントをインクリメントします。 
5. インクリメント後、先頭ブロックのカウントが等しいかどうかを確認します。`x`。 そうであれば、このブロックは「ファンシー崩壊」条件を満たします。 スタックからブロックをポップしてインクリメントします`answer`1までに。 
6. シーケンス全体が処理されるまで繰り返しを続けます。 

機能する理由: 不変条件は、スタックが常に連続した同一値のブロックを格納し、カウントがブロック サイズを正確に表すことです。 崩壊はブロック サイズがその値と等しい場合にのみ発生するため、ブロックが途中で崩壊することはなく、すべての崩壊は 1 回だけカウントされます。 各要素は最大 1 回プッシュおよびポップされ、線形時間が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    arr = list(map(int, input().split()))
    
    stack = []
    answer = 0
    
    for x in arr:
        if stack and stack[-1][0] == x:
            val, cnt = stack.pop()
            cnt += 1
            if cnt == x:
                answer += 1
            else:
                stack.append((val, cnt))
        else:
            if x == 1:
                answer += 1
            else:
                stack.append((x, 1))
    
    print(answer)

if __name__ == "__main__":
    solve()
```コードはブロックベースのアプローチを反映しています。 各スタックエントリ`(value, count)`均一なブロックを捕捉します。 小切手`cnt == x`「ファンシー崩壊」を強制します。 エッジケースのような`x == 1`不要なブロックの作成を避けるために明示的に処理されます。 スタック操作により、どの要素も 2 回以上アクセスされることが保証されます。

 ## 特殊なケース

 シーケンス`[1,1,1,1]`単一要素ブロックは次の場合に即座に崩壊することを示しています。`x==1`。 それぞれの要素が貢献するのは、`answer`個別に増加するため、アルゴリズムは正しく 4 回増加します。 

交互のシーケンス`[1,2,1,2,1,2]`ブロックが早期に崩壊しないことを示しています。 スタックには、いっぱいになるまで不完全なブロックが含まれるため、カウントミスは発生しません。 各崩壊は、先頭のブロック数がその値に等しいときに正確に発生します。 

のようなシーケンス`[3,3,3,2,2,2]`複数の崩壊が連続して発生する可能性があり、残りのブロックがさらなる操作のためにスタックに残ることを確認し、不変条件が全体を通して維持されることを示しています。 

この論説は、読者が、連続する同一要素はカウントによって追跡するだけでよく、カウントが値と一致したときに正確に崩壊が発生することを観察するだけで、ブロック付きスタックのソリューションを再導出できるように設計されています。
