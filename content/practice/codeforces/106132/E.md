 ## 解決策
 ## 問題の理解

 コンパクトな文字列として記述された単一の算術式が与えられます。 式には、10 進数、プラス記号、および乗算記号のみが含まれます。 各桁は独立した数値であるため、複数桁の整数や括弧はありません。 

タスクは、乗算が加算よりも強力であり、同じ演算子タイプ内で評価が左から右に進む標準的な演算子のルールに基づいてこの式を評価することです。 最終出力は完全に評価された式の整数の結果ですが、非常に大きくなる可能性があるため、任意精度の算術演算が必要です。 

制約の長さは短く、最大 1000 文字です。 これにより、二次または三次解析技術が遅すぎるという懸念が即座に排除されます。 O(n²) アプローチでも存続する可能性はありますが、その必要はありません。 優先順位を正しく処理すれば、リニア スキャンで十分であることは明らかです。 

優先順位を無視して左から右への評価を想定すると、微妙な落とし穴が発生します。 たとえば、通訳すると、`2+3*4`厳密に左から右に指定すると、`(2+3)*4 = 20`、これはルール上間違っています。 もう 1 つの間違いは、乗算チェーンを適切にグループ化せずに数字を個別に評価しようとすることです。 

エッジ ケースは、乗算チェーンにゼロが含まれる場合、または式が長い乗算シーケンスで開始または終了する場合に発生します。 例えば、`0*1*2+3`最終項を追加する前に、積全体を正しくゼロに折りたたむ必要があります。 

## アプローチ

 ブルート フォース解釈では、文字列を繰り返しスキャンし、最も優先順位の高い演算を評価するか、完全な括弧をシミュレートします。 1 つの方法は、式をすべての可能な括弧に変換するか、乗算セグメントを見つけてそれらの計算値で置き換えることによって式を繰り返し縮小することです。 これは、各リダクションによって文字列がシフトされ、再スキャンが必要になる可能性があり、O(n²) 以上の動作が発生する可能性があるため、すぐに非効率になります。 

より構造化されたブルート フォース アプローチは、式を明示的にトークンに変換し、最初に乗算、次に加算を繰り返し解決することで評価をシミュレートすることです。 これでも通常、トークン リストを複数回渡す必要があります。 最悪の場合、各パスで演算子が 1 つだけ削除され、O(n²) の動作が発生します。 

重要な観察は、乗算はローカルでのみ相互作用するということです。乗算は、プラス記号で区切られた連続したセグメントを形成します。 乗算は優先順位が高く、結合されたままであるため、形式のすべての最大セグメントは次のようになります。`a * b * c * ...`独立して完全に折りたたむことができます。 このようなすべてのセグメントが 1 つの数値に削減されると、加算のみが残り、これを 1 回のパスで累積することができます。 

これにより、現在の乗算チェーンの実行中の積を維持し、プラス記号が出現するたびにそれを実行中の合計に加算する単一の線形スキャンが可能になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在の乗算アキュムレータと最終合計という 2 つの状態を維持しながら、式を左から右に処理します。 

1. 現在の合計が 0、現在の積が 1 に等しい状態から開始します。 これらはそれぞれ、これまでに処理されたすべての評価とアクティブな乗算チェーンを表します。 
2. 式を 1 文字ずつ読みます。 数字が見つかると、それは整数に変換され、現在の積に乗算されます。 これが機能するのは、プラス演算子がそれを中断するまで、数字が乗算チェーンに属しているためです。 
3. プラス記号が出現すると、現在の積を実行中の合計に加算して現在の乗算チェーンを終了し、積を 1 にリセットします。 これは、加算が独立した乗法ブロックを分離することを反映しています。 
4. 乗算記号が現れた場合、すぐには何もしません。乗算は、今後の数字が現在の積にどのようにグループ化されるかにのみ影響するためです。 
5. 文字列全体を処理した後、最後の乗算チェーンがプラス記号で終わっていないため、最終的な積を合計に加算します。 

重要な考え方は、乗算は数字を積に継続的に折り畳むことによって遅延的に処理され、加算は完成した積を最終結果にコミットするということです。 

### なぜ効果があるのか

 スキャンのどの時点でも、現在の積は最後のプラス記号以降の式の連続セグメントの値を正確に表します。 これは、乗算が結合的であり、チェーンの左結合評価が増分乗算と同等であるため当てはまります。 プラスが現れるたびに、式を独立したブロックに分割し、値がそれ以上相互作用しないようにします。 したがって、これらのブロック積を合計すると、元の式の正確な優先順位が正しい評価が再現されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

s = input().strip()

total = 0
cur = 1

for ch in s:
    if ch.isdigit():
        cur *= int(ch)
    elif ch == '*':
        continue
    else:  # '+'
        total += cur
        cur = 1

total += cur
print(total)
```この実装は、前述の不変構造を直接反映しています。 変数`cur`完全な乗算セグメントを累積しますが、`total`完了したすべてのセグメントの合計を保存します。 

微妙だが重要な詳細は、最後に追加されたものです。`cur`ループが終了した後。 このステップを行わないと、式がプラス記号で終わらない限り、最後の乗算チェーンは決してコミットされません (定義上、常にそうなります)。 

もう 1 つの詳細は、乗算記号が明示的に無視されることです。 これは安全です。乗算では、演算子を読み取る時点ではアクションが必要なく、接続する桁でのみアクションが必要です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys as _sys
    from math import prod
    s = _sys.stdin.readline().strip()

    total = 0
    cur = 1
    for ch in s:
        if ch.isdigit():
            cur *= int(ch)
        elif ch == '*':
            continue
        else:
            total += cur
            cur = 1
    total += cur
    return str(total)

 ## 特殊なケース

 エッジ ケースの 1 つは、式に文字列境界で終わる長い乗算チェーンが含まれている場合です。`2*3*4`。 アルゴリズムは数字を次のように処理します。`cur`最後までプラス記号が表示されないため、最後の追加ステップで製品が正しくコミットされます。`24`。 

もう 1 つのエッジ ケースは、チェーンの奥深くでのゼロによる乗算です。たとえば、`9*0*5+7`。 乗算の累積は、最初のゼロの桁ですぐにゼロに崩壊し、このゼロは合計に追加されるまでチェーンの残りの部分で持続し、次の結果が得られます。`0 + 7 = 7`。 

最後の微妙なケースは、両方の演算子を混合した連続演算です。`8+2*3*4+1`。 このアルゴリズムでは、プラスが発生するたびに現在の乗算セグメントが凍結されて加算され、加算境界を越えた乗算の漏れが防止されます。
