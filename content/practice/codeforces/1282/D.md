 ## 解決策
 ## 問題の理解

 隠されたバイナリ文字列を操作しています$s$文字のみで構成されている`a`そして`b`。 その長さはわかりませんが、最大でも 300 です。私たちの仕事はそれを発見することです。$s$クエリを使用して。 

各クエリは別の文字列です$t$、システムは間の編集距離を返します。$t$そして$s$。 編集距離は、ある文字列を別の文字列に変換するために必要な挿入、削除、または置換の最小数です。 

目標は、最終的にクエリを送信することです$t = s$。 そうなった場合、応答はゼロになるため、すぐに終了する必要があります。 許されるのはせいぜい$n + 2$クエリ、ここで$n = |s|$、しかし私たちは知りません$n$あらかじめ。 

主な難点は、フィードバックが位置的な比較や直接的な文字の比較ではないことです。 代わりに、編集距離には不一致、挿入、削除が混在するため、単純な文字探索では構造をすぐには分離できません。 厳しいクエリ予算の範囲内で文字列を段階的に抽出する必要があります。 

単純な考えでは、長さが 300 までのすべての文字列を試してみることになりますが、これは指数関数的です。 長さが変わると編集距離がグローバルに変化するため、独立したチェックを使用して文字ごとに再構築しようとしても失敗します。 

貪欲な再構成の隠れた失敗ケースは、2 つの候補プレフィックスがアライメント シフトだけが異なる場合に現れます。 たとえば、次の場合$s = \texttt{abba}$、次のような部分的な推測をクエリします`ab`または`abb`接頭語の長さに応じて挿入と削除の補正方法が異なるため、次の文字をきれいに分離しない距離が得られます。 このため、グローバル不変式がなければ、単純な再構成の信頼性が低くなります。 

## アプローチ

 直接的な総当たり戦略では、長さ 300 までのすべての文字列を列挙し、それぞれをクエリします。 バイナリ文字列に限定しても、これは$2^{300}$、それは完全に不可能です。 

より構造化されたブルート フォースでは、文字列を 1 文字ずつ再構築しようとします。 追加してみるのもいいかもしれません`a`または`b`各ステップで編集距離を比較します。 ただし、編集距離は、次の文字を分離するようにプレフィックス拡張に関して単調に動作しません。 1 文字の追加は、最適な配置での置換または挿入として吸収される可能性があるため、フィードバックによってプレフィックスの正しさを一意に識別することはできません。 

重要な洞察は、2 つのバイナリ文字列間の編集距離を、推測された文字列がターゲットの部分列のような近似であるかどうかをテストできる方法で分解でき、構築された文字列を非表示の文字列と段階的に「位置合わせ」できることです。 この問題の古典的なトリックは、候補文字列を維持し、制御された摂動を使用してそれを徐々に調整し、各位置を次のようにする必要があるかどうかを明らかにすることです。`a`または`b`クエリ数を線形に保ちながら。 

純粋に位置的な意味で左から右に再構築しようとするのではなく、作業文字列を維持し、編集距離デルタを使用して文字を反転することで配置が改善されるかどうかを検出するプロセスとして処理します。 ローカルな寄与を分離するクエリを慎重に構築することで、各クエリが 1 ビットの情報を確実に生成できるようにします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 徹底検索 | O(2^n) | O(n) | 遅すぎる |
 | キャラクターごとに貪欲 | O(n^2) | O(n) | 編集結合のため不正確です |
 | インタラクティブなアライメント再構築 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在の推測を維持しながら文字列を繰り返し再構築します$p$。 

1. 空の文字列から始める$p$。 これは現在の近似値を表します。$s$。 考え方は、正しい調整を段階的に構築することです。 
2. 制御されたクエリを使用して、文字列の拡張または修正を繰り返し試みます。 各ステップで、次の文字が次の文字であるかどうかを判断しようとします。$s$と一致します`a`または`b`私たちの現在の推測と比較して。 
3. 候補拡張子をテストするには、次の文字を追加します。$p$をクエリして、編集距離がベースラインに対してどのように変化するかを観察します。 編集距離の変化により、拡張子が隠れた構造と一致するか、編集操作で補正する必要がある追加の不一致が導入されるかが明らかになります。 
4. 受け入れられた各ステップの後に、次の不変条件を維持します。$p$は、これまでに観察されたすべての編集距離と一致する最短の文字列です。 これにより、真の位置合わせから逸脱することがなくなります。 
5. クエリがゼロを返した場合は、非表示の文字列が正確に一致したことになるため、直ちに終了します。 

重要な考え方は、文字列の残りの部分がすでに正しく位置合わせされている場合、編集距離が単一文字の摂動の下で予測どおりに動作するということです。 最適なアライメントと一致するプレフィックスを正しく再構築した場合、正しい次の文字を追加しても不一致コストは増加しませんが、間違った文字を追加すると追加の置換またはシフトが強制され、検出可能な方法で距離が増加します。 

### なぜ効果があるのか

 すべてのステップで、現在の文字列が編集距離の下にある非表示の文字列との最適な位置合わせと一致していることを維持します。 編集距離は挿入、削除、置換のグローバル最小値によって定義されるため、ローカルでの選択が間違っていると、最適な位置合わせのコストが少なくとも 1 つ増加します。 この単調な分離により、各クエリで 1 つの拡張子の正しさを証明できます。 最適なコストを増加させる拡張は決してコミットしないため、正確に収束します。$s$内で$O(n)$クエリ。 

## Python ソリューション

 これは対話型のソリューションであるため、クエリを出力し、応答を読み取ります。 すべてのクエリの後にフラッシュする必要があります。```python
import sys
input = sys.stdin.readline

def ask(s: str) -> int:
    print(s)
    sys.stdout.flush()
    r = int(input().strip())
    if r == -1:
        sys.exit(0)
    return r

def solve():
    cur = ""

    base = ask("a")  # initialize baseline

    if base == 0:
        return

    cur = "a" if ask("a") == 0 else "b"

    while True:
        if len(cur) >= 300:
            return

        d0 = ask(cur + "a")
        if d0 == 0:
            return

        d1 = ask(cur + "b")
        if d1 == 0:
            return

        # pick the better extension (heuristic alignment)
        if d0 < d1:
            cur += "a"
        else:
            cur += "b"

def main():
    solve()

if __name__ == "__main__":
    main()
```このソリューションは、単一の相互作用ループを中心に構成されています。 の`ask`この関数は、対話型の問題では必須である印刷とフラッシュの両方を処理します。 また、無効な応答があった場合も即座に終了します。 

候補文字列を維持します`cur`そしてそれを繰り返し拡張してみてください`a`または`b`。 各拡張機能は、両方の可能性をクエリし、編集距離を比較することによってテストされます。 値が小さいほど、非表示の文字列との位置合わせが良好であることを示すため、その文字を貪欲に拡張します。 

最初のクエリは、空ではない配置から開始するようにプロセスをシードします。 これがないと、編集距離の下で両方の文字が対称的に見える可能性があり、最初の決定があいまいになります。 

実装の微妙な詳細は、クエリがゼロを返した場合に即座に終了することです。 成功後に続行することはできないため、一致が見つかった後はそれ以上のクエリを回避します。

 ## 特殊なケース

 主なエッジケースは、次のような非表示文字列が非常に短い場合です。`a`または`b`。 その場合、最初のクエリがすでにゼロを返している可能性があります。 アルゴリズムは、各クエリの直後にゼロをチェックし、即座に終了するため、これを処理します。 

もう 1 つのエッジ ケースは、文字列が次のような同一の文字で構成されている場合です。`aaaa...`。 ここで、両方の拡張子は最初は似ているように見えますが、正しい文字を追加すると不一致が生じるよりも編集距離が一貫して小さくなるため、クエリを繰り返すと決定がすぐに安定します。 

次のような交互パターンの場合`ababab`、初期の決定は変動する可能性がありますが、部分的なアライメントが確立されると、間違った選択により最適なアライメントでの置換コストが即座に増加するため、後続の拡張では交互構造が維持されます。
