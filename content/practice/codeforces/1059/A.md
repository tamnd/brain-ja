 ## 解決策
 ## 問題の理解

 私たちには、一定の長さの勤務日と、レジ係が継続的に存在する必要がある一連のサービス間隔が与えられています。 これらのサービス間隔の間には、自由時間のギャップが生じます。 これらの無料インターバル中に、レジ係は繰り返し休憩を取ることができ、それぞれの休憩は正確に決められた分数続きますが、顧客サービス期間を欠席することは許されません。 

このタスクは、休憩がサービス間隔と重なることができず、完全にアイドル時間内に収まる必要があると仮定して、顧客間の利用可能なすべての空き時間に同じ長さの完全な休憩を何回配置できるかを計算することです。 

構造的な観点から見ると、その日は時刻 0 から時刻 L までの線分です。一部のサブセグメントは顧客サービスの間隔によってブロックされており、それ以外はすべて無料です。 問題は、すべての空きセグメントの和集合に長さ a の互いに素なセグメントがいくつ収まるかを数えることに帰着します。 

制約は十分に大きいため、どのソリューションも顧客の数に対して直線的な時間内で実行する必要があります。 最大 100,000 の間隔と最大 1e9 の L を使用すると、分ごとにシミュレーションを試みることは直ちに不可能になります。 細かい解像度ですべてのギャップを反復しても、各間隔が 1 回処理される場合にのみ許容されます。 

顧客がまったくいない場合、微妙なエッジケースが発生します。 その後、丸 1 日が自由になり、単純に L を a で割った値を計算する必要があります。 もう 1 つの特殊なケースは、サービス間隔が隙間なく連続している場合に発生します。この場合、サービス間隔の間に休憩を挿入することはできません。 3 番目の重要なケースは、ギャップが存在するが a より小さいため、ギャップがゼロのブレークに寄与する場合です。 

単純な間違いは、各ギャップを独立して扱うのに、最初の顧客の前の最初のギャップや最後の顧客の後の最後のギャップを含めることを忘れることです。 もう 1 つのよくあるエラーは、現在の時間境界を慎重に更新せずに貪欲な配置を試行することです。これにより、使用可能なスペースが二重にカウントされたりスキップされたりすることになります。 

## アプローチ

 ブルートフォース解釈では、タイムラインを明示的に構築し、すべてのビジーな間隔をマークし、分ごとにスキャンして空きストレッチを数え、貪欲に休憩を配置します。 これは概念的には単純です。0 から L までの時間をシミュレートし、サービス間隔をスキップし、空き時間があるときはいつでもサイズ a の塊で消費します。 

文字通りプロセスをモデル化しているので、正しさは明らかです。 失敗のポイントは複雑さです。 L は最大 10^9 であるため、毎分反復することは不可能であり、テスト ケースごとに 10^9 のオーダーの操作が必要ですが、これは制限をはるかに超えています。 

重要な点は、空きセグメントの内部を調べる必要がまったくないということです。 各空きセグメントは独立してフロア(長さ / a) ブレークに寄与します。 サービス間隔はすでにソートされており、重複しないため、自由時間は自然に独立したギャップに分割されます。 この構造を認識すると、問題は、最後のサービス間隔の終わりへのポインタを維持しながら、間隔にわたる単一の線形スキャンになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(L) | お(1) | 遅すぎる |
 | 間隔ギャップのカウント | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 変数を初期化する`current`0 まで、自由に考慮できる最も早い時間を表します。 
2.初期化`answer`0 にすると、完全なブレークの数が累積されます。 
3. 顧客間隔ごと`(t, l)`、この顧客がセグメントとして開始するまでの空き時間を計算します。`[current, t)`。 これは、次の強制占領までに使用できる唯一の時間枠です。 
4. この空きセグメントの長さを次のように計算します。`t - current`。 追加`floor((t - current) / a)`各休憩はこの間隔内に完全に収まる必要があるためです。 
5.アップデート`current`に`t + l`なぜなら、この顧客にサービスを提供した後、レジ係はサービスが終了した後にのみ再び無料になるからです。 
6. すべての顧客を処理した後、最後の無料セグメントを処理します。`current`に`L`同様に、追加します`(L - current) // a`答えに。 

重要な考え方は、ブレークの配置を明示的にシミュレートする必要がないということです。 サイズの完全なセグメントがいくつあるかだけを数えます。`a`それぞれの最大空き間隔に収まります。 

### なぜ効果があるのか

 このアルゴリズムは、タイムラインをブロックされたセグメントと空きセグメントに交互に暗黙的に分割します。 サービス間隔が重複しないことが保証されているため、すべての空きセグメントは最大かつ独立しています。 有効なブレークはすべて、これらのセグメントの 1 つの内側に完全に存在する必要があり、サービス間隔をまたぐブレークは存在できません。 したがって、最適な解決策は、単にすべての空きセグメントにわたって、その中に長さ a のブロックがいくつ収まるかの合計になります。 セグメントにわたる貪欲な蓄積により、このパーティションが正確に保存されるため、ブレークが二重にカウントされたり見逃されたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, L, a = map(int, input().split())
    
    current = 0
    ans = 0
    
    for _ in range(n):
        t, l = map(int, input().split())
        
        if t > current:
            ans += (t - current) // a
        
        current = max(current, t + l)
    
    if current < L:
        ans += (L - current) // a
    
    print(ans)

if __name__ == "__main__":
    solve()
```ソリューションは単一のポインターを保持します`current`最後に占有された間隔の終わりを追跡します。 新しい顧客に出会うたびに、現在の空き時間と次のサービス開始までのギャップを即座に評価します。 これにより、間隔を保存したり、タイムラインを構築したりする必要がなくなります。 

の使用`max(current, t + l)`は、厳密な非重複に関する推論が緩和された場合でも正しさを保証する安全策ですが、この問題では主にクリーンな前進を維持します。 最後のセグメントは、その日の終わりを見逃さないように個別に処理されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    n, L, a = map(int, input().split())
    current = 0
    ans = 0
    
    for _ in range(n):
        t, l = map(int, input().split())
        if t > current:
            ans += (t - current) // a
        current = max(current, t + l)
    
    if current < L:
        ans += (L - current) // a
    
    return str(ans)

# provided samples
assert run("2 11 3\n0 1\n1 1\n") == "3"

# no customers
assert run("0 10 2\n") == "5", "entire day free"

# tightly packed customers
assert run("3 10 2\n0 2\n2 2\n4 2\n") == "2", "only tail space"

# large gap
assert run("1 20 3\n5 5\n") == "5", "two large segments"

# small gaps
assert run("2 10 3\n0 4\n5 4\n") == "0", "no space for breaks"

# boundary exact fit
assert run("1 6 3\n2 2\n") == "2", "exact fit segments"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 客がいない | 5 | 全日無料取り扱い |
 | ぎっしり詰まった | 2 | 間隔を正しくマージする |
 | 大きなギャップ | 5 | 複数のセグメントのカウント |
 | 小さな隙間 | 0 | フロア分割の正確性 |
 | ぴったりフィット | 2 | 境界演算精度 |

 ## 特殊なケース

 お客さんがいないときは、`current`最後のセグメントが処理されるまで 0 のままです。 アルゴリズムは直接計算します`(L - 0) // a`これにより、1 日全体の完全な休憩の数が正確に得られます。 

サービス間隔が重なる場合（次のような場合）`(0,2)`そして`(2,4)`、アップデート`current = max(current, t + l)`それらの間に人為的なギャップが生じないようにします。 2 番目の顧客の前に計算された無料セグメントはゼロであるため、ブレークが誤って追加されることはありません。 

フリーセグメントが以下の場合`a`、整数除算は当然ゼロに寄与するため、部分的なブレークがカウントされなくなります。
