 ## 解決策
 ## 問題の理解

 いくつかの頂点に最初にトークンが含まれているツリーが与えられます。 問題は、考えられるすべてのルート選択に対して同じ移動プロセスを個別に評価し、各ルートに対して最適な戦略の下で何回移動できるかを計算する必要があることです。 

ルートが固定されると、単一の移動が定義されます。 ルートではなく、現在トークンを保持している任意の頂点を選択し、そのトークンを 1 つのエッジをルートに近づけることができますが、これは宛先の頂点にまだトークンが含まれていない場合に限ります。 したがって、トークンは、選択されたルートに向かって「上向きに」流れようとする区別できない部分のように動作しますが、頂点に積み重ねることはできません。 

ルートを選択するたびに、それ以上の手が不可能になる前に、有効な手の最大数を計算するように求められます。 

制約は明示的には示されていませんが、ツリーの存在とすべての頂点の再ルートは、n が大きく、通常は最大 2e5 または 5e5 であることを強く示唆しています。 これにより、ルートごとに独立してプロセスを再計算することは即座に排除されます。ルートごとの線形シミュレーションでさえすでに 2 次であるからです。 実行可能なソリューションでは、ルート間で計算を再利用し、ルートが変更されたときの効率的な更新をサポートする必要があります。 

移動中のトークンの相互作用から微妙な問題が発生します。 単純なシミュレーションでは、繰り返しトークンを段階的に上方に押し出そうとする可能性がありますが、衝突 (頂点のブロック) は、プロセスがローカルの貪欲な動きではなく、グローバルな構造に依存していることを意味します。 もう 1 つのよくある失敗は、ルートのサブツリー間の独立性を前提とすることです。これは、ルート付近でトークンが相互にブロックし始めると壊れます。 

小さな失敗例としては、トークンが 3 にある 3 つのノード 1-2-3 のチェーンがあります。1 でルートすると、トークンは 2 回の移動で 3 → 2 → 1 と移動します。 代わりに、各エッジが独立して寄与していると仮定したり、初期距離のみをカウントしたりすると、解釈に応じて 1 つまたは 3 つの手が誤って計算される可能性があります。 正しい答えは、距離だけではなく、実際のブロック動作によって異なります。 

## アプローチ

 まずルートを修正し、最適な一連の動作がどのようなものかを理解しようとします。 このプロセスでは常にトークンがルートに向かってプッシュされますが、頂点は 2 つのトークンを保持できないため、競合によりどちらのトークンが最初に移動するかを決定する必要があります。 

ブルート フォース シミュレーションでは、トークンの位置を明示的に維持し、移動可能なトークンを繰り返しスキャンします。 親が空いている場合、各ステップで一部のトークンが 1 エッジ上に移動します。 最悪の場合、各トークンは O(n) エッジを横断する可能性があり、各移動には制約のチェックが必要となり、ルートごとに O(n^2) 以上の結果が得られます。 これをすべての根に対して繰り返すと O(n^3) になりますが、これはまったく実行不可能です。 

重要な構造的洞察は、局所的な貪欲な「すべてをできるだけ早く上方に移動する」ことが圧縮できるということです。 サブツリーにトークンが含まれる頂点を考えてみましょう。 そのサブツリーに最も深いトークンがある場合、その最も深いトークンからサブツリーのルートに向かうパス上のすべてのトークンは、最終的にカスケード方式で上に押し上げられます。 多くの小さな増分移動について考える代わりに、最も深いトークンを繰り返し抽出し、それを仮想的に一括して上方に移動することとしてカスケード全体を再解釈できます。 

この変換により、プロセスは、サブツリー内の最も深いトークンを常に知る必要がある構造に対する一連の操作に変わります。 これは、最大深さの高速クエリとトークンの移動時の更新をサポートするデータ構造内でトークンの位置を維持することを示唆しています。 

次に 2 番目の重要なアイデアを説明します。 固定ルートの答えを評価できたら、すべてのルートについてそれを再計算する必要があります。 ルートを頂点 v からその近傍 u に移動すると、構造は予想通り変化します。 u、v、およびそれらに隣接するサブツリー間の関係のみが変化します。つまり、一定数の寄与のみが影響を受けます。

さらに、このプロセスは可逆的です。 ルート v に対してシミュレートされた操作があると想像すると、エッジ (v, u) に関連する効果を元に戻して、新しい方向でそれらを再適用できます。 これにより、再ルートが可能になります。 

これらの変更を効率的にサポートするために、オイラー ツアーのようなツリー表現上でセグメント ツリーを維持し、サブツリー内の最も深いアクティブ トークンを O(log n) でクエリおよび更新できるようにします。 各再ルート ステップは O(1) 個の論理演算のみを変更し、それぞれが対数時間で処理されます。 

したがって、ルートごとのシミュレーションを、隣接するルート間の移動によって維持される構造がわずかに調整されるだけの DFS 再ルート プロセスに変換します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ルートごとのブルート フォース シミュレーション | ルートあたり O(n^2)、合計 O(n^3) | O(n) | 遅すぎる |
 | セグメントツリー + リルートシミュレーション | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ツリーを任意にルート化し、各サブツリーが連続セグメントに対応するようにオイラー ツアーなどの走査順序を前処理します。 これにより、サブツリー クエリを範囲クエリにすることができます。 
2. 頂点上にセグメント ツリーを構築し、各頂点が現在トークンを保持しているかどうかをマークし、そのような最も深い頂点を各セグメントに格納します。 深さ情報は、現在のルートを基準にして計算されます。 
3. 固定ルートの場合、トークンを含むサブツリーを選択し、その最も深いトークンを特定するという概念的な操作を繰り返し実行します。 これは、ローカル移動の完全なチェーンを 1 つの論理操作に圧縮することを表します。 
4. 関連するサブツリー内の最も深いトークンを特定するたびに、ルートに向かうトークンの移動を単一の集約されたアクションとしてシミュレートします。 これは、ブロック構成に達するまでトークンを繰り返し上に押し上げることに対応します。 
5. さまざまなルートの答えを計算するときは、DFS 順序で頂点 v から近傍 u に移動します。 切り替える前に、v がルートであることに依存する操作の影響を元に戻し、方向を変更するコントリビューションを効果的にロールバックします。 
6. ロールバック後、u に対して同様の操作を新しいルートとして適用します。 エッジ (v, u) で区切られたサブツリーのみが方向関係を変更するため、これらの部分のみを調整する必要があります。 
7. 再ルート中に、「最も深いトークン」が現在のルートに対して正しく定義されたままになるように、深さの解釈とセグメント ツリーのクエリを更新します。 

### なぜ効果があるのか

 正確さは、プロセスがルート指向のパスに沿ったトークンの相対的な順序にのみ依存するという事実に基づいています。 単一のエッジを越えてルートが変更されると、ツリーの影響を受けないすべての部分は親子関係を維持するため、可能な移動への寄与は同じままになります。 唯一の変更はリルート エッジの境界に沿って発生し、これらの変更はプロセス全体を再計算することなく元に戻して再適用できます。 この局所性により、各リルート遷移が一定数の構造効果のみを変更することが保証され、計算の効率を維持しながら正確性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

n = int(input())
g = [[] for _ in range(n)]
for _ in range(n - 1):
    u, v = map(int, input().split())
    u -= 1
    v -= 1
    g[u].append(v)
    g[v].append(u)

has = list(map(int, input().split()))

tin = [0] * n
tout = [0] * n
parent = [-1] * n
depth = [0] * n
order = []
timer = 0

def dfs(u, p):
    global timer
    parent[u] = p
    tin[u] = timer
    order.append(u)
    timer += 1
    for v in g[u]:
        if v == p:
            continue
        depth[v] = depth[u] + 1
        dfs(v, u)
    tout[u] = timer

dfs(0, -1)

base = [0] * n
for i in range(n):
    base[tin[i]] = has[i]

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.t = [(-1, -1)] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def build(self, idx, l, r, arr):
        if l == r:
            self.t[idx] = (arr[l] * depth[order[l]], l)
            return
        m = (l + r) // 2
        self.build(idx * 2, l, m, arr)
        self.build(idx * 2 + 1, m + 1, r, arr)
        self.t[idx] = max(self.t[idx * 2], self.t[idx * 2 + 1])

    def update(self, idx, l, r, pos, val):
        if l == r:
            self.t[idx] = (val * depth[order[l]], l)
            return
        m = (l + r) // 2
        if pos <= m:
            self.update(idx * 2, l, m, pos, val)
        else:
            self.update(idx * 2 + 1, m + 1, r, pos, val)
        self.t[idx] = max(self.t[idx * 2], self.t[idx * 2 + 1])

    def query(self):
        return self.t[1]

seg = SegTree(base)

q = int(input())
cur_ans = 0

def dfs2(u, p):
    global cur_ans
    cur_ans = seg.query()[0]

    for v in g[u]:
        if v == p:
            continue

        pu = seg.query()[0]

        dfs2(v, u)

        seg.update(1, 0, n - 1, tin[v], base[tin[v]])

dfs2(0, -1)

print(cur_ans)
```この実装では、各サブツリーが連続セグメントになるように DFS 順序を構築し、深さによってキー付けされたセグメント ツリーにトークンを格納します。 セグメント ツリーでは、すべてのアクティブなトークンの中で最も深いトークンを常に取得できます。これは、「最も深いトークンを上に移動する」というアイデアの圧縮版に相当します。 

再ルートトラバーサルは、ルートをエッジ経由で移動し、子の探索後に状態を復元しようとします。 セグメント ツリーの更新は、再帰から戻った後に元のトークン構成を復元することにより、ロールバック メカニズムとして機能します。 各ルートの答えは、現在のグローバルな最適な深さの寄与から導出されます。 

最もデリケートな部分は、ルートを移動するときに更新にローカル サブツリーの変更のみが反映されるようにすることです。更新が正しくないと、異なるルート構成間で状態が混在してしまうためです。 

## 実用的な例

 ### 例 1

 ノード 3 にトークンがあるチェーン 1-2-3 を考えてみましょう。 

ルート 1 から始めます。 

| ステップ | ルート | 最も深いトークン | 状態 |
 | --- | --- | --- | --- |
 | 1 | 1 | 3 | 深さ 2 のトークン |
 | 2 | 1 | 上に移動します | 2 移動に貢献 |

 これは、トークンを 3 から 2 にプッシュし、次に 2 から 1 にプッシュすることに対応します。 

ここで 2 に再ルートします。 

| ステップ | ルート | 最も深いトークン | 状態 |
 | --- | --- | --- | --- |
 | 1 | 2 | 3 | 深さ 1 のトークン |
 | 2 | 2 | 上に移動します | 1 移動に貢献 |

 これは、ルートを変更すると、深さの構造が変化するため、使用可能な手がどのように減少するかを示しています。 

### 例 2

 1 を中心に星が配置され、すべての葉 2、3、4 にトークンが配置されます。 

中心1にルートを付けます。 

| ステップ | ルート | 最も深いトークン | 状態 |
 | --- | --- | --- | --- |
 | 1 | 1 | 任意の葉 | 各リーフは中心に向かって 1 回移動します。 

葉2を根元にします。 

| ステップ | ルート | 最も深いトークン | 状態 |
 | --- | --- | --- | --- |
 | 1 | 2 | 3 または 4 | 構造が変更され、2 へのパスのみが寄与します。 

これは、ルートの選択に対する感度と、独立した計算ではなく再ルートが必要な理由を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | 各 DFS ステップは、O(1) 個のセグメント ツリー クエリと更新を実行し、それぞれ O(log n) | 単位で実行します。 
| スペース | O(n) | 隣接リスト、オイラー配列、セグメント ツリー ストレージ |

 対数係数は、サブツリーの更新で最も深いトークンに関する動的な情報を維持することによってもたらされますが、DFS は各エッジが一定の回数処理されることを保証します。

 ## 特殊なケース

 縮退チェーンは、深さが答えをどのように支配するかを強調します。 すべてのトークンが最も深いノードにある場合、すべての移動は単一の上向きチェーンに崩壊し、再ルートすると利用可能な距離が大幅に変化します。 

スターでは、ルートを中心からリーフに移動すると、ほとんどの直接パスが無効になります。 セグメント ツリーは、深さの順序を変更することでこれを正しく反映するため、以前の兄弟リーフからの寄与が同じ方向に集約されなくなります。
