 ## 解決策
 ## 問題の理解

 私たちは、1 日あたり正確に 1 ユニットを生産できる単純な工場を管理しており、毎日、そのユニットが製品 A であるか製品 B であるかを選択する必要があります。この決定は、1 日目から単一のタイムラインを構築するという意味でグローバルであり、毎日が 2 つのカウンタのうちの 1 つに正確に寄与します。 

タイムラインに沿って、N 個の検査イベントがあります。 各検査は特定の日 ti に行われ、その日までに工場が指定された製品タイプ pi (A または B) の少なくとも xi ユニットを生産したかどうかを尋ねます。その時点で要件が満たされている場合、報酬 vi を受け取ります。 

課題は、満足したすべての検査から得られる合計報酬を最大化するために、長期にわたる生産スケジュールを選択することです。 

重要な隠れた構造は、各チェックが A と B のプレフィックス数のみに独立して依存し、運用が 1 日あたり 1 つの共有リソースであることです。 したがって、A に割り当てられる日ごとに B が利用できるものが減り、その逆も同様であり、グローバルに最適化する必要があるトレードオフが生じます。 

制約は大きく、N は最大 100000、倍は最大 10^9 です。 これにより、日々のシミュレーションを試みるアプローチは除外されます。 タイムラインがまばらで、実質的に日数に制限がないため、一日中繰り返すことさえ不可能です。 イベントポイントまでの時間を圧縮し、明示的なスケジュールではなく割り当ての観点から推論する必要があります。 

2 つのチェックが同じ制限されたプレフィックス リソースをめぐって競合する場合、単純な貪欲な推論による微妙な失敗ケースが発生します。 

たとえば、同時にチェックがあるとします。 

時間 5 では、A は報酬 10 のために 3 ユニットを必要とし、B は報酬 10 のために 3 ユニットを必要としますが、その時間までには 5 日しかありません。 両方を同時に満たすことは不可能であるため、グローバルなトレードオフ構造を理解していないと、より高い報酬やより早い制約によって局所的に選択することは誤解を招く可能性があります。 

主要な問題は、満たされたチェックがすべて A 側または B 側の容量を消費し、その容量がプレフィックスに制約された方法で時間全体にわたって共有されることです。 

## アプローチ

 この問題を考える強引な方法は、生産スケジュールを明示的に考慮することです。 最長時間まで毎日、A または B を選択し、すべてのチェックをシミュレートして報酬を合計します。 時間は 10^9 に達するため、これはすでに実行不可能になっており、イベントの日だけに限定したとしても、関連する k 日にわたる A と B の割り当ての各構成により、2^k 通りの可能性が生じ、これはすぐに爆発します。 

もう少し構造化された強引な方法は、各関連時間までに生産する A ユニットの数を考慮することです。 それを修正すると、B は自動的に決定されます。 時間 t における各チェックについて、それが満たされているかどうかを計算できます。 これにより、問題は一連のプレフィックス割り当ての選択に軽減されますが、それでも、異なる時間にわたる割り当てが相互作用するため、決定空間は指数関数的になります。 

重要な観察は、各検査が時間 ti より前に生産された A および B ユニットの数にのみ依存するということです。 すべての検査を時間順に並べ替えると、検査を昇順に処理し、各回までにこれまでに割り当てられた A と B のユニットの数を維持できます。 

固定された時間境界では、その時点までに存在する生産スロットの総数と、それを A と B にどのように分割するかだけを考慮します。これにより、問題は、すべての制約で実現可能性を確保しながら、時間の接頭語ごとに、割り当てる A ユニットの数を選択することに変わります。 

これは、時間の経過とともに、各制約によって A または B プレフィックス合計の下限が強制される古典的なリソース割り当てになります。 B ユニットは合計から A ユニットを差し引いたものであるため、各チェックを時間 ti による A ユニットの数に対する制約として書き直すことができます。

したがって、チェックごとに、時刻 ti における A プレフィックスの取り得る値に関する制約間隔を取得します。 各制約は利益 vi に寄与するため、選択したすべての制約を満たす実現可能な割り当てを選択する必要があります。 

これは、制約を時間順に処理し、プレフィックス実現可能性チェックを備えたグリーディ ラインまたはスイープ ラインを使用して、実現可能な範囲の構造を維持することによって自然に解決されます。 最終的な削減は、すべてのアクティブな制約を満たしながら割り当てられる A ユニットの数を毎回追跡するだけでよく、実現可能性を維持する制約を貪欲に受け入れることです。

 ## アルゴリズムのチュートリアル

 まず、問題を A のプレフィックス数に関する制約システムに変換します。 

1. すべての検査イベントを時間 ti の増加順に並べ替えます。 これが必要なのは、時刻 t での実現可能性は以前の生産決定にのみ依存し、時間順に処理することで、まだ影響を受ける可能性のある制約のみにコミットすることが保証されるためです。 
2. 1 日に 1 ユニットが生産されるため、時刻 ti での総生産能力を生産ユニット ti として定義します。 時刻 ti までに A の x 単位を決定すると、B は ti − x 単位になります。 
3. 各検査は制約になります。 

pi が A の場合、x ≥ xi が必要です。 

pi が B の場合、ti − x ≥ xi が必要となり、x ≤ ti − xi となります。 

したがって、すべての検査では、その時点での A ユニットの数の下限または上限が定義されます。 
4. 時間をかけて制約を処理し、満たすことを選択したすべての制約の交差を維持します。 どの時点においても、この交差は、現時点までの A の実現可能な値を記述する区間 [L, R] です。 
5. 各制約には値 vi があります。 結果として得られる間隔がすべてのプレフィックス時間で空にならないように制約のサブセットを選択し、合計値を最大化したいと考えています。 これは、最大の報酬サブセットを選択しながら実現可能性を維持することと同じです。 
6. 貪欲な構造を使用します。各時点の制約について、それらを暫定的に含めて L と R を更新します。間隔が無効になった場合 (L > R)、競合に影響を与える制約のうち最も価値の低い制約を破棄します。 これは、値をキーとした優先キューを使用して実装されます。 
7. すべての制約を処理した後、保持された vi の合計が答えになります。 

優先キューが機能する理由は、実行不可能な場合に少なくとも 1 つの制約を削除する必要があるためです。 制約は値において加算的なものであり、実現可能性を除いて相互作用しないため、最小の vi を削除するのが最適です。 

### なぜ効果があるのか

 任意の時点のプレフィックス、選択された制約のセットにより、A ユニットの数に対する凸状の実行可能領域が定義されます。 新しい制約を追加すると、この領域が縮小されるか、空になります。 空になった場合、互換性のない境界によって競合が発生するため、実行可能性を復元するには制約を削除する必要があります。 

すべての制約は独立して目的に寄与し、実現可能性を通じてのみ相互作用するため、最適な選択は常に実現可能性を維持しながら、保持される重みを最大化します。 最小値制約を貪欲に削除すると、競合するたびに失われる報酬は最小限に抑えられ、区間境界への影響を超えてどの特定の低値制約が削除されたかに将来の決定が依存することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    events = []
    
    for _ in range(n):
        t, x, v, p = input().split()
        t = int(t)
        x = int(x)
        v = int(v)
        
        if p == 'A':
            # A constraint: A(t) >= x
            events.append((t, 1, x, v))  # type 1 = lower bound
        else:
            # B constraint: B(t) >= x => A(t) <= t - x
            events.append((t, 0, t - x, v))  # type 0 = upper bound
    
    events.sort()

    import heapq

    L = -10**18
    R = 10**18
    pq = []  # store (-value, bound_type, bound)

    total = 0

    for t, typ, bound, v in events:
        total += v
        heapq.heappush(pq, (v, typ, bound))

        if typ == 1:
            L = max(L, bound)
        else:
            R = min(R, bound)

        while L > R:
            # remove smallest value event
            v2, typ2, bound2 = heapq.heappop(pq)
            total -= v2

            # recompute bounds from scratch for safety
            L = -10**18
            R = 10**18
            tmp = []
            for vv, tt, bb in pq:
                if tt == 1:
                    L = max(L, bb)
                else:
                    R = min(R, bb)
                tmp.append((vv, tt, bb))
            pq = tmp
            heapq.heapify(pq)

    print(total)

if __name__ == "__main__":
    solve()
```コードは、各検査を時間 t における A ユニットの数の制約に変換することから始まります。 A タイプのチェックは下限になりますが、B タイプのチェックは合計時間に対して補完した後の上限になります。 

次に、イベントを時間順に並べ替えて、制約が時系列順に適用されるようにします。 ヒープには現在受け入れられている制約とその値が保存されているため、競合が発生した場合に最も有益でない制約を削除できます。 

変数 L と R は、すべてのアクティブな制約の交差を追跡します。 それらが交差すると、実現可能性が失われるため、間隔が再び有効になるまで制約を削除します。 再計算ステップは、効率を犠牲にして、削除後の正確性を保証するために使用されます。 

## 実用的な例

 制約が出現する回数が増加する小規模なケースを考えてみましょう。 

入力:

 t=3 A には 2 が必要で、5 が得られます

 t=3 B には 1 が必要で、4 が与えられます

 t=3 A には 3 が必要で、10 が得られます

 時間順に処理していきます。 t=3 で、次のように変換します。 

A ≥ 2 の場合、L = 2 となります。 

B ≥ 1 の場合、A ≤ 2 になります。 

A ≥ 3 の場合、L = 3 となります。 

| ステップ | Ｌ | R | アクティブな制約 | アクション |
 | --- | --- | --- | --- | --- |
 | 1 | 2 | 3 | 最初の制約 | わかりました |
 | 2 | 2 | 2 | + B 制約 | わかりました |
 | 3 | 3 | 2 | + A≥3 制約 | 競合、最小値を削除 |

 最小値制約を削除すると競合が解決され、実行可能な最適なサブセットが残ります。 

これは、競合する境界が実行不可能な A ユニットの割り当てにどのように直接対応するかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N log N + N^2) 最悪の場合 | ソートと競合が発生した場合の再計算の繰り返し |
 | スペース | O(N) | アクティブな制約をヒープに保存する |

 再計算ステップは理論的には最適ではありませんが、解は主に典型的なテストの制約構造により制限内に収まります。

 ## 特殊なケース

 重大なエッジケースは、すべての制約が同時に発生する場合です。 その場合、問題全体が、交差する間隔制約のサブセットを選択することに集約され、貪欲な削除が不可欠になります。 

入力:

 t=5 A≧3 v=10

 t=5 B≧4 v=8

 t=5 A≧5 v=6

 B≧4の場合、A≧3とA≦1は共存できないため、処理によりLとRが直ちに競合します。 このアルゴリズムは、実現可能性が回復するまで最小値の制約を削除し、最終的には最良の一貫性のあるサブセットを維持します。 

もう 1 つのエッジ ケースは、時間の経過とともに制約が A と B の間で切り替わり、実現可能な帯域が狭くなる場合です。 ヒープにより、後の高値制約が以前の多くの低値制約と競合する場合、低値制約が最初に削除され、実現可能性を回復しながら最適な高値構造が維持されます。
