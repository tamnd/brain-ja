 ## 解決策
 ## 問題の理解

 N 個のノードを持つルート ツリーが与えられます。各ノードには 1 つの英小文字が格納されます。 ルートはノード 1 に固定されています。クエリごとに、ターゲット ノード u とパターン文字列 t が与えられます。 そのパスに沿った文字のシーケンスが t と正確に一致するように、u の祖先のルート端から始まる別個の下向きパスがいくつあるかを数える必要があります。 

t が有効であるかどうかは、ルートから u へのパス上の開始ノード p1 を選択し、厳密に |t| だけ親子エッジを通って下方向に移動することによって決定されます。 − 1 ステップ、途中で t の文字を照合し、最終ノード p|t| を確保します。 はまだ root から u へのパス上にあります。 出現箇所の違いは、一致した文字列の違いだけでなく、ツリー パス内の開始位置の選択の違いに対応します。 

重要な構造オブジェクトはルートから u へのパスであり、すべてのクエリは、このパス上のどこかから始まる連続したラベル付きセグメントとして現れる t の下向きの出現回数をカウントすることに帰着します。 

制約は大きく、N と Q は最大 3 × 10^5 であり、すべてのクエリ文字列の合計長も 3 × 10^5 によって制限されます。 これにより、ツリーをたどったりパスを明示的にスキャンしたりして各クエリを処理するソリューションは即座に除外されます。 N またはサブツリー サイズでさえ、クエリごとの線形トラバーサルは非常に遅すぎます。 

素朴なアプローチでは、クエリごとに u のすべての祖先を走査し、考えられる各開始位置から文字列を下向きに照合しようとします。 チェーン形状のツリーでは、これはクエリごとに O(N × |t|) に縮退し、最悪の場合は O(NQ) となり、完全に実行不可能になります。 

ルートからノードへの文字列を明示的に事前計算しようとすると、より微妙な障害モードが表示されます。 すべてのパス文字列を保存したとしても、部分文字列を単純にチェックすると二次関数の動作やメモリの爆発が発生します。 

## アプローチ

 ブルート フォースのアイデアは単純です。クエリ (u, t) ごとに、ルートから u までのパス上の各ノード x から歩き、下に向かって t を 1 文字ずつ一致させようとします。 これは、オカレンスの定義に直接従うため、正しいです。 ただし、最悪の場合のチェーン ツリーでは、各パスの長さは N であり、各クエリ文字列も長さ N になる可能性があるため、クエリごとに O(N^2) になります。 最大 3 × 10^5 クエリでは、これは爆発的に増加します。 

重要な観察は、マッチング中に分岐構造を実際に調査する必要がないということです。 すべての候補一致は単一のルートから u へのパスに限定され、すべての一致はそのパスに沿って純粋に線形です。 これは、問題が基本的に、ツリー パスによって定義された動的文字列のパターン カウントに関するものであることを意味します。 

これは、視点を逆転させることを強く示唆しています。各クエリのパスをスキャンする代わりに、プレフィックス情報を使用して「ルートからノードへのパスに沿って文字列が何回出現するか」を回答できるようにツリーを前処理します。 このための標準ツールは、ルートからノードへの文字列に対するトライのような構造と、周波数集約、または同等のプレフィックス オートマトン状態の DSU-on-tree スタイル集約を組み合わせたものです。 

最もクリーンな解決策は、ルートからノードまでのすべての文字列のトライを構築することです。 ツリー内の各ノードは、そのパス文字列を表す 1 つのトライ ノードに正確に対応します。 次に、すべてのクエリは、u の祖先チェーン上のトライ ノードの数が、このトライ構造の接尾辞関係としてのパターン t に一致するかをカウントすることに帰着します。 失敗リンクを使用してトライを強化するか、深さをキーとしたサブツリーの頻度カウントを保存することにより、文字をスキャンする代わりに状態をジャンプすることでクエリに答えることができます。

より直接的で実装可能なアプローチは、各ノードをルート パス上のプレフィックス オートマトンの状態として扱い、バイナリ リフティングまたはヘビーライト集約と組み合わせたハッシュまたはローリング プレフィックス表現を使用することです。 ただし、ここでの最も標準的な競技プログラミング ソリューションは、ルートからノードへの文字列の永続的なトライを構築し、各トライ ノードでそれが表示される深さのリストを維持し、有効な深さの範囲内でバイナリ検索によって各クエリに答えることです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NQ · | t | ) |
 | 永続的なトライ + 深さの集約 | O((N + Q) log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ノード 1 でツリーをルートし、DFS を実行して各ノードの親と深さを計算します。これは、すべてのクエリがルートから u へのパスに制限され、深さが有効な一致範囲を定義するためです。 
2. 各ノードのバージョンがルートから現在のノードへの文字列に対応するツリー上に永続トライを構築します。 親から子に移動するとき、子のキャラクターを挿入して新しいトライ バージョンを作成し、変更されていないトライ ノードをすべて再利用します。 これにより、各ツリー ノードがそのプレフィックス文字列を表す対応するトライ状態を持つことが保証されます。 
3. すべてのトライ ノードについて、そのトライ状態で終了するツリー ノードの深さのリストを維持します。 各ツリー ノードは 1 つのパス文字列に正確に対応するため、このリストは DFS トラバーサル中に各ノードを訪問してそのトライ バージョンにアタッチするときに自然に構築されます。 
4. 構築後、トライノードごとに深さリストをソートします。 これにより、特定の深さ間隔内に発生する回数を効率的にカウントできます。 
5. クエリ (u, t) の場合、ノード u の祖先のトライ状態から開始してトライ内を歩く t をシミュレートします。 ツリーをたどる代わりに、文字を整列させながら親ポインターを使用して u の対応するトライ状態からトライ エッジを逆方向にたどることによって t との一致を試みます。 どこかの時点で失敗すると、答えはゼロになります。 
6. 一致したパターンの終わりに対応するトライ ノードに到達したら、有効なプレフィックス範囲内に存在する出現数を計算します。 有効な範囲は、深さが少なくとも |t| である root-to-u パス上のすべてのノードです。 − 1、最大深さ[u]。 一致したトライ ノードの深さリストを二分探索して、この間隔内にエンドポイントがいくつあるかを数えます。 
7. このカウントをクエリごとに出力します。 

### なぜ効果があるのか

 ルートからノードへの各パスは、正確に 1 つのトライ パスに対応し、パターンの各出現は、深さがそのパス内のパターンの終了位置と一致するトライ ノードに対応します。 永続的なトライでは、同一のプレフィックスが共有されることが保証されるため、各パターンの一致は一意の状態に対応します。 深さのフィルタリングにより、root から u へのパス内に完全に含まれる出現のみがカウントされるようになります。 すべての有効な出現はトライ構造内で 1 回だけ表され、深さの制約によってカウントされるため、過大なカウントや過少カウントは発生しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import defaultdict

sys.setrecursionlimit(10**7)

class TrieNode:
    __slots__ = ("next", "depths")
    def __init__(self):
        self.next = {}
        self.depths = []

def insert(prev, ch, depth):
    node = TrieNode()
    node.next = dict(prev.next)
    for k, v in prev.next.items():
        node.next[k] = v
    if ch not in node.next:
        node.next[ch] = TrieNode()
    # copy pointer to child chain root is handled outside
    node.depths = []
    return node

def dfs(u, p):
    for v in g[u]:
        if v == p:
            continue
        parent[v] = u
        depth[v] = depth[u] + 1
        dfs(v, u)

def build_trie(u, p):
    ch = s[u]
    if p == -1:
        trie_state[u] = TrieNode()
        trie_state[u].next[ch] = TrieNode()
        trie_state[u] = trie_state[u].next[ch]
    else:
        prev = trie_state[p]
        if ch in prev.next:
            trie_state[u] = prev.next[ch]
        else:
            prev.next[ch] = TrieNode()
            trie_state[u] = prev.next[ch]
    trie_state[u].depths.append(depth[u])
    for v in g[u]:
        if v != p:
            build_trie(v, u)

def collect(node):
    for nxt in node.next.values():
        collect(nxt)
        node.depths.extend(nxt.depths)
    node.depths.sort()

def count_range(arr, l, r):
    import bisect
    return bisect.bisect_right(arr, r) - bisect.bisect_left(arr, l)

n = int(input())
s_raw = input().strip()

s = [""] + list(s_raw)

g = [[] for _ in range(n + 1)]
for _ in range(n - 1):
    a, b = map(int, input().split())
    g[a].append(b)
    g[b].append(a)

parent = [0] * (n + 1)
depth = [0] * (n + 1)

dfs(1, -1)

trie_state = [None] * (n + 1)
build_trie(1, -1)

collect(trie_state[1])

q = int(input())
for _ in range(q):
    u, t = input().split()
    u = int(u)
    cur = trie_state[u]
    ok = True
    for c in t:
        if c not in cur.next:
            ok = False
            break
        cur = cur.next[c]
    if not ok:
        print(0)
        continue
    l = depth[u] - (len(t) - 1)
    r = depth[u]
    print(count_range(cur.depths, l, r))
```DFS は深さを計算するので、「パスに沿った位置」を数値間隔に変換できます。 トライ構造では、ルートからノードへの各文字列が共有構造にマップされるため、プレフィックスは再計算されずに再利用されます。 

の`collect`このステップは、子から祖先までのすべての終端出現を集約するため、すべてのトライ ノードが出現するすべての深さを知ることができるため、非常に重要です。 これらのリストを並べ替えると、クエリの二分検索が可能になります。 

各クエリは、トライ内のプレフィックス ウォークと、事前に計算された並べ替えリスト上の範囲カウントになります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N + Q log N) | DFS は線形時間で構造を構築し、各クエリはパターンを 1 回実行してバイナリ検索を実行します。

この制約により、およそ 3 × 10^5 の演算が可能になり、二分探索の対数係数は制限内に収まるようになります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、パターンの長さがクエリ対象のノードの深さを超える場合です。 その場合、計算された下限深度は負になり、負の深度にはノードが存在しないため、アルゴリズムは正しく何もカウントしません。 

もう 1 つのケースは、チェーンに沿って文字が繰り返される場合です。 たとえば、チェーン「aaaaa」では、最後のノードのクエリ「aaa」は、重複する複数の開始点をカウントする必要があります。 トライベースの深さの集計は、すべてのエンドポイントを正しくキャプチャし、すべての有効なセグメントをカウントします。 

共有プレフィックスが構造的に再利用されている場合でも、ルートからノードへの各パスが永続トライで独立して表現されるため、異なる分岐に同じラベルを持つ分岐ツリーも正しく処理されます。
