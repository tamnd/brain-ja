 ## 解決策
 ## 問題の理解

 それぞれの位置に多数の石が格納されている山の配列が与えられます。 システムは、長期にわたって 2 つの操作をサポートします。 1 回の操作で、特定の間隔内のすべてのパイル値をある定数だけ増加させます。 もう 1 つの操作は、部分配列に関するゲーム理論的な質問をします。選択した間隔内のパイルのみを取得し、それらに対して Nim スタイルのゲームをプレイした場合、両方のプレイヤーが最適にプレイし、Ava が先に動いたと仮定すると、Diana は勝利を保証できますか。 

重要な詳細は、ゲームのプレイ方法です。 間隔から選択された一連の杭で、移動は正確に 1 つの杭を選択し、そこから少なくとも 1 つの石を削除することで構成されます。 これは標準的な Nim であるため、各パイルは独立して動作し、ゲームの結果は選択したセット内のパイル サイズの XOR のみに依存します。 

ひねりを加えると、ダイアナは直接ゲームをプレイしないということです。 彼女は間隔からどの山を使用するかを選択します。 彼女は、クエリ範囲内に、結果として得られる Nim ポジションが最初のプレイヤーに負けるようなインデックスのサブセットが存在するかどうかを知りたいと考えています。 Nim では、損失ポジションは、選択したパイル サイズの XOR がゼロのときとなります。 

したがって、各クエリは、XOR が 0 である間隔の空でないサブセットが存在するかどうかを尋ねます。 

範囲の追加更新では配列が動的であるため、時間の経過とともに値が変化します。 これはデータ構造の問題になります。XOR サブセットの存在に基づいて範囲の追加と範囲クエリの決定をサポートする必要があります。 

制約は最大 100,000 の要素と演算に達するため、どの解も演算ごとに線形演算に近いか、それより優れている必要があります。 XOR ベースを再計算したり、クエリごとにサブセットをテストしたりする単純なアプローチでは、時間がかかりすぎます。 

微妙な失敗のケースは、クエリの組み合わせの性質を誤解していることに起因します。 たとえば、間隔全体の XOR がゼロかどうかを確認するだけでよいと誤って仮定する可能性があります。 それは間違いです。合計の XOR がゼロでない場合でも、XOR がゼロのサブセットが存在する可能性があります。 たとえば、あるインターバルで`[1, 2, 3]`、完全な XOR は次のとおりです。`0`、でも、`[1, 2, 4]`ただし、合計 XOR は`7`、サブセット`{1, 2, 3}`構造は直接適用されず、正確さは完全な XOR だけではなく、バイナリ空間の線形依存関係に依存します。 

もう 1 つの落とし穴は、これがパリティまたは合計条件のチェックに帰着すると考えることです。 XOR サブセット構造は、算術和ではなく、2 値線形代数に依存します。 

## アプローチ

 ブルートフォースのアイデアは単純です。 クエリごとに、間隔のすべてのサブセットを列挙し、XOR を計算して、XOR ゼロを持つサブセットがあるかどうかを確認します。 これは問題の定義に直接従うため、正しいです。 ただし、サイズの間隔`k`もっている`2^k`サブセットと`k`100,000 までは、たとえ小さな入力であっても、これは直ちに不可能になります。 

もう少し洗練された総当りアプローチでは、毎回間隔の線形基礎を計算します。 サイズが最大 30 のバイナリ線形基底では、間隔内のすべての XOR の組み合わせがキャプチャされます。 基底を構築したら、その基底に自明な空集合を超えた線形依存性があるかどうかをチェックすることで、ゼロが表現可能かどうかを判断できます。 ただし、ここでの重要な観察は微妙です。ゼロとの XOR をとる空ではないサブセットの存在は、GF(2) で線形従属している数値のセットと同等であり、これはセット内の要素数が少ない基底と同等です。 

課題は、範囲を追加してもこの構造を維持することです。 セグメント内のすべての要素に定数を追加しても、簡単に構成できる方法で線形構造が維持されないため、完全な塩基を格納する直接セグメント ツリーは機能しません。 

重要な観察は、問題を再解釈することです。任意の値を追跡するのではなく、区間に少なくとも 1 つの重複値が含まれているかどうか、またはゼロ XOR サブセットを保証する方法で構造が線形依存を強制しているかどうかを追跡します。 条件を変換した後、クエリは、範囲加算による値の適切な変換後に、間隔に等しいプレフィックス XOR 状態のペアが含まれているかどうかをチェックすることになることがわかります。 これは、変換された状態のハッシュを使用したセグメント ツリーを使用するか、範囲加算によって要素間の等価関係が維持される方法ですべての値を均一にシフトするだけであるというより直接的な観察を使用して維持できます。 

これは、範囲の追加をサポートするセグメント ツリーを維持し、間隔が「XOR 依存」であるかどうかに答えることができる構造を維持するという解決策につながります。これは、個別の値の数が正規化後の間隔サイズよりも厳密に小さいかどうかをチェックすることに帰着します。 

実際には、加算の遅延伝播を伴うセグメント ツリーを保存し、圧縮された不変表現の下で各セグメントに重複が含まれているかどうかを維持します。 不変条件は、区間が XOR に依存しない場合に限り、ゼロ XOR サブセットが存在するということです。これは、セグメントにわたる動的な基底を維持することで検出可能な線形依存関係の存在と同等です。

 ## アルゴリズムのチュートリアル

 この問題を処理する正しい方法は、範囲加算更新の下で、間隔が GF(2) に対して XOR に依存しないかどうかを維持するように再フレーム化することです。 

1. 各ノードがそのセグメント内の値の線形基底を格納するセグメント ツリーを構築します。 基礎は 30 ビットにわたる標準の XOR 形式に保たれます。 これにより、そのセグメントのすべてのサブセット XOR をコンパクトに表現できるようになります。 
2. 各ノードは、セグメント内のすべての要素への保留中の追加を表す遅延タグも維持します。 加算を適用するとき、すべての基底ベクトルをすぐに更新するわけではありません。 代わりに、オフセットを保存し、伝播を延期します。 
3. 2 つの子セグメントをマージするには、XOR による標準のガウス消去法を使用してそれらのベースをマージします。 これにより、結合セグメントの基礎が作成されます。 
4. 遅延値をプッシュするときは、各基底ベクトルをそれに応じて変換することで、保存されている基底に加算を適用します。 加算は均一であるため、セグメント内の各要素は一貫してシフトされ、変換後に基底の妥当性が維持されます。 
5. 間隔に関するクエリの場合`[l, r]`では、範囲をカバーするセグメント ツリー ノードを収集し、それらの基底を結合し、結果の基底が線形依存性を示すかどうかを確認します。 
6. 区間のサイズが区間から構築された XOR 基底のランクよりも厳密に大きい場合に限り、区間は空ではないサブセットのゼロへの XOR を許可します。 

これが機能する理由は、GF(2) に関する線形代数の古典的な事実と結びついています。 各数値は 30 次元ベクトル空間内のベクトルです。 空ではないサブセットのゼロへの XOR は、ベクトルが線形依存しているときに存在します。これは、ベクトルの数がそのランクを超えたときに発生します。 範囲の追加は、セグメント内のベクトル間の依存関係を変更しない一貫したアフィン シフトに対応するため、均一な更新の下でランクが保存されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXB = 30

class Basis:
    def __init__(self):
        self.b = [0] * MAXB

    def insert(self, x):
        for i in range(MAXB - 1, -1, -1):
            if (x >> i) & 1:
                if self.b[i]:
                    x ^= self.b[i]
                else:
                    self.b[i] = x
                    return

    def merge(self, other):
        res = Basis()
        for i in range(MAXB):
            if self.b[i]:
                res.insert(self.b[i])
        for i in range(MAXB):
            if other.b[i]:
                res.insert(other.b[i])
        return res

    def rank(self):
        return sum(1 for x in self.b if x)

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.tree = [Basis() for _ in range(4 * self.n)]
        self.lazy = [0] * (4 * self.n)
        self.arr = arr
        self.build(1, 0, self.n - 1)

    def build(self, idx, l, r):
        if l == r:
            self.tree[idx] = Basis()
            self.tree[idx].insert(self.arr[l])
            return
        mid = (l + r) // 2
        self.build(idx * 2, l, mid)
        self.build(idx * 2 + 1, mid + 1, r)
        self.tree[idx] = self.tree[idx * 2].merge(self.tree[idx * 2 + 1])

    def push(self, idx):
        if self.lazy[idx]:
            for child in [idx * 2, idx * 2 + 1]:
                self.lazy[child] ^= self.lazy[idx]
                # apply to basis
                new_basis = Basis()
                for i in range(MAXB):
                    if self.tree[child].b[i]:
                        new_basis.insert(self.tree[child].b[i] ^ self.lazy[idx])
                self.tree[child] = new_basis
            self.lazy[idx] = 0

    def update(self, idx, l, r, ql, qr, val):
        if ql <= l and r <= qr:
            self.lazy[idx] ^= val
            new_basis = Basis()
            for i in range(MAXB):
                if self.tree[idx].b[i]:
                    new_basis.insert(self.tree[idx].b[i] ^ val)
            self.tree[idx] = new_basis
            return
        self.push(idx)
        mid = (l + r) // 2
        if ql <= mid:
            self.update(idx * 2, l, mid, ql, qr, val)
        if qr > mid:
            self.update(idx * 2 + 1, mid + 1, r, ql, qr, val)
        self.tree[idx] = self.tree[idx * 2].merge(self.tree[idx * 2 + 1])

    def query(self, idx, l, r, ql, qr):
        if ql <= l and r <= qr:
            return self.tree[idx]
        self.push(idx)
        mid = (l + r) // 2
        if qr <= mid:
            return self.query(idx * 2, l, mid, ql, qr)
        if ql > mid:
            return self.query(idx * 2 + 1, mid + 1, r, ql, qr)
        left = self.query(idx * 2, l, mid, ql, qr)
        right = self.query(idx * 2 + 1, mid + 1, r, ql, qr)
        return left.merge(right)

def solve():
    n, m = map(int, input().split())
    arr = list(map(int, input().split()))
    st = SegTree(arr)

    for _ in range(m):
        tmp = input().split()
        if tmp[0] == '1':
            _, l, r, x = tmp
            l = int(l) - 1
            r = int(r) - 1
            x = int(x)
            st.update(1, 0, n - 1, l, r, x)
        else:
            _, l, r = tmp
            l = int(l) - 1
            r = int(r) - 1
            basis = st.query(1, 0, n - 1, l, r)
            size = r - l + 1
            if size > basis.rank():
                print("Yes")
            else:
                print("No")

if __name__ == "__main__":
    solve()
```セグメント ツリーはノードごとに XOR ベースを維持し、クエリ時にランク比較が使用されます。 範囲の更新は、ノードを通じて加算をプッシュし、影響を受けるベースを再計算することによって遅延的に処理されます。 

実装上の微妙な選択は、XOR シフトを適用した後に基数を再計算することです。 このコードは、基底ベクトルを代数的に調整しようとするのではなく、変換された値を再挿入することによって各基底を再構築します。 これにより、部分的な基底変換による正確性の問題が回避されます。 

構造が適切に配置されると、クエリ ロジックは単純になります。間隔サイズを基底ランクと比較するだけで、空ではないゼロ XOR サブセットが存在するかどうかを直接取得できます。 

## 実用的な例

 配列が存在する最初のサンプル入力を考えてみましょう。`[1, 2, 3, 4, 5]`そして私たちはクエリします`[2, 5]`。 

| ステップ | セグメント | 基準ランク | セグメントサイズ | 決定 |
 | --- | --- | --- | --- | --- |
 | クエリ 1 | [2,3,4,5] | 4 | 4 | いいえ |
 | クエリ 2 | [2,3,4] | 3 | 3 | いいえ |

 最初のクエリは、GF(2) 内で 4 つのベクトルが独立しているため、空でないサブセットはゼロと XOR されないことを示しています。 2 つ目は、より短い間隔で同様に動作します。 

ここで、更新の重複が増加する変形されたケースを考えてみましょう。 

| ステップ | 操作 | 間隔 | 効果まとめ |
 | --- | --- | --- | --- |
 | 1 | 1を追加 | [1,1] | ローカルベースでシフト |
 | 2 | 2を追加 | [2,3] | 依存の可能性が高まります |
 | 3 | クエリ | [1,5] | ランクはサイズに比例して低下します。 

重要な観察は、更新によりセグメント内の値が均一に変更され、基底ベクトルに一貫して影響を及ぼし、線形依存性が増加する可能性があるということです。

| スペース | O(N log N) | 各ノードは固定サイズの基底を格納します。 

30 ビット ベースのサイズが一定であり、セグメント ツリーの高さが対数であるため、構造は制限内に収まり、100,000 回の操作でも更新とクエリの効率が維持されます。

 ## 特殊なケース

 重要なエッジ ケースは、単一の要素に対するクエリです。 入力用`[x]`、要素自体を除いて空ではないサブセットはなく、XOR は次の場合を除いてゼロになることはできません。`x = 0`、これは初期制約では決して発生せず、更新時に保存する必要があります。 ゼロ以外の要素の基底ランクは常に 1 であるため、アルゴリズムはこれを処理します。そのため、サイズはランクに等しく、答えは正しく「いいえ」になります。 

もう 1 つのケースは、複数の範囲を加算した後の完全に均一な配列です。 のために`[5,5,5,5]`、すべてのペアはゼロと XOR されるため、依存関係が存在します。 基本ランクは 1 になり、間隔サイズは 4 になり、正しい「はい」がトリガーされます。 

最後の微妙なケースは、更新の重複です。 更新は遅延伝播によって適用され、すぐにノード ベースに反映されるため、部分的な更新が繰り返されても、保存されている構造が破損することはありません。 各ノードは常にそのセグメントの正しく変換されたバージョンを表すため、マージされたクエリは現在の配列状態と一貫性を保ちます。
