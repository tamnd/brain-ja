 ## 問題の理解

 正の整数のリストが与えられ、正確に実行することができます。$k$操作。 各操作では 1 つの位置を選択し、その要素を 1 ずつ増やします。すべての増分が適用された後、配列全体の最大公約数を調べ、この値を最大化したいと考えます。 

より具体的に言い換えると、配列から開始し、予算は次のようになります。$k$単位が増加します。 これらの増分を要素全体に任意に分配できますが、それは単位ステップ内でのみです。 すべての増分を費やした後、結果の数値が大きな公約数を共有するようにします。 

重要な問題は、値を減らすことはできず、増やすことだけが許可されており、正確に支出しなければならないことです。$k$増分、最大ではない$k$。 

制約が意味するのは、$n$すべてのテストケースにわたって、$10^6$、および の値$a_i$も集合的に次のように制限されます$10^6$。 これにより、テスト ケースごとの値の範囲内で二次関数を再計算するアプローチは即座に除外されます。 すべてのペアのチェックや操作のシミュレーションに依存する解決策は不可能です。 の合計$k$非常に大きく、最大で$10^{12}$これは、操作を直接シミュレートできないことも意味します。 

微妙なエッジケースは、「まさに$k$」要件。候補となるターゲット gcd が以下の数を使用して機能する場合$k$増分を増やすには、gcd を破壊せずに残りの増分を配布できる場合を除き、すぐに受け入れることはできません。 

たとえば、gcd が必要だとします。$g = 2$すでに 3 つの増分だけを使用して配列を 2 の倍数に調整できますが、$k = 5$。 残りの 2 つの増分を任意に追加すると、慎重に構造化しないと割り切れない可能性があります。 

もう 1 つのエッジ ケースは、すべての要素がすでに大きな数の倍数である場合です。 したがって、残りの演算を使用してさらに増加できる可能性があるため、答えは単に初期の gcd ではありません。 

## アプローチ

 強引なアイデアは、最終的な gcd を推測することです。$g$、有効な最終配列を構築し、次の値で割り切れる値に到達できるかどうかを確認します。$g$せいぜい使用$k$増加します。 固定の場合$g$、各要素$a_i$次の倍数に増やす必要があります$g$。 各要素のコストはその倍数までの距離であり、すべての要素を合計すると、すべてを次の値で割り切れる最小コストが得られます。$g$。 

この野蛮なアプローチは可能な限りすべてを反復します$g$おおよそまで$\max(a_i) + k$、それぞれについて$g$コストを最初から再計算します$O(n)$。 これは次のことにつながります$O(n \cdot \max A)$が遅すぎるときは、$\max A = 10^6$。 

重要な観察は、候補 gcd を修正すると、$g$、各数値は独立して決定論的なコストに寄与します。次の倍数に切り上げられる必要があります。$g$。 これは問題を、各剰余クラスのモジュロに該当する値の数を数えるという問題に変換します。$g$、およびモジュール調整の合計。 

残りの微妙な点は、追加の処理です。$k - \text{cost}$操作。 正確に追加して以来$g$任意の要素に対して、次のような割り算が維持されます。$g$、残りの操作はサイズのチャンクでのみ有効です。$g$。 これにより、残りは次で割り切れなければならないという条件が生じます。$g$。 

次に、可能な限りすべてをスキャンします$g$、実現可能性を計算し、有効な最大値を取得します。

 ## アルゴリズムのチュートリアル

 テスト ケースごとに、入力内のすべての値に対して周波数配列を構築します。 これにより、等差数列に含まれる要素の数を効率的に答えることができます。 

次に、すべての候補 gcd を試します$g$1 から可能な最大値まで。 

1.固定の場合$g$、すべての要素を次の値で割り切れるようにするために必要な最小増分数を計算します。$g$。 要素ごとに$a_i$、必要な増加量は$(g - a_i \bmod g) \bmod g$。 頻度数を使用して、すべての要素についてこれを合計します。 
2.この合計費用を超える場合$k$、 それから$g$不可能なのでスキップします。 
3. コストが最大でも$k$、残りを計算します$k - \text{cost}$。 この残り物は、割り算を壊すことなく使用できる必要があります。 唯一の安全な操作は追加です$g$任意の要素に変換できるため、残りは次で割り切れる必要があります。$g$。 
4. 両方の条件が当てはまる場合、マークを付けます。$g$可能な限り。 
5. 可能な限り最大限のことを考慮します$g$。 

これが機能する理由は、gcd を含む有効な最終配列がすべて$g$すべての要素が 0 を法として合同でなければなりません$g$。 値を増やすことしかできないため、各要素の最適な戦略は独立しています。つまり、値を最も近い倍数にプッシュします。$g$。 逸脱すると、実現可能性は向上せずにコストが増加するだけです。 有効な構成に達した後は、残りの操作を任意に使用することはできません。分割可能性を維持する必要があるため、強制的にサイズのブロックに分割されます。$g$。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        
        mx = max(a)
        freq = [0] * (mx + 1)
        for v in a:
            freq[v] += 1
        
        # prefix not needed, we use frequency directly
        
        ans = 1
        
        for g in range(1, mx + 1):
            cost = 0
            
            # compute cost to make all numbers divisible by g
            for r in range(g):
                # sum over v = r + t*g
                add = 0
                v = r
                while v <= mx:
                    add += freq[v]
                    v += g
                
                if add == 0:
                    continue
                
                # all numbers in this residue contribute (g - r) mod g
                if r == 0:
                    continue
                cost += add * (g - r)
                if cost > k:
                    break
            
            if cost > k:
                continue
            
            if (k - cost) % g == 0:
                ans = g
        
        print(ans)

if __name__ == "__main__":
    solve()
```このコードは、要素を繰り返し反復処理しないように、最初に入力を周波数配列に圧縮します。 各候補の gcd について$g$、剰余クラスをモジュロで処理します$g$。 残基ごとに$r$、値を調べます$r, r+g, r+2g, \dots$そしてそこに入る数字の数を数えます。 

このような各数値は正確に寄与します$(g - r)$次の倍数に達するまで増分します$g$、その剰​​余のすべての値が同じ剰余を共有するためです。 

最終的な実現可能性チェックでは、予算の制約と残りの操作の分割可能性の両方が強制され、残りの増分を安全に配布できることが保証されます。

 ## 特殊なケース

 重大なエッジケースは、配列がすでに候補で完全に割り切れる場合です。$g$。 その状況では、コストはゼロであり、正しさは完全に次のとおりであるかどうかに依存します。$k$の倍数です$g$。 残りの部分でも可分性を維持する必要があるため、アルゴリズムはこれを自然に処理します。$k \bmod g = 0$。 

もう 1 つのエッジケースは次のような場合です$g = 1$。 すべての配列は演算を行わずに 1 で割り切れるため、コストは常にゼロであり、答えは常に少なくとも 1 になります。アルゴリズムは正しく維持します。$g = 1$フォールバックとして。 

3 番目のエッジケースは次の場合に発生します。$k$直接の丸めコストを超過するのに十分な大きさです。 このアルゴリズムは依然としてモジュロ条件によって実現可能性を制限しており、過剰な操作によって暗黙的に gcd が無効になることがないようになっています。
