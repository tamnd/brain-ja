 ## 解決策
 ## 問題の理解

 ビデオ ストリームの循環メニューが表示されます。 ジョージはストリーム 1 にカーソルを固定した状態から開始します。彼は合計 3 種類のボタンを繰り返し押すことができます。$m$回: 円上でカーソルを 1 ステップ左に移動するか、1 ステップ右に移動するか、現在選択されているストリームを再生します。 

各ストリーム$i$報酬逓減モデルというものがあります。 初めてストリームを再生したとき$i$、彼は稼いでいます$a_i$。 2回目にプレイすると、報酬が減少します$b_i$、そして一般的には$k$- 回目のプレイで得られる成果$\max(a_i - (k-1)b_i, 0)$。 値が非正になると、それ以降のプレイではゼロが得られます。 

目標は、正確な範囲内でカーソルの移動と再生のシーケンスを選択することです。$m$ボタンを押すと、収集された報酬の合計が最大になります。 

重要な相互作用は、移動にはプレスのコストがかかりますが、さまざまなストリームへのアクセスが可能になるのに対し、再生ではプレスが消費され、ストリームごとの繰り返しに応じて価値が減少するという点です。 

制約は十分に小さいため、ポジションと残りの動きに対する三次またはわずかに悪い動的プログラミングが可能になります。 と$n \le 200$そして$m \le 1000$、サイズの状態空間$O(nm)$すでに合理的であり、次のような移行が含まれます。$O(n)$作業は最適化された形式でも実行可能です。 フルボタンシーケンスを列挙したり、単純な方法でストリームごとの再生数を維持したりするようなことは、組み合わせ的に爆発的に発生します。 

同じストリームで繰り返し再生すると、微妙な問題が発生します。 位置と残りの動きだけを追跡する単純な DP は、各ストリームが再生された回数もエンコードしない限り失敗します。これは、状態の爆発により直接は不可能です。 

もう 1 つのエッジの動作は、動きが円形であることです。 たとえば、ストリーム 1 から左に移動すると、ストリームに移動します。$n$したがって、最短の移動では、直線距離ではなく、常に時計回りと反時計回りの両方の距離を考慮する必要があります。 

最後に、報酬の減衰により、「貪欲な繰り返しプレイ」は局所的には魅力的ですが、1 つのストリームであまりにも多くの再生を費やすと他の場所での機会が減少するため、世界的には制限されます。 

## アプローチ

 ブルートフォース戦略では、考えられるすべてのシーケンスをシミュレートします。$m$ボタンを押します。 押すたびに最大 3 つの選択肢に分岐するため、シーケンスの合計数は次のようになります。$3^m$、すでに天文学的に大きい$m = 1000$。 報酬はストリームごとの履歴に依存するため、明らかな対称性を枝刈りしても役に立ちません。 

もう少し構造化されたブルート フォースでは、「現在のカーソル位置、各ストリームが再生された回数」のような DP 状態を試みます。 報酬関数はストリームごとのカウントのみに依存するため、これは原理的には正しいですが、状態空間は次のようになります。$O(n^m)$最悪の場合、それは不可能です。 

重要な観察は、報酬構造がストリームごとに分離可能であるということです。合計ゲインは、再生数が凹状に減少するシーケンスのストリーム全体の合計です。 これは、ストリームへのアクセス回数が固定されている場合、正確な再生順序ではなく、再生回数だけを気にすればよいことを示唆しています。 一方、移動は訪問の手配方法にのみ影響します。 

これは、標準的な最適化手法につながります。つまり、ボタンを押すシーケンスの観点から考えるのではなく、各ストリームに何回「再生を割り当てる」のか、また、順番にストリームにアクセスするのにどのくらいの移動コストが必要なのかという観点から考えます。 カーソルが円の上にあるので、$n \le 200$、距離を事前計算してから、ストリームと残りの動きに対して動的プログラミングを実行できます。 

私たちはこのプロセスをストリーム上にパスを構築するものとして扱い、ストリームに到着するたびに複数の再生を連続して実行する可能性があります。 移動はプレイ回数に依存しないため、連続プレイは常に最適です。そのため、ノードに到達したら、同じ限界報酬パターンのためにすぐに離れて戻ってくることは決して有益ではありません。 

したがって、問題は次のようになります。ストリームへの一連の訪問を選択し、その間の移動コストを支払い、各訪問で既知のプレフィックス合計報酬関数を使用して実行する再生回数を選択します。 

ストリームごとに事前計算します$i$配列$gain[i][k]$、プレイの合計報酬$k$続けて何回も。 次に、州に対して DP を実行します$(i, t)$: ストリームで終了する最大報酬$i$正確に使用した$t$ボタンが押されました。 移行では、以前のストリームからの移行が考慮されます$j$に$i$, 移動コストとプレイコストを支払います。 

以来$n$が小さい場合、最短円周距離を事前に計算できます。$O(1)$、トランジションは$O(n)$州ごとに、収量$O(n^2 m)$、これは許容範囲です。

 ## アルゴリズムのチュートリアル

 まずストリームごとの報酬関数をプレフィックス合計に変換し、次に時間と終了位置に応じて階層化された DP を実行します。 

### ステップ

 1. ストリームごとに$i$、有効な再生の最大数を計算します。$c_i$、これが最大です$k$そのような$a_i - (k-1)b_i > 0$。 

これは、ストリームを連続して再生することを検討する回数を制限します。 
2. 事前計算$gain[i][k]$最初の合計として$k$ストリームの再生$i$。 

これはゼロで切り捨てられる単純な等差数列です。 

事前に計算する理由は、後で「支出」を評価する必要があるためです。$k$ここで再生を押します」と一定時間で表示されます。 
3. ストリームのすべてのペア間の循環距離を事前計算します。$$dist(i, j) = \min(|i-j|, n-|i-j|)$$これは、ストリーム間を移動するために必要なボタンを押す回数を表します。 
4. DP テーブルの初期化$dp[t][i]$、正確に後の最大報酬を意味します$t$ストリームで終了するボタンの押下$i$。 

から始める$dp[0][1] = 0$、カーソルは報酬なしでストリーム 1 から始まるためです。 
5. 毎回$t$0から$m$、および現在の位置ごとに$i$、すべてのターゲット ストリームを試します$j$。 

移動に余裕があれば$d = dist(i, j)$、残りの予算を次の演劇に費やすことを検討しています。$j$。 
6. それぞれについて$j$、考えられるすべての再生回数を試してください$k$そのような$t + d + k \le m$。 

アップデート：$$dp[t+d+k][j] = \max(dp[t+d+k][j], dp[t][i] + gain[j][k])$$7. 答えは全体の最大値です$dp[t][i]$のために$t \le m$。 

### なぜ効果があるのか

 DP の不変条件は次のとおりです。$dp[t][i]$正確に達成した後に達成可能な最高の報酬を保存します$t$ストリームで終了するボタンの押下$i$、すべての有効な動きとプレーのシーケンスを考慮します。 すべての遷移は、有効な次のアクション ブロックに対応します。$i$に$j$、その後、再生します$k$回。 プレイは連続して最適にグループ化され、移動コストは報酬に依存しないため、すべての有効な戦略を総コストや利益を変えることなくそのようなブロックに分解できます。 これにより、最適なシーケンスが DP 表現から除外されなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
a = list(map(int, input().split()))
b = list(map(int, input().split()))

# precompute gain
gain = []
max_take = []

for i in range(n):
    cur = []
    total = 0
    k = 0
    while True:
        val = a[i] - k * b[i]
        if val <= 0:
            break
        total += val
        cur.append(total)
        k += 1
        if k > m:
            break
    gain.append(cur)
    max_take.append(len(cur))

# circular distance
def dist(i, j):
    d = abs(i - j)
    return min(d, n - d)

INF = -10**18
dp = [[INF] * n for _ in range(m + 1)]
dp[0][0] = 0  # start at stream 1 (index 0)

for t in range(m + 1):
    for i in range(n):
        if dp[t][i] == INF:
            continue
        cur_val = dp[t][i]
        for j in range(n):
            d = dist(i, j)
            nt = t + d
            if nt > m:
                continue
            # try k plays
            max_k = min(max_take[j], m - nt)
            for k in range(max_k + 1):
                nt2 = nt + k
                if nt2 > m:
                    break
                val = cur_val + (gain[j][k - 1] if k > 0 else 0)
                if val > dp[nt2][j]:
                    dp[nt2][j] = val

ans = max(max(row) for row in dp)
print(ans)
```DP テーブルには時間と位置によってインデックスが付けられます。 初期化では、ストリーム 1 のみが開始点として正しく設定されます。 ネストされたループは、すべての可能な動きとバンドルされたプレイ アクションを明示的に列挙します。 

微妙な点は、劇が束になっているということです。動きを挟み込まず、1 つずつ再生します。 移動は報酬に直接影響せず、ノードでのプレイは消費時間を除いて将来の移動の決定とは独立しているため、これは安全です。 

ゲイン ルックアップではプレフィックス合計が使用されるため、次の報酬を取得します。$k$遊ぶのは$O(1)$。

 ## 特殊なケース

 まれなケースは、すべてが$b_i$が大きいため、最初のプレイのみが意味のあるものになります。 例えば：```
n = 2, m = 3
a = [5, 4]
b = [10, 10]
```ストリームごとに 1 回の再生のみが重要です。 DP は繰り返しの再生を正しく回避します。`gain[i]`1 つの要素の後で切り捨てられます。 最適な戦略は、純粋に 2 つのノードにわたるルーティングの問題になります。 

もう 1 つは、移動コストで予算がすべて消費される場合です。 例えば：```
n = 200, m = 1
```移動を必要とするトランジションはすぐに予算を超え、開始ノードでのプレイのみが有効なアクションとして残るため、アルゴリズムは引き続き機能します。 

最後に、すべてのストリームが同一の場合、DP は時間を任意に分配しますが、位置に関係なく常に同じ報酬を蓄積します。 時間の経過に伴う状態圧縮により、シーケンスの順序付けの問題が正確さに影響を与えることがなくなります。
