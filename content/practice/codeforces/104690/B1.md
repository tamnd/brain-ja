 ## 問題の理解

 ターゲットとなる「金属」のマルチセットが与えられており、各金属タイプは正の整数インデックスによって識別され、各インデックスに対して少なくとも必要な数のユニットをある最大値まで生産できなければなりません。 選択した単一の卑金属から開始し、固定の変換ルールを繰り返し適用することができます。つまり、金属の 1 単位を取得します。`i`それを消費し、より小さい指数の金属を生成します`i - a`そして`i - b`(それらのインデックスが正の場合)。 インデックスが 1 未満の金属は何も寄与しないため、下に進むにつれてプロセスは自然に「消滅」します。 

タスクは、固定されたプロセスをシミュレートすることではなく、この変換を何度も適用し、余分なものを破棄した後、必要なすべての量を満たすことができるように、可能な限り最小の開始金属インデックスを決定することです。 

入力により、必要な最高の金属指数が得られます`N`、2つのオフセット`A`そして`B`各金属がどのように分割されるかを定義し、次に金属の需要配列を定義します。`1`を通して`N`。 出力は、すべての要求を生成できる最小の開始インデックス、または開始インデックスが機能しないことを示す信号です。 

この変換は分岐プロセスを作成するように見えますが、重要な問題は余剰を自由に破棄できることです。 これにより、構造はシミュレーションの問題ではなく、依存関係の有向グラフに関する実現可能性の問題に近づきます。 

制約 (元の問題では、これは Codeforces ジム内の Code Jam スタイル設定に由来します) により、次のことが可能になります。`N`したがって、各候補開始値の完全な展開をシミュレートするソリューションは非常に遅すぎます。 単純なシミュレーションではノードが繰り返し拡張され、最悪の場合、単一のユニットが多くのレベルにわたるカスケードをトリガーし、開始値の繰り返し試行で二次関数またはさらに悪い動作が発生する可能性があります。 

微妙なエッジ ケースは、需要が小さいインデックスでのみ存在するが、`(i - A)`そして`(i - B)`。 「高級金属は常に優れている」と常に想定する素朴な貪欲さは失敗する可能性があります。なぜなら、出発点によっては、金属が大きくても特定の残留物を生成できないためです。 

## アプローチ

 ブルートフォースの見方は簡単です: 開始金属インデックスを選択します`S`、変換プロセスをシミュレートし、最終的に各金属を何ユニット生産できるかを追跡し、すべての要求が満たされているかどうかを確認します。 各メタルは最大 2 つの小さなメタルをスポーンする可能性があるため、最悪の場合、作成されるノードの数は枝分かれしたツリーのように増加します。 メモ化してもこれを候補者ごとに繰り返す`S`まで`N`のオーダーの操作数につながります。`O(N^2)`さらに悪いことに、大規模な入力には遅すぎます。 

重要な観察は、すべての候補開始から順に明示的にシミュレーションする必要がないということです。 代わりに、視点を逆にすることができます。金属指数の各需要は、繰り返しの逆遷移を通じてそれを生成できる、より高い指数からの「サポート」を必要とすると考えることができます。 各金属インデックスは、2 つのより大きなインデックスのみに依存します。`i + A`そして`i + B`。 これにより、問題は依存関係の伝播または逆グラフの到達可能性の条件に変わります。 

各開始点を個別にテストするのではなく、要件を上方に伝播することによって、固定の開始インデックスが十分であるかどうかを計算します。 金属のユニットが「必要」だと想像すると、`i`、その後、その要件をその可能な親に適用する必要があります`i + A`そして`i + B`。 構造が単調になる: 開始インデックスの場合`S`機能する場合は、すべてを生成するためのより多くの余地があるため、より大きな開始インデックスも機能します。 この単調性により、二分探索が可能になります。`S`。 

修正の実現可能性チェック`S`高いインデックスから低いインデックスまで貪欲に実行され、必要なカウントが増加します。 これにより、明示的なシミュレーションが回避され、各チェックが線形に保たれます。`N`。

 ## アルゴリズムのチュートリアル

 開始インデックス候補を修正します`S`必要な金属をすべて生成できるかどうかをテストします。 

1. 配列を初期化します`need[i]`各金属の必要なユニット数に等しい`i`。 
2. インデックスから繰り返します`1`まで`S`であらゆる要件をプッシュします。`i`上向きに`i + A`そして`i + B`。 ユニットを「使用」するたびに、`i`、より高級な金属から製造されたに違いないと仮定するため、デクリメントします。`need[i]`そして増加します`need[i + A]`そして`need[i + B]`有効な場合はそれに応じて。 これは、変換の逆をモデル化します。 
3. インデックスは昇順に処理されるため、一度ポジションを解決すると、そのポジションは再度必要になることはありません。 すべての依存関係が上向きであるため、この順序付けは機能します。 
4. 伝播後、すべての`need[i]`のために`i ≤ S`はゼロまたは負です。 プラスの需要が範囲内に残っている場合、開始インデックスは`S`では不十分です。 
5. 二分探索をします`S`から`1`に`max possible index`、上記の実現可能性チェックを使用します。 

正確さは、すべての変換がインデックスを厳密に減少させるという事実にかかっており、そのため、すべての生産チェーンは非循環であり、より大きなインデックスからより小さなインデックスへと流れます。 この方向を逆にすると、有向非循環依存関係グラフが得られ、伝播は要求を満たすことができるすべての方法を完全に捕捉します。 

### なぜ効果があるのか

 ポジションの各需要単位`i`最終的には、より高いインデックスのチェーンから取得される必要があり、そのようなチェーンはすべて、逆エッジの繰り返し適用に対応します。`(i → i + A)`そして`(i → i + B)`。 伝播により、必要なすべてのユニットがすべての可能な先祖に確実に「リフト」されます。 完全に伝播した後、候補範囲内で矛盾が発生しない場合`S`の場合、インデックス ≤ のみを使用したすべての要求の有効な分解が存在します。`S`、有効な構造が存在することを意味します。 実現可能性の単調性`S`二分探索により有効な最小開始点が見つかることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(S, N, A, B, req):
    need = req[:]
    
    for i in range(1, S + 1):
        if need[i] <= 0:
            continue
        
        cnt = need[i]
        need[i] = 0
        
        j1 = i + A
        j2 = i + B
        
        if j1 <= N:
            need[j1] += cnt
        if j2 <= N:
            need[j2] += cnt
    
    for i in range(1, S + 1):
        if need[i] > 0:
            return False
    return True

def solve():
    N, A, B = map(int, input().split())
    req = [0] + list(map(int, input().split()))
    
    lo, hi = 1, N
    ans = -1
    
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid, N, A, B, req):
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1
    
    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、実現可能性のチェックと、可能な出発金属の検索を分離します。 の`can`関数は逆伝播を実行し、すべての要求が逆変換規則に従って一貫して上方に押し上げられるようにします。 二分探索は実現可能性の単調性を利用します。 

一般的な実装の落とし穴は、伝播によって要求配列が変化するため、チェックごとに要求配列をコピーするのを忘れることです。 もう 1 つの微妙な問題は、次の場合の境界処理です。`i + A`または`i + B`を超える`N`これらの金属は必要な範囲外にあり、正確さに影響を与えないため、これは無視する必要があります。 

## 実用的な例

 ### 例 1

 仮定してください`N = 5`、`A = 1`、`B = 2`、要件は次のとおりです。`[0, 0, 1, 0, 0, 0]`。 

テストします`S = 3`。 

| 私 | | 前に [i] が必要です アクション | 伝播した |
 | --- | --- | --- | --- |
 | 1 | 0 | スキップ | なし |
 | 2 | 1 | プッシュ | 必要[3] += 1、必要[4] += 1 |
 | 3 | 1 | プッシュ | 必要[4] += 1、必要[5] += 1 |

 処理後、内部のすべての要求が`≤ S`解決されているので、`S = 3`動作します。 

これは、単一の要求がどのようにして複数の上位の依存関係に拡張される可能性があるか、また貪欲なローカル解決がなぜ必要なのかを示しています。 

### 例 2

 しましょう`N = 4`、`A = 1`、`B = 2`、需要あり`[0, 1, 1, 0, 0]`。 

| 私 | | 前に [i] が必要です アクション | 伝播した |
 | --- | --- | --- | --- |
 | 1 | 1 | プッシュ | 必要[2] += 1、必要[3] += 1 |
 | 2 | 2 | プッシュ | 必要[3] += 2、必要[4] += 2 |
 | 3 | 3 | プッシュ | 必要[4] += 3 |

 現在、インデックス 4 は需要を蓄積していますが、それ以上の伝播範囲外にあります。 もし`S`が小さすぎると需要が残り、実行不可能であることがわかります。 

これは、選択する理由を示しています`S`ローカル拡張が十分であるように見えても、小さすぎると失敗します。

 ## 特殊なケース

 重要なエッジケースは、すべての需要がインデックスに集中している場合です。`1`。 そのような状況では、繰り返される逆伝播力が予想よりも速い上昇を要求する場合、比較的大きな開始インデックスでも必要になる可能性があります。 伝播では常に両方の親ブランチが尊重されるため、アルゴリズムはこれを処理します。そのため、隠れた依存関係が失われることはありません。 

もう一つのケースは次のような場合です。`i + A`または`i + B`超える`N`。 これらの遷移は安全に無視されます。これは、無関係な金属タイプを作成する生産に相当します。 この問題では余分なものを破棄できるため、これは実現可能性に影響を与えず、伝播時の境界チェックによって正しく処理されます。
