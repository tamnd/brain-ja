 ## 解決策
 ## 問題の理解

 このタスクは、固定の参照文字列と複数の候補文字列を比較し、残りの文字を並べ替えずに参照から一部の文字を削除することで各候補を取得できるかどうかを確認することを中心に展開します。 言い換えれば、クエリ文字列ごとに、それがベースライン文字列のサブシーケンスとして現れるかどうかを判断する必要があります。 

ベースライン文字列はシステムによって生成される一連の文字を表し、各デザイン文字列は必要な構成を表します。 ベースラインから文字を削除することはできますが、順序を変更したり、新しい文字を挿入したりすることはできません。 各設計の出力は、その設計を順序を維持した方法でベースラインに埋め込むことができるかどうかに応じて、単純に「はい」または「いいえ」の決定を行います。 

基線の長さを次のようにします$n$そして、あると仮定します$q$デザインストリング、それぞれ全長最大$n$。 各クエリの直接 2 ポインタ スキャンでは、ベースラインで直線的な時間がかかるため、単純な解決策はおおよそ次のようになります。$O(q \cdot n)$。 両方の場合$q$そして$n$が大きい場合、特に両方が接近できる場合には、すぐに遅くなりすぎます。$10^5$、最悪の場合は約$10^{10}$キャラクターの比較。 

各デザインの長さはベースラインと同じ長さであるという制約により、長い文字列を短い文字列に一致させようとするケースは除外されますが、すべてのデザインがベースラインとほぼ同じ長さになるという病的なケースを防ぐことはできません。 このような場合、ベースラインのフル スキャンを繰り返すことがボトルネックになります。 

ベースラインに繰り返し文字が含まれており、デザインにも繰り返しが含まれている場合、微妙なエッジ ケースが発生します。 たとえば、ベースラインが次の場合、`aaaaabaaaaa`そしてデザインは`aaaaaa`不注意な貪欲マッチャーは、個々のマッチング ロジックが正しい場合でも、一致するたびに最初からスキャンを繰り返し、誤って二次動作に低下する可能性があります。 

注意深く順序付けせずに文字の位置のみを事前計算しようとすると、別の問題が発生します。 たとえば、文字の頻度のみを保存するとすぐに失敗します: ベースライン`abc`そしてデザイン`cba`同じ周波数を持っていますが、デザインは有効なサブシーケンスではありません。 

## アプローチ

 ブルート フォース手法では、ポインタでベースラインを通過し、文字が一致するたびに前進することで、各デザインを個別にチェックします。 これは、サブシーケンス定義を直接適用するため、正しいです。 ただし、デザインごとにこのスキャンを繰り返すと、同じベースライン文字列を繰り返し走査することになり、クエリの数が多い場合には実行時間が支配的になります。 

重要な観察は、短い文字列を固定された長い文字列と照合するという同じ構造的問題を繰り返し解決しているということです。 一致を最初から再計算する代わりに、ベースラインを前処理して、次に出現する各文字にすぐにジャンプできるようにすることができます。 すべての位置と文字について、次の出現箇所がわかれば、実装に応じてステップごとに対数時間または定数時間で各デザインを進めることができます。 

これにより、各一致ステップがリニア スキャンから直接ジャンプに変換され、クエリの繰り返しによる冗長な作業が削除されます。 問題の構造では、異なるクエリ間の相互作用は必要ないため、それらを分離するには前処理で十分です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (クエリごとに 2 つのポインタ) |$O(q \cdot n)$|$O(1)$| 遅すぎる |
 | 次回発生の前処理 | (O(n \cdot \sigma + \sum | d_i | )) |

 ここ$\sigma$アルファベットのサイズです。 

## アルゴリズムのチュートリアル

 「位置 i の文字 c が必要な場合、次にどこに行けばよいか」に即座に答えられるように、ベースラインを前処理します。 

1. ベースライン内のすべてのインデックスとすべての文字について、そのインデックス以降にその文字が次に出現する位置を格納する次の位置のテーブルを構築します。 これは、各文字の最新の位置を維持しながら、文字列を右から左にスキャンすることによって構築されます。 この逆方向により、位置 i にいるときに、それ以降のすべての位置の答えがすでにわかっていることが保証されます。 
2. 各デザイン文字列について、ベースラインの最初の文字の前に最初に設定されたポインタを使用して、ベースラインとのマッチングをシミュレートします。 
3. デザイン内のすべての文字について、事前計算されたテーブルを使用して、その文字が表示される次の有効な位置にポインタをジャンプします。 そのような立場が存在しない場合、そのデザインは形成できないと即座に結論付けます。 
4. デザインのすべての文字が正常に処理された場合、それは有効なサブシーケンスであることが確認されます。 

順方向にスキャンする代わりに次のテーブルを使用する理由は、ベースラインの同じサフィックスを繰り返し走査する必要がなくなるからです。 各ステップは直接検索になります。 

### なぜ効果があるのか

 いつでも、ポインターは常に、デザインのプレフィックスが一致したベースライン内の可能な限り最も早い位置を表します。 次の出現テーブルでは、常に次の文字の実行可能な最も早い位置にジャンプするため、一致の有効な継続が存在する場合、それに到達することが保証されます。 これにより、クエリごとに複数回チェックされる文字がないことを保証しながら、有効な埋め込みを決してスキップしない貪欲な不変条件が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_next(s):
    n = len(s)
    nxt = [[n] * 26 for _ in range(n + 1)]
    
    last = [n] * 26
    for i in range(n - 1, -1, -1):
        last[ord(s[i]) - 97] = i
        for c in range(26):
            nxt[i][c] = last[c]
    return nxt

def solve():
    b = input().strip()
    n = len(b)
    nxt = build_next(b)
    
    q = int(input())
    out = []
    
    for _ in range(q):
        d = input().strip()
        pos = 0
        ok = True
        
        for ch in d:
            c = ord(ch) - 97
            if pos >= n or nxt[pos][c] == n:
                ok = False
                break
            pos = nxt[pos][c] + 1
        
        out.append("YES" if ok else "NO")
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装の中核となるのは、`build_next`関数。 テーブルを構築します。`nxt[i][c]`以降の最も古いインデックスを返します。`i`どこの文字`c`が表示されます。 これにより、マッチング中に一定時間のジャンプが可能になります。 

クエリ処理中に、`pos`ベースラインでどこまで一致したかを追跡します。 デザイン内の各文字ごとに移動します`pos`次の有効な出現に 1 を加えたものです。次の検索は厳密に一致した位置の後に開始する必要があるためです。 必要な文字が残りのサフィックスから欠落した時点で、早期に終了します。 

よくある落とし穴は移動を忘れることです`pos`文字に一致した後、前に進みます。 なしで`+1`、アルゴリズムが同じ位置を繰り返し一致させ、無効なケースを誤って受け入れたり、誤ったループに入ったりする可能性があります。 

## 実用的な例

 ベースラインを検討する`abac`2つのデザインで`ac`そして`ca`。 

初めてのデザインに関しては`ac`:

 | ステップ | キャラクター | 前の位置 | nxt ルックアップ | 後の位置 | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | | 0 | 0 | 1 | 一致しました |
 | 2 | c | 1 | 3 | 4 | 一致しました |

 両方の文字が順番に見つかるため、このデザインは採用されました。 

2つ目のデザインについては、`ca`:

 | ステップ | キャラクター | 前の位置 | nxt ルックアップ | 後の位置 | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | c | 0 | 3 | 4 | 一致しました |
 | 2 | | 4 | なし | - | 失敗 |

 を使用した後、2 番目のステップは失敗します。`c`、ありません`a`ベースラインの後半に表示されます。 

これらのトレースは、ポインターが前方にのみ移動し、前の位置に戻らないことを示しており、これにより正しい順序が強制されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 | 時間 | (O(n \cdot \sigma + \sum | d_i |

 ## 特殊なケース

 特殊なケースの 1 つは、デザインが空の場合です。 空のシーケンスは常にサブシーケンスであるため、処理する文字がないため、アルゴリズムはトラバーサルなしですぐに成功します。 

もう 1 つのケースは、ベースラインが非常に短いのにデザインが長い場合です。 たとえば、ベースライン`ab`そしてデザイン`aba`。 最後の文字検索中に、次回出現テーブルは有効な位置が存在しないことを示すセンチネル値を返し、アルゴリズムはそれ以上のスキャンを行わずにデザインを正しく拒否します。 

3 番目のケースは、ベースラインで文字が頻繁に繰り返される場合です。 ベースライン用`aaaaaa`そしてデザイン`aaaaa`の場合、ポインタは連続する位置 0、1、2、3、4、5 を決定論的に進み、後戻りや曖昧さがなくなります。
