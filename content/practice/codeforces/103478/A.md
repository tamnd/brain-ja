 ## 解決策
 ## 問題の理解

 複数の Codeforces アカウントが与えられ、それぞれが独自の評価値から始まります。 時間の経過とともに、一連のコンテストが発生し、各コンテストは固定のレーティング変更に貢献します。 コンテストごとに、参加するアカウントを 1 つだけ選択する必要があります。 アカウントがコンテストに選ばれると、そのアカウントのみがそのコンテストの評価変更を受けますが、他のすべてのアカウントは変更されません。 

すべてのコンテストがアカウントに割り当てられると、各アカウントには評価変更の一部が蓄積されることになります。 各アカウントの最終的な価値は、その初期評価に割り当てられたすべてのコンテストへの貢献の合計を加えたものになります。 私たちの目標は、すべてのアカウント間での最終評価の最大値ができるだけ大きくなるように、コンテストをアカウント間で分散することです。 

問題の構造はトレードオフを示唆しています。多くのプラスの利益を 1 つのアカウントに集中させると最大値が増加しますが、マイナスの値はアカウントを引き下げる可能性があります。 すべてのアカウントで最終的な最大値を最大化しているため、他のアカウントが残りのコンテストのシンクとして機能する一方で、コンテストのサブセットを選択して 1 つの「最高の」アカウントを構築しようとしています。 

この制約により、最大 100,000 のアカウントと 100,000 のコンテストが許可されます。 代入を列挙しようとするソリューションや、サブセットに対する動的プログラミングさえも不可能です。 解は線形または線形演算に近く、O(n + m) または O((n + m) log n) 程度でなければなりません。 

すべての di が負の場合、微妙なエッジ ケースが発生します。 現在の最良のアカウントに常にプラスを割り当て、その他の場所にマイナスを割り当てる単純な貪欲な戦略は、アカウント間でマイナスを分散しても、代替候補を下げることによって間接的にグローバル最大値に影響を与えるという事実を明示的に考慮していなければ、失敗する可能性があります。 

もう 1 つの特殊なケースは、すべての di が正の場合です。 その場合、最適な戦略はすべてのコンテストを 1 つのアカウントに積み重ねることですが、最終的な目的を考慮せずにコンテストごとの割り当てを貪欲に考えても、これはすぐにはわかりません。 

## アプローチ

 強引な解釈では、各コンテストを n 個のアカウントのうちの 1 つに割り当てられる可能性をすべて考慮します。 割り当てごとに、最終的な評価を計算し、アカウント全体の最大値を追跡します。 これにより、コンテストごとに n 個の選択肢があり、n^m 個の可能な割り当てが生成されます。 たとえ小さな値であっても、これは天文学的に大きく、まったく実行不可能です。 

重要な観察は、最終的な答えにとって実際に重要となるのは 1 つのアカウントだけ、つまり、すべての更新後に最終的に最大となるアカウントだけであるということです。 どのアカウントが最終的な最大値になるかを修正するとします。 したがって、このアカウントに送信されないすべてのコンテストの課題は、そのアカウントに間接的に影響を与えることを除いて、無関係になります。 したがって、選択したアカウント i に対して、できるだけ多くの有益な di を割り当てることで、その最終的な価値を最大化したいと考えます。 

ただし、すべてのコンテストをそのアカウントに割り当てる必要はありません。 他の場所に割り当てられたコンテストは i に寄与しないため、i を最大化するには、明らかにすべてのコンテストを i に割り当てることを好みます。 これを妨げる制限はありません。 したがって、任意の固定アカウント i について、その最良の最終値は単純に ri + sum(すべてのコンテストにわたる di) となります。 

これは、すべてのアカウントが独立して同じ合計増加額 (di) を達成できることを意味します。 したがって、アカウント間の唯一の違いは初期値 ri です。 可能な限り最高の最終最大値は、最大の初期評価を持つアカウントを取得し、そのアカウントにすべてのコンテストを与えることによって達成されます。

微妙な推論ステップは、すべての di が常に 1 つのアカウントにのみ適用され、アカウント全体の最大値を最大化しているため、現在の最大候補への寄与を減らす方法でコンテストをアカウント間で分割する理由は決してないことを認識することです。 最も強力な初期アカウントにすべてを集中させることは、すべての選択肢を支配します。 

ここで、問題を単純な計算にまとめることができます。つまり、di の合計を計算し、それを最大 ri に加算します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース割り当て | O(n^m) | O(n) | 遅すぎる |
 | 最適な集約 | O(n + m) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. n と m を読み取り、続いて初期評価の配列 ri とコンテストの変更の配列 di を読み取ります。 
2. すべての初期定格の最大値を計算します。 これは、すべてのアカウントの中で最も強力な開始点を表します。 最適なソリューションは必ず何らかの理由で終了する必要があり、最良のベースラインから開始することが常に支配的です。 
3. すべての di の合計を計算します。 これは、すべてのコンテストにわたってシステムに注入される利用可能なレーティングの合計を表します。 
4. di の合計を最大初期定格に加算します。 これは、すべてのコンテストをすでに最高の開始値を持つアカウントに割り当て、このアカウントが全額の利益を蓄積することを保証することに相当します。 
5. 結果の値を出力します。 

なぜ効果があるのか

 どの時点でも、各コンテストは 1 つのアカウントに 1 つの di を寄付します。 したがって、すべてのアカウントを結合すると、付加価値の合計は固定され、sum(di) に等しくなります。 最終的なアカウントの最大値を最大化しているため、この一定の合計をできるだけ多く単一のアカウントに集中させたいと考えています。 複数のアカウントに寄付を分割する分配では、すべての寄付を集中する場合と比較して、単一のアカウントで達成可能なピーク値しか減少しません。 したがって、最適な戦略は、初期値が最も高いアカウントにすべての拠出を割り当て、最終的な答えを max(ri) + sum(di) にすることです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    r = list(map(int, input().split()))
    d = list(map(int, input().split()))
    
    best = max(r)
    total = sum(d)
    
    print(best + total)

if __name__ == "__main__":
    solve()
```実装は簡単です。初期評価を 1 回スキャンして最大値を見つけ、コンテスト デルタを 1 回スキャンして合計を計算します。 結果は、これら 2 つの値の合計になります。 並べ替えやシミュレーションは必要ありません。 

よくある間違いは、コンテストごとに課題をシミュレートしようとしたり、アカウントごとの更新を追跡しようとしたりすることですが、これは不必要であり、TLE の危険性があります。 もう 1 つの間違いは、正の di と負の di を別々に分配しようとすることですが、これは合計が不変であり、代入から独立していることを無視しています。 

## 実用的な例

 ### 例 1

 入力:

 r = [1500, 1500]

 d = [300、-300]

 次のように計算します。 

| ステップ | 最高の評価 | 和 | 現在の答え |
 | --- | --- | --- | --- |
 | 初期化 | 1500 | 0 | 1500 |
 | 合計後 | 1500 | 0 | 1500 |

 最終結果は1500です。 

これは利益と損失が相殺されるケースを示しています。 1 つのコンテストがポジティブで、もう 1 つがネガティブなコンテストであっても、両方ともどこかに割り当てられる必要があり、合計の最終的な効果はゼロになります。 達成可能な最高の最大値は、初期の最高の評価のままです。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    r = list(map(int, input().split()))
    d = list(map(int, input().split()))
    return str(max(r) + sum(d))

 ## 特殊なケース

 重要なエッジケースは、すべての di が負の場合です。 たとえば、ri = [100, 90] および di = [-10, -20] の場合、アルゴリズムは最大 ri = 100 および合計 di = -30 を計算し、70 を生成します。実行により、すべての更新が概念的に最適なアカウントに割り当てられ、100 ～ 30 が得られます。アカウント間でネガティブを分散しようとしても、すべてのネガティブが依然としてどこかに割り当てられている必要があるため、最大値は改善されません。 

もう 1 つのエッジケースは、アカウントが 1 つしかない場合です。 この場合、すべてのコンテストをそれに割り当てる必要があるため、答えは r1 + sum(di) になります。 max(r) は r1 であるため、アルゴリズムはこれを自然に処理します。 

最後のエッジケースは、すべての di がゼロの場合です。 システムは何もせず、答えは単純に最大初期評価になります。 sum(di) がゼロで最大値が変化しないため、アルゴリズムは正しく減少します。
