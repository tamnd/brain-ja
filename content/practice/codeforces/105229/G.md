 ## 解決策
 ## 問題の理解

 上に単調なパスが何本存在するかを数えるように求められます。$n \times n$左下隅からのグリッド$(0,0)$右上隅に$(n,n)$, ここで、移動するたびに、x 座標または y 座標のいずれかが 1 だけ増加します。 

この複雑機構は、グリッド ポイント上に配置された最大 10 個の不動の「ナイト ピース」のセットによって実現されます。 パスは、訪問した時点ですべての訪問ポイントが安全である場合にのみ有効です。 これらの駒は中国のチェスの騎士のようにブロッキング ルールで攻撃するため、安全性は動的です。騎士によるある方向へのジャンプは、中間の「脚」のマスが空の場合にのみ有効になります。 移動中に駒を削除できるため、パスが進むにつれて攻撃パターンが変化します。 

重要な点は、ナイトの位置に足を踏み入れることが許可され、即座にそのナイトをボードから削除することです。 削除されると、以降のステップでの攻撃に寄与しなくなります。 これにより、安全制約の履歴が静的ではなく依存するようになります。 

グリッドのサイズは各次元で最大 100 ですが、ナイトの数は最大 10 です。これは、ナイトのサブセットの数がわずかであるため、ナイトのすべての構成にわたる直接状態追跡が実現可能であることをすぐに示唆しています。$2^{10} = 1024$。 ただし、単調パスの数だけでも指数関数的に増加するため、単純なパスの列挙は不可能です。$n$、 だいたい$\binom{2n}{n}$、それはすでに約$10^{58}$いつ$n=100$。 

単純なアプローチでは、すべてのパスをシミュレートし、ナイトが除去されるときにどのマスが攻撃されるかを動的に更新しようとします。 これは、異なる残りのナイト セットで同じセルに到達する可能性があり、それらの状態が大幅に異なるため、失敗します。 微妙なエッジケースは、ナイトを踏むとその後の動きがブロックされる攻撃を無効にする場合です。 たとえば、2 人の騎士は、どちらかが先に捕らえられているかどうかに応じて、お互いの攻撃ラインをブロックできます。 攻撃を静的として扱うソリューションは、有効なパスを誤って拒否します。 

もう 1 つの失敗例は、キャプチャの順序付け効果を無視したことに起因します。 パスが早い段階でナイトを通過すると、以前は安全ではなかったグリッドの広い領域が「ロック解除」される可能性があります。 グリッド セル上の静的な DP だけでは、この依存関係を表すことはできません。 

## アプローチ

 強引なアイデアは、からのすべての単調なパスをシミュレートすることです。$(0,0)$に$(n,n)$。 各ステップで、現在の生存しているナイトのセットの下で次のセルが攻撃されているかどうかを確認し、セルにナイトが含まれている場合はそれを削除します。 これはルールに正確に従っているため、論理的には正しいです。 

ただし、単調パスの数は$\binom{2n}{n}$、これは指数関数的です$n$。 たとえ$n=30$、これは実行不可能になります。$n=100$それはまったく不可能です。 各ステップでは、最大 10 人のナイトからの攻撃範囲を再計算する必要もあり、事態はさらに悪化します。 

重要な観察は、グリッドの動きが単調であるため、座標に対して動的計画法を使用できるということです。 唯一欠けている要素は、攻撃の制約がどの騎士がまだ生きているかに依存することです。 ナイトは最大 10 個であるため、完全なシステム状態は残りのナイトのサブセット マスクとして表すことができます。 これにより、問題が階層化された DP に変換されます。$(x, y, \text{mask})$。 

攻撃の有効性はサブセットのみに依存するため、ナイトのサブセットごとに、どのグリッド セルが攻撃されるかを事前に計算できます。 その後、トランジションは標準のグリッド DP になり、ナイトに足を踏み入れたときに更新される追加の次元が追加されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースパス |$O(\binom{2n}{n} \cdot m)$|$O(n)$| 遅すぎる |
 | グリッド上のビットマスク DP |$O(n^2 \cdot 2^m \cdot m)$|$O(n^2 \cdot 2^m)$| 承認済み |

 ## アルゴリズムのチュートリアル

 DP テーブルを定義します。`dp[x][y][mask]`セルに到達する有効な方法の数を表します$(x,y)$まさに騎士のセットで`mask`まだ生きています。 

### 1. ナイトの位置とインデックス付けを事前計算する

 各ナイトに 0 から 0 までのインデックスを割り当てます。$m-1$。 これにより、ビットマスクを使用して生死ステータスを表現できるようになります。 また、素早い検索のために座標も保存されます。 

### 2. すべてのマスクの攻撃マップを事前計算する

 ナイトのサブセットごとに、ブール グリッドを計算します。`attacked[mask][x][y]`セルかどうかを示す$(x,y)$まさにその騎士たちが生きているときに攻撃されます。 

サブセット内の各ナイトについて、考えられる 4 つの動きパターンをシミュレートします。 各パターンでは、「脚」の正方形が同じサブセット内の別のナイトによって占有されているかどうかを確認する必要があります。 足がブロックされている場合、その方向は無効です。 

このステップは、DP の移行中に攻撃を繰り返し再計算する必要がなくなるため、非常に重要です。 

### 3. DP の初期化

 から始めます$(0,0)$騎士全員が生きている状態で。 初期状態は次の場合にのみ有効です。$(0,0)$フルマスクの下では攻撃されません。 この問題ではナイトが開始できないことが保証されているため、$(0,0)$、設定しました`dp[0][0][full_mask] = 1`。 

### 4. グリッド上の DP 遷移

 セルを昇順に繰り返します。$x + y$、先行処理がすでに計算されていることを確認します。 州ごとに$(x,y,mask)$、右と上に移動しようとします。 

に移動するたびに、$(nx, ny)$、次の 2 つの可能性を考えます。 

目的地に騎士がいる場合$k$、現在攻撃されていない場合にのみ、そこに足を踏み入れることが許可されています。`mask`に移行します。`mask without k`。 

宛先が空の場合は、次の条件で攻撃されないようにする必要があります。`mask`、同じマスクを使い続けています。 

これにより、「エントリ時のキャプチャ」ルールが正しくキャプチャされます。 

### 5. 最終的な答えを蓄積する

 結果はすべての合計です`dp[n][n][mask]`残りの騎士のサブセットで終了する可能性があるため、すべてのマスクに適用されます。 

### なぜ効果があるのか

 あらゆる時点で、DP 状態は、将来の有効性に影響を与える情報 (位置と生存騎士数) を正確にエンコードします。 攻撃動作は生きている騎士とその位置のみに依存し、動きは単調なので再訪問は発生しないため、2 つの部分的な経路は同じに到達します。$(x,y,mask)$将来の可能性という点では同等です。 これにより、最適な下部構造が確保され、二重カウントが防止されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

n, m = map(int, input().split())
horses = [tuple(map(int, input().split())) for _ in range(m)]

pos_to_idx = {horses[i]: i for i in range(m)}

# precompute subsets
max_mask = 1 << m

# knight move patterns with leg checks
moves = [
    (2, 1, 1, 0),
    (2, -1, 1, 0),
    (-2, 1, -1, 0),
    (-2, -1, -1, 0),
    (1, 2, 0, 1),
    (-1, 2, 0, 1),
    (1, -2, 0, -1),
    (-1, -2, 0, -1),
]

attacked = [[[False] * (n + 1) for _ in range(n + 1)] for _ in range(max_mask)]

for mask in range(max_mask):
    occ = [[False] * (n + 1) for _ in range(n + 1)]
    for i in range(m):
        if mask & (1 << i):
            x, y = horses[i]
            occ[x][y] = True

    for i in range(m):
        if not (mask & (1 << i)):
            continue
        x, y = horses[i]
        for dx, dy, lx, ly in moves:
            lx0, ly0 = x + lx, y + ly
            tx, ty = x + dx, y + dy
            if 0 <= lx0 <= n and 0 <= ly0 <= n:
                if occ[lx0][ly0]:
                    continue
            if 0 <= tx <= n and 0 <= ty <= n:
                attacked[mask][tx][ty] = True

dp = [[[0] * max_mask for _ in range(n + 1)] for _ in range(n + 1)]

full = max_mask - 1
dp[0][0][full] = 1

for x in range(n + 1):
    for y in range(n + 1):
        for mask in range(max_mask):
            cur = dp[x][y][mask]
            if not cur:
                continue

            for dx, dy in [(1, 0), (0, 1)]:
                nx, ny = x + dx, y + dy
                if nx > n or ny > n:
                    continue

                if attacked[mask][nx][ny]:
                    continue

                if (nx, ny) in pos_to_idx:
                    k = pos_to_idx[(nx, ny)]
                    nmask = mask & ~(1 << k)
                else:
                    nmask = mask

                dp[nx][ny][nmask] = (dp[nx][ny][nmask] + cur) % MOD

ans = 0
for mask in range(max_mask):
    ans = (ans + dp[n][n][mask]) % MOD

print(ans)
```実装は DP 定義に直接準拠します。 事前計算ステップでは、DP ループが O(1) 安全性チェックのみを必要とするように、各サブセットの攻撃マップを構築します。 マスクを変更するのは前者のみであるため、トランジションではナイトに足を踏み入れるか、空のセルに足を踏み入れるかを注意深く区別します。 

よくある落とし穴は、攻撃マップが元の構成だけでなくサブセットに依存することを忘れていることです。 もう 1 つの微妙な問題は、レッグ スクエアとターゲット スクエアの両方で境界が一貫してチェックされるようにすることです。

 ## 特殊なケース

 重要なエッジケースは、ナイトに足を踏み入れると、将来の合法性が劇的に変わる場合です。 マスクは入力時にすぐに更新され、攻撃テーブルは常に現在のマスクのみを使用してクエリされるため、アルゴリズムはこれを処理します。 たとえば、セルが以前は完全なマスクの下では安全ではなかったが、以前にブロッキング ナイトを捕らえた後に安全になった場合でも、DP はチェックのみを行うため、引き続きそのセルを正しく許可します。`attacked[mask][x][y]`。 

もう 1 つのエッジ ケースは、複数のナイト間で攻撃範囲が重複していることです。 各サブセットは個別にアタック グリッドを再計算するため、重複する影響は二重にカウントされることなく自然にマージされます。 

最後のエッジ ケースは、異なる残りのナイト セットで終了するパスです。 DP は最後にすべてのマスクを合計し、残りのナイトが決して遭遇せず、パス全体で生存し続ける場合を含め、有効なエンドポイント構成が失われないことを保証します。
