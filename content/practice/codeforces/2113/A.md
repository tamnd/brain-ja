 ## 解決策
 ## 問題の理解

 一定の温度で開始するグリルと、無制限に繰り返し調理できる2種類のシャシリクが与えられます。 一部を調理するたびに、まず現在の温度が十分に高いかどうかを確認し、その後グリルの温度が下がります。 2 つのタイプは、必要な最低開始温度とグリルから消費する熱量の両方が異なります。 

課題は、グリルが冷えすぎてどちらの要件も満たせない前に、調理する部分の合計数を最大化できるように、2 つのタイプを調理する順序を決定することです。 

重要な点は、各タイプの固定数を事前に選択していないことです。 気温は継続的に低下するため、あらゆる決定が将来の可用性に影響します。 これにより、この問題は単純なカウント演習ではなく、順序付けと貪欲な最適化の問題になります。 

制約は、最大 10^9 の値を持つ 10^4 テスト ケースまで適用されます。 これにより、単純な方法で各ステップで両方の選択を繰り返し試行するシミュレーションは即座に除外されます。 ステップごとのシミュレーションはテスト ケースごとに O(k) まで低下する可能性があり、k が大きいと速度が非常に遅くなります。 私たちは、同一の決定を 1 つずつシミュレートするのではなく、長いシーケンスの同一の決定を推論するソリューションを必要としています。 

要件と効率の両方において一方のタイプの方が厳密に劣る場合、たとえば、より高い温度を必要とするが、さらに温度を下げる場合など、微妙なエッジ ケースが発生します。 その場合、最初にそれを調理するのが最適であることは決してありませんが、現在利用可能なタイプを常に選択する単純な貪欲な人は、依然としてそれを選択し、将来の容量を失う可能性があります。 

もう 1 つの注意が必要な状況は、両方のタイプが利用可能であるが、後で一方が利用できなくなる場合です。 早い段階で間違った順序を選択すると、温度が下がるだけなので、将来の多くの操作が永久にブロックされる可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、調理上の決定のあらゆる可能なシーケンスをシミュレートします。 各ステップで、どのタイプが利用可能であるかを確認し、両方の選択肢を再帰的に試し、結果の温度と合計数を追跡します。 これにより、すべての有効なシーケンスが正しく探索されますが、分岐係数は最大 2 であり、深さは大きくなる可能性があり、最悪の場合の温度降下チェーンでは最大 10^9 になる可能性があります。 枝刈りが適用された場合でも、異なるシーケンスを通じて同じ温度に到達できるため、状態空間は巨大なままになります。 

問題の構造により、ブルートフォースは不要になります。 各アクションは温度を永続的に下げます。操作には 2 種類しかありません。 重要な点は、温度降下の点で要件に比べて「コスト効率が高い」操作を常に優先する必要があるということです。そうすることで、将来の柔軟性がより高く保たれるからです。 

これは、貪欲な注文戦略につながります。 両方のタイプが可能な場合には、将来のステップのために高い温度を維持できるため、温度降下が小さい方を優先します。 ただし、必ずしも小さいドロップをグローバルに最初に選択することはできません。遅延しすぎると、要件の制約が高くなって、後でそのタイプを使用できなくなる可能性があるからです。 

そのため、段階的に完全にシミュレーションするのではなく、プロセスを圧縮します。つまり、現在最適なタイプをできるだけ多く繰り返し取得し、温度を一括で更新し、他のタイプがより良くなったり必要になったりした場合に切り替えます。

 ## アルゴリズムのチュートリアル

 各テスト ケースを独立して処理し、各操作をブロック内で何回適用できるかという観点から推論します。

1. まず、どのタイプが温度低下が小さいかを特定します。 タイプ 1 の低下がタイプ 2 以下の場合、タイプ 1 を「貪欲に優先する」オプションとみなします。 温度を維持することは常に将来の有効な操作の回数を延ばすのに役立つため、これは重要です。 
2. 有効である限り、優先されるタイプを使用するよう努めます。 必要な最低温度を維持しながら何回塗布できるかを計算します。 段階的にシミュレーションする代わりに、算術演算から直接最大カウントを計算します。 
3. タイプを適用するたびに、その降下と使用回数を掛けて現在の温度を下げます。 この一括更新は、繰り返されるシミュレーションを置き換えます。 
4. 温度が低すぎるため、または切り替えが有利になったために、優先タイプが使用できなくなったら、他のタイプに切り替えて同じロジックを繰り返します。 
5. 両方のフェーズのすべての操作を合計し、結果を返します。 

微妙な推論のポイントは、ある型が最初に使用するには最適ではなくなると、その型が温度に与える影響は元に戻せないということです。 したがって、順序は動的に切り替えるのではなく、ドロップ サイズを比較することによって完全に決定されます。 

### なぜ効果があるのか

 重要な不変条件は、すべてのステップで、これまでに同じ回数の操作を使用したすべてのシーケンスの中で、可能な限り最高の残留温度を維持することです。 将来の操作の数は現在の温度に単調に依存するため、各ブロックの後で温度を最大に保つことで、他の順序と比較して潜在的な将来の操作が失われることがなくなります。 早期に高ドロップ操作を使用する逸脱は、新しい有効な動きのロックを解除することなく、将来の可用性を低下させるだけです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(k, a, b, x, y):
    ans = 0

    # Decide which type is better to use first (smaller drop is preferred)
    if x < y or (x == y and a <= b):
        first_a, first_b = a, b
        first_x, first_y = x, y
    else:
        first_a, first_b = b, a
        first_x, first_y = y, x

    # Try greedy for first type, then second type
    for req, dec in [(first_a, first_x), (first_b, first_y)]:
        if k < req:
            continue
        # how many times we can apply this type in a row
        cnt = (k - req) // dec + 1
        ans += cnt
        k -= cnt * dec

    return ans

def main():
    t = int(input())
    for _ in range(t):
        k, a, b, x, y = map(int, input().split())
        print(solve_case(k, a, b, x, y))

if __name__ == "__main__":
    main()
```実装は、温度低下に基づいてどのタイプを優先するかを決定することから始まります。 タイブレーカーでは要件も使用されます。これは、両方が同じように低下​​した場合、要件が低いタイプが常に少なくとも同等に使用できるためです。 

その後、ループする代わりに、単純な算術式を使用して連続使用回数を計算します。 少なくとも 1 回調理できた場合、最後の有効なステップは温度がまだ要件を超えているときであるため、カウントは次のようになります。`(k - req) // dec + 1`。 

ワンショットで合計温度降下を差し引くことで、反復シミュレーションを行わなくても状態が正しく遷移することが保証されます。 これにより、時間の問題と変動境界エラーの両方が回避されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        k, a, b, x, y = map(int, input().split())
        # same logic as solution
        def solve(k, a, b, x, y):
            if x < y or (x == y and a <= b):
                req1, dec1 = a, x
                req2, dec2 = b, y
            else:
                req1, dec1 = b, y
                req2, dec2 = a, x

            ans = 0
            if k >= req1:
                c = (k - req1) // dec1 + 1
                ans += c
                k -= c * dec1
            if k >= req2:
                c = (k - req2) // dec2 + 1
                ans += c
            return ans

        out.append(str(solve(k, a, b, x, y)))
    return "\n".join(out)

 ## 特殊なケース

 エッジ ケースの 1 つは、両方のタイプのドロップ値は同じだが、要件が異なる場合です。 この状況では、アルゴリズムは要件が低いものを最初に優先し、早期のブロックが発生しないようにします。 たとえば、`k=50, a=10, b=5, x=y=2`、アルゴリズムは最初にタイプ b を使用し、`(50-5)//2 + 1 = 23`その後、残りの温度でタイプ a に切り替わります。 

もう 1 つのケースは、最初は 1 つのタイプのみが有効であるが、もう 1 つのタイプを 1 回使用した後に無効になる場合です。 バルク式は、両方が使用可能なままであると仮定するのではなく、温度を更新した後に実現可能性を再計算するため、これを自然に処理します。 

最後のケースは、どちらのタイプも最初は使用できない場合です。`k=5, a=10, b=12`。 最初のチェックで両方の条件が失敗するため、アルゴリズムはすぐにゼロを返し、無効な算術ループや負のループを回避します。
