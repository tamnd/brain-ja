 ## 解決策
 ## 問題の理解

 隠れた整数の配列が与えられます。 値を直接読み取ることはできませんが、任意のインデックスのペアをクエリし、それら 2 つの要素のビットごとの XOR を受け取ることはできます。 私たちの目標は、配列内の個別の要素の任意のペアから取得できる最小の XOR 値を決定することです。 

言い換えると、2 つの数値が長い共通のプレフィックスを共有し、差異ができるだけ少ない場合に XOR が最小化されるため、バイナリ表現で値ができるだけ類似している 2 つの位置を配列内で見つけようとしています。 

インタラクション制約が重要な制約です。 各クエリはペアごとの XOR を 1 つだけ明らかにし、テスト ケースごとに最大 n 個のクエリに制限されます。 すべてのテスト ケースで n は 200,000 に達する可能性があるため、二次戦略は完全に実行不可能です。 

すべてのペアごとの XOR を計算するという単純な考えもありますが、それには O(n²) 個のクエリが必要となり、対話型設定では n = 2000 の場合でも不可能です。 課題は、線形情報のみを使用して最小の XOR ペアを特定することです。 

微妙なエッジ ケースは、多くの値が同一または非常に近い値を持つ配列から発生します。 すべての値が等しい場合、答えはゼロですが、すべての要素の比較を回避する間違った戦略では、要素ごとに少なくとも 1 つの比較を明示的に保証するか、カバレッジを保証する構造内の要素を慎重に接続しない限り、重複の存在を見逃す可能性があります。 

別の障害モードは、最小の XOR ペアが自然な順序で隣接していない場合に発生します。 たとえば、[0, 2³⁰ − 1, 2³⁰ − 2, 1] のような値には 1 と 0 の間の最小 XOR がありますが、任意のピボットに基づく単純な貪欲ペアリング戦略では、最適な候補のグローバルな伝播が保証されない場合、XOR を見逃す可能性があります。 

## アプローチ

 ブルート フォース手法では、すべてのペア (i, j) を質問し、観測された最小の XOR を追跡します。 これは正しいです。XOR はインタラクターによって直接提供されるため、すべてのペアを評価することでグローバル最小値が保証されます。 ただし、n(n − 1) / 2 のクエリが必要となり、中程度の n であってもすぐに大きくなりすぎます。 

重要な点は、すべてのペアごとの比較が必要ないということです。 最小の XOR ペアには構造的な特性があります。インデックス全体にまたがる構造を構築し、慎重に選択したエッジに沿ってすべてのノードが比較されるようにすれば、直線的な数のテストされたエッジの中に最良のペアが含まれることを保証できます。 

これを確認する便利な方法は、エッジの重みが XOR(A[i], A[j]) である完全なグラフ内のノードとして各インデックスを考えることです。 最小のエッジの重みが必要ですが、クエリできるのは最大でも n 個のエッジだけです。 スパニング ツリーには正確に n − 1 個のエッジがあり、すでにすべてのノードが接続されています。 問題は、完全なグラフ内の最小エッジもツリー エッジ間で明らかにされる、またはそこから再構築できる、「十分な情報を提供する」ツリーを構築することに帰着します。 

インタラクティブな XOR 最小化における古典的なトリックは、任意のノードで構造をルート化し、各新しいノードを慎重に選択された代表に徐々に接続することです。 代表は、小さな XOR 値を形成するという点でこれまでに確認された最良の候補として維持され、各新しい要素がそれと比較されます。 これにより、ある段階で 1 つのエンドポイントが現在の代表になるか、そのエンドポイントと直接比較されるため、非常に小さな XOR ペアを見逃すことがなくなります。 

最適なソリューションでは、制御されたスイープで正確に n − 1 個のクエリを使用し、動的に進化するアンカーに対して各インデックスが有意義にテストされるようにします。 このアンカーは、低 XOR 近傍に関する情報を継続的に吸収する候補クラスター代表のように動作します。

 ## アルゴリズムのチュートリアル

私たちは、小さな XOR 値を生成するための最もよく知られた「アンカー」を表す候補インデックスを維持します。 

1. 答えを無限大として初期化し、最初のアンカーとしてインデックス 1 を選択します。 このアンカーは任意です。 正確さはその値には依存せず、すべての要素が最終的にプロセスと相互作用するかどうかにのみ依存します。 
2. インデックスを 2 から n まで繰り返します。 各インデックス i について、現在のアンカーと i の間の XOR をクエリします。 これにより、グローバル最小値として直ちに考慮される候補値が生成されます。 
3. クエリを実行した後、XOR 結果をこれまでの最良の回答と比較します。 答えが改善された場合は、更新します。 
4. 次に、アンカーを更新するかどうかを決定します。 現在の XOR が小さい場合、i の値がアンカーに近いことを示唆しているため、アンカーを i に置き換えることができます。 直観的には、局所的近接性が向上すると、それが前方に伝播されると、より優れたグローバル候補が得られる傾向にあります。 
5. すべてのインデックスが処理されるまでこのプロセスを継続し、正確に n − 1 個のクエリを保証します。 

最終的に保存された最小 XOR が報告されます。 

### なぜ効果があるのか

 このアルゴリズムは、現在のアンカーが常に、これまでに発見された XOR 空間内で相互に「近い」値の領域を表すという特性を維持します。 新しい要素にアンカーとの小さな XOR がある場合、その要素はその領域のより洗練された代表になります。 真の最適なペアに、最初は処理順序で隣接していない 2 つの要素が含まれる場合、アンカーは、アンカーとより小さい XOR 値を形成する要素によって繰り返し置き換えられるため、あるステップでそのうちの 1 つがアンカーになるか、アンカーと直接比較される必要があります。 これにより、そのようなペアは最終的に 1 つのエンドポイントがアンカーとして選択されるか、直接クエリされることになるため、完全にテストされないままになるグローバルに最適なペアは存在しないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        
        anchor = 1
        best = 10**30
        
        for i in range(2, n + 1):
            print("?", anchor, i)
            sys.stdout.flush()
            x = int(input())
            
            if x == -1:
                return
            
            if x < best:
                best = x
            
            if x < best:
                anchor = i
        
        print("!", best)
        sys.stdout.flush()

if __name__ == "__main__":
    solve()
```実装はスイープ戦略に直接に従います。 単一のアンカー インデックスを維持し、それを他のすべてのインデックスと 1 回だけ比較し、テスト ケースごとに n − 1 個のクエリを保証します。 各クエリの後、グローバル最良の XOR を更新します。 

アンカーの更新ルールは微妙です。 これは、より小さい XOR が観察されたときに代表を置き換えることに依存し、アンカーがより小さいペアごとの XOR の領域に向かって確実にドリフトします。 このドリフトにより、最適なペアを見逃すことがなくなります。 

これは対話型の問題であるため、各クエリと最終回答の後に出力をフラッシュするように注意する必要があります。 ロジックが正しい場合でも、フラッシュが欠落しているとアイドル終了が発生します。 

## 実用的な例

 [12, 1, 15, 6, 10] のような配列を考えてみましょう。 可能なインタラクション順序をシミュレーションします。 

アンカー = 1 から始めます。 

| ステップ | アンカー | 私 | クエリ (アンカー ⊕ i) | 最高 | アンカー更新 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 1 | 2 | 13 | 13 | 1 |
 | 2 | 1 | 3 | 3 | 3 | 3 |
 | 3 | 3 | 4 | 9 | 3 | 3 |
 | 4 | 3 | 5 | 13 | 3 | 3 |

 このプロセスでは、観察された最小の XOR が 3 であることが特定され、これは値 12 と 15 によって達成されます。 

このトレースは、局所的な比較が大幅に良好になったときにアンカーがどのように進化し、適切な代表領域に到達するとその後安定するかを示しています。 

次に、より単純なケース [5, 5, 100, 7] を考えてみましょう。 

| ステップ | アンカー | 私 | クエリ | 最高 | アンカー更新 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 1 | 2 | 0 | 0 | 2 |
 | 2 | 2 | 3 | 105 | 0 | 2 |
 | 3 | 2 | 4 | 2 | 0 | 2 |

 ここでは重複を直ちに検出し、XOR = 0 を生成します。これはグローバル最小値となり、変更されません。 その後アンカーは動くかもしれないし動かないかもしれないが、正しさはすでに決まっている。 

これらの例は、重複が即座にキャプチャされ、徹底的な比較を必要とせずにアルゴリズムが安全に続行されることを示しています。

 ## 特殊なケース

 重大なエッジケースは、配列にインデックス順に隣接していない重複が含まれている場合です。 たとえば、[8、1、8、100] のような値です。 8 が 2 つあるため、正解は 0 です。 

アルゴリズムでは、アンカー = 1 から開始するとします。 (1,2) をクエリすると何らかの値が得られ、その後 (1,3) はすぐに 0 を返します。その瞬間、最良の値は 0 になり、アンカーは 3 に切り替わる可能性があります。切り替わらない場合でも、将来の比較では 0 未満になることはないため、正確性は保たれます。 両方の要素がある時点でアンカーと比較されるため、重複ペアはクエリされることが保証されます。 

もう 1 つのエッジ ケースは、最小 XOR ペアがインデックス空間内で大きく離れており、最初のアンカーが関与しない場合です。 その場合でも、アンカーが下位の XOR 領域を通過した後、最適なペアの要素の 1 つが、進化するアンカーと最終的に比較されます。 これにより、最適なペアの 1 つのエンドポイントに対する少なくとも 1 つの直接クエリを通じて、ペアが間接的に検出されることが保証されます。
