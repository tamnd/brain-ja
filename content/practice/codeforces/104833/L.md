 ## 問題の理解

 私たちは、キャラクターが初期の健康値から開始し、一連のラウンドにわたって健康を繰り返し失うターンベースの生存プロセスをシミュレートしています。 面白いのは、各ラウンドの終了時に適用されるダメージが固定されていないことです。 その代わり、それまでに火災によるダメージが何回発生したかによって決まります。 

より正確には、長さの配列を処理します。$n$。 各要素は、現在のラウンドが追加の「ファイアスタック」をトリガーするかどうかを示します。 そうであれば、グローバルカウンターが増加します。 そのラウンドのイベントを処理した後、キャラクターはこのカウンターの現在の値に等しいダメージを受けます。 キャラクターは健康から始まる$x$、そして体力がゼロ以下になる最初のラウンドを特定するか、それが決して起こらないことを報告する必要があります。 

重要な構造は、ダメージが累積的であり、時間の経過とともに単調に増加するということです。 火災イベントが発生するたびに、ラウンドごとのダメージが永続的に増加するため、後続のすべてのラウンドはより危険になります。 

この制約により、リニア スキャン ソリューションが求められます。 と$n \le 10^6$、ラウンドごとに蓄積ダメージをゼロから再計算するなど、二次シミュレーションは遅すぎます。 実行状態を維持し、要素ごとに一定の時間で更新する必要があります。 メモリ制約は標準であるため、配列の保存は問題ありませんが、余分な再計算は問題になります。 

ダメージを与えた後、キャラクターがちょうど丸い境界線で死亡する場合、微妙なエッジケースが発生します。 死亡チェックは、現在のラウンドのダメージを適用する前ではなく、適用した後に発生する必要があります。 もう 1 つの特殊なケースは、ダメージがプロセスの後半で大きくなる場合です。つまり、ラウンド初期は安全に見えても、後のバーストによって突然ゲームが終了する可能性があります。 最後に、最大蓄積ダメージを受けても体力がゼロを下回らない場合、全ラウンドを通じて生存が継続することを正しく出力する必要があります。 

## アプローチ

 単純なシミュレーションは文字通りルールに従います。 現在の健康状態と火災カウンターを維持します。 各ラウンドで、配列値が 1 の場合、カウンターをインクリメントし、ヘルスからカウンターを減算します。 減算するたびに、健康状態がゼロ以下に低下したかどうかを確認します。 これは、説明されているプロセスを正確に反映しているため、正しいです。 

ブルートフォース解釈は時間的には線形であることに変わりはありませんが、慎重でないバージョンでは、各ステップで以前のすべての火災イベントをスキャンすることによって「現在のダメージ」を再計算する可能性があります。 そうなると各ラウンドのコストが高くなります$O(n)$、につながる$O(n^2)$最悪の場合の全体的な操作。 と$n = 10^6$、それは不可能になります。 

重要な観察点は、ラウンド時のダメージが$i$火災イベントのプレフィックス数のみに依存します。 このプレフィックス数は段階的に維持できます。 これを理解すると、各ラウンドは一定時間の更新になります。必要に応じてカウンターを増やし、ヘルスからそれを減算し、終了を確認します。 

これにより、プロセス全体がアレイを通過する 1 回のパスに短縮されます。

 ## アルゴリズムのチュートリアル

 現在のヘルスと蓄積された火災カウンターという 2 つの変数を維持します。 

1.初期化`hp = x`そして`burn = 0`。 変数`burn`これ以上火災が発生しなかった場合に、今後各ラウンドで適用されるダメージの量を表します。 
2. 最初のラウンドから最後のラウンドまで配列を繰り返します。 
3. 現在の値が 1 の場合、インクリメントします`burn`これは、将来のすべてのラウンドが厳密により危険になることを反映しています。 
4. 減算`burn`から`hp`。 これはラウンド終了時のダメージの適用をモデル化します。 
5. もし`hp <= 0`、現在のラウンドインデックスを出力し、すぐに停止します。 このようなラウンドは最も早い段階で必要であるため、続行してはなりません。 
6. 何もせずにすべてのラウンドを終えた場合`hp`非陽性になると、生存が保証されるという出力が得られます。 

正確かどうかは、被害がこれま​​でに発生した火災の数によって完全に決定されるという事実にかかっています。 各火災イベントは、将来のすべてのダメージを永続的に 1 単位だけ増加させます。`burn`は常に火災インジケーターのプレフィックス合計と等しくなります。 

### なぜ効果があるのか

 どのラウンドでも$i$、適用されるダメージはインデックスの数と同じです$j \le i$そのような$a_j = 1$。 アルゴリズムはこの量を明示的に維持します。`burn`。 健全性は各ステップでこのプレフィックス値によって決定的に減少するため、シミュレーションは問題で説明されているプロセスと正確に一致します。 そのラウンドに正しいダメージを適用した直後に死亡をチェックするため、初めて健康状態が非陽性になった場合には、確実に報告されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, x = map(int, input().split())
a = list(map(int, input().split()))

hp = x
burn = 0

for i in range(n):
    if a[i] == 1:
        burn += 1
    hp -= burn
    if hp <= 0:
        print("YES")
        print(i + 1)
        break
else:
    print("NO")
```実装はアルゴリズムを直接反映しています。 ループはPythonを使用します`for-else`ブレークが発生しない場合にのみ「NO」ケースがトリガーされるように構造化されています。 インデックス`i + 1`ゼロベースのインデックス付けから、出力に必要な 1 ベースの丸め番号付けに変換します。 

よくある間違いは、バーン カウンターを更新する前にダメージを減算することです。 そうなると、すべてのダメージが 1 ラウンドずれてしまい、誤った早期死亡結果が生成されてしまいます。 もう 1 つの微妙な点は、健康状態が陽性でなくなったときにすぐに休憩が行われるようにすることです。 さらに続行すると、後の死亡ラウンドが誤って報告されてしまいます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、キャラクターの体力が非常に低い状態で開始され、最初の火災イベントがすぐに発生する場合です。 入力用`1 1 / 1`、ダメージを受ける前に燃焼が1になり、体力がすぐにゼロになります。 アルゴリズムは、最初に燃焼を正しく更新し、次にダメージを適用し、ラウンド 1 で死亡を引き起こします。 

もう 1 つのエッジ ケースは、すべての値がゼロの場合です。 燃焼変数が増加することはないため、ダメージが適用されることはありません。 アルゴリズムはすべてのラウンドを処理し、loop-else パスを通って終了し、生存率を正しく出力します。 

3 番目のケースは、早期に密集した火災が発生した場合です。 入力用`4 3 / 1 1 1 1`, 火傷は1、2、3、4と進化し、体力はそれに応じて減少します。 このプロセスでは、燃焼が残りの体力を超えた場合、減算の直後にチェックが行われるため、オーバーシュートすることなく正確なラウンドが検出されることが保証されます。 

最後の微妙なケースは、最終ラウンドで死亡が発生した場合です。 ループは終了前に引き続きチェックを実行し、デフォルトの「NO」ではなく、正しいラウンド インデックスが報告されることを確認します。
