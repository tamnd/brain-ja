 ## 解決策
 ## 問題の理解

 私たちに与えられたアイテムは非常に小さな世界、ちょうど 8 種類のお土産です。 各タイプの在庫には限りがあり、8 つの整数の配列で表されます。 別途、$n$people, and each person independently requests exactly one of these eight types. その人が検討された時点で、要求されたタイプの在庫がまだ残っている場合、そのタイプのアイテムが 1 つ受け取られ、在庫が 1 つ減ります。 そうでない場合、彼らは何も受け取りません。 

タスクは、与えられた順序で人々を処理すると仮定して、この自然な貪欲な割り当てプロセスの下で何人の人が満足できるかを計算することです。 

The input size is large in terms of number of people, up to$2 \times 10^5$, ただし、アイテムユニバースのサイズは8に固定されています。 これにより、直ちに解空間が制約されます。 一定時間を超えて 1 人当たりの負荷の高い操作をシミュレートしようとするアプローチは、それが厳密に線形を維持する場合にのみ受け入れられます。$n$。 1 人あたり 8 種類のネストされたスキャンを伴うものは問題ありませんが、一定サイズよりも大きい動的構造に対する 1 人ごとの検索を伴うものは不要なオーバーヘッドになります。 

微妙なエッジケースは、枯渇順序から発生します。 単純にタイプごとにリクエストをカウントし、個別に供給と比較できると単純に解釈すると、それは正しくありません。リクエストは順番に処理され、在庫はグローバルに消費されるためです。 たとえば、タイプ 1 に 1 つのアイテムがあり、2 人がタイプ 1 をリクエストした場合、全体的な推論では世界的な需要が供給と等しい場合でも、最初の商品のみが提供されます。 

もう 1 つの特殊なケースは、一部のタイプの在庫がゼロである場合です。 これらのタイプのリクエストは、たとえシーケンスの早い段階で出現したとしても、常に失敗する必要があります。 たとえば、次の場合$a_3 = 0$誰かがタイプ 3 をリクエストした場合、注文やその他の可用性に関係なく、それらは決してカウントされるべきではありません。 

## アプローチ

 直接シミュレーションは、問題文の後に文字通り続きます。 サイズ 8 の残りの在庫配列を維持します。 次に、すべてを繰り返します$n$人々。 ご希望の種類の在庫がまだあるかどうかを一人ひとり確認させていただきます。 「はい」の場合、それをデクリメントし、答えをインクリメントします。 

これが機能するのは、各決定がそのタイプの現在の残り容量のみに依存するためです。 各操作は O(1) であるため、プロセス全体は O(n) であり、十分に制限内にあります。 

よくある間違った考え方は、タイプごとにカウントを集計してから計算することです。$\sum \min(\text{demand}_i, a_i)$。 これは型間に相互作用がない場合にのみ順序付け制約を無視しますが、ここでは相互作用は型ごとに厳密にローカルです。 この特定の問題では、異なるタイプが同じ株式をめぐって競合することがないため、その集計は実際に正しくなります。 唯一の相互作用は、各タイプ内で独立して行われます。 これは、プロセスを 8 つの独立したキューとして見ることができ、それぞれが到着順に独自の在庫を消費することを意味します。 ただし、タイプごとの頻度カウントの実装は、直接シミュレーションに比べて不必要に複雑になります。 

本当の洞察は、状態空間がわずか 8 つの整数であるため、パフォーマンスを心配することなく安全に逐次シミュレーションできるということです。

 ## アルゴリズムのチュートリアル

 説明どおりに割り当てプロセスを正確にシミュレートします。 

1. 配列を初期化する`stock`サイズ 8 には、各アイテム タイプの利用可能な数量が含まれます。 これは、任意の時点での各お土産タイプの残容量を表します。 
2. カウンタの初期化`ans = 0`何人の人がサービスを受けられたかを追跡するため。 
3. 各人物を順番に繰り返します。 人向け$i$、要求されたタイプを読み取ります$b_i$。 早期に使用すると、後のリクエストの可用性が低下するため、この順序は重要です。 
4. かどうかを確認します。`stock[b_i] > 0`。 割り当てられている場合は、デクリメントしてそのアイテムをこの人に割り当てます。`stock[b_i]`そして増加する`ans`。 
5. もし`stock[b_i] == 0`、そのタイプは使い果たされており、それ以上の要求を満たすことができないため、何も行いません。 
6. 全員を処理したら出力`ans`。 

重要な考え方は、各ストック バケットは独立して進化しますが、その進化はリクエストの時系列順に依存するということです。 このプロセスは到着順序に関して純粋に貪欲であるため、リクエストを先読みしたり並べ替えたりする必要はありません。 

### なぜ効果があるのか

 各タイプは、固定容量を持つ独立したリソースのように動作します。 タイプのリクエストのたびに$x$到着した後、重要な唯一の制約は、残りの容量があるかどうかです。$x$はポジティブです。 どのリクエストも他のタイプの在庫に影響を与えることはできないため、決定はタイプ間で独立しています。 アルゴリズムは、次の不変条件を保持します。`stock[i]`常に、元の量からそのタイプで受け入れられたリクエストの数を引いたものと等しくなります。$i$これまで見られた。 これにより、どの型も過剰に割り当てられることがなくなり、受け入れられたすべての割り当てが実際に使用可能なユニットに対応することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    b = list(map(int, input().split()))
    a = list(map(int, input().split()))

    stock = a[:]  # 8 types
    ans = 0

    for x in b:
        x -= 1  # convert to 0-index
        if stock[x] > 0:
            stock[x] -= 1
            ans += 1

    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは、人数、リクエスト、そして 8 種類の品目ごとに利用可能な在庫を読み取ります。 唯一の微妙な実装の詳細は、入力の 1 インデックス付き型から 0 インデックス付きの配列アクセスへの変換です。 残りは、貪欲な割り当てルールの直接のシミュレーションです。 

各リクエストは 1 回だけ処理され、各チェックは定数時間の配列アクセスです。 状態は 8 要素のストック配列によって完全にキャプチャされるため、追加のデータ構造は必要ありません。

 ## 特殊なケース

 エッジケースの 1 つは、すべての株式価値がゼロになる場合です。 アルゴリズムは引き続きすべてのリクエストを反復処理しますが、すべてのチェックが失敗するため、回答が増加することはありません。 入力用`n = 3`、リクエスト`[1,2,3]`、ストックオールゼロ、不変式`stock[i] >= 0`全体を通して保持し、`ans`はゼロのままで、正しい出力が生成されます。 

もう 1 つのエッジ ケースは、単一のタイプがすべてのリクエストを支配する場合です。 タイプ 1 の在庫が 2 で、5 人全員がタイプ 1 をリクエストした場合、アルゴリズムは在庫を 2 回減らしてから、それ以上のリクエストの受け付けを停止します。 二次受付後、`stock[0]`がゼロになるため、後続の反復では残りのリクエストがすべて正しく拒否されます。 

最後のエッジケースは、在庫がすべてのリクエストに対して十分な大きさである場合です。 その場合、すべてのリクエストは`stock[x] > 0`チェックすると、アルゴリズムは単純にすべてをカウントします。$n$人々は、決して拒否ブランチに到達しないでください。
