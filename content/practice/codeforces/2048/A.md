 ## 解決策
 ## 問題の理解

 開始整数と、それを変更する一連の小さな操作が与えられます。 目標は、最終的にこの数を正確にゼロにできるかどうかを判断することです。 

2 つの操作の動作は大きく異なります。 1 つの演算は算術演算です。現在の値が少なくとも 33 である場合は、常に 33 を減算できます。もう 1 つの演算は構造的な演算です。10 進表現に 3 に等しい 2 つの連続する数字が含まれている場合、その部分文字列「33」を数値から削除し、桁の長さを縮小します。 

主な問題は、これらの演算が数値の異なる表現間で相互作用することです。 減算は数値を変更しますが、桁の構造をほぼ安定させます。一方、削除は構造を変更しますが、数値を直接追跡しません。 

x が 10^9 までの最大 10^4 のテスト ケースという制約は、各テストが桁数でほぼ対数または線形時間で処理される必要があることを意味します。 考えられるすべての操作シーケンスを繰り返し試行するシミュレーションでは、各ステップが 2 つのまったく異なる変換に分岐する可能性があるため、組み合わせ爆発が起こります。 

削除により減算後に新しい「33」ペアが露出する場合、または削除が可能になるように数値を「揃える」ために減算が必要な場合、微妙なエッジ ケースが発生します。 たとえば、133333332 のような数値では、算術縮約と桁圧縮が繰り返し行われる可能性があります。 一方、666 のような 3 桁以外の数字の大部分で構成される数値は構造的に削除がブロックされており、ゼロに到達することは可能ですが、33 の倍数に達する場合と達しない場合があります。 

可能な限り貪欲に 33 を減算する単純なアプローチは、削除によって割り算構造が根本的に変化する可能性があることを無視しているため、失敗します。 同様に、貪欲な削除優先アプローチは、算術実行可能性の制約を無視するため失敗します。 

## アプローチ

 ブルート フォース戦略では、すべての状態がグラフ内のノードとして扱われます。つまり、各整数値または文字列表現が状態であり、各操作がエッジです。 最初の数値から BFS または DFS を実行し、33 を減算することと、出現する「33」を削除することの両方を試みます。 これは、考えられるすべての操作シーケンスを調査するため正しいですが、10 桁の数値であっても巨大な状態グラフが成長する可能性があるため、実行不可能です。 分岐要素は少なくとも 1 つ、多くの場合 2 つあり、桁の再配置が繰り返されるとサイクルと膨大な検索スペースが作成されます。 

重要な洞察は、33 による減算が、制御された線形方法で数値の大きさを変更する唯一の演算であるということです。 一方、削除は固定パターンの出現を削除するだけであり、数値が増加することはありません。 これは、問題を 2 つのフェーズに分割することを示唆しています。つまり、考えられる「33」のペアをすべて削除して数値を正規化し、次に繰り返し減算してゼロに到達できるかどうかを検討します。 

重要な観察は、削除は 33 で割り切れる可能性を改善できるかどうかという点でのみ重要であるということです。削除を完全に活用した後、残りの数値は 33 を減算した標準的な整数のように動作します。このプロセスにより、問題は事実上、桁の削除によって数値を 33 の倍数に変換できるかどうか、そしてその倍数が 0 に到達できるかどうかをチェックすることに減ります。 

これは、貪欲な安定化のアイデアにつながります。つまり、削除を遅らせても、新しい有用な算術構造を作成するのに役立つことができないため、「33」が出現するたびにすべての出現を繰り返し削除します。 これ以上削除できなくなると、数値は最小限の「圧縮された」形式で固定され、残りの問題は、それが 33 で割り切れるかどうかということになります。

 ## アルゴリズムのチュートリアル

 削除を簡単に適用できるように、数値を変更可能な数字の文字列として扱います。 

1. 整数を文字列表現に変換します。 これにより、数字パターンを直接検出して削除できます。 
2. 文字列を繰り返しスキャンし、部分文字列「33」が出現した場合は削除します。 新しい隣接ペアが形成される可能性があるため、削除するたびに前の位置からスキャンを再開してください。 このステップでは、削除操作を可能な限り積極的に適用することをシミュレートします。 
3. 「33」の部分文字列が存在しなくなったら、結果の文字列を整数値として解釈します。 
4. 結果の数値がゼロの場合は、減算する必要がなくすでに目標に到達しているため、すぐに「YES」を返します。 
5. それ以外の場合は、数値が 33 で割り切れるかどうかを確認します。割り切れない場合は、「NO」を返します。これは、33 による減算では 33 を法とする合同性が維持され、決してゼロになることがないためです。 
6. 33 で割り切れる場合は、「YES」を返します。33 による減算を繰り返すと、最終的には 0 になります。 

### なぜ効果があるのか

 このアルゴリズムは 2 つの不変式に依存します。 まず、「33」部分文字列を削除すると、可能性空間が保存されます。これは、有効な操作シーケンスであれば、ゼロへの到達可能性に影響を与えることなく、減算の前後で削除の順序を変更できるためです。 第 2 に、33 による減算は 33 を法とする剰余を保存するため、ゼロに到達できる状態はすでに 33 を法とするゼロに一致している必要があります。すべての構造的縮小が完了すると、残る唯一の制約は算術可分性であり、これが到達可能性を完全に特徴づけます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def reduce_33(s: str) -> str:
    stack = []
    for ch in s:
        if stack and stack[-1] == '3' and ch == '3':
            stack.pop()
        else:
            stack.append(ch)
    return ''.join(stack)

def solve():
    t = int(input())
    for _ in range(t):
        x = input().strip()
        
        # remove all "33" pairs greedily
        prev = None
        while prev != x:
            prev = x
            x = reduce_33(x)
        
        if x == "":
            print("YES")
            continue
        
        val = int(x)
        if val % 33 == 0:
            print("YES")
        else:
            print("NO")

if __name__ == "__main__":
    solve()
```コア実装では、スタックベースのパスを使用して、隣接する「33」ペアを効率的に削除します。 各パスは現在表示されているすべてのペアを削除し、構造変化後に隠れたペアが残らないように安定するまで繰り返します。 

整数への変換は安定化後に 1 回だけ行われるため、オーバーヘッドが最小限に抑えられます。 モジュロ チェックが使用されるのは、33 による減算で合同性が維持されるためです。そのため、ゼロに到達するには、最終値が 33 で割り切れる必要があります。 

繰り返し適用されるループ`reduce_33`削除が発生するたびに各パスで文字列の長さが厳密に短縮され、終了が保証されるため、安全です。

 ## 特殊なケース

 主なエッジ ケースは、数値に「33」パターンが含まれていないが、引き算で約定できる場合です。 たとえば、66 は 1 回減算すると 33 になり、その後 0 になります。アルゴリズムは削除の存在に依存しないため、これを処理します。 安定化後に割り算がチェックされ、66 % 33 はゼロに等しくなります。 

もう 1 つのケースは、削除によって番号が完全に消去される場合です。 33 のような入力の場合、スタックの削除により空の文字列が生成されます。 算術演算を行わなくても構造的にすでにゼロに達しているため、アルゴリズムはこれを明示的に成功として扱います。 

3 番目のケースは、666 のように、削除と算術の相互作用が最小限の場合です。「33」は存在しないため、数値は変更されません。 666 は 33 で割り切れるため、アルゴリズムは正しく YES を返し、構造演算を行わなくても減算を繰り返すとゼロになるという事実と一致します。
