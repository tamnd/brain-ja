 ## 問題の理解

 アクセスシーケンスがあります`a[1..n]`。 選択したキャッシュ容量に対して`m`、LRU キャッシュは、最近使用されたアイテムから最も最近使用されたアイテムまでのアイテムを維持します。 項目にアクセスすると、その項目がリストの最初の項目になります。 キャッシュがすでにいっぱいで、アクセスされた項目が存在しない場合は、最後の項目が削除されます。 

各クエリは容量を与えます`m`提案された LRU リスト。 リストに含めることができるのは次の数未満です`m`末尾のゼロは入力のパディングとしてのみ使用されます。 容量のある固定アクセス シーケンスを処理しているときに、この正確なリストがいつ表示されるかどうかを判断する必要があります。`m`。 

LRU の状態を観察する重要な方法は、逆の方向から見ることです。 実行が処理されたばかりだとします`a[i]`。 位置から開始`i`そして後ろ向きに歩きます。 初めて値に遭遇したとき、それはその値の最後に使用された値です。 最初に見つかった個別の値は LRU リストの先頭、2 番目の個別の値は次の項目、というようになります。 したがって、LRU の容量リストは、`m`最初です`m`スキャン中に個別の値が検出されました`a[i], a[i-1], ...`逆方向、または以下の場合はすべての個別の値`m`が現れました。 

この観察により、クエリごとに個別のリンク リストをシミュレートする必要が完全になくなりました。 

境界は、意図的に十分に小さいものになっています。`O(n^2)`前処理ステップ。 以来`n <= 5000`、二次境界は、1 つのケースに対して最大約 2,500 万回の反復を意味します。 公式の制限時間はわずか 1 秒であるため、すべてのクエリの単純なシミュレーションは不必要にコストがかかり、三次解は明らかに不可能です。 クエリリスト要素の合計数は最大で次のとおりです。`2 * 10^6`、そのため、クエリ リスト自体を読み取ってハッシュすることは手頃な価格です。 の合計`n`そして`q`テスト ケース全体も制限されているため、二次前処理全体が管理可能に保たれます。 

見落としがちなエッジケースがいくつかあります。 

まず、空の要求リストは有効です。 考慮する：```

1
1 0
```キャッシュは最初は空なので、答えは次のようになります。`Yes`。 最初のアクセス後の状態のみをチェックし、キャッシュに何かが含まれている必要があると想定するソリューションでは、誤って出力されます。`No`。 意図したソリューションでは、最初の空のキャッシュも有効な時点として扱います。 

次に、クエリにはその容量よりも少ない要素を含めることができます。 例えば：```
1
3 1
1 2 3
3 1 2 0
```答えは`Yes`。 アクセス直後`2`、容量のキャッシュ`3`のみが含まれます`[2, 1]`。 不注意な実装では、容量が 3 であるため、キャッシュにちょうど 3 つの要素が必要になる可能性がありますが、これは誤りです。 

第三に、本物の LRU リスト内では重複した値が発生することはできません。 例えば：```

## アプローチ

 直接的なアプローチは、すべてのクエリを個別に処理することです。 容量のあるクエリの場合`m`、すべてを通じて LRU キャッシュをシミュレートできます。`n`にアクセスして、要求されたリストが表示されるかどうかを確認します。 適切なハッシュ マップとリンク リストを使用すると、各 LRU 操作を実行できます。`O(1)`したがって、1 つのクエリにコストがかかります`O(n)`すべてのクエリにはコストがかかります`O(nq)`。 最大の単一ケース境界では、これは約`5000 * 2000 = 10 million`アクセス操作。 複数のケースにわたる、個人の成果`n`そして`q`値は依然として大きくなる可能性があるため、この問題はより再利用可能な前処理ステップを中心に設計されています。 単純な配列ベースの実装は、任意の要素を前に移動するとコストがかかるため、さらに悪いことになります。`O(n)`、与える`O(qn^2)`オペレーション、最大約 500 億の基本シフト。 

すべてのクエリが正確な LRU 動作を独立して再現できるため、ブルート フォース アプローチが機能します。 アクセス順序がすべてのクエリで同一であるため、同じ最新情報を繰り返し検出するのは無駄であるため、失敗します。 

重要な観察は、位置の後の LRU の状態です。`i`取得する要素の数を決定するまでは、実際には容量には依存しません。 完全な最新順序は、アクセス シーケンスによってすでに決定されています。 から逆方向にスキャン`i`、最初に見つかったときにすべての値を受け取ります。 これにより、最新のものから最も新しいものへの順序で並べられた個別の値のユニバーサル シーケンスが生成されます。 容量`m`単に最初のものを要求するだけです`m`要素。 

これにより、問題はシーケンス ハッシュ問題に変わります。 あらゆるエンドポイントに対して`i`、逆方向にスキャンし、すべての値の最初の出現のみを保持し、結果のプレフィックスの多項式ハッシュを構築します。 クエリ リストは同じハッシュで表すことができます。 ハッシュが長さのリストに一致する場合`L`、必要な LRU プレフィックスが見つかりました。 

リストがその容量より短いクエリには、追加の条件が 1 つあります。 その場合、キャッシュは単に要求されたリストを最初に保持する必要はありません。`L`要素。 まさにそれらが含まれている必要があります`L`キャッシュがまだいっぱいになっていないためです。 したがって、エンドポイントで`i`、で見られる個別の値の合計数`a[1..i]`も正確でなければなりません`L`。 

簡単な問題を改善できます`O(n^2 + nq)`さらにハッシュソリューションを使用します。 すべてのハッシュを保存してからすべてのエンドポイントですべてのクエリをスキャンするのではなく、最初にクエリを読み取り、そのターゲット ハッシュを辞書に入れます。 二次前処理パス中に、ハッシュが検出されたクエリはすぐに解決されます。 これにより、`O(n^2 + sum(m_i))`予想される時間とのみ`O(n + q)`入力リストとは別に補助メモリ。

 ハッシュは符号なしの 64 ビット多項式ハッシュであるため、算術演算はモジュロで実行されます。`2^64`乗算後にマスクすることによって。 これは、この問題に対して受け入れられている解決策で一般的に使用されているものと同じ衝突耐性スタイルです。 

## アルゴリズムのチュートリアル

 1. アクセス シーケンスを前処理する前に、すべてのクエリを読み取ります。 末尾のゼロ埋め込みを削除し、その容量、実際の長さ、および多項式ハッシュを記録します。 空のリストはすぐにマークされます`Yes`キャッシュは空から始まるためです。 
2. 重複する識別子を含む空でないクエリを拒否します。 実際の LRU リストには重複を含めることはできないため、そのようなクエリを生成することはできません。 
3. コンピューティング`distinct[i]`、プレフィックスに現れる異なる識別子の数`a[1..i]`。 この値は、要求されたリストの要素がキャッシュ容量よりも少ないクエリの場合にのみ必要です。 
4. 有効なクエリをすべて、キーがキーの辞書に入れます。`(length, hash)`。 値は、その正確なペアを持つクエリ インデックスのリストです。 これは、前処理中に発見されたハッシュが、すべてのクエリを再度スキャンすることなく、すべての一致するクエリを即座に解決できるようにするためです。`q`クエリ。 
5. しましょう`D`要求されたリストの最大長になります。 あらゆるエンドポイントに対して`i`、スキャン`a[i], a[i-1], ...`シーケンスの先頭に到達するまで、または`D`明確な値が見つかりました。 タイムスタンプ配列は、配列全体を毎回クリアすることなく、現在の逆方向スキャン中に検出された値を区別するために使用されます。 
6. 新しい個別の値が見つかるたびに、それを現在の最新シーケンスに追加し、その多項式ハッシュを更新します。 現在の個別の値の数が要求された長さである場合は、検索します。`(length, hash)`クエリ辞書にあります。 
7. ハッシュ ルックアップによって返されたすべてのクエリについて、その容量が要求された長さと等しい場合は、クエリを受け入れます。 その場合、キャッシュがいっぱいになり、その最初の`length`要素はまさにクエリされたリストです。 
8. 容量が要求された長さよりも大きい場合は、次の場合にのみクエリを受け入れます。`distinct[i]`要求された長さに等しい。 これは、要求された要素のみが処理されたプレフィックス内のどこかに出現していることを意味するため、キャッシュには追加の古い要素ではなく、要求された数の要素が正確に含まれます。 
9. すべてのエンドポイントが処理されたら、印刷します。`Yes`解決されたすべてのクエリに対して、`No`未解決のクエリごとに。 

### なぜ効果があるのか

 ポジション直後の約定を検討する`i`。 任意の識別子に対して`x`、の発生`x`最も近い`i`は現在の最後のアクセスです。 から逆方向にスキャンすると`i`、初めて見る`x`まさにその最後のアクセスに遭遇します。 したがって、逆方向スキャンによって最初の検出を順序付けすると、現在知られているすべての識別子が、最も最近使用されたものから最も最近使用されたものの順に並べられます。 最初を取る`m`個別の値により、容量の正確な LRU リストが得られます。`m`。 

アルゴリズムは考えられるすべてのエンドポイントを検査します`i`そしてそれらの異なるプレフィックスを正確に構築します。 したがって、すべての実際の LRU 状態が考慮されます。 全容量クエリは、そのシーケンスがこれらのプレフィックスのいずれかに等しい場合に正確に一致します。 短いクエリは、これまでに確認された値の完全なセットがクエリと同じサイズである場合に正確に一致します。そうでない場合、キャッシュに追加の要素が含まれることになるためです。 不変条件は、エンドポイントを処理した後、`i`、逆方向スキャンの最初`k`個別の値はまさに最初です`k`そのエンドポイントでの LRU の最新順序の位置。 考えられるすべてのエンドポイントが検査されるため、有効な状態が失われることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MASK = (1 << 64) - 1
BASE = 911382323

def solve():
    t = int(input())
    output = []

    for _ in range(t):
        n, q = map(int, input().split())
        a = list(map(int, input().split()))

        queries = [None] * q
        answers = [False] * q

        # need[(length << 64) | hash] = query indices
        need = {}
        max_len = 0

        for qi in range(q):
            parts = list(map(int, input().split()))
            capacity = parts[0]
            values = parts[1:]

            while values and values[-1] == 0:
                values.pop()

            length = len(values)

            if length == 0:
                # The cache is empty before the first access.
                answers[qi] = True
                queries[qi] = (capacity, 0, 0, False)
                continue

            # An LRU list cannot contain duplicate identifiers.
            if len(set(values)) != length:
                queries[qi] = (capacity, length, 0, False)
                continue

            h = 0
            for x in values:
                h = (h * BASE + x) & MASK

            queries[qi] = (capacity, length, h, True)

            if length > max_len:
                max_len = length

            key = (length << 64) | h
            need.setdefault(key, []).append(qi)

        # distinct[i] = number of distinct values in a[0..i-1].
        distinct = [0] * (n + 1)
        seen_prefix = [0] * (n + 1)
        count = 0

        for i, x in enumerate(a, 1):
            if seen_prefix[x] == 0:
                seen_prefix[x] = 1
                count += 1
            distinct[i] = count

        if max_len > 0 and need:
            # Timestamp trick avoids clearing seen_backward for every endpoint.
            seen_backward = [0] * (n + 1)
            wanted_length = [False] * (max_len + 1)

            for capacity, length, h, valid in queries:
                if valid:
                    wanted_length[length] = True

            stamp = 0

            for end in range(n):
                stamp += 1
                h = 0
                cnt = 0
                j = end

                while j >= 0 and cnt < max_len:
                    x = a[j]

                    if seen_backward[x] != stamp:
                        seen_backward[x] = stamp
                        cnt += 1
                        h = (h * BASE + x) & MASK

                        if wanted_length[cnt]:
                            key = (cnt << 64) | h
                            matched = need.get(key)

                            if matched is not None:
                                total_distinct = distinct[end + 1]

                                for qi in matched:
                                    if answers[qi]:
                                        continue

                                    capacity, length, _, valid = queries[qi]

                                    if not valid:
                                        continue

                                    if capacity == length:
                                        answers[qi] = True
                                    elif total_distinct == length:
                                        answers[qi] = True

                    j -= 1

        for ok in answers:
            output.append("Yes" if ok else "No")

    sys.stdout.write("\n".join(output))

if __name__ == "__main__":
    solve()
```クエリの前処理は、考えられるすべてのターゲットを辞書検索に変えることができるため、高価なアクセス シーケンス スキャンの前に行われます。 入力リストにゼロが埋め込まれている場合、これら 2 つの数値の意味が異なるため、クエリの容量は実際のリストの長さとは別に保存されます。 

重複チェックはクエリを挿入する前に意図的に実行されます。`need`。 ハッシュは高速な比較に使用されますが、多項式ハッシュは確率的であるため、構造的に不可能なリストを拒否することで、単に衝突が原因で重複シーケンスが受け入れられることを回避できます。 

の`distinct`prefix 配列は、各エンドポイントまでに出現した異なる識別子の数をカウントします。 クエリの場合`capacity > length`、条件`distinct[end + 1] == length`これはまさに、要求されたリストを超えてキャッシュがまだ満たされていない状態です。 

逆方向スキャンでは、エンドポイントごとにブール配列をクリアする代わりに、タイムスタンプ配列を使用します。 いつ`stamp`変更すると、古いマークはすべて論理的に非アクティブになります。 これにより、追加のコストが節約されます`O(n^2)`操作をクリアし、内側のループを実際の逆方向スキャンに集中させます。 

ハッシュは、LRU リストと同じ順序で更新されます。 逆方向スキャンで次のことがわかる場合`x`、 それから`y`、 それから`z`、結果の値は次のハッシュです。`[x, y, z]`、その逆ではありません。 Python 整数は C++ 符号なし整数のように自然にオーバーフローしないため、マスクが必要です。 申請中`& MASK`算術モジュロを明示的に再現します`2^64`。 

目的の算術演算は正確にモジュロであるため、マスク後の整数オーバーフローのバグはありません。`2^64`。 辞書キーを作成するときに長さが 64 ビットシフトされるため、64 ビット ハッシュが等しい場合でも、異なるリストの長さはキーを共有できません。 

ループは次の場合に停止します。`cnt == max_len`逆方向インデックスが特定の境界に達したときではなく、 これ以上のものを要求するクエリはないため、これで十分です。`max_len`個別の値、およびそれを超えるものはクエリに影響を与えることはできません。

 | 4 | 3 |`[3, 1, 2]`| 3 |

 最初のクエリは、`[1, 2]`容量 2 の場合、エンドポイント 3 で一致します。 

2 番目のクエリは、`[2, 3]`容量 2 では、決して発生しません。 エンドポイント 4 は次で始まります`[3, 1]`、 ない`[2, 3]`。 

3 番目のクエリは、`[3, 1, 2]`容量 3 の場合、エンドポイント 4 で一致します。 

4 番目のクエリの容量は 4 ですが、要求するのは`[2, 1]`。 エンドポイント 2 では、2 つの異なる識別子のみが出現しているため、容量 4 のキャッシュには正確に次の内容が含まれます。`[2, 1]`。 したがって、クエリは次のようになります。`Yes`。 

この例は、キャッシュ容量と実際のリストの長さを別々に扱う必要がある理由を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |`O(nD + sum(m_i))`予想される |`D`要求されたリストの最大長であり、`D <= n`; 最悪のケースは`O(n^2 + sum(m_i))`|
 | スペース |`O(n + q)`| 個別のカウント、タイムスタンプ配列、クエリ、およびハッシュ ディクショナリのプレフィックス |

 最悪の場合の前処理は最大でも実行されます。`n`逆方向スキャン、それぞれ最大で収集`n`個別の値なので、最大でもパフォーマンスを発揮します`25 million`内部反復`n = 5000`。 クエリ入力の合計には最大でも次のものが含まれます`2 * 10^6`整数。 これは、クエリごとに完全な LRU シミュレーションを個別に実行するよりも大幅に優れており、`O(n^2)`同じアイデアの直接実装で使用されるハッシュ マトリックス。 公式のメモリ制限は 512 MB ですが、上記の実装では線形補助メモリのみが使用されます。 

唯一の確率部分は 64 ビット多項式ハッシュです。 算術モジュロあり`2^64`可能なすべての識別子よりも基数が大きい場合、偶然等価になる可能性は非常に低いです。 これは、目的のハッシュ ソリューションで使用される標準のトレードオフです。

 ## 特殊なケース

 ### 要求されたリストが空です

 のために```
1
1 1
1
1 0
```ゼロが削除され、長さ 0 のリストが残ります。 アルゴリズムはこのクエリを次のようにマークします。`Yes`すぐに。 最初のアクセスの前にはキャッシュが空であるため、逆方向スキャンは必要ありません。 これは、他の点では正しい解決策が間違った答えを受け取る原因となることが多いケースを直接処理します。 

### リストがその容量より短い

 のために```
1
3 1
1 2 3
3 1 2 0
```要求されたリストは`[1, 2]`、容量は3つですが。 エンドポイント 2 では、後方個別シーケンスは次のようになります。`[2, 1]`したがって、この特定のクエリはそこでは一致しません。 エンドポイント 1 でのシーケンスは次のとおりです。`[1]`。 エンドポイント 3 では、次のようになります。`[3, 2, 1]`。 したがって、正しい出力は実際には`No`。 

より直接的な肯定的なケースは次のとおりです。```
1
3 1
1 2 1
3 1 2 0
```エンドポイント 2 では、後方個別シーケンスは次のようになります。`[2, 1]`、 ない`[1, 2]`、ただし、エンドポイント 3 では、`[1, 2]`。 2 つの異なる値のみが出現しているため、容量 3 のキャッシュには正確に次の値が含まれます。`[1, 2]`。 出力は`Yes`。 

平等`distinct[end] == length`これが、このケースと完全なキャッシュを区別するものです。 要求されたリストの背後に追加の古い項目がまだ存在する可能性があるため、プレフィックスだけを照合するだけでは十分ではありません。 

### クエリ内の重複した識別子

 のために```
1
2 1
1 2
2 1 1
```クエリリストは`[1, 1]`。 実際のすべての LRU 状態には個別の識別子が含まれているため、答えは次のようになります。`No`。 実装では、クエリ ハッシュを計算または登録する前に重複を検出します。 

### 連続した繰り返しアクセス

 のために```
1
3 1
1 1 2
2 2 1
```州は`[1]`、`[1]`、 そして`[2, 1]`。 最終的な状態はクエリと正確に一致するため、答えは次のようになります。`Yes`。 逆方向スキャンは、2 番目のスキャンに遭遇したときにこれを自然に処理します。`1`、早いほど`1`スキャン中は重複として無視されます。 

### 未満`m`独特の価値観が現れてきた

 のために```
1
3 1
1 2
3 1 2 0
```最後までに 2 つの異なる識別子だけが現れました。 逆方向の個別シーケンスは次のとおりです。`[2, 1]`、容量 3 のキャッシュには、まさにこれら 2 つの要素が含まれています。 を求めるクエリ`[2, 1]`長さが 2 であるため受け入れられます。`distinct[2]`も2つです。 

代わりにシーケンスが```
1
3 1
1 2 3
3 2 1 0
```要求された`[2, 1]`3 つの異なる値が出現した時点では、完全なキャッシュではありません。 一度`3`が出現した場合、クエリに要素が 2 つしかないというだけの理由で、容量 3 のキャッシュはそれを破棄できません。 個別プレフィックス条件は、このような誤検知を防ぎます。 

### 要求されたリストが利用可能な最新シーケンスよりも長いです

 アクセスシーケンスが次のようになっているとします。```
1
3 1
1 1 1
3 1 2 3
```2 つまたは 3 つの異なる識別子は存在しないため、逆方向スキャンでは長さ 3 の最新シーケンスを構築できません。 質問は未解決のままですが、答えは次のとおりです。`No`。 内部スキャンは要求された長さに達する前にアクセス シーケンスの開始時に停止するため、実装はこれを自然に処理します。 

### 同じターゲットが複数のエンドポイントに表示されます

 クエリは何度も一致する可能性があります。 例えば、```
1
4 1
1 2 1 2
2 2 1
```2 回目のアクセス後に一致し、4 回目のアクセス後にも一致します。 アルゴリズムは、どのエンドポイントが最初に一致したかを記憶する必要はありません。 ハッシュが見つかり、容量条件が満たされると、答えは永久に得られます。`Yes`。 

この問題では、少なくとも 1 つの有効なエンドポイントが存在するかどうかのみが問われるため、正確性はどちらの出現が最初に見つかるかには依存しません。
