 ## 解決策
 ## 問題の理解

 ブライアンは屋台の列を歩きます。 各屋台で、彼は現金を限られたトークンの保管場所に変換するか、すぐにトークンを使ってマスコットを入手するかの選択に直面します。 トークンは繰り越される制約付きリソースのように動作しますが、固定容量に制限されているため、超過分は破棄されます。 

各ストールには 2 つのパラメータが提供されます。 1 つ目は、そこでお金を費やした場合に受け取るトークンの数、2 つ目は、同じ数のマスコットを受け取るために費やさなければならないトークンの数です。 重要なのは、トークンの購入はマスコットの数に直接影響を与えず、マスコットを購入してもトークンの容量は変更されず、現在のトークンのストックが減るだけであるということです。 

タスクは、すべての屋台を順番に処理した後、マスコットの総数を最大化するために 2 つのアクションのどちらを取るかを、屋台ごとに決定することです。 

この制約により、決定に対する指数関数的な検索が即座に除外されます。 最大 100,000 の屋台の場合、屋台ごとに 2 つの選択肢に分岐するアプローチは 2^n として増加しますが、これは不可能です。 O(n^2) の遷移でも遅すぎます。 唯一の実行可能なソリューションは、理想的にはトークンの容量に比例して、ポジションごとに小さな状態を維持するものです。 

主要な構造上の制約は、トークン容量 m が最大 100 であることです。これは、有効なソリューションでは「現在保持されているトークン」を動的プログラミングの状態次元として扱う必要があるという決定的なヒントです。 

トークンの購入が上限を超えると、微妙なエッジケースが発生します。 たとえば、m = 10 で現在 8 つのトークンを所有し、5 つのトークンを購入すると、最終的には 13 ではなく 10 になります。これを固定することを忘れた実装では、将来の購買力が誤って膨らむことになります。 

もう 1 つのエッジ ケースは、bi がゼロの場合です。 その場合、屋台はトークンを消費しない無料のマスコット獲得として使用できますが、それでもトークン購入オプションと競合します。将来の屋台によっては、より良い場合もそうでない場合もあります。 その時点で貪欲な選択は危険です。 

最後に、ai = 0 のストールが重要です。 これらは無料のトークン取得を可能にし、将来の実現可能性を大きく変える可能性がありますが、マスコットの購入と依然として競合するため、適切なタイミングで取得された場合に限ります。 

## アプローチ

 ブルートフォース戦略では、考えられるすべての決定シーケンスをシミュレートします。 各屋台では、トークンを購入するか、十分なトークンが利用可能な場合はマスコットを購入するかの 2 つの可能性に分岐します。 これにより、ノードごとに 2 つの分岐を持つ決定木が構築され、O(2^n) 状態になります。 現在の位置と現在のトークン数のみが重要であることを認識しない限り、同一の状態を枝刈りしても効果はありません。 

重要な観察は、将来の決定を下すために必要な唯一の記憶は、ブライアンが現在保有しているトークンの数であるということです。 それ以外はすべて入力プレフィックスによって修正されます。 トークンは m によって制限されるため、ストールあたりの個別の状態の総数は最大でも m + 1 です。これにより、問題は小さな状態空間をもつライン上の動的計画法に変換されます。 

状態 dp[i][t] を、正確に t 個のトークンを保持しながら最初の i 個のストールを処理した後に取得できるマスコットの最大数として定義します。 各状態から、ストール i での 2 つのアクションを考慮します。 トークンを購入する場合は、min(m, t + ai) に遷移します。 マスコットを購入する場合、t ≥ bi の条件で t - bi に遷移し、答えに bi を追加します。 

この構造は事実上、各層が m 個のノードのみを持ち、各ノードが最大 2 つの出力遷移を持つ階層化グラフです。 これにより、溶液は O(nm) になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n) | O(n) | 遅すぎる |
 | トークンを使用した動的プログラミング | O(n・m) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 ストールを 1 つずつ処理し、考えられるトークン数に対する DP テーブルを維持します。

1. DP 配列を初期化します。ここで、 dp[t] は、正確に t 個のトークンを使用して現在のプレフィックスを処理した後に達成可能な最大マスコットを表します。 最初は dp[0] = 0 であり、他のすべての状態は不可能です。 
2. 各ストール i に対して、不可能な値で満たされた新しい next_dp 配列を作成します。 この分離は、同じストールからの遷移が互いに干渉しないようにするために必要です。 
3. dp[t] が有効な場合、0 から m までの考えられるすべてのトークン カウント t について、2 つのアクションを検討します。 
4. まずトークンの購入を検討します。 これにより状態は t + ai に移動しますが、トークンには上限があるため、それを m に固定します。 next_dp[min(m, t + ai)] を dp[t] で更新します。 
5. 次に、マスコットの購入を検討します。 t ≥ bi の場合、t - bi に移行し、マスコット数を bi だけ増やすことができます。 next_dp[t - bi] を dp[t] + bi で更新します。 
6. ストール i のすべてのトークン状態を処理した後、dp を next_dp に置き換えます。 
7. すべてのストールが処理された後、答えはすべての dp[t] の最大値になります。 

これが機能する理由は、dp[t] が各プレフィックスを処理した後の特定のトークン レベルで可能な最高のマスコット数を常に表すためです。 すべての有効な決定シーケンスは、これらの状態を通過する 1 つのパスに正確に対応し、すべての状態遷移は、失速時の 2 つの法的措置の 1 つに正確に対応します。 

不変条件は、i の処理が停止した後、ちょうど t 個のトークンで終わるすべての戦略の中で達成可能な最大マスコットを dp[t] が保管することです。 すべての遷移は局所的に正確さを維持し、両方のアクションを徹底的に考慮するため、最適なシーケンスが除外されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    NEG = -10**18
    dp = [NEG] * (m + 1)
    dp[0] = 0

    for i in range(n):
        ndp = [NEG] * (m + 1)

        ai = a[i]
        bi = b[i]

        for t in range(m + 1):
            if dp[t] == NEG:
                continue

            # option 1: buy tokens
            nt = t + ai
            if nt > m:
                nt = m
            if dp[t] > ndp[nt]:
                ndp[nt] = dp[t]

            # option 2: buy mascots
            if t >= bi:
                nt = t - bi
                val = dp[t] + bi
                if val > ndp[nt]:
                    ndp[nt] = val

        dp = ndp

    print(max(dp))

if __name__ == "__main__":
    solve()
```実装では 2 つの配列のみが保持されます。`dp`そして`ndp`、メモリが m 単位で線形に保たれるようにするため。 センチネル値`NEG`到達不可能な状態を表し、無効な遷移の伝播を防ぎます。 クランプ`min(m, t + ai)`トークンの上限を超えても追加の使用可能な状態は作成されないため、これは必須です。 

各反復では前回のストールからの値が厳密に使用されるため、部分的に更新された状態が誤って再利用されることがなくなります。 

## 実用的な例

 m = 5 で 3 つのストールがある小規模なシナリオを考えてみましょう。 

ストール 1 では、a1 = 2 および b1 = 3 と仮定します。ストール 2 では、a2 = 3 および b2 = 2。ストール 3 では、a3 = 0 および b3 = 4 とします。 

最初の dp は次のとおりです。 

| トークン | DP |
 | --- | --- |
 | 0 | 0 |
 | 1..5 | -∞ |

 ストール 1 の後、トークン 0 からトークンを購入して 2 に達するか、マスコットを購入できないため何もしないかのどちらかです。 したがって、 dp は次のようになります。 

| トークン | DP |
 | --- | --- |
 | 0 | -∞ |
 | 2 | 0 |
 | その他 | -∞ |

 ストール 2 の後、状態 2 からは 5 トークンに進むか、2 つのマスコットに 2 トークンを費やすことができます。 したがって、次のようになります。 

| トークン | DP |
 | --- | --- |
 | 0 | -∞ |
 | 3 | 0 |
 | 0 | 2 (支出から) |

 したがって、柔軟性を維持しながら、マスコットをすでに収集したブランチが最適な構造に含まれるようになりました。 

ストール 3 の後、a3 = 0 なので、トークン レベルに応じて状態を変更せずに繰り越すか、可能であればマスコットを消費することができます。 これは、ゼロトークン遷移がどのようにして最適なパスを再形成するかを示しています。 

このトレースは、最適性が可能な限り貪欲にマスコットを取得するのではなく、トークン支出の決定を遅らせたり進めたりすることに依存していることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n・m) | n 個のストールのそれぞれは、一定の遷移を伴う最大 m 個のトークン状態を処理します。 
| スペース | O(m) | サイズ m + 1 の 2 つの配列のみが維持されます。 

積 n · m は最大 10^7 であり、単純なループと整数演算で実装した場合、Python の時間制限内に問題なく収まります。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    NEG = -10**18
    dp = [NEG] * (m + 1)
    dp[0] = 0

    for i in range(n):
        ndp = [NEG] * (m + 1)
        ai, bi = a[i], b[i]

        for t in range(m + 1):
            if dp[t] == NEG:
                continue

            nt = min(m, t + ai)
            ndp[nt] = max(ndp[nt], dp[t])

            if t >= bi:
                ndp[t - bi] = max(ndp[t - bi], dp[t] + bi)

        dp = ndp

    return str(max(dp))

 ## 特殊なケース

 重大なエッジケースは、ai が容量を超えるほど大きい場合です。 たとえば、m = 5 および ai = 10 です。任意の t から開始すると、トークンの購入は常に状態 5 になります。アルゴリズムはこれを正しくクランプし、容量を超える人為的な状態が発生しないようにします。 

もう 1 つのケースは、bi が m に等しい場合です。 m = 10、bi = 10 と仮定します。その場合、マスコットを購入するとトークンが完全に消費され、その後の失速は、以前のトークンの蓄積に価値があるかどうかに大きく依存します。 遷移によりゼロトークン状態への移行が可能になるため、DP はこれを自然に捉えます。 

ai = 0 および bi = 0 の場合、両方のアクションはトークンの状態を保持しますが、一方のアクションは無料のマスコットを提供します。 DP 遷移では最大値が保持され、無効な状態の相互作用が発生しないため、DP は常にこれらの空きマスコットを蓄積することを好みます。 

最後に、すべての AI がゼロの場合、システムは純粋に、いつトークンを使用するかというスケジュールの問題になります。 DP はマスコットの消費パスのみを探索することになりますが、状態は決して増加せず、支出によってのみ減少するため、依然として正しく処理されます。
