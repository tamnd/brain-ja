 ## 解決策
 ## 問題の理解

 非常に長い 10 進数文字列が与えられ、隣接する数字の間にカットを挿入して、連続したチャンクに分割することができます。 各チャンクは数値として解釈されますが、制限が 1 つあります。チャンクが正確に 1 桁でない限り、先頭にゼロのあるチャンクは許可されません。`"0"`。 

分割後、これらのチャンクのうち 3 で割り切れる数値を表すチャンクがいくつあるかをカウントし、このカウントを最大化したいと考えています。 

したがって、タスクは数値自体の値を計算することではなく、その数字シーケンスの一部を選択することです。 各ピースは、その桁の合計が 3 で割り切れる場合は 1 ポイント、そうでない場合は 0 ポイントを与えます。 目的は、「良い」セグメントの数を最大化することです。 

入力長は最大 200,000 桁です。 これにより、すべてのパーティションを試行する戦略は即座に除外されます。 パーティションは 199,999 回のバイナリ カットの決定によって決定されるため、ブルート フォースは最悪の場合、指数関数的に増加します。 

O(n^2) 個の部分文字列があるため、部分文字列の合計を繰り返し再評価する場合、すべてのセグメンテーションに対する単純な動的プログラミングも実行不可能になります。 

重要な点は、先頭のゼロが単一文字セグメントでのみ許可されることです。 これは、合計を操作するためにゼロをより長いブロックに自由にグループ化するのを妨げるために重要です。 

いくつかの危険な状況に留意することが重要です。 

たとえば、文字列がすべてゼロの場合、`"0000"`、各桁を次のように分離する必要があるため、最適な答えは 4 です。`"0"`、それぞれは 3 で割り切れます。 

文字列に次のような数字が含まれている場合`"111111"`、最善の戦略は、mod 3 の合計のバランスを保つのに役立つ場合にのみ、可能な限り分割することですが、グループ化は割り算構造に影響を与えるため、任意に分割することが常に最適であるとは限りません。 

文字列が`"303"`、文字列全体を取得すると合計は 6 になるため、答えは 1 になりますが、次のように分割されます。`"3|0|3"`3 つの有効なセグメントが得られます。 これは、併合において割り算が単調ではないことを示しています。 

## アプローチ

 ブルート フォース ビューでは、文字列を切断するあらゆる可能な方法を検討し、結果として得られる各パーティションを評価します。 長さ n の文字列の場合、カットを配置する方法は 2^(n−1) 通りあります。 1 つのパーティションの評価に O(n) かかるとしても、合計は O(n・2^n) となり、n が 200,000 までは不可能です。 

より構造化されたブルート フォースは動的プログラミングです。 dp[i] をプレフィックス i の有効なセグメントの最大数とする。 i から、以前のすべてのカット位置 j < i を試し、部分文字列 s[j..i] が 3 で割り切れるかどうかを確認します。割り切れるかどうかの確認は、接頭辞の合計によって行うことができるため、各遷移は O(1) ですが、DP は O(n^2) で、まだ大きすぎます。 

重要な観察は、3 で割り切れる可能性は 3 を法とする桁の合計にのみ依存するということです。セグメントの桁の合計が 0 mod 3 に一致する場合、+1 が寄与します。 

ここで、3 を法とするプレフィックスの合計に関して問題を書き直します。pref[i] を i を法とする i までの桁の合計とします。pref[i] == pref[j] の場合、セグメント (j+1..i) は適切です。 

したがって、選択した各セグメントが 2 つの等しいプレフィックス mod 状態に対応するように、配列をできるだけ多くのセグメントに分割したいと考えています。 

これにより、問題は一連の等しい mod 位置の選択に変換されますが、セグメントが互いに素で連続しているという制約が伴います。 

貪欲な洞察は、位置 i を確認するたびに、まだ有効な同じプレフィックス mod 状態を持つ最も古い前の位置 j でセグメントを閉じることを試行する必要があるということです。 これは、順序を尊重しながら、ペアの数を最大化する方法で、等しいプレフィックス状態の出現をペアにすることと同じです。 

最適な構造は、セグメントの開始点として各プレフィックス モジュロ クラスが何回「利用可能」であるかを追跡する 3 つのカウンターを備えた貪欲なスイープになります。 

1 桁のゼロは常に有効なセグメントであり、値 0 を持つ通常の数字として扱うことができるため、先行ゼロ制約は最適なカウントに影響を及ぼさないことがわかります。 

現在開いているプレフィックス状態の数を貪欲に維持し、一致する状態が再び見つかった場合は、将来の柔軟性を最大化するためにセグメントをすぐに閉じます。

 ## アルゴリズムのチュートリアル

 数字列を、3 を法とするプレフィックス合計のシーケンスに変換します。 

1. 文字列を左から右にスキャンしながら、プレフィックスのモジュロ値を計算します。 位置 i では、現在のプレフィックスの残り r がわかります。 
2. この残りが閉じられていないセグメントの「開始境界」として何回出現したかを表すカウンタ cnt[r] を維持します。 文字列の前の空のプレフィックスが開始点として機能するため、最初は cnt[0] = 1 になります。 
3. 位置 i に到達したら、現在の剰余 r を確認します。 cnt[r] が正の場合、i で終わるセグメントが直ちに形成されます。 この位置を前の位置とペアにするため、答えをインクリメントし、cnt[r] をデクリメントします。 
4. cnt[r] がゼロの場合、cnt[r] をインクリメントすることで、この剰余を潜在的な将来の開始点として保存します。 
5. 文字列の終わりまで続けます。 

重要な考え方は、セグメントを閉じるたびに、両方のエンドポイントが同じプレフィックス合計のモジュロ 3 を共有するため、その桁の合計が 3 で割り切れることを確認するということです。 

### なぜ効果があるのか

 このアルゴリズムは基本的に、左から右へのスキャンで等しいプレフィックス残基をペアにし、常に可能な限り早い有効なセグメントを閉じます。 最適な解決策は、等しいプレフィックスモジュロ値を持つ位置間のペアリングを引き起こします。 可能なときにセグメントを閉じるのを遅らせた場合、その開口部が後で別の有効なセグメントを形成するために使用される可能性があるため、将来の柔軟性が低下するだけです。 したがって、貪欲にすぐに閉じても、可能なペアの数は決して減らず、セグメントの総数はそのようなペアの数と等しくなります。

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    
    cnt = [0, 0, 0]
    cnt[0] = 1
    
    pref = 0
    ans = 0
    
    for ch in s:
        pref = (pref + (ord(ch) - 48)) % 3
        
        if cnt[pref] > 0:
            ans += 1
            cnt = [0, 0, 0]
            cnt[0] = 1
            pref = 0
        else:
            cnt[pref] += 1
    
    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、現在のプレフィックスの残りと小さな周波数配列のみが保持されます。 リセット ステップは文字列の切断に対応します。有効なセグメントを形成したら、その境界からカウントを再開します。 セグメントが互いに素であるため、これは非常に重要です。そのため、各カットの後にプレフィックス ロジックを再起動する必要があります。 

微妙な点は、カットが成功した後にカウンタの状態とプレフィックスの残りの両方をリセットすることです。 リセットしないと、セグメントの重複が誤って許可されてしまいます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    s = input().strip()
    cnt = [0, 0, 0]
    cnt[0] = 1
    pref = 0
    ans = 0

    for ch in s:
        pref = (pref + (ord(ch) - 48)) % 3
        if cnt[pref] > 0:
            ans += 1
            cnt = [0, 0, 0]
            cnt[0] = 1
            pref = 0
        else:
            cnt[pref] += 1

    return str(ans)

# provided sample
assert run("3121\n") == "2", "sample 1"

# all digits form one number divisible by 3
assert run("6\n") == "1", "single digit divisible"

# all zeros
assert run("0000\n") == "4", "each zero is a segment"

# alternating pattern
assert run("303\n") == "3", "max splitting"

# no divisible segments except single digits
assert run("111\n") == "1", "minimal case"
```| テスト入力 | 期待される出力 | 検証内容 |

 ## 特殊なケース

 のために`"0000"`、アルゴリズムは cnt[0] = 1 から始まります。最初の桁では、プレフィックスは 0 であるため、セグメントはすぐに閉じられます。 状態がリセットされて繰り返され、4 つのセグメントが生成されます。 これは、各ゼロを分離する必要があるという制約と一致します。 

のために`"111"`、prefix mod 値は 1、2、0 です。最後の位置のみがセグメントを閉じるため、セグメントは 1 つだけ形成されます。 cnt[r] は一致する状態が存在する場合にのみ使用されるため、アルゴリズムは不必要な分割を強制しません。 

のために`"303"`、プレフィックス 0 を繰り返すと、すべてのステップで即座に閉じることができ、最大限のセグメンテーションが生成されます。 リセットにより、各カットが独立していることが保証され、プレフィックス状態の重複した再利用が防止されます。
