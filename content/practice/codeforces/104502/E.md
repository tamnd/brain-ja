 ## 解決策
 ## 問題の理解

 私たちは、バイナリ表現を通じて整数に対して定義された関数を操作しています。 任意の正の整数の場合$x$、先行ゼロのないバイナリ形式を見てみましょう。 次に、隣接するビットをスキャンし、ビット値が 0 から 1、または 1 から 0 に何回変化したかを数えます。そのカウントが値です。$f(x)$。 

各クエリでは 2 つの数値が得られます$n$そして$k$。 タスクは整数の数を数える事です$x$範囲内で$1 \le x \le n$まさに持っています$k$バイナリ表現における隣接するビット間の遷移。 

制約$n \le 2^{60} - 1$すべての数値が最大 60 ビットに収まることを意味します。 これは、すべての値に対するブルート フォース反復が行われるため、ビットに対する数値動的プログラミング アプローチを直ちに示唆します。$n$実行不可能なとき$n$大きくて最大です$10^5$クエリ。 

素朴な考えは、計算することです$f(x)$それぞれに$x$まで$n$。 単一のクエリでも次のような問題が発生する可能性があるため、これは不可能です。$n$近く$10^{18}$、各数値に対してビット スキャンを実行すると、すでに時間制限を超えてしまいます。 

より微妙な失敗例は、クエリの独立性を尊重せずに制限値まで値を事前計算しようとした場合に発生します。 たとえば、すべてのクエリが同じ事前計算された配列を最大まで共有すると仮定すると、$n$、これでもメモリと前処理時間の両方で失敗します。$n$できる$2^{60}$。 

もう 1 つの重要なエッジ ケースは、バイナリの長さが 1 である小さな値です。$x = 1$、$f(x) = 0$そして、どの DP も、隣接するペアが存在しないという事実を正しく処理する必要があります。 

## アプローチ

 ブルートフォースの解決策は簡単です。 それぞれの番号について$x$1から$n$、それをバイナリに変換し、連続するビットが何回異なるかを数えます。 これには必要です$O(\log x)$数値ごとに計算されるため、1 つのクエリにコストがかかります$O(n \log n)$。 と$n$まで$10^{18}$、これはまったく不可能です。 

重要な観察は、私たちが興味があるのは個々の数値ではなく、制限された数の遷移を持つ長さ 60 までのバイナリ文字列であるということです。 これは古典的なビット上の DP です。数値を直接列挙する代わりに、最上位ビットから下に向かってビットごとに数値を構築し、発生した遷移の数とまだプレフィックスが厳密であるかどうかを追跡します。$n$。 

重要な構造は、前のビットがわかったら、新しいビットを追加すると遷移数が増加するかどうかのどちらかであるということです。 これは、状態が位置、前のビット、これまでの遷移の数、およびまだ接頭辞によって制約されているかどうかだけを記憶する必要があることを意味します。$n$。 

これにより、列挙の問題が軽減されます。$n$最大でも列挙できる数値$60 \times 2 \times 60 \times 2$クエリごとにステートを生成するため、十分に高速です。

 ## アルゴリズムのチュートリアル

 のバイナリ表現に対してビット DP を使用して、各クエリを独立して処理します。$n$。 

1.変換$n$最上位ビットから最下位ビットまでの 60 ビットのバイナリ配列に変換されます。 すべての数値が均一に揃うように固定長で作業します。 これにより、DP 内での可変長のエッジ ケースの処理が回避されます。 
2. ポジションに対する DP 関数を定義します。 それぞれの位置で、接頭辞を超えないという制約を考慮して、0 を配置するか 1 を配置するかを決定します。$n$まだきついなら。 
3. DP 状態には、現在のビット位置が含まれます。$n$、配置された前のビット、および現在の遷移数。 また、最初に選択されたビットが誤って遷移としてカウントされないように、開始位置に特別な「前のビットがまだない」状態も含めます。 
4. あるビットから次のビットに遷移するとき、遷移カウントを更新します。 前のビットが存在し、現在のビットと異なる場合は、カウントを 1 つインクリメントします。 それ以外の場合は、変更されないままになります。 
5. すべてのビットを処理した後の最終状態でのみ結果を蓄積します。 遷移数が次の場合$k$、答えに 1 を加えます。 
6. 各クエリについて、1 から 1 までの数値を表すすべての有効な DP パスを合計します。$n$。 すべてゼロの数値は正ではないため、確実に除外されます。 

### なぜ効果があるのか

 範囲内のすべての整数$[1, n]$のバイナリ表現によって辞書編集的に制限される長さ 60 以下のバイナリ文字列に一意に対応します。$n$。 DP は、これらの文字列を繰り返しなく正確に列挙します。 遷移カウンターは隣接するビットのみに基づいて決定論的に進化するため、DP 状態は計算に必要なすべての情報を完全にキャプチャします。$f(x)$。 すべての有効な数値は 1 回だけ表現され、無効な数値は次の値を超えないためです。$n$厳しい制約の下で許可される場合、最終的な合計は必要なセットを正確にカウントします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXB = 60

def solve_case(n, k):
    bits = [(n >> i) & 1 for i in range(MAXB - 1, -1, -1)]

    from functools import lru_cache

    @lru_cache(None)
    def dp(pos, tight, started, prev, cnt):
        if cnt > k:
            return 0
        if pos == MAXB:
            return 1 if started and cnt == k else 0

        limit = bits[pos] if tight else 1
        res = 0

        for b in (0, 1):
            if b > limit:
                continue
            ntight = tight and (b == limit)

            if not started:
                if b == 0:
                    res += dp(pos + 1, ntight, False, 0, cnt)
                else:
                    res += dp(pos + 1, ntight, True, b, cnt)
            else:
                ncnt = cnt + (b != prev)
                res += dp(pos + 1, ntight, True, b, ncnt)

        return res

    return dp(0, True, False, 0, 0)

def main():
    q = int(input())
    for _ in range(q):
        n, k = map(int, input().split())
        print(solve_case(n, k))

if __name__ == "__main__":
    main()
```DP はメモ化された再帰として実装されます。 状態は、バイナリ表現の配置を開始したかどうかを明示的に追跡します。 これにより、先頭のゼロが数値の一部として誤ってカウントされることがなくなります。 の`tight`フラグは上限を強制します$n$少しずつ。 

遷移ロジックは、最初の非ゼロ ビットと後続のビットを注意深く区別します。 これは不可欠です。なぜなら、$f(x)$先行ゼロのない実際のバイナリ表現にのみ適用されます。 

剪定の様子`cnt > k`すでに目標遷移数を超えている状態の不必要な探索を防ぎます。 

## 実用的な例

 検討してください$n = 13$、$k = 2$。 13 までのバイナリ表現には次のものがあります。 

遷移に焦点を当てた簡略化されたビューで DP 状態を追跡します。 

| ポジション | タイト | 開始しました | 前へ | カウント | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 1 | 0 | - | 0 | 最初の 1 を選択 |
 | 1 | さまざまです | 1 | 1 | 0 | 拡張する |
 | 2 | さまざまです | 1 | 0 | 1 | 遷移 |
 | 3 | さまざまです | 1 | 1 | 2 | 移行に達しました |

 これは、ビットが交互に切り替わるたびに単一パスがどのように遷移を蓄積するかを示しています。 

ここで小さなケースを考えてみましょう$n = 5$、$k = 2$。 有効な数値は次のとおりです。 

- 101 (5) には 2 つのトランジションがあります
 - 先頭のゼロは許可されていないため、010 は無効です

 | 番号 | バイナリ | f(x) |
 | --- | --- | --- |
 | 1 | 1 | 0 |
 | 2 | 10 | 1 |
 | 3 | 11 | 0 |
 | 4 | 100 | 1 |
 | 5 | 101 | 2 |

 寄与する数値は 1 つだけです。 

これにより、DP が正確に 2 ビットの変更で数値を正しく分離していることが確認されます。

 ## 特殊なケース

 重要なエッジケースの 1 つは次のような場合です。$x$は 2 の累乗です。 そのバイナリ表現は 1 の後にゼロが続くため、常に 1 つの遷移が存在します。 最初のビットが 1 で後続のすべてのビットが 0 であるため、DP はこれを自然に処理し、1 から 0 への変化が 1 回だけ寄与します。 

もう一つのエッジケースは、$x = 1$。 バイナリ表現の長さは 1 であるため、隣接するペアはありません。 DP は単一の 1 を配置した直後に終了状態に到達し、遷移カウントはゼロのままであり、定義と一致します。 

先頭のゼロの処理も重要です。 なしで`started`フラグを使用すると、「000101」のような文字列が誤って追加のトランジションに寄与してしまいます。 DP は、すべてゼロのプレフィックスを無視し、最初の 1 が配置された後にのみ遷移カウントを開始することでこれを回避します。
