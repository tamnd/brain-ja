 ## 解決策
 ## 問題の理解

 整数の配列が与えられ、非常に珍しい並べ替え手順を繰り返し適用します。 この手順では、バブル ソートのように隣接する要素を比較するのではなく、位置のすべてのペアを比較します。 インデックスの順序付きペアごとに、最初のインデックスの要素が 2 番目のインデックスの要素より小さい場合、2 つの値が交換されます。 これはすべての位置に対して二重ループで実行されるため、すべての要素は他のすべての要素と何度も対話できます。 

必要なキーの量は、最終的にソートされた配列ではなく、このプロシージャが配列の各プレフィックスに対して実行されるときに実行されるスワップの数です。 1 から n までの各 k について、最初の k 要素を取得し、この完全な手順を実行し、プロセス全体で実行されたスワップの数をカウントします。 

出力は、すべてのプレフィックスのこれらのスワップ数のシーケンスです。 

この制約は、n がテスト ケースごとに最大 10^5 であり、テスト全体の合計 n が最大 10^6 であることを意味します。 並べ替えプロセスの直接シミュレーションでは、プレフィックスごとに最大 n² 個の比較が実行され、プレフィックスごとに個別に実行した場合、潜在的に総作業量は n³ になります。 1 回の実行でもすでに O(n²) であり、規模的には遅すぎます。 ソリューションでは、テスト ケースごとに問題を線形またはほぼ線形に近づける必要があります。 

要素が等しい場合、微妙なエッジケースが発生します。 条件は厳密に ai < aj であるため、等しい値によってスワップがトリガーされることはありません。 重複はプロセス内で安定したブロックとして動作するため、これは重要です。 たとえば、配列 [2, 2, 1] の場合、最初の 2 つの要素は互いにスワップすることはありませんが、どちらも 1 と相互作用します。重複を個別に処理せずに厳密な順序付けを前提とするアプローチでは、スワップの寄与を誤ってカウントします。 

もう 1 つの微妙なケースは、増分プレフィックスです。 単純な実装では、プレフィックスごとに並べ替えプロセス全体を個別に再実行しようとする可能性がありますが、スワップによって配列の順序が大幅に変更されるため、中間作業は明らかな方法で再利用できません。 重要な問題は、プロシージャがグローバルに実際に何を行っているかを理解しない限り、プレフィックス k を処理した後の状態はプレフィックス k-1 の単純な拡張ではないことです。 

## アプローチ

 ブルート フォース解釈は文字通りのアルゴリズムに従います。 各プレフィックスについて、ネストされたループをシミュレートし、すべてのペア (i, j) を繰り返しスキャンし、ai < aj になるたびに交換します。 各実行には O(k²) 回の比較と、場合によっては O(k²) 回のスワップがかかります。 すべてのプレフィックスを合計すると、ゼロから再計算し、各実行自体が 2 次であるため、最悪の場合、これは O(n³) になります。 これは、10^5 までの n には実行できません。 

重要な洞察は、これを動的なスワッピング プロセスとして考えるのをやめ、代わりに各要素がスワップ数にどのような影響を及ぼしているかを再解釈することです。 

接頭辞を修正し、単一の要素 x を調べます。 x がスワップに関与するたびに、比較の時点で x < y となる要素 y とペアにする必要があります。 アルゴリズムの構造により、最終的には、スワップを通じて、より大きな要素がより小さな要素を繰り返し「引っ張る」ことが保証されます。 要素の各ペアは、相対的な順序と相互作用の頻度のみに応じて、予測可能な数のスワップに寄与します。 

要素を値の昇順に処理すると、以前に確認された要素の数が大きいか小さいかを数えることができ、寄与分を段階的に蓄積できます。 これにより、問題は値に対する周波数構造の維持に変換され、新しい要素のそれぞれが、それよりも大きい以前の要素の数に基づいて交換に寄与します。

これにより、周波数配列にわたるプレフィックス統計を維持するタスクが軽減され、通常はフェンウィック ツリーまたはセグメント ツリーで処理されます。 それぞれの新しい要素は、以前に挿入された要素の数より厳密に大きく貢献し、プレフィックス集約を通じて間接的に将来の計算にも影響します。 各プレフィックスの合計スワップ数は、動的に増加するマルチセットにわたる反転のような寄与の累積になります。

 ## アルゴリズムのチュートリアル

 私たちは、交換プロセスを、各要素が以前に見た要素との「順不同の相互作用」に何回参加したかをカウントするものとして再解釈します。 各プレフィックスは段階的に処理されます。 

1. 値に対してフェンウィック ツリー (または同様の構造) を維持し、現在のプレフィックスでこれまでに各値が何回出現したかを追跡します。 この構造は、対数時間でのプレフィックス合計をサポートします。 
2. 配列を左から右に反復処理します。 位置 k で、構造体に a[k] を挿入します。 挿入前に、以前に挿入された要素が厳密に a[k] より大きいものがいくつあるかをクエリします。 この値は、接頭辞 k の答えに追加されます。 
3. 当社は寄付金の累計を維持します。 接頭辞 k の答えは、前の答えに a[k] からの寄与を加えたものです。 
4. 「より大きな要素の数」を計算するには、total_so_far − prefix_sum(a[k]) を使用します。 これは、prefix_sum が要素数 ≤ a[k] を与えるため機能します。 
5. 各プレフィックスは前のプレフィックスに基づいて構築されるため、各プレフィックスの結果を保存します。 

重要な点は、各挿入は以前の要素にのみ依存するため、以前のプレフィックスを再構築する必要がないということです。 

### なぜ効果があるのか

 交換プロセスは、相対的な順序が安定するまで、要素のすべてのペアを効果的に繰り返し比較します。 比較ループ内で小さい要素が大きい要素と出会うたびに、スワップが発生します。 実行全体にわたって、各ペアは、その順序とプレフィックス内の存在によってのみ決定される固定数のスワップに貢献します。 

これにより、合計スワップ数は、要素ごとに、以前に確認されたより大きい要素の数を合計することと等価になります。 これはまさにフェンウィック ツリーによって維持されている反転構造です。 すべてのプレフィックスは前のプレフィックスの単なる拡張であるため、これらの寄与は過去のインタラクションを再処理することなく一貫して蓄積されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        fw = Fenwick(n)
        total = 0
        res = []

        for x in a:
            greater = total - fw.sum(x)
            total += 1
            fw.add(x, 1)
            res.append(str(greater))

        print(" ".join(res))

if __name__ == "__main__":
    solve()
```フェンウィック ツリーには、これまでに確認された値の頻度が保存されます。 各ステップでは、合計数からプレフィックスの合計を引いた値を使用して、現在の値を超える以前の要素の数が計算されます。 

よくある実装の落とし穴は、問題の制約で値が 1 からインデックス付けされていることを忘れることです。これにより、Fenwick ツリーに直接インデックス付けできるようになります。 もう 1 つの微妙な問題は、操作の順序です。クエリは現在の要素を挿入する前に実行する必要があります。そうしないと、要素自体が誤ってカウントされてしまいます。

## 特殊なケース

 [7] のような単一要素入力の場合、フェンウィック ツリーは空で、前の要素が存在しないため、寄与はゼロとなり、計算全体を通じてゼロのままになります。 

完全に減少するシーケンス [5、4、3、2、1] の場合、各要素は、その前に見られたより大きな要素の数と正確に一致します。 最初の要素は 0 を寄与し、2 番目の要素は 1 を寄与し、3 番目の要素は 2 を寄与し、以下同様になります。 各クエリは挿入前に現在の要素より大きい以前の要素をすべて取得するため、アルゴリズムはこれらを正しく累積します。 

[2, 2, 2] のような値が繰り返される配列の場合、条件が厳密に ai < aj であるため、すべてのプレフィックス クエリはゼロを返します。そのため、等しい値によってスワップが発生することはありません。 フェンウィックの構造は、「厳密に大きい」と「以上」を正しく分離し、重複によってカウントが膨らまないようにします。
