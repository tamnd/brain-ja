 ## 解決策
 ## 問題の理解

 このシステムは、複数のランタンを備えた公園をモデル化しており、各ランタンには最終的に燃え尽きるランプが搭載されています。 すべてのランプには既知の寿命があるため、各ランタンは特定の時間に「有効期限イベント」を生成すると考えることができます。 ランプが切れると、共有在庫から交換用ランプが届くまで、そのランタンは一時的に使用できなくなります。 

シミュレーションでは、ランプを 1 つずつ個別に交換するだけではありません。 代わりに、障害はバッチで処理されます。 切れたランプの数がしきい値に達すると、影響を受けたすべてのランタンが一緒に回収されます。 これらのランタンはインデックスの昇順に処理され、限られた在庫から交換用のランプが取り付けられます。 交換するたびに、そのランタンの新しいバーンアウト時間が即座にスケジュールされるため、ランタンは将来の故障のシステムに再び入ります。 

このプロセスはランプ故障の時間順に毎日続きます。 シミュレーションは、必要な交換を実行するのに十分なランプが在庫に含まれていない最初の瞬間に停止します。答えは、これが起こる日になります。 

したがって、入力は、独立した定期タイマー (ランタンごとに 1 つ) のシステム、障害のバッチ処理をトリガーするグローバルしきい値 m、および処理中に不足する可能性がある有限のリソース プールを記述します。 出力は 1 つの時点、つまりシステムが必要なメンテナンスを完了できなくなる最も早い日です。 

複雑さの観点から見ると、自然な制約は、タイム ステップごとにすべてのランタンをスキャンする単純なシミュレーションが直ちに実行不可能であることを意味します。 このプロセスはイベント (ランプの期限切れ) によって駆動され、そのようなイベントの数は膨大になる可能性があり、実行された交換の数に達する可能性があります。 これにより、対数時間データ構造を使用したイベント駆動型のアプローチが強制されます。 

いくつかの特殊なケースでは、単純な実装が壊れます。 

問題の 1 つは同時障害です。 複数のランプが同時に期限切れになった場合は、まとめて処理する必要があります。 たとえば、3 つのランタンがすべて時刻 10 に期限切れになり、m が 2 に等しい場合、3 つすべてを複数日に分けずに 1 つのバッチで収集する必要があります。 有効期限を 1 つずつ処理する単純なアプローチでは、誤って複数の部分置換がトリガーされてしまいます。 

もう 1 つの問題は、補充時にランタン インデックスによる注文です。 バッチにランタンが任意の順序で含まれているが、交換品を最小のインデックスから割り当てなければならない場合、このバッチのソートに失敗すると、在庫消費順序が不正確になり、将来の失敗のタイミングが不正確になります。 

最後に、ランタンをバッチで補充する前に、在庫がなくなっているかどうかを確認する必要があります。 バッチの途中で在庫が不足した場合は、その時点でシミュレーションを直ちに停止する必要があります。 

## アプローチ

 直接シミュレーションでは、各ランタンの現在の状態が維持され、次の故障時期に向けて繰り返しスキャンされます。 各タイム ステップでは、期限切れのすべてのランプが処理され、状態が再構築され、続行されます。 概念的には単純ですが、このアプローチはすべてのランタンを繰り返しスキャンまたは分類することになります。 n 個のランタンがあり、ランタンごとに O(n) 個のイベントが発生する可能性がある場合、O(n²) 個以上の動作が発生することになります。 

重要な点は、システムが完全にイベント駆動型であるということです。 各ランタンは将来の有効期限のストリームに寄与し、私たちは次に小さい有効期限のみを気にします。 これは、すべてのアクティブなランプを有効期限順に並べた構造に維持することを示唆しています。 最小ヒープは、当然のことながら、最も初期の障害を効率的に抽出することをサポートします。 

2 番目の構造要件は、障害を時間ごとにグループ化することです。 最小有効期限を抽出するときは、同じ有効期限を持つすべてのランタンを収集する必要もあります。 これにより、同時イベントが誤って分割されるのを防ぎます。

失敗したランタンのバッチが形成されたら、ランタン インデックスの昇順で処理する必要があります。 これには、2 番目の順序付けされた構造または並べ替え手順が必要です。 代替品を割り当てた後、影響を受ける各ランタンは新しい有効期限を生成し、グローバルな時間順序構造に再挿入する必要があります。 

このプロセスは 2 つの構造システムになります。イベント スケジューリング用に有効期限によって順序付けされた 1 つのヒープと、バッチ処理用にランタン インデックスによって順序付けされた一時的なソート構造です。

 | ブルートフォースシミュレーション | O(n²) 以上 | O(n) | 遅すぎる |
 | ヒープベースのイベント シミュレーション | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ランタンの次の障害時間を表すペア (expiration_time、lantern_id) の最小ヒープを維持します。 また、利用可能なランプの在庫カウンターも維持しています。 

イベントを時間の増加順に繰り返し処理します。 

1. 各ランタンの初期有効期限を使用してヒープを初期化します。 各ランタンは正確に 1 つのエントリに貢献します。 これは、各ランタンが初めて失敗することを表します。 
2. ヒープから最小の有効期限を繰り返し抽出します。 これにより、少なくとも 1 つのランプが切れる最も早い瞬間が得られます。 
3. 有効期限がこの最小時間と等しいすべてのヒープ エントリを収集します。 これらは、同時に失敗するすべてのランタンを表します。 これらは 1 つのバッチとして処理する必要があるため、グループ化します。 
4. このバッチに含まれるランタンの数を確認します。 在庫がこの数より少ない場合、プロセスは続行できず、現在の時間が答えとなります。 
5. 影響を受けたランタンをインデックス順に並べ替えます。 これにより、置換が正しい決定的な順序で割り当てられるようになります。 
6. インデックスの昇順のランタンごとに、ストックから 1 つのランプを消費し、固定寿命を加算して新しい有効期限を計算し、更新されたイベントをヒープにプッシュします。 
7. 在庫がなくなるまでプロセスを続けます。 

重要な不変条件は、現在アクティブなランプごとに次の有効期限が常にヒープに格納されることです。 バッチを処理するたびに、現在の最小時間に発生するイベントを正確に削除し、将来の新しいイベントに置き換えます。 ランタンがスキップされたり重複したりすることはなく、時間順に並べることでシミュレーション タイムラインの正確性が保証されます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m, stock = map(int, input().split())
    
    # lifetime of each lantern's lamp
    life = list(map(int, input().split()))
    
    # current heap: (expire_time, lantern_id)
    heap = []
    
    for i in range(n):
        heapq.heappush(heap, (life[i], i))
    
    current_time = 0
    
    while heap:
        t, _ = heap[0]
        
        # collect all events at time t
        batch = []
        while heap and heap[0][0] == t:
            _, i = heapq.heappop(heap)
            batch.append(i)
        
        # check stock
        if stock < len(batch):
            print(t)
            return
        
        # process in index order
        batch.sort()
        
        for i in batch:
            stock -= 1
            new_t = t + life[i]
            heapq.heappush(heap, (new_t, i))
    
    # if never exhausted
    print(-1)

if __name__ == "__main__":
    solve()
```ヒープには、各ランタンの次回の故障時刻が保存されます。 各反復では最も早い時間を取得し、その時点で失敗したすべてのランタンを収集します。 バッチをインデックスで並べ替えると、必要な補充順序が強制されます。 交換するたびに、そのランタンの次の故障時期が即座にスケジュールされ、イベント駆動型の構造が維持されます。 

微妙な点は、バッチが完全に形成された後でのみ在庫をチェックすることです。 これは、バッチの部分処理が無効であるため必要です。グループ内のすべてのランタンが補充されるか、どれも補充されません。 

## 実用的な例

 3 つのランタンと寿命を備えた小さなシステムを考えてみましょう。`[2, 3, 2]`、および在庫`5`。 

ヒープエントリから始めます`(2,0)`、`(3,1)`、`(2,2)`。 

| ステップ | ヒープ最小値 | バッチ | 在庫 | アクション |
 | --- | --- | --- | --- | --- |
 | 1 | 2 | [0,2] | 5 | 両方を処理する |
 | 2 | 3 | [1] | 3 | プロセス 1 |

 時間 2 では、ランタン 0 と 2 が同時に失敗します。 在庫が十分にあるため、両方が交換され、時間 4 と 4 で押し戻されます。時間 3 で、ランタン 1 が故障し、交換されます。 

これは、同時イベントが正しくグループ化されていることを示しています。 単純なランタンごとの処理では、ランタン 0 と 2 が誤って別々に扱われ、意図したバッチ ロジックが壊れます。 

次に、在庫枯渇について考えてみましょう。 生涯`[1,1,1]`、 ストック`2`。 

| ステップ | ヒープ最小値 | バッチ | 在庫 | アクション |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | [0,1,2] | 2 | 停止 |

 時間 1 では、3 つのランタンすべてが同時に失敗します。 バッチ サイズが在庫を超えているため、答えは 1 です。障害を 1 つずつ処理するアプローチでは、在庫が 2 回の個別の更新に十分であると誤って考えることになります。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n + k log n) | ヒープへのランタンの挿入と再挿入には log n のコストがかかり、各失敗イベントは 1 回処理されます。 
| スペース | O(n) | ヒープには、ランタンごとに最大 1 つのアクティブ イベントが保存されます。 

ヒープ操作の数は実行される置換の数に比例し、各操作は対数になります。 これは、最大 2e5 または同様の制限までの n の一般的な制約内に問題なく適合します。

 ## 特殊なケース

 重大なエッジケースは、すべてのランタンが同時に期限切れになる場合です。 アルゴリズムは、置換を試みる前に、それらすべてを含む単一のバッチを形成する必要があります。 ヒープベースのグループ化では、処理前に同じタイムスタンプを持つすべてのエントリを継続的にポップするため、これが保証されます。 

もう 1 つの微妙なケースは、バッチ中の部分的な在庫の可用性です。 正しい動作は、置換が行われる前に停止することです。 この実装では、在庫を使用する前に完全なバッチ サイズと照合して在庫をチェックし、アトミックな処理を保証します。 

最後のエッジケースは、同じ寿命のランタンを繰り返し再挿入することです。 複数のランタンが同一の将来の有効期限を生成した場合でも、各ヒープ エントリには一意のランタン識別子が含まれるため、それらは独立して処理されます。 これにより、衝突によって異なる状態が誤って結合されるのを防ぎます。
