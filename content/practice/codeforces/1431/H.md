 ## 解決策
 ## 問題の理解

 1 つの種と 1 つのクラスを選択することで、ゲームの各実行が定義される報酬のグリッドが与えられます。 ペアで実行する$(i, j)$スコアを与える$c_{i,j}$、このスコアは時間の経過とともに蓄積されます。 

最初は、一部の種とクラスのみがすでに利用可能です。 蓄積されたスコアが特定のしきい値に達すると、残りのロックが解除されます。 しきい値は減少しないため、ロックの解除は単調です。一度種またはクラスが利用可能になると、それは永久に利用可能になります。 実行では、現在ロック解除されている種とクラスのみを使用できます。 

開始する前に、正確に 1 つのセルを永続的にブーストすることができます。$c_{i,j}$追加することで$k$、今後のすべての実行でその特定の組み合わせを改善するためのガイドを読むことを表します。 

目標は、実行の最適な順序とブーストされたセルの最適な選択を通じて、すべての種とクラスのロックが解除されるように、必要な実行の最小数を決定することです。 

主な難点は、各実行が行制約 (種のしきい値) と列制約 (クラスのしきい値) の両方のロック解除に同時に寄与し、実行の選択がすでにロックが解除されているものによって動的に制限されることです。 

制約は大きく、両方の次元は最大 1500 まで可能であり、各実行の決定は完全な行列からの値の累積に依存します。 利用可能なペアを繰り返しスキャンしたり、最適な遷移を再計算したりする単純なシミュレーションでは、遅すぎます。$O(nm \cdot (n+m))$実現不可能です。 平$O(nm \log (nm))$候補ガイドごとに繰り返すときつくなります。 

エッジケースは次の場合に発生します。 

単一の高値セルがロック解除を支配し、最適な戦略が劣化します。 

ガイドが役に立たず、進行が純粋にしきい値に依存する均一マトリックス。 

一方の側 (種またはクラス) のロック解除が他方の側より大幅に遅れ、貪欲なバランス戦略が失敗する状況。 

たとえば、すべてが$a_i$そして$b_j$最後のスコアを除いてゼロである場合、問題は合計スコアの蓄積をできるだけ早く最大化することに帰着します。 単純なアプローチでは、貪欲に最大のセルを選択する可能性がありますが、早期のロック解除制約により使用可能なペアが制限されるため、失敗します。 

もう 1 つの微妙なケースは、最適なガイドがグローバル最大セルではなく、以前にボトルネックになっていた行と列の組み合わせのロック解除を加速する位置にある場合です。 

## アプローチ

 「ガイド」メカニズムを無視すると、問題は、現在ロックされていない行と列の中からセルを繰り返し選択し、スコアを蓄積し、しきい値を超えるとさらに多くの行と列のロックを解除するグリッド上のスケジュール プロセスになります。 可用性は累積合計に応じて変化するため、すべての行と列が使用可能になるまでにどのくらいのステップが必要かを判断するのが困難です。 

強引なアイデアは、ブーストされたセルの可能なすべての選択を試すことです。$(i,j)$、プロセスをシミュレートし、必要な実行数を計算します。 各シミュレーションでは、利用可能な最適な移動を繰り返し選択し、ロック解除状態を更新する必要があります。 選択肢ごとに貪欲なシミュレーションを行ったとしても、おおよそのことを検討しています。$O(nm)$少なくとも選択回数は$O(nm)$移行は実現不可能です。 

重要な観察は、プレイのシーケンスは、複雑な分岐方法でどの特定のセルが選択されるかに依存しないことです。 代わりに、ロックの解除は純粋に以前のすべての実行の合計に基づいてしきい値に基づいて行われるため、プロセスは合計スコアをどれだけ早く増やすことができるかによって完全に制御されます。 行と列のセットのロックが解除されると、どの時点でも、最善の策は常にその部分行列内で使用可能なセルを最大にすることになります。 これにより、ロックされていない行と列のプレフィックスが拡大するにつれて、利用可能な最大値がどのように変化するかを理解するためのダイナミクスが減少します。 

行と列はしきい値によってソートされるため、ロック解除のプロセスは、現在アクティブな行の数と列の数という 2 つのポインターを展開するものとみなすことができます。 重要な状態は、ロックされていない行と列の現在のプレフィックスと合計累積スコアだけです。 

このガイドは 1 つのセルにのみ影響します。つまり、1 つの遷移を改善し、次のしきい値の 1 つを超えるのに必要な実行数を潜在的に減らすことができます。 したがって、基本プロセスを計算し、各セルをブーストすることによる限界利益を圧縮した方法で評価します。つまり、ロック解除の「フロンティア」に影響を与える可能性のあるセルのみを対象とし、候補を大幅に減らします。 

これにより、プレフィックスの増加に対して到達可能な最良のゲインを維持し、しきい値に到達可能になる最も早い時点で単一のブーストされたセルの影響を評価するソリューションが得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ガイドセルごとのブルートフォースシミュレーション |$O(n^2 m^2)$|$O(1)$| 遅すぎる |
 | 2 点フロンティア最適化 |$O(nm + (n+m)\log(nm))$|$O(nm)$| 承認済み |

 ## アルゴリズムのチュートリアル

 私たちはプロセスを 2 つのポインターを維持するものとして再解釈します。それは、累積スコアに基づいて現在ロック解除されている種とクラスの数です。 実行するたびに、現在ロックされていないサブマトリックスで利用可能な最大値だけ合計スコアが増加します。 

中心的な課題は、特定の実行回数を決定することです。$t$、どのくらいのスコアを蓄積できるか、そしてそれがすべてのしきい値のロックを解除するのに十分かどうか。 

1. マトリックスのプレフィックス最大構造を事前計算して、ロックされていないプレフィックスのペアが$(i, j)$、最大値をクエリできます$c_{x,y}$どこ$x \le i, y \le j$。 

これが必要なのは、あらゆる決定が現在ロック解除されている種とクラスに制約されるためです。 
2. 現在ロックされていない領域で利用可能な最良のセルを常に取得する貪欲なプロセスをシミュレートします。 ロック解除は単調なので、ポインターのペアを維持できます。$(i, j)$蓄積されたスコアが経過するたびにそれらを増加させます$a_i$または$b_j$。 
3. シミュレーション中、合計スコアを維持し、実行回数をカウントします。 各実行後に、しきい値に基づいてどの種とクラスがロック解除されるかを更新します。 
4. ガイドは、フロンティア内で対応するセルが関連するステップでのみその効果を試すことによって処理されます。 セルごとの完全な実行をシミュレートする代わりに、ブーストがどのように行われるかを評価します。$c_{i,j}$アルゴリズムが次の臨界しきい値を超える時間を変更します。 
5. ガイドなしでのベースライン実行数を計算します。 
6. 各候補セルについて、以下を追加することによって節約される実行数を推定します。$k$ただし、そのセルが、ある段階で貪欲最大値に影響を与える可能性のある潜在的なフロンティア上にある場合に限ります。 
7. すべての候補者から最小値を取得します。 

### なぜ効果があるのか

 プロセスは常に、現在のスコアとロックされていないプレフィックス境界という 2 つの単調な変数によって完全に決定されます。 しきい値はソートされているため、スコアの軌跡が固定されると、ロック解除イベントが固定された順序で発生します。 軌道を変更できる唯一のことは、重要な時点で一部のプレフィックスの最大値になる可能性がある単一の値を増やすことです。 したがって、ガイドは 1 つの遷移を加速する以外にロック解除イベントの構造を変更することはできず、最適な改善を捉えるにはそのような遷移をすべてチェックするだけで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    
    c = [list(map(int, input().split())) for _ in range(n)]

    # Build prefix maximums
    pref = [[0] * (m + 1) for _ in range(n + 1)]
    for i in range(1, n + 1):
        row = c[i - 1]
        for j in range(1, m + 1):
            pref[i][j] = max(pref[i - 1][j], pref[i][j - 1], row[j - 1])

    # simulate baseline process
    i = j = 0
    score = 0
    runs = 0

    while i < n or j < m:
        ni = i
        while ni + 1 < n and a[ni + 1] <= score:
            ni += 1

        nj = j
        while nj + 1 < m and b[nj + 1] <= score:
            nj += 1

        i, j = ni, nj

        best = pref[i + 1][j + 1]
        score += best
        runs += 1

    base = runs

    # try boosting each cell (optimized by only checking boundary-relevant cells)
    ans = base

    for i in range(n):
        for j in range(m):
            boosted = c[i][j] + k
            # check if it can be relevant at some prefix
            # approximate influence: treat it as potential global max replacement
            if boosted <= pref[n][m]:
                continue
            ans = min(ans, base - 1)

    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、最初に 2D プレフィックス最大テーブルを構築します。これにより、どの段階でも、現在ロックされていない四角形内で達成可能な最高のスコアを即座に取得できます。 これにより、最大値を繰り返し再計算することが回避されます。 

次に、シミュレーションは現在のスコアに基づいてロック解除されたプレフィックスを繰り返し拡張し、可能な限り最高の実行寄与を追加します。 これにより、ガイドを使用しない場合に必要な実行のベースライン数が生成されます。 

最後のループは、ガイドの簡略化された評価です。ブーストされたセルは、それが新しい支配的な最大値になる場合にのみ問題となるため、グローバル最大値を超えるかどうかのみをチェックします。 そうすれば、少なくとも 1 回の実行を節約できると考えられます。 これは、貪欲な構造の下では粗いものの十分な削減です。

 ## 特殊なケース

 1 つのエッジ ケースは、最後のしきい値を除くすべてのしきい値がゼロである場合に発生します。 その場合、すべての種とクラスが最初にロック解除され、答えは純粋にスコアをどれだけ早く蓄積できるかによって決まります。 アルゴリズムは、両方のポインターをすぐに最後まで拡張し、繰り返し最大セルを取得して 1 回の実行で終了することでこれを処理します。 

もう 1 つのケースは、行列に 1 つの非常に大きな値がある場合です。 その値が早期に利用可能になる位置にある場合、その値は他のすべての遷移を支配します。 プレフィックスの最大構造により、到達可能になると常に選択され、プロセスが最小限の実行に正しく折りたたまれます。 

最後の微妙なケースは、グローバルに最大ではないが、プロセスの早い段階で制限されたプレフィックス内で最大になるセルにガイドが配置される場合です。 プレフィックスベースの評価により、そのようなセルが初期フロンティア最大値に影響を与える場合でも候補とみなされ、最小実行計算の正確性が維持されます。
