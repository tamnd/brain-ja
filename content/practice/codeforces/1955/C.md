 ## 解決策
 ## 問題の理解

 私たちには一定の耐久性を持つ一連の船と、常に現在の左端の生存船、次に現在の右端の生存船をターゲットとする固定攻撃パターンが与えられ、合計が 1 になるまでこの交互を繰り返します。$k$攻撃が行われたか、すべての船が沈没しました。 

攻撃ごとに、選択した船の耐久性が 1 つだけ減少します。 船がゼロに達すると、その船はラインから消え、残りの船がギャップを埋めるため、新しい「最初」と「最後」は常に、残っている生存セグメントに対して定義されます。 課題は、すべての攻撃が実行された後に何隻の船が完全に沈没するかを決定することです。 

重要な問題は制約サイズにあります。 まであります$10^4$テスト ケース、およびすべてのテストにわたる船舶の合計数は最大です。$2 \cdot 10^5$、しかし攻撃の数$k$と同じ大きさにすることができます$10^{15}$。 これにより、攻撃ごとに 1 つの操作を実行するシミュレーションは直ちに除外されます。 攻撃ごとにリニアスキャンさえ不可能です。$k$矮小化できる$n$何桁も大きい。 

単純なシミュレーションでは、両端からの繰り返しの削除にも苦労します。 リストとポップまたはシフトを使用して実装すると、リスクが発生します$O(n)$削除ごとに実行されますが、最悪の場合は遅すぎます。 

片側が予想よりも早く空になると、微妙な障害モードが表示されます。 たとえば、すべての小さな値が片側に集中している場合、単純な交互アプローチでは、明示的に処理しない限り、一方の端が使い果たされた後でも誤って「切り替え」を続ける可能性があります。 

## アプローチ

 直接的な総当たりアプローチは簡単です。2 つのポインタを維持します。$l$そして$r$、各攻撃をシミュレートし、選択したエンドポイントをデクリメントし、船がゼロに達したときにポインターを内側に移動します。 これは文字通りプロセスを反映しているため、これは正しいです。 ただし、それぞれの攻撃は、$O(1)$、までありますが、$10^{15}$攻撃を制限時間内に実行することは不可能です。 

重要な観察は、実際にはすべての攻撃を個別にシミュレートする必要がないということです。 重要なのは、いずれかのエンドポイントが使い果たされるまでに、各エンドポイントが何回の攻撃を消費するかです。 いつでも、左右の次の船がゼロになるか、相手側が優勢になるまで繰り返し攻撃されます。 

交互の操作という観点から考えるのではなく、プロセスをブロックに圧縮します。 利用可能な攻撃バジェットを比較するとき、私たちは常に 2 つのエンドポイントのうち小さい方を完全に使い果たすように努めます。 双方が生存している場合は、現在の耐久性を比較し、攻撃を一括して割り当てます。つまり、左の船が最初に破壊されるか、右の船が最初に破壊されるかのどちらかです。 これにより、プロセスが両端からの一連の削除となり、それぞれが一定時間内に実行されます。 

船が削除されると、更新されたエンドポイントと残りの作業が続行されます。$k$。 各船は最大 1 回除去されるため、合計作業量はすべてのテスト ケースにわたって直線的になります。

 ## アルゴリズムのチュートリアル

 生存セグメントの左端に 1 つ、右端に 1 つという 2 つのポインターと、沈没船の数を示すカウンターを維持します。 

1. 2 つのインデックスを初期化する$l = 0$、$r = n - 1$、沈没船のカウンターはゼロです。 現在の左右の船の残りの耐久性も追跡します。 
2. その間$l \le r$そしてまだ攻撃が残っている$k > 0$、耐久力の小さい方に基づいてどちらの側が最初に攻撃されるかを決定します。$a[l]$そして$a[r]$。 交流圧力では耐久性の小さい側の方が早く消耗するためです。 
3. もし$a[l] \le a[r]$, 現在のバランスでは、左側の船が最初に完全に破壊されると仮定します。 残り攻撃力が足りているか比較する$k$完全に減らす$a[l]$。 そうでない場合は、これ以上船を沈めることはできないため、すぐに停止します。 
4. それ以外の場合は減算します$a[l]$から$k$、沈んだカウンターをインクリメントし、移動します$l$一歩右へ。 次に、次のようにして右の船の耐久性を減らします。$a[l]$というのは、左の船を倒す過程で、半分の確率で右の船も攻撃されたからです。 この再配分は、交互の攻撃パターンを反映しています。 
5. The symmetric case applies when$a[r] < a[l]$: 最初に適切な船を完全に消費し、差し引きます$a[r]$から$k$、カウンターをインクリメントし、移動します$r$残して減らす$a[l]$それに応じて。 
6. どこかの時点で船の耐久性がゼロになった場合、ポインタを動かすことで暗黙的に耐久性が削除され、次のペアに進みます。 

核となる考え方は、各作戦で少なくとも 1 隻の船を除去するため、ループは実行できるのは 1 つだけであるということです。$O(n)$回。 

### なぜ効果があるのか

 アルゴリズムはキーの不変条件を保持します。つまり、各ステップの後、残りの値は$k$は、縮小されたセグメントにまだ適用する必要がある攻撃の数を正確に表しており、両方のエンドポイントは反対側からの以前のすべてのクロス攻撃を反映しています。 

各反復で少なくとも 1 つのエンドポイント (2 つのエンドポイントのうち小さい方) が完全に解決されるため、交互構造に違反するような方法で船が部分的に再訪されることはありません。 このプロセスは、1 つのエンドポイントが最初に停止することが保証される最大セグメントに交互攻撃をグループ化することに相当します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))

        l, r = 0, n - 1
        ans = 0

        while l < r and k > 0:
            if a[l] <= a[r]:
                if k < a[l]:
                    break
                k -= a[l]
                a[r] -= a[l]
                l += 1
                ans += 1
            else:
                if k < a[r]:
                    break
                k -= a[r]
                a[l] -= a[r]
                r -= 1
                ans += 1

        if l == r and k > 0:
            ans += 1 if k >= a[l] else 0

        print(ans)

if __name__ == "__main__":
    solve()
```この実装では、2 つのポインターを使用して船のアクティブなセグメントを表します。 各ループの反復では、残りの耐久性が小さい方に応じて、左側または右側から 1 隻の船が削除されます。 減算ステップは、一方の端に攻撃を集中させながら、反対側の端が交互にダメージを受けるという事実をモデル化します。 

最終チェックでは、船が 1 隻だけ残った場合を処理します。 残りの攻撃が十分であれば撃沈とカウントされます。 

微妙な点は、交互ターンを明示的にシミュレートすることは決してないということです。 代わりに、エンド間の耐久性の転送は、時間の経過とともに両端がインターリーブ方式で攻撃されるという事実を暗黙的に捉えます。

 ## 特殊なケース

 船が 1 隻だけ残っている場合、アルゴリズムは交互の動作から単一の線形消耗チェックに切り替わります。 たとえば、次の場合$a = [7]$そして$k = 5$、残りの攻撃が不十分であるため、追加の船は沈められません。 

片側が非常に小さい場合、次のようになります。$a = [1, 100, 100]$、左側の船はすぐに除去されますが、除去によって右側にわずかなダメージしか伝わりません。 このアルゴリズムは、対称的な枯渇を誤って仮定するのではなく、更新された値で正しく続行されます。 

いつ$k$運用中に枯渇すると、無効な減算を実行する前にループが中断され、マイナスの耐久性が導入されず、追加の船がカウントされないことが保証されます。
