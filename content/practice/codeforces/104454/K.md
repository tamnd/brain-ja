 ## 問題の理解

 タスクのコレクションが与えられ、各タスクには日単位で測定される独自の繰り返し期間があります。 タスクに価値がある場合$a_i$、最初に 0 日目に完了したら、再度何日目にも繰り返す必要があります。$a_i, 2a_i, 3a_i,\dots$、それらの日が次の期間内にある限り$k$私たちが計画している日々。 の値$a_i = 0$これは、タスクが最初の完了後に以降の繰り返しを生成しない特殊なケースです。 

目標は、毎日 1 から 1 までを決定することです。$k$、すべてのタスクを合わせてその日に必要なタスクの繰り返しの数。 

直接的な解釈は、すべてのタスクが将来の一連の日を「生み出す」ということです。 私たちは、計画ウィンドウで毎日これらのシーケンスが交差する数を数えています。 

制約により、最大で$10^5$タスクと$10^5$日々。 これにより、各タスクを毎日シミュレートするソリューションは除外されます。単純な伝播は次のような問題につながるためです。$O(nk)$最悪の場合の動作は、$10^{10}$操作は実行不可能です。 それぞれの倍数すべてを繰り返しても$a_i$更新の総数を慎重に制限する必要があるため、構造なしで個別に実行すると、遅すぎます。 

次の場合、微妙なエッジケースが発生します。$a_i = 0$。 この場合、不注意な実装により通常のステップ サイズのように処理しようとし、倍数を生成するときにゼロによる除算や無限ループが発生する可能性があります。 もう一つのエッジケースは、$a_i > k$、計画範囲内で繰り返しが発生することはありませんが、単純なループが不必要な処理を試行する可能性があります。 

たとえば、次の場合$n=2, k=6$そして$a = [0, 1]$の場合、最初のタスクは 0 日目以降は何も貢献しませんが、2 番目のタスクは 1 から 6 まで毎日貢献します。正しい出力は次のとおりです。$1,2,1,2,1,2$。 不適切な処理を行うソリューション$a_i=0$誤って伝播しようとしたり、クラッシュしたりする可能性があります。 

## アプローチ

 ブルートフォースアプローチは、問題を文字通りに解釈することから始まります。 各タスクについて、その期間の倍数を段階的に実行することによって、将来のすべての発生をシミュレートします。 倍数ごとに$d = a_i, 2a_i, 3a_i, \dots$まで$k$、日ごとにカウンターをインクリメントします$d$。 

これは、すべてのタスクの正確な寄与を直接構築するため、正しいです。 ただし、多くのタスクの値が小さい場合、コストが問題になります。$a_i$。 もし$a_i = 1$すべてのタスクについて、それぞれのタスクが毎日に貢献し、成果を生み出します$O(nk)$更新情報。 と$n = k = 10^5$、この結果は$10^{10}$実現可能な限界をはるかに超えています。 

重要な観察は、これが典型的な「ふるいのような蓄積」パターンであるということです。 各タスクを個別にシミュレーションするのではなく、タスクを期間ごとに集計します。 同じ値を共有するタスクの数を数えると$a$、それぞれが異なる$a$の倍数で繰り返し貢献する$a$。 これにより、タスクごとのシミュレーションから値ごとの頻度累積に切り替えることができます。 

周波数配列を取得したら$freq[a]$、可能なステップ サイズを反復するだけで済みます。$a$、そしてそれぞれについて、その寄与をすべての倍数に分配します。 これにより、除数やふるいの問題が最適化されるのと同様に、繰り返しの作業がグループ化された作業に変換されます。

 ## アルゴリズムのチュートリアル

 タスクのリストを繰り返し間隔の頻度表に変換します。 次に、貢献を複数にわたって効率的に伝播します。 

1. アレイを構築する`freq`どこ`freq[x]`繰り返し期間を持つタスクの数を正確に保存します`x`。 これにより、同一の動作がグループ化され、冗長な作業が回避されます。 
2. 回答配列を作成する`ans`サイズの`k`、ゼロに初期化されます。 各ポジション`ans[d]`一日に発生するタスクの数を保存します`d`。 
3. 考えられる各期間値について`x`1から`k`、 もし`freq[x] > 0`、その貢献をすべての倍数に分配します。`x`範囲内です。 これは繰り返しを意味します`d = x, 2x, 3x, ... ≤ k`そして追加`freq[x]`に`ans[d]`。 
4. すべてのタスクを無視します。`a_i = 0`なぜなら、それらは将来の繰り返しには決して寄与しないからです。 
5. 配列を出力する`ans[1..k]`。 

各期間クラスは、一定の間隔でタイムラインを伝播する「波」のように動作します。 グループ化すると、各 Wave がタスクごとに 1 回ではなく 1 回処理されるようになります。 

### なぜ効果があるのか

 いつでも$d$、ピリオドのあるタスク$x$正確にいつ貢献するか$d$の倍数です$x$。 アルゴリズムにより、それぞれの$x$、そのような倍数ごとにその周波数を加算します。 すべてのタスクは頻度バケット内で正確に 1 回カウントされ、有効日に正確に追加されるため、過剰カウントや欠落は発生しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))
    
    freq = [0] * (k + 1)
    
    for x in a:
        if x != 0 and x <= k:
            freq[x] += 1
    
    ans = [0] * (k + 1)
    
    for x in range(1, k + 1):
        if freq[x] == 0:
            continue
        for d in range(x, k + 1, x):
            ans[d] += freq[x]
    
    print(*ans[1:k+1])

if __name__ == "__main__":
    solve()
```コードは、各繰り返し間隔を共有するタスクの数をカウントすることから始まります。 小切手`x != 0`ゼロでは有効な日数の等差数列が生成されないため、無効なステップ サイズを回避します。 2番目の条件`x <= k`時間枠内で実際に現れる可能性のある間隔のみを処理するようにします。 

入れ子になったループ構造が中心的な伝播ステップです。 期間ごとに`x`、その倍数にアクセスし、対応する日カウンターをインクリメントします。 これは、周期的な出来事の数学的定義を反映しています。 

微妙な点の 1 つはインデックス付けです。回答配列のサイズが決まります。`k+1`これにより、日付のインデックスが配列の位置と自然に整列し、書き込み時の off-by-one エラーが回避されます。`ans[d]`。

def run(inp: str) -> str:

    import sys
    input = sys.stdin.readline

 ## 特殊なケース

 重要なエッジケースは、すべての値がゼロの場合です。 この状況では、伝播は発生せず、出力は完全にゼロでなければなりません。 度数表ではゼロが除外されるため、ネストされたループによって寄与が追加されることはありません。 

もう 1 つのケースは、すべての値が 1 に等しい場合です。すべてのタスクが毎日に貢献し、アルゴリズムはすべての周波数をすべての位置に蓄積します。 以来`freq[1] = n`、毎日になります。`n`。 

値を超える場合`k`、伝播ループ内で有効なインデックスとして現れることはありません。 これらは安全に無視されます。`x <= k`チェックして、無駄な反復を防止し、特別な処理を行わずに正確性を確保します。 

最後に、多数の小さな値と大きな値の組み合わせなどの混合分布は、グループ化の利点を示しています。 小さな値が実行時間の大半を占めますが、グループ化により、それぞれがタスクごとではなく除数チェーンごとに 1 回処理されるようになります。
