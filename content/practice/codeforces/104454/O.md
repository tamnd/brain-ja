 ## 解決策
 ## 問題の理解

 グリッドは 10 × 10 の固定戦場で、各セルは水または船の一部です。 船はクエリを開始する前にすでに正しく配置されており、すべての船は水平または垂直に隣接するセルによって形成された接続された形状です。 合計でちょうど 10 隻の船があり、そのサイズは既知の分布に従っています。4 隻の船は 1 つのセルで構成され、3 隻の船が 2 つのセルを占有し、2 隻の船が 3 つのセルを占有し、1 隻の船が 4 つのセルを占有します。 

このグリッドを読み取った後、一連のコマンドを処理します。 1 つのタイプのコマンドは特定のセルへの砲撃をシミュレートし、もう 1 つのタイプはすべての艦艇の現在の状態の報告を要求します。 船は、攻撃を受けたセルの数に応じて、完全に無傷、部分的に損傷、または完全に破壊された 3 つの状態のいずれかになります。 

出力要件は、2 番目のタイプのコマンドにのみ関連付けられます。 レポート クエリごとに、まだ攻撃を受けていない船の数、攻撃を受けたが破壊されていない船の数、その時点で完全に破壊された船の数を出力する必要があります。 

制約は非常に小さく、グリッドは 100 セルに固定され、コマンドの数は最大 100 です。これにより、高度なデータ構造や漸近的に最適化されたクエリ処理の必要性が即座に排除されます。 クエリごとに完全な船の状態を再計算することも許容されますが、状態を増分的に維持することで、より良い結果を得ることができます。 

主な微妙な点は、単純なアプローチでは、繰り返されるショットを二重にカウントしたり、接続されたコンポーネントを事前計算せずにその場で船のアイデンティティを推測しようとしたりすると、失敗することがよくあることです。 もう 1 つのよくある間違いは、各 SHOW で船の状態を最初から再計算することです。これは安全ですが不要であり、一貫性のない部分的なヒットを追跡する場合に間違いやすくなります。 

具体的なエッジケースは、同じセルが複数回ショットされる場合に発生します。 たとえば、サイズ 2 の船が 1 つのセルで攻撃を受け、その後その同じセルが再びターゲットになった場合、最初のショットのみが船の状態を変更します。 SHOT コマンドごとにヒット数を増加させる不用意な実装は、船が早すぎる沈没として誤ってマークされてしまいます。 

もう 1 つのエッジ ケースは、射撃の前に発行される SHOW コマンドです。このコマンドでは、すべての船舶が無傷であると報告されなければなりません。 ヒット カウントを遅延して初期化するロジックは、これらの初期のクエリを誤って分類する危険性があります。 

## アプローチ

 最も直接的なアイデアは、各 SHOT を独立して処理し、SHOW が表示されるたびに、グリッド全体をスキャンしてどのセルがヒットしたかを確認することによって、すべての船の状態を最初から再計算することです。 これはグリッドが小さいため機能しますが、各 SHOW が 100 個のセルのフル スキャンとグループ化ロジックの繰り返しをトリガーする可能性があるため、概念的には非効率になります。 最大 100 個のクエリではこれでも許容できますが、責任が混在し、シップ メンバーシップとヒット追跡が繰り返し再構築されるため、誤って実装されやすくなります。 

より構造化されたアプローチは、問題を 2 つのフェーズに分けることです。 まず、グリッド上のフラッドフィルを使用して、すべての船舶を一度識別します。 各船は、セルの固定リストと既知のサイズを持つコンポーネントになります。 次に、船ごとに、攻撃を受けたセルの数を追跡する小さな状態を維持します。 すべてのショットで 1 つのセルが更新され、セルから出荷までの直接マッピングを使用して、対応するコンポーネントを一定時間で更新します。 これにより、現在のヒット数に基づいて各船を分類するだけで済むため、SHOW クエリが簡単になります。 

重要な洞察は、船のアイデンティティは決して変化せず、ダメージだけが蓄積するということです。 接続コンポーネントを事前計算すると、問題の動的部分は、これらのコンポーネントに対するカウンターの維持に減ります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | SHOW ごとに再計算する | O(q · 100) | O(100) | 承認済み |
 | 事前計算 + 増分更新を出荷 | O(100 + q) | O(100) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、グリッドをラベル付きの船舶のセットに変換して、すべてのセルがどの船舶に属しているかを認識できるようにします。 

1. グリッドのすべてのセルをスキャンします。 まだ船舶に割り当てられていない船舶セグメントを含むセルを見つけるたびに、そのセルからフラッドフィルを開始します。 このフラッドフィルは、接続されているすべての船舶セルを収集し、それらに同じ船舶識別子を割り当てます。 このステップが必要なのは、後のアップデートが個々のセルだけでなく船全体に影響を与える必要があるためです。 
2. 発見された各船について、そのサイズを保存し、ヒットしたセルの数のカウンターを初期化します。 この時点では、まだショットが発生していないため、すべてのヒット カウンタはゼロです。 
3. 各グリッド セルから船舶 ID への直接マッピングを構築するか、船舶の一部ではない場合は水としてマークします。 これにより、SHOT コマンド中に一定時間のルックアップが可能になります。 
4. セルがすでにショットされているかどうかを追跡するブール グリッドを維持します。 同じセルへのショットの繰り返しで状態を複数回変更してはいけないため、これは重要です。 
5. 各コマンドを順番に処理します。 SHOT コマンドが到着したら、座標をセルに変換します。 セルがすでに撃たれている場合は、完全に無視します。 それ以外の場合は、それをショットとしてマークし、セルが船に属している場合は、その船のヒットカウンターをインクリメントします。 
6. SHOW コマンドが表示されると、すべての船舶を反復処理して、それぞれを分類します。 ヒット数がゼロの場合、ダメージはありません。 ヒット数がそのサイズと同じ場合、沈没します。 それ以外の場合は、部分的にヒットします。 

正確さは、すべてのセルが正確に 1 つの船に寄与し、各セルが非ショットからショットへ 1 回しか移行できないという事実に依存します。 

### なぜ効果があるのか

 プロセス全体を通じて維持される不変条件は、各船のヒット カウンターが、それまでに撃たれたその船の個別のセルの数と正確に等しいということです。 繰り返されるショットの二重カウントを明示的に防止するため、すべての増分は新しくヒットした一意のセルに対応します。 船のメンバーシップは最初の満水から固定されるため、SHOW 中の分類は単に船のサイズに対するこのカウンターの関数であり、無損傷、被弾、沈没の定義と正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

n = 10
grid = [input().strip() for _ in range(10)]

ship_id = [[-1] * 10 for _ in range(10)]
ships = []

dx = [1, -1, 0, 0]
dy = [0, 0, 1, -1]

def bfs(sx, sy, idx):
    q = deque()
    q.append((sx, sy))
    ship_id[sx][sy] = idx
    cells = [(sx, sy)]
    
    while q:
        x, y = q.popleft()
        for k in range(4):
            nx, ny = x + dx[k], y + dy[k]
            if 0 <= nx < 10 and 0 <= ny < 10:
                if grid[nx][ny] == '#' and ship_id[nx][ny] == -1:
                    ship_id[nx][ny] = idx
                    q.append((nx, ny))
                    cells.append((nx, ny))
    
    return cells

for i in range(10):
    for j in range(10):
        if grid[i][j] == '#' and ship_id[i][j] == -1:
            cells = bfs(i, j, len(ships))
            ships.append({
                "size": len(cells),
                "hits": 0
            })

shot = [[False] * 10 for _ in range(10)]

q = int(input())
for _ in range(q):
    cmd = input().split()
    
    if cmd[0] == "SHOT":
        x = int(cmd[1]) - 1
        y = int(cmd[2]) - 1
        if not shot[x][y]:
            shot[x][y] = True
            sid = ship_id[x][y]
            if sid != -1:
                ships[sid]["hits"] += 1
    
    else:
        undamaged = 0
        hit = 0
        sunk = 0
        
        for s in ships:
            if s["hits"] == 0:
                undamaged += 1
            elif s["hits"] == s["size"]:
                sunk += 1
            else:
                hit += 1
        
        print(undamaged, hit, sunk)
```コードは、グリッドを読み取り、BFS フラッド フィルを使用してすべての船舶セルをグループ化することから始まります。 検出された各コンポーネントは、そのサイズと変更可能なヒット カウンターとともに保存されます。 の`ship_id`マトリックスは、任意のセルからその船までの一定時間のマッピングを提供します。 

シミュレーション中に、`shot`マトリックスは二重カウントを防ぎます。 ターゲット セルが船に属している場合、有効な新しいショットごとに、正確に 1 つの船のカウンターが増加します。 

SHOW クエリの場合は、すべての船舶を単純にスキャンし、蓄積された損傷状態に基づいて分類します。 

よくある実装の落とし穴は、入力座標を 1 ベースのインデックスから 0 ベースのインデックスに変換するのを忘れることです。これにより、すべてのショットが静かにシフトされ、クラッシュすることなく誤った分類が生成されます。

 個々の船舶の ID は抽象的であるため、船舶を高レベルでのみ追跡しますが、数の推移は明示的です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

| スペース | O(100) | グリッド、船舶マッピング、小型船舶メタデータ配列 |

 ## 特殊なケース

 船のないグリッドは、フラッド フィルでコンポーネントが見つからないため、自然に処理されます。そのため、すべての SHOW クエリは空のリストを反復処理し、すべて 0 を返します。 

単一の大型船により、部分的な損傷と完全な破壊が正確に区別されます。 このアルゴリズムは、その船の 1 つのカウンターを増分し、カウンターがその合計サイズと等しい場合にのみ沈没として分類します。 

同じセルでショットを繰り返してもカウンターには影響しません。`shot`マトリックスは繰り返しの更新をブロックします。 これにより、各船のセルがヒット カウントに最大 1 回だけ寄与するという不変条件が維持され、誤って早期沈没を引き起こす過剰カウントが防止されます。
