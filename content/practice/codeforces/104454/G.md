 ## 解決策
 ## 問題の理解

 すでに建設された道路で接続された都市の集合が与えられ、無向グラフを形成します。 これらの都市のいくつかには、ビールを 1 単位ずつ保管する醸造所があり、いくつかの都市にはイーゴリが開設を望んでいる工場もあります。 工場を開くとビール 1 樽が消費されます。重要な制限は、ビール樽はグラフの同じ接続コンポーネント内の道路に沿ってのみ輸送できることです。 

醸造所の中には Igor に属するものと、他のプレイヤーに属するものがあります。 イゴールはいつでも自分の樽を制限なく使用できますが、他人の樽を使用する必要がある場合、それはその醸造所の都市から工場の都市までの道がある場合にのみ機能します。 

課題は、接続性の制約を考慮して、最初に自分のビール樽を貪欲に使用し、必要な場合にのみ他のビール樽を使用すると仮定して、イーゴリが自分のビール醸造所から何個のビール樽を取るか、また他のプレーヤーから何個を取ることを強制されるかを決定することです。 

入力サイズは最大 100,000 の都市、工場、醸造所、道路に及ぶため、醸造所と工場のすべてのペア間の移動をシミュレートしようとするソリューションは不可能です。 グラフに対する単純な全ペアの到達可能性チェックでは、関連するノードの数が少なくとも 2 次の動作につながり、これは許容制限をはるかに超えます。 

正しいソリューションでは、すべての到達可能性クエリがパス検索ではなくローカル カウントになるように、グラフ構造を連結コンポーネントに圧縮する必要があります。 

Igor に十分な合計醸造所があるにもかかわらず、それらが接続されていないコンポーネントに分割されている場合、微妙なエッジ ケースが発生します。 たとえば、2 つのコンポーネントがあり、1 つは 5 つの工場と 5 つの Igor の醸造所を含み、もう 1 つは 5 つの工場があるが Igor の醸造所はなく、敵対する醸造所のみを含むとします。 世界的には Igor は十分なビールを持っていますが、ローカルではコンポーネント間でビールを転送できないため、2 番目のコンポーネントで相手のビールを使用する必要があります。 

もう 1 つのエッジ ケースは、同じ都市に複数の醸造所や工場が存在する場合です。 これらは、単一の存在フラグとしてではなく、カウントの多重度として扱われる必要があります。 

## アプローチ

 強引な解釈では、すべての工場とすべての醸造所の間の到達可能性をシミュレートします。 工場ごとに、到達可能な醸造所を見つけて、それを使用済みとしてマークし、すべての工場が満足するまで続行します。 各到達可能性チェックには、BFS や DFS などのグラフの走査が必要です。また、最大 100,000 の工場や醸造所が存在する可能性があるため、最悪の場合、大きなグラフの走査が繰り返され、実装の詳細や訪問した状態の再利用に応じて、O(MG + KG) かそれ以上のオーダーの複雑さが生じます。 これはすぐに実行不可能になります。 

重要な観察は、道路が都市を接続されたコンポーネントに分割しており、各コンポーネント内では、どの醸造所もどの工場にもサービスを提供できるということです。 接続性がわかってしまえば、コンポーネント内の正確なパス構造は問題になりません。 重要なのは、各接続コンポーネント内に各タイプの工場や醸造所がいくつ存在するかだけです。 

これにより、問題はコンポーネントにわたる計数問題に変換されます。 各コンポーネントについて、その中に工場が何社あるのか、その中にイゴールの醸造所が何社あるのか、そして敵の醸造所が何社いるのかがわかっていれば、そこで使用されているイゴールの樽の数をローカルで計算できます。これは単に、そのコンポーネントのイゴールの醸造所とそのコンポーネントの工場の間の最小値です。 そのコンポーネント内の残りの工場は、相手の醸造所によって満たされる必要がありますが、これも同じコンポーネント内の可用性によって制限されます。 

したがって、グラフは、素セット共用体構造または BFS ラベル付けを使用してコンポーネントに縮小され、すべてのオブジェクトがコンポーネントごとに集約されます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ファクトリごとのブルート フォース BFS/DFS | O(M · (N + G)) | O(N + G) | 遅すぎる |
 | DSU / 接続コンポーネントの集約 | O(N + G + M + K + L) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 この問題は、グラフを接続されたコンポーネントに折りたたみ、各コンポーネント内のリソースをカウントすることで解決します。 

1. 都市およびすべての道路のユニオン エンドポイント上に素のセット ユニオン構造を構築します。 このステップでは、ビールを交換できるすべての都市をグループ化します。 
2. すべての道路を処理した後、各都市の代表的な親を計算して、すべての都市が単一の接続コンポーネント ID にマップされるようにします。 このステップでは、グラフのパーティションを定義します。 
3. コンポーネントによってインデックス付けされた 3 つの配列またはハッシュ マップを作成します。1 つは工場の数用、1 つは Igor の醸造所用、もう 1 つは敵の醸造所用です。 最初はすべての値がゼロです。 
4. すべての工場を反復処理し、その都市を含むコンポーネントの工場数を増やします。 これにより、空間需要がコンポーネントごとの需要に変換されます。 
5. すべての Igor 醸造所を反復処理し、対応するコンポーネント内の Igor のビール数を増やします。 これにより、供給量が現地での入手可能量に変換されます。 
6. すべての対戦相手のビール醸造所を反復処理し、コンポーネントごとに対戦相手のビール数を増やします。 これにより、到達可能性の制約によって海外からの供給が分離されます。 
7. 各コンポーネントについて、そのコンポーネント内の工場数とイゴール醸造所数の最小値として、イゴールのビールで満足できる工場の数を計算します。 これを Igor の使用法に対する回答に追加します。 
8. Igor の使用後にそのコンポーネント内に残っている不満足なファクトリを計算します。 これらはできれば相手ビールで満たさなければならないため、最低限の残り工場と相手ビール醸造所数を相手使用量に加えてください。 

これが機能する理由は、接続が転送の実現可能性を完全に決定するという事実から来ています。 コンポーネント内では、そのコンポーネント内の都市のすべてのペアの間にパスが存在するため、あらゆる供給を需要に任意に一致させることができます。 コンポーネント間での転送は不可能であるため、すべての一致の決定はコンポーネントごとに独立して分解されます。 これにより、グローバル最適化は、接続された各コンポーネントでの独立したローカル グリーディ マッチングと同等になります。また、すべてのバレルが同一で交換可能であるため、コンポーネント内のグリーディは最適です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class DSU:
    def __init__(self, n):
        self.p = list(range(n + 1))
        self.r = [0] * (n + 1)

    def find(self, x):
        while self.p[x] != x:
            self.p[x] = self.p[self.p[x]]
            x = self.p[x]
        return x

    def union(self, a, b):
        a = self.find(a)
        b = self.find(b)
        if a == b:
            return
        if self.r[a] < self.r[b]:
            a, b = b, a
        self.p[b] = a
        if self.r[a] == self.r[b]:
            self.r[a] += 1

def main():
    n = int(input())
    m = int(input())
    factories = list(map(int, input().split()))
    k = int(input())
    igor = list(map(int, input().split()))
    l = int(input())
    others = list(map(int, input().split()))
    g = int(input())

    dsu = DSU(n)

    for _ in range(g):
        a, b = map(int, input().split())
        dsu.union(a, b)

    comp_fact = {}
    comp_igor = {}
    comp_other = {}

    for city in factories:
        c = dsu.find(city)
        comp_fact[c] = comp_fact.get(c, 0) + 1

    for city in igor:
        c = dsu.find(city)
        comp_igor[c] = comp_igor.get(c, 0) + 1

    for city in others:
        c = dsu.find(city)
        comp_other[c] = comp_other.get(c, 0) + 1

    igor_used = 0
    other_used = 0

    for c in comp_fact:
        f = comp_fact[c]
        i = comp_igor.get(c, 0)
        o = comp_other.get(c, 0)

        use_i = min(f, i)
        igor_used += use_i

        remaining = f - use_i
        other_used += min(remaining, o)

    print(igor_used, other_used)

if __name__ == "__main__":
    main()
```このソリューションは、グラフを読み取り、都市上に DSU を構築することから始まります。DSU では、すべての道路が 2 つの都市を単一の接続されたコンポーネントに統合します。 これにより、到達可能性クエリが DSU ルートと等しくなることが保証されます。 

その後、プログラムはハッシュ マップを使用してコンポーネントごとのカウントを集計します。 入力リストに表示される都市のみが重要であるため、これは重要です。 すべてのカテゴリに対してサイズ N の配列は必要なく、スパース辞書で十分です。 

最後に、各コンポーネントは個別に処理されます。 各コンポーネント内での貪欲な決定 (最初に Igor のビールを使用する) は安全です。コンポーネント間での転送は不可能であるため、あるコンポーネントの Igor のビールを別のコンポーネント用に確保するメリットはありません。 

よくある実装の落とし穴は、カウント時に DSU ルートを取り忘れたり、都市インデックスとコンポーネント インデックスを混合したりすることです。 もう 1 つの微妙な問題は、ビールが世界的に十分に足りると仮定することです。 コンポーネントごとに正しいロジックが常に維持される必要があります。 

## 実用的な例

 ### サンプル 1

 ファクトリー: [1、4、3、2]

 イゴール醸造所: [2, 8]

 対戦相手のブルワリー: [8, 7, 6, 5]

 道路はコンポーネントを接続します: {1,2,3,4,5}、{6}、{7,8}

 コンポーネントの割り当てを計算します。 

| コンポーネント | 工場 | イゴール・ビール | 相手のビール | イゴールが使用 | 相手が使用した |
 | --- | --- | --- | --- | --- | --- |
 | C1 (1-5) | 4 | 1 | 1 | 1 | 1 |

 このトレースは、Igor には世界的に 2 つの醸造所があるにもかかわらず、主要な需要コンポーネントで役立つのは 1 つだけであることを示しています。 

### サンプル 2

 この場合、グラフ構造により複数の絡み合ったコンポーネントが作成され、主な影響は、Igor の供給が不均一な地域に工場が分割されることです。 コンポーネントごとの貪欲なマッチングにより、Igor のビールが最初に地元で消費され、その後に初めて相手のビールが使用されることが保証されます。 

| コンポーネント | 工場 | イゴール・ビール | 相手のビール | イゴールが使用 | 相手が使用した |
 | --- | --- | --- | --- | --- | --- |
 | C1 | 2 | 1 | 2 | 1 | 1 |
 | C2 | 3 | 1 | 1 | 1 | 2 |

 合計はそれぞれ 2 と 3 になり、必要な出力と一致します。 

この痕跡は、ある成分で過剰な相手ビールが別の成分で不足しているビールを補うことができないことを強調しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 |---|---|---|---|

 | 時間 | O(N + G + M + K + L α(N)) | DSU ユニオンに加え、すべてのリストを 1 回通過して検索します。 

| スペース | O(N + C) | DSU アレイとコンポーネントごとのマップ |

 すべての操作は入力のサイズにおいて線形に近いため、アルゴリズムは制限内で快適に実行されます。 DSU は、接続が効率的に計算されることを保証し、その後のすべての作業は単純な集計です。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、グローバル カウントが十分であることを示しているが、コンポーネントの分布により完全な一致が妨げられる場合です。 2 つのコンポーネントが存在し、1 つは多くの工場があるがイゴール ビールは存在せず、もう 1 つは過剰なイゴール ビールがあるが工場は存在しないと仮定します。 アルゴリズムは各コンポーネントを独立して処理するため、余剰部分は移行できません。 DSU のグループ化により、これらのケースは確実に分離され、各コンポーネントの使用量はゼロまたは制限されます。 

別の特殊なケースには、都市ごとに複数のエントリが含まれます。 ブール値フラグを使用するのではなくカウントをインクリメントするため、複数の醸造所や工場がある都市は多重度に正しく寄与します。 DSU マッピングにより、これらが正しいコンポーネント合計に集約され、正しい最小ベースのマッチングに必要な正確なカウントが維持されます。
