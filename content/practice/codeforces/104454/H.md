 ## 解決策
 ## 問題の理解

 4 人のプレイヤーはそれぞれ、都市の共有マップ上に 2 種類のものを構築します。 まず、業界トークンを特定の都市に配置します。 すべてのプレイヤーにわたって複数のトークンが都市に着くと、都市には複数の産業が含まれる可能性があります。 次に、各プレーヤーが道路を建設します。各道路は 2 つの都市を結び、正確に 1 人のプレーヤーに属します。 

道路のスコアリング ルールは各道路にローカルなものですが、世界的な産業の状況によって異なります。 都市をつなぐ道路として`u`そして`v`、それを建設したプレイヤーは、現在都市に存在する産業トークンの総数に等しいポイントを獲得します。`u`それに加えて市内の人たち`v`。 最後のタスクは、各プレイヤーが建設したすべての道路のスコアの合計を独立して計算することです。 

重要な相互作用は、産業はすべてのプレーヤーにわたってグローバルである一方、道路は各プレーヤーにプライベートであるということです。 つまり、道路の価値は、プレイヤー自身の行動だけではなく、共有される集約情報に依存するということです。 

制約により、最大で`10^5`各プレイヤーが貢献できるのは最大でも都市`10^4`産業と`10^4`道路。 これにより、合計は最大で`4 * 10^4`業界の配置と道路の順序が同じです。 道路ごとまたはクエリごとに業界の数を繰り返し再計算しようとするソリューションは、特にリストをスキャンしたり合計を最初から再計算したりする場合には、時間がかかりすぎます。 線形または線形に近い前処理戦略が必要です。 

すべてのプレーヤーにわたって業界が正しく集計されていない場合、微妙な失敗例が発生します。 たとえば、都市の場合、`1`複数のプレーヤーによる産業が含まれていますが、最後に読み取ったプレーヤーの貢献、都市に関係する道路スコアのみをカウントします。`1`過小評価されるだろう。 もう 1 つのよくある間違いは、スコアが明示的にグローバル総数に依存する場合に、業界をプレーヤーごとに扱うことです。 

## アプローチ

 直接シミュレーションのアプローチでは、すべての業界の配置を保存し、業界のリスト全体をスキャンすることで、道路ごとに両方のエンドポイントに存在する業界の数をカウントします。 これは、道路ごとにすべての業界の配置をループし、最悪のケースを与える可能性があることを意味します。`O(G * M)`プレイヤーごとに。 と`G`そして`M`まで`10^4`、これはすでに到達できます`10^8`最悪の場合のパターンではプレイヤーごとの操作が遅くなり、4 人のプレイヤーではこれが遅くなりすぎます。 

改善は懸念事項を分離することによってもたらされます。 各道路に必要なのは、2 つの終点にある産業の合計数だけです。 その価値は道路自体には依存せず、都市全体の産業の最終的な分布にのみ依存します。 したがって、繰り返し再計算する代わりに、最初にすべての業界の配置を単一の周波数配列に圧縮します。`cnt[c]`、各都市に存在する産業の数を表します。 

この配列が構築されると、すべての道路評価は定数時間になります。`(u, v)`、スコアは単純に`cnt[u] + cnt[v]`。 各プレイヤーの答えは、自分の道路上でのこの式の合計にすぎません。 

これにより、スキャンの繰り返しによる問題が、単一の前処理ステップとすべての道路上の直線パスに軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (道路ごとに業種をスキャン) | O(G × 産業全体) | O(全産業) | 遅すぎる |
 | 都市別のプレフィックス集約 | O(N + 産業の合計 + 道路の合計) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ステップ

 1. 都市の数を読み取る`N`そして配列を初期化します`cnt`サイズの`N + 1`ゼロ付き。 

この配列には、プレイヤーに関係なく、各都市に存在する産業トークンの数が格納されます。 
2. 4 つのプレーヤーのそれぞれについて、業界での配置リストを読みます。 すべての都市インデックスについて`x`そのリストで増分します`cnt[x]`1つずつ。 

これにより、すべてのプレーヤーの業界が単一のグローバル頻度テーブルに統合されます。 
3. 各プレーヤーについて、ランニング スコア変数をゼロに初期化します。 
4. そのプレイヤーの道路のリストを読み取ります。 それぞれの道ごとに`(a, b)`、 追加`cnt[a] + cnt[b]`そのプレイヤーのスコアに。 

これが機能するのは、どちらかのエンドポイントのすべての業界がその道路の価値に 1 回だけ貢献するためです。 
5. 4 つの累積スコアを出力します。 

### なぜ効果があるのか

 いつでも、`cnt[c]`都市に配置された産業トークンの正確な数を表します`c`。 この値は道路とは独立しており、すべてのプレーヤーの業界活動の統合にのみ依存します。 

各道路の寄与は端点全体で純粋に加算されるため、プレーヤーの合計スコアは、事前に計算された頂点の重みのみに依存する関数のエッジの合計になります。 道路が別の道路に影響を与えることはなく、読み取り後に業界の配置が変更されることもないため、頂点の重みへの分解は計算全体を通じて正確かつ安定しています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    cnt = [0] * (n + 1)

    players_industries = []

    for _ in range(4):
        m, g = map(int, input().split())
        inds = list(map(int, input().split()))
        players_industries.append((m, g, inds))
        for c in inds:
            cnt[c] += 1

    res = []

    for i in range(4):
        m, g, inds = players_industries[i]
        total = 0
        for _ in range(g):
            a, b = map(int, input().split())
            total += cnt[a] + cnt[b]
        res.append(total)

    print(*res)

if __name__ == "__main__":
    solve()
```このソリューションはまず、すべてのプレーヤーの業界リストに対するシングル パスでグローバルな業界周波数配列を構築します。 次に、各プレーヤーの道路を処理するときにこの配列を再利用し、各道路が一定時間で評価されるようにします。 

よくある落とし穴は、道路評価中に業界数を再計算しようとしたり、プレイヤーごとの業界数を誤って分離したりすることです。 正しい解釈は、すべての業界が共有プールに貢献しているということです。 

もう 1 つの微妙な点は、すべての業界が判明した後に道路が処理されるため、増分更新や順序付けの考慮が必要ないことです。

 ## 特殊なケース

 重要なエッジケースの 1 つは、異なるプレーヤーの複数の産業が同じ都市に集積している場合です。 アルゴリズムはすべての増分を合計して次のように計算するため、これを自然に処理します。`cnt[c]`道路処理が始まる前に。 ３つの産業が集まる都市としては、`cnt[c]`は分布に関係なく 3 になり、その都市を使用するすべての道路は 3 つの寄与すべてを正しくカウントします。 

もう 1 つのケースは、プレイヤーに道路がない場合です。 その状況では、道路上のループは何も貢献せず、プレーヤーのスコアはゼロのままになります。スコアは建設された道路を通じてのみ定義されるため、これは正しいことです。 

さらなるケースは、異なる道路で都市の終点が繰り返されることです。 各道路は独立しており、常に同じ事前計算された配列を使用して評価されるため、都市を繰り返し使用しても同じものを再利用するだけです。`cnt[c]`副作用や突然変異のない値。
