 ## 解決策
 ## 問題の理解

 Vasyaは少なくとも書かなければなりません`n`ある晩のコード行。 彼は生産性から始める`v`、彼が書いていることを意味します`v`最初のお茶休憩前のセリフ。 休憩するたびに、彼の生産性は 1 分の 1 ずつ低下します。`k`、整数の除算を使用します。 

彼が書いた合計行数は次のとおりです。$$v + \left\lfloor \frac{v}{k} \right\rfloor + \left\lfloor \frac{v}{k^2} \right\rfloor + \cdots$$次の項がゼロになるとプロセスは停止します。 最小の開始生産性を見つけなければなりません`v`書かれた行の合計が少なくとも`n`。 

制約が十分に大きいため、可能な限りすべてのことを試みる必要があります`v`単純に遅すぎるでしょう。`n`到達できる`10^9`、つまり、からの線形スキャン`1`上向きには 10 億回の反復が必要になる可能性があります。 たとえ各反復が小さいとしても、それは 2 秒の制限時間に快適に収まる量をはるかに超えています。 

合計の構造が重要です。 として`v`増加しても、書き込まれた総行数は減少しません。 開始時の生産性が高くなると、常に少なくとも以前と同じ数のラインが生成されます。 この単調な動作こそが、二分探索を適用できるものなのです。 

不注意な実装を黙って破壊してしまう可能性のあるエッジケースがいくつかあります。 

考慮する：```
1 2
```正しい答えは次のとおりです。```
1
```バグのある実装により、二分検索が開始される可能性があります。`0`答え自体が可能な最小値である場合、条件を誤って処理します。 

もう 1 つの微妙なケースは、合計が次の値を超える場合です。`n`早い：```
59 10
```のために`v = 54`:$$54 + 5 = 59$$答えはまさに`54`。 実装が次のようなべき乗を計算する場合`k^i`直接的には、他の言語ではオーバーフローや不要な作業が発生する可能性があります。 反復除算はより安全でクリーンです。 

もう 1 つの重要なシナリオは次のような場合です。`k`特に小さいです`2`:```
1000000000 2
```による除算のため、シーケンスには多くの非ゼロ項が含まれています。`2`ゆっくりと減少します。 大きなべき乗を非効率的に繰り返し再計算するソリューションは、遅くなりすぎる可能性があります。 意図したアプローチでは、対数的に多くの除算のみが必要です。 

## アプローチ

 最も直接的なアプローチはブルートフォースです。 のすべての値を試すことができます`v`から始まる`1`。 候補ごとに、以下を計算します。$$v + \left\lfloor \frac{v}{k} \right\rfloor + \left\lfloor \frac{v}{k^2} \right\rfloor + \cdots$$条件がゼロになるまで。 最初`v`合計が少なくとも`n`が答えです。 

これは、定義が問題ステートメントのプロセスと正確に一致するため、機能します。 問題は規模だ。 最悪の場合、答え自体が次のようなものになる可能性があります。`10^9`, そのため、候補を 1 つずつチェックすると、信じられないほど時間がかかります。 

重要な観察は、書かれた行の合計が次の単調関数を形成するということです。`v`。 

何らかの価値がある場合`v`プログラムを終了するには十分な値であり、その後はさらに大きな値でも十分です。 同様に、いくつかの場合、`v`値が不足すると、それ以下の値も不足します。 

これにより、問題は回答空間に対する従来の二分探索に変換されます。 

すべての値をテストするのではなく、範囲を検索します。`[1, n]`。 各中間点について`mid`、Vasya が次から始めて何行書けるかを計算します。`mid`。 合計が少なくとも`n`の場合、答えは左半分にあります。`mid`。 それ以外の場合は、右に進みます。 

ヘルパーの計算自体は効率的です。 各項は次のように除算されます。`k`したがって、反復回数は対数のみになります。`v`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n log n) | お(1) | 遅すぎる |
 | 最適 | O(log n × log n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ヘルパー関数を定義する`enough(v)`Vasya が生産性から始めて何行書けるかを計算します`v`。 
2. ヘルパー関数内で、現在の生産性を累計に繰り返し加算し、その生産性を次の値で割ります。`k`。 
3. 生産性がゼロになったら停止します。これ以降のすべての項もゼロになるためです。 
4. 最終合計が少なくとも`n`、 戻る`True`。 それ以外の場合は戻る`False`。 
5. 範囲に対して二分探索を実行します。`[1, n]`。 
6. コンピューティング`mid = (left + right) // 2`。 
7.次のことを確認します。`mid`ヘルパー関数を使用すれば十分です。 
8. もし`mid`機能する場合は、それを回答候補として記録し、左半分の検索を続けます。 これを行うのは、有効な最小値が必要なためです。 
9. もし`mid`機能しない場合は、右半分を検索してください。 
10. 検索間隔が空になるまで検索を続けます。 
11. 見つかった最小の有効な値を出力します。 

### なぜ効果があるのか

 正しさは単調性に依存します。 

させて`f(v)`生産性から始めて書かれた総行数になります`v`。 

合計の各項:$$\left\lfloor \frac{v}{k^i} \right\rfloor$$として減少していません`v`が増加します。 つまり、`f(v)`それ自体は減っていません。 

したがって、答えより小さい値では不十分で、答え以上の値で十分である境界点が存在します。 二分探索では常にこの境界が正しく維持され、最終的には有効な最小値が分離されます。`v`。 

ヘルパー関数も、問題で説明されている生産性の低下を直接シミュレートするため、正しいものです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def enough(v, n, k):
    total = 0
    current = v

    while current > 0:
        total += current
        current //= k

    return total >= n

def solve():
    n, k = map(int, input().split())

    left, right = 1, n
    answer = n

    while left <= right:
        mid = (left + right) // 2

        if enough(mid, n, k):
            answer = mid
            right = mid - 1
        else:
            left = mid + 1

    print(answer)

solve()
```ヘルパー関数は、問題からの正確な生産性プロセスに従います。 から始まる`v`、現在の寄与を加算し続け、で除算します。`k`各ステップの後に。 

反復除算の使用は、次のような計算能力よりも安全です。`k^i`。 寄与がゼロになるとループは自然に停止します。 

二分探索では、すべての値が厳密に以下であるという不変条件が維持されます。`left`は無効であることが知られていますが、それより大きい値はすべて`right`すでに処理または破棄されています。 

探索範囲は`[1, n]`なぜなら`n`それ自体で常に十分です。 Vasya が最初のバッチのみを作成し、その後は何も書かなかったとしても、`n`ラインがはっきりと機能します。 

よくある 1 つ違いの間違いは、有効な中間点を見つけた後に間違った境界を更新することです。 有効な最小値が必要なので、次のようにして左半分の検索を続ける必要があります。```
right = mid - 1
```もう 1 つの微妙な詳細は、左に移動する前に候補の回答を保存することです。 そうしないと、最終的な有効な中間点が失われる可能性があります。

 ## 特殊なケース

 可能な最小の入力を考えてみましょう。```
1 2
```二分探索は次から始まります`left = right = 1`。 

のために`mid = 1`:$$1 + 0 = 1$$条件はすぐに成功するため、答えは次のようになります。`1`。 

このケースでは、検索境界が正しく初期化されていること、およびアルゴリズムがアンダーフローなしで最小の有効な答えを処理していることが確認されます。 

次に、次のことを考えてみましょう。```
10 2
```正しい答えは、`6`。 

ヘルパーの計算をトレースします。 

| 現在 | 合計 |
 | --- | --- |
 | 6 | 6 |
 | 3 | 9 |
 | 1 | 10 |
 | 0 | 停止 |

 合計が正確に達する`10`、 それで`6`有効です。 よくある間違いは、`>`の代わりに`>=`充足性をチェックするとき。 このバグにより、完全一致が誤って拒否されてしまいます。 

最後に、生産性がほぼ即座に低下するケースを考えてみましょう。```
100 10
```のために`v = 91`:$$91 + 9 = 100$$次の項はゼロです。 

このケースでは、ヘルパー関数が除算がゼロに達すると、永久に継続したり不必要な作業を実行したりするのではなく、正しく停止することが確認されました。
