 ## 解決策
 ## 問題の理解

 ゲームは、同一の文字の隣接するブロックのシーケンスとして考えることができるバイナリ文字列で動作します。 各ターンで、プレイヤーは同じ文字で構成される連続したセグメントを削除し、文字列の残りの 2 つの部分が縫い合わされます。 スコアはプレイヤーが何回動かしたかではなく、具体的には何回動かしたかを表します。`1`プロセス全体にわたって個人的に削除される文字。 

重要な点は、移動が単一のキャラクターの削除に限定されないことです。 プレイヤーは 1 回のアクションで同一のキャラクターのラン全体を削除できます。つまり、ゲームは基本的に、どのブロックをどの順序で削除するかを選択することになりますが、残りのランの構造はブロックがマージされるにつれて変化し続けます。 

テスト ケースごとの入力サイズは小さく、文字列の長さは最大 100、最大 500 のテスト ケースです。 これにより、ゲーム状態の指数関数的なシミュレーションが即座に除外されます。 すべての部分文字列に対する 3 次または 2 次のシミュレーションであっても、テスト ケースごとに許容されますが、完全なゲーム ツリーを探索するものは不必要な過剰なものです。 

これを「アリスが交互のブロックで掴めるものを数える」と扱うと、素朴な間違いが生じます。 これは失敗します。削除により文字列の分離された部分がマージされ、新しい隣接関係と新しい機会が作成される可能性があるためです。 

たとえば、次のように考えてみましょう`101`。 アリスが最初のものを貪欲に削除した場合`1`、文字列は次のようになります`01`、しかし、代わりに彼女が真ん中を削除した場合`0`、文字列は次のようになります`11`、将来の得点機会を劇的に変えます。 構造変化を無視した戦略は、そのような小さな入力でも誤った計算を行う可能性があります。 

もう 1 つの失敗例は、次のような文字列を交互に使用することです。`101010`。 最適なプレイは削除後のグループ化効果に依存しており、表示されているブロックを単純に貪欲に削除しても最適な構造は維持されません。 

## アプローチ

 ブルートフォースの観点では、ゲーム全体をミニマックス検索としてシミュレートします。 各状態は文字列であり、各移動は削除する同一の文字の連続を選択します。 ある状態から可能な移動の数は実行の数に比例し、移動するたびに文字列が変化して新しい状態が生成されます。 これはすぐに完全なゲーム ツリーになります。 

文字列の長さは最大でも 100 ですが、分岐係数は 1 移動あたりおよそ O(n) で、深さも O(n) であるため、状態の数は天文学的に多くなります。 メモ化は原理的には役に立ちますが、削除によって隣接関係の順序が変更され、さまざまな方法でマージが実行されるため、個別の状態の数は依然として指数関数的に増加します。 

重要な観察は、個々の登場人物のアイデンティティは、連続するランの構造ほど重要ではないということです。 文字列をブロックに圧縮すると、ゲームはブロックの数になります。`1`- ブロックの存在とそれらが周囲とどのように相互作用するか`0`-ブロック。 各移動は常にブロック全体を削除します。重要なのは、アリスとボブのどちらがブロックを取得できるかだけです。`1`- アクセスできなくなったり、あまり好ましくない構成にマージされたりする前にブロックします。 

より単純で深い見方をすると、`1`ブロックは最終的に誰かによって削除され、プレイヤーは交互にブロック全体を取得します。 それぞれの動きで連続するブロックが 1 つだけ削除されるため、圧縮効果が安定した後、ゲームは位置の降順でブロックを選択することになり、最適なプレイはソートされた順序でブロック長を処理することに合わせて調整されます。 

文字列がランに圧縮されると、プロセスは効果的にセグメントの重みをターンベースで選択することになります。`1`-run は、それを取得するプレイヤーにその長さを提供し、両方のプレイヤーは、貪欲な方法で利用可能な最大の貢献から交互に選択します。 

This reduces the problem from dynamic string manipulation to a static multiset game over run lengths.

 ## アルゴリズムのチュートリアル

 1. First compress the string into maximal consecutive segments. Each segment is recorded as a pair consisting of its character and its length. This is necessary because every move deletes an entire contiguous equal block, so the natural atomic unit of the game is a run, not a character.
 2. Extract only the lengths of segments that contain`1`。 これらは、アリスのスコアの考えられるすべてのソースを表します。`1`彼女の得点に貢献する。 
3. これらを並べ替えます`1`-セグメントの長さを降順に並べます。 その理由は、大きなブロックを遅らせても相手は同等かそれ以上に有利な位置でブロックを奪うことしかできないため、両プレーヤーが事実上、早い段階で大きな得点ブロックを奪おうと競争しているからです。 
4. このソートされたリストを交互に繰り返すシミュレーションを行います。 アリスは、利用可能な最大の 1 番目、3 番目、5 番目などを取得します。`1`- セグメント、ボブは 2 番目、4 番目などを取得します。 
5. アリスが取得した値を合計して、最終的な答えを生成します。 

重要な推論ステップは、文字列が独立したブロックに縮小されると、離れたブロック間の相互作用によって寄与サイズが変化しなくなるということです。 ゲームの複雑さは、独立した重みを巡る単純な競合割り当て問題に集約されます。 

### なぜ効果があるのか

 移動するたびに、最大の連続ブロックが 1 つだけ削除されます。 完全圧縮後は、どのブロックを先に削除するかだけが意味のある決定となります。 合併しても総数が増えることはないので、`1`ブロック内のそれぞれ`1`-segment は、削除されるまでその重量を保持します。 交互のターン順序により、これらの重みの所有権が降順に固定され、動きを再配置しても、ボブに同等以上のブロックへのアクセスを早く与えずに、アリスのより小さなブロックへのアクセスを向上させることはできません。 これにより、ソートされたセグメントの重みに対する貪欲な選択に最適な戦略が固定されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        s = input().strip()
        
        ones = []
        
        i = 0
        n = len(s)
        
        while i < n:
            j = i
            while j < n and s[j] == s[i]:
                j += 1
            
            if s[i] == '1':
                ones.append(j - i)
            
            i = j
        
        ones.sort(reverse=True)
        
        ans = 0
        for k in range(0, len(ones), 2):
            ans += ones[k]
        
        print(ans)

if __name__ == "__main__":
    solve()
```実装は、文字列をスキャンしてランレングスを構築することから始まります。 内側のループは最大の連続セグメントを識別し、各ブロックがアトミックに処理されることを保証します。 ゼロのセグメントはアリスのスコアに寄与しないため、1 のセグメントのみが保存されます。 

これらのセグメント長を降順に並べ替えることは、以前に導出された貪欲な割り当て戦略と一致します。 インデックス 0 から始まる 2 つおきの要素を合計するループは、アリスが 1 番目、3 番目、およびその後の利用可能な最良のブロックを取得することに直接対応します。 

よくある実装の落とし穴は、ランの圧縮を忘れて個々の文字をカウントすることです。これにより、移動がブロック全体で動作するという前提が崩れてしまいます。 

## 実用的な例

 インプットを考慮する`01111001`。 圧縮ステップによりセグメントが生成されます`0 | 1111 | 00 | 1`。 の`1`-セグメントには長さがあります`[4, 1]`。 

| ステップ | ワンズセグメント | 並べ替え済み | アリスが選ぶ | 現在の合計 |
 | --- | --- | --- | --- | --- |
 | 開始 | [4,1] | [4,1] | 4 | 4 |
 | 次へ | [4,1] | [4,1] | 1 (ボブは 1 を取る) | 4 |

 アリスのスコアは4になります。 

ここで考えてみましょう`101010`。 圧縮すると`1 | 0 | 1 | 0 | 1 | 0`、したがって、1 のセグメントは次のようになります。`[1, 1, 1]`。 

| ステップ | ワンズセグメント | 並べ替え済み | アリスが選ぶ | 現在の合計 |
 | --- | --- | --- | --- | --- |
 | 開始 | [1、1、1] | [1、1、1] | 1 | 1 |
 | 次へ | [1、1、1] | [1、1、1] | 1 | 2 |
 | 次へ | [1、1、1] | [1、1、1] | 1 | 3 |

 これは、完全に交互の構造でも、アリスは利用可能な合計の半分を切り上げて収集することを示しています。`1`-ブロックの重み、貪欲な交互と一致します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    import sys
    input = sys.stdin.readline

    T = int(input())
    out = []
    for _ in range(T):
        s = input().strip()
        ones = []
        i = 0
        n = len(s)
        while i < n:
            j = i
            while j < n and s[j] == s[i]:
                j += 1
            if s[i] == '1':
                ones.append(j - i)
            i = j
        ones.sort(reverse=True)
        ans = sum(ones[k] for k in range(0, len(ones), 2))
        out.append(str(ans))
    return "\n".join(out)

assert run("1\n0\n") == "0"
assert run("1\n1\n") == "1"
assert run("1\n101\n") == "1"
assert run("1\n110011\n") == "2"

 ## 特殊なケース

 次のような完全にゼロの文字列`0000`何も生成しません`1`したがって、スコア付けされたブロックのリストは空であり、アリスは決してポイントを獲得しないため、アルゴリズムは正しくゼロを返します。 

完全に 1 つの文字列のような`111111`長さ 6 の単一セグメントに圧縮されます。 アリスは最初の動きですぐにそれを受け取り、他にセグメントがないため、干渉することなく値全体を受け取ります。 

次のような交互構造`1010101`複数の単位セグメントを生成します。 ソートによりそれらの独立性が維持され、交互選択により、アリスは文字列の構造変化をシミュレートすることなく、他のすべてのセグメントを一貫してキャプチャできます。
