 ## 解決策
 ## 問題の理解

 質問戦略を二分決定木として考えてください。 すべての内部ノードは 1 つの質問であり、その 2 つの外向きエッジは回答「はい」と「いいえ」に対応し、すべてのリーフは正確に 1 人の人物を識別します。 質問には現在候補者の任意のサブセットが含まれる可能性があるため、ノードでは候補者の任意のバイナリ パーティションを使用できます。 したがって、元のゲームはまさにバイナリ プレフィックス ツリーを構築する問題です。 

人物 (i) が深さ (l_i) に到達した場合、アキネーターはその人物がいつ選ばれたかを正確に (l_i) 質問します。 (p_i=a_i/\sum a_j) なので、予想される質問数は次のようになります。 

[
 \frac{\sum_ia_i l_i}{\sum_ia_i}。 
】

 分母は固定されているため、実際の最適化ターゲットは整数です

 [
 \sum_i a_i l_i.
 】

 ツリーの深さは最大でも (k) でなければなりません。 (n) 個の葉と最大 (k) の高さを持つ二分木は、(n\le 2^k) のときに正確に存在します。 これが失敗した場合、どのような質問戦略でも、許可された質問数内ですべての人を区別することはできません。 同じ条件は、バイナリ プレフィックス コード用の Kraft バウンドです。 

(n) の制約は小さいですが、ツリーまたはサブセットの列挙は許可されません。 (n\le100) の場合、(O(n^3)) でさえ無害ですが、(n) の指数関数的なものはまったく実行不可能です。 確率は (10^{12}) ほどの整数で表されるため、実装は浮動小数点ではなく正確な整数で完全に動作する必要があります。 

単純な実装を騙す可能性のある境界ケースがいくつかあります。 可能性のある人物が 1 名であれば、質問は必要ありません。 例えば、```
1 1
1000000000000
```答えがあります`0/1`。 すべての人が少なくとも 1 つの質問が必要であると仮定したソリューションでは、誤って正の値が出力されます。 

深さの限界により、通常のハフマン構築が不可能になる可能性があります。 例えば、```
3 1
1 2 3
```出力があります`No solution`1 つの二項質問には、考えられる答えの順序が 2 つしかないためです。 高さ制約をチェックせずに通常のハフマンコーディングを実行すると、深さ 2 のツリーが黙って生成される可能性があります。 

反対の境界は (n=2^k) の場合です。 この場合、重みに関係なく、すべてのリーフが正確に深さ (k) になければなりません。 例えば、```
4 2
1 2 3 4
```重み付けコスト (2(1+2+3+4)=20) があるため、答えは次のようになります。`2/1`。 ある人に短いコードを与えようとする戦略は、別の人に 2 つ以上の質問を深くさせなければ実現できません。 

最後に、等しい重みは順序の間違いを検出するのに役立ちます。 と```
3 2
1 1 1
```最適な深さは (1,2,2) で、総コストは (5) となり、答えが得られます。`5/3`。 ここでは、最も頻繁に使用される人は特別ではないため、タイを正しく処理しても同じ合計が得られるはずです。 

## アプローチ

 直接的なアプローチでは、考えられるすべての二分決定木を試します。 現在考えられる人の集合 (S) において、質問は空ではない適切なサブセット (A\subset S) を選択します。(A) は Yes 分岐になり、(S\setminus A) は No 分岐になります。 サブセットに対する再帰的動的プログラムは、すべてのサブセットと残りの深さの最適なコストを記憶できます。 

これは正しいです。なぜなら、考えられるすべての質問戦略にはまさにそのような最初の分割があり、結果として生じる 2 つの部分問題は最初の質問の後に独立しているからです。 残念ながら、(2^n) 個のサブセットが存在するため、考えられるすべての分割を考慮すると、それに加えて指数関数的な作業が必要になります。 すべてのサブセット全体で、順序付けされた非自明な分割の数は次のようになります。 

[
 \sum_{S\ne\varnothing} (2^{|S|}-2)
 =3^n-2^{n+1}+1。 
】

 (n=100) の場合、(3^{100}) は約 (5.15\cdot10^{47}) であるため、このアプローチはリモートでは実行できません。 

有益な観察は、どの人がどの正確なバイナリ文字列にアクセスするかは実際には気にしないということです。 私たちは深さだけを気にしています(l_i)。 一連の深さは、クラフトの不等式を満たす場合に、バイナリ プレフィックス ツリーによって実現可能です。 

[
 \sum_i2^{-l_i}\le1。 
】

 最適なツリーの場合、合計が小さければ、制約に違反することなく一部のコードを短縮できるため、等式が成り立ちます。 したがって、この問題は、(1\le l_i\le k) および (\sum 2^{-l_i}=1) に従って (\sum a_i l_i) を最小化する、長さ制限のあるハフマン符号化問題になります。 

この制約のあるハフマン問題を解決する特にクリーンな方法があります。 すべての人の最初の長さがゼロであると想像してください。 クラフト合計は (n) になります。 人 (i) の長さを (l-1) から (l) に増やすと、クラフト合計は (2^{-l}) だけ減少し、コストは正確に (a_i) になります。 クラフト削減の合計が (n-1) になる長さの増加を実行する必要があります。 

これにより、問題はバイナリのコインコレクター問題に変わります。 すべての人 (i) に対して、額面のコインを (k) 作成します。 

[
 2^{-1},2^{-2},\ldots,2^{-k},
 】

 そしてそれらのコインすべてに価値 (a_i) を与えます。 額面の合計が (n-1) になる最小値のコレクションが必要です。 レベル (l) に対応するコインが選択された場合、レベル (l) までその人のコードの長さが増加することを表します。 これは、長さ制限のあるハフマン コーディングのパッケージ マージの背後にある標準的な削減です。 

すべての額面は 2 の累乗であるため、コインの問題には貪欲な解決策があります。 最小額面では、より大きな額面は 2 倍の大きさになるため、選択したコインはペアで存在する必要があります。 可能な限り最も安価なペアは、利用可能な 2 つの最も安価なコインから形成されます。 そのペアは、次の額面の 1 つのコインとして扱うことができます。 1 枚のコインが余った場合、そのコインは厳密解には決して関与できないため、最も高価な残ったコインは破棄できます。 このプロセスを繰り返すことで、パッケージ マージ アルゴリズムが生成されます。 

ブルート フォースはすべてのバイナリ パーティションを明示的に探索するため機能します。 パッケージマージの観察により、これらすべてのツリーを、最も安価な関連パッケージを含む (k) 個のソートされたリストのみに置き換えることができます。 (n,k\le100) なので、単純な (O(nk)) 実装でも十分に高速です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O(3^n)) | (O(2^n)) | 遅すぎる |
 | 最適なパッケージマージ | (O(nk)) | (O(n)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 重み (a_i) を非降下順に並べ替えます。 等しい重みは任意の順序で配置できます。 パッケージ結合アルゴリズムでは、常に値の昇順に項目が必要であり、並べ替えられた 2 つの隣接する項目から形成されるパッケージの値は、前のパッケージよりも小さくなりません。 
2. (n\le2^k) かどうかを確認します。 そうでない場合、深さ (k) 内に (n) 個の異なる葉が存在するはずがないので、次のように出力します。`No solution`。 
3. ソートされた重量を額面のコインの初期リスト (2^{-k}) とみなします。 これらは最小のコインなので、ペアになることができる最初のコインです。 
4. 以下の処理を (k-1) 回繰り返します。 現在ソートされたリストの連続する要素を、最も安価な 2 つの要素から順にペアにします。 各ペアは 2 つの要素の合計を値とするパッケージになります。 次に、パッケージ リストを元の重量の別のコピーとマージし、結果を並べ替えます。 

元の重量は、新しい 2 倍の額面の通常の硬貨を表します。 パッケージは、まったく同じ額面に結合された 2 つの小さなコインを表しています。 両方の選択肢を 1 つのソート済みリストに保持しておくことで、後で決定する際に、単一の高価なコインと安価なパッケージのどちらかを選択することができます。 
5. これらの (k-1) ラウンドの後、最後にもう一度連続要素をペアにしますが、結果として得られるパッケージを元の重みとマージしないでください。 これらのパッケージの額面は (1) になりました。 
6. (n-1) 個の最も安価な最終パッケージを選択し、それらの値を追加します。 この合計は、重み付けされた質問の最小可能数です。 
7. 結果の整数を (S=\sum a_i) で除算します。 分子と (S) の最大公約数を計算し、両方をそれで割り、約分した分数を出力します。 

### なぜ効果があるのか

 (l_i) を人 (i) に割り当てられる最終的な深さとします。 すべての (l_i=0) から開始すると、クラフト合計は (n) になります。 (l_i) を (l_i-1) から (l_i) に増やすと、その合計は (2^{-l_i}) だけ減少しますが、目的は (a_i) だけ増加します。 有効な完全な二分木に到達するには、クラフト合計が正確に (1) になる必要があるため、選択されたリダクションの合計値は (n-1) でなければなりません。 

パッケージマージ構造は、この最小値選択の問題を正確に解決します。 どの額面においても、有効なソリューションは最小額面を偶数回しか使用できません。 このようなコインを (2r) 使用する場合、(2r) 最も安いコインを使用することが常に最適であり、それらは (r) の連続するペアにグループ化できます。 各ペアを 1 つのパッケージに置き換えると、合計額面と合計金額の両方が保持されます。 したがって、より小さい金額のレイヤーを貪欲に解くと、次のレイヤーに必要な選択肢のセットが正確に生成されます。 

最後のレイヤーでは、選択したすべてのアイテムの額面が (1) であるため、そのうち (n-1) を選択すると、合計額面が (n-1) になります。 パッケージを拡張すると、コード長ごとの単位増加ごとに選択されたコインが 1 つ与えられるため、パッケージの合計値は正確に (\sum_i a_i l_i) になります。 package-merge はその値を最小化するため、結果のコードには予想される質問の数が最小限になります。 結果として得られる長さはクラフト等式を満たし、最大でも (k) であるため、それらを実現するバイナリ プレフィックス ツリーが存在します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def merge_sorted(a, b):
    """Merge two already sorted lists."""
    res = []
    i = 0
    j = 0

    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            res.append(a[i])
            i += 1
        else:
            res.append(b[j])
            j += 1

    if i < len(a):
        res.extend(a[i:])
    if j < len(b):
        res.extend(b[j:])

    return res

def solve():
    n, k = map(int, input().split())
    weights = list(map(int, input().split()))
    weights.sort()

    if n > (1 << k):
        print("No solution")
        return

    current = weights[:]

    # Move from denomination 2^(-k) up to denomination 2^(-1).
    # At every intermediate level, packages are merged with
    # the original coins of the new denomination.
    for _ in range(k - 1):
        packages = []
        for i in range(0, len(current) - 1, 2):
            packages.append(current[i] + current[i + 1])

        current = merge_sorted(weights, packages)

    # One final packaging step creates denomination-1 items.
    final_packages = []
    for i in range(0, len(current) - 1, 2):
        final_packages.append(current[i] + current[i + 1])

    # final_packages is already sorted.
    numerator = sum(final_packages[:n - 1])
    denominator = sum(weights)

    g = __import__("math").gcd(numerator, denominator)
    numerator //= g
    denominator //= g

    print(f"{numerator}/{denominator}")

if __name__ == "__main__":
    solve()
```入力重みは最初に 1 回ソートされます。 パッケージの値は並べ替えられたリストの隣接する要素を追加することによって形成されるため、並べ替えだけで十分です。したがって、結果として得られるパッケージ リストも並べ替えられます。 

の`merge_sorted`関数はこの特性を利用します。 (n) 個の元の重みを現在のパッケージ リストと線形時間でマージします。 すべてのレベルでリスト全体を再ソートしても (n,k\le100) は問題なく通過しますが、マージによって意図した (O(nk)) の複雑さが明確になります。 

ループは最初の (k-1) レベルまでのみ実行されます。 最終パッケージには額面 (1) があり、額面 (1) の元のコインは存在しないため、最終レベルは意図的に個別に処理されます。 元の重みを最終リストに混合すると、額面構成に 1 つずれたエラーが発生します。 

ペアを作成するときに使用される範囲は次のとおりです。`range(0, len(current) - 1, 2)`。 現在のリストに奇数の要素がある場合、最後の要素は未使用のままになります。 リストはソートされているため、その要素は最も高価な要素であり、まさに package-merge によって破棄される項目です。 

実現可能性チェックでは、`1 << k`したがって、浮動小数点対数や丸めの問題はありません。 Python の整数は、可能な最大の中間値も安全に処理します。 関連する最大の重み付きコストは (n^2\cdot10^{12}) 程度であり、Python の任意精度の整数が快適に処理できる値をはるかに下回ります。 

最終的なパッケージリストはすでにソートされています。`current`はソートされ、連続する各ペアの合計は減少しません。 したがって、(n-1) 個の最も安価なパッケージは単にその最初の (n-1) 個の要素です。 

(n=1) の場合、そのスライスは空であり、分子は 0 になります。 分母が正なので、換算された答えは正しいです`0/1`。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | (O(nk)) | (k) レベルのそれぞれは、(O(n)) 個のパッケージを作成し、(O(n)) 個の要素の 2 つのソートされたリストをマージします。 |
 | スペース | (O(n)) | 元の重量、現在のリスト、および 1 つのパッケージ リストのみが保存されます。 |

 (n,k\le100) を使用すると、アルゴリズムは定数因数までの (10^4) 程度のリスト レベルの演算のみを実行します。 整数値も十分に小さいため、正確な任意精度の演算は低コストで実行できるため、このソリューションは 2 秒および 256 MB の制限内に問題なく収まります。 

## テストケース```python
import sys
import io
import math

def merge_sorted(a, b):
    res = []
    i = 0
    j = 0

    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            res.append(a[i])
            i += 1
        else:
            res.append(b[j])
            j += 1

    res.extend(a[i:])
    res.extend(b[j:])
    return res

def solve_text(inp: str) -> str:
    old_stdin = sys.stdin
    try:
        sys.stdin = io.StringIO(inp)
        input = sys.stdin.readline

        n, k = map(int, input().split())
        weights = list(map(int, input().split()))
        weights.sort()

        if n > (1 << k):
            return "No solution"

        current = weights[:]

        for _ in range(k - 1):
            packages = [
                current[i] + current[i + 1]
                for i in range(0, len(current) - 1, 2)
            ]
            current = merge_sorted(weights, packages)

        final_packages = [
            current[i] + current[i + 1]
            for i in range(0, len(current) - 1, 2)
        ]

        numerator = sum(final_packages[:n - 1])
        denominator = sum(weights)

        g = math.gcd(numerator, denominator)
        return f"{numerator // g}/{denominator // g}"
    finally:
        sys.stdin = old_stdin

def run(inp: str) -> str:
    return solve_text(inp)

# Smallest impossible case
assert run("3 1\n1 2 3\n") == "No solution", "three people cannot fit at depth 1"

# Maximum-size case
assert run("100 100\n" + " ".join(["1"] * 100) + "\n") == "168/25", \

 ## 特殊なケース

 一人の人の場合、入力は```
1 1
1000000000000
```容量チェックに合格します。 初期リストには 1 つの値が含まれており、形成するペアはありません。 最終的なパッケージ リストは空であるため、(n-1=0) 最も安いパッケージを選択するとコストはゼロになります。 分母が正なので、`0/1`。 これは、アキネーターがその人物が誰であるかをすでに知っているという事実と一致します。 

あまりにも多くの人がいる場合は、次のことを検討してください。```
3 1
1 2 3
```アルゴリズムは (3>2^1) を直ちにチェックします。 3 つの葉を持つことができる高さのバイナリ ツリーはないため、次のように表示されます。`No solution`。 これにより、不完全な最終パッケージ リストが有効なコードと間違われるのを防ぎます。 

正確な容量境界については、```
4 2
1 1 1 1
```4 つのリーフは深さ 2 の 4 つの位置すべてを占める必要があります。 最初のパッケージ化では値 (2) の 2 つのパッケージが作成され、中間リストが形成された後にのみ最後のパッケージ化で値 (4) の 1 つのパッケージが作成され、その結果選択されたコストは (8) になります。 総重量で割ると (4) となります。`2/1`。 1 つのリーフを短くすると、別のリーフが深さ 2 を超えることになるため、コードワードを短くする余地はありません。 

3人で同じ重さになると、```
3 2
1 1 1
```最初のパッケージリストは`[2]`、元の重みとマージされて取得されます。`[1,1,1,2]`。 最終的なパッケージは、`[2,3]`、両方を選択する必要があります。 それらの合計値は (5) ですが、確率の重みの合計は (3) です。`5/3`。 対応する長さは (1,2,2) で、そのクラフト和は (1/2+1/4+1/4=1) です。 

最大の入力サイズの場合、```
100 100
1 1 1 ... 1
```100 の重みが 1 に等しい場合、十分な深さの制限は拘束されません。 最適な等重二分木には、深さ 6 で 28 枚の葉、深さ 7 で 72 枚の葉があり、次のようになります。 

[
 28\cdot6+72\cdot7=672。 
】

 予想される質問数は (672/100=168/25) です。 このテストでは、パッケージの構築が多くのレベルで正しく継続され、最終部分が正確に削減されることが確認されます。
