 ## 解決策
 ## 問題の理解

 1 行に配置された一連の整数が与えられ、それを 3 つの連続するセグメントに分割したいとします。 カット ポイントは 3 つの空でない部分を生成する必要があり、各部分の合計がまったく同じである必要があります。 

言い換えれば、配列内で配列をプレフィックス、中間セグメント、およびサフィックスに分割する 2 つのカット位置を探します。ここで、3 つのセグメントの合計は同じ値になります。 

入力サイズは非常に大きくなり、最大 500,000 要素になる可能性があります。 これにより、カット位置のすべてのペアを直接試行するソリューションは即座に除外されます。これは、次の順序をチェックする必要があるためです。$n^2$これは 2 秒で計算できる範囲をはるかに超えています。 線形または線形に近い時間に近いものが必要です。 

最初の重要な構造上の制約は、配列の合計が 3 で割り切れない場合、答えは自動的に 0 になるということです。 この場合、どのように分割しても等和分割は不可能です。 

素朴な考えを打ち破る微妙なエッジケースがいくつかあります。 

1 つは、多くのプレフィックス合計が合計の必要な 3 分の 1 に一致するが、有効なサフィックス アライメントが存在しない場合です。 たとえば、`[0, 0, 0, 0]`、すべてのプレフィックスの合計はゼロであり、すべての分割は一見すると有効であるように見えますが、3 つの空ではない部分を保持するカット位置のみが有効であり、カットの順序を強制しない場合は過剰カウントが発生します。 

もう 1 つのエッジ ケースは、ターゲット合計がゼロの場合です。 これは、ゼロサム接頭語が非常に頻繁に発生する可能性があり、単純なカウントでは、重複する選択肢が独立していない場合に誤って独立したものとして扱う可能性があるため、危険です。 たとえば、`[0, 0, 0]`、複数のプレフィックス位置が部分的な条件を満たしている場合でも、有効な分割は 1 つだけ存在します。 

主な難しさは、組み合わせを効率的にカウントしながら、最初のカットが 2 番目のカットの前に発生するように強制することです。 

## アプローチ

 ブルートフォースのアイデアは単純です。 すべてのカットインデックスのペアを試します$i, j$そのような$1 \le i < j < n$。 各ペアについて、3 つのセグメントの合計を計算し、等しいかどうかを確認します。 プレフィックスの合計を事前計算して O(1) のセグメントの合計を取得したとしても、依然として O(n²) 個のペアが存在します。 と$n = 5 \cdot 10^5$、これには次のオーダーが必要になります$10^{11}$チェックですが、それは不可能です。 

重要な観察は、問題がプレフィックス合計と固定ターゲット値に関する推論に帰着するということです。 合計を$S$。 有効な分割が存在する場合、各セグメントの合計は次のようになります。$S/3$。 この値を$T$。 次に、プレフィックスの合計が等しいインデックスを探します。$T$(最初のカット)、およびプレフィックスの合計が等しいインデックス$2T$（2番目のカット）。 制約は、2 番目のカットが最初のカットの後に来る必要があるということです。 

これにより、問題は、プレフィックス合計が一致する順序ペア、つまりプレフィックス合計が等しいすべての位置をカウントすることに変換されます。$T$プレフィックスの合計が等しい後続の位置とペアになる可能性があります$2T$。 すべてのペアを明示的に検索する代わりに、左から右に 1 回スキャンして、これまでに見つかった有効なファーストカット位置の数を数えます。 

プレフィックス合計に遭遇した回数のカウンターを維持します$T$。 プレフィックスの合計が等しい位置に到達したとき$2T$、以前に見たすべての$T$位置はそれと有効なペアを形成するため、そのカウンターを答えに追加します。 

これにより、問題はアレイ上の 1 回のパスに軽減されます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 遅すぎる |
 | プレフィックス合計のカウント | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 配列を 1 回スキャンするときにプレフィックスの合計を定義します。 

1. 合計値を計算する$S$。 もし$S$が 3 で割り切れない場合は、等しいパーティションが存在しないため、すぐに 0 を返します。 
2. 目標を設定する$T = S / 3$。 次に、次と等しいプレフィックス合計値を探します。$T$そして$2T$。 
3. 実行中のプレフィックス合計を初期化します。`pref = 0`、カウンター`count_T = 0`、そして答え`ans = 0`。 
4. 配列をインデックス 0 から n − 1 まで繰り返し、更新します。`pref += a[i]`。 
5.いつでも`pref == 2T`最後の要素ではないので追加します`count_T`に`ans`。 これが機能するのは、以前のすべての位置で`pref == T`最初のカットとして機能します。 
6.いつでも`pref == T`そして私たちは最後の位置にいません、増分します`count_T`。 
7. 配列の最後まで続けます。 

### なぜ効果があるのか

 このアルゴリズムは、有効な分解が、次のプレフィックス合計ヒットの順序付けられたペアに正確に対応するという事実に依存しています。$T$そして$2T$。 有効な分割は、プレフィックス合計が次のインデックスで最初のカットを選択する必要があります。$T$、その後の 2 番目のカットでは、プレフィックスの合計は$2T$。 左から右にスキャンすることで、次の点に到達したことを確認します。$2T$位置、すべて有効$T$それ以前の位置はすでにカウントされており、それぞれが 1 つの有効なトリプル パーティションを生成します。 これにより、カウントされたペアと有効な分割の間の 1 対 1 のマッピングが保持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    total = sum(a)
    if total % 3 != 0:
        print(0)
        return
    
    target = total // 3
    pref = 0
    count_first = 0
    ans = 0
    
    for i in range(n):
        pref += a[i]
        
        if i < n - 1 and pref == 2 * target:
            ans += count_first
        
        if i < n - 1 and pref == target:
            count_first += 1
    
    print(ans)

if __name__ == "__main__":
    solve()
```解決策は、配列を読み取り、その合計を計算することから始まります。 可算性チェックは、不可能なケースを早期に排除し、不必要な走査ロジックを防ぐため、不可欠です。 

変数`pref`プレフィックスの合計を動的に維持し、再計算を回避します。 重要な点は更新の順序です。つまり、次の位置に到達したときです。`pref == 2 * target`、最初に現在のものを使用します`count_first`後で更新される可能性がある前に。 これにより、両方の条件がインデックス間で相互作用する可能性がある場合の正確性が保証されます。 

条件`i < n - 1`2 番目のカットが最後に配置されず、空ではない 3 番目のセグメントが保持されます。

 サンプル入力を使用します。 

入力:```

 | 私 | a[i] | 接頭語 | カウントファースト | 答え | イベント |

これにより、以下の現象が繰り返し発生することが確認されます。$2T$以前の有効なすべてを正しく累積します$T$ポジション。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    from sys import stdin
    n = int(stdin.readline())
    a = list(map(int, stdin.readline().split()))
    
    total = sum(a)
    if total % 3 != 0:
        return "0"
    
    target = total // 3
    pref = 0
    count_first = 0
    ans = 0
    
    for i in range(n):
        pref += a[i]
        if i < n - 1 and pref == 2 * target:
            ans += count_first
        if i < n - 1 and pref == target:
            count_first += 1
    
    return str(ans)

# provided sample
assert run("5\n1 2 3 0 3\n") == "2"

# all zeros small
assert run("3\n0 0 0\n") == "1"

# no solution due to indivisible sum
assert run("4\n1 1 1 1\n") == "0"

# multiple zeros creating many prefixes
assert run("5\n0 0 0 0 0\n") == "6"

# minimal invalid size
assert run("2\n1 2\n") == "0"

 ## 特殊なケース

 重要なエッジ ケースは、配列に多くのゼロが含まれており、プレフィックスの合計が両方の値と等しくなる場合です。$T$そして$2T$非常に頻繁に。 

入力の場合:```
5
0 0 0 0 0
```合計は0なので、$T = 0$。 Every prefix sum is 0.

 アルゴリズムを見てみる:

 最後を除く各インデックスで、すべての位置がインクリメントされます`count_first`そしてまた、`ans`後の位置に到達したとき。 スキャンの構造により、各 2 番目のカットが以前のすべての最初のカットを蓄積するため、有効な順序付きカットの各ペアが正確に 1 回カウントされることが保証されます。 

これは、すべての値が同一である縮退の場合でも、順序付け制約が純粋にシングルパス累積ロジックを通じて維持されることを示しています。
