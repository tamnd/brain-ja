 ## 解決策
 ## 問題の理解

 2 種類の記号から構築された奇妙な混合記数法を使用して正の整数を表すように求められます。 

1 つ目の種類は、0 から 9 までの通常の 10 進数です。各桁には所定のコストがあり、それを表現で 1 回使用すると、その量のコストがかかります。 

2 番目の種類は、I、V、X、L、C、D、M の 7 つのローマ記号で構成されます。これらのそれぞれは文字列ルールベースの数値体系としては扱われなくなり、数値が固定された数字のように動作します。つまり、I は 1 に寄与し、V は 5 に寄与し、X は 10 に寄与し、L は 50 に寄与し、C は 100 に寄与し、D は 500 に寄与し、M は 1000 に寄与します。各ローマ字記号にも、 使用ごとに独自のコストがかかります。 

数値は 10 進数の位置形式で記述されますが、各位置では 10 進数またはこれらのローマ字のいずれかを使用できます。 値 v のシンボルが位置 i (0 から右から数えて) に配置されると、合計値に v · 10^i が加わります。 最終的に記述された式は、指定された整数 n に正確に評価される必要があります。 

タスクは、総コストを最小限に抑えながら合計が n と正確に一致するように、各位置のシンボルを選択することです。 

n ≤ 10^18 という制約は、小数点以下の桁数が最大 19 桁であることを意味します。 テスト ケースの数は最大 2000 と大きいため、値の範囲が指数関数的ではなく、テスト ケースごとの桁数が線形に近い解でなければなりません。 コストは大きくなりますが、64 ビットまたは Python 整数が必要であることを除けば、複雑さとは無関係です。 

微妙な問題は、9 より大きい記号が存在することです。これは、数字が独立しているという通常の前提を破ります。 M = 1000 のようなシンボルを低い位置に配置すると、より高い位置へのキャリーが発生する可能性があります。 これは、10 進数の各桁を独立して扱うことができず、桁ごとの欲張りは失敗することを意味します。 

キャリーを追跡せずにポジションごとにすべての選択肢を試す単純なアプローチは失敗します。 たとえば、19 を表したいときに、X (10) を単位位置に配置し、I (1) を単位位置に個別に配置すると、オーバーシュートが発生したり、上位桁の調整が必要になったりする可能性があります。 キャリーを介したポジション間のやり取りが最も難しい点です。 

別の失敗例は、高い値のシンボルが低い位置で使用された場合に発生します。 たとえば、1000 を表す単位の位置に M (1000) を配置すると正しく動作しますが、1000 + 10 のような混合構成に配置すると、次の桁へのキャリーを補正する必要があり、上位の位置の構造が変わります。 

## アプローチ

 強引なアイデアは、各小数点位置を独立して扱い、17 個の可能な記号 (10 桁と 7 個のローマ字) をすべて試すことです。 位置ごとに、結果の合計を計算し、それが n に等しいかどうかを確認します。 これは、シンボルがより高い位置にオーバーフローする可能性があり、ローカルな決定が独立していないため、失敗します。 各位置へのすべてのシンボルの割り当てを総当りで試したとしても、検索空間は最悪の場合でも 17^19 となり、これはまったく実行不可能です。 

重要な観察は、シンボルはキャリーを通じて相互作用しますが、相互作用は隣接する位置間で厳密に局所的であるということです。 値 v を位置 i に配置すると、位置 i にのみ影響し、i+1 へのキャリーが作成されます。 つまり、桁上げ状態を維持しながら、最下位桁から最上位桁まで処理できるということです。 

これにより、問題は n の位置にわたる数値動的計画法プロセスに変換されます。 各位置で、n のターゲット桁と入ってくるキャリーがわかります。 17 個のシンボルの 1 つを選択し、その値とキャリーを加算し、結果の桁と次のキャリーを決定します。 すべての位置でターゲットの数字を正確に一致させたいと考えています。

唯一の問題は、ローマ字が 1 つの位置で最大 1000 まで寄与する可能性があるため、キャリーが大きくなる可能性があることです。 ただし、ポジションは 19 しかなく、各ステップは 10 で割られるため、キャリーは任意に爆発することができず、数千に制限されたままになります。 これにより、状態空間 DP over (位置、キャリー) が実現可能になり、遷移が小さくなります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 割り当てに対するブルートフォース | O(17^19) | お(19) | 遅すぎる |
 | 桁上げ状態の桁 DP | O(位置 × 状態 × 17) | O(状態) | 承認済み |

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。 

1. n の 10 進数を最下位から最上位に抽出します。 これにより、各位置のターゲット桁が定義され、キャリーを考慮した後に正確に一致する必要があります。 
2. 現在のキャリー値 c を位置 i に保持しながら、最初の i 位置を処理するための最小コストとして動的プログラミング状態を定義します。 このキャリーは、前のポジションからの累積オーバーフローを表します。 
3. キャリー 0、コスト 0 で位置 0 の DP を初期化します。これは、受信オーバーフローのない単位桁から開始することに対応します。 
4. 各位置 i および到達可能なキャリー c ごとに、17 個の利用可能なシンボルをそれぞれ配置してみます。 シンボルの値が v でコストが [v] であるとします。 この位置に寄与する合計値は v + c になります。 
5. 結果の桁 rem = (v + c) mod 10 を計算します。これは、位置 i の n のターゲット桁と等しくなければなりません。 一致しない場合、このシンボルの配置はこの状態では無効です。 
6. 一致する場合、次のキャリー next_c = (v + c) // を計算します。 10. キャリー next_c を使用して DP を位置 i + 1 に移行し、最小コストを更新します。 
7. すべてのポジションを処理した後でも、キャリーがまだ残っている可能性があります。 このキャリーは、n の上位の暗黙的な桁と一致する必要があります。つまり、n の長さを超えるとそれらの桁はゼロになります。 したがって、有効な終端位置でキャリーがゼロになるまで遷移を続けます。 
8. 答えは、n のすべての桁を消費し、キャリー ゼロで終了したすべての DP 状態の中での最小コストです。 

なぜそれが機能するのかは、10 進数の加算の構造に関係しています。 すべてのシンボルの配置は、それ自体の桁にのみ影響し、決定論的な方法でオーバーフローを前方に伝播します。 DP 状態は、曖昧さなく続行するために必要な情報を正確に取得します。ポジションとキャリーが将来の実現可能性を完全に決定します。 キャリーを除いて、以前の選択が将来に影響を与えることはないため、状態圧縮はロスレスです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

romans = [1, 5, 10, 50, 100, 500, 1000]

def solve_case(n, cost_d, cost_r):
    digits = list(map(int, str(n)))[::-1]
    L = len(digits)

    values = list(range(10)) + romans
    costs = cost_d + cost_r

    INF = 10**30
    dp = {0: 0}  # carry -> cost at position 0

    for i in range(L):
        ndp = {}
        target = digits[i]

        for carry, cur_cost in dp.items():
            for v, cst in zip(values, costs):
                s = v + carry
                if s % 10 != target:
                    continue
                nc = s // 10
                nc_cost = cur_cost + cst
                if nc not in ndp or nc_cost < ndp[nc]:
                    ndp[nc] = nc_cost

        dp = ndp
        if not dp:
            return -1

    # process remaining carry
    i = L
    while dp:
        if 0 in dp:
            return dp[0]

        ndp = {}
        target = 0

        for carry, cur_cost in dp.items():
            for v, cst in zip(values, costs):
                s = v + carry
                if s % 10 != target:
                    continue
                nc = s // 10
                nc_cost = cur_cost + cst
                if nc not in ndp or nc_cost < ndp[nc]:
                    ndp[nc] = nc_cost

        dp = ndp
        i += 1
        if i > L + 60:
            break

    return min(dp.values()) if dp else -1

def main():
    t = int(input())
    for _ in range(t):
        n = int(input().strip())
        cost_d = list(map(int, input().split()))
        cost_r = list(map(int, input().split()))
        print(solve_case(n, cost_d, cost_r))

if __name__ == "__main__":
    main()
```この実装では、キャリーによってキーが設定された辞書が維持されるため、到達不能な状態の保存が回避されます。 各層は、数値の小数点以下 1 桁に、残りのキャリーをフラッシュするための追加の層を加えたものに対応します。 

移行ステップでは、数字の一致が厳密に強制され、構築された表現の正確さが保証されます。 コストは段階的に累積され、キャリー状態ごとの最小コストのみが保持されます。 

実際の微妙な点は、キャリーが消えるまで長さ n を超えて処理を続けることです。 これが必要なのは、低い位置で大きなシンボルを選択すると、値が元の長さを超えて上位の虚数桁に押し込まれる可能性があるためです。 

## 実用的な例

 簡単にするために、n = 102 ですべてのコストが 1 である小さな例を考えてみましょう。 数字は[2、0、1]です。 

位置 0 では、ターゲットは 2 です。桁 2 をキャリー 0 で配置してキャリー 0 を与えることも、ローマ字の I と必要に応じてキャリー調整を使用することもできますが、残り 2 が得られる配置のみが残ります。 

位置 1 では、ターゲットは 0 です。DP は可能な状態を繰り越し、モジュロ 10 の後にゼロを生成する以前の選択の組み合わせのみが残ります。 

| ポジション | 搬入 | 選択されたシンボル | 値の合計 | 桁チェック | 実行する | コスト |
 | --- | --- | --- | --- | --- | --- | --- |
 | 0 | 0 | 2 | 2 | 一致 | 0 | 1 |
 | 1 | 0 | 0 | 0 | 一致 | 0 | 2 |
 | 2 | 0 | 1 | 1 | 一致 | 0 | 3 |

 これにより、標準の数字表現が有効であり、ベースラインとして機能することが確認されます。 

ここで、ローマ字記号を使用することが有益な場合を考えてみましょう。 ある位置で数字を X = 10 に置き換えるとします。 これにより、値を次の桁にシフトするキャリーが作成されます。 DP は、局所的な修正を強制するのではなく、より高いキャリー状態に移行することでこれを捉えます。これは、オーバーフローが回避されるのではなく、どのように意図的に使用されるかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(T × L × C × 17) | L ≤ 19 桁、C は到達可能なキャリー状態の数、17 シンボルにわたる遷移 |
 | スペース | O(C) | 現在の DP マップのみが保存されます。 

桁の長さは一定の制限があり、キャリー状態は実際にはまばらなままであるため、ソリューションは 1 秒の制約内で最大 2000 の T に対して十分効率的になります。

 ## 特殊なケース

 ローマ字シンボルが低い位置に配置され、キャリー チェーンが生成されると、重大なエッジ ケースが発生します。 たとえば、1000 のような数値の単位の場所に M = 1000 を配置すると、100 がより高い位置にキャリーされます。 DP は、位置 0 のキャリー 0 から位置 1 のキャリー 100 に移動することでこれを処理し、上位桁が解決されるまで処理を継続して、n の残りの構造との一貫性を確保します。 

もう 1 つのエッジ ケースは、複数の表現が同じ桁の剰余を生成するが、キャリーが異なる場合です。 たとえば、あるポジションの 10 は X (10) から取得することも、0 からより低いポジションからキャリー 1 を取得することもできます。 DP は、キャリーを状態の一部として扱うことでこれらのケースを明示的に分離し、両方の可能性が独立して評価され、より安価な方だけが生き残ることを保証します。
