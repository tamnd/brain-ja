 ## 解決策
 ## 問題の理解

 1 から 5 までのインデックスが付けられた 5 種類のスピリットが与えられ、各種類のコピーが一定数あります。 それぞれのタイプのスピリット`i`固定された本質的価値を持つ`i`。 

「召喚」と呼ばれる 1 回の操作で、利用可能なスピリットの一部が選択されます。 選択したスピリットごとに、それが貢献するかどうかを個別に決定します`1`またはその価値を最大限に貢献します`i`。 選択したすべてのスピリットの貢献度の合計は 6 を超えてはなりません。ちょうど 6 の場合、この操作により値 6 の新しいスピリットが 1 つ生成されます。元のスピリットはそれぞれ、召喚ごとに最大 1 回使用でき、召喚で使用された場合は消費されます。 

課題は、生成できる値 6 のスピリットの最大数を計算することです。 

入力サイズは大きく、最大 100,000 のテスト ケースがあり、タイプごとに最大 10^9 までカウントされます。 これにより、個々の選択をシミュレートしたり、テスト ケースごとにサブセットを列挙しようとするアプローチは即座に排除されます。 有効なソリューションはすべて、考えられるすべての有効な呼び出しの固定された構造的特徴付けに依存して、各テスト ケースを一定時間で処理する必要があります。 

微妙な失敗例は、貢献度を 1 にダウングレードする機能を尊重せずに「高い値を貪欲に詰め込む」ことを試みた場合に発生します。たとえば、正しくペアにされていない限り、5 を使用しても自動的に 6 に到達することはできません。 

次の入力を考えてみましょう。```
1 0 0 0 1
```単純な考えでは 5 だけを使用しようとするかもしれませんが、すべての値を取得しても 5 になり、ギャップを埋める追加のアイテムがないため、単一の 5 では合計 6 に達することはできません。 正解は 0 ですが、不用意に貪欲にアプローチすると、多くの場合カウントがオーバーされます。 

もう 1 つの落とし穴は、各スピリットが常にその価値を最大限に発揮すると仮定していることです。 間の切り替えの柔軟性`1`そして`i`これがグループ化構造を自明ではないものにしています。 

## アプローチ

 ブルートフォース解釈では、利用可能な蒸留酒のすべてのサブセットを列挙し、サブセットごとに「1 または i」の選択肢のすべての割り当てを試行し、一部の割り当ての合計が 6 になるかどうかを確認します。これは原理的には正しいですが、すぐに爆発します。中程度の数であっても、サブセットの数は指数関数的であり、サブセットごとの割り当ての選択により別の指数係数が追加されます。 1 つのテスト ケースに限定したとしても、これは実現不可能です。 

重要な観察は、召喚内で重要なのは、選択されたアイテムの数と、1 ではなく完全な値を使用してどれだけの「追加価値」が抽出されるかだけであるということです。サブセットに k 個のスピリットが含まれている場合、それらすべてを 1 に割り当てるとベースライン k が与えられ、それらの一部を選択して完全な値を提供すると追加の値が追加されます。`(i - 1)`選ばれた精霊ごとに。 したがって、有効な各召喚は、基本合計とボーナスが正確に 6 に等しいアイテムの小さなマルチセットによって特徴付けられます。 

目標金額が非常に小さいため、有効な召喚は最大でも 6 つのスピリットで構成される必要があります。 これにより、有効なグループのすべての構造パターンを列挙できるようになり、問題はカウントからそのようなパターンを貪欲に繰り返し抽出することになります。 

中心となる考え方は、小さなグループは、生成される 6 つあたりのスピリットの消費が少ないため、常により価値があるということです。 したがって、最初に 2 つのアイテム、次に 3 つのアイテムなどで有効な召喚を形成することを優先し、常に各レベルでできるだけ多くのアイテムを取得します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | パターンベースの貪欲なグループ化 | テスト ケースごとに O(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、考えられるすべての有効な召喚をサイズ別に分類します。 

サイズ 2 の召喚は、基本寄与 2 の後のボーナス合計が 4 であるという条件を満たさなければなりません。これにより、ペアの組み合わせは、値の合計が 6 になる正確なものになります: (1,5)、(2,4)、および (3,3)。これは、これらのペアのみが必要なボーナス構造を提供できるためです。 

サイズ 3 の召喚は、ベース 3 とボーナス 3 を満たす必要があります。つまり、値の合計が 6 になり、組み合わせ (1,1,4)、(1,2,3)、および (2,2,2) が得られる必要があります。 

より大きなグループも存在しますが、生産された結果ごとにより多くのスピリッツを消費するため、効率の点では厳密に劣ります。 私たちの目標は召喚の数を最大化することなので、常に小さい有効なグループを最初に優先します。 

アルゴリズムは次のように進行します。 

1. 利用可能な数を使用して、できるだけ多くの有効なサイズ 2 召喚を形成するようにしてください。 貪欲に (1,5)、次に (2,4)、次に (3,3) を照合し、使用済みのスピリッツを在庫から差し引きます。 試合が成功するたびに 1 つの結果が生成され、ちょうど 2 つのスピリットが消費されます。 
2. 可能なペアをすべて使い果たした後、サイズ 3 の召喚に進みます。 1 つのタイプのみを使用するため、最初に (2,2,2) を貪欲に形成し、次に (1,2,3)、次に (1,1,4) を形成し、それに応じてカウントを消費します。 
3. 分布の制約により小さな構造が見逃された場合は、必要な場合にのみ大きなパターンが考慮されますが、それらが支配的であり、前のステップで達成された以上に最終的なカウントが増加することはありません。 

この順序の背後にある理由は、すべての有効な召喚は消費されたスピリットの固定数に対応し、召喚ごとの消費を最小限に抑えることで、利用可能なプールから抽出できる素の有効な構造の数が最大になるということです。 

### なぜ効果があるのか

 すべての有効な召喚は、調整された合計が 6 に等しい、最大 6 つのスピリットのマルチセットに対応します。そのようなマルチセットは、そのサイズと構成によって完全に記述され、すべての構成は上記の列挙されたパターンでカバーされます。 各召喚は独立しており、ばらばらのリソースを消費するため、召喚の数を最大化することは、可能な限り多くの小さな有効なパターンを貪欲に抽出することと同じです。 リソースの総消費量を増やさずに、より大きなパターンをより多くの呼び出しに分割することはできないため、サイズを増やすことによる貪欲な順序付けにより最適性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(a):
    c1, c2, c3, c4, c5 = a
    ans = 0

    # size-2 patterns: (1,5), (2,4), (3,3)
    x = min(c1, c5)
    ans += x
    c1 -= x
    c5 -= x

    x = min(c2, c4)
    ans += x
    c2 -= x
    c4 -= x

    x = c3 // 2
    ans += x
    c3 -= 2 * x

    # size-3 patterns: (2,2,2)
    x = c2 // 3
    ans += x
    c2 -= 3 * x

    # (1,2,3)
    x = min(c1, c2, c3)
    ans += x
    c1 -= x
    c2 -= x
    c3 -= x

    # (1,1,4)
    x = min(c4, c1 // 2)
    ans += x
    c4 -= x
    c1 -= 2 * x

    return ans

def main():
    t = int(input())
    out = []
    for _ in range(t):
        a = list(map(int, input().split()))
        out.append(str(solve_case(a)))
    print("\n".join(out))

if __name__ == "__main__":
    main()
```実装では、パターン抽出順序を直接エンコードします。 ペア編成は召喚を作成する最もリソース効率の高い方法であるため、最初に処理されます。 その後、トリプルを使用して残りの構造を消費します。 各操作はカウントの直接の min-or-greedy 減算であり、テスト ケースごとの一定時間の処理が保証されます。 

よくある微妙な点は、各パターンを固定された順序で適用する必要があることです。 (1,2,3) のようなより制約されたパターンでは、以前の選択がスピリッツの利用可能性に影響を与えるため、それらを並べ替えると最適性が損なわれる可能性があります。

 ## 特殊なケース

 タイプ 5 とタイプ 1 のみが存在する場合、アルゴリズムは最初にそれらをペアにしようとします。 各 (1,5) は両方のリソースを消費しますが、無効な部分構造は作成しないため、残った 5 または 1 は有効な構成を形成できず、正しく無視されます。 

タイプ 3 のみが存在する場合、アルゴリズムはトリプルを試行する前に (3,3) ペアの形成を優先し、不可能な部分構成で単一の 3 が無駄にならないようにします。 残りの単一の 3 は有効な召喚を形成できません。これは、すべての有効なグループには少なくとも 2 つの互換性のある要素が必要であるというルールに一致します。 

タイプごとに 10^9 など、カウントが非常に大きい場合、アルゴリズムは項目ごとに反復されません。 すべての演算は整数の除算と min 演算によって実行されるため、スケーリングは正確性やパフォーマンスに影響を与えません。
