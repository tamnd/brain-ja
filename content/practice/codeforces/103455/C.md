 ## 解決策
 ## 問題の理解

 私たちには、単純な信号機ゲームのタイムラインと、信号が永久に赤になる前にゴールラインに到達しようとする一組の競技者が与えられています。 ライトは時間 0 で赤の状態で始まり、特定の瞬間に赤と緑の間で昇順に切り替わります。 最後に記録されたスイッチの後、ライトは永遠に赤色のままになります。 

各競技者は位置 0 からスタートし、目標距離に到達することを目指します。$K$。 信号が青の間は、一定の速度で前進します。 ライトが赤のときはまったく動きません。 瞬時に始動および停止できるため、加速遅れや慣性を考慮する必要がありません。 問題は、各競技者がその距離に到達できるかどうかを判断することです$K$ライトが永久的な赤に落ち着く前に。 

入力は光の変化の数を提供します$M$、競争相手の数$N$、目標距離$K$、ライトが状態を切り替える時間のリスト、および各競技者の速度。 出力は、競技者ごとのバイナリ インジケーターです。時間内にゴールに到達した場合は 1、それ以外の場合は 0 となります。 

制約は十分に小さいため、すべての緑の区間にわたって競技者ごとに直接シミュレーションが可能です。 と$M, N \le 5000$、ナイーブな$O(MN)$または$O(M+N)$操作の総数は最大でも約 1 回であるため、テスト戦略ごとに十分です。$2.5 \cdot 10^7$、きれいに実装されていれば、Python の時間制限に快適に適合します。 

微妙なポイントは光の交互構造です。 ライトが赤から始まるので、最初の間隔は$t_1$は赤、次に緑です$t_1$に$t_2$、次に再び赤色、というように続きます。 もう 1 つのエッジ ケースは、最後のスイッチの後のライトは常に赤のままであるため、その後の動作は問題になりません。 

単純な間違いは、動きが連続的であると仮定したり、すべての青の時間を単一のブロックとして扱うことです。 たとえば、スイッチが時々$2, 5$、ライトはそれらの正確な間隔の間でのみ緑色になり、それらの点を除くすべての場所では緑色になりません。 これを誤解すると、移動時間を過大にカウントし、すべての速いプレーヤーを勝者として誤って宣言することにつながります。 

別の特殊なケースは、競技者の所要時間がグリーンインターバルの終わりに正確に一致する場合に発生します。 信号は切り替え時間にすぐに赤に変わるため、その正確な瞬間にゴールに到達したことは、解釈にもよりますが、厳密にその前またはその瞬間に距離を完走した場合にのみ有効です。 正しいモデルは、カットオフまたはカットオフ前に到達したことを成功として扱います。 

## アプローチ

 この強引なアイデアは簡単です。各競合他社の光の変化のタイムラインを個別にシミュレートします。 競合他社がこれまでにどれだけ移動したかを維持し、連続する切り替え時間の間隔ごとに繰り返します。 緑の間隔ごとに、速度と持続時間の積として移動距離を計算し、到達するまでそれを累積します。$K$またはタイムラインが終了します。 

このアプローチは実際のプロセスを直接モデル化するため、正しいです。 失敗点はパフォーマンスです。 各競合他社はすべてをスキャンします$M$間隔があるため、複雑さは次のようになります。$O(NM)$、最悪の場合、2,500 万回の操作に達します。 これは境界線ですが、概念的には無駄になりますが、最適化された Python ではまだ許容されます。 

重要な観察は、各緑色のセグメント内での動きが決定的かつ線形であるため、秒ごとの動作をシミュレートする必要がないことです。 代わりに、各競技者を個別に扱いますが、事前に計算された青の継続時間にわたって累積到達可能距離を直接計算できます。 これにより、問題は 1 秒あたりのシミュレーションを行わずに、競技者ごとにタイムラインを 1 回通過するだけで済みます。 

さらに単純化すると、到達するまでの合計グリーンタイムのみが必要になるということです。$K$、セグメント内の正確な停止点ではありません。 競合他社が時間を必要とする場合$K / p_i$、その必要時間を超えるまで貪欲に緑の間隔を蓄積できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 1 秒あたりのブルート フォース シミュレーション |$O(N \cdot \sum t)$|$O(1)$| 遅すぎる |
 | 競技者ごとのインターバルシミュレーション |$O(NM)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 切り替え時間を赤と緑の交互の間隔に変換します。 信号が赤から始まるので、最初のインターバル$[0, t_1)$赤です、$[t_1, t_2)$は緑色などです。 後の最後の間隔$t_M$は永遠に赤いので、動きには何も貢献しません。 

各競技者について、緑のインターバル中に到達するまでにどれだけの距離を蓄積できるかを計算します。$K$さもなければ、グリーンタイムがなくなってしまいます。 

### ステップ

 1. 最初の赤から緑への遷移から始まる連続する切り替え時間をペアにして、緑の間隔のリストを作成します。 初期状態は赤色であるため、最初の使用可能な間隔は から始まります。$t_1$もし$M \ge 1$。 それぞれの緑の間隔は、$[t_{2i-1}, t_{2i})$。 各緑の間隔の長さは次のとおりです。$t_{2i} - t_{2i-1}$。 
2. スピードのある各競技者に対して$p_i$、連続的に移動した場合にゴールに到達するのに必要な時間を計算します。$K / p_i$。 これにより、蓄積しなければならないグリーンタイムの目標量が決まります。 
3. 緑色の間隔を順番に繰り返し、残りの必要な緑色の時間から各間隔の時​​間を減算します。 インターバルが残りの要件を完全に満たしている場合、早期に停止し、競合他社を成功としてマークします。 
4. すべての緑の区間が使い果たされ、所要時間がまだプラスの場合、競技者は時間内にゴールラインに到達することができません。 

### なぜ効果があるのか

 重要な不変条件は、緑の区間のみが進行に寄与し、各緑の区間内では一定の速度で直線的に進行するということです。 したがって、ゴールに到達できるかどうかは、グリーンタイムの配分方法ではなく、合計の合計グリーンタイムのみに依存します。 このアルゴリズムは、使用可能な期間を時系列で正確に合計することでこの不変条件を維持し、青時間が二重にカウントされたり順序が間違ったりしないようにします。 必要な合計青時間に達すると、対応する物理的距離が$p_i \cdot t$競合他社がそれに達しているか、それを上回っていることを保証します$K$。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    m, n, k = map(int, input().split())
    t = list(map(int, input().split()))
    p = list(map(int, input().split()))

    green = []
    # light starts red, so t[0] is red->green
    for i in range(0, m - 1, 2):
        green.append(t[i + 1] - t[i])

    # for each player, check if enough green time exists
    res = []

    for speed in p:
        need = k / speed
        ok = False
        for dur in green:
            if need <= dur:
                ok = True
                break
            need -= dur
        res.append("1" if ok else "0")

    print(" ".join(res))

if __name__ == "__main__":
    solve()
```コードはまず、連続するトグル時間をペアにして、使用可能な緑色のセグメントを構築します。 ループオーバー`range(0, m - 1, 2)`赤から緑、および緑から赤の構造を反映します。 

各競合他社の変数は、`need`距離をカバーするのに必要な青時間を表します$K$。 緑の間隔ごとに、この要件が軽減されます。 その瞬間`need`一定期間内に が非正になると、競合他社が成功します。 

よくある落とし穴は、浮動小数点累積を使用して距離を直接シミュレートしようとすることです。 ここではそれが機能しますが、より安定した解釈は、問題を累積距離ではなく所要時間に縮小することです。これにより、部分的な間隔の消費に関する推論エラーが回避されます。

 ## 特殊なケース

 エッジケースの 1 つは、青の間隔がまったくない場合、または最初の切り替えが非常に遅い場合です。 その状況では、次のことをしない限り、すべての競合他社は失敗します。$K = 0$。 アルゴリズムはこれを処理します。`green`リストが空になるため、すべての競技者はすぐに使用可能な時間を使い果たします。 

もう 1 つのエッジ ケースは、競技者の所要時間がすべてのグリーン インターバルの合計と正確に一致する場合です。 この場合、減算ループは正確に 0 で終了し、条件は次のようになります。`need <= dur`最後の間隔境界で成功をトリガーします。 これは、可能な最後の瞬間に終了することが許可される意図された動作と一致します。 

3 番目のエッジ ケースは、非常に狭い間隔が交互に発生するもので、複数の短い緑色のウィンドウが組み合わされて、必要なしきい値にかろうじて到達します。 累積減算アプローチでは、要件が満たされるまですべての間隔が順番に消費されるため、断片化は問題になりません。
