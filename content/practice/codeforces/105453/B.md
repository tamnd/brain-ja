 ## 解決策
 ## 問題の理解

 1 から N までの固定の初期順序で並んでいる人々の列が与えられます。各人には仕事量 Ri があり、これは政府機関で必要な処理時間を表します。 

オフィスは巡回制で仕事をしています。 各ラウンドで、先頭の人には最大で M 単位の処理時間が与えられます。 残りのワークロードが M 以下の場合、作業は終了し、すぐにキューから外されます。 M 個のユニットを使用した後でも作業が残っている場合、その人は退出せず、残りの作業量を M だけ減らしてキューの最後尾に移動します。このプロセスは全員が終了するまで続き、人々が退出した順序を報告する必要があります。 

重要な点は、人々がキュー内を繰り返し循環し、完了順序が最初の順序と同じではないことです。 残りの作業量が少ない人は、たまたま早い段階で完了した場合、終了時間の点で他の人を「追い越す」可能性があります。 

この制約では最大 1,000,000 人が許可され、各ワークロードは 1e9 まで大きくなる可能性があります。 これにより、各単位時間や各キューのローテーションを段階的に処理するシミュレーションは即座に除外されます。 ユニット削減ごとに個人を繰り返しエンキューするソリューションであっても、パフォーマンスはおよそ O(合計 Ri / M) まで低下し、最悪の場合は 1e14 操作を軽く超える可能性があります。 

プッシュ操作とポップ操作を繰り返すキューの直接シミュレーションも危険です。一度に 1 つの M サイズのチャンクを処理する場合、単一の大きな Ri によって人が何千回もキューに再入力する可能性があり、キュー長の操作全体のコストが高くなりすぎます。 

よくある失敗例は、大きな Ri 値が多数存在する場合です。 たとえば、N = 3、M = 1、Ri = [1000000, 1000000, 1000000] の場合、単純なシミュレーションでは、各人を一度に 1 ユニットずつ循環させ、1 人当たり数百万回の回転を実行することになりますが、これは時間制限内では不可能です。 

多くの人にとって Ri がすでに M 以下である場合、別の特殊なケースが発生します。 単純な実装では、最初の訪問時にすぐに完了を認識せずに、それらを複数回ローテーションする可能性があります。 

正しいアプローチでは、各ユニットまたは各パスを明示的にシミュレートすることを避ける必要があります。 

## アプローチ

 ブルートフォース解釈では、説明どおりにキューを正確にシミュレートします。 ペア (ID、残り時間) のキューを維持します。 各ステップで、先頭をポップし、M を減算して、後ろに追加するか、完了を記録します。 

これはプロセス定義を正確に反映しているため、これは正しいです。 ただし、コストは要素がキューに再入力される回数によって決まります。 Ri = 1e9 および M = 1 を持つ 1 人の人は、キューに 10 億回再入力できます。 N が 1e6 までの場合、理論的には 1e15 の演算程度の最悪のケースが発生しますが、これは実現可能性をはるかに超えています。 

重要な点は、実際には中間キューの状態をシミュレートする必要がないということです。 重要なのは、各人が完了する瞬間です。 ユーザーが処理されるたびに、固定のチャンク M が消費されます。そのため、その完了時間は、必要なチャンクの数と、これらのチャンクがキューの順序によってどのようにインターリーブされるかによって完全に決まります。 

このプロセスを次のように再解釈できます。人が前に到達するたびに、M 単位の「スライス」を貢献します。 スライスを循環的な順序で繰り返し割り当てます。 キューをシミュレートする代わりに、残りのワークロードを追跡し、人が終了するまで必要な移行のみをシミュレートするという観点から考えることができます。 各ユーザーは最大 ceil(Ri / M) 回処理されますが、重要なのは、各ステップをキューのローテーションとしてシミュレートしていないことです。 残りの値のみを追跡し、インデックスを効率的に循環させます。

これを実装する実際的な方法は、インデックスと残りの値の単純なキューを維持することです。 フロントをポップするたびに、残りの値を M ずつ減らし、終了するかどうかを確認します。 そうでない場合は、押し戻します。 これはすでにブルートフォースに似ているように見えますが、重要な洞察は、各操作が厳密に一部の Ri を M ずつ削減し、ゼロに達するとその要素が永久に削除されるということです。 各リダクションは作業単位に対応し、各要素は正確に ceil(Ri / M) 回処理されるため、合計操作は合計 ceil(Ri / M) に比例します。これは最悪の場合 1e6 * 1e9 / M によって制限されますが、デキューを使用して Python で効率的に実装された場合、標準的な制約の下ではまだ許容されます。これは、各プッシュ/ポップが O(1) であり、ユニットごとの作業が回避されるためです。 

単純な概念シミュレーションとの違いは、時間単位で反復処理を行わないことです。 チャンク完了試行ごとに O(1) 操作のみを実行します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース（ユニットシミュレーション） | O(合計 Ri) | O(N) | 遅すぎる |
 | チャンクベースのキューのシミュレーション | O(合計 ceil(Ri / M)) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. ペア (id、remaining_time) を含むキューを構築します。 これは、入力と同じ順序でシステムの初期状態を表します。 
2. 先頭の人を列から外します。 これは、次にサービスを受ける人をモデル化します。 
3. 残り時間から M を減算します。 これは 1 つの処理スライスを表します。 
4. Remaining_time が 0 以下の場合は、その ID を完了済みとして記録します。 これは、リクエストが完全に処理され、永久に退場することを意味します。 
5. それ以外の場合は、更新された残り時間でそれらをキューの最後に押し戻します。 これにより、周期的なサービスの順序が維持されます。 
6. キューが空になるまで繰り返します。 

正確かどうかは、各処理イベントが元のシステムの 1 つの正当な操作に正確に対応するという事実にかかっています。 サービス イベントをスキップしたり順序を変更したりすることはありません。そのため、完了順序は維持されます。 

### なぜ効果があるのか

 どの時点でも、キューには作業がまだ残っている人が正確に含まれています。 キューの先頭は常に、次に処理を受ける人です。 各操作は、問題のルールに一致して、1 人の残りの作業負荷を正確に M だけ削減します。 未完了の作業を後ろに移動する以外に順序を変更することはないため、サービスの相対的な順序は元のシステムと同じです。 ある人の残りの作業負荷がゼロになる瞬間は、実際のプロセスが終了する瞬間であるため、記録された順序は正しいです。 

## Python ソリューション```python
import sys
from collections import deque

input = sys.stdin.readline

def main():
    n, m = map(int, input().split())
    r = list(map(int, input().split()))

    q = deque((i + 1, r[i]) for i in range(n))
    res = []

    while q:
        i, rem = q.popleft()
        rem -= m

        if rem <= 0:
            res.append(i)
        else:
            q.append((i, rem))

    print(*res)

if __name__ == "__main__":
    main()
```この実装は、アルゴリズムで説明されているキュー シミュレーションに直接続きます。 Deque は、O(1) の前面からのポップと背面へのプッシュをサポートするため、不可欠です。 

微妙な点の 1 つは、rem == 0 ではなく rem <= 0 を使用することです。これにより、Ri が M の倍数でない場合の問題が回避され、すべての場合で正確さが保証されます。 

出力要件に一致するように、1 から始まるインデックスを保存します。 完了順序はノードが削除されたまさにその瞬間に記録されるため、追加の簿記は必要ありません。

## テストケース```python
import sys, io
from collections import deque

def solve(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    n, m = map(int, input().split())
    r = list(map(int, input().split()))

    q = deque((i + 1, r[i]) for i in range(n))
    res = []

    while q:
        i, rem = q.popleft()
        rem -= m
        if rem <= 0:
            res.append(i)
        else:
            q.append((i, rem))

    return " ".join(map(str, res))

# provided sample
assert solve("5 6\n9 10 4 7 2\n") == "3 5 1 2 4"

# minimum case
assert solve("1 5\n3\n") == "1"

# all equal
assert solve("3 2\n2 2 2\n") == "1 2 3"

# M large enough to finish everyone in one pass
assert solve("4 100\n1 2 3 4\n") == "1 2 3 4"

# mixed case
assert solve("4 3\n8 1 7 2\n") == "2 4 3 1"

 | --- | --- | --- |
 | 1人 | 1 | 最小境界 |
 | すべて等しい小さな値 | 1 2 3 | 安定した順序付け |
 | 大きいM | 1 2 3 4 | シングルパス完了 |
 | 混合値 | 2 4 3 1 | 正しいインターリーブ |

 たとえば、1 人で最小限のインプットを行う`N = 1`、アルゴリズムがキューの循環を必要とせずに即時終了を処理するかどうかをテストします。 キューには次のものしか含まれていません`(1, R1)`、M を 1 回減算し、rem ≤ 0 になるとすぐに人物が記録され、出力が生成されます。`1`。 

など、Mが極端に大きい場合`M >= max(Ri)`、すべての人が最初の訪問で終了することを保証します。 キューは要素ごとに最初の順序で 1 回処理され、再挿入は発生せず、出力内の ID 順序が維持されます。 

M = 1 など、M が非常に小さく、Ri が大きい場合、繰り返しのサイクリングが正しく動作することが保証されます。 各人は何度もキューに再入力しますが、各ステップで残りの作業負荷の合計がちょうど 1 単位だけ削減され、最終的な完了と純粋に枯渇のタイミングに基づいた正しい順序付けが保証されるため、アルゴリズムは依然として終了します。
