 ## 解決策
 ## 問題の理解

 指定された包括的な間隔内で、その期間内に何暦日が存在するかをカウントする必要があります。`YYYYMMDD`表現には連続する 3 桁の数字が含まれます`202`。 

日付は数値としてプロパティと比較されません。 実際の 8 文字の表現が重要です。 例えば、`22020101`含まれています`202`部分文字列は年の 2 桁目から始まるため、`20190202`部分文字列が年から月にまたがっているため、これが含まれています。 

入力には最大で次のものが含まれます`10^5`独立した日付間隔。 年数は以下に限定されます`2000`を通して`9999`, したがって、可能な年は 8000 年だけです。 これにより、範囲全体にほぼ 300 万日が含まれるため、すべてのクエリを毎日スキャンする必要がなくなります。`10^5`ケースが近づいてくるだろう`3 * 10^11`日付チェック。 小さい固定年の範囲は、すべての年を 1 回前処理し、プレフィックス合計を使用して各クエリに答えることを提案します。 

難しいのは、境界と異なる場所です。`202`現れることがあります。 不注意な解決策では、年に次の内容が含まれているかどうかのみを確認する可能性があります。`202`そして、その月と日に関係するケースを見逃します。 たとえば、間隔`2111 02 01`に`2111 02 03`有効な日付は 1 つだけです。`21110202`, 部分文字列は月と日の部分で形成されているためです。 もう 1 つの間違いは、終了日を除外していることです。 のために`2020 01 01`に`2020 01 02`、両方の完全な文字列に次のものが含まれるため、両方の日付が有効です。`202`、したがって、答えは次のとおりです`2`。 

うるう年も重要です。 たとえば、間隔`2200 02 28`に`2200 03 01`2200 はうるう年ではないため、3 日ではなく 2 日が含まれています。 

## アプローチ

 直接的な解決策は、間隔内のすべての日付を反復処理し、それを次のように変換することです。`YYYYMMDD`、どうかを確認してください。`"202"`が表示されます。 毎日 1 回だけ検査されるため、これが正しいことを証明するのは簡単です。 ただし、可能な最大の間隔は 2000 年から 9999 年までで、これには約 290 万日が含まれます。 その作業を何時間も繰り返すことで、`10^5`クエリが制限をはるかに超えています。 

重要な観察点は、カレンダーの範囲がクエリの数に比べて小さいことです。 可能な年は 8000 年しかありません。 毎年、その中に含まれる有効な日付の数をカウントすることで前処理できます。`202`、また、年の内部のプレフィックス情報も保存します。 

クエリの場合、答えは次のようになります。`number of valid days in years before Y2`プラス`number of valid days from January 1 to the ending date`、開始日の前日に計算された同じ値を差し引いたもの。 

これにより、前処理後にすべてのクエリが一定量の作業に変わります。

 ## アルゴリズムのチュートリアル

 1. 2000 年から 9999 年までの各年の情報を事前計算します。各年について、すべての有効な月と日をシミュレートし、8 桁の日付文字列を作成し、それに含まれる日付文字列が含まれているかどうかを数えます。`202`。 

年数は固定されており小さいため、この前処理は低コストであり、クエリから繰り返しの作業が不要になります。 
2. プレフィックス配列を保存します。`prefix[y]`2000 年から年末までの有効な日付の数です。`y`。 

これにより、何年も前からクエリ境界に到達するまでに即座に回答することができます。 
3. 毎年、月と日ごとの累積数も保存します。 これにより、クエリが年の途中で終了する場合、年の初めの部分だけをカウントすることができます。 
4. 有効な日付の数を返す関数を定義します。`2000-01-01`任意の日付に。 

事前に計算された完全な年と部分的な年の情報が結合されます。 
5. 各クエリに次のように答えます。`count(end_date) - count(day_before_start_date)`前日を減算すると、包含期間が正しく処理されます。 

なぜ効果があるのか:

 プレフィックス関数は常に、固定された開始点から要求された日付までの日数を正確にカウントします。 クエリ間隔の場合、最初の日より前にすべてを削除すると、間隔内の日数がそのまま残ります。 すべての日付は完全に従ってカウントされるため、`YYYYMMDD`前処理中の表現、発生する可能性はありません`202`見逃されています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def leap(y):
    return y % 400 == 0 or (y % 4 == 0 and y % 100 != 0)

days_in_month = [31, 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31]

year_pref = [0] * 10001
inside = {}

for y in range(2000, 10000):
    cur = [[0] * 32 for _ in range(13)]
    total = 0
    for m in range(1, 13):
        limit = days_in_month[m - 1]
        if m == 2 and leap(y):
            limit += 1
        for d in range(1, limit + 1):
            if "202" in f"{y:04d}{m:02d}{d:02d}":
                total += 1
            cur[m][d] = total
    inside[y] = cur
    year_pref[y] = year_pref[y - 1] + total

def count_to(y, m, d):
    if y < 2000:
        return 0
    ans = year_pref[y - 1]
    if m:
        ans += inside[y][m][d]
    return ans

def previous_day(y, m, d):
    d -= 1
    if d == 0:
        m -= 1
        if m == 0:
            return y - 1, 12, 31
        d = days_in_month[m - 1]
        if m == 2 and leap(y):
            d += 1
    return y, m, d

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        y1, m1, d1, y2, m2, d2 = map(int, input().split())
        py, pm, pd = previous_day(y1, m1, d1)
        out.append(str(count_to(y2, m2, d2) - count_to(py, pm, pd)))
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```前処理ループは 2 種類の情報を構築します。`year_pref`店舗が完成した年数`inside[y]`特定の 1 年間の累積回答を保存します。 後者では、クエリごとに数か月、数日にわたる繰り返しを回避できます。 

クエリ関数は、まずターゲット年の前のすべての完全な年を取得し、次にターゲット年の内部の部分カウントを追加します。 前日関数が使用されるのは、プレフィックス関数が含まれるためです。 これがないと、開始日が 2 回カウントされてしまいます。 

サポートされている範囲全体の合計日数はわずか数百万であるため、Python の整数はここではオーバーフローしません。 避けるべき主な実装の詳細は、月の境界を越えて逆方向に移動するときに 2 月を正しく処理することです。

 ## 特殊なケース

 部分文字列は年の境界を越えて月または日になる場合があります。 入力用`2111 02 01 2111 02 03`、アルゴリズムは年を検査するだけではありません。 前処理中に完全な文字列をチェックします。`21110202`、したがって、答えは正しいです`1`。 

を含む年`202`その年の毎日が有効になります。 のために`2202 01 01 2202 12 31`、部分文字列は年の数字自体に表示されます。 2202 年の事前処理値は、その年の日数です。`365`、クエリはその完全な年の数を返します。 

うるう年は、存在できる日付の数に影響します。 のために`2200 02 28 2200 03 01`、逆方向の日付の計算ではグレゴリオ暦が使用され、2200 年はうるう年ではないことが認識されます。 2 月は 28 日なので、無効な 2 月 29 日は導入されません。
