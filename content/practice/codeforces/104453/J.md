 ## 解決策
 ## 問題の理解

 私たちは、1 つの狭い道路沿いに住む複数の隣人の活動をシミュレートしています。 各隣人は、1 から N までのインデックスが付けられた家を所有しています。時間の経過とともに、到着と出発の試行を説明するイベントの時系列ログを受け取ります。 

近所のkさんが到着すると、家のkの真ん前に車を停めようとします。 ただし、これは家 1 から k-1 までのすべての位置が空いている場合にのみ可能です。 そうしないと、家にたどり着けず、代わりに共有の駐車場に車を停めることになります。 

隣人 k が立ち去ることを決めたとき、彼らの行動は車がどこにあるかによって異なります。 自分の車が共有駐車場にある場合、すぐに正常に出発します。 車が家の前に駐車されている場合、家 1 ～ k-1 の前の道路セグメントに現在車がいない場合にのみ出発できます。 その条件が満たされない場合でも、すぐに退職するとは限りません。 先に出発しなければならない先行車に妨害される可能性があり、その妨害が彼らに有利に解決しない場合、彼らは敷地内に留まる。 

最後のタスクは、すべてのイベントを処理した後、各ネイバーを 3 つの状態 (未到着、正常に出発、または一晩滞在) のいずれかに分類することです。 

この制約により、最大 100,000 のイベントと 100,000 の近隣イベントが許可されます。 これにより、イベントごとに住宅のプレフィックス全体をスキャンして可視性やブロック条件を再計算するソリューションは即座に除外されます。これは、最悪の場合、二次的な動作につながるためです。 

重要な点は、出発は要求時の 1 回の小切手だけではないということです。 隣人が家から出ようとすると、車が先にブロックされることで遅れる可能性があります。これは、システムがインデックス全体にカスケード依存構造を持っていることを意味します。 

素朴なシミュレーションを壊すエッジ ケースの 1 つは、その時点でプレフィックスが明確であれば、出発要求が常に即座に解決されると仮定することです。 たとえば、位置 5 の車が位置 3 の車によってブロックされ、それ自体が以前の構造によってブロックされている構成を考えてみましょう。 単純な 1 パス チェックでは、最終的に 3 が離れると解放される可能性があるにもかかわらず、誤って 5 を離れることができないとマークされてしまいます。 

もう 1 つのエッジ ケースは、同じ隣人の複数の到着と出発です。 正しい解決策では、単にフラグを切り替えるのではなく、各到着を状態の再確立として扱う必要があります。 

最後に、隣人が現在「駐車しているかどうか」を追跡するだけでは十分ではありません。 また、プレフィックス ブロッキング ダイナミクスの下で家の位置からの離脱が実現可能になるかどうかも判断する必要があります。これは、最も早いブロッキング位置の効率的な解決をサポートする構造が必要であることを示唆しています。 

## アプローチ

 ブルートフォース手法では、必要に応じて 1 から k-1 までのすべての位置が空かどうかを明示的にチェックすることで、各イベントをシミュレートします。 これには、サイズ O(k) のプレフィックスをスキャンする必要があり、最悪の場合、k は O(N) になる可能性があります。 イベントが M 個ある場合、時間計算量は O(NM) となり、10^5 の制約には遅すぎます。 

主な非効率性は、プレフィックス間隔に車両がないかどうかを繰り返し再計算することです。 これは、動的な占有を維持し、プレフィックス空のクエリに効率的に応答できるデータ構造が必要であることを示唆しています。 セグメント ツリーまたはフェンウィック ツリーは、プレフィックス内に車両が存在するかどうかを追跡し、チェックを対数時間に短縮します。 

ただし、より深く観察すると、プロセスがさらに簡素化されます。 ブロックに関連する唯一の情報は、プレフィックス内の左端の車両の存在です。 完全な占有履歴は必要ありません。特定の時点でプレフィックスが空かどうかだけが必要です。 これは、一連の占有位置と最小限のプレフィックス クエリをサポートする構造を使用して維持できます。

正しい削減は、家の前の占有駐車位置の動的に順序付けられたセットを維持することです。 駐車が成功すると、到着によって位置が挿入されます。 出発すると削除されます。 移動の実現可能性は、[1, k−1] 内に占有位置が存在するかどうかのみに依存します。これは、最小占有位置が < k であるかどうかを確認することに相当します。 これにより、ソートされた構造を維持し、プレフィックス最小のクエリに効率的に応答することが問題になります。 

バランスのとれた BST またはプレフィックス最小追跡を備えたソート セットでは、すべての操作を対数時間で実行できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NM) | O(N) | 遅すぎる |
 | 最適 (順序付きセット/プレフィックス最小構造) | O(M log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 道路を占有駐車位置のセットとしてモデル化します。 各位置は、現在家の前に車を停めている隣人に対応します。 

1. 現在占有されているすべてのハウスフロントポジションの分類された構造を維持します。 これは、道路を物理的にブロックしているすべての車両をプレフィックス順に表します。 
2. 各隣人の状態（未到着、現在家にいる、現在駐車場にいる、またはすでに出発している）を追跡する配列または地図を維持します。 これは、繰り返されるイベントを正しく解釈するために必要です。 
3. 「+ k」イベントを処理する場合、まず [1, k−1] 区間に占有位置が存在するかどうかを確認します。 これは、占有セット内の最小要素が k 未満であるかどうかを確認することと同じです。 
4. そのようなブロック位置が存在しない場合は、k を占有セットに挿入します。これは、車が家の前に駐車されていることを意味します。 それ以外の場合は、車は共有駐車場に行ったとみなされるため、非閉塞状態として別途記録されます。 
5. 「-k」イベントを処理するとき、隣人が現在共有駐車場にいるかどうかを確認します。 そうであれば、彼らはすぐに出発し、終了としてマークされます。 
6. 隣人が家の前に駐車している場合、占有セットから k を削除しようとします。ただし、それがプレフィックス条件に影響を与える現時点で最小のブロック要素である場合に限ります。 k がそれより小さいインデックスによってブロックされない場合は、k を離れて削除できます。 
7. 小さいインデックスによってブロックされている場合は、まだ削除できません。 待機中としてマークしたままにします。 
8. すべてのイベントを処理した後、近隣住民が駐車場にいたことがあるか、正常に移動したことがあるか、または到着しなかったかに基づいて各近隣住民を分類します。 

重要な不変条件は、占有セットには常に、現在道路の一部のプレフィックスをブロックしている車両が正確に含まれており、プレフィックス順序の制約に違反しない場合にのみ出発が許可されるということです。 最小の占有位置はゲートキーパーとして機能します。小さいインデックスが依然として道路をブロックしている間、より大きなインデックスはハウス ポジションから離れることはできません。 これにより、すべての有効な出発が、イベントごとに貪欲に処理されるのではなく、グローバルに一貫した順序で処理されることが保証されます。 

ブロッキングはプレフィックスの最小値のみに依存するため、出発を許可する構成では、最終的にはある時点で車両が最小のブロッキング要素として公開される必要があります。 このアルゴリズムは、この順序制約の下で構造的に適格な場合にのみ車両を削除し、時期尚早または無効な削除を防ぎます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())

    present = [False] * (n + 1)
    left = [False] * (n + 1)

    parked = set()
    import bisect
    arr = []

    def has_block(k):
        if not arr:
            return False
        # smallest occupied position
        return arr[0] < k

    for _ in range(m):
        op, k = input().split()
        k = int(k)

        if op == '+':
            if not has_block(k):
                # parked in front of house
                if k not in parked:
                    parked.add(k)
                    bisect.insort(arr, k)
            else:
                # goes to external parking (not tracked in occupied set)
                pass
            present[k] = True

        else:
            # departure request
            if k in parked:
                # can only leave if no blocking smaller index remains
                # if k is currently minimal, it can leave
                if arr and arr[0] == k:
                    parked.remove(k)
                    arr.pop(0)
                    left[k] = True
            else:
                # in external parking
                left[k] = True

    for i in range(1, n + 1):
        if not present[i]:
            print(-1)
        elif left[i]:
            print("YES")
        else:
            print("NO")

if __name__ == "__main__":
    solve()
```このソリューションでは、近隣者が到着したかどうか、および近隣者が正常に出発したかどうかという 2 つの状態が維持されます。 リスト`arr`現在道路をブロックしているすべての車両をソートされた順序で維持するため、最小の要素には常に O(1) 時間でアクセスできます。 挿入ではバイナリ挿入を使用して順序を保持しますが、前方からの削除では最もブロックされている車両の解決をシミュレートします。 

セット`parked`道路を物理的に妨げている車と外部駐車中の車を区別します。 駐車中の車のみがプレフィックス制約と対話します。 

微妙な実装の詳細は、車が現在最小のブロックインデックスである場合にのみ家からの出発が許可されることです。 これは、より小さいインデックスの車が道路の前に留まらないという制約をエンコードします。

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    from collections import defaultdict

    n, m = map(int, input().split())
    present = [False] * (n + 1)
    left = [False] * (n + 1)
    parked = set()
    import bisect
    arr = []

    def has_block(k):
        return arr and arr[0] < k

    for _ in range(m):
        op, k = input().split()
        k = int(k)
        if op == '+':
            if not has_block(k):
                if k not in parked:
                    parked.add(k)
                    bisect.insort(arr, k)

        else:

        if not present[i]:
            out.append("-1")
        elif left[i]:
            out.append("YES")
        else:

    return "\n".join(out)

 ## 特殊なケース

 主なエッジ ケースは、ネイバーが到着したものの、より小さいインデックスによってすぐにブロックされる場合です。 この状況では、アクティブなパーク セットには参加しません。 たとえば、1 がすでにブロックしている後に 2 が到着した場合、2 は 1 が解決されるまでプレフィックスの状態に影響を与えることはできません。 このアルゴリズムは、より小さなブロック位置が存在しない場合にのみ、順序付けられた構造に挿入することでこれを保証します。 

もう 1 つのケースは、同じ隣人の到着と出発が繰り返される場合です。 近隣住民が到着したかどうかと、正常に出発したかどうかを個別に追跡するため、再到着によって最終的な分類が上書きされることはありません。 状態はイベント全体で累積されます。 

最後のエッジ ケースは、ブロックされたセットに現在ネイバーが存在しないときに離脱しようとすることです。 これは、常にすぐに出発できる外部駐車場に対応します。 このアルゴリズムは、その分岐内のプレフィックス制約を明示的にバイパスし、内部順序付けが適用されない場合でも正確さを保証します。
