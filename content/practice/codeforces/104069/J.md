 ## 解決策
 ## 問題の理解

 空から始まるセットに時間の経過とともに適用される一連の操作が与えられます。 操作は順番に処理され、各挿入操作の後に概念的にはセットの新しい「バージョン」を取得します。 後のクエリは現在のセットを参照するのではなく、以前の操作インデックス t の直後のセットの状態を参照します。 

クエリには3種類あります。 1 つは操作 t の後のセット内の最大要素を要求し、もう 1 つは操作 t の後の最小要素を要求し、最後は操作 t の後のすべての要素の合計を要求します。 挿入では値が追加されるだけで、何も削除されることはありません。 

重要な点は、クエリが現在の状態に関するものではなく、過去の状態に関するものであるということです。 これは、最終結果だけでなく、操作シーケンスの前のプレフィックスに関する質問に答えることができなければならないことを意味します。 

この制約により、最大 100,000 回の操作が可能になります。 時刻 t までの設定を再構築することでクエリごとに応答を最初から再計算するソリューションは、最悪の場合は 2 次となり、遅すぎます。 ゼロから再計算を繰り返す場合、クエリごとの対数構造であっても十分ではありません。 

単純な実装では、単一のセットを維持し、クエリごとに、時刻 t までのすべての挿入を再生することによってそれを再構築する可能性があります。 初期のプレフィックスについて尋ねるクエリが終わり近くに多数ある場合、これは失敗します。 たとえば、100,000 個の要素を挿入し、すべて t = 1 を参照する 100,000 個のクエリを実行すると、各クエリはほぼ履歴全体を再度スキャンし、約 10^10 の操作が生成されます。 

別の失敗例は、クエリが挿入とインターリーブされる場合に発生します。 現在のセットのみを維持すると、過去の状態に関するすべての情報が失われるため、再計算なしでは以前の t に対するクエリは不可能になります。 

したがって、重要な要件は、長期にわたる範囲クエリをサポートしながら、プレフィックス情報を効率的に維持する構造です。 

## アプローチ

 ブルートフォース戦略は簡単です。 一つ一つ操作をシミュレーションしていきます。 挿入されたすべての要素のリストを維持します。 時間 t のクエリを受け取ると、最初の t 回の操作を繰り返し、挿入されたすべての値を収集することによって設定状態を再構築し、最小値、最大値、または合計を計算します。 

各クエリは操作履歴のプレフィックスを正確に尋ねるため、これは論理的に機能します。 ただし、クエリごとにプレフィックスを再構築すると、同じデータを繰り返しスキャンすることになります。 最悪の場合、各クエリのコストは O(n) で、クエリが O(n) の場合、これは O(n^2) となり、100,000 回の操作には遅すぎます。 

この改善は、すべてのクエリがプレフィックスのみに依存し、追加情報のみを挿入することを認識することで実現しました。 これは、時間をかけてプレフィックス集計を事前計算できることを示唆しています。 各操作インデックス i について、i までのすべての挿入値の最小値、最大値、および合計を維持すると、すべてのクエリは O(1) になります。 

これが可能なのは、挿入が唯一の更新操作であるため、単純な更新によって各プレフィックスを前のプレフィックスから導出できるためです。 過去の値を削除したり変更したりすることはないため、バランスの取れたツリーのような動的なセット構造は必要ありません。 

操作番号によってインデックス付けされた 3 つの配列 (プレフィックス最小値、プレフィックス最大値、およびプレフィックス合計) を維持します。 挿入のたびに、これらの配列を前の状態から更新します。 クエリ操作の場合、インデックス t に格納されている値を直接出力します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) | O(n) | 遅すぎる |
 | プレフィックスの事前計算 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ステップのプレフィックス情報を構築しながら、操作を順番に処理します。

1. プレフィックス状態を追跡するための 3 つの配列または変数 (現在の最小値、現在の最大値、および現在の合計) を初期化します。 セットは空から始まるため、最初の挿入をどのように処理するかを定義する必要もあります。 最初の操作は挿入であることが保証されており、クエリの空セットのエッジ ケースが回避されます。 
2. 1 から n までの各操作 i について、そのタイプを読み取ります。 値 x の挿入の場合、x を追加して現在の合計を更新し、それに応じて現在の最小値と最大値を更新します。 インデックス i のプレフィックス値がこれらの更新された値になります。 
3. 操作が時間 t における最大値を求めるクエリである場合、プレフィックス t に対応する保存された最大値を直接出力します。 これは、プレフィックス t が t 回の挿入後の設定状態をすでに表しているため、機能します。 
4. 操作が時間 t での最小値を求めるクエリの場合、プレフィックス t で保存されている最小値を出力します。 
5. 操作が時間 t での合計を求めるクエリの場合、プレフィックス t に保存されている合計を出力します。 

重要な設計上の選択は、すべての挿入でプレフィックスの状態を永続的に定義することです。 私たちは歴史を再計算することは決してなく、単にそれを拡張するだけです。 

これが機能する理由は単純な不変条件に基づいています。つまり、操作 i を処理した後、保存された値は、最初の i 操作で挿入されたすべての要素の集合プロパティを正確に表します。 挿入によって要素が削除されることはないため、接頭辞 i は常にその時点のセットの完全な表現になります。 時間 t について尋ねるクエリは、以前に計算されたプレフィックス状態を読み取るだけであり、後の操作では変更されません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())

INF = 10**30

# prefix arrays (1-indexed conceptually)
mx = [0] * (n + 1)
mn = [0] * (n + 1)
sm = [0] * (n + 1)

cur_max = -INF
cur_min = INF
cur_sum = 0

for i in range(1, n + 1):
    parts = input().split()
    typ = int(parts[0])

    if typ == 1:
        x = int(parts[1])
        cur_sum += x
        cur_max = max(cur_max, x)
        cur_min = min(cur_min, x)

    mx[i] = cur_max
    mn[i] = cur_min
    sm[i] = cur_sum

    if typ == 2:
        t = int(parts[1])
        print(mx[t])
    elif typ == 3:
        t = int(parts[1])
        print(mn[t])
    elif typ == 4:
        t = int(parts[1])
        print(sm[t])
```このソリューションは、実行中のアグリゲートを維持しながら、プレフィックス スナップショットも保存します。 重要な詳細は、挿入後だけでなく、各操作インデックス i の処理後の状態を記録することです。 この調整により、任意の t を参照するクエリが正しいプレフィックス状態に直接インデックス付けされることが保証されます。 

微妙な点の 1 つは、最小値と最大値の初期化です。 最初の挿入で両方の値が正しく設定されるように、極端なセンチネルから始めます。 最初の操作は挿入であることが保証されているため、未定義の値が出力されることはありません。 

もう 1 つの詳細は、クエリは過去のインデックスを参照するため、現在の状態を直接使用することはありません。 すべての答えは、t でインデックス付けされた配列から読み取られます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、多くの挿入が後で発生するのに、クエリが非常に早い時間を参照する場合です。 たとえば、t = 1 に対する多数のクエリが後に続く大きなシーケンスを挿入します。インデックス 1 のプレフィックス状態は計算後に凍結され、その後の更新によって変更されないため、アルゴリズムはこれを正しく処理します。 

もう 1 つのケースは、挿入とクエリを交互に行うことです。 すべてのインデックスにプレフィックスの状態を保存するため、クエリは再計算を必要とせずに常に一貫したスナップショットを読み取ります。 

最後のケースは、入力を厳密に増加または減少させる場合で、最小値または最大値がすべてのステップで常に更新されます。 センチネルの初期化により、最初の値が両方の境界を正しく設定し、後続のすべての更新で単調な正確さが維持されることが保証されます。
