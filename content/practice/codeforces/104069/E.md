 ## 解決策
 ## 問題の理解

 私たちは、削除が永続的なマルチセットのような構造に保存された靴のサイズのコレクションを管理しています。 顧客が到着するたびに、許容可能な靴の最小サイズを指定します。私たちは、そのサイズが少なくともそのしきい値である、入手可能な最小の靴を顧客に提供する必要があります。 靴が割り当てられると、インベントリから削除され、再利用することはできません。 

入力により、靴のサイズの初期配列が提供され、その後、一連のクエリが提供されます。 各クエリは入力では独立していますが、実行では独立していません。これは、以前の割り当てにより、後のクエリで使用できるプールが変更されるためです。 クエリごとに、割り当てられた靴のサイズを出力するか、適切な靴が存在しない場合は -1 を出力します。 

この制約では、最大 10^9 の値で、最大 200,000 個の靴と 200,000 個のクエリが許可されます。 すべてのクエリに対して配列全体をスキャンしようとするソリューションは、n·q 回の操作で実行されます。これは、最悪の場合、最大 4·10^10 の比較になります。 これは、Python や最適化された C++ で数秒で実行できる速度をはるかに超えています。 

素朴なアプローチは、クエリが減少しているすでにソートされたリストのような単純なシナリオでは失敗します。 たとえば、靴が [1、2、3、4、5] で、クエリがすべて 5 の場合、各クエリはリスト全体をスキャンして、最後に残っている有効な要素を見つけます。 答えは明白ですが、リニア スキャンの繰り返しが実行時間の大半を占めます。 

微妙なエッジケースでは、同じ値が繰り返されます。 入力が [4, 4, 4] でクエリが [4, 4, 4, 4] の場合、正しい動作は、クエリごとに 4 を 1 つ消費し、使い果たされるまで、-1 を返すことです。 要素を削除済みとしてマークするのを忘れたり、重複を誤って処理したりする単純な解決策では、同じシューズを複数回再利用するか、有効な一致をスキップすることになります。 

## アプローチ

 ブルート フォース戦略は簡単です。クエリごとに、配列全体を左から右にスキャンし、少なくとも x である最初の要素を見つけて出力し、配列から削除します。 削除は、要素を物理的に削除するか、要素をマークすることによって実行できます。 ステートメントで指定されたルールを直接シミュレートするため、正確さがすぐにわかります。 

失敗点はパフォーマンスです。 最悪の場合、各クエリのコストは O(n) となり、q 個のクエリがあるため O(nq) になります。 n と q が両方とも 2・10^5 までの場合、これは実行不可能になります。 

重要な点は、値の動的なセットに対して 2 つの操作が繰り返し必要であるということです。つまり、少なくとも x である最小の要素を見つけて、それを削除します。 これはまさに、動的順序セットに対する先行クエリのようなクエリです。 最初の配列をソートすると、問題は下限検索と削除を効率的にサポートする構造を維持することになります。 

バランスの取れた二分探索ツリーまたはマルチセットはこれを直接サポートしますが、競技プログラミングでは、ソートされた構造と二分探索を使用して効率的にシミュレートできます。 ただし、Python リストでの削除は線形であるため、削除によって大きなセグメントがシフトされない構造が必要です。 頻度カウントのセグメント ツリーや、二分化と遅延削除によるソートされたコンテナも機能しますが、最もクリーンなアプローチは、圧縮された値ドメインのセグメント ツリー、または出現回数を保存するフェンウィック ツリーで、バイナリ リフティングによって次に利用可能な値を見つけることができます。 

サイズは 10^9 までですが、存在する個別の値は 2・10^5 のみであるため、値を圧縮します。 圧縮後も周波数は維持されます。 各クエリは、「x によって制約された値の順序でプレフィックスの合計 ≥ ターゲット位置を持つ最初のインデックスを検索する」になります。 まず、バイナリ検索を使用して、値が x 以上である最初の圧縮インデックスを見つけます。次に、フェンウィック ツリーの「k 番目」スタイルのウォークを使用して、次に利用可能なアクティブなインデックスを見つけます。 これにより、有効な利用可能な最小の靴が得られ、その数が減ります。 

これにより、各クエリが O(log n) に減り、合計は O((n + q) log n) になります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | 最適 (Fenwick / マルチセット シミュレーション) | O((n+q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず靴のサイズを並べ替えて圧縮し、元の値にマッピングしながら昇順に推論できるようにします。 それぞれの個別のサイズは、ソートされた配列内のインデックスを取得します。 

これらのインデックス上にフェンウィック ツリーを構築し、各位置にそのサイズの靴が現在いくつあるかを格納します。 

各クエリ x について、x を、値が少なくとも x である圧縮配列内の最初のインデックスに変換します。 この時点からは、x より前のすべてがこのクエリでは無効になるため、構造体のサフィックスのみを気にするようになります。 

次に、フェンウィック ツリーを使用して、そのインデックス以降にまだ正のカウントがある最初の位置を見つけます。 これは標準の「累積頻度が目標に達する最初のプレフィックスを見つける」操作であり、1 からではなく下限インデックスから開始するように適合されています。 

その位置を特定したら、その値を出力し、フェンウィック ツリー内の頻度を減分します。 

そのような位置が存在しない場合は、-1 を出力します。 

### なぜ効果があるのか

 あらゆるステップで、フェンウィック ツリーは利用可能なシューズの正確なマルチセットを維持します。 二分探索ステップにより、クエリしきい値より小さい値が考慮されることがなくなります。 「k 番目のような」走査により、有効な候補の中からまだ生きている最小のインデックスが確実に選択されます。 削除するたびに構造が即座に更新されるため、今後のクエリでは常に正しい残りの在庫が反映され、シミュレーションは問題の定義と正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def kth(self, k):
        pos = 0
        bitmask = 1 << (self.n.bit_length())
        while bitmask:
            nxt = pos + bitmask
            if nxt <= self.n and self.bit[nxt] < k:
                k -= self.bit[nxt]
                pos = nxt
            bitmask >>= 1
        return pos + 1

def lower_bound(arr, x):
    lo, hi = 0, len(arr)
    while lo < hi:
        mid = (lo + hi) // 2
        if arr[mid] >= x:
            hi = mid
        else:
            lo = mid + 1
    return lo

def main():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    vals = sorted(set(a))
    idx = {v: i + 1 for i, v in enumerate(vals)}

    fw = Fenwick(len(vals))

    for v in a:
        fw.add(idx[v], 1)

    for _ in range(q):
        x = int(input())
        pos = lower_bound(vals, x)
        if pos == len(vals):
            print(-1)
            continue

        # convert to Fenwick index range [pos+1 ... end]
        # we need first active in suffix, so we compare counts
        total_before = fw.sum(pos)
        total_all = fw.sum(len(vals))
        if total_all - total_before <= 0:
            print(-1)
            continue

        # find (total_before + 1)-th alive element overall
        # but must ensure it's within suffix; this is guaranteed by construction
        k = total_before + 1
        i = fw.kth(k)

        if i < pos + 1:
            # fallback safety, should not happen
            i = fw.kth(total_before + 1)

        print(vals[i - 1])
        fw.add(i, -1)

if __name__ == "__main__":
    main()
```フェンウィック ツリーは、各靴サイズの頻度を圧縮形式で維持します。 の`lower_bound`関数は、最初の適格なサイズ インデックスを見つけます。 次に、そのインデックスの前に有効な靴がいくつ存在するかを計算し、グローバル k 番目のクエリを使用して次に利用可能な靴を選択します。 これが機能するのは、開始ランクを制限することで無効な候補がすべて事実上スキップされるためです。 

よくある注意点は、誤って x より小さい靴を選択しないようにすることです。 そのため、プレフィックス数を明示的に比較し、最初の有効なランクから選択を開始します。 もう 1 つの微妙な点は、重複を正しく処理することです。フェンウィック ツリーは多重度を格納するため、同じサイズは自然に 1 つずつ消費されます。

 ## 特殊なケース

 システム内の単一の靴の場合、アルゴリズムは即時の消耗を正しく処理します。 入力が`10`続いて 2 つのクエリ`10, 10`、フェンウィック ツリーには最初は 1 つのアクティブな要素があります。 最初のクエリはそれを見つけて削除し、2 番目のクエリは残りの要素がゼロであることを確認し、-1 を返します。 

重複の場合、構造は各出現を独立して処理します。 のような場合`[4,4,4]`クエリ付き`[4,4,4,4]`、クエリが成功するたびに、頻度がちょうど 1 ずつ減少します。 最後のクエリでは、プレフィックスの合計がしきい値を超えてゼロであることが観察され、-1 が正しく出力されます。 

しきい値スキップについては、次の点を考慮してください。`[1,100]`クエリ付き`50`。 下限は 100 から始まるため、アルゴリズムは 1 を考慮しません。その後、フェンウィック ツリーは最初の有効な要素として 100 を直接返し、配列の前に無効な小さい要素が存在する場合でも正確さを保ちます。
