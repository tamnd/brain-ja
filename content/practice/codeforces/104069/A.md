 ## 解決策
 ## 問題の理解

 チアゴとネイサンの 2 人のプレーヤーは、公式ルールのように 2 ポイントごとにサーバーが交代するのではなく、ブロックごとにサーバーが切り替わる卓球スタイルのゲームをプレイしています。 代わりに、誰が得点したかに関係なく、合計 k 点が得点されるごとにサーバーが変わります。 チアゴはいつも試合の開始時にサービスを開始します。 

複数の独立したテスト ケースでの現在のスコアが与えられます。 ケースごとに、現在のプレイ総ポイント数に基づいて、次に誰がサーブするかを決定する必要があります。 各ポイントがサーブサイクルを進めるため、これまでにプレイされたポイント数以外には、スコア自体はサーブの変更に影響しません。 

各テスト ケースは、k、サービス変更のブロック サイズ、および現在のスコア T と N を提供します。これらから、合計で何ポイントがプレイされたかを計算し、完全なサービス ブロックが何回経過したかを決定します。 完了したブロックの数が偶数の場合、依然としてチアゴがサーバーです。 奇数であれば、ネイサンが仕えます。 

この制約では、最大 10^4 のテスト ケースと、k およびスコアの最大 10^9 の値が許可されます。 これにより、各ポイントを個別に処理するシミュレーションは即座に除外されます。 ポイントごとのシミュレーションでは、1 回のテストで最大 2 × 10^9 の演算が必要になりますが、これは実現可能な限界をはるかに超えています。 解はテスト ケースごとに O(1) である必要があります。 

点の総数がちょうど k で割り切れる場合、微妙なエッジ ケースが発生します。 この場合、最終ポイントの直後にサーブが切り替わるため、完了したブロックの数が偶数か奇数かによって次のサーバーが決まります。 もう 1 つの特殊なケースは、T = 0 および N = 0 の場合です。これは、ポイントがまだプレーされていないことを意味するため、チアゴはまだサービスを提供している必要があります。 

## アプローチ

 単純な考えは、ゲームをポイントごとにシミュレートすることです。 チアゴをサーバーとして開始し、ポイントごとにカウンターをインクリメントし、k ポイントごとにサーバーを切り替えます。 T + N ステップを処理した後、現在のサーバーを出力します。 これはルールに直接従うため、正しいです。 

ただし、T + N は 2 × 10^9 まで大きくなる可能性があるため、このアプローチは制約の下では不可能になります。 ポイントごとに 1 つの操作を実行するだけでも、制限時間を数桁超えてしまいます。 

重要な点は、個々の点を追跡する必要がないということです。 唯一関連する数量は、サイズ k の完成したブロックの総数です。 S = T + N を計算すると、完全なブロックの数は S // k になります。 各ブロックはサーバーを 1 回だけ反転するため、サーバーはこの商のパリティのみに依存します。 

これにより、問題全体がテスト ケースごとの定数時間の算術計算に縮小されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | テストあたり O(T + N) | お(1) | 遅すぎる |
 | 算術ブロックカウント | テストごとに O(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各テスト ケースの k、T、および N を読み取ります。 これらは、ブロック サイズとゲーム状態の現在の合計ポイントを定義します。 
2. S = T + N、これまでにプレーした合計ポイント数を計算します。 サーブの切り替えは、完了した完全な k ポイント セグメントの数にのみ依存します。 
3. ブロック = S // k を計算します。 各完全なブロックは、サーバーが切り替わるまでの 1 つの完全なサービス間隔に対応します。 
4. ブロックが偶数の場合、チアゴがサーブを開始し、偶数のフリップでサーブがスターターに戻るため、「チアゴ」を出力します。 
5. ブロックが奇数の場合は、「Nathan」を出力します。これは、フリップ数が奇数であるということは、サーブがスターターから切り替わったことを意味するためです。 

### なぜ効果があるのか

サーブは、グローバル ポイント シーケンス内のサイズ k の固定境界でのみ変更されます。 これにより、タイムラインが連続した間隔に分割され、各間隔で現在のサーバーが 1 回だけ反転されます。 チアゴは時間ゼロからサービスを開始するため、Sポイント後のサーバーは完全なインターバルを何回越えたかのみに依存します。 現在の間隔内の部分的な進行状況は次のサーバーには影響しません。完了した間隔のみが問題となります。 したがって、S // k のパリティによって完全に答えが決まります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    k, T, N = map(int, input().split())
    total = T + N
    blocks = total // k

    if blocks % 2 == 0:
        print("Thiago")
    else:
        print("Nathan")
```実装は数学的リダクションの直後に行われます。 重要なステップは、状態を合計ポイントに折りたたんで、個々の得点シーケンスを追跡する必要性を回避することです。 整数除算によって完了したサービス間隔の数が計算され、パリティによってサーバーが決定されます。 

よくある間違いは、切り替えがゼロを含む k 番目のポイントごとではなく、k ポイントの後に発生することを忘れていることです。 フロア分割を使用すると、off-by-one の問題が発生することなく、これが正しく処理されます。 もう 1 つの微妙な点は、得点はサーブ ルールに影響を与えないため、誰が最後のポイントを得点したかを考慮する必要がないことです。 

## 実用的な例

 ### 例 1

 合計ポイント S = 5

 | ステップ | S | ブロック = S // k | パリティ | サーバー |

これにより、スコアの分布が不均等であっても、重要なのは合計ポイントのみであることがわかります。 

### 例 2

 | --- | --- | --- | --- | --- |
 | イニシャル | 4 | 0 | 偶数 | チアゴ |

 フルブロックが完成していないため、チアゴはサービスを継続する。 これは、不完全なブロックがスイッチをトリガーしないことを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(t) | 各テスト ケースは、一定数の算術演算を実行します。 
| スペース | お(1) | 入力サイズに関係なく、少数の整数だけが保存されます。 

このソリューションは、各テスト ケースが 1 つの除算とモジュロ演算に削減されるため、最大 10^4 のテスト ケースを快適に処理できます。 

## テストケース```python
import sys, io

def solve(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        k, T, N = map(int, input().split())
        total = T + N
        blocks = total // k
        out.append("Thiago" if blocks % 2 == 0 else "Nathan")
    return "\n".join(out)

# provided sample-style cases
assert solve("2\n7 1 0\n2 2 8\n") == "Thiago\nNathan"

# k large, no switch
assert solve("1\n10 3 4\n") == "Thiago"

# exact boundary switch
assert solve("1\n5 3 2\n") == "Nathan"

# multiple switches
assert solve("1\n3 9 0\n") == "Thiago"

# zero points
assert solve("1\n5 0 0\n") == "Thiago"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | k=10、S=7 | チアゴ | 完了したブロックがありません |
 | k=5、S=5 | ネイサン | 正確な境界反転 |
 | k=3、S=9 | チアゴ | 偶数回のフリップ |
 | k=5、S=0 | チアゴ | 初期状態 |

 ## 特殊なケース

 ポイントがプレイされていない場合、T = 0 および N = 0、合計は S = 0 です。計算により、ブロック = 0 // k = 0 が得られ、これは偶数であるため、チアゴがサーバーとして正しく識別されます。 

k = 4 や S = 8 など、S が正確に k の倍数である場合、ブロック = 2 が得られます。2 つのフルサービスインターバルが完了したため、サーブは 2 回切り替わり、チアゴに戻りました。 実装では、境界を明示的に検出する必要なく、これを正しくキャプチャします。 

k = 10^9 や 2 × 10^9 に近い S などの非常に大きな値の場合でも、整数の除算は定数時間で実行され、Python でのオーバーフローの問題を安全に回避します。
