 ## 解決策
 ## 問題の理解

 バイナリ文字列と部分文字列に対する多くのクエリが与えられます。 クエリ間隔ごとに、現在の部分文字列の連続する部分を繰り返し削除します。 唯一の制限は、どのような種類の部分を削除できるかということです。削除されるセグメントは厳密に交互でなければなりません。つまり、その中の隣接するすべてのペアが異なる文字で構成されている必要があります。 

1 回の削除で 1 文字、または次のような長いセグメントを削除できます。`0101`または`101`、しかし決して次のようなことはありません`00`または`111`これらには等しい隣接ビットが含まれているためです。 削除するたびに、文字列の残りの部分がギャップを埋めて新しい文字列を形成し、何も残らなくなるまで続けます。 タスクは、すべてのクエリ部分文字列に必要なそのような削除の最小数を計算することです。 

制約は大きく、最大 200,000 文字と 200,000 クエリがあります。 これにより、削除をシミュレートしたり、各クエリを線形時間で処理したりするソリューションは即座に除外されます。 許容可能なソリューションでは、文字列を線形時間で前処理し、各クエリに定数時間または対数時間で応答する必要があります。 

ここでよく見られる単純な間違いは、交互の部分文字列を削除できるため、長い交互のセグメントを貪欲に削除する必要があると想定することです。 この直感は単純な場合には役に立ちません。 たとえば、文字列では`11011`、貪欲な削除を試みる可能性があります`101`まず出発`11`、さらに 2 つの削除が必要になります。 ただし、別の戦略が可能に思えるかもしれませんが、それでも答えを 3 未満に減らすことはできません。主な問題は、削除が文字の恣意的な選択ではなく、隣接構造によって制約されることです。 

もう 1 つの微妙なエッジ ケースは、部分文字列がすでに完全に交互になっている場合です。`01010`。 この場合、答えは明らかに 1 ですが、同一文字の連続をカウントするだけのメソッドは、そのような連続がないことを正しく処理する必要があります。 

## アプローチ

 ブルートフォース戦略は簡単です。プロセスをシミュレートします。 クエリの部分文字列ごとに、現在の文字列を繰り返しスキャンし、最大の交互セグメントを見つけて削除し、空になるまで続行します。 各スキャンには線形時間がかかり、最悪の場合は線形削除まで実行され、最悪のシナリオでは三次的な動作が発生する可能性があります。 これは制約の下ではすぐに失敗します。 

重要な観察は、実際には削除をシミュレートする必要がまったくないということです。 代わりに、どのような構造が複数の操作の実行を強制するのかを考えます。 複数の削除にまたがって作業を分割する必要があるのは、元の部分文字列内の 2 つの隣接する文字が等しい場合だけです。 このようなペアは、文字列の他の部分をどのように削除するかに関係なく、同じ交互セグメントの一部になることはできません。これは、隣接関係の等価性が、連続するセグメント内で永続的な障害となるためです。 

これは単純化につながります: インデックスを見るたびに`i`そのような`a[i] == a[i+1]`の場合、部分文字列には基本ケース以外に少なくとも 1 つの追加操作が必要です。 逆に、部分文字列に等しい隣接ペアがない場合は、それ自体が交互になっており、1 回の操作で削除できます。 

したがって、答えは純粋に、各クエリ間隔内の隣接する等しいペアに対するカウントの問題になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 削除のシミュレーション | クエリあたり O(n²) | O(n) | 遅すぎる |
 | 隣接する等しいペアのプレフィックスの合計 | O(n) 個の前処理後のクエリごとに O(1) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各クエリを事前計算された配列のカウントに減らします。 

1. 補助配列を構築する`bad`、 どこ`bad[i] = 1`もし`a[i] == a[i+1]`、 さもないと`0`。 これにより、交互が途切れた位置を正確に捕捉します。 
2. プレフィックス合計配列を構築します`bad`。 これにより、任意の間隔に存在する等隣接ペアの数をすばやく計算できます。 
3. クエリごとに`[l, r]`、インデックスの数を計算します`i`で`[l, r-1]`どこ`a[i] == a[i+1]`プレフィックスの合計を使用します。 
4. 答えは次のとおりです。`1 + count_of_bad_pairs`。 の`1`は基本演算に対応し、それぞれの内部等価性により追加の演算が強制されます。 

これが機能する理由は、等しい文字のすべての最大ブロックがちょうど 1 つの強制分離ポイントに寄与し、そのような各ポイントを単一の交互削除内で処理できないためです。 

### なぜ効果があるのか

 不変条件は、有効な操作は隣接する等しい文字を含まない部分文字列のみを使用できるということです。 したがって、すべての位置で、`a[i] == a[i+1]`2 つの異なる「代替互換領域」間の必須カットとして機能します。 これらのカットは独立しているため、それぞれのカットで最小操作数が 1 つずつ増加します。 削除の構造では、これらの境界をまたぐセグメントは交互条件に違反するため、これらの境界を越えてマージすることはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n, q = map(int, input().split())
    s = input().strip()

    bad = [0] * (n + 1)
    for i in range(n - 1):
        if s[i] == s[i + 1]:
            bad[i + 1] = 1

    pref = [0] * (n + 1)
    for i in range(1, n + 1):
        pref[i] = pref[i - 1] + bad[i]

    out = []
    for _ in range(q):
        l, r = map(int, input().split())
        cnt = pref[r - 1] - pref[l - 1]
        out.append(str(cnt + 1))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    main()
```この実装は、観測値をプレフィックス合計に直接変換することに依存しています。 の`bad`配列は、各インデックスが文字間の境界に対応するようにシフトされ、クエリを処理する際の off-by-one の問題が回避されます。 次に、プレフィックス合計により、各クエリが定数時間範囲合計に変換されます。 

よくある間違いは、隣接性チェックが適用されることを忘れることです。`i`そして`i+1`、クエリ境界内の文字に直接ではありません。 これが、クエリで使用される理由です。`r-1`悪いポジションを数えるときの上限として。

 ## 特殊なケース

 単一の文字で構成される部分文字列は常に隣接するペアを生成しないため、答えは 1 になります。アルゴリズムはこれを処理します。これは、クエリ範囲が制限されているためです。`[l, r-1]`は空になり、プレフィックスの差はゼロになります。 

次のような完全に均一な部分文字列`000000`すべての境界で不良ペアを作成し、アルゴリズムは正確にカウントします`length - 1`、次のような正しい操作数が生成されます。`length - 1 + 1`。 

次のような完全に交互の部分文字列`010101`には不正なペアがないため、プレフィックスの合計の差はゼロとなり、答えは 1 つの操作に集約され、セグメント全体が 1 回の削除に対してすでに有効であるという事実と一致します。
