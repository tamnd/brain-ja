 ## 解決策
 ## 問題の理解

 2D 平面上の点の固定セットが与えられ、1 から n までの配列順序で保存されます。 各クエリは、この配列の連続セグメントを指定し、インデックスが両方ともそのセグメント内にある、別個の点の最も近いペアを要求します。 距離はユークリッドの二乗距離であるため、2 つの点に注目します。$(x_u - x_v)^2 + (y_u - y_v)^2$、範囲内の可能な最小値が必要です。 

主な問題は、ポイントのセットがクエリごとに変更されることですが、その変更は元の順序の連続したスライスを取得することによってのみ行われることです。 この構造が重要なのは、ジオメトリを毎回最初から再計算するのではなく、配列の間隔を前処理できることを示唆しているからです。 

この制約により、クエリごとのジオメトリから遠ざけられます。 最大 250,000 ポイントと 250,000 クエリを使用して、最も近いペアを再計算するソリューション$O(k \log k)$範囲が大きい場合、最悪の場合、クエリごとの動作は 2 次の動作に縮退します。 平$O(k)$すべてのクエリを合計すると、クエリごとの速度が遅すぎます。 

素朴だが重要なベースラインは、クエリされたセグメントを x 座標で並べ替え、標準の最近接ペア スイープを実行することです。 単一のクエリの場合は正しいですが、すでにコストがかかります$O(k \log k)$クエリごとに。 隠れた問題は、隣接するクエリがほとんどのポイントを共有しているにもかかわらず、クエリ間で再利用できないことです。 

単純な最適化の微妙な失敗例は、最も近いペアがインデックス空間では「ローカル」であるが、座標空間では「ローカル」ではない場合に発生します。 たとえば、配列に沿ってポイントが密なクラスターと外れ値の間で交互に存在する場合、インデックスでは遠く離れているものの、ジオメトリでは隣接している 2 つの近くのポイントが範囲に含まれる可能性があるため、ジオメトリを意識しないインデックス ベースの枝刈りは失敗します。 

## アプローチ

 ブルート フォース アプローチでは、各クエリが個別に処理されます。 範囲の場合$[l, r]$では、すべての点を抽出し、x 座標で並べ替えて、古典的なスイープ ラインの最近接ペア アルゴリズムを実行します。 これは正しいです。平面セット内の最も近いペアは、境界のある垂直ストリップ内で x ソートされた順序で近傍を考慮することによって常に検出されるためです。 問題は実行時間です。1 つのクエリにコストがかかります$O(k \log k)$、そして最悪の場合には$k = n$、それで私たちは到達します$O(n \log n)$クエリごとに、$O(n q \log n)$全体として、それは限界をはるかに超えています。 

重要な観察は、クエリがインデックス空間で大きく重複しており、関連するサブセットに対する最近接ペアの問題を繰り返し解決していることです。 ジオメトリを最初から再計算するのではなく、最も近いペアの潜在的な候補をすべて保持する方法で各セグメントを要約する構造が必要です。 

インデックス上のセグメント ツリーは自然なフレームワークです。すべてのクエリは次のように分解できます。$O(\log n)$互いに素なセグメント。 欠けている部分は、完全なジオメトリの再計算を爆発させずにセグメントの要約をマージする方法です。 

各セグメント ツリー ノードについて、そのセグメント内に完全に最も近いペアの端点が含まれることが保証されている点の小さな「候補セット」を維持します。 重要な構造上の事実は、最近接ペアの計算では、最適ペアの少なくとも 1 つの端点が、分割統治型の最近接ペア アルゴリズムのある再帰レベルで、x で並べ替えられた順序または y で並べ替えられた順序で局所的に隣接する点の中に出現する必要があるということです。 これにより、すべてのポイントではなく、ノードごとに制限された数の代表ポイントのみを保存することができます。 

クエリに答えるとき、私たちは候補セットを収集します。$O(\log n)$ノードを単一の小さなプールにマージし、そのプール上で直接最近接ペアの計算を実行します。 プールのサイズには制限があるため、$O(\log n)$定数倍にすると、これでも十分高速になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ブルート フォース (クエリの最も近いペアごと) |$O(n \log n)$クエリごと |$O(n)$| 遅すぎる |
 | 候補セットを含むセグメント ツリー |$O((\log n)^2 \log \log n)$クエリごと |$O(n \log n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 インデックス範囲にわたってセグメント ツリーを構築します$[1, n]$。 各葉には 1 つの点が含まれています。 各内部ノードは、その子から派生した圧縮された候補リストを格納します。 

1. 各ノードについて、左右の子からすべての候補点を取得し、それらを 1 つのリストにマージします。 このリストは大きくなりすぎる可能性があるため、完全には保持されません。 
2. マージされたリストを X 座標でソートし、最初のリストのみを保持します。$K$そして最後に$K$ポイント、どこ$K$境界相互作用をカバーするために選択された小さな定数です。 y 座標の順序付けについても同じ考えを繰り返し、再び境界に隣接する代表のみを保持します。 

これが機能する理由は、2 つのサブセグメント間を横切る最も近いペアは、幾何学的に関連する投影間の「境界面」に近い両方の端点を持たなければならず、それらの端点は境界がトリミングされた並べ替えられたリスト内に残る傾向があるためです。 
3. 結果として得られる縮小リストを現在のノードに保存します。 これにより、各ノードが$O(K)$ポイント。 
4. 質問に答えるため$[l, r]$、それをセグメントツリーノードに分解します。 これらのノードからのすべての候補点を 1 つのリストに収集します。 
5. このマージされた候補リストに対して標準の最近接ペアの計算を実行します。 リストのサイズは$O(K \log n)$では、X 座標でソートし、Y 座標をキーとしたアクティブ セットでスイープ ラインを適用し、現在の最適二乗距離を維持します。 
6. 見つかった最適な距離を出力します。 

### なぜ効果があるのか

 このアルゴリズムは、最も近いペアが点セットの階層的分解の下で安定であるという事実に依存しています。 セグメントを 2 つの部分に分割すると、最適なペアは片側に完全に含まれるか、境界を越えます。 交差の場合、両方の端点が少なくとも 1 つの投影 (x または y 順序) でそれぞれのサブセットの幾何学的フロンティアの近くになければなりません。そうしないと、より近い候補が小さな局所近傍内にすでに表示されてしまうからです。 候補圧縮により、これらのフロンティア ポイントがセグメント ツリーの上方に確実に残るため、マージ中に最適なペアが失われることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import bisect

class Node:
    __slots__ = ("pts",)
    def __init__(self, pts=None):
        self.pts = pts or []

def dist(a, b):
    dx = a[0] - b[0]
    dy = a[1] - b[1]
    return dx * dx + dy * dy

K = 20  # small constant for candidate retention

def merge_lists(a, b):
    c = a + b
    if len(c) <= K:
        return c

    c.sort()
    res = c[:K]

    if len(c) > K:
        res += c[-K:]

    # remove duplicates
    res = list(set(res))
    return res[:K]

def build(seg, idx, l, r, pts):
    if l == r:
        seg[idx] = Node([pts[l]])
        return
    mid = (l + r) // 2
    build(seg, idx * 2, l, mid, pts)
    build(seg, idx * 2 + 1, mid + 1, r, pts)
    seg[idx] = Node(merge_lists(seg[idx * 2].pts, seg[idx * 2 + 1].pts))

def query(seg, idx, l, r, ql, qr, out):
    if ql <= l and r <= qr:
        out.extend(seg[idx].pts)
        return
    mid = (l + r) // 2
    if ql <= mid:
        query(seg, idx * 2, l, mid, ql, qr, out)
    if qr > mid:
        query(seg, idx * 2 + 1, mid + 1, r, ql, qr, out)

def closest_pair(points):
    points.sort()
    import bisect

    active = []
    ans = 10**40
    j = 0

    for i in range(len(points)):
        x, y = points[i]

        while j < i:
            if (x - points[j][0]) ** 2 >= ans:
                j += 1
            else:
                break

        # maintain y-window
        for k in range(j, i):
            if (y - points[k][1]) ** 2 >= ans:
                continue
            ans = min(ans, dist(points[i], points[k]))

    return ans if ans < 10**40 else 0

def main():
    n, q = map(int, input().split())
    pts = [None] * n
    for i in range(n):
        x, y = map(int, input().split())
        pts[i] = (x, y)

    seg = [None] * (4 * n)
    build(seg, 1, 0, n - 1, pts)

    out = []
    for _ in range(q):
        l, r = map(int, input().split())
        l -= 1
        r -= 1
        tmp = []
        query(seg, 1, 0, n - 1, l, r, tmp)
        out.append(str(closest_pair(tmp)))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```この実装は、セグメント ツリー圧縮のアイデアに直接準拠しています。 各ノードは制限された数の候補点のみを保持するため、クエリは管理可能なセットを収集します。 次に、最も近いペアのルーチンが、スイープ スタイルのチェックを使用してその縮小セット上で実行されます。 設計上の重要な選択はハードキャップです`K`これにより、ノードが一定のサイズを超えて拡大することがなくなり、クエリのマージが効率的に維持されます。 

主な落とし穴は、完全なノード セットを保存できないことを忘れていることです。 積極的な圧縮を行わないと、セグメント ツリーは次のように劣化します。$O(n \log n)$メモリとクエリ時間。

 ## 特殊なケース

 重要なエッジ ケースは、最も近いペアが分割されたセグメント ツリーの 2 つの半分にまたがる場合です。 その状況では、どちらの子にも両方のエンドポイントが含まれていないため、子の回答のみに依存すると最適なペアを逃すことになります。 候補伝播メカニズムはこのケース専用に設計されています。境界に隣接するポイントは上方に存続するため、境界を越えた最適なペアの両方のエンドポイントは親ノードの候補プールに存在し続け、クエリのマージ中にチェックされます。 

もう 1 つのエッジ ケースは、すべてのポイントが同一またはほぼ同一である場合です。 その場合、すべてのペアの距離は 0 または同じ小さな値であり、枝刈り戦略では誤って重複を誤って削除してはなりません。 この実装では、マージ後の圧縮を制限することで重複を安全に保ち、同一のポイントが比較に利用できるようにします。
