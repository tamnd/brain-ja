 ## 解決策
 ## 問題の理解

 事実上、ノード 1 をルートとする有向ツリーであるルート構造が与えられます。すべてのノードは、ルートから 1 つの有向パスだけで到達可能であるため、入力ではエッジが任意の方向でリストされる可能性がありますが、基礎となる構造は、一意のルートからノードへのパスを持つツリーのように動作します。 

各有向エッジはスキー場を表します。 すべてのゲレンデには 2 つの重要な属性があります。1 つは合計で滑走できるスキーヤーの数を制限するキャパシティー、もう 1 つはスキーヤー 1 人あたりのコストで、プラス (私たちが支払う)、ゼロ、またはマイナス (私たちが報奨金を獲得する) のいずれかになります。 複数のスキーヤーが同じ斜面を使用する場合、コストはスキーヤーごとに個別に適用されるため、エッジの総コストは、そこを通過するスキーヤーの数に比例して増加します。 

各スキーヤーはノード 1 から開始し、1 とは異なる目的地ノードを選択します。グラフは一意のパスを持つツリーであるため、目的地を選択することは、ルートからノードへのパスを選択することと同じです。 スキーヤーは、エッジを使用せずに早めに停止したり、さらに歩いたりすることもできますが、すべてのノードがすでに固有のパスの自然な終点であるため、それは無関係です。 

目標は 2 つあります。 まず、エッジがその容量を超えて使用されないように、派遣できるスキーヤーの数を最大化する必要があります。 第 2 に、この最大値を達成する有効な目的地にスキーヤーを割り当てるすべての方法の中で、すべてのエッジにわたる合計 (エッジを通過するフローとそのコストを乗じたもの) である総コストを最小限に抑える必要があります。 

これは、各ノードが考えられるシンクを表し、フローの各単位がルートからノードへのパスを選択する 1 人のスキーヤーに対応するツリー フロー問題です。 

この制約では最大 100,000 ノードが許可され、ノードごとのパスやフローの再計算などの二次関数は除外されます。 テスト ケースごとに線形または線形に近い方法 (通常は O(N) または O(N log N) が必要です。 メモリは隣接リストと DP テーブルに十分な大きさです。 

重要なエッジケースはマイナスコストから発生します。 すべてのコストがマイナスで容量が大きい場合、ユニットごとに総コストが削減されるため、最適な戦略はできるだけ多くのフローを押し込むことです。 これは、フローの最大化がコストの最小化と自明に相互作用するわけではないことを意味します。 両方を同時に処理する必要があります。 

もう 1 つの微妙なケースは、一部のエッジの容量がゼロである可能性があることです。 これらのエッジは、下流ノードが存在する場合でも、そのサブツリーを超えるフローを効果的にブロックします。 

最後に、入力の方向がルートからリーフの方向と一致することは保証されません。 構造は根のあるツリーですが、エッジを正しく解釈する必要があります。 

## アプローチ

 強引なアイデアは、各スキーヤーを個別に扱うことです。 スキーヤーを 1 人ずつ割り当て、そのたびに宛先ノードを選択し、そのパス上のすべてのエッジにまだ容量が残っているかどうかを確認できます。 各割り当てはパスに沿って検証して更新するのに最悪の場合 O(N) かかるため、K 人のスキーヤーを派遣すると O(KN) のコストがかかります。 最適解では K は O(N) になる可能性があるため、これは O(N^2) となり、10^5 ノードには遅すぎます。 

問題は個々のスキーヤーに関するものではなく、木上の集合的な流れに関するものであることを観察することで改善できます。 各スキーヤーはルートからノードへのパスに沿って 1 単位のフローを提供するため、ルートから各エッジに容量があるツリーにフローを割り当てます。 これは、実現可能性がサブツリーの要求によって決まる古典的なツリー フロー問題です。 

重要な洞察は、ツリーをボトムアップで処理し、すべての子孫に最適にサービスを提供するために各エッジを通過する必要があるフローの量を決定することです。 各ノードは、フローが終了できる「シンク オプション」を表すことができます。 各ノードがフローの 1 単位を吸収する可能性があると考えると、スキーヤーの数を最大化することは、エッジ容量による制約を受けて、シンクとしてアクティブ化するノードの数を最大化することと同じになります。

最大流量が決定されると、同じ固定流量値に対するコストの最小化が再配分の問題になります。 コストは単位フローごとのエッジごとに線形であるため、各サブツリーに入る合計フローが実現可能性の制約によって固定されることを考慮しながら、より安価なエッジを通じて優先的にフローをプッシュしたいと考えています。 

両方の部分を同時に解決するきれいな方法は、ツリー上での動的プログラミングです。 各ノードについて、容量を考慮しながらサブツリー内に割り当てることができるスキーヤーの最大数を計算し、そのフローを達成するための最小コストも維持します。 これは子に対するナップザックのようなマージになりますが、構造はツリーであり、各エッジは親と子のみを接続するため、マージは、容量制限のある親エッジを介して独立したサブツリー フローを結合することになります。 

この構造により、各サブツリーが単一の「フロー要件」を上向きに寄与し、親エッジがすべてのフローを飽和または通過させることが保証されます。 これは葉から根まで貪欲に蓄積することにつながります。

 ## アルゴリズムのチュートリアル

 ツリーのルートをノード 1 に設定し、接続性によって暗示される一意のパス構造に沿ってルートから離れる方向にすべてのエッジを解釈します。 

事後探索を実行し、ノードごとに、そのサブツリーに割り当てられるスキーヤーの数を計算します。 各ノードは、子からの寄与を集約し、エッジを通って上向きにフローを親に渡そうとします。 

1. ツリーの隣接リストを作成し、各有向エッジの容量とコストを保存します。 
2. ノード 1 でツリーをルートし、DFS を使用して親子構造を計算します。 
3. 各ノードに対して値を定義します。`dp[u]`をルートとするサブツリー内で完全に割り当てることができるスキーヤーの最大数を表します。`u`エッジ容量を超えることはありません。 
4. の子をたどる`u`。 それぞれの子どもたち`v`流量値を生成します`dp[v]`これは、多くのスキーヤーがそのサブツリーから出発し、エッジ (u, v) を通過する必要があることを意味します。 
5. 容量のあるエッジ (u, v) の場合`S`、貢献度は`min(dp[v], S)`。 容量を超える過剰なフローは上向きにル​​ーティングできないため、廃棄されます。 
6. 容量上限を適用した後、すべての子からの合計フローを累積します。 この合計は`dp[u]`。 
7. dp を計算している間、コストの累積を維持します。 各子エッジについて、次の場合、`x = min(dp[v], S)`を追加します。`x * C`そのエッジを通過する各ユニットがコスト C を支払うためです。 
8. 最大限のスキーヤーの答えは次のとおりです。`dp[1]`、ルートの子エッジに到達できる合計フロー。 
9. 合計最小コストは、DP 計算中の累積コストです。 

重要な点は、接続エッジの容量制約を除いて各サブツリーが独立しているため、ローカルな決定によってグローバルな実現可能性が完全に決定されることです。 

### なぜ効果があるのか

 流れの各単位は、正確に 1 人のスキーヤーと、正確に 1 つの根からシンクまでの経路に対応します。 グラフはツリーであるため、これらのパスは、構造ではなく、カウント能力の点でのみエッジ素です。 DP は、各エッジでの寄与を明示的にクランプすることで、エッジがその容量を超えるフローを伝送しないようにします。 すべてのサブツリーは独立して処理され、単一の親エッジを介してのみ対話するため、貪欲なクランプが最適です。代替パスがないため、コストを削減したりフローを増加したりできる代替ルーティングはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    T = int(input())
    for tc in range(1, T + 1):
        n = int(input())
        g = [[] for _ in range(n + 1)]
        
        for _ in range(n - 1):
            u, v, s, c = map(int, input().split())
            g[u].append((v, s, c))
            g[v].append((u, s, c))
        
        visited = [False] * (n + 1)
        dp = [0] * (n + 1)
        cost = 0

        def dfs(u):
            nonlocal cost
            visited[u] = True
            total = 0
            for v, s, c in g[u]:
                if visited[v]:
                    continue
                child_flow = dfs(v)
                used = child_flow if child_flow < s else s
                total += used
                cost += used * c
            dp[u] = total
            return dp[u]

        ans_flow = dfs(1)
        print(f"Case #{tc}: {ans_flow} {cost}")

solve()
```実装は直接ポストオーダー DFS に従います。 各ノードは子からのフローを集約し、各エッジはクランプを介してその容量を強制します。 グローバル コストは、子がフローを返すときに各エッジの寄与が 1 回だけ決定されるため、トラバース中に累積されます。 

微妙な点は、親ポインターを渡すのではなく、訪問したノードをマークすることに依存しているため、明示的にエッジを反転することが回避されます。 もう 1 つの重要な詳細は再帰の深さです。N により最大 100,000 まで増やす必要があります。 

## 実用的な例

 ノード 1 が複数の分岐を持つ小さなツリーに接続する最初のサンプルを考えてみましょう。 DFS は最初にリーフを処理するため、各リーフは 1 人のスキーヤーを上向きに送り出すことができた場合、1 に等しい dp を返します。 

| ノード | 子の流れ | エッジキャップを適用 | dp[ノード] |
 | --- | --- | --- | --- |
 | リーフノード | 0 または 1 | なし | 1 |
 | 内部ノード | 子の合計 | 最小容量 | 集約された |

 ルートでは、キャパシティ フィルタリング後にすべての実行可能なフローが合計され、最終的なスキーヤーの数が生成されます。 コストはフローとエッジ コストの積として各エッジで累積され、高価なエッジが必要最小限のフローを確実に伝送できるようにします。 

2 番目のサンプルでは、​​一部のエッジのコストが負になっています。 DFS は引き続き容量によってフローをクランプしますが、コストは単位フローごとに累積されるため、飽和した場合にはマイナスコスト エッジによって総コストが効果的に削減されます。 これにより、フローを最大化すると、可能な限りマイナスコストのエッジを自動的に最大限に活用できることが確認されます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、ノードに複数の子があるが、1 つの接続エッジの容量がゼロである場合です。 その場合、DFS はその子サブツリーの dp を返しますが、`min(dp, 0)`がゼロになるため、フローは上方に通過せず、サブツリーが正しく分離されます。 

もう 1 つのケースは、すべてのエッジのコストがマイナスで、容量が大きい場合です。 dp は実現可能な最大のフローを集計し、コストの累積により報酬が正しく減算されるため、アルゴリズムは依然としてすべての可能なフローを上方に渡します。 

最後のケースは、根が多くの葉につながっている星形の木です。 各リーフは独立して寄与し、dp[1] は出力エッジのすべての容量の合計となり、各エッジが独立してフローを制限するという直観と一致します。
