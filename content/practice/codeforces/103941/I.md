 ## 解決策
 ## 問題の理解

 建物を表す 3 次元グリッドが与えられます。 このグリッド内のすべての点は、座標によって識別される部屋です。$(x, y, z)$。 この建物内の移動は徒歩ではなく、専用の循環エレベーターを利用して行われます。 

エレベーターには正確に 3 種類あり、それぞれが 1 つの軸に制限されています。 零式エレベーターが移動します。$x$-軸に沿って 1 を入力します。$y$-軸に沿って 2 と入力します。$z$-軸。 各エレベーターは有向サイクルのように動作します。つまり、軸に沿って前進し、最大座標から最小座標に戻り、無限に継続します。 サイクルに沿って隣接する部屋間の移動にはすべて 1 秒かかり、乗客は整数秒でのみ出入りできます。 

各部屋には、各タイプのエレベーターが 1 台ずつアクセス可能です。 各エレベーターは、その軸に沿ったすべての部屋で共有されるグローバルなエンティティです。 さらに、各エレベーターには時間 0 の初期位置があります。 

乗客は指定された時間に到着し、出発の部屋から目的の部屋まで移動する必要があります。 それらのパスは固定された順序に制約されます。まず、$x$-座標、次に$y$-座標、次に$z$-座標。 各フェーズは、対応するエレベーター タイプによって排他的に処理され、座標がすでに一致する場合、そのフェーズはスキップされます。 

重要な問題は、任意の動きをシミュレートしていないことです。 代わりに、厳格なスケジュール ルールに基づいて、すべての乗客の「エレベーターに入る」および「エレベーターを出る」アクションのすべての完全なイベント ログを再構築する必要があります。 乗客は ID 順に列を作り、エレベーターは固定されたタイミングで周期的に動きます。複数のエレベーターが関係する場合、インデックスの低いエレベーターが同時にイベントをより早く処理します。 

出力は、時間、乗客 ID、エレベーター ID、アクション (IN または OUT)、およびそれが発生した部屋を含む、すべての乗客の移動の時系列ログです。 

制約は非常に小さいです。$n, m, h \le 8$、乗客は最大でも50人です。 これにより、慎重なシミュレーションを超えた重いデータ構造や最適化の必要性が即座に排除されます。 問題は漸近効率に関するものではなく、順序付けルールを使用して同期された離散イベントを正しくモデル化することにあります。 

いくつかの微妙な状況によって、単純なシミュレーションが簡単に崩れてしまうことがあります。 

問題の 1 つは、エレベーターの動きが周期的で決定論的であるにもかかわらず、乗客が任意の時間に到着する可能性があることです。 エレベーターの位相調整を無視して移動時間を計算すると、誤って即時にアクセスできると想定してしまう可能性があります。 たとえば、乗客が移動する必要がある場合$y$, ただし、エレベーターは現在そのサイクルにかなり進んでおり、エレベーターが部屋に到着するまでに数秒待つ必要がある可能性があります。 

もう 1 つの微妙な問題は注文です。 2 人の乗客が同時に部屋に到着した場合、乗客 ID の順序によって退室と入室の両方の順序が決まり、エレベーターのインデックスによってさらに同点が解消されます。 順序付けを厳密に強制しない単純なタイムステップ シミュレーションでは、距離が正しい場合でも、不正確なログが生成されます。 

最後に、「降車後次の秒まで再入場できない」ルールにより、セグメント間に必須の遅延が導入されます。これは、各乗客の動きが区分的でありながらもグローバルに同期されていることを意味します。 

## アプローチ

 強引なアイデアは、時間を秒ごとにシミュレートすることです。 毎秒ごとに、すべてのエレベーターをそのサイクルに沿って 1 ステップ前進させてから、すべての乗客を処理します。つまり、誰がターゲットの部屋に到着し、誰が退室し、誰が入場するかを決定します。 これは実際のプロセスを反映しているため、概念的には単純で正しいものです。 

ただし、対象期間が長くなる可能性があるため、このアプローチは失敗します。 乗客はエレベーターの整列を待つ場合があり、実際のイベントの数は少ないにもかかわらず、システムは最大数千秒間のアイドル待機をシミュレートする必要がある場合があります。 さらに重要なことは、単純な秒ごとのシミュレーションでは、複数のエレベーターと複数の乗客にわたって一貫した順序を維持する必要があるため、イベントのスケジュールが複雑になります。 

重要な観察は、実際にはアイドル時間を継続的にシミュレートする必要がないということです。 すべての乗客の動きは、次に使用可能なエレベーターの位置に到達するための決定的な「追いつき時間」によって決まります。 グリッド サイズが小さく、動きが周期的であるため、任意の開始時間と位置について、特定のタイプのエレベーターがその部屋に到着する最も早い時間を計算できます。 

これにより、問題は各乗客経路の各セグメントの離散イベント時間を計算することに変わります。 各セグメントは「整列まで待機 + 移動 + 即時転送」の操作となり、それらのイベント ポイントのみをシミュレートできます。 

当社は時間順に並べられたグローバル イベント リストを維持し、各時間内で、低いエレベーター インデックスが高いものよりも前に処理されるというルールを適用し、各エレベーター内で到着 (IN) よりも前に出発 (OUT) が発生し、乗客 ID が順序付けされます。 

これにより、継続的なシミュレーションからイベントのスケジューリングまでの問題が軽減されます。

 ## アルゴリズムのチュートリアル

 すべての乗客を、軸ごとに 1 つずつ、最大 3 つの独立したセグメントを順番に実行するものとして扱います。$x \rightarrow y \rightarrow z$。 各セグメントは、座標が異なる場合にのみ実行されます。 

時間によってソートされたイベントの優先キューを維持し、すべての「エレベーターに入る」アクションと「エレベーターを出る」アクションをイベントとしてエンコードすることによって、システムをシミュレートします。 

1. 各乗客の現在位置を開始部屋として初期化し、現在時刻を到着時刻として初期化します。 現在の座標が次に必要な座標とすでに一致している場合は、次のセグメントに直接スキップします。 
2. 軸に沿った必要なセグメントの場合$d$、適切なエレベーターが最初に使用できる時期を計算します。 各エレベータは軸長に等しい周期で周期的に移動します。 現在の部屋から、次回のエレベーターのタイプを決定します$d$その部屋に到達するか、使用可能になります。 これにより、可能な限り早い搭乗時間が得られます。 
3. 搭乗時間が決まりましたら、その時間にINイベントを予定します。 乗客はすぐにその部屋にあるエレベーターに乗ります。 
4. 現在の座標からターゲット座標までの軸に沿った移動距離を循環順序で計算します。 これにより、エレベーターがこのセグメントの目的の部屋に何秒後に到着するかが決まります。 
5. 搭乗時間に移動時間を加えた時刻に OUT イベントをスケジュールします。 
6. OUT イベント後、乗客の位置と時刻を更新します。 また、終了後少なくとも 1 秒までは次のセグメントを開始できないというルールも適用します。 
7. すべての乗客がすべてのセグメントを終了するまで繰り返します。 
8. すべてのイベントが保存され、最終的に時間順に並べ替えられます。 時間が同点の場合は、小さいエレベーター インデックスが最初、その中では IN の前に OUT、その中で小さい乗客 ID が最初という順序でイベントが出力されます。 

正確さは、各セグメントを、決定論的な周期運動から導出された、明確に定義された開始時間と終了時間を持つ原子間隔として扱うかどうかにかかっています。 エレベーターの周期構造により、どの部屋でも位置合わせまでの待ち時間がサイクル長を法として明確に定義されるため、すべてのセグメントをシミュレーションではなくモジュール距離の算術演算に減らすことができます。 

不変条件は、キュー内のすべてのイベントがシステム内で一意に決定された実際の物理的な遷移を表し、中間のアイドル秒数に依存するイベントがないことです。 すべてのインタラクションは整数倍で、部屋の境界でのみ発生するため、モーションをセグメントの端点に折りたたむと正確さが保たれます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def mod_dist(a, b, n):
    if b >= a:
        return b - a
    return n - (a - b)

def wait_time(cur_pos, start_pos, size):
    # time until cyclic elevator starting from start_pos reaches cur_pos
    if cur_pos >= start_pos:
        return cur_pos - start_pos
    return size - (start_pos - cur_pos)

def solve():
    n, m, h = map(int, input().split())
    k = int(input())
    
    elevators = [[] for _ in range(3)]
    for i in range(k):
        t, x, y, z = map(int, input().split())
        elevators[t].append((i + 1, x, y, z))

    q = int(input())
    passengers = []
    for i in range(q):
        pti, fx, fy, fz, tx, ty, tz = map(int, input().split())
        passengers.append([pti, fx, fy, fz, tx, ty, tz, i + 1])

    events = []

    def add_event(t, pid, eid, x, y, z, typ):
        events.append((t, eid, typ, pid, x, y, z))

    for pti, fx, fy, fz, tx, ty, tz, pid in passengers:
        cur_t = pti
        cx, cy, cz = fx, fy, fz

        def process_axis(axis, target, size):
            nonlocal cur_t, cx, cy, cz, pid
            if axis == 0:
                if cx == target:
                    return
                start = cx
                dist = wait_time(cx, start, size)
                t_in = cur_t + dist
                add_event(t_in, 1, pid, cx, cy, cz, "IN")
                t_out = t_in + mod_dist(cx, target, size)
                add_event(t_out, 1, pid, target, cy, cz, "OUT")
                cur_t = t_out + 1
                cx = target
            elif axis == 1:
                if cy == target:
                    return
                start = cy
                dist = wait_time(cy, start, size)
                t_in = cur_t + dist
                add_event(t_in, 2, pid, cx, cy, cz, "IN")
                t_out = t_in + mod_dist(cy, target, size)
                add_event(t_out, 2, pid, cx, target, cz, "OUT")
                cur_t = t_out + 1
                cy = target
            else:
                if cz == target:
                    return
                start = cz
                dist = wait_time(cz, start, size)
                t_in = cur_t + dist
                add_event(t_in, 3, pid, cx, cy, cz, "IN")
                t_out = t_in + mod_dist(cz, target, size)
                add_event(t_out, 3, pid, cx, cy, target)
                cur_t = t_out + 1
                cz = target

        process_axis(0, tx, n)
        process_axis(1, ty, m)
        process_axis(2, tz, h)

    def typ_order(t):
        return 0 if t == "OUT" else 1

    events.sort(key=lambda e: (e[0], e[1], typ_order(e[2]), e[3]))

    for t, eid, typ, pid, x, y, z in events:
        print(f"[{t}s] Person {pid} {typ} Elevator {eid} at ({x}, {y}, {z})")

if __name__ == "__main__":
    solve()
```この実装では、各乗客の移動を 3 つの軸セグメントとしてエンコードします。 セグメントごとに、循環エレベーターが現在の部屋と一致するまでの待ち時間を計算し、その軸に沿ったモジュラー距離として移動時間を計算します。 中間の動きをシミュレートするのではなく、IN イベントと OUT イベントの両方をすぐに追加します。 

仕分けのステップは非常に重要です。 2 つのイベントが同じ秒に発生した場合でも、エレベーター インデックスは同点を解消する必要があり、同じタイムスタンプで到着する前に出発が処理されるように、その中で OUT が IN の前に来る必要があります。 乗客 ID が最後の勝負を分けます。 

アップデート`cur_t = t_out + 1`セグメント間に必須の 1 秒のギャップを強制します。 

## 実用的な例

 1 人の乗客が移動する単純化された 2×2×2 のケースを考えてみましょう。$(1,1,1)$に$(2,1,1)$。 

| ステップ | 現在時刻 | ポジション | アクション |
 | --- | --- | --- | --- |
 | 開始 | 1 | (1,1,1) | 到着 |
 | エックスイン | 1 | (1,1,1) | X エレベーターに入ります |
 | エックスアウト | 2 | (2,1,1) | Xエレベーターを出る |

 これにより、単一軸の移動が 1 つの整列されたサイクル移動になることが確認されます。 

ここで、次の 2 軸の動きを考えます。$(1,1,1)$に$(2,2,1)$。 

| ステップ | 時間 | ポジション | イベント |
 | --- | --- | --- | --- |
 | 1 | 1 | (1,1,1) | IN Xエレベーター |
 | 2 | 2 | (2,1,1) | OUT Xエレベーター |
 | 3 | 3 | (2,1,1) | IN yエレベーター |
 | 4 | 4 | (2,2,1) | OUT Yエレベーター |

 これは、セグメント間で強制された 1 秒待機ルールと、座標更新がどのようにきれいにカスケードされるかを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、乗客が軸のターゲット座標から正確にスタートする場合です。 このような状況では、そのセグメントに対してエレベーター イベントが生成されるべきではなく、時間が誤って進んではいけません。 実装では、座標がすでに一致している場合に早期に返すことでこれを処理します。 

もう 1 つのエッジ ケースは、異なる乗客が同時に部屋に到着する場合です。 並べ替えはイベント全体にわたってグローバルに行われるため、IN イベントと OUT イベントは両方とも時間順、エレベーター インデックス順、OUT 前 IN 順、乗客 ID 順に並べられます。 これにより、複数のインタラクションが同時に発生した場合でも、決定的な順序付けが保証されます。 

最後の微妙なケースは、ターゲット座標が現在の座標より小さいラップアラウンド移動です。 モジュラー距離の計算により、エレベーターが負の移動または長さゼロの移動を誤って想定するのではなく、周期的に継続することが保証されます。
