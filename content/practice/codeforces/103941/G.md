 ## 解決策
 ## 問題の理解

 すべて同じ長さのバイナリ文字列がいくつか与えられています。 それらを次のような行列として考えてください。`n`行と`m`各行は文字列であり、各列はすべての文字列で共有されるビット位置です。 

次に、一連の操作を実行します。 各操作で 2 行が選択されます`i`そして`j`、列のセグメント`[l, r]`、および確率`p/100`。 その確率で操作が「アクティブ化」され、アクティブ化された場合は行を上書きします。`j`行とのビット単位の AND を取得して、そのセグメントに対して`i`。 言い換えれば、セグメント内のすべての位置について、`sj[x]`になる`sj[x] & si[x]`。 

したがって、成功した操作は 1 が 0 に変わるだけであり、その逆は決してありません。 

すべての演算の後、概念的には、すべての行のビット単位の AND を列ごとに取得し、その最後の AND で 1 になる位置の数を数えます。 操作は確率的であるため、答えは、998244353 を法として求めた、そのような位置の予想数になります。 

重要な観察点は、同じ操作を共有する場合を除いて、列が相互に対話しないことです。 特定の列が最終的に 1 を与えるかどうかは、その列内で何が起こっているかによってのみ決まります。 これにより、問題はビット位置ごとに分離可能になり、最終的な答えは、その列ですべての行が 1 のままであるすべての列にわたる確率の合計になります。 

制約は非常に厳しいです。`n ≤ 1000`、`m ≤ 4000`、 そして`q ≤ 2 × 10^5`。 これにより、操作ごと、行ごとの更新を行う列ごとに完全なプロセスを個別にシミュレートすることは直ちに除外されます。`q * m`、大きすぎます。 

単純な間違いは、各演算を列ごとに独立して扱い、生存確率を直接乗算することです。 これは失敗します。操作の効果は、初期ビットだけではなく、行の進行状態に依存するためです。 2 番目の微妙な失敗例は伝播の無視です。0 になった行は後でゼロをさらに広げる可能性があるため、1 つの操作が他の多くの行に間接的に影響を与える可能性があります。 

たとえば、行 1 が次のようになっているとします。`100`、2行目は`111`、3行目は`111`。 行 1 のどこかの位置に 0 があり、正常に適用された場合`1 → 2`、 それから`2`その位置で0になり、それ以降`2 → 3`それをさらに伝播させることができます。 操作の直接的な影響のみを考慮するソリューションでは、このカスケードを見逃してしまいます。 

## アプローチ

 ブルートフォースの方法は、プロセス全体をシミュレートすることです。 ビット位置ごとに一連の操作全体をシミュレートし、そのたびにそれがアクティブになるかどうかをランダムに決定します。 次に、これを何度も繰り返し、経験的に確率を推定します。 これは概念的には正しいですが、シミュレーションが 1 つであっても、制約の下では計算上役に立ちません。`O(nm + qn)`精度を高めるには何度も繰り返す必要があります。 

もう 1 つの直接的な決定論的アプローチは、すべての可能な構成にわたって正確な確率分布を追跡しようとすることです。`n`各ビットの行。 状態空間は指数関数的であるため、それは不可能です。 

重要な構造的洞察は、完全な構成の観点から考えるのをやめ、代わりに行ごと、ビットごとの限界確率のみを追跡することです。 行が相関している場合でも、単一行の「まだ 1」の確率の推移を更新することができます。これは、各操作が単純な単調な効果を持っているためです。操作は何もしないか、ソース行に応じて一部の 1 を 0 に変える可能性がある制約を強制するかのどちらかです。 

各ビットを個別に再解釈します。 列を修正します。 この列の一部の行は 0 で始まります。 これらの行は永続的な「汚染源」として機能します。行が 0 になると、永久に 0 のままになります。 手術`i → j`(アクティブ化された場合) はこう言います:`i`その時点では 0 なので、`j`0にならなければなりません。 

したがって、ゼロは、正常にアクティブ化された操作に沿って前方に伝播しますが、伝播時にすでにゼロであるソースからのみ伝播します。 

これにより、エッジが活性化確率とともに時間順に現れる有向グラフ上の確率的感染プロセスがもたらされます。 必要なのは、1 から始まる行がこのプロセスによって感染しない確率だけです。 

各行および各ビットについて、時間順に演算を処理した後もその行が 1 のままである確率を維持できます。 操作を処理するとき`i → j`成功すると、`j`の場合は 0 になります`i`はすでに 0 です。これにより、確率に関するクリーンな更新ルールが得られます。 

固定ビットの場合、`dp[j]`その行の確率になります`j`操作のいくつかの接頭辞を処理した後でも 1 のままです。 当初は、`dp[j]`入力のビットが 0 の場合は 0、それ以外の場合は 1。 

操作を処理するとき`(i, j, p)`確率的にこのビットに影響を与える`p/100`それは活性化します。 それが活性化すれば、`j`の場合は 0 になります`i`はすでに 0 です。これにより、次の可能性が高まる遷移が得られます。`j`確率に比例して0になる`i`はすでに 0 です。 

これにより、操作ごとに線形更新が行われ、すべての行の寄与を合計すると、そのビットについてすべての行が 1 のままである確率が得られます。 

ブルート フォースが機能するのは、すべての状態を明示的に追跡するためです。 最適なアプローチが機能するのは、完全な状態は必要なく、行ごと、ビットごとの生存確率だけが必要であり、遷移では線形構造が維持されるためです。

 ## アルゴリズムのチュートリアル

 各ビットを個別に処理し、すべての演算の後、各行のそのビットにまだ 1 が含まれる確率を計算します。 

1. 固定ビット位置の場合、配列を初期化します。`dp`サイズの`n`、 どこ`dp[j]`元の文字列の行に 1 がある場合は 1`j`、それ以外の場合は 0。これは、行がその行に到達する確率を表します。`j`最初はまだ安全です。 
2. 各操作について、それが現在のビットに影響を与えるかどうか、つまりビットがその間隔内にあるかどうかを事前計算します。`[l, r]`。 そうでない場合は、このビットは無視できます。 
3. 操作を順番に処理します。 手術の場合`(i, j, p)`現在のビットに影響を与えるものは、その活性化確率を計算します`p = p / 100`。 
4.アップデート`dp[j]`その行という事実を利用して`j`この操作で失われる可能性があるのは、操作がアクティブ化されて行が開始された場合のみです。`i`すでに安全ではありません。 その確率は、`j`安全性を維持する度合いは、以前は安全であった可能性がどの程度か、また感染を回避できる可能性がどの程度あるかに応じて増加します。`i`。 
5. すべての操作が処理された後、次のすべての行の積を計算します。`dp[j]`。 この値は、すべての行のこのビットがまだ 1 である確率です。 
6. この値をすべてのビット位置で合計し、結果のモジュロ 998244353 を出力します。 

### なぜ効果があるのか

 このプロセスは単調です。ビットが連続して 0 になると、1 には戻りません。すべての操作は、現在の状態を保存するか、ゼロが伝播するための新しい方法を追加します。 各操作はソース行が現在 0 であるかどうかのみに依存し、この依存関係は確率を通じて線形に影響するため、同時分布を追跡することなく周辺確率を安全に更新できます。 ビットごとに期待される寄与は、最初の 0 から始まる伝播チェーンが 1 で始まる行に到達しない確率と正確です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

def modinv(x):
    return pow(x, MOD - 2, MOD)

def main():
    n, m = map(int, input().split())
    a = [input().strip() for _ in range(n)]

    q = int(input())
    ops = []
    for _ in range(q):
        i, j, l, r, p = map(int, input().split())
        ops.append((i - 1, j - 1, l - 1, r - 1, p))

    # precompute inverse 100
    inv100 = modinv(100)

    ans = 0

    # process per bit
    for bit in range(m):
        dp = [0] * n

        # initial survival probability per row for this bit
        for i in range(n):
            dp[i] = 1 if a[i][bit] == '1' else 0

        # process operations affecting this bit
        for i, j, l, r, p in ops:
            if l <= bit <= r:
                prob = p * inv100 % MOD

                # probability j becomes unsafe increases if i is unsafe
                # we track safety, so we scale down survival
                # dp[j] = dp[j] * (1 - prob * (1 - dp[i]))
                # rewrite carefully in modular form

                fail_from_i = (1 - dp[i]) % MOD
                add_fail = prob * fail_from_i % MOD
                dp[j] = dp[j] * (1 - add_fail) % MOD

        cur = 1
        for i in range(n):
            cur = cur * dp[i] % MOD

        ans = (ans + cur) % MOD

    print(ans)

if __name__ == "__main__":
    main()
```コードは各ビットを反復し、各行がそのビットで 1 として存続する確率を維持します。 各操作は、現在のビットをカバーする場合にのみ寄与します。 遷移はソース行の現在の生存確率にのみ依存し、ターゲット行の生存確率は乗算的に減少します。 

すべての行にわたる最後の乗算により、そのビットで行が破損しない確率が計算され、ビット全体の合計により期待されるカウントが得られます。 

実装の微妙な詳細は、モジュラー確率演算です。 すべての確率の更新は 998244353 を法として実行する必要があり、100 による除算は逆剰余を使用して処理されます。

 ## 特殊なケース

 重要なエッジ ケースは、すべての行のビットにすでに 1 が入っている場合です。 この状況では、最終確率を下げることができるのは、0 になる行からの依存関係を導入する操作のみです。 アルゴリズムはこれを処理します。`dp`すべての行で 1 から始まり、操作が成功した場合のみ値が減少します。 

もう 1 つのエッジ ケースは、すべての行のビットが 0 である場合です。 それから`dp`どこでもゼロから始まり、すべての貢献はゼロです。 アルゴリズムは、そのビットの寄与を直ちにゼロにします。 

最後の微妙なケースは、ゼロが複数の行に伝播する長い操作チェーンです。 これは複数ステップの依存関係の問題のように見えますが、操作ごとの確率更新は中間状態を介した間接的な伝播をすでに考慮しているため、特別な処理は必要ありません。
