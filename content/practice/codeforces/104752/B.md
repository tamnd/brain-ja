 ## 解決策
 ## 問題の理解

 バイナリ文字列を構築しようとしていますが、その構造を無制限に自由に選択することはできません。 0 と 1 が与えられ、同じ文字の連続には長さが制限されているとも言われます。 有効な文字列は、使用可能な 0 または 1 の数を超えてはならず、また、連続するブロック内に連続する 0 や 1 が多すぎることも避けなければなりません。 

タスクは、明示的な文字列を構築することではなく、これらの制約の下で形成できる有効なバイナリ文字列の最大長を決定することです。 

入力により 4 つの値が得られます。 最初の 2 つは、使用できるゼロと 1 の数の予算です。 最後の 2 つの制限ラン長: 連続する 0 のブロックはゼロラン制限を超えることはできず、連続する 1 のブロックは 1 ラン制限を超えることはできません。 

構造について考えると、有効な文字列は 0 と 1 の交互のブロックで構成されると考えると便利です。 各ブロックには最大サイズがあり、合計の長さは、0 または 1 がなくなる前に適合することができたすべてのブロックの合計にすぎません。 

制約はパラメータごとに最大 100 万までと十分に大きいため、考えられるすべての文字列に対するシミュレーションやアレンジメントに対する貪欲なバックトラックが排除されます。 二次関数や指数関数は即座に不可能になります。 構造は少数の意味のある構成に縮小されるため、すべての可能な分割にわたる線形スキャンさえも不要です。 

いくつかの特殊なケースが重要です。 

どちらかのラン制限がゼロの場合、そのキャラクターはまったく出現できません。 たとえば、M0 がゼロであるが C0 が正の場合、単一のゼロでも制約に違反するため、どこにもゼロを配置することはできません。 その場合、M1 の対象となるのは 1 つだけです。 

M0 と M1 の両方がゼロの場合、ゼロより長い文字列は存在できません。 

もう 1 つの微妙なケースは、一方の文字が豊富に存在するが、もう一方の文字が非常に制限されている場合に発生します。 たとえば、C0 = 1000、C1 = 1、M0 = 10、M1 = 1 です。最良の配置は、単に「すべてのゼロを最初に使用する」というものではありません。これは、実行によって交互が強制され、単一のゼロを中心にゼロをグループ化する方法が制限されるためです。 

単純な間違いは、ブロックごとに min(C0, M0) 個のゼロと、ブロックごとに min(C1, M1) 個の 1 を独立して取得し、任意の数のブロックを合計できると想定していることです。 これは、ブロックが交互に配置される必要があること、およびブロックの数が最初になくなった文字によって制限されることを無視しています。 

## アプローチ

 ブルート フォース アプローチでは、現在の実行長と残りのクォータを追跡しながら、各ステップで 0 を追加するか 1 を追加するかを決定して、再帰的または反復的な構築によって最長の有効なバイナリ文字列を構築しようとします。 これは制約を直接尊重するため概念的には機能しますが、巨大な状態空間を探索します。 各ポジションは最大 2 つの選択肢に分岐し、最悪の場合は指数関数的な増加につながります。 メモ化を行ったとしても、状態には残りのカウントと現在のランレングスが含まれますが、それでも最大 O(C0 * C1 * M0 * M1) という非常に大きな DP スペースが発生し、制限には大きすぎます。 

重要な観察点は、最適なストリングは可能な限り常にフル実行容量を使用するということです。 ブロック内では、実行中に未使用の容量を残すことは文字列を短くするだけであるため、早期に停止する理由はありません。 したがって、すべてのブロックは M0 ゼロの長さ、またはゼロがなくなるまでのいずれかであり、1 の場合も同様です。 

したがって、構造は交互のセグメントに崩壊します。サイズが最大 M0 のゼロのブロック、次にサイズが最大 M1 のブロック、またはその逆を繰り返し配置します。 残りの唯一の決定は、どの文字で開始するかです。開始文字は、1 つのリソースが使い果たされる前にどれだけの完全なブロックを収めることができるかに影響するためです。

したがって、両方の開始選択肢に対して可能な限り最適な長さを計算し、最大値を採用します。 各シミュレーションのブロック数は線形ですが、各ステップは少なくとも 1 つの完全なブロック容量を消費するため、ステップ数は O((C0 / M0) + (C1 / M1)) によって制限されます。これは入力サイズに比べて小さいです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(C0 + C1) 再帰 | 遅すぎる |
 | 最適 | お(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ゼロのブロックから始めるか、1 のブロックから始めるという 2 つの可能な構造をテストして、答えを計算します。 

1. 固定された開始文字の選択の下で貪欲に文字列を構築することをシミュレートするヘルパー関数を定義します。 この関数は、残りの 0、残りの 1、およびブロックを配置する順番を示すフラグを維持します。 この構造は、有効な文字列が交互に実行されるという事実を捉えています。 
2. ゼロの番になったら、残りのゼロと M0 の間に最小値に等しいサイズのブロックを配置します。 その金額をゼロ予算から差し引きます。 これが最適なのは、配置を短くしても全長が短くなるだけで、後のステップの実現可能性が向上しないためです。 
3. 自分の番になったら、同様にサイズ min(残り M1) のブロックを配置し、それを引きます。 これにより、すべてのブロックが制約の下で最大限に埋められるようになります。 
4. どちらのキャラクターもそれ以上貢献できなくなるまで交互にターンします。 残りのカウントが両方とも 0 になるか、文字が使い果たされて必要なタイプの有効なブロックを 1 つも形成できない場合、プロセスは停止します。 
5. 0 から始まる合計の長さと 1 から始まる合計の長さを別々に計算し、最大値を取得します。 

重要な点は、1 つの文字が単一の有効なブロックを形成することさえできない場合の処理​​です。 M0 がゼロで、ゼロのブロックを配置することになっている場合、その分岐はすぐに無効になります。 これは、その構成からゼロ寄与を返すことによって処理されます。 

### なぜ効果があるのか

 有効な構造のどの時点でも、特定の文字のブロックを配置する場合、最大許容ラン サイズ未満のものを使用することは、将来の実現可能性を助けず、厳密に全体の長さを短縮するため、最適とは言えません。 各実行後に文字を切り替えることが必須であるため、唯一意味のある構造は最大実行のシーケンスだけです。 したがって、すべての最適解は、いずれかの文字から始まる 2 つの交互の最大ラン パターンの 1 つに対応し、その中で最も優れたものが全体的に最適になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build(c0, c1, m0, m1, start_zero):
    z, o = c0, c1
    total = 0
    turn_zero = start_zero

    while True:
        if turn_zero:
            if z == 0:
                break
            if m0 == 0:
                break
            take = min(z, m0)
            if take == 0:
                break
            z -= take
            total += take
        else:
            if o == 0:
                break
            if m1 == 0:
                break
            take = min(o, m1)
            if take == 0:
                break
            o -= take
            total += take
        turn_zero = not turn_zero

    return total

def solve():
    c0, c1, m0, m1 = map(int, input().split())

    ans1 = build(c0, c1, m0, m1, True)
    ans2 = build(c0, c1, m0, m1, False)

    print(max(ans1, ans2))

if __name__ == "__main__":
    solve()
```機能`build`貪欲な交互構造をシミュレートします。 現在の実行で許可されている限り多くのシンボルを常に消費し、制限を超える実行がないようにします。 キャラクタの枯渇またはゼロラン制限のいずれかにより、必要なブロックを形成できない場合、シミュレーションは停止します。 

最初の文字によってリソースがブロックに分割される方法が決まるため、両方の開始構成を明示的に試します。 最終的な答えは 2 つの最大値です。 

この実装では、キャラクターごとのシミュレーションが回避されます。 各反復ではブロック全体が削除され、定数時間の収束が保証されます。 

## 実用的な例

```両方のスタートをシミュレーションします。

トレースは、制限のバランスが取れている場合、最適な戦略では両方のリソースが使い果たされるまでフル ブロックを交互に使用することを示しています。

10 1 1 1
```ゼロから始める:

 | --- | --- | --- | --- | --- |
 | 1 | 0 | (10,1) | 1 | 1 |

 | 3 | 0 | (9,0) | 0 (ブロック) | 停止 |

 合計は 2 です。

 | ステップ | ターン | 残り (0,1) | テイク | 合計 |

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | お(1) | 各シミュレーションはブロック全体を消費します。 ステップ数は min(C0/M0, C1/M1) によって制限されます。これは制約に対して一定です |
 | スペース | お(1) | 少数のカウンターのみが維持されます。 

計算はテスト ケースごとに一定時間で行われ、個々の文字を処理しないため、大規模な入力であっても制限内に簡単に収まります。 

## テストケース```python

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    def build(c0, c1, m0, m1, start_zero):
        z, o = c0, c1
        total = 0
        turn_zero = start_zero

        while True:
            if turn_zero:
                if z == 0 or m0 == 0:
                    break

                z -= take

                o -= take

            turn_zero = not turn_zero

    c0, c1, m0, m1 = map(int, sys.stdin.readline().split())

 ## 特殊なケース

 エッジ ケースの 1 つは、実行制限がゼロの場合です。 たとえば、入力`5 5 0 3`ゼロはまったく出現できないことを意味します。 アルゴリズムのゼロスタート シミュレーションは、最初のゼロ ターンですぐに失敗します。`m0 == 0`, そのため、そのブランチからの寄与はゼロになります。 ワンスタートブランチは正しく生成します`min(5,3) + 0 = 3`。 

もう 1 つのエッジ ケースは、次のような対称的な小さな入力です。`1 1 1 1`。 どちらの開始戦略でも、どちらの順序でも 0 と 1 を 1 つ配置できるため、長さ 2 が生成されます。 シミュレーションは 1 回交互に行われ、両方のリソースを使い果たすと停止します。 

3 番目のケースは、次のような著しく不均衡な制限です。`100 1 50 1`。 ゼロから始めると、ゼロが 1 つ、次に 1 が 1 つ、合計 2 が生成されますが、1 から始めると 1 しか生成されません。アルゴリズムは、希少な文字から始めると、ブロックされる前に使用率がわずかに向上することを正しく認識します。
