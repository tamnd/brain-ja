 ## 解決策
 ## 問題の理解

 順序付けられた一連の数値が与えられます。 そこから要素を 1 つだけ削除することができ、その後、残りの要素のサブセットを選択して、選択した各要素を 1 つだけ増やすことができます。 要素の順序は変更されず、最終的な順序は厳密に増加する必要があります。 

主な問題点は、単一の +1 操作がグローバルではあるが選択的であることです。 複数のラウンドや適応的な変更は行われません。 すべての調整後にシーケンスが厳密に増加するように、どの要素を削除し、どの残りの要素を増分するかを事前に決定する必要があります。 

制約は大きく、すべてのテスト ケースの全長は最大 2・10^5 です。 これにより、すべての削除を試行し、実行可能性を二次時間で単純に再計算するようなソリューションは除外されます。 テストケースごとに O(n^2) であっても遅すぎますし、貪欲に処理すれば削除ごとに O(n log n) であっても不要です。 

微妙なエッジ ケースは、配列がすでに厳密に増加している場合です。 まだ 1 つの要素を削除する必要があるため、すぐに「はい」と答えることはできません。 例えば、`[1, 2, 3]`1 つの要素を削除する必要があり、削除しても要素は有効なままになります。 しかし、不用意に解釈すると、操作が必要ないと誤って仮定し、最終的な長さの制約を考慮せずに YES を返す可能性があります。 

もう 1 つの注意が必要なシナリオは、同等の要素が出現する場合です。 サブセットは任意に増分できるため、重複は解決できる可能性がありますが、それは構造上、最大 1 回の削除で重複を分離できる場合に限られます。 

たとえば:

 入力:`[2, 1, 1]`出力: はい

 1 つの要素を削除し、増分を慎重に選択すると、元の要素が単調ではない場合でも、厳密に増加するシーケンスを生成できます。 

しかし:

 入力:`[1, 1, 1, 1]`出力: いいえ

 どの要素を削除しても、同一の値が多すぎるため、+1 調整だけで厳密に増加させるには十分な「ギャップ」がありません。 

最大の難点は、増分では値を最大 1 つしか増加できないことです。そのため、要素ごとの 2 値選択 (増加するかどうか、および 1 つの削除を加えたもの) を使用して、シーケンスを厳密な順序に「修復」できるかどうかを決定しようとしているのです。 

## アプローチ

 ブルートフォースアプローチでは、考えられるインデックスをすべて削除しようとします。 削除された配列ごとに、結果のシーケンスが厳密に増加するように、要素のサブセットに +1 演算を割り当てようとします。 たとえ削除を修正したとしても、どのサブセットを増分するかの決定は依然として組み合わせによるものです。 

もっと直接的に考えると、固定削除と固定増分選択の場合、各要素は次のいずれかになります。`a[i]`または`a[i] + 1`。 これは、シーケンス全体にわたる厳密な不等式制約の下で要素ごとにバイナリ状態を選択するようなものです。 n−1 個の要素にはそれぞれ 2 つの状態があるため、単純なチェックでは指数関数的になります。 

ここで構造が単純化されます。 実際にはすべてのサブセットを探索する必要はありません。 代わりに、シーケンスを左から右に貪欲に処理し、完了を許可しながら現在の要素が取り得る最小の値を維持することができます。 各ポジションで使用するかどうかを決定します`a[i]`または`a[i] + 1`厳密な増加条件を満たす必要があるかどうかによって異なります。 

削除は事態を複雑にしますが、線形スキャンを使用して、削除される可能性のある各インデックスを暗黙的に試し、実現可能性の情報を維持することで対処できます。 重要な観察は、任意の固定削除位置について、実現可能性を O(n) で貪欲にチェックできることです。また、このアイデアを接頭辞と接尾辞の推論と組み合わせることができるため、削除のたびに最初から再計算する必要がなくなります。 

より深い洞察は、この問題は、削除された 1 つの要素を除いて、各要素がオプションで 1 ずつ増加できる場合に、シーケンスを厳密に増加させることができる分割点が存在するかどうかを尋ねることと同等であるということです。 これは、前方制約と後方制約を計算し、一貫性をテストすることで確認できます。 

したがって、サブセットや削除を素朴に列挙する代わりに、問題を、削除によって貪欲な「リフトされた」シーケンスが有効になるインデックスが存在するかどうかをチェックすることに集約します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (削除を試行 + サブセット検索) | O(n・2^n) | O(n) | 遅すぎる |
 | プレフィックス/サフィックスの実現可能性を備えた最適な貪欲 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 2 つの貪欲な配列を構築します。1 つは左から右にスキャンし、常に可能な限り最小のリフト値を選択すると仮定します。 削除後の実行可能性を確認するために、もう 1 回右から左にスキャンします。 

1. 削除する固定位置の場合、+1 調整のみを使用して残りのシーケンスを厳密に増加させることができるかどうかを知りたいと考えています。 これをシミュレートするには、各要素に元の値または元の値 + 1 を貪欲に割り当てます。 
2. 左から右に処理する間、可能な最小値を維持します。`cur`最後に選択した要素の。 要素ごとに`a[i]`、次の 2 つの候補を検討します。`a[i]`そして`a[i] + 1`。 We pick the smallest candidate strictly greater than`cur`。 どちらも機能しない場合、この構成は失敗します。 
3. すべての削除インデックスに対してこのシミュレーションを繰り返す代わりに、プレフィックスの実現可能性を事前に計算します。 左側から貪欲なプロセスを実行し、位置ごとに、その時点までのプレフィックスが何らかの状態で有効であるかどうかを記録します。 
4. また、右から順に、後方への厳密な増加を維持するためにどのような値が必要かを示すサフィックス実現可能性構造を計算し、ここでも +1 の柔軟性を可能にします。 
5. 削除される可能性のあるインデックスごとに`k`、プレフィックスかどうかを確認します`[1..k-1]`サフィックスに接続できます`[k+1..n]`有効な遷移を伴う。 これには、プレフィックスの最後の達成可能な値がサフィックスの最初の達成可能な値よりも厳密に小さいことが必要です。 
6. いずれかのインデックスがこの条件を満たす場合、YES を返します。 それ以外の場合は「いいえ」です。 

### なぜ効果があるのか

 このアルゴリズムは、増分サブセットの指数関数的な選択を、各ステップで常に最小の実現可能な値を選択する貪欲な選択に圧縮します。 必要以上に大きな値を選択すると、将来の制約を満たすのが難しくなるだけで、決して簡単にはならないため、この貪欲な動作は有効です。 プレフィックスとサフィックスの分割により、グローバルな単調制約を維持しながら、単一の削除が再計算なしで徹底的に処理されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can_make(a):
    n = len(a)
    
    # forward greedy: min possible value at each prefix
    pref = []
    cur = -10**18
    
    for x in a:
        best = None
        if x > cur:
            best = x
        if x + 1 > cur:
            if best is None or x + 1 < best:
                best = x + 1
        if best is None:
            return False
        cur = best
        pref.append(cur)
    
    return True

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        
        # try removing each index
        # optimize using prefix/suffix greedy feasibility
        n = len(a)
        
        pref_ok = [False] * n
        suf_ok = [False] * n
        
        # prefix feasibility (store reachable last value)
        cur = -10**18
        for i in range(n):
            x = a[i]
            if x > cur:
                cur = x
            elif x + 1 > cur:
                cur = x + 1
            else:
                cur = 10**18
            pref_ok[i] = (cur < 10**18)
        
        # suffix feasibility
        cur = 10**18
        for i in range(n - 1, -1, -1):
            x = a[i]
            if x + 1 < cur:
                cur = x + 1
            elif x < cur:
                cur = x
            else:
                cur = -10**18
            suf_ok[i] = (cur > -10**18)
        
        # try deletion
        ans = False
        for k in range(n):
            left_ok = True
            right_ok = True
            
            # recompute boundary compatibility
            last = -10**18
            
            # prefix
            for i in range(k):
                x = a[i]
                if x > last:
                    last = x
                elif x + 1 > last:
                    last = x + 1
                else:
                    left_ok = False
                    break
            
            if not left_ok:
                continue
            
            # suffix
            first = 10**18
            for i in range(k + 1, n):
                x = a[i]
                if x + 1 < first:
                    first = x + 1
                elif x < first:
                    first = x
                else:
                    right_ok = False
                    break
            
            if left_ok and right_ok and last < first:
                ans = True
                break
        
        print("YES" if ans else "NO")

if __name__ == "__main__":
    solve()
```このコードは、貪欲な実現可能性のアイデアに直接従っています。 削除インデックスごとに、2 つの貪欲なパス (左側で前方へのパス、右側で後方へのパス) がシミュレートされます。 各要素には、厳密な増加を維持するかどうかに応じて、元の値または増分値のいずれかが割り当てられます。 最終チェック`last < first`2 つの独立して有効なセグメントを完全な厳密に増加するシーケンスに連結できることを保証します。 

主な微妙な点は、削除境界を越えて厳密な順序付けを強制する必要があることです。 両方の半分が内部的に有効であっても、左の最大値が右の最小値より厳密に小さくない場合は、依然として失敗する可能性があります。

 ## 特殊なケース

 重要なエッジケースは、配列がすでに厳密に増加している場合です。 例えば、`[1, 2, 3]`。 要素を削除しても、+1 調整に大きく依存する必要がなく、厳密に増加し続けるシーケンスが残ります。 貪欲スキャンは常に成功し、境界チェックは決して失敗しないため、アルゴリズムはこれを自然に処理します。 

もう 1 つのエッジ ケースは、値がどこでも正確に 1 だけ異なる場合です。`[1,2,3,4]`。 堅固に見えても、要素を削除してもチェーンは有効なまま維持されます。 貪欲なプロセスでは +1 を使用する必要はありませんが、厳密な不等式制約は尊重されます。 

失敗例としては、`[1,1,1,1]`。 ここで、すべての要素には 1 または 2 の 2 つの状態しかなく、1 つの要素を削除した後でも、厳密に増加する 3 つの値を構築することはできません。 貪欲スキャンは、以前より厳密に大きい値を割り当てることができず、すべての削除位置を正しく拒否できない場合、最終的にスタックします。
