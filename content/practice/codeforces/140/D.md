 ## 解決策
 ## 問題の理解

 ゲンナディはコンテストの最初の 10 分間をステートメントを読むだけに費やします。 その後、ソリューションを作成する時間がちょうど 710 分残っています。 各問題には一定の執筆時間が必要で、いつでも好きなときに問題を一時停止したり再開したりできます。 

珍しいのはペナルティの定義です。 解決された問題に対するペナルティは、提出時間から午前 0 時までの距離 (分単位) です。 21:00 に提出するとペナルティ 180 が与えられ、03:00 に提出するとペナルティ 180 が与えられます。真夜中に提出するとペナルティ 0 が与えられます。 

目標は辞書編集です。 まず、解決される問題の数を最大化します。 最大数を解決するすべての戦略の中で、ペナルティの合計を最小限に抑えます。 

入力により、すべての問題の執筆時間がわかります。 出力には、解決可能な問題の最大数と達成可能な最小合計ペナルティの 2 つの整数が含まれている必要があります。 

制約は小さいです。 問題は最大 100 個あり、各書き込み時間は最大 720 回です。指数関数的探索でも大きすぎます。$2^{100}$不可能ですが、$O(n^2)$または$O(n \log n)$全然大丈夫です。 コンテストの総使用可能時間はわずか 710 分であるため、多くのスケジュール スタイルのアプローチが実現可能になります。 

難しいのは、最適な提出スケジュールがどのようなものかを理解することです。 不注意な実装では、すべての問題が完了したらすぐに提出されるべきであると想定する可能性がありますが、これは間違いです。 

次の入力を考えてみましょう。```
2
100 100
```両方の問題が午前 0 時までに終了した場合、すぐに提出するとペナルティが与えられます。$250 + 150 = 400$。 しかし、Gennady はただ待って、ちょうど真夜中に両方を提出することができ、合計ペナルティは 0 になります。執筆順序は重要ですが、提出時間は完了後に個別に選択できます。 

もう 1 つの微妙なケースは、問題が午前 0 時前に終了するのに、別の問題が午前 0 時以降に終了する場合に発生します。```
2
30 330
```最初の問題は18:40に終了します。 2 回目は 00:10 に終了します。 最適な戦略は、最初の送信を真夜中まで遅らせることです。 ペナルティは、$0 + 10 = 10$、 ない$320 + 10 = 330$。 

3 番目の特殊なケースは、コンテストがちょうど 06:00 に終了する場合です。```
1
710
```Gennady は 18:10 に書き始め、06:00 ちょうどに書き終えます。 この送信は許可されており、06:00 は午前 0 時から 6 時間であるため、ペナルティは 360 です。 

よくある間違いは、書き込み可能時間を 710 時間ではなく 720 時間として扱うことです。最初の 10 分間は解くことができません。 

## アプローチ

 ブルートフォースアプローチでは、問題のすべてのサブセットと考えられるすべての順序が試行されます。 注文ごとに完了時間をシミュレーションし、可能な限り最適な提出スケジュールを計算できます。 これは概念的に機能します。ペナルティの合計は午前 0 時を基準とした完了時間のみに依存するためです。 

問題は順列の数です。 たとえ20件の問題でも、すべての注文を確認することは不可能になります。 と$n = 100$, 階乗計算量は完全に手の届かないところにあります。 

重要な点は、提出のタイミングが見た目よりもはるかに柔軟であるということです。 

問題が真夜中前に完了したとします。 より早く提出すると、真夜中までの距離が大きくなるため、ペナルティが増加するだけです。 提出には時間がかからないため、午前 0 時前に完了した問題はすべて、午前 0 時ちょうどに提出する必要があります。 

ここで、午前 0 時以降に問題が終了したとします。 提出が遅れると、真夜中から遠ざかるため、ペナルティが増加するだけです。 したがって、深夜以降の問題はすべて、完了したらすぐに提出する必要があります。 

これにより問題は完全に変わります。 解決された問題のペナルティは次のようになります。$$| \text{completion time} - 350 |$$ここで、時間は 18:10 以降の分単位で測定され、真夜中は 350 分後に発生します。 

あとは問題を書く順番を決めるだけです。 

最初の目標は、解決された問題を最大化することです。 すべての問題の価値は等しいため、できるだけ多くの問題を解決するための最適な方法は、最初に短い問題を取り上げることです。 長い問題を短い問題に置き換えても、710 分以内に完了するタスクの総数が減るだけです。 

解決可能な問題の最大数を修正した後でも、最小限のペナルティが必要です。 選択した問題のうち、完了時間から 350 までの距離の合計を最小化する必要があります。 

一見、これはスケジュールの最適化の問題のように見えますが、別の観察によってさらに単純化されます。 

完了時間が午前 0 時より前の場合、完了時間を増やすとペナルティが減ります。 完了時間が午前 0 時以降の場合、完了時間を長くするとペナルティが増加します。 したがって、理想的な完了時間は、可能な限り午前 0 時に近づくように集中します。 

選択した問題を昇順に並べ替えることで、まさにこれが実現されます。 短いジョブは早く終了するため、完了時間が遅くなり真夜中に近くなります。 これは、古典的なスケジュール問題で使用されるのと同じ交換引数です。 

したがって、最適な戦略は次のとおりです。 

1. すべての問題時間を並べ替えます。 
2. 合計が 710 を超えない最大のプレフィックスを取得します。 
3. プレフィックスの合計を完了時間として計算します。 
4.追加$|t_i - 350|$完了時間ごとに。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n! \cdot n)$|$O(n)$| 遅すぎる |
 | 最適 |$O(n \log n)$|$O(1)$番外編 | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 問題の時間を配列に読み取ります。 
2. 配列を非降順で並べ替えます。 

まず短い問題を解くことで、利用可能な 710 分に収まる問題の数が最大になります。 
3. 累積書き込み時間を維持しながら、ソートされた配列を走査します。 

次の問題を追加すると 710 を超える場合は、すぐに中止してください。 以降の問題はすべて少なくとも同じくらい大きいため、どちらにも当てはまりません。 
4. 受け入れられたすべての問題について、その完了時間を記録します。 

完走タイムは18:10から計測します。 深夜は 350 分後に発生します。 
5. この完了時間に対するペナルティ寄与を追加します。 

最適な送信ルールは次のとおりです。 

- 問題が午前 0 時前に終了する場合は、午前 0 時ちょうどに提出してください。 
- 終了が午前0時を過ぎる場合は、すぐに提出してください。 

どちらのケースも次のようにキャプチャされます。$$| \text{completion time} - 350 |$$6. 受け入れられた問題の数をカウントし、そのカウントと合計ペナルティを出力します。 

### なぜ効果があるのか

 書き込み時間を増やして並べ替えると、完了した問題の数が最大になります。これは、短いタスクの前に長いタスクが含まれるスケジュールは、それらを交換することで改善できるためです。 このようなスワップの後、合計消費時間は増加しません。 

同じ一連の問題を解決するすべてのスケジュールの中で、最短優先はすべてのプレフィックスの完了時間を最小限に抑えます。 ペナルティは午前 0 時からの距離であるため、完了時刻を午前 0 時に近づけても、答えは改善されるだけです。 午前 0 時より前の完了時刻は遅い方が有利であり、午前 0 時以降の完了時刻は早い方が有利です。 ソートされた順序により、選択したセットに対して達成可能な、真夜中頃に最も密なクラスタリングが作成されます。 

送信は瞬時に行われるため、送信ポリシーは最適です。 午前 0 時前に完了したソリューションは、いつでも無料で午前 0 時まで待つことができ、午前 0 時以降に完了したソリューションはそれ以上待つ必要はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    a.sort()

    total_time = 0
    total_penalty = 0
    solved = 0

    for x in a:
        if total_time + x > 710:
            break

        total_time += x
        solved += 1

        total_penalty += abs(total_time - 350)

    print(solved, total_penalty)

solve()
```解決策は、問題の時間を分類することから始まります。 これにより、最初に最小の問題を当てはめることが保証され、解決可能なタスクの数が最大化されます。`total_time`18:10 から計測された現在の問題の完了時間を保存します。 深夜は 350 分後に発生するため、違約金は次のようになります。`abs(total_time - 350)`。 

停止条件は非常に重要です。```
if total_time + x > 710:
```コンテストでは、最初の読み上げフェーズの後、正確に 710 分間の書き込みが許可されます。 正確に 710 で終了することは有効であるため、比較は次のように行う必要があります。`>`の代わりに`>=`。 

もう 1 つの微妙な点は、提出の瞬間を明示的にシミュレートしていないことです。 絶対値式は、最適な提出戦略をすでにエンコードしています。 

この実装では少数の整変数のみを使用するため、入力配列を除けばメモリ使用量は一定に保たれます。

## テストケース```python
# helper: run solution on input string, return output string
import sys, io

def solve():
    input = sys.stdin.readline

    n = int(input())
    a = list(map(int, input().split()))

    a.sort()

    total_time = 0
    total_penalty = 0
    solved = 0

    for x in a:
        if total_time + x > 710:
            break

        total_time += x
        solved += 1

        total_penalty += max(0, total_time - 350)

    print(solved, total_penalty)

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    out = sys.stdout.getvalue()

    sys.stdin = backup_stdin
    sys.stdout = backup_stdout

    return out
