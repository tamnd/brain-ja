 ## 解決策
 ## 問題の理解

 このタスクは基本的に、Connect Four ボード上での「もしも」のシミュレーションです。 ゲームの現在の状態を表す 6 × 7 のグリッドが与えられます。各セルには赤いピース、別の色、または空のピースが含まれます。 また、重力ルールに従って、任意の 1 つの列に赤いピースを配置することもできます。つまり、その列の一番下の空のセルを占有することになります。 

7 つの列のそれぞれについて、可能であればその列に赤いピースをドロップすることをシミュレートします。 駒を配置した後、この手が赤の勝ち局面を作るかどうかを確認します。 勝ちは、4 つの赤いピースが水平、垂直、または斜め 2 つの対角方向のいずれかに連続して並んでいることとして定義されます。 手の後にそのようなラインが少なくとも 1 つ存在する場合、その列は勝ち手とみなされます。 

出力は、赤がそこでプレイした場合に赤が即座に勝つような列の数です。 

グリッド サイズは 6 x 7 に固定されているため、状態空間は一定です。 これは、すべての可能性をチェックして基板を複数回スキャンする単純なソリューションでも、すでに実現可能であることを意味します。 重要な制約の意味は、列あたり最大数千の操作までのソリューションは完全に安全であるということです。 

列がすでにいっぱいの場合、微妙なエッジケースが発生します。 その場合、その移動は無効であり、無視する必要があります。 もう 1 つのエッジ ケースは、ボードに勝ちに近い部分的な構造が既に含まれているにもかかわらず、駒を配置してもすぐに 4 連続が形成されない場合です。 チェック後にシミュレートされた移動を元に戻すのを忘れる単純な実装では、列全体で状態が誤って蓄積される可能性があります。 

コーナーケースの例として、ピースを配置すると対角 4 が完成する列を考えてみましょう。 重力を正しくシミュレートすることを忘れて、代わりに一番上の空のセルに駒を配置した場合、有効な勝利を逃す可能性があります。 同様に、カラムのテスト後にボードの復元に失敗した場合、後のチェックが以前のシミュレーションによって汚染されてしまいます。 

## アプローチ

 直接的な総当たりアプローチでは、すべての列を試し、赤いピースを落とすことをシミュレートしてから、ボード全体をスキャンして、行に 4 つの赤いピースのシーケンスが存在するかどうかを検出します。 ボードは 6 × 7 しかないため、考えられるすべての開始位置と方向をチェックするのは継続的な作業ですが、それでも各列ごとに繰り返されます。 これにより、合計 7 つのシミュレーションが行われ、それぞれの後にボード全体のスキャンが行われます。 

スキャン自体は、右、下、斜め右下、斜め上右の 4 つの方向のそれぞれで、各セルを 4 つのシーケンスの潜在的な開始点としてチェックします。 各チェックは一定時間であるため、フルスキャンも一定時間です。 したがって、ブルートフォース ソリューションはすでに効率的ですが、新しいピースが 1 つだけ追加された場合でもボード全体を再チェックするため、その構造は若干冗長です。 

重要な点は、ボード上の勝ちを正しく検出する関数がすでにある場合、すべてを最初から再計算する必要がないということです。 ボードは小さいため、シミュレートされた各移動の後にこの関数を再利用する方が、段階的に状態を維持しようとするよりも簡単でエラーが発生しにくくなります。 したがって、この問題は、クリーンな win-check 関数を使用した直接シミュレーションによって最もよく解決されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 各動きをブルート フォース スキャン | O(7 × 6 × 7) | お(1) | 承認済み |
 | シミュレート + 完全な勝利チェック | O(7 × 6 × 7) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ボードを固定グリッドとして扱い、各列に 1 つの赤いピースを配置するシミュレーションを繰り返します。

1. 6 x 7 ボードを読み取り、変更可能なグリッドとして保存します。 これにより、新しい構造を割り当てることなく、シミュレーション中に一時的に変更することができます。 
2. 赤がボード上のどこかに勝ちラインがあるかどうかをチェックするヘルパー関数を定義します。 この関数はすべてのセルをスキャンし、水平右方向、垂直下方向、斜め右下、斜め上右の 4 つの方向をチェックします。 各チェックでは、連続する 4 つのセルを比較する前に、インデックスが範囲内にあることを確認します。 すべてのセルをチェックする理由は、勝利セグメントはそのセグメントの左上端のセルから少なくとも一方向に開始する必要があるためです。 
3. 有効な勝ち手のカウンターを初期化します。 
4. 7 つの列のそれぞれを反復処理し、それぞれを候補手として扱います。 
5. 各列について、最初の空のセルが見つかるまで下の行から上に向かってスキャンして重力をシミュレートします。 空のセルが存在しない場合、その列はいっぱいであるため、スキップします。 このステップにより、実際のゲームとまったく同じようにピースが着地するようになります。 
6. 見つかったセルに赤いピースを一時的に置きます。 
7. 更新されたボード上で win-check 機能を実行します。 true を返した場合は、この手によって即座に勝利が得られるため、回答カウンタをインクリメントします。 
8. シミュレートされたピースを削除して、元のボードの状態を復元します。 各列を個別にテストする必要があるため、これは非常に重要です。 
9. すべての列をテストした後、カウンターを出力します。 

### なぜ効果があるのか

 このアルゴリズムは、シミュレーションと評価を厳密に分離することに依存しています。 各列は、変更されていないボード上で個別にテストされます。 勝利チェック機能は、考えられるすべての開始点と方向を網羅しているため、移動後に 4 列が存在する場合、それがどこに出現したかに関係なく検出されます。 すべての可能な合法的な手が正確に 1 回シミュレートされるため、勝ちとなるすべての手が正確に 1 回カウントされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def win(field):
    for row in range(6):
        for col in range(7):
            if col + 3 < 7:
                if field[row][col] == field[row][col+1] == field[row][col+2] == field[row][col+3] == 'R':
                    return True
            if row + 3 < 6:
                if field[row][col] == field[row+1][col] == field[row+2][col] == field[row+3][col] == 'R':
                    return True
            if col + 3 < 7 and row + 3 < 6:
                if field[row][col] == field[row+1][col+1] == field[row+2][col+2] == field[row+3][col+3] == 'R':
                    return True
            if col + 3 < 7 and row - 3 >= 0:
                if field[row][col] == field[row-1][col+1] == field[row-2][col+2] == field[row-3][col+3] == 'R':
                    return True
    return False

field = [list(input().strip()) for _ in range(6)]

ans = 0

for col in range(7):
    row = 5
    while row >= 0 and field[row][col] != '.':
        row -= 1

    if row < 0:
        continue

    field[row][col] = 'R'

    if win(field):
        ans += 1

    field[row][col] = '.'

print(ans)
```この解決策は、勝利検出ルーチンを定義することから始まります。 各方向は境界チェックを使用して明示的に処理されるため、インデックスが範囲外になることはありません。 ロジックは水平、垂直、斜めの場合において対称的であり、検出の完全性を保証します。 

メインループは各列を独立して試行します。 重力シミュレーションは単純な下向きスキャンによって実行されますが、これはボードの高さが一定であることを考慮すると最適です。 駒を配置した後、すぐにボードを評価し、それを元に戻します。 このロールバック ステップにより、反復にわたる状態の漏洩が防止されます。 

よくある落とし穴は、カラムのテスト後にセルを復元し忘れることです。 これにより、後のシミュレーションで余分な赤い部分がすでに存在すると想定され、不正確な結果が生成されます。

 ## 特殊なケース

 フルカラムは最も単純な構造のエッジケースです。 アルゴリズムは、空のセルが見つからなくなるまで上方向にスキャンし、その列をスキップすることでこれを処理します。 これにより、違法に作品を配置することがなくなります。 

2 番目のエッジケースは、手を出す前にすでに勝ちが存在している場合です。 この問題では、配置後に勝利を生み出す手を求めているため、シミュレートされた手が勝利状態につながる列のみをカウントします。 勝利チェック機能は、シミュレーションされた配置ごとに適用されるため、既存の勝利がカウントに干渉することはありません。 

3 番目のエッジ ケースは、ボードの境界での対角線の完成です。 たとえば、行 0 または行 5 で終わる対角線は、慎重な境界チェックを必要とします。 この実装では、4 つのセルを比較する前にインデックス アクセスを明示的に保護し、無効なメモリ アクセスや構成の欠落がないことを保証します。
