 ## 解決策
 ## 問題の理解

 0 から N−1 までラベル付けされた同じ頂点セット上に 2 つのルート付き二分木が与えられます。 最初のツリーは初期構成で、2 番目のツリーはターゲット構成です。 ルートを除く各頂点には親が 1 つだけあるため、入力形式は両方のツリーの親ポインターを効果的に記述します。 

許可される操作は、サブツリー上の構造的な移動です。 非ルート頂点 v を選択し、v をルートとするサブツリー全体をデタッチし、そのサブツリー内にない頂点 u の下に再アタッチします。 ツリーは、すべての操作の後、有効なルート付きバイナリ ツリーを維持する必要があります。 目標は、最初のツリーを 2 番目のツリーと同型のツリーに変換することです。つまり、任意のノードで左右の子を入れ替えるまでは構造が同一になります。 

重要な制約は N ≤ 1000 であり、最大 N 回の操作が許可されます。 これは、構成に対するグローバル検索をシミュレートできないことをすでに示唆しています。 各操作は、制御された数のステップで構造的な不一致を減らす方法で、貪欲に、または決定論的に選択する必要があります。 

微妙な点は、ここでの「二分木」は順序制約ではなく構造制約であるということです。 各ノードには最大 2 つの子がありますが、同型性の目的で子は順序付けされていません。 これにより、左右の位置を保持する必要がなくなりますが、サブツリーのマルチセット構造のみを照合する必要があることも意味します。 

サブツリーをボトムアップで突き合わせることを繰り返し試行する単純なアプローチは、サブツリーの移動によってバイナリ制約が一時的に無効にならないことを注意深く確認しないと困難になります。 もう 1 つの脆弱なケースは、構造ではなくラベルの順序によってノードを照合しようとする場合です。 ラベルは任意であるため、そのようなアプローチはすぐに機能しません。 

代表的な障害シナリオは、両方のツリーの次数シーケンスが同一であるものの、形状が完全に異なる場合です。 貪欲な「親ラベルによる一致」戦略は、アライメントを誤って仮定し、ノードが 2 つの子を超える場合に無効な中間ツリーを生成します。 

## アプローチ

 この問題を考える強引な方法は、ターゲット ツリーと比較して親が「間違っている」頂点を繰り返し選択することによって、ツリー a をツリー b に編集することを検討することです。 ノードを 1 つずつ修正し、各操作の後にサブツリーがターゲットのサブツリーと一致するかどうかを確認することもできます。 ただし、サブツリーの同型性を繰り返しチェックすると、チェックごとに O(N) のコストがかかり、潜在的な O(N) 個の動きに対してこれを実行すると、O(N^2) かそれより悪い動作が発生します。これは、ここでは数値的には許容可能ですが、「どの手が正しいか」の決定が局所的に明確に定義されていないため、概念的には不安定です。 

さらに深い観察は、変換中にツリーの部分的な正確さを維持する必要がないということです。 必要なのは、移動するたびに構造が有効なままであり、ターゲット ツリーを着実に「構築」していることを確認することだけです。 任意のサブツリーを再アタッチできるため、慎重に選択した順序でノードを処理することにより、ターゲット ツリーを最初から効果的に再構築できます。 

重要な洞察は、両方のツリーを 0 にルートし、標準的なターゲット構造を計算し、ターゲット ツリーのトポロジー順序でノードを繰り返し接続することによってそれを再構築することです。 各ノードは 1 回だけ配置でき、一度配置すると再度移動する必要はありません。 サブツリーを移動する操作により、すでに構築されている部分構造全体を 1 ステップで再配置することができ、増分構築をシミュレートするのに十分強力です。 

不一致を修正しようとするのではなく、プロセスを「分散した初期状態からターゲット ツリーを構築する」ものとして扱います。 すでに正しく配置されているサブツリーのセットを維持し、ターゲットの親関係に従って新しいサブツリーをアタッチします。 各ノードには最大 2 つの子があるため、バイナリ制約に違反することなく、常にその正しい親の下にサブツリーをアタッチできます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 貪欲な局所修正 | O(N^2) | O(N) | 遅すぎる/不安定 |
 | ルート順序からターゲットを構築する | O(N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず両方のツリーを 0 にルートし、隣接リストを計算します。 ターゲット ツリーから、ルートから始まる親配列または BFS オーダーを抽出します。 

次に、親が常に子より前に処理されるように、ターゲット ツリーの BFS 順序でノードを処理します。 

1. 現在のツリーを初期ツリー構造として初期化します。 また、有効な動きを識別できるように、その親ポインターも維持します。 
2. ターゲット ツリー内のノードを 0 から始まる BFS 順序でスキャンします。ルートはすでに正しいため、スキップされます。 
3. 各ノード v について (ターゲットの順序で)、ターゲット ツリー内の目的の親 u を決定します。 
4. 現在のツリー内で v を見つけ、v をルートとするサブツリーを u の下に移動する操作を実行します。 u は BFS 順序で前に処理されるため、これは常に有効です。そのため、v のターゲットの親はすでに配置されており、v のサブツリー内に存在することはできません。 
5. アタッチ後、現在のツリーの親表現を更新します。 
6. すべてのノードがターゲット構造に従って接続されるまで続行します。 

ルートを除く各ノードは 1 回だけ接続されるため、操作の数は最大 N-1 です。 

### なぜ効果があるのか

 正確さは、ノード v を処理するときに、そのターゲットの親 u がすでに現在のツリー内に正しく配置されており、v のサブツリー内に存在しないという不変条件に依存します。 これにより、再接続操作が常に合法であることが保証されます。 BFS の順序により、親から子への処理が保証されるため、サイクル違反や包含違反は発生しません。 すべてのノードを処理した後、すべての頂点はターゲット ツリーとまったく同じ親を持ちます。これは構造的同型性を意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def build_children(par):
    n = len(par) + 1
    g = [[] for _ in range(n)]
    for i, p in enumerate(par, start=1):
        g[p].append(i)
    return g

def bfs_parent_tree(g, root=0):
    from collections import deque
    parent = [-1] * len(g)
    order = []
    q = deque([root])
    parent[root] = -2
    while q:
        v = q.popleft()
        order.append(v)
        for to in g[v]:
            if parent[to] == -1:
                parent[to] = v
                q.append(to)
    parent[root] = -1
    return parent, order

def solve():
    n = int(input())
    pa = list(map(int, input().split()))
    pb = list(map(int, input().split()))

    ga = build_children(pa)
    gb = build_children(pb)

    par_b, order = bfs_parent_tree(gb, 0)

    parent = [-1] * n
    for i, p in enumerate(pa, start=1):
        parent[i] = p
    parent[0] = -1

    children = [[] for _ in range(n)]
    for v in range(1, n):
        children[parent[v]].append(v)

    def is_ancestor(x, y):
        while y != -1:
            if y == x:
                return True
            y = parent[y]
        return False

    ops = []

    # process nodes in BFS order of target tree
    for v in order:
        if v == 0:
            continue
        u = par_b[v]

        # ensure v is detached correctly before reattaching
        p = parent[v]
        if p == u:
            continue

        # move v under u
        # ensure u not in subtree of v
        if is_ancestor(v, u):
            continue

        # detach v
        if p != -1:
            children[p].remove(v)

        # attach
        parent[v] = u
        children[u].append(v)
        ops.append((v, u))

    print(len(ops))
    for v, u in ops:
        print(v, u)

if __name__ == "__main__":
    solve()
```このソリューションでは、まず親配列から両方のツリーを再構築します。 次に、ターゲット ツリーの BFS 順序付けを構築します。これにより、すべてのノードの親がノード自体の前に処理されることが保証されます。 の`parent`そして`children`構造は進化する現在のツリーを表し、すべての操作は両方を一貫して更新します。 

祖先チェックは、問題の制約に違反する、自身の子孫の下にサブツリーをアタッチしないことを保証する安全策です。 BFS の順序により、正しい構築ではこれがすでに防止されていますが、このチェックにより、実装上の微妙な間違いが防止されます。 

各操作は (v, u) ペアを追加し、ノードごとに最大 1 つの操作を実行します。 

## 実用的な例

 ### 例 1

 最初のツリーがチェーンでターゲット ツリーがスターである小さなケースを考えてみましょう。 

操作を追跡します。 

| ステップ | ノード v | ターゲットの親 u | 現在の親 | 操作 |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 0 | 2 | 1 → 0 に移動 |
 | 2 | 2 | 0 | 3 | 2 → 0 を移動 |
 | 3 | 3 | 0 | 0 | スキップ |

 移動するたびに、チェーンの形状が徐々に星形に変わります。 ステップ 2 の後、すべてのノードがルートの下に正しく接続されます。 

これは、ノードが一度正しく配置されると、二度と移動されないことを示しています。 

### 例 2

 ツリーがすでに正しい場合:

 | ステップ | ノード v | ターゲットの親 u | 現在の親 | 操作 |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 0 | 0 | スキップ |
 | 2 | 2 | 1 | 1 | スキップ |

 初期構造がすでにターゲットと一致しているため、操作は必要ありません。 

これにより、アルゴリズムが不必要な動きを導入していないことが確認されます。

 ## 特殊なケース

 エッジ ケースの 1 つは、最初のツリーがすでにターゲットと同型であるものの、異なる子の順序で配置されている場合です。 同型性は順序付けを無視するため、隣接リストを正確に一致させようとする単純なアルゴリズムは、不必要な移動を誤って実行する可能性があります。 このソリューションでは、BFS ベースの親割り当てにより、親ポインターが異なる場合にのみ動作することが保証されるため、移動はトリガーされません。 

もう 1 つのエッジ ケースは、ノードの正しい親が現在のサブツリー内にある場合です。 不用意に実装すると、移動が試みられ、「u は v のサブツリーにない」という制約に違反する可能性があります。 祖先チェックはこの状況を防ぎますが、BFS の順序付けにより、正しく構築されたシーケンスではそれが不可能になります。 

最後の微妙なケースは、ノードの複数の子を再配置する必要がある場合です。 各子は BFS 順序で独立して処理されるため、各添付ファイルは干渉することなく個別に処理され、中間のバイナリ制約を超えないことが保証されます。
