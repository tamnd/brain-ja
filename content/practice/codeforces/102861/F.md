 ## 解決策
 ## 問題の理解

 入力はファストミントンの試合の時系列記録です。 各文字は、試合中に発生した 1 つのイベント (サーバーの得点、レシーバーの得点、または現在のスコアの印刷要求のいずれか) を表します。 プログラムは試合を正確に順番どおりに再生し、すべてのスコア要求にその時点での試合の状態を返す必要があります。 

試合には最大 3 つのゲームが含まれており、2 つのゲームに勝った最初のプレーヤーが試合に勝ちます。 各ゲームでは、1 人のプレイヤーが勝利条件に達するまでポイントが蓄積されます。 プレーヤーは、少なくとも 5 ポイントを獲得し、少なくとも 2 点リードするか、10 ポイントに到達した時点でゲームに勝利します。 各ポイントの後、得点したプレーヤーが次のポイントのサーバーになります。 最初のゲームは左のプレーヤーのサービスから始まり、後のゲームは前のゲームに勝ったプレーヤーのサービスから始まります。 

入力は一連のイベントのみであるため、大きな数値制約はありません。 関連する境界は、そのシーケンス内の文字数です。 直接シミュレーションでは各イベントが 1 回処理されるため、実行時間は入力サイズに比例して増加します。 すべてのクエリに対して最初から一致状態を繰り返し再構築するアプローチでは、不必要な繰り返し作業が実行され、多くのスコア通知が存在する場合は二次関数になる可能性があります。 

いくつかの詳細により、単純な実装が損なわれる可能性があります。 よくある間違いは、2 ポイントのアドバンテージがなくても、10 ポイントに到達したプレーヤーがすぐに勝つことを忘れていることです。 たとえば、入力`SSSSSSSSSSQ`左のプレイヤーが 10 ポイントでゲームに勝利した状態で終了するため、出力は次のようになります。`0 (winner) - 0`これが最初の試合で、試合終了後に最終試合のスコアが要求された場合。 5 点差と 2 点差の条件のみをチェックするソリューションでは、誤ってゲームが継続されてしまいます。 

もう 1 つの注意が必要な状況は、スコア発表後のサービング プレーヤーです。 入力用`SQ`、左のプレイヤーが唯一のポイントを獲得し、次のサーバーとしてマークする必要があります。 出力は`0 (1*) - 0 (0)`。 次のラリーまで元のサーバーを保持するソリューションでは、間違ったプレイヤーがマークされてしまいます。 

ゲーム間の移行も誤って処理されやすいです。 たとえば、右のプレーヤーが最初のゲームに勝った後、右のプレーヤーが 2 番目のゲームの最初のポイントを提供します。 サーバーは左側のプレーヤーにリセットされません。 このルールを忘れると、その後のスコア発表がすべて変更されます。 

## アプローチ

 最も直接的な解決策は、すべてのラリーをシミュレートすることです。 キャラクターごとに、総当たり実装により、現在のポイントを維持し、ゲームが終了したかどうかを確認し、ゲーム スコアを更新し、要求された状態を出力できます。 これはすでにルールの自然な表現であり、試合ルールは現在の位置より前に発生したイベントにのみ依存するため、これは正しいことです。 

それほど慎重ではない総当たりバージョンでは、あらゆる問題を処理できる可能性があります。`Q`入力プレフィックス全体を最初から再生してスコアを再構築します。 入力に多くのスコアリクエストが含まれており、シーケンスの長さが`n`、これには大まかに必要になります`n`それぞれの操作`n`リクエストの結果、`O(n²)`仕事。 

この繰り返しを取り除く観察は、すべてのイベントが一致状態を 1 回だけ変更するということです。 将来のイベントに必要な完全な情報は、各プレーヤーが勝ったゲーム数、ゲームの現在のポイント、現在のサーバー、および試合がすでに終了したかどうかなど、少数です。 古いイベントを再検討する必要がないため、左から右にスキャンしながらこの状態を保存するだけで十分です。 

ルールが決定的であるため、ブルート フォースは機能しますが、すでに処理された情報を再計算する場合は失敗します。 一致状態のサイズが一定であるという観察により、問題全体をシングル パス シミュレーションに縮小できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 大規模なイベント シーケンスには遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 左右のプレーヤーが勝ったゲーム、現在のゲーム ポイント、次のラリーにサーブするプレーヤーを記録します。 最初は左のプレーヤーがサービスを行い、ゲームスコアとポイントスコアは両方ともゼロです。 これらの変数は、将来のイベントに影響を与える可能性のあるすべてを記述します。 
2. イベント シーケンス内の各文字を左から右に読みます。 得点イベントの場合、ポイントを受け取るプレーヤーを決定します。 サーバーが得点すると、サーバーはポイントを獲得します。 レシーバーが得点すると、他のプレイヤーがポイントを獲得します。 スコアラーは常に次のラリーにサーブを提供するため、ポイントを獲得した後は、その同じプレーヤーを次のサーバーにします。 
3. 各ポイントの後、現在のゲームが終了したかどうかを確認します。 プレーヤーは、少なくとも 5 ポイントを獲得し、少なくとも 2 点リードした場合、または 10 ポイントに達した場合に勝ちます。 最新のラリーがゲームを完了している可能性があるため、チェックはポイント合計を更新した後に行う必要があります。 
4. ゲームが終了したら、勝者のゲーム数を増やし、ポイントスコアをゼロにリセットします。 そのゲームでプレイヤーが合計 2 勝した場合、試合は終了します。 それ以外の場合は、完了したゲームの勝者が次のゲームのサーバーになります。 
5. スコアのアナウンスが表示されたら、保存された状態を印刷します。 試合がまだアクティブな場合は、両方のゲーム スコアと両方のポイント スコアを出力し、正しいプレーヤーにサーバー マーカーを追加します。 試合が終了した場合は、最終試合のスコアのみを印刷し、勝者にマークを付けます。 

機能する理由: 維持される状態は、まさに次のイベントの結果を決定するためにルールによって必要とされる情報です。 すべての文字が処理された後、変数は、これまでに確認されたすべてのイベント後の真の一致状況を表します。 各ラリーは 1 回適用され、すべてのゲーム移行はルールに直接従うため、今後のすべてのスコア発表は正しい状態から生成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()

    games = [0, 0]
    points = [0, 0]
    server = 0
    finished = False
    winner = -1

    ans = []

    def game_winner():
        if points[0] >= 10:
            return 0
        if points[1] >= 10:
            return 1
        if points[0] >= 5 and points[0] - points[1] >= 2:
            return 0
        if points[1] >= 5 and points[1] - points[0] >= 2:
            return 1
        return -1

    def current_score():
        if finished:
            if winner == 0:
                return f"{games[0]} (winner) - {games[1]}"
            return f"{games[0]} - {games[1]} (winner)"

        left = str(points[0]) + ("*" if server == 0 else "")
        right = str(points[1]) + ("*" if server == 1 else "")
        return f"{games[0]} ({left}) - {games[1]} ({right})"

    for c in s:
        if c == 'S' or c == 'R':
            if not finished:
                scorer = server if c == 'S' else 1 - server
                points[scorer] += 1
                server = scorer

                w = game_winner()
                if w != -1:
                    games[w] += 1
                    points = [0, 0]
                    if games[w] == 2:
                        finished = True
                        winner = w
                    else:
                        server = w
        else:
            ans.append(current_score())

    sys.stdout.write("\n".join(ans))

if __name__ == "__main__":
    solve()
```の`games`配列には一致スコアが格納されますが、`points`現在のゲームスコアのみを保存します。 これらを別々にしておくことで、2 つの異なる勝利条件が混在することを避けられます。 

の`server`変数は常に次のラリーにサービスを提供するプレーヤーを指します。 得点したプレーヤーは、最初にサーブをしていたかレシーブしていたかに関係なく、再びサーブを行うため、得点イベントの直後に更新する必要があります。 

の`game_winner`関数は、2 ポイント ルールの前に 10 ポイント ルールをチェックします。 この順序付けはすべての状態に必要なわけではありませんが、即時の終了条件が明示的になります。 関数は戻ります`-1`ゲームが続いている間。 

ゲームが終了すると、ポイント配列はリセットされます。 試合の勝者が決定した後は次のラリーがないため、コードは最終ではない試合の後にのみサーバーを変更します。 

スコアのフォーマットはシミュレーションから分離されています。 これにより、出力の詳細が一致ロジックに影響を与えることがなくなり、アクティブな一致と終了した一致の区別が明確になります。

 ## 特殊なケース

 10 ポイント ルールは、2 ポイント アドバンテージ条件に依存する前にチェックすることで処理されます。 入力用`SSSSSSSSSSQ`、左のプレイヤーが 10 ポイントに達すると、最初のゲームはすぐに終了し、スコア要求が出力されます。`1 (winner) - 0`。 アルゴリズムは、より大きなリードを待つことはありません。 

各ラリー後のサービングの移行は、スコアラーを新しいサーバーとして割り当てることによって処理されます。 入力用`SQ`、最初のイベントは左のプレイヤーに 1 ポイントを与え、2 番目のイベントは出力します。`0 (1*) - 0 (0)`。 スコアラーが次のラリーにサービスを提供するため、星が左側に表示されます。 

新しいゲームの開始では、前のゲームの勝者がサーバーとして使用されます。 左のプレイヤーが最初のゲームに勝って 2 番目のゲームが開始される場合、シミュレーションでは元の開始プレイヤーにリセットされるのではなく、左のプレイヤーがサーバーとして維持されます。 これは一致状態の不変条件に従い、将来の誤ったポイントの割り当てを防ぎます。 

終了したマッチの状態も保存されます。 プレーヤーが 2 ゲーム勝利に到達すると、その後`Q`イベントはスコアリングを続行するのではなく、最終結果を出力し続けます。 勝者が判明した後は、試合の状態は不変になります。
