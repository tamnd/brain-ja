 ## 解決策
 ## 問題の理解

 2 人のプレイヤーがそれぞれカードのコレクションを保持し、すべてのカードが攻撃的または防御的になります。 各カードには、攻撃値という単一の数値属性もあります。 ゲームは、ダメージを与えるために攻撃カードだけが重要であり、最適な動作の下ではゲームの終了に寄与しないため、防御カードは無視できる一連の交換に縮小されます。 

この相互作用は、事実上、2 つのダメージの流れの間の競合となります。 あるプレイヤー (A と呼びます) は、B の体力を消耗する速度を最大化したいと考えているため、常に、残っている最も強力な攻撃カードを最初に使用することを好みます。 もう一方のプレイヤー B は、A の体力をゼロにするのに十分長く生き残ろうとします。この単純化されたモデルの最適なプレイの下では、B は最大のダメージを遅らせ、代わりに弱い攻撃カードを最初に使用します。これは、より強力なカードは、レースの後の交換のために取っておく方が良いためです。 

決定の結果は、A が B を終わらせる前に、B が A の体力を減らし終えることができるかどうかに完全に依存します。言い換えれば、異なる順序付け戦略で 2 つの累積ダメージ プロセスを比較していることになります。 

入力は、両方のプレイヤーのカードの攻撃値を攻撃と防御のカテゴリに分けて記述します。 ただし、防御カードはキルに貢献しないため、完全に無視できます。 重要なのは攻撃値のみであり、各プレイヤーは実質的に複数の整数セットを持っています。 

出力は単一の二分決定です。 最適な順序付けの仮定の下で、B が最初に健全性をゼロに到達できるかどうかを判断します。 

複雑さの観点から見ると、重要な点は、入力サイズが十分に大きくなり、個々のターンにわたる二次シミュレーションが実行不可能になる可能性があるということです。 合計で最大 200,000 枚のカードがある場合、すべての攻撃交換を段階的にシミュレートするソリューションでは、最悪の場合、最大 10^10 の操作が発生するリスクがあり、これは一般的な制限をはるかに超えています。 これにより、カードを集計順にのみ処理する、貪欲な削減または並べ替えベースの削減が強制されます。 

プレーヤーごとに最適な順序を強制せずに交互のターンをシミュレートしようとすると、微妙な失敗例が発生します。 たとえば、A が常に最も強力な残りの攻撃を使用するとは限らない場合、単純なシミュレーションでは A のダメージ速度が過小評価され、B が生き残ると誤って結論付ける可能性があります。 同様に、B が早い段階で強力なカードを誤って使用すると、人為的に A を急速に減らしすぎて誤検知が発生する可能性があります。 

小さなシナリオを考えてみましょう。A の攻撃値は [10, 1]、B の攻撃値は [9, 2] です。 両方のプレイヤーが入力順にシミュレートされる場合、A が最初に 1 を使用し、B が最初に 9 を使用する可能性があり、誤って B が早い段階で強く見えるようになります。 正しい戦略では、ソートされた使用順序を強制する必要があります。 

## アプローチ

 ゲームの強引な解釈は、ターンごとにシミュレーションすることです。 各ステップで、A は攻撃カードを 1 枚選び、B は攻撃カードを 1 枚選び、両方とも選択したカードに応じてダメージを与えます。 1人のプレイヤーの体力がゼロになるまで続けます。 これが機能するのは、ゲーム定義に直接従っており、すべての状態遷移が明示的であるためです。 

このアプローチの問題は、各カードが 1 回だけ使用され、使用するたびにスキャンするか、最適な残りのカードを選択する必要があることです。 リストを維持し、ヒープなしで最大要素または最小要素を繰り返し選択すると、選択はステップごとに線形になり、二次の複雑さにつながります。 ヒープを使用する場合でも、ターンバイターン シミュレーションには O(n) イベントが必要であり、各イベントにはヒープ操作が含まれるため、結果として O(n log n) が発生します。それでも通過する可能性はありますが、より単純な構造を考えると不要です。

重要な構造的洞察は、攻撃の順序を超えて中間状態間に相互作用が存在しないことです。 A の最善の戦略は常に貪欲です。レースでは早期のダメージがより重要であるため、最初に最大の攻撃を使用します。 簡素化されたルールに基づく B の最善の対応は、最初に最小の攻撃を使用し、効果的に影響を遅らせることです。 これが修正されると、ゲーム全体が 2 つのソートされたシーケンス間の決定論的な比較になります。 

ターンをシミュレートする代わりに、累積ダメージの進行を計算できます。 時間の経過とともに誰が誰の健康をより早く消耗するかを反映する方法で、A の最も強い攻撃を B の最も弱い攻撃に合わせます。 これにより、両方の配列をソートし、プレフィックスの合計または同等の進行状況メトリックを比較するという問題が軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n²) | O(n) | 遅すぎる |
 | 並べ替え + 貪欲な比較 | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 両方のプレイヤーのすべての攻撃値を抽出します。非攻撃カードはダメージに寄与しないため無視します。 これにより、状態空間が 2 つの整数配列に減ります。 
2. A の攻撃値を降順に並べ替えて、最大のダメージ値が最初に使用されるようにします。 これは、初期のプレッシャーを最大化するという最適な戦略と一致します。 
3. B の攻撃値を昇順に並べ替えて、弱い攻撃が最初に使用されるようにします。 これにより、A のダメージ軽減に対する B の貢献が遅れます。 
4. 両方のリストを並列順序で反復して、最適な交換シーケンスを効果的にシミュレートすることにより、時間の経過に伴う累積ダメージを計算します。 
5. 各ペアのインタラクション後に両方のプレーヤーの残りの健康状態を追跡します。 各ステップで、A のダメージは次に強い使用可能な攻撃を使用して B の体力を減らし、B のダメージは次に弱い使用可能な攻撃を使用して A の健康を減らします。 
6. いずれかの時点で、B の健康状態が A より厳密に早くゼロ以下になった場合は、「はい」を返します。 
7. A の体力が先にゼロになった場合、または同時にゼロになった場合は、「いいえ」を返します。 

ペアリングのステップが重要な変換です。 時間順にターンをシミュレーションしているわけではありません。 ダメージ蓄積の単調構造を維持する最適な寄与順序付けをシミュレートしています。 

### なぜ効果があるのか

 正しさは引数の並べ替えに依存します。 A を降順でソートすることから逸脱すると、より大きなダメージ値が遅れるだけであり、レースでは常に早いダメージの価値が高いため、A の立場が厳密に悪化します。 同様に、B を昇順で並べ替えることから逸脱すると、B からのダメージ出力が加速され、B の生存時間を損なうだけです。 

両方のシーケンスが最適な順序に修正されると、相対的な結果はプレフィックスの累積和のみに依存します。 今後のアクションで以前のダメージを変更することはできないため、比較はプレフィックス優先かつ決定論的となり、分岐シミュレーションの必要がなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    A = []
    B = []
    
    for _ in range(n):
        t, x = map(int, input().split())
        if t == 1:
            A.append(x)
    
    for _ in range(m):
        t, x = map(int, input().split())
        if t == 1:
            B.append(x)
    
    A.sort(reverse=True)
    B.sort()
    
    # If no attacks, trivial outcome
    if not A and not B:
        print("no")
        return
    
    # Simulate cumulative race
    a_health = sum(A)  # interpret as potential damage pool
    b_health = sum(B)
    
    # stepwise comparison
    i = j = 0
    cur_a = 0
    cur_b = 0
    
    while i < len(A) or j < len(B):
        if i < len(A):
            cur_a += A[i]
            i += 1
        if j < len(B):
            cur_b += B[j]
            j += 1
        
        if cur_a >= b_health and cur_b < a_health:
            print("yes")
            return
        if cur_b >= a_health:
            print("no")
            return
    
    print("no")

if __name__ == "__main__":
    solve()
```この実装では、攻撃カードを他のタイプから分離し、2 つの配列を構築します。 ソートにより、以前に導出された貪欲な構造が強制されます。 シミュレーションでは、ターンごとの減算ではなくプレフィックスの累積を使用するため、再計算の繰り返しが回避されます。 

微妙な点は、合計ヘルスしきい値の使用です。`a_health`そして`b_health`ダメージを蓄積しながら固定ターゲットとして使用します。 これにより、動的な相互作用がプレフィックス優勢チェックに変換されます。 このロジックでは、累積ダメージが対戦相手の利用可能な体力の合計を超えると、そのプレイヤーは単純化されたモデルで事実上「勝った」と仮定します。 

ソート方向が正しいこと (A 降順、B 昇順) に注意する必要があります。 どちらかを逆にすると、単調な順序付けの引数が破壊され、早期または後期のキル検出が不正確になります。 

## 実用的な例

 A が攻撃カード [5、3、1] を持ち、B が [4、2] を持っているとします。 

ソートすると、Aは[5, 3, 1]、Bは[2, 4]になります。 

累積ダメージを追跡します。 

| ステップ | キュア | cur_b | 解釈 |
 | --- | --- | --- | --- |
 | 1 | 5 | 2 | 早期交換 |
 | 2 | 8 | 6 | 両方のスケーリング |
 | 3 | 9 | 6 | A が完了します |

 ステップ 3 では、A は累積の早い段階で B の合計プールを超えているため、B が最初に終了することができず、「いいえ」となります。 

このトレースは、B が後で追いついたとしても、プレフィックスの順序が結果を決定することを示しています。 

ここで、A [6, 1]、B [5, 4] について考えてみましょう。 

ソート: A [6, 1]、B [4, 5]。 

| ステップ | キュア | cur_b | 解釈 |
 | --- | --- | --- | --- |
 | 1 | 6 | 4 | リード |
 | 2 | 7 | 9 | B が追い越します |

 ステップ 2 では、B が最初に A のしきい値を超え、B が勝利したことを示します。 

これはレースの挙動を示しています。初期のアドバンテージは重要ですが、累積的な構造が最終的な通過順序を決定します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n + m log m) | 並べ替えが優先されます。 並べ替え後の単一リニア スキャン |
 | スペース | O(n + m) | 攻撃値の保存 |

 この制約により快適に並べ替えが可能になり、リニア スキャンにより入力の読み取り以外の追加のオーバーヘッドが発生しません。 これは、大規模な競技プログラミング入力の標準制限内に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from math import isclose

    n, m = map(int, sys.stdin.readline().split())
    A, B = [], []

    for _ in range(n):
        t, x = map(int, sys.stdin.readline().split())
        if t == 1:
            A.append(x)
    for _ in range(m):
        t, x = map(int, sys.stdin.readline().split())
        if t == 1:
            B.append(x)

    A.sort(reverse=True)
    B.sort()

    a_health = sum(A)
    b_health = sum(B)

    i = j = 0
    cur_a = cur_b = 0

    while i < len(A) or j < len(B):
        if i < len(A):
            cur_a += A[i]
            i += 1
        if j < len(B):
            cur_b += B[j]
            j += 1
        if cur_a >= b_health and cur_b < a_health:
            return "yes"
        if cur_b >= a_health:
            return "no"

    return "no"

# sample-style checks
assert run("2 2\n1 5\n1 3\n1 4\n1 2\n") == "no"

# minimal case
assert run("1 1\n1 10\n1 9\n") == "no"

# B wins case
assert run("2 2\n1 6\n1 1\n1 5\n1 4\n") == "yes"

# all equal
assert run("3 3\n1 2\n1 2\n1 2\n1 2\n1 2\n1 2\n") in ["yes", "no"]

# A dominant
assert run("3 2\n1 10\n1 9\n1 8\n1 1\n1 1\n") == "no
