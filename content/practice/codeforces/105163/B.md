 ## 解決策
 ## 問題の理解

 文字で構成される単一の文字列が与えられ、変更ができなくなるまでローカル リダクション ルールを繰り返し適用します。 ルールは簡単です。同じ文字が 3 つ隣接すると、それらの文字は文字列から消えます。 欠失により、以前に分離されていた部分の境界を越えて新しいトリプルが形成される可能性があるため、安定するまでプロセスを継続する必要があります。 

出力は、可能なすべての削除が実行された後の最終文字列です。 すべてを削除すると、結果は空の文字列になります。 

主要な構造上の制約は、各キャラクターがプロセス中に非常に小さな近傍とのみ対話することです。 削除はカスケードできますが、その効果は常にローカルです。キャラクターは、その周囲が一致している場合にのみ、削除可能なトリプルの一部になることができます。 

入力長が 10^5 程度の場合、削除のたびに文字列全体を繰り返しスキャンする単純なシミュレーションでは、敵対的な場合に潜在的に O(n^2) 時間が必要になります。 たとえば、次のような文字列`aaabbbccc...`崩壊するたびに再スキャンが繰り返され、二次的な動作が発生します。 

削除によって境界を越えて新しいトリプルが作成される場合、より微妙な失敗例が発生します。 

入力:`aabbbbaa`正しい出力:`aa`単純な左から右への削除パスは削除する可能性があります`bbb`、生産`aabaa`、その後、グローバルに再処理しない限り、新しい中間領域を正しくマージして再チェックすることができません。 

これは、正確さが、グローバルな再スキャンではなく、直近の歴史を認識し続けることに依存していることを示しています。 

## アプローチ

 ブルートフォースのアイデアは、文字列を繰り返しスキャンし、3 つ連続する等しい文字が出現した場合はそれを削除することです。 削除するたびに文字列が縮小し、最初からスキャンが再開されます。 これが機能するのは、すべての有効な削除が最終的に適用され、同一のトリプルのみが消えるため、順序は正確さには関係ありません。 

問題はパフォーマンスです。 文字列の各パスには O(n) のコストがかかり、最悪の場合、パスごとに 1 つのトリプルしか削除できない可能性があります。 のような文字列の場合`aaa...a`長さが n の場合、アルゴリズムは O(n) パスを実行し、各スキャンが O(n) であるため、時間は O(n^2) になります。 

重要な点は、プロセスがアクティブなままの最後の数文字のみに依存しているということです。 キャラクターを配置したら、そのキャラクターが前の 2 つの生き残ったキャラクターと長さ 3 のランを形成するかどうかだけが問題になります。 これまでのものは、最終的な圧縮表現を除いて、将来の進化とは無関係です。 

これは、現在の縮小形式を段階的に追跡する構造を維持することを示唆しています。 スタックは当然、進化する接尾辞を表します。 新しい文字を追加するたびに、最後の 3 つの要素を検査するだけで済みます。 一致する場合は直ちにキャンセルされ、以前の部分を再スキャンすることなく続行されます。 

これにより、グローバルに繰り返されるプロセスが単一の線形パスに変わります。

 ## アルゴリズムのチュートリアル

 現在の縮小された文字列を表すスタックを維持しながら、文字列を左から右に処理します。 

1. 空のスタックを初期化します。 このスタックは、現在位置を処理した後の有効な縮小プレフィックスを常に表します。 
2. 入力文字列の各文字を左から右に繰り返します。 
3. 現在の文字をスタックにプッシュします。 これにより、現在の暫定的な縮小文字列が拡張されます。 
4. 挿入するたびに、スタック内の最後の 3 文字が同一かどうかを確認します。 これは、最新の文字を含まずに以前の部分が新しいトリプルを形成できないため、削除をトリガーできる唯一のパターンです。 
5. 最後の 3 文字が同じ場合、それらをスタックから削除します。 これは、有効なトリプルの削除をシミュレートし、削除によって作成された新しい隣接効果を即座に公開します。 
6. 次の文字の処理を続けます。 このプロセスは本質的に増分的なものであるため、バックトラッキングや再スキャンは必要ありません。 

### なぜ効果があるのか

 スタック不変条件は、i 番目の文字を処理した後、三重削除ルールに基づいてスタックにプレフィックス s[0..i] の完全に縮小された形式が含まれることです。 新しく追加された文字のみが含まれる可能性があるため、プレフィックス内で完全に発生する可能性のある削除はすべてすでに適用されています。 削除では文字列がローカルで短縮されるだけで、前の 2 文字よりも左側に依存関係が作成されることはないため、完全性を保証するにはチェックをスタック サフィックスに制限するだけで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    st = []

    for ch in s:
        st.append(ch)
        if len(st) >= 3 and st[-1] == st[-2] == st[-3]:
            c = st[-1]
            st.pop()
            st.pop()
            st.pop()

    print("".join(st))

if __name__ == "__main__":
    solve()
```この実装はスタック プロセスを直接ミラーリングします。 スタックとして使用される Python リストに文字を保存します。 追加するたびに、最後の 3 つのエントリのみが検査されます。 一致する場合は、ちょうど 3 つの要素を削除します。 

微妙な点は、トリプルを削除するときにループが必要ないことです。 複数のカスケードで繰り返しのチェックが必要な問題とは異なり、ここでは削除するたびに厳密に長さが 3 ずつ減り、新しいトリプルには直前の文字が含まれている必要があり、以降の反復で自然にチェックされます。 

最後の結合により、最終的な縮小された文字列が再構築されます。

 ## 特殊なケース

 微妙なケースの 1 つは、以前の削除によって作成された境界を越えて複数の崩壊が連鎖する場合です。 たとえば:

 入力:`aaabaaa`処理:

 開始スタックは次のように進化します`aaa`すぐに倒れて立ち去る`baaa`、その後、末尾`aaa`再び倒れて去ります`b`。 

各削除後にスタックは真の削減されたプレフィックスを反映するため、アルゴリズムはこれを自然に処理します。 次に追加される文字は常に現在のサフィックスと比較されるため、新しく公開されたトリプルが見逃されることはありません。 

もう 1 つのエッジ ケースは、削除が最初に発生し、空のスタックが残る場合です。 最後の 3 つの要素にアクセスする前に常にスタック長をチェックするため、アンダーフローは発生せず、アルゴリズムは空の状態から安全に続行されます。
