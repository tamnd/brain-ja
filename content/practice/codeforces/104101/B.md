 ## 解決策
 ## 問題の理解

 時系列のイベント ログに従って健康状態が時間の経過とともに変化する 1 人のゲーム キャラクターをシミュレートしています。 キャラクターは初期体力値から始まり、レベルアップするたびに追加の体力を獲得します。 ある時点で、健康状態を永続的に増加させ、受動的能力のロックを解除する特別なアイテムを購入することもできます。 

アイテムを取得した後、キャラクターが敵を攻撃するたびに、その敵が現在クールダウン中でない場合、パッシブがトリガーされることがあります。 これがトリガーされると、キャラクターの現在の健康状態に基づいてダメージ値が計算され、そのダメージの一部が治癒に変換されます。 回復はキャラクターの現在の健康状態に即座に追加され、その後の計算に影響を与える可能性があります。 

入力は、昇順にソートされたタイムスタンプ付きイベントのシーケンスです。 各イベントは、体力を一定量増加させるレベルアップ、大きな一定の体力ボーナスを付与してパッシブを有効にする購入イベント、またはクールダウン状態に応じてパッシブをトリガーする場合としない場合がある 5 人の可能な敵のうちの 1 人に対する攻撃のいずれかです。 クールダウンは敵ごとに個別に追跡されるため、異なる敵を攻撃しても互いのクールダウン タイマーは干渉しません。 

出力は、すべてのイベントを順番に処理した後の最終的なヘルス値です。 

制約は十分小さいため、直接シミュレーションで十分です。 イベントは最大 1000 件あり、時間は 60 分のウィンドウにわたって秒単位で与えられるため、イベントごとに一定の作業を行う単純な O(m) シミュレーションでも十分に高速です。 

主な微妙な点は、敵ごとのクールダウン ロジックを正しく処理し、アイテムの購入後にのみパッシブが適用されるようにすることにあります。 もう 1 つの頻繁なエラーの原因は、パッシブ内の操作の順序です。ダメージは攻撃時の現在のヘルスに依存し、回復はダメージを計算する前ではなく計算後に適用されます。 

単純な間違いは、クールダウンが敵ごとにあることを忘れることです。 たとえば、00:10 の攻撃が敵 1 にヒットし、次に 00:20 の別の攻撃が敵 2 にヒットした場合、アイテムがアクティブであれば、最初のトリガーから 10 秒が経過しても、2 番目の攻撃は敵 2 でパッシブをトリガーする必要があります。 

もう 1 つの微妙なケースは、クールダウン境界です。 時間 t に攻撃がトリガーされた場合、時間 t + 29 で同じ敵に対する 2 回目の攻撃はトリガーされませんが、時間 t + 30 では再び許可される必要があります。 

## アプローチ

 最も直接的なアプローチは、説明どおりにタイムラインをシミュレートすることです。 キャラクターの現在の健康状態、アイテムが購入されたかどうか、各敵についてパッシブが最後にトリガーされた時間を維持します。 

イベントごとに、タイムスタンプを秒単位で解析し、順番に処理します。 レベルアップイベントは単純に一定量の体力を追加します。 アイテムを購入すると固定ボーナスが追加され、将来の受動的計算が可能になります。 攻撃イベントは、アイテムがアクティブであるかどうか、およびその敵のクールダウン条件が満たされているかどうかを確認します。 両方が当てはまる場合、現在の体力を使用してダメージを計算し、そのダメージの下限パーセンテージとして治癒を計算し、それを体力に追加します。 また、その敵の最後のトリガー時間も更新します。 

入力サイズがすでに小さいため、ブルート フォース バリアントの構造はそれほど変わりません。 唯一の非効率性は、時間の解析を再計算したり、以前のイベントを不必要にスキャンしたりすることですが、それでも制限内に収まります。 実際の改善は概念的なものです。敵ごとの状態を追跡することで、各イベントを O(1) で処理できるようになります。

 ## アルゴリズムのチュートリアル

クールダウン ロジックは差異のみに依存するため、比較を簡素化するためにすべてのタイムスタンプを秒に変換します。 

1. 現在の健康状態を H1 として初期化し、アイテムを未購入としてマークします。 また、初期の攻撃が常にクールダウン チェックに合格するように、サイズ 5 の配列 last_trigger を非常に負の値で初期化します。 
2. イベントを時系列に処理します。 
3. イベントがレベルアップの場合、体力を H2 増加させます。 
4. イベントが購入イベントの場合、体力を 800 増加させ、アイテムをアクティブとしてマークします。 
5. イベントが敵 x への攻撃である場合、まずアイテムが購入されているかどうかを確認します。 そうでない場合、攻撃は何も行いません。 
6. アイテムがアクティブな場合は、current_time - last_trigger[x] >= 30 という条件を使用して敵 x のクールダウンをチェックします。これが失敗した場合は、攻撃を無視します。 
7. クールダウンが許す場合、ダメージは 125 + Floor(0.06 * current_health) として計算されます。 
8. 回復力を床 (0.1 * ダメージ) として計算し、それを現在の体力に追加します。 
9. last_trigger[x] を現在時刻に更新します。 

重要な考え方は、健康状態の変化はその後のダメージ計算を含む後続のイベントに即座に影響を与えるため、適切に更新する必要があるということです。 

### なぜ効果があるのか

 シミュレーションはあらゆる瞬間において、イベント履歴によって暗示されるゲームの正確な状態 (現在の健康状態、アイテムの入手可能性、敵ごとのクールダウン ステータス) を維持します。 各イベントは、現在の状態とイベント自体にのみ基づいて、この状態を決定的に遷移させます。 イベントは時間の増加順に処理され、各更新はゲーム ルールと正確に一致するため、将来のイベントは未処理の情報に依存せず、正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def parse_time(s):
    mm, ss = s.split(":")
    return int(mm) * 60 + int(ss)

def solve():
    H1, H2, m = map(int, input().split())
    
    hp = H1
    item = False

    last = [-10**9] * 5

    for _ in range(m):
        parts = input().split()
        t = parse_time(parts[0])
        typ = int(parts[1])

        if typ == 2:
            hp += H2

        elif typ == 1:
            hp += 800
            item = True

        else:
            x = int(parts[2]) - 1
            if not item:
                continue
            if t - last[x] < 30:
                continue

            damage = 125 + int(0.06 * hp)
            heal = int(damage * 0.1)

            hp += heal
            last[x] = t

    print(hp)

if __name__ == "__main__":
    solve()
```実装はイベント駆動型構造に直接に従います。 時間はイベントごとに 1 回秒に変換されるため、複雑な解析を繰り返すことがなくなります。 

クールダウンチェックでは厳密な不等式が使用されます`t - last[x] < 30`これは、30 秒の最小ギャップを強制するのと同じです。 ヘルス依存の計算では、問題ステートメントの要求どおりに整数の切り捨てが使用されます。

 ## 特殊なケース

 重要なエッジケースの 1 つは、商品が購入される前に攻撃することです。 そのような状況では、たとえクールダウン ロジックで攻撃が許可されていたとしても、攻撃は完全に無視されなければなりません。 シミュレーションでは、以下をチェックすることでこれを処理します。`item`計算の前にフラグを立てます。 

もう 1 つのエッジケースは、まさにクールダウンの境界で攻撃が繰り返されることです。 攻撃が時間 t に発生し、別の攻撃が t + 30 に発生した場合、2 番目の攻撃がトリガーされる必要があります。 条件`t - last[x] < 30`厳密に小さいギャップのみを正しく拒否するため、等価性は合格します。 

最後のエッジケースは、複数のレベルアップと以前の回復後の現在の健康状態にダメージが依存することです。 体力は各イベントの直後に更新されるため、同じ 1 分間に複数のイベントが発生した場合でも、ダメージ計算式は常に攻撃の瞬間の正しい状態を反映します。
