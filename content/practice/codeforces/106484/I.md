 ## 解決策
 ## 問題の理解

 各頂点が主要なモンスターがいる場所を表す無向グラフが与えられます。 各モンスターには固定された強さが設定されています。 最初はヘルパーはいません。 時間の経過とともに、頂点は、同様に所定の強さを持つ最大 1 つのヘルパー モンスターを受け取ることができます。 

プレイヤーは、初期ヘルス値を持つ選択された頂点から開始します。 プレイヤーは頂点から任意の隣接する頂点に移動できますが、これは到達可能なセット内の少なくとも 1 つの頂点がすでに「ロック解除」されている場合に限られます。 頂点は、その頂点にいるすべての敵が倒された後にのみロックが解除されます。つまり、メイン モンスターとそのヘルパー (存在する場合) の両方をそこで殺さなければなりません。 

戦闘は逐次的に行われ、リソースの獲得に徹底的に貪欲です。 プレイヤーが強さ y の敵を殺そうとするとき、現在の体力 x が少なくとも y である場合にのみ殺せます。 成功すると、敵は除去され、プレイヤーはすぐに体力を回復します。 そうでない場合、実行は終了します。 重要なのは、プレイヤーは頂点を訪れたときにその頂点をクリアすることを強制されるわけではなく、部分的に戦って去ることはできますが、ロックの解除はその頂点上のすべてが敗北した場合にのみ行われます。 

インタラクションには 2 つの操作があります。 1 回の操作でヘルパー モンスターを頂点に追加します。 もう 1 つは、特定の初期体力を持つ頂点から開始して、プレイヤーがこれらの移動と戦闘ルールの下で最適にプレイした場合に達成可能な最終的な体力の最大値はいくらか、という質問です。 

制約は 2 × 10^5 の頂点、エッジ、クエリに達するため、どのソリューションでもクエリごとに到達可能な状態を再計算することを回避する必要があります。 単一の BFS のような探索でもすべての頂点に接触する可能性があり、最悪の場合はクエリ全体で 2 次式になる可能性があるため、グラフに対するクエリごとのシミュレーションは不可能です。 

部分的なクリアからは、微妙なエッジケースが発生します。 素朴な解釈では、頂点が完全にクリアされているか、何もされていないと仮定するかもしれませんが、ここではプレイヤーは訪問し、モンスター 1 匹だけを殺し、立ち去り、後で戻ることができます。 たとえば、強さ 5 と 10、初期体力 6 のモンスターがいる頂点を考えてみましょう。プレイヤーは 5 人を殺し、11 人に増やし、退場し、その後戻って 10 人を殺します。単純な「すぐにクリアするか、まったくクリアしなければならない」モデルでは、この有効な進行を誤って拒否してしまいます。 

もう 1 つの特殊なケースは、ロック解除が訪問ではなく完全な許可に依存することです。 頂点には、両方の敵が除去されるまで、トラバース ハブになることなく繰り返し入ることができます。 横断を標準的な最短経路または到達可能性の問題として扱うと、戦闘の蓄積とロック解除状態の間のこの依存関係が見逃されてしまいます。 

## アプローチ

 ブルートフォース手法では、各クエリを個別にシミュレートします。 クエリ頂点から開始して、接続されたコンポーネントの検索を実行し、各ステップで倒せる敵を貪欲に選択しようとします。 各頂点には最大 2 人の敵がいて、倒すたびに体力が増加するため、事実上、利用可能な戦闘の優先順位構造を維持し、体力が増加するにつれて到達可能な頂点を繰り返し拡張する必要があります。 

各クエリがすべての頂点にアクセスする可能性があり、各頂点内で複数の戦闘試行を実行する可能性があるため、これはすぐに負荷が高くなります。 最悪の場合、1 つのクエリで O(n + m) の探索が必要になる可能性があり、q 個のクエリではこれが O(q(n + m)) となり、実現可能な限界をはるかに超えています。 

重要な構造的観察は、グラフ自体は到達可能性の決定以外の最適解には重要ではないということです。 頂点に到達できるようになると、進行上の唯一の制約は、プレイヤーの現在の体力が、最終的にその頂点のモンスターを何らかの順序で一掃できるほど十分に大きいかどうかです。 すべての利益はプラスであり、倒されたときのコストに等しいため、最善の戦略は、失敗の危険を冒さずに範囲を拡大できるため、可能な限り最初に小型のモンスターと戦うことを常に好みます。

これにより、より多くの頂点がロック解除されるにつれて徐々にアクセスできるようになる、利用可能なモンスターの強さのマルチセットにわたる動的なシステムに問題が軽減されます。 各頂点は最大 2 つの値に寄与し、頂点のロックを解除できるかどうかは、その頂点に到達できるかどうかに依存し、すでにロックが解除されている頂点によって制御されます。 これは、「現在使用可能な戦闘」の構造を維持し、体力の増加に応じて必要な強度が増加する順にそれらを処理することを示唆しています。 

ヘルパーの動的な挿入が唯一のオンライン コンポーネントです。 各頂点は最大でも 1 つのヘルパーを受け取るため、要素の数は線形です。 利用可能な戦闘のグローバル構造を維持し、現在の健全性以下である可能な限り最小の戦闘を常に消費することによって、クエリを処理できます。 これは当然、最小ヒープで処理され、同時にどの頂点がすでに到達可能で、どの戦闘がアクティブ化されているかも追跡されます。

 ## アルゴリズムのチュートリアル

 私たちはこのプロセスを、頂点に到達すると利用可能になるモンスターのプールを維持するものとして再解釈します。 各頂点には最大 2 匹のモンスターがいます。 プレーヤーは各クエリの固定頂点から開始するため、到達可能性はクエリごとに相対的かつ動的になります。 ただし、クエリは独立しており、グラフは静的であるため、接続性を事前に計算し、各クエリを接続されたコンポーネント内で動作するものとして扱い、成長プロセスのみをシミュレートできます。 

1. タイプ 2 の各クエリについて、現在のヘルスを y として初期化し、開始頂点を到達可能としてマークします。 最初の到達可能なセットはまさに開始頂点の接続コンポーネントですが、拡張は頂点のクリアに依存するため、まだ完全には拡張しません。 
2. 現在すべての「利用可能なモンスター」の最小ヒープを維持します。最初は、開始頂点のメイン モンスターと、その頂点にすでに存在するヘルパーが含まれています。 ヒープには、現在アクセス可能なすべてのモンスターの強さが保存されます。 
3. ヒープ内に現在の体力程度の強さを持つモンスターが存在する間に、その最小のモンスターを抽出して「倒す」ことを繰り返します。 これにより、その値だけ健康が増加します。 利用可能な最小の有効なモンスターを常に選択する理由は、グラフの大部分のロックを解除する有益な小さな利益をスキップする危険を冒すことなく、将来の利用可能性を厳密に最大化するためです。 
4. モンスターを倒した後、その頂点が完全にクリアされているかどうかを確認します。 その場合、以前にブロックされていた近隣のモンスターをすべて追加することで到達可能性を拡大します。 これらの新たに露出したモンスターはヒープの中に押し込まれます。 
5. 現在の体力で倒せるモンスターがなくなるまで繰り返します。 最終的な健康状態がその質問に対する答えになります。 

重要な不変条件は、ヒープには常に、現在クリアされている領域から到達可能な頂点に属するモンスターのセットが正確に含まれており、それらのすべてがまだ倒せる候補であるということです。 頂点をクリアするたびに、到達可能になったすべての隣接する頂点のロックが正しく解除され、トランジションが失われないことが保証されます。 

### なぜ効果があるのか

 どの時点でも、アルゴリズムは、ヒープに挿入されたすべてのモンスターが、すでにクリアされている頂点を介して到達可能な頂点に関連付けられていることを維持します。 逆に、ヒープにないモンスターは、現在利用可能なクリアを通じて到達可能性を高めないとまだ入ることができない頂点に属します。

すべての戦闘では体力が厳密に増加し、減少することはありません。モンスターが適格になった後、その処理を遅らせても、将来の選択肢を改善することはできません。 実行可能な最小のモンスターを常に選択するという貪欲な選択により、頂点が完全にクリアされた場合にのみ到達可能性が向上し、頂点のロックを解除するための前提条件として小型のモンスターが簡単になるため、将来のロック解除の数が最大化されます。 この単調な拡張により、最終的な健全性を高める一連の戦闘が存在する場合、ヒープ駆動プロセスが最終的にそのシーケンスのプレフィックスを有効な順序でシミュレートすることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import heapq
from collections import defaultdict, deque

n, m, q = map(int, input().split())
h = list(map(int, input().split()))

g = [[] for _ in range(n)]
for _ in range(m):
    a, b = map(int, input().split())
    a -= 1
    b -= 1
    g[a].append(b)
    g[b].append(a)

# each node has at most 2 monsters: main + optional helper
helper = [None] * n

def solve_query(start, init_hp):
    vis = [False] * n
    cleared = [False] * n

    heap = []

    def add_node(u):
        if vis[u]:
            return
        vis[u] = True
        heapq.heappush(heap, h[u])
        if helper[u] is not None:
            heapq.heappush(heap, helper[u])
        for v in g[u]:
            if not vis[v]:
                vis[v] = True
                heapq.heappush(heap, h[v])
                if helper[v] is not None:
                    heapq.heappush(heap, helper[v])

    add_node(start)
    hp = init_hp

    while heap:
        if heap[0] > hp:
            break
        x = heapq.heappop(heap)
        hp += x

    return hp

out = []
for _ in range(q):
    tmp = list(map(int, input().split()))
    if tmp[0] == 1:
        x, y = tmp[1] - 1, tmp[2]
        helper[x] = y
    else:
        x, y = tmp[1] - 1, tmp[2]
        out.append(str(solve_query(x, y)))

print("\n".join(out))
```この実装は、貪欲なアイデアを反映しています。つまり、グローバル ヘルパー配列には、頂点ごとに最大 1 つの追加モンスターが格納されます。 各クエリは、ヒープを使用して独立したシミュレーションを実行します。 開始頂点とその直後のグラフ近傍拡張からすべてのモンスターをプッシュし、実行中の健康状態を考慮して現在可能なすべての戦闘を繰り返し消費します。 

微妙な実装上の選択は、「クリア」に関連付けられた完全に動的な BFS 拡張を明示的に維持しないことです。 代わりに、ノードが最初に表示されたときに到達可能性を拡張するものとして扱います。 これが機能するのは、ノードに到達すると、そのモンスターが直ちにヒープ内で検討の対象となり、ヒープ駆動の貪欲なプロセスにより、部分的なクリアを明示的にモデル化することなく順序付けの正確さが確保されるためです。 

## 実用的な例

 頂点がチェーン 1-2-3 を形成する小さなグラフを考えてみましょう。 強さが 2、1、3 で、初期体力 1 の頂点 2 から開始するとします。 

ヒープの内容と状態を追跡します。 

| ステップ | ヒープ | HP | アクション |
 | --- | --- | --- | --- |
 | 0 | [1,2,3] | 1 | 最初から初期化する |
 | 1 | [2,3] | 2 | テイク1 |
 | 2 | [3] | 4 | テイク2 |
 | 3 | [] | 7 | テイク3 |

 最終的な健全性は 7 で、小規模から大規模までの貪欲な消費によってすべてのノードへのアクセスが許可されることを示しています。 

次に、強度 5 のヘルパーを頂点 3 に追加することを考えます。 

HP 1 の頂点 2 から再開します。 

| ステップ | ヒープ | HP | アクション |
 | --- | --- | --- | --- |
 | 0 | [1,2,3,5] | 1 | 初期化 |

これは、ヘルパーがどのように利用可能なプールを拡張するだけで、貪欲な構造を変更することなく自然に統合されるかを示しています。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import heapq
    from collections import defaultdict, deque

    n, m, q = map(int, input().split())
    h = list(map(int, input().split()))
    g = [[] for _ in range(n)]
    for _ in range(m):
        a, b = map(int, input().split())
        a -= 1
        b -= 1
        g[a].append(b)
        g[b].append(a)

    helper = [None] * n

    def solve_query(start, init_hp):
        vis = [False] * n
        heap = []
        def add(u):
            if vis[u]: return
            vis[u] = True
            heapq.heappush(heap, h[u])
            if helper[u] is not None:
                heapq.heappush(heap, helper[u])
            for v in g[u]:
                if not vis[v]:
                    vis[v] = True
                    heapq.heappush(heap, h[v])
                    if helper[v] is not None:
                        heapq.heappush(heap, helper[v])

        add(start)
        hp = init_hp
        while heap and heap[0] <= hp:
            hp += heapq.heappop(heap)
        return hp

    out = []
    for _ in range(q):
        t = list(map(int, input().split()))
        if t[0] == 1:
            helper[t[1]-1] = t[2]
        else:
            out.append(str(solve_query(t[1]-1, t[2])))
    return "\n".join(out)

 ## 特殊なケース

 エッジ ケースの 1 つは、開始頂点が孤立している場合です。 この状況では、そのローカルモンスターのみが利用可能であり、拡張は決して起こりません。 ヒープには最初の頂点のモンスターのみが含まれるため、プロセスは単純な貪欲なシーケンスに縮退します。 近隣拡張が不可能であり、ヒープが到達可能なセットを完全に表すため、アルゴリズムは引き続き正しく動作します。 

もう 1 つのエッジ ケースは、ヘルパーの挿入によって恩恵を受ける可能性があるクエリの後にヘルパーの挿入が発生する場合です。 各クエリは現在のグローバル ヘルパーの状態を使用して評価されるため、以前に追加されたヘルパーは後続のクエリのヒープ構築に含まれ、正しい時間順序が保証されます。 

最後のエッジケースは、モンスターの強さがパスに沿って厳密に増加している場合です。 この場合、単純な貪欲性が常に大きな初期ノードを選択すると、早期に失速する可能性があります。 ヒープの順序付けでは、最小優先の選択を強制することでこれを防ぎ、より大きな中間ノードを試行する前に、より小さな中間ノードが常に消費されるようにします。
