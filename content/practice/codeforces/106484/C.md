 ## 解決策
 ## 問題の理解

 通常の FIFO 構造のように動作するキューを維持しますが、追加のルールが 1 つあります。それは、すべての値がいつでも最大 1 回出現できるということです。 格納できる値は 1 から m までの整数であり、この構造を変更またはクエリする Q 操作を処理します。 

操作は3つあります。 キューの最後に値を挿入しようとしますが、値がまだ存在しない場合にのみ成功します。 もう 1 つは、先頭の要素を削除します。これは、この操作が表示されるときにキューが空ではないことが保証されているため、常に有効です。 最後の操作では、現在キュー内にある x 番目の要素を前から後ろの順序で要求し、その位置が存在しない場合、答えは -1 になります。 

重要な点は、任意のコンテナをシミュレートするように求められるのではなく、一意性制約と位置クエリを備えたシーケンスをシミュレートするように求められることです。 Q ≤ 10^6 および m ≤ 10^6 という制約により、キューをスキャンしたり、操作ごとに線形検索によってメンバーシップをチェックしたりするアプローチは除外されます。 単一の O(n) 操作を Q 回繰り返したとしても、キュー サイズは最悪の場合 Q まで増大する可能性があるため、すぐに制限を超えてしまいます。 

単純な間違いは、キューを Python リストとして表し、次のように使用することです。`x in list`独自性を強化するため。 もう 1 つは、リストにインデックスを付けることでクエリに応答しますが、前から削除するとすべてがシフトされ、ポップごとに O(n) になることを忘れます。 

具体的な失敗例は、キューが大きくなり、クエリが頻繁に発生する場合に現れます。 

入力:

 1 1

 1 1

 1 2

 1 3

 ...

 3 100000

 単純なリストベースのソリューションでは、メンバーシップを繰り返しスキャンし、ポップ上の要素をシフトするため、タイムアウトが発生します。 

もう 1 つの微妙なバグは、一意性を無視することで発生します。重複を許可すると、最初の出現位置のクエリがあいまいになり、意図したモデルから逸脱してしまいます。 

## アプローチ

 ブルート フォース シミュレーションでは、キューが動的リストとして保持されます。 挿入では、リスト全体をスキャンして、値がすでに存在するかどうかを確認します。 見つからない場合は末尾に追加されます。 Pop は、スライスまたは Pop(0) によって最初の要素を削除し、インデックスを直接クエリします。 

操作を正確に反映しているため、正確性は簡単です。 問題はパフォーマンスです。 メンバーシップチェックには O(n) のコストがかかり、前方からのポップもシフトにより O(n) のコストがかかります。 Q が最大 10^6 で、キュー サイズが直線的に増加する可能性がある場合、総作業量は O(Q^2) となり、実現可能な制限をはるかに超えます。 

重要な観察は、変化する意味での「リスト構造」を実際に維持する必要はないということです。 要素の相対的な順序を保持し、一意の要素の追加、最も古い要素の削除、現在の順序でのインデックスによるアクセスの 3 つの操作をサポートするだけで済みます。 

これは、関心を分離することを示唆しています。挿入順序を表す固定配列内の要素を追跡し、先頭の移動ポインタを維持します。 要素を物理的に削除する代わりに、ヘッド インデックスを進めます。 一意性を強制するために、値が現在キュー内でアクティブであるかどうかを示すブール配列またはハッシュ セットを維持します。 これにより、すべての操作が O(1) に削減されます。 

キューはアレイ上の仮想ウィンドウとなり、コストのかかる削除がすべて削除されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(Q^2) | O(Q) | 遅すぎる |
 | 最適 | O(Q) | O(Q) | 承認済み |

 ## アルゴリズムのチュートリアル

 3 つの構造を維持します: 配列`arr`挿入された値を順番に保存するポインタ`head`現在のフロントとブール配列をマークする`in_queue`値が現在アクティブなキュー ウィンドウ内にあるかどうかを示します。 

1. 値 x による挿入操作の場合、最初に次のことを確認します。`in_queue[x]`は誤りです。 false の場合は、x を追加します。`arr`そしてマークを付ける`in_queue[x] = true`。 これにより、キューをスキャンしなくても一意性が保証されます。 
2. ポップ操作の場合、次のように移動します。`head`アクティブな要素を 1 つスキップするまで前進します。 具体的には、次の要素を取得します。`arr[head]`、キューにないものとしてマークし、インクリメントします`head`。 これは、各要素が 1 回だけ削除されるため、O(1) の償却時間でフロントを削除することをシミュレートします。 
3. x 番目の要素を要求するクエリ操作の場合、実際のインデックスを次のように計算します。`head + x - 1`。 このインデックスが現在の配列の長さを超えている場合は、-1 を出力します。 それ以外の場合は出力します`arr[index]`。 その理由は、アクティブなキューは常に処理された配列の連続したサフィックスであるためです。 

これが機能する理由は、すべての要素がすでにヘッド ポインターによって永続的にスキップされているか、まだアクティブなサフィックスの一部であるという不変条件に基づいています。`arr`。 厳密なアクティブ セット フラグを維持しているため、削除後に要素が構造に再び入ることはなく、要素が 2 回出現することもありません。 したがって、キューの状態は常にセグメントによって正確に表現されます。`arr[head : len(arr)]`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    Q, m = map(int, input().split())
    
    arr = []
    in_queue = [False] * (m + 1)
    head = 0
    
    out = []
    
    for _ in range(Q):
        tmp = input().split()
        t = int(tmp[0])
        
        if t == 1:
            x = int(tmp[1])
            if not in_queue[x]:
                arr.append(x)
                in_queue[x] = True
        
        elif t == 2:
            x = arr[head]
            in_queue[x] = False
            head += 1
        
        else:
            x = int(tmp[1])
            idx = head + x - 1
            if idx >= len(arr):
                out.append("-1")
            else:
                out.append(str(arr[idx]))
    
    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、挿入されたすべての値が増加する配列に格納され、左側から物理的に削除されることはありません。 の`head`ポインターは、コストのかかる deque ポップを置き換えます。 ブール配列では挿入時に O(1) メンバーシップ チェックが行われることが保証されるため、重複が追加されることはありません。 

微妙な点の 1 つは、私たちは決して萎縮しないということです`arr`。 これは意図的なものです。古い要素はメモリ内に残っていますが、それらは一度無視されます。`head`彼らを追い越します。 クエリは構造的な変更ではなく、インデックス演算のみに依存します。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、削除せずに同じ値を繰り返し挿入することです。 たとえば:

 入力:```
1 5
1 1
1 1
1 1
3 1
```このアルゴリズムでは、値 1 のインスタンスが 1 つだけ保持されます。`in_queue[1]`すべての繰り返しをブロックします。 キューの状態は`[1]`なので、クエリは 1 を返します。 

もう 1 つのエッジ ケースは、多数のポップの後に現在のサイズを超えるクエリを実行することです。 

入力:```
1 3
1 1
1 2
2
3 2
```ポップの後だけ`[2]`残っています。 2 番目の要素をクエリすると計算されます`head + 1`を超える`len(arr)`したがって、答えは -1 です。 ポインタベースの表現により、無効なメモリにアクセスすることがなくなります。 境界は純粋に算術的にチェックされます。 

最後のエッジ ケースは、すべての操作が挿入とそれに続くクエリである最大入力ストレスです。 物理的な削除は行われないため、配列は増加しますが、O(Q) メモリに対しては有効なままであり、すべてのクエリは一定時間内に解決されます。
