 ## 解決策
 ## 問題の理解

 長さが常に偶数である数字の文字列で表されるチケットが与えられます。 この文字列を 2 つの等しい半分に分割し、左半分の桁の合計が右半分の桁の合計と等しい場合、チケットは「バランスが取れている」とみなされます。 

このタスクは残高の確認とは異なります。 文字列の長さを変更せずに、指定された文字列の 1 桁だけを変更し、0 から 9 までの他の桁に置き換える必要があります。 この 1 つの変更の後、結果として得られる数値のバランスが取れるようにしたいと考えています。 考えられるすべての有効な結果の中で、辞書編集的に最小のものを出力する必要があります。 1 桁の変更でバランスが取れない場合、答えは -1 になります。

 重要な問題は、1 つの桁を変更すると、その桁自体の値と 2 つの半分の差の両方に影響があり、変更によって不均衡が修正される可能性があるすべての位置を考慮する必要があることです。

 この制約により、合計で最大 100 桁が許可されます。 これは、約 O(n^2 · 10) または O(n · 10 · 10) までの解は容易に十分に高速であることを意味します。 ただし、前処理を行わずに各位置の合計を繰り返し再計算するソリューションは、限界が小さい場合には依然として許容されます。

 元の数値がすでにバランスされている場合、微妙なエッジケースが表示されます。 その場合でも、正確に 1 桁を変更する必要があり、その後、新しい数値のバランスが取れていることを確認する必要があります。 たとえば、文字列はすでにバランスが取れているが、考えられるすべての 1 桁の変更によってバランスが崩れた場合、答えは -1 になります。

 もう 1 つの注意が必要な状況は、複数の有効な回答が存在する場合です。 辞書編集的な順序が必要であるため、昇順ですべての可能性を慎重にチェックしない限り、機能する最初の桁の変更を貪欲に選択することはできません。

 ## アプローチ

 ブルートフォース手法では、位置と置換桁の可能な限りの選択が試行されます。 変更候補ごとに、2 つの半分の合計を再計算し、それらが一致するかどうかを確認します。 これは簡単です。位置 i を数字 d に置き換えるシミュレーションを行い、O(n) で両方の半和を計算し、バランスを検証します。 候補が O(n · 10) あり、各チェックのコストが O(n) であるため、合計の複雑さは O(n^2 · 10) になります。 n が 100 までであればこれでも問題ありませんが、不必要に繰り返しが多くなります。

 重要な点は、毎回合計を最初から再計算する必要がないということです。 2 つの部分間の不均衡は 1 回で追跡できます。 数字を変更すると、左半分と右半分の差に与える影響は局所的であり、予測可能です。 数字が左半分にある場合、数字を増減すると左の合計がシフトします。 右半分についても同様ですが、バランス状態には逆の効果があります。 これにより、各チェックが O(1) に減ります。 

これが候補ごとに O(1) 更新になると、すべての位置と桁を効率的にスキャンでき、候補を順番に構築することで有効な結果の中から辞書編集的に最小のものを選択します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n² · 10) | O(n) | 許容範囲内だが遅い |
 | 最適化されたすべて試してみる | O(n · 10) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 元の文字列の左半分と右半分の数字の合計を計算します。 これにより、両側の間に初期の不均衡が生じます。 
2. 文字列内の各位置 i を左から右に繰り返します。 前の位置が辞書編集上の順序を支配するため、順序は重要です。 
3. 各位置 i について、現在の数字を元の数字を除く 0 ～ 9 の可能なすべての数字に置き換えてみます。 
4. 置換ごとに、この変更が左右の半分の和にどのような影響を与えるかを計算します。 位置が左半分にある場合は、古い数字を減算し、新しい数字を左の合計に加算します。 それ以外の場合は、同じ更新を正しい合計に適用します。 
5. 更新された左の合計が更新された右の合計と等しいかどうかを確認します。 一致する場合、候補文字列は有効です。 
6. 数字を昇順にスキャンするときに最初に見つかった有効な候補を追跡します。 位置を左から右に、桁を小さいものから大きいものに処理するため、最初の有効な候補が辞書編集的に最小になります。 
7. その候補を出力します。 候補が見つからなかった場合は -1 を出力します。 

### なぜ効果があるのか

 どのステップでも、変化する値は 2 つの半和のいずれかに対する 1 桁の寄与だけです。 弦の残りの部分は変更されないため、バランス状態は、事前に計算された差に対する一定の調整のみに依存します。 これにより、すべての候補の評価が独立し、局所的に正確になります。 辞書編集順は、昇順で最初に位置をスキャンし、次に数字をスキャンすることによって適用されるため、後の候補が以前の有効な候補をオーバーライドすることはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s) // 2
    arr = list(map(int, s))

    left_sum = sum(arr[:n])
    right_sum = sum(arr[n:])

    for i in range(2 * n):
        original = arr[i]

        for d in range(10):
            if d == original:
                continue

            if i < n:
                new_left = left_sum - original + d
                new_right = right_sum
            else:
                new_left = left_sum
                new_right = right_sum - original + d

            if new_left == new_right:
                arr[i] = d
                print("".join(map(str, arr)))
                return

    print(-1)

if __name__ == "__main__":
    solve()
```この解決策は、文字列を概念的に 2 つに分割し、それらの合計を 1 回計算することから始まります。 これにより、後で再計算を繰り返すことが回避されます。 

次に、各位置が個別にテストされます。 置換をシミュレートする場合、インデックスがどちらの半分に属するかに応じて、2 つの合計のうち 1 つだけが更新されます。 これがチェックを O(1) にする理由です。 

ループの順序は重要です。 インデックスを左から右に、数字を 0 から 9 まで繰り返すため、最初に成功した構築は自動的に辞書編集的に最小限になるため、候補を保存したり比較したりする必要はありません。 

よくある間違いは、配列を復元せずにその場で変更することですが、ここでは有効な答えが見つかった場合にのみ代入し、すぐに返すため、ロールバック ロジックは必要ありません。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、1 桁の変更が行われるたびにバランス状態が崩れる場合です。 たとえば、半分の差が大きすぎて 1 桁の変更で補正できない場合、アルゴリズムはすべての候補を網羅し、正しく -1 を返します。 

もう 1 つのケースは、複数のソリューションが異なる半分に存在する場合です。 スキャンでは以前のインデックスが優先されるため、両方のバランスが修正されている場合でも、左半分の有効な変更が辞書順で右半分の変更よりも常に優先されます。 この順序付けは正確性を保つために不可欠であり、完全な文字列間の明示的な比較を避けます。
