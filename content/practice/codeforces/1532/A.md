 ## 解決策
 ## 問題の理解

 一連の独立したクエリが与えられます。 各クエリは 2 つの整数で構成されており、すべてのペアについて算術合計を計算し、すぐに出力する必要があります。 

テスト ケース間に依存関係はありません。 各ペアは個別に処理できるため、問題は 1 つの定数時間操作を繰り返し適用することになります。 

この制約では、各整数の範囲が -1000 ～ 1000 である、最大 10,000 のテスト ケースが許可されます。これは、値の大きさが十分に小さいため、Python では整数のオーバーフローが問題にならず、低レベル言語でも 32 ビット整数で十分であることを意味します。 支配的な要因は、すべてのテスト ケースにわたる操作の数です。 

素朴な解釈では、中間構造を構築するか、処理前にすべての入力を保存することを示唆するかもしれませんが、問題にはそれが必要なものはありません。 テスト ケースごとに一定以上の作業を行うアプローチはここでも合格しますが、不必要なオーバーヘッドが発生します。 

エッジケースは最小限ですが、それでも認識する価値があります。 よくある間違いは、負の値を誤って処理したり、テスト ケースごとに改行を出力し忘れたりすることです。 

たとえば、次のように入力します。```
1
-1000 1000
```正しい出力は次のとおりです。```
0
```不用意に実装すると、数値の加算ではなく文字列の連結が試行され、`-10001000`これは入力を整数ではなく文字列として扱うため、正しくありません。 

## アプローチ

 ブルートフォース解釈では、各テスト ケースを読み取り、標準の算術演算を使用して合計を計算し、それを出力します。 各操作は O(1) であるため、合計作業量はテスト ケースの数に比例します。 

直接計算以外に利用できる構造はありません。 プレフィックスの再利用、並べ替え、グラフの走査はありません。 この問題は基本的に、入力パイプラインと出力フォーマットが正しいかどうかの健全性チェックです。 

唯一意味のある「最適化」は、高速な入力解析を確保し、ループ内での不必要な変換や文字列操作を回避することです。 したがって、最適なソリューションは、アルゴリズム構造において総当たりアプローチと同じであり、実装のクリーンさと I/O 効率のみが異なります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | ブルート フォース (テスト ケースごとの直接合計) | O(t) | お(1) | 承認済み |
 | 最適 (高速 I/O + 直接加算) | O(t) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 整数を読み取る`t`、実行する必要がある独立した加算の数を定義します。 これにより、メイン ループの反復回数が決まります。 

2. テスト ケースごとに 2 つの整数を読み取ります。`a`そして`b`入力から。 解析ステップにより、値が文字列ではなく数値として解釈されるため、算術演算が正しく動作します。 

3. 合計を計算します`a + b`。 これはテスト ケースごとに必要な唯一の変換であり、問​​題ステートメントに直接対応します。 

4. 結果をすぐに印刷し、必要な形式を維持するために各出力がそれぞれの行に表示されるようにします。 

### なぜ効果があるのか

 各テスト ケースは独立しており、単一の算術式を定義します。 加算演算は決定的であり、副作用はありません。 各結果を正確に 1 回計算して出力するため、アルゴリズムは入力と出力の間の 1 対 1 のマッピングを保持します。 隠れた状態やテスト ケース間の相互作用がないため、正しさは整数加算の正しさから直接得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    t = int(input())
    out = []
    for _ in range(t):
        a, b = map(int, input().split())
        out.append(str(a + b))
    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    main()
```このソリューションは、高速バッファー I/O を使用して入力を読み取ります。これは、最大 10,000 行を処理する場合に重要です。 各行は 2 つの整数に分割され、それらの合計が出力リストに追加されます。 印刷前に結果を蓄積するという決定により、コストのかかる書き込み操作を繰り返す必要がなくなります。 

よくある間違いは、次を使用してループ内で印刷することです。`print`ここではまだ許容可能ですが、制約が厳しい場合は遅くなります。 もう 1 つの潜在的な問題は、入力文字列を整数に変換するのを忘れることです。その場合、数値の加算ではなく文字列の連結が発生します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 |---|---|---|
 | 時間 | O(t) | 各テスト ケースは、単一の加算と定数時間の I/O 解析を実行します。 
| スペース | O(t) | 出力ストレージには、印刷前にテスト ケースごとに 1 つの文字列が保持されます。 

この制約では最大 10,000 回の操作が可能で、各操作は一定時間であるため、ソリューションは制限内で快適に実行されます。 出力リストのみが保存されるため、メモリ使用量も最小限に抑えられます。 

## テストケース```python
import sys, io

def solve():
    input = sys.stdin.readline
    t = int(input())
    out = []
    for _ in range(t):
        a, b = map(int, input().split())
        out.append(str(a + b))
    return "\n".join(out)

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return solve()

# provided samples
assert run("4\n1 5\n314 15\n-99 99\n123 987\n") == "6\n329\n0\n1110"

# minimum input
assert run("1\n0 0\n") == "0"

# all negative
assert run("2\n-1 -2\n-1000 -1000\n") == "-3\n-2000"

# mixed signs
assert run("3\n1 -1\n10 -3\n-7 20\n") == "0\n7\n13"

# boundary values
assert run("2\n1000 1000\n-1000 1000\n") == "2000\n0"
```| テスト入力 | 期待される出力 | 検証内容 |
 |---|---|---|
 | 単一のゼロペア | 0 | 最小限の入力処理 |
 | すべての否定 | -3、-2000 | 符号の正しさ |
 | 混合標識 | 0、7、13 | ケース間の算術的正確性 |
 | 境界値 | 2000年0 | 制約制限 |

 ## 特殊なケース

 最も単純なエッジケースは、両方の数値がゼロの場合です。 入力：```
1
0 0
```アルゴリズムは両方の整数を読み取り、計算します`0 + 0`、および出力`0`。 特別な分岐は必要なく、他のすべての場合と同じロジックが適用されます。 

別のケースには、次のような制約範囲内の極端な値が含まれます。```
1
-1000 1000
```ここで、合計はちょうどゼロになります。 このアルゴリズムは整数の直接加算を実行するため、Python ではオーバーフローや精度損失のリスクがなく、追加の処理を行わなくても出力は正しいままです。
