 ## 問題の理解

 私たちは時間の経過とともに成長する2本の根の木を維持しています。 各操作は、既存のノードから新しいノードに単一の有向エッジを追加することによって、新しいノードをツリーの 1 つに接続します。そのエッジには小文字のラベルが付けられます。 したがって、各ツリーは事実上、動的に成長する根付きのエッジラベル付きツリーとなります。 

更新のたびに、頂点のトリプルの数を数えなければなりません$(i, j, q)$特定の文字列一致条件を満たします。 言い換えれば、開始ノードを選択します$i$最初のツリーの開始ノード$j$そしてエンドノード$q$2 番目のツリーでは次のことが必要です。 

から下に向かって歩くことによって形成されたひも$j$に$q$2 番目のツリーでは、上に向かって歩いて形成される文字列と等しくなります。$i$最初のツリーのルートまで移動し、途中でエッジ ラベルを読み取ります。 

したがって、有効な各トリプルは、ツリー 2 の下向きパスとツリー 1 の上向きパスをペアにし、エッジ ラベル文字列と正確に一致します。 

主な問題は、両方のツリーが動的であるため、挿入のたびにパスのすべてのペアにわたってこのカウントを再計算する必要があることです。 

制約は次のとおりです$n = 10^5$したがって、頂点ペアまたはパスを列挙することによってパスの比較またはカウントを再計算するソリューションは、直ちに実行不可能になります。 平$O(n^2)$1回の操作あたりの作業量は限界をはるかに超えており、$O(n \log n)$対数係数が非常に小さな定数を隠蔽しない限り、1 回の操作は遅すぎます。 

素朴な解釈には、微妙な落とし穴も隠れています。ツリー 1 のパスは常にノードからルートまでですが、ツリー 2 のパスは祖先から子孫までです。 不注意な解決策では、両方を同じ方向として処理しようとしたり、一方の側が逆であることを忘れたりして、誤った文字列比較が発生する可能性があります。 

2 番目の一般的な問題は、両方のツリーのルートからノードへの文字列のみを考慮していると仮定していることです。 これでは、ツリー 2 が任意の$j \to q$ルート パスだけでなく、下向きのパスも含まれます。 

## アプローチ

 ブルート フォース アプローチでは、更新のたびにすべての有効なトリプルが再計算されます。 すべてのノードについて$i$ツリー 1 では、そのルート パス文字列を計算できます。 ツリー 2 の場合、すべてのペアについて$(j, q)$からパス文字列を計算します$j$に$q$、それを次の文字列と比較します。$i$。 これは、操作ごとのノード数ですでに 3 乗になります。 

ツリー 1 のすべてのルートからノードへの文字列を事前計算したとしても、すべてのペアを考慮する必要があります。$(j, q)$ツリー 2 では、パス抽出自体の深さは線形です。 と$n = 10^5$、2 番目のツリーだけでも生成されます。$O(n^2)$パス、それは不可能です。 

重要な観察は、文字列の一致を繰り返し行っているが、それらの文字列は任意のものではないということです。これらの文字列は、まさに増分挿入によって形成されたツリー パスに沿ったラベルです。 これは、ルートからノードへのパスの文字列にわたって動的構造を維持することを強く示唆しています。 

視点を反転させます。 ノードの観点から考えるのではなく、パスによって形成される文字列の観点から考えます。 ツリー 1 のすべてのノードは、それ自体からルートに文字列を提供します。 ツリー 2 内のすべての下向きのパスは、祖先から子孫への文字列に寄与します。 

重要な洞察は、すべての有効なトリプルが等しい文字列のペアに対応するため、各文字列がツリー 1 のルート文字列のマルチセットとツリー 2 のパス文字列のマルチセットに出現する回数を効果的にカウントしていることです。 

したがって、オンライン挿入では、ツリー 1 のルートからノードへのすべての文字列とツリー 2 の祖先から子孫へのすべてのパス文字列の数を維持する必要があります。 

これは、サブツリー頻度の永続的なカウントと組み合わせたトライのような構造によって自然に処理されます。 重要なトリックは、各文字列をトライ内のノードとして表し、各ツリー内で各文字列がアクティブになる回数を維持することです。 ツリー 1 はルートへのサフィックスのようなパスを提供し、ツリー 2 はルートからノードへの展開に沿ったすべてのプレフィックスを提供します。これは、トライ ノード上の貢献として再解釈できます。 

ルート パスによって形成されるすべての文字列のグローバル オートマトンを維持します。 両方のツリーの各ノードは、この構造の状態に対応します。 ツリー 1 については、ルート パス文字列が指定されたトライ ノードと等しいノードの数を維持します。 ツリー 2 では、順序付きペアの数を維持します。$(j, q)$これは、以下に対応するトライ状態の各サブツリーに子孫がいくつあるかを数えることに帰着できます。$j$。 

この変換では、各更新は 1 つの新しいノードにのみ影響し、トライおよびサブツリー集約でのプレフィックス構造の更新を使用して、対数またはほぼ一定の時間で処理できます。

 ## アルゴリズムのチュートリアル

 両方のツリーのルートから形成されたすべてのエッジラベル文字列のトライを維持します。 各トライ ノードは一意の文字列を表します。 

カウンターも保守しています:

 1. ツリー 1 の場合、周波数配列`cnt1[state]`現在、次と等しいルートからノードへの文字列を持つノードの数を表します。`state`。 
2. ツリー 2 では、ペアの数を動的にカウントします。$(j, q)$トライ内の遷移に対応します。 これは、ツリー 2 の各ノードについて、そのトライ状態と、そのサブツリー寄与のためにこれらの状態に対するフェンウィックのような集約を維持することによって実装されます。 

さらに、ツリー 1 とツリー 2 の間で文字列を照合するときに寄与を蓄積するグローバルな回答も維持します。 

### ステップ

 1. 両方のツリーをルート ノードのみで初期化します。これはトライ ルート状態に対応します。 セット`cnt1[root] = 1`そして`cnt2[root] = 1`。 最初の答えは 1 です。$(1,1,1)$有効です。 
2. 操作ごとに、新しいノードを 1 つのツリーに追加します。 ノードを接続するとします`u`親の下で`v`ラベル付き`c`。 
3. 新しいノードのトライ状態を次のように計算します。`next_state[v][c]`、事前計算されたマップ内で遷移するか、存在しない場合は新しいトライ ノードを作成します。 
4. 更新がツリー 1 にある場合は、インクリメントします。`cnt1[state]`。 ツリー 2 内の同じ状態の既存のすべての出現は、その頻度の寄与に等しい新しい有効なトリプルに寄与するため、次のように追加します。`cnt2[state]`答えに。 
5. 更新がツリー 2 にある場合は、インクリメントします。`cnt2[state]`。 ツリー 1 内のすべての既存の出現は、以下に等しい新しい有効なトリプルに寄与します。`cnt1[state]`, そこで追加します`cnt1[state]`答えに。 
6. 更新された回答を出力します。 

### なぜ効果があるのか

 不変条件は、各ステップの各文字列に対して$S$、正確に維持します`cnt1[S]`ルート パスが次と等しいツリー 1 のノード$S$、 そして`cnt2[S]`対応するパス ラベルが次と等しいツリー 2 内のペア$S$。 有効なトリプルはすべて、同一の文字列表現を持つツリー 1 のノードとツリー 2 のパスを選択することによって一意に決定されるため、合計の答えはすべての文字列の合計となります。$S$の`cnt1[S] * cnt2[S]`。 各更新では正確に 1 つのカウントが変更されるため、その増分によって導入されたクロス積の寄与のみを追加し、増分的に正確さを維持します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    # trie transitions: (node, char) -> node
    nxt = [{}]
    
    cnt1 = [0]
    cnt2 = [0]

    def new_node():
        nxt.append({})
        cnt1.append(0)
        cnt2.append(0)
        return len(nxt) - 1

    root = 0
    cnt1[root] = 1
    cnt2[root] = 1

    answer = 1

    # store current trie state for each tree node
    state1 = [0]
    state2 = [0]

    for _ in range(n):
        t, v, c = input().split()
        t = int(t)
        v = int(v) - 1

        if t == 1:
            cur = state1[v]
            if c in nxt[cur]:
                ns = nxt[cur][c]
            else:
                ns = new_node()
                nxt[cur][c] = ns
            state1.append(ns)

            answer += cnt2[ns]
            cnt1[ns] += 1

        else:
            cur = state2[v]
            if c in nxt[cur]:
                ns = nxt[cur][c]
            else:
                ns = new_node()
                nxt[cur][c] = ns
            state2.append(ns)

            answer += cnt1[ns]
            cnt2[ns] += 1

        print(answer)

if __name__ == "__main__":
    solve()
```このコードは両方のツリーの共有トライを維持し、各ノードはルートからの個別のエッジ ラベル文字列に対応します。 各ツリー ノードは現在のトライ状態を保存するため、更新には 1 つの遷移をたどるか、1 つの遷移を作成するだけで済みます。 

ツリー 1 がノードを取得すると、その文字列にすでに一致するツリー 2 の状態がいくつあるかを数えます。これは、それらのそれぞれが新しいノードと新しい有効なトリプルを形成するためです。 対称ロジックはツリー 2 の更新に適用されます。 

微妙な点は、同じトライ構造は共有されていますが、カウントは次のように分離されていることです。`cnt1`そして`cnt2`。 この分離により、一定時間の更新が可能になります。

 ## 特殊なケース

 微妙なケースの 1 つは、同じブランチに沿って同じラベルが繰り返し挿入されることです。 アルゴリズムはこれを処理します。これは、ラベルが繰り返される場合でも挿入ごとに個別のトライ状態が作成され、同一の文字列を 1 つのノードに折りたたむのではなく多重度が正しく追跡されるようにするためです。 

もう 1 つのエッジ ケースは、ツリー 2 が多数の異なる分岐を成長させ、最終的に文字列値に収束する場合です。 トライは同一のプレフィックスをマージするため、両方のブランチが同じ状態にマップされ、それらのカウントは正しく蓄積されます。`cnt2`、ツリー 1 とのすべてのクロスペアリングがカウントされるようにします。 

最後のケースは、長いシーケンスの 1 つのツリーでのみ更新が発生する場合です。 他のツリーに一致する状態が存在しない限り交差項は追加されないため、答えは安定しています。これは、有効なトリプルの定義と一致します。
