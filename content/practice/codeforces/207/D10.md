 ## 解決策
 ## 問題の理解

 ドキュメントのストリームが与えられます。各ドキュメントは名前と本文で構成される短いテキストです。 各ドキュメントは、3 つの非表示クラスのいずれかに正確に属します。 トレーニング中に、これら 3 つのクラスのドキュメントのラベル付きデータセットが存在しますが、実際のタスクでは識別子フィールドは無関係であり、トレーニング識別子はテスト識別子と一致しません。 

このタスクは、3 つのラベルを持つ古典的なテキスト分類問題に帰着します。 各入力インスタンスは小さなドキュメント (最大 10KB) であり、それが 3 つのサブジェクト クラスのどれに属するかを決定する必要があります。 

この制約は、ソリューションが任意のテキストを効率的に処理する必要があり、すべてのトレーニング ドキュメントと単純に比較するなど、ドキュメントごとの大量の計算に依存できないことを意味します。 トレーニング コーパスが大きい場合、トレーニング セットに対するブルート フォース類似性スキャンは遅すぎます。これは、各テスト ドキュメントですべてのトレーニング ドキュメントをスキャンし、フルテキスト コンテンツを比較する必要があるためです。 

微妙な問題は、識別子フィールドが無意味であることです。 これを機能として組み込む単純な実装ではノイズが発生します。 もう 1 つのよくある落とし穴は、正規化せずにドキュメント全体を単一の文字列として扱うことです。 空白、大文字と小文字、または句読点の違いにより、トークン統計が変化し、頻度ベースのモデルの分類品質が低下する可能性があります。 

エッジケースには、非常に短い文書 (おそらくタイトル行と最小限のテキストのみ) や、冠詞や前置詞などの非常に一般的な単語が大半を占める文書が含まれます。 ストップワードを無視しない単純な分類器は、意味のあるコンテンツではなく、より冗長なトレーニング サンプルを持つクラスに誤って偏る可能性があります。 

## アプローチ

 直接的な総当たり戦略は、テスト ドキュメントをすべてのトレーニング ドキュメントと比較し、たとえばトークンの重複や編集距離を使用して類似性スコアを計算することです。 T 個のトレーニング ドキュメントがあり、各比較のコストが O(L) (L がドキュメントの長さである場合) の場合、1 つのテスト ドキュメントの分類には O(T · L) のコストがかかります。 複数のテスト ケースを使用すると、これはすぐに実行不可能になります。 

重要な点は、実際にはドキュメントレベルの比較が必要ないということです。 どのクラスがドキュメントを生成したかを推定するだけで済みます。 これにより、問題は単語のクラス条件付き尤度の推定に変換されます。 すべてのトレーニング ドキュメントをクラスごとに集約すると、3 つの主題それぞれのトークンに対する頻度モデルを構築できます。 

これは、多項単純ベイズ分類器に直接つながります。 各クラスは単語の確率分布を定義します。 テスト文書の場合、各クラスで文書の尤度を計算し、事後スコアが最大となるクラスを選択します。 クラスが 3 つしかないため、評価はクラスの数が一定であり、ドキュメント内のトークンの数が線形です。 

トレーニング フェーズは、クラスごとの単語数を計算するために、すべてのトレーニング データに対する 1 回のパスになります。 推論フェーズは、トークンごとの対数確率の単純な累積になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースドキュメントマッチング | クエリあたり O(T·L) | O(T・L) | 遅すぎる |
 | ナイーブ ベイズ テキスト分類 | クエリごとの O(L) | O(V) | 承認済み |

 ## アルゴリズムのチュートリアル

 3 つのクラスごとに確率的言語モデルを構築することで、この問題を解決します。

1. トレーニング コーパスを読み、すべてのドキュメントをクラス ラベルごとにグループ化します。 クラスごとに、各トークンの出現をカウントする辞書を維持します。 これは、単語がそのクラスに属する可能性を推定するために必要です。 
2. トレーニング ドキュメントの処理中に、空白で分割して各ドキュメントを単語にトークン化します。 各ワードは、対応するクラスの頻度カウンタを更新します。 また、後で確率を正規化するために、クラスごとの合計トークン数も追跡します。 
3. トレーニング後、クラス事前分布を計算します。 この問題のほとんどの構成では、データセットのバランスが設計によって保たれているため、事前分布は均一であるか、クラスごとのドキュメント数から導出される可能性があります。 
4. 各テスト ドキュメントについて、トレーニングと同じ方法でトークン化します。 
5. クラスごとに、対数事前確率で初期化されたスコアを計算します。 次に、ドキュメント内のすべてのトークンについて、そのトークンの対数確率をクラスの下に追加します。 目に見えない単語の確率がゼロになることを避けるために、ラプラス平滑化を適用します。 
6. 累積スコアが最大のクラスを選択し、そのラベルを出力します。 

ラプラス平滑化が必要な理由は、そうしないと、単一の未認識の単語によってクラスの確率がゼロになり、そのクラスが誤って完全に削除されてしまうためです。 

### なぜ効果があるのか

 中心となる不変条件は、各クラスがその単語分布の一貫した経験的推定を維持し、スコアリング関数が観察された文書がその分布によって生成された可能性がどの程度あるかを評価することです。 対数確率は加算的であるため、アルゴリズムは数値アンダーフローを発生させることなく、結合尤度によってクラスを正しくランク付けします。 この決定ルールは、クラスを条件とした単語の独立性のナイーブ ベイズの仮定に基づく最大事後分類に相当します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import math
    from collections import defaultdict

    data = sys.stdin.read().splitlines()
    doc_id = int(data[0])
    tokens = " ".join(data[1:]).split()

    # synthetic minimal model
    word_counts = [
        defaultdict(int, {"a": 5, "b": 1}),
        defaultdict(int, {"c": 5, "d": 1}),
        defaultdict(int, {"e": 5, "f": 1}),
    ]
    total = [6, 6, 6]
    vocab = 10

    best = -1e18
    ans = 1

    for c in range(3):
        score = 0.0
        denom = total[c] + vocab
        for w in tokens:
            score += math.log((word_counts[c][w] + 1) / denom)
        if score > best:
            best = score
            ans = c + 1

    return str(ans)

# minimal content skew
assert run("1\na b") in {"1", "2", "3"}

# class-specific dominance
assert run("2\na a a") == "1"

# different class dominance
assert run("3\nc c c") == "2"

# unseen tokens test
assert run("4\nx y z") in {"1", "2", "3"}

 ## 特殊なケース

 主なエッジケースは、ドキュメントに目に見えない単語のみが含まれている場合です。 平滑化を行わないと、すべてのクラス確率がゼロになり、分類器はクラスを区別できなくなります。 ラプラス平滑化を使用すると、目に見えない各トークンが小さいながらもゼロではない確率に寄与するため、クラス間の比較を意味のあるものに保つことができます。 

もう 1 つの特殊なケースは、単一の単語などの非常に短いドキュメントです。 その場合、分類はクラス間でのその単語の相対的な平滑化された頻度によって完全に決定されます。 このアルゴリズムは、単一の尤度比を比較することに正確に帰着しますが、それでも確率モデルの下で正確性が維持されます。
