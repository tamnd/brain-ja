 ## 解決策
 ## 問題の理解

 私たちは、Codeforces の評価が時間の経過とともにどのように変化し、その評価が目に見えるタイトルにどのように変換されるかをシミュレーションしています。 各ユーザーは初期評価から開始し、コンテストによって引き起こされる一連の評価変更を経ます。 各変更の後、評価はいくつかの固定間隔のいずれかに分類され、各間隔は初心者、生徒、エキスパートなどの特定のタイトルに対応します。 

タスクは、評価の完全な履歴を追跡することではなく、_タイトル カテゴリ_ がいつ変更されたかを検出することだけです。 コンテスト前のタイトルがコンテストの評価変更を適用した後のタイトルと異なる場合は、「old_title -> new_title」という形式で遷移を出力する必要があります。 テスト ケースのすべてのコンテストを処理した後、最終タイトルも出力します。 

制約は小さく、テスト ケースは最大 100 件、各テスト ケースには最大 100 件の評価更新があります。 これは、操作の合計数が最大 10,000 であることを意味します。 各更新を一定時間で処理するソリューションであればどれでも十分です。 更新のたびにタイトルを最初から繰り返し再計算しても問題ありません。 

微妙な点は、評価の変更が 1 つのステップで複数の境界を越える可能性があることです。 たとえば、いくつかのタイトル バンドをスキップして、レーティングが 1500 から 2500 に直接ジャンプする場合があります。 このような場合、中間の遷移ではなく、そのステップの開始タイトルから更新後の最終タイトルまでの遷移を 1 つだけ出力します。 

もう 1 つのエッジ ケースは、評価が開始され、複数の更新にわたって同じブラケット内に留まる場合です。 その場合、数値評価が変化しても、それらのステップについては何も出力されません。 

## アプローチ

 問題を解決する直接的な方法は、各コンテストの後にレーティングをシミュレートし、レーティングがどの区間に該当するかを確認して、対応するタイトルを再計算することです。 可能な間隔は 10 個だけであるため、この検索は定数時間になります。 

この総当りシミュレーションは、すでに構造上の最適なアプローチと一致しています。 更新ごとに、レーティングを調整し、しきい値テーブルをスキャンしてタイトルを再計算し、前のタイトルと比較します。 それらが異なる場合は、遷移を出力します。 

状態空間が小さく、各ステップが独立しているため、隠れた最適化は必要ありません。 唯一の意味のある作業は、評価からタイトルへのマッピングを維持し、それが変更されたときに追跡することです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ステップごとに再計算 | テストあたり O(n) | お(1) | 承認済み |
 | 複数のテストでも同じ | O(合計 n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### タイトルマッピング

 まず、固定しきい値を最高から最低までチェックすることによって、評価値を対応するタイトルに変換する関数を定義します。 

### ステップ

 1. 初期評価から始めて、その初期タイトルを計算します。 これは比較する前のタイトルになります。 
2. 定格が変更されるたびに、指定されたデルタを追加して現在の定格を更新します。 これはコンテストの結果をモデル化したものです。 
3. しきい値マッピングを使用して、更新された評価から新しいタイトルを計算します。 このステップでは、数値状態をカテゴリ状態に変換します。 
4. 新しいタイトルと前のタイトルを比較します。 異なる場合は「previous_title -> new_title」と出力します。 これは、同じブラケット内の内部評価の変動を無視し、目に見える推移のみをキャプチャします。 
5. 前のタイトルを新しいタイトルに更新して続行します。 
6. すべてのコンテストを処理した後、最終タイトルをもう一度出力します。 

### なぜ効果があるのか

評価からタイトルへのマッピングは、整数行を互いに素な間隔に分割したものです。 すべての評価は 1 つのタイトルに正確に対応し、各更新はこのパーティション内の現在の位置にのみ影響します。 前のタイトルだけを覚えておくことで、変化を検出するために必要な情報がすべて保存されます。これは、2 つの連続する評価が異なる間隔に該当するときに遷移が正確に発生するためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def get_title(r):
    if r >= 3000:
        return "Legendary grandmaster"
    if r >= 2600:
        return "International grandmaster"
    if r >= 2400:
        return "Grandmaster"
    if r >= 2300:
        return "International master"
    if r >= 2100:
        return "Master"
    if r >= 1900:
        return "Candidate master"
    if r >= 1600:
        return "Expert"
    if r >= 1400:
        return "Specialist"
    if r >= 1200:
        return "Pupil"
    return "Newbie"

t = int(input())
out_lines = []

for _ in range(t):
    n, k = map(int, input().split())
    rating = k
    prev = get_title(rating)

    for _ in range(n):
        rating += int(input())
        cur = get_title(rating)
        if cur != prev:
            out_lines.append(f"{prev} -> {cur}")
            prev = cur

    out_lines.append(prev)

print("\n".join(out_lines))
```実装の中核となるのは、`get_title`この関数は、最初の一致が常に正しいように評価間隔を降順でエンコードします。 これにより、複雑なデータ構造が必要なくなります。 

遷移は純粋にカテゴリのメンバーシップに依存するため、以前の評価ではなく、前のタイトル文字列のみを保存します。 各更新では評価が調整され、カテゴリが再計算され、条件付きで遷移が出力されます。 

出力には各コンテスト後の状態が記述されているため、新しいタイトルを計算する前にレーティングの更新を適用するように注意する必要があります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(T・n) | 各評価更新では、定数時間のタイトル ルックアップが再計算されます。

assert run("1\n1 1000\n0\n") == "Newbie", "min size"

# single upward transition
assert run("1\n1 1190\n20\n") == "Newbie -> Pupil\nPupil", "boundary up"

# multiple transitions in one jump
assert run("1\n1 1500\n1000\n") == "Pupil -> Master\nMaster", "skip bands"

# down crossing
assert run("1\n2 2100\n0\n-1000\n") == "Master -> Candidate master\nCandidate master", "downward change"

# oscillation
assert run("1\n3 1300\n100\n-100\n100\n") == "Pupil -> Specialist\nSpecialist -> Pupil\nPupil -> Specialist\nSpecialist", "oscillation"

 ## 特殊なケース

 一般的なエッジ ケースは、まさに境界上で開始されることです。 たとえば、評価 1200 は、まさに初心者と生徒の境界です。 1200 が初心者ではなく生徒として分類されるように、マッピングは正しい不等号順序で実装する必要があります。 アルゴリズムは、しきい値を最高から最低までチェックし、包括的な下限を使用することでこれを処理します。 

もう 1 つのケースは、多くのブラケットにまたがる大規模な 1 つの更新です。 たとえば、1500 から開始して +2000 を追加すると、トップ カテゴリに直接ジャンプします。 中間カテゴリは明示的に追跡されないため、アルゴリズムは引き続き最終カテゴリのみを計算し、単一の遷移を出力します。 

最後のケースは、すべての更新にわたって移行が発生しない場合です。 この状況では、「古い -> 新しい」イベントがトリガーされないため、最後のタイトルのみが出力されます。
