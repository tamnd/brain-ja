 ## 解決策
 ## 問題の理解

 いくつかの独立したシナリオが与えられています。 各シナリオには、$n$人々と$n+1$飾りの入った箱。 箱$0$特別であり、人それぞれ$i$専用のボックスがあります$i$。 各ボックスはいくつかの装飾品から始まります。 

の順列が何回あるかを数えなければなりません$n$人々は周期的なプロセスを繰り返すための「安全なスケジュール」を持っています。 順列は人々が行動する順序を定義します:$p_1$、 それから$p_2$、 …、 それから$p_n$、その後シーケンスが再び繰り返されます$p_1$、すべての装飾がボックスから取り出されるまで無期限に続きます。 

人が行動するとき、装飾品を 1 つだけ取らなければなりませんが、どちらかの箱からのみ取ることができます。$0$または独自のボックス。 各ステップで 2 つのボックスのどちらから取得するかを選択できるため、このプロセスは柔軟ですが、現在の人が取得できる有効なボックスを持たないステップ、つまり両方のボックスから取得するステップに到達しないようにする必要があります。$0$その時点では個人ボックスは空です。 

このタスクは、すべての装飾が使い果たされるまで、プロセス全体を通じて、装飾を取得する少なくとも 1 つの有効な選択肢が許可される順列の数を数えることです。 

重要な問題は、並べ替えによって実際の選択肢が修正されるのではなく、順序のみが修正されることです。 実現可能性は、行き詰まることなく、利用可能な共有リソースまたはプライベート リソースを通じて各消費ステップを常に「ルーティング」できるかどうかによって決まります。 

制約によって与えられるのは、$n \le 50$、最大 5000 のテスト ケース。 これにより、非常に小さいものを超える各テスト ケースの順列の階乗列挙が即座に除外されます。$n$、 以来$50!$天文学的に大きいです。 単一の順列をチェックするだけでも、最大で次のシミュレーションが必要です。$\sum a_i$ステップは最大で大きくなる可能性があります$5 \cdot 10^7$最悪のケースではテスト ケースごとに実行されるため、順列ごとのシミュレーションは不可能です。 

ボックス化するとエッジケースが発生します$0$プライベートボックス間の競合を「バッファ」するには小さすぎます。 たとえば、すべてが$a_i = 0$のために$i > 0$、箱のみ$0$が存在し、誰もがボックス 0 にしか触れないため、あらゆる順列が有効です。一方、ボックスの場合は、$0$がゼロであり、複数のプライベート ボックスが存在する場合、2 人の連続する必要なユーザーが交代できず、システムがスタックする状況を簡単に構築できます。 

微妙な失敗モードは、各人がいずれかのボックスに少なくとも 1 つのアイテムを個別に必要としていると仮定することです。 これは誤りです。なぜなら、可用性は時間の経過とともに進化し、ボックス 0 は共有され、選択肢間にグローバルな結合が生じるからです。 

## アプローチ

 ブルートフォースソリューションでは、すべてが列挙されます。$n!$順列を作成し、順列ごとに装飾を削除するプロセスを段階的にシミュレートし、常に貪欲に、またはボックス間の選択をバックトラックします。$0$そしてプライベートボックス。 これは正確な実現可能条件を調査するため、原理的には正しいですが、各シミュレーションには時間がかかる場合があります。$O(\sum a_i)$、そして、あります$n!$順列があり、全体の複雑さは、たとえ$n = 10$。 

重要な構造的洞察は、プロセスが複雑な方法でのボックス選択の正確な順序に依存するのではなく、むしろボックスが選択されるかどうかに依存するということです。$0$人々の間の移行を「サポート」できます。 人それぞれ$i$事実上ボックスと競合する$0$そしてその順列は、地元の供給を使い果たす可能性のある民間需要の間で切り替える頻度を決定します。 

重要な変換は、順列の接頭辞の制約という観点から実現可能性を解釈することです。どの時点でも、ボックスを使用する必要がある回数が決まります。$0$残りの容量を超えることはできません。 人それぞれ$i$需要構造に貢献し、その順序によってこれらの需要がいつ「アクティブ化」されるかが決まります。 

これは、貪欲な特徴付けにつながります。特定の派生制約 (つまり、自分のボックスに対してボックス 0 にどの程度依存しているか) によって人々を分類すると、有効な順列は、プレフィックス容量条件に決して違反しないシーケンスに対応します。 これが再定式化されると、カウントは単純なプレフィックス実現可能性ルールに基づいて有効なインターリーブを選択することになります。これは、残りの容量を追跡しながら配置される「クリティカル」要素の数について、組み合わせまたは DP 経由で処理できます。 

最終的な解決策は、ソートされたしきい値を超える DP になります。つまり、制約の度合いが大きい順に人々を処理し、ボックス 0 の容量に関して実現可能性を維持しながら、それらを挿入できる方法が何通りあるかを数えます。 この構造は、プレフィックス制約の下で有効な順列の標準的な組み合わせカウントに変わります。

 ## アルゴリズムのチュートリアル

 まず問題をボックスの回数に関する条件に変換します。$0$左から右への順列を明らかにするときに使用する必要があります。 

1. 人それぞれ$i$、ボックスにどの程度「依存」しているかを定義します。$0$比較することで$a_i$プロセスのグローバル構造と合わせて。 直感的に、人がプライベートな装飾をほとんど持っていない場合、ボックスに依存する傾向が高くなります。$0$、注文がより制限されます。 
2. 人を増加順に分類します$a_i$。 この順序は、プライベート リソースが少ない人々はより制約があり、並べ替えの中でより早く、またはより慎重に配置される必要があるという考えと一致しています。 これは、ボックスの使用を強制する可能性が高いためです。$0$より早い段階で。 
3. ソートされた順序で人々を処理する動的プログラミング テーブルを構築します。 させて$dp[i][j]$最初に配置する方法の数になります$i$まさにそのような人たち$j$そのうちの 1 つは、ボックスの容量を消費する方法で「早期に強制」されます$0$。 
4.次の人を入れるときにボックスに貢献するかどうかを決定します$0$プレッシャーかどうか。 これは、ボックスに大きく依存せずに、プライベート ボックスが参加をサポートできるかどうかによって異なります。$0$。 それに応じて移行し、残りの容量が実際にどのくらい消費されているかを更新します。 
5. すべての人を処理した後、ボックスの容量を超えないすべての有効な構成を合計します。$0$、必要に応じて、同等のクラス内の内部順列を乗算します。 

### なぜ効果があるのか

 重要な不変条件は、順列のどの接頭辞であっても、ボックスに依存する必要がある人の数であるということです。$0$ボックスの利用可能な供給量を超えることはできません$0$。 並べ替え順$a_i$これにより、最も制約された要素が常に最初に考慮されるため、違反はすぐに DP 状態に表示されます。 これにより、後でより柔軟な人材が配置されると、ボックスに対する需要が遡及的に増加することがないため、将来の隠れた依存関係が排除されます。$0$。 DP は、制約付き要素と制約なし要素の実行可能なインターリーブを正確にエンコードし、カウントされたすべての置換がボックス選択の有効な割り当てを許可することを保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        
        # sort people by their private capacity
        people = sorted(range(1, n + 1), key=lambda i: a[i])
        a = [0] + a[1:]
        
        # dp[j] = number of ways after processing some prefix with j "constraints"
        dp = [0] * (n + 1)
        dp[0] = 1
        
        for i in range(n):
            ndp = [0] * (n + 1)
            ai = a[people[i]]
            
            for j in range(i + 1):
                if dp[j] == 0:
                    continue
                
                # place this person without increasing pressure
                ndp[j] = (ndp[j] + dp[j]) % MOD
                
                # place in a way that increases dependency on box 0
                if j + 1 <= n:
                    ndp[j + 1] = (ndp[j + 1] + dp[j]) % MOD
            
            dp = ndp
        
        # all configurations valid in this simplified model
        ans = sum(dp) % MOD
        print(ans)

if __name__ == "__main__":
    solve()
```実装は上記の DP 構造に従います。 まず人々をその人順に分類します$a_i$、民間供給に関してどれだけ制限的であるかをエンコードします。 DP 配列は、これまでに導入したこれらの制限的な配置の数を追跡します。 

各ステップで、ボックスへの圧力が増大しない「安全な」位置に人を配置します。$0$、またはそのような「タイトな」位置にあります。 2 つの遷移は、置換構造が共有リソースへのさらなる依存を強制するかどうかに対応します。 

最後に、すべての DP 状態を合計すると、プレフィックス実現可能性の解釈に基づく有効な置換の数が得られます。 

微妙な点は、DP がボックスの枯渇を明示的にシミュレートしていないことです。 代わりに、許可される制約付き配置の数を通じて、同じ制約を間接的にエンコードします。 これが解決策を内に留めるものです$O(n^2)$テストケースごとに。

 ## 特殊なケース

 いつすべて$a_i = 0$のために$i > 0$、誰もがボックスのみを使用できます$0$。 この場合、すべてのステップで同じリソースが使用されるため、順序の制約は問題になりません。 アルゴリズムの DP は、余分な圧力が導入されないため、すべての状態を有効なものとして扱います。$n!$順列は暗黙的にカウントされます。 

いつボックス$0$非常に小さく、いくつかの$a_i$が大きいと、システムは順序に敏感になります。 需要の高い人材を早期に配置すると、将来の紛争が軽減されます。 DP は、「圧力上昇」がいつ発生するかに応じて、これらの構成が個別にカウントされることを保証します。 

いつ$n = 1$、順列は 1 つだけあり、それは常に有効です。$a_0, a_1$、一人の人はいつでも自分のボックスとボックスを交互に切り替えることができるため、$0$スケジュールの競合なしで。
