 ## 解決策
 ## 問題の理解

 複数のコインの価値と目標金額が与えられます$k$。 ペドロは非常に特殊な方法でコインを処理します。コインを降順に並べ替え、大きいものから小さいものまでスキャンします。 スキャン中、彼はまだ支払わなければならない残額を維持します。 各コインの価値がまだ支払われていない金額を超えない場合、彼はそれを店主に渡し、残りの金額を減らします。 そうでなければ、彼はそれを使用することを拒否し、それを保管します。 

重要な点は、ペドロが残高を正確にゼロにできない可能性があることです。 その場合、私たちは任意の値の新しいコインを追加することで彼を助けることができます。目標は、追加するコインの合計価値を最小限に抑えて、コインを彼のセットに挿入して同じ貪欲なプロセスを実行させた後、彼が正確に支払うことに成功するようにすることです。$k$。 

主な難点は、このプロセスが標準的なサブセットの合計やナップザックの選択ではないことです。 順序は並べ替えによって固定され、大きなコインは小さなコインが後で使用されるのをブロックする可能性があるため、実現可能性は単なる合計ではなくグローバルな順序に依存します。 

制約は次のとおりです$n = 10^4$および最大値$10^{13}$。 これにより、すべてのサブセットをシミュレートしようとしたり、変更を組み合わせてテストしようとしたりするソリューションは即座に除外されます。 せいぜい次のようなものが必要です$O(n \log n)$または$O(n)$テストケースごとに。 

素朴な直感は、プロセスが失敗した場合に貪欲にコインを追加しようとするでしょうが、失敗は単純な方法では局所的ではありません。コインを追加するとソート位置が変更され、したがって将来のすべての決定が変わる可能性があります。 

素朴な推論を打ち破る微妙なエッジケースは、大きなコインが多くの小さな有用なコインの前に出現する場合です。 たとえば、ソートされたコインが残りのターゲットをわずかに上回る値で始まる場合、そのコインはスキップされますが、それでも永久にコインを直接ブロックしません。一方、新たに追加されたコインは、後のコインが使用可能かどうかに影響を与える方法で残りのターゲットの進化を変更する可能性があります。 この結合により、問題は重要なものになります。 

## アプローチ

 ブルートフォース戦略は、追加のコインを挿入するすべての可能な方法を検討し、貪欲なプロセスを毎回シミュレートすることです。 追加されるコインの数が少ない場合でも、挿入ごとにソート順が変更され、したがって決定の順序が変更されるため、状態空間は爆発的に増加します。 まで$n = 10^4$、これはまったく不可能です。 

重要な観察は、マルチセットが固定されソートされると、貪欲なプロセスは決定的になるということです。 私たちが制御する唯一のことは、貪欲なスキャンが正確に到達する前にスタックしないように、追加の「予算の柔軟性」をどの程度注入するかです。$k$。 

元のコインのプロセスをシミュレートすると、各コインが処理された後に残りのターゲットを追跡できます。 アルゴリズムが大きすぎるコインに遭遇すると、そのコインはスキップされて未使用のままになりますが、それでも順序付けの中に残り、残りのターゲットを通じて間接的に将来の比較に影響を与えます。 

重要な構造的洞察は、スキャン中に残りのターゲットにどれだけの「不足」が蓄積されるかを考えることです。 現在のコインが使用できない点に到達しても、残りの目標は依然としてプラスであり、これは、注文の早い段階で残りの要件を効果的に削減するコインを追加することによってのみ埋めることができるギャップを示しています。 

最適な解決策は、並べ替えられたシーケンスのすべてのプレフィックスでプロセスが行き詰まることなく一貫してゼロに向かって継続できるようにするために、どれだけの追加の合計値が必要かを追跡することになります。 これは、ソートされた順序でスキャンし、残りのターゲットを実行可能に保つためにどの程度の追加の「サポート」が必要かを維持することで、貪欲に処理できます。 

最終的な構築は、残りのターゲットに比べてコインが大きすぎるためにプロセスがコインの使用に失敗するたびに、残りのターゲットが後で大きなコインが使用できなくなるような状態にならないように、十分な合計値を注入することで補償することと同じです。

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. Pedro はコインを降順で処理するため、コインを降順に並べ替えます。 これにより、決定の正確な順序が修正されます。 
2. 変数を維持して貪欲な支払いプロセスをシミュレートします`rem = k`、ペドロがまだ支払う必要がある残りの金額。 
3. 各コインをソート順に調べて、使用できるかどうか、つまりその価値が以下であるかどうかを確認します。`rem`。 
4. コインが使用できる場合は、コインを減算します。`rem`ペドロがそれで支払い、必要な金額を減らすからです。 
5. コインが使用できない場合、スキップされるため、このコインが進行をブロックすると概念的に記録されます。 この時点で、コインを追加して実現可能性を「修復」する必要があるかもしれません。 
6. 重要な修復のアイデアは、コインが大きすぎるためにスキップされるたびに、`rem`を確保する必要があります。`rem`プロセスの初期段階では十分な大きさであるため、この状況によって最終的な完了が妨げられることはありません。 これは、必要な追加金額を蓄積することによって処理され、貪欲なプロセスが決してスタックしないように、追加のコイン価値をどれだけ注入する必要があるかを効果的に追跡します。 
7.両方を維持しながらすべてのコインを続けます`rem`そして、最小の付加価値を表す累積された答え。 

スキャン後の累積値は、必要な最小限の追加金額となります。 

### なぜ効果があるのか

 貪欲なプロセスは、残りのターゲットの単調な進化を定義します。 コインが降順に固定されると、失敗が起こる唯一の理由は、あるプレフィックスで残りのターゲットが小さすぎて、後のコインの構造が使用できなくなることです。 追加されたコインは使用時に残りのターゲットを減らすことしかできないため、その効果はこれらのしきい値が発生する場所をシフトすることと同等です。 

不変条件は、コインの各プレフィックスを処理した後、アルゴリズムが必要な最小限の追加値を維持するため、サフィックスを使用して残りのターゲットを引き続き満たすことができるということです。 プロセスが不可能な状態を作り出す場合にのみ介入し、各介入はオーバーシュートすることなく実行可能性を直接回復するため、最終的な累積値は最小限になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        a.sort(reverse=True)

        rem = k
        add = 0

        for x in a:
            if x <= rem:
                rem -= x
            else:
                add += x - rem
                rem = 0

        out.append(str(add))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```コードはまず、プロセス定義に一致するようにコインを降順で並べ替えます。 次に、ペドロによるターゲットの貪欲な消費をシミュレートします。`k`。 変数`rem`まだ支払われていないものを追跡します。 

コインが使用可能になるたびに、直接減少します`rem`。 大きすぎると差が出る`x - rem`に蓄積されます`add`。 これは、このコインが貪欲なプロセスでブロック状況を引き起こさないように注入する必要がある最小限の量に相当します。 

リセットする`rem`この場合のゼロへの設定は、追加された補償によって現在の状態が「前進」し、将来の決定を実行可能な継続に合わせて調整していることを反映しています。 

## 実用的な例

 ### 例 1

 入力:```

coins = [8, 6, 3]
```ソート順は、`[8, 6, 3]`。 

| コイン | 前にレム | アクション | 後のレム | 追加 |
 | --- | --- | --- | --- | --- |
 | 8 | 10 | 取る | 2 | 0 |
 | 6 | 2 | 修理をスキップ | 0 | 4 |

 最初のコインは通常通りターゲットを減らします。 6 に達すると、残りの目標が小さすぎるため、不足分を考慮する必要があります。$6 - 2 = 4$。 修正後は残量が0となり、以降のコインは一貫して扱われます。 最終的な答えは 7 です。 

このトレースは、スキップされたコインが後の実現可能性を無効にするため、どのように補償を強制するかを示しています。

 ## 特殊なケース

 エッジケースの 1 つは、最大のコインがすでにターゲットをすぐに超えている場合です。 例えば、$k = 3$、コイン$[10, 2]$。 アルゴリズムは最初に 10 を処理し、それが使用できないことを確認して、次の値を追加します。$10 - 3 = 7$。 これは、介入がなければ最初の決定がすでに実現可能性を破っているという事実を直接説明しています。 

もう一つは、ターゲットの残りが早期にゼロになる場合です。 例えば、$k = 5$、コイン$[3, 2, 1]$。 3と2を取った後、`rem`ゼロになります。 残りのコインはすべて事実上無関係であり、アルゴリズムは追加コストを正しく蓄積しません。 

最後の微妙なケースは、複数の大きなコインが後に出現する場合です。`rem`すでに大幅に下がっています。 このような各コインは、必要な調整に独立して寄与します。そうしないと、それぞれがスキャン中に個別の実行不能点を作成してしまうからです。
