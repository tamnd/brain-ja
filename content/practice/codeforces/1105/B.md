 ## 解決策
 ## 問題の理解

 文字列と固定ウィンドウ サイズが与えられます。$k$。 タスクは、長さの異なる複数のブロックを繰り返し切り出すことです。$k$文字列から。 選択した各ブロックは、同じ文字が繰り返されて構成されている必要があります$k$選択されたすべてのブロックは同じ文字を使用する必要があります。 

目標は、選択できるそのようなブロックの数を最大化することです。 キャラクターを修正したら、事実上、重複しない長さのランが何回あるかを尋ねることになります。$k$その文字全体からなる文字列を文字列から抽出できます。 

制約$n \le 2 \cdot 10^5$すべての部分文字列に対する二次スキャンを除外します。 すべての開始位置をテストし、各テスト内の部分文字列を貪欲に検証しようとするアプローチでは、部分文字列を繰り返しチェックすると性能が低下する可能性があるため、時間がかかりすぎます。$O(nk)$最悪の場合。 

よく見られる素朴な誤解は、非オーバーラップを考慮せずに、有効な各ウィンドウを独立して扱うことです。 たとえば、次のような文字列では`"aaaaaa"`と$k = 2$、重複するウィンドウを数えるかもしれません`"aa"`位置 1、2、3、4、5 ですが、問題により重複が禁止されています。 正解は 5 ではなく 3 です。 

もう 1 つの微妙なケースは、キャラクターが頻繁に登場するものの断片化されている場合です。 例えば、`"aabaaa"`と$k = 2$。 ブロックが失敗するたびに再起動する素朴な貪欲な左から右へのスキャンは、戦略的にスキップすることで最適なキャラクターに対してより多くの有効なブロックを生成できることを誤って見逃してしまう可能性があります。 

## アプローチ

 ブルートフォースのアイデアは単純明快です。`'a'`に`'z'`、文字列をスキャンし、貪欲に長さのセグメントを取得しようとします。$k$私たちが見るたびに$k$その文字の連続出現。 セグメントを取得した後、次のようにスキップする必要があります$k$重複を避けてスキャンを続行します。 

これが機能するのは、文字を修正すると、すべての有効なブロックが完全にその文字で構成されなければならないためです。そのため、文字列内でその文字が連続して実行されることだけを考慮すればよいからです。 各実行内で私たちができる最善のことは、それをサイズの塊に分割することです$k$。 

ブルート フォースが遅くなるのは、開始位置ごとに部分文字列の有効性を再計算するなど、不用意に実装された場合のみです。 それは次のことにつながります$O(nk)$行動。 ただし、実行を前処理するか、単純に文字ごとに 1 回スキャンする場合は、文字ごとに線形のままです。 

重要な観察は、ブロックがキャラクター間で相互作用しないことです。 各キャラクターは独立して貢献し、サイズの完全なグループがいくつあるかを計算するだけで済みます。$k$同一文字の最大の連続セグメントに存在します。 

したがって、タスクは文字列を 1 回スキャンし、連続する実行をカウントし、長さの各実行をカウントすることになります。$L$、追加$L // k$そのキャラクターの合計に。

 ## アルゴリズムのチュートリアル

 文字列を同一の文字の連続するランに圧縮し、各ランを個別に処理します。 

1. 文字列の最初の文字から開始し、左から右にスキャンするポインタを維持します。 

これが機能する理由は、妥当性が連続した等価性のみに依存するため、グローバルな分布よりも境界が重要であるためです。 
2. 各位置で、文字は同じまま前方に拡張し、同一文字の最大セグメントを形成します。 

有効なブロックはすべてそのようなセグメント内に完全に存在する必要があるため、これにより使用可能な構造がすべて分離されます。 
3. セグメントの長さを次のようにします。$L$。 サイズの完全なブロックがいくつあるかを計算する$k$フィット：$L // k$。 

このような各ブロックは、次の長さの有効な部分文字列に対応します。$k$同じ文字で。 
4. この値を累計の回答に加算します。 
5. 文字列が完全に処理されるまで、セグメントの終わりから続行します。 

### なぜ効果があるのか

 有効な各部分文字列は、同一文字の 1 つの連続に完全に含まれている必要があります。 2 つの異なる文字が有効なブロックを共有することはできず、ブロック内で文字を混合することは禁止されています。 一定の長さのランの内側$L$、サイズが重複しないブロックを可能な限り最適にパッキングする$k$まさに$L // k$、すべてのブロックが消費するため、$k$キャラクターなので、ランを別々に分割してもメリットはありません。 これにより、実行が独立しているため、貪欲なセグメンテーションがグローバルに最適であることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    s = input().strip()

    ans = 0
    i = 0

    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1

        length = j - i
        ans += length // k

        i = j

    print(ans)

if __name__ == "__main__":
    solve()
```コードは 1 回のリニア スキャンを実行します。 内側のループは文字の変更が発生するまでセグメントを拡張し、ランレングスを効果的に計算します。 整数の除算`length // k`そのセグメントに収まる完全な非重複ブロックの数をキャプチャします。 

よくある間違いは、有効な部分文字列が見つかるたびに、ランレングスにまとめずにカウントを再開しようとすることです。 これにより、同じ文字が繰り返しスキャンされ、重複処理が正しく行われなくなります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, k = map(int, input().split())
    s = input().strip()

    ans = 0
    i = 0
    while i < n:
        j = i
        while j < n and s[j] == s[i]:
            j += 1
        ans += (j - i) // k
        i = j

    return str(ans)

# provided sample
assert run("8 2\naaacaabb\n") == "2"

# all same characters
assert run("6 2\naaaaaa\n") == "3"

# no valid block
assert run("5 3\nabcde\n") == "0"

# boundary k=1
assert run("4 1\nabcd\n") == "4"

# single run mixed structure
assert run("10 2\naaabbbccaa\n") == "4"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`6 2 aaaaaa`| 3 | フルランパッキング |
 |`5 3 abcde`| 0 | 有効なセグメントがありません |
 |`4 1 abcd`| 4 | k=1 のエッジケース |
 |`10 2 aaabbbccaa`| 4 | 1 文字につき複数回実行 |

 ## 特殊なケース

 重要なエッジ ケースは、有効なブロックが同じキャラクターの複数の別々のランに存在する場合です。 このアルゴリズムは、単一の連続ブロックを必要とするのではなく、実行ごとの寄与を合計することによってこれを処理します。 

例えば、`"aabaaa"`と$k = 2$。 ランは、`"aa"`、`"b"`、`"aaa"`。 キャラクターについて`'a'`、貢献は$1 + 1 = 2$。 これは最適な選択 (最初の実行からの 1 ブロックと最後の実行からの 1 ブロック) に一致します。 

もう一つのエッジケースは、$k = 1$。 すべての文字はそれ自体が有効なブロックであり、答えは文字列全体にわたる単一文字の最大頻度になります。すべての文字列がその全長に寄与するため、文字列分割ロジックは自然にこれを処理します。
