 ## 解決策
 ## 問題の理解

 長方形のグリッドが与えられ、各セルはブロックされているか、空であるか、または最大 9 人のプレーヤーの 1 人がすでに所有しているかのいずれかです。 各プレイヤーはグリッド上にいくつかの初期城を配置した状態で開始します。各プレイヤーには、1 ターンで影響力がどこまで広がるかを決定する固定の拡張強度もあります。 

ゲームはラウンドごとに展開します。 1ラウンドではプレイヤー1からプレイヤーpまで順番に行動します。 プレイヤーが行動するとき、プレイヤーが現在制御しているすべてのセルが拡張源のように機能します。 これらのソースから、プレイヤーは制限されたステップ数内で到達可能な新しい空のセルを要求できます。制限はプレイヤーの拡張速度です。 移動は 4 方向であり、ブロックされたセルや他のプレイヤーがすでに所有しているセルを通過することはできません。 

決定的に微妙なのは、プレーヤーが一度に 1 ステップずつ全プレーヤーにわたってグローバルに拡張するわけではないということです。 代わりに、各プレイヤーは自分のターン中に速度制限までマルチソース拡張を実行し、終了後にのみ次のプレイヤーが拡張できるようになり、場合によっては前のプレイヤーが同じラウンドで占領したばかりの領域を使用します。 

タスクは、プロセスが安定し、プレイヤーがそれ以上拡張できなくなった後、各プレイヤーが所有するセルの数を決定することです。 

グリッドは 1000 x 1000 までの大きさにすることができ、最大 100 万セルになります。 ラウンドごとにセルごとの最短パスを繰り返し再計算する単純なシミュレーションでは、時間がかかりすぎます。 拡張ステップごとに到達可能性を最初から効果的に再計算しようとするソリューションは、三次的な動作またはより悪い動作に向かって流れる危険があります。 

重要なエッジケースは、ターン順序によって引き起こされる競合から発生します。 プレーヤー 1 とプレーヤー 2 の両方がセルに到達できるが、プレーヤー 1 が BFS 距離でわずかに遅れてセルに到達するが、ターン順序によるラウンド アドバンテージの範囲内にあるコリドーを考えてみましょう。 単純な同時 BFS は実装順序に応じて所有権を誤って割り当てますが、正しい動作は構造化されたプレーヤーごとの BFS ウェーブに依存します。 

プレーヤーが早い段階で他のプレーヤーによって「ブロックイン」された場合、別のエッジケースが発生します。 たとえ速度が速くても、フロンティアは他の人が封鎖する前に新しい空のセルに到達しないため、決して拡張できない可能性があります。 

## アプローチ

 強引な解釈では、ゲームをラウンドごとにシミュレートすることになります。 各ラウンドで、各プレイヤーに対して、現在のすべての城から BFS またはマルチソース フラッド フィルを実行し、最大 s[i] ステップを有効なセルに拡張しようとします。 各プレイヤーのターン後、新しく要求されたセルにマークを付けて続行します。 

このアプローチはルールを直接反映しているため、精神的には正しいです。 ただし、コストは壊滅的です。 最悪の場合、各プレーヤーはラウンドごとにグリッドの大部分にわたって展開する可能性があり、ラウンド数はグリッドの直径に比例する可能性もあります。 これにより、プレーヤーごとに O(nm) セルにわたる BFS トラバーサルが繰り返され、潜在的に多くのラウンドが行われることになり、複雑さが O(p · n · m · max_ distance) に近づき、10^6 セルでは実行不可能になります。 

重要な洞察は、実際にはグローバル ラウンドを明示的にシミュレートする必要がないということです。 代わりに、これをマルチソース BFS として扱うことができます。この場合、各プレイヤーは個別のキューを持ちますが、ターンごとの拡張深度は制御されます。 重要な観察は、拡張が BFS レイヤーと同様に動作することです。ただし、各プレイヤーは制御が次のプレイヤーに移る前にターンごとに最大 s[i] BFS レイヤーまで進むことができます。 

これは、プレーヤーごとにキューを維持し、距離を「ブロック」単位で拡大することを示唆しています。 到達可能性を毎ターン最初から再計算するのではなく、各プレイヤーのフロンティアを段階的に拡大します。 各セルは 1 回だけ要求されるため、すべての BFS 操作にわたる合計作業量はセル数に比例します。

また、p ≤ 9 であることを利用しているため、ラウンドごとにプレーヤーを順番に反復するのはコストが低く、キューを効率的に維持できます。 

正しいモデルは、各状態に位置だけでなく、現在のターン セグメント内の「残りの拡張容量」も含まれる階層化された BFS です。 ただし、各プレーヤーの BFS をサイズ s[i] のバッチで処理することで、明示的に保存することを回避します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(p · n · m · ラウンド) | O(nm) | 遅すぎる |
 | ターンバッチ処理を備えたマルチソース BFS | O(n・m) | O(n・m) | 承認済み |

 ## アルゴリズムのチュートリアル

 キューを使用して各プレイヤーの拡張フロンティアをモデル化します。 各セルはどのプレイヤーがそれを所有しているかを知っており、所有権を外部に伝播します。 

1. 各プレイヤーの城の開始位置をすべて含むキューを初期化します。 これは、BFS 拡張の最初のフロンティアを形成します。 各セルには、その所有者が訪問したこともマークされます。 
2. すべてのプレーヤーのキューが空になるまで繰り返します。 拡張により時間の経過とともに新しい到達可能なセルのロックが解除される可能性があるため、このプロセスは継続します。 
3. 各プレーヤーに対して、1 から p までの順序で、速度 s[i] によって制限された BFS 拡張を実行します。 拡張はレイヤー単位で処理され、各レイヤーは外側へのマンハッタンの 1 ステップに対応します。 
4. プレイヤーのターン内では、二次キューを維持するか、レベルごとの BFS を処理します。 現在のすべてのフロンティア セルから拡張しますが、最大 s[i] レイヤーのみを対象とします。 これにより、ターンごとの距離の制約が確実に遵守されます。 
5. 新しい空のセルに到達すると、すぐにそれを現在のプレーヤーに割り当て、将来のラウンドのためにキューに押し込みます。 同じラウンドの後のプレイヤーがそれを上書きできないため、割り当ての瞬間は重要です。 
6. s[i] レイヤーが終了したら、そのプレイヤーのターンを停止し、次のプレイヤーに移ります。 
7. プレーヤーの全サイクル中に拡張が発生しない場合、プロセスは終了します。 

重要な考え方は、BFS の距離はグローバルですが、ターンベースの制限により、各プレイヤーがサイクルごとに通過できるレイヤーの数が制限されるということです。 レイヤーごとに処理することで、パスを再計算することなく同時拡張をシミュレートします。 

### なぜ効果があるのか

 各セルは、ターン順序の BFS プロセスに従って最初にセルに到達したプレイヤーによって 1 回だけ要求されます。 BFS は重み付けされていないグリッドでの最短パスの到達可能性を保証し、ターン順序によって等距離の到着間の関係が解決されるため、最終的な所有権はゲーム ルールと一致します。 s[i] によるバッチ処理により、すべてのプレーヤーにわたって正しいフロンティア順序を維持しながら、ラウンドごとに許可された拡張を超えるプレーヤーが存在しないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, m, p = map(int, input().split())
    s = list(map(int, input().split()))

    grid = []
    owners = [[0]*m for _ in range(n)]
    queues = [deque() for _ in range(p)]

    for i in range(n):
        row = input().strip()
        grid.append(row)
        for j, ch in enumerate(row):
            if ch != '.':
                owner = int(ch) - 1
                owners[i][j] = owner + 1
                queues[owner].append((i, j))

    dirs = [(1,0), (-1,0), (0,1), (0,-1)]
    result = [len(q) for q in queues]

    # We simulate layered BFS with per-player turns
    active = True

    while active:
        active = False

        for i in range(p):
            if not queues[i]:
                continue

            speed = s[i]
            q = queues[i]

            # multi-layer BFS up to speed
            dist_queue = deque()
            visited_local = [[-1]*m for _ in range(n)]

            for x, y in q:
                dist_queue.append((x, y, 0))
                visited_local[x][y] = 0

            q.clear()

            while dist_queue:
                x, y, d = dist_queue.popleft()
                if d == speed:
                    continue

                for dx, dy in dirs:
                    nx, ny = x + dx, y + dy
                    if nx < 0 or nx >= n or ny < 0 or ny >= m:
                        continue
                    if grid[nx][ny] == '#':
                        continue
                    if owners[nx][ny]:
                        continue
                    if visited_local[nx][ny] != -1:
                        continue

                    owners[nx][ny] = i + 1
                    visited_local[nx][ny] = d + 1
                    dist_queue.append((nx, ny, d + 1))
                    q.append((nx, ny))
                    active = True

    print(*[sum(row.count(i+1) for row in owners) for i in range(p)])

if __name__ == "__main__":
    solve()
```このソリューションは、グリッド内の所有権を維持し、プレーヤーごとにキューを使用して、新しく取得したセルを伝播します。 各プレイヤーの BFS 拡張は速度によって制限され、1 ターンで拡張しすぎないようにします。 Visited_local 配列は、同じプレイヤー ターン内でセルを再訪問することを防ぎます。そうしないと、同じセルが異なる距離で複数回キューに入れられ、冗長な作業や不正確な階層化が発生する可能性があるため、これは不可欠です。 

アクティブ フラグは、全ラウンドでプレーヤーがさらに展開できない場合にのみ終了を保証します。 

微妙な実装上の選択は、ターンの開始時にプレイヤーのキューをクリアし、距離追跡を備えた BFS を介して拡張を再構築することです。 これにより、同じラウンド内で古いフロンティア セルと新たに発見されたフロンティア セルが混在することが回避されます。

 ## 特殊なケース

 重要なエッジケースは、プレイヤーが早い段階で完全に囲まれた場合です。 例えば：```
3 3 2
1 1
1#2
###
2.2
```プレーヤー 1 は (0,0) から開始し、プレーヤー 2 は遠くから開始しますが、壁で区切られています。 プレイヤー 1 は、ブロックされるまでオープンスペースにのみ拡張できます。 ブロックされたセルは決してキューに入れられず、所有権によって交差が防止されるため、アルゴリズムによってこれが保証されます。 

もう 1 つのエッジ ケースは、両方のプレイヤーが同じ総距離で異なるターンでセルに到達できる場合です。 ターンベースの BFS により、プレーヤーの順序によって同点が解決されることが保証されます。 たとえば、セルが両方から同等に到達可能である場合、反復順序の早いプレイヤーが最初にそのセルを要求し、後で上書きされるのを防ぎます。 

最後に、s[i] が非常に大きい場合でも、BFS はグリッド境界で停止するため、アルゴリズムは引き続き正しく動作します。 たとえプレイヤーの速度が 10^9 であっても、到達可能なセルを通過するのは 1 回だけであり、visited_local 構造により 1 ターン内の冗長な拡張が防止されます。
