 ## 解決策
 ## 問題の理解

 ファームは、ヒープ順に書かれた完全なバイナリ ツリーです。 ツリー 1 はルートであり、すべてのツリー`i > 1`親がいる`i // 2`。 木`i`最初に含まれています`a[i]`リンゴ。 

お客様のご要望`(u, v, c, w)`特別だから`u`～の祖先であることが保証されている`v`。 顧客が購入できるのは最大でも`c`リンゴですが、この顧客に販売されるすべてのリンゴは、`u`に`v`。 そのようなリンゴはそれぞれ収入を得ます`w`ドル。 リンゴはさまざまな顧客に分割できます。目標は、木の生産能力と顧客の制限の両方を尊重しながら、すべてのリクエストに対して販売するリンゴの数を選択することです。 

公式の制限は次のとおりです`n,m <= 100000`テストケースごと、合計`n`そして合計`m`すべてのテスト ケースにわたって、`10^6`。 制限時間は 6 秒、メモリ制限は 512 MB です。 ツリーノードには深さのみがあります`O(log n)`なぜなら、ツリーはバイナリ ヒープであり、これが対数深さの動的プログラムを可能にする構造的事実だからです。 で`n = 100000`、ペアごとのリクエスト操作を 2 次数実行するアルゴリズムはすでに大きすぎますが、`O((n+m) log^2 n)`方法は意図した範囲内です。 オリジナルの受け入れられた実装では、まさにこのツリー DP のアイデアが使用されています。 

一見自然な貪欲な実装が失敗するケースがいくつかあります。 1 つ目は、価格を下げてリクエストを処理する必要があるが、単に任意のリンゴをパスに沿って取るだけでは十分ではないということです。 考慮する```
1
2 2
1 1
1 2 1 10
2 2 1 9
```正しい答えは、`19`。 最初の顧客は木 1 のリンゴを取り、2 番目の顧客のために木 2 にリンゴを残します。 不注意な実装では、代わりにツリー 2 を使用して最初のリクエストが満たされ、その後 2 番目のリクエストは何も取得されず、答えは次のようになります。`10`。 

2 番目のエッジ ケースは、2 つのエンドポイントが等しいリクエストです。 のために```
1
1 2
5
1 1 3 10
1 1 5 2
```答えは`34`。 どちらのリクエストも唯一のツリーに制限されているため、最初のリクエストでは 3 個のリンゴが販売され、2 番目のリクエストでは残りの 2 個が販売されます。すべてのパスに少なくとも 1 つのエッジがあると想定する実装では、このケースが誤って処理される可能性があります。 

3 番目の問題は、リクエストがそのパスに含まれるリンゴよりも多くのリンゴを要求する可能性があることです。 のために```
1
3 1
1 1 1
2 3 10 7
```このパスには木 2 と 3 しか含まれていないため、販売できるリンゴは 2 個だけであり、答えは次のようになります。`14`。 要求された数量を使用する`c`パスの使用可能な容量を確認せずに直接使用すると、オーバーカウントされる可能性があります。 

## アプローチ

 直接的なアプローチは、すべてのリンゴを個別の品目として扱い、すべてのリクエストを買い手候補として扱うことです。 すべてのリンゴについて、パスにそのツリーが含まれるすべてのリクエストを試して、利用可能な最も高い価格を選択することができます。 割り当てが最大重みの 2 部マッチングとして解決される場合、これは概念的には正しいですが、次の理由により完全に実行不可能です。`a[i]`と同じ大きさにすることができます`10^9`、したがって、個々のリンゴの合計数は次の数に達します。`10^14`。 

代わりに、リンゴをツリーごとに圧縮し、最大コストのフロー ネットワークを構築できます。 木は供給としてリンゴの数に寄与し、リクエストはその容量と価格に寄与します。 リクエストをそのパス上のすべてのツリーに接続すると、最大で`O(m log n)`すべてのパスが対数の長さを持つため、リクエスト ツリーの発生率が低くなります。 グラフはすでに大きく、一般的な最大コスト フロー アルゴリズムでは、容量が膨大であるため、膨大な数の拡張が必要になる可能性があります。 これはパスの特別な構造を利用しません。 

有益な観察は、すべてのリクエストが祖先から子孫までの垂直パスであるということです。 これにより、割り当ての問題が根のあるツリー上のホール型の実現可能性問題に変わります。 リクエストの固定セットの場合、リクエストのすべてのコレクションが、許可されたパスの和集合に十分な数のリンゴを持っている場合に、リクエストを完全に満たすことができます。 パスはこの祖先と子孫の形式を持つため、潜在的にタイトなホール集合は、1 つの区別された下向きパスを含むルート付きサブツリーによって表すことができます。 これらのホール制約はすべてツリー DP で維持できます。 

2 番目の観察は利益に関するものです。 リクエストを降順に処理します`w`。 より高価なリクエストはすべて可能な限りすでに満たされていると仮定します。 現在のリクエストでは、すでに構築された割り当てを実現可能に保ちながら、できるだけ多くの需要を追加したいと考えています。 追加できるとしたら`C`リンゴ、利益増加はまさに`C * w`なので最大化します`C`が最適です。 販売されたリンゴの合計数のみが重要であるため、同一価格リクエストは任意の順序で処理できます。 

考えられるすべてのルートに対して`x`のサブツリーのコピーを維持します。`x`、再びヒープとして表されます。`v[x]`ホール DP で使用される残りの容量値を保存します。`f[x]`現在のホール スラックを保存します。 相対ノードの場合`y`、再発は

 [
 f[y] = v[y] + \min(0,f[2y]) + \min(0,f[2y+1])。 
】

 行方不明の子どもたちの寄付金はゼロ。 負の子の値は、そのサブツリーに親を通じて供給する必要がある不足があることを意味するため、親はその負の量を継承します。 非負の子は内部的にすでに十分な容量を持っており、親を制約しません。 

からのリクエストがあったとき、`A`に`B`が追加されると、そのエンドポイント`B`は、ルートが次の祖先であるすべての祖先コピーの新しい要求単位として扱われます。`A`。 このようなコピーごとに、次で終了するパスのホール スラックを計算します。`B`兄弟サブツリーからの避けられない欠損も含まれます。 これらのゆるみの最小値は、ホール条件に違反することなく追加できる最大量となります。 

実装は元のコンテスト ソリューションに従います。`v`そして`f`ツリーDPを直接。

 ## アルゴリズムのチュートリアル

 1. すべてのリクエストを読み、価格の安い順に並べ替えます。`w`。 すべてのリンゴは顧客の価格を除き、顧客にとって同じ価値を持つため、高価格のリンゴは常に低価格のリンゴよりも前に割り当てられる必要があります。 
2. すべての木について`x`、ルートとなるサブツリーを表す補助ヒープを構築します。`x`。 根`x`相対インデックスを受け取ります`1`、その子はインデックスを受け取ります`2`そして`3`、彼らの子供たちは受け取ります`4`を通して`7`、 等々。 これにより、すべての祖先と子孫のパスを、相対インデックスに対する通常の親と子の操作で表すことができます。 
3. 補助ツリーごとに初期化します。`v`各相対ノードのリンゴの数を使用します。 最初は何も要求されていないため、`f`に等しい`v`。 
4. あらゆるリクエストに対して`(A,B,C,W)`、まず、の相対インデックスを決定します。`B`祖先をルートとするすべての補助ツリーで`x`の`A`。 深さの差がある場合`d`、次に相対ヒープインデックス`B`最後のものを保持することで得られます`d`の二進数`B`そして先頭のバイナリを追加します`1`。 
5. 1 つの固定補助根の場合`x`、から始めます`dp = f[o]`、 どこ`o`の相対位置です`B`。 から徒歩`o`副根に向かって。 どの先祖にも`y`、 追加`v[y]`、実際のパスではリンゴを使用できるため、`y`。 次に、パスの子の兄弟を調べます。 その兄弟が陰性の場合`f`、その不足は対応するホールセットにとって避けられないため、その負の値を`dp`。 
6. 最低限のものを取る`dp`すべての補助根にわたって`x`からの道中で`A`グローバルルートに。 この最小値は、ホール制約を不可能にすることなく受け入れられる、この要求の最大追加量です。 交換する`C`小さい場合はこの最小値までにします。 
7. その結果、`C`がゼロの場合、現在のリクエストでは何も販売できないため、DP は変更しないままにしておきます。 それ以外の場合は追加します`C * W`答えに。 
8. 承認された金額を適用します`C`関連するすべての補助ツリーに。 減少`v[x][o]`そして`f[x][o]`による`C`、その後、再計算します`f`の先祖について`o`同じ繰り返しを使用します。 これらのノードのみがホール スラックを変更できるため、補助ツリー全体を再計算する理由はありません。 

不変条件は、価格の降順でソートされたリクエストのプレフィックスを処理した後、維持されるということです。`f`値は、そのプレフィックスに対して受け入れられる数量の実行可能な割り当てを正確に記述し、すべての標準的なホール制約はいくつかの方法で表されます。`f`値、または次の挿入時に計算されたパス スラックによって決まります。 挿入ステップでは可能な限り最大のものを選択します`C`これらすべてのスラックは負ではないままです。 したがって、受け入れられた高価格のリンゴはすべて、実現可能性が許す限り常に保管されます。 すべてのリクエストは高価格から低価格へ処理されるため、これより優れた総利益を得ることができる実現可能なソリューションはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []

    for _ in range(T):
        n, m = map(int, input().split())
        a = [0] + list(map(int, input().split()))

        # v[x] and f[x] describe the subtree rooted at x.
        # Index 0 is unused.
        v = [None] * (n + 1)
        f = [None] * (n + 1)
        size = [0] * (n + 1)

        # Map a relative heap index z inside the subtree of x
        # to the original heap node.
        def actual_node(x, z):
            h = 1 << (z.bit_length() - 1)
            return x * h + (z - h)

        # Build the auxiliary heap for every x.
        for x in range(1, n + 1):
            lo, hi = 1, n + 1

            # Find the largest valid relative heap index.
            while lo + 1 < hi:
                mid = (lo + hi) >> 1
                y = actual_node(x, mid)
                if y <= n:
                    lo = mid
                else:
                    hi = mid

            mx = lo
            size[x] = mx

            vals = [0] * (mx + 1)
            for z in range(1, mx + 1):
                vals[z] = a[actual_node(x, z)]

            v[x] = vals
            f[x] = vals.copy()

        requests = []
        for _ in range(m):
            u, wv, c, w = map(int, input().split())
            requests.append((u, wv, c, w))

        requests.sort(key=lambda e: e[3], reverse=True)

        ans = 0

        def getid(x, y):
            d = y.bit_length() - x.bit_length()
            k = 1 << d
            return y - (x - 1) * k

        for A, B, C, W in requests:
            # First pass: find the largest feasible amount.
            x = A
            while x:
                o = getid(x, B)
                mx = size[x]
                vx = v[x]
                fx = f[x]

                dp = fx[o]
                y = o >> 1

                while y:
                    dp += vx[y]

                    t = y << 1
                    if t <= mx and t != o and fx[t] < 0:
                        dp += fx[t]

                    t = (y << 1) | 1
                    if t <= mx and t != o and fx[t] < 0:
                        dp += fx[t]

                    y >>= 1

                if dp < C:
                    C = dp

                x >>= 1

            if C <= 0:
                continue

            ans += C * W

            # Second pass: actually insert the accepted demand.
            x = A
            while x:
                o = getid(x, B)
                mx = size[x]
                vx = v[x]
                fx = f[x]

                vx[o] -= C
                fx[o] -= C

                y = o >> 1
                while y:
                    cur = vx[y]

                    t = y << 1
                    if t <= mx and fx[t] < 0:
                        cur += fx[t]

                    t = (y << 1) | 1
                    if t <= mx and fx[t] < 0:
                        cur += fx[t]

                    fx[y] = cur
                    y >>= 1

                x >>= 1

        out.append(str(ans))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```補助ツリーは、相対的なヒープ位置によってインデックスが付けられたリストとして格納されます。 表現`actual_node(x, z)`相対インデックスで表される元のノードを再構築します`z`。 の最上位の設定ビットの場合、`z`は`h`、 それから`z = h + r`対応する元のノードは`x * h + r`。 

既知の子孫の相対インデックス`B`より安く手に入れることができます。 もし`d`間の深さの差です`x`そして`B`、 それから`k = 2^d`、相対インデックスは次のようになります。`B - (x - 1)k`。 これは、リファレンス実装で使用されるビット操作と同等です。 

リクエストの最初のパスでは、その実現可能な数量のみが決定されます。 2 番目のパスでは、その量がわかった後でのみ DP が変更されます。 部分的に処理されたリクエストは、それ自身の残りの数量の実行可能性チェックに影響を与える可能性があるため、これら 2 つのパスを混合することは正しくありません。 

すべての容量と答えには、C++ の 64 ビット整数が必要です。 Python の整数には任意の精度があるため、特別なオーバーフロー処理は必要ありません。 の`C <= 0`チェックも必要です。 ゼロ スラックは、現在のリクエストではデマンドを追加できないことを意味しますが、実行可能な維持状態では負の値は発生しません。 

## 実用的な例

 公式サンプルの場合、リクエストは価格順に処理されます。`(2,4,2,4)`、`(2,5,2,3)`、 そして`(1,2,3,1)`。 その木にはリンゴがあります`[2,1,3,1,1]`。 公式の出力は次のとおりです`13`。

 ## 特殊なケース

 共有エンドポイントのケース```
1
2 2
1 1
1 2 1 10
2 2 1 9
```特定の物理的なリンゴを選択するのではなく、ホール スラックによって処理されます。 最初の要求が受け入れられた後、補助 DP は、より制限的な要求によってツリー 2 がまだ必要であることを記録します。 したがって、2 番目のリクエストは引き続き実行可能であり、`19`。 

エンドポイントが等しい場合```
1
1 2
5
1 1 3 10
1 1 5 2
```パスのエッジがまったくありません。 最初のリクエストの場合、相対インデックスは単純に次のようになります。`1`、そのため、最初のパスでは緩みが見られます`5`そして受け入れます`3`。 アップデートにより、ルート スラックが次から変更されます。`5`に`2`。 2 番目のリクエストは正確に受け入れられます`2`、与える`30 + 10 = 40`。 

パス容量を超えたリクエスト、```
1
3 1
1 1 1
2 3 10 7
```相対パスがある`2 -> 3`。 初期のホール スラックは、利用可能な 2 つのリンゴの合計です。`2`、したがって、要求された数量`10`に縮小されます`2`。 結果的に利益は`2 * 7 = 14`。 

大きなヒープ境界```
1
100000 1
1 1 1 ... 1
1 100000 100000 1
```からのバイナリ プレフィックス チェーンを含むパスがあります。`1`に`100000`。 以来`100000`バイナリの長さは 17 なので、そのパスには 17 個のノードが含まれます。 このアルゴリズムの相対インデックス変換は、ヒープ インデックスのバイナリ表現に従うため、使用可能な 17 個のリンゴを正確にカウントし、次の値を返します。`17`、ツリーの無関係な枝を横断することなく。
