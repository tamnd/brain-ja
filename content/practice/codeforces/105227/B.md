 ## 解決策
 ## 問題の理解

 長いビデオが与えられました`c`秒。 視聴には毎秒消費が必要です`a`インターネット接続中にダウンロードできるデータ単位`b`1 秒あたりのデータ単位を継続的に測定します。 

視聴を開始するのが早すぎると、ある時点でビデオがそれまでにダウンロードしたデータよりも多くのデータを要求するため、再生が停止する可能性があります。 ただし、視聴中でもダウンロードは継続されるため、再生中にバッファが部分的に補充される可能性があります。 

目標は整数の待ち時間を選択することです`t`これにより、一度再生が開始されると、最後まで継続的に再生を続けることができ、いつでも利用可能なダウンロード データを超えることはありません。 私たちはそのような最小のものを望んでいます`t`。 

重要な量は、単なる総データ量ではなく、ダウンロードされた量と視聴によって消費された量との間の継続的なバランスです。 時間に`t0`、ダウンロード量は`b * t0`。 時刻に再生を開始してから`t`、監視されている部分は`t0 - t`、必要な`a * (t0 - t)`データ。 条件は次のようになります。`b * t0 ≥ a * (t0 - t)`みんなのために`t0`で`[t, t + c]`。 

制約は小さく、`a, b, c ≤ 1000`したがって、予想される待ち時間に関するシミュレーションさえも実行可能ですが、連続時間の直接チェックは依然として不必要に複雑になります。 実際の構造は線形であるため、直接的な式が期待されます。 

接続が消費量に比べて非常に速い場合、微妙なエッジケースが発生します。 たとえば、次の場合`b ≥ a`であれば、ストリーミングは常に安全であり、待つ必要はありません。 もう 1 つのエッジケースは次のような場合です`b`よりわずかに小さいだけです`a`ここで、単純な「必要な合計とダウンロードされた合計を比較する」アプローチは、中間のバッファーの枯渇を無視するため失敗します。 

## アプローチ

 強引なアイデアは、考えられるすべての待ち時間を試すことです`t`、再生を秒単位でシミュレートし、バッファーが負になるかどうかを確認します。 候補者ごとに`t`、ダウンロードされたデータと消費されたデータを追跡します`c`秒。 これは、状態が決定論的に進化するため機能しますが、最悪の場合には遅すぎます。`O(c^2)`すべてをテストした場合の動作`t`そしてシミュレーションする`c`毎回のステップ。 

重要な観察点は、制約が`b * t0 ≥ a * (t0 - t)`直線的です`t0`したがって、最悪の時点で成立する場合は、どこでも成立します。 最悪のポイントは再生の終了時に発生します。`t0 = t + c`。 その時点で不等式を確保すると、両側が直線的に成長し、消費の傾きがダウンロードよりも高くなるため、初期の瞬間は自動的にその不平等を満たします。 

したがって、次のことを強制するだけで済みます。`b * (t + c) ≥ a * c`展開すると次のようになります。`b * t + b * c ≥ a * c`それで：`b * t ≥ c * (a - b)`以来`a > b`、右辺は正であり、次のように直接解くことができます。`t ≥ ceil(c * (a - b) / b)`これを満たす最小の整数を採用します。

 ## アルゴリズムのチュートリアル

 再生の最悪の瞬間でもバッファが不足しないようにすることで、最小待ち時間を導き出します。 

1. 再生中の 1 秒あたりの純不足率を次のように計算します。`a - b`。 これは、視聴中に補充されるよりも多くのデータが消費される量です。 
2. ビデオの全再生時間にわたって蓄積された合計不足額を計算します。`c`、つまり`c * (a - b)`。 これは、再生を開始する前にどれだけのバッファをプリロードする必要があるかを表します。 
3. 待っていることを観察してください`t`秒が生成します`b * t`バッファの単位。 
4. プリロードされたバッファが不足分をすべてカバーするのに十分であることを要求します。`b * t ≥ c * (a - b)`。 
5. を解く`t`上限のある整数除算を使用する:`t = (c * (a - b) + b - 1) // b`。 
6. 出力`t`。 

秒ごとの追跡ではなく総赤字に焦点を当てる理由は、ダウンロードと消費の両方が直線的に進化するためです。 開始時の合計バッファーが時間の経過とともに正味損失をカバーするのに十分になると、システムは一定のレートで進化するため、中間点が制約に違反することはできません。 

### なぜ効果があるのか

 再生中、バッファは一定のレートで変化します。`b - a`、これは負です。`a > b`。 したがって、バッファは再生の最後の瞬間に最小化されます。 バッファーが最後に負でないことを確認すると、バッファーがそれより早く負になることがないことが保証されます。 これにより、ある区間にわたる連続的な実現可能性条件が、1 つのエンドポイントにおける単一の不等式に縮小されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    a, b, c = map(int, input().split())
    
    deficit = c * (a - b)
    
    if deficit <= 0:
        print(0)
        return
    
    t = (deficit + b - 1) // b
    print(t)

if __name__ == "__main__":
    solve()
```このコードは、ビデオ全体を視聴するために必要な追加データの合計を計算し、その量を蓄積するためにダウンロードに必要な秒数を決定します。 表現`(deficit + b - 1) // b`待ち時間を過小評価しないようにするための標準的な上限区分です。 

よくある落とし穴は、整数の除算を切り上げる必要があることを忘れていることです。待機時間が必要よりわずかに短いと、再生の終わり近くでエラーが発生するためです。

 ## 特殊なケース

 エッジケースの 1 つは次の場合に発生します。`b`に非常に近いです`a`。 入力用`a = 100, b = 99, c = 1`、赤字は`1`、待ってます`1`2 番目では、ちょうど十分なバッファが得られます。 アルゴリズムは計算します`ceil(1 / 99) = 1`、要件に一致します。 

もう 1 つのエッジ ケースは、ビデオが長くても不均衡が小さい場合です。`a = 5, b = 4, c = 1000`。 合計の赤字は、`1000`、待機時間は 1 秒ごとにのみ影響します。`4`、結果は次のようになります`250`。 天井部門はシミュレーションなしでこれを正確に処理します。 

最後のエッジケースは次のような場合です`c = 1`。 次に、条件は 1 秒間十分なバッファを確保することになり、式は次のようになります。`ceil((a - b) / b)`これは、再生の最初の 1 秒だけが重要であるという直観と正確に一致します。
