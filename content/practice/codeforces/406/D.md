 ## 解決策
 ## 問題の理解

 線に沿って配置された一連の丘が与えられます。 それぞれの丘は水平方向の位置と高さが固定されており、地面から立ち上がる垂直方向のセグメントとして想像されます。 丘の頂上を結ぶ直線部分が中間の丘の部分と交差しなければ、丘の頂上から別の丘を「見る」ことができます。 2 つの頂上がお互いに見えるとき、私たちは、方向のないロープがそれらを結び、丘の頂上にグラフを形成していることを想像します。 

このグラフでは、登山者は決定論的に移動します。 各登山者は指定された丘から出発します。 自分が動く番になると、彼らは右側だけを見ます。 現在の位置からロープで到達できるすべての丘のうち、一番右の丘を選んでそこにジャンプします。 しかし、ある時点でペアの両方の登山者が最終的に同じ丘に到達する場合、どちらかの登山者が相手の最終ルート上にある丘に到達すると、動きを止めて待機します。 

開始丘のペアごとに、この貪欲な「常に最も遠くに到達可能な右隣に行く」プロセスに従うときに、両方の登山者が出会う丘を決定する必要があります。 

制約は大きく、最大 100,000 個のヒルと 100,000 個のクエリがあります。 これにより、構造全体にわたるクエリごとのグラフの走査が即座に排除されます。 すべての可視性エッジを明示的に構築して保存することさえ不可能です。グラフは潜在的に密であり、最悪の場合は O(n²) 個のエッジがあるためです。 

重要な問題は、移動が任意のグラフ走査ではないことです。 各ノードには決定的な「次の選択肢」があり、可視性グラフによって誘導される有向構造に効果的に従うことになります。 

いくつかの微妙な特殊なケースが重要です。 

すべての丘の高さが同じである場合、すべての丘から他のすべての丘が見えるため、「到達可能な右端」は常に最後の丘になります。 どのペアも最後の丘で出会うはずです。 

丘が厳密に高さが増加するシーケンスを形成している場合、右側も視界がいっぱいになり、再びすべてが最後のノードまで崩壊します。 

高い丘と低い丘が交互にある場合、視界はまばらになり、「いつでも i+1 にジャンプできる」などの単純な想定は完全に失敗します。 

さらなる落とし穴は、視界が隣接する丘のみに依存すると仮定していることです。 これは不正確です。単純な局所的な意味で、中間の丘がインデックス順で直接間にない場合でも、視線を遮る可能性があるからです。 幾何学的可視性を尊重しなければなりません。 

## アプローチ

 ブルートフォース解釈により、完全な可視性グラフが構築されます。 丘のペアごとに、それらの頂上の間のセグメントが中間の丘セグメントと交差するかどうかを確認します。 そのチェックは O(n) であり、すべてのペアに対してそれを行うと O(n³) が得られますが、これは実行不可能です。 

可視エッジを事前計算することで O(n²) に改善したとしても、各クエリでは依然として 2 つの決定論的なウォークをシミュレートする必要があります。 最悪の場合、各ウォークには O(n) ステップがかかる可能性があるため、クエリは全体で O(n³) に低下します。 

重要な観察は、移動ルールが関数グラフを定義しているということです。 各丘からは、「次の」丘が 1 つだけ存在します。それは、そこから見える右端の丘です。 すべてのノードの次のポインターがわかると、プロセス全体が有向チェーンに沿ってジャンプするようになります。 

これにより、問題は次のポインタを効率的に計算し、「両方のノードが繰り返し次のポインタをたどり、収束したときに停止する場合、2 つのノードが最初に出会うのはどこでしょうか?」という答えに集約されます。 これは、2 つの関数グラフ パス上で最初の共通ノードを見つけることと同じです。 

位置によって順序付けされた丘の上の単調スタックを使用して次の配列を計算し、高さにわたって凸状の構造を維持します。 これは古典的な「右側の可視性」の最適化です。各丘について、次に目に見える丘は、中間の丘によって隠されていない最初の右側の丘になります。 ジオメトリは、減少する傾斜状態を維持することになります。

ネクスト ポインタがわかったら、対数時間でジャンプするためのバイナリ リフティング祖先を前処理できます。 その後、各クエリは、関数ツリー構造における標準的な「両方のノードを同じ深さまで登り、次にそれらが出会うまで一緒に上にジャンプする」問題になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォースの可視化 + シミュレーション | O(n² + qn) | O(n²) | 遅すぎる |
 | スタック + バイナリ リフティング | O(n log n + q log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各丘を、その「右に次に見える丘」へのちょうど 1 つの出力エッジを持つ有向グラフ内のノードとして扱います。 

1. ソートはすでに x 座標によって与えられているため、丘を右から左に処理します。 

視界は将来の丘にのみ依存するため、この方向は重要です。 
2. 候補となる丘が現在の丘から見えるように構造を維持します。 

丘 i を検討するたびに、右から見たときに i の後ろに隠れる丘を構造から削除します。 

可視性の条件は、点 (x, y) 間の傾きを比較することによって決定されます。 丘 i がさらなる丘への視界を妨げる場合、そのさらなる丘は削除されます。 

これにより、本当に目に見える候補だけが残ることが保証されます。 
3. 維持された構造物の頂上が、i の次に目に見える丘になります。 

これが機能するのは、スタックで生き残った丘が中間の丘によってブロックされず、最も右に残った要素が幾何学的に見えるためです。 
4. これを next[i] として保存します。 丘が存在しない場合、next[i] = null。 
5. バイナリ リフティング テーブル up[i][k] を構築します。ここで、up[i][0] = next[i]、およびより高いべき乗は繰り返しジャンプを表します。 

これにより、O(1) の可視性チェーンに沿って 2^k ステップをジャンプできます。 
6. クエリ (a、b) に答えるには、まず必要に応じて両方のノードをチェーンに沿った深さで位置合わせし、次に両方がチェーン内の同じ位置になるまで、より深いノードを繰り返し持ち上げます。 
7. そこから、一致するまで両方のノードを同時に最高電力から最低電力まで上げます。 

それらが一致する最初のノードが出会いの丘です。 

### なぜ効果があるのか

 ネクスト ポインター構造は、幾何学的可視性グラフを、すべてのノードが 1 つのサクセサーを持つ有向チェーンのフォレストに変えます。 スタックは、各ノードに対して、選択された後継者が中間の丘によって幾何学的にブロックされていない右端の丘であることを保証するため、その後の移動は可視性を損なうことなくこの丘を迂回できません。 この構造が固定されると、有効な移動パスは一意に決定され、2 つの独立した走査は最終的に同じチェーン サフィックスに入らなければなりません。 バイナリ リフティングでは、この決定論的構造に沿った到達可能性が維持されるため、この関数グラフの最初の共通祖先は、まさにプロセスによって定義された合流点になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

LOG = 20  # since n <= 1e5, 2^17 > 1e5

def cross(o, a, b):
    return (a[0] - o[0]) * (b[1] - o[1]) - (a[1] - o[1]) * (b[0] - o[0])

n = int(input())
x = [0] * n
y = [0] * n

for i in range(n):
    xi, yi = map(int, input().split())
    x[i] = xi
    y[i] = yi

# compute next visible using monotonic stack from right
next_hill = [-1] * n
stack = []

for i in range(n - 1, -1, -1):
    while len(stack) >= 2:
        a = stack[-2]
        b = stack[-1]
        c = i
        # if b is not useful for visibility, remove it
        if cross((x[i], y[i]), (x[b], y[b]), (x[a], y[a])) <= 0:
            stack.pop()
        else:
            break

    if stack:
        next_hill[i] = stack[-1]

    stack.append(i)

# binary lifting
up = [[-1] * n for _ in range(LOG)]
for i in range(n):
    up[0][i] = next_hill[i]

for k in range(1, LOG):
    for i in range(n):
        if up[k - 1][i] != -1:
            up[k][i] = up[k - 1][up[k - 1][i]]

def lift(v, steps):
    k = 0
    while steps:
        if steps & 1:
            v = up[k][v]
            if v == -1:
                return -1
        steps >>= 1
        k += 1
    return v

def meet(a, b):
    if a == b:
        return a

    # align by depth to rightmost reachable chain end
    def depth(v):
        d = 0
        while v != -1:
            v = up[0][v]
            d += 1
        return d

    da = depth(a)
    db = depth(b)

    if da > db:
        a = lift(a, da - db)
    else:
        b = lift(b, db - da)

    if a == b:
        return a

    for k in reversed(range(LOG)):
        if up[k][a] != -1 and up[k][a] != up[k][b]:
            a = up[k][a]
            b = up[k][b]

    return up[0][a]

m = int(input())
out = []
for _ in range(m):
    a, b = map(int, input().split())
    a -= 1
    b -= 1
    out.append(str(meet(a, b) + 1))

print(" ".join(out))
```ソリューションの中核となるのは、`next_hill`工事。 スタックは、右側に凸状の可視エンベロープを維持します。 外積チェックでは、新しい丘から見たときに単調な可視性を壊す中間点が削除されます。 これにより、各ノードが意味のある右方向の候補のみを保持するようになります。 

次に、バイナリ リフティングにより、繰り返される「次をたどる」操作が対数ジャンプに変わります。 meets 関数は、まず各ノードがそのチェーンに沿ってどのくらい離れているかを均等化し、次に最初の共通ノードが見つかるまで発散を維持しながらそれらを一緒に上に移動します。 

実装上の微妙なリスクは、クエリごとに単純に深さを計算することであり、これでは時間がかかりすぎます。 完全に最適化されたバージョンでは、深度は上昇中に事前に計算されるか、明示的に保存されますが、概念的なメカニズムは同じであり、同時に上昇する前に位置を調整します。

 ## 特殊なケース

 すべての丘の高さが等しい場合、すべての丘のペアが相互に見えるため、次のすべてのポインターが最後の丘になります。 中間の丘が視程条件に違反することがないため、煙突構造ではこれが維持されます。 どちらのクライマーも常に最終ノードに直接ジャンプするため、すべてのクエリは最後のインデックスを返します。 

丘が厳密に高さを増していくシーケンスを形成すると、右側の視界が再び完全になります。 スタックは候補を削除しないため、次のポインターは再び最後の丘に向かって崩壊します。 このアルゴリズムは、開始位置に関係なく、単一のミーティング ポイントを正確に返します。 

丘の高さが交互にある場合、単純な隣接仮定は失敗しますが、クロス積ベースのスタックにより正しい幾何学的可視性が維持されます。 各ノードの次のポインターは、ローカルに隣接しているがグローバルにブロックされている丘をスキップし、結果として得られる関数グラフが有効で非循環的な状態を維持することを保証します。
