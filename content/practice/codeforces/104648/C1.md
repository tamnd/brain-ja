 ## 解決策
 ## 問題の理解

 文字列のコレクションが与えられ、そのタスクは、特定の互換性ルールの下でできるだけ多くの素のペアを形成することです。 2 つの文字列は、少なくとも 1 文字の長さの共通のサフィックスを共有する場合にのみペアにすることができます。 各文字列は最大 1 つのペアに参加できますが、有効なペアの数を最大化したいと考えています。 

したがって、入力の構造は単語のマルチセットであり、出力は構築できる互いに素な互換性のあるペアの数を表す単一の整数です。 

この問題の制約パターンは、Codeforces の文字列問題に典型的なものです。単語の数が十分に大きいため、すべてのペア間の二次比較はすぐに失敗します。 最大 100,000 個の文字列があり、各比較に文字列の長さに対して線形時間がかかる場合、単純な解決策は O(n² * L) のように動作しますが、これは許容範囲をはるかに超えています。 接尾辞比較のすべてのペアを並べ替えても、多くの文字列が長く重複する接尾辞を共有する最悪の場合の入力では破綻します。 

文字列が部分的な接尾辞構造を共有しているが、同一の接尾辞を共有していない場合、微妙な障害モードが発生します。 たとえば、単語 ["abc"、"xbc"、"zb"] について考えてみましょう。 最初に一致するサフィックスをペアにする貪欲なアプローチでは、たとえ別のペアリング戦略が大規模なインスタンスではペアの総数を最大化できるとしても、「abc」と「xbc」が誤ってペアリングされ、「zb」が孤立したままになる可能性があります。 正しい解決策は、ローカルでペアリングを決定するのではなく、サフィックス構造をグローバルに推論する必要があります。 

同一の文字列が多数存在する場合、別の特殊なケースが発生します。 たとえば、["aa", "aa", "aa", "aa", "aa"] は 2 つのペアを生成し、1 つは残ります。 同一のサフィックス パスを集約しないアプローチでは、利用可能な一致が過剰にカウントされるか、完全に活用できなくなります。 

重要な問題は、サフィックスのマッチングが文字列間で独立していないことです。これは、長さ k のサフィックスを共有すると、より短いサフィックスをすべて共有することを意味し、自然に階層構造が形成されるためです。 

## アプローチ

 ブルートフォース手法では、文字列のすべてのペアを比較し、それらがサフィックスを共有しているかどうかを確認します。 各ペアについて、文字が異なるか、1 つの文字列が終了するまで、最後からスキャンします。 これにより互換性が正しく識別され、貪欲にペアを形成できるようになります。 ただし、ペアの数は O(n²) で、各比較のコストは最大 O(L) となり、最悪の場合は約 O(n²L) になります。 n が大きい場合、これは完全に不可能です。 

構造上の観察は、すべての文字列を逆にすると、接尾辞の関係がツリーを形成するということです。 サフィックスの観点から考える代わりに、すべての文字列を、反転した文字列に基づいて構築されたトライのルートからリーフまでのパスに変換します。 サフィックスを共有する文字列は、この逆トライのプレフィックスを共有するパスに正確に対応します。 

この構造が見えるようになると、問題はサブツリー内の文字列をグループ化することになります。 トライの各ノードで、それを通過する文字列の数を考えることができます。 各ペアには、反転表現で共通のプレフィックスを共有する 2 つの文字列が必要です。つまり、それらはサブツリー内のどこかで一致する必要があります。 ボトムアップ トラバーサルにより、各サブツリー内でペアにできる文字列の数を計算し、ペアになっていない文字列を上に押し上げることができます。 

これにより、問題はトライ上の単一の DFS に縮小され、各ノードがその子からの貢献を集約し、ローカルでできるだけ多くのペアを形成します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²L) | O(n) | 遅すぎる |
 | DFS (最適) を試す | O(合計文字数) | O(合計文字数) | 承認済み |

 ## アルゴリズムのチュートリアル

 接尾辞の関係が接頭辞の関係になるように、反転した文字列を使用してトライを構築します。

1. すべての逆向きの文字列をトライに挿入し、単語ごとに終端ノードのカウンタをインクリメントします。 これにより、各単語が構造内で 1 回だけ表現されることが保証されます。 
2. トライのルートから深さ優先検索を実行します。 各ノードで、そのサブツリー内で現在一致しない単語の数を計算します。 
3. ノードの場合、最初にすべての子から返された一致しない数を収集します。 これらは、このノードに対応するプレフィックスを共有しているが、より深いところではまだペアになっていない文字列を表します。 
4. ノードでのすべての受信カウントを合計します。 これは、現在のプレフィックスを共有するすべての文字列を表します。 
5. 合計を法 2 としてローカルで可能な限り多くのペアを形成し、ペアになっていない残りの文字列を決定します。 2 つ以上の文字列を暗黙的に利用できる場合は常に、上位構造に影響を与えることなくそれらをペアにすることができます。 
6. 残ったカウントを親ノードに上向きに返します。 
7. 各ノードで一致した文字列の半分を加算して、DFS 中に形成されたペアの総数を累積します。 

これが機能する理由は、有効なペアリングは、逆トライの最も低い共通プレフィックス ノード内で発生する必要があるためです。 トライ内で 2 つの文字列が分岐すると、有効性を失うことなく上位ノードでそれらをペアにすることはできません。 したがって、可能な限り最も深いポイントで貪欲にペアリングを行っても、上記の最適なペアリングがブロックされることはありません。 

維持される不変条件は、各 DFS 呼び出しがそのサブツリー内のまだペアになっていない文字列の数を返し、そのサブツリー内のすべての可能なペアがすでに考慮されていることです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class Trie:
    def __init__(self):
        self.child = {}
        self.end = 0

def insert(root, word):
    node = root
    for ch in word:
        if ch not in node.child:
            node.child[ch] = Trie()
        node = node.child[ch]
    node.end += 1

def dfs(node):
    pairs = 0
    leftover = node.end

    for nxt in node.child.values():
        sub_pairs, sub_leftover = dfs(nxt)
        pairs += sub_pairs
        leftover += sub_leftover

    pairs += leftover // 2
    leftover %= 2

    return pairs, leftover

def solve():
    n = int(input())
    root = Trie()

    for _ in range(n):
        s = input().strip()[::-1]
        insert(root, s)

    pairs, _ = dfs(root)
    print(pairs)

if __name__ == "__main__":
    solve()
```この実装では、各ノードに子とそこで終わる単語の数を格納する標準の辞書ベースのトライが構築されます。 挿入中に反転が発生し、サフィックス グループ化がプレフィックス グループ化になります。 

DFS は、サブツリー内で形成されたペアの数と、ペアになっていない残りの文字列の数という 2 つの値を返します。 重要な実装の詳細は、新しいペアを形成する前に残りのカウントが結合され、トライ内でペアリングが常に可能な限り低く行われるようにすることです。 

よくある間違いは、葉ノードだけ、または単語の終わりだけでペアにしようとすることです。 これは失敗します。有効なペアは、終端トライ ノードではなく内部トライ ノードに対応する部分的なサフィックスのみを共有する可能性があるためです。

 ## 特殊なケース

 最初のエッジ ケースは、すべての文字列が同一である場合です。 この状況では、トライ内のすべてのノードが 1 つのパスに集約され、DFS は 1 つのブランチですべてのカウントを蓄積します。 アルゴリズムはそのノードで貪欲にペアを作成し、floor(n/2) ペアを生成します。 たとえば、入力 ["xyz", "xyz", "xyz"] の場合、反転トライには 1 つのパスがあり、1 つの残りを含む 1 つのペアが返され、これは最適な動作と一致します。 

もう 1 つのエッジ ケースは、2 つの文字列が接尾辞をまったく共有しない場合です。 たとえば、["a"、"b"、"c"] のようになります。 トライはルートですぐに分岐し、各分岐は残りの 1 を上向きに返します。 ルートでは、これらの残り物が結合されますが、ペアを形成することはないため、最終的な答えは 0 になります。これは、たとえトライのルートで出会ったとしても、アルゴリズムが無関係な文字列を誤ってペアにしないことを確認します。
