 ## 解決策
 ## 問題の理解

 文字列のコレクションが与えられ、そのタスクは、非常に具体的な互換性ルールの下で、できるだけ多くの文字列のペアを形成することです。 2 つの文字列は、空ではないサフィックスを共有する場合にのみ有効な方法でペアリングできます。ペアリングは、各文字列が最大 1 回使用されるように、構築できるそのような素なペアの数を最大化することを目的としています。 

問題の構造は基本的に単語間の接尾辞の関係に関するものです。 各文字列を右から左に読むものと考えると、問題は、端から比較したときに、できるだけ遅く「一致」する文字列をグループ化することになります。 共有サフィックスが深くなるほど、2 つの文字列の関連性がより強くなりますが、目的は類似性を最大化することではなく、素の有効なペアの数を最大化することです。 

入力は文字列のリストです。 出力は、上記のルールに従って形成できる有効なペアの数を表す単一の整数です。 

この制約は、単純なペアごとの比較アプローチが生き残れないことを意味します。 最大約 10^5 の文字列があり、各文字列が長くなる可能性がある場合、すべてのペアを直接比較すると、サフィックス比較の数が 2 次爆発的に増加し、直ちに遅すぎます。 すべてのペアごとの最長の共通サフィックス値を構築するだけでも、時間制限を数桁超えてしまいます。 

いくつかのエッジケースは、構造がないと貪欲なローカルマッチングが失敗する理由を明らかにします。 たとえば、すべての文字列が同一の場合、`["abc", "abc", "abc", "abc"]`、正解は2ペアです。 単純な貪欲なアプローチでは、グローバル グループ化を尊重しない場合、誤って文字列をペアにする可能性があり、サフィックス階層の奥深くでより適切に構造化されたペアリングがブロックされる可能性があります。 

別の失敗例は、サフィックスが部分的に重複する場合に発生します。 例えば`["aba", "cba", "bba", "aba"]`。 局所的に類似した文字列は、早期にペアリングを決定することを促す可能性がありますが、正しい解決策は、浅い一致ではなく完全な接尾辞構造によるグループ化に依存します。 

重要な問題は、互換性が階層的であり、ペアごとに独立していないことです。 

## アプローチ

 ブルートフォース戦略では、文字列の各ペア間で最も長い共通サフィックスを計算し、有効なサフィックス関係を持つペアを貪欲に一致させようとします。 これにはすぐに 2 つの問題が発生します。 まず、ペアごとのサフィックス類似度の計算にはペアごとに O(L) のコストがかかり、全体では O(N^2 L) になります。 第 2 に、たとえこれらの値が利用可能だったとしても、最適な素のペアを選択することは、密なグラフに対する全体的なマッチングの問題であり、制約に対して遅すぎる一般的なマッチング アルゴリズムが必要となります。 

重要な観察は、すべての文字列を逆にすると、接尾辞の関係が自然にツリー構造を形成するということです。 サフィックスについて考える代わりに、反転した文字列のプレフィックスについて考えます。 これにより、問題が逆の単語に基づいて構築されたトライに変換されます。 トライの各ノードは、単語の一部のサブセットの共通の接尾辞を表し、その接尾辞を共有するすべての単語は、そのノードをルートとするサブツリーに含まれます。 

問題をこのように捉えると、ペアリングは各サブツリー内でローカルになります。 どのノードでも、その子孫セット内でできるだけ多くの単語をペアにしたいと考えています。 ノードに複数の子サブツリーがある場合、各サブツリーは多数の「ペアになっていない残りの文字列」を提供し、それらの残りは上位の祖先で出会った場合にのみペアになります。 

中心的なアイデアは、トライの事後探索を実行し、各サブツリーに残っているペアになっていない文字列の数を計算し、子からのカウントを使用して各ノードでできるだけ多くのペアを貪欲に一致させることです。 これにより、グローバル ペアリングの問題が、一致しないアイテムのボトムアップ フローに縮小されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースペアワイズマッチング | O(N^2・L) | O(N^2) | 遅すぎる |
 | トライ + ポストオーダーの貪欲なペアリング | O(合計文字数) | O(合計文字数) | 承認済み |

 ## アルゴリズムのチュートリアル

 データ構造内でサフィックスがプレフィックスになるように、反転した文字列を使用してトライを構築します。 

1. すべての文字列を反転してからトライに挿入します。 各終端ノードは、そのノードで終わる単語の数を示すカウントを増やします。 これにより、すべての文字列がサフィックス構造に基づいてグループ化されます。 
2. トライのルートから深さ優先のトラバースを実行します。 各ノードで、子の処理後にサブツリー内のペアになっていない文字列の数を計算します。 
3. 各ノードについて、その子によって返された「不対のカウント」を収集します。 これらは、現在のサフィックスを共有しているがまだ空いている文字列を表します。 
4. 現在のノードのすべての子の剰余を合計します。 この合計が偶数であれば、すべてをローカルでペアにすることができるため、上向きには何も渡されません。 奇数の場合は、ちょうど 1 つの文字列がペアになっていない状態のままにし、親ノードに伝播する必要があります。 
5. ノードで残りの文字列を結合するたびに、子からの寄与の合計の半分と、このノードで正確に終了する文字列を加えて、ローカルで形成したペアの数を数えます。 
6. ペアの合計数をグローバルに累積しながら、ペアになっていない文字列の数 (正規化された形式では 0 または 1) を親に返します。 

微妙な点は、ペアリングは常にトライの可能な限り早い段階で行われるということです。これは、より深い文字列を最初にペアリングしても将来の可能性が制限されることはありませんが、ペアリングを遅らせると、一致しない文字列がツリーの上位に取り残されるリスクが増大するだけであるためです。 

### なぜ効果があるのか

 トライは、あらゆる深さのサフィックス等価クラスによって文字列を分割します。 どのノードでも、そのサブツリー内のすべての文字列はそのノードによって表されるサフィックスを共有し、サブツリーの外にある文字列はそれより長いサフィックスを共有できません。 これにより、厳密な分離が作成されます。サブツリー内のペアリングの決定は、親ノードを経由する場合を除き、外部からの文字列を使用しても改善できません。

不変条件は、ノードの処理後、アルゴリズムがそのサブツリー内全体で形成されるペアの数を最大化し、必要最小限のペアになっていない文字列のみが上方に渡されるということです。 すべてのペアリングには 2 つの文字列が必要であり、サブツリー内のすべての候補文字列はより深いサフィックス構造に関して同等であるため、サブツリー内の代替配置は可用性の制約に違反することなくペアの数を増やすことはできません。 

## Python ソリューション```python
import sys
sys.setrecursionlimit(10**7)
input = sys.stdin.readline

class Node:
    __slots__ = ("ch", "cnt")
    def __init__(self):
        self.ch = {}
        self.cnt = 0

def solve():
    n = int(input())
    root = Node()

    # build trie of reversed strings
    for _ in range(n):
        s = input().strip()[::-1]
        cur = root
        for c in s:
            if c not in cur.ch:
                cur.ch[c] = Node()
            cur = cur.ch[c]
        cur.cnt += 1

    ans = 0

    def dfs(node):
        nonlocal ans
        leftover = node.cnt

        for nxt in node.ch.values():
            leftover += dfs(nxt)

        ans += leftover // 2
        return leftover % 2

    dfs(root)
    print(ans)

if __name__ == "__main__":
    solve()
```trie ノードには、子の遷移と、そのノードで正確に終了する文字列の数のカウンターが格納されます。 文字列を反転すると、サフィックスがプレフィックスになり、トラバーサルでサフィックスと同等の文字列が自然に集約されます。 

DFS は、パリティのような値、つまりペアになっていない文字列がサブツリーに 1 つ残っているかどうかを返します。 グローバル応答は、2 による整数除算を使用して、ノードで 2 つの使用可能な文字列が一致するたびに累積されます。 

よくある間違いは、リーフ ノードでのみ貪欲に一致させようとすることです。 これは、複数のブランチが集まる内部ノードにペアリングの機会が存在することが多いため、失敗します。 もう 1 つの微妙な問題は、リーフ ノードだけでなく、内部ノードで終わる文字列もペアリング能力に寄与することを忘れていることです。 

## 実用的な例

 入力を考慮してください:```
4
aba
cba
bba
aba
```文字列を反転してトライに挿入します。 構造グループの接尾辞は次のとおりです`"aba"`そして`"cba"`逆形式の共有プレフィックスに基づいています。 

ノードで`"aba"`が 2 回出現すると、それら 2 つはすぐに 1 つのペアを形成します。 他の枝からの残りの文字列は上に伝播します。 

| ノード | CNT | 子供の食べ残し | 合計 | ペアが形成されました | 残り物は返却されました |
 | --- | --- | --- | --- | --- | --- |
 | アバの葉 | 2 | 0 | 2 | 1 | 0 |
 | 他の葉 | 各1個 | 0 | 1 | 0 | 1 |

 最終的な答えは 1 ペアで、1 つの文字列は未使用のままになります。 

このトレースは、無関係な分岐を妨げることなく、同一の文字列がどのようにローカルでペアになっているかを示しています。 

ここで次のことを考えてみましょう。```
6
aa
aa
a
a
aaa
aaa
```ここでは、より深いサフィックス一致が優勢です。 このトライは、すべての文字列をネストされたサフィックス チェーンにグループ化します。 

より深いノードでは、`"aaa"`最初にペア、次に`"aa"`、 それから`"a"`残りの空き状況に応じて。 

| ノードの深さ | 貢献 | ペア | 残り物 |
 | --- | --- | --- | --- |
 | 最も深い (aaa) | 2 | 1 | 0 |
 | ミッド (aa) | 2 | 1 | 0 |
 | ルートレベル (a) | 2 | 1 | 0 |

 合計ペア = 3。 

This demonstrates that the algorithm always resolves the most specific suffix matches before broader ones.

 ## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(合計文字数) | Each character is inserted once into the trie and visited once in DFS |
 | スペース | O(合計文字数) | Trie stores one node per unique prefix of reversed strings |

 トライ エッジの総数が文字列長の合計に対して線形であるため、アルゴリズムは制約内に快適に適合し、ペアごとの比較が回避されます。 Even with large inputs, each character is processed a constant number of times.

 ## 特殊なケース

 次のような単一の短い文字列の場合`"a"`、トライはカウント 1 の 1 つのノードで構成されます。DFS は残りの 1 を返し、ペアは形成されず、正しく 0 が生成されます。 

次のような同じ文字列が繰り返される場合`"aaaa"`偶数回出現すると、すべてのコピーが同じトライ ノードのローカル ペアリングで消費されます。 このアルゴリズムは、不要な残り物を上方に伝播させることなく、即座にペアを形成します。 

次のような斜めの接尾辞チェーンの場合`"a"`、`"aa"`、`"aaa"`、構造はトライ内で単一のパスを形成します。 ペアリングは最初に最も深いレベルで行われ、より長いサフィックス一致が優先されるようになり、残りの伝播によって上位ノードの実現可能性が正しく維持されます。
