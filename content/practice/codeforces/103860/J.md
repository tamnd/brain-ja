 ## 解決策
 ## 問題の理解

 各テスト ケースには、10 問の多肢選択クイズの隠された「解答キー」が記述されており、すべての質問に A、B、C、D の中から正解の選択肢が 1 つだけあります。受験者は同じクイズを繰り返し受験し、各試行で 2 つのことが記録されます。選択された 10 文字の解答文字列と、最終スコアです。各正解は 10 点で、その他は 0 点です。 

タスクは、一意の応答キーを回復することではなく、観察されたすべての試行を考慮して、まだ可能な異なる応答キーの数を数えることです。 回答キーの候補は、記録されたすべての試行と一致する場合に有効です。つまり、送信された各文字列と位置ごとに比較したときに、一致の数が報告されたスコアを 10 で割った値と一致する必要があります。 

したがって、非表示オブジェクトは 4 文字のアルファベットにわたる長さ 10 の文字列であり、すべての観察により、その文字列内の固定パターンに一致する位置の数に制約が課されます。 

制約は非常に厳しい構造になっています。 非表示の文字列には 10 個の位置しかないため、合計の検索スペースは 4^10 で、これは約 100 万通りの可能性があります。 ただし、テスト ケースと試行の数は多く、すべてのケースで合計最大 20,000 行になります。 これにより、単純に入れ子になった方法ですべての制約に対してすべての候補文字列をチェックすることは直ちに除外されます。これは、最悪の場合、およそ 1e6 x 2e4 を乗算することになるからです。 

すべてのスコアがゼロの場合、微妙な特殊なケースが発生します。 これは、単一の回答キーがあるという意味ではなく、送信されたすべての文字列のすべての位置で正しい回答が異なる必要があることを意味します。 複数の提出者が同意しない可能性があるため、立場を超えて独立していると誤って想定することが簡単に起こります。 たとえば、ある試行が「AAAAAAAAAA 0」の場合、真のキーのどの位置にも A を含めることはできませんが、別の試行では、共同制約されない限り、一部の位置に A を含めることができる可能性があります。 

主な問題点は、各試行が 10 次元の離散ベクトルに対するグローバルな制約であり、位置ごとに独立していないことです。 

## アプローチ

 ブルートフォース手法では、考えられるすべての回答キー、つまり {A、B、C、D} にわたる 10 個の長さの文字列すべてが列挙されます。 候補キーごとに、すべての試行をチェックし、一致する位置の数を計算し、指定されたスコアを 10 で割った値に等しいことを確認します。問題定義を直接シミュレートしているため、これは正しいです。 

問題は規模だ。 候補は 4^10、約 1,048,576 個あります。 各候補について、最大 20,000 回の試行と比較することができ、各試行には 10 回の比較がかかります。 これにより、最悪の場合、およそ 2e11 文字の比較が行われることになり、これは実現可能な制限をはるかに超えています。 

構造は別の角度から示唆しています。 隠された答えは 10 桁のみに依存し、試行ごとに固定文字列との一致数が制限されます。 グローバルに考える代わりに、位置ごとに値を割り当てるという観点から考えることができますが、制約は試行ごとに単一の等価制約を通じてすべての位置を結合します。 

重要な観察は、解答キーを 4 つのシンボルにわたる 10 次元のベクトルとして扱うことができ、各試行はそのベクトルとの一致をカウントする関数を定義するということです。 次元が小さく固定 (10) であるため、考えられるすべてのキーを列挙できますが、チェックを効率的に行う必要があります。 秘訣は、試行ごとに、候補ごとの高速検証を可能にするビットマスクのような構造または周波数グループを事前計算することです。 ただし、10 は小さいため、最も直接的な最適化が許容されます。テスト ケースごとに 1 回、すべての 4^10 文字列をブルート フォースで実行しますが、各候補を O(n * 10) で検証し、早期終了による枝刈りと合計 n に対する厳しい制約に依存します。

これを確認するためのより構造化された方法は、すべての試行を事前に保存し、各候補の回答について試行ごとの一致を蓄積することです。 制約は一貫しており、10 は固定されているため、不一致が検出された場合の早期終了により、平均コストが大幅に削減されます。 

したがって、問題は、テスト ケースごとに 1 回、考えられるすべての回答キーを列挙し、それらを効率的に検証することに帰着します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース列挙 | O(4^10・n・10) | O(n) | 最悪の場合遅すぎる |
 | 早期プルーニングによる最適化された列挙 | O(4^10 · n) 償却 | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. テスト ケースのすべての試行を読み取り、10 文字の文字列とそれに必要な一致数 k (スコアを 10 で割った値) で構成される各ペアを保存します。 これにより、一連のグローバル制約が与えられます。 
2. アルファベット {A、B、C、D} を含むすべての 10 文字の文字列を列挙します。 このような各文字列は、回答キーの候補となります。 これは、候補の総数がちょうど 4^10 で固定されており小さいため、実現可能です。 
3. 候補キーごとに、記録されたすべての試行を繰り返します。 
4. 試行ごとに、候補と試行文字列の間で一致する位置の数を計算します。 これは単純な 10 段階の比較です。 
5. 一致カウントが試行に必要な k と異なる場合は、この候補を直ちに破棄し、次の候補に移動します。 ほとんどの無効な候補者はすぐに失敗するため、この早期の終了は非常に重要です。 
6. 候補者がすべての試行に合格した場合、それを有効な回答キーとしてカウントします。 
7. すべての候補をチェックした後、合計数を出力します。 

これが機能する理由は、問題ステートメントから導出されたまったく同じ制約に対してすべての候補がチェックされるためです。 すべての制約セットの交差によって定義されたソリューション セットのメンバーシップを直接テストしています。また、可能なキーの有限空間全体を徹底的に列挙するため、有効な割り当てを見逃すことはありません。 

正確さは、各候補が独立しており、すべての制約に対して完全に検証されているという事実にかかっており、列挙は 4 つのシンボルにわたる 10 長の文字列の空間全体を 1 回だけカバーします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from itertools import product

def solve():
    t = int(input())
    
    alphabet = ['A', 'B', 'C', 'D']
    all_candidates = list(product(alphabet, repeat=10))
    
    for _ in range(t):
        n = int(input())
        tests = []
        for _ in range(n):
            s, a = input().split()
            a = int(a) // 10
            tests.append((s, a))
        
        ans = 0
        
        for cand in all_candidates:
            ok = True
            for s, need in tests:
                cnt = 0
                for i in range(10):
                    if cand[i] == s[i]:
                        cnt += 1
                if cnt != need:
                    ok = False
                    break
            if ok:
                ans += 1
        
        print(ans)

if __name__ == "__main__":
    solve()
```コードはまず、アルファベットのデカルト積を使用して、すべての 4^10 候補文字列を事前計算します。 これにより、テスト ケースごとに再構築する必要がなくなります。 テスト ケースごとに、観察されたすべてのクイズ結果を解析し、スコアを必要な一致数に変換します。 

検証中、各候補はすべての試行に対してチェックされます。 内側のループは正確に 10 個の位置を比較し、一致をカウントします。 早めに中断することで、矛盾が見つかった場合に残りの試行をチェックするのに時間を無駄にすることがなくなります。 

一般的な実装上の落とし穴は、スコアを 10 で割って正しい位置の数に変換することを忘れることです。もう 1 つは、テスト ケースごとに候補空間を再構築することです。これにより、不必要なオーバーヘッドが追加されます。

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from itertools import product

    input = sys.stdin.readline

    all_candidates = list(product(alphabet, repeat=10))

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        tests = []
        for _ in range(n):
            s, a = input().split()
            a = int(a) // 10

        for cand in all_candidates:
            ok = True
            for s, need in tests:
                cnt = 0
                for i in range(10):

                        cnt += 1
                if cnt != need:
                    ok = False
                    break
            if ok:
                ans += 1
        out.append(str(ans))
    return "\n".join(out)

 ## 特殊なケース

 重要なエッジ ケースは、すべての試行のスコアが 0 である場合です。その状況では、すべての受験者は、試行ごとに少なくとも 1 つの位置で各テスト文字列に同意しなければなりません。 必要な数の位置で単一の禁止パターンにさえ一致する候補は検証中に除外されるため、アルゴリズムはこれを自然に処理します。 

もう 1 つのエッジケースは、すべての試技がフルスコアと同一である場合です。 たとえば、すべての試行が「AAAAAAAAAA 100」の場合、すべて A の文字列のみが残ります。 列挙によってそれが検出され、他のすべての候補は最初のチェックで拒否されます。 

最後に、部分制約が矛盾するケースは正しく処理されます。これは、拒否が試行ごとに独立して発生し、候補は制約の交差構造と一致して、すべての制約を同時に満たす必要があるためです。
