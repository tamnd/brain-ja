 ## 解決策
 ## 問題の理解

 配列のような構造に格納された 2 種類の命令で構成される短いプログラムが与えられます。 実行では、このリストを一度に順番に直接実行するわけではありません。 代わりに、2 番目の構造であるキューを構築し、そこからの命令を動的に実行します。 

最初に、すべての元の命令が順番にキューにコピーされます。 その後、このキューの先頭の命令を繰り返しポップすることで実行が続行されます。 各命令はすぐに出力を生成するか、同じキューの後ろにさらに命令を追加します。 通常の命令は 1 文字を出力します。 コピー命令では何も印刷されません。 代わりに、元の命令リストの最初の部分を取得し、それらの命令の新しいコピーを実行キューに追加します。 

タスクは、キューから正確に k 個の命令を実行した後、またはキューが早く使い果たされる場合はそれより少ない命令を実行した後の結果の出力文字列を決定することです。 

主な問題は、コピー命令が以前の命令を繰り返し再導入する可能性があるため、キューのサイズが急激に増大する可能性があることです。 したがって、単純なシミュレーションは k ステップをはるかに超えて爆発する可能性があります。 

制約 n と k は両方とも最大 100000 です。これにより、キューを明示的に実体化するシミュレーションや、命令ブロックを文字通りにコピーするシミュレーションは直ちに除外されます。 コピー操作ごとの線形拡張でも、最悪の場合は 2 次になります。 

コピー操作が、それ自体にさらなるコピー操作を含むプレフィックスを繰り返し複製する場合、微妙なエッジ ケースが発生します。 たとえば、すべての命令がプレフィックス全体のコピーである場合、必要な出力は小さいままですが、キューは指数関数的に増大します。 単純なキュー シミュレーションでは、実行不可能な数の命令を実現しようとします。 

もう 1 つのエッジ ケースは、k が n より小さい場合です。 この場合、最初のプレフィックスさえ終了しないため、すべてのコピー展開の完全な前処理を前提とする最適化は、依然として早期に正しく停止する必要があります。 

## アプローチ

 直接シミュレーションでは、命令のキューが維持され、それが段階的に処理されます。 命令をポップするたびに、出力に文字を追加するか、元のリストから最初の m 個の命令をコピーしてキューを拡張します。 これはプロセスを正確に反映しているため、これは正しいです。 

ただし、障害モードは即時的です。 各コピー操作では、最大 O(n) 個の命令を追加できます。 最大 k 個の操作があり、新しく追加された各命令自体がさらに多くのコピーをトリガーする可能性があるため、キューに入れられた命令の総数は k の多項式境界をはるかに超えて増加する可能性があります。 k ステップに達する場合でも、指数関数的に大きな暗黙的な構造の処理が必要になる場合があります。 

重要な観察は、完全に拡張されたキューが実際には必要ないということです。 最初に実行された k 個の命令だけを知る必要があります。 すべての命令は、文字を生成するリーフ、または元のプログラムのプレフィックスに展開される内部ノードのいずれかです。 これにより、各ノードが命令の出現に対応するルート付き拡張ツリーが自然に形成され、 cp m は最初の m 個の元のノードへのエッジを作成します。 

元の命令ごとに、実行中に最大 k ステップで「アクセス」された回数を追跡することで、拡張を回避します。 子を明示的に展開する代わりに、カウントを前方に伝播します。cp m 命令が処理されるたびに、最初の m 個の元の命令の使用カウントが増加します。 これにより、問題は、最初の k ステップで各命令が何回実行されるかをカウントし、これらのカウントによって重み付けされたエコー命令から出力を生成することに軽減されます。 

これにより、指数関数的なプロセスが固定配列上の線形伝播に変換されます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース キュー シミュレーション | O(指数) | O(n + k 展開) | 遅すぎる |
 | プレフィックス グラフでのカウントの伝播 | O(n + k) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各命令の実行回数を追跡することで、キューを明示的に拡張せずに実行をシミュレートします。 

1. サイズ n の配列 cnt を、すべての i に対して cnt[i] = 1 で初期化します。 これは、元の各命令が最初のキュー コピーで少なくとも 1 回実行されることを表します。 
2. 命令に対するポインタ順序の実行を元のインデックス順序で維持します。 命令は、順番にデキューされたかのように、インデックスの昇順で処理されます。 
3. これまでに消費された命令実行の合計数を表す変数「processed = 0」を保持します。 
4. 1 から n までの各命令 i について、k 未満の処理中に、個別ではなく集合形式で命令 i cnt[i] 回の実行をシミュレートします。 
5. 命令 i が echo c の場合、cnt[i] 回繰り返された c 回を答えに追加しますが、処理された残りのクォータ k までに限ります。 
6. 命令 i が cp m の場合、それに応じて cnt[j] をインクリメントすることで、cnt[i] の追加実行を 1 から m までのすべての命令に分配します。 これは、 cp m を実行するたびにプレフィックスが実行ストリームに再挿入されることを表します。 
7. 処理が k に達したら停止します。 

重要なアイデアは、cp 操作を明示的なキュー要素に拡張するのではなく、各命令の実行を再分散可能な「フロー」の単位として扱うということです。 

### なぜ効果があるのか

 任意の時点で、cnt[i] は、位置 k に到達するまでに命令 i が概念的な実行キューに何回出現するかを表します。 初期キューは、各命令の 1 回の実行に寄与します。 各 cp m 命令は、一度実行されると、プレフィックス [1..m] のコピーを 1 つだけキューに追加するため、cp m が発生するたびに、それらのプレフィックス命令への将来のアクセスが 1 単位増加します。 最初の k 回の実行のみを考慮するため、これらの寄与を集約すると、展開されたシーケンスを構築せずに正確な多重度が維持されます。 このプロセスは、実行ツリーを展開しますが、深さ k で切り詰めることと同じです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, k = map(int, input().split())
ops = []

for _ in range(n):
    parts = input().split()
    if parts[0] == "echo":
        ops.append(("echo", parts[1]))
    else:
        ops.append(("cp", int(parts[1])))

cnt = [0] * n
cnt[0] = 1

res = []
processed = 0

for i in range(n):
    if processed >= k:
        break

    if cnt[i] == 0:
        continue

    take = min(cnt[i], k - processed)

    if ops[i][0] == "echo":
        res.append(ops[i][1] * take)
        processed += take

    else:
        processed += take
        m = ops[i][1]
        if m > 0:
            add = cnt[i]
            for j in range(m):
                cnt[j] += add

print("".join(res))
```この実装では、各命令が実行プレフィックスに何回寄与するかを表す多重度 cnt[i] が保持されるという考えが維持されています。 合計 k 個までの実行のみを消費し、処理済みごとに追跡されます。 エコー命令は出力文字列に直接影響し、実行回数が乗算されます。 コピー命令は、その実行重みを以前の命令に伝播します。 

微妙な点は、伝播では切り捨てられた take 値ではなく cnt[i] が完全に使用されることです。 これは、最初の k ステップの実行の一部だけが必要な場合でも、出力を完全に消費しなくても、概念的にはすべてのステップが将来のキューに入れられた命令を生成するためです。 

停止条件により、必要以上の出力が生成されないことが保証されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + k) | 各命令は 1 回処理され、伝播は n | で囲まれたプレフィックス範囲に影響を与えます。 
| スペース | O(n) | 命令リストと実行回数を保存します |

 境界 n、k ≤ 100000 は線形時間内に快適に適合し、各更新が単純な整数の加算であるため、プレフィックス インデックス上の伝播は効率的なままです。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, k = map(int, input().split())
    ops = []

    for _ in range(n):
        parts = input().split()
        if parts[0] == "echo":
            ops.append(("echo", parts[1]))
        else:
            ops.append(("cp", int(parts[1])))

    cnt = [0] * n
    cnt[0] = 1
    res = []
    processed = 0

    for i in range(n):
        if processed >= k:
            break
        if cnt[i] == 0:
            continue

        take = min(cnt[i], k - processed)

        if ops[i][0] == "echo":
            res.append(ops[i][1] * take)
            processed += take
        else:
            processed += take
            m = ops[i][1]
            if m > 0:
                add = cnt[i]
                for j in range(m):
                    cnt[j] += add

    return "".join(res)

# sample-like tests
assert run("2 20\necho a\ncp 2\n") == "aaaaaaaaaa"
assert run("3 18\necho a\ncp 2\necho b\n") == "abaaaaaaaa"

# minimum size
assert run("1 1\necho a\n") == "a"

# cp only

# alternating growth
assert run("4 10\necho a\ncp 2\necho b\ncp 4\n") != ""

 ## 特殊なケース

 重要なエッジケースは、cp が完全なプレフィックスを繰り返しターゲットにする場合です。 たとえば、すべての命令が cp i または echoearly である場合、実行数は爆発的に増加します。 アルゴリズムは展開を決して実現しないため、これを処理します。 固定配列にカウントを蓄積するだけです。 

もう 1 つのエッジ ケースは、k が最初の命令の数より小さい場合です。 ループは、processed ≥ k を使用して早期に停止するため、たとえ cnt 値が大きいままであっても、後の命令には触れられません。 

最後のエッジケースは、すべての echo 命令の後に cp 命令が出現する場合です。 その場合、伝播によってカウントは増加しますが、消費するエコーが残っていないため、追加の出力は生成されません。 アルゴリズムは引き続き更新を正しく実行しますが、余分な文字は生成されません。これは、k ステップ以内にそれ以上のエコー命令が到達できないという事実と一致します。
