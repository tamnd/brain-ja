 ## 解決策
 ## 問題の理解

 私たちは、時間が通常の 24 時間時計で進行するのではなく、未知の時間数の後に循環する周期的な時間システムを観察しています。$k$。 このシステムでは、到達後を除いて通常通り時間が1時間進みます。$k-1$、0 に戻ります。したがって、状態空間は実質的に算術剰余になります。$k$。 

3 つの整数が与えられます$x$、$y$、 そして$z$。 時計が示しているという解釈です$x$今、そして正確に進んだ後$y$何時間も表示されます$z$。 タスクは、有効な値を決定することです。$k$それがこの移行を可能にするか、そのような移行が不可能であると報告する$k$存在します。 複数の値がある場合、$k$仕事はどれでもOKです。 

重要な制約は、両方とも$x$そして$z$と同じ大きさにすることができます$10^9$、 そして$y$まで大きくすることもできます$10^9$、まであるかもしれませんが、$10^5$テストケース。 これにより、あらゆる可能性を試みるアプローチは即座に排除されます。$k$、 以来$k$それ自体は最大まで行くことができます$2 \cdot 10^9$、テストケースごとにリニアスキャンさえも不可能です。 

微妙な点は、ラッピング動作が完全に係数に依存することです。$k$。 私たちが満たさなければならない方程式は、単純な線形等式ではなく、モジュラー条件です。$$(x + y) \bmod k = z.$$これにより依存関係が生じます。$k$両方の前方差と一致する必要があります$y$そして、それによって暗示されるラップ動作$x$そして$z$。 

エッジケースは、ラップがまったく発生しない場合に発生します。 もし$x + y = z$通常の整数の場合、十分に大きい任意の整数$k > \max(x, z)$は機能し、複数の回答が許可されているため、このケースは常に解決可能です。 ただし、これは次の場合にのみ有効です。$x + y \ge z$。 もし$x + y < z$、モジュラーラップではこれより大きな結果を生成できないため、答えは次のようになります。$-1$。 

もう 1 つの重要なエッジケースは次のような場合です。$y = 0$。 その場合に必要となるのは、$x = z$。 そうでない場合は直ちに不可能です。 「はい」の場合、任意$k > \max(x, z)$動作しますが、やはり任意の有効な値を返すことができます。 

最も重要な隠れた困難は、$k$は、「ラップされていない」フォワード値と観察された結果との差の約数でなければなりませんが、ラップの可能性を考慮した後でのみです。 これが問題を簡単ではないものにしています。 

## アプローチ

 ブルートフォースアプローチでは、考えられるすべての値を試します。$k$から$1$に$2 \cdot 10^9$。 候補者ごとに$k$、プロセスをシミュレートします。$(x + y) \bmod k$そしてそれが等しいかどうかを確認してください$z$。 これは問題の定義からすると正しいですが、遅すぎます。 まで$10^5$テストケース以降$2 \cdot 10^9$ケースごとに候補者が増えると、管理不能になります$10^{14}$操作。 

重要な観察は、私たちが実際に使用する唯一の情報は、$k$それが値とどのように相互作用するかです$x$、$y$、 そして$z$モジュラー演算を通じて。 条件を書き換えると、次のようになります。$$(x + y) \equiv z \pmod{k},$$これは次と同等です。$$x + y - z \equiv 0 \pmod{k}.$$それで$k$の約数でなければなりません$d = x + y - z$と仮定すると$d \ge 0$。 これにより、検索スペースがすべての整数から次の値まで直ちに削減されます。$2 \cdot 10^9$単一の数の約数のみに適用されます。 ただし、モジュール解釈が有効であるという制約、つまり中間値が超過できないという制約は依然として尊重する必要があります。$k-1$間違っています。 

もし$d < 0$の場合、モジュラー演算では値がそれを超えることはないため、方程式は成立しません。$x + y$ラッピング前ですのですぐにご返却させていただきます$-1$。 

取得したら$d \ge 0$、有効な約数を検索します$k$の$d$そのような$k > \max(x, z)$またはラップ構造が一貫したままになるようにします。 どれも有効なので、$k$分けなければなりません$d$の約数を検査するだけで済みます。$d$、最大でも$O(\sqrt{d})$。 

これにより、この問題は、単純な整合性チェックと組み合わされた除数の列挙問題に変わります。

 ## アルゴリズムのチュートリアル

 1. テスト ケースごとに、次の値を計算します。$d = x + y - z$。 この量は、モジュラー ラッピングを適用する前に、単純な前進動作がターゲット状態をどの程度オーバーシュートおよびアンダーシュートするかを測定します。 もし$d < 0$、出力$-1$なぜなら、負のオーバーシュートを有効なラップアラウンド等式に変換できる係数はないからです。 
2. もし$d = 0$、 それから$x + y = z$。 この場合、十分に大きな$k$ラップせずに等価性を維持します。 有効な任意のものを出力できます$k$、 例えば$k = 2 \cdot 10^9$常に制約を満たすためです。 
3. もし$d > 0$、の約数をすべて列挙します$d$。 各約数について$k$、クロック制約を満たしているかどうかを確認します。 約数が重要な理由は次のとおりです$k$生の転送時間と観察されたラップ時間の差を除算する必要があります。そうでない場合、モジュール式の等価性は維持できません。 
4. それぞれの約数候補について$k$からステップアップしているかどうかを確認します。$x$までに進む$y$モジュロの下$k$収量$z$。 この直接チェックにより、複数の約数が存在する場合でも正確さが保証されます。 
5. 最初の有効な値を返します$k$見つかった。 存在しない場合は出力$-1$。 

### なぜ効果があるのか

 重要な不変条件は、有効なクロック サイズが存在することです。$k$違いを強制する$x + y - z$正確に次の倍数になる$k$。 これはモジュールの等価性の直接的な結果です。 逆に、ラップ動作も考慮する除数は、同じモジュラー サイクルを正しく再構築します。 システムを制約する唯一の数値の可能な約数をすべて列挙するため、有効な候補を見逃すことはなく、無効な候補を受け入れることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        x, y, z = map(int, input().split())

        d = x + y - z

        if d < 0:
            print(-1)
            continue

        if d == 0:
            print(2_000_000_000)
            continue

        # enumerate divisors of d
        ans = -1
        i = 1
        while i * i <= d:
            if d % i == 0:
                k1 = i
                k2 = d // i

                # candidate k1
                if k1 >= 1 and k1 <= 2_000_000_000:
                    if (x + y) % k1 == z:
                        ans = k1
                        break

                # candidate k2
                if k2 >= 1 and k2 <= 2_000_000_000:
                    if (x + y) % k2 == z:
                        ans = k2
                        break

            i += 1

        print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、除数検索への還元の直後に続きます。 値$d = x + y - z$モジュラー演算によって引き起こされる唯一の構造的制約を捉えます。 除数列挙ループは次まで実行されます。$\sqrt{d}$有効な係数はすべて除数のペアとして現れる必要があるため、これで十分です。 

微妙な実装の詳細は両方を処理します$i$そして$d/i$対称的に、有効なので$k$は除数ペアのどちらの側にも現れることができます。 早めの休憩は有効なので安全です$k$は受け入れられ、最初に見つかったものがすぐに返されます。 

特別な場合$d = 0$不必要な除数ロジックを回避し、実際にはラッピング制約が適用されないという事実を反映しています。 

## 実用的な例

 ### 例 1

 入力:```
x = 1, y = 9, z = 1
```ここ：$$d = 1 + 9 - 1 = 9$$9 の約数を列挙します: 1、3、9。 

| ステップ | 私 | d%i | k 人の候補者 | チェック (x+y)%k | 有効 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 1 | 0 | 1、9 | 10 % 1 = 0、10 % 9 = 1 | 1 または 9 |

 1 と 9 は両方とも生の算術演算では有効ですが、制約と一致するもののみが受け入れられます。 最初に見つかったので、アルゴリズムはすぐに 1 を返します。 

これは、複数の有効なクロックが存在できることを示しています。 

### 例 2

 入力:```
x = 3, y = 49, z = 4
```計算:$$d = 3 + 49 - 4 = 48$$約数には、1、2、3、4、6、8、12、16、24、48 があります。 

| ステップ | 私 | d%i | k テスト | (x+y)%k | z=4 に一致 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 1 | 0 | 1、48 | 0、0 | いいえ |
 | 2 | 2 | 0 | 2、24 | 0、0 | いいえ |
 | 3 | 3 | 0 | 3、16 | 0、0 | いいえ |
 | 4 | 4 | 0 | 4、12 | 0、10 | k=4 が一致 |

 で$k = 4$、次のようになります。$$(3 + 49) \bmod 4 = 52 \bmod 4 = 0 \neq 4$$したがって、除数であるにもかかわらず、最終チェックに失敗し、有効な一致または枯渇するまで続行されます。 

これは、除数ロジックを超えて最終的なモジュラー検証が必要な理由を示しています。

 ## 特殊なケース

 エッジケースの 1 つは次のような場合です$x + y < z$。 例えば、$x=2, y=1, z=10$。 それから$d = -7$、アルゴリズムはすぐに出力します$-1$。 どのモジュラー システムでも、ラップする前に線形和を超えて値を増やすことはできないため、$k$条件を満たすことができます。 

もう 1 つのエッジケースは次のような場合です$x = z$そして$y = 0$。 例えば、$x=5, y=0, z=5$。 それから$d=0$、アルゴリズムは大きな有効な値を出力します。$k$、 のような$2 \cdot 10^9$。 これが機能するのは、時間が経過しないため、十分に大きなサイクルでは平等が保たれるためです。 

最後の微妙なケースは、複数の約数が存在するが、モジュラー条件を満たすのは一部のみである場合です。 のために$x=3, y=49, z=4$、いくつかの約数が存在することがわかりました。$48$存在しますが、実際に正しいモジュール結果を生成するのはサブセットだけです。 このアルゴリズムは、すべての約数が有効であると仮定するのではなく、各候補を明示的にチェックし、これらの混合ケースにおける正確性を保証します。
