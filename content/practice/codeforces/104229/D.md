 ## 解決策
 ## 問題の理解

 私たちは道路網が木を形成する国を与えられています。 各都市はノードであり、都市のすべてのペアは 1 つの単純なパスによって接続されています。 複数の観光客がおり、それぞれが 1 から m までのインデックスで識別され、各観光客はいつでも常に 1 つの都市に「居住」しています。 

最初に、各観光客は固定された都市から始まります。 時間の経過とともに、3 種類の操作が発生します。 まず、連続するインデックス範囲で指定された一部の観光客が新しい都市に旅行する可能性があります。 旅行により位置が変わり、古い都市と新しい都市の間のツリー上の最短経路の長さだけ幸福度が減少します。 第二に、都市でイベントが発生し、現在そこにいるすべての観光客の幸福度が一定の値だけ増加する可能性があります。 第三に、特定の観光客の現在の幸福度を報告するよう求められる場合があります。 

難しいのは、場所と蓄積された価値の両方が、世界的な都市の出来事と個人の移動履歴の組み合わせに依存することです。 ツリー構造では、距離は座標の差ではなくツリー内の最短経路であるため、移動コストが重要になります。 

この制約は十分に大きいため、どのソリューションでもすべてのツーリストに対するクエリごとの走査やパス長の単純な再計算を繰り返し回避する必要があります。 最大 200,000 人の観光客、クエリ、都市を想定すると、m または q での 2 次関数は直ちに実行不可能になります。 操作ごとの線形アプローチでも生き残ることはできません。 

微妙な問題が旅行クエリに現れます。観光客がすでに目的地の都市にいる場合、移動しないため、距離コストは発生しません。 これは、範囲をやみくもに上書きできないことを意味します。 現在の都市が異なるものにのみ、条件付きで更新を適用する必要があります。 

もう 1 つの重要なエッジ ケースは、イベントと移動の重複によって発生します。 観光客は、いくつかのイベントが適用された後に都市を離れ、その後、その都市がさらに多くのイベントを受信する可能性があります。 観光客はそれらの最新情報を受け取るべきではありません。 これにより、各観光客がその都市に最後に滞在した時期を追跡せずに、グローバルな「都市ごとのイベント総数」のみを保存することが除外されます。 

## アプローチ

 直接シミュレーションのアプローチでは、各クエリを文字通りに処理します。 旅行クエリの場合、影響を受けるすべての観光客を反復処理し、LCA 経由で木の距離を計算し、都市を更新してスコアを維持します。 イベントのクエリの場合は、現在その都市にいるすべての観光客を更新します。 クエリの場合は、1 人の観光客の価値を再計算します。 

これは正しいですが、大規模化するとすぐに失敗します。 最悪の場合、1 つの旅行クエリが O(m) 人の観光客に影響を及ぼし、そのようなクエリが O(q) 件あり、制限をはるかに超える O(mq) になります。 

この構造は、問題を 2 つの独立したコンポーネントに分割することを示唆しています。 コンポーネントの 1 つは、効率的な範囲の更新により、観光客指数ごとに現在の都市メンバーシップを維持することです。 もう 1 つは、過去の貢献が正しくカウントされるように、観光客ごとのスナップショット追跡を使用して都市ごとのグローバル イベントの蓄積を維持することです。 

移動コストについては、各観光客が木の端に沿った距離を独自に累積します。 これは時間の経過とともに加算されるため、必要なのは 2 つの都市間の距離を計算し、それを個人カウンターに追加する高速な方法だけです。 

重要な洞察は、観光客を ID によってインデックス付けされた独立したレコードとして扱うことができる一方、都市ベースの効果は観光客ごとの「最後に見た都市の価値」スナップショットを使用してグローバルに保存できることです。 これにより、イベント処理が履歴の再生ではなく差分追跡に変換されます。 

範囲旅行を効率的にするために、観光客指数に対してセグメント ツリーを使用します。 各セグメント ツリー ノードには、そのセグメント内のすべての観光客が現在同じ都市に属しているかどうかが格納されます。 ノードが均一で、すでにターゲット都市と一致している場合は、そのノードをスキップします。 それ以外の場合は、葉まで下りて、必要な場合にのみ更新を適用します。 これにより、各観光客の都市がすべての操作にわたって対数回のみ変更されることが保証されます。

ツリー上の距離クエリは、LCA 前処理を使用して処理されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(m・q) | O(m) | 遅すぎる |
 | セグメントツリー + LCA + 遅延都市追跡 | O((m + q) log m + q log n) | O(m + n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### 前処理

 まず、ツリーを任意にルート化し、LCA クエリのバイナリ リフティング テーブルを前処理します。 これにより、任意の 2 つの都市間の距離を n 単位の対数時間で計算できます。 

また、m 人の観光客に対してセグメント ツリーを構築します。 各リーフは旅行者に対応し、現在の都市を保存します。 各内部ノードは、セグメントが均一であれば単一の都市値を格納し、それ以外の場合は混合としてマークされます。 

観光客ごとに、現在の都市、累計旅行コスト、最後に確認された都市イベントの合計のスナップショットという 3 つの追加配列を維持します。 

### 処理操作

 1. 値 d を持つ都市 c の都市イベントの場合、グローバル配列をインクリメントします。`city_sum[c]`d.による これは、時間の経過とともにその都市で蓄積されたイベント価値の合計を表します。 
2. 観光客を都市 c に移動させる範囲 [l, r] にわたる旅行クエリの場合、セグメント ツリーをトラバースします。 ノードが完全に範囲内にあり、すでに都市 c と均一である場合は、何も行いません。 それ以外の場合、ノードがリーフであるか部分的に混合されている場合は、下降します。 

各リーフで 1 人の観光客を処理します。 現在の都市がすでに c である場合は、それらをスキップします。 それ以外の場合は、LCA を使用して旧市から c までの距離を計算し、それを旅行コストに追加し、都市を更新し、都市のスナップショットを現在の city_sum[c] にリセットします。 
3. 観光客 i に関するクエリの場合、彼らの幸福度を現在の都市への貢献と旅行ペナルティとして計算します。 市の寄付金は、`city_sum[city[i]] - snapshot[i]`。 最終的な答えは、累計旅費を差し引きます。 

### なぜ効果があるのか

 重要な不変条件は、すべての観光客にとって、都市のイベントからの貢献は常に、彼らが現在の都市に入った瞬間と比較して測定されるということです。 セグメント ツリーにより、都市の割り当てが常に最新の動きと一致していることが保証されます。 過去のスナップショットを遡って変更することは決してないので、各観光客はその都市に実際に存在していた期間からのイベント増分のみを受け取ります。 旅行コストは個別に累積され、実際の移動にのみ依存するため、旅行者が実行したすべての移動の最短経路距離の合計が常に正確になります。 関心の分離により正確性が保証されます。都市のイベントはグローバルですが、スナップショットを通じて観光客ごとに時間枠が設定され、旅行はローカルであり、遷移ごとに加算されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
sys.setrecursionlimit(10**7)

# LCA preprocessing
def build_lca(n, g):
    LOG = 20
    parent = [[-1] * (n + 1) for _ in range(LOG)]
    depth = [0] * (n + 1)

    stack = [(1, -1)]
    order = []
    while stack:
        v, p = stack.pop()
        parent[0][v] = p
        for to in g[v]:
            if to == p:
                continue
            depth[to] = depth[v] + 1
            stack.append((to, v))

    # iterative DFS already set parent[0], fix root
    parent[0][1] = -1

    for k in range(1, LOG):
        for v in range(1, n + 1):
            if parent[k - 1][v] != -1:
                parent[k][v] = parent[k - 1][parent[k - 1][v]]

    def lca(a, b):
        if depth[a] < depth[b]:
            a, b = b, a
        diff = depth[a] - depth[b]
        for k in range(LOG):
            if diff & (1 << k):
                a = parent[k][a]
        if a == b:
            return a
        for k in reversed(range(LOG)):
            if parent[k][a] != parent[k][b]:
                a = parent[k][a]
                b = parent[k][b]
        return parent[0][a]

    def dist(a, b):
        c = lca(a, b)
        return depth[a] + depth[b] - 2 * depth[c]

    return parent, depth, lca, dist

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.city = [0] * (4 * self.n)
        self.is_uniform = [True] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def build(self, idx, l, r, arr):
        if l == r:
            self.city[idx] = arr[l]
            return
        mid = (l + r) // 2
        self.build(idx * 2, l, mid, arr)
        self.build(idx * 2 + 1, mid + 1, r, arr)
        self.pull(idx)

    def pull(self, idx):
        lc, rc = idx * 2, idx * 2 + 1
        if self.is_uniform[lc] and self.is_uniform[rc] and self.city[lc] == self.city[rc]:
            self.is_uniform[idx] = True
            self.city[idx] = self.city[lc]
        else:
            self.is_uniform[idx] = False

    def update(self, idx, l, r, ql, qr, target):
        if r < ql or l > qr:
            return
        if self.is_uniform[idx] and self.city[idx] == target:
            return
        if l == r:
            i = l
            if self.city[idx] != target:
                old = self.city[idx]
                self.city[idx] = target
                process_move(i, old, target)
            return

        mid = (l + r) // 2
        self.update(idx * 2, l, mid, ql, qr, target)
        self.update(idx * 2 + 1, mid + 1, r, ql, qr, target)
        self.pull(idx)

# globals
n, m, q = map(int, input().split())
a = list(map(int, input().split()))
g = [[] for _ in range(n + 1)]
for _ in range(n - 1):
    u, v = map(int, input().split())
    g[u].append(v)
    g[v].append(u)

parent, depth, lca, dist = build_lca(n, g)

city_sum = [0] * (n + 1)
tour_city = a[:]
snapshot = [0] * m
travel_cost = [0] * m

def process_move(i, old, new):
    travel_cost[i] += dist(old, new)
    tour_city[i] = new
    snapshot[i] = city_sum[new]

seg = SegTree(tour_city)

out = []

for _ in range(q):
    tmp = input().split()
    if tmp[0] == 'e':
        c = int(tmp[1])
        d = int(tmp[2])
        city_sum[c] += d

    elif tmp[0] == 't':
        f = int(tmp[1]) - 1
        g_ = int(tmp[2]) - 1
        c = int(tmp[3])
        seg.update(1, 0, m - 1, f, g_, c)

    else:
        i = int(tmp[1]) - 1
        ans = city_sum[tour_city[i]] - snapshot[i] - travel_cost[i]
        out.append(str(ans))

sys.stdout.write("\n".join(out))
```セグメント ツリーは、インデックス空間内で観光客がどこに位置するかを管理することのみを担当します。 実際のセマンティック更新は次の場所で行われます。`process_move`これにより、構造の更新と状態の更新が明確に分離されます。 

微妙な点は、移動中のスナップショットの更新です。 到着時点でのターゲット都市の現在の累積値を使用する必要があります。そうしないと、その後の都市イベントが誤ってカウントされます。 

## 実用的な例

 ### 例 1

 都市 1 が 2 および 3 に接続する小さな木について考えてみましょう。2 人の観光客が都市から出発します [1、3]。 都市 3 で 5 を加算してイベントを実行し、観光客 2 を都市 3 に移動して、観光客 2 をクエリするとします。 

| ステップ | 操作 | 都市合計 | 観光都市 | スナップショット | 旅費 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | e(3,5) | 都市3=5 | [1,3] | [0,0] | [0,0] |
 | 2 | 2 → 3 に移動 | 都市3=5 | [1,3] | [0,5] | 距離(3,3)=0 |
 | 3 | q(2) | 都市3=5 | [1,3] | [0,5] | [0,0] |

 答えは`5 - 5 - 0 = 0`。 

このトレースは、スナップショットが移動前の都市イベントの二重カウントを正しく防止していることを示しています。 

### 例 2

 観光客が 2 つの都市間を複数回移動し、そのたびに距離が増えたとします。 

| ステップ | 操作 | 都市 | 旅費 |
 | --- | --- | --- | --- |
 | 1 | 1 から開始 | 1 | 0 |
 | 2 | 1→2へ移動 | 2 | 1 |
 | 3 | 2→3へ移動 | 3 | 2 |
 | 4 | 3→2を移動 | 2 | 3 |

 これは、移動コストが移行中に純粋に加算され、中間のクエリやイベントに依存しないことを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((m + q) log m + q log n) | セグメント ツリーの更新は各観光客に対数的に影響します。 LCA クエリは O(log n) |
 | スペース | O(m + n) | 観光客用の配列、セグメント ツリー、LCA テーブル |

 これは、各観光客がすべての範囲操作にわたって対数回しか完全に処理できないことと、バイナリ リフティングにより各ツリー距離クエリが高速であるため、制限内に問題なく収まります。

 ## 特殊なケース

 重要なエッジケースは、旅行者が範囲移動中にすでに目的地の都市にいる場合です。 その場合、都市の割り当てとスナップショットの更新の両方を含めて、それらを完全にスキップする必要があります。 ターゲット都市に一致する均一セグメントはそれ以上走査されないため、セグメント ツリーによってこれが保証されます。 

もう 1 つのエッジケースは、観光客が去った後に都市がイベントを受信するときに発生します。 各観光客は入国時に都市の累積価値のスナップショットを保存するため、その後の増分は影響しません。 たとえば、観光客が値 10 の後に都市 5 を去り、その後都市 5 が 20 に増加した場合、その貢献度は出発時に計算された差分で凍結されたままになります。 

最後に、部分的に重複する範囲更新を繰り返す場合は、セグメント ツリー内で慎重に伝播する必要があります。 葉に適切に分割しないと、一部の観光客が誤って古い都市に留まってしまう可能性があります。 再帰的降下により、影響を受けるすべてのリーフが最終的に必要なときに正確に更新され、重複するすべての操作にわたって一貫性が維持されます。
