 ## 解決策
 ## 問題の理解

 配列が与えられ、各クエリは、非常に具体的なルールを使用してその連続セグメントを完全に削除できるかどうかを尋ねます。 このルールは、最初はセグメント内のすべての個別の数値を含む「利用可能な値」のセットで機能します。 1 回の操作で、このセット内にまだ存在する値を選択し、その値の連続したブロック全体を配列から削除し、セットからも値を削除して、その値が二度と使用できないようにします。 

したがって、このプロセスは「値を選択し、その最大の連続ブロックの 1 つを削除し、その値を永久に破棄する」という一連の手順であり、すべてを削除できれば成功します。 

この難しさは、ブロックを削除すると隣接するブロックがマージされ、後で存在するブロックが変わるという事実に起因します。 したがって、削除の順序が重要であり、さまざまな選択により、将来の移動のロックが解除されたり、ブロックされたりする可能性があります。 

クエリは、これらの制約の下で、指定されたサブ配列を完全に空にできるかどうかを尋ねます。 

制約が非常に厳しいため、クエリごとのシミュレーションは不可能です。 合計最大 200,000 個の要素とクエリがあるため、繰り返しスキャンまたは削除をシミュレートしようとするアプローチは、$O(n)$クエリごとに失敗します。 平$O(n \log n)$最悪の場合、クエリごとのサイズが大きすぎます。 これは、全体の複雑さが線形に近い前処理ベースのソリューションであることを強く示唆しています。 

任意の順序で値を貪欲に削除すると機能すると仮定すると、微妙な障害モードが発生します。 たとえば、次のような交互パターンでは、$1,2,1,2$、間違った最初のブロックを選択すると、セグメントが完全に分割され、完了できなくなる可能性があります。 このプロセスは順序に依存しません。 

## アプローチ

 ブルートフォースのアイデアは単純で、プロセスをシミュレートします。 特定のサブ配列について、現在の配列とアクティブな値のセットを維持し、ブロックを削除できる値を繰り返し選択し、その連続するランの 1 つを削除し、配列が空になるか有効な移動が存在しなくなるまで続行します。 考えられるすべての選択肢を試したとしても、削除ごとにアレイのスキャンにコストがかかり、最大で$O(n)$クエリごとの削除数。 これにより、少なくとも$O(n^2)$クエリごとに実行されますが、これは完全に不可能です。 

重要な点は、この操作では連続したブロック全体が削除されるだけであり、値が一度使用されると永久に消えるということです。 これにより、すべての値が最終構造内の 1 つの「間隔寄与」に責任を負うことになります。 このプロセスは、同じ値のブロックの両端から内側に向​​かって配列を徐々に折りたたむものとして再解釈できます。 重要なのは、正確な順序ではなく、インターリーブ制約に囚われずに各値を「削除可能」にできるかどうかです。 

問題を再構成する有効な方法は、セグメントの境界の相互作用に注目することです。 値が複数回出現すると、配列が交互の領域に分割され、配列を削除できるかどうかは、それらの領域が連続した削除を妨げない方法でクリアできるかどうかによって異なります。 

これは古典的な変換につながります。つまり、各値の出現を間隔として扱い、ネストの理由を説明します。 このプロセスは、間隔の包含と一致する有効な削除順序を見つけることができたときに正確に成功します。これは、最初/最後の出現によって形成された構造が矛盾なく処理できるかどうかをチェックすることに帰着します。 これは、クエリされたセグメント内で、すべての値の出現によって、あるステップで有効な連続削除の選択を妨げる不可避の「ロックされたインターリーブ」パターンが作成されないようにすることと同じです。 

これは、範囲制約のある最初/最後の出現に対するスタックのようなスキャンを使用し、これらの間隔制約の実現可能性をチェックするセグメント構造でクエリに応答することを使用して検証できます。

 ## アルゴリズムのチュートリアル

 重要なのは、問題を値の間隔にわたる制約チェック問題に変換することです。 

まず、すべての値について、配列内で最初と最後に出現する値を前処理します。 あらゆるクエリ内で$[l,r]$、完全に含まれるまたは部分的に交差する物質のみを値とし、その構造が不可能なインターリーブを強制しないことを確認する必要があります。 

次に、セグメントが「削除可能」かどうかを把握する構造を構築します。 これは、エンドポイントをスキャンし、間隔の有効なネストをシミュレートするスタックを維持することによって行われます。 

1. 各値について、配列内の最初の出現位置と最後の出現位置を計算します。 これにより、値が「存在する」セグメントが定義されます。 これが重要な理由は、有効な削除では 1 つの連続したブロックを選択する必要があるため、値のすべての出現がこれらのエンドポイントを通じて相互作用するためです。 
2. お問い合わせの場合$[l,r]$、概念的に、この間隔内に出現するすべての値に注目を制限し、その範囲内でクリップされた出現範囲を考慮します。$[l,r]$。 クエリの外に出現するものは部分配列の一部ではないため、無関係です。 
3. 間隔を左から右にスキャンし、間隔が開始されたが終了していないアクティブな値のスタックを維持します。 現在の位置に最初に出現する値が見つかった場合、それをプッシュします。 最後の出現に到達すると、それをポップします。 
4. このプロセス中にスタックの最上位にない値を閉じようとすると、交差構造が検出されます。 これは、連続した削除では解決できない方法で、ある値の間隔が別の値の中に誤って入れ子になっているインターリーブ パターンに対応します。 
5. クエリされたセグメント内の値の交差が発生しない場合にのみ、「YES」と回答します。 

このロジックが機能する理由は、有効な削除が適切にネストされた間隔構造に正確に対応しているためです。 削除するたびに、連続したブロックが削除され、値が永久に削除されます。つまり、間隔は一致する括弧のように動作する必要があります。 交差する間隔により、2 つの値が相互にブロックされる状況が強制され、以前に削除された後、少なくとも 1 つの値が単一の連続ブロックとして削除されなくなります。 

したがって、スタックの不変条件は、現在開いているすべての間隔が有効なネストを形成することです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    first = {}
    last = {}

    for i, x in enumerate(a):
        if x not in first:
            first[x] = i
        last[x] = i

    # build arrays of endpoints
    start = [[] for _ in range(n)]
    end = [[] for _ in range(n)]

    for x in first:
        start[first[x]].append(x)
        end[last[x]].append(x)

    # next occurrence jump structure (not strictly needed in final compressed view,
    # but helps conceptual stack validation)
    res = []

    for _ in range(q):
        l, r = map(int, input().split())
        l -= 1
        r -= 1

        stack = []
        seen = set()
        ok = True

        for i in range(l, r + 1):
            x = a[i]

            if x not in seen:
                seen.add(x)
                stack.append(x)

            if last[x] == i:
                if not stack or stack[-1] != x:
                    ok = False
                    break
                stack.pop()

        print("YES" if ok and not stack else "NO")

if __name__ == "__main__":
    solve()
```この実装では、各クエリ セグメント内のインターバルのネストのスタック解釈を直接シミュレートします。 の`seen`set は、各値がスキャンごとに 1 回だけアクティブになることを保証します。これは、制限されたサブ配列に初めて値の間隔を入力したときのみを考慮するという考えと一致します。 の`stack`正しいネストを強制します。値は、現在最も最近開かれた間隔である場合にのみ終了できます。 違反がある場合は、有効な削除に解決できないインターリーブ パターンを示します。 

最終チェックでは、開いたすべての間隔がスキャンの終了までに適切に閉じられていることを確認します。

 ## 特殊なケース

 重大なエッジ ケースは、クエリ ウィンドウ内の複数の互いに素なセグメントに値が表示される場合です。 のような場合$[1,2,1,2,1]$、単純な貪欲な削除では、最初に 1 つを削除するか、最初に 2 つを削除しようとする可能性がありますが、どちらの選択もトラップされたインターリーブにつながります。 どちらの値の間隔も適切にネストされていないため、スタック プロセスはこれを正しく検出します。 

もう 1 つのエッジ ケースは、値の最初または最後の出現がクエリ範囲外にある場合です。 その場合、部分的に表示された間隔のように動作し、単純な全配列前処理では、それを完全なブロックとして誤って処理してしまいます。 クエリローカル スキャンは、クエリ セグメント内で最初に見つかった値のみをアクティブにすることでこれを回避します。 

3 番目のエッジ ケースは、厳密に増加する個別の値のシーケンスです。 すべての値はシングルトン間隔を形成するため、スタックはネストに違反することはなく、すべてのクエリは YES を返します。これは、他の値と干渉する値がない場合は、どの順序で削除しても機能するという直感と一致します。
