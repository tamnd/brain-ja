 ## 解決策
 ## 問題の理解

 バイナリ文字列が与えられ、位置で終わるすべてのプレフィックスについて計算するように求められます。`i`、非常に厳密なルールの下で、そのプレフィックスが文字列の前のプレフィックスとどの程度一致するか。 固定位置の場合`i`、可能な限りすべての長さを試します`j`から`0`まで`i-1`。 各候補の長さについて`j`、プレフィックスを比較します`s[1..j]`接尾辞付き`s[i-j+1..i]`ただし、平等を求めるのではなく、対応するすべての文字が異なることを要求します。 

有効なものの中で`j`、最大のものを採用します。 その値は次のようになります`q[i]`。 出力は、文字列内のすべての位置に対するこれらの値のシーケンスです。 

これを言い換える便利な方法は、次で終わる各接尾辞についてです。`i`、文字列の先頭をその上に「オーバーレイ」しようとしますが、一致した文字のペアがすべて一致しない場合の重複のみをカウントします。 基本的に、完全なビット単位の補数一致として終了セグメントと位置合わせできる最長のプレフィックスを見つけています。 

制約は大きく、すべてのテスト ケースの合計長は 20 万に達します。 これにより、あらゆる可能性をチェックするアプローチが除外されます。`j`これは、3 次または 2 次の最悪の場合の動作につながるためです。 テスト ケースごとに線形時間に近いソリューションが必要です。 

文字列が長い交互構造または繰り返し構造である場合、微妙なエッジケースが発生します。 このような場合、単純なマッチングでは同じ文字を繰り返し再スキャンする傾向があり、冗長な作業が発生します。 もう 1 つのエッジ ケースは、すべて 0 またはすべて 1 のような単調な文字列です。この場合、すべての比較がすぐに失敗し、些細な初期の成長を除くすべての位置で答えが 0 に崩壊します。 

## アプローチ

 ブルートフォースのアイデアは単純です。 ポジションごとに`i`、私たちはできる限りのことを試みます`j`から`i-1`まで`0`、それぞれについて`j`私たちは比較します`s[1..j]`と`s[i-j+1..i]`。 最初はやめておきます`j`ここで、ペアになっている文字はすべて異なります。 それぞれの比較にかかる費用`O(j)`これがすべて繰り返されるため、`j`まで`i`、単一の位置が次のように劣化する可能性があります。`O(i^2)`。 すべての位置を合計すると、最悪の場合、これは 3 次になります。これは、実行可能な限界をはるかに超えています。`n = 2 × 10^5`。 

重要な点は、「すべての文字が異なる」という条件は、標準的な接頭辞関数スタイルの考え方を使用して、変換された文字列の接頭辞を元の文字列と照合することに等しいということです。 各文字をマッピングすると`0 -> 1`そして`1 -> 0`、次に、`s[1..j]`とは異なります`s[i-j+1..i]`どこでもは、次のことを確認するのと同じです。`complement(s[1..j]) == s[i-j+1..i]`。 

これにより、問題は古典的なプレフィックス マッチング構造に変わります。つまり、すべての位置について、その位置で終わるサフィックスと一致する補文字列の最長のプレフィックスが必要になります。 これはまさに、プレフィックス関数の計算 (KMP スタイルの故障関数) が線形時間で増分を維持するように設計されているものです。 

補文字列を一度構築し、元の文字列をスキャンしながらその上で接頭辞関数のような配列を計算し、以前の長さをすべて再チェックすることなく、有効な最長一致を効率的に維持します。

 ## アルゴリズムのチュートリアル

 この問題を、現在のインデックスで終わるサフィックスと一致する固定パターン (補数文字列) の最長のプレフィックスをすべての位置で維持することに帰着します。 

1. 各文字が反転された文字列の変換バージョンを構築します。`0 -> 1`そして`1 -> 0`。 これは、「すべての位置が異なる」条件下で元の文字列と照合するパターンを表します。 
2. 配列を初期化する`pi`サイズの`n`どこ`pi[i]`位置で終わるサフィックスと一致する、変換された文字列の最長のプレフィックスの長さを表します。`i`。 
3. インデックスから開始して文字列を左から右に反復処理します。`1`。 
4. 変数を維持する`j`、現在の候補一致の長さを追跡します。 
5. ポジションごとに`i`、 その間`j > 0`元の文字列の現在の文字が、変換された接頭辞の対応する文字と一致しない場合、reduce`j`以前に計算されたプレフィックス リンクを使用する`pi[j-1]`。 このステップでは、ゼロからやり直すのではなく、以前の計算を再利用します。 
6. 現在の文字が変換された比較で一致する場合、インクリメントします。`j`1つずつ。 
7.ストア`pi[i] = j`。 
8. 答え`q[i]`アンチプレフィックス関数は正確に`pi[i]`で終わる接尾辞と位置的に完全な不一致を形成する最大の接頭辞を表すためです。`i`。 

重要な考え方は、不一致が発生するたびに最初からやり直す必要はないということです。 代わりに、一致する可能性がある最も長くて小さいプレフィックスにフォールバックし、冗長な比較を回避しながら正確さを維持します。 

### なぜ効果があるのか

 アルゴリズムは次の不変条件を維持します。`j`は常に、現在の位置で終わるサフィックスと一致する、変換された文字列の最長の有効なプレフィックスの長さです。 不一致が発生した場合、これより長い候補の長さは、すでに何らかのインデックスで違反しているため、現在の位置では機能しません。そのため、プレフィックス構造によって指定される次善の候補に安全にフォールバックします。 これにより、すべてのフォールバック遷移にわたってすべての文字が最大一定回数処理されることが保証され、正確さを維持しながら線形の複雑さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input().strip())
        s = input().strip()

        # build complement string
        # 0 -> 1, 1 -> 0
        # but we do not need to store full string explicitly for pi logic
        def comp(c):
            return '1' if c == '0' else '0'

        pi = [0] * n
        j = 0

        for i in range(n):
            while j > 0 and s[i] == comp(s[j]):
                j = pi[j - 1]

            if s[i] != comp(s[j]):
                # cannot extend match
                pass
            else:
                j += 1

            pi[i] = j

        print(*pi)

if __name__ == "__main__":
    solve()
```コア ループは、プレフィックス関数パターンに厳密に従っています。 比較では、直接等価ではなく補数関係が使用されます。これが、標準 KMP からの唯一の概念的な変更です。 

変数`j`で終わる現在の接尾辞と一致する補数接頭辞の量を表します。`i`。 不一致が発生した場合は、以前に計算された値を使用します。`pi`値をゼロにリセットするのではなく、より小さい有効な境界線にジャンプします。 

よくある実装上の落とし穴は、比較が等価ではなく補数の等価であることを忘れていることです。 もう 1 つの微妙な問題は、`pi[j]`の代わりに`pi[j-1]`フォールバックする場合、インデックスが誤ってシフトされ、フォールバック チェーンが切断されます。

    sys.stdin = io.StringIO(inp)

    def solve():
        t = int(input())

            s = input().strip()

            def comp(c):
                return '1' if c == '0' else '0'

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての文字が同一である文字列です。 この場合、文字は補数と一致しないため、すべての比較は直ちに失敗します。 アルゴリズムは維持します`j`全体を通してゼロであり、それぞれ`pi[i]`はゼロのままで、予想される動作と一致します。 

もう 1 つのエッジ ケースは、完全に交互するバイナリ文字列です。 ここで、各位置は前の構造の補数と正確に一致するため、プレフィックスの長さは着実に増加します。 フォールバック メカニズムは決してトリガーされません。これは、構造が理想的である場合には前方拡張ロジックだけで十分であることを裏付けています。 

最後の微妙なケースは、部分一致は存在するが途中で壊れている場合です。 フォールバック チェーンにより、不一致が発生した後でも、再起動するのではなく、最も長い有効な以前の境界が回復され、線形動作と正確性が同時に維持されます。
