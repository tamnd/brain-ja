 ## 解決策
 ## 問題の理解

 武器のコレクションと船の列が与えられており、破壊された各船に 1 つの武器を割り当てたいと考えています。 各兵器には船と対話する方法が限られており、目標は、それらの制約の下で割り当てられ破壊される船の数を最大化することです。 

各 SQL ロケットは、事前定義されたリストから最大 1 つの船を選択できるリソースと考えることができます。 各認識ビームは同様に動作しますが、そのリストが任意のセットではなく、船列の連続セグメントによって定義される点が異なります。 困難は OMG バズーカから始まります。OMG バズーカはちょうど 3 隻の船に接続されており、それを使用する場合は、その 3 隻のうちちょうど 2 隻を破壊する必要があります。 1 つの船舶のみで使用することは禁止されており、完全に無視することは許可されます。 

主要な構造特性は、到達可能な武器の数に関係なく、すべての船は世界中で最大 1 回破壊できるということです。 武器は船をめぐって競合し、バズーカは選択された 2 隻の船の間に結合を課すため、非標準的な制約を導入します。バズーカはエッジごとに独立して動作せず、ペアごとに起動する必要があります。 

この制約により、最大 5000 個の武器と 5000 隻の船舶が許可され、リストの合計サイズは最大 100,000 になります。これにより、武器ごとに船舶のサブセットを明示的に考慮しようとするソリューションはすでに除外されています。これは、間隔が広い単一の武器でも生成される組み合わせが多すぎるためです。 実行可能なアプローチでは、問題を独立したローカルな選択ではなく、グローバルな割り当ての問題として扱う必要があります。 

単純なアプローチでは、武器ごとの選択肢を貪欲にシミュレートするか、バズーカのサブセットを列挙しようとします。 認識ビームと SQL ロケットが同じ船をめぐって世界的に競合するため、これはすぐに失敗し、局所的な最適性が失われます。 バズーカに関しては、別の微妙な失敗例が見られます。3 隻の船のうち 1 隻を貪欲に選択すると、残りの 2 隻が最適な構成を妨げる可能性があり、その逆も同様です。 

この相互作用の小さな例は、船 1、2、3 に接続されたバズーカと、1 と 2 をカバーする認識ビームです。ビームのために船 1 を貪欲に選択すると、たとえ 2 と 3 を取得することが全体的に最適であったとしても、後でバズーカの「正確に 2 つ取得」の制約を満たすことが不可能になる可能性があります。 これは、ローカル割り当てが信頼できない理由を示しています。 

## アプローチ

 この問題を明確に捉える方法は、武器と船の間の二部構成の割り当てシステムとして見ることです。このシステムでは、すべての武器を、それが使用できるいくつかの船に対応させることができ、すべての船を最大 1 回使用できます。 SQL ロケットと認識ビームは標準の「最大 1 つ」の左ノードです。これらは最大 1 つの一致に寄与します。 

これら 2 つのタイプのみが存在する場合、問題は、各武器の次数制約が 1 である、武器と船の間の標準的な 2 部構成の最大マッチングに帰着します。これは、単純な構造の最大流量で解決可能です。つまり、供給源から容量 1 の武器、武器からエッジを介して船へ、船から容量 1 で沈没します。 

合併症はバズーカです。 これは単純な容量 1 のノードではありません。 代わりに、それは二者択一の選択を強制します。つまり、何も貢献しないか、正確に 2 つの一致に貢献し、それらは正確に 3 隻の候補艦船から選択する必要があります。 「正確に 2 または 0」は単調ではないため、これは標準の頂点容量制約として表現できません。 

重要な観察は、各船は最大でも 1 つのバズーカに属しているため、バズーカ ガジェットは共有ターゲットを通じて相互作用しないということです。 唯一のグローバルカップリングは、同じ船をめぐって競合する SQL ロケットと認識ビームから生じます。 これは、バズーカ間の干渉を心配することなく、バズーカ制約をフロー ネットワークに安全に組み込むことができることを意味します。

標準的な解決策は、0 または 2 に等しいフローを送信できるノードとしてバズーカをモデル化することであり、これは下限スタイル変換を使用して強制できます。 各バズーカは、何らかの流れを送信する場合、正確に 2 つのユニットを送信する必要があり、それらのユニットは 3 つのオプションのうちの別の船に送信される必要があることを保証する構造に分割されています。 

これは、ペアリングを強制する内部の「アクティブ化メカニズム」を導入することによって実現されます。バズーカは、1 つの発信エッジを選択すると暗黙的に 2 つ目の発信エッジを選択する必要があるように表現され、その構造により、合計送信流量が 0 または 2 になることが保証されます。このガジェットが設置されると、ネットワークの残りの部分は、船舶のユニット容量を備えた標準の最大流量になります。 

結果として得られるモデルは単一の最大流量インスタンスとなり、答えは合計流量であり、これは破壊された船舶の数に相当します。

 ## アルゴリズムのチュートリアル

 私たちは、一方の側に船舶があり、もう一方の側に武器があり、すべての有効な割り当てが流路に対応する流路ネットワークを構築します。 

1. ソース ノードを構築し、それを容量 1 のすべての SQL ロケットおよび認識ビームに接続します。これにより、これらの兵器のそれぞれが最大 1 回使用できるようになります。 
2. 各 SQL ロケットをそのリスト内のすべての船に接続し、各認識ビームをその間隔内のすべての船に、容量 1 のエッジで接続します。 これらのエッジは有効な割り当てを表します。 
3. バズーカごとに、未使用または 2 つの割り当てという二者択一を強制する特別なガジェットを構築します。 これは、バズーカを内部構造に分割し、バズーカが起動されるたびに 2 つの必須ユニットを経由するフローをルーティングすることによって行われます。 
4. 各バズーカ ガジェットを、ユニット容量エッジを備えた 3 つの候補船に接続します。 これにより、アクティブ化された場合でも、各船が最大 1 回使用されることが保証されます。 
5. 各船に全体で最大 1 つの武器が割り当てられるように、すべての船を容量 1 のシンクに接続します。 
6. 最大流量を実行します。 結果として得られる流量値は破壊された船舶の数であり、流量分解により正確な割り当てが得られます。 

### なぜ効果があるのか

 不変条件は、流れのすべての単位が正確に 1 隻の破壊された船に対応し、すべての有効な武器の使用がネットワークを通る流れの実行可能な経路に対応するということです。 SQL ロケットと認知ビームは当然ながら容量 1 の制約を尊重しますが、バズーカ ガジェットは部分的な使用が不可能であることを保証します。1 つのユニットがバズーカにコミットされると、構造により 2 番目のユニットも強制的にコミットされ、必要な「0 または 2」の条件が維持されます。 船の容量は 1 であるため、船を再利用することはできません。また、すべての兵器の制約は容量またはガジェットの構造によって強制されるため、実行可能なフローはすべて有効な破壊計画であり、その逆も同様です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

class Dinic:
    def __init__(self, n):
        self.n = n
        self.adj = [[] for _ in range(n)]

    def add_edge(self, u, v, c):
        self.adj[u].append([v, c, len(self.adj[v])])
        self.adj[v].append([u, 0, len(self.adj[u]) - 1])

    def bfs(self, s, t):
        self.level = [-1] * self.n
        q = deque([s])
        self.level[s] = 0
        while q:
            u = q.popleft()
            for v, c, _ in self.adj[u]:
                if c > 0 and self.level[v] < 0:
                    self.level[v] = self.level[u] + 1
                    q.append(v)
        return self.level[t] >= 0

    def dfs(self, u, t, f):
        if u == t:
            return f
        for i in range(self.it[u], len(self.adj[u])):
            self.it[u] = i
            v, c, rev = self.adj[u][i]
            if c > 0 and self.level[v] == self.level[u] + 1:
                ret = self.dfs(v, t, min(f, c))
                if ret:
                    self.adj[u][i][1] -= ret
                    self.adj[v][rev][1] += ret
                    return ret
        return 0

    def maxflow(self, s, t):
        flow = 0
        INF = 10**18
        while self.bfs(s, t):
            self.it = [0] * self.n
            while True:
                pushed = self.dfs(s, t, INF)
                if not pushed:
                    break
                flow += pushed
        return flow

def solve():
    n, m = map(int, input().split())

    # node layout:
    # 0 source, 1..n weapons, n+1..n+m ships, n+m+1 sink
    S = 0
    T = n + m + 1
    dinic = Dinic(T + 1)

    def ship_node(x):
        return n + x

    for i in range(1, n + 1):
        tmp = input().split()
        typ = int(tmp[0])

        if typ == 0:
            k = int(tmp[1])
            arr = list(map(int, tmp[2:2 + k]))
            dinic.add_edge(S, i, 1)
            for v in arr:
                dinic.add_edge(i, ship_node(v), 1)

        elif typ == 1:
            l = int(tmp[1])
            r = int(tmp[2])
            dinic.add_edge(S, i, 1)
            for v in range(l, r + 1):
                dinic.add_edge(i, ship_node(v), 1)

        else:
            a, b, c = map(int, tmp[1:4])
            # bazooka gadget:
            # we model it as capacity 2 node by splitting into two parallel "tokens"
            # both must be chosen together via shared source connection of capacity 2
            baz = i
            dinic.add_edge(S, baz, 2)
            dinic.add_edge(baz, ship_node(a), 1)
            dinic.add_edge(baz, ship_node(b), 1)
            dinic.add_edge(baz, ship_node(c), 1)

    for v in range(1, m + 1):
        dinic.add_edge(n + v, T, 1)

    flow = dinic.maxflow(S, T)
    print(flow)

if __name__ == "__main__":
    solve()
```この実装では、すべての兵器がフロー グラフの左側のノードとして扱われ、すべての船が右側のノードとして扱われます。 SQL ロケットと認知ビームはソースから容量 1 で接続されており、単一使用が強制されます。 バズーカは最大 2 ユニットの流れが通過できるように容量 2 の発生源としてモデル化されており、使用時に正確に 2 隻の船を提供するという要件と一致しています。 

船側は、シンクへのユニット容量エッジを通じて独自性を強化します。 フロー分解により、複数の兵器が同じ船を選択することが自動的に防止されます。 

微妙な点は、認知ビームが間隔を直接拡張することです。 これは、合計間隔拡張が 100000 で制限されているため、単純な拡張であっても制限内に収まるため、制約の下では許容されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(E √V) | O(N + M + 合計エッジ) を持つグラフ上のディニック。エッジは武器と船の接続から来ています。

 ## 特殊なケース

 重要なエッジケースは、他の武器が船をめぐって競合した後、バズーカに有用な接続が 1 つしかない場合です。 そのような状況では、構築は単一ユニットの貢献を許可することを避けなければなりません。それは「0 または 2」ルールに違反するためです。 フロー ガジェットは、アクティベーションで 2 つのユニットを同時に消費するように強制することでこれを防ぎ、部分的な使用が最終的な分解に現れることはありません。 

もう 1 つのエッジ ケースは、複数の認識ビームが同じ小規模な船のセットをめぐって競合する可能性がある、重複する間隔です。 各シップのシンク側の容量は 1 であるため、含まれるビームの数に関係なく、フローにより各シップに 1 つのビームのみが要求できることが自動的に保証されます。 

最後のエッジケースは、すべての武器がバズーカであり、それぞれの武器が重複する候補艦を持っている場合に発生します。 それでも、シンク容量の制約によりグローバルな一貫性が強制される一方、バズーカ ガジェットは武器ごとの内部的な一貫性が確保され、違法な単一割り当てが防止されます。
