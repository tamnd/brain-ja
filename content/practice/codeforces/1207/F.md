 ## 解決策
 ## 問題の理解

 1 ～ 500000 のインデックスが付けられた、最初はすべて 0 の非常に大きな配列を維持しており、2 つの操作をサポートしています。 最初の操作では、単一の位置に値を追加します。 2 番目の操作では、構造化された合計を求めます。係数を修正します。$x$そして残り$y$、次に、インデックスが等差数列内にあるすべての配列値を合計します。$y, y+x, y+2x, \dots$許容範囲内です。 

したがって、タイプ 2 の各クエリは、1 つの剰余クラスのモジュロに格納されている合計重みを要求します。$x$ただし、最大 500000 までのインデックスのみです。課題は、更新とクエリの両方がオンラインで完全に混在しており、クエリのモジュラスが固定されておらず、最大 500000 までの任意の数値になる可能性があることです。 

制約は最大 500,000 クエリという極端なもので、原則として各クエリは配列の大部分に影響を与える可能性があります。 クエリごとの単純なスキャンはすぐに約$5 \cdot 10^{5} \times 5 \cdot 10^{5}$、これは実現可能な限界をはるかに超えています。 要素ごとの対数係数であっても、配列全体に繰り返し適用すると遅すぎます。 

隠された構造は、小さな係数と大きな係数が大きく異なる動作をするということです。 大きい$x$小さい等差数列を生成しますが、$x$長いものを生み出します。 解決策は、これら 2 つの体制を別々に扱うかどうかにかかっています。 

単純な推論を打ち破る微妙な問題は、すべての係数の合計を個別に事前計算できると仮定していることです。 更新後は、そのような事前計算はすべて無効になり、再計算にはコストがかかりすぎます。 

もう 1 つの落とし穴は、タイプ 1 の更新がすべての残基クラスに同時に影響することを忘れていることです。 単一のインデックスは無限に多くのモジュラー進行に関与するため、簿記戦略では、すべてのモジュラスに明示的に触れることなく、更新が正しく伝播することを保証する必要があります。 

## アプローチ

 ブルート フォース ソリューションでは、各クエリが個別に処理されます。 タイプ 1 の更新の場合、単純に配列をインクリメントします。 パラメータを含むタイプ 2 クエリの場合$x, y$、すべてのインデックスを反復処理します$i = y, y+x, y+2x, \dots \le 500000$そして値を合計します。 

これはクエリの定義に直接従うため、正解です。 問題はパフォーマンスです。 いつ$x = 1$、ループは 500000 要素に触れます。 このようなクエリが多数出現すると、最悪の場合、総作業量は 2 次関数になります。 500,000 クエリでは、これは完全に不可能です。 

重要な観察は、高速なメソッドが必要なのは次の場合のみであるということです。$x$小さいです。 もし$x$が大きく、等差数列は短いため、ブルート フォースは実際には高速です。 もし$x$規模は小さく、進行は長いですが、そのような少数の$x$値は制限されており、これは剰余に対する事前計算を示唆しています。 

しきい値を導入します$B \approx \sqrt{500000}$。 全員にとって$x \le B$、補助構造物を保守します。 そういったそれぞれに対して$x$、配列を維持します`sum[x][r]`～に一致するインデックスのすべての値の合計を表す$r \mod x$。 位置で更新を実行するとき$i$、すべて更新します`sum[x][i % x]`のために$x \le B$。 これには費用がかかります$O(B)$アップデートごとに。 

クエリの場合$x \le B$の場合、事前計算されたバケットを使用して O(1) で答えます。 クエリの場合$x > B$、進行を直接反復します。$N / B$。 

これによりワークロードが分割されるため、全体としてコストが高すぎる操作はなくなります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(N)$クエリごと |$O(N)$| 遅すぎる |
 | 閾値分解 |$O(\sqrt{N})$操作ごとに償却 |$O(N \sqrt{N})$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. しきい値を選択します$B = \lceil \sqrt{500000} \rceil$。 これにより、「多数の剰余クラス」が「数ステップ進行」から分離されます。 
2. メインアレイを保守する`a[i]`現在の値を保存します。 これは、大規模なステップのクエリで高速に直接アクセスするために必要です。 
3. あらゆる人にとって$x \le B$、辞書のような構造を維持します。`bucket[x][r]`インデックスが一致するすべての値の合計を格納する$r \mod x$。 これにより、各モジュール クラスが単一の集約値に圧縮されます。 
4. アップデート処理時`1 x y`、最初に更新します`a[x] += y`。 それから、それぞれについて$d \le B$、更新します`bucket[d][x % d] += y`。 これにより、事前に計算されたすべてのモジュラー和が正確なままになります。 アップデートごとのコストは、$O(B)$。 
5. クエリを処理するとき`2 x y`：

- もし$x \le B$、直接返します`bucket[x][y]`これは、関連するすべてのインデックスの合計がすでに含まれているためです。 
- それ以外の場合は、次から始まるインデックスを反復処理します。$y$、ステップバイ$x$、蓄積します`a[i]`。 

分割が機能する理由は、すべてのクエリが定数時間で処理されるか、または次の条件で区切られた短いループで処理されるためです。$N/B$。 

### なぜ効果があるのか

 正確さは、あらゆる小さな係数に対して次の不変条件に依存します。$x \le B$、`bucket[x][r]`インデックスが一致する配列内の現在すべての要素の合計と常に等しくなります。$r \mod x$。 各更新では、デルタ値がそのようなすべての適切な残差クラスに正確に追加されます。$x$、したがって、不変式は段階的に保存されます。 大きなモジュライの場合、クエリの長​​さが十分に小さいため、要素を欠落させることなく直接計算できるため、事前計算は行いません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

N = 500000
import math

B = int(math.sqrt(N)) + 1

a = [0] * (N + 1)

bucket = [None] * (B + 1)
for i in range(B + 1):
    bucket[i] = {}

out = []

q = int(input())
for _ in range(q):
    t, x, y = map(int, input().split())

    if t == 1:
        i = x
        val = y
        a[i] += val

        for d in range(1, B + 1):
            r = i % d
            if r in bucket[d]:
                bucket[d][r] += val
            else:
                bucket[d][r] = val

    else:
        mod = x
        r = y

        if mod <= B:
            out.append(str(bucket[mod].get(r, 0)))
        else:
            s = 0
            start = r
            while start <= N:
                s += a[start]
                start += mod
            out.append(str(s))

print("\n".join(out))
```この実装では、直接インデックスを作成するための完全な配列が維持されます。これは、大規模なステップのクエリを効率的に処理するために不可欠です。 の`bucket`構造体は、小さな係数の剰余和のみを格納する係数ごとのハッシュ マップであり、500000 までのすべての値の完全な配列を格納するコストを回避します。 

全体にわたる更新ループ`d ≤ B`が中心的なトレードオフです。 許容できる理由は、$B$は約 700 であり、500,000 回の更新でも合計操作量が制限内に収まります。 

大きなモジュライのクエリ分岐は等差数列の直接走査に依存します。これは、訪問される要素の数が次の範囲に制限されているため安全です。$N/x$、 そして$x > B$。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(\sqrt{N})$アップデートごとに、$O(1)$または$O(N/x)$クエリごと | 更新はすべての小さなモジュライに影響し、大きなクエリはいくつかのインデックスを横断します。 
| スペース |$O(N + B^2)$| 小さな係数の配列と剰余バケット |

 分割により、すべての高価な操作が多くの安価な操作で補われるため、すべてのクエリにわたって総作業量が管理可能な状態に保たれます。 と$B \approx \sqrt{N}$、更新コストとクエリコストの両方のバランスが取れています。$O(\sqrt{N})$償却され、500,000 回の操作の制限内に問題なく収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import math
    N = 500000
    B = int(math.sqrt(N)) + 1

    a = [0] * (N + 1)
    bucket = [dict() for _ in range(B + 1)]
    out = []

    q = int(input())
    for _ in range(q):
        t, x, y = map(int, input().split())

        if t == 1:
            i, val = x, y
            a[i] += val
            for d in range(1, B + 1):
                r = i % d
                bucket[d][r] = bucket[d].get(r, 0) + val

        else:
            mod, r = x, y
            if mod <= B:
                out.append(str(bucket[mod].get(r, 0)))
            else:
                s = 0
                i = r
                while i <= N:
                    s += a[i]
                    i += mod
                out.append(str(s))

    return "\n".join(out)

 ## 特殊なケース

 重要なエッジケースは、更新が小さな係数の多くの剰余クラスに分類されるインデックスに影響を与える場合です。 インデックス 1 での更新を考えてみましょう。すべての小さな係数について$x$、インデックス 1 は剰余に属します$1 \bmod x$したがって、すべてのバケットを更新する必要があります。 アルゴリズムはすべてを反復することでこれを処理します。$x \le B$、すべてのモジュラー分解にわたって一貫性を確保します。 

別のケースとしては、次のようなクエリがあります。$x = 1$。 これは、配列全体を合計することになります。 以来$x$が小さい場合、バケットは剰余 0 に格納されているグローバル合計をすぐに返し、走査は必要ありません。 

最後の微妙なケースが大きい$x$進行には最大でも 1 つの要素が含まれるため、ループは 1 回実行され、すぐに戻ります。 これにより、事前計算なしでも最悪のクエリ コストが安全であることが確認されます。
