 ## 解決策
 ## 問題の理解

 私たちには、ビー玉のコレクションを構築して操作するシステムが与えられています。各ビー玉は、後でより大きなセットにグループ化できる原子単位として考えることができます。 これらのセットは階層的に形成されます。セットは、以前に作成された 2 つのセットの結合として定義でき、葉が個々の大理石で内部ノードが結合を表すバイナリ フォレスト構造を自然に形成します。 

この構築に加えて、各ビー玉を赤か赤ではないかと解釈して、ビー玉のバイナリ割り当てを決定する必要があります。 この制約は、個々のビー玉だけでなく、階層内の集合セットにも適用されます。特定のクエリでは、セットに対応するサブツリー内に表示できる赤いビー玉の数に制限が課されます。 これらの制限は下限と上限の両方にすることができ、これは制約が局所的に適用されるのではなく構造全体に伝播するフローのような解釈を直ちに示唆します。 

2 番目のタイプの操作では、将来の制約と結合に影響を与える方法でビー玉を考慮から削除できるため、この構造が複雑になります。 取り外された大理石は単に無視されるわけではありません。 セットの構造を通じて間接的に制約に関与するため、その効果はグローバル割り当てにおいて一貫して保持される必要があります。 

最終的な目標は、削除を考慮しながら、すべての階層結合制約とすべてのサブツリー カーディナリティ制約を満たす、赤と赤以外のビー玉の一貫した割り当てが存在するかどうかを判断し、存在する場合はそのような割り当てを構築するか、実現可能性を検証することです。 

問題のサイズが十分に大きいため、サブセットごとに制約を明示的に追跡したり、操作ごとに実現可能性を再計算したりするアプローチは遅すぎます。 任意のサブセットに対して制約を再計算しようとする単純な定式化は、各制約がユニオン フォレストの大部分に影響を与える可能性があるため、すぐに 2 次の動作に劣化します。 

主要な構造上の制約は、すべての関係が階層的であり、フロー ネットワークに埋め込むことができるということです。 これは、正しいモデルが組み合わせ検索ではなく、境界を伴う循環実行可能性の問題であることを強く示唆しています。 

エッジケースは、除去が結合構造とどのように相互作用するかによって発生します。 たとえば、大理石が多くの結合に深く埋め込まれた後に削除される場合、単純なアプローチでは大理石が完全に削除され、祖先セット内の数の保存が崩れる可能性があります。 別の失敗モードは、削除されたビー玉に部分的に依存するサブツリーに設定された制約が適用されるときに発生します。単純に削除された要素を無視すると、過小評価されて下限に違反し、誤った実行不可能な結論が生成されます。 

## アプローチ

 ブルートフォースアプローチでは、問題をグローバルな制約を満たすタスクとして扱います。 各ビー玉を赤または赤ではないものとして割り当ててから、すべてのセットのすべての制約を検証してみることができます。 これにより、すでに次のサイズの解空間が得られます。$2^n$、これは中程度の n であっても直ちに実行不可能です。 

もう少し構造化されたブルート フォースでは、すべての操作の後にすべての制約についてサブツリーの合計を再計算しようとします。 m 個の制約があり、各検証がサブツリーを通過する場合、各チェックのコストは O(n) となり、割り当ての試行ごとに O(nm) が与えられます。 実現可能性を一度だけ評価したとしても、すべてのサブツリー メンバーシップを構築すると、明示的に、大きな重複領域を繰り返し走査することになります。 最悪の場合、ユニオン フォレストがチェーンに縮退する場合、各制約はほぼすべてのノードに影響するため、前処理だけで 2 次関数になります。 

重要な観察は、すべての制約が本質的に線形であるということです。つまり、サブツリー内で選択されたビー玉の合計が制限されます。 これは、各ビー玉がバイナリ変数であり、各サブツリー制約が容量制約となるフロー定式化に直ちにマッピングされます。 結合構造は自然な分解を提供します。任意のサブセットの観点から考える代わりに、階層に沿ってフローが保存されるネットワークとして構造を解釈します。 

各ビー玉は、赤 (流れが通過する) または赤でない (流れがブロックされる) として割り当てることができる流れの単位に対応します。 各サブツリー制約は、循環システム内のエッジ制約またはノード制約になります。 下限と上限は当然 LR フロー制約に対応します。 

難しいのは除去を組み込むことです。 削除された大理石は、フロー構造の一貫性を維持する必要があるため、単純に削除することはできません。 代わりに、それを通過するフローが一貫して再ルーティングされるように、リダイレクトする必要があります。 これは、削除されたノードがフロー保存システムの一部として残り、全体のフロー バランスが変わらないようにネットワークを変換することによって実現されます。 

問題が下限と上限のある循環に完全に変換されると、最大流量への標準的な削減を使用して解決できます。各境界エッジを容量制約に変換し、スーパー ソースとシンクを導入し、すべての要求が満たされるかどうかを確認します。

 ## アルゴリズムのチュートリアル

 次に、ユニオン フォレストとすべての制約の両方をエンコードするフロー ネットワークを構築します。

1. 入力操作からバイナリ ユニオン フォレストを構築します。 各ノードは、単一の大理石または結合されたセットのいずれかを表します。 葉は個々のビー玉に対応し、内部ノードは 2 つの子の結合を表します。 これにより、すべてのセットにわたって根付きフォレスト構造が得られます。 
2. 各ビー玉を、最終的な赤カウントに 0 または 1 のいずれかを与えることができる単位変数として解釈します。 これをフロー決定として表します。ビー玉を通して 1 つのユニットを送信することは、それを赤として選択することに相当します。 
3. 各ユニオン ノードについて、セットの値が子の合計と等しいことを確認することで、親と子の間の一貫性を確保します。 これは、内部ノードでのフロー保存を使用してモデル化されます。 
4. サブツリー上のすべての制約について、下限と上限をフロー グラフ内の有界容量エッジに変換します。 「部分木Ｓの赤いビー玉Ｌ個とＲ個の間」という制約が、当該ノードを通過するフローに対するデマンド制約となる。 これにより、有効な循環は、許容される最小および最大のレッド カウントの両方を遵守することが保証されます。 
5. 標準的な循環変換を導入します。各有界エッジを下限調整で置き換え、これらの下限によって引き起こされるノード要求を計算し、スーパー ソースとスーパー シンクを構築します。 これにより、実現可能性が最大流量の問題に変換されます。 
6. 削除されたビー玉をネットワーク内に確実に残し、流れの保存が保たれるように寄与エッジをリダイレクトすることで、それらを処理します。 ノードを削除する代わりに、隣接関係を調整して、削除されたビー玉を通過するフローが、流入と流出の平等を維持する専用の構造を介して一貫して再ルーティングされるようにします。 これにより、削除によって祖先セットの保存制約が破られないことが保証されます。 
7. スーパー ソースからスーパー シンクまで最大流量を実行します。 すべての需要エッジが満たされる場合、実行可能な割り当てが存在します。 それ以外の場合、ビー玉の有効な色はすべての制約を満たしません。 
8. フローから割り当てを回復します。ビー玉は、対応するエッジを通るフローが選択を表す方向に飽和している場合にのみ赤色になります。 

### なぜ効果があるのか

 この構造では、すべての制約が同じ単位変数に対する線形保存則であることが強制されます。 各ビー玉は正確に 1 単位の潜在的な流れに寄与し、すべての結合ノードは加算性を保持します。 下限と上限により実行可能な流量範囲が制限され、循環の削減により、実行可能な流量が有効な割り当てに対応することが保証され、またその逆も同様です。 保守的なネットワークではすべての制約が容量制限としてエンコードされるため、有効なフローはすべてのサブツリー要件を同時に自動的に満たします。

from collections import deque

class Dinic:
    def __init__(self, n):
        self.n = n
        self.adj = [[] for _ in range(n)]

    def add_edge(self, u, v, c):
        self.adj[u].append([v, c, len(self.adj[v])])
        self.adj[v].append([u, 0, len(self.adj[u]) - 1])

    def bfs(self, s, t, level):
        q = deque([s])
        level[:] = [-1] * self.n
        level[s] = 0
        while q:
            u = q.popleft()
            for v, c, r in self.adj[u]:
                if c > 0 and level[v] == -1:
                    level[v] = level[u] + 1
                    q.append(v)
        return level[t] != -1

    def dfs(self, u, t, f, level, it):
        if u == t:
            return f
        for i in range(it[u], len(self.adj[u])):
            it[u] = i
            v, c, r = self.adj[u][i]
            if c > 0 and level[v] == level[u] + 1:
                ret = self.dfs(v, t, min(f, c), level, it)
                if ret:
                    self.adj[u][i][1] -= ret
                    self.adj[v][r][1] += ret
                    return ret
        return 0

    def maxflow(self, s, t):
        flow = 0
        level = [-1] * self.n
        while self.bfs(s, t, level):
            it = [0] * self.n
            while True:
                f = self.dfs(s, t, 10**18, level, it)
                if not f:
                    break
                flow += f
        return flow

## 実用的な例

 2 つのビー玉が 1 つのセットにマージされている 4 つのビー玉を含む小さなシステムを考えてみましょう。マージされたセットには正確に 2 つの赤いビー玉が含まれなければならないという制約があります。 

4 つのユニット ソースが 4 つのリーフ ノードに供給され、次にそれらを集約するユニオン ノードでフロー グラフを構築します。 制約はユニオンノードを通過する2台の要求となります。 フローを実行すると、制約を満たして赤として渡すユニットを 2 つだけ割り当てます。 

| ステップ | アクティブノード | 割り当てられたフロー | 制約ステータス |

次に、削除の場合を考えてみましょう。結合の一部となった後、1 つのビー玉が削除されます。 削除する代わりに、寄与エッジのルートを変更し、それを通過したであろう流れが保存方程式に保存されるようにします。 これにより、祖先制約で正しい総容量が引き続き参照されるようになります。 

| ステップ | 削除されたノード | フロールーティング | 制約の影響 |

 これは、除去しても保存が損なわれないことを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、ビー玉が複数の結合操作で深く埋め込まれた後に削除される場合です。 この状況では、単純な解決策ではノードを削除してサブツリーのサイズを減らし、祖先に対する上限の制約を破ることになります。 正しいフロー モデルでは、ノードがグラフ内に保持され、祖先ノードが引き続き一貫したフロー単位を受け取るように、その寄与が再ルーティングされます。 

サブツリー制約が削除されたビー玉全体に適用される場合、別のエッジ ケースが発生します。 削除されたノードを単純に無視すると、サブツリーの容量がゼロになるため、制約を満たすことが不可能であるように見えます。 フロー定式化では、削除されたノードは依然として保存エッジを通じて寄与するため、元の構造で許可されていれば要求を満たすことができます。 

最後の微妙なケースは、複数のコンストレイントが同じユニオン ノードで重なり合う場合です。 単純な制約ごとの評価では、共有された貢献が二重にカウントされたり、見逃されたりする可能性があります。 循環モデルでは、すべての制約が単一の実現可能性システムとして同時にエンコードされ、制約間の干渉なしに一貫した全体的な満足が保証されます。
