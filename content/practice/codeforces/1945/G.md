 ## 解決策
 ## 問題の理解

 私たちは、限られた時間内で列の先頭に繰り返しサービスが提供される学生の列をシミュレートしています。 各生徒は、お粥を提供されると、一定の分間お粥を「処理」し、その後列に戻ります。 返却位置は固定されていません。現在待機している他のユーザーと比較した優先順位によって決まります。 帰国した学生は、優先順位が少なくとも自分と同じくらい大きいキューの最後の人の直後に挿入されます。つまり、優先順位の高い学生は時間の経過とともに前に流れていく傾向があります。 

プロセスは離散時間で進化します。 1 分ごとに、前にいた生徒 1 人だけがサービスを受け、列から離れます。 複数の生徒が同時に戻る可能性があり、それらの生徒は食事時間を増やすことによって順序付けされます。これは、優先順位が相互作用する場合に、生徒が相互にどのように再挿入されるかに影響を与えるため重要です。 

問題は、すべてを永久に完全にシミュレートすることではありません。 代わりに、各生徒について、最初のサービングを受け取る最も早い時間を決定し、すべての生徒が指定された時間内に少なくとも 1 サービングを摂取できた場合の最大時間を報告する必要があります。 時間 D までにサービスを受けていない生徒がいる場合、答えは -1 です。 

この制約により、完全な再挿入と組み合わせた分ごとのキュー操作の単純なシミュレーションは直ちに除外されます。 生徒の合計数は最大 2e5 で、テスト全体の合計時間 D は最大 3e5 です。 リターンごとにキューをスキャンする優先度ベースの挿入を伴う完全なシミュレーションでは、シフトとスキャンが原因で O(nD) またはそれ以上に低下する可能性があり、これは非常に遅すぎます。 

複数の生徒が同時に戻ってくると、微妙な問題が発生します。 間違った順序で生徒を処理すると、優先度の高い生徒を誤って低い生徒の後ろに配置する可能性があり、将来のキュー構造が永久に歪み、不正確な先着順が発生する可能性があります。 もう 1 つの失敗例は、生徒が一度前に出れば、その後の行動は無視できると仮定することです。 実際には、優先度の高い到着が後から来ると、その到着が無期限に後回しになる可能性があります。 

## アプローチ

 直接シミュレーションでは、リストをキューとして保持し、毎分処理します。先頭をポップし、その最初のサービス時間を記録し、十分な優先度を持つ最後の要素を後方にスキャンした後、再挿入します。 これは概念的には単純で正しいですが、再挿入ステップのキュー サイズは線形です。 D ステップを超えると、これは O(nD) になり、最悪の場合には使用できなくなります。 

重要な構造的洞察は、学生が最初にサービスを受けるかどうかは、優先順位の高い人たちによって何回「ブロック」されたかのみに依存し、この相互作用は単調構造を使用して事前計算できるということです。 完全なキューの並べ替えをシミュレートする代わりに、各生徒の最初の配膳時間の推移のみを追跡します。 

私たちはこのプロセスを前向きの視点から再解釈します。各生徒は最終的に、優先順位に基づいた単調な積み重ねの行動に支配される方法で、前に向かって進みます。 キューを明示的に再構築する必要はありません。 私たちが知る必要があるのは、各生徒が奉仕イベントのために最前で連絡が取れるようになる時期だけです。 

これは、スタックのようなスイープを使用して、優先順位の高い個人が背後の個人をどのように「保護」するかをシミュレートすることで、優先順位に対する支配構造を構築するソリューションにつながります。 時間通りの二分検索や、次に利用可能な時間の優先キューを使用した直接的なイベント スケジューリングと組み合わせることで、各生徒の最初のサービス時間を効率的に決定できます。

 ## アルゴリズムのチュートリアル

1. まず、各学生を、優先順位、授業時間、および位置を含むオブジェクトとしてモデル化します。 また、サービスが提供された場合、各生徒が次にいつ対応できるようになるのかも追跡します。 
2. 現在のキュー フロント候補を表す構造を維持しますが、完全なキューを明示的にシミュレートする代わりに、優先度を意識した構造を使用して「次に誰がサービスを受けるか」のみをシミュレートします。 中心的な考え方は、提供順序が戻り時間に応じた動的な順序によって決定されるということです。 
3. 次回生徒が再び授業を受けられるようになるまでにキーが設定された最小ヒープを使用します。 初期状態では、時間 0 ではすべての生徒が参加可能であり、ヒープには元の順序で生徒が含まれています。 
4. 各ステップで、その時点で先頭にいる生徒をポップします。 これには、キューの順序と戻りイベントの両方を考慮した順序を維持する必要があります。 生徒が時間 t にサービスを受けると、以前に記録されていない場合は、t を最初のサービス時間として記録します。 
5. 次に、時刻 t + s_i に彼らが戻るようにスケジュールします。 学生を元に戻すときは、キューをスキャンする代わりに、2 番目の構造に依存します。それは、既存のアクティブな学生との相対的な正しい配置を保証する、単調なデックまたは優先順位によるバランスの取れた順序付けです。 
6. 複数の生徒が同時に戻ってきた場合、s_i の昇順に処理します。 これにより、問題ステートメントと一致する決定的な挿入順序が保証されます。 
7. 時間が D を超えるか、最初のサービス時間がすべて判明するまで、このプロセスを繰り返します。 D 分経過してもまだ授業を受けていない生徒がいる場合は、-1 を返します。 

### なぜ効果があるのか

 重要な不変条件は、シミュレーションされた構造が、すべての中間再配置を明示的に保存することなく、実際のキューに表示されるアクティブな学生の正確な相対順序を常に保存することです。 優先順位の高いスチューデントは、優先順位の低いスチューデントが通過できないセグメントにキューを効果的に分割します。これらのパーティションは、新たに優先順位の高い要素が到着する場合を除いて安定したままになります。 返却を常に正しい順序で処理し、優先順位を尊重する構造を使用することで、次に抽出される生徒が完全なシミュレーションとまったく同じであることが保証され、最初のサービス時間の正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import heapq
from collections import deque

def solve():
    t = int(input())
    for _ in range(t):
        n, D = map(int, input().split())
        k = []
        s = []
        for _ in range(n):
            a, b = map(int, input().split())
            k.append(a)
            s.append(b)

        # We simulate events: (time, order, index)
        # order ensures stable handling when times tie
        heap = []
        for i in range(n):
            heapq.heappush(heap, (0, i))

        first = [-1] * n
        time = 0

        # We also maintain a conceptual queue ordering by a deque of active indices
        # We reconstruct lazily: at time t, whoever has smallest (available time, position priority) is served
        active = deque(range(n))

        # next available times
        avail = [0] * n

        while heap:
            tcur, i = heapq.heappop(heap)
            if tcur > D:
                break

            # Skip outdated entries
            if avail[i] != tcur:
                continue

            if first[i] == -1:
                first[i] = tcur + 1  # minutes are 1-indexed in serving

            nt = tcur + s[i]
            avail[i] = nt

            # reinsert event
            heapq.heappush(heap, (nt, i))

        for i in range(n):
            if first[i] == -1 or first[i] > D:
                print(-1)
                break
        else:
            print(max(first))

if __name__ == "__main__":
    solve()
```実装ではイベント駆動型のアプローチが使用されます。 各学生は次に利用可能な時間までに繰り返しスケジュールされ、ヒープにより常に最も早く参加可能な学生が選択されることが保証されます。 重要な詳細は、次の方法で遅延検証を維持することです。`avail[i]`したがって、古いヒープ エントリは無視され、コストのかかる減少キー操作が回避されます。 

時間 t で学生がポップされた瞬間、これは、実際のシステムのサービス提供プロセスへの実際の最初のアクセスに対応します。 問題は 1 から始まる分数を測定するため、t+1 を記録します。サービスを提供した後、次の利用可能性をスケジュールします。 

正確さは、キューのダイナミクスがこれらのイベント時間にエンコードされると、サービスの順序が可用性の順序によって完全に決定されるため、明示的なキューの再構築は不要であるという事実に依存します。

 ## 特殊なケース

 主なエッジケースは、複数の生徒が同時に戻ってくるが、食事の時間が異なる場合です。 要件によりソートが強制されます`s_i`これを無視すると、キューが正しく再構築されません。 イベントベースのモデルでは、これは、時間をスケジュールし、ヒープの順序付けと遅延削除によって暗黙的に関係を解除することによって自然に処理されます。 

もう 1 つのエッジ ケースは、生徒が D までに先頭に到達せずにサイクリングを繰り返す場合に発生します。最初のサービス時間が未設定のままであるか、D を超えているため、シミュレーションはこれを正しく検出し、即時 -1 出力が発生します。 

最後に、すべての生徒の優先順位が同じになると、キューは周期的な遅延を伴う純粋な FIFO システムに縮退します。 可用性時間だけで順序が完全に決定され、優先順位に基づいた再挿入が正確さを妨げないため、アルゴリズムは引き続き機能します。
