 ## 解決策
 ## 問題の理解

 私たちは、時間と酸素がさまざまな形で同じ通貨となる、制約された生存プロセスをシミュレートしています。 掘削や機械の操作など、あらゆる場所で 1 秒を費やすごとに、酸素タンクが 1 つ減ります。 酸素を増やす唯一の方法は、金属ユニットを採掘し、抽出装置でバッチ処理することです。 

各金属タイプは繰り返し採掘できます。 1 つのユニットのマイニングには固定の時間がかかり、マイニングされたユニットのバッチの処理にはバッチ サイズに関係なく固定のオーバーヘッド時間がかかります。 バッチが処理されると、採掘された金属がすぐに追加の酸素に変換されます。 

このプロセスは、初期の酸素貯蔵量から始まります。 作業中、時間の経過とともに酸素は減少し続けます。 瞬間が完了する前にゼロに達すると、プロセスは即座に失敗します。 目標は、採掘と処理に費やされる合計経過時間を最小限に抑えながら、酸素埋蔵量が少なくとも目標レベルに達する状態に到達することです。 

重要な問題は、採掘で酸素が遅延して生成されることです。 酸素獲得の恩恵を受ける前に、採掘と処理時間を生き残る必要があるため、何を採掘するかについてのすべての決定は、遅延を生き延びるかどうかの決定でもあります。 

制約は十分小さいため、テスト ケースごとの線形または線形に近い推論で十分です。 テストごとに最大でも数千の操作があるため、長時間にわたる状態ごとの動的プログラミングや酸素範囲を伴うものは、高度に最適化されている場合にのみ許容されますが、無制限のリソースと均一な処理コストの構造は、状態の爆発ではなく貪欲な削減を強く示唆しています。 

処理のオーバーヘッドを考慮せずに、単純なソリューションが「ユニットあたり最も多くの酸素を供給するものを常に採掘」しようとした場合、微妙な失敗例が発生します。 もう 1 つの失敗例は、戦略が処理フェーズ中の生存を無視した場合に発生します。バッチが利益を生む場合でも、酸素を追加する前に、酸素タンクは採掘と処理期間全体を生き延びるのに十分な大きさでなければなりません。 

たとえば、初期の酸素が少なく、最高の金属を処理するまでに長い採掘時間が必要な場合、長期的には十分な利益が得られるにもかかわらず、最初のバッチを完了することさえ不可能になる可能性があります。 

## アプローチ

 直接総当たり戦略では、すべての決定が、抽出装置を実行する前に各金属のユニット数を採掘するかの選択として扱われます。 その後、時間の経過、酸素が秒ごとに減少し、処理が完了した後にのみ酸素が増加することをシミュレートします。 各バッチは、すべての金属にわたって選択されたユニット数の組み合わせです。 

このアプローチはプロセスを正確に反映しているため、正しいです。バッチ組成を選択し、採掘および加工中に酸素が決してゼロ以下にならないことを確認し、酸素増加量を適用し、目標に達するまで繰り返します。 問題は、分岐要素が膨大であることです。 適切なバッチサイズに制限したとしても、すべてのバッチで金属の任意の組み合わせを選択できるため、可能なシーケンスの数は時間の経過とともに指数関数的に増加します。 最悪の場合は、中程度の制限でも不可能になります。 

重要な簡素化は、バッチ処理では固定間接費のみが発生し、すべての金属は時間と酸素の両方に直線的に寄与することに気づくことから来ています。 金属を混合するバッチは、独立した単位アクションの線形結合にすぎず、処理オーバーヘッドが唯一の非線形要素です。 つまり、バッチ内で唯一意味のある決定は、どの混合物がそれらを生成するかではなく、合計マイニングに費やす秒数です。

これが認識されると、問題はリソース変換モデルに集約されます。 採掘される 1 秒ごとに時間がかかり、後で酸素が生成されます。 各バッチには一定のペナルティが時間内に適用されますが、マイニングされた作業は蓄積されます。 処理オーバーヘッドはマイニング単位全体で償却されるため、最良の戦略はマイニング時間単位当たりの酸素獲得量を最大化することです。 

これにより、最適な効率比を持つ金属を選択し、それをバッチで繰り返し使用するという問題が軽減され、各バッチが処理の遅延に耐えられる十分な大きさになることが保証されます。

 ## アルゴリズムのチュートリアル

 1. 各金属について、消費時間と比較して追加される酸素の量として定義される、採掘単位あたりの正味有用性を計算します。 すべてのユニットは一度選択されると同じように動作するため、これは基本的な効率信号です。 
2. 最も効率の高い金属を選択します。 消費する時間よりも早く酸素を改善する金属がない場合、酸素は時間の経過とともに減少するだけであるため、初期の酸素がすでに目標を満たしていない限り、より高い目標に到達することは不可能です。 
3. 現在の酸素を実行状態として維持します。 このプロセスはバッチで繰り返され、各バッチでは選択された最良の金属のみが使用されます。 
4. 特定の現在の酸素レベルに対して、抽出装置を実行する必要がある前に採掘できるユニットの数を決定します。 各ユニットにはマイニング時間と同じ時間がかかり、バッチには固定の処理時間も含まれている必要があります。 これにより、マイニング時間と処理時間の合計がバッチの開始時に利用可能な酸素を超えてはいけないという制約が課されます。 
5. この制約の下で安全にマイニングできるユニットの最大数を選択します。 これにより、すべてのユニットの効率が同一であり、処理オーバーヘッドが固定されるため、バッチごとの酸素獲得量が最大化されます。 
6. バッチ遷移を適用します。酸素から費やした合計時間を減算し、加工された金属から得られた酸素を加算します。 
7. 酸素が目標に達するか超える場合、または実行可能な状態で酸素を増加できるバッチがない場合に停止します。 

重要な不変条件は、各バッチの開始時の酸素値が、故障するまでに継続的に費やすことができる時間を正確に表すということです。 各バッチは、バッチ内で費やされる合計時間が開始時に利用可能な酸素を決して超えないようにすることで、実現可能性を維持します。 酸素は個別のバッチ完了時にのみ増加するため、有効なスケジュールはこの分割を尊重する必要があります。 効率の低い金属やより小さなバッチを使用する逸脱は、オーバーヘッドを削減せずに、単位時間あたりの酸素獲得量を削減します。これは、実現可能性を向上させることなく目標への到達を遅らせるだけであるため、貪欲な選択は安全です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        c, e, p, n = map(int, input().split())

        best_g, best_d = 0, 1

        metals = []
        for _ in range(n):
            d, g = map(int, input().split())
            metals.append((d, g))

        # pick best efficiency metal: compare g/d
        for d, g in metals:
            if g * best_d > best_g * d:
                best_g, best_d = g, d

        # if no improvement possible, only decay in time
        if best_g <= best_d:
            if c >= e:
                out.append("0")
            else:
                out.append("TRAPPED")
            continue

        O = c
        time_spent = 0

        # simulate batch processing
        while O < e:
            # max units we can safely mine before processing
            if O <= p:
                break

            # must satisfy O >= x*d + p
            x = (O - p) // best_d
            if x <= 0:
                break

            # batch cost and gain
            batch_time = x * best_d + p
            gain = x * best_g

            O = O - batch_time + gain
            time_spent += batch_time

            if batch_time == 0:
                break

        if O >= e:
            out.append(str(time_spent))
        else:
            out.append("TRAPPED")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、まず、単位採掘時間あたりの酸素獲得量を比較することにより、最も効率的な金属を特定します。 比較では、浮動小数点の精度の問題を回避するために相互乗算を使用します。 この選択により、今後のすべての決定が単一の反復アクションに減ります。 

シミュレーション ループは、繰り返される抽出サイクルを表します。 各サイクルについて、アルゴリズムは、現在の酸素レベルから固定処理コストを引いたものによって制約され、処理前に安全に採掘できるユニットの数を計算します。 これにより、採掘中または加工中に酸素タンクがゼロになることがなくなります。 

各反復では、酸素と経過時間の両方が更新されます。 終了条件には、正常に完了した場合と不可能な場合の両方が含まれます。つまり、目標に達したか、有効なバッチを作成できなかったかのいずれかです。 

実装の微妙な詳細は、バッチに酸素制約内に処理時間を含める必要があるという厳密な要件です。 これを無視すると、実現可能なバッチ サイズが過大評価され、無効な生存パスが得られます。

### 例 2

 入力:```
c = 10, e = 25, p = 1
metals:
(2, 4), (10, 25)
```2 番目の金属は単位時間あたりの効率が高いため、優先されます。 

| ステップ | 前の酸素 | 採掘されたユニット | バッチ時間 | |後の酸素 合計時間 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 10 | 0 (早期に大量の最高の金属を保管するのに十分な安全なスペースがありません) | - | - | - |

 ここで重要な観察は、長期的な効率が高いにもかかわらず、処理オーバーヘッドに対して酸素が不足しすぎるとバッチを安全に開始できないということです。 これはまさに、実現可能性をチェックしないと単純な「常に最良の比率」ロジックが失敗する可能性がある場所です。 

このシステムは、完全に安全なバッチが可能な場合にのみ進行し、生存の制約がなければ効率だけでは不十分であることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 | 時間 | テスト ケースあたり O(n) | 各テストでは金属を 1 回スキャンし、少数のバッチ シミュレーションを実行します。

 ## 特殊なケース

 初期酸素がバッチを開始するのにかろうじて十分であるが、処理時間を含めるには十分ではない場合、重大なエッジケースが発生します。 この状況では、マイニングのみが実行可能であっても、処理を通じて生存期間も延長する必要があるため、アルゴリズムはバッチを正しく拒否します。 条件`O > p`マイニングが開始される前に、少なくとも処理が存続できることを保証します。 

もう 1 つのエッジ ケースは、すべての金属の純利益が正ではない場合です。 そのシナリオでは、すべてのバッチで時間の経過とともに酸素が厳密に減少します。 アルゴリズムは、最初に目標がすでに満たされていない限り、より高い目標に到達することは不可能であると即座に結論付けます。これは、一連の減少変換がより高いしきい値を超えることができないためです。 

最後の微妙なケースは、バッチで酸素が生成されるものの、初期段階でそれ自体のコストを補うのに十分ではない場合に発生します。 酸素は完全なバッチの完了後にのみ更新され、特別なケースを必要とせずに消費と補充の正しい順序が維持されるため、シミュレーションはこれを自然に処理します。
