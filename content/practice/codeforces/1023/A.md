 ## 問題の理解

 パターン文字列が与えられています`s`そしてターゲット文字列`t`。 パターンは、単一の特殊文字が含まれる場合があることを除けば、通常の小文字の文字列とほぼ同じように見えます。`*`。 このワイルドカードは柔軟です。パターンを「インスタンス化」するときに、パターンを置き換えることができます。`*`空の文字列を含む任意の小文字の文字列。 それ以外はすべて`s`変更されないままでなければなりません。 

課題は、何か代替品を選択できるかどうかを決定することです。`*`結果の文字列が正確に等しくなるようにします。`t`。 

制約の観点から見ると、どちらの文字列も最大 200,000 文字と非常に大きくなる可能性があります。 これにより、多くの置換を明示的にテストしようとするアプローチは即座に除外されます。`*`または、可能なすべての拡張を構築します。 どのソリューションでも、文字列を線形時間で検査し、文字ごとに一定の作業のみを実行する必要があります。 

微妙なエッジケースは、次のような事実から生じます。`*`完全に消える可能性があります。 誰かが少なくとも 1 つのキャラクターを貢献しなければならないと仮定すると、次のようなケースでは失敗します。`s = "ab*cd"`そして`t = "abcd"`。 

もう 1 つのよくある落とし穴は、次のことを忘れることです。`*`1 文字だけでなく、非常に長い文字列を表すこともできます。 たとえば、次の場合`s = "a*b"`そして`t = "axxxxb"`、中央のセグメントは任意の大きさにできます。 

最後に、最も危険なケースは次のような場合です。`s`はありません`*`全然。 その場合、答えは純粋に等価性チェックです。 常に分裂させようとする単純なアプローチ`*`存在を確認しないと、文字列全体が誤ってプレフィックスまたはサフィックス ロジックとして扱われます。 

## アプローチ

 強引な解釈では、ワイルドカードの可能なすべての置換を試みることになります。 もし`*`位置の間に表示されます`L`そして`R`で`s`、私たちは調整しようとします`s`の接頭辞と接尾辞`t`そして真ん中を任意に埋めます。 ただし、置換できる文字列の数は`*`ギャップの長さは指数関数的です。 長さだけを考慮する場合でも、次のすべての値を試す必要があります。`0`まで`m`、そして長さごとに文字列を再構築するか、アライメントを検証します。 これにより、最悪の場合、少なくとも二次的な動作が発生します。 

重要な点は、ワイルドカードが唯一の柔軟な部分であるということです。 左側にあるものすべて`*`のプレフィックスと一致する必要があります`t`、右側のすべては接尾辞と一致する必要があります。`t`。 これらの固定パーツの位置を調整したら、残る唯一の問題は、`t`ワイルドカード拡張に対応するのに十分な「中間スペース」がある。 

これにより、ワイルドカードの前後で両方の文字列を分割し、プレフィックス一致、サフィックス一致、長さの実現可能性という 3 つの条件をチェックするという問題が軽減されます。 すべての置換を探索するのではなく、1 つの構造的制約のみを検証します。

 ## アルゴリズムのチュートリアル

 1.スキャン`s`の位置を見つけるために`*`それが存在する場合。 ワイルドカードがない場合、答えは次のことを確認することになります。`s == t`。 これが必要なのは、柔軟性がないとパターンが固定されてしまうためです。 
2. もし`*`存在する、分割される`s`2 つの固定部分: プレフィックスに分割`left = s[:i]`と接尾語`right = s[i+1:]`。 これらは正確に一致する必要がある部分です`t`。 
3. かどうかを確認します。`t`少なくとも固定部分の合計と同じ長さになります。 具体的には、`len(t) >= len(left) + len(right)`。 そうでない場合は、空の代替品でもギャップを埋めることはできません。 
4. 比較する`left`という接頭辞が付く`t`。 つまり検証する`t[:len(left)] == left`。 これにより、ワイルドカードが固定構造の変更に使用されなくなります。 
5. 比較する`right`の接尾辞が付いている`t`。 つまり検証する`t[-len(right):] == right`。 これにより、ワイルドカード拡張を挿入した後にパターンの末尾が正しく配置されるようになります。 
6. プレフィックスとサフィックスの両方が一致し、長さの条件が成立する場合、ワイルドカードは正確に中間セグメントを吸収できます。`t`。 そうでなければ、それはできません。 

### なぜ効果があるのか

 ワイルドカードは唯一の自由の源であり、2 つの固定文字列の間に挿入された連続したセグメントのように動作します。 有効な一致では、ワイルドカード領域外の文字の正確な順序が保持される必要があります。 したがって、どのソリューションでも、次のプレフィックスを揃える必要があります。`s`という接頭辞が付く`t`と接尾辞`s`の接尾辞が付いている`t`。 これらの制約が満たされると、残りの部分は`t`ワイルドカード置換に一意に対応します。 これ以外の自由度は存在しないため、これらのチェックは必要かつ十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    s = input().strip()
    t = input().strip()

    if '*' not in s:
        print("YES" if s == t else "NO")
        return

    i = s.index('*')
    left = s[:i]
    right = s[i+1:]

    if len(left) + len(right) > m:
        print("NO")
        return

    if t[:len(left)] != left:
        print("NO")
        return

    if t[m - len(right):] != right:
        print("NO")
        return

    print("YES")

if __name__ == "__main__":
    solve()
```実装は、ワイルドカードが存在しない縮退ケースを処理することから始まります。これは、問題を直接の等価性チェックに減らすためです。 ワイルドカードが見つかったら、パターンをプレフィックス部分とサフィックス部分に明示的に分割し、ワイルドカード自体には触れないようにします。 

長さチェックは、短い文字列の無効なスライスを防ぎ、ワイルドカードが文字列の残りの部分をカバーする必要があるという実現可能性条件を強制するため、非常に重要です。`t`。 プレフィックスとサフィックスの比較は直接スライスを使用して行われ、文字あたり O(1) の検証が保証されます。 

実装の微妙な詳細の 1 つは、`m - len(right)`ワイルドカードがどこに動的に配置されるかを推論しようとするのではなく、 これにより、1 つ違いの間違いが回避され、ワイルドカードの大きさに関係なく接尾辞の位置合わせが維持されます。

 ## 特殊なケース

 エッジケースの 1 つは、ワイルドカードが先頭にある場合です。`s = "*abc"`そして`t = "zzzabc"`。 アルゴリズムセット`left = ""`そしてサフィックスのみをチェックします。 サフィックスマッチ`t[-3:] == "abc"`成功し、プレフィックス チェックは空に true になります。 

もう 1 つのエッジ ケースは、ワイルドカードが末尾にある場合です。`s = "abc*"`そして`t = "abcxyz"`。 ここ`right = ""`したがって、サフィックス チェックでは空の文字列が比較され、常に成功し、プレフィックス制約のみが問題となります。 

最後の微妙なケースは次のような場合です。`s`ワイルドカードがなく、次の値より長い`t`。 このアルゴリズムは直ちに等価性チェック分岐に入り、スライス ロジックを試行せずに正しく拒否し、偶発的なインデックス エラーを防ぎます。
