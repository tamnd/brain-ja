 ## 解決策
 ## 問題の理解

 ちょうど 2 列の非常に小さなゲーム ボードが与えられ、$n$列。 プレイヤーは左上のセルから開始し、右下のセルに到達したいと考えています。 一部のセルはトラップによってブロックされており、トラップに足を踏み入れるとすぐにパスが無効になります。 

移動ルールは標準のグリッド問題よりも寛大です。 どの細胞からでも$(x, y)$、任意のセルに移動できます$(x', y')$行と列の違いが最大 1 つである限り。 これには、水平、垂直、斜めの移動が含まれます。つまり、各位置は最大 8 つの隣接位置に接続されます (境界上では少なくなります)。 タスクは単に、からの有効なパスが存在するかどうかを判断することです。$(1, 1)$に$(2, n)$それは決して罠を踏まないことです。 

入力サイズは非常に小さいため、$n \le 100$。 このことから、かなり単純なグラフ走査手法でも十分であることがすぐにわかります。 すべてのセルにわたる直接 BFS または DFS は最大 200 ノードであり、各ノードには一定次数のエッジがあるため、$O(n)$または$O(n^2)$解決策は自明に速いです。 

微妙な問題は、斜めの移動ルールに起因します。 対角線が許可されているため、4 方向または 2 行の特別な構造のみを想定している多くのソリューションでは、有効なショートカットが見逃される可能性があります。 たとえば、まっすぐな水平ルートをブロックするトラップを「飛び回る」ことができます。 

もう 1 つの特殊なケースは、開始制約と終了制約から発生します。 この問題はそれを保証します$(1,1)$そして$(2,n)$は安全なので検証する必要はありませんが、やみくもに境界をチェックしたり、インデックスを誤って処理したりする実装では、依然として誤ってブロックしてしまう可能性があります。 

単純な間違いは、列内で右方向にしか移動できないと考えることです。 これは誤りです。なぜなら、垂直方向および斜め方向に移動すると以前の列に戻ることができるためです。これは、サイクルが存在することを意味します。 列インデックスの単調性を前提とした解決策はいずれも正しくありません。 

## アプローチ

 ブルートフォース解釈では、すべてのセルをグラフ ノードとして扱い、最初から検索を実行します。 各ノードには、隣接するセルがグリッド内にありトラップではないかどうかに応じて、最大 8 つのエッジがあります。 DFS または BFS は、ターゲットが見つかるか、検索によってコンポーネントが使い果たされるまで、到達可能なすべてのセルを探索します。 

しかないから$2n \le 200$すべての近隣ノードを繰り返しチェックするだけでもコストはかかりません。 最悪の場合の仕事量はエッジの数に比例します。$8 \cdot 200$したがって、数千回の操作が必要です。 

より高度な最適化は必要ありませんが、この問題が構造的に単純である理由に注目することは役に立ちます。 グリッドは小さく、接続性は静的で、パス履歴に依存する重みや制約はありません。 これにより、これは無向暗黙的グラフにおける純粋な到達可能性の問題になります。 

状態を圧縮したり、列の遷移について貪欲に推論したりすることもできますが、それは不必要であり、斜めの移動により単純な行ごとの推論が壊れるため、間違いを招く危険があります。 最も安全でクリーンなアプローチは、標準の BFS/DFS です。

 | --- | --- | --- | --- |
 | ブルートフォース DFS/BFS |$O(n)$|$O(n)$| 承認済み |
 | 最適なBFS/DFS |$O(n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 各セルをグラフ内のノードとしてモデル化します。 2 つのノードは、座標間の移動が許可され、両方のセルが安全であれば接続されています。 

1. グリッドの表現を 2 by として構築します。$n$文字の配列。 各セルは安全かブロックされています。 
2. セルを再訪問したり、斜めの動きによって引き起こされるサイクルに陥ることを避けるために、訪問先の配列を同じサイズに維持します。 
3. 開始セルでキュー (またはスタック) を初期化します。$(1, 1)$。 
4. データ構造からセルを繰り返し抽出し、それを現在位置とみなします。 
5. 現在位置が$(2, n)$、有効なパスが見つかったので、すぐに成功を返します。 
6. 行を変化させて、最大 8 つの隣接する動きをすべて試します。$-1, 0, +1$とコラム$-1, 0, +1$、ゼロ移動をスキップします。 
7. 各近隣について、それがグリッド内にあり、トラップではないことを確認します。 
8. ネイバーが有効で未訪問の場合、訪問済みとしてマークし、キューにプッシュします。 
9. 到達せずに探索が終了した場合$(2, n)$、返品失敗。 

重要な設計上の選択は、キューに押し込むときにすぐに訪問済みのマークを付けることです。 これにより、不必要な繰り返しが発生する、異なる対角線パスを介して同じ状態に再度アクセスすることが防止されます。 

### なぜ効果があるのか

 グリッドは、すべての動きが可逆的でコストが等しい、重みのないグラフを形成します。 BFS または DFS は、到達可能なノードのセットを最初から正確に探索します。 すべての有効なパスはこのグラフ内の一連の有効なエッジに対応するため、$(2, n)$検索において、有効なパスがゲーム内に存在することと同等です。 訪問された構造は、到達可能性ではなく冗長な探索を防止するだけであるため、到達可能な構成を考慮から除外することなく終了を保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n = int(input().strip())
    g = [input().strip() for _ in range(2)]
    
    # (row, col), 0-indexed
    start = (0, 0)
    target = (1, n - 1)
    
    if g[0][0] == '1' or g[1][n - 1] == '1':
        print("NO")
        return
    
    vis = [[False] * n for _ in range(2)]
    q = deque()
    q.append(start)
    vis[0][0] = True
    
    while q:
        r, c = q.popleft()
        if (r, c) == target:
            print("YES")
            return
        
        for dr in (-1, 0, 1):
            for dc in (-1, 0, 1):
                if dr == 0 and dc == 0:
                    continue
                nr, nc = r + dr, c + dc
                if 0 <= nr < 2 and 0 <= nc < n:
                    if not vis[nr][nc] and g[nr][nc] == '0':
                        vis[nr][nc] = True
                        q.append((nr, nc))
    
    print("NO")

if __name__ == "__main__":
    solve()
```この実装は、前述の BFS を直接反映しています。 グリッドは 2 つの文字列として保存され、境界での off-by-1 エラーを避けるためにインデックス付けは 0 ベースに保たれます。 ネストされたループオーバー$(-1, 0, 1)$行と列の両方で、手動でリストすることなく、可能な 8 つの手をすべて列挙します。 

よくある間違いは、$(0,0)$移動すると、同じセルが誤って無期限に再挿入されます。 もう 1 つは、訪問済みのマーキングをデキュー時まで遅らせることです。これにより、異なる対角線を介して同じノードが繰り返しエンキューされることになり、制約が小さいにもかかわらず実行時間が不必要に増加する可能性があります。 

## 実用的な例

 単純なグリッドを考えてみましょう。```
n = 4
row1 = 0000
row2 = 0010
```BFS 探索をトレースします。 

| ステップ | 現在 | 拡張後のキュー | 追加訪問 |
 | --- | --- | --- | --- |
 | 1 | (1,1) | (1,2)、(2,1)、(2,2) | (1,2)、(2,1)、(2,2) |
 | 2 | (1,2) | ... | 安全であれば隣人を追加 |
 | 3 | ... | ... | ... |

 検索では、最初から、トラップが行 2 の直接の経路をブロックしている場合でも、列 2 または 3 で行を移動することで斜めに移動することで回避できることがすぐにわかります。 

次に、ブロッキングの例を考えてみましょう。```
n = 3
row1 = 010
row2 = 101
```| ステップ | 現在 | 拡張後のキュー | 追加訪問 |
 | --- | --- | --- | --- |

 ## 特殊なケース

 一般的なエッジケースは、トラップがジグザグを形成し、直線の動きを妨げているように見えますが、それでも斜めの逃げ場を残している場合です。 例えば：```
n = 3
000
010
```から$(1,1)$、BFS は次の場所に移動できます。$(2,2)$斜めに、そして、$(1,3)$、そして最後に$(2,3)$。 8 方向すべてが常に探索されるため、アルゴリズムはこれを正しく処理します。 

もう 1 つのエッジ ケースは、唯一の有効なパスが隣接する列の行を繰り返し切り替える場合です。 斜めの移動がなければ、これには明示的な垂直遷移が必要になりますが、ここでは隣接要素の列挙の一部として自然に発生します。 

最後に、BFS は方向の偏りを想定せず、到達可能なすべての構成を均一に扱うため、細い曲がりくねった廊下を除いてほとんどすべてのセルがブロックされているケースでも正しく処理されます。
