 ## 解決策
 ## 問題の理解

 バスは、固定された一連の道路セグメントを通過します。 連続するセグメントの間には信号機があり、すべての信号は同じ同期サイクルに従います。 

各サイクルは継続します`g + r`秒。 最初はライトが緑色です`g`サイクルの秒間、次の期間は赤色になります。`r`秒。 時間に`0`すべての信号は緑色で始まります。 バスは信号が青のときにのみ交差点を横断できます。 ちょうど緑が終了するときに到着した場合は、次の緑フェーズまで待つ必要があります。 

入力により、すべての道路セグメントの移動時間が得られます。 バスは出発時間に合わせて出発します`t`、最初のセグメントを通過し、場合によっては最初の交差点で待機し、次のセグメントを通過するなど、最後のセグメントの後に目的地に到着するまで続きます。 

クエリ時間ごとに`t_i`、目的地への正確な到着時間を計算する必要があります。 

この制約により、クエリごとにすべての交差を個別にシミュレートすることが完全に排除されます。 両方`n`そして`q`までです`10^5`、だから、`O(nq)`ソリューションは次のように実行されます`10^10`制限時間を大幅に超えた最悪の場合の作戦。 クエリごとに線形または対数に近い値が必要です。 

厄介な点は、待機が現在時間のサイクル長に依存することです。 バスはわずかに異なる時間に同じ交差点に到着し、すぐに通過するか、ほぼ赤信号のフェーズ全体を待つことがあります。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

ちょうど青が終わるときにバスが交差点に到着したとします。```
g = 3, r = 2
arrival = 3
```間隔`[0,3)`緑色であり、`[3,5)`は赤です。 バスは待たなければなりません。 治療中`<= g`緑は間違った答えを出します。 

もう 1 つの微妙なケースは、多くの連続する交差点を待たずに通過する場合に発生します。```
n = 2
g = 10, r = 5
segments = [2,2,2]
start = 1
```交差点の到着時間は、`3`そして`5`、両方とも緑色の内側にあります。 サイクルを誤って丸める不注意なシミュレーションにより、不必要な待機が挿入される可能性があります。 

その逆の極端な行為が交差点ごとに繰り返される。```
n = 2
g = 1, r = 10
segments = [1,1,1]
start = 0
```バスは時間通りに最初の交差点に到着します`1`、ちょうど赤になるまで待機します。`11`で 2 番目の交差点に到着します。`12`、まで再び待ちます`22`、で終了します`23`。 

もう 1 つのよくあるバグは、その後の最終セグメントに信号機がないことを忘れることによって発生します。 待ち時間は交差点でのみチェックされ、目的地に到着した後はチェックされません。 

## アプローチ

 直接シミュレーションは簡単です。 クエリごとに、現在の時刻を維持します。 セグメントの長さを追加し、これが最後のセグメントでない場合は、新しい時点での信号機の状態を検査します。 

させて`T = g + r`。 もし`current % T < g`、バスはすぐに通過します。 それ以外の場合は、次の倍数まで待機します。`T`。 

このシミュレーションは、移動と待機の正確なルールに従っているため、正確です。 問題はコストです。 すべてのクエリがすべてを処理します`n`交差するため、全体の複雑さは次のようになります。`O(nq)`。 両方の値が等しい場合`10^5`、これは届きます`10^10`操作。 

重要な観察は、待機動作は時間の剰余にのみ依存するということです。`T`。 

関数を定義します。```
f(x) = final arrival time if the bus starts at time x
```開始時間をちょうど 1 サイクルだけ増やした場合に何が起こるかを考えてみましょう`T`。 

今後の到着時間もすべて正確に増加します`T`、したがって、緑/赤の決定は同じままになります。 軌道全体が 1 サイクル前方にシフトします。 

つまり:```
f(x + T) = f(x) + T
```この周期構造により、問題は、`T`サイクル長を法とした可能な剰余。 

残念ながら`T`それ自体は次のように大きくなる可能性があります`10^9`したがって、すべての剰余を直接事前計算することはまだできません。 

次の観察はさらに強力です。 開始時刻は連続的に変化するため、待機パターンは特定のブレークポイントでのみ変化します。 2 つのブレークポイントの間では、答えは単純に次のようになります。```
f(x) = x + constant
```各交差は、そこでの待機をトリガーする不良残基の 1 つの間隔に寄与します。 すべての交差点を処理した後、時間軸全体が、合計待ち時間が固定される間隔に分割されます。 

交差点を逆方向に処理して、順序付けられたマップ内でこれらの間隔を維持できます。 その後、すべてのクエリは一定間隔での二分検索になります。 

最終的な複雑さは、`O(n log n + q log n)`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | 最適 | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### 主要な再定式化

 しましょう:```
pref[i] = l1 + l2 + ... + li
```最初の部分を通過した後、`i`セグメントに達すると、バスは交差点に到着します`i`時間:```
start + pref[i] + waits_before_i
```バスは交差点で待たなければなりません`i`もし:```
(start + pref[i] + waits_before_i) mod T >= g
```順方向にシミュレーションする代わりに、待機が発生する開始時刻を決定します。 

### 区間の解釈

 交差点までに蓄積された待ち時間の合計を仮定します`i`開始時間の一定の間隔内ですでに修正されています。 

次に、交差点での待機条件`i`は、開始時間に関する単純なモジュラー間隔条件になります。 

この間隔を超えると、将来の待機時間がちょうど増加します`r`。 

交差を 1 つずつ処理するときに、開始時間の残差を均等に累積された待機時間で間隔に分割します。 

### データ構造

 剰余モジュロにわたって互いに素な区間を保存します`T`。 

間隔ごとに次のことを維持します。```
value = total extra waiting accumulated
```最初はすべての残基が待機しています`0`。 

交差点を処理する場合:

 1. 現在の間隔ごとに、どの剰余部分範囲がこの交差点で待機を引き起こすかを計算します。 
2. 必要に応じて間隔を分割します。 
3.追加`r`影響を受ける駒の待機値に。 

各交差点で最大 2 つの新しい境界が導入されるため、区間の総数は線形のままです。 

### 質問に答える

 クエリ開始時刻の場合`x`:

 1. コンピューティング`k = x mod T`。 
2. 次の区間を見つけます。`k`。 
3. 保存されている待機値を次のようにします。`w`。 
4. 最終的な答えは次のとおりです。```
x + total_segment_sum + w
```### なぜ効果があるのか

 残基の任意の間隔内では、すべての交差点でまったく同じ決定が行われ、すぐに通過するか、赤のフェーズを 1 つ待つかのいずれかになります。 決定の順序は固定されているため、合計の待機時間も固定されます。 

残基が境界を越え、交差部分で動作が変化すると、待機時間の合計はちょうど 1 つの追加の赤色フェーズだけ増加します。 インターバル構造はこれらのトランジションを正確に捉えます。 

すべてのライトは同期されているため、開始時間を 1 サイクルだけシフトするとすべての決定が保持されるため、残差クラスが動作を完全に決定します。 

## Python ソリューション```python
import sys
from bisect import bisect_right

input = sys.stdin.readline

def solve():
    n, g, r = map(int, input().split())
    l = list(map(int, input().split()))

    T = g + r
    total = sum(l)

    pref = []
    s = 0
    for i in range(n):
        s += l[i]
        pref.append(s % T)

    # events[pos] = added waiting after this breakpoint
    events = []

    cur_add = 0

    intervals = [(0, 0)]

    for p in pref:
        new_intervals = []

        for start, val in intervals:
            end = T

            L = (g - p - val) % T
            R = (-p - val) % T

            if L < R:
                pieces = [
                    (start, min(end, L), val),
                    (max(start, L), min(end, R), val + r),
                    (max(start, R), end, val),
                ]
            else:
                pieces = [
                    (start, min(end, R), val),
                    (max(start, R), min(end, L), val + r),
                    (max(start, L), end, val),
                ]

            for a, b, v in pieces:
                if a < b:
                    new_intervals.append((a, v))
                    if b < T:
                        new_intervals.append((b, val))

        new_intervals.sort()

        merged = []
        for pos, val in new_intervals:
            if merged and merged[-1][1] == val:
                continue
            merged.append((pos, val))

        intervals = merged

    starts = [x[0] for x in intervals]
    vals = [x[1] for x in intervals]

    q = int(input())

    out = []

    for _ in range(q):
        t = int(input())

        k = t % T
        idx = bisect_right(starts, k) - 1

        out.append(str(t + total + vals[idx]))

    print("\n".join(out))

solve()
```このソリューションでは、明示的な範囲ではなく間隔の境界を保存します。 間隔が次から始まる場合`starts[i]`、次の境界まで続きます。 

前処理フェーズでは、残差の分割を段階的に調整します。 交差点ごとに、どの残基がそこで待機することを強制するかを決定し、追加します。`r`彼らの蓄積された遅れに。 

モジュラー演算が最も難しい部分です。 条件:```
(start + pref[i] + current_wait) mod T >= g
```残基の循環間隔を定義します。 循環間隔はゼロの周りをラップする可能性があるため、実装では 2 つのケースを個別に処理します。 

もう 1 つの微妙な点は、`>= g`。 時間ぴったりに到着`g`信号がすでに赤になったことを意味します。 使用する`>`代わりに、不正確な答えが生成されます。 

すべての算術演算では Python 整数が使用され、必要な 64 ビット範囲が自然にサポートされます。
