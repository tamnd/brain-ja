 ## 解決策
 ## 問題の理解

 私たちは持っています`n`人々は厳密に増加する座標で線上に配置されます。 PMPは人から始まる`s`、すぐに訪問済みとしてカウントされます。 それ以降のすべての移動は、その移動に使用されたチケットに応じて、厳密に左または厳密に右に進む必要があります。 

左側のチケットを使用すると、大きいインデックスから小さいインデックスに移動できます。 適切なチケットを使用すると、小さいインデックスから大きいインデックスに移動できます。 PMP はまさに`l`チケットを残して、`n - 1 - l`適切なチケットを購入し、すべての人が必ず 1 回訪問する必要があります。 

タスクは、総移動距離を最小限に抑え、最適な訪問順序を 1 つ出力することです。 

最初の重要な観察は、方向制約がツアー全体ではなく、個々の動きごとに適用されるということです。 PMP は、チケット数が一致する限り、左右を何度でも交互に実行できます。 

座標はソートされており、到達できます`10^9`したがって、距離は 64 ビット整数で保存する必要があります。 人数は以下までです`10^5`、二次関数は即座に除外されます。 一定期間にわたる動的プログラミング ソリューション`O(n^2)`状態はすでにメモリと時間の両方で大きすぎます。 線形に近いものが必要です。`O(n log n)`。 

問題の微妙な部分は実現可能性です。 すべてのペアではありません`(l, s)`全員を訪問できるようになります。 

仮定する`n = 5`、`s = 1`、`l = 2`。```
1 2 3 4 5
^
start
```一番左の位置から、さらに左には人がいません。 残ったチケットは一切使用できません。 正しい出力は次のとおりです`-1`。 

不注意な解決策では、チケットの合計数が次と等しいかどうかのみを確認する可能性があります。`n - 1`これは常に true ですが、位置の制約は無視されます。 

もう 1 つの簡単な間違いは、全体の移動を最小限に抑えるということは、常に近くの未訪問の人を訪問することを意味すると仮定することです。 考慮する：```
n = 5, s = 3, l = 2
x = [0, 1, 100, 101, 102]
```貪欲に最も近い側に最初に行くと、次のようになります。```
100 -> 101 -> 102 -> 1 -> 0
distance = 1 + 1 + 101 + 1 = 104
```しかし、より良いルートは次のとおりです。```
100 -> 1 -> 0 -> 101 -> 102
distance = 99 + 1 + 101 + 1 = 202
```実際、この例はさらに深いことを示しています。チケットの制約により、後で高価なジャンプが強制される可能性があります。 ローカルでの貪欲な決定は、将来の方向の可用性を制御しません。 

もう 1 つの危険なコーナーケースは、片側のノードが非常に少ない場合に発生します。```
n = 6, s = 2, l = 4
```左側にはノードが 1 つだけあります`s`したがって、左側のノードがすべて使い果たされる前に、最大で 1 回の左移動が発生する可能性があります。 有効な解決策はすべて、途中で右側に戻り、慎重にチケットを消費する必要があります。 単純なシミュレーションは、一方の側で使用可能な手をすべて早く消費してしまうため、スタックしてしまうことがよくあります。 

問題の実際の構造は、有効な一連の方向がどのようなものかを理解することから生まれます。 

## アプローチ

 ブルートフォースのアイデアは単純です。 残りのすべての順列を試すことができます`n - 1`人々は、各移動方向が利用可能なチケットと一致するかどうかを確認し、合計距離を計算します。 

これが機能するのは、概念的に制約が小さいためです。すべての有効なツアーは単に頂点の順序にすぎません。 問題は順列の数です。 たとえ`n = 15`、すでにおおよその情報が得られています`10^12`可能性。 

より洗練されたブルート フォースでは、サブセット上で DP を使用します。```
dp[mask][last][left_used]
```これにより、どの人が訪問したか、現在どこにいるか、残りのチケットが何枚消費されたかが追跡されます。 

すべての移動は現在のエンドポイントと移動方向のみに依存するため、トランジションは正確です。 しかし、状態の数は膨大になります。```
2^n * n * n
```平`n = 25`は不可能ですが、実際の限界は`10^5`。 

したがって、ラインの形状を利用する必要があります。 

重要な観察は、各方向クラス内の正確な順序はほとんど重要ではないということです。 重要なのは、何回立場を変えるかです。 

私たちが現在、ある位置にいるとします。 連続して複数回右に移動する場合、最も安価な方法は、右側のノードを昇順に訪問することです。 スキップすると、不必要な後戻りが発生するだけです。 

同様に、連続して左に移動すると、降順でノードを訪問する必要があります。 

つまり、あらゆる最適解は非常に厳密な形をとります。 パスは、左側の最も近い未訪問のノードと右側の最も近い未訪問のノードを交互に取得します。 唯一の本当の選択は、次にどの方向に進むかです。 

次に、チケットの数を考えてみましょう。 させて：```
L = l
R = n - 1 - l
```左に移動するたびに現在のインデックスが減少し、右に移動するたびに現在のインデックスが増加します。 

から始まる`s`、すべての移動の後:```
final_position = s + R - L
```すべての訪問インデックスは以下の範囲内に収まる必要があるため、`[1, n]`、実行可能条件が得られます。```
1 <= s + R - L <= n
```置き換える`R = n - 1 - L`:```
1 <= s + (n - 1 - 2L) <= n
```これは次のように単純化されます。```
s - 1 <= L <= n - s
```この条件でも十分です。 

実現可能性が確立されると、最適な戦略は驚くほどシンプルになります。 可能な限り、常に方向を変える必要があります。 ロングジャンプは、現在訪問している間隔の一方の側からもう一方の側に移動するときに発生します。 代替では、現在の位置が残りのノードの中央付近に維持されるため、これらのジャンプが最小限に抑えられます。 

最適な構築は次のとおりです。```
left, right, left, right...
```チケットの数と空き状況に応じて、右から始まる対称バージョンも選択できます。 

各移動は常に、その方向で最も近い未訪問のノードを移動します。 

これにより、線形時間構造が得られます。

 | ブルートフォース | お(ん!) | O(n) | 遅すぎる |
 | ビットマスク DP | O(2^n · n^2) | O(2^n · n) | 遅すぎる |
 | 貪欲に建設的 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.読む`n`、`l`、`s`そして座標配列。 
2. 正しいチケットの数を計算します。```
r = n - 1 - l
```1. 実現可能性を確認します。 

左に動かすと、現在のインデックスが減少します。 しかないので、`s - 1`開始時に残った人、これ以上使用することはできません`s - 1`残ったチケット。 

同様に、あるのは`n - s`右側の人が多いため、それ以上の右側のチケットを使用することはできません。 

いずれかの条件が失敗した場合は、出力します`-1`。 

1. 2 つのポインターを維持します。`L`から始まります`s - 1`、左側の最も近い未訪問者。`R`から始まります`s + 1`、右側の最も近い未訪問者。 

1. 貪欲に動作シーケンスを構築します。 

可能な限り、残りのチケットが多い方向を使用してください。 これによりツアーのバランスが保たれ、後で一方に偏ってしまうのを防ぎます。 

左に移動した場合は追加します`L`答えとデクリメントへ`L`。 

正しい動きをした場合は追加します`R`答えと増加`R`。 

1.すべて終わるまで続けます`n - 1`動きが構築されます。 
2. 生産されたオーダーをシミュレートして合計距離を計算します。 

から開始`s`。 

次のすべての人のために`v`:```
cost += abs(x[cur] - x[v])
cur = v
```1. 総距離と訪問順序を出力します。 

### なぜ効果があるのか

 常に、左への移動で到達可能な最も安価なノードは、左側にある最も近い未訪問のノードです。 それ以上の距離を選択すると、より近いノードがスキップされ、後で追加の交差が強制され、合計距離が増加するだけです。 

同じ議論が右の動きにも当てはまります。 

したがって、意味のある唯一の決定は、方向の順序です。 一方向への連続移動が多すぎると、現在の位置が極端な終点に向かって移動し、次の反対方向へのジャンプのコストが高くなります。 可能な限り交互に配置すると、これらの交差間隔のジャンプが最小限に抑えられます。 

実行可能条件により、必要なすべての方向への移動が、その側のノードを使い果たすことなく常に実行できることが保証されます。 

すべての移動が局所的に最適であり、方向パターンによって将来の横断コストが最小限に抑えられるため、結果として得られるツアーは全体的に最適になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, l, s = map(int, input().split())
    x = list(map(int, input().split()))

    r = n - 1 - l

    if l > s - 1 or r > n - s:
        print(-1)
        return

    left_ptr = s - 1
    right_ptr = s + 1

    left_rem = l
    right_rem = r

    ans = []

    while left_rem > 0 or right_rem > 0:
        if left_rem > right_rem:
            ans.append(left_ptr)
            left_ptr -= 1
            left_rem -= 1
        else:
            ans.append(right_ptr)
            right_ptr += 1
            right_rem -= 1

        if left_rem == 0:
            while right_rem > 0:
                ans.append(right_ptr)
                right_ptr += 1
                right_rem -= 1

        if right_rem == 0:
            while left_rem > 0:
                ans.append(left_ptr)
                left_ptr -= 1
                left_rem -= 1

    cur = s - 1
    total = 0

    for v in ans:
        total += abs(x[cur] - x[v - 1])
        cur = v - 1

    print(total)
    print(*ans)

solve()
```実現可能性のチェックは最初の微妙な部分です。 左側のチケットには、現在の位置の左側に実際のノードが必要です。 左への移動中にインデックスは厳密に減少するため、それ以上の値を使用することはできません。`s - 1`全体的にそういう動き。 

この構造により、開始位置の周囲に 2 つの移動境界が維持されます。 すべての左への移動は最も近い残りの左ノードを消費し、すべての右への移動は最も近い残りの右ノードを消費します。 

実装では、出力形式で 1 ​​から始まるインデックスが必要なため、1 から始まるインデックスを使用してノード番号を格納します。 座標配列自体は 0 ベースのままであるため、すべてのアクセスで`v - 1`。 

もう 1 つの簡単な間違いは、建設中に距離を段階的に計算することです。 現在の位置は移動するたびに変化するため、最も安全なアプローチは、最初に完全な順序を構築し、その後パスを一度シミュレートすることです。 

距離に関係するすべての算術では Python 整数が使用され、当然 64 ビット範囲がサポートされます。

l > s - 1
2 > 0
```そしてすぐに印刷します`-1`。

0 5 10 20
