 ## 解決策

 ## 問題の理解

 時間順にシャーマンを表す一連の値が与えられます。 各ポジションには「力」があり、シングルポジションを継続的に更新していきます。 更新のたびに、インデックスが存在するかどうかを確認する必要があります。$j$の値が$j$厳密に前のすべての値の合計に等しい$j$。 そのようなインデックスが存在する場合はそれらのいずれかを出力し、存在しない場合は -1 を出力します。 

より操作的な方法で言い換えると、ポイント更新の下で配列を維持し、正しいエンドポイントがプレフィックスの合計と等しくなるようにプレフィックス境界によって配列が分割されているかどうかを繰り返し確認します。 

制約は次のとおりです$2 \cdot 10^5$要素と$2 \cdot 10^5$そのため、クエリごとのプレフィックス合計を再計算することはすでに境界線に達していますが、まだ実現可能です。 本当に難しいのは、クエリごとに各位置をチェックすることは最悪の場合二次関数的となり、遅すぎることです。 高速な範囲合計クエリを可能にする構造と、更新のたびにすべての位置をスキャンせずに有効なインデックスを見つける何らかの方法が必要です。 

すべての値が小さいかゼロの場合、微妙なエッジ ケースが発生します。 その場合、多くのインデックスが条件を自明または部分的に満たすため、1 つの候補 (最後の要素やプレフィックスをスキャンした後の最初の一致など) だけをチェックする単純なアプローチでは、配列内の他の場所で有効な答えを簡単に見逃してしまう可能性があります。 もう 1 つのエッジ ケースは、更新によって値が繰り返し反転されるため、有効なインデックスが配列全体で移動し、静的な事前計算アプローチが破壊される場合です。 

## アプローチ

 ブルートフォース戦略は簡単です。各更新後にプレフィックスの合計を左から右に計算し、位置が存在するかどうかを確認します。$j$満足する$a_j = \sum_{i<j} a_i$。 各クエリにはコストがかかります$O(n)$、与える$O(nq)$トータルオペレーション。 と$n, q \le 2 \cdot 10^5$、これは届きます$4 \cdot 10^{10}$これは実行可能な限界をはるかに超えています。 

重要な観察は、すべてを最初から再計算する必要はなく、プレフィックスの合計を維持し、それらを効率的にクエリするためだけであるということです。 条件$a_j = \text{prefixSum}(j-1)$次のように書き換えることができます。$$\text{prefixSum}(j) = 2 \cdot \text{prefixSum}(j-1)$$これでも検索が直接単純化されるわけではありませんが、問題がプレフィックスの合計構造に密接に関係していることがわかります。 

より直接的なアプローチは、プレフィックス合計のフェンウィック ツリー (またはセグメント ツリー) を維持し、条件が当てはまるインデックスをすばやく見つけることができる 2 番目の構造を使用することです。 秘訣は、各位置に次のものを格納する派生配列上にセグメント ツリーを維持することです。$$f[i] = a[i] - \text{prefixSum}(i-1)$$したがって、有効なキングシャーマンはまさに次のようなインデックスになります。$f[i] = 0$。 問題は、プレフィックスの合計が更新に依存することです。$f[i]$独立していない。 代わりに、2 つのセグメント ツリーを維持します。1 つは配列自体用 (プレフィックスの合計を計算するため)、もう 1 つはプレフィックスの合計に基づくインデックスの検索を使用した暗黙的なチェックです。 

標準的な意図されたソリューションでは、明示的なメンテナンスを回避します。$f[i]$。 代わりに、候補インデックスについて次のことが観察されます。$i$、そのプレフィックスの合計を計算できます。$O(\log n)$なので、有効性をすぐにテストできます。 問題は、単調述語がツリー上で保持されるインデックスを見つけることに帰着します。これは、チェック関数を使用してセグメント ツリー上で二分探索を行うことを提案します。 

合計を格納するセグメント ツリーを構築し、セグメントを表すノードで再帰的検索を実行します。$[l, r]$、左半分の合計を計算し、潜在的な候補ポジションと比較します。 重要なアイデアは、トラバーサル中にその場でプレフィックスの合計を維持すれば、有効なインデックスが左側または右側の子に存在するかどうかを判断できるということです。 

これにより、各ノードで現在のセグメントの左側にあるすべての合計が維持されるツリー降下が行われ、中間点の状態を効率的にチェックできるようになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nq)$|$O(n)$| 遅すぎる |
 | ガイド付き検索を使用したセグメント ツリー |$O(q \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 配列全体の合計を格納するセグメント ツリーを使用します。 

1. 範囲の合計を対数時間でクエリできるように、初期配列にセグメント ツリーを構築します。 これは、すべての有効性チェックがプレフィックスの合計に依存するため必要です。 
2. 位置の更新ごとに$p$、その位置に対応するセグメント ツリー ノードを新しい値で更新します$x$。 これにより、今後のすべてのプレフィックス合計に変更が確実に反映されます。 
3. 更新のたびに、セグメント ツリーに対する再帰検索を使用して、有効なインデックスの検索を試みます。 と呼ばれる実行中のプレフィックス合計を維持します。`left_sum`、最初はゼロで、厳密に現在のセグメントの前の要素の合計を表します。 
4. セグメントをカバーするノードで$[l, r]$, compute the sum of the left child. これは、完全に調査した場合の左半分の貢献を表します。 条件が満たされる位置が存在するかどうかをチェックすることで、有効なインデックスが左側の子に存在するかどうかをテストします。`left_sum`。 
5. 左の子に有効なインデックスが含まれている可能性がある場合は、最初にその子に降りていきます。`left_sum`変わらない。 それ以外の場合は更新します`left_sum`左の子の合計を合計し、右の子に移動します。 
6. 葉の位置に到達したら$i$かどうかを確認します。`left_sum == a[i]`。 もしそうなら、私たちは戻ります$i$正当なキングシャーマンとして。 
7. トラバース中に条件を満たすリーフがない場合は、-1 を返します。 

検索が機能するのは、すべての決定点でセグメント境界に対応する正確なプレフィックスの合計が保存されているためです。したがって、リーフ チェックは元の定義と同等になります。 

### なぜ効果があるのか

 再帰のどの時点でも、`left_sum`元の配列順序で現在のセグメントよりも厳密に前のすべての要素の合計に等しくなります。 この不変式により、インデックスに到達したときに、$i$、`left_sum`まさに$\sum_{j<i} a[j]$。 リーフ条件は問題の要件と直接一致するため、返されたインデックスはすべて有効です。 逆に、有効なインデックスが存在する場合、各ノードでの決定が正確なプレフィックス分割に基づいて実現可能性を維持するため、ガイド付き降下はそれを含むブランチを決して破棄しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.t = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def build(self, v, l, r, arr):
        if l == r:
            self.t[v] = arr[l]
        else:
            m = (l + r) // 2
            self.build(v * 2, l, m, arr)
            self.build(v * 2 + 1, m + 1, r, arr)
            self.t[v] = self.t[v * 2] + self.t[v * 2 + 1]

    def update(self, v, l, r, pos, val):
        if l == r:
            self.t[v] = val
        else:
            m = (l + r) // 2
            if pos <= m:
                self.update(v * 2, l, m, pos, val)
            else:
                self.update(v * 2 + 1, m + 1, r, pos, val)
            self.t[v] = self.t[v * 2] + self.t[v * 2 + 1]

    def find(self, v, l, r, left_sum):
        if l == r:
            return l if self.t[v] == left_sum else -1

        m = (l + r) // 2
        left_sum_left = left_sum

        if self.t[v * 2] >= 0:
            res = self.find(v * 2, l, m, left_sum_left)
            if res != -1:
                return res

        left_sum_right = left_sum + self.t[v * 2]
        return self.find(v * 2 + 1, m + 1, r, left_sum_right)

    def query_answer(self):
        return self.find(1, 0, self.n - 1, 0)

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    st = SegTree(a)

    for _ in range(q):
        p, x = map(int, input().split())
        st.update(1, 0, n - 1, p - 1, x)
        ans = st.query_answer()
        print(ans + 1 if ans != -1 else -1)

if __name__ == "__main__":
    solve()
```セグメント ツリーには合計が格納されるため、トラバーサル中にプレフィックス推論を再構築できます。 更新操作では、変更が行われるたびに正確さが維持されます。 

検索関数は、プレフィックスの合計を最初から再計算するのではなく、暗黙的に再構築する制御された降下です。 

微妙な点の 1 つは、インデックスは内部的には 0 から始まりますが、出力では 1 から始まるため、検索が成功した後に最終調整が必要になることです。 

## 実用的な例

 ### 例 1

 入力:```
2 1
1 3
1 2
```更新後の配列は次のようになります`[2, 3]`。 

私たちは以下を横断します:

 | ステップ | セグメント | 左和 | アクション |
 | --- | --- | --- | --- |
 | 1 | [0,1] | 0 | 左の子をチェック |
 | 2 | [0,0] | 0 | 0 != 2 |
 | 3 | [1,1] | 2 | 2 != 3 |
 | 4 | 終わり | - | 一致しません |

 プレフィックス合計の等価性を満たすインデックスがないため、出力は -1 になります。 

### 例 2

 更新後の入力シーケンスは最終的に次のようになります`[2, 4, 6]`。 

| ステップ | セグメント | 左和 | アクション |
 | --- | --- | --- | --- |
 | 1 | [0,2] | 0 | 最初に左に行きます |
 | 2 | [0,1] | 0 | リーフ 0 に一致はありません |
 | 3 | [2,2] | 6 | チェックリーフ |
 | 4 | 一致 | - | インデックス 2 を返す |

 これにより、アルゴリズムが 1 ベースのインデックス付けでインデックス 3 を正しく識別していることが確認されます。

 ## 特殊なケース

 サイズ 1 の最小配列は、アルゴリズムが空のプレフィックス合計をゼロとして正しく処理するかどうかをテストします。 更新後に単一の値がゼロになった場合、インデックスは受け入れられる必要があります。 

完全に均一な配列では、複数のインデックスが条件を満たす可能性があり、アルゴリズムが一意性を仮定してはいけないという事実が強調されます。 

次のようなプレフィックスの等価性が存在しないケース`[1, 2, 4]`を使用すると、一致を誤って報告することなく、検索でセグメント ツリーの両方のブランチが正しく検索されるようになります。 

最後のエッジケースは、更新によって有効なインデックスが配列全体で移動される場合です。 検索は更新のたびに再計算されるため、古い仮定がクエリ間で持続してはなりません。
