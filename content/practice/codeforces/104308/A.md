 ## 解決策
 ## 問題の理解

 入力は、単位幅のレンガを垂直に積み重ねて構成されたいくつかの独立した「ランドスケープ」を記述します。 各ランドスケープは、位置の値が格納される配列です。`i`はその時点での壁の高さを表します。 

雨が降ると、高い壁の間の隙間に水がたまることがあります。 水は、位置の左側と右側の両方に高いまたは同等の壁がある場合にのみ閉じ込められます。そうでない場合、水は流れ出てしまうからです。 

各テスト ケースのタスクは、雨が降った後に構造全体に閉じ込められたままになる水の総量を計算することです。 

この制約は最大 10,000 のテスト ケースを意味しますが、すべてのケースにわたるポジションの合計数は最大 20,000 です。 この単一の境界が重要です。テスト ケースごとに線形に近いソリューションはすでに遅すぎますが、全体として要素ごとに線形スキャンであれば許容できます。 テスト ケースごとの二次関数は、限界をはるかに超えます。 

正確さのためには、いくつかの特殊なケースが重要です。 

次のような厳密に増加する配列`[1, 2, 3, 4]`どの位置にもそれ自体より高い左側の境界がないため、水をトラップしません。 答えは 0 でなければなりません。 

次のような厳密に減少する配列`[4, 3, 2, 1]`も同じ理由で水をトラップしませんが、適切なペアリングを行わずに片側の最大値のみを調べる単純なアルゴリズムは、不用意に実装された場合、マイナスの寄与または部分的な寄与を誤ってカウントする可能性があります。 

ようなフラット配列`[2, 2, 2, 2]`水分も溜まりません。 一部の不適切な実装では、包括的な最大値の代わりに厳密な不等式を使用する場合、誤って等しい境界がトラップ スペースとして扱われてしまいます。 

最後に、次のような単一要素または空構造のような場合`[5]`コンテナを形成できないため、0 を返さなければなりません。 

## アプローチ

 閉じ込められた水を計算する直接的な方法は、各位置を個別に検査し、その上に溜まっている水の量を判断することです。 特定のインデックスに対して`i`、水位は左側の最も高い壁と右側の最も高い壁によって制限されます。 それらを次のように表すと、`L[i]`そして`R[i]`、次に水上の位置`i`は`max(0, min(L[i], R[i]) - h[i])`。 

ブルートフォース実装は次のように計算します。`L[i]`そして`R[i]`すべてのインデックスを左右にスキャンします。 これは、各位置の制約を明示的に再構築するため、正しいです。 ただし、各インデックスの境界を再計算するには O(n) の作業が必要となり、テスト ケースごとに O(n²) の作業が必要になります。 合計あり`n`最大 2×10⁴ では、テスト ケースが敵対的に分散されている場合、この最悪の動作は 1 秒という厳しい制限内では遅すぎます。 

重要な点は、左右の最大値を繰り返し再計算する必要がないことです。 これらは一度だけ事前計算できます。 プレフィックス最大値とサフィックス最大値の配列を取得したら、各位置を O(1) で評価することができ、問題を線形スキャンに減らすことができます。 さらに最適化を進めると、両端から実行最大値を維持する 2 ポインター手法を使用して補助配列が完全に削除され、各要素が 1 回処理されるようになります。 

2 ポインタ法が機能するのは、どの位置でも閉じ込められた水の制限要因が常に、どちらかの側からこれまでに観察された最良の境界のうち小さい方であるためです。 常に小さい境界を持つ側を進めることで、そのステップでの決定が最終的なものであり、後から改善することはできないことが保証されます。

 ## アルゴリズムのチュートリアル

 最大値を実行するツーポインター戦略を使用します。 

1. 2 つのポインタを初期化する`l = 0`そして`r = n - 1`、および 2 つの変数`left_max = 0`そして`right_max = 0`。 これらは、これまでに各側から見た最良の境界を表しています。 
2. その間`l < r`、 比較する`h[l]`そして`h[r]`。 高さの小さい側が次の計算を決定します。 
3. もし`h[l] <= h[r]`、位置を処理します`l`。 その理由は、正しい境界が少なくとも次の値であることがすでに保証されているためです。`h[l]`したがって、制限要因は次のとおりです。`left_max`。 もし`h[l] >= left_max`、更新します`left_max`。 そうしないと、水が次の場所に蓄積します。`left_max - h[l]`。 次にインクリメントします`l`。 
4. それ以外の場合は位置を処理します`r`対称的に。 もし`h[r] >= right_max`、 アップデート`right_max`。 それ以外の場合は追加します`right_max - h[r]`。 次にデクリメントします`r`。 
5. スイープ中にすべての寄与を蓄積します。 

すべてのステップで、反対側がその指数の上限を形成するのに十分な高さが保証されているため、将来の情報を必要とせずに、常に 1 つの境界に対する水の寄与を最終決定します。 

### なぜ効果があるのか

 不変条件は、いかなる瞬間においても、すべての位置が現在の位置の厳密に外側であるということです。`[l, r]`ウィンドウは、正しい境界制約を使用してすでに完全に処理されています。 小さい側を処理するという決定により、選択したインデックスの反対側の境界が処理される高さと少なくとも同じ大きさになることが保証されるため、不明な制限要因は処理される側の実行最大値だけになります。 これにより、後の調整によって計算された水位が変更されるのを防ぎます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        h = list(map(int, input().split()))

        l, r = 0, n - 1
        left_max, right_max = 0, 0
        water = 0

        while l < r:
            if h[l] <= h[r]:
                if h[l] >= left_max:
                    left_max = h[l]
                else:
                    water += left_max - h[l]
                l += 1
            else:
                if h[r] >= right_max:
                    right_max = h[r]
                else:
                    water += right_max - h[r]
                r -= 1

        out.append(str(water))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```コードは、中心に向かって縮小する 2 つのポインターを維持します。 各ステップで、小さい方の境界が最初に処理されます。これは、その側の水位が、これまでに確認された最良の境界によってすでに完全に決定されているためです。 実行最大値により、配列全体のスキャンが再計算されなくなり、累積された`water`変数はすぐに貢献を収集します。 

よくある実装上の間違いは、比較することです。`h[l]`そして`h[r]`ただし、個別の最大値を維持することを忘れると、内部ピークが現れたときに過小カウントされてしまいます。 もう 1 つの問題は、現在の高さを使用する前にポインターを更新することです。これにより、ロジックが 1 インデックス分シフトされ、結果が静かに破損します。

 ## 特殊なケース

 単一要素の入力の場合、次のようになります`[7]`の場合、アルゴリズムは両方のポインターを同じインデックスに設定し、処理せずにすぐに終了し、0 を生成します。境界は形成されないため、水を数えることはできません。 

のようなフラットな構造の場合`[4, 4, 4, 4]`、 両方`left_max`そして`right_max`はすぐに 4 に更新され、すべての比較で境界以下のギャップは検出されません。 蓄積された水は全体を通して 0 のままであり、予想される物理的解釈と一致します。 

厳密に増加するシーケンスの場合、左ポインタ側が常に更新されます。`left_max`欠陥が検出される前に、各ステップで。 どの要素もその実行最大値を下回ることがないため、水は追加されません。 同じロジックが厳密に減少するシーケンスにも対称的に適用され、右ポインタが優先され、その側での蓄積が防止されます。
