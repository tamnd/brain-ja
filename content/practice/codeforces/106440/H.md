 ## 解決策
 ## 問題の理解

 この問題では、時間の経過とともにリズム チャートのテンポが切り替わるタイムラインについて説明します。 チャートはビート単位で測定されますが、実際の実行時間は秒単位で測定されます。 これら 2 つの間の変換は現在の BPM に依存し、BPM は特定のビート位置で変化します。 

より具体的には、一連の変化点が与えられます。 各変化点は、あるビート位置から開始して BPM が特定の値になり、次の変化点までアクティブなままであることを示します。 BPM は 1 ビートにかかる時間を決定するため、ビートの各セグメントはビート位置と時間の間の線形関数に対応します。 

システムは 2 種類のクエリに応答する必要があります。 1 つのクエリでビート位置をリアルタイムに変換し、区分的線形関数を効果的に評価します。 もう 1 つのクエリは、リアルタイムをビート位置に変換します。これには、同じ区分的線形関数を逆変換する必要があります。 

主な困難は入力のサイズにあります。 最大 500,000 の BPM セグメントと 500,000 のクエリが存在する可能性があるため、セグメントを線形にスキャンして各クエリを処理するソリューションは失敗します。 クエリごとの対数アプローチであっても、事前計算された構造を中心に慎重に設計する必要があります。そうしないと、多くのセグメントにわたる浮動小数点変換が遅くなりすぎます。 

微妙な問題は、変換の両方向でセグメントの境界を正確に尊重する必要があることです。 ビート クエリがセグメント内に到達した場合は、誤って次のインターバルに移行しないように、そのセグメントの一定の BPM のみを使用して評価する必要があります。 同様に、時間をビートに変換し直す場合、正しいセグメントはビート インデックスではなく累積時間によって決定されます。 

一般的な失敗例は、ソリューションがビートとタイムのプレフィックス合計のみを事前計算し、反転のサポートを忘れた場合に発生します。 たとえば、BPM 120 の 1 つのセグメントを除いてすべての BPM が 60 の場合、総継続時間の比例スケーリングを使用した単純な逆変換では、より速いセグメントでは時間の蓄積が遅くなるため、クエリが誤ってより速いセグメントに配置されます。 

## アプローチ

 ブルートフォース解釈は簡単です。 拍と時間のクエリに答えるために、どの BPM セグメントにその拍が含まれているかを特定し、それより前のすべてのセグメントからの寄与を合計し、最後に現在のセグメント内の部分的な寄与を追加します。 time-to-beat クエリの場合は、時間をかけてシミュレーションし、ターゲット時間を通過するまでセグメント期間を累積してから、そのセグメント内の端数位置を計算します。 

これは、各セグメントが線形で独立しているため機能しますが、各クエリですべてのセグメントをスキャンする必要があるため、速度が非常に遅くなります。 n と q が 500,000 までの場合、最悪の場合は 10^11 の演算程度になり、これは実行不可能です。 

重要な観察は、両方の変換が単一の単調区分線形関数に基づいているということです。 ビート位置は、厳密に増加し続ける関数を通じて時間にマッピングされます。 各セグメントは、60 / BPM によって決定される直線的な傾きに影響します。 両方のドメインで累積ブレークポイントを事前計算すると、両方向をセグメント境界を越える二分探索問題に変換できます。 

具体的には、2 つの配列を構築します。 1 つはセグメント開始の拍位置を保存し、もう 1 つはそれらの開始における対応する累積時間値を保存します。 各セグメントの傾きは一定であるため、セグメント内の時間は O(1) で計算できます。 これにより、セグメントを見つけた後の拍と時間の関係が簡単になります。 ビートまでの時間を計算するには、時間プレフィックス配列を二分検索してセグメントを見つけ、その中の線形関数を反転します。 

この変換により、両方のクエリ タイプが O(log n) に減少し、二分検索が大半を占めます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ブルートフォース | O(nq) | お(1) | 遅すぎる |
 | 最適 | O(n + q log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

チャートをセグメントの集合として扱います。各セグメントは既知のビート位置で始まり、次のブレークポイントまで一定の BPM を持ちます。 

1. すべてのセグメントの開始位置と BPM 値を読み取ります。 これらはビート空間の間隔を定義します。 各間隔は、拍から秒への一定の変換率に関連付けられています。 
2. セグメントにわたるプレフィックス構造を事前計算します。 各セグメント i について、その開始までに経過した秒数を計算します。 これは蓄積することによって行われます`(s[i+1] - s[i]) * (60 / b[i])`。 これにより、セグメント インデックスから時間ごとに厳密に増加するマッピングが作成されます。 
3. 2 つの配列を構築します。1 つはビート境界用、もう 1 つは対応する時間境界用です。 これらの配列は、2 つの座標系で同じ区分線形関数を定義します。 
4. Beat-to-Time クエリの場合、最大セグメントの開始部分をバイナリ検索します。`s[i]`そのような`s[i] ≤ x`。 位置が特定されたら、次のように時間を計算します。`t[i] + (x - s[i]) * (60 / b[i])`。 
5. タイムトゥビートクエリの場合、次のような時間配列内の最大セグメント開始部分をバイナリ検索します。`t[i] ≤ x`。 次に、次を使用してセグメント内で反転します。`s[i] + (x - t[i]) * (b[i] / 60)`。 
6. 十分な精度の浮動小数点演算を使用して結果を出力します。 

正確さは、両方のマッピングが各セグメント内で厳密に増加し、線形であるため、反転が誤ってセグメント境界を越えることがないという事実に依存します。 

### なぜ効果があるのか

 各セグメントは、ビート空間と時間空間の間の正の傾きを持つ線形変換を定義します。 すべての傾きが正であるため、グローバル関数は厳密に増加しており、したがって反転可能です。 プレフィックス配列には、この単調関数の正確な境界値が格納されます。 単調性によって一意の有効な間隔が保証されるため、二分検索ではクエリを含むセグメントが正確に識別されます。 セグメント内では、その区間内では変換が変化しないため、線形補間は正確です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def find_segment(arr, x):
    # largest i such that arr[i] <= x
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] <= x:
            lo = mid + 1
        else:
            hi = mid - 1
    return hi

def solve():
    n = int(input())
    s = []
    b = []
    
    for _ in range(n):
        si, bi = input().split()
        s.append(int(si))
        b.append(int(bi))
    
    # compute time at segment starts
    t = [0.0] * n
    
    for i in range(n - 1):
        length_beats = s[i + 1] - s[i]
        t[i + 1] = t[i] + length_beats * 60.0 / b[i]
    
    q = int(input())
    
    for _ in range(q):
        parts = input().split()
        typ = parts[0]
        x = float(parts[1])
        
        if typ == 'B':
            i = find_segment(s, x)
            ans = t[i] + (x - s[i]) * 60.0 / b[i]
            print(f"{ans:.12f}")
        else:
            i = find_segment(t, x)
            ans = s[i] + (x - t[i]) * b[i] / 60.0
            print(f"{ans:.12f}")

if __name__ == "__main__":
    solve()
```このコードは、まずすべてのセグメント境界を読み取り、各セグメント開始時の時刻のプレフィックス配列を構築します。 この接頭辞の構築は、区分的定義を直接クエリ可能な構造に変える重要な前処理ステップです。 

の`find_segment`関数は二分探索を実行して正しい間隔を見つけます。 境界がクエリより大きくない最後のインデックスを常に返します。これにより、ビート ドメインとタイム ドメインの両方で正しいセグメントが選択されます。 

ビートクエリの場合、ビート境界配列を使用します。`s`をクリックしてセグメントを特定し、ローカル線形公式を適用します。 時間クエリの場合も同じことを行いますが、時間プレフィックス配列を使用します。`t`。 両方の操作の対称性により、ソリューションがクリーンになり、反転のための個別のデータ構造が回避されます。 

浮動小数点演算には注意が必要です。 すべての中間値は倍精度で保持され、最終出力では 1e-6 許容差を満たすのに十分な小数点以下の桁数が使用されます。 

## 実用的な例

 2 つのセグメントを持つ単純なチャートを考えてみましょう。ビートは BPM 120 の 0 から始まり、ビート 100 で BPM 60 になります。これは、最初のセグメントの方が速く、時間の蓄積がより遅いことを意味します。 

| ステップ | クエリ | セグメント | 計算 | 結果 |
 | --- | --- | --- | --- | --- |
 | 1 | B50 | 0 | 50 * 0.5 | 25 |
 | 2 | B120 | 1 | 100 * 0.5 + 20 * 1 | 70 |

 トレースは、最初のセグメントが 1 ビートあたり 60/120 = 0.5 秒を使用するのに対し、2 番目のセグメントは 1 ビートあたり 1 秒を使用する様子を示しています。 プレフィックス構造により、コントリビューションが正しく分離されることが保証されます。 

次に、同じ構造に対する逆クエリを考えてみましょう。 

| ステップ | クエリ | セグメント | 計算 | 結果 |
 | --- | --- | --- | --- | --- |
 | 1 | S25 | 0 | 25*2 | 50 |
 | 2 | S70 | 1 | 100 + (70 - 50) * 1 | 120 |

 これにより、反転によって元のビート位置が正しく再構築されることが確認されます。

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n = int(input())
    s = []
    b = []
    for _ in range(n):
        si, bi = input().split()
        s.append(int(si))
        b.append(int(bi))

    t = [0.0] * n
    for i in range(n - 1):
        t[i + 1] = t[i] + (s[i + 1] - s[i]) * 60.0 / b[i]

    def find(arr, x):
        lo, hi = 0, len(arr) - 1
        while lo <= hi:
            mid = (lo + hi) // 2
            if arr[mid] <= x:
                lo = mid + 1
            else:
                hi = mid - 1
        return hi

    q = int(input())
    out = []
    for _ in range(q):
        typ, xs = input().split()

            i = find(t, x)
            out.append(str(s[i] + (x - t[i]) * b[i] / 60.0))

    return "\n".join(out)

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、クエリがセグメント境界に正確に到達する場合です。 セグメントの開始は包括的に定義されるため、両方の配列で一貫して等価性を扱う必要があります。 たとえば、セグメントがビート 100 で始まる場合、クエリ B 100 は前のセグメントではなく、そのセグメントに属している必要があります。 二分検索の実装は、値 ≤ x の最後のインデックスを返し、このルールが直接適用されます。 

もう 1 つのケースは、単一セグメントのチャートです。 ここでは遷移がないため、プレフィックス構築ではアクセスを回避する必要があります。`s[i+1]`。 実装では、時刻プレフィックスを構築するときに最大 n-1 まで反復するだけでこれを処理します。 

最後に、プレフィックス時間と正確に等しい反転クエリは、正しいセグメント開始にマップする必要があります。 時間配列は厳密に増加しているため、二分探索では再び曖昧さのない正しい境界が選択され、順方向マッピングと逆方向マッピングの間の一貫性が維持されます。
