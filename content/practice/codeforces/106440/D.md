 ## 問題の理解

 一連のコンテナーが与えられ、各コンテナーには基本サイズと容量があります。 面白いのは、コンテナをネストできることですが、厳密なルールがあります。コンテナは他のコンテナを最大 1 つまで直接保持でき、内部コンテナの有効サイズがその容量を超えない場合にのみ保持できます。 コンテナーが別のコンテナーを保持すると、そのコンテナー自体の有効サイズが、そのコンテナーに含まれるものの有効サイズ全体だけ増加し、これがネストのチェーンを通じて上方に伝播します。 

任意のクエリ間隔に対して$[L, R]$、それらのコンテナのみに限定します。 すべてが 1 つの最も外側のコンテナ内に収まるように、それらすべてを 1 つのネスト チェーンに配置できるかどうかを知りたいと考えています。 不可能な場合は、間隔内のすべての容量を同じ値で均一に増やすことができます。$x$、そしてそのような最小値を見つけなければなりません$x$これにより、有効な完全なネストが可能になります。 

重要なオブジェクトは生のサイズだけではありません$a_i$ただし、チェーンの「負荷」が誘発されます。各コンテナーは独自のサイズに加えて、その中にあるすべてのものに影響を与えるため、順序が重要です。 

制約は大きく、最大で$2 \cdot 10^5$要素とクエリ全体。 これにより、クエリごとにすべての置換を試行したり、最初から貪欲にネストをシミュレートしたりするソリューションは即座に除外されます。$O(n)$クエリごとに。 平$O(n \log n)$最悪の場合、クエリごとの処理が遅すぎるため、$q$も大きいです。 

容量がぎりぎり不足しているにもかかわらず、容量が不均等に分散されている場合、微妙なエッジケースが発生します。 たとえば、大容量のコンテナーは、そのサイズのためにチェーンの奥深くに配置され、容量が無駄になる可能性があります。 グローバルな制約を持たずに、常に最小値を最初に配置するか、最大値を最初に配置する単純な貪欲型は失敗する可能性があります。 

必要な場合には、別の特殊なケースが発生します。$x$均一な不足ではなく、チェーン内の単一の厳しいボトルネックによって決まります。 たとえば、ほとんどの容量がすでに機能している構成ですが、1 つの特定のプレフィックス合計違反によりゼロ以外の増加が強制され、そのプレフィックス構造が欠けていると不正確な応答が発生します。 

## アプローチ

 ブルート フォース ビューでは、すべてのコンテナが$[L, R]$単一のチェーンに配置する必要があります。 順序を修正すると、最も内側から外側に向かって結果の有効サイズを計算し、各コンテナが蓄積された内部構造を保持できるかどうかを確認できます。 これは簡単です。並べ替えまたは並べ替え、最も深いコンテナから外側に向かってシミュレートし、制約を検証します。 

これが機能するのは、一度注文が決まれば、実現可能性を直線的に確認できるためです。 問題は、$(R-L+1)!$可能な注文ですが、非常に短い間隔であっても実行不可能です。 

構造的な洞察は、入れ子構造の最終的な有効サイズは常にすべてのサイズの合計であるということです。$a_i$、順序に関係なく。 異なるのは、チェーン構築の各ステップでどれだけの「空き容量スラック」が利用できるかです。 逆に考えると、最も内側のコンテナから外側に向かって、各ステップでは、現在の累積サイズが次のコンテナの容量を超えないことが必要になります。 したがって、私たちは増加するサフィックス合計をサポートできるように容量を効率的に調整しようとしています。 

これにより、問題はスケジューリングのような条件に集約されます。つまり、各ステップで既知の累計に対して容量制約が満たされるようにコンテナを注文する必要があります。 最適な配置は、サイズの寄与に対する容量の制約によって並べ替えてから、プレフィックスの実現可能性条件をチェックすることであることがわかります。

 ## アルゴリズムのチュートリアル

 単一のクエリ間隔に焦点を当てます$[L, R]$、関連するペアを抽出します$(a_i, b_i)$。 

1. 要素を昇順に並べ替えます。$b_i$。 

この順序により、より厳しい容量制約を持つコンテナーが実現可能性構築の早い段階で考慮されるようになります。 
2. 実行中のサフィックス スタイルの累積を計算しますが、このソート順でプレフィックスとして実装されます。 

させて`need`すでに配置されている内部コンテナの現在の累積有効サイズを表します。 初期化する`need = 0`。 
3. ソートされた順序でコンテナを走査します。 コンテナごとに$(a, b)$、次の外側のレイヤーとして扱います。 

まず、すでに中にあるものを含めることができるかどうかを確認します。それには、次のことが必要です。$need \le b$。 これが失敗すると、現在の順序付けは実行できなくなります。 
4. 可能な場合は更新します`need += a`。 

これは、このコンテナが内部構造を包み込むと、その寄与により合計の有効サイズが増加することを反映しています。 
5. すべての要素を処理した後、違反が発生しなければ実現可能となります。 

「すべての容量を増やす」をサポートするには、$x$” クエリでは、変更される唯一の条件が次のとおりであることがわかります。$need \le b_i + x$。 固定順序の場合、各ステップで赤字を定義します。$need - b_i$。 すべてのステップにわたる最大のプラスの赤字は、まさに最小値です$x$必須。 

したがって、並べ替え後、次のように計算します。$$x = \max(0, \max_i (need_i - b_i))$$どこ$need_i$コンテナを使用する前の累積サイズです$i$。 

### なぜ効果があるのか

 容量順に並べ替えることにより、実行可能なソリューションを、実行可能性を損なうことなく、コンテナの容量が減少しないとみなされるソリューションに確実に変換できます。これは、2 つの隣接するコンテナを交換するためです。$b_i \le b_j$事前に制約を厳しくすることはできません。 ランニングサム構造は正確なネスト負荷伝播を捕捉し、すべての違反は順序付けのアーティファクトではなく、有効なチェーン内の実際のボトルネックに対応します。 最大不足は、容量が必要な累積サイズを下回る最も厳しい点を捉えており、その量だけすべての容量を増やすと、すべての違反が同時に解消されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_query(arr):
    arr.sort(key=lambda x: x[1])  # sort by capacity b
    
    need = 0
    max_deficit = 0
    
    for a, b in arr:
        if need > b:
            max_deficit = max(max_deficit, need - b)
        need += a
    
    return max_deficit

def can_fit(arr):
    arr.sort(key=lambda x: x[1])
    need = 0
    for a, b in arr:
        if need > b:
            return False
        need += a
    return True

def main():
    t = int(input())
    out = []
    
    for _ in range(t):
        n, q = map(int, input().split())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))
        
        items = list(zip(a, b))
        
        for _ in range(q):
            l, r = map(int, input().split())
            l -= 1
            
            seg = items[l:r]
            
            if can_fit(seg):
                out.append("Yes")
            else:
                x = solve_query(seg)
                out.append("No")
                out.append(str(x))
    
    print("\n".join(out))

if __name__ == "__main__":
    main()
```このソリューションは、クエリ セグメントごとにペアのリストを作成し、容量ごとに並べ替えた後、貪欲な実行可能性チェックを適用します。 機能`can_fit`変更せずにネストが可能かどうかを検証します。`solve_query`すべてのステップにわたる最大不足分を計算し、これにより必要な最小均一容量増加が直接得られます。 

微妙な点は、両方の関数が同一の並べ替えロジックに依存していることです。 赤字の計算は、実現可能性のために使用されるまったく同じ順序と比較してのみ意味をなすため、これは不可欠です。 もう 1 つの重要な詳細は、蓄積された`need`容量を確認すると増加します。これは正しいネスト方向を反映しています。内部構造が最初に固定され、次に外側に巻き付けられます。

 ## 特殊なケース

 重要なエッジ ケースは、すべての容量が等しいにもかかわらず、サイズがその値をわずかに超えて蓄積される場合です。 のような入力の場合$a = [2,2,2]$、$b = [3,3,3]$、ソート順序は重要ではありませんが、プレフィックスの累積は次のようになります。$2,4,6$。 最初の違反はステップ 2 で赤字で発生します。$1$、正しく生成されます$x = 1$。 アルゴリズムは、最大値を追跡するため、これを処理します。$need - b$最終ステップだけでなく、すべてのステップにわたって。 

もう 1 つのケースは、単一の大きなアイテムが容量順にソートされた順序の最初に表示される場合です。 例えば$a = [10,1,1]$、$b = [10,1,1]$。 容量別に並べ替えると、容量の小さいアイテムが最初に来るようになり、大きいアイテムの前に小さいアイテムが強制的に蓄積されます。 これは直観に反しているように思えるかもしれませんが、これにより、必要なスラックを過小評価することがなくなります。 違反があればすぐに捕捉されるため、アルゴリズムは引き続き機能します。`need`小さいものを超える$b$、そして結果として生じる赤字は最終的な答えに正しく伝播します。 

3 番目のエッジケースは、複数の点で実現可能性がほとんど損なわれていない場合です。 アルゴリズムは依然として正しい値を返します$x$なぜなら最大赤字だけが重要だからです。 単一の均一な増加によりすべての制約が同時に修正されるため、より小さな不足については個別に処理する必要はありません。
