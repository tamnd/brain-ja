 ## 解決策
 ## 問題の理解

 1 から n までの値を持つコインのセットが与えられ、各値は 1 回だけ出現するため、実際には 1 から n までの整数のサブセットを選択していることになります。 目標は、合計が正確に m になるサブセットを選択することです。 

ただし、選択は追加のプレフィックス ルールによって制限されます。 すべての i に対して、制限 a_i が与えられます。これは、選択されたすべてのコインのうち、最大 i の価値を持つコインのうち、最大で a_i を選択できることを意味します。 言い換えれば、選択したセットを調べて、それをプレフィックス [1, i] の値に制限する場合、そのサイズは a_i を超えてはなりません。 

このようなサブセットを構築するか、有効なサブセットが存在しないと判断する必要があります。 

制約は大きく、テスト全体で n が最大 10^6 であるため、テスト ケースごとに O(n log n) を超える二次関数または線形の解は失敗します。 これにより、合計や部分集合に対するナップザック スタイルの動的プログラミングが即座に排除されます。 O(n sqrt n) の構築でも、このスケールでは遅すぎます。 ソリューションは、効率的な実現可能性チェックを備えた貪欲な構築に依存する必要があります。 

プレフィックス制約をグローバルに無視して貪欲な推論を適用すると、微妙な失敗例が発生します。 たとえば、合計の実現可能性のみに基づいて最初に大きなコインを選択しようとすると、たとえ最終的な合計が達成可能に見えたとしても、初期の厳しいプレフィックス制限を破ってしまう可能性があります。 もう 1 つの失敗モードは、同じコインが将来のすべてのプレフィックスに影響を与えることを考慮せずに、位置 i でローカルに有効なコインを選択することです。これにより、後で暗黙的に制約に違反する可能性があります。 

たとえば、n = 5 と仮定し、合計 5 にすぐに到達するのに役立つためコイン 5 を早めに選択しますが、a_5 は 0 です。その場合、[1,5] 内の単一の選択さえも無効になります。 プレフィックスの実現可能性を無視した素朴な貪欲なアプローチはすぐに失敗します。 

中心となる問題は、選択されたすべてのコインが将来のすべてのプレフィックス制約に同時に影響を与えるため、実現可能性はローカルな特性ではなくグローバルな特性であることです。 

## アプローチ

 ブルート フォース ソリューションでは、{1, 2, ..., n} のすべてのサブセットを列挙し、それらの合計を計算し、各サブセットのプレフィックス制約をチェックします。 これは正しいですが、2^n 個のサブセットがあり、n = 40 の場合でもすでに大きすぎるため、実行不可能ですが、ここでは n が 10^6 に達します。 

より構造化されたベースラインは、合計 m に対する 0/1 ナップザック動的計画法です。ここで、 dp[s] は、制約を尊重しながら合計 s に到達できるかどうかを示します。 m が n(n+1)/2 に達する可能性があり、時間とメモリの両方が法外な量になるため、これはすぐに失敗します。 

重要な観察は、価値が固定され厳密に増加しているため、より大きなコインは常に総額ではより「高価」ですが、数は少ないということです。 これは、大きな値から下に向かう貪欲な構築を示唆しています。 ただし、プレフィックス制約はすべての決定に関係します。コイン i を選択すると、すべての j ≥ i のプレフィックス数が増加するため、どのプレフィックスもその境界 a_j を超えないようにする必要があります。 

これにより、問題は動的な実現可能性プロセスに変換され、各選択は将来のすべてのプレフィックスの範囲更新となり、すべてのプレフィックス容量が負でないことを継続的に維持する必要があります。 この構造はまさに、遅延伝播を備えたセグメント ツリーが得意とするものです。すべてのプレフィックスで残りの容量スラックを追跡し、それがゼロを下回らないようにします。 

次に、最初に大きなコインを取得しようと貪欲に試みますが、それは、そうすることでシステムの実行可能性が維持され、必要な合計 m をオーバーシュートしない場合に限ります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース サブセット | O(2^n · n) | O(n) | 遅すぎる |
 | 合計の DP | O(nm) | O(m) | 遅すぎる |
 | 貪欲 + セグメント ツリー | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

インデックス 1 から n までのセグメント ツリーを維持します。 位置 i では、ツリーはプレフィックス [1, i] で既に選択したコインの数を格納し、制約をスラック値 a_i - selected_prefix[i] に変換します。 私たちが維持する不変条件は、すべてのスラックが常に非負でなければならないということです。 

また、選択したコインの現在の合計額と未処理のコインの残りの合計額も維持します。 

1. 各位置 i に a_i に等しい初期スラックを格納するセグメント ツリーを初期化します。 また、current_sum を 0 に設定し、total_remaining_sum を n(n+1)/2 に設定します。 これにより、選択が行われる前に全容量が得られます。 
2. i を n から 1 まで繰り返し、コイン i を含めるかどうかを決定します。 アイテムあたりの合計額に大きく寄与するため、私たちは常に大きなコインを最初に検討します。 
3. i を含める前に、current_sum + i が m を超えているかどうかを確認してください。 そうなった場合、目標合計をオーバーシュートして後で回復することはできないため、i をすぐにスキップします。 
4. i を含めようとすると、i を選択するとすべてのプレフィックス j ≥ i のカウントが増加するため、セグメント [i, n] に範囲更新を適用してスラックを 1 減らします。 
5. 更新後、セグメント ツリーの最小スラックをクエリします。 最小スラックが負になった場合、この選択は何らかのプレフィックス制約に違反するため、更新をロールバックして i を破棄します。 
6. 更新が有効な場合、i を応答セットに永続的に保持し、i を追加して current_sum を更新します。 
7. すべての値を処理した後、current_sum が m に等しいかどうかを確認します。 存在する場合は、選択したセットを出力します。 それ以外の場合は、有効な構造が存在しません。 

これが機能する理由は、グローバルな影響を考慮した後、プレフィックス システム全体が実行可能である場合にのみコインを受け入れるためです。 セグメント ツリーはグローバルな実現可能性条件を強制しますが、貪欲な順序付けにより、不必要な小さな選択を行わずに効率的に m に到達するために、より大きな寄与を優先することが保証されます。 

不変条件は、各コインが受け入れられた後も、すべてのプレフィックス制約が満たされたままであり、スラック配列が残りの容量を正しく反映していることです。 拒否されたコインはすべて、即時の実行可能性違反または合計オーバーシュートによってのみ拒否されるため、有効な解が失われることはなく、単調な実行可能性に違反することなく後で修復できる可能性があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, n, arr):
        self.n = n
        self.minv = [0] * (4 * n)
        self.lazy = [0] * (4 * n)
        self.build(1, 1, n, arr)

    def build(self, idx, l, r, arr):
        if l == r:
            self.minv[idx] = arr[l]
            return
        mid = (l + r) // 2
        self.build(idx * 2, l, mid, arr)
        self.build(idx * 2 + 1, mid + 1, r, arr)
        self.minv[idx] = min(self.minv[idx * 2], self.minv[idx * 2 + 1])

    def push(self, idx):
        if self.lazy[idx] != 0:
            for child in (idx * 2, idx * 2 + 1):
                self.minv[child] += self.lazy[idx]
                self.lazy[child] += self.lazy[idx]
            self.lazy[idx] = 0

    def update(self, idx, l, r, ql, qr, val):
        if ql <= l and r <= qr:
            self.minv[idx] += val
            self.lazy[idx] += val
            return
        self.push(idx)
        mid = (l + r) // 2
        if ql <= mid:
            self.update(idx * 2, l, mid, ql, qr, val)
        if qr > mid:
            self.update(idx * 2 + 1, mid + 1, r, ql, qr, val)
        self.minv[idx] = min(self.minv[idx * 2], self.minv[idx * 2 + 1])

    def query_min(self):
        return self.minv[1]

def solve():
    n, m = map(int, input().split())
    a = [0] + list(map(int, input().split()))

    total = n * (n + 1) // 2
    if m > total:
        print(-1)
        return

    seg = SegTree(n, a)
    res = []
    cur = 0

    for i in range(n, 0, -1):
        if cur + i > m:
            continue

        seg.update(1, 1, n, i, n, -1)
        if seg.query_min() < 0:
            seg.update(1, 1, n, i, n, 1)
            continue

        res.append(i)
        cur += i

    if cur != m:
        print(-1)
        return

    res.sort()
    print(len(res))
    print(*res)

if __name__ == "__main__":
    solve()
```セグメント ツリーは、プレフィックス制約の下で実現可能性の条件を維持するためにのみ使用されます。 コイン i を暫定的に選択するたびに、i を含むすべての接頭辞から 1 単位のスラックを減算します。 これにより負の最小値が発生した場合は、直ちに操作を元に戻し、実行不可能な部分的な解決策に決してコミットしないようにします。 

プレフィックス制約は合計とは直接影響せず、選択されたインデックスの構造とのみ影響するため、合計の追跡は実現可能性とは切り離されています。 

セットを降順で構築するため、最後の並べ替えステップは純粋に出力形式のためのものです。

## 複雑さの分析

 ## 特殊なケース

 初期のインデックスでプレフィックス制約が非常に小さい場合、タイトなケースが発生します。 たとえば、n = 5、a = [0、1、1、1、5]。 コイン 1 を含めようとすると、a_1 = 0 であるため、直ちに解は不可能になります。アルゴリズムは、コイン 1 にコミットする前にセグメント ツリーを更新することでこれを処理します。 最小スラックが負になり、即時ロールバックがトリガーされます。 

別のケースは、合計 m に大きなコインが必要であるが、それらを含めると累積的な影響により初期のプレフィックス容量を侵害する場合です。 たとえば、a_3 が小さい場合、コイン 5 と 4 は、合計が最適であっても選択できない可能性があります。 セグメント ツリーは、影響を受けるすべてのプレフィックスに影響を伝播することでこれを保証します。 

最後のケースは、m が全和 n(n+1)/2 に等しい場合です。 アルゴリズムはすべてのコインを取得しようとしますが、すべてのプレフィックス制約が ID a_i = i と一致する場合にのみ成功します。 最初の違反中にスラックが負になると、より厳しい制約が検出され、誤った完全選択が防止されます。
