 ## 解決策
 ## 問題の理解

 ルート化されたバージョン ツリーが与えられます。 バージョン 1 がルートです。 以前のバージョンでは、他のすべてのバージョンには 1 つの親があり、親から子へのエッジには文字が含まれます。 ルートからノードへのパスに沿った文字シーケンスは、バージョンの「署名文字列」を定義します。 

各ノードの文字列は、ルートからそのノードまで下に移動し、エッジ文字を順番に連結することによって取得されます。 タスクは、これらの文字列によってすべてのノードを辞書編集順に並べ替えることです。2 つのノードが同じ文字列を生成する場合、インデックスが小さいノードが最初に来るという追加のルールが適用されます。 

重要な問題は、これらの文字列が明示的に指定されていないことです。 各文字列はツリー内のパスによって暗黙的に定義されるため、単純にすべての文字列を構築するとノードごとの深さが線形になり、ツリーがチェーンの場合は 2 次の合計作業量に低下する可能性があります。 

この制約により、テストごとに最大 100,000 ノードが許可され、すべてのテストの合計サイズも 100,000 で制限されます。 これにより、完全な文字列を具体化するアプローチや、最悪の場合に上方に繰り返し歩くことによってノードを比較するアプローチは即座に排除されます。 n log n 回程度の比較を行うソリューションもまだ許容されますが、各比較は効率的であり、理想的には対数または定数償却される必要があります。 

2 つのノードがまったく同じルート パス文字列を共有する場合、微妙なエッジ ケースが発生します。 これは、ツリーの異なる部分にある同一のラベル付きパスを介して異なるノードに到達した場合に発生する可能性があります。 この場合、辞書編集的な比較だけでは不十分であり、指数によるタイブレークが決定的となります。 文字列を比較するだけで安定した順序付けを強制しないアプローチは、このシナリオでは失敗します。 

## アプローチ

 直接的なアイデアは、すべてのノードの文字列を明示的に構築し、それらを並べ替えることです。 各ノードは明確に定義されたパス文字列に対応するため、これは概念的には正しいです。 ただし、各文字列の構築にはその深さに比例して時間がかかります。 チェーン形状のツリーでは、深さは n に達する可能性があり、合計は 1 + 2 + ... + n (つまり 2 次) になります。 これらの明示的な文字列を並べ替えると、さらに n log n 係数が上に追加されるため、このアプローチは使用できなくなります。 

重要な点は、完全な文字列は必要なく、2 つのルートからノードへの文字列を辞書編集的に比較する機能のみが必要であるということです。 これは、ツリーを暗黙的なトライとして扱うことを示唆しています。 各ノードは文字列を表し、各エッジに 1 つの文字が追加されます。 ルートから最初に異なる位置を見つけて 2 つの文字列を比較したいと考えています。 

対数ステップでルート パスに沿ってジャンプし、プレフィックスを効率的に比較できれば、2 つのルート パス間で最も長い共通プレフィックスの長さを二分探索できます。 その長さが判明したら、両側の次の文字によって順序が決まります。 

これをサポートするために、バイナリ リフティングを使用して O(log n) 時間でツリーを上に移動し、各ルートからノードへのパスのローリング ハッシュも維持します。 これにより、クエリ ステップごとに O(log n) 回の前処理を行った後、同じ深さの 2 つのプレフィックスが O(1) 時間で同一であるかどうかを確認できます。 次に、これをプレフィックス長の二分検索と組み合わせます。各チェックでは祖先のリフティングとハッシュが使用されます。 各比較は O(log² n)、並べ替えは O(n log² n) となり、制約には十分です。

 | ブルート フォース (明示的な文字列) | O(n²) 最悪の場合 | O(n²) | 遅すぎる |
 | LCA + バイナリリフティング + ハッシュ比較ソート | O(n log² n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべてのノードを 2^k 番目の祖先までリフトできるようにツリーを前処理し、ノードから親にステップ移動するときにエッジ上の文字を回復するのに十分な情報も保存します。

また、各ノードのルート パス文字列のローリング ハッシュも計算します。 ノード v に親 p とエッジ文字 c がある場合、そのハッシュは親のハッシュを c で拡張するものとして定義します。 

前処理の後、ルート文字列を比較するカスタム コンパレーターを使用してノードを並べ替えます。 

1. 2 つのノード u と v について、まずそれらの深さを比較します。 より深い場合は、辞書編集的に必ずしも大きいとは限らないため、深さだけでは十分ではありませんが、比較範囲を制限します。 
2. ルートからノードまでの文字列の最長の共通プレフィックスの長さを計算します。 この長さを 0 から min(深さ(u), 深さ(v)) の範囲で二分探索します。 候補の長さが k の場合、u と v からそれらの k 番目の先祖にジャンプし、それらのプレフィックス エンドポイントのハッシュを比較します。 
3. LCP 長さ L が見つかったら、u と v を深さ L+1 までリフトすることにより、各パス上の (L+1) 番目のノードを識別します。 これらのノードの入力エッジの文字によって、文字列内の次のシンボルが決まります。 
4. 文字が異なる場合、それによって順序が直接決まります。 それらが同一の場合、LCP 検索を通じて暗黙的に比較ロジックを続行しますが、実際には、このケースは文字列が同一である場合にのみ発生します。 
5. 文字列全体が同一の場合は、ノード インデックスの比較に戻り、決定的な順序付けを保証します。 

### なぜ効果があるのか

 このアルゴリズムは、辞書編集的な比較を、2 つのルートからノードへのパスが分岐する最初の位置を見つけることに簡素化します。 バイナリ リフティングにより、対数時間内に任意のプレフィックス エンドポイントに到達できることが保証され、ハッシュにより、プレフィックスの等価性を効率的にチェックできることが保証されます。 二分検索では正確な分岐点が分離されるため、文字列自体を構築することなく、すべての比較で標準の辞書編集文字列比較が忠実にシミュレートされます。 ソートは一貫したコンパレータのみに依存するため、最終的な順序は必要な辞書編集順序と一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

B = 91138233
MOD = (1 << 61) - 1

def modmul(a, b):
    return (a * b) % MOD

def add(a, b):
    s = a + b
    return s % MOD

def solve():
    n = int(input())
    parent = [0] * (n + 1)
    ch = [0] * (n + 1)
    g = [[] for _ in range(n + 1)]

    for i in range(2, n + 1):
        x, c = input().split()
        x = int(x)
        parent[i] = x
        ch[i] = ord(c) - ord('a') + 1
        g[x].append(i)

    LOG = (n).bit_length()

    up = [[0] * (n + 1) for _ in range(LOG)]
    depth = [0] * (n + 1)
    h = [0] * (n + 1)

    up[0][1] = 0
    depth[1] = 0
    h[1] = 0

    order = [1]
    for v in order:
        for to in g[v]:
            depth[to] = depth[v] + 1
            up[0][to] = v
            h[to] = (h[v] * B + ch[to]) % MOD
            order.append(to)

    for j in range(1, LOG):
        for i in range(1, n + 1):
            up[j][i] = up[j - 1][up[j - 1][i]]

    def lift(u, k):
        for j in range(LOG):
            if k & (1 << j):
                u = up[j][u]
        return u

    def get_kth_node(u, k):
        return lift(u, depth[u] - k)

    def cmp(u, v):
        if u == v:
            return 0
        lo, hi = 0, min(depth[u], depth[v])

        while lo < hi:
            mid = (lo + hi + 1) // 2
            if lift(u, depth[u] - mid) == lift(v, depth[v] - mid):
                lo = mid
            else:
                hi = mid - 1

        lcp = lo
        if lcp == min(depth[u], depth[v]):
            if depth[u] != depth[v]:
                return -1 if depth[u] < depth[v] else 1
            return u - v

        u_node = lift(u, depth[u] - (lcp + 1))
        v_node = lift(v, depth[v] - (lcp + 1))

        cu = ch[u_node]
        cv = ch[v_node]
        if cu != cv:
            return -1 if cu < cv else 1
        return u - v

    from functools import cmp_to_key
    nodes = list(range(1, n + 1))
    nodes.sort(key=cmp_to_key(cmp))

    print(*nodes)

if __name__ == "__main__":
    t = int(input())
    for _ in range(t):
        solve()
```コア実装はバイナリ リフティング テーブルを構築するため、対数時間で任意の祖先に到達できます。 次に、コンパレータは、2 つのノード間の最初の異なる深さを特定することにより、辞書編集的な比較を動的に再構築します。 唯一の微妙な部分は、明示的な文字列を保存することがないため、各エンドポイントからの繰り返しリフティングによって「プレフィックス長」をノードに慎重に変換することです。 

最終的なソートは完全にこのコンパレータに依存するため、正確性はコンパレータが一貫性と推移的であるかどうかにかかっています。これは、決定論的な文字列セット上の真の辞書編集順序を反映しているため保証されます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、あるノードの文字列が別のノードのプレフィックスである場合です。 たとえば、「ab」を表すノードと「aba」を表す別のノードが考えられます。 この状況では、コンパレータはプレフィックスが完全に等しいことを確認した後、最初に長さに基づいて決定する必要があります。 LCP のバイナリ検索では完全な短い長さが返され、比較は深さの順序に戻り、短い文字列が最初に配置されるため、アルゴリズムはこれを処理します。 

もう 1 つのエッジ ケースは、異なるノードによって生成される同一の文字列です。これは、2 つのノードがルートからの同一のパス ラベルを持つ場合に発生する可能性があります。 この場合、LCP は両方のノードの完全な深さに等しく、コンパレーターは直ちにインデックス比較を解決して、決定的な順序付けを保証します。 

最後の微妙なケースは、バイナリ リフティングが不可欠な深く歪んだツリーです。 祖先ジャンプがなければ、2 つの深いノードを比較するには、段階的に上に進む必要があり、時間制限を超えてしまいます。 リフティング ステップでは、深さに関係なく、各プレフィックス チェックが対数のままであることが保証されます。
