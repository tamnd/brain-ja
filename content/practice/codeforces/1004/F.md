 ## 解決策
 ## 問題の理解

 時間の経過とともに変化する配列が与えられるので、与えられたセグメント内のサブ配列に関するクエリに繰り返し答える必要があります。 どのセグメントでも$[l, r]$、すべての連続した部分配列を考慮します$[L, R]$その中に完全に含まれています。 このようなサブ配列ごとに、その中のすべての要素のビット単位の OR を計算します。 クエリは、これらのサブ配列のうち、少なくとも固定しきい値である OR 値を生成するものがいくつあるかを尋ねます。$x$、 どこ$x$決して変わりません。 

直接読み取ると、更新中の OR 値に単調条件を持つサブ配列を繰り返しカウントしていることがわかります。 問題は、サブ配列の OR が可逆的な方法で簡単に構成できないことと、更新により構造を動的に維持する必要があることです。 

この制約により、ほぼ線形またはクエリごとの対数的な動作が求められます。 と$n, m \le 10^5$クエリごとにサブ配列情報を再計算したり、単純にセグメントをスキャンしたりするソリューションは生き残れません。 平$O(n \sqrt n)$または$O(n \log n)$クエリごとに繰り返すと大きすぎます$10^5$回。 OR 情報を最初から再計算することを避ける構造が必要です。 

重要なエッジケースが発生するのは次のような場合です$x = 0$。 この場合、すべてのサブ配列は自明に OR を満たします。$\ge 0$したがって、すべてのクエリは、すべてのサブ配列をカウントすることになります。$[l, r]$、つまり$\frac{(r-l+1)(r-l+2)}{2}$。 OR 条件を再計算するアルゴリズムは引き続き機能する可能性がありますが、この退化ケースを過度に複雑にしてはなりません。 

もう 1 つの微妙なケースは、更新により新しいビットで大きな値が導入される場合です。 OR はサブ配列を拡張するときにのみ増加しますが、更新によって以前の構造がローカルで無効になる可能性があるため、静的な前処理アプローチは失敗します。 

最後の重要なエッジ シナリオは、小さなセグメントです。 たとえば、次の場合$l = r$、答えはかどうかによってのみ異なります。$a_l \ge x$したがって、正しさは単一要素推論に優雅に劣化する必要があります。 

## アプローチ

 ブルート フォース ソリューションでは、各クエリが個別に処理されます。 お問い合わせの場合$[l, r]$、その中のすべての部分配列を列挙し、それらの OR を直接計算します。 スタートポジションごとに$L$、延長します$R$OR を段階的に維持します。 OR は次で更新できるため、これは正解です。$O(1)$拡張子ごとに。 ただし、各クエリにはコストがかかります$O((r-l+1)^2)$、そして$10^5$クエリの場合、これは壊滅的に大きくなります。 

重要な観察は、実際にはすべてのサブ配列の正確な OR 値が必要ではなく、それらがしきい値を満たすかどうかだけが必要であるということです。 条件「または」$\ge x$” はビットごとに再フレーム化できます。サブ配列が不良であるのは、サブ配列に設定されている少なくとも 1 つのビットが欠落している場合のみです。$x$。 したがって、必要な部分をすべてカバーすることに重点を置いています。 

OR を直接追跡する代わりに、問題を逆転させます。 サブ配列は、必要なすべてのビットが少なくとも 1 回含まれる場合に適しています。$x$。 同様に、補数の観点から考えることができます: OR が到達しない部分配列$x$必要なビット位置をカバーできないものです。 この構造により、「悪い制約」に対する古典的なスライディング ウィンドウが可能になり、合計から不良サブ配列を差し引いて良好なサブ配列をカウントできます。 

動的側面は、各ノードがそのセグメント上のサブ配列 OR 動作の圧縮表現を維持するセグメント ツリーを使用して処理されます。 各ノードについて、そのセグメント境界を越える部分配列のすべての個別の OR 結果を単調圧縮リストに保存します。 これは「個別のサブ配列 OR の数」に関する標準的なトリックですが、各拡張はビットを追加するだけであり、個別の OR の数は次の制限を受けるため、小さいままです。$O(20)$出発点ごとに。 

各セグメント ツリー ノードについて、以下を維持します。 

セグメントに完全に含まれるサブ配列の可能な OR 結果のリスト、および OR が条件を満たすサブ配列の総数。 マージ中に、左右の子を結合し、圧縮された OR セットを使用して境界を越えた部分配列も計算します。 

これにより、更新が可能になります$O(\log n \cdot 20^2)$とクエリ$O(\log n \cdot 20)$、これで十分です$10^5$操作。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(n^2)$クエリごと |$O(1)$| 遅すぎる |
 | OR 状態にわたる最適なセグメント ツリー |$O((n+m)\log n \cdot 20^2)$|$O(n \log n \cdot 20)$| 承認済み |

 ## アルゴリズムのチュートリアル

 各ノードがその区間内の部分配列 OR の動作を要約するセグメント ツリーを構築します。 

1. 各ノードは、そのセグメントに完全に含まれるサブアレイの達成可能な OR 値を表すペアのリストとその頻度を格納します。 個別の OR 値のみを保持します。 これが可能なのは、OR 値ではビットが増加するだけであり、したがって個別の状態の数が少ないためです。 
2. 単一要素に対応するリーフノードの場合$a[i]$、構造体にはサブ配列が 1 つだけ含まれており、OR は次と等しくなります。$a[i]$。 これがDPの基礎となります。 
3. 内部ノードの場合、左右の子構造をマージします。 まず、すべての部分配列を完全に左または右の子に含めます。 次に、中点を横切る部分配列を処理します。 
4. 交差部分配列を計算するには、左側の子からすべてのサフィックス OR を取得し、右側の子からすべてのプレフィックス OR を取得します。 すべてのサフィックス OR 値について$o_L$とプレフィックス OR 値$o_R$、結合された OR は次のようになります。$o_L \,|\, o_R$。 それに応じてカウントを蓄積します。 OR 状態の数が制限されているため、このマージは効率的に行われます。 
5. 各ノードはさらに、OR が少なくとも次であるセグメント内のサブ配列の総数を格納します。$x$、同じ DP 表現から計算されます。 
6. ポイントの更新によりリーフが変更され、ルートへのパス上の値が再計算されます。 これには対数時間がかかります。 
7. 範囲クエリは、カバーするセグメント ツリー ノードを結合します。$[l, r]$そして、保存されている構造をマージして、有効な部分配列の最終的な数を計算します。 

これが機能する理由: 重要な不変条件は、各ノードがセグメント内のすべてのサブ配列の OR 結果の正確なマルチセットを格納し、同一の OR 結果をマージすることで圧縮されることです。 OR はビットを追加することしかできず、ビット数は最大 20 であるため、セグメントごとの個別の OR 値の数は制限されたままであり、すべてのサブ配列の OR はノードの組み合わせで 1 回だけ表されます。 マージ操作では、サブ配列を子に分割できるすべての方法が列挙されるため、サブ配列が欠落したり二重にカウントされたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXB = 20
MASK = (1 << MAXB) - 1

class Node:
    __slots__ = ("pref", "suff", "all_or", "cnt_good", "total")
    def __init__(self):
        self.pref = []   # list of (or_value, count)
        self.suff = []   # list of (or_value, count)
        self.all_or = [] # list of (or_value, count)
        self.cnt_good = 0
        self.total = 0

def merge_lists(a, b):
    res = {}
    for v, c in a:
        res[v] = res.get(v, 0) + c
    for v, c in b:
        res[v] = res.get(v, 0) + c
    return list(res.items())

def build(a, v, l, r):
    if l == r:
        node = Node()
        val = a[l]
        node.pref = [(val, 1)]
        node.suff = [(val, 1)]
        node.all_or = [(val, 1)]
        node.total = 1
        node.cnt_good = 1 if val >= x else 0
        v[l] = node
        return node

    mid = (l + r) // 2
    L = build(a, v, l, mid)
    R = build(a, v, mid + 1, r)

    node = Node()

    # prefix ORs
    node.pref = L.pref[:]
    for v2, c2 in R.pref:
        nv = v2
        node.pref.append((nv, c2))
    node.pref = merge_lists(node.pref, [])

    # suffix ORs
    node.suff = R.suff[:]
    for v2, c2 in L.suff:
        node.suff.append((v2, c2))
    node.suff = merge_lists(node.suff, [])

    # all ORs (cross combine)
    tmp = L.all_or + R.all_or
    cross = {}
    for lv, lc in L.suff:
        for rv, rc in R.pref:
            ov = lv | rv
            cross[ov] = cross.get(ov, 0) + lc * rc

    node.all_or = merge_lists(tmp, list(cross.items()))

    node.total = sum(c for _, c in node.all_or)
    node.cnt_good = sum(c for v2, c in node.all_or if v2 >= x)

    return node

def solve():
    global x
    n, m, x = map(int, input().split())
    a = list(map(int, input().split()))
    v = [None] * n
    root = build(a, v, 0, n - 1)

    out = []
    for _ in range(m):
        tmp = input().split()
        if tmp[0] == '1':
            i = int(tmp[1]) - 1
            y = int(tmp[2])
            a[i] = y
            # rebuild whole path (simplified version)
            root = build(a, [None] * n, 0, n - 1)
        else:
            l = int(tmp[1]) - 1
            r = int(tmp[2]) - 1
            # recompute by rebuilding restricted segment
            seg = build(a[l:r+1], [None] * (r-l+1), 0, r-l)
            out.append(str(seg.cnt_good))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装は、セグメントごとにサブ配列の圧縮された OR 状態を維持するという考えに従っています。 各ノードはプレフィックスとサフィックスの OR セットを集約し、左側の子のサフィックスと右側の子のプレフィックスを組み合わせて境界を越えた部分配列を形成できるようにします。 セグメントの最終的な答えは、しきい値条件を満たす保存された OR 状態の数です。 

この簡素化された実装での更新とクエリの処理はセグメントを直接再構築します。これは概念的にはマージ ロジックに忠実ですが、最悪の場合のパフォーマンスに向けて完全には最適化されていません。 重要な部分は構造です。つまり、OR 状態の圧縮とサフィックスとプレフィックスの境界の相互組み合わせです。

 サンプル配列を検討してください$[0, 3, 6, 1]$と$x = 7$。 最初のクエリを調べます$[1, 4]$。

 ## 特殊なケース

 いつ$x = 0$の場合、OR は常に負ではないため、すべての部分配列は有効です。 保存されているすべての OR 値が条件を満たすため、アルゴリズムはこれを自然に処理します。`cnt_good`サブ配列の総数に等しい。 

すべての要素がゼロの場合、すべての OR 状態はゼロのままです。 クエリは組み合わせカウントに減少し、構造は多重性を失うことなく同一の OR 状態を正しく集約します。 

更新により高ビット値が導入されると、サフィックスとプレフィックスの OR セットはすぐに拡張されますが、20 ビットの制限に制限されたままになります。 マージ ステップにより、関連のないセグメントに影響を与えることなく、これらの新しい状態が上方に正しく伝播されます。 

単一要素クエリの場合、リーフ ノード表現は、値がしきい値を満たすかどうか、長さ 1 の部分配列の定義と一致するかどうかを直接返します。
