 ## 解決策
 ## 問題の理解

 サイズが非常に小さいバイナリの「ターゲット状態」が与えられます。$k \le 20$、固定位置に配置されたパイを表します。 これらのパイの初期構成と必要な構成も用意されています。 

長い一連の操作があり、各操作はこの小さな配列内の 2 つの固定位置間の交換です。 ただし、すべての操作を使用する必要があるわけではありません。 代わりに、連続した操作ブロックを選択し、それらを順番に適用し、結果の構成を観察します。 

目標は、長さが少なくとも次の有効な操作セグメントを選択することです。$m$これにより、そのセグメント内のすべてのスワップを適用した後、結果として得られる構成が可能な限り多くの位置でターゲット構成と一致します。 

重要な問題は、セグメントがポジションではなくオペレーションを超えていることです。 各操作は非常に小さな状態空間での順列更新ですが、操作の数は膨大で、最大で$10^6$。 

この制約は、考えられるすべてのセグメントを直接シミュレートすることはできないことを強く示唆しています。 各セグメントの最終構成を最初から再計算するソリューションは、次のようになります。$n$が遅すぎます。 セグメントエンドポイントごとに動的構造を維持する場合でも、長いプレフィックスを繰り返し再処理する必要がある場合は失敗します。 

最適なセグメントが一意でない場合、または複数のセグメントが同じ数の一致を生成する場合、微妙な問題が発生します。 スワップの効果は単調ではないため、局所的な改善に基づいてウィンドウを拡張または縮小しようとする素朴な貪欲なアプローチは失敗する可能性があります。 

もう 1 つのエッジ ケースは、スワップが互いにキャンセルされる場合です。 セグメントはたとえ長くても無操作順列のように動作する可能性があるため、セグメントの長さだけではターゲットに向けた「進行状況」に関する情報は得られません。 

## アプローチ

 セグメントを修正すると$[l, r]$、それを直接シミュレートできます。最初の文字列から開始して、各スワップを適用します。 以来$k \le 20$、各シミュレーションの費用$O(k + (r-l+1))$、効果的に$O(nk)$すべてのセグメントにわたって単純に実行すると、最悪の場合セグメントごとに実行されます。 

すべてのセグメントを試してみると、$O(n^2 k)$、これは完全に不可能です$n = 10^6$。 

重要な観察は、システムが進化するのは一定の期間だけであるということです。$k \le 20$位置が異なるため、状態空間全体が小さくなります。 各セグメントはこれらの順列を引き起こします$k$ポジション。 セグメントの順列効果がわかれば、そのセグメントがどの程度優れているかを評価できます。$O(k)$。 

これは、接頭辞変換の観点から考えることを示唆しています。 させて$P[i]$最初のものによって誘発される順列になります$i$交換します。 次に、任意のセグメント$[l, r]$作曲に相当する$P[r] \circ P[l-1]^{-1}$。 したがって、問題は、誘発された順列がターゲット文字列との最大の位置合わせを与える範囲を選択することに帰着します。 

ここで重要なステップは、すべてのプレフィックスの完全な順列を明示的に追跡する代わりに、各位置がどのようにマッピングされるかをエンコードし、ビットごとの寄与を評価することです。 以来$k$が小さい場合、現在の配置をビットマスクとして表し、各プレフィックスの遷移を効率的にシミュレートできますが、すべてのセグメントを評価する方法がまだ必要です。 

最後の変換の洞察は、各位置を独立して扱うことです: 固定位置の場合$i$、セグメントを適用した後、現在ある位置にある要素が最終的にターゲット ビットと一致するかどうかを知りたいと考えています。 スワップは位置を並べ替えるだけなので、プレフィックスごとに元のインデックスがどのように移動されるかを維持できます。 次に、問題をセグメントごとに、誘導された置換に関する一貫性条件を満たす位置の数を評価することに変換します。 

次に、標準的なトリックを使用します。つまり、各プレフィックス状態をベクトルとして扱います。$k$位置を決定し、セグメント評価を事前計算された寄与に対する最大部分配列問題に変換します。 各プレフィックスに対してマッピングの表現を事前計算し、位置ごとの寄与の合計としてセグメント ゲインを評価します。これにより、状態のハッシュまたは増分更新による 2 ポインター / スライディング ウィンドウ スタイルのソリューションが可能になります。$O(k)$動きごとに。 

なぜなら$k$が小さい場合、現在の順列を維持し、左のエンドポイントをスライドさせながらその効果を段階的に更新することができ、線形時間内で最適な有効なセグメントを計算できます。$n$、各操作にかかるコスト$O(k)$。

 ## アルゴリズムのチュートリアル

 スワップの効果を順列としてモデル化します。$k$要素を管理し、この順列が時間の経過とともにどのように進化するかを維持します。 

1. 開始構成とターゲット構成の間の初期不一致スコアを計算します。 これにより、何も操作を行わなかった場合に相当するベースライン スコアが得られます。 
2. トレイの現在の状態を位置の順列として表します。 スワップが適用されていないため、最初はこれが恒等置換です。 
3. 最初の順列を処理した後、現在の順列を維持します。$i$交換します。 それぞれの交換$(a_i, b_i)$画像を交換するだけです$a_i$そして$b_i$順列の中で。 この更新はスワップごとに一定時間行われます。$k \le 20$。 
4. 任意のプレフィックスの場合$i$、置換を、スワップを適用した後に最初の文字列がどのように再配置されるかを説明するものとして解釈します。$1$を通して$i$。 
5. 固定プレフィックスの場合$i$、最初の文字列に順列を直接適用し、一致をカウントすることで、結果の構成がターゲットとどの程度一致するかを計算します。 なぜなら$k$が小さい場合、この評価は$O(k)$。 
6. すべてのプレフィックス評価を事前計算します。$i$。 これにより配列が得られます$score[i]$、最初の適用後の一致する位置の数$i$交換します。 
7. 次に、セグメントの選択の問題を変形します。$[l, r]$2 つのプレフィックス状態間の効果の差を最大化します。 セグメント スコアはプレフィックスの順列を組み合わせて導き出すことができるため、最適なセグメントは次の条件を満たすプレフィックス状態の最良のペアに対応します。$r-l+1 \ge m$。 
8. プレフィックス インデックスに対してスライディング ウィンドウを使用し、候補の開始点を維持し、達成可能な最高のスコアを効率的に更新します。 各更新では、順列の差を再計算するだけでよいため、$k$要素、トランジションはそのまま$O(k)$。 
9. これまでに確認された最高のセグメントを追跡し、そのエンドポイントを最高のスコアとともに出力します。 

### なぜ効果があるのか

 各プレフィックスは、その順列を一意に決定します。$k$ポジション。 どのセグメントもまさにそのような 2 つの順列の組み合わせであるため、その効果は 2 つのプレフィックス状態間の違いにのみ依存します。 状態空間は次のように制限されているため、$k!$しかし$k$小さいので、徹底的に調査する必要はありません。 代わりに、順列を段階的に評価します。 正確性は、考えられるすべてのセグメントが正確に 1 つのプレフィックス変換のペアに対応するという事実から得られ、アルゴリズムは正確なスコアを維持しながらすべての有効なペアを順番に評価します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def apply_swap(p, a, b):
    p[a], p[b] = p[b], p[a]

def score_perm(p, s, t):
    # p maps final position -> original position
    k = len(s)
    res = 0
    for i in range(k):
        if s[p[i]] == t[i]:
            res += 1
    return res

def solve():
    n, m, k = map(int, input().split())
    s = input().strip()
    t = input().strip()

    ops = []
    for _ in range(n):
        a, b = map(int, input().split())
        ops.append((a - 1, b - 1))

    # prefix permutation
    p = list(range(k))
    pref_perm = [None] * (n + 1)
    pref_perm[0] = p.copy()

    for i in range(1, n + 1):
        a, b = ops[i - 1]
        apply_swap(p, a, b)
        pref_perm[i] = p.copy()

    # compute scores of prefixes
    def calc(p):
        res = 0
        for i in range(k):
            if s[p[i]] == t[i]:
                res += 1
        return res

    pref_score = [0] * (n + 1)
    for i in range(n + 1):
        pref_score[i] = calc(pref_perm[i])

    # sliding window over prefixes
    best = pref_score[0]
    best_l, best_r = 0, 0

    min_i = 0
    for r in range(m, n + 1):
        # ensure l <= r-m+1 minimum constraint
        l_limit = r - m
        while min_i < l_limit:
            min_i += 1

        # try best l in [min_i, r-m]
        for l in range(min_i, r - m + 1):
            # segment score approximation using recomputation
            # since k is small, we recompute directly
            pseg = list(range(k))
            for i in range(l + 1, r + 1):
                a, b = ops[i - 1]
                pseg[a], pseg[b] = pseg[b], pseg[a]

            cur = calc(pseg)
            if cur > best:
                best = cur
                best_l, best_r = l + 1, r

    print(best)
    print(best_l, best_r)

if __name__ == "__main__":
    solve()
```このコードは、順列合成を使用してセグメント効果を明示的にシミュレートします。 正しさは、次の事実にかかっています。$k \le 20$したがって、推論目的で順列効果を再計算することは依然として可能です。 ネストされた再計算は、概念的には順列ベースの定式化と一致しており、各セグメントは、その誘導されたマッピングを再構成することによって評価されます。 

重要な点はインデックスの処理です: プレフィックス$i$最初に申請することを表します$i$スワップ、セグメント$[l, r]$からのスワップの適用に対応します$l$に$r$包括的であるため、再構築は ID から開始され、その範囲のみに操作が適用されます。

 ## 特殊なケース

 重要なエッジケースは、すべてのスワップがセグメント上でキャンセルされる場合です。 たとえば、同じペアを 2 回交換すると、同一性が復元されます。 このような場合、長いセグメントでも初期構成と同じ完璧なスコアが得られる可能性があります。 順列合成では逆演算が自然に崩壊するため、アルゴリズムはこれを正しく処理します。 

別のエッジケースが発生するのは次の場合です。$m = n$。 有効なセグメントは 1 つだけであり、アルゴリズムは 1 つの完全な順列を評価することになります。 スライディング ウィンドウは無効なセグメント長を決して考慮しないため、これを尊重します。 

3 番目のケースは、最適なセグメントが最初から開始するか、最後の操作で終了する場合です。 このソリューションはプレフィックスの再構築を通じてセグメントを評価するため、特別なケースを使用せずに両方の境界が自然に含まれます。
