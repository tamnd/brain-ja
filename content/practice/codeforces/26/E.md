 ## 解決策
 ## 問題の理解

 各プロセスは、次の 2 つのアトミック命令を繰り返し実行します。```
yi := y
y := yi + 1
```共有変数`y`から始まります`0`。 すべてのプロセスには独自のプライベート変数があります`yi`したがって、異なるプロセスが互いのローカル状態を上書きすることはありません。 

重要な点は、2 つの命令が別々のアトミック操作であるということです。 プロセスは現在の値を読み取ることができます。`y`、長い間中断され、後で書き直す`yi + 1`古い値を使用しています。 このため、増分が失われる可能性があります。 

すべての操作が中断することなく順番に実行された場合、最終的な値は次のようになります。```
sum(ni)
```しかし、任意のインターリーブを使用すると、最終的な答えははるかに小さくなる可能性があります。 

ある実行スケジュールが正確に生産できるかどうかを尋ねられます。`W`。 「はい」の場合、実行された命令の有効なシーケンスを 1 つ出力する必要があります。 スケジュールには、実行された命令ごとに 1 つのプロセス インデックスが含まれるため、その長さは正確に次のとおりである必要があります。```
2 * sum(ni)
```各ループ反復で 2 つの命令が実行されるためです。 

制約は、ある次元では驚くほど小さく、別の次元では大きくなります。 多くてもあります`100`プロセスがあり、各プロセスは最大で`1000`反復なので、反復の合計数は最大で`100000`。 つまり、明示的なスケジュールを作成して印刷することは完全に実現可能です。 

実現不可能なことは、可能なすべてのインターリーブを調査することです。 すべての反復で 2 つの操作が行われるため、天文学的に多くのスケジュールが存在します。 執行命令に対するブルートフォース検索は不可能です。 

難しいのは、到達可能な最終値を理解することです。 

それぞれ 1 回の反復を行う 2 つのプロセスを考えてみましょう。```
P1: read 0
P2: read 0
P1: write 1
P2: write 1
```最終的な値は次のようになります`1`、2つの増分があったにもかかわらず。 両方のプロセスが同じ古い値を読み取ったため、1 つの増分が失われました。 

ここで、次のような単一のプロセスを考えてみましょう。`n1 = 11`。 同時実行性がないため、すべてのインクリメントは成功します。 唯一可能な最終値は次のとおりです。`11`。 求める`W = 10`不可能です。 

よくある間違った仮定は、間のすべての値が`1`そして`sum(ni)`到達可能です。 プロセスが少なすぎると失敗します。 

例えば：```
2 1
1 1
```両方のプロセスが読み取りできるため、可能です`0`どちらかが書き込む前に。 

しかし：```
1 0
1
```不可能です。 少なくとも 1 つの書き込みが常に発生し、その書き込みがセットされます。`y`少なくとも`1`。 

もう 1 つの微妙なケースは、1 つのプロセスが他のプロセスよりもはるかに長い場合です。```
2 5
100 1
```不注意な施工により、誤って長い工程が増加する可能性があります`y`はるかに超えた`5`。 スケジュールでは、多くの書き込みが相互に上書きされるように、古い読み取りを慎重に調整する必要があります。 

重要な課題はシミュレーションではなく、どのような最終値が発生するかを正確に特徴付けることです。 

## アプローチ

 ブルートフォースのアイデアは単純です。 あらゆる瞬間に、次の命令が存在するプロセスを選択し、その命令を実行し、再帰的に続行します。 最後に、最終値が次と等しいかどうかを確認します。`W`。 

これが機能するのは、ステートメントで任意のインターリーブが許可されているためです。そのため、すべてのスケジュールを列挙すると、最終的には到達可能なすべての状態が見つかります。 

問題は分岐要素です。 反復の合計数が次のようになると仮定します。`S`。 それから、`2S`アトミック操作。 命令の依存関係を無視したとしても、インターリーブの数はすでに膨大です。```
(2S)!
```と`S = 100000`、これは完全に絶望的です。 

画期的な進歩は実際に何が変わるのかを理解することから生まれる`y`。 

書き込み命令は常に以下を設定します。```
y = old_read_value + 1
```複数のプロセスが同じ値を読み取った場合`k`、その後、すべての書き込みが後で設定されます`y`に`k + 1`。 このような書き込みが何回発生しても、値は 1 回しか増加しません。 

したがって、実行はレイヤーで表示できます。```
0 -> 1 -> 2 -> ...
```から増やすには`k`に`k + 1`、少なくとも 1 つのプロセスが新規読み取りを実行する必要があります。`k`。 任意の数の追加プロセスも読み取ることができます`k`、しかし、その後の書き込みでは値はさらに増加し​​ません。 

これにより、すぐに特徴がわかります。 

最終的な値が`W`。 

そうすると、次のような連鎖が存在するはずです。`W`成功した増分。 インクリメントが成功するたびに、何らかのプロセスで 1 回の反復が必要になります。 プロセスは、最新の値を繰り返し読み取ることによって、複数の成功した増分に寄与する可能性があります。 

可能な最小の最終値は、書き込みの前に最初の読み取りがすべて行われたときに取得されます。 その後、すべての書き込みが保存されます`1`したがって、最終的な答えは次のとおりです。`1`。 

可能な最終的な最大値は次のとおりです。`sum(ni)`すべての増分が連続して成功したとき。 

ただし、すべての中間値に到達できるわけではありません。 重要な観察は次のとおりです。 

のプロセス`ni`反復が貢献できるのはせいぜい`ni`インクリメントは成功しましたが、参加する場合は、その最初の反復で何らかの値を読み取り、最終的に少なくとも 1 つのインクリメントを生成する必要があります。 

構造を注意深く検討した結果、到達可能な値は次のようになります。```
1 <= W <= sum(ni)
```ただし、プロセスが 1 つしかなく、答えを正確に求める必要がある場合は除きます。`n1`。 

残りのタスクは建設的なものです。 明確なスケジュールが必要です。 

構造はエレガントです。 メインカウンターとして機能するプロセスを 1 つ選択し、正確に実行します`W`成功した増分。 残りのすべての反復は、最終値を変更しない古い上書きになります。 

古い上書きを作成するには、カウンタがさらに進む前に古い値を何度も繰り返して読み取らせます。

 ## アルゴリズムのチュートリアル

 1. 合計の反復数を計算します。```
S = sum(ni)
```1. 単一プロセスの場合は個別に処理します。 

プロセスが 1 つだけなので、インターリーブはありません。 反復ごとに増加します`y`ちょうど 1 だけなので、最終的な値は等しくなければなりません`n1`。 
2. 複数のプロセスの場合は、次のことを確認します。```
1 <= W <= S
```そうでない場合は、印刷してください`No`。 

1. 主要な増加プロセスとして 1 つのプロセスを選択します。 プロセスを使用します`1`。 
2. 正確に予約する`W`すべてのプロセスを反復して、成功したインクリメント チェーンを形成します。 

考え方としては、これらの予約された反復がほぼ順番に実行されるということです。```
read k
write k + 1
```のために`k = 0, 1, ..., W - 1`。 

1. 残りのすべての反復は無害な古い書き込みに変換されます。 

カウンタが進みすぎる前に、これらの追加の反復で古い値を読み取るようにします。 後で彼らが返事を書くとき、`old + 1`、上書きされます`y`以前にすでに持っていた値が使用されるため、最終的な値は増加しません。 
2. スケジュールを明示的に作成します。 

正常に増加するたびに、次のようになります。 

まず、選択した反復の読み取り命令を実行します。 

次に、その書き込み命令をただちに実行します。 

これにより、次のことが保証されます`y`1つ増えます。 
3. 残りの反復ごとに次のようにします。 

カウンタが最終値に達する前に、読み取り命令を早めに実行してください。 

カウンタが少なくとも同じ値に達するまで、その書き込み命令を遅らせます。 

その後、書き込みは無害になります。 
4. スケジュールを出力します。 

### なぜ効果があるのか

 不変条件は、予約されたチェーンのみが新しい値を提供するということです。 

インクリメントが成功するたびに、現在の値が読み取られます。`y`そしてすぐに書き戻します`y + 1`, したがって、値はちょうど 1 回増加します。 

古い反復ごとに以前の値が読み取られます`k`。 遅延書き込みが発生するまでに、`y`すでに少なくとも`k + 1`。 書き込み`k + 1`到達した最大値を再び増やすことはできません。 

正確に施工いたしますので、`W`増分が成功し、他のすべての反復が新しい増分に寄与しないようにすると、最終値は正確になります。`W`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, w = map(int, input().split())
    a = list(map(int, input().split()))

    total = sum(a)

    if n == 1:
        if w != a[0]:
            print("No")
            return

        print("Yes")
        ans = []

        for _ in range(a[0]):
            ans.append(1)
            ans.append(1)

        print(*ans)
        return

    if w < 1 or w > total:
        print("No")
        return

    print("Yes")

    rem = a[:]
    ans = []

    good = []

    need = w

    for i in range(n):
        take = min(rem[i], need)
        rem[i] -= take
        need -= take

        for _ in range(take):
            good.append(i + 1)

        if need == 0:
            break

    bad = []

    for i in range(n):
        for _ in range(rem[i]):
            bad.append(i + 1)

    # stale reads
    for p in bad:
        ans.append(p)

    # successful increments
    for p in good:
        ans.append(p)
        ans.append(p)

    # stale writes
    for p in bad:
        ans.append(p)

    print(*ans)

solve()
```この構築では、反復を 2 つのグループに分割します。 

の`good`反復は実際の増加に関与します`0`に`W`。 それぞれが読み取りと書き込みを連続して実行し、1 回のインクリメントの成功を保証します。 

の`bad`反復は古い上書きです。 成功したチェーンが開始される前に、それらの読み取り命令が最初に実行されます。 その瞬間、それらはすべて同じ小さな値を読み取ります。通常は`0`。 

それらの書き込み命令は、成功したすべてのインクリメントが完了するまで延期されます。 それまでに、`y`はすでに十分な大きさであるため、これらの書き込みによって増加することはできません。 

スケジュール形式は微妙です。 各プロセス インデックスは、反復全体ではなく、その次の命令を参照します。 それで次のように書く：```
ans.append(p)
ans.append(p)
```これは、同じ反復で最初に読み取り命令を実行し、次に書き込み命令を実行することを意味します。 

よくある間違いは、各反復がちょうど 2 つのスケジュール エントリに寄与することを忘れることです。 最終的なスケジュールの長さは次のようにする必要があります。```
2 * sum(ni)
```この構造は自動的にそれを満たします。
