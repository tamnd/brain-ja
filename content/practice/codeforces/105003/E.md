 ## 問題の理解

 道路で接続された都市の重み付けされた無向グラフが与えられます。 2 人のプレイヤーは異なる都市のセットから開始します。Huize は開始都市のセットをコントロールし、Jacobo は別のセットをコントロールします。 これらの開始位置から、両プレイヤーは同時にグラフを通じて影響力を拡大します。 拡張は道路に沿って移動し、各道路には移動時間が設定されているため、影響は離散的なステップではなく最短経路の意味で広がります。 

各都市は最初に到達した人が主張します。 両方のプレイヤーが同時に都市に到着した場合、ハコボが引き分けで勝ちます。 一度都市を占領すると、相手はその都市にアクセスできなくなるため、今後の道はそこを通過できなくなります。 

問題は、一部の道路が最初は使用できないことです。 都市インデックスがマークされた道路には「コード」が必要で、そのコードはプレイヤーがその特定の都市をすでに征服している場合にのみ取得されます。 その都市を占領した後にのみ、そのプレイヤーは道路を使用できるようになります。 

最終的な目標は、プロセスが安定した後に各プレイヤーが最終的に制御できる都市の数を決定し、ハコボが厳密に勝つかどうかを決定することです。 彼がそうする場合、特別なメッセージと征服された都市の違いを出力します。 それ以外の場合は、負けのメッセージを出力します。 

この制約により、テスト ケースごとに線形に近いアルゴリズムまたは対数グラフ アルゴリズムが使用されるようになります。 すべてのテストにわたるノードとエッジの合計数は約 20 万に制限されるため、状態ごとまたはロック解除イベントごとにダイクストラを繰り返すソリューションは、慎重に最適化しない限り遅すぎます。 複数のソースと重み付けされた最短パスの拡散の存在は、複数のソースの最短パス プロセスを強く示唆しています。 問題は、ロックされたエッジによって依存関係が作成されることです。これにより、ノードの訪問によってトリガーされる状態遷移が効果的に導入されます。 

単純なアプローチでは、新しい都市がエッジのロックを解除するたびに、最短経路を繰り返し再計算することになります。 これはすぐに失敗します。最悪の場合、すべての都市がエッジのロックを解除し、グラフ全体でダイクストラ実行が繰り返され、合計入力サイズに対して三次のような動作が発生する可能性があるためです。 

2 番目の単純なアイデアは、ロックを無視して、両方のプレイヤーに対して標準のマルチソース ダイクストラを実行することです。 これは、特定の都市に到達するまで一部のエッジが使用できないため、正確性が損なわれます。 簡単な反例としては、長さは最適であるものの、一方のプレイヤーにとっては遠く、もう一方のプレイヤーにとっては近い都市の背後にある道路が挙げられます。 ロックを無視すると、到達可能性が変化し、結果全体が変化します。 

ロックされたエッジが主要都市に 2 番目に到着したプレイヤーにのみ利益をもたらす場合、微妙なエッジケースが発生します。 同点はハコボに渡されるため、都市は同点のタイミングで正確に把握できれば、多くの下流側の主張を覆す近道を開くことができる。 どのソリューションでも、都市の要求とエッジのアクティブ化の正確な順序を尊重する必要があります。 

## アプローチ

 ロックを無視すると、構造は 2 セットのソースからなる古典的なマルチソース ダイクストラになります。 各都市はホイゼとハコボから最も早い到着時間を取得し、これらの時間を同点で有利なハコボと比較することによって所有権が決定されます。 これは、ロックされていないバージョンのグラフでは正しいです。 

ブルート フォース拡張機能は、ロック解除プロセスを動的にシミュレートします。 プレイヤーが主要都市に到達するたびに、発信側のロックされたエッジをアクティブにし、最短経路を再計算します。 ルールが正確に反映されているため、正確性は簡単です。新しいエッジが利用可能になると、グラフは進化します。 ただし、これにより最短経路の計算が繰り返し行われることになります。 最悪のケースでは、O(N) 都市のそれぞれが O(M) エッジのロックを解除する可能性があり、ロックを解除するたびに O(M log N) のダイクストラ実行がトリガーされ、制限をはるかに超える O(N M log N) になります。

重要な観察は、ロック解除を状態拡張として扱う場合、エッジのアクティブ化は最短パス構造の観点から基本的に動的ではないということです。 距離を再計算する代わりに、「コードを取得した」ことを特定のエッジの緩和を可能にする状態の一部として扱うことができます。 都市に到達すると、そのプレイヤーはその都市から発信されるすべてのロックされたエッジがすぐに使用できるようになります。これは、ダイクストラでノードが確定した瞬間にそれらのエッジを緩和プロセスに注入することで処理できます。 

これにより、問題は、制御された隣接関係を明らかにした 2 つのソースの最短パスの計算に変換されます。 各ノードは、優先キューからポップされると、以前は休止状態だった追加のエッジが表示されます。 これは、動的隣接アクティベーションによる最短パスで使用される原理とまったく同じですが、プレーヤーごとに 1 回の実行で実装されます。 

したがって、修正されたダイクストラを 2 回 (Huize 用に 1 回、Jacobo 用に 1 回) 実行します。 各実行は、形式 (距離、ノード) の状態に対する優先キューを維持します。 ノードが完了すると、そのノードにコードが含まれるすべてのエッジがアクティブになります。 これらのエッジは、将来の緩和のために通常の隣接エッジとして扱われます。 各エッジは最大 1 回アクティブ化されるため、全体の複雑さは標準ダイクストラに近いままになります。 

最後に、Jacobo が同点で有利な場合とノードごとの到着時間を比較します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ロックを解除するたびにディクストラを再計算する | O(N M log N) | お(お) | 遅すぎる |
 | 単一の修正されたマルチソース Dijkstra | O((N + M) log N) | O(N + M) | 承認済み |

 ## アルゴリズムのチュートリアル

 1 人のプレイヤーの場合の解決策について説明します。 同じプロセスが 2 回実行されます。 

1. 距離ゼロにあるプレーヤーのすべての開始都市で優先キューを初期化します。 これは、複数のソースからの同時拡張を表します。 
2. 無限に初期化された配列 dist[node] を維持します。 これには、各都市への既知の最も早い到着時刻が保存されます。 
3. ロックされたエッジを必要な都市ごとにグループ化する構造を維持します。これにより、都市が処理されるときに、それに依存するすべてのエッジをアクティブ化できます。 
4. 優先キューが空でない間に、現在の距離が最小のノードを抽出します。 この距離が dist[node] と比べて古い場合はスキップしてください。 
5. ノードが初めてファイナライズされると、コードシティがこのノードであるすべてのエッジが直ちにアクティブ化されます。 これにより、これらのエッジを将来のリラックスに利用できるようになります。 
6. ノードに付随する現在アクティブなエッジをすべてリラックスします。 近隣へのより短いパスが見つかった場合は、dist を更新して優先キューにプッシュします。 
7. 到達可能なすべてのノードが処理されるまで続行します。 

両方の距離配列を計算した後、各都市の所有権を割り当てます。 Huizeの距離が小さければHuizeが勝ちます。 ハコボの距離が小さいか等しい場合、ハコボが勝ちます。 

最終的な答えは、割り当てられたノードを数えることによって計算されます。 

### なぜ効果があるのか

 不変条件は、ノードが優先キューからポップされるときに、現在利用可能なエッジ セットの下でのその最短距離が確定するということです。 エッジはロック解除都市が確定したときにのみ追加されるため、前提条件となる最短パス時間が正しく決定されるまでエッジは使用可能になりません。 これにより、ロックされたエッジを使用するパスは、ロック解除された都市に真の最短時間で到達した後にのみ考慮され、ゲーム ルールと正確に一致することが保証されます。 エッジの追加は単調であり、最終的な状態のみに依存するため、このプロセスでは標準的なダイクストラの正確さが維持されます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

INF = 10**30

def dijkstra(n, adj, starts, unlocks):
    dist = [INF] * (n + 1)
    pq = []

    for s in starts:
        dist[s] = 0
        heapq.heappush(pq, (0, s))

    used = [False] * (n + 1)

    while pq:
        d, u = heapq.heappop(pq)
        if d != dist[u]:
            continue

        if not used[u]:
            used[u] = True
            for v, w in unlocks[u]:
                adj.append((u, v, w))

        for i in range(len(adj[u])):
            v, w = adj[u][i]
            nd = d + w
            if nd < dist[v]:
                dist[v] = nd
                heapq.heappush(pq, (nd, v))

    return dist

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())

        adj = [[] for _ in range(n + 1)]
        unlocks = [[] for _ in range(n + 1)]

        edges = []

        for _ in range(m):
            u, v, w, c = map(int, input().split())
            if c == 0:
                adj[u].append((v, w))
                adj[v].append((u, w))
            else:
                unlocks[c].append((u, v, w))
                unlocks[c].append((v, u, w))

        h = int(input())
        hs = list(map(int, input().split()))
        j = int(input())
        js = list(map(int, input().split()))

        dh = dijkstra(n, adj, hs, unlocks)
        dj = dijkstra(n, adj, js, unlocks)

        hc = jc = 0
        for i in range(1, n + 1):
            if dh[i] < dj[i]:
                hc += 1
            else:
                jc += 1

        if jc > hc:
            print("La hora de juego")
            print(jc - hc)
        else:
            print("Hasta luego Huize, es la hora de Olivia")

if __name__ == "__main__":
    solve()
```この実装では、各プレイヤーに対して修正されたダイクストラが実行されます。 隣接リスト`adj`常に利用可能な道路が含まれています。 構造`unlocks`都市が完成した後にのみ使用可能になる道路を保管します。 

重要な点は、ノードが優先キューから初めてポップされたときにのみ、ロックされたエッジをアクティブにすることです。 これにより、その都市への最短経路の到着時間が決定されたまさにその瞬間にアクティベーションが行われることが保証されます。 

次に、アクティブ化がプレーヤーに依存せず、どの都市に最適な時間で到達するかのみに依存するという事実に基づいて、両方のプレーヤーに対して同じグラフ構造を再利用します。
