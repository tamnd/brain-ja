 ## 解決策
 ## 問題の理解

 容量が固定された 2 つのコンテナが与えられます。 最初のものは次まで耐えることができます`a`水の単位と秒まで`b`。 最初のタンクが次のように始まる初期構成も受け取ります。`c`単位と 2 番目の`d`、この最初のペアは、完全な長方形内の任意の点にすることができます。`[0, a] × [0, b]`。 

次に、一連の操作が適用されます。 各操作では、2 つのタンク間で水を移動する試みが説明されます。 操作値が正の場合、水を最初のタンクから 2 番目のタンクに移そうとします。 負の場合は、水を逆方向に移送しようとします。 すべての移送は、移送したい量、移送元のタンクに利用可能な水の量、移送先のタンクにどれだけの空き容量が残っているかという 3 つのことによって同時に制約されます。 

最後のタスクは、1 つの初期状態をシミュレートすることではなく、考えられるすべての開始ペアについて最初のタンク内の最終量を計算することです。`(c, d)`。 これにより、問題は、およそ 100 万の州のサイズのグリッドの変換を評価することに変わります。`a, b ≤ 1000`。 

素朴な解釈では、各開始状態を個別にシミュレートし、すべてを適用することを示唆しています。`n ≤ 10^4`操作。 それはすでに約約かかります`10^4 × 10^6 = 10^10`実現可能な範囲をはるかに超えた更新です。 

それほど明らかではない問題は、プロセスが代数的な意味で線形ではないことです。 各操作は可用性と残りの容量の両方によってクリップされるため、中間状態の小さな変化が非線形に伝播する可能性があります。 システムが正確な整数の境界に依存するため、合計または平均のみを追跡しようとする単純な DP は失敗します。 

単純な推論を打ち破る重要なエッジケースは飽和です。 たとえば、タンクが満杯になった場合、たとえその違いが 1 ユニットだけであっても、そのタンクへの今後の移送は部分的に空の場合とは異なる動作をします。 これは、状態の圧縮では正確な区分動作を保持する必要があることを意味します。 

## アプローチ

 ブルートフォース手法では、すべてを反復処理することになります。`(c, d)`をペアにして、それぞれのシーケンス全体をシミュレートします。 それぞれのシミュレーションは、`O(n)`したがって、全体の複雑さは次のようになります。`O(a · b · n)`、最悪の場合は約`10^10`操作。 これでは実行不可能です。 

重要な観察は、システムが区分的に線形で単調であるが、ブレークポイントは完全に容量によって制御されていることです。`a`そして`b`、操作の数ではありません。 各操作の後、状態のグリッドの変換は、タンクが満杯になるか空になる境界に沿ってのみ値が変化するグリッドのままです。 容量が小さい (≤ 1000) ため、完全な状態空間を明示的に維持し、段階的に更新できます。 

初期状態ごとに最初から再計算する代わりに、2D DP テーブルを維持します。`dp[x][y]`最初から開始して、操作のいくつかのプレフィックスを処理した後の最初のタンク内の量を表します`(x, y)`。 各操作により、このテーブル全体が次のように変換されます。`O(a·b)`隣接する州間で局所的に水を押し出す効果を計算することで時間を計算します。 各ステップは現在のセルにのみ依存するため、履歴を再計算する必要はありません。 

したがって、問題は次のシーケンスを適用することに帰着します。`n`境界グリッド上のグローバル変換。それぞれグリッド サイズにわたる線形時間で行われます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(a・b・n) | O(1) おまけ | 遅すぎる |
 | グリッド DP シミュレーション | O(n・a・b) | O(a・b) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちはグリッドを維持します`dp[x][y]`、 どこ`x`はタンク 1 の現在の量であり、`y`はタンク 2 の現在の量です。最初は、このグリッドは ID です: 各状態`(c, d)`ファイナルにマップします`(c, d)`操作の前に。 

各操作により、このグリッドが新しいグリッドに変換されます。 

1.初期化`dp[x][y] = x`みんなのために`0 ≤ x ≤ a`、`0 ≤ y ≤ b`。 これは、操作の前に、最初のタンクに正確に次のものが含まれているという事実をエンコードします。`x`。 
2. 各演算値について`v`、新しいグリッドを構築します`ndp`。 
3. もし`v > 0`では、水をタンク 1 からタンク 2 に押し込むことをシミュレートします。すべての状態について`(x, y)`、転送量の制限は次のとおりです。`x`そして`b - y`。 結果の状態は次のようになります`(x - t, y + t)`どこ`t = min(v, x, b - y)`。 ウェブアサイン`ndp[x][y] = dp[x - t][y + t]`なぜなら、移動後、最終的な値が前の DP レイヤーからすでにわかっている新しい状態に到達するからです。 
4. もし`v < 0`では、対称的な操作を行います。水はタンク 2 からタンク 1 に移動します。それぞれについて`(x, y)`、計算する`t = min(-v, y, a - x)`、に遷移します`(x + t, y - t)`。 設定しました`ndp[x][y] = dp[x + t][y - t]`。 
5. 交換する`dp`と`ndp`そして続けます。 

すべての操作を処理した後、`dp[c][d]`その開始構成のタンク 1 の最終量を直接示します。 

重要なアイデアは、状態ごとに水の量を時間的に前方に進化させるのではなく、各操作によって引き起こされる変換を通じてマッピング全体を後方に押し出すということです。 

### なぜ効果があるのか

 各操作は、最終状態から前の状態への決定論的なマッピングを定義します。 すべての状態には、特定の操作の下で正確に 1 つの先行操作があるため (移動量は容量制約によって一意に決定されるため)、変換は実行可能なグリッド上で全単射的になります。 これにより、逆遷移を通じて値を伝播する際に、衝突や曖昧さのない正確さが確保されます。 DP テーブルは基本的に、すべての操作にわたってこれらの全単射の構成を追跡します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, a, b = map(int, input().split())
    v = list(map(int, input().split()))

    dp = [[i for j in range(b + 1)] for i in range(a + 1)]

    for move in v:
        ndp = [[0] * (b + 1) for _ in range(a + 1)]

        if move > 0:
            for x in range(a + 1):
                for y in range(b + 1):
                    t = min(move, x, b - y)
                    nx, ny = x - t, y + t
                    ndp[x][y] = dp[nx][ny]
        else:
            mv = -move
            for x in range(a + 1):
                for y in range(b + 1):
                    t = min(mv, y, a - x)
                    nx, ny = x + t, y - t
                    ndp[x][y] = dp[nx][ny]

        dp = ndp

    out = []
    for x in range(a + 1):
        out.append(" ".join(str(dp[x][y]) for y in range(b + 1)))
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このコードは完全な状態テーブルを初期化し、各操作の後にそれを繰り返し書き換えます。 ネストされたループは、すべての状態遷移がローカルの容量制約にのみ依存するという事実を反映しているため、各更新は再帰や追加の構造を使用せずに直接計算できます。 最終的なテーブルは、必要な出力形式と一致して行ごとに印刷されます。 

境界処理は暗黙的に行われます。`min`利用可能な水または残りの容量を超えて移送されないことを保証する表現。 

## 実用的な例

 ### 例 1

 入力:```
n=3, a=4, b=4
v = [-2, 1, 2]
```単一の状態を追跡します`(c=3, d=2)`。 

| ステップ | 操作 | 状態 (x,y) | 転送 | 新しい状態 |
 | --- | --- | --- | --- | --- |
 | 0 | 初期化 | (3,2) | - | (3,2) |
 | 1 | -2 | (3,2) | 1 | (4,1) |
 | 2 | +1 | (4,1) | 1 | (3,2) |
 | 3 | +2 | (3,2) | 2 | (1,4) |

 最終的な1号戦車は`1`。 

このトレースは、特に容量制限によって意図した転送が減少するステップ 1 で、中間の飽和が転送サイズにどのような影響を与えるかを示しています。 

### 例 2

 最小限のシステムを考えてみましょう。```
n=1, a=2, b=2, v=[2]
```状態について`(2,1)`:

 | ステップ | 状態 | 転送 | 結果 |
 | --- | --- | --- | --- |
 | 初期化 | (2,1) | - | (2,1) |
 | オプ | (2,1) | 1 | (1,2) |

 移送は、要求された量ではなく、2 番目のタンクの残存容量によって制限されます。 

これにより、クリッピング動作が完全にキャプチャされていることが確認されます。`min`表現。

 ## 特殊なケース

 主なエッジケースは、移送開始時に 1 つのタンクがすでに満杯または空の場合に発生します。 たとえば、次の場合`a = b = 2`、`c = 2`、`d = 0`、タンク 1 からタンク 2 に移動しようとしますが、方向に応じて目的地が満杯かソースが空であるため、水は移動しません。 アルゴリズムはこれを正しく処理します。`t = min(x, b - y, v)`は自動的にゼロになり、状態は変化しません。 

もう 1 つのケースは、飽和と放出が繰り返され、水が意図した量を完全に移送することなくタンク間を往復する場合です。 DP 移行では常に瞬間的な容量制約が尊重されるため、各ステップが近似値ではなく現在の正確な状態から実行可能性を再計算するため、繰り返し操作でも一貫性が保たれます。
