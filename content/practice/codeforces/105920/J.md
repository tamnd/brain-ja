 ## 解決策
 ## 問題の理解

 入力は、簡略化されたブリッジ オークションにおける一連のアクションを記述します。 4 人のプレーヤーが固定された循環順序で行動し、各アクションはビッド (「2C」または「1S」などのオークション)、パス、ダブル、またはリダブルのいずれかになります。 

この規則は、これらの行為が法的にどのように表示されるかを規定します。 入札では、最初にレベル (1 ～ 7) を比較し、次にスーツの順序 (クラブ < ダイヤモンド < ハート < スペード < トランプなし) を比較する厳密な順序に従って、常に現在の最高入札額を引き上げる必要があります。 パスはいつでも許可されます。 ダブルは、最後に意味のあるビッドが対戦相手によって行われた場合にのみ合法であり、リダブルは、最後の意味のあるアクションが対戦相手によって行われたダブルである場合にのみ合法です。 オークションは、4 人のプレーヤー全員がすぐにパスした場合、またはパス以外のアクションが発生した後に 3 回連続したパスがあった場合に終了します。 

タスクは、特定の一連のアクションがこれらのルールの下で有効であるかどうか、そしてそれが実際に終了する完全なオークションを表すかどうかを判断することです。 

入力サイズは十分小さいため、テスト ケースごとのリニア スキャンでも十分です。 ケースごとに最大 320 のアクションと 100 のケースがある場合、ステップごとに一定量の状態を維持するソリューションは十分に高速であるため、バックトラックや分岐のシミュレーションを試みるアプローチは必要ありません。 

主な困難はパフォーマンスではなく、進化するオークション状態を忠実に維持することです。つまり、最後に意味のある入札を行ったのは誰か、最後のアクションはダブルかどうか、現在のシーケンスは終了ルールを満たしているかどうかなどです。 

いくつかのエッジな状況では、単純な実装が壊れる傾向があります。 1 つは完全にパスで構成されるシーケンスです。 たとえば、「P P P P」は有効で完全です。 終了を決定する前に非パスアクションをチェックするだけの単純なアプローチでは、そのアクションが誤って拒否される可能性があります。 

もう 1 つの注意が必要な状況は、入札の前にパスが発生し、その後入札が表示され、その後パスが再開される場合です。 3 パス終了ルールは、非パス アクションが存在した後にのみ適用されるため、初期のパスによって完了ロジックがトリガーされるべきではありません。 

3 番目の微妙なケースは、パートナーシップ間でダブルとダブルが交互に行われることです。 たとえば、ビッドの後、次のプレーヤーによる有効なダブル、それに続く相手のパートナーシップによる有効なリダブルは、最後の非パス アクションの所有権を厳密に追跡する必要があります。 誰が作成したかを追跡せずに「最後のアクション タイプ」だけをチェックする実装は失敗します。 

## アプローチ

 妥当性を検証する総当り的な方法では、アクションごとに、最後の有効な入札が何であったか、入札の所有者は誰か、二重または二重が許可されるかどうかをゼロから再計算しながら、オークション全体をシミュレートします。 各ステップについて、シーケンスを逆方向にスキャンして、最後の非パス アクションを見つけて正当性を判断できます。 n 個のアクションのそれぞれで最大 n 個前のアクションをスキャンする必要があるため、テスト ケースごとに O(n²) 個のソリューションが得られます。 テストあたり 320 のアクションと 100 のテストでは、これは境界線に達し、不要になります。 

重要な点は、必要な情報はすべて段階的に維持できるということです。 いつでも、現在の最高入札額、落札したプレーヤー、最新の非パス アクションのタイプと所有者を覚えていればよいだけです。 それぞれの新しいアクションの合法性は、完全な履歴ではなく、この一定サイズの状態にのみ依存します。 

これらの変数を追跡すると、すべてのアクションは一定時間の遷移になります。 また、最後の非パス アクション以降の連続パスのカウンターも維持し、ビッド、ダブル、またはリダブルが発生するたびにリセットします。 これにより、過去のイベントを再検討することなく、終了条件が直接モデル化されます。

 | 最適なシミュレーション | テストあたり O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

小さな状態を追跡しながら、アクションを順番に処理します。 

1. 現在のプレイヤー インデックスを維持し、0 から 3 まで循環します。各アクションはターン順にプレイヤーに割り当てられます。 
2. 最後の有効な入札をペア (レベル、スーツ ランク) として保存します。 最初は入札はありません。 
3. 私たちは、最後の意味のある入札の所有者、つまり上書きされなかった最新のオークションを行ったプレイヤーを追跡します。 
4. 最後の非パス アクション タイプとその所有者を追跡します。 これは double と redouble を検証するために必要です。 
5. 最後の非パスアクション以降の連続パスのカウンターを維持します。 
6. 非パス アクションが発生したかどうかを示すフラグを維持します。これは、「4 つの最初のパスすべて」の終了条件に必要です。 

各アクションについて:

 1. アクションがパスの場合、パス カウンタをインクリメントします。 パス カウンタが 4 に達し、非パス アクションが発生していない場合は、終了を受け入れます。 それ以外の場合、非パス アクションがあり、パス カウンタが 3 に達した場合、オークションは完了します。 
2. アクションが入札の場合、現在の入札が存在する場合、それが厳密にそれを上回っていることを確認します。 そうでない場合、シーケンスは無効です。 最後の入札を更新し、パスカウンターをリセットします。 
3. アクションがダブルの場合、パス以外の最後のアクションが相手のビッドであることを確認します。 そうでない場合、シーケンスは無効です。 このダブルを最後の非パスアクションとして記録し、パスカウンターをリセットします。 
4. アクションがリダブルの場合、パス以外の最後のアクションが相手のダブルであったことを確認します。 そうでない場合、シーケンスは無効です。 同様に状態を更新し、パスカウンターをリセットします。 
5. いずれかの時点でアクションがこれらの規則に違反した場合、当社は直ちに無効とします。 
6. すべてのアクションを処理した後、有効な終了条件に達したかどうかを確認します。 そうでない場合、シーケンスは不完全であるため無効です。 

重要な不変条件は、保存された状態が、次の手を検証するために必要な最小限の情報、つまり現在の最高入札額、最後の意味のあるアクションの ID とタイプを正確に表すことです。 すべてのルールは歴史のこれら 2 つの側面にのみ依存するため、完全なシーケンスを再検討する必要はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

suit_rank = {'C': 0, 'D': 1, 'H': 2, 'S': 3, 'N': 4}

def parse_bid(b):
    # b like "2C" or "1N"
    level = int(b[0])
    suit = suit_rank[b[1]]
    return level, suit

def is_higher(a, b):
    # a > b?
    return a[0] > b[0] or (a[0] == b[0] and a[1] > b[1])

t = int(input())
for _ in range(t):
    arr = input().split()
    n = len(arr)

    player = 0

    last_bid = None
    last_bid_player = -1

    last_nonpass_type = None
    last_nonpass_player = -1

    pass_count = 0
    had_nonpass = False

    valid = True

    for x in arr:
        p = player
        player = (player + 1) % 4

        if x == 'P':
            pass_count += 1
            if had_nonpass and pass_count == 3:
                break
            continue

        had_nonpass = True

        if x == 'X':
            if last_nonpass_type != 'BID':
                valid = False
                break
            if last_nonpass_player == p:
                valid = False
                break
            last_nonpass_type = 'X'
            last_nonpass_player = p
            pass_count = 0
            continue

        if x == 'XX':
            if last_nonpass_type != 'X':
                valid = False
                break
            if last_nonpass_player == p:
                valid = False
                break
            last_nonpass_type = 'XX'
            last_nonpass_player = p
            pass_count = 0
            continue

        level, suit = parse_bid(x)

        if last_bid is not None:
            if not is_higher((level, suit), last_bid):
                valid = False
                break

        last_bid = (level, suit)
        last_bid_player = p

        last_nonpass_type = 'BID'
        last_nonpass_player = p
        pass_count = 0

    if not valid:
        print("NO")
        continue

    if had_nonpass and pass_count >= 3:
        print("YES")
    elif (not had_nonpass) and pass_count == 4:
        print("YES")
    else:
        print("NO")
```このコードは、前述のステート マシンを直接反映しています。 プレーヤーのインデックス作成により、正しいターン割り当てが保証されます。 入札比較では、レベルとスーツのランクに辞書順を使用します。 最後の非パスアクションは明示的に追跡されるため、ダブルおよびダブルの合法性はタイプと相手の所有権の両方に依存します。 意味のあるアクションが発生するたびにパス カウントがリセットされ、終了が正しく検出されるようになります。 

微妙な点として、終了はすべてのアクションの処理後にのみチェックされますが、オークションが完了すると、その後のアクションは有効性とは無関係であるため、連続する 3 つのパスでの早期中断が許可されます。 

## 実用的な例

 | 2 | P | 1 | 2 | ふ | た |

 4 回目のパスの後、「4 つの最初のパスすべて」のルールが満たされるため、出力は YES になります。 これにより、入札がなくてもまだ有効な完了したオークションであることが確認されます。 

ここで、「P P 1C P P P」を考えてみましょう。

 | 2 | P | 1 | - | 2 | ふ | た |

 ステップ 6 では、入札後に 3 回連続でパスがあり、オークションが完了します。 これは、最初の 2 つのパスは終了にカウントされないため、had_nonpass フラグが必要な理由を示しています。

 ## 特殊なケース

 純粋に通過するシーケンスは、入札を必要としない特別な終了ルールを示します。 アルゴリズムは、非パス アクションが見られない間に 4 つの連続したパスが発生したかどうかをチェックすることで、これを個別に処理します。 パス カウンタが 4 に達すると、条件は直ちに受け入れられます。 

最初の入札の前にパスが発生するシーケンスでは、実装が終了に向けて初期パスを誤ってカウントするかどうかをテストします。 コードでは、had_nonpass フラグにより​​、意味のあるアクションの後のパスのみが 3 パス ルールの対象となることが保証されるため、早期のパスによってオークションが途中で終了することはありません。 

Double および redouble 検証は、最後の非パス アクションのタイプと所有者の両方の追跡に依存します。 プレーヤーが自分のチームの入札直後にダブルを試みた場合、所有権チェックは失敗します。 このアルゴリズムは、現在のプレーヤー インデックスを last_nonpass_player と明示的に比較し、対戦相手のみがこれらのアクションをトリガーできるようにし、交互のパートナーシップ間で正確さを維持します。
