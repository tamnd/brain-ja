 ## 問題の理解

 キョウカが一定の順序で倒そうとする一連のボスが与えられます。 各ボス タイプは複数回出現する可能性があり、これらの出現は独立していません。後の「ラウンド」でボスが利用できるかどうかは、シーケンスの早い段階ですでに倒されているものによって決まります。 

重要なルールは、同じボスの前回の出現が倒され、さらにパラメータに関連付けられたグローバルな依存関係がある場合にのみ、繰り返されるボスが「再び利用可能」になるということです。`k`満足しています。 実際には、これにより階層化された制約が作成されます。同じ値の繰り返しの出現を独立して処理することはできず、出現間の間隔と依存関係を強制する隠れた構造が存在します。 

タスクは、これらの可用性の制約に違反することなく、指定された一連のボス戦を指定された順序で実行できるかどうかを判断することです。 

入力サイズが大きいため、合計`n`最大 400 万のテストケースにわたって。 これは、テスト ケースごとに線形以上の解、または発生回数がさらに悪い 2 次関数を超える解は失敗することを直ちに意味します。 各要素を償却 O(1) 時間または O(log n) 時間で処理するソリューションを強いられます。 

単純な解釈では、可用性ルールを明示的にシミュレートし、ボスごとのラウンドと依存関係を追跡することになります。 そのためには、以前の発生を繰り返しスキャンしたり、複雑な状態遷移を維持したりする必要があり、単一のボスが何度も出現する敵対的なケースでは O(n²) の動作になる危険性があります。 

ボスが大きなギャップを持って繰り返し出現する場合、微妙なエッジケースが発生します。 たとえば、同じ値が 1 つおきに繰り返される場合、過去の構造に基づいて適格性を再計算する単純なシミュレーションでは、長い依存関係チェーンが繰り返し再検討され、深刻なパフォーマンスの問題が発生する可能性があります。 別のエッジケースが発生するのは次の場合です。`k`に比べて大きいです`n`これにより、グローバル制約が事実上非アクティブになり、常にトリガーされると想定する実装の誤解を招く可能性があります。

 最初の直感は、プロセスを直接シミュレートすることです。 私たちは、ボスのタイプごとに、以前の出現が倒されたかどうかを維持し、また、グローバルな制約が以下に基づいているかどうかを追跡しようとします。`k`満足しています。 すべての新しい要素について、これらのルールに基づいて現在「利用可能」であるかどうかを確認します。 

ルールは以前の出現と固定オフセットにのみ依存するため、これは概念的に機能します。`k`。 ただし、障害点はパフォーマンスにあります。ボスを処理するたびに、その最後に発生したことを推論し、以前のセグメント全体に制約を伝播する必要がある場合があります。 最悪の場合、単一のボスが O(n) 回出現し、逆方向にスキャンしたり出現ごとの依存関係チェーンを維持したりする単純なブックキーピングでは O(n²) 回の動作が発生します。 

重要な観察は、実際には完全な依存関係グラフを再構築する必要がないということです。 各ボスの実現可能性は、その最新の発生と限られた量の履歴にのみ依存します。 ラウンドをシミュレートする代わりに、ボス タイプごとに必要な最小限の状態と、それによって暗示されるグローバル ウィンドウ制約を追跡します。`k`。 これにより、要素ごとに少量の一定量の情報を維持し、それを O(1) 時間で更新するという問題が軽減されます。

 ## アルゴリズムのチュートリアル

 この制約は、同じボスの繰り返しの出現がその最新の位置と、それに関連付けられたグローバルな間隔条件によってのみ制御されることを強制するものであると解釈します。`k`。 

配列またはハッシュマップを維持します`last`、 どこ`last[x]`どのボスの最新のインデックスを保存しますか`x`現れた。 

また、ボスを再び見たときに、その以前の出現が必要な構造と互換性があることを確認する簡単な有効性チェックも維持します。 重要なのは、現在の位置と比較するだけであるということです。`last[x]`そしておそらくは、以下から導出されるグローバルしきい値に対して`k`。 

### ステップ

 1. 辞書を初期化する`last`すべての値を に設定すると、`-1`、つまりボスがまだ登場していないことを意味します。 これは、すべてのボスが最初はシーケンス内で「新鮮」であることを表します。 
2. シーケンスを左から右に繰り返します。 それぞれのポジションで`i`、現在の上司のタイプを考慮してください。`x = a[i]`。 
3. もし`x`これまでに登場したことはありません、記録します`last[x] = i`そして続けます。 最初の出現を検証するための依存関係はありません。 
4. もし`x`以前に出現した場合は、次のギャップがあるかどうかを確認してください。`i`そして`last[x]`によって引き起こされる制約と一致します。`k`。 このギャップが許容される構造に違反する場合、シーケンスは不可能であると即座に結論付けます。 
5. 制約が満たされる場合は、更新します。`last[x] = i`そして処理を続行します。 
6. シーケンス全体が違反なく処理された場合は、YES を出力します。 

これが機能する理由は、繰り返されるボスに関係するすべての制約が、連続するボス間の関係に崩壊するためです。 以前の出現に関係する制約は、最後の出現まで推移的にすでに適用されているため、最後の出現以降の古い出現を追跡することに利点はありません。 

### なぜ効果があるのか

 アルゴリズムは、すべてのボス タイプに対して、次の不変条件を維持します。`last[x]`常に、以前のすべての制約と一致する最新の有効な出現を表します。 実現可能性の違反は、新しい出来事が以前のものと比較して無効なギャップを「橋渡し」しようとした瞬間に現れるはずです。 すべてのより深い履歴はすでに最後の有効な位置にエンコードされているため、最初にこの不変条件を破らなければ、後で隠れた競合が導入されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n, m, k = map(int, input().split())
        a = list(map(int, input().split()))
        
        last = [-1] * (m + 1)
        
        ok = True
        
        for i, x in enumerate(a):
            if last[x] != -1:
                # check consistency of repeat occurrence
                # derived condition: repeated structure must not violate spacing
                if i - last[x] <= k:
                    ok = False
                    break
            last[x] = i
        
        out.append("YES" if ok else "NO")
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()

重要な部分は条件です`i - last[x] <= k`。 これは、繰り返し発生する間隔が近すぎると依存関係ルールに違反するという考えをコード化しています。 この条件が失敗すると、後で修正することはできないため、早期に停止します。

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    input = sys.stdin.readline

    res = []

 重要なエッジケースの 1 つは次のような場合です。`k`に比べて非常に大きいです`n`。 この状況での状態は、`i - last[x] <= k`決してトリガーされず、すべてのシーケンスが有効になります。 アルゴリズムはこれを自然に処理します。`last[x]`比較では常に、次の範囲内で小さな違いが生じます。`n`。
