 ## 解決策
 ## 問題の理解

 毎日、ある程度の数のゴミユニットが生成され、すべてのユニットは、ゴミが発生した日または翌日に廃棄する必要があります。 廃棄はユニットを袋に詰めることによって行われ、各袋は一定の容量まで保持できます。$k$、準備したその日にすぐに袋を空にします。 目標は、使用される袋の総数が最小限に抑えられるように、ゴミを最長 1 日で運び、袋にグループ化する方法をスケジュールすることです。 

重要な制約は、ガベージの有効期間が非常に短く、最大でも連続 2 日間しか利用できないことです。 これにより、グローバルなスケジュールの問題ではなく、隣接する日の間にローカルな相互作用が生じます。 出力は、これらの隣接制約の下ですべてのユニットをカバーするために必要な、容量が制限されたグループの最小数にすぎません。 

入力サイズが到達しました$2 \cdot 10^5$したがって、すべての日のペア間の割り当てをシミュレートしようとする二次戦略は遅すぎます。 実行可能なアプローチは線形または線形に近いものだけです。$10^8$Python C のような効率性では、単純な操作は 3 秒が安全な上限であり、Python のオーバーヘッドにより、これに近づくことができます。$10^7$意味のある操作。 

袋の容量を無駄にしないためにゴミの処理を延期する必要がある場合、微妙なエッジケースが発生します。 たとえば、ある日の量が少なく、次の日の量が多い場合、単純に毎日別々に梱包すると容量が無駄になる可能性がありますが、許容範囲内で単位を前後に移動すると袋の数を減らすことができます。 

最終日に別の特殊なケースが発生します。 当日出たゴミ$n$これ以上延期することはできないため、将来のバランス調整能力を暗黙的に想定する戦略は、境界を慎重に処理する必要があります。 

## アプローチ

 強引なアイデアは、考えられるすべての決定をシミュレートすることです。毎日、翌日に保管するユニットの数とすぐに処分するユニットの数を決定し、すべての配布を袋に入れてみるというものです。 これには、各ユニットを 2 日のうちの 1 日に割り当てることができ、毎日をバッグにグループ化することで別の組み合わせレイヤーが導入されるため、非常に多くの構成を検討する必要があります。 たとえ残りのユニットに対する日々の動的計画法に限定したとしても、状態空間は最大でキャリー値の可能性を伴って拡大します。$k$、トランジションを行う$O(nk)$、次の場合には大きすぎます。$k$までです$10^9$。 

構造の単純化は、個々のユニットを明示的にシミュレートする必要がないことに気づいたことから来ています。 重要なのは1日何単位かです$i$日に延期される$i+1$、日からユニットを延期したため$i$日と一緒に処理する必要があります$i+1$。 繰り越される単位の数が決まると、その日の残りの決定が決定的になります。単にカウントを最小限に抑えるために貪欲にバッグを埋めるだけです。 

貪欲な洞察の中心は、毎日、前日の残りのユニットと現在のユニットを組み合わせることで、容量を最大限に再利用したいということです。 個々の割り当てを追跡する代わりに、毎日の開始時にまだ「保留中」になっているユニットの数を追跡し、ローカルで手荷物数を最小限に抑えるために翌日に延期する必要がある追加のユニットの数を計算します。 

これにより、問題は、未処理のキャリーオーバー ガベージを表す単純な状態変数を使用した単一の左から右へのパスに縮小されます。

 ## アルゴリズムのチュートリアル

 新しいゴミと前日の残り物を含め、その日に梱包できるゴミの数を維持しながら、日順に処理します。 

1. 変数を初期化する`carry`前日から延期されたゴミを表す0を初期化します。`ans`使用するバッグの数を 0 にします。 
2. 毎日について$i$、 追加$a_i$に`carry`、新しく生成されたすべてのゴミは今日か明日のいずれかに利用できるようになるためです。 
3. 利用可能なすべてのゴミを使って、今日何袋の袋を作ることができるかを計算します。 各バッグには次の容量が入ります$k$ユニットなので、完成できるバッグの数は`carry`は`carry // k`。 この値を答えに加えて減らします`carry`したがって、モジュロを使用して$k$。 
4. 残りの部分`carry`満杯のバッグを形成した後は、今日バッグ全体を満たすことができない残りのユニットを表します。 これらの残り物は、次の日のゴミと合わせるか、翌日には完成するため、そのまま保管しておきます。 
5. 次の日に移動する前に、残り物が合理的に処理できる量を超えていないことを確認してください。 各ユニットは最大 1 日しか進められないため、残ったものは自動的に繰り越しとして有効になります。 
6. 処理日後$n$、残りすべて`carry`最終日に処分しなければなりません。 追加`carry // k`もう一度答えに。 

正確かどうかは、その日に部分的なバッグがあれば、利用可能なユニットを使用してできるだけ早く完了する必要があるという事実にかかっています。完了を遅らせても容量は増えませんが、ペアリングの機会を失うリスクがあるためです。 

### なぜ効果があるのか

 日の境界では、残りのすべてのユニットは次の日のみと対話でき、それ以降は対話できません。 したがって、局所的に最適な戦略は、常にできるだけ多くの満杯のバッグをすぐに埋めることです。満杯のバッグの形成を延期するグループ化では、1 日を超えて将来のペアリングの可能性を向上させることはできないからです。 不変条件は、処理後の日です。$i$、残りのユニットはすべて、まさに日が経つまでに再検討する必要があるユニットです。$i+1$、完成したすべてのバッグは、そのプレフィックスに対して最適に固定されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))

    carry = 0
    ans = 0

    for x in a:
        carry += x
        ans += carry // k
        carry %= k

    ans += carry // k
    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、利用可能なガベージ ユニットの実行中のプールを維持し、各ステップで満杯の袋を貪欲に抽出します。 整数除算は、現在の可用性から形成できる完全なバッグの数を正確に取得し、モジュロは翌日にやり取りする必要がある残りのユニットのみを保持します。 最後の追加は、最終日のクリーンアップを処理します。 

微妙な点は、翌日に移動する単位の数を明示的に決定することはないということです。 これは、完全なグループを形成した後の残りの部分で暗黙的にエンコードされます。残りの部分だけが将来の組み合わせから恩恵を受けることができるため、これで十分です。

 ## 特殊なケース

 1 日未満の場合$k$入力などの単位`1 10 / 3`、アルゴリズムセット`carry = 3`、反復中に満杯のバッグが計算されず、最後のキャリーは破棄されます。`3 // 10 = 0`、正しく 0 を生成します。 その正しさは、延期は不可能であるため、完全なバッグ形成に関してすべてのユニットが未使用のままでなければならないという事実から来ています。 

まったく同じ 1 日については、$k$、 のような`1 10 / 10`、アルゴリズムはちょうど 1 つのバッグを形成します。`carry // k = 1`そしてキャリーをゼロに減らします。 これにより、各ステップで満杯のバッグを貪欲に抽出することで、特別なケーシングを必要とせずに正確に適合するシナリオが正しく処理されることが確認されます。
