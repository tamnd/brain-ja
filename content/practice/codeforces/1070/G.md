 ## 解決策
 ## 問題の理解

 長さのある 1 次元のボードが与えられます$n$。 各セルには、ある程度の HP を持つモンスター、HP を増加させるポーション、または空のセルを含めることができます。 さらに、$m$ヒーローは最初に個別の空のセルに配置され、各ヒーローは独自の HP から始まります。 

集合点として単一のセルを選択する必要があります。 次に、ヒーローを順番に 1 人ずつそのセルに送ります。 主人公は独特の直線的な道を一マス一マス歩いていきます。 移動しながらポーションを収集し、途中で遭遇するモンスターと戦うこともあります。 ポーションはすぐに消費されて HP が増加します。ヒーローの現在の HP がモンスターの HP 以上である場合、モンスターは倒されます。そうでない場合、ヒーローは死亡し、設定全体が無効になります。 ヒーローが生き残った場合、モンスターは将来のすべてのヒーローから消えます。 

重要な難点は、初期のヒーローは、相互作用するモンスターやポーションを削除することでボードを永続的に変更するため、ヒーローの順序が重要になることです。 

目標は、すべてのヒーローが安全に到着できるように、集合ポイントとヒーローの順序を見つけることです。 

制約$n \le 100$そして$m \le n$ことを示します$O(n^2)$または$O(n^2 \log n)$解決策は受け入れられます。 ヒーローのすべての組み合わせを試したり、候補ごとに完全なシミュレーションを再計算したりすると、時間がかかりすぎます。 

素朴だが自然なアイデアは、ラリー ポイントを固定し、ヒーローのすべてのオーダーを試し、それぞれをシミュレートすることです。 つまり$m!$ラリーポイントごとの順列と各シミュレーションは次のようになります。$O(n)$、これはたとえ$m = 10$。 

2 番目の単純なアイデアは、各集結ポイントの入力順序でヒーローを貪欲にシミュレートすることです。 これは失敗します。最適な順序は、どのヒーローがモンスターを早期に安全に排除するのに十分強いかに依存するためです。 

微妙なエッジケースは、ヒーローが別のヒーローによってのみ除去できるモンスターを追い越さなければならないときに、その別のヒーローが集合地点の反対側にいる場合に発生します。 欲張りな左から右または右から左の順序付けは、有効な解決策が存在する場合でも失敗する可能性があります。 

## アプローチ

 重要な観察は、固定されたラリー ポイントの場合、各ヒーローが開始点とラリー ポイントの間のセグメントに決定的な影響を与えるということです。 ヒーローの順序がわかれば、弱いヒーローが同じルートを試みる前に、どのヒーローがモンスターを「一掃」できるかを効果的に決定できます。 

重要な単純化は、視点を逆転させることです。ヒーロー間の動的な相互作用について考える代わりに、残りの障害物の固定セットを前提として、各ヒーローが集合地点まで横断できるかどうかを計算し、徐々に道を容易にする順序を求めます。 

固定の集合ポイントでは、各ヒーローは「安全要件」を引き起こします。つまり、そのパスに沿って累積 HP が 1 を下回ってはなりません。これは、モンスターをマイナスの貢献、ポーションをプラスの貢献とみなして、そのパスに必要な最小の初期 HP を計算するのと同じですが、モンスターは以前のヒーローによって殺された後に消滅するというひねりが加えられています。 

これは、貪欲なスケジュール解釈につながります。 各ヒーローには、生き残るためにどれだけの「バッファー」が必要かを表す値を割り当てることができます。 より小さなバッファーで生き残ることができるヒーローはより柔軟であり、より強力なヒーローによってボードが部分的に改善された後でも生き残る可能性が高いため、通常は後から行く必要があります。 

正しい戦略は、各ヒーローと各候補ラリー ポイントについて、そのヒーローが残りの未処理のヒーローの中で最初に進むと仮定して、そのヒーローがラリー ポイントに到達できるかどうかを事前計算することです。 次に、現在実行可能なヒーローを繰り返し選択することで貪欲に順序を選択し、そのヒーローが道を切り開くかのように状態を更新します。 

私たちはすべてのラリーポイントを試します。 それぞれについて、生きているヒーローの複数のセットを維持し、現在旅を生き残ることができるヒーローを繰り返し選択します。 ある段階で実行可能なヒーローがいない場合、この集結ポイントは失敗します。 

これが機能するのは、ヒーローが横断に成功すると、モンスターを除去しポーションを消費することでボードを改善するだけであり、今後の道が難しくなることはないからです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース順列 |$O(n \cdot m!)$|$O(n)$| 遅すぎる |
 | 各ラリーを試す + 実現可能性を貪欲に注文 |$O(n^3)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 ラリーポイントを修正$r$。 左側と右側を独立して扱いますが、同じロジックが対称的に適用されます。 

1. 各ヒーローについて、そのパスへの最初の最終的な効果を計算します。$r$。 歩き始めから歩き始めるまでをシミュレーションします。$r$、モンスターとポーションを収集しますが、これは以前のヒーローがボードを変更していないという仮定の下で実現可能性を判断するためにのみ使用されます。 
2. ボードの現在の状態について、関数を定義します。`can(hero)`これは、主人公の移動をシミュレートし、その HP がゼロを下回らないかどうかをチェックします。 このシミュレーションは、$O(n)$。 
3. 未使用のヒーローのセットを維持します。 
4. 未使用のヒーローをすべて繰り返しスキャンし、満足するヒーローを見つけます。`can(hero)`。 
5. 実行可能なヒーローが見つかったら、その完全な移動をボード上で永続的にシミュレートし、モンスターと消費したポーションを削除し、使用済みとしてマークします。 
6. 主人公を回答順に追加します。 
7. ある繰り返しで、使用されていないヒーローが実行可能でない場合は、この集結ポイントを中止します。 
8. すべてのヒーローが正常に配置されたら、この集合ポイントと順序を出力します。 

明らかでない部分は、貪欲な選択を繰り返すことがなぜ有効なのかということです。 その理由は、ヒーロー間の唯一の交流は障害物の除去によるものだからです。 障害物の除去は HP を増加させるか、将来のパスに沿ったダメージを軽減することしかできないため、現在実行可能なヒーローは、他のヒーローが行動した後も引き続き実行可能です。 

### なぜ効果があるのか

 いつでも、ボードにはアクティブな障害物のサブセットが反映されます。 ヒーローの横断結果は、障害物の除去に関しては単調です。モンスターを除去したり、以前のポーションによって HP を追加したりしても、以前は実行可能だったパスが実行不可能になることはありません。 したがって、ある段階でヒーローが実現可能になったら、それを選択しても将来の解決策を妨げることはできません。 解決策が存在する場合、まだ配置されていないヒーローの中に、実行可能なヒーローが常に少なくとも 1 人存在します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def simulate(hero_start, hero_hp, board, r):
    n = len(board)
    hp = hero_hp
    pos = hero_start

    step = 1 if r > pos else -1
    i = pos

    while i != r:
        i += step
        cell = board[i]

        if cell < 0:
            hp += cell  # monster: subtract
            if hp < 0:
                return False
            board[i] = 0
        elif cell > 0:
            hp += cell
            board[i] = 0

    return True

def can(hero_start, hero_hp, board, r):
    hp = hero_hp
    i = hero_start
    step = 1 if r > i else -1

    while i != r:
        i += step
        cell = board[i]
        if cell < 0:
            hp += cell
            if hp < 0:
                return False
        elif cell > 0:
            hp += cell
    return True

n, m = map(int, input().split())

heroes = []
for _ in range(m):
    s, h = map(int, input().split())
    heroes.append((s - 1, h))

board = list(map(int, input().split()))

for r in range(n):
    b = board[:]
    used = [False] * m
    order = []

    ok = True

    for _ in range(m):
        found = -1

        for i in range(m):
            if used[i]:
                continue
            s, h = heroes[i]
            if can(s, h, b, r):
                found = i
                break

        if found == -1:
            ok = False
            break

        s, h = heroes[found]
        if not simulate(s, h, b, r):
            ok = False
            break

        used[found] = True
        order.append(found + 1)

    if ok:
        print(r + 1)
        print(*order)
        break

の`can`この関数は、ボードの現在の状態を考慮してヒーローが変更せずに生き残るかどうかをチェックします。 の`simulate`関数は同じ走査を実行しますが、消費されたモンスターとポーションも削除します。 

微妙な点は、両方の関数がパス全体を毎回再計算することですが、これは許容できる理由です。$n \le 100$そして私たちはせいぜいこれを行います$O(n^2)$ラリーポイントあたりの回。 

貪欲な選択ループは、現在生き残ることができるヒーローを選択しようとします。 正確かどうかは、ボードがきれいになるにつれて実現可能性が高まるという事実に依存します。

 ## 特殊なケース

 すべてのヒーローが重いモンスターの同じ側からスタートする場合、重要なエッジケースが 1 つ発生します。 最初に選択したヒーローが十分に強くない場合、貪欲な選択は行き詰まっているように見える可能性があります。 ただし、有効な構成では、少なくとも 1 人のヒーローが現在のボード状態を通過できる必要があります。そうでない場合、その集合点に対する解決策は存在しません。 シミュレーションにより、実行可能なヒーローのみが選択されることが保証されるため、アルゴリズムが解決可能な配置を誤って破棄することはありません。 

もう 1 つのエッジケースは、ポーションがモンスターのすぐ隣にある場合です。 弱いヒーローは、最初にポーションを消費しないと失敗する可能性があります。 ポーションは遭遇するとすぐに適用されるため、その後の戦闘の前に HP が増加するため、シミュレーションではこれが正しく説明されています。 

最後に、集結地点がモンスターの密集地帯の中にある場合、初期のヒーローは後のヒーローが再利用する道を空けなければならない可能性があります。 単調なクリア特性により、モンスターが一度除去されると、それが存在しないことによって将来失敗が引き起こされることがないことが保証され、貪欲なプロセスの一貫性が保証されます。
