 ## 解決策
 ## 問題の理解

 私たちに与えられたタイムラインは、`n`日々。 企業は毎日、次のことを行う必要があります。`k`CPU コアですが、固定パッケージを購入する代わりに、複数の重複するレンタル オファーからコアをレンタルできます。 各オファーは連続した日間隔でのみアクティブになり、アクティブな日ごとに最大で`c_i`コア。 その日にそのオファーからレンタルされるコアはすべて料金がかかります`p_i`。 

毎日、各アクティブなオファーから取得するコアの数を選択します。 すべてのアクティブなオファーの合計利用可能容量が少なくとも`k`、私たちはただ取るだけです`k`それ以外の場合は、利用可能なものはすべて採用し、需要が完全に満たされていないことを受け入れます。 目標は、一日を通しての総コストを最小限に抑えることです。 

主な問題点は、オファーが時間的に重複することですが、決定はその日ごとにローカルで行われます。毎日、利用可能な最も安価なコアを最初に選択し、最大で`k`。 

制約は私たちを`O((n + m) log m)`または`O(n log m)`解決。 と`n`100万までと`m`最大 20 万件の場合、すべてのアクティブなオファーに対する 1 日あたりの並べ替えやスキャンは遅すぎます。 平`O(nm)`2e11作戦に到達してしまうため、不可能です。 

単純な間違いは、最良のものを再計算することです`k`すべてのアクティブなオファーを収集し、価格順に並べ替えることで、毎日コアを収集します。 それはそうでしょう`O(n m log m)`最悪の場合。 

もう 1 つの微妙なエッジケースは、高価なオファーが早期に表示され、安価なオファーが後から開始される場合に発生します。 価格順のグローバル構造を維持しないと、より安価なコアが入手可能になるのを待たずに、誤って高価なコアを早期に購入してしまう可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、毎日を独立して処理します。 特定の日について、その日を含む間隔のすべてのオファーを収集し、価格順に並べ替えて、到達するまで貪欲にコアを取得します。`k`。 これは正しいです。1 日以内であれば、常に安価なコアが優先されるはずです。 ただし、1 日あたりのアクティブなオファーを再計算するにはコストがかかります。 すべてのオファーが一日にまたがる最悪の場合、繰り返し並べ替えることになります。`m`のアイテム`n`日々、与える`O(n m log m)`限界をはるかに超えた複雑さ。 

重要な観察は、可用性は時間の経過とともに変化しますが、決定ルールは静的であり、常に最も安価な利用可能なコアを最初に選択するということです。 これは、現在アクティブなオファーを価格順に並べたグローバル構造を維持し、間隔の開始と終了に合わせて更新することを示唆しています。 時間の経過に伴うスイープ ラインと、最も安価な容量の挿入、削除、抽出をサポートするデータ構造を使用して、日を順番に処理できます。 

主な課題は、各オファーに容量制限があることです`c_i`1日あたり、部分的に使用する場合があります。 価格順に並べられたマルチセットのような構造で残りの容量を追跡する必要があります。 毎日、私たちは利用可能な最も安いオファーから、いずれかに達するまで繰り返し消費します。`k`または排気供給。 

遅延削除と組み合わせたヒープや価格値に対するセグメント ツリーなどのバランスの取れた構造を使用して、アクティブなオファーをモデル化できます。 一般的な CF ソリューションは、イベントを処理し、価格ごとに複数セットの容量を維持することによって圧縮し、常に最低価格のバケットから最初に消費します。

 | 最適なスイープ + マルチセット | O((n + m) log m) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 日から時間を処理します`1`今日`n`価格順に並べ替えられたすべてのアクティブなオファーを維持しながら。 

1. 各オファーを 2 つのイベントに変換します: 日`l_i`活動的になり、日中は`r_i + 1`非アクティブになります。 これにより、毎日最初から再計算するのではなく、アクティブな容量を段階的に更新できるようになります。 すべてのオファーを毎日再確認すると時間がかかりすぎるため、これが必要です。 
2. すべてのアクティブなオファーのうち、その価格で利用可能な合計容量を保存する、価格をキーとした構造を維持します。 オファーがアクティブになると、`c_i`その価格バケットに。 有効期限が切れたら、それを差し引きます。 
3. 毎日、最も安い価格のバケットから、いずれかが回収されるまで繰り返し取得します。`k`コアが残っているか、容量が残っていない。 より安価なバケットが存在する間により高価なバケットから取り出されたユニットは、コストを削減するために置き換えることができるため、常に安価な価格を最初に使い果たします。 
4. 容量を消費するにつれてコストが蓄積されます。 取るとき`x`価格からのコア`p`、追加します`x * p`答えに。 
5. 現在の構成のすべての消費を処理した後、翌日に進みます。 

### なぜ効果があるのか

 決まった日に、問題は次のことを選択することになります。`k`各容量の単位の重量（価格）が固定されており、総コストを最小限に抑えたいアイテム。 これは、すべてのアイテムがユニット コアに分割できるフラクショナル ナップザックに相当します。 アクティブ化間隔を除いて日の間に結合はないため、日ごとに独立して正確さを維持するだけで十分です。 不変条件は、毎日の開始時に、アクティブなオファーの利用可能なすべての容量が構造に正確に含まれており、価格を上げて貪欲に消費することで常にその日に最適な選択肢が得られるということです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k, m = map(int, input().split())

    add = [[] for _ in range(n + 2)]
    rem = [[] for _ in range(n + 2)]

    for _ in range(m):
        l, r, c, p = map(int, input().split())
        add[l].append((p, c))
        rem[r + 1].append((p, c))

    import heapq

    active = {}
    heap = []

    def add_offer(p, c):
        active[p] = active.get(p, 0) + c
        heapq.heappush(heap, p)

    def remove_offer(p, c):
        active[p] -= c
        if active[p] == 0:
            del active[p]

    ans = 0

    for day in range(1, n + 1):
        for p, c in add[day]:
            add_offer(p, c)

        for p, c in rem[day]:
            remove_offer(p, c)

        need = k

        while need > 0 and heap:
            p = heap[0]
            if p not in active:
                heapq.heappop(heap)
                continue

            avail = active[p]
            take = min(need, avail)
            ans += take * p
            need -= take

            if take == avail:
                heapq.heappop(heap)
                del active[p]
            else:
                active[p] -= take

    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションではイベント リストを使用します`add`そして`rem`毎日どのオファーが開始され、どのオファーが終了するかを管理します。 ヒープには候補価格が保存されます。 辞書`active`価格ごとの合計残り容量を保存します。 

複数のオファーの株価や容量が変化するため、ヒープには古いエントリが含まれる可能性があります。 したがって、最上位要素を使用する前に、それがまだ存在していることを確認します。`active`。 そうでない場合は、ゆっくりと破棄します。 

消費ロジックは常に最も安い価格から削除し、必要に応じてバケットを部分的に消費します。 

微妙な点は、個々のオファーを追跡することはなく、価格ごとの総容量のみを追跡することです。 同じ価格のすべてのユニットは交換可能であるため、これは有効です。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、オファーが 1 日だけにわたる場合です。 イベントベースの更新により、同じ反復内で正しく追加および削除されることが保証されます。 例えば：```
1 2 3 5
```1 日目にアクティブ化され、3 日目に削除されるため、1 日目と 2 日目にのみ影響します。add/rem リストは、特別なケースを使用せずにこれを保証します。 

もう 1 つのエッジケースは、同じ価格での複数のオファーです。 価格ごとに容量を集約するため、ロジックの分割が回避されます。 ヒープには重複した価格エントリが含まれる可能性がありますが、遅延削除により正確さが保証されます。 

最後のエッジケースは、総容量が以下の場合です。`k`。 ヒープが空になるとループが停止し、完全な割り当てを強制することなく、使用可能なコアのみが正しく蓄積されます。
