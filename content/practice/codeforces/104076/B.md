 ## 解決策
 ## 問題の理解

 狭い洞窟を決められた順番で歩く二人。 先頭のパンは常に先行しており、2 番目のショウはスタート時にちょうど 1 ユニット後ろに続きます。 どちらも離散的な時間ステップで前進しますが、トーチが現在燃えている場合は 1 秒でしか移動できません。 トーチの燃料がなくなると、所有者は立ち止まって一定秒間燃料を補給する必要があり、その間は歩くことができません。 重要なのは、トーチに早期に燃料を補給することはできないということです。 燃料補給を開始する前に完全に燃え尽きる必要があります。 

各秒には厳密な順序があります。トーチが点灯している場合はパンが最初に移動し、トーチが点灯している場合はショウが移動しようとします。 パンは常に前を走り、追い越しを阻止するため、ショウの動きは、最初のオフセットを超えた空間的な相互作用ではなく、彼自身の聖火のスケジュールによって制限されます。 

クエリ時間 qi ごとに、両方のウォーカーが貪欲に行動する、つまり松明が許すたびに歩くと仮定して、ショウが開始位置からどれだけ移動したかを尋ねます。 

中心的な問題は、動きが連続的または独立していないことです。 各人は固定長の「燃焼フェーズ」と固定長の「給油フェーズ」を交互に繰り返し、これらのフェーズは以前の消費量に応じて時間の経過とともに変化します。 システムは決定的ですが周期的であり、クエリは最大 10^16 まで非常に大きくなる可能性があるため、1 秒あたりの直接シミュレーションは不可能です。 

制約により、この構造が明確になります。 テスト ケースは最大 10^5 まで存在できますが、すべてのサイクル パラメーターとクエリの合計は 10^6 に制限されます。 これは、どのソリューションも線形時間でテスト ケースごとに前処理し、定数時間または対数時間で各クエリに応答する必要があることを強く示唆しています。 qi が 10^16 に達する可能性があるため、qi を経て反復されるものは直ちに実行不可能になります。 

微妙なエッジ ケースが初期条件から発生します。両方のトーチは時間 0 ですでに燃料が補給されています。 これは、両方がフル容量で燃焼フェーズで開始することを意味します。 もう 1 つの明白ではない点は、各秒内の厳密な順序付けです。Pang は Shou の前に移動します。これは、単純なシミュレーションで同期が重要になるエッジ ケースで Shou の移動が「許可される」かどうかに影響する可能性があります。 ただし、Shou の動きは Pang に影響を与えず、その逆も同様であるため、順序が問題になるのは、位置依存のブロックを誤ってシミュレートしようとした場合のみです。 

最後のエッジケースは、トーチが 1 秒間燃焼するか、1 秒間燃料を補給する場合です。 このような場合、慎重なモジュラー演算を行わずに連続間隔を仮定すると、単純なサイクル検出によって位相境界がずれてしまう可能性があります。 

## アプローチ

 強引な解釈は簡単です。 私たちは 1 秒ごとにシミュレーションを行い、現在の燃焼フェーズが何秒残っているか、および燃料を補給しているかどうかを両方の人について追跡します。 各ステップでは、燃料または給油タイマーが減少し、可能であれば位置が増加します。 これは文字通りルールに従っているので正しいです。 ただし、各クエリは最大 10^16 になる可能性があるため、秒ごとにシミュレーションすることは不可能です。 クエリ全体でシミュレーションを再利用したとしても、1 つのテスト ケースで 10^16 のオーダーの操作が必要になる可能性があります。 

重要な観察は、各人が独立して定期的に行動しているということです。 各トーチのパターンは固定サイクルです。1 秒間燃焼し、b 秒間燃料を補給し、これを繰り返します。 書き込み中、1 秒あたり正確に 1 単位の距離が増加します。 給油中は動きません。 したがって、問題は、長さ q のプレフィックス内に「アクティブ秒」（燃焼秒数）が何秒発生するかをカウントすることに帰着します。 

各人について、長さ (a + b) の繰り返しブロックとしてタイムラインをモデル化できます。 各完全なサイクルで、正確に 1 ステップ移動します。 長い時間 q に対して、完全なサイクルがいくつ適合するかを計算し、残りの部分サイクルを処理します。 これにより、彼らが歩いている合計秒数が得られます。

唯一の微妙な点は、パンのスケジュールがショウの邪魔になるかどうかです。 ショウの動きは自分のトーチの状態と追い越せないというルールのみに依存するため、ショウの移動能力には影響しません。 パンは常に最初に動き、先を行くため、ショウの制約は、パンの正確なタイミングとは関係なく、「松明が燃えているときはいつでもショウが動く」という制約になります。 したがって、ショウを単独で治療することができます。 

これにより、前処理後の各クエリは単純な算術計算に減ります。

 | ブルートフォースシミュレーション | O(∑q) | お(1) | 遅すぎる |
 | 循環演算 | クエリごとに O(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ショウの動作モデル

 1. Shou のトーチ スケジュールを長さ a2 + b2 の繰り返しサイクルとして扱います。 

各サイクルの最初の a2 秒間は、1 秒あたり 1 ユニット移動します。 次の b2 秒間、彼は燃料を補給しているため動きません。 
2. クエリ時間 q について、q に収まる完全なサイクルの数を計算します。 

これは q // (a2 + b2) です。 それぞれの完全なサイクルは、正確に 2 単位の動きに寄与します。 
3. q % (a2 + b2) を使用して、全サイクル後の残り時間を計算します。 

この残りのウィンドウは、燃焼段階の一部または燃料補給段階の一部を覆う場合があります。 
4. 答えに min(a2, 剰余) を追加します。 

残りが完全に燃焼セグメント内にある場合、Shou は残りのすべての秒数を提供します。 それ以外の場合、彼は燃焼部分のみを提供します。 
5. 総移動量を full_cycles * a2 + min(a2, 剰余) として出力します。 

### なぜ効果があるのか

 Shou の状態の進化は、彼の内部の周期的なトーチ サイクルのみに依存します。これは決定論的であり、位置や相互作用には依存しません。 タイムラインは固定構造の独立したサイクルに分割されており、各サイクル内での動きへの寄与は固定されています。 時間のプレフィックスは、完全なサイクルとサイクルのプレフィックスに一意に分解されるため、これらのばらばらの間隔にわたる寄与を合計すると、正確さが保たれます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []

    for _ in range(T):
        a1, b1, a2, b2, n = map(int, input().split())

        cycle = a2 + b2
        burn = a2

        for _ in range(n):
            q = int(input())

            full = q // cycle
            rem = q % cycle

            ans = full * burn + min(burn, rem)
            out.append(str(ans))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```Pang は Shou の移動回数に影響を与えないため、このソリューションでは Shou のパラメータのみが分離されます。 重要な計算は、時間を完全なサイクルと残りの部分に分割し、それぞれを燃焼秒数に変換することです。 

q は 10^16 までであるため、整数演算は安全ですが、Python はそれを自然に処理します。 高速入力と事前に蓄積された出力の使用により、最大 10^5 のテスト ケースにわたるオーバーヘッドが回避されます。 

## 実用的な例

 ### 例 1

 a2 = 3、b2 = 2、q = 11 とします。 

サイクルの長さは 5 です。 

| q | 全サイクル | 残り | 全額寄付 | 部分的な貢献 | 合計 |
 | --- | --- | --- | --- | --- | --- |
 | 11 | 2 | 1 | 2 * 3 = 6 | 1 | 7 |

 解釈によると、Shou は 11 秒で 2 つの完全な燃焼と燃料のサイクルを完了し、その後 1 秒間だけ燃焼が発生する新しいサイクルに入るということです。 

これにより、部分サイクルがシミュレーションなしで正しく処理されることが確認されます。 

### 例 2

 a2 = 4、b2 = 3、q = 20 とします。 

周期の長さは 7 です。 

| q | 全サイクル | 残り | 全額寄付 | 部分的な貢献 | 合計 |
 | --- | --- | --- | --- | --- | --- |
 | 20 | 2 | 6 | 2 * 4 = 8 | 4 | 12 |

 残りは燃焼時間を超えるため、燃焼部分のみが寄与します。 これにより、燃焼セグメントと燃料セグメントの間の境界全体の正確性がチェックされます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | テスト ケースあたり O(n) | 各クエリは算術 | を使用して一定時間で処理されます。 
| スペース | お(1) | 少数の変数のみが保存されます。 

この制約により、すべてのテスト ケースにわたって合計 10^6 までのクエリが許可されるため、線形合計処理で十分です。 各クエリは、制限内で少数の整数演算に減ります。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    T = int(input())
    out = []

    for _ in range(T):
        a1, b1, a2, b2, n = map(int, input().split())
        cycle = a2 + b2
        burn = a2

        for _ in range(n):
            q = int(input())
            full = q // cycle
            rem = q % cycle
            out.append(str(full * burn + min(burn, rem)))

    return "\n".join(out)

# minimum values

 ## 特殊なケース

 重要なエッジ ケースは、q がサイクル境界に正確に位置する場合です。 たとえば、a2 = 5 および b2 = 2 の場合、q = 7 では、剰余は 0 になります。 アルゴリズムは full_cycles * 5 + 0 を生成し、完全なサイクルを超えて部分的な書き込みが寄与していないことを正確に捕捉します。 

別のケースは、q が a2 より小さい場合です。 この状況では、full_cycles は 0 で、min(a2, q) は直接 q を返します。これは、Shou が常に燃焼フェーズにあり、毎秒移動することを意味します。 これにより、特別な分岐が必要なくなります。 

最後のケースは b2 = 0 の場合です。サイクルは純粋に燃焼するため、サイクル = a2 となり、毎秒運動に寄与します。 full_cycles * a2 + min(a2, 0) は直観と一致してきれいに q に単純化されるため、式は q に帰着します。
