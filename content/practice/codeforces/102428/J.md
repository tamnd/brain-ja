 ## 解決策
 ## 問題の理解

 左から右にインデックスが付けられた、異なる植物の高さの配列があります。 バッタはあるインデックスから開始し、左か右のどちらかを見ていきます。 現在立っている植物の高さよりも厳密に高さが大きい、その方向の最初のインデックスにジャンプします。 ジャンプが成功するたびに、方向が逆転します。 現在の方向に背の高い植物がなくなると、プロセスは終了します。 

配列は時間の経過とともに変化します。 更新により 1 つの植物の高さが増加しますが、目撃されるたびに現在の高さでバッタが到達する最終的な指標が求められます。 回答は記録の時系列順を尊重する必要があります。 

N,M≤2⋅10 5 の範囲により、観測ごとにすべてのジャンプを個別にシミュレートすることができなくなります。 単一の軌道には Θ(N) 個のジャンプが含まれる可能性があるため、2⋅10 5 の照準に対してそれを行うには、Θ(NM)=4⋅10 10 のジャンプ操作が必要になる可能性があります。 セグメント ツリーを使用して各ジャンプを見つけても、Θ(NMlogN) が残りますが、これは元の問題の 3 秒の制限をはるかに超えています。 元のコンテストでは、3 秒の制限と 1024 MB のメモリ制限が指定されています。 

最初のエッジ ケースは境界プラントです。 考慮する```
3 1
1 2 3
L 1
```バッタはすでに一番左の植物にいて、それ以上左を見ることができないので、答えは次のようになります。`1`。 無効なインデックスを使用して検索したり、すべての目撃情報が少なくとも 1 回ジャンプすると仮定したりする不注意な実装は、ここで失敗する可能性があります。 

2 番目の特殊なケースは、最初の背の高い植物が必ずしも隣接しているわけではないということです。 のために```
4 1
1 2 3 4
R 1
```植物 2 が最初の背の高い植物であるため、バッタは植物 1 から植物 2 に直接ジャンプします。 対照的に、```
4 1
1 5 2 3
R 3
```答えは`4`、 ない`2`、検索が右側に制限されており、プラント 2 が間違った側にあるためです。 

3 番目のエッジ ケースは、更新されたプラントをスキップするために使用されていたジャンプを変更する更新から発生します。 のために```
5 3
1 5 2 4 3
R 1
U 4 6
R 1
```最初の答えは`2`。 植物 4 が高さ 6 まで成長した後でも、答えは変わりません。`2`植物 2 が最初に検出され、すでに植物 1 よりも高いためです。最初の背の高い植物ではなく、最も背の高い植物を単純に検索する実装では、間違った結果が得られます。 

4 番目のエッジ ケースは、更新されたプラントがバッタの現在位置でない場合でも、更新によって将来のジャンプが変更される可能性があることです。 例えば、```
5 2
1 4 2 5 3
R 1
U 3 6
```最初のクエリはプラント 2 で停止します。更新後、他の場所で開始される今後のクエリでは、最初の背の高いプラントとしてプラント 3 が検出される可能性があります。 データ構造は、クエリに直接表示される植物だけでなく、現在の高さの順序を表す必要があります。 

## アプローチ

 直接的なアプローチは、バッタの行動を正確にシミュレートすることです。 現在の位置から、より高い植物が見つかるまで現在の方向にスキャンし、そこに移動し、方向を反転して続行します。 範囲最大セグメント ツリーは、値が現在の高さを超える最初の位置を見つけることで、より高い植物の検索を O(logN) まで改善できます。 ただし、シミュレーションのジャンプ数は潜在的に線形のままです。 次のようなシーケンス```
7 5 3 1 2 4 6
```プラント 4 から開始し、最初に右に見るとプラント 4、5、3、6、2、7、1 にアクセスするため、1 つのクエリに実際には Θ(N) 個のジャンプが含まれる可能性があります。 

有用な構造観察は、成功したすべてのジャンプが厳密に高い植物に向かうということです。 より具体的には、i から右にジャンプした後、厳密に i と目的地の間にあるすべての植物の高さは目的地よりも小さくなります。 次の左ジャンプでは、i と前の目的地の間にあるすべての植物がすでに前の目的地よりも小さいため、新しい目的地は厳密に i の左側になければなりません。 同じ議論が繰り返されます。 

したがって、訪問位置は間隔を広げます。 現在のプラントは常に、その間隔内で最も高いプラントになります。 次のジャンプでは、その間隔の現在カバーされていない側のみが検索されます。 これにより、軌道は、配列の最近接と上位の関係を通るウォークに変わります。 

固定配列の場合、これらの関係は最大デカルト ツリーで表すことができます。 各植物のどちらかの側に最も近いより大きな植物は、その木の祖先です。 したがって、バッタは、左右の祖先を交互にデカルト ツリーの中を上向きに移動します。 したがって、静的問題全体は、最近接より大きな構造を構築した後、線形時間で解決できます。 

難点はアップデートです。 ポイントを増やすとデカルト ツリーが変更される可能性があるため、更新のたびにデカルト ツリーを再構築すると、やはり時間がかかりすぎます。 この動的バージョンを処理する標準的な方法は、更新のブロックでレコードを処理することです。 ブロックの先頭で、完全な静的ジャンプ構造を構築します。 ブロック中に変更されたプラントは O(B) 個だけです (B はブロック サイズです)。 クエリは、変更されたプラントの 1 つによって影響を受ける部分に到達するまで静的ジャンプ構造に従い、変更されたプラントは明示的に処理されます。 N の周りで B を選択すると、レコードあたりのコストのかかる操作の数が線形未満になります。 

以下の実装では、このアイデアのより直接的なバージョンが使用されています。 レコードのブロックごとに最近接最大ジャンプ構造を再構築し、ブロック内の変更を明示的に処理します。 静的構造ではバイナリ リフティングが使用されるため、影響を受けない軌道部分は対数時間でスキップされます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NM) | O(N) | 遅すぎる |
 | セグメントツリーシミュレーション | O(NMlogN) 最悪の場合 | O(N) | 遅すぎる |
 | 静的ジャンプ構造によるブロック分解 | O((N+M) N logN) | O(NlogN) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 時系列レコードを、約 B= M 個のレコードを含むブロックに分割します。 各ブロックの先頭では、現在の高さが固定されていると見なされます。 
2. 固定配列の場合、単調スタックを使用して、すべての位置の左側と右側で最も近い大きいプラントを計算します。 左ポインタは、H j >H i で最も近い位置 j<i であり、右ポインタは対称的に定義されます。 
3. すべてのプラントに 2 つの状態を作成します。 状態 (i,0) はバッタが i を見て左を向いていることを意味し、状態 (i,1) はバッタが右を向いていることを意味します。 状態の出力エッジは、まさにその方向に最も近いより大きなプラントであり、その後に方向が変わります。 
4. すべてのエッジは、厳密に高い高さの植物に接続されます。 したがって、状態グラフは非周期的になります。 高さの降順で状態を処理し、最終的な目的地を計算します。 状態に外向きのエッジがない場合、その状態自体が答えになります。 それ以外の場合、その答えは、目的地における反対方向の状態の既知の答えになります。 
5. これらの状態エッジを越えるバイナリ リフティングを構築します。`up[k][s]`は、状態 s から 2 k 回ジャンプした後に到達する状態を表します。 それとともに、リフトされたセグメント全体が現在のブロックにとって安全かどうか、つまりブロック内で変更されたプラントがいずれかのジャンプを妨げることができないかどうかを維持します。 
6. ブロックの読み取り中に、更新されたすべてのプラントを記録します。 これらのプラントのみが、ジャンプ構造の構築に使用される静的配列と異なります。 目撃情報に答えるときは、静的ジャンプ構造を使用して、軌道の影響を受けない部分をスキップします。 静的ジャンプを受け入れる前に、その検索間隔内にある変更されたプラントを確認してください。 それらの 1 つが現在のプラントよりも高く、静的な宛先より前に発生する場合、静的なエッジは無効になるため、現在の高さを使用してジャンプを直接シミュレートします。 
7. 直接ジャンプが変更されたプラントに到達したら、明示的に続行します。 ブロック内には変更されたプラントが最大 B 個あるため、例外的な決定の数はブロック サイズによって制限されます。 他のすべての部分は、事前に計算されたジャンプ構造を使用します。 
8. ブロックを処理した後、そのすべての更新を実際の高さの配列に適用し、次のブロックの静的な最近接最大構造を再構築します。 O(NlogN) かかるバイナリ リフティング テーブルを除けば、再構築は線形です。 

機能する理由: 静的構造は、現在のブロックの影響を受けていないすべてのプラントに対して正確です。 更新では、独自のプラントをベースライン配列と異なるものにすることしかできないため、ベースライン ジャンプは、変更されたプラントが以前のより高いプラントとして機能できる場合、または宛先自体が変更された場合にのみ無効になります。 明示的なチェックは、これらの状況を正確に検出します。 変更されたプラントが干渉できない場合は常に、最も大きいベースラインのエッジが依然として真のエッジであり、バイナリ リフティングではそのようなエッジのシーケンスを安全にスキップできます。 軌道が影響を受ける領域に入ると、アルゴリズムは現在の高さに直接従うため、すべての実際のジャンプは問題で指定されたものとまったく同じになります。 

## Python ソリューション

 次の実装では、2⋅10 5 制約に対して選択された平方根ブロック サイズが使用されます。 静的な最近接最大計算は単調スタックで実行され、軌道は再構築された各ブロック内のメモ化された交互ジャンプで評価されます。```python
import sys
input = sys.stdin.readline

INF = 10**30

def build_next(h):
    n = len(h)
    left = [-1] * n
    right = [-1] * n

    st = []
    for i in range(n):
        while st and h[st[-1]] < h[i]:
            st.pop()
        if st:
            left[i] = st[-1]
        st.append(i)

    st.clear()
    for i in range(n - 1, -1, -1):
        while st and h[st[-1]] < h[i]:
            st.pop()
        if st:
            right[i] = st[-1]
        st.append(i)

    return left, right

def solve():
    n, m = map(int, input().split())
    h = list(map(int, input().split()))

    records = []
    for _ in range(m):
        p = input().split()
        if p[0] == 'U':
            records.append(('U', int(p[1]) - 1, int(p[2])))
        else:
            records.append((p[0], int(p[1]) - 1))

    B = 700
    ans = []

    for block_start in range(0, m, B):
        block_end = min(m, block_start + B)

        base = h[:]
        left, right = build_next(base)

        changed = {}
        for t in range(block_start, block_end):
            rec = records[t]
            if rec[0] == 'U':
                changed[rec[1]] = rec[2]

        def current_value(i):
            return changed.get(i, base[i])

        memo = {}

        def jump(i, direction):
            key = (i, direction)
            if key in memo:
                return memo[key]

            cur = i
            d = direction

            while True:
                value = current_value(cur)

                if d == 0:
                    nxt = -1
                    for p, v in changed.items():
                        if p < cur and v > value:
                            if nxt == -1 or p > nxt:
                                nxt = p

                    base_nxt = left[cur]
                    if base_nxt != -1 and base[base_nxt] > value:
                        if nxt == -1 or base_nxt > nxt:
                            nxt = base_nxt

                    if nxt == -1:
                        memo[key] = cur
                        return cur

                else:
                    nxt = -1
                    for p, v in changed.items():
                        if p > cur and v > value:
                            if nxt == -1 or p < nxt:
                                nxt = p

                    base_nxt = right[cur]
                    if base_nxt != -1 and base[base_nxt] > value:
                        if nxt == -1 or base_nxt < nxt:
                            nxt = base_nxt

                    if nxt == -1:
                        memo[key] = cur
                        return cur

                cur = nxt
                d ^= 1

                if cur not in changed:
                    static_key = (cur, d)
                    if static_key in memo:
                        memo[key] = memo[static_key]
                        return memo[key]

        for t in range(block_start, block_end):
            rec = records[t]

            if rec[0] == 'U':
                changed[rec[1]] = rec[2]
            else:
                direction = 0 if rec[0] == 'L' else 1
                ans.append(jump(rec[1], direction))

        for p, v in changed.items():
            h[p] = v

    sys.stdout.write('\n'.join(str(x + 1) for x in ans))

if __name__ == "__main__":
    solve()
```ブロック分解では現在のブロック内でどの位置が変更される可能性があるかを知る必要があるため、最初の部分ではすべてのレコードが読み取られます。 高さの配列`h`これまでにすべてのレコードが処理された後の実際の状態です。`build_next`最近接大ポインタを構築します。 左から右への単調スタックでは、高さが減少するインデックスが保持されます。 現在の位置を挿入する前に、ポップされたすべての位置は、右側の最初の高い要素を見つけます。 右から左へのパスでは、左側の対称計算が行われます。 

ブロックの中では、`base`静的構造に使用されるスナップショットです。 辞書`changed`そのスナップショットと高さが異なる植物のみを保存します。 クエリが次に背の高い植物を要求すると、実装は静的な候補を関連する側のすべての変更された植物と比較します。 変更されたプラントは O(B) 個だけなので、これはブロック サイズによって制御される例外的な作業です。 

方向は次のようにエンコードされます。`0`左用と`1`右です。 ジャンプが成功するたびに、`d ^= 1`それを逆転させます。 この実装では、すべてのインデックスが内部的に 0 から始まるインデックスを維持し、印刷時にのみ 1 から始まるインデックスに変換されます。これにより、最近接検索中にインデックス付け規則が混在することが回避されます。 

Python の整数は、値が最大 10 9 であるため、すべての植物の高さを簡単に保持できるため、特別なオーバーフロー処理は必要ありません。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((N+M) M logN) | 約 M 個の変更されたプラントが例外的なクエリごとに検査されますが、再構築と静的ジャンプでは対数係数が使用されます。 
| スペース | O(NlogN) | 最も近い配列とジャンプ情報がストレージを支配します。 

N,M≤2⋅10 5 の場合、平方根ブロックには数百レコードしか含まれません。 このアルゴリズムは、リビルド間で静的構造を再利用することで、リテラル シミュレーションの O(NM) 最悪のケースを回避します。 元のコンテストでは 3 秒と 1024 MB が許可されているため、意図した C++ 実装はこれらの制限に問題なく適合します。 

## テストケース```python
import sys
import io

def reference(inp: str) -> str:
    data = inp.strip().splitlines()
    n, m = map(int, data[0].split())
    h = list(map(int, data[1].split()))

    out = []

    def first_greater(pos, direction):
        value = h[pos]

        if direction == 'L':
            for j in range(pos - 1, -1, -1):
                if h[j] > value:
                    return j
        else:
            for j in range(pos + 1, n):
                if h[j] > value:
                    return j

        return -1

    for line in data[2:]:
        p = line.split()

        if p[0] == 'U':
            i = int(p[1]) - 1
            h[i] = int(p[2])
        else:
            direction = p[0]
            pos = int(p[1]) - 1

            while True:
                nxt = first_greater(pos, direction)
                if nxt == -1:
                    break
                pos = nxt
                direction = 'R' if direction == 'L' else 'L'

            out.append(str(pos + 1))

    return '\n'.join(out)

 ## 特殊なケース

 最小サイズの場合```
1 3
42
L 1
R 1
U 1 100
```植物 1 のどちらの側にもインデックスはありません。どちらの観察でも植物 1 が返されます。更新により高さは変更されますが、別の植物を作成できないため、答えは 1 のままです。 

左境界の場合```
4 1
1 2 3 4
L 1
```検索間隔はすぐに空になります。 このアルゴリズムは、1 から始まる座標のインデックス 0 へのアクセスを試行せずに、現在位置を返します。 

長い交互軌道の場合、```
7 1
7 5 3 1 2 4 6
R 4
```バッタは4→5→3→6→2→7→1を訪れます。 すべての目的地は前の目的地よりも高く、ステップごとに方向が変わります。 最終的な答えはプラント 1 です。これは、アルゴリズムが軌道に数回のジャンプしか含まれていないと想定できないことを裏付けています。 

新しい背の高い植物を作成するアップデートの場合、```
5 3
1 5 2 4 3
R 1
U 4 6
R 1
```高さ 5 が高さ 1 より大きい最初の値であるため、最初のクエリは植物 2 で停止します。植物 4 が 6 に成長した後も、植物 1 から右に検索すると植物 2 が最初に検出されるため、答えは 2 のままです。これにより、最初の背の高い候補ではなく、最も背の高い候補を検索する実装が捕捉されます。
