 ## 解決策
 ## 問題の理解

 私たちには従業員という根を張った木が与えられています。 従業員 1 がルートであり、他のすべての従業員には、より小さいインデックスを持つ直属のマネージャーが 1 人だけ存在するため、構造はルート付きツリーになります。 各ノードには、その従業員の専門分野を表す 1 つの小文字のラベルが付いています。 

各クエリ文字列について、その文字列に正確に一致するツリー内の下向きのパスがいくつあるかを数える必要があります。 有効なパスは、あるノードから開始し、厳密に子に移動する必要があります (各ステップは直接の下位に移動する必要があります)。 そのパスに沿ったラベルのシーケンスは、クエリ文字列と 1 文字ずつ一致する必要があります。 

したがって、各クエリは、ツリー内の任意の場所に、指定されたパターンを表すルートから葉へのチェーンまたは内部の下向きチェーンがいくつあるかを尋ねます。 

制約は大きいです。 ツリーには最大 400k のノードを含めることができ、すべてのクエリ文字列の合計長は最大 1e6 です。 ツリーをたどることによって各クエリを処理しようとするソリューションは、クエリごとに 1 回の走査でさえ、最悪の場合すでに 2 次関数になるため、すぐに遅すぎます。 これにより、クエリごとにすべてのノードを再チェックしたり、パターンごとにすべてのノードから DFS を実行したりするアプローチは除外されます。 

多くのノードが同一のプレフィックスを共有する場合、微妙なエッジケースが発生します。 たとえば、ツリーが長いチェーンであり、文字列が「aaaaa」のように反復的である場合、各ノードからの単純な一致では、同じプレフィックス一致が繰り返し再計算されます。 もう 1 つのエッジ ケースは、複数のクエリが同一であるか、重なり合っている場合です。 クエリごとの再計算が爆発的に増加する可能性があります。 

重要な観察は、任意のパスではなく、ツリー内のラベル付きパスをカウントしていること、およびすべてのクエリが事前にわかっているため、グローバルな前処理が可能であることです。 

## アプローチ

 ブルートフォースのアイデアは単純です。 各クエリ文字列について、ツリー内のすべての可能な開始ノードを試し、下方向に DFS を実行し、文字を 1 つずつ照合します。 全長の一致が成功するたびに、答えが増加します。 

これは、開始点ごとに 1 回だけ、考えられるすべての下向きパスを列挙するため、正しいです。 問題はコストです。 ノードごとに、DFS は最悪の場合 O(n) ダウンする可能性があり、O(m) 個のクエリが存在します。 重複を無視しても、これは O(n * m) となり、両方が 4e5 までの場合、これは実現不可能です。 

重要な洞察は、クエリを独立して処理すべきではないということです。 代わりに、すべてのクエリ文字列を、すべてのプレフィックスを同時に表す単一の構造にマージします。 これは当然、クエリ文字列のトライです。 このトライの各ノードは何らかのクエリのプレフィックスを表しており、このトライのパスに対応する従業員ツリーの下向きのパスの数を知りたいと考えています。 

ここで問題は、従業員ツリーとトライという 2 つの構造を同時に走査することになります。 任意の従業員ノードで、ある開始点からのパスに沿ってラベルを照合した場合にどのトライ状態になるかを知りたいと考えています。 ただし、すべての (ツリー ノード、トライ ノード) ペアに対して DP を直接実行すると、遷移を慎重に制御しない限り、大きすぎます。 

これを処理する標準的な方法は、各ノードに対して、そのノードで終了するすべてのパターン一致を表すアクティブなトライ状態のマルチセットを維持しながら、従業員ツリー上で DFS を実行することです。 遷移を効率的に行うために、アクティブな状態のローリング セットを使用し、親情報を再利用します。 

ただし、単純に実装すると、依然として O(n * アルファベット) かそれ以上のリスクが発生します。 重要な改善点は、トライ内の遷移が文字ごとに決定的であることが観察できるため、トライ ノードからはツリー内の現在の文字の次の状態のみを知る必要があることです。 これは、すべてのクエリ文字列から構築された Aho-Corasick オートマトンを使用することを示唆しています。

すべてのクエリに対して Aho-Corasick を構築すると、ツリー内のすべてのノードをそのキャラクターを有限オートマトン状態にフィードするものとして扱うことができます。 ツリー内の任意の開始点からのウォークを考慮すると、ルート状態でオートマトンを開始し、下に向かって歩くことによってマッチングをシミュレートできます。 完成したパターンに対応するオートマトン ノードに到達するたびに、カウントが増加します。 

残りの微妙な点は、ルートから始まるものだけでなく、考えられるすべての開始位置で出現をカウントする必要があることです。 これは、ツリー上の DP を介して、すべてのノードを潜在的な開始として暗黙的に扱うことによって処理されます。各ノードでは、親状態から継続することと、そのノードで新たに開始することの両方が考慮されます。 これは、オートマトンの遷移とパターン終了カウンターの蓄積を使用して、単一の DFS に折りたたむことができます。 

したがって、オートマトンの状態をツリーの下に伝播し、各ノードで現在のオートマトンの状態で終了するパターンの数を数えます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとのブルート フォース DFS | O(n・m・深さ) | O(n) | 遅すぎる |
 | Aho-Corasick + ツリー DFS 伝播 | O(n + 合計 | s | + m) |

 ## アルゴリズムのチュートリアル

 1. すべてのクエリ文字列からトライを構築し、各文字列を挿入し、そのクエリの終端ノードをマークします。 各ターミナル ノードには、そこで終了するクエリの数が格納されます。 これは、複数の同一のクエリを正しくカウントするために必要です。 
2. BFS を使用して障害リンクを計算することにより、トライを Aho-Corasick オートマトンに変換します。 これらのリンクにより、不一致が発生した場合に部分一致の間で移行できるようになります。 これにより、各文字の遷移が確実に O(1) で償却されます。 
3. オートマトンのノードとキャラクターから次の状態に直接ジャンプできるように、遷移テーブルを構築します。 これにより、ツリーの走査中に障害リンクのウォーキングが繰り返されることが回避されます。 
4. 従業員ツリーに対して DFS を実行します。 各ノードで、DFS のルートからそのノードまでのパスに対応する現在のオートマトンの状態を維持します。 
5. ノードに入ると、ノードのキャラクターを使用してオートマトンの状態を遷移させます。 遷移後、そのオートマトン状態の出力数を、ここで終わるすべてのクエリの答えに追加します。 
6. この更新されたオートマトンの状態を使用して子に再帰します。 
7. 各 DFS 呼び出しには独自の状態があるため、値によって渡される場合、オートマトンの状態に対してバックトラッキングは必要ありません。 

これが機能する主な理由は、ツリー内のすべての下向きパスが 1 つの DFS パスに正確に対応し、Aho-Corasick がノードで終わるすべての部分文字列がステップごとに O(1) の償却時間で認識されることを保証するためです。 オートマトンの状態は、現在のノードで終わるすべての可能なサフィックス一致をエンコードするため、有効なクエリの出現はすべて、その最終状態にアクセスしたときに 1 回だけカウントされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class Node:
    __slots__ = ("next", "link", "out", "go")
    def __init__(self):
        self.next = [-1] * 26
        self.link = 0
        self.out = 0
        self.go = [-1] * 26

def add_string(trie, s):
    v = 0
    for ch in s:
        c = ord(ch) - 97
        if trie[v].next[c] == -1:
            trie[v].next[c] = len(trie)
            trie.append(Node())
        v = trie[v].next[c]
    trie[v].out += 1
    return v

def build_aho(trie):
    from collections import deque
    q = deque()

    for c in range(26):
        u = trie[0].next[c]
        if u != -1:
            trie[u].link = 0
            q.append(u)
        else:
            trie[0].next[c] = 0

    while q:
        v = q.popleft()
        for c in range(26):
            u = trie[v].next[c]
            if u != -1:
                trie[u].link = trie[trie[v].link].next[c]
                q.append(u)
            else:
                trie[v].next[c] = trie[trie[v].link].next[c]

    for i in range(len(trie)):
        trie[i].go = trie[i].next

def dfs_tree(v, p, state, tree, labels, trie, ans):
    c = ord(labels[v]) - 97
    state = trie[state].go[c]
    ans[0] += trie[state].out

    for to in tree[v]:
        if to == p:
            continue
        dfs_tree(to, v, state, tree, labels, trie, ans)

def main():
    n, m = map(int, input().split())
    p = [0] * n
    tree = [[] for _ in range(n)]
    for i in range(1, n):
        p[i] = int(input().split()[0]) if False else None

    # parents are given in line form, correct parsing:
    parts = list(map(int, input().split()))
    for i, par in enumerate(parts, start=1):
        tree[par - 1].append(i)

    labels = input().strip()

    trie = [Node()]
    query_nodes = []

    queries = []
    for _ in range(m):
        s = input().strip()
        queries.append(s)
        query_nodes.append(add_string(trie, s))

    build_aho(trie)

    ans = [0]

    dfs_tree(0, -1, 0, tree, labels, trie, ans)

    print(ans[0])

if __name__ == "__main__":
    main()
```トライ構造はすべてのクエリ文字列を保存し、各ターミナル ノードでカウンタをインクリメントします。 Aho-Corasick ビルド ステップは、各ノードが文字ごとに O(1) 個の遷移を持つように、失敗した遷移を完全な決定論的オートマトンに変換します。 

従業員ツリー上の DFS は、現在のルートからノードへのパスに沿ったすべてのサフィックス一致を表す単一のオートマトン状態を保持します。 各ノードで、ノード ラベルを使用して状態を進め、その状態で終了するすべての完了したパターンを蓄積します。 

実装上の微妙な問題は、ツリーが親配列から正しく構築されるようにすることです。 入力形式が圧縮されているため、子のインデックス作成時の off-by-one エラーを回避するには、慎重な解析が必要です。

 ## 特殊なケース

 重要なエッジ ケースは、多くのパターンが「a」、「aa」、「aaa」などのプレフィックスを共有する場合です。 オートマトンは、「a」というラベルの付いたノード上の 1 回の走査が、そこで終了するすべての有効なサフィックス一致に寄与することを保証します。 単純な DFS では、重複するプレフィックス チェックを繰り返し再計算しますが、ここでは障害リンクにより、すべての重複が 1 つの状態遷移に圧縮されます。 

もう 1 つの特殊なケースは、ツリーのさまざまな枝にわたってパターンが重なり合う場合です。 各ツリー ノードは 1 つのオートマトン遷移に寄与するため、多くのパスが部分構造を共有している場合でも、それぞれは重複することなく独立してカウントされます。 

最後のエッジケースは、単一文字のクエリです。 1 つの遷移後のオートマトンの状態には端末出力が直接含まれるため、これらは各ノードで即座に処理され、より深いトラバーサルを必要とせずに、一致するすべてのノードがカウントされます。
