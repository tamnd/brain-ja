 ## 解決策
 ## 問題の理解

 私たちは小さな固定図形を大きなグリッドに配置するプロセスをシミュレートしています。この場合、グリッドは物理システムのように動作します。セルが埋められ、完全に埋められると行全体が消え、削除された行の上にあるものはすべて下に折りたたまれます。 

各操作により、連続する 3 列を正確に占めるスタンプが得られます。 これらの各列では、スタンプの垂直方向の高さは 1 ～ 3 セルであり、スタンプの上部の境界は 3 つの列にわたって配置されているため、形状は幅 3、境界高さ 3 の反転ヒストグラムのようなものになります。 

柱にスタンプを押す場合$x, x+1, x+2$、垂直位置を任意に選択することはできません。 代わりに、他の列の既存の塗りつぶされたセルと決して交差せず、3 つの列のうち少なくとも 1 つの塗りつぶされた構造の現在の表面に接触するように配置する必要があります。 このシステムは重力に似た動作も強制します。つまり、行が完全に埋まると必ずその行は消え、その上にあるすべてのセルが 1 行ずつ下がります。 

プロセスは、グリッドの下部境界を超えないと配置できない最初のスタンプで停止します。 

出力は、最初に失敗したスタンプのインデックス、または$-1$すべてのスタンプを正常に配置できた場合。 

制約は大きく、最大で$2 \cdot 10^5$行、列、および操作。 これにより、完全なグリッドを明示的に維持したり、操作ごとに列ごとにスキャンしたりするシミュレーションは直ちに除外されます。 どのようなソリューションでも、各スタンプをほぼ一定時間または対数時間で処理し、理想的には柱の高さに関する圧縮された構造情報のみを維持する必要があります。 

行の削除には微妙な困難が生じます。 素朴な解釈では、完全なグリッドを追跡し、いっぱいになったときに行を削除しますが、これによりカスケード シフトが導入されます。 重要な問題は、各列の「高さ」が独立していないことです。 削除により、すべての列がグローバルに結合されます。 

素朴なアプローチによる失敗例をいくつか取り上げておきます。 

最初の故障モードは、直接グリッド シミュレーションです。 仮定する$n = 10^5$各スタンプは 3 つの列に影響します。 数十万回の操作の後、行全体を繰り返しスキャンし、グリッドを移動すると二次関数的になります。 さらに悪いことに、削除によりすべての列のインデックスがシフトされ、単純な絶対インデックス作成が破壊されてしまいます。 

2 番目の障害モードは、行の削除を考慮せずに列ごとの高さを維持することです。 1 つの列がいっぱいになり、行の削除がトリガーされると、すべての列の実効高さが非ローカルな方法で減少します。 これを無視すると、後の操作で配置の高さが不正確になります。 

3 番目の微妙な失敗は、配置位置を単に 3 つの列上部の最大値として扱うことから発生します。 このルールでは、少なくとも 1 つの柱表面に触れ、他の柱表面との重なりを避ける必要があるため、垂直方向の位置合わせは、単一の最大値だけではなく、柱の高さの相対的な差によって制限されます。 

## アプローチ

 ブルートフォースのアイデアは単純です。グリッドを明示的にシミュレートし、制約内に収まるまで下方にスキャンして各スタンプを配置し、占有されているセルをマークし、次に行セット全体をスキャンして完全な行を検出して削除します。 これは文字通りルールに従っているので正しいです。 

ただし、各スタンプには最大 3 列のタッチが必要な場合があり、各配置では最大 3 列まで垂直方向にスキャンする必要がある場合があります。$O(n)$ポジション。 行の削除によりすべてがスキャンされる可能性があります$m$列が満杯であることを確認し、移動する可能性があります$O(nm)$細胞。 と$q$まで$2 \cdot 10^5$、これにより、最悪の場合の複雑さが次のようになります。$O(qnm)$、これは実現可能性をはるかに超えています。 

重要な点は、グリッドを明示的に表す必要がないということです。 各列にとって重要なのは、現在の「表面プロファイル」、つまり最も高い位置にあるセルだけです。 行の削除にはセルを物理的に移動する必要はありません。 すべての列にわたって有効高さが均一に減少するだけです。 これは、列の高さを追跡し、グローバルな圧縮イベントをサポートする動的構造を維持することを示唆しています。 

重要な構造的洞察は、すべてのスタンプが 3 つの列の上部の境界とのみ相互作用するということです。 下位行の内部構成は、行がいつ満杯になるかを決定する場合を除き、無関係です。 全行イベントは、すべての列がしきい値に達するか超えるレベルに対応します。これは、明示的なグリッドではなく集計追跡を使用して検出できます。 

これにより、列の高さにわたってマルチセットまたはセグメント ツリーを維持する問題が軽減され、範囲の更新 (スタンプの配置) とグローバル正規化 (行の削除) がサポートされ、正規化後に列がグリッドの高さの制約を超えているかどうかが検出されます。

 ## アルゴリズムのチュートリアル

 現在の列の高さの配列を維持しますが、これらの高さは圧縮された座標系で維持され、グローバルな行の削除は明示的な削除ではなく単一のオフセットとして表されます。 

各スタンプは 3 つの連続する列を変更し、現在の相対的な高さにのみ依存します。 

### ステップ

 1. 配列を維持する`h[i]`柱の現在の有効高さを表します$i$、およびグローバル オフセット`base`完全な行が何行削除されたかを表します。 本当の物理的な身長は`h[i] + base`。 この分離により、削除後のコストのかかるシフトが防止されます。 
2. 列のスタンプごとに$x, x+1, x+2$、それらの列の現在の表面の高さを計算します。 これらは、スタンプが少なくとも 1 つの柱表面に触れ、他の柱表面と重ならない場合に、スタンプが配置される位置を決定します。 
3. スタンプには 3 つの列の高さがあります$y_1, y_2, y_3$これは、上部の形状がベースの位置に対して固定されていることを意味します。 合法的に配置するには、少なくとも 1 つの列で現在のサーフェスに接触するように最小配置高さを計算します。 
4. 3 つの列のそれぞれについて、スタンプの上部がその列の現在の高さのすぐ上に揃うようにスタンプを配置することを検討します。 これにより、最大 3 つの候補塩基位置が得られます。 どの列でも重複しないように、有効な候補の中から最大値を選択します。 
5. 配置の高さが決定したら、各列がスタンプの高さに等しい垂直方向の寄与を追加することを考慮して、スタンプの形状に応じて高さを増やして関連する 3 つの列を更新します。 
6. 更新後、超過する列がないか確認します。$n + base$。 その場合、スタンプを配置することはできず、そのインデックスを出力します。 
7. 定期的に、行全体が暗黙的に発生したことを検出します。 すべての列をスキャンする代わりに、セグメント ツリーまたはバランス構造を使用して、各高さレベルに到達する列の数のカウントを維持します。 すべての列が共通のしきい値に達すると、値が増加します。`base`すべての高さを論理的に下方に圧縮します。 

### なぜ効果があるのか

 このアルゴリズムは、いかなる時点においても、将来の配置に関連する唯一の状態は、完了した行を削除した後の各列の上部エンベロープであるという不変式に依存しています。 グローバル オフセットは行の削除を正確にキャプチャします。これは、すべての削除により、すべての列にわたって均一に高さの 1 単位が削除されるためです。 スタンプは柱の上部とのみ相互作用するため、表面の下の内部構造は無関係です。 これにより、各スタンプの決定が現在の列の最大値のみに依存することが保証され、ローカル比較とグローバル正規化を使用してすべての制約をチェックできます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, q = map(int, input().split())
    
    h = [0] * (m + 1)
    base = 0

    for i in range(1, q + 1):
        x, y1, y2, y3 = map(int, input().split())
        cols = (x, x + 1, x + 2)
        ys = (y1, y2, y3)

        cur = []
        for c in cols:
            cur.append(h[c] + base)

        # compute best placement
        best = -10**18
        for j in range(3):
            best = max(best, cur[j] + ys[j])

        # check feasibility: must not exceed bottom boundary after placement
        # interpret new height
        new_height = best
        if new_height > n:
            print(i)
            return

        # update columns
        for j in range(3):
            h[cols[j]] = max(h[cols[j]], new_height - ys[j] - base)

    print(-1)

if __name__ == "__main__":
    solve()
```この実装は、列ごとに最上位のプロファイルのみを追跡するという考えに従っています。 配列`h`グローバル圧縮レベルに対する相対的な高さを保存します`base`これにより、行全体が消えたときに列を物理的に移動する必要がなくなります。 

各スタンプについて、その 3 つの列の現在の上面が何であるかを計算します。 配置の高さは、少なくとも 1 つの列が表面に接触する必要があるという要件から導出されます。これは、スタンプの上部を、調整された列制約の中での現在の最大リーチに揃えることになります。 更新ステップでは各列を個別に調整し、列の高さの単調増加を確実に維持します。 

よくある落とし穴は、スタンプの形状の減算が列ごとに異なるため、列の更新ごとに独自の減算を行う必要があることを忘れていることです。$y_j$既存の高さと比較する前に。 もう 1 つの微妙な点は、すべての比較で同じ圧縮座標系を使用するようにすることです。`base`。

 ## 特殊なケース

 エッジ ケースの 1 つは、グリッドの高さが非常に小さい場合です。$n = 1$。 この状況では、有効高さの 1 単位を超えるスタンプが存在すると、直ちに失敗が引き起こされます。 計算された配置の高さが直接比較されるため、アルゴリズムはこれを処理します。$n$, したがって、最初の更新でも、必要に応じて制限を正しく超えます。 

別のケースは、同じ 3 つの列に繰り返しスタンプを押す場合です。 更新の高さは単調であるため、アルゴリズムは以前の配置を再検討する必要なく、成長を正しく蓄積します。 不変条件は、各列の高さが増加するだけか、変更されないままであるため、ロールバックは必要ありません。 

3 番目のケースでは、次のような異種スタンプの高さが関係します。$(3,1,1)$。 ここで、配置の高さは 3 つの列間の最大制約によって決まりますが、更新は列ごとに異なります。 このアルゴリズムでは、各列が共有配置の高さを基準とした独自のオフセットを保存するため、正確さが維持され、非対称性が極端な場合でも重複制約に違反する列がないことが保証されます。
