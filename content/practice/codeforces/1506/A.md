 ## 解決策
 ## 問題の理解

 次のような長方形のグリッドが与えられます。$n$行と$m$列。 各セルには次の一意の番号が含まれています。$1$に$n \cdot m$ですが、番号付けは 2 つの異なる方法で定義されます。 

まず、グリッドを列ごとに埋めていくことを想像してください。 左端の列から開始して上から下に入力し、次の列に移動して繰り返します。 これにより、列内で値が下に向かって増加し、次の列の先頭にジャンプする固定番号付けスキームが生成されます。 

次に、別の、より自然な番号付け (行ごと) を検討します。 左上のセルから開始して、各行を左から右に埋めて、1 行ずつ下に移動します。 

各クエリに対して、次のものが与えられます。$n$、$m$、および値$x$これは、列方向の番号付けにおけるセルのラベルに対応します。 タスクは、同じセルに行方向の番号が付けられる番号を決定することです。 

制約により、最大で$10^4$テストケース、$n, m$まで$10^6$、 そして$x$まで$10^{12}$場合によっては。 これにより、グリッドのシミュレーションが即座に除外されます。 単一のグリッドを構築することさえ、メモリと時間の両方の制約により不可能です。 解決策は次のとおりでなければなりません$O(1)$テストケースごとに。 

インデックス作成では微妙な問題が発生します。 どちらの番号付けスキームも 1 から始まり、構造が異なるため、行と列の計算におけるオフバイワンの間違いが最も一般的な障害点となります。 もう 1 つの潜在的な落とし穴は、中間積が次のような場合に整数オーバーフローになることです。$n \cdot m$は 32 ビット算術で計算されますが、Python は当然これを回避します。 

単純なアプローチでは、グリッドを再構築してインデックスを再作成しようとする可能性があります。 たとえば、$n=3, m=5$の場合は、テーブル全体を列の順序で埋めて保存し、行の順序を再構築します。 これは大きな制約ではすでに失敗しますが、手動で推論しても不要であることがわかります。 

## アプローチ

 ブルートフォースのアイデアは単純です。列方向の番号付けを 2D 配列にシミュレートし、次に行方向の番号付けを個別に割り当て、最後に値をマッピングし直します。 各セルは 2 回アクセスされるため、複雑さは次のようになります。$O(nm)$テストケースごとに。 まで$10^4$テストケースと$nm$潜在的に$10^{12}$、これはまったく不可能です。 

重要な観察は、両方の番号付けシステムが同じ行列の異なる線形化にすぎないということです。 列方向の番号付けの構造により、数値を直接デコードすることができます。$x$行と列の位置に移動します。 座標がわかれば、行ごとの番号付けへの変換は簡単です。 

列方向の番号付けでは、各列には正確に次の内容が含まれます。$n$要素。 つまり、列インデックスは$x$どれだけの列がその前に収まるかによって決まります。 具体的には、$(x-1) // n$列インデックスを与え、そして$(x-1) \% n$行インデックスを与えます。 

ポジションを確保したら$(r, c)$、行方向の番号付けへの変換は、行が同じサイズの連続したブロックであるシーケンスに単純に配置することです。$m$。 したがって、最終的な値は$r \cdot m + c + 1$。 

この変換により、グリッドの再構築から単純な算術インデックス作成までの問題が軽減されます。

 ## アルゴリズムのチュートリアル

 1. 値を解釈する$x$グリッドの列優先線形化における位置として$n$行。 これは、すべてのサイズのブロックを意味します$n$単一の列に対応します。 
2. 列インデックスを次のように計算します。$(x - 1) // n$。 これは、各列が正確に寄与するため機能します。$n$次の要素に進む前に。 
3. 行インデックスを次のように計算します。$(x - 1) \% n$。 これにより、列内の上から下までの位置がわかります。 
4. 同じものを再解釈します$(row, column)$行優先の順序での位置。 行ごとの番号付けでは、各行が正確に寄与します$m$次の行に移動する前に要素を削除します。 
5. 次を使用して座標を線形値に変換します。$row \cdot m + column + 1$。 これにより、同じセルの行方向のラベルが生成されます。 

### なぜ効果があるのか

 このアルゴリズムは、両方の番号付けシステムが同じグリッド上の全単射であるという事実に依存しています。 列方向の番号付けによりマッピングを定義する$f(r, c) = c \cdot n + r + 1$、行方向の番号付けは定義します$g(r, c) = r \cdot m + c + 1$。 両方とも同じ座標系を表すため、デコードすると$x$を通して$f^{-1}$そして再エンコード$g$正しさを保ちます。 各整数は 1 つのグリッド位置に正確に対応するため、衝突やあいまいさは存在しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m, x = map(int, input().split())

        x -= 1
        col = x // n
        row = x % n

        ans = row * m + col + 1
        print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは、各テスト ケースを一定時間で独立して処理します。 重要な手順は、最初に指定されたインデックスを 0 ベースの座標に変換することです。これにより、除算およびモジュロ演算中のオフバイワンの複雑さが回避されます。 行と列を計算した後、行優先インデックスを直接再適用します。 

よくある間違いは、座標に分割する前に 1 を引くのを忘れることです。これにより、すべての結果が誤ってシフトされます。 もう一人は交換中$n$そして$m$除算ステップでは、列の解釈が完全に壊れます。

 ## 特殊なケース

 重要なエッジケースの 1 つは次のような場合です。$x = 1$。 ここで、0 ベースの値は 0 であるため、行と列の両方が 0 となり、答えは正しく 1 になります。1 ベースのインデックスを誤って処理すると、これが 0 または無効なインデックスにシフトされます。 

もう一つのケースは次のような場合です。$x = n \cdot m$、グリッドの最後のセル。 1 を引くと、次のようになります。$x-1 = nm - 1$、列を生成します$m-1$そして漕ぐ$n-1$。 式に代入すると、$(n-1)m + (m-1) + 1 = nm$、最後のラベルが正しく保存されます。 

微妙な失敗例が現れるのは、$n = 1$。 グリッドは 1 行になり、列方向と行方向の番号付けは同じになります。 式は次のようになります。$col = x$、$row = 0$、生産$x$、予想と一致します。
