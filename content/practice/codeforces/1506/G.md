[CF 1506G - 残りの文字列を最大化する](https://codeforces.com/problemset/problem/1506/G)

 **評価:** 2000
 **タグ:** ブルート フォース、データ構造、DP、貪欲、文字列
 **解決時間:** 1 分 58 秒
 **確認済み:** はい

 ## 解決策
 ## 問題の理解

 小文字の文字列が与えられます。 文字を繰り返し削除することはできますが、制限があります。文字を削除できるのは、その文字が文字列内の別の場所にまだ存在する場合のみです。 結果の文字列に繰り返しの文字が含まれなくなるまで、つまり残りのすべての文字が 1 回だけ出現するまで、削除を続けます。 

重要な自由は、削除が強制されたり、固定された順序で連続的に実行されたりしないことです。 削除の位置と順序の両方を選択します。 選択が異なると、最終的な「個別文字」文字列も異なります。 すべての有効な最終文字列の中で、辞書編集上最大の文字列が必要です。 

したがって、タスクは文字列の重複を排除するだけではありません。 最終的な一意の文字列が辞書順でできるだけ大きくなるように、どの繰り返し文字を削除するかを決定します。 

制約は非常に重要です。 すべてのテスト ケースの合計の長さは最大 200,000 です。 これにより、遅いループで文字列のスキャンと頻度の更新を繰り返して単純に削除をシミュレートしようとするソリューションは除外されます。これは、最悪の場合、二次的な動作に低下する可能性があるためです。 

単純な考えとしては、複数セットのカウントを維持しながら、貪欲に文字の削除を繰り返し試行することです。 削除するたびに構造が変化し、「最適な選択」を最初から再計算するとコストがかかる可能性があるため、これはすでに問題に直面しています。 

重複する範囲で文字が繰り返される場合、微妙なエッジケースが表示されます。 

たとえば、次のことを考えてみましょう。```
abacaba
```初期に出​​現した小さな文字を貪欲に削除すると、辞書編集的に必要以上に小さな接頭辞が保持されてしまう可能性があります。 正しい答えは次のとおりです。```
cba
```全体的な計画を立てずに単に最後に出現したものを保持したり、左端の重複を削除したりする不注意な戦略は失敗します。最適な答えは、「大きな文字を早期に保持する」ことと「後で大きな文字を利用できるようにする」ことのバランスに依存するためです。 

文字列にすでにすべての一意の文字が含まれている場合、別の失敗ケースが発生します。 その場合、削除は許可されず、答えは文字列そのものになります。 少なくとも 1 つの削除を前提とするアルゴリズムでは、一意の文字を誤って削除しないように注意する必要があります。 

## アプローチ

 ブルート フォースの観点では、プロセスを文字列の状態検索として扱います。 現在の文字列から、その文字が複数回出現するインデックスを削除して、すべての文字が一意になるまで再帰的に試すことができます。 これにより、有効な削除シーケンスがすべて調査されます。 

州の数は膨大です。 各文字が一度削除されたとしても、本質的には制約の下に保持する出現のサブセットを選択することになり、これが組み合わせ爆発につながります。 長さ n のすべての同一文字の文字列のような最悪のケースでは、1 つが残るまですべての削除が許可され、選択肢の分岐は単純に調査すると依然として指数関数的な動作につながります。 

重要な点は、最終的な文字列は常に、元の文字列とは異なる文字がそれぞれ 1 回出現するだけで構成されるということです。 唯一の実際の決定は、各文字のどの出現を保持するかですが、これらの選択は辞書編集上の順序と将来の利用可能性によって制限されます。 

文字列を左から右に処理しますが、文字を保持するかどうかはすぐには決定しません。 代わりに、可能な限り最良の接尾辞の選択を維持します。どの時点でも、後で出現することを保証しながら、以前に出現した文字を安全に削除できる場合は、より大きな辞書編集結果が得られる可能性があるため、その文字の組み込みを遅らせる必要があります。 

これは古典的な貪欲な問題になります。最終出現制約と組み合わせた単調スタックのアイデアを使用して答えを構築します。 私たちは常にキャラクターを「望ましさ」の高い順に保つよう努めますが、後で再び出現する場合は、以前のキャラクターを破棄することができます。 

最終的な構造は、それぞれの異なる文字が 1 回だけ出現する辞書編集上最大のサブシーケンスを構築することになります。

 ## アルゴリズムのチュートリアル

 一意性を確保しながら、可能な限り最良のサブシーケンスを貪欲に構築することで問題を解決します。 

1. 文字列内のすべての文字の最後の出現インデックスを計算します。 これにより、今キャラクターを破棄しても後で必要に応じて選択しても安全かどうかが分かります。 位置 i にいて、s[i] の最後に出現したのが j である場合、i の後でも s[i] を取得するチャンスがまだあることがわかります。 
2. 構築中の現在の回答を表すスタック (またはリスト) を維持します。 
3. 文字がすでにスタックに含まれているかどうかを示すブール配列「used」を維持します。 これにより、最終的な一意性制約が適用されます。 
4. 文字列を左から右に繰り返します。 位置 i の各文字 c について:

 - c がすでに使用されている場合は、完全にスキップします。 
- それ以外の場合は、今すぐ挿入する必要があるか、スタックの最後から小さな文字をいくつか削除する必要があるかを決定してください。 
5. スタックが空ではなく、スタック内の最後の文字が c より小さく、最後の文字がまだ後で表示される (最後の出現インデックスが i より大きい) 場合は、安全にポップできます。 これは、後で配置する別の機会が保証されており、置き換えることで辞書編集上の順序が改善されるためです。 
6. 有効な削除をすべて行った後、c をスタックに追加し、使用済みとしてマークします。 
7. 文字列の終わりまで続けます。 スタックが最終的な答えです。 

### なぜ効果があるのか

不変条件は、スタック内のすべての文字が後の位置を使用して完了する実行可能な方法をまだ持っているという制約の下で、スタックが処理された接頭辞から形成された辞書編集上可能な最大のシーケンスを表すことです。 キャラクターを削除するときは、後で再び出現する場合にのみ削除し、実現可能性が保たれるようにします。 私たちが文字を保持するときは、それを削除すると実現可能性に違反するか、辞書編集上の順序を改善できなくなるためです。 これにより、ローカルで次善の選択がグローバルに最適な構成を妨げることがないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    last = {c: i for i, c in enumerate(s)}
    used = [False] * 26
    stack = []

    for i, c in enumerate(s):
        idx = ord(c) - 97

        if used[idx]:
            continue

        while stack:
            top = stack[-1]
            if top < c and last[top] > i:
                used[ord(top) - 97] = False
                stack.pop()
            else:
                break

        stack.append(c)
        used[idx] = True

    print("".join(stack))

if __name__ == "__main__":
    t = int(input())
    for _ in range(t):
        solve()
```この解決策は最後の出現の計算に依存しているため、後で再び出現することがわかっている場合を除き、文字を永久に破棄することはありません。 スタックはサブシーケンス構造を強制し、使用される配列により、各文字が最終出力に 1 回だけ出現することが保証されます。 

最も微妙な部分は、ポッピング ループ内の状態です。 先頭の文字が現在の文字よりも厳密に小さく、まだ後で表示される場合にのみ、先頭の文字が削除されます。 いずれかの条件が失敗した場合は、それを削除すると一意性が侵害されるか、実現可能性が失われるため、すぐに停止します。

 ## 特殊なケース

 次のような単一文字列の場合`a`、アルゴリズムはすぐに生成します`a`除去やポップがトリガーされないためです。 使用される配列により重複が防止されますが、出現するのは 1 つだけであるため、ここでは関係ありません。 

次のようなすべて同一の文字を含む文字列の場合`aaaaa`、使用される配列により、最初の文字以降のすべての文字がスキップされます。 各文字には厳密に言うと辞書編集的にこれより大きな置換の機会がないため、スタックが 1 つの要素を超えて増大することはありません。 

次のようなすでに一意の文字列の場合`abc`、挿入前に文字が使用済みとしてマークされることはなく、最後の出現は重要ではないためポップは発生しません。 結果は変わりません。 

次のような減少する文字列の場合、`dcbaabcd`、アルゴリズムは最初に減少するスタックを構築し、その後厳密に大きな文字が出現した場合にのみ置換を許可します。 実現可能性は最後の出現位置によって制限されるため、安全なポップのみが発生し、最終結果は一意性を損なうことなく最良の辞書編集を反映します。
