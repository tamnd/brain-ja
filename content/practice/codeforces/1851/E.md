 ## 解決策
 ## 問題の理解

 私たちにはポーションの種類のコレクションが与えられており、各タイプには直接購入価格が設定されていますが、一部のポーションは固定レシピに従って他のポーションを混合することによって生産することもできます。 各レシピはその材料を完全に消費するため、一度使用すると、それらの入力ポーションはなくなります。 レシピ構造は非循環的であるため、それ自体からポーションを最終的に派生させる方法はありません。 

当初、Nastya はすでにいくつかの種類のポーションを無制限に供給しています。 これらのタイプは購入する必要がないため、無料のリソースとして扱うことができます。 他のすべてのポーション タイプについては、そのポーションを直接購入するか、一連の有効な混合を通じて生産することによって、そのポーションを少なくとも 1 ユニット入手するために必要なコインの最小量を決定する必要があります。 

入力は、有向依存関係システムを記述します。各ポーションは、その生成に必要なポーションのセットをリストします。 これは、エッジが材料から結果のポーションを指す有向非循環グラフを定義します。 タスクは、各ノードを「アクティブ化」するための最小コストを計算することです。ここで、アクティブ化コストは、その購入価格またはその前提条件のコストの合計です。 

制約は、線形または線形に近い解決策を意味します。 すべてのテスト ケースにわたるポーションの合計数と依存関係エッジの合計数は最大 2×10^5 であるため、緩和ステップごとのエッジ数に比例した作業を実行するソリューションや、繰り返し再計算を使用するソリューションはタイムアウトになります。 これにより、ノードごとの単純な再帰的再計算と二次伝播が即座に排除されます。 

ポーションが最初の無料セットの一部である場合、微妙な問題が発生します。 このようなノードは、入力の後半にリストされる依存関係がある場合でも、ゼロコストのソースのように動作します。 このオーバーライドを無視する不用意なアプローチは、無料であるはずのポーションに誤って正のコストを割り当てる可能性があります。 

もう 1 つの落とし穴は、レシピが入力順に処理できると想定していることです。 依存関係は DAG を形成しますが、入力内でトポロジー的にソートされていないため、依存関係の順序を考慮せずにコストを計算すると、初期化されていない値が使用されることになります。 

## アプローチ

 直接的なアプローチは、各ポーションを個別に扱い、それを構築するすべての可能な方法を再帰的に拡張することによってそのコストを計算しようとすることです。 特定のポーションについて、購入コストを計算するか、すべてのレシピを試してその材料のコストを合計します。 再帰とメモ化を使用してこれらの値を計算すると、各ポーションの最適コストはその前提条件にのみ依存するという事実から正確さがわかります。 

ただし、これでは効率が低下します。 最悪の場合、あるポーションが他の多くのポーションに依存する可能性があり、重複する部分問題全体で再計算すると、同じ依存関係のエッジを繰り返したどることになります。 合計エッジが最大 2×10^5 になると、ノードごとの単純な DFS が二次動作に低下する可能性があります。 

重要な観察は、依存関係グラフが非循環的であり、トポロジカルな順序で処理される場合、各ポーションはすでに計算可能な部分問題にのみ依存するということです。 ノードを有効な順序で処理すると、すでに最終化された前提条件の値から各ノードの答えを 1 回だけ計算できます。 これにより、問題は DAG 上の単一パスに変換され、各ノードが入力エッジからの情報を集約します。 

また、初期の無料ポーションをコストゼロのソースとして扱うことで組み込み、自然に増殖の種をまきます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ノードごとのブルート フォース DFS | O(n・m) | O(n + m) | 遅すぎる |
 | DAG 上のトポロジカル DP | O(n + m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ポーションを有向グラフのノードとしてモデル化します。 ポーション i がポーション j を必要とする場合、j は i の前に計算される必要があるため、j から i への有向エッジを作成します。

また、各ノードが持つ前提条件の数をカウントする入次数も計算します。 次数 0 のノードは何にも依存しないため、すぐに処理できます。 

1. 各材料から生成に役立つポーションまでのエッジを反転してグラフを作成します。 これにより、依存関係フローが計算順序と一致することが保証されます。 
2. 各ポーションが最初に直接購入コストを持つコスト配列を初期化します。 無料セットのポーションについては、コインを消費せずにいつでも入手できるため、コストをゼロに上書きします。 
3. 依存関係エッジに基づいて各ノードの入次数を計算します。 これにより、どのノードが処理の準備ができているかがわかります。 
4. 入次数が 0 のすべてのノードでキューを初期化します。 これらのノードには満たされていない前提条件がないため、現在のコストはすでに最終的です。 
5. キュー順にノードを処理します。 ノード u について、すべての外向きエッジ u → v を考慮します。u の寄与を使用してコストの改善を試みることにより、v を更新します。 具体的には、各 v の前提条件の最もよく知られているコストの累計を維持します。 
6. 各入力寄与を処理した後、v の次数を減少させます。 indegree が 0 に達すると、v のすべての前提条件が考慮されるため、v を確定してキューにプッシュできます。 
7. すべてのノードが処理されるまで続行します。 各ノードは、すべての依存関係が解決されるときに 1 回だけ評価されます。 

核となる不変条件は、ノードが処理されるときに、そのすべての前提条件に可能な最小コストがすでに割り当てられていることです。 すでに最適化されている部分結果を組み合わせて直接購入コストと比較するだけなので、その後の操作によって最終的な値が減額されることはありません。 これにより、トポロジカル DP の正確さが保証されます。 

## Python ソリューション```python
import sys
from collections import deque

input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        c = list(map(int, input().split()))
        free = set(map(lambda x: int(x) - 1, input().split()))

        g = [[] for _ in range(n)]
        indeg = [0] * n
        need = [[] for _ in range(n)]

        for i in range(n):
            tmp = list(map(int, input().split()))
            m = tmp[0]
            req = [x - 1 for x in tmp[1:]]
            need[i] = req
            indeg[i] = m
            for v in req:
                g[v].append(i)

        dp = c[:]
        for i in free:
            dp[i] = 0

        q = deque()

        for i in range(n):
            if indeg[i] == 0:
                q.append(i)

        while q:
            u = q.popleft()
            for v in g[u]:
                dp[v] = min(dp[v], sum(dp[x] for x in need[v]))
                indeg[v] -= 1
                if indeg[v] == 0:
                    q.append(v)

        print(*dp)

if __name__ == "__main__":
    solve()
```グラフは逆に構築されるため、前提条件が処理されると、その依存ノードに寄与できるようになります。 の`need`list には完全な依存関係リストが格納されているため、ノードの準備ができたら、その要素の合計を 1 ステップで計算できます。 キューにより、ノードが依存関係の順序で処理されることが保証されます。 

重要な実装の詳細は、すべての前提条件が確認された場合にのみノードを完成させるということです。 この時点で、使用するすべての dp 値がすでに最適になっているため、依存関係の合計は有効です。 

## 実用的な例

 自由に使用できるポーションと組み合わせに依存するポーションが 5 つある小さなシステムを考えてみましょう。 dp 値と角度を追跡します。 

### トレース例 1

 | ステップ | 処理されたノード | dp アップデート | 度数変化 |
 | --- | --- | --- | --- |
 | 初期化 | なし | コストと無料セットからの初期 dp | 初期度数 |
 | 1 | 次数 0 のノード | 変化なし | 隣人が減少する |
 | 2 | 次の準備完了ノード | 前提条件を使用して再計算された dp | 伝播する |
 | 最終 | すべてのノード | 安定した dp 値 | すべてゼロ |

 このトレースは、すべての前提条件が考慮された後でのみ dp 値がどのように安定するかを反映しており、時期尚早な計算が正確さに影響を与えないことが保証されています。 

### トレース例 2

 無料のポーションが複数の依存関係を通じてゼロコストを伝播する 2 番目のケースは、初期の可用性によって下流コストがどのように大幅に削減されるかを示しています。 無料のコンポーネントに依存するノードは、前提条件が処理されるとすぐに低い値に収束します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m) | 各ノードと各依存関係エッジはトポロジ順に 1 回処理されます。 
| スペース | O(n + m) | グラフ ストレージと dp、indegree、および依存関係リストの配列 |

 テスト ケース全体の入力サイズの合計は 2×10^5 で制限されるため、すべてのノードとエッジを線形に走査するだけで制限内を快適に通過できます。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    input = sys.stdin.readline
    t = int(input())
    out_lines = []

    for _ in range(t):
        n, k = map(int, input().split())
        c = list(map(int, input().split()))
        free = set(map(lambda x: int(x) - 1, input().split()))

        g = [[] for _ in range(n)]
        indeg = [0] * n
        need = [[] for _ in range(n)]

        for i in range(n):
            tmp = list(map(int, input().split()))
            m = tmp[0]
            req = [x - 1 for x in tmp[1:]]
            need[i] = req
            indeg[i] = m
            for v in req:
                g[v].append(i)

        dp = c[:]
        for i in free:
            dp[i] = 0

        q = deque(i for i in range(n) if indeg[i] == 0)

        while q:
            u = q.popleft()
            for v in g[u]:
                dp[v] = min(dp[v], sum(dp[x] for x in need[v]))
                indeg[v] -= 1
                if indeg[v] == 0:
                    q.append(v)

        out_lines.append(" ".join(map(str, dp)))

    return "\n".join(out_lines)

 ## 特殊なケース

 重要なケースの 1 つは、ポーションが購入可能で作成可能であるが、作成の方が高価である場合です。 このような状況でも、アルゴリズムは両方のオプションを比較する必要があります。 これは、dp を直接コストで初期化し、適用するだけで処理されます。`min`レシピコストが計算されるときに、強制的な上書きが行われないようにします。 

もう 1 つのケースは、無料のポーションが依存関係の連鎖の奥深くに表示される場合です。 処理前に dp をゼロに初期化するため、前提条件が集約されると、それに依存するノードは削減されたコストを正しく継承します。 

最後のエッジ ケースは、依存関係がなく、フリー セットに含まれていないノードです。 代替構造が存在しないため、購入コストと同額のままであるはずです。 このようなノードは単に初期化されるだけで、受信エッジを通じて決して更新されないため、アルゴリズムはこれを保持します。
