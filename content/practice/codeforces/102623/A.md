 ## 問題の理解

 アークメイジは、フルサイズのマナプールから始まります。`n`。 毎秒、彼は次のことを費やします。`x`十分なマナが利用可能な場合は、マナを使用して水のエレメントを 1 つ召喚します。そうでない場合は、待つこともできます。 その決断の後、彼のオーラは回復する`y`マナ、でもマナはそれを超えることはできない`n`。 

課題は、最初の期間中に可能な最大の召喚数を見つけることです。`m`秒。 各テスト ケースには、マナ制限、利用可能な秒数、1 回の召喚にかかるマナ コスト、および再生量が示されています。 

制約によって主な困難が明確になります。 まであります`100000`テスト ケース。各値は次のように大きくできます。`10^9`。 毎秒処理するシミュレーションには、最大で`10^14`最悪の場合、2 秒の制限をはるかに超えて操作が可能になります。 ソリューションでは、テスト ケースごとにプロセスを一定時間に短縮する必要があります。 

トリッキーなケースは、再生とマナの上限との相互作用から生じます。 直接シミュレーションは、小さな例では機能することがよくありますが、次の場合には失敗します。`m`巨大な場合、またはアークメイジが永久にキャストできるか、蓄積された再生に頼らなければならない場合。 

たとえば、次のことを考えてみましょう。```
1
2 5 1 1
```正しい出力は次のとおりです。```
5
```不注意な解決策では、召喚ごとにマナが必要になるため、マナが減少すると考える可能性があります。 ただし、コストと再生は等しいため、1 秒ごとにマナは同じ値に戻ります。 

もう 1 つのエッジケースは、再生が呪文コストよりも小さい場合です。```
1
6 10 4 2
```正しい出力は次のとおりです。```
6
```アークメイジが可能な限り待機する必要があると仮定したシミュレーションでは、再生が必要になる前に最初の全マナをいくつかの即時キャストに変換できるという事実を見落とす可能性があります。 

最後の境界ケースは、秒数が制限要因となる場合です。```
1
100 3 20 5
```正しい出力は次のとおりです。```
3
```マナの供給量はより多くの呪文を唱えるのに十分な量ですが、ゲームはちょうど 3 秒間続くため、許可されるアクションは 3 つだけです。 

## アプローチ

 簡単なアプローチは、毎秒シミュレーションすることです。 現在のマナ値を維持し、召喚が可能かどうかを確認し、減算します。`x`そうであれば、追加します`y`キャップをかぶせた状態。 これはゲームのルールに従っているため、結果は正しいです。 

問題は秒数です。 以来`m`到達できる`10^9`そしてそれがあるかもしれません`10^5`テスト ケース、シミュレートされた合計秒数は次のとおりです。`10^14`。 シミュレーションはプロセスを理解するのには役立ちますが、最終的なソリューションには使用できません。 

重要な観察は、重要な唯一のリソースは、全期間にわたって利用可能なマナの総量であるということです。 最初はアークメイジが所有しています`n`マナ。 以下の期間中`m - 1`せいぜい修復`(m - 1) * y`追加のマナを回復することができます。 最後の1秒の回復は最終決定後に行われるため、別の召喚を作成することはできません。 

いつ`x <= y`、すべての召喚は復元後に事実上元が取れます。 アークメイジはフルスタートなので、`n >= x + y >= x`、彼は毎秒キャストできます。 

いつ`x > y`、すべての召喚は 1 回の回復が返されるよりも多くのマナを消費します。 ただし、召喚に費やせるマナの総量は、初期マナと最後のアクション前のすべての回復量によって制限されます。 この合計をで割ると、`x`可能な最大召喚数を示します。 答えも超えることはできません`m`、しかないからです。`m`秒。 

したがって、最適な解決策は定数時間の計算です。

 ## アルゴリズムのチュートリアル

 1.回生量の場合`y`少なくとも呪文コスト以上です`x`、出力`m`。 すべてのキャストは 2 秒目の終わりに回復によって補償されるため、アークメイジは利用可能なすべての秒間に召喚できます。 
2. それ以外の場合は、召喚に使用できる合計マナを次のように計算します。`n + (m - 1) * y`。 初期マナは最初のアクションの前に利用可能で、最初のアクションのみが利用可能です。`m - 1`修復は将来の召喚に貢献できます。 
3. この合計を次の値で割ります。`x`利用可能なマナで支払うことができる完全な召喚の最大数を取得します。 
4. 結果を次のように制限する`m`, なぜなら、たとえ無制限のマナであっても、1秒間に複数の召喚を生成することはできないからです。 

なぜ効果があるのか:

 いつ`x > y`、召喚ごとに永久に削除されます`x - y`修復後のシステムからのマナ。 待機と詠唱の正確な順序によって、消費できるマナの総量は増加しません。 初期マナと最初の`m - 1`修復はすべての召喚に利用できる完全な予算です。 すべての召喚は正確に消費します`x`この予算から計算されるため、召喚数は予算の整数除算を超えることはできません。`x`。 アークメイジは、カウントが制限内にあるときはいつでも、この利用可能なマナを消費するようにアクションを調整できるため、この制限は達成可能です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    ans = []

    for _ in range(t):
        n, m, x, y = map(int, input().split())

        if y >= x:
            ans.append(str(m))
        else:
            ans.append(str(min(m, (n + (m - 1) * y) // x)))

    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```この解決策は、まず、再生が呪文の使用と歩調を合わせている場合を分けます。 このような状況では、一秒もスキップする理由はありません。 

他の場合の式は、`n + (m - 1) * y`キャストに貢献できるマナの合計を表します。 乗算では、`m - 1`それよりも`m`最後の 1 秒後の復元は、別の呪文を作成するには遅すぎるためです。 

Python の整数は、最大の中間値を安全に処理します。 最大の乗算は約`10^18`、これは Python の任意精度整数型に快適に適合します。 の`min`この操作は、計算されたマナ バジェットが利用可能な秒数よりも多くの呪文を許可する境界を処理します。

 ## 特殊なケース

```アルゴリズムは以下を計算します。```
