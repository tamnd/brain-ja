 ## 解決策

 ## 問題の理解

 各友人は 2 つの食品タイプに関連付けられており、各食品タイプには皿の在庫が限られています。 友人が呼ばれると、好みの 2 種類からそれぞれ 1 皿ずつ食べようとします。 これら 2 つのタイプのうち少なくとも 1 つがまだ在庫がある場合、友人は安全に去り、対応する食料の数を減らします。 その時点で両方のタイプがすでに空の場合、友人は危険になり、すぐにプロセスを終了します。 

このタスクは、固定された順序で貪欲にシミュレーションすることではなく、すべての友人がペアから少なくとも 1 皿を提供できるような友人の順序が存在するかどうかを判断し、そのような順序が存在する場合は出力することです。 

制約が十分に大きいため、友人のすべての順列を試みる解決策は不可能です。 最大 200,000 人の友達でも、$m!$あるいは階乗のような推論は無関係です。 友人に対する二次戦略でさえ遅すぎるでしょう。$m^2$到達する$4 \cdot 10^{10}$。 これにより、線形または線形に近いグラフ処理が可能になります。 

食品タイプの初期在庫がゼロの場合、微妙なエッジケースが発生します。 両方の食べ物がゼロから始まる友人は、すべての注文ですぐに失敗するはずなので、答えは自動的に不可能になります。 もう 1 つの注意が必要なケースは、複数の友人が、容量が非常に小さい単一の種類の食品に依存している場合です。 そのリソースを依存関係の間違った方向に早く消費すると、たとえ有効なグローバル順序が存在していても、後の友人がブロックされる可能性があります。 これはまさに、段階的または任意の順序による単純な貪欲さが失敗するタイプの状況です。 

## アプローチ

 素朴に推論しようとすると、そのプロセスをシミュレートすることを想像できます。現在提供できる友人を繰り返し選び、利用可能な食べ物の 1 つから 1 皿を消費し、それを答えに追加します。 これは貪欲なスケジューリングの問題に似ています。 「誰かが今満足できる限り、私たちはその人を処理する」というのが正しい直観でしょう。 しかし、これは失敗します。なぜなら、早​​すぎる種類の食品を摂取すると、将来の入手可能性が減少し、一部の友達を残すことが不可能になる可能性があるからです。 

もう 1 つの強引なアイデアは、友人のすべての順列を試して、実現可能性を確認することです。 これは階乗増加のため直ちに実行不可能です。 

重要な観察は、各フレンドは、処理時に 2 つのリソースのうち少なくとも 1 つが利用可能な状態にあることだけを要求しているということです。 これは、少なくとも 1 つのインシデント食品タイプがまだ容量がある限り、各ノード (友人) が「生きている」グラフ プロセスとして再構成できます。 エッジの両方のエンドポイントが使い果たされると、ノードは停止します。 

視点を逆転させることができます。 失敗を避ける順序を構築する代わりに、「安全な」友人を最後から削除することをシミュレートできます。 他のすべてを考慮した後、2 つの食品タイプのうち少なくとも 1 つがまだ容量が残っている場合、友人は最後に置くのが安全です。 これは、現在の残りのキャパシティを考慮すると生存が保証されているフレンドを繰り返し削除し、それらを注文にコミットするにつれてキャパシティを徐々に削減する必要があることを示唆しています。 

これにより、エッジが頂点からの容量を消費するグラフ上で貪欲なプロセスが発生します。 正しい戦略は、常に有効な友人を選択し、それらを配置するときに、制御された方法でエンドポイントの 1 つの可用性を低下させることです。 誤った選択を避けるために、私たちは常にまだ容量が残っているエンドポイントを選択します。 

より構造化されたビューは、食品の種類を容量を持つノードとして扱い、友人をエッジとして扱うことです。 ある程度の残存容量を維持し、まだ満足できるエッジを常に削除します。 エッジが確保されると、可能であればそのエンドポイントの 1 つの容量を削減します。 どちらのエンドポイントにも容量がない場合、プロセスは不可能です。 

これは、使用可能なエッジのスタックまたはキューを備えた貪欲な構造になります。

 ## アルゴリズムのチュートリアル

 各友人を 2 つの食品タイプ間のエッジとしてモデル化し、各食品タイプの残りの容量を追跡します。 

1. 食品の種類ごとに隣接リストを作成し、どの友人がそれに依存しているかを保存し、現在の残りの容量を維持します$w_i$タイプごとに。 これにより、どのエッジがまだ満たされる可能性があるかをすぐに知ることができます。 
2. 「安全な」友人の初期セットを計算します。これは、少なくとも 1 つのエンドポイント食品タイプが現在プラスの能力を持っている友人を意味します。 これらは、どの段階でも安全に処理できる唯一の候補です。 
3. 友人候補のスタック (またはキュー) を維持します。 最初に、自明に停止していない (つまり、両方のエンドポイントの容量がゼロではない) すべてのフレンドをプッシュします。 
4. スタックから友人を繰り返しポップします。 両方の食品タイプがすでに容量ゼロになっている場合は、処理できないため、スキップします。 
5. それ以外の場合は、この友人を回答順序に割り当てます。 エンドポイントの 1 つから 1 つのプレートを消費しようとします。 両方のエンドポイントにまだプラスの容量がある場合は任意に選択しますが、安定した選択は、容量が残っているいずれかのエンドポイントから消費することです。 
6. 食品タイプを消費した後、その残量を更新します。 これにより、接続されている新しい友達が新たに「安全」になったり、新たに関連性が高まったりする場合は、それらをスタックにプッシュします。 
7. すべての友達が処理されるまで、または有効な動きがなくなるまで続行します。 すべての友人を処理した場合は、構築された順序を出力します。 それ以外の場合は、出力エラーになります。 

### なぜ効果があるのか

 重要な不変条件は、少なくとも 1 つのエンドポイントに空き容量がある場合にのみ、フレンドを注文に含めることです。 これにより、両方のリソースが使い果たされた瞬間に友人を割り当てることがなくなります。 消費するたびに容量が 1 つだけ減少し、フレンドをコミットするときにのみ容量が減少するため、残りのすべての未処理エッジの実現可能性が維持されます。 

このプロセスは、動的に縮小するリソース グラフ上で、有効な逆トポロジーのような順序付けを効果的に構築します。 あらゆる障害状態は、残りのすべての友人が枯渇した種類の食品にのみ発生する構成に正確に対応しており、これは有効な順序が存在しないことを意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    w = list(map(int, input().split()))

    g = [[] for _ in range(n)]
    edges = []

    for i in range(m):
        x, y = map(int, input().split())
        x -= 1
        y -= 1
        edges.append((x, y))
        g[x].append(i)
        g[y].append(i)

    used = [False] * m
    order = []

    # current availability
    import collections
    q = collections.deque()

    # initially push all edges
    for i in range(m):
        q.append(i)

    while q:
        i = q.pop()
        if used[i]:
            continue

        x, y = edges[i]

        if w[x] == 0 and w[y] == 0:
            continue

        used[i] = True
        order.append(i + 1)

        # consume from a valid endpoint
        if w[x] > 0:
            w[x] -= 1
        else:
            w[y] -= 1

        # push neighbors again since state changed
        for j in g[x]:
            if not used[j]:
                q.append(j)
        for j in g[y]:
            if not used[j]:
                q.append(j)

    if len(order) != m:
        print("NO")
    else:
        print("YES")
        print(*order[::-1])

if __name__ == "__main__":
    solve()
```この実装では、友人候補のスタックを保持し、それらの割り当てを繰り返し試行します。 重要な点は、最終的な順序を逆にすることです。これは、直接順方向のスケジュールではなく、有効な削除シーケンスを効果的に構築しているためです。 

隣接リストにより、食品の種類の容量が変更されるたびに、影響を受けるすべての友人が再検討されるようになります。 訪問済み配列により、すでに固定された友人の繰り返し処理が防止されます。 

よくある間違いは、可用性を確認せずにエンドポイントを恣意的に選択することです。 条件`if w[x] > 0`使い果たされたタイプを決して消費しないようにします。

 ## 特殊なケース

 直接的な失敗のケースは、友人の両方の食べ物の種類がゼロから始まる場合に発生します。 アルゴリズムはそのような友人をすぐに破棄します。`w[x] == 0 and w[y] == 0`、処理の最後にそのような友人が存在する場合、合計数は一致しません`m`、NOを生成します。 

ボトルネックとなるケースは、多くの友人が 1 つの容量の少ない種類の食品を共有する場合に発生します。 このアルゴリズムは、食品タイプが利用可能な場合にのみ食品タイプを消費し、ゼロに達すると、残りのエッジは、他のエンドポイントにまだ容量がある場合にのみ処理されます。 両方のエンドポイントが枯渇した場合、それらのエッジは正しく拒否され、無効な順序付けが防止されます。 

すべての友人が両方のエンドポイントを繰り返し共有する密なグラフのケースは、各エッジが最大 1 回処理され、隣接関係のプッシュが既存の接続を通じてのみ発生し、線形の複雑さが維持されるため、引き続き機能します。
