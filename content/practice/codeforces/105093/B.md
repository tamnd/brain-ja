 ## 解決策
 ## 問題の理解

 ヌクレオチドの配列を表す文字列を維持しています。各位置には 1 つの大文字が含まれています。 2種類の操作により文字列が時間とともに変化します。 1 回の操作で 2 つの指定された位置の文字を交換し、シーケンスを効果的に再配置します。 もう 1 つの操作では、指定された部分文字列内の特定の文字の頻度を求め、それが何回出現するかを報告する必要があります。 

重要な点は、文字列が動的であるということです。 クエリは独立していません。スワップは、後のすべての操作の文字列を永続的に変更します。 各カウント クエリは、以前のすべてのスワップに依存します。 

制約は、素朴なアイデアが失敗する理由を示しています。 文字列の長さと操作の数は両方とも、テスト ケース全体で合計で最大 100,000 になる可能性があるため、クエリごとに部分文字列をスキャンするソリューションは、最悪の場合、二次的な動作に低下します。 n と q が約 100,000 の単一のテスト ケースでも、O(nq) アプローチは不可能になります。 

微妙なエッジケースは、スワップが 2 つのポジションにのみ影響を与えるものの、頻繁に発生する可能性があるという事実から生じます。 たとえば、隣接する要素を繰り返し交換すると、文字列は常に変化するため、事前に計算されたプレフィックス情報は、動的に維持されない限り無効になります。 

単純な間違いは、l から r までスキャンして、すべての COUNT クエリのカウントを再計算することです。 「AAAA...A」のような長さ 100000 の文字列の場合、1 つのクエリに 100000 ステップかかる可能性があり、100000 クエリでは 10^10 の操作になります。 

もう 1 つの失敗モードは、文字ごとのプレフィックスの合計を維持しようとしますが、スワップによって単調な構造が壊れることを忘れてしまうことです。 2 つの文字を交換した後、それらのインデックスを超えるすべてのプレフィックス データを更新する必要がありますが、これを直接実行するとコストがかかりすぎます。 

## アプローチ

 ブルートフォース戦略は単純です。 文字列を可変配列として保存します。 SWAP i j の場合、O(1) の 2 つの文字を交換します。 COUNT x l r の場合、l から r までを繰り返し、x の出現回数を数えます。 これはクエリの定義を直接反映しているため、これは正しいです。 ただし、カウント ステップは O(r - l + 1) であり、最悪の場合は O(n) になります。 最大 100,000 クエリでは O(nq) となり、遅すぎます。 

これを改善するには、範囲をスキャンせずに範囲周波数のクエリに答える方法が必要です。 重要な観察は、単一の文字の出現のみをカウントしており、アルファベットのサイズは固定されており小さい (最大 26 大文字) ということです。 これは、範囲全体にわたって文字ごとの頻度情報を維持することを示唆しています。 

この自然な構造は、各ノードがサイズ 26 の頻度配列を格納するセグメント ツリーです。各リーフは 1 つの文字に対応し、内部ノードは子からの集計されたカウントを格納します。 COUNT クエリはセグメント ツリーに対する範囲合計クエリになり、要求された文字の頻度を返します。 SWAP 操作は 2 つの位置を更新することで処理できます。両方のリーフを更新し、変更を上方に伝播します。 

ブルート フォースに対する主な改善点は、範囲の集計が n で対数的になることと、変更されるリーフが 2 つだけであるため、更新も対数的のままであることです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | セグメントツリー | O((n + q) log n) | O(26n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 文字列に対してセグメント ツリーを構築します。各ノードには、そのセグメント内の文字数を表すサイズ 26 の配列が格納されます。 これにより、互いに素なセグメントからの結果を効率的に組み合わせることができます。 
2. 位置 i に対応する各リーフ ノードについて、s[i] の文字のみがカウント 1 を持つように頻度配列を初期化します。これにより、文字列の基本状態がエンコードされます。 
3. 内部ノードを構築するときは、周波数配列を要素ごとに合計して子をマージします。 これにより、各ノードがそのセグメントを正しく表すことが保証されます。 
4. COUNT x l r クエリを処理するには、セグメント ツリーをトラバースし、[l, r] を完全または部分的にカバーするセグメントの度数配列を合計します。 結果として文字 x に対応する値を抽出します。 これにより、個々の位置をスキャンする必要がなくなります。 
5. SWAP i j 操作を処理するには、位置 i と j にある文字を取得し、リーフ値を置き換えて変更を上方に伝播することによって、セグメント ツリー内の両方の位置を更新します。 各更新は独立しており、1 つの位置のみを調整します。 
6. COUNT 個のクエリの結果をテスト ケースごとにリストにまとめて順番に出力します。 

### なぜ効果があるのか

 セグメント ツリーは、すべてのノードがそのセグメントの正しい頻度カウントを格納するという不変条件を維持します。 カウントは互いに素な間隔で加算されるため、子をマージすると正確さが保たれます。 すべての更新ではリーフ ノードとその祖先のみが変更されるため、影響を受けるすべてのセグメントが一貫して修復されます。 すべてのクエリは、要求された範囲と正確に一致する結合部分を持たないツリー セグメントに分解されるため、保存されているカウントを合計すると正しい頻度が得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, s):
        self.n = len(s)
        self.t = [[0] * 26 for _ in range(4 * self.n)]
        self.s = list(s)
        self.build(1, 0, self.n - 1)

    def build(self, v, l, r):
        if l == r:
            self.t[v][ord(self.s[l]) - 65] = 1
            return
        m = (l + r) // 2
        self.build(v * 2, l, m)
        self.build(v * 2 + 1, m + 1, r)
        for i in range(26):
            self.t[v][i] = self.t[v * 2][i] + self.t[v * 2 + 1][i]

    def update(self, v, l, r, pos, old_c, new_c):
        if l == r:
            self.t[v][ord(old_c) - 65] -= 1
            self.t[v][ord(new_c) - 65] += 1
            self.s[l] = new_c
            return
        m = (l + r) // 2
        if pos <= m:
            self.update(v * 2, l, m, pos, old_c, new_c)
        else:
            self.update(v * 2 + 1, m + 1, r, pos, old_c, new_c)
        for i in range(26):
            self.t[v][i] = self.t[v * 2][i] + self.t[v * 2 + 1][i]

    def query(self, v, l, r, ql, qr, ch):
        if qr < l or r < ql:
            return 0
        if ql <= l and r <= qr:
            return self.t[v][ch]
        m = (l + r) // 2
        return self.query(v * 2, l, m, ql, qr, ch) + self.query(v * 2 + 1, m + 1, r, ql, qr, ch)

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n, q = map(int, input().split())
        s = input().strip()

        st = SegTree(s)
        res = []

        for _ in range(q):
            parts = input().split()
            if parts[0] == "SWAP":
                i = int(parts[1]) - 1
                j = int(parts[2]) - 1
                if i == j:
                    continue
                ci = st.s[i]
                cj = st.s[j]
                st.update(1, 0, n - 1, i, ci, cj)
                st.update(1, 0, n - 1, j, cj, ci)

            else:
                ch = ord(parts[1]) - 65
                l = int(parts[2]) - 1
                r = int(parts[3]) - 1
                ans = st.query(1, 0, n - 1, l, r, ch)
                res.append(str(ans))

        out.append(" ".join(res))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```セグメント ツリーには、すべてのノードに 26 長の周波数配列が格納されます。 これは中心的なデータ構造です。すべての操作は、これらの配列の維持またはクエリに帰着します。 

SWAP 操作は 2 ポイントの更新として実装されます。 更新ごとにリーフが変更され、親ノードが再計算されます。 更新ロジックでは、古い文字数と新しい文字数が慎重に置き換えられるため、古い頻度が残らないようになります。 古い文字のデクリメントに失敗すると、黙ってカウントが増加するため、これは重要です。 

クエリはツリーを下方に受け渡し、クエリ範囲内に完全に含まれるセグメントからの結果のみを蓄積します。 部分的な重複は再帰的に分割されます。 

## 実用的な例

 ### 例 1

 入力:```
s = ABA
COUNT A 1 2
SWAP 2 3
COUNT A 1 2
```最初のセグメント ツリーはカウントを表します。 

| セグメント | あ | B |
 | --- | --- | --- |
 | [1,3] | 2 | 1 |

 クエリトレース:

 | 操作 | 範囲 | 結果 |
 | --- | --- | --- |
 | カウント A 1 2 | 「AB」 | 1 |
 | スワップ 2 3 | 「AAB」 | - |
 | カウント A 1 2 | 「AA」 | 2 |

 最初のクエリでは、初期配置のみが表示されます。 位置 2 と 3 を交換した後、構造はリーフ ノードと内部合計を更新するため、2 番目のクエリには新しい構成が反映されます。 

これは、更新が将来のクエリに対して完全に永続的であることを示しています。 

### 例 2

 入力:```
s = ABDDACAADBEAA
COUNT A 1 13
COUNT A 1 10
SWAP 2 12
```文字列内で文字を移動するスワップの効果に焦点を当てます。 

スワップの前に、固定セグメントに対してカウントが計算されます。 

| クエリ | セグメント | カウント |
 | --- | --- | --- |
 | 1 | [1,13] | 計算された合計 |
 | 2 | [1,10] | サブセットの合計 |

 位置 2 と 12 を交換すると、ツリーの 2 つの離れた部分が変更されますが、変更されるのは 2 つの葉だけです。 残りの構造はそのまま残り、更新がローカルであることがわかります。 

これにより、更新ごとに O(log n) ノードのみが影響を受けるというセグメント ツリーの不変性が確認されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n) | 各更新は O(log n) ノードに触れ、各クエリは O(log n) セグメントを走査します。 
| スペース | O(26n) | 各セグメント ツリー ノードには、長さ 26 の配列が格納されます。 

n と q の合計が最大 100000 であるため、これは制限内に問題なく収まります。対数係数は小さいままであるため、実際には解が効率的になります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、同じインデックスを交換することです。 その場合、両方の更新が同じリーフをターゲットにしており、ガードがないとコードが誤ってデクリメントおよびインクリメントする可能性があります。 この実装では、i == j の場合に明示的にスキップし、二重変更が発生しないようにします。 

もう 1 つのエッジ ケースは、何度もスワップした後で範囲全体をクエリすることです。 更新はローカルであるため、セグメント ツリーの一貫性は保たれ、全範囲クエリでは正しいグローバル カウントが返されます。 

最後のエッジケースは、多くの操作を伴う文字の交互変換です。 頻繁な更新下でも、各操作は O(log n) ノードにのみ影響するため、隠れた二次関数の動作は現れません。
