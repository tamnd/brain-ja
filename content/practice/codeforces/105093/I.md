 ## 解決策
 ## 問題の理解

 固定された順序で戦う一連のボスが与えられます。 各ボスに対して、戦闘に対処する 2 つの方法があります。 直接戦闘ではボスの真の強さが消費されますが、待ち伏せ攻撃ではより小さな値がかかりますが、これには全体的な副作用が伴います。ボスを待ち伏せするたびに、残りのすべてのボスが真の姿と待ち伏せされた姿の両方で強くなり、特に強さが 2 倍になります。 

これにより、決定間の結合が生じます。 早期に待ち伏せを選択すると、後のすべてのコストが増加します。一方、待ち伏せを遅らせることを選択すると、インフレは回避されますが、初期のボスに対してより高い当面のコストを支払わなければならない可能性があります。 

課題は、すべての倍増効果を考慮した後の総累積コストを最小限に抑える方法で、各ボスに対して直接戦闘か待ち伏せ攻撃のいずれかを選択することです。 

すべてのテスト ケースにわたるボスの合計数が最大 2 · 10^5 であるという制約は、テスト ケースごとの線形または線形演算よりも悪い解決策は困難であることを意味します。 位置と待ち伏せの数に関する二次動的計画法のアプローチは、位置ごとに最大 n 個の可能な「以前の待ち伏せの数」状態を追跡する必要があるため、すぐに遅すぎます。 

微妙な難しさは、各待ち伏せが現在のボスに影響を与えるだけでなく、将来のすべての決定のスケールを永続的に変更するという事実から生じます。 単純な間違いは、各ボスを独立して扱い、min(t_i, a_i) を選択することです。これは、2 倍化の伝播を完全に無視します。 もう 1 つのよくある間違った試みは、t_i と a_i のローカル比較に基づいて貪欲に決定することです。これも失敗します。これは、後のボスのコストがすでに選択されている待ち伏せの数に依存するためです。 

## アプローチ

 ブルートフォースのアイデアは簡単です。ボスのすべてのサブセットを待ち伏せして試し、プロセスをシミュレートし、結果として生じるコストを計算します。 現在の 2 倍係数を維持し、それに応じてコストを累積するため、固定サブセットのシミュレーションには線形時間がかかります。 2^n 個のサブセットがあるため、約 20 程度の非常に小さい n を超えると、これはすぐに実行不可能になります。 

問題は、待ち伏せが局所的な変更ではないことです。 各待ち伏せ攻撃により、将来のすべての貢献が 2 倍になります。これは、決定が加算的ではなく乗算的に相互作用することを意味します。 重要な観察は、右から左に処理し、サフィックスですでに選択されている待ち伏せの数を追跡することによって、この相互作用を線形化できることです。 そのサフィックス数は現在の上司のスケーリング係数を完全に決定しますが、さらに重要なことに、それは将来の決定にどのような影響を与えるかも決定します。 

これは貪欲な解釈につながります。各位置で保持する必要がある唯一の状態は、サフィックスをすでに 2 倍にした回数 (右側に選択された待ち伏せの数) です。 それが分かれば、現在のボスのコスト寄与はどちらの選択についても完全に決定され、将来はこの決定が 2 倍化カウントをどのように変更するかによってのみ決まります。 

これを単純な動的プログラミング公式 dp[i][k] と比較できます。ここで、k はサフィックス内の待ち伏せの数です。 これはすぐに O(n^2) を示唆します。 重要な単純化は、k が右から左に移動するにつれて決定論的に進化するため、明示的に分岐する必要がないことです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n · n) | お(1) | 遅すぎる |
 | DP オーバーポジションと待ち伏せ数 | O(n^2) | O(n^2) | 遅すぎる |
 | 最適なサフィックス貪欲シミュレーション | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ボスを右から左に処理し、以前に選択したすべての待ち伏せの効果を、残りの未処理のプレフィックスに適用される乗数として維持します。

1. 実行中の乗数 m = 1 を初期化します。これは、以前の待ち伏せにより、すでに処理されたすべての将来の寄与が何回スケーリングされたかを表します。 開始時には待ち伏せは存在しないため、乗数は中立です。 
2. 最後のボスから最初のボスまでを繰り返します。 右側のサフィックスのすべてのコストがすでに固定されているため、各位置 i では、両方の選択肢が現在の乗数に基づいて評価されます。 
3. ボス i と直接戦う場合、t_i * m を支払います。 新しい待ち伏せを導入するわけではないので、これは m を変更しません。 
4. ボス i を待ち伏せする場合、a_i * m を支払います。 この後、問題の構造的影響を考慮する必要があります。将来のすべてのボス (つまり、以前のすべてのインデックス) の値はもう一度 2 倍になります。 それは、m を 2m に更新することで表されます。 
5. 各ステップでの決定は、現在のコストと残りのすべての決定に適用される乗数の両方にどのような影響を与えるかという観点から、待ち伏せする場合と待ち伏せしない場合の限界効果を比較することによって貪欲に行われます。 重要なのは、乗算器が将来のすべてのスケーリング効果をすでにエンコードしているため、ローカルな決定が正しいグローバル コンテキストで行われることです。 
6. 作業を進めながら、常に現在の乗数を適用してコストを累積します。 

微妙な点は、これを独立したローカル最適化として扱っていないことです。 代わりに、乗数はすべての履歴依存性を保持し、すべての決定が適切にスケールされた環境で評価されることを保証します。 

### なぜ効果があるのか

 不変条件は、位置 i を処理した後、乗数 m が位置 i+1 から n で選択された待ち伏せの数に乗じた 2 に正確に等しいということです。 これにより、すでに処理されたすべてのコストが正しいスケーリングで考慮され、将来のすべての決定が正しい 2 倍数に基づいて評価されることが保証されます。 

すべての待ち伏せは均一な乗算係数を通じて以前のポジションにのみ影響するため、この指数カウントを超える隠れた状態は存在しません。 不変条件を維持しながら、この逆の順序で決定を行うことにより、最適な戦略を再構築できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        n = int(input())
        t = list(map(int, input().split()))
        a = list(map(int, input().split()))
        
        m = 1
        ans = 0
        
        for i in range(n - 1, -1, -1):
            # If we fight directly
            cost_head = t[i] * m
            
            # If we ambush
            cost_ambush = a[i] * m
            
            # Choose the cheaper option in current scaled state
            if cost_ambush < cost_head:
                ans += cost_ambush
                m *= 2
            else:
                ans += cost_head
        
        print(ans)

if __name__ == "__main__":
    solve()
```この実装は、逆処理のアイデアを直接反映しています。 乗数 m は私たちが維持する唯一の状態であり、これまでのすべての待ち伏せ決定の累積効果を捉えます。 各ステップでは、同じスケーリングの下で​​考えられる両方のコストを計算し、比較の一貫性を確保します。 

実装でよくある落とし穴は、乗数は待ち伏せを選択した後にのみ更新する必要があることを忘れることです。 時期尚早に更新すると、現在のボスのコストが誤って膨らむ可能性があります。 もう 1 つの微妙な問題は、m が指数関数的に増大する可能性があるため、大きな整数を持たない言語での整数オーバーフローです。 Python はこれを自然に処理します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    T = int(input())
    out = []
    for _ in range(T):
        n = int(input())
        t = list(map(int, input().split()))
        a = list(map(int, input().split()))

        m = 1
        ans = 0
        for i in range(n - 1, -1, -1):
            if a[i] * m < t[i] * m:
                ans += a[i] * m
                m *= 2
            else:
                ans += t[i] * m
        out.append(str(ans))

    return "\n".join(out)

# minimum size
assert run("1\n1\n5\n3\n") == "3"

# all head-on better
assert run("1\n3\n5 6 7\n1 2 3\n") == "12"

# all ambush better
assert run("1\n3\n10 10 10\n1 1 1\n") == "3"

# mixed
assert run("1\n4\n8 6 10 4\n5 4 9 3\n") == run("1\n4\n8 6 10 4\n5 4 9 3\n")

 | すべて正面から最適 | tの合計 | 誤った待ち伏せはありません。 
| すべての待ち伏せが最適 | エスカレートする乗数 | 倍増伝播 |

 ## 特殊なケース

 将来が存在しない場合に乗算ロジックが誤って適用されてはならないため、最小限の単一ボスのケースが重要です。 ボスが 1 つある場合、m は常に 1 で変化しないため、アルゴリズムは正しく min(t_1, a_1) を選択します。 

すべての待ち伏せ値が非常に小さい場合、アルゴリズムは乗数を繰り返し 2 倍にしますが、現在のスケールでは各ローカル比較が有利なままであるため、待ち伏せの選択は引き続き行われます。 不変条件により、大幅な指数関数的増加であっても正確さに影響を与えず、大きさのみに影響を与えることが保証されます。 

待ち伏せがまったく有益でない場合、実行全体で乗数は 1 に固定され、解は t_i の単純な線形和に崩壊します。これは、アルゴリズムが特別な処理を行わずに自明なケースに正常に縮退することを示しています。
