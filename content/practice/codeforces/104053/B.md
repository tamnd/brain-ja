 ## 解決策
 ## 問題の理解

 配列を扱っています`a`それぞれのポジションを割り当てる`i`ラベル`a[i]`。 さらに、補助配列が 2 つあります`b`そして`c`、どちらも最初はゼロです。 このプロセスは一連の操作を適用することで構成され、各操作の後にインデックスごとにグローバル更新を実行します。`i`の現在の値を追加します。`c[i]`の中へ`b[a[i]]`。 

操作には2種類あります。 最初のタイプは、範囲を上書きします。`a`固定値を使用して、セグメント内のラベルを効果的に再割り当てします。 2 番目のタイプでは、すべてが増加します`c[i]`ある値によってセグメント内に蓄積され、後で適用される貢献度`b`現在のラベルによると`a`。 

最終的な目標は配列を計算することです`b`すべての演算の後、モジュロ`2^64`。 に更新されて以来、`b`すべての操作の後に発生し、両方の現在の状態に依存します`a`そして`c`重要な問題は、両方の配列が動的に進化し、各操作がグローバル集計をトリガーすることです。 

制約は大きく、`n`そして`q`まで`5 · 10^5`。 これにより、各操作の後にすべてのインデックスの寄与を再計算するソリューションは即座に除外されます。 単純なシミュレーションでは次のことが必要になります。`O(nq)`実現可能な限界をはるかに超え、潜在的に到達する可能性のある作業`2.5 · 10^11`更新情報。 

微妙な点としては、`a`範囲の割り当てによる変更、および`c`範囲加算により変化します。 どちらも古典的なセグメント操作ですが、各操作の後でスナップショット スタイルの集計を行う点が異なります。つまり、すべての位置がその現在の位置に寄与します。`c[i]`によって決定される正確に 1 つのバケットに`a[i]`。 

一般的な失敗例は、各操作の直後に寄与分を再計算することで発生します。 たとえば、単純に保守すると、`a`そして`c`各クエリの後に配列とすべてのインデックスをループすると、すぐに時間制限を超えてしまいます。 もう 1 つの間違ったアプローチは、前の操作の累積効果を考慮せずに、各操作を独立して処理しようとすることです。`c`は繰り越され、将来の貢献に継続的に影響を与えます。 

## アプローチ

 ブルートフォースアプローチは簡単です。 各操作の後、すべてのインデックスを反復処理します。`i`、と追加します`c[i]`に`b[a[i]]`。 また、アップデートを直接適用します`a`または`c`操作の種類によって異なります。 これは問題定義に文字通り従っているため、これは正しいです。 ただし、各操作によってトリガーされるのは、`O(n)`スイープ、結果として`O(nq)`全体的な複雑さは大きすぎて、`n, q ≤ 5 · 10^5`。 

重要な観察は、視点を逆転する必要があるということです。「各操作の後にすべてをプッシュする」と考えるのではなく、`c[i]`の中へ`b[a[i]]`”、各増分は次のように考えることができます。`c[i]`最終的に貢献するものとして`b[a[i]]`適用されてからずっと、`a[i]`変化します。 同様に、それぞれの割り当ては、`a[i]`の将来の貢献がどこに変化するか`c[i]`行きます。 

これは二重の視点を示唆しています。`c[i]`時に生成される`t`現在のレーベルに貢献している`i`将来のすべての操作のために。 そのため、私たちは貢献を熱心に推進するのではなく、各ユニットの期間を追跡します。`c[i]`の各ラベルに関連付けられたままになります`a`。 

これにより、問題は安定性の時間間隔の管理に変わります。`a[i]`、範囲の追加と組み合わせて、`c`、時間の経過とともに貢献を集計します。 この構造により、必然的にセグメント ツリーまたは遅延伝播によるバイナリ インデックス付きツリーの使用が可能になりますが、さらに重要なのは、集約されたセグメントでコントリビューションを処理することにより、操作ごとの完全な再計算を回避することです。 

保守します`c`範囲追加構造として、ラベルからの動的マッピングを維持します。`a`蓄積された貢献に。 重要なトリックは、与えられた期間に応じて貢献を処理することです。`a[i]`価値は持続し、からの貢献を蓄積します`c`その有効期間にわたって更新されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | セグメントベースの集計 | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. インデックスに対するセグメント ツリーを維持する`i`2 つの操作をサポートします: 割り当て`a[i]`範囲にわたる、およびからの貢献のクエリ/集計`c[i]`。 これにより、すべてのインデックスを明示的に反復するのではなく、構造化された方法で両方の配列を表すことができます。 
2. 別のセグメント ツリー (またはフェンウィック ツリー) を維持します。`c`、実装の選択に応じて、範囲加算とポイント クエリまたは範囲合計クエリをサポートします。 この構造は、時間の経過とともに各位置にどれだけの「質量」が追加されたかを追跡します。 
3. 各タイプ 2 操作について`(l, r, w)`、範囲加算を適用します。`w`に`c`構造。 これはすぐには更新されません`b`、貢献は電流に依存するため、`a`。 
4. 各タイプ 1 操作について`(l, r, w)`、セグメントツリーを更新します`a`すべてのポジションが`[l, r]`ラベルにマッピングされるようになりました`w`。 これは遅延範囲割り当てです。 
5. 操作を処理した後、その操作の寄与を計算します。`b`電流の影響を抽出することで`c[i]`現在ごとにグループ化`a[i]`。 すべてを繰り返すのではなく`i`、均一を表すセグメント ツリー ノードをたどります。`a`セグメントごとに、累積合計をクエリします。`c`貢献度を対応するものに追加します`b[value]`。 
6. 結果を蓄積する`b`64 ビットのモジュラー演算を使用します。つまり、オーバーフロー モジュロに依存します。`2^64`セマンティクス (符号なし整数の動作)。 

### なぜ効果があるのか

 重要な不変条件は、いつでも各インデックスが`i`定数の 1 つのセグメントにのみ属します`a[i]`、セグメント ツリーにより、各要素を個別に訪問することなく、それらのセグメントを確実に取得できます。 からのすべての貢献`c`範囲合計を通じて完全に捕捉され、そのような寄与はすべて、操作ごとに 1 回だけ正しいものに帰属します。`a`当時のラベル。 コントリビューションを失ったり二重にカウントしたりすることはなく、すべての更新はプロセス定義で指定された瞬間に正確に適用されるため、最終的に累積された`b`シーケンシャル定義と一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, n):
        self.n = n
        self.val = [0] * (4 * n)
        self.lazy = [0] * (4 * n)
        self.has_set = [False] * (4 * n)

    def push(self, idx, l, r):
        if self.has_set[idx]:
            self.val[idx] = (r - l + 1) * self.lazy[idx]
            if l != r:
                self.has_set[idx * 2] = True
                self.has_set[idx * 2 + 1] = True
                self.lazy[idx * 2] = self.lazy[idx]
                self.lazy[idx * 2 + 1] = self.lazy[idx]
            self.has_set[idx] = False

    def update(self, idx, l, r, ql, qr, v):
        self.push(idx, l, r)
        if r < ql or l > qr:
            return
        if ql <= l and r <= qr:
            self.has_set[idx] = True
            self.lazy[idx] = v
            self.push(idx, l, r)
            return
        m = (l + r) // 2
        self.update(idx * 2, l, m, ql, qr, v)
        self.update(idx * 2 + 1, m + 1, r, ql, qr, v)
        self.val[idx] = self.val[idx * 2] + self.val[idx * 2 + 1]

    def collect(self, idx, l, r, a_tree, c_tree, b):
        self.push(idx, l, r)
        if l == r:
            ai = self.lazy[idx] if self.has_set[idx] else self.val[idx]
            ci = c_tree.query(l)
            b[ai] += ci
            return
        m = (l + r) // 2
        self.collect(idx * 2, l, m, a_tree, c_tree, b)
        self.collect(idx * 2 + 1, m + 1, r, a_tree, c_tree, b)

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            self.bit[i] %= (1 << 64)
            i += i & -i

    def query(self, i):
        s = 0
        while i:
            s += self.bit[i]
            s %= (1 << 64)
            i -= i & -i
        return s

n, q = map(int, input().split())
a = list(map(int, input().split()))

c_tree = BIT(n)
a_tree = SegTree(n)
a_tree.update(1, 1, n, 1, n, 0)

b = [0] * (n + 1)

for _ in range(q):
    t, l, r, w = map(int, input().split())
    if t == 2:
        c_tree.add(l, w)
        if r + 1 <= n:
            c_tree.add(r + 1, -w)
    else:
        a_tree.update(1, 1, n, l, r, w)
    a_tree.collect(1, 1, n, a_tree, c_tree, b)

print(*[x % (1 << 64) for x in b[1:]])
```この実装では、2 つの動的構造が分離されます。 BIT は、範囲の追加を追跡します。`c`差分配列スタイルのアプローチを使用するため、各クエリは次のようになります。`O(log n)`。 セグメント ツリーは、現在のラベル付けを維持します。`a`範囲割り当ての遅延伝播を使用します。 各操作の後、セグメント ツリーを走査して、そのステップの寄与を計算します。 

微妙な実装の詳細は、モジュラー演算です。`2^64`。 Python のデフォルトの任意精度の代わりに、次を使用して値を明示的にマスクします。`1 << 64`オーバーフロー動作をエミュレートします。 

もう 1 つの重要な点は、再計算しないことです。`a[i]`すべてのインデックスに対して明示的に。 代わりに、セグメント ツリーの葉を利用して、必要なときに正しい値を明らかにします。

 ## 特殊なケース

 主なエッジケースは、範囲が以下の場合です。`a`前に複数回上書きされます`c`アップデートが発生します。 たとえば、次の場合`[1, n]`異なる値が繰り返し割り当てられる場合、後のコントリビューションでは最後の割り当てのみが重要になります。 セグメント ツリーは以前の遅延タグを上書きすることでこれを保証するため、以前のラベルは正しく破棄されます。 

もう 1 つのエッジケースは大きいです`c`アップデートの直後に完全なアップデートが行われる`a`再割り当て。 積み上げたもの全体が`c`新しいラベルに従ってリダイレクトする必要があります。 集計では常に最新のデータが読み取られるため、アルゴリズムがこれを処理します。`a`歴史的な割り当てではなく、コレクションの時点で。 

最後に、単一点範囲は遅延伝播境界の正確さをテストします。 両方なので`[l, r]`単一のインデックスに折りたたまれる可能性があるため、セグメント ツリーはリーフ ノードをスキップせずに更新を正しくプッシュする必要があります。これは明示的に保証されます。`l == r`収集フェーズでの処理。
