 ## 解決策
 ## 問題の理解

 インストールされているアプリのリストが記載された電話が与えられます。 各アプリはある程度のメモリを消費し、削除した場合の利便性の損失として測定される「コスト」も発生します。 すべてのアプリは 1 つまたは 2 つのコンビニエンス ポイントを提供します。 

タスクは、解放されたメモリの合計が少なくとも必要なしきい値になるように、アプリのサブセットを削除することです。$m$利便性の全体的な損失を最小限に抑えながら。 十分なメモリを解放できない場合は、その事実を報告する必要があります。 

したがって、入力により 2 つの並列配列が得られます。1 つはメモリ サイズを記述し、もう 1 つは各アプリの「重要性」を記述します。 合計サイズに関するナップザックのような制約を満たすサブセットを選択していますが、取り得る値が 2 つだけであるため、コストは非常に単純です。 

ソリューションを形成する主な制約は、すべてのテスト ケースにわたるアプリの総数です。$2 \cdot 10^5$。 これにより、すべてのサブセットを試行したり、メモリ値に対して二次動的計画法を使用したりするソリューションは即座に除外されます。 ナップザックが一杯になった$m$それも不可能なので$m$到達できる$10^9$。 

一般的な失敗モードは、これを標準的なナップサックまたは比率による貪欲な問題のように扱うことから発生します。 たとえば、メモリ対コスト比が最適なアプリを選択すると失敗する可能性があります。 

入力:```
3 10
6 5 4
2 1 1
```貪欲な比率では、合計メモリ 11 コスト 3 に対して (6,2) と (5,1) を選択する可能性があります。しかし、最適なのは (6,2)+(4,1)=10 コスト 3 なので、同点であれば間違いが隠れる可能性があります。 さらに悪い例としては、コストが 1 または 2 のみで連続的ではないために貪欲が失敗する場合があります。 

もう 1 つの微妙なエッジ ケースは、最適なソリューションでは多くの低コストのアプリ (b = 1) が使用されるが、単純なアプローチでは b = 2 のアプリが最初に使い果たされてしまい、停止が早すぎる場合です。 

コストが 1 か 2 だけであるという構造が、問題を扱いやすくしています。 

## アプローチ

 ブルート フォース アプローチでは、アプリのすべてのサブセットを列挙し、総メモリと総コストを計算して、最適な有効なサブセットを取得します。 すべてのサブセットがチェックされるため、これは概念的には機能しますが、それには次のことが必要です。$2^n$評価は、たとえ$n = 40$。 

より構造化されたブルート フォースは、インデックスとメモリ合計に対する再帰または DP を使用してすべてのサブセットを試行することですが、メモリ ディメンションは最大です。$10^9$、DP 状態空間の爆発が即座に行われます。 

重要な観察は、コストは二値的であるということです。すべてのアプリは 2 つのグループのいずれかに属します。 これは、アプリをコストに基づいて 2 つのリストに分けることを提案しています。 各グループのアプリをメモリの降順で並べ替えると、最適なソリューションはコスト 1 グループとコスト 2 グループからいくつかの最大メモリ項目を取得します。 

ただし、トレードオフはグローバルであるため、個別に選択するだけでは十分ではありません。場合によっては、より多くのメモリを解放できる場合には、コスト 2 のわずかに小さいアプリを使用する方が良い場合があります。 

重要な洞察は、すべてのアプリをメモリの降順で並べ替えますが、コスト 2 のアプリをいくつ含めるかを段階的に選択できる方法で処理することです。 ソート後に両方のグループのメモリのプレフィックス合計を事前計算します。 次に、最良の結果を得るために可能な限りすべての計算を試みます$k$コスト 2 のアプリを使用し、残りのメモリ要件をコスト 1 のアプリを使用して満たします。 

これにより、サブセットを検索するのではなく、ソートされた 2 つのシーケンスをプレフィックス合計と結合するという問題が軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(2^n)$|$O(n)$| 遅すぎる |
 | 最適 (ソート + 貪欲 + プレフィックス合計) |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 アプリケーションをコスト 1 のグループとコスト 2 のグループの 2 つのグループに分割しました。 

1. すべてのアプリをコストに基づいて 2 つのリストに分けます。 これにより、相互にトレードオフする 2 つの「価格帯」が分離されます。 
2. 両方のリストをメモリ サイズの降順に並べ替えます。 これにより、いつでも$k$グループからアプリを選択する場合、メモリ獲得の点で最も効率的なものを常に採用しています。 
3. 両方のグループのプレフィックス合計配列を構築します。 インデックスのプレフィックスの合計$i$最良のものを使用して取得可能な最大のメモリを提供します$i$そのタイプのアプリ。 
4. 利用可能なメモリの合計を計算します。 すべてのアプリを取得しても足りない場合は、すぐに -1 を出力します。 
5. 考えられる数字ごとに$i$コスト 2 のアプリ (0 から len(b2) まで) を取得し、獲得したメモリを計算します。 すでに届いている場合$m$、記録コスト$2i$。 
6. 十分でない場合は、必要な残りのメモリを計算し、プレフィックス合計の二分探索を使用して必要なコスト 1 アプリの数を決定します。 
7. すべての有効な分割にわたる最小総コストを追跡します。 

これが機能する理由は、コスト 2 のアプリはコスト的には厳密に劣りますが、アイテムごとのメモリでは潜在的に優れているため、唯一意味のある決定は、それらを含める数だけであるためです。 修正されると、残りはコスト 1 のアプリからの 1 つの貪欲なフィルに減ります。 

### なぜ効果があるのか

 最適なソリューションは、各コスト グループ内で選択したアプリが最大のメモリを搭載するように再配置できます。 ソリューションでメモリの小さいアプリが使用されている一方で、同じグループ内でメモリの大きいアプリが使用されていない場合、スワップによりコストを増加させることなく実現可能性が向上または維持されます。 この交換引数により、各グループ内のプレフィックス選択のみを考慮しても最適な構成を見逃すことがなくなります。 両方のグループがプレフィックスの選択肢に縮小されると、残る自由度はコスト 2 のグループからどれだけの項目を取得するかだけになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))
        
        ones = []
        twos = []
        
        total = 0
        
        for ai, bi in zip(a, b):
            total += ai
            if bi == 1:
                ones.append(ai)
            else:
                twos.append(ai)
        
        if total < m:
            print(-1)
            continue
        
        ones.sort(reverse=True)
        twos.sort(reverse=True)
        
        pre1 = [0]
        for x in ones:
            pre1.append(pre1[-1] + x)
        
        pre2 = [0]
        for x in twos:
            pre2.append(pre2[-1] + x)
        
        ans = float('inf')
        
        j = len(ones)
        
        for i in range(len(twos) + 1):
            mem2 = pre2[i]
            cost = 2 * i
            
            if mem2 >= m:
                ans = min(ans, cost)
                continue
            
            need = m - mem2
            
            # smallest j such that pre1[j] >= need
            l, r = 0, len(ones)
            while l <= r:
                mid = (l + r) // 2
                if pre1[mid] >= need:
                    j = mid
                    r = mid - 1
                else:
                    l = mid + 1
            
            if pre1[j] >= need:
                ans = min(ans, cost + j)
        
        print(ans if ans != float('inf') else -1)

if __name__ == "__main__":
    solve()
```実装では、まずアプリを 2 つの配列に分割し、それぞれを並べ替えます。 プレフィックスの合計により、各グループから固定数を取得する定数時間の評価が可能になります。 二分探索では、コスト 2 アプリの選択を固定した後に必要なコスト 1 アプリの最小数が見つかります。 これにより、合計の繰り返しの再計算が回避され、2 番目のグループの反復ごとに解が対数時間内に保たれます。 

微妙な点は、残りの要件が変化するため、コスト 2 のカウントを選択するたびに二分探索を再計算する必要があることです。 もう 1 つの重要な詳細は、コスト 2 のアプリだけですでに要件を満たしている場合の処理​​です。 

## 実用的な例

 ### 例 1

 入力:```
n=5, m=7
a=[5,3,2,1,4]
b=[2,1,1,2,1]
```私たちは次のように分けました。 

| グループ | 値 |
 | --- | --- |
 | コスト1 | [3,2,4] |
 | コスト2 | [5,1] |

 並べ替え:

 コスト1 → [4,3,2]

 コスト2 → [5,1]

 プレフィックスの合計:

 コスト 1: [0,4,7,9]

 コスト 2: [0,5,6]

 選択肢を試してみます。 

| コスト2カウント | メモリ2 | 残り | 最良のコスト1 | 総費用 |
 | --- | --- | --- | --- | --- |
 | 0 | 0 | 7 | 2 (3+4) | 2 |
 | 1 | 5 | 2 | 1 | 3 |
 | 2 | 6 | 1 | 0 | 4 |

 最小値は 2 です。 

これにより、高価なコスト 2 のアプリを完全にスキップすることが最適であることがわかります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(n \log n)$| 並べ替えが優先されます。 各テストでは、コスト 1 のプレフィックスに対する二分探索を使用して、コスト 2 のアイテムに対する線形スキャンも実行されます。 
| スペース |$O(n)$| 2 つのグループとプレフィックスの合計を保存する |

 合計の複雑さは安全です。$n$テスト全体の境界は次のとおりです$2 \cdot 10^5$、そして各演算はその合計において最大でも対数または線形です。
