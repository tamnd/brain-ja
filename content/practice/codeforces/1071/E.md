 ## 解決策
 ## 問題の理解

 私たちは、ロープで形成された堅くて柔軟な「バー」を制御しています。その端点は、高さ 0 と高さ 2 つの水平セグメントに沿ってスライドするように拘束されています。$h$。 いつでも、ロープは下部レール上の点と上部レール上の点を接続する直線セグメントです。 各エンドポイントは独自のレールに沿って移動できますが、そこから離れることはできず、その速度は共有最大値によって制限されます。$v$。 

雨粒が次々と降り注ぐ。 各ドロップは、レール間の垂直ストリップ内の時間と点によって定義されます。 ドロップが到着すると、その時点でロープのセグメントがその点を通過する必要があります。 与えられた初期位置から開始する 2 つの端点の連続動作を選択することができ、それぞれの時点でそのような「セグメントには点が含まれなければならない」という制約をすべて満たすことを可能にする、可能な限り最小の最大速度が必要です。 

入力サイズにより解決策が強制されます$O(n \log n)$または$O(n \log^2 n)$。 と$n \le 10^5$、細かい離散化で連続運動をシミュレートしたり、重いジオメトリを使用して速度推定ごとに独立して実行可能性をチェックしたりする試みは、各チェックがほぼ線形で数値的に安定していない限り、遅すぎます。 

素朴なアプローチの最も脆弱な部分は、各雨粒を個別に処理することです。 一定時間、ロープ拘束は 2 つの端点で同時に幾何学的条件となり、これらの拘束は速度制限を通じて時間の経過とともに相互作用します。 もう 1 つの微妙な失敗は、制約を満たすためにエンドポイントを常に「ジャンプ」できると想定し、連続する必要な構成間の移動が実現可能性を決定するということを無視していることから発生します。 

典型的な誤ったシナリオは、エンドポイント間で十分な速度で移動しない限り、2 回の連続ドロップによって互換性のないロープ構成が強制される場合です。 各ドロップが個別に到達可能かどうかのみをチェックする貪欲なソルバーは、次のようなケースを誤って受け入れます。 

ロープを通さなければなりません$(1, 4)$で$t=1$、 それから$(4, 4)$で$t=2$。 エンドポイントが遠くから始まる場合、たとえそれぞれの制約だけが幾何学的に実現可能であっても、必要な水平移動は想定される小さな速度を超える可能性があります。 

## アプローチ

 最大の問題は、各雨滴が 2 つの移動点によって定義される線分に幾何学的制約を課し、これらの制約が正確なタイムスタンプで満たされなければならないことです。 ロープをセグメントとして考える代わりに、端点の X 座標で表す方がより生産的です。$a(t)$下のレールと$b(t)$上部のレールの上。 時のロープ$t$間のセグメントです$(a(t), 0)$そして$(b(t), h)$。 

ポイント$(x, y)$垂直比に沿った線形補間を満たす場合、このセグメント上に正確に位置します。$$x = a(t) + \frac{y}{h}(b(t) - a(t)).$$これを書き直すと、次の線形制約が与えられます。$a(t)$そして$b(t)$:$$x = (1 - \lambda)a(t) + \lambda b(t), \quad \lambda = \frac{y}{h}.$$したがって、各雨滴は、特定の時間における 2 つの終点の位置を関連付ける線形方程式を定義します。 時間と時間の間に、各エンドポイントは制限された速度で移動します。これは、次の実現可能な値を意味します。$a(t)$そして$b(t)$リプシッツ条件によって制約された区間として進化します。 

強引なアイデアは、実行可能なすべてのペアを維持しながら、時間を継続的にシミュレートすることです。$(a, b)$。 そのセットは、時間の経過とともに変化する 2D の凸領域であり、各イベントでライン制約と交差します。 ただし、最大で任意の凸領域を維持します。$10^5$交差点は遅すぎて複雑すぎます。 

重要な観察は、固定速度での実現可能性をテストできることです。$v$イベントを時間順に処理し、各エンドポイントのすべての可能な位置のセットを間隔として維持することによって。 雨滴ごとに、制約により実行可能な間隔のペアが減少します。 イベント間の各間隔は、$v \cdot \Delta t$両方向に。 

これは到達可能な状態の順伝播になりますが、制約が結合しているため、$a$そして$b$、状態は 2 つの独立した区間ではなく、2D ストリップ内の実行可能な領域です。 重要な単純化は、実行可能領域が線形複雑度以下の凸多角形のままであり、その境界は常に一定数の「アクティブな」制約によって決定されることです。 

最小値を見つけるには$v$、答えを二分探索します。 候補者ごとに$v$、間隔伝播と制約クリッピングを通じて、可能なエンドポイント位置のセットを暗黙的に維持しながら、時間順に実現可能性をシミュレートします。 どこかの時点で実行可能領域が空になった場合、それは$v$では不十分です。

 ## アルゴリズムのチュートリアル

 候補速度を修正します$v$すべての制約が満たされるかどうかをテストします。 

1. 左端点のすべての可能な位置のセットを維持します。$a$そして右端点$b$現時点では 2D の凸状の実行可能領域として表されますが、最後のイベントから派生した境界を使用して暗黙的に表されます。 これが機能するのは、移動の制約が時間的に線形であり、凸性が維持されるためです。 
2.初期状態からスタート$a(0) = e_1$、$b(0) = e_2$。 これは状態空間内の単一点であり、動きの前には不確実性がゼロであることを表します。 
3. 雨粒ごとに時間の増加順に時間差を計算します。$\Delta t$前回のイベントから。 実現可能性を拡大する:$a$そして$b$それぞれが最大で独立して移動できます$v \cdot \Delta t$、したがって、到達可能な領域はダイヤモンド形の拡張になります。$(a, b)$-空間。 
4. 雨滴の状態を線形制約に変換します。$$(1-\lambda)a + \lambda b = x, \quad \lambda = \frac{y}{h}.$$これにより、実行可能領域が線でスライスされます。 拡張された領域をこの線と交差させ、問題を少なくとも 1 つの実行可能なペアが存在するかどうかを見つけることに落とし込みます。$(a, b)$モーション境界とロープ拘束の両方を満たします。 
5. 交差は、線形関係を代入した後、1 つの変数への実行可能領域の射影が空でないかどうかをチェックすることに帰着します。 代数的に次のように代入します。$b$に関しては$a$、次の 1D 間隔制約が得られます。$a$。 
6. 私たちはこの間隔を長期間維持します。 拡張ステップごとに次のように拡大します。$v \cdot \Delta t$、各制約は、線形方程式から導出された別の区間と交差します。 
7. いずれかのステップで間隔が空になった場合、現在の$v$は無効です。 
8. すべてのイベントが正常に処理されると、候補者は$v$実現可能です。 

二分探索をします$v$十分に広い範囲にわたって、通常は最大$10^9$必要な精度まで調整します。 

### なぜ効果があるのか

 いつでも、速度制約の下にあるエンドポイントのすべての有効な構成は、凸集合を形成します。$(a, b)$-空間。 それぞれの雨滴は、この凸集合を線と交差させる線形等式制約を導入します。 イベント間のモーションでは、凸性を維持しながら正方形のミンコフスキー和を適用します。 列挙ではなく実行可能性のみが必要なため、状態は投影後に単一の間隔を追跡するように崩壊します。 凸性により、解が存在する場合、それがこの区間表現によって捕捉され、近似によって失われないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check(v, n, w, h, e1, e2, drops):
    lo, hi = e1, e1
    lo2, hi2 = e2, e2
    prev_t = 0

    for t, x, y in drops:
        dt = t - prev_t
        prev_t = t

        move = v * dt
        lo -= move
        hi += move
        lo2 -= move
        hi2 += move

        lo = max(lo, 0)
        hi = min(hi, w)
        lo2 = max(lo2, 0)
        hi2 = min(hi2, w)

        lam = y / h

        # from x = (1-lam)a + lam b => b = (x - (1-lam)a)/lam
        # feasibility reduces to existence of a in [lo, hi]
        # such that resulting b in [lo2, hi2]

        if lam == 0:
            if not (lo <= x <= hi):
                return False
            continue

        if lam == 1:
            if not (lo2 <= x <= hi2):
                return False
            continue

        # derive constraints on a
        a1 = (x - lam * hi2) / (1 - lam)
        a2 = (x - lam * lo2) / (1 - lam)

        if a1 > a2:
            a1, a2 = a2, a1

        lo = max(lo, a1)
        hi = min(hi, a2)

        if lo > hi:
            return False

    return True

def solve():
    n, w, h = map(int, input().split())
    e1, e2 = map(int, input().split())
    drops = [tuple(map(int, input().split())) for _ in range(n)]

    def ok(v):
        return check(v, n, w, h, e1, e2, drops)

    lo, hi = 0.0, 1e9
    for _ in range(60):
        mid = (lo + hi) / 2
        if ok(mid):
            hi = mid
        else:
            lo = mid

    print(hi)

if __name__ == "__main__":
    solve()
```このソリューションは、実現可能性のチェックを最適化から分離します。 の`check`関数は時間を順番にシミュレートし、速度に基づいて到達可能な終点位置を拡張し、雨滴によって引き起こされる各線形制約と交差します。 二分探索はこの実現可能性テストをラップし、有効な最小速度に収束します。 

デリケートな点は、ロープ コンストレイントの置換の処理です。 代数は、1 つの変数を分離し、それを区間制限に正しく変換するという点で一貫性がなければなりません。 もう 1 つの微妙な点は、移動が物理的に制限されるため、拡張後にエンドポイントの位置をレールの境界に固定することです。$[0, w]$。 数値の安定性が重要であるため、すべての比較は浮動小数点で行われ、バイナリ検索の精度は控えめに選択されます。

 ## 特殊なケース

 重大なエッジ ケースは、2 つの連続した雨滴によって矛盾したエンドポイントの順序が強制される場合です。 たとえば、上部レールでのドロップでは、両方のエンドポイントを効果的に修正する特定の線形関係が強制され、次のドロップでは逆の構成が必要になります。 最初の制約の後に実行可能な間隔が崩壊し、時間間の拡張ではオーバーラップを再導入するには不十分であるため、アルゴリズムはこれを処理します。$v$十分な大きさです。 

別のケースでは、雨滴が 1 つのレールの非常に近くにある場合に発生し、$\lambda$実装ではこれらの縮退を明示的に処理するため、除算によって浮動小数点誤差が増幅されず、区間交差の正確性が維持されます。 

最後の微妙なケースは、長い時間の空白です。 2 つの制約が個別に互換性がある場合でも、大きな$\Delta t$交差する前に実行可能領域を強制的に拡張します。 この拡張が両方のエンドポイントに対称的に適用されない場合、実現可能性チェックでは到達可能な状態が過小評価され、不可能であることが誤って報告されます。
