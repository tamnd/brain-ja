 ## 解決策
 ## 問題の理解

 配列が与えられ、配列全体を左から右にカバーする連続したセグメントに分割することができます。 各セグメントは、要素の XOR である 1 つの値に要約されます。 配列がこれらのセグメント XOR に圧縮されたら、それらすべてのセグメント値のビットごとの OR を計算します。 タスクは、この最終的な OR が指定された制限を超えないようにセグメントの最大数を選択することです。$x$。 有効なセグメンテーションを 1 つも作成できない場合は、次のように出力します。$-1$。 

この構造では、配列を強制的に連続ブロックに分割するため、実際に決定するのはカット ポイントをどこに配置するかです。 各カットは XOR の集計方法を変更し、それらの XOR 結果は OR を介して相互作用します。これは XOR とはまったく異なる動作をします。 XOR はローカルで可逆的ですが、OR はビットを蓄積するだけでビットを削除しないため、すべてのセグメントが一部のビットを永久に「ロックイン」する可能性があります。 

制約は、ソリューション形状の主な信号です。 合計あり$n \le 10^5$すべてのテスト ケースにわたって、すべてのセグメンテーションやエンドポイント上の二次 DP さえも試行するアプローチは失敗します。 テスト ケースごとに線形または線形に近いアプローチが必要で、これには貪欲な構築やビットごとの推論が含まれる可能性があります。 

いくつかのエッジケースは、素朴な思考がどこで崩れるかを明らかにします。 

すべての要素がゼロの場合、$x = 0$、すべてのセグメンテーションが有効であり、答えは次のようになります。$n$。 OR の寄与がゼロになったときに早期に停止する貪欲なプログラムは、ここでは失敗します。 

もし$x = 0$しかし、配列要素がゼロ以外の場合は、配列全体をカバーする 1 つのセグメントでもゼロ以外の XOR が生成され、直ちに OR 境界に違反するため、有効なセグメンテーションが存在しません。 

もし$x$には設定ビットがほとんどないため、セグメントの XOR で禁止ビットが導入された場合は、単一のセグメントでも不可能になる可能性があります。 配列全体の合計 XOR のみを追跡する単純なアプローチでは、これを見逃してしまいます。 

主な問題点は、各セグメントが独立して寄与するため、分割すると OR が増加することです。 これにより緊張が生じます。セグメントが増えると OR の可能性が高まりますが、ビットの分離にも役立つ可能性があります。 

## アプローチ

 ブルートフォース戦略では、配列をセグメントに分割するためにあらゆる方法が試行されます。 パーティションごとに、各セグメントの XOR を計算し、すべてのセグメントの結果を OR します。 これは正しいですが、実行不可能です。 配列のパーティション数は指数関数的です。$n$、 具体的には$2^{n-1}$また、XOR を効率的に計算しても、組み合わせ爆発は減少しません。 

より構造化された総当たり攻撃により、セグメントの数が修正されます。$k$を実行し、実現可能性を確認してみます。 それでも、カットポイントを複数人に分配すると、$n$ポジションは～につながります$\binom{n-1}{k-1}$可能性はありますが、最悪の場合でも指数関数的に増加します。 

重要な洞察は、視点を逆転させることです。 セグメントを構築して OR を計算する代わりに、セグメントのビットに焦点を当てます。$x$。 セグメント XOR はビットを OR に提供し、セグメント XOR にビットが現れると、そのビットは永続的に組み込まれます。 これは、すべてのセグメントの XOR がビットマスクのサブセットであるセグメンテーションのみを使用できることを意味します。$x$。 それ以外の場合、OR は次の値を超えます$x$。 

したがって、問題は次のようになります。各セグメントの XOR が外部のビットを導入しないように、配列をできるだけ多くのセグメントに分割します。$x$。 セグメントの数を最大化したいので、できるだけ早くカットする必要がありますが、それは現在のセグメントの XOR がまだ有効な場合に限られます。$x$。 

これにより、問題は貪欲スキャンに変換されます。つまり、現在のプレフィックス セグメントの XOR が「互換性」がある場合は常に、左から XOR を蓄積します。$x$、セグメントを閉じます。 ただし、妥当性と最大限の削減について慎重に検討しない限り、貪欲だけでは十分ではありません。 

最適なアプローチは、有効なセグメンテーションが、各セグメントの XOR がビット制約内に収まるプレフィックス XOR 境界のシーケンスに対応することを観察することです。 セグメントの最大数は、不必要にカットを延期しないようにしながら、制約に違反することなくセグメントを安全に終了できるときにカットすることによって達成されます。 

これにより、問題は、実行中の XOR と、現在の XOR がセグメント終了として受け入れられるかどうかに関する条件を伴う単一パスに縮小されます。

 ## アルゴリズムのチュートリアル

 配列を左から右にスキャンしながら、実行中の XOR を維持します。 この実行中の XOR は、構築中の現在のセグメントの XOR を表します。 

1. 変数を初期化する`cur_xor = 0`そしてカウンター`segments = 0`。 OR アキュムレータも実行し続けます`or_acc = 0`。 
2. 配列を反復処理します。 要素ごとに更新します`cur_xor ^= a[i]`。 これにより、現在のセグメントが拡張されます。 
3. 更新後、このセグメント値を追加すると制約に違反するかどうかを確認します。 セグメントは、外部ビットを導入しない場合にのみ「安全」になります。$x$を検証することでチェックされます。`cur_xor | or_acc`まだ ≤$x$。 直感的には、完成したセグメントの XOR に現れるビットは、最終的な OR に永続的に寄与すると考えられます。 
4. 条件が満たされる場合、このセグメントを終了します: インクリメント`segments`、 アップデート`or_acc |= cur_xor`、そしてリセット`cur_xor = 0`。 これは、有効性を維持しながら、セグメントをできるだけ早く閉じることを意味します。 
5. 配列の最後にある場合`cur_xor`がゼロでない場合は、それを最終セグメントとして扱い、同じ方法で検証する必要があります。 制約に違反する場合は戻ります$-1$。 
6. 戻る`segments`。 

セグメントが有効になったらすぐに閉じるという貪欲な選択は正しいです。カットを遅らせるとセグメントがマージされるだけで、セグメントの数が減り、OR はセグメントが増えると増大するだけなので制約には役立ちません。 

### なぜ効果があるのか

 各セグメントは、最終的な OR に固定 XOR 値を寄与し、これらの寄与は独立しています。 いずれかのセグメントの XOR にビットが出現すると、そのビットは OR 結果に永久に残ります。 このアルゴリズムにより、無効なビットが導入されず、実行可能性が低下しない場合にのみセグメントがコミットされることが保証されます。 セグメントをマージしても OR を減らすことはできず、セグメントの数を減らすだけであるため、最も早い安全なカットが常に最大値を保持します。 

不変条件は、どの時点でも、`or_acc`すべてのファイナライズされたセグメントの正確な OR が含まれており、`cur_xor`は完成が未定の候補セグメントを表す。 すべてのカットは、セグメントをさらに拡張しても答えが増加しない、または実現可能性に違反しない場合にのみ行われます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, x = map(int, input().split())
    a = list(map(int, input().split()))

    or_acc = 0
    cur_xor = 0
    segments = 0

    for v in a:
        cur_xor ^= v

        # if current segment XOR already exceeds allowed bits, we must stop
        if (cur_xor | or_acc) <= x:
            # greedily cut here
            segments += 1
            or_acc |= cur_xor
            cur_xor = 0

    # leftover segment
    if cur_xor:
        if (cur_xor | or_acc) <= x:
            segments += 1
        else:
            print(-1)
            return

    print(segments)

t = int(input())
for _ in range(t):
    solve()
```この実装は貪欲スキャンを直接ミラーリングします。 XOR の累積によって現在のセグメントが定義されます。 OR アキュムレータには、以前のセグメントによってすでにコミットされたすべてのビットが格納されます。 決定的な条件`(cur_xor | or_acc) <= x`禁止ビットが決して導入されないようにします。 

最後の残りのチェックが必要なのは、最後のセグメントがループ内で閉じられていない可能性があり、それを無視すると無効なパーティションが黙って受け入れられてしまうためです。

 ## 特殊なケース

 重大なエッジケースは次のような場合です。$x = 0$。 この状況では、すべてのセグメントの XOR が 0 である必要があり、そうでない場合は 1 ビットでも制約に違反します。 アルゴリズムはこれを処理します。`cur_xor`すぐに原因となる`(cur_xor | or_acc)`超える$x$、無効なカットを防止し、強制的にリターンします。$-1$ただし、配列全体の XOR 構造ですべてのセグメントがゼロになることが許可されている場合は除きます。 

配列にゼロのみが含まれる場合、別のエッジ ケースが発生します。 ここ`cur_xor`は常にゼロであり、すべての位置が有効なカットをトリガーします。 アルゴリズムが生成するのは、$n$OR 制約に影響を与えることなく各要素を分離できるためです。 

3 番目のケースは、配列に XOR でキャンセルされる交互ビットがあるが、それでも中間の非ゼロ プレフィックスが導入される場合です。 貪欲な構造により、安全な場合にのみカットすることが保証され、OR は終了したセグメントのみを追跡するため、早期の制約違反は発生しません。
