 ## 解決策
 ## 問題の理解

 与えられるポジションのリストは増え続け、ラインから選手を繰り返し削除するプロセスが与えられます。 各ラウンドで現在のラインナップを確認し、ポジションにいる選手を排除しようとします。$a_1, a_2, \ldots, a_k$。 これらのポジションは常に、元のラインナップではなく、現在残っているラインナップを基準にして解釈されます。 要求された順位が現在のプレーヤー数より大きい場合、その順位はそのラウンドでは無視されます。 ラウンド内で可能なすべての削除が同時に実行された後、短縮されたラインでプロセスを繰り返します。 削除なしでフルラウンドが終了するとゲームは終了し、残ったものが勝者として宣言されます。 

クエリごとに$n_i$、私たちは尋ねられます：から始めます$n_i$プレイヤー、最後に何人が生き残るのか。 

制約は非常に特殊な点で小さいです。 両方$k$そしてそれぞれ$a_i$最大 100 であり、各クエリ$n_i$これは、システムが十分に小さいため、慎重に実行すればプロセスを直接シミュレートすることが可能であることを直ちに示唆しています。 ただし、クエリごとの単純なシミュレーションは、各ラウンドで削除とスキャンの繰り返しが行われるため、実装が非効率であれば依然として無駄になります。 

さらに微妙な点は、このプロセスは決定論的ですが、削除のたびに変更される相対インデックス作成にのみ依存していることです。 そのため、誤ってインデックスを静的に扱ったり、削除によって位置が移動することを忘れたりした場合に、誤って実装することが容易になります。 

いくつかの特殊なケースが重要です。 

もし$n < a_1$の場合、削除は発生しないため、すべてのプレイヤーが勝者となります。 たとえば、次の場合$a = [3, 5]$そして$n = 2$の場合、答えは 2 でなければなりません。盲目的にインデックスにアクセスしようとする単純な実装では、誤って削除を試行したり、誤って配列を縮小したりする可能性があります。 

複数の場合$a_i$値が現在のサイズを超えている場合は、各ラウンドで境界内の値のみを考慮する必要があります。 たとえば、次の場合$a = [2, 4, 6]$現在のサイズは 3 なので、位置 2 のみが削除されます。 

最後に、不用意なアプローチでは、インデックスが固定されていると仮定して、ラウンドごとに削除される数を事前計算しようとする可能性があります。 ラウンド内の削除が同時に発生し、将来のインデックス作成が非線形に変更されるため、これは失敗します。 

## アプローチ

 ブルートフォースのアプローチは簡単です。プレイヤーのリストを明示的に管理し、ラウンドをシミュレートします。 各ラウンドでリストに目を通し、位置をマークします。$a_1, a_2, \ldots, a_k$現在のリストではまだ有効です。 次に、それらを削除し、完全なパスで削除がなくなるまで繰り返します。 

これはプロセス定義に直接従うため、正しく機能します。 問題はパフォーマンスです。各ラウンドで最大 100 個の要素をスキャンし、最大 100 個の要素を繰り返す可能性があります。$O(n)$最悪の場合はラウンド。 横切って$q$クエリの場合、これは制約が 100 までであれば快適に小さくなりますが、それでも不必要に重く、ラウンドごとにリストの再構築を行うと実装の効率が低下する危険性があります。 

重要な観察は、状態空間が小さいということです。 プレーヤーの数は最大 100 人であるため、クエリごとに個別にシミュレーションする代わりに、すべてのプレーヤーの答えを事前計算できます。$n \in [1, 100]$。 各シミュレーションは有界システム内で実行され、決定的な結果が生成されます。 考えられるすべての初期サイズの結果を一度計算したら、O(1) で各クエリに答えます。 

シミュレーション自体を若干改善することもできます。リストを繰り返し再構築する代わりに、ブール配列を維持するか、リストを使用して、必要な場合にのみ再構築します。 すべてが小さいため、微細な最適化よりも明確さが重要です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとのブルート フォース シミュレーション |$O(q \cdot n^2)$|$O(n)$| 受け入れられます (かろうじて、小さな制約) |
 | すべてを事前計算する$n \le 100$|$O(100^3)$最悪の場合の合計 |$O(100)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1 から 100 までの可能な開始サイズごとにプロセスを 1 回シミュレートし、最終的な生存者数を保存します。 

1. 固定始動の場合$n$、プレーヤーを表すリストを作成します$1$を通して$n$。 アイデンティティは重要ではないため、このリストは存在のみを追跡し、アイデンティティは追跡しません。 
2. ラウンド内で削除が発生しなくなるまでラウンドを繰り返し実行します。 フラグを使用して、少なくとも 1 つの削除が行われたかどうかを検出します。 
3. 各ラウンドで、ソートされたインデックスのリストを反復処理します。$a_1, \ldots, a_k$。 それぞれについて$a_i$、現在のリストのサイズ内にあるかどうかを確認します。 存在する場合は、その位置を削除対象としてマークします。 
4. すべてスキャンしたら$a_i$、マークされたすべての位置を同時に削除します。 前の要素を削除するとインデックスがシフトするため、同時性が重要です。 最初にマーキングすると、同じラウンド内での誤ったカスケード シフトが回避されます。 
5. ラウンド全体でポジションが削除されなかった場合は、プロセスを終了します。 残りのリストのサイズがこの問題の答えです$n$。 
6. 各クエリが一定時間内に応答されるように、この結果を配列に格納します。 

これが機能する主な理由は、固定$n$、プロセスは決定的であり、クエリから独立しています。 それぞれの最終状態を計算したら、$n$、クエリは相互作用しないため、再利用は安全です。 

### なぜ効果があるのか

 重要な不変条件は、各ラウンドが残りのプレイヤーの明確に定義された現在の順列に基づいて動作し、重要な唯一の状態は現在のプレイヤーの数とその相対的な順序であるということです。 削除ルールは ID ではなくランク位置のみに依存するため、プレイヤーを匿名のインデックスとして扱った場合でも、シミュレーションは正確さを維持します。 有効なインデックスが存在しない限り、各トランジションは厳密にプレイヤーの数を減らします。$a$、その時点でシステムは固定点に到達します。 これにより、保存された結果の終了と正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def simulate(n, a):
    players = list(range(n))
    
    while True:
        removed = [False] * len(players)
        any_removed = False

        for idx in a:
            if idx <= len(players):
                removed[idx - 1] = True

        if not any(removed):
            return len(players)

        new_players = []
        for i in range(len(players)):
            if not removed[i]:
                new_players.append(players[i])

        players = new_players

def main():
    t = int(input())
    
    # Precompute answers for all n up to 100
    # We'll recompute per test case since a changes
    for _ in range(t):
        k, q = map(int, input().split())
        a = list(map(int, input().split()))
        ns = list(map(int, input().split()))

        # cache for this test case
        ans = [0] * 101

        for n in range(1, 101):
            ans[n] = simulate(n, a)

        print(" ".join(str(ans[n]) for n in ns))

if __name__ == "__main__":
    main()
```この実装は、説明されているシミュレーションを反映しています。 内部関数は、ブール除去マスクを使用して各ラウンド後にプレーヤー リストを再構築します。これにより、反復中にリストから削除するときに発生する微妙なインデックス シフトのバグが回避されます。 

シーケンスが次のとおりであるため、テスト ケースごとに結果を事前計算します。$a$テストケース間の変更。 以来$n$が 100 で制限されている場合でも、100 回のシミュレーションを再計算することは依然として簡単です。 

最もデリケートな点はインデックス作成です。$a_i$は 1 から始まりますが、Python リストは 0 から始まります。 除去マスクは直接マッピングされます$a_i - 1$正しいスロットに差し込みます。 

## 実用的な例

 小さな実例をたどります$a = [2, 4]$、$n = 5$。 

### トレース

 | ラウンド | 選手 | 削除のマークが付いています | 取り外し後 | 終了しました |
 | --- | --- | --- | --- | --- |
 | 1 | [1,2,3,4,5] | 2、4 | [1,3,5] | いいえ |
 | 2 | [1,3,5] | 2 無効、4 無効 | [1,3,5] | はい |

 2 番目のラウンドでは何も削除されないため、プロセスは停止します。 

これは、終了が、インデックスが存在するかどうかに依存することを示しています。$a$かどうかではなく、まだ有効です$a$それ自体は空ではありません。 

### 2 番目の例

 しましょう$a = [1, 2, 3]$、$n = 3$。 

| ラウンド | 選手 | マーク付き | 取り外し後 | 終了しました |
 | --- | --- | --- | --- | --- |
 | 1 | [1,2,3] | 1、2、3 | [] | いいえ |
 | 2 | [] | なし | [] | はい |

 これは、次のような場合に急速な崩壊を示します。$a$現在のリストを完全にカバーしています。

 ## 特殊なケース

 いつ$n$の最小値より小さいです$a$の場合、シミュレーションは削除を行わずに完全なパスをすぐに実行します。 たとえば、$a = [3, 5]$そして$n = 2$、最初のラウンドには有効な削除がないため、答えは完全な 2 になります。削除マスクは空のままであり、ループは即座に終了するため、アルゴリズムがこれを処理します。 

いつ$n$のいずれかに等しい$a_i$、範囲内のインデックスのみが削除されます。 例えば、$a = [1, 4]$、$n = 3$、最初のラウンドでは位置 1 のみが削除されます。 マスクベースの削除により、無効なアクセスが発生せず、残りの要素が正しく保存されます。 

1 ラウンドですべてのポジションが削除されると、次の反復では空のリストが表示され、すぐに停止します。 ループ条件では続行する前に削除がないかチェックされるため、これは自然に処理されます。
