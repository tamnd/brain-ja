 ## 解決策
 ## 問題の理解

 駅 A には、固定された順序の鉄道車両が与えられています。各車両には 1 から n までの一意のラベルが付けられていますが、それらの順序は任意です。 車両を移動する唯一の方法は、A から中間ステーション B へ、B から最終ステーション C へ、そして A から C へ直接という 3 つの指示された操作を介することです。 

目標は、ステーション C のすべての車両をラベルの厳密な昇順で終了することです。つまり、最初に車両 1、次に車両 2、というように n まで続きます。 これを達成する許可された一連の動きを出力する必要があり、すべての有効なシーケンスの中で、最小の操作数で 1 つを生成するように求められます。 それが不可能な場合は、-1 を出力する必要があります。 

主な制限は、A、B、C の両方がブロックに関してスタックのように動作することです。 特に、B には線路が 1 つしかないため、B に到着する車両は LIFO 動作によって制約されます。後から到着する車両は、将来の移動のブロックを解除するために早めに出発する必要がある場合があります。 

入力サイズは n = 100000 までになります。任意の再配置をシミュレートしたり、動きの順列を探索したりするソリューションは、直ちに実行不可能になります。 重度の定数因子が含まれる場合、O(n log n) でさえ境界線であり、O(n^2) は完全に問題外であるため、解は n において線形または線形に近いものでなければなりません。 

構造が B に特定の中間順序を強制し、後で修正することができない場合、微妙な失敗のケースが発生します。 

たとえば、次のことを考えてみましょう。```
3
2 1 3
```単純に 2 を B に送信し、次に 1 を B に送信し、その後 3 を C に直接送信しようとすると、システムはスタックします。これは、1 が B の 2 をブロックしますが、制約の下で 3 が正しく処理される前に 2 が後で必要になるためです。 これは、将来の要件を考慮せずに任意に B にプッシュすると、プロセスがデッドロックになる可能性があることを示しています。 

もう一つの問題のあるケース:```
2
2 1
```1が2より先に終わらないといけないのでこれは無理ですが、2が先に出てきて手次第でBかCにはまってしまいます。 B 経由ですべてを送信する貪欲な試みは失敗します。 

これらの例は、実現可能性は、B のスタックの性質によって課せられる避けられない順序制約の逆転を回避できるかどうかに依存することを示唆しています。 

## アプローチ

 強引な解釈では、これを巨大な状態空間における最短経路問題として扱うことになります。 各状態は、A、B、C の車の順序で構成されます。各移動は状態間を遷移し、ソートされた C を生成するシーケンスを検索します。状態の表現も n で線形であり、分岐係数は最大 3 であるため、BFS は完全に実行不可能です。 

より構造化されたブルート フォース アプローチは、貪欲な戦略をシミュレートする可能性があります。可能であれば、次に必要な車両 k を常に A または B から C に移動し、それ以外の場合はブロックしている車両を B に移動します。B には隠れた順序制約が導入されているため、これは依然として失敗します。 車が B に押し込まれると、その相対的な順序によって、今後の運転が可能かどうかが決まります。 グローバル条件がないと、この貪欲なアプローチにより、車が間違った順序で B に閉じ込められる可能性があります。 

重要な点は、C の最終順序が 1 から n までに固定されていることです。 これにより、ラベルの昇順で車を処理する必要があります。 それぞれの値 i について、アクセス可能になった瞬間に最終的にそれを C に持ってくる必要があります。 これは、B がスタック バッファーのように動作することを考慮しながら、問題をソートされた順序で値を取得するシミュレーションに変換します。 

重要な構造的洞察は、追跡しなければならない唯一の意味のある状態は、次に必要な車両が A で利用可能であるか、または一時的に B に移動する必要がある大きな車両の下に現在隠されているかどうかであるということです。これにより、プロセスがスタックを維持し、B が将来の要件に合わせて後入れ先出し方式で要素を一時的にのみ格納できるという制約に違反しないことが保証されます。

 ## アルゴリズムのチュートリアル

 ポインタを維持します`need`また、ステーション A を入力シーケンス上のポインターとしてシミュレートし、ステーション B を明示的なスタックとしてシミュレートします。 

1. から始める`need = 1`、 索引`i = 0`初期配列と空のスタック B にあります。また、操作の出力リストも維持します。 
2. その間`need <= n`、私たちは車を確保しようとしています`need`Cに達する。 
3. B の上部が等しい場合`need`、B からポップして C に移動します。操作「B C」を記録し、インクリメントします。`need`。 B はすでに正しい次の車を所有しているため、これが最も直接的な解決策です。 
4. それ以外の場合、A にまだ車が残っている場合は、次の車に乗ります`x = a[i]`そしてそれを加工します。 もし`x == need`、すぐに A から C に移動し、両方をインクリメントします。`i`そして`need`。 もし`x != need`、それを A から B に移動し、スタックにプッシュして、インクリメントします。`i`。 これにより、順序の制約を尊重しながらも進行を妨げることがなくなります。 
5. A が使い果たされ、B の上部がなくなった場合`need`、プロセスが停止しており、有効なシーケンスが存在しません。 -1を出力します。 
6. すべての車が順番に C に配置されるまで続けます。 

中心的なアイデアは、B がまだ必要のない自動車の一時的な保管構造として機能するということです。 車がすぐに C に行ける場合は、車を B に押し込むことはありません。そうすることは進行を遅らせるだけであり、不必要なブロックを作成する可能性があるためです。 

### なぜ効果があるのか

 このアルゴリズムでは、自動車が厳密に昇順で C に入力されるように強制されます。 いつでもBの車はすべて以前に登場した車です`need`に達しましたが、等しくありませんでした`need`。 A は順番に処理され、B はスタックであるため、B 内の車は先頭になったときにのみ解放できます。これは、より小さい保留中の要素が、先に使用する必要があるより大きい保留中の要素の下にトラップされないという要件と正確に一致します。 このようなトラップが発生すると、暴露不能として現れます。`need`A または B から、不可能であることを正しく通知します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    a = list(map(int, input().split()))

    need = 1
    i = 0
    st = []
    ops = []

    while need <= n:
        if st and st[-1] == need:
            st.pop()
            ops.append("B C")
            need += 1
            continue

        if i < n:
            x = a[i]
            i += 1

            if x == need:
                ops.append("A C")
                need += 1
            else:
                st.append(x)
                ops.append("A B")
        else:
            print(-1)
            return

    print(len(ops))
    print("\n".join(ops))

if __name__ == "__main__":
    solve()
```実装はシミュレーションの後に直接実行されます。 ポインタ`i`これにより、ステーション A を固定の順序で 1 回だけ消費することが保証されます。 スタック`st`はステーション B を表しており、LIFO 制約に一致するその上部とのみ対話します。 

微妙な詳細は、移動の優先順位です。A からさらに消費する前に、常に最初に必要な要素について B をチェックします。そうしないと、追加の要素が B にプッシュされ、すでに利用可能なソリューションがブロックされる可能性があるため、これが必要です。 

障害状態は、A が空で、B が必要な車両を供給できない場合にのみ発生します。 これは、システムが行き詰まっていると思われる唯一の点です。

### 例 2

 入力:```
5
1 2 3 5 4
```1、2、3 を C に直接配置すると、4 の前に 5 に到達します。 

その時点で:

 - B は空です
 - A にはまだ [5, 4] が含まれています
 - 必要 = 4

 4 の前に 5 を処理する必要がありますが、5 の方が大きいため、正しい順序付けが妨げられます。 5 が B にプッシュされると、後で 4 の上に位置するため、順序制約に違反せずに 4 を公開することが不可能になります。 

アルゴリズムは最終的に、A が空で B top が 4 ではない状態に到達し、失敗をトリガーして -1 を出力します。 

これは重要な制約を裏付けています。つまり、より大きな要素を、まだ先に処理する必要がある小さな要素の上に永続的に配置することはできません。
