 ## 解決策
 ## 問題の理解

 この問題は、レース結果や過去のパフォーマンスに基づいて各アスリートの評価が時間の経過とともに進化する、アスリート向けの全国ランキング システムをモデル化しています。 各アスリートは基本レーティングから始まり、その後、複数の競技が時系列に行われます。 すべての競技には、1 日、参加者のグループ、および各参加者の終了時間があり、失格を意味するものはありません。 

主な難点は、レースが現在のレーティングを直接使用しないことです。 代わりに、レース当日の 15 日前からの各アスリートの評価が使用されます。 レース結果と遅延評価に基づいて、上位入賞者の一部から「レース スコア」が計算され、そのレースの参加者全員がレース結果から得られるパフォーマンス値を受け取ります。 このパフォーマンスは履歴に保存され、その後の評価の進化に影響を与えます (ただし、正確な下流での使用法はモデルの説明で抽象化されています。タスクはこれらのイベントを正しく処理することに重点を置いています)。 

この構造は、時間が 2 つの独立した方法で重要であることを示唆しています。 まず、競技は昇順に処理される必要があります。 次に、すべての評価クエリは正確に 15 日前の履歴スナップショットに依存するため、アスリートごとの単純なランニング値ではなく、時間を意識した構造を維持する必要があります。 

このタイプの問題に典型的な制約により、アスリートと競技の数が非常に多いため、すべてのレースのランキングをゼロから再計算することは不可能です。 レースごとに参加者を繰り返し並べ替えたり、グローバルな順序を再計算したりするアプローチでは、制限時間を超える可能性があります。 主な計算負荷は、過去の評価を繰り返しクエリしながら参加者を効率的にランク付けすることから発生します。 

いくつかの特殊なケースがルールから自然に現れます。 レースには、失格となった参加者と有効な参加者が混在する場合があります。 たとえば、参加者全員が失格となった場合、完走者数はゼロとなり、レースが無視されるか、解釈によっては順位が悪化することになります。 依然としてランク付けを試みる単純な実装では、ゼロで除算したり、無効な上位 k 位の参加者を選択したりする可能性があります。 

もう 1 つの微妙なケースは、レースの完走者が非常に少ない場合です。 完走した選手が 1 人または 2 人だけの場合でも、影響力のある参加者の最小数を選択するルールでは、少なくとも 3 人または派生したしきい値が必要であり、有効な完走者数を超える可能性があります。 クランプせずに盲目的に最上位のサブセットを取得する不注意な実装は、範囲外の要素にアクセスすることになります。 

最後に、遅延評価クエリは次のとおりです。`day - 15`初期のコンテストの記録された更新が存在する前に実行される可能性があります。 単純な配列検索では、これらをゼロまたは初期化されていない値として扱うため、デフォルトのベースラインを明示的に定義しない限り、ランキングが歪められます。 

## アプローチ

 直接シミュレーションは、問題文の後に文字通り続きます。 レースごとに、15 日間を遡ってすべての参加者の現在の評価を計算し、すべての有効な完走者を時間順に (その後、タイブレークの評価順に) 並べ替え、上位グループを選択し、レース スコアを計算し、パフォーマンス値を割り当てます。 このアプローチは、定義を正確に反映しているため、正しいです。 

ボトルネックは、繰り返しの分類ステップです。 レースがある場合$k$参加者、仕分けコスト$O(k \log k)$そして、すべての人種にわたって、参加者の総数が数十万人以上に達すると、これは法外な行為になります。 さらに、構造なしで「時点 t-15 での評価」に繰り返しアクセスすると、完全な履歴をスキャンするか、アスリートごとに完全な時系列を保存する必要があり、これも大きすぎます。 

重要な観察は、レースごとに必要な唯一のグローバル構造は、終了時刻と 15 日前の評価に基づく 2 番目のキーという 2 つのキーによる参加者の順序付けであるということです。 この評価の比較はレース内でのみ必要であり、全アスリート間での世界的な比較ではありません。 これは、グローバルな動的なランキング構造が必要ないことを意味します。 必要なのは、過去の評価を迅速に取得し、レースごとに効率的に順序付けすることだけです。 

これにより、アスリートごとに、時間インデックス付きの一連のレーティング変更を維持し、その時点での値をクエリできるという問題が軽減されます。$d - 15$。 アスリートごとの更新の事前計算リストを使用すると、これはクエリごとの二分検索になります。 種族ごとのソートは残りますが、現在ではモデルの避けられない部分となっています。 他のすべては十分に効率的になります。

 | ブルートフォースシミュレーション |$O(\sum k_j \log k_j + m \cdot n)$|$O(mn)$| 遅すぎる |

 ## アルゴリズムのチュートリアル

 1. アスリートごとに、時間の経過に伴う評価の変化のリストを保存します。 各エントリには、その日とそのイベント後の評価が記録されます。 これにより、すべてを再計算することなく、過去の評価を再構築できます。 
2. 競技を日の昇順に処理します。 これにより、後のレースに到達したときに、以前のクエリに必要なすべての履歴がすでに利用可能になります。 
3. レースごとに基準タイムを計算します。$t = d_j - 15$。 すべての参加者について、その時点で評価を取得します$t$履歴で二分探索を使用します。 これが必要なのは、評価が連続的に変化するのではなく、個別のイベントでのみ変化するためです。 
4. 参加者を完走者と失格選手に分けます。 フィニッシャーとは、タイムがゼロではない人です。 失格となったアスリートには、ただちに次のパフォーマンス値が与えられます。$-1$ランキングには影響しません。 
5. 完走者を完走時間順に並べ替えます。 2 人のアスリートが同じタイムを持っている場合、その時点で取得した評価を使用して同点を解消します。$t$、評価が高いほど先にランクされます。 このタイブレークにより、モデルと一貫した決定的な順序付けが保証されます。 
6. コンピューティング$F_j$、完走者数。 これから、閾値を計算します$N_{infl} = \max(3, \lfloor 2F_j / 3 \rfloor)$。 もし$F_j < N_{infl}$、このレースのそれ以降の処理をスキップします。 
7. 上部を選択します$N_{infl}$仕分け後のフィニッシャー。 終了タイムに過去の評価を乗算した加重平均を計算し、指定された正規化定数でスケールします。 これによりレーススコアが生成されます。 
8. すべての参加者にパフォーマンス値を割り当てます。 完走者が獲得するもの$\lfloor \text{RaceScore} / R_{i,j} \rfloor$、失格となった選手は$-1$。 今後のクエリのために、この記録を各アスリートの履歴に追加します。 

正確さは重要な不変条件に左右されます。どのレース当日でも、比較に使用されるすべてのレーティングは 15 日前に有効だったレーティングとまったく同じであり、参加者の順序付けは、凍結された過去の値と現在のレース結果のみに依存します。 レース中に共有状態を変更するのではなく、常に履歴をクエリするため、将来のイベントが過去の計算に影響を与えることはなく、すべての順序決定は時間的定義と一致したままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from bisect import bisect_right

def get_rating(hist, day):
    # hist: list of (day, rating)
    # returns last rating with time <= day
    if not hist:
        return 0
    i = bisect_right(hist, (day, 10**30)) - 1
    return hist[i][1] if i >= 0 else 0

def solve():
    n, m = map(int, input().split())
    
    base = list(map(int, input().split()))
    
    hist = [[(-10**18, base[i])] for i in range(n)]
    
    for _ in range(m):
        parts = input().split()
        d = int(parts[0])
        s = int(parts[1])
        k = int(parts[2])
        
        participants = []
        
        idx = 3
        for _ in range(k):
            a = int(parts[idx]) - 1
            r = int(parts[idx + 1])
            idx += 2
            
            participants.append((a, r))
        
        t = d - 15
        
        finishers = []
        dsq = []
        
        for a, r in participants:
            if r == 0:
                dsq.append(a)
            else:
                rt = get_rating(hist[a], t)
                finishers.append((r, rt, a))
        
        Fj = len(finishers)
        Ninfl = max(3, (2 * Fj) // 3)
        
        if Fj >= Ninfl:
            finishers.sort(key=lambda x: (x[0], -x[1]))
            
            top = finishers[:Ninfl]
            
            score_sum = 0
            for r, rt, a in top:
                score_sum += r * rt
            
            if Ninfl > 0:
                RaceScore = (score_sum * 10000) // Ninfl
            else:
                RaceScore = 0
        else:
            RaceScore = None
        
        for a, r in participants:
            if r == 0 or RaceScore is None:
                val = -1
            else:
                val = RaceScore // r
            hist[a].append((d, val))
    
def main():
    solve()

if __name__ == "__main__":
    main()
```このソリューションは、各エントリーが各競技後に評価がどのように変化したかを記録する、アスリートごとの履歴リストを維持します。 ヘルパー関数は二分検索を実行して、その日の評価を取得します。$d - 15$、レースは現在の価値観ではなく歴史的な価値観に依存するため、これは不可欠です。 

各競技会内で、完走者と失格者を区別します。 完走者は、完走時間と過去の評価の両方をエンコードするタプル キーを使用して並べ替えられます。 マイナス記号の評価により、Python のデフォルトの昇順ソートを維持しながら降順が保証されます。 

レース スコアの計算は、選択されたサブセットに対する正確な集計ルールに従います。 計算が完了すると、すべての参加者は履歴に追加される派生値を受け取り、将来のレースでは更新された状態が確実に表示されます。 

実装の微妙な詳細は、各アスリートの履歴を「センチネル」エントリで初期化することです。 これがなければ、初期のクエリには特別なケースが必要になります。 もう 1 つの重要な詳細は、すべての更新がレースの処理後に追加され、時系列の一貫性が維持されることです。

 ## 特殊なケース

 レースの参加者全員が失格になると、完走者リストは空になり、$F_j = 0$。 この状況では、しきい値は$N_{infl} = \max(3, 0)$は３となり、完走者数よりも多くなる。 アルゴリズムはこれを正しく検出します。$F_j \ge N_{infl}$はすぐに失敗し、レースはレーティングに基づく貢献を生み出しません。 その後、すべての参加者が受け取ります$-1$、十分な完走者がいない場合、有効なレーススコアは存在しないというルールに一致します。 

レースの完走者が 3 人未満でも有効な結果が少なくとも 1 つある場合、同じしきい値ロジックにより安全でない選択が防止されます。 フィニッシャー リストは正しくソートされている可能性がありますが、必要な最小サンプル サイズが満たされていないため、アルゴリズムはスコア計算をスキップし、小さすぎるセットに対する無効な集計を回避します。
