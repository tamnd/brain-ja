 ## 解決策
 ## 問題の理解

 Ivan は、各アイテムが複数のタイプのいずれかに属するアイテムのコレクションを取得する必要があります。 種類ごとに、必要な数量を正確に購入する必要があります。 価格は、アイテムがそのタイプのプロモーションの日に購入されるかどうかによって異なります。通常の日では、各アイテムの価格は 2 単位ですが、プロモーションの日では 1 単位の費用がかかります。 

彼は 1 日あたりちょうど 1 単位のお金を稼ぎます。 十分なお金が貯まっていれば、いつでも好きなだけアイテムを買うことができます。 プロモーションはタイプ固有および日固有であり、特定の日に特定のタイプが割引になることを示すペアのリストとして提供されます。 

目標は、Ivan が必要な購入をすべて完了できる最も早い日を決定することです。これは、Ivan が十分な蓄えを持ち、すべての有益な割引を最適に使用したことを意味します。 

主な難点は、Ivan が各アイテムをいつ購入するかを選択できること、そして割引は種類ごとに時間の経過とともに異なるため、時間をかけて購入のスケジュールを立てることが重要であるということです。 

制約は非常に小さいため、最大約 1000 日、1000 種類、合計 1000 個のアイテムが関係します。 これは、慎重に最適化しない限り、チェックあたりの日数が 2 次になることを排除し、特に前処理されている場合には、ほぼ線形の処理による 1 日あたりの実行可能性チェックが許容されることを強く示唆しています。 

貪欲な直感がタイムラインに誤って適用されると、微妙な失敗例が発生します。 たとえば、将来の割引を考慮せずに手頃な価格ですぐに購入すると、失敗する可能性があります。 もう 1 つの落とし穴は、Ivan が十分な合計金額を持ったら、後からいつでも割引購入品を埋め戻せると想定していることです。これは、割引が日数に関連付けられており、遡及できないことを無視しています。 

小さな失敗シナリオの例としては、あるタイプが数日後にのみ割引されるが、貪欲に早期に購入すると高価な購入で資金が枯渇し、待っていてもメリットがなくなる場合があります。 

入力:```
1 1
2
2 1
```Ivan が 1 日目にすぐに購入した場合、両方のアイテムに対して 2 を支払います。 ただし、最適な戦略は、両方のアイテムのコストが 1 になる 2 日目まで待つことです。これにより、必要な合計金額が 4 から 2 に減り、実現可能性のタイミングが変わります。 

これは核となる構造を示しています。答えは、特定の日までにコスト 1 で各タイプのアイテムが何個購入できるかによって決まります。 

## アプローチ

 強引なアプローチは、毎日シミュレーションすることです。 毎日、収入を蓄積し、その日までにすべての買い物を完了できるかどうかを確認します。 実現可能性をテストするために、各アイテムを 1 日に割り当てて、割引を使用するか全額を支払うかを決定してみます。 

単純な実現可能性チェックでは、最初にすべての割引商談を貪欲に割り当ててから、残りの項目を正規価格で満たそうとする可能性があります。 ただし、これを構造化せずに毎日個別に行うと、すべてのオファーを繰り返しスキャンすることになり、1 日あたり O(m + n) 単位で割り当てを再評価することになり、O(nm) 以上の結果が生じる可能性があります。 

重要な観察は、固定日 D の場合、唯一の関連情報は、種類ごとに、D 以降に少なくとも 1 つの割引がある商品がいくつあるかということです。そのような各商品はコスト 1 で購入できます。 残りのコストは 2 です。したがって、実現可能性はタイプごとの決定論的な計算に減ります。 

タイプごとに、割引日のソートされたリストを事前に計算できます。 次に、候補日 D について、二分検索を使用して、そのタイプで利用可能な割引ユニットの数をすぐに計算できます。 これにより、実現可能性チェックは合計前処理 O(m log m + n log m) とチェックごとの O(n log m) に変わります。 

D は実現可能性において単調であるため、1 から 1000 までの日数にわたって答えを二分探索できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(D · (n + m)) | O(m) | 遅すぎる |
 | 二分探索 + 前処理 | O((n + m) log m + n log D) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 指定された日 D ですべての購入を完了できるかどうかをテストしたいと考えています。 

1. すべての割引日をタイプごとにグループ化します。 タイプごとに、割引される日のソートされたリストを保存します。 ソートは、D までに発生する割引の数を効率的にクエリできるようにするために必要です。 
2. 固定日 D の実行可能性チェック関数を定義します。この関数は、Ivan が D 日まで購入できる場合にすべての購入を完了できるかどうかを決定します。 
3. 各タイプ i について、≤ D である割引日数を計算します。この値は、コスト 1 でこのタイプのアイテムを何個購入できるかを表します。 
4. これを必要数量 k_i と比較します。 k_i 個のアイテムが必要で、x 個の割引機会がある場合、x 個のアイテムは安く購入でき、残りの max(0, k_i - x) はコスト 2 で購入する必要があります。 
5. すべてのタイプの合計コストを合計します。 これにより、D 日までにすべての購入を完了するために必要な最低金額が得られます。 
6. この必要コストと、Ivan が D 日までに貯めたお金、つまり D を比較します (1 日あたり 1 を稼ぐため)。 総費用 ≤ D の場合、D 日が可能です。 
7. 実現可能性が成立するように、範囲 [1, 1000] 内の最小の D を二分探索します。 

### なぜ効果があるのか

 任意の固定日 D について、各割引は存在するか存在しません。 価格はタイプごとに独立しているため、タイプ間の相互作用はありません。 タイプ内の最適な戦略は、利用可能なすべての割引スロットを常に最初に使用することです。これは、可用性を超えて制限なく厳密にコストを削減するためです。 これにより、タイプごとのコスト計算が確定的になります。 D を増加させると割引の機会が増えて利用可能なお金が増えるだけなので、D が増加しても実現可能性が低下することはないため、単調性が続きます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, m = map(int, input().split())
k = list(map(int, input().split()))

discounts = [[] for _ in range(n)]
for _ in range(m):
    d, t = map(int, input().split())
    discounts[t - 1].append(d)

for i in range(n):
    discounts[i].sort()

def can(day):
    total_cost = 0

    for i in range(n):
        need = k[i]
        if need == 0:
            continue

        dlist = discounts[i]

        # count how many discounts are available up to 'day'
        l, r = 0, len(dlist)
        while l < r:
            mid = (l + r) // 2
            if dlist[mid] <= day:
                l = mid + 1
            else:
                r = mid
        cheap = l

        cheap = min(cheap, need)
        total_cost += cheap + 2 * (need - cheap)

    return total_cost <= day

lo, hi = 1, 1000
ans = 1000

while lo <= hi:
    mid = (lo + hi) // 2
    if can(mid):
        ans = mid
        hi = mid - 1
    else:
        lo = mid + 1

print(ans)
```このソリューションでは、まず、種類ごとの割引日のリストを作成します。 この構造は、時間に依存するすべての情報を効率的にクエリできる方法で分離するため、不可欠です。 次に、実現可能性関数は、スケジューリングの問題を純粋な算術コスト計算に変換します。 

二分探索は、Ivan が D 日までに終了できれば、金額も割引も増えるだけなので、それ以降の日までに終了できるという事実に基づいています。 

内部`can`の場合、各割引リストに対する二分探索が唯一の重要なステップです。 候補日までに利用可能なプロモーションの数をカウントします。 この数は、安く購入できる商品の数を直接決定します。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、タイプに必要なアイテムよりも多くの割引日数がある場合です。 アルゴリズムは、使用可能な割引の上限を正しく設定します。`min(cheap, need)`、数えすぎを防ぎます。 

もう 1 つのケースは、割引が存在するものの、最適な完了日よりも後に割引が適用される場合です。 例えば：```
1 1
2
5 1
```割引があっても初期には意味がありません。 実現可能性チェックにより、日 ≤ D の割引のみが考慮されることが保証されます。 

最後の微妙なケースは、Ivan に十分なお金があるが、割引が不十分で、コストが依然として高い場合です。 実現可能性は予算だけではなく、蓄積された資金と達成可能な削減コストの両方に依存するため、アルゴリズムがこれを処理します。
