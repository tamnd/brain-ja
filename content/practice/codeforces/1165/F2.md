 ## 解決策
 ## 問題の理解

 Ivan は、アイテムの固定マルチセットをタイプに分けて購入する必要があります。各タイプには特定の数のコピーが必要です。 彼は毎日正確に 1 単位の通貨を獲得し、その日の夕方にアイテムを購入するためにすぐに使用したり、後で使用するために保存したりすることができます。 

通常、各アイテムの価格は 2 ユニットですが、そのアイテムの種類が特定の日にセールになっている場合は、コストは 1 ユニットのみです。 難点は、売上がグローバルではなく、特定の日の特定の種類にのみ適用され、同じ種類の複数の売上が異なる日に発生する可能性があることです。 

問題は、個別に総コストを最小化することではなく、お金が時間の経過とともに直線的に蓄積されることを考慮して、イワンがすべての購入を完了できる日を最小化することです。 D 日までに、彼は合計で正確に D ユニットのお金を持っています。彼は、可能な限り割引を利用しながら、どの時点でも蓄積した金額を超えて支出しないように、複数の日にまたがって購入をスケジュールしたいと考えています。 

入力には、タイプごとの必要数量と販売イベントのリストが記述されます。 出力は、必要なすべてのアイテムを最適なタイミングと割引の使用で購入できる最も早い日です。 

最大の難点は、割引を待つために購入が遅れる可能性があることですが、延期すると後で利用できる金額にも影響します。 決定は基本的に、固定期限 D までに、いつでも利用可能な資金を超過することなく、割引購入の合計をスケジュールできるかどうかに関するものです。 

この制約により、日々のトランザクションのシミュレーションを回避するソリューションが必要になります。 最大 200,000 のタイプと 200,000 のオファーがあるため、何日もかけて繰り返し、実現可能性を最初から再計算するアプローチは遅すぎます。 長期間にわたる単純なシミュレーションや、1 日あたりの再計算を貪欲に行うと、二次関数またはさらに悪い動作が発生します。 

同じタイプで多くの販売が重なった場合、微妙なエッジケースが発生します。 たとえば、タイプに多数のセール日がある場合、単純なアプローチでは各アイテムを最も早いセールに貪欲に割り当てようとする可能性がありますが、特定のセール発生を使用できるのは 1 つのアイテムだけであるため、これは実現可能性を損なう可能性があります。 もう 1 つのエッジ ケースは、売上は存在するものの、問題にするには遅すぎる場合です。つまり、待機すると利用可能な有効なキャッシュ フロー構造が減少し、それを補うことができないため、最適な戦略は売上を完全に無視します。 

## アプローチ

 強引なアイデアは、時間をシミュレートすることです。 候補日 D については、Ivan が合計 D 個のバールを持っていると仮定し、購入を 1 から D までの日に割り当てようとします。各アイテムは、セール日にはコスト 1 で購入でき、それ以外の場合はコスト 2 で購入できます。 単純なシミュレーションでは、最初に割引スロットを貪欲に割り当て、次に残りの需要を通常の購入で満たし、合計支出が利用可能な金額を超えるかどうかを確認します。 

これは実際の制約を反映しているため、原理的には正しいです。 ただし、代償として、候補日ごとにすべての売上とすべてのアイテムを処理する必要があり、実行可能な最小の日を検索する必要があるため、これを何度も繰り返す必要があります。 数日間にわたる二分探索では、これは O((n + m) log D) になりますが、これは実現可能性のチェックが効率的である場合に限ります。 

重要な観察は、固定日 D の実現可能性は、接頭辞 [1, D] 内で各タイプのアイテムをいくつ割引で購入できるかを数えることに帰着できるということです。 各セール イベントでは、特定のタイプに対して最大 1 つの割引購入の機会が与えられます。 したがって、各タイプについて、k_i を超えた追加販売によってコストがさらに削減されることはないため、[1, D] 内の最も早い k_i 販売日のみが問題となります。

これにより、問題は、固定 D の場合、種類ごとに原価 1 で購入できる品目数を計算し、残りの原価 2 の品目が予算 D に収まるかどうかを確認するという計算に変換されます。貪欲な構造が自然に現れます。各販売機会は潜在的な節約単位ですが、使用できるのは品目ごとに 1 回だけです。 

2 番目の重要な洞察は、D 日までに終了できれば、より多くのお金とより多くの売上を得ることができるため、D' > D までに終了することもできるため、二分探索が機能するということです。 この単調性により、問題を実現可能性のチェックに単純化することができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | ブルートフォースシミュレーション | O(D (n + m)) | O(n + m) | 遅すぎる |
 | 二分探索 + 貪欲な実現可能性 | O((n + m) log N) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 答えを値Dとして、その日までにすべての購入を完了できるかどうかを確認します。 

1. すべてのセール イベントを日ごとに並べ替え、タイプごとにグループ化します。 これにより、各マイクロトランザクション タイプのすべてのセール日にすぐにアクセスできるようになります。 グループ化しないと、一定の日の制限に対して使用可能な割引を効率的にカウントできません。 

2. 候補日 D については、日 ≤ D の売上のみを考慮します。タイプごとに、その売上のうちどれだけがこのプレフィックスに該当するかを抽出します。 これらは、そのタイプで利用可能な割引購入の最大数を表します。 

3. タイプ i ごとに、割引価格で購入できる商品の数 (min(k_i, available_sales_i)) を計算します。 これは、各販売で削減できるのは必要な品目のコストが 1 つだけであり、k_i を超える追加販売は役に立たないためです。 

4. タイプ i の残りのアイテム (k_i から割引アイテムを差し引いたものに等しい) は、正規価格 2 で購入する必要があります。 

5. すべてのタイプにわたる合計コストを、discount_items * 1 と left_items * 2 に加えて計算します。 

6. この合計コストが ≤ D であるかどうかを確認します。そうである場合、D 日目は実行可能です。 

7. 範囲 [1, max_day_possible] で D に対して二分探索を使用します。 割引なしでは各項目のコストが 2 であるため、必要な最大境界は 2 * sum(k_i) です。 

### なぜ効果があるのか

 固定日 D の場合、あらゆる最適な戦略を、各タイプごとに可能な場合は常に割引購入を使用する戦略に変換できます。これは、割引によって入手可能性を超えた実現可能性の制約に影響を与えることなく厳密にコストが改善されるためです。 各セールは独立しており、正確に 1 つのアイテムに適用されるため、私たちができる最善のことは、できるだけ多くのセールを必要なアイテムと一致させることです。 マッチング後、残りのアイテムはすべて全額支払わなければなりません。 これにより、その D に対する支出が最小限に抑えられるため、実現可能性のチェックが正確になります。 

単調性は、D を増加しても金額と潜在的な割引が増えるだけで、オプションが削除されることはないため、実現可能性は上向きに保たれるという事実から来ています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(D, n, k, sales_by_type, max_day):
    # count available sales up to day D per type
    total_cost = 0

    for i in range(n):
        ki = k[i]
        if ki == 0:
            continue

        # count sales in prefix
        cnt = 0
        for d in sales_by_type[i]:
            if d > D:
                break
            cnt += 1

        discount = cnt if cnt < ki else ki
        remaining = ki - discount

        total_cost += discount + remaining * 2
        if total_cost > D:
            return False

    return total_cost <= D

def solve():
    n, m = map(int, input().split())
    k = list(map(int, input().split()))

    sales_by_type = [[] for _ in range(n)]
    max_day = 0

    for _ in range(m):
        d, t = map(int, input().split())
        t -= 1
        sales_by_type[t].append(d)
        if d > max_day:
            max_day = d

    for i in range(n):
        sales_by_type[i].sort()

    lo, hi = 1, 2 * sum(k)

    while lo < hi:
        mid = (lo + hi) // 2
        if can(mid, n, k, sales_by_type, max_day):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```このソリューションは、各実現可能性チェックで関連するイベントのみをスキャンできるように、タイプごとに売上をグループ化することから始まります。 各リストはソートされているため、単純なプレフィックス スキャンを使用して、しきい値日までに売上が何件落ちたかをカウントできます。 実現可能性関数は、タイプごとに使用可能なすべての割引を貪欲に適用することにより、特定の日に可能な最良のコスト構造を計算します。 

二分検索はこの実現可能性チェックをラップし、最小の有効な日が見つかるまで範囲を縮小します。 上限は安全です。最悪の場合でも各アイテムのコストは 2 であるため、2 日目までに終了すれば常に十分です * sum(k_i)。 

実装の微妙な点は、1 日あたりのお金の流れをシミュレートしようとしていないことです。 「いつでも蓄積されたお金以上に支出できない」という条件は、総コストの制約に陥ります。なぜなら、お金の到着は直線的かつ均一であるため、総コストが尊重される限り、購入の順序は実現可能性に影響を与えることなく再配置できるからです。

 ## 特殊なケース

 あるタイプのすべての売上が必要な数量を超えた場合、そのうちの k_i だけが問題になります。 アルゴリズムは、min(k_i, cnt) で割引をクランプすることでこれを処理し、過剰カウントが発生しないようにします。 

売上がまったくない場合、実現可能性は総コスト 2 * sum(k_i) ≤ D かどうかを確認することになり、二分探索は自然にその値に収束します。 

売上が存在するものの、1 つのタイプに集中している場合、タイプごとにグループ化することで、他のタイプに誤って配分することがなくなり、コスト計算の正確性が維持されます。
