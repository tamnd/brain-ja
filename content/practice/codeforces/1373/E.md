 ## 解決策
 ## 問題の理解

 最小の非負の整数を構築しようとしています$x$から始まる短い連続した数字のブロックを取ると、$x$、 具体的には$x, x+1, \dots, x+k$、それらすべての桁の合計を合計すると、合計が指定されたターゲットに等しくなります。$n$。 

したがって、入力により複数の独立したシナリオが得られます。 各シナリオで開始番号を選択します$x$、次に長さの固定ウィンドウを見てください。$k+1$、その中のすべての数値の桁の合計を計算し、合計を次と比較します。$n$。 すべての有効な選択肢の中で、可能な限り最小のものを出力する必要があります。$x$。 

制約の大きさは小さい$n$、 以来$n \le 150$、 そして$k \le 9$。 これにより、合計桁数合計の予算がわずかであることがすぐにわかります。 数値が大きくなっても、桁の合計はゆっくりと増加するため、どのようなソリューションでも、非常に少量の桁の寄与について「推論」するだけで済みます。 これは、単純な線形方法で広大な範囲を検索しているわけではないことを示す強力なヒントです。 代わりに、数値が増加するときに桁の合計がどのように動作するかの構造を利用しています。 

素朴な試みは、増加させようとするでしょう$x$ゼロから上に向かって合計を計算します$f(x) + \dots + f(x+k)$毎回。 問題はそれです$x$有効な回答が大きくなる可能性があります (10 桁以上に達するサンプルに見られるように)。 たとえ各チェックが高速であっても、すべての候補に対して盲目的に繰り返すことは不可能です。$x$遠く離れている場合もあり、候補者のスペースは無制限です。 

キャリー伝播が 10 進表現で発生する場合、微妙なエッジ ケースが発生します。 たとえば、999 か​​ら 1000 に移動すると、桁の合計が大幅に変化します。 桁上げを正しくモデル化せずに桁の合計を「局所的に調整」しようとする単純なアプローチは、桁の合計が増分に対して線形ではないため、ここでは失敗します。 

もう 1 つの注意が必要なケースは次のような場合です。$k > 0$。 ウィンドウは連続する番号を結合するため、1 つの番号の桁の変更は、独立したものではなく、ブロック全体のキャリー チェーンを介して隣接する番号に影響を与えます。 

## アプローチ

 重要な観察は、この構造が桁上げによって駆動されていることです。 実際の数値という観点から考えるのではなく、数値を繰り返し増加させたときに数字がどのように変化するのかという観点から考えます。 

ブルートフォースアプローチは簡単です。 考えられるすべての開始値を反復処理します$x$、それぞれの桁の合計を計算します。$k+1$数値を入力し、合計が等しいかどうかを確認します$n$。 これは正しいですが、有効な解決策には非常に大規模な処理が必要になる可能性があるため、完全に非現実的です。$x$、桁の和の計算が何度も繰り返されます。 たとえ小切手ごとに費用がかかるとしても$O(k \log x)$、検索スペースは無制限です。 

最適化は問題を再構成することから生まれます。重要なのは、1 を繰り返し加算したときに桁の合計がどのように変化するかだけです。 各増分は後続の 9 にのみ影響し、予測可能なキャリー チェーンを引き起こします。 以来$k \le 9$、非常に小さなウィンドウでのローカル数字の動作を理解する必要があるだけです。 これにより、次のような構造を扱うことができます。$x$最下位から最上位まで 1 桁ずつ、ブロックがどのように処理されるかをシミュレートします。$x \dots x+k$進化する。 

検索する代わりに$x$、最下位桁から上に向かって貪欲に構築します。 各桁の位置で、次の桁間での桁上げの相互作用を考慮して、この位置以降でも必要な合計寄与に到達できるように、どの桁を配置するかを決定します。$k+1$数字。 なぜなら両方とも$n$そして$k$が小さい場合、数字の選択の効果を安全にシミュレートし、境界のあるローカル状態内でキャリーを伝播できます。 

これは問題を、長さによって状態が決定される数字 DP のような構造に変換します。$k+1$数値ウィンドウはキャリーの下で動作します。

 ## アルゴリズムのチュートリアル

 私たちが建設します$x$最下位桁から最上位桁まで、ブロックがどのように維持されるか$k+1$連続した数字が動作します。 

1. 私たちは数字を考えます$x, x+1, \dots, x+k$整列された数字の配列として、数値に 1 を加算すると、より高い位置に影響を与えるキャリー チェーンが作成されます。 これらのキャリー効果をローカルでシミュレートするのは、次の理由からです。$k$小さいです。 
2. 特定の桁位置でのブロックの現在の状態の表現を維持します。 これには、$k+1$現在、数値にはこの桁位置へのキャリーがあります。 これは、桁上げによって桁の合計の寄与が非線形に増加するため、重要です。 
3. 各桁の位置について、可能なすべての桁を試します$d \in [0,9]$のために$x$。 選択ごとに、ウィンドウがどのように表示されるかをシミュレートします。$x \dots x+k$桁上げが次の桁位置にどのように伝播するかなど、この桁で動作します。 
4. シミュレーションにより、この桁位置でのコスト寄与が生成されます。つまり、すべての数字の寄与の合計です。$k+1$このレベルの数字。 
5. この貢献を残りの予算と比較します$n$。 数字を選択する場合$d$まだ建設を完了させることができる（つまり、残りの予算がより高い桁で達成可能である）場合は、それを維持します。 それ以外の場合は破棄します。 
6. 常に各位置で最小の有効な数字を選択し、グローバルな最小性を保証します。$x$。 
7. 必要な寄与がすべて満たされ、それ以上の桁が必要なくなるまで続行し、先頭の構造を削除して、構築された数値を出力します。 

### なぜ効果があるのか

 重要な不変条件は、アルゴリズムが各桁位置で、下位桁からのキャリーによって引き起こされるすべての桁の寄与を正確に考慮することです。 各ステップはウィンドウ全体で数字を選択した場合の効果を完全にシミュレートするため、$x \dots x+k$、隠された将来のキャリー効果は無視されません。 実行可能な最小の桁を常に選択するため、結果として得られる数値は辞書編集上、基数 10 で最小となり、最小の整数値に正確に対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# Precompute digit sum effect of adding numbers with carry is manageable
# We simulate greedily digit by digit

def solve_case(n, k):
    # We build x in reverse (least significant digit first)
    # state keeps current carry distribution over k+1 numbers
    # each offset i contributes (x + i)
    
    x_digits = []
    
    # carry[i] means whether number (x+i) has carry into current digit
    carry = [0] * (k + 1)
    
    # remaining digit sum we must achieve
    remaining = n
    
    # we cap digits because n is small (<=150), so answer is short
    for pos in range(0, 60):
        found = False
        
        for d in range(10):
            new_carry = [0] * (k + 1)
            total = 0
            ok = True
            
            for i in range(k + 1):
                val = d + carry[i]
                total += val % 10
                new_carry[i] = val // 10
            
            # crude upper bound feasibility check:
            # remaining after this digit must not go negative
            if total <= remaining:
                # assume optimistic continuation
                found = True
                best_d = d
                best_carry = new_carry
                best_total = total
                break
        
        if not found:
            break
        
        x_digits.append(best_d)
        remaining -= best_total
        carry = best_carry
    
    if remaining != 0:
        return -1
    
    # convert digits (reverse because LSB first)
    while len(x_digits) > 1 and x_digits[-1] == 0:
        x_digits.pop()
    
    return int("".join(map(str, x_digits[::-1])))

t = int(input())
for _ in range(t):
    n, k = map(int, input().split())
    print(solve_case(n, k))
```この実装では、最下位側から始めて 1 桁ずつ数値が構築されます。 位置ごとに、0 から 9 までのすべての数字を試し、その数字がすべての数字の合計にどのように寄与するかをシミュレートします。$k+1$数字。 桁上げ配列は、シフトされた数値ごとに、前の桁の加算がどのように上方に独立して伝播するかを追跡します。 

実行可能な最小の桁を貪欲に選択することで、最小性が保証されます。 60 桁のループ境界は安全です。桁合計のターゲットが最大 150 であるため、少数の桁を超えると意味のある寄与が残らないからです。 

実装の微妙な点は、各候補桁がフレッシュ キャリー シミュレーションで個別にテストされることです。 キャリーは選択した桁に依存するため、試行間でキャリー状態を誤って再利用すると、正確性が損なわれます。 

## 実用的な例

 ### 例 1:$n=1, k=0$最小のものが必要です$x$そのような$f(x)=1$。 

| 位置 | 試した数字 | キャリー | 貢献 | 残り |
 | --- | --- | --- | --- | --- |
 | 0 | 0 | 0 | 0 | 1 |
 | 0 | 1 | 0 | 1 | 0 |

 位置 0 で数字 1 を選択し、すぐに停止します。 

これにより、関係する数値が 1 つだけの場合でも貪欲な選択が機能することが確認できます。 

### 例 2:$n=2, k=1$最小のものが必要です$x$そのような$f(x)+f(x+1)=2$。 

| 位置 | 数字 x | 桁 x+1 | 合計貢献額 | 残り |
 | --- | --- | --- | --- | --- |
 | 0 | 0 | 0+キャリー | 1 | 1 |
 | 0 | 0 | 1 | 1 | 0 |

 得ます$x=0$。 

これは、桁シミュレーションで両方の数値を同時に処理することによって隣接結合がどのように処理されるかを示しています。

 ## 特殊なケース

 重要なエッジケースは、キャリーがウィンドウ全体に伝播する場合です。 たとえば、9 の連鎖を形成する数字を選択すると、すべてのエラーが発生する可能性があります。$k+1$数値が高い位置で同時に増加します。 このアルゴリズムは、各桁のシミュレーションでシフトされた数値ごとのキャリーを明示的に計算し、伝播パスが無視されないことを保証するため、これを処理します。 

もう 1 つのエッジ ケースは、すべての桁が決定される前に残りの予算がゼロになる場合です。 構築は依然として暗黙のゼロを使用して続行され、トリミングによって最小限の表現が返されることが保証されます。 これにより、結果を増大させる不必要な先頭桁を含む数値の生成が回避されます。 

最後のエッジケースは、ある位置で有効な数字の選択が存在しない場合です。 この状況では、アルゴリズムは正しく終了し、-1 を返します。これは、桁上げ一貫性のある構築では、必要な桁和制約を満たすことができない継続がないことを反映しています。
