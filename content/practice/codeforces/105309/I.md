 ## 解決策
 ## 問題の理解

 同じ長さの 2 つの文字列が与えられ、連続したセグメントに作用する操作を使用して最初の文字列を変更できます。 各操作ではセグメントを選択し、2 つの固定変換のうち 1 つをそのセグメント内のすべての文字に適用します。 

最初の変換では、アルファベットの中点を中心に文字を反転し、先頭に近い文字が末尾に近い文字に移動するように位置をマッピングします。 2 番目の変換は、文字をアルファベットの 13 位置分回転させ、対称的なペア構造を形成します。この変換を 2 回適用すると、元の文字が返されます。 

タスクは、初期文字列をターゲット文字列に変換するために必要なセグメント操作の最小数を決定するか、それがまったく不可能であるかを決定することです。 

重要な制約は、操作が区間全体に適用されるということです。これは、独立した位置ごとの変換を解決していないことを直ちに示唆しています。 代わりに、連続する位置で同じ操作タイプが必要な場合にマージできる、必要な文字レベルの変換のシーケンスを扱います。 

入力サイズは最大 100 万文字まで可能で、どのソリューションも線形時間で実行されます。 考えられるすべてのセグメントをチェックしたり、インターバル操作を明示的にシミュレートしたりするアプローチは失敗します。これは、セグメントに対する 2 次スキャンでも実行時間を数桁超過するためです。 

どちらの変換でもソース内の文字がターゲットに到達できない場合、微妙なエッジ ケースが発生します。 たとえば、文字の裏面がその反対側と異なるが、どちらもターゲット文字と等しくない場合、一連の操作ではその位置を修正できません。 操作はセグメント全体で均一であるため、隣接する文字に影響を与えずに 1 つの文字を独立して修正することはできないため、不可能性はグローバルに伝播します。 

もう 1 つのエッジ ケースは、位置 i で反転し、i+1 で反対を繰り返し必要とするなど、必要な変換が位置間で交互に行われる場合です。 単純な貪欲な人は、文字ごとにセグメントの開始と終了を試みるかもしれませんが、連続した位置が同じ必要な変換を共有する場合、セグメントは拡張される可能性があるため、それは重要になりすぎます。 

## アプローチ

 強引なアイデアは、操作を直接シミュレートすることです。 考えられるすべてのセグメントを試し、いずれかの変換を適用し、すべての文字列状態に BFS を適用することができます。 各移動は有効な文字列間で遷移するため、これは原理的には正しいですが、状態空間は膨大です。 各文字列には n 個の位置があり、各操作の選択はセグメント エンドポイントのペアと変換タイプに依存し、状態ごとに O(n^2) 個の遷移が与えられます。 可能な文字列の数は 26^n であるため、制限された BFS であってもすぐに爆発します。 

各位置に関連する変換が 2 つだけあるという事実に焦点を当てることで、より構造化されたブルート フォースがわずかに改善されます。 インデックスごとに、逆または逆 (または両方のシーケンス) で s[i] を t[i] に変換できるかどうかを計算できます。 次に、問題を、位置ごとにいくつかのラベルのうちの 1 つを割り当て、その後セグメントにグループ化することに縮小します。 それでも、単純にセグメント パーティションを再計算すると、最悪の場合でも O(n^2) のコストがかかります。 

重要な観察は、実際の中間文字列について推論する必要がまったくないということです。 各操作は、セグメント上の変換状態の均一な切り替えにすぎません。 したがって、文字列の観点から考える代わりに、可能であれば、s[i] を t[i] に固定するためにどの変換が必要かを各位置がエンコードする派生配列の観点から考えます。

すべての位置が必要な状態にマップされると、問題は次のようになります。この配列を最小数のセグメントでカバーし、各セグメントが固定された方法で状態を変更する一貫したアクションを適用します。 同じ要件を持つ最大の連続ブロックは 1 回の操作で処理できるため、この構造は均一領域間の遷移をカウントするように崩壊します。 

これにより、問題は状態圧縮による線形スキャンに軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 文字列に対するブルート フォース BFS | 指数 | 指数 | 遅すぎる |
 | 単純な間隔シミュレーション | O(n^2) | O(n) | 遅すぎる |
 | 圧縮を使用した最適なリニア スキャン | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、各文字ペア (s[i]、t[i]) を、どのような変換が必要かを示す小さな可能性のセットに変換します。 逆方向と逆方向は固定のインボリューションであるため、各文字には一定数の到達可能な結果のみが含まれます。 どちらの演算も有効な組み合わせも s[i] を t[i] にマッピングできない場合は、直ちに不可能であると結論付けます。 

次に、各位置をターゲット操作ラベルに正規化します。 重要な考え方は、操作の正確な順序は気にせず、必要な位置ごとの変換を実現できる最小数の連続セグメントだけを気にするということです。 

次に、配列を左から右にスキャンし、同じ操作ラベルを必要とする連続する位置をグループ化します。 セグメントに適用される単一の操作では互換性のない変換要件を混在させることができないため、ラベルが変更されるたびに新しいセグメントを開始する必要があります。 

最後に、そのようなセグメントがいくつ存在するかを数えます。これにより、最小移動数が直接得られます。 

### なぜ効果があるのか

 各操作は連続した範囲に対して均一に作用するため、選択したセグメント内ではすべての位置が同じ変換を受ける必要があります。 これにより、ソリューションでは、各ブロックが単一の一貫した変換要件に対応する連続ブロックにのみ配列を分割できるという制約が生じます。 隣接する 2 つの異なる要件をマージしようとすると、少なくとも 1 つの位置で不一致が生じ、無効になります。 したがって、操作の最小数は、実行可能性フィルタリング後の同一の変換ラベルの連続実行の最大数と正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# map letter to 0..25
def val(c):
    return ord(c) - 97

def rev(x):
    return 25 - x

def opp(x):
    return (x + 13) % 26

def solve():
    n = int(input().strip())
    s = input().strip()
    t = input().strip()

    ops = []

    for i in range(n):
        a = val(s[i])
        b = val(t[i])

        ok = False

        # try no-op (should match directly)
        if a == b:
            ops.append(0)
            continue

        # try reverse
        if rev(a) == b:
            ops.append(1)
            continue

        # try opposite
        if opp(a) == b:
            ops.append(2)
            continue

        # try combinations (reverse then opposite or opposite then reverse)
        if opp(rev(a)) == b or rev(opp(a)) == b:
            ops.append(3)
            continue

        print(-1)
        return

    ans = 0
    prev = -1

    for x in ops:
        if x != prev:
            ans += 1
            prev = x

    print(ans)

if __name__ == "__main__":
    solve()
```この解決策では、まず各文字変換を少数の記号状態の 1 つに圧縮します。 このチェックでは、両方の操作を順番に適用すると正しい結果が得られる可能性も含め、許可された変換を使用してターゲット文字に到達できるかどうかを明示的にテストします。 

この配列を構築した後、2 番目のループで、必要な連続セグメントの数がカウントされます。 変数`prev`以前の必要な状態を追跡し、変更が発生するたびに応答が増加します。 最初の要素は常に新しいセグメントを開始します。 

実装の微妙な点は、セグメントをカウントする前に実現可能性をチェックする必要があることです。 到達できない位置がある場合、続行すると誤解を招くセグメント数が生成されます。

 ## 特殊なケース

 エッジ ケースの 1 つは、すべての位置に個別に到達可能であるが、必要なさまざまな操作が交互に行われる場合です。 s = "aaaa" および t = "znzn" のような入力の場合、アルゴリズムは [reverse、opposite、reverse、opposite] のようなシーケンスを割り当てます。 スキャンでは 4 つのセグメントが生成され、互換性のある操作を共有する隣接する 2 つの位置がないことが正しく反映されています。 

もう 1 つのエッジ ケースは、完全に均一な変換です。 すべての位置が反対側を介してマップされる場合、ops 配列は定数です。 スキャンでは単一のセグメントが生成されます。つまり、全範囲に適用される 1 つの操作で十分です。 

最後のエッジケースは不可能です。 逆も逆も（またはそれらの合成も）ターゲットを生み出さないポジションの場合、アルゴリズムは直ちに停止します。 たとえば、s[i] = 'a' で、t[i] が集合 {a, z, n} に含まれない文字である場合、その位置は許可されたシーケンスの下では固定できず、他の位置に関係なく文字列全体を固定することは不可能です。
