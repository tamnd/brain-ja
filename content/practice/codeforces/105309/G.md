 ## 解決策
 ## 問題の理解

 私たちはパンケーキ店の輪を与えられました。 各店舗にはある程度の数のパンケーキがあり、すべての店舗がサイクルで配置されているため、最後の店舗を通過すると最初の店舗に戻ります。 

2 人のプレイヤーがこのサークルと対話します。 まず、ルーラが開始ストアを選択し、次にオスカーが別の開始ストアを選択します。 その後、両者は領土を拡大しますが、それぞれが相手のすでに占有されている店舗に制約されます。 移動は常に循環順序に沿って行われ、どちらも相手が既に訪れている店舗を通過することはできません。 

動きは他のプレイヤーの訪問セグメントによってのみブロックされるため、開始時の 2 つの選択肢によって、円が 2 つの連続する円弧にどのように分割されるかが効果的に決まります。 各プレイヤーは最終的にこれらのアークの 1 つにすべてのパンケーキを集めます。アークの境界は、選択した 2 つの開始位置によって完全に決定されます。 

ルーラの視点から見ると、彼女は最初に開始する店を選択し、オスカーはその後で最適に反応します。 オスカーの目標は、ルーラが最終的に集めたパンケーキができるだけ小さくなるように出発点を選択することですが、ルーラは保証された結果を最大化したいと考えています。 

入力により複数のテスト ケースが提供されます。 各テスト ケースでは、店舗の数と各店舗のパンケーキについて説明します。 出力は、ルーラが両側からの最適なプレイの下で保証できる最大のパンケーキの合計です。 

すべてのテスト ケースにわたる n の合計が最大 2×10^5 であるという制約は、テスト ケースごとにほぼ線形またはほぼ線形よりも悪い値を許容できないことを意味します。 テスト ケースあたり O(n²) 戦略では、最悪の場合約 10^10 の演算に達するため、遅すぎます。 すべてのテストで O(n²) であっても、明らかに失敗します。 これにより、円形配列での接頭辞合計と二分探索または 2 ポインタ手法が推進されます。 

循環ラップを考慮せずに間隔について局所的に推論する場合、微妙な失敗例が発生します。 たとえば、価値の高いストアが n と 1 の間の境界を越えて分割されている場合、線形間隔モデルは壊れます。 

p = [100, 1, 1, 100] の場合、反対側の点を選択すると、[100,1] や [1,100] のような円弧が生成される可能性があり、単純な線形セグメンテーションでは、これらが円上で実際に隣接していることを見逃してしまいます。 正しい解決策では、配列を循環として扱う必要があります。 

もう 1 つの落とし穴は、Lura が点のペアに対して 2 つの固定円弧のうち大きい方を単純に取ると仮定していることです。 正しい値は、最適なトラバース方向に依存します。これは、循環構造に暗黙的に含まれており、無視できません。 

## アプローチ

 ブルートフォース戦略は、ルーラに対して可能なすべての開始ストアとオスカーに対して可能なすべての応答を試みます。 開始点 i と j の固定ペアの場合、円は 2 つの円弧に分割されます。 両方の円弧のパンケーキの合計を計算し、制約によって引き起こされる 2 つの可能な方向のうち良い方を Lura に割り当てます。 これには、アークサムを計算するためにペアごとに O(n) の作業が必要で、単純に実行した場合は合計が O(n³) になり、各ペアにプレフィックス合計が使用された場合は O(n²) になります。 

10^5 までの n に対しては、O(n²) でも遅すぎます。 重要な観察は、開始位置 i が固定されている場合、オスカーは任意の複雑な戦略を選択していないということです。 j の選択は、円が 2 つの相補的な円弧にどのように切断されるかを決定するだけです。 Lura の最終的なゲインは、これら 2 つの弧の合計の最大値になります。これは、円が i と j で分割されたときの大きい方の部分のサイズに相当します。 

総和が T で、1 つのアークの合計が x である場合、もう 1 つのアークは T − x であるため、Lura は max(x, T − x) を取得します。 これを最小限に抑えることは、x を可能な限り T/2 に近づけることと同じです。 したがって、オスカーは、i から j までのアーク和が可能な限りバランスがとれるように j を選択しようとします。

したがって、各 i について、問題は次のようになります。円上のすべての j の中で、i から始まるプレフィックスの合計が合計の半分に最も近くなるカットを見つけます。 次に、ルーラは、オスカーが最適に応答した後、達成可能な最良のバランスを最大化するために i を選択します。 

これにより、問題は、プレフィックス合計を含む倍増配列に対する古典的な「ターゲットに最も近いプレフィックス合計」クエリに変換され、二分探索を使用して解決できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 遅すぎる |
 | プレフィックス + 二分検索 | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 円を 2 回複製した線形配列に展開して、円セグメントが通常の間隔になるようにします。 この拡張配列上でプレフィックスの合計を構築します。 

1. すべてのストアの合計 T を計算し、長さ 2n の配列でプレフィックスの合計を構築します。ここで、後半は最初の半分を繰り返します。 これにより、i で始まる円形セグメントを標準の部分配列の合計として表すことができます。 
2. 元の範囲内の各開始位置 i について、区間 (i+1, i+n−1) 内の端点 j のみを考慮します。 この制限により、1 つの完全な円を超えて完全にラップすることがなくなり、セグメントの意味が保たれます。 
3. 固定の i と j に対して、x = i から j までのパンケーキの合計を前方に定義します。 これは、prefix[j] − prefix[i] として計算されます。 相補的な円弧の値は T − x です。 
4. このペアに対して Lura が受け取る値は max(x, T − x) です。 これは、x が T/2 にできるだけ近い場合に最小化されます。これは、2 つの円弧のバランスが可能な限り保たれるためです。 
5. したがって、各 i について、prefix[j] が prefix[i] + T/2 に最も近くなるような j を検索します。 ソートされたプレフィックス構造に対して二分探索を使用して、最適な候補 j を見つけます。 
6. 各 i に対して最適な j を評価し、結果の値 max(x, T − x) を計算し、すべての i にわたって最大値を維持します。 

最終的な答えは、ルーラが最適な開始位置を選択することによって強制できる最高の保証された結果です。 

### なぜ効果があるのか

 重要な不変条件は、開始点のどのペアでも、円は正確に 2 つの相補的な円弧に分割され、Lura のゲインは大きい方の円弧のサイズのみに依存するということです。 この削減が行われると、敵対的な構造は消滅します。オスカーの最適な応答は、単にプレフィックスの合計に関する幾何学的なバランスの問題です。 すべての有効な分割はプレフィックス合計の 1 つの違いに正確に対応するため、T/2 に最も近い値を検索すると、設定を見逃すことなくすべての最適な応答が取得されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        p = list(map(int, input().split()))
        
        T = sum(p)
        a = p + p
        
        pref = [0] * (2 * n + 1)
        for i in range(2 * n):
            pref[i + 1] = pref[i] + a[i]
        
        best = 0
        
        from bisect import bisect_left
        
        for i in range(n):
            base = pref[i]
            target = base + T / 2
            
            l = i + 1
            r = i + n - 1
            
            # binary search on pref to find closest pref[j]
            # we search in indices [l, r]
            
            # convert to values
            # we binary search on pref[l..r]
            lo, hi = l, r
            
            while lo <= hi:
                mid = (lo + hi) // 2
                if pref[mid] < target:
                    lo = mid + 1
                else:
                    hi = mid - 1
            
            candidates = []
            if l <= lo <= r:
                candidates.append(lo)
            if l <= lo - 1 <= r:
                candidates.append(lo - 1)
            
            for j in candidates:
                x = pref[j] - base
                val = max(x, T - x)
                if val > best:
                    best = val
        
        print(best)

if __name__ == "__main__":
    solve()
```この実装では、循環間隔が線形範囲になるように、2 倍の配列にプレフィックスの合計が構築されます。 開始インデックス i ごとに、円弧の合計が合計の半分に最も近くなる分割点 j を検索します。 二分検索では、生のインデックスではなくプレフィックス値がターゲットとなるため、検索位置の周囲の候補をチェックする必要があります。 

浮動小数点除算はターゲットに対してのみ使用するように注意する必要があります。 2_T および 2_x で整数演算を使用すると、厳密な実装における精度の問題を回避できます。 lo および lo−1 周辺の候補処理により、正確なターゲットが存在しない場合でも正確さが保証されます。 

## 実用的な例

 円が [4, 9, 3, 5] である小さな構成を考えてみましょう。 合計は21になります。 

固定開始点 i = 0 (値 4) について、円の周囲の可能なカット点 j を調べます。 目標は、10.5 に最も近い 4 から始まるプレフィックスの合計を見つけることです。 

| j | アークサム x | T − x | max(x, T − x) |
 | --- | --- | --- | --- |
 | 1 | 13 | 8 | 13 |
 | 2 | 16 | 5 | 16 |
 | 3 | 21 | 0 | 21 |

 i = 0 からの最良のカットは、値 13 を与える j = 1 です。 

ここで、i = 1 (値 9) について考えてみましょう。 

| j | アークサム x | T − x | max(x, T − x) |
 | --- | --- | --- | --- |
 | 2 | 12 | 9 | 12 |
 | 3 | 17 | 4 | 17 |
 | 4 | 21 | 0 | 21 |

 最良のカットは、値 12 の j = 2 です。 

これは、開始点が異なると可能な限り最適なバランスが異なることを示しており、ルーラは最悪の場合の結果を最大化する開始位置を選択します。

 ## 特殊なケース

 すべてのパンケーキが小さな連続領域に集中している場合、重要なエッジケースが現れます。 [100, 1, 1, 1, 1] のような入力の場合、100 個のクラスターの分割を回避するカットを行うと、非常に不均一な円弧が生成されます。 このアルゴリズムはこれを正しく処理します。これは、半分に最も近い検索でも大きなブロックに隣接する境界が返され、達成可能な円弧が最大化されるためです。 

もう 1 つのケースは、最適な分割がちょうど中間にあるものの、プレフィックスの合計として明示的に存在しない場合です。 たとえば、[2、2、2、2]。 ターゲットは 4 ですが、すべての開始点から正確に 4 に等しいプレフィックスはありません。 二分検索では、どちらかの側で最も近いプレフィックスが正しく選択され、選択された円弧が可能な限りバランスが取れていることが保証されます。 

最後の微妙なケースはラップアラウンド優勢であり、最良のアークが n 対 1 の境界を越えます。 複製された配列の構築により、そのようなすべてのセグメントが連続した間隔として表現されることが保証されるため、拡張プレフィックス合計配列を超える特別な処理は必要ありません。
