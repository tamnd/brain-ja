 ## 問題の理解

 ブロックの重みの複数のセットが与えられます。 重量値ごとに$i$、 がある$a_i$同一の重量のブロック$i$。 プレイヤーは交互に残りのブロックを取得し、その重みをゼロから始まる累計に加算します。 合計を指定された目標とまったく同じにするプレーヤー$k$、またはブロックが残っていないため移動できない場合は負けです。 フィービーは常に最初に動き、両方のプレイヤーが最適にプレイすると想定されます。 

ゲームのクエリでは、ブロックの固定構成と目標合計が求められます。$k$、両方のプレイヤーが完璧に行動した場合、どちらが勝ちますか。 さらに、単一の更新を許可されています$a_i$クエリ間の値。 

したがって、各クエリは、頻度配列のポイント更新か、同じ重み付きトークンのマルチセットのゲーム評価のいずれかです。 

制約は大きく、最大で$2 \cdot 10^5$重みとクエリ、重みには最大までのカウントを含めることができます。$10^8$。 目標金額$k$まで行くことができます$10^{18}$これにより、合計の列挙、ゲーム状態のシミュレーション、またはプレフィックス DP の構築に依存する解決策は次のとおりであることがすぐにわかります。$k$不可能です。 すべての重みのクエリごとの線形スキャンでさえ境界線にありますが、それでも許容できる可能性がありますが、二次的なものや依存するものはすべて$k$は除外されます。 

このゲームの微妙な問題は、単に金額の到達可能性だけが問題ではないということです。 負けの条件には、「$k$」そして「もう手は残っていない」。 これにより、相互作用する 2 つの負け状態が作成されます。 「誰に届くのか」という素朴な欲張りな解釈$k$まず」だけでは不十分です。 

よくある失敗例は、合計だけが重要であると仮定することです。 たとえば、合計が以下の場合、$k$、最後のプレイヤーは力尽きてすぐに負けますが、合計が大きければ、正確に到達します$k$たとえ後で勝ち手があったとしても、タイミングを誤ると損失を強いられる可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、残りのマルチセットと現在の合計に対する再帰を使用して、すべてのゲーム状態をシミュレートします。 各状態は、残りのすべてのブロック タイプに分岐します。 状態の数は指数関数的です$n$、そしてメモ化を行ったとしても、状態空間は残りのブロックの可能なすべてのサブセットと可能な合計に依存します。$k$。 以来$k$できる$10^{18}$、合計によってインデックス付けされた DP は不可能です。 ゲーム理論に基づいた慎重な DP であっても、クエリごとに大規模な状態遷移を追跡する必要があり、これでは遅すぎます。 

重要な観察は、手の正確な順序はパリティと合計がヒットするかどうかを制御する能力を超えて重要ではないということです。$k$強制された瞬間に。 これにより、ゲームはマルチセットの構造的特性に還元されます。つまり、移動するプレイヤーが重要なしきい値を「完了」するプレイヤーになることを回避できるかどうかです。 

決定的に単純化しているのは、ゲームをプレイヤーが交互にトークンを消費するプロセスとして見なすことであり、唯一の負けの瞬間はプレイヤーが末期状態に追い込まれたときです。 これは古典的な「特別な負けトリガーを持つアイテムを順番に削除する」問題になります。これは、移動するプレイヤーが、早期終了を回避するために移動する総移動数に対して同等の優位性を強制できるかどうかを分析することに還元できます。$k$。 

重要な変革は、利用可能な手の合計数という観点から考えることです。$S = \sum a_i$、および合計を正確にヒットさせることなく、手のプレフィックスをいくつプレイできるか$k$。 プレイヤーは残りのブロックを選択できるため、合計を効果的に遅らせたり加速したりできますが、最適なプレイの下で 1 つの順序構造だけが一貫している場合、枯渇または強制完了の必然性を避けることはできません。 

これにより、問題は、以下から導出される単純なパリティ条件に基づいて、最初のプレーヤーのポジションが負けているかどうかを判断するという問題に軽減されます。$k$は、マルチセット構造全体内のサブセット合計境界として表すことができます。 更新ではローカル数のみが変更されるため、グローバル集計は維持されます。 

実際には、解決策は、ブロックの総数を維持し、重みの合計が少なくとも$k$、そして残りの動きの同等性により最初のプレイヤーが最終的な動きを強制されるかどうか。 これが機能する理由は、最適なプレイが効果的にゲームを強制的なシーケンスに減らすためです。$S$厳密な合計で単一の禁止終了条件を伴う移動$k$、これはパリティ反転されたしきい値のように動作します。

 ## アルゴリズムのチュートリアル

 ブロックの総数という 2 つのグローバル数量を維持します。$S = \sum a_i$、および加重合計の合計$T = \sum i \cdot a_i$。 

各クエリはこれらの値を変更またはテストします。 

### ステップ

 1.初期化$S$そして$T$入力配列から。 これらはそれぞれ、存在する手数と、すべてのブロックが取られた場合に利用可能な合計がいくらになるかを表します。 
2. インデックスでの SET 操作の場合$i$、その重みの寄与を更新します。古い寄与を削除し、新しい寄与を追加します。 これにより両方が維持されます$S$そして$T$一貫性のある。 
3. パラメータ付きのゲームクエリの場合$k$、まず比較してください$T$と$k$。 もし$T < k$、合計は決して達しません$k$したがって、ゲームは常に力尽きて終了し、勝者は純粋に次の要素の同等性によって決まります。$S$。 フィービーが始まってから、もし$S$彼女が最後の動きをして負けるのは奇妙ですが、そうでなければライアンが負けます。 
4. もし$T \ge k$、そして到達$k$可能です。 最適なプレイでは、移動するプレイヤーが合計を作成することを強制されるかどうかが重要な問題になります。$k$彼らの順番で。 これも同様にパリティ条件になります。結果は、しきい値に達するまでに残っている安全な手の数が最初のプレイヤーのターンと一致するかどうかによって決まります。 
5. 条件は次のことをチェックすることを単純化します。$(T - k)$～に対して偶数か奇数か$S$。 フィービーが最終移動を強いられることを回避できるようにパリティが揃った場合、彼女の勝ちです。 そうでなければライアンが勝ちます。 

### なぜ効果があるのか

 不変なのは、どのステージでも、プレイヤーはマルチセット自体ではなく、消費の順序のみを制御するということです。 ゲームは固定長のシーケンスとして進化します。$S$移動します。唯一の特徴は、累積和が正確に一致するかどうかです。$k$強制的な境界線で。 プレフィックスの合計に寄与する重みを除いて、すべての手が交換可能であるため、ゲームはパリティ制御のスケジューリング問題に帰着します。 どの戦略も一度強制終了位置の同等性を変更することはできません$S$そして$T$が固定されているため、結果はこれらの集計によって完全に決定されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    S = sum(a)
    T = sum((i + 1) * a[i] for i in range(n))

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == "SET":
            i = int(tmp[1]) - 1
            x = int(tmp[2])
            T -= (i + 1) * a[i]
            S -= a[i]
            a[i] = x
            T += (i + 1) * a[i]
            S += a[i]
        else:
            k = int(tmp[1])

            if T < k:
                if S % 2 == 1:
                    print("PHEBE")
                else:
                    print("RYAN")
            else:
                if (T - k) % 2 == S % 2:
                    print("PHEBE")
                else:
                    print("RYAN")

if __name__ == "__main__":
    solve()
```この実装では、利用可能なブロックの数とその合計の重みの合計の両方が維持されるため、各更新は一定時間で処理されます。 重要な点は、ゲームを決してシミュレートしないということです。 代わりに、各クエリは定数時間のパリティ チェックに縮小されます。 更新ステップでは、二重カウントを避けるために、新しい寄与を適用する前に古い寄与を慎重に削除します。 

唯一の微妙な部分は、インデックスの一貫性を保つことです。問題では重みは 1 から始まりますが、Python では配列は 0 から始まるからです。

 ## 特殊なケース

 エッジケースの 1 つは次のような場合です$k$達成可能な合計額を超えています。 その場合、ゲームは常にすべてのブロックを使い果たすことで終了します。 たとえば、$a = [1]$そして$k = 10$、移動は 1 つだけです。 フィービーはそれを受け取り、すぐにブロックを残さなくなり、負け条件がトリガーされるため、フィービーは負けます。 アルゴリズムはこれを捕捉します。$T < k$そして$S = 1$, したがって、パリティ ロジックに従って PHEBE を返します。 

もう 1 つのエッジケースは次のような場合です$k$は合計とまったく同じです。 その場合、最後の動きは必然的に$k$。 のために$a = [2,1]$そして$k = 3$、最後のブロックを取ることを強制された人が合計を完了し、負けます。 手数は固定されているため、パリティ条件によって、誰がその強制的な最終状態に到達するかが正確に決定されます。
