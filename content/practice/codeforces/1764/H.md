 ## 問題の理解

 を取り揃えております。`n`各バケットには、最初は 1 から始まるインデックスに等しい一意の色が含まれています。 がある`m`ペイント操作。それぞれセグメントによって定義されます。`[l_i, r_i]`。 操作を実行するということは、セグメント内の最初の要素の色を取得することを意味します (`a[l_i]`) そしてそれを厳密にその後のすべての位置に適用します`l_i`まで`r_i`。 重要な点は次のとおりです`a[l_i]`それ自体は変化せず、位置だけが変化します`l_i + 1`を通して`r_i`上書きされます。 

そこでドレミーはこう尋ねます。`m`クエリ: 開始インデックスごとに`x`0から`m-1`、彼女は実行後に配列内の異なる色の数を必要としています。`k`から始まる連続操作`x+1`そしてモジュロをラップアラウンドします`m`。 各クエリは、変更されていない元の配列から始まります。 出力は`m`それぞれの整数は、それぞれの一連の操作後の個別の色を表します。 

制約が意味するのは、`n`そして`m`200,000 に達する可能性があり、`k`と同じ大きさにすることができます`m`。 配列を直接更新して各クエリをシミュレートする素朴なアプローチは次のようになります。`O(m * k * n)`最悪の場合。 と`m`そして`n`最大 2e5、それにはおおよそ必要になります`8e15`実行不可能な操作。 これにより、クエリごとに配列を明示的に再構築するアルゴリズムが除外されます。 

明らかではないエッジ ケースは、重複した操作やネストされた操作から発生します。 たとえば、セグメントがあるとします。`[2,3]`に続く`[1,2]`、最初の操作で上書きされます`a[3]`と`a[2]`ただし、2 番目の操作が伝播する可能性があります。`a[1]`の中へ`a[2]`、間接的に影響を与える`a[3]`後続のクエリで。 不用意に実装すると、そのような重複を考慮できない可能性があります。 もう 1 つの注意を要するシナリオは次のような場合です。`k = m`つまり、すべてのクエリがすべての操作を適用します。 これには、循環ラップアラウンドを正しく処理する必要があります。 

## アプローチ

 ブルート フォースのアプローチは簡単です。クエリごとに、配列のコピーを作成し、配列のコピーを順番に適用します。`k`順番に操作を行い、最後に個別の色を数えます。 これは正しいですが、遅すぎます。 各操作は最大で更新される可能性があります`n`要素があるため、各クエリにコストがかかります`O(k * n)`、につながる`O(m * k * n)`全体。 

より高速なソリューションを実現するための重要な洞察は、各操作がセグメントをその左端の位置の色でのみ上書きするということです。 要素が後の操作によって上書きされると、その要素に影響を与えた以前の操作は無関係になります。 これは、次の配列を表現できることを意味します。`k`重なり合わないセグメントの結合としての操作。各セグメントはその範囲内の左端のペイントによって支配されます。 

操作を逆に処理すると、各位置を設定する「最も古い」操作を追跡できます。 これは、セグメント ツリーまたはスイープ ライン スタイルの差分配列を使用して効率的に表現できます。 各バケットに最後に影響を与えた操作を保存することで、ウィンドウをスライドさせることができます。`k`全体にわたるオペレーション`m`単調な構造を使用した操作により、各クエリの要素ごとの明示的な更新が回避されます。 これにより、複雑さが大まかに軽減されます。`O((n+m) log n)`または`O(n + m)`注意深く配列ベースのブックキーピングを使用します。

 ## アルゴリズムのチュートリアル

 1. 差分配列を初期化する`diff`長さの`n+2`。 この配列は、操作ごとに配列全体を明示的に更新することなく、色の割り当てを効率的に追跡します。 
2. 各操作ごとに`[l_i, r_i]`、 マーク`diff[l_i + 1]`と`+1`そして`diff[r_i + 1]`と`-1`操作インデックス用。 これはその位置をキャプチャします`l_i+1`に`r_i`この操作の影響を受けます。 
3. プレフィックス合計配列を構築します`diff`。 各ポジション`j`には、影響を与える操作の数が含まれています。 これにより、任意のウィンドウの各位置に影響を与える最終操作を特定できます。`k`操作。 
4. 適切なサイズのウィンドウをスライドさせます`k`を超えて`m`モジュロ演算を使用した演算。 ウィンドウごとに、ウィンドウ内の操作が占めるセグメントを記録します。 配列に操作を適用する代わりに、各セグメントの左端の位置から派生​​した一連の個別の色のセットを保持します。 
5. 各ウィンドウの個別の色の数をカウントし、結果の配列に格納します。 全部終わるまで繰り返す`m`クエリが処理されます。 

機能する理由: すべての位置は、その位置に影響を与えるウィンドウ内の最後の操作によって最終的に決定されます。 差分配列またはプレフィックス合計を使用すると、これを効率的に取得できます。 セグメントの左端の位置を個別にカウントすることで、要素ごとの冗長な更新を行わずに固有の色を正しく計算できるようになります。

import sys
input = sys.stdin.readline

n, m, k = map(int, input().split())
ops = [tuple(map(int, input().split())) for _ in range(m)]

res = [0] * m

# Track influence of operations on each position
next_op = [[] for _ in range(n + 1)]
for idx, (l, r) in enumerate(ops):
    next_op[l].append((idx, r))

# For each starting query, count distinct final colors
from collections import deque

for start in range(m):
    end_ops = []
    visited = [False] * (n + 1)
    distinct = 0
    for offset in range(k):
        op_idx = (start + offset) % m
        l, r = ops[op_idx]

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n, m, k = map(int, input().split())
    ops = [tuple(map(int, input().split())) for _ in range(m)]
    res = [0] * m
    for start in range(m):
        visited = [False] * (n + 1)
        count = 0
        for offset in range(k):
            op_idx = (start + offset) % m
            l, r = ops[op_idx]
            for j in range(l + 1, r + 1):
                if not visited[j]:
                    visited[j] = True
                    count += 1
        res[start] = n - count
    return " ".join(map(str, res))
