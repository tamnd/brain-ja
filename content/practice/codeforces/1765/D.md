 ## 解決策
 ## 問題の理解

 一連のビデオが与えられ、それぞれのダウンロード サイズと、一度に保存できるメガバイト数を制限する固定ディスク容量が指定されています。 各ビデオのダウンロードにはそのサイズに比例した時間がかかり、ダウンロード後はちょうど 1 分で視聴できます。 視聴してもダウンロードはブロックされないため、ダウンロードと視聴が時間的に重なる可能性があります。 

重要な制約は、ダウンロードが厳密に連続的に行われることです。 一度に実行できるダウンロードは 1 つだけであり、ダウンロードを開始すると、そのサイズに等しいディスク領域がすぐに予約されます。 十分な空き容量がない場合は、以前に視聴したビデオが削除され、容量が解放されるまでダウンロードを待つ必要があります。 削除は瞬時に行われ、視聴後に行われます。 

目標は、ダウンロードと視聴を一定の順序でスケジュールして、最終的にすべてのビデオが視聴され、合計完了時間を最小限に抑えることです。 

入力はビデオのサイズとディスク容量だけです。 出力は、最後のビデオが視聴されるまでの最小合計時間です。 

最大 200000 の制約 n は、状態シミュレーションごとに重い定数を伴う二次関数や O(n log n) さえも除外します。 各ビデオのダウンロードには最大 10^9 分かかる可能性があるため、分ごと、またはイベントごとに時間を直接シミュレーションすることは不可能です。 

いくつかの特殊なケースは、早期に切り分ける価値があります。 

ディスクが非常に大きい場合、たとえば m が少なくともすべてのサイズの合計である場合、ダウンロードをブロックするものは何もありません。 答えは簡単です。最後のビデオはサイズの合計でダウンロードが終了しますが、その後 1 分以内に視聴する必要があるため、答えは sum(a) + 1 になります。 

ディスクが小さい場合、たとえば m が単一ビデオの最大サイズに等しい場合、システムは非常に制限されます。 ほぼすべての視聴後に削除を待たなければならない可能性があります。つまり、ダウンロードの順序が重要になります。 

大きなビデオが早期にダウンロードされてもすぐに視聴できない場合、微妙な失敗例が発生し、その後のダウンロードが不必要にブロックされます。 たとえば、最初に巨大なビデオをダウンロードすると、ディスク容量が長時間占有され、以前にダウンロードして視聴できたはずの小さなビデオが遅れます。 

## アプローチ

 ブルートフォース戦略では、ビデオのすべての可能な順序を試し、プロセスをシミュレートします。 順列ごとに、現在の時刻、進行中のダウンロード、ディスク使用量、および利用可能なビデオのキューを維持します。 各シミュレーション ステップでは、次のダウンロード完了または監視完了まで時間を進め、それに応じて状態を更新します。 これはルールに直接従うので正しいですが、n! があります。 順列化が必要であり、1 回のシミュレーションでも O(n) のコストがかかるため、これは完全に不可能になります。 

問題の実際の構造は、ダウンロード プロセスが唯一のシリアル ボトルネックであるということです。 ダウンロード チャンネルの視聴は無料ですが、ディスクの可用性に影響します。 重要な点は、重要なのは、スペースが利用可能になったときと比較してビデオのダウンロードがいつ終了するかだけであり、任意のスケジュールを正確にインターリーブすることではないということです。 

順列の観点から考える代わりに、私たちは実行可能なスケジュールを維持する観点から考えます。つまり、常に次のビデオのダウンロードを続けるか、ディスク容量が十分でないために待機せざるを得なくなるかのどちらかです。 目標は、待ち時間を最小限に抑えるようにビデオを配置することです。 

重要な洞察は、大きなビデオはディスク容量を長時間確保し、今後のダウンロードを遅らせるため、ブロッキングの原因となるものであるということです。 このプロセスを貪欲なスケジューリングの問題として扱う場合、大規模なダウンロードを開始するときに、完了してスペースを解放できたはずの小さなダウンロードに早い時間を無駄にしないようにしたいと考えます。

これにより、シミュレーションと組み合わせた 2 ポインターの貪欲な構築が可能になります。 私たちは、合計サイズが m を超えない「アクティブなダウンロード」の現在のウィンドウを維持します。 ダウンロードを順番に進めるよう努めますが、ビデオが収まらない場合は、最も早くダウンロードを完了し、スペースを解放してから続行することで時間を進めます。 

これにより、最適なパイプラインが効果的にシミュレートされます。ダウンロードは順次に進行しますが、必要な場合にのみ停止し、ダウンロード フェーズと監視フェーズの間の並行進行を常に最大化します。

 | ブルートフォース | お(ん!) | O(n) | 遅すぎる |

 ## アルゴリズムのチュートリアル

 現在どのダウンロードが進行中で、どのくらいのディスク容量を占有しているかを追跡する構造を維持しながら、ビデオを順番に処理します。 

1. アクティブなダウンロードのキューを維持します。それぞれの終了時間とサイズ、および使用済みディスク容量を追跡する変数が含まれます。 現在時刻も維持します。 
2. ビデオを順番に繰り返し、できるだけ早く各ビデオのダウンロードを開始しようとします。 十分な空きディスク容量がある場合は、すぐにダウンロードを開始し、完了時間をスケジュールします。 
3. 十分なスペースがない場合は、アクティブなファイルの中で最も早くダウンロードが完了するまで時間を進めます。 ダウンロードが完了すると、視聴時間が 1 分追加され、その後にのみディスク領域が解放されます。 これは、視聴が完了するまでスペースが占有されるという制約を反映しています。 
4. 完了したダウンロードを繰り返しポップし、視聴後にスペースを解放し、現在のビデオが開始できるまで続行します。 
5. 各ビデオの終了時刻を、視聴が終了した時刻として記録します。 
6. 答えは、すべてのビデオの最大終了時間です。 

重要な構造上の考え方は、時間は宇宙を待たなければならない場合にのみ前進するということです。 このようなイベントの合間に、私たちは貪欲にダウンロードを実行し続けます。 

なぜそれが機能するかは、スケジュールの単調性の特性に基づいています。 ダウンロードはシリアルで非プリエンプティブであるため、スペースの制約なしにダウンロードを遅らせても、最終的な完了時間を改善することはできません。 延期する唯一の理由は、将来の実現可能性を確保するためです。 このアルゴリズムは常に、ディスク容量によって必要な場合にのみ遅延します。つまり、不必要なアイドル時間が発生することはありません。 すべてのビデオが順番に処理され、すべての制約違反が必要最小限のタイムジャンプをトリガーするため、スケジュールはシステムの最適なイベント駆動型シミュレーションと同等です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    
    # each element: (finish_download_time, size)
    from collections import deque
    
    time = 0
    used = 0
    q = deque()
    
    ans = 0
    
    i = 0
    while i < n or q:
        # if nothing downloading, jump start next
        if not q and i < n:
            time = max(time, 0)
        
        # try to start as many downloads as possible
        while i < n and used + a[i] <= m:
            used += a[i]
            q.append((time + a[i], a[i]))
            i += 1
        
        if q:
            # next completion
            ft, sz = q.popleft()
            time = ft
            
            # watching takes 1 minute
            finish_watch = time + 1
            ans = max(ans, finish_watch)
            
            # free space after watch
            used -= sz
            time = finish_watch

        else:
            # no active downloads, must advance time
            if i < n:
                time = time
            else:
                break
    
    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、アクティブなダウンロードのキューが維持され、それぞれに完了時間がタグ付けされます。 ディスク容量が許す限り、常に新しいダウンロードを開始しようとします。 続行できない場合は、次のダウンロード終了まで時間を進め、視聴をシミュレートしてから、ディスク領域を解放します。 微妙な点は、ディスク領域がダウンロードの完了時ではなく、視聴の完了後にのみ解放されるということです。そのため、終了時刻と終了_監視時刻を分けています。 

変数`ans`ビデオの最後に視聴が終了した時間を追跡します。これが真の完了基準です。

 ## 特殊なケース

 エッジ ケースの 1 つは、ビデオが 1 つだけ存在する場合です。 アルゴリズムはダウンロードを直ちに開始し、そのサイズに等しい時間に完了します。監視すると 1 分が追加され、サイズに 1 を加えたものが生成されます。 これは、単一の要素を持ち、ブロック イベントを持たないキューから直接得られます。 

もう 1 つのエッジ ケースは、すべてのビデオが一度にディスクに正確に収まる場合です。 キューは時間 0 で完全にいっぱいになり、完了するたびに監視と即時のスペース解放がトリガーされます。 システムは完全に利用されたパイプラインのように動作し、アルゴリズムはアイドル時間を発生させることなく連続した終了を正しく処理します。 

3 番目のエッジケースは、すべてのビデオが大きすぎて他のビデオと共存できない場合です。 この場合、キューのサイズは常に 1 であり、反復ごとに時間が進み、次のダウンロードが開始される前に完了します。 アルゴリズムは自然に、イベント間の正しい間隔で順次実行されるように縮退します。
