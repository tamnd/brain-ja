 ## 解決策
 ## 問題の理解

 エルフが一人ずつ到着するシーケンスが与えられます。 各エルフには病気の閾値があります$s_i$。 それぞれに健康価値が設定された固定の料理セットもあります$h$そしておいしさの価値$t$。 

料理はエルフに割り当てることができますが、料理の健康状態がエルフの病気の閾値よりも厳密に小さい場合にのみ、そのエルフを殺します。 エルフに自分を殺す料理が割り当てられていない場合、そのエルフは完全に無視され、何も貢献しません。 重要なのは死んだエルフだけであり、それらのエルフのために、私たちは彼らが消費する料理の総合的な美味しさを最大限に高めたいと考えています。 

重要な制約は、すべてのエルフだけでなく、次のエルフのすべてのプレフィックスに対して最適な答えを出力しなければならないことです。$1$に$n$。 つまり、新しいエルフが到着するたびに、最初のエルフだけを使用して、達成可能な最高の総合的な美味しさを知る必要があります。$i$エルフとすべての料理。 

限界$n, m \le 200000$完全なマッチングを再計算したり、エルフごとにすべての料理をスキャンしようとするアプローチは除外します。 エルフとディッシュの間のすべての割り当てをチェックする素朴なソリューションは、増大するセットに対する二部マッチングのように動作し、少なくとも$O(nm)$容認できる範囲をはるかに超えた行動です。 ソートとプレフィックスごとの繰り返しスキャンでも、依然として二次作業が蓄積されます。 

料理の健康状態は非常に高いが、美味しさが低い場合、微妙なエッジケースが発生します。 入手可能な最もおいしい料理を常に現在のエルフに割り当てる貪欲な戦略は、より弱い選択肢で満足できたはずの料理がエルフに「無駄に」なり、将来の総利益が減少する可能性があるため、失敗する可能性があります。 複数のエルフが同様のしきい値を共有する場合、別の特殊なケースが発生します。 グローバル構造がないと、プレフィックス間でディッシュを最適に再利用すると一貫性がなくなります。 

## アプローチ

 視点を逆にすると、エルフに料理を割り当てるのではなく、料理がいつ使用可能になるかを考えると、構造がより明確になります。 

健康を考えた料理$h$を持つエルフのみが使用できます$s_i > h$。 したがって、各料理には事実上、対象となる最初の接頭辞によって定義される「開始時間」があります。 エルフが到着すると、健康状態がそのエルフのしきい値未満であるすべての料理が考慮されます。 

ここで、各接頭辞のタスクは次のようになります。 利用可能なすべての料理 ($h < s_i$)、各料理を最大 1 回使用できるように、美味しさの合計を最大化するサブセットを選択します。 これは、入手可能な最高の料理を繰り返し摂取することに相当します。 

ブルートフォースアプローチでは、プレフィックスごとにすべての料理をスキャンし、それらをフィルタリングします。$h < s_i$、美味しさ順に分類し、入手可能な最高のものを選択します。 これには費用がかかります$O(nm \log m)$実装によっては、遅すぎる場合もあります。 

重要な洞察は、現在「適格」な料理のデータ構造を維持しながら、エルフを順番に処理することです。 として$s_i$増加すると、より多くの料理が対象になります。 対象となるすべての料理を、おいしさに基づいて最大ヒープに維持できます。 各料理は対象となるときに 1 回だけ挿入されます。 エルフごとに、残っている最良の料理を繰り返し取り出しますが、各料理がグローバルで最大 1 回使用されるようにする必要もあります。そのため、一度削除すると元に戻らないようになります。 

微妙な点は、それぞれの接頭語の答えが累積的であるということです。前の接頭語で料理が取得されると、後の接頭語ではその料理は失われます。 したがって、利用可能なディッシュのグローバル プールを維持し、しきい値が増加するにつれてそれらを段階的にアクティブ化します。 

エルフをしきい値によって並べ替えますが、プレフィックスの回答を元の順序で保持する必要があります。 健康状態ごとに料理を並べ替えると、高い順に料理をアクティブにすることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nm \log m)$|$O(m)$| 遅すぎる |
 | 最適 (ヒープ + ソート) |$O((n+m)\log m)$|$O(m)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべての料理を健康価値順に並べ替えます$h$昇順で。 これにより、ある料理が一部のエルフに適格になると、その後のすべてのエルフにも適格になることが保証されます。 
2. 料理に対するポインタと、現在適格でまだ使用されていないすべての料理のおいしさの値を保存する最大ヒープを維持します。 
3. 実行中のインデックスを維持しながら、エルフを到着順に処理します$i$。 
4. エルフごとに$i$、すべてのディッシュをヒープに挿入します$h < s_i$まだ挿入されていないもの。 このステップにより、有効になったときに使用可能なディッシュのプールが拡張されます。 
5. アクティブ化後、ヒープから最高においしい料理を繰り返し抽出し、それを現在のプレフィックスの答えに追加します。 ヒープが空になった場合、またはプレフィックス構造で有益な割り当てが不可能な場合は停止します。 
6. 選択したすべての美味しさの値の合計をプレフィックスの答えとして保存します$i$、次のエルフに進みます。 

### なぜ効果があるのか

 どのプレフィックスでも$i$、ヒープには、最初のエルフの中のいくつかのエルフに割り当てることができる料理のセットが正確に含まれています。$i$到着。 資格が決定されるとすべての割り当ては独立しており、すでに削除された料理を今後の接頭辞で使用することはできないため、最高の美味しさの料理を貪欲に選択することが最適です。 段階的なアクティブ化により、料理が見逃されることはなくなり、しきい値が単調に増加するため、料理が 2 回適格になったり、再検討されたりすることはありません。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    s = list(map(int, input().split()))

    dishes = []
    for _ in range(m):
        h, t = map(int, input().split())
        dishes.append((h, t))

    dishes.sort()
    heap = []
    ans = []
    j = 0
    total = 0

    for i in range(n):
        while j < m and dishes[j][0] < s[i]:
            heapq.heappush(heap, -dishes[j][1])
            j += 1

        if heap:
            total += -heapq.heappop(heap)

        ans.append(total)

    print(*ans)

if __name__ == "__main__":
    solve()
```料理は 1 回の直線スイープで有効にできるように並べ替えられています。 ヒープには負のおいしさの値が保存され、Python の最小ヒープを使用して最大ヒープをシミュレートします。 ポインタ$j$各料理が正確に 1 回処理されることを保証します。 

微妙な点は、エルフごとに 1 つの料理だけをポップすることです。 これは、各エルフが最大 1 つの料理を消費でき、一度消費すると累積合計に寄与するという解釈と一致します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O((n+m)\log m)$| 各皿が 1 回挿入されると、各ポップのコストは log m |
 | スペース |$O(m)$| ヒープには対象となるすべてのディッシュが格納されます。 

境界$n, m \le 200000$各操作は対数的であり、合計ヒープ操作は入力サイズにおいて線形であるため、快適にフィットします。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque
    import heapq

    n, m = map(int, input().split())
    s = list(map(int, input().split()))
    dishes = [tuple(map(int, input().split())) for _ in range(m)]
    dishes.sort()

    heap = []
    j = 0
    total = 0
    res = []

    for i in range(n):
        while j < m and dishes[j][0] < s[i]:
            heapq.heappush(heap, -dishes[j][1])
            j += 1
        if heap:
            total += -heapq.heappop(heap)
        res.append(str(total))

    return " ".join(res)

 ## 特殊なケース

 重大なエッジケースは、現在のエルフを満たす料理がない場合です。 のような入力の場合$s = [1,1,1]$そしてすべて$h \ge 2$、ヒープは要素を決して受け取らないため、すべてのプレフィックス出力はゼロのままでなければなりません。 挿入は行われず、ヒープ チェックによってポップが防止されるため、アルゴリズムはこれを自然に処理します。 

もう 1 つのエッジ ケースは、大幅な急増により多くの料理が一度に利用可能になる場合です。$s_i$。 ポインタベースのアクティベーションにより、選択が行われる前にすべての料理が 1 回だけ挿入されることが保証されるため、注文によっておいしい料理がスキップされることはありません。 

最後のエッジケースは、美味しさの値が大きくて近い場合です。 ヒープ内では相対的な順序のみが重要であるため、結合は正確さに影響を与えず、それぞれは曖昧さなく独立して使用されます。
