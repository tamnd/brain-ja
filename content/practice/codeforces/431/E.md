 ## 問題の理解

 私たちには一組の容器が与えられ、それぞれの容器には一定量の水銀が入っています。 時間の経過とともに、2 種類の操作が発生します。 

最初の操作では、単一の容器内の水銀の量が変化します。 概念的には、そのチューブを空にしてから再充填すると、その水銀レベルがまったく新しい値になります。 この操作の後は、現在の値のみが重要になるため、常に進化する高さの配列を扱うことになります。 

2 番目の操作はより抽象的です。 私たちには一定量の水が与えられており、この水をすべてのチューブに分割分配を含む任意の方法で分配することが許可されています。 分配後、各チューブの総内容物は、元の水銀と受け取った水を加えたものになります。 その特定の分布については、最終的に最大の総体積となるチューブに注目します。 任意の分散戦略を自由に選択できるため、選択が異なると最大値も異なります。 このタスクでは、悲観的な意味で最善の戦略を求めます。考えられるすべての分散の中で、その分散によって生成される最大負荷を考慮し、この最大値を最小化する分散を選択します。 

したがって、2 番目のクエリは、固定総量の水を加えた後に達成可能な最小の最大最終高さを求めています。 

制約が非常に厳しいため、どのソリューションでもクエリごとに最初から再計算することを回避する必要があります。 最大 100,000 回の操作では、クエリごとの O(n) 再計算でもすでに大きすぎ、クエリごとの並べ替えを伴うものは明らかに不可能です。 動的な更新とグローバル クエリの繰り返しを効率的にサポートし、操作ごとに対数的な動作を行う構造が必要です。 

2 番目のクエリには微妙な困難が現れます。答えは単一のチューブに直接結び付けられるのではなく、グローバルな再配布に依存します。 注ぐ水をシミュレートしたり、それをチューブに個別に割り当てたりしようとする単純な解釈は失敗します。最適な戦略は本質的にグローバルであり、本質的に均等化されるためです。 

単純な失敗例は、貪欲な代入がなぜ失敗するのかを示しています。 

入力:```
3 1
1 10 10
2 10
```最適なバランスを考慮せずに、最初に水を貪欲に最小のチューブに分配しようと誤って試みると、水を入れすぎてバランスが崩れたままになる可能性があります。 正しい答えは、局所的な貪欲な充填ではなく、レベルを均等化することから得られます。 

正しい値は、チューブごとの決定ではなく、グローバルしきい値によって決定されます。 

## アプローチ

 強引なアプローチでは、すべてのチューブに水がどのように分配されるかをシミュレートしようとします。 分布の候補として、各チューブに水の量を割り当て、その結果の最大値を計算します。 次に、考えられるすべてのディストリビューションを検索して、最適なものを見つけようとします。 

たとえインテリジェントな分布に限定したとしても、可能性の空間は本質的に連続的かつ指数関数的です。 これにより、直接列挙することができなくなります。 

重要な観察は、固定されたターゲットの最大高さに対して、$T$すべてのチューブを最大で 100 まで上げるにはどのくらいの水が必要かという、より単純な質問をすることができます。$T$それを超えずに？ 

チューブにすでに高さがある場合$h_i$、それから最大で届くようにするために$T$、次の場合にのみ水を追加できます。$h_i < T$、そして正確に必要になります$T - h_i$。 チューブはすでに上にあります$T$何も受け取らない。 

したがって、どのチューブも超過しないようにするために必要な総水量は、$T$は：$$\sum \max(0, T - h_i)$$ここで、2 番目のクエリが検索問題になります。$T$: 最小のものが必要です$T$必要な水は最大でも$v$。 同様に、最小のものを見つける必要があります。$T$すべてのチューブをレベルまで「満たす」ことができるように$T$利用可能な水を使用して。 

これにより、問題は単調関数逆変換に変換されます。 として$T$が増えても必要な水は増えるだけなので二分探索ができます$T$。 

残りの課題は合計を計算することです$\sum \max(0, T - h_i)$更新中すぐに。 これには、カウントとプレフィックス合計の両方を含む動的マルチセットを維持する必要があります。 圧縮された座標上のフェンウィック ツリーを使用すると、値の数をクエリできます。$\le T$とそれらの和を求めることで、対数時間での関数の評価が可能になります。

 | 二分探索 + フェンウィック ツリー | O(q log² n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在の水銀高のマルチセットを維持し、ポイントの更新と並べ替えられた値に対する範囲クエリの 2 つの操作をサポートします。 

1. 初期の高さとタイプ 1 の操作からのすべての置換値を含む、配列内に出現する可能性のあるすべての値を収集します。 それらをインデックス可能なドメインに圧縮します。 
2. この圧縮されたドメイン上にフェンウィック ツリーを構築します。 各位置には、現在その値を持つチューブの数とそれらの値の合計という 2 つの量が保存されます。 
3. 初期配列を使用して構造体を初期化します。 
4. タイプ 1 の更新操作ごとに、そのチューブの古い値をフェンウィック ツリーから削除し、新しい値を挿入します。 これにより、マルチセットの一貫性が常に保たれます。 
5. ボリュームのあるタイプ 2 の各クエリについて$v$、考えられる最終的な最大高さに対して二分探索を実行します。$T$。 検索範囲は、現在の最小高さから最大高さに加えた値までです。$v$、最終的な答えはそれを超えることはできないためです。 
6. 候補者のために$T$、すべてのチューブを水平まで上げるのに必要な水の量を計算します。$T$。 これを行うには、圧縮された値の数を見つけます。$\le T$、そしてそれらの合計はいくらか。 そのプレフィックスが以下に対応する場合、$k$合計を持つ要素$S$の場合、必要な水は次のとおりです。$$k \cdot T - S$$7. 必要な場合、水は以下の量となります。$v$、 それから$T$は達成可能であるため、より小さい値を試します。 それ以外の場合は増加します$T$。 
8. 二分探索が収束した後、実行可能な最小値を出力します。$T$。 

正確さは、最適な再配分が常に、しきい値を下回るすべてのチューブがそのしきい値まで均等化され、それを上回るチューブがそのまま残される構成を生成するという事実に依存します。 

### なぜ効果があるのか

 固定の場合$T$、最適な戦略が強制されます。チューブに割り当てられる水は、$T$最大値を小さく保つことに関しては無駄になります。 したがって、有用な割り当てはすべて、より小さな要素を生成するために使用されます。 これは、最適な構成がカットオフ レベルによって完全に記述されることを意味します。$T$そして実現可能性は、以下のものをすべて持ち上げるコストを支払えるかどうかによってのみ決まります。$T$まで$T$。 このコストは単調なので$T$、二分探索では、実行可能な最小しきい値が正しく検出されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit_cnt = [0] * (n + 1)
        self.bit_sum = [0] * (n + 1)

    def add(self, i, c, s):
        while i <= self.n:
            self.bit_cnt[i] += c
            self.bit_sum[i] += s
            i += i & -i

    def query(self, i):
        cnt = 0
        sm = 0
        while i > 0:
            cnt += self.bit_cnt[i]
            sm += self.bit_sum[i]
            i -= i & -i
        return cnt, sm

    def range_sum(self, l, r):
        c2, s2 = self.query(r)
        c1, s1 = self.query(l - 1)
        return c2 - c1, s2 - s1

def main():
    n, q = map(int, input().split())
    h = list(map(int, input().split()))
    ops = []

    vals = set(h)

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == '1':
            p = int(tmp[1]) - 1
            x = int(tmp[2])
            ops.append((1, p, x))
            vals.add(x)
        else:
            v = int(tmp[1])
            ops.append((2, v))

    vals = sorted(vals)
    comp = {v: i + 1 for i, v in enumerate(vals)}

    fw = Fenwick(len(vals))

    for i, v in enumerate(h):
        fw.add(comp[v], 1, v)

    def get_leq(T):
        # number and sum of values <= T
        # binary search on vals
        lo, hi = 0, len(vals) - 1
        pos = -1
        while lo <= hi:
            mid = (lo + hi) // 2
            if vals[mid] <= T:
                pos = mid
                lo = mid + 1
            else:
                hi = mid - 1
        if pos == -1:
            return 0, 0
        return fw.query(pos + 1)

    def can(T, v):
        cnt, sm = get_leq(T)
        return cnt * T - sm <= v

    for op in ops:
        if op[0] == 1:
            _, p, x = op
            old = h[p]
            fw.add(comp[old], -1, -old)
            h[p] = x
            fw.add(comp[x], 1, x)
        else:
            v = op[1]

            lo, hi = min(vals), max(vals) + v
            while lo < hi:
                mid = (lo + hi) // 2
                if can(mid, v):
                    hi = mid
                else:
                    lo = mid + 1
            print(f"{lo:.10f}")

if __name__ == "__main__":
    main()
```この実装は、カウントと合計の両方を追跡するフェンウィック ツリーの維持を中心としています。 実現可能性は、しきい値を下回る要素の数とそれらの合計寄与度の両方に依存するため、この二重ストレージは不可欠です。 

各クエリ内の二分検索では、整数演算のみを使用して実数値関数が評価されます。 唯一の浮動小数点ステップは出力フォーマットです。 よくある落とし穴は、水によって最終しきい値がすべての初期値よりも高くなる可能性があるため、検索範囲には最大高さを超える値が含まれている必要があることを忘れていることです。 

の`get_leq`関数は、圧縮された座標リストに対して二分探索を実行します。 座標セットのサイズは、プロセス全体にわたって導入される個別の値の数によって制限されるため、これは許容されます。

 ## 特殊なケース

 重要な例外ケースの 1 つは、すべてのチューブがすでに候補しきい値を超えている場合です。$T$。 この状況では、水は必要なく、実行可能性チェックはすぐに true を返すはずです。 プレフィックス数がゼロになり、計算されたコストがゼロになるため、アルゴリズムはこれを処理します。 

もう一つのケースは次のような場合です。$T$現在のすべての高さを下回っています。 この場合も、合計に寄与するチューブはなく、必要な水はゼロになります。 これにより、二分探索で低い値が自明に実現可能な場合に誤って拒否されることがなくなります。 

3 番目のケースは更新中に発生し、値が同じ値に置き換えられます。 論理的には何も変更されませんが、フェンウィック ツリーは削除と挿入を実行します。 両方の操作がキャンセルされるため、マルチセットの一貫性が保たれ、プレフィックス計算でドリフトは発生しません。
