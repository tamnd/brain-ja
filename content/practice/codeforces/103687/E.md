 ## 解決策
 ## 問題の理解

 直線的な一連のステージの進行をシミュレートしており、先に進む前に各ステージをクリアする必要があります。 どの段階でも、1 回の試みが成功して次の段階に進むことも、失敗して同じ段階に留まるものの健康状態が低下することもあります。 

キャラクターのヘルスプールとマナプールは限られています。 体力は、試行中に失敗した場合にのみ減少します。 体力がゼロになると、そのランは失敗したとみなされます。そのため、賢明な戦略は、そのような事態が起こらないようにする必要があります。 

ステージでの各試行には 1 単位の時間がかかります。 成功するとステージ i から i + 1 に移動しますが、失敗すると i に留まりますが、体力が 1 減ります。 ステージに挑戦することに加えて、私たちは 2 つの異なる回復メカニズムを使用して健康を回復するために時間を費やすことができます。1 つはマナを消費し、もう 1 つはダメージを受けた直後にのみ使用できるという特別な制限があります。 

一部のステージには、時間を費やすことなくマナを即座に最大値まで補充する特別な「トーテム」が含まれています。 これは、マナが世界的に単調に減少しているわけではないことを意味します。 ステージに応じて定期的にリセットできます。 

目標は、完全な体力とマナから開始して、ステージ n を超えて到達するのに必要な予想合計時間を最小限に抑えることです。 最適な戦略はステージごとに決まっているわけではなく、現在の体力、マナ、および特別なダメージ後の回復が利用可能かどうかによって異なります。 

制約は数値的なスケールではなく、構造的な意味で厳しいです。 n が最大 1000、ヘルスが最大 9、マナが最大 6 であるため、状態空間は十分に小さいため、すべての構成にわたって動的プログラミングを行うことができます。 ただし、ステージ内に確率的な遷移と周期的な動作が存在するということは、単純な最短経路ではなく、期待値の最適化問題を解決していることを意味します。 

健康状態が 1 の場合、微妙なエッジケースが発生します。 失敗すると実行が即座に終了するため、hp = 1 の状態では回復を優先するか、試みるリスクを非常に慎重に考慮する必要があります。 もう 1 つの注意が必要なケースは、ステージにトーテムがある場合です。マナは効果的に複数回フルにリセットされる可能性があるため、単調なマナ消費を前提とした戦略は間違っている可能性があります。 

## アプローチ

 強引なアプローチでは、すべての状態を確率グラフ内のノードとして扱い、収束するまで遷移を繰り返し緩和することで期待値を計算しようとします。 各状態は、ステージ、体力、マナ、およびダメージ後の回復が利用可能かどうかによって定義されます。 各状態から 3 つのアクションから選択でき、それぞれが確率的または決定的な遷移を生成します。 

これにより、最大約 1000 × 9 × 7 × 2 の状態、約 126000 の状態を含む方程式系が得られます。 すべての状態にわたる単純な反復期待伝播は、サイズ的にはまだ許容可能ですが、クエリごとに段階的に遷移をシミュレートしようとしたり、再計算を伴う再帰を使用したりすると、ステージ内の重複する状態と確率的ループの繰り返しの再計算により、すぐに実行不可能になります。 

重要な観察は、確率的遷移にもかかわらず、システムは慎重に選択された方向に非周期的であるということです。 ステージインデックスは成功すると厳密に増加し、健康状態は失敗すると厳密に減少します。 マナは変化しますが制限があり、ダメージ後の利用可能量にも制限があります。 これは、ステージの逆の順序で動的プログラミングを実行し、ステージ内で健全性を昇順に処理できることを意味します。これにより、すべての「障害遷移」が既知のより小さな健全性状態をすでにポイントしているようになります。 

チャレンジ試行の確率的遷移は、期待が現れる唯一の場所ですが、失敗すると常に健康状態が低下するため、同じ状態に対する循環依存関係は作成されません。 これにより、反復ソルバーの必要性がなくなり、直接 DP 定式化が可能になります。

 ## アルゴリズムのチュートリアル

 特定の構成からゲームを終了するまでの最小予想残り時間を表す DP 状態を定義します。 設定には、現在のステージ i、現在のヘルス hp、現在のマナ mp、および特別なダメージ後の回復が現在利用可能かどうかを示すブール フラグが含まれます。 

1. n から 1 まで逆の順序でステージを処理します。その理由は、成功した試行は常に i + 1 に進むため、将来の値はすでにわかっている必要があるためです。 
2. ステージ n + 1 の基本ケースを定義します。最後のステージを通過すると、タスクが完了するため、リソースに関係なく、予想される残り時間はゼロになります。 
3. ステージ i の状態を計算する前に、ステージのトーテム効果が存在する場合は適用します。 これは、ステージ i に入るたびに、マナがすぐに最大容量にリセットされることを意味します。 このリセットはオプションではなく、時間もかかりません。そのため、ステージ i のすべての DP 状態では、mp がすでにこのルールと一致していると想定されます。 
4. 各状態について、私たちは 3 つの可能な決定を評価します。ステージを試行する、マナを使用して健康を回復することに集中する、および可能であればダメージ後の回復を使用するです。 
5. 挑戦を検討する場合、私たちは常に 1 単位の時間を即座に支払います。 その後、確率 pi で、体力やマナを変更せずにステージ i + 1 に移行します。 確率 1 − pi では、ステージ i に留まりますが、体力が 1 つ失われ、次の決定のためにダメージ後の回復のロックが解除されます。 期待値は、これら 2 つの結果を組み合わせて形成されます。 
6. フォーカスを考慮する場合、マナが利用可能であることを確認します。 そうであれば、T1 時間を支払い、体力を 1 増やし、マナを 1 減らします。 この移行は決定的です。 
7. ダメージ後の回復を考慮すると、フラグがアクティブな場合にのみ使用できます。 許可されている場合は、T2 時間を支払い、体力を 1 増加させ、フラグを消費して別のダメージ イベントが発生するまで再利用できないようにします。 
8. 各状態の DP 値は、すべての有効なアクションの最小値です。 

### なぜ効果があるのか

 遷移ごとにステージ インデックスが増加するか、ヘルスが減少します。どちらの操作も、以前は解決できなかった状態に戻ることはありません。 唯一の確率的要素である成功確率は、再帰項が常に厳密に小さい健全性状態またはすでに計算されているより高いステージ状態を参照する線形期待方程式を生成します。 これにより、各 DP 状態が明確に定義され、反復近似を行わずに逆の順序で正確に計算できることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, H, S = map(int, input().split())
    p_raw = list(map(int, input().split()))
    p = [x / 100.0 for x in p_raw]

    tmp = list(map(int, input().split()))
    K = tmp[0]
    totem = set(tmp[1:]) if K > 0 else set()

    T1, T2 = map(int, input().split())

    NEG = 1e100

    # dp[i][hp][mp][flag], but we compress by rolling over i
    dp_next = [[[ [0.0]*2 for _ in range(S+1)] for __ in range(H+1)] for ___ in range(2)]
    dp_cur  = [[[ [0.0]*2 for _ in range(S+1)] for __ in range(H+1)] for ___ in range(2)]

    # stage n+1 is 0
    for hp in range(H+1):
        for mp in range(S+1):
            for f in range(2):
                dp_next[hp][mp][f] = 0.0

    for i in range(n, 0, -1):

        for hp in range(H+1):
            for mp in range(S+1):
                for f in range(2):
                    dp_cur[hp][mp][f] = NEG

        for hp in range(1, H+1):
            for mp in range(S+1):
                for f in range(2):

                    # totem refill
                    cur_mp = S if i in totem else mp

                    best = NEG

                    # action 1: challenge
                    if hp > 0:
                        succ = dp_next[hp][cur_mp][0]
                        fail = dp_cur[hp-1][cur_mp][1] if hp-1 > 0 else NEG
                        val = 1 + p[i-1] * succ + (1 - p[i-1]) * fail
                        best = min(best, val)

                    # action 2: focus
                    if mp > 0 and hp < H:
                        val = T1 + dp_cur[hp+1][mp-1][f]
                        best = min(best, val)

                    # action 3: hiveblood
                    if f == 1 and hp < H:
                        val = T2 + dp_cur[hp+1][mp][0]
                        best = min(best, val)

                    dp_cur[hp][mp][f] = best

        dp_next, dp_cur = dp_cur, dp_next

    ans = dp_next[H][S][0]
    print(f"{ans:.10f}")

if __name__ == "__main__":
    solve()
```このソリューションでは、ステージ全体にわたるリバース ダイナミック プログラミング スイープを使用します。 主要な実装の詳細は、固定ステージ内で同じ dp 配列を使用して状態を埋めることです。これは、失敗遷移は厳密に低いヘルスにのみ移行し、同じ反復ですでに計算されているためです。 

トーテム処理は、遷移を評価する前にステージ状態ごとにローカルに適用され、マナが常にステージの開始条件と一致していることが保証されます。 

確率の遷移は線形期待値を通じて直接処理され、成功と失敗の分岐に分割されます。 障害ブランチは hp − 1 で dp_cur を使用しますが、これは健全性を超える反復順序によりすでに満たされています。

 ## 特殊なケース

 ヘルスが 1 の場合、重大なエッジ ケースが発生します。その状況では、障害が発生するとヘルスが 0 になり、無効になります。そのため、DP はそのブランチを使用不可として効果的に処理する必要があります。 トランジションは、無効な hp − 1 状態に無限のコストを割り当てることでこれを処理し、代替手段が存在しない限り、死が差し迫っているときにアルゴリズムがギャンブルを選択しないようにします。 

もう 1 つの重要なケースは、ステージにトーテムが含まれている場合です。 マナはエントリ時に強制的にリセットされるため、DP 状態は入力マナを無視してローカルで再計算する必要があります。 これにより、ステージ移行時に枯渇したマナが誤って再利用されるのを防ぎます。 

巣血の制限も微妙です。 その利用可能性は以前にダメージを受けたかどうかに依存するため、グローバル リソースとして扱うことはできません。 このフラグにより​​、障害発生直後にのみ使用可能になることが保証され、DP は使用後に問題の制約に合わせて明示的にリセットします。
