 ## 解決策
 ## 問題の理解

 ウィリアムは、時間の経過とともに到着する友人のグループに繰り返しデザートを提供します。 重要な制約は、新しいグループが到着した後、その場にいるすべての人に整数のスライスが与えられるように、常にデザートを一定の数の等しいスライスに切り分けなければならないことです。 

このプロセスは動的です。 最初はスライスはありません。 最初のグループが到着すると、ウィリアムはホールケーキをいくつかの等しい部分に切り、それらの全員に均等に分けられるようにします。 その後、さらに多くの人々が到着すると、ウィリアムは既存のすべてのスライスを取得し、それぞれをさらに同じ数の小さな等しい部分に分割することができます。 この演算では、スライスの合計数に整数係数を乗算します。 制約は、均等な分散が可能な状態を保つために、そのような各改良の後、スライスの総数が現在の総人数で割り切れなければならないということです。 

出力は、スライスが個人にどのように分配されるかに関するものではなく、すべての段階でルールを尊重しながら、ウィリアムが常に最適なカットを選択して最終的な細分割数を最小限に抑えると仮定すると、すべてのグループが到着した後の最終スライスの可能な最小数に関するものです。 

入力は一連のグループ サイズであり、各ステップでサービスを受ける必要がある累積人数を維持します。 

制約は小さく、グループの数は最大 10、各グループ サイズは最大 10 です。これにより、ステップごとの定数時間演算を超える高度な最適化や漸近の必要性が即座に排除されます。 合理的な国家に対する強引な攻撃であっても通過するだろう。 本当の課題は、繰り返される可分性制約の不変構造を認識することです。 

素朴な解釈では、各ステップで異なる乗数を検討することで、厳しい決定をシミュレートしようとするかもしれませんが、任意の絞り込みの選択を試みると、分岐係数は急速に増大します。 もう 1 つの間違ったアプローチは、累積合計ではなく現在のグループ サイズのみを考慮することです。これは、複数のグループが累積するとすぐに中断されます。 

スライスの数を各グループ サイズで独立して割り切れるようにすれば十分であると仮定すると、微妙な失敗のケースが発生します。 たとえば、グループが 2、3、および 4 の場合、2、次に 3、次に 4 で割り算を個別に強制すると、実際の制約が累積的に 2、次に 5、次に 9 であることが無視されます。 

## アプローチ

 ブルート フォース モデルは、各グループの後のスライスの数を追跡し、各ステップで考えられるすべての整数乗数を列挙しようとします。 ステップ i で、現在 s 個のスライスと t 人がいる場合、k・s が t で割り切れるような整数 k を選択する必要があります。 このような k の値をすべて試してみると、爆発が起こります。k が大きくなる可能性があり、最大 10 ステップにわたる一連の選択によって可能性が不必要に増大するからです。 たとえ制約が小さいとしても、このアプローチでは構造がわかりにくくなります。 

重要な観察は、状態が 1 つの整数で完全に記述されるということです。スライスの数は常に現在の人数の倍数でなければならず、以前のすべての制約と一致する最小の数が必要です。 人の数が t から t + a_i に増加するたびに、現在のスライス数を新しい合計の倍数に調整する必要があります。 現在のスライス数には整数しか乗算できないため、最適な戦略は常に、新しい要件によって暗示される最小公倍数構造まで増やすことです。 

これにより、各ステップで整数倍にしかスケールアップできないという制限の下で、問題は、現在の人数の累積合計で割り切れる最小の数値を常に維持するという実行値を維持することになります。 すべてのステップで新しいプレフィックスの合計で割り算が行われるため、達成可能な最小の最終数値は、グループ サイズのすべてのプレフィックスの合計の最小公倍数になります。

これが機能するのは、更新のたびに現在のスライスの合計数に割り算の制約が適用され、数値がすべての接頭辞の合計で割り切れると、その後の乗算ステップでも有効なままになるためです。 構造は崩壊し、LCM の蓄積が繰り返されます。

 ## アルゴリズムのチュートリアル

 現在の人数と最小有効スライス数を表す現在の回答の 2 つの値を維持しながら、グループを順番に処理します。 

1. 人数ゼロ、スライス 1 つから始めます。 制約が適用される前に中立的な乗法恒等式が必要なため、スライス数は 1 から始まります。 これにより、最初のグループを一貫して処理できるようになります。 
2. グループのサイズごとに、現在の合計人数に追加します。 この累積値は、このグループが到着した後に均等にサービスを受けなければならない人の数です。 
3. 現在のスライス数を、新しい合計人数で割り切れるように更新します。 整数の乗算によってのみスケーリングできるため、新しい合計でも割り切れる現在のスライス数の最小倍数を計算します。 これは、スライス数を lcm(current_slices, current_people) に置き換えることと同じです。 
4. すべてのグループに対してこのプロセスを継続し、常に完全なプレフィックスの合計で割り切れるようにします。 以前の制約によって更新された値が構成によって分割されるため、各ステップでは以前のすべてのグループの実現可能性が維持されます。 
5. すべてのグループを処理した後、最終的なスライス数を出力します。 

重要な不変条件は、i 番目のグループを処理した後の現在のスライス数が、最初の i グループ サイズの合計で割り切れる最小の数であり、前の状態からの連続した整数乗算によって取得できることです。 これにより、有効な設定は各中間プレフィックスの合計で割り切れる必要があり、プロセスは常に最小の倍数にアップグレードされるため、これより小さい有効な設定が存在しないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from math import gcd

def lcm(a, b):
    return a // gcd(a, b) * b

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    people = 0
    slices = 1

    for x in a:
        people += x
        slices = lcm(slices, people)

    print(slices)

if __name__ == "__main__":
    solve()
```実装はアルゴリズムを直接反映しています。 の`people`変数は、各ステップでのアクティブな割り算要件である出席者のプレフィックス合計を追跡します。 の`slices`変数は、実行可能な最小のスライス数を追跡します。 

唯一の重要な操作は LCM の更新です。 使用する`a // gcd(a, b) * b`オーバーフローを回避し、計算を安定させます。 乗算の順序は、一般的な競争上の制約において Python が効率的に処理できる範囲を超える中間的な成長を避けるために慎重に選択されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from math import gcd

    def lcm(a, b):
        return a // gcd(a, b) * b

    n = int(input())
    a = list(map(int, input().split()))

    people = 0
    slices = 1

    for x in a:
        people += x
        slices = lcm(slices, people)

    return str(slices)

# provided sample
assert run("3\n2 3 10\n") == "30"

# minimum case
assert run("1\n1\n") == "1"

# all equal small groups
assert run("3\n1 1 1\n") == "6"

# increasing primes-like pattern
assert run("4\n2 3 5 7\n") == "210"

# single large group
assert run("1\n10\n") == "10"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 つの 3 つのグループ | 6 | 累積 LCM 増加率 |

 ## 特殊なケース

 エッジ ケースの 1 つは、すべてのグループ サイズが 1 の場合です。その状況では、累積合計はステップごとに 1 ずつ増加し、アルゴリズムは 1、2、3 などの最小公倍数を連続的に取得します。 入力用`1 1 1 1`、計算はスライス = 1、次に 2、次に 6、次に 12 と進みます。各ステップが強制されるのは、新しい人数が増えるたびに、スライス数を増やさないと満たせない新しい除数要件が導入されるためです。 

もう 1 つのケースは、単一のグループにすべての人が含まれる場合です。たとえば、`10`一人で。 アルゴリズムは即座に people を 10 に設定し、スライスを lcm(1, 10) に更新して 10 を生成します。中間の制約がないため、それ以上の乗算は必要なく、結果はすでに最小になっています。 

より微妙なシナリオは、グループ サイズが互いに素である場合に発生します。`2, 3, 5`。 プレフィックスの合計は 2、5、および 10 になり、アルゴリズムは 2 → 10 → 10 を正しく構築します。すべての制約が吸収されると最終値は安定し、共有分割構造を通じて後の制約が前の制約を包含できることがわかります。
