 ## 解決策
 ## 問題の理解

 私たちは、プレイヤーが固定されたデッキから繰り返しカードを引いて、池と呼ばれる成長するカードの列にカードを配置するシーケンシャル カード ゲームをシミュレートしています。 プレイヤーは一定のサイクルで行動します。プレイヤー 1、次に 2、最大 n まで、そしてそれを繰り返します。 

引いたカードはそれぞれ池の右端に追加されます。 挿入直後に、池に同じランクのカードが 2 枚あるかどうかを確認します。 このような繰り返しが存在する場合、ゲームは、そのランクの最初の出現から始まり、新しく挿入されたカードで終わる池の連続したセグメントを削除します。 そのセグメント全体は捨て札に移され、二度と使用されることはありません。 

このような削除が行われるたびに、現在のプレイヤーは削除されたセグメントに応じてポイントを獲得します。 スコアは、固定スコア テーブルに従って、セグメントの長さと、そのセグメント内に表示される個別のスーツの数によって異なります。 

このタスクは、m 枚すべてのカードを順番に処理し、すべての除去をシミュレートし、すべての得点イベントを時系列で出力し、最後にすべてのプレイヤーの合計スコアを出力することです。 

制約は設計を強制するものです。 プレイヤーの数は最大でも 24 人と少ないですが、カードの数は最大 200 万枚と非常に多くなります。 これにより、池をスキャンして一致を探したり、イベントごとにセグメント統計を最初から再計算したりするアプローチは即座に除外されます。 除去ごとに直線的でもある解決策は失敗します。 

プロセスの構造も重要です。各カードは正確に 1 回挿入され、多くても 1 回取り外されます。これは、すべての操作が一定に償却される場合、全体の線形時間シミュレーションが可能であることを示唆しています。 

挿入のたびに池を単純に再計算しようとすると、微妙な失敗のケースが発生します。 たとえば、すべてのカードが同じランクを共有している場合、挿入するたびに池の完全なリセットがトリガーされ、単純な「逆方向にスキャンして一致するものを見つける」アプローチでは二次時間に劣化してしまいます。 

もう 1 つの落とし穴は、削除されたセグメントを毎回スキャンして、そのセグメント内の個別のスーツの数を再計算することです。 セグメントは大きくなる可能性があるため、大規模な削除が頻繁に発生する敵対的なケースでは二次的な動作にもつながります。 

## アプローチ

 直接シミュレーションでは、池がリストとして維持されます。 新しいカードごとに、そのランクが以前に出現したものを見つけるために逆方向にスキャンします。 セグメントが見つかったら、そのセグメントを削除し、削除された範囲をスキャンしてスコアを計算します。 これは文字通りルールに従っているので正しいですが、遅すぎます。 最悪の場合、挿入ごとに池全体がスキャンされ、削除ごとに大きなセグメントがスキャンされるため、O(m²) になります。 

重要な観察は、池が常に時折カットを伴うスタックのように動作することです。 前の位置 p で一致が発生すると、p から先頭までのすべてが削除されます。 これは、池が常に歴史の接頭語であり、途中から削除したり、複雑な構造を維持したりする必要がないことを意味します。 

これにより、スタックベースのシミュレーションが可能になります。 現在の池を表す配列にカードを保存します。 また、各ランクについて、現在のスタック内の最新の位置も維持します。 新しいカードが到着し、そのランクが以前に登場したことがある場合、カットがどこから始まるのかがすぐにわかり、その位置より上にすべてがポップされます。 

削除されたセグメント内のスーツの多様性を効率的に計算するために、スタックに沿って各スーツのプレフィックス数を維持します。 スートが 4 つしかないため、各プレフィックス エントリには 4 つの整数が格納されます。 次に、任意のセグメント内の個別のスーツの数は、減算によって O(1) で計算できます。 

各カードは 1 回プッシュされ、最大 1 回ポップされるため、すべての操作は O(1) で償却されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(㎡) | O(m) | 遅すぎる |
 | スタック + ハッシュ + プレフィックス数 | O(m) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

シミュレーション中に、現在の池を表すカードのスタック、ランクからスタック内の最新の位置へのマッピング、スタックに沿ったスートのプレフィックス数という 3 つの主要な構造を維持します。 

1. すべてのプレイヤーの空のスタックとスコア配列を初期化します。 また、ランクから位置へのマップを「未表示」の値で初期化します。 
2. カードを入力順に 1 枚ずつ処理します。 各カードについて、インデックス モジュロ n を使用して現在のプレイヤーを決定します。 
3. カードをスタックに追加します。 追加中に、各位置にその時点までの D、C、H、および P の累積カウントが格納されるようにプレフィックス スーツのカウントを計算します。 
4. このカードのランクが現在のスタックに以前に登場したかどうかを確認します。 そうでない場合は、その位置を記録して続行します。 
5. 位置 p に出現すると「釣り」イベントが発生します。 p から現在のスタックの先頭までのセグメントが削除されます。 
6. 現在のスタック サイズと p の差としてセグメント長を計算します。 
7. プレフィックス合計を使用してセグメント内の個別のスーツの数を計算します。先頭のプレフィックス数から p-1 のプレフィックス数を減算し、ゼロ以外のスーツの合計の数を数えます。 
8. 提供されたスコア表を使用して、この (長さ、スーツ数) ペアのスコアを計算し、現在のプレーヤーに追加します。 
9. p-1 までのプレフィックスのみが残るまでスタックから要素をポップします。 ポッピング中、除外されたカードのランク位置を無効にします。 
10. 次のカードの処理を続けます。 

正確さは、ランクが繰り返されるたびに、ゲームが常に現在の池でそのランクが前回出現した時点から始まるサフィックスを正確に削除するという事実に依存します。 これにより、池が過去の一致しないカードの有効なスタックのままであることが保証されます。 各カードは将来一致するまでスタックに残るか、または 1 回だけ削除されるため、プレフィックス構造は全体を通して一貫したままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# suit mapping
suit_id = {'D': 0, 'C': 1, 'H': 2, 'P': 3}

# rank mapping (2-9, T, J, Q, K, A)
rank_id = {str(i): i - 2 for i in range(2, 10)}
rank_id.update({'T': 8, 'J': 9, 'Q': 10, 'K': 11, 'A': 12})

# NOTE: scoring table must be filled according to statement
# score[l][c] where l <= 14, c <= 4
score = [[0] * 5 for _ in range(15)]
# (assume filled externally from problem table)

def solve():
    n, m = map(int, input().split())
    cards = input().split()

    stack_rank = []
    stack_suit = []
    # prefix counts: dp[i][suit]
    pref = [[0, 0, 0, 0]]

    # last position of rank in current stack
    last_pos = [-1] * 13

    # player scores
    ans = [0] * n

    top = 0

    for i in range(m):
        card = cards[i]
        player = i % n

        s = suit_id[card[0]]
        r = rank_id[card[1]]

        stack_rank.append(r)
        stack_suit.append(s)

        pref.append(pref[-1][:])
        pref[-1][s] += 1

        pos = top  # new position index

        if last_pos[r] == -1:
            last_pos[r] = pos
            top += 1
            continue

        p = last_pos[r]

        l = top - p + 1

        # compute suit count in segment [p, top]
        cnt = [0, 0, 0, 0]
        for k in range(4):
            cnt[k] = pref[top + 1][k] - pref[p][k]

        c = sum(1 for x in cnt if x > 0)

        ans[player] += score[l][c]

        # remove segment
        new_top = p
        while top > new_top:
            last_pos[stack_rank[top]] = -1
            top -= 1

        last_pos[r] = new_top
        top += 1  # current card becomes only element at that position

    print(*ans)

if __name__ == "__main__":
    solve()
```スタックには現在の池の状態が保存されます。`top`そのサイズを追跡します。 プレフィックス配列により、任意のセグメント内で定数時間のスーツのカウントが可能になります。 イベントごとの唯一の直線的な作業は、削除されたカードをポップすることであり、各カードは全体で最大 1 回ポップされます。 

実装の微妙な点は、`last_pos`。 これは常に現在のアクティブなスタック内の位置を参照するため、カードが削除されるたびに無効化する必要があります。 

## 実用的な例

 同じランクがすぐに再び現れる小さな概念的なトレースを考えてみましょう。 

初期状態は空のスタックであり、最後の出現は記録されません。 

| ステップ | カード | スタック | 最後の位置 | アクション |
 | --- | --- | --- | --- | --- |
 | 1 | D3 | [D3] | 3→0 | プッシュ |
 | 2 | H3 | [ ] | 3 件を見た | 一致トリガーの削除 |

 H3 が到着すると、ランク 3 は以前は位置 0 にあったため、セグメント [0..1] が削除されます。 削除されたセグメントには D3 と H3 の両方が含まれるため、長さは 2、スーツ数は 2 になります。 

これは、カットが隣接する要素だけでなく、常に前の出現箇所から現在の端までに及ぶことを示しています。 隣接するカードのみをチェックするアプローチでは、この動作が見逃されます。 

次に、より長いセグメント内に複数の異なるスーツがあるケースを考えてみましょう。 

| ステップ | カード | スタック (前) | アクション | セグメント |
 | --- | --- | --- | --- | --- |
 | 1 | D2 | [D2] | プッシュ | - |
 | 2 | C3 | [D2、C3] | プッシュ | - |
 | 3 | H2 | [D2,C3,H2] | マッチ 2 | [D2,C3,H2] |

 ステップ 3 では、ランク 2 が繰り返されます。 セグメントにはスーツ D、C、H が含まれているため、c = 3 になります。プレフィックス合計構造により、この計算はセグメントの長さに依存しません。

 ## 特殊なケース

 重要なエッジケースは、すべての入ってくるカードが除去を誘発する場合です。 このシナリオでは、スタックが小さいサイズを超えることはありません。 各カードの挿入と取り外しが 1 回だけ行われ、カードが再度アクセスされることはないため、アルゴリズムは線形のままです。 

もう 1 つの特殊なケースは、除去がスタックの大部分に重なる場合です。 その場合でも、プレフィックス配列は再計算されず、クエリのみが行われるため、有効なままになります。 正確かどうかは、プレフィックス値が一度書き込まれた後は不変であるため、その後のポップに関係なく、履歴セグメント クエリの一貫性が維持されるという事実に依存します。 

最後のエッジケースは、複数のプレイヤーが得点イベントをトリガーする場合です。 スコアは状態に依存しないため、プレーヤー配列への蓄積は後の除去の影響を受けず、正しい最終合計が保証されます。
