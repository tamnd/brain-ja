 ## 解決策
 ## 問題の理解

 私たちは、クリティカル ヒットが発生する確率が固定されておらず、前回のクリティカル ヒットからの経過時間に依存するゲーム メカニクスを検討しています。 クリティカルが発生しない状態が長くなるほど確率は高くなり、上限は 1 です。 

より正確には、この確率がどれだけ速く成長するかを制御するパラメーター c があります。 どの攻撃でも、i を最後のクリティカル ヒット以降、またはクリティカルがまだ発生していない場合はゲーム開始以降の攻撃の数として定義します。 この攻撃がクリティカルヒットとなる確率は min(1, i · c) です。 

無限の攻撃シーケンスにわたって、このシステムは長期的な平均クリティカル率を引き起こします。 つまり、最初の n 回の攻撃で期待されるクリティカル ヒット数を n で割ると、n が大きくなるにつれてこの比率はある値 p に収束します。 p が与えられているので、対応する c を回復する必要があります。 

重要な問題は、プロセスがメモリレスではないことです。 各攻撃は、以前の「連続失敗」の長さに依存するため、システムは単純なベルヌーイ数列ではなく、更新プロセスとなります。 

入力サイズは小さく、最大 100 個のテスト ケースがあるため、各テスト ケースでは対数または小規模な定因数反復法さえも実行できます。 重要なのは、p と c の間の数学的関係の正確さであり、大規模なデータ構造の最適化ではありません。 

p が 1 に非常に近い場合、微妙なエッジ ケースが発生します。その場合、c も 1 に近い必要があり、逆関係を解く際には数値安定性が重要になります。 もう 1 つの特殊なケースは、p が非常に小さい場合です。 この場合、c は小さくなり、システムはほとんどの場合 i = 1 または 2 でリセットされ、期待値は確率関数の最初の線形セグメントによって支配されます。 

単純なシミュレーション手法では、長いシーケンスにわたってマルコフ過程をシミュレートしようとします。 各ステップは O(1) ですが、定常レートへの収束は非常に遅く、分散に依存するため、1e-8 のような厳しい誤差要件では非実用的であり、数値的に不安定になります。 

## アプローチ

 中心的な観察は、プロセスが連続するクリティカル ヒット間の独立した「サイクル」に分解できるということです。 各サイクルはクリティカルの直後に開始され、次のクリティカルで終了します。 サイクルの長さによって長期的なクリティカル率が決まります。予想されるサイクルの長さが E[L] の場合、攻撃ごとに予想されるクリティカル数は単純に 1 / E[L] になります。 

サイクル内では、成功確率は直線的に増加します。クリティカル後の i 回目の試行では、成功確率は min(1, i c) です。 これにより、 i c が 1 に達するかどうかに応じて 2 つのレジームが作成されます。 k を k c ≥ 1 となる最小の整数とします。その場合、i < k の場合、確率は i c となり、i = k でサイクルが終了することが保証されます。 

ブルートフォース計算では、考えられるすべての失敗と成功のパスを合計することで、予想されるサイクル長が明示的に計算されます。 これは、各状態が成功または失敗によって分岐するため、k ですぐに指数関数的になりますが、k は 1/c まで大きくなる可能性があるため、c が小さい場合、これは実行不可能になります。 

重要な洞察は、ランダム性を直接シミュレートする必要がないということです。 故障確率が位置ごとに決定的であるプロセスの停止時間の予想だけが必要です。 これにより、生存確率を合計することにより、c の関数として E[L] の閉じた形式の式を書くことができます。 

E[L](c) が得られると、ターゲット条件は p = 1 / E[L](c) になります。 E[L](c) は c において単調であるため、二分探索を使用して c を解くことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(大きい、非収束) | お(1) | 遅すぎる |
 | 期待値 + 二分探索 | O(log(1/ε) · k) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

固定 c の予想サイクル長を計算し、二分探索を使用して関係を反転します。 

1. c の候補値を決定します。 k = ceil(1 / c) を決定します。 これは、確率が 1 に達する最初のインデックスです。これにより、プロセスが線形成長フェーズと決定論的終了フェーズに分割されます。 
2. 生存確率 S_i を計算します。これは、試行 i までにクリティカルが発生しなかった確率です。 最初は S_0 = 1 です。i ≥ 1 の場合、S_i = S_{i-1} · (1 − min(1, i c))。 これは、サイクルがステップ i を超えて継続する可能性を追跡します。 
3. 予想サイクル長は、各試行前の生存確率の全ステップの合計です。 具体的には、プロセスがまだ終了していない場合、各ステップは 1 単位時間に寄与するため、すべての i にわたって E[L] = Σ S_{i-1} となります。 
4. i を 1 から k まで繰り返します。 i < k の場合、(1 − i c) を使用して生存期間を乗算的に更新します。 i = k でプロセスが終了するため、停止します。 
5. p_hat = 1 / E[L] を計算します。 これは、この c の値に対して長期的に予想されるクリティカル率です。 
6. 区間 (0, 1] 内の c に対して二分探索を使用します。中間点ごとに、p_hat を計算し、ターゲット p と比較します。p_hat が大きすぎる場合は、c が大きすぎるため、減らす必要があります。そうでない場合は、c を増やします。
 7. 間隔が固定精度しきい値 (通常は 1e-12) より小さくなるまで続行し、最終的な絶対誤差が 1e-8 以内になるようにします。 

### なぜ効果があるのか

 このプロセスは更新プロセスであり、各サイクルは独立しており、同様に分散されます。 このようなシステムにおける長期にわたるイベントの頻度は、予想される到着間隔の逆数になります。 各サイクルの長さは履歴には依存せず、c のみに依存するため、E[L](c) はシステムを完全に特徴付けます。 c を増加すると、より早期に終了する確率が厳密に増加し、予想されるサイクル長が減少し、p が増加するため、単調性が維持されます。 これにより、二分探索が一意の解に収束することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def expected_cycle(c):
    s = 1.0
    total = 0.0
    i = 1
    while True:
        prob = i * c
        if prob >= 1.0:
            total += s
            break
        total += s
        s *= (1.0 - prob)
        i += 1
    return total

def solve_case(p):
    lo, hi = 0.0, 1.0
    for _ in range(80):
        mid = (lo + hi) / 2.0
        e = expected_cycle(mid)
        p_hat = 1.0 / e
        if p_hat > p:
            hi = mid
        else:
            lo = mid
    return (lo + hi) / 2.0

t = int(input())
for _ in range(t):
    p = float(input())
    ans = solve_case(p)
    print(f"{ans:.15f}")
```機能`expected_cycle`リニューアルのアイデアをそのまま実現。 サイクル内の連続した試行を順を追って実行し、生存確率と蓄積された期待値の両方を追跡します。 確率が 1 に達した瞬間にサイクルは終了する必要があるため、累積を停止します。 

c を p にマッピングする関数は単調増加であるため、二分探索は c に対して行われます。 ループ数 80 は、倍精度で 1e-8 をはるかに下回る誤差を達成するには十分です。 

微妙な点は、生存確率を通じて期待される長さを蓄積することです。`s`。 これにより、すべての障害シーケンスの列挙が回避され、指数関数的な分岐が単一の線形パスに圧縮されます。 

## 実用的な例

 c が中程度、たとえば c = 0.5 である小さな概念的な例を考えてみましょう。 この場合、確率は 0.5、1.0 になります。 サイクルは、障害発生後、決定的にステップ 1 またはステップ 2 で終了します。 

| 私 | 問題 | 私の前に生き残る | 貢献 |
 | --- | --- | --- | --- |
 | 1 | 0.5 | 1.0 | 1.0 |
 | 2 | 1.0 | 0.5 | 0.5 |

 予想されるサイクル長は 1.5 であるため、p = 2/3 となります。 

ここで、より小さい c = 0.25 を考えてみましょう。 

| 私 | 問題 | 私の前に生き残る | 貢献 |

 | 4 | 1.0 | 0.09375 | 0.09375 |

 予想されるサイクル長は寄与の合計で約 2.21875、p ≈ 0.45 となります。 

これらのトレースは、生存率がどのように乗算的に減衰するのか、そしてなぜ線形列挙で十分なのかを示しています。

import sys, io

def run(inp: str) -> str:

        total = 0.0
        i = 1
        while True:
            prob = i * c
            if prob >= 1.0:
                total += s
                break

            s *= (1.0 - prob)
            i += 1
        return total

    def solve_case(p):

            p_hat = 1.0 / e
            if p_hat > p:
                hi = mid
            else:
                lo = mid

    t = int(input())
    out = []
    for _ in range(t):

 ## 特殊なケース

 p が正確に 1 の場合、唯一の一貫した構成は c = 1 です。この場合、最初の攻撃以降のすべての攻撃は即座にクリティカルになることが保証され、サイクル長は正確に 1 です。 

p が極端に小さい場合、c も小さくなり、生存積は非常にゆっくりと減衰します。 予想されるサイクル内のループは多くの反復を処理する必要がありますが、i c がしきい値を超えると確率が最終的に 1 に達するため、それでもすぐに終了します。 

c が、非常に大きな i で i c が 1 になるしきい値に近い場合、生存確率の繰り返し乗算がアンダーフローする可能性があるため、浮動小数点精度が重要になります。 このアルゴリズムは、倍精度を使用し、決定的なカットオフに達したときに早期に停止することでこれを回避します。
