 ## 解決策
 ## 問題の理解

 プログラミングの問題のプールが与えられ、各問題には 3 人の生徒のうち誰が解決できるかが正確にラベル付けされています。 すべての問題は、生徒 1、2、および 3 の間で設定された解決可能性に応じて、7 つのカテゴリのいずれかに分類されます。問題によっては、1 人の生徒だけが解決できるもの、特定の 2 人の生徒だけが解決できるもの、および 3 人全員が解決できるものもあります。 

私たちの仕事は、問題が解決できるかどうかを判断することではなく、各問題をそれを解決できる生徒の 1 人に割り当てることです。 割り当て後、各問題は、割り当てられた 1 人の生徒によって解決されたものとしてカウントされます。 目標は、割り当てられた問題が最も少ない学生ができるだけ多くなるように、課題を配布することです。 つまり、すべての課題が決まった後、3 人の生徒の最小作業量を最大化したいと考えています。 

この制約では、カテゴリごとに最大 100,000 のテスト ケースと最大 7 × 10^8 の値が許可されるため、どのソリューションもテスト ケースごとに一定時間で実行する必要があります。 問題のシミュレーションや割り当ての検索を伴うものは、問題の総数が多すぎて明示的に列挙できないため、直ちに実行不可能になります。 

構造を持たずに貪欲な割り当てを試みると、微妙な失敗モードが発生します。 たとえば、常に現在最も弱い生徒に共通の問題を与えると、後でもっと良い再配分が可能だったときに行き詰まってしまう可能性があります。 

F1 = F4 = F7 = 1、その他がゼロである単純な状況を考えてみましょう。 単純な貪欲なアプローチでは、すべての生徒にとって正解が明らかに 1 であるにもかかわらず、最初に F7 を恣意的に割り当て、その後の割り当てを最適にバランスさせることができなくなる可能性があります。 これは、共有カテゴリに関するローカルな決定がグローバルな最適性を損なう可能性があることを示しています。 

主な問題点は、カテゴリー F3、F5、F6、および F7 が生徒間のカップリングを生み出すことです。 これらの共有の問題は、慎重に分割する必要がある柔軟なリソースとして機能します。 

## アプローチ

 強引な解釈では、各問題を個別に扱い、有効な生徒に対して各問題の可能なすべての割り当てを試みることになります。 各 F7 問題には 3 つの選択肢があり、F3、F5、F6 にはそれぞれ 2 つの選択肢があり、その他の問題には固定の割り当てがあります。 これにより、構成の数はおよそ 3^{F7} × 2^{F3+F5+F6} と指数関数的に増加し、これは入力が小さい場合でも天文学的に大きくなります。 

これは有効な分布をすべて調査するため概念的には機能しますが、組み合わせ爆発によりすぐに失敗します。 問題の構造は対称性を示唆しています。問題となるのは生徒ごとの合計だけであり、個々の問題の正体は問題ではありません。 

重要な観察は、生徒ごとの最終的な数のみを考慮しており、すべてのカテゴリが線形的で構造化された方法で貢献しているということです。 独身学生カテゴリー F1、F2、F4 は定額拠出金です。 混合カテゴリーは再配布できますが、制限された自由度の範囲内でのみ再配布できます。 

割り当てという観点から考えるのではなく、各カテゴリがどれだけの柔軟性を提供するのかという観点から考えるようになりました。 各 F7 の問題は 3 人全員の学生に 1 単位の柔軟性をもたらし、各 F3 は学生 1 と 2 の間の柔軟性に貢献します。 この問題は、制約のあるバランスの問題になります。各学生が少なくとも x 個の課題を受け取るように、値 x を最大化したいと考えています。 

x を回答候補として扱い、実現可能性を確認できます。 固定 x の場合、各生徒が少なくとも x に到達するように共有問題を配布できるかどうかを確認します。 これにより、問題は、共有プールを使用して余剰容量のバランスをとれるかどうかを確認するだけになります。

実現可能性を考慮して、最初にすべての強制寄与を割り当てます。 次に、生徒ごとの赤字を計算します。 次に、共有カテゴリが構造化された方法で貪欲に使用されます。最初に 2 人の生徒の共有プールを使用して不足分をカバーし、最後に完全に柔軟なプール F7 を使用して残りの不均衡をカバーします。 これが機能するのは、F7 が任意に指示できる唯一のリソースであるためです。 

二分探索の代わりに閉じた形式を導出することで、さらに単純化できます。 制限要因は、合計の制約を尊重しながら、各生徒が共有カテゴリからどれだけブーストできるかです。

 ## アルゴリズムのチュートリアル

 まず、カテゴリを 3 つの合計に対する寄与として再解釈します。 生徒 1 は最初に、F1 からのすべての問題に加えて、F3、F5、および F7 から割り当てることを決定した問題を受け取ります。 他の人にとっても同様です。 

1. まず強制問題を割り当てます。 生徒 1 は F1、生徒 2 は F2、生徒 3 は F4 を取得します。 この部分は変更できないため、ベースラインとなります。 
2. F3 を生徒 1 と 2 の間でのみ分割できるプールとして扱います。同様に、F5 は 1 と 3 の間で分割され、F6 は 2 と 3 の間で分割されます。これらはペアごとのバランシング ツールとして機能します。 
3. 重要な制限は、これらのプールのそれぞれが特定の 2 人の学生のみを支援できるため、世界的な不均衡を完全には解決できないことです。 3 つすべてを同時に調整するには F7 のみを使用できます。 
4. 各生徒に少なくとも x 点を達成させたいとします。 単一の生徒の寄付をすべて使用した後、各生徒がベースラインからどれだけ不足しているかを計算します。 
5. 次に、可能な限り不足を減らすために、ペアごとのプールを貪欲に割り当てます。 たとえば、F3 は、生徒 1 と生徒 2 の欠点を最も効率的な方法で同時に減らすために使用されます。 
6. ペアごとのプールを使い果たした後、F7 を使用して残りの不足分を補う必要があります。 各 F7 問題はどの生徒にも 1 単位を提供するため、最大赤字ギャップを自由に減らすことができます。 
7. 答えは、必要な報酬の合計が利用可能な柔軟なリソースを超えない最大の x です。 

### なぜ効果があるのか

 この構造は、グローバルに柔軟なリソースを 1 つだけ備えたフローのようなバランシング システムに縮小されます。 ペアワイズ リソースはローカルで不均衡を軽減することしかできず、エンドポイントを超えてグローバルな再配分を生み出すことはできません。 したがって、実現可能な解決策は、完全に柔軟なプール F7 が、ペアごとのプールを最適に使用した後の残りの不均衡をカバーできるかどうかによって完全に決まります。 他のすべての割り当ては線形で独立しているため、実現可能条件は正確になり、割り当ての検索は必要ありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []
    
    for _ in range(T):
        S = int(input())
        f1, f2, f3, f4, f5, f6, f7 = map(int, input().split())
        
        # baseline contributions
        a1 = f1
        a2 = f2
        a3 = f4
        
        # pair pools
        p12 = f3
        p13 = f5
        p23 = f6
        
        # total sum constraint: a1+a2+a3 + p12+p13+p23+f7 = S
        
        # We binary search x
        lo, hi = 0, S
        
        def can(x):
            need1 = max(0, x - a1)
            need2 = max(0, x - a2)
            need3 = max(0, x - a3)
            
            # use pair pools greedily
            use12 = min(p12, need1 + need2)
            # split as much as possible
            take1 = min(need1, use12)
            need1 -= take1
            need2 -= (use12 - take1)
            
            use13 = min(p13, need1 + need3)
            take1 = min(need1, use13)
            need1 -= take1
            need3 -= (use13 - take1)
            
            use23 = min(p23, need2 + need3)
            take2 = min(need2, use23)
            need2 -= take2
            need3 -= (use23 - take2)
            
            total_need = need1 + need2 + need3
            return total_need <= f7
        
        ans = 0
        while lo <= hi:
            mid = (lo + hi) // 2
            if can(mid):
                ans = mid
                lo = mid + 1
            else:
                hi = mid - 1
        
        out.append(str(ans))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このコードは、候補最小値 x の実現可能性チェックを実装します。 強制カテゴリを反映して、ベースライン数が最初に分離されます。 機能`can(x)`各学生が必要とする追加課題の数を計算します。 

重要な実装の詳細は、ペアごとのプールを貪欲に消費することです。 各プールは、最初に 2 つのエンドポイントで可能な限り多くの満たされていないニーズを満たす方法で適用されます。 各プールは独立しており、一度使用されるとその容量がなくなるため、この順序は重要です。 

二分探索は、実現可能性チェックが x において単調であるとみなされる場合でも、正確さを保証します。 x を増やすと赤字が増えるだけなので、ある値が実行不可能になると、それより大きな値もすべて実行不可能になります。

 ## 特殊なケース

 重要なエッジ ケースは、すべての問題が単一の生徒のカテゴリ F1、F2、および F4 に属する場合です。 この場合、共有された柔軟性は存在しないため、答えは単にこれら 3 つのカウントの最小値になります。 すべてのペアワイズ プールと F7 プールがゼロであるため、アルゴリズムはこれを処理します。そのため、x の実現可能性はベースライン値のみにすぐに依存します。 

もう 1 つの特殊なケースは、すべての問題が F7 にある場合です。 ここで、すべての問題は完全に柔軟であるため、最適解は S // 3 です。アルゴリズムは、ベースライン ゼロ初期化後のすべての不足をカバーする F7 を通じてこれを効果的にモデル化します。 

3 番目のエッジ ケースは、ペアごとのプールが大きいにもかかわらず F7 がゼロである場合です。 これは、ペアごとのバランスをとることで 3 方向の不均衡を修正することができず、ペアごとの転送を使い果たした後でも 1 人の生徒が満足度を満たしていない場合は必ず実現可能性チェックが正しく失敗することを明らかにします。
