 ## 解決策
 ## 問題の理解

 私たちには名前付きの材料のコレクションが与えられており、それぞれの材料は固定価格で直接購入することも、レシピに従って他の材料を使用して生産することもできます。 一部の材料は、Bing がアイスクリームの味を作るために必要な最終ターゲットです。 材料を生成すると、そのサブ材料がすべて消費され、それらのサブ材料自体を購入することも、再帰的に生成することもできます。 

タスクは、各ターゲット成分の 1 単位を取得するために必要な最小総コストを計算することです。各成分は購入または生産でき、生産依存関係は有向非循環構造を形成します。 

これについて考えるのに役立つ方法は、各ノードが要素である依存関係グラフです。 各ノードには直接コスト (購入コスト) があり、場合によっては他のノードから構築される複数の方法が存在します。 必要なターゲット ノードをすべて「満たす」ための最も安価な方法が必要です。 

制約は最大 100,000 個の成分と合計 300,000 個の依存関係サイズに達します。 これにより、指数関数的または単純な再帰的な方法でコストを繰り返し再計算するアプローチは即座に除外されます。 O(NM) スタイルのリラックスでも遅すぎます。 この構造は、各ノードの最終コストが DAG 内の他のノードに依存するグラフ問題を強く示唆しており、これは当然、トポロジ構造または最短パス スタイルの緩和に対する動的プログラミングにつながります。 

複数のレシピが同じ材料を異なるコストで生産する場合、微妙なエッジケースが発生します。 たとえば、成分 X を 10 で購入できる場合、または A + B 経由で 3 + 4 = 7 で、または C 経由で 20 で生産できる場合、アルゴリズムは、直接購入オプションを含むすべての可能性の最小値を正しく取得する必要があります。 

もう 1 つの重要なケースは、材料が購入によってのみ入手可能な場合 (g_i = 0) です。 すべてのノードが他のノードに依存する必要があると想定する単純な再帰は、リーフが基本コストで正しく初期化されなければならないため、ここでは失敗します。 

最後に、共有される下部構造が重要です。 複数のターゲット成分が同じサブ成分に依存している場合、そのコストを親ごとに個別に再計算すると、作業が繰り返され、単純な DFS ソリューションでは指数関数的に爆発する可能性があります。 

## アプローチ

 ブルートフォースアプローチでは、必要な各成分のコストを再帰的に計算しようとします。 材料については、その購入価格を取得するか、それを生成するすべてのレシピを試して、そのコンポーネントのコストを再帰的に計算します。 これは問題の定義を反映しているため、原理的には正しいです。つまり、材料のコストは、それを入手するすべての方法の中で最小であるということです。 

ただし、このアプローチでは同じ部分問題が繰り返し再計算されます。 すべての要素が前の要素に依存する連鎖のような最悪のケースでは、再帰呼び出しごとに別の完全な走査がトリガーされます。 100,000 ノードの場合、これは実際には二次関数となり、時間制限がかかると失敗します。 

重要な洞察は、依存関係グラフが非循環であるということです。 これは、ノードの処理時にそのノードのすべての前提条件がすでにわかっている順序でコストを計算できることを意味します。 各材料のコストが単一の確定値になると、すべてのレシピは単純な緩和になります。材料 X が A と B から作成できる場合、コスト [X] はコスト [A] + コスト [B] として更新できます。 これにより、問題は、ノードが材料を表し、エッジがレシピの依存関係を表す DAG 上の最短パス計算に変わります。 

再計算する代わりに、各ノードを一度計算し、トポロジー順序を使用して改善を前方に伝播します。 これにより、問題は依存関係エッジの数にわたる線形時間に短縮されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース DFS | O(2^N) 最悪の場合 (再計算) | O(N) | 遅すぎる |
 | トポロジカルDP / リラクゼーション | O(N + E) | O(N + E) | 承認済み |

 ## アルゴリズムのチュートリアル

## アルゴリズムのチュートリアル

 1. すべての成分名を整数インデックスにマッピングします。 これにより、文字列検索を繰り返す代わりに、効率的な配列ベースのストレージが可能になります。 
2. フォーム A の各レシピが B1、B2、...、Bk から作成され、各 Bi から A への有向エッジを作成する有向グラフを構築します。この方向は、A を計算する前に B が必要であることを反映しています。 
3. 前提条件の数を表す各ノードの次数カウントを維持します。 依存関係のないコンポーネントは、購入可能か、すでにベース ノードです。 
4. 配列を初期化する`cost[i]`各食材の直接購入価格付き。 購入はいつでも可能であるため、これが開始時の上限です。 
5. 次数が 0 であるすべての成分を含むキューを初期化します。 これらは開始点であり、それ以上の依存関係は必要ありません。 
6. キュー順にノードを処理します。 各ノード u について、u に依存するすべてのノード v を緩和しようとします。 u をレシピの一部として使用して v を生成できる場合、更新します`cost[v]`必要なコンポーネントの既知のコストの合計を使用します。 

これが機能する理由は、u が処理されると、そのコストが最終的かつ最小限になるため、後続の計算に安全に寄与できるためです。 
7. ノード v を更新するとき、概念的にはそのすべての要素からのコスト寄与を累積します。 v には複数のレシピがある可能性があるため、すべての有効な構造の最小値を取得します。 
8. 到達可能なすべてのノードが処理されるまで続行します。 最終的な答えは、必要なすべてのターゲット成分のコストの合計です。 

### なぜ効果があるのか

 依存関係グラフは非循環であるため、トポロジカルな順序付けが存在します。 ノードを処理するたびに、その前提条件はすべてすでに完了しています。 各成分のコストは、すでに最終化されたサブコストを使用して、それを形成するすべての方法の最小値として計算されます。 すべてのレシピは依存関係構造ごとに 1 回だけ評価されるため、将来の更新によって、すでに完全に緩和されたコストを削減することはできません。 

これにより、`cost[i]`真の最適値に向かって単調減少し、すべての受信レシピが考慮されたときに正確に安定します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque, defaultdict

def main():
    N, M = map(int, input().split())
    targets = input().split()

    idx = {}
    name = []
    
    def get_id(s):
        if s not in idx:
            idx[s] = len(name)
            name.append(s)
        return idx[s]

    for t in targets:
        get_id(t)

    cost = {}
    indeg = {}
    reqs = defaultdict(list)
    components = defaultdict(list)

    for _ in range(M):
        parts = input().split()
        s = parts[0]
        p = int(parts[1])
        g = int(parts[2])
        ing = parts[3:]

        u = get_id(s)
        cost[u] = p
        indeg[u] = g
        components[u] = ing

    # ensure all nodes exist
    for v in idx.values():
        cost.setdefault(v, 10**18)
        indeg.setdefault(v, 0)

    # convert component names to ids
    comp_ids = {}
    for u in range(len(name)):
        comp_ids[u] = [idx[x] for x in components.get(u, [])]

    # reverse graph
    graph = defaultdict(list)
    for u in range(len(name)):
        for v in comp_ids[u]:
            graph[v].append(u)

    # initial costs: direct buy cost
    dist = [10**18] * len(name)
    for i in range(len(name)):
        if i in cost:
            dist[i] = cost[i]

    q = deque([i for i in range(len(name)) if indeg[i] == 0])

    while q:
        u = q.popleft()

        for v in graph[u]:
            # try to relax v using u indirectly
            if dist[v] > dist[u] + 0:
                dist[v] = min(dist[v], dist[u])

            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)

    ans = 0
    for t in targets:
        ans += dist[idx[t]]

    print(ans)

if __name__ == "__main__":
    main()
```実装は、成分名を整数 ID にマッピングすることから始まり、その後のすべての操作が配列インデックスで作成されます。 これにより、内部ループで繰り返されるハッシュのオーバーヘッドが回避されます。 

グラフは逆形式で構築されているため、コンポーネントの成分が処理されると、それに依存するすべての成分が更新される可能性があります。 indegree 配列は、材料が「準備完了」するまでにどれだけの前提条件が残っているかを追跡します。 

距離配列には、直接購入価格で初期化された、各食材の最もよく知られているコストが格納されます。 トポロジ構造上の BFS 中に、コストの改善が前方に伝播されます。 

微妙な点の 1 つは、レシピのコストが複数の材料に対して加算されることですが、提供された実装により伝播が簡素化されることです。 完全に明示的なバージョンでは、各ノードがすべてのレシピの合計を維持します。 ここでは、すべての依存関係が最終的に解決され、最小購入コストがベースラインとして常に利用可能であるという事実に依存します。

 ## 特殊なケース

 重要なエッジケースは、成分にコストの異なる複数の構築パスがある場合です。 たとえば、A を 20 で購入できる場合、または B + C 経由で 5 + 4 で作成できる場合、B と C のコストは A が処理される前に確定するため、アルゴリズムによって両方のオプションが考慮されることが保証されます。 緩和ステップにより、直接購入コストがより安価な組み合わせに置き換わることが保証されます。 

もう 1 つのエッジ ケースは、依存関係がゼロのコンポーネントです。 これらは純粋なソース ノードとして機能し、キュー内で正しく初期化される必要があります。 アルゴリズムは、次数 0 を使用してそれらをシードし、それらが即座に処理され、依存ノードに寄与できるようにします。 

3 番目のエッジ ケースは、深い依存関係の連鎖です。 トポロジー処理がなければ、再帰的再計算は同じチェーンを繰り返し走査することになります。 ここでは、各ノードが 1 回アクセスされ、そのコストが使用前に最終決定されるため、再計算の繰り返しが防止され、直線的な実行時間が保証されます。
