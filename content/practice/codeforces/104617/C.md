 ## 解決策
 ## 問題の理解

 アイスクリームのフレーバー、霧雨、トッピングという 3 つの独立した文字列コレクションが与えられています。 デザートは、アイスクリーム 2 スクープ、小雨 1 つ、トッピング 1 つで構成されます。 2 つのスクープはフレーバー リストから選択され、同じフレーバーまたは 2 つの異なるフレーバーにすることができます。 2 つのスクープの順序は重要ではないため、A から B を選択することは、B から A を選択することと同じです。 

課題は、これらのルールに従って、いくつの異なるデザートを形成できるかを数えることです。 選択したコンポーネントのいずれかが異なる場合、つまりスクープ ペア、霧雨、またはトッピングのいずれかが異なる場合、2 つのデザートは異なるものとみなされます。 

制約に関する主な観察点は、各リストに含まれる項目が最大 100 個であることです。 これにより、繰り返しのある順序付けされていないペアの数が最大 5050 であるため、フレーバーのすべてのペアを明示的に考慮することが可能になります。最大 100 個の霧雨と 100 個のトッピングを掛け合わせると、絶対的な最悪のケースで約 5,000 万の組み合わせが得られます。これは、単純に実装した場合、すでに Python の境界線に達していますが、列挙の代わりに算術を使用して計算すれば、まだ管理可能です。 

単純な間違いは、すべてのデザートの組み合わせを文字列のタプルとして明示的に構築し、セットに保存しようとすることです。 このアプローチは論理的には正しいですが、文字列の処理と数百万のタプルのハッシュによる不要なオーバーヘッドが発生するリスクがあります。 

2 つ目の微妙な落とし穴は、スクープの組み合わせを誤解していることから発生します。 たとえば、フレーバー A、B、C の場合、有効なペアは AA、AB、AC、BB、BC、CC です。 AB と BA を別のものとして扱うと、二重にカウントされ、答えが間違って水増しされてしまいます。 

他に構造上の制約は存在しないため、問題は依存関係の検索や最適化ではなく、組み合わせのカウントに帰着します。 

## アプローチ

 ブルートフォースソリューションでは、すべての方法を明示的に反復して 2 つのフレーバー (置換あり) を選択し、次にすべての霧雨、さらにすべてのトッピングを反復します。 選択ごとに、デザートの表現を作成し、一意性を確保するためにセットに挿入します。 これが機能するのは、セットがスクープ順で対称性によって生じる重複を自然に削除するためです。 

欠点は、このメソッドがすべてのトリプルの組み合わせを明示的に構築することです。 100 種類のフレーバーがある場合、100 × 100 = 10000 の順序付きペアが存在しますが、順序付けされていないペアは約 5050 のみです。 順序を修正したとしても、最終的には最大 10,000 ペアまで反復することになります。 100 回の霧雨と 100 回のトッピングを掛けると、最大 1 億回の反復が得られます。 各反復にはタプルの作成とハッシュが含まれますが、Python では遅すぎます。 

問題の構造では、3 つのコンポーネント間の相互作用が排除されています。 スクープペアの選択は、霧雨の選択やトッピングの選択とは独立しています。 この分離可能性は、合計の答えが独立したカウントの積であることを意味します。 

したがって、タスクは次のようになります。 

繰り返しを許可して順序のないフレーバーのペアを数え、それから霧雨とトッピングの数を掛けます。 

唯一重要な部分は、フレーバーのペアを正しくカウントすることです。 

n をフレーバーの数としましょう。 繰り返しのある有効な順序なしペアの数は n(n+1)/2 です。 これは、2 つのインデックス i ≤ j を選択することで得られます。 

それが計算されたら、それに d × t を掛けます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n² · d · t) | O(n² · d · t) | 遅すぎる |
 | 最適 | O(n + d + t) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

1. フレーバーのリストを読み、何種類あるか数えます。 これをnと呼びます。 実際の文字列ではなくカウントのみが必要なため、これは重要です。 
2. n × (n + 1) / 2 を使用して、繰り返しが許可される順序付けされていないフレーバーのペアの数を計算します。これは、i ≤ j であるすべてのペア (i, j) を直接カウントします。 
3. 霧雨のリストを読み、それを d として数えます。 
4. トッピングのリストを読み、それらを t として数えます。 
5. 3 つの独立した選択肢 (フレーバー ペア × d × t) を乗算し、結果を出力します。 

### なぜ効果があるのか

 すべての有効なデザートは、3 つの独立した決定によって一意に決定されます。フレーバーからサイズ 2 のマルチセット、霧雨 1 つ、トッピング 1 つです。 フレーバーの選択は、サイズ 2 の組み合わせマルチセットを形成し、標準のカウント式 n(n+1)/2 は、そのような各マルチセットを 1 回だけ列挙します。 霧雨とトッピングの選択は相互に、またはフレーバーの選択と相互作用しないため、乗算の原理が直接適用されます。 各コンポーネントは独立して選択され、すべての組み合わせが有効であるため、組み合わせが二重にカウントされたり見逃されたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    flavors = input().split()
    drizzles = input().split()
    toppings = input().split()

    n = len(flavors)
    d = len(drizzles)
    t = len(toppings)

    pairs = n * (n + 1) // 2
    print(pairs * d * t)

if __name__ == "__main__":
    main()
```ソリューションは各行を読み取り、それをすぐにトークンのリストに変換します。`split`、空白区切りを超えた解析ロジックの必要性を回避します。 重要なのは長さだけであるため、これらのリストを超えるストレージは必要ありません。 

重要な計算は`n * (n + 1) // 2`、繰り返しのある順序のないペアをカウントします。 整数除算を使用すると、偶数 n と奇数 n の両方の正確性が保証されます。 最後の乗算では、独立した組み合わせの選択肢が結合されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + d + t) | 各行はトークンをカウントするために 1 回スキャンされ、その後定数時間の演算が行われます。 
| スペース | お(1) | カウントのみが保存されます。 組み合わせ構造は構築されません。 

入力サイズは小さいですが、入力サイズが最大であったとしても、列挙が完全に回避され、解析後にすべてが定数時間演算に削減されるため、解は自明な制限内に留まります。

## 特殊なケース

 微妙なエッジケースは、フレーバーが 1 つしかない場合です。 入力の場合:```
Vanilla
Chocolate
Sprinkles
```n = 1 なので、フレーバーのペア = 1 × 2 / 2 = 1 となります。有効なスクープの選択肢は (バニラ、バニラ) のみです。 アルゴリズムは、特別な分岐を行わずにこれを正しく処理します。 

もう 1 つのケースは、すべてのリストが最小限である場合です。```
A
B
C
```ここでは、各カテゴリにはオプションが 1 つだけあるため、結果は 1 のままです。 ペア数が有効なままであり、除算やゼロエッジの動作が発生しないため、乗算は依然として保持されます。 

最後に、フレーバーが大きくても霧雨やトッピングが単一要素リストである場合、1 を乗算するとカウントが保持され、条件付き処理が必要ないため、式は正確さを損なうことなくそれらの次元を自然に縮小します。
