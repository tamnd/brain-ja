 ## 問題の理解

 番号の付いたチェストの列が与えられ、それぞれにある程度の枚数のコインが入っています。 各移動で、プレイヤーは整数の位置を選択します$x$、その動きは 3 つの特定の宝箱に同時に影響します。$x$、$2x$、 そして$2x+1$。 これらのチェストのそれぞれから、コインが存在する場合は 1 枚が取り出されます。 

すべての宝箱が空になるとゲームは終了します。 2 人のプレイヤーがポリカルプスから始めて交互に手を動かし、どちらもゲームをできるだけ早く終了したいという意味でのみ最適にプレイします。 問題はどちらが勝つかということではなく、ゲームを終了するために両者が協力すると仮定して、すべてのコインを空にするのに必要な総手数がどれだけ少ないかということです。 

重要な構造は、それぞれの動きがインデックスの小さな「ツリー状」パターンをターゲットにしていることです。 あらゆる選択を$x$バイナリ ヒープのインデックス付けスキームでルートとその 2 つの子を定義します。 

入力サイズが小さいため、$n \le 100$そして$a_i \le 1000$。 これは、コイン数の指数関数的な爆発を避ける限り、ノードごとのシミュレーション、貪欲な調整の繰り返し、さらにはサブセットに対する状態ベースの動的プログラミングを含むあらゆるソリューションが実現可能であることを直ちに示唆しています。 

最初の微妙なエッジ ケースは、有効な手が存在しない場合に現れます。 ない場合$x$そのような$2x+1 \le n$、その場合はまったく操作ができなくなります。 このような構成で少なくとも 1 つのチェストにコインが含まれている場合、ゲームは決して終了できません。 たとえば、次のようなとき$n=1$そして$a_1>0$、有効なものはありません$x$、したがって、答えは次のとおりです$-1$。 

2 番目の微妙な点は、動きが重なり合うことです。 チェスト内のコインは、複数の異なる選択肢によって取り出すことができます。$x$。 たとえば、チェスト 4 は次の影響を受けます。$x=2$（以来$2x=4$）だけでなく、構造内の他の動きにも間接的に関連します。 この重複は、単純な「リーフから上に向かって貪欲に処理する」アプローチでは、操作間のグローバルな結合が無視されるため、最小移動数を誤ってカウントする可能性があることを意味します。 

## アプローチ

 この問題を考える強引な方法は、考えられるあらゆる一連の動きをシミュレートすることです。 それぞれの動きは有効なものを選択します$x$、各状態はコイン数の配列です。 すべてのコインがゼロになるまですべての選択を再帰的に試行し、最小の深さを取得します。 これはすべてのシーケンスを探索するので正しいですが、完全に実行不可能です。$n=100$、分岐因子はおおよそ次のとおりです。$n/2$、深さは最大です。$\max a_i$、そのため、状態空間は指数関数的に爆発します。 

重要な観察は、各手はコインを減らす方法において独立しているということです。$x$現在の値に関係なく、常に 3 つのポジションのそれぞれからちょうど 1 枚のコインを減算します。 これは、問題はコイン除去の命令ではなく、それぞれの回数を選択することであることを意味します。$x$が使用されます。 

させて$t_x$ポジションを選択した回数になります$x$。 それからそれぞれの胸$i$すべての合計に等しいコインを失います$t_x$そのような$i \in \{x, 2x, 2x+1\}$。 問題は、負でない整数を選択することです。$t_x$最小化する$\sum t_x$、チェストの要件をすべて満たすことが条件となります。 

これにより、問題はバイナリインデックス付きツリーのカバー問題に変換されます。 各操作は最大 3 つのノードをカバーし、最小限の合計操作を使用して必要なすべての「コイン需要」をカバーしたいと考えています。 

なぜなら$n$が小さい場合、ノードを逆の順序で処理できます。$n$1 まで下げて、必要な使用量を上方に押し上げます。ノードがまだコインを必要とする場合、それを含む操作を適用する必要があります。 これは、有効な親に対する要求の貪欲な伝播を誘発します。

 ## アルゴリズムのチュートリアル

 からノードを処理します$n$まで$1$、各ノードを「強制操作センター」として使用する必要がある回数を維持します。 

1. 配列を初期化する$need[i]$と$a_i$。 これは、各チェストで取り除かなければならない残りのコインを表します。 
2. 反復する$i$から$n$まで$1$。 治療します$i$潜在的な操作ルートとして。 
3. もし$i > 0$、操作を適用する回数を決定します$i$。 アプリケーションごとに 1 コインが削除されます$i$、$2i$、 そして$2i+1$。 胸を満たすために$i$、少なくとも操作を適用する必要があります$need[i]$回。 
4. しましょう$t = need[i]$。 追加$t$操作を使用することにコミットしているため、答えに戻ります$i$それを何度も。 
5. 減少$need[i]$による$t$、ゼロにします。 
6. 増加させることで効果を上方に伝播する$need[2i]$そして$need[2i+1]$による$t$、これらのポジションも操作時にコインを失うため、$i$が使用されます。 限界を超えないようにする必要があります。 
7. すべてのノードが処理されるまで続行します。 

終わった後、あれば$need[i]$有効な操作でカバーできないノード (特に親経由でアクセスできない場合) については、ゼロ以外の値が返されます。$-1$。 

重要なのは、大きなインデックスから小さなインデックスへの処理により、操作を何回使用するかを決定するときに、より高いインデックスの制約への影響がすべてすでに考慮されていることです。 

### なぜ効果があるのか

 アルゴリズムは、各インデックスにおける不変条件を維持します。$i$、ノードのすべてのコイン要件が$i$すでに最適に満たされています。 加工時$i$を減らすために残された唯一の方法$need[i]$操作を使用することです$i$これは、以前に満たされた制約に違反することなく、より小さなインデックス操作が総コストを削減するような影響を与えることができないためです。 これにより、各ステップでローカルに強制された決定が作成され、すべての依存関係がバイナリ ヒープ構造内で親から子に流れるため、逆のトポロジー順序で処理することで将来の競合が防止されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    a = [0] + a  # 1-indexed

    need = a[:]
    ans = 0

    for i in range(n, 0, -1):
        if need[i] <= 0:
            continue

        t = need[i]
        ans += t
        need[i] -= t

        if i * 2 <= n:
            need[i * 2] += t
        if i * 2 + 1 <= n:
            need[i * 2 + 1] += t

    for i in range(1, n + 1):
        if need[i] > 0:
            print(-1)
            return

    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、要件をインデックスの逆順に下方にプッシュするという考えに従っています。 配列のインデックスは 1 で、遷移のヒープ構造に一致します。$i \rightarrow 2i, 2i+1$。 各ノードの欠陥は、そのノードで多数の操作を直接トリガーし、その影響は子に伝播されます。 

微妙な点は、ノードを「修正」するのは 1 回だけであるということです。これは、ノードを処理した後は、後のステップでそのノードを再検討することがないためです。 これにより、二重カウントが回避され、制約の線形伝播が保証されます。

 ## 特殊なケース

 最もデリケートなケースは次のような場合です。$n = 1$。 有効なものはありません$x$なぜなら、状態が$2x+1 \le n$すべてが肯定的な場合は失敗します$x$。 もし$a_1 > 0$、手は存在せず、答えは次のようになります。$-1$。 ループはいかなる操作も適用しないため、アルゴリズムはこれを正しく処理します。$need[1]$ゼロ以外の場合、失敗が引き起こされます。 

別のエッジケースは、すべてのコインが葉の近くに集中している場合に発生します。$a_n > 0$。 どの操作もターゲットにできないため、$n$次のように表示されない限り$2x$または$2x+1$、実現可能性は完全に親の連鎖が存在するかどうかに依存します。 逆の処理により、リーフが削減を必要とする場合、その要求が上方に押し上げられ、有効な祖先がそれを吸収できない場合には実行不可能性が検出されます。 

3 番目のケースは、伝播によって要求が相殺される場合です。 中間ノードが一時的に負または過剰に正になった場合でも、最後の検証ステップで構造全体の一貫性が保証され、隠れた過剰カウントによって不正確な答えが生成されるのを防ぎます。
