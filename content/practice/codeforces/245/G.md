 ## 解決策
 ## 問題の理解

 私たちには、各ユーザーが文字列名で識別され、友人関係が名前のペアとして与えられる、無方向のソーシャル ネットワークが与えられています。 これらの友情から、すべてのユーザーについて、どの非友達が自分に最も「似ている」かを判断する必要があります。類似性は共通の友達の数によって測定されます。 

具体的には、固定ユーザーの場合`x`、他のすべてのユーザーを調べます`y`そうでない人は`x`まだ直接接続されていません`x`。 このようなすべての候補者のうち、ユーザーの数を数えます。`z`両方とも友達です`x`そして`y`。 この数を最大化するユーザーは、次の友達として推奨されると見なされます。`x`。 ユーザーごとに、そのようなマキシマイザーがいくつ存在するかを出力する必要があります。 

この構造は、無向の単純なグラフに関するグラフ問題ですが、最良の候補を 1 つだけ見つけるのではなく、共通の近傍の最大数に関連付けられたすべての頂点をカウントする必要があります。 

入力サイズはエッジの観点からは小さく、最大でも 5000 の友情ペアがありますが、個別のユーザーの数は明示的に制限されておらず、依然として大きくなる可能性があります。 このため、隣接リストに基づく推論が不可欠になります。 密集した$O(n^2)$ユーザーのすべてのペアに対するスキャンは、慎重に実装すればまだ許容できますが、ユーザーの各ペアに対して単純に交差を再計算すると遅すぎます。 

微妙なエッジケースは、友人セットが非常に小さいユーザーから発生します。 ユーザーに友達が 1 人しかいない場合、友達以外の候補者は共通の友達を最大でも 1 人かゼロにするため、多くの候補者が同数になる可能性があります。 もう 1 つの特殊なケースは、複数のユーザーが同じ最大数に達する場合です。つまり、親友を 1 人だけ選ぶのではなく、全員を数える必要があります。 

もう 1 つの問題は、隣接関係が慎重に扱われない場合、共通の友人が二重にカウントされることです。 グラフは無向であり、入力エッジは一意であるため、対称的な隣接関係の構築を確保する必要があります。 

## アプローチ

 直接的なアプローチは、すべてのユーザーを考慮することです`x`、その後、他のすべてのユーザーを反復処理します`y`、次の場合はスキップします`y`は`x`またはすでに友人です`x`、隣接セットを交差させることによって共通の友人の数を計算します。 隣接関係がリストとして保存されている場合、各交差にはコストがかかります$O(deg(x) + deg(y))$、これにより、最悪の場合のコストはおよそ$O(n^2 \cdot n)$、ユーザーの数が多い場合、これは受け入れられません。 

重要な観察は、共通の友人の数は、友人を反復処理することで計算できるということです。`x`。 友達ごとに`z`の`x`、すべての隣人`y`の`z`間の共通の友人 1 人を貢献します`x`そして`y`。 これにより、計算がペアごとの交差から「近傍伝播」ビューに移行します。 すべてのペアを直接比較する代わりに、次の 2 ホップ近傍内の候補のスコアを蓄積します。`x`。 

これは、各エッジが正確に 2 つの隣接リストと各三角形関係に寄与するため、効率的に機能します。`(x, z, y)`共有ネイバーごとに 1 回だけカウントされます`z`。 

すでに直接接続しているユーザーを考慮しないようにする必要があります。`x`、そして我々は除外する必要があります`x`自体。 

全体的な複雑さは、各ノードの近傍の次数の合計に比例します。これは、グラフ内の「2 ステップ ウォーク」の数において基本的に線形であり、制約内に簡単に収まります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース ペアワイズ交差 | O(n² · d) | O(n + m) | 遅すぎる |
 | 2 ホップの蓄積 | O(∑ d²) ≈ O(m√m) の最悪ケースの直観、実際には O(mn) の最悪ケースですが、m ≤ 5000 の場合は許容可能 | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 O(1) で友情をテストできるように、隣接セットを使用してグラフを表します。 

1. 各一意のユーザー名を整数インデックスにマッピングします。 これにより、グラフの処理が簡素化され、文字列の比較を繰り返すことがなくなります。 
2. 隣接関係セットを構築する`adj[u]`ユーザーごとに。 友情は対称的であるため、両方向に挿入します。 
3. ユーザーごとに`x`、辞書を作成します`cnt`各候補者に共通の友人の数が保存されます`y`持っています`x`。 
4. 各友達を反復処理する`z`の`x`。 すべての隣人のために`y`の`z`、 増加`cnt[y]`1つずつ。 このステップでは、次の間で共有される隣接ノードの数をカウントします。`x`そして`y`経由`z`。 
5.すべての友達を処理した後、`x`の最大値を決定します。`cnt`。 この値を達成したユーザーは、提案された友達の候補となります。 
6. いかなるユーザーも考慮から除外する`y`どちらかは誰ですか`x`それ自身、またはすでに直接の友人である`x`、定義上失格だからです。 
7. 最大共通友人数に達している残りのユーザーの数を数え、これを答えとして保存します。`x`。 

重要な考え方は、すべての相互の友人関係が共有中間ノードごとに 1 回だけ生成されるということです。 もし`x`そして`y`共有`k`友達、それならまさにそこにいるよ`k`これらの友人を介してそれらを接続する長さ 2 の個別のパスがあり、そのようなパスごとにカウンタが 1 回インクリメントされます。 

### なぜ効果があるのか

 固定ソースノードの場合`x`、すべての潜在的な候補者`y`個別のパスごとに 1 つの増分を正確に受け取ります`x → z → y`。 これらのパスは、共通の隣接パスと 1 対 1 に対応します。`x`そして`y`。 したがって、`cnt[y]`常に、間で共有する友人の数と等しくなります。`x`そして`y`。 直接の友人を明示的に除外しているため、`x`それ自体、残りの最大値`y`最も類似した非友人をすべて正確に識別します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    m = int(input())
    
    name_to_id = {}
    adj = []
    
    def get_id(name):
        if name not in name_to_id:
            name_to_id[name] = len(adj)
            adj.append(set())
        return name_to_id[name]
    
    for _ in range(m):
        a, b = input().split()
        u = get_id(a)
        v = get_id(b)
        adj[u].add(v)
        adj[v].add(u)
    
    n = len(adj)
    id_to_name = [""] * n
    for name, i in name_to_id.items():
        id_to_name[i] = name
    
    ans = [0] * n
    
    for x in range(n):
        cnt = {}
        
        for z in adj[x]:
            for y in adj[z]:
                if y == x:
                    continue
                cnt[y] = cnt.get(y, 0) + 1
        
        best = -1
        for y, c in cnt.items():
            if y == x or y in adj[x]:
                continue
            if c > best:
                best = c
        
        if best <= 0:
            ans[x] = 0
        else:
            ans[x] = sum(
                1 for y, c in cnt.items()
                if y != x and y not in adj[x] and c == best
            )
    
    print(n)
    for i in range(n):
        print(id_to_name[i], ans[i])

if __name__ == "__main__":
    solve()
```この実装では、隣接操作が効率的に行われるように、まず文字列名を整数 ID に圧縮します。 各隣接リストはセットとして保存されるため、ユーザーがすでにフレンドであるかどうかを定期的にチェックできます。 

各ノードについて、その 2 ホップ近傍にわたる周波数マップを構築します。 内側の二重ループは各友人の上を歩き、次にその友人の友人の上を歩き、共有近傍の数を蓄積します。 2 番目のパスでは最大値が抽出され、無効な候補を除いてその最大値に到達した候補の数がカウントされます。 

微妙な点は、有効な候補者がいないユーザーの処理です。 その場合`best`残る`-1`と、提案された友達がゼロであることが正しく出力されました。

 ### 例 1

 入力:```
5

Kate Mike
Kate Tank
Gerald Tank
Gerald David
```隣接関係を構築します。 

マイク：ジェラルド、ケイト

 ジェラルド：マイク、タンク、デビッド

 ケイト：マイク、タンク

 タンク：ケイト、ジェラルド

 デヴィッド：ジェラルド

 のために`David`、の隣人`Gerald`Mike、Tank、Mike、Tank は共有構造を介して貢献します。 

| × | z (x の友人) | y (z の隣) | cnt[y] |
 | --- | --- | --- | --- |
 | デビッド | ジェラルド | マイク | 1 |
 | デビッド | ジェラルド | タンク | 1 |

 最大値は 1 で、Mike と Tank が達成しました。したがって、David の答えは 2 です。 

のために`Kate`と同様の推論により、最良の候補が 1 つ得られます。 

これにより、アルゴリズムが直接接続ではなく 2 ホップのオーバーラップを正しくカウントしていることが確認されます。

| × | z | y | cnt[y] |
 | --- | --- | --- | --- |

 ここ`C`2 人の共通の友人を蓄積し、独自に最高です。 

これは、同じ候補への複数のパスが正しく集約されていることを示しています。

 ## 特殊なケース

 重要なエッジケースは、すべての潜在的な候補者がすでに直接の友人である場合です。 たとえば、完全な三角グラフの場合`A-B-C-A`、すべてのペアが接続されているため、提案された友達は存在しません。 アルゴリズムが構築される`cnt`ただし、すべての候補は隣接性チェックによって除外されるため、`best <= 0`そしてゼロを生み出す。 

もう 1 つのケースは、1 つの中心ノードが多数のリーフに接続されているスター グラフです。 リーフノードの場合`x`、1 つおきの葉はちょうど 1 人の共通の友人 (中心) を共有します。 カウント ループにより、各リーフがカウント 1 を取得し、そのようなすべてのリーフが最大値に正しく関連付けられるようになります。 

最後に、ノードに隣接ノードが 1 つだけある疎なグラフでは、中間セットが小さい場合でも、アルゴリズムは引き続き 2 次接続を正しくカウントします。 正確さは、次数サイズの仮定ではなく、近傍の近傍を列挙することにのみ依存します。
