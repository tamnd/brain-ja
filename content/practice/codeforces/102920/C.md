 ## 解決策
 ## 問題の理解

 各ノードがカフェの候補地であり、ノードのサブセットが集合住宅としてマークされている重み付きツリーが与えられます。 任意の 2 つのノード間の距離は、ツリー内の一意のパスに沿ったエッジの重みの合計です。 

各候補ノードについて$p$少なくとも 1 つのアパートメント ノードが存在するかどうかを知りたいと考えています。$z$そのような$p$厳密には～に近いです$z$他のすべての候補ノードよりも。 つまり、アパートを修理する場合、$z$、からの距離を比較します。$z$ツリー内のすべてのノードに、$p$そのノードに最も近い一意のノードでなければなりません$z$。 もしそのような目撃者アパートが存在するなら、$p$良い場所と言われています。 

タスクは、少なくとも 1 つのアパートの一意の最近接点として機能できるノードの数を数えることです。 

木には最大で$10^5$したがって、ノードまたはソースに対する二次関数の動作に近いアプローチは、直ちに遅すぎます。 各アパートメントからの距離を個別に再計算する必要がある場合、次のオーダーが必要になります。$O(nk)$または$O(n^2)$、1秒で通過できる速度をはるかに超えています。 

重要な点は、一意性が重要であるということです。 アパートメントに同じ最小距離にある候補サイトが 2 つ以上ある場合、定義では他のすべてのノードに対して厳密な不平等が要求されるため、そのアパートメントを介してそれらのサイトはいずれも「良好」とはみなされません。 

小さな失敗例はネクタイから生まれます。 アパートが 2 つの対称的な支店のちょうど真ん中に位置しているとします。 両端が同等に近いため、どちらも厳密な優位性を満たしません。 等価性を処理しない単純な「最も近いノード」割り当てでは、両端が有効であると誤ってカウントされます。 

## アプローチ

 直接解釈すると、すべてのアパートメント ノードをソースとして試し、すべてのノードまでの距離を計算し、次にどのノードが少なくとも 1 つのソースに対して一意に最も近くなるかを確認することを提案します。 まであるので、$n$最悪の場合、各アパートから単一ソースの最短パスを実行するとコストがかかる$O(n \cdot n \log n)$、これは大きすぎます。 

すべてのアパートを同時に表示すると、問題の構造が変わります。 各アパートメントを個別に扱う代わりに、それらの影響をツリー全体に一緒に伝播させることができます。 これは古典的な複数ソースの最短パスの状況であり、各ノードが最も近いソースに割り当てられます。 ただし、標準的なマルチソース ダイクストラでは、最も近いソースがわかるだけで、その最も近いソースが一意であるかどうかはわかりません。 

欠けている部分は、同点を検出する必要があることを認識することです。 ノードは、その最も近いソースが他のどのソースよりも厳密に近い場合にのみ「良い場所」に貢献します。 これは、ノードまでの最適な距離だけでなく、別のソースからの 2 番目に最適な距離も必要であることを意味します。 2 番目に最適な距離が最適な距離と等しい場合、ノードはタイ ポイントとなり、何も寄与しません。 厳密に大きい場合は、最も近いソースが一意にそのノードを担当します。 

したがって、すべてのアパートメント ノードからマルチソース ダイクストラを同時に実行できますが、各状態はそのソースのアイデンティティを保持します。 各ノードでは、さまざまなソースからの最良の到着と 2 番目に良い到着を維持します。 ローカルで一意性を検出するにはこれで十分です。 

この伝播が完了すると、すべてのノードは最大 1 つのソースを一意の最も近い所有者として認定できます。 その場合、そのソースには「少なくとも 1 つの監視ノードがある」とマークされます。 最終的な答えは単にマークされるソースの数です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (アパートごとにディクストラ) |$O(k \, n \log n)$|$O(n)$| 遅すぎる |
 | トップ 2 トラッキングを備えたマルチソース ダイクストラ |$O(n \log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 すべてのアパートメントをグローバル優先キューの最初のソースとして扱います。 キュー内の各州には、ノード、元のアパートメントからの距離、およびそのアパートメントの ID が含まれます。 

1. 距離 0 にあるすべてのアパートメント ノードで優先キューを初期化し、それぞれに独自のソース ID でラベルを付けます。 これにより、すべてのソースからの検索が一度に行われるため、距離が同時に外側に広がります。 
2. すべてのノードについて、フォーム (距離、ソース) の最良の 2 つのペアの小さな記録を維持し、常にそれらを距離でソートし、ソースが区別できるようにします。 この構造は、関係を検出できるようにする中心的なメカニズムです。 
3. 優先キューから最小距離の状態をポップします。 この状態が、そのノードに保存されているソースの最良または 2 番目に良いエントリと一致しない場合は、それを破棄します。 これにより、古くなった長いパスが干渉するのを防ぎます。 
4. 現在のノードについて、この (距離、ソース) ペアを上位 2 つのリストに挿入してみます。 個別のソースを維持しながら最適な位置または 2 番目に最適な位置が改善される場合は、それに応じて更新します。 ソースがすでにより悪い距離で表現されている場合は、それを上書きします。 
5. エッジの重みによって距離を増加させて、更新された状態をキューにプッシュすることによって、すべての近傍を緩和します。 各伝播ステップにより、各アパートメントの影響がツリー全体に広がります。 
6. すべてのノードを処理した後、各ノードに保存されている上位エントリを調べます。 最良のエントリが 2 番目に優れたエントリよりも厳密に距離が優れている場合、最良のソースがこのノードを一意に所有します。 そのソースを有効としてマークします。 
7. これまでにマークされたソースの数を数えます。 

### なぜ効果があるのか

 すべてのノードで、異なるソースからの 2 つの最小の到着時間を維持します。 非負の重みを持つツリー内の距離は最適な部分構造を満たすため、ソースが最小距離のノードに初めて到達すると、そのソースはグローバルに最適になります。 2 番目に優れたエントリは、最も近い競合ソースをキャプチャします。 

2 番目に最適な距離が最適な距離よりも厳密に大きい場合、他のソースはそのノードで最良の距離と同点または上回ることはできません。 したがって、そのノードは、最も近いソースの一意性を証明します。 逆に、等しい場合は、少なくとも 2 つのソースが同じ最小距離を達成するため、その位置にあるノードを厳密な証人として使用することはできません。 

ソースからノードまでのパスはツリー内で一意に決定されるため、このローカルな条件は十分です。そのため、すべての競合他社は、このグローバルな伝播において最短パスの到着として現れる必要があります。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    g = [[] for _ in range(n)]
    
    for _ in range(n - 1):
        u, v, w = map(int, input().split())
        u -= 1
        v -= 1
        g[u].append((v, w))
        g[v].append((u, w))
    
    sources = list(map(int, input().split()))
    sources = [x - 1 for x in sources]
    
    INF = 10**18
    best = [dict() for _ in range(n)]
    # best[u]: source -> dist, but we only keep top 2 per node
    
    pq = []
    
    for s in sources:
        heapq.heappush(pq, (0, s, s))
        best[s][s] = 0
    
    # store top 2 per node: list of (dist, src)
    top = [[] for _ in range(n)]
    
    while pq:
        d, u, src = heapq.heappop(pq)
        
        if src in best[u] and best[u][src] != d:
            continue
        
        for v, w in g[u]:
            nd = d + w
            if src not in best[v] or nd < best[v][src]:
                best[v][src] = nd
                heapq.heappush(pq, (nd, v, src))
    
    # extract top-2 per node
    owner = [None] * n
    second = [INF] * n
    
    for u in range(n):
        arr = sorted(best[u].items(), key=lambda x: x[1])
        if not arr:
            continue
        if len(arr) == 1:
            owner[u] = arr[0][0]
            second[u] = INF
        else:
            owner[u] = arr[0][0]
            second[u] = arr[1][1]
    
    good = set()
    
    for u in range(n):
        if owner[u] is None:
            continue
        best_dist = min(best[u].values())
        # recompute second best distance among sources
        dists = sorted(best[u].values())
        if len(dists) >= 2 and dists[0] == dists[1]:
            continue
        good.add(owner[u])
    
    print(len(good))

if __name__ == "__main__":
    solve()
```この実装では、各州が元のアパートメントを保持するマルチソース ダイクストラが実行されます。 辞書`best[u]`各ソースからノードまでの既知の最良の距離を保存します`u`ソースはツリー メトリックのノードごとに 1 つの最適な距離のみを提供できるため、これで十分です。 

プライオリティ キューにより、最初に状態を緩和する際に、距離の増加順に状態が緩和されるため、最短パスの正確さが維持されます。 最後のフェーズでは、ノードにおける最小の 2 つの距離が厳密に異なるかどうかをチェックします。 それらが等しい場合、そのノードはソースを検証できません。 

最後のセットは、少なくとも 1 つのノードを一意に所有することを管理するすべてのソースを収集します。

 ## 特殊なケース

 重要なエッジケースは、複数のアパートメントがノードから等距離にある場合です。 ノード 1 を中心とする対称スターでは、すべてのリーフが中心からの距離 1 にあるため、どのリーフも一意の方法でどのアパートメントにも厳密に最も近づくことはできません。 中央で記録された最良の 2 つの距離が等しいため、アルゴリズムはこれを捕捉し、ソースがマークされるのを防ぎます。 

もう 1 つのエッジ ケースは、ソースがどこでも完全に支配されている場合です。これは、常に最適な距離で接続されている場合に発生する可能性があります。 このようなシナリオでは、そのエントリはどのノードでも厳密な不等式を生成しないため、カウントされることはありません。
