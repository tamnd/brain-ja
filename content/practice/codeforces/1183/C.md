 ## 問題の理解

 We are simulating a sequence of exactly$n$ゲームターン。 Vova はいつでもバッテリーを充電できます$k$、そして各ターン、彼はチャージを減らす2つのアクションのうち1つを選択する必要があります。 

ワンアクションはバッテリーの損失という点では安価ですが、バッテリーが十分に高い場合にのみ使用できます。 もう 1 つのアクションはより高価ですが、要件が弱いため、より頻繁に使用できます。 目標はすべて完了することです$n$いかなる回転後もバッテリーがゼロ以下にならないようにしながら回転します。 すべての有効な戦略の中で、コストのかかるアクションが使用される回数を最大化したいと考えています。 

したがって、問題は実現可能性だけではなく、時間の経過とともに変化するハードなリソース制約の下で「より良い」動きの数を最大化することにもあります。 

重要な問題は、各ターンでの選択が将来の両方のアクションの利用可能性に影響を与えることです。 グローバルな推論を持たない貪欲な選択は、簡単に失敗する可能性があります。なぜなら、早​​い段階であまりにも多くの安価な手を使用すると、後で違法な状態に追い込まれる可能性があるためです。一方、あまりにも多くの高価な手を使用すると、生き残ることができる総ターン数が減少します。 

制約は大きく、$q \le 10^5$そして$n, k \le 10^9$。 これにより、ターン中のシミュレーションが即座に除外されます。 どのソリューションでも、クエリごとに対数時間または定数時間で答えを計算する必要があります。 平$O(n)$テストケースごとには不可能です。 

バッテリーが、より安価なデクリメントのみを使用してすべてのターンを実行するのにかろうじて十分である場合、微妙なエッジケースが表示されます。$b$。 たとえ全体としてそれが可能であったとしても、順番によっては各ターン後の厳格なプラス要件が実現可能性を損なう可能性があります。これは、一連の大きな減少により予想よりも早くバッテリーがゼロ以下になる可能性があるためです。

 ## アルゴリズムのチュートリアル

 必須の最小限の消費とオプションのアップグレードの観点からプロセスを書き直します。 

1. 常に安価なオプションを使用する場合の最小総消費量を計算します。$b$。 これは$n \cdot b$。 これがすでに超えているか等しい場合$k$の場合、有効なシーケンスは存在しません。 その理由は、可能な限り最善の戦略を講じたとしても、すべての段階でバッテリーをプラスに保つことはできないためです。 
2. 可能であれば、ベースラインコストを支払った後に残りの使用可能な予算を計算します。$k - n \cdot b$。 これは、バッテリーの一部を交換することで、どの程度の追加バッテリー損失が許容できるかを表します。$b$-と一緒に動きます$a$-動きます。 
3. を交換するたびに、$b$- で移動します$a$-移動すると追加料金がかかります$a - b$バッテリーの単位。 これは、動きを改善するための増分コストです。 残りの予算の範囲内で、そのような交換の数を最大化したいと考えています。 
4. したがって、置換の最大数は次のとおりです。$\left\lfloor \frac{k - n b}{a - b} \right\rfloor$。 ただし、総ターン数を超えることはできません$n$, したがって、この値と$n$。 
5. 最終的な答えは、$a$-moves を実行し、実現可能性が失敗した場合は出力します。$-1$。 

### なぜ効果があるのか

 有効なシーケンスはすべて、正確に次のように構成されている必要があります。$n$動き、それぞれが次のいずれかに貢献します$a$または$b$総消費量に。 すべての移動はバッテリーを減少させるだけであり回復は存在しないため、移動の順序はバッテリーが早期にゼロにならないようにすること以外には実現可能性に影響しません。 厳密な正の制約は、合計消費量が厳密に次の値よりも小さい場合に満たされます。$k$なぜなら、以前の状態に違反することなく、いつでも後でより高コストの動きを手配できるからです。 これにより、問題は 2 つの固定費にわたる単純な予算配分問題に変換されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    for _ in range(q):
        k, n, a, b = map(int, input().split())

        if k <= n * b:
            print(-1)
            continue

        # extra budget beyond baseline all-b moves
        extra = k - n * b

        # each a-move instead of b-move costs (a - b) extra
        ans = extra // (a - b)

        # cannot exceed number of turns
        if ans > n:
            ans = n

        print(ans)

if __name__ == "__main__":
    solve()
```実装では、あらゆる移動にコストを使用するベースライン戦略を使用して実現可能性を直接計算します。$b$。 それが過ぎると、アップグレードできる回数が計算されます。$b$-に移動する$a$- 利用可能な追加予算を使用して移動します。 

引き算$k - n \cdot b$整数サイズが固定されている言語では 64 ビット算術を使用して慎重に実行する必要がありますが、Python は大きな整数を安全に処理します。 による除算$a - b$は整数のフロア除算であり、許容できる完全なアップグレードの数と一致します。

import sys, io

def run(inp: str) -> str:

 ## 特殊なケース

 エッジケースの 1 つは次の場合に発生します。$k$と全く同じです$n \cdot b$。 このような状況では、システムに余裕はありません。 を置き換えようとする試みは、$b$- で移動します$a$-移動するとすぐに実行可能性が損なわれます。 アルゴリズムは正しく返します$-1$これは、最小限の戦略でもプラスのバッファーが残らないという事実と一致します。 

次の場合には、別のエッジケースが発生します。$a - b$利用可能なスラックに比べて大きい。 バッテリーの合計がすべての移動に十分な場合でも、アップグレードできるのはわずか数回だけです。 各アップグレードは残りの予算の個別の固定量を消費するため、分割ステップにより、過大な計算が行われないことが保証されます。 

最終的な境界ケースは次のような場合です。$n$非常に大きいですが、$k$ほんの少し上にあります$n \cdot b$。 入力サイズが大きいにもかかわらず、答えは非常に小さくなり、定数時間の計算により、$n$算数を超えて。
