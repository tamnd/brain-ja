 ## 解決策
 ## 問題の理解

 一列に配置された一連の場所が与えられます。 各場所には最初、ある程度の量のゴミが含まれています。 清掃プロセスには、何人かの作業員を選択する必要があり、これらの作業員が順番に場所を移動し、各場所でゴミを清掃します。 作業員が現場に到着したら、そこでゴミを取り除くことができますが、作業員の数に応じて、残ったゴミの一部が繰り越される場合があります。 

重要な問題は、固定数の作業員をシミュレートすることではなく、すべての場所のすべてのゴミを最後の場所の終了までに完全に除去できるように、必要な最小限の作業員の数を決定することです。 

各作業員は各拠点の処理能力に貢献しており、ある拠点に利用可能な作業員に比べてゴミが多すぎる場合は、その一部を次の拠点に「前方移動」する必要がありますが、一部はすぐに削除できます。 最適なシフトを行った後でも、最後の場所にまだゴミが残っている場合は、選択した作業員の数が不十分です。 

入力は各位置のゴミの量を表します。 出力は単一の整数です。これは、指定されたルールに基づいてすべての場所のすべてのゴミを処理できるようにするワーカーの最小数です。 

この制約により、最大約 200,000 単位の大きさと、O(n^2) シミュレーションが不可能なほど大きな配列サイズが許可されます。 ワーカーの候補数ごとにワーカーの動作をシミュレートしようとする単純なアプローチでは、O(n) 回のスキャンに O(A) 回の可能なワーカー数を乗算することになり、これでは遅すぎます。 これは、線形実現可能性チェックと組み合わせて、答えに対する対数検索を即座に示唆します。 

ポジション間の移動を処理するときに、微妙な障害モードが発生します。 ロケーションに k よりわずかに多く 2,000 を超えないユニットがある場合でも、超過分が慎重に転送された場合に限り、実行可能です。 完全にクリアするか完全にフォワードする単純な貪欲な戦略は、この中間体制を打ち破る可能性があります。 たとえば、k = 3 でポジションに 5 ユニットがある場合、ローカルで 5 つすべてを削除することは不可能ですが、より適切な分割が存在する場合でも次のポジションが実行不可能になる可能性があるため、5 つすべてを転送することも不可能です。 

最後のポジションは、もう 1 つの重要なエッジ ケースです。 最終的な場所に残ったものはそれ以上転送できないため、残りの量が直接の容量を超えた場合、構成は直ちに失敗する必要があります。 

## アプローチ

 ソリューションの中核となる構造は、実現可能性がワーカーの数において単調であるという観察から得られます。 k 人のワーカーがすべてを掃除するのに十分な場合、すべてのローカル操作はキャパシティが増加する場合にのみ容易になるため、さらに大きな数 k + 1 でも十分です。 この単調性は、最小 k を二分探索することを示唆しています。 

強引なアイデアでは、1 から可能な最大値までの考えられる k をそれぞれ試し、k 人のワーカーがすべてのゴミを掃除できるかどうかを確認します。 各チェックでは、ラインに沿ったプロセスをシミュレートし、ゴミを貪欲に配布または転送する必要があります。 各シミュレーションは O(n) であり、k は約 200000 まで大きくなる可能性があるため、複雑さは O(nA) となり、大きすぎます。 

改善は懸念事項を分離することで実現します。 問題を k に対する直接シミュレーションとして扱う代わりに、k を実現可能性パラメーターとして扱い、「k 人の作業員がすべての場所を掃除できるか?」という「はい」か「いいえ」の質問をします。 これにより問題が単調な決定問題に変換され、二分探索が可能になります。 

残りの課題は、実現可能性チェックを正しく実装することです。 それぞれの立場で、どれだけのゴミを現地で撤去し、どれだけの量を転送するかを決定する必要があります。 最適な戦略の構造はキャパシティ制限によって強制されます。各ワーカーはローカルな移動と移動の両方に貢献できますが、唯一意味のある体制は、現在の量が k 以内、k と 2k の間、または 2k を超えるかどうかです。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |

 | 二分探索 + O(n) 実現可能性チェック | O(n log A) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### 固定 k の実現可能性チェック

 1. 最初の位置から開始して、その位置での現在のゴミの量 x を追跡します。 最初は、x がその位置の入力値です。 

この値は、地元のゴミと、以前の場所から持ち込まれたゴミの両方を表します。 
2. x ≤ k の場合、この場所にあるすべてのゴミを取り除き、前方には何も運びません。 

これが機能するのは、すべてのゴミをこの位置の空いている作業員が直接処理できるためです。 
3. x > 2k の場合、直ちに失敗します。 

その理由は、たとえ k 人の作業員全員が移送と撤去にフルに貢献したとしても、1 つの場所で処理できるのは最大 2,000 ユニットであるため、これを超えると完了は不可能になるということです。 
4. k < x ≤ 2k で、これが最後の場所ではない場合は、作業を最適に分割します。k ユニッ​​トをローカルに削除し、x − k ユニッ​​トを次の場所に転送します。 

k 人のワーカーがその能力をローカルで完全に消費し、残りの超過分は最もコンパクトな方法で繰り越される必要があるという考えです。 
5. k < x ≤ 2k で、これが最後の場所である場合、失敗します。 

最後に転送は不可能であるため、k を超える超過は解決できません。 
6. 次の場所に移動し、転送されたゴミを初期量に追加し、すべての場所が処理されるまで繰り返します。 
7. すべての位置が失敗を引き起こすことなく処理される場合、k は実現可能です。 

### なぜ効果があるのか

 重要な不変条件は、すべてのステップで、キャリーされる値が、将来の場所で処理する必要がある最小限の避けられない残り物を表すということです。 トランジション ルールにより、必要以上にフォワードしないことが保証されます。これは、余分にフォワードすると、将来のポジションを満たすことが難しくなるだけだからです。 2k の制限は、各ワーカーがローカル移動の最大 1 単位と転送容量の最大 1 単位に寄与するという事実から生じているため、場所ごとの有効処理の合計は 2k に制限されます。 これを超える構成は、有効なワーカー割り当てに分解できません。 

二分探索は、実現可能性関数が単調であるため有効です。k を増加しても、どの位置でもゴミを処理する能力が低下することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(k, a):
    carry = 0
    n = len(a)
    
    for i in range(n):
        x = a[i] + carry
        
        if x <= k:
            carry = 0
        elif x > 2 * k:
            return False
        else:
            if i == n - 1:
                return False
            carry = x - k
            
    return True

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    lo, hi = 1, max(a)
    
    while lo < hi:
        mid = (lo + hi) // 2
        if can(mid, a):
            hi = mid
        else:
            lo = mid + 1
    
    print(lo)

if __name__ == "__main__":
    solve()
```実装では実現可能性チェックを関数に分離します。`can(k, a)`これは貪欲な前進プロセスをシミュレートします。 変数`carry`は、前の位置からプッシュされた残りのゴミを表し、現在の場所に追加されます。 

重要な詳細は、`k < x ≤ 2k`場合。 私たちは常に正確に転送します`x - k`、それ以上でもそれ以下でもありません。 転送量を少なくすると、現在の位置に未処理のゴミが余分に残ることになり、実現可能性と矛盾します。 これ以上転送すると、現在のポジションが改善されずに、将来のポジションが難しくなるだけです。 

二分探索境界は次のように選択されます。`[1, max(a)]`ゴミが存在する場合は少なくとも 1 人の作業員が必要になるため、`max(a)`ワーカーは、転送することなく単一のポジションを簡単に処理します。 

## 実用的な例

 ### 例 1

 検討してください`a = [3, 2, 4]`。 

私たちは実現可能性をテストします`k = 3`。 

| 私 | a[i] | キャリー | × | 決定 | 新しいキャリー |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 3 | 0 | 3 | x ≤ k、クリア | 0 |
 | 1 | 2 | 0 | 2 | x ≤ k、クリア | 0 |
 | 2 | 4 | 0 | 4 | k < x ≤ 2k、最後 → 失敗 | - |

 したがって、k = 3 は実現不可能です。 

のために`k = 4`:

 | 私 | a[i] | キャリー | × | 決定 | 新しいキャリー |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 3 | 0 | 3 | クリア | 0 |
 | 1 | 2 | 0 | 2 | クリア | 0 |
 | 2 | 4 | 0 | 4 | x ≤ k、クリア | 0 |

 k = 4 なので、答えは 4 になります。 

これにより、二分探索境界の動作が確認されます。 

### 例 2

 検討してください`a = [5, 1, 6]`、k = 4。 

| 私 | a[i] | キャリー | × | 決定 | 新しいキャリー |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 5 | 0 | 5 | k < x ≤ 2k → キャリー 1 | 1 |
 | 1 | 1 | 1 | 2 | x ≤ k、クリア | 0 |
 | 2 | 6 | 0 | 6 | k < x ≤ 2k、最後 → 失敗 | - |

 これは、前の位置から転送すると次の位置での負荷が軽減されるものの、それでも大きすぎる最終位置を救済できないことを示しています。

 ## 特殊なケース

 単一の場所が 2k を超える場合は、実現可能性チェックで直ちに処理されます。 たとえば、k = 3 で、場所に 7 ユニットがある場合、条件は次のようになります。`x > 2k`失敗を引き起こします。 これは、ワーカー間で最大限に分割しても、ワーカーごとの制限に違反せずにワークロードを分散できない状況に対応します。 

最終的な場所の制約は個別に適用されます。 キャリーによって最後の位置が k を超える場合、それが 2k 以内であっても、アルゴリズムはそれを正しく拒否します。 たとえば、k = 4、最後の位置 x = 6 の場合、中間のケースに入り、最後に転送が不可能であることが検出されます。 

中間の分割ケースにより、過剰分は常に制御された方法で前方に押し出されます。 x = k + t の場合、正確に t を転送すると、次の位置が厳密に必要なものだけを受信することが保証され、負荷を恣意的に増大させるのではなく、将来の位置の実現可能性が維持されます。
