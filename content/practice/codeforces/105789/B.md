 ## 解決策
 ## 問題の理解

 それぞれがビットで構成されるベクトルのコレクションが与えられ、それらのいくつかを選択してサブセットを形成することができます。 目標は、選択したサブセットのサイズが偶数である必要があるという追加要件とともに、ビットごとの XOR がゼロである空ではないサブセットを選択できるかどうかを決定することです。 

入力はバイナリ ベクトルのリストとして理解できます。 各ベクトルは GF(2) 上のベクトル空間内の点を表すため、加算は XOR に対応します。 このタスクは、XOR でゼロ ベクトルに相殺され、カーディナリティも偶数であるベクトルの選択が存在するかどうかを判断することです。 

出力は通常、元のステートメントに応じて二分決定または構築されたサブセットですが、概念的には、そのようなサブセットの実現可能性を判断することに帰着します。 

複雑さの観点から、ベクトルは固定幅または制限された幅のビットマスクとして扱われます。 これは、GF(2) 上の線形代数が正しいフレームワークであることを直ちに示唆します。 単純なサブセット列挙では、すべてをチェックする必要があります。$2^n$サブセット、$n$40 程度。ベクトル次元が$m$、ガウス消去法は、$O(nm^2)$または$O(n^3)$実装に応じたアプローチ。次の場合に許容されます。$n, m$ビットセットの最適化により最大数千になります。 

基底を貪欲に構築してゼロ XOR サブセットを見つけようとするが、消去中にどの元のベクトルがゼロに崩壊するかを追跡しない場合、微妙な失敗ケースが発生します。 たとえば、ベクトルが線形依存しているにもかかわらず、その依存関係が明示的に記録されていない場合、単純な基底構築者は、解が存在しないという誤った結論を下す可能性があります。 

もう 1 つの特殊なケースは、ベクトルがすべて線形独立である場合です。 その場合、唯一の解決策は単純な空の組み合わせであり、これは許可されていないため、空でないサブセット XOR はゼロに等しくなります。 

偶数サイズの制約も別の罠です。 有効な XOR ゼロのサブセットのサイズが奇数である可能性があるため、パリティを強制しない限り、線形代数の問題を直接解決するだけでは十分ではありません。 

## アプローチ

 ブルートフォース戦略では、すべてのサブセットを列挙し、それらの XOR を計算し、両方の条件をチェックします。 これが機能するのは、XOR が結合的であり、サブセットの生成中に実行中の XOR を維持できるためです。 ただし、サブセットの数は増加するにつれて増加します。$2^n$, だから、たとえ$n = 40$、すでに約 1 兆件のオペレーションに達していますが、これは実現可能な限界をはるかに超えています。 

XOR の構造は、GF(2) ではなく線形代数に切り替えることを示唆しています。 各ベクトルはバイナリ行列の行であり、XOR ゼロのサブセットを見つけることは、行間の非自明な線形依存関係を見つけることに対応します。 ガウス消去法により基礎が構築され、依存する行が特定されます。 

重要な観察は、消去中に行が完全にゼロになるたびに、このベクトルが以前のベクトルの組み合わせとして表現できることを示しているということです。 これは、XOR が 0 であるこのベクトルを含むサブセットが存在することも意味します。 したがって、すべてのサブセットを検索する代わりに、そのような依存行を検出し、暗黙的に組み合わせを再構築するだけで済みます。 

パリティ制約は、1 に設定された追加ビットで各ベクトルを拡張することによって処理されます。これにより、最後の座標の XOR もゼロでなければならないため、有効な XOR とゼロの組み合わせには偶数のベクトルが含まれなければならないという問題が変換されます。 これにより、パリティを明示的に追跡しなくても、サブセット サイズが強制的に均等になります。

 ## アルゴリズムのチュートリアル

 各ベクトルをビットマスクとして扱い、1 に初期化された 1 つの追加ビットによって拡張します。 

1. すべてのベクトルに 1 に等しいパリティ ビットを追加します。 これにより、XOR の組み合わせが最後の座標のサブセット サイズのパリティを確実に反映します。 
2. 拡張ベクトルを使用して、GF(2) に対してガウス消去法を実行します。 削除は、最上位の位置から最下位の位置まで少しずつ進みます。 
3. 各ベクトルについて、以前に確立された基底ベクトルを使用してそれを削減しようとします。 ベクトルがゼロになる場合、それは現在の基底に依存します。 
4. 消去中にベクトルがゼロになるたびに、それを有効な依存関係に寄与する候補として記録します。 
5. 削除が完了したら、依存ベクトルが見つかったかどうかを確認します。 存在しない場合は、すべてのベクトルは線形独立であり、有効なサブセットは存在しないと結論付けます。 
6. 依存ベクトルが存在する場合は、消去関係をバックトラックしてゼロと XOR するサブセットを再構築します。 

ステップ 3 が重要である理由は、ガウス消去法が単に基礎を構築するだけではないためです。 元のベクトルの線形結合を暗黙的に定義します。 ベクトルがゼロに減少するということは、そのベクトルが前のベクトルの範囲内にあることを意味します。 

### なぜ効果があるのか

 消去プロセスでは、基底ベクトルの現在のセットがすべての処理されたベクトルとまったく同じ部分空間にまたがるという不変条件が維持されます。 ゼロに減少するベクトルはすべてこのスパン内にあり、これは以前のベクトルの線形結合であることを意味します。 この組み合わせは、XOR が 0 である空ではないサブセットに直接対応します。 追加されたパリティ座標により、最後のビットの XOR はゼロでなければならないため、有効な組み合わせには必ず偶数のベクトルが含まれる必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = [list(map(int, input().split())) for _ in range(n)]

    # append parity bit = 1 to enforce even subset size
    for i in range(n):
        a[i].append(1)

    m += 1

    basis = [-1] * m  # basis column -> row index
    where = [-1] * n  # which basis vector each row becomes

    for i in range(n):
        row = a[i][:]
        for bit in range(m - 1, -1, -1):
            if row[bit] == 0:
                continue
            if basis[bit] == -1:
                basis[bit] = i
                where[i] = bit
                break
            # eliminate
            j = basis[bit]
            for k in range(m):
                row[k] ^= a[j][k]
        else:
            # row became zero
            where[i] = -2  # dependent vector

    dependent = [i for i in range(n) if where[i] == -2]
    if not dependent:
        print("NO")
        return

    # we just output existence; reconstructing subset can be simplified
    print("YES")

if __name__ == "__main__":
    solve()
```実装では行ごとに消去が実行されます。 の`basis`配列は、どの行が各ピボット ビットを現在定義しているかを追跡します。 行が新しいピボットを見つけられず、完全にゼロになると、その行は依存としてマークされます。 これは、自明ではない XOR の組み合わせが存在することを示す重要な信号です。 

追加されたパリティ ビットは、他の座標とまったく同じように扱われます。 最初は常に 1 であるため、有効な XOR とゼロの組み合わせでは偶数の行を選択する必要があります。そうでない場合、最後の座標は 1 のままになります。 

微妙な点の 1 つは、消去ループの順序です。 ビットを上位から下位に反復することで、一貫したピボット選択が保証され、基底表現のあいまいさが回避されます。 XOR 除去では、GF(2) の正確性を維持するために全行 XOR が使用されます。

 ### 例 1

 入力:```
3 2
1 0
1 0
0 1
```パリティ ビットを追加します。 

| 行 | ベクトル (拡張) |
 | --- | --- |
 | 0 | 1 0 1 |
 | 1 | 1 0 1 |
 | 2 | 0 1 1 |

 削除は次のように行われます。 

| ステップ | 行 | アクション | 結果 |
 | --- | --- | --- | --- |
 | 1 | 0 | ピボットになります | 基礎[2]=0 |
 | 2 | 1 | 行 0 → 0 との XOR | 依存 |
 | 3 | 2 | ピボットになります | 基礎[1]=2 |

 行 1 はゼロになり、有効な依存関係を示します。 

これにより、ベクトル 0 と 1 がゼロ XOR サブセットを形成し、パリティ ビットによって均一なサイズが保証されることが確認されます。 

### 例 2

 入力:```
2 2
1 0
0 1
```拡張:

 | 行 | ベクトル |
 | --- | --- |
 | 0 | 1 0 1 |
 | 1 | 0 1 1 |

 両方の行がすぐにピボットになり、削除しても行がゼロになります。 

これは完全な線形独立性を示しているため、空ではない XOR ゼロのサブセットは存在しません。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、入力にゼロ ベクトルが現れる場合です。 その状況では、削除せずにゼロになるため、アルゴリズムはすぐに依存関係として扱います。 たとえば:

 入力:```
1 3
0 0 0
```拡張後、行はすでに 0 に等しいため、依存としてマークされ、答えは YES になります。 この単一ベクトルを含むサブセットは XOR ゼロを持ち、追加されたパリティ ビット構造により偶数のサイズを持つため、これは正しいです。 

もう 1 つのエッジ ケースは、すべてのベクトルが個別の基底ベクトルである場合です。 その場合、すべての行がピボットになり、行が折りたたまれることはありません。 例えば：```
2 2
1 0
0 1
```各行は新しい基準方向を作成するため、依存関係は存在しません。 アルゴリズムは正しく NO を出力し、空でない XOR ゼロのサブセットは線形独立セット内に形成できないという事実と一致します。 

3 番目のケースはベクトルが重複している場合です。 2 つの同一のベクトルが現れた場合、2 番目のベクトルは最初のピボットと XOR を計算してゼロになり、有効な依存関係が直ちに生成されます。 これは、解の最も単純で自明でないトリガーであり、GF(2) の繰り返しが線形依存に直接対応することを確認します。
