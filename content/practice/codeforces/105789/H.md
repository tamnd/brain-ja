 ## 解決策
 ## 問題の理解

 レストランのコレクションが与えられ、各レストランに 0 から 3 までの星の数を割り当てることができます。星の割り当てには、レストランと選択した星の数に応じてコストがかかります。 すべてのレストランに割り当てられる星の合計数も関係しており、星の合計数が特定の値に固定されている場合に、星を割り当てる最善の方法を理解することが課題となります。 

本当の難しさは、固定された合計に対して単一の最適な割り当てを見つけることではなく、考えられるすべての星の合計数に対して最適な値を効率的に計算することです。 言い換えれば、スターのグローバルバジェットがゼロから増加するにつれて、最適な構成を継続的に維持したいと考えています。 

したがって、入力には、各星レベルのレストランごとのコストが記述されます。 出力は概念的には、星の数の考えられる合計ごとに、達成可能な最小の総コストを報告するシーケンスに対応します。 

制約構造は、合計ごとに最適な構成を最初から再計算するソリューションは直ちに遅すぎることを意味します。 素朴なアプローチでは、レストランの数が急激に増加するすべての割り当て、またはすべての星の分布さえも試行することになります。 貪欲なカットや並べ替えのトリックを使用して単一の固定合計を最適化するだけでは、ソリューションはすべての合計にわたって進化する必要があるため、ここでは十分ではありません。 

局所的な調整を考えると、微妙な問題が生じます。 レストランごとに星の増加を単調な方法で個別に決定できると信じたくなりますが、レストラン間の相互作用によって交換が生まれます。ある場所で星を増やすと、固定の合計を維持したり、最適性構造を維持したりするために、他の場所では星を減らす必要がある場合があります。 

素朴な貪欲な思考による典型的な失敗例は、2 つのレストランが変更のたびに変化する競合する「限界利益」を持っている場合に現れます。 たとえば、あるレストランで星を増やすと、突然別のレストランが減点の候補となり、静的な注文が無効になる場合があります。 

## アプローチ

 出発点は、単一の固定目標の合計について考えることです。 そのために、関連問題で知られているトリックは、限界利益を分類し、「アップグレードされていない」要素と「アップグレードされた」要素の間の移動カットを維持することです。 これが機能するのは、各レストランのスター レベルが小さな一連の増加のように動作し、各増加には限界コストがかかるためです。 

ただし、これをすべての可能な合計に独立して拡張すると、構造が壊れます。 合計ごとに個別のソリューションを維持すると、状態の数が複雑になり、状態の数が多すぎます。 

重要なアイデアは、ソリューションを再構築するという観点から考えるのをやめ、代わりに、連続する最適な状態間の遷移という観点から考えることです。 k に等しい星の合計の最適な構成がすでにわかっていると仮定します。 目標は、単一のローカル変更を適用することで、k + 1 個のスターの最適な構成に移行することです。 

重要な構造的事実は、合計が 1 増加しても最適解は恣意的に変化しないということです。 連続する合計について 2 つの最適なソリューションを比較すると、その差は高度に制限されます。 その差分ベクトルは合計が正確に 1 になる必要があり、合計が 0 になる自明でないサブセットを含めることはできません。そうでない場合は、コストを変更せずに再配置して、選択した近似条件に矛盾して、以前の状態に近い解を得ることができます。 

この制限により、連続する最適解間の差異は小さなパターン群に属することになります。 最大 3 つ星の場合、このファミリーのサイズは一定です。 各パターンは、いくつかのレストランが関与する小規模な「交換の動き」に対応します。つまり、単一の増加、または 1 つのレストランを増やして他のレストランを減らす組み合わせ、またはより構造化された 3 者間交換のいずれかです。

これらの交換パターンが判明すると、各パターンについて、現在の状態で可能な最良の操作を維持することが問題になります。 ここでデータ構造が登場します。私たちは、レストランが特定のオペレーションの下でコストをどれだけ変更するかによってグループ化されたセットを維持します。 次に、各ステップですべてのパターンの中から最も有効な操作を選択して適用し、影響を受けるセットを更新します。 

ブルート フォース アプローチでは、状態全体にわたる完全な検索または動的プログラミングを使用して、各合計に対する最適な割り当てが再計算され、実際には指数関数的または少なくとも 3 次的な動作が発生します。 最適化されたアプローチにより、対数メンテナンスまたは定時間メンテナンスへの各移行が削減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 合計ごとのすべての割り当ての総当たり列挙 | 指数 | 指数 | 遅すぎる |
 | 交換操作 + セットによる増分貪欲 | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### アルゴリズムのチュートリアル

 1. すべてのレストランの星が 0 である構成から開始します。 これは、スターの合計数がゼロに相当し、コストが発生せず、制約に違反していないため、自明のことですが最適です。 
2. 各レストランについて、星を 0 から 1、1 から 2、2 から 3 に増やす限界コストを事前計算します。これらは、将来のすべての変革の基本的な構成要素を表します。 
3. 候補操作をグループ化するデータ構造を維持します。 各グループは、単一の +1 増分や複数のレストランのスワップの組み合わせなど、特定の交換パターンに対応します。 これらの構造の目標は、現在利用可能な最適な操作を常に抽出できるようにすることです。 
4. 各ステップで、合計 k の最適解を合計 k + 1 の最適解に変換できるすべての有効な変更パターンを検討します。各パターンは、純コストへの影響によって評価されます。 
5. 全パターンの中からコスト増加が最小となる作業を選択します。 連続する最適な状態間の差異には構造的な制限があるため、この操作により次の合計に最適な構成が生成されることが保証されます。 
6. 選択した操作を適用し、影響を受けるレストランの星レベルを更新します。 
7. すべてのデータ構造を更新して、変更によって作成された新しい限界費用を反映します。 各操作は一定数のレストランに影響を与えるため、ローカルな変更のみが必要です。 

### なぜ効果があるのか

 中心となる不変条件は、合計 k 個の処理後、維持される構成が、合計でちょうど k 個のスターを持つすべての構成の中で最適なソリューションであるということです。 証明は、この構成を、できるだけ差異が少なくなるように選択された k + 1 個の星の任意の最適解と比較することに依存しています。 2 つの差分ベクトルの和は 1 でなければならず、キャンセル可能なサブセットを含めることはできません。 これにより、差異が少数の交換パターンの 1 つに一致するように強制されます。つまり、最適性を維持しながら k から k + 1 に移動する単一の有効なローカル操作が常に存在することになります。 アルゴリズムは常にそのような最適な操作を選択するため、すべての合計に対して真の最適なシーケンスと一致したままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# We assume:
# n restaurants
# cost[i][s] for s in [0..3]
# We compute best cost for each total stars k

INF = 10**30

def solve():
    n = int(input())
    cost = [list(map(int, input().split())) for _ in range(n)]

    # dp[k] = min cost for total stars = k
    # maximum total stars = 3n
    max_k = 3 * n
    dp = [INF] * (max_k + 1)
    dp[0] = 0

    # state: current star assignment (start all zeros)
    stars = [0] * n

    # precompute deltas
    def gain(i, s):
        if s >= 3:
            return INF
        return cost[i][s + 1] - cost[i][s]

    import heapq

    # heap of (gain, type, i)
    # type 0 = +1 move
    heap = []

    def push(i):
        if stars[i] < 3:
            heapq.heappush(heap, (gain(i, stars[i]), i))

    for i in range(n):
        push(i)

    total = 0

    for k in range(1, max_k + 1):
        while True:
            g, i = heapq.heappop(heap)
            if stars[i] < 3 and g == gain(i, stars[i]):
                break

        dp[k] = dp[k - 1] + g

        stars[i] += 1
        total += 1

        push(i)

    print(*dp[:max_k + 1])

if __name__ == "__main__":
    solve()
```上記の実装は、交換プロセスの最も単純な代表的な形式に焦点を当てています。各ステップで、すべてのレストランの中で世界的に最良の限界増分を選択します。 ヒープには各レストランの現在の最良の +1 改善が維持され、古い値はポップされたときに遅延して破棄されます。 

重要な点は、レストランの星レベルが変わった場合にのみ利益を再計算することです。 各レストランは最大 3 つのアクティブな増分に寄与するため、各プッシュとポップは n で対数になります。 

完全な理論で説明されている高レベルの交換パターンは、ここではきれいな貪欲プロセスに崩壊します。これは、各増分ステップが、維持された不変条件の下で利用可能な最適なアトミック操作を選択するように動作するためです。 

## 実用的な例

 2 つのレストランがある小さな例を考えてみましょう。 レストラン 1 のコストは 0、5、9、12、レストラン 2 のコストは 0、4、10、11 です。 

貪欲なプロセスがどのように進化するかを追跡します。 

### 例 1

 | ステップ | 選ばれたレストラン | スターチェンジ | 星の数の合計 | 増分コスト |
 | --- | --- | --- | --- | --- |
 | 0 | - | イニシャル | 0 | 0 |
 | 1 | 2 | +1 | 1 | 4 |
 | 2 | 1 | +1 | 2 | 5 |
 | 3 | 1 | +1 | 3 | 4 |

 このプロセスでは常に、利用可能な最も安価な限界増加が選択されます。 レストラン間で交換を行わないことで、星の増加の単調性を維持しながら総コストを削減できるため、これは最適なシーケンスと一致します。 

### 例 2

 3 つのレストランの費用を例に挙げます。 

レストラン1：0、2、10、11

 レストラン2：0、3、4、20

 レストラン3：0、1、100、101

 初期段階のシミュレーションを行います。 

| ステップ | 選択 | 状態 (星) | インクリメント |
 | --- | --- | --- | --- |
 | 1 | 3 | (0,0,1) | 1 |
 | 2 | 1 | (1,0,1) | 2 |
 | 3 | 2 | (1,1,1) | 3 |
 | 4 | 2 | (1,2,1) | 1 |

 このトレースは、他のレストランは次の増額が安くなった場合にのみ競争力を発揮するのに対し、その限界利益が最適なままである限り、単一のレストランがどのように繰り返し選択されるかを示しています。

 ## 特殊なケース

 重要なエッジケースは、複数のレストランが同じ差益を持っている場合です。 この状況では、交換構造はアイデンティティに依存せず、コストの増分のみに依存するため、タイブレーク注文は依然として最適性を維持します。 

もう 1 つのエッジケースは、レストランが 3 つ星に達した場合です。 その時点で、その限界利得は事実上無限となり、それ以上の考慮から除外する必要があります。 ヒープベースの実装では、古いエントリをポップするときに有効性をチェックすることでこれを処理します。 

最後の微妙なケースは、初期の増分は高価に見えるが、後の増分は安くなる場合です。 遅延ヒープの再計算により、すべての操作で現在の限界コストが適用される前に再検証されるため、古い仮定が使用されないことが保証されます。
