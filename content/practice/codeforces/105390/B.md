 ## 問題の理解

 バイナリ文字列とパラメータが与えられます$k$。 の各値に対して、$k$から$1$まで$\lfloor n/2 \rfloor$、長さのウィンドウに作用する変換を繰り返し適用することができます。$2k$。 ウィンドウは選択したインデックスを中心に配置されます$i$を書き換えます。$k$すぐ左の文字$i$1 つに分割しますが、$k$すぐ右側の文字$i$強制的にゼロが入力されます。 

タスクは、最終的な文字列を明示的に生成することではなく、すべての文字列を計算することです。$k$、結果の文字列が最適な再生の下で達成可能な最大数の文字列を持つために必要なそのような操作の最小数。 

重要な難点は、各操作が単調ではないことです。選択した中心の左側の 1 を増加させますが、同時に右側の 1 を 0 に変えることで破壊します。 これにより、プロセスは単純な「すべてゼロを修正する」問題ではなく、シフト効果に似たものになります。 

制約により許可されるのは、$n$まで$10^5$テストごとと合計$n$テスト全体でも$10^5$。 これにより、線形シミュレーションまたは二次シミュレーションをそれぞれ独立して再計算するアプローチは即座に除外されます。$k$。 平$O(n \log n)$テストケースごとにすべてを繰り返すと遅すぎます$k$。 ソリューションでは、さまざまな値にわたって構造を再利用する必要があります。$k$または、次のように貪欲なスキャンを維持します。$k$つまり、合計入力サイズは線形です。 

微妙なエッジケースは、ビットが交互に配置された文字列から生じます。 たとえば、文字列が次の場合、`010101`、「ゼロを個別に修正するだけ」という素朴な考えは失敗します。ゼロを修正すると、その右側に新しいゼロが作成され、以前の利益が元に戻される可能性があるためです。 もう 1 つの特殊なケースは、すでにすべて 1 である文字列であり、すべての文字列の答えが 0 でなければなりません。$k$、貪欲なプロシージャでは、不必要な操作の実行を回避する必要があります。 

異なる故障モードが境界付近に現れます: 大規模な場合$k$、有効な中心となるインデックスはほとんどなく、多くの位置は対称的に影響を受けることができません。 すべてのインデックスを完全にカバーすると仮定したソリューションは、終わり近くで壊れてしまいます。 

## アプローチ

 ブルートフォース解釈とは、固定のプロセスをシミュレートすることです。$k$。 文字列を繰り返しスキャンし、有益と思われるインデックスを選択し、変換を適用し、改善が不可能になるまで継続します。 それぞれの操作でタッチする$2k$位置なので、単一のシミュレーション ステップは次のようになります。$O(k)$、最悪の場合は適用される可能性があります$O(n)$操作。 これを毎回繰り返すと、$k$複雑さに別の係数を掛けます$n$、合計は次のようになります$O(n^3)$最悪の場合、それは実現可能な限界をはるかに超えています。 

重要な観察は、この操作が「シフトされた修復ツール」のように動作することです。 位置にゼロが表示された場合$j$、それを修正する唯一の方法はセンターを選択することです$i$合間に$[j, j+k-1]$。 そのような選択を行うと、右側のブロックが上書きされます。$i$、新しいゼロが作成される可能性がありますが、重要なことに、それらの新しく作成されたゼロは常に右に押し出されます。 これにより、プロセスに方向性のある構造が与えられます。つまり、ゼロは操作によって右方向にのみ移動でき、任意に再配置することはできません。 

この構造により、貪欲な戦略が可能になります。つまり、文字列を左から右に処理し、まだ解決されていないゼロが見つかった場合は常に、その位置をカバーしながら操作をできるだけ右に配置します。 この選択により、新しいゼロの作成が可能な限り遅延され、以前に処理された位置が安定したままになります。

 ## アルゴリズムのチュートリアル

 それぞれについて$k$、貪欲な修復プロセスをシミュレートします。 

1. ポインタを維持したまま、文字列を左から右にスキャンし始めます。$i$これは、正しいことがまだ保証されていない最初の位置を表します。 
2. ポジションに出会ったとき$i$ゼロが含まれている場合は、それを左側のセグメントでカバーする操作を適用することにします。 すべての有効な中心の中で、可能な限り右端の中心を選択します$c = i + k - 1$, これにより、「ダメージゾーン」が可能な限り右に移動するためです。 
3. 次の操作を適用します。$c$。 これにより位置が強制されます$[c-k+1, c]$なる、そして地位を得る$[c+1, c+k]$ゼロになること。 
4. 操作を適用した後、その位置からスキャンを続行します$c+1$、その点の左側はすべて建設によってすでに完成しているためです。 
5. スキャンが文字列の終わりに達するまで繰り返します。 使用された操作の数がこの問題の答えです$k$。 

重要な考え方は、各操作は左端の未解決のゼロを解決しますが、未解決の作業をさらに右にシフトする可能性があるということです。 エフェクトの境界を常に右に押すことで、以前のセグメントに再度アクセスすることを避けます。 

これが機能する理由は単調性の性質に由来します。選択した操作の左側のセグメントの一部として位置が渡されると、その右側で開始される将来の操作によって再び影響を受けることはありません。 常に右端の有効な中心を選択するため、すべての操作で干渉領域が厳密に前方に押し出され、以前の決定が決して無効にならないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_one(s, n, k):
    s = list(map(int, s))
    ops = 0
    i = 0

    while i < n:
        if s[i] == 1:
            i += 1
            continue

        c = min(n - k - 1, i + k - 1)
        ops += 1

        left_start = c - k + 1
        for j in range(left_start, c + 1):
            if 0 <= j < n:
                s[j] = 1

        for j in range(c + 1, min(n, c + k + 1)):
            s[j] = 0

        i = c + 1

    return ops

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input().strip())
        s = input().strip()

        res = []
        for k in range(1, n // 2 + 1):
            res.append(str(solve_one(s, n, k)))

        print(" ".join(res))

if __name__ == "__main__":
    solve()
```実装は貪欲スキャンを直接エンコードします。 重要な詳細は、センターの選択方法です。`c = min(n - k - 1, i + k - 1)`これにより、中心の有効な範囲を尊重しながら、可能な限り右端に移動することが保証されます。 

また、差分配列を賢く使おうとするのではなく、操作の効果を明示的にシミュレートします。 これは意図的なものです。正確かどうかは 1 と 0 がどのようにローカルに伝播するかを理解することに依存しており、不正確な遅延構造では重複する相互作用を簡単に見逃してしまうからです。 

スキャンジャンプ`i = c + 1`これは、すでに安定化されている左側のセグメントの再処理を防ぐ重要な最適化です。

 ## 特殊なケース

 次のようなすでに均一な文字列の場合`111111`、検出されたすべての位置がすでに安定しているため、スキャンによって操作がトリガーされることはありません。 アルゴリズムはすべての場合に正しくゼロを返します。$k$メインループはゼロのみに作用するためです。 

完全に交互の文字列の場合、すべての操作で新しいゼロが導入され、他のゼロが修正されますが、貪欲な右シフトにより、各パスで少なくとも 1 つの未解決のゼロ領域が解決されます。 ポインタ ジャンプにより、安定化されたプレフィックスを再訪することなく終了が保証されるため、プロセスは引き続き線形パスに収束します。 

小さいとき$k = 1$、操作は 1 つの位置と 1 つの近傍を反転するローカル修正に退化し、アルゴリズムは単純な貪欲なクリーンアップに縮小されます。 一般的に$k = n/2$、有効な中心の数は少なくなりますが、中心の選択が有効な範囲に固定され、範囲外の伝播を防ぐため、同じロジックが依然として適用されます。
