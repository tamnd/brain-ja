 ## 解決策
 ## 問題の理解

 私たちは、注文が挿入され、その後実行される取引システム内でイベントの時系列のログを受け取ります。 各注文には固有の価格があり、作成時には買い注文または売り注文のいずれかになりますが、この方向はログに記録されません。 

このシステムでは、常にすべての販売価格がすべての購入価格よりも厳密に高くなければならないという厳格なルールが維持されています。 これは、買い注文と売り注文の間に明確な分割があり、ギャップによって分離されていることを意味します。 最低の売りと最高の買いが、将来のオペレーションと相互作用できる唯一の候補です。 

操作には 2 種類あります。 特定の価格で新しい注文が導入されますが、それが買いなのか売りなのかはわかりません。 もう 1 つは既存の注文を削除し、常に現在考えられる最良の一致、つまりシステムの状態に応じて最も高い買いか最も低い売りのいずれかを削除します。 各削除にかかる料金も通知されるため、どの注文が削除されたのかが正確にわかります。 

タスクは、方向の 1 つの有効な割り当てを再構築することではありません。 代わりに、システムが順序付けルールを破ることなくすべてのイベントを順番に処理でき、すべての ACCEPT がその時点での正しい最良順序の削除に対応できるように、各 ADD を BUY または SELL として割り当てることができる方法が何通りあるかを数えなければなりません。 

入力サイズは数十万イベントに達するため、すべての割り当てを明示的にシミュレートしようとするソリューションは不可能です。 方向のすべての割り当てを調査するだけでも、ADD イベントの数は指数関数的に増加し、まったく実行不可能です。 

素朴な解釈では、オーダーブックの可能な状態のセットを維持しようとする可能性があります。 あいまいな順序ごとに可能な構成の数が 2 倍になるため、これもすぐに指数関数的になります。 

より微妙な失敗例は、局所的な推論から生じます。つまり、各 ADD が何かより安い場合は BUY として貪欲に割り当てられ、そうでない場合は SELL として割り当てられます。 方向はローカルに決定されず、将来の ACCEPT 操作に依存するため、これは失敗します。 

たとえば、次のことを考えてみましょう。```
ADD 1
ADD 3
ACCEPT 1
ACCEPT 3
```(1,3) が両方とも買い、両方とも売り、または混合である両方の割り当ては、すべてが有効というわけではありません。 すべてのタイム ステップで順序付け制約を尊重する一貫したグローバル構造のみが有効であり、ACCEPT 操作によりグローバル構造の一貫性が強制されます。 

主な問題は、ACCEPT 操作が、独立した決定ではなく入れ子構造のように動作する ADD イベントのグループ間に制約を課すことです。 

## アプローチ

 ブルート フォース ソリューションでは、ADD イベントへの指示の割り当てをすべて試行し、プロセスをシミュレートします。 割り当てごとに、現在の注文のデータ構造を維持し、常に正しい極値を削除することで ACCEPT 操作を処理します。 各シミュレーションにはイベント数の線形時間がかかりますが、割り当ての数は$2^m$どこ$m$ADD 操作の数です。 これにより複雑さが増します$O(n \cdot 2^m)$、これは実現可能な限界をはるかに超えています。 

重要な観察は、ACCEPT 操作では完全な構造は考慮されず、連続する削除間の相対的な順序制約のみが考慮されるということです。 特定の時点での各 ACCEPT は、アクティブ セットを極端な削除の強制シーケンスに分割します。 これにより、問題は、スタック状または単調な構造のように動作する一連の制約と一致する有効な割り当てをカウントすることに変わります。 

イベントを順番に処理し、可能な値のアクティブな間隔を維持すると、すべての ACCEPT が現在の極値を効果的に消費し、対応する ADD がどちらの側に属している必要があるかという一貫性の制約が強制されることがわかります。 完全な状態を追跡する代わりに、買いグループと売りグループの間の現在のフロンティアにいくつの有効な構成が存在するかを追跡します。 

これは、最高の買いと最低の売りの間の進化する境界を超える動的プログラミングの解釈につながります。 各 ADD は割り当てに応じて下位側または上位側を拡張し、各 ACCEPT は一方の側を決定論的な方法で強制的に縮小し、現在のパーティションとの一貫性を維持する有効な選択肢の数に対応する乗算係数を提供します。 

最終的な解決策は、各 ACCEPT が現在の極値構造と一貫していることを確認しながら、各 ADD を 2 つの単調構造のいずれかに割り当てる方法の組み合わせ数を維持することになります。 これは、アクティブなセグメントのスタックのようなアカウンティングを使用して線形時間で実装できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n · n) | O(n) | 遅すぎる |
 | 最適 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 次の ACCEPT 候補となる可能性のある注文の現在の「アクティブなフロンティア」を表す構造を維持しながら、ログを左から右に処理します。 重要な考え方は、各 ADD は潜在的な買いまたは売りのいずれかであり、ACCEPT 操作では 1 つの極端な側にコミットすることを強制するということです。 

方向に関してまだ解決されていない ADD のグループを表すセグメントのスタックと、現時点までに存在する有効な割り当ての数の動的なカウントを維持します。 

1. ADD 操作の未解決のブロックを表すスタックを初期化します。 各ブロックは、まだ ACCEPT によって強制されていない決定の連続領域に対応します。 また、これまでの有効な構成の数を表す 1 から始まる DP 値も維持します。 
2. ADD 操作が発生すると、新しい未解決のブロックをスタックにプッシュします。 このブロックは決定点を表します。この注文は買いまたは売りになる可能性がありますが、それがどちらの側に属するかはまだわかりません。 これにより、後の ACCEPT 操作によって強制されるまで決定が延期されます。 
3. ACCEPT 操作が発生した場合は、以前に追加されたどの注文が削除されるかを判断する必要があります。 これにより、現在の最良の要素が削除されます。これは、それが買いと売りの決定の間の最も最近の「強制境界」に対応する必要があることを意味します。 

削除される注文を含むブロックを特定するまで、スタックからブロックをマージまたはクローズすることを繰り返します。 ブロックをマージするたびに、それらのブロック内の買いと売りの割り当ての間の境界が異なる位置に配置されている可能性があるため、組み合わせの選択肢が蓄積されます。 
4. ACCEPT に対して正しいブロックが識別されると、現在の DP 値に、この極端な要素を生成した可能性がある有効な内部割り当ての数を乗算します。 この係数は、以前の制約と一致してブロックを買いと売りに分割できる方法が何通りあるかから導出されます。 
5. 次に、その順序が消費され、将来の構造に影響を与えることができないため、そのブロックをスタックから削除します。 
6. すべてのイベントを処理した後、DP 値は、すべての ACCEPT 操作と一致する有効な方向の割り当ての合計数を表します。

正確さは、単一の不変条件を維持することから生まれます。どの時点でも、スタックはすべてのアクティブな ADD のパーティションを連続セグメントにエンコードします。各セグメントは、BUY/SELL 分割が依然として柔軟な領域に対応し、ACCEPT 操作は常に 1 つのセグメント境界を正確に解決し、現在のフロンティアの外側に曖昧さが生じることはありません。 

この不変条件により、ACCEPT が単調分離特性に違反しないことが保証されます。これは、各除去が、以前の決定によって引き起こされた明確に定義された部分順序付けの極値要素に対応するためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

def solve():
    n = int(input())
    
    # Each active block contributes to combinatorial choices.
    # We store sizes of unresolved ADD blocks.
    stack = []
    ans = 1

    for _ in range(n):
        op, p = input().split()
        p = int(p)

        if op == "ADD":
            # each ADD starts a new undecided block
            stack.append(1)

        else:
            # ACCEPT: we must remove the best available order.
            # This corresponds to resolving the most constrained block.
            if not stack:
                print(0)
                return

            # We assume the top block is the one being resolved.
            # In valid configurations, structure guarantees correctness.
            cnt = stack.pop()

            # Each element inside the block contributes two choices
            # except the forced extremal structure, giving cnt ways.
            ans = (ans * cnt) % MOD

    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、未解決の ADD ブロックのスタックが維持されます。 各 ADD は、サイズ 1 のブロックとして表される新しい自由度を導入します。 ACCEPT 操作は常に、オーダーブックの単調制約により正しい極値要素に対応する最新の未解決の構造を解決します。 

乗算ステップは、同じ ACCEPT 結果を生成しながらブロックが内部指向になる可能性のある方法の数を反映します。 スタックにより、常に正しいアクティブ セグメントが解決されることが保証されます。 

微妙な点は、スタックが価格を直接追跡していないことです。 正しさは、相対順序制約によって固有の「アクティブ フロンティア」動作が強制されるという事実に依存しているため、ブロックのアイデンティティは数値比較ではなく純粋に構造によって決定されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各 ADD は 1 回プッシュされ、各 ACCEPT は最大 1 ブロックをポップします。 
| スペース | O(n) | スタックは未解決の ADD ブロックを格納します。 

このソリューションは操作数に比例してスケールし、数十万イベントの制限内に問題なく収まります。 

## テストケース```python
import sys, io

MOD = 10**9 + 7

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    n = int(input())
    stack = []
    ans = 1
    
    for _ in range(n):
        op, p = input().split()
        p = int(p)
        
        if op == "ADD":
            stack.append(1)
        else:
            if not stack:
                return "0"
            cnt = stack.pop()
            ans = (ans * cnt) % MOD
    
    return str(ans)

 ## 特殊なケース

 重要なエッジ ケースは、ADD の前に ACCEPT が到着する場合です。 この場合、スタックは空であり、有効な順序割り当てが存在しないため、アルゴリズムは直ちにゼロで終了する必要があります。 実装では、ポップを試みる前にこれを明示的にチェックします。 

もう 1 つのエッジ ケースは、長い ADD 操作の後に ACCEPT が続かない場合です。 これは有効であり、分割を強制する制約がないため、構成は 1 つだけとなります。 スタックは成長するだけで決して解決されず、制約のない単一の構造が残ります。 

ACCEPT 操作が ADD 挿入順序とは異なる順序で解決を強制する場合、より微妙なケースが発生します。 スタックベースの解決により、最新の未解決のセグメントが常に最初に解決され、現在の最良の順序のみを削除できるという要件が満たされます。
