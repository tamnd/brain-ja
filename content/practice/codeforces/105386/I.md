 ## 解決策
 ## 問題の理解

 文字列が与えられ、それを循環的にシフトすることができます。 シフトを選択した後、円内に配置された結果の文字列を確認します。これは、最後の文字が最初の文字に隣接しているとみなされることを意味します。 回転された文字列では、隣接する 2 つの文字が同じにならないように、できるだけ少ない文字を変更する必要があります。 

1 回の操作で、任意の位置を任意の小文字に変更できます。 考えられるすべての回転について、回転された文字列を「適切」にするために必要な変更の数を測定し、最も少ない変更数を与える回転を選択します。 

文字列の長さはすべてのテスト ケースで最大 500,000 になる可能性があるため、合計サイズが 2 次のものは失敗します。 n 回転あるため、1 回転あたりの線形時間さえも不可能です。 これにより、シフトごとに答えを最初から再計算することが直ちに排除されます。 

回転によって弦の難易度が変わると考えるのは素朴な誤解です。 たとえば、文字列を別の位置で切断すると、同じ文字が途切れたり、長く続いたりする可能性があり、その結果、答えが変わる可能性があると予想する人もいるかもしれません。 ただし、隣接関係をチェックするときに文字列は循環しているとみなされるため、すべてのローテーションで同じ循環隣接構造が保持され、インデックスが再作成されるだけです。 

一般的なエッジ ケースは、「aaaaaa」のような完全に均一な文字列です。 すべてのローテーションは同じように見えます。最良の戦略は、サイクルに沿って交互に変更することです。 もう 1 つは、「aaabbbccc」のような交互の長いブロックで構成される文字列で、各ブロックが独立してコストに寄与します。 

## アプローチ

 ブルートフォース戦略では、すべてのローテーションを試します。 シフトごとに、隣接する 2 つの文字が一致しないようにするために必要な最小限の変更数を計算します。 固定文字列についてこれを計算する直接的な方法は、各位置に隣接する文字とは異なる新しい文字を割り当てる必要があるサイクル グラフとして表示することです。 動的プログラミングを使用してこれを最適化しようとしても、各回転には依然として線形処理が必要となり、合計作業量は O(n^2) になります。 

重要な観察は、文字列を回転しても、位置間の循環隣接関係が変化しないことです。 サイクル内の隣接ペアのすべては、インデックスがシフトされただけで、回転後も隣接ペアのままになります。 これは、「等しい隣接ペアが発生する場所」の構造が回転を通じて不変であることを意味します。 

回転を修正すると、問題は局所的なものになります。唯一重要な情報は、等しい文字がサイクルに沿ってどのように連続セグメントを形成するかということです。 長さ L の同一文字のセグメント内で、隣接する 2 つの文字が等しくならないように、それらの約半分を変更するのが最善の戦略です。 これは、回転とは無関係に L に比例するコストに寄与します。 

回転によってこれらの周期的な実行は変更されないため、答えはすべてのシフトで同じになります。 したがって、元の巡回文字列に対してコストを計算する必要があるのは 1 回だけです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべての回転にわたるブルート フォース | O(n²) | お(1) | 遅すぎる |
 | 周期的な実行での単一パス | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列を循環として扱い、連続する同一文字の最大セグメントに圧縮します。

1. 文字列をトラバースし、概念的にサイクルにマージします。つまり、最後の文字と最初の文字も隣接していると見なされます。 それらが等しい場合、それらは同じランに属しているため、ランの境界を分割するのではなく、それに応じて回転させます。 
2. この循環的な意味での同一文字の最大ランをすべて特定します。 各ランにはある程度の長さ L があります。 
3. 実行ごとに、隣接する 2 つの文字が等しくないように変更する必要がある文字の数を計算します。 均一な実行内では、他のすべてのキャラクターを変更せずに維持できるため、実行によって寄与されるコストは Floor(L / 2) になります。 
4. すべての実行にわたるこれらの寄与を合計して、最終的な答えを取得します。 

唯一の微妙な部分は、循環マージを正しく処理することです。 最初と最後の文字が等しい場合、それらは同じ実行に属し、寄与を計算する前にマージする必要があります。 そうしないと、1 つの周期的な実行を 2 つの別個の線形実行として誤って扱うことになり、必要な変更が過小評価されてしまいます。 

### なぜ効果があるのか

 このアルゴリズムは、2 つの同一の文字が隣接する場合にのみ違反が発生するという意味で、すべての隣接制約が独立しているという事実に基づいています。 等しい文字の各最大ブロックは、制約が密集した孤立領域を形成し、最適な修復戦略はそのブロックに局所的です。 回転によってどの位置が巡回近傍と等しいかは変わらないため、ランへの分解とその長さは変化せず、すべての回転のコストが固定されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve(s: str) -> int:
    n = len(s)
    if n == 1:
        return 0

    # build cyclic runs
    runs = []

    i = 0
    while i < n:
        j = i + 1
        while j < n and s[j] == s[i]:
            j += 1
        runs.append(j - i)
        i = j

    # merge first and last run if cyclicly connected
    if len(runs) > 1 and s[0] == s[-1]:
        runs[0] += runs[-1]
        runs.pop()

    # compute cost
    ans = 0
    for L in runs:
        ans += L // 2
    return ans

def main():
    t = int(input())
    for _ in range(t):
        s = input().strip()
        print(solve(s))

if __name__ == "__main__":
    main()
```この実装では、まず文字列が連続する等しい文字のランに圧縮されます。 これは 1 回のスキャンで実行されるため、直線的な時間で実行されます。 唯一の重要な手順は、最初と最後の実行が同じ文字を共有する場合にマージすることです。これにより、文字列の循環的な性質が確実に尊重されます。 

ランが形成されると、それぞれの長さの半分が切り捨てられて答えに寄与します。 これは、均一セグメント内の隣接する重複を修正するための最適な戦略と直接一致します。 

## 実用的な例

 ### 例 1

 検討してください`s = "aaabbaa"`。 

まず線形ランを形成します。`"aaa"`、`"bb"`、`"aa"`。 最初と最後の文字は両方とも`'a'`、最初と最後の実行をマージします。`"aaaaa"`そして`"bb"`。 

| ステップ | 走る | アクション |
 | --- | --- | --- |
 | イニシャル | [3、2、2] | 線形セグメンテーション |
 | マージ | [5、2] | 最初と最後にマージされました |
 | コスト | 2 + 1 | 床(5/2) + 床(2/2) |

 最終的な答えは 3 です。 

これは、循環マージが不可欠であることを示しています。 そうしないと、構造が間違って扱われてしまいます。 

### 例 2

 検討してください`s = "abcde"`。 

すべての文字は個別であるため、すべての文字の長さは 1 になります。 

| ステップ | 走る | アクション |
 | --- | --- | --- |
 | イニシャル | [1,1,1,1,1] | 各文字を分離 |
 | マージ | [1,1,1,1,1] | マージは必要ありません |
 | コスト | 0 | 全フロア(1/2) |

 文字列はすでに有効であるため、変更する必要はありません。 

これは、隣接関係違反が存在しない場合、アルゴリズムが自然にゼロを返すことを示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    def solve(s: str) -> int:
        n = len(s)
        if n == 1:
            return 0

        runs = []
        i = 0
        while i < n:
            j = i + 1
            while j < n and s[j] == s[i]:
                j += 1
            runs.append(j - i)
            i = j

        if len(runs) > 1 and s[0] == s[-1]:
            runs[0] += runs[-1]
            runs.pop()

        return sum(x // 2 for x in runs)

    t = int(sys.stdin.readline())
    out = []
    for _ in range(t):
        s = sys.stdin.readline().strip()
        out.append(str(solve(s)))
    return "\n".join(out)

# provided + basic cases
assert run("1\nabccbbbbd\n") == "3"
assert run("1\nabcde\n") == "0"

# single char
assert run("1\nx\n") == "0"

# all same
assert run("1\naaaaa\n") == "2"

# alternating
assert run("1\nababab\n") == "0"

 | --- | --- | --- |
 | 単一の文字 | 0 | 最小境界の場合 |
 | すべて等しい | 2 | 循環実行の処理 |

 ## 特殊なケース

 単一文字の文字列は、隣接するペアがないためすでに自明に有効であり、長さ 1 の単一のランがあるため、アルゴリズムは正しく 0 を返します。 

次のような完全に均一な循環文字列`"aaaaa"`循環隣接性を考慮した後、1 つのマージされた実行を形成します。 アルゴリズムはエンドポイントをマージし、floor(5/2) を計算し、正しく 2 を生成します。これは、循環マージを忘れると誤って 2 つの別個の実行が生成され、寄与分が過小カウントまたは誤カウントされるケースです。 

のような文字列`"ababa"`サイクル内に等しい隣接ペアがありません。 ラン分解では長さ 1 のランのみが生成されるため、すべての寄与はゼロとなり、変更が必要ないという事実と一致します。
