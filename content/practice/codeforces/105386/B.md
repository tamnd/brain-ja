 ## 解決策
 ## 問題の理解

 いくつかのコンテストが並行して開催されています。 各コンテストにはすでにある程度の数の参加チームがあり、必要に応じて追加のチームのプールをこれらのコンテストに分散させることができます。 

各コンテストでは、そのコンテストのチームの総数が固定値の倍数に達するたびに、非常に簡単な方法で金メダルが授与されます。$k$、そのコンテストは金メダルを1つ生み出しました。 同様に、コンテストが次のような結果になった場合、$t$チーム、貢献します$\lfloor t / k \rfloor$メダル。 

初期構成から始めます$a_i$各コンテストのチーム、そしてあなたも$m$コンテスト間で任意に割り当てることができる追加チーム。 すべてのチームはどこかに割り当てられる必要があり、割り当てごとに、対応するコンテストのチーム数が 1 つずつ増えます。 

タスクはすべてを配布することです$m$すべてのコンテストの合計メダル数を最大化する方法でチームを強化します。 

制約は非常に直接的な意味で重要です。 コンテストは最大 100 個ありますが、追加チームの数は$m$そして初期カウント$a_i$どちらも次のように大きくすることができます$10^9$。 単一のテスト ケースでも数十億の操作が必要になる可能性があるため、チームごとにプロセスをシミュレートする戦略は即座に除外されます。 ソリューションは、個々の割り当てではなく、チームの集合的なブロックで推論することによって機能する必要があります。 

追加のすべてのチームが個別に局所的に最適な何かを提供すると仮定すると、素朴な貪欲な思考による微妙な失敗例が現れます。 たとえば、チームを 1 つ追加しても、コンテストのメダル数がすぐに増えるわけではありませんが、慎重に選択した追加順序により、しきい値を「完了」し、メダルのロックを解除できます。 単一チームごとの当面の利益のみに注目すると、次の複数チームに向けた進歩が重要であるという事実を見落とします。 

もう 1 つの落とし穴は、いくつかのチームを分散した後、残りのチームを一律に扱えると想定していることです。 の倍数に一致しないコンテストがまだある場合、これは不正確になります。$k$、異なるコンテスト内での部分的な進歩が将来のメダルに重要な影響を与えるためです。 

## アプローチ

 ブルートフォースのアイデアは単純です。各ステップで、残りのチームの 1 つをいずれかのコンテストに割り当ててみて、メダルの総数を再計算し、すべてのチームが割り当てられるまで再帰的または反復的に続行します。 これは、考えられるすべての分布を調査するため、正しいです。 ただし、それぞれの$m$チームは最大で$n$選択肢が増えるため、検索スペースは次のように拡大します$n^m$、これは、 の小さな値であっても完全に実行不可能です。$m$。 

重要な観察は、メダルは各コンテストが次の倍数を通過した回数のみに依存するということです。$k$。 これは、各コンテストの状態がその剰余モジュロによって完全に捕捉されることを意味します。$k$、そしてすべての有用なアクションは、次の倍数に到達するために残りを終了するか、サイズのブロック全体を提供するかのいずれかです$k$その後。 

これにより、問題はチームごとの決定からメダルごとの増分に変わります。 各コンテストは、+1 メダルを獲得する「機会」を提供するものと考えることができ、各コンテストには追加のチームで測定されるコストがかかります。 次に、最も安価な機会を最初に選択したいと考えますが、コンテストごとの最初の調整の後、残りの利益はすべて均一に動作することもわかります。 

この構造により、ソリューションを 2 つのフェーズに分けることができます。最初にすべての「残りの修正」を最適化し、次に残りのチームを一括して処理します。

 ## アルゴリズムのチュートリアル

 まず問題を「すでに獲得できるメダルの数」と「追加のチームを使用して追加のメダルをどれだけ強制できるか」に変換します。 

各コンテスト$i$最初は貢献する$\lfloor a_i / k \rfloor$メダルはすでに複数完成しているため、すぐに獲得できます。 

ここで、各コンテスト内に残っている構造に焦点を当てます。 させて$r_i = a_i \bmod k$。 いくつかのチームを追加した場合、メダル数を効率的に増やす唯一の方法は、コンテストを次の倍数まで進めることです。$k$。 それには正確に必要です$k - r_i$チームの場合$r_i \neq 0$、 そして$k$チームの場合$r_i = 0$なぜなら、正確に倍数にあるということは、次の倍数に「近い」という意味ではないからです。 

したがって、各コンテストは 1 つの有意義なアップグレードを提供します。コストを支払います。$c_i$チームは次の複数の境界を完了することで +1 メダルを獲得します。 

私たちはこれらのコストを分類し、十分なチームがある限り貪欲にコストを受け取ります。 

これらのアップグレード後、選択されたすべてのコンテストは、次の倍数と完全に一致するようになりました。$k$。 残りのコンテストはまだ固定された構造を持っていますが、残りの$m$チームはサイズの完全なブロックを通じてのみ対話するようになりました$k$、複数のコンテストに分散することは、それらを最適にグループ化することよりも優れたパフォーマンスを発揮することはできません。 残りのチームから得られる最善の結果は、次のとおりです。$\lfloor m_{\text{left}} / k \rfloor$追加のメダル。 

これにより、クリーンなプロセスが実現します。 

1. 初期メダルを次のように計算します。$\sum \lfloor a_i / k \rfloor$。 
2. コンテストごとに、次の倍数に到達するためのコストを計算します。$c_i$。 
3. コストを整理し、貪欲に支出する$m$彼らの上で。 
4. 残りの貢献を追加する$\lfloor m / k \rfloor$。 

それが機能する理由は、状態の構造的な圧縮にあります。 すべてのコンテストには、(次の倍数に到達するための) 不均一な遷移が 1 つだけあり、その後、将来のすべてのゲインは同じサイズのブロックで同じように動作します。$k$。 これにより、すべての非対称性が最大でも次の時点で解消されることが保証されます。$n$決定し、残りは一律になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        m = int(input())

        base = 0
        costs = []

        for x in a:
            base += x // k
            r = x % k
            if r == 0:
                costs.append(k)
            else:
                costs.append(k - r)

        costs.sort()

        extra = 0
        for c in costs:
            if m < c:
                break
            m -= c
            extra += 1

        extra += m // k
        print(base + extra)

if __name__ == "__main__":
    solve()
```コードはまず、初期設定から保証されたメダル貢献度を抽出します。 次に、各コンテストの「完了コスト」のリストを作成します。これは、そのコンテストを次の倍数まで進めるために必要なチームの数を意味します。$k$。 これらのコストを分類することで、チームを常に最も効率的なアップグレードに最初に費やすことができます。 

手頃な価格のアップグレードを使い果たした後、残りのチームは整数除算を使用して一括処理されます。$k$、すべてのコンテストが揃った後は、完全なブロックのみが追加のメダルを提供できるためです。 

ここでよくある間違いは、残りのゼロをコストゼロとして扱うことで、誤って無料のメダルを許可してしまいます。 そのため、コードでは明示的にコストを割り当てます。$k$その場合。 

## 実用的な例

 ### 例 1

 検討してください$k = 5$、とのコンテスト$a = [4, 6]$、 そして$m = 6$。 

初期メダルは以下の通りです。 

- 4 貢献 0
 - 6 が 1 に貢献

 したがって、底 = 1

 現在の費用は次のとおりです。 

- コンテスト 1: 5 に到達するには 1 チームが必要 → コスト 1
 - コンテスト 2: 10 チームに到達するには 4 チームが必要 → コスト 4

 コストを並べ替えます: [1, 4]

 | ステップ | メートル | アクション | 追加のメダル |
 | --- | --- | --- | --- |
 | 0 | 6 | 開始 | 0 |
 | 1 | 5 | コスト 1 を取る | 1 |
 | 2 | 1 | コスト4かかりますか？ いいえ | 1 |

 残りは m = 5 ですか? 実際には最初のステップの後は m=5 ですが、2 回目の試行以降は 4 を取ることができないため、m=5 になります。 

残りのメダル = 5 // 5 = 1

 合計 = 基本 1 + 追加 2 = 3

 これは、残ったチームが均等なブロックを形成する一方で、早期完了がどのように優先されるかを示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    T = int(input())
    out = []
    for _ in range(T):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))
        m = int(input())

        base = 0
        costs = []
        for x in a:
            base += x // k
            r = x % k
            costs.append(k if r == 0 else k - r)

        costs.sort()
        extra = 0
        for c in costs:
            if m < c:
                break
            m -= c
            extra += 1
        extra += m // k
        out.append(str(base + extra))

    return "\n".join(out)

# minimum size
assert run("1\n1 5\n0\n3\n") == "0"

# already optimal alignment
assert run("1\n2 3\n3 6\n5\n") == "2"

# all equal values
assert run("1\n3 4\n1 1 1\n12\n") == run("1\n3 4\n1 1 1\n12\n")

# k = 1 edge case
assert run("1\n2 1\n10 20\n100\n") == "130"

# tight remainder interaction
assert run("1\n2 5\n4 9\n3\n") == "3"

 ## 特殊なケース

 主なエッジケースは次のような場合です$k = 1$。 この状況では、どのチームも常にメダルに貢献するため、全体の最適化は単純な加算に集約されます。 すべてのコストが 1 になり、追加のチームはすべて最終部門を通じて直接貢献するため、アルゴリズムはこれを自然に処理します。 

もう 1 つのエッジ ケースは、コンテストがすでに倍数に達している場合です。$k$。 コストは次のように設定されています$k$、ゼロではないため、誤った無料アップグレードが防止されます。 アルゴリズムは、このようなコンテストを、次のゲインの前に完全なブロックが必要であるものとして正しく処理します。 

最後の微妙なケースは、残りのチームがすべてアップグレードを完了するのに不十分な場合に発生します。 その状況では、ソートされたコスト ループは早期に終了し、サイズの完全なブロックのみが終了します。$k$これは、部分的な進歩には価値がないことを正しく反映しています。
