 ## 解決策
 ## 問題の理解

 私たちは、プログラミング コンテストで受理された提出物を時系列で処理します。 各提出物はチームと問題に属しており、すべての提出物はすでに成功したものであるため、すべての行が正しい解決策の試みを表します。 

提出物ごとに、バルーンが授与されるかどうかを決定する必要があります。 風船は、チームが初めて問題を解決した場合にのみ授与されます。 ただし、タイミングが重要です。 コンテストのフリーズ時間 240 分の前に、チームが最初に問題を解決すると必ず風船が得られます。 フリーズ後、最初のソルブでバルーンを獲得できるのは、そのチームがこれまでに受け取ったバルーンの数が合計 3 個未満の場合のみです。 

したがって、タスクは、チームおよび問題ごとに最初の解決策を追跡するだけでなく、各チームがすでに受け取った風船の数の実行カウントを維持し、提出時間に応じて条件付きルールを適用することも必要です。 

入力サイズは最大 5000 の提出物で、最大 410 のチームと 13 の問題が含まれます。 これは十分に小さいため、チームごとの状態を配列で快適に維持できます。 以前の送信をクエリごとに素朴にチェックするソリューションは、実装が非効率な場合にのみ遅すぎますが、5000 を超える二次スキャンでもまだ許容可能です。 本当の懸念は、漸近的な制限ではなく、クリーンな状態の追跡です。 

微妙な失敗のケースは、同じチームおよび問題に対して重複して承認された提出物から発生します。 バルーン ロジックでは、最初に受け入れられた送信のみが重要になります。 

たとえば、チームが時間 10 に問題 2 を解決し、時間 50 に再度問題を解決した場合、最初の問題のみを考慮する必要があります。 解決された状態を追跡しない単純なアプローチでは、誤って複数のバルーンが付与されてしまいます。 

もう 1 つの特殊なケースは、フリーズ時間の後です。 チームが時刻 240 より前にすでに 3 つの風船を持っており、240 以降に新しい問題を解くとします。最初の解決であっても、風船は与えられません。 不注意な実装でも、最初の解決策であるため、それが与えられる可能性があります。 

最後に、提出物はすでに時間順に並べ替えられているため、順序が重要になります。 これにより、再並べ替えや先読みを行わずに、順次処理し、正確な増分状態を維持できることが保証されます。 

## アプローチ

 直接的なアプローチは、各提出物を個別に処理し、提出物ごとに以前のすべての提出物をスキャンして、チームがその問題を解決するのが初めてかどうかを判断することです。 そうであれば、以前の出力をスキャンして、チームがこれまでに受け取った風船の数を数えます。 これが機能するのは、各ステップで必要な履歴をすべて明示的に再構築するためです。 

ただし、n 個の送信ごとに、最大 n 個の以前のエントリをスキャンする必要があるため、O(n^2) 時間がかかります。 n が最大 5,000 の場合、これは約 2,500 万チェックであり、これは境界線ですが、より単純な構造が存在することを考えると不要です。 さらに重要なのは、このアプローチは解決された状態とバルーン カウントの再計算を繰り返し行うため、正しく実装するのが難しいことです。 

重要な観察は、履歴を再計算する必要がまったくないということです。 私たちが常に知る必要があるのは 2 つのことだけです。それは、チームが特定の問題をすでに解決したかどうか、もう 1 つはそのチームがすでに受け取った風船の数です。 どちらも増分的に保存できます。 

問題がそのチームによってすでに解決されているかどうかを示す、チームおよび問題のペアごとのブール状態を維持します。 また、これまでに獲得した風船のチームごとのカウンターも維持しています。 その後、これらの構造をチェックして更新することで、各送信が一定時間で処理されます。 

これにより、問題全体がストリーミング シミュレーションに集約されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n^2) | O(n) | 遅すぎて不必要 |
 | 最適 | O(n) | O(チーム × 問題) | 承認済み |

 ## アルゴリズムのチュートリアル

 提出された内容を順番に 1 つずつ処理します。 

1. 2D ブール配列を初期化する`solved[team][problem]`すべてのチームと問題について偽として扱われます。 これは、チームが以前に特定の問題をすでに解決したかどうかを追跡します。 
2. 配列を初期化する`balloons[team] = 0`すべてのチームのために。 これには、各チームがこれまでに受け取った風船の数が保存されます。 
3. 提出ごとに`(a, b, c)`順序としては、まず次のことを確認してください。`solved[a][b]`それはすでに真実です。 true の場合、これは繰り返しの解決であり、バルーンは生成されないため、すぐに 0 が出力されます。 
4. 偽の場合は、マークを付けます。`solved[a][b] = true`なぜなら、チームがこの問題を解決するのはこれが初めてだからです。 
5.提出時間が過ぎた場合`c < 240`、常にバルーンを授与するため、増分します`balloons[a]`問題IDを出力します`b`。 
6.提出時間が過ぎた場合`c >= 240`、チェックします`balloons[a] < 3`。 true の場合、インクリメントします`balloons[a]`そして出力`b`。 それ以外の場合は 0 を出力します。 

重要な設計上の選択は、最初に発生したときにすぐに解決済みの状態を更新し、その問題に対する今後のすべての送信が時間に関係なく確実に無視されるようにすることです。 

なぜ機能するのか: ストリーム処理のどの時点でも、`solved[a][b]`は、そのペアの最初の解決イベントがシーケンスの早い段階ですでに発生したかどうかを正確に表します。 時系列で処理するため、この状態は実際のコンテストの進行と一致します。 の`balloons[a]`カウンタは、付与ルールを満たす、以前に受け入れられた最初のソルブの数を正確に反映するため、履歴を再計算することなくフリーズ条件をローカルに評価できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    solved = [[False] * 14 for _ in range(411)]
    balloons = [0] * 411
    
    out = []
    
    for _ in range(n):
        a, b, c = map(int, input().split())
        
        if solved[a][b]:
            out.append("0")
            continue
        
        solved[a][b] = True
        
        if c < 240:
            balloons[a] += 1
            out.append(str(b))
        else:
            if balloons[a] < 3:
                balloons[a] += 1
                out.append(str(b))
            else:
                out.append("0")
    
    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装は、前述のステート マシンを直接反映しています。 の`solved`テーブルのサイズは、問題の制約 (最大 410 チームと 13 個の問題) を使用して設定されるため、インデックス付けでのオフバイ 1 の問題を避けるために、少し多めに割り当てます。 の`balloons`配列はチームごとの合計を追跡します。 

微妙な点は、`solved[a][b] = True`最初のソルブを検出したらすぐに、時間ロジックを適用する前に。 これにより、時間条件が異なる場合でも、繰り返しの提出が誤って授与ロジックに再入力されることがなくなります。 

また、出力をリストに蓄積し、一度印刷することで、繰り返しの I/O オーバーヘッドを回避します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 送信ごとに、配列の定数チェックと更新がトリガーされます。 
| スペース | O(チーム × 問題) | 解決された状態とチームごとのカウンターを格納するブール テーブル |

 制約が十分に小さいため、直接シミュレーションは簡単に高速になります。 最大 5000 件の送信では、各操作が O(1) であるため、Python でもこれを快適に処理できます。

 ## 特殊なケース

 フリーズ境界をまたいで解決する難しいケースが繰り返されます。 チームがフリーズ前に問題を解決し、フリーズ後に再度問題を解決したとします。 

入力:```
1 1 100
1 1 250
```最初の提出セット`solved[1][1] = True`そして風船をプレゼントします。 2 番目の送信はすぐに解決済みチェックに失敗し、0 を出力します。問題定義と一致する最初の解決条件がすでに破られているため、フリーズ ルールはまったく考慮されません。 

もう 1 つのエッジ ケースは、フリーズ時にちょうどバルーン制限に達することです。```
1 1 10
1 2 20
1 3 30
1 4 240
```3 回のフリーズ前の解決の後、`balloons[1] = 3`。 4 番目の送信はちょうど 240 で行われるため、フリーズ後の状態になります。 条件では厳密に 3 つ未満のバルーンが必要であるため、バルーンは授与されません。 実装チェック`balloons[a] < 3`なので、出力は正しく 0 になります。
