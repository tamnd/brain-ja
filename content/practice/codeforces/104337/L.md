 ## 解決策
 ## 問題の理解

 エッジで接続された点の直線が与えられます。 各エッジは白または黒のいずれかに色付けされ、各文字が連続する点間のエッジの色を表すバイナリ文字列としてエンコードされます。 したがって、長さ n の文字列は、行内の n+1 個の点を表します。 

2 人のプレイヤーが交互にターンします。 ターンでは、プレイヤーは内側に少なくとも 1 つのエッジがある連続したポイントのセグメントを選択します。また、内側のエッジがすべて対戦相手に禁止されている 1 色のセグメントのみを選択できます。 Bon Bon は、内部エッジに黒いエッジが含まれていないセグメントのみを選択できます。つまり、選択したセグメントは完全に白いエッジの領域内に存在する必要があります。 対称的に、Lyra は白いエッジのないセグメントのみを選択できます。 このようなセグメントを選択した後、選択したすべての点が入射エッジとともに削除され、残りの点は 1 つのブロックとして接続されたままでなければなりません。つまり、削除によって残りの構造を複数の切断されたコンポーネントに分割することはできません。 

プレイヤーは有効な手を打てなかった場合に負けます。 

問題は、先に動くボンボンが最適なプレーで勝利を強要できるかどうかだ。 

入力サイズは非常に大きく、テスト ケースは最大 100 万、テスト全体の文字列の合計長は最大 200 万です。 これにより、テストごとの二次推論や手のシミュレーションが直ちに除外されます。 テストごとに線形であっても、慎重に償却するか、直接組み合わせて観察する必要があります。 どのようなソリューションでも、各テスト ケースを基本的に 1 回のスキャンまたは定数時間推論に減らす必要があります。 

主な落とし穴は、これがセグメントに関する単純な公平なゲームであると想定していることです。 「削除後に分割しない」という制約が重要な点です。 単純にセグメントを削除して接続性をチェックする単純なシミュレーションは、接続性がローカルな合法性だけでなくグローバルな構造に依存するため、小さな入力でも失敗します。 

## アプローチ

 ブルートフォースアプローチでは、考えられるすべての動きをシミュレートしようとします。 指定された構成から、Bon Bon のすべての有効なセグメントを列挙し、次に Lyra について、結果の状態を再帰的に探索します。 各移動では、セグメントに白いエッジのみが含まれているか、黒いエッジのみが含まれているかを確認し、セグメントを削除しても残りのグラフが切断されないことを確認する必要があります。 

最悪の場合、分岐係数はすでに O(n) であり、深さも O(n) になる可能性があり、指数関数的に複雑になります。 状態空間はどのポイントが残っているか、および削除後に非ローカルな方法で変化する正確な隣接構造に依存するため、メモ化さえ役に立ちません。 

重要な観察は、ゲームが実際には除去の完全な形状に依存しているのではなく、接続を切断することなく「純粋な色のブロック」をどれだけ選択できるかにのみ依存しているということです。 移動により、単色領域内の連続した間隔が効果的に削除されますが、残りのグラフが接続されたままであるという制約により、移動は 1 つのアクティブ セグメントを最大 2 つのアクティブ セグメントに分割するような動作を強制され、最適な再生は同じ色の連続にわたる単純なパリティのような構造に崩壊します。 

文字列を同一の文字の最大ランに圧縮すると、各ランは独立した選択に寄与できる単位のように動作します。 ゲームは、プレイヤーが少なくとも 1 つの手を強制できる「アクティブな決定ポイント」となるランが何回あるかを数えるというものです。 勝者は、これらの有効な手の合計数が奇数かどうかだけで決まります。 

これにより、問題は実行圧縮とパリティ計算を伴う線形スキャンに変わります。

 ## アルゴリズムのチュートリアル

 バイナリ文字列をスキャンし、同じ文字の連続したセグメントにグループ化することで、各テスト ケースを削減します。

1. 文字が変更される回数を数えながら、文字列を左から右にたどります。 同一ビットの最大セグメントはそれぞれ 1 ランです。 これにより、文字列が 000…0111…1000… のような交互のブロックに分割されます。 
2. そのような実行の数を計算します。 この数は、結果を決定するために重要な唯一の数量です。 
3. ランカウントの同等性に基づいて勝者を決定します。 出た数が奇数の場合はボンボンの勝ちです。 互角の場合はライラが勝ちます。 

パリティが現れる理由は、各移動が、色の交互の 1 つの「レイヤー」を消費することに対応する連続した構造を効果的に削除するためです。 プレイヤーは開始動作を除いて対称的であるため、ゲームはセグメントの直線チェーン上の標準的な交互除去に縮小されます。これは、ランに関するチェーンの長さが奇数であるか偶数であるかによって完全に特徴付けられます。 

### なぜ効果があるのか

 不変条件は、有効な移動の後でも、残りの構造が交互の色のランのシーケンスとして表現でき、移動するたびにランの数が 1 つだけ減少するということです。 有効なセグメントはすべて単色領域内に完全に存在し、その削除により実行間のちょうど 1 つの境界が崩壊するため、どの移動もこの縮小をスキップすることはできません。 プレイヤーは交互に行動し、ターン順序を除いて両方のパワーが同じであるため、ゲームは実行回数と同じサイズの山から 1 つのユニットを繰り返し取り除くことと同じになります。 山のサイズが奇数の場合、最初のプレーヤーが勝ちます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        s = input().strip()
        if not s:
            out.append("NO")
            continue
        
        runs = 1
        for i in range(1, len(s)):
            if s[i] != s[i - 1]:
                runs += 1
        
        if runs % 2 == 1:
            out.append("YES")
        else:
            out.append("NO")
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```コードは各テスト ケースを個別に処理します。 キー ループは、連続する文字間の遷移をカウントします。これにより、明示的に保存せずに実行数が直接得られます。 空文字列ガードは防御的ですが、制約がある場合は厳密に必要というわけではありません。 

その後、パリティ チェックによって決定が行われます。 追加のデータ構造は必要ありません。これは、合計入力サイズの制約を考慮すると不可欠です。 

## 実用的な例

 簡単な入力を考えてみましょう`0011`。 

実行と決定を追跡します。 

| 私 | s[i] | s[i-1] | 走る |
 | --- | --- | --- | --- |
 | 0 | 0 | - | 1 |
 | 1 | 0 | 0 | 1 |
 | 2 | 1 | 0 | 2 |
 | 3 | 1 | 1 | 2 |

 実行が 2 回あるため、出力は NO になります。 

これは、ゲームを対称的な応答にペアにすることができるため、偶数の長さの交互構造が 2 番目のプレーヤーに有利であることを示しています。 

ここで考えてみましょう`010`。 

| 私 | s[i] | s[i-1] | 走る |
 | --- | --- | --- | --- |
 | 0 | 0 | - | 1 |
 | 1 | 1 | 0 | 2 |
 | 2 | 0 | 1 | 3 |

 実行が 3 回あるため、出力は YES になります。 

これは、追加の交互セグメントが最初のプレーヤーに最終的な比類のない手を与え、パリティ ルールを裏付けることを示しています。

 ## 特殊なケース

 次のような遷移のない文字列`000000`実行は 1 回だけ行われます。 実行カウントが 1 であるため、アルゴリズムは YES を返します。これは、最初のプレーヤーが 1 つの決定的な動きを持っていることを意味します。 

次のような完全に交互の文字列`0101010`多くのランを生み出します。 キャラクターが反転するたびにランカウントが 1 つずつ増加し、最終的なパリティによって勝者が直接決まります。 このアルゴリズムは、特別なケースを使用せずに、これを 1 回のスキャンで処理します。 

次のような 2 ブロックの文字列`111000`2 つの実行を生成します。 すべての移動で 1 つの有効な境界層が削除され、偶数のカウントにより最初の移動後の対称性が保証されるため、2 番目のプレイヤーが勝ちます。
