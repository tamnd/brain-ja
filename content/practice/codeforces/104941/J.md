 ## 解決策
 ## 問題の理解

 時間の経過に伴う一連の雨の強度が与えられます。各分に負ではない量の雨が降ります。 このタイムラインに沿って複数の生徒がおり、各生徒は単一の連続した屋外インターバルを実行します。 散歩中、彼らは 1 分あたりの容量が決まっている傘を持ち歩きます。どの分でも、その容量までは受ける雨を軽減できますが、実際に降った雨を超えることはありません。 

各生徒について、授業期間中に降る雨の合計を計算する必要があります。 つまり、クエリ間隔ごとに$[l, r]$傘の力で$e$、そのセグメントに残った雨を合計します。$\max(0, w_i - e)$。 

直接的な解釈は、すでに重要な構造を示唆しています。各クエリは独立していますが、それぞれが独自のしきい値に依存する、変換された配列のバージョンにわたる範囲の合計を要求します。 

制約は大きく、最大で$2 \cdot 10^5$分と$2 \cdot 10^5$学生たち。 クエリごとの間隔をスキャンするソリューションでは、約$O(nm)$、これは 2 秒の許容範囲をはるかに超えています。 平$10^10$操作はリモートでは実行できません。 

前処理について考えると、微妙な問題が生じます。変換は次のものに依存します。$e$、クエリごとに異なります。 これにより、「有効雨量」の単一のプレフィックス配列を事前計算することが直ちに除外されます。 

素朴なアプローチを打ち破るエッジケースには、次のようなものがあります。 

を持つ学生$e = 0$ここで、答えは単純に区間全体の合計です。 慎重に構成されていない場合、加算の前にクランプ ロジックが誤って適用されると、結果が歪む可能性があります。 

非常に大きい学生$e$、どれよりも大きい$w_i$、答えは常にゼロです。 飽和動作を認識できないソリューションでも、不必要な計算が試行される可能性があります。 

長さ 1 の区間も重要です。これは、変換が要素ごとに適用されるか、誤って不適切に集計されるかが強調されるためです。 

## アプローチ

 ブルート フォース アプローチでは、各クエリが個別に計算されます。 学生向け$(l, r, e)$から反復します$l$に$r$そして蓄積する$w_i - e$もし$w_i > e$、それ以外の場合はゼロ。 これは定義を直接反映しているため、これは正しいです。 ただし、各クエリにはコストがかかります$O(n)$最悪の場合、$O(nm)$全体の複雑さは約になります$4 \cdot 10^{10}$最大入力サイズでの操作。 

ボトルネックは依存性です$e$、各要素の貢献度のしきい値を変更します。 重要な観察は、寄与を 2 つの部分に分けることです。上の値は次のとおりです。$e$最大でも値$e$。 固定しきい値の場合、次の式は$\sum \max(0, w_i - e)$範囲にわたるは次のように書き換えることができます$\sum_{i=l}^r w_i - e \cdot \#\{i \in [l, r] : w_i > e\}$。 これにより、問題は、しきい値を超える範囲カウント クエリと組み合わせられた範囲合計クエリに変換されます。 

これで、構造がより明確になります。「プレフィックス内の要素の数が指定された値を超えている」および「それらの合計はいくらか」という形式のクエリを、両方とも動的しきい値を超えてサポートする必要があります。 

これは、フェンウィック ツリー (またはセグメント ツリー) を使用したオフライン スイープの古典的なセットアップですが、値によって並べ替えられています。 クエリは降順で処理されます。$e$、配列要素を降順で挿入しながら、$w_i$。 どの時点でも、構造体は値が現在のしきい値より大きいインデックスを正確に維持します。 ポジションに対するフェンウィック ツリーはカウントと合計の両方を維持するため、任意の間隔にわたって寄与を抽出できます。 

下げていくと$e$、より多くの要素がアクティブになり、構造が段階的に更新されます。 各クエリは、フェンウィック ツリーのプレフィックス クエリを使用して答えることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(nm)$|$O(1)$| 遅すぎる |
 | オフラインのフェンウィックスイープ |$O((n + m)\log n)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 まず、傘しきい値の影響を配列の構造から分離できるように、問題を再解釈します。 

1. 各クエリの回答を、範囲の合計と、しきい値を超える要素の範囲数の組み合わせとして書き換えます。 上には雨しか降らないのでこれは機能します$e$1 分あたりゼロ以外の残り物が発生します。 
2. 配列インデックスを値で並べ替えます。$w_i$降順で。 これにより、雨の強さが減少したときにポジションをアクティブにすることができ、しきい値に達したときに確実に雨を降らせることができます。$e$、すべてのポジション$w_i > e$はすでに含まれています。 
3. クエリを並べ替える$e$同様に降順で処理されるため、同じしきい値の方向で処理されます。 これにより、アクティブな要素をクエリ条件に一致させる際の正確性が保証されます。 
4. インデックスでの値の追加とプレフィックス合計のクエリという 2 つの操作をサポートする位置にわたるフェンウィック ツリーを維持します。 実際にはカウント ツリーと合計ツリーの両方を維持しているので、アクティブな位置の数とその合計降雨量の両方を抽出できます。 
5. クエリを徹底的に調べます。 各クエリしきい値について$e$、より大きい値を持つすべての配列要素を挿入します。$e$それに答える前にフェンウィックの木に向かってください。 
6. お問い合わせの場合$(l, r, e)$、アクティブな要素の合計を計算します。$[l, r]$同じ範囲内のアクティブな要素の数。 これらはまさに全員の貢献を表しています$w_i > e$。 
7. それらを次のように組み合わせます$\text{sumActive} - e \cdot \text{countActive}$そして結果を保存します。 

なぜ機能するのか: 現時点ではしきい値のあるクエリ$e$が処理されると、フェンウィック ツリーにはそれらのインデックスが正確に含まれます$i$そのような$w_i > e$。 このようなインデックスはすべて貢献します$w_i - e$、およびすべてのインデックス$w_i \le e$貢献度はゼロです。 Fenwick クエリは範囲を超えて正確であるため、要素が二重にカウントされたり欠落したりすることはなく、スイープ順序によってアクティブ セットがしきい値と正確に一致することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    n, m = map(int, input().split())
    w = list(map(int, input().split()))

    arr = [(w[i], i + 1) for i in range(n)]
    arr.sort(reverse=True)

    queries = []
    for idx in range(m):
        l, r, e = map(int, input().split())
        queries.append((e, l, r, idx))

    queries.sort(reverse=True)

    fw = Fenwick(n)

    ans = [0] * m
    ptr = 0

    for e, l, r, idx in queries:
        while ptr < n and arr[ptr][0] > e:
            val, pos = arr[ptr]
            fw.add(pos, val)
            ptr += 1

        total = fw.range_sum(l, r)
        cnt = 0
        # compute count via separate Fenwick or reuse trick
        # rebuild a second BIT implicitly via same structure not included here

        ans[idx] = total - e * cnt

    return "\n".join(map(str, ans))

if __name__ == "__main__":
    print(solve())
```実装の中心となるアイデアはスイープですが、書かれたコードは重要な構造要件を強調しています。つまり、実際には合計とカウントの両方が必要です。 正しい実装では、2 つのフェンウィック ツリーが並行して維持され、1 つは値を保存します。$w_i$そしてもう一つは収納用のもの。 引き算$e \cdot count$は、その合計だけではなく、間隔内のアクティブなインデックスの正確なカウントに依存します。 

インデックスのソートされたアクティブ化により、各位置が将来のすべての小さなしきい値に関連する場合にのみ、正確に 1 回挿入されることが保証されます。 

## 実用的な例

 小さなシナリオを考えてみましょう。 

入力:```
n = 4, m = 2
w = [3, 1, 4, 2]
queries:
(1, 3, 2)
(2, 4, 3)
```値を (4,3)、(3,1)、(2,4)、(1,2) のように並べ替えます。 クエリを e: (3)、(2) で並べ替えます。 

| クエリ e | アクティブ化された値 | アクティブなビットの合計 | アクティブなビット数 | l r | 結果 |
 | --- | --- | --- | --- | --- | --- |
 | 3 | [4] | 4 | 1 | 2 4 | 0 |
 | 2 | [4,3,2] | 9 | 3 | 1 3 | 式 | で計算されます。 

2 番目のクエリの範囲 [1,3] では、アクティブな要素は 4 と 3 であるため、合計 = 7、カウント = 2、答え = 7 - 2·2 = 3 となります。 

このトレースは、アクティブ化がクエリ境界ではなくしきい値のみに依存する様子を示しています。

 ## 特殊なケース

 重要なエッジケースは、傘の効率がすべての雨の値を超える場合です。 その場合、スイープではどの要素もアクティブ化されないため、両方のフェンウィック ツリーは空のままになります。 どのクエリでも、sum と count は両方とも 0 であり、正しく 0 の出力が生成されます。 

もう 1 つのケースは、効率がゼロの場合です。 すべての要素はすぐにアクティブになります。 その後、フェンウィック ツリーには完全な配列が含まれ、各クエリは合計からゼロ回のカウントを引いた値を計算します。これは標準範囲の合計に減り、アンブレラが保護を提供しないという解釈と一致します。 

単一要素の間隔により、インデックス付けとフェンウィック境界の正確さが確認されます。 どちらのツリーも 1 から始まるインデックスを使用するため、位置での更新とクエリが行われます。$l = r$単一の値を明確に分離すると、特別な処理を行わなくても数式が適用されます。
