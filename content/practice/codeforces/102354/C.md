 ## 解決策
 ## 問題の理解

 私たちは一連の金銭共有イベントを時系列に処理します。 正の値は、パブリック アカウントに多くの資金が追加されたことを意味します。 負の値は、借り手が対応する正の金額を要求していることを表します。 アカウント残高がマイナスにならないように、どのリクエストを承認するかを決定する必要があります。 

すべての有効な決定の中で、主な目的は、できるだけ多くのリクエストを承認することです。 同様に、拒否されるリクエストの数も最小限に抑えたいと考えています。 最適な決定が複数存在する場合、いずれかが受け入れられます。 

出力にはイベントごとに 1 行が含まれます。 ポジティブな出来事は常に生み出す`resupplied`。 否定的なイベントの場合、出力には、そのリクエストが最終的に承認されたままになったか、選択されたリクエストのセットから削除されたかが示されます。 

最大 (10^5) 個のリクエストと (10^5) 個の再供給が存在する可能性があるため、シーケンス全体には最大 (2\cdot10^5) 個のイベントが含まれます。 (2^{100000}) は実際の限界をはるかに超えているため、リクエストの多くのサブセットを試行するアルゴリズムは直ちに不可能です。 (O(n^2)) アルゴリズムでさえ、最悪の場合には約 (10^{10}) 個の演算を実行することになりますが、これは 1 秒の制限時間には多すぎます。 基本的に線形処理、つまり (O(n\log n)) 処​​理が必要です。 

値自体の大きさは最大 (10^9) であり、(2\cdot10^5) 個のイベントが発生する可能性があるため、金額の合計はおよそ (2\cdot10^{14}) に達する可能性があります。 Python の整数はこれを安全に処理しますが、固定幅の整数を使用する言語では 64 ビット演算を使用する必要があります。 

すでに受け入れられたより大きなリクエストを後で削除する場合にのみ、現在のリクエストを受け入れることができる場合、微妙なケースが発生します。 例えば：```
3 1
+5
-3
-4
-2
```最適な出力は次のとおりです。```
resupplied
declined
approved
approved
```受付後`-3`、残り 2 ユニットのみなので、`-4`との併用はお受けできません。 不注意で貪欲なアルゴリズムは単に衰退する可能性があります`-4`、その後も断ります`-2`現在の残高だけを見ていたからです。 より適切な決定は、サイズ 3 の以前のリクエストをサイズ 4 のリクエストに置き換えることです。その時点で承認されたリクエストの合計数は 1 のままで、残りの 2 ユニットが最後のリクエストを承認できます。 

もう 1 つのエッジ ケースは、残高がマイナスになる原因となるリクエスト自体が、受け入れられた最大のリクエストである場合です。 例えば：```
1 1
+3

```唯一の正しい出力は次のとおりです。```

```アルゴリズムは、リクエストを一時的に受け入れた後、残高をマイナスのままにしてはいけません。 受け入れられた最大のリクエスト (ここでは現在のリクエスト) がすぐに削除されます。 

3 番目のケースは、金額が利用可能な残高と正確に等しいリクエストです。```

+5

最後に、リクエストの間に複数の再供給が発生する可能性があります。```

## アプローチ

 最も直接的なアプローチは、リクエストのすべてのサブセットを考慮することです。 サブセットごとに、イベントを時系列でシミュレートし、選択されたすべてのリクエストをその位置で支払うことができるかどうかを確認します。 すべての実行可能なサブセットの中で、最大数のリクエストを含むサブセットを保持します。 これは正しいです。承認されたリクエストの考えられるすべてのセットが明示的に考慮されるからです。 

問題はサブセットの数です。 (n) 個のリクエストには (2^n) 個の可能な選択肢があり、1 つの選択肢をチェックするには (O(n+m)) 時間がかかります。 したがって、最悪の場合の操作数は (O((n+m)2^n)) となり、(10^5) どころか、数十のリクエストですらすでに絶望的になります。 

重要な観察は、すべてのリクエストが目的に対してまったく同じ価値を持っているということです。つまり、リクエストを承認すると、回答に 1 つ貢献します。 リクエスト間で異なる唯一のことは、消費する金額です。 

ある時点で、選択されたリクエストにこれまでに提供されたよりも多くの資金が必要になるとします。 すでに受け入れられたリクエストを少なくとも 1 つ削除する必要があります。 リクエストを 1 つ削除すると、承認されたリクエストの数が 1 つだけ減少するため、可能な限り最善の修復は、解放される金額が最も大きいリクエストを削除することです。 より大きなリクエストを削除すると、より小さなリクエストを削除した場合と少なくとも同じ残高が得られますが、1 回の承認にまったく同じコストがかかります。 

これは必然的に貪欲な戦略につながります。 すべてのリクエストを一時的に受け入れます。 残高がマイナスになる場合は、現在受け付けているリクエストのうち最大のリクエストを削除します。 最大ヒープを使用すると、そのリクエストを効率的に見つけることができます。 

重要な部分は、以前に削除されたリクエストを後のリクエストで置き換えることができるということです。 このため、適合しない最初のリクエストを単に拒否するだけでは十分ではありません。 ヒープにより、受け入れられるリクエストの最大数を維持しながら、以前の決定を修正できるようになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O((n+m)2^n)) | (O(n+m)) | 遅すぎる |
 | max-heap を使用した貪欲な | (O((n+m)\log n)) | (O(n)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 完全なイベント シーケンスを読み取り、最初は各イベントの決定を含まない出力配列を作成します。 変数を保持する`balance`、最初はゼロで、これまでにすべての承認されたリクエストが処理された後に現在利用可能な金額を表します。 
2. すべてのポジティブなイベントについて、その値を`balance`そして書きます`resupplied`そのイベントのために。 補給は他の決定と競合することがないため、いつでもすぐに組み込むことができます。 
3. ネガティブな出来事ごとに、`cost`その絶対値になります。 減算してリクエストを一時的に承認します`cost`から`balance`。 この受け付けられたリクエストをその位置とともに max-heap に保存します。 
4. 結果の残高がマイナスでない場合は、リクエストを承認したままにします。 現時点では、現在受け入れられているリクエストのセットが実行可能であるため、何も削除する理由はありません。 
5. 残高がマイナスの場合は、最大のコストを持つ受け入れられたリクエストをヒープから削除します。 そのリクエストを次のようにマークします`declined`そしてそのコストを元に戻します`balance`。 すべてのリクエストは目標に対して正確に 1 ユニット貢献するため、最大のリクエストを削除することが最善の修復です。すべての可能な削除は承認を 1 つ失い、最大のリクエストは最大の金額を返します。 
6. イベント シーケンス全体を続行します。 最終的に、ヒープに残っているすべてのリクエストは承認されますが、ヒープから削除されたすべてのリクエストは拒否されます。 出力配列には、一時的に受け入れられ、後で削除されたリクエストを含む、すべてのリクエストの最終ステータスがすでに記録されています。 

### なぜ効果があるのか

 イベント シーケンスのプレフィックスを処理した後、ヒープには、そのプレフィックスのすべての実行可能な選択肢の中から可能な最大数のリクエストを含む、承認されたリクエストの実行可能なセットが含まれます。 

新しいリクエストが適合する場合、それを追加すると承認されるリクエストの数が 1 つ増えるため、新しいセットはそのプレフィックスに最適になります。 適合しない場合は、受け入れられたリクエストの一部を削除する必要があります。 削除できるたびに承認の数が 1 つずつ減りますが、最大のリクエストを削除すると可能な限り最大のバランスが残ります。 したがって、ヒープには、承認数が最大のすべての選択肢の中から可能な限り最良のセットが含まれます。 将来のイベントは、残っている金額とすでに選択されているリクエストにのみ依存するため、同じ規模のソリューション間で可能な限り最大の残高を維持することは、将来の実現可能性を損なうことはありません。 これにより、シーケンス全体にわたって不変条件が維持され、承認されたリクエストの全体的に最適な数が得られます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    total = n + m

    events = [int(input()) for _ in range(total)]

    balance = 0
    heap = []
    answer = [""] * total

    for i, x in enumerate(events):
        if x > 0:
            balance += x
            answer[i] = "resupplied"
        else:
            cost = -x

            balance -= cost
            heapq.heappush(heap, (-cost, i))
            answer[i] = "approved"

            if balance < 0:
                neg_cost, idx = heapq.heappop(heap)
                removed_cost = -neg_cost

                balance += removed_cost
                answer[idx] = "declined"

    sys.stdout.write("\n".join(answer))

if __name__ == "__main__":
    solve()
```の`balance`変数は、現在承認されているすべてのリクエスト後に残っている実際の金額を表します。 ポジティブなイベントが発生すると、リクエストの決定が行われる前にこの値が増加します。 

リクエストの場合、コードは最初に次の内容を挿入します。`(-cost, index)`Python の最小ヒープに格納されます。 コストを否定すると、最小のヒープ キーが最大の元のコストに変わり、実質的に最大ヒープが得られます。 

リクエストは最初にマークされます`approved`貪欲アルゴリズムはそれを候補として考慮する必要があるためです。 これによりマイナスの残高が生じた場合は、リクエストが 1 つだけ削除されます。 ポップされたヒープ エントリから、どのリクエストを拒否するか、そしてその決定によってどれだけのお金が回復されるかがわかります。 

ヒープから削除されたリクエストは現在のリクエストではない可能性があるため、すべてのヒープ エントリに格納されたインデックスが必要です。 インデックスがなければ、削除する量はわかりますが、対応する出力行を更新できません。 

テストは`balance < 0`、 ない`balance <= 0`。 最後に承認されたリクエストによってアカウントの残りの残高がすべて消費される可能性があるため、残高ゼロは有効です。 

Python では整数オーバーフローの問題はありません。 可能な最大の累積値は (10^{14}) 程度で、Python の任意精度の整数で快適に処理できます。 

入力は次のように読み取られます`sys.stdin.readline`、すべての出力は 1 つの文字列にまとめられます。 これにより、最大 (2\cdot10^5) 行に対して多数の個別の出力操作を実行するオーバーヘッドが回避されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | (O((n+m)\log n)) | 各リクエストは一度ヒープに挿入され、場合によってはヒープから削除されます。 |

approved
declined
```これにより、現在のリクエストがヒープから削除されたリクエストである可能性があることが確認されます。 

厳密にゼロの境界は次のように処理されます。```
2 1
+5
-5
-1
```承認後残高がゼロになる`-5`, したがって、削除は発生しません。 最後のリクエストのみが拒否されます。 出力は次のとおりです。```
resupplied
approved
declined
```使用する`<= 0`ヒープ修復条件では、サイズ 5 のリクエストが誤って削除されてしまいます。 

シーケンスには、借用の前にいくつかの再供給を含めることもできます。```
3 2
+2
+3
-4
-1
-1
```最初のリクエストの前に残高が 5 に達します。 4の申請を承認した後は1なので、1の申請も承認されて残高がゼロになります。 最終リクエストは承認できません。 出力は次のとおりです。```
resupplied
resupplied
approved
approved
declined
```このアルゴリズムは、すべてのポジティブなイベントを単純に蓄積します。`balance`, そのため、連続して補給する場合に特別な処理は必要ありません。 

大量の場合は、もう 1 つの現実的なエッジケースです。 例えば：```
2 2
+1000000000
+1000000000
-1000000000
-1000000000
```残高は (2\cdot10^9) に達し、両方のリクエストが承認され、ゼロのままになります。 Python の整数演算はこれらの値を直接処理し、変換や切り捨てを行わずにリクエストのコストをヒープに保存します。 

最後の微妙な点は、拒否されたリクエストはかなり以前に発生した可能性があることです。 出力行は、後でヒープによって削除されるときに変更する必要があります。 そのため、すべてのヒープ エントリには元のイベント インデックスが格納されます。 このインデックスがないと、アルゴリズムは正しいリクエスト サイズを見つけることはできますが、イベントごとに必要な出力を生成できません。
