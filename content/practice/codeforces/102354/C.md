 ## 解決策
 ## 問題の理解

 2 種類のイベントを含む 1 つの時系列シーケンスを処理します。 正の値は、その金額が共有アカウントに追加されることを意味します。 負の値は、そのサイズがその数値の絶対値である借用リクエストを表します。 アカウントはゼロから始まり、承認されたリクエストによりその金額がアカウントから直ちに削除されます。 リクエストは、その時点でアカウントが支払い可能な場合にのみ承認されます。 

出力にはイベントごとに 1 行が含まれます。 ポジティブなイベントは常に次のように出力されます。`resupplied`。 ご要望に応じて印刷いたします`approved`そのリクエストを受け入れられたセットに保持すると、`declined`さもないと。 目的は、借りた金額の合計ではなく、拒否されたリクエストの合計数を最小限に抑えることです。 

最大 (10^5) 個の要求と (10^5) 個の再供給が存在する可能性があるため、イベント シーケンスには (2\cdot10^5) 個の要素を含めることができます。 二次アルゴリズムは、最悪の場合、1 秒の制限をはるかに超える (4\cdot10^{10}) 程度の演算を実行する可能性があります。 基本的に線形または (O(N\log N)) の作業が必要です (N=n+m)。 金額は (10^9) に達し、その合計はおよそ (2\cdot10^{14}) に達する可能性があるため、実行残高では 32 ビット整数よりもはるかに大きな値を保持できる整数型を使用する必要があります。 Python の整数はすでにこれを安全に提供しています。 

最初の注意が必要なケースは、リクエスト自体がアカウントに対して大きすぎる場合です。 例えば、```
1 1
-5
+5
```出力があります```
declined
resupplied
```後から到着したお金は遡って承認できないため、最初のリクエストは拒否する必要があります。 最初にすべての補給の合計量を計算してから、どのリクエストを受け入れるかを決定する不用意な解決策では、最初のリクエストが誤って実行可能であると扱われてしまいます。 

もう 1 つの微妙なケースは、現在のリクエストは拒否できるが、以前のリクエストを拒否した方が良い場合です。 考慮する、```
3 1
+5
-3
-2
-1
```正しい出力は```
resupplied
approved
approved
approved
```ここでは、最初の 2 つのリクエスト後の残高はゼロであるため、最後のリクエストは不可能であり、実際には拒否する必要があります。 したがって、正しい出力は代わりに```
resupplied
approved
approved
declined
```より分かりやすい例は次のとおりです。```
3 1
+5
-4
-3
+10
```で`-3`、アカウントには 1 ユニットのみが残っています。 現在のリクエスト 3 ではなく、以前のリクエスト 4 を拒否することで、現在のプレフィックスを実現可能にできます。出力は次のようになります。```
resupplied
declined
approved
resupplied
```資金が不足している場合は常に現在のリクエストを拒否する貪欲なルールでは、不必要に受け入れられたリクエストが失われます。 

1 つのイベントで複数のリクエストを削除する必要がある場合もあります。 例えば、```
3 1
+3
-2
-2
-2
```最初の 2 つのリクエストを受け入れた後、3 番目のリクエストが到着すると残高はマイナスになります。 ここでは、受け入れられた最大のリクエストを削除するだけで十分ですが、一般的には複数の削除が必要になる場合があります。 実装では、残高が負でなくなるまで、受け入れられたリクエストを削除し続ける必要があります。 

## アプローチ

 直接的な総当たりアプローチは、すべてのリクエストが承認されるか拒否されるかを個別に決定することです。 (n) 個のリクエストの場合、(2^n) 個の可能なサブセットが存在します。 サブセットごとに、完全なイベント シーケンスをスキャンし、受け付けられたリクエストがあらゆる時点で実行可能かどうかを確認できます。 これにより、(O((n+m)2^n)) の演算が行われます。 (n=10^5) では (2^n) 自体も絶望的になるため、このアプローチは最適化の対象を理解する場合にのみ役立ちます。 

重要な観察は、実現可能性はこれまでに確認された受け入れられたリクエストの総量にのみ依存するということです。 これまでに受け取った補給の合計が (S) で、プレフィックス内で受け入れられた要求の合計が (C) であるとします。 プレフィックスは (C\le S) の場合に正確に使用できます。 

次に、リクエストを左から右に処理し、すべてのリクエストを暫定的に受け入れます。 現在のリクエストを受け入れることで合計が利用可能な金額を超える場合は、処理されたプレフィックスから少なくとも 1 つの受け入れられたリクエストを削除する必要があります。 目標は拒否されたリクエストをカウントするため、1 回の削除で実現可能性が回復できる場合は必ず 1 つのリクエストを削除する必要があります。 受け入れられたすべてのリクエストの中で、最大のリクエストを削除すると、同じ 1 回の拒否のコストが発生しながら、消費コストが最大に削減されます。 

この貪欲な選択により、将来のリクエストに備えて最大限の資金が確保されます。 受け入れられた 2 つのリクエストのサイズが (a<b) であるとします。 どちらかを拒否する必要がある場合、(b) を拒否すると (a) を拒否するよりも多くの資金 (b-a) が残りますが、どちらの選択でも拒否されるリクエストの数が 1 つだけ増加します。 残高が大きくなっても、将来の実現可能性が悪化することはありません。 

これにより、現在受け入れられているすべてのリクエスト サイズを含む最大ヒープが自然に得られます。 リクエストが到着したら、それを暫定的に受け入れてヒープに挿入します。 残高がマイナスになった場合は、受け入れられた最大のリクエストをヒープから削除し、そのリクエストを拒否済みとしてマークします。 残高がマイナスでなくなるまで繰り返します。 ヒープを使用すると、(O(\log n)) で受け入れられた最大のリクエストを見つけることができます。 

ブルートフォース手法では、どの決定が交換可能であるかを認識する方法がないため、受け入れられる可能性のあるすべてのサブセットが考慮されます。 貪欲な方法は、すべてのリクエストの目標において同じコスト、つまり 1 回の拒否が発生しますが、金額は異なりますという事実を利用します。 拒否が強制される場合は常に、受け入れられた最大のリクエストが最も価値のあるものであり、破棄されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O((n+m)2^n)) | (O(n+m)) | 遅すぎる |
 | 最適 | (O((n+m)\log n)) | (O(n+m)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 完全なイベント シーケンスを読み取り、イベント タイプに従って初期化された出力配列を作成します。 ポジティブな出来事の場合、答えはすぐに得られます`resupplied`; リクエストの場合、最初にマークを付けます`approved`貪欲なアルゴリズムは最初にすべてのリクエストを受け入れようとするためです。 
2. メンテナンス`balance`、アカウントに現在残っている金額、および受け入れられたリクエストの最大ヒープ。 パイソンの`heapq`は最小ヒープであるため、各リクエスト量を負の数として保存します。 後のヒープ削除によって以前のリクエストが拒否される可能性があるため、イベント インデックスを量とともに保存します。 
3. 値 (x) の正のイベントが発生した場合、(x) を加算します。`balance`。 再供給は利用可能なお金を増やすだけなので、ヒープから何も削除する必要はありません。 
4. 値 (-x) の負のイベントが発生した場合、それを暫定的に承認します。 から (x) を引きます`balance`そして (( -x,index)) をヒープに挿入します。 
5. もし`balance`が負になった場合、ヒープから最大のリクエストを繰り返し削除します。 量 (x) を表すヒープ エントリの場合は、(x) を加算し直します。`balance`そしてそのリクエストの出力を変更します`approved`に`declined`。 

削除されたリクエストは現在のリクエストである必要はありません。 これは中心となる貪欲なステップです。1 回の拒否で可能な限り最大の金額を回収し、将来のリクエストのために可能な限り最大の残高を残すことができます。 
6. すべてのイベントが処理されるまで続行します。 受け入れられたリクエストはすべてヒープ内に残り、ヒープから削除されたリクエストはすべてマークされます。`declined`。 

### なぜ効果があるのか

 プレフィックスを処理した後、ヒープには、アルゴリズムが現在受け入れているリクエストが正確に含まれます。 不変条件は、それらの合計コストがそのプレフィックスで受け取った補給の合計を決して超えないということです。そのため、アカウント残高は常に負ではありません。 

新しいリクエストによって不足が生じた場合、実行可能なすべてのソリューションは、受け入れられたプレフィックスから少なくとも 1 つのリクエストを拒否する必要があります。 このアルゴリズムは、受け入れられた最大のリクエストを拒否します。 これにより、最大のリクエストが実行可能性を回復するたびに 1 回の拒否で十分であるため、新しい拒否の数を可能な限り最小限に抑えます。 複数のリクエストを削除する必要がある場合、削除ごとに残りの最大のリクエストが選択され、拒否ごとに回収される金額が最大になります。 

さらに強力なのは、処理されたプレフィックスで受け入れられたリクエストの数が同じであるすべての実行可能な選択肢の中で、可能な限り最大の残高を維持することは、将来的には常に少なくとも同じくらい良いことです。 最大のリクエストを拒否することで、まさにそれが実現されます。 したがって、貪欲な状態では、同じ数の拒否がある別のソリューションよりも将来のリクエストの可能性が少なくなることはありません。 イベント シーケンスの帰納により、拒否されたリクエストの最終的な数は最小限になります。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    total = n + m

    events = [int(input()) for _ in range(total)]

    answer = []
    heap = []
    balance = 0

    for i, x in enumerate(events):
        if x > 0:
            balance += x
            answer.append("resupplied")
            continue

        amount = -x
        balance -= amount
        heapq.heappush(heap, (-amount, i))
        answer.append("approved")

        while balance < 0:
            neg_amount, idx = heapq.heappop(heap)
            amount_removed = -neg_amount
            balance += amount_removed
            answer[idx] = "declined"

    sys.stdout.write("\n".join(answer))

if __name__ == "__main__":
    solve()
```すべてのリクエストが安定したイベント インデックスを持つように、入力は最初に保存されます。 このインデックスが必要なのは、以前に受け入れられたリクエストが、後で拒否することを決定したリクエストになる可能性があるためです。 

補給の場合はコードが増えるだけ`balance`そして記録`resupplied`。 より多くのお金が到着しても、既存の受け入れられたリクエストは受け入れられたままであるため、ヒープを変更する理由はありません。 

リクエストの場合、コードはまずリクエストを受け入れられたものとして扱います。 これにより、その金額が一時的に差し引かれます`balance`そしてそれをヒープに挿入します。 結果の残高がマイナスの場合、現在のプレフィックスはすべての仮承認で実現可能ではありません。 

ヒープストア`(-amount, index)`。 Python のヒープは最小値を返すため、最も負のエントリが最大のリクエスト量に対応します。 たとえば、サイズ 3、8、および 5 のリクエストは次のように保存されます。`-3`、`-8`、 そして`-5`、 それで`-8`が最初に削除されます。 

リクエストが削除されると、コードはその金額を残高に追加し、変更します。`answer[idx]`に`declined`。 このため、リクエストが到着した瞬間に出力を単純に決定することはできません。 最初に承認されたリクエストが、後で拒否されるリクエストになる可能性があります。 

の`while`条件ではなく条件が必要です`if`。 単一の大きなリクエストにより、他のすべての受け入れられたリクエストよりも大きな不足が生じる可能性があるため、いくつかの受け入れられたリクエストを破棄する必要がある場合があります。 残高が負の場合、ヒープには常に少なくとも現在のリクエストが含まれるため、実行可能性を回復する前にループで要素が不足することはありません。 

Python の整数は、オーバーフローすることなく、およそ (2\cdot10^{14}) の可能なバランスを処理します。 ヒープには最大 (n) 個のリクエストが含まれており、すべてのリクエストは 1 回挿入され、最大 1 回削除されます。

-4
-3
-1
```後`-4`残高は 1 です。受け入れる`-3`バランスは (-2) になります。 ヒープにはサイズ 4 と 3 のリクエストが含まれているため、サイズ 4 のリクエストは削除されます。 バランスは 2 になり、サイズ 3 のリクエストは受け入れられたままになります。 決勝戦`-1`その後成功し、残高 1 が残ります。出力は次のようになります。`resupplied`、`declined`、`approved`、`approved`。 

3 番目のエッジ ケースは、残高がゼロになる正確な境界です。 と```
3 1
+5
-2
-3
-1
```最初のリクエストは残高 3 のまま、2 番目のリクエストは残高 0 のまま、3 番目のリクエストは残高をマイナスにします。 暫定的な受け入れ後のヒープにはサイズ 2、3、および 1 が含まれるため、最大のリクエストであるサイズ 3 が削除されます。 残高は 2 に戻り、現在のサイズ 1 のリクエストは承認されたままになります。 出力は`resupplied`、`approved`、`declined`、`approved`。 条件は次のとおりです。`balance < 0`、 ない`balance <= 0`なぜなら、資金をまったくゼロにすることもまだ実現可能だからです。 

4 番目のエッジ ケースは、複数の削除を必要とする不足を生み出すリクエストです。 例えば、```
3 1
+3
-2
-2
-2
```最初のリクエストの後、残高は 1 になります。2 番目のリクエストの後は (-1) になるため、ヒープはサイズ 2 のリクエストを 1 つ削除し、残高を 1 に戻します。現在のリクエストは承認されたままになります。 次のサイズ 2 リクエストでは再び不足が生じるため、別のサイズ 2 リクエストは削除されます。 したがって、このアルゴリズムは、単一の拒否で常に十分であると想定するのではなく、1 つのイベントで複数の削除を処理します。 

最後のエッジケースは最大入力サイズです。 (10^5) 個の再供給により、`+1`続いて (10^5) 個のリクエストが続きます`-1`、すべてのリクエストはすぐに実行可能です。 ヒープは (10^5) 要素まで増加しますが、すべての操作は (O(\log n)) のままであり、完全なシーケンスには (O((n+m)\log n)) 時間と (O(n+m)) メモリのみが必要です。
