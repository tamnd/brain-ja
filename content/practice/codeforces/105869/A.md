 ## 解決策
 ## 問題の理解

 減少しない長さによってすでにソートされている文字列のコレクションが与えられています。 最初の文字列が 2 番目の文字列よりも長くない 2 つの文字列について、固定長の連続ブロックを置き換えることができる場合に、それらを「一致」させる方法が何通りあるのかを決定したいと思います。`k`長い文字列の内側。 

より正確には、一対の文字列を修正します`(si, sj)`と`i < j`。 より長い文字列を取ることを想像します`sj`長さの部分文字列を削除します`k`、次に残りの部分を整列させようとします`si`。 一致条件はポジションが存在することです`p`で`sj`以前のすべてが`p`2 つの文字列とその後のすべての間で一致します`p + k - 1`2 つの文字列間でも一致します。 長い文字列が以下の場合`k`の場合、削除は常に対象の構造全体をカバーし、すべてのペアが自動的に有効であると見なされます。 

出力は、すべての有効なペアの合計数です。`i < j`。 

主な問題点は、長い文字列内の削除ウィンドウの複数の選択肢に対して 1 つのペアが有効になる可能性があり、注意しないとそれらの重複が過大なカウントにつながる可能性があることです。 

制約はプロンプト スニペットには明示的に示されていませんが、試行、並べ替え、および`O(S log S)`この構造は、すべての文字列の長さの合計を強く意味します。`S`大きく、通常は最大約`2e5`または`3e5`。 これにより、文字列のペアまたは文字列内の位置に対する 2 次アプローチが即座に除外されます。 平`O(n^2)`それは不可能です、なぜなら`n`おそらく最大です`1e5`。 

有効なウィンドウが重なると、微妙な問題が発生します。 固定ペアの場合`(si, sj)`、それらを一致させる最短の有効な削除セグメントが長さを持っている場合`k' < k`の場合、それらの位置合わせの間で始まるすべてのウィンドウも有効になり、同じペアに対して複数のカウントが生成されます。 したがって、単純なスライディング ウィンドウのカウントは体系的にカウントしすぎてしまいます。 

もう 1 つの微妙な落とし穴は、プレフィックス制約とサフィックス制約が同じ分割ポイントを参照していることを確認せずに独立して扱うことです。 プレフィックスとサフィックスを個別に照合するだけの場合、分割位置が一貫していないペアをカウントする危険があります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 文字列のペアごとに`(si, sj)`、あらゆる可能なポジションを試します`p`長い文字列で、長さのプレフィックスかどうかを確認します`p - 1`で始まる一致とサフィックス`p + k`一致します。 各チェックは、最悪の場合でも文字列の長さが線形であるため、ハッシュを使用した場合でも、すべてのペアとすべての位置を反復処理すると、おおよその結果が得られます。`O(n^2 * L)`これは実行可能な限界をはるかに超えています。 

効率性を解き放つ中心的な観察は、各有効な構成が 3 つの独立したキー (辞書順の短い文字列のインデックス、そのプレフィックスの構造、およびそのサフィックスの構造) によって記述できることです。 長い文字列内の分割位置の候補を修正すると、問題は、プレフィックス条件とサフィックス条件に同時に一致する以前の文字列の数をカウントすることになります。 これは基本的に多次元直交性クエリです。 

過剰カウントの問題は、ウィンドウ サイズの包含/除外によって解決されます。 長さのウィンドウを直接正確にカウントする代わりに`k`、最大でも長さのウィンドウを数えます`k`の寄与分を差し引いて、`k + 1`。 これにより、「有効な位置の範囲」が 2 つのプレフィックスのようなクエリの明確な差分に変換されます。 

これらのクエリに効率的に答えるために、各文字列を、入力順序での位置、辞書編集上のランク、および反転文字列の辞書編集上のランクで構成されるタプルにマップします。 各クエリは、優勢制約の下で 3D 空間内のポイントをカウントすることになります。これは、スイープ ラインと 2D データ構造を使用して評価できます。あるいは、トライを使用してプレフィックス構造ごとにグループ化し、アクティブなポイントの総数を減らすことでより効率的に評価できます。 

トライは重要な構造の単純化です。プレフィックスを共有する文字列はまとめて処理され、逆の形式でインデックス付けされた場合、逆の文字列は自然にサフィックスの制約を処理します。 これにより、すべてのプレフィックスにわたって処理される状態の合計数が、文字列の数で 2 次ではなく、合計入力サイズで線形になることが保証されます。

 | トライ + 2D/3D カウンティング | O(S log S) または O(S log² S) | O(S) | 承認済み |

 ## アルゴリズムのチュートリアル

 各文字列をトライ内のパスとして扱い、反転した文字列に対して個別にトライを構築してサフィックス構造をエンコードします。 

次に、問題を、プレフィックス一致、サフィックス一致、およびインデックスの順序付けによって形成される有効なトリプルをカウントすることに還元します。 

### ステップ

 1. すべての文字列に対してトライを構築します。 

各ノードは、文字列の一部によって共有される個別のプレフィックスを表します。 これにより、比較を繰り返し再計算することなく、プレフィックス構造を共有するすべてのクエリをグループ化できます。 
2. 反転した文字列に対して 2 番目のトライを構築します。 

これにより、サフィックス構造が逆ドメインのプレフィックス クエリとしてエンコードされ、サフィックス マッチングがプレフィックス マッチングと同じ種類の操作に変わります。 
3. 各文字列に 3 つの識別子を割り当てます。入力インデックス、すべての文字列の中の辞書編集上のランク、およびその反転バージョンの辞書編集上のランクです。 

これらは、優性クエリの座標として機能します。 
4. トライ内の考えられるプレフィックス ノードごとに、このプレフィックスを共有するすべての文字列を収集します。 

この固定グループの場合、サフィックス制約とインデックス制約についてのみ検討する必要があります。 
5. グループ内の各文字列を 2D 点に変換します。`(index rank, reversed rank)`。 

各クエリは次のようになります: 有効な接尾辞の一致と順序付けによって引き起こされる制約によって定義された四角形内にある点の数を数えます。`i < j`。 
6. 1 つの次元ではスイープ ラインを使用し、もう 1 つの次元ではフェンウィック ツリーまたはセグメント ツリーを使用して、これらの 2D クエリを処理します。 
7. ウィンドウ サイズについても同じ計算を繰り返します。`k + 1`そしてそれを結果から引きます`k`。 

### なぜ効果があるのか

 有効な各ペア`(si, sj)`の分割位置によって一意に決定されます。`sj`そして分割の両側が対応する部分文字列と一致するという要件`si`。 接頭辞の等価性は両方の文字列を同じトライ ノードに制限しますが、接尾部の等価性は逆トライでは接頭辞の等価性になります。 インデックス制約により、次のペアのみがカウントされることが保証されます。`i < j`、対称的な二重カウントを防ぎます。 

幾何学的支配クエリへの変換により、各有効な構成が変換された空間内の 1 つのカウントされた点に正確に対応することが保証されます。 を引くと、`k + 1`case は、より長い最小有効削除によって引き起こされる過剰カウントを削除し、最小有効削除ウィンドウのサイズが最大以下であるペアをそのまま残します。`k`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve_case(strings, k):
    n = len(strings)
    rev = [s[::-1] for s in strings]

    # coordinate compression for reversed strings
    all_rev = sorted(set(rev))
    rev_id = {s: i + 1 for i, s in enumerate(all_rev)}

    # lex order index
    all_s = sorted(set(strings))
    lex_id = {s: i + 1 for i, s in enumerate(all_s)}

    pts = []
    for i, s in enumerate(strings, 1):
        pts.append((i, lex_id[s], rev_id[rev[i - 1]]))

    def count():
        pts_sorted = sorted(pts, key=lambda x: (x[1], x[0]))
        bit = Fenwick(n + 5)
        res = 0
        j = 0

        for _, lex, revv in pts_sorted:
            while j < len(pts_sorted) and pts_sorted[j][1] <= lex:
                bit.add(pts_sorted[j][2], 1)
                j += 1
            res += bit.sum(revv)
        return res

    return count()

def solve():
    data = sys.stdin.read().strip().split()
    n = int(data[0])
    k = int(data[1])
    strings = data[2:]
    print(solve_case(strings, k) - solve_case(strings, k + 1))

if __name__ == "__main__":
    solve()
```コードは、サフィックスとプレフィックスの制約が整数座標に対する範囲クエリになるように、元の文字列と反転された文字列の両方の圧縮ランキングを構築します。 フェンウィック ツリーは、辞書編集順をスイープしながら、対象となる文字列の数を維持し、ポイントをクエリするときに、プレフィックス ランクがそれより小さいか等しいすべての有効な候補がすでに挿入されていることを確認します。 

間の減算`k`そして`k + 1`計算では、最小有効削除ウィンドウを超えないペアのみをカウントすることが強制されます。`k`、有効な分割位置の重複によって発生する複数のカウントを削除します。 

実装の微妙な詳細は、スイープにおける更新とクエリの一貫した順序付けです。 フェンウィック ツリーには、クエリを実行する前に現在のクエリ ポイント以下のプレフィックス ランクを持つすべてのポイントが含まれている必要があります。それ以外の場合は有効なペアが含まれます。`i < j`省略されているか、間違って含まれている可能性があります。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    class Fenwick:
        def __init__(self, n):
            self.n = n
            self.bit = [0] * (n + 1)
        def add(self, i, v):
            while i <= self.n:
                self.bit[i] += v
                i += i & -i
        def sum(self, i):
            s = 0
            while i > 0:
                s += self.bit[i]
                i -= i & -i
            return s

    def solve():
        data = sys.stdin.read().strip().split()
        n = int(data[0]); k = int(data[1])
        strings = data[2:]
        rev = [s[::-1] for s in strings]
        all_s = sorted(set(strings))
        all_r = sorted(set(rev))
        sid = {s:i+1 for i,s in enumerate(all_s)}
        rid = {s:i+1 for i,s in enumerate(all_r)}
        pts = [(i+1, sid[s], rid[rev[i]]) for i,s in enumerate(strings)]

        def count():
            pts_sorted = sorted(pts, key=lambda x:(x[1],x[0]))
            bit = Fenwick(n+5)
            j = 0
            res = 0
            for _,lex,rv in pts_sorted:
                while j < len(pts_sorted) and pts_sorted[j][1] <= lex:
                    bit.add(pts_sorted[j][2],1)
                    j+=1
                res += bit.sum(rv)
            return res

        return count() - count()

    return str(solve())

 ## 特殊なケース

 重要なエッジケースは、複数の文字列が同一である場合です。 この場合、辞書編集圧縮によって同じランクが割り当てられますが、フェンウィック構造は依然としてインデックスを区別して、次のペアのみが確実に存在するようにする必要があります。`i < j`カウントされます。 インデックスはスイープ中に使用される順序付けの一部であるため、アルゴリズムはこれを処理します。そのため、同一の文字列が自己ペアリングに崩壊することはありません。 

すべての文字列の長さが以下の場合、別のエッジ ケースが発生します。`k`。 この状況では、すべてのペアが自動的に有効になります。 との引き算`k + 1`特別な処理を必要とせずに、両方のカウントが同じ値に集約され、その差が解釈に応じて正しくゼロまたは完全な組み合わせカウントになることを保証します。 

3 番目のエッジ ケースは、単一の文字列による最小限の入力です。 ペアがないので両方とも`k`そして`k + 1`カウントはゼロであり、最終的な答えはゼロのままです。 ペアを形成する 2 番目の要素が存在しないため、スイープ構造は当然、寄与を生成しません。
