 ## 解決策
 ## 問題の理解

 私たちには大砲のセットが与えられており、各大砲は発砲するたびに一定量のダメージを与えます。 時間は不連続な秒単位で進み、各秒ごとにすべての大砲が同時に発射されます。 ただし、OwlBear には回転シールドがあります。k 番目の秒時点で、ちょうど 1 つの大砲、具体的には (k−1) mod n でインデックス付けされた大砲をブロックします。そのため、その秒の大砲はダメージをゼロにできますが、他のすべての大砲は依然として最大のダメージを与えます。 

すべてのクエリ値 h について、最初の t 秒間に与えられる累積ダメージの合計が少なくとも h になるように、最小の秒数 t を決定する必要があります。 

重要な点は、ブロックされる大砲が毎秒周期的に変化するため、各大砲は n 秒に 1 回だけブロックされ、長期間にわたって各大砲は均等にブロックされることです。 これにより、貢献に繰り返しパターンが生じます。 

この制約は、n が 100,000 まで、テスト全体の n と q の合計が 200,000 までであることを意味するため、どの解も線形またはテスト ケースごとの n log n に近い必要があります。 h が最大 10^9 になる可能性があり、1 秒あたりのダメージが十分に大きいため、応答が非常に大きな t に達する可能性があるため、すべての秒の単純なシミュレーションは不可能です。 

単純なアプローチでは、秒ごとにシミュレーションを試み、アクティブな大砲の合計を毎回再計算し、h に達するまで累積しようとする可能性があります。 これは、1 秒あたりのコストが O(n) であるため失敗します。最悪の場合、t も大きくなり、完全に実行不可能な O(n・t) になる可能性があります。 

より慎重なブルートフォースでは、すべての大砲の合計を事前に計算し、ブロックされた大砲を毎秒減算することでこれをわずかに改善しますが、それでも秒ごとにシミュレーションすると、大規模な応答には時間がかかりすぎます。 

h が小さい場合、それほど明白ではないエッジケースが現れます。 たとえば、h が 1 秒間に考えられる最大ダメージよりも小さい場合、答えは 1 になります。少なくとも完全なサイクルが必要であると想定する解決策は、ここでは失敗します。 

n = 2 の場合、別のエッジ ケースが発生します。シールドは 2 つの大砲の間で交互にブロックするため、毎秒異なる要素が除去されます。 このパターンは非常に規則的であり、モジュロ インデックス処理の誤りにより、大砲がどの秒でブロックされるかというオフバイワン エラーが発生することがよくあります。 

## アプローチ

 ブルートフォースの見方は簡単です。 各秒 k で、a[(k−1) mod n] を除くすべての a[i] の合計として合計ダメージを計算し、h に達するまで実行中のプレフィックスの合計を保持します。 これはルールに正確に従っているので正しいですが、毎秒最初から合計を計算すると O(n) のコストがかかり、合計の複雑さは O(n・t) になります。 t は大きくなる可能性があり、h は 10^9 まで無制限であるため、このアプローチはすぐにタイムアウトになります。 

重要な観察は、すべての大砲の合計が一定であることです。これを S と呼びます。各秒で、ちょうど 1 つの大砲が除外されるため、2 番目 k でのダメージは S − a[(k−1) mod n] となります。 n 秒の全サイクルにわたって、各大砲は 1 回だけ除外されるため、全サイクルの合計ダメージは n・S − S = (n−1)S となります。 

これにより、問題の構造が「動的再計算」から長さ n の固定反復配列 (各要素は S − a[i]) に縮小されます。 次に、合計が h に達する最小のプレフィックス長を見つける必要があります。これは、無限周期配列に対する標準的なプレフィックス合計 + 二分探索問題になります。 処理する必要があるのは完全なサイクルと部分的なサイクル プレフィックスだけです。これにより、前処理後にクエリごとに O(log n) で答えを計算できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n・t) | お(1) | 遅すぎる |
 | 周期パターンでのプレフィックス + 二分検索 | O(n + q log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. すべての大砲によるダメージの合計 S を計算します。 これは、大砲がブロックされなかった場合の 1 秒間のダメージを表します。 
2. b[i] = S − a[i] となる配列 b を構築します。 これは、大砲 i がブロックされたときの 2 番目の実際のダメージ寄与度を表します。 
3. 完全な 1 サイクルにわたって b に関するプレフィックス合計配列を構築します。 これにより、サイクルの任意のプレフィックスにわたるダメージを高速に計算できます。 
4. 1 つの完全なサイクルにおける合計ダメージを、cycle_sum = sum(b) として計算します。 
5. 各クエリ h について、まず、h をcycle_sum で割ることによって、必要な完全なサイクル数を決定します。 各完全なサイクルは固定量のダメージに寄与するため、シミュレーションなしで何秒間も直接ジャンプできます。 
6. 残りの必要なダメージを全サイクル後の残りの値に減らします。 
7. 残りの部分サイクルでは、プレフィックスの合計が残りのダメージに達する b の最小プレフィックス長をバイナリ検索します。これを周期的に繰り返します。 これが機能するのは、サイクル内ではシーケンスが固定されており、プレフィックスの合計が単調であるためです。 

### なぜ効果があるのか

 重要な不変条件は、毎秒のダメージが現在ブロックされているインデックスのみに依存し、そのブロック パターンが n 秒ごとに繰り返されるということです。 これにより、一連の秒ごとの損傷が周期 n で周期的であることが保証されます。 これが認識されると、プロセス全体は、固定配列の無限の繰り返しにわたってプレフィックスの合計を見つけることと同等になります。 周期配列上のプレフィックスの合計は完全なサイクルと部分的なサイクルに分解されるため、常に答えを完全なサイクルの線形数と 1 サイクル内の限定された検索に分離できます。 この構造により、この構築された配列内のプレフィックスの合計は単調であるため、貪欲検索またはバイナリ検索ステップで有効な短いプレフィックスがスキップされることがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        q = int(input())
        queries = [int(input()) for _ in range(q)]

        S = sum(a)
        b = [S - x for x in a]

        pref = [0] * (n + 1)
        for i in range(n):
            pref[i + 1] = pref[i] + b[i]

        cycle_sum = pref[n]

        for h in queries:
            full = h // cycle_sum
            rem = h % cycle_sum

            if rem == 0:
                out.append(str(full * n))
                continue

            lo, hi = 1, n
            ans = n
            while lo <= hi:
                mid = (lo + hi) // 2
                if pref[mid] >= rem:
                    ans = mid
                    hi = mid - 1
                else:
                    lo = mid + 1

            out.append(str(full * n + ans))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この解決策は、各秒のダメージをブロックされたインデックスごとに 1 つの値に圧縮することから始まります。 b のプレフィックス配列は 1 サイクル内の累積ダメージを取得し、cycle_sum は全回転の寄与を取得します。 各クエリについて、完全なサイクル数が除算によって抽出されるため、シミュレーションが回避されます。 

サイクル内では、ダメージの蓄積は時間の経過とともに確実に増加するため、二分探索ステップは非常に重要です。 これにより、プレフィックスの合計が残りの要件を超えると、それより長いすべてのプレフィックスも要件を満たし、検索が有効になることが保証されます。 

ここでよくある間違いは、ブロックされたインデックスが n 秒ごとにリセットされ、ラップアラウンドなしでグローバルに増加するわけではないことを忘れていることです。 それは周期構造を誤って破壊し、間違った答えにつながる可能性があります。 

## 実用的な例

 サンプル入力を使用します。 

n = 4、a = [2、3、2、7]

 まず S = 14 を計算します。つまり b = [12, 11, 12, 7]、cycle_sum = 42 となります。 

### クエリ 1: h = 27

 full = 27 // 42 = 0、rem = 27 を計算します。 

b の接頭辞を検索します。 

| 秒 | ブロックされたインデックス | プレフィックスの合計 |
 | --- | --- | --- |
 | 1 | 0 | 12 |
 | 2 | 1 | 23 |
 | 3 | 2 | 35 |

 2 番目の 3 では、35 ≥ 27 に達するため、答えは 3 になります。 

これは純粋な部分サイクルの場合を示しています。 

### クエリ 2: h = 12

 フル = 0、レム = 12。 

最初の 2 番目のプレフィックスはすでに 12 なので、答えは 1 です。 

これにより、最小しきい値が正しいことが確認されます。

 | 測定 | 複雑さ | 説明 |

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、必要なダメージ h が 1 番目と 2 番目の寄与よりも小さい場合です。 この場合、最初の 1 秒ですでに十分なダメージが得られるため、答えは 1 でなければなりません。 rem ≤ pref[1] の場合はすぐにバイナリ検索がトリガーされ 1 が返されるため、アルゴリズムはこれを処理します。 

別のケースは、h がcycle_sum の正確な倍数である場合です。 その場合、rem はゼロになり、答えは正確に全サイクル×n 秒でなければなりません。 コードは、full * n を返すことでこれを明示的に処理し、空の剰余への誤ったバイナリ検索を回避します。 

n = 2 の場合、ブロックされたインデックスは厳密に 0 と 1 の間で切り替わります。 b が各秒の寄与を独立して正しくエンコードし、独立性に関する仮定が違反されないことを保証するため、プレフィックスの構築は引き続き機能します。
