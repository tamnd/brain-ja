 ## 解決策
 ## 問題の理解

 各プレイヤーは最初、自分の色の 1 つの色のカードを所有しています。 プレーヤー`i`から始まる`a[i]`カード、すべてカラー`i`。 スワップでは、2 人のプレイヤーがそれぞれ 1 枚のカードを交換します。 プレイヤーは自分の色のカードのみを与えることができ、すでに所有している色のカードを受け取ることはできません。 

この目標は、単にカードを再配布するよりも強力です。 すべてのプレイヤーは、最終的には自分の色のカードをすべて取り除く必要があります。 プレイヤーは自分の色しか指定できないため、すべての色のカードが`i`プレイヤーに何も残らないまで、スワップを通じて譲渡する必要があります`i`。 

重複する色に関する制限が最大の難点です。 プレイヤーが色を受け取ったら`x`、他の色を受け取ることはできません`x`また。 スワップを不用意に繰り返すと、解決策が存在する場合でもプロセスが簡単にデッドロックする可能性があります。 

制約は大きいです。 両方`n`そして`s`までです`2 * 10^5`、スワップの総数も大きくなる可能性があります。 すべてのプレイヤーを繰り返しスキャンしたり、カードの所有権を明示的にシミュレートしたりするアルゴリズムは遅すぎます。 二次関数の動作は直ちに除外されます。 このソリューションは、生成されるスワップ数において線形時間に近い速度で動作する必要があります。 

隠れたカウント条件もあります。 交換するたびに、2 人のプレイヤーのそれぞれからちょうど 1 枚のカードが取り除かれます。 プレイヤーの場合`i`から始まる`a[i]`カード、次にプレイヤー`i`正確に参加しなければなりません`a[i]`スワップするたびにカードを 1 枚手放すことができるためです。 すべてのプレイヤーを合計すると:$$\sum a[i]$$すべてのスワップが寄与するため、均等である必要があります`2`合計参加数に加算されます。 

その条件だけでは十分ではありません。 また、1 人のプレイヤーが他のプレイヤーの合計より多くの回数参加することはできません。 誰かのプレイヤーが他のプレイヤーよりも多くのカードを持っている場合、最終的にはこのプレイヤーにはまだカードが残っているにもかかわらず、他のプレイヤーはスワップを使い果たします。 

例えば：```
3 5
5 0 0
```プレイヤー 1 は 5 つのスワップを必要としますが、プレイヤー 2 と 3 は一緒に 0 スワップしか参加できません。 正しい答えは、`No`。 

別の微妙なケースは次のとおりです。```
3 3
1 1 1
```合計が奇数になります。 すべてのスワップでは 2 枚のカードが消費されるため、どのシーケンスでも 3 枚のカードすべてを完了することはできません。 正しい答えは、`No`。 

より興味深い有効なケースは次のとおりです。```
4 4
2 1 1 0
```単純な貪欲な戦略では、受信した色を慎重に追跡せずに、最大数を繰り返しペアリングする可能性があります。 これにより、後で重複色の競合が発生する可能性があります。 ペアを繰り返すと各プレーヤーが同じ色を 2 回受け取ることになるため、正しい構造では、プレーヤーのペアが複数回交換されないことを保証する必要があります。 

この観察は重要な構造的洞察となります。 

## アプローチ

 この問題を考える強引な方法は、カードの所有権を直接シミュレートすることです。 すべてのステップで、合法的に交換できる 2 人のプレイヤーを検索し、交換を実行し、所有権セットを更新し、すべてのカードが消えるか合法的な手がなくなるまで続行します。 

このアプローチはゲームのルールに文字通り従うため、最終的に成功すれば正しいものになります。 問題は効率と状態の複雑さです。 各プレイヤーは多くの色を蓄積する可能性があるため、合法性を確認するには大規模なセットを維持する必要があります。 さらに悪いことに、どのペアを交換するかを決めるのは簡単ではありません。 ローカルの選択を誤ると、有効なグローバル ソリューションが存在する場合でも、後でデッドロックになる可能性があります。 

最悪の場合、次のような事態が起こる可能性があります。$$\frac{\sum a[i]}{2}$$スワップが発生し、各ステップでの有効なペアの単純な検索は 2 次またはそれ以上のものになります。 

重要な観察は、プレイヤーは同じ色を二度受け取ることはできないということです。 プレイヤー以来`i`いつも色を与えてくれる`i`、他のプレイヤーとプレイヤーを交換できます`i`多くても一度。 

それは問題を完全に変えます。 

カードについて考える代わりに、グラフについて考えてください。 プレイヤー間のすべての交換`u`そして`v`1つのエッジを作成します。 2 人のプレイヤーが 2 回交換することはできないため、グラフは単純でなければなりません。 プレイヤーの程度`i`正確に等しい`a[i]`, すべてのカードを配るには、それだけ多くのスワップに参加しなければならないからです。 

タスクは次のようになります。 

単純な無向グラフを構築します。`n`次数シーケンスが次である頂点`a`。 

これは古典的なグラフィック シーケンスの問題です。 

グラフィカル シーケンスの標準的な貪欲な構築は、Havel-Hakimi プロセスです。 残りの次数が最大の頂点を繰り返し取得し、それを他のいくつかの最高次数の頂点に接続します。 接続するたびに、両方の次数が 1 ずつ減少します。 

これはスワップの解釈と完全に一致します。 接続中`u`そして`v`つまり、それらの間のスワップを 1 回だけスケジュールすることになります。 

ブルート フォース シミュレーションは、一時的なカード所有権状態を考慮するため失敗します。 グラフの解釈により、その複雑さは完全に解消されます。 エッジの繰り返しがないことを確認すると、色の制約が自動的に満たされます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(s²) 以上 | O(s) | 遅すぎる |
 | 最適 | O(s log n) | O(s) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 度数列を読む`a[i]`。 
2. 度数の合計が偶数であるかどうかを確認します。 

すべてのスワップは度に貢献します`2`、各エンドポイントに 1 つ。 合計が奇数の場合、すぐには解決できなくなります。 
3. 正の次数を持つすべてのプレーヤーを、残りの次数順に並べられた最大ヒープに挿入します。 
4. プレーヤーを繰り返し抽出する`u`残りの次数が最大の`d`。 

プレーヤー`u`まだ必要です`d`異なるスワップパートナー。 
5. 数が少ない場合`d`他のプレイヤーがヒープ内に残っている場合、構築は不可能です。 

単純なグラフでは、1 つの頂点を現在存在する頂点よりも多くの個別の頂点に接続することはできません。 
6.次の項目を一時的に削除します`d`ヒープの中から最高位のプレイヤーを集めます。 
7. 抽出された各プレーヤーについて`v`:

 1. スワップを追加する`(u, v)`答えに。 
2. 減少`v`の残り度は1つです。 
3.ストア`v`度数がプラスのままの場合は再挿入します。 
8. すべての処理が完了したら`d`近隣のプレイヤーは、更新されたすべてのプレーヤーをヒープに再挿入します。 
9. ヒープが空になるまで続行します。 
10. 構築されたすべてのエッジをスワップとして出力します。 

### なぜ効果があるのか

 不変条件は、残りの次数が常に、部分的に構築された単純なグラフの未完了のスワップ要件を記述することです。 

最大次数の頂点を削除すると`u`それを接続します`d`異なる頂点がある場合、必要な残りのスワップをすべて満たします。`u`ワンステップで。 選択されたすべての近傍は個別であるため、繰り返されるエッジは表示されません。 各エッジは 1 つのスワップに対応するため、同じ色を 2 回受け取るプレイヤーはいません。 

ハベル・ハキミの定理は、グラフィカルな実現が存在する場合、この貪欲な削減によって実現可能性が維持されることを保証します。 あるステップで、接続するための十分な個別の頂点が存在しない場合、必要な次数を持つ単純なグラフは存在できません。 

したがって、アルゴリズムは、有効なスワップ スケジュールが存在する場合に正確にそれを構築します。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, s = map(int, input().split())
    a = list(map(int, input().split()))

    if sum(a) % 2:
        print("No")
        return

    pq = []

    for i, deg in enumerate(a, 1):
        if deg > 0:
            heapq.heappush(pq, (-deg, i))

    ans = []

    while pq:
        deg_u, u = heapq.heappop(pq)
        deg_u = -deg_u

        if deg_u > len(pq):
            print("No")
            return

        taken = []

        for _ in range(deg_u):
            deg_v, v = heapq.heappop(pq)
            deg_v = -deg_v

            ans.append((u, v))

            deg_v -= 1

            if deg_v < 0:
                print("No")
                return

            if deg_v > 0:
                taken.append((-deg_v, v))

        for item in taken:
            heapq.heappush(pq, item)

    print("Yes")
    print(len(ans))

    for u, v in ans:
        print(u, v)

solve()
```ヒープにはペアが格納されます`(-degree, vertex)`そのため、Python の最小ヒープは最大ヒープのように動作します。 

最もデリケートな部分は実現可能性のチェックです。```
if deg_u > len(pq):
```プレーヤー`u`ニーズ`deg_u`明確な隣人。 残っている頂点の数がそれより少ない場合、単純なグラフの構築は不可能です。 

もう 1 つの微妙な点は、隣接要素をデクリメントした後すぐに再挿入しないことです。 まずすべてを削除します`deg_u`近隣のノードは、それらを 1 回ずつ処理してから、更新された値をプッシュバックします。 これにより、隣接するすべてのエッジが明確になることが保証され、エッジの重複が防止されます。 

アルゴリズムがカードの色を明示的に追跡することはありません。 グラフ構造にはすでに色のルールが適用されています。 プレーヤーの各ペアは最大 1 回交換するため、どのプレーヤーも同じ色を 2 回受け取ることはできません。
