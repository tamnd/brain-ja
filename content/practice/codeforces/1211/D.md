 ## 問題の理解

 プレイヤーには複数の評価が与えられています。 各プレイヤーは最大 1 回しか使用できません。私たちの目標は、厳密な構造上の制約の下で、できるだけ多くのバラバラなチームを形成することです。 

すべての有効なチームは、2 つの同種のプレーヤー グループで構成されます。 あるグループはまさに`a`プレイヤー全員が同じレーティング値を共有`x`。 2番目のグループはまさに`b`プレイヤー全員が別の評価値を共有`k · x`。 チームは、これら 2 つのグループが同時に存在し、すべてのチームにわたって素である場合にのみ有効です。 

したがって、各チームは基本的に数字のカウント間の組み合わせルールになります。`a`何らかの値のコピー`x`、 そして`b`価値のコピー`k·x`。 さまざまなチームが値の頻度を消費し、プレーヤーが一度使用されると、再度参加することはできません。 

課題は、そのようなチームをどれだけ多く構築できるかを最大化することです。 

入力サイズは最大 300,000 要素に達するため、構造なしで貪欲にチームの形成を繰り返しシミュレートしようとするソリューションは遅すぎます。 たとえ$O(n^2)$ペアリング戦略は、多くの周波数バケット間の互換性を繰り返し確認する必要があるため、すぐには実行不可能です。 唯一の実行可能な方向は、配列を周波数に圧縮し、構造化された順序 (通常は対数またはほぼ線形) で値を処理することです。 

微妙な問題は、選択肢が価値観を越えて相互作用することです。 貪欲に値を一致させると`x`早すぎても遅すぎても、利用可能性に影響する可能性があります。`k·x`したがって、順序を慎重に制御しない単純な貪欲なアプローチは失敗する可能性があります。 

よくある失敗例は次のとおりです。十分な情報が得られたらすぐにチームを結成しようとしているとします。`x`そして`k·x`、将来の貢献を考慮せずに。 これにより、後でより最適なペアリングに必要な価値の高い要素が無駄になる可能性があります。 

もう 1 つの問題は順序付けです。`k·x`よりも大きいです`x`、昇順で処理することで常に処理できるようになります。`x`まず制約を前進させて、状態を再検討することを避けます。 

## アプローチ

 強引なアイデアは、頻度の観点から考え、可能なすべてをスキャンしてチームの構築を繰り返し試行することです。`x`かどうかを確認します`freq[x] >= a`そして`freq[k·x] >= b`、そしてチームを引き算して数えます。 変化が起こらなくなるまでこれを繰り返すことは概念的には正しいですが、非常に時間がかかります。 最悪の場合、各反復で削除されるチームは 1 つだけになる可能性があり、すべての値をスキャンするとコストがかかります$O(U)$、につながる$O(U \cdot \text{answer})$、両方が大きい場合は大きすぎます。 

重要な観察は、この問題は完全に周波数と、周波数間の決定的なペアリングによって引き起こされるということです。`x`そして`k·x`。 与えられた回数を修正したら`x`チームの拠点として使用されると、すべてが強制的になります。 唯一の実際の決定は、各値から何チームを取得するかですが、値を昇順に処理する場合、この決定はローカルです。 

標準的な最適化では、マップまたは配列内の頻度を維持し、ソートされた順序で値を反復処理します。 それぞれの値について`x`、利用可能なリソースを使用して形成できるチームの数を計算します。`x`最初のグループとして。 このような各チームが消費するのは、`a`のコピー`x`そして`b`のコピー`k·x`。 頻度を更新します`k·x`それに応じて。 

なぜなら`k·x`常により大きい`x`、到着したら`x`、の周波数`x`これは最終的なものであり、将来の操作によって変更されることはありません。 これにより、1 回のパスで十分になります。

 ## アルゴリズムのチュートリアル

 まず入力を評価の周波数マップに圧縮します。 これにより、無関係な順序が削除され、問題が算術オーバーカウントに変わります。 

次に、すべての個別の評価を昇順に並べ替えて、すべての値が複数の評価の前に処理されるようにします。`k·x`。 

1. 頻度表を作成する`freq[v]`すべての評価について。 このステップが必要なのは、位置ではなくカウントのみが重要であるためです。 
2. すべての個別の値を抽出し、それらを徐々に並べ替えます。 並べ替えにより、値を処理するときに次のことが保証されます。`x`、考えられるすべての将来の消費者`k·x`まだ処理されていないか、影響を与えません`x`後で。 
3. 各値を反復処理します。`x`ソートされた順序で。 この瞬間、`freq[x]`最終的に利用可能な数を表します`x`。 
4. 何チームから開始できるかを計算します。`x`低評価グループとして。 これは`t = freq[x] // a`。 各チームが必要とするため、これ以上の編成はできません`a`のコピー`x`。 
5. ただし、利用可能かどうかによっても制限されます。`k·x`。 そこでキャップを付けます`t`による`freq[k·x] // b`。 これにより、使いすぎを防ぐことができます`k·x`。 
6.追加`t`答えに。 次に、リソースを減算します。`freq[x]`による`t · a`そして減らす`freq[k·x]`による`t · b`。 これにより、素的な使用が強制されます。 

重要な点は、決して再考しないことです`x`。 残っているもの`x`すべての 2 番目のグループは厳密に大きい値を必要とするため、後続のステップで 2 番目のグループとして使用されないため、処理後は後で使用することはできません。 

### なぜ効果があるのか

 このアルゴリズムは方向依存性を強制します。つまり、どのチームも小さい値をソースとして使用し、大きい値をシンクとして使用します。 昇順に処理することで、一度割り当てた使用法を確実にします。`x`、その後の操作が遡って影響を与えることはできません。 したがって、各値は 1 回だけ決定され、形成されるすべてのチームはローカル制約が与えられた場合に最大になります。 これによりサイクルが排除され、貪欲なローカル ペアリングが将来の最適なペアリングをブロックしないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, a, b, k = map(int, input().split())
    arr = list(map(int, input().split()))
    
    from collections import Counter
    freq = Counter(arr)
    
    vals = sorted(freq.keys())
    
    ans = 0
    
    for x in vals:
        if freq[x] == 0:
            continue
        y = x * k
        
        if y not in freq:
            continue
        
        # number of possible teams from x
        t = min(freq[x] // a, freq[y] // b)
        
        if t > 0:
            freq[x] -= t * a
            freq[y] -= t * b
            ans += t
    
    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、純粋にカウントだけで推論できるように、最初に頻度マップを構築します。 キーを並べ替えると、常に小さい評価が最初に処理されるようになります。 

ループ内では、両方の場合にのみペアリングを試行します。`x`そして`k·x`存在する。 ボトルネックの計算では両側で整数の除算を使用し、両方の制約を同時に考慮するために最小値を取得します。 頻度テーブルを更新すると、プレーヤーが再利用されなくなります。 

よくある落とし穴は、からの引き算を忘れることです。`freq[y]`。 これがないと、後の値ですでに使用されている要素が誤って再利用され、答えが膨張してしまいます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import Counter

    n, a, b, k = map(int, sys.stdin.readline().split())
    arr = list(map(int, sys.stdin.readline().split()))
    
    freq = Counter(arr)
    vals = sorted(freq.keys())
    
    ans = 0
    for x in vals:
        y = x * k
        if freq[x] == 0 or y not in freq:
            continue
        t = min(freq[x] // a, freq[y] // b)
        freq[x] -= t * a
        freq[y] -= t * b
        ans += t
    
    return str(ans)

# provided sample
assert run("12 1 2 2\n1 1 2 2 2 2 2 3 3 4 6 6\n") == "3"

# all equal no pairing
assert run("5 2 2 2\n1 1 1 1 1\n") == "0"

# exact single team
assert run("3 1 2 2\n1 2 2\n") == "1"

# chain interference
assert run("6 1 1 2\n1 1 2 2 4 4\n") == "2"

# large k break (no multiples)
assert run("4 1 1 10\n1 1 2 2\n") == "0"

 | 最小有効 | 1 | シングルチーム編成 |
 | チェーンケース | 2 | 複数の相互作用 |
 | 大きなk | 0 | パートナーがいないとチームが妨げられる |

 ## 特殊なケース

 重要なエッジケースは、複数の値が次のように機能する場合です。`k·x` for different `x`。 たとえば、両方の場合、`x`そして`x/k`配列内に存在する場合、不用意に貪欲な減算を行うと、共有プールを過剰に消費する可能性があります。 ソートされた順序処理はこれを防ぎます。`x`処理され、再検討されることはなく、すべての使用法は最小のソースで決定されます。
