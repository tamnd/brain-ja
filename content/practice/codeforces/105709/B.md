 ## 解決策
 ## 問題の理解

 このタスクは、ルート付きツリーを維持し、ノードのペア間の関係クエリに答えることです。 ツリー内の任意の 2 つのノードについて、それらの最も低い共通の祖先、つまりルートから両方へのパス上にあるルート構造の最も深いノードを決定する必要があります。 

入力は、エッジによって記述されたツリーとして解釈され、その後に複数のクエリが続きます。 各クエリでは 2 つのノードが与えられ、ルートへのパスが最初に合流する場所を表す 1 つのノードを返さなければなりません。 

明示的な制約がない場合でも、この種の問題には、ほとんどの場合、最大数十万のノードとクエリが関係します。 これにより、一度に 1 ステップずつ上に向かって進み、すべてのクエリのパスを再計算するアプローチは即座に除外されます。これは、最悪の場合、二次関数の動作に低下するためです。 ソリューションでは、各クエリが対数時間またはほぼ一定の時間で応答できるようにツリーを前処理する必要があります。 

いくつかのエッジな状況では、単純な実装が壊れる傾向があります。 ツリーがチェーンである場合 (1 が 2 に接続され、3 が 4 に接続されている)、エンドポイントの最も低い共通の祖先は常にチェーン内の上位の祖先になります。 単純な上向き歩行ソリューションでは、クエリごとに 1 ステップを繰り返し登る可能性があり、ツリーの深さに比例した最悪の場合のコストが発生します。 

もう 1 つの微妙なケースは、一方のノードが他方のノードの祖先である場合に発生します。 たとえば、ノード 2 がノード 5 の親である場合、クエリ (2, 5) に対する答えは 2 でなければなりません。深さを誤って等化しようとしたり、祖先をオーバーシュートしたりするアプローチは、等化の瞬間に慎重に停止しないと、簡単に正しいノードを通り過ぎてしまう可能性があります。 

## アプローチ

 2 つのノードのクエリに答える最も直接的な方法は、ルートへのパスを再構築して比較することです。 各ノードの親を保存し、クエリごとに、ルートに到達するまで各ノードを繰り返し上向きに移動し、訪問したノードを記録します。 最下位の共通祖先が、これら 2 つのパスの最後の共有ノードになります。 

すべてのノードには親が 1 つだけ存在するため、ルートへの各パスは一意に定義されるため、これは正しく機能します。 ただし、クエリごとにこれらのパスを構築するとコストがかかります。 ツリーの高さが n に比例し、クエリが q 個ある場合、このアプローチではクエリごとに O(n) の作業が必要になり、合計操作数が O(nq) になる可能性があります。n と q の両方が大きい場合、これは遅すぎます。 

重要な観察は、繰り返し上向きの動きがクエリ間で冗長であるということです。 ツリーの構造は変わらないため、祖先関係を事前に計算できます。 一度に 1 つの親をステップ実行する代わりに、ノードごとにサイズの 2 のべき乗のジャンプを事前計算できます。 これにより、任意のノードを大きなステップで上方に持ち上げることができ、対数時間で中間の祖先を効果的にスキップできます。 

この手法はバイナリ リフティングとして知られています。 up[k][v] がノード v の 2^k 番目の祖先を表すテーブルを保存します。この構造を使用すると、最初に両方のノードを同じ深さに位置合わせし、次にそれらが一致するまで、可能な限り高い 2 のべき乗から下方向にそれらを一緒に持ち上げることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース (パスウォーキング) | クエリあたり O(n) | O(n) | 遅すぎる |
 | バイナリリフティング | O((n + q) log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. ノード 1 でツリーをルートし、深さ優先検索または幅優先検索を実行して、すべてのノードの親と深さを計算します。 これにより基準フレームが確立されるため、すべてのノードがルートからどのくらい離れているかを知ることができます。 
2. up[0][v] が v の直接の親であり、up[k][v] が up[k-1][up[k-1][v]] として定義されるバイナリ リフティング テーブルを構築します。 これにより、指数関数的に増加する距離にある祖先がエンコードされます。 
3. log2(n) までのすべての k についてテーブルを事前計算します。 これにより、対数ステップ数で任意の距離をジャンプできることが保証されます。 
4. 各クエリ (u、v) について、まずそれらの深さを比較します。 1 つのノードが深い場合は、両方のノードが同じ深さになるまで、バイナリ リフティング テーブルを使用してノードを上方に持ち上げます。 これにより、段階的に移動する必要がなくなります。 
5. 両方のノードの深さを調整したら、それらがすでに同じかどうかを確認します。 そうである場合、そのノードは最下位の共通祖先です。 
6. それらが異なる場合は、両方のノードを 2 の最大累乗から 0 まで上方に持ち上げてみます。 特定のレベルの祖先が異なる場合は常に、両方のノードを同時に上に移動します。 これにより、LCA の下でそれらの同期が維持されます。 
7. すべてのジャンプが完了すると、両方のノードが最も低い共通祖先の直接の子になるため、どちらかの親を返すと答えが得られます。 

### なぜ効果があるのか

 正確さは祖先テーブルの構造から得られます。 アルゴリズムで上向きに移動するたびに、真の LCA が両方のノードの上にあるという不変条件が維持されます。 ノードを同じ深さまで持ち上げる場合、それらの相対的な祖先は変更せず、ルートからの距離を揃えるだけです。 次に、2 の高い累乗から下方向への大きなジャンプを試みるときは、LCA をオーバーシュートしない場合にのみジャンプを実行します。 これにより、正しい祖先を決してバイパスしないことが保証され、最終的には両方のノードがまだ LCA より厳密に下にある最上位のノードに収束するため、それらの親は LCA 自体でなければなりません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    n = int(input())
    adj = [[] for _ in range(n + 1)]

    for _ in range(n - 1):
        u, v = map(int, input().split())
        adj[u].append(v)
        adj[v].append(u)

    LOG = (n).bit_length()

    up = [[0] * (n + 1) for _ in range(LOG)]
    depth = [0] * (n + 1)

    stack = [(1, 0)]
    parent = [0] * (n + 1)
    parent[1] = 1

    while stack:
        node, p = stack.pop()
        parent[node] = p
        for nei in adj[node]:
            if nei == p:
                continue
            depth[nei] = depth[node] + 1
            stack.append((nei, node))

    for v in range(1, n + 1):
        up[0][v] = parent[v]

    for k in range(1, LOG):
        for v in range(1, n + 1):
            up[k][v] = up[k - 1][up[k - 1][v]]

    def lift(x, dist):
        k = 0
        while dist:
            if dist & 1:
                x = up[k][x]
            dist >>= 1
            k += 1
        return x

    def lca(a, b):
        if depth[a] < depth[b]:
            a, b = b, a

        a = lift(a, depth[a] - depth[b])

        if a == b:
            return a

        for k in range(LOG - 1, -1, -1):
            if up[k][a] != up[k][b]:
                a = up[k][a]
                b = up[k][b]

        return up[0][a]

    q = int(input())
    out = []
    for _ in range(q):
        u, v = map(int, input().split())
        out.append(str(lca(u, v)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装は、ツリーの隣接リスト表現を構築することから始まります。 親配列と深さ配列は、ノード 1 をルートとするスタックベースの走査で計算され、すべてのノードがその直接の祖先とルートからの距離を確実に認識します。 

次に、バイナリリフティングテーブルはボトムアップで充填されます。 重要な詳細は、up[k][v] が up[k-1][v] に依存するため、小さなジャンプは大きなジャンプの前に計算する必要があるということです。 

リフト関数は深度均等化ステップを実行します。 距離をバイナリで解釈し、設定されたビットに対応するジャンプを適用します。 これは、一度に 1 レベルずつ繰り返し移動するよりも効率的です。 

lca 関数は、最初に深さを正規化し、次に 2 のべき乗に対するトップダウン チェックを実行します。 条件 up[k][a] != up[k][b] により、祖先がまだ安全に LCA 以下にある場合にのみ移動することが保証されます。 

## 実用的な例

 1 を根とする小さな木を考えてみましょう。 

入力エッジ:

 1-2、1-3、2-4、2-5

 クエリ: (4, 5)

 両方のノードの深さは 2 です。アルゴリズムはリフティング ステップをスキップします。 最高のジャンプ レベルでは、リフティング決定後のノード 2 で両方のノードが同じ祖先を共有するため、結果は 2 になります。 

| ステップ | | b | アクション |
 | --- | --- | --- | --- |
 | 開始 | 4 | 5 | 同じ深さ |
 | k=2をチェック | 2 | 2 | 両方とも互いの祖先とは異なります。 
| 最終 | 2 | 2 | 親を返す |

 これにより、兄弟が正しく処理されることが確認されます。 

次にクエリ (3, 4) を考えてみましょう。 

ノード 3 は深さ 1 にあり、ノード 4 は深さ 2 にあるため、4 は 2 のレベルにリフトされて 2 になります。 ここで (3, 2) を比較すると、それらは異なり、最も高い有効なリフトは、それらの親が 1 に収束していることを示しています。 

| ステップ | | b | アクション |
 | --- | --- | --- | --- |
 | 開始 | 3 | 4 | 深さが違う |
 | リフト | 3 | 2 | 深さを均等にする |
 | チェック | 3 | 2 | 上に移動 |
 | 最終 | 1 | 1 | 1を返す |

 これは、異なる深さのノードの正しい処理を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n) | リフティング テーブルの構築には n log n がかかり、各クエリには log n がかかります。 
| スペース | O(n log n) | 祖先テーブルにはノードごとにログ n エントリが保存されます。 

これは、最大 200,000 のノードとクエリのツリーに対する一般的な制約内に快適に適合します。

 ## 特殊なケース

 1-2-3-4 などのチェーン形状のツリーは、リフティング ロジックが最大深さの差を正しく処理するかどうかをテストします。 クエリ (4, 1) の場合、アルゴリズムはバイナリ ジャンプによってノード 4 を持ち上げます。4 は 2、次に 1 にジャンプしますが、ノード 1 は変更されません。 1 のすべての祖先自体がルート表現内にあるため、最後の比較は 1 に正しく収束します。 

2 が 5 のすぐ上にあるツリー内のクエリ (2, 5) など、あるノードが別のノードの祖先であるケースでは、深さの等化がオーバーシュートしないことが確認されます。 リフト後、ノード 5 は 2 になり、ノードはすぐに一致するため、アルゴリズムは不要な上方移動を行わずに 2 を返します。
