 ## 解決策
 ## 問題の理解

 私たちにはフィンチのコレクションが与えられており、それぞれのフィンチは最初は別々の保護区に住んでいます。 すべてのフィンチには、固定された一連の特性が付属しており、各特性の位置は、からの小さなアルファベットの文字です。`'a'`に`'j'`。 ダーウィンは時間の経過とともに、これらの特性に基づいて保護区を統合する操作を実行します。その結果、それぞれの保護区がどれくらいの大きさになるか、そして最大の保護区が全体でどれくらいの大きさになるかを継続的に追跡する必要があります。 

このプロセスは 3 種類の操作によって推進されます。 1 回の操作で特定の特性位置が有効になり、その瞬間から、その位置で同じ特性を共有する少なくとも 1 羽のフィンチを含む 2 つの聖域は接続されているとみなされ、効果的にマージされます。 これは 1 回限りのマージではありません。 これは、永続化され、以前のアクティベーションと相互作用するグローバル ルールです。 別の操作では、特定のフィンチがいる保護区のサイズを尋ねます。 最後の操作では、現在形成されている最大の保護区のサイズを尋ねます。 

この制約は、アクティベーションのたびに接続を最初から再構築する余裕がないことを示唆するような厳しいものです。 最大 100,000 のフィンチ、100,000 の特性、および 100,000 のクエリがあり、特性文字列の合計入力サイズは約 100 万文字に制限されます。 クエリごとにすべてのフィンチにわたる接続性を繰り返し再計算するソリューションは、クエリごとの線形スキャンでさえすでに 10^10 の演算に近づいているため、遅すぎます。 

同じ特性インデックスを繰り返しアクティブ化すると、微妙な問題が発生します。 素朴なアプローチが各アクティベーションを独立して扱い、そのアクティベーションに対してのみユニオンを再計算する場合、以前のマージによってコンポーネント構造がすでに変更されているという事実を誤って見逃してしまう可能性があります。そのため、今後のアクティベーションは元のフィンチではなく、すでにマージされたグループに対して操作する必要があります。 

もう 1 つの特殊なケースは、特性位置内の繰り返し文字から発生します。 多くのフィンチが同じ位置で同じ文字を共有する場合、処理順序に依存するペアごとのマージではなく、すべてのフィンチが単一の連結コンポーネントになる必要があります。 適切なグループ化を行わずに単純なペアごとのマージを行うと、部分的な接続や二次関数の爆発が発生する可能性があります。 

具体的な失敗シナリオとして、すべてのフィンチが同じ性格を持っていると仮定します。`'a'`位置 1 で、その位置をアクティブにします。 すべてのペアを結合する単純なアプローチでは、約 n^2 の演算が実行されますが、これではすでに遅すぎます。 正しい動作は、それらすべてがただちに単一の接続コンポーネントになることです。 

## アプローチ

 ブルートフォース戦略では、マージプロセスを直接シミュレートします。 私たちは各保護区でフィンチの群れを明示的に維持しています。 特性の位置がアクティブになると、すべてのフィンチをスキャンし、その位置で同じ特性を共有するフィンチをグループ化し、それらのセットをマージします。 クエリ タイプ 2 はフィンチを含むセットのサイズをカウントし、タイプ 3 は最大セット サイズを追跡します。 

このアプローチの正しさは、文字通りルールに従っているため簡単です。すべてのアクティベーションが特性に基づいて新しい等価関係を強制し、それに応じてセットがマージされます。 問題はそのコストです。 各アクティベーションでは、すべてのフィンチをスキャンし、場合によっては多くのマージを実行する必要があります。 n と q が最大 10^5 の場合、最悪の場合、およそ O(nq) の動作が発生しますが、これは実現可能性をはるかに超えています。 

重要な観察は、プロセスの構造が基本的に二部構成の動的な接続問題であるということです。フィンチは活性化された位置で共有される特性値を通じてのみ接続します。 最初は各フィンチが孤立しており、徐々にエッジが現れます。 エッジ タイプ (特性インデックス) がアクティブになると、そのインデックスにあるすべての等しい文字グループが一度に完全に接続されます。 

これは、フィンチをマージの主な対象として直接扱うべきではないことを示唆しています。 代わりに、特性位置ごとにキャラクターごとにフィンチを事前に 1 回グループ化し、クエリ時にグループ全体をアクティブ化することで、各アクティブ化の効果を少数の結合操作に圧縮します。 コンポーネントをマージするだけで分割することがないため、素集合結合 (DSU) 構造が自然なツールになります。 

すべての特性インデックスとすべての文字について、その位置にその文字を持つフィンチのリストを前処理します。 次に、特性がアクティブ化されると、その特性の各キャラクター バケット内のすべてのフィンチを結合します。 各フィンチは最大で k 個のバケットに参加し、各バケットは 1 回だけ処理されるため、合計の結合作業はすべてのアクティベーションにわたって nk で線形になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(nk) | 遅すぎる |
 | 最適 (DSU + グループ化) | O(nk + q α(n)) | O(nk) | 承認済み |

 ## アルゴリズムのチュートリアル

 各フィンチを素集合和集合構造のノードとして表します。 各ノードは、サイズ 1 の独自のコンポーネントで開始します。 また、最大コンポーネント サイズを追跡するグローバル変数も維持します。 

各特性インデックスとキャラクターを、その位置でその正確な値を持つフィンチのリストにマッピングする構造を事前計算します。 これにより、入力文字列が、将来のすべてのマージ操作を表すバケットのコレクションに変換されます。 

次に、クエリを順番に処理しますが、各特性インデックスが最大 1 回アクティブ化されるようにします。 これを繰り返しても追加の効果はないため、ブール配列は特性がすでに適用されているかどうかを追跡します。 

アルゴリズムは次のように進行します。 

1. n 個のノード上に DSU を構築し、親ポインター自体を初期化し、サイズを 1 に設定します。最大コンポーネント サイズは 1 から始まります。これにより、DSU に格納されているすべてのコンポーネント サイズが正確であるという不変条件が確立されます。 
2. すべての特性位置 j およびすべての文字 c について、フィンチ i の位置 j に文字 c があるすべてのインデックス i を格納するようにバケットを事前計算します。 このステップでは、今後のアクティブ化を一連のバッチ ユニオンに変換します。 
3. 特性 j がすでに処理されているかどうかを追跡する配列 active[j] を維持します。 これにより、作業の繰り返しが防止され、各グループが 1 回だけマージされることが保証されます。 
4. 特性 j を持つタイプ 1 のクエリの場合、アクティブ化されていない場合は、次のすべての文字を反復処理します。`'a'`に`'j'`。 位置 j の各キャラクター バケットについて、そのバケット内のすべてのフィンチとバケット内の最初のフィンチを繰り返し結合します。 これにより、(j, 文字) ごとに単一の連結成分が形成されます。 処理後、j をアクティブ化済みとしてマークします。 
5. タイプ 2 のクエリの場合、クエリされたフィンチを含む DSU コンポーネントのサイズを出力します。 
6. タイプ 3 のクエリの場合、グローバル最大コンポーネント サイズを出力します。 

重要な実装の詳細は、バケットを処理するときに、すべてのペアを結合しないことです。 代わりに、代表的な要素を選択し、他のすべての要素をそれにマージして、バケットごとの直線的な作業を保証します。 

### なぜ効果があるのか

 各アクティベーションにより、「位置 j で同じ文字を共有するフィンチは 1 つのグループに属する」という形式の等価関係が導入されます。 これらの関係は各文字クラス内で推移的であるため、各バケットは誘導されたグラフ内で完全なクリークを形成します。 DSU は、段階的なエッジ挿入の下で接続されたコンポーネントを正しく維持します。 各バケットは 1 回だけ処理されるため、必要なエッジはすべて 1 回だけ追加され、接続する必要がある 2 つのフィンチが少なくとも 1 つのアクティブ化された (j, 文字) ペアを共有し、そのバケット内でマージされるため、接続の欠落は発生しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class DSU:
    def __init__(self, n):
        self.parent = list(range(n))
        self.size = [1] * n
        self.max_size = 1

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]
            x = self.parent[x]
        return x

    def union(self, a, b):
        a = self.find(a)
        b = self.find(b)
        if a == b:
            return
        if self.size[a] < self.size[b]:
            a, b = b, a
        self.parent[b] = a
        self.size[a] += self.size[b]
        if self.size[a] > self.max_size:
            self.max_size = self.size[a]

n, k, q = map(int, input().split())
traits = [input().strip() for _ in range(n)]

buckets = [[[] for _ in range(10)] for _ in range(k)]
for i in range(n):
    for j, ch in enumerate(traits[i]):
        buckets[j][ord(ch) - 97].append(i)

dsu = DSU(n)
used = [False] * k

for _ in range(q):
    tmp = input().split()
    t = int(tmp[0])

    if t == 1:
        j = int(tmp[1]) - 1
        if used[j]:
            continue
        used[j] = True

        for c in range(10):
            lst = buckets[j][c]
            if not lst:
                continue
            root = lst[0]
            for v in lst[1:]:
                dsu.union(root, v)

    elif t == 2:
        i = int(tmp[1]) - 1
        print(dsu.size[dsu.find(i)])

    else:
        print(dsu.max_size)
```DSU 実装では、サイズによるパス圧縮と結合を使用するため、大きなバケット間で繰り返しマージが効率的に行われます。 バケット配列は特性情報を圧縮して、各結合演算が (位置、文字) ごとに 1 回だけ生成されるようにします。 使用された配列により、特性インデックスを再処理することがなくなります。再適用すると不必要に共用体が繰り返されるため、これは重要です。 

微妙な点の 1 つは、結合は常にバケットの固定された代表に対して相対的に実行されることです。 これにより、任意の p を繰り返しマージした場合に発生する二次関数の動作が回避されます。
