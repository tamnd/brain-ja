 ## 解決策
 ## 問題の理解

 括弧文字列のコレクションが与えられます。各文字列は開き括弧と閉じ括弧の混合です。 これらの文字列から、素のペアを形成することができます。 各文字列は最大 1 回使用でき、2 つの文字列をペアとして連結すると、結果の文字列は正しいブラケット シーケンスになる必要があります。 

正しい括弧の順序とは、左から右に読んだ場合に、どの接頭辞でも閉じ括弧の数が開き括弧の数よりも多くなることがなく、最後には開き括弧と閉じ括弧の合計数が等しいことを意味します。 

課題は、そのような有効なペアをどれだけ多く形成できるかを最大化することです。 

この制約により、O(n log n) または O(n) の解決策が求められます。 文字列の数は最大 100,000 個、合計の長さは最大 500,000 になる可能性があるため、すべてのペアを比較したり、連結を直接シミュレートしたりするアプローチは遅すぎます。 各文字列を小さな署名に圧縮してから、貪欲に一致させる必要があります。 

微妙な難しさは、弦は全体のバランスだけで特徴づけられるわけではないという事実から生じます。 合計バランスが同じ 2 つの文字列を連結すると、中間のプレフィックスがゼロを下回る可能性があるため、動作が大きく異なる場合があります。 

単純な間違いは、純残高のみを追跡することです。 たとえば、「())(」と「(」の合計がキャンセルされるという理由だけで「()」と「(」を互換性があるものとして扱うのは正しくありません。「())(」は内部的に無効であり、別のプレフィックスを安全に吸収できないからです。

 ## アプローチ

 強引なアイデアは、文字列のすべてのペアを試し、連結によって有効な括弧シーケンスが生成されるかどうかを確認することです。 各ペアについて、連結をシミュレートし、プレフィックスのバランスを検証します。 各チェックには両方の文字列の合計長に対して直線的な時間がかかるため、最悪の場合、これは O(n² · L) となり、実行可能な制限をはるかに超えます。 

重要な観察は、すべての文字列が 2 つの値、つまり最終的なバランスと最悪のプレフィックス バランスによって要約できることです。 バランスを「(」の場合は +1、「)」の場合は -1 として定義すると、すべての文字列で最小のプレフィックス合計と最終合計が生成されます。 これら 2 つの値は、反対の「タイプ」の別の文字列と安全に結合できるかどうかを完全に決定します。 

決して負にならず、非負のバランスで終わる文字列を「左に重い候補」として扱い、逆に決して正にならず、非正のバランスで終わる文字列を「右に重い候補」として扱う場合、ペアリングは、生の文字列ではなく、互換性のある署名の一致に帰着します。 

問題は 2 つのカテゴリ間のマッチング タスクとなり、各文字列がどの程度の不均衡を許容できるかに関する制約に影響します。 

分類した後は、すべてを貪欲なペアリング戦略にまとめることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース ペアリング + 検証 | O(n² · L) | お(1) | 遅すぎる |
 | バランス署名 + 貪欲なマッチング | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各文字列を処理し、ネットバランスと最小プレフィックスバランスという 2 つの値を計算します。 

1. 各文字列について、文字をスキャンしてバランスを計算します。 「(」の場合はインクリメントし、「)」の場合はデクリメントします。 スキャン中に最小プレフィックス残高も追跡します。 これにより、文字列がゼロよりどれだけ下になるかがわかります。 
2. 文字列のプレフィックス合計がゼロを下回った場合、その文字列は「終了が重い」文字列のように動作します。 それ以外の場合は、「開いても安全」です。 文字列は、正のバランスで終わるか負のバランスで終わるかに基づいて 2 つのグループに分類されますが、キーの分類は、文字列をペアの左側または右側に安全に追加できるかどうかに基づいています。 
3. 各文字列をペア (net_balance、min_prefix) に圧縮します。 このペアは、追加時に初期バランスがどのように変化するかを正確に捉えています。 
4. 文字列を 2 つのカテゴリに分割します。

正味残高が負でない文字列と、正味残高が負の文字列。 直観的には、ポジティブなものは開始サポートを必要とし、ネガティブなものは終了サポートを提供します。 
5. 非負のグループについては、最小プレフィックス制約によって昇順に並べ替えます。 これにより、最初に「最も壊れやすい」弦を使用することが保証されます。つまり、初期の不均衡をあまり許容できないことになります。 
6. ネガティブ グループの場合は、逆の制約によって並べ替え、一致するのが最も簡単な文字列を効果的に優先します。 
7. 貪欲に各側から 1 つずつ一致させます。 私たちは、実行可能なプレフィックスに対するカウンターを維持します。プレフィックス制約に違反することなくバランスが補える場合、ポジティブ グループの文字列をネガティブ グループの文字列と組み合わせることができます。 
8. 成功した各一致は 1 つの有効なペアを形成し、両方の文字列が考慮から削除されます。 

### なぜ効果があるのか

 重要な不変条件は、利用可能な最も制約された文字列を常に最初に一致させることです。 最小プレフィックス条件がより厳密な文字列には有効なパートナーが少なくなるため、延期しても最終的な一致数が減るだけです。 ソートにより、ペアリングが可能であれば、両方の候補がまだ利用可能なうちにペアリングに遭遇することが保証されます。 バランス制約により、受け入れられたペアがグローバルに有効なシーケンスに連結されることが保証されます。これは、どちらの文字列も、一度正しい順序で配置されると不可逆的なプレフィックス違反が発生するためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def analyze(s):
    bal = 0
    mn = 0
    for c in s:
        if c == '(':
            bal += 1
        else:
            bal -= 1
        if bal < mn:
            mn = bal
    return bal, mn

n = int(input())
pos = []
neg = []

for _ in range(n):
    s = input().strip()
    bal, mn = analyze(s)
    if bal >= 0:
        pos.append((mn, bal))
    else:
        neg.append((mn - bal, -bal))

pos.sort()
neg.sort()

i = j = 0
ans = 0

while i < len(pos) and j < len(neg):
    mn1, bal1 = pos[i]
    mn2, need = neg[j]

    if bal1 + need >= 0:
        ans += 1
        i += 1
        j += 1
    else:
        i += 1

print(ans)
```この解決策は、各弦をバランス プロファイルに圧縮することから始まります。 ヘルパー関数は、ネットバランスと最小プレフィックス値の両方を計算します。これにより、文字列が連結の途中に配置された場合に無効になるかどうかが決まります。 

次に、文字列は、負の残高で終わるか負の残高で終わるかに基づいて分割されます。 この分離は、一方の側を過剰な開口能力を提供するものとして扱い、もう一方の側をそれを必要とするものとして扱うことができるため、非常に重要です。 

並べ替えにより、最も制限の厳しい文字列が最初に一致するように試行されます。 2 つのポインターは両方のグループをスキャンし、一致が形成された場合、またはペアにできないために候補がスキップされた場合にのみ先に進みます。 

よくある実装の落とし穴は、プレフィックス最小値を無視し、ネット バランスのみを使用することです。 これにより、グローバルにはキャンセルされるがローカルでは壊れる文字列のペアが作成され、正確さが無効になります。

 ## 特殊なケース

 特殊なケースの 1 つは、「()」のようなすでに完全な正しい括弧シーケンスになっている文字列です。 これらのネット残高はゼロであり、プレフィックス動作は負ではありません。 アルゴリズムはそれらを柔軟な要素として扱い、制約に違反することなく他の中立または相補的な文字列と自然に組み合わせます。 

もう 1 つのエッジ ケースは、「())(()」など、初期に大きくマイナスになるが、後で回復する文字列です。ネット残高がゼロであっても、プレフィックスのディップにより、多くのペアリングで使用できなくなります。最小プレフィックスの追跡により、そのような文字列は制限的として正しく分類され、初期の不足を補う有効なパートナーが存在する場合にのみペアリングされます。

 最後のエッジケースは、すべての文字列が一方向に大きく偏っている場合です。 この状況でも、ソートにより、考えられるすべての一致が正しい順序で試行されることが保証されますが、有効な補数が存在しなくなると貪欲スキャンは自然に停止し、過剰カウントが回避されます。
