 ## 解決策
 ## 問題の理解

 チャンネルには、`n`購読者。 新しい投稿が公開されたとき、正確には`a`購読者はオンラインなので、`a`人々はすぐに投稿を読みます。 

その後、一連の通知を受け取ります。 あ`'+'`これは、加入者がオンラインになり、`'-'`一部の加入者がオフラインになったことを意味します。 シーケンスが有効であることはわかっていますが、各通知がどの特定のサブスクライバーを参照しているかはわかりません。 

問題は、すべての購読者がある時点でその投稿を読んだかどうかです。 

考えられる答えは 3 つあります。`YES`通知がどの人に言及しているかに関係なく、すべての購読者がその投稿を読んでいる必要があることを意味します。`NO`つまり、全員が投稿を読めるように通知に購読者を割り当てることはできません。`MAYBE`つまり、一部の割り当てでは全員が投稿を読むことができますが、他の割り当てではそうではありません。 

制約は非常に小さいです。 両方`n`そして`q`は最大 100、テスト ケースは最大 500 です。 高価なシミュレーションであっても、制限内に問題なく収まります。 課題はパフォーマンスではなく、通知によってどのような情報が明らかにされるかを正しく推論することです。 

重要な問題は、私たちはアイデンティティを決して学ばないことです。 誰かがオンラインになったとき、その人はこれまで投稿を読んだことがない購読者である可能性があります。または、以前にすでにオンラインで、オフラインになった後に戻ってきた人である可能性があります。 

次の例を考えてみましょう。```text
n = 5
a = 4
s = "-+"
```最初は 4 人がその投稿を読みました。 

その後`-`、1人が去ります。 

その後`+`、同じ人が戻ってくるか、5 番目の加入者が初めてオンラインになります。 

どちらの解釈も有効です。 あるケースでは 5 人の購読者全員が投稿を読みましたが、他のケースでは 4 人だけが投稿を読みました。 正しい答えは、`MAYBE`。 

もう 1 つの簡単な間違いは、最終的なオンライン購読者数だけを見てしまうことです。```text
n = 5
a = 2
s = "++-"
```オンライン数は2→3→4→3となります。 

これまでに確認されたオンライン購読者の最大数はわずか 4 人であるため、少なくとも 1 人の購読者はオンラインにアクセスして投稿を読む機会がありませんでした。 答えは`NO`。 

最初に全員がすでにオンラインになっている場合、別のエッジケースが発生します。```text
n = 5
a = 5
s = "--+"
```すべての購読者は、投稿が公開されるとすぐにそれを読みます。 今後の通知は関係ありません。 答えは`YES`。 

## アプローチ

 ブルートフォースアプローチでは、どの購読者がすでに投稿を読んだかを正確に追跡しようとします。 いつでも`'+'`発生した場合は、どのオフラインの加入者がオンラインになったかを判断する必要があります。 身元が不明であるため、すべての通知が複数の可能性に分岐する可能性があります。 

可能な状態の数は、通知の数に応じて指数関数的に増加します。 通知が 100 件しかない場合でも、そのような検索はまったく現実的ではありません。 

重要な観察は、私たちは実際にはアイデンティティを気にしていないということです。 私たちが知る必要があるのは、すべての購読者が投稿を読んだことが可能か不可能か、または保証されているかどうかだけです。 

その投稿を読む機会があった人の数を考えてみましょう。 

当初は、`a`購読者はすでに読んでいます。 

毎`'+'`この通知により、投稿が公開されてから一度もオンラインになったことのない新しい購読者が 1 人紹介される可能性があります。 すべてを楽観的に仮定すると、`'+'`新しい未読購読者を取り込んだ場合、可能な最大読者数は次のようになります。```text
a + number_of_pluses
```上限がある`n`。 

この楽観的な数さえも下回る場合は、`n`、その後、一部の購読者は投稿を読むことができなくなります。 答えは`NO`。 

次に、すべての購読者が投稿を読んだことが保証されるのはいつかを考えてみましょう。 

オンライン購読者数がいつでも上限に達した場合`n`の場合、その瞬間にはすべての加入者が同時にオンラインになっている必要があります。 オンラインの誰もがその投稿を読むので、すべての購読者は間違いなくそれを読んでいます。 これが発生すると、その後の通知によって事実を変更することはできません。 

そこで、オンライン数をシミュレートします。 いつか届くなら`n`、答えは`YES`。 

どちらの条件も当てはまらない場合、すべての加入者に到達することは可能ですが、強制はされません。 答えは`MAYBE`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | ブルートフォース | 指数関数的`q`| 指数 | 遅すぎる |
 | 最適 | O(q) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 現在のオンライン数が次の値に等しい状態から開始します。`a`。 

2. 何個数えるか`'+'`通知は文字列に表示されます。 

3. もし`a + plus_count < n`、出力`NO`。 

これは、投稿を読んだ可能性のある個別の購読者の最大数です。 まだ下にある場合`n`、すべての購読者に到達することは不可能です。 

4. それ以外の場合は、通知シーケンスを通じてオンライン数をシミュレートします。 

5. それぞれについて`'+'`、現在のオンライン数を 1 つ増やします。 

6. それぞれについて`'-'`、現在のオンライン数を 1 つ減らします。 

7. 更新するたびに、現在のオンライン数が以下と等しいかどうかを確認します。`n`。 

存在する場合は出力します`YES`。 

8. シミュレーションが完了せずに終了した場合`n`、出力`MAYBE`。 

### なぜ効果があるのか

 最初のチェックで可能性が判断されます。 最初は`a`人々はその投稿を読みました。 あ`'+'`通知は、新しいリーダーを作成できる唯一のイベントであり、そのようなイベントごとに、未読の購読者を最大 1 人追加できます。 したがって`a + plus_count`投稿を読むことができる購読者数の上限です。 その境界が以下の場合`n`、成功は不可能です。 

成功を保証するには、オンライン数が正確に増加することを観察してください。`n`、すべての加入者が同時にオンラインになります。 すべての購読者はその瞬間に投稿を読んだはずです。 読み取りは永続的なため、答えはすぐにわかります`YES`。 

成功の可能性はあるが、オンライン数に達しない場合`n`、あらゆる解釈が存在します。`'+'`新しい加入者と解釈を導入します。`'+'`イベントは、戻ってきたサブスクライバーに対応します。 どちらの結果も実現可能であるため、正解は次のとおりです。`MAYBE`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())

for _ in range(t):
    n, a, q = map(int, input().split())
    s = input().strip()

    if a + s.count('+') < n:
        print("NO")
        continue

    cur = a
    guaranteed = (cur == n)

    for ch in s:
        if ch == '+':
            cur += 1
        else:
            cur -= 1

        if cur == n:
            guaranteed = True

    if guaranteed:
        print("YES")
    else:
        print("MAYBE")
```最初の部分では、投稿を読む可能性のある個別の購読者の最大数を計算します。 その値が以下の場合`n`、答えはすぐにわかります。`NO`。 

それ以外の場合は、オンライン数をシミュレートします。 保証条件はカウントがこの値に達するかどうかのみに依存するため、ID は追跡されません。`n`。 

変数`guaranteed`すべての加入者をオンラインで同時に確認したかどうかを保存します。 また、次のように初期化する必要があります`cur == n`なぜなら、通知が届く前に全員がすでにオンラインになっている可能性があるからです。 

シミュレーションでは、各通知を単純に適用し、現在のカウントが次の値になるかどうかを確認します。`n`。 

この問題によって通知シーケンスの一貫性が保証されるため、無効な状態に対して特別な処理は必要ありません。

## 複雑さの分析

 |---|---|---|

以来`q ≤ 100`、実行時間はわずかです。 テスト ケースが 500 件あったとしても、総作業量はわずか数万回であり、制限をはるかに下回っています。 

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    input = sys.stdin.readline
    t = int(input())
    ans = []

    for _ in range(t):
        n, a, q = map(int, input().split())
        s = input().strip()

        if a + s.count('+') < n:
            ans.append("NO")
            continue

        cur = a
        guaranteed = (cur == n)

        for ch in s:
            if ch == '+':
                cur += 1
            else:
                cur -= 1

            if cur == n:
                guaranteed = True

        ans.append("YES" if guaranteed else "MAYBE")

    return "\n".join(ans) + "\n"

"""

"""

-
"""
) == """YES
"""

 ## 特殊なケース

 ### 公開時には全員がオンラインです

 入力:```text
1
5 5 3
--+
```アルゴリズムは次から始まります`cur = 5`、すでに等しい`n`。 変数`guaranteed`になる`True`通知を処理する前に。 

購読者は後でオフラインになっても、すでに投稿を読んでいます。 出力は次のとおりです。```text
YES
```通知の処理後にのみカウントをチェックするソリューションでは、このケースを見逃す可能性があります。 

### 「+」通知が不十分です

 入力:```text
1
5 2 3
++-
```次のように計算します。```text
2 + 2 = 4
```リーダーの最大数は 4 つだけです。 ID を割り当てなくても、5 人の購読者全員が投稿を読むことはできません。 

アルゴリズムは即座に次の出力を出力します。```text
NO
```シミュレーションを必要とせずに。 

### 可能性はあるが不確実

 入力:```text
1
5 4 2
-+
```可能性チェックにより次の結果が得られます。```text
4 + 1 = 5
```だから成功は可能です。 

オンライン数は次のとおりです。```text
4 -> 3 -> 4
```カウントが 5 に達することはないため、すべての購読者が投稿を読んだことを保証することはできません。 

有効な解釈の 1 つは、同じ購読者が離れて戻ってきて、読者が 4 人だけになるというものです。 もう 1 つは、行方不明の購読者が最後にオンラインになり、読者が 5 人になることです。 

アルゴリズムは正しく出力します。```text
MAYBE
```
