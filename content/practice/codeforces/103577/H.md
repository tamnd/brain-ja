 ## 解決策
 ## 問題の理解

 3 人の参加者が位置 0 から位置 d まで直線セグメントに沿って移動します。 そのうちの 2 人、イーライとラファは、同じ目的地に向かって一定の速度で独立して移動しますが、開始位置も速度も異なります。 Eli は 0 から開始し、速度 v0 で移動するため、位置は d に達するまで v0 · t として直線的に増加し、その後は d に留まります。 ラファは位置 1 でわずかに先行して開始し、速度 v1 でより速く移動するため、彼の位置は min(1 + v1 · t, d) になります。 

3 人目の参加者であるトミは 0 から開始し、速度 v2 で 2 人の人間よりもはるかに速く移動します。 彼の動きは単純に直線的ではありません。 彼は常にイーライとラファの中でより近い人間に向かって走ります。 どちらかに到達すると、すぐに方向を変えてもう一方に向かって走り、両方の人間が位置 d に到達するまでこの往復運動を繰り返します。 その瞬間を境にとみもdで止まります。 

タスクは、特定の時間 t におけるトミの位置を計算することです。 

制約は小さく、d、v0、v1、v2、t はすべて最大 100 です。これにより、数値最適化や高精度技術による連続シミュレーションの必要性が即座に排除されます。 方向転換の回数はトミがイーライまたはラファに会う頻度によって制限され、すべての動きは決定的な出会い点を持って線形であるため、直接的なイベントベースのシミュレーションであっても安全です。 

単純な考えを打ち破る唯一の微妙な点は、トミの動作が移動するターゲットに依存しているということです。 Eli と Rafa の両方が継続的に前進しているため、固定エンドポイントを想定した単純な実装は失敗します。 

典型的な失敗例は、最も近い人物ではなく、常にエリとラファの間の中間点に向かって移動することでトミをシミュレートしようとすることです。 そのため、ラファがイーライの相対位置を追い越してどちらが近いかが変わると、誤った動作が発生します。 

もう 1 つの失敗例は、固定時間の増分でステップを実行する場合です (たとえば、1 分ごとにシミュレートする)。 v2 は最大 100、時間は最大 100 であるため、Tomi は更新の間に複数のセグメントを横断し、1 ステップで複数の会議をスキップし、誤った切り替えロジックが発生する可能性があります。 

## アプローチ

 この強引なアイデアは、時間を少しずつ継続的にシミュレートすることです。 小さなタイム ステップごとに、イーライの位置、ラファの位置、トミの位置を再計算し、小さなデルタだけトミを正しい方向に移動します。 動きは決定論的であるため、これは概念的に機能しますが、方向の変化を見逃さないように十分に小さいステップ サイズが必要です。 100 分間で 1e-6 秒のような解像度を使用すると、約 6e9 ステップとなり、1 秒の制限で処理できる値をはるかに超えます。 

重要な観察は、任意に頻繁に方向を変えるものはないということです。 Eli と Rafa はそれぞれ、d での移動から停止までの状態変更を 1 つだけ行います。 トミの方向性が変わるのは、そのうちの一人に出会ったときだけです。 連続する 2 つの会議の間、全員が直線的に移動するため、すべてのポジションは時間内の単純な一次関数で表すことができます。 これは、システム全体が区分的に線形であり、イベント境界が少数しかないことを意味します。 

継続的にシミュレーションするのではなく、あるイベントから次のイベントにジャンプします。 私たちは、トミが次にいつイーライかラファを攻撃するかを計算し、短い方の時間をとり、その時点まですべてを進め、トミの方向を反転させます。 また、人間が d に到達したとき、または時間 t に到達したときに、シミュレーションに上限を設けます。 各イベントは線形方程式を使用して分析的に計算されるため、ステップ数は少ないままです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (小さなステップのシミュレーション) | O(t / ε) | お(1) | 遅すぎる |
 | イベント駆動型シミュレーション | O(k)、k ≤ 会議の数 | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

現在の時刻、トミの位置、トミの方向を維持します。 また、エリとラファの位置を時間の関数として計算します。 

1. ラファが位置 1 にあり、エリが 0 にあるため、トミを 0 に置き、最初の方向をラファに向けて時間 0 で開始します。この選択は、トミが時間 0 でラファの位置に向かって移動するというルールと一致します。 
2. 各ステップで、現時点での Eli と Rafa の現在位置を計算します。 どちらも d に達するまで線形であるため、各位置を最大でも d にクランプします。 
3. 次のイベント時間を決定します。トミがイーライまたはラファに到着する最も早い時間です。 これは、Tomi の指示に応じて一次方程式を解くことによって行われます。 トミが右に移動した場合、トミの位置がラファまたはエリの位置と同じ方向に進んでいる場合、その位置がいつになるかを解きます。 トミが左に移動した場合、対称計算を実行します。 
4. また、Eli または Rafa のいずれかが d に達する時刻も計算します。その後、彼らの動きが線形から一定に変化するためです。 これにより、別の潜在的なイベント境界が導入されます。 
5. これらの候補イベント時間と残り時間 t の最小値を取得します。 これにより、質的に何も変化しない次の時間間隔が得られます。 
6. 速度公式を使用して、すべての位置をその時点まで進めます。 それに応じて現在時刻を更新します。 
7. この時点でトミがイーライまたはラファに会った場合は、向きを変えてください。 これはバウンド動作を正確にモデル化します。 
8. 現在時刻が t になるか、人間が d でトミが d になるまで繰り返します。 

なぜ効果があるのか

 連続する 2 つのイベント時間の間では、エリ、ラファ、トミの順序はモーションの決定に影響を与えるような変化はありません。 すべての位置は一次関数であるため、次の衝突の正体は単純な一次方程式を解くことによって決定されます。 常に最も早いイベントにジャンプすることで、方向の変化や速度領域の変化を決してスキップしないようにします。 これにより、シミュレーションは近似ではなく正確になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    d, v0, v1, v2, t = map(int, input().split())

    def pos_e(ti):
        return min(v0 * ti, d)

    def pos_r(ti):
        return min(1 + v1 * ti, d)

    # Tomi state
    tcur = 0.0
    x = 0.0
    dir = 1  # 1 means right, -1 means left

    while tcur < t:
        if x >= d:
            print(f"{d:.10f}")
            return

        # compute current positions
        pe = pos_e(tcur)
        pr = pos_r(tcur)

        # remaining time
        dt_limit = t - tcur

        # time to hit Eli or Rafa depending on direction
        dt = float('inf')

        if dir == 1:
            if pr > x:
                dt = min(dt, (pr - x) / v2)
            if pe > x:
                dt = min(dt, (pe - x) / v2)
        else:
            if pr < x:
                dt = min(dt, (x - pr) / v2)
            if pe < x:
                dt = min(dt, (x - pe) / v2)

        dt = min(dt, dt_limit)

        # advance
        x += dir * v2 * dt
        tcur += dt

        # update direction if meeting occurred
        pe2 = pos_e(tcur)
        pr2 = pos_r(tcur)

        if abs(x - pe2) < 1e-9 or abs(x - pr2) < 1e-9:
            dir *= -1

    print(f"{x:.10f}")

if __name__ == "__main__":
    solve()
```実装はイベント ジャンプのアイデアに従っています。 ヘルパー関数 pos_e および pos_r は、d でクランプする区分的線形運動をエンコードします。 メイン ループは、次に考えられるインタラクションを計算することで時間を進めます。 方向の処理は明示的です。Tomi が右に移動する場合、次の衝突では彼の前にあるエンティティのみが問題となり、左に移動する場合も同様です。 

微妙な点は、浮動小数点の等価性です。 線形方程式を解くため、数学的には正確な等しいことが期待されますが、浮動誤差が蓄積する可能性があります。 許容差チェックにより、会議が確実に認識されることが保証されます。 

もう 1 つの微妙な点は、d でのクランプです。 Eli または Rafa が d に達すると、実質的にそれ以降のイベントへの貢献が停止されるため、pos_e と pos_r はその後一定のままになります。 

## 実用的な例

 ### 例 1

 入力:```
10 1 2 3 1
```時間 0 では、Eli は 0、Rafa は 1、Tomi は 0 で右に移動します。 

| 時間 | エリ | ラファ | とみ | イベント |
 | --- | --- | --- | --- | --- |
 | 0 | 0 | 1 | 0 | 開始 |
 | 1 | 1 | 3 | 3 | ラファを殴る |

 1分後、Tomiは3ユニット移動しました。 彼は正確に t = 1 でラファに到達するため、出力は 3 になります。 

これにより、最初のやり取りはイーライが関係する前にラファと行われたことが確認されます。 

### 例 2

 入力:```
10 1 2 3 10
```時間の経過とともに、トミが停止する前に、両方の人間が d = 10 に達します。 トミは跳ね続けますが、最終的には境界で終了します。 

| 時間 | エリ | ラファ | とみ |
 | --- | --- | --- | --- |
 | 0 | 0 | 1 | 0 |
 | 5 | 5 | 11→10 | ~10 |
 | 10 | 10 | 10 | 10 |

 これは、両方の人間が d で飽和すると、中間の振動に関係なく、Tomi もそこで安定す​​ることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(k) | 各反復は次のイベント (会議または境界変更) にジャンプしますが、制約の下ではそのようなイベントの数は少なくなります。 
| スペース | お(1) | 一定の状態変数のみが保存されます。 

制約 d、v0、v1、v2、t ≤ 100 により、各イベントを個別にシミュレートしたとしても、イベントの数はわずかなままであることが保証されます。 アルゴリズムは制限時間内に簡単に収まります。

 ## 特殊なケース

 エッジケースの 1 つは、イーライの動作に意味のある変化が生じるよりも早いタイミングで、トミがすぐにラファに到着したときに発生します。 入力で`10 1 2 3 1`, ラファは t = 0 で位置 1 にあり、トミも 0 にあるため、トミは t = 1 で最初にラファに到達します。アルゴリズムはこれを直線的な出会いとして計算し、エリの遅い動きによる複雑さが現れる前に前進運動を正しく停止します。 

もう 1 つのエッジ ケースは、イーライとラファの両方が t よりも先に d に到達した場合です。 で`10 1 2 3 100`、どちらの人間も位置 10 で比較的早く飽和します。 その瞬間以降、トミの動きは固定点とそれ自体の間を単純に往復するだけになり、実質的に d の静止状態に崩壊します。 pos_e と pos_r が d でクランプされ、その境界を越えてそれ以上のイベントが生成されないため、シミュレーションはこれを処理します。 

最後のエッジ ケースは t = 0 です。アルゴリズムはループに入らず、Tomi は原点に留まり、予想される出力と正確に一致します。
