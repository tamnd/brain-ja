 ## 解決策
 ## 問題の理解

 ルート付きトライが与えられます。各ノードは、ルートからそのノードまでのパスに沿って文字を連結して形成された文字列に対応します。 各ノードには要求値も含まれます。これは、そのノードによって表される文字列を一定回数書き込む必要があることを意味します。 

書き込みは文字を横切ることによって実行されます。 手動で文字を入力するたびに、固定コストがかかります`a`。 ただし、単語の完成をショートカットできるキャッシュ メカニズムもあります。接頭辞を入力すると、システムは現在の接頭辞に一致する辞書編集上最小の単語を提案し、固定コストを支払うことでその提案された単語を即座に完成させることができます。`b`。 

タスクは、トライ内のすべての要求された単語について、手動入力とキャッシュベースの補完を組み合わせて総コストを最小限に抑える方法を決定することです。 

入力構造はルート付きツリーを記述します。 各ノードは自分が持っている子の数を知っており、子はエッジ文字の辞書編集順にすでに順序付けされています。 キャッシュ選択では常に辞書編集上の最小の補完が優先されるため、この順序は重要です。 

出力は、すべてのノードの要求を満たすための最小総コストです。 

重要な問題は、すべてのノードが単語に対応しているにもかかわらず、サブセットを選択していないことです。 すべてのノードを次のように処理する必要があります`c[i] > 0`、場合によっては複数回実行し、プレフィックスを共有する方法と、キャッシュを使用していつ「早期終了」するかを決定します。 

制約から、`n`は最大 2 × 10^5 であるため、ツリー サイズが線形または線形に近いものより悪い解は失敗します。 これにより、ノード間のペアごとの推論や、パスを繰り返し再計算する動的プログラミングが即座に除外されます。 ソリューションは、単一の走査でトライを処理するか、線形時間集計と同等のものを処理する必要があります。 

キャッシュの使用量がノードごとに独立して考慮される場合、単純な危険なケースが発生します。 たとえば、2 つのノードが長いプレフィックスを共有しているが、最後の文字だけが異なる場合、それらを個別に扱うと、プレフィックスのコストが 2 倍にカウントされ、共有構造が失われます。 もう 1 つの微妙な失敗例は、キャッシュがワードごとに常に役立つと想定していることです。実際には、料金を支払う必要があります。`b`十分なサフィックスが残っているとそれ以上のコストがかかる場合にのみ意味があります。`b`、そしてこれは単一のノードだけではなくサブツリー構造に依存します。 

## アプローチ

 ブルートフォース戦略では、必要な各単語を個別に書くことをシミュレートします。 各ノードに対して、`c[i] > 0`、その文字列の長さを計算します`len(i)`そしてコストを想定する`len(i) * a`、オプションで最終セグメントをキャッシュ コストに置き換えます`b`。 これにより、トライの共有プレフィックス構造が即座に無視されますが、共有プレフィックスを明示的にウォークすることで問題を修正しようとしても、重複するパス全体でのキャッシュ使用量の組み合わせについて推論する必要があります。 

さらに深刻な問題は、キャッシュの決定がサブツリー全体にわたって相互作用することです。 あるノードでキャッシュを使用することに決めた場合、その出現におけるすべてのより深い文字に対する支払いを事実上停止します。 したがって、問題はノードごとの最適化ではなく、各ノードが重みに寄与し、決定が上方に伝播するサブツリーの最適化です。 

重要な観察は、これが基本的にトライ上のツリー DP であり、各ノードが文字列を表し、単語の出現ごとに独立して寄与するということです。 サブツリー内のすべてのリクエストを処理するコストを計算し、キャッシュを使用してノードで「停止」するか、さらに深く入力を続けるかを決定したいと考えています。 

タイピングをルートからエッジをトラバースすると考えると、エッジを下るたびに料金を支払うことになります。`a`アクティブなトラバースごとにキャラクターごとに。 ただし、単語は辞書順に分岐するため、キャッシュは常に最小の継続を選択します。これは、ノードでキャッシュを使用することを決定すると、事実上、そのサブツリー内のすべての要求を 1 回の支払いで完了することを約束することになります。`b`トラバースを続ける代わりに。 

これは、きれいな DP 解釈につながります。つまり、各ノードで、子に拡張して支払うか、停止して支払うかのいずれかになります。`b`辞書編集的に一貫した走査を通じて集約されたサブツリー要求全体に対して 1 回。 

これにより、すべてのノードを満たす最適なコストをノードごとに計算するという問題が軽減されます。`c[i]`そのサブツリーでは、辞書編集的な走査順序を尊重する累積コストの概念を継承しながら、子結果を順番に結合します。

 ## アルゴリズムのチュートリアル

 DFS でトライを処理し、DP 値をボトムアップで計算します。 

1. 定義する`dp[u]`ノードのサブツリー内のすべての要求を満たすための最小コストとして`u`から始めると仮定すると、`u`すでにプレフィックスを入力しています。 

この定式化により、プレフィックス コストをサブツリーの決定から分離することができます。 
2. リーフノードの場合、需要がある場合`c[u]`、すべての出現箇所を入力するか、キャッシュを繰り返し使用して支払う必要があります。 キャッシュは単語を即座に終了するため、各単語の出現を独立して処理できるため、コストは次のようになります。`c[u] * min(depth_cost, b)`どこ`depth_cost`親累積によって暗黙的に処理されます。 

実際には、リーフは DP 集約以外の特別な処理を必要としません。 
3. 内部ノードの場合、まず辞書順にすべての子の DP を計算します。 

順序付けが重要なのは、キャッシュが常に現在のプレフィックスと一致する辞書編集上最小の補完を選択するためです。そのため、サブツリーのマージでは、遷移の正確さを維持するためにこの順序を尊重する必要があります。 
4. 次に、次のサブツリーを処理する 2 つの方法を検討します。`u`。 

1 つ目の方法は、通常どおり続行することです。すべての子 DP 値を結合し、エッジによって寄与される走査コストを追加し、効果的に支払います。`a`必要なすべての訪問にわたるエッジトラバーサルごとに。 

2 番目の方法は、次の場所でキャッシュを使用することです。`u`。 ここでキャッシュを使用すると、サブツリー内のすべての要求は`u`コストを抑えてすぐに満足できる`b`、それ以上のトラバースは無視されます。 

これは有効です。なぜなら、一度キャッシュの完了をコミットすると、`u`、システムは辞書編集上最小の補完を直接出力します。`u`、これはトライ順序制約と一致します。 
5. したがって、反復は次のようになります。 

dp[u] = min(b, (dp[v] + すべての要求に必要なエッジを v に往復するコスト)) の子の合計)

 微妙な部分はエッジコストです`a`サブツリーがアクセスされた回数に比例して発生します。 これは、重み付けされた寄与をボトムアップで蓄積することと同等であり、要求された各リーフは、そのパス上の各エッジを通る 1 回の走査に寄与します。 
6. これを効率的に計算するために、事後 DFS を実行し、サブツリーの需要合計を維持します。 各エッジが寄与する`a * total_demand_in_child_subtree`。 
7. 最後に、各ノードで全走査コストを比較します。`b`そして最低限のものを取る。 

### なぜ効果があるのか

 重要な不変条件は、すべてのノードについて`u`, DP は、次の 2 つの徹底的な選択肢の下で、サブツリー内のすべての要求に応えるための最小コストを正確に表します。`u`または、キャッシュを一度だけ使用します`u`をクリックして、その下にあるすべての処理を終了します。 サブツリー内の部分キャッシュは、コストを増加させることなく常に最も使用されているノードに常に上方にシフトできるため、最適なソリューションは、残りのサブツリー全体を置き換えるノードでのみキャッシュの使用が発生するソリューションに変換できます。 これにより、重複するキャッシュの決定が排除され、問題は独立したサブツリーの選択に軽減されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
sys.setrecursionlimit(10**7)

n, a, b = map(int, input().split())

children = [[] for _ in range(n)]
c = [0] * n

for i in range(n):
    parts = list(map(int, input().split()))
    c[i] = parts[0]
    k = parts[1]
    if k:
        children[i] = parts[2:]

def dfs(u):
    total_cost = 0
    total_cnt = c[u]

    for v in children[u]:
        child_cost, child_cnt = dfs(v)
        total_cost += child_cost
        total_cnt += child_cnt

    # cost contributed by edges is proportional to number of words
    total_cost += total_cnt * a

    # option: use cache at this node
    total_cost = min(total_cost, b)

    return total_cost, total_cnt

ans, _ = dfs(0)
print(ans)
```DFS は、コストとサブツリー内の終端ワード数の両方を返します。 各ワードがすべての祖先エッジを通る走査コストに寄与するため、カウントが必要になります。 掛け算`total_cnt * a`このノード レベルでは、要求された単語ごとに 1 文字のトラバースが必要であるという事実がわかります。 

ノードのキャッシュはすべてのサブツリー構造をオーバーライドするため、キャッシュの決定は子の集約後に適用されます。 

微妙な点は、すべてのサブツリーの要求を、エッジ コストに等しく寄与する独立した単位として扱うことです。 これは正しいです。キャッシュで置き換えられない限り、要求されたすべての単語がそのパス上のすべてのエッジを 1 回の出現ごとに 1 回だけ通過する必要があるからです。

## 特殊なケース

 重大なエッジケースは次のような場合です。`b = 0`。 この状況では、キャッシュは常にすべての要求をカバーする可能な限り最高のノードで使用され、全体の応答がゼロになるようにする必要があります。 すべてのノードがその累積コストをゼロと比較し、即座にキャッシュを選択するため、DP はこれを正しく処理します。 

もう 1 つのエッジケースは次のような場合です`a = 0`。 ここでは入力は無料であるため、キャッシュもゼロでない限り役に立ちません。 アルゴリズムは正しくゼロエッジコストを蓄積し、`b`負の比較が不可能でない限り、関係ありません。 

構造的なエッジケースは、需要が重なり合う深いブランチ全体に分散される場合に発生します。 たとえば、サブツリーの下のすべての葉が要求されると、サブツリーの数が大きくなり、乗算は`total_cnt * a`キャッシュが選択されない限り、優先されます。 DP は、サブツリーの蓄積がより高価になる時点でキャッシュが考慮されることを保証します。`b`、数えすぎを防ぎます。
