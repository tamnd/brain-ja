 ## 解決策
 ## 問題の理解

 最初の質問を除くすべての質問には 1 つの前提条件があり、その前提条件のインデックスは常に小さい、ルート構造に配置された一連の質問が与えられます。 これは、質問が前のインデックスから後のインデックスに向かうルート付きツリーを形成することを意味しますが、各ノードには親が 1 つだけあるため、構造は実際にはノード 1 をルートとするルート付きツリーになります。 

各質問 i にはスコア ai と成功確率 pi があります。 質問を試みると、正しく答えて続行するか、失敗してプロセスが即座に停止し、将来の機会がすべて失われます。 成功すると、ai を獲得し、後のプロセスでそれに依存する質問に進むことができます。 

主な制限は、質問の順序を自由に変更できないことです。 質問には、その前提条件が解決された後にのみ回答できます。 ただし、現在利用可能な質問の中から、次にどの質問に挑戦するかを選択できます。 

目標は、すべての確率を事前に把握し、予想される合計スコアを最大化する順序付け戦略を選択することです。 

出力は、最適な適応順序付けを想定した単一の期待値です。 

n が 100000 までの制約は、二次関数または O(n log^2 n) 戦略を慎重に扱う必要があることを意味しますが、実際の制約は、解が順列にわたるグローバルな検索ではなく、ローカルな順序付けルールに帰着する必要があることです。 

素朴な解釈では、考えられるすべての戦略をシミュレートすることになります。 順番を固定してもn個ある！ 各順序付けには、予想される生存確率を評価する必要があります。 これはすぐには不可能です。 

2 番目の素朴なアイデアは、利用可能なノードのサブセットに対する動的プログラミングです。 各状態で次の質問を選択し、遷移は成功確率に応じて異なります。 しかし、いつでも複数の子が利用可能になるため、状態空間は指数関数的に増加します。 

DFS や BFS のような固定トラバーサルが最適であると人々が想定している場合、より微妙な失敗ケースが発生します。 これは、価値とリスクの比率が異なる 2 つの質問が、確率とスコアに応じて異なる方法でインターリーブされる可能性があるため、失敗します。 

たとえば、次の 2 つの独立した質問を考えてみましょう。 

入力:

 n = 2

 a = [100, 1]

 p = [0.5, 0.99]

 質問 1 を最初に解くと、継続構造の確率は低くなりますが、早期に停止すると高い価値が失われるため、期待される貢献度は高くなります。 最初に質問 2 に回答すると、質問 1 に到達する可能性は高くなりますが、期待される利益は変化します。 これは、順序がツリー構造だけでなくトレードオフに依存していることを示しています。 

主な困難は、最適な戦略では、前提条件を尊重しながら、兄弟間の順序を動的に決定する必要があることです。 

## アプローチ

 ブルート フォース ソリューションでは、ツリーの有効なトポロジー順序をすべて明示的に考慮し、それぞれの期待値を計算します。 ツリーに限定しても、各ノードの子は任意にインターリーブできるため、有効な順序の数は分岐係数で指数関数的に増加します。 1 つの順序を評価するには、シーケンスに沿った生存確率 (O(n)) をシミュレートする必要があります。 これにより、全体的な複雑さが指数関数的に増加します。 

構造的な洞察は、ノードが利用可能になると、そのノードに関して重要なのは、そのノードがそのノードに到達することを条件とした期待値にどのように寄与するかだけであるということです。 各質問は、それまでのすべての試行が成功した場合にのみ、その値に影響します。 これにより、選択されたシーケンスに沿った乗法的な生存確率が作成されます。 

現在利用可能な質問を試す順序を修正するとします。 到達確率が S の時点で質問 i を試みると、その期待される寄与度は S * pi * ai となり、その後の生存率は S * pi になります。 これは、各アイテムが以前に配置された場合に「減衰係数」pi が適用されているかのように動作することを示唆しています。

これにより、問題は、乗法生存下で期待値に寄与する順序付けタスクに変換されます。 古典的な交換議論が適用されます。利用可能な 2 つの質問 i と j を比較する場合、それらを交換すると、i を j の前に置くとより良い寄与が得られるかどうかに応じて、期待値が変化します。 これにより、生存損失ごとの期待増分利益の最大化に基づいたペアごとの順序付けルールが得られます。 

重要な観察は、各質問は、ローカル スワップの下で順序が最適になる方法でスコアと成功確率を組み合わせたキーによって優先順位付けされる必要があるということです。 ノードがアクティブ化されると、そのスケジューリングはアクティブなノード間のグローバルな順序にのみ依存するため、依存関係構造はアクティブ化のタイミングを超えてこのルールに干渉しません。 

したがって、問題は、新しいノードが利用可能になったときに優先順位構造を維持しながら、優先キーによって決定された順序で利用可能なノードを繰り返し選択することに帰着します。 

このような問題を解決する標準的な方法は、各ノードの実効値を計算し、優先キュー内のノードを処理して、導出された順序付けルールに基づいて常に最適な候補を確実に選択できるようにすることです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべての注文に対するブルートフォース | 指数 | O(n) | 遅すぎる |
 | 優先順位に基づいた貪欲なスケジューリング | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在利用可能な質問のプールを維持する方法でツリーを処理し、導出された優先順位に従って常に最適な次の質問を選択します。 

1. ノード 1 をルートとして解釈し、前提条件のリンクを使用してツリーを構築します。 各ノードは、その親が処理されるときにロック解除されます。 
2. 現在利用可能なすべてのノードを含む優先順位構造を維持します。 最初はノード 1 のみが使用可能です。 
3. 各ノードの有効な順序付けキーを、そのスコアと成功確率の関数として定義します。 このキーは、有効なシーケンスの中でこのノードを早い段階で試行することがどの程度有益であるかを決定します。 順序付けは、引数を交換して予想される限界寄与度を比較することで得られます。 
4. 各ステップで、最高の優先順位で使用可能なノードを抽出します。 これは、そこに到達する現在の生存確率を考慮すると、最も期待されるゲインが得られるノードです。 
5. 正常に完了した場合のみ続行できるため、実行中の生存確率に選択したノードの確率 pi を掛けます。 
6. ノードの予想される寄与 (current_survival * pi * ai) を追加します。 
7. ノードを処理した後、その子をアクティブ化し (ノード i+1 は入力構造に従って 1 つのノードだけロックを解除する場合があります)、それらを優先構造に挿入します。 
8. ノードがなくなるまで続行します。 

重要な考え方は、実行中の生存確率は、選択した順序で現時点までに失敗していない確率を表すということです。 すべてのノードは、この生存確率と自身の成功確率によって重み付けされた値を提供します。 

### なぜ効果があるのか

 このアルゴリズムは、一貫した順序不変式に依存しています。現在利用可能なすべてのノードの中で、降順の優先キーでノードを処理することは、スワップ引数の下で常に局所的に最適です。 順序キーは生存加重寄与に対するそのような交換の限界効果の比較から正確に導出されているため、2 つの隣接する利用可能なノードを交換するような偏差は期待値を向上させることはできません。 依存関係はノードが利用可能なセットに入るタイミングのみを制御し、利用可能になった後の相対的な順序には影響を与えないため、貪欲な選択はプロセス全体を通じて最適なままです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import heapq

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    p = list(map(float, input().split()))
    parent = list(map(int, input().split()))
    
    g = [[] for _ in range(n)]
    for i, pr in enumerate(parent, start=1):
        g[pr - 1].append(i)
    
    # We use a priority queue: maximize expected contribution density
    # key = - (a[i] * p[i]) / (1 - p[i]) form heuristic ordering
    # (derived from exchange argument on survival-weighted expectation)
    
    def key(i):
        return (a[i] * p[i]) / (1.0 - p[i] + 1e-18)
    
    pq = []
    heapq.heappush(pq, (-key(0), 0))
    
    alive = [False] * n
    alive[0] = True
    
    ans = 0.0
    survival = 1.0
    
    while pq:
        _, u = heapq.heappop(pq)
        
        # process u
        ans += survival * p[u] * a[u]
        survival *= p[u]
        
        for v in g[u]:
            if not alive[v]:
                alive[v] = True
                heapq.heappush(pq, (-key(v), v))
    
    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、まず前提条件配列から依存関係ツリーを構築し、各ノード i+1 を ti の子に変換します。 これにより、ノードは親が処理された後にのみ使用可能になります。 

優先キューには現在利用可能なすべてのノードが格納され、キー関数はスコアと生存確率のバランスをとる交換ベースの順序ヒューリスティックをエンコードします。 常に最大のキーを持つノードを選択します。 

変数`survival`以前に選択したすべての質問を正常に完了できる確率を追跡します。 各ステップで現在のノードの成功確率が乗算され、それに応じて期待される寄与が追加されます。 

分母のイプシロンを小さくすると、円周率が 1 に非常に近い場合の除算の不安定性が回避されます。 

## 実用的な例

 ### 例 1

 入力:

 n = 3

 a = [10, 5, 1]

 p = [0.9, 0.9, 0.9]

 親 = [1, 1]

 ノード 2 と 3 は両方とも、ノード 1 の後に使用可能になります。 

| ステップ | 利用可能 | 選ばれた | サバイバル | 貢献 |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 1 | 1.0 → 0.9 | 1 * 0.9 * 10 = 9 |
 | 2 | 2、3 | 2 | 0.9 → 0.81 | 0.9 * 0.9 * 5 = 4.05 |
 | 3 | 3 | 3 | 0.81 → 0.729 | 0.81 * 0.9 * 1 = 0.729 |

 合計 = 13.779

 このトレースは、生存率が乗算的にどのように縮小するのか、そして確率が等しい場合でも兄弟間の順序が重要である理由を示しています。 

### 例 2

 入力:

 n = 2

 a = [100, 1]

 p = [0.5, 0.99]

 親 = [1]

 | ステップ | 利用可能 | 選ばれた | サバイバル | 貢献 |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 1 | 1.0 → 0.5 | 50 |
 | 2 | 2 | 2 | 0.5 → 0.495 | 0.495 |

 合計 = 50.495

 スワップされると、継続確率が低いにもかかわらず、高価値ノードがより高い即時期待ゲインによって保護されるため、期待値が低下します。 

これは、順序付けが純粋に確率やスコアだけによって行われない理由を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n log n) | 各ノードは優先キューに一度挿入され、優先キューから抽出されます。 
| スペース | O(n) | すべてのノードの隣接リストとヒープ ストレージ |

 ## 特殊なケース

 1 つの重要なエッジ ケースは、確率が 1 に非常に近いときに発生します。その場合、除算を含む式が使用されます。`(1 - p)`数値的に不安定になります。 実装では、小さなイプシロンを使用してこれを防止し、効果的な比較結果を変更することなく安定した順序付けを保証します。 

ノードに同時に使用可能になる多くの子がある場合、別のケースが発生します。 このアルゴリズムは、親を処理した直後にすべての子を挿入し、バイアスなくすべての子が順序付けの対象として考慮されるようにします。 

最後に、確率が非常に小さい場合、生存率は急速に低下し、後のノードはほとんど貢献しません。 生存率は常に乗算的に更新され、プロセスの正確な確率セマンティクスと一致するため、アルゴリズムはこれを引き続き正しく処理します。
