 ## 解決策
 ## 問題の理解

 この問題は 2 つの点の集合を扱います。1 つの集合は集合 U として考えることができ、もう 1 つの集合は集合 V として考えることができます。各点は単なる単一の数値ではなく、座標のペアであり、U の要素については (ux, uy)、V の要素については (vx, vy) として記述されます。 

タスクは、特定のスコアリング ルールを通じてこれらのポイントがどのように相互作用するかを維持し、推論することです。 U の点と V の点を組み合わせる場合、ペアの値は ux + vx や uy + vy などの合計を含む式によって定義されます。システムが考慮するすべての有効な組み合わせにわたって、これら 2 つの合計の最大値を最小化することに関心があります。 

重要な構造上の観察は、ux + vx と uy + vy の比較が、差異間の比較 (ux − uy と vy − vx) として書き換えられることです。 これは、すべてのポイントを単一の派生値に還元できることを意味し、それが順序付けキーのように機能します。 この変換が行われると、U と V の間の相互作用は、これらの派生 ID と、これらの ID の間隔がどのように結合されるかのみに依存するものになります。 

システムはこれらのポイントにわたる動的な更新をサポートしており、各更新後に最適なペアリング値を効率的に計算できる必要があります。 素朴なアプローチでは、すべての変更後に U と V にわたる点のすべてのペアをチェックすることによって、答えを最初から再計算します。 

最大 200,000 回の更新があり、各再計算ですべてのペアがチェックされる場合、クエリごとの複雑さは 2 次になり、最悪の場合 10^10 のオーダーの演算が必要になるため、直ちに実行不可能になります。 

複数のポイントが同じ派生 ID を共有する場合、より微妙な問題が発生します。 ソリューションが一意性を誤って仮定したり、U と V の両方の寄与を一貫して追跡せずに片側のみを並べ替えたりすると、最適なクロス選択が失われる誤ったペアリングが生成される可能性があります。 

たとえば、U に点 (10, 0) と (0, 10) が含まれ、V に (5, 0) と (0, 5) が含まれる場合、1 つの座標差のみをソートする単純な貪欲ペアリングでは、両方のセットにわたって左右の寄与を混合する最適なクロス ペアリングを見逃す可能性があります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 すべてのクエリについて、U のすべての点と V のすべての点を反復処理し、max(ux + vx, uy + vy) を評価して最小値を取得することで答えを計算します。 これは、考えられるすべてのペアリングを直接チェックし、最適なペアリングを選択するため、正しいです。 

ただし、各セットに n 個の点がある場合、クエリごとに n 回の二乗比較が必要になります。 n が 200000 までになると、1 つの評価でも大きすぎて、更新を繰り返すと完全に管理できなくなります。 

重要な洞察は、ux + vx ≥ uy + vy という比較が ux − uy ≥ vy − vx として書き換えられるということです。 この変換により、問題は各点に単一のスカラー ID を割り当てることができ、U と V の間の相互作用はこの軸に沿った順序のみに依存する問題に変換されます。 

すべてがこの ID 行にマッピングされると、ID の間隔にわたって構造化された情報を維持することが問題になります。 ペアごとの相互作用を再計算する代わりに、ID 空間上でセグメント ツリーを維持します。 各ノードは、その間隔内の可能な限り最適な構成に関する集約された情報を保存します。 

微妙な部分は、各ノードが単純な座標の最小値だけでなく、異なる子の要素を混合するときに達成可能な最良の max(ux + vx, uy + vy) を表す結合値も格納する必要があることです。 重要な観察は、2 つのセグメントを結合する場合、不等式により空間が 2 つの単調なケースに分割されるため、唯一の意味のある相互作用は U の一方の側と V の反対側のペアから得られるということです。 

これにより、セグメント ツリー ノードの定数時間マージ ルールが実現され、各更新またはクエリを対数時間で実行できるようになります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | クエリあたり O(n²) | お(1) | 遅すぎる |
 | ID 上のセグメント ツリー変換 | 更新/クエリごとに O(log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ## アルゴリズムのチュートリアル

 1. 各点 (u_x、u_y) をスカラー キー id = u_x − u_y に変換し、V 点についても同様に id = v_y − v_x を使用します。 これにより、比較条件が 1 つの軸に沿った単純な順序付け問題に縮小されます。 
2. 考えられるすべての ID のソートされたセットに対してセグメント ツリーを構築します。 各リーフは特定の ID 値に対応し、その ID に属するポイントの集約情報を格納します。 
3. セグメント ツリーの各ノードに、最小 u_x、最小 u_y、最小 v_x、最小 v_y、およびこのセグメント内の点のみを使用して達成可能な max(u_x + v_x, u_y + v_y) の最良の値の 5 つの値を保存します。 
4. 2 つの子ノードを結合する場合、まず u_x、u_y、v_x、v_y の要素ごとの最小値を取得して最小値を直接伝播します。 これにより、各セグメントが最適なローカル座標の代表を正確に追跡することが保証されます。 
5. 変換された不等式を使用して、左子と右子の間の最良の相互寄与を計算します。 意味のある候補は、左側の u_y と右側の v_y のペア、または右側の u_x と左側の v_x のペアからのみ得られます。 これは、ID の順序付けが u_x − u_y ≥ v_y − v_x を満たすかどうかから直接導き出されます。 
6. 子の最良値と 2 つの相互組み合わせケースの最小値を取得して、親ノードの最良値を更新します。 これにより、すべての有効なペアが各マージ ステップで 1 回だけ考慮されることが保証されます。 
7. 入力の更新ごとに、対応するリーフを変更し、セグメント ツリー パスに沿って上方向に値を再計算します。 

### なぜ効果があるのか

 正確さは、合計間の比較が、導出された ID に対する単調な順序に分解されるという事実に依存します。 この順序でポイントが分割されると、最適なペアリングはセグメント内に完全に留まるか、セグメント ツリー内の 2 つの隣接する部分構造間を 1 回だけ交差します。 マージ ルールは、構造的に異なる 2 つのクロス構成を正確に列挙します。 考えられるすべてのペアリングは、最初の分岐の境界で考慮されるマージのパスに対応するため、セグメント ツリーはルートで正しいグローバル最小値を維持します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**30

class Node:
    __slots__ = ("ux", "uy", "vx", "vy", "best")
    def __init__(self):
        self.ux = INF
        self.uy = INF
        self.vx = INF
        self.vy = INF
        self.best = INF

def merge(left: Node, right: Node) -> Node:
    res = Node()

    res.ux = min(left.ux, right.ux)
    res.uy = min(left.uy, right.uy)
    res.vx = min(left.vx, right.vx)
    res.vy = min(left.vy, right.vy)

    res.best = min(left.best, right.best)

    # cross transitions:
    # left U with right V
    res.best = min(res.best, left.uy + right.vy)

    # right U with left V
    res.best = min(res.best, right.ux + left.vx)

    return res

class SegTree:
    def __init__(self, n):
        self.n = n
        self.size = 1
        while self.size < n:
            self.size <<= 1
        self.data = [Node() for _ in range(2 * self.size)]

    def update(self, idx, ux, uy, vx, vy):
        i = idx + self.size
        node = self.data[i]
        node.ux = ux
        node.uy = uy
        node.vx = vx
        node.vy = vy
        node.best = min(ux + vx, uy + vy)

        i //= 2
        while i:
            self.data[i] = merge(self.data[2 * i], self.data[2 * i + 1])
            i //= 2

    def query(self):
        return self.data[1].best

def solve():
    n, q = map(int, input().split())
    st = SegTree(n)

    for i in range(n):
        ux, uy, vx, vy = map(int, input().split())
        st.update(i, ux, uy, vx, vy)

    out = []
    for _ in range(q):
        t = list(map(int, input().split()))
        if t[0] == 1:
            i, ux, uy, vx, vy = t[1], t[2], t[3], t[4], t[5]
            st.update(i, ux, uy, vx, vy)
        else:
            out.append(str(st.query()))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、各ノードが生の最小値とその区間の最良のペアリング スコアの両方を保存する完全なセグメント ツリーが維持されます。 各更新ではリーフが変更され、すべての祖先が再計算され、マージ関数によって正確さが維持されます。 

マージ関数は唯一の重要な部分です。 これは、最適なペアリングは分割の片側の内側にとどまるか、構造的に有効な 2 つの方法で左右の間を横切るかのいずれかであるというアイデアをエンコードしています。 コードの残りの部分は、標準的な反復セグメント ツリーのメンテナンスです。 

よくある落とし穴は、リーフを更新した後に完全なノードを再計算するのを忘れることです。 もう 1 つの微妙な問題は、実際には左から右と右から左の両方の相互作用をチェックする必要があるのに、必要な交差項は 1 つだけであると仮定していることです。 

## 実用的な例

 片側に 2 つの要素がある小さなインスタンスを考えてみましょう。そこでは更新が実行され、最適なペア値がクエリされます。 

入力：```
2 2
1 3 2 4
5 1 1 6
2 0 0 0 0
1 1 2 2 2 2
2 0 0 0 0
```| ステップ | アクション | ノード値 (ux、uy、vx、vy) | 最高 |
 | --- | --- | --- | --- |
 | 1 | idx 0 を挿入 | (1,3,2,4) | 5 |
 | 2 | idx 1 を挿入 | 統合されました | 更新されました |

これにより、グローバル構造を更新するにはローカルな変更で十分であることが確認され、セグメント ツリーは影響を受ける領域のみを一貫して再計算します。

 ## 特殊なケース

 1 つのエッジ ケースは、すべての点が両方のセットで同一である場合に発生します。 この状況では、すべてのペアのスコアが同じになるため、セグメント ツリーはマージ順序に関係なく、一貫してその値を返す必要があります。 すべての最小項と交差項が同じ式に評価されるため、実装ではこれが処理され、偶発的なバイアスが導入されません。 

別のエッジ ケースは、両方の座標において一方のセットが他方のセットよりも優勢である場合に発生します。たとえば、すべての U ポイントが非常に大きな ux と非常に小さな uy を持ち、V が反転されます。 最適なペアリングは常に交差項から得られ、マージ関数は両方の交差方向を明示的にチェックして、正しい値が見逃されないようにします。 

最後のエッジ ケースは、ツリーの奥深くにあるリーフに影響を与える単一の更新です。 正確かどうかは、すべての祖先を再計算するかどうかに依存します。 反復的な上向きループにより、古いノードが残らないことが保証されるため、ルートは常に更新されたグローバル最適値を反映します。
