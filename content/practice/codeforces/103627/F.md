 ## 解決策
 ## 問題の理解

 重み付けされた幾何学的更新のコレクションを処理し、フォームの軸に沿って配置された接頭辞の四角形の内側に合計重みがどのくらいあるかについてのクエリに答えるように求められます。$[1, x] \times [1, y]$。 問題は、更新が静的な点ではなく、平面内の線に沿って移動するイベントのように動作する構造化された寄与であり、各更新の寄与が包含と排除を通じて暗黙的に定義されることです。 

提供されたチュートリアルの重要な再定式化は、四角形について直接考える代わりに、各四角形の更新を加重コーナー イベントの小さなセットに変換することです。 この変換の後、問題はポイントの重みの動的累積になり、各ポイントがプレフィックス形式ですべてのクエリに寄与します。 言い換えれば、各イベントは座標で重みを加算または減算し、すべてのクエリはプレフィックス四角形の合計を要求します。 

構造によって暗示される制約は十分に大きいため、すべてのクエリと更新に対する二次スイープは不可能です。 クエリごとにすべてのイベントをスキャンして寄与度を再計算する単純なアプローチではコストがかかります$O((N+M)Q)$、入力が数千を超えると、すぐに実行できなくなります。 これにより、通常は操作ごとに対数時間で、増分更新とプレフィックス合計クエリを効率的にサポートするデータ構造が必要になります。 

微妙なエッジケースは、次のような座標のシフトから発生します。$x_2 + 1$そして$y_2 + 1$。 これらにより、包含範囲と排他範囲の間の境界が明確に分離されます。 これらのシフトを忘れると、オフバイ 1 エラーが発生し、ゼロに寄与するはずの四角形が依然としてプレフィックス構造に重みを漏洩します。 

もう 1 つの重要なケース ケースは、変換の重なり合いです。複数の長方形により、共有コーナーでの影響がキャンセルされる可能性があります。 実装が包含/除外記号を慎重に尊重しない場合、データ構造が正しい場合でも、最終的なプレフィックス合計では領域が 2 倍にカウントされるか、またはアンダーカウントされます。 

## アプローチ

 ブルートフォース解釈は簡単です。 各長方形を 4 つの加重コーナー イベントに変換した後、グリッド上の配列を維持します。 クエリごとに$(x, y)$、すべてのイベントを反復処理し、座標が範囲内にあるポイントの寄与を合計します。$[1, x] \times [1, y]$。 各チェックは一定時間であるため、各クエリにはイベント数に比例した時間がかかります。 

これは正しいです。変換により、4 つの角の点がキャンセルされて、すべての長方形が意図した重みに正確に寄与することが保証されるからです。 ただし、ある場合は、$N$長方形と$Q$クエリ、これは次のことにつながります$O((N+Q)(N))$最悪の場合の動作が遅すぎます。 

重要な観察は、各クエリが 2 次元のプレフィックスの合計であるということです。 これを認識したら、スイープ ラインを使用して寸法を分離できます。 イベントを分類する基準$x$、データ構造を維持しながら昇順に処理します。$y$プレフィックス合計をサポートします。 各更新は、次の位置に重みを挿入することに対応します。$y$-座標。各クエリは、最大ですべてのアクティブな重みの合計を要求します。$y$。 

これにより、問題は標準の動的プレフィックス合計構造に帰着します。 圧縮された木の上にあるフェンウィックの木$y$-軸で十分です。 各イベントはポイント更新またはクエリのいずれかになり、すべてを次の順序でソートして処理します。$x$。 

残る複雑な問題は、元の問題が純粋に軸合わせされていないことです。 このチュートリアルでは、構造を水平方向、垂直方向、および 2 つの斜め方向の 4 つの方向のケースに分解します。 それぞれの対角線の場合は、座標を回転または再パラメータ化し、次のような制約を変更することによって、軸に揃えられた接頭辞の合計の問題に還元されます。$x - y \le C$または$x + y \le C$標準のプレフィックス範囲に含めます。 

したがって、完全な解決策は 4 つの変換されたスイープ問題の組み合わせであり、それぞれが同じフェンウィック ベースのプレフィックス累積で処理されます。

 ## アルゴリズムのチュートリアル

 まず、すべての幾何学的オブジェクトを加重点イベントのコレクションに縮小します。 元の各長方形には 4 つの符号付き点が含まれるため、プレフィックスの合計をクエリすると、包含-除外を介してカウントが再現されます。 この変換はエリア クエリをポイント累積クエリに変換するため、不可欠です。 

この縮小後、スイープ ラインを使用して一度に 1 つの方向を処理します。 適切な座標変換の後、同じメカニズムがすべての方向に対して再利用されます。 

### 水平スイープ (ケース 1)

 1. すべてのイベントを昇順に並べ替えます$x$-座標。 これにより、ポイントを処理するときに、より小さい値のすべての寄与が確実に取り除かれます。$x$はすでにデータ構造に含まれています。 
2. 過剰に圧縮されたフェンウィックツリーを維持する$y$-コーディネート。 各インデックスは、その垂直レベルで累積された重みを保存します。 
3. イベントを順番に処理します。 イベントが更新の場合は、その重みをそのイベントに追加します。$y$-フェンウィックツリー内の位置。 でのクエリの場合$(x, y)$、すべてのプレフィックスの合計を計算します。$y' \le y$。 これは内部の合計貢献度を返します$[1, x] \times [1, y]$現在のスイープ状態。 

これが機能する理由は、スイープ ラインによってすべての有効性が保証されるためです。$x$- クエリが処理されるときに、コントリビューションはすでにアクティブになっています。 

### 垂直スイープ (ケース 2)

 1. 座標を交換し、同じ手順を適用します。 構造の対称性により、交換が保証されます。$x$そして$y$プレフィックス関係を保持します。 

### 斜めスイープ$y = x$(ケース3)

 1. 次を使用して座標を再パラメータ化します。$u = x - y$。 これにより、対角線の制約が軸に沿った制約に変換されます。$(u, y)$-空間。 
2. 変換された座標でそれぞれが長方形になるように、クエリ領域を 2 つのサブ領域に分割します。 これにより、三角形の境界を直接処理することが回避されます。 
3. 変換された座標に対してケース 1 またはケース 2 と同じスイープ ロジックを実行します。 

重要なアイデアは、$x - y$対角線を垂直境界に変換し、プレフィックス合計を再び適用できるようにします。 

### 対角スイープ$y = -x$(事例4)

 1. 次を使用して再パラメータ化します。$v = x + y$。 これにより、反対角拘束が軸に沿った拘束に変換されます。$(x, v)$または$(y, v)$空間。 
2. 境界の切り捨てを処理するために、クエリ領域をプレフィックス表現可能な 2 つの領域の差として表現します。 
3. 同じスイープ構造を再度適用し、すべてをケース 1 に戻します。 

### なぜ効果があるのか

 すべての段階で、アルゴリズムは、変換された座標が処理されたプレフィックス内にあるすべてのイベントの重みの合計をフェンウィック ツリーが正確に格納するという不変条件を維持します。 スイープ ラインは 1 次元での正確性を保証しますが、座標変換では、軸に整列していないすべての制約を、変換された空間のプレフィックスとして書き換えることができます。 各変換は関連する領域にわたって全単射であり、プレフィックスの蓄積に必要な順序を保持するため、寄与が失われたり二重にカウントされたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    n = int(input())
    events = []
    ys = []

    rects = []
    for _ in range(n):
        x1, y1, x2, y2 = map(int, input().split())
        rects.append((x1, y1, x2, y2))
        ys.extend([y1, y2 + 1])

        events.append((x1, y1, 1))
        events.append((x2 + 1, y1, 1))
        events.append((x1, y2 + 1, 1))
        events.append((x2 + 1, y2 + 1, 1))

    q = int(input())
    queries = []
    for i in range(q):
        x, y = map(int, input().split())
        queries.append((x, y, i))
        ys.append(y)

    ys = sorted(set(ys))
    comp = {v: i + 1 for i, v in enumerate(ys)}

    bit = Fenwick(len(ys))

    ev = []
    for x, y, w in events:
        ev.append((x, 0, y, w))
    for x, y, i in queries:
        ev.append((x, 1, y, i))

    ev.sort()

    ans = [0] * q

    for item in ev:
        if item[1] == 0:
            _, _, y, w = item
            bit.add(comp[y], w)
        else:
            _, _, y, i = item
            ans[i] = bit.sum(comp[y])

    print("\n".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```コードは並べ替えられたスイープ ラインを実装します。$x$-コーディネート。 すべての四角形の寄与は包含/除外記号付きのコーナー イベントに拡張され、クエリは同じイベント ストリームに挿入されます。 座標圧縮が必要な理由は、$y$-値は大きいことも疎な場合もあり、フェンウィック ツリーにはコンパクトなインデックス範囲が必要です。 

微妙な点は、イベントの順序が等しいことです。$x$。 更新はクエリの前に同時に処理する必要があります$x$定義に境界が含まれる場合$x$。 この順序が逆になると、正確に境界上にある点が失われ、体系的な過小カウントが発生します。

 ## 特殊なケース

 一般的な失敗例は、更新とクエリが同じ座標を共有する場合に発生します。 イベントが次の場所に存在するとします。$x = 5$クエリも次のとおりです$x = 5$。 更新前にクエリが処理される場合、その境界での寄与は無視されます。 正しい順序は、指定されたスイープ位置に対して最初にすべての更新を処理し、プレフィックスに境界点が含まれていることを確認することです。 

もう一つの微妙なケースは、$x_2 + 1$そして$y_2 + 1$シフトします。 長方形の場合$[1,1]$に$[1,1]$、シフトを省略するとキャンセルが発生し、寄与が誤ってゼロになります。 正しくシフトすると、4 つのコーナー イベントは (1,1) での単一の有効単位の寄与に減少します。これがクエリで確認されるはずです。 

3 番目のケースは、座標圧縮の誤処理です。 もし$y$- 値はインデックス作成前に重複排除されないため、Fenwick インデックスは論理的に異なる値と重複する可能性があります。 たとえば、同時に 2 つの異なるイベントが発生したとします。$y$同じ圧縮インデックスにマップする必要があります。 そうしないと、スイープ ロジックが正しい場合でも、プレフィックスの合計が誤って二重にカウントされます。
