 ## 解決策
 ## 問題の理解

 私たちに与えられた自動販売機には、スナックパックのコレクションが入っており、それぞれに名前とルーブルとコペイカで表された価格が付いています。 買い手も同じ形式で表現される固定金額を持っています。 課題は、価格ができるだけ高く、かつ購入者の金額を超えないスナック パックを 1 つ選択することです。ただし、購入者は正確な金額を支払わなければならない、つまり変更は許可されないという追加の制約があります。 

したがって、入力はアイテムのリストに対する制約付き選択問題を表します。各アイテムには数値的な重み (その価格) があり、固定予算以下の最大重みを見つける必要があります。 

制約の構造は、リニア スキャン ソリューションを強く示唆しています。 最大 100,000 項目の場合、項目ごとにソートまたは繰り返し検索を実行するアプローチは O(N log N) で許容されますが、最適な候補が 1 つだけ必要なため、不必要なオーバーヘッドは回避できます。 これにより、ペアごとの比較やネストされたスキャンなどの 2 次関数が即座に除外されます。 

問題の微妙な部分は、通貨形式の解析です。 値は「R,cc」のような文字列として指定されます。ルーブルとコペイカは単一の整数値に正規化する必要があります。 不注意な実装では、文字列を辞書順に比較したり、適切な正規化を行わずにルーブルとコペイカを別々に比較したりする可能性があり、その結果、順序が正しくなくなる可能性があります。 

いくつかの特殊なケースが重要です。 

エッジケースの 1 つは、手頃な価格のアイテムがない場合です。 たとえば、予算が 10,00 で、すべてのアイテムのコストがそれより高い場合、正しい出力は「-1」です。 最適な候補を誤って初期化する単純な解決策 (たとえば、手頃な価格をチェックせずにインデックス 0 を使用する) では、誤って無効なスナックが返されます。 

もう 1 つのエッジ ケースは、複数の商品の最高価格が同じである場合です。 たとえば、2 つのアイテムの価格が両方とも 50,00 で、予算が 50,00 の場合、どちらでも有効です。 バグのある実装では、比較ロジックに応じて有効な候補を上書きしたりスキップしたりする可能性がありますが、安定した「最大値 ≤ 予算を取る」ロジックは機能します。 

最後のエッジケースは、価格が予算に非常に近い場合、特に 99,99 対 100,00 など、コペイカの境界付近です。 コペイカの解析が正しくないと、比較が 100 倍ずれて、正確性が静かに損なわれる可能性があります。 

## アプローチ

 この強引なアイデアは簡単です。すべての価格を 1 つの整数単位に変換し、すべてのアイテムをスキャンして、その価格が予算内であるかどうかを確認します。 一致する場合は、これまでに見つかった最良の候補と比較し、最大値を維持します。 

これは、問題が制約の下で最大の要素を見つけることに帰着するため、機能します。 ただし、単一の実現可能な最大値を超えて順序付けする必要がないため、並べ替えなどのより複雑な戦略は必要ありません。 

ブルート フォース アプローチはすでに O(N) で実行されており、漸近的な複雑さの点で最適です。 接頭辞の合計や組み合わせ論のような隠れた構造はありません。 各項目は独立しています。 単純な試みに比べて実際に改善された唯一の点は、通貨の価値を注意深く正規化することです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース スキャン | O(N) | お(1) | 承認済み |
 | 並べ替えてからスキャン | O(N log N) | O(N) | 受け入れられるが不要 |

 ## アルゴリズムのチュートリアル

 すべての金額を合計コペイカを表す整数に変換し、最も有効な候補を追跡しながらアイテムに対して 1 回のパスを実行します。 

1. 予算文字列をルーブルとコペイカに解析し、合計予算をコペイカで次のように計算します。`budget = R * 100 + cc`。 これにより、すべての項目にわたって均一な比較が保証されます。 
2. 2 つの変数を初期化します。`best_price = -1`そして`best_name = ""`。 番兵`-1`有効なアイテムがそれを置き換えることを保証します。 
3. 各スナック パックについて、その価格文字列を同じ整数形式に解析します。 正確さを保つために、このステップは予算換算と同じである必要があります。 
4. スナックの価格が予算以下であるかどうかを確認します。 そうでない場合は、そのままでは購入できないため、完全にスキップしてください。 
5. スナックが手頃な価格で、その価格が以下の場合`best_price`、両方を更新します`best_price`そして`best_name`このアイテムで。 この貪欲な更新は、実現可能な最大値のみを考慮するため機能します。 
6. すべての項目を処理した後、出力します`best_name`少なくとも 1 回更新された場合は、「-1」を出力します。 

### なぜ効果があるのか

 スキャンの各ステップで、`best_price`これまでにない最大の手頃な価格を保管します。 厳密に大きい有効な値が見つかった場合にのみ更新するため、常に処理されたプレフィックスを超える最大値になります。 スキャンが終了すると、プレフィックスは配列全体になるため、保存される値は予算制約の下でのグローバル最大値になります。 すべての項目が独立しており副作用がないため、今後の操作で以前の比較が無効になることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def parse_money(s):
    # format: R,cc
    r, cc = s.strip().split(',')
    return int(r) * 100 + int(cc)

n, budget_str = input().split()
n = int(n)
budget = parse_money(budget_str)

best_price = -1
best_name = ""

for _ in range(n):
    parts = input().split()
    name = parts[0]
    price = parse_money(parts[1])

    if price <= budget and price > best_price:
        best_price = price
        best_name = name

print(best_name if best_price != -1 else -1)
```ソリューションの中核となるのは、`parse_money`すべての値を単一の比較可能な整数に正規化する関数。 この手順を行わないと、ルーブルとコペイカの混合値を比較するには辞書編集またはタプル ロジックが必要になり、手動実装ではエラーが発生しやすくなります。 

スキャンでは単一の最良の候補が維持され、厳密により良い手頃な価格が見つかった場合にのみ更新されます。 これにより、並べ替えや追加のデータ構造を必要とせずに正確性が保証されます。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    def parse_money(s):
        r, cc = s.strip().split(',')
        return int(r) * 100 + int(cc)

    n, budget_str = input().split()
    n = int(n)
    budget = parse_money(budget_str)

    best_price = -1
    best_name = ""

    for _ in range(n):
        parts = input().split()
        name = parts[0]
        price = parse_money(parts[1])
        if price <= budget and price > best_price:
            best_price = price
            best_name = name

    return str(best_name if best_price != -1 else -1)

 ## 特殊なケース

 重要なエッジケースの 1 つは、すべてのアイテムが予算よりも高価である場合です。 たとえば、予算が 10,00、項目が 20,00 と 30,00 の場合、アルゴリズムは更新されません。`best_price`、-1のままです。 有効な候補が選択されていないため、出力は正しく「-1」になります。 

別のエッジ ケースがまったく同じように発生します。 予算が 50,00 で、アイテムの価格がちょうど 50,00 の場合、条件は`price <= budget`それが受け入れられることを保証します。 スキャンが更新される`best_price`そして、後に同等以上の有効な項目が現れない限り、これが最終的な答えになります。 

3 番目の特殊なケースは、解析の正確性です。 0,05 のような入力の場合、コペイカをパディングまたは 2 桁の値として解釈しないと、0.05 ルーブルではなく 5 として扱われ、比較が中断されてしまいます。 整数をコペイカに正規化すると、0,05 が一貫して 5 になり、比較が正しいままになります。
