 ## 解決策
 ## 問題の理解

 正の整数を表す 10 進数の文字列が与えられます。 この文字列から、考えられるすべての連続する部分文字列を考慮し、それを数値として解釈し、これらの部分文字列の数値のうち 3 で割り切れる数値がいくつあるかを数えます。 

各部分文字列は、数字列内の開始位置と終了位置を選択することによって形成されます。 タスクは、これらの部分文字列のうち、3 で割り切れる値を生成するものがいくつあるかを数えることです。 

数字列の長さは次のように長くなる可能性があるため、制約は非常に重要です。$10^5$テストケースごとに。 すべての部分文字列を直接列挙すると、約$O(m^2)$部分文字列は次のようになります$10^{10}$最悪の場合、実行可能な限界をはるかに超えます。 これにより、各部分文字列を個別に構築してテストするアプローチは即座に除外されます。 

文字列に 0 などの数字や繰り返しの数字が含まれる場合、微妙なエッジ ケースが発生します。 たとえば、1 桁の部分文字列は常に非常に小さく、先頭にゼロがある部分文字列は割り切れる可能性を変更しませんが、整数の解析とオーバーフローが発生しやすい累積に依存する単純な数値変換アプローチに影響を与えます。 

もう 1 つの重要な観察事項は、大きな部分文字列を直接変換すると、標準の整数の制限を超える可能性があることです。 たとえば、100,000 桁の数値を、単純なループベースのソリューションで Python スタイルの大きな整数で繰り返し実行した場合、制限時間内に安全に保存することはできません。 

## アプローチ

 ブルートフォースソリューションは、インデックスのすべてのペアを反復します。$x \le y$、数値を構築します$f(x,y)$、そしてそれが 3 で割り切れるかどうかをチェックします。数値が 3 で割り切れるのは、その桁の合計が 3 で割り切れる場合に限り、割り切れるチェック自体は低コストです。ただし、その最適化を行ったとしても、各部分文字列の桁の合計を最初から計算するのはまだコストがかかります。$O(m)$クエリごとに、$O(m^3)$単純に実行した場合の合計、または$O(m^2)$プレフィックス合計が使用されている場合。 

改良版でも遅すぎるので、$m^2$までの長さの部分文字列$m$にはまだ大きすぎます$10^5$。 

重要な観察は、3 で割り切れるかどうかは、桁の順序や位置の重みではなく、桁の合計にのみ依存するということです。 これは、すべての部分文字列が数字の配列内の範囲の合計に対応し、合計が 3 で割り切れる範囲がいくつあるかを数えていることを意味します。 

数字を 3 を法とするプレフィックス合計配列に変換すると、この問題は、等しい値を持つプレフィックス インデックスのペアをカウントすることと同等になります。 このような各ペアは、桁の合計が 3 で割り切れる部分文字列を定義します。 

したがって、問題は古典的なプレフィックス頻度カウントの問題に帰着します。

 ## アルゴリズムのチュートリアル

 数字列を整数の配列として書き換えます。 実行中のプレフィックス合計モジュロ 3 を維持します。 

1. 周波数配列を初期化する`cnt`サイズ 3 の場合、`cnt[r]`プレフィックス合計がいくつ残っているかを保存します`r`モジュロ 3. まず始めます。`cnt[0] = 1`空のプレフィックスの合計は 0 になるためです。 
2. 累積和モジュロを維持しながら、左から右に数字を繰り返します。 3. 各数字を読み取った後、累積剰余を更新します。 
3. 現在のプレフィックスが残っている位置にいるときはいつでも`r`、残りを含む以前のすべてのプレフィックス`r`現在の位置で終わる有効な部分文字列を形成します。 追加します`cnt[r]`答えに。 
4. カウント後、インクリメントします`cnt[r]`今後の一致に現在のプレフィックスを含めます。 

各ステップは、すべての部分文字列を暗黙的に構築することに直接対応します。 部分文字列を明示的に生成する代わりに、プレフィックスの状態を比較します。 

### なぜ効果があるのか

 インデックスの部分文字列$l$に$r$桁の合計は、prefixSum[r] から prefixSum[l-1] を引いた値に等しくなります。 この合計は、両方の接頭辞の合計が 3 を法とする同じ値を持つ場合に限り、3 で割り切れます。 したがって、すべての有効な部分文字列は、等しい接頭辞の剰余のペアに対応し、部分文字列のカウントは、そのようなペアのカウントとなります。 アルゴリズムは、文字列を処理するときにこれらのペアを 1 回だけ列挙します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_one(m, s):
    cnt = [0, 0, 0]
    cnt[0] = 1

    cur = 0
    ans = 0

    for ch in s:
        cur = (cur + (ord(ch) - 48)) % 3
        ans += cnt[cur]
        cnt[cur] += 1

    return ans

def main():
    t = int(input())
    for _ in range(t):
        m, s = input().split()
        m = int(m)
        print(solve_one(m, s))

if __name__ == "__main__":
    main()
```このソリューションでは、プレフィックス合計のモジュロ 3 に対応するカウンターが 3 つだけ維持されます。実行中の剰余は桁ごとに更新され、整数のオーバーフローや部分文字列の構築が回避されます。 

よくある落とし穴は、各部分文字列の桁の合計を誤って再計算し、二次関数の動作を引き起こすことです。 もう一つは頭文字を忘れることです`cnt[0] = 1`、インデックス 0 から始まる部分文字列を考慮します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    def solve_one(m, s):
        cnt = [0, 0, 0]
        cnt[0] = 1
        cur = 0
        ans = 0
        for ch in s:
            cur = (cur + (ord(ch) - 48)) % 3
            ans += cnt[cur]
            cnt[cur] += 1
        return ans

    t = int(input())
    out = []
    for _ in range(t):
        m, s = input().split()
        out.append(str(solve_one(int(m), s)))
    return "\n".join(out)

# provided samples

# custom cases

assert run("1\n1 0\n") == "1", "zero digit"
assert run("1\n3 111\n") == "6", "all substrings divisible"
assert run("1\n3 124\n") == "2", "mixed case"

 ## 特殊なケース

 キー エッジ ケースは、完全にゼロで構成される文字列です。 すべての部分文字列の合計はゼロであるため、すべての部分文字列は有効です。 すべてのプレフィックスの残りが 0 のままであるため、アルゴリズムはこれを正しく処理します。そのため、すべての新しいプレフィックスは以前のすべてのプレフィックスと一致し、$m(m+1)/2$自然にカウントされます。 

もう 1 つの特殊なケースは、1 桁の文字列です。 アルゴリズムが初期化されます`cnt[0] = 1`したがって、数字が 3 で割り切れる場合は、1 つの有効な部分文字列として正しくカウントされ、それ以外の場合は 0 としてカウントされます。 これにより、特殊な場合のロジックが回避されます。 

3 番目のケースは、「111111」のような交互の数字です。 ここでは、すべてのプレフィックスの合計がモジュロ 3 空間で決定論的に循環し、剰余が繰り返されるため、位置推論ではなく周波数の累積によって正確なカウントが保証されます。
