 ## 解決策
 ## 問題の理解

 分ごとのトラフィック値のストリームを監視する監視システムをシミュレートしています。 毎分、現在のトラフィックを固定容量のしきい値と比較します。 システムは、1 回の違反や 1 回の安全な読み取りにはすぐには反応しません。 代わりに、ヒステリシスを使用します。過負荷が継続した場合にのみアラーム状態に入り、回復が継続した場合にのみアラーム状態を終了します。 

より正確には、システムが通常の状態にあるときに、トラフィックが厳密にしきい値を上回った状態が連続して何分間続いたかをカウントします。 このカウントが所定の制限に達すると、システムはアラームに切り替わります。 その後、アラームが発生している間、トラフィックがしきい値以下に継続して何分続いたかをカウントします。 回復カウンタが別の制限に達すると、システムは通常の状態に戻ります。 警戒中は、安全な時間が十分に蓄積されるまで継続的にそこに留まります。 

出力は、シミュレーション全体にわたってシステムがアラーム状態にあった合計分数です。 

制約は、テスト ケースあたり最大 10 万分、テスト ケース 100 個までです。 これにより、一定の作業を超えて分当たり高価な構造を再計算またはシミュレーションしようとするアプローチが除外されます。 すべてのソリューションはテスト ケースごとに線形である必要があります。 

微妙なエッジケースが遷移から発生します。 単純な実装では、状態変化時にカウンタがリセットされることを忘れたり、遷移分を誤って 2 回カウントしたりすることがよくあります。 

たとえば、しきい値が 5 で、3 回連続して高い値になった後にアラームが発生し、2 回連続して安全な値になった後にクリアされると考えます。 

入力:```
6 5 3 2
6 6 6 1 1 1
```ここでは、アラームは 3 分目にトリガーされます。不注意な実装では、4 分目にすぐにクリアが開始され、システムがアラームを終了するのが早すぎると誤って判断されたり、正確な遷移構造が含まれていないためにアラーム継続時間を誤ってカウントしたりする可能性があります。 正しい動作は、アラームが 3 番目の最高値の分後にのみ開始され、連続した 2 つの安全な分後にのみ終了することです。 

もう 1 つのエッジ ケースは、システムがまったくアラームに入らない場合です。 連続した実行がしきい値に達しないため、たとえ孤立したスパイクがあったとしても、答えはゼロでなければなりません。 

## アプローチ

 ブルートフォースのアイデアは、現在の状態を維持し、連続する高値と低値をカウンターして、説明どおりにシステムをシミュレートすることです。 毎分カウンターを更新し、状態遷移が発生するかどうかを確認します。 また、アラームに費やした分数も累積します。 

このシミュレーションは 1 分ごとに 1 回処理されるため、すでに最適に近い状態になっています。 単純なソリューションが遅くなる唯一の原因は、誰かが各位置で連続するストリークを最初から再計算し、逆方向にスキャンしたり、セグメントを再チェックしたりする場合です。 これは、最悪の場合、特に値が交互に繰り返されてプレフィックスの再スキャンが強制される場合には、二次時間まで低下します。 

重要な洞察は、プロセスが本質的にステート マシン ベースであるということです。 システムは、現在の状態 (正常またはアラーム) と連続した実行を追跡する 2 つのカウンターのみに依存します。 過去の議事録を再度参照したり、複雑なデータ構造を維持したりする必要はありません。 各遷移はローカル条件によってトリガーされるため、単一の左から右へのパスで十分です。 

これにより、配列を 1 回スキャンする間に変数の数を一定に維持するという問題が軽減されます。

 | ブルート フォース (再スキャン実行) | O(N²) | お(1) | 遅すぎる |
 | ステートマシンのシミュレーション | O(N) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在の状態と 2 つのカウンターを維持します。 

1. システムを通常の状態に初期化します。 カウンターを設定する`high_streak = 0`そして`low_streak = 0`。 こちらもセット`alarm_time = 0`。 
2. 毎分のトラフィック値を左から右に繰り返します。 毎分、それをしきい値と比較します。 
3. 現在の状態が正常で、トラフィックがしきい値を超えている場合、インクリメントします。`high_streak`。 それ以外の場合はリセット`high_streak`ゼロに。 いつ`high_streak`必要なアクティベーション長に達すると、状態をアラームに切り替えてリセットします`low_streak`。 
4. 現在の状態がアラームの場合、この分を次のように累積します。`alarm_time`システムは 1 分間アクティブであると見なされるため、移行ロジックの前に実行されます。 
5. アラームが発生している間、トラフィックがしきい値以下の場合は、増加します。`low_streak`。 それ以外の場合はリセット`low_streak`ゼロに。 いつ`low_streak`必要なクリアランス長に達したら、状態を通常に戻してリセットします`high_streak`。 
6. すべての分が処理されるまでこのプロセスを続けます。 

重要な点は、アラーム時間が将来の遷移ではなく、毎分の状態に基づいてカウントされることです。 これにより、状態を切り替える瞬間のオフバイワンエラーが回避されます。 

### なぜ効果があるのか

 システムは、連続実行カウンタの形式のみのメモリを備えた有限状態マシンによって完全に記述されます。 どの時点でも、将来の状態は現在の状態と、しきい値に対する現在の値にのみ依存します。 カウンタにより、実行以降の履歴を必要とせずに、連続した実行が正しく検出されることが保証されます。 毎分 1 回の状態遷移チェックと、場合によっては 1 回のカウンタ更新が行われるため、情報が失われることはなく、再計算は必要ありません。 これにより、正確性と線形処理が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []
    
    for _ in range(T):
        N, Xmax, A, C = map(int, input().split())
        arr = list(map(int, input().split()))
        
        state = 0  # 0 = normal, 1 = alarm
        high_streak = 0
        low_streak = 0
        alarm_time = 0
        
        for x in arr:
            if state == 1:
                alarm_time += 1
            
            if state == 0:
                if x > Xmax:
                    high_streak += 1
                else:
                    high_streak = 0
                
                if high_streak >= A:
                    state = 1
                    low_streak = 0
            else:
                if x <= Xmax:
                    low_streak += 1
                else:
                    low_streak = 0
                
                if low_streak >= C:
                    state = 0
                    high_streak = 0
        
        out.append(str(alarm_time))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションは、トラフィック アレイ上の単一パスとして構成されています。 変数`state`モニターが現在警報を発しているかどうかを追跡します。 カウンター`high_streak`そして`low_streak`状態に応じて相互に関連します。 アラーム時間は、システムが分の開始時にすでにアラーム状態にある場合にのみ増分され、1 分間のカバレッジが正しくキャプチャされます。 

よくある間違いは、追加する前に状態を更新することです。`alarm_time`これにより、最後のアラーム分が失われます。 もう 1 つの微妙な問題は、状態を切り替えるときに反対側のカウンタをリセットできないことです。これにより、状態が反転した直後に意図しない遷移が発生する可能性があります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    T = int(input())
    res = []

    for _ in range(T):
        N, Xmax, A, C = map(int, input().split())
        arr = list(map(int, input().split()))
        
        state = 0
        high = 0
        low = 0
        alarm = 0
        
        for x in arr:
            if state == 1:
                alarm += 1
            
            if state == 0:
                if x > Xmax:
                    high += 1
                else:
                    high = 0
                if high >= A:
                    state = 1
                    low = 0
            else:
                if x <= Xmax:
                    low += 1
                else:
                    low = 0
                if low >= C:
                    state = 0
                    high = 0
        
        res.append(str(alarm))
    
    return "\n".join(res)

 ## 特殊なケース

 エッジ ケースの 1 つは、アクティブ化とクリアのしきい値が両方とも 1 の場合です。システムは非常に敏感になり、状態がすぐに切り替わります。 ストリークカウンターが 1 ステップでしきい値に達し、現在の分を正しく処理した後でも状態遷移が発生するため、アルゴリズムはこれを処理します。 

もう 1 つのエッジ ケースは、アレイの終わり近くでアラームをクリアする十分な時間がないままアラームをトリガーする長いシーケンスです。 このアルゴリズムは、アレイが終了するまでのみアラーム分をカウントし、最終クリアランスを必要としません。これは、観測されたアラーム時間のみを測定するため、問題定義と一致します。 

最後の微妙なケースは、トラフィックがしきい値付近で変動し、カウンタが繰り返しリセットされる場合です。 両方のカウンタが反対の条件でリセットされるため、無効なキャリーオーバーは発生せず、ステート マシンは誤ってトリガーされることなく安定したままになります。
