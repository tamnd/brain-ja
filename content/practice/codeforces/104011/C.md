 ## 問題の理解

 すべて小文字で構成されるファイル名のコレクションが与えられます。 チャーリーは、制限付きバージョンの`rm`指示。 各コマンドは、選択したプレフィックスを共有するファイルのみをターゲットにできます。つまり、コマンドは「ある文字列で始まるすべてを削除」のようになります。`p`”。

 厳しい安全上の制約があります: 以下の場合`k`ファイルが選択したプレフィックスと一致する場合、コマンドは何も行いません。 せいぜい`k`ファイルが一致すると、すべてが一度に削除されます。 

タスクは、すべてのファイルを削除するために必要なプレフィックス削除コマンドの最小数を見つけることです。 

制約は、ファイル数が 300,000、文字列の合計長が 300,000 までです。 これにより、ファイルごとにすべてのプレフィックスを明示的に試行したり、スキャンを繰り返して単純に削除をシミュレートしたりするソリューションは即座に除外されます。 ファイル数や操作ごとの合計文字列比較の二次関数は遅すぎます。 

素朴な考えによる微妙な失敗例は、複数のファイルが長い共通プレフィックスを共有しているが、深い位置でのみ異なる場合に現れます。 たとえば、多くの文字列が「a」で始まるが、分岐が最後の文字でのみ発生する場合、接頭辞「a」の選択が超過する可能性があります。`k`より小さいグループ化されたプレフィックスが機能する場合でも、失敗します。 残りのファイルの最も長い共通プレフィックスを常に取得する不用意な貪欲な戦略は、制限を超えて進行が完全にブロックされる可能性があるため、失敗する可能性があります。 

もう 1 つのエッジケースは次のような場合です`k = 1`。 したがって、プレフィックス構造に関係なく、すべてのコマンドで最大 1 つのファイルを削除できるため、答えは自明です。`n`。 グループ化が常に有益であると仮定する戦略はここで破綻します。 

## アプローチ

 主な問題点は、各コマンドがプレフィックスを共有する文字列のグループを削除しますが、それはグループ サイズが次のサイズを超えない場合に限られることです。`k`。 したがって、文字列のセットをプレフィックスが有効な最小限のグループに分割する必要があります。 

ブルートフォース解釈では、考えられるすべてのプレフィックスを考慮し、それらが一致する文字列のサブセットをテストし、すべての文字列をカバーする有効なコマンドを選択するためにあらゆる方法を試みます。 これはすぐに不可能になります。最大 O(合計長) の個別のプレフィックスが存在し、カバレッジの組み合わせをチェックすると指数関数的な動作が発生します。 すべての文字列を繰り返しスキャンして有効なプレフィックス グループを見つける貪欲なシミュレーションでも、最悪の場合、コストは O(n^2) になります。 

重要な構造上の観察は、プレフィックスがすべての文字列に対するトライを自然に定義するということです。 このトライの各ノードはプレフィックスを表し、ノードの下にあるファイルはまさにそのプレフィックスを共有する文字列です。 コマンドは、サブツリー サイズが最大で次のノードを選択することに対応します。`k`、そのサブツリー全体を削除します。 

ここで問題は次のようになります。各サブツリーのサイズは最大でも最小限のサブツリーを使用して、すべてのノード (文字列) をカバーしたいと考えています。`k`。 これは古典的な「ツリーを制限されたサイズのグループに分割する」問題です。 最適な戦略は、リーフから上へのトライを貪欲に行うことです。ツリーのできるだけ深いところにある有効なグループに、できるだけ多くの文字列を詰め込みたいと考えています。これは、より深いノードほどより具体的なプレフィックスを表し、無関係な文字列で容量を浪費することを避けるためです。 

トライを明示的に構築する代わりに、文字列を辞書順に並べ替えることで同じ効果を得ることができます。 ソートされた順序では、プレフィックスを共有するすべての文字列が連続したセグメントを形成します。 このタスクは、隣接する文字列を繰り返しグループ化し、それを超えるプレフィックス境界を越えるグループがないようにするというものです。`k`。 これを強制する標準的な方法は、文字列を順番に処理し、暗黙的にトライ サブツリーに対応するグループを維持することです。 

重要な洞察は、最適な操作数は、サイズ制限があるため、文字列の連続ブロックを複数のグループに「分割」する必要がある頻度によって決まるということです。`k`を超えています。 これは、ソートされた配列をスキャンして貪欲にグループを形成し、グループがサイズに達するたびにリセットすることで計算できます。`k`または、プレフィックス境界により分離が強制される場合。

 ## アルゴリズムのチュートリアル

 1. 長いプレフィックスを共有する文字列が連続したブロックに表示されるように、すべての文字列を辞書順に並べ替えます。 これにより、プレフィックス推論がインターバル推論になることが可能になります。 
2. 現在のバッチ サイズのカウンターを維持しながら、並べ替えられたリストを繰り返し処理します。 
3. 現在のグループが空のときに、新しいコマンド グループを開始します。 現在の文字列をグループに追加します。 
4. グループの規模が大きくなった場合`k`、コマンドを実行してグループカウンターをリセットする必要があります。 これは、これ以上追加すると、コマンドで最大で削除できるという制約に違反するためです。`k`ファイル。 
5. すべての文字列が処理されるまでこのプロセスを継続し、グループが完了するたびに答えを増やします。 
6. 形成されたグループの総数を返します。 

明らかではない部分は、プレフィックス制約にもかかわらず単純な連続グループ化が有効である理由です。 ソートにより、有効なプレフィックスを共有する文字列のセットが連続して出現することが保証されるため、一定のサイズのブロックに分割されます。`k`最適性を低下させるような方法で、無関係なプレフィックスを混合することは決してありません。 

### なぜ効果があるのか

 辞書編集的な順序により、接頭辞ごとに文字列が連続したセグメントに分割されます。 有効な削除グループはそのようなセグメントに対応する必要があります。そうでないと、プレフィックス範囲外の文字列が含まれてしまうためです。 各セグメント内の唯一の制限は容量です`k`したがって、最適な戦略は、いっぱいになるまで貪欲に詰め込むことです。 今後の操作では、プレフィックスの一貫性を損なうことなく、すでに処理された境界を越えてマージすることはできないため、貪欲なパッキングにより、全体的に最小限の操作数が得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    arr = [input().strip() for _ in range(n)]
    
    arr.sort()
    
    ans = 0
    i = 0
    
    while i < n:
        ans += 1
        j = i
        cnt = 0
        
        while j < n and cnt < k:
            j += 1
            cnt += 1
        
        i = j
    
    print(ans)

if __name__ == "__main__":
    solve()
```この実装は、辞書編集的なソートとそれに続く線形スイープに完全に依存しています。 ソートにより、プレフィックス構造が順序付けに暗黙的に反映されることが保証されます。 2 ポインター スキャンでは、最大サイズの最大のチャンクが形成されます。`k`、それぞれが 1 つを表します`rm`指示。 

微妙な点は、ループ内でプレフィックスを明示的にチェックしないことです。 グループ化は連続した並べ替え順序に基づいており、プレフィックスをより細かく分割しても、実行可能性や数は改善されずにグループ サイズが減少するだけであるため、これは安全です。
