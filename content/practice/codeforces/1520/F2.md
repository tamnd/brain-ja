 ## 解決策
 ## 問題の理解

 長さの隠されたバイナリ配列を扱っています$n$、各位置は 0 または 1 のいずれかです。 配列はそれ自体では変化しませんが、現在の配列の位置を正しく特定するたびに、私たち自身のアクションによって変更されます。$k$左から 0 番目の位置は永久に 1 に反転されます。 

配列を観察する唯一の方法は、範囲合計クエリを使用することです。 セグメントに対するクエリ$[l, r]$現在その間隔内にあるものの数を返します。 配列はバイナリであるため、ゼロはセグメント長内の補数にすぎないため、セグメント内にゼロがいくつあるかが暗黙的にわかります。 

タスクは繰り返されます$t$独立したリクエスト。 リクエストごとに値が与えられます$k$の位置を出力する必要があります。$k$配列の現在の状態の - 番目のゼロ。 各回答の後、ゼロが 1 になるため、配列が変化します。 

制約が厳しいため、すべてのクエリに慎重に予算を計上する必要があります。 配列は次のような大きさにすることができます$2 \cdot 10^5$、まであります$10^4$クエリ。 インタラクティブなリクエストの総数は制限されているため、アレイを繰り返しスキャンしたり、状態を最初から再構築したりするアプローチは、すぐに遅すぎます。 クエリごとの 1 つのバイナリ検索であっても、慎重に最適化する必要があります。各バイナリ検索では対話型呼び出しの数に対数係数が乗算されるためです。$n$。 

単純なアプローチでは、最初に完全な配列を再構築しようとします。 これは、各位置を個別にクエリするか、完全にわかるまでセグメントを再帰的に分割する必要があるため、失敗します。$O(n)$または$O(n \log n)$許可された予算をはるかに超えるクエリ。 

それぞれを見つけようとすると、別の失敗例が表示されます。$k$-番目のゼロを最初からスキャンしてデクリメントする$k$範囲クエリを使用します。 それは退化します$O(n)$最悪の場合、処理できないリクエストごとに$t = 10^4$。 

動的な更新により、さらに微妙な問題が発生します。 各回答の後、1 つのゼロが 1 になるため、クエリの構造が変化します。 すべてのクエリにわたって固定プレフィックス構造を前提とするメソッドは、最初の更新後に誤った結果を暗黙的に生成します。 

## アプローチ

 ブルートフォースのアイデアは単純です。クエリごとに、左から右にスキャンし、ゼロのカウンターを維持します。 ゼロに達するたびに減少します$k$、ゼロになったらその位置を出力します。 これは概念的には正しいですが、各位置が 0 か 1 かを知る必要があります。 配列がわからないため、サイズ 1 の範囲クエリを使用して各位置を個別にクエリする必要があります。 それはすでにコストがかかります$O(n)$リクエストごとにクエリが発生するため、$O(n t)$、それは完全に不可能です。 

より構造化されたアプローチは、範囲合計を介してプレフィックス情報を計算できるという事実を利用することです。 任意の接頭辞に含まれる 1 の数を計算できれば$[1, x]$の場合、ゼロの数は単純に次のようになります。$x - \text{ones}(1, x)$。 これにより、問題は最小のインデックスを見つけることに変換されます。$x$ゼロの数は次のようになります$x$少なくとも$k$。 

この条件は単調です$x$, したがって、二分探索が適用可能になります。 二分探索内の各チェックでは範囲合計クエリが尋ねられ、そこから現在の中間点に少なくとも次の値が含まれているかどうかを導き出します。$k$プレフィックスにゼロが含まれています。 プレフィックス ゼロのカウントに答えることができたら、$k$-番目のゼロは対数時間で見つけることができます。 

複雑なのは、すべてのバイナリ検索に複数の対話型クエリが必要であり、クエリの総数が厳しく制限されていることです。 この解決策は、構造化されていない方法で任意の部分構造を繰り返しクエリする必要がないという事実に依存しています。 すべての操作は純粋にプレフィックス評価によって駆動され、単一の位置を 0 から 1 に反転する更新を除いて、各クエリは独立しています。 

これにより、範囲の合計をクエリする機能を維持し、リクエストごとにインデックスで二分検索を使用するという標準的なソリューションが得られます。 位置が見つかると概念的にそれを反転し、インタラクターの状態がすでに更新されているため、将来のプレフィックス合計にはこの変更が自動的に反映されるため、更新は暗黙的です。

 ## アルゴリズムのチュートリアル

 1. リクエストごとに、プレフィックスに少なくとも以下が含まれる最小のインデックスを見つけたいと考えています。$k$ゼロ。 これをインデックス範囲にわたる単調な検索問題として扱います。$[1, n]$。 
2. プレフィックス内のゼロの数を計算する関数を定義します。$[1, x]$。 これは次のように計算されます$x - \text{sum}(1, x)$、合計はインタラクターから取得されます。 このステップでは、隠れたバイナリ構造を直接使用可能な量に変換します。 
3. 範囲に対して二分探索を実行します。$[1, n]$。 それぞれの中間点で$m$、内の 1 の合計をクエリします。$[1, m]$、それをゼロの数に変換し、少なくとも次であるかどうかを確認します。$k$。 そうであれば、答えは左半分にあります。 それ以外の場合は、右半分にあります。 
4. 二分探索が単一の位置に収束するまで続けます。 その立場というのは、$k$現在の配列内の - 番目のゼロ。 
5. 見つかった位置を出力し、正解後のインタラクターの状態変化に基づいて更新ロジックを直ちに実行します。 反転された位置は、今後のすべてのクエリで 1 つとして扱われるようになりました。 

重要な不変点は、各更新の後、インタラクターは常に現在の配列状態を正確に表し、すべてのプレフィックス クエリは以前のすべての反転を反映することです。 二分探索の正しさは、述語「プレフィックスに少なくとも次の内容が含まれる」の単調性に依存します。$k$ゼロ」。これはプレフィックスの合計にのみ依存し、更新後も有効です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def ask(l, r):
    print(f"? {l} {r}")
    sys.stdout.flush()
    res = int(input())
    if res == -1:
        exit(0)
    return res

def find_kth_zero(n, k):
    l, r = 1, n
    while l < r:
        m = (l + r) // 2
        ones = ask(1, m)
        zeros = m - ones
        if zeros >= k:
            r = m
        else:
            l = m + 1
    return l

def main():
    n, t = map(int, input().split())
    for _ in range(t):
        k = int(input())
        pos = find_kth_zero(n, k)
        print(f"! {pos}")
        sys.stdout.flush()

if __name__ == "__main__":
    main()
```ソリューションの中核となるのは、`ask`裁判官との対話をカプセル化する関数。 すべての二分探索ステップは、この関数によって返されるプレフィックスの合計に依存します。 問題はゼロで表現されますが、インタラクターは 1 の合計しか提供しないため、プレフィックス内の 1 から 0 への変換は不可欠です。 

バイナリ検索ループは標準ですが、重要な点は、常にインデックス 1 からクエリを実行することです。これにより、プレフィックス情報のみを使用することが保証され、配列のさまざまな状態にわたって一貫性と比較性が維持されます。 

## 実用的な例

 ### トレースの例

 小さな概念的配列を考えてみましょう。 

初期状態:`[1, 0, 1, 1, 0, 1]`と求めたとします。$k = 2$。 

二分検索を実行します。 

| ステップ | l | r | メートル | もの(1..m) | ゼロ(1..m) | 決定 |
 | --- | --- | --- | --- | --- | --- | --- |
 | 1 | 1 | 6 | 3 | 2 | 1 | 右に行きます |
 | 2 | 4 | 6 | 5 | 3 | 2 | 左に行く |
 | 3 | 4 | 5 | 4 | 3 | 1 | 右に行きます |

 最終的な答えは 5 位です。 

この後、位置 5 が 1 になり、配列は次のようになります。`[1, 0, 1, 1, 1, 1]`。 

このトレースは、述語が単調であり、将来のクエリには常に変更されたプレフィックスの合計が反映されるため、更新によって正確性が損なわれないことを示しています。

 ## 特殊なケース

 重要なエッジケースは、最初のいくつかの要素がすべて 1 である場合です。 その場合、最初の有効なゼロが配列の奥深くに出現する可能性があり、二分検索ではゼロを含まないプレフィックスを正しく無視する必要があります。 1 だけの接頭辞は 0 を生成し、正しく失敗するため、述語は引き続き機能します。$k \ge 1$状態。 

もう 1 つのエッジ ケースは、何度もフリップした後にクエリが繰り返されることです。 反転するたびにプレフィックス構造が変更されるため、固定インデックスに関するキャッシュされた推論は壊れてしまいます。 このアルゴリズムはキャッシュを完全に回避し、新しいプレフィックス クエリのみに依存するため、結局のところ正しいままになります。$t$更新情報。 

最後の微妙なケースは次のような場合です。$k$残りのゼロの総数に等しい。 この場合、正しい答えは常に右端の 0 であり、最終セグメントに到達するまで小さなプレフィックスはすべて条件を満たさないため、二分探索は自然にそれに収束します。
