 ## 解決策
 ## 問題の理解

 Lesha には、今日と明日の 2 つの別々の時間予算があります。 各講義ノートには、そのインデックスに等しい固定の読書コストがあります。つまり、ノート 1 には 1 時間、ノート 2 には 2 時間かかります。 彼はメモの任意のサブセットを選択できますが、選択した各メモは 1 日で完全に読まれなければならず、各メモは両日にわたって最大 1 回しか使用できません。 

目標は、彼が読んだ個別のメモの合計数を最大化し、メモを 2 つのグループに分割することです。1 つのグループは今日割り当てられ、合計コストが以下のグループに割り当てられます。`a`、および明日に割り当てられる別のグループ (合計コストが超えない)`b`。 

メモは無期限にインデックス付けされますが、コストが直線的に増加するため、実際に使用できるのは小さなインデックスのみです。 重要な構造は、小さいインデックスは厳密に安価であるため、カウントを最大化するという点では常に効率的であるということです。 

制約により許可されるのは、`a, b`最大 10^9 です。これにより、ナップザック状態をシミュレートしたり、サブセットを動的に試行したりする試みが即座に除外されます。 どのような解決策でも、可能性を列挙するのではなく、最適な選択の構造について直接推論する必要があります。 

単純な間違いは、全体的な調整を行わずに、毎日貪欲にノートを割り当てようとすることです。 たとえば、次の場合`a = 3`そして`b = 3`、選択する`{1,2}`今日は3時間を使い切ってしまい、明日に役立つものは高額品以外何も残らない。 ただし、割り当てを交換したり、別の方法で分割したりすると、合計数が向上する可能性があります。 もう 1 つの微妙な失敗モードは、グローバルな一意性を確保せずに、毎日独立して可能な限り最小の音符を選択することです。 両日とも同じ安い紙幣を使おうとするかもしれません。 

## アプローチ

 この強引なアイデアは、2 日間の間で音符の接頭辞を分割するためにあらゆる方法を試みることです。 固定最大ノートインデックスの場合`k`の任意のサブセットを選択できます。`{1..k}`、各要素を 1 日目または 2 日目のいずれかに割り当て、両方の合計の実現可能性を確認します。 これはすでに指数関数的です`k`, 各メモには、未使用、1 日目、2 日目の 3 つの選択肢があるためです。 キャップをしても`k`最大値で、`k(k+1)/2 ≤ a+b`、割り当ての数があまりにも急速に増加します。 

重要な観察は、コストが厳密に増加しているため、最適なソリューションは常にプレフィックスのような選択で構成されるということです。 より大きな番号の紙幣が使用される場合、すべての安価な未使用紙幣が常に最初に含めるより良い候補になります。 これにより、問題は最小の数値を 2 つのナップザックに分散することになります。 

課題の観点から考えるのではなく、視点を逆転させます。まず分割を無視してできるだけ多くの小さなメモを取ろうとし、次にそれを 2 日間にどのように分割するかを決定します。 メモ 1、2、3、…、k を取ると、その合計コストは次のようになります。`k(k+1)/2`。 最大限のものを選択します`k`この合計が`a + b`。 その後、残りのタスクは、最初にこれらを分割することです`k`2 つの容量制約間の数値。 

プレフィックスが固定されたら、最大から最小まで貪欲に割り当てるのが最適です。大きなアイテムは配置するのが難しいため、それらを収容できる日の最初に配置する必要があります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース サブセット | 指数 | 指数 | 遅すぎる |
 | プレフィックス + 貪欲な分割 | O(k) | O(k) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ステップ 1: 最大プレフィックスを見つける

 最大のものを計算します`k`そのような`1 + 2 + ... + k ≤ a + b`。 これにより、合計しても支払えない紙幣を使用しようとすることがなくなります。 

その理由は、次のような最適なソリューションは、`k`ノートは必ず最初のノートのサブセットを使用する必要があります。`k`なぜなら、大きな音符を優先して小さな音符をスキップすることは決して有益ではないからです。 

### ステップ 2: 残りの容量を初期化する

 治療します`a`そして`b`as remaining capacities for two independent bins. Initially both are full.

 ### ステップ 3: k から 1 までノートを割り当てます。 

We iterate from`k`まで`1`。 ノートごとに`i`、都合の良い日に配置するようにしています。 

可能であれば初日に配置することを好みます。 そうでない場合は、2 日目に挑戦します。 

下に行く理由は、ノートが大きくなるほど制限が厳しくなるためです。 遅延すると、たとえ有効な割り当てが存在していても、実現可能性が失われる可能性があります。 

### ステップ 4: 割り当てを保存する

 私たちは 2 つのリストを維持しています。1 つは 1 日目用、もう 1 つは 2 日目用です。 ノートを割り当てるたびに、対応する容量からそのコストが減算されます。 

### ステップ 5: 出力

 両方のグループを印刷します。 

### なぜ効果があるのか

 正しさは単調な交換引数に依存します。 最適な解は、要素の数を減らすことなく、整数の接頭辞を使用する解に変換できます。 プレフィックスが固定されたら、最初に大きな要素を割り当てても、実行可能なソリューションがブロックされることはありません。大きな要素の配置に失敗すると、両方のビンが小さすぎてその要素を収容できないことを意味し、その要素を含む有効なパーティションの実現可能性と矛盾します。 

したがって、最大から最小への貪欲な配置により、実現可能性が維持され、利用可能なすべての数値の使用が最大化されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def max_k(total):
    k = 0
    cur = 0
    while True:
        if cur + (k + 1) > total:
            break
        k += 1
        cur += k
    return k

a, b = map(int, input().split())
total = a + b

k = max_k(total)

a_rem, b_rem = a, b
day1 = []
day2 = []

for i in range(k, 0, -1):
    if i <= a_rem:
        day1.append(i)
        a_rem -= i
    else:
        day2.append(i)
        b_rem -= i

print(len(day1))
print(*day1)
print(len(day2))
print(*day2)
```最初の関数は、結合容量に適合する最大のプレフィックス合計を計算します。 これにより、世界的に可能な数値を超える数値を考慮する必要がなくなります。 

貪欲ループは以下から処理します。`k`下向きに。 各数値は、それが収まる最初のビンに配置されます。 減算アップデートにより、容量を超えることがなくなります。 

最初に 1 日目を試すかどうかは任意です。 最終的な割り当ては一意ではないため、どちらの順序でも機能します。 

## 実用的な例

 ### 例 1: a = 3、b = 3

 まず最大値を計算します`k`そのような`k(k+1)/2 ≤ 6`。 これにより、`k = 3`以来`1+2+3 = 6`。 

| 私 | レム | ビーレム | アクション | 1日目 | 2日目 |
 | --- | --- | --- | --- | --- | --- |
 | 3 | 3 | 3 | 1日目に収まる | [3] | [] |
 | 2 | 0 | 3 | 2日目に収まる | [3] | [2] |
 | 1 | 0 | 1 | 2日目に収まる | [3] | [2,1] |

 1 日目はちょうど 3 時間を使用し、2 日目はちょうど 3 時間を使用します。 メモはすべて使用されます。 

これは、貪欲な順序により、大きな制約を最初に配置しながら、小さな要素を不必要にブロックすることを回避していることがわかります。 

### 例 2: a = 5、b = 2

 合計は7なので、`k = 3`以来`1+2+3 = 6`。 

| 私 | レム | ビーレム | アクション | 1日目 | 2日目 |
 | --- | --- | --- | --- | --- | --- |
 | 3 | 5 | 2 | 1日目に収まる | [3] | [] |
 | 2 | 2 | 2 | 1日目に収まる | [3,2] | [] |
 | 1 | 0 | 2 | 2日目に収まる | [3,2] | [1] |

 これは、不均衡が自然に処理されていることを示しています。容量が大きいほど重いアイテムが最初に吸収されますが、容量が小さいほど、残りの小さな要素が引き続き受け入れられます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(k) | 選択されたプレフィックスを 1 回通過します |
 | スペース | O(k) | 割り当てられたノートを保存する |

 の値`k`は、次のような最大の整数によって制限されます。`k(k+1)/2 ≤ 2×10^9`、これは約 60000 であるため、解は簡単に制限内に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    a, b = map(int, input().split())
    total = a + b

    k = 0
    cur = 0
    while cur + (k + 1) <= total:
        k += 1
        cur += k

    a_rem, b_rem = a, b
    day1 = []
    day2 = []

    for i in range(k, 0, -1):
        if i <= a_rem:
            day1.append(i)
            a_rem -= i
        else:
            day2.append(i)
            b_rem -= i

    out = []
    out.append(str(len(day1)))
    out.append(" ".join(map(str, day1)))
    out.append(str(len(day2)))
    out.append(" ".join(map(str, day2)))
    return "\n".join(out)

# sample
assert run("3 3") is not None

# minimum case
assert run("0 0") == "0\n\n0\n"

# only one day
assert run("10 0") is not None

# asymmetric split
assert run("5 2") is not None

# large balanced
assert run("1000000000 1000000000") is not None

 | 0 0 | 空のグループ | ゼロキャパシティーの取り扱い |
 | 10 0 | 一日ですべて | 片面梱包 |
 | 5 2 | 分割の実現可能性 | 貪欲な配布の正確性 |
 | 大きい等しい | フル活用 | パフォーマンスとプレフィックス バインド |

 ## 特殊なケース

 いずれかのとき`a`または`b`がゼロの場合、貪欲なチェックは最初に空の側で失敗し、すべてのアイテムが唯一の利用可能な容量に移されるため、アルゴリズムは自然にすべてを other day に配置します。 

非常に大きな等しい入力の場合、プレフィックスの計算は約 60000 で停止するため、オーバーフローやパフォーマンスの問題は発生しません。 貪欲ループは引き続きこのプレフィックス上でのみ実行され、入力の大きさに依存しない線形時間動作が保証されます。 

微妙なケースとしては、たとえば、容量が大きく偏っている場合があります。`a = 1`そして`b = 1000000000`。 このアルゴリズムでは、最初に総容量からプレフィックスを決定し、次に小さな値を最初に大きなビンに割り当て、特別な場合のロジックを使用せずに実現可能性を維持します。
