 ## 解決策
 ## 問題の理解

 円形に配置されたコインが与えられます。 各コインは上を向いているか下を向いています。 2 人のプレイヤーが交互にターンを行い、各ターンでプレイヤーは現在表になっているコインを 1 枚選び、それを取り除き、隣の 2 枚を裏返す必要があります。 コインが取り除かれると円が縮小し、隣接構造が動的に変化します。 

プレイヤーが移動し、上向きのコインがなくなった場合、プレイヤーは即座に負けます。 動くたびにコインの数が減るため、ゲームは必ず終了します。 

タスクは、初期設定ごとに、両側からの完璧なプレイを前提として最初のプレイヤーが勝利を強制できるかどうかを決定することです。 

制約は小さく、テスト ケースごとに最大 100 コインです。 これにより、大量の計算や大規模な状態の検索を必要とするのではなく、ゲームの構造的特性を考慮した戦略を検討できるようになります。 完全なゲーム ツリー シミュレーションは理論的には可能ですが、各移動が現在有効なすべての「上」位置に分岐し、状態空間が指数関数的に増大するため、すぐに実行不可能になります。 

特にコインが非常に少ない場合、微妙なエッジケースが発生します。$n \le 3$。 このような場合、コインを削除すると同じコインを 2 回投げたり、すべての隣接効果を排除したりする可能性があるため、投げるルールは劣化します。 安定した 3 近傍構造を仮定した単純なシミュレーションでは、これらの小さなケースでは不正確な遷移が生成されます。 

## アプローチ

 ブルート フォース ソリューションでは、到達可能なすべての構成にわたる再帰的なミニマックス プロセスとしてゲーム全体をシミュレートします。 各状態は、現在の循環バイナリ文字列と移動するプレーヤーによって定義されます。 各状態から、可能な限りのアップ コインの削除を試み、その結果の構成の結果を再帰的に計算します。 このアプローチは、ゲーム定義を直接エンコードするため正しいですが、状態の数が指数関数的に増加するため、非常に遅すぎます。$n$、そしてさらには$n = 100$、到達可能な構成の数は天文学的に膨大です。 

重要な観察は、ゲームは単純な構造的パリティ効果を超えて、アップコインの正確な位置に敏感ではないということです。 各移動は 1 つのアップ コインを取り除き、2 つの隣接コインを裏返します。これにより、ローカル パリティが効果的に切り替わり、円の周囲に「アクティビティ」が転送されます。 このタイプの操作は、アクティブな要素の正確な配置ではなく、アクティブな要素の数の同等性のみが重要となる公平なゲームの特徴です。 

決定的に単純化された点は、勝者はアップコインの数が奇数か偶数かのみに依存し、最初に手が不可能な場合については若干の修正が加えられることです。 開始時にアップコインがない場合、最初のプレイヤーは即時に負けます。 それ以外の場合、アップコインのカウントが奇数である場合に限り、最初のプレーヤーはいつでも勝利を強制することができます。 

これが機能するのは、すべての移動で 1 つのアップ コインが削除され、フリップ後に残りのアクティブ セットのパリティ構造が保持されるためです。 フリップは、対戦相手が制御できる方法でアップ コインの総数のパリティを変更しないため、ゲームはパリティ ゲームになります。

 | ブルートフォース | 指数 | 指数 | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. テスト ケースの数を読み取り、各構成を個別に処理します。 テスト ケース間に相互作用がないため、各構成は独立しています。 
2. 現在表を向いているコインの数を数えます。 これは、結果を決定するために重要な唯一の状態変数です。 
3. アップコインがゼロの場合、最初のプレーヤーは移動できず、すぐに負けます。 これは強制的に負けるポジションです。 
4. それ以外の場合は、アップコインの数のパリティをチェックします。 奇数の場合は、最初のプレイヤーが勝ちます。 偶数の場合は、2 番目のプレーヤーが勝ちます。 
5. 各テストケースの結果を出力します。 

これが機能する理由は、すべての動きで正確に 1 枚のアップ コインが削除され、プレイヤーがこの不変条件を破る方法で「有効なアクティブ セット」のパリティを変更できないためです。 ゲームは効果的なアクティブユニットを交互に除去することになり、最初のプレイヤーがこの交互のプロセスが有利に終わる位置から開始したときに正確に勝利します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n = int(input().strip())
    s = input().strip()

    ups = s.count('U')

    if ups == 0:
        print("NO")
    elif ups % 2 == 1:
        print("YES")
    else:
        print("NO")
```実装は、導出された不変条件に直接続きます。 アップコインの数を計算し、パリティチェックを適用するだけです。 文字列はテスト ケースごとに 1 回読み取られ、カウントはその長さに比例します。 

よくある実装の落とし穴は、文字列を読み取るときに改行文字を削除するのを忘れたり、誤って複数の行を間違って読み取ったりすることです。 もう 1 つの微妙な問題は、円構造には明示的なモデリングが必要であると想定していることですが、不変条件が特定されれば、その必要はありません。 

## 実用的な例

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | テスト ケースごとの文字数のカウント |
 | スペース | お(1) | 入力文字列とカウンターのみを保存する |

 この制約により、最大 100 個の長さの文字列を含む最大 100 個のテスト ケースが許可されます。テスト ケースごとのリニア スキャンは、制限時間内で簡単に十分に高速になります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        s = input().strip()

        ups = s.count('U')
        if ups == 0:
            out.append("NO")
        elif ups % 2 == 1:
            out.append("YES")
        else:
            out.append("NO")

    return "\n".join(out)

# provided samples
assert run("""3
5
UUDUD
5
UDDUD
2
UU""") == """YES
NO
NO"""

# custom cases
assert run("""4
1
D
1
U
3
UUU
4
UUDD""") == """NO
YES
YES
NO"""
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1D | いいえ | 移動はできません |
 | 1U | はい | 単一の勝ち手 |
 | ううう | はい | 奇数パリティのマルチケース |
 | ＵＵＤＤ | いいえ | 偶数パリティ混合ケース |

 ## 特殊なケース

 単一のコインの場合、動作は完全にそれが上昇しているか下落しているかによって異なります。 ダウンしている場合、最初のプレイヤーは何も動けず、すぐに負けます。 それがアップの場合、彼らはそれを取り除き、ゲームは即座に彼らに有利に終了します。 パリティ ルールは両方のケースに正しく一致します。 

すべてのコインが上にある場合、すべての移動で隣のコインを裏返しながらアクティブなコインが 1 つ取り除かれますが、パリティが決定要因のままです。 カウントが奇数の場合、最初のプレーヤーが常に最終手のアドバンテージを保持します。 

UUDD のような交互構成の場合、有効な動きはありますが、フリップの構造によってパリティの結果は変わらないため、最適なプレイで 2 番目のプレーヤーが勝ちます。
