 ## 解決策
 ## 問題の理解

 私たちは、人が時間の経過とともに確率的な「花火バッチ」を繰り返し生成する状況をモデル化しています。 各制作の試行には一定の時間がかかり、作成された花火はそれぞれ独立して「完璧」である可能性が低くなります。 ある程度の数の花火を作成した後、人は蓄積されたすべての花火を一度に「爆発させる」ことを選択できますが、これには追加の固定時間がかかり、そのバッチ内に少なくとも 1 つの完璧な花火が存在する場合に成功するか、最初からプロセスを続行します。 

決定は、単純に花火を何発打ち上げるかではなく、いつ花火を停止して爆発させるかということによって決まります。これは、爆発によって試行サイクルがリセットされますが、時間がかかるためです。 目標は、最初に成功したバッチが発生するまでの予想される合計時間を最小限に抑えることです。 

入力では、テスト ケースごとに 3 つのパラメーターが記述されます。 1 つ目は 1 つの花火を打ち上げる時間、2 つ目は現在保管されているすべての花火を爆発させるのにかかる時間コスト、3 つ目は各花火の成功確率を決定する確率スケールです。 出力は、最適な戦略のもとで最初に爆発が成功するまでの最小予想時間です。 

構造上の主な問題点は、このプロセスがバッチごとに確率的に成功する反復決定問題であり、各バッチの成功確率が爆発前に蓄積された花火の数に指数関数的に依存することです。 

複雑さの観点から見ると、制約により最大 10^4 のテスト ケースと最大 10^9 の大きな値が許可されます。 これにより、単純な方法でプロセスをシミュレートしたり、考えられる大きなバッチ サイズを反復したりする戦略は即座に除外されます。 どのようなソリューションでも、各テスト ケースを定数時間の式、または凸関数または単峰関数に対する非常に小さな限定された最適化のいずれかに削減する必要があります。 

素朴な貪欲な推論では、微妙な失敗モードが現れます。 バッチ サイズを増やすと成功確率が高まるため常に効果があると考える人もいるかもしれませんが、生産時間の直線的なコストも増加します。 もう 1 つの間違ったアプローチは、試行の最大数を固定して期待値をシミュレートすることですが、これは失敗確率の指数関数的減衰と大きなパラメーター範囲により中断されます。 

具体的なエッジ ケースは、成功確率が非常に小さい場合 (たとえば、p = 1)、各花火がほとんど成功しない場合です。 その場合、頻繁にリセットしても、サイクルごとに 1 つの花火だけを生成するのが最適である可能性があります。 一方、p = 10000 の場合、1 つの花火ですでに成功が保証されているため、バッチ処理は不要です。 正しい解は、数値が不安定になることなく、両方の極端な値をスムーズに処理する必要があります。 

## アプローチ

 ブルートフォース戦略は、考えられるすべてのバッチ サイズ k を考慮することです。 各 k について、1 サイクルの予想時間を計算します。k 倍の生産時間と爆発時間に、成功までの予想サイクル数を掛けたものです。 サイズ k のバッチの成功確率は、1 から k 個の花火がすべて失敗する確率を引いたもので、正規化された確率形式では 1 から (1 − p)^k を引いた値となります。 これにより、予想されるサイクル数は成功確率の逆数に等しくなります。 したがって、各 k の予想合計時間を計算し、最小値を取得できます。 

この強引なアイデアは正しいですが、k は任意に大きくできるため、すぐに遅すぎます。 k の上限を大きな範囲に設定した場合でも、関数はべき乗に依存するため、慎重に評価する必要があります。 さらに重要なことは、最適な k は任意の意味で大きくはなく、成功確率の限界利益がコストの限界増加と釣り合う非常に狭い範囲内にあることです。

重要な洞察は、k に対する期待コスト関数が単峰性であることを認識することです。 k が増加すると、成功確率は 1 に向かって指数関数的に増加しますが、コストは直線的に増加します。 これにより、単一の最小点が作成されます。 したがって、三分探索または直接単調勾配推論を使用して最適な k を検索できます。 

これにより、k を増やすことによる限界利益が余分な生成時間を上回らなくなる場合に最適化が行われるため、O(log range) または O(1) 個の候補チェックで関数を評価するという問題が軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | k に対するブルート フォース | O(テストごとの最大K) | お(1) | 遅すぎる |
 | k | 上の三項探索 テストあたり O(log maxK) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 確率 p を花火ごとの成功確率に変換し、各花火が確率 p / 10000 で独立して成功するように分数としてスケーリングします。これが必要なのは、バッチの成功が独立した試行の繰り返しに依存するためです。 
2. 各爆発の前に k 個の花火を発射した場合の予想時間を計算する関数cost(k)を定義します。 この関数は、まずバッチの失敗確率を (1 − p)^k として計算し、次にそれをバッチの成功確率に変換します。 
3. 予想されるサイクル長を、k 倍の製造時間と爆発時間を加算して計算します。 これは、バッチが成功したかどうかを確認するまでに費やされる確定的な時間を表します。 
4. バッチの成功確率を、成功までの予想サイクル数 (成功確率の逆数) に変換します。 これにサイクル コストを掛けて、予想される合計時間を求めます。 
5. 予想される時間を最小限に抑えるために、考えられる k 値を検索します。 関数は単峰性であるため、k の整数領域に対して三分探索を適用します。 各ステップで、cost(mid1) とcost(mid2) を比較して、どちらの半分に最適値が含まれるかを決定します。 
6. 範囲を十分に狭めた後、残りのすべての候補 k 値を直接評価し、最小値を取得します。 

### なぜ効果があるのか

 正確さは、線形増加項と凸状減少指数関数項の合計である期待時間関数の構造に依存します。 大きい k では線形項が支配的ですが、小さい k では指数項が支配的です。 これにより、単一のグローバル最小値が保証されます。 三分探索では、どの時点でも関数が複数の互いに素な最小値を持つことができず、一方の辺を破棄しても最適解を排除できないため、正確性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(n, m, p):
    # convert probability
    prob = p / 10000.0

    # if probability is 1, one firework always succeeds
    if prob == 1.0:
        return n + m

    def expected(k):
        # probability all k fail
        fail = (1.0 - prob) ** k
        success = 1.0 - fail
        cycle = k * n + m
        return cycle / success

    lo, hi = 1, 200000  # safe upper bound
    for _ in range(60):
        m1 = lo + (hi - lo) // 3
        m2 = hi - (hi - lo) // 3
        if expected(m1) < expected(m2):
            hi = m2
        else:
            lo = m1

    ans = float('inf')
    for k in range(max(1, lo - 5), hi + 6):
        ans = min(ans, expected(k))

    return ans

def main():
    t = int(input())
    for _ in range(t):
        n, m, p = map(int, input().split())
        print(f"{solve_case(n, m, p):.10f}")

if __name__ == "__main__":
    main()
```この解決策は、決定を単一の整数パラメーター k (サイクルごとの花火の数) に分離します。 機能`expected(k)`コストと成功確率の両方を直接エンコードし、検索フェーズはその関数の単峰性の性質に依存します。 浮動小数点三項探索では丸めの影響により正確な整数の最小値が見つからない可能性があるため、最後のローカル スキャンが必要です。 

1 に近い値の累乗を繰り返すとアンダーフローする可能性があるため、確率の計算には注意が必要です。 ただし、指定された制約内では、慎重に実装すれば倍精度で十分です。 

## 実用的な例

 ### 例 1

 入力:

 n = 1、m = 1、p = 5000

 小さい k 値を比較します。 

| k | サイクルコスト k*n + m | 成功確率 | 期待値 |
 | --- | --- | --- | --- |
 | 1 | 2 | 0.5 | 4 |
 | 2 | 3 | 0.75 | 4 |
 | 3 | 4 | 0.875 | 4.57 |

 最小値は小さい k で早期に発生し、最適な期待時間は 4 です。 

これは、成功確率がすでにかなり大きい場合には、中程度のバッチ サイズであってもすぐに有益でなくなることを示しています。 

### 例 2

 入力:

 n = 1、m = 2、p = 10000

 ここで確率 = 1 であるため、1 つの花火は常に成功します。 

| k | サイクルコスト | 成功確率 | 予想される |
 | --- | --- | --- | --- |
 | 1 | 3 | 1 | 3 |

 k を大きくしても時間が増加するだけなので、k = 1 が最適です。 

これは、確率が最大でバッチ処理が役に立たないという退化したケースを裏付けています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、p が 10000 に等しい場合です。これは、すべての花火が完璧であることを意味します。 この状況では、最適な戦略は、花火を 1 発生成し、すぐに爆発させることに退化します。 さらにバッチ処理を試みても、コストが直線的に増加するだけで、確率は向上しません。アルゴリズムは、n + m を早期に返すことでこれを正しく処理します。 

もう 1 つの特殊なケースは、p が非常に小さい場合です。 固定 k の成功確率は非常に小さくなるため、予想されるサイクル数は非常に大きくなります。 コスト関数が指数関数的な減衰によって支配され、最適値が小さな k 値に近づくため、三分探索は引き続き機能します。 

最後の微妙なケースは、k が大きい場合の数値不安定性です。 この領域では、(1 − p)^k がゼロにアンダーフローする可能性があり、浮動小数点演算の成功確率が 1 に等しくなります。 このアルゴリズムは、k を妥当な範囲に制限し、最適値に近い候補を直接検証することでこれを回避し、浮動小数点の制限にもかかわらず正確さを保証します。
