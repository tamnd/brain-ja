 ## 解決策
 ## 問題の理解

 一連の船があり、各船は固定最大数の木箱スロットを持つコンテナのように動作します。 最初はすべての船が空です。 時間の経過とともに、木箱は選択した船のインデックスに注がれます。 その船がすでに満杯の場合、オーバーフローは次の船に続き、すべての木箱が配置されるか、最後の船を通り過ぎてしまうまで続きます。その場合、残りの木箱は廃棄されます。 

2 番目のタイプのクエリは、以前の積み込みがすべて処理された後、その時点で特定の船に保管されている現在の木枠の数を尋ねます。 

したがって、システムは容量を備えた動的な 1 次元のパイプラインであり、すべての更新は「スペースが見つかるまで前進する」操作であり、すべてのクエリはポイント検査です。 

この制約により、私たちは素朴なシミュレーションから遠ざけられます。 最大 100,000 隻の船舶と 100,000 回のオペレーションでは、積荷ごとに船ごとに前進する単純なアプローチでは、二次的な動作に低下する可能性があります。 最悪の場合、すべての負荷はシップ 1 で開始され、ほぼシップ N に伝播し、約 10^10 のプリミティブ操作が生成されます。これは 2 秒間の制限をはるかに超えています。 

部分的な塗りつぶしでは、さらに微妙な問題が発生します。 単一の船がさまざまな積み込み作業で何度も訪問される可能性があり、そのたびに最終的に満杯になるまで少数の木箱しか受け取りません。 クレートを 1 つずつ処理するソリューションや、集約せずに容量を段階的に更新するソリューションは、論理的に正しい場合でも、静かにタイムアウトします。 

明示的に検討する価値のあるエッジ ケースには、最初に完全に飽和した船舶のチェーンが含まれます。この場合、負荷はすぐに前方にスキップされます。次に例を示します。 

入力:```
5 1
0 0 10 10 10
1 1 7
```ここでは、船 1 と 2 はすでに満員であるか事実上使用できないため、船 3 からロードを開始する必要があります。効率的にスキップしない単純な実装では、船 1 と 2 を繰り返しチェックすることで時間が無駄になります。 

もう 1 つのエッジ ケースは、小さな負荷が繰り返される場合です。```
3 3
5 5 5
1 1 1
1 1 1
1 1 1
```それぞれの操作は小さいとはいえ、クレートごとに再分散するアプローチは、同じインデックスに対して作業を繰り返すため、非常に遅くなります。 

## アプローチ

 ブルートフォースシミュレーションは簡単です。 各積み込み操作では、指定されたシップ インデックスから開始して先に進みます。 各船では、入荷量から差し引いて残りの容量までできるだけ多くの木箱を受け取り、必要に応じて次の船に進みます。 これは、オーバーフロー伝播のルールに正確に従っているため、正しいです。 

問題は、このスキャンでは船舶の長い接頭辞が何度も再訪問される可能性があることです。 すべての操作が先頭付近で開始される場合、各更新に O(N) かかる可能性があり、最悪の場合は O(NM) の動作が発生する可能性があります。 

重要な構造的観察は、船が最大積載量に達した場合にのみ「無関係」になるということです。 その瞬間以降は、スキップ ポイントとして以外に、今後の割り当てに再び寄与することはありません。 これは、有効なポジションのアクティブなセットが時間の経過とともに縮小するだけであることを意味します。 満員の船を効率的に飛び越えることができれば、各船を一度除去することができます。これは、素のセットユニオンスタイルの「次の生存位置」構造、または高速な「最初の非満員検索」クエリをサポートするセグメントツリーを示唆しています。 

船当たりの残存能力を維持します。 積み荷ごとに、すべてのインデックスをスキャンするのではなく、開始位置以降でまだ容量が残っている次の船に繰り返しジャンプします。 次に、可能な限りそこに押し込みます。 いっぱいになると非アクティブとしてマークされるため、今後のジャンプでは完全にスキップされます。 

これにより、船全体で繰り返しスキャンする必要がなくなり、問題が一連のジャンプと更新に変わります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(NM) | O(N) | 遅すぎる |
 | セグメント ツリー/DSU ジャンプ | O((N + M) log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 配列を保存します`rem[i] = G[i]`、各船の残りの容量を表します。 また、まだ正の残存容量がある位置またはそれを超えた位置で最初のインデックスを迅速に見つけられるデータ構造も維持しています。 これには、範囲全体の最大残り容量を格納するセグメント ツリーで十分です。 

船から始まる各積荷作業ごとに`K`と`C`木箱を使い果たすか、使用可能な船がなくなるまで、次に使用可能な船を繰り返し見つけ、そこに木箱を配布します。 

1.初期化`i`以降の最初のインデックスとして`K`どこ`rem[i] > 0`。 これは、条件に対するセグメント ツリーの「最初に true」クエリを使用して検出されます。`rem[i] > 0`。 多くの船舶はすでに満員である可能性があり、完全にスキップする必要があるため、このステップが必要です。 
2. その間`i`存在し、`C > 0`、船内に置ける木箱の数を計算します。`i`として`x = min(rem[i], C)`。 次に減算します`x`両方から`rem[i]`そして`C`。 
3. もし`rem[i]`この操作後にゼロになると、この位置が非アクティブとしてマークされるようにセグメント ツリーを更新します。 これにより、今後の検索ではこの船を完全にスキップすることが保証されます。 
4. もし`rem[i]`まだポジティブですが、`C`がゼロの場合、操作は直ちに終了します。 これ以上クレートが配布されないため、手動で進めません。 
5. それ以外の場合、`C`がまだプラスであり、現在の船が満員である場合、次の使用可能な船を次の時刻またはその後に再度クエリします。`i + 1`。 

重要な構造上の考え方は、船が完全に飽和した場合にのみ移動が発生するということです。 部分的な塗りつぶしは動きを引き起こしません。 残りの容量が減るだけです。 

### なぜ効果があるのか

 どの時点においても、すべての船には明確に定義された残存容量があり、木枠は、まだスペースがある船をスキップすることなく、常に厳密に左から右に流れます。 セグメント ツリーは常に、必要なサフィックスで利用可能な容量を持つ最も早いシップを返すため、すべての配置ステップでは元の貪欲ルールが尊重されます。 

船舶は収容力がゼロになった場合にのみ考慮から削除され、一度削除されると再びアクティブになることはないため、各削除は永続的です。 これにより、検索構造が単調に縮小するだけとなり、不必要なスキャンが繰り返されることがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.t = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def build(self, v, l, r, arr):
        if l == r:
            self.t[v] = arr[l]
            return
        m = (l + r) // 2
        self.build(v * 2, l, m, arr)
        self.build(v * 2 + 1, m + 1, r, arr)
        self.t[v] = max(self.t[v * 2], self.t[v * 2 + 1])

    def update(self, v, l, r, idx, val):
        if l == r:
            self.t[v] = val
            return
        m = (l + r) // 2
        if idx <= m:
            self.update(v * 2, l, m, idx, val)
        else:
            self.update(v * 2 + 1, m + 1, r, idx, val)
        self.t[v] = max(self.t[v * 2], self.t[v * 2 + 1])

    def find_first(self, v, l, r, ql, qr):
        if r < ql or l > qr or self.t[v] == 0:
            return -1
        if l == r:
            return l
        m = (l + r) // 2
        res = self.find_first(v * 2, l, m, ql, qr)
        if res != -1:
            return res
        return self.find_first(v * 2 + 1, m + 1, r, ql, qr)

def main():
    n, m = map(int, input().split())
    g = list(map(int, input().split()))
    rem = g[:]
    st = SegTree(rem)

    out = []

    for _ in range(m):
        tmp = list(map(int, input().split()))
        if tmp[0] == 1:
            _, k, c = tmp
            k -= 1
            i = st.find_first(1, 0, n - 1, k, n - 1)
            while i != -1 and c > 0:
                take = min(rem[i], c)
                rem[i] -= take
                c -= take
                st.update(1, 0, n - 1, i, rem[i])
                if rem[i] > 0:
                    break
                i = st.find_first(1, 0, n - 1, i + 1, n - 1)
        else:
            _, k = tmp
            out.append(str(rem[k - 1]))

    print("\n".join(out))

if __name__ == "__main__":
    main()
```セグメント ツリーは 2 つの役割で使用されます。 1 つ目は、範囲内の最大残存容量を追跡して、使用可能な船が存在するかどうかを迅速に判断できるようにすることです。 2 つ目は、まだ容量のあるサフィックス内の最初のインデックスを配置することです。これは、左から右の順序を維持するために不可欠です。 

更新操作は、船舶の残りの容量を変更した後に常に適用されます。 船舶がゼロに達すると、セグメント ツリーの値がゼロになるため、以降の検索では事実上見えなくなります。 

ロード クエリ内のループは、各反復がシップを完全に消費するか、木枠が残っていないときに早期に終了するように慎重に構造化されています。 重要なのは、決して直線的にスキャンしないことです。 すべてのジャンプは対数的です。

 ## 特殊なケース

 主なエッジケースは、開始船がすでに満員である場合です。 その状況では、最初のセグメント ツリー クエリはすぐに次の利用可能なシップにジャンプし、フル スロットに誤って書き込もうとすることはありません。 この構造により、格納された値がゼロであるため、完全な船舶が有効な候補として返されないことが保証されます。 

もう 1 つのエッジ ケースは、最後の船を超えた完全なオーバーフローです。 セグメント ツリー検索で有効なインデックスが返されない場合、アルゴリズムは直ちに停止し、残りのクレートを破棄します。 これは、余った木箱は海に落ちるというルールと一致します。 

最後の微妙なケースは、複数の作戦にわたって同じ船の部分的な充填が繰り返されることです。 セグメント ツリーには常に現在の残りの容量が反映されるため、船舶が再訪問されるたびに、現在利用可能なスペースのみが使用されます。 ゼロに達すると、考慮対象から永久に削除され、再び誤って選択されることがなくなります。
