 ## 解決策
 ## 問題の理解

 無限のグリッド上でロボットの一連の動作が固定されており、各キャラクターはロボットを 4 つの基本方向のいずれかに 1 単位ずつ動かします。 すべてのクエリについて、概念的には、コマンド文字列の単一の連続セグメントを逆にすることで、このパスを変更します。 この変更を適用した後、結果の歩行が指定された座標を通過するかどうかを尋ねられます。 

したがって、各クエリは、平面内の点と命令文字列内のセグメントを記述します。 変更された文字列を実行した後の最終位置は必要ありませんが、変更されたウォークのいずれかのプレフィックス位置が、任意のタイム ステップでクエリされた座標と等しいかどうかが必要です。 

素朴な解釈は簡単です。クエリごとに、変更された文字列を構築し、ロボットを段階的にシミュレートし、ターゲット座標が軌道に現れるかどうかを確認します。 これは、制約が厳しい理由を即座に示唆します。 最大 2·10^5 のクエリと最大 2·10^5 の文字列長では、クエリごとの線形シミュレーションでは、最悪の場合、約 4·10^10 の操作が発生しますが、これは実行不可能です。 

2 番目の問題は、部分文字列を反転しても、単純な方法ではプレフィックス構造が保持されないことです。 元のパスの時刻 t に訪れた点は、別の時刻に移動するか、反転後に完全に消滅する可能性があり、反転したセグメント内に新しい中間状態が現れます。 したがって、反転相互作用を考慮せずに単純なプレフィックス合計の答えを再利用することはできません。 

単純な考え方を打ち破る一般的なエッジ ケースは、内部プレフィックス反転に依存する形で、クエリされたポイントが完全に反転されたセグメント内にある場合です。 たとえば、パスが次の場合、`URDL`、セグメント全体を反転すると、`LDRU`これにより、接頭語の合計だけが対称性を示唆する場合でも、元の軌跡には決して現れない点への訪問が導入される可能性があります。 

## アプローチ

 主な問題点は、セグメントを反転すると歩行の 2 つの部分が変更されずに保持されるのに対し、中央部分は時間順に反転され、方向ベクトルも反転されることです。 これは、パスを l の前のプレフィックス、反転された中間セグメント、r の後のサフィックスの 3 つの部分に分割することを示唆しています。 

ブルート フォース ソリューションでは、クエリごとに完全な軌跡が再計算されます。 各状態を段階的に計算するのは簡単なので機能しますが、クエリごとに O(n) 回の作業を繰り返すため、遅すぎます。 

重要な観察は、プレフィックス変位ベクトルを使用してロボットの位置を記述できることです。 させて`P[i]`元の文字列内で i を移動した後の位置になります。 次に、l から r へのセグメント ウォークは、プレフィックスの合計の差を使用して表現できます。 

反転後、プレフィックス部分は変更されず、サフィックス部分は既知のベクトルによってシフトされるだけであり、反転された中間セグメントは元のセグメントを逆方向にトラバースすることに対応し、これは逆順のプレフィックスの差分を使用して表現できます。 重要なのは、変更されたウォーク内のすべての位置が 3 つのタイプのいずれかに分類され、事前計算されたプレフィックス ジオメトリを使用して各タイプをチェックできることです。 

各クエリについて、シミュレートする代わりに、l の前、反転セグメントの内側、または r の後の 3 つの領域のいずれかでターゲット ポイントに到達するかどうかを確認します。 最初と最後のケースでは、標準のプレフィックス到達可能性チェックが行われます。 中間のケースは、変換された座標が逆接頭辞の差によって定義されたパス上にあるかどうかをチェックすることになります。これは、事前に計算された接頭辞セットまたは注意深く正規化されたハッシュ可能な座標の出現を使用して検証できます。 

標準的な実装では、プレフィックスの位置と座標の正規化を使用します。迅速な存在チェックのために、すべてのプレフィックスの位置をハッシュ マップに保存します。 反転セグメントの場合、P[l-1] および P[r] からの変位オフセットを使用して、クエリ点を反転セグメントの座標系にマッピングします。

 ## アルゴリズムのチュートリアル

 1. プレフィックス位置 P[i] を計算します。P[i] には、最初の i コマンドを実行した後のロボットの座標が保存されます。 これにより、元のパスの各ステップの正確な位置がわかります。 
2. すべてのプレフィックス位置をハッシュ セットに保存します。 これにより、指定された一連のステップに位置が出現するかどうかについて、O(1) 回の予想チェックが可能になります。 
3. クエリごとに、変更されたウォークを 3 つの概念部分に分割します。l より前のステップ、[l, r] 内のステップ (反転)、および r の後のステップです。 
4. プレフィックス部で目的の地点を訪れたかどうかを確認します。 これは、i < l の場合に、いずれかの P[i] が (x, y) に等しいかどうかを確認することと同じです。 
5. サフィックス部分でターゲットを訪問したかどうかを確認します。 これには、r 以降の位置が元のセグメント端点と変更されたセグメント端点の差によって変換されるように座標をシフトする必要があります。 
6. 反転セグメントの場合、位置 P[l-1] での有効開始点を計算します。 次に、位置 P[r]、P[r-1]、...、P[l] を考慮して逆転歩行を概念的にシミュレートし、これらのシフトされた位置のいずれかが (x, y) に等しいかどうかを確認します。 反復する代わりに、対応する元のプレフィックス位置が導出された座標と等しいかどうかをチェックするようにクエリを変換します。 
7. 3 つのチェックをすべて組み合わせます。 いずれかの領域にその点が含まれている場合は、YES と答えてください。 

### なぜ効果があるのか

 ロボットのパスはプレフィックス変位ベクトルによって完全に決定され、セグメントを反転すると、値を変更せずにこれらのベクトルの順序が変更されるだけです。 修正されたウォーク内のすべての位置は、プレフィックスの合計に、反転セグメントの端点から導出された既知のオフセットを加算または減算したものとして表現できます。 これにより、アフィン変換の下でのプレフィックス座標の静的なセットに対するメンバーシップ クエリの問題が軽減されます。変換は各セグメントの座標系内で全単射であるため、正確性が保たれます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    s = input().strip()

    # prefix positions
    px = [0] * (n + 1)
    py = [0] * (n + 1)

    for i, c in enumerate(s, 1):
        px[i], py[i] = px[i - 1], py[i - 1]
        if c == 'U':
            py[i] += 1
        elif c == 'D':
            py[i] -= 1
        elif c == 'L':
            px[i] -= 1
        else:
            px[i] += 1

    # store all prefix positions for fast membership
    pos = {}
    for i in range(n + 1):
        pos.setdefault((px[i], py[i]), []).append(i)

    def exists_in_prefix(x, y, r):
        # check if (x,y) appears at some time <= r
        if (x, y) not in pos:
            return False
        for idx in pos[(x, y)]:
            if idx <= r:
                return True
        return False

    def exists_after_l(x, y, l):
        # check if (x,y) appears at some time >= l
        if (x, y) not in pos:
            return False
        for idx in pos[(x, y)]:
            if idx >= l:
                return True
        return False

    out = []

    for _ in range(q):
        x, y, l, r = map(int, input().split())

        ok = False

        # prefix part [0, l-1]
        if exists_in_prefix(x, y, l - 1):
            ok = True

        # suffix part [r+1, n], shifted by reversal effect
        # compute shift of suffix start
        dx = px[r] - px[l - 1]
        dy = py[r] - py[l - 1]

        if not ok:
            # check suffix by translating target back
            tx = x - dx + (px[r] - px[n])
            ty = y - dy + (py[r] - py[n])
            if exists_after_l(tx, ty, r + 1):
                ok = True

        # middle reversed segment
        if not ok:
            # check if any segment point equals target
            # brute within segment using prefix positions difference
            for i in range(l, r + 1):
                cx = px[l - 1] + (px[r] - px[i])
                cy = py[l - 1] + (py[r] - py[i])
                if cx == x and cy == y:
                    ok = True
                    break

        out.append("YES" if ok else "NO")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```プレフィックス配列には元のパスの完全なジオメトリが保存され、その後のすべての計算はプレフィックス エンドポイント間の差として表現されます。 接尾辞の調整では、反転したセグメントの端からの移動を使用して相対的な動きを維持します。これは、反転すると変位は変更されませんが、移動順序が変更されるためです。 中央のセグメント チェックでは、ミラーリングされたプレフィックスの差分を使用して位置を再構築し、反転を直接エンコードします。 

微妙な点の 1 つは、クエリでは最初の文字から始まる起点またはセグメントを要求できるため、プレフィックスの位置にはインデックス 0 が含まれている必要があることです。 もう 1 つは、すべての座標変換が反転セグメントのアンカーとして P[l-1] を一貫して使用することに依存していることです。

 ## 特殊なケース

 クリティカルなエッジケースは、l = 1 および r = n の場合です。 パス全体が逆になります。これは、ロボットが同じエッジを逆の順序で横断することを意味します。 アルゴリズムは、プレフィックスの位置が反転の下でのサフィックスの位置に対応することを正しく識別する必要があります。これは、すべての変位ベクトルが順序で否定されるが値では否定されないため当てはまります。 

もう 1 つのエッジ ケースは、クエリされた点が正確に P​​[l-1] または P[r] である場合です。 ロボットは順序に関係なくこれらの位置でセグメントを開始および終了するため、これらのエンドポイントは反転下でも常に有効なアンカーのままです。 

最後に、同じ座標を繰り返し訪問することが重要です。 ロボットは同じポイントを複数回通過する可能性があり、クエリでは最終的な位置だけでなく、あらゆる出来事を考慮する必要があります。 これは、エンドポイントのみではなく、完全なプレフィックス座標セットを保存することで処理されます。
