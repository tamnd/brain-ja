 ## 解決策
 ## 問題の理解

 ランタンの列を表すバイナリ文字列が与えられ、各位置が点灯または消灯します。 1 回の操作で、任意の連続セグメントを選択し、その中のすべてのビットを反転して、0 を 1 に、1 を 0 に変えることができます。 目標は、このようなセグメントの反転をできるだけ少なくして、文字列全体が均一 (すべて 0 またはすべて 1) になる構成に到達することです。 

入力サイズは最大 100,000 文字まで可能です。 これにより、考えられるすべてのセグメントを試したり、フリップのシーケンスを明示的にシミュレートしたりするアプローチは即座に除外されます。 部分文字列の数だけでも二次関数であるため、線形または線形に近い時間よりも悪い時間は困難になります。 

素朴なアイデアは、考えられるすべての最終ターゲット状態 (すべて 0 またはすべて 1) を選択してから、文字列が一致するまでセグメントの反転を貪欲にまたは素朴にシミュレートすることです。 もう 1 つのよくある誤った試みは、マージの機会を考慮せずに、不一致文字の最大ブロックを個別に反転することです。これにより、操作が過剰にカウントされる可能性があります。 

たとえば、次のように考えてみましょう`010`。 すべてゼロを目指す場合、中央のセグメントを反転すると次のようになります。`000`一度の動きで。 一致しない各文字を個別に反転する貪欲な場合、誤って 2 つの操作が提案されてしまいます。 逆に、`01010`1 つのセグメントを反転すると、将来の複数の境界が変更されるため、不注意なローカル決定は簡単に過大評価または過小評価される可能性があります。 

微妙な問題は、フリップはローカルで孤立して機能せず、隣接構造を変更するため、実際のコストは個々のキャラクター自体ではなく、連続するキャラクター間の遷移に依存することです。 

## アプローチ

 ブルートフォースアプローチでは、考えられるセグメント反転のあらゆるシーケンスが考慮されます。 ターゲットに向かって進むのに役立つセグメントを反転することだけに限定したとしても、反転するたびに文字列が変化し、新しいセグメントの可能性が作成されるため、セグメントを選択する方法の数は指数関数的に増加します。 これは、非常に小さい n を超えるとすぐに実行不可能になります。 

より構造化されたブルート フォースでは、ターゲット文字列をすべて 0 またはすべて 1 に修正して、貪欲な修正をシミュレートします。 左から右にスイープすると、ターゲットとの不一致が見つかるたびに、不一致が解決されるまでその位置から前方に反転します。 これは固定ターゲットの場合は正しいですが、強制的に反転させる回数について推論する必要があります。 

重要な観察は、ターゲットを決定すると、最適な戦略は文字列の遷移によって完全に決定されるということです。 すべてのゼロをターゲットにするとします。 変遷を見るたびに`0 → 1`、これは、これらのセグメントを修正するために最終的に反転する必要があるセグメントに入っていることを意味します。 同様に、すべてのトランジション`1 → 0`はそのようなセグメントの終わりを示します。 1 の連続ブロックはそれぞれ 1 回だけ反転する必要があり、各反転はブロック全体を最適にカバーできます。 

したがって、文字列をすべて 0 に変換するのに必要なフリップの数は、連続する 1 のブロックの数に等しくなります。 対称的に、すべて 1 に変換するのに必要なフリップの数は、連続する 0 のブロックの数に等しくなります。 答えは単にこれら 2 つの値の最小値です。 

問題は、セグメントを動的に選択することから、バイナリ文字列内の実行をカウントすることにまで及びます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 文字列を 1 回スキャンし、連続するセグメントの数を数えます。`'1'`存在する。 新しいセグメントは、`'1'`が表示されますが、前の文字は表示されません`'1'`。 これは、すべてをゼロに変えることを目的とした場合に、孤立した 1 のグループをいくつ処理する必要があるかを数えます。 
2. 文字列を 1 回スキャンし、連続するセグメントの数を数えます。`'0'`同じロジックを使用して存在します。 これは、すべてを 1 に変換する場合に必要なフリップの数を表します。 
3. 2 つのカウントを比較し、小さい方の値を出力します。 これは、可能な 2 つの最終均一状態のうち、安価な方を選択することに対応します。 

これが機能する理由: 最適解におけるすべてのフリップは、ターゲットとは異なる同一文字の最大連続セグメント全体をカバーすると想定できます。 より大きな連続領域を反転してもコストは増加せず、断片化は軽減されるため、セグメントを複数の反転に分割しても役に立ちません。 したがって、各最大ブロックは必要な操作を 1 つだけ提供し、分離されたブロック間の相互作用によってこの数を減らすことはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def count_blocks(s, ch):
    cnt = 0
    n = len(s)
    i = 0
    while i < n:
        if s[i] == ch:
            cnt += 1
            while i < n and s[i] == ch:
                i += 1
        else:
            i += 1
    return cnt

def solve():
    n = int(input().strip())
    s = input().strip()

    ones = count_blocks(s, '1')
    zeros = count_blocks(s, '0')

    print(min(ones, zeros))

if __name__ == "__main__":
    solve()
```機能`count_blocks`指定された文字の連続実行の数を計算します。 文字列内を進み、新しいブロックの開始に遭遇した場合にのみカウンターをインクリメントし、そのブロックの残りの部分を直ちにスキップします。 これにより、直線的な移動が保証されます。 

1 ブロックと 0 ブロックの数は両方とも計算されます。これは、それらが 2 つの可能なターゲット構成に対応しているためです。 どの均一な状態を達成したいかは自由に選択できるため、最終的な答えは最小値になります。 

よくある間違いは、反転を明示的にシミュレートしようとすることです。 最適解ではフリップがオーバーラップする必要はなく、問題の構造によりブロック境界によってコストが完全に決定されることが保証されるため、これは不要です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    def count_blocks(s, ch):
        cnt = 0
        i = 0
        n = len(s)
        while i < n:
            if s[i] == ch:
                cnt += 1
                while i < n and s[i] == ch:
                    i += 1
            else:
                i += 1
        return cnt

    n = int(input().strip())
    s = input().strip()
    return str(min(count_blocks(s, '1'), count_blocks(s, '0')))

 ## 特殊なケース

 のような文字列`11111`内部遷移はありません。 このアルゴリズムは、1 のブロック 1 つと、0 のブロック 0 をゼロとしてカウントします。 最小値はゼロであり、反転が必要ないという事実と一致します。 

のために`010101`、すべての文字が交互になり、3 つの 1 ブロックと 3 つのゼロ ブロックが生成されます。 アルゴリズムは正しく 3 を返します。これは、ターゲットの選択に応じて、孤立した各文字が独自の修正を必要とすることを反映しています。 

のようなパターンの場合、`000111000`、中央のセグメントは、選択されたすべて 0 のターゲットと異なる唯一のセグメントです。 このアルゴリズムは単一の 1 ブロックをカウントし、1 回のフリップで 1 回の操作で中央領域全体をカバーできることを正確に捕捉します。
