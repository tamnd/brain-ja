 ## 解決策
 ## 問題の理解

 左から右にインデックスが付けられた建物の列が与えられ、各建物には一定数の学生が収容されています。 フレディは常に最初の建物から開始し、順番に進むことしかできません。 各クエリ値について、学生の総数がそのクエリ値以上である建物の最小プレフィックスを知りたいと考えています。 すべての建物を訪問しても合計がクエリよりも小さい場合は、回答は不可能です。 

これは基本的にプレフィックスの蓄積の問題です。 各クエリは、プレフィックスの合計がしきい値に達するか、しきい値を超える最初の位置を求めます。 

この制約により、最大 100,000 の建物と 100,000 のクエリが許可されます。 クエリごとの直接シミュレーションでは、毎回最初からスキャンすることになり、最悪の場合は 10^10 の演算が発生することになりますが、これは Python では遅すぎます。 これにより、合計を繰り返し再計算するソリューションは即座に排除されます。 

構築値にゼロが含まれる場合、エッジ ケースが発生します。 進歩が常に建物ごとに行われると仮定する単純なポインタ アプローチは、多くの連続する建物が何も寄与しない場合に失敗する可能性があります。 たとえば、すべての a_i がゼロで q_j が正の場合、正解は -1 であり、増分進行に依存するメソッドは総和に対して到達可能性を明示的にチェックする必要があります。 

もう 1 つの微妙なケースは、q_j がゼロの場合です。 生徒がいないため、意味のある量の建物を訪問する必要はないため、正解は常に 1 ですが、最初の建物は依然として最小の接頭辞です。 

## アプローチ

 ブルート フォース方式では、各クエリが個別に処理されます。 特定の q について、最初の建物から開始して、q に達するかそれを超えるまで生徒数を累積します。 これは問題定義に直接従うため、正しいです。 ただし、最悪の場合、各クエリで n 個の建物すべてをスキャンする必要がある場合があります。 m 個のクエリの場合、これは O(nm) となり、最大 10^10 回の操作になります。 

重要な点は、すべてのクエリが同じ静的プレフィックス構造で動作することです。 配列のプレフィックスの合計を計算すると、すべてのクエリは検索問題になります。prefix[i] ≥ q となる最小のインデックス i を見つけるという問題になります。 プレフィックスの合計は減少しないため、クエリごとに二分検索を使用できます。 これにより、各クエリが O(log n) に減り、合計が O((n + m) log n) になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nm) | お(1) | 遅すぎる |
 | プレフィックス + 二分検索 | O((n + m) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. 建物配列のプレフィックスの合計を計算します。ここで、prefix[i] には建物 1 から i までの生徒の総数が格納されます。 これにより、問題は繰り返しの合計ではなく、範囲の到達可能性に変換されます。 
2. 各クエリ q について、q が合計プレフィックス [n] より大きいかどうかを確認します。 そうであれば、すべての建物を訪問しても足りないため、すぐに -1 を出力します。 
3. q が 0 の場合、最小の有効なプレフィックスは最初の建物であるため、1 を出力します。 これは、蓄積が必要ない縮退ケースを処理します。 
4. それ以外の場合は、プレフィックス配列に対して二分検索を実行して、prefix[i] ≥ q となる最小のインデックス i を見つけます。 これが機能するのは、プレフィックスの合計が単調に減少しないためです。 
5. クエリごとに i を出力します。 

### なぜ効果があるのか

 prefix sum 配列は累積到達可能性をエンコードします。prefix[i] は、建物 i で停止することによって達成できるものを正確に表します。 右に移動しても値が減少することはないため、条件 prefix[i] ≥ q は有効な回答の連続領域を定義します。 二分探索は、この単調構造を利用して、最初の有効なインデックスを見つけます。 prefix[i] が q を超えると、その後のすべてのインデックスもそれを満たし、最初に見つかった境界の正確さが保証されるため、アルゴリズムは有効な答えを見逃すことはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    q = list(map(int, input().split()))

    prefix = [0] * n
    prefix[0] = a[0]
    for i in range(1, n):
        prefix[i] = prefix[i - 1] + a[i]

    total = prefix[-1]
    out = []

    for x in q:
        if x == 0:
            out.append("1")
            continue
        if x > total:
            out.append("-1")
            continue

        lo, hi = 0, n - 1
        ans = n - 1

        while lo <= hi:
            mid = (lo + hi) // 2
            if prefix[mid] >= x:
                ans = mid
                hi = mid - 1
            else:
                lo = mid + 1

        out.append(str(ans + 1))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この解決策は、すべてのクエリが繰り返し合計ではなく累積合計に対する検索になるように、プレフィックス合計配列を構築することから始まります。 二分探索は、オーバーヘッドを回避し、プレフィックス制約が満たされる最初の位置を明示的に制御するために手動で実装されます。 変換`ans + 1`配列の内部ではインデックスが 0 ですが、問題ではインデックスが 1 の建物位置が使用されるため、これが必要です。 

特別な取り扱いは、`x == 0`不必要な二分探索を防止し、最初のプレフィックスが常に有効である境界条件の正確性を保証します。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての建物の価値がゼロである場合です。 この状況では、プレフィックス配列は決して増加しないため、肯定的なクエリはすぐに -1 を返す必要があります。 バイナリ検索条件 prefix[mid] ≥ x が決して満たされず、総和チェックがクエリを早期に拒否するため、アルゴリズムはこれを処理します。 

もう 1 つのエッジ ケースは、最初の建物がすでにクエリを満たしている場合です。 たとえば、a = [100, ...]、q = 50 です。プレフィックス配列は大きな値から始まるため、バイナリ検索は正しくインデックス 0 を返し、出力 1 に変換されます。正確かどうかは、有効なインデックスだけでなく、左端の有効なインデックスを検索することに依存します。
