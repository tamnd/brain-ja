 ## 解決策
 ## 問題の理解

 トークンが固定の非リーフ頂点から始まるツリーが与えられます。 目的は、2 人のプレイヤーが順番に行動した場合に、このトークンがいずれかのリーフ頂点に到達することが保証できるかどうかを判断することです。 

1 人のプレイヤーがトークンを制御します。 各ターン、トークンはその場に留まるか、隣接するエッジに沿って移動することができます。 他のプレイヤーは、ツリー内の 1 つの「ブロックされたエッジ」を制御します。 いつでも、正確に 1 つのエッジがブロックされる可能性があり、ブロッカーは、各変更後に開始される長さ k のクールダウン期間の後にのみ、どのエッジをブロックするかを変更できます。 トークンの動きに合わせて時間が進むため、ブロッカーはブロックされたエッジを変更する能力を徐々に取り戻します。 

ブロッカーが最初に移動するため、最初にブロックされたエッジを選択すると、ツリーの初期構造が即座に形成されます。 問題は、ブロッカーがどのようにプレイするかに関係なく、トークンプレイヤーが何らかの葉に到達することを保証する戦略を持っているかどうかです。 

入力は、すべてのテスト ケースにわたって最大 5×10^5 の頂点を持つツリーであるため、すべての解はテスト ケースごとに線形に近づく必要があります。 すべての頂点ペアを 1 回走査するだけでもすでに制限を超えてしまうため、パスまたはゲーム状態に対する 2 次アプローチは不可能です。 

微妙な失敗例は、ブロッカーが独自の脱出方向を繰り返し「シャドウ」できる場合に発生します。 

トークンが一方の端近くから始まる長いパス グラフを考えてみましょう。 k が大きい場合、ブロッカーは進行を妨げるのに十分な長さだけ前方エッジをブロックし続けることができます。 トークンが単に最も近いリーフに向かって歩くと仮定する素朴な貪欲なアプローチは、移動が無期限に遅延する可能性があることを無視しているため、失敗します。 

別の特殊なケースは、木に単一の分岐点があるが、すべての枝が異なる深さの葉につながっている場合に発生します。 k が小さい場合、1 つのエッジをブロックするだけでは十分ではありませんが、k が大きい場合、ブロッカーは開始領域を効果的に分離できます。 

これらのケースは、問題が最短パスだけに関するものではなく、周期的なブロッキング制約の下で永続的に安全なエスケープ パスが存在するかどうかにあることを示しています。 

## アプローチ

 強引なアイデアは、ゲームの状態をシミュレートすることです。 状態には、現在の頂点、現在ブロックされているエッジ、およびクールダウン タイマーが含まれます。 各状態から、すべてのトークンの移動とすべての有効なブロッカー アクションに分岐します。 これにより、各頂点をブロックされたエッジおよび多くのクールダウン値と組み合わせることができるため、サイズがおよそ n × 2 × k のゲーム グラフが構築されます。 

クールダウンの詳細を単純化して無視したとしても、最終的には両方のプレイヤーの位置とタイミングを効果的にエンコードする状態空間上の遷移を探索することになります。 ブロッカーは任意のエッジを繰り返し選択でき、トークンのパスは履歴に依存するため、これはすぐに O(n^2) またはさらに悪い状態に爆発します。 

重要な観察は、ブロッカーのパワーがローカルであるということです。つまり、どの時点でも 1 つのエッジのみが無効になります。 これは、トークンがツリーの単一の切断を回避することのみを強制されることを意味します。 問題は、ブロッカーが考えられるすべてのルートからリーフへのパスに沿った進行を繰り返し阻止できるかどうかに帰着します。 

ゲームの完全な状態を追跡する代わりに、視点を逆転させます。 開始頂点でツリーを根付かせることを想像してください。 すべての出口が周期的にブロックされる可能性がある領域に永続的にトラップされることなく、子サブツリーを介して常に最終的にリーフに到達できる場合、トークンは成功します。 

これは枝刈りの解釈につながります。つまり、特定の頂点が最適なブロッキング下でも確実に脱出できるのであれば、その頂点は「安全」であるということになります。 葉はまったく安全です。 定期的に適用される単一のエッジ ブロックでは完全に制御できない安全な領域につながる隣接ノードが少なくとも 1 つある場合、ノードは安全になります。

クールダウン k は、ブロッカーが 1 つのエッジ上でその分岐からの脱出を防ぐのに十分な長さの制御を維持できるかどうかを判断する上で重要になります。 これにより、問題は、限られた「制御の深さ」のパスに沿った到達可能性の制約と組み合わせたツリー上の DP に変わります。 

2 つの体制を比較します。 k が大きい場合、ブロッカーは単一のクリティカル エッジを効果的にロックして、そのエッジを永久に削除することをシミュレートできるため、複数の独立したエスケープ ルートを持つ分岐のみが問題になります。 k が小さい場合、トークンはブロッカーの制御を維持する能力を上回る可能性があり、リーフへの単純なパスであれば十分になります。 

最適な解決策は、トークンがブロッキング スケジュールを上回ることができる子サブツリーが存在するかどうかをノードごとに計算することになります。これは、リーフまでの距離を伝播し、k から導出されるブロッキング ホライズンと比較する DFS を介して評価できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 完全なゲームシミュレーション | O(n・k・度) | O(n・k) | 遅すぎる |
 | 距離 + クールダウン推論によるツリー DP | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 開始頂点でツリーをルートします。 私たちが計算する重要な量は、サブツリー内のすべてのノードから任意のリーフまでの最小距離です。これは、リーフに到達することが終了条件であり、距離によってブロッカーが干渉しなければならない時間を把握できるためです。 

1. まず、開始頂点から DFS を実行して計算します。`dist[u]`、からのエッジの最小数`u`ルート化されたサブツリー内の任意のリーフまで。 これにより、妨げられなければできるだけ早く脱出することができます。 最小距離を使用する理由は、遅延はブロッカーのリセットと再配置に役立つだけであるため、トークンは常に最速の終了を優先するためです。 
2. 同じトラバース中に、親子構造を追跡して、どのエッジが上向きの避難ルート上にあるかを確認します。 ブロッカーは一度に 1 つのエッジのみをブロックできるため、最も危険なエッジは進行のための唯一の導管となるエッジです。 
3. 各ノードについて`u`、k に基づいて「危険しきい値」を定義します。トークンが分岐点またはリーフに到達するために単一のコリドーを通って k 個を超える連続ステップを必要とする場合、ブロッカーはそのコリドーを継続的に抑制できます。 これは、長くて細いチェーンは、深さが k を超える前に最終的に分岐しない限り安全ではないことを意味します。 
4. ブール値を伝播します`win[u]`ボトムアップ。 葉には`win = True`。 内部ノードの場合は、子が存在するかどうかを確認します。`v`そのような`win[v]`は true であり、そのパスは`v`ブロッカーが完全なブロッキング サイクルを維持するには十分な長さではありません。 この条件は、サブツリーのエスケープ深さを k と効果的に比較します。 
5. 最後に、開始頂点で、この制約の下で安全なサブツリーにつながる出力方向が存在する場合、答えは「YES」、そうでない場合は「NO」になります。 

### なぜ効果があるのか

 ブロッカーの最適な戦略は常に、一度に 1 つのエッジに焦点を当てることになります。 クールダウンでは継続的な切り替えが妨げられるため、複数のブランチをブロックしようとする試みはすべてシリアル化する必要があります。 これにより、相互作用は、サブツリーに沿った脱出時間と、同じボトルネック エッジを閉じた状態に保つのに十分な速さで同じボトルネック エッジに再度アクセスするブロッカーの能力との間の競争に変わります。 DP は、単一のエッジが繰り返し再ブロックされる前に、各サブツリーが保証されたエスケープを提供するかどうかをエンコードすることで、まさにこの競合を捕捉します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    n, k, v = map(int, input().split())
    g = [[] for _ in range(n + 1)]
    for _ in range(n - 1):
        a, b = map(int, input().split())
        g[a].append(b)
        g[b].append(a)

    parent = [-1] * (n + 1)
    order = []
    stack = [v]
    parent[v] = 0

    while stack:
        u = stack.pop()
        order.append(u)
        for w in g[u]:
            if w == parent[u]:
                continue
            if parent[w] == -1:
                parent[w] = u
                stack.append(w)

    dist = [10**9] * (n + 1)

    for u in reversed(order):
        is_leaf = True
        best = 10**9
        for w in g[u]:
            if w == parent[u]:
                continue
            is_leaf = False
            best = min(best, dist[w])
        if is_leaf:
            dist[u] = 0
        else:
            dist[u] = best + 1

    win = [False] * (n + 1)

    for u in reversed(order):
        is_leaf = True
        ok = False
        for w in g[u]:
            if w == parent[u]:
                continue
            is_leaf = False
            if win[w] and dist[w] <= k:
                ok = True
        if is_leaf:
            win[u] = True
        else:
            win[u] = ok

    print("YES" if win[v] else "NO")

def main():
    t = int(input())
    for _ in range(t):
        solve()

if __name__ == "__main__":
    main()
```実装では、まず開始ノードからルート トラバーサルを構築します。 子関係を非再帰的な DFS 順序で繰り返し評価するため、明示的な親配列が必要です。 の`dist`配列は、最終化される前にすべてのノードが子の最小リーフ距離を集計するように、逆の走査順序を使用してボトムアップで計算されます。 

2 番目の DP パスは、各ノードが勝っているかどうかを計算します。 条件`dist[w] <= k`ブロッカーが唯一のアクティブなブロッキング エッジに対する制御を繰り返し完全に再確立する前に、サブツリーに到達できるかどうかをエンコードします。 これは、長い廊下からの脱出を制限する中心的な制約です。 

最終的な答えは単純に、開始頂点が勝っているかどうかです。 

## 実用的な例

 ### サンプル 1

 ノードごとに 1 つの代表的なサブツリー決定のみを追跡し、子が十分に迅速な脱出につながるかどうかに焦点を当てます。 

| ノード | 距離 | 勝つ |
 | --- | --- | --- |
 | 葉 | 0 | 本当 |
 | 葉に近い内部ノード | 1-2 | 子 dist ≤ k | の場合は True
 | ルート 1 | 子供 2 または 5 に依存します | 本当 |

 ノード 1 では、少なくとも 1 つの分岐がブロッキングしきい値内でのエスケープを許可しているため、結果は YES になります。 

これは、複数のエスケープ ルートが存在し、少なくとも 1 つが k に対して十分に速い場合、トークンが勝利を強制できることを確認します。 

### サンプル 2

 各ノードに継続パスが 1 つだけある長いチェーン。 

| ノード | 距離 | 勝つ |
 | --- | --- | --- |
 | 葉 | 0 | 本当 |
 | チェーンノード | 増加する | False は上向きに伝播します。 

開始ノード 4 では、利用可能な唯一のルートがブロッキングしきい値を超えているため、ブロッカーによって進行が無期限に遅延され、NO が返される可能性があります。 

これは、k が脱出深さに比べて大きい場合、単一経路構造が脆弱であることを示しています。
