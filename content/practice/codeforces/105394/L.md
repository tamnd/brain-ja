 ## 問題の理解

 3 つの洗濯プログラム A、B、または C のいずれかを使用して洗濯する必要があるアイテムが与えられています。各洗濯物には 1 つのプログラムが使用され、最大で 1 つの洗濯プログラムを使用できます。$k$アイテム。 すべてのアイテムには単一の固定プログラムはなく、代わりに一連の許可されたプログラムが付属しています。 一部のアイテムは完全に柔軟で、どのプログラムでも洗濯できますが、他のアイテムでは 1 つまたは 2 つのプログラムが禁止されており、最も制限の厳しいアイテムでは 1 つのプログラムのみが許可されます。 

入力は、許可されるプログラムに基づいてすべての項目を 7 つのカテゴリにグループ化します。つまり、A のみ、B のみ、C のみを許可するカテゴリ、厳密に 2 つのプログラムを許可するカテゴリ (AB、BC、AC)、および 3 つのプログラムすべてを許可するカテゴリ (ABC) です。 タスクは、ロードの合計数を最小限に抑えながら、すべてのアイテムをロードに分割する方法を決定することです。各ロードは単一のプログラムを選択し、互換性を尊重します。 

重要な構造上の制約は、プログラムの選択においてすべての負荷が均一であるため、同じバッチ内で A 負荷と B 負荷を混合することは不可能であるということです。 ただし、項目は、さまざまなプログラムの負荷にわたって柔軟に割り当てられるため、特に ABC カテゴリはどこでも使用できます。 

制約$k \le 10^9$そして最大までカウントします$10^9$カテゴリごとに設定すると、アイテムごとのシミュレーションが直ちに除外されます。 正しい解決策は、カウントと推論を一括して集計する必要があります。 プログラムが 3 つしかないため、問題全体は、共有の柔軟な供給の下で 3 つの容量ストリームのバランスをとることに帰着します。 

単純な故障モードは、各プログラムを個別に扱う場合に発生します。 たとえば、プログラムごとに必要な項目を計算し、個別に上限を取る場合、ABC 項目は 1 つだけではなくすべてのプログラムのギャップを埋めるために使用できるため、負荷が過大にカウントされます。 もう 1 つの失敗は、プログラムが完全なロードの完了にどの程度近づいているかを考慮せずに、現在不足が最も少ないプログラムに ABC 項目を貪欲に割り当てることで発生します。これにより、柔軟性が無駄になる可能性があります。 

主な問題点は、ABC 項目がどのプログラムでも「部分ロードを完了」できる共有リソースのように動作し、ロードを完了すると答えが 1 つだけ減るということです。 最適化全体は、これらの完了がどこで行われるかを決定することにあります。 

## アプローチ

 直接的な強引なアプローチでは、すべての項目を特定の負荷とプログラムに割り当てようとします。 つまり、アイテムを最大でサイズのグループに分割することになります。$k$、互換性の制約を確認しながら、グループごとに A、B、または C を選択します。 プログラムの選択を無視しても、パーティションの数は$n$アイテム数は指数関数的であり、カウントで集計しても、各カテゴリの負荷に対するすべての可能な割り当てにわたって膨大な検索スペースが残ります。 これは実行可能な計算をはるかに超えています。 

最初の単純化は、個々の負荷という観点から考えるのをやめ、代わりにプログラムごとの総需要という観点から考えることです。 ABC の柔軟性を一時的に無視した場合、プログラムごとに、そのプログラムに「必要」なアイテムの数を計算できます。 

プログラム A の場合、A、AB、AC、および ABC のすべての項目が需要に寄与します。 B と C についても同様です。これにより、3 つの総需要値が得られます。 

各需要を独立して次のように分割すると、$k$、プログラムごとのロードのベースライン数を取得します。 ただし、各 ABC 項目は 1 回しか使用されない場合でも 3 つの要求すべてでカウントされるため、この二重カウントでは ABC 項目が大きくカウントされます。 

重要な観察は、ABC アイテムが柔軟性の唯一の源であり、その唯一の有意義な効果は、部分的に充填された負荷に残りの容量を埋めるか、十分な量が蓄積されたときに負荷全体を削除することによって、必要な負荷の数を減らすことであるということです。 

基本的な要求を計算すると、構造は次のようになります。各プログラムには、サイズに応じた一連の負荷が含まれます。$k$ただし、残りによって決定される部分的に充填された 1 つのロードを除く。 ABC 項目は任意のプログラムに割り当てることができ、常に部分ロードを完了するか、プログラムの完全ロードの数を減らすことが最適な使用法です。 

これにより、問題は 3 つのバケットにわたるリソース割り当てタスクに変わります。 まず、ABC 分散を無視してプログラムごとの最小ロード数を構築し、次に ABC 項目を使用して、最も「無駄な」部分的に埋められたロードを最初にターゲットにすることで、ロードの総数を可能な限り削減します。 

最適な戦略は 2 つの段階で貪欲になります。 まず、ABC アイテムを使用して、A、B、および C にわたる不完全なロードを埋めます。これは、部分的なロードを完了すると、1 つのロードが削減されるという即時のメリットが得られるためです。 その後、残りの ABC アイテムはブロック内で使用できます。$k$それぞれ、プログラムから 1 つの完全なロードを削除する可能性があります。

 ## アルゴリズムのチュートリアル

 私たちは 3 つの集約された需要を維持しています。 

1. 各項目が互換性のあるすべてのプログラムに割り当てられているかのように、各プログラムの基本需要を計算します。 

A-需要 = cA + cAB + cAC + cABC

 B 需要 = cB + cAB + cBC + cABC

 C 需要 = cC + cAC + cBC + cABC
 2. 各需要を次の値で割ってベースライン負荷数に変換します。$k$。 各プログラムについて、全ロードの数と残りがあるかどうかの両方を計算します。 これにより、これらの上限の合計に等しい最初の答えが得られます。 
3. A、B、C の剰余を抽出します。これらは部分的に充填された荷重を表します。 部分的なロードを完了するとロードの総数が 1 つ減るため、最初に ABC アイテムを使用してこれらの残りを埋めることを優先します。 
4. すべての部分ロードが完了したか、ABC アイテムの不足により完了できなかった後、残りの ABC アイテムをサイズのチャンクにグループ化します。$k$。 それぞれの完全なチャンクを使用して、プログラムの 1 つの完全なロードを削除できるため、そのようなチャンクごとに答えが 1 つ減ります。 
5. ABC 項目がチャンクを完全に形成するには不十分な場合、残りが処理された後、負荷軽減の観点から事実上無駄になります。 

### なぜ効果があるのか

 不変条件は、どの時点においても、現在の計画が固定数のプログラム ラベル付きロードで構成されており、ABC 項目を使用するすべての操作で、残りが削減されるか (部分ロードを完全ロードに変換し、ロード カウントを 1 つ減らす)、または問題を除去するのに十分な追加項目を提供して完全ロード全体を削除するかのいずれかであるということです。$k$-サイズのブロック。 各負荷には独立した容量制約があるため、ABC アイテムが複数の負荷削減単位に貢献する方法はありません。 常に ABC 項目を最初に最も高い即時限界ゲインに適用するため (全負荷の削除の前に部分的な完了)、どの順序で割り当てても総負荷をより効果的に削減することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        k = int(input())
        c = list(map(int, input().split()))
        cA, cB, cC, cAB, cBC, cAC, cABC = c

        # base demands per program
        A = cA + cAB + cAC + cABC
        B = cB + cAB + cBC + cABC
        C = cC + cAC + cBC + cABC

        # full loads and remainders
        loadsA, remA = divmod(A, k)
        loadsB, remB = divmod(B, k)
        loadsC, remC = divmod(C, k)

        base = loadsA + loadsB + loadsC
        rems = [(remA, loadsA), (remB, loadsB), (remC, loadsC)]

        abc = cABC

        # first, try to fill remainders (each completion reduces one load)
        for i in range(3):
            rem, full = rems[i]
            if rem > 0 and abc > 0:
                need = k - rem
                if abc >= need:
                    abc -= need
                    base -= 1
                    rems[i] = (0, full + 1)
                else:
                    rems[i] = (rem + abc, full)
                    abc = 0

        # remaining ABC used in full chunks
        base -= abc // k

        print(base)

if __name__ == "__main__":
    solve()
```コードは、すべての項目カテゴリをプログラムごとの需要に折りたたむことから始まります。これが、負荷カウントに重要な唯一の構造です。 次に、各プログラムが個別に必要とする完全ロードの数を計算します。 ABC 品目はまだ割り当てられていないため、過大評価が生成されます。 

剰余処理ループは、ABC 項目を使用して、部分的に満たされたロードを明示的に完了しようとします。 ロードを完了するとすぐに答えが減ってしまうので、まずはここで貪欲にABCを消費します。 このフェーズの後は、残りの ABC 項目によって部分負荷をさらに改善することはできません。 

最後に、残りの ABC アイテムはグループで消費されます。$k$、各グループは、プログラムから 1 つの完全なロードを削除する機能を表します。 この時点では残りのロードはすべてフルサイズのユニットであり、部分的な最適化が残っていないため、これは安全です。

 ## 特殊なケース

 主なエッジケースは、プログラムのすぐ下に剰余がある場合です。$k$、 のような$k=5$残りは 4 で、単一の ABC 項目でロードが完了し、ロードの総数が 1 つ減ります。 アルゴリズムは、一括割り当ての前にこれを明示的にチェックし、この高価値の移動が決して見逃されないようにします。
