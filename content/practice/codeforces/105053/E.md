 ## 解決策
 ## 問題の理解

 N 人の顧客が関与したイベントの時系列のログが与えられます。 各顧客はレストランに入るときに 1 回、レストランを出るときに 1 回だけ現れます。 入力はこれを符号付き整数のシーケンスとしてエンコードします。正の値は顧客が入場することを意味し、負の値は顧客が退席することを意味します。 

このログの背後には隠された構造があります。各顧客は 2 つの回線 (G 線または S 線) のいずれかに割り当てられる必要があります。顧客が入場すると、割り当てられた回線の後ろに加わります。 特定のタイプのパンケーキ スタックが提供されると、対応するラインの最後に到着した顧客に常に行きます。これは、ラインが LIFO を削除したスタックのように動作することを意味します。 したがって、出発のシーケンスは、ラインごとに 1 つずつ、2 つの独立したスタックと一致する必要があります。 

タスクは、到着をシミュレートし、出発イベントで常に正しいスタックからポップするときに、観察された出発シーケンスが有効になるように、各顧客を 2 つの路線のいずれかに割り当てることができるかどうかを判断することです。 可能であれば、顧客の有効な割り当てを G または S に出力します。それ以外の場合は、アスタリスクを出力します。 

N ≤ 1000 という制約は、シーケンス長が最大 2000 イベントであることを意味します。 これにより、2^N の可能性の割り当てに対する指数関数的な検索が即座に除外されます。 O(N^2) または O(N log N) に近い解があれば十分です。 

将来の競合を考慮せずに貪欲な割り当てが行われた場合、微妙な失敗のケースが発生します。 たとえば、2 人の顧客が入れ子の形で時間的に重なり、その出口が誤ってインターリーブする場合、それらを任意に割り当てると、必要なポップがスタックの最上位以外の要素から来るという状況が発生する可能性がありますが、これは不可能です。 

具体的な問題となるパターンは、依存関係の交差です。 顧客 1 が入場し、次に顧客 2 が入場し、次に顧客 1 が退出し、次に顧客 2 が退場したとします。 両方を同じスタックに割り当てれば、これは機能します。 しかし、G に 1 を割り当て、S に 2 を割り当てると、両方のスタックが独立して制約を満たします。 ただし、より複雑なネストで出発順序を逆にすると、顧客を誤って分割した場合に、不可能なスタック動作が強制される可能性があります。 

主な問題は、各スタックが割り当てられた間隔にわたって後入れ先出し制約を強制するため、単一スタック内で無効な「インターリーブ」が発生しないように顧客を分割する必要があることです。 

## アプローチ

 強引なアイデアは、N 人の顧客のすべての割り当てを 2 つのグループに分けて試し、プロセスをシミュレーションすることです。 割り当てごとに 2 つのスタックを維持します。 イベント ログをスキャンします。到着時には正しいスタックにプッシュし、出発時には対応するスタックの先頭が顧客の出発と一致するかどうかを確認します。 そうでない場合、割り当ては失敗します。 

これは概念的には機能しますが、2^N 個のパーティションをチェックする必要があります。 各シミュレーションは O(N) であるため、合計の複雑さは O(N · 2^N) になります。これは、1000 の場合はおろか、N = 20 の場合でも実現不可能です。 

重要な観察は、一連のイベントが顧客に対する部分的な注文構造をすでに決定しているということです。 どのお客様にも入場から退場までの間隔があります。 この間隔内に、他の顧客がネストされる可能性があります。 2 人の顧客の間隔が「禁止されたインターリーブ」を作成する方法で交差する場合、それらを同じスタックに配置することはできません。 これは、顧客の各ペアがスタックの共有を許可される場合と許可されない場合があるという制約を満たす問題になります。

この問題をグラフの色付けの問題に変換できます。 各顧客をノードとするグラフを作成します。 アクティブな顧客のスタックを使用してイベント シーケンスをスキャンします。 顧客が終了するときは、割り当てられたスタックの最新のアクティブな顧客と一致する必要があります。 プロセス中に構造的な矛盾が検出された場合、いくつかのペアを分離する必要があると推測します。 より直接的には、このプロセスは、有効な代入が、置換スタック プロセスの 2 つのスタックへの有効な分解に対応することを強制するものとして解釈できます。これは、特定の暗黙的なグラフが 2 部構成であるかどうかをチェックするのと同等です。 

効率的な解決策は、アクティブな顧客ごとに、現在のスタック割り当てがわかっている場合はそれを維持しながらプロセスをシミュレートすることです。 顧客が入力すると、一時的に割り当てが解除されます。 離れるときは、2 つのスタックのうちの 1 つの上部と一致する必要があります。 両方のスタックが実行可能な選択肢である場合は、延期します。 1 つだけが有効な場合は、コミットします。 どちらも有効でない場合、構成は不可能です。 

より深い構造は、どの時点でも、2 つのスタックが現在アクティブなインターバルの 2 つのネストされたセットに対応するということです。 それぞれの離脱により、顧客がどのスタックに属さなければならないかが制約され、これらの制約の伝播によって決定的な割り当てが生成されるか、矛盾が検出されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | 制約伝播シミュレーション | O(N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 各行の現在のアクティブな顧客を表す 2 つのスタックを維持します。 また、最初は不明であった、各顧客に割り当てられた回線を格納する配列も維持します。 

イベント シーケンスを左から右に処理します。 

1. 顧客が入ってきたのを見て、すぐにその顧客を割り当てることはありません。 代わりに、それらの顧客を「アクティブだが割り当てられていない」顧客の一時的なプールに押し込みます。 これは、将来のイベントによって正しいスタックがまだ強制されていないことを反映しています。 
2. 顧客 x の離脱を確認すると、x が現在スタック G またはスタック S のいずれかの先頭にあるかどうかを確認します。それがちょうど 1 つのスタックの先頭にある場合、x はそのスタックに属している必要があるため、それに応じて x を割り当て、ポップします。 
3. x が両方のスタックの最上位にある場合は、どちらのスタックを選択してもかまいませんが、一貫性を確保する必要があります。 たとえば G を決定的に選択し、そこに x を割り当てます。 この選択は安全です。なぜなら、後の制約によって矛盾が検出されない限り、代替の選択は対称的になるからです。 
4. x がどちらのスタックの先頭にもない場合、スタックでは最後に挿入されたアクティブな要素の削除のみが許可されるため、割り当てはできません。 即返品不可です。 
5. x を割り当てた後、割り当てによって暗示されるすべての制約が一貫していることを確認します。これは、以前に割り当てられていないアクティブな顧客がスタック内の正しい相対順序に残ることを意味します。 未割り当ての顧客は常に、挿入オーダーで割り当てられた顧客の下にあるため、これはスタック構造によって暗黙的に処理されます。 
6. すべてのイベントが処理されるまで続行します。 成功すると、最終的な割り当て配列によって必要な出力が得られます。 

微妙な点は、スタックが厳密な入れ子構造を強制していることです。顧客がスタックに配置されると、そのスタック内でその上のすべての顧客は早めに退出する必要があります。 これは、イベント ログで必要な動作と正確に一致します。 

### なぜ効果があるのか

いつでも、各スタックは、その明細に割り当てられた顧客の有効な LIFO 注文を表します。 不変条件は、スタック内のすべての割り当てられた顧客が、スタックの動作と一致して、厳密に入場時間の昇順および退出時間の降順で表示されることです。 出発イベントが発生すると、他の顧客が LIFO 制約に違反する可能性があるため、有効な候補はスタックトップのみになります。 したがって、すべての強制割り当てが必要であり、両方のスタックが対称的な有効な部分解を表すため、2 つの有効なスタックの間でどのような選択をしても、将来の一貫した完了の可能性が維持されます。 矛盾に達した場合、それはスタック プロパティの違反に相当し、どのパーティションもイベント シーケンスを満たすことができないことを意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    events = list(map(int, input().split()))

    pos = {}
    for i, x in enumerate(events):
        if x > 0:
            pos[x] = i

    stack_g = []
    stack_s = []
    ans = ['?'] * (n + 1)

    for x in events:
        if x > 0:
            stack_g.append(x)
            stack_s.append(x)
        else:
            c = -x

            top_g = stack_g[-1] if stack_g else None
            top_s = stack_s[-1] if stack_s else None

            if top_g == c and top_s == c:
                ans[c] = 'G'
                stack_g.pop()
                stack_s.pop()
            elif top_g == c:
                ans[c] = 'G'
                stack_g.pop()
                if c in stack_s:
                    stack_s.remove(c)
            elif top_s == c:
                ans[c] = 'S'
                stack_s.pop()
                if c in stack_g:
                    stack_g.remove(c)
            else:
                print("*")
                return

    print("".join(ans[1:]))

if __name__ == "__main__":
    solve()
```この実装では、2 つの行を反映する 2 つの概念的なスタックが保持されます。 参入イベントごとに、顧客は潜在的な候補者として両方のスタックに追加され、その後の退出によって決定が強制されるまで続きます。 終了時に、スタックのトップのみがその時点で合法的に終了できるため、顧客が現在どちらかのスタックのトップにいるかどうかを確認します。 両方のスタックが許可する場合は、任意に割り当てます。 1 つだけが許可すると、割り当ては強制されます。 

重要な実装の詳細は、顧客が割り当てられると、そのラインに参加できなくなるため、他のスタックからも削除されることです。 顧客がどちらのスタックの最上位にもいない場合、まさに障害状態に達します。これは、イベント シーケンスが LIFO 構造と矛盾することを意味します。

 ## 特殊なケース

 単一の顧客事例は、対話を強制する制約がないため、どちらの割り当ても有効であることを示しています。 アルゴリズムは単にプッシュしてすぐにポップし、任意に割り当てます。 

次のような完全にネストされたシーケンス`+1 +2 +3 -3 -2 -1`単一のスタックで十分な場合を例に挙げます。 すべての出発点はアクティブな構造の先頭と一致するため、アルゴリズムは競合することなくすべてを同じ行に割り当てます。 

のような交差構造`+1 +2 -1 +3 -2 -3`失敗を示しています。 加工時`-1`の場合、顧客 1 は、一貫した割り当ての下ではどちらの有効なスタックの先頭にもありません。これは、一方のスタックで 2 がブロックし、もう一方のスタックで 3 がまだ削除されていないためです。 2 つの LIFO スタックへの分割ではシーケンスを実現できないため、これにより必要なアスタリスク出力が生成されます。
