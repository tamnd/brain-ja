 ## 解決策
 ## 問題の理解

 それぞれの犬の散歩の仕事は、アリスが最大 1 回選択できる項目とみなすことができます。 ジョブには、7 日間の要件パターンと支払い額という 2 つの情報が付属しています。 パターンは、犬を散歩させる必要がある曜日を示す長さ 7 のバイナリ ベクトルです。 アリスが仕事を引き受けた場合、彼女はそのパターンで 1 とマークされた毎日にその犬の散歩をすることを約束し、そのような約束ごとに彼女の 1 日の能力の 1 つが消費されます。 

週ごとのスケジュールは固定されています。7 日間のそれぞれで、アリスは最大 2 匹の犬を散歩できるため、毎日のキャパシティーは 2 になります。ジョブは複数の日に同時にキャパシティーを消費する可能性があるため、制約は選択したすべてのジョブにわたってグローバルです。 

タスクは、毎日、その日に必要な選択されたジョブの数が 2 を超えないようにしながら、支払総額を最大化するジョブのサブセットを選択することです。 

入力サイズは N の観点からは小さく、最大でも 100 ジョブですが、7 日間にわたる制約の結合は強力です。 これは、ジョブのサブセットに対するブルート フォースが概念的に可能であることを直ちに示唆しています。$2^{100}$サブセットですが、明らかに実行不可能です。 ただし、実際の構造では、各ジョブは 7 つの共有リソースのみと対話します。これは、状態空間が基本的に N 自体ではなく、1 日あたりの負荷によって制御されることを意味します。 

単純に貪欲なアプローチは失敗します。なぜなら、早​​期に高収入の仕事を選択すると、その価値を超える複数の小規模な仕事がブロックされる可能性があるからです。 たとえば、報酬 100 で 7 日間すべてを必要とするジョブは、局所的には最適に見えるかもしれませんが、結合していない日のサブセットを必要とする 2 つのジョブでは、1 日あたりのキャパシティ制約を尊重しながら合計 200 が得られる可能性があります。 

もう 1 つの微妙な失敗例は、1 日に複数のジョブが重なり合う場合に発生します。 1 つの忙しい日をすべて含む中程度の価値のジョブを選択しすぎると、最後の最後でのみ実行可能性に違反する可能性があり、貪欲な選択を遡及的に修正するのが困難になります。 

## アプローチ

 直接的なブルート フォース手法では、ジョブのすべてのサブセットを列挙し、毎週の容量使用量をシミュレートすることで実現可能性をチェックし、総利益を計算します。 実現可能性チェックのコスト$O(7N)$選択したジョブが毎日必要な数をカウントするため、サブセットごとに。 と$2^N$サブセットの場合、これは次のようになります$O(2^N \cdot N)$、これは天文学的に大きい$N = 100$。 

重要な観察は、唯一の共有リソース制約は、容量 2 を持つ 7 曜日だけであるということです。これは、システム状態が 7 日間のそれぞれに使用されるスロットの数、つまり各エントリが含まれる 7 次元ベクトルによって完全に記述されることを意味します。$\{0,1,2\}$。 そのような状態の総数は、$3^7 = 2187$、動的プログラミングには十分小さいです。 

各ジョブは、座標が 2 を超えない限り、固定のバイナリ ベクトルを現在の状態に追加することによってシステムを移行します。これにより、問題は、アイテムがジョブ、ディメンションが曜日である、小さな多次元容量空間にわたる古典的なナップザック スタイルの DP に変換されます。 

したがって、すべての実行可能な負荷構成に対して DP を実行し、各ジョブを実行するかスキップするかを検討して状態を更新します。 100 個のジョブをサイズ 2187 の状態空間に圧縮することで、ソリューションの効率が向上します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(2^N \cdot N)$|$O(7)$| 遅すぎる |
 | 日負荷状態における最適な DP |$O(N \cdot 3^7)$|$O(3^7)$| 承認済み |

 ## アルゴリズムのチュートリアル

 We represent each DP state as a 7-tuple of integers, where each entry records how many dogs are already assigned to that day. 各エントリの範囲は 0 ～ 2 です。 

1. 辞書または配列を初期化する`dp`ここで、キーは 7 日間の状態、値は達成可能な最大利益です。 値 0 を持つすべてゼロの状態から開始します。これはジョブを選択しないことを表します。 
2. ジョブを 1 つずつ処理します。 ジョブごとに、7 日間の要件ベクトルとその支払いを抽出します。 
3. 既存の DP 状態ごとに、2 つの可能性を検討します。状態を変更しないでジョブをスキップするか、ジョブを取得してその要件ベクトルを状態に追加します。 
4. ジョブを引き受けようとするときは、毎日の結果のカウントが 2 を超えないことを確認して実現可能性を検証します。これにより、アリスのキャパシティ制約が確実に尊重されます。 
5. 結果の状態が有効な場合、その状態の DP テーブル エントリを、現在の値と以前の状態の値にジョブの支払いを加えた最大値で更新します。 
6. すべてのジョブを処理した後、答えはすべての DP 状態にわたる最大値になります。 

重要な考え方は、DP はどのジョブが選択されたかを記憶する必要はなく、誘導された負荷構成のみを記憶する必要があるということです。 将来のすべての制約はジョブ ID ではなく現在の負荷のみに依存するため、これは有効です。 

### なぜ効果があるのか

 どの時点でも、各 DP 状態は、ジョブのプレフィックスを処理した後に達成可能な負荷構成のセットと、各構成で得られる最大の利益を正確にエンコードします。 新しいジョブを処理するとき、トランジションでは、ジョブを除外または含めることによって、以前に有効だった設定を拡張するあらゆる方法が考慮されます。 実現可能性は累積日負荷のみに依存し、これらは状態で完全に表現されるため、将来の決定に必要な情報が失われることはありません。 したがって、DP の不変条件が成り立ちます。i 個のジョブを処理した後、最適な利益を伴う到達可能なすべての有効な状態が正しく記録されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def encode(state):
    # base-3 encoding of 7 digits
    res = 0
    for x in state:
        res = res * 3 + x
    return res

def decode(x):
    state = [0] * 7
    for i in range(6, -1, -1):
        state[i] = x % 3
        x //= 3
    return state

def add_state(state, req):
    new_state = state[:]
    for i in range(7):
        new_state[i] += req[i]
        if new_state[i] > 2:
            return None
    return new_state

def solve():
    n = int(input())
    jobs = []
    for _ in range(n):
        *days, val = map(int, input().split())
        jobs.append((days, val))

    dp = {encode([0]*7): 0}

    for days, val in jobs:
        cur_items = list(dp.items())
        for mask, profit in cur_items:
            state = decode(mask)

            new_state = add_state(state, days)
            if new_state is not None:
                new_mask = encode(new_state)
                if new_mask not in dp or dp[new_mask] < profit + val:
                    dp[new_mask] = profit + val

    print(max(dp.values()))

if __name__ == "__main__":
    solve()
```DP テーブルは、7 日間の負荷ベクトルの Base-3 エンコードをキーとする辞書として保存されます。 これにより、状態をコンパクトに保ちながら、内側のループで 7 要素のリストを繰り返しコピーすることが回避されます。 

各ジョブは、現在の状態のスナップショットを反復処理することによって処理されます。 現在のジョブの更新が同じジョブの他の遷移にすぐに影響を与えてはならず、そうしないと選択項目が過大になってしまうため、これは不可欠です。 

Base-3 エンコードにより、状態の高速ハッシュと比較が保証され、デコードは遷移を適用する必要がある場合にのみ行われます。 状態空間が小さいため、このオーバーヘッドは無視できます。
