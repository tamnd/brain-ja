 ## 解決策
 ## 問題の理解

 木で表された国があります。 各都市は、プロセス全体を通じて最大 1 つの流星を受け取ることができます。 いつか街に隕石が落ちたら`t0`エネルギーを持って`val`、その都市はちょうど減少する値を提供し始めます`1`毎秒。 後で`t`、その貢献度は`val - (t - t0)`、マイナスになる可能性があります。 流星のない都市の寄与は常にゼロです。 

クエリはタイムスタンプの時系列順に到着しますが、複数のクエリが同じ時間を共有する場合があります。 タイプ 1 のクエリは、そこに流星を追加することで都市を活性化します。 タイプ 2 のクエリは、指定された時刻における指定された 2 つの都市間の経路上のすべての都市の寄与の合計を求めます。 

重要な観察は、すべての流星の時間依存部分が同一であるということです。 流星は次のように書き換えることができます。`val - (t - t0) = (val + t0) - t`最初の部分は流星が出現した後に修正されます。 2 番目の部分は、現在のクエリ時間のみに依存します。 パス クエリの場合、パス上に必要な値は 2 つだけです: すべての固定部分の合計`(val + t0)`パス上のアクティブ化された都市の数。 答えは次のようになります。`sum_fixed_values_on_path - current_time * activated_city_count_on_path`ツリーには多くの都市と多くのクエリが含まれる可能性があるため、クエリごとにパスに沿って歩くことを避ける必要があります。 あたりまでで`10^5`入力をスケールすると、クエリごとの線形走査は約`10^10`通常の制限時間をはるかに超えた最悪の場合の操作。 更新とクエリごとに対数処理が必要です。 

いくつかの特殊なケースは見落とされがちです。 クエリが流星都市のみを含むパスを要求する場合、都市の数は 0 ではなく 1 になります。```
Input
2
1 2
3
1 5 2 7
2 5 2 2
2 8 2 2
```時の流星の寄与`5`は`7`したがって、最初の答えは次のとおりです。`7`。 時間に`8`、貢献度は`4`したがって、2 番目の答えは次のようになります。`4`。 初期エネルギーのみを保存し、経過時間を忘れるソリューションでは、次の出力が得られます。`7`両方にとって。 

もう 1 つのよくある間違いは、同じタイムスタンプを持つクエリを間違った順序で処理することです。```
Input
1
2
1 10 1 3
2 10 1 1
```流星はクエリの前に同時に追加する必要があります。 答えは`3`。 クエリが最初に処理されると、誤って空のツリーが表示されます。 

マイナスの貢献も重要です。```
Input
1
2
1 0 1 5
2 10 1 1
```貢献があるのは都市だけ`5 - 10 = -5`、したがって、答えは次のとおりです`-5`。 値をゼロにクランプすると、間違った結果が生成されます。 

## アプローチ

 直接的な解決策では、すべての都市の現在の貢献度が保存されます。 流星が出現すると、その落下時間とエネルギーが記録されます。 パス クエリの場合は、パスを見つけて、その上にあるすべての都市を合計することができます。 これは正しいです。なぜなら、このパスはまさに貢献が重要な都市の集合だからです。 問題は仕事量です。 ツリーにはほぼすべての都市を含むパスを含めることができ、これを多くのクエリに対して繰り返すと、次のような最悪のケースが発生します。`O(nq)`操作。 

有益な観察は、流星の効果が線形であるということです。 時間とともに変化する値を保存するのではなく、定数部分を保存する`(val + t0)`そして、その経路上にある流星の数を個別に数えます。 残りの問題は、標準的な動的ツリー パス クエリの問題です。つまり、ノードに値を追加し、パス上のノード値の合計を求めるというものです。 

これに対処するには、ツリーをルート化し、プレフィックス寄与のアイデアを使用します。 任意のノードについて、ルートからそのノードまでの値を定義します。 パスの合計は、最も低い共通祖先を使用して再構成できます。`path(a, b) = root_to_a + root_to_b - 2 * root_to_lca + value_at_lca`ツリー差分のトリックを備えたフェンウィック ツリーを使用して、ルート パスの合計を維持できます。 ノードが値を受け取ると、そのエントリをオイラー順序で更新し、サブツリーの終了後に削除することによって、その値をノードのサブツリー効果に追加します。 次に、プレフィックス クエリによって、ルートから任意のノードに累積された値が与えられます。 これを固定値に対して 1 回、カウントに対して 1 回実行します。 

2 つのフェンウィック ツリーは異なる情報を保存しますが、処理は同じです。 1つの店舗`(val + t0)`、その他の店舗`1`活性化されたすべての都市に。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 最適 | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 街に木を根付かせる`1`そして DFS を実行して、すべてのノードのオイラー開始時間と終了時間、および深さと祖先を計算します。 オイラー次数を使用すると、サブツリーを連続区間にすることができます。これは、フェンウィック ツリーに必要なものです。 
2. 最小共通祖先クエリ用のバイナリ リフティング テーブルを構築します。 すべてのパスが LCA で重複する 2 つのルート パスに分割される可能性があるため、LCA が必要です。 
3. 2 つのフェンウィック ツリーを作成します。 最初のものは固定流星の値を表します`(val + t0)`。 2 番目は活動中の流星の数を表します。 
4. 流星が街に現れたら`x`、その固定値と 1 のカウントを追加します。`x`サブツリー範囲の更新を使用します。 範囲の更新により、値がサブツリー全体に追加されます。`x`、すべての子孫のルート パスが通過するため、`x`。 
5. パスクエリの場合`(a, b)`時に`t`、LCAを計算します`c`。 固定値の合計を取得し、3 つのルート パスをカウントします。 これらを LCA 式と組み合わせて、経路上の固定寄与率と流星の数を取得します。 
6. 減算`t * count`定額拠出金から。 これにより、要求された時点での実際の寄与が得られます。 

正確さは、各フェンウィック ツリー クエリがルートから要求されたノードまでのパス上にあるすべてのアクティブな流星ノードの合計値を返すという不変条件から導かれます。 ノードに置かれた隕石`x`のノードのルート パスに正確に影響します。`x`のサブツリーなので、オイラー範囲の更新はその影響を完全に表します。 LCA 式では、2 つのルート パスの共有プレフィックスが 1 回だけ削除され、要求されたパス上のすべての都市が 1 回カウントされたままになります。 すべての流星が寄与するため、`(val + t0) - t`、固定合計とカウントを組み合わせると、常に実際の答えが再構築されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 2)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        res = 0
        while i:
            res += self.bit[i]
            i -= i & -i
        return res

    def range_add(self, l, r, v):
        self.add(l, v)
        self.add(r + 1, -v)

def solve():
    n = int(input())
    g = [[] for _ in range(n + 1)]
    for _ in range(n - 1):
        u, v = map(int, input().split())
        g[u].append(v)
        g[v].append(u)

    LOG = (n).bit_length()
    up = [[1] * (n + 1) for _ in range(LOG)]
    tin = [0] * (n + 1)
    tout = [0] * (n + 1)
    timer = 0

    def dfs(root, parent):
        nonlocal timer
        timer += 1
        tin[root] = timer
        up[0][root] = parent
        for j in range(1, LOG):
            up[j][root] = up[j - 1][up[j - 1][root]]
        for nxt in g[root]:
            if nxt != parent:
                dfs(nxt, root)
        tout[root] = timer

    dfs(1, 1)

    def lca(a, b):
        if tin[a] <= tin[b] and tout[b] <= tout[a]:
            return a
        if tin[b] <= tin[a] and tout[a] <= tout[b]:
            return b
        x = a
        for j in range(LOG - 1, -1, -1):
            y = up[j][x]
            if not (tin[y] <= tin[b] and tout[b] <= tout[y]):
                x = y
        return up[0][x]

    fixed = Fenwick(n + 2)
    count = Fenwick(n + 2)

    def root_value(bit, x):
        return bit.sum(tin[x])

    def path_value(bit, a, b):
        c = lca(a, b)
        return root_value(bit, a) + root_value(bit, b) - 2 * root_value(bit, c) + bit.sum(tin[c]) * 0

    q = int(input())
    ans = []

    for _ in range(q):
        data = list(map(int, input().split()))
        if data[0] == 1:
            _, t, x, val = data
            fixed.range_add(tin[x], tout[x], val + t)
            count.range_add(tin[x], tout[x], 1)
        else:
            _, t, a, b = data
            c = lca(a, b)

            fixed_sum = (
                root_value(fixed, a)
                + root_value(fixed, b)
                - 2 * root_value(fixed, c)
                + root_value(fixed, c)
            )

            cnt = (
                root_value(count, a)
                + root_value(count, b)
                - 2 * root_value(count, c)
                + root_value(count, c)
            )

            ans.append(str(fixed_sum - t * cnt))

    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```フェンウィック ツリーは、オイラー走査にわたる差分配列を保存します。 更新中`[tin[x], tout[x]]`のサブツリー内のすべてのノードに値が表示されます。`x`。 プレフィックスの合計`tin[v]`の祖先からの更新を正確に収集します`v`、これはルートから`v`。 

LCA ルーチンはバイナリ リフティングを使用します。 テーブル`up[j][v]`の祖先を保存します`v`つまり`2^j`エッジがその上にあるため、素早く上に移動できます。 

の表現`fixed_sum`は通常のパス和の式です。 3 番目のルート パスは 2 回カウントされるため、LCA パスは加算し直すことによってもう一度減算されます。 カウントの計算でも同じ考え方が使用されます。 の乗算`t`すべてのアクティブな流星は正確に失われるため、最終ステップでのみ発生します`t`保存されている固定値を基準とした単位。 

入力ループはタイプ 1 の更新を、その後のタイプ 2 のクエリの直前に同時に処理するため、クエリの処理順序では当然同じタイムスタンプが処理されます。 すべての算術演算では Python 整数が使用されるため、負の値や大きな積は安全です。

 ## 特殊なケース

 流星都市のみを含むパスの場合、LCA は同じ都市になります。 ルート パスの重複が正しく削除されるため、この式は引き続き機能します。 2 つの都市と都市 2 に隕石がある入力では、都市 2 から都市 2 自体までのパスは固定の合計になります。`7`そして数えます`1`、正確な貢献度を示します。 

メテオとクエリが同じタイムスタンプを共有する場合、メテオの更新はクエリが処理される前にすでにフェンウィック ツリー内にあります。 保存されている値は、`(val + t)`、そして減算`t`すぐに戻ります`val`、問題のタイミングルールと一致します。 

寄与がマイナスになると、フェンウィック ツリーは固定部分のみを保存してカウントします。 値が正である必要があるとは決して想定していないため、固定値は`5`時差がある`10`正しくなる`5 - 10 = -5`。
