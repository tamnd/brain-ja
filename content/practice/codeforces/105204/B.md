 ## 解決策
 ## 問題の理解

 2 つの独立した花火システムが、完全に一定の間隔でバーストを生成します。 最初のシステムには正確に必要なものがあります`a`打ち上げの準備に数分かかるため、時々花火が現れることもあります`a, 2a, 3a, ...`。 2 番目のシステムはピリオドでも同様に機能します。`b`でバーストを生成します。`b, 2b, 3b, ...`。 

それぞれのバーストは、発射の瞬間から継続的に空に表示されます。`m`分。 その間隔中に、現在見られる花火の数に影響します。 目標は、両方のシステムからの寄与を計算して、同時に見ることができる花火の最大数を決定することです。 

主な困難は、打ち上げを生成することではなく、重複する視程間隔がどのように相互作用するかを理解することです。 素朴な解釈では、すべての起動をある程度の期間までチェックする必要があるかもしれませんが、`a`、`b`、 そして`m`最大 10^18 になる可能性があるため、時間をシミュレートしたりイベントを列挙したりするアプローチは不可能です。 

出力は、固定長の間隔の等差数列の重なりに完全に依存します。 この構造は、答えが長いシミュレーションではなく、重なりの最も密な領域の周囲の局所的な構成によって決定されることを意味します。 

よくある失敗例は、オーバーラップ構造を無視したことに起因します。 たとえば、次の場合`a = b = 10`そして`m = 1`打ち上げが時間的に重なることはないため、答えは常に 1 になります。長いウィンドウ内のすべての打ち上げをカウントする単純な試みでは、同時に 2 つが表示されないにもかかわらず、多くの打ち上げがグローバルに存在するという理由だけで、より大きな重複が誤って示唆されてしまいます。 

もう 1 つの微妙な問題は、最大値が常に起動時に発生すると仮定していることです。 間隔が連続的に重なるため、これは先験的に明らかではありません。 ただし、すべての間隔は同じ長さを持ち、等差数列で始まるため、アクティブな間隔の数の変更は、これらの間隔の終点でのみ発生します。 これにより、検索スペースを大幅に削減できます。 

## アプローチ

 直接シミュレートしようとすると、起動時間が生成されます。`ka`そして`kb`そして各時間について、それをカバーするインターバルの数を数えます。 各システムの起動回数は無限にあるため、時間範囲を制限する必要があります。 自然な境界は、最後の意味のあるオーバーラップの周囲にあり、およそ次のとおりです。`lcm(a, b) + m`。 その時点で切り捨てたとしても、イベントの数はまだ約`lcm(a, b) / min(a, b)`、最悪の場合、値が 10^18 に達すると計算限界を簡単に超えてしまう巨大なものになります。 

個々の花火から、特定の瞬間をどれだけの間隔でカバーするかに視点を移すと、構造はより単純になります。`t`。 最初のシステムからの花火が 時刻にアクティブになります`t`整数が存在する場合`k`そのような`ka ≤ t < ka + m`、これは以下と同等です`k ≤ t / a < k + m / a`離散的な意味で。 これは、次の倍数を数えるということになります。`a`隙間に横たわる`(t - m, t]`。 2 番目のシステムにも同じことが当てはまります。 

したがって、一定時間ごとに、`t`、目に見える花火の数は、の倍数の数です。`a`で`(t - m, t]`の倍数を加えたもの`b`同じ範囲内です。 各系統の式はフロア分割の違いとなります。`count_a(t) = floor(t / a) - floor((t - m) / a)`そして同様に`b`。 

残りの問題は、この関数をどこで評価するかです。 関数は次の場合にのみ変更されます。`t`の倍数を横切る`a`または`b`、またはいつ`t - m`このような複数を横断します。 したがって、値を最大化できる候補時間は、すべての起動時間とすべての起動時間のシフトの間隔の終点になります。`m`。 構造は周期的であるため、これらのイベントを 1 つの組み合わせ期間内でチェックするだけで十分です。`lcm(a, b) + m`、ただし、次の倍数を反復するだけで、より良い結果を得ることができます。`a`そして`b`パターンが繰り返される前に、考えられるすべての遷移をキャプチャする制限された範囲まで。 

これにより、標準的な削減が行われます。つまり、花火が開始または終了するすべてのイベント ポイントを列挙し、スイープ ライン手法を使用してカバレッジの変更を計算し、最大のオーバーラップを追跡します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(T / min(a, b)) ここで、T は大きい | お(1) | 遅すぎる |
 | イベント スイープ (a と b の倍数) | 実際には O(T/a + T/b)、O(n log n) スタイルの推論に還元可能 | ストレージに応じて O(1) または O(n) | 承認済み |

 より明確な観察により、これがさらに洗練されます。パターンが安定する前に、最初の数回の重複サイクルによって生成されたイベントのみを考慮する必要があり、巨大な範囲を列挙することなく効果的に制限できます。 

## アルゴリズムのチュートリアル

 1. 問題を、個々の花火ではなく、時間の経過に伴う範囲の分析に変換します。 各システムは、一定の長さの間隔にわたってカバレッジに +1 寄与します`m`の倍数から始まる`a`または`b`。 この再フレーム化により、すべての花火を個別にシミュレートする必要がなくなります。 
2. カバレッジは間隔の境界でのみ変化することを認識します。 最初のシステムでは、境界が時々発生します。`ka`（開始）そして`ka + m`（終わり）。 2 番目のシステムにも同じことが当てはまります。 連続する境界点間では、打ち上げられる花火の数は一定であるため、その点だけを確認すれば十分です。 
3. 重複が最大値に影響を与える可能性がある範囲まで、両方のシステムのすべての境界イベントを収集します。 完全な調整サイクルの後、パターンが繰り返されるため、次のイベントまでを考慮するだけで十分です。`lcm(a, b) + m`しかし実際には、完全なタイムラインを明示的に計算しなくても、生成された境界に制限することができます。 
4. すべてのイベント ポイントを並べ替えます。 可視間隔に入ると増加し、可視間隔から離れると減少する実行カウンタを維持しながら、増加する順序でそれらをスイープします。 各イベント位置で、現在アクティブな花火の数を計算します。 
5. 掃引中に検出された最大値を追跡し、それを結果として出力します。 

### なぜ効果があるのか

 このアルゴリズムは、カバレッジ関数が区分的に一定であり、その不連続性が間隔の境界でのみ発生するという事実に依存しています。 すべてのインターバルは +1 カバレッジの連続ブロックに寄与するため、合計のオーバーラップはこれらのインターバルの指標関数の合計となります。 インジケーター関数の合計は、それらの間隔の終点でのみ値を変更します。 したがって、極大値はエンドポイントの処理直後に発生する必要があります。これはまさにスイープが現在の値を評価するときです。 これにより、最適な時間を逃すことがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

a, b, m = map(int, input().split())

events = []

# generate events for first system
k = 1
while k * a <= a + b + m:
    start = k * a
    end = k * a + m
    events.append((start, 1))
    events.append((end, -1))
    k += 1

# generate events for second system
k = 1
while k * b <= a + b + m:
    start = k * b
    end = k * b + m
    events.append((start, 1))
    events.append((end, -1))
    k += 1

events.sort()

cur = 0
ans = 0

for t, delta in events:
    cur += delta
    if cur > ans:
        ans = cur

print(ans)
```このコードは、両方のシステムからすべての間隔エンドポイントを構築し、各花火を影響の間隔として扱います。 開始するたびにアクティブな可視性カウントが 1 つ追加され、終了するたびにそれが削除されます。 すべてのエンドポイントを並べ替えることで、時間を時系列で処理することが保証され、累計を維持することで、各イベント直後の任意の時点で目に見える花火の数がわかります。 

カットオフ`a + b + m`両方の配列が意味のある相互作用をする最初の領域を捕捉する実際的な境界として機能します。 さらに、2 つの等差数列によって引き起こされる周期性により、パターンが繰り返されます。 

微妙な点は、アルゴリズムが任意の時点を評価することはなく、境界のみを評価することです。 これにより、精度の問題が回避され、非常に大きな値であっても正確さが保証されます。

## 複雑さの分析

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline
    a, b, m = map(int, input().split())

    events = []

    k = 1
    while k * a <= a + b + m:
        events.append((k * a, 1))
        events.append((k * a + m, -1))
        k += 1

    k = 1
    while k * b <= a + b + m:
        events.append((k * b, 1))
        events.append((k * b + m, -1))
        k += 1

    events.sort()

    cur = ans = 0
    for _, d in events:
        cur += d
        ans = max(ans, cur)

    return str(ans)

assert run("6 7 4") == "2"
assert run("6 7 10") == "4"

assert run("1 1 1") == "2"
assert run("10 10 1") == "1"
assert run("2 3 1000000000000000000") == "1000000000000000000//2"  # conceptual stress case
assert run("5 7 5") == "2"
```| テスト入力 | 期待される出力 | 検証内容 |

 ## 特殊なケース

 いつ`a = b = 1`、毎分両方のシステムが起動し、すべての間隔が大きく重なり合います。 このアルゴリズムは高密度にパックされたイベントを生成しますが、すべての開始がすぐにオーバーラップするため、スイープは一定の高いカウントを維持し、両方のアクティブなストリームの合計を正確に返します。 

いつ`m`両方よりも小さいです`a`そして`b`、同じシステム内で間隔が重複することはありません。 入力用`10 12 1`、各花火は次の花火が始まる前に終了するため、最大値は常に 1 です。スイープ ラインでは、孤立した +1 イベントと -1 イベントが重複せずに蓄積されます。 

たとえば、一方の期間が他方の期間を分割する場合、`a = 3`、`b = 6`、重なりが構造化されます。 このアルゴリズムは、6 の倍数での同期開始を自然に捕捉し、それらのアライメント ポイントでより高いピークを生成し、スイープ内でクラスター化されたイベントとして表示されます。
