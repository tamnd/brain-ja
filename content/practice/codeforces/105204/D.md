 ## 問題の理解

 私たちには学生の列が与えられました。 各生徒は 2 つのパラメータによって記述されます。 そのうちの 1 つは、あと何回食べ物を提供する必要があるかを伝え、もう 1 つは、食べ物を受け取ってから 1 回分を食べ終わるまでにどれくらい時間がかかるかを伝えます。 

調理人は巡回で業務を行います。 各ラウンドで彼がサーブできるのは最大でも`x`キュー内で最初に利用可能な生徒に分配されます。 生徒は配膳を受け取った後、自分の食事時間と同じ一定時間列から離れ、さらに配膳が必要な場合は列の最後尾に戻ります。 このプロセスは、必要なサービングがすべて完了するか、許容される合計時間が経過するまで続行されます。`D`を超えています。 

タスクはパラメータの最小値を見つけることです`d`そうすることで時間内にすべてを完了できるようになります`D`。 そうでない場合`d`存在します、答えは`-1`。 

この制約は、最大 200,000 人の学生を扱い、最大 300,000 人の学生を扱うことを示唆しています。 これにより、注意深いデータ構造を持たずに単純な方法で毎分またはすべての提供ステップを処理するシミュレーションは即座に除外されます。 単位時間あたりの直接シミュレーションでは、最悪の場合、簡単に 10^10 の演算に達して失敗します。 

微妙な問題は、学生が非同期でキューから出たり再び入ったりするため、時間の経過とともにキューの順序が変化することです。 キューの状態をあらゆる瞬間に明示的にシミュレートしようとするアプローチは拡張できません。 

単純なアプローチでよくある失敗例は、再挿入のタイミングを無視したことにあります。 たとえば、食事時間が長い生徒が早めに配膳された場合、生徒は後で戻ってきて、単純な FIFO シミュレーションでは正しく予測できない方法でキューをブロックする可能性があります。 

## アプローチ

 簡単なアイデアは、プロセスを直接シミュレートすることです。 キューを明示的に維持し、最大まで繰り返し取得します。`x`生徒に一食分を割り当て、残りの必要量を減らし、食事時間が終了したら押し戻します。 これは原理的には正しいですが、各サービングは将来のイベントを引き起こし、最悪の場合、イベントの数は全生徒の総サービング数に比例します。 各生徒は最大まで要求できるため、`10^9`これは不可能になります。 

重要な構造的観察は、システムがパラメータに関して単調に進化するということです。`d`。 特定の値の場合、`d`時間内に完了できるようにする`D`、その後、さらに大きな値`d`今後のラウンドを遅らせるだけであり、実現可能性を高めることはできません。 この単調性は、次の二分探索を示唆しています。`d`。 

残りの課題は、固定化の実現可能性をどのように確認するかです。`d`すべての単位ステップをシミュレートする必要はありません。 時間の経過とともに満員のキューを追跡するのではなく、イベントに焦点を当てます。各生徒には、食事後にキューに戻るときに「次に利用可能な時間」が与えられます。 私たちは常にサービスを提供します`x`受講可能時間が最も短い生徒。生徒を遅らせても完了が遅れるだけです。 

これにより、問題は、利用可能時間によって順序付けされた優先順位構造を使用したイベント駆動型のシミュレーションに変わります。

 ## アルゴリズムのチュートリアル

 候補値を確定する`d`すべての生徒が時間内に終了できるかどうかをテストします`D`。 

1. 次回各生徒が食事を受け取ることができるようになるまでに順序付けされた優先キューを初期化します。 当初は、すべての生徒が時間通りに参加可能です`0`、キーを使用して挿入されます`0`。 各エントリには、まだ必要なサービングの数と、サービングごとの食事時間も保存されます。 
2. から始まるグローバル現在時刻を維持します。`0`。 
3. まだ食べ終わっていない料理がある間、これを繰り返します。 

1. 現在の時間を、全生徒の中で最も短い空き時間まで進めます。 
2. まで抽出します`x`利用可能時間が現在時刻以下の学生。 
3. 選択した生徒ごとに、残りの一人分を 1 つずつ減らします。 
4. 生徒がさらに多くの食事を必要とする場合は、更新された利用可能時間を次の時間に設定して構造に再挿入します。`current_time + si`。 

私たちが常に最も早い時間に受講可能な生徒を受け入れる理由は、進行を進める唯一の操作がサービスであるため、準備ができている生徒を延期しても総完了時間を短縮できないためです。 
4. いずれかの時点でシミュレーション時間が超過した場合`D`、私たちは立ち止まってこれを宣言します`d`実現不可能。 
5. 二分探索を使用する`d`実行可能な最小値を見つけます。 

### なぜ効果があるのか

 重要な不変条件は、いつでも優先キューが、再びサービスを受ける資格のあるすべての生徒を正確に表し、サービスに再参加できる最も早い時間順に並べられることです。 常に最も早い時間に受講可能な生徒に対応するという貪欲な選択により、早期に完了する可能性のある完了を人為的に遅らせることがなくなります。 サービス容量は固定されているため、`x`ラウンドごとに、代替順序を付けても、並列処理を増やすことなく、一部のサービスを延期するだけです。 

の単調性`d`構成が実現可能になると、すべてがより大きくなることが保証されます。`d`値は実行可能なままであるため、二分探索が有効になります。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def check(n, x, D, students, d):
    # heap stores (available_time, remaining_servings, eat_time)
    heap = []
    for k, s in students:
        heapq.heappush(heap, (0, k, s))

    time = 0

    while heap:
        time = max(time, heap[0][0])

        batch = []
        for _ in range(x):
            if not heap or heap[0][0] > time:
                break
            batch.append(heapq.heappop(heap))

        if not batch:
            time = heap[0][0]
            continue

        for avail, k, s in batch:
            k -= 1
            if k > 0:
                heapq.heappush(heap, (time + s, k, s))

        time += d
        if time > D:
            return False

    return True

def solve():
    n, x, D = map(int, input().split())
    students = [tuple(map(int, input().split())) for _ in range(n)]

    lo, hi = 1, D
    ans = -1

    while lo <= hi:
        mid = (lo + hi) // 2
        if check(n, x, D, students, mid):
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1

    print(ans)

if __name__ == "__main__":
    solve()

二分探索はこのチェックをラップし、実行可能な最小値を見つけます。`d`。 

実装によくある落とし穴は、受講可能な生徒がいないときに時間を進めるのを忘れることで、無限ループにつながります。 もう 1 つは、次回の空き状況を更新せずに、生徒を誤って再入学させることで、正確性が損なわれます。

 ## 特殊なケース

 エッジケースの 1 つは、長い遅延の後、すべての生徒が同時に応答できなくなる場合に発生します。 その状況では、ヒープは現時点で空になり、アルゴリズムは次の利用可能時間に直接ジャンプする必要があります。 このジャンプがないと、シミュレーションが停止するか、誤って時間を段階的に増加させることになります。 

もう 1 つのエッジケースは次のような場合です`x`定員を超えています。 バッチ選択ループは、存在しない要素をポップしようとせずに早期に停止する必要があります。そうしないと、プログラムがクラッシュしたり、ラウンドのカウントを誤ったりします。 

最後のコーナーケースは、生徒が最後に必要な配膳を終えたときです。 これらをヒープに再挿入してはなりません。 それらを削除しないと、残りの作業はゼロですがアクティブなエントリが残った状態でシミュレーションが無期限にループします。
