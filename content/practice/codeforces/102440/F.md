 ## 解決策
 ## 問題の理解

 私たちには (1) から (n) までの番号が付けられた友人がいます。友人 (i) は、3 つのチームのうちのいずれかに、ちょうど (i) の力を与えます。 すべての友達は 1 つのチームに所属する必要があり、3 つのチームの合計は等しくなければなりません。 タスクは、そのようなパーティションを印刷するか、パーティションが存在しないことを報告することです。 

総合的な強さは、

 [
 S = 1+2+\dots+n = \frac{n(n+1)}2.
 】

 有効なパーティションが存在する場合、すべてのチームに強みが必要です

 [
 T = \frac{S}{3} = \frac{n(n+1)}6.
 】

 したがって、(n(n+1)) を (6) で割り切れることが最初の必要条件です。 ただし、小さい (n) の場合は十分ではありません。 たとえば、(n=2) の場合、合計戦力は (3) となるため、ターゲットは (1) になりますが、戦力 (1) のチームを編成できるのはフレンド (1) だけです。 同様に、(n=3) にはターゲット (2) がありますが、その強さを持つのは番号 (2) の 1 人の友人だけです。 

制約 (n\le 10^6) は、問題の建設的な性質を決定的にします。 すべて (n 人) のプレイヤーをパスする余裕はありますが、指数関数や二次関数は完全に範囲外です。 コンテストの公式バージョンでは、この問題に 1 秒の制限と 256 MB のメモリが与えられているため、意図した解決策は (n) で線形に近いものでなければなりません。 

割り算のみに基づいた解決策では誤って処理される可能性がある小さな境界ケースがいくつかあります。 (n=1) の場合、合計戦力は (1) となるため、プラス戦力チームが 3 つ存在することは不可能です。 (n=2) の場合、合計は 3 で割り切れますが、ターゲットは (1) であり、強さ (1) のプレイヤーは 1 人だけなので、答えは変わりません。`Impossible`。 (n=3) の場合、ターゲットは (2) であり、ここでもその合計を持つサブセットは 1 つだけ、つまり ({2}) です。 入力 (n=4) の合計は (10) であり、3 で割り切れないため、直ちに不可能になります。 最初の可能な値は (n=5) で、チームは ({5})、({4,1})、および ({3,2}) となり、すべての強さが (5) になります。 

## アプローチ

 直接的な総当たりソリューションでは、すべてのプレーヤーを 3 つのチームのいずれかに個別に割り当てることができます。 (3^n) 個の代入があります。 割り当てを選択した後、割り当てごとに (O(n)) 個の作業を要し、3 つの合計を計算してそれらが等しいかどうかを確認します。 したがって、最悪の場合の操作数は (n3^n) 程度になります。 (n=30) の場合でも、これはすでに大きすぎますが、実際の制限は (10^6) に達します。 

サブセット検索アプローチの方がわずかに優れているだけです。 必要な合計を持つサブセットとして 1 つのチームを選択し、残りのプレーヤーを分割しようとすることもできますが、サブセットの列挙にはすでに (2^n) のコストがかかります。 プレイヤーの強さが正確に連続する整数 (1,2,\dots,n) であるという事実により、一般的なサブセット合計インスタンスよりもはるかに強力な構造が得られます。 

重要な観察は、6 つの連続する数字に注目することです。 ブロックを考えてみる

 [
 L、L+1、L+2、L+3、L+4、L+5。 
】

 いつでも 3 つのペアに分割できます

 [
 {L+5,L},\qquad
 {L+4,L+1},\qquad
 {L+3、L+2}。 
】

 すべてのペアには合計があります

 [
 2L+5。 
】

 したがって、3 つのチームの強さの平等を変えることなく、6 人の連続プレーヤーの各ブロックをすでに有効なソリューションに追加できます。 つまり、いくつかの小さな開始構成を構築するだけで済みます。 その後、追加の 6 人のプレーヤーごとに同様に処理されます。 

有用な基本構成は特に小さいです。 

[
 \begin{整列}
 n=5 &: {5}、{4,1}、{3,2}、\
 n=6 &: {6,1}、{5,2}、{4,3}、\
 n=8 &: {8,4},{7,5},{6,3,2,1},\
 n=9 &: {9,6}、{8,7}、{5,4,3,2,1}。 
\end{整列}
 】

 チーム合計はそれぞれ(5)、(7)、(12)、(15)です。 

これら 4 つの塩基は、解決策につながる可能性のあるすべての残基クラスをカバーします。 (n\equiv 0\pmod 6) の場合は、(6) から開始します。 (n\equiv2\pmod6) の場合は (8) から開始します。 (n\equiv3\pmod6) の場合は (9) から開始します。 (n\equiv5\pmod6) の場合は (5) から開始します。 (n) の残りの値には剰余 (1) または (4) があるため、それらの合計強度は 3 で割り切れません。 

2 つの例外的な小さな値 (n=2) と (n=3) があり、割り算は成立しますが、分割は存在しません。 したがって、完全な条件は (n\ge5) および

 [
 n\bmod6\in{0,2,3,5}。 
】

 | アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | (O(n3^n)) | (O(n)) | 遅すぎる |
 | 最適な施工 | (O(n)) | (O(n)) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. (n\bmod6) を計算します。 (n<5) の場合、特に注意が必要な候補は (1,2,3,4) だけであり、すべては不可能です。 剰余が (1) または (4) の場合、強さの合計は 3 で割り切れないので、次のように出力します。`Impossible`。 
2. 残留物に応じて小さい塩基を選択します。 剰余 (5) については、(1,\dots,5) の ({5})、({4,1})、および ({3,2}) への分割を使用します。 剰余 (0) には、(1,\dots,6) と ({6,1})、({5,2})、および ({4,3}) を使用します。 剰余 (2) には、(1,\dots,8) と ({8,4})、({7,5})、および ({6,3,2,1}) を使用します。 剰余 (3) には、(1,\dots,9) と ({9,6})、({8,7})、および ({5,4,3,2,1}) を使用します。 
3. しましょう`left`基数に含まれない最初の数値になります。 残りのプレイヤーを 6 人ずつのブロックに分けて処理します。 (L) から始まるブロックの場合、第 1 チームに (L+5) と (L) を、第 2 チームに (L+4) と (L+1) を、第 3 チームに (L+3) と (L+2) を追加します。 各チームは正確に (2L+5) の追加戦力を受け取ります。 
4. (L) を 6 ずつ増やし、すべてのプレーヤーが割り当てられるまで続けます。 基本サイズは (n) と同じ剰余 6 をもつため、残りのプレイヤー数は常に 6 の倍数になります。 
5. 印刷`Possible`そして構築された3つのチーム。 基本合計が等しく、追加された 6 人のプレイヤー ブロックがすべてのチームに同じ金額を貢献するため、それらの合計は等しくなります。 

### なぜ効果があるのか

 不変条件は、ベースと任意の数の完全な 6 人のプレーヤーのブロックを処理した後、3 つのチームすべてがまったく同じ総強さを持ち、処理されたすべてのプレーヤーが正確に 1 つのチームに属するということです。 基数はこの不変条件を直接満たします。 以降のすべてのブロックでは、追加された 3 つのペアの合計は同じ (2L+5) になるため、ブロックを追加すると等価性が維持されます。 基本ブロックとすべての処理済みブロックには最終的に (1) から (n) までのすべてのプレーヤーが含まれるため、最終チームは完全な有効なパーティションを形成します。 

不可能ですが、(n\equiv1) または (4\pmod6) の場合、(n(n+1)/2) は 3 で割り切れないため、等しいチーム合計は存在できません。 5 未満の残りの値は個別にチェックされ、どれも 3 つの同等のポジティブな強さのチームを認めません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())

    if n < 5 or n % 6 in (1, 4):
        print("Impossible")
        return

    r = n % 6

    if r == 5:
        teams = [
            [5],
            [4, 1],
            [3, 2],
        ]
        start = 6

    elif r == 0:
        teams = [
            [6, 1],
            [5, 2],
            [4, 3],
        ]
        start = 7

    elif r == 2:
        teams = [
            [8, 4],
            [7, 5],
            [6, 3, 2, 1],
        ]
        start = 9

    else:  # r == 3
        teams = [
            [9, 6],
            [8, 7],
            [5, 4, 3, 2, 1],
        ]
        start = 10

    left = start

    while left <= n:
        teams[0].extend([left + 5, left])
        teams[1].extend([left + 4, left + 1])
        teams[2].extend([left + 3, left + 2])
        left += 6

    out = ["Possible"]

    for team in teams:
        out.append(str(len(team)))
        out.append(" ".join(map(str, team)))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```最初の条件は、割り算の失敗と小さな例外値の両方を処理します。 チェック中`n < 5`そうしないと (n=2) と (n=3) が割り算テストに合格するため、剰余の前が便利です。 

4 つの基本ケースは、構造の中で唯一真に特別な部分であるため、ハードコーディングされています。 それらのサイズは (5,6,8,9) であり、対応する各剰余は次のことを保証します。`n - start + 1`は6で割り切れます。 

ループは、一度にちょうど 6 人の新しいプレーヤーを処理します。 最初のチームが受け取るのは、`left + 5`そして`left`、2番目は受け取ります`left + 4`そして`left + 1`、3番目は受け取ります`left + 3`そして`left + 2`。 3 つのペアの合計は同じ値になるため、実行中のターゲットの計算は必要ありません。 

Python の整数には任意の精度があるため、概念的に合計を計算するときにオーバーフローの問題は発生しません。 実装では総強度を計算する必要さえないため、構造も単純になります。 

出力では、すべてのプレーヤー番号が 3 つのリストに保存されます。 すべてのプレイヤーは 1 回だけ出現し、(n\le10^6) 回出現するため、保存されるデータの総量は (O(n)) になります。 各リストを一度結合すると、すべての数値を個別に出力するオーバーヘッドが回避されます。 

## 実用的な例

 ### サンプル 1: (n=6)

 剰余は (0) であるため、アルゴリズムは 6 人プレイベースを使用します。 

| ステップ | チーム1 | チーム2 | チーム3 |
 | --- | --- | --- | --- |
 | ベース | (6,1) | (5,2) | (4,3) |
 | 合計 | (7) | (7) | (7) |
 | 残りのプレイヤー | なし | なし | なし |

 3 つの合計はすべて (7) で、(1) から (6) までのすべてのプレイヤーが 1 回だけ発生します。 結果の出力は、最初のサンプルと同じ構造になります。 

### サンプル 2: (n=9)

 余りは(3)なので、9人ベースがそのまま使われます。 

| ステップ | チーム1 | チーム2 | チーム3 |
 | --- | --- | --- | --- |
 | ベース | (9,6) | (8,7) | (5,4,3,2,1) |
 | 合計 | (15) | (15) | (15) |
 | 残りのプレイヤー | なし | なし | なし |

 繰り返しますが、すべてのプレーヤーが 1 回使用され、3 つの合計はすべて等しくなります (15)。 これはまさに 2 番目のサンプルに示されている構造です。 

2 つのサンプルは、合計が 3 で割り切れるかどうかを確認することだけに基づいて解決策を作成しない理由も示しています。 構築には有効な小さな開始パーティションが必要で、その後は 6 人のプレーヤーのブロックの不変条件が引き継ぎます。

 ## 特殊なケース

 (n=1) の場合、アルゴリズムはすぐに出力します。`Impossible`なぜなら、負でない 3 つのチームの合計がすべて同じ (1/3) になることはないからです。 何も構築する必要はありません。 

(n=2) の場合、合計強度は (3) となるため、必要な強度は (1) になります。 強さ (1) を持つ可能なチームは ({1}) だけであり、強さ (1) を持つチームをさらに 2 つ作成する方法はありません。 の`n < 5`残留チェックが誤って受け入れる前に、条件がこれを検出します。 

(n=3) の場合、合計は (6) となり、目標強度は (2) になります。 合計 (2) を持つ唯一のサブセットは ({2}) であるため、そのようなチームを 3 つ形成することはできません。 この場合も、同じ小さい値の条件で処理されます。 

(n=4) の場合、合計は (10) となり、3 で割り切れません。 剰余は (4) であるため、アルゴリズムは次のように出力します。`Impossible`建設を試みることなく。 

(n=5) の場合、特別な塩基は次のようになります。 

[
 {5}、\クワッド{4,1}、\クワッド{3,2}。 
】

 どのチームにも強みがあります (5)。 これは可能な最小の有効な入力であり、有効なケースのリストに残基 (5) を含める必要がある理由も説明されています。 

(n=8) の場合、塩基は次のようになります。 

[
 {8,4}、\クワッド{7,5}、\クワッド{6,3,2,1}。 
】

 各チームには強さ（12）があります。 このケースは、6 の倍数を構築する方法しか知らない実装を捉えています。 

(n=11) の場合、アルゴリズムは 5 人のプレーヤーの構築から開始し、ブロック (6,\dots,11) を処理します。 そのブロックは、

 [
 {11,6}、\クワッド{10,7}、\クワッド{9,8}、
 】

(n=10^6) の場合、剰余は (4) なので、答えはすぐに得られます。`Impossible`。 最大入力が必ずしも大きな出力を意味するわけではないため、これは便利です。 このアルゴリズムは、100 万要素の構造を不必要に割り当てるのではなく、一定時間内にそれを拒否します。
