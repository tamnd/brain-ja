 ## 解決策
 ## 問題の理解

 このプロセスは単一のエンティティから始まり、分単位で測定される離散時間ステップにわたって進化します。 毎分、一定数の新しいエンティティが現在の合計に追加されます。 追加される数を制御するルールはステップごとに独立しているのではなく、直前の 1 分間に追加された数によって異なります。 

で表すと$a_m$1分間に作成された新しいuxionの数$m$の場合、問題は、分のインデックスが奇数か偶数かに応じて増分の動作が交互になる繰り返しを定義します。 システムは、ちょうど 1 つの uxion がすでに存在する状態で 0 分に始まり、その初期状態を超えると以前の成長履歴は意味を持ちません。 

各クエリの出力は、クエリ後に存在する uxion の合計数です。$M$minutes、つまり 1 分から 1 分までのすべての増分を累積します。$M$, 最初の1から始めます。 

制約$M \le 60$競技プログラミングの観点からは非常に小さいです。 これにより、定数または線形の前処理を超えた漸近的な最適化の必要性が即座に排除されます。 たとえ$O(M)$すべてのテスト全体で最悪の場合でも最大約 3600 回の操作が発生するため、テスト ケースごとのシミュレーションは非常に高速です。 

微妙な落とし穴は、「成長量」自体が進化して再利用されることを忘れていることです。 毎分独立して何か固定されたものを2倍にするかコピーするという単純な解釈は、不正確なシーケンスにつながります。 たとえば、偶数分ごとに常に 1 分からの元の増分が 2 倍になると仮定すると、シーケンスは意図した交互の繰り返しからすぐに外れてしまいます。 

2 番目の問題は、初期値を正しく処理しない場合に発生します。 分 0 にはすでに 1 uxion が含まれているため、最初の増分は以前の「成長履歴」のない基本状態から開始されるため、最初のデルタを一貫して定義することが重要です。 

具体的な失敗例は、ルールを「奇数分に 1 を追加し、偶数分に 2 を追加する」と解釈することです。これにより、線形パターンが生成されます。 のために$M = 4$、これは与えるでしょう$1 + (1 + 2 + 1 + 2) = 7$、正解は 10 ですが、増分自体が進化する必要があることを示しています。 

## アプローチ

 ブルートフォース手法では、現在の合計と最後に追加された増分の両方を維持しながら、分ごとにシミュレーションを行います。 各ステップで、現在の分が奇数か偶数かに基づいて次の増分を計算し、それを合計に加算します。 これはステートメントを直接反映しており、繰り返しを圧縮したり近似したりすることがないため、正しいです。 

非効率性は次の場合にのみ現れます。$M$大きかった。 各テストケースには次のことが必要です$O(M)$アップデート、そして全体にわたって$T$こうなる場合$O(T \cdot M)$。 どちらも 60 で制限されているため、これは最大でも数千回の操作になります。 

重要な観察は、プロセスでは前のステップ以降の値に依存するものは何もないということです。 これは純粋な 1 次再帰であるため、オプションのプレフィックス充填を超える高度なデータ構造や事前計算による利点はありません。 この構造は本質的には決定論的なシーケンス生成問題です。 

必要以上に高速な最適化では、60 までのすべての値を 1 回事前計算し、クエリに応答します。$O(1)$、しかし、それさえも、パフォーマンスの必要性よりも、コードのクリーンさに関するものです。

 ## アルゴリズムのチュートリアル

 1. 初期合計を 1 に設定して開始します。これは、分 0 における単一の uxion を表します。また、分 1 で前の状態からちょうど 1 単位の増加が追加されるため、最初の「増加増分」を 1 に初期化します。 
2. 1 からクエリの最大値まで分ごとに繰り返します。$M$。 各ステップで、パリティに基づいて増分がどのように変化するかを決定します。 
3. 現在の分が奇数の場合は、増分を前の分から変更しないでください。 これは、奇数分に前の増加量を繰り返すというルールを反映しています。 
4. 現在の分が偶数の場合、前の増分を 2 倍にします。 これにより、偶数分間指定された高速レプリケーション動作がキャプチャされます。 
5. 現在の分の増分を決定したら、それを uxion の合計数に追加します。 
6. 各クエリにすぐに回答できるように、毎分後の合計を配列に保存します。 
7. 各テスト ケースについて、そのテスト ケースに対応する事前計算された合計を出力します。$M$。 

### なぜ効果があるのか

 このアルゴリズムは、現在の合計と最後の増分という 2 つの状態を正確に追跡します。 問題定義により、将来の展開がこれら 2 つの値のみに依存することが保証されるため、これら 2 つがシステムの完全な状態記述を形成します。 隠れた依存関係なしに、毎分この状態を次の状態に決定論的に変換するため、シミュレーションによって計算されたシーケンスは、すべてのプロセスに対して一意に実際のプロセスと一致します。$M$。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAX_M = 60

# precompute answers
total = [0] * (MAX_M + 1)

# minute 0
total[0] = 1

# last increment
inc = 1

for m in range(1, MAX_M + 1):
    if m == 1:
        inc = 1
    else:
        if m % 2 == 0:
            inc *= 2
        # odd minute: inc stays the same

    total[m] = total[m - 1] + inc

t = int(input())
for _ in range(t):
    m = int(input())
    print(total[m])
```コードは再発を直接反映しています。 配列`total`は毎分ごとに uxion の累積数を保存するため、各クエリは定数時間のルックアップになります。 

変数`inc`現時点で追加された新しい uxion の数を表します。 それはその場で更新されます。偶数ステップでは 2 倍になり、奇数ステップでは変更されず、交互のルールに正確に一致します。 最初の 1 分は明示的に処理されるため、繰り返しの開始増分は明確に定義されます。 

よくある間違いは、増分を更新する前に合計を更新することです。これにより、シーケンスが 1 分ずれます。 正しい順序は、まず現在の分の増分を決定し、それを累積合計に適用することです。

## テストケース```python
import sys, io

def solve(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    MAX_M = 60
    total = [0] * (MAX_M + 1)
    total[0] = 1
    inc = 1

    for m in range(1, MAX_M + 1):
        if m == 1:
            inc = 1
        else:
            if m % 2 == 0:
                inc *= 2
        total[m] = total[m - 1] + inc

    t = int(input())
    out = []
    for _ in range(t):
        m = int(input())
        out.append(str(total[m]))
    return "\n".join(out)

# provided samples
assert solve("4\n1\n2\n3\n4\n") == "2\n4\n6\n10"

# custom cases
assert solve("1\n0\n") == "1", "minimum case"
assert solve("1\n4\n") == "10", "small recurrence check"
assert solve("3\n2\n3\n4\n") == "4\n6\n10", "monotonic progression"
assert solve("2\n60\n59\n") == solve("2\n60\n59\n"), "consistency check"
```| テスト入力 | 期待される出力 | 検証内容 |

 ## 特殊なケース

 いつ$M = 0$、成長は起こらず、答えは正確に初期のuxion数になります。 アルゴリズムはこれを処理します。`total[0]`明示的に 1 に設定され、変更されることはありません。 

のために$M = 1$、最初の増分のみが適用されます。 このロジックにより、増分は使用前に初期化されるため、出力は 2 になります。 

境界線に向けて$M = 60$、偶数分での 2 倍化の繰り返しは、Python では依然として安全な整数制限内に収まりますが、固定幅言語では、これがオーバーフローに関する考慮事項が重要になる場所です。 シミュレーションは近似や浮動小数点演算に依存しないため、正確なままです。 

よくある間違いは、1 分からではなく 0 分からループを開始することです。これにより、すべてのパリティ ベースの遷移がシフトされ、まったく異なるシーケンスが生成されます。 段階的な構造では、分 0 を固定の初期状態として固定することで、それを防ぎます。
