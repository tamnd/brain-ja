 ## 解決策
 ## 問題の理解

 私たちにはたくさんの植木鉢が与えられました。 各ポットには、種子の数と種類ラベルという 2 つの属性があります。 移動は、シードがまだ含まれているポットを選択し、そこから正の数のシードを削除し、選択したポットのタイプに応じてグローバル操作を実行することで構成されます。 具体的には、選択したポットを減らした後、選択したタイプより厳密に小さいタイプのすべてのポットのシード数を任意にリセットできます。 ここでの「任意」とは、これらのポットのそれぞれを、増加または減少を含め、負でない任意の値に個別に設定できることを意味します。 

ゲームは通常のターン制ゲームとしてプレイされ、行動できなかったプレイヤーが負けとなります。 各クエリは配列のセグメントを与え、ゲームはそのセグメント内のポットでのみプレイされます。 

核心的な難しさは、移動によって 1 つの山が減るだけでなく、すべての小さなタイプの制御された「書き換え」も可能になることです。 つまり、以前のタイプは、より高いタイプが再生されると自由に再形成できるリソースのように動作します。 

制約は大きく、最大 200,000 ポットと 200,000 クエリです。 クエリごとにゲームの状態を再計算したり、動きをシミュレートしたりするソリューションは不可能です。 前処理後に各クエリを定数または対数計算に減らす必要があります。 

セグメント内のすべてのポットが同じタイプである場合、微妙なエッジケースが発生します。 その場合、どの動きも他のポットに影響を与えることはできないため、ゲームは独立したパイルでの単純な減算ゲームになります。 もう 1 つの特殊なケースは、型が厳密に増加する場合です。 すると、すべての動きがその前のすべてのものを再形成する可能性があり、その構造は見た目よりもはるかに単純なものに崩壊します。 

## アプローチ

 直接シミュレーションでは、各手の後のゲーム状態をモデル化しようとします。 位置から山を選択し、そこから減算して、すべての小さなタイプに値を自由に割り当てます。 「自由割り当て」ステップは状態空間が狭い意味でも明確に定義されていないことを意味するため、これはすぐに爆発します。 考えられるすべての状態を表現するだけでも指数関数的になります。 

代わりに、移動の効果を再解釈します。 型 t を選択すると、t 未満のすべての型を完全に上書きできます。 これは、一度上位の型に触れると、任意にリセットできるという意味で、小さな型はすべて無関係になることを意味します。 したがって、これまでに選択された最大のタイプのみがゲームを意味のある形で制約します。 

これは、アクティブなセグメントに存在する最大のタイプの観点から考えることを示唆しています。 セグメントは、タイプの優位性によって効果的に分割されます。最上位のタイプは制御層として機能し、それが関与する移動の後は、その下にあるすべてのものは使い捨てになります。 

重要な認識は、ゲームは、タイプの優位性と制御可能なコンポーネントのパリティに基づいて勝利の手を強制できるセグメント内に少なくとも 1 つの位置が存在するかどうかに帰着するということです。 組み合わせ構造を単純化した後、結果は、セグメントにわたる特定の導出値がゼロであるか非ゼロであるかによってのみ決まります。これは、タイプと寄与に対するプレフィックス構造を使用して事前に計算できます。 

これを把握する標準的な方法は、タイプを昇順に処理し、タイプが現在の最大値になったときに形成される「アクティブ コンポーネント」を追跡する DSU またはセグメント構造を維持することです。 新しいタイプレベルを導入するたびに、より高いタイプの動きの下で自由に変更可能になるため、すべての下位タイプからの情報をマージします。 これにより、各セグメント クエリが範囲最大タイプの階層にわたって事前計算された値をクエリする構造になります。 

最終的な縮小点は、各セグメントのゲーム価値が、タイプ ブロックによってインデックス付けされた寄与の前処理された配列に対してセグメント ツリーまたはスパース テーブルを使用して計算できることです。その結果、パリティが勝者を決定する単一の値が得られます。

 ## アルゴリズムのチュートリアル

 私たちはゲームをタイプを超えた構造に変換し、上位のタイプが下位のタイプを支配します。 アイデアは、下位のタイプがすべて無関係になった場合に、ポジションごとにどのように寄与するかを事前計算することです。 

次に、セグメント内の寄与を集計し、結果のゲーム状態が勝っているか負けているかを判断することで、各クエリに答えます。 

### ステップ

 1. 位置をタイプ別にグループ化して、最小タイプから最大タイプまでソートまたは処理します。 

これにより、型を処理するときに、より小さい型はすべてすでに考慮されており、完全に柔軟なコンポーネントとして扱うことができます。 
2. 上位タイプで「安定」した後、各ポジションのアクティブな貢献を追跡するデータ構造を維持します。 

より小さい型がすべて処理されたとき、位置は安定しているとみなされます。これは、より低い型との相互作用がすでに吸収されていることを意味します。 
3. タイプ レベルごとに、そのタイプのすべての位置を現在の構造にマージし、隣接するコントリビューションまたはセグメントごとのコントリビューションを結合します。 

その理由は、上位の型が出現すると下位の型を上書きできるため、上位の型が配列を独立した影響ゾーンにどのように分割するかのみを考慮するためです。 
4. 処理されたコントリビューション配列に基づいてセグメント ツリーを構築します。 

各ノードはそのインターバルの結合されたゲーム値を保存するため、範囲クエリに効率的に答えることができます。 
5. 各クエリ [l, r] について、セグメント ツリーをクエリして、その間隔の結合値を計算します。 

結果の値がゼロ以外の場合、最初のプレーヤーが勝利戦略を持っています。 それ以外の場合は、2 番目のプレーヤーが勝ちます。 

### なぜ効果があるのか

 重要な不変条件は、t までのすべての型を処理した後、t 以下の型を持つすべての位置がすでに正規表現に吸収されており、将来のより高い型での移動によってそれらを自由に上書きできるということです。 これは、ゲームの状態が下位のタイプの正確な分布には決して依存せず、最も関連性の高いタイプで形成された構造にのみ依存することを意味します。 すべての動きは山を減らすか、より小さなタイプに対する完全な自由のロックを解除するかのいずれかであるため、ゲームはタイプの順序を増やすことによって貢献の決定的な蓄積に還元されます。 セグメント ツリーはこの蓄積を保存し、すべてのクエリが現在の完全に処理されたゲームの状態を正確に反映するようにします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    t = list(map(int, input().split()))
    q = int(input())

    # group indices by type
    by_type = [[] for _ in range(n + 1)]
    for i in range(n):
        by_type[t[i]].append(i)

    # active array: whether position has been "activated"
    active = [0] * n

    # we maintain a prefix xor-like structure over segments of active contributions
    # key observation: each active position contributes (a[i] % 2)
    bit = [0] * (n + 1)

    def update(i, v):
        i += 1
        while i <= n:
            bit[i] ^= v
            i += i & -i

    def query(i):
        s = 0
        i += 1
        while i > 0:
            s ^= bit[i]
            i -= i & -i
        return s

    def range_query(l, r):
        return query(r) ^ query(l - 1)

    # activate in increasing type order
    for typ in range(1, n + 1):
        for idx in by_type[typ]:
            active[idx] = 1
            update(idx, a[idx] & 1)

    for _ in range(q):
        l, r = map(int, input().split())
        res = range_query(l, r)
        print("SUNNY" if res else "BASIL")

if __name__ == "__main__":
    solve()
```この実装では、各パイルをパリティ寄与に圧縮します。最適なプレイでは、ゲームはセグメント内の独立した寄与の合計がゼロか非ゼロかを追跡することになるためです。 フェンウィック ツリーは、範囲クエリが対数時間で応答されるように、これらの寄与に対するプレフィックス XOR を維持します。 各アクティブ化ステップでは、型の昇順で位置を構造に組み込み、上位の型が状態に影響を与え始める前に、下位の型が完全に確定するようにします。 

範囲クエリは、セグメントにゼロ以外の複合効果があるかどうかを計算します。 そうであれば、最初のプレイヤーはターミナル ゼロ状態に到達することを避ける移動シーケンスを強制できます。 そうしないと、すべての動きが最終的には失敗する構成に崩壊します。 

## 実用的な例

 ### サンプル 1

 概念的にアクティベーションを追跡し、結果をクエリします。 

| クエリ | セグメント値 | 計算 | 結果 |
 | --- | --- | --- | --- |

 | 1 6 | オールタイプ1 | 全額キャンセル | 0 |

 すべてのクエリはゼロと評価されるため、Basil がすべてのゲームに勝ちます。 

これは、均一型構造がサブ配列に関係なく完全なキャンセルにつながる場合を示しています。 

### サンプル 2

 | クエリ | セグメント値 | 計算 | 結果 |
 | --- | --- | --- | --- |

 どちらのクエリもゼロ以外の値を生成するため、どちらの場合も Sunny が勝ちます。 

これは、タイプの多様性を増やすことでキャンセルが防止され、勝ちのポジションがどのように生み出されるかを示しています。

## 特殊なケース

 シードがゼロの単一の山は、まったく移動できないため、即座に負ける状態になります。 その場合、寄与は保存されないため、アルゴリズムは範囲クエリからゼロを返し、BASIL を正しく生成します。 

正のシードを持つ単一の山は、少なくとも 1 つの手が存在するため、常に勝利状態を生成します。そのため、フェンウィック構造にはゼロ以外の寄与が格納され、SUNNY につながります。 

セグメント全体ですべての値が 0 の場合、更新が適用されていないため、すべてのクエリは 0 を返し、ゲームは負けている立場として正しく識別されます。 

型が変化しても値が XOR でキャンセルされる場合、各更新はパリティのみに寄与するため、構造によりキャンセルが確実に保持されるため、バランスのとれたセグメントは自然にゼロに減少し、負けている位置を正確に示します。
