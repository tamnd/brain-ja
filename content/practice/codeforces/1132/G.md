 ## 解決策
 ## 問題の理解

 整数の長い配列と固定ウィンドウ サイズが与えられます。 連続する長さのセグメントごとに`k`、インデックスのサブシーケンスを構築する非常に特殊なプロセスをシミュレートするように求められます。 

セグメント内の任意の位置から開始して、現在の値より厳密に大きい値を持つ右側の次の出現箇所に繰り返しジャンプします。 重要なのは、ジャンプは任意ではないということです。 インデックスから`p`、次のインデックスは、値が増加する右側の最小位置として一意に定義されます。 これにより、開始位置が固定されると、サブシーケンスが決定的になります。 

各ウィンドウについて、そのウィンドウ内で開始インデックスを最適に選択した場合に、このような貪欲なプロセスにどれくらいの時間がかかるかを知りたいと考えています。 

制約は極端です。配列の長さは 100 万に達する可能性があり、ウィンドウは配列のほぼ全体にわたってスライドします。 各ウィンドウを個別に処理し、対数的なオーバーヘッドを伴うソリューションは遅すぎます。 これにより、すべての位置について欲張りチェーンを最初から再計算することが直ちに排除されます。 

値が繰り返される場合、または局所的な増加がまばらな場合、微妙な問題が発生します。 素朴な直観は、これが各ウィンドウ内の最長増加部分列問題であることを示唆するかもしれませんが、「貪欲な次に大きな要素」ルールにより、構造的に異なります。 次の要素の選択は強制されるため、サブシーケンスの選択は最適化されず、開始点のみが最適化されます。 

単純な推論の一般的な失敗ケースは、極大値が右端のはるかに大きな値に近い場合です。 

たとえば、次のようなウィンドウで`[3, 1, 2, 100, 4]`、から始まります`3`すぐにジャンプします`100`で開始しながら、短いチェーンを与えます。`1`より長いチェーンが得られます`1 → 2 → 100`。 常にウィンドウ内の最大値から開始しようとする単純なアプローチでは、このようなケースを見逃してしまいます。 

本当の課題は、ウィンドウをスライドさせながら多くの開始点を効率的に評価しなければならないことです。 

## アプローチ

 ブルートフォース ソリューションでは、ウィンドウごとに、ウィンドウ内のすべてのインデックスから貪欲なプロセスをシミュレートします。 各開始位置から右に繰り返しスキャンして、次に厳密に大きい要素を見つけます。 各スキャンは最悪の場合でも線形であるため、1 回のシミュレーションは O(k) ですが、すべての開始に対してそれを実行すると、ウィンドウごとに O(k²) になります。 最大 O(n) ウィンドウの場合、最悪の場合、およそ O(n³) になると、これは完全に不可能になります。 

重要な観察は、貪欲なプロセスは配列の「次に大きい要素」構造のみに依存しているということです。 すべてのインデックスについて、次にどこにジャンプするかがわかると、任意の開始点からのシーケンスの長さは、各ノードが最大 1 つの出力エッジを持つ有向グラフ内の単純なチェーン長になります。 

したがって、問題は 2 つの部分に分かれます。 まず、すべての位置について次に大きい要素インデックスを計算します。 次に、ウィンドウごとに、チェーン全体がそのウィンドウ内に留まるインデックスから始まる最長のチェーンを決定します。 

最初の部分は、O(n) での古典的な単調スタック計算です。 2 番目の部分は、チェーンがウィンドウから出る可能性があり、現在のセグメント内に残っているジャンプのみをカウントするようにする必要があるため、より複雑です。 これは、ジャンプ ポインタを前処理し、バイナリ リフティング テーブルまたは同等のジャンプ圧縮を使用することで処理され、ウィンドウ内に留まるチェーンのセグメントを効率的に「スキップ」できます。 最終的な構造では、線形前処理の後、実装に応じて各ウィンドウをほぼ O(1) または O(log n) で処理できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n·k²) | お(1) | 遅すぎる |
 | 単調スタック + ジャンプ前処理 | O(n log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべてのインデックスを計算する`i`次の位置`nxt[i]`そのような右に`a[nxt[i]] > a[i]`。 これは、単調減少スタックを使用して行われます。 スタックにより、次に大きな要素が常に線形時間で解決されることが保証されます。 
2. ジャンプ構造を構築する`nxt`。 各位置には出力エッジが最大 1 つあるため、それを関数グラフとして扱います。 バイナリリフティングテーブルを事前計算します`up[i][j]`、適用した結果を意味します`2^j`から始まる貪欲なジャンプ`i`。 
3. ジャンプと同時に、ジャンプ後に到達可能な最大の位置を維持します。 これが必要なのは、チェーンが現在のウィンドウから出ないようにする必要があるためです。 
4. ウィンドウごとに`[l, r]`、可能なすべての開始位置を評価します`i`で`[l, r]`。 スタートごとに、範囲内に留まる最高のバイナリ リフティング ステップを使用してジャンプを繰り返し試行します。`r`。 ジャンプが成功するたびに、それに応じてチェーンの長さが増加します。 
5. ウィンドウ内のすべてのスタートにおける最大チェーン長を追跡します。 

重要な最適化は、貪欲なチェーンに沿って一歩ずつ歩くのではなく、事前に計算された指数関数的なジャンプを使用して、境界内に留まりながら大部分をスキップすることです。 

### なぜ効果があるのか

 次の要素が一意に定義されるため、各インデックスは一意の貪欲チェーンを決定的に定義します。 これにより、構造は互いに素な順方向パスの集合となります。 バイナリ リフティングでは、繰り返される遷移を圧縮しながら、これらのパスに沿った到達可能性を維持します。 すべてのジャンプは値を厳密に増加させるため、サイクルは存在できず、各チェーンは有限です。 正確さは、貪欲なサブシーケンスが正確に、`nxt`関数。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, k = map(int, input().split())
a = list(map(int, input().split()))

# next greater element
nxt = [n] * n
stack = []

for i in range(n):
    while stack and a[stack[-1]] < a[i]:
        nxt[stack.pop()] = i
    stack.append(i)

LOG = 20
up = [[n] * n for _ in range(LOG)]
up[0] = nxt[:]

for j in range(1, LOG):
    for i in range(n):
        if up[j-1][i] < n:
            up[j][i] = up[j-1][up[j-1][i]]
        else:
            up[j][i] = n

def get_len(i, r):
    if i > r:
        return 0
    cnt = 1
    cur = i
    for j in reversed(range(LOG)):
        nxt_pos = up[j][cur]
        if nxt_pos <= r:
            cnt += 1 << j
            cur = nxt_pos
    return cnt

res = []
for l in range(n - k + 1):
    r = l + k - 1
    best = 0
    for i in range(l, r + 1):
        best = max(best, get_len(i, r))
    res.append(str(best))

print(" ".join(res))
```この解決策は、単調スタックを使用して次に大きい要素配列を計算することから始まります。 各要素は最大 1 回プッシュおよびポップされるため、線形な前処理が保証されます。 

バイナリリフティングテーブル`up`そのように構築されています`up[j][i]`ジャンプの結果を表します`2^j`次に大きなチェーンに沿って回数を増やします。 これにより、ウィンドウ内でチェーンがどこまで伸びるかを評価する際に、対数ステップで多くの遷移をスキップすることができます。 

機能`get_len(i, r)`インデックスから取得できる貪欲なジャンプの数を計算します`i`正しい境界線を離れることなく`r`。 これは、最大の有効なジャンプを最初に貪欲に適用します。これは、チェーンが厳密に増加しており、非循環であるため機能します。 

最後に、各ウィンドウがスキャンされ、ジャンプ機能を使用してすべての開始位置がテストされます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、最適な開始点がウィンドウの終わり近くにあるにもかかわらず、内部に残るロング ジャンプ チェーンにつながる場合です。 たとえば、`[1, 100, 2, 3, 4]`、インデックス 3 から開始すると、インデックス 1 から開始するよりも長い有効なチェーンが生成されます。アルゴリズムはウィンドウ内のすべての開始位置を評価し、バイナリ リフティングは開始ランクには依存せず、範囲内の到達可能性にのみ依存するため、これを正しく処理します。 

もう 1 つのエッジ ケースは、次に大きい要素がウィンドウの外側にある場合です。 その状況では、有効な継続がグローバルに存在する場合でも、チェーンは早期に終了します。 の`get_len`関数は境界を明示的にチェックします`r`、ウィンドウを出るジャンプがカウントされないことを保証し、すべてのサブセグメントの正確さを独立して保持します。
