 ## 解決策
 ## 問題の理解

 固定された順序で到着する生徒のシーケンスが与えられ、各生徒は特定の数のピザのスライスを消費します。 K 枚のピザが準備されており、すべてのピザは同じ数のスライスを持つ必要があり、この値を X と呼びます。ピザは次々に提供されます。各生徒は可能であれば現在のピザから必要な数のスライスを取り出しますが、残りのスライスが十分でない場合は、現在のピザはすぐに破棄され、その生徒のために新しいピザが開かれます。 

目標は、K 個以上のピザを必要とせずにすべての生徒にサービスを提供できるように、可能な限り小さい X を選択することです。 

重要な点は、プロセスが貪欲かつ直線的であることです。各生徒は現在の状況に適合するか、強制的にリセットされます。 つまり、使用されるピザの数は、プレフィックスの合計が X の倍数を超える頻度によって完全に決まります。 

この制約では、最大 100,000 人の学生と 100,000 個のピザが許可されるため、すべての候補 X 値を試し、それぞれについて単純にシミュレーションするソリューションは遅すぎます。 要求が 10^6 に達し、合計が 10^11 に達する可能性があるため、すべての要求の合計まで X を総当たりで処理することは不可能です。 候補者ごとのリニアスキャンでも制限時間を超えてしまいます。 

1 人の生徒が X を超える要求をした場合、微妙なエッジ ケースが発生します。その場合、現在のモデルでは、生徒に焼きたてのピザを与えることを意味しているため、X は常に少なくとも max(d_i) でなければなりません。 もう 1 つのエッジ ケースは、K が十分に大きいため、非常に小さな X でも機能する可能性がありますが、最小の X が単なる合計ではなく、シーケンス内の局所的な「オーバーフロー ポイント」によって依然として制約される場合です。 

## アプローチ

 直接的なアプローチは、値 X を推測し、提供プロセスをシミュレートすることです。 固定 X の場合、生徒を反復処理し、現在のピザの残りのスライスを追跡し、使用されたピザの数をカウントします。 生徒が収まらないときは、新しいピザを作り始めます。 このシミュレーションは X あたり O(N) です。 

難しいのは X を選択することです。X は少なくとも max(d_i)、最大でも sum(d_i) であるため、それを二分探索できます。 ただし、実現可能性関数は単調です。特定の X が機能する場合、より大きな X も機能します。これは、ピザが大きくても休憩の数が増加することはないためです。 この単調性により、X に対する二分探索が可能になります。 

重要な洞察は、実現可能性は、欲張りパッキングによって最大 K 個のセグメントが生成されるかどうかによってのみ決まるということです。各セグメントは、合計が X を超えない連続する生徒のグループです。セグメントが X を超えると、強制的にカットされます。 したがって、X をチェックするということは、作成されたそのようなセグメントの数を数えるということになります。

 | 二分探索 + 貪欲チェック | O(N 対数合計(d)) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 関数を定義します`can(X)`各ピザに X 枚のスライスがある場合、K 枚のピザで十分かどうかを返します。 

1. ピザの使用量がゼロ、現在のピザの残量がゼロの状態から開始します。 

概念的には、これをまだピザを開いていないものとして扱います。 
2. 生徒を順番に繰り返します。 

要求 d_i を持つ生徒ごとに、現在のピザにそれらを当てはめてみます。 
3. 現在のピザに少なくとも d_i 枚のスライスが残っている場合は、そこから d_i を減算します。 

このモデルは、新しいピザを開けずに提供します。 
4. それ以外の場合は、この生徒のために新しいピザを開かなければなりません。 

ピザの枚数を 1 つ増やし、残りの容量を X に設定し、d_i を減算します。 
5. いずれかの時点で 1 人の生徒が d_i > X の場合は、すぐに false を返します。 

これが必要なのは、たとえ焼きたてのピザでも、そうでないと満足できないからです。 
6. すべての生徒を処理した後、使用されたピザの合計が K 以下であるかどうかを返します。 

一度`can(X)`が定義されている場合、max(d_i) と sum(d_i) の間で X を二分探索し、次のような最小の X を選択します。`can(X)`それは本当です。 

これが機能する理由: それぞれの固定 X は、配列の決定論的な貪欲なセグメンテーションを定義します。 X を増加させるとセグメントはマージのみ可能で、分割はできません。そのため、使用されるピザの数は X において単調に増加しません。これにより、二分探索の正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(a, k, x):
    used = 1
    rem = x
    for v in a:
        if v > x:
            return False
        if rem >= v:
            rem -= v
        else:
            used += 1
            rem = x - v
            if used > k:
                return False
    return used <= k

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))

    lo = max(a)
    hi = sum(a)

    while lo < hi:
        mid = (lo + hi) // 2
        if can(a, k, mid):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```このソリューションでは、実現可能性のチェックと X の検索を分離します。`can`この機能は、ピザがどのように消費されるかを正確にシミュレートし、残りのスライスを追跡し、必要なピザの数をカウントします。 

よくある間違いは、合わない生徒がピザを部分的に食べずに残りを食べて、すぐに焼きたてのピザを強制することを忘れていることです。 だからこそリセットするのです`rem = x - v`残った容量を前に持ち越そうとするのではなく。 

もう 1 つの微妙な点は初期化です`used = 1`。 ピザを開けるのは必要なときだけですが、最初の生徒は到着したら必ず存在するピザから食べます。

 ## 特殊なケース

 エッジ ケースの 1 つは、K が N に比べて非常に大きい場合です。`N = 5, K = 100`、答えは単純に max(d_i) です。 二分探索は lo = max(a) で開始されるため、アルゴリズムはこれを処理します。`can(lo)`生徒が定員を超えることはなく、必要に応じて生徒全員が焼きたてのピザに収まるので、すぐに成功します。 

もう 1 つの特殊なケースは、すべての需要が同一である場合です。 のために`a = [3,3,3,3]`の場合、候補 X = 3 では、生徒 1 人につき 1 枚のピザが得られるため、4 枚のピザが使用されます。 実現可能性チェックは正しくインクリメントされます`used`減算後に残りがゼロになるたびに、アンダーカウントが発生しないようにします。 

最後のエッジ ケースは、中央に 1 つの大きなスパイクがあるシーケンスです。 のために`a = [1,1,100,1,1]`、X < 100 は明示的なチェックにより直ちに失敗します。`if v > x`。 これにより、シミュレーションが不可能なリクエストを部分的に処理しようとする誤った試みが防止され、バイナリ検索が無効な範囲に逸脱することがなくなります。
