 ## 解決策
 ## 問題の理解

 私たちは、処理と呼ばれる共有リソースの下で 2 つの順序付けられたアクティビティのリストが注目を集めるために競合する、非常に特殊な休暇ルーチンをシミュレートしています。 ウィリアムは、気質ポイントの初期予算から始めて、気質を消費する疲れるアクティビティと、気質を回復する爽快なアクティビティという 2 つのキューに直面します。 

このプロセスは貪欲かつステートフルです。 あらゆる瞬間に、次の未実行の疲れるアクティビティと、次の未実行の爽快なアクティビティへの指示が存在します。 ウィリアムはいつも次の面倒な作業を最初に実行しようとします。 もしその人がそのコストを支払うのに十分な気質を持っているなら、彼はそれを実行し、自分の気質を減らします。 余裕がなければ、気分を高揚させる活動に切り替えて次の活動を行い、気質を高めます。 疲れるアクティビティがなくなると、残っている爽快なアクティビティを順番に実行するだけです。 

出力は、両方のリストが使い果たされたか、それ以上の進行が不可能になったためにプロセスが自然に停止する前に実行されたアクティビティの合計数です。 

制約は、両方のリストが適度に大きく、それぞれ最大 10^4 であるのに対し、配置は最大 10^5 であることを示しています。 これにより、繰り返し逆方向にスキャンしたり、ネストされた方法で決定を再試行したりするシミュレーションは直ちに除外されます。 各アクティビティは最大 1 回しか消費されず、決定はローカルであるため、両方のシーケンスにわたる線形パスで十分です。 

微妙な失敗のケースは、素朴なシミュレーションが誤って決定を再検討する場合、または一度疲れるアクティビティが手の届かないものになると、それは永遠に無理なままであるとアルゴリズムが想定する場合に発生します。 元気を与えるステップは気質を高める可能性があるため、これは誤りです。 

たとえば、次のことを考えてみましょう。```
D = 10
C = 2: [15, 5]
R = 1: [20]
```素朴な貪欲な人は、「15 は不可能だから、5 まで飛ばして」と構造を間違って理解するかもしれません。 正しい動作は次のとおりです。15 はできないので、爽快な 20 を取得してから続行する必要があります。 

もう 1 つのエッジ ケースは、将来の疲れるアクティビティを解放するのに、爽快なアクティビティが不十分なため、プロセスが行き詰まって、慎重に正しく切り替えなければ進歩が不可能なパターンに陥る場合です。 

## アプローチ

 ブルートフォース解釈は文字通りプロセスをシミュレートします。各ステップで、次の面倒なアクティビティを実行できるかどうかを確認します。 「はい」の場合、私たちはそれを消費します。 そうでない場合は、次の元気を与える活動を実行します。 これはルールに直接一致しており、正しいです。なぜなら、決定は現在の性質と次に利用可能なアクティビティにのみ依存するからです。 

問題はパフォーマンスです。 各ステップは O(1) ですが、C + R までのステップがあるため、これは線形に見えます。 ただし、冗長なスキャンを引き起こす方法で手頃な価格を繰り返しチェックしたり、リスト間で素朴なバックトラッキングを試みたりすると、微妙な非効率が生じます。 不用意に実装すると、事実上二次関数となるループ構造の各爽快なアクションの後に、うんざりする実現可能性を繰り返し再評価する可能性があります。 

重要な観察は、両方のポインターが前方にのみ移動することです。 各アクティビティは 1 回だけ使用されます。 これは、ロールバックや繰り返しスキャンを行わずに、現在の配置を維持しながら単一パスで安全にシミュレーションできることを意味します。 

必要な実際の構造は、リストごとに 1 つずつの 2 つのインデックスと、O(1) で次のアクションを常に決定するループだけです。 貪欲ルール自体は、すでに決定的なパスを定義しています。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション (不注意な繰り返しチェック) | O((C+R)^2) 最悪の場合 | お(1) | 遅すぎる |
 | 2 ポインター貪欲シミュレーション | O(C+R) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ステップ

 1. 2 つのポインタを初期化し、1 つは疲れるリストの先頭に、もう 1 つは爽快なリストの先頭に配置し、現在の処理を D に設定します。また、実行されたアクティビティのカウンタも初期化します。 
2. いずれかのリストに未処理のアクティビティがまだ残っている間に、次の面倒なアクティビティが存在する場合は、そのアクティビティの実行を試みます。 
3. 疲れるアクティビティが存在し、そのコストが現在の処理を超えていない場合は、そのコストを減算し、疲れるポインタを進め、カウンタをインクリメントします。 私たちは常に疲れるアクティビティを優先するため、すぐにループを続けます。 
4. 疲れるアクティビティはあるものの、費用がかかりすぎる場合は、爽快なリストに切り替えて、可能な場合は次のアクティビティを実行します。 その値を性質に追加し、そのポインタを進め、カウンタをインクリメントします。 
5. 爽快なアクティビティは残っていないが、疲れるアクティビティはまだ手が出せない場合、それ以上のアクションは不可能であるため、プロセスは停止します。 
6. 疲れるアクティビティを使い果たした場合は、残りの爽快なアクティビティをすべて順番に消費し、その値を追加してカウンターを増やします。 

### なぜ効果があるのか

 どの段階においても、唯一重要な決定は、次の骨の折れるアクティビティが現在の状況で実行可能かどうかです。 存在する場合、問題のルールによって強制的に実行されます。 そうでない場合、唯一の代替アクションは、次の活性化活動があればそれを行うことです。 これ以上の分岐選択肢はありません。 

各アクティビティは 1 回だけ消費され、ポインターは進むだけであるため、システムが以前の状態に戻ることはありません。 性質は各アクション内で単調に進化し、貪欲な選択は問題の決定論的なポリシーを反映します。 これにより、シミュレーションがルールで定義された正確なシーケンスに逸脱することなく従うことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    D, C, R = map(int, input().split())
    tiring = [int(input()) for _ in range(C)]
    invigorating = [int(input()) for _ in range(R)]
    
    i = j = 0
    d = D
    cnt = 0
    
    while i < C or j < R:
        if i < C and tiring[i] <= d:
            d -= tiring[i]
            i += 1
            cnt += 1
        else:
            if j < R:
                d += invigorating[j]
                j += 1
                cnt += 1
            else:
                break
    
    print(cnt)

if __name__ == "__main__":
    solve()
```実装はポインター シミュレーションの直後に続きます。 アクティビティが残っている間、ループは継続します。 最初のブランチは優先ルールを適用します。次の疲れるアクティビティが手頃な価格であれば、すぐにそれを実行します。 

else 分岐は、疲れるアクティビティに余裕がないか、疲れ果てたときにトリガーされます。 その場合、私たちは元気を与える活動をするようにしています。 何も存在しない場合は、それ以上状態を変更することはできないため、中断します。 

よくある落とし穴は、爽快なアクティビティは順番に実行する必要があり、スキップできないことを忘れていることです。これは単一のポインター j によって強制されます。

 | 測定 | 複雑さ | 説明 |

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、最初の疲れるアクティビティの費用が高すぎて、爽快なアクティビティが 1 つしか存在しない場合です。 アルゴリズムは、同じ疲れるポインタを再評価する前に、爽快なポインタを正しく消費し、性質を更新します。 

入力：```
D = 5
tiring = [10]
invigorating = [3]
```実行は、最初に爽快なアクティビティを実行して性質を 8 に上げ、次に同じ疲れるアクティビティを再チェックすることで進行しますが、それでも失敗するため、カウント 1 で停止します。 

もう 1 つのエッジ ケースは、最初は疲れるアクティビティがすべて手頃な価格であり、爽快なアクティビティがまったく使用されない場合です。 ループは常に疲れるブランチを選択し、不必要なチェックを行わずに単調な消費を保証します。 

最後に、爽快なアクティビティが早期に使い果たされると、気質を高めるメカニズムが残っていないため、次の疲れるアクティビティに手が届かなくなると、アルゴリズムはすぐに停止します。
