 ## 問題の理解

 16 進数で書かれた個別の数値のコレクションと一連のクエリが与えられます。 クエリごとに 10 進数を受け取ります$x$。 タスクは、指定された 16 進数の 1 つを選択することです。$a_i$組み合わせると$x$そして$a_i$16 進数で桁ごとに定義された特別な演算を使用すると、結果の値は通常の 10 進数の順序で可能な限り大きくなります。 選択したインデックスを出力する必要があります$a_i$。 

重要な点は、この演算が通常の加算ではなく、10 進数の桁上げベースの XOR ではないことです。 16 進数ごとに独立して定義されます。各桁はキャリーなしで結合されるため、$3_H ⊕ 4_H = 7_H$、$A_H ⊕ B_H = 5_H$。 各 16 進数は、16 を法とする加算のように動作します。 

各クエリは独立しているため、クエリ間の「最大結果ペアリング」問題を繰り返し解決します。$x$そして固定された数値セット。 

制約は大きく、最大で$10^5$数字と$10^5$クエリ。 すべてを試す素朴な解決策$a_i$クエリごとに実行される$10^{10}$実行可能な限界をはるかに超えた最悪の場合の操作。 クエリごとのリニア スキャンであっても、すぐに除外されます。 

微妙なエッジ ケースは、入力が異なる基数で与えられることです。$a_i$は長さ 20 までの 16 進文字列ですが、$x$は 10 進数で与えられます$10^{18}$。 どのソリューションでも、操作を適用する前に表現を正しく正規化する必要があります。 もう 1 つの潜在的な落とし穴は、演算が通常の加算と同じように動作すると想定していることです。これにより、キャリーが誤って導入され、間違った順序が生成されてしまいます。 

## アプローチ

 ブルートフォースの方法は簡単です。 クエリごとに、次の桁ごとの 16 進数の合計を計算します。$x$あらゆるものと$a_i$、結果を比較可能な値に変換し、最大値を追跡します。 これは、操作の定義を直接評価するため、正解です。 ただし、それぞれの計算は$O(L)$どこ$L \approx 20$そしてそれを全員に繰り返します$n$クエリごとの要素、つまり$O(nqL)$。 と$n = q = 10^5$、これはおおよそになります$2 \times 10^{11}$数字の操作が遅すぎます。 

重要な観察は、数値が 2 進数で解釈される場合、基数 16 の「桁上げなし」の数字単位の加算は、構造的にビット単位の XOR と同じであるということです。 16 進数の各桁は 4 つの独立したビットに対応し、桁ごとの 16 を法とする加算は、これらの 4 ビット ブロックに対して正確に XOR されます。 すべての数値をバイナリに変換すると、その演算は整数に対する標準的な XOR になります。 

これにより、問題は古典的な問題に変換されます。整数のセットが与えられた場合、指定された数値との XOR を最大化する要素を求めるクエリに答えます。 これはまさにバイナリ トライが設計されたものです。 すべての候補をスキャンするのではなく、ビットごとに可能な限り最良の XOR 値を貪欲に構築し、常に現在のビットを反転するブランチを選択します。$x$可能であれば。

 ## アルゴリズムのチュートリアル

 まず、すべての 16 進数を 2 進数表現に変換します。 各 16 進数は 4 ビットに対応するため、20 文字の 16 進数は最大 80 ビットになります。 

次に、これらのビットに対してバイナリ トライを構築します。各ノードはビットのプレフィックスを表し、それを通過する少なくとも 1 つの数値のインデックスを格納します。 

各クエリについて:

 1. 10進数を変換する$x$格納された数値の最大長をカバーするのに十分なビットのみを考慮して、バイナリ表現に変換します。 これにより、すべての値の間の位置合わせが保証されます。 
2. トライのルートから開始して、次のビットを処理します。$x$最も重要なものから最も重要でないものまで。 
3. 各ビット位置で、現在のビットの反対側のビットへの移動を試みます。$x$。 もし$x$ビット 0 がある場合は、ビット 1 の分岐を優先します。 ビット 1 がある場合は、ビット 0 を優先します。これは、ビットが異なる場合に XOR が 1 を生成し、上位ビットが最終値を支配するためです。 
4. 優先ブランチが存在しない場合は、使用可能なブランチにフォールバックします。 
5. すべてのビットが処理されるまで続行します。 最終ノードに保存されているインデックスが答えです。 

貪欲なステップの背後にある理由は、上位ビットが下位ビットよりも最終的な数値に大きく寄与するためです。 したがって、最初の異なるビットを最大化すると、後のビットに関係なく、全体の結果が最大化されます。 

### なぜ効果があるのか

 トライ トラバーサルでは、最上位ビットから最下位ビットへの XOR 結果が構築されます。 下位ビットは上位位置での損失を補償できないため、各位置で、そのビットで 1 を生成する分岐を選択することが、0 を生成する選択よりも厳密に優先されます。 異なるビット位置での XOR 決定は独立しているため、各ノードでの最適な選択が将来の最適な選択を制約することはありません。 これにより、ビットごとの貪欲な最大化によって全体的に最適な結果が得られることが確立されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

BIT = 80

class Node:
    __slots__ = ("ch", "idx")
    def __init__(self):
        self.ch = [-1, -1]
        self.idx = -1

trie = [Node()]

def new_node():
    trie.append(Node())
    return len(trie) - 1

def insert(x, idx):
    node = 0
    for i in range(BIT - 1, -1, -1):
        b = (x >> i) & 1
        if trie[node].ch[b] == -1:
            trie[node].ch[b] = new_node()
        node = trie[node].ch[b]
        trie[node].idx = idx

def query(x):
    node = 0
    for i in range(BIT - 1, -1, -1):
        b = (x >> i) & 1
        want = b ^ 1
        if trie[node].ch[want] != -1:
            node = trie[node].ch[want]
        else:
            node = trie[node].ch[b]
    return trie[node].idx

n, q = map(int, input().split())
a = input().split()

for i, s in enumerate(a):
    val = int(s, 16)
    insert(val, i + 1)

for _ in range(q):
    x = int(input())
    print(query(x))
```実装は、80 ビット整数のバイナリ トライを中心にしています。 各挿入は最上位ビットから最下位ビットまで進み、必要な場合にのみノードを作成し、訪問したすべてのノードにインデックスを保存するため、どのプレフィックスでも有効な候補を回復できます。 

クエリ中に、再び上位ビットから下位ビットに移動します。 各ステップで、現在のビットを反転する分岐をたどろうとします。$x$これにより、XOR 結果におけるそのビットの寄与が最大化されるためです。 そのブランチが存在しない場合は、使用可能な唯一の継続にフォールバックします。 

微妙な点は、リーフだけでなく各ノードにも常にインデックスを保存していることです。 これにより、たとえスパーストライの早い段階で停止したとしても、返す有効な候補インデックスがまだあることが保証されます。

        def __init__(self):
            self.ch = [-1, -1]

                trie[node].ch[b] = new_node()
            node = trie[node].ch[b]
            trie[node].idx = idx

    def query(x):
        node = 0
        for i in range(BIT - 1, -1, -1):
            b = (x >> i) & 1
            want = b ^ 1
            if trie[node].ch[want] != -1:
                node = trie[node].ch[want]

 ## 特殊なケース

 例外的なケースは、数値が 1 つだけ存在する場合など、トライが非常にまばらになる場合に発生します。 その場合、すべてのクエリは、関係なくそのインデックスを返す必要があります。$x$。 すべてのトラバーサル パスが唯一の利用可能なブランチに集約されるため、アルゴリズムはこれを自然に処理します。 

もう 1 つのケースは、すべての数値がバイナリで長い共通のプレフィックスを共有する場合です。 この場合、トライは分岐のない長いチェーンになります。 この状況でも、貪欲なルールは依然として機能します。分岐の決定が問題となるのは、代替案が存在する場合のみだからです。 それ以外の場合は、トラバースが強制されます。 

3 番目のケースは、16 進値の長さが大幅に異なる場合です。 バイナリへの変換後、短い数値には先行ゼロが効果的に埋め込まれ、トライではそれらを一貫してより小さい値として扱い、上位ビットでの正しい比較を保証します。
