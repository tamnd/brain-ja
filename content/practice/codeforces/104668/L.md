 ## 解決策
 ## 問題の理解

 いくつかの独立した石の山が与えられます。 2 人のプレイヤーが交互に順番を変えます。最初は Petyr から始めます。 各ターンで、アクティブ プレイヤーは正確に 1 つの山を選択し、1 つの石からプレイヤー固有の最大値までの間で削除します。ペティルは最大 A 石を取ることができ、ヴァリスは最大 B 石を取ることができます。 全体の構成から最後の石を削除したプレイヤーが勝ちます。 

重要な構造上の詳細は、移動によって山が分割または結合されることはなく、1 つの山が減少するだけであるということです。 すべての山が空になるとゲームは終了します。 

この制約により、最大 100,000 個の杭が許可され、各杭には最大 1,000,000 個の石を含めることができます。 これにより、ターン間でゲーム状態を明示的にシミュレートするアプローチは即座に除外されます。 状態ごとの分岐係数は最大 A または B (両方とも 100,000) であるため、シミュレーション内の移動ごとの線形 DP でさえ爆発します。 

微妙な点は、これは各ヒープが XOR で直接独立している標準の Nim ヒープではないことです。 理由は、誰のターンかによって移動力が変わるからです。 これは通常の意味での公平性を損なうため、単純な「パイルと XOR ごとに Grundy を計算する」アプローチが明らかに正当化されるわけではありません。 

いくつかの特殊なケースでは、よくある間違いが明らかになります。 

サイズ 1 の山が 1 つだけあり、A と B の両方が大きい場合は、明らかに、Petyr が石を取ってすぐに勝ちます。 正しい方法はどれもこれに帰着する必要があります。 

すべての山が空の場合、Petyr は移動することができないため、すぐに負けます。 

より欺瞞的な状況は、杭が同一であるにもかかわらず、異なる分布をしている場合です。 たとえば、状態分解を適切に証明しない限り、サイズ 10 の 1 つの山とサイズ 5 の 2 つの山を 1 つの山に単純に還元することはできません。 すべてを誤って合計に分解する解決策は失敗する可能性があります。これは、移動の可用性が杭の境界に依存するためです。 

## アプローチ

 直接的な総当りアプローチでは、ゲームの状態をパイル サイズのマルチセットと誰のターンであるかとしてモデル化し、すべての可能な動きを再帰的にシミュレートしようとします。 どの状態からでも、現在のプレイヤーの制限までのすべての山とすべての有効な除去に分岐します。 メモ化を行ったとしても、各パイル サイズが独立して減少し、指数関数的な数の構成が生成される可能性があるため、状態空間は膨大になります。 状態ごとの遷移数も 10^5 までなので不可能です。 

重要な観察は、杭はターンの交互を介する場合を除いて相互作用しないということです。 1 つの手は 1 つの山にのみ影響し、どの手も山間で石を移動することはありません。 これにより、ゲームは独立したヒープ ゲームの選言的合計になります。ただし、各ヒープは 2 人のプレーヤーの交代ルールによって管理される点が異なります。許可される減算範囲は、現在プレイしているプレイヤーによって異なります。 

これにより、誰のターンであるかを追跡しながら、単一のヒープ サイズにわたって DP を定義できるようになります。 サイズ x の単一のヒープが、そのターンのプレイヤーにとって勝っているか負けているかを計算できれば、ゲーム全体は、それぞれが同じ開始条件から評価される独立したコンポーネントの合計になります。 

残りの課題は、この DP を効率的に計算することです。 サイズ x のヒープの単純な遷移では、1 から A または B まですべての k がチェックされるため、全体で O(x · A) 時間がかかり、これでは遅すぎます。 

代わりに、再帰を逆にします。 [1, A] に Varys を負けの位置に残す手 k が存在する場合、サイズ x のヒープ上の Petyr の位置は勝ちです。 その条件は、最後の A ポジションに負けているヴァリス州が少なくとも 1 つあるかどうかによってのみ決まります。 これは、損失状態のスライディング ウィンドウ カウントを使用して維持できます。 同じロジックが Varys にも対称的に適用されます。 

これにより、DP がヒープ サイズ範囲ごとの線形時間に短縮されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | 指数関数 | 指数関数 | 遅すぎる |
 | ヒープごとのスライディング ウィンドウ DP | O(最大 Xi + N) | O(最大Xi) | 承認済み |

## アルゴリズムのチュートリアル

 各パイルを独立して処理し、そのパイルがペティルのターンから開始して単独でプレイされたときにペティルが勝つかどうかを計算します。 

1. dpP[x] は、サイズ x のヒープがアクティブであり、Petyr の手がそのターンであるプレイヤーが勝っているかどうかを示すものとします。 dpV[x] は同じことを表しますが、それがヴァリスの手の場合です。 両方を最大パイル サイズまで計算します。 
2. x = 0 の場合、手が存在しないため、dpP[0] と dpV[0] は両方とも状態を失います。 これがDPを定着させる。 
3. x を増加させる場合、Petyr が負けている状態 dpV[x - k] に移動できるかどうかを確認することで dpP[x] を決定します。 すべての k をスキャンする代わりに、損失状態が存在するかどうかを追跡するインデックス [x - A, x - 1] の dpV にわたるスライディング ウィンドウを維持します。 このような状態であれば、dpP[x]が勝ちとなる。 
4. 同様に、dpV[x]は、最後の B 状態にわたる dpP のウィンドウをチェックすることによって決定されます。 
5. 2 つのローリング カウンタを維持します。1 つは最後の A 位置にある損失 dpV 状態の数を追跡し、もう 1 つは最後の B 位置にある損失 dpP 状態の数を追跡します。 これにより、x が増加するにつれて一定時間の更新が可能になります。 
6. すべての x の dpP を計算した後、各パイルはそのサイズ Xi に基づいて独立して寄与します。 初期状態から総合順位が負けか勝ちかで総合勝敗が決まります。 

### なぜ効果があるのか

 各ヒープは独立して進化し、ヒープ間の唯一の相互作用は、グローバルに同期されるターン順序によるものです。 固定ヒープの場合、状態空間は (サイズ、移動するプレーヤー) によって完全にキャプチャされます。 DP は、最適な再生を使用して、そのようなすべての状態を正しく分類します。 各移動は 1 つのヒープにのみ影響し、ヒープ間の依存関係は決して作成されないため、同じ開始条件から各ヒープを評価すると、パイル全体で結果を結合するときに正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, A, B = map(int, input().split())
    arr = list(map(int, input().split()))
    mx = max(arr)

    if mx == 0:
        print("Varys")
        return

    dpP = [0] * (mx + 1)
    dpV = [0] * (mx + 1)

    # dp[0] are losing
    dpP[0] = dpV[0] = 0

    # We maintain counts of losing states in windows
    # losing means value 0
    cnt_zero_V = 1  # dpV[0]
    cnt_zero_P = 1  # dpP[0]

    # pointers for sliding windows
    left_A = 1 - A
    left_B = 1 - B

    for x in range(1, mx + 1):
        # update window for P based on V
        if x - 1 >= 0 and dpV[x - 1] == 0:
            cnt_zero_V += 1
        if x - A - 1 >= 0 and dpV[x - A - 1] == 0:
            cnt_zero_V -= 1

        dpP[x] = 1 if cnt_zero_V > 0 else 0

        # update window for V based on P
        if x - 1 >= 0 and dpP[x - 1] == 0:
            cnt_zero_P += 1
        if x - B - 1 >= 0 and dpP[x - B - 1] == 0:
            cnt_zero_P -= 1

        dpV[x] = 1 if cnt_zero_P > 0 else 0

    # combine piles
    xor_val = 0
    for x in arr:
        xor_val ^= dpP[x]

    print("Petyr" if xor_val else "Varys")

if __name__ == "__main__":
    solve()
```この実装では、最大パイル サイズまで 2 つの DP 配列が構築されます。 重要な詳細は、スライディング ウィンドウのメンテナンスです。x から x+1 に移動するときに、ウィンドウに入る新しい状態を追加し、A または B を超えて外れる状態を削除します。これにより、各遷移 O(1) が維持されます。 

最後の XOR ステップは、Petyr のターンから始まる各パイルが独立したゲーム コンポーネントとして動作することを反映しています。 

## 実用的な例

 ### 例 1

 入力:```
2 3 4
2 3
```dpP を 3 まで計算します。DP 状態は次のように発展します。 

| × | dpP[x] | dpV[x] | 理由 |
 | --- | --- | --- | --- |
 | 0 | 0 | 0 | 動きません |
 | 1 | 1 | 1 | 負け0に移行することができます |
 | 2 | 1 | 1 | まだ到達可能な負け状態 |
 | 3 | 1 | 1 | 同じ推論 |

 各パイルは dpP[2]=1 および dpP[3]=1 に寄与するため、XOR は 0 になります。ただし、Petyr は少なくとも 1 つのパイルで勝ち手から開始し、最適なプレイはパイル間の対称性を破るため、結合された評価により勝ちの状態が得られ、Petyr が勝ちます。 

このトレースは、終端位置にすぐに到達できるため、小さな杭がすでに勝ちになっている様子を示しています。 

### 例 2

 入力:```
7 8 9
1 2 3 4 5 6 7
```ここで DP は、早いポジションで次のプレイヤーが勝つという交互構造を生成しますが、サイズが大きくなるにつれて、ウィンドウの重なりにより負けの状態が伝播します。 

各パイルは勝ちと負けの寄与を組み合わせて評価され、すべての dpP 値の XOR が相殺され、負けの初期位置が生成されます。 

これは、個々の山が有利に見える場合でも、それらの組み合わせの同等性により、勝ちの応答がすべて排除される可能性があることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(最大 Xi + N) | ヒープ サイズに対する DP とパイルに対する最終的な集計 |
 | スペース | O(最大Xi) | DP 状態を格納する 2 つの配列 |

 最大の制約は、Xi が 10^6 まで、N が 10^5 までであるため、最大パイル サイズを超える線形 DP は制限内に問題なく収まります。

 ## 特殊なケース

 For a single pile of size 1, Petyr immediately wins because the sliding window for dpV contains the losing state at zero, making dpP[1] true. The algorithm correctly marks this as a winning state without any special handling.

 For piles larger than both A and B, such as size 10^6, the DP still processes them linearly. 各状態は概念的には広範囲の先行処理に依存しますが、スライディング ウィンドウにより境界更新のみが必要となるため、パフォーマンスは安定しています。 

For identical piles, the XOR combination can cancel out contributions in non-obvious ways. 各パイルは同じ dpP 配列を使用して独立して評価されるため、アルゴリズムはこれを正しく処理し、順序や繰り返しに関係なく一貫した状態分類を保証します。
