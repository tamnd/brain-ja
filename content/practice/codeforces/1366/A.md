 ## 問題の理解

 各テスト ケースが棒とダイヤモンドの 2 種類の材料を記述するリソース管理の問題が与えられています。 これらの材料から 2 つの異なるアイテムを作成できます。 1 つのアイテムはスティック 2 つとダイヤモンド 1 つを消費し、もう 1 つのアイテムはスティック 1 つとダイヤモンド 2 つを消費します。 作成されたすべてのアイテムは正確に 1 単位の利益で販売できるため、リソース制限に違反せずに構築できるアイテムの数を最大化することが課題となります。 

重要なのは、作成の順序ではなく、リソースの総消費量が利用可能なスティックとダイヤモンドの範囲内に収まるように、各タイプをいくつ選択するかです。 作成された各アイテムは価値が独立しているため、目的はリソースの制約の下で有効な (2,1) と (1,2) のペアの総数を最大化することになります。 

この制約では、最大 1000 個のテスト ケースが許可され、各テスト ケースには最大 10^9 の値が含まれます。 これにより、シミュレーションや組み合わせの検索が即座に除外されます。 どれだけのシャベルや剣を構築するかを列挙しようとするアプローチは、テスト ケースごとに O(a + b) 以下に劣化し、あまりにも遅すぎます。 テストケースごとに定数時間の式が必要です。 

素朴だが重要な落とし穴は、最初にできるだけ多くのシャベルを作るなど、すべてのリソースを常に一方向に貪欲に使用する必要があると想定していることです。 例えば、棒が4本、ダイヤが4つある場合、最初にシャベルを貪欲に取るとシャベル1本（棒2本、ダイヤ1本）が得られ、棒2本とダイヤ3本が残れば剣が1本可能となり、合計2本が最適となります。 しかし、他のディストリビューションでは、慎重に検討しないと、貪欲な選択が誤解を招く可能性があります。 

より微妙なエッジケースは、リソースの不均衡が非常に大きい場合です。 たとえば、スティック 1 つとダイヤモンド 10 個の場合、両方のレシピに少なくとも 1 つのスティックが必要となるため、ダイヤモンドが豊富であってもアイテムを作成することはできません。 同様に、スティック 10 個とダイヤモンド 1 個でも結果はゼロになります。 正しいソリューションでは、両方のリソースがバランスの取れたペアで消費される必要があることを暗黙的に把握する必要があります。 

## アプローチ

 強引な戦略は、可能な限りすべての数のシャベルを試すことです。 シャベルの数を x に固定すると、スティックが 2 個とダイヤモンドが x 個消費され、残りのスティックとダイヤモンドによって制限される剣の数を計算するためのリソースが減ります。 0 から min(a//2, b) までのすべての x を試し、最良の結果を計算します。 

すべての有効な解は x 個のシャベルと y 個の剣の選択に対応するため、このアプローチは正しいです。 ただし、x の範囲は最悪の場合 10^9 に達する可能性があり、この線形スキャンは実行不可能になります。 各評価は O(1) であるため、合計の複雑さはテスト ケースごとに O(min(a, b)) となり、1000 回のテストには遅すぎます。 

重要な観察は、各アイテムが合計でちょうど 3 つのリソースを消費しますが、その比率は異なるということです。 シャベルはスティック2本とダイヤモンド1個、剣はスティック1本とダイヤモンド2個です。 この対称性は、作成された各アイテムが実質的に 3 つのユニットを「消費」することを意味しますが、制限要因は総リソースではなく、スティックとダイヤモンドのバランスです。 

ペアリングの観点から考えると、すべてのアイテムは、より豊富なリソースの 1 ユニットを 2 回、もう 1 ユニットを 1 回消費します。 これは、答えがリソースの合計と a と b の間の不均衡の両方によって制約されることを示唆しています。 最適な構築では、1 つのリソースが小さすぎてバランスのとれたクラフトができなくなるまで、常にできるだけ多くのペアが使用されます。

結果として得られる構造は、リソースのバランスが完全に保たれている場合、答えは作成可能なアイテムの総数 ((a + b) // 3) によって制限され、また、実現可能性を保証する方法でより小さいリソースによって制限されるというものです。 各項目はすべての構成にわたって両方のリソースの少なくとも 1 ユニットを消費する必要があるため、より厳しい制約は (a + b) // 3 と min(a, b) の間の最小値であることがわかります。 

両方の制約を直接捉える定数時間の式に到達します。

 ## アルゴリズムのチュートリアル

 最適なソリューションは、消費可能なトリプルの合計とリソースのバランスという 2 つの同時制約の下でアイテムの最大数を計算することに依存します。 

1. 各テスト ケースについて、スティック a とダイヤモンド b の数を読み取ります。 これらは、2 つのクラフト レシピに分散する必要がある利用可能なリソースを定義します。 
2. 不均衡を無視した場合に考えられるアイテムの総数を計算します。これは (a + b) // 3. これは、すべてのアイテムが合計でちょうど 3 つのリソースを消費するという事実を表しているため、完全にバランスの取れたシステムであってもこの制限を超えることはできません。 これにより、生産の絶対的な上限が決まります。 
3. 希少なリソースによって制限されるアイテムの数、min(a, b) を計算します。 各アイテムには両方のリソースを何らかの組み合わせで少なくとも 1 ユニット必要とするため、より小さいリソース プールを超えることはできません。 
4. これら 2 つの限界の最小値を最終的な答えとして採用します。 これにより、総消費量制限とスティックとダイヤモンドの間のバランス制約の両方が確実に尊重されます。 

### なぜ効果があるのか

 作成されたすべてのアイテムは、結合されたリソース プールをちょうど 3 ユニット削減するため、(a + b) // 3 を超える解決策はありません。同時に、両方のレシピに両方の材料が含まれているため、すべてのアイテムは合計で両方のリソースを少なくとも 1 ユニット消費する必要があります。 これにより、項目の数が a と b の小さい方を超えることはできなくなります。 有効な構造は両方の制約を満たす必要があり、2 つの項目タイプにより不均衡を柔軟に再配分できるため、これら 2 つの境界のうち小さい方を常に達成することが可能です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    a, b = map(int, input().split())
    print(min((a + b) // 3, min(a, b)))
```このソリューションは、各テスト ケースを個別に処理し、一定時間で 2 つの量を計算します。 1 つ目は、リソースを 3 つにグループ化することで得られる、完全な梱包で可能なアイテムの合計数です。 2 つ目は、小さいリソース タイプによって課される制限で、スティックもダイヤモンドも可用性の制約を超えて過剰に使用されないようにします。 

最終的な答えはこれら 2 つの値の最小値であり、これにより実現可能性と最適性の両方が保証されます。 

よくある間違いは、(a + b) // 3 のみを使用することです。これは、1 つのリソースが不足しているときに答えを過大評価します。 もう 1 つの間違いは、min(a, b) のみを使用することです。これは、両方のバランスが取れている場合でも、合計リソースがまだ不十分である可能性があるという事実を無視しています。

 ## 特殊なケース

 重大なエッジケースは、1 つのリソースがゼロの場合です。 入力 1000000000 0 の場合、両方の式で min((a+b)//3, min(a,b)) = 0 が生成され、クラフトは正しく防止されます。 合計を優先する素朴な貪欲なアプローチは、多くの項目が可能であると誤って想定する可能性がありますが、すべてのレシピが両方の材料を必要とすることを無視します。 

もう 1 つのエッジ ケースは、1 と 10 などの極端な不均衡です。式では min(11//3, 1) = 1 が得られ、1 つの項目のみが可能であることを意味します。 実行をトレースすると、有効な最初のクラフトの後、少なくとも 1 つのリソースがすぐに使い果たされることが確認されます。 

最後に、10^9 や 10^9 などの対称的な大きな入力で整数の安定性をテストします。 式は 2*10^9 // 3 に減ります。これは Python の整数に安全に収まり、オーバーフローやパフォーマンスの問題が発生しないことが保証されます。
