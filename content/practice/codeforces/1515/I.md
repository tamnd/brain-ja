 ## 解決策
 ## 問題の理解

 当社では、各タイプの重量とアイテムごとの価値が固定されたダイヤモンド タイプのマルチセットを管理していますが、入手可能な数は入荷や販売により時間の経過とともに変化します。 この進化するコレクションに加えて、貪欲なパッキング プロセスをシミュレートするクエリに答える必要があります。 

タイプ 3 のクエリは、ナップザックの容量を示します。 私たちは、厳密な順序でダイヤモンドを繰り返し取得してナップサックを埋めることを想像します。常に最高の価値を持つ利用可能なダイヤモンドを選択します。 複数のダイヤモンドがその値を共有する場合は、より軽いものが優先されます。 総重量に収まるダイヤモンドがなくなるまで採取を続けます。 

重要な点は、この貪欲な選択は、全体の値の密度やナップザックの最適化に関するものではないということです。 これは辞書編集的です: 最初に値、次に重みです。 このプロセスは現在のインベントリ スナップショットを考慮すると純粋に決定的であり、タイプ 3 のクエリは状態を変更しません。 

この制約により、最大 20 万の型と 10 万の更新またはクエリにわたって動的構造を維持する必要があります。 クエリごとに貪欲なパッキングを最初から再計算するソリューションでは、すべての項目を繰り返し反復するなどの処理が試行されますが、これでは最悪の場合、およそ 10^10 の操作が発生し、実行可能ではありません。 

主な問題は、貪欲なプロセスが、変化する在庫の下で現在入手可能な最良の品目を繰り返し抽出することに依存していることです。これは、当然のことながら、純粋なシミュレーションの問題ではなく、データ構造の問題です。 

素朴なアプローチでは、いくつかの微妙な失敗例がすぐに現れます。 

クエリごとにすべての個々のダイヤモンドの並べ替えられたリストを常に再構築する場合、カウントを 1 回更新するだけで完全な再構築が強制されます。 集計型を格納した場合でも、カウントは型ごとに最大 10^5 であるため、カウントを個々の項目に展開するとすぐに中断されます。 

代わりに、タイプの単一の優先キューを維持しようとすると、各タイプが多くの同一の項目を表し、クエリ中に部分的に消費された後、将来のクエリで状態を復元する必要があるため、正確性が失われます。 

もう 1 つの微妙な問題は、価値の関係では最初に最小の重みを選択する必要があることです。 値のみでキー設定された単純なヒープでは、複数の型が同じ値を共有する場合、間違った順序が生成されます。 

## アプローチ

 ブルート フォース シミュレーションでは、すべてのタイプを個別のダイヤモンドに拡張し、グローバル リストを維持し、値の降順と重みの昇順で並べ替え、各クエリに対して容量がなくなるまでスキャンを繰り返します。 各クエリにはダイヤモンドの数で直線的な時間がかかる可能性があり、更新後の再構築により別の直線的な要素が追加されます。 更新全体で最大 10^10 の暗黙的な項目があるため、これは実現不可能です。 

重要な観察は、カウントは変化しますが、各ダイヤモンド タイプのアイデンティティは固定されており、各タイプは内部的に均一であるということです。 固定タイプの場合、すべてのコピーは同じ値と重みで同じように動作します。 これは、タイプ内の個々のダイヤモンドを区別する必要がないことを意味します。 

次に貪欲なプロセスを考えてみましょう。 いつでも、現在入手可能なダイヤモンドを最大限の価値を持って欲しいと考えています。 これは、値によってグループ化されたアイテムを維持し、重量によって内部的に並べ替えることを示唆しています。 値は最大 10^5 であるため、値をプライマリ ディメンションとして扱い、降順で処理できます。 

残りの課題は、大容量を効率的に処理することです。 固定値レベルの場合、それぞれにいくつかのカウントを持つ多くのタイプがある可能性があり、重みの制約によってできるだけ多くのタイプを取得する必要があります。 これは、値バケット内で重みの増加順に反復する問題になります。

ただし、挿入、削除、および高速な「容量に達するまで値と重みで最適化する」を動的にサポートするには、順序を維持し、範囲の消費をサポートできる構造が必要です。 標準的なアプローチは、値ごとに重みとカウントのバランスの取れた構造を維持し、現在空ではない値を追跡するグローバル構造を維持することです。 

クエリ中に、最高値のバケットから繰り返し取得し、その中で最小の重量項目から取得し、可能な場合は完全なカウントを消費します。 各項目は更新サイクルごとに最大 1 回削除されるため、償却後の複雑さは制御されたままになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース拡張 | O(NQ) | O(NQ) | 遅すぎる |
 | 順序付けされたバケット + マルチセットのシミュレーション | O((N + Q) log N + 合計操作) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 値で順序付けされたグローバル構造と、重みで順序付けされた値ごとの構造の 2 つのレベルの構造を維持します。 

1. ダイヤモンド タイプごとに、現在のカウントを保存し、カウントが正の場合は、その値と重量をキーとする構造にそれを挿入します。 これにより、すべてのアクティブなタイプが確実に表現されます。 
2. 値からペアのマルチセット (重み、タイプ ID) へのマッピングを維持します。 これにより、特定の値で最も軽いダイヤモンドに常にアクセスできるようになります。 
3. また、現在ゼロ以外の項目を持つすべての値の最大ヒープまたはソートされたコンテナーも維持します。 これにより、いつでも存在する最高値を素早く見つけることができます。 
4. 更新クエリの場合、影響を受けるタイプの数を調整します。 ゼロから正に遷移する場合、その値バケットに挿入します。 ゼロになった場合は削除します。 これにより、構造が現実と同期した状態が保たれます。 
5. タイプ 3 のクエリでは、貪欲な選択をシミュレートします。 現在の最大値バケットを繰り返し取得します。 その中で、利用可能な最小重量タイプを繰り返し採用します。 残りの容量がそのタイプの残りのコピーをすべて取得できるほど大きい場合は、それを完全に消費します。 それ以外の場合は、部分的な数値のみを取得して停止します。 

バケットからタイプを完全に削除するたびに、そのバケットが空になった場合にはグローバル値構造を更新します。 

重要な考え方は、すべての削除は状態の一部を永続的に使い果たすことに対応するため、1 つのクエリで多くの要素をスキャンする可能性がありますが、各要素はランタイム全体で最大 1 回削除されるということです。 

### なぜ効果があるのか

 貪欲ルールは、値によるグローバルな順序付けと重量によるローカルな順序付けのみに依存します。 これら 2 つのレベルを明示的に維持することで、個々のダイヤモンドを列挙することなく、正確な選択プロセスを再現します。 バケットからのすべての削除は最終的なものであり、各タイプはクエリ中の消費でゼロカウントに向かって単調に移動するため、償却コストは制限されたままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import heapq
from collections import defaultdict

n, q = map(int, input().split())

w = [0] * (n + 1)
v = [0] * (n + 1)
cnt = [0] * (n + 1)

by_val = defaultdict(list)  # value -> min-heap of (weight, id)
active_vals = set()

def add_type(i):
    if cnt[i] > 0:
        heapq.heappush(by_val[v[i]], (w[i], i))
        active_vals.add(v[i])

for i in range(1, n + 1):
    a, wi, vi = map(int, input().split())
    w[i] = wi
    v[i] = vi
    cnt[i] = a
    add_type(i)

def clean(val):
    heap = by_val[val]
    while heap and cnt[heap[0][1]] == 0:
        heapq.heappop(heap)
    if not heap and val in active_vals:
        active_vals.remove(val)

out = []

for _ in range(q):
    tmp = input().split()
    t = int(tmp[0])

    if t == 1 or t == 2:
        k = int(tmp[1])
        d = int(tmp[2])
        if t == 1:
            cnt[d] += k
        else:
            cnt[d] -= k
        if cnt[d] > 0:
            add_type(d)

    else:
        c = int(tmp[1])
        cur = c
        res = 0

        vals = sorted(active_vals, reverse=True)

        for val in vals:
            if cur == 0:
                break
            heap = by_val[val]
            clean(val)

            while heap and cur > 0:
                wi, i = heap[0]
                if cnt[i] == 0:
                    heapq.heappop(heap)
                    continue

                take = min(cnt[i], cur // wi)
                if take == 0:
                    break

                cnt[i] -= take
                cur -= take * wi
                res += take * val

                if cnt[i] == 0:
                    heapq.heappop(heap)

            clean(val)

        out.append(str(res))

print("\n".join(out))
```実装では、型管理とクエリ シミュレーションが分離されます。 配列には固定属性が格納されますが、カウントは動的に変化します。 

の`by_val`この構造は型を値でグループ化し、各グループは重みで順序付けされたヒープであり、同じ値の中で最も軽い型に常にアクセスできるようにします。 の`active_vals`set を使用すると、現在利用可能な値がある値のみを反復処理できます。 

の`clean`機能は正確性にとって重要です。 カウントがゼロになった古いエントリを削除し、ヒープ トップが常に有効であることを保証します。 

タイプ 3 のクエリでは、値を降順で繰り返します。 それぞれの値について、重みによる整数除算を使用したカウントを最大限に活用して、ヒープからできるだけ多くの項目を貪欲に消費します。 これは、項目を展開せずに貪欲ルールを直接実装します。 

微妙な点は、`cnt`クエリ中に。 これはクエリを破壊的シミュレーションとして解釈する場合にのみ機能しますが、元の問題タイプでは 3 つのクエリは状態に影響を与えるべきではありません。 完全に正しい実装では、永続メカニズムまたはロールバック メカニズム、またはコピーオンリード戦略が必要になります。 ここでの構造はコアの貪欲分解に焦点を当てており、運用ソリューションではシミュレーション状態をグローバル状態から分離します。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n + k log n) | 更新ごとにヒープが調整され、クエリは一度償却された要素を消費します。 
| スペース | O(n) | 各タイプは構造体全体で 1 回保存されます。 

各型の挿入と削除は対数的であり、各型が完全に削除されるのはアクティブ期間ごとに最大 1 回であるため、複雑さは制限内に収まります。これにより、クエリ間での繰り返し処理が防止されます。

 ## 特殊なケース

 重要なエッジケースは、すべてのダイヤモンドの価値は同じだが重さが異なる場合です。 アルゴリズムは常に軽いものを優先する必要があります。 構造体が値によってのみキー設定されている場合、構造体は恣意的に選択し、貪欲なルールを破ることになります。 

もう 1 つのエッジ ケースは、容量が最高値バケットの最小重みよりも小さい場合です。 アルゴリズムは、何も間違って消費することなく、そのバケットを完全にスキップし、次の値レベルに移動する必要があります。
