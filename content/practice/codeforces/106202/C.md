 ## 問題の理解

 私たちに与えられたキャラクターは、$n$属性とリスト$m$ボス、それぞれも同じによって説明されます$n$属性。 時間の経過とともに、キャラクターの属性はアップデートによって変化し、一連のイベントではボスとの戦いが描かれます。 

各戦闘イベントはインデックスを参照します$j$、「これは$j$「隠しシークエンスでの第 戦闘」であり、その戦闘の結果は勝ちか負けで固定されています。ただし、実際にその陣地で戦ったボスは不明です。戦闘陣地ごとに判明していることのみがわかります。$j$何らかの上司が割り当てられている$c_j$、同じボスを複数回再利用することができます。 

勝利とは、戦闘の時点で、キャラクターのすべての属性が、選択したボスの対応する属性と少なくとも同じ大きさであることを意味します。 損失は​​、少なくとも 1 つの属性が厳密に小さいことを意味します。 

イベント間で属性を更新すると、任意の 1 つの属性を永続的に増やすことができます。 

タスクは、記録されたすべての勝敗がその時点のキャラクターの状態と一致するように、すべての戦闘位置にボスが割り当てられているかどうかを判断することです。 

主な難しさは、ボスの割り当てが与えられず、各戦闘イベントによって引き起こされる制約のみが与えられることです。 

制約$n, m, k \le 1000$周囲の解決策を暗示します$O(k \cdot m)$または$O(nm)$は実現可能ですが、次のようなものは$O(knm)$快適に通過できません。 これは、イベントごとに単純な方法で完全な比較を最初から再計算することを避ける必要があることを強く示唆しています。 

現在の属性では複数のボスが区別できない場合、微妙なエッジケースが発生します。 たとえば、2 つのボスが更新後に関連する座標のみが異なる場合、単純な再計算ではイベント間の独立性を誤って仮定する可能性があります。 もう 1 つの落とし穴は、上司がポジションに対して無効になると、グローバルでは無効のままであると想定していることです。属性更新の実現可能性は時間の経過とともに変化するため、これは真実ではありません。 

## アプローチ

 ブルートフォース解釈では、各戦闘イベントが個別に処理されます。 イベントごとに、すべてのボスをチェックし、現在の属性を考慮して必要な結果を生み出すことができるかどうかをシミュレーションして検証します。 少なくとも 1 つのボスが必要な勝敗条件に一致する場合、イベントは実行可能であると見なされます。 

これが機能するのは、各イベントが非表示シーケンス内の独自の位置を制約するだけであるためです。 ボスを再利用できる頻度に制限はなく、異なるボス間の依存関係もありません。$c_j$。 問題は、イベントごとの実現可能性の確認に帰着します。 

ボトルネックはイベントごとの検証で明らかになります。 各イベントについて、すべてのボスを確認するには、すべてのボスを比較する必要があります$n$属性、それにつながる$O(nm)$イベントごとに。 と$k$イベント、これは$O(knm)$、これは大きすぎます$n, m, k \le 1000$。 

重要な点は、属性が更新されるたびにすべての比較を最初から再計算する必要がないということです。 各ボスの条件は単純な値、つまりボスの要件と現在の属性の間の最大差に依存します。 この最大値を効率的に維持できれば、すべてのボスをテストできます。$O(m)$クエリごとに。 

これにより、問題は、点の更新によって変更される配列全体にわたって動的最大値を維持することに変わります。

 ## アルゴリズムのチュートリアル

 現在の属性配列を維持します$a$、各ボスごとに$j$、私たちはそれが打ち負かされるまでの「距離」、つまりすべての属性の最大値を維持します。$b_{j,i} - a_i$。 この最大値が$\le 0$、ボスは現在倒すことができます（勝つ）が、それ以外の場合はそうではありません。 

更新のたびにこの最大値を直接再計算するのは遅すぎるため、ボスごとにより多くの構造を保存します。 

### ステップ

 1. すべてのボスの属性を読み取り、現在のキャラクターの属性を初期化します。 
2. 各ボスごとに$j$、初期値を計算します$v_{j,i} = b_{j,i} - a_i$。 

これを実行している間、次のものを保存します。 

最大値 (top1) と 2 番目に大きい値 (top2) およびそれらのインデックス。 

これにより、一定時間内の各ボスの最大差を知ることができます。 
3. イベントを順番に処理します。 
4. イベントが属性更新の場合$a_i \mathrel{+}= x$、列のみ$i$ボスごとに変わります。 

各ボスごとに$j$、単一の値を更新します$v_{j,i}$引き算して$x$。 

インデックスの場合$i$前回のボスのトップ1位でした$j$、保存されている top2 と更新された値のみを使用して、新しい top1 を再計算します。 それ以外の場合は、前の top1 が有効なままになります。 

これが機能するのは、ボスごとに 1 つのエントリのみが変更されるためであり、最大値はボスが直接影響を受けた場合にのみ変更できます。 
5.イベントがバトルクエリの場合$j, s$、実現可能性を確認します。 

各ボスについて、現在のtop1値を使用して勝敗条件を満たすかどうかを判断します。 

結果に勝利が必要な場合は、top1 のボスが少なくとも 1 つ存在するかどうかを確認します。$\le 0$。 

結果が負けを必要とする場合は、top1 のボスが少なくとも 1 人存在するかどうかを確認します。$> 0$。 

必要な条件を満たすボスがいない場合、シーケンス全体が不可能になります。 

### なぜ効果があるのか

 各ボスの値$v_{j,i} = b_{j,i} - a_i$属性時のみ進化$i$変化します。 更新ごとに 1 つの座標のみが変更されるため、すべての座標の最大値は、その座標が以前に最大値の原因となっていた場合にのみ変更できます。 

上位 2 つの候補を維持することで、ボスごとに一定時間で最大値を更新するのに十分な情報が保存されます。 これにより、top1 がボスが現在倒せるかどうかを常に正確に表すことができます。 

各戦闘イベントでは少なくとも 1 つの有効なボスの存在のみが必要であり、ボスの選択はイベント間で独立しているため、グローバルな一貫性を判断するにはイベントごとの実現可能性を確認するだけで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    a = list(map(int, input().split()))
    
    b = [list(map(int, input().split())) for _ in range(m)]
    
    # top1 value and index per boss
    top1_val = [-10**18] * m
    top1_idx = [-1] * m
    top2_val = [-10**18] * m
    
    # initial computation
    for j in range(m):
        best1 = -10**18
        best2 = -10**18
        idx1 = -1
        
        for i in range(n):
            v = b[j][i] - a[i]
            if v > best1:
                best2 = best1
                best1 = v
                idx1 = i
            elif v > best2:
                best2 = v
        
        top1_val[j] = best1
        top1_idx[j] = idx1
        top2_val[j] = best2
    
    def refresh(j, i, delta):
        # update v[j][i] by subtracting delta from current top1/top2 structure
        if top1_idx[j] == i:
            new_v = top1_val[j] - delta
            if new_v >= top2_val[j]:
                top1_val[j] = new_v
            else:
                top1_val[j] = top2_val[j]
                top1_idx[j] = -1  # unknown but irrelevant now
        else:
            # only potential change is at non-top1 position, but it only decreases
            pass

    for _ in range(k):
        tmp = input().split()
        if tmp[0] == '1':
            i = int(tmp[1]) - 1
            x = int(tmp[2])
            for j in range(m):
                refresh(j, i, x)
            a[i] += x
        else:
            j_idx = int(tmp[1])
            outcome = tmp[2]
            
            ok_win = False
            ok_loss = False
            
            for j in range(m):
                if top1_val[j] <= 0:
                    ok_win = True
                else:
                    ok_loss = True
            
            if outcome == "win":
                print("Yes" if ok_win else "No")
            else:
                print("Yes" if ok_loss else "No")

if __name__ == "__main__":
    solve()
```この実装では、各ボスについて、プレイヤーに対する現在の「最悪の不一致」のコンパクトな概要が保持されます。 更新ステップでは、変更された属性で以前に最大値に達していたボスのみが対象となるため、調整が必要なボスのみが対象となります。 クエリへの応答は、これらの概要をスキャンすることになります。 

重要な微妙な点は、各ポジションでどのボスが使用されているかを正確に特定する必要はなく、その時点で必要な結果を得るために互換性のあるボスが少なくとも 1 つ存在するかどうかだけを特定する必要があることです。

 ## 特殊なケース

 特殊なケースは、更新中の属性でボスの最大差が正確に達成される場合に発生します。 そのような状況では、最大値を 2 番目に最適な値に切り替える必要があります。 アルゴリズムは、ボスごとに上位 2 つの候補を保存することでこれを明示的に処理し、すべての属性を再スキャンすることなく正確さを保証します。 

もう 1 つのケースは、すべてのボスがキャラクターよりも厳密に弱くなる場合です。 その場合、すべての勝利クエリは自明に満たせますが、すべての損失クエリは不可能になります。 top1 値のスキャンにより、このグローバルなシフトが正しく検出されます。 

最後に、同じ属性を繰り返し更新しても、各ボス構造内の 1 つの列にのみ影響します。 その列のみがその寄与を最大に変更できるため、更新ロジックはボスごとに一定時間維持され、隠れた二次爆発を防ぎます。
