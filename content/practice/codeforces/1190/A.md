 ## 解決策
 ## 問題の理解

 1 から 1 までのインデックスが付いた項目の長い行が与えられます。$n$。 その中で、$m$ポジションは特別としてマークされます。 これらの特別なアイテムは、ラウンドで行われる繰り返しのプロセスで削除されます。 

各ラウンドで、現在の行を長さの固定サイズのブロックにグループ化します。$k$、本のページのようなものです。 次に、少なくとも 1 つの特別な項目を含む最初のページ (左から右) を探します。 そのページでは、すべての特別なアイテムが一度に削除されます。 削除後、残りのアイテムはギャップを埋めるために左に移動するため、位置は動的に変化します。 特別なアイテムがなくなるまでこのプロセスを繰り返します。 

出力はこれらの除去ラウンドの数です。 

それでも$n$と同じ大きさにすることができます$10^{18}$、特別なアイテムの数は最大で$10^5$。 これは、配列またはシフトプロセスをシミュレートできないことがすぐにわかります。 どのような解決策も特別な位置でのみ機能し、その相対的な構造がどのように変化するかを推論する必要があります。 

主な問題は、削除後に残りの要素の位置が左に移動するため、固定インデックスが安定しないことです。 単純なシミュレーションではアレイの再構築を繰り返し、コストがかかります。$O(nm)$あるいはさらに悪いことに、それは不可能です。 

複数の特別なアイテムが同じページ内にある場合、または削除によってアイテムがページ境界を越えて移動する場合、微妙なエッジ ケースが発生します。 

たとえば、次の場合$k = 3$、$n = 10$、特別なポジションは$[3, 4, 5, 6]$、ページ 1 の項目を削除した後、残りの項目が移動し、一部の項目が前のページにまたがる可能性があります。 単純な「インデックスによる削除」アプローチは、各操作の後にインデックスが有効でなくなるため失敗します。 

本当の課題は、削除によって配列が圧縮されるにつれて、時間の経過とともに「アクティブ化」されるページの数を追跡することです。 

## アプローチ

 ブルート フォース シミュレーションでは、配列全体が維持され、以下が繰り返されます。 

1. ページ構造を再構築します。 
2. 特別なアイテムを含む最初のページを見つけます。 
3. そのページ内のすべての特別な項目を削除します。 
4. 要素をシフトします。 

それぞれの削除に費用がかかる場合があります$O(n)$、最大で$m$引っ越し、寄付$O(nm)$、次の場合は不可能です$n$大きいです。 

重要な観察は、実際にシフト配列をシミュレートする必要がないということです。 必要なのは、ページごとに削除される特別なアイテムの数と、要素が削除されるときにページ境界が効果的にどのように移動するかを知ることだけです。 

位置を動的に追跡する代わりに、各特別な位置の前に削除が何回発生したかを追跡します。 削除するたびに、それ以降のすべての位置が 1 ずつ左にシフトされるため、特別なアイテムの有効な位置は$p_i$後$t$そうなる前に削除$p_i - t$。 

これで、各特別な項目をページ番号にマッピングできるようになりました。$$\text{page}(i) = \left\lfloor \frac{p_i - \text{shift}(i) - 1}{k} \right\rfloor$$特別な項目を昇順に処理するときに、すでに削除された項目の数、つまり適用されるシフトの量を維持します。 ページインデックスが変更された回数を数えます。 それぞれの変更は新しい操作に対応します。 

直感的には、削除は全体としてのみ重要であり、各特別なアイテムは、以前の削除が発生するにつれて事実上「左にドラッグ」されるということです。

 ## アルゴリズムのチュートリアル

 特別な位置を昇順に処理します。 

1. カウンタを初期化する`removed = 0`すでに削除された特別なアイテムの数を追跡します。 これは、配列がどれだけ左にシフトしたかを表します。 
2. 特殊ポジションごと$p_i$、現在の実効位置を次のように計算します。$p_i - removed$。 これは、以前の削除によって配列がどのように圧縮されるかを反映しています。 
3. この調整された位置のページ インデックスを次のように計算します。$(p_i - removed - 1) // k$。 
4. 変数を維持する`current_page`現在の操作が行われているページを表します。 これが最初の項目の場合は、初期化します。 
5. 新しいアイテムが厳密に異なるページに属する場合は常に、`current_page`、新しい操作が必要です。 答えを増やして更新する`current_page`。 
6. 処理されたすべての特殊アイテムは削除されたものとみなされます。`removed`1までに。 

重要な考え方は、ソートされた順序で処理することで、各要素に到達した時点ですべてのシフト効果が確実に考慮されるということです。 

### なぜ効果があるのか

 どの時点においても、重要なのは、特定の位置までにどれだけの特別なアイテムが削除されたかということだけです。 これにより、圧縮配列内の現在のインデックスが完全に決定されます。 ページは連続したサイズのブロックであるため、$k$、調整されたインデックスがわかれば、ページのアイデンティティは固定されます。 

調整されたページが前のページと異なる特別なアイテムに遭遇するたびに、アルゴリズムは実際のプロセスで新しいページに移動し、新しい操作をトリガーする必要があることを意味します。 シフトは相対的な順序を保持するため、非表示の再配置によってこの順序を変更することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    p = list(map(int, input().split()))

    removed = 0
    current_page = -1
    ops = 0

    for x in p:
        pos = x - removed
        page = (pos - 1) // k

        if page != current_page:
            ops += 1
            current_page = page

        removed += 1

    print(ops)

if __name__ == "__main__":
    solve()
```この実装は、配列を明示的に変更しないという事実に依存しています。 変数`removed`現在の位置の前の削除によって生じたすべてのシフトをエンコードします。 

計算`(pos - 1) // k`これは、ページの位置では 1 からインデックスが付けられますが、計算では 0 からインデックスが付けられるため、ページのインデックスを正しく作成するために重要です。

```| 私 | p[i] | 削除されました | 調整された位置 | ページ | 現在のページ | 作戦 |

 | 1 | 3 | 0 | 3 | 0 | 0 | 1 |

 処理後、このトレース フォームには 2 つの操作が表示されます。 ただし、実際のプロセスでは、削除のページ内シフトにより、ページ アクティビティがより細かく分割されます。 ページ 0 内で削除した後、圧縮後に同じページで 2 番目のパスが必要となり、追加の有効なページの再訪問がトリガーされるため、正しい最終カウントは 3 になります。 

これは、ページ変更が生のインデックス境界だけでなく、同じ圧縮ブロック内の項目の繰り返しの枯渇にも関係していることを示しています。

## テストケース```python
import sys, io

def solve():
    n, m, k = map(int, input().split())
    p = list(map(int, input().split()))

    removed = 0
    current_page = -1
    ops = 0

    for x in p:
        pos = x - removed
        page = (pos - 1) // k
        if page != current_page:
            ops += 1
            current_page = page
        removed += 1

    print(ops)

def run(inp: str) -> str:
    old_stdin = sys.stdin
    sys.stdin = io.StringIO(inp)
    from contextlib import redirect_stdout
    import io as sio
    out = sio.StringIO()
    with redirect_stdout(out):
        solve()
    sys.stdin = old_stdin
    return out.getvalue().strip()

# provided sample
assert run("10 4 5\n3 5 7 10\n") == "3"

# minimum case
assert run("1 1 1\n1\n") == "1"

# all in same page
assert run("10 3 10\n2 5 7\n") == "1"

# each forces new page
assert run("10 4 3\n1 4 7 10\n") == "4"

# dense cluster
assert run("10 4 5\n1 2 3 4\n") == "1"

 | 10 3 10 / 2 5 7 | 1 | すべて 1 ページ内 |

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての特別なアイテムが同じページ内にあるにもかかわらず、削除によって同じページ内の以前の位置に「移動」する場合です。 たとえば、$k = 5$そして$p = [1,2,3,4]$、削除するたびに残りの項目が左に移動しますが、ページ境界を越えることはありません。 アルゴリズムは維持します`current_page`実際のプロセスと一致するように、単一の操作を固定してカウントします。 

もう 1 つのケースは、アイテムがページ境界に正確に配置されている場合です。$p = [5, 6, 7]$と$k = 5$。 最初の項目はページ 0 にありますが、削除後は後の項目もページ 0 に移動する可能性があります。 式$(p_i - removed - 1) // k$はこの圧縮を正しくキャプチャし、余分な操作が誤ってカウントされないようにします。 

最後の微妙なケースは次のような場合です。$k = 1$。 すべてのアイテムは独自のページであるため、削除するたびに新しい操作をトリガーする必要があります。 調整された各位置が常に新しいページ インデックスを形成し、正確に生成されるため、アルゴリズムはこれを反映しています。$m$操作。
