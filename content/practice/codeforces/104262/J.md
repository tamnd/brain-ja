 ## 解決策
 ## 問題の理解

 私たちには次のようなシステムが与えられています$n$それぞれのエンジンには時間の経過とともに変化する燃料要件があります。 初めはどのエンジンも$i$初期燃料必要量がある$f_{1,i}$。 その後には、$m$イベント。 各イベントは特定のタイム ステップで発生し、連続するセグメント内のすべてのエンジンの燃料必要量が増加します。$[l_t, r_t]$定額で$d_t$。 これらの更新は時間の経過とともに蓄積されるため、後の燃料値には、各エンジンに影響を与えた以前のすべての寄与が含まれます。 

したがって、エンジンの燃料値は静的なものではなく、時間の経過とともに適用される範囲加算のプレフィックス累積結果です。 クエリでは、さまざまなエンジンの合計燃料を要求します。$[ql, qr]$ただし、時間の経過による燃料の進化のみを考慮しています$a$時間までに$b$。 時間間隔には包括的な値が含まれ、次まで延長される場合があります。$m+1$、すべての更新後の状態を表します。 

主な問題点は、エンジン インデックスと時間の両方の要素が動的であることです。 各更新はエンジンの範囲に影響し、各クエリはエンジンの範囲と時間の範囲の両方にわたって集計されます。 

この制約により、次元ごとに線形または線形に近い解決策が求められます。 と$n, m, q \le 2 \cdot 10^5$、クエリごとにすべてのエンジンまたはすべての更新を再計算するアプローチは、すぐに時間制限を超えてしまいます。 フルタイム進化の素朴なシミュレーションには、最大で次のことが含まれます。$O(nm)$移行は実現不可能です。 

クエリに時間が含まれる場合、微妙なエッジケースが発生します。$m+1$。 つまり、すべての更新後のシステムを単なる中間状態ではなく、有効なクエリ エンドポイントとして扱う必要があります。 もう 1 つのエッジ ケースは、クエリが単一のエンジンまたは単一のタイム ステップにまたがる場合です。 このような場合、時間範囲のプレフィックス処理で off-by-one エラーが発生します。 

## アプローチ

 直接シミュレーションでは、エンジン値の配列が時間の経過とともに維持されます。 更新ごとにセグメントが変更され、各クエリで複数の時間層の部分配列の合計が再計算されます。 これには、クエリごとにプレフィックスの合計を再計算するか、配列の完全な履歴を維持する必要があります。 エンジン全体のプレフィックス合計を使用しても、各時間ステップは依然として最大で変化します。$O(n)$価値観につながる$O(nm)$全体的に作業量が大きすぎます。 

重要な観察は、問題はエンジン インデックスと時間の両方において線形であり、更新は追加的であるということです。 各更新は、エンジン範囲と時間間隔の両方に重複するすべてのクエリに独立して寄与します。 これは、貢献を分離できることを示唆しています。 

進化する配列の観点から考えるのではなく、各更新を、一方の軸がエンジン インデックス、もう一方の軸が時間であるグリッド上の 2D 長方形の加算に寄与するものとして再解釈します。 クエリは、このグリッド内の四角形の合計を要求します。 これにより、問題は古典的なオフライン 2D 範囲合計問題に変換されます。 

私たちは、時間の経過とともに範囲クエリをプレフィックスの違いに変えるというアイデアを使用して、この値をさらに削減します。 お問い合わせの場合$[a, b]$まで寄与度を計算します。$b$マイナス寄与分まで$a-1$。 したがって、時間の経過に伴うプレフィックスの蓄積をサポートする構造のみが必要です。 

毎回の更新ごとに$t$、貢献します$d_t$すべてのエンジン位置に$[l_t, r_t]$いつでも$\ge t$。 固定クエリの場合は、次のことのみを考慮します。$t$中にある$[a, b]$。 これにより、問題は、更新間隔とクエリ四角形の間の重み付けされた重複をカウントすることに変換されます。 

時間をかけてスイープし、エンジン インデックス上のフェンウィック ツリー (またはセグメント ツリー) を維持することで、すべてのイベントをオフラインで処理できます。 各タイム ステップで、エンジンの範囲追加として更新を適用します。 また、2 つの Fenwick スナップショットを維持するか、時間の経過とともに差分手法を使用することによって、時間境界に達したクエリも処理します。 

より構造化された方法は、差分配列による範囲の加算と範囲の合計をサポートするフェンウィック ツリーと組み合わせて、経時的なスイープを使用することです。 現在のアクティブなコントリビューションを格納するエンジン位置の BIT を維持しながら、時間をかけてイベントを処理します。 クエリごとに、一度に合計を計算します$b$時刻の合計を引いたもの$a-1$これは、クエリ エンドポイントを保存し、2 回評価することで実行できます。 

これにより、更新が時間順に 1 回適用され、プレフィックス蓄積スナップショットを使用して各クエリに応答するオフライン ソリューションが実現します。

 ## アルゴリズムのチュートリアル

 時間処理をプレフィックス蓄積に変換し、エンジン処理をフェンウィック ツリー構造に変換します。 

1. 各クエリを分割する$(ql, qr, a, b)$2 つのサブクエリに分割: 1 つはプレフィックス用$b$、プレフィックス用に 1 つ$a-1$、反対の符号を持ちます。 これは、貢献度が超過しているためです。$[a,b]$までのプレフィックスに等しい$b$までのマイナス接頭辞$a-1$。 これにより、フルタイム履歴を明示的に維持することが回避されます。 
2. すべての更新とクエリを時間順に並べ替えます。 各更新は、その時間インデックスからアクティブになるイベントです。 
3. エンジン インデックスに対するフェンウィック ツリーを維持します。 ツリーには、現在までに適用されたすべての更新の現在の累積効果が保存されます。 
4. 1から2までの処理時間$m+1$。 毎回$t$、まずアップデートを適用します$t-1$(アップデート以降$t$への移行に影響を与える$t+1$）。 これにより、状態とプレフィックス解釈の一貫性が保たれます。 
5. クエリのエンドポイント時間に到達するたびに$t$、フェンウィック ツリーを使用してエンジン範囲全体の合計を計算し、適切な符号を付けて加算します。 
6. 内部的に差分配列を維持することにより、フェンウィック ツリーで範囲更新 + 範囲クエリ トリックを使用します。 それぞれのアップデート$(l, r, d)$でのポイント更新となります。$l$そして$-d$で$r+1$、プレフィックスの合計で現在のエンジン値を表すことができます。 

すべてのイベントが処理された後、すべてのクエリの寄与が最終的な回答に蓄積されます。 

### なぜ効果があるのか

 このアルゴリズムは、時間とエンジンの両方の次元にわたる寄与の線形性に依存しています。 各アップデートは、その範囲内のすべてのエンジンに独立して寄与し、その後ずっと保持されます。 時間間隔をプレフィックスの差に変換することで、時間範囲に含まれるクエリに対して各更新が正確にカウントされるようになります。 フェンウィック ツリーにより、スナップショットごとにエンジン範囲が正しく集計されるようになります。 どちらの分解も正確で独立しているため、交互作用項が失われたり二重にカウントされたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_add(self, l, r, v):
        self.add(l, v)
        if r + 1 <= self.n:
            self.add(r + 1, -v)

def solve():
    n, m, q = map(int, input().split())
    base = list(map(int, input().split()))

    updates = []
    for _ in range(m):
        l, r, d = map(int, input().split())
        updates.append((l, r, d))

    queries = [[] for _ in range(m + 2)]
    ans = [0] * q

    for i in range(q):
        l, r, a, b = map(int, input().split())
        queries[b].append((i, l, r, 1))
        if a > 1:
            queries[a - 1].append((i, l, r, -1))

    bit = BIT(n)

    for i, v in enumerate(base, 1):
        bit.range_add(i, i, v)

    for t in range(0, m + 1):
        for idx, l, r, sign in queries[t]:
            ans[idx] += sign * (bit.sum(r) - bit.sum(l - 1))

        if t < m:
            l, r, d = updates[t]
            bit.range_add(l, r, d)

    print("\n".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```このソリューションは、初期の燃料要件を使用してフェンウィック ツリーを初期化します。 各アップデートはエンジンの範囲の追加として適用されます。 クエリはエンドポイントで 2 つのイベントに分割されるため、各クエリは、BIT からのプレフィックス合計を使用して、正に 1 回、負に 1 回の合計 2 回評価されます。 

主な微妙な点は順序付けです。クエリは一度に実行されます。$t$アップデートを適用する前に回答されます$t$、時間インデックス付けが状態遷移の定義と一致することを保証します。

 ## 特殊なケース

 微妙なエッジ ケースは、クエリが時間 1 で開始される場合です。その場合、何もありません。$a-1$したがって、正のエンドポイントのみが使用されます。 コードは明示的にチェックします`if a > 1`負の寄与を追加する前に、時間 0 への無効なインデックス付けを防ぎます。 

もう 1 つのケースは、クエリが次で終了する場合です。$m+1$。 これらは一定期間バケットに保存されます$m+1$、時間が経過しても更新が行われないため、$m$、状態は安定したままで、最終的な配列が正しく反映されます。
