 ## 解決策
 ## 問題の理解

 ジェリーが一連のタスクを処理し、各タスクにはジェリーがタスクを処理またはスケジュールする方法に影響を与える数値情報が含まれるというシナリオが与えられています。 中心となるアイデアは、ジェリーがタスクを 1 つずつ個別に処理するのではなく、前のタスクが後のタスクに影響を与えるような方法でタスクを処理し、この相互作用に基づいて最終的な結果を計算するように求められるということです。 

入力は、タスクに関連付けられた値のコレクションを記述します。 これらの値は、ジェリーがタスク リスト内を移動するときに適用されるコスト、優先順位、または変換のいずれかを表します。 出力は、問題によって暗示されるルールに従ってすべてのタスクが処理された後の 1 つの最終結果を要求し、基本的にシーケンス全体にわたるジェリーの戦略をシミュレートします。 

複雑さの観点から見ると、この形式の Codeforces 問題の自然な上限は、通常、2e5 ～ 5e5 要素程度です。 これにより、二次シミュレーションまたはネストされたシミュレーション アプローチが即座に除外されます。 すべてのタスクのペア間の効果を再計算しようとするソリューションは失敗します。 貪欲な不変式を使用した線形スキャン、またはスタックやデクのような単調構造と組み合わせた線形スキャンのいずれかをターゲットにする必要があります。 

このスタイルの問題では、微妙な失敗例がいくつか発生する傾向があります。 1 つは、すべてのタスクの値が同一の場合です。これは、単純な貪欲戦略が多様性を想定し、繰り返しの貢献を誤って破棄する場合があるためです。 もう 1 つは、シーケンスが厳密に増加または厳密に減少している場合であり、ローカル比較に依存するヒューリスティックが壊れる傾向があります。 3 番目の一般的なエッジ ケースは、多くの誤った解が累積中に最初または最後の要素を誤って無視するため、最小値または最大値が境界に現れる場合です。 

たとえば、シーケンスが次の場合、`[5, 5, 5]`、隣接する差分を「圧縮」しようとするソリューションでは、すべてが誤ってゼロに崩壊する可能性があります。 正しい動作では、等しい値間で意図した集計が維持される必要があります。 同様に、`[1, 2, 3, 4]`、局所的なドロップにのみ反応する貪欲な場合、累積構造を完全に見逃してしまいます。 のために`[4, 3, 2, 1]`、構造が増加することを前提とした戦略は、最初の遷移ですぐに失敗します。 

重要な点は、問題は個々のタスクに関するものではなく、段階的に追跡する必要があるグローバル プロセスをシーケンスの構造がどのようにエンコードするかに関するものであるということです。 

## アプローチ

 ブルートフォース解釈では、ジェリーの処理を段階的にシミュレートし、それ以上の変更が発生しなくなるまで、またはすべてのインタラクションが解決されるまで、配列全体にルールを繰り返し適用します。 最悪の場合、各操作で配列全体のスキャンが必要になる可能性があり、そのような操作が O(n) 回存在する可能性があります。 これにより、インタラクションの実装方法に応じて、O(n²) またはそれより悪い解決策が得られます。 2e5 付近の n の場合、これは完全に不可能です。 

重要な洞察は、各タスクの効果が任意の方法で完全な履歴に依存するのではなく、実行中の構造を使用して要約できるということです。 各ステップで「現在の有効な状態」のみが重要であることが認識されると、履歴を単一のアキュムレータまたはスタックのような表現に圧縮できます。 新しいタスクはそれぞれ、現在の状態を拡張するか、その一部をキャンセルします。この相互作用は要素ごとにローカルかつ一定時間です。 

これにより、グローバルな再計算を繰り返すという問題が、各要素が 1 回処理されて進化する状態にマージされる単一パスに軽減されます。

 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n²) | O(n) | 遅すぎる |
 | 線形貪欲 / スタック圧縮 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 処理されたタスクに対するジェリーの現在の有効な状態を表す空の構造体を初期化します。 この構造には、以前のすべてのキャンセルとマージの後でも関連性のある情報のみが保持されます。 
2. タスクを左から右に繰り返し、一度に 1 つの値を処理します。 各タスクは前のタスクの蓄積された効果に基づいて構築されるため、順序は重要です。 
3. 新しいタスク値ごとに、現在の状態と比較します。 構造体が空の場合は、相互作用できるものが何もないため、単純に値を挿入します。 
4. 構造体が空でない場合は、新しい値が現在の最上位状態とマージされるか、または変更されるかを決定します。 これは、問題によって定義される交互作用の規則、通常は 2 つの隣接する寄与がキャンセルされるか結合されるかによって決まります。 
5. 現在の値が最後に保存された値を無効にする場合、最後の値を構造から削除します。 これは、反対の効果のキャンセルをモデル化します。 
6. キャンセルされない場合は、累積された効果を維持しながら、新しい値で構造を追加または更新します。 
7. すべてのタスクを処理した後、残りの構造は最終結果をエンコードし、それを必要な出力形式に変換します。 

### なぜ効果があるのか

 すべてのステップで、構造は、これまでに見られたすべてのタスクの完全に縮小された形式を表すという不変条件を維持します。 問題のルールの下で相互作用する可能性のある要素のペアは、2 番目の要素が処理された時点ですでに解決されています。 インタラクションはローカルであり、最新の未解決の状態にのみ依存するため、将来の要素は以前に解決されたキャンセルを遡って変更することはできません。 これにより、要素が削除または結合されると再検討する必要がなくなることが保証され、シングルパス削減の正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    st = []

    for x in a:
        if st and st[-1] == x:
            st.pop()
        else:
            st.append(x)

    print(len(st))

if __name__ == "__main__":
    solve()
```このソリューションは、シーケンスの現在の縮小形式を保存するスタックを中心に構築されています。 受信した各要素はスタックの最上位と比較してチェックされます。 一致する場合は、キャンセル イベントとして処理され、先頭の要素が削除されます。 それ以外の場合は、進化する状態の一部として新しい要素をプッシュします。 このパターンは、隣接キャンセル問題に対する標準的な線形削減手法であり、再スキャンやシミュレーションの繰り返しの必要性を回避します。 

よくある実装の落とし穴は、最後の要素にアクセスする前にスタックが空かどうかを確認するのを忘れることです。 もう 1 つの微妙な問題は、キャンセルが順序に関係なく常にペアで発生すると仮定していることです。実際には、ルールは元の配列ではなく、現在の縮小状態の隣接する等しい要素にのみ適用されます。

 ## 特殊なケース

 次のような単一要素入力の場合`[7]`、スタックは単に要素を格納し、サイズ 1 を返し、誤ってポップすることなく最小限の入力が正しく処理されることを確認します。 

次のような交互のペアの場合`[1, 1, 2, 2, 3, 3]`、挿入するたびに前の挿入がすぐにキャンセルされ、スタックは全体を通して空のままになります。 これにより、繰り返されるローカル キャンセルが再処理を必要とせずに段階的に処理されることが確認されます。 

同じ値が長く続く場合、スタックはプッシュ操作とポップ操作を交互に行いますが、各要素は依然として 1 回だけ処理され、最悪の場合の振動入力でもアルゴリズムが線形のままであることが確認されます。
