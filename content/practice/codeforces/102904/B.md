 ## 解決策
 ## 問題の理解

 私たちには、順番に満たされる必要がある一連の金銭要求と、ゼロから始まる固定の利用可能な金額が与えられます。 リクエストごとに利用可能な残高が増加または減少し、シーケンスが進むにつれてプロセスは段階的に進化します。 このタスクは、操作によって暗示されるルールに従って、残高が無効になることなくすべてのリクエストを処理できるかどうかを判断し、すべてを処理した後の最終状態を計算することです。 

この問題を考えるのに役立つ方法は、一連のトランザクションの下で金融口座をシミュレートしているということです。 操作ごとに現在の残高が変更され、システムはどの時点でも残高がゼロを下回ることを暗黙的に禁止する場合があります。これは、利用可能な以上のお金を使おうとすることに相当するためです。 このシミュレーションがうまく進むか、その結果バランスがどうなるかによって出力が決まります。 

この制約は、シーケンスの長さが十分に大きくなり、二次再計算または反復再計算アプローチが失敗する可能性があることを意味します。 したがって、ソリューションは各演算を一定時間または対数時間で、理想的には単一の線形パスで処理する必要があります。 

主な微妙な点は、中間のバランスが最終値よりも重要であるというエッジ ケースでは、単純なシミュレーションが機能しなくなる可能性があることです。 たとえば、次のようなシーケンスを考えてみましょう。`[+5, -3, -4]`。 単純なアプローチでは、純額のみに焦点を当てる可能性があります。`-2`、不可能であると結論付けますが、実際の失敗は残高がマイナスになる 3 番目のステップで発生します。 逆に、次のようなシーケンス`[+5, -2, -3]`最終的な残高がゼロであっても、実現可能性を維持します。 正確さは、合計だけではなく、実行中のプレフィックスを追跡することに依存します。 

すべての演算が負の場合、別の特殊なケースが発生します。 例えば`[-1, -1, -1]`最終的な合計に関係なく、すぐに失敗します。 最終的なバランスだけをチェックする不用意な解決策では、そのようなケースが誤って受け入れられてしまいます。 

## アプローチ

 ブルートフォース解釈は単純なシミュレーションです。 実行バランスを維持し、配列を反復処理して、各操作を 1 つずつ適用します。 更新のたびに、残高が有効であるかどうかを確認します。 無効になった場合は、早期に停止して失敗を報告します。 

このアプローチは、問題で説明されているプロセスを直接モデル化しているため、正しいです。 ただし、その非効率性は正確さではなく、すべてのプレフィックスの有効性を最初から再計算したり、以前のセグメントを複数回再チェックしたりするなど、より単純な方法またはネストされた方法で実装された場合に再計算が繰り返される可能性があることにあります。 増分状態の維持に注意しないと、最悪の場合、O(n²) の動作に陥ります。 

重要な洞察は、システムには現在の残高を超える履歴依存性がないということです。 各操作は単一のスカラー状態を変更し、すべての制約はその状態に対してローカルです。 これは、以前の決定を見直す必要がないことを意味します。 プロセス全体は、各ステップで下限制約を強制しながらプレフィックスの合計を維持することに帰着します。 

これにより、問題が単一の線形スキャンに変換され、バランスが更新され、すぐに検証されます。

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. 変数を初期化する`balance`現在の利用可能な金額を表すにはゼロにします。 これは、トランザクションが適用される前のシステム状態を表します。 
2. 操作のリストを順番に繰り返し、更新します。`balance`各演算値を加算することによって。 これは、各リクエストがアカウントを直接変更する、問題で説明されている実際のプロセスをモデル化しています。 
3. 各操作を適用した後、すぐに次のことを確認します。`balance`マイナスになってしまった。 存在する場合は、プロセスを終了し、失敗を返します。 このチェックにより、どの時点でも保有額以上の支出はできないという制約が強制されます。 
4. 残高がゼロを下回らずに反復が完了した場合は、最終残高とともに成功を返します。 最終的な値は、すべての有効なトランザクションが適用された後の残りの金額を表します。 

### なぜ効果があるのか

 重要な不変条件は、反復の各ステップで、`balance`これまでに処理されたすべての操作の合計と等しくなります。 各操作は 1 回だけ適用され、将来の値に依存する操作はないため、状態はこの現在の合計によって完全に把握されます。 有効性の条件は、プレフィックスの合計が負になるかどうかのみに依存します。 この条件に違反するプレフィックスがない場合、すべての中間状態が有効となり、プロセスはシステムのルールと一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    arr = list(map(int, input().split()))

    balance = 0
    for x in arr:
        balance += x
        if balance < 0:
            print("NO")
            return

    print("YES")
    print(balance)

if __name__ == "__main__":
    solve()
```解は単一の整数を維持します`balance`配列をスキャンしながら更新します。 実装の重要な詳細は、各更新後の即時チェックです。これにより、検証を延期するのではなく、無効な状態が発生したらすぐに検出できるようになります。 この関数は障害発生時に早期に終了するため、ランタイムは直線的に保たれます。

 ## 特殊なケース

 エッジ ケースの 1 つは、最初の演算が負の場合です。 入力用`n = 3, [-1, 2, 3]`、アルゴリズムは最初のステップを処理し、すぐに検出します`balance = -1`、失敗を返します。 これにより、早期終了が正しく処理され、それ以上の処理が必要ないことが確認されます。 

もう 1 つのエッジ ケースは、値が振動するものの、ゼロを下回らない場合です。 のために`3, [1, -1, 1]`、バランスは次のように進化します`1 → 0 → 1`。 このアルゴリズムは失敗条件をトリガーすることはなく、ゼロと等しいことが許可され、厳密に負の値のみが禁止されていることを示しています。 

最後のエッジ ケースは、長いゼロのシーケンスです。 のために`5, [0, 0, 0, 0, 0]`、残高はずっとゼロのままです。 アルゴリズムはシーケンスを正しく受け入れ、変更しない操作が有効性に影響を与えないことを確認します。
