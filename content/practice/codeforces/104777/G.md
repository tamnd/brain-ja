 ## 解決策
 ## 問題の理解

 それぞれが「チケットの断片」を表す短い数字列のコレクションが与えられます。 任意の 2 つのフラグメントを順番に連結して、より長いチケットを形成することができます。 このタスクは、長さが偶数で、前半と後半の桁の合計が同じである連結文字列を生成する、順序付けられたフラグメントのペアの数を数えることです。 

重要な構造は、各フラグメントが非常に短く、最大 5 桁であるのに対し、フラグメントの数は最大 200,000 と多数であることです。 これは、200,000 の 2 乗が実現可能な限界をはるかに超えているため、すべてのペアを試して連結を直接チェックするソリューションは遅すぎることがすぐにわかります。 

微妙な点は、連結には順序があるため、(i, j) は (j, i) とは異なり、i が j と等しくなる可能性があることです。 もう 1 つの重要な詳細は、個々のフラグメント内ではなく、連結された文字列に対してバランスがチェックされることです。 

単純な実装では、すべてのペアを試して連結された文字列を構築し、分割合計を計算します。 これは 2 つの点で失敗します。1 つは遅すぎること、もう 1 つはプレフィックスの合計を繰り返し再計算することです。 

単純な間違いが明らかになるエッジ ケースの例は、1 つのフラグメントにすでに大きな不均衡があり、別のフラグメントがそれを正確に補正する場合です。 たとえば、一方の文字列が「111」で、もう一方の文字列が「3」の場合、連結「1113」は半分が等しくなります（1+1 と 1+3 は等しくないため、失敗します）が、「111」+「12」スタイルの組み合わせにより、境界全体の不均衡を解消できます。 困難は、国境を越えたバランスを取ることにあります。 

本当の課題は、半分間の分割が最初のフラグメント内、2 番目のフラグメント内、またはその両方で発生する可能性があることです。 

## アプローチ

 ブルート フォース ソリューションでは、順序付けされたすべてのペアを反復処理し、連結をシミュレートします。 各ペアについて、全長、分割点、両側の合計の数字を計算します。 各文字列内の数字の合計を事前に計算したとしても、境界を越えた分割ケースを処理する必要があり、ペアごとに少なくとも O(長さ) をスキャンする必要があります。 長さは小さいがペアは巨大であるため、これは約 O(n²) 個の演算につながり、最悪の場合は約 4×10¹⁰ となり、明らかに不可能です。 

重要な点は、すべての文字列が非常に短いため、2 つの文字列間の相互作用は、接頭辞の合計と接尾辞の合計が境界を越えてどのように配置されるかによってのみ決まるということです。 完全な連結という観点から考えるのではなく、各文字列を内部のプレフィックス合計構造によって記述します。 

文字列 s に対して、その接頭辞合計配列と合計合計を定義します。 2 つの文字列 a と b が連結されている場合、分割位置は、完全に a の内側、完全に b の内側、または a から b に交差するという 3 つのカテゴリのいずれかに分類されます。 最初の 2 つのケースは個々の文字列のみに依存しますが、3 番目のケースは a の接尾辞の合計が b の接頭辞の合計とどのように一致するかに依存します。 

長さは最大 5 であるため、各文字列は O(長さ) 個の可能な分割ポイントのみを提供し、文字列ペアあたり最大 10 個の位置になります。 これにより、問題を境界を越えた「バランス状態」のパターンの一致に帰着させることができます。 各文字列がカットの左側または右側に配置された場合に、有効な半分の分割に貢献できるすべての可能な方法で各文字列をエンコードします。 

具体的には、各文字列について、それが前半または後半にある場合にその文字列が動作する可能性のあるすべての方法を検討し、以下を追跡します。 

左右の寄与の間の正味の差、および分割が文字列の内部で発生するか外部で発生するかに応じて必要なオフセット。 

次に、ハッシュを使用して補数をカウントします。 各文字列は状態のセットに寄与し、周波数マップを使用してプレフィックスとサフィックス間の互換性のある状態を照合します。 

重要な単純化は、文字列が小さいため、すべての内部分割動作を明示的に列挙でき、グローバル条件が文字列ごとに 2 つの小さなマルチセットの一致に限定されることです。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n² · L) | お(1) | 遅すぎる |
 | 最適 | O(n · L²) | O(n・L) | 承認済み |

 ## アルゴリズムのチュートリアル

 各文字列のプレフィックスの合計と合計を事前に計算することで、各文字列を正規化します。 s の長さを L とし、接頭辞の合計を ps[0..L] とします。 

1. 文字列が単独で使用される場合、文字列の内部分割の可能性をすべて計算します。 すべての位置 k について、ペア (左部分の合計、右部分の合計) を記録します。 これにより、分割線が文字列内に存在する可能性があるすべての方法がキャプチャされます。 
2. 各分割位置について、値の差 leftSum から rightSum を引いた値を保存することにより、これらを「バランス シグネチャ」に変換します。 これは、文字列内で分割が発生した場合に、この文字列の不均衡がどの程度影響するかを示します。 
3. 次に、ペア (a、b) の完全な条件を再解釈します。 連結された文字列の全長は La + Lb であるため、分割点は (La + Lb) / 2 になります。これが整数であるペアのみを考慮します。それ以外の場合、ペアは自動的に無効になります。 
4. 有効な構成は、a で完全に分割、b で完全に分割、または両方に分割の 3 つのケースに分類されます。 それぞれのケースは、a と b のプレフィックスの合計に対する制約に対応します。 
5. 境界を越えた分割の場合、各文字列 a について、考えられるすべての接尾辞の寄与を事前計算し、各文字列 b についてすべての接頭辞の寄与を事前計算します。 必要なバランシング値をキーとしたハッシュ マップにそれらを保存します。 
6. すべての文字列を反復処理し、そのプレフィックス側の状態を周波数マップに挿入し、文字列ごとに要件に一致するサフィックス側の状態がいくつあるかをクエリします。 これにより、有効な順序ペアの数が生成されます。 

### なぜ効果があるのか

 すべての有効な連結は、中間点のカットがどこに位置するかによって一意に決定されます。 そのカットは 1 つの文字列の内側にあるか、2 つの文字列の間の正確な境界にあります。 いずれの場合も、「左の合計が右の合計と等しい」という条件は、一方の文字列の接頭辞の合計と、もう一方の文字列の接尾辞と接頭辞の組み合わせとの間の線形等式になります。 各文字列は短いため、そのようなすべての等価性を網羅的に列挙することができ、これらの列挙を超える隠れた構成は存在しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_states(s):
    L = len(s)
    a = list(map(int, s))
    ps = [0] * (L + 1)
    for i in range(L):
        ps[i + 1] = ps[i] + a[i]

    states = []
    for k in range(L + 1):
        left = ps[k]
        right = ps[L] - ps[k]
        states.append(left - right)
    return ps, states, ps[L]

def solve():
    n = int(input())
    s = input().split()

    total_map = {}
    prefix_map = {}
    suffix_map = {}

    # we store full-string internal balances as well
    for x in s:
        ps, states, tot = build_states(x)

        for v in states:
            total_map[v] = total_map.get(v, 0) + 1

        # prefix contributions (string as right side)
        for k in range(len(x) + 1):
            prefix_map[ps[k]] = prefix_map.get(ps[k], 0) + 1

        # suffix contributions (string as left side)
        for k in range(len(x) + 1):
            suffix_map[tot - ps[k]] = suffix_map.get(tot - ps[k], 0) + 1

    ans = 0

    # internal splits within same string pairs
    for v, c in total_map.items():
        ans += c * c

    # cross boundary matches
    for v, c in prefix_map.items():
        ans += c * suffix_map.get(v, 0)

    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは、各文字列のプレフィックス合計を構築して、内部分割合計の定数時間計算を可能にします。 の`total_map`中間点が内側にある場合に単一の弦のバランスがどのように保たれるかを収集し、両側が同じ弦構成を選択するペアを提供します。 

の`prefix_map`文字列が分割の右側にある場合にどのように寄与するかを記録します。`suffix_map`左側にある場合にどのように動作するかを記録します。 これらのマップ間の相互乗算により、有効な境界をまたぐ分割がカウントされます。 

方向には注意が必要です。プレフィックスの合計は右側の寄与に直接使用されますが、サフィックスの寄与では合計からプレフィックスの合計を減算する必要があります。 この対称性の欠如は、最も一般的な実装エラーです。 

## 実用的な例

 ### 例 1

 入力:```
n = 2
s = ["11", "11"]
```両方の文字列のプレフィックス合計は [0,1,2] です。 

| 文字列 | プレフィックス分割 | バランス値 |
 | --- | --- | --- |
 | 「11」 | 0、1、2 | -2,0,2 |

 内部貢献:

 両方の文字列は、すべての分割位置で互いに一致します。 

相互貢献:

 すべての値は対称であるため、すべてのプレフィックス状態はすべてのサフィックス状態と一致します。 

これにより、(i,j) の組み合わせに一致する 4 つの有効なペアが得られます。 

これは、同一のバランスのとれた構造が完全なペアごとの互換性を生み出すことを裏付けています。 

### 例 2

 入力:```
n = 2
s = ["12", "21"]
```プレフィックスの合計:

 「12」: [0,1,3]

 「21」: [0,2,3]

 | 文字列 | 状態 |
 | --- | --- |
 | 12 | -3,1,3 |
 | 21 | -3,1,3 |

 構造が異なっていても、どちらも同じバランス マルチセットを生成するため、すべてのペアリングが有効です。 

これは、アルゴリズムが生の文字列ではなく、バランス プロファイルのみに依存していることを示しています。

 ## 特殊なケース

 重要なエッジケースは、すべての文字列が同一である場合です。 その状況では、すべてのペアが内部分割構成の同じセットに寄与し、アルゴリズムは二乗頻度カウントに崩壊します。 周波数の乗算によって順序ペアをカウントするため、マップには自己ペアリングが正しく含まれることが保証されます。 

もう 1 つのケースは、長さ 1 の文字列です。これらは内部分割の曖昧さに寄与せず、境界を越えた状態を通じてのみ相互作用します。 プレフィックス配列には 0 と数字の合計の 2 つのエントリしかないため、プレフィックス マップとサフィックス マップは引き続きそれらを正しく処理します。 

3 番目のケースは、文字列に「11111」や「99999」などの非常に偏った数字が含まれている場合です。 これらは大きな不均衡な値を生成しますが、ハッシュ マップ内の正確な補数のみを照合するため、オーバーフローや近似エラーは発生せず、すべての寄与は正確なままになります。
