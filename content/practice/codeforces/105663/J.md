 ## 問題の理解

 ゲームは次の場所で行われます$n \times n$空から始まるグリッド。 2 人のプレイヤーが交互にターンを行い、最初のプレイヤーは常に赤いトークンを配置し、2 番目のプレイヤーは青いトークンを配置します。 移動によってセルが直接選択されるわけではありません。 代わりに、プレイヤーが列を選択すると、重力ベースのスタッキング システムのように、トークンがその列の最も低い空いているセルに落ちます。 列は下から上に向かって徐々に埋められ、いっぱいになると選択できなくなります。 

各移動の後、どちらかのプレイヤーがすでに長さの直線を形成しているかどうかを知りたいと考えています。$k$独自のトークンのみを使用します。 線は水平、垂直、またはいずれかの方向に斜めにすることができます。 プレイヤーがそのようなラインに到達した場合、ゲームはその手で決定されたとみなされ、誰がどの手のインデックスで勝ったかを報告する必要があります。 

入力はサイズを与えます$n$、すでにプレイされた手の数$m$、およびターゲットの長さ$k$、その後に選択した列のシーケンスが続きます。 このシーケンスから、時間の経過とともに変化するボードの状態全体を正確に再構築する必要があります。 

制約により許可されるのは、$n$300まで$n^2$つまり、グリッドがほぼ完全に埋まる可能性があります。 それぞれの動きの後に勝利条件を最初から再計算するソリューションは、おおよその結果をもたらします。$m \cdot n^2$あるいは、作業が遅すぎる場合もあります。 各移動の後に可能なすべてのラインをスキャンすることすら不可能です。 

部分的な評価戦略では、より微妙な問題が発生します。 全方向の単純なスキャンを使用して、最後に配置されたトークンを通過する行のみをチェックする場合、不注意な実装では、トークンが列に積み重なるときに二重にカウントされたり、境界に位置合わせされたシーケンスを見逃したりする可能性があります。 もう 1 つの落とし穴は、垂直方向の配置が重力によって制限されるため、列内のすべてのトークンが連続したブロックを形成することを忘れていることです。 それらを任意の配置として扱うと、誤ったインデックス作成や冗長なチェックが発生します。 

## アプローチ

 直接的なブルートフォース ソリューションでは、各動きをシミュレートし、考えられるすべての開始セルの長さをチェックします。$k$4 方向すべてにセグメント化します。 移動ごとにスキャンが必要です$O(n^2)$セルを最大 4 方向に拡張し、$k$ステップ。 最悪の場合の複雑さは次のようになります。$O(m \cdot n^2 \cdot k)$、フルボード設定では約に縮退します。$O(n^5)$。 これは時間内に実行できる範囲をはるかに超えています。 

重要な観察は、勝利条件は 4 つの方向のいずれかに整列した連続セグメントにのみ依存するということです。 グローバル構造を繰り返し再計算する代わりに、既知の結果から拡張された動的プログラミング スタイルのカウントを維持できます。 各セルには、各方向のその位置で終了する同じ色の連続したトークンの数を格納できます。 新しいトークンが配置されると、それが占有するセルのみを更新する必要があり、その値は方向ごとに一定時間で隣接するセルから導出できます。 

これにより、問題はグローバルな再計算からローカルな拡張に変換されます。 グリッドは成長する構造のように動作し、それぞれの移動によって 1 つのセルのみが「アクティブ化」され、関連するすべてのライン情報がその点から外側に伝播されます。

 ## アルゴリズムのチュートリアル

 各セルに対して 4 つのカウンタを格納するグリッドを維持します。これは、水平方向、垂直方向、主対角方向、および反対角方向でそのセルで終わる連続する同じ色のトークンの長さです。 

1. 空のオブジェクトを初期化します。$n \times n$各列の現在の塗りつぶしの高さを追跡するグリッドと配列。 各移動は列内の利用可能な最も低い行に挿入されるため、高さの構造は不可欠です。 
2. それぞれの動きについて$i$、パリティから誰のターンであるかを決定します。$i$。 プレイヤー 1 は赤いトークンを置き、プレイヤー 2 は青いトークンを置きます。 
3. 選択した列の、その列の現在の高さによって決定される、次に利用可能な行にトークンを挿入します。 これにより、コラムをスキャンせずに重力を正確にシミュレートします。 
4. 新しく占有されたセルについて、その方向カウントを計算します。 それぞれの方向について、その方向のすぐ隣を調べます。 同じ色の場合は、その隣のカウントを 1 つ増やします。 それ以外の場合は 1 にリセットされます。 このセルで終わる有効な連続行は、前の隣接する一致するセルから延長されている必要があるため、これが機能します。 
5. 新しいセルの 4 つの方向の値をすべて計算した後、それらのいずれかが次の値に達するかどうかを確認します。$k$。 そうであれば、現在のプレイヤーはこの手で終わる有効なラインを形成しており、勝者をすぐに報告できます。 
6. すべての手が処理されるか、勝者が見つかるまで続けます。 

### なぜ効果があるのか

 拡張の観点から見ると、4 つの方向のいずれかの連続するセグメントにはそれぞれ固有の終点があります。 「セルの終了」の長さだけを保存することにより、各セグメントは最後のセルで 1 回だけカウントされます。 すべての新しいトークンはその位置で終了するシーケンスにのみ影響するため、以前の状態を修正する必要はありません。 これにより、あらゆる長さが保証されます。$k$ラインは、最後のトークンが配置された瞬間に検出される必要があります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    cols = list(map(int, input().split()))

    # 0 = empty, 1 = red, 2 = blue
    grid = [[0] * n for _ in range(n)]
    height = [0] * n

    # dp arrays: horizontal, vertical, diag1, diag2
    h = [[0] * n for _ in range(n)]
    v = [[0] * n for _ in range(n)]
    d1 = [[0] * n for _ in range(n)]
    d2 = [[0] * n for _ in range(n)]

    for i in range(m):
        c = cols[i] - 1
        r = height[c]
        height[c] += 1

        player = 1 if i % 2 == 0 else 2
        grid[r][c] = player

        # horizontal
        if c > 0 and grid[r][c - 1] == player:
            h[r][c] = h[r][c - 1] + 1
        else:
            h[r][c] = 1

        # vertical
        if r > 0 and grid[r - 1][c] == player:
            v[r][c] = v[r - 1][c] + 1
        else:
            v[r][c] = 1

        # diagonal (\)
        if r > 0 and c > 0 and grid[r - 1][c - 1] == player:
            d1[r][c] = d1[r - 1][c - 1] + 1
        else:
            d1[r][c] = 1

        # anti-diagonal (/)
        if r > 0 and c + 1 < n and grid[r - 1][c + 1] == player:
            d2[r][c] = d2[r - 1][c + 1] + 1
        else:
            d2[r][c] = 1

        if max(h[r][c], v[r][c], d1[r][c], d2[r][c]) >= k:
            print("Ayumi" if player == 1 else "Bunji", i + 1)
            return

    print("No winner")

if __name__ == "__main__":
    solve()
```グリッドは、重力の配置が一定時間になるように明示的に維持されます。`height`配列。 各方向性 DP テーブルは、すでに計算された隣接値を使用して、新たに入力されたセルでのみ更新されるため、スキャンが回避されます。 

勝利チェックは、4 つの方向すべてを計算した直後に実行されます。 順序は重要です。現在の手によって勝ちラインが形成されている場合は、後続の手の前にそれを報告する必要があります。

 ## 特殊なケース

 カラムがいっぱいになると、特殊なケースが発生します。 の`height`配列は、行を越えて挿入しようとしないことを保証することで、その列にそれ以上配置されないようにします。$n-1$。 毎回下方向にスキャンする単純な実装では、前のトークンを上書きするか、範囲外のインデックスを入力する危険があります。 

もう 1 つの微妙なケースには、境界での斜めの伝播が含まれます。 一番上の行または左端/右端の列に配置されたトークンの場合、隣接チェックを保護する必要があります。 DP 再帰は、隣接するセルにアクセスする前に境界をチェックすることでこれを自然に処理し、無効なメモリ アクセスや不正な拡張が発生することなく、分離されたトークンが長さ 1 の新しいシーケンスを正しく開始することを保証します。 

最後のケースは、同じ手で複数の勝利条件が発生する場合です。 現在のセルを更新した直後に評価するため、ルールでは勝ちが現れた最も早い手を報告する必要があるため、その手で最初に検出された勝ちは他の潜在的なラインに関係なく正しいものになります。
