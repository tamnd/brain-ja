 ## 解決策
 ## 問題の理解

 この問題では、グローバル ビット単位の演算とそれに続く 2 種類のクエリによって繰り返し変更される整数の配列について説明します。 1 つのクエリは特定の位置の現在の値を要求し、もう 1 つのクエリは配列全体で k 番目に大きい値を要求します。 クエリ間では、すべての要素に均一に適用される操作を除いて、配列は変更されません。 

重要な詳細は、操作がすべての要素に一度に適用される破壊的な更新 (ビットごとの AND、OR、および指定された数値との XOR) であるということです。 このような操作を数多く行った後、配列を明示的に維持すると、更新のたびにすべての要素が処理されるため、時間がかかりすぎます。 

2 番目のクエリ タイプはより微妙です。 位置は要求されませんが、配列全体の順序統計が要求されます。 つまり、高速なグローバル変換と高速なランキング クエリの両方をサポートする構造が必要です。 

制約 (このタイプの Codeforces タスクの標準) では通常、最大 200,000 の操作が許可され、クエリごとの要素ごとの更新は不可能になります。 演算のたびに配列全体を再計算する素朴なアプローチでは O(nq) がかかりますが、n と q の両方が大きい場合、これは実行可能な制限をはるかに超えます。 

素朴だが重要な失敗例は、グローバル ビット効果を考慮せずに XOR、AND、および OR を要素ごとに独立して更新可能として扱うことから発生します。 たとえば、配列が次の場合、`[1, 2, 3]`そして、XOR 演算を繰り返し適用し、クエリごとに各要素を直接再計算することは、多くの演算にわたって 2 次的になります。 

もう 1 つの微妙な落とし穴は、ビット単位の演算後の k 番目に大きいクエリを誤解することです。 たとえば、OR はビットの増加のみ、AND はビットのクリアのみ、XOR はビットを反転します。 これらの変換を適切に追跡しないと、更新のたびに配列を並べ替えると、中程度の入力であってもタイムアウトが発生します。 

## アプローチ

 ブルートフォースのアイデアは単純です。完全な配列を明示的に維持します。 AND、OR、または XOR 演算ごとに、すべての要素を反復処理して更新します。 ポイントクエリの場合は、保存された値を返します。 k 番目に大きいクエリの場合は、配列を並べ替えて必要な要素を選択します。 

これは定義を正確に反映しているため、正しく機能します。 すべての操作はすべての要素に適用され、並べ替えには常に真の順序が反映されます。 

ただし、各グローバル操作には O(n) のコストがかかり、並べ替えのため、k 番目のクエリにはそれぞれ O(n log n) のコストがかかります。 最大 q 個の演算では、合計の複雑さは O(nq + q n log n) になりますが、n と q が両方とも大きい場合、これは大きすぎます。 

重要な点は、すべての更新がビット単位で配列全体にわたって均一であることです。 各値を個別に追跡するのではなく、各ビット位置がグローバルにどのように変換されるかを追跡します。 各要素の値は、同じ一連のビットごとの関数によって変換されるため、変換を値ではなくビットのマッピングとして表すことができます。 

各ビットがどのように進化するかを説明する 2 つの概念マスクを維持します。XOR がビットを反転する方法と、AND/OR がビットを 0 または 1 に強制する方法です。この変換が維持されると、それを遅延適用して、必要な場合にのみ値を再構築できます。 

k 番目に大きいクエリに効率的に答えるために、必要な場合にのみ変換された値を再構築し、変換された表現を使用してクエリごとに 1 回ソートするか、制約に応じてビット状態の頻度をカウントできる構造を維持します。 

中心的な考え方は、ビット単位の操作がビット位置ごとに適切に構成され、更新ごとにすべての配列要素に触れる必要がなくなるということです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | ブルートフォース | O(nq + q n log n) | O(n) | 遅すぎる |
 | ビットごとの変換の追跡 | O(q log A + n log A) 償却 | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは、任意の数値の各ビットが一連の演算によってどのように変換されるかをコンパクトに表現します。 配列を変更する代わりに、これまでに適用されたすべての操作で単一ビットに何が起こるかを示す「遅延ビット関数」を維持します。 

1. 変換を適用しない状態で開始します。つまり、すべてのビットが変更されずに通過します。 これは、各ビット位置の ID マッピングに対応します。 

2. 値 c の AND 演算の場合、c の 0 である各ビットは、すべての配列要素の対応するビットを強制的に 0 にします。c の 1 であるビットは影響を受けません。 これは、強制ゼロ化を反映するように変換を更新することを意味します。 

3. 値 c との OR 演算の場合、c で 1 である各ビットは、すべての要素で対応するビットを強制的に 1 にします。 それに応じてグローバル ビット マッピングを更新します。 

4. 値 c による XOR 演算の場合、c のビットが 1 であるときは常に、各ビットの状態が反転します。これは、それらのビット位置の変換状態を切り替えることによって処理されます。 

5. インデックス i の値クエリの場合、現在のビット変換を元の格納値 a[i] に適用し、現在の値を O(log A) に再構築します。 

6. k 番目に大きいクエリの場合、すべての要素に変換を適用し、結果を収集し、k 番目の統計を抽出します。 

この効率は、ステップ 2、3、および 4 が n に依存せず、ビット幅のみに依存するという事実から来ています。 すべての配列要素は、変換を通じて暗黙的に更新されます。 

### なぜ効果があるのか

どの時点でも、各要素は、ビットごとの演算の固定シーケンスを初期値に適用した結果です。 ビット単位の演算は各ビット位置で独立して動作するため、各ビットの最終値は最初のビットとそのビット位置に適用される演算のシーケンスのみに依存します。 この独立性により、要素ごとの更新をビットごとのステート マシンに置き換えることができます。 すべての要素が同じ変換を共有するため、オンデマンドで適用すると、直接インデックス付けと順序付けクエリの両方の正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def apply_transform(x, mask_and, mask_or, mask_xor):
    # first OR, then XOR, then AND (typical normalized form reasoning)
    x |= mask_or
    x ^= mask_xor
    x &= mask_and
    return x

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    mask_and = (1 << 20) - 1  # assume 20-bit values typical in CF
    mask_or = 0
    mask_xor = 0

    for _ in range(q):
        tmp = input().split()
        if tmp[0] == 'AND':
            c = int(tmp[1])
            mask_and &= c
            mask_or &= c
            mask_xor &= c

        elif tmp[0] == 'OR':
            c = int(tmp[1])
            mask_or |= c
            mask_and |= c

        elif tmp[0] == 'XOR':
            c = int(tmp[1])
            mask_xor ^= c

        elif tmp[0] == 'GET':
            i = int(tmp[1]) - 1
            print(apply_transform(a[i], mask_and, mask_or, mask_xor))

        else:  # KTH
            k = int(tmp[1])
            arr = [apply_transform(x, mask_and, mask_or, mask_xor) for x in a]
            arr.sort(reverse=True)
            print(arr[k - 1])

if __name__ == "__main__":
    solve()
```コードは、すべての操作の累積効果を表す 3 つのグローバル ビットマスクを維持します。 配列を更新する代わりに、各ビットの動作をエンコードするこれらのマスクを更新します。 の`apply_transform`関数は、必要に応じて要素の現在の値を再構築します。 

順序付けクエリはオンデマンドですべての値を再計算しますが、これは、そのようなクエリが比較的少ない場合にのみ許容されます。 この問題のより厳密なバージョンでは、遅延伝播を備えたビットごとのトライやセグメント ツリーなどのより高度なデータ構造が、この再構成ステップを置き換えます。 

よくある間違いは、内部で間違った順序で演算を適用することです。`apply_transform`。 正しい順序では、変換の構成方法を考慮する必要があります。つまり、OR で最初にビットを設定し、XOR でビットを反転し、最後にビットをクリアします。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 |---|---|---|
 | 時間 | O(q + n log n (k 番目のクエリごと) | ビットマスク更新は O(1)、順序付けクエリの場合のみ再構築 |
 | スペース | O(n) | 元の配列は変更せずに保存されます。 

このソリューションは、中程度の数の順序付けクエリに対して効率的であり、すべてのグローバル操作に対して一定時間のビットマスク更新に依存します。 これは、n と q が約 2e5 までであるものの、k 番目のクエリが支配的ではない一般的な制約に適合します。

 ## 特殊なケース

 クリティカルなエッジケースは、ビットを徐々に消去する AND 演算の繰り返しです。 のような入力の場合`[7, 3, 5]`連続して`AND 6`そして`AND 2`、変換により値がゼロに向かって縮小されます。 AND マスクは継続的に縮小し、再構築では常に最新のマスクが一貫して適用されるため、アルゴリズムはこれを処理します。 

XOR 演算が連続して何度も適用される場合、別のエッジ ケースが発生します。 たとえば、`XOR 1`2回効果を打ち消します。 XOR 累積は可逆的かつ自己反転であるため、マスク表現はこれを自然に捉えており、明示的に履歴を追跡しなくても状態が正しく切り替わります。 

3 番目のエッジ ケースには、重複を生成する大量の変換後の k 番目のクエリが含まれます。 複数の要素が同じ値に折りたたまれる可能性があるため、並べ替えはその時点で完全に再構築された値に対して動作し、多重性が維持されるため、引き続き正しく機能します。
