 ## 解決策
 ## 問題の理解

 位置 1 から位置 n まで一列に配置された一連のプラットフォームが与えられます。 各プラットフォームには高さがあります。 キャラクターはプラットフォーム 1 からスタートし、一連のジャンプを使用してプラットフォーム n に到達したいと考えています。 

プラットフォーム i からプラットフォーム j へのジャンプは、2 つの条件が同時に成立する場合にのみ許可されます。 まず、インデックス距離が d を超えてはいけないため、j はウィンドウ i - d から i + d 内になければなりません。 第 2 に、目的地のプラットフォームは現在のプラットフォームと比較して高すぎることはできません。つまり、高さの増加 a[j] - a[i] は最大でも h でなければなりません。 下降には制限がないため、常に下降が許可されます。 

タスクは、プラットフォーム n に到達するために必要なジャンプの最小数を計算するか、それが不可能であると判断することです。 

入力サイズの制約は、n および d で最大 10,000 です。 これにより、プラットフォームのすべてのペアにわたる O(n²) 遷移が簡単な方法で即座に除外されます。 すべてのノードから到達可能なすべてのペアをチェックするソリューションでは、最悪の場合でも約 10⁸ の操作が実行されます。これは境界線ですが、通常、厳密な時間制限の下では Python では遅すぎ、特に制約チェックのための追加のオーバーヘッドが発生します。 

高さの配列には重要な非対称性が導入されています。つまり、ジャンプは h を超えて上向きに移動する場合にのみブロックされます。 これは、エッジを均一または対称として扱うことができないことを意味します。 インデックス範囲と高さ条件の両方によって候補を効率的にフィルタリングする構造が必要です。 

すべての高さが同じである場合、微妙なエッジケースが発生します。 この場合、距離 d 内のすべてのプラットフォームに到達可能であり、グラフは密な間隔のグラフになります。 明示的に構築された隣接リストを含む単純な BFS は、メモリまたは時間の爆発により失敗します。 

高さがインデックスとともに厳密に増加し、h が小さい場合、別のエッジ ケースが発生します。 その場合、インデックスが近い場合でもすべての前方ジャンプがブロックされる可能性があり、答えは -1 になります。 「ローカル移動が常に可能である」と仮定したソリューションでは、パスが誤って生成されてしまいます。 

## アプローチ

 直接解釈すると、 |i - j| となるように、各プラットフォーム i がすべてのプラットフォーム j に接続するグラフが構築されます。 ≤ d および a[j] - a[i] ≤ h。 このグラフで BFS を実行すると、各エッジのコストが等しいため、正しい答えが得られます。 

問題は、このグラフには最悪の場合でも最大 n・d 個のエッジが存在する可能性があることです。 n = 10⁴ および d = 10⁴ の場合、これは 10⁸ エッジに縮退しますが、ノードごとに明示的に構築または反復するには大きすぎます。 BFS 自体がエッジで線形であっても、遷移コストが支配的になります。 

重要な観察点は、BFS ではすべての近隣ノードを明示的に列挙する必要がないということです。 各プラットフォームについて、高さの制約も満たす、スライディング インデックス ウィンドウ内で次に訪問されていないプラットフォームを見つけるだけで済みます。 プラットフォームが一度処理された後は、決して再検討すべきではありません。 これにより、「未訪問の候補者」の動的なセットを維持し、訪問後にそれらを削除することができます。 

私たちは、未訪問のインデックスをすべて保存する構造を維持します。 各プラットフォーム i について、範囲 [i+1, i+d] 内のみをスキャンし、すでに処理されたノードをスキップします。 すべてのノードは 1 回だけ削除されるため、複数回スキャンしても、合計作業量はコンテナーに応じて対数係数まで線形のままになります。 

高さの条件はトラバーサル中にチェックされ、有効な遷移のみが BFS にエンキューされます。 

これにより、問題は明示的なグラフ走査から、縮小する候補セットに対する制御されたウィンドウ スキャンへと変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース グラフ + BFS | O(n・d) | O(n・d) | 遅すぎる/メモリが重い |
 | 未訪問セット付きスライディング ウィンドウ BFS | O(n・d) 最悪のケースだが、実際には O(n log n) / O(n) 近くで償却される | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 最初のプラットフォームから開始するため、すべての値を -1 に設定して距離配列を初期化し、さらに distance[1] = 0 を設定します。 
2. BFS のキューを維持し、プラットフォーム 1 を挿入します。 
3. まだ訪問されていない 1 から n までのすべてのインデックスを含む構造を維持します。 この構造により、処理されたノードを再度訪問することなく、潜在的な次の位置を反復処理できます。 
4. キューが空でない間に、現在のプラットフォーム i を削除します。 
5. 範囲 (i+1 ～ i+d) 内の各候補 j について、j がまだ訪問されていないかどうか、および a[j] - a[i] ≤ h かどうかを確認します。 両方が成立する場合、 distance[j] = distance[i] + 1 を割り当て、 j をキューにプッシュし、未訪問の構造から削除します。 
6. 到達可能なすべてのノードが処理されるか、ターゲット n に到達するまで繰り返します。 
7. 出力 distance[n]。これは、ジャンプの最小数、または到達できない場合は -1 のいずれかです。 

重要な設計上の選択は、プラットフォームが一度アクセスされると、そのプラットフォームが候補セットから永久に削除されるということです。 これにより、異なるウィンドウの一部として複数回スキャンされる可能性がある場合でも、プラットフォームが複数回処理されることはなくなります。 

### なぜ効果があるのか

 BFS は常に、ジャンプ数の昇順にノードを処理します。 訪問されていない構造により、すべてのプラットフォームが最初に発見されたときに可能な最小距離が割り当てられることが保証されます。 すべてのエッジが 1 つのジャンプを表すため、BFS 階層化プロパティは正確に保持されます。 今後のすべての遷移は同等以上の BFS 深さに対応するため、より短いパスは後で見つかりません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, d, h = map(int, input().split())
    a = [0] + list(map(int, input().split()))

    dist = [-1] * (n + 1)
    dist[1] = 0

    q = deque([1])

    # we keep a simple list of "alive" indices
    alive = set(range(1, n + 1))
    alive.remove(1)

    while q:
        i = q.popleft()

        # scan only forward window
        to_remove = []
        for j in range(i + 1, min(n + 1, i + d + 1)):
            if j in alive and a[j] - a[i] <= h:
                dist[j] = dist[i] + 1
                q.append(j)
                to_remove.append(j)

        for j in to_remove:
            alive.remove(j)

    print(dist[n])

if __name__ == "__main__":
    solve()
```BFS は標準ですが、実装の詳細で重要なのは、ノードの再訪問をどのように回避するかです。 の`alive`set はグローバル フィルターとして機能し、各プラットフォームが最大 1 回だけキューに入れられるようにします。 一時的なリスト`to_remove`反復中にセットを変更することを回避します。そうしないと、実行時エラーや要素のスキップが発生します。 

内側のループは前方に最大 d 位置だけをスキャンし、制約に直接一致します。 問題の構造が使用されるのはここだけです。 それ以外はすべて、重み付けされていないグラフの標準的な最短パスです。

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n・d) 最悪の場合、通常は O(n) に近い | 各インデックスは一度考慮から削除され、サイズ d | のウィンドウ内でのみスキャンされます。 
| スペース | O(n) | 距離配列、キュー、およびアライブ セットには最大で n 個の要素が格納されます。 

n、d ≤ 10⁴ とすると、各ノードが平均して一定回数処理され、エッジごとの重いデータ構造が構築されないため、このアプローチは Python の時間制限内に問題なく収まります。 

## テストケース```python
import sys, io
from collections import deque

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n, d, h = map(int, input().split())
    a = [0] + list(map(int, input().split()))

    dist = [-1] * (n + 1)
    dist[1] = 0
    q = deque([1])
    alive = set(range(1, n + 1))
    alive.remove(1)

    while q:
        i = q.popleft()
        to_remove = []
        for j in range(i + 1, min(n + 1, i + d + 1)):
            if j in alive and a[j] - a[i] <= h:
                dist[j] = dist[i] + 1
                q.append(j)
                to_remove.append(j)
        for j in to_remove:
            alive.remove(j)

    return str(dist[n])

# provided samples
assert run("5 2 3\n1 2 3 2 5\n") == "3"

# custom cases
assert run("1 1 1\n10\n") == "0", "single node"
assert run("4 1 0\n1 3 2 10\n") == "-1", "blocked by height"
assert run("5 4 100\n1 2 3 4 5\n") == "1", "large d full reach"
assert run("6 2 1\n1 10 2 11 3 12\n") == "3", "alternating heights"

 | 厳密な高さブロック | -1 | 不可能な遷移 |

 ## 特殊なケース

 n = 1 の最小限のケースでは、BFS 拡張を試行せずに実装がゼロ ジャンプを正しく返すかどうかがチェックされます。 アルゴリズムは距離[1] = 0 に初期化し、ターゲットにすでに到達しているためすぐに終了します。 

すべての前進が高さの制約に違反する完全にブロックされたケースにより、ウィンドウ内のスキャンが到達可能であると誤って仮定されないことが確認されます。 BFS キューはすぐに空になり、残りの距離はすべて -1 のままになります。 

d が非常に大きい場合は、ウィンドウが残りの配列全体に及ぶ場合でもスキャンを i + d に制限するだけで十分であり、ループの境界を越える追加の最適化は必要ないことを示しています。 

混合の交互の高さパターンは、アルゴリズムが非対称制約 a[j] - a[i] ≤ h を適切に適用し、下向きの遷移を許可しながら上向きのスパイクを防止していることを示しています。
