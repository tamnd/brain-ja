 ## 解決策
 ## 問題の理解

 時間の経過とともにサンプリングされた一連のダウンロード速度と固定ウィンドウ サイズが与えられます。$k$。 連続する長さのセグメントごとに$k$、そのセグメントの平均速度を計算する必要があります。 平均が計算されると、その大きさに応じてさまざまな単位で表示されます。平均が 1024 以上の場合は MiBps で表示され、それ以外の場合は KiBps で表示されます。 

概念的には、このタスクは配列に対するスライディング ウィンドウ集計問題と、それに続く単純なしきい値ベースの単位変換です。 各ウィンドウは 1 つの出力値を生成し、出力ではウィンドウごとに単位規則を個別に保持する必要があります。 

もし$n$大きい、たとえば最大$10^5$、各ウィンドウの合計を単純に再計算するには、$O(k)$ポジションごとに仕事をすることで、$O(nk)$トータルオペレーション。 最悪の場合、$k$も大きい場合、これは非常に遅くなりすぎます。$10^{10}$操作。 

さらに微妙な点は、出力は合計ではなく平均に依存するということです。 つまり、すべてのウィンドウで除算が必要であり、丸めの適用が早すぎると不注意な整数除算が誤った単位分類につながる可能性があります。 正しいアプローチでは、分割する前に各ウィンドウの合計が正確に計算されるようにする必要があります。 

典型的なエッジ ケースは、値がしきい値の境界付近で変動するときに発生します。 たとえば、次の場合$k = 3$そしてウィンドウの合計は正確に$3071$、平均は$1023.666...$これは、MiBps ではなく KiBps として分類される必要があります。 平均を比較するのではなく、生の合計を 1024 と比較する実装では、そのようなケースが誤って分類されます。 

## アプローチ

 ブルートフォースの解決策は簡単です: すべての開始インデックスに対して$i$、次をスキャンします$k$要素を計算し、合計を計算し、除算します。$k$を選択し、単位変換ルールを適用します。 これは問題の定義に直接従っており、各ウィンドウを独立して処理するため、これは正しいです。 

このアプローチの問題は、繰り返し作業が行われることです。 新しいウィンドウはそれぞれ、前のウィンドウとほぼ完全に重複しますが、総当たり法では合計が最初から再計算されます。 のために$n$大きさの窓$k$、これはおおよそ次のようになります$n \cdot k$追加。 両方のとき$n$そして$k$が大きいため、これでは遅すぎます。 

重要な点は、連続するウィンドウは要素が 1 つだけ異なっていることです。つまり、前のウィンドウの左端の要素が削除され、右側に新しい要素が追加されます。 これにより、現在の合計を維持することができます。 各ウィンドウの合計を再計算する代わりに、出力値を減算し、入力値を加算することで一定時間で更新します。 これにより、総作業量が削減されます。$O(nk)$に$O(n)$。 

合計を効率的に維持した後、各ウィンドウの平均が一定時間で計算され、単位変換ルールがすぐに適用されます。

 | ブルートフォース |$O(nk)$|$O(1)$| 遅すぎる |
 | スライディングウィンドウ |$O(n)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 最初の合計を計算します。$k$要素。 これにより初期ウィンドウが形成され、後続のすべての更新のベースライン値が確立されます。 
2. 合計を次の値で割ることにより、この初期ウィンドウの平均を計算します。$k$。 この平均が 1024 以上であるかどうかに応じて、MiBps または KiBps で出力します。 
3. インデックスから反復処理する$k$に$n-1$、各位置を新しいウィンドウの右端として扱います。 
4. 新しい位置ごとに、ウィンドウから出る要素を減算し、入る新しい要素を加算することによって累計を更新します。 これにより、最初から再計算することなく、合計が現在のウィンドウと一致するように保たれます。 
5. 合計を更新した後、次の値で割って新しい平均を計算します。$k$。 
6. 算出された平均値に基づいて単位変換ルールを再度適用し、結果を出力します。 

核となる不変条件は、反復ごとに、現在の合計が最後の合計の合計と正確に等しいということです。$k$現在のインデックスで終わる要素。 各更新では古い要素が 1 つだけ削除され、新しい要素が 1 つだけ追加されるため、合計は常に現在のウィンドウと一致します。 これにより、計算されたすべての平均が正しいことが保証され、したがってそれに基づくすべての単位分類も正しいことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    data = list(map(int, input().split()))
    n, k = data[0], data[1]
    arr = data[2:]

    window_sum = sum(arr[:k])
    out = []

    def format_avg(avg):
        if avg >= 1024:
            return str(avg) + " MiBps"
        else:
            return str(avg) + " KiBps"

    avg = window_sum // k
    # if exact average is required as float, adjust here; problem assumes integer style display
    out.append(format_avg(avg))

    for i in range(k, n):
        window_sum += arr[i]
        window_sum -= arr[i - k]
        avg = window_sum // k
        out.append(format_avg(avg))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションは、1 回のパスで配列を読み取り、最初のウィンドウ合計に対する直接プレフィックスを使用して最初のウィンドウ合計を初期化します。$k$要素。 スライディング更新ステップは、受信要素を追加し、送信要素を削除して、一定時間の更新を維持することによって実装されます。 

実装上の微妙な問題は、整数の除算です。 元の問題が実数値の平均を期待している場合、フロア分割を使用することは正しくありません。 その場合、1024 と比較する前に浮動小数点演算を使用して合計を除算する必要があります。ただし、スライディング ウィンドウの構造は変わりません。 

出力フォーマット関数は、各ウィンドウの結果が均一に扱われるように、しきい値ロジックをカプセル化します。 

## 実用的な例

 次のような単純なケースを考えてみましょう。$n = 5$、$k = 3$、配列は$[1024, 1024, 1024, 512, 512]$。 

初期ウィンドウ合計は 3072 で、平均は 1024 になります。 

| ステップ | ウィンドウ | 合計 | 平均 | 出力 |

 | 0 | [1024、1024、1024] | 3072 | 1024 | MiBps |
 | 1 | [1024、1024、512] | 2560 | 853 | KiBps |
 | 2 | [1024、512、512] | 2048年 | 682 | KiBps |

 このトレースは、スライディング更新が正確さを維持しながら、ステップごとに 1 つの要素のみを変更する方法を示しています。 

次に、境界に敏感な場合を考えてみましょう。$n = 4$、$k = 2$、 配列$[1535, 1536, 0, 0]$。 

| ステップ | ウィンドウ | 合計 | 平均 | 出力 |
 | --- | --- | --- | --- | --- |

 この例は、分類が個々の値や近似推論ではなく、ウィンドウごとに計算された平均に基づいている必要があることを示しています。

 ## 特殊なケース

 重要なエッジ ケースは、ウィンドウ平均が 1024 しきい値に非常に近い場合に発生します。 ウィンドウ合計 2047 を次のように考えます。$k = 2$、平均は 1023.5 になります。 関係するすべての値が個別に 1024 を超える場合でも、正しい分類は KiBps です。分類は完全合計後の計算されたウィンドウ平均にのみ依存するため、アルゴリズムはこれを正しく処理します。 

もう 1 つのエッジケースは次のような場合です$k = 1$。 この状況では、すべてのウィンドウは単一の要素であり、スライディング更新は各値の直接出力に縮退します。 「古い要素を削除し、新しい要素を追加する」ステップが簡単になり、それぞれの合計が要素自体と正確に等しくなるため、不変条件は依然として維持されます。 

最後のエッジケースは、すべての値がゼロの場合です。 すべてのウィンドウ合計は実行中ゼロのままであり、出力は一貫して KiBps 単位に留まります。 スライディング ウィンドウは引き続き更新を実行しますが、各更新は正確にキャンセルされ、特別なケースを使用せずに正確さが維持されます。
