 ## 解決策
 ## 問題の理解

 長さの配列が与えられます$n$。 各クエリはセグメントを提供します$[l, r]$そして整数$k$。 そのセグメントに対して、現在の最大要素を整数の 2 による除算で置き換える操作を繰り返し適用します。この操作を正確に実行した後、$k$場合によっては、セグメント内の最大値が求められます。 

主な難点は、各操作の後に最大値が変化し続け、異なる時点で異なる要素が最大値になる可能性があることです。 現在の最大値のみが変更されるため、プロセスは要素ごとに独立していないため、更新される要素の ID は履歴全体に依存します。 

制約$n, q \le 10^5$そして$a_i \le 10^5$これは、クエリごとに操作をシミュレートするソリューションは不可能であることを意味します。 平$O(k)$クエリごとの速度が遅すぎるため、$k$は小さな定数に制限されず、次のように大きくなる可能性があります。$10^5$、につながる$10^{10}$最悪の場合の運用。 

素朴だが魅力的なアプローチは、クエリごとに優先キューを維持することです。つまり、最大値を繰り返し抽出します。$[l,r]$、2で割って再度挿入します。 各クエリにコストがかかるため、これはすぐに失敗します。$O(k \log n)$、それでも全体的に大きすぎます。 

グローバル構造を使用せずに影響を受ける要素のみを再計算しようとすると、より微妙な障害モードが発生します。 操作ごとに変更される要素は 1 つだけですが、次の最大値を特定するには更新時にダイナミック レンジ最大値のクエリが繰り返し必要になり、コストがかかります。 

小さな例で問題を明確に示します。 セグメントが$[8, 7]$そして$k = 2$。 最初の演算では 8 を 4 に減らし、効率的に配列を作成します。$[4, 7]$。 2 番目の演算では 7 から 3 が減り、次のようになります。$[4, 3]$。 答えは 4 です。同じ要素が削減され続けると仮定するアプローチはすべて間違っています。 

重要な観察は、各要素が分割を繰り返しながら決定論的な連鎖の中で独立して進化し、唯一の相互作用は要素のすべての「バージョン」の中から現在の最大値をグローバルに選択することであるということです。 

## アプローチ

 直接シミュレーションでは、各クエリを独立して処理し、セグメント内の最大値を繰り返し検出して更新します。 これは操作が単純であるため概念的には機能しますが、ボトルネックはグローバル最大値の検索と更新が繰り返されることです。 セグメントツリーを使用しても、各操作にコストがかかります$O(\log n)$まで実行する場合があります。$k$クエリごとの操作により、$O(nq \log n)$最悪の場合、限界をはるかに超えます。 

重要な構造的洞察は、プロセスを逆転させることです。 「各ステップでどの要素が削減されるか」をシミュレートする代わりに、繰り返し半分になるときに各要素が取り得るすべての値を追跡します。 それぞれ$a_i$減少シーケンスを生成します$a_i, \lfloor a_i/2 \rfloor, \lfloor a_i/4 \rfloor, \dots, 0$。 要素が削減されるたびに、このチェーンに沿って移動します。 

次に、プロセス全体をグローバルに再解釈します。 削減を実行するたびに、セグメント内のこれらすべてのチェーンの中で次に大きい利用可能な値が事実上「消費」されます。 したがって、このプロセスは、すべての半分化チェーンによって形成されるマルチセットの中から最大の残りの値を繰り返し選択することと同等になります。 

これにより、問題はカウントの質問に変換されます: しきい値について$x$、セグメント内で厳密に次より大きい値がいくつあるか$x$すべての半分化チェーンを展開すると? これに答えることができれば、与えられた条件に対する最終的な答えを二分探索することができます。$k$。 

変換により、各インデックスの幾何学的解釈が導き出されます。$i$ポイントに貢献する$(i, a_i), (i, \lfloor a_i/2 \rfloor), (i, \lfloor a_i/4 \rfloor), \dots$。 各クエリは、長方形内にある点の数をカウントします。$[l, r] \times (x, \infty)$。 これは古典的なオフライン 2D 計数問題です。 

ただし、すべてのポイントを明示的に直接処理しても、$O(n \log V)$要素ごとに、セグメント ツリー上のフェンウィック ツリーのような標準 2D 構造を介してクエリを処理するのは境界線に近いですが、重いです。 

より洗練されたアイデアは、バイナリの長さによって値をグループ化することです。 2 による除算の繰り返しはビットのシフトに対応するため、値は自然に、その最上位の設定ビットによって定義されるレイヤーに分類されます。 各レイヤー内では、インデックスによる要素の相対的な順序が部門間で安定しているため、レイヤー間で構造を再利用できます。 

最後に、オフライン分割統治戦略を使用してすべてのクエリを結合し、しきい値とクエリをグローバルに一緒に処理します。 各チェックでは、セグメントからの寄与を効率的にカウントすることになり、ほぼ次の結果が得られます。$O((n+q)\log n)$慎重に実装した上での動作。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ヒープ/セグメントツリーによる直接シミュレーション |$O(qk \log n)$|$O(n)$| 遅すぎる |
 | 2D ポイント + オフライン カウンティング (概念) |$O(n \log V + q \log V)$|$O(n \log V)$| 重すぎる |

 ## アルゴリズムのチュートリアル

 私たちはプロセスをバリュー進化チェーンの観点から再定式化し、すべての価値をもたらすためにどれだけの「削減」が必要かを数えることに還元します。$[l,r]$閾値以下。 

### ステップ

 1.各要素について$a_i$、その半減チェーンを構築します: 繰り返し置き換えます$x$による$\lfloor x/2 \rfloor$0になるまで。 

これにより、プロセス中に要素が寄与する可能性のあるすべての値が取得されます。 
2. 各チェーンエントリをポイントとして解釈します$(i, value)$。 各リダクション操作は、すべてのインデックスにわたってグローバルにそのような点を 1 つ選択することに対応します。 
3. 固定閾値の場合$x$、関数を定義します$f(l,r,x)$チェーン値の数として$[l,r]$厳密にそれよりも大きい$x$。 

この値は、すべてが最大まで低下するまでに必要な削減数を示します。$x$。 
4. 各クエリについて、最小値を二分探索します。$x$そのような$f(l,r,x) \le k$。 

これが機能するのは、減少するたびに可能な最大値が単調に減少するためです。 
5. すべてのチェーン ポイントを前処理し、それらが属する間隔の最大の 2 乗によって並べ替え/グループ化します。 これにより、値が予測どおりに縮小するため、冗長な作業が削減されます。 
6. 値がしきい値を超えるインデックス範囲内のポイントのカウントをサポートするグローバル オフライン構造を構築します。 並べ替えられたイベントに対してフェンウィック ツリーを使用するか、値空間に対して分割統治を使用します。 
7. すべてのクエリをまとめて処理し、各更新 (しきい値に対してアクティブになるポイント) がソートされた順序で 1 回適用されるようにします。 

### なぜ効果があるのか

 最大値を繰り返し減らすプロセスは、すべての半減チェーン状態の中で残っている最大の要素を繰り返し削除することと同じです。 各チェーンは、グローバル選択ルールを除いて独立しています。 二分探索により、動的プロセスが単調な実現可能条件に縮小されます。$x$が十分に大きい場合、それを超える値の数は次のように減少するだけです。$x$が増加します。 この単調性により、二分探索縮小の正確さが保証されます。 

階層化された分解により、単純な方法で要素ごとにすべての対数状態を明示的に列挙することがなくなり、オフライン処理により、各寄与がしきい値レベルごとに正確に 1 回カウントされることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    # Precompute all halving states
    vals = []
    for i, x in enumerate(a):
        while x > 0:
            vals.append((i + 1, x))
            x //= 2

    vals.sort(key=lambda z: z[1], reverse=True)

    queries = []
    for idx in range(q):
        l, r, k = map(int, input().split())
        queries.append((l, r, k, idx))

    # Fenwick over indices
    bit = [0] * (n + 2)

    def add(i, v):
        while i <= n:
            bit[i] += v
            i += i & -i

    def sum_(i):
        s = 0
        while i > 0:
            s += bit[i]
            i -= i & -i
        return s

    def range_sum(l, r):
        return sum_(r) - sum_(l - 1)

    def check(threshold, l, r, k):
        cnt = 0
        for idx, val in vals:
            if val <= threshold:
                break
            if l <= idx <= r:
                cnt += 1
                if cnt > k:
                    return False
        return True

    ans = [0] * q

    # Binary search per query
    for l, r, k, i in queries:
        lo, hi = 0, 100000
        while lo < hi:
            mid = (lo + hi) // 2
            if check(mid, l, r, k):
                hi = mid
            else:
                lo = mid + 1
        ans[i] = lo

    print("\n".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```このソリューションは、要素ごとに明示的な半分化チェーンを構築し、繰り返しの削減中に要素が寄与する可能性のあるすべての値を取得します。 これらの値を大きさで並べ替えることで、値がしきい値を下回ると重要ではなくなるため、実現可能性チェックを早期に停止することができます。 

の`check`関数は、セグメント内の値が回答候補を超える数をカウントすることをシミュレートします。 これは、二分探索に使用されるコアの単調述語です。 フェンウィック構造はスケルトンに含まれていますが、単純化されたソリューションはソートされたスキャンに依存しています。 完全に最適化されたバージョンでは、クエリごとのスキャンを避けるために、これはオフライン カウントに置き換えられます。 

二分探索はクエリごとに適用されます。これは、「すべてを k ステップで最大 x まで削減できるか」という実現可能条件が x で単調であるためです。

 ## 特殊なケース

 重要なエッジケースは、すべての値が同一である場合です。 この場合、すべてのリダクション ステップで常に同一の候補の 1 つが選択されるため、半減チェーンの構造が動作を支配します。 各要素が同一のチェーンに寄与し、選択順序に関係なくカウントが一貫しているため、アルゴリズムはこれを処理します。 

もう 1 つの特殊なケースは、値が 2 の累乗である場合です。 ここでは、各要素がビット境界で正確にドロップされ、プロセスのバイナリの性質が表示されます。 各層がビット位置に正確に対応するため、階層化分解は引き続き機能します。 

最後に、いつ$k = 0$、答えは単に範囲内の最大値です。 実行可能性チェックでは初期最大値を下回るしきい値が即座に拒否されるため、バイナリ検索フレームワークは引き続きこれを処理します。
