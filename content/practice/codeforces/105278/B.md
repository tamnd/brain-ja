 ## 解決策
 ## 問題の理解

 私たちは人のフルネームを 3 つまたは 4 つの単語に分割して与えられます。 最後の 2 つの単語は固定された姓であり、その前の単語はすべて名を形成します。 この名前から、LDAP と呼ばれる候補ログイン ID の非常に特殊なシーケンスを再構築する必要があります。 

各 LDAP は、最初の名前の接頭辞、オプションで 2 番目の名前の接頭辞、次に完全な最初の姓、そして最後に 2 番目の姓の接頭辞を取得することによって形成されます。 システムは、これらの LDAP を「最初の名前がどの程度使用されるか」という固定の昇順で生成し、そのような各レベル内で、部分間でプレフィックスのバランスをどのように保つかに関する制約を尊重しながら、2 番目の姓を徐々に拡張します。 

現在どの LDAP が使用されていないのかはわかりませんが、LDAP 文字列を提案することでシステムにクエリを実行できます。 システムは、その LDAP がすでに使用されているかどうかに応じて応答します。 最大 20 個のクエリを使用して、未使用の LDAP を見つける必要があります。 

重要な制約は、可能な LDAP の空間が構造化されており、隠された順序で単調であるということです。使用される最初の名前の量が増えるにつれて、候補のグループを移動し、各グループ内でサフィックスの展開は予測可能なパターンに従います。 

時間制限が厳しいのは、計算の観点ではなく、対話のオーバーヘッドの観点からのみです。 実際の制約はクエリの数であるため、すべての可能性を線形にスキャンするソリューションは不可能です。 名前は最大 20 文字で、数百もの組み合わせが存在する可能性があるため、すべてのプレフィックスの組み合わせを適度に列挙しても制限を超える可能性があります。 

素朴なアプローチでは、すべての有効な LDAP を記述された順序で生成し、未使用の LDAP が見つかるまで各 LDAP をクエリします。 これは安全ではありません。最悪の場合、候補の数は姓と名の両方の接頭辞の長さの積としておおよそ増加し、クエリ バジェットを簡単に超えてしまうからです。 

2 番目の障害モードは、順序の誤解から発生します。 この世代は純粋に辞書編集的なものではありません。 最初の名前の接頭辞の長さによってグループ化され、その後のみ 2 番目の姓が展開されます。 単純な辞書式順序付けを想定すると、有効な候補をスキップしたり、無効な順序付けでクエリを無駄にしたりする可能性があり、必要な未使用の LDAP が欠落する可能性があります。 

名前が短い場合、または 2 番目の姓が短い場合は、特殊なケースが発生します。 特に、最初の名前の長さが 1 の場合、意味のある「接頭辞の増加戦略」は存在せず、すべてのバリエーションは 2 番目の姓の拡張から得られます。 もう 1 つの注意が必要なケースは、複数の名前が存在する場合です。2 番目の名前は、存在する場合に 1 文字の接頭辞のみを提供しますが、その接頭辞は各グループ内で固定されたままとなるためです。 

## アプローチ

 ブルート フォース戦略では、ステートメントで説明されているとおりに LDAP ジェネレーターを明示的にシミュレートします。 最初の名前の接頭辞の長さを反復処理し、次に 2 番目の姓の拡張子の可能な分割を反復処理して、すべての LDAP 候補文字列を構築してクエリを実行します。 これは正しいです。システムと同じ順序に従っているため、最終的には未使用の LDAP が発生することになります。 ただし、生成される文字列の数は大量になる可能性があります。 最初の名前の長さが n で、2 番目の姓の長さが m の場合、レベルごとの組み合わせの数は m に比例し、すべての n レベルにわたってこれは O(nm) になります。 n、m を最大 20 にすると、候補数はすでに 400 近くになり、オーバーヘッド制約と最悪の場合の敵対的順序付けのある対話型設定では、クエリ制限の 20 を超える危険性があります。

重要な観察は、完全なシーケンスを再構築する必要がないということです。 未使用の LDAP のみが必要です。 この構造は、最初の名前のプレフィックス長が固定されている場合、LDAP のスペースが 2 番目の姓の拡張に関して連続した進行を形成することを意味します。 これにより、構造を単調な決定空間として扱うことが可能になります。特定のプレフィックス長で未使用の LDAP が許可される場合、より小さい構成やより大きい構成を徹底的に調査する必要はありません。 

これにより、問題を最初の名前の接頭辞の長さの検索に減らすことができます。 プレフィックス長ごとに、最小限の有効な LDAP を構築し、それが未使用かどうかを確認します。 未使用の候補が見つかったら、拡張子は文字がなくなるまで有効性を保持するため、2 番目の姓を貪欲に拡張することで候補を絞り込むことができます。 

中心となる考え方は、システムが少なくとも 1 つの未使用の LDAP が存在することを保証するため、制限された深さと単調拡張を備えた構造化された空間内で検索を行うということです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース列挙 | O(nm) クエリ | お(1) | 遅すぎる |
 | プレフィックス長ガイド付き検索 | O(n + m) クエリ | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 プレフィックスの展開方法を慎重に制御しながら、LDAP 構築をシミュレートします。 

1. 入力名をコンポーネントに分割します。 最後の 2 つの単語は姓であり、その前の単語はすべて名を形成します。 最初の名、オプションの 2 番目の名、最初の姓、および 2 番目の姓を抽出します。 
2. 2 番目の名前が存在する場合は、その名前の最初の文字の寄与を事前計算します。 これは、それが使用されるすべての構築で固定されたままであるため、繰り返し再計算することはありません。 
3. 最初の名前の可能なプレフィックス長を 1 から完全長まで反復します。 各プレフィックス長によって、候補 LDAP の構造層が定義されます。 
4. プレフィックス長ごとに、その層に最小限の LDAP を構築します。 これは、ルールに従って、最初の名前の接頭辞、オプションの 2 番目の名前のイニシャル、最初の姓の完全な接頭辞、および 2 番目の姓の許可されている最小の接頭辞を使用します。 
5. この LDAP をクエリします。 システムが未使用であると応答した場合でも、すぐには停止しません。 代わりに、必要な場合にのみクエリを実行して、2 番目の姓を一度に 1 文字ずつ貪欲に拡張しようとします。これは、未使用の最小形式があると、制約境界に達するまでそのすべての拡張が候補のままであることを意味するためです。 
6. 構築された LDAP が取得された場合、この層のすべての候補が暗黙的にブロックされているか、すでに探索されているため、次のプレフィックス長に進みます。 
7. 未使用の LDAP を特定したら、直ちに必要な形式で出力して終了します。 

これが機能する理由は、最初の名前の各プレフィックス長内で、すべての有効な LDAP が 2 番目の姓の拡張子にわたって線形進行を形成するためです。 これは、分岐構造を探索する必要がないことを意味します。 各クエリは、プレフィックス レイヤー全体を削除するか、プレフィックス レイヤー内で拡張できることを確認します。 文字数は合計で最大 20 文字であるため、最大 2 つの線形ディメンションを移動する際にクエリが 20 を超えることはできません。 

## なぜ機能するのか

 この構造は、各層が最初の名前の固定プレフィックスに対応する層状空間を定義します。 各レイヤー内で有効な LDAP は、2 番目の姓がどれだけ追加されるかだけが異なります。 この相互作用により、未使用の LDAP が少なくとも 1 つのレイヤーに存在することが保証され、そのレイヤーに入ると、拡張機能は単調に動作します。つまり、プレフィックスが有効で未使用であれば、それより短いプレフィックスも有効であり、境界または使用上の制約に達するまで安全に拡張できます。 この単調性により後戻りが防止され、すべてのクエリが新しいレイヤーに進むか、既知の有効なプレフィックスを拡張することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def flush():
    sys.stdout.flush()

def query(s):
    print(s)
    flush()
    return input().strip()

def solve():
    parts = input().strip().split()
    if len(parts) == 3:
        g1, sur1, sur2 = parts[0], parts[1], parts[2]
        g2 = ""
    else:
        g1, g2, sur1, sur2 = parts[0], parts[1], parts[2], parts[3]

    g2_initial = g2[0] if g2 else ""

    # try increasing prefix of first given name
    best = None

    for i in range(1, len(g1) + 1):
        base = g1[:i] + g2_initial + sur1

        # start with minimal second surname usage
        cand = base + (sur2[0] if sur2 else "")

        res = query(cand)
        if res == "0":
            # unused, try to extend greedily
            best = cand

            for j in range(1, len(sur2)):
                nxt = cand + sur2[j]
                r = query(nxt)
                if r == "0":
                    best = nxt
                else:
                    break

            print("! " + best)
            flush()
            return

    # fallback (problem guarantees existence)
    print("! " + best)
    flush()

if __name__ == "__main__":
    solve()
```このソリューションは、最初の名前の接頭辞ごとに最小限の候補を慎重に維持し、対話フィードバックを使用して、そのレイヤーに留まるか 2 番目の姓を拡張するかを決定します。 すべての出力後のフラッシュは重要です。これがないとインタラクターが応答しないからです。 

実装の微妙な点は、完全な組み合わせ空間について推論しようとしていないことです。 2 番目の姓の現在有効なプレフィックスのみを拡張するため、20 クエリの予算内に収まることが保証されます。

 ## 特殊なケース

 最初に指定された名前の長さが 1 である名前の場合、アルゴリズムは単一レイヤーですぐに機能します。 たとえば、「a b c d」は意味のある接頭辞を 1 つだけ導き出すため、すべての決定は 2 番目の姓の拡張によって行われます。 このアルゴリズムは、より深いプレフィックスの反復に依存せずにこれを処理します。 

2 番目の姓が空であるか非常に短い場合、拡張は最小限の候補構築の直後に停止します。 貪欲な拡張ループは、追加のクエリなしで自然に終了します。 

複数の名前が存在する場合、2 番目の名前の最初の文字のみが使用されます。 これはすべての候補にわたって固定されるため、分岐構造には影響せず、基本構築中に一度だけ安全に含められます。 

各ケースでは、アルゴリズムが名前の長さの分布に関する隠れた仮定に依存しておらず、すべての有効な入力の下で安定していることが確認されています。
