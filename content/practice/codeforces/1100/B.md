 ## 解決策
 ## 問題の理解

 一連の問題が与えられ、それぞれに 1 から n までの難易度のタグが付けられます。 Arkady は作成された問題のプールを保持しており、1 から n までのすべての難易度の未使用の問題を 1 つだけ選ぶことができれば、いつでもコンテストを行うことができます。 コンテストが形成されると、選択された問題はプールから削除されます。 

プロセスはオンラインで行われます。 新しい問題が到着するたびに、n 個の難易度すべての完全なセットがプールで利用可能になったかどうかを判断する必要があります。 「はい」の場合、アルカディはすぐに各難易度を 1 つだけ使用してコンテストを開催し、それに応じてプールが減ります。 その瞬間には 1 を出力し、それ以外の場合は 0 を出力します。 

重要な難易度は、時間の経過とともに問題が蓄積され、最後のコンテスト以降にすべての難易度が少なくとも 1 回出現した場合にのみコンテストを形成できることですが、コンテストごとに消費されるコピーは難易度ごとに 1 つだけです。 

この制約では、n も 100,000 までのイベントを 100,000 まで許可します。 挿入のたびに可用性を最初から再計算するソリューションでは、ステップごとに最大 n 個の要素をスキャンする必要があるため、時間がかかりすぎ、最悪の場合は O(nm) の動作が発生し、これは 1 秒には大きすぎます。 

微妙なエッジケースが繰り返しトリガーされます。 たとえば、n = 3 でストリームが 1 2 3 1 2 3 の場合、単純なアプローチでは、プールが明示的に「リセット」されていないため、2 番目の 1 2 3 はトリガーされるべきではないと考えるかもしれませんが、実際には、最初のコンテストでそれぞれ 1 つが消費され、2 番目のトリプレットが再び利用可能になります。 

もう 1 つのよくある間違いは、同じ難易度の複数のコピーは「コンテストごとに少なくとも 1 つの未使用のコピー」以上には役に立たないことを忘れていることです。 難易度 2 が 10 回出現しても、常に新しいコンテストの形成に寄与するスロットは 1 つだけです。 

## アプローチ

 ブルートフォース解釈では、作成されたすべての問題のマルチセットが保持されます。 挿入するたびに、1 から n までのすべての難易度がプールに少なくとも 1 回存在するかどうかがチェックされます。 「はい」の場合、各難易度の発生を 1 つ削除することでコンテストを形成し、1 を出力します。 

これはルールを直接シミュレートするため、これは正しいです。 ただし、実現可能性をチェックするには、n 個の難易度すべてを毎回スキャンする必要があり、これはイベントごとに O(n) になります。 イベントが m 個の場合、これは O(nm) となり、最悪の場合は 10^10 の演算となり、制限をはるかに超えます。 

重要な観察は、重要なのは、現在、各難易度の未使用のインスタンスが少なくとも 1 つあるかどうかだけであるということです。 現在「正の量で利用可能な」個別の困難の数のカウンターを維持する場合、すべての値を繰り返しスキャンする必要はありません。 問題を追加するたびに、その頻度が更新されます。 周波数が 1 になるたびに、新しい「カバーされる難易度」が得られます。 コンテスト中に 1 つの発生を削除するたびに、一部の頻度がゼロになり、対象範囲が減少します。 

したがって、n 個のタイプすべてを繰り返し検証する代わりに、現時点で少なくとも 1 回出現する個別の困難の数を追跡します。 そのカウントが n に達すると、コンテストがトリガーされ、それらの n 個の難易度に対してすべての周波数がちょうど 1 だけ減らされます。 これにより、完全な再スキャンを行わずにカバレッジを正しくリセットすることが保証されます。 

中心的な効率は、各問題がコンテスト サイクルごとに最大 1 回ずつ増減され、合計作業量が線形になるという事実から生まれます。

 ## アルゴリズムのチュートリアル

 私たちは 2 つの構造を維持します: 周波数配列`cnt[d]`プール内に存在する難易度 d の未使用のコピーの数とカウンターを保存する`have`現在抱えている個別の困難の数を保存する`cnt[d] > 0`。 

また、コンテストが形成されたときに、各難易度の 1 つのインスタンスをクリアするためのリストまたは単純なループ メカニズムも維持します。 

### ステップ

 1. 配列を初期化する`cnt`サイズ n+1 のゼロとセット`have = 0`。 

配列は、各イベント後の現在のプールの状態を表します。 
2. 受信する各難易度 x を繰り返します。 

これを、プールに 1 つの新しい問題を挿入するものとして扱います。 
3. もし`cnt[x] == 0`挿入前に増分する`have`この難易度が新たに利用可能になるためです。 
4.増加`cnt[x]`1までに。 
5.挿入後、以下のことを確認してください。`have == n`。 

この条件は、1 から n までのすべての難易度がプールに少なくとも 1 回存在することを意味し、コンテストが可能です。 
6. コンテストが可能な場合は、この位置に 1 を出力し、1 から n までの各難易度から 1 つの問題を削除することをシミュレートします。 

1 から n までの各 i について、デクリメントします`cnt[i]`1. ある場合`cnt[i]`ゼロになる、減少する`have`。 
7. コンテストが成立しない場合は 0 を出力します。 

### なぜ効果があるのか

 不変条件とは、`cnt[d]`以前に実行されたすべてのコンテストの後に、難易度 d の未使用の問題の数が常に反映されます。 変数`have`満たすインデックスの数を正確にカウントします`cnt[d] > 0`。 コンテストは、すべての難易度に少なくとも 1 つの利用可能な問題がある場合にのみ可能です。これは以下と同等です。`have == n`。 

コンテストを作成する場合、各難易度のインスタンスを 1 つだけ削除します。これにより、各難易度がコンテストに 1 つだけの問題を与えるため、正確さが保たれます。 すべての条件が満たされているという前提条件により、難易度がゼロ以下に除去されることはないため、システムは一貫性を保ちます。`cnt[i] > 0`トリガー時。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))

    cnt = [0] * (n + 1)
    have = 0
    res = []

    for x in a:
        if cnt[x] == 0:
            have += 1
        cnt[x] += 1

        if have == n:
            res.append('1')
            for i in range(1, n + 1):
                cnt[i] -= 1
                if cnt[i] == 0:
                    have -= 1
        else:
            res.append('0')

    print(''.join(res))

if __name__ == "__main__":
    solve()
```実装はアルゴリズムを直接反映しています。 重要な詳細は更新中です`have`周波数がゼロと正の間で遷移する場合にのみ、利用可能な個別の困難の真の数が維持されることが保証されます。 

コンテスト形成ループは、すべての難易度からちょうど 1 を減算します。すべての周波数が正の場合にのみそのブロックに入るので、これは安全です。

 ## 特殊なケース

 重要なエッジケースは、最初の瞬間にコンテストが即座に発生する場合です。 アルゴリズムはこれを処理します。`have`到達する`n`まさに最初のフルカバレッジです。 

もう 1 つの特殊なケースは、単一の難易度が頻繁に繰り返されることです。 1つの困難が何度出現しても、貢献するのは1回だけです`have`、そのため、余分なコピーが時期尚早にコンテストを引き起こすことはありません。 

最後のエッジケースは、連続したコンテストトリガーです。 コンテストの後、頻度は 1 つ減りますが、ストリームにすでに重複が含まれている場合、システムはすぐに再び適格になる可能性があります。 デクリメントループは更新することで正確さを保証します`have`一貫して行われるため、古くなった「完全にカバーされた」状態は残りません。
