 ## 解決策
 ## 問題の理解

 それぞれ固定容量を持つ一連のマシンと、各アプリケーションがこれらのマシンに配置する必要がある複数の同一のポッドで構成されるアプリケーションのコレクションが与えられます。 各ポッドは 1 つのアプリケーションに属しており、ノードの容量を考慮して、すべてのポッドを 1 つのノードに割り当てる必要があります。 

すべてのポッドが配置された後、各アプリケーションには品質メトリクスが設定されます。そのアプリケーションについて、すべてのノードを調べ、最終的にそのアプリケーションのポッドの数を数え、すべてのノードの最小値を取得します。 この値は、アプリケーションのポッドをほとんどまたはまったく受け取らないノードにペナルティを与えるため、アプリケーションがどの程度均等に分散されているかを捕捉します。 

目的は、アプリケーションごとの最小値ができるだけ大きくなるように、すべてのポッドをノード間で分散することです。 言い換えれば、すべてのアプリケーションがすべてのノードに少なくとも一定の回数だけ表示されるようにし、すべてのアプリケーションで同時に保証される最小頻度を最大化したいと考えています。 

この制約は、ノードとアプリケーションの数が両方とも 100,000 に達する可能性があり、ポッド数も同様に大きくなる可能性があることを示しています。 これにより、明示的に配置をシミュレートしたり、アプリケーションごとにノードを反復しようとしたりするソリューションは即座に除外されます。 二次関数または二次関数に近いアプローチでも、$N \cdot M$不可能です。 

重要な構造上の制約は、ポッドの総数が総容量を超えないことです。したがって、実現可能性は、世界的にスペースが不足することでは決してありません。 問題は純粋にノード間の分散バランスにあります。 

1 つのアプリケーションのポッドが非常に少ない場合、微妙なエッジ ケースが発生します。 たとえば、アプリケーションにポッドが 1 つだけある場合、そのノードごとの最小値は、配置に関係なく常にゼロになります。$N-1$ノードはそのアプリケーションのポッドを受け取りません。 これにより、少なくとも 1 つのアプリケーションが十分に小さく、意味のある拡散ができない場合には、グローバルな答えが強制的にゼロになります。 

もう 1 つの特殊なケースは、容量が極端に偏っている場合です。 1 つのノードにほぼすべての容量がある場合、素朴な直観ではそこにすべてを詰め込むことを提案するかもしれませんが、他のノードはほとんどのアプリケーションに対してポッドを取得しないため、アプリケーションごとの最小値が破壊されます。 

## アプローチ

 強引なアイデアは、ノード間でアプリケーションごとにポッドの分散を直接構築し、その結果の最小値を計算することです。 固定目標値の実現可能性の確認に限定しても$x$、各ノードが少なくとも$x$そのアプリケーションのポッド。 これは、共有ノード容量によるアプリケーション間の依存関係を伴う組み合わせ割り当ての問題になります。 

構造を使用せずに割り当てを貪欲にシミュレートしようとすると、アプリケーションが直接ではなくノードの容量を通じてのみ対話するという事実にすぐに遭遇します。 これは、割り当てを明示的に構築するのではなく、特定のターゲット最小値をサポートするために総容量がどのくらい必要かを総合的に推論する必要があることを示唆しています。 

候補値を固定する$x$。 アプリケーションごとに$j$、ノードごとの最小値を少なくとも$x$の場合、すべてのノードは少なくとも受信する必要があります$x$そのアプリケーションのポッド。 あるので$N$ノード、これはすでにそのアプリケーションを意味します$j$少なくとも必要になります$x \cdot N$ポッドの合計。 したがって、実現可能性の必要条件は、$a_j \ge x \cdot N$みんなのために$j$。 いずれかのアプリケーションがこれに失敗すると、目標を達成することは不可能になります。 

ただし、配置できるポッドの合計数はノードの容量によって制限されるため、これだけでは十分ではありません。 各ノードは少なくともホストする必要があります$x$各アプリケーションのポッド。つまり、各ノードは少なくとも$x \cdot M$アプリケーション全体の合計ポッド。 したがって、各ノード$i$満たさなければなりません$c_i \ge x \cdot M$。 これにより、2 番目の必要条件が与えられます。 

すべてのアプリケーションに十分な合計ポッドがあり、すべてのノードに十分な容量がある場合、概念的には正確に割り当てることができるため、これら 2 つの条件も十分であることがわかります。$x$すべてのアプリケーションのポッドをすべてのノードに配置し、残りのポッドを任意に分散します。 残りの柔軟性は、グローバル容量条件によって保証されます。 

したがって、実現可能性は、固定値に対する 2 つの単純な不等式をチェックすることに帰着します。$x$、有効な最大値を二分探索できます。$x$。 

代入を構築するという強引な考え方は、単調述語に対する実行可能性チェックに置き換えられ、二分探索が可能になります。

 ## アルゴリズムのチュートリアル

 答えを二分探索します$x$、これは、強制したいノードごと、アプリケーションごとの最小保証を表します。 

1. 検索範囲を設定します。$x$0 から可能な最大値までの間で、総容量をアプリケーション数とノードの数で割った値によって制限されます。 

上限は重要ではありません。 次のような大きな値を安全に使用できます。$\sum c_i$。 
2. 候補者が確定した場合$x$、すべてのアプリケーションが満たしているかどうかを確認します。$a_j \ge x \cdot N$。 

これにより、少なくとも配置するのに十分なポッドが確保されます。$x$そのアプリケーションの各ノード上で。 
3. At the same time, check whether every node satisfies$c_i \ge x \cdot M$。 

これにより、各ノードがすべてのアプリケーションにわたって必要な数のポッドをサポートできるようになります。 
4. 両方の条件が満たされる場合、候補者は$x$実現可能です。 それ以外の場合はそうではありません。 
5.二分探索$x$、可能な場合は右に移動し、不可能な場合は左に移動して、有効な最大値を見つけます。 

重要な実装の詳細は、両方のチェックがリニア スキャンであるため、各実現可能性テストは$O(N+M)$、二分探索ではこれを乗算します。$\log \max a_j$。 

### なぜ効果があるのか

 核となる不変条件は、目標の実現可能性です。$x$グローバルな供給とノードごとの容量が均一なベースライン割り当てをサポートできるかどうかによってのみ決まります。$x$ノードごとのアプリケーションごとのポッド。 これらのベースラインが満たされると、アプリケーションの最小値を下回ることなく、残りのすべてのポッドを任意に配布できます。$x$追加のポッドはノード上のカウントを増やすだけで、最小値を減らすことはないためです。 これにより、実現可能性述語が単調になります。$x$、二分探索の正確さを保証します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(x, n, m, c, a):
    need_per_app = n * x
    need_per_node = m * x

    for v in a:
        if v < need_per_app:
            return False

    for v in c:
        if v < need_per_node:
            return False

    return True

def solve():
    n, m = map(int, input().split())
    c = list(map(int, input().split()))
    a = list(map(int, input().split()))

    lo, hi = 0, 10**18
    ans = 0

    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid, n, m, c, a):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    print(ans)

if __name__ == "__main__":
    solve()
```実装では、実現可能性を 2 つの派生制約をチェックするクリーンな関数に分離します。 二分探索では、考えられる答えの空間を探索します。 

微妙な点は、上限が慎重に導出されるのではなく、大きく設定されていることです。 一度実現可能性はすぐに失敗するので、これは安全です$x$の乗算により意味のある境界を超えます$N$そして$M$。 もう 1 つの詳細は、すべての算術演算が Python 整数で実行され、オーバーフローの懸念が回避されることです。
