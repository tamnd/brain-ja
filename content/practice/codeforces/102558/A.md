 ## 解決策
 # 問題の理解

 Vasyaには料理のコレクションがあります。 各料理には 1 人分に必要な量が記載された材料のリストがあり、各料理は既知のゲストの数に合わせて準備されます。 このタスクは、買い物プロセス全体をシミュレートすることです。入手可能なすべての食材を何パック購入する必要があるかを決定し、合計価格を計算し、完成した料理 1 品分の栄養価を計算します。 

入力には 2 つの独立したカタログが含まれています。 最初の項目では、ショップ パッケージ (パッケージ サイズ、測定単位、価格) について説明します。 2 つ目は、各食材の一定量の栄養データを説明します。 レシピやカタログでは同じ材料が異なる単位で表示される場合があるため、最初にすべての計算を共通の単位に変換する必要があります。 

制限は直接処理するには十分小さいです。 料理は最大 1000 品、それぞれの料理には最大 100 種類の材料が含まれており、どちらのカタログにも最大 1000 件のエントリが含まれています。 これは、レシピの材料の総数が最大 100,000 であることを意味します。総入力サイズに比例して機能するアルゴリズムが必要です。 ここでは、レシピのすべての材料についてすべてのカタログを繰り返しスキャンしても、約 1 億件の比較が可能ですが、辞書を使用する方が簡単で、きれいな線形ソリューションが得られます。 

難しい部分は主に単位と、1 食分とすべての食分の違いに関連しています。 たとえば、レシピが必要な場合、`500 ml`牛乳と店で売っている`1 l`パッケージの場合、購入計算には次のものを使用する必要があります`0.5`パッケージは切り上げられますが、栄養計算は正確に使用する必要があります`500 ml`。 

よくある間違いは、異なる意味を持つ単位を交換可能なものとして扱うことです。 例えば、`tens`そして`cnt`どちらもオブジェクトの量を記述しますが、`kg`そして`l`変換できません。 このステートメントは、必要なすべての変換が有効であることを保証するため、実装では正しい乗数を適用するだけで済みます。 

もう 1 つの微妙なケースは、いくつかの料理に登場する食材です。 例えば：```
2
a 1 1
x 500 g
b 1 1
x 700 g
1

1

```正しいパッケージ数は次のとおりです。`2`, なぜなら、合計金額は`1200 g`。 各皿を別々に丸めるソリューションも得られます。`2`ここで、しかし`100 g`そして`100 g`レシピと`150 g`パッケージを 2 つではなく、誤って 2 つのパッケージを購入することになりますか? 重要なルールは、必要な金額をすべて合計してから買い物をするということです。 

もう 1 つのケースは、レシピの材料が栄養カタログとは異なる単位で測定されている場合です。```
1

```栄養価はカタログ記載の半分です。 生の数値を使用する`500`のカタログ値で`1 l`結果は2倍になります。 

# アプローチ

 簡単な解決策は、すべての料理とすべての材料を個別に処理することです。 レシピの材料ごとにカタログを検索し、分量を換算して栄養計算し、必要量を更新します。 すべての成分の寄与は独立しており、それらを組み合わせるには加算で十分であるため、これは正しいです。 このアプローチの問題は、検索が繰り返されることです。 100,000 のレシピ エントリのそれぞれが 1,000 の要素カタログをスキャンすると、比較の数は約 1 億に達します。 

有益な観察は、成分名が各カタログ内で一意であるということです。 つまり、ハッシュ マップを使用してカタログに 1 回インデックスを付けることができます。 その後、すべての成分検索は一定時間になります。 

2 番目の観察は、すべての単位変換が乗算的であるということです。 あらゆる量を基本単位に変換できます。質量はグラム、体積はミリリットル、個数は個数です。 すべてが同じ表現になると、要件の合計、パッケージ数の計算、栄養の計算が通常の算術になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ブルートフォース | O(レシピアイテムの合計 * カタログサイズ) | お(1) | 最悪の場合は遅すぎる |
 | 最適 | O(レシピ項目の合計 + k + m + n) | O(k + m + n) | 承認済み |

 # アルゴリズムのチュートリアル

 1. 価格カタログを読み、すべての材料を名前で保管します。 パッケージの計算が元の単位に依存しないように、各パッケージのサイズを基本数量に変換します。 
2. 栄養カタログを読み、各成分について、1 基本単位に相当するタンパク質、脂肪、炭水化物、エネルギーの量を保存します。 換算されたカタログ量で割ることにより、すべてのレシピ量を直接乗算することができます。 
3. すべての料理について、名前を保存し、栄養価を計算します。 レシピ内のすべての材料について、1 食分あたりの量を基本単位に変換し、基本単位あたりの栄養価を掛けます。 
4. 同時に、食材の量とゲストの数を乗算した値をグローバル必要量マップに追加します。 このマップは、すべての料理に必要なすべての材料の正確な量を表します。 
5. すべての料理が処理されたら、価格カタログから食材ごとのパッケージ数を計算します。 一部のパッケージは購入できないため、必要数量をパッケージサイズで除算し切り上げてください。 
6. 合計価格、パッケージ数、各料理の計算された栄養成分を出力します。 

アルゴリズムの背後にある不変条件は、料理の接頭辞を処理した後、グローバル要件マップにはその接頭辞に必要な量が正確に含まれており、保存されているすべての栄養価は正規化された材料の量から計算されるということです。 残りの各ディッシュは独立して寄与するため、すべてのディッシュが処理されるまで同じ更新を継続すると正確さが維持されます。 

# Python ソリューション```python
import sys
import math
input = sys.stdin.readline

def factor(u):
    if u == "kg" or u == "l":
        return 1000
    if u == "tens":
        return 10
    return 1

def solve():
    n = int(input())
    dishes = []
    for _ in range(n):
        name, c, z = input().split()
        c = int(c)
        z = int(z)
        ing = []
        for _ in range(z):
            s, a, u = input().split()
            ing.append((s, int(a), u))
        dishes.append((name, c, ing))

    k = int(input())
    price = {}
    order = []
    for _ in range(k):
        t, p, a, u = input().split()
        a = int(a)
        price[t] = (int(p), a * factor(u))
        order.append(t)

    m = int(input())
    nutrition = {}
    for _ in range(m):
        t, a, u, pr, f, ch, fv = input().split()
        amount = int(a) * factor(u)
        nutrition[t] = (
            float(pr) / amount,
            float(f) / amount,
            float(ch) / amount,
            float(fv) / amount
        )

    need = {}
    answers = []

    for name, cnt, ing in dishes:
        cur = [0.0, 0.0, 0.0, 0.0]
        for s, a, u in ing:
            amount = a * factor(u)
            if s not in need:
                need[s] = 0
            need[s] += amount * cnt

            pr, f, ch, fv = nutrition[s]
            cur[0] += amount * pr
            cur[1] += amount * f
            cur[2] += amount * ch
            cur[3] += amount * fv
        answers.append((name, cur))

    total = 0
    packs = []
    for t in order:
        p, size = price[t]
        cnt = math.ceil((need.get(t, 0) - 1e-12) / size)
        packs.append((t, cnt))
        total += cnt * p

    out = [str(total)]
    for t, c in packs:
        out.append(f"{t} {c}")
    for name, vals in answers:
        out.append("{} {:.10f} {:.10f} {:.10f} {:.10f}".format(name, *vals))
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```の`factor`関数は、サポートされているすべての単位をその基本表現に変換します。 キログラムとリットルはそれぞれの基本単位の 1000 分の 1 になり、10 は 10 個の個別の物体になります。 

価格ディクショナリには、レシピで使用されるのと同じ表現でパッケージのサイズが格納されます。 これにより、最終的な購入計算からすべての単位処理が削除されます。 

栄養ディクショナリには、カタログ エントリごとではなく基本単位ごとに値が保存されます。 たとえば、カタログに 100 グラムに 20 グラムのタンパク質が含まれていると記載されている場合、保存される値は次のようになります。`0.2`グラムあたりのタンパク質。 

レシピ処理中に、コードは 2 つの独立した更新を実行します。 の`need`マップはすべてのゲストの買い物数量を追跡します。`cur`完全な 1 つの料理の栄養を追跡します。 これら 2 つの値を混合すると、誤った答えが生じることがよくあります。 

浮動小数点除算では次のような値が生成される可能性があるため、最後の天井演算には小さなイプシロンが含まれます。`1.000000000001`。 制約が小さいため、Python では整数のオーバーフローは問題になりません。

 # エッジケース

 このアルゴリズムは、演算の前に変換することで単位の不一致を処理します。 牛乳の例では、`500 ml`になる`500`栄養カタログには基本単位ごとの値が保存されますが、`1000 ml`, したがって、結果はカタログ値のちょうど半分になります。 

アルゴリズムは更新することで共有成分を処理します`need`食材が登場するたびに。 料理が2品必要な場合`100 g`それぞれとパッケージのサイズは`150 g`、最後の要件は`200 g`、与える`ceil(200 / 150) = 2`パッケージ。 個々のレシピを早期に丸めることはありません。 

ゼロユースのカタログエントリも処理されます。 出力では、どのレシピにも必要のない材料を含め、すべての価格カタログの材料を印刷する必要があります。 ルックアップで使用されるのは、`need.get(t, 0)`、それらの成分のパッケージはゼロになります。
