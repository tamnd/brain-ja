 ## 解決策
 ## 問題の理解

 3 つの異なるシンボルを持つ簡略化された三目並べのバリエーションとして、常に 3 x 3 の非常に小さなボードの最終状態が与えられます。 1 人のプレイヤーは X を配置し、別のプレイヤーは O を配置し、3 番目のプレイヤーはプラス記号を配置します。 一部のセルはまだ空である可能性があります。 ボードはすでに完成した構成になっており、どのプレイヤーが勝利ラインを形成したか (存在する場合) を判断するように求められます。 

ウィニング ラインとは、水平、垂直、または斜めに直線状に並んだ 3 つの同じシンボルを意味します。 勝者が 1 人だけ存在するか、誰も勝者がいない場合、結果は引き分けになります。 また、2 つの異なるシンボルが同じボード内で同時に勝ちラインを形成することは決してないことも保証されています。 

入力サイズはテスト ケースの数が非常に多く、最大 10,000 ボードですが、各ボードのサイズは一定です。 これにより、ボードごとの一定時間を超える最適化の必要性が直ちになくなります。 テスト ケースごとに 9 セルの固定スキャン以上のことを行うものは、すでに過剰です。 

微妙なエッジケースは、空のセルや部分的な行から発生します。 たとえば、次のような行`X X .`ほぼ1つを形成するにもかかわらず、勝利ではありません。 もう 1 つは斜めのチェックです。これは不注意な実装で見落とされることがよくあります。 たとえば、次のようなボード```
X . .
. X .
. . X
```X を返さなければなりません。 

実装の主な落とし穴は、シンボルをカウントするだけで十分であると誤って想定していることです。 たとえば、ボード上に 3 つの X があっても、それらが揃っていない限り勝利は保証されません。 

## アプローチ

 ブルートフォースのアイデアは、すべてのテスト ケースについて、可能なすべての行を明示的にチェックすることです。 ボードは 3 × 3 しかないので、勝ちラインは 3 行、3 列、2 つの対角線の合計 8 つになります。 行ごとに、3 つのセルすべてに同じシンボルが含まれており、空でないかどうかを確認します。 これはラインごとに一定の作業となるため、各ボードには一定の時間がかかります。 

より素朴だが構造化されていないアプローチは、3 つのセルのすべてのサブセットを試し、それらが線を形成しているかどうかを検証することです。 グリッドの形状は固定されており、事前にわかっているため、これは不要です。 このアプローチはまだ機能しますが、冗長なチェックが発生し、実装が困難になります。 

重要な観察は、勝ちラインのセットが固定されており、小さいということです。 これにより、問題がゲーム シミュレーションから直接パターン マッチング タスクに変換されます。 動きのシミュレーションや妥当性のチェックは行っておらず、静的なパターンを認識しているだけです。

 ## アルゴリズムのチュートリアル

 8 つの勝ちラインすべてを、平坦化された 3 x 3 グリッド上のインデックス トリプルとして事前定義します。 

1. 各ボードを、9 文字のリストなど、すぐにインデックスを作成できる構造に変換します。 これにより、行のチェックが簡単になり、文字列インデックス作成ロジックの繰り返しが回避されます。 このステップは、行チェックを均一にして読みやすく保つため、重要です。 
2. 8 つの勝ちパターン (3 行、3 列、2 つの対角線) を定義します。 各パターンは、平坦化されたボード内のインデックスの 3 倍にすぎません。 
3. の各シンボルについて`X`、`O`、 そして`+`、8 つのパターンのいずれかがそのシンボルによって完全に占有されているかどうかを確認します。 これは、パターン内の 3 つの位置すべてがシンボルと一致することを確認することで行われます。 
4. シンボルが 1 つだけ勝利条件を満たす場合、そのシンボルを出力します。 
5. 満たすシンボルがない場合は出力`DRAW`。 

3 つのシンボルすべてを個別に明示的にチェックする理由は、問題ステートメントを超えて利用できる重複の保証がないためです。 同時勝者がいないことは保証されていますが、それでもそれぞれを個別に検証する必要があります。 

### なぜ効果があるのか

 3 x 3 の三目並べボードで考えられる勝ちの構成はすべて、事前に定義された 8 つのラインの 1 つに正確に対応します。 勝利を形成する幾何学的な配置は他にありません。 すべてのシンボルをすべての有効なラインに対してテストするため、勝利ボードは少なくとも 1 回のチェックで検出される必要があります。 逆に、非勝利ボードはフルライン条件を満たすことができないため、誤って勝利として分類することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

LINES = [
    (0, 1, 2), (3, 4, 5), (6, 7, 8),  # rows
    (0, 3, 6), (1, 4, 7), (2, 5, 8),  # cols
    (0, 4, 8), (2, 4, 6)              # diagonals
]

def winner(board, ch):
    return any(board[a] == board[b] == board[c] == ch for a, b, c in LINES)

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        grid = []
        for _ in range(3):
            grid.append(input().strip())
        board = ''.join(grid)

        if winner(board, 'X'):
            out.append('X')
        elif winner(board, 'O'):
            out.append('O')
        elif winner(board, '+'):
            out.append('+')
        else:
            out.append('DRAW')

    print('\n'.join(out))

if __name__ == "__main__":
    solve()
```このソリューションは、各グリッドを長さ 9 の単一の文字列に平坦化し、ライン チェックが単純なインデックス比較になるようにします。 の`LINES`配列は、考えられるすべての勝利構成をエンコードするため、実行中の座標演算の必要がなくなります。 

の`winner`関数はコアロジックです。 8 行すべてをスキャンし、3 つの位置すべてに同じターゲット シンボルが含まれているかどうかを確認します。 これは、検索やシミュレーションではなく、パターンの直接一致です。 

チェックの順序はタイブレークの場合にのみ重要ですが、この問題では同時勝者が存在しないことが保証されているため、X、次に O、次に + をチェックするのが安全かつ決定的です。

これは、特別なケースを使用せずに、事前計算されたライン リストによって斜めの検出がどのように自然に処理されるかを示しています。

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

            out.append('O')
        elif winner(board, '+'):
            out.append('+')
        else:
            out.append('DRAW')

    return "\n".join(out)

 ## 特殊なケース

 空のボード ケースは、アルゴリズムがシンボル数から勝ちを推測していないことを示しています。 ボード`"..."`3 回繰り返すと、8 つのパターンのいずれにも一致する行が生成されないため、すべて`winner`チェックは false を返し、出力は次のようになります`DRAW`。 

などの斜め方向のみの勝利`+O., O+O, .O+`斜めのパターンであることを確認します`(0,4,8)`が正しく含まれており、対称的にチェックされます`(2,4,6)`。 これら 2 つのパターンがなければ、プラスプレイヤーの勝利は体系的に逃されてしまいます。 

次のような列が勝ちます。```
X O .
X O .
X O .
```平坦化後の垂直インデックスの一貫性をテストします。 インデックス`(0,3,6)`最初の列を正しく表しており、等価性チェックによって 3 つの行すべてが同じ行に正しく寄与していることが確認されます。
