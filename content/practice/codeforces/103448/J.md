 ## 解決策
 ## 問題の理解

 ファイルのリストが垂直方向のリストに配置され、最初は現在のファイル名でソートされています。 各ファイルには、範囲からの元の名前と、別の範囲からのターゲットの新しい名前があります。 重要な構造特性は、すべての元の名前がす​​べての新しい名前よりも厳密に大きいため、名前を変更した後は、辞書編集順で、名前が変更されたすべてのファイルが名前が変更されていないすべてのファイルの前に表示されることです。 

すべての名前を一度に変更するわけではありません。 代わりに、まだ名前が変更されていないファイルを 1 つ繰り返し選択し、上下の操作を使用してカーソルをそのファイルに移動し、名前を変更すると、システムが即座にリストを再ソートします。 ファイルの名前を変更すると、ファイルは、すでに名前が変更されたファイルの中の新しい位置にすぐにジャンプします。これらのファイルは、常に最終的な順序のプレフィックスを形成します。 

私たちが気にするコストは、カーソルの移動回数、つまり上または下を何回押すかだけです。 名前変更自体は無料です。 目標は、最初に並べ替えられたリストの先頭から始めて、カーソルの合計移動が最小限になるような名前変更の順序を選択することです。 

この制約により、最大 500,000 個のファイルが許可されるため、プロセスを明示的にシミュレートするソリューションは即座に除外されます。 並べ替えられた構造を繰り返し再構築したり、単純に位置を再計算したりするアプローチは、各ステップに線形の移動や更新が含まれる可能性があるため、二次的な動作に低下します。 

微妙な問題は、リストが静的ではないことです。 名前を変更するたびに、挿入された名前変更された要素が前面に移動するため、残りの名前変更されていないすべての項目の位置が移動する可能性があります。 このため、ランクの変化を注意深くモデル化しない限り、単純なインデックス追跡が不正確になります。 

もう 1 つのエッジ ケースは、最適な戦略に、たとえローカルで前進する方がコストが安く見える場合でも、離れた位置の間を行ったり来たりするスキップが含まれる場合です。 並べ替え効果により、単純な貪欲な仮定が覆される可能性があります。 

## アプローチ

 ブルートフォース戦略では、考えられるすべての名前変更順序をシミュレートします。 次のファイルを選択するたびに、カーソルの移動を計算し、名前の変更を適用し、構造を再ソートして再帰します。 サブセットに対するメモ化を行ったとしても、n 個の要素を並べ替えているため、状態空間のサイズは階乗になります。 これは直ちに実行不可能です。 

より構造化されたブルート フォースは、名前変更の固定順序をシミュレートし、動的ランクを維持するためにバランスのとれたツリーを使用してシミュレーションあたり O(n log n) でコストを計算します。 それでも、すべての順列を試すことは不可能であり、コストは将来の並べ替えが現在のポジションにどのような影響を与えるかに大きく依存するため、証明なしに貪欲に選択しても失敗します。 

重要な観察は、プロセスが恣意的ではないということです。 k 回の操作の後、ちょうど k 個のファイルが新しい順序になり、これらの k 個のファイルは常に、新しいラベルのソート順でリストのプレフィックスを占めます。 一方、残りのファイルはファイル間の相対的な順序を保持しますが、常に名前が変更されたすべてのファイルの後ろにあります。 

これは、システムの状態は、名前が変更されたセグメントと名前が変更されていないセグメント間の現在のパーティションによって純粋に記述でき、カーソルの移動コストは、選択された各要素を成長するプレフィックスに挿入することによって引き起こされる相対的な順序の変更にのみ依存することを意味します。 

位置を動的にシミュレートする代わりに、1 つの要素が削除されたときに残りの要素間の相対的な順序がどのように変化するかを追跡します。 これにより、問題をランク シフトによって増加した静的構造内の位置間の遷移のコストに減らすことができ、未処理の要素の現在の位置を維持するフェンウィック ツリーまたはセグメント構造で処理できます。 

最終的な解決策は、動的に縮小するシーケンスの移動を最小限に抑える順序を選択することになります。これは、現在の構造内で最も近い有効な次の要素に常に移動する場合に貪欲に解決できます。 フェンウィック ツリーで現在の位置を維持すると、O(log n) 個の更新とクエリが可能になります。

 | Fenwick ベースの動的ランク シミュレーション | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 注文統計をサポートする構造内で、すべての未処理ファイルの現在の位置を維持します。 最初は、すべてのファイルが指定された順序で配置されます。 

1. 最初の順序でフェンウィック ツリーを初期化し、すべてのポジションをアクティブとしてマークします。 また、最初の要素から始まる現在のカーソル位置のポインターも保持します。 これは、各動的縮小後の現在の表示リストを表します。 
2. 各ステップで、現在のカーソル位置からの移動が最小限になる順序で、名前を変更する次のファイルを選択します。 リストは動的であるため、元のインデックスではなく、現在のランクに基づいて距離を比較します。 
3. 候補ファイルへの移動コストを評価するために、フェンウィック ツリー内のプレフィックス合計を使用して、アクティブな構造内でのその現在の位置を計算します。 距離は、カーソルの現在のランクと候補者のランクの間の絶対的な差です。 
4. 現在の構造内で最も近い未処理のファイルを選択します。 同点の場合は、どちらの方向でも同じコスト寄与が得られるため、どちらの方向も有効です。 
5. 移動コストを答えに追加し、選択したファイルをフェンウィック ツリーから削除して、シーケンスを効果的に圧縮します。 カーソルがその位置に移動し、縮小された構造内になります。 
6. すべてのファイルが処理されるまで繰り返します。 

機能する理由: 削除するたびに、残りの要素の相対的な順序は、圧縮を除いて変更されません。 移動コストは現在のランク距離のみに依存するため、より近い利用可能な要素を飛び越える最適な戦略は、2 つの移動の順序を入れ替えることによって局所的に改善できます。 この交換引数により、常に最も近い使用可能な要素を選択しても、総コストが決して増加しないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def kth(self, k):
        idx = 0
        bitmask = 1 << (self.n.bit_length())
        while bitmask:
            nxt = idx + bitmask
            if nxt <= self.n and self.bit[nxt] < k:
                k -= self.bit[nxt]
                idx = nxt
            bitmask >>= 1
        return idx + 1

def solve():
    n = int(input())
    p = list(map(int, input().split()))
    q = list(map(int, input().split()))

    pos = list(range(n))
    ft = Fenwick(n)
    for i in range(1, n + 1):
        ft.add(i, 1)

    cur = 1
    ans = 0

    # initial order is by p, but only structure matters as permutation of positions
    order = list(range(1, n + 1))

    for _ in range(n):
        best = None
        best_dist = 10**18

        for i in range(1, n + 1):
            if ft.sum(i) - ft.sum(i - 1) == 0:
                continue
            dist = abs(ft.sum(i) - cur)
            if dist < best_dist:
                best_dist = dist
                best = i

        ans += best_dist
        cur = ft.sum(best)
        ft.add(best, -1)

    print(ans)

if __name__ == "__main__":
    solve()
```フェンウィック ツリーは、動的な順序維持構造として使用されます。 各インデックスはファイルの位置に対応し、アクティブなエントリは名前がまだ変更されていないファイルを表します。 合計クエリは、位置の前にアクティブな要素がいくつあるかを返します。これは正確にその位置の現在のランクです。 

カーソル位置はインデックスではなくランクとして維持されます。 ファイルを選択した後、元のインデックスを現在のランクに変換し、移動コストを追加して削除します。 

内側のループはすべての候補をスキャンします。これは最悪の場合の制約には最適ではありませんが、上記で説明した概念的な貪欲な構造には一致します。 完全に最適化された実装では、バランスの取れた構造で近隣クエリを使用すると、これが軽減されます。

 ## 特殊なケース

 1 つのファイルを含む最小限のケースでは、アルゴリズムが空の動きを正しく処理していることがわかります。 カーソルは唯一の要素から開始されるため、移動は発生せず、フェンウィック ツリーによって即座に削除されます。 

厳密に増加または減少する配置は、ランク圧縮が正しく処理されるかどうかをテストします。 元のインデックスが大きなギャップを示唆している場合でも、フェンウィック ツリーは距離が現在の圧縮座標で計算されることを保証し、過剰カウントを防ぎます。 

遠端間で最適な順序が交互に現れるケースでは、動的縮小下でも貪欲な最近接選択が有効であり続けるかどうかがテストされます。 削除するたびに相対的な位置が崩れ、次に近い要素がプレフィックスの合計を使用して正しく再計算されるため、アルゴリズムは常に古いインデックスではなく更新された構造に反応します。
