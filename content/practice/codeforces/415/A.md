 ## 解決策
 ## 問題の理解

 工場には、左から右にインデックスされたライトの列があります。 すべてのライトは「オン」状態から始まります。 マシュモクは一連のボタン押しを実行し、各ボタンにはその効果が右にどれだけ広がるかを決定するインデックスがあります。 

インデックス付きボタンの場合`i`を押すと、その位置からすべてのライトがスキャンされます`i`最後まで点灯し、まだ点灯しているライトをすべて消します。 すでに消えている照明は消えたままになり、前に点灯します`i`影響を受けません。 

タスクは、ライトごとに、どのボタンを押したことが初めてライトを消灯したかを判断することです。 影響を受けた回数やその後何が起こったかについては尋ねられません。スイッチをオフにするシーケンスの中で最初に押したときだけが尋ねられます。 

制約は小さく、ライトの数もボタンを押す回数も最大 100 回です。これにより、高度なデータ構造や対数最適化の必要性が即座に排除されます。 単純な 2 次シミュレーションでも、合計演算数が約 10,000 に制限されるため、制限時間内に問題なく収まります。 

微妙な点は、ボタンの順序が保証されていないことです。 後のボタンのインデックスは前のボタンよりも小さい場合があり、これによりどのライトが影響を受けるか、いつオフになるかが変わります。 もう 1 つの重要な詳細は、ライトがオフになると、その後ボタンを押しても記録された応答を変更できないことです。 

単純な間違いは、各ボタンが以前の押下とは無関係な固定セグメントにのみ影響を与えると仮定することです。 たとえば、「まだオン」という条件を無視すると、間違った回答を繰り返し上書きしてしまう可能性があります。 

次の小さなシナリオを考えてみましょう。 

入力:```
3 2
2 1
```正しい動作:

 2 を押すとライト 2 と 3 が消灯し、両方にボタン 2 が割り当てられます。1 を押すとライト 1 が消灯し、ボタン 1 が割り当てられます。 

すでに消灯している照明を再度消灯し続ける不注意なシミュレーションにより、回答が誤って上書きされたり、回答を複数回再割り当てしようとしたりする可能性があります。 

重要なのは、各ライトをオンからオフに移行する瞬間に 1 回だけ割り当てる必要があるということです。 

## アプローチ

 プロセスについて考える最も直接的な方法は、説明どおりに正確にシミュレーションすることです。 各ライトが点灯しているかどうかを表す配列と、各ライトの答えを格納する別の配列を維持します。 ボタンを押すたびに、影響を受けるすべてのライトをインデックスからスキャンします。`n`、まだ点灯しているライトに遭遇したときは常に、このボタンで消灯済みとしてマークします。 

このアプローチは工場のプロセスを段階的に反映しているため、正しいです。 問題は効率です。最悪の場合、それぞれの`m`印刷機は最大でスキャンできます`n`ライト、大まかにつながる`n * m`操作。 最大操作数は 10,000 回のみであるため、制約が与えられている場合でも、これは許容できます。 

もう少し概念的な観察により、推論が簡素化されます。 ライト`j`以下のインデックスを持つボタンに初めて遭遇するとオフになります。`j`シーケンスで。 より大きなインデックスを持つ以前のボタンは影響を受けず、有効なボタンが表示されるとライトはすでにオフになっており、再度考慮されることはありません。 この観察結果はシミュレーションと一致しており、各ライトとボタンを 1 回通過するだけで十分な理由が説明されています。 

したがって、直接的なシミュレーションと派生した「最初の予選プレス」の観点の両方が、同じ実装構造につながります。

 ## アルゴリズムのチュートリアル

 プロセスの展開に直接対応する方法でシミュレーションを説明します。 

1. 配列を初期化する`ans`サイズの`n`、ゼロで埋められます。 これにより、各ライトを消すボタンのインデックスが保存されます。 ブール配列も維持します`on`すべて true に初期化され、すべてのライトが最初にオンであることを表します。 
2. 最初に押したときから最後に押したときまで、指定された順序でボタンを繰り返します。 
3. インデックス付きの各ボタンについて`b_k`、位置からすべてのライトをスキャンします`b_k`を通して`n`。 
4. 位置にライトが点灯している場合`j`まだオンです、割り当てます`ans[j] = b_k`そしてそれをオフとしてマークします。 
5. ライトがすでにオフになっている場合は、結果が以前に決定されており変更できないため、スキップします。 
6. すべてのボタンの押下が処理されるまで続行します。 

ライトがまだオンのときにのみ割り当てる理由は、最初にオフ状態に移行する正確な瞬間をキャプチャしているためです。 その位置をカバーする後続のボタンは無視する必要があります。 

### なぜ効果があるのか

 各ライトの状態はオンからオフに 1 回だけ変化します。 インデックス付きのボタンを初めて使用するとき`b_k ≤ j`加工されていて軽い`j`以前のボタンではカバーできなかったため、まだオンになっています。 その報道には必然的に以下のものが含まれる`j`範囲内にある場合はオフになります。 その瞬間以降、上書きが明示的に禁止されているため、後続の操作は記録された応答に影響を与えることはできません。 これにより、次のことが保証されます`ans[j]`到着した最も古い有効な印刷物を保存します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    b = list(map(int, input().split()))

    ans = [0] * n
    on = [True] * n

    for btn in b:
        i = btn - 1
        for j in range(i, n):
            if on[j]:
                on[j] = False
                ans[j] = btn

    print(*ans)

if __name__ == "__main__":
    solve()
```このソリューションは、前述した正確なシミュレーションに従います。 配列`on`各ライトが 1 回だけ割り当てられるようにします。 内側のループは次から始まります`btn - 1`これは、実装ではライトのインデックスが 0 であるのに対し、入力のインデックスは 1 であるためです。 

よくある落とし穴は、ライトがオフになったら、後のボタンでその答えを上書きしてはいけないということを忘れることです。 条件チェック`if on[j]`この不変条件を強制します。

 ## 特殊なケース

 最小の単一ライトのケースでは、実装がインデックス付けを正しく処理し、無効な範囲にアクセスしようとしないことをチェックします。 いつ`n = 1`、任意のボタン`1`唯一のライトをすぐに消し、割り当ては簡単です。 

ボタンが厳密に増加している場合、各押下はまだカバーされていないサフィックスのみに影響を与える傾向があります。 アルゴリズムは、インデックスが初めてカバーされるときに各ライトを正確に割り当て、位置と最も早い条件を満たすボタンとの間の直接マッピングを生成します。 

ボタンが厳密に減少している場合、最初に押すだけでほぼすべてがカバーされます。 この状況でも、内側のループは正しく実行されますが、値を割り当てるのは 1 回だけであり、後で押しても変更するアクティブなライトが見つかりません。 これにより、`on`配列は上書きを正しく防止します。 

報道内容が重なり合う場合、早期の広範囲報道が後の狭い範囲報道を先取りする可能性があります。 条件`if on[j]`ライトが割り当てられると固定されたままになるため、積極的なオーバーラップ パターンの下でも正確さが維持されます。
