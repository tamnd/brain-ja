 ## 解決策
 ## 問題の理解

 2 種類の引用トークンのみで構成されるシーケンスが与えられます。 各トークンは、次のように書かれた左のスタイルのいずれかです。`<<`または次のように書かれた正しいスタイル`>>`。 課題は、これらを固定の左括弧または閉じ括弧として解釈することではありません。 代わりに、各トークンは曖昧です。周囲の構造に応じて、開始引用符または終了引用符として動作する可能性があります。 

有効な構造は再帰的に定義されます。 空の文字列は有効です。 2 つの有効な構造を連結できます。 そして、有効な構造は次のようにラップできます。`<< A >>`またはとして`>> A <<`、 どこ`A`それ自体は有効です。 これは、2 つの対称的な括弧システムがあることを意味します。1 つは通常の括弧のように動作し、もう 1 つは反転され、両方とも任意にネストできます。 

このような構造を構築した後、引用トークンを除くすべてを消去します。 入力はまさにそのような「平坦化された」シーケンスであり、それが有効な構造から来たものであるかどうかを判断する必要があります。 可能であれば、各トークンを開始引用符または終了引用符としてラベル付けすることにより、1 つの有効な解釈を再構築する必要もあります。 複数の解釈が存在する場合は、いずれか 1 つを受け入れます。 

入力の長さは最大でも約 254 文字ですが、トークンは 2 文字の文字列であるため、有効なシーケンスの長さは最大でも約 127 です。これは十分小さいため、O(n) または O(n log n) の貪欲な解析またはスタックベースの解析で十分ですが、解釈の指数関数的な列挙は不必要で安全ではありません。 

微妙な問題はあいまいさです。次のようなトークンです。`<<`あるペアリング タイプではオープナーとして機能し、別のペアリング タイプではクローザーとして機能します。 単純な固定括弧の解釈はすぐに失敗します。 たとえば、次の文字列`<<>>`複数の点で有効である可能性がありますが、`<<`いつもオープニングのように、`>>`閉じると次のようなケースが誤って拒否されるため、常に`>><<`、これらは逆ペアリングで有効です。 

もう 1 つのエッジ ケースは、ネストの制約により、通常はオープナーであるトークンがクローザーとして機能するように構造が強制する場合です。 ここで、互換性を慎重に考慮しないと、欲張りな選択が失敗する可能性があります。 

## アプローチ

 強引なアイデアは、各トークンの「開始引用」または「終了引用」のいずれかとして考えられるすべての解釈を試み、さらに各ネスト レベルでどのペアリング システムが使用されるかを検討することです。 これは、すべてのポジションが複数の役割に分岐し、解釈の数がカタルーニャ語の構造にペアの方向の割り当てを掛け合わせたように増加するため、指数関数的な増加につながります。 長さ100でもこれは不可能です。 

重要な観察は、実際にはペアリングのタイプをグローバルに決定する必要がないということです。 以前に開いたセグメントを閉じるときに、終了トークンが開始トークンと互換性があることを確認するだけで済みます。 それぞれの開始記号の選択によって、対応する終了記号が何である必要があるかが完全に決まり、またその逆も同様です。 

これにより、問題は 1 つひねったスタック プロセスに短縮されます。トークンは開始または終了として解釈できますが、合法性は、トークンが現在のオープン構造と一致できるかどうかによって決まります。 トークンを見たとき、それがスタックの最上位と互換性がある場合、それを終了トークンとして処理しようとします。 互換性がない場合は、オープニング トークンになる必要があります。 

強制クローズの延期は決して有益ではないため、この貪欲な決定で十分です。プレフィックスをクローズできなくなると、以前の構造に違反することなく、その後の再解釈で不一致を修正することはできません。

 ## アルゴリズムのチュートリアル

 現在開いている引用符のスタックを維持しながら、トークンを左から右に処理します。 各スタック エントリには、開始相場のタイプが保存されます。 

1. 入力文字列を長さ 2 のトークンに解析します (`<<`または`>>`）。 これにより、各決定が文字ごとではなくトークンごとに行われるため、推論が簡素化されます。 
2. 空のスタックと配列を維持する`ans`各トークンが開始として割り当てられているかどうかを格納します (`[`) または終了 (`]`）。 
3. 各トークンについて、スタックの現在のトップを閉じることができるかどうかを確認します。 スタックが空でなく、最上位要素が現在のトークンとは異なる型である場合、トークンは終了トークンとして互換性があります。 これは、ペアリングは反対のシンボル間でなければならないというルールを反映しています。 
4. トークンがスタックトップを閉じることができる場合、スタックをポップし、この位置を次のようにマークします。`]`。 
5. それ以外の場合、それを開始トークンとして扱い、その型をスタックにプッシュし、次のようにマークします。`[`。 
6. すべてのトークンを処理した後、スタックが空でない場合は、有効な構造が存在しないため、失敗が出力されます。 

### なぜ効果があるのか

 スタック不変条件は、逆の順序で一致する終了引用符を必要とする、現在開いている引用符のシーケンスを常に表すことです。 試合を終えるたびに、直近の比類のない開幕戦と対戦することを強いられます。 トークンがトップを合法的に閉じることができない場合、以前のオープナーはすべてスタックの奥深くにあり、さらに多くのネスト違反が必要になるため、以前のオープナーも閉じることができません。 したがって、オープニングが唯一の一貫した解釈です。 ネスト制約は厳密に後入れ先出しであるため、このローカルな決定によりグローバルな一貫性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    
    # parse into tokens: "<<", ">>"
    tokens = []
    i = 0
    while i < len(s):
        tokens.append(s[i:i+2])
        i += 2
    
    stack = []
    ans = []
    
    for tok in tokens:
        if stack and stack[-1] != tok:
            # treat as closing
            stack.pop()
            ans.append(']')
        else:
            # treat as opening
            stack.append(tok)
            ans.append('[')
    
    if stack:
        print("Keine Loesung")
    else:
        print("".join(ans))

if __name__ == "__main__":
    solve()
```すべての決定はトークンの粒度で行われるため、実装ではまず生の文字列を論理トークンに圧縮します。 スタックには、各オープンクオートの実際のトークンタイプが保存されます。 重要な決定は比較です`stack[-1] != tok`、有効なペアは異なるシンボルで構成されなければならないというルールをエンコードします。 この条件が失敗するか、スタックが空の場合は、新しいセグメントを開く必要があります。 

よくある間違いは、スタックトップが現在のトークンと一致する場合にクローズを許可してしまうことです。 このシステムでは同一のシンボルが有効な囲みペアを形成できないため、これはペアリング ルールに違反します。

 ## 特殊なケース

 エッジ ケースの 1 つは、文字列が、通常は何かを閉じることが期待されるトークンで始まる場合です。`>><<`。 スタックが最初は空であるため、アルゴリズムはこれを正しく処理し、その ID に関係なく最初のトークンを強制的に開始として処理します。 

もう 1 つのエッジケースは、次のような完全に対称な文字列です。`<<<<>>>>`、方向性を仮定すると、素朴な固定解釈は失敗します。 スタックにより、各クロージングの決定が利用可能なオープン構造によってのみ決定されることが保証されます。 

3 番目のエッジ ケースは、カウントではバランスがとれているように見えますが、構造的に不可能なシーケンスです。`<<>>><<`。 スタックは可能な限り閉じようとしますが、最終的には何も閉じることができないトークンに遭遇します。
