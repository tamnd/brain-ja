 ## 解決策
 ## 問題の理解

 私たちには、払い戻し伝票の生成に使用できる 2 台の同一の機械を備えたチケット印刷システムが与えられました。 各マシンは操作ごとに最大 1 つのチケットを生成でき、チケットを生成した後は冷却期間の間使用できなくなります。`a`分。 マシンを一度使用すると消費します`b`アクティブな作業時間の分。 重要な制限は、常にアクティブに操作できるのは 1 台のマシンのみであることです。つまり、両方のマシンの準備ができていても、両方のマシンを並行して実行することはできません。 

各テストケースにはクールダウンが与えられます`a`、操作時間`b`、チケットの枚数`n`。 タスクは、すべてを作成するのに必要な最小合計時間を決定することです。`n`チケット。 

制約`n ≤ 10^9`チケットごとのシミュレーションは直ちに除外されます。 各チケットに対する対数シミュレーションやイベントごとのシミュレーションでも遅すぎます。`10^5`テストケース。 解は、テスト ケースごとに閉じた形式で一定時間内に導出する必要があります。 

この問題の微妙な点は、マシン制約が対称並列処理ではないことです。 マシンが 2 台ある場合でも、一度に実行できる操作は 1 つだけです。これは、並列処理というよりも、クールダウン スロットを交互にスケジュールすることに似ています。 2 台のマシンがスループットの 2 倍を意味すると考えるのは単純な誤解ですが、「一度に 1 台のマシンのみを使用できる」という制限があるため、これは誤りです。 

エッジケースは次の場合に発生します。`a = 0`、クールダウンがなくなり、プロセスが純粋に逐次的に行われるようになったとき、および`a`に比べて非常に大きいです`b`そのため、同じマシンを短期間で再利用することは不可能になります。 もう 1 つの重要なエッジケースは、`n = 1`、必要な操作は 1 つだけであり、クールダウンは関係ありません。 

## アプローチ

 ブルートフォース手法では、時間を明示的にシミュレートします。 現在の時刻を維持し、各マシンがいつ利用可能になるかを追跡し、操作を実行するために次に利用可能なマシンを繰り返し選択します。 各チケットの後、時間を進めます。`b`、そのマシンを次の期限まで使用不可としてマークします。`current_time + a`、すべてのチケットが作成されるまで続行します。 これはシステム制約を直接モデル化しているため、これは正しいです。 

ただし、このアプローチはすぐに劣化します。 それぞれの`n`チケットではマシンの状態を更新し、可用性を選択する必要があるため、複雑さは次のとおりです。`O(n)`テストケースごとに。 と`n`まで`10^9`、これは不可能です。 

重要な観察は、システムが実際には分岐したり、最後の操作時刻以降の履歴に依存したりしないことです。 一度に使用できるマシンは 1 台だけであるため、唯一の実際の決定は、前の操作の終了後にすぐにマシンを再利用できるか、それともクールダウンを待たなければならないかということです。 これにより、繰り返しのパターンが作成されます。クールダウンが短い場合は継続的に作業し、クールダウンが長い場合はアイドル状態の隙間に強制的に入るかのどちらかです。 

このプロセスは 2 つのケース構造に集約されます。 クールダウンの場合`a`十分に小さいため、1 つの操作を終えて切り替えを行う頃には、マシンはすでに準備が整っており、待つ必要はありません。 それ以外の場合は、いくつかの操作の間にアイドル時間を挿入する必要があります。 各操作には効果的に時間がかかります`b`時間ですが、もし`a > b`、それなら待たなければなりません`a - b`切り替えでは並列実行が許可されないため、同じマシンを再利用する前に実行されます。 

これにより、プロセスが直線的なスケジュールに単純化されます。合計時間は`n * b`さらに、クールダウンが実行時間を超えるたびに追加のアイドル ギャップが発生します。

 ## アルゴリズムのチュートリアル

 スケジュールを次のシーケンスとしてモデル化します。`n`次々と実行される操作。 

1.時間から始める`0`。 各チケットに必要なものは正確に`b`アクティブな作業時間（分）であるため、基本時間は常に`n * b`。 これは、すべてのチケットの必須処理時間を考慮します。 
2. クールダウンによってアイドル時間が発生するかどうかを比較して判断します。`a`そして`b`。 1つの操作が終わったら、すぐにお金を使います`b`時間になるので、次の操作が開始されます`b`数分後。 もし`a ≤ b`、その後、再び操作する準備が整うまでに、マシンはすでに冷却されています。 待つ必要はありません。 
3. もし`a > b`、操作が終了した後も、マシンはさらに冷却されます。`(a - b)`そうでなければ次の操作を開始する数分後です。 一度に 1 台のマシンしか操作できないため、2 台目のマシンを使用してこのギャップを隠すことはできません。 これにより、連続する各操作の間に、避けられないアイドル期間が生じます。 
4. あります`n - 1`間の移行`n`操作なので追加します`(n - 1) * max(0, a - b)`合計時間に。 
5. 計算された合計を返します。 

### なぜ効果があるのか

 スケジュールは、操作間の連続した依存関係によって完全に決定されます。 操作は重複できないため、非効率となる可能性があるのは、マシンを再利用する際にクールダウンを待つことだけです。 システムは余分な並列容量を蓄積することはないため、各ギャップは独立しており同一です。 これにより、プロセスは、各エッジが次のいずれかに寄与する線形チェーンと同等になります。`b`一人で、または`b + (a - b)`クールダウンが実行時間を超えるかどうかに応じて異なります。 

最初の操作を除くすべての操作の前には 1 つの遷移があり、各遷移は同一の構造を持っているため、式は合計累積時間と正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    a, b, n = map(int, input().split())
    
    base = n * b
    idle = max(0, a - b) * (n - 1)
    
    print(base + idle)
```この実装は、合計時間を必須の作業とオプションのアイドル ギャップに分解することを直接エンコードします。 掛け算`n * b`各チケットの作成コストを累積します。 用語`(n - 1)`これは、最初の操作をブロックする以前のアクションがないため、最初の操作には事前のクールダウン要件がないことを示しています。 の`max(0, a - b)`クールダウンが次の操作の実行にすでに費やした時間を超えた場合にのみアイドル時間を追加します。 

よくある落とし穴は、クールダウンが実行時間と重なることを忘れることです。 もし`a ≤ b`、マシンは終了前または終了直後に利用可能になるため、余分な待ち時間は発生しません。 

## 実用的な例

 代表的な 2 つのケースを考えてみましょう。 

初め、`a = 1, b = 3, n = 4`。 

| ステップ | 稼働時間 | 次の準備時間 | アイドル追加 | 合計 |
 | --- | --- | --- | --- | --- |
 | 1 | 3 | 3 | 0 | 3 |
 | 2 | 3 | 6 | 0 | 6 |
 | 3 | 3 | 9 | 0 | 9 |
 | 4 | 3 | 12 | 0 | 12 |

 ここ`a < b`, そのため、クールダウンがスケジュールに影響することはありません。 結果は単純に`n * b = 12`。 

2番、`a = 7, b = 3, n = 4`。 

| ステップ | 稼働時間 | クールダウンギャップ | アイドル追加 | 合計 |
 | --- | --- | --- | --- | --- |
 | 1 | 3 | - | 0 | 3 |
 | 2 | 3 | 7 - 3 = 4 | 4 | 10 |
 | 3 | 3 | 4 | 4 | 17 |
 | 4 | 3 | 4 | 4 | 24 |

 次の操作の基本時間枠が終了した後もマシンがまだ冷却中であるため、各移行では 4 分間のアイドル期間が強制されます。 

これらのトレースは、アイドル状態がクールダウンが実行時間を超えた場合にのみ発生し、すべての遷移にわたって均一に繰り返されることを示しています。

## テストケース```python
# helper: run solution on input string, return output string
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline
    
    t = int(input())
    out = []
    for _ in range(t):
        a, b, n = map(int, input().split())
        base = n * b
        idle = max(0, a - b) * (n - 1)
        out.append(str(base + idle))
    return "\n".join(out)

 ## 特殊なケース

 いつ`a = 0`、システムにはクールダウンがまったくないため、各チケットは遅延なく連続して処理されます。 この式は正しく減少します。`max(0, a - b)`がゼロになるので、合計時間はちょうど`n * b`。 

いつ`a = b`、次の操作が開始される正確なときにマシンが使用可能になります。 これにより、アイドル時間のない完璧なパイプラインが作成され、これも式と一致します。`(a - b) = 0`。 

いつ`a > b`、すべての遷移では固定遅延が発生します。 たとえば、`a = 5, b = 2, n = 3`、最初のステップ以降の各ステップでは 3 分の遅延が発生します。 スケジュールは決定的かつ線形になり、式はまさに 2 つのそのような遷移を説明します。 

いつ`n = 1`、トランジションはまったくありません。 の`(n - 1)`ファクターはアイドル状態の影響を適切に排除し、単一の操作コストのみを残します。`b`。
