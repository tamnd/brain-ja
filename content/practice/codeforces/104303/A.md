 ## 解決策
 ## 問題の理解

 複数の独立したシナリオが与えられます。 各シナリオでは、学生は運ぶ必要がある固定数のアイテムから始まり、パスに沿っていくつかのチェックポイントがあります。 各チェックポイントで、学生がそのチェックポイントを「使用する」ことを選択すると、一定数のアイテムが取り上げられ、そのチェックポイントのヘルパーによって目的地まで輸送されます。 ヘルパーの利用ごとに 1 ドリンクの料金がかかります。 

学生はチェックポイントを訪れる順序を選択することができ、最終的にすべてのアイテムが確実に輸送されるようにしながら、最終的に使用する異なるチェックポイントの数を最小限に抑えることが目標です。 

重要な相互作用は、各チェックポイントが固定容量に寄与し、チェックポイントを使用すると残りの負荷が軽減されることです。 複数のチェックポイントが使用される場合、輸送されるアイテムの合計はそれらの寄与の合計となり、この合計は初期負荷に達するか、それを超える必要があります。 

各シナリオの出力は、それらの合計が少なくとも初期項目数になるように必要なチェックポイントの最小数です。 

制約は十分に小さいため、ソートとリニア スキャンで簡単に十分です。 各テストには最大 200 のチェックポイントがあり、値は中程度であるため、テスト ソリューションあたりの O(n log n) または O(n) は十分に制限内にあります。 

大きな貢献が分散している場合、微妙な失敗例が現れます。 単純なアプローチでは、並べ替えを行わずに任意の順序付けまたは貪欲な選択をシミュレートしようとする可能性があり、最適なサブセットを逃してしまう可能性があります。 たとえば、最初に小規模なコントリビュータを選択すると、必要なチェックポイントの総数が減少する大規模なコントリビュータが存在する場合でも、カウントが不必要に増加する可能性があります。 

もう 1 つのエッジ ケースは、単一のチェックポイントがすでに要件を満たしている場合です。 これを明示的に処理しないアルゴリズムは、ソート後に自然に最初に最大のものを選択する場合にのみ正しく縮退します。 

## アプローチ

 ブルートフォース解釈では、チェックポイントのすべてのサブセットを考慮し、その合計を計算し、その合計が必要な負荷に達する最小のサブセットを選択します。 これは、すべての可能性を直接テストするため、正しいです。 ただし、これには 2^n 個のサブセットをチェックする必要があり、n = 200 の場合でも、サブセットの数が現実的な計算限界を超えるため、これは完全に不可能です。 

単調な目的を持つ選択問題として再解釈すると、問題の構造は大幅に単純化されます。 各チェックポイントは独立して寄与し、順序は最終的な合計には影響せず、どのチェックポイントが選択されるかのみが重要です。 必要な合計に達しながら、選択するチェックポイントの数を最小限に抑えるには、常により大きな貢献を最初に優先する必要があります。 これにより、問題は古典的な貪欲な戦略に変わります。つまり、貢献度を降順に並べ替え、累積合計が目標に達するまで選択を続けるというものです。 

これが機能するのは、大きな値の代わりに小さな値を使用する最適解は、選択された要素の数を増やすことなく、未使用の大きな値と交換することで改善できるためです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n · n) | O(n) | 遅すぎる |
 | 貪欲な並べ替え | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。

1. 貢献度の配列 a とともに、n と w を読み取ります。 これらは、各チェックポイントがオフロードできる項目の数を表します。 
2. 最大の寄与が最初に考慮されるように、配列を降順に並べ替えます。 この順序により、各選択により残りの負荷が最大限に削減されることが保証されます。 
3. 累計をゼロに、カウンタをゼロに初期化します。 合計はこれまでにオフロードされたアイテムの数を追跡し、カウンターは使用されたチェックポイントの数を追跡します。 
4. ソートされた配列を反復処理し、各値を累計に加算し、毎回カウンターを 1 ずつ増やします。 
5. 現在の合計が w 以上になったら、すぐに停止します。 現時点でのカウンターは、必要なチェックポイントの最小数です。 
6. カウンタを出力します。 

早期に停止できる理由は、要件が満たされた後にチェックポイントを追加しても、実行可能性が向上せずに数が増えるだけだからです。 

### なぜ効果があるのか

 貪欲な戦略は交換議論に依存しています。 k 個のチェックポイントを使用するが、最大 k 個の寄与のうちの 1 つを含まない最適解が存在すると仮定します。 次に、合計を減らさずに、より大きな未使用の値に置き換えることができる、より小さな選択された値が存在する必要があります。 この置換によって選択される要素の数が増えることはないため、この変換を繰り返し適用すると、常に利用可能な最大の寄与を最初に選択するソリューションが得られます。 したがって、ソートされた貪欲な構築は最適なソリューションと一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    
    for _ in range(t):
        n, w = map(int, input().split())
        a = list(map(int, input().split()))
        
        a.sort(reverse=True)
        
        total = 0
        cnt = 0
        
        for x in a:
            total += x
            cnt += 1
            if total >= w:
                break
        
        out.append(str(cnt))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装は貪欲戦略に直接従います。 逆に並べ替えると、常に最大の残りの貢献者が最初に選択されます。 ループは要件が満たされるまで寄与を蓄積し、停止した瞬間に最小数のピックが得られます。 

よくある間違いは、目標は合計を最大化することではなく、カウントを最小化することであることを忘れることです。これがソート方向が重要である理由です。 もう 1 つの微妙な問題は、累積をケースごとにリセットする必要があるため、複数のテスト ケースを個別に処理することです。

 ステップ 3 では、合計が 100 を超えているため、答えは 3 です。これは、最大の寄与を早期に選択すると、必要なチェックポイントの数が最小限に抑えられることを示しています。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(T · n log n) | テスト ケースごとに並べ替えが優先されます。 
| スペース | O(n) | アレイのストレージ |

 この制約により、テストごとに最大 200 個の要素が許可されるため、200 個の数値を最大 200 回ソートすることは、制限内であれば簡単です。 貪欲スキャンは線形であり、並べ替えと比較すると無視できる程度です。

 ## 特殊なケース

 重要なエッジケースは、最大の単一貢献がすでに要件を満たしているか、それを超えている場合です。 入力の場合:```
n = 3, w = 10
a = [10, 1, 1]
```並べ替えると得られるもの`[10, 1, 1]`。 最初のステップはすでにターゲットに到達しているため、アルゴリズムは答え 1 ですぐに停止します。完全な走査が完了するまでチェックを誤って遅らせるアプローチはいずれも正しいことになりますが、時間の無駄になります。 寄与のバランスをとろうとするアプローチでは、最初に複数の小さな要素が誤って選択され、次善の 3 が返される可能性があります。 

もう 1 つのエッジ ケースは、すべての値が小さく、その組み合わせのみが機能する場合です。```
n = 4, w = 20
a = [6, 6, 6, 6]
```ソート順序は変更されず、累積は 3 ピック後に 18 に達し、4 ピック後に 24 に達します。 アルゴリズムは正しく 4 を返し、特別なケースを使用せずに完全な消費シナリオを自然に処理していることを示しています。
