 ## 解決策
 ## 問題の理解

 各位置が 0 または 1 のバイナリ文字列が与えられます。最大で k 個のゼロを 1 に変更できます。 これらの変更を実行した後、できるだけ多くの互いに素なセグメントを抽出します。各セグメントは、完全に 1 で構成される長さ d の連続ブロックです。 

重要な制約は、選択したセグメントが重なってはいけないということです。そのため、位置 i から始まるセグメントを取る場合、i から i + d − 1 の範囲内の位置を別のセグメントに使用することはできません。 k 個のゼロを最適に反転した後、そのようなセグメントの数を最大化しようとしています。 

各テスト ケースは独立しており、文字列の長さは最大 2000 ですが、k は最大 100、d は最大 50 です。これは、テストあたり O(n²k) または O(nk) のような解が許容されることをすぐに示唆していますが、最適化が不十分な場合、n の 3 次のものは境界線になります。 

わずかな失敗例は、少数のゼロを少し前後に反転することで全体的により多くのセグメントのロックを解除できるということを考慮せずに、貪欲な戦略でセグメントの選択が早すぎる場合に発生します。 たとえば、d = 3 で、文字列が 00111000 (k = 2) の場合、最初に考えられるセグメントを貪欲に修正すると、後続の 1 つのセグメントではなく 2 つのセグメントが有効になるフリップが消費される可能性があります。 

もう 1 つのエッジ ケースは、d = 1 の場合です。この場合、すべての位置はすでに有効なセグメントであり、答えは単純に位置の数に k に応じて追加の処理を加えたものになります。ただし、実際には、反転後にゼロはすでに単一長のセグメントとして使用できるため、反転は重要ではありません。 

最後に、k = 0 の場合、長さ d の互いに素な all-one ブロックがいくつ存在するかを数えることになります。これは純粋に構造的なものであり、既存の 1 の連続を注意深くセグメント化する必要があります。 

## アプローチ

 この強引なアイデアは、k 個のゼロを反転した後、セグメントを選択する可能なあらゆる方法を試みることです。 反転する位置のサブセットを列挙し、長さ d のオールワン セグメントがいくつ形成できるかを貪欲に確認することを想像することもできます。 固定セットのフリップの場合でも、セグメントのカウントは線形ですが、フリップの選択肢の数は組み合わせによるもので、およそ O(n が k を選択) であり、あまりにも多すぎます。 

2 番目のブルートフォースの改良は、位置、残りのフリップ、およびすでに取得したセグメントの数に対する動的プログラミングです。 位置 i から、スキップするか、可能であればセグメントを開始するか、ウィンドウ内でゼロを反転します。 これはすでに最適な構造に向かって進んでいますが、ウィンドウの再計算コストが素朴である場合、依然として O(n²k) かそれ以上のリスクがあります。 

重要な観察は、問題の構造が間隔ベースで局所的であるということです。 各セグメントはオーバーラップ制約を除いて独立しており、長さ d の各セグメントは、そのウィンドウ内でいくつかのゼロを 1 に変換する必要があります。 すべての長さ d のウィンドウ内のゼロの数を事前計算すると、そのウィンドウを有効にするために必要なフリップの回数が正確にわかります。 

これにより、問題は、それぞれにコスト (内部のゼロの数) と予算 k が設定された、互いに素な間隔を選択することに変換されます。 ナップザックのような制約の下で間隔の数を最大化したいと考えていますが、間隔は重複できないという追加の制限があります。 これは、位置、残りの予算、セグメント数に対する動的プログラミングを示唆しています。 

dp[i][j] を、j 回のフリップで i までのプレフィックスを使用して取得できる有効なセグメントの最大数として定義します。 各位置 i から、それをスキップするか、i ≥ d の場合、そのウィンドウ内のゼロの数に等しいコストを使用して i で終わるセグメントの形成を試みます。 n が小さい (2000) ため、スライディング ウィンドウとプレフィックス合計を使用して効率的に遷移を計算できます。 

重要な改善点は、ゼロ カウントを繰り返し再計算する代わりに、ゼロのプレフィックス合計を維持するため、各ウィンドウ コストが O(1) となり、合計遷移が O(nk) になることです。

 ## アルゴリズムのチュートリアル

 prefix[i] が S[0..i−1] に現れるゼロの数をカウントするプレフィックス合計配列を構築することによって文字列を前処理します。 これにより、任意のセグメント内のゼロの数を一定時間内に計算できます。 

次に、ポジションと残りのフリップに対して DP を構築します。 

1. DP テーブルを初期化します。ここで、dp[i][j] は、最大 j 回のフリップで最初の i 文字を使用して形成できるセグメントの最大数を表します。 文字がゼロの場合はセグメントがゼロになるため、すべての j に対して dp[0][j] = 0 を除くすべての値を非常に負の数に設定します。 
2. 位置 i を 0 から n まで繰り返します。 各位置で、まず現在の文字をスキップして値を前方に伝播します。これは、dp[i+1][j] がすべての j に対して少なくとも dp[i][j] になることを意味します。 これは、i でセグメントを開始しないことに対応します。 
3. 各位置 i から、セグメントを配置するのに十分な長さがある場合 (i + d ≤ n)、接頭語の合計を使用して S[i..i+d−1] をすべて 1 に変換するコストを計算します。 このコストは、そのウィンドウ内のゼロの数です。 
4. このコストが最大でも j の場合、i+d−1 で終わる 1 つのセグメントを取得することで、dp[i][j] から dp[i+d][j −cost] に遷移できます。 dp[i+d][j −cost] を dp[i][j] + 1 で更新します。 
5. すべてのポジションとすべてのフリップ予算に対してこのプロセスを継続し、常に既知の最良の値を維持します。 
6. 最終的な答えは、すべての i と j の dp[i][j] の最大値です。 

なぜ効果があるのか

 DP は、セグメントが取得されるときに正確に d 位置だけ前方に遷移することによって、重複しないセグメントを強制します。 すべてのセグメントの決定は連続したブロックを消費し、それらのインデックスの再利用は決して許可されません。 プレフィックスベースのコストにより、各候補セグメントに必要なフリップの数が正確に考慮されます。 すべての有効な解決策はそのようなセグメント ピックのシーケンスに対応し、そのようなすべてのシーケンスは DP で表現できるため、最適な解決策が除外されることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    INF = -10**9

    for _ in range(T):
        k, d, S = input().split()
        k = int(k)
        n = len(S)

        # prefix sum of zeros
        pref = [0] * (n + 1)
        for i in range(n):
            pref[i + 1] = pref[i] + (S[i] == '0')

        dp = [[INF] * (k + 1) for _ in range(n + 1)]
        for j in range(k + 1):
            dp[0][j] = 0

        for i in range(n):
            for j in range(k + 1):
                if dp[i][j] == INF:
                    continue

                # skip position i
                if dp[i][j] > dp[i + 1][j]:
                    dp[i + 1][j] = dp[i][j]

                # take segment starting at i
                if i + d <= n:
                    cost = pref[i + d] - pref[i]
                    if cost <= j:
                        nj = j - cost
                        if dp[i + d][nj] < dp[i][j] + 1:
                            dp[i + d][nj] = dp[i][j] + 1

        ans = 0
        for i in range(n + 1):
            for j in range(k + 1):
                ans = max(ans, dp[i][j])

        print(ans)

if __name__ == "__main__":
    solve()
```この実装は、位置と残りのフリップによって dp にインデックスを付けることができるという事実に大きく依存しています。 プレフィックス配列は、各候補ウィンドウ内のゼロの数を再計算することを回避するために重要です。そうしないと、解が O(n²k) になってしまいます。 

スキップ トランジションでは、セグメントの開始を強制しないようにします。一方、テイク トランジションでは、有効な長さ d のブロックのみを配置し、ポインタを d だけ前方に移動して、素性を保証します。 

## 実用的な例

 S = 10111101、k = 2、d = 4 を考えてみましょう。 

長さ 4 の各ウィンドウでゼロ カウントを計算します。 

インデックス 0 ウィンドウ 1011 にはゼロが 1 つあります

 インデックス 1 ウィンドウ 0111 にはゼロが 1 つあります

 インデックス 2 ウィンドウ 1111 にはゼロが 0 あります

 インデックス 3 ウィンドウ 1110 にはゼロが 1 つあります

 インデックス 4 ウィンドウ 1101 にはゼロが 1 つあります

 DP は、最初にインデックス 2 でゼロコスト ウィンドウを取得し、セグメントを 1 つすぐに与えることを検討します。その後、オーバーラップ制約と限られた反転により、別の互いに素なセグメントを形成できません。 

| 私 | j (反転) | アクション | dp値 |
 | --- | --- | --- | --- |
 | 0 | 2 | 開始 | 0 |
 | 2 | 2 | テイク1111 | 1 |
 | 6 | 2 | 終わり | 1 |

 これは、最適な戦略ではゼロコストまたは低コストのウィンドウが優先されることを示しています。 

ここで、S = 000000、k = 3、d = 2 について考えてみましょう。 

長さ 2 の各セグメントには 2 回のフリップがかかります。 k = 3 では 2 つのセグメントには不十分であるため、最大でも 1 つのセグメントを取ることができます。 

| 私 | j | アクション | DP |
 | --- | --- | --- | --- |
 | 0 | 3 | 00を取る | 1 |
 | 2 | 1 | 次は取れません | 1 |

 これは、フリップ バジェットがどのようにセグメント数を直接制限するかを示しています。

 ## 特殊なケース

 重要なエッジ ケースは、k = 0 の場合です。この状況では、DP は既存のオール 1 ブロックをカウントするのとまったく同じように動作する必要があります。 たとえば、S = 11101111、d = 3 では、反転せずにすでに完全に有効になっているウィンドウのみをカウントする必要があります。 j = 0 の場合、コスト > 0 の遷移は禁止され、コスト 0 のセグメントのみが生き残るため、DP はこれを処理します。 

もう 1 つのエッジ ケースは、個別には魅力的に見えますが、一緒に選択できない重なり合うウィンドウです。 S = 111111 および d = 4 の場合、異なるインデックスで始まる有効なウィンドウが複数ありますが、dp[i+d] ジャンプにより 1 つを選択すると他のウィンドウがブロックされます。 DP は構造的に非結合性を強制するため、重複するセグメントを二重にカウントすることはありません。
