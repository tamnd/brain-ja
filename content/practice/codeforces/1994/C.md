 ## 問題の理解

 値の行が与えられ、非常に具体的なシミュレーション ルールの下で「適切に」動作する連続セグメントの数を数えたいとします。 

セグメントを選択するとき$[l, r]$、その要素を左から右に処理し、累計を維持します$g$。 各要素を追加した後、累計がしきい値を超えた場合$x$、合計はゼロにリセットされます。 それ以外の場合は、そのままになります。 セグメント全体を処理した後、最終的な値が以下の場合、セグメントは良好であるとみなされます。$g$ゼロではありません。 タスクは、複数のテスト ケースにわたって、そのような良好なセグメントをすべてカウントすることです。 

この制約により、テスト ケースごとに線形または線形に近い解決策の観点から考えることが求められます。 すべてのテスト ケースの合計の長さは最大でも$2 \cdot 10^5$これにより、すべてのセグメントを明示的にチェックするなどの二次関数は除外されます。 有効なソリューションは基本的に、各要素が一定の回数処理されるスライディング ウィンドウまたは増分構造を維持する必要があります。 

値が相対的に非常に大きい場合、微妙なエッジケースが発生します。$x$。 このような場合、すべての要素が個別に合計をリセットします。これは、単一要素セグメントのみが有効であることを意味します。 もう 1 つのエッジ ケースは、配列が減少していない、またはすべて小さい値である場合です。この場合、長いセグメントはリセットされずに多くのステップを乗り越え、プレフィックスの合計のみを追跡する単純なロジックではオーバーカウントが発生します。 

## アプローチ

 ブルートフォースソリューションはすべてのセグメントを試みます$[l, r]$、プロセスをシミュレートし、最終的に$g$はゼロではありません。 各シミュレーションには次の時間がかかります$O(n)$、につながる$O(n^3)$最悪の場合、合計が遅すぎます。 

重要な観察は、プロセスが最後のリセット以降の現在の累積合計にのみ依存しているということです。 合計額を超えると$x$、ゼロにワイプされ、プロセスがローカルで再起動されます。 これにより、累計が決して超過しない自然な「有効なブロック」が作成されます。$x$、ブロック間の境界は独立して動作します。 

問題は、現在の合計がリセットをトリガーする前に、各位置から始まるセグメントをどこまで拡張できるかを追跡することに帰着します。 これらの境界がわかれば、2 ポインターまたはプレフィックスベースのカウント戦略を使用して有効なセグメントをカウントできます。 

ブルート フォースはリセットを明示的にシミュレートするため機能しますが、同じプレフィックス動作を繰り返し再計算するため失敗します。 リセットによって配列が独立したセグメントに分割されるという観察により、計算された構造を再利用し、寄与を効率的にカウントできるようになります。

 ## アルゴリズムのチュートリアル

 各テスト ケースを個別に処理し、配列全体にわたってスライディング ウィンドウを維持します。 

1. 左ポインタを維持します$l$そして累計$g$。 アイデアは、最大セグメントを次の時点で開始するようにすることです。$l$プロセスがリセットされていない場合。 
2. 繰り返します$r$左から右に追加$a[r]$に$g$。 これは、現在のセグメントの拡張をシミュレートします。 
3. もし$g$を超える$x$、設定によってリセットをシミュレートします$g = 0$そして動く$l$に$r + 1$。 これは、前のセグメントが$r$有効な継続に貢献できません。 
4. 各ポジションで$r$、 もし$g \neq 0$、その後任意の開始点$l' \in [l, r]$で終わる有効なセグメントを生成します$r$なぜなら、これらの開始のいずれも、到達する前に即時リセットを引き起こすことはなかったはずだからです。$r$。 追加します$r - l + 1$答えに。 
5. 最後まで継続し、貢献を積み上げます。 

重要な考え方は、リセットによって配列が独立したブロックに分割され、各ブロック内で、プロセス後に生き残った各位置で終わるすべてのサブ配列をカウントするということです。 

### なぜ効果があるのか

 不変条件は、いつでも、$l$常に、リセットが発生していない現在のアクティブ ブロックの最初のインデックスを指します。$l$。 累計$g$処理されたセグメントを正確に表します$[l, r]$ゲームのルールの下で。 リセットするたびに、それ以上拡張できない以前のすべてのコントリビューションが正しく破棄されます。 これにより、各有効なセグメントが 1 回だけカウントされ、完了前に必ずリセットがトリガーされるため、すべての無効なセグメントが除外されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, x = map(int, input().split())
        a = list(map(int, input().split()))
        
        l = 0
        g = 0
        ans = 0
        
        for r in range(n):
            g += a[r]
            
            if g > x:
                g = 0
                l = r + 1
                continue
            
            ans += (r - l + 1)
        
        print(ans)

if __name__ == "__main__":
    solve()
```実装はスライディング ウィンドウ ロジックに直接に従います。 ポインタ$l$は、リセットが発生した場合にのみ更新されます。これは、しきい値を超えることに相当します。 貢献$r - l + 1$で終わる部分配列の有効な開始点をすべてカウントします。$r$。 リセット手順がないと、無効な部分和が将来のセグメントに誤って引き継がれてしまうため、リセット手順は非常に重要です。 

## 実用的な例

合計は 2 で、予想される動作と一致します。 

ここで考えてみましょう$[1, 1, 1, 1]$と$x = 2$。 合計が次の値を超えるまでウィンドウが拡大します。$x$、その後リセットされ、各安全ブロック内の貢献度を繰り返しカウントします。 トレースは、有効なブロック内のすべての拡張が線形に寄与し、リセットによってブロック間の相互汚染が防止されることを示しています。

 ## 特殊なケース

 すべての要素がより大きい場合$x$、すべてのステップで即時リセットがトリガーされるため、長さ 1 のセグメントのみが有効です。 アルゴリズムはこれを処理します。$g > x$、リセットして移動します$l$現在のインデックスを超えて、無効なセグメントが寄与しないようにします。 

すべての要素が小さく、合計が超えない場合$x$、ウィンドウは決してリセットされず、答えはすべての部分配列数の合計になります。これは次の式で計算されます。$(r - l + 1)$正しく蓄積されます。 

リセットが正確な位置で発生した場合$r$の場合、実装では、そのステップでは貢献がカウントされないことが保証されます。$g$は、回答に追加する前にクリアされ、壊れたセグメントが誤って含まれるのを防ぎます。
