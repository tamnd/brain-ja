 ## 解決策
 ## 問題の理解

 それぞれの高さが固定された建物の列が与えられます。 時間の経過とともに、砂嵐が建物の一部のセグメントを部分的に「覆い」、そのセグメント内の各建物は特定の高さ制限までしか見えなくなります。 この制限を超えるものは非表示になり、このクリッピングは建物ごとに個別に適用されます。 

各クエリは建物の連続した範囲を選択し、その範囲に新しい可視性の上限を課します。 建物が以前の嵐によってすでに部分的に覆われている場合、可視性はその建物に影響を与えるすべての適用された制約の中で常に最小であるため、より厳しい (小さい) キャップが優先されます。 更新のたびに、すべての建物の表示可能なフロアの合計数を計算する必要があります。 

したがって、すべての更新後の主要な数量は、現在の可視高さのすべての建物の合計になります。ここで、各建物の可視高さは、適用される最小の暴風雨キャップによって切り取られた元の高さになります。 

制約は大きく、最大 100,000 の建物と 100,000 の更新です。 各クエリの後に範囲全体または配列全体をスキャンする単純な再計算では、遅すぎます。 クエリごとに線形でもあるソリューションは明らかに制限を超えています。 範囲の更新と高速なグローバル集約をサポートする構造が必要です。 

更新が複雑に重なる場合、微妙なエッジケースが発生します。 たとえば、後でクエリを実行すると、以前は上限が小さかったリージョンの上限が増加する可能性があります。 すべての嵐において可視性は最小限であるため、キャップを増やしても、すでに縮小されている建物には何も影響しません。これにより、慎重にマージ セマンティクスを行わずに更新を割り当てとして扱うソリューションが誤解を招く可能性があります。 

次の入力を考えてみましょう。```
3 2
5 5 5
1 3 2
2 3 10
```最初のクエリの後、すべての建物は 2 になるため、合計は 6 になります。2 番目のクエリの後は、2 が依然としてこれらの建物に対する最小制約であるため、何も変更されるはずはありません。 単純な「上書き」アプローチでは、配列の一部が誤って生成されてしまいます。 

これは、範囲最小割り当て構造を維持しているが、各操作の後にグローバル合計クエリを使用していることをすぐに示唆しています。 

## アプローチ

 ブルーフォースのアイデアは単純明快です。 現在表示されている高さの配列を維持します。 クエリごとに、セグメント内のすべての建物を反復処理し、各値を次のように更新します。`min(current_value, f)`、その後、合計を再計算します。 これは正しいです。各建物に適用される最小上限が個別に追跡されるからです。 

ただし、このアプローチは次のことを行います。$O(n)$更新のためだけにクエリごとに動作し、場合によっては別のクエリも実行される$O(n)$合計を再計算するため。 と$n, q \le 10^5$、これはおおよそ次のことにつながります$10^{10}$実行可能な限界をはるかに超えた最悪の場合の操作。 

重要な観察は、各更新では値が減少するだけで、値が増加することはないということです。 建物の目に見える高さが低くなると、より高い値を求めて再検討する必要はありません。 この単調性により、同じ要素を繰り返し処理することを避けることができます。 

これを利用するために、遅延伝播を備えたセグメント ツリーを使用します。 各ノードには、そのセグメントの総和とセグメント内の最大値が格納されます。 重要な操作は範囲「chmin」です: apply`a[i] = min(a[i], f)`ある範囲にわたって。 

セグメント内の最大値がすでに以下の場合`f`、何も変わりません。 セグメント内の最小値が次の値より大きい場合`f`を使用すると、降下せずに 1 ステップでセグメント合計を完全に上書きできます。 そうでない場合は、作戦を中止する必要があります。 

この構造では、必要な場合を除き、個々の要素に触れることは避けられ、各要素は安定するまでに対数倍しか減らすことができません。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 範囲 chmin | のセグメント ツリー O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ノードが 2 つの値 (セグメントの合計とセグメント内の最大値) を格納するセグメント ツリーを維持します。 

1. 初期の高さからセグメント ツリーを構築します。 各リーフには 1 つの建物が格納され、内部ノードは子からの合計と最大値を結合します。 これにより、スカイラインの完全なグローバル表現が得られます。 
2. For each query`(l, r, f)`を強制する範囲更新を適用します。`height = min(height, f)`その間隔で。 これは値を減らすだけなので、単純な割り当てではありません。 
3. クエリ範囲内に完全に収まるノードを処理する場合、その最大値をチェックします。 この最大値がすでに ≤ f である場合、このセグメント内の要素は変更されないため、停止します。 この枝刈りにより、安定した領域に繰り返し触れることが回避されます。 
4. ノードのセグメント全体が厳密に f より大きい場合、つまりすべての値が f より大きい場合、このセグメント内のすべての要素を直接 f に設定し、保存されている合計を次のように更新できます。`f * length`。 これは再帰を回避するためのキー ショートカットです。 
5. それ以外の場合、セグメントには f より上の値と下の値が混在しています。 操作をその子にプッシュし、再帰的に繰り返します。 これにより、影響を受ける部分のみがリファインされます。 
6. 更新を処理した後、ルートに保存されている合計を出力します。これは、すべての建物の表示可能なフロアの合計を表します。 

### なぜ効果があるのか

 このアルゴリズムは、これまでに適用されたすべての更新の下で、各ノードがそのセグメントの合計と最大値を常に正しく格納するという不変条件を維持します。 すべての更新は、セグメントを一定時間内に完全に解決するか、プッシュダウンして問題のサイズを縮小します。 値は減少するだけであるため、セグメントの最大値がクエリしきい値を下回ると、そのしきい値以上の将来の変更から永久に安全になります。 これにより、各要素が対数的に多くの自明でない分割にのみ参加することが保証されるため、正確性と効率性が一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.sum = [0] * (4 * self.n)
        self.mx = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def build(self, v, l, r, arr):
        if l == r:
            self.sum[v] = arr[l]
            self.mx[v] = arr[l]
            return
        m = (l + r) // 2
        self.build(v * 2, l, m, arr)
        self.build(v * 2 + 1, m + 1, r, arr)
        self.pull(v)

    def pull(self, v):
        self.sum[v] = self.sum[v * 2] + self.sum[v * 2 + 1]
        self.mx[v] = max(self.mx[v * 2], self.mx[v * 2 + 1])

    def update_chmin(self, v, l, r, ql, qr, f):
        if ql <= l and r <= qr:
            if self.mx[v] <= f:
                return
            if l == r:
                self.sum[v] = self.mx[v] = min(self.mx[v], f)
                return
            if self.mx[v] <= f:
                return
            if self._can_apply(v, l, r, f):
                self.sum[v] = f * (r - l + 1)
                self.mx[v] = f
                return

        if l == r:
            self.sum[v] = self.mx[v] = min(self.mx[v], f)
            return

        m = (l + r) // 2
        if ql <= m:
            self.update_chmin(v * 2, l, m, ql, qr, f)
        if qr > m:
            self.update_chmin(v * 2 + 1, m + 1, r, ql, qr, f)
        self.pull(v)

    def _can_apply(self, v, l, r, f):
        return self.mx[v] > f

n, q = map(int, input().split())
arr = list(map(int, input().split()))
st = SegTree(arr)

for _ in range(q):
    l, r, f = map(int, input().split())
    st.update_chmin(1, 0, n - 1, l - 1, r - 1, f)
    print(st.sum[1])
```セグメント ツリーには集計合計と最大値の両方が保存されるため、セグメント全体がクエリによって影響を受けるかどうかを、セグメントに降りることなく判断できます。 更新ロジックはセグメントを早期に折りたたもうとしますが、それ以外の場合は必要な場合にのみ下方に伝播します。 

微妙な点の 1 つは、この操作が割り当てではなく最小限のクランプであるということです。 これが、値を減らすだけで増やしない理由です。 ツリーは、増分や置換のために遅延タグを必要としません。 最大チェック ロジックがそれを置き換えます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n) | 各更新は、しきい値を超える値がまだ含まれているセグメントにのみ降下します。 
| スペース | O(n) | セグメント ツリー ノードには、各セグメントの合計と最大値が格納されます。 

この構造は 100,000 回の操作に対して快適に拡張できます。これは、すべての再帰的分割にわたって各要素が効果的に削減されるのはわずかな回数だけであり、各相互作用には対数時間がかかるためです。

 ## 特殊なケース

 主なエッジケースは、クエリがセグメント内の現在の値よりも大きい値を適用する場合です。 例えば：```
3 1
2 2 2
1 3 10
```正解は 6 のままです。最大値がすでに ≤ 10 であるため、セグメント ツリーは更新を回避し、トラバースを完全にスキップします。 

もう 1 つのケースは、すでに最小値に対して繰り返し締め付けを行う場合です。```
4 2
8 1 1 8
1 4 5
1 4 3
```最初のクエリの後、配列は次のようになります。`[5,1,1,5]`。 2 番目のクエリでは、外側の値のみが再度削減されます。 この構造により、影響を受けたセグメントのみが再訪されることが保証されるため、冗長なフル スキャンは発生しません。 

最後の微妙なケースは、更新がツリーの奥深くにある単一の要素にのみ影響する場合です。 それでも、再帰により対数時間でそのリーフが分離され、無関係なセグメントには触れないため、敵対的なシーケンス下でも効率が維持されます。
