 ## 解決策
 ## 問題の理解

 一連の日数にわたって銀行口座をシミュレーションしています。 毎日は固定料金で始まります$p$ルーブルがアカウントに適用されます。 特定の日に、この請求が発生する前に、Arkady はアカウントにお金を入金します。 

タイムラインは厳密に 1 日目から 1 日目までの時系列です$m$。 最初の残高はゼロです。 毎日、入金日であれば残高が増えてから日払いとなります。$p$が差し引かれます。 この操作の後、残高がマイナスかどうかを確認します。 毎日のチャージ後、マイナス残高が何日で発生するかをカウントする必要があります。 

重要な観察は、このプロセスは純粋に累積的であるということです。つまり、その日の残高は$d$以前の預金と固定の減算のみに依存します。$p$1日あたり。 リセットや分岐動作はありません。 

制約があるため、単純なシミュレーションは不可能になります。 日数$m$と同じ大きさにすることができます$10^9$したがって、毎日繰り返すことは不可能です。 ただし、入金イベントの数は$n$せいぜい$10^5$、これは並べ替えや線形処理に十分な大きさです。 この間の非対称性は、$n$そして$m$は構造上の中心的なヒントです。実際にバランスが変わるのはわずか数日だけです。 

単純なアプローチでは、すべてをシミュレートしてしまいます。$m$日を維持し、ランニングバランスを維持します。 これは$O(m)$、次の場合はまったく不可能です。$m = 10^9$。 

もっと巧妙で素朴なアイデアは、入金日のみを処理し、その間に何か単純なことが起こると仮定することです。 これは失敗します。残高は毎日直線的に変化するため、入金のない日であっても残高は大幅に変化します。 

素朴な推論を打ち破るエッジケースには、次のようなものがあります。 

- デポジットがまったくない場合、残高は次のように減少します。$p$毎日なので、すべての日がマイナスです。 
- 終わり近くに単一の大きな預金: 初期の日はマイナスですが、後のものは回復する可能性があります。 
- 毎日の預金を一時的にキャンセルするデポジットにより、セグメント間で交互のサイン動作が発生します。 

これらの動作は、タイムラインを日ごとにシミュレートするのではなく、区分的線形関数として扱う必要があることを示しています。 

## アプローチ

 毎日シミュレーションする場合、バランス変数を維持し、1 から 2 までループします。$m$、発生時にデポジットを適用し、減算します。$p$毎回。 これは正しいですが、次の場合には遅すぎます。$m$最大で必要になるため、サイズは大きくなります。$10^9$繰り返し。 

重要な観察は、一定の線形減少を除いて、入金日の間隔内では何も変化しないことです。 間隔の開始時の残高がわかっている場合は、シミュレーションの代わりに算術推論を使用して、その間隔でマイナスの残高が生じる日数を計算できます。 

入金日を順番に処理し、連続する入金イベント間の各間隔をブロックとして扱います。 各ブロック内で、残高は次のように減少します。$p$1 日あたり、等差数列を形成します。 残高がいつゼロを下回るかを直接判断し、マイナスの日数をカウントすることができます。 

これにより、処理の問題が軽減されます$n + 1$代わりにセグメント$m$日々。

 ## アルゴリズムのチュートリアル

 現在の残高を追跡し、すべての入金イベントを日の昇順に繰り返します。 

1. 現在の残高を 0 に初期化し、前日ポインタを 1 に設定します。考え方としては、1 日目から次の入金日までの日範囲を処理するということです。 
2. 当日の各入金イベントについて$d$価値のあるもの$t$、最初に前のポインタから次の日までの日数を処理します。$d - 1$、入金が発生しない場所。 この間に残高は次のように減少します。$p$毎日。 

シミュレーションする代わりに、これを線形シーケンスとして扱います。つまり、現在の残高から開始して、$k$残高が残る日$balance - k \cdot p$。 これらの日数のうち、減算後にマイナス残高となる日数を決定します。 
3. 当日デポジットを適用$d$： 追加$t$残高を計算し、すぐに差し引きます$p$支払いは入金後に行われるため、その日限りです。 結果の残高がマイナスの場合は、答えを増分します。 
4. 前のポインタを次の場所に移動します。$d + 1$、その日から$d$完全に加工されています。 
5. すべての入金日を処理した後、最後の処理日から次の日までの残りのセグメントを処理します。$m$同じ算術ロジックを使用します。 

重要な詳細は、反復せずに、減少する算術シーケンス内でゼロ未満になる値の数を正確にカウントすることです。 

### なぜ効果があるのか

 入金間では、残高は固定ステップの単純な等差数列として変化します。$-p$。 このようなシーケンスには、しきい値の交差点が 1 つあります。つまり、一度負になると、永久に負のままになります。 この単調性により、残高がゼロを下回る最初のインデックスを見つけることで、マイナスの日数をカウントできるようになります。 各セグメントは独立しており完全に計算されるため、毎日が 1 回だけカウントされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def count_negative_days(n, p, m, events):
    ans = 0
    cur = 0
    prev_day = 1

    for d, t in events:
        # process days [prev_day, d-1]
        length = d - prev_day
        if length > 0:
            # balance starts at cur and decreases by p each day
            # find first k such that cur - k*p < 0
            if cur < 0:
                ans += length
            else:
                first_neg = cur // p + 1
                if first_neg < 1:
                    first_neg = 1
                if first_neg <= length:
                    ans += length - first_neg + 1

            cur -= length * p

        # process deposit day d
        cur += t
        cur -= p
        if cur < 0:
            ans += 1

        prev_day = d + 1

    # tail segment
    if prev_day <= m:
        length = m - prev_day + 1
        if cur < 0:
            ans += length
        else:
            first_neg = cur // p + 1
            if first_neg <= length:
                ans += length - first_neg + 1

    return ans

def main():
    n, p, m = map(int, input().split())
    events = [tuple(map(int, input().split())) for _ in range(n)]
    print(count_negative_days(n, p, m, events))

if __name__ == "__main__":
    main()
```この実装では、入金と入金の間に各セグメントが処理され、数日にわたる反復処理が回避されます。 中心的な考え方は、セグメントの開始残高がわかったら、それを毎日正確に減らすということです。$p$, したがって、整数除算を使用して負になる境界を計算できます。 

唯一の微妙な部分は、プラスの開始残高から最初のマイナスの日への移行を正しく処理することです。 表現`cur // p + 1`セグメント内で 1 から始まるインデックスを想定して、繰り返された減算がゼロを下回る最初のインデックスを返します。

 ## 特殊なケース

 エッジケースの 1 つは、デポジットがない場合です。 その場合の残高は単純に$-p, -2p, \dots$, なので毎日がマイナスです。 アルゴリズムは、イベント ループをスキップし、残高ゼロから開始して最後の末尾セグメントを処理し、すべてのセグメントを正しくカウントすることでこれを処理します。$m$日々。 

もう 1 つのケースは、将来のマイナス残高を防ぐための多額の預金です。 セグメント ロジックは、開始残高が負ではなく、最初の負のインデックスがセグメントの長さを超えていることを検出するため、ゼロ日が寄与します。 

最後の微妙なケースは、最終日に入金が発生する場合です。 アルゴリズムはその日を通常どおり処理し、残りのセグメントは空になり、長さ 0 の間隔によるオフバイ 1 エラーが回避されます。
