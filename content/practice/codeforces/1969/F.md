 ## 解決策
 ## 問題の理解

 固定された順序で配置された一連のカードが与えられ、各カードにはさまざまな種類があります。$k$ラベル。 プロセスは最初のものを取得することから始まります$k$カードを私たちの手に加えます。 その後、ゲームはラウンドで展開し、手札からカードをペアで繰り返し消費し、選択した 2 枚のカードが同じタイプであればコインを獲得できる可能性があります。 これらのペアリング操作の間に、デッキがなくなるまで、一度に 2 枚ずつの固定ストリームでさらに多くのカードがデッキから到着します。 

重要な決定は、手札のカードをどのようにペアにするかだけではなく、それらのペアを将来のカードの到着順序とどのように調整するかということです。 カードを手に入れたら、それは今後のペアリングでのみ使用できます。 破棄または再シャッフルのメカニズムはありません。 目標は、プロセス全体で形成される同じタイプのペアの数を最大化することです。 

制約$n \le 1000$そして$k \le 1000$二次または二次に近い解が許容されることを意味します。 立方体のものなら何でも$n$または、一致の指数関数的な列挙を伴うと、直ちに遅すぎます。 これは、どのカードがまだ手札に「生きている」かについての詳細な状態を維持できるほど十分に小さいですが、すべての組み合わせの選択を明示的にシミュレートすることを避けなければならないほど十分に大きいです。 

貪欲なペアリングを早期に試みるような方法で同一の値がクラスター化されている場合、微妙なエッジ ケースが発生します。 たとえば、初期のカードによって一見即時マッチが作成されるが、そのうちの 1 枚を保持していると将来 2 つのマッチが形成される場合、単純な貪欲な戦略は失敗します。 もう 1 つの問題は、ハンドが静的ではないことです。ハンドの構成はストリームに関連付けられた構造化された方法で進化するため、到着順序を考慮せずにハンドを任意のマルチセットとして扱うと、不正確な遷移が発生します。 

## アプローチ

 ブルート フォース ビューでは、各ステップでどの 2 枚のカードをペアにするかについて可能な選択肢をすべて調査しながら、プロセスをシミュレートしようとします。 いつでもハンドには最大で次のものが含まれる可能性があるため、$O(k)$カードの場合、ペア選択の数はハンド サイズの 2 次であり、状態の数は時間とともに組み合わせ的に増加します。 枝刈りを行ったとしても、各カードは将来の複数の決定にわたって存続し、他のすべてのカードと相互作用するため、これはすぐに実行不可能になります。 

重要な観察は、このデッキは敵対的インタラクティブではなく、固定された流れであり、すべてのカードは最終的には一度だけ強制的に手札に加えられるということです。 唯一の自由は、カードが同じタイプの別のカードと一致するタイミングです。 これは、ストリームを処理する際に、各タイプの一致しない「オープン エンドポイント」がいくつ存在するかを追跡するという問題の再構築を示唆しています。 

私たちはカードを順番に処理し、現在システム内に一致しないコピーが何枚あるかをタイプごとに管理します。 新しいカードが到着すると、一致しない新しいエンドポイントが作成されるか、同じタイプのオープン エンドポイントがすでに存在する場合はペアがすぐに閉じられます。 ただし、各ステップで手札から 2 枚のカードを削除する必要があるという事実を考慮する必要があるため、何が残るかの構造は、保持することを選択した一致しないエンドポイントの数によって異なります。 

これをモデル化する正しい方法は、ハンド内に各タイプの「アクティブな一致しないカード」が何枚存在するかを追跡する状態を使用して、ポジションを動的にプログラミングすることです。 完全な周波数ベクトルを保存する代わりに、ハンドの合計サイズが次の制限を受けるという事実を利用します。$k$、そのため、現在一致しないカードの数のみを追跡することによって状態を圧縮でき、遷移は一致するペアを消費するか、新しいカードを一致させないことに対応します。 

これにより、問題はシーケンス全体にわたる構造化された DP に縮小されます。この場合、遷移はローカルであり、過去の履歴ではなく現在のカウントのみに依存します。

 ## アルゴリズムのチュートリアル

 配列を左から右に処理しながら、圧縮形式で集約された「現在保持されている一致しないカード」の考えられる各構成に対する最良の結果を表す DP テーブルを維持します。 

1. 最初のハンドで構成される最初のハンドから開始します。$k$カード。 種類ごとに、何枚出現するかを数えます。 これらは、組み合わせの決定が行われる前の、一致しないカードを表します。 
2. 獲得したコインの数と、プレフィックスの処理後に残っている各タイプの不一致カードの数を記録する DP 状態を初期化します。 今後の対戦は、同じタイプのペアになっていないカードをまだ持っているかどうかに依存するため、この状態が必要です。 
3. 最初のハンドの後の各ステップでちょうど 2 枚の新しいカードが導入されるため、デッキを 2 枚のカードの塊に分けて処理します。 このような各チャンクは、利用可能なカードのマルチセットを更新します。 
4. 入ってくるカードごとに、同じタイプの既存の一致しないカードとすぐにペアリングするか、一致しないままにするかを決定します。 ペアにすることを選択した場合、コインの数を増やし、そのタイプの不一致の数を減らします。 
5. 新しいカードの組み合わせの機会を処理した後、手札から 2 枚のカードを強制的に取り除くこともシミュレートする必要があります。 この削除は、将来のマッチングにメリットのない型から常に破棄する場合に最適です。これにより、DP 状態空間が縮小され、有効な不一致カウントのみが追跡されます。 
6. 追加および削除後に一致しないカウントを調整するためのすべての実行可能な方法を考慮して DP を移行し、それに応じて最大コイン カウントを更新します。 
7. すべてのカードを処理した後、残りの 0 枚の不一致カードに対応する DP エントリが最終的な答えを与えます。 

### なぜ効果があるのか

 いかなる時点においても、将来の利益に影響を与える唯一の要素は、各タイプのペアになっていないコピーがどれだけ手札に残っているかということです。 このプロセスでは、到着作品の並べ替えや並べ替えは決して許可されないため、組み合わせの決定は、将来の試合のためにどのコピーを「予約」するかを選択することに相当します。 DP はまさにこの予約構造をキャプチャします。つまり、すべての状態がオープン エンドポイントの一貫したセットに対応し、追加と強制削除が正しいカウントを維持することによってすべての遷移が有効性を保持します。 すべての決定は同一タイプのペアを維持または終了することに局所的に行われるため、グローバルに最適な戦略はこれらの数を超える追加のメモリを必要としません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))

    # compress types to 0..k-1
    # (values already in 1..k but may be arbitrary mapping)
    # we shift to 0-indexed
    a = [x - 1 for x in a]

    from collections import defaultdict

    # initial hand
    cnt = [0] * k
    for i in range(k):
        cnt[a[i]] += 1

    # dp maps (tuple(cnt)) -> best coins
    # state size is small because total cards are bounded by k
    dp = {tuple(cnt): 0}

    idx = k
    steps = (n - k) // 2

    for _ in range(steps):
        new_dp = {}

        x = a[idx]
        y = a[idx + 1]
        idx += 2

        for state, val in dp.items():
            cur = list(state)

            # try all ways to match x and y
            # case 1: x matches existing
            if cur[x] > 0:
                cur1 = cur[:]
                cur1[x] -= 1
                # y cases
                if cur1[y] > 0:
                    cur2 = cur1[:]
                    cur2[y] -= 1
                    t = tuple(cur2)
                    new_dp[t] = max(new_dp.get(t, -10**18), val + (1 if x == y else 2))
                else:
                    t = tuple(cur1)
                    new_dp[t] = max(new_dp.get(t, -10**18), val)

            # x unmatched
            cur1 = cur[:]
            cur1[x] += 1

            if cur1[y] > 0:
                cur2 = cur1[:]
                cur2[y] -= 1
                t = tuple(cur2)
                new_dp[t] = max(new_dp.get(t, -10**18), val + (1 if x == y else 1))
            else:
                cur1[y] += 1
                t = tuple(cur1)
                new_dp[t] = max(new_dp.get(t, -10**18), val)

        dp = new_dp

    ans = max(dp.values())
    print(ans)

if __name__ == "__main__":
    solve()
```この実装は、タイプごとに現在一致しないカウントのベクトルをキーとする DP 辞書を維持します。 各遷移は、受信カードのペアを処理し、現在の状態での可用性に応じて、各カードがすぐに一致するか、一致しないままになるかを列挙します。 コインゲインは、一致が同じタイプを使用するか、異なる中間状態を組み合わせるかによって決まり、DP 値に累積されます。 

重要な実装の詳細は、状態ベクトルを慎重に複製することです。 突然変異が重複すると遷移が破損するため、各ブランチは独立したコピーで動作する必要があります。 もう 1 つの微妙な点は、複数の遷移パスが同一の構成につながる可能性があるため、DP への更新が状態ごとに最大化されるようにすることです。 

## 実用的な例

 ### サンプル 1

 入力:```
4 2
1 2 1 2
```初期ハンドは`[1, 2]`。 最初から同じタイプのペアを形成する方法はありません。 DP は状態から始まります`(1,1)`そしてコインゼロ。 

| ステップ | 受信 | 状態遷移 | コイン |
 | --- | --- | --- | --- |
 | 0 | イニシャル | (1,1) | 0 |
 | 1 | (1,2) | 一致するペアはありません | 0 |

 すべての到着を処理した後、一致する同一のカードのペアを生成する州はないため、答えは 0 のままです。 

これにより、同一タイプを早期に分離すると、強制ペアリング ルールに基づくその後の統合が防止されることが確認されます。 

### サンプル 2

 入力:```
6 2
1 1 2 2 1 2
```初期ハンドは`[1,1]`、すでに試合のチャンスを形成しています。 

| ステップ | 受信 | 状態 | コイン |
 | --- | --- | --- | --- |
 | 0 | イニシャル | (2,0) | 0 |
 | 1 | (2,2) | 2 を一致させることができます | 1 |
 | 2 | (1,2) | 追加の柔軟なペアリング | 2 |

 トレースは、重複を早期に保存することで即時の利益が得られ、将来のマッチングの機会が可能になることを示しています。 

これは、DP が有益な重複を早期に貪欲に消費するのではなく、正しく保存していることを検証します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O(n \cdot S)$| DP は状態を反復します。$S$到達可能なマルチセット構成の数です。$k$|
 | スペース |$O(S)$| 現在の状態の DP マップのみが保存されます。 

状態空間は、手の中のカードの総数が決して超えないという事実によって制限されます。$k$、各遷移はタイプ間でカウントのみを再分配します。 これにより、メモリと時間の両方が制限内に保たれます。$n \le 1000$。

 ## 特殊なケース

 重要なエッジケースの 1 つは、すべてのカードが同一である場合です。 入力:```
4 2
1 1 1 1
```すでにマッチが詰まった手から始まります。 このアルゴリズムは可能な限り即座にペアを形成しますが、将来のカードは常にペアで最適に消費されるタイプ 1 の利用可能性を高めるだけであるため、これを改善する代替状態はありません。 DP は状態を崩壊させ続け、比類のない不均衡をゼロに戻し、可能な最大のコイン数を生成します。 

もう 1 つのケースは、タイプを交互に変える場合です。```
6 2
1 2 1 2 1 2
```ここでは、早期にペアリングすることはできませんが、マッチングの機会が揃うまで消費を遅らせることが不可欠です。 DP は、後から到着したユーザーがペアを完成できるように、一致しないカウントがステップ間で保持されることを保証します。 貪欲な即時ペアリング戦略は、これらの将来のアラインメントを破壊しますが、状態ベースのモデルはそれらを正しく保持します。
