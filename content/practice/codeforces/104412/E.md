 ## 解決策
 ## 問題の理解

 私たちには一連の仕事が与えられており、それぞれの仕事は、決定的なカレンダー ルールに従って、一定の金額を繰り返し支払われます。 各ジョブは有効な日付に開始され、特定の日付に終了することも無期限に継続することもでき、ジョブの種類に応じて一連の支払い日が生成されます。 

日付間隔で構成されるクエリの場合$[L, R]$, 支払日がその期間内にあるすべてのジョブから受け取った合計金額を計算する必要があります。ただし、ジョブの終了日 (終了日がある場合) とそれ以前に支払いが行われた場合にのみ支払いが寄与するという重要なルールが適用されます。 

したがって、中心的な構造は「ジョブの間隔」ではなく、「生成されたイベントの間隔」です。 各ジョブは日付の付いた一連の支払いに拡張され、クエリはこれらのイベントのサブセットの合計を要求します。 

制約があるため、そのようなイベントがどれだけ存在し得るかについて、慎重に考える必要があります。 多くてもあります$10^3$ジョブは複数ありますが、各ジョブは 2000 年から 9999 年までの数年にわたる場合があります。毎週のジョブでは年間約 50 件の支払いが発生し、隔週のジョブでは約 24 件、月次のジョブでは約 12 件の支払いが発生します。これは、何千年にもわたって依然として、やみくもに拡張すると非常に多くの潜在的な支払いイベントを引き起こす可能性があります。 一方で、$10^5$したがって、クエリごとに回答を最初から再計算することも実行できません。 

主な微妙な点は、支払いが任意の順序ではないことです。各タイプは厳密なカレンダー ルールに従います。 毎週の支払いは常に金曜日に発生し、隔週の支払いは毎月の固定日 (15 日と最終日) に発生し、月次の支払いは毎月の末日に発生します。 この規則性により、イベントを効率的に列挙したり構造化したりできるようになります。 

間違いやすいいくつかの特殊なケースがあります。 

問題の 1 つは、終了日のないジョブです。 これらは、無期限ではなく、最大クエリ日付範囲まで支払いを生成し続ける必要があります。 

もう 1 つの問題は、境界の包含です。 支払いがジョブの終了日に発生する場合は、それを含める必要がありますが、それ以降の支払いは除外されます。 終了日よりも前に生成を厳密に停止する単純な実装では、有効な支払いが失われます。 

3 番目の問題は、カレンダーの正確さです。 うるう年は 2 月の長さに影響し、隔週および月次のスケジュールでは月末の計算が必要です。 日付の進み方に小さな間違いがあると、将来のすべての支払いが暗黙のうちに変更され、回答の大部分が破損する可能性があります。 

最後に、開始日の調整が重要です。 ジョブは、有効なアンカー日 (タイプに応じて月曜日、1 日/16 日、または毎月 1 日) にのみ開始できます。 正しく調整できない場合、生成されたすべての支払いシーケンスがシフトされます。 

## アプローチ

 強引なアイデアは簡単です。すべてのジョブをそのすべての支払日まで拡張し、各支払をペアとして保存します。$(date, amount)$、各クエリについて、クエリ間隔内にあるすべての支払いを合計します。 

これが機能するのは、各支払いが独立しており、加算的に寄与するためです。 すべてのイベントが生成されると、その正しさはすぐにわかります。 

問題は規模だ。 毎週の仕事をフルタイムの範囲に拡大すると、それぞれの仕事だけで数十万の支払いが発生する可能性があります。 まで$10^3$ジョブの場合、これは数億のイベントに達する可能性があり、時間とメモリの両方で大きすぎます。 

重要な観察は、すべての支払いがイベントのグローバル リストとして表現されると、クエリは並べ替えられた配列に対する単純な範囲合計クエリになるということです。 これにより、問題は繰り返しの再計算から、1 回の前処理と効率的なクエリへの応答へと変わります。 

したがって、最適化されたアプローチは、すべての支払いイベントを一度生成し、それらを次のように保存することです。$(date\_index, amount)$、日付で並べ替え、金額に対するプレフィックスの合計を構築し、二分検索を使用して各クエリに答えて関連するセグメントを分離します。 

重要な改善点は、すべての負荷の高いカレンダー ロジックを単一の前処理フェーズに移動することで、クエリ時間がイベント数で線形ではなく対数になるようになりました。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (すべてのジョブ/イベントのクエリ スキャンごと) |$O(NQ \cdot T)$|$O(1)$| 遅すぎる |
 | イベント生成 + ソート + プレフィックス合計 |$O(E \log E + Q \log E)$|$O(E)$| 承認済み |

 ここ$E$生成された支払いイベントの総数です。 

## アルゴリズムのチュートリアル

 まず、すべての日付を、固定原点 (2000 年 1 月 1 日) からの日数を表す単一の整数に変換します。 これにより、日付を比較し、二分探索を効率的に適用できるようになります。 

### ステップ

 1. カレンダー対応の変換関数を使用して、すべての入力日付を整数の日付インデックスに変換します。 これにより、日/月/年のロジックを繰り返し処理することなく、算術演算と比較を実行できるようになります。 
2. ジョブごとに、そのアクティブな間隔を決定します。 終了日が欠落している場合、目的のためにはそれを非常に大きな日付として扱い、実質的には無限大とみなします。 その後、クエリの評価中に後でクランプします。 
3. ジョブ タイプごとに、アクティブな間隔内で有効な支払い日をすべて生成します。 

毎週のジョブの場合、開始日以降の最初の金曜日を特定し、7 日を繰り返し追加します。 

隔週のジョブの場合、毎月 15 日と末日が生成され、ジョブの範囲内に含まれるジョブが含まれます。 

月次ジョブの場合、間隔内の各月の最終日が生成されます。 

毎日反復しない理由は、任意の日付ではなく、構造化された支払いアンカーのみを考慮しているためです。 
4. 生成された支払日ごとに記録を保存します。$(day\_index, amount)$。 これにより、すべてのジョブが 1 つのイベント リストにフラット化されます。 
5. イベントリストを日のインデックスで並べ替えます。 この順序により、スキャンの代わりに二分検索を使用して範囲クエリに答えることができます。 
6. ソートされたイベント量に対してプレフィックス合計配列を構築します。 これにより、任意の範囲が 2 つのプレフィックス値の差に変換されます。 
7. 各クエリについて$[L, R]$、両方のエンドポイントを日のインデックスに変換します。 二分探索を使用して、L より前ではない最初のイベントと R より後ではない最後のイベントを検索し、プレフィックスの差を使用して合計を計算します。 

### なぜ効果があるのか

 重要な不変条件は、すべての支払いがグローバル イベント リスト内で 1 回だけ表され、リストが時間順に並べ替えられていることです。 プレフィックス合計は連続セグメントにわたる加算構造を保持するため、クエリ間隔はこの並べ替えられたリスト内の連続する部分配列に対応します。 二分探索はその部分配列の境界を正確に識別し、その部分配列にわたるプレフィックスの合計は区間内の合計収益と等しくなります。 

生成では各ジョブの有効期間が尊重され、並べ替えではメンバーシップは変更されず、順序のみが変更されるため、支払いが二重にカウントされたり省略されたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from bisect import bisect_left, bisect_right

# --- date utilities ---
def is_leap(y):
    return (y % 400 == 0) or (y % 4 == 0 and y % 100 != 0)

def days_in_month(y, m):
    md = [31, 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31]
    if m == 2 and is_leap(y):
        return 29
    return md[m - 1]

# convert date to day index from 01/01/2000
def to_day(d, m, y):
    days = 0
    for yy in range(2000, y):
        days += 366 if is_leap(yy) else 365
    for mm in range(1, m):
        days += days_in_month(y, mm)
    days += d - 1
    return days

# weekday: 01/01/2000 is Saturday (index 5 if Monday=0)
def weekday_of_day(day):
    return (5 + day) % 7

def parse_date(s):
    d, m, y = map(int, s.split('/'))
    return to_day(d, m, y)

events = []

n, q = map(int, input().split())

for _ in range(n):
    parts = input().split()
    amount = int(parts[0])
    start = parse_date(parts[1])
    end_raw = parts[2]
    typ = parts[3]

    if end_raw == "None":
        end = float('inf')
    else:
        end = parse_date(end_raw)

    if typ == "weekly":
        d = start
        while d <= end:
            if weekday_of_day(d) == 4:  # Friday
                events.append((d, amount))
            d += 1

    elif typ == "monthly":
        y = 2000
        m = 1
        cur = 0
        while cur < start:
            cur += days_in_month(y, m)
            m += 1
            if m == 13:
                m = 1
                y += 1

        # move to month containing start
        y = 2000
        m = 1
        cur = 0
        while cur + days_in_month(y, m) <= start:
            cur += days_in_month(y, m)
            m += 1
            if m == 13:
                m = 1
                y += 1

        while True:
            last_day = cur + days_in_month(y, m) - 1
            if last_day > end:
                break
            if last_day >= start:
                events.append((last_day, amount))

            cur += days_in_month(y, m)
            m += 1
            if m == 13:
                m = 1
                y += 1

    else:  # bi-weekly
        y = 2000
        m = 1
        cur = 0

        while True:
            dim = days_in_month(y, m)
            d15 = cur + 14
            dlast = cur + dim - 1

            if d15 >= start and d15 <= end:
                events.append((d15, amount))
            if dlast >= start and dlast <= end:
                events.append((dlast, amount))

            cur += dim
            m += 1
            if m == 13:
                m = 1
                y += 1

            if cur > end:
                break

events.sort()
pref = [0]
for _, v in events:
    pref.append(pref[-1] + v)

dates = [d for d, _ in events]

def query(l, r):
    L = parse_date(l)
    R = parse_date(r)
    i = bisect_left(dates, L)
    j = bisect_right(dates, R)
    return pref[j] - pref[i]

for _ in range(q):
    l, r = input().split()
    print(query(l, r))
```この実装は、すべての操作を並べ替えとプレフィックスの合計に減らすために、すべてを線形タイムラインに変換することに依存しています。 主な注意点は、正しい日付のインデックス付けと、開始日または終了日の正確な支払いが境界条件に含まれていることを確認することです。 

毎週のジェネレーターは金曜日の直接スキャンを使用します。 これは単純ですが、固定原点からの正確な曜日の計算に依存します。 隔週および月次のジェネレーターは、1 日ごとの反復ではなく月境界の演算に依存しているため、イベント生成が実現可能になります。 

## 実用的な例

 イベント生成を説明するために、いくつかのジョブと 1 つのクエリを含む単純化されたシナリオを考えてみましょう。

このトレースは、カレンダー ロジックのすべての複雑さが前処理に分離され、クエリがジョブ構造から独立していることを示しています。

 ## 特殊なケース

 終了日のないジョブは、最大のクエリ範囲まで支払いを生成し続ける必要があります。 実装では、これは末尾を無限大として扱い、その後バイナリ検索中にクエリ境界によってフィルタリングすることで処理され、無限生成が発生しないようにします。 

ジョブの終了日に正確に発生する支払いを含める必要があります。 これは世代チェックにより保証されます。`<= end`、 ない`< end`したがって、境界イベントは保存されます。 

うるう年は月次生成、特に 2 月に影響します。 の`days_in_month`この機能により、正しい月の長さが保証されるため、閏年をまたいででも月の末日の支払いが正確に保たれ、長期にわたるスケジュールのずれを防ぎます。
