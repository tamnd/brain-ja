 ## 解決策
 ## 問題の理解

 私たちには、根を張ったツリーを形成する会社階層が与えられています。 各従業員には、直属の上司が 1 人しかいません。ただし、最上位のマネージャーには上司がいません。 これは、エッジが従業員からその上司を指し、すべてのノードが最終的にルートにつながる有向ツリーと考えることができます。 

各従業員は、単なる整数のラベルである「グループ」にも属します。 システムのアップグレード後、従業員は自分のグループだけでなく、ルートに至るまでのスーパーバイザーのチェーンにあるすべてのグループに対して責任があるとみなされます。 

このタスクは、従業員ごとに、その従業員からツリーのルートまでのパス上に表示される個別のグループ ラベルの数を計算することです。 

したがって、問題は次のようになります。ルート化されたツリー内の各ノードについて、ルートへのパスに沿ったノード ラベルのセット内の固有の値の数を数えます。 

制約$N \le 10^6$本質的に線形または線形に近い時間を目指すことを強いられます。 繰り返し上向きに歩いてノードごとの情報を再計算するアプローチは、次のように劣化します。$O(N^2)$鎖状のツリーでは、これは受け入れられません。 平$O(N \log N)$この規模では一定の要素が大きいため、メソッドは慎重に設計する必要があります。 

微妙なエッジ ケースは、すべてのノードが一意のグループを持つ深いチェーンです。 その場合、ノードの答えは$i$は単にその深さであり、ノードごとのカウントを再開するソリューションはタイムアウトになります。 

もう 1 つのエッジ ケースは、すべてのノードが同じグループを共有する場合です。 すべてのノードの正解は 1 ですが、単純なマージ構造では、重複が慎重に処理されないとカウントが大きくなりすぎる可能性があります。 

## アプローチ

 ブルートフォースアプローチは簡単です。 各従業員について、スーパーバイザ チェーンをルートまでたどり、すべてのグループ ID を 1 つのセットに収集し、そのサイズを返します。 これは問題の定義に直接従うため、正しいです。つまり、監視パスに沿って表示されるすべてのグループを明示的に収集します。 

ただし、このアプローチは遅すぎます。 最悪の場合、ツリーはある長さの単一のチェーンになります。$N$。 各ノードについて、以下までトラバースします。$O(N)$祖先と挿入コストを設定する$O(1)$平均的、与える$O(N^2)$トータルオペレーション。 と$N = 10^6$、これは限界をはるかに超えています。 

重要な観察は、ルート パスに沿ってプレフィックスのような情報を繰り返しカウントしていることです。 各ノードの答えは、ルートからそのノードまでのパス上でこれまでに確認されたグループ値のセットにのみ依存します。 ルートからリーフへの走査順序でノードを処理すると、現在のパスを表すグローバル構造を維持できます。 

難しいのは、一意性の処理です。現在のパス上にグループがすでに存在するかどうかを知る必要があります。 これは、アクティブな DFS パス上のグループの頻度カウントを維持することを示唆しています。 ノードに入るときに、そのグループを追加します。 離れるときは取り外します。 パス上の個別のグループの数は、単に正の頻度を持つキーの数です。 

これにより、問題は古典的な「ツリー上の DSU / パス状態のある DFS」パターンに変わりますが、注意深い周波数追跡が必要になります。 インクリメンタルな状態を維持することで再計算を回避します。 

課題は、$N$は大きいため、再帰の深さとオーバーヘッドを考慮する必要があります。 多くの場合、反復 DFS の方が安全ですが、PyPy では再帰的 DFS を使用することも、慎重に制御すれば再帰制限を増やすこともできます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (ノードごとにルートへのウォーク) | O(N²) | O(1) おまけ | 遅すぎる |
 | パス上の周波数マップを使用した DFS | O(N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 ## アルゴリズムのチュートリアル

 1. スーパーバイザ ポインタをツリー構造に反転して、子から親への関係から隣接リストを構築します。 これにより、ルートから上方向ではなく下方向へのトラバースが可能になります。これは、パス情報を効率的に再利用するために必要です。 
2. スーパーバイザ 0 を持つルート ノードを特定します。これは、すべてのノードが最終的にそれに接続するため、トラバーサルの唯一の開始点です。 
3. ルートから開始して深さ優先トラバーサルを実行し、2 つの構造を維持します。1 つは現在のルートからノードへのパス上に各グループが出現する回数を格納する頻度辞書、もう 1 つは現在アクティブな個別のグループの数を示すカウンターです。 
4. ノードに入るとき、そのグループの頻度を増やします。 この頻度が 1 になる場合、このグループが現在のパスに新たに導入されたことを意味するため、個別のグループ カウンタをインクリメントします。 
5. 現在の個別グループ カウンタをこのノードの応答として保存します。これは、ルート パス上の固有グループの数を正確に表すためです。 
6. すべての子に再帰し、更新された状態を下方向に伝播します。 
7. すべての子を終了したら、現在のノードのグループの頻度を減らしてバックトラックします。 その頻度が 0 に低下すると、そのグループはアクティブ パスに存在しなくなるため、個別カウンターをデクリメントします。 

これが機能する理由は、DFS 中のどの時点でも、維持される状態が現在のルートからノードへのパスに沿ったグループのマルチセットを正確に表すためです。 この走査の一環としてすべてのノードが 1 回だけ訪問されるため、各ノードの応答はパス状態の一貫したスナップショットを使用して計算されます。 

## Python ソリューション```python
import sys
sys.setrecursionlimit(10**7)
input = sys.stdin.readline

def solve():
    n = int(input())
    parent = list(map(int, input().split()))
    group = list(map(int, input().split()))

    children = [[] for _ in range(n + 1)]
    root = -1

    for i in range(1, n + 1):
        p = parent[i - 1]
        if p == 0:
            root = i
        else:
            children[p].append(i)

    ans = [0] * (n + 1)
    freq = {}
    distinct = 0

    def dfs(u):
        nonlocal distinct

        g = group[u - 1]
        freq[g] = freq.get(g, 0) + 1
        if freq[g] == 1:
            distinct += 1

        ans[u] = distinct

        for v in children[u]:
            dfs(v)

        freq[g] -= 1
        if freq[g] == 0:
            distinct -= 1

    dfs(root)

    print(*ans[1:])

if __name__ == "__main__":
    solve()
```この解決策は、スーパーバイザ ポインタを子隣接リストに反転することから始まります。 これが必要なのは、自然入力では親ポインターが記述されていますが、DFS 状態はルートからリーフまで自然に維持されるためです。 

の`freq`辞書は、現在の再帰スタックに沿って各グループが何回出現するかを追跡します。 の`distinct`変数を使用すると、辞書サイズの再計算が回避されます。再計算を行わないと、大規模な場合に遅すぎる可能性があります。 段階的に更新することが重要です。 

後戻りのステップは不可欠です。 再帰から戻った後にグループを削除しないと、ブランチ間で状態がリークし、グループが誤ってカウントされすぎます。

 ## 特殊なケース

 シングルノード企業は、DFS の前にアルゴリズムがルート状態を正しく初期化するかどうかを公開します。 走査はノード 1 から始まり、そのグループを追加し、再帰の問題なく即座に回答 1 を記録します。 

均一グループ ツリーは、周波数追跡によって過剰カウントが回避されるかどうかをテストします。 すべてのノードは同じグループを繰り返し追加しますが、個別のカウンターはルートで 1 回だけ増加し、再度増加することはなく、一貫した 1 が生成されます。 

グループ値が繰り返される歪んだツリーにより、バックトラッキングが正しく実装されることが保証されます。 ブランチから戻るときに、頻度を減らさないと、グループが無関係なサブツリーに誤って伝播され、回答が膨らむ可能性があります。 DFS 削除ステップでは、各サブツリーがそれ自体のアクティブ パス状態のみを認識することが保証されます。
