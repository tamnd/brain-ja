 ## 解決策
 ## 問題の理解

 それぞれの長さが最大 8 の、短い小文字の文字列のコレクションが与えられます。リスト内のすべての文字列について、同じリストから 2 つの文字列を取得し、それらを順番に連結することによってその文字列を形成できるかどうかを判断する必要があります。 選択した 2 つの文字列は同じ要素であってもよく、別個のインデックスを使用する必要はありません。 

したがって、各文字列に対して$s_i$、基本的に、プレフィックスがセット内の何らかの文字列であり、サフィックスもセット内の何らかの文字列であるような分割ポイントが存在するかどうかを尋ねています。 

ここでは制約構造が非常に重要です。 すべてのテスト ケースにわたる文字列の合計数が最大であっても、$10^5$、それぞれの個々の文字列は非常に短く、最大長は 8 です。これは、すべての部分文字列またはすべての分割を列挙するなど、文字列の長さに大きく依存するアプローチは、文字列ごとに最大 7 つの分割位置があるため安全であることを直ちに示唆します。 

ただし、クエリごとに文字列のすべてのペアを試す単純なアプローチでは、やはり時間がかかりすぎます。 すべてをチェックしようとすると、$s_i$すべてのペアに対して$(s_j, s_k)$、つまり$O(n^3)$文字列の連結チェックは最悪の場合に行われますが、これは実行不可能です。$10^5$。 

注文を考えるとき、さらに微妙な問題が生じます。 文字列は 2 つの小さな文字列から形成されるため、これらの小さな文字列は入力順序のどこにでも出現する可能性があり、必ずしも現在の文字列の前に現れるとは限りません。 これにより、完全なセットを明示的に考慮しない限り、貪欲な構築やプレフィックスのみの構築が排除されます。 

一般に、誤ったソリューションを破壊するエッジ ケースは、重複と自己連結によって発生します。 

一例としては次のようなケースが挙げられます。 

入力:```
1
3
a
aa
aaa
```正しい出力は次のとおりです。```
011
```なぜなら、「aa」=「a」+「a」、および「aaa」=「aa」+「a」だからです。 

バグのあるアプローチは、少なくとも 1 つの部分が入力順序の前に出現する必要があると想定している場合、または同じ文字列を 2 回使用することを禁止している場合、失敗する可能性があります。 

もう 1 つの微妙なケースは、複数の分解が存在するが、有効である必要があるのは 1 つだけである場合です。 たとえば、「abc」は「a」+「bc」または「ab」+「c」として分割できます。 必要なのは有効な分割が 1 つだけ存在することです。 

## アプローチ

 ブルートフォースのアイデアは簡単です: 各文字列に対して$s_i$、考えられるすべての分割位置を試してください。 分割位置ごとに、指定された文字列のセットにプレフィックスとサフィックスが存在するかどうかを確認します。 各文字列の長さは最大 8 であるため、文字列ごとに最大 7 つの分割があり、各メンバーシップ チェックはハッシュ セットを使用して定数時間で実行できます。 

これにより、問題はすでに約$O(n \cdot L)$、 どこ$L \le 8$、大まかに言うと$O(n)$。 ただし、メンバーシップを効率的に検証する方法と、部分的に構築された状態の誤った再利用を回避する方法に注意する必要があります。 

異なるが同等の視点により、構造がより明確になります。 文字列ごとに考えるのではなく、まずすべての文字列をハッシュ セットに挿入します。 次に、文字列ごとにすべての分割ポイントをテストし、両方の部分がセット内に存在するかどうかを確認します。 この問題では、2 つの部分が異なる文字列であることや、特定の順序で個別に出現する必要がないため、これが機能します。 

重要な洞察は、最大長が小さいため、複雑な前処理が完全に不要になるということです。 全体的な困難は、各文字列の考えられるすべてのパーティションをチェックし、セットのメンバーシップをテストすることになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (文字列のペア) |$O(n^2 \cdot L)$|$O(n)$| 遅すぎる |
 | 分割 + ハッシュ セット |$O(n \cdot L)$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべての入力文字列をハッシュ セットに保存し、任意の部分文字列に対するメンバーシップ クエリが平均して一定時間になるようにします。 このグローバル構造は、使用が許可されているすべての可能な構成要素を表します。 
2. 文字列ごとに$s$、すべての可能な分割位置を反復します。$i$1から$|s|-1$。 各スプリットは分割します$s$プレフィックスに$s[0:i]$と接尾語$s[i:]$。 すべての分割をチェックする理由は、有効な構造がこれらのパーティションの 1 つに正確に対応する必要があるためです。 
3. 分割ごとに、プレフィックスとサフィックスの両方がハッシュ セットに存在するかどうかを確認します。 両方が存在する場合、すぐに次のように結論付けることができます。$s$構築可能であるため、有効としてマークします。 
4. 分割によって 2 つの有効な辞書文字列が生成されない場合は、その文字列を無効としてマークします。 
5. これをテスト ケースごとに個別に繰り返し、ケースごとにハッシュ セットを再構築します。 

なぜ機能するのか: すべての有効な表現$s = a + b$の分割インデックスに一意に対応します$s$。 考えられるすべての分割インデックスを列挙するため、考えられるすべての分解をカバーします。 ハッシュ セットにより、順序や多重度の制約に関係なく、各候補部分が入力内のどこかに存在するかどうかが正しく検出されることが保証されます。 複製はセット表現 (または必要に応じて同等の周波数を意識した構造) に保存されるため、当然のことながら自己使用が許可されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        arr = [input().strip() for _ in range(n)]
        st = set(arr)

        res = []
        for s in arr:
            ok = False
            m = len(s)
            for i in range(1, m):
                if s[:i] in st and s[i:] in st:
                    ok = True
                    break
            res.append('1' if ok else '0')

        print(''.join(res))

if __name__ == "__main__":
    solve()
```このソリューションは、定数時間のメンバーシップ チェック用のセットを構築し、各文字列を個別に評価します。 内側のループは、簡単な空の分割を除くすべての分割ポイントを試行します。 有効な分解が見つかると、存在することだけが重要であるため、分解はショートします。 

文字列の長さが最大 ​​8 であるため、スライス操作は安全であり、各部分文字列の抽出は実際には定数時間です。 

よくある実装上の間違いは、テスト ケースごとにセットを再構築するのを忘れることです。これにより、以前のテスト ケースの文字列が結果に誤った影響を与える可能性があります。 もう 1 つの微妙な点は、同じ文字列の再利用を許可することです。 このセットはクエリごとの使用数を追跡しないため、これは自然に処理されます。

 ## 特殊なケース

 文字列「aa」のような自己連結の場合、アルゴリズムは位置 1 での分割をチェックします。接頭辞「a」と接尾辞「a」の両方がセット内で見つかるため、文字列は正しく有効とマークされます。 

「a」のみが存在し「b」が存在しない「ab」など、一部の部分が欠落している場合、各分割は少なくとも 1 つのメンバーシップ チェックに失敗するため、文字列は正しく無効とマークされます。 

「a」と「aa」による「aaa」のような連鎖構造の場合、プレフィックス「aa」とサフィックス「a」を使用して位置 2 での分割が成功し、アルゴリズムが反復構築や DP を必要とせずにマルチステップ合成を正しくサポートしていることがわかります。
