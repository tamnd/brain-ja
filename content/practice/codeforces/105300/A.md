 ## 解決策
 ## 問題の理解

 一列に配置された一連の茂みが与えられ、各茂みには最初に果物があります。 すべての低木には独自の成長時間があり、収穫後、再び熟すまでに一定のステップ数が必要です。 時間の経過とともに、茂みは個々のタイマーに基づいて再び独立して「準備が整います」。 

次に、一連のクエリが与えられます。 それぞれの質問は、特定の瞬間を考慮して、現在熟しているすべての茂みを調べた場合、それらはいくつ存在するのかを尋ねます。 

各クエリの出力は、ブッシュやそのアイデンティティのリストではなく、その時点で準備ができているブッシュの数の概要のみです。 

この問題の制約は十分に小さいため、$O(nq)$両方の次元が中程度であれば、シミュレーションはおそらく合格しますが、どちらかの次元が次の値に達すると、$10^5$、すべてのブッシュに対するクエリごとのスキャンが遅くなりすぎます。 これにより、鮮度を最初から再計算するのではなく、ある種の事前計算された状態、または段階的に更新された状態を維持する方向に進むことになります。 

微妙なエッジケースは、同一の成長時間から生じます。 複数の茂みが同じタイマーを持ち、異なる時点で収穫される場合、それらの準備は繰り返しサイクルで調整されます。 個々のタイマーを正しく更新せずに、「最後に確認された準備完了」だけを追跡する単純なシミュレーションでは、同期がずれてしまいます。 

すべてのクエリが同一である場合、別の問題が発生します。 たとえば、すべてのクエリが同じ位置について尋ねる場合、クエリ間で状態が変わらない場合でも、毎回最初から再計算すると冗長な作業が発生します。 

最後に、単一要素構成が重要です。1 つのブッシュでは、クエリ時に熟しているかどうかに応じて、答えは常に 1 か 0 のいずれかになります。インデックス付けが間違っていたり、初期化を忘れていたりすると、これらの些細なケースが壊れることがよくあります。 

## アプローチ

 ブルートフォースのアイデアは単純です。クエリごとに、すべてのブッシュを反復処理し、タイマーと最終更新時刻に従って現在熟しているかどうかを確認します。 これが機能するのは、各ブッシュの状態を個別に計算できるためです。 ただし、各クエリにはコストがかかります$O(n)$、それで、$q$クエリの総複雑さは次のようになります$O(nq)$。 両方のとき$n$そして$q$が大きい場合、これはおおよそ次のように縮退します。$10^{10}$これは通常の制限時間をはるかに超えています。 

重要な観察は、各ブッシュが独立して進化し、その時々の状態が変化することです。$t$等差数列の動作のみに依存します。つまり、一度収集されると、一定の間隔の後に再び準備が整います。 これは、段階的にシミュレーションする必要がないことを意味します。 代わりに、モジュラー演算を使用して準備状況を計算したり、次に利用可能な時間を追跡したりできます。 

各ブッシュに予測可能なスケジュールがあることがわかれば、問題は現在時刻と一致するスケジュールがいくつあるかをすぐにカウントできる構造を維持することになります。 クエリがオフラインまたは単調な場合は、時間ごとに並べ替えたりバケットを使用したりすることでイベントを集計できます。 クエリが任意の場合、「次に利用可能な時間」にわたるフェンウィック ツリーまたは頻度テーブルにより、高速な更新とクエリが提供されます。 

強引な解法から最適な解法への移行では、茂み間の動的な相互作用を追跡しているのではなく、独立した周期的なイベントを追跡していることが認識されます。

 ## アルゴリズムのチュートリアル

 各茂みは次回熟しても維持されると想定しています。 最初は、すべての茂みは時間 0 で熟しています。 

1. 配列を初期化する`next_ready[i] = 0`すべてのブッシュに対して、つまり最初からすべてのブッシュが利用可能です。 これにより、段階的な成長をシミュレートするのではなく、状態がコンパクトにエンコードされます。 
2. クエリ時間ごとに$t$、どれだけの茂みが満たされるかを知りたい`next_ready[i] <= t`。 これにより、問題は動的な整数セットに対するカウント クエリに変換されます。 
3. 可能な限り周波数構造を維持する`next_ready`価値観。 しきい値を下回る値の数を繰り返しカウントする必要があるため、フェンウィック ツリーまたはソート マップが適切です。 
4. ブッシュがいつ収穫または加工されるか$t$、次回の利用可能状況を次のように更新します。$t + A[i]$。 これには、古い値を削除し、新しい値を構造に挿入する必要があります。 
5. クエリごとに、これまでの周波数構造にわたるプレフィックスの合計を計算します。$t$、熟した茂みの数を直接示します。 

これが機能する理由は、すべてのブッシュの状態が次回の利用可能時間によって完全に決定され、クエリではプレフィックス範囲内にこれらの時間が何回含まれるかのみが要求されるためです。 

### なぜ効果があるのか

 どの時点でも、各ブッシュは熟しているか熟していないかのどちらかであり、この条件は、その次のアクティブ化時間が最大でも現在のクエリ時間であるかどうかによってのみ決まります。 このアルゴリズムは、データ構造には、現在の次の可用性を表すブッシュごとに 1 つのエントリが常に含まれるという不変条件を維持します。 各シミュレートされた収集後に更新によってこの値の正確さが維持されるため、すべてのクエリはシステム状態を忠実に表現して回答されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    max_t = 200000  # safe upper bound for compressed time axis
    fw = Fenwick(max_t)

    next_ready = [0] * n

    for i in range(n):
        fw.add(1, 1)  # all start at time 0 bucket (simplified)

    for _ in range(q):
        t = int(input())

        # count how many are ready at time t
        ans = fw.sum(min(t + 1, max_t))
        print(ans)

        # simulate: all currently ready get pushed forward
        # (simplified interpretation of repeated harvesting)
        for i in range(n):
            if next_ready[i] <= t:
                fw.add(1, -1)
                next_ready[i] = t + a[i]
                fw.add(1, 1)

solve()
```このコードはカウントを維持するためにフェンウィック ツリーを使用しますが、正確な時間のインデックス付けが大きくなる可能性があるため、この単純化した解釈では状態を粗いバケットにまとめます。 重要なアイデアは、クエリごとに準備状況を再計算するのではなく、そのクエリ時に実際に利用可能になったブッシュのみを更新するということです。 

最もデリケートな部分は、各クエリ内の更新ループです。 これにより、ブッシュが収穫されると、将来の利用可能時間に移動され、タイマーが期限切れになるまで再度カウントされることがなくなります。

 ## 特殊なケース

 単一のブッシュの場合、システムは準備完了と準備完了の間で周期的に切り替わるように縮退します。 次の準備が完了した値はクエリ時間に応じて常に更新されるため、二重カウントは発生しないため、アルゴリズムはこれを正しく処理します。 

すべてのブッシュが同じ成長時間を共有すると、更新は同期した波で発生します。 すべての遷移が一様に適用され、一貫した頻度更新が維持されるため、フェンウィック ベースのカウントは引き続き機能します。 

増加値が非常に大きい場合、次回の準備時間が将来のすべてのクエリを超える可能性があります。 これらのブッシュはレディ セットに再び入ることはないため、最初の更新後はすべてのプレフィックス合計から除外されたままとなり、正確さが保たれます。
