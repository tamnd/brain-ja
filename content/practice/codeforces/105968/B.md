 ## 解決策
 ## 問題の理解

 整数の範囲にわたる複数のクエリを処理しており、クエリごとに、指定された間隔内にあるすべての素数の合計を計算する必要があります。 各クエリは左と右のエンドポイントを提供し、タスクはこれら 2 つの境界間の素数の合計を迅速に返すことです。 

ここでの重要な構造は、同じ数値の世界がすべてのクエリで再利用されるということです。 これは、素数を再計算したり、クエリごとにゼロから素数を合計したりするのは冗長であることをすぐに示唆しています。 代わりに、固定範囲にわたる前処理ステップと、それに続く高速範囲クエリが必要です。 

入力範囲で可能な最大値が大きい場合、たとえば最大 n の場合、クエリごとのスキャンのコストは O(n) となり、多数のクエリを掛け合わせると速度が非常に遅くなります。 たとえば、n が 10^6 で、10^5 のクエリがある場合、単純なアプローチでは約 10^11 の操作が必要になりますが、これは一般的な時間制限の下では実現できません。 これにより、前処理がおよそ O(n log log n) または O(n) 時間で完了し、各クエリに O(1) で応答できるようになります。 

範囲が 1 から始まる場合、微妙なエッジケースが発生します。1 は素数ではないため、1 の素数性を誤って初期化するアプローチでは、誤って合計にそれが含まれる可能性があります。 たとえば、クエリが [1, 10] の場合、正しい素数は 2、3、5、7 で、答えは 17 です。1 を素数として扱うバグのあるふるいでは、18 が返されます。 

[x, x] など、範囲が非常に小さい場合や縮退している場合には、別の問題が発生します。 その場合、正しさは x が素数かどうかに完全に依存し、オフバイワン エラーなしでシングルポイント クエリをサポートするには、プレフィックスの合計を慎重に構築する必要があります。 

## アプローチ

 簡単なアプローチは、各クエリを個別に処理することです。 各範囲 [l, r] について、すべての数値を反復処理し、試行除算によって素数かどうかを確認し、合計を累積します。 これは概念的には単純で正しいですが、n までの素数テストには O(sqrt n) のコストがかかり、すべてのクエリのすべての数値に対してそれを実行すると、クエリ範囲ごとの最悪のケースでは O(n sqrt n) になります。 クエリが多数あると、これはすぐに実行不可能になります。 

この非効率性は、素数の再計算と重複する範囲の部分和の再計算を繰り返し行うことから発生します。 問題の構造は、各数値の素数性がクエリとは独立しており、一度判明すると決して変更されないことを示唆しています。 これにより前処理が可能になります。 

エラトステネスのふるいは、O(n log log n) 内の n までのすべての数値の素数を計算します。 素数をマークするブール配列を取得したら、prefix[i] が 1 から i までのすべての素数の合計を格納するプレフィックス合計配列を構築できます。 その後、任意のクエリ [l, r] は prefix[r] - prefix[l - 1] として答えることができ、クエリごとに O(1) が得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(Q・N √N) | お(1) | 遅すぎる |
 | ふるい + 接頭語の合計 | O(N log log N + Q) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 どの数値が素数であるかについての全体的なビューを構築し、それを高速範囲クエリをサポートする累積情報に変換します。 

### ステップ

1. すべてのクエリにわたって可能な最大のエンドポイントに基づいて、最大値 n を選択します。 これにより、必要となる可能性のあるすべての数値が前処理でカバーされることが保証されます。 
2. サイズ n + 1 の配列 is_prime を作成し、0 と 1 を除くすべてのエントリを true として初期化します。この初期化は、素数が 2 以上についてのみ不明であることを反映しています。 
3. i を 2 から sqrt(n) まで反復してエラトステネスのふるいを実行します。 i がまだ素数としてマークされている場合は、i * i から始まる i のすべての倍数を非素数としてマークします。 より小さい倍数はより小さい素数によってすでに処理されているため、i * i から開始するだけで十分です。 
4. ふるいが完了したら、prefix[i] が 1 から i までのすべての素数の合計を格納するプレフィックス合計配列 prefix を構築します。 各 i について、is_prime[i] が true の場合、i を累計に加算します。 それ以外の場合は 0 を追加します。 
5. 各クエリ [l, r] について、l > 1 の場合は prefix[r] - prefix[l - 1] として結果を計算し、そうでない場合は単に prefix[r] として計算します。 これにより、範囲の合計が定数時間の算術演算に変換されます。 

### なぜ効果があるのか

 ふるいの終わりでは、is_prime ですべての合成数が false としてマークされ、残りのすべての true エントリは素数に正確に対応します。 プレフィックス配列は固定配列の累積合計として構築されるため、プレフィックス間隔ごとに正確な合計が保存されます。 範囲の合計は 2 つのプレフィックスの合計に分解できるため、すべてのクエリは再計算せずに正確に回答されます。 不変条件は、prefix[i] が常に [1, i] 内のすべての素数の合計に等しいということです。これは、各インデックスが素数である場合にのみ 1 回だけ寄与するため当てはまります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_sieve(n):
    is_prime = [True] * (n + 1)
    if n >= 0:
        is_prime[0] = False
    if n >= 1:
        is_prime[1] = False

    i = 2
    while i * i <= n:
        if is_prime[i]:
            step = i
            start = i * i
            for j in range(start, n + 1, step):
                is_prime[j] = False
        i += 1

    return is_prime

def build_prefix(is_prime):
    n = len(is_prime) - 1
    prefix = [0] * (n + 1)
    running = 0
    for i in range(1, n + 1):
        if is_prime[i]:
            running += i
        prefix[i] = running
    return prefix

def solve():
    data = input().strip().split()
    if not data:
        return

    q = int(data[0])
    queries = []
    max_r = 0

    idx = 1
    for _ in range(q):
        l = int(data[idx])
        r = int(data[idx + 1])
        idx += 2
        queries.append((l, r))
        if r > max_r:
            max_r = r

    is_prime = build_sieve(max_r)
    prefix = build_prefix(is_prime)

    out = []
    for l, r in queries:
        if l > 1:
            out.append(str(prefix[r] - prefix[l - 1]))
        else:
            out.append(str(prefix[r]))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```ふるいの構築により、前処理ステップとして素数性が分離され、クエリ間で作業が繰り返されないことが保証されます。 プレフィックス構築により、静的分類が O(1) 区間合計をサポートする構造に変換されます。 唯一のデリケートな部分は、クエリの下限を正しく処理することです。プレフィックスの減算には、prefix[-1] のインデックス付けを避けるために l が 1 に等しい場合にガードが必要になるためです。 

## 実用的な例

 素数を手動で追跡できる狭い範囲でのクエリを検討してください。 

入力例:```
3
1 10
5 5
6 20
```まず、20 までの素数 (2、3、5、7、11、13、17、19) を構築します。接頭辞の合計は次のように展開します。 

| 私 | プライム[i] | 接頭辞[i] |
 | --- | --- | --- |
 | 1 | ふ | 0 |
 | 2 | た | 2 |
 | 3 | た | 5 |
 | 4 | ふ | 5 |
 | 5 | た | 10 |
 | 6 | ふ | 10 |
 | 7 | た | 17 |
 | 8 | ふ | 17 |
 | 9 | ふ | 17 |

 クエリ [1, 10] の場合、prefix[10] = 17 が返されます。これは 2 + 3 + 5 + 7 に一致します。

[6, 20] の場合、素数 7、11、13、17、19 に対応する 77 - 10 = 67 を計算します。 

このトレースは、プレフィックスの違いによって各クエリ範囲内の寄与が正確に分離されていることを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(N log log N + Q) | sieve はすべての数値を 1 回前処理し、各クエリは一定時間内に応答されます。 
| スペース | O(N) | 配列には素数とプレフィックスの合計が最大値まで格納されます。 

前処理コストは、数百万までの一般的な制約では許容可能であり、各クエリが一定数の配列ルックアップに減少するため、クエリ処理が最適化されます。

 ## 特殊なケース

 1 から始まる範囲は、接頭辞の減算によって負のインデックスへのアクセスが正しく回避されるかどうかをテストします。 入力 [1, 10] の場合、アルゴリズムは prefix[10] を直接使用します。prefix[0] は暗黙的に 0 として定義されているため、結果は正しいままです。 

[5, 5] のような単一点範囲を使用すると、減算によって誤って値が削除されることがなくなります。 計算は prefix[5] - prefix[4] となり、正確に 5 が分離されます。 

[14, 16] など、非素数が大半を占める大きな範囲では、合成の多い区間では特別な処理を行わなくても寄与がゼロであることが確認されています。 ふるいはすでに 14、15、16 を非素数としてマークしているため、プレフィックスはそのセグメント全体で変更されず、減算では正しく 0 が得られます。
