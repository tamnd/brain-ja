 ## 問題の理解

 私たちには一連のタスクが与えられており、それぞれの処理時間は固定されており、グローバルな期限が設定されています。 タスクは順番に起動する必要があります。つまり、タスクは`i`タスクの前に開始できません`i-1`が開始されました。 これにより、完了順序ではなく開始時間に基づいた依存関係チェーンが作成されます。 ただし、タスクが開始されると、それらは同一のサーバーのプール上で実行され、各サーバーは一度に 1 つのタスクのみを処理でき、現在のタスクが終了するとすぐに使用可能になります。 

重要な決定は、タスクを自由にスケジュールする方法ではなく、2 つの制約を尊重しながらタスクをサーバーに割り当てる方法です。タスクは順番にアクティブ化され、すべてが完了するまでの合計経過時間が超えてはなりません。`T`。 これを可能にする最小限のサーバー数が必要であるか、無限のリソースでも期限に間に合わないと判断します。 

制約`N, T ≤ 10^5`そして`A[i] ≤ 10^5`線形または線形算術よりも悪い解はすべて、`N`苦労するだろう。 すべてのサーバー割り当てに対する 3 次または 2 次シミュレーションは、各チェックを繰り返すとすでに遅すぎるため、直ちに実行できなくなります。 

単一のタスクが制限時間を超えた場合、微妙だが重要なエッジ ケースが発生します。 たとえば、次の場合`T = 5`そしていくつか`A[i] = 10`、そのタスクだけでは期限に違反するため、サーバーがいくつあっても役に立ちません。 

別の特殊なケースは、同一のタスクから発生します。 すべてのタスクが`1`そして`T = 5`の場合、並列処理を行っても、時間内に重複するタスクの数に応じて合計スループットの上限を超えることはできません。 開始順序の同期を無視する単純な貪欲な割り当てでは、必要なサーバーが過小評価されます。 

最後の障害モードは、タスクの順序を変更できると想定した場合に発生します。 それはできません。 強制的な順次開始制約により、これは同一マシン上での従来のスケジューリングとは根本的に異なります。 

## アプローチ

 直接シミュレーションでは、固定数のサーバーを試行します。`k`そして、利用可能な最も早いサーバーにタスクを貪欲に割り当てます。 各シミュレーションの費用`O(N log k)`優先キューを使用して次の空き状況を追跡します。 全部試してみる`k`から`1`に`N`与える`O(N^2 log N)`が遅すぎます。 

実現可能性が単調であることに気づいて最適化したとしても、`k`、検索を減らすことができます`k`二分探索を使用します。 残りの課題は、指定された数のサーバーが時間内に終了できるかどうかを効率的に確認する方法です。`T`。 

重要な洞察は、可用性時間に基づくスケジュール プロセスとしてサーバーの使用状況をモデル化することです。 各タスクは順序制約で許可されるとすぐに開始されますが、その実行は空いているサーバーに割り当てることができます。 当社では、サーバーの次の空き時間の構造を維持しています。 固定の場合`k`、各タスクを最も早い利用可能なサーバーに貪欲に割り当てます。 タスクが強制的に開始されたときにそのサーバーがビジー状態である場合、空になるまで割り当てを遅らせます。 メイクスパンは、最後の完了時間によって決まります。 

これが機能するのは、順序制約によって開始時刻の自由度が失われるためです。`i`常に「リリース」される`i-1`(概念的には) スケジューリングは、マシンの可用性に対する制約のある割り当ての問題になります。 

最小のものを二分探索します`k`完了時間 ≤ となります`T`。

 ## アルゴリズムのチュートリアル

 シーケンスを 1 つずつ利用可能になるタスクとして扱います。 サーバーの数が一定であるかどうかをテストします`k`で十分です。 

1. 候補者の場合`k`、サイズの最小ヒープを初期化します`k`、各要素はサーバーの次の空き時間を表し、すべて時刻から始まります。`0`。 これは、すべてのサーバーが最初はアイドル状態であることを表します。 
2. タスクを順番に繰り返します。 タスクごとに`i`、利用可能な最も早いサーバー時間を取得します`t = heap.pop()`。 最初に無料になるサーバーです。 
3. タスクは、その位置制約より早く開始することはできません。これは実質的に時間です。`i`リリースのユニット間隔を仮定すると。 より正確には、タスクは順番に到着するものとして扱います。 したがって、最も早い開始時間は、現在のタスクのリリース時間とサーバーの可用性の最大値になります。 
4. 実際の開始時刻を次のように計算します。`start = max(t, current_release_time)`。 
5. 完了時間は`start + A[i]`。 この値をサーバーの次の空き時間としてヒープにプッシュします。 
6. すべてのタスクの最大完了時間を追跡します。 
7. すべてのタスクを処理した後、この最大完了時間が ≤ であるかどうかを返します。`T`。 
8. 二分探索を使用する`k`から`1`に`N`実行可能な最小値を見つけます。 

### なぜ効果があるのか

 アルゴリズムは常に、最も早く空きになったサーバーに次のタスクを割り当てます。 他の割り当てでは、タスクはリリース順に処理する必要があるため、将来のタスクに早期に対応できるようにすることはなく、そのタスクの完了が遅れるだけです。 この貪欲な選択により、固定数のサーバーに対して可能な限り最も早い完了プロファイルが保存されます。 したがって、スケジュールが存在する場合は、`k`時間内のサーバー`T`、この建設もそのスケジュールと同等の完成時間を達成します。 

実現可能性関数は単調です`k`: サーバーを追加すると、待ち時間が短縮されるか、待ち時間が変更されないだけであり、待ち時間が増加することはありません。 これにより、バイナリ検索の正確さが保証されます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def can(k, a, T):
    heap = [0] * k
    heapq.heapify(heap)
    max_time = 0

    for i, x in enumerate(a):
        t = heapq.heappop(heap)
        start = max(t, i)
        finish = start + x
        max_time = max(max_time, finish)
        heapq.heappush(heap, finish)

        if max_time > T:
            return False

    return max_time <= T

def solve():
    n, T = map(int, input().split())
    a = list(map(int, input().split()))

    if max(a) > T:
        print(-1)
        return

    lo, hi = 1, n
    ans = n

    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid, a, T):
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1

    print(ans)

if __name__ == "__main__":
    solve()
```コア シミュレーションは、各サーバーが再び利用可能になった時点を追跡する最小ヒープによって処理されます。 各タスクは利用可能な最も早いサーバーに貪欲に割り当てられるため、作業が存在するときにマシンが不必要にアイドル状態になることはありません。 

二分探索はこの実現可能性チェックをラップし、最小の十分な構成が見つかるまで候補サーバーの数を減らします。 

微妙な点は、単一のタスクが超過した場合の早期の枝刈りです。`T`。 これがなければ、バイナリ検索は機能しますが、不可能な構成を探索するために時間が無駄になります。

 ## 特殊なケース

 次のような単一の過大なタスク`A = [100]`と`T = 10`即座に不可能状態が引き起こされます。 アルゴリズムはこれを事前にチェックします。`max(a) > T`、戻る`-1`不必要なシミュレーションなしで。 

小規模なタスクを含む完全にシーケンシャルなワークロードでは、チェーンの合計長が制限を遵守している場合、1 台のサーバーでも十分であることが確認されます。 ヒープには常に単一の要素が含まれており、完了は純粋に累積的に行われます。 

大規模な均一タスクを伴う高度に並列化されたワークロードでは、ヒープのバランス動作に負荷がかかります。 各タスクは、他のサーバーが使用可能になるまで同じサーバーを繰り返し選択します。これは、明示的なパーティショニング ロジックを使用せずに、貪欲な選択によって負荷が正しく分散されることを示しています。
