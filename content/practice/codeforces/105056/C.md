 ## 解決策
 ## 問題の理解

 位置から 1 次元の線分上を移動するオブジェクトをシミュレートしています`0`決まった目的地へ`k`。 各モジュールはこの線上のどこかから開始し、1 秒あたり 1 ユニットの一定速度で右に移動します。 各ウイルスも同じ線上のどこかから始まりますが、同じ速度で左に移動します。 

どちらも同じ速度で反対方向に移動するため、モジュールとウイルスは決して遭遇しないか、または初期位置によって完全に決定される決定的な時間に 1 回だけ遭遇します。 これらが出会ったとき、ウイルス モジュールの互換性エントリが与えられているかどうかに応じて、相互作用する可能性があります。 そのようなエントリがない場合、それらは単に相互に通過します。 エントリーがある場合、双方が能力値を持っている状態で戦闘が発生し、一方または両方が削除される可能性があります。 生き残ったモジュールも容量を失う可能性があり、生き残ったウイルスは左に移動し続け、後で他のモジュールに遭遇する可能性があります。 

最終的な目標は、時間の経過に伴う位置を明示的にシミュレートすることではなく、どのモジュールがすべてのインタラクションを生き残るかを判断し、それらを到着時間順にソートしてサーバーに出力することです。 すべてのモジュールが位置に向かって 1 つの速度で移動するため、`k`、到着時間は開始位置によってのみ異なります。 

制約が非常に厳しいため、考えられるすべての衝突を単純にペアごとにシミュレーションすることは不可能です。 モジュールは最大 1,000 個、ウイルスは 5,000 個までありますが、相互作用ルールは最大 500,000 個あります。 すべてのモジュールとウイルスのペアをチェックしたり、毎秒シミュレートしたりするソリューションは、明らかに制限を超えています。 代わりに、相互作用はまばらであり、初期位置によって完全に決定されるという事実に依存する必要があります。 

複数のインタラクションが同時に衝突した場合、微妙な問題が発生します。 モジュールは以前の戦闘によって変更される可能性があるため、同時衝突の処理順序が結果に影響を与える可能性があります。 正しい解決策は、同時性の一貫した解釈を尊重する必要があります。 

エッジケースの 1 つは、モジュールとウイルスが同じ位置から始まる場合です。 その場合、それらは時間 0 ですぐに衝突するため、他の衝突と同様に処理する必要があります。 

もう 1 つのエッジ ケースは、ウイルスとモジュールのペアが相互作用リストに存在するが、その位置が次のような場合です。`(virus_position - module_position)`奇数です。 その後、それらは半整数時間で衝突し、正確に整数秒で衝突することはありません。 これらのペアは無視する必要があります。 

最後に、モジュールは複数の相互作用に関与する可能性があり、その能力は生存するたびに変化します。 固定モジュール容量を前提とした不用意な実装は、誤った結果を生成します。 

## アプローチ

 ブルートフォース解釈では、システムを秒ごとにシミュレートし、すべての位置を更新し、すべての可能な重複をチェックしようとします。 これは概念的には単純ですが、実行不可能です。位置の範囲は最大 10^9 であるため、単一のシミュレーションでも数十億のステップが必要となり、各ステップですべてのモジュールをすべてのウイルスに対してチェックする必要があります。 

より構造化されたブルート フォースでは、考えられるすべてのペアごとの衝突時間を計算することで、これを改善します。 会合する可能性のあるすべてのモジュールとウイルスのペアについて、会合時間を計算し、時系列でイベントをシミュレートします。 これですでに問題はイベント処理に限定されていますが、すべてを考慮すると依然としてリスクが大きくなります。`n * m`ペアは最大 500 万ペアになる可能性があります。 

重要な点は、すべてのペアを考慮する必要はなく、入力クエリで明示的に指定されたペアのみを考慮する必要があるということです。 この問題は相互作用のまばらなセットを提供し、生存と能力の変化を決定する際に重要となるのはそれらの相互作用のみです。 それ以外の遭遇は何の影響もないので無関係です。 

自分自身を次のことに限定すると、`q`指定されたインタラクションを使用すると、システムは古典的なイベント シミュレーション問題になります。 各イベントには、初期位置によって決定されるタイムスタンプがあります。 イベントを時間順に並べ替えて順番に処理し、モジュールとウイルスの状態を更新します。 

残りの課題は、インタラクションを正しく解決し、モジュールの容量が失われたり削除された場合の状態変化を処理したりすることです。

 ## アルゴリズムのチュートリアル

 ### 重要なアイデア

 有効なウイルスとモジュールの相互作用を、特定の時間にスケジュールされたイベントとして扱い、それらのイベントのみをシミュレートします。 

### ステップ

 1. すべてのモジュール データを読み取り、各モジュールを名前とその初期容量および位置で保存します。 

戦闘により両方が変更されるため、現在の可変容量と生存/死亡フラグも保存します。 
2. すべてのウイルス データを読み取り、各ウイルスをその ID と位置、および生存/死亡フラグに基づいて保存します。 
3. を読んでください。`q`インタラクションルール。 ウイルスとモジュール間のルールごとに、それらが実際に一致するかどうかを計算します。 

位置にあるモジュール`x`位置にあるウイルスと`y`お互いに向かって進むのは、次の場合にのみです。`y > x`そして`(y - x)`は均等です。 集合時間は`(y - x) // 2`。 
4. 有効な会議ごとにイベントを作成します。`(time, virus_id, module_id, virus_capacity_against_module)`そしてそれをリストに保存します。 
5. すべてのイベントを時間順に並べ替えます。 複数のイベントが同じ時間を共有する場合、それらは一緒に処理されます。 
6. 時間の増加順にイベントを繰り返します。 

- モジュールまたはウイルスがすでに死んでいる場合は、イベントをスキップします。 
- ウイルスの容量が定義されていない場合 (フィルタリングにより発生しないはずです)、スキップします。 
- モジュール容量の比較`C`そしてウイルスの容量`X`。 

- もし`C > X`、ウイルスが死滅し、モジュールの容量が`C - X`。 
- もし`C < X`、モジュールが停止します。 
- 等しい場合、両方とも死亡します。 
7. すべてのイベントを処理した後、まだ生きているすべてのモジュールを収集します。 
8. 残りのモジュールを到着時間順に並べ替えます。 すべてのモジュールが速度 1 で位置まで移動するため、`k`、到着時間は`k - position`, so sorting by increasing arrival time is equivalent to sorting by decreasing initial position.

 ### なぜ効果があるのか

 Every interaction that can affect the system is encoded as a deterministic event. Since movement is uniform, no event depends on intermediate positional randomness. The only evolving state is module capacity and alive status, and both are updated only at event times. 各イベントは 1 つの可能なインタラクションを完全にキャプチャしているため、イベントをスキップすることは実際の物理的な遭遇を削除することに相当し、余分なイベントを処理することは決して起こらない衝突を作り出すことに相当します。 

正しさは、連続するイベント間では、別のイベントの結果に影響を与える可能性のあるペアについて何も変わらないという不変条件にかかっています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, q = map(int, input().split())

    modules = {}
    module_pos = {}
    module_alive = {}
    module_cap = {}

    for _ in range(n):
        name, cap, pos = input().split()
        cap = int(cap)
        pos = int(pos)
        modules[name] = name
        module_pos[name] = pos
        module_alive[name] = True
        module_cap[name] = cap

    virus_pos = {}
    virus_alive = {}

    for _ in range(m):
        vid, pos = map(int, input().split())
        virus_pos[vid] = pos
        virus_alive[vid] = True

    events = []

    for _ in range(q):
        vid, mod, cap = input().split()
        vid = int(vid)
        cap = int(cap)

        if mod not in module_pos or vid not in virus_pos:
            continue

        x = module_pos[mod]
        y = virus_pos[vid]

        if y <= x:
            continue

        diff = y - x
        if diff % 2 != 0:
            continue

        t = diff // 2
        events.append((t, vid, mod, cap))

    events.sort()

    for t, vid, mod, cap in events:
        if not module_alive[mod] or not virus_alive[vid]:
            continue

        C = module_cap[mod]
        X = cap

        if C > X:
            module_cap[mod] -= X
            virus_alive[vid] = False
        elif C < X:
            module_alive[mod] = False
        else:
            module_alive[mod] = False
            virus_alive[vid] = False

    remaining = [name for name in module_pos if module_alive[name]]

    remaining.sort(key=lambda x: -module_pos[x])

    print(len(remaining))
    print(" ".join(remaining))

if __name__ == "__main__":
    solve()
```モジュールとウイルスのディクショナリは位置などの静的な入力プロパティを保持し、別の配列が動的な状態を追跡します。 立場は決して変わりませんが、能力と生存状況は変わるため、この分離は重要です。 

イベント リストは核となる構造であり、各エントリは 1 つの起こり得る衝突をエンコードします。 並べ替えることで、インタラクションを正しい時間順序で処理できるようになります。 

最後の並べ替えステップでは、速度が均一で到着順序が時間 0 で完全に決定されるため、到着時間を直接シミュレートする代わりに初期位置を使用します。 

## 実用的な例

 ### 例 1

 入力:```
modules:
A(0, 5), B(3, 2)
viruses:
V1(6), V2(7)
events:
(V1, A, 4), (V2, B, 2)
```イベント時間:

 | 時間 | イベント | モジュールキャップ | ウイルスキャップ | 結果 |
 | --- | --- | --- | --- | --- |
 | 3 | V1-A | 5 | 4 | A は生き残り (キャップ 1)、V1 は死亡します。 
| 2 | V2-B | 3 | 2 | B は生存 (キャップ 1)、V2 は死亡 |

 時間順に処理:

 | ステップ | 生きているモジュール | アクション |
 | --- | --- | --- |
 | t=2 | Ａ、Ｂ | B は生き残り、上限は減少します |
 | t=3 | Ａ、Ｂ | A が生き残り、上限が減少します |

 両方のモジュールが生き残り、最終的な順序は位置に依存します: A が最初です。 

これは、時間によるイベントの順序付けにより、正しいカスケード更新が保証されることを示しています。 

### 例 2

 同時発生するイベントを考慮してください。 

| 時間 | イベント | モジュールキャップ | ウイルスキャップ |
 | --- | --- | --- | --- |
 | 2 | V1-A | 3 | 3 |
 | 2 | V2-A | 2 | 1 |

 V1-A が最初に処理される場合、A はすぐに終了し、V2-A はスキップされます。 逆にすると、代わりに A が 2 番目のイベントで死亡します。 どちらの方法でも A は除去されますが、ウイルスの生存率は異なります。 これは、タイブレークがローカルでのみ重要であるにもかかわらず、一貫した処理の下では最終モジュール セットの一貫性が保たれる理由を示しています。

 ## 特殊なケース

 重要なエッジケースは、複数のウイルスが同じタイムスタンプで同じモジュールと衝突する場合です。 アルゴリズムはそれらを順番に処理しますが、各イベントがモジュールの状態を即座に更新し、同時に順序付けられたマイクロインタラクションの一貫した物理的解釈と一致するため、正確性が維持されます。 

もう 1 つの重要なケースは、容量が定義されていないモジュールにウイルスが遭遇した場合です。 これらのイベントは早期にフィルタリングされ、シミュレーションにまったく入らないことが保証され、不必要な状態チェックが回避されます。 

最後に、どのイベントにも決して出現しないモジュールはそのまま残され、位置に基づいて最終的にソートされたリストに単純に含まれ、イベント システムが関連するオブジェクトのみに影響を与えることが確認されます。
