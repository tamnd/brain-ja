 ## 解決策
 ## 問題の理解

 同じ問題トピックの複数セットを記述する長さ n の 2 つのシーケンスが与えられます。 最初のシーケンスは、ソリューションが 1 つずつ利用可能になり、新しいソリューションがそれぞれスタックに配置される順序を表します。 2 番目のシーケンスは、これらのソリューションをスタックから取得して処理する必要がある正確な順序を示しています。 

各瞬間に、最初のシーケンスから次に使用可能な要素をスタックにプッシュするか、スタックの先頭をポップして 2 番目のシーケンスの次に必要な要素として出力します。 目標は、ポップされたシーケンスが 2 番目の配列と正確に一致するように、正確に n 個のプッシュと n 個のポップのシーケンスを実行できるかどうかを判断し、可能であれば、そのような一連の操作を構築することです。 

n ≤ 100 という制約は、二次関数の解、または線形スタック演算を使用した単純なシミュレーションであっても、容易に十分に高速であることを意味します。 単純な貪欲なシミュレーションを超える高度なデータ構造や最適化は必要ありません。 唯一の微妙な点は、値が明確ではなく、通常の「1 から n へのスタックの置換」の直感を注意深く適応させる必要があるため、重複時の正確性です。 

単純な試みでは、プッシュとポップのすべての可能なインターリーブを元に戻そうとする可能性があります。 このアプローチはステップごとに分岐し、状態の数が指数関数的に増加します。 n = 100 の場合でも、これは完全に不可能になります。 

さらに微妙な間違ったアプローチは、常に最初にすべてをプッシュしてから、順番にポップしようとすることです。 目的の出力が後の要素がプッシュされる前に初期のポップが必要な場合、これは明らかに失敗します。 

重要なエッジ ケース パターンは、次に必要な出力が将来の入力シーケンスのより深いところにあるにもかかわらず、現在別の要素がスタック上でそれをブロックしている場合です。 間違った要素を早い段階でポップすると、必要な順序が永久にブロックされる可能性があります。 

## アプローチ

 ブルート フォース アプローチでは、S および C 操作のすべてのシーケンスが考慮され、現在のスタックが維持され、生成された出力がターゲットと一致するかどうかがチェックされます。 2n 個の位置のそれぞれは制約付きで S または C のいずれかにできるため、有効なシーケンスの数は組み合わせ的に増加します。 最悪の場合、これはカタロニア数のような構造のオーダーで探索され、n とともに指数関数的に増加します。 これは、n = 30 の場合でもすぐに不可能になります。 

重要な観察は、プロセスが強力な貪欲な構造を持っているということです。 要素がスタックの最上位にあり、次に必要な出力と一致すると、その削除を遅らせても役に立ちません。 他の選択肢を選択すると、それがより深く埋められるだけであり、将来必要な要素がブロックされる危険があります。 これは、スタックのトップが次に必要な要素と一致するときはいつでも、すぐにポップする必要があることを意味します。 

このアイデアでは、プロセス全体が入力シーケンスの 1 つの左から右へのスキャンとなり、プッシュをシミュレートしながら、可能な限り継続的にポップを実行します。 これにより、スタックとターゲット シーケンスへのポインタを維持するという問題が軽減されます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(2^{2n}) | O(n) | 遅すぎる |
 | 最適 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 スタック、2 つのポインター、結果文字列を使用してプロセスをシミュレートします。

1. 空のスタックを初期化し、ターゲット シーケンスのポインタ j = 0 を設定します。 
2. ソース シーケンスに対して i を 0 から n − 1 まで繰り返します。 要素ごとに、それをスタックにプッシュし、「S」操作を記録します。 要素にアクセスできるのはスタック構造を通じてのみであり、現在のソース要素を将来の一致に使用できるようにする必要があるため、プッシュが必要です。 
3. プッシュするたびに、スタックの最上部を繰り返し確認します。 スタックが空ではなく、先頭が現在のターゲット要素 b[j] に等しい場合、それをスタックからポップし、「C」を記録し、j をインクリメントします。 この貪欲な削除により、遅延はその上にブロック要素を追加するだけであるため、利用可能な正しい一致を遅らせることがなくなります。 
4. すべてのソース要素がプッシュされるまで、このプロセスを続けます。 
5. すべてのプッシュが完了した後、ターゲット シーケンス (j == n) 内のすべての要素が正常に一致した場合、記録された操作は有効なソリューションを形成します。 そうでなければ不可能です。 

### なぜ効果があるのか

 不変条件は、シミュレーションのどの時点でも、スタックはプッシュされたがまだ出力されていない要素のセットを正確に表し、それらの相対的な順序は挿入時間によって固定されるということです。 スタックの最上位が次に必要な出力と一致する場合は、スタックの最上位をすぐに削除することが常に安全かつ最適です。これを残しておくと、有効な一致が延期されるだけであり、その上に新しいブロック要素が導入される可能性があるためです。 ターゲット シーケンス内の要素が一致しない状態でプロセスが終了した場合、必要な要素の一部が正しいタイミングでスタックの先頭に公開されなかったことを意味し、操作の順序を変更しても修正できません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    
    stack = []
    res = []
    j = 0
    
    for x in a:
        stack.append(x)
        res.append('S')
        
        while stack and j < n and stack[-1] == b[j]:
            stack.pop()
            res.append('C')
            j += 1
    
    if j == n:
        print("YES")
        print("".join(res))
    else:
        print("NO")

if __name__ == "__main__":
    solve()
```実装はアルゴリズムに直接に従います。 スタックには、現在保持されているすべてのソリューションが保存されます。 各プッシュの後、内側のループは、次に必要な出力をすぐに満たす要素を貪欲に削除します。 ポインタ j により、ターゲット シーケンスをスキップしたり並べ替えたりすることがなくなります。 最終チェックでは、必要な出力がすべて生成されたことを確認します。 そうしないと、一部の要素がスタックの順序付けによって永続的にブロックされました。 

微妙な点は、重複が自然に処理されることです。 照合は ID ではなく値によって行われるため、複数の同一の値は同じように扱われます。また、正確性は一意性ではなくスタック順序のみに依存するため、貪欲なルールが引き続き適用されます。 

## 実用的な例

 ### 例 1

 入力:

 n = 4

 a = [4, 1, 2, 2]

 b = [1, 2, 4, 2]

 | ステップ | アクション | スタック | j | 出力 |
 | --- | --- | --- | --- | --- |
 | 1 | プッシュ 4 | [4] | 0 | S |
 | 2 | 1 を押します | [4,1] | 0 | SS |
 | 3 | ポップ1 | [4] | 1 | エスエスシー |
 | 4 | プッシュ2 | [4,2] | 1 | ＳＳＣＳ |
 | 5 | ポップ2 | [4] | 2 | SSCSC |
 | 6 | プッシュ2 | [4,2] | 2 | ＳＳＣＳＣＳ |
 | 7 | ポップ2 | [4] | 3 | SSCSCSC |
 | 8 | ポップ4 | [] | 4 | SSCSCCSC |

 このトレースは、トップがターゲットに一致するたびに即座にポップすることで、不要なブロックが発生しないことを示しています。 一致が表示されるたびに、即座に解決されます。 

### 例 2

 入力:

 n = 3

 a = [2, 3, 1]

 b = [1、2、3]

 2 (スタック [2]) をプッシュし、3 (スタック [2,3]) をプッシュし、最終的に 1 を出力する必要があります。ただし、適切なタイミングで 1 がスタックの一番上に現れることはありません。 2 と 3 がすでにブロックしてからでは遅すぎます。 プロセスはスタック [2,3,1] で終了しますが、3 と 2 の前に 1 をポップすることができないため、必要な順序を実行できません。 

これは、両方のシーケンスに同じマルチセットが含まれている場合でも、スタック制約により順序付けが不可能になる可能性があることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各要素は 1 回プッシュされ、最大 1 回ポップされます。 
| スペース | O(n) | スタックには最大 n 個の要素が保持されます。 

n ≤ 100 の場合、線形複雑さは十分に十分です。アルゴリズムは要素ごとに一定量の作業を実行し、ネストされた検索やバックトラッキングは必要ありません。

import sys, io

def solve():
    input = sys.stdin.readline
    n = int(input().strip())
    a = list(map(int, input().split()))

    stack = []
    res = []
    j = 0

        res.append('S')

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    return solve()

 ## 特殊なケース

 同一の値が多数出現すると、微妙なエッジ ケースが発生します。 等価比較は位置に依存せず、実行可能性の観点からはすべての出現を区別できないため、アルゴリズムは引き続き正しく動作します。 スタック構造のみが正確さを決定します。 

もう 1 つのケースは、ターゲット シーケンスがプッシュされる前に要素を必要とする場合です。 その状況では、貪欲なシミュレーションは、上部でアクセスできるようになるか、ブロックされたままになるまで、すべてをプッシュします。 先頭の正しい位置に到達しない場合、最終ポインタ j は n に到達せず、不可能であることを正しく示します。
