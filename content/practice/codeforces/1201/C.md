 ## 解決策
 ## 問題の理解

 数値のリストが与えられ、単一の要素を繰り返し 1 ずつ増やすことができます。 このような各増分には 1 回の操作のコストがかかり、総予算は最大でも$k$操作。 目標は、合計やグローバル統計を最大化することではなく、特に配列を並べ替えた後の中央値を最大化することです。 

配列サイズが奇数であるため、中央値が最終的な位置にある要素になります。$n/2$並べ替え後。 重要な問題は、一部の要素を増やすと並べ替え順序が変わる可能性があるため、中央値が元の配列の固定インデックスに関連付けられないことです。 

制約が非常に大きいため、操作を 1 つずつシミュレートする戦略は不可能です。 と$n$まで$2 \cdot 10^5$そして$k$まで$10^9$、単一の長さの演算ループでも$k$明らかに制限時間を超えてしまいます。 実行可能な解決策は、問題をソートと線形処理、または答えに対する対数検索のいずれかに削減する必要があります。 

貪欲に中央値を直接上げようと考えると、微妙な失敗モードが現れます。 現在の中央値要素のみを増加させる場合、並べ替え後の中央値の状態を維持するために、その右側にある他の要素も増やす必要がある可能性があるという事実を無視します。 たとえば、中央値を単独で増加させるだけの場合、その右側にある小さな要素によって、並べ替え後に中央値が中央値になることが妨げられる可能性があります。 

動的にソートされた構造を維持し、中央値を繰り返し調整しようとすると、2 番目の間違いが発生します。 これは、挿入と削除を繰り返すため遅くなりすぎ、問題の実際の構造がわかりにくくなります。最終的な答えには中央位置以上の要素のみが重要です。 

## アプローチ

 ブルート フォース アプローチでは、要素間のすべての可能な分布で操作を適用するプロセスをシミュレートします。 増加するたびに配列を再ソートし、中央値を追跡します。 たとえ有望な要素間で増分を分配することだけに限定したとしても、可能な分配の数は次の要素との組み合わせで増加します。$k$、このアプローチは実行不可能になります。 

重要な観察は、配列がソートされると、中央値は固定位置に位置し、その位置以降の要素のみが配列の大きさに影響を与えることができるということです。 中央値の左側にある要素は、中央値を制限しません。要素を増やすと中央値が向上するだけか、再並べ替え後も中央値が変更されないままになるためです。 

これは貪欲な構造につながります。中央値とその右側のすべてのものを上げて、中央値をできるだけ上に押し上げたいと考えます。 中央値の目標値を固定すると、右半分のすべての要素をその値以上にするために必要な操作の数を確認できます。 これは当然、実現可能性のチェックにつながります。 

ここからは、二分探索が自然なツールになります。 配列の中央値とサフィックスを予算内でそのレベルまで引き上げることができるように、最大​​中央値を検索します。$k$。 ソート後の各チェックは直線的です。

 | 最適 (二分探索 + 貪欲チェック) |$O(n \log (k + \max a))$|$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 まず中央位置が固定されるように配列を並べ替えます。 させて$m = n/2$。 From this point, the median we control is at index$m$、インデックスのみ$m, m+1, \ldots, n-1$候補中央値を強制するための事項。 

1. 中央値に関する推論には安定した順序付けが必要であるため、配列をソートします。 並べ替えないと、どの要素が中央値を制約しているかを特定できません。 
2. 指定された値かどうかをチェックする関数を定義します。$x$中央値として達成できます。 アイデアは、インデックスからすべての要素を強制することです$m$今後は少なくとも$x$なぜなら、それらすべてが少なくとも$x$、中央値も少なくとも$x$。 
3. これを達成するためのコストを計算するために、インデックスから反復処理を行います。$m$に$n-1$そして赤字を積み上げる$\max(0, x - a[i])$。 これは、これらの要素を次の値に引き上げるのに必要な最小増分数を表します。$x$。 その理由は、中央値から離れる要素を増やしても中央値の到達を保証することにはならないからです。$x$より大きな要素によって中央領域から押し出される可能性があるためです。 
4. 必要経費の合計が以内の場合$k$、次に値$x$実現可能です。 そうしないと大きすぎます。 
5. 二分探索をします$x$。 下限は現在の中央値であり、上限はすべてを加算することで拡張できます。$k$最良の場合、中央値要素に対する操作。 
6. 最終的な答えは実現可能な最大のものです$x$。 

### なぜ効果があるのか

 重要な不変条件は、ソートされた配列では、中央値がインデックスで始まるサフィックスによって完全に決定されることです。$m$。 すべての要素を少なくともこのサフィックスに含めることに成功する戦略$x$中央値も少なくともであることを保証します$x$、要素の少なくとも半分は$\ge x$。 逆に、サフィックスを次のように上げることができない場合は、$x$予算内で、中央値を達成するためのあらゆる試み$x$制御領域内の一部の要素が下に残るため失敗します。$x$、中央値を押し下げます。 これにより、実現可能性チェックが必要かつ十分になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(a, m, k, x):
    cost = 0
    for i in range(m, len(a)):
        if a[i] < x:
            cost += x - a[i]
            if cost > k:
                return False
    return True

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))
    a.sort()

    m = n // 2

    lo = a[m]
    hi = a[m] + k

    ans = lo
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(a, m, k, mid):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    print(ans)

if __name__ == "__main__":
    solve()
```ソートのステップは、中央値の位置をロックして、実現可能性に関するすべての推論が値ベースではなく位置ベースになるため、不可欠です。 ヘルパー関数`can`右半分のみが候補中央値の強制に寄与するという考えを直接エンコードします。 

実行可能性が単調であるため、ここでは二分探索は安全です。$x$が達成可能であれば、それ以上の操作は必要ないため、さらに小さな値も達成可能です。 

上限の選択$a[m] + k$すべての操作が中央値要素自体に集中する、可能な限り最良のシナリオを反映しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, k = map(int, input().split())
    a = list(map(int, input().split()))
    a.sort()
    m = n // 2

    def can(x):
        cost = 0
        for i in range(m, n):
            if a[i] < x:
                cost += x - a[i]
                if cost > k:
                    return False
        return True

    lo, hi = a[m], a[m] + k
    ans = lo
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    return str(ans)

# samples
assert run("3 2\n1 3 5\n") == "5"

# custom: minimum
assert run("1 10\n5\n") == "15"

# all equal
assert run("5 3\n7 7 7 7 7\n") == "8"

# large skew
assert run("5 5\n1 1 1 1 10\n") == "3"

# no budget
assert run("3 0\n1 2 3\n") == "2"

 ## 特殊なケース

 重要なエッジ ケースは、中央値がすでに配列内の最大要素である場合です。 この場合、サフィックスは非常に小さく、中央位置を増やすだけで十分であるように思われるかもしれませんが、実現可能性チェックでは、まだ持ち上げる必要がある右側の要素が正しく考慮されます。 

別のケースが発生する場合$k$非常に大きいです。 二分探索では、既存のすべての要素を超えて中央値が上昇します。コストは、最初の分布ではなく、サフィックスに含まれる要素の数によって完全に決まります。
