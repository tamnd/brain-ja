 ## 解決策
 ## 問題の理解

 私たちには根の生えた木が与えられています。 各頂点は +1 または -1 のいずれかの値を持ちます。 初期ライフ値 1 を持つ時間 0 の固定頂点から開始します。 

時間は離散的なステップで進みます。 各タイム ステップでは、3 つのことが厳密な順序で発生します。まず、現在立っている頂点に応じてライフを獲得または失います。次に、ライフがゼロになるか、その時点で溶岩がすでにその頂点に到達している場合はすぐに死にます。そして、まだ生きている場合にのみ、次のタイム ステップで移動する隣接する頂点を選択します。 

溶岩は根元から外側に広がり、t ステップ後に根元から最大 t の距離にあるすべての頂点が浸水したと見なされます。 これは、深いノードは長期間安全である一方、浅いノードは早く安全でなくなることを意味します。 移動は生存チェックの後に発生するため、頂点に入る瞬間が重要です。到着が早すぎると、一歩遅ければ頂点が安全だったとしても、即座に死亡する可能性があります。 

タスクは、最初の頂点から始めて、死ぬまでに実行できる移動の数を最大化することです。 

制約は十分に大きいため、n はテストごとに最大数十万になる可能性があり、多くのテスト ケースが存在する可能性があります。 これにより、考えられるすべてのパスをシミュレートしたり、パスごとに独立して状態を再計算しようとするものは直ちに除外されます。 どのソリューションでも、テスト ケースごとにほぼ直線的な時間でツリーを処理し、軌跡を列挙するのではなく構造を再利用する必要があります。 

主な微妙なエッジケースは、死がどのように引き起こされるかによって生じます。 まず、ライフ値の更新は洪水の安全性を確認する前に行われます。 つまり、重みが -1 の頂点は、溶岩が問題になる前に、あなたを殺す可能性があることを意味します。 第二に、溶岩が頂点に到達するときに正確に到着することは致命的であるため、「距離の平等」は安全ではありません。 第三に、移動はステップごとに強制されるため、安全な高価値ノードに留まるという選択肢はなく、貪欲なローカル推論は失敗します。 

小さな失敗例: ノードの重みが -1 で、まだフラッディングされていないと仮定します。 素朴なアプローチでは、溶岩は遠くにあるので安全だと考えるかもしれませんが、ライフが 1 のときに溶岩に足を踏み入れると、移動する前に即死が発生します。 

## アプローチ

 ブルート フォース アプローチでは、これを (現在の頂点、現在のライフ値、現在の時間) によって定義される状態に対する最短パス スタイルの検索として処理しようとします。 各州からすべての近隣地域に分岐し、生活の変化と洪水をシミュレートします。 これは正確なルールに従っているため、原理的には正しいですが、状態空間が爆発します。 ライフ値は n まで大きさに制限がなく、時間は n まで増加し、分岐は次数に比例するため、最悪の場合の複雑さはツリーの深さで指数関数的になります。 メモ化しても、敵対的な場合には個別の状態の数は Θ(n²) のままです。 

重要な観察は、生命の進化は経路に沿った累積量のみに依存するのに対し、洪水のタイミングは深さのみに依存するということです。 これにより 2 つの効果が分離されます。1 つはパスに依存する追加の重みであり、もう 1 つはルートに対する純粋な位置です。 問題は、各頂点にデッドライン (深さ) があり、各パスに決してゼロになってはいけない実行中のプレフィックス合計制約があるツリー内で下向きまたは上向きに制約されたウォークを選択することに帰着します。 

この構造により、再ルートまたは DFS ベースの DP が可能になり、正のプレフィックス合計を維持し、フラッド タイミングよりも先に進みながら、ノードごとに最適な「存続可能な拡張深度」、または同等にそのノードから始まるパスの最長有効継続を追跡できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース状態検索 | 指数 | O(n²) 以上 | 遅すぎる |
 | 深さを考慮したプレフィックス制約を備えたツリー DP | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

中心的な考え方は、ルートからノードへの各パスを 2 つの制約を持つシーケンスとして扱うことです。重みのプレフィックス合計は正の値を維持する必要があり、位置インデックスは常に浸水深制約より厳密に小さくなければなりません。 

開始ノードからの DFS を使用してこれを解決しますが、位置を追跡するだけでなく、現在のパスに沿って、これまでに発生した累積寿命と最小プレフィックス寿命の両方を維持します。 

1. ツリーのルートを 1 に設定し、BFS または DFS を使用してルートからのすべてのノードの深さを事前計算します。 これにより、各ノードがフラッディングになる正確な時間がわかります。 
2. 開始ノードから DFS を開始します。 現在の寿命の合計と、これまでのパスに沿って確認された最小寿命の 2 つの実行値を維持します。 これらは、すでに生存条件に違反しているかどうかを表します。 
3. 各ノードで、他のことを行う前に、まずノードの重みを現在のライフに適用します。 これは問題ステートメント内の強制された順序を反映しており、正確さのために不可欠です。 
4. 現在のノードがこのタイム ステップですでにフラッディングされているかどうかを、その深さを使用して直ちに確認します。 そうであれば、道はここで止まります。 
5. ライフ値がゼロ以下になっていないかも確認します。 そうなると、道もここで止まってしまいます。 
6. それ以外の場合は、現在のノード (または親を除く隣接ノード) のすべての子に対して、DFS を再帰的に続行し、移動カウンタを 1 つ増やします。 
7. 最初の頂点から開始して、すべての有効な DFS ブランチにわたる最大移動数を追跡します。 

主な問題点は、異なる累積寿命を持つ状態を再検討する可能性があるため、単純な DFS が過剰にカウントしてしまうことです。 この構造は、ライフが非ポジティブになるか、フラッディングが追いつくと、そのブランチから継続することはできないため、枝刈りは安全であるという事実に依存することで、明示的なメモ化を回避します。 

### なぜ効果があるのか

 すべての有効な軌道は、プレフィックス合計条件と単調深さ制約によって制約されたツリー内のルート方向のウォークに正確に対応します。 DFS は、時間がパスに沿った深さによって暗黙的にエンコードされるため、一貫性のない時間状態にあるノードを再訪問することなく、そのようなすべてのウォークを探索します。 プルーニング条件は元のプロセスの失敗条件と正確に一致するため、無効な拡張子はカウントされず、すべての有効な拡張子は何らかの DFS パスから到達可能になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
sys.setrecursionlimit(10**7)

def solve():
    n, st = map(int, input().split())
    w = [0] + list(map(int, input().split()))

    g = [[] for _ in range(n + 1)]
    for i in range(n - 1):
        u, v = map(int, input().split())
        g[u].append(v)
        g[v].append(u)

    # compute depth from root = 1 (lava source)
    depth = [-1] * (n + 1)
    from collections import deque
    q = deque([1])
    depth[1] = 0
    while q:
        u = q.popleft()
        for v in g[u]:
            if depth[v] == -1:
                depth[v] = depth[u] + 1
                q.append(v)

    ans = 0

    def dfs(u, p, life, moves, cur_depth):
        nonlocal ans

        life += w[u]
        if life <= 0:
            return
        if cur_depth > depth[u]:
            return

        ans = max(ans, moves)

        for v in g[u]:
            if v == p:
                continue
            dfs(v, u, life, moves + 1, cur_depth + 1)

    dfs(st, -1, 1, 0, depth[st])
    print(ans)

t = int(input())
for _ in range(t):
    solve()
```この実装では、フラッド タイミングの前処理が DFS 状態から分離されます。 溶岩の挙動は根までの距離のみに依存するため、深さは根から一度計算されます。 DFS は明示的に存続期間を保持し、プロセス内の強制順序付けと一致する終了条件をチェックする前に更新します。 

微妙な点の 1 つは、DFS は動作ステップに合わせて現在の時間の深さの概念も保持していることです。 これにより、動きと溶岩の膨張が同期します。 

## 実用的な例

 元のステートメントにはサンプルが含まれていないため、最小限のツリーを考えてみましょう。 

最初の例: 重みを付けた 1 をルートとする 3 つのノードのライン`[+1, -1, +1]`、ノード 2 から開始します。溶岩の深さは根から成長するため、最初にノード 1 が安全でなくなります。 ノード 2 から開始するとライフ 1 が与えられ、次に -1 を適用するとライフ 0 になり、プロセスはすぐに終了するため、移動はできません。 最初の更新直後に寿命制約に違反するため、DFS は最初の遷移で停止します。 

2 番目の例: 開始ノードが深く、すべての重みが +1 であるバランスの取れたツリー。 この場合、寿命は増加するだけであり、唯一の制限要因はノードに到達する溶岩です。 DFS は、深さの制約によってさらなる移動が停止されるまで、最も深い分岐をたどります。 これは、明示的な貪欲ロジックがなくても、アルゴリズムが自然に深い安全領域を好むことを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | テスト ケースあたり O(n) | DFS では各エッジが 1 回トラバースされ、深さの前処理は線形です。 
| スペース | O(n) | 隣接リスト、再帰スタック、深さ配列 |

 n 回のテストの合計は大きいものの線形であり、ライフ制約とフラッド制約に基づく枝刈りによる状態爆発が発生しないため、制約によりこれが可能になります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    def solve():
        n, st = map(int, input().split())
        w = [0] + list(map(int, input().split()))
        g = [[] for _ in range(n + 1)]
        for _ in range(n - 1):
            u, v = map(int, input().split())
            g[u].append(v)
            g[v].append(u)

        from collections import deque
        depth = [-1] * (n + 1)
        q = deque([1])
        depth[1] = 0
        while q:
            u = q.popleft()
            for v in g[u]:
                if depth[v] == -1:
                    depth[v] = depth[u] + 1
                    q.append(v)

        ans = 0
        sys.setrecursionlimit(10**7)

        def dfs(u, p, life, moves, d):
            nonlocal ans
            life += w[u]
            if life <= 0 or d > depth[u]:
                return
            ans = max(ans, moves)
            for v in g[u]:
                if v != p:
                    dfs(v, u, life, moves + 1, d + 1)

        dfs(st, -1, 1, 0, depth[st])
        return str(ans)

    t = int(input())
    out = []
    for _ in range(t):
        out.append(solve())
    return "\n".join(out)

assert run("1\n2 2\n1 1\n1 2\n") == "1", "simple move"
assert run("1\n2 2\n1 -1\n1 2\n") == "0", "immediate death"

 ## 特殊なケース

 A key edge case is when the starting node itself has a negative weight. In that case, the life update happens before any movement, so the process ends immediately. The DFS handles this correctly because it applies the weight before exploring children, so no recursive call is made.

 Another edge case is when a node becomes flooded exactly at the moment you arrive. Since the depth check uses a strict comparison, arriving at equal depth triggers termination. DFS 条件`cur_depth > depth[u]`問題のルールと正確に一致し、平等が死として扱われることを保証します。 

3 番目のエッジ ケースは、人生が正の値と負の値の間で揺れ動く深い経路です。 に基づいた剪定`life <= 0`パスが無効になるとそれ以上拡張されなくなり、交互の重みパターンでの指数関数的な分岐が防止されます。
