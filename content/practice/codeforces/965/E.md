 ## 解決策
 ## 問題の理解

 それぞれが変数名を表す、個別の小文字文字列のコレクションが与えられます。 元の名前ごとに、新しい短縮識別子として機能するその文字列の空でないプレフィックスを選択する必要があります。 制約は、すべての名前を短縮した後、結果として得られる 2 つの名前が同一であってはいけないということです。 

プレフィックスを選択する有効な方法の中で、選択したプレフィックスの長さの合計を最小にする方法が必要です。 

したがって、問題は一意のプレフィックスを見つけることだけではなく、それらのバランスをとることです。局所的には短いプレフィックスの方が常に優れていますが、それを選択すると、後で他の文字列に長いプレフィックスの使用を強制する可能性があります。 課題は、これらの競合をグローバルに解決して総コストを最小限に抑えることです。 

制約は厳しいです。 文字列は最大 100,000 個あり、すべての文字列の合計長も最大 100,000 です。これは、どのソリューションも、処理される合計文字数が線形または線形に近い必要があることを直ちに示唆しています。 完全な文字列をペアごとに繰り返し比較したり、各文字列のプレフィックスの一意性を最初から再計算したりしようとするものはすべて合格しません。 

単純なメンタル モデルは次のようになります。各文字列について、他の文字列で使用されていない最短のプレフィックスを試します。 問題は、「他の文字列によって使用されない」かどうかが他のすべての文字列の選択に依存するため、ローカルで貪欲な決定が失敗する可能性があることです。 

多くの文字列が長い共通のプレフィックスを共有しているが、後で分岐する場合、微妙な失敗例が発生します。 1 つの文字列が初期に非常に短いプレフィックスを使用すると、最初の文字列のプレフィックスをわずかに長くすると総コストが削減されるとしても、他の文字列を大幅に拡張する必要が生じる可能性があります。 たとえば:

 入力:```
3
aaa
aab
aac
```貪欲に割り当てると`"a"`最初の文字列に、残りの 2 つは必要になる場合があります`"aa"`またはそれ以上長くなると、総コストが不必要に増加します。 最適な割り当ては、独立した選択ではなく、集団の構造に依存します。 

重要な隠された構造は、一意性が共有プレフィックスによって完全に制御されるということであり、これはすべての文字列をプレフィックス ツリーに編成することを示唆しています。 

## アプローチ

 ブルートフォースのアイデアは単純です。 文字列ごとに、別の文字列で選択された接頭辞と一致しない接頭辞が見つかるまで、長さを増やしていきます。 これを適切にチェックするには、選択したプレフィックスのグローバル セットを維持し、それに対して各候補プレフィックスを検証する必要があります。 最悪の場合、長さ L の各文字列で O(L) 個のプレフィックスをチェックする必要があり、各チェックには文字列のハッシュ化または比較が含まれるため、全長で 2 次の動作が発生します。 全長が 100000 までになると、再スキャンを繰り返すと遅くなりすぎます。 

重要な観察点は、プレフィックスの競合は恣意的なものではなく、構造化されているということです。 2 つのプレフィックスが競合するのは、一方の文字列が別の文字列のプレフィックスである場合、またはプレフィックス ツリー内のパスを共有している場合のみです。 すべての文字列のトライを構築すると、すべてのプレフィックスがノードに対応し、一意性はそのノードを通過する文字列の数によって決まります。 

これは視点を逆転させることを示唆しています。 最短から最長まで貪欲にプレフィックスを割り当てるのではなく、必要性の観点から考えます。 トライ内のノードは、そのノードまでのパスがすべての文字列の中で一意であるか、他の文字列をさらに下にプッシュすることで一意にできる場合にのみ、文字列の有効な候補となります。 コストの最小化は、トライに対する動的プログラミングの解釈を自然に示唆します。つまり、2 つの文字列が同じノードで停止しないように、各文字列にトライの停止点を割り当てます。 

この構造はツリー DP 問題になります。 各ノードは、通過する文字列の数を認識しており、一意性を強制するために、そのうちのいくつが下方に継続する必要があるかを決定します。 私たちが支払うコストは、各弦が止まる深さに比例します。 全体の深さの増加を最小限に抑える方法で、「余分な」弦を下に押し込みます。 

ノードへの文字列のフローのような割り当てを伴うトライとしてみなされると、最適な戦略は貪欲なボトムアップになります。各ノードで、できるだけ多くの文字列をここで停止させておき、残りの文字列を子にプッシュします。

 | --- | --- | --- | --- |
 | ブルート フォース プレフィックス チェック | O(N * L^2) | O(N * L) | 遅すぎる |
 | トライ + ボトムアップ割り当て | O(全長) | O(全長) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべての文字列のトライを構築します。各ノードはプレフィックスに対応し、通過する文字列の数を格納します。 次に、葉から上に向かって割り当て問題を解決します。

1. すべての文字列をトライに挿入し、訪問したノードごとにカウンターをインクリメントします。 このカウンターは、このプレフィックスを共有する文字列の数を表します。 これは、プレフィックスが安全に使用できるかどうかを判断する基本的な情報です。 
2. トライの事後探索を定義します。 上位で何が起こるかを決定する前に、より深いプレフィックスに関する決定が最終決定されるように、親よりも先に子を処理します。 
3. 各ノードで、まだ「未割り当て」であり、現在このサブツリーに存在する文字列の数を表す値を維持します。 リーフ パスの場合、これは、そこで終了する文字列または通過する文字列の数として開始されます。 
4. 特定のノードについて、最初にすべての子から貢献を収集します。 これらは、下位でプレフィックスが割り当てられていない文字列を表しており、ここまたは上で引き続き割り当てることができます。 
5. 複数の文字列が同じノードに到達する場合、それ以上停止すると一意性に違反するため、ここで安全に停止できるのは 1 つまでです。 したがって、このノードが存在する場合は、このノードで停止する文字列を 1 つだけ割り当てます。 
6. このノードにある残りの文字列はすべて上に押し上げる必要があります。 ただし、ボトムアップで処理を行っているため、上に押し上げることは、超過したカウントを親に返すことと同じです。 
7. ノードで停止する文字列を割り当てるたびに、そのノードの深さが合計の答えに追加されます。 これは、その文字列に対して選択されたプレフィックスの長さを反映します。 
8. ルートは残りの文字列をすべて蓄積し、すべての文字列がどこかに割り当てられるようにします。 

重要な考え方は、すべての文字列が、プレフィックスを一意に「要求」できる可能な限り最上位のノードに割り当てられますが、競合はサブツリー内でローカルに解決されるということです。 

### なぜ効果があるのか

 trie は文字列を接頭辞によって分割します。 どのノードでも、そのサブツリー内のすべての文字列は、そのプレフィックスまでは区別できません。 複数の文字列が同じノードで停止しようとすると、一意性が損なわれるため、そこに割り当てることができるのは最大でも 1 つだけです。 他の課題はさらに深く掘り下げる必要があります。 

ボトムアップ処理により、より深いレベルに割り当てられた可能性のある文字列が、より高いレベルを検討する前にすでに最適に配置されていることが保証されます。 これにより、より深い固有の機会が最初に解決されるため、浅い深さでの時期尚早な割り当てが防止されます。 不変条件は、ノードを処理するときに、すべての子がより深い深さで割り当てられた文字列の数をすでに最大化しているため、残りの文字列はこのノード以上を使用することを強制され、ここで 1 つの割り当てを選択すると、すべての同等の選択肢の中で合計の深さが最小化されるということです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

class Node:
    __slots__ = ("ch", "cnt")
    def __init__(self):
        self.ch = [-1] * 26
        self.cnt = 0

def new_node():
    return Node()

nodes = [new_node()]

def add_string(s):
    v = 0
    nodes[v].cnt += 1
    for c in s:
        x = ord(c) - 97
        if nodes[v].ch[x] == -1:
            nodes[v].ch[x] = len(nodes)
            nodes.append(new_node())
        v = nodes[v].ch[x]
        nodes[v].cnt += 1

def dfs(v, depth):
    res = 0
    rem = nodes[v].cnt

    for nx in nodes[v].ch:
        if nx != -1:
            got_res, got_rem = dfs(nx, depth + 1)
            res += got_res
            rem -= (nodes[nx].cnt - got_rem)

    if rem > 0:
        res += depth
        rem -= 1

    return res, rem

n = int(input())
words = [input().strip() for _ in range(n)]

for w in words:
    add_string(w)

ans, _ = dfs(0, 0)
print(ans)
```トライ構造は標準です。各ノードは通過する文字列の数を追跡し、後でそのプレフィックスを求めて競合する候補の数を決定します。 

DFS は 2 つの値を計算します。そのサブツリー内で割り当てられたプレフィックスによって寄与される合計コストと、未割り当てのままでツリーの上位で処理する必要がある文字列の数です。 ループ内の減算ステップにより、子サブツリーにすでに割り当てられている文字列が削除され、親には残った競合のみが表示されるようになります。 

微妙な実装の詳細は、子の処理後にのみ現在のノードでコストを割り当てることです。 これにより、1 つの文字列を除くすべての文字列に対してより深い割り当てが不可能な場合にのみ、ここでプレフィックスを割り当てることが保証されます。
