 ## 解決策
 ## 問題の理解

 2 つのチームが与えられ、それぞれのチームは、スキル値が連続する整数セグメントを形成するすべてのアスリートで構成されます。 モンランドには以下のスキルがあります$l_M$に$r_M$、Berland は以下のスキルを持っています。$l_B$に$r_B$。 モンランド出身の特別なアスリート、スキルのある選手$l_M$、Monocarp として固定されます。 

各試合ではモンランドの選手が 2 名、ベルランドの選手が 2 名ずつ使用され、試合をまたがって選手を再利用することはできません。 Monocarp が関係するすべての試合では、Monland の別のプレーヤー 1 名とペアにする必要があり、Monland の別のプレーヤー 2 名と対戦する必要があります。 モンランドの 2 つのスキルの合計がベルランドの 2 つのスキルの合計以上である場合、試合はモノカープ側の勝利とみなされます。 

私たちは、試合間でプレイヤーを再利用しないという制限の下で、Monocarp が参加できる勝利試合の数を最大化したいと考えています。 

入力の構造は、生のサイズよりも重要です。 範囲は最大で$10^9$, しかし、各チームは単純なインターバルです。 これにより、プレーヤーを列挙したり、試合を直接シミュレートしようとするソリューションは即座に除外されます。 すべては、テスト ケースごとに定数または対数の作業を伴う区間演算と貪欲なペアリング ロジックの観点から表現する必要があります。 

微妙な問題は、Monocarp が常に最も弱い Monland プレイヤーであることです。 彼の貢献は固定されているため、これにより彼が関与するすべての試合が制限されるため、唯一の柔軟性は彼のパートナーを選択し、対戦相手のペアを選択することです。 

もう 1 つの明白ではない点は、リソースの消費を除いて、一致は独立しているということです。 強力な組み合わせが使用されると、それらのアスリートはいなくなります。 早い段階で貪欲なミスをすると、将来のより強力な試合が妨げられる可能性があります。 

素朴な推論を打ち破ることが多いエッジケース:

 たとえば、モンランドが全体的にベルランドよりも厳密に弱い場合、$l_M=10, r_M=13$そして$l_B=11, r_B=15$の場合、非常に特定の組み合わせのみが可能となり、多くのプレイヤーが存在するにもかかわらず 1 つの一致のみが機能する場合があります。 

たとえば、ベルランドが完全に弱かった場合、$l_B=1, r_B=2000$モンランドが高い間、すべてのペアが機能し、答えはモンランドが形成できる素のペアの数によって純粋に制限されます。 

主な落とし穴は、Monocarp を可能な限り最も強力なチームメイトと常にペアにする必要があると想定していることです。 そうなると、将来の強力な対戦相手のペアに対抗するために必要な強力な選手が無駄になる可能性があります。 

## アプローチ

 強引な解釈では、Monocarp のパートナーを明示的に選択し、次に 2 人の対戦相手を選択し、それらのプレイヤーを削除して再帰しようとします。 各試合には、大まかに次のものがあります。$O(n^3)$モンランドから 1 人のパートナーを選択し、ベルランドから 2 人の対戦相手を選択するため、選択肢の組み合わせになります。 複数の試合では、試合ごとにプールが減り、将来の選択が以前の選択に依存するため、これは組み合わせ的に急速に爆発します。 

このアプローチは、すべての制約を尊重するため、原理的には正しいですが、状態空間が膨大であり、各一致での決定が独立していないため、すぐに失敗します。 

重要な観察は、ペアに関する唯一の関連情報はその合計であるということです。 両方のチームが連続した整数範囲であるため、ペアの合計も非常に構造化された間隔を形成します。 個々のプレーヤーについて考える代わりに、利用可能なペアの合計について考えることができます。 

モノカープのスキルは固定です$l_M$。 選んだパートナーにとって$x$Monland から、Monland ペアの合計は次のようになります。$l_M + x$。 プレーヤーを再利用できないため、パートナーの各選択は、プレーヤーからの異なる値を 1 つだけ消費します。$(l_M+1, r_M]$。 

同様に、各試合では 2 人の異なるベルランド プレーヤーが消費され、ベルランドの範囲からペアの合計が形成されます。 自然な戦略は、実現可能性に応じて、利用可能な最小のモンランド ペアの合計と最大の利用可能なベルランド ペアの合計を一致させ、またはその逆を行い、柔軟性を確保することです。 

問題は、ソートされた 2 つのペア合計のマルチセット間で成功した素のペア比較の数を最大化することに帰着します。 基礎となるセットは両方とも間隔であるため、2 つのポインターを使用してこれを貪欲にシミュレートできます。 

私たちは以下を効果的に構築します。 

- モンランドで利用できるパートナースキル:$l_M+1 \dots r_M$- ベルランドが利用できるスキル:$l_B \dots r_B$各試合ではパートナー 1 名と対戦相手 2 名が消費されます。 最適な戦略は、Monocarp と選択したパートナーの組み合わせになります。$x$、そして満足するように対戦相手を最適に組み合わせます。$$l_M + x \ge y + z$$マッチを最大化するために、強い Berland ペアを不必要に無駄にしないようにしながら、実行可能な最も弱い構成から開始してマッチを満たすよう貪欲に試みます。 

これにより、ペアの合計のソートされたリストに対する 2 ポインターの貪欲な動作が発生しますが、シーケンスが連続しているため、明示的なシミュレーションを行わなくても、閉じた形式のペアリングの動作を導き出すことができます。

 ## アルゴリズムのチュートリアル

 できるだけ多くの有効な一致を形成するという観点から問題を書き直します。各一致では、Monland の 1 つの要素 (Monocarp を除く) と Berland の 2 つの要素が消費されます。 

1. 利用可能な Monland パートナーの数を計算します。$A = r_M - l_M$。 これは、Monocarp の可能な個別のチームメイトの数です。 各試合ではそのようなパートナーを 1 つだけ使用するため、答えは次の値を超えることはできません$A$。 
2. 存在する Berland プレーヤーの数を計算します。$B = r_B - l_B + 1$。 各試合で 2 人のベルランド選手が消費されるため、答えは次の値を超えることはできません$\lfloor B/2 \rfloor$。 
3. 残る唯一の制約は、スキルの合計の観点から試合が可能かどうかです。 考えられる最も弱いモンランドのペアは次のとおりです。$l_M + (l_M+1)$。 一番強いのは、$l_M + r_M$。 同様に、ベルランドペアの合計の範囲は次のとおりです。$l_B + (l_B+1)$に$r_B + (r_B-1)$。 
4. 実現可能性のボトルネックは、リソースを消費するときに、残りの最も強いモンランド ペアと最も弱いベルランド ペアの間で少なくとも 1 つの有効なペアを常に形成できるかどうかによって決まります。 両者は連続した間隔であるため、考えられる最も強いモンランドのペアが最も弱いベルランドのペアよりも依然として弱い場合、試合はまったく不可能になります。 
5. 少なくとも 1 つの一致が可能であれば、極端な値を貪欲に消費しながら不平等を満たすためにいつでもペアの順序を変更できるため、リソースの制限を超える追加の構造的制約が発生することはありません。 インターバル構造により、未使用の強力なプレーヤーが不可能な試合を強いられる「デッドコンフィギュレーション」が発生しないことが保証されます。 
6. したがって、一致の最大数は、単に 2 つのリソース境界の最小値になります。$$\min(A, \lfloor B/2 \rfloor)$$少なくとも 1 つの有効なペアが存在することが条件です。 最強のモンランドペアでも最弱のベルランドペアに勝てない場合、答えはゼロになります。 

### なぜ効果があるのか

 重要な不変条件は、両方のチームをソートした後、モンランドのペアが利用可能な最も強いものから必要な最も弱いものまでマッチングされ、バーランドのペアが利用可能な最も弱いものから順に消費されるという最適な戦略に変換できることです。 両方のサイドが隣接しているため、サイド内でパートナーを交換しても実現可能性が低下することはなく、一致可能性が向上または維持されるだけです。 この交換の議論により、個々の構成を追跡する必要がなくなり、問題は容量の制約と 1 回の実現可能性チェックに軽減されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        lM, rM = map(int, input().split())
        lB, rB = map(int, input().split())

        # Monocarp is lM, must choose partner from (lM+1 ... rM)
        A = max(0, rM - lM)

        # total Berland players
        B = rB - lB + 1

        # smallest possible Monland pair sum
        min_M = lM + (lM + 1)

        # largest possible Berland pair sum
        max_B = rB + (rB - 1)

        if A <= 0:
            out.append("0")
            continue

        # feasibility check: can any match be won?
        if min_M > max_B:
            out.append("0")
            continue

        ans = min(A, B // 2)
        out.append(str(ans))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装では、導出された容量制約を直接エンコードします。 変数`A`counts how many distinct teammates Monocarp can use, which caps the number of matches. 変数`B // 2`各試合で 2 人のベルランド選手が消費されることを反映しています。 実現可能性チェックでは、考えられる最も弱いモンランド ペアと最も強いベルランド ペアを比較します。 それさえ失敗すると、構成は成功しません。 

微妙な詳細が次のような場合に対処します。$r_M = l_M$。 その状況では、Monocarp には利用可能なパートナーがいないため、試合を形成することができません。`A`早期にゼロにクランプされます。

 ## 特殊なケース

 Monland に Monocarp のみが含まれる場合、次の計算は$A$がゼロになると、アルゴリズムはただちにゼロの一致を返します。 これは、2 人でモンランド チームを結成できないという事実と一致します。 

ベルランドのプレイヤーが 2 人未満の場合、$B//2$はゼロであるため、モンランドが非常に強い場合でも、各ゲームには 2 人の対戦相手が必要なため、構造的に試合は不可能です。 

Monland が非常に弱いにもかかわらず、まだ多くのパートナーがいる場合、不平等チェックによって実現可能性が失敗し、アルゴリズムは容量のみに基づいて過剰カウントを正しく回避します。 

両方の範囲が大きく重複している場合、実現可能性は自明に満たされ、答えはリソースのペアによって厳密に支配され、min 式はそれを正確に捕捉します。
