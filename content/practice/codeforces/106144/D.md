 ## 問題の理解

 私たちは、Monocarp の季節を通しての食事スケジュールをシミュレーションしています。$n$日々。 ある日、彼は市場を訪れ、グーズベリーの「バッチ」を購入します。 各バッチには 2 つのパラメータがあります: 期間$a_i$、つまり、その日に購入した場合$i$彼は次もそれを食べ続けるだろう$a_i$連続した日数と毎日の幸福値$b_i$つまり、バッチがアクティブである間、毎日利益が得られます$b_i$幸せ。 

重要な制限は、バッチが時間的に重複できないことです。 Monocarp が日にバッチを購入したら$i$、彼は昼まで忙しいです$i + a_i - 1$、次に購入できるのはちょうどその日です$i + a_i$。 アクティブなバッチがない日に何も買わなければ、その日の幸福度はゼロになります。 

フルシーズンが固定された後、配列を取得します。$h_1, h_2, \dots, h_n$毎日が次のいずれかに貢献します$b_i$(アクティブなバッチによってカバーされている場合)、そうでない場合はゼロ。 

プランのスコアは、やや間接的な方法で計算されます。 あらゆる長さに対して、$m$ウィンドウ内で幸福の合計を計算し、そのようなウィンドウすべてで最小値を取得します。 目標は、この最小スライディング ウィンドウの合計が最大になるようにバッチの開始日を選択することです。 

制約$n \le 2 \cdot 10^5$すべてのテスト ケースにわたって、テスト ケースごとに線形または線形に近いものが必要であることが強く示唆されています。 ネストされた方法でウィンドウごとまたは開始構成ごとに寄与を再計算するアプローチは遅すぎます。 

明らかではない問題は、1 回の購入が間隔全体に影響を及ぼし、各ウィンドウの合計が重複する間隔を集計することです。 たとえ開始位置が制限されていても、有効なシーケンスの数は依然として指数関数的であるため、素朴な「すべての有効な購入スケジュールを試す」はすぐに爆発します。$n$。 

貪欲な配置が将来のウィンドウを無視する場合、微妙な失敗例が発生します。 たとえば、次の場合$m$が小さく、非常に長く高価値のバッチを早い段階で配置すると、初期のウィンドウが膨らむ可能性がありますが、その後のギャップが残り、一部のウィンドウがゼロになります。 そのため、貪欲な戦略は真の最小値を過大評価することになります。 

もう 1 つの落とし穴は、最良の答えが累積幸福度の最大化に対応すると仮定することです。 目標は合計ではなく最小ウィンドウのみに依存するため、これは不正確です。 

## アプローチ

 ブルートフォース解釈では、バッチ開始日の可能なすべての有効なシーケンスを選択し、結果の配列をシミュレートします。$h$、すべてのスライディング ウィンドウの合計を計算し、最良の最小値を取得します。 これは正しいですが、有効なスケジュールの数は組み合わせによって増加するため、不可能です。 制約の下で毎日が選択またはスキップされた場合でも、依存関係は「次の日までスキップします」$i + a_i$」により、列挙は依然として指数関数的に行われます。 

重要な観察は、目的がローカル ウィンドウのサイズの合計にのみ依存するということです。$m$、各バッチは均一の値に寄与します。$b_i$連続セグメント全体にわたって。 これにより、問題はライン上のカバレッジの制御に変わり、選択された各間隔によって一定の密度が追加されます。 難しいのは、全長にわたって最小カバレッジを最大化するために、重複しない間隔を選択することです。$m$窓。 

これは、時間の経過とともにカバレッジ関数を維持し、あらゆる長さのウィンドウを保証するものとして再構成できます。$m$十分な貢献が蓄積されます。 時間をかけて推論する代わりに、赤字について推論することができます。ウィンドウが小さすぎる場合は、それをカバーするのに十分な高い値の間隔が配置されていることを確認する必要があります。 

「すべてのスライディング ウィンドウの最小値」制約を処理する標準的な方法は、差分配列でカバレッジを維持し、ウィンドウ境界で制約を強制することです。 各間隔は高さの長方形に寄与します$b_i$そしてタスクは、すべての長さになるように間隔を選択することになります。$m$セグメントは少なくとも一定の合計高さを受け取ります。 

答えは二分探索できます$p$そして、毎日をすべての長さでカバーできるようなスケジュールを立てることができるかどうかを尋ねます。$m$合計は少なくとも$p$。 固定の場合$p$、どこでも十分な密度を確保するだけで十分です。 これは、貪欲な実現可能性の問題になります。左から右にスキャンし、その位置でカバレッジが不十分な場合は常にスキャンします。$i$、将来の十分なカバレッジに貢献するバッチを開始する必要があります。 

強制的な決定の構造により、貪欲な決定論が可能になります。ポジションに赤字が現れると、$i$、有効なソリューションでは、 以降で開始される十分なバッチを導入する必要があります。$i$まだ影響を及ぼしている$i$将来のバッチでは、過去のカバーされていないウィンドウを遡及的に修正できないためです。

 ## アルゴリズムのチュートリアル

 答えを値として扱います$p$、次にそれが達成可能かどうかを確認し、最後に実現可能な最大値に合わせて有効なスケジュールを再構築します。 

1.二分探索をします$p$、保証したい最小スライディング ウィンドウの合計。 これはうまくいきます。なぜなら、ある程度のことを達成できれば、$p$、制約を緩和することで、より小さな値を達成することもできます。 
2. 固定の場合$p$では、差分配列を使用して、毎日どのくらいのカバレッジが現在アクティブであるかを追跡する配列を維持します。 これにより、間隔の寄与を効率的にシミュレートできるようになります。 
3. 日を左から右にスキャンし、その日の現在の累積幸福度を計算します。$i$。 この位置以降で終了するすべてのウィンドウに対して現在の値がすでに十分である場合は、何も行いません。 
4. もしもその日$i$すべての長さのウィンドウをサポートするために必要なものに比べて十分にカバーされていません$m$をカバーするバッチを開始する必要があります。$i$。 可能な限り早い日に開始され、まだカバーできるバッチを選択します。$i$、前のバッチが終了する前に新しいバッチを開始できないという制約を尊重します。 
5. この時点で開始できるすべての有効なバッチの中から 1 つを貪欲に選択し、差分配列を使用してそのすべての寄与を適用し、そのアクティブな範囲をマークし、次の方法で将来のカバレッジを増やします。$b_i$1日あたり。 
6. このプロセスを最後まで続けます。 どこかの時点で赤字を修正するための有効なバッチが見つからない場合、ターゲットは$p$不可能です。 
7. 二分探索の後、もう一度構築を再実行して、選択した実際の日数を出力します。 

重要な点は、各強制配置がローカルで正当化されることです。$i$が小さすぎると、今後のバッチでその合計を増やすことができないため、これを修正する唯一の方法は、すでにそのウィンドウにまたがるカバレッジを導入することです。 

### なぜ効果があるのか

 どの位置でも$i$、アルゴリズムにより、次で終わるすべてのウィンドウが保証されます。$i$選択したバッチからの十分な累積寄与がある。 必要なバッチを延期すると、一部のウィンドウが永久に満たされないままになるため、貪欲なステップが強制されます。 各バッチは連続した間隔に影響し、期間が固定されているため、すべての決定は適用範囲を前方にのみ拡張し、後方には拡張しないため、ローカル修正はグローバルに有効なままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check(n, m, a, b, target):
    # difference array for active happiness
    diff = [0] * (n + 3)
    cur = 0
    active_until = 0

    chosen = []
    i = 1

    for i in range(1, n + 1):
        cur += diff[i]

        # compute sliding window ending at i
        if i >= m:
            window_start = i - m + 1

            # if coverage at window start is insufficient, we must start a batch
            if cur < target:
                # find a batch we can start at window_start or earlier
                # and that can still be started now (respecting cooldown)
                best = -1

                for j in range(window_start, i + 1):
                    if j >= active_until:
                        best = j
                        break

                if best == -1:
                    return False, []

                idx = best
                chosen.append(idx)

                active_until = idx + a[idx - 1]

                diff[idx] += b[idx - 1]
                diff[active_until] -= b[idx - 1]
                cur += b[idx - 1]

        # enforce decay of diff implicitly
        # (handled by diff array only)

    return True, chosen

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n, m = map(int, input().split())
        a = list(map(int, input().split()))
        b = list(map(int, input().split()))

        lo, hi = 0, sum(b)

        best_plan = []
        best_val = 0

        while lo <= hi:
            mid = (lo + hi) // 2
            ok, plan = check(n, m, a, b, mid)

            if ok:
                best_val = mid
                best_plan = plan
                lo = mid + 1
            else:
                hi = mid - 1

        out.append(str(best_val) + " " + str(len(best_plan)))
        out.append(" ".join(map(str, best_plan)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、実現可能性のチェックと二分探索による最適化が分離されています。 差分配列は、ウィンドウ全体の合計の再計算を防ぐ中心的なメカニズムです。 変数`active_until`バッチが重複できないという制約を強制します。そうしないと、貪欲なステップによって間隔が不正にスタックされる可能性があるため、これは不可欠です。 

貪欲スキャンにより、実行中の寄与が不十分な場合は必ず、現在のウィンドウに影響を与える最も早い実行可能な位置にバッチが即座に挿入されます。 この順序により、いずれにせよ過去のウィンドウには役立たない将来の機会を逃すことがなくなります。

 ## 特殊なケース

 重大なエッジケースは、非常に大規模な場合に発生します。$a_i$早期に存在し、中程度の$b_i$、遅い日はもっと高くなります$b_i$ただし期間は短くなります。 素朴な価値に貪欲なアプローチでは、後半の高値を選択することになります$b_i$そして、初期の長いカバレッジが多くのウィンドウを安定させるという事実を見逃しています。 

もう 1 つのエッジケースは次のような場合です$m = 1$。 ここで問題は、最小日次値の最大化に帰着します。これにより、ウィンドウ推論ではなく継続的なカバレッジが強制されます。 毎日がウィンドウ制約となるため、アルゴリズムは引き続きこの問題を処理します。そのため、カバーされていない日があるとすぐに強制バッチ配置がトリガーされます。 

3 番目のケースは、すべてが$a_i$まさに$m$。 次に、各バッチがウィンドウ サイズと完全に一致し、最適な戦略は、ローカルの寄与を最大化する互いに素なセグメントを選択することになります。 すべての配置がウィンドウ ブロックに直接対応し、重複の曖昧さが存在しないため、貪欲スキャンは自然にこの構造に一致します。
