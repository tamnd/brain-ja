 ## 解決策
 ## 問題の理解

 戦場のセルの行を表すバイナリ文字列が与えられます。 各セルは空であるか、敵が含まれています。 目標は、2 種類のアクションを使用してすべての敵を排除することです。 落雷は、選ばれた敵を 1 人だけ除去します。 火の玉は、選択した 1 人の敵を除去し、隣接する敵が存在する場合はその敵も除去します。 制限は、プロセス全体で使用できる火の玉は最大 1 つですが、稲妻は何度でも使用できるということです。 

タスクは、すべての敵を排除するために必要なアクションの総数を最小限に抑えることです。 各敵は、雷によって直接、または火の玉効果によって間接的に除去されなければなりません。 

重要な問題は、単一の火の玉を使用するかどうか、またどこに使用するかを決定することです。これは、その効果が局所構造に大きく依存するためです。 最大 3 人の連続した敵を除去できる可能性がありますが、敵がまばらな地域と重なる場合は配置が無駄になる可能性もあります。 

この制約により、テスト ケース全体の長さの合計は 3·10^5 までとなります。 これは、ケースごとに O(n^2) スキャンを実行すると、最悪のケースでは約 10^10 の演算にまで縮退してしまい、これは実行不可能であるため、ソリューションはテスト ケースごとに線形または線形に近いものでなければならないことを直ちに意味します。 

単純な考えは、火の玉のあらゆる可能な位置を試して、残っている敵の数を再計算することです。 これにより、文字列が繰り返しスキャンされ、O(n^2) の動作が得られます。 もう 1 つの単純なアプローチは、火の玉の配置を考慮せずに左から右へ貪欲に削除することですが、最適な火の玉の位置は局所的な密度だけでなく全体的な構造に依存するため、これは失敗します。 

いくつかの特殊なケースでは、構造が明確に明らかになります。 

文字列がすべてゼロの場合、アクションは必要ないため、答えはゼロになります。 

たとえば、文字列がすべて 1 の場合、`11111`、稲妻のみの戦略には 5 つのアクションが必要です。 位置 3 に配置された 1 つの火の玉は、境界を慎重に考慮した場合にのみ 5 つすべてを削除しますが、実際には最大 3 つを削除し、さらに 2 つを残すため、最適な答えは 1 つや 2 つではなく、3 つのアクションになります。 

敵が孤立している場合`10101`、火の玉は、複数の分離されたものをカバーする配置がないため、ほとんど役に立ちません。 中央に配置してオーバーラップを減らす場合、最適な稲妻は 5 つまたはわずかに少なくなりますが、ゲインは最小限です。 

これらのケースは、火の玉が密集した連続したセグメントでのみ有効であり、その最大の効果は常に、単一の連続したブロック内で火の玉を適用することによって得られることを示唆しています。 

## アプローチ

 火の玉の制約を無視すれば、問題は簡単です。各敵には 1 つの稲妻が必要なので、答えは単に 1 の数です。 

単一の火の玉を導入すると、1 回の操作で最大 3 人の連続する敵の集団を排除できるため、状況が変わります。 さらに重要なのは、局所的な密度を減らすことで、連続したブロック全体での節約を統合できることです。 

ブルートフォースアプローチは、s[i] = '1' である各インデックス i を火の玉の中心として試すことです。 このような選択ごとに、i とその近傍の削除をシミュレートし、残りの i を数えます。 この再計算には O(n) のコストがかかり、すべての候補に対してそれを実行すると O(n^2) が得られます。 

重要な観察は、文字列が連続するブロックの独立したブロックに分解されることです。 ゼロはコンポーネントを分離し、ブロック間の相互作用を防ぐため、火の玉は単一のブロックにのみ意味のある影響を与えます。 長さ k のブロック内で、火の玉がなければ k 個の稲妻が必要です。 火の玉が 1 つあれば、必要なアクションの数が最大 2 つ減ります。これは、3 つの別々の稲妻ではなく、1 回のアクションで 3 つの連続した火の玉を除去することが最善の結果となるためです。 

したがって、問題全体は、火の玉を配置することで最大の削減が得られる連続セグメントを見つけることに帰着します。 長さ k のブロックでは、k ≥ 1 の場合ゲインはちょうど 1、k ≥ 3 の場合は 2 になります。また、隣接関係のオーバーラップによって火の玉ごとに 3 つを超える異なるものを削除できないため、3 は不可能です。 

世界中で許可されている火の玉は 1 つだけなので、保存された稲妻を最大化できる最適なブロックが必要です。 ただし、グローバル最適戦略はさらに簡素化されます。明示的にブロックを選択する必要はなく、合計を計算して、最大で 2 である可能な限りの節約を差し引くだけです。 

より正確には、最適な節約は、ブロック内で 3 つの連続するパターンを見つけることによって達成されます。 そのようなパターンが存在する場合、2 つの操作が節約されます。 そのようなパターンは存在しないが、隣接するパターンのペアが少なくとも 1 つ存在する場合は、1 を保存します。そうでない場合は、何も保存できません。 

これにより、問題は文字列を 1 回スキャンするだけで済みます。

 | --- | --- | --- | --- |
 | ブルートフォース火の玉の位置 | O(n^2) | お(1) | 遅すぎる |
 | ブロックをスキャンして最適なゲインを計算する | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列を処理し、1 の合計数、連続する 1 のペアが存在するかどうか、および連続した 1 が 3 つ存在するかどうかという 3 つの値を追跡します。 

1. 文字列内の 1 の合計数を数えます。 これは、雷攻撃のみを使用する場合の基本コストです。 
2. 文字列を左から右にスキャンし、1 が連続して実行されているかどうかを確認します。 私たちが見るたびに`s[i] = s[i-1] = '1'`、火の玉は 2 つの別々の稲妻よりも効率的に少なくとも 2 つの隣接する敵を排除できるため、少なくとも 1 の節約が可能であるとマークします。 
3. 会うたびに`s[i] = s[i-1] = s[i-2] = '1'`、単一の火の玉が 3 つの別々の雷攻撃を置き換えることができるため、2 というより強力なセービングが可能であることをマークします。 
4. スキャン後、達成可能な最適な保存方法を決定します。 トリプルがどこかに存在する場合、保存は 2 です。それ以外の場合、ペアが存在する場合、保存は 1 です。それ以外の場合、保存は 0 です。 
5. total_ones から保存を差し引いた値を出力します。 

これが機能する理由は、火の玉は常に最大 3 つの位置の連続した領域に影響を及ぼし、唯一の有意義な改善は複数の連続する稲妻を置き換えることから得られるためです。 単一の火の玉は 3 つ以上の位置をカバーできないため、実行が長くても、これらの場合を超えて火の玉あたりの効率は向上しません。 

### なぜ効果があるのか

 このアルゴリズムは、単一の火の玉の利点がローカルの隣接構造によって完全に決定されるという事実に基づいています。 すべての最適な配置は、連続した配置内の構成に還元できます。 このような実行では、可能な限り最大の改善は、火の玉の位置を中心にどれだけ連続して実行できるかによって制限されます。 これにより、グローバル最適化問題が定数因子のローカル パターン検索に制限され、これらのパターン以外の構成ではより良い改善が得られないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n = int(input())
    s = input().strip()

    ones = s.count('1')

    best = 0

    for i in range(n):
        if s[i] == '1':
            if i > 0 and s[i-1] == '1':
                best = max(best, 1)
            if i > 1 and s[i-1] == '1' and s[i-2] == '1':
                best = 2

    print(ones - best)
```通常、各敵には落雷が必要となるため、解決策はすべての敵を数えることから始まります。 変数`best`単一の火の玉を使用してこのコストをどれだけ削減できるかを追跡します。 

スキャン中に、隣接パターンが検出されます。 連続するもののペアにより、少なくとも 1 つの火の玉が 2 つの稲妻を 1 つの火の玉と他の場所に残った 1 つの稲妻に置き換えることで 1 回の操作を節約できることが保証されます。 3 つの隣接する敵を 3 つの別々の稲妻の代わりに 1 つの火の玉に置き換えることができるため、1 の 3 つにより最大 2 つの節約が保証されます。 

この実装では単純な左から右へのスキャンが使用されており、トリプルが見つかった瞬間に安全に設定できます。`best = 2`なぜなら、この改善を超える構成は存在できないからです。 

インデックス i-2 は有効な場合にのみアクセスする必要があるため、境界には注意が必要です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各文字はテスト ケースごとに 1 回処理されます。 
| スペース | お(1) | カウンタとフラグのみが保存されます。 

すべてのテスト ケースにわたる全長の制約は 3·10^5 であるため、テスト ケースごとに 1 回の線形スキャンは制限内に問題なく収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n = int(input())
        s = input().strip()

        ones = s.count('1')
        best = 0

        for i in range(n):
            if s[i] == '1':
                if i > 0 and s[i-1] == '1':
                    best = max(best, 1)
                if i > 1 and s[i-1] == '1' and s[i-2] == '1':
                    best = 2

        out.append(str(ones - best))

    return "\n".join(out)

# edge: no enemies
assert run("1\n5\n00000\n") == "0"

# edge: all ones small
assert run("1\n3\n111\n") == "1"

# edge: separated ones
assert run("1\n5\n10101\n") == "5"

# edge: mixed blocks
assert run("1\n6\n110111\n") == "2"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 00000 | 0 | 操作は必要ありません |
 | 111 | 1 | ファイアボールの最大のメリット |
 | 10101 | 5 | 隣接メリットなし |
 | 110111 | 2 | トリプル節約の混合ブロック |

 ## 特殊なケース

 のような文字列の場合`00000`の場合、アルゴリズムはすぐにゼロの 1 をカウントし、隣接条件をトリガーしません。 保存はできないため、出力は正確にゼロになります。 

のために`111`、スキャンではペアとトリプルの両方が検出されます。 インデックス 2 では、トリプル条件の最適値が 2 に設定され、答え 1 が得られます。これは、3 つの稲妻を 1 つの火の玉に置き換え、そのセグメントに敵が残っていないことに対応します。 

のために`10101`、隣接するものは存在しないため、最良はゼロのままです。 すべての敵は孤立しており、それぞれに個別の稲妻が必要です。 

のために`110111`、最初のブロックはペアを提供し、2 番目のブロックはトリプルを提供するため、最良は 2 になります。アルゴリズムは、最大の圧縮が得られる場所にのみファイアボールを正しく適用します。利用可能なファイアボールは 1 つだけであるため、ブロックが別々であることは無視されます。
