 ## 解決策
 ## 問題の理解

 2 つの非常に特殊な削除ルールの下で縮小できる配列が与えられています。 最初のルールでは、配列内に現在存在する最小値を 1 つだけ削除することができ、複数の位置にその最小値が含まれている場合、どれを消すかを自由に選択できます。 2 番目のルールはより構造化されています。配列が現在 2 つの等しい値で始まっている場合、それらの両方を一度に削除できます。 

目標は、できるだけ少ない操作で配列を完全に消去することです。 各操作は長さを短縮しますが、効果は非対称です。1 つのルールはグローバル最小セットから選択された 1 つの要素のみを削除し、もう 1 つのルールは先頭の固定隣接ペアを削除しますが、これらの 2 つの要素が一致する場合に限ります。 

すべてのテスト ケースの合計サイズが最大 2·10^5 であるという制約は、テスト スイートごとに線形に近い、または線形算術的なソリューションが必要であることを意味します。 ネストされたスキャンを使用して動的配列の削除を繰り返しシミュレートするアプローチは、特に単純なループで「最小値の検索」または「プレフィックスの等価性のチェック」操作を繰り返すと O(n^2) に向かって劣化するため、遅すぎます。 

プレフィックス操作が最小要素の削除とどのように相互作用するかに微妙な問題が生じます。 最小値を削除すると、以前はその最小値によって分離されていた新しい隣接する等しいペアが露出する可能性があります。 可能な限り常にプレフィックス操作を適用する素朴な貪欲な戦略は、特定の最小値を早期に削除すると、将来の複数のペアの削除のロックが解除される可能性があることを無視すると、失敗する可能性があります。 

たとえば、[2, 1, 1, 2] のような配列を考えてみましょう。 中央から最小の 1 を熱心に削除すると、後でペアの削除を 2 回適用する機会が妨げられる可能性があります。 最適な戦略は、ペアがカスケードできるように構造を保持するかどうかに依存します。 

もう 1 つのエッジ状況は、[3, 3, 2, 2, 1, 1] のように、配列がすでに完全に隣接する等しいペアで構成されている場合です。 ここで、最適なプレイは不必要な単一の削除を完全に回避し、ペアの可能性を考慮せずに最小限の削除を優先する戦略は操作を過剰にカウントします。 

## アプローチ

 ブルート フォース戦略では、あらゆる状態ですべての有効な操作をシミュレートします。各ステップで、可能なすべての位置にある最小要素の削除を試行するか、プレフィックスで許可されている場合は最初の 2 つの要素を削除します。 これにより、配列状態に対する検索ツリーが形成されます。 メモ化を行ったとしても、同じ最小値の異なる出現を削除すると将来の隣接構造が異なるため、個別の状態の数が爆発的に増加する可能性があります。 最悪の場合、各削除が複数の次の構成に分岐し、指数関数的な動作が発生します。 

重要な点は、2 番目の操作は純粋に構造的なものであるということです。配列が 2 つの等しい要素で始まる場合にのみペアを削除し、常に両方を即座に消費します。 これは、境界を正しく位置合わせするときは常に、等しい要素の最大プレフィックスが強制削減のスタックのように動作することを意味します。 

最初の操作は、順序付けとグローバルに対話する唯一の操作です。 ただし、制約もあります。常に現在の最小値をターゲットとします。 これは、最小値より大きい値は、より小さい要素の削除によって公開される場合を除いて、直接削除されることはないことを示唆しています。 

重要な構造的変化は、立場の観点から考えるのをやめ、代わりに大きさによって分類された価値の観点から考えることです。 最小要素の削除を決定するたびに、将来の可能性のあるペアの削減を「中断」するか、バッチ削除を可能にする構造を維持するかを事実上選択していることになります。

これは、貪欲な圧縮の観点につながります。値を昇順に処理する場合、各値を個別に何回削除する必要があるか、隣接するペアリング カスケードを通じて何回削除できるかを推論できます。 配列は自然にセグメントに分解され、介在する小さな要素が削除されると、等しい値がペアで消滅する可能性があります。 

最適な解決策は、すべての小さい値を削除する効果を繰り返しシミュレートした後、いくつの「アクティブ ブロック」が生き残るかを追跡し、残った不一致要素を解決するために必要な削除の数をカウントすることになります。 

これを形式化する便利な方法は、値をスキャンし、左からのペアリングが崩れた後に各値の要素がいくつ残っているかを追跡する構造を維持し、小さなブロッカーが消えたときに 2 番目の操作を等しい隣接セグメントの貪欲なスタックキャンセルとして扱うことです。

 ## アルゴリズムのチュートリアル

 このプロセスを、より小さい値を削除した後に隣接する等しい要素が隣接するたびに、ペアでキャンセルできる配列の縮小表現を維持するものとして再解釈します。 

考えられるすべてのペアの削除が適用された後、現在の有効なプレフィックスを表す値のスタックを維持しながら、配列を左から右に処理します。 

1. 考えられるすべてのプレフィックス ペアの削除後の現在の縮小配列を表す空のスタックを初期化します。 
2. 配列内の各要素を左から右に繰り返します。 各要素について、現在の構造へのマージを試みます。 
3. スタックが空ではなく、その最上位が現在の要素と等しい場合は、現在の要素をプッシュする代わりに最上位を削除します。 これは、2 番目の操作を暗黙的に適用することに対応します。これは、2 つの隣接する等しい要素が有効な状態で連続するとすぐに相殺されるためです。 
4. スタックトップが異なる場合は、現在の要素をプッシュします。 これは、現在ペアリングが不可能な境界を表します。 
5. 配列全体を処理した後、スタックにはペアのキャンセルだけでは削除できない要素が含まれます。 残りの各要素は、プロセスのある段階での最初の操作の強制使用に対応します。 
6. 答えは、最終的なスタックのサイズです。キャンセル可能な構造はすべてすでに削除されている一方で、残っている一致しない要素はすべて、ある時点で最小要素として個別に削除する必要があるからです。 

これが機能する理由は、2 番目の演算のすべての有効な使用法が、完全に縮小された状態で等しい隣接する要素のペアを削除することに正確に対応しているためです。 このようなすべてのキャンセルを貪欲にシミュレートすることで、人為的な障壁が残らないようにします。 残っているのは、有効な操作の順序に基づいてペアにすることができない要素だけであり、そのような各要素は、最適な戦略において 1 つの最小削除イベントを強制します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    st = []
    for x in a:
        if st and st[-1] == x:
            st.pop()
        else:
            st.append(x)
    
    print(len(st))

t = int(input())
for _ in range(t):
    solve()
```このソリューションは、隣接する等しい要素を即座に折りたたむスタックを維持します。 ポップ操作は、2 番目に許可された操作を最も積極的な形式で適用することに正確に対応します。これは、有効なシーケンス内で 2 つの等しい値が隣接するたびに、将来の実現可能性に影響を与えることなくそれらを削除できるためです。 

最終的なスタック サイズは、考えられるすべてのペアを削除した後の既約剰余を表すため、出力されます。 残りの各要素は構造的に分離されており、許可された操作では隣接要素とペアにすることができないため、最初の操作を使用して個別の削除手順が強制されます。 

微妙な点は、「最小限の削除」を明示的にシミュレートすることは決してないということです。 その操作は不変式に吸収されます。ペアリングで削除できないものは最終的に 1 つずつ削除する必要があり、スタックはその残余を正確にキャプチャします。 

## 実用的な例

 ### 例 1

 入力:

 [5、2、5、2、2、4]

 | ステップ | 要素 | 前にスタック | アクション | | の後にスタック
 | --- | --- | --- | --- | --- |
 | 1 | 5 | [] | プッシュ | [5] |
 | 2 | 2 | [5] | プッシュ | [5、2] |
 | 3 | 5 | [5、2] | プッシュ | [5、2、5] |
 | 4 | 2 | [5、2、5] | プッシュ | [5、2、5、2] |

 | 6 | 4 | [5、2、5] | プッシュ | [5、2、5、4] |

 最終的な答えは 4 です。 

このトレースは、他のすべての構造が既約剰余として存続する一方で、等しい要素の正確な隣接のみがどのようにキャンセルをトリガーするかを示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from sys import stdin
    input = stdin.readline

    def solve():
        n = int(input())
        a = list(map(int, input().split()))
        st = []
        for x in a:
            if st and st[-1] == x:
                st.pop()
            else:
                st.append(x)
        return len(st)

    t = int(input())
    out = []
    for _ in range(t):
        out.append(str(solve()))
    return "\n".join(out)

# sample-like cases
assert run("1\n1\n5\n") == "1"
assert run("1\n2\n1 1\n") == "0"

# all equal long cancellation
assert run("1\n6\n2 2 2 2 2 2\n") == "0"

# alternating no cancellation
assert run("1\n5\n1 2 3 4 5\n") == "5"

# partial cancellation
assert run("1\n6\n1 1 2 2 3 3\n") == "0"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 要素 | 1 | 最小限のケース、ペアリングなし |
 | すべての等しいペア | 0 | フルカスケードキャンセル |
 | 交互 | n | マージはできません |
 | グループ化されたペア | 0 | ブロックでペアリングを完了する |

 ## 特殊なケース

 エッジ ケースの 1 つは、[7] のような単一要素の配列です。 スタックは空で開始され、要素がプッシュされ、最終的なスタック サイズは 1 になります。これは、1 つの削除が必要であることを正しく反映しています。 

もう 1 つのエッジ ケースは、[4、4、3、3、2、2] のような完全に対称的なペア構造です。 スタックは各ステップでペアを繰り返しキャンセルし、最終的には空になります。 これは、明示的なグローバル推論を必要とせずに、アルゴリズムが連鎖キャンセルを正しく処理していることを示しています。 

3 番目のケースは、キャンセルが [1, 2, 2, 1] などの中間構造に依存する場合です。 最初の2が押して、次の2でキャンセル、その後は1と1でキャンセル。 隣接関係は常に元の配列ではなく現在の縮小されたプレフィックスで評価されるため、スタック モデルはこの非ローカルな相互作用を正しくキャプチャします。
