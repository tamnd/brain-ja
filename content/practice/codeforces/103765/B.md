 ## 解決策
 ## 問題の理解

 単一の小文字列でプレイされるゲームが与えられています。 2 人のプレーヤーが最初のプレーヤーから順番に交互にターンします。 移動は、現在の文字列内で隣接する同一文字のペアを選択し、両方を削除してから、残りの部分をつなぎ合わせることで構成されます。 プレイヤーが自分の番にそのようなペアを見つけることができなかった場合、そのプレイヤーは即座に負けます。 

タスクは、指定された開始文字列ごとに、両方のプレーヤーが最適にプレーすると仮定して、最初のプレーヤーが勝利戦略を持っているかどうかを判断することです。 

制約は非常に厳しいので、すべてのテスト ケースの合計の長さは 100 万に達する可能性があります。 これにより、移動ごとに線形スキャンを使用して単純な方法で文字列上の移動を繰り返しシミュレートするアプローチは除外されます。これは、最悪の場合、削除ごとに文字列が 2 文字ずつ減り、そのような移動が O(n) 個存在する可能性があり、全体で O(n²) 個の動作が発生する可能性があるためです。 

微妙な点は、このゲームは任意の削除ではなく、隣接する等しいペアを削除することだけを目的としているということです。 これにより、構造は高度に局所的になりますが、削除によって元々存在しなかった新しい隣接ペアが作成される可能性があるため、位置全体で独立していません。 

重要なエッジ ケースには、隣接する等しいペアがまったくない文字列、すべての文字が同一である文字列、削除がカスケードされる文字列などがあります。 たとえば、`"abccba"`、真ん中を削除`"cc"`新しいチャンスの構造を生み出しますが、局所的な貪欲さよりも利用可能な手の同等性の方が重要であるため、必ずしも最初のプレイヤーが勝つとは限りません。 

もう 1 つの重要な特殊ケースは、複数の素のペアが存在する場合です。 素朴な直感では、各ペアが独立した動きであると思われるかもしれませんが、1 つのペアを削除すると他のペアが破壊または作成される可能性があるため、それは誤りです。 

## アプローチ

 ブルート フォースの解釈は簡単です。ゲームの状態をシミュレートします。 考えられるすべての動きについて、隣接する等しいペアを 1 つ削除し、結果の文字列を再帰的に評価し、現在のプレイヤーが強制的に勝利できるかどうかを決定します。 これは文字列を使った古典的なゲーム DP です。 

ただし、個別の状態の数は爆発的に増加します。 文字列構成によってメモ化したとしても、削除のたびに隣接関係がグローバルに変化し、到達可能な状態の数は最悪の場合指数関数的に増加します。 のような文字列の場合`"aaaaa...."`、移動するたびに長さが減少しますが、新しい隣接構成が作成され、依然として巨大な分岐構造が生成されます。 これは、実行可能な複雑さの限界を即座に超えます。 

重要な観察は、すべての移動がちょうど 2 文字を削除し、残りの文字の相対的な順序を決して変更しないことです。 さらに重要なのは、各手ごとに長さが 2 ずつ減少するため、ゲームは常に偶数ステップの厳密な減少シーケンスで進行します。 これは、ゲーム全体が実際には、どの手が選択されるかではなく、どれだけ多くの手が可能かによって決まることを意味します。 

スタック プロセスの観点から考えると、すべての削除は、隣接する同一の文字のペアをポップすることに相当します。 スタックを使用して左から右に貪欲に処理する場合、隣接する等しいペアを繰り返し削除するプロセスは決定論的です。現在の文字がスタックの先頭に等しい場合は、プッシュするのではなく先頭を削除します。 

この貪欲なリダクションでは、最終的にリダクションされた文字列が計算され、発生した削除の数が暗黙的にカウントされます。 それぞれの削除はゲーム内の動きです。 各移動によって長さが正確に 2 減少するため、移動の合計数は順序に関係なく固定されます。 これにより、ゲームはパリティ問題に陥ります。削除可能な数が奇数の場合は、最初のプレーヤーが勝ち、そうでない場合は 2 番目のプレーヤーが勝ちます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース ゲーム DP | 指数 | 指数 | 遅すぎる |
 | スタック削減 + パリティ | テストあたり O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。 

1. 文字列の現在の縮小形式を表す空のスタックを初期化します。 このスタックは、その中に等しい隣接する 2 つの文字がないという不変条件をモデル化します。 
2. 文字列を左から右に 1 文字ずつスキャンします。 各文字について、スタックが空でない場合はスタックの最上位と比較します。 
3. スタックが空でなく、最上位要素が現在の文字と等しい場合は、スタックをプッシュする代わりにポップします。 これは、隣接する等価ペアの削除を行うことを表している。 これが正しい理由は、隣接する等しいペアは最終的には削除される必要があり、その削除が遅れても削除の合計数には影響しないためです。 
4. それ以外の場合は、現在の文字をスタックにプッシュし、現在の縮小構造を拡張します。 
5. 実行された削除の数のカウンターを維持します。 一致するペアに対応するポップごとに、このカウンタが 1 ずつ増加します。 
6. 文字列全体を処理した後、削除数のパリティをチェックします。 奇数の場合は、最初のプレイヤーが最後の有効な手を行ったため、「はい」を出力します。 偶数の場合は「No」を出力します。 

### なぜ効果があるのか

 重要な不変条件は、文字列の各プレフィックスをスタック ルールで処理した後、スタックは考えられるすべての最適なプレイ シーケンスの下でそのプレフィックスの完全に縮小された形式を表し、実行される削除の数は有効な手の順序に関係なく固定されることです。 これは、削除は隣接する等しいペアを削除するだけで、総数に決して曖昧さを生じないという事実から導かれます。すべての有効なゲーム シーケンスは、何らかの順序で素のペアを削除することに対応しますが、各削除は厳密に長さを 2 だけ削減し、総数を変更するような方法で残りの構造のパリティに影響を与えないため、削除可能なペアの総数は並べ替えの下で不変です。 

したがって、ゲームは、スタックプロセスで発生するそのようなキャンセルの数を数え、パリティによって勝者を決定することになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    out = []
    
    for _ in range(T):
        s = input().strip()
        stack = []
        moves = 0
        
        for ch in s:
            if stack and stack[-1] == ch:
                stack.pop()
                moves += 1
            else:
                stack.append(ch)
        
        if moves % 2 == 1:
            out.append("Yes")
        else:
            out.append("No")
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションでは、スタックを使用して、隣接する等しい文字のキャンセルをシミュレートします。 各キャンセルはゲーム内の 1 つの有効な動きに正確に対応するため、変数`moves`最適なプレイで利用可能な手の合計数を追跡します。 

重要な点は、以前の決定を再考する必要がまったくないということです。 ペアが削除されると、新しい隣接関係を公開する以外は将来の削除に影響を与えることはできず、スタックは自然にそれを処理します。 

最終的な決定は純粋にパリティに基づいて行われるため、これ以上のゲーム理論的な推論は必要ありません。

 ## 特殊なケース

 次のような単一の文字の場合`"a"`、スタックは決してポップを実行しないので、`moves = 0`そして出力は`"No"`。 アルゴリズムは、有効な手が存在しないことを正確に識別します。 

のために`"aaaa"`、プロセスは連続的です。最初の 2 文字がキャンセルされ、次に残りの 2 文字がキャンセルされ、合計 2 つの移動が生成されます。 スタックはちょうど 2 つのポップを記録するため、パリティは偶数で、結果は次のようになります。`"No"`。 

次のような交互の文字列の場合`"ababab"`、隣接する等しいペアが形成されることはないため、スタックは増加するだけでポップすることはありません。 移動カウントはゼロのままで、正しく生成されます。`"No"`どの段階でも法的な措置は存在しないからです。
