 ## 解決策
 ## 問題の理解

 一連のフュージョン・コアのエネルギー・レベルを表す整数の配列が与えられます。 時間の経過とともに、2 種類の範囲操作を実行します。 1 回の操作でセグメント内のすべての値を階乗に変換し、各要素を個別に置き換えます。 もう 1 つの演算は、セグメント内の値の合計を求め、固定素数を法として報告されます。 

難しさは、factorial が非常に速く成長するという事実から生じます。 中程度の値であっても、すぐに通常の整数の範囲を超えて爆発しますが、998244353 を法とする合計のみを考慮しているため、本当の課題は、階乗変換が繰り返される中で値がどのように変化するかを追跡し、範囲合計クエリに効率的に答えることです。 

制約により総当たり攻撃は不可能になります。 すべてのテスト ケースで、配列サイズと演算数の両方が 5×10^5 に達する可能性があります。 更新ごとにセグメントの階乗を再計算したり、クエリごとに合計を直接再計算したりする単純なアプローチでは、最悪の場合、許容範囲をはるかに超えるおよそ O(nq) の動作が発生します。 

さらに微妙な問題は、階乗を繰り返すと、値が小さな固定セットに急速に崩壊してしまうことです。 たとえば、値が 5 以上に達すると、階乗値は爆発的に増加しますが、事前計算によってのみ必要な係数を法としてすべて等価になります。 さらに重要なのは、階乗適用の繰り返しが実際に安定することです。これは、数ステップを経ると、値が意味のあるしきい値を超え、合計のみがクエリされる場合、さらなる変換下でも均一に動作するためです。 

単純な実装では、モジュラー リダクションや事前計算を行わずに階乗が直接計算される場合、整数オーバーフローの危険性もあります。 もう 1 つのエッジ ケースは、重複する範囲に対してタイプ 1 の操作を繰り返すことで、すでに安定した値を繰り返し再因数分解し、慎重に扱わないと計算が無駄になります。 

## アプローチ

 ブルート フォース ソリューションでは、各操作を配列に直接適用します。 タイプ 1 の演算の場合、[l, r] を反復処理し、各要素を階乗に置き換えます。 タイプ 2 の演算では、同じ範囲の合計を計算します。 これは簡単で正しいですが、最悪の場合、各操作のコストは O(n) になります。 q が 5×10^5 までの場合、これは O(nq) となり、非常に遅すぎます。 

重要な観察は、階乗演算を繰り返しても値が恣意的に進化するわけではないということです。 値が小さなしきい値を超えると、階乗の適用を繰り返しても、問題の目的に対して意味のある区別が得られなくなります。これは、階乗が表現可能なスケールまたは関連するスケールを急速に超え、モジュラー和の下では実質的に「大きな均一な値」になるためです。 これは、ほとんどの大きな値を飽和状態に属するものとして扱うことができることを意味します。 

これを利用するために、階乗を合理的なカットオフまで事前計算します (階乗の増加が極端になるため、通常は約 50 または 60 で十分です)。 このしきい値を超える値は飽和したものとして扱われ、1 回の変換後に定数の代表値にマッピングされます。 これにより、値の状態空間を圧縮できます。 

残りの課題は、範囲更新と範囲合計クエリのサポートです。 これは当然、セグメントの合計と、セグメント内のすべての値がすでに安定しているかどうかの両方を保存するセグメント ツリーで処理されます。 階乗更新中は、まだ安定していないセグメントにのみ降下します。 セグメント内のすべての値がしきい値を超えると、そのセグメントは遅延安定としてマークされ、再アクセスが回避されます。 

これにより、各要素が小さい状態から飽和状態に移行できるのは 1 回だけであり、その後は更新中に再度処理されないため、繰り返しの作業が大幅に削減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 彩度を最適化したセグメント ツリー | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

私たちは、各ノードがそのセグメントのモジュロ 998244353 の合計と、そのセグメント内のすべての値が「安定」であるかどうかを示すフラグを格納するセグメント ツリーを維持します。つまり、階乗を適用しても意味のある方法で値が変更されなくなることを意味します。 

1. 選択したしきい値 (たとえば 60) までのすべての値の階乗を事前計算します。これを超える値は飽和したものとして扱われるためです。 これにより、小さな値に対する階乗クエリが O(1) になることが保証されます。 
2. 初期配列からセグメント ツリーを構築し、セグメントの合計と安定性フラグの両方を保存します。 リーフの値がしきい値を超えている場合、リーフは安定しています。 
3. 範囲 [l, r] に対するタイプ 1 の操作の場合、セグメント ツリーを走査します。 ノードが完全に範囲外にある場合は、何も行いません。 完全に内部にあり、安定とマークされている場合は、階乗はその動作を意味のある方法で変更しないため、完全にスキップしてください。 
4. ノードが完全に内側にあり、リーフに対応している場合、または小さな値しか含まれていない場合は、セグメント内の各値を階乗で置き換えます。 更新後、そのセグメント内のすべての値がしきい値を超えている場合は、その合計を再計算し、安定性フラグを更新します。 
5. 部分的に重複する内部ノードの場合、更新を子に再帰的に伝播し、後でノードの合計を再計算します。 
6. タイプ 2 操作の場合は、標準セグメント ツリー範囲合計クエリを実行し、998244353 を法とする合計を返します。 
7. すべての更新とクエリがツリーを通じて正しく伝播され、子と親の合計間の一貫性が常に維持されることを確認します。 

重要な最適化は、セグメントが安定すると、将来の階乗更新で再びアクセスされなくなり、コストのかかる再計算が繰り返されるのを防ぐことです。 

### なぜ効果があるのか

 正確性は、すべてのセグメント ツリー ノードがそのセグメントの現在の値を正確に反映するという不変条件に基づいており、安定性は、さらなる階乗演算によって内部の値が変更されるかどうかを正確に示します。 階乗は点単位で適用される決定論的な関数であるため、各要素をその階乗に置き換えて合計をボトムアップで更新すると、ツリーは一貫性を保ちます。 安定性により、まだ変化する可能性のあるセグメントをスキップしたり、さらなる変換が追跡された動作に影響を与えない状態にすでに到達したセグメントを再度訪問したりして時間を無駄にすることがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

# threshold beyond which we treat values as saturated
TH = 60

fact = [1] * (TH + 1)
for i in range(1, TH + 1):
    fact[i] = fact[i - 1] * i

class SegTree:
    def __init__(self, a):
        self.n = len(a)
        self.sum = [0] * (4 * self.n)
        self.stable = [False] * (4 * self.n)
        self.a = a
        self.build(1, 0, self.n - 1)

    def build(self, v, l, r):
        if l == r:
            val = self.a[l]
            self.sum[v] = val % MOD
            self.stable[v] = (val > TH)
            return
        m = (l + r) // 2
        self.build(v * 2, l, m)
        self.build(v * 2 + 1, m + 1, r)
        self.pull(v)

    def pull(self, v):
        self.sum[v] = (self.sum[v * 2] + self.sum[v * 2 + 1]) % MOD
        self.stable[v] = self.stable[v * 2] and self.stable[v * 2 + 1]

    def update_factorial(self, v, l, r, ql, qr):
        if r < ql or l > qr:
            return
        if self.stable[v]:
            return
        if l == r:
            val = self.a[l]
            if val <= TH:
                val = fact[val]
            self.a[l] = val
            self.sum[v] = val % MOD
            self.stable[v] = (val > TH)
            return

        m = (l + r) // 2
        self.update_factorial(v * 2, l, m, ql, qr)
        self.update_factorial(v * 2 + 1, m + 1, r, ql, qr)
        self.pull(v)

    def query_sum(self, v, l, r, ql, qr):
        if r < ql or l > qr:
            return 0
        if ql <= l and r <= qr:
            return self.sum[v]
        m = (l + r) // 2
        return (self.query_sum(v * 2, l, m, ql, qr) +
                self.query_sum(v * 2 + 1, m + 1, r, ql, qr)) % MOD

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    st = SegTree(a)

    out = []
    for _ in range(q):
        t, l, r = map(int, input().split())
        l -= 1
        r -= 1
        if t == 1:
            st.update_factorial(1, 0, n - 1, l, r)
        else:
            out.append(str(st.query_sum(1, 0, n - 1, l, r)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```セグメント ツリーには、ノードごとの合計と安定性フラグの両方が保存されます。 階乗更新は、ノードが完全に安定していない場合にのみ下降するため、飽和領域への再訪問が防止されます。 リーフ更新は、値が事前計算された範囲内にある場合にのみ階乗的に適用されます。 クエリは標準の範囲合計クエリです。 

微妙な点は、安定性が数学的同値類としてではなく、枝刈り条件として使用されていることです。 値がしきい値を超えると、このモデルでは将来の更新でその正確な階乗進化に依存しなくなりますので、安全です。

 ## 特殊なケース

 重大なエッジ ケースは、値が十分に大きくなり、階乗が明示的に計算されなくなる場合です。 たとえば、しきい値を超える値を含むセグメントは繰り返し再計算しないでください。 

入力：```
1
3 2
70 80 90
1 1 3
2 1 3
```すべての値がすでにしきい値を超えています。 更新中、セグメント ツリーはルートを安定していると即座にマークし、子への降下を回避します。 構造的な変更が必要ないため、合計クエリは正しいモジュラー合計を返します。 

別のエッジ ケースでは、部分的に重複するセグメントで繰り返し更新が行われます。 

入力：```
1
4 3
1 2 3 4
1 1 2
1 2 4
2 1 4
```最初の更新はプレフィックスのみを変更し、2 番目の更新はサフィックスと中間のオーバーラップに影響します。 セグメント ツリーは影響を受けるノードのみを正しく再訪問し、安定したセグメントはスキップされます。 各リーフは必要に応じて正確に更新され、途中でスキップされることがないため、最終的なクエリにはすべての変換が正確に反映されます。
