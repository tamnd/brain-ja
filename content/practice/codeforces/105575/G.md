 ## 解決策
 ## 問題の理解

 3 つの整数のコレクションが与えられています。 これらは、時間の経過とともに一致させる必要がある 3 種類のリソースであると考えることができます。1 つのセットはダメージを受けても「生存」するユニットを表し、他の 2 つのセットはユニットを保護するか、生存中にその有効性を高める機器を表します。 

モデル化されているプロセスは、これらのリソース間の相互作用の継続的な蓄積として解釈できます。 最初のグループの各ユニットは 2 番目のグループの 1 つのアイテムとペアになり、そのユニットがどれだけ長く生き残るかに応じて、3 番目のグループのアイテムとも相互作用します。 計算する必要がある最終量は、関連するすべてのアクティビティが終了する前に、これらの相互作用から累積される有効寄与の合計です。 

重要な問題は、結果が 3 つのグループの組み合わせに大きく依存することです。 割り当てが不適切だと、強力なリソースが弱いライフタイムに浪費され、合計の寄与が減少する可能性があります。 

制約 (複数のテスト ケースにわたって最大サイズの配列を使用する、このスタイルの問題に典型的なもの) は、すべてのペアリングを試行したり、相互作用を明示的にシミュレートしたりするソリューションは非常に遅すぎることを意味します。 単純なアプローチでは、順列またはマッチング戦略が考慮され、階乗または少なくとも二次爆発が発生しますが、各テストに大きな配列が含まれる場合、これは実行できません。 

グループの 1 つが別のグループよりも大幅に大きい場合、微妙なエッジ ケースが発生します。 たとえば、ソートせずに入力順に貪欲にペアリングすると、次善のマッチングが簡単に得られます。 

生存時間が一致しない状況を考えてみましょう。 

入力:```
a = [10, 1]
b = [1, 10]
```順番にペアになった場合、より強いサバイバー (10) は弱いサポート (1) を受け取り、弱いサバイバーは強いサポートを受け取ります。 これにより、潜在的な貢献が早期に失われることになります。 正しい戦略は明らかに、大型と大型をペアにすることです。 

もう 1 つのエッジ ケースは、トリミング後に 1 つのリストが空であるか、事実上無関係である場合です。 単純な実装では、無効なインデックスにアクセスしようとしたり、同じサイズを想定したりする可能性があります。 

## アプローチ

 ブルートフォースソリューションでは、最初のグループの各要素をすべての可能な置換で 2 番目のグループの要素に割り当てようとし、同様に 3 番目のグループがどのように相互作用するかを決定します。 これはシステムを正しくモデル化しますが、すべてのマッチングを反復する必要があります。 ペアリングに限定しても、各割り当ての選択が将来の貢献に影響を与えるため、これはすでに階乗的なサイズになります。 n の値が大きい場合、これは完全に不可能になります。 

重要な観察は、システムが同一性ではなく相対的な順序付けのみに依存しているということです。 不一致はペアを交換することで局所的に改善できるため、より強力なユニットは常により強力なサポートと一致する必要があります。 2 つのペアの強度が「交差」している場合、それらを交換すると、すべての寄与が厳密に改善または維持されます。 これは、最適な構造としての並べ替えに直接つながる古典的な交換議論です。 

各グループを降順にソートする必要があることを受け入れると、相互作用の構造は線形になります。 次に、「ダメージ枯渇点」の昇順でしきい値を処理することにより、寄与度の進化をシミュレートします。 各イベントは、リソースが完全に消費される瞬間に対応し、イベント間では貢献度が一定の割合で増加します。 

残っているアクティブなユニットの数を維持し、何も変化しない間隔で貢献度を蓄積します。 しきい値に達すると、アクティブな数を減らして続行します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n!) かそれ以上 | O(n) | 遅すぎる |
 | 最適 (ソート + スイープ シミュレーション) | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 3 つの配列すべてを降順に並べ替えて、より強力な要素が最初に考慮されるようにします。 これにより、より高い容量または耐久性が常により高い衝撃位置に割り当てられるようになります。 
2. ソート後に、最初のグループと 2 番目のグループのインデックスをインデックスでペアにします。 各ペアは、生存値と盾のような能力を持つユニットを表します。 
3. ユニットごとに、同じインデックスに 3 番目のグループの要素が存在する場合、ユニットの生存制限によって制限される追加の潜在的な貢献を表す追加イベントを作成します。 
4. これらすべての寄与をイベントのリストに収集します。各イベントにはしきい値と関連する寄与値があります。 
5. これらのイベントをしきい値で並べ替えて、「枯渇までの時間」が増加する順に処理します。 
6. 経過した合計「時間」または累積ダメージを維持しながら、イベントを一掃します。 イベントごとに、しきい値に達するまでに追加の寄与がどれだけ蓄積されるかを計算します。 
7. 寄付を蓄積しますが、イベントで利用可能な寄付を超えないように上限を設けます。 各イベントのしきい値を通過するときのアクティブ数を減らします。 
8. 最終的に累積された答えは、すべてのリソースが使い果たされる前に収集された合計貢献度です。 

### なぜ効果があるのか

 正しさは、順序付けに関する交換引数から得られます。 より強力な生存ユニットが別の利用可能なユニットよりも弱いシールドとペアになっている場合、それらを交換しても貢献を減らすことはできず、少なくとも 1 つのペアリングは厳密に改善されます。 これにより、並べ替えによって最適なペアが揃うことが保証されます。 

システムは離散点の間で線形に進化するため、スイープは機能します。 しきい値間では何も変化しないため、累積は均一であり、段階的なシミュレーションではなくブロック単位で計算できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))
    c = list(map(int, input().split()))

    a.sort(reverse=True)
    b.sort(reverse=True)
    c.sort(reverse=True)

    b = b[:n]
    c = c[:n]

    events = []

    for i in range(n):
        events.append([a[i], b[i]])
        if i < len(c):
            events.append([min(a[i], c[i]), 0])

    events.sort()

    ans = 0
    dec = 0
    tim = 0
    num = len(events) - 1

    for i in range(len(events)):
        diff = events[i][0] - dec
        tim += num * diff
        ans += min(tim, events[i][1])
        num -= 1
        dec = events[i][0]

    print(ans)

if __name__ == "__main__":
    t = int(input())
    for _ in range(t):
        solve()
```実装は、貪欲なペアリングの原則を適用して、すべての配列を降順に並べ替えることから始まります。 ソート後は上位一致のみが重要となるため、2 番目と 3 番目の配列はプライマリ ユニットの数に一致するようにトリミングされます。 

イベント リストはすべてのインタラクションをエンコードします。 各ペアは、以下の基本イベントに貢献します。`a[i]`そして`b[i]`、およびオプションで上限付きイベント`c[i]`。 これらのイベントをしきい値で並べ替えることで、枯渇度の高い順に処理できるようになります。 

スイープ変数は、累積時間の実行概念を維持します (`tim`)、アクティブなセグメントがいくつ残っているか (`num`)、およびしきい値スペースでどこまで進んだか (`dec`）。 各反復は次のしきい値に進み、その間隔で寄与を蓄積し、1 つのイベントを消費します。 

微妙なディテールは、`min(a[i], c[i])`これにより、3 番目のリソースが対応するユニットの生存能力を超えて貢献できないことが保証されます。 これにより、サポートが生存可能性を超えた場合の過剰カウントが防止されます。

 ## 特殊なケース

 重大なエッジ ケースは、ある配列に非常に大きな値のみが含まれ、別の配列に非常に小さな値が含まれる場合です。 並べ替えを行わないと、ペアリングによって極値が誤って間違った方向に割り当てられ、合計の寄与が崩れてしまいます。 並べ替え後、大きな値は正しく整列し、スイープは単調に動作します。 

もう 1 つのエッジ ケースは、3 番目の配列内のすべての値が 0 である場合です。 この場合、塩基対の寄与のみが問題となります。 アルゴリズムは依然としてイベントを作成しますが、二次的な寄与はすべて消え、スイープは一次ペアにわたる線形累積にきれいに減少します。 

最後のエッジケースは、すべての配列が同じ値を持つ場合です。 その状況では、すべてのペアリングは同等であり、アルゴリズムの並べ替えによって構造は変更されませんが、決定的な処理順序が保証されます。 スイープは依然として均一のしきい値を正しく処理し、対称性の下での安定性を確認します。
