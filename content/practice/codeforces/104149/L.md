 ## 解決策
 ## 問題の理解

 長い階段を表すバイナリ文字列が与えられます。 各文字はステップに対応し、 でマークされた位置のみが対応します。`1`壊れているので修理する必要があります。 壊れたステップはすべて 1 回の操作で修復する必要があり、その操作は階段の 1 つの連続したセグメントに適用する必要があります。 

私たちが使用する呪文は常に連続した区間全体を固定しますが、その使用可能な範囲は書き方によって異なります。 最も単純な形式では、最大 32 の連続ステップをカバーできます。 単語の前に「long」という単語を繰り返し追加することで範囲を拡張でき、「long」を追加するたびに、処理できる最大ステップ数が 2 倍になります。 したがって、呪文の能力は等比数列を形成します。 

課題は、すべてをカバーできる最短の有効な呪文形式を決定することです。`1`単一の連続セグメントを持つ文字列内。 

入力文字列は 10^6 文字に達する可能性があるため、どのソリューションでも線形時間で入力文字列をスキャンする必要があります。 部分文字列に対する繰り返しシミュレーションや範囲の再計算を伴うものは、遅すぎます。 

重要な構造的観察は、最初と最後の出現のみが存在することです。`1`案件。 すべての分断されたステップをカバーする単一の連続セグメントを選択すると、その最小必要長は完全にこれら 2 つの端の間の距離によって決まります。 

素朴な間違いは、複数の互いに素なグループを考慮する必要があると考えることです。`1`s またはセグメントの数を数えます`1`性差別主義者。 たとえば、次のような文字列では`100010001`、誰かが複数の呪文が必要であると誤って考えるかもしれません。 実際には、この呪文は連続した間隔をカバーするため、いずれにしても間にゼロを含める必要があり、重要なのは境界間隔だけです。 

もう 1 つの潜在的な間違いは、呪文のスケーリングを誤解することです。 増加は「long」が何回付加されるかに関して指数関数的であるため、これを線形増加として扱うと、大きなスパンについては不正確な答えが得られます。 

## アプローチ

 ブルートフォースのアイデアは、すべてを含むセグメントの可能な開始位置と終了位置をすべて試してみることです。`1`s、その長さを計算し、その長さをカバーするために必要な「長い」プレフィックスの数を決定します。 有効なセグメントは最初の時点またはその前で開始する必要があることがわかると、これはすぐに不要になります。`1`そして最後の時点またはその後で終了します`1`より大きな値を選択すると、要件がさらに悪化するだけです。 エンドポイントのすべてのペアを試行すると、最大 10^6 の長さの文字列にわたって二次関数の動作が発生しますが、これは実行可能な制限をはるかに超えています。 

重要な洞察は、問題が単一の区間、つまりすべてを含む最小の区間に集約されるということです。`1`s は最初からの間隔です`1`最後まで`1`。 その長さを`L`。 呪文は少なくともサポートする必要があります`L`ステップ。 

ここで必要なのは、次のような「長い」プレフィックスの最小数を決定することだけです。```
32 * 2^(k-1) >= L
```これは、基本フォームがすでに容量 32 に対応しており、追加の「ロング」ごとにその容量が 2 倍になるという事実から来ています。 必要なスパンを超える容量を押し上げる最小の指数を効果的に解決しています。

 | 最初/最後に使用`1`と対数スケーリング | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 文字列を 1 回スキャンして、最初の文字列のインデックスを見つけます。`1`そして最後`1`。 これにより、カバーする必要がある最小限のセグメントが定義されます。 より小さなセグメントでは、少なくとも 1 つの壊れたステップが欠落します。 
2. 必要な長さを計算します`L = last_one_index - first_one_index + 1`。 これは、すべての中断されたステップを含む最小の連続間隔です。 
3. 1 つの「ロング」に対応する基本容量 32 から開始します。 
4. 概念的に「長い」を適用する回数を数えながら、容量を 2 倍にすることを繰り返します。 最小のものを効果的に見つけています`k >= 1`そのような`32 * 2^(k-1) >= L`。 
5. 単語「long」を繰り返し出力します`k`時間をスペースで区切ります。 

### なぜ効果があるのか

 呪文は常に連続した間隔で作用するため、有効な解決策は少なくとも最初と最後の間の間隔をカバーする必要があります。`1`。 その間隔を超えて拡張しても、必要な容量が増加するだけです。 それぞれの「長い」容量は 2 倍になるため、問題は固定ターゲット長に適合する最小の 2 のべき乗スケーリングを見つけることになります。 単調増加により、容量が超過すると、`L`、それ以上の数のプレフィックスが機能します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    
    n = len(s)
    first = -1
    last = -1
    
    for i, ch in enumerate(s):
        if ch == '1':
            if first == -1:
                first = i
            last = i
    
    L = last - first + 1
    
    k = 1
    cap = 32
    
    while cap < L:
        cap *= 2
        k += 1
    
    print(" ".join(["long"] * k))

if __name__ == "__main__":
    solve()
```実装は、境界間隔を特定することから始まります。`1`単一パスで。 次に、必要なスパン長を計算します。 その後、呪文の容量が 32 から始まる指数関数的な増加をシミュレートし、容量が十分になるまで「長い」プレフィックスの数を増やします。 ループは必要な長さで対数的であるため、制約の下では安全です。 

微妙な点は、`k`最小の呪文にもすでに 1 つの「ロング」が含まれているため、0 ではなく 1 です。 これは、最短の有効なフォームが空ではないサンプル出力と一致します。

 ## 特殊なケース

 厄介なケースは次のような場合です。`1`すでにぎっしり詰まっています。 たとえば、`11111`、最初と最後の位置が近いため、必要な長さは小さくなります。 アルゴリズムは最小間隔を正しく計算し、すぐに基本容量に留まり、単一の「ロング」を生成します。 

別のケースは次のような場合です。`1`は、非常に大きな文字列の端に現れます。 たとえ間に何百万ものゼロがあるとしても、最初と最後の間の距離だけが重要です。`1`重要です。 スキャンはこれを O(n) 時間で正確にキャプチャしますが、増加が指数関数的であるため、2 倍化ループは依然として小さいままです。 

最後のエッジケースは単一です`1`。 この場合、`L = 1`、基本容量がすでにそれをカバーしているため、出力は再び 1 つの「長い」ものになり、最も短い呪文であっても少なくとも 1 つの接頭辞があるという定義と一致します。
