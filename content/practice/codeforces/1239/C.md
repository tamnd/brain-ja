 ## 解決策
 ## 問題の理解

 左から右にインデックスされた座席の列が与えられ、各座席にはちょうど 1 人の乗客が座っています。 すべての乗客には、座席 1 のすぐ左側にある給水タンクに行く準備をする予定の時間があります。乗客が行くことを決めたら、座席の配置で観察した内容に応じて、すぐにタンクまで歩いて行ける場合とそうでない場合があります。 

重要な問題は、乗客が席を離れるのは、厳密に左側の座席がすべて占有されている場合のみであることです。 左の席に空席があると、「私の前の人がすでに並んでいる」と解釈し、座ったままにして後でもう一度席に座ります。 乗客が行くことを決心すると、最終的にはタンクに到達し、そこで正確に p 単位の時間を過ごすことになります。 複数の乗客が同時にタンクの使用を開始しようとすると、一番左のインデックス付きの乗客だけが最初に進むことができ、他の乗客は遅れます。 

私たちが計算しなければならないのは、座席ごとに、その乗客がタンクの使用を終了する正確な時刻です。 

制約は大きく、乗客数は最大 100,000 人、時間は最大 10^9 です。 分ごとの動作をシミュレートしたり、イベントごとに左隣を繰り返しスキャンしたりするソリューションは、最悪の場合二次動作に低下するため、遅すぎます。 

微妙な難しさは「もう行ってもいいですか？」ということです。 時間だけでなく、その時点で前の座席がすべてまだ占有されているかどうかにも依存し、それらの占有間隔自体は以前の決定によって決定されます。 

単純な間違いは、各乗客を独立して扱い、到着順に処理することです。 これは失敗します。タンクの「左端優先」ルールにより、後の席が早い決定を妨げる可能性があるためです。 

たとえば、t1 = 0 および t2 = 0、p = 10 の 2 人の乗客について考えてみましょう。両方とも同時に準備ができていても、乗客 1 が最初に乗車する必要があります。 t2 も 0 であっても、乗客 2 は、乗客 1 が時刻 10 に終了するまで開始できません。t_i によってソートするだけの単純なアプローチでは、座席の優先順位の制約が無視されます。 

もう 1 つの失敗例は、左チェック ルールに起因します。 座席 i の乗客は後で準備が整いますが、現在左側の座席はすべて占有されているとします。 準備時間のみが順序を決定すると誤って仮定すると、左側の空きにより遅れが生じるという制約に違反して、入場が早すぎてしまう可能性があります。 

実際の構造は、このプロセスが、座席の位置によって追加の順序付けルールが課せられた、制約された単一サーバーのキューのように動作するというものです。 

## アプローチ

 ブルートフォース シミュレーションでは、すべての座席を繰り返しスキャンし、そのたびにどの乗客が対象となるかを確認し、その中で最小のインデックスを選択します。 誰かを処理した後、その終了瞬間まで時間を進めて、それを繰り返します。 

これは正しいですが、根本的に遅すぎます。 各選択には最大 n 個の座席のスキャンが必要ですが、そのような選択が n 個存在する可能性があり、O(n^2) の動作が生成されます。 

重要な観察は、適格性は動的な左側の占有に依存しますが、決定の構造は単調であるということです。 座席が適格になり、選択されると、一定の間隔で他の座席をブロックします。 これは、実際のサービス開始時刻の昇順に乗客を処理できることを意味しますが、それらの開始時刻を効率的に計算する必要があります。 

私たちは、現在対象となるすべての乗客の中から最小のインデックスが選択されるようにしながら、利用可能な人を追跡する優先順位構造を使用してプロセスをシミュレーションします。 ただし、適格性は左側の完了制約に依存するため、時間による直接優先キューでは不十分です。

正しい洞察は、最終完了時刻のポインタを維持し、複数の到着準備ができたときに常に左端の空いている乗客にサービスを提供しながら、時間を昇順に処理することです。 当社は、インデックス順に注文された「準備はできているがまだサービスを受けていない」乗客の列を維持し、次の到着または現在のサービス完了まで慎重に時間を進めます。 

これにより、問題は効率的な順序付けを備えたイベント駆動型のシミュレーションに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n²) | O(n) | 遅すぎる |
 | イベント駆動型のキュー + 順序付け | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 当社は、到着したがまだサービスを受けていない乗客を常に把握する構造を維持しており、規則で許可されている正確な順序で乗客を処理します。 

1. 元のインデックスを維持しながら、到着時間別に乗客を並べ替えるか反復します。 これにより、システムへの到着を時系列順に導入することができます。 
2. 到着時刻に達したがまだサービスを開始していないすべての乗客に対して、座席インデックス順に並べられた優先キュー (最小ヒープ) を維持します。 
3. タンクがいつ空になるかを表す現在の時間変数を維持します。 
4. t_i が現在時刻以下であるすべての乗客をヒープに繰り返し追加することにより、時間をかけて繰り返します。 これにより、現在奉仕できるすべての候補者が確実に選択できるようになります。 
5. ヒープが空でない場合は、最小のインデックス乗客を抽出し、そのサービス開始時刻を現在時刻として割り当てます。 終了時刻は current_time + p となり、current_time をその値に更新します。 
6. ヒープが空の場合は、current_time を次の到着時刻までジャンプさせて、アイドル期間のシミュレーションで時間を無駄にしないようにします。 
7. すべての乗客が処理されるまで繰り返します。 

微妙な理由は、到着は継続的に発生するにもかかわらず、サービスの決定はタンクが空になったとき、または新しい乗客が適格になったときのいずれかの離散的なイベントポイントでのみ行われるということです。 

### なぜ効果があるのか

 いつでも、誰が次に行けるかについての唯一の制約は、タンクが空いていなければならず、現在対象となるすべての乗客の中で最小のインデックスを選択する必要があることです。 ヒープ不変条件により、常に左端の適格な座席が選択されることが保証され、時間進行ルールにより、適格な乗客がスキップされないことが保証されます。 すべての乗客は 1 回だけ挿入され、1 回だけ取り外されるため、サービスの順序付けは問題の制約に厳密に従います。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    n, p = map(int, input().split())
    t = list(map(int, input().split()))
    
    people = sorted([(t[i], i) for i in range(n)])
    
    heap = []
    res = [0] * n
    
    i = 0
    time = 0
    
    while i < n or heap:
        if not heap and i < n and time < people[i][0]:
            time = people[i][0]
        
        while i < n and people[i][0] <= time:
            heapq.heappush(heap, people[i][1])
            i += 1
        
        if heap:
            idx = heapq.heappop(heap)
            start = time
            finish = start + p
            res[idx] = finish
            time = finish
    
    print(*res)

if __name__ == "__main__":
    solve()
```このコードは、まず各乗客をそのインデックスと組み合わせ、到着時刻で並べ替えて、段階的にアクティブ化できるようにします。 ヒープには準備ができている乗客のインデックスが保存されており、常に最小のインデックスをポップすることで、利用可能な左端の乗客が最初にタンクを使用するというルールが適用されます。 

時間変数はシミュレーション クロックとして機能します。 誰も準備ができていない場合は、次の到着時間に直接ジャンプします。これにより、アイドル期間中の不必要な反復が回避されます。 誰かがサービスを受けると、タンクが占有されていることを反映して時間を p だけ進めます。 

微妙な点は、適格性が暗黙的に処理されることです。乗客の到着時刻に達した場合にのみ乗客を押し込み、ヒープは準備ができている乗客の間での順序付けのみを制御するため、左席の占有率を明示的にモデル化する必要はありません。 この制約は、以前のシートが適格になった時点で常に後のシートよりも前にヒープに入るという事実によって効果的にエンコードされています。

 この実行では、到着タイミングとインデックスの順序がどのように相互作用するかを示します。 座席 4 が座席 0 と同時に到着したとしても、インデックスの順序によって同点は解決され、後から到着した人は時間が進んだときに単に入場するだけです。

 ## 特殊なケース

 重要なエッジケースは、複数の乗客が時刻 0 に到着する場合です。`n = 3, p = 5, t = [0,0,0]`、すべてがすぐに適格となり、ヒープによってシート 1 が最初に処理され、次に 2、次に 3 が処理されることが保証されます。出力は p の連続した倍数になり、左端の優先順位が正しく適用されていることを確認します。 

もう 1 つのエッジ ケースは、システムがアイドル状態になる到着がまばらであることです。 入力用`n = 2, p = 10, t = [0, 100]`たとえば、座席 1 は時刻 10 に提供され、その後システムは座席 2 の時刻 100 にジャンプし、110 が生成されます。タイムジャンプ ロジックにより、誤った中間処理が防止され、人為的な遅延が発生しないことが保証されます。 

最後の微妙なケースは、タンクが空になったちょうどそのタイミングで後から乗客が到着する場合です。 のために`n = 2, p = 5, t = [0, 5]`、乗客 1 は 5 で終了し、乗客 2 はその時点ですでに資格を持っています。 ヒープベースの挿入により、アイドル時間なしで即座に処理されることが保証され、期待どおり出力 5 と 10 が生成されます。
