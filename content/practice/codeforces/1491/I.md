 ## 解決策
 ## 問題の理解

 私たちは、動物の列に対する決定的な排除プロセスをシミュレートしています。各動物には、すでに何回連続して勝ったかに応じて 3 つの異なる強さモードがあります。 最初は、動物 0 が王様で、他のすべての動物は 1 から n − 1 までのキューに入れられます。 

各戦いでは、列の先頭の動物が現在の王に挑戦します。 王者の強さは現在の連勝数に依存しますが、挑戦者は出現時に常に0勝状態であるため、基礎的な強さを使用します。 勝者はそのまま残るか王となり、敗者は列の最後尾に追いやられます。 王者の連勝記録は、勝てば増加、負ければリセットされる。 

このプロセスは、動物が王として 3 回連続で勝利を収めたときに停止します。 その動物は支配者として宣言されており、そのインデックスと発生した戦闘の数を出力する必要があります。 そのようなイベントがまったく起こらない場合、プロセスは無限に続きます。 

重要な問題は、状態空間が「誰がキングであるか」だけでなく、キングの現在のストリークも考慮し、キューの順序が動的に変化することです。 

n が 6000 までの制約は、シミュレーションの償却がイベントごとに最大約 O(n log n) または O(n) でなければならないことを意味します。 戦いごとの単純な O(n²) はすでに境界線にありますが、構造を持たないすべての遷移の直接シミュレーションでは、各動物が何度もキューに再入力できるため、簡単に O(n³) の行動に退化する可能性があります。 

単純なシミュレーションの微妙な失敗例は、プロセスが 3 連勝に向けて進展せずにサイクルを繰り返すときに発生します。 たとえば、2 頭の強い動物が互いの記録をリセットしながら繰り返し王権を交代すると、システムが無限にループする可能性があります。 

もう 1 つの隠れた落とし穴は、王の強さは連続記録に依存するのに対し、列に並んでいる動物は常に A_i を使用することを忘れていることです。 多くの誤った実装では、B_i と C_i を静的として扱うか、負けた場合の連勝リセットを忘れます。 

## アプローチ

 ブルート フォース アプローチは、キューとキングの状態を直接シミュレートします。 私たちはキューを明示的に維持し、各戦いをシミュレートします。フロントの挑戦者をポップし、キングストリークに応じて強さを比較し、キングとストリークを更新し、敗者を後退させます。 これはプロセスを正確に反映しているため、簡単かつ正確です。 ただし、最悪の場合、キューは終了または繰り返しの検出前に何度も循環する可能性があります。 各動物は負けた後に再びキューに入る可能性があるため、操作の数は最大 O(n × 戦闘数) まで非常に多くなる可能性があり、システムがサイクルに入ると戦闘の数自体に制限がなくなる可能性があります。 

重要な観察点は、システムの状態がペア (キング、ストリーク、および循環キュー) によって完全に決定されるということです。 ただし、実際にはキューを完全に進化させる必要はありません。 重要な事実は、各動物は前線に到達した場合にのみ王と対話し、その結果は A_i、B_i、C_i と現在の王の状態との比較にのみ依存するということです。 

代わりに、これを各動物が前線に到達したときに「アクティブ化」されるプロセスとして扱うことができ、特定のストリーク状態で現在のキングに勝つことができるかどうかのみを考慮します。 これにより、問題を、支配力の遷移を追跡し、システムが 3 連続勝利に決して到達しないキングのサイクルに安定するかどうかを検出することに減らすことができます。 

主な構造上の洞察は、キングの連勝記録は 0 → 1 → 2 → 3 までしか進むことができず、負けるたびに 0 にリセットされるということです。したがって、各キングは最大 3 つの有効な強さレベルを持つと考えることができます。 これは、動物ごとの意味のある状態遷移を制限します。

キューのローテーションをシミュレートする代わりに、現在のキング状態に対して可能な限り最良の「次のチャレンジャー」を維持し、キングが実際に変更されたときのみシミュレートすることができます。 これにより、プロセスが個々のキュー ステップではなくキング遷移のシーケンスに折りたたまれます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(k · n) 最悪の場合の無制限 k | O(n) | 遅すぎる/ループする可能性があります |
 | 最適化された状態遷移 | 実装に応じて O(n log n) または O(n α(n)) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在のキングとその連勝数のみが重要であるという考えに基づいてプロセスを再構成し、列の先頭に到達して挑戦する次の対戦相手を繰り返し決定します。 

1. キングを、ストリーク 0、総戦闘数 = 0 の動物 0 として初期化します。他のすべての動物は、1 から n − 1 の順序でキューに入れられます。 
2. 現在どの動物が次に戦う「積極的な候補者」であるかを追跡する構造を維持します。 キューの順序は保持されるため、概念的にはインデックスをシミュレートしますが、ポインタとイベントのタイミングを追跡することで物理的にキューを回転させることは避けます。 
3. ストリーク s を持つ現在のキング i について、s = 0 の場合は A_i、s = 1 の場合は B_i、s = 2 の場合は C_i としてその有効強度を決定します。 
4. j をキュー順序の次のチャレンジャーとします。 A_j と王の実効力を比較します。 A_j が大きい場合、j が新しいキングとなり、そのストリークは 1 になり、前のキングはキューの最後尾に移動します。 
5. キングが勝った場合、その連勝数が増加します。 連勝が 3 になった場合はすぐに停止し、キングと総戦闘数を出力します。 
6. このプロセスを続行し、償却ローテーションを使用したデキューやポインタを使用したインデックス付きシミュレーションなど、完全な再エンキュー操作を回避する構造を使用してキューの位置を慎重に更新します。 
7. システムが以前に確認された構成 (キング、ストリーク、相対キュー順序) に戻る場合は、永久にループすると結論付け、-1 -1 を出力します。 

### なぜ効果があるのか

 重要な不変条件は、システムのすべての状態が現在のキング、そのストリーク、およびキューの相対的な循環順序によって一意に決定されるということです。 遷移ごとにキングのストリークが増加するか、キングが変更されるため、意味のある個別の状態の数は、動物の数×3 ストリーク レベル×可能な循環シフトによって制限されます。 

プロセスは状態をスキップできないため、構成が繰り返されると、システムは 3 連続に向けて進行しないサイクルに入ります。 逆に、ストリークが 3 に達した場合は、固定キングの単一チェーンに沿ってストリークが厳密に増加するため、それがその状態の最初の発生である必要があります。 

したがって、シミュレーションはストリーク 3 で吸収に達するか、繰り返しによって検出されるサイクルに入ります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

def solve():
    n = int(input())
    A = []
    B = []
    C = []
    for _ in range(n):
        a,b,c = map(int,input().split())
        A.append(a)
        B.append(b)
        C.append(c)

    dq = deque(range(1,n))
    king = 0
    streak = 0
    fights = 0

    seen = set()

    def state():
        # compress state: king, streak, and queue snapshot (expensive but conceptual)
        return (king, streak, tuple(dq))

    while True:
        if streak == 3:
            print(king, fights)
            return

        # cycle detection (for correctness description; optimized solutions avoid full snapshot)
        st = (king, streak, tuple(dq))
        if st in seen:
            print(-1, -1)
            return
        seen.add(st)

        if not dq:
            print(-1, -1)
            return

        challenger = dq.popleft()
        fights += 1

        king_power = A[king] if streak == 0 else (B[king] if streak == 1 else C[king])
        challenger_power = A[challenger]

        if king_power > challenger_power:
            streak += 1
            dq.append(challenger)
        else:
            dq.append(king)
            king = challenger
            streak = 1

if __name__ == "__main__":
    solve()
```コードは文字通りのプロセスに従います。 キューはデキューに格納されるため、フロント チャレンジャーは O(1) でアクセスされます。 キングのパワーは、そのストリークに基づいて動的に計算されます。 戦闘ごとにカウンターが増加し、状態が更新されます。 

サイクル検出では両端キューの完全なスナップショットが使用されます。これは完全な制約には十分効率的ではありませんが、概念的な正確性の議論には一致します。 受け入れられた実装では、このスナップショットは、構造的不変条件に対するよりコンパクトなハッシュ戦略に置き換えられるか、遷移に対するより強力な単調性引数の使用を完全に回避します。 

最もデリケートな部分は連勝の移行の処理です。負けた後、新しいキングは常に連勝 1 から始まり、0 になることはありません。これは、キングになる行為がその動物の 1 回の連続勝利状態として即座にカウントされることを反映しています。 

## 実用的な例

 ### トレースの例

 キューの順序が少なく、すぐに終了するという単純化されたシナリオをシミュレートします。 

| 戦う | キング | ストリーク | チャレンジャー | キングパワー | チャレンジャーパワー | 結果 |
 | --- | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | 1 | A0 | A1 | 1勝 |
 | 2 | 0 | 1 | 2 | B0 | A2 | 2勝 |
 | 3 | 0 | 2 | 3 | C0 | A3 | 0勝 |

 戦闘 3 の後、動物 3 がストリーク 1 でキングになります。 

これは、連勝によって王の強さがどのように変化するか、そして一度の敗北がシステムの制御をどのようにリセットするかを示しています。 

このトレースは、強さは動物ごとに静的ではなく、同じ動物がそのストリークの状態に応じて優勢になることも負ける可能性があることを示しています。

 ## 特殊なケース

 特殊なケースの 1 つは、最初のキングが 2 回連続で勝つほど強くない場合に発生します。 このような場合、継続的に負けてキューに再入力されるため、ストリークの蓄積が防止されます。 このシステムは、進歩なしにすべての動物を循環させることができるため、繰り返しの検出が強制されます。 

別のケースは、1 匹の動物が厳密に優勢な C_i を持っているが A_i が弱い場合に発生し、2 勝した後でのみ強くなる場合です。 これにより、収束が大幅に遅れ、ストリーク 3 への最終移行前に部分的な優勢の長いチェーンが作成される可能性があります。 

最後の重要なケースは、システムが、キングと 1 人の挑戦者が繰り返し交代する構成に入る場合です。 キューは実質的に周期的になり、サイクル検出がなければシミュレーションは無限に実行されることになります。
