 ## 解決策
 ## 問題の理解

 トランポリンの強さを一列に並べて与えられます。 各トランポリンは強制ジャンプのように動作します: ペコラが所定の位置に着地した場合`i`、彼女はすぐに発射されます`i + S[i]`。 トランポリンを使用すると、その強さは 1 ずつ減少しますが、1 を下回ることはなく、最終的にはすべてのトランポリンは強さ 1 で安定します。 

単一の「パス」は強制ジャンプの連鎖です。 ペコラは開始トランポリンを選択し、右側のアレイから離れるまでジャンプを追い続けます。 彼女はパスを早く中断することはできません。 目標は、このようなパスを複数回実行して、すべてのトランポリンの強さをちょうど 1 つに減らし、パスの数を最小限に抑えることです。 

パスでトランポリンが使用されるたびに、正確に 1 つのデクリメントが発生します。そのため、実際の制約は、絶対的にどれだけ遠くまでジャンプするかではなく、時間の経過とともに変化する決定的なジャンプ リンクにパスが従うことを考慮しながら、すべてのパスにわたって各インデックスが何回アクセスされるかということです。 

この制約により、素朴な意味での総当たりシミュレーションは不可能になります。 と`n`最大 5000、最大 1e9 の値の場合、すべての開始点を繰り返し試行したり、単位減分ごとにすべてのパスを段階的にシミュレートしたりする戦略は、テスト ケースごとに二次関数またはさらに悪い動作に退化します。 合計以来`n`オーバーテストも 5000 です。`O(n^2)`または`O(n^2 log n)`このアプローチは境界線に近いかもしれませんが、定数が大きい場合には依然として危険です。 立方体的なものはすぐには実現不可能です。 

トリッキーなエッジの動作は、大きなジャンプと強度の減少との間の相互作用から生じます。 大きな値は独立して動作すると単純に予想されますが、実際には、単一のパスが固定等差数列内の複数の離れた位置に影響を与える可能性があり、値がどのように縮小するかに応じて、後のパスでそれらのパスが再利用される場合とされない場合があります。 

具体的な落とし穴がいくつかあります。 

「常に最大の残りの値から開始する」という単純な欲張りな考えも考えられますが、中間の削減に応じて 1 つのパスがそれらの位置に到達する場合もあれば、到達しない場合もあるため、これは失敗します。 たとえば、初期の位置に非常に大きな値がある場合、後から開始するパスはそれらの位置に到達できない可能性があるため、ローカルの貪欲な順序付けにより、グローバルな到達可能性構造が破壊されます。 

もう 1 つの微妙な問題は、各ポジションを独立して処理できると想定していることです。 たとえば、1 つの 100 を除くすべての値が 2 の場合、単純なソルバーは、100 にはその位置から始まる 99 個の個別のパスが必要であると考えるかもしれませんが、実際には、トラバース パスに応じて多くの減分がパス間で共有される可能性があります。 

重要な隠された構造は、各パスが決定論的なウォークを誘発し、すべての訪問が非常に制御された方法で将来の構造をシフトすることです。 

## アプローチ

 ブルート フォース ビューでは、パスを明示的にシミュレートします。 各パスでは、開始インデックスを選択し、配列を終了するまでジャンプ チェーンをシミュレートし、訪問したすべての位置をデクリメントします。 すべての値が 1 つになるまで繰り返します。 これは問題定義に正確に従っているので、これは正しいです。 

ただし、コストは法外です。 各パスは O(n) 個の位置を横断することができ、最悪の場合、一部の位置には O(max S_i) 回のパスが必要となり、複雑さが爆発的に実現可能な限界を超えてしまう可能性があります。 

重要な観察は、視点を反転することです。 パスの観点から考えるのではなく、各ポジションが将来のポジションに与える貢献の観点から考えます。 定位置に着地するたびに`i`、への訪問を「スケジュール」します。`i + S[i]`。 したがって、すべてのインデックスは別のインデックスへの有向エッジを作成し、そのプロセスは重みが減少するにつれてゆっくりと縮小する関数グラフに対する動的な走査になります。 

重要な構造的洞察は、エッジは時間の経過とともに変化しますが、各インデックスのターゲットは左方向にのみ移動するということです（`S[i]`減少します）。 これは、各ノードの出力エッジが単調にのみ「スライド」できることを意味し、各単位の減少は有効な構造変化の制限された数に対応します。 

私たちは貢献をスイープのような方法で処理できます。つまり、ポジションが使用されると、そのターゲットに「ニーズ」が伝播されます。 各ポジションに何回エントリーする必要があるかを維持し、同じパス内でチェーンされない限り、各エントリーは正確に 1 つのパス貢献に対応します。 

これにより、問題は、必要な訪問の動的な蓄積を維持し、すべての伝播チェーンを満たすために必要な独立した開始点の数を数えることに軽減されます。 最終的な答えは、すでに進行中の伝播ではカバーできないチェーンを開始する必要がある回数に対応します。

 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n * 最大 S) | O(n) | 遅すぎる |
 | 伝播 / 貪欲なフローの蓄積 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 このプロセスを、各インデックスから現在の宛先までの依存関係フローを構築するものと解釈します。`i + S[i]`。 各位置には「受信需要」が蓄積されます。これは、すべてのパスにわたってその位置を何回訪問する必要があるかを意味します。 

1. 配列を初期化する`need`サイズの`n + 2`各ポジションを何回アクティブにする必要があるかを追跡します。 まだ走査をスケジュールしていないため、最初はすべての値がゼロです。 
2. インデックスを左から右に移動します。 各インデックスで`i`、最初に、初期の伝播によりこの位置をまだ何回訪問する必要があるかを考慮します。 もし`need[i] > 0`、それらのそれぞれを進行中のパスの一部として扱い、その効果を前方に伝播します。 
3. 毎回の位置`i`が使用されると、強制的に次への移行が行われます。`i + S[i]`。 追加します`need[i]`に`need[i + S[i]]`。 これは、必要なすべての訪問が`i`チェーンを前に続けます。 
4. 伝播後、いくつの新しいパスを開始する必要があるかを決定します。`i`。 「カバーされていない要件」が残っている場合は、`i`、これは、以前のチェーンがそこに到達していないことを意味するため、そのような各ユニットは新しいパスの開始に対応します。 それに応じて答えを増やします。 
5. 使用してから`i`強度は概念的に減少しますが、減少を明示的にシミュレートしません。 その代わりに、単調な伝播は、繰り返しの寄与が必要な訪問ごとに正確に 1 回前方に流れることを保証することによって、将来の弱体化をすでに考慮しています。 

### なぜ効果があるのか

 各パスは一連の決定論的な前方ジャンプとして見ることができ、インデックスの昇順で左から右への寄与の連鎖を引き起こします。 インデックスを順番に処理すると、すべての受信コントリビューションが`i`はすでに決まっています。 残りの赤字は`i`正確に始まる新しいパスから開始する必要があります`i`、以前のインデックスは到達できないため、`i`すでに計上されていない状態で`need[i]`。 伝播により、各訪問が同じチェーン構造を継続することが保証されるため、チェーンを分割する必要はなく、マージは蓄積によって自然に行われます。`need`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        s = list(map(int, input().split()))
        
        need = [0] * (n + 5)
        ans = 0
        
        for i in range(n):
            if need[i] > 0:
                jump = i + s[i]
                if jump <= n:
                    need[jump] += need[i]
            
            if need[i] == 0:
                continue
            
            ans += need[i]
            jump = i + s[i]
            if jump <= n:
                need[jump] += need[i]
            
            need[i] = 0
        
        print(ans)

if __name__ == "__main__":
    solve()
```コードは単一の伝播配列を維持します。`need`、現在各位置を通過するトラバース チェーンの数を追跡します。 メインループはインデックスを昇順に処理するため、すべての受信チェーンが各ステップですでに認識されています。 

各インデックスで、保留中のチェーンは前方に続行されるか、チェーンが存在しない場合は新しいパスを開始する必要があります。 ジャンプの計算`i + s[i]`トランポリン遷移をエンコードし、境界により配列を超えた出口を無視することが保証されます。 

実装の微妙な選択がリセットされる`need[i]`加工後。 これにより、以前の複数のインデックスが同じ位置に伝播する場合の二重カウントが防止されます。

 ## 特殊なケース

 重要なエッジ ケースは、すべての値がすでに 1 である場合です。その状況では、伝播はまったく起こらないため、アルゴリズムは答えをインクリメントしません。 これは安全なので、`need[i]`全体を通してゼロのままです。 

もう 1 つのケースは、値が非常に大きい場合です。 たとえば、次の場合`S[1] = 10^9`の場合、ジャンプはすぐに配列から出てしまうため、インデックスはそれ以上の伝播に寄与しません。 アルゴリズムはこれを自然に処理します。`i + S[i] > n`単に更新を破棄します。 

最後の微妙なケースは、複数のインデックスが同じターゲットに伝播する場合です。 なぜなら`need`カウントが蓄積されると、これらのマージは自然に結合され、各ユニットは依然として独立した必要な訪問として扱われ、複数のチェーンが収束した場合でも正確さが維持されます。
