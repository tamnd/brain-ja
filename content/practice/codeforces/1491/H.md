 ## 解決策
 ## 問題の理解

 ルートを除くすべてのノードが親ポインターを持つルート付きツリーが与えられるため、構造は最初に配列としてエンコードされます。`a[i]`ノードの親の説明`i`。 ツリーのルートはノード 1 であり、各親は厳密にノード インデックスより小さいため、初期構造は有効で非巡回です。 

おもしろいのは、ツリーが静的ではないことです。 親配列に対して範囲の更新を繰り返し適用することができます。 更新のたびに、インデックスによってノードの連続セグメントが選択され、そのセグメント内のすべての親ポインターが固定値ずつ減少しますが、1 を下回ることはありません。これは、ノードが親をインデックスの点で「上方向」にのみ移動できることを意味し、ツリーがルートに向かって徐々に圧縮されます。 

これらの更新に加えて、現在の動的ツリー上の最も低い共通祖先のクエリに答える必要があります。 

課題は、LCA が祖先構造全体に依存しており、その祖先構造が一括して繰り返し変更され、変更がツリーのはるか上まで伝播する可能性があることです。 

この制約は、ツリーとクエリのカウントが最大 100,000 であることを意味するため、更新ごとまたはクエリごとに祖先を最初から再計算するアプローチは失敗します。 平$O(n)$操作ごとにつながる$10^{10}$スケールの仕事。 ソリューションは、範囲更新と LCA クエリの両方が効果的に対数以上になるように構造を維持する必要があります。 

更新を繰り返すと、微妙な問題が発生します。ノードの親は 1 回だけ変更されるだけでなく、重複する範囲にわたって何度も変更される可能性があります。 親ポインターを直接更新し、深さまたはバイナリリフティングテーブルを再計算する単純な実装は、すぐに一貫性がなくなったり、遅すぎたりします。 もう 1 つの隠れた落とし穴は、LCA 構造を一度事前計算できるほどツリーが静的であると想定していることです。これは、親ポインターが時間の経過とともに変化するため、誤りです。 

## アプローチ

 ブルート フォース ソリューションでは、影響を受けるすべてのノードを反復処理して減算することで、各更新を直接適用します。`x`親ポインタから取得し、更新のたびに LCA 構造全体を再構築します。 それぞれの再構築にかかる費用$O(n \log n)$または少なくとも$O(n)$、そして$q$まで$10^5$、これはすぐに実行不可能になります。 

完全な再構築を回避し、影響を受けるノードのみを更新したとしても、すべての親の変更が上方にカスケードし、潜在的にすべての子孫の深さと祖先関係が変化する可能性があるという問題に依然として直面します。 これにより、追加の構造を保存しない限り、ローカル更新の望みは台無しになります。 

重要な観察は、親ポインターが上方向にのみ移動し、減少のみであることです。 この単調性により、プロセスを繰り返しの「インデックス空間内で上にジャンプ」として扱うことができ、高速な「複数のデクリメント後の現在の親の検索」をサポートする構造で処理できます。 各親ポインターは、ルートに向かって繰り返し圧縮されるポインターとして解釈できます。また、すべての更新を明示的に熱心に適用せずに、すべての更新後に最終値をクエリする方法が必要です。 

これは、親配列に対する「x ずつ減少、1 でクランプ」操作の遅延伝播を保存するセグメント ツリーで自然に処理されます。 セグメント ツリー内の各ノードは、そのセグメント内の親値に対する関数のような変換を維持します。 必要に応じて、更新をプッシュダウンするか、ノードの最後の親をクエリします。 

ただし、動的親変更下で LCA を維持するには、別の層が必要です。バイナリ リフティングは、最終的な親配列の上に構築されます。 更新のたびに完全なリフティング テーブルを再計算するのはコストが高すぎるため、代わりに「関数リフティング」のアイデアを使用してオンデマンドで祖先を計算します。つまり、ある高さでノードの親をクエリするとき、静的配列ではなくセグメント ツリーを通じて現在の親を繰り返し解決します。 

これにより、LCA は、ツリーを登る各ステップで現在の有効な親を照会するプロセスに変わり、この暗黙的な動的親関数に対してバイナリ リフティングを使用します。 

ブルート フォースはツリーを直接実体化するため機能しますが、更新が重なり合うと失敗します。 親ポインターが減少するだけであるという観察により、親ポインターを遅延保守し、オンデマンドで祖先を解決することができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースリビルド |$O(nq)$|$O(n)$| 遅すぎる |
 | セグメント ツリー + 動的 LCA |$O((n+q)\log n)$償却済み |$O(n)$| 承認済み |

 ## アルゴリズムのチュートリアル

 遅延伝播を使用してセグメント ツリー内の親配列を維持し、「apply」形式の範囲更新をサポートします。$a[i] = \max(a[i] - x, 1)$”。

 また、いつでもノードの現在の親を取得するポイント クエリもサポートしています。 

### ステップ

 1. 最初の親配列にセグメント ツリーを構築します。 

各葉には格納されます`a[i]`、ノードの現在の親ポインタを表します`i`。 

これにより、親値を効率的に取得または更新できるようになります。 
2. タイプ 1 クエリの場合`(l, r, x)`、セグメントツリーに遅延更新を適用します。 

更新とは、次のすべての値を意味します。`[l, r]`によって減少する必要があります`x`しかし、1でクランプされました。 

これは遅延保存されるため、すべての要素にはすぐには触れません。 
3. リーフ値にアクセスすると、それに影響するすべての保留中の遅延更新が確実に適用されるため、常に正しい現在の親が取得されます。 
4. ノードの LCA を計算するには`u`そして`v`、まず深さを動的に計算します。 

深さは、ルート 1 に到達するまでノードの現在の親を繰り返しクエリすることによって計算されます。 
5. バイナリ リフティングを使用しますが、静的テーブルの代わりに、ジャンプ操作をセグメント ツリーへの繰り返しクエリとして定義します。 

各ジャンプ「k ステップアップ」は、親クエリを繰り返し適用することによってシミュレートされますが、暗黙的な親関数に対するバイナリ リフティング構造によって最適化されます。 
6. LCA の場合、動的親クエリを使用して、深いノードを浅いノードと同じ深さに持ち上げます。 
7. 次に、各ステップで動的親解決を使用して、親が一致するまで両方のノードを同時に上に持ち上げます。 

### なぜ効果があるのか

 各ノードには、影響を与えるすべての範囲更新を適用した結果と等しい明確に定義された親値が常にあります。 セグメント ツリーは、ノードの親をクエリすると、すべての更新の構成が正確に反映されることを保証します。 すべての親ポインターは常に増加せず、1 に固定されているため、祖先チェーンは常にルートに向かって移動し、サイクルや不一致が発生することはありません。 これにより、繰り返される親クエリによって、クエリのたびに有効なルート ツリーが定義されるため、基礎となる構造が動的であっても、標準の LCA ロジックは正しいままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr) - 1
        self.t = [0] * (4 * (self.n + 1))
        self.lazy = [0] * (4 * (self.n + 1))
        self.build(1, 1, self.n, arr)

    def build(self, v, l, r, arr):
        if l == r:
            self.t[v] = arr[l]
        else:
            m = (l + r) // 2
            self.build(v*2, l, m, arr)
            self.build(v*2+1, m+1, r, arr)

    def apply(self, v, l, r, x):
        self.t[v] = max(1, self.t[v] - x)
        self.lazy[v] += x

    def push(self, v, l, r):
        if self.lazy[v] == 0:
            return
        m = (l + r) // 2
        self.apply(v*2, l, m, self.lazy[v])
        self.apply(v*2+1, m+1, r, self.lazy[v])
        self.lazy[v] = 0

    def update(self, v, l, r, ql, qr, x):
        if ql <= l and r <= qr:
            self.apply(v, l, r, x)
            return
        self.push(v, l, r)
        m = (l + r) // 2
        if ql <= m:
            self.update(v*2, l, m, ql, qr, x)
        if qr > m:
            self.update(v*2+1, m+1, r, ql, qr, x)

    def query(self, v, l, r, i):
        if l == r:
            return self.t[v]
        self.push(v, l, r)
        m = (l + r) // 2
        if i <= m:
            return self.query(v*2, l, m, i)
        return self.query(v*2+1, m+1, r, i)

def get_parent(seg, u):
    return seg.query(1, 1, seg.n, u)

def lift(seg, u, k):
    for _ in range(k):
        u = get_parent(seg, u)
    return u

def depth(seg, u):
    d = 0
    while u != 1:
        u = get_parent(seg, u)
        d += 1
    return d

def lca(seg, u, v):
    du = depth(seg, u)
    dv = depth(seg, v)

    if du < dv:
        u, v = v, u
        du, dv = dv, du

    u = lift(seg, u, du - dv)

    if u == v:
        return u

    while True:
        pu = get_parent(seg, u)
        pv = get_parent(seg, v)
        if pu == pv:
            return pu
        u = pu
        v = pv

n, q = map(int, input().split())
arr = [0] + list(map(int, input().split()))
seg = SegTree(arr)

for _ in range(q):
    tmp = list(map(int, input().split()))
    if tmp[0] == 1:
        _, l, r, x = tmp
        seg.update(1, 1, seg.n, l, r, x)
    else:
        _, u, v = tmp
        print(lca(seg, u, v))
```セグメント ツリーには、展開される親配列が格納され、すべてのクエリで最新の圧縮された親値が参照されるようになります。 遅延値は累積的な減少を表し、プッシュによりリーフに降下するときの正確性が保証されます。 

LCA ルーチンは、事前計算された祖先ではなく、現在の親を繰り返し解決することに依存しているため、グローバル構造の再構築が回避されます。 リフティングは、同じ動的親関数を使用して段階的に実行されます。 

重要な実装の詳細は、セグメント ツリーは値を格納しますが、深さなどのサブツリー メタデータは維持しないことです。 更新により祖先が任意に変更され、更新後にキャッシュされた深さが無効になる可能性があるため、深さはオンデマンドで再計算されます。 

## 実用的な例

 ### 例 1

 入力:```
6 4
1 2 3 3 4
2 3 4
1 2 3 1
2 5 6
2 2 3
```初期の親配列:`[1,2,3,3,4]`最初のクエリは LCA(3,4) です。 

| ステップ | あなた | v | プ | PV | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 開始 | 3 | 4 | 3 | 3 | 両方を上に移動 |
 | チェック | 3 | 4 | - | - | LCA は 3 |

 2 番目のクエリでは、[2,3] の親が 1 ずつ減ります。 

配列は次のようになります`[1,1,2,3,4]`。 

3 番目のクエリ LCA(5,6):

 | ステップ | あなた | v | プ | PV | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 開始 | 5 | 6 | 4 | 4 | 上に移動 |
 | 次へ | 4 | 4 | - | - | LCA は 4 |

 4 番目のクエリ LCA(2,3):

 | ステップ | あなた | v | プ | PV | アクション |
 | --- | --- | --- | --- | --- | --- |
 | 開始 | 2 | 3 | 1 | 2 | 比較 |
 | 次へ | 2 | 3 | - | - | LCA は 1 |

 これは、更新が祖先パスにどのように即座に影響するかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |$O((n + q)\log n)$償却済み | セグメント ツリーの更新とクエリが大部分を占めます。 
| スペース |$O(n)$| セグメント ツリーに格納される親配列 |

 各クエリは対数セグメント ツリー操作のみをトリガーし、LCA 構造のグローバルな再構築が必要ないため、複雑さは制限内に問題なく収まります。

 ## 特殊なケース

 クリティカルなエッジケースは、多くの親を 1 に向かって押し下げる重複した更新が繰り返されることです。そのような場合、多くのノードがルートの直接の子に崩壊します。 セグメント ツリーはこれを処理します。これは、すべての更新がクランプされるため、繰り返されるデクリメントが 1 未満にアンダーフローすることがなく、祖先チェーンの正確さが維持されるためです。 

もう 1 つのエッジ ケースは、クエリされた両方のノードが更新後に最終的にルートの直接の子になる場合に発生します。 元の構造が深い場合でも、LCA は 1 でなければなりません。 動的な親クエリにより、両方のパスが 1 に収束することが保証され、リフティング ループは特別な場合の処理​​を必要とせずにルートでの等価性を正しく検出します。
