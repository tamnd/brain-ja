 ## 解決策
 ## 問題の理解

 長さの隠し配列が与えられます$n$ここで、各位置はカフェを表し、各カフェは正確に 1 種類のコーヒーを生産します。 位置の値$i$コーヒー品種のラベルです$a_i$, しかし、私たちはそれを直接見ることはありません。 

代わりに、カフェにクエリを実行すると、最後のスライディング ウィンドウに応じた 2 値の回答を受け取ることができます。$k$コーヒーを味わった。 クエリのさまざまな種類のカフェが最後に表示された場合$k$コーヒーを味見した場合、システムは肯定的に応答し、それ以外の場合は否定的に応答します。 各クエリの後、味見されたコーヒーは最大で次のサイズのキューに追加されます。$k$、古いエントリはドロップアウトされます。 この記憶はいつでもリセットできます。 

The task is to determine how many distinct values exist in the hidden array using only these noisy membership checks, while the adversary may even choose the array adaptively as long as answers remain consistent.

 主な問題は、各クエリが純粋な等価性テストではないことです。 これは履歴に依存するため、同じインデックスに対して繰り返しクエリを実行すると、以前のインタラクションに応じて異なる答えが得られる可能性があります。 

以来$n \le 1024$、ナイーブな$O(n^2)$インタラクション戦略はクエリ バジェット内で許容される可能性がありますが、それは慎重に制御されている場合に限られます。 ただし、メモリの適応的な性質により、クエリを不用意に再利用すると情報が破損する可能性があるため、安定した比較に依存するアプローチではメモリの状態を積極的に管理する必要があります。 

重複を直接検出しようとすると、微妙な障害モードが発生します。 たとえば、インデックスのクエリ$i$そして$j$リセットなしで交互に実行すると相互汚染が発生します。肯定的な答えは、等価性ではなく記憶履歴を反映している可能性があります。$a_i$そして$a_j$。 もう 1 つの問題は、「最初に見た」クエリが常に新規性を反映していると想定していることです。これは、ウィンドウから削除された後に同じ値が再び表示されるとすぐに壊れてしまいます。 

したがって、ソリューションでは、各クエリが既知のメモリ状態で解釈される、制御された環境をシミュレートする必要があります。 

## アプローチ

 直接的な強引なアイデアは、すべてのカフェを新品種の候補として扱い、それが以前に確認された代表的なものと一致するかどうかを確認することです。 すべてのペアを比較しようとするかもしれません$(i, j)$メモリをリセットし、両方のインデックスを慎重に調査します。 これには必要になります$O(n^2)$比較には、メモリ効果を安定させるために複数のクエリが含まれる可能性があります。 最悪の場合、クエリ バジェットが厳しい場合、これは遅くなりすぎます。 

重要な点は、メモリ ウィンドウが重要なのは「最近の履歴」だけであり、リセットを使用するとメモリ ウィンドウを完全に削除できるということです。 制御された比較ブロックの前にリセットすると、クエリの各シーケンスは白紙の状態から開始されます。つまり、答えは、現在のクエリが以前の実験ではなく、新しく構築されたウィンドウ内の要素と一致するかどうかのみに依存します。 

これにより、決定論的な調査パターンを構築できます。つまり、各インデックスを分離し、メモリ ウィンドウ内にどの値があるかを正確に知る制御された履歴を明示的に構築します。 次に、メンバーシップをウィンドウに強制し、後のクエリでそれが検出されるかどうかを観察することで、間接的に等価性をテストできます。 

標準的な高レベルの戦略は、リセットで区切られたセッションを使用してペアごとの比較をシミュレートすることです。 私たちは発見された代表者のセットを維持します。 新しいインデックスごとに、その代表値のみを含む制御されたメモリ ウィンドウを再構築し、新しいインデックスが一致を報告するかどうかを確認することによって、その値が既知の代表値と一致するかどうかをテストします。 

これにより、問題は、クリーンなメモリ環境で実行される「既知のクラスと等しい」チェックの繰り返しに軽減されます。

 ## アルゴリズムのチュートリアル

 私たちは代表的な指数のリストを管理しており、それぞれがこれまでに確認した異なるコーヒー品種を表しています。 

1. 空の代表リストから開始し、リセットを発行してメモリ状態が空であることを確認します。 これにより、後続のすべてのインタラクションが既知のベースラインから始まることが保証されます。 
2. すべてのカフェを反復処理します。$1$に$n$。 インデックスごとに$i$、既存の既知の品種に属するかどうかを判断します。 
3. 各代表者ごとに$r$、管理されたテストを実行します。 メモリをリセットしてからクエリを実行します$r$その通り$k$回。 これにより、次のことが保証されます$a_r$メモリウィンドウに存在します。 
4. この制御されたメモリ状態を構築した後、もう一度リセットして同じ状態を再構築しますが、代表値のみがウィンドウ内にあることを確認します。 次にクエリを実行します$i$。 この制御された設定の下で答えが肯定的であれば、次のように結論付けます。$a_i = a_r$。 

これが機能する理由は、同一に構築されたウィンドウの下で平等をメンバーシップに変換できるためです。 メモリは各テストの前に完全にリセットされるため、以前のチェックによる汚染はありません。 

1. 該当する代表者がいない場合$i$、追加します$i$新たな代表として。 
2. すべてのインデックスが処理されるまで続行します。 代表者の数が答えです。 

### なぜ効果があるのか

 すべての比較段階で、メモリ状態が最初から完全に再構築されます。つまり、クエリに対する答えは、そのセッションに明示的に挿入されたコーヒーのシーケンスのみに依存します。 これにより、以前のインタラクションへの依存性が取り除かれ、インタラクティブ システムが構築されたウィンドウの決定論的な関数に縮小されます。 各代表はその値のみを含むウィンドウによって一意に識別されるため、等価性チェックは一貫性があり推移的となり、各カフェが 1 つのクラスに正確に割り当てられるようになります。 したがって、最後に維持される代表値の数は、非表示配列内の個別の値の数と等しくなります。 

## Python ソリューション```python
import sys

input = sys.stdin.readline
print = sys.stdout.write

def query(x):
    print(f"? {x}\n")
    sys.stdout.flush()
    return input().strip()

def reset():
    print("R\n")
    sys.stdout.flush()

def main():
    n, k = map(int, input().split())

    reps = []

    # We will store one representative per discovered value
    for i in range(1, n + 1):
        found = False

        for r in reps:
            reset()

            # build memory: insert r k times
            for _ in range(k):
                query(r)

            # now test i in this controlled environment
            reset()
            for _ in range(k):
                query(r)

            ans = query(i)
            if ans == 'Y':
                found = True
                break

        if not found:
            reps.append(i)

    print(f"! {len(reps)}\n")
    sys.stdout.flush()

if __name__ == "__main__":
    main()
```この実装は、厳密にリセットで分離されたインタラクション ブロックを中心に構造化されています。 ヘルパー関数はクエリとリセット ロジックを分離して、フラッシュとフォーマットの一貫性を確保します。これは対話型の問題では重要です。 

代表的なループにより、不安定なメモリ状態に依存することがなくなります。 比較するたびに環境が最初から再構築されます。 二重リセット パターンにより、このタイプの問題で最も一般的な誤答の原因である、候補チェック間での残留状態のリークが発生しないことが保証されます。

 ## 特殊なケース

 重要なエッジ ケースは、同じ値が配列内で遠く離れて出現するため、その値がメモリ ウィンドウの外に現れる場合です。 このような状況では、リセットを行わない単純なアプローチでは、同じ値が誤って複数回新しい値として分類される可能性があります。 リセットベースの構造では、すべての等価性チェックが新しく構築されたメモリ状態で実行されるようにすることでこれを防ぎます。そのため、元の配列内の距離は無関係です。 

もう 1 つのエッジケースは次のような場合です$k = 1$。 ここで、メモリには最後にクエリされた要素のみが含まれるため、繰り返される値は制御されたウィンドウに挿入した直後に比較する必要があります。 このアルゴリズムの各テスト前のリセット構造は、履歴の永続性に依存しないため、正確性を保証します。 

最後のエッジケースは、敵対的適応行動です。 配列はクエリに依存する可能性があるため、固定された非表示構造を前提とする戦略は失敗します。 リセット分離により、すべての決定が一貫したローカル ビューから行われることが保証され、適応的な変更は以前に完了した比較とは無関係になります。
