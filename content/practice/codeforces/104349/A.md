 ## 解決策
 ## 問題の理解

 バイト単位で測定された生のファイル サイズが与えられており、バイト (B)、キビバイト (KiB)、およびメビバイト (MiB) の 3 つの可能な単位のみを使用して、コンパクトな「人間が判読できる」形式で表示する必要があります。 出力は常に単一の数値であり、その直後にこれらの単位文字列のいずれかが続きます。スペースは含まれません。 

各単位は 2 のべき乗のスケーリングに対応します。 1 KiB は 1024 バイトに相当し、1 MiB は 1024 KiB (1024 平方バイト) に相当します。 出力する数値は常に 1 ～ 1023 の整数である必要があり、単位間で変換する場合は切り捨てる必要があります。 

したがって、タスクは、変換後の値が 1 以上、最大 1023 になるような可能な限り最大の単位を選択し、その単位で下限整数を出力することです。 

m の制約は 10^9 までですが、これは十分小さいので、1024^2 は約 10^6 であり、1024^3 はすでに 10^9 を超えているため、最大でも MiB スケールしか扱いません。 これは、決定空間が非常に浅いことを意味します。B、KiB、および MiB のみが重要です。 

境界をチェックせずに常に上向きに変換したり、常に貪欲に正規化しようとすると、単純な間違いが発生します。 たとえば、1401 バイトを 1401 B として扱うことは、1401 が 1023 を超えるため無効ですが、これを KiB に変換すると、フロアリング後の 1 KiB が得られ、これは有効です。 もう 1 つの落とし穴は、数値が [1, 1023] 以内に収まらなければならないというルールを失うことです。これにより、数学的に正しい場合でも 0 MiB や 0 KiB のような出力が禁止されます。 

もう 1 つの微妙な問題は順序付けです。最初に KiB を試行し、次に MiB を試行すると、MiB が有効な場合でも、誤って小さい単位を選択してしまう可能性があります。 たとえば、14510629 バイトは 13 MiB である必要がありますが、丸め後の方が「早く適合する」ため、不用意にアプローチすると KiB で停止する可能性があります。 

## アプローチ

 強引なアイデアは、3 つのユニットすべてを個別に試してみることです。 単位ごとに、整数の除算を使用して変換された値を計算し、それが有効な範囲 [1, 1023] 内にあるかどうかを確認します。 複数の単位が有効な場合は、その中で最大の単位が選択されます (B よりも KiB よりも MiB)。 これが機能するのは、候補が 3 つだけであり、各変換が定数時間であるためです。 

この非効率性は、多くのユニットや繰り返しの再計算を含む一般化されたバージョンを想像した場合にのみ現れますが、それでも構造は十分に単純であるため、実際にはブルート フォースがすでに最適化されています。 

重要な観察は、単位系が厳密に階層的であり、各ステップが 1024 の因数であるということです。これは、動的に検索したり最適化したりする必要がないことを意味します。 必要なのは、固定定数による割り算をテストし、床材の割り算を適用することだけです。 数値範囲の制約により、有効な表現が 1 つだけ強制されるため、答えは商を範囲内に保つ最高の単位によって決まります。

 ## アルゴリズムのチュートリアル

 各テストケースを個別に評価します。 

1. 指定されたバイト単位のサイズ m から開始します。 これが基本表現であり、他のすべての単位は 1024 による除算を繰り返すことで得られます。 
2. MiB で値を表現できるかどうかを確認します。 m // (1024 * 1024) を計算します。 結果が 1 以上、最大 1023 の場合は、すぐに単位として MiB を選択します。 これは、MiB が許容される最大の単位であり、最も圧縮された表現が必要であるためです。 
3. MiB が有効でない場合は、KiB を確認します。 m // 1024 を計算します。この値が [1, 1023] にある場合、その数値で KiB を出力します。 
4. MiB も KiB も機能しない場合は、バイトに戻り、m B を直接出力します。 この時点で m はすでに [1, 1023] になければなりません。そうでなければ KiB が有効になるからです。 
5. 選択した数値を単位文字列と連結して出力​​します。

これが機能する理由は、base-1024 スケーリングの構造からわかります。 各単位は前の単位の正確に 1024 倍であるため、変換された値は整数除算によって一意に決定されます。 出力番号が [1, 1023] のままでなければならないという制約により、フロアリング後に最大 1 つのユニット レベルが条件を満たすことが保証されます。 MiB が KiB を支配し、KiB が B を支配するため、最も高い有効なユニットを選択すると、有効な小さい表現をスキップしたり、有効な大きい表現を見逃したりすることはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        m = int(input())

        mib = m // (1024 * 1024)
        if 1 <= mib <= 1023:
            print(str(mib) + "MiB")
            continue

        kib = m // 1024
        if 1 <= kib <= 1023:
            print(str(kib) + "KiB")
            continue

        print(str(m) + "B")

if __name__ == "__main__":
    solve()
```ソリューションはユニット階層に直接従います。 MiB チェックは、有効であれば最もコンパクトな表現を生成するため、最初に実行されます。 KiB チェックは MiB が失敗した場合にのみ到達し、両方のスケーリングされた表現が許容される数値境界を超えるか小さすぎる場合にのみバイトが使用されます。 整数の除算では、必要な切り捨て動作が自然に強制されるため、追加の丸めロジックは必要ありません。 

よくある実装上の間違いは、MiB の前に KiB をチェックすることです。これにより、最適ではない単位が生成される可能性があります。 もう 1 つは、下限 1 を忘れることです。これにより、1024 未満の小さな値に対して 0 KiB のような無効な出力が発生する可能性があります。 

## 実用的な例

 まず、入力 m = 1401 について考えます。 

| ステップ | メートル | MiB | キロバイト | 選ばれた |
 | --- | --- | --- | --- | --- |
 | MiB を確認する | 1401 | 0 | - | いいえ |
 | KiB をチェック | 1401 | - | 1 | キロバイト |

 ここでは 1401 // 1024 = 1 となり、これは有効です。 MiB 変換では 0 が得られますが、これは必要な最小数を下回っているため無効です。 アルゴリズムは KiB を正しく選択します。 

ここで、m = 14510629 について考えてみましょう。 

| ステップ | メートル | MiB | キロバイト | 選ばれた |
 | --- | --- | --- | --- | --- |
 | MiB を確認する | 14510629 | 13 | - | MiB |
 | 停止 | - | 13 | - | MiB |

 ここで、14510629 // 1048576 は 13 に相当します。これは [1, 1023] 内にあるため、MiB がすぐに選択されます。 MiB はすでに要件を満たしているため、KiB は評価されません。 

これらの例は、階層が一意の選択を強制する方法と、床材が単位変換とどのように相互作用するかを示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        m = int(input())

        mib = m // (1024 * 1024)
        if 1 <= mib <= 1023:
            out.append(str(mib) + "MiB")
            continue

        kib = m // 1024
        if 1 <= kib <= 1023:
            out.append(str(kib) + "KiB")
            continue

        out.append(str(m) + "B")

    return "\n".join(out)

# provided samples
assert run("3\n29\n1401\n14510629\n") == "29B\n1KiB\n13MiB"

# custom cases
assert run("1\n1\n") == "1B"
assert run("1\n1023\n") == "1023B"
assert run("1\n1024\n") == "1KiB"
assert run("1\n1048576\n") == "1MiB"
assert run("1\n1048575\n") == "1023KiB"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 | 1B | 可能な最小値 |
 | 1023 | 1023B | バイトの上限 |
 | 1024 | 1KiB | 正確な KiB 境界 |
 | 1048576 | 1MiB | 正確な MiB 境界 |
 | 1048575 | 1023KiB | MiB のすぐ下の境界 |

 ## 特殊なケース

 m = 1 の場合、MiB チェックでは 0 が返され、KiB チェックでも 0 が返されるため、アルゴリズムはバイトにフォールバックして 1B を出力します。 1024 未満の値を表現できるのはバイトのみであるため、これは正しいです。 

m = 1024 の場合、MiB は 0、KiB は 1 であるため、アルゴリズムは 1KiB を選択します。 これは、現在の単位が有効な数値範囲を超えたらすぐに次の単位に切り替える必要があるという要件に一致します。 

m = 1048576 の場合、MiB は 1 になり、これは有効であるため、アルゴリズムは 1MiB を直接選択します。 これは、最も高い有効な単位が常に優先され、1024 の正確なべき乗が曖昧さなくより高い単位にきれいにマッピングされることを示しています。
