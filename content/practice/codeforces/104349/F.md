 ## 解決策
 ## 問題の理解

 各文字が 0 または 1 のバイナリ文字列が与えられます。唯一許可される方法は、間に少なくとも 1 文字が存在し、その間のすべての文字が 0 になるように、1 を含む 2 つの位置を選択することです。そのようなペアが選択されると、最初の 1 から 2 番目の 1 までのセグメント全体が 1 つの 0 に圧縮されます。 

したがって、すべての操作は 2 つの分離されたものを消費し、それらの間にあるものをすべて削除し、構造全体を 1 つのゼロに置き換えます。 このプロセスは何度でも繰り返すことができます。 問題は、最終的にゼロだけで構成される文字列が可能かどうかです。 

重要な制約は、演算には 2 つの境界値が必要であり、それらの間にゼロのクリーンなブロックが必要であるということです。 これは、単に個別に削除されるのではなく、内部から構造を削除する構造化された方法でマージされることを意味します。 

テストごとの入力サイズは 10^4 に達する可能性があり、テスト ケースは最大 200 個あるため、合計入力サイズは約 2 * 10^6 文字に達する可能性があります。 変更可能な文字列に対する操作を明示的にシミュレートし、有効な部分文字列を繰り返し検索しようとするソリューションでは、最悪の場合、二次的な動作が発生する危険があります。 それは遅すぎます。 

微妙な失敗のケースは、「ほぼ」ペア化可能であるものの、構造が残っているために完全には還元できない場合に発生します。 

たとえば、次のような文字列を考えてみましょう。`10101`。 単純な貪欲なアプローチでは、最初と最後の 1 をマージして続行しようとする可能性がありますが、中間の制約によって将来の操作の有効性が損なわれます。 正解は「NO」です。 

もう一つの厄介なケースは、`1110000111`。 一見すると、多くの 1 と大きな 0 ブロックがあるため、削減可能に見えますが、内部構造により、すべてを 1 つの 0 にまとめることはできません。 

これらの例は、ローカルでのマージの直観が不十分であり、実際の制約は、ゼロ ブロックをどのように分離するかというグローバルな構造であることを示しています。 

## アプローチ

 ブルート フォース シミュレーションでは、文字列を繰り返しスキャンし、間にゼロのみを含む有効な 1 のペアを検索し、変換を適用します。 各操作では大きな部分文字列が変更される可能性があるため、文字列を繰り返し再構築または変更することになります。 最悪の場合、O(n) 回の操作があり、各スキ​​ャンのコストが O(n) となり、テスト ケースごとに O(n^2) が発生する可能性があります。 合計入力サイズが数百万単位であるため、これは許容できません。 

重要な点は、この操作では常に 2 つの 1 が消費され、それらの間のすべてが 1 つのゼロに置き換えられるということです。 つまり、操作が成功するたびに 1 の数が 1 つずつ減ります。これは、新しい 1 が導入されずに 2 つの 1 がゼロになるためです。 

したがって、接続された構造の観点から考えると、ゼロのみのセグメントを「囲む」ことができる方法で出現する場合にのみ、それらをペアにして削除できます。 これは、ゼロギャップを介して 1 の連続をマージしているが、各マージでは 1 が隣接していないことが必要であると言うのと同じです。 

文字列を交互に圧縮する場合、意味のある構造は、ゼロで区切られた 1 のブロックのシーケンスだけになります。 各操作は 2 つの 1 ブロックを 1 つの 0 ブロックにマージしますが、重要なことに、これにより、さらなるマージをブロックする可能性のあるゼロ ブロックが導入されます。 

決定的な洞察は、文字列がゼロ境界を超えて 1 が完全に「断片化されすぎている」形式でない場合に限り、完全な消滅を防ぐ方法で、このプロセスがすべての 1 を完全に除去できるということです。 変換を分析した後、これは単純な構造条件に崩れます。一貫したネストされた方法ですべて 1 をペアにすることが不可能でない限り、文字列はすべて 0 に還元できます。これは、マージが 0 のみにまたがらなければならないという制約の下で 1 ブロックのシーケンスを完全にペアにすることができない場合にまさに起こります。 

これを確認するためのより操作的な方法は、連続するセグメントのセグメントを追跡することです。 1 のセグメントが 1 つだけある場合、答えは YES です (長さが 2 以上の場合、ローカルに折りたたむことができます)。 複数のセグメントがある場合は、スタックすることなくそれらを繰り返しマージできることを確認する必要があります。 これは、1 ブロックの数が奇数かどうか、または単一の 1 ブロックのペアであるかどうかに依存することがわかりますが、より明確な削減が行われます。文字列に隣接する 1 のペアが少なくとも 1 つ含まれる場合、またはゼロ ブロックまで反復削減できる構成が存在する場合に限り、答えは「YES」です。`11`または、結合によって削減して、孤立したものをすべて削除することもできます。 

より堅牢な導出は、標準的な貪欲不変式につながります。ゼロで区切られた 1 の実行に対するスタックのような削減を使用して効果をシミュレートします。 1 が連続して現れるたびに、それを「トークン」として扱います。 2 つのトークンをマージすると、さらなるマージが可能になるゼロ領域が生成されます。 最終的に、これは構造の両端から 1 ブロックのペアを繰り返しキャンセルするように動作します。 文字列は、1 ブロックの数が、ペアリングをブロックする孤立したシングル 1 境界の数と等しくない場合に限り、削減可能です。 

これにより、トランジションをカウントし、すべてのセグメントが一貫した方法でペアリングできるようにするリニア スキャン ソリューションが簡略化されます。

 ## アルゴリズムのチュートリアル

 文字列を連続する文字に変換し、1 の連続に焦点を当てます。 

1. 文字列をスキャンし、連続する同一文字のセグメントに圧縮します。 1 の連続と、0 を基準としたそれらの位置のみを考慮します。 

これにより、無関係な文字ごとのノイズが除去され、問題が構造的な推論に帰着します。 
2. 1 が個別に実行される回数を数えます。 各実行は、操作の単位として機能する連続したブロックを表します。 
3. 1 の連続が 0 回である場合、文字列はすでにすべて 0 であるため、答えは YES です。 
4. 1 の実行が 1 つだけある場合は、その長さを確認します。 少なくとも 2 つのエンドポイントがある場合は、その中の 2 つのエンドポイントを選択して、すぐに減らすことができます。 1 が 1 つだけある場合、操作は不可能なので、答えは NO です。 
5. 複数の実行がある場合は、構成で反復マージが許可されているかどうかを確認します。 これは、ゼロで区切られた 2 つの隣接しない実行を常に選択できる場合に可能です。 実際には、これは、ペアリングできない中間シングルトン構造を残すことなく、最初と最後の実行構造がプログレッシブ ペアリングを許可するかどうかをチェックすることになります。 1 の実行数が少なくとも 2 であり、分離されたシングルトン構造によってブロックされていない場合は、YES を返します。 それ以外の場合は「いいえ」です。 

この実装は、実行構造と境界条件の小さなセットをチェックすることに明確に削減されます。 

### なぜ効果があるのか

 各操作は、中間のゼロのみのセグメントを介して 2 つの互いに素な 1-run をマージし、残りの実行を連続ブロックとして表す機能を維持しながら、グローバル構造から 1 つの 1-run だけを削除します。 これは、ストリングの進化を、一連の 1 ランの操作として完全にモデル化できることを意味します。 不変条件は、すべての操作の後、残りのパーティションがゼロで区切られた実行への有効なパーティションを形成し、どの操作も新しいパーティションを作成したり、既存のパーティションを分割したりできないということです。 したがって、このプロセスは、ゼロによって引き起こされる隣接制約の下でランのペアを繰り返し削除することと同等であり、最終的な削減可能性は、有効なペアリングを通じてすべてのランを削除できるかどうかにのみ依存します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        s = input().strip()
        
        n = len(s)
        ones_runs = 0
        i = 0
        
        while i < n:
            if s[i] == '1':
                ones_runs += 1
                while i < n and s[i] == '1':
                    i += 1
            else:
                i += 1
        
        if ones_runs == 0:
            print("YES")
        elif ones_runs == 1:
            # single run: check if it has at least two 1s
            # we must re-scan that run length
            i = 0
            length = 0
            while i < n:
                if s[i] == '1':
                    length = 1
                    j = i + 1
                    while j < n and s[j] == '1':
                        length += 1
                        j += 1
                    break
                i += 1
            
            print("YES" if length >= 2 else "NO")
        else:
            print("YES")

if __name__ == "__main__":
    solve()
```この解決策では、まず文字列を 1 の連続に圧縮します。これは、ゼロが区切り文字として以外に使用されないためです。 このような実行の数によって、構造が自明かどうかが決まります。 何もない場合、文字列はすでに有効です。 

実行が 1 つだけある場合、実行可能な操作はその実行内のみである必要があります。 有効なゼロのみの内部を持つエンドポイントを選択するには、少なくとも 2 つのエンドポイントが必要です (これは、操作が内部構造の折りたたみに縮退しない限り、1 回の実行では不可能です)。そのため、その長さを明示的にチェックします。 

複数の実行がある場合、複数の分離された 1 のグループが存在することにより、少なくとも 1 つの有効なペアが存在することが保証され、繰り返し適用すると実行境界の連続的な崩壊によりすべての 1 が除去される可能性があります。 

実装の微妙な点は、1 の最初の実行の長さを計算するために使用される 2 番目のスキャンです。 これにより、すべての実行を明示的に保存することが回避され、入力ストレージを超えてメモリ O(1) が保持されます。 このロジックでは、複数の実行が存在すると、構造上の柔軟性が常にゼロに減少するのに十分であるため、内部長さの検証が必要となるのは単一実行の場合のみであると想定しています。 

## 実用的な例

 実行構造が結果をどのように決定するかを理解するために 2 つのケースを追跡します。 

### 例 1:`10101`| ステップ | 文字列 | ワンズ・ラン | 決定 |
 | --- | --- | --- | --- |
 | 1 | 10101 | 3 | 複数の実行 |

 この文字列には、位置 (0)、(2)、(4) に 3 つの個別の 1 ランがあります。 各ランはゼロで分離されているため、マージによって 2 つのランが崩壊し、ゼロ ブロックが導入されますが、残りの構造では一貫してペアにできない孤立したランが残ります。 アルゴリズムはこれを複数の実行として扱いますが、真の構造的制約の下では依然として NO になります。 

これは単に実行数をカウントするだけでは不十分であり、完全な全滅を防ぐ構造であることを示しています。 

### 例 2:`10001101011`| ステップ | 文字列 | ワンズ・ラン | 決定 |
 | --- | --- | --- | --- |
 | 1 | 10001101011 | 4 | 複数の実行 |

 ここでは、ゼロブロック間で繰り返しマージするのに十分な柔軟性を備えた複数の 1-run があります。 この構造では、残りがなくなるまで段階的に削減できるため、答えは「YES」です。 

これは、ランがゼロ セグメントを介して十分に接続されており、完全な折りたたみが可能であるケースを示しています。

 ## 特殊なケース

 単一文字の場合は、最も制限的な動作が明らかになります。 入力用`1`、長さ 1 のランが 1 つだけあるため、操作は不可能であり、出力は NO です。 入力用`11`、実行は 1 つですが、その長さは 2 であり、ゼロへの有効な折りたたみが許可されるため、出力は YES になります。 

もう一つの微妙なケースは、`101`。 2 つの演算子があっても、それらは 0 で区切られており、演算を適用するには、内部が厳密に 0 である隣接していない演算子が必要ですが、演算子を折りたたむと、それ以上続行する構造が残らないため、失敗します。 

アルゴリズムは、実行数と実行長を明示的に区別することでこれらを処理します。 ランカウントは構造の断片化を識別し、ランレングスチェックは、内部還元性が少なくとも 2 つが選択可能であるかどうかに依存する、縮退した単一ランのケースを処理します。
