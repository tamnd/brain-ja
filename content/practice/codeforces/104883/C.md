 ## 問題の理解

 大きな整数が与えられます`a`バイナリ文字列および非負の整数として書き込まれます。`x`。 別の整数を構築する必要があります`b`を超えないもの`a`、そしてそのような有効なすべての中で`b`の可能な最大値が必要です。`b`。 妥当性を定義する制約は、計算するときの制約です。`a XOR b`、その結果に設定されているビットの数は少なくとも`x`。 

より具体的に言えば、各ビット位置は、次のビットが一致する場合にのみ XOR に寄与します。`a`そして`b`異なる。 したがって、2進数を選択しようとしています`b`それは少なくとも強制しながら可能な限り大きくします`x`意見が合わない位置`a`を超えることはありません`a`辞書編集上のバイナリ順。 

長さ`a`サイズが大きくなる可能性があるため、どのソリューションでも線形時間で処理する必要があります。 の値`x`大きくすることもできますが、各位置が XOR ポップカウントに寄与するのは最大でも 1 であるため、基本的にはビット位置の数によって制限されます。 この観察により、次のような実行不可能なケースはすでに排除されています。`x`～の長さを超える`a`。 

単純な戦略では、すべての候補者を構築しようとします。`b`両方の条件を確認しますが、検索スペースのビット数は指数関数的に増加します。 実現可能性をチェックせずに貪欲な選択をしても失敗する可能性があります。`b`後で十分な XOR に到達する機能がブロックされる可能性があります。 

貪欲に最大化すると微妙な失敗例が現れる`b`早期に実行すると、必要な XOR カウントを達成するために残りのポジションが不十分になります。 たとえば、次の場合`a = 1010`そして`x = 3`、選択する`b = 1010`プレフィックス値を最大化しますが、XOR ポップカウントが生成されます`0`、以前の決定が制限的すぎたために、その後の調整では十分な不一致を回復できない可能性があります。 

最も難しいのは、辞書編集上の最大化という 2 つの競合する目標のバランスを取ることです。`b`少なくとも蓄積できる十分な将来のポジションを確保しながら`x`不一致。 

## アプローチ

 ブルート フォース アプローチでは、すべてのバイナリ文字列が列挙されます。`b`～と同じ長さの`a`、それらをフィルタリングします`b ≤ a`、計算する`popcount(a XOR b)`、有効な最大値を取得します`b`。 これは、あらゆる可能性を明示的にチェックするため、正しいです。 ただし、検討が必要です`2^n`候補者と各チェックにかかる時間`O(n)`、合計は`O(n 2^n)`、これは実現可能な限界をはるかに超えています。 

重要な観察点は、XOR 条件は順序には影響を受けず、異なる位置の数にのみ影響されるということです。 各位置は独立して XOR ポップカウントに 0 または 1 を与えるため、実現可能性はそれらの配置ではなく、残っている位置の数によってのみ決まります。 これにより、問題は単純な実現可能性制約を伴う貪欲な構造に変わります。 

私たちは建設します`b`最上位ビットから最下位ビットまで。 それぞれの位置で、`1`それが続くなら`b ≤ a`そして、必要な数の XOR を達成するのに十分な残りの位置がまだ残っています。 選択する場合`1`実現不可能なので、`0`。 まだ必要な XOR の数と残りのポジションの数を追跡し、要件を満たすことが不可能になる状態に決してコミットしないようにします。

 ## アルゴリズムのチュートリアル

 次のバイナリ文字列を処理します`a`左から右に、最初にそれを最上位ビットとして扱います。 

1. コンピューティング`n`、の長さ`a`、すぐに次のことを確認します。`x > n`。 そうである場合、XOR は位置ごとに最大 1 つの寄与しか作成できないため、解決策は存在しません。 
2. のプレフィックスかどうかを追跡するポインタを初期化します。`b`はまだ接頭辞と同じです`a`。 この制約により、決して超過しないことが保証されます`a`。 カウンタも初期化します`need = x`、まだ作成する必要がある XOR の数を表します。 
3. 各ポジションで`i`、残っているポジションの数がわかっているので、達成可能な最大の XOR 寄与を次のように計算できます。`remaining_positions`。 これにより、実現可能性の条件が与えられます。つまり、あらゆる決定は次の場合にのみ有効です。`need_after_choice ≤ remaining_positions`。 
4. 設定してみる`b[i] = 1`まず、最終的な数値を最大化したいからです。 この選択は、すでに以下のいずれかの場合にのみ許可されます`a`、または内の対応するビット`a`もです`1`。 このビットを選択すると、一致するかどうかを更新します`a[i]`そして減らす`need`この位置が XOR に寄与する場合。 
5. 選択があれば`b[i] = 1`残りの要件を満たすことが不可能になるため、それを破棄し、代わりに`b[i] = 0`。 それに応じて XOR 要件とタイトネス状態を再度更新します。 
6. すべてのビットが処理されるまで続行します。 最後に、結果がゼロでない限り、先頭のゼロを削除します。 

### なぜ効果があるのか

 すべての位置で、アルゴリズムは、残りのサフィックスが残りの XOR 要件を満たすのに十分な長さを持つという特性を維持します。 各ビットは独立して最大 1 つの XOR ユニットに寄与できるため、実現可能性は配置ではなくカウントのみに依存します。 ～に対する貪欲な好み`1`両方の選択肢が有効な場合は常に、より大きな辞書編集パスを選択する一方で、実現可能性チェックにより、後でグローバル制約に違反する選択肢が防止されます。 この組み合わせにより、ローカルで選択されたものがないことが保証されます。`1`グローバルに必要な構成をブロックすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    a = input().strip()
    x = int(input().strip())
    
    n = len(a)
    
    if x > n:
        print(-1)
        return
    
    b = []
    need = x
    tight = True  # b prefix == a prefix
    
    for i in range(n):
        remaining = n - i - 1
        
        # try to place 1
        for bit in (1, 0):
            if bit == 1:
                if tight and a[i] == '0':
                    continue
            # compute new need if we place bit
            new_need = need - (bit != int(a[i]))
            
            if new_need < 0:
                continue
            
            if new_need <= remaining:
                b.append(str(bit))
                need = new_need
                
                if tight:
                    if bit == 1 and a[i] == '0':
                        tight = False
                    elif bit == 0 and a[i] == '1':
                        tight = False
                    elif a[i] == '0' and bit == 0:
                        tight = True
                    elif a[i] == '1' and bit == 1:
                        tight = True
                break
    
    res = ''.join(b).lstrip('0')
    print(res if res else "0")

if __name__ == "__main__":
    solve()
```実装は貪欲な構造に直接続きます。 内側のループは次のことを試みます`1`まず結果の数値を最大化します。 実現可能性チェックでは、ビットを選択した後でも、残りの位置が必要なすべての XOR 差異に対応できることが確認されます。 の`tight`変数はまだ一致しているかどうかをエンコードします`a`その通り; それを下回ると、将来のビットは上から制限されなくなります。 

微妙な詳細は、`need`これは、次のステップの実現可能性をチェックする前に実行する必要があります。 もう 1 つの重要な詳細は、`0`しっかりと固定された状態で配置され、`a[i]`は`1`、構築される数は厳密に小さくなり、将来のビットは自由に最大化できます。

import sys, io

def run(inp: str) -> str:

 ## 特殊なケース

 いつ`x`のビット数を超えています`a`、すべてのビットが XOR に寄与する必要がありますが、十分な位置がありません。 入力用`a = 10101`、`x = 10`、アルゴリズムはすぐに拒否します。`x > n`。 

いつ`a`すべては 1 であり、`x = 0`、貪欲な戦略は常に維持されます`b = a`、偏差を強制する XOR 要件がないためです。 これは、制約がバインドされていない場合、アルゴリズムが辞書編集上の最大値を正しく優先することを示しています。 

いつ`a`が 1 ビットの場合、決定は直接の実現可能性チェックに集約されます。 のために`a = 1`、`x = 1`、唯一の有効な構造は`b = 0`、境界を尊重しながら要件を満たす唯一の方法であるため、アルゴリズムはそれを選択します。 

いつ`a`主要なものはたくさんありますが、規模は大きいです`x`、初期の選択肢`1`一致する位置が多すぎると、実行できなくなる可能性があります。 実現可能性チェックにより、そのようなパスへのコミットが防止され、残りの位置を引き続き使用して必要な XOR 差分を蓄積できることが保証されます。
