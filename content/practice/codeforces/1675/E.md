 ## 解決策
 ## 問題の理解

 英語の小文字で構成される文字列が与えられ、それに対してグローバル変換を繰り返し実行できます。 1 回の操作で 1 つの文字を選択します。`'d'`、出現するすべての文字列を置き換えます。`'d'`この場合、アルファベットの前の文字を含む文字列内`'c'`。 アルファベットは循環するので、`'a'`に包み込む`'z'`。 

タスクは、最大でも適用することです`k`このようなグローバルなデクリメントは、そのたびに文字列内にまだ出現する文字を選択し、最終的に辞書編集上可能な限り最小の文字列になります。 

主な難点は、各操作が一度に出現するすべての文字に影響し、同じ文字が複数回選択される可能性があり、カスケード シフトが発生することです。 文字を再配置するのではなく、グローバル ルールに基づいて文字値を繰り返し圧縮するだけです。 

この制約は、任意の操作シーケンスをシミュレートできないことを強く示唆しています。 すべてのテスト ケースにわたる文字列の長さは最大でも`2 * 10^5`したがって、すべての解はテストごとに線形、または合計が線形に近い必要があります。 操作数`k`と同じ大きさにすることができます`10^9`したがって、操作を直接反復することはできません。 代わりに、変換の構造について推論する必要があります。 

微妙なエッジケースは、アルファベットの周期的な性質から生じます。 たとえば、減らすと`'a'`一度、それは`'z'`これは辞書編集的に大きく、後で最適な選択に影響を与える可能性があります。 計画なしに常に最大の文字を削減する単純な貪欲なアプローチは、次善のサイクルに簡単に陥る可能性があります。 

もう 1 つの落とし穴は、各文字を個別に削減できると想定していることです。 それは誤りです。`'b'`に`'a'`将来的には削減される可能性があります`'a'`他の場所で事業を行った場合よりもはるかに価値が高くなります。 

## アプローチ

 ブルートフォース解釈では、各操作をシミュレートします。 すべてのステップで、文字列内に存在するすべての文字をスキャンし、1 つ選択して変換を適用します。 各操作が O(n) であり、最大で`k`演算を実行すると、最悪の場合の複雑さは O(nk) になり、これは実行不可能です。`k`まで`10^9`。 

より賢く文字の頻度を維持しようとしても、次にどの文字を減らすかを選択することが非局所的な方法でグローバル構造に影響を与えるという問題に依然として直面します。 本当の障害は、私たちが関心があるのは操作のシーケンスではなく、各文字からその縮小された形式への最終的な誘導マッピングであるということです。 

重要な観察点は、各文字はアルファベットの下方向にのみ移動でき、すべての操作で 1 つの異なる文字値 (1 つの出現ではなく) が正確に減少するということです。 したがって、このプロセスは、すべての個別の文字に割り当てられる合計の減少量が最大以下であるという制約のもとで、各文字クラスに何段階の「下降」を割り当てるかを決定することに相当します。`k`、そして手紙が消えるたびに、私たちはそれに対するオペレーションの支出を停止します。 

これは、変換関数の観点から考える必要があることを示唆しています。`f(c)`各文字を最後の文字にマッピングします。 辞書編集の結果を最小限に抑えたいので、アルファベットの初期の文字をできるだけ積極的に削減する必要があります。`'a'`早期に行うと、辞書編集上の最大の改善が得られます。 

これは貪欲な戦略につながります。つまり、すべてのキャラクターを繰り返し押し下げようとします。`'a'`ただし、文字が完全に削除されると (別のクラスにマージされる下位の文字になると)、独立して考慮する必要がなくなることを考慮する必要があります。 これを正式化する正しい方法は、からの手紙を処理することです。`'z'`大きな文字を早期に削減すると、文字列の早い段階で辞書編集的により強力な改善が得られるため、下向きに、貪欲に上位の文字を最初に削減する操作を実行します。 

アルファベットを 26 ノードとしてモデル化し、文字列内にどの文字がまだ存在するかを追跡しながら、各文字を段階的に押し下げるために必要な操作の数を維持できます。 文字数は 26 文字しかないので、最大 26 文字までの支出による効果をシミュレーションできます。`k`集約を削減し、マージを慎重に伝播します。

 ## アルゴリズムのチュートリアル

 グローバルなデクリメントが繰り返される中で各文字がどのように進化するかを追跡します。 

1. 文字列内の各文字の頻度を計算します。 これにより、どの文字が「アクティブ」であり、変換時に考慮する必要があるかがわかります。 
2. 配列を維持する`shift[c]`何歩かを表す文字`c`合計で減ります。 最初はすべてゼロです。 これは、適用する最終的なマッピングをエンコードします。 
3. からの文字を反復処理します。`'a'`に`'z'`、残りの操作を使用してそれらを削減しようとします`k`。 文字ごとに、操作がなくなるか、以前に処理されたクラスにマージされるまで、文字をどこまで押し下げることができるかを決定します。 
4. When we decide to reduce a letter`c`1 ステップごとに、概念的には 1 つの操作を費やし、発生するすべての操作をリダイレクトします。`c`に`c-1`。 これにより、下位のバケットへのマージが発生する可能性があるため、文字列を繰り返し変更するのではなく、シフトを蓄積します。 
5.次のいずれかになるまで続けます。`k == 0`または有益な削減が残っていない場合。 重要な考え方は、辞書順で前の文字を改善すると最大の効果が得られるため、常に小さい文字を最初に優先するということです。 
6. 最終シフトを計算した後、適用して結果の文字列を構築します。`shift`循環ラップアラウンドを考慮しながら、各文字に適用します。 

### なぜ効果があるのか

 不変条件は、辞書編集上の最適性を維持する方法で、各文字クラスに適用される減分数をどの時点でも正しく考慮していることです。 辞書編集的な順序は左から右に決定されるため、アルファベットの前にある小さな文字を縮小する操作は、後の大きな文字にのみ影響を与える操作よりも優先されます。 貪欲な順序付けにより、文字列のプレフィックスを改善せずに延期される可能性のある変換操作を無駄にすることがなくなります。 州が 26 しかないため、文字ごとのシフトを集約することで、すべての有益なマージが完全にキャプチャされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        s = input().strip()

        freq = [0] * 26
        for ch in s:
            freq[ord(ch) - 97] += 1

        # shift[i] = how many steps letter i is reduced
        shift = [0] * 26

        # We simulate greedy consumption of k reductions from 'b' to 'a', etc.
        # The idea: we try to push letters downward in alphabet order.
        for c in range(25, 0, -1):
            if k == 0:
                break
            if freq[c] == 0:
                continue

            # We can only reduce this letter at most freq[c] times "usefully"
            take = min(k, freq[c])
            shift[c] += take
            k -= take

            # those letters effectively become c-1, so merge frequencies
            freq[c - 1] += freq[c]
            freq[c] = 0

        # apply shift
        res = []
        for ch in s:
            c = ord(ch) - 97
            # total downward shift modulo 26
            # shift only tracks accumulated merges; final mapping is implicit
            while shift[c]:
                c -= 1
                if c < 0:
                    c = 25
                shift[c] += shift[c + 1] - 1 if False else 0  # no-op safety
                break
            res.append(chr(c + 97))

        print("".join(res))

if __name__ == "__main__":
    solve()
```このコードは、文字を高位から低位に貪欲に折りたたむという考えに従っています。 頻度配列は、各文字クラスで使用できる文字の数を把握するために使用されます。 操作を費やすにつれて、文字をその前の文字にマージし、文字列全体に繰り返し触れることなく、グローバルなデクリメントを効果的にシミュレートします。 

実装上の微妙な問題は、各減少を明示的にシミュレートしていないことです。 代わりに、各文字クラスが下方向にマージされた回数を累積します。 最後の再構成ステップでは、結果として得られたマッピングを単純に適用します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n, k = map(int, input().split())
        s = input().strip()

        freq = [0] * 26
        for ch in s:
            freq[ord(ch) - 97] += 1

        shift = [0] * 26

        for c in range(25, 0, -1):
            if k == 0:
                break
            if freq[c] == 0:
                continue
            take = min(k, freq[c])
            k -= take
            freq[c - 1] += freq[c]
            freq[c] = 0

        res = []
        for ch in s:
            c = ord(ch) - 97
            while shift[c]:
                c = (c - 1) % 26
                shift[c] += 0
                break
            res.append(chr(c + 97))

        out.append("".join(res))

    return "\n".join(out)

 ## 特殊なケース

 トリッキーなエッジケースは、すべての文字を折りたたむのに必要な操作を超える場合です。`'a'`。 その場合、余分な操作は無駄なサイクルとなり、文字列はさらに改善されません。 たとえば、`"abc"`そして大きい`k`、最適な結果は単純に次のようになります。`"aaa"`循環シフトではなく、`'z'`。 

もう 1 つのエッジ ケースは、循環ラップアラウンドです。 減らしたら`'a'`それはなる`'z'`、これは辞書編集的にはさらに悪いです。 操作を盲目的に適用する単純な貪欲なアルゴリズムにより、誤って問題が発生する可能性があります。`'z'`文字列の早い段階で実行すると、何もしないよりも悪い結果が生じます。 アルゴリズムは決して処理しないことでこれを回避します。`'a'`有益な削減目標として。 

最後に、次のような文字が繰り返される文字列`"aaaaa"`に関係なく変更されないままでなければなりません`k`, 上のあらゆる操作以来、`'a'`辞書編集上の順序が悪化するだけです。 アルゴリズムは正しく演算に費やすことはありません`'a'`貪欲な順序付けによって妨げられる間接的なマージを強制されない限り。
