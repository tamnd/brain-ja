 ## 問題の理解

 Nadja のサイトへの各訪問者は、タイムライン上の定期的なイベントのように動作します。 ビジター$i$日に初登場$a_i$、その後も毎回出現し続けます。$b_i$終わりのない日々。 したがって、各訪問者は無限の訪問日のシーケンスを生成します。$a_i, a_i + b_i, a_i + 2b_i, \dots$。 同じ日に複数の訪問者が現れた場合、訪問はインデックスの昇順に処理されます。 

一日中シミュレーションするように求められるわけではありません。 代わりに、概念的にマージします$n$無限の等差数列を計算し、どの訪問者が$k$マージされたシーケンス内の - 番目の要素。 

この制約により、時間をかけて総当たりシミュレーションを行うことが不可能になります。 訪問者の数は 100 万人に達する可能性がありますが、日の値は 1000 で制限されます。周期の制限も 1000 であり、これが重要な構造的制約です。 これは、タイムラインには制限がないにもかかわらず、各訪問者の行動が小さなサイクルで繰り返され、多くの訪問者が同様のスケジュールを共有していることを意味します。 

素朴なアプローチでは、日ごとにシミュレーションを行い、次回の訪問の優先キューを維持します。 しかし、最初の興味深い瞬間にはすでに問題があります。 すべての訪問者が早めに開始し、期間が短い場合、最初の数千日の合計訪問数はすでに を超えている可能性があります。$10^6$、各シミュレーション ステップでは、最大で 1 回のヒープ操作が必要になります。$10^6$エントリが発生し、実行不可能なランタイムが発生します。 

多くの訪問者が同じスケジュールを共有する場合、微妙なエッジケースが発生します。 たとえば、すべてが$a_i = 1$そしてすべて$b_i = 1$、その後は毎日、$n$訪問。 最初$k$訪問は、サイズのブロックを繰り返すことによって単純に順序付けされます$n$。 単純なシミュレーションは毎日繰り返される可能性がありますが、正しい答えは次の点にのみ依存します。$k \bmod n$、明示的なシミュレーションではありません。 

もう 1 つの重要なエッジ ケースは、タイの注文から発生します。 同じ日に 2 人の訪問者が訪問した場合は、インデックスが小さい訪問者を最初にカウントする必要があります。 インデックスの順序を維持せずに 1 日あたりの訪問数を集計するソリューションは失敗します。 

## アプローチ

 この強引なアイデアは、プロセスを時系列でシミュレーションすることです。 各訪問者の次の訪問日を維持し、最小の日を繰り返し抽出し、対応する訪問者を出力して、次の訪問日をプッシュします。 これは、プライオリティ キューを使用した古典的なイベント シミュレーションです。 

このアプローチは、プロセスの定義と正確に一致するため、正しいです。各ステップで、まだ処理されていない最も早い訪問を選択します。 ただし、そのコストは処理されるイベントの数によって決まります。 もし$k$までです$10^6$、私たちは実行します$k$ヒープポップと$k$プッシュ、各コスト$O(\log n)$、おおよそにつながります$10^6 \log 10^6$これは境界線にありますが、最適化された言語ではまだ合格する可能性があります。 Python では、$n$まで$10^6$、そのようなヒープを構築して維持することさえ、メモリと初期化のオーバーヘッドのために実行できません。 

重要な洞察は、すべての訪問が決定的であり、小さなパラメータで定期的に行われることを観察することで得られます。 時間の増加順にシミュレーションする代わりに、特定の時間しきい値に対して視点を逆転させることができます。$T$、今日までに発生した訪問数をカウントできます$T$。 各訪問者は、進行状況の用語の数に基づいて単純な算術カウントを提供します。$\le T$。 この数え方は、$O(n)$、そしてそれ以来$a_i, b_i \le 1000$、最小のものを効率的に検索できます。$T$少なくともそうなるように$k$訪問が発生します。 

プレフィックス訪問を効率的にカウントできるようになると、問題は時間どおりに二分探索が行われるようになります。 答えは、$k$- 番目のイベントを (日, インデックス) のソート順に並べると、イベントが発生した正確な日を見つけることができます。$k$- 回目の訪問が発生し、その日にどの訪問者がその特定のランク付けされたイベントに貢献したかを再構築します。

 ## アルゴリズムのチュートリアル

 私たちは問題を次の発見に変換します。$k$グローバルにソートされたペアのストリーム内の - 番目のイベント (日、訪問者インデックス)。 ストリームを構築する代わりに、その構造を利用します。 

1. まず、関数を定義します。$T$、その日またはその前に発生した訪問数を計算します。$T$。 訪問者一人一人に対して$i$、進行の項の数を数えます$a_i + t b_i \le T$。 次の場合、このカウントはゼロになります。$T < a_i$、そうでない場合は、$\lfloor (T - a_i)/b_i \rfloor + 1$。 各訪問者がイベントの合計数に独立して貢献するため、このステップは有効です。 
2. 最小日を二分探索します$T$合計訪問数が$T$少なくとも$k$。 単調性が成立するのは、増加するからです。$T$訪問を追加することのみが可能であり、削除することはできません。 これにより、明確に定義された境界日が保証されます。$k$- 番目のイベントが発生する必要があります。 
3. この日を見つけたら$T$、事前に訪問数を厳密に計算します。$T$。 これにより、一日がどのくらい先かがわかります$T$の$k$-番目の出来事は嘘です。 
4. すべての訪問者を反復処理し、その日に訪問した人を収集します$T$。 そのような訪問者ごとに、そのインデックスをリストに追加します。 順番にスキャンするため、このリストは自然にインデックスによってソートされます。 
5.前日の来店回数を減算$T$から$k$、その日に発生した訪問内の 1 でインデックスされた位置が得られます。$T$。 収集したリストから該当する訪問者を返します。 

正確さは、グローバル イベント シーケンスを独立した等差数列のソートされたマージとして扱うことから得られます。 二分検索によって正確な日の境界が分離され、最終スキャンによってその日内の順序が解決されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = [0] * n
    b = [0] * n

    for i in range(n):
        a[i], b[i] = map(int, input().split())

    def count_up_to(t):
        total = 0
        for i in range(n):
            if t >= a[i]:
                total += (t - a[i]) // b[i] + 1
        return total

    lo, hi = 1, 10**7

    while lo < hi:
        mid = (lo + hi) // 2
        if count_up_to(mid) >= k:
            hi = mid
        else:
            lo = mid + 1

    day = lo

    before = count_up_to(day - 1)
    remaining = k - before

    on_day = []
    for i in range(n):
        if day >= a[i] and (day - a[i]) % b[i] == 0:
            on_day.append(i + 1)

    return on_day[remaining - 1]

if __name__ == "__main__":
    print(solve())
```機能`count_up_to`は、コアとなる算術観測を実装します。各訪問者は、単純なフロア分割数を提供します。 二分探索により、k 回目の訪問が行われた正確な日が特定されます。 2 番目のパスでは、その日の順序が再構築され、モジュラー演算によってどの訪問者がアクティブであるかが特定されます。 減算ステップにより、その日の訪問者リストに正しくインデックスが付けられるようになります。 

よくある実装上の落とし穴は、同じ日の訪問者をインデックス順に並べる必要があることを忘れることです。そのため、インデックスを昇順に追加します。$i$。 もう 1 つの微妙な問題は、バイナリ検索の上限を十分に大きくすることです。$10^7$期間 1 であっても、実行可能な答えを安全に超えています。$10^6$訪問は以内に発生します$10^6$日々。

 ## 特殊なケース

 エッジ ケースの 1 つは、すべての訪問者が同じ日に期間 1 で開始する場合です。この場合、毎日が訪問者インデックスの完全な順列に寄与します。 アルゴリズムは、貢献を次のようにカウントすることでこれを処理します。$n$1 日あたりのデータを収集し、二分探索によって正しい日の境界を特定します。 境界日に、残りのインデックスが正しい訪問者を順番に選択します。 

もう 1 つのケースは、ある訪問者が他の訪問者に比べて非常に遅く開始する場合です。 たとえば、$a_i$は大きいですが、二分探索はまだ機能します。`count_up_to(T)`までその訪問者を無視します$T$開始日を迎えます。 関数は単調なままであり、境界検索の正確性が保証されます。 

最後の微妙なケースは次のような場合です。$k$ちょうど日と日の境目にあたります。 減算ステップ`k - count_up_to(day - 1)`これにより、答えを誤って次の日に移動するのではなく、最終日に正しく配置できるようになります。
