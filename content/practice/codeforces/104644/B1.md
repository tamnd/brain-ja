 ## 解決策
 ## 問題の理解

 私たちは時間の経過とともに貪欲なリソース割り当てシステムを効果的にシミュレートしています。 

N 個のアイテムがあり、各アイテムは異なるフレーバーのロリポップを表します。 N 人のお客様も続々とご来店いただいております。 各顧客は、受け入れてもよいフレーバーのリストを提供します。 顧客が到着したら、ロリポップを与えるかどうかをすぐに決定し、与える場合は、許容できるリストから 1 つのフレーバーを正確に選択する必要があります。 制約は、フレーバーが販売されると永久に失われ、後の顧客が再利用できないことです。 顧客が好むフレーバーがまだ入手できない場合、その顧客は何も受け取りません。 

主な問題点は、決定は取り消し不可能であり、将来の顧客の好みが不明であることです。 人気のあるフレーバーを早期に採用すると、後でより良い割り当てが妨げられる可能性があるため、各ステップはローカルな選択であり、グローバルな結果をもたらします。 

出力は顧客ごとに 1 つずつの一連の決定であり、各決定はリストのフレーバー インデックスか、サービスの提供を拒否した場合は -1 になります。 

制約の観点から見ると、N は対話型スタイルのバリアントでは 2×10^5 以上などの一般的な競技プログラミングの制限に達する可能性があります。これは、各顧客をほぼ一定時間または対数時間で処理する必要があることを意味します。 フレーバー リストを繰り返しスキャンしたり、将来の結果をシミュレートしようとするアプローチは、すべての顧客の合計嗜好サイズが最悪の場合 O(N^2) に達する可能性があるため、拡張できません。 

顧客が重複しているが同一ではない設定セットを持っている場合、微妙なエッジケースが発生します。 「常にリストの最初に利用可能なフレーバーを提供する」といった単純な戦略は、初期の顧客が後の数人の顧客にとって唯一の選択肢であるフレーバーを消費した場合に失敗する可能性があります。 たとえば、顧客 1 が {1, 2} を好み、顧客 2 が {1} のみを好む場合、顧客 1 にフレーバー 1 を割り当てると、代わりに顧客 1 にフレーバー 2 を与えることでより適切な割り当てが存在するにもかかわらず、顧客 2 が即座に完全にブロックされます。 

顧客のリストが空の場合、別の特殊なケースが発生します。 この場合、唯一の有効な出力は -1 であり、少なくとも 1 つのオプションを想定した貪欲な実装ではクラッシュするか、空のリストに誤ってインデックスが付けられる可能性があります。 

## アプローチ

 ブルートフォースの観点は、可用性を考慮しながら、顧客に対するフレーバーの可能な割り当てをすべて試すことです。 顧客ごとに、好みリスト内の利用可能なすべてのフレーバーに分岐し、再帰的に続行します。 これは、顧客とフレーバーの間の有効な一致をすべて調査するため、正しいです。 ただし、各顧客が残りのフレーバーをすべて好むという最悪のケースでは、分岐係数は N から始まり、ゆっくりと減少し、およそ N! が生成されます。 可能な割り当て。 重複を枝刈りしたとしても、検索空間は指数関数的に増大し、20 または 25 あたりで N を超えるとすぐに実行不可能になります。 

重要な構造上の観察は、これが任意の制約を伴う一般的な割り当て問題ではなく、片側が静的で右側の各ノードが最大 1 回消費され、決定がオンラインで行われる 2 部マッチングであるということです。 無駄を避けるという観点から考えると、問題ははるかに単純になります。理想的には、各フレーバーは実際に必要な場合にのみ使用されるべきです。 

プロセスを再構成する有効な方法は、顧客を処理し、常に消費しても「安全」なフレーバー、つまり将来の顧客にとって唯一残された選択肢ではないフレーバーを割り当てるように努めることです。 オフライン用語では、これは、将来の制約でそれほど重要ではないフレーバーを優先することに対応します。 一般的なインタラクティブな解釈では未来が分からないため、一般的に受け入れられている解決策は、可用性を維持し、実行可能なフレーバーを一貫して割り当てる貪欲なマッチング戦略に帰着し、多くの場合、問題の正確なバリエーションに応じて順序付けや単純な決定論的な選択ルールに依存します。

このタスクの最も単純な決定論的モデルでは、正しいアプローチは、利用可能なフレーバーのセットを維持し、顧客ごとにリストからまだ利用可能なフレーバーを選択することになります。 複数の値が使用可能な場合は、このバージョンの意図された制約の下で有効な貪欲な割り当てが存在することが問題によって保証されるため、どの選択をしても機能します。 素朴な思考による失敗例は、将来の制約についての不必要な推測から生じますが、B1 バージョンの構造では必要ありません。 

したがって、ブルート フォースと最適なソリューションの違いは、すべての割り当てを探索することから、使用されているフレーバーのグローバルな状態を維持し、顧客ごとにシングル パスの決定を下すことへの移行です。

 ## アルゴリズムのチュートリアル

 1. フレーバーの数 N を読み取り、各フレーバーがまだ利用可能かどうかを追跡する構造を初期化します。 ロリポップはまだ販売されていないため、すべてのフレーバーを最初に入手可能としてマークします。 
2. 到着順に顧客を処理します。 各顧客は許容できるフレーバーのリストを提供します。 
3. リストが空の場合は、割り当てができないため、すぐに -1 を出力します。 これは厳しい制約であり、選択できるものではありません。 
4. それ以外の場合は、顧客のリストを繰り返して、まだ利用可能な最初のフレーバーを見つけます。 有効な割り当てでは実行可能なオプションを 1 つ選択するだけで済み、未使用のフレーバーは実行可能性の観点から交換可能であるため、この手順で十分です。 
5. 有効なフレーバーが見つかった場合は、そのインデックスを出力し、使用不可としてマークします。 
6. 利用可能なフレーバーがリストに存在しない場合は、-1 を出力して次の顧客に移動します。 

### なぜ効果があるのか

 すべてのステップで、アルゴリズムは、各フレーバーが最大 1 回使用され、行われたすべての割り当てが可用性に関してローカルに有効であるという不変条件を保持します。 重要な特性は、実現可能性が単調であるということです。フレーバーは一度利用できなくなると、その後は使用できないため、有効なソリューションは再利用を避ける必要があります。 各顧客は 1 回だけ処理され、現在実行可能なオプションが存在する場合は常にそれを選択するため、制約に違反することはありません。 貪欲な選択では、将来の顧客を予測する必要はありません。この問題により、このバージョンの制約の下では、優先リストからの利用可能な選択肢が安全であることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    used = [False] * n
    out = []

    for _ in range(n):
        arr = list(map(int, input().split()))
        d = arr[0]
        if d == 0:
            out.append("-1")
            continue

        chosen = -1
        for i in range(1, d + 1):
            v = arr[i]
            if not used[v]:
                chosen = v
                break

        if chosen == -1:
            out.append("-1")
        else:
            used[chosen] = True
            out.append(str(chosen))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```この実装では、各フレーバーがすでに販売されているかどうかを追跡するためのブール配列が保持されます。 これにより、フレーバーごとに O(1) チェックが可能になります。 顧客ラインごとに、好みのリストを解析し、未使用のフレーバーが見つかるまで 1 回スキャンします。 最初の有効なフレーバーがすぐに選択され、アルゴリズムの貪欲ルールに一致します。 

唯一の微妙な点は、顧客の好みがまったくない場合に確実に正しく処理できるようにすることです。 この場合、リストへのインデックス作成を試みてはなりません。 もう 1 つの詳細は、行ごとの印刷が遅くなるのを避けるために、出力がバッファリングされて最後に書き込まれることです。

 ## 特殊なケース

 空の設定リストの場合、アルゴリズムは選択を試みる前に -1 を直接出力し、無効なインデックス付けを防ぎます。 

複数の顧客が同じ 1 つのフレーバーを希望する場合、最初に遭遇した顧客がそれを受け取りますが、可用性配列によって使用済みとしてマークされるため、後続のすべての顧客は正常に失敗します。 

好みをすべて使い果たした顧客の場合、有効なフレーバーが見つからないままスキャンが完了し、正しく -1 が出力されます。 このアルゴリズムは、設定リストのサイズ内で線形時間で実行されますが、各要素は入力行ごとに 1 回だけチェックされるため、これは許容範囲内です。
