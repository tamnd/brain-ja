 ## 解決策
 ## 問題の理解

 各通知は特定の瞬間に到着し、指定された長さのビデオが含まれます。 Vasya は常に、通知が届いた順にビデオを視聴します。 通知が表示されたときにアイドル状態であれば、すぐにそのビデオを見始めます。 彼がすでに何かを視聴している場合、新しいビデオは、以前の未完成のビデオがすべて視聴されるまでキュー内で待機します。 

入力では、到着時間の降順以外の順序で通知がすでに提供されているため、順序を変更する必要はありません。 タスクは、すべての通知を処理した後、最終ビデオの終了時間を決定するだけです。 

通知の数は 200,000 に達しますが、到着時間と期間は両方とも (10^9) に達する可能性があります。 時間を繰り返しシミュレートしたり、新しい通知ごとに以前に処理された通知をスキャンしたりするアルゴリズムでは、実行する操作が多すぎます。 線形解法は容易に十分に高速ですが、二次解法は除外されます。 終了時間が (2 \times 10^9) を超える可能性があるため、アルゴリズムでは値が 32 ビット整数に収まるという仮定も避ける必要がありますが、Python の整数はこれを自然に処理します。 

簡単な間違いの 1 つは、次の通知が届くまで Vasya がアイドル状態になる可能性があることを忘れていることです。 

例：```
2
1 2
10 3
```正しい答えは、`13`。 Vasya は時間通りに最初のビデオを終了します`3`、時間が来るまで待ちます`10`、次に 2 番目のビデオを まで視聴します。`13`。 前回の終了時間に単純に継続時間を加算すると、誤って生成されます。`6`。 

もう 1 つの微妙なケースは、複数の通知がまったく同じ瞬間に到着する場合に発生します。```
3
5 2
5 4
5 1
```正しい答えは、`12`。 最初のビデオは時刻にすぐに始まります`5`、他の 2 つは到着順にその後ろに追加されます。 同じタイムスタンプを持つ通知を同時の独立したイベントとして扱うと、その順序が失われます。 

3 番目のケースは、前のビデオが終了したときに通知が到着する場合です。```
2
1 4
5 3
```正しい答えは、`8`。 時間に`5`Vasya はもう忙しくないので、2 番目のビデオがすぐに始まります。 次のような厳密な比較を使用する`finish > arrival`の代わりに`finish >= arrival`スケジュールを誤ってずらす可能性があります。 

## アプローチ

 簡単なシミュレーションにより、待機中のすべてのビデオがキューに入れられます。 通知が到着するたびに、シミュレーションは時間を進め、完了したビデオをすべて削除し、到着したビデオをすぐに開始するか、キューに追加します。 これはルールを忠実にモデル化していますが、最悪の場合、到着ごとに多くのキューに入れられたビデオが再度処理される可能性があります。 (n) 個の通知を使用すると、(n = 200000) の場合、(O(n^2)) 個の作業、つまりおよそ (4 \times 10^{10}) 個の操作が必要になる可能性があります。 

キュー自体は実際には不要です。 いかなる時点においても、将来の通知に影響を与える唯一の情報は、Vasya が自由になる時刻だけです。 いくつかの通知を処理した後、彼は時間まで忙しいままであることが保証されていると仮定します。`finish`。 新しい通知が時刻に到着したとき`t`、考えられる状況は 2 つだけです。 

もし`finish <= t`, 通知が表示されるとき、Vasya はアイドル状態です。 新しいビデオは次から始まります`t`そして終了します`t + d`。 

もし`finish > t`、ヴァシャはまだ忙しいです。 新しいビデオはちょうど次の時間から始まります`finish`そしてで終わります`finish + d`。 

どちらの状況も 1 つの式で表すことができます。```
finish = max(finish, t) + d
```この単一の変数は監視キュー全体の状態を完全にキャプチャし、すべての通知を一度に処理できるようにします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.初期化`finish = 0`。 通知が届くまで、Vasya はアイドル状態になります。 
2. 指定された順序で通知を 1 つずつ読みます。 入力は到着時間によってすでにソートされているため、前処理は必要ありません。 
3. 到着時刻を含む通知ごとに`t`と期間`d`、計算する`start = max(finish, t)`。 Vasya がまだビジーの場合、ビデオは次の時間まで待機します。`finish`。 それ以外の場合は、すぐに開始されます`t`。 
4.アップデート`finish = start + d`。 これは、処理されたすべての通知が完全に監視された最も早い瞬間になります。 
5. すべての通知が処理された後、出力します。`finish`。 

### なぜ効果があるのか

 重要な不変条件は、最初の処理後、`i`通知、`finish`は、これらのビデオがすべて視聴された正確な時間に相当します。 次の通知が到着したとき、前のビデオはそれ以降に開始できません。`finish`なぜなら、これまでの通知はすべてすでにスケジュールされているからです。 Vasya がアイドル状態の場合、新しいビデオがすぐに始まります。 彼が忙しい場合は、新しいビデオを開始する前に、以前のすべてのビデオを終了する必要があるため、できるだけ早い開始が正確です。`finish`。 更新中`finish`と`max(finish, t) + d`は不変式を保持し、最後の通知の後は最終ビデオの完了時間を表します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    finish = 0

    for _ in range(n):
        t, d = map(int, input().split())
        finish = max(finish, t) + d

    print(finish)

if __name__ == "__main__":
    solve()
```このソリューションでは変数が 1 つだけ保持されます。`finish`、現在のスケジュールの終了を表します。 すべての通知は、アルゴリズムで導出された式を使用してこの値を更新します。 

表現`max(finish, t)`分岐せずに両方の可能な状態を処理します。 Vasya がすでに忙しい場合は、現在のスケジュールが中断されることなく継続されます。 すでにすべてを完了している場合、スケジュールは通知の到着時刻から再開されます。 

比較には、`max`厳密な不等式ではなく、前のビデオが終了したときに到着する通知を正確に処理します。 Python の整数は必要に応じて自動的に増加するため、終了時間が非常に長くても安全です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | すべての通知は 1 回だけ処理されます。 |
 | スペース | お(1) | 現在の終了時刻のみが保存されます。 |

 通知ごとに一定の作業を行って 200,000 件の通知を処理すると、制限時間内に簡単に収まり、一定のメモリ使用量は使用可能なメモリをはるかに下回ります。 

## テストケース```python
import sys
import io

def solve():
    input = sys.stdin.readline
    n = int(input())
    finish = 0
    for _ in range(n):
        t, d = map(int, input().split())
        finish = max(finish, t) + d
    print(finish)

def run(inp: str) -> str:
    backup_stdin = sys.stdin
    backup_stdout = sys.stdout
    sys.stdin = io.StringIO(inp)
    out = io.StringIO()
    sys.stdout = out
    solve()
    sys.stdin = backup_stdin
    sys.stdout = backup_stdout
    return out.getvalue().strip()

assert run("5\n1 4\n3 3\n6 1\n10 2\n10 3\n") == "15", "sample 1"

assert run("1\n7 5\n") == "12", "single notification"

assert run("2\n1 2\n10 3\n") == "13", "idle period"

assert run("3\n5 2\n5 4\n5 1\n") == "12", "same arrival time"

assert run("2\n1 4\n5 3\n") == "8", "arrival at finish"

assert run("3\n1 1000000000\n1 1000000000\n1 1000000000\n") == "3000000001", "large values"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 つの通知 | 12 | 有効な最小入力値 |
 | アイドルギャップ | 13 | アイドル状態になった後にスケジュールを再起動する |
 | 到着時間は同じ | 12 | 入力順序は保持されます |
 | ゴールに到着 | 8 | ビデオが通知時刻に正確に終了する境界 |
 | 長い期間 | 3000000001 | 非常に長い終了時間の正しい処理 |

 ## 特殊なケース

 アイドルギャップを考慮してください。```
2
1 2
10 3
```アルゴリズムは次から始まります`finish = 0`。 最初の通知の後、`finish = max(0, 1) + 2 = 3`。 2回目のお知らせにつきましては、`finish = max(3, 10) + 3 = 13`。 スケジュールは時間どおりに正しく再開されます`10`時間から続ける代わりに`3`。 

ここで、同じタイムスタンプを持つ複数の通知について考えてみましょう。```
3
5 2
5 4
5 1
```更新内容は、`7`、 それから`11`、 それから`12`。 新しい開始時刻は以前の通知によって生成された終了時刻に依存するため、すべての通知は入力順序で処理されます。 

最後に、前のビデオが終了したときに通知が届くと考えてください。```
2
1 4
5 3
```最初の通知の後、`finish = 5`。 2回目のアップデートは、`max(5, 5) + 3 = 8`。 以来`finish`と到着時間が等しい場合、新しいビデオは不要な待ち時間なしですぐに開始され、必要な動作と一致します。
