 ## 解決策
 ## 問題の理解

 送信機の垂直スタックが与えられ、それぞれが小文字の上に文字列で記述されます。 各送信機は、時間の経過とともに 1 秒あたり 1 文字ずつシーケンスを発信し、その文字列が終了すると調整信号の発信を停止しますが、依然として存在します。 

2 つのトランスミッターのペアの互換性は、最初からどれくらい長く同じように動作するかによって定義されます。文字列を 1 文字ずつ比較し、不一致が発生するか 1 つの文字列が終了するまで、一致する最初の位置の数を数えます。 これは、まさに共通のプレフィックスの長さです。 

送信機のグループの場合、グループの品質は、グループ内のすべての順序なしペアにわたるこれらのペアごとのプレフィックス一致長の合計です。 選択できるのは連続したフロアのセグメントだけであり、そのようなセグメントの合計品質が K 以上であるものがいくつあるかを数えなければなりません。 

主な問題点は、単純な解釈ではすべてのセグメント内に 2 次構造がすでに示唆されていることです。すべてのペアが寄与するため、セグメントが大きく文字列が長い場合、1 つのセグメントを直接評価するだけでもコストがかかります。 

この制約は、すべての文字列の合計の長さが最大 ​​10^6 であることを意味するため、入力全体にわたって文字列の合計長に比例する操作は可能ですが、N の 2 乗やセグメントの再計算などの繰り返しの処理は許可されません。 N 自体が大きくなる可能性があるため、どのソリューションでもセグメントごとにペアごとの相互作用を最初から再計算することを避ける必要があります。 

微妙だが重要なエッジ ケースは、非常に長い共有プレフィックスを持つ文字列から発生します。 たとえば、多くの文字列が同じ長い文字チェーンで始まる場合、たとえ小さなセグメントであっても、非常に大きなペアごとのスコアがすぐに蓄積される可能性があります。 ステップごとにすべてのペアごとのオーバーラップを再計算する単純なスライディング ウィンドウでは、そのような構造化された入力でも時間がオーバーフローしてしまいます。 

もう 1 つの特殊なケースは、空の文字列または単一文字の文字列と長い文字列が混在していることです。 単純に見えますが、プレフィックス比較を通じて正しく貢献し、文字列終了の誤った処理により、ペアのスコアリングで 1 つ違いのエラーが発生することがよくあります。 

## アプローチ

 ブルートフォースのアイデアは簡単です。すべてのセグメント [l, r] について、そのセグメント内のすべてのペア (i, j) を反復処理し、それらの文字列の最長の共通プレフィックスを明示的に計算することでスコアを計算します。 各 LCP 計算には文字列の長さに対して直線的な時間がかかるため、単一セグメントでもコストが O (セグメント内の文字列の合計長) になる可能性があります。 すべての O(N^2) セグメントを合計すると、これは非常に大きくなります。 

ボトルネックは、類似したプレフィックス間で繰り返される LCP 計算です。 重要な観察は、LCP が共有プレフィックスによって完全に決定され、トライを使用して効率的に表現できるということです。 ペアごとの一致を再計算する代わりに、各トライ ノードを通過するアクティブな文字列の数のカウントを維持できます。 

新しい文字列がウィンドウに追加されると、その合計スコアへの寄与は、その文字列を含む LCP の既存のすべての文字列の正確な合計になります。 トライでは、これは文字列をたどり、各プレフィックスの深さを共有する前の文字列の数を累積することによって計算できます。 これにより、二次比較から文字列の線形走査へのペアの寄与が減少します。 

残りの課題は、すべての連続するサブ配列を考慮する必要があるため、このトライベースの増分スコアリングと 2 ポインター スライディング ウィンドウを組み合わせます。 適切なエンドポイントが拡大するにつれて、貢献が蓄積されます。 左のエンドポイントが前方に移動すると、文字列が削除され、以前に提供されたスコアが残りの要素から減算されます。 

これにより、各文字列が 1 回挿入および削除され、各操作でトライ内のその長さだけが消費される構造が得られます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(N^2・L) | O(1) おまけ | 遅すぎる |
 | トライ + スライディング ウィンドウ | O(全長) | O(全長) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ノードが現在のウィンドウ内で通過する文字列の数を格納するトライを維持します。 これにより、特定のプレフィックスを共有する文字列の数をいつでも数えることができます。 

また、現在のウィンドウ内のペアごとのスコアの合計を表す現在の合計 S も維持します。 

1. 空のトライを初期化し、S = 0 に設定します。2 つのポインター l = 0 および r = 0 を設定します。 
2. 右ポインタを展開します。 現在の文字列 s[r] について、トライをたどることによって、それが既存の文字列にどの程度寄与しているかを計算します。 各文字位置 i で、長さ i の接頭辞を表すトライ ノードにいる場合、現在のノード数を寄与に追加します。 これが機能するのは、そのノードを通過するすべての既存の文字列が、s[r] と少なくとも i 文字の接頭辞を共有しているためです。 この寄与を S に追加し、パスに沿ってカウントをインクリメントすることで s[r] をトライに挿入します。 
3. ウィンドウ [l, r] が S >= K に達すると、この左境界のすべての有効な拡張をカウントしようとします。 右側にさらに文字列を追加しても S が増加するだけであるため、現在の r がこの l の最小エンドポイントになります。 したがって、すべてのセグメント [l, r]、[l, r+1]、...、[l, N-1] は有効であるため、答えに (N - r) を追加します。 
4. l を前に進める前に、トライから文字列 s[l] を削除します。 これを正しく行うには、まず同じプレフィックス ウォークを使用して残りの文字列に対する寄与を計算し、それを S から減算し、次にトライ内のパスに沿ってカウントをデクリメントします。 
5. l を前方に移動し、l が N に達するまで繰り返します。 

正確さは、S が現在のウィンドウ内のペアごとの寄与の合計と常に等しいことを維持することにかかっています。 各挿入では、新しい文字列に関係するすべてのペアが正確に追加され、各削除では、残りの文字列に対してまったく同じペアが減算されます。 

スライディング ウィンドウの順序により、r は前方にのみ移動するため、各文字列は 1 回挿入され、各文字列の削除は 1 回ずつ行われます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Node:
    __slots__ = ("child", "cnt")
    def __init__(self):
        self.child = {}
        self.cnt = 0

class Trie:
    def __init__(self):
        self.root = Node()

    def add(self, s):
        node = self.root
        node.cnt += 1
        for ch in s:
            if ch not in node.child:
                node.child[ch] = Node()
            node = node.child[ch]
            node.cnt += 1

    def remove(self, s):
        node = self.root
        node.cnt -= 1
        for ch in s:
            node = node.child[ch]
            node.cnt -= 1

    def contribution(self, s):
        node = self.root
        res = 0
        for ch in s:
            if ch not in node.child:
                return res
            node = node.child[ch]
            res += node.cnt
        return res

def solve():
    n, k = map(int, input().split())
    s = [input().strip() for _ in range(n)]

    trie = Trie()
    l = 0
    r = 0
    cur = 0
    ans = 0

    while l < n:
        while r < n and cur < k:
            cur += trie.contribution(s[r])
            trie.add(s[r])
            r += 1

        if cur >= k:
            ans += (n - r + 1)

        trie.remove(s[l])
        cur -= trie.contribution(s[l])
        l += 1

        if r < l:
            r = l

    print(ans)

if __name__ == "__main__":
    solve()
```トライは、ペアごとの比較をプレフィックス集計に置き換えるコア構造です。 の`cnt`フィールドを使用すると、プレフィックスを共有するアクティブな文字列の数を即座に知ることができます。これは、その深さで追加の LCP ユニットを獲得するペアの数に直接変換されます。 

スライディング ウィンドウ ロジックにより、一度進むと正しいエンドポイントを再検討することがなくなり、合計の複雑さが合計入力サイズで線形に保たれます。 

微妙な点の 1 つは、削除の順序です。カウントをデクリメントする前に、発信文字列の寄与を計算する必要があります。そうしないと、残りの文字列との重複が過小評価されてしまいます。 

## 実用的な例

 最初のサンプルを考えてみましょう。 

入力文字列は、`set, stop, setting, state`。 ウィンドウが大きくなるにつれて、次のような共有プレフィックスが追加されます。`st`多くの文字列が最初の文字を共有しているため、貢献度がすぐに蓄積されます。 

空のウィンドウから始めます。 左から拡張して、ペアごとのプレフィックスの合計が K を超えるまで、文字列を徐々に含めます。それが発生すると、右境界のさらなる拡張はその左境界の有効性を保持するため、複数のセグメントが一度にカウントされます。 

2 番目のサンプルでは、​​次のような同一の文字列を繰り返します。`rating, rating`強い寄与を生み出す: それぞれの同一のペアが文字列の全長に寄与するため、スコアはそのブロック内で二次関数的に増加します。 すべてのプレフィックス ノードが複数のパスを蓄積するため、アルゴリズムはトライ カウントを介してこれを瞬時に取得します。

 ## 特殊なケース

 同一の文字列の場合、すべてのペアが文字列全体の長さに寄与します。 パス上のすべてのノードのカウントが増加するため、トライはこれを正しく処理します。そのため、挿入のたびに、既存の同一文字列の数に完全な深さの寄与を乗算したものが正確に追加されます。 

共有プレフィックスのない厳密に素な文字列の場合、すべての寄与はゼロになります。 トライはルートでのトラバーサルをすぐに終了し、文字列ごとに O(1) の効果的な寄与を保証します。 

次のような高度にネストされたプレフィックスの場合`a, ab, abc, abcd`、寄与は累積的に増加するため、スライディング ウィンドウは再計算せずに大きなプレフィックスの重複を正しく累積する必要があります。 トライ ノード カウントのプレフィックス合計の性質により、各レベルがアクティブな文字列ペアごとに 1 回だけカウントされることが保証されます。
