 ## 解決策
 ## 問題の理解

 各値が最大 1023 である整数の配列が与えられるので、すべての数値は 10 ビットに収まります。 審査員は、XOR の観点から考えられる最も強い連続セグメントに関心を持っています。ここで、「最も強い」とは、サブアレイ全体で可能な最大の XOR を意味します。 

次に、プロセスが変わります。配列内のどこにでも、新しい数値を 1 つだけ挿入できます。 この挿入される数値は 0 ～ 1023 の範囲内になければならず、バイナリ表現で正確に k 個のセット ビットを含む必要があります。 挿入後、再びすべての連続するサブ配列を調べ、それらすべてについて最大の XOR を計算します。 目標は、この最大値ができるだけ大きくなるように、挿入される値とその位置の両方を選択することです。 

出力はテスト ケースごとに 1 つの整数、つまり最適な挿入後に達成可能な最適なサブ配列 XOR です。 

n が 100000 までの制約により、配列上の二次関数は直ちに失敗します。 V が小さい場合を除き、挿入された値の候補あたり O(n log V) であっても境界線に達します。ここでは、V は 1024 個の可能な値に固定されています。 この小さな領域が主な構造上のヒントです。つまり、任意の整数を検索しているのではなく、マスクの小さなサブセットを検索しているだけです。 

最適な部分配列が挿入された要素をまったく使用しない場合、微妙なエッジ ケースが発生します。 たとえば、元の配列にすでに非常に強力な XOR セグメントが含まれている場合、不適切に選択された x を挿入しても改善できないため、元の答えは変更されていないと考える必要があります。 もう 1 つのエッジ ケースは、最適なセグメントに挿入された要素が含まれている必要があるが、挿入ポイントの両側に広がる長いセグメントの一部としてのみ含まれ、挿入ポイントで開始または終了する必要がない場合です。 

## アプローチ

 直接的なアプローチは、x のすべての有効な値とすべての可能な挿入位置を試すことです。 挿入後、プレフィックス XOR 列挙を使用して最大サブ配列 XOR を再計算します。 これは、O(n) 個の位置があり、すべてのサブ配列に対するナイーブ スキャンでは最適なサブ配列 XOR の各再計算が O(n^2) であるため、テスト ケースごとの動作は O(n^2) になります。 最適化を行ったとしても、挿入位置ごとに構造を繰り返し再構築することは限界をはるかに超えています。 

最大サブ配列 XOR の標準的な最適化では、プレフィックス XOR を使用します。 任意のサブ配列 XOR は、P[r] XOR P[l − 1] として表現できます。 これにより、問題はプレフィックス値に対する最大 XOR ペア クエリに変換され、O(n · 10) のバイナリ トライを使用して効率的に処理されます。 

重要な構造の単純化は、1 つの要素を挿入しても部分配列 XOR の動作が根本的に変わるわけではないということです。 挿入された要素を回避するか、要素を含める新しいサブ配列を導入するだけです。 それを回避するサブ配列は正確に元のものであるため、元の最大値を追跡する必要があるのは 1 回だけです。 これを含むサブ配列は、プレフィックス部分、挿入された値、およびサフィックス部分に分解でき、変更されたエンドポイントを使用してプレフィックス XOR 関係に折り返すことができます。 

k は最大 10 であるため、[0, 1023] の範囲内のすべての有効な x 値を列挙できます。これは最大 1024 個の候補になります。 各候補について、トライを再構築せずに、プレフィックス XOR に対するトライを使用して、その最良の寄与を計算します。

 ## アルゴリズムのチュートリアル

 まず、元の配列のプレフィックス XOR を計算します。 これにより、任意のサブ配列 XOR を 2 つのプレフィックス値間の XOR として書き込むことができます。 また、これらのプレフィックス値に対してバイナリ トライを構築することで、最大の XOR ペアを効率的にクエリできるようになります。 

次に、元の配列内の最適なサブ配列 XOR を計算します。 これは、標準的な最大プレフィックス XOR ペアの問題です。プレフィックス P[j] ごとに、以前のプレフィックス間で最も一致するものをトライしてクエリし、答えを更新します。

次に、ポップカウントが k に等しい、0 ～ 1023 の範囲内のすべての整数 x を列挙します。 このような x ごとに、x をどこかに挿入した後、最適な部分配列 XOR を評価します。 

挿入の影響を処理するには、挿入された要素を含むサブ配列が 2 つの接頭辞インデックス i < j を選択し、(P[i] XOR P[j]) XOR x を計算することに対応していることがわかります。 固定 j の場合、トライを使用して最適な i を計算し、本来の意味で j で終わる最適な部分配列を与え、それを x と XOR して、挿入された要素がそのセグメントに対する単一のグローバル トグルとして機能することを考慮します。 

したがって、各 j について、P[i] XOR P[j] の i < j にわたる bestPair(j) = max を計算します。 これはまさに、プレフィックス空間の位置 j で終わる最適なサブ配列 XOR です。 挿入された要素を j で終わるセグメントに含めることに決めた場合、達成可能な最良の値は bestPair(j) XOR x になります。 すべての j の最大値を取得します。 

最適な答えは挿入された要素を完全に無視する可能性があるため、これを元の最良の部分配列 XOR と比較します。 

### なぜ効果があるのか

 最終的な配列内のすべてのサブ配列は、2 つのカテゴリのいずれかに分類されます。 挿入された要素が含まれておらず、元の最大値にすでに考慮されているか、挿入された要素が含まれており、x が 1 回だけ適用された 2 つのプレフィックス XOR 状態の組み合わせとして一意に表現できるかのいずれかです。 トライベースの計算では、考えられるすべてのプレフィックス ペアがすでに列挙されているため、これらの候補に対する最終的な XOR として x を適用すると、挿入位置を明示的にシミュレートする必要がなく、すべての挿入要素サブ配列がカバーされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MAXB = 10
MAXV = 1 << MAXB  # 1024

class Trie:
    __slots__ = ("nxt", "cnt")

    def __init__(self):
        self.nxt = [[-1, -1]]
        self.cnt = [0]

    def add(self, x):
        node = 0
        self.cnt[node] += 1
        for b in reversed(range(MAXB)):
            bit = (x >> b) & 1
            if self.nxt[node][bit] == -1:
                self.nxt[node][bit] = len(self.nxt)
                self.nxt.append([-1, -1])
                self.cnt.append(0)
            node = self.nxt[node][bit]
            self.cnt[node] += 1

    def query_max_xor(self, x):
        node = 0
        if self.cnt[node] == 0:
            return 0
        res = 0
        for b in reversed(range(MAXB)):
            bit = (x >> b) & 1
            want = bit ^ 1
            if self.nxt[node][want] != -1 and self.cnt[self.nxt[node][want]] > 0:
                res |= (1 << b)
                node = self.nxt[node][want]
            else:
                node = self.nxt[node][bit]
        return res

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n, k = map(int, input().split())
        a = list(map(int, input().split()))

        # prefix XOR
        px = [0] * (n + 1)
        for i in range(n):
            px[i + 1] = px[i] ^ a[i]

        # original best subarray XOR
        trie = Trie()
        trie.add(px[0])

        best_original = 0
        best_end = [0] * (n + 1)

        for j in range(1, n + 1):
            best_here = trie.query_max_xor(px[j])
            best_end[j] = best_here
            best_original = max(best_original, best_here)
            trie.add(px[j])

        valid_x = []
        for x in range(MAXV):
            if x.bit_count() == k:
                valid_x.append(x)

        answer = best_original

        # recompute trie for prefix usage in second pass
        for x in valid_x:
            trie = Trie()
            trie.add(px[0])
            for j in range(1, n + 1):
                best_here = trie.query_max_xor(px[j])
                candidate = best_here ^ x
                answer = max(answer, candidate)
                trie.add(px[j])

        out.append(str(answer))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```実装では、プレフィックスの構築と候補の評価が分離されます。 トライは、有効な x 値に対する第 2 フェーズのテスト ケースごとに再構築されます。 これにより、挿入された異なる値の間で状態が混在することが回避されます。 プレフィックス XOR 配列により、すべてのサブ配列がペアごとの XOR クエリとして表現されるようになり、トライにより、ステップあたりの対数時間で効率的に最適なペアが得られます。 

微妙な点は、挿入位置を明示的に選択しないことです。 これが安全である理由は、挿入された要素を含むすべてのサブ配列がプレフィックス状態のペアに対応しており、j を反復するときにトライがすでにそのようなペアをすべて探索しているためです。 挿入位置は、どのセグメントのエンドポイントが選択されるかによって暗黙的にエンコードされます。 

## 実用的な例

 大きさよりも構造が重要な小さな配列を考えてみましょう。 プレフィックス XOR を通常どおり計算し、k が可能な x 値の小さなセットを選択すると仮定します。 

最良のサブ配列の終わりがどのように進化するかを追跡します。 

| j | px[j] | ベストペア(j) | ×の候補 |
 | --- | --- | --- | --- |
 | 1 | p1 | 0 | 0 ^ x |
 | 2 | p2 | 最大(p1^p2) | ベストペア ^ x |
 | 3 | p3 | 最大(前) | ベストペア ^ x |

 この表は、x の唯一の影響は、各位置で終了する最適なペアの最終的な切り替えであることを示しています。 

これにより、挿入によってどのプレフィックス ペアが重要になるのではなく、結果の XOR 値がどのように変換されるかのみが変更されることが確認されます。 

## 複雑さの分析

 ## 特殊なケース

 挿入された要素が使用されないケースは、アルゴリズムが常に元の最良の部分配列 XOR と比較し、それをベースラインとして保持するため、自然に処理されます。 

挿入された要素が最適なセグメントに必要な場合は、第 2 フェーズで処理されます。このフェーズでは、すべてのプレフィックス ペアが x との XOR で評価され、挿入にまたがるセグメントがプレフィックスの組み合わせとして表現されることが保証されます。 

複数の最適な挿入位置がある場合は、位置が明示的にモデル化されていないため、計算とは無関係です。 考えられるすべてのスパンはプレフィックス ペアを通じてすでにエンコードされているため、有効な挿入位置はトライ プロセスで考慮されるペアに対応します。
