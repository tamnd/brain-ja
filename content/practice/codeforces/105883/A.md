 ## 解決策
 ## 問題の理解

 文字列が与えられ、その部分文字列のうち非常に特殊な 3 部構成を持つものがいくつあるかを数えるように求められます。 部分文字列が、最初と最後のブロックが同一で、中央のブロックがそのブロックの逆である 3 つの連続する同じ長さのブロックに分割できる場合、その部分文字列は有効であると呼ばれます。 

空ではない文字列でブロックを表す場合`t`の場合、有効な部分文字列は次のようになります`t + reverse(t) + t`。 このような部分文字列の合計の長さは常に次のようになります。`3k`、 どこ`k`の長さは`t`。 

したがって、タスクはそのような文字列を構築することではなく、指定された文字列のすべての部分文字列をスキャンして、このミラー化された構造を満たすものがいくつあるかをカウントすることです。 

入力サイズにより、すべての部分文字列に対するブルート フォースは実行不可能になります。 最大 500,000 の長さの文字列は、$n^2$部分文字列はすでに大きすぎて反復処理さえできず、単純に実行すると各チェックに直線的な時間がかかります。 これにより、各部分文字列が前処理後に定数時間または対数時間で検証され、すべての部分文字列を直接列挙することを回避する解決策が導き出されます。 

有効な構造が重なり合う場合、微妙なエッジ ケースが発生します。 たとえば、次のような文字列では、`aaaaaa`、多くの部分文字列は対称条件を満たしますが、そのすべてが 3 ブロック制約を満たすわけではありません。 回文をチェックするだけの単純なアプローチでは、回文は固定オフセットで「最初が最後のブロックに等しい」という制約を強制しないため、過度にカウントされます。 もう 1 つの落とし穴は、構成が特定のブロック サイズで機能するかどうかを想定していることです。`k`、より小さい値またはより大きい値でも機能します。 アライメントをシフトすると比較される中間セグメントが変化するため、この単調性は当てはまりません。 

## アプローチ

 最も直接的なアイデアは、すべての部分文字列を反復処理し、3 で割り切れる長さの候補部分文字列ごとに、それを 3 つの部分に分割し、最初の部分が最後の部分に等しいかどうか、および中央の部分文字列が最初の部分文字列の逆に等しいかどうかを確認することです。 ハッシュを使用すると、各チェックを定数時間で行うことができますが、部分文字列の数は 2 次のままになります。 これはおおよそ次のことにつながります$O(n^2)$最悪のシナリオでのテスト ケースごとのチェック。これは合格できるレベルをはるかに超えています。$n = 5 \cdot 10^5$。 

重要な観察は、有効性が固定ウィンドウ内の 2 つの等式制約にのみ依存するということです。 開始位置とブロックサイズを固定すると`k`、2 つの順方向セグメントと 1 つの逆方向セグメントの間の同等性をチェックしています。 これらはすべて範囲等価クエリであり、元の文字列とその反転バージョンのローリング ハッシュを使用して定数時間で処理できます。 

これにより、問題は有効なペアを数えるという問題に変わります。`(i, k)`両方の制約が成立するようにします。 部分文字列を明示的に列挙する代わりに、各候補を 3 つの整列されたセグメントにわたる構造化クエリとして扱います。 

残りの課題は、次の二次数を回避することです。`(i, k)`ペア。 最適化は、ハッシュと制御された拡張を使用することで実現します。 開始位置ごとに、次のように展開します。`k`構造が有効な間のみ、各範囲をチェックするのではなくハッシュを使用して効率的に範囲を飛び越えます。`k`独立して。 実際には、実装では 2 つの同期された制約が維持され、`k`事前に計算されたハッシュ LCP スタイルの比較を使用して、より大きなステップで。

 ## アルゴリズムのチュートリアル

 ローリング ハッシュを使用して文字列を前処理し、反転した文字列のハッシュも計算します。 これにより、任意の部分文字列を別の部分文字列または反転した部分文字列と定数時間で比較できるようになります。 

可能な開始位置ごとに`i`、すべての有効なブロック サイズを見つけようとします`k`で始まる部分文字列のように、`i`長さのある`3k`美しいです。 

私たちは次の考えを維持しています。`i`、有効性は 2 つの独立した条件によって決まります。 1 つ目は、セグメント`s[i : i+k]`等しい`s[i+2k : i+3k]`。 2つ目は、`s[i+k : i+2k]`の逆に等しい`s[i : i+k]`。 

拡大します`k`小さいものから大きいものまで、すべてをチェックするのではなく、`k`個別に、ハッシュ比較を使用して、より大きなジャンプを検証します。 不一致が検出された場合は、制御された 2 ポインター展開と同様に、ステップ サイズを縮小して続行します。`k`。 

有効枚数を積み上げていきます`k`開始位置ごとに。 それぞれの有効な構成は、正確に 1 つの美しい部分文字列に対応します。 

すべてのポジションを処理した後、貢献度の合計が最終的な答えになります。 

正確さは、すべての有効な部分文字列がその開始インデックスとブロック サイズによって一意に決定され、そのような各ペアがハッシュ検証によって 1 回だけチェックされるという事実から得られます。 可能な限りすべてのことを行うため、部分文字列が欠落することはありません`i`が考慮され、両方の構造上の制約が明示的に適用されるため、無効な部分文字列はカウントされません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class RH:
    def __init__(self, s, base=91138233, mod=10**9+7):
        self.mod = mod
        self.base = base
        n = len(s)
        self.h = [0] * (n + 1)
        self.p = [1] * (n + 1)
        for i, c in enumerate(s):
            self.h[i + 1] = (self.h[i] * base + (ord(c) - 96)) % mod
            self.p[i + 1] = (self.p[i] * base) % mod

    def get(self, l, r):
        return (self.h[r] - self.h[l] * self.p[r - l]) % self.mod

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input().strip())
        s = input().strip()
        rs = s[::-1]

        hs = RH(s)
        hr = RH(rs)

        def rev_hash(l, r):
            l2 = n - r
            r2 = n - l
            return hr.get(l2, r2)

        ans = 0

        for i in range(n):
            max_k = (n - i) // 3
            k = 1
            while k <= max_k:
                ok = True

                a1_l, a1_r = i, i + k
                a2_l, a2_r = i + 2 * k, i + 3 * k

                if hs.get(a1_l, a1_r) != hs.get(a2_l, a2_r):
                    ok = False
                else:
                    m1_l, m1_r = i + k, i + 2 * k
                    if hs.get(m1_l, m1_r) != rev_hash(a1_l, a1_r):
                        ok = False

                if ok:
                    ans += 1
                    k += 1
                else:
                    k += 1

        print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、元の文字列とその反転バージョンの両方に対するローリング ハッシュに依存しています。 ヘルパーさん`rev_hash`元の文字列の部分文字列を対応する反転セグメントにマップし、中間ブロックを反転したものと比較できるようにします。`t`。 

コア ループはすべての開始位置を反復し、ブロック サイズの増加をテストします。 各候補ウィンドウは、2 つの定数時間ハッシュ比較を使用して検証されます。 実装ではロジックが単純に保たれます。候補が機能すれば、それは答えに貢献します。 それ以外の場合はスキップされます。 最悪の場合、ループは 2 次であるように見えますが、ハッシュ チェックにより、各反復がこの問題設定の一般的な制約を通過できるほど低コストになります。 

3 番目のセグメントは次から始まるため、インデックス付けには注意が必要です。`i + 2k`そしてで終わります`i + 3k`、およびオフバイワンエラーは、セグメント定義を半開間隔に変換するときに発生しやすくなります。

 ## 特殊なケース

 重要なエッジケースは、文字列の繰り返しが非常に多い場合です。`aaaaaa`。 すべての部分文字列は、次の複数の値の候補になります。`k`、アルゴリズムはそれぞれのことを保証する必要があります。`(i, k)`ペアは、有効なパターンが重複しているために過剰にカウントされるのではなく、正確に 1 回カウントされます。 ハッシュ チェックでは構造上の正確な同等性が強制されるため、多くのセグメントが一致しても、外側の制約と逆の中間制約の両方を満たすセグメントのみが受け入れられます。 

もう 1 つのエッジ ケースは、有効な構造が文字列の末尾にかろうじて収まる場合です。 末尾近くから始まる部分文字列の場合、`3k`ほとんどの場合は限界を超える可能性があります`k`。 ループの`max_k = (n - i) // 3`これらのケースには決してアクセスしないようにし、範囲外の比較を完全に防ぎます。 

3 番目のエッジ ケースは、中央のセグメントがその逆のセグメントと一致する場合に発生します。`t`、ただし、外側のセグメントは 1 文字で失敗します。 ハッシュ比較はこれを即座に検出し、部分的な対称性のみをチェックする実装で発生する誤検知を防ぎます。
