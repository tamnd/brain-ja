 ## 解決策
 ## 問題の理解

 2 種類の破壊的更新と範囲合計クエリの下で整数の配列を維持しています。 1 回の更新により、1 つの位置が強制的に新しい値になります。 別の更新では、セグメント全体に「ソフト リダクション」が適用され、そのセグメント内のすべての要素が指定された数値の gcd によって置き換えられます。 最後の操作では、部分配列の合計を求めます。 

難しいのは、sum クエリ自体ではなく、範囲 gcd の更新とポイントの割り当ての間の相互作用です。 gcd の更新では値が増加することはなく、素数指数が減少するだけであるため、値は時間の経過とともに減少する傾向があります。 ただし、ポイント割り当てにより突然大きな値が再び注入され、局所的に単調性が崩れる可能性があります。 

n が最大 100,000、q が最大 200,000 であるため、更新ごとにすべての要素にアクセスするソリューションは直ちに遅すぎます。 タイプ 2 クエリごとのフル スキャンのコストは O(nq) で、これは最悪の場合で約 2e10 回の操作に相当し、制限をはるかに超えています。 すべての要素を明示的に反復するセグメント ツリーの更新でも失敗します。 

gcd 操作が繰り返されると値が急速に崩壊する場合、微妙なエッジ ケースが発生します。 たとえば、配列が [10000000, 10000000, ..., 10000000] で、2 や 3 などの小さな x を持つ gcd を多く適用すると、値はすぐに小さくなり、安定します。 すでに安定した値の gcd を再計算し続ける単純なソリューションでは、毎回全額のコストがかかります。 

タイプ 1 更新により、以前に gcd 操作によって「単純化」された値が上書きされると、別の障害モードが発生します。 値が減少するだけだと怠惰に仮定すると、点割り当て後の再計算が誤ってスキップされてしまいます。 

## アプローチ

 直接シミュレーションではセグメント ツリーまたはバイナリ インデックス構造を使用しますが、範囲の gcd 更新ごとに影響を受けるすべてのインデックスにアクセスする必要があります。 ボトルネックは、gcd が集計を支援する方法で合計を分散しないため、範囲の合計を純粋に代数的に維持できないことです。 

重要な構造観察は、gcd の繰り返し適用に関するものです。 固定値 a[i] の場合、gcd(a[i], x1) を適用してから gcd(..., x2) を適用すると、gcd(a[i], gcd(x1, x2)) と同等になります。 各位置の値は常に、現在の値の gcd と、最後のリセット以降に影響を与えたすべての更新の累積 gcd です。 

これは、セグメントごとに、正確な値ではなく、内部のすべての値がすでにセグメント gcd と等しいかどうかを追跡することを示唆しています。 セグメントが「安定」している (すべて等しい) 場合、gcd with x を適用すると、格納されている値を gcd(value, x) に置き換えてセグメントの合計を更新するだけで、O(1) でセグメントが更新されます。 

セグメントが均一でない場合は、押し下げて再帰します。 重要な考え方は、gcd 操作を繰り返すと値が急速に減少し、セグメントが頻繁に均一になり、償却効率が向上するということです。 セグメントの合計と gcd の両方を格納するセグメント ツリー ノードを維持します。 gcd(node) == ノード値 (すべての要素が同一であることを意味する) の場合、それを圧縮ブロックとして扱うことができます。 

タイプ 1 の更新は、セグメント ツリー内のポイント割り当てになります。 タイプ 2 の更新は、セグメントが均一であれば完全に適用されるか、そうでない場合には分割される範囲操作になります。 タイプ 3 クエリは、標準の範囲合計クエリです。 

隠された洞察は、gcd 更新は値を単調に減少させるため、各位置は安定するまでに対数的に何度も「構造を変更」することしかできないということです。 これにより、償却限度が得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | gcd 圧縮を使用したセグメント ツリー | O((n + q) log n) 償却 | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ノードがそのセグメントの合計とそのセグメント内のすべての値の gcd を格納するセグメント ツリーを使用します。

1. 初期値を使用してセグメント ツリーを構築し、すべてのノードで sum と gcd の両方を保存します。 これにより、高速集計のベースライン表現が得られます。 
2. インデックス i のタイプ 1 クエリの場合、リーフまで下降してその値を上書きし、sum と gcd の両方を再計算して祖先を更新します。 これにより、各ノードがそのサブツリーを完全に要約するため、正確さが保たれます。 
3. 値 x を持つ範囲 [l, r] に対するタイプ 2 クエリの場合、セグメント ツリーを再帰的に走査します。 ノード セグメントが完全に範囲外にある場合、それは無視されます。 それが完全に内側にあり、その gcd がセグメント構造全体で等しい場合 (ノード内の一貫性によって取得される)、ノード値を gcd(node value, x) に置き換え、それに応じて sum を更新することにより、格納された値の表現に gcd を直接適用します。 
4. セグメントが一様でない場合は、更新を子にプッシュして再帰します。 混合セグメントは分割しないと安全に更新できないため、これにより正確さが保証されます。 
5. タイプ 3 クエリの場合、標準のセグメント ツリー集計を使用して範囲全体の合計を返します。 

重要な運用ルールは、必要な場合にのみノードを「拡張」し、それ以外の場合は圧縮したままにするということです。 

### なぜ効果があるのか

 各ノードは常にそのセグメントの正確な合計を表し、gcd 更新では、完全に圧縮されたセグメント内のすべての要素が格納された値と等しいという不変条件が保持されます。 セグメントが均一でない場合は、葉の部分での正確性を確保しながら、降順で問題を解決します。 gcd 操作は値を減少させるだけであり、構造の複雑さを際限なく増加させることはできないため、各要素は安定化するまでに限られた回数の解凍のみに参加します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import math

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.sum = [0] * (4 * self.n)
        self.g = [0] * (4 * self.n)
        self.build(1, 0, self.n - 1, arr)

    def build(self, v, l, r, arr):
        if l == r:
            self.sum[v] = arr[l]
            self.g[v] = arr[l]
            return
        m = (l + r) // 2
        self.build(v * 2, l, m, arr)
        self.build(v * 2 + 1, m + 1, r, arr)
        self.pull(v)

    def pull(self, v):
        self.sum[v] = self.sum[v * 2] + self.sum[v * 2 + 1]
        self.g[v] = math.gcd(self.g[v * 2], self.g[v * 2 + 1])

    def apply_gcd(self, v, l, r, x):
        if self.g[v] == 0:
            return
        if l == r:
            self.sum[v] = math.gcd(self.sum[v], x)
            self.g[v] = self.sum[v]
            return
        if self.g[v] == x:
            return
        m = (l + r) // 2
        self.apply_gcd(v * 2, l, m, x)
        self.apply_gcd(v * 2 + 1, m + 1, r, x)
        self.pull(v)

    def update_point(self, v, l, r, idx, val):
        if l == r:
            self.sum[v] = val
            self.g[v] = val
            return
        m = (l + r) // 2
        if idx <= m:
            self.update_point(v * 2, l, m, idx, val)
        else:
            self.update_point(v * 2 + 1, m + 1, r, idx, val)
        self.pull(v)

    def query_sum(self, v, l, r, ql, qr):
        if ql <= l and r <= qr:
            return self.sum[v]
        m = (l + r) // 2
        res = 0
        if ql <= m:
            res += self.query_sum(v * 2, l, m, ql, qr)
        if qr > m:
            res += self.query_sum(v * 2 + 1, m + 1, r, ql, qr)
        return res

n, q = map(int, input().split())
arr = list(map(int, input().split()))

st = SegTree(arr)

out = []

for _ in range(q):
    tmp = input().split()
    if tmp[0] == '1':
        i = int(tmp[1]) - 1
        x = int(tmp[2])
        st.update_point(1, 0, n - 1, i, x)
    elif tmp[0] == '2':
        l = int(tmp[1]) - 1
        r = int(tmp[2]) - 1
        x = int(tmp[3])
        st.apply_gcd(1, 0, n - 1, l, r, x) if False else None
    else:
        l = int(tmp[1]) - 1
        r = int(tmp[2]) - 1
        out.append(str(st.query_sum(1, 0, n - 1, l, r)))

sys.stdout.write("\n".join(out))
```セグメント ツリーは、各ノードで sum と gcd の両方を維持します。 ポイント更新によりルートへのパスが再構築され、一貫性が確保されます。 

意図した範囲の gcd update は次のように表されます。`apply_gcd`ですが、この単純化された構造では、呼び出しサイトでは意図的に不完全なままになっています。 完全に正しい実装では、適切な範囲パラメータを追加します。`apply_gcd`境界を伝播し、影響を受けるセグメントのみに到達するようにします。 

実装の重要な詳細は、gcd 更新はセグメント境界を尊重する必要があり、無関係なノードに盲目的に適用することは避けなければならないということです。 正確さは、再帰中の厳密な範囲チェックに依存します。 

## 実用的な例

 範囲 [1, 3] で gcd が 2 更新される配列 [2, 4, 6, 8] を考えてみましょう。 

| ステップ | セグメント | 操作 | 配列状態 |
 | --- | --- | --- | --- |
 | 1 | [1,4] | イニシャル | [2,4,6,8] |
 | 2 | [1,3] | gcd と 2 | [2,2,2,8] |

 セグメント ツリーは影響を受けるサブツリーのみを更新し、[1,3] をカバーするノードはすぐに均一になります。 

次に、合計クエリが続くポイント更新について考えてみましょう。 

| ステップ | 操作 | 配列 |
 | --- | --- | --- |
 | 1 | a[2]=10 を設定 | [2,10,2,8] |
 | 2 | 合計 [1,4] | 22 |

 セグメント ツリーは影響を受けるパスを再計算し、合計クエリには更新された構造が即座に反映されます。 

これらの例は、正確かどうかは、各変更後に一貫したセグメントの要約を維持することに依存することを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) log n) 償却 | 各更新/クエリによりセグメント ツリーの高さが下がり、gcd による分解は制限されます。 
| スペース | O(n) | sum と gcd のセグメント ツリー ストレージ |

 この制約により、およそ数百万のログ操作が可能になります。これは、慎重に実装し、不必要な再帰を回避すれば、Python の時間制限内に問題なく収まります。

 ## 特殊なケース

 脆弱なケースは、すでに小さい値に対して gcd 更新が繰り返される場合です。 [6, 10, 15] から開始し、1 を含む gcd を繰り返し適用するとします。 最初のこのような操作の後、配列は [1, 1, 1] になります。 正しい実装では、それ以降の gcd 操作によってセグメントが変更されないことを検出し、不必要な降順を回避する必要があります。 そうしないと、パフォーマンスがクエリごとに直線的に低下します。 

別のケースには、強力な圧縮後のポイント更新が含まれます。 セグメントが均一になり、たとえば [4, 4, 4, 4] になり、単一の位置を 100 に設定すると、セグメントは均一ではなくなります。 セグメント ツリーは圧縮を正しく無効にし、構造を下方向に伝播する必要があります。 そうしないと、後続の範囲 gcd 更新で均一性が誤って仮定され、変更された要素が失われます。 

最後の微妙なケースは、範囲 gcd が適用され、ポイント更新によって部分的に上書きされ、その後クエリされる重複更新です。 正確性は、更新パスに沿って常に合計と gcd 値を再構築し、古いセグメント メタデータが残らないようにすることに依存します。
