 ## 解決策
 ## 問題の理解

 空で始まり、一連の操作によって変更される文字列を維持しています。 各操作は、末尾に小文字を追加するか、最後の文字が存在する場合は削除するか、現在の文字列内の指定された文字をすべて別の文字に置き換えるグローバル置換を実行します。 

タスクは、すべての操作を順番にシミュレートし、最終的な結果の文字列を出力することです。 何も残っていない場合は、空であることを示す特別なメッセージが出力されます。 

最大の難関は3番目の作戦だ。 文字列全体をスキャンし、タイプ 3 クエリごとに文字を置換する直接シミュレーションは遅すぎます。 最大 100,000 回の操作、線形サイズの文字列、および潜在的に多数のグローバル置換を使用すると、単純なアプローチは二次関数またはさらに悪い動作に退化します。 

エッジケースは主に、削除と置換の間の相互作用から発生します。 置換は位置には依存せず、文字の同一性にのみ依存しますが、削除は論理的に変換された後に文字が消える可能性があることを意味します。 たとえば、「ab」を追加し、a を c に置き換えて削除した場合、最終的な構造は、変換を熱心に適用するか遅延的に適用するかによって異なります。 単純な実装では、置換を繰り返すと、a から b、その後 b から c などのチェーンが形成される可能性があることも忘れてしまう可能性があります。 

もう 1 つの微妙なケースは、交換サイクルが繰り返されることです。 a が b に置き換えられ、その後 b が a に置き換えられる場合、文字列全体を繰り返し書き換える単純な実装では、完全な再スキャンが繰り返される危険があります。 

## アプローチ

 ブルート フォース ソリューションでは、文字列を直接保存し、文字どおり操作を適用します。 最後に追加と削除は O(1) ですが、置換操作では文字列全体がスキャンされ、出現するすべての x が y に置き換えられます。 最悪の場合、O(q) 回の操作があり、各置換に O(n) のコストがかかる可能性があります (n は q まで増加します)。 これにより、O(q²) が得られますが、これは 100,000 回の操作では許容範囲をはるかに超えています。 

重要な点は、置換が行われるときに文字列自体を書き換える必要がないということです。 各文字は、そのリテラル値によって重要ではなく、動的文字変換システムの下で現在どのようにマッピングされているかによって重要になります。 文字列を変更する代わりに、各文字からその現在の表現へのマッピングを維持します。 文字を追加すると、その現在のマップされた形式が保存されます。 置換をクエリすると、マッピングが更新されます。 削除すると、最後に保存されたマップされた文字が削除されます。 

重要な考え方は、置換は文字に対する関数の合成であり、保存されたテキストの変更ではないということです。 文字列内の各文字は元の ID を記憶しており、マッピングによってそれが現在何を表しているかがわかります。

 | --- | --- | --- | --- |
 | ブルートフォース | O(q²) | O(q) | 遅すぎる |
 | マッピング + スタック | O(q) | O(q) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは2つの体制を維持しています。 1 つは、追加された文字のシーケンスを表すスタックです。 2番目は配列です`mp`どこ`mp[c]`現在の代表キャラクターです`c`。 

また、逆の考え方も暗黙的に維持しています。つまり、スタックを書き換えることはなく、スタックの値を解釈するだけです。`mp`。 

1. 配列を初期化する`mp`各文字がそれ自体にマッピングされるようにします。 空のスタックを初期化します。 
2. タイプ 1 の文字による演算の場合`x`、 押す`mp[x]`スタックに。 マッピングされたバージョンはすぐに保存されるため、将来の変更が履歴の意図に影響を与えることはありません。 
3. タイプ 2 の操作の場合、スタックが空でない場合はスタックからポップします。 これは、現在の文字列の最後の文字を削除することを直接モデル化します。 
4. タイプ3の文字による操作の場合`x`そして`y`、マッピングを更新して、現在マッピングされているすべての文字が`x`代わりにマップする必要があります`y`。 具体的には、すべてのエントリを更新します`mp[c]`どこ`mp[c] == x`に設定します。`y`。 アルファベットのサイズは 26 しかないので、これは定数時間です。 
5. すべての操作を処理した後、最終的なマッピングを使用してスタックに格納されている各文字を変換することにより、答えを再構築します。 

これが機能する理由は、アイデンティティと表現を分離することにあります。 スタックには元の追加アクションのシーケンスが保存されますが、`mp`その後に適用されたすべての変換が蓄積されます。 スタック内の文字は常に、現在の意味を反映します。`mp`。 Since replacements are global over character identity and not position-dependent, this separation is exact and lossless.

 ## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    mp = [chr(ord('a') + i) for i in range(26)]
    st = []

    for _ in range(q):
        parts = input().split()
        if parts[0] == '1':
            x = parts[1]
            st.append(mp[ord(x) - 97])
        elif parts[0] == '2':
            if st:
                st.pop()
        else:
            x = parts[1]
            y = parts[2]
            x = mp[ord(x) - 97]
            y = mp[ord(y) - 97]
            for i in range(26):
                if mp[i] == x:
                    mp[i] = y

    if not st:
        print("The final string is empty")
    else:
        print("".join(st))

if __name__ == "__main__":
    solve()
```この実装では、構造の信頼できる情報源としてスタックが維持されますが、マッピング配列はグローバルな置換を反映するように進化します。 重要な繊細さは適用です`mp[x]`これにより、古い文字が現在の意味形式で固定されます。 交換時には両方を正規化します`x`そして`y`更新を適用する前に現在のマッピングを確認し、置換の連鎖が存在する場合の不整合を防ぎます。 

スタック内のすべての文字はすでに最終的なマップされた状態を反映しているため、最終的な再構築は簡単です。

 ## 特殊なケース

 特殊なケースの 1 つは、空を超えて削除が繰り返されることです。 のような入力の場合`1 a`続いて複数の`2`操作を行う場合、スタックはエラーなく空のままでなければなりません。 この実装では、ポップする前にスタックの長さをチェックし、安全性を確保します。 

もう 1 つのケースは、サイクルを形成する交換の繰り返しです。 例えば、`a→b`、`b→c`、`c→a`。 マッピングのアプローチでは、各操作が現在の代表に基づいて書き換えられ、履歴のロールバックを必要とせずに一貫性が維持されるため、これに対処します。 

最後の微妙なケースは、削除後の置換です。 削除はスタックにのみ影響し、マッピングには影響しないため、要素を削除した後に置換を適用しても以前の状態は破壊されません。 マッピングは残りの文字にのみ適用され続け、ポップされた要素は永久に破棄されます。
