 ## 解決策
 ## 問題の理解

 長さが正確に一致する配列から始めます。$2^n$。 

最終的な値は、隣接する要素を繰り返し組み合わせることによって生成されます。 最初のレベルではビット単位の OR が使用され、次のレベルではビット単位の XOR が使用され、次に再び OR、次に再び XOR が 1 つの数値だけが残るまで交互に使用されます。 残りの数値が現在の配列の答えになります。 

初期配列が与えられた後、更新を受け取ります。 更新ごとに 1 つの配列位置が変更され、変更のたびに新しい最終値を出力する必要があります。 

主な難点は、配列には最大で次のものを含めることができることです。$2^{17} = 131072$要素はいくつでもありえます$10^5$更新情報。 更新のたびにリダクションプロセス全体を再計算するには、毎回配列全体に触れる必要があります。 1 回の完全な再計算にはコストがかかります$O(2^n)$、おおよそ次のようになります$131072$クエリごとの操作。 と$10^5$クエリ、それ以上に増加$10^{10}$2 秒の制限をはるかに超えた操作。 

リダクションの構造は固定されています。 要素のすべてのペアが結合され、次にそれらの結果のすべてのペアが結合されます。 変わるのは 1 枚の葉の値だけです。 これは、各内部ノードがその子の結果を格納するツリー構造を強く示唆しています。 

見落としやすいケースがいくつかあります。 

いつ$n = 1$、ツリーには内部レベルが 1 つだけあります。 答えは簡単です:```
a1 OR a2
```ルートを常に XOR で開始するソリューションは失敗します。 

例：```
1 1
1 2
1 3
```最初に:```
1 OR 2 = 3
```アップデート後:```
3 OR 2 = 3
```出力：```
3
```もう 1 つのよくある間違いは、各レベルに間違った操作を割り当てることです。 

例：```
2 0
1 2 3 4
```レベル 1:```
1 OR 2 = 3
3 OR 4 = 7
```レベル 2:```
3 XOR 7 = 4
```答え：```
4
```OR レベルと XOR レベルを交換すると、結果は異なります。 

3 番目の微妙なケースは、更新後に発生します。 変更されたリーフからルートまでのパス上のノードのみが変更される必要があります。 ツリーの無関係な部分を再構築すると時間が無駄になり、データ構造の目的が損なわれます。 

## アプローチ

 最も直接的な解決策は、ステートメントの説明を正確にシミュレートすることです。 

クエリごとに、配列要素を更新し、次のレベルのリダクションを繰り返し構築し、OR 演算と XOR 演算を交互に行い、1 つの値が残るまで続行します。 これは、文字通り答えの定義に従っているため、正しいです。 

問題はコストです。 配列には以下が含まれます$2^n$要素。 1 回の完全なリダクションでは、すべての要素に一定回数アクセスするため、クエリごとにコストがかかります$O(2^n)$。 最悪の場合は次のようになります。$$10^5 \times 131072$$まったく実行不可能な操作です。 

重要な観察は、リダクション プロセスによってすでに完全な二分木が形成されていることです。 

各リーフは 1 つの配列要素に対応します。 各内部ノードは、その 2 つの子を結合した結果を格納します。 操作は、リーフからのノードの高さのみに依存します。 リーフのすぐ上のノードでは OR が使用され、次のレベルでは XOR が使用され、その後再び OR が使用されます。 

1 つの配列要素が変更されると、そのルート パス上のノードのみが影響を受けます。 葉が変化していないため、他のすべてのサブツリーは変化しません。 

これはまさにセグメント ツリーによって処理される更新パターンです。 削減値をすべてのノードに保存します。 ポイント更新では 1 つのリーフが変更され、再計算のみが行われます。$O(\log N)$先祖たち。 ルートには常に必要な答えが含まれています。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(m・2^n) | O(2^n) | 遅すぎる |
 | 最適なセグメント ツリー | O((2^n) + m log(2^n)) | O(2^n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 元の配列値を葉に含むセグメント ツリーを構築します。 
2. すべての内部ノードについて、そのレベルでどの操作を適用するかを決定します。 
3. 問題の最初のリダクション ステップで OR が使用されるため、葉のすぐ上のノードではビットごとの OR が使用されます。 
4. 次のレベルでは XOR が使用され、その次のレベルでは OR が使用され、ルートまで交互に使用されます。 
5. 構築中に、左と右の子の値を再帰的に構築します。 
6. 現在のレベルに割り当てられた操作を使用して子を結合し、結果をノードに保存します。 
7. アップデートについて$(p, b)$、対応するリーフに移動し、その値を次のように置き換えます。$b$。 
8. 再帰から戻るときに、構築中に使用したのと同じレベル依存の操作を使用してすべての祖先を再計算します。 
9. 更新が完了すると、ルート値は新しい答えと等しくなります。 出力してください。 

### なぜ効果があるのか

 すべての内部ノードは、元のプロセスの対応する中間リダクションに表示される値を正確に表します。 最下位の内部レベルには、最初の反復と一致するペアごとの OR 結果が保存されます。 次のレベルには、それらの値の XOR 結果が保存され、2 番目の反復と一致します。 

不変条件は、各ノードが常に交互の OR/XOR ルールに従ってそのセグメントの正しいリダクション値を格納することです。 構築により、すべてのノードの不変条件が確立されます。 ポイントの更新では 1 つのリーフのみが変更されるため、そのリーフを含むセグメントを持つノードのみが無効になります。 ルートへのパスを再計算すると、不変式が復元されます。 ルートは配列全体を表すため、その値は常に必要な答えになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n, m = map(int, input().split())
    arr = list(map(int, input().split()))

    size = 1 << n
    tree = [0] * (4 * size)

    def build(node, left, right, use_or):
        if left == right:
            tree[node] = arr[left]
            return

        mid = (left + right) // 2

        build(node * 2, left, mid, not use_or)
        build(node * 2 + 1, mid + 1, right, not use_or)

        if use_or:
            tree[node] = tree[node * 2] | tree[node * 2 + 1]
        else:
            tree[node] = tree[node * 2] ^ tree[node * 2 + 1]

    def update(node, left, right, idx, value, use_or):
        if left == right:
            tree[node] = value
            return

        mid = (left + right) // 2

        if idx <= mid:
            update(node * 2, left, mid, idx, value, not use_or)
        else:
            update(node * 2 + 1, mid + 1, right, idx, value, not use_or)

        if use_or:
            tree[node] = tree[node * 2] | tree[node * 2 + 1]
        else:
            tree[node] = tree[node * 2] ^ tree[node * 2 + 1]

    build(1, 0, size - 1, n % 2 == 1)

    answers = []

    for _ in range(m):
        p, b = map(int, input().split())
        update(1, 0, size - 1, p - 1, b, n % 2 == 1)
        answers.append(str(tree[1]))

    sys.stdout.write("\n".join(answers))

if __name__ == "__main__":
    main()
```ツリーには、問題によって記述されたリダクション値が正確に保存されます。 パラメータ`use_or`どの操作がそのレベルに属するかをノードに伝えます。 

ルート操作は木の高さによって異なります。 もし`n`が奇数の場合、ルートは OR を使用します。 もし`n`が偶数の場合、ルートは XOR を使用します。 これは、最下位レベルの OR で始まる交互操作から直接続きます。 

構築中、再帰呼び出しごとに、次のレベルの操作が反転されます。`not use_or`。 再帰がリーフより上のレベルに到達するまでに、演算は常に OR になります。 

更新も同じロジックに従います。 ルートからリーフへのパスは 1 つだけ訪問されるため、対数的な複雑さが得られます。 リーフを変更した後、構築中に使用したのとまったく同じ操作を使用して各祖先が再計算されます。 

すべての演算は、以下の値に対してビット単位の OR および XOR であるため、オーバーフローの懸念はありません。$2^{30}$。

 ## 特殊なケース

 最小の木を考えてみましょう。```
1 1
1 2
1 3
```内部ノードは 1 つだけです。 ツリーは以下を計算します。```
3 OR 2 = 3
```アルゴリズムは次のルートを構築します。`use_or=True`なぜなら`n`奇数です。 答えは次のように正しく報告されます`3`。 

ルート演算が XOR である場合を考えてみましょう。```
2 0
1 2 3 4
```ツリーレベルは次のとおりです。```
1 OR 2 = 3
3 OR 4 = 7
3 XOR 7 = 4
```アルゴリズムはルートを次のように開始します。`use_or=False`なぜなら`n`は均等です。 再帰的交互では、下位レベルの OR が作成され、必要なシーケンスと正確に一致します。 

最終的な配列位置を更新することを検討してください。```
2 1
1 2 4 8
4 0
```更新前:```
(1|2)=3
(4|8)=12
3^12=15
```アップデート後:```
(1|2)=3
(4|0)=4
3^4=7
```4 番目のリーフとその祖先をカバーするノードのみが再計算されます。 アルゴリズムはそのパスと出力を正確に更新します。`7`、境界インデックスの正しい処理を確認します。
