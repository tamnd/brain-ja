 ## 解決策
 ## 問題の理解

 システムは、ライブ プログラミング コンテストのスコアボードを維持します。 0 から k までのインデックスが付けられた複数のチームがあり、送信は厳密にタイムスタンプの昇順で到着します。 それぞれの提出物は 1 つのチームに属し、26 通のレターのうちの 1 つの問題に属し、承認または拒否されます。 

問題は、最初に解決された場合にのみチームのスコアに貢献します。 解決時間は、その問題に対して最初に受理された送信の分ベースのタイムスタンプです。 最初の承認の前に拒否された提出物には、それぞれ 20 分のペナルティが追加されます。 チームの問題が解決されると、同じ問題に対するその後の提出は得点には影響しません。 

チームのランクは、まず解決した問題の数によって決定され、次に合計ペナルティ時間によって決定されます (小さいほど優れています)。 解決数とペナルティが同じチームは同じランクになります。 

このタスクは、通常の意味で完全なスコアボードを明示的に維持することではなく、チーム 0 のみを監視することです。チーム 0 が新たに問題を解決するたびに、そのタイムスタンプ、問題文字、およびその解決策を組み込んだ直後にそのランクがどのように変化するかを出力する必要があります。 ランクが変わらない場合でも、イベントは報告する必要があります。 

主な困難は、チーム 0 が新たに解決するたびに、解決数とペナルティの両方に応じた動的な順序付けの下で、他のすべてのチームとの比較をランクに反映する必要があることです。 

制約は大きく、最大 100,000 チーム、200,000 件の提出までです。 これにより、イベントごとに完全なランキングを最初から再計算するアプローチは即座に除外されます。 更新のたびにすべてのチームをスキャンするソリューションでは、許容限界をはるかに超える O(nk) まで劣化します。 各更新を対数または対数に近い時間で評価できるように、十分な構造を維持するアプローチが必要です。 

微妙な特殊なケースは、同等のランキングから発生します。 同一の解決数とペナルティを持つ 2 つのチームは同じランク番号を共有するため、ランクの計算は事実上、(解決数、ペナルティ) による辞書順で厳密に上位にあるチームの数をカウントすることに基づいています。 

もう 1 つのよくある落とし穴は、問題ごとに最初に受け入れられた提出物のみが重要であることを忘れていることです。 チームはストリーム内の同じ問題に対して多数の AC 提出を持っている可能性がありますが、最も早いものだけがカウントされ、その 1 つがペナルティを与える前にのみ拒否されます。 

## アプローチ

 直接シミュレーションでは、チームごとに解決された問題の数と合計ペナルティが維持され、提出ごとにこれらの値が更新されます。 チーム 0 に関する更新が行われるたびに、すべてのチームをスキャンし、現在のペア (解決済み、ペナルティ) を比較することによって、そのランクを再計算します。 これが機能するのは、ランキングが純粋にこれら 2 つの値によって定義され、比較関数が明確に定義されているためです。 

問題は、この単純なランキングの再計算にコストがかかることです。 チーム 0 の解決イベントごとに、k チームのスキャンには O(k) のコストがかかります。 最悪の場合、そのようなイベントが O(n) 件あり、合計は O(nk) になります。n と k がそれぞれ最大 200,000 と 100,000 になる場合、これは大きすぎます。 

重要な観察は、すべてのチームの完全な並べ替え順序は決して必要ないということです。 特定の瞬間に、厳密にチーム 0 よりも優れているチームが何チームあるかを知る必要があるだけです。これにより、タスクは、解決されたカウントとペナルティという 2 次元のキー空間にわたる動的なカウント問題に縮小されます。 

これは、ポイントの更新 (チームの解決済みカウントまたはペナルティが変更されたとき) とプレフィックスまたはドミナンス クエリをサポートするデータ構造を維持することを示唆しています。 ただし、ペナルティは時間の累積に依存し、大きく変動するため、ペナルティの次元を簡単に離散化することはできません。 より現実的なアプローチは、チームを解決数ごとにグループ化し、各グループ内でペナルティごとに順序付けられた構造を維持することです。

考えられる解決数ごとに、ペナルティのバランスの取れた構造 (またはソートされたリスト) を維持できます。 解決数は最大 26 であるため、グループ化は小さく安定しています。 各チームは、新しい問題を解決した場合にのみ移動し、解決数が 1 増加し、ペナルティが既知の値だけ増加します。 

したがって、チーム 0 をランク付けするために、厳密に多くの問題を解決したチームが何チームあるか、および同じ解決済みグループ内で厳密にペナルティが小さいチームが何チームあるかを計算します。 これは、各グループがソートされたマルチセット構造で維持されている場合に効率的になります。 

システムは動的ですが、更新はローカライズされます。チームの各ソルブはグループ内の 1 つの要素のみを変更するため、削除と再挿入を O(log k) 時間で行うことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 各イベント後にブルート フォースでランクを再計算する | O(nk) | O(k) | 遅すぎる |
 | 解決済み + 順序付けされたペナルティでグループ化 | O(n log k) | O(k) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 提出物を順番に解析し、各チームと問題が解決されたかどうか、最初の承認までに何回試行が失敗したかを管理します。 これは、ペナルティが最初の AC 前の失敗にのみ依存するため必要です。 
2. 各チームについて、解決された問題の数とペナルティの合計という 2 つの基本的な値を維持します。 これらはスコアボードの位置を定義します。 
3. 解決数ごとにグループ化された構造を維持します。 各チームの解決済みカウントは 0 ～ 26 であるため、現在そのバケット内にあるチームのペナルティのソートされたマルチセットを各カウントに対して保存します。 
4. 最初は、すべてのチームがバケット内にあり、解決済み = 0、ペナルティ = 0 です。 
5. 送信を処理するときに、対応するチームの状態を更新します。 その問題が最初に受け入れられる前に拒否された場合は、一時的な失敗のカウントを増やします。 それが最初の受け入れである場合、その寄与を計算し、バケット移行を実行します。 
6. チームが新しい問題を解決すると、古い (解決済み、ペナルティ) 状態が現在のバケットから削除され、更新された状態が次のバケットに挿入されます。 これにより、すべてのバケットの一貫性が保たれます。 
7. AC イベントでチーム 0 を更新した後、以下を合計してそのランクを計算します。 

より高い解決数を持つバケット内のすべてのチームに加えて、厳密に優れた (より低い) ペナルティを持つバケット内のすべてのチーム。 
8. タイムスタンプ、問題、ランク遷移を出力します。 以前のランクは、更新前に同じ手順を使用してオンザフライで再計算することも、増分的に保存することもできます。 

なぜ効果があるのか:

 不変条件は、すべてのチームが常にその解決数に対応する 1 つのバケットに保存され、各バケット内でペナルティが完全に順序付けされることです。 ランキング ルールでは、最初に解決された数を比較し、次にペナルティを比較するため、他のチームよりも上位にランク付けされるチームは、より高いバケットに位置するか、同じバケットの並べ替えられたペナルティ順で前に現れる必要があります。 この構造により、ランク クエリは、明確に定義された順序付けされたパーティション内の要素をカウントするのと同等になり、更新のたびに正確性が維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from bisect import bisect_left, bisect_right, insort

def parse_time_to_minutes(t):
    # hh:mm:ss.SSS -> minutes
    hh = int(t[0:2])
    mm = int(t[3:5])
    return hh * 60 + mm

def time_str(t):
    return t  # already formatted

def solve():
    k, n = map(int, input().split())

    # per team: solved count, penalty
    solved = [0] * (k + 1)
    penalty = [0] * (k + 1)

    # per team per problem state
    solved_prob = [[False] * 26 for _ in range(k + 1)]
    fail_count = [[0] * 26 for _ in range(k + 1)]

    # buckets: solved_count -> sorted list of penalties
    buckets = [ [] for _ in range(27) ]

    # initially all teams in (0, 0)
    for i in range(k + 1):
        buckets[0].append(0)

    for b in buckets:
        b.sort()

    def remove(bucket, val):
        i = bisect_left(bucket, val)
        bucket.pop(i)

    def rank_of(team):
        sc = solved[team]
        p = penalty[team]

        better = 0
        for s in range(sc + 1, 27):
            better += len(buckets[s])

        bucket = buckets[sc]
        idx = bisect_left(bucket, p)
        better += idx

        return better + 1

    for _ in range(n):
        parts = input().split()
        t = parts[0]
        team = int(parts[1])
        prob = ord(parts[2]) - 65
        res = parts[3]

        if solved_prob[team][prob]:
            continue

        if res == "RJ":
            fail_count[team][prob] += 1
            continue

        # AC case
        solved_prob[team][prob] = True

        old_sc = solved[team]
        old_pen = penalty[team]

        add_pen = parse_time_to_minutes(t) + 20 * fail_count[team][prob]
        penalty[team] += add_pen
        solved[team] += 1

        # move between buckets
        remove(buckets[old_sc], old_pen)
        insort(buckets[old_sc + 1], penalty[team])

        if team == 0:
            prev_rank = rank_of(team)  # after update; recompute by subtracting effect

            # compute rank before update by temporarily reverting
            # revert
            remove(buckets[old_sc + 1], penalty[team])
            insort(buckets[old_sc], old_pen)

            solved[team] -= 1
            penalty[team] = old_pen

            cur_rank = rank_of(team)

            # reapply update
            remove(buckets[old_sc], old_pen)
            insort(buckets[old_sc + 1], old_pen + add_pen)

            solved[team] += 1
            penalty[team] = old_pen + add_pen

            print(f"{t} {parts[2]} #{cur_rank} -> #{prev_rank}")

if __name__ == "__main__":
    solve()
```この実装では、各チームの状態を段階的に追跡し、バケット化されたマルチセットを使用して、解決されたカウントとペナルティによる順序を維持します。 二分操作により、更新が各バケット内で対数的に維持されることが保証されます。 

ランク計算関数は、より高い解決バケット内のすべてのチームをカウントし、次に同じバケット内で厳密に優れたペナルティ位置を持つチームが何チームあるかをカウントします。 これはランキング ルールを直接反映しています。 

チーム 0 の少し冗長な「元に戻して再適用」セクションにより、グローバル状態を再構築せずに更新前と更新後の両方のランクを計算できるようになります。

 ## 特殊なケース

 チームが同じ問題に対して複数の AC を提出する場合、微妙なケースが発生します。 このアルゴリズムは、問題を解決済みとしてマークし、その後の送信を無視することでこれを保護し、ペナルティや解決済みのカウントが二重にカウントされないようにします。 

もう 1 つのエッジ ケースは、最初の解決によりチームがバケット間を移動する場合です。 削除と挿入は正しい順序で行う必要があります。 そうしないと、ランク計算で一時的に矛盾した状態が観察されます。 この実装により、更新が各送信イベント内でアトミックであることが保証されます。 

最後のケースは同順位です。 複数のチームが同じ（解決済み、ペナルティ）を共有する場合、それらはすべて同じバケットの位置を占めます。 ランクの計算では厳密に優れたチームのみが正しくカウントされるため、同点のチームには追加の処理を行わずに自然に同じランク番号が与えられます。
