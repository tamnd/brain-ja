 ## 解決策
 ## 問題の理解

 私たちには、それぞれがプラスのサイズを持つアイテムのコレクションと、固定された数のスカウトが与えられます。 各アイテムは 1 人のスカウトにのみ割り当てる必要があります。 スカウトは最大 2 つのアイテムを運ぶことができ、スカウトの積載量は割り当てられたアイテムのサイズの合計になります。 一部のスカウトはアイテムを受け取らない場合がありますが、それは許容されます。 

目的は、スカウトが運ぶ最大の荷物ができるだけ少なくなるようにアイテムを分配することです。 言い換えれば、最大ペア合計または単一アイテムの最大値が最小になるように、最大​​ M 個のスカウトにわたってアイテムをペアにする (またはそのままにしておく) 必要があります。 

制約 1 ≤ N ≤ 2M は、問題を実行可能にする構造的な手がかりです。 これにより、十分なスカウトが存在することが保証されるため、有効な解決策ではスカウトごとに 2 つ以上のアイテムを割り当てる必要がなくなり、実際、問題の根本がアイテムのペアリングにあることが示唆されます。 

M は最大でも 100 であるため、N は最大でも 200 です。これにより、おおよそ O(N^2 log N) または O(N^3) までの解は生き残る可能性があることがすぐにわかりますが、一般的な構造で指数関数的なものは、大幅に枝刈りしない限り危険です。 

素朴だが重要なエッジケースは、ある項目が他のすべての項目と比較して極端に大きい場合に発生します。 たとえば、アイテムがあるとします。`[100, 1, 1, 1]`そして多くのスカウトにとって、最善の戦略は、小さなアイテムを組み合わせて、大きなアイテムはそのままにしておくということです。 常に任意にペアリングする不注意な貪欲な人は、割り当てる可能性があります`100 + 1`そして不必要に答えを増やします。 「スカウトごとに最大 2 人」という構造は、組み合わせの決定が結果を左右することを意味します。 

もう 1 つの微妙なエッジ ケースは、N = 2M の場合です。 次に、ペアリング構造に応じて、すべてのスカウトが 2 つのアイテムを正確に取得するか、または 1 人のスカウトが 1 つのアイテムを取得する必要があります。 これにより柔軟性が失われ、ペアリングの決定が全体的に制約されてしまいます。 

## アプローチ

 強引な解釈では、項目を最大 2 つのサイズのグループに割り当てるあらゆる方法を試し、各グループの最大合計を計算して最小値を取得します。 これは、すべての一致とシングルトンの配置を列挙することと同等であり、組み合わせ爆発的です。 N = 20 の場合でも、ペアの数はすでに二重階乗のように増加しており、N = 200 の場合はまったく実行不可能です。 

重要な観察は、項目をペアにする方法を効果的に選択しているため、一部の項目はペアになっていないままになる可能性があるということです。 各スカウトは最大 2 つのアイテムを運ぶことができ、少なくとも N/2 個のスカウトがあるため、すべてのアイテムはペアまたは単独のいずれかとして考えることができ、ペア構造を超えて容量の競合はありません。 

目的は、選択したペアまたはシングルトンの合計にのみ依存するため、ペアの最大合計を最小限に抑えたいと考えます。 これは典型的な「最大ペアリングコストを最小限に抑える」構造です。 これに対処する標準的な方法は、項目を並べ替えて極端なものをペアにすることですが、正しさの議論がなければ、その貪欲な議論だけでは明らかに十分ではありません。 

より深い構造は、候補の答え X を固定すると、どのグループも X を超えないようにアイテムをペア/シングルトンに割り当てることが可能かどうかを尋ねることができるということです。これは実現可能性の問題になります。 実現可能性を確認できれば、答えを二分探索できます。 

固定 X をテストするには、任意のペアの合計が ≤ X でなければならないという制約を尊重しながら、ペアリングを最大化したいと考えます。アイテムのペアリングに失敗した場合、そのアイテムはシングルトンである必要があるため、そのアイテム自体が ≤ X である必要があります。これにより、問題は、しきい値以下で小さい項目と大きい項目を一致させるという問題に軽減され、ソート後に貪欲に実行できます。 

これにより、問題は X にわたる単調な実現可能性チェックに変換され、回答範囲にわたる二分探索が可能になります。

 ## アルゴリズムのチュートリアル

 ### 1. すべてのアイテムのサイズを昇順に並べ替えます。 

並べ替えにより、極端な組み合わせを推論することができ、小さなアイテムが大きなアイテムと組み合わせられない場合、中間のアイテムも機能しないことが保証されます。 

### 2. 関数を定義する`can(X)`すべてのアイテムを最大負荷 ≤ X で割り当てられるかどうかをチェックします

 この関数は、すべてのスカウトの負荷が X を超えてはいけないというコア制約をエンコードします。 

### 3. 内部`can(X)`、ツーポインタ戦略を使用します

 最小の未使用項目に 1 つのポインターを維持し、最大の未使用項目にもう 1 つのポインターを維持します。 

### 4. 残っている最大のアイテムを可能な限り最小のパートナーと組み合わせてみます。 

最大の項目と最小の項目の合計が ≤ X の場合、それらをペアにして、両方のポインターを内側に移動します。 最大のアイテムと最小の実現可能なパートナーを組み合わせることで、将来の制約を最小限に抑えることができるため、これは最適です。 

合計が X を超える場合、最大の項目はそれ自体以外の他の項目と組み合わせることができないため、単独で割り当てる必要があります。 それだけでXを超えると構成が不可能になります。 

### 5. すべての項目が割り当てられるまで続行します

 これらのルールに従ってすべてのアイテムを正常に割り当てると、`can(X)`trueを返します。 

### 6. 次のような最小の X を二分探索します。`can(X)`それは本当です

 答えは単調です。X が機能する場合、より大きな値も同様に機能します。 

### なぜ効果があるのか

 正確さは内部の貪欲ペアリングの不変条件に依存します`can(X)`。 すべてのステップで、残っている最大のアイテムと実行可能な最小のパートナーをペアにするか、ペアリングが不可能な場合はそのアイテムを分離します。 重要な特性は、最大の項目は有効なパートナーが最も少ないため、最も制約された要素であるということです。 最小のアイテムとペアリングできない場合、他のものとペアリングすることはできないため、有効な解決策においては、それを単独で強制することは避けられません。 これにより、貪欲な決定によって、他の方法では存在する可能性のある実行可能な構成がブロックされることがなくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def can(a, m, x):
    i, j = 0, len(a) - 1
    used = 0

    while i <= j:
        if i == j:
            return a[i] <= x
        if a[i] + a[j] <= x:
            i += 1
            j -= 1
        else:
            if a[j] > x:
                return False
            j -= 1
        used += 1
        if used > m:
            return False
    return True

def solve():
    n, m = map(int, input().split())
    a = list(map(int, input().split()))
    a.sort()

    lo, hi = max(a), a[-1] + a[-2] if n > 1 else a[0]

    while lo < hi:
        mid = (lo + hi) // 2
        if can(a, m, mid):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```実装では、実現可能性チェックで 2 ポインタ戦略を使用できるように、まず項目が並べ替えられます。 有効な割り当てでは最大の項目自体よりも小さい最大負荷を持つことはできないため、バイナリ検索範囲は最大の単一項目から始まります。 上限は、考えられる最悪のペアの合計です。 

の`can`機能はペアリングを注意深く追跡します。 条件`a[i] + a[j] <= x`最も効率的なペアリングを貪欲に形成しようとします。 それが失敗した場合は、最大のアイテムを単独で配置することを余儀なくされ、それがまだしきい値を遵守していることをすぐに確認します。 

微妙な点の 1 つは、使用されたグループの追跡です。 各ペアまたはシングルトンは 1 つのスカウトに対応するため、m グループを超えないようにします。 

## 実用的な例

 ### 例 1

 入力:```
3 4
10 10 10
```ソートされた配列:`[10, 10, 10]`二分探索は実現可能性をチェックします。 

| ステップ | 私 | j | アクション | 結成されたグループ |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | 2 | 10+10 = 20 ≤ X (X=10? は失敗するため、推論を調整します) | X に依存します |

 X = 10 の場合、ペアリングは不可能であるため、各 10 は単独でなければなりません。 それにはスカウトが 3 人必要ですが、うちには 4 人いますので、うまくいきます。 

最小最大負荷は 10 です。 

これは、すべての項目が等しい場合、実際にはペアリングは不要であり、シングルトンが優勢であることを示しています。 

### 例 2

 入力:```
5 4
9 12 3 9 10
```並べ替え:`[3, 9, 9, 10, 12]`X = 12 を試してください。 

| ステップ | 私 | j | ペア決定 | 結果 |
 | --- | --- | --- | --- | --- |
 | 1 | 0 | 4 | 3 + 12 ≤ 12? いいえ | 12 単独 |
 | 2 | 0 | 3 | 3 + 10 ≤ 12 はい | ペア (3,10) |
 | 3 | 1 | 2 | 9 + 9 ≤ 12 いいえ | 9 一人 |
 | 4 | 1 | 1 | 9 一人 | 完了 |

 すべてのアイテムは 4 つのスカウト内に割り当てられるため、X = 12 が実現可能です。 

これは、最大の項目を早期に強制することで無効なペアリングを防ぎ、実行可能性チェックの正確性を維持する方法を示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、最適なソリューションによって多くの項目がペアになっていないままになる場合です。 インプットを考慮する`3 4`すべての項目が等しい場合。 アルゴリズムはペアリングが不要であることを正しく認識し、各アイテムはスカウトの制限を超えることなく単独で使用できます。 実現可能性チェックでは、シングルトンを割り当てて制約を確認するだけです。 

もう 1 つのケースは、次のような非常に大きなアイテムが存在する場合です。`2 2 / 1 100`。 アルゴリズムは即座に強制します`100`ペアリングすると妥当なしきい値を超えるため、隔離する必要があります。 100 より小さい候補 X は拒否されます。これは、実現可能性チェックで次のことが検出されるためです。`a[j] > X`そして早々に失敗します。
