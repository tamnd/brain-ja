 ## 解決策
 ## 問題の理解

 文字列のコレクションが与えられ、各文字列は簡略化されたローマ数字体系で書かれた数値を表します。 各文字は、固定値 1、5、10、50、100、500、1000 を持つ標準ローマ記号 I、V、X、L、C、D、M のいずれかです。 

解釈規則は、古典的な厳密なローマ規則ではなく、緩和されたバージョンです。厳密に値が大きいシンボルの左側にシンボルが出現すると、その左側のシンボルはマイナスに寄与します。 それ以外の場合はプラスに貢献します。 通常のローマ数字システムとは異なり、減算は隣接するペアに限定されないため、文字列の後ろに現れるより大きな記号によって記号を「キャンセル」できます。 

入力文字列ごとに、このルールに従って結果の整数値を計算し、出力する必要があります。 

入力サイズにより構造が重要になります。 文字列は最大 1,000 個まで指定でき、すべての文字列の合計長は最大 300,000 文字です。 これは、どのソリューションも合計入力サイズが線形である必要があることを意味します。 各文字列を複数回スキャンしたり、文字のすべてのペアを比較したりするアプローチでは、時間がかかりすぎます。 

素朴な解釈では、すべての文字を後のすべての文字と比較して、それが減算されるかどうかを判断することを提案するかもしれません。 これにより、文字列ごとに 2 次の動作が発生しますが、これは指定されたスケールでは不可能です。 

重要な微妙な点は、減算は、右側のどこかに大きなシンボルが存在するかどうかのみに依存し、距離やそのようなシンボルが何個存在するかには依存しないことです。 

典型的な失敗例は、隣接する文字間の減算のみを解釈することに起因します。 たとえば、文字列「IVI」では、ローカル ルールによって V から I が減算されますが、最後の I が再び正であることを見逃してしまう可能性があります。 

次の文字が大きい場合にのみ減算すると、別の失敗ケースが発生します。 「IXC」では、I と X の両方が後続の大きなシンボルの影響を受けるはずですが、隣接ベースのロジックでは I に対する C の影響が見逃されます。 

## アプローチ

 この強引なアイデアは簡単です。文字ごとに、その右側のすべてをスキャンして、より大きな値のローマ字が存在するかどうかを確認します。 そのようなシンボルが存在する場合は現在の値を減算し、存在しない場合は加算します。 

これは、ルール定義を直接エンコードしているため、正しいです。シンボルの右側に大きなシンボルがある場合、そのシンボルはまさに負になります。 ただし、これには、文字列内の L 文字ごとに、さらに最大 L 文字をスキャンする必要があります。 これにより、文字列あたり O(L²) が得られ、合計長が 300,000 の最悪の場合、これは 10¹⁰ 操作を超えることになり、実現可能な限界をはるかに超えています。 

最適化は視点を逆転させることで実現します。 「この位置の右側に大きなシンボルが存在しますか?」と尋ねる代わりに、「右側から遠くに見える最大のシンボルは何ですか?」と尋ねます。 文字列を右から左にトラバースすると、これまでに検出された最大ローマ字値を維持できます。 各文字について、この最大値よりも厳密に小さい場合は、それを減算する必要があります。 それ以外の場合はプラスに寄与し、最大値を更新します。 

これが機能するのは、「右側に大きなシンボルが存在する」という条件が「サフィックスの最大値が現在の値より大きい」と同等であるためです。

 | 最適 | O(L) 合計 | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 各ローマ数字列を個別に処理します。 

1. 固定マッピングを使用して、各ローマ字をその整数値に変換します。 これにより、シンボル間の定数時間の比較が可能になります。 
2. 変数を初期化する`max_right`ゼロに。 これにより、右からのスキャン中にこれまでに確認された最大値が保存されます。 
3. 文字列を最後の文字から最初の文字までたどります。 
4. 各文字について、その値を次と比較します。`max_right`。 厳密に以下の場合`max_right`、実行中の答えからそれを引きます。 それ以外の場合は、追加して更新します`max_right`この値に。 
5. すべての文字を処理した後、累計を出力します。 

ステップ 4 の重要な考え方は、より大きなシンボルを明示的に検索する必要がないということです。 接尾辞の最大値は、そのようなシンボルが存在するかどうかをすでにエンコードしています。 

### なぜ効果があるのか

 右から左へのスキャン中の任意の位置で、`max_right`i の厳密に右側にあるすべての文字の最大値を表します。 したがって、i の文字は、その右側に、より大きな値を持つ文字が存在する場合にのみ減算されます。 これは問題定義と正確に一致します。 不変条件は、サフィックス i+1..n を処理した後、`max_right`はそのサフィックスの最大値に等しく、位置 i の正しい分類が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

value = {
    'I': 1,
    'V': 5,
    'X': 10,
    'L': 50,
    'C': 100,
    'D': 500,
    'M': 1000
}

def solve(s: str) -> int:
    max_right = 0
    ans = 0

    for ch in reversed(s):
        v = value[ch]
        if v < max_right:
            ans -= v
        else:
            ans += v
            max_right = v

    return ans

def main():
    n = int(input())
    for _ in range(n):
        s = input().strip()
        print(solve(s))

if __name__ == "__main__":
    main()
```マッピング テーブルは固定されており、各文字を定数時間で検索できます。 

メインループは各文字列を個別に処理します。 反転は次のことを保証するため非常に重要です。`max_right`は、接頭辞のプロパティではなく、常に接尾辞の最大値を参照します。 

減算条件は厳密に`v < max_right`、 ない`<=`等しい値は、問題のルールに基づいて減算をトリガーしないためです。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、隣接していない、遠く離れたシンボルによって減算がトリガーされる場合です。 で`ID`、I は大きな記号の隣にありませんが、D が後に現れるため、それでも減算されます。 処理中、最初に D が表示され、設定が行われます。`max_right = 500`、その後、I が処理されて減算され、正しく 499 が生成されます。 

もう 1 つのエッジ ケースは、値が増加し、その後再び減少する場合です。`IVI`。 最初の I はそれより大きな接尾辞なしで処理されるため、追加されます。 次に、V は接尾辞の最大値を更新します。 次に、最後の I が V と比較され、減算されます。 これにより、ペアごとの比較を必要とせずに、アルゴリズムが局所的な増加とその後の減少を正しく処理していることが確認されます。 

最後の微妙なケースは、次のような大きなシンボルが繰り返されることです。`MCM`。 最初の M は最大値を設定し、その右側に M が存在するため C が減算され、最後の M は通常どおり加算されます。 サフィックスの最大値により、文字列の後ろに複数の大きなシンボルが存在する場合でも、前のシンボルが正しく分類されることが保証されます。
