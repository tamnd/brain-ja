 ## 解決策
 ## 問題の理解

 各位置がベリーを含むか空である長いバイナリ文字列でターンベースのゲームをシミュレートしています。 移動はインデックスの選択で構成されます$i$そして固定長セグメント内のすべてのベリーを削除します$i$に$i+3$。 両方のプレイヤーが交互に手を動かし、それぞれの動きで文字列からベリーが永久に削除されるため、今後の動きでは構成が徐々にまばらになっていきます。 

おじいちゃんは常に決定的な貪欲なルールを実行します。つまり、自分の番が来たら、有効な長さ 4 のセグメントをすべてスキャンし、現在最大数のベリーを含むセグメントを選択します。 いくつかのセグメントが同点の場合、均一にランダムに選択します。 エリックは自分のターンで任意のセグメントを選択できます。彼の目標は、ゲームの終わりまでに集めたベリーの総数が少なくともおじいちゃんの総数と同じになるようにすることです。 

入力によって初期構成が提供され、その後の対話はおじいちゃんの選択したセグメントを読み取り、ベリーがなくなるまでエリックの選択したセグメントで応答することで構成されます。 それぞれの動きは状態を永続的に変更するため、決定は最初の文字列だけではなく、進化する文字列に適応する必要があります。 

文字列の長さは最大です$10^5$、そしてどの位置にもちょうど半分のベリーが含まれています。 これにより、各ターン後に文字列全体にわたって最適な動きを最初から再計算するソリューションは即座に除外されます。 移動ごとのリニア スキャンでも、約$10^5 \times 10^4$最悪の場合、動作が遅くなり、厳密なインタラクティブ設定には対応しません。 

微妙な難しさは、目的が単に単独で移動ごとのゲインを最大化することではないということです。 素朴な貪欲な反応は、価値の高い領域を早期に無駄にし、将来の動きはおじいちゃんの適応的な貪欲戦略よりも厳密に悪いものになる可能性があります。 

いくつかの失敗シナリオが自然に現れます。 If Erik always picks the first maximum segment he sees, then on inputs like a dense cluster of overlapping berry windows, he may consistently choose a suboptimal tie and fall behind. 各移動後にウィンドウ全体の合計を再計算すると、再計算コストが大きく影響します。 各削除が重なり合うウィンドウに影響を与えることを無視すると、古い評価を使用し、無効な「最良の」セグメントを繰り返し選択する可能性があります。 

## アプローチ

 The brute force strategy is straightforward: at each turn, compute the number of berries in every length 4 segment, pick the best one, and simulate removal. 各再計算スキャン$O(N)$窓があり、$O(N)$各移動が少なくとも 1 つのベリーを削除し、$N/2$全体的にベリー類。 これは次のことにつながります$O(N^2)$時間、つまり約$10^{10}$実現可能性をはるかに超えた、最悪の場合に備えた作戦。 

重要な観察は、各ステップでの決定は現在のウィンドウの合計にのみ依存し、各移動は小さなローカル領域にのみ影響するということです。 セグメントのとき$[i, i+3]$が削除されると、これら 4 つの位置に重なるウィンドウのみが変更されます。 つまり、すべてのウィンドウ合計を再計算するのではなく、段階的に維持できるということです。 

これにより、問題は、小さな間隔で範囲を更新し、最大値を繰り返し抽出することで、ウィンドウ スコアの動的な配列を維持することに変わります。 ヒープなどの max 構造は候補ウィンドウを保存できますが、古いエントリは現在の文字列の状態を反映しなくなったときに遅延して破棄されます。 各更新では変更のみが行われます$O(1)$したがって、償却された複雑さが効率的になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(N^2)$|$O(N)$| 遅すぎる |
 | ローカル更新を含むヒープ |$O(N \log N)$|$O(N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 現在のベリー配列と、長さ 4 のウィンドウごとに現在のスコアを追跡する補助構造を維持します。 また、ウィンドウ スコアをキーとした優先キューも維持します。 

1. 各位置に現在ベリーがあるかどうかを表す配列を初期化します。 配列を構築する`score[i]`ポジションのベリーの数に等しい$i$に$i+3$。 これは、そのセグメントを選択することの即時的な価値を表します。 
2. すべてのインデックスを挿入します$i$をキーとした最大ヒープに`score[i]`。 各エントリにはバージョン マーカーも保存されるか、後で一貫性を再チェックすることに依存します。 
3. 各ターンごとに、それが誰の動きであるかを決定します。 おじいちゃんの移動中、インデックスを読む$i$、ベリーを取り除きます$i$に$i+3$それらの位置がまだ存在する場合はゼロに設定します。 
4. ベリーを削除した後、これら 4 つの位置によって影響を受けるすべてのウィンドウ スコアを更新します。 各位置は最大 4 つのウィンドウに属するため、これらのいくつかのウィンドウの合計を再計算し、更新された値をヒープにプッシュします。 
5. エリックの動きについては、保存されているスコアが現在の真のスコアと一致するウィンドウが見つかるまで、ヒープの先頭を繰り返し抽出します。 更新後に古いヒープ エントリが残るため、このフィルタリングが必要です。 
6. そのインデックスを出力し、同じ削除プロセスを適用して、影響を受けるウィンドウを再度更新します。 
7. すべてのベリーが除去されるまで続けます。除去された時点で有効なウィンドウは残っておらず、プロセスは自然に終了します。 

### なぜ効果があるのか

 すべてのステップで、ヒープは現在の利益によってランク付けされたすべての候補セグメントを表します。 古いエントリが含まれている場合でも、すべての有効なセグメントは、最終的には常に、最後の変更後にプッシュされた正しい最新のエントリによって表されます。 したがって、最初の古くない最大値は、現在の状態で可能な最善の法的措置に正確に対応します。 両方のプレイヤーが同じ種類のオブジェクトを削除し、更新が対称的であるため、エリックは、同じ進化する状態の歪んだ見方ではなく、常に最適に反応し、古い情報によって体系的に価値が失われることがないようにします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    s = list(input().strip())
    
    alive = [1 if c == 'b' else 0 for c in s]
    
    def window_sum(i):
        return alive[i] + alive[i+1] + alive[i+2] + alive[i+3]
    
    import heapq
    heap = []
    
    for i in range(n - 3):
        heapq.heappush(heap, (-(window_sum(i)), i))
    
    def apply_move(i):
        for j in range(i, i + 4):
            if alive[j]:
                alive[j] = 0
        for j in range(i - 3, i + 4):
            if 0 <= j <= n - 4:
                heapq.heappush(heap, (-(window_sum(j)), j))
    
    def get_best():
        while heap:
            negv, i = heapq.heappop(heap)
            if i < 0 or i > n - 4:
                continue
            if -negv == window_sum(i):
                return i
        return -1
    
    # interactive loop
    total_b = sum(alive)
    while total_b > 0:
        # grandpa move
        try:
            gi = input().strip()
            if not gi:
                break
            gi = int(gi)
        except:
            break
        
        apply_move(gi)
        total_b = sum(alive)
        if total_b == 0:
            break
        
        # erik move
        bi = get_best()
        if bi == -1:
            break
        
        sys.stdout.write(str(bi) + "\n")
        sys.stdout.flush()
        apply_move(bi)
        total_b = sum(alive)

if __name__ == "__main__":
    solve()
```この実装では、残りのベリーのブール配列が保持され、各移動後に影響を受けるウィンドウの合計のみが再計算されます。 ヒープには候補セグメントが現在の値順に格納され、古いエントリは抽出中に遅延して破棄されます。 の`apply_move`4 つのセルの削除に重なっているウィンドウのみが変更できるため、この関数は移動ごとに最大 8 つのウィンドウ開始を更新します。 

正確さは、構造をすべての削除と同期させながら、Erik の現在の最大有効ウィンドウを常に選択することに依存します。 

## 実用的な例

 短い構成例を考えてみましょう。 

入力文字列:`b.bbbb.b`長さ 4 のウィンドウ合計のみを追跡します。 

| ステップ | 移動 | 私が選んだ | 生きている状態 (概念) | 最適なウィンドウ値 |
 | --- | --- | --- | --- | --- |
 | 1 | おじいちゃん | 2 | 中間領域の縮小 | 3 |
 | 2 | エリック | 5 | 右領域が縮小されました | 3 |

 おじいさんが高密度領域を選択した後、エリックは更新されたウィンドウ値を再計算し、別の局所的に最適な領域で応答します。 ヒープにより、Erik はすでに部分的にクリアされている古い高値ウィンドウを決して選択しないことが保証されます。 

2 番目のケース:

 入力文字列:`bbbb....bbbb`| ステップ | 移動 | 私が選んだ | 効果 |
 | --- | --- | --- | --- |
 | 1 | おじいちゃん | 0 | 最初のブロックを大幅に削除します。 
| 2 | エリック | 8 | 2 番目のブロックを大幅に削除します。 

これは、アルゴリズムが切断された高密度領域を自然に分離し、両方のプレーヤーが独立したクラスターから同等の値を確実に抽出できることを示しています。

 ## 特殊なケース

 エッジ ケースの 1 つは、複数の重複ウィンドウの原因となっていたベリーが削除によって削除される場合です。 たとえば、セグメントが完全に密集している場合、`bbbb`と が削除された場合は、影響を受ける 4 つのウィンドウの開始をすべて更新する必要があります。 そうしないと、古い値がヒープ内に残り、後で誤って選択される可能性があります。 ヒープ検証ステップにより、再計算時にこれらのエントリが確実に破棄されます。 

別のケースは境界付近で発生します。 インデックス 0 またはその近くで移動が選択された場合$N-4$、影響を受けるウィンドウは 8 つ未満です。 更新ロジックは明示的に境界をチェックし、無効なインデックスが再計算されないようにし、範囲外のヒープ エントリが導入されるのを防ぎます。
