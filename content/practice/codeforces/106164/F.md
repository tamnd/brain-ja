 ## 解決策
 ## 問題の理解

 私たちには、決まった順序で並べられた一連の祭りの屋台が与えられています。 各屋台には 2 つの属性があります。それは、ジャックがその屋台に入った場合に出会う人々の数と、その屋台に入ることによって得られる幸福です。 ジャックは左から右に歩き、すべての屋台に入るかスキップするかを決定します。 

決定はしきい値によって決まります。 屋台は、その幸福度が厳密にこのしきい値よりも大きい場合にのみ検討の対象となります。 資格のある屋台の中で、ジャックには会う総人数に厳しい制限があり、順番に屋台を処理し、次の資格のある屋台が制限を超えないときはいつでも貪欲に参加します。 

したがって、固定しきい値の場合、プロセスは決定的です。左から右にスキャンし、幸福度が小さすぎる屋台を無視し、そうでない場合は、残りの容量が許せばそれらを取得しようとします。 目的は、選択した屋台から蓄積される幸福の合計です。 タスクは、この合計幸福度を最大化するしきい値を選択することです。複数のしきい値が同じ最良の値を与える場合、そのような最小のしきい値を出力する必要があります。 

この制約により、すべてのしきい値を個別に試してプロセスを最初からシミュレートするソリューションは遅すぎることがわかります。 すべてのテスト ケースでテストごとに最大 200,000 のストールが発生するため、しきい値ごとの単純な再計算では、最悪の場合、時間内に収まる範囲をはるかに超えた 2 次の動作が発生します。 

直感が当てにならない微妙なケースがいくつかあります。 1 つは、しきい値を下げることでより多くの「良い」ストールが可能になるため、効果があるように見える場合です。しかし、幸福度は低くてもコストの高いストールはより早く処理され、容量を消費するため、実際には害を及ぼす可能性があります。 

たとえば、高幸福度の屋台が遅れて出現するが、その前に中程度の幸福度の高価な屋台がいくつかある場合を考えてみましょう。 低いしきい値にはそれらすべてが含まれ、最高の屋台に到達する前にジャックの能力が使い果たされ、全体的な幸福度が減少します。 しきい値を高くすると、初期のブロッカーが除外され、最適なストールが可能になります。 

もう 1 つの重要なエッジ ケースは、複数のしきい値が同じ結果をもたらす場合です。 答えには最小のしきい値が必要であるため、最初に最大値を確認したときだけでなく、適格性が低下する方向に最も早いしきい値を正確に追跡する必要があります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 考えられるしきい値ごとに、左から右への完全なシミュレーションを実行します。つまり、各ストールが適格であるかどうかを確認し、可能であれば貪欲にそれを採用します。 これは正しいです。なぜなら、プロセスはまさに問題が定義しているものだからです。 ただし、しきい値は最大 1e9 の異なる値を取ることができ、重要な値、つまり明確な幸福値に限定したとしても、最大 200,000 の候補が存在します。 各シミュレーションは線形であるため、最悪の場合、これはおよそ 2e10 回の操作となり、実行不可能です。 

重要な点は、しきい値によって処理の順序や容量ルールが変更されないことです。 どのストールが貪欲なプロセスに「見える」かを制御するだけです。 したがって、問題は、幸福度が減少する順に動的にストールを有効にし、貪欲な選択がどのように進化するかを追跡するという問題になります。 

幸福度の減少によって屋台を並べ替えると、しきい値が減少するにつれて、屋台はこの順序で 1 つずつアクティブ化されます。 いつでも、アクティブ セットは、この並べ替えられたリストのプレフィックスで構成されます。 各プレフィックスについて、元のインデックス順序に対して同じ貪欲スキャンを実行し、アクティブなストールのみを考慮した結果が必要です。

プレフィックスごとに最初から再計算するのではなく、段階的にプロセスをシミュレートします。 ストールがアクティブになると、以前に最終決定された決定のみに基づいて、貪欲なプロセスがそれを受け入れるかどうかを即座に決定します。 これが機能するのは、インデックス順序における以前の決定は一度行われると決して変更されず、貪欲ルールは過去の選択にのみ依存するためです。 

これを効率的にサポートするために、すでに受け入れられたストールが現在の総コストに寄与していることを格納するデータ構造を維持します。これにより、新しいストールに到達する前にどのくらいの容量が使用されたかをクエリできるようになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | しきい値を超えるブルート フォース | O(N²) | O(N) | 遅すぎる |
 | 幸福度 + インクリメンタル貪欲シミュレーションで並べ替え | O(N log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### ## アルゴリズムのチュートリアル

 1. すべての屋台を幸福度の降順に並べ替えます。 これにより、しきい値が減少するにつれてストールが適格になる順序が決まります。 幸福度の高い屋台ほど早く入手可能になります。 
2. すでに受け入れられたストールが会った人の総数に寄与していることを追跡し、ストール インデックスに対するプレフィックス合計クエリをサポートする構造を維持します。 これは、特定の位置の前にどれだけの容量が使用されているかを知るために必要です。 
3. 現在使用されている人数の累計と、選択した屋台から蓄積された幸福度の合計を維持します。 これらは現時点での貪欲プロセスの状態を表しています。 
4. 幸福度の高い順に屋台を一掃します。 ストールがアクティブになると、元の貪欲ルールがインデックス順に実行するのとまったく同じように、ストールを処理しようとします。 
5. 位置 i の屋台について、i より前の屋台の中からすでに何人の人が選択されているかを計算します。 このストールの追加が制限 P を超えない場合は、それを受け入れて、構造と累計の両方を更新します。 それ以外の場合は、永久にスキップします。 
6. 各アクティブ化ステップの後、現在の合計幸福度を回答候補として記録します。 この時点に対応するしきい値は、現在の幸福度レベルのすぐ下にあります。これは、このストールが適格になった時点であるためです。 
7. これまでに見た最高の幸福を記録します。 スイープの後半で同じ幸福度が再び達成された場合は、保存されているしきい値を新しいしきい値に更新します。これは、より小さいしきい値に対応するためです。 

### なぜ効果があるのか

 どのストールが適格であるかを決定すると、貪欲なプロセスは完全に決定されます。 幸福度の降順で失速を処理するとき、しきい値が減少するにつれて出現する順序ですべての可能な資格セットを正確にシミュレートします。 各ストールは最大でも 1 回決定され、その決定はインデックス順で以前に固定された決定にのみ依存するため、将来のアクティブ化によって以前の選択が無効になることはありません。 これにより、増分シミュレーションは、しきい値ごとに個別に完全な貪欲プロセスを実行するのと同等になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class BIT:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        return self.sum(r) - self.sum(l - 1)

def solve():
    T = int(input())
    for _ in range(T):
        N, P = map(int, input().split())
        h = [0] * N
        p = [0] * N

        for i in range(N):
            h[i], p[i] = map(int, input().split())

        order = sorted(range(N), key=lambda i: -h[i])

        bit = BIT(N)
        used_people = 0
        total_happiness = 0

        best_happiness = 0
        best_threshold = 10**18

        i = 0
        while i < N:
            j = i
            while j < N and h[order[j]] == h[order[i]]:
                j += 1

            for k in range(i, j):
                idx = order[k] + 1

                people_before = bit.sum(idx - 1)

                if people_before + p[order[k]] <= P:
                    bit.add(idx, p[order[k]])
                    used_people += p[order[k]]
                    total_happiness += h[order[k]]

            current_threshold = h[order[i]] - 1 if i < N else 0

            if total_happiness > best_happiness or (
                total_happiness == best_happiness and current_threshold < best_threshold
            ):
                best_happiness = total_happiness
                best_threshold = current_threshold

            i = j

        print(best_happiness, best_threshold)

if __name__ == "__main__":
    solve()
```このソリューションは、インデックス上にフェンウィック ツリーを構築し、任意のプレフィックスにすでに取り込まれている人の総数を維持します。 これにより、各実現可能性チェックを対数時間で実行できるようになります。 

屋台の掃除は幸福度の降順に行われます。 等しい幸福によるグループ化により、同じしきい値境界を共有するすべてのストールが一緒に処理されることが保証されるため、しきい値の更新は一貫しています。 

微妙な点は、容量を理由に一度拒否されたストールは決して再検討されないことです。 これは、インデックス順に決定が行われるとすぐに最終決定されるという、元の貪欲なプロセスと一致します。

 ## 特殊なケース

 エッジ ケースの 1 つは、高幸福度のストールが遅れて現れても、先にアクティブ化されたストールが容量を消費したためにのみブロックされる場合に発生します。 この状況では、決定がインデックスの順序で固定され、容量チェックによって無効な包含が防止されるため、アルゴリズムは早期のオーバーコミットを正しく回避します。 

もう 1 つのエッジ ケースは、複数の屋台が同じ幸福値を共有する場合です。 これらはスイープ内で同時にアクティブになるため、グループ化によって確実に 1 つのバッチで処理されるため、同じ値レベル内で分割されたしきい値に誤って依存することはありません。 

最後のエッジ ケースは、すべての p 値が P を超えているために失速することができない場合です。その場合、フェンウィック ツリーはスイープ全体を通じて空のままで、合計幸福度は 0 のままで、最小しきい値は当然スイープによって生成される最小の可能な値になり、これは定義と一致します。
