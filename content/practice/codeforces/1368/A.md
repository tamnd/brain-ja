 ## 解決策
 ## 問題の理解

 2 つの正の整数から始めます。`a`そして`b`。 1 つの操作で、1 つの変数をもう 1 つの変数に追加できます。`a += b`または`b += a`。 

操作ごとに変更される値は 1 つだけです。 私たちの目標は、2 つの数値のうち少なくとも 1 つが指定された制限より厳密に大きくなるようにすることです。`n`。 テスト ケースごとに、必要な操作の最小数を見つける必要があります。 

テスト数の点では制約は小さく、最大でも 100 ケースですが、値自体は次のように大きくなる可能性があります。`10^9`。 このことから、検索や動的プログラミングを使用して、考えられるすべての選択シーケンスをシミュレートすべきではないことがすぐにわかります。 1手あたり分岐係数が2でも爆発するだろう。 直接的な戦略が必要です。 

有益な観察は、数値が非常に急速に増加することです。 常に大きい値を小さい値に加算すると、シーケンスはフィボナッチ増加と同様に動作します。 値から開始して、`10^9`を超える前に必要な操作の数`n`ほんの数十人です。 これは、常に正しい貪欲な選択をしていれば、単純なシミュレーションがすでに十分に高速であることを意味します。 

慎重に確認する価値のある特殊なケースがいくつかあります。 

仮定する`a = 1`、`b = 1`、`n = 1`。 答えは`1`、 ない`0`、目標は厳密にそれよりも大きくなることであるため、`n`。 最初は両方の値が等しい`n`, そのため、依然として 1 つの操作が必要です。 

仮定する`a = 1`、`b = 2`、`n = 3`。 一度の操作で到達できるのは、`(3,2)`または`(1,3)`、ただし、どちらの値も超えません`3`。 2回目の操作が必要です。 正しい答えは、`2`。 値が等しくなったら停止するという不注意な実装`n`間違った結果が生じます。 

仮定する`a = 5`、`b = 4`、`n = 100`。 アップデートの選択を誤ると、操作数が増加する可能性があります。 たとえば、小さい値を大きい値に繰り返し加算すると、最適な戦略よりも成長が遅くなります。 最小の答えを得るには、各ステップで可能な限り最大の増加を行う必要があります。 

## アプローチ

 ブルートフォースの観点とは、すべての操作を二者択一の選択として考えることです。 州から`(a, b)`に移動するかもしれません`(a + b, b)`または`(a, a + b)`。 操作の数を最小限に抑えたいので、到達可能なすべての状態に対する幅優先検索を想像することができます。 

BFS は操作数の増加に応じて状態を探索するため、このアプローチは正しいです。 問題は州の数です。 控えめなステップ数の後でも、分岐係数 2 により、指数関数的に多くの可能性が生まれます。 このような検索はまったく現実的ではありません。 

重要な観察は、もし私たちがそれを超えたいと思うなら、いつでも、ということです。`n`できるだけ早く、常に大きい数値を小さい数値に加算する必要があります。 

仮定する`a ≤ b`。 

私たちが演奏したら`a += b`、新しい値は次のようになります`a + b`。 

代わりに私たちが実行する場合`b += a`、新しい値は次のようになります`b + a`ですが、小さい方の値は変化しません。 

最初の選択は変化します`(a, b)`の中へ`(a + b, b)`、2番目はそれを次のように変換します`(a, a + b)`。 

どちらの演算後の大きい方の数値も同じです。`a + b`。 違いは、最初の選択では小さい値も増加することです。 将来の加算では両方の数値が使用されるため、より大きな小さな値は将来の演算にのみ役立ちます。 小さい値をできるだけ大きくしておくことは決して悪いことではなく、多くの場合役に立ちます。 

これにより、次のような単純な貪欲なプロセスが行われます。 

いずれかが超えるまで、大きい数を小さい数に加算し続けます。`n`。 

値はフィボナッチ数のように増加するため、反復回数はわずかです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | 最適な貪欲なシミュレーション | O(k) | お(1) | 承認済み |

 ここ`k`実行された操作の数です。指定された制約の場合、最大でも約 50 です。 

## アルゴリズムのチュートリアル

 1. 演算カウンタをゼロに初期化します。 
2. 両方とも`a`そして`b`せいぜい`n`、操作の実行を続けます。 
3. 2 つの値を比較します。 
4. もし`a < b`、 実行する`a += b`。 
5. それ以外の場合は実行します`b += a`。 

This always increases the smaller value, producing the largest possible pair for future growth.
 6. オペレーションカウンタをインクリメントします。 
7. どちらかの値が大きくなった場合`n`、カウンターを停止して出力します。 

### なぜ効果があるのか

 あらゆるステップで、`x`小さい方の値になり、`y`より大きな値になります。 

考えられる次の 2 つの状態は次のとおりです。`(x + y, y)`そして`(x, x + y)`。 

どちらも同じ新しい最大値を作成します。`x + y`。 差額が残額となります。 そのままにしておきます`y`常に少なくともそれを維持するのと同じくらい良いです`x`、 なぜなら`y ≥ x`。 

したがって、1 回の操作の後、小さい方の値を更新すると、2 つの数値が両方とも代替状態の対応する数値と少なくとも同じ大きさの状態が生成されます。 将来の操作にはこれらの値の加算のみが含まれるため、コンポーネントごとに大きな状態から開始しても、これを超える操作を必要とすることはできません。`n`。 

したがって、各ステップでより小さい値を更新する最適な解決策が常に存在し、これがまさにアルゴリズムの動作です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    
    for _ in range(t):
        a, b, n = map(int, input().split())
        
        ops = 0
        
        while max(a, b) <= n:
            if a < b:
                a += b
            else:
                b += a
            ops += 1
        
        print(ops)

solve()
```両方の数値がまだ十分大きくない間、ループは継続します。 使用する`max(a, b) <= n`どちらの値も超過しないと言うのと同じです`n`。 

貪欲なステップは常に小さい値を更新します。 これがソリューションの中心となるアイデアです。 更新のたびに、操作カウンターが増加します。 

Python の整数には任意の精度があるため、値が一時的に次の値よりも大きくなることがあっても、オーバーフローの心配はありません。`10^9`。 

よくある間違いは、値が次の値に等しくなったときに停止することです。`n`。 この問題では、値が以下より_厳密に大きい_必要があります。`n`したがって、条件は次のようになります。`<= n`ループの中。

## テストケース```python
# helper: run solution on input string, return output string
import sys
import io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    input = sys.stdin.readline

    t = int(input())
    ans = []

    for _ in range(t):
        a, b, n = map(int, input().split())

        ops = 0
        while max(a, b) <= n:
            if a < b:
                a += b
            else:
                b += a
            ops += 1

        ans.append(str(ops))

    return "\n".join(ans)

# provided sample

assert run("1\n1 2 2\n") == "1", "exceed immediately"
