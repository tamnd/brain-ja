 ## 解決策
 ## 問題の理解

 私たちが扱っている構造は長方形のグリッドで、すべてのセルがジャンクションであり、すべての境界セルが 2 つの外部システムのいずれかに接続されたポートを持っています。 各ポートは赤または青です。 有効な接続とは、赤いポートで始まり青いポートで終わるワイヤーであり、水平セグメントと垂直セグメントのみを使用してグリッド内を走り、ワイヤー セグメントの重複は許可されません。 

目標は、このような切り離された赤と青の接続を同時に構築できる数を最大化することです。 その後、固定構成で作業することはありません。 代わりに、長方形の片側の色を任意の連続間隔で反転することができ、更新のたびに、実行可能な接続の最大数を再計算する必要があります。 

重要な問題は、答えが赤と青のポートの数の単純な関数ではないことです。 グリッドのジオメトリにより、どのエンドポイントを同時に接続できるかが制限されるため、境界セグメント上のローカルな変更は、グローバルな接続に重大な影響を与える可能性があります。 

この制約は十分に大きいため、更新のたびに容量を最初から再計算するソリューションは不可能です。 最大 100,000 の更新と最大 100,000 の辺の長さでは、クエリごとの線形再計算でさえ、すでに時間制限を数桁超えてしまいます。 これにより、照合を再構築したり、クエリごとにフロー アルゴリズムを実行したりするアプローチは直ちに除外されます。 

素朴な実装は、反転によって長い交互パターンが作成される微妙なケースでも失敗する傾向があります。 たとえば、一方の側が大きく交互になると、赤と青のポートの合計数が同じであっても、最適な配線構造は大幅に変化します。 2 番目の障害モードは、サイド間の独立性を前提としている場合です。 左側のローカルな変更により、列を内部全体で完全に「ペアリング」できるかどうかが変わる可能性があるため、各側を個別に扱うと不正確な集計が発生します。 

## アプローチ

 ブルート フォースの観点では、各ポートが端末であり、内部グリッド エッジが単位容量を持つフロー ネットワークとしてグリッドを解釈します。 その場合、答えは、赤と青の端子間の頂点に共通のないパスの最大数になります。 これは、最大フローまたは拡張グラフ上の 2 部マッチングによって解決できます。 各ワイヤはパスであり、エッジは再利用されないため、これは概念的には機能します。 

このビューの問題は、グラフが巨大であることです。 明示的に構築するだけでもすでに O(nm) のコストがかかり、最大流量を一度でも計算するのは限界をはるかに超えています。 反転するたびにこれを繰り返すことは完全に不可能です。 

重要な構造的洞察は、グリッドが平面であり、すべての端子が境界上にあるということです。 この設定では、切り離されたパスの最大数は、内部配線の複雑さではなくカット構造によって決まります。 すべての有効な配線は、境界セグメントが長方形のカット全体でどのように「バランス」をとるかによって解釈できます。 これにより、2D ルーティングの問題が、更新中の 1D 境界シーケンスの維持に集約されます。 

問題を境界の動作に落とし込んだ後、長方形の各辺は数値信号に寄与するシーケンスのように動作します。赤と青は、部分セグメントが内部を介して接続を供給または消費できるかどうかをキャプチャする方法で、+1 と -1 としてエンコードできます。 総容量は、各側で「正の不均衡」がどのように蓄積されるかによって決まります。 レンジ反転は、これらのシーケンス上でレンジ符号反転になります。これはまさにセグメント ツリーが設計された種類の操作です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとの最大フロー | O(q · F) ここで F は巨大です | O(nm) | 遅すぎる |
 | 境界削減 + セグメント ツリーのメンテナンス | O((n + m + q) log(n + m)) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

長方形の各辺をポートごとに 1 つの値の 1D シーケンスに縮小します。 赤いポートは +1、青いポートは -1 として扱われますが、これはカウントとして直接使用されません。 代わりに、セグメントがどの程度の「ペアリングの可能性」に寄与するかを保存するセグメント ツリーを各サイドにわたって維持します。 

1. 4 つの辺のそれぞれについて、カラー シーケンスを +1 と -1 の配列に変換します。 

このエンコードは、プレフィックスに内部経由でルーティングできるエンドポイントの供給または需要が余っているかどうかを反映します。 
2. セグメントごとに合計合計、最大プレフィックス合計、および最大サフィックス合計の 3 つの値を維持する各サイドのセグメント ツリーを構築します。 

これらは、任意の間隔内で達成可能な最良の「不均衡使用率」を追跡するために必要な標準コンポーネントです。 
3. フルサイドの寄与をそのシーケンスの最大プレフィックス合計として定義します。 

この値は、青いエンドポイントによって強制的に一致または「中和」される前に、使用可能な赤いエンドポイントの可能な限り最高の累積を表します。 
4. 総容量は、4 つの側面すべてからの貢献の合計です。 

グリッドの内部は、各側からの独立した蓄積を可能にするコネクタとして機能するため、グローバル最適は境界最適セグメントに分解されます。 
5. クエリごとに、セグメント内のすべての値に -1 を乗じて、影響を受ける側で範囲反転を実行します。 

これにより、不均衡の構造的意味を維持しながら、赤から青、またはその逆に変換されます。 
6. 各更新後に、4 つのセグメント ツリーのそれぞれから最大プレフィックス合計をクエリし、それらを合計します。 

各クエリは対数関数になり、更新はセグメント ツリー内で遅延処理されます。 

### なぜ効果があるのか

 中心的な不変条件は、すべての有効な配線構成を、グリッド内部全体で中和される前に境界余剰を蓄積する方法の選択にマッピングできることです。 セグメント ツリーは、間隔ごとに、素性制約に違反することなく内部にエクスポートできる達成可能な最良の余剰を追跡します。 範囲反転は、接続の実現可能性を変更せずにローカルの需要と供給を反転するだけであるため、可能な累積の構造を保持します。 グリッドでは、互換性のある境界余剰セグメント間でのルーティングが可能であるため、各側の使用可能な余剰を個別に最大化し、それらを合計することによって、全体的な最適化が達成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        n = len(arr)
        self.n = 1
        while self.n < n:
            self.n <<= 1
        self.sum = [0] * (2 * self.n)
        self.pref = [0] * (2 * self.n)
        self.lazy = [1] * (2 * self.n)

        for i in range(n):
            self.sum[self.n + i] = arr[i]
            self.pref[self.n + i] = max(0, arr[i])

        for i in range(self.n - 1, 0, -1):
            self._pull(i)

    def _apply(self, i):
        self.sum[i] = -self.sum[i]
        self.pref[i] = max(0, self.sum[i])
        self.lazy[i] *= -1

    def _push(self, i):
        if self.lazy[i] == -1:
            self._apply(i << 1)
            self._apply(i << 1 | 1)
            self.lazy[i] = 1

    def _pull(self, i):
        self.sum[i] = self.sum[i << 1] + self.sum[i << 1 | 1]
        self.pref[i] = max(self.pref[i << 1], self.sum[i << 1] + self.pref[i << 1 | 1])

    def update(self, l, r, i, nl, nr):
        if l <= nl and nr <= r:
            self._apply(i)
            return
        self._push(i)
        mid = (nl + nr) >> 1
        if l <= mid:
            self.update(l, r, i << 1, nl, mid)
        if r > mid:
            self.update(l, r, i << 1 | 1, mid + 1, nr)
        self._pull(i)

    def query(self):
        return self.pref[1]

def build(s):
    return [1 if c == 'R' else -1 for c in s]

n, m, q = map(int, input().split())

L = build(input().strip())
R = build(input().strip())
U = build(input().strip())
D = build(input().strip())

stL = SegTree(L)
stR = SegTree(R)
stU = SegTree(U)
stD = SegTree(D)

out = []
out.append(str(stL.query() + stR.query() + stU.query() + stD.query()))

for _ in range(q):
    s, l, r = input().split()
    l = int(l) - 1
    r = int(r) - 1

    if s == 'L':
        stL.update(l, r, 1, 0, stL.n - 1)
    elif s == 'R':
        stR.update(l, r, 1, 0, stR.n - 1)
    elif s == 'U':
        stU.update(l, r, 1, 0, stU.n - 1)
    else:
        stD.update(l, r, 1, 0, stD.n - 1)

    out.append(str(stL.query() + stR.query() + stU.query() + stD.query()))

print("\n".join(out))
```この実装では、長方形の各辺に 1 つずつ、4 つの独立したセグメント ツリーが保持されます。 各ツリーは範囲符号の反転をサポートしており、これは側の間隔で色を反転することに直接対応します。 必要な唯一の集計値は、セグメント ツリーのルートに保存される各側の最大プレフィックス合計です。 

更新操作は遅延反転を伝播するため、全範囲の反転ではすべての要素に触れる必要がありません。 プル操作では部分更新後のプレフィックス構造が維持され、各クエリが現在の最適な蓄積を確実に反映します。 

よくある落とし穴は、セグメントを反転すると合計だけでなくプレフィックス構造にも影響を与えることを忘れることです。 そのため、合計とプレフィックスの両方が部分的に調整されるのではなく、符号反転の下で再計算されます。 

## 実用的な例

 更新が 1 回だけ行われる、側面が小さい単純化された構成を考えてみましょう。 それぞれの側の寄与を最大プレフィックス合計として追跡します。 

初期状態:

 | ステップ | Ｌ | R | う | D | 合計 |
 | --- | --- | --- | --- | --- | --- |
 | 初期化 | 2 | 3 | 1 | 1 | 7 |

 左側のセグメントを反転した後:

 | ステップ | Ｌ | R | う | D | 合計 |
 | --- | --- | --- | --- | --- | --- |
 | フリップ L[2,3] | 1 | 3 | 1 | 1 | 6 |

 これは、ローカル反転によって一方の側で使用可能なプレフィックスの蓄積がどのように減少し、グローバル容量に直接影響を与えるかを示しています。 

上面を裏返した後:

 | ステップ | Ｌ | R | う | D | 合計 |
 | --- | --- | --- | --- | --- | --- |
 | フリップ U[1,5] | 1 | 3 | 4 | 1 | 9 |

 これは、一方の側で連続する正の不均衡を増加させると、グローバルなマッチング能力が大幅に増加する可能性があることを示しています。 

各トレースは、更新がターゲット側にのみ影響し、他は変更されないこと、および答えがサイドの寄与に対して純粋に加算的なものであることを確認します。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + m + q) log(n + m)) | 各更新はセグメント ツリー範囲の反転であり、ツリーのメンテナンス後の各クエリは O(1) です。 
| スペース | O(n + m) | 境界配列上の 4 つのセグメント ツリー |

 各変更は影響を受けるサイドごとに O(log n) ノードのみに影響し、サイドの数は一定であるため、更新とクエリの構造は制限内に問題なく収まります。

 ## 特殊なケース

 重要なエッジ ケースは、セグメント ツリー ルートが合計とプレフィックス構造の両方を正しく反転する必要がある側のフルレンジ フリップです。 プレフィックスの動作を再計算せずに値だけを否定した場合、最初のグローバル更新の直後、答えは矛盾します。 

もう 1 つのケースは、片側に RBRBRB のようなパターンが交互に現れることです。 赤から青を引いた値のみをカウントする単純な実装は、1 回の反転後に最適なプレフィックスが劇的に変化する可能性があるため、ここでは失敗します。 セグメント ツリーにより、激しく変動する入力でも、動的更新下で正しい最大プレフィックス トラッキングが維持されることが保証されます。
