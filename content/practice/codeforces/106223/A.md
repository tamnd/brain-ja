 ## 問題の理解

 いくつかの野菜があります。 野菜`i`大量に生産する必要がある`A_i`、現在 1 つのユニットを生産すると消費されます`B_i`水の単位。 必要な水の合計は次の合計です。`A_i * B_i`野菜全般に。 

アップグレードにより、一部の機能が低下する可能性があります`A_i`1 つ増えるということは、町が必要とするその野菜の単位が 1 つ減るか、またはいくらか減るということです。`B_i`つまり、その野菜の残りの単位ごとに必要な水の単位が 1 単位減ります。 すべてのクエリについて、最大で次のことを実行できます。`X`アップグレードに必要な最終的な水の消費量を可能な限り最小限に抑える必要があります。 

重要なのは、すべての操作が現在の 1 つの野菜の生産物を減らすことです。 減らしたら`A_i`、当面の改善が現状です。`B_i`。 減らしたら`B_i`、当面の改善が現状です。`A_i`。 課題は、水を最大限に除去するアップグレードを選択することです。 

制限には慎重なアプローチが必要です。 の値`A_i`そして`B_i`サイズが大きくなる可能性があるため、考えられるすべてのアップグレードをシミュレートすることは不可能です。 野菜には数百万以上の削減の可能性があり、有用な操作の総数は、すべての操作に対する線形シミュレーションで処理できる数をはるかに超える場合があります。 クエリが多い場合は、回答の構造を前処理する必要があります。 

難しいのは、削減が役に立たなくなる時期を理解し、更新の繰り返しを回避することです。 

ある野菜を考えてみましょう`A = 3`そして`B = 5`。 その最初の貢献は、`15`。 減らしたら`A`3回繰り返すと水が減ります`5`、 それから`5`、 それから`5`、ゼロに達します。 減らす`B`代わりに、その後の利益は小さくなります`A`変更されました。 操作を 1 つずつ貪欲に混合する不注意な実装は、小規模な場合にはまだ正しいかもしれませんが、非常に遅くなります。 

もう 1 つの特殊なケースは、一方の側がもう一方の側よりもはるかに大きい場合です。 例えば：```
Input:

1000000
1

999999000000
```すべての個別のゲインを作成しようとするソリューションでは、200 万の値を保存する必要がありますが、これは不必要であり、より大きな制約の下では失敗する可能性があります。

## アプローチ

 直接的なアプローチは、アップグレードを貪欲にシミュレートすることです。 各ステップで、すべての野菜を確認し、現在最も水を節約できる操作を選択し、それを適用して続行します。 これは正しいです。なぜなら、すべての操作には明確な即時利益があり、常に可能な限り最大の削減を望んでいるからです。 

問題は操作回数です。 野菜がある場合`A_i = 10^6`、すでに 100 万件の有用なアップグレードに貢献できます。 多くの野菜では、シミュレーション操作の数が膨大になる可能性があります。 最適な操作の探索を繰り返すと、状況はさらに悪化し、周囲にまで到達します。`O(total upgrades * N)`時間。 

問題を変える観察は、野菜には複雑な一連の利益がないということです。 付け合わせの野菜の場合`A_i`そして`B_i`、最善の戦略は、小さい側を完全に削除することです。 小さい側は必要なアップグレードの数を示し、それらのアップグレードのそれぞれが大きい側を正確に節約します。 

もし`A_i <= B_i`、減らすことができます`A_i`その通り`A_i`回、すべての操作が保存されます`B_i`。 その後、野菜の貢献はゼロになります。 同じ推論が機能するのは次の場合です。`B_i <= A_i`。 

したがって、それぞれの野菜は同一の値のグループになります。 グループには以下が含まれます`min(A_i, B_i)`アップグレード、それぞれの価値`max(A_i, B_i)`水。 現在の世界的な問題は、これらのグループの中で最大の値を取ることです。 

各グループ内の値は等しいため、それらを展開する必要はありません。 値によってグループを並べ替え、プレフィックス数とプレフィックス合計を保存し、二分検索で各クエリに答えます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(アップグレードの合計 * N) | O(N) | 遅すぎる |
 | 最適 | O(N log N + Q log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 初期水消費量を以下の合計として計算します。`A_i * B_i`。 すべての野菜について、値を含む圧縮グループを作成します`max(A_i, B_i)`そしてサイズ`min(A_i, B_i)`。 サイズは、その値のアップグレードが何回存在するかを表します。 

圧縮が機能するのは、長方形の領域を削除するための最良の方法だからです。`A_i * B_i`小さい次元から行または列を削除することです。 

1. すべてのグループを値の降順に並べ替えます。 より大きな節約を常に最初に使用する必要があるため、最適なシーケンスはこの順序のプレフィックスになります。 
2. プレフィックス配列を構築します。 各グループの後にカバーされたアップグレードの数と、それらすべてのグループを受講した後に節約された水の合計を保存します。 

これらのプレフィックスを使用すると、クエリでアップグレードを 1 つずつ処理するのではなく、グループ全体をスキップできます。 

1. お問い合わせの場合`X`、累積アップグレード数が到達するか超える最初のグループを見つけます。`X`。 

その前にある完全なグループをすべて取得します。 現在のグループ内にアップグレードが残っている場合は、残りの量にそのグループの値を掛けます。 

1. 初期の水使用量から最大節約水を差し引きます。 その結果、最終的な水の必要量は可能な限り最小限になります。 

それが機能する理由: すべての野菜は、その大きい面に等しい同一のアップグレード値のコレクションに貢献します。 最適な解決策は、単にグローバルで利用可能な最大のアップグレード値を採用することです。 圧縮されたグループを並べ替えると、正確にそれらの値が最初に配置され、プレフィックスの計算により、クエリに対して可能な限り最適な節約水量が見つかります。 

## Python ソリューション```python
import sys
from bisect import bisect_left

input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    groups = []
    total = 0

    for x, y in zip(a, b):
        total += x * y
        groups.append((max(x, y), min(x, y)))

    groups.sort(reverse=True)

    counts = []
    sums = []
    cur_count = 0
    cur_sum = 0

    for value, cnt in groups:
        cur_count += cnt
        cur_sum += value * cnt
        counts.append(cur_count)
        sums.append(cur_sum)

    ans = []

    for _ in range(q):
        x = int(input())
        if x == 0:
            ans.append(str(total))
            continue

        idx = bisect_left(counts, x)

        if idx == 0:
            saved = x * groups[0][0]
        else:
            saved = sums[idx - 1]
            used = counts[idx - 1]
            saved += (x - used) * groups[idx][0]

        ans.append(str(total - saved))

    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```各野菜は圧縮グループを形成する前に両方の値を必要とするため、入力配列が最初に読み取られます。 最初の答えは乗算を使用して累積されるため、Python 整数は自然に大きな積を処理します。 

グループの作成は、実装の中心的な詳細です。 保管します`(larger side, smaller side)`大きい側はすべての有用なアップグレードの値であり、小さい側はアップグレードが存在する回数であるためです。 

並べ替えた後、`counts`各ポジションまでに含まれるアップグレードの数を保存します。`sums`対応する総削減量を格納します。 二分探索では、答えの位置を含む最初のグループが見つかります。 そのグループの前のすべては完全に取得され、現在のグループは部分的に取得される可能性があります。 

Python の整数は自動的に増加するため、オーバーフローや特殊な整数サイズを処理する必要はありません。 重要な境界は、クエリが有効なアップグレードの合計数より大きい場合です。これは、最後のグループが見つかり、追加の量は合計をゼロにする以外には何も寄与しないため処理されます。

## テストケース```python
import sys
import io
from bisect import bisect_left

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    n, q = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    groups = []
    total = 0

    for x, y in zip(a, b):
        total += x * y
        groups.append((max(x, y), min(x, y)))

    groups.sort(reverse=True)

    counts = []
    sums = []
    c = 0
    s = 0

    for v, cnt in groups:
        c += cnt
        s += v * cnt
        counts.append(c)
        sums.append(s)

    out = []

    for _ in range(q):
        x = int(input())
        idx = bisect_left(counts, x)
        if idx == 0:
            saved = x * groups[0][0]
        else:
            saved = sums[idx - 1]
            saved += (x - counts[idx - 1]) * groups[idx][0]
        out.append(str(total - saved))

    return "\n".join(out)

 ## 特殊なケース

 巨大な野菜の場合は圧縮で対応します。 のために`1000000 x 1000000`野菜、アルゴリズムは値を持つ 1 つのグループを保存します`1000000`そして数えます`1000000`。 1 つのアップグレードを要求するクエリは、そのグループを直接見つけて減算します。`1000000`初期製品から。 

アップグレードが有効な操作の合計を超える場合も、自然に処理されます。 プレフィックス数が可能な削減の総数に達し、最終的な水の値はゼロになります。 追加のアップグレードによって水の消費量がマイナスになることはないため、答えはゼロのままです。 

複数の野菜の最高価値が同じ場合、並べ替えることでそれらをまとめておくことができます。 二分探索は、これらの等しいグループのいずれか 1 つ内で停止する可能性がありますが、結合されたグループ内のすべての操作には同じ利点があるため、結果は変わりません。
