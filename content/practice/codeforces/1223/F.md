 ## 解決策
 ## 問題の理解

 配列と、消滅を伴うスタックのように動作する独特のキャンセルプロセスが与えられています。 スタックを維持しながら、配列を左から右にスキャンします。 値を確認したときに、スタックトップが異なる場合は、それをプッシュします。 同じ場合は、新しい要素をプッシュする代わりに上部を削除します。 したがって、等しい隣接する「相互作用」はペアを排除します。 

このようにすべての要素を処理した後、スタックが空になった場合、完全な配列は良好であると呼ばれます。 タスクは、指定された配列のうち、このプロセスで適切なサブ配列がいくつあるかを数えることです。 

各クエリは独立しており、すべてのクエリにわたる合計入力サイズは十分に大きいため、すべての部分配列に対する二次アプローチは不可能です。 

直接解釈するだけでも、その難しさを理解するのに十分です。すべてのサブ配列で、両方向にキャンセルできるスタック プロセスをシミュレートする必要があり、キャンセルはローカル構造だけでなく、進化する履歴に依存します。 

主な制約の意味は、全長が 3e5 までであることです。 どのような解も、テストごとに線形に近いか、最悪の場合でも対数線形に近いものでなければなりません。 サブ配列の列挙とシミュレーションは O(n^2) 個のサブ配列であり、それぞれが O(n) になる可能性があり、これは完全に実行不可能です。 

さらに微妙な問題は、キャンセルが単調ではないことです。 サブ配列を拡張すると、キャンセル パターンが作成されることも破棄されることもあるため、隣接する 2 つのサブ配列は独立していません。 

素朴な直感を打ち破るエッジケースには、次のようなものがあります。 

のような配列`[1, 2, 3, 2, 1]`ここでは直接の重複は存在しませんが、キャンセルは隣接関係ではなく深いペアリング構造に依存します。 

別の例は、次のような交互構造です。`[1, 2, 1, 2, 1, 2]`ここで、スタック状態が安定せずに振動するため、単純な「ペアカウント」は失敗します。 

最後に、次のような均一な配列`[x, x, x, x]`は一見単純です。ペアで完全にキャンセルされますが、それは長さが偶数の場合に限られます。 

これらのパターンは重要な難しさを示しています。スタック プロセスは、局所的な削除だけでなく、動的削減後に隣接する等しいブロックを繰り返しキャンセルすることに相当します。 

## アプローチ

 ブルートフォースの解決策は簡単です。 各サブ配列について、説明どおりにスタック プロセスを正確にシミュレートします。 各要素は前の先頭をプッシュまたはキャンセルするため、各シミュレーションは部分配列の長さが線形になります。 O(n^2) 個のサブ配列の場合、最悪の場合は O(n^3) になり、サブ配列の開始ごとに慎重に最適化した場合は O(n^2) になります。 これは、3e5 までの n にとっては遅すぎます。 

重要な観察は、スタック プロセスが隣接する等しいペアを繰り返し削除するように動作することですが、重要なのは、それが単に配列内の隣接する削除ではないということです。 代わりに、これは現在の縮小形式に依存する縮小プロセスです。 重要な構造的洞察は、すべての配列がこのキャンセル プロセスによって得られる標準的な「縮小スタック形式」を持ち、これらの縮小形式がどのように相互作用するかによってセグメントの連結を分析できるということです。 

各プレフィックスをその縮小されたスタック状態で表す場合、セグメントの拡張はスタック状態間の遷移を適用することに対応します。 重要な特性は、スタック状態が常に隣接する値が異なるシーケンスであり、最後の値のみをプッシュまたはポップすることによって展開されることです。 

これにより、分割統治スタイルのアイデアが可能になります。スタック状態の圧縮表現を維持しながら、中間点を固定し、外側に拡張することで有効なサブ配列をカウントします。 各プッシュ/ポップ操作では最上位のみが変更され、構造は段階的に維持できるため、拡張中に発生する個別のスタック状態の数は制限されます。 

公式ソリューションで使用されているより深いトリックは、各位置を「サフィックスが削減された状態」間の遷移に寄与するものとして扱い、これらの状態をハッシュすることで有効な一致をカウントすることです。 サブ配列の 2 つの半分が完全にキャンセルされる場合、それらの縮小形式は相互に互換性のある逆変換でなければならず、これはエンコードされたスタック状態を比較することで検出できます。 

したがって、すべてのサブ配列をシミュレートする代わりに、考えられる削減されたスタック シグネチャを列挙し、ハッシュと 2 ポインタまたは分割統治の計数戦略を使用して相補的なものを照合します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | テストごとに O(n^2) 以上 | O(n) | 遅すぎる |
 | 最適 (状態 + ハッシュ + 分割統治) | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. プレフィックスのスタック プロセスのローリング表現を事前計算し、最終スタックだけでなくその構造全体のハッシュを維持します。 プッシュまたはポップするたびに、現在のスタック シーケンスを表すローリング ハッシュが更新されます。 これにより、O(1) のスタック状態間の等価性チェックが可能になります。 
2. すべての位置について、そこで終わるプレフィックスを処理した後、削減されたスタックを計算します。 スタックの内容とそのハッシュ署名の両方を保存します。 これにより、サフィックスの動作を間接的に比較する方法が得られます。 
3. サブ配列が存在することを確認します。`[l, r]`は、空のスタックから処理すると空のスタックになる場合にのみ有効です。 これは、処理後にスタックが削減されたと言うのと同じです。`[l, r]`は空です。 
4. 最初から再計算するのではなく、処理を解釈します。`[l, r]`プレフィックスの削減されたスタックから開始する`l-1`そして要素を適用します`l..r`。 部分配列は、最終状態が正確に空に戻ったときに有効になります。 
5. 右のエンドポイントをスイープするときに、スタック状態 (ハッシュによってエンコードされた) からその周波数までのマップを維持します。 右のエンドポイントごとに、スタックの状態を段階的に更新し、以前の左の状態が何回で完全にキャンセルできるかをカウントします。 
6. 解除条件は、プレフィックスによるスタック状態が解除されることです。`l-1`接尾辞の逆展開と正確に一致する必要があります`[l, r]`。 ハッシュを使用して、O(1) で互換性のある状態を照合します。 
7. スタック状態の動的構造を維持しながら配列を反復処理し、状態署名をキーとしたハッシュ マップを使用して一致の数を蓄積します。 

### なぜ効果があるのか

 各状態が完全にキャンセルされた後に残っているものを正確にエンコードするという意味で、スタック プロセスは決定論的で可逆的です。 空になるサブ配列は、プレフィックス状態の完全な反転を表す必要があります。 各中間スタックをハッシュとしてエンコードすると状態の同一性が保持され、遷移は最上位のみを変更するため、同一のハッシュは同一のスタック構成を意味します。 これにより、部分配列の有効性をチェックする問題が、変換された状態空間内の等しい状態のペアを数えることに軽減され、頻度の累積によって処理されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    # stack of (value, hash of prefix-stack)
    st = []
    
    # rolling hash parameters
    MOD = (1 << 61) - 1
    BASE = 91138233

    def mul(a, b):
        return (a * b) % MOD

    def add(a, b):
        return (a + b) % MOD

    # hash of empty stack
    empty_hash = 0

    freq = {empty_hash: 1}
    cur_hash = 0
    ans = 0

    # we simulate the cancellation process but track prefix states
    for x in a:
        if st and st[-1][0] == x:
            # pop
            st.pop()
            if st:
                cur_hash = st[-1][1]
            else:
                cur_hash = 0
        else:
            # push
            prev_hash = cur_hash
            cur_hash = (prev_hash * BASE + x) % MOD
            st.append((x, cur_hash))

        # count occurrences of this state
        ans += freq.get(cur_hash, 0)
        freq[cur_hash] = freq.get(cur_hash, 0) + 1

    print(ans)

if __name__ == "__main__":
    solve()
```このコードは、現在の縮小スタックをローリング ハッシュのシーケンスとして維持します。 各プッシュは値を追加してハッシュを更新し、各ポップはスタックに保存されている以前のハッシュを復元します。 これにより、プレフィックス状態の正確な縮小表現が常に確保されます。 

頻度マップは、各スタック状態が出現する頻度をカウントします。 状態を再訪するときは常に、縮小されたスタックが現在のものと一致する以前のプレフィックスが存在することを意味し、それらの間の部分配列が完全にキャンセルされることを意味します。 

微妙な部分は、ポップ後にハッシュを再計算するのではなく、すべてのスタック深度でハッシュを保存することです。これにより、操作ごとに O(1) の正確さが維持されます。

 ## 特殊なケース

 次のような単一の繰り返し値配列`[x, x, x, x]`は、キャンセルがペアリングの順序に依存することを示しています。 空のスタック状態のハッシュの等価性を介して、空の状態への同一の戻りがそれぞれカウントされるため、アルゴリズムはこれを処理します。 

次のような交互配列`[1,2,1,2]`は、スタック状態が完全にキャンセルされずに中間構成に戻ることができることを示しています。 周波数マップにより、完全なスタック一致のみが寄与することが保証されます。 

厳密に増加する配列では、最初の数ステップ後に一致するスタック状態が生成されることはありません。そのため、答えはゼロのままであり、すべてのハッシュが個別のままであるため、正しくキャプチャされます。
