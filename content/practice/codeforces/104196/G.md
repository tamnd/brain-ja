 ## 解決策
 ## 問題の理解

 次の形式で文字列として記述された 3 つの整数を含む 1 つの算術式が与えられます。$x + y = z$または$x \times y = z$。 私たちが受け取った表現は意図的に間違っていますが、これは特定の種類の間違いによって生成されました。誰かが 3 つの数値のうち 2 つを取得し、それぞれを空ではないプレフィックスとサフィックスに分割し、それら 2 つの数値の間でプレフィックスのみを交換しました。 接尾辞はそのまま残ります。 

したがって、次のような 2 つの数値を取ると、`x = AB`そして`y = CD`、次のように分割点を選択します。`x = A|B`そして`y = C|D`、次にそれらを次のように変換します。`C|B`そして`A|D`。 3 番目の数字は変更されません。 3 つの数値のうち 1 つのペアに対してこのような演算を 1 回だけ実行すると、式は正しい方程式になります。 

タスクは、元の正しい方程式を復元することです。 保証によれば、方程式を真にする数値とプレフィックス分割点のペアを選択する有効な方法が 1 つだけ存在します。 

入力サイズが十分小さいため、各数値は以下になります。$2^{31}$、つまり、1 つの番号につき最大でも約 10 桁ということになります。 これにより、高度な最適化の必要性が即座に排除されます。 総検索スペースは約$10 \times 10 \times 3$数値のペアごとに可能性があり、3 つのペアだけが存在します。 

微妙な点は、スワップされた結果によって中間文字列の先頭にゼロが導入される可能性があることですが、それらは解析時には依然として有効な整数です。 したがって、文字列を生の数字シーケンスとして扱い、検証時にのみ整数として解釈する必要があります。 

エッジケースは主に、プレフィックス分割の動作に起因します。 分割は適切である必要があります。つまり、空のプレフィックスや文字列全体を取得することはできません。 例えば、`"12"`次のようにのみ分割できます`"1|2"`、 ない`"|12"`または`"12|"`。 数値の長さが 1 の場合、スワップにまったく参加できないため、これは重要になります。 

もう 1 つの特殊なケースは、オペレーターに依存する正確性です。 オペランドを再配置することなく、加算と乗算の両方を与えられたとおりに正確にテストする必要があります。 

## アプローチ

 直接的なアプローチは、説明された間違いをシミュレートするためにあらゆる可能な方法を試みることです。 3 つの数値のうち 2 つを選択し、それぞれの有効な分割位置をすべて試し、接頭辞を交換し、数値を再構築し、結果の式が有効になるかどうかを確認します。 

これが機能するのは、構造が非常に制約されているためです。 許可される唯一の変換は、選択した 2 つの文字列間でプレフィックスを交換することです。 これは、ある長さの文字列のペアの場合を意味します$n$そして$m$、 がある$(n-1)(m-1)$それらを分割する可能な方法。 以来$n, m \le 10$、これはペアあたり最大約 81 回の操作です。 3ペアしかないので、作業全体はわずかです。 

強引な代替案は、各数値を 2 つの元の数値の任意の組み合わせから生じる可能性があるものとして扱い、隠された元の状態の再構築を試みることですが、順方向シミュレーション空間がすでに小さく構造化されているため、これは不要です。 

重要な点は、一度に複数の交換を考慮する必要がなく、サフィックスの交換やより複雑な再配置を考慮する必要がないことです。 この問題により、破損が単一のプレフィックス スワップに明示的に制限され、列挙が完全かつ安全になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべてのプレフィックス交換に対するブルートフォース |$O(3 \cdot n^2)$|$O(1)$| 承認済み |
 | ブルートと同じ最適 (構造化列挙) |$O(n^2)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 3 つの数値を文字列として扱い、許容されるすべての破損の回復を体系的にシミュレートします。 

1. 入力を 3 つの文字列に解析します。$x$、$y$、 そして$z$、演算子を読み取ります。 これにより、文字列形式で作業を続けることができるため、接頭辞の操作が簡単になります。 
2. 以下の順序のないペアごとに、$(x, y)$、$(x, z)$、 そして$(y, z)$、これらはプレフィックスの交換によって破損した 2 つの番号であると仮定します。 
3. 選択したペアについて、最初の文字列内のすべての有効な分割点と 2 番目の文字列内のすべての有効な分割点を繰り返します。 位置の分割ポイント$i$プレフィックスが前の部分文字列であることを意味します$i$、接尾辞は次のとおりです$i$これからも。 分割は満足する必要があります$1 \le i < \text{len}$。 
4. サフィックスを固定したままプレフィックスを交換することにより、2 つの文字列の交換バージョンを構築します。 元の文字列が$a = A + B$そして$b = C + D$、変換された文字列は次のようになります$C + B$そして$A + D$。 
5. スワップ後に完全なトリプルを再構築します。 3 番目の数字は変更されません。 
6. 3 つの文字列すべてを整数に変換し、指定された演算子の下で方程式が成り立つかどうかを確認します。 オペレーターが`+`、確認します$a + b = c$。 もしそうなら`*`、確認します$a \times b = c$。 
7. 有効な場合は、一意性が保証されているため、再構成された方程式がすぐに出力されます。 

これが機能する理由は、考えられるすべてのプレフィックス分割を列挙することによって、元の破損プロセスを正確に元に戻すことができるという事実から来ています。 すべての数値のペアとその中のすべての正当な分割点を試すため、すべての有効な変換がこの検索空間に出現する必要があります。 この列挙によって生成されずに最終的な方程式を生成できる代替構造は存在しないため、正しい構成が 1 回だけ見つかることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def parse(expr):
    parts = expr.strip().split()
    return parts[0], parts[1], parts[2], parts[3]

def check(a, op, b, c):
    if op == '+':
        return a + b == c
    else:
        return a * b == c

def try_pair(a, b, c, op):
    na, nb = len(a), len(b)

    for i in range(1, na):
        for j in range(1, nb):
            a1 = b[:j] + a[i:]
            b1 = a[:i] + b[j:]

            x = int(a1)
            y = int(b1)
            z = int(c)

            if check(x, op, y, z):
                return a1, b1, c
            if check(x, op, z, y):
                return a1, c, b1

    return None

def solve():
    expr = input().strip().split()
    x, op, y, eq, z = expr

    pairs = [
        (x, y, z),
        (x, z, y),
        (y, z, x)
    ]

    for a, b, c in pairs:
        res = try_pair(a, b, c, op)
        if res:
            A, B, C = res

            if (A, B, C) == (x, y, z):
                print(f"{A} {op} {B} = {C}")
            elif (A, C, B) == (x, y, z):
                print(f"{A} {op} {C} = {B}")
            elif (B, A, C) == (x, y, z):
                print(f"{B} {op} {A} = {C}")
            elif (B, C, A) == (x, y, z):
                print(f"{B} {op} {C} = {A}")
            return

if __name__ == "__main__":
    solve()
```コードは、最後の検証ステップまですべてを文字列形式で保持します。 これにより、必要になるまで不必要な演算が回避されます。 各ペアは独立してテストされ、各ペアについてすべてのプレフィックス分割の組み合わせが網羅されます。 

よくある落とし穴は、交換されたペアが最終方程式の 3 つの位置のうちの任意の 2 つに対応できることを忘れていることです。そのため、実装では、3 番目の触れられていない数値のすべての配置に対する一貫性が明示的にテストされます。

トレースは、プレフィックス カットの 1 つの組み合わせのみが、一意性の保証に一致する一貫した算術同一性を生成することを示しています。 

次に、加算スタイルの例を考えてみましょう。

これらの例は、ヒューリスティックなガイダンスを必要とせず、純粋にプレフィックス分割を列挙することによって正確さが達成されることを示しています。

 ## 特殊なケース

 重要なエッジ ケースは、1 つの数値の長さが 1 である場合です。その状況では、有効なプレフィックス分割が存在しないため、その数値はスワップに参加できません。 分割点をめぐるループは 1 から始まり、長さから 1 を引いたところで終了し、反復が生成されないため、アルゴリズムはこれを自然に処理します。 

たとえば、次のように考えてみましょう`5 + 12 = 17`。 私たちが関与しようとすると`5`スワップでは有効な分割がないため、ペアは何も寄与しません。 その後、アルゴリズムは、次の要素が含まれるペアのみを考慮します。`(12, 17)`またはその他、正確性を保証します。 

もう 1 つのケースは、スワップによって先行ゼロが導入される場合です。 たとえば、プレフィックスを交換すると、`"103"`そして`"45"`生産できる`"403"`そして`"15"`。 これらは変換ルールの下では依然として有効な整数であるため、整数チェックは正しいままです。 

最後の微妙なケースは、どの再構築された数値が方程式内のどの位置に対応するかを正しく割り当てることを保証することです。 スワップされたペアはどちらの順序でも着地する可能性があるため、検証中に両方の方向を明示的にテストします。 これにより、演算は正しいがオペランドの配置が間違っているというサイレントな不一致が防止されます。
