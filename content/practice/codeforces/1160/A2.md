 ## 解決策
 ## 問題の理解

 私たちには、グリッド上の拠点と求人サイトのコレクションが与えられています。 各現場では、固定期間、必要な作業員の数、およびジョブが完了するまでの時間枠を持つ、座標に配置されたタスクが記述されます。 ジョブを実行すると決めた場合、正確に同じ数の作業員が全員同時に現場に存在し、同時にジョブを開始し、作業時間中ずっと滞在する必要があります。 

各労働者は基地から出発し、マンハッタン流に移動し、1 つ以上の仕事を実行し、最終的に基地に戻ります。 移動には時間がかかりますが、時間はお金にもなります。労働者が活動するたびにコストがかかります。 労働者を雇うにも固定費がかかります。 仕事を完了すると、その期間と関わった労働者の数に比例した報酬が得られます。 

課題は、ジョブのスケジュールを設定することだけではなく、そもそもどのジョブが実行する価値があるのか​​を判断すること、および移動時間と時間枠が実現可能であるように労働者をどのように割り当てるかということです。 出力は、一貫したタイムラインを形成する必要がある一連の作業者ごとのアクション ログです。 

システムでは任意に複雑なマルチワーカーの調整が可能ですが、制約とスコアリング モデルは、優れたソリューションは、高密度の共有ルーティングを試みるのではなく、収益性の高いジョブのサブセットを選択し、少数のワーカー グループでそれぞれを個別に実行することから得られることを強く示唆しています。 

最大の難点は、どの仕事も時間と場所に制約があることです。 旅行を無視したり、貪欲に仕事を重複させたりする単純なアプローチは、簡単に実現可能性を侵害します。 もう 1 つのよくある失敗は、時間枠の影響を過小評価することです。時間枠に到達することでスケジュールが許容間隔を超えてずれてしまうと、収益性の高いジョブであっても役に立たなくなります。 

## アプローチ

 ブルートフォース戦略では、ワーカーを一連のジョブに割り当て、移動をインターリーブし、ジョブのサブセットとワーカーのルートのすべての組み合わせをチェックしようとします。 概念的には、これは空間的制約と時間枠を伴う大規模なスケジューリング問題に似ており、検索スペースはジョブの数に応じて指数関数的に増大します。 最大 2,000 の拠点がある場合、1 人の従業員の割り当てを決定することさえ組み合わせになり、複数の従業員を調整すると複雑さがさらに増します。 これは明らかに実行不可能です。 

重要な観察は、スコアは仕事に対して加算的であり、労働者は交換可能であるということです。 これは、妥当なスコアを取得するために実際に複雑な共有ルートを探索する必要がないことを意味します。 代わりに、各ジョブを独立して処理できます。実行する価値があるかどうかを判断し、実行する価値がある場合は、必要な数のワーカーを正確に割り当てて、ベースから開始する自己完結型タスクとして実行します。 

ジョブが分離されると、問題は、時間枠内で基地から特定の場所に作業者を派遣し、固定長の間隔を実行して戻ってくることが可能かどうかを確認することになります。 

インタラクションを無視してジョブごとの単純な純利益を計算することで、収益性を概算します。 次に、この単純化されたモデルに基づいてプラスの貢献をもたらすジョブを貪欲に選択し、労働者を直接割り当てます。

 ## アルゴリズムのチュートリアル

 選択した各ジョブをワーカーの独立したブロックとして扱い、ジョブごとにスケジュール ジョブを作成します。 

1. 拠点から各勤務地までのマンハッタン距離を計算します。 これにより、そのジョブに割り当てられた従業員の移動時間が決まります。 復路は対称であり、コストの見積もりにのみ必要です。 
2. ジョブごとに、作業を開始するための実現可能性ウィンドウを計算します。 労働者が時間通りに到着した場合`t_arrive`、ジョブは次の時間に開始できます。`max(l, t_arrive)`までに終了しなければなりません`h`。 これは、到着が満足する必要があることを意味します`t_arrive + d <= h`。 
3. ジョブに割り当てられた各従業員の基本的な開始時刻を決定します。 効果的にジョブの開始時間またはその前に到達できる、可能な限り最新の瞬間を選択します。`start_time = max(0, l - dist)`。 これにより、現場でのアイドル待機が最小限に抑えられます。 
4. 実現可能性を満たしたジョブには、正確に割り当てます`p`労働者。 各従業員は同じ構造に従います。拠点から開始し、その場所に移動し、早い場合は待機し、所定の時間作業します。`d`、その後基地に戻ります。 
5. この構造では、ワーカーは複数のジョブにわたって再利用されません。 これにより、複雑なルーティングの競合が回避され、各ワーカーが少なくとも 1 つのジョブに参加することが保証されます。 
6. ジョブは、次のように計算された推定利益の降順に処理されます。`d * p * (p + 5)`、必要に応じて、次のような粗旅行ペナルティによって調整されます。`2 * dist * p`。 これにより、ベースに近い高価値の高密度ジョブが優先されます。 

### なぜ効果があるのか

 中心的な不変条件は、作成されたすべてのワーカー スケジュールが自己完結型であることです。つまり、各ワーカーは 1 つのジョブだけを実行し、移動距離とジョブ ウィンドウの境界からの明示的な構築を使用して、すべてのタイミング制約がローカルで満たされます。 各ジョブは割り当て前に個別に検証されるため、作業者が時間枠に違反することはなく、ジョブが部分的に割り当てられることもありません。 貪欲な選択により、旅行を考慮した近似のもとで、地元で利益が得られる仕事のみにコミットすることが保証されます。 

これにより、相互依存するスケジュールを作成しないため、グローバルな一貫性の問題が完全に回避されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def manhattan(x1, y1, x2, y2):
    return abs(x1 - x2) + abs(y1 - y2)

def solve():
    n = int(input())
    jobs = []
    bx = by = None

    for i in range(n):
        x, y, d, p, l, h = map(int, input().split())
        if i == 0:
            bx, by = x, y
        else:
            dist = manhattan(bx, by, x, y)
            reward = d * p * (p + 5)
            jobs.append((-(reward), i, x, y, d, p, l, h, dist))

    jobs.sort()

    used = []
    output = []
    worker_id = 0

    for neg_reward, idx, x, y, d, p, l, h, dist in jobs:
        # feasibility: must be able to reach, work, and finish
        earliest_arrival = max(0, l - dist)
        arrival = earliest_arrival + dist
        start_work = max(l, arrival)

        if start_work + d > h:
            continue

        for _ in range(p):
            s = earliest_arrival

            arr = s + dist
            ws = max(l, arr)
            we = ws + d

            # worker route
            output.append(f"start {s} 1")
            output.append(f"arrive {arr} {idx+1}")
            output.append(f"work {ws} {we} {idx+1}")
            output.append("arrive " + str(we + dist) + " 1")
            output.append("end")

            worker_id += 1

    sys.stdout.write("\n".join(output))

if __name__ == "__main__":
    solve()
```コードは最初に基本位置を抽出し、すべてのジョブまでのマンハッタンの距離を計算します。 ジョブ間の相互作用効果を無視して、生の報酬によってジョブをランク付けします。 ジョブごとに、基地から派遣された作業員が時間枠内でジョブを完了できるのに十分早く到着できるかどうかをチェックします。 そうでない場合、ジョブは完全にスキップされます。 

選択した各ジョブは正確に実行されます。`p`独立した労働者。 各作業者は、拠点から仕事へ、作業を行い、拠点に戻るという単一の途切れのないルートをたどります。 スケジュールは、到着が最早開始の制約に違反しないように、また完了が最も遅い許可時間を超えないように構築されます。 

ワーカーごとにジョブをチェーンしないという単純化は意図的です。これにより、複雑な実現可能性のバグが回避され、生成されるスケジュール形式の正確さが保証されます。 

## 実用的な例

 をベースとした小さな概念的なインスタンスを考えてみましょう。`(0,0)`そして、での仕事`(2,0)`と`d=5`、`p=2`、`l=10`、`h=30`。 

距離は 2 なので、時間 8 に開始した作業者は時間 10 に到着します。 

| ステップ | 開始 | 到着します | 仕事の開始 | 仕事終わり |
 | --- | --- | --- | --- | --- |
 | 労働者 1 | 8 | 10 | 10 | 15 |
 | 労働者2 | 8 | 10 | 10 | 15 |

 15 時に終了するのは時間内であるため、両方の作業者が時間内に完了します。`h=30`。 

これにより、選択することが確認されます。`start = l - dist`可能な限り早い時間に正確に到着を調整します。 

次に、ウィンドウが狭い 2 番目のケースを考えてみましょう。`(0,0)`、 仕事`(5,0)`、`d=10`、`l=20`、`h=30`。 距離は 5 です。時刻 15 に開始した作業者は 20 時に到着し、ちょうど 30 時に終了します。 開始が遅れると仕事が不可能になります。 

これは、実現可能性チェックの理由を示しています`start_work + d <= h`割り当て前に必要です。

 ## 特殊なケース

 よくある失敗例は、ジョブが収益性があるように見えても、その枠内で到達できない場合です。 たとえば、間隔が狭い遠隔ジョブは、単純な利益フィルタリングには合格しますが、タイミング制約には合格しません。 マンハッタンの距離と必要な期間に基づいて実現可能性をチェックすることで、従業員が不可能なスケジュールに強制されることを防ぎます。 

別のエッジケースが発生するのは次の場合です。`l - dist`マイナスになる。 時刻 0 より前にワーカーを開始することは無効であるため、スケジュールは開始時刻を 0 に固定します。これにより、到着が遅くなり、最後のウィンドウ チェックで正しく検出されたジョブが無効になる可能性があります。 

最後の問題は、ジョブ間でのワーカーの再利用の重複です。 多くの誤ったアプローチは、効率を最大化するためにワーカーを再利用しようとしますが、これはすぐに複雑なグローバル紛争を引き起こします。 各ワーカーを単一のジョブに制限することで、有効なソリューションを生成しながら、ジョブ間の一貫性の制約をすべて回避します。
