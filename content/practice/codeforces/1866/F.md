 ## 解決策
 ## 問題の理解

 私たちはプレイヤーのグループを維持しており、各プレイヤーは攻撃的価値と防御的価値という 2 つの進化する属性によって記述されます。 時間の経過とともに、更新によって両方の属性が独立して変更される可能性があります。 いつでも、現在の値だけでなく、各プレーヤーが世界的にどのように比較されるかにも依存するランキング システムを評価する必要があります。 

ランキングの最初のレイヤーは純粋に座標に関するものです。 プレイヤーの攻撃ランクは、厳密に大きな攻撃値を持つプレイヤーが何人いるかによって決まります。 守備ランクについても同様の考え方が当てはまります。 したがって、各プレーヤーは 2 つの独立した 1 次元の順序で配置され、更新によって値が変更されるため、どちらのランキングも動的になります。 

第 2 層では、問題が興味深いものになります。 各プレイヤーには、攻撃ランクと防御ランクの合計に等しい総合スコアが割り当てられます。 クエリに対する最終的な答えは、これらの合計スコアの中での特定のプレーヤーのランクです。 

この難しさは、更新ごとに値がグローバルに変更されるため、多くのプレイヤーのすべてのランクが一度に変更される可能性があるという事実に起因します。 最大 100,000 人のプレーヤーと 100,000 のオペレーションでは、クエリごとにすべてのランクを再計算することは現実的ではありません。 

単純なアプローチでは、クエリが表示されるたびに、すべてのプレーヤーの両方のランクが再計算されます。 これにはすでにランク再計算ごとに O(N) のコストがかかり、クエリごとに再計算を行うと O(NQ) となり、制限をはるかに超えています。 

たとえば、A または B で並べ替えてローカルで更新するなど、1 つの順序のみを維持しようとすると、より微妙な失敗のケースが発生します。 RankA と RankB は独立したグローバル比較であるため、一方の配列で単調性を前提とするローカルまたは増分構造は、もう一方の次元が変化すると壊れます。 

中心的な課題は、RankA と RankB がどちらも更新中のグローバル順序統計であり、クエリでそれらの合計の順序統計が要求されることです。 

## アプローチ

 ブルート フォース手法では、比較を並べ替えたりカウントしたりすることで、クエリごとに RankA と RankB を最初から再計算します。 クエリごとに、すべてのプレーヤーをスキャンし、値を比較し、合計スコアを計算します。 これは定義に正しく準拠していますが、各クエリにはランクを再計算するためだけに線形時間がかかり、さらにクエリに答えるために別の線形スキャンが必要になります。 Q が 10^5 までの場合、最悪の場合、これはおよそ 10^10 回の演算となり、遅すぎます。 

重要な観察は、RankA と RankB は両方とも、単に「現在の値に 1 を加えた値よりも大きい要素の数」であるということです。 これは、動的マルチセットにわたるグローバル順序統計に相当します。 これは、ランクを直接再計算する代わりに、値に対する頻度構造を維持し、「x より大きいカウント」クエリをサポートしていることを示唆しています。 

ただし、依然としてすべての i に対して RankA(i) + RankB(i) が必要であり、さらに重要なことに、これらの合計間のランキングをサポートする必要があります。 重要なアイデアは、問題を 2 つの部分に分割することです。1 つは周波数に対してフェンウィック ツリーを使用して RankA と RankB を維持し、もう 1 つは合計値に対する順序統計をサポートする 2 番目の構造を使用して結合スコアの分布を維持することです。 

微妙な洞察は、A と B が変化する一方で、RankA と RankB はペアごとの関係ではなく、値のグローバルなカウントのみに依存するということです。 各更新は頻度に対する 1 つの値の寄与のみに影響するため、フェンウィック ツリーを使用すると、両方のランキングを O(log M) 時間で維持できます。 

RankA と RankB がすべてのプレイヤーに利用可能になったら、S_i = RankA(i) + RankB(i) にわたる動的構造を維持する必要があります。 更新は単一のプレイヤーの A または B にのみ影響するため、そのプレイヤーの RankA または RankB のみが変更されるため、更新ごとに S_i は 1 つだけ変更されます。 これにより、2 番目のフェンウィック ツリーまたは S 値のバランスのとれた構造を維持することができます。 

したがって、各操作は少数の対数更新になります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(NQ) | O(N) | 遅すぎる |
 | 最適 | O((N+Q) log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 A 値と B 値の 2 つの頻度構造を個別に維持し、3 番目の構造は、指定された合計ランク合計を持つプレーヤーの数を追跡するために維持します。 

1. A と B の値の範囲にわたって 2 つのフェンウィック ツリー (または周波数配列) を初期化します。また、各プレーヤーの現在の A[i]、B[i] も保存します。 これにより、イベントが発生したときに個々の値を更新できるようになります。 
2. 入力配列から初期頻度カウントを構築します。 これらから、RankA(i) を次のように計算できます。`1 + count of elements strictly greater than A[i]`、つまり`N - prefix_count(A[i])`。 
3. 同様に、B に対して同じロジックを使用して RankB(i) を計算します。 
4. すべてのプレーヤーの初期複合スコア S[i] = RankA(i) + RankB(i) を計算します。 
5. 可能な S 値にわたってフェンウィック ツリー (またはバランスの取れた周波数構造) を維持します。 すべての初期 S[i] 値を挿入します。 
6. タイプ 1 の更新 (A[k] を変更) の場合:

 まず、A 周波数構造から A[k] の寄与を除去します。 次に、+1 または -1 を適用した後に新しい値を挿入します。 これにより、RankA クエリが正しいままになります。 
7. A[k] を更新した後、フェンウィック ツリーを使用して RankA(k) を再計算します。 S 構造から古い S[k] を削除し、RankB(k) (A 更新によって変更されていない) を再計算し、新しい S[k] を計算して挿入し直します。 
8. タイプ 2 の更新 (B[k] の変更) の場合、対称操作を実行します。B 周波数を更新し、RankB(k) を再計算し、それに応じて S[k] を更新します。 
9. クエリ タイプ 3 の場合、S[j] < S[k] に 1 を加えたプレーヤーの数である RankOverall(k) が必要です。 これは、S フェンウィック ツリーのプレフィックス クエリです。 

### なぜ効果があるのか

 RankA と RankB は動的マルチセットの順序統計であり、フェンウィック ツリーはこれらのカウントを正確に維持します。 各更新は各マルチセット内の 1 人のプレイヤーの貢献にのみ影響するため、O(log N) の調整後もグローバル構造は正しいままになります。 S[i] は i の現在のランクにのみ依存し、更新ごとに 1 人のプレイヤーだけが変更されるため、S を維持することで正確さが段階的に維持されます。 最終的なランキング クエリでは、S 値に対する標準のプレフィックス数が減ります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def range_sum(self, l, r):
        if r < l:
            return 0
        return self.sum(r) - self.sum(l - 1)

def rank_from_fenwick(bit, x, maxv, n):
    return n - bit.sum(x)

def main():
    N = int(input())
    A = [0] + list(map(int, input().split()))
    B = [0] + list(map(int, input().split()))
    Q = int(input())

    MAXV = 100000

    bitA = Fenwick(MAXV)
    bitB = Fenwick(MAXV)

    for i in range(1, N + 1):
        bitA.add(A[i], 1)
        bitB.add(B[i], 1)

    def get_rankA(x):
        return N - bitA.sum(x)

    def get_rankB(x):
        return N - bitB.sum(x)

    S = [0] * (N + 1)
    bitS = Fenwick(2 * N + 5)

    for i in range(1, N + 1):
        S[i] = get_rankA(A[i]) + get_rankB(B[i])
        bitS.add(S[i], 1)

    for _ in range(Q):
        tmp = input().split()
        if tmp[0] == '1':
            k = int(tmp[1])
            sign = tmp[2]
            bitA.add(A[k], -1)
            if sign == '+':
                A[k] += 1
            else:
                A[k] -= 1
            bitA.add(A[k], 1)

            old = S[k]
            bitS.add(old, -1)

            S[k] = get_rankA(A[k]) + get_rankB(B[k])
            bitS.add(S[k], 1)

        elif tmp[0] == '2':
            k = int(tmp[1])
            sign = tmp[2]
            bitB.add(B[k], -1)
            if sign == '+':
                B[k] += 1
            else:
                B[k] -= 1
            bitB.add(B[k], 1)

            old = S[k]
            bitS.add(old, -1)

            S[k] = get_rankA(A[k]) + get_rankB(B[k])
            bitS.add(S[k], 1)

        else:
            k = int(tmp[1])
            print(bitS.sum(S[k] - 1) + 1)
```この実装は、3 つの独立した周波数ドメインのフェンウィック ツリーに依存しています。 2 つは、A と B の動的な順序統計を維持するために使用されます。3 つ目は、結合されたランク値 S の分布を維持します。重要な詳細は、更新がローカルであることです。操作ごとに 1 つのインデックスのみが変更されるため、2 つの Fenwick クエリ後の S の再計算は定数時間です。 

よくある落とし穴は、RankA が厳密に大きな値に依存していることを忘れていることです。そのため、RankA を次のように計算します。`N - prefix_sum(x)`それよりも`prefix_sum(x)`自体。 もう 1 つの微妙な問題は、ランクを再計算する前に、A と B の値の更新が頻度構造に正しく反映されていることを確認することです。

 ## 特殊なケース

 重要なエッジ ケースは、すべての A または B の値が等しい場合です。 その場合、RankA と RankB はすべてのプレイヤーに対して両方とも 1 でなければならず、S は定数です。 等価性を適切に処理せずに誤って厳密なプレフィックス数を使用する実装では、誤った順序付けが生成されます。 

もう 1 つの微妙なケースは、同じインデックスに対してインクリメントとデクリメントが繰り返されることです。 各更新はランクを再計算する前に周波数構造に即座に反映する必要があるため、新しい値を挿入する前に古い値を削除しないと、後続のすべてのランク計算が破損します。
