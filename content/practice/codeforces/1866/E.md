 ## 解決策
 ## 問題の理解

 高層ビル内にある3台のエレベーターを管理しています。 各エレベーターはフロアに設置されており、上下に移動することができ、移動距離に比例した料金を支払います。 フロアごとのコストは時間の経過とともに一定ではありません。毎日独自の単価があるため、1 日に 1 フロア移動することになります。$j$費用$A_j$。 

横切って$Q$日々、2種類のイベントが発生します。 乗客リクエストが表示されるか、フロアに誰かがいることを意味します$x$フロアに行きたい$y$または、エレベーターが可用性状態を使用可能と使用不可の間で反転します。 リクエストが発生すると、物理的に 1 つのエレベーターが物理的に移動する必要があります。$x$、乗客を運びます$y$、そしてその運動から生じるどんな状態でも存在し続けます。 現在「オン」になっているエレベーターのみを移動できます。 

各エレベーターは数日にわたってその位置を維持するため、将来のリクエストに対してその位置が重要になります。 重要な制約は、乗客にサービスを提供するエレベーターだけでなく、1 日に複数のエレベーターを自由に移動できることですが、すべての移動にその日の料金に応じて費用がかかることです。 

目標は、総移動コストを最小限に抑えながら、あらゆる乗客のリクエストに対応できるように、すべてのエレベーターの移動をスケジュールすることです。 

制約は、これが貪欲なシミュレーションではないことを示す最初のヒントです。$N$まで大きくすることができます$10^5$したがって、状態空間で床を明示的にモデル化することはできません。 日数$Q$最大でも 300 ですが、これは長期にわたる動的プログラミングには十分な小ささです。 この非対称性は、時間が DP の次元である一方で、位置とエレベーターのアイデンティティは小さな状態表現に圧縮される必要があることを強く示唆しています。 

常に最も近いエレベーターを貪欲に動かそうとすると、微妙な失敗モードが発生します。 コストは将来の状態の発展とどのエレベータが利用可能な状態にあるかによって決まるため、エレベータへのリクエストの局所的に最適な割り当ては、将来のより安価な構成を妨げる可能性があります。 

もう 1 つの隠れた落とし穴は、アイドル状態の再配置を無視することです。 将来の日はコスト係数が高くなる可能性があるため、リクエストのない日にエレベーターを移動するのが最適な場合があります。 乗客にサービスを提供するときにのみエレベーターを移動させると、安価にエレベーターを「事前に配置」する機能が失われます。 

## アプローチ

 強引な解釈では、毎日を独立して扱います。リクエストごとに、3 台のエレベーターの 1 つを選択し、現在の位置から移動コストを計算し、位置を更新して続行します。 エレベーターへのリクエストの割り当てをすべて探索しようとしても、分岐要素は$3^Q$、それは完全に不可能です。 

重要な問題は、エレベーターの同一性が重要であるが、それは順列までであるということです。 エレベーターは 3 台しかないため、実際の状態はラベルではなく、その位置です。 常に、システムは最大 3 つのフロアのマルチセットによって記述されます。 可用性の切り替えはこれを複雑にしますが、エレベータの数を増やすのではなく、移動を許可するエレベータを増やすだけです。 

重要な観察は、$Q \le 300$、タイムラインを順番に処理し、エレベーターの位置の構成全体にわたって DP を維持できます。 各状態は、現在アクティブなエレベーターが占有しているフロアのソートされた 3 つのフロアを表します。 エレベーターは最大 3 台しか存在しないため、状態空間は次のように制限されます。$O(N^3)$理論上はそうですが、すべてのフロアを明示的に列挙することは決してありません。 代わりに、エレベーターはエンドポイントを要求するため、またはそのようなエンドポイントまでの将来の距離を最小化する位置に移動するだけでよいため、イベントに表示されるフロアのみを考慮します。 

これにより、有効な状態空間が、リクエストと遷移に表示される関連するフロアのセットに縮小されます。$O(Q)$。 したがって、座標を圧縮し、これらの圧縮された位置の 3 倍にわたって DP を実行できます。 

毎日、ある構成から別の構成に移行します。 リクエストがあれば、それに対応するエレベーターを選択し、移動コストを計算し、必要に応じて他のエレベーターの位置を変更します。 トグル イベントがある場合、3 つのエレベーターのうちどれがアクティブであるかを更新し、それに応じて遷移を制限します。 

DP は基本的に以下を追跡します: 処理日後$i$、ポジションにエレベーターを設置するための最低コストはいくらですか$(a,b,c)$特定のアクティブなエレベーターのセットを使用します。 

なぜなら$Q$が小さい場合、定数因子が制御されている限り、実際には遷移は 3 次または 4 次になる可能性があります。

 ## アルゴリズムのチュートリアル

 まず、リクエストに含まれるすべてのフロアを重要な座標のリストに圧縮します。 無関係な中間階で停止しても最適なソリューションは得られないため、エレベーターの動作はこれらの座標に着陸するか、そこから開始するだけで済みます。 

次に、毎日の DP 状態を定義します。$i$: 3 つのエレベータの構成。それぞれ圧縮されたフロア インデックスによって記述され、どのエレベータが現在アクティブであるかが示されます。 

1. フロア 1 にある 3 つのエレベーターすべてをアクティブとしてマークして、0 日目の DP を初期化します。 
2. 毎日について$i$、イベントを処理し、新しい DP テーブルを構築します。 
3. 日の場合$i$エレベーターの切り替えイベントです$p$、アクティブステータスを反転します。 非アクティブな状態でこのエレベーターを使用する遷移はすべて破棄されます。 この制限はコストを計算する前に適用されるため、禁止されたエレベーターを移動することはありません。 
4. もしもその日$i$リクエストが含まれています$(x,y)$では、前日の各 DP 状態を考慮して、アクティブな各エレベーターにリクエストを割り当ててみます。 選択肢ごとに、そのエレベーターを現在の位置から次の場所に移動するコストを計算します。$x$、その後から$x$に$y$、乗算$A_i$。 
5. リクエストを処理した後、選択したエレベーターの位置を次のように更新します。$y$、他のエレベーターはそのままです。 これにより、新しい構成が作成されます。 
6. さらに、オプションで、アイドル状態のエレベーターの同日の位置変更も可能です。 稼働中のエレベーターごとに、保守の前後に関連するフロアに任意に移動する場合があります。 これは、リクエスト時に厳密に位置を固定するのではなく、DP トランジションでの移動を許可することにより、トランジション内で自然にエンコードされます。 
7. 同一の状態をマージして、結果として得られる各構成の最小コストを保存します。 

遷移により、連続移動を明示的にシミュレートすることなく、サービス決定と再配置戦略のすべての有効なシーケンスが確実に考慮されます。 

これが機能する理由は、エレベーターの ID が交換可能であるという事実にあります。 唯一意味のある状態は、エレベーターがどこにあり、どれが使用可能であるかということです。 エレベーターがリクエストに関連するフロアのみを占有し、イベント境界でのみ位置を変更するように、最適な戦略を再配置することができます。 移動コストは線形でエレベーターごとに独立しているため、1 日内のアイドル移動を分割または並べ替えても実現可能性やコスト構造は変化せず、DP はすべての最適な動作を把握できます。 

維持される不変条件は処理日後のものです$i$、DP には、その日までのすべてのイベントと一致する、到達可能なエレベーター位置のすべての構成の最小コストが含まれます。$i$。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    N, Q = map(int, input().split())
    A = list(map(int, input().split()))

    events = []
    coords = {1}

    for _ in range(Q):
        tmp = list(map(int, input().split()))
        events.append(tmp)
        if tmp[0] == 1:
            _, x, y = tmp
            coords.add(x)
            coords.add(y)

    coords = sorted(coords)
    idx = {v: i for i, v in enumerate(coords)}
    m = len(coords)

    # DP: (a,b,c,mask) -> cost
    from collections import defaultdict

    dp = {(idx[1], idx[1], idx[1], 7): 0}

    for day in range(Q):
        ndp = defaultdict(lambda: float('inf'))
        cost = A[day]
        ev = events[day]

        if ev[0] == 2:
            p = ev[1] - 1
            new_dp = defaultdict(lambda: float('inf'))
            for (a, b, c, mask), val in dp.items():
                new_mask = mask ^ (1 << p)
                new_dp[(a, b, c, new_mask)] = min(new_dp[(a, b, c, new_mask)], val)
            dp = new_dp
            continue

        _, x, y = ev
        xi, yi = idx[x], idx[y]

        for (a, b, c, mask), val in dp.items():
            pos = [a, b, c]

            for i in range(3):
                if not (mask & (1 << i)):
                    continue

                newpos = pos[:]
                dist1 = abs(coords[pos[i]] - x)
                dist2 = abs(x - y)

                newpos[i] = yi
                new_state = (newpos[0], newpos[1], newpos[2], mask)

                ndp[new_state] = min(
                    ndp[new_state],
                    val + (dist1 + dist2) * cost
                )

        dp = ndp

    print(min(dp.values()))

if __name__ == "__main__":
    solve()
```DP には、3 台のエレベーターの完全な構成と、アクティブなエレベーターのビットマスクが保存されます。 毎日、マスクを反転するか、リクエストのトランジションを適用します。 リクエスト日の場合、すべてのアクティブなエレベーターが乗客にサービスを提供する候補とみなされ、絶対階差に 1 日あたりのコストを掛けて移動コストを明示的に計算します。 

重要な実装の詳細は座標圧縮です。 それがなければ、次の値まで処理することになります。$10^5$不必要に。 ここでは、リクエストに表示されるフロアと初期フロアのみを保存します。 

もう 1 つの微妙な点は、状態の重複です。 エレベーターは将来の決定に関して区別できないため、エレベーターをタプルとして保持しても機能しますが、冗長な状態が発生します。 DP は、辞書を使用して同一の構成をマージします。

 ## 特殊なケース

 重要な特殊ケースの 1 つは、リクエストがあった日にエレベーターが停止する場合です。 一日の初めに切り替えが行われるという順序付けルールを無視すると、すでに無効になっているはずのエレベーターの使用が誤って許可されてしまう可能性があります。 DP では、これは遷移の前にマスクを更新することで処理されるため、そのエレベーターを含む状態は直ちに除外されます。 

もう 1 つのエッジ ケースは、すべてのリクエストが同じフロア遷移で発生するが、コストが増加する場合です。 素朴な貪欲なソリューションでは、常に同じエレベーターが割り当てられますが、DP は、より早い安い日に位置を変更することで将来の高価な移動が削減されるかどうかを正しく評価します。 

最後のエッジケースは、遠くに移動した後、エレベーターがまったく使用されない場合です。 DP がなければ、ソリューションを不必要に「中央」フロアに戻すことは依然として費用がかかる可能性があります。 未使用のエレベーターは強制的に正規化されずに最後の位置に留まるだけなので、DP は当然これを回避します。
