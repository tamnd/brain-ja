 ## 解決策
 ## 問題の理解

 学生はたくさんいますが、「一緒にいなければいけない」関係で明確につながっている学生は比較的少数です。 これらの関係は、生徒に関する無向グラフを形成します。 各生徒は番号の付いた 1 枚のカードから始めます。カードの交換は、最終グラフに存在する友情リンクに沿ってのみ可能です。 何かが始まる前に追加の友情エッジを追加することができます。目標は、追加する追加のエッジの数を最小限に抑えることです。 

重要な要件は、単一の最終的な取り決めに関するものではなく、堅牢性に関するものです。最初のカードがどのように配布されたとしても、友情エッジに沿った交換を使用して、親友のすべてのペアが最終的に同じカード値を保持する状態に到達することが常に可能でなければなりません。 

重要な構造は、スワップが友情グラフの接続されたコンポーネントに制限されることです。 接続されたコンポーネント内ではカードを任意に並べ替えることができますが、コンポーネント間ではカードは永久に分離されます。 つまり、問題全体は、最終的に接続されたコンポーネントが、ベストフレンド エッジによって課せられる「等しくなければならない」制約とどのように相互作用するかということになります。 

制約は最大 200,000 のベストフレンド関係に及ぶため、どのソリューションでも基本的にグラフを、union-find や DFS ベースのコンポーネント分析などの線形または線形に近いプロセスに削減する必要があります。 エッジやノードで二次関数を扱うことは直ちに不可能です。 

ベストフレンドエッジがチェーンまたはサイクルを形成する場合、微妙なエッジケースが現れます。 たとえば、ベストフレンド関係が 1-2、2-3、3-4 の場合、各エッジは隣接するペアについてのみ会話しますが、推移的な要件により、4 つのノードすべてが単一の同期ユニットとして動作することが強制されます。 エッジを個別にチェックするだけの単純なアプローチは、接続による伝播を無視するため、ここでは失敗します。 

## アプローチ

 この強引なアイデアは、システムをシミュレートすることです。友情エッジのセットを追加して、考えられる初期割り当てごとに、すべての親友ペアが最終的に等しくなるように交換を常に調整できるかどうかを検証してみます。 可能な初期カード割り当ての数は天文学的に多く、単一の構成をチェックするだけでもコンポーネント内の到達可能性と順列について推論する必要があるため、これはすぐに実行不可能になります。 

構造を単純化するには、2 つの層を分離する必要があります。 1 つのレイヤーは、交換が可能な場所を決定する友情グラフです。 もう 1 つの層は、平等制約を課すベストフレンド グラフです。 友情グラフの接続されたコンポーネント内では、スワップによって値を自由に並べ替えることができるため、重要なのはどのノードが同じコンポーネントになるかだけです。 

重要な観察は、等価制約がベストフレンド グラフの接続性に沿って伝播するということです。 ノード A がノード B と等しく、B が C と等しくなければならない場合、A、B、および C はすべて、初期分布に関係なくシステムが常にそれらの値を調整できる状況に強制されなければなりません。 これは、制約されたノードが単一の柔軟なユニットとして動作できるほど強力な友情構造がある場合にのみ可能になります。 

追加されるエッジの最小数は、ベスト フレンド グラフの接続された各コンポーネントがフレンドシップ構造によって完全に「サポート」されることを保証するために必要なものです。つまり、制約されたノードが独立したスワッピング領域に分割されることはありません。 これは、各親友コンポーネントを 1 つの統合された友情コンポーネントに接続することになります。そのためには、そのような各コンポーネントがまだ内部接続されていない場合は内部接続する必要があります。 

実際には、これは、サイズ k のベストフレンド グラフの各接続コンポーネントが、友情システムの下で完全に内部接続されるためには、k から 1 つのエッジを引いたものを必要とすることを意味します。

 ## アルゴリズムのチュートリアル

 制約は接続を通じてのみ伝播するため、ベスト フレンド グラフを接続コンポーネントに圧縮して進めます。 

### 1. 親友グラフの接続コンポーネントを構築する

 私たちは各生徒をノードとして扱い、それぞれの親友関係をエッジとして扱います。 DFS または DSU を使用して、接続されているすべてのコンポーネントを識別します。 このステップでは、推移的な等価性圧力を捉えます。同じコンポーネント内の 2 つのノードは、有効な最終割り当ての下で一貫して動作する必要があります。 

### 2. 各コンポーネントのサイズを測定します

 接続されたコンポーネントごとに、それに含まれるノードの数を数えます。 このサイズによって、内部に存在する独立した同期ポイントの数が決まります。 

### 3. 必要な内部接続を計算する

 サイズ k のコンポーネントが「安全」であるのは、フレンドシップ システムがそのノード間の完全な内部混合を許可している場合のみです。 コンポーネントが断片化された部品ではなく、単一の柔軟なユニットのように動作できるようにするには、少なくとも k から 1 を引いたエッジが必要です。 

コンポーネントがすでに複数の友情関係にある領域にまたがっている場合は、それらを概念的に「縫い合わせる」必要があります。 失われたそれぞれのつながりは、1 つの新しい友情に対応します。 

### 4. すべてのコンポーネントの合計

 すべての接続コンポーネントの合計 (サイズ - 1) を計算します。 これにより、最初のカード配布に関係なく、すべての親友の制約が常に満たされることを保証するために必要な追加の友情の最小数が得られます。 

### なぜ効果があるのか

 ベストフレンド グラフの各接続コンポーネント内では、すべてのノードが等価性要件のチェーンを通じて相互に制約されます。 友情構造がそれらを完全に接続していない場合、一部のノードが別々のスワッピング領域に閉じ込められ、任意の初期割り当ての下で同一の値を保証することが不可能になります。 このような各コンポーネントを強制的に内部で完全に接続することで、すべてのベスト フレンド エッジに沿って等価性制約を常に満たせるように、割り当てを自由に再配置できるようになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    n, m = map(int, input().split())
    
    adj = {}
    
    for _ in range(m):
        a, b = map(int, input().split())
        a -= 1
        b -= 1
        if a not in adj:
            adj[a] = []
        if b not in adj:
            adj[b] = []
        adj[a].append(b)
        adj[b].append(a)

    visited = set()

    def dfs(start):
        stack = [start]
        visited.add(start)
        cnt = 0
        while stack:
            u = stack.pop()
            cnt += 1
            for v in adj.get(u, []):
                if v not in visited:
                    visited.add(v)
                    stack.append(v)
        return cnt

    answer = 0

    for node in adj:
        if node not in visited:
            size = dfs(node)
            answer += max(0, size - 1)

    print(answer)

if __name__ == "__main__":
    solve()
```この実装では、ベストフレンド グラフの隣接リストを構築し、反復 DFS を実行してコンポーネント サイズを計算します。 新しい未訪問のノードが見つかるたびに、その接続されたコンポーネント全体を調査し、そのサイズをカウントします。 そのコンポーネントの寄与は、サイズから 1 を引いたものとして追加されます。 

微妙な実装の詳細は、再帰負荷の高いトラバーサルの代わりに反復 DFS を使用することです。これにより、友情の長いチェーンでのスタック オーバーフローが回避されます。 もう 1 つの重要な点は、ベストフレンド エッジのエンドポイントのみが関連するため、ノードが 1 から n まで密であると仮定するのではなく、隣接ディクショナリを反復処理することです。 

## 実用的な例

 ### 例 1

 入力:```
5 3
1 2
2 3
4 5
```次のようにコンポーネントを構築します。 

| ステップ | ノード | 訪問されたコンポーネント | コンポーネントのサイズ |
 | --- | --- | --- | --- |
 | 1 | 1 | {1,2,3} | 3 |
 | 2 | 4 | {4,5} | 2 |

 答えの合計は (3−1) + (2−1) = 3 となります。 

これは、各クラスターが内部的に安定化する必要があるため、個別のベストフレンド クラスターが最終コストにどのように独立して寄与するかを示しています。 

### 例 2

 入力:```
4 2
1 2
3 4
```| ステップ | ノード | 訪問されたコンポーネント | コンポーネントのサイズ |
 | --- | --- | --- | --- |
 | 1 | 1 | {1,2} | 2 |
 | 2 | 3 | {3,4} | 2 |

 答えは (2−1) + (2−1) = 2 です。 

このケースは、切断されたペアが独立して動作し、任意の初期カード配布下で完全に同期可能になるためにそれぞれ 1 つの追加接続が必要であることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + m) | ベストフレンド グラフ内の各ノードとエッジは、DFS 中に 1 回アクセスされます。 
| スペース | O(n + m) | 隣接リストと訪問された構造はグラフを保存します。 

この制約では最大 2×10^5 のエッジが許可されるため、線形トラバースは問題なく制限内に収まります。 このアルゴリズムは単一のグラフ パスを実行するため、時間とメモリの制限の両方に簡単に適合します。

 ## 特殊なケース

 退化したケースは、親友のエッジがまったく存在しない場合です。 グラフには制約がないため、余分な友情は必要ありません。 処理するコンポーネントがないため、アルゴリズムは当然ゼロを返します。 

もう一つのケースは、親友関係が長く続くケースです。 すべてのノードの次数は最大 2 ですが、それらは単一の連結コンポーネントを形成し、アルゴリズムはチェーン全体をサイズ k の 1 つの単位として正しく扱い、k マイナス 1 に寄与します。 

星のような非常に偏ったグラフも正しく動作します。 センターはすべてのノードを 1 つのコンポーネントに接続し、その寄与はリーフの数になります。これは、任意の初期配布下で完全な同期性を確保するために必要な内部接続の必要数と一致します。
