 ## 解決策
 ## 問題の理解

 私たちは成長を続けるスタックのコレクションを維持しており、スタックの数とその内容は時間の経過とともに変化します。 最初はスタックはありません。 システムは一連の操作を順番に処理します。 

1 つの操作で新しい空のスタックが作成され、それが最後に追加されます。 別の操作では、選択したスタックに値をプッシュします。 3 番目の操作では、スタックの最後から挿入順に数えて、特定のスタックにプッシュされた j 番目の値を要求します。 

したがって、各スタックは挿入順序の標準スタックのように動作しますが、クエリは最上位の要素を要求しません。 代わりに、挿入インデックスによる履歴アクセスを要求します。 

制約は非常に小さく、合計操作数は最大 100 です。 これにより、単純な線形処理を超えるパフォーマンスに関する懸念がすぐに解消されます。 操作ごとに一定または線形の作業を実行するアプローチはどれも快適に通過できます。 

主な微妙な点はパフォーマンスではなく、インデックス作成の正確さです。 各スタックは独立して成長し、操作は作成順序に応じて 1 から始まる識別子によってスタックを参照します。 単純な実装では、スタック インデックスを混同したり、逆の操作で j 番目の要素が上からの深さではなく挿入順序を参照していると誤解したりすることで、簡単に間違いが発生する可能性があります。 

典型的な失敗例は、スタックを削除または動的再インデックス作成が必要であると誤って処理した場合に発生します。 たとえば、j 番目の要素を「上から j 番目」と解釈すると、インデックス付けが誤って逆になる可能性があります。 実際には、これは単に j 番目にプッシュされた要素です。 

## アプローチ

 直接シミュレーションは問題の構造と正確に一致します。 私たちはスタックのリストを管理しています。 各スタックは、値を挿入順に格納するリストです。 タイプ 1 の操作が表示されると、新しい空のリストが追加されます。 タイプ 2 の操作が出現すると、対応するスタックに値を追加します。 タイプ 3 の操作が出現すると、スタックに直接インデックスを付けます。 

これが機能するのは、すべての操作がローカルであり、グローバル構造を必要としないためです。 バランス調整、検索、永続化は必要ありません。 すべてのクエリは、O(1) 更新後、O(1) 時間以内に応答されます。 

ここには意味のある最適化問題がないため、ブルート フォースのバリアントは構造が同一になります。 より複雑なデータ構造を使用しようとしても、オーバーヘッドが増えるだけで、メリットはありません。 

重要な観察は、スタックが独立しており、スタックの成長履歴がまさに追加された値のシーケンスであるということです。 したがって、j 番目の要素は文字通り、基礎となる配列のインデックス j-1 にあります。

 ## アルゴリズムのチュートリアル

 1. 空のリストから始める`stacks`。 これは、スタックの現在のコレクションを作成順に表します。 各スタック自体は、プッシュされた値を到着順に格納するリストです。 
2. タイプ 1 の操作が発生すると、新しい空のリストを`stacks`。 この新しいリストは、要素のない新しいスタックを表します。 
3.第2種操作時`(i, x)`発生、追加`x`に`stacks[i-1]`。 これは、挿入順序を維持しながら、スタック i へのプッシュをシミュレートします。 
4. タイプ 3 の操作の場合`(i, j)`発生、出力`stacks[i-1][j-1]`。 これにより、そのスタック内の j 番目に挿入された要素が直接取得されます。 

正確さは、各スタックを純粋な追加専用シーケンスとして維持することで実現されます。 削除や変更が発生しないため、挿入順序は安定した位置インデックス付けと同等です。 

### なぜ効果があるのか

 各スタックは独立しており、追加操作のみを受け取ります。 これは、スタック内の値のシーケンスが挿入の時系列順であることを意味します。 要素を削除したり並べ替えたりする操作はないため、j 番目に挿入された要素の位置は変更されません。 したがって、位置によるインデックス付けは、挿入履歴を追跡することと同じです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    q = int(input().strip())
    stacks = []

    for _ in range(q):
        parts = input().split()
        t = int(parts[0])

        if t == 1:
            stacks.append([])

        elif t == 2:
            i = int(parts[1]) - 1
            x = int(parts[2])
            stacks[i].append(x)

        else:
            i = int(parts[1]) - 1
            j = int(parts[2]) - 1
            print(stacks[i][j])

if __name__ == "__main__":
    main()
```実装はアルゴリズムを直接反映しています。 各スタックは Python リストとして保存されるため、追加は O(1) で償却されます。 インデックス付けは、スタックと要素の両方で 1 ベースから 0 ベースに調整されます。 

唯一のよくある間違いは、入力におけるスタック インデックスと要素の位置の両方が 1 から始まることを忘れていることです。 変換はアクセスするたびに一貫して適用する必要があります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(Q) | 各操作は O(1) 作業 (インデックスの追加、作成、直接実行) を実行します。 
| スペース | O(Q) | プッシュされた各値は、すべてのスタックにわたって 1 回保存されます。 

操作が 100 回に制限されているため、このソリューションは非常に高速になります。 クエリごとに一定時間の操作が行われるため、さらに高い制約でも安全に保たれます。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    q = int(sys.stdin.readline().strip())
    stacks = []
    out = []

    for _ in range(q):
        parts = sys.stdin.readline().split()
        t = int(parts[0])

        if t == 1:
            stacks.append([])
        elif t == 2:
            i = int(parts[1]) - 1
            x = int(parts[2])
            stacks[i].append(x)
        else:
            i = int(parts[1]) - 1
            j = int(parts[2]) - 1
            out.append(str(stacks[i][j]))

    return "\n".join(out)

 ## 特殊なケース

 エッジ ケースの 1 つは、プッシュを行わずにスタック作成直後にクエリを実行することです。 この問題では有効なクエリが保証されているため、この状況は入力では発生しませんが、論理的には空のスタックにアクセスすることは無効になります。 実装は保証に依存しており、追加のチェックは追加されません。 

もう 1 つの微妙なケースは、1 から始まるインデックスが一貫して変換されるようにすることです。 たとえば、スタック 1 はインデックス 0 に格納されます。このシフトがプッシュまたはクエリのいずれかで忘れられた場合、プログラムは依然として範囲内に留まりながら、不正な結果を静かに返します。 

最後のケースは、プッシュが発生する前に複数のスタックが作成される場合です。 構造体は空のリストをエラーなく正しく割り当て、後のプッシュが識別子の順序で正しいスタックに確実に配置されるようにする必要があります。
