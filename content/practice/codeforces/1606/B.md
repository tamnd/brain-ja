 ## 解決策
 ## 問題の理解

 最初に更新された 1 台のコンピューターからネットワーク内のすべてのコンピューターにオペレーティング システムの更新をコピーするのに必要な最小時間を決定するように求められます。 各コンピュータは 1 時間あたり最大 1 台の他のコンピュータにアップデートをコピーでき、ネットワークには合計`k`パッチ ケーブルを使用すると、1 時間あたりの同時転送数が制限されます。 目標は、複数のテスト ケースについて、すべてのコンピューターに更新プログラムが適用されるように必要な最小時間数を出力することです。 

主な制約は次のとおりです。`n`そして`k`それぞれ最大で可能です$10^{18}$、最大で$10^5$テストケース。 すべてのコンピューターの操作をシミュレートすると遅すぎるため、時間ごとに直接シミュレートするソリューションは除外されます。 代わりに、ソリューションは、更新されるコンピューターの時間ごとの増加を数学的に推論し、反復処理を行わずに非常に大きな数を処理する必要があります。 

次の場合、微妙なエッジケースが発生します。`k`に比べて非常に小さいです`n`。 たとえば、次の場合`n = 7`そして`k = 1`、すでに複数のコンピュータが更新されているにもかかわらず、1 時間あたり 1 台の新しいコンピュータのみが更新を受信できるため、更新はほぼ直線的に広がります。 逆に、もし`k >= n - 1`、複数の更新を同時に実行できるため、時間が大幅に短縮されます。 場合`n = 1`は簡単です。更新は必要ありません。出力は次のようにする必要があります。`0`。 

## アプローチ

 ブルート フォース アプローチでは、時間ごとにシミュレーションを行います。つまり、アップデートが行われたコンピュータのカウンタを維持し、利用可能なパッチ ケーブルに基づいてアップデートできるコンピュータの数を計算し、すべてのアップデートが行われるまで続行します。`n`コンピューターが更新されます。 この方法は正しいですが、その複雑さはおおよそ以下に比例します。`n`、大規模な場合は実行不可能になります`n`まで$10^{18}$。 

最適なアプローチに関する洞察は、スプレッドを 2 つの段階として見ることから得られます。 最初のフェーズでは、更新されたコンピューターの数が増加したとき、`u`未満です`k`、更新容量は次によって制限されます。`u`というのは、各コンピュータは 1 時間あたり 1 台のコンピュータにしかアップデートを送信できないからです。 このフェーズでは、更新されるコンピューターの数が 1 時間ごとに 2 倍になります。 第 2 フェーズでは、`u >= k`、1 時間あたりの更新数の上限は次のとおりです。`k`、パッチケーブルがボトルネックになるからです。 このフェーズでは、更新されたコンピューターの数は次のように直線的に増加します。`k`到着するまでの毎時間`n`。 

この観察結果を使用して、2 つの部分に分けて必要な時間数を計算できます。 まず、更新されたコンピューターが到達するまでにかかる時間を数えます。`k`倍増経由で。 次に、更新されたコンピュータの数が少なくとも`k`、更新するコンピューターの残りの数を計算し、次で割ります。`k`追加で必要な時間数を取得します。 これにより、複雑さが軽減されます。`O(log k + 1)`これは、最大の制約に対しても十分に高速です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | テスト ケースあたり O(n) | お(1) | 10^18 までの n には遅すぎます |
 | ダブリング + リニアフェーズ | テスト ケースごとに O(log k + 1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1.読む`t`、テスト ケースの数、および各テスト ケースについて、次の情報を読み取ります。`n`そして`k`。 
2.初期化`hours = 0`そして`updated = 1`アップデートが適用されたコンピューターの数を追跡します。 
3. その間`updated < k`そして`updated < n`、1 時間ごとに更新されるコンピューターの数が 2 倍になります。 インクリメント`hours`倍増ステップごとに。 更新されたコンピュータの数が`k`、更新された各コンピュータは新しいコンピュータにコピーできます。 
4. 倍増フェーズの後、次の場合`updated >= n`、印刷`hours`すべてのコンピューターが更新されるため、その結果となります。 
5. それ以外の場合は、残りのコンピュータを次のように計算します。`remaining = n - updated`。 現在、1 時間ごとに最大で更新されます`k`コンピュータを使用するため、さらに必要な時間は`(remaining + k - 1) // k`切り上げること。 これらの時間を合計に加えてください。 
6. テストケースの合計時間を出力します。 

機能する理由: アルゴリズムは、次の不変条件を維持します。`updated`は常に、その時間にアップデートを実行できるコンピューターの最大数を表します。 最初のフェーズでは、最大の増加は更新されたコンピューターの数によって制限されます (`updated < k`)、指数関数的な増加をもたらします。 第 2 フェーズでは、ボトルネックはパッチ ケーブルの数であるため、増加は次のように直線的になります。`k`1時間あたり。 これにより、計算される合計時間は最小限に抑えられます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def min_hours(n, k):
    if n == 1:
        return 0
    hours = 0
    updated = 1
    while updated < k and updated < n:
        updated *= 2
        hours += 1
    if updated >= n:
        return hours
    remaining = n - updated
    hours += (remaining + k - 1) // k
    return hours

t = int(input())
for _ in range(t):
    n, k = map(int, input().split())
    print(min_hours(n, k))
```このソリューションは、次を使用して入力を効率的に読み取ります。`sys.stdin.readline`潜在的に多数のテストケースが存在するためです。 の`min_hours`関数は、上記のアルゴリズムをカプセル化します。 倍増が起こるのは、`updated < k`、このしきい値を超えると、線形位相が計算されます。 線形フェーズでの切り上げには注意が必要です。`(remaining + k - 1) // k`これにより、off-by-one エラーが回避されます。 

## 実用的な例

 最初のサンプルを考えてみましょう`n = 8, k = 3`。 

| 時間 | 更新されました | メモ |
 | --- | --- | --- |
 | 0 | 1 | 初期状態 |
 | 1 | 2 | 1 < 3 | なので double
 | 2 | 4 | 2 < 3 なので double → 最終的に k=3 で上限が設定され、次は 2 倍になって 4 |
 | 3 | 8 | 残り = 8 - 4 = 4 → k=3 の線形相 → 時間 = ceil(4/3) = 2 → 合計時間 = 4 |

 これは予想される出力と一致します`4`。 

のために`n = 7, k = 1`、倍加フェーズは発生しません。`updated >= k`最初は失敗します。 アルゴリズムは直ちに線形成長に入ります。 

| 時間 | 更新されました | メモ |
 | --- | --- | --- |
 | 0 | 1 | 初期状態 |
 | 1 | 2 | k=1 を追加 |
 | 2 | 3 | k=1 を追加 |
 | 3 | 4 | k=1 を追加 |
 | 4 | 5 | k=1 を追加 |
 | 5 | 6 | k=1 を追加 |
 | 6 | 7 | k=1 を追加 → 完了 |

 出力は`6`、予想通り。

 ## 特殊なケース

 のために`n = 1, k = 1`、最初のコンピューターにはすでにアップデートがインストールされています。 アルゴリズムは戻ります`0`ループに入ることなく、最小限のシナリオを正しく処理します。 

のために`k = 1`、1 時間ごとに 1 台のコンピューターのみを更新できます。 2 倍化ループはスキップされ、アルゴリズムは次の要素を追加します。`(n - 1 + 1 - 1) // 1 = n - 1`これは、予想される線形スプレッドと一致します。 例えば、`n = 7, k = 1``を生成します
