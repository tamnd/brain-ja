 ## 解決策
 ## 問題の理解

 建物の廊下システムを表す長方形のグリッドが与えられています。 グリッドの各セルは、空、壁、鍵、施錠されたドア、または開始位置のいずれかです。 開始セルから、人は一定の一連の方向に従って移動します。 移動ルールは標準的なグリッド ステップではありません。方向を選択すると、人はさらなる移動を何かが妨げるまで、その方向にセルごとにスライドし続けます。 

ブロック セルは、グリッド、壁、またはロックされたドアの境界である可能性があります。 施錠されたドアの動作は、その人が現在少なくとも 1 つの鍵を所持しているかどうかに応じて異なります。 鍵が利用可能な場合、ドアに到達するとすぐにドアが開き、移動は停止することなくドアを通過し続け、1 つの鍵を消費します。 鍵は通過時に自動的に回収され、持ち運べる数に制限はありません。 重要なのは、キーはまったく障害物ではなく、キーを持ち上げた後も正常に動作し続けることです。 

2 つのモードがあります。 D が 0 に等しい場合、グリッドには空のセルと壁のみが含まれるため、移動は純粋に幾何学的なスライドになります。 D が 1 に等しい場合、移動はこれまでに収集された鍵の数に依存するため、鍵とドアが存在し、状態の変化が生じます。 

タスクは、各移動コマンドをシミュレートし、そのスライド中に通過したセルの数を出力することです。 

この制約では、最大 10^5 のセルと 10^5 の移動が許可されるため、移動ごとにグリッドを線形にスキャンするソリューションは遅すぎます。 移動ごとにセルごとに再ウォークする単純なシミュレーションでは、O(HW × L) にまで低下する可能性があり、これは現実的ではありません。 ソリューションでは、同じセグメントを繰り返し再処理することを回避し、キーやドアによって引き起こされる動的な状態変化を効率的に処理する必要があります。 

ドアとキーが相互作用するときに、微妙なエッジケースが現れます。 たとえば、同じ方向のドアの後ろに鍵がある廊下を考えてみましょう。 鍵が以前にすでに収集されているかどうかに応じて、ドアが動きを停止する場合と停止しない場合があり、それによってスライドの有効な到達可能なセグメントが変わります。 障害物は静的ではないため、単純に事前計算された「次の障害物」テーブルは D = 1 で壊れます。 

もう 1 つのエッジ ケースは、最後のキーが消費されたまさにそのときにドアに遭遇する場合です。 消費する瞬間が重要です。ドアは横断中に開かれるため、遭遇した瞬間にそれが障壁のように見えても、停止したとはみなされません。 

## アプローチ

 それぞれの動きを段階的にシミュレーションすると、プロセスは簡単になります。 現在の位置から、指定された方向に一度に 1 セルずつ歩き、位置を更新し、境界、壁、鍵、ドアを確認します。 キーを押すたびに、キーカウンターがインクリメントされます。 ドアに当たるとき、私たちは鍵を持っているかどうかを確認します。 はいの場合は、1 つ消費して続行します。そうでない場合は、ドアに入る前に停止します。 ルールを正確に反映しているため、正しさは即座にわかります。 

このアプローチの問題はパフォーマンスです。 最悪の場合、L 個の移動のそれぞれがほぼグリッド全体を横断する可能性があり、O(HW × L) 回の操作が必要になります。 両方とも 10^5 までなので、これは 10^10 ステップとなり、制限をはるかに超えています。 

重要な観察は、グリッド自体が静的であり、各ステップ中の動きは行または列に沿って厳密に単調であるということです。 これにより、各方向での「次のブロッキング イベント」情報の前処理が可能になります。 ただし、標準的なスライディング問題とは異なり、鍵が消費され、ドアが通行可能になると、ブロッカーのセットが変化します。 これにより、完全に静的なジャンプ テーブルが妨げられます。

解決策は、構造を状態から分離することです。 壁とグリッドの境界は永続的なブロッカーであり、次に近い壁の遷移でエンコードできます。 鍵やドアは一時的なものです。 私たちはドアを条件付きブロッカーとして扱います。ドアはキー数がゼロの場合にのみ壁のように動作し、それ以外の場合は通過可能で状態を消費します。 

これは方向性スイープ戦略につながります。 各行と列について、各方向で最も近い次の特別イベントを維持します。 また、ドアとキーの動的な構造も維持しており、通常は座標順に並べられたセットを使用して、セルごとにステップ実行するのではなく、次の候補のキーまたはドアに直接ジャンプできます。 各スライドは、単位ステップではなく、重要なイベント間の一連のジャンプになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(HW・L) | O(HW) | 遅すぎる |
 | イベント駆動型の方向性ジャンプ | O((H+W+L) log HW) | O(HW) | 承認済み |

 ## アルゴリズムのチュートリアル

 行と列ごとに順序付けされた構造を使用して、各方向を独立して処理するという観点からソリューションを説明します。 

1. すべての特殊セルを行と列ごとにグループ化して、グリッドを前処理します。 行ごとに、壁、鍵、ドアの位置を並べ替えて保存します。 列についても同じことを行います。 これにより、どの方向でも高速な「次のイベント」クエリが可能になります。 
2. キーとドアの 2 つの順序セットをグローバルに維持し、それらの座標によってインデックスを付けます。 これらのセットを使用すると、収集時に鍵を取り外し、開いたときにドアを効果的に「無効にする」ことができます。 
3. S の位置から開始し、現在保持されているキーの数をゼロとして保持する変数を初期化します。 
4. 移動ごとに、水平方向か垂直方向かを決定します。 水平の場合は、行構造を操作します。 垂直の場合は、柱構造を使用します。 この制限により、ステップごとの動きが 1 次元になります。 
5. 関連する障害物のソートされたリストに対する二分探索を使用して、現在位置から選択した方向で最も近いイベントに繰り返しジャンプします。 これにより、動きを停止または変更できる次の候補セルが得られます。 
6. 次のイベントが壁または境界である場合、そのセルまでの距離を計算して答えに追加し、移動を停止します。 
7. 次のイベントがキーの場合は、それに移動し、キーカウンターを増やし、構造からそれを削除し、同じ方向に同じ動きを続けます。 
8. 次のイベントがドアで、少なくとも 1 つの鍵がある場合は、その中に移動し、鍵の数を減らし、ドアを取り除くか、開いているとマークして、移動を続けます。 
9. 次のイベントがドアで、鍵がない場合、ドアは壁のように動作するため、その直前で停止します。 
10. 各手ごとに通過したセルの数を累積して出力します。 

### なぜ効果があるのか

 行または列に沿った動きは常に、その方向の最も近い未解決のイベントによって完全に決定されます。 現在位置とそのイベントの間にある他のすべてのセルは空であるため、停止条件とは無関係です。 鍵やドアは、遭遇した瞬間にのみ重要であり、処理された後はブロッカーとして再び現れることはありません。 これにより、各特別なセルが最大 1 回処理されることが保証され、以前の構成を再検討することなく、移動するたびに状態が前進します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    H, W, D = map(int, input().split())
    grid = [list(input().strip()) for _ in range(H)]
    L = int(input())
    moves = input().strip()

    # locate start
    sx = sy = 0
    for i in range(H):
        for j in range(W):
            if grid[i][j] == 'S':
                sx, sy = i, j

    keys = set()
    doors = set()

    for i in range(H):
        for j in range(W):
            if grid[i][j] == 'K':
                keys.add((i, j))
            elif grid[i][j] == 'L':
                doors.add((i, j))

    x, y = sx, sy
    have = 0

    def is_wall(i, j):
        if i < 0 or i >= H or j < 0 or j >= W:
            return True
        return grid[i][j] == '#'

    for c in moves:
        dx = dy = 0
        if c == 'U':
            dx = -1
        elif c == 'D':
            dx = 1
        elif c == 'L':
            dy = -1
        else:
            dy = 1

        steps = 0

        while True:
            nx, ny = x + dx, y + dy

            if nx < 0 or nx >= H or ny < 0 or ny >= W:
                break
            if grid[nx][ny] == '#':
                break

            if (nx, ny) in keys:
                have += 1
                keys.remove((nx, ny))

            if (nx, ny) in doors:
                if have > 0:
                    have -= 1
                    doors.remove((nx, ny))
                    x, y = nx, ny
                    steps += 1
                    continue
                else:
                    break

            x, y = nx, ny
            steps += 1

        print(steps)

def main():
    solve()

if __name__ == "__main__":
    main()
```実装は直接シミュレーション戦略に従います。 グリッドはそのまま保存され、キーとドアは状態が動的に変化するようにセットで追跡されます。 各移動は、説明どおりのルールを正確に適用しながら、選択した方向に一度に 1 つのセルを繰り返し進めます。 の`steps`カウンタは、その移動で通過した有効なセルの数を追跡します。 

重要な点は、ループ内のイベントの順序です。 キーは、ドアのロジックが評価される前に、セルに入るとすぐに取得されます。 その後、現在のキー数を使用してドアが処理され、ドアが開いた瞬間にキーが消費されることが保証されます。 

境界チェックと壁チェックは、これらのセルに入る前に動きが停止するため、無効なインデックス作成を防ぐために最初に実行されます。

 ## 特殊なケース

 重要なケースの 1 つは、同じ方向のドアの直前に鍵が置かれている場合です。 アルゴリズムは、ドアが評価される前にキーが収集されていることを確認する必要があります。 たとえば、連続して`S K L #`、右に移動すると最初に鍵が回収され、鍵の数が増えて初めてドアを開けることができます。 実装では、セルの内容を順番に処理し、移動が継続するかどうかを判断する前に状態を更新することで、これを強制します。 

もう 1 つのエッジ ケースは、利用可能な最後のキーがドア セル上で正確に消費される場合です。 消費は入った瞬間に行われるため、ドアは開いているとみなされる必要があります。 シミュレーションでは、ドアに遭遇するとすぐにキーの数を減算し、事前に利用可能なキーがない場合にのみ停止することでこれを処理します。 

最後のエッジケースは境界停止です。 次のセルがグリッドの外側にある場合、その無効なセルは歩数に加算されずに移動が停止します。 この実装では、グリッドにアクセスする前に境界をチェックし、行列の端でも正確さを保証します。
