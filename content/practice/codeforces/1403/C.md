 ## 解決策
 ## 実際に何が問題になっているのか

 間違った動作が何を意味するのか追跡してみましょう。 

入力：```
3 4
#.##
####
##..
```グリッド：```
#.##
####
##..
```4つしかない`#`セルの合計。 

しかし、出力は`9`これは、「セルごとに何かと隣接セルをカウントする」または「すべての 2x2 部分構造 / 隣接関係の寄与をカウントする」に疑わしいほど近いです。 これは、コードが単にセルを数えるのではなく、セルごとに追加の貢献を蓄積していることを強く示唆しています。`#`。 

非常に一般的なバグのパターンは次のとおりです。 

- 隣接する四角形または四角形を反復処理する
 - または重複を二重にカウントします
 - またはオブジェクトの代わりに貢献をカウントする

 ただし、最も単純かつ重要な観察は次のとおりです。 

> 期待される出力は、次の数にのみ依存します。`#`構造上ではなく、細胞です。 

したがって、「賢い」ロジック (DFS、コンポーネント拡張、隣接関係、エリア拡張など) は基本的に不要であり、過剰にカウントされます。 

## 根本原因

 以前のバージョンではおそらく次のようなことが行われます。 

- それぞれを数えます`#`- ただし、その周囲に拡張することもできます (例: 4 近傍または 8 近傍をチェックする)
 - または寄付金を複数回誤って合計した場合

 これにより、次のような誇張された結果が得られます`9`。 

修正方法は、**すべての派生ロジックを完全に削除**し、不変式を維持することです。 

> それぞれ`#`は答えにちょうど 1 を与えます。

 ## 正しい解決策 (ターゲットを絞った修正、同じアプローチ: セルの数)

 グリッドをスキャンしてカウントするという、意図したシンプルなアプローチを維持します。`#`。```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    ans = 0
    
    for _ in range(n):
        row = input().strip()
        # count directly, no extra logic
        ans += row.count('#')
    
    print(ans)

if __name__ == "__main__":
    solve()
```## これで問題が解決する理由

 - トラバーサルなし、近隣拡張なし、重複リスクなし
 - 各セルは 1 回だけ処理されます
 -`.count('#')`行ごとのリニアスキャンを保証します
 - 全体的な複雑さは最適なままです:`O(n*m)`## 複雑さ

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n・m) | 各セルは 1 回読み取られます。 
| スペース | お(1) | 余分な構造はありません |
