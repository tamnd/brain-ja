 ## 解決策
 ## 問題の理解

 いくつかの独立したシナリオが与えられています。 それぞれに多数の Cookie があり、各 Cookie はタイプに属し、消滅する期限があります。 ジャンは時間が経つとクッキーを食べたがります。クッキーを食べるたびに、すでに食べたクッキーの数に応じて次のクッキーまでの待ち時間が長くなります。 最初のクッキーはすぐに食べることができますが、2 番目のクッキーは最初のクッキーを食べてから 1 単位待つ必要があり、3 番目のクッキーは 2 番目のクッキーを食べてから 2 単位待つ必要があります。 ジャンがすでに食べている場合$k-1$クッキーを食べて、$k$- 回目$t$、そうすると時間内に次のものを食べることができません$t + (k-1)$。 

各クッキーは指定された時間に消えますが、ジャンはその時間にそれを食べることも許可されています。 同じ種類のクッキーが複数存在し、ジャンはそれらをいくつでも食べることができます。 目標は、Jan が少なくとも 1 回食べることができる異なる種類のクッキーの数を最大化することです。 

重要な問題は、より多くのクッキーを食べると将来の待ち時間が長くなり、後の締め切りを満たすことが難しくなるということです。 決定は、タイプが利用可能かどうかだけでなく、増加するコストのスケジュールの中で十分早めにスケジュールできるかどうかによって決まります。 

制約は、それに近いものが必要であることを意味します。$O(n \log n)$または$O(n \log m)$テストケースごとに。 まで$2 \cdot 10^5$すべてのサブセットを試したり、タイプごとにスケジュールを個別にシミュレートしたりするアプローチは遅すぎます。 ソートを行わずに型ごとの欲張りなシミュレーションを行った場合でも、二次的な動作のリスクが生じます。 

型に期限の異なる複数の Cookie がある場合、微妙なエッジ ケースが発生します。 間違った出来事を選択することが重要です。 

たとえば、タイプ 1 には時刻 1 と 100 の Cookie があり、タイプ 2 には時刻 2 の Cookie があるとします。将来のコストを考慮せずに、各タイプの可能な限り最も早い Cookie を貪欲に選択すると、時刻 1 でタイプ 1 を取得し、時刻 2 でタイプ 2 を取得する可能性があり、これは機能します。 ただし、タイプ 2 の期限が 2 ではなく 1 である場合、異なる順序付けが成功したとしても、タイプ 1 を選択すると、最初にタイプ 2 がブロックされます。 これは、可用性だけでなく、選択したタイプの順序についても考慮する必要があることを示しています。 

もう 1 つのエッジ ケースは、型に遅延 Cookie しかない場合です。 タイプが「存在」している場合でも、遅延コストが増加するため、シーケンスの非常に早い段階でスケジュールされている場合にのみ使用できる可能性があります。 

## アプローチ

 この強引なアイデアは、各型を独立して扱い、Jan が何らかの順序で型のどのサブセットを正常に選択できるかを決定しようとすることです。 タイプの固定サブセットについては、選択した各タイプに代表的な Cookie を割り当て、期限と増加する遅延ルールを考慮してそれらをある順序でスケジュールできるかどうかをシミュレートします。 

型のサブセットの数が指数関数的に増加するため、これはすぐにコストが高くなります。 たとえサブセットを修正したとしても、順序付けごとにシーケンス内の位置に応じて到着時間を再計算する必要があるため、実現可能性をチェックすること自体は簡単ではありません。 と$m$まで$5 \cdot 10^4$、これは不可能です。 

重要な観察点は、タイプごとに複数の Cookie が必要になることは決してなく、それ以前のものは柔軟性を低下させるだけであるため、タイプごとに最新の使用可能な期限候補のみを考慮するのが最適であるということです。 型を決定したら、それをサポートできる最適な Cookie のみを考慮します。 

ここで、問題は次のとおりです。できるだけ多くのタイプを選択したいのですが、選択した各タイプが期限制約に影響します。 選択すると$k$タイプがある場合は、それらに位置を割り当てる必要があります$1$を通して$k$、そして$i$- 番目に選択されたタイプは、最大でも一度に達成可能である必要があります$i(i-1)/2$加えて、スケジューリングからの基本的な変更が加えられますが、より単純に、段階的にシミュレーションします。$i$- 番目に選択されたクッキーは、遅延の合計に等しい時間に食べられます$0 + 1 + 2 + \dots + (i-1)$、つまり$(i-1)i/2$、時間 0 から開始すると仮定します。 

ただし、Cookie には任意の期限があるため、直接の実現可能性チェックが必要です。期限を増やして選択したタイプを並べ替える場合、その順序で割り当てたときに、累積的な遅延の増加の下でそれぞれのタイプが期限までに配置されることを確認したいと考えています。 

これは、可能な限り最善の期限でソートされたタイプを考慮するという、貪欲な戦略につながります。 すでに選択したタイプの数を維持します。 それぞれのタイプについて、含めることができるかどうかを確認します。 サイズが合えば$k$、次のタイプは遅延後に食べられます。$k$したがって、選択された期限が少なくとも現在のシーケンス長を考慮して食べられる時刻であるかどうかをテストします。 「はい」の場合は、それを含めます。 

各タイプを 1 つの値にまとめます。Jan はどのコピーを食べるかを選択できるため、達成可能な最良の期限は単にその Cookie の最大の期限になります。 次に、実行可能性の制約を維持しながら、これらの値の昇順でタイプを貪欲に選択します。

 ## アルゴリズムのチュートリアル

 まず入力を圧縮して、各タイプが 1 つの数値 (そのタイプのすべての Cookie の最大消失時間) で表されるようにします。 以前の Cookie は制約を厳しくするだけであるため、これにより、そのタイプを使用する可能性が最大限に高まります。 

1. すべての Cookie を読み取り、タイプごとに発生する最大期限を計算します。 これにより、問題は次から選択することに変わります。$m$それぞれの項目には期限が 1 つあります。 
2. すべてのタイプを、計算された期限によって降順でない順序で並べ替えます。 その理由は、累積的な食事の遅れが大きくなると、それらを遅らせても期限を超過するリスクが高まるだけであるため、最も制限の厳しいタイプに最初にコミットしたいということです。 
3. カウンタの初期化$k = 0$、これまでに選択に成功したタイプの数を表します。 
4. ソートされた期限のリストを繰り返し処理します。 種類ごとに期限あり$d$、ジャンが次のクッキーを食べる時間を計算します。 その時間は現在の累積待機コストであり、次の値となります。$k(k+1)/2$正確に追跡されていれば、次の利用可能な時刻を段階的に維持することで完全な式を避けることができます。 次回の所要時間を超えない場合$d$、このタイプと増分を受け入れます$k$。 それ以外の場合はスキップします。 

重要な考え方は、ある型を受け入れると将来の遅延が増加するだけであるため、ある型が実現可能性テストに失敗すると、その後は決して実現不可能になるということです。 

### なぜ効果があるのか

 どの時点でも、アルゴリズムは、制約に違反することなく、期限の昇順にスケジュールできる、すでに選択されたタイプのセットを維持します。 期限で並べ替えることにより、新しいタイプを検討するときに、実行可能なすべての選択の中でのその位置について、可能な限り最小の成長状態に対してテストすることが保証されます。 型がこの順序付けの最も早い位置に収まらない場合、それを後のどこかに挿入しても、必要な待ち時間が増加するだけであり、実行可能性はさらに低くなります。 これにより、貪欲な受け入れが将来の実現可能性の決定を決して無効にしないことが確立され、型をスキップすることは安全です。なぜなら、それを含む有効な解決策は、以前に受け入れられた型をより厳しい期限で置き換える必要があり、ソート順序の最適性に矛盾するためです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []
    for _ in range(t):
        m, n = map(int, input().split())
        
        # best deadline per type
        best = [0] * (m + 1)
        
        for _ in range(n):
            a, ti = map(int, input().split())
            if ti > best[a]:
                best[a] = ti
        
        deadlines = [best[i] for i in range(1, m + 1)]
        deadlines.sort()
        
        k = 0
        current_time = 0
        
        for d in deadlines:
            # if we take this as (k+1)-th cookie, it is eaten at current_time + k
            if current_time + k <= d:
                current_time += k
                k += 1
        
        out.append(str(k))
    
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```圧縮ステップにより、タイプごとに最も許容度の高い Cookie のみを追跡することが保証されます。 ソートされた期限の配列により、貪欲な選択に必要な構造が作成されます。 変数`k`そして`current_time`累積遅延効果をエンコードします。次のタイプを選択するとき、待機コストはすでに選択されているタイプの数だけ増加します。 

条件`current_time + k <= d`次のクッキーが消える前に配置できるかどうかをチェックします。次の食事時間は、現在の累積遅延時間と、クッキーをその位置に配置することによって誘発される追加の遅延時間に加算されるためです。`k+1`。

 ## 特殊なケース

 多くのタイプが同じ期限を共有し、累積遅延がそれを超える前に少数のタイプしか選択できない場合、微妙なケースが発生します。 入力の場合:```
1
4 4
1 1
2 1
3 1
4 10
```圧縮された期限は、$[1, 1, 1, 10]$。 このアルゴリズムは、最初にコスト 0 で最初のタイプを取得し、すぐに 2 番目のタイプを試行しますが、次に必要な時間が 1 である一方で、current_time + k が 1 (期限に等しく、まだ許可されている) になるため、失敗します。 2 種類を選択した後、次の試行には 1 を超える時間 2 が必要になるため、タイトなグループから 2 種類しか選択できません。 締め切り10の最終タイプはオーダー次第で前後して受け付けますが、大きいのできついものがなくなってから必ず入ります。 

これにより、アルゴリズムが緩和された制約の恩恵を受ける前に、初期の制約が正しく飽和していることが確認されます。
