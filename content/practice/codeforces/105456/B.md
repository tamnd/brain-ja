 ## 解決策
 ## 問題の理解

 SMS メッセージを表す小文字の文字列が与えられます。 ペドロは正確に削除して短くする必要がある$n - k$残りの文字の相対的な順序を変更せずに維持します。 考えられるすべての長さの部分列の中で$k$、辞書編集的に最小のものを必要とします。 

重要な制約は、文字の順序変更は許可されておらず、削除のみが許可されていることです。 したがって、タスクは並べ替えや並べ替えではなく、辞書編集順に基づいて最適な部分列を選択することです。 

制約$n \le 100000$テスト ケースごとに、すべてのサブシーケンスを試行したり、指数関数や二次関数の探索を使用したりするソリューションは直ちに除外されます。 たとえ$O(nk)$両方が大きくなる可能性がある場合、動的プログラミングのアプローチは遅すぎます。 私たちは、各キャラクターがほぼ一定の償却時間で決定されるという貪欲な構築を強いられています。 

メッセージに長く減少する文字や繰り返しの文字が含まれる場合、微妙なエッジ ケースが発生します。 たとえば、次のような文字列では`dcba`と$k = 2$、将来の実現可能性を考慮せずに、常に次の利用可能な最小のキャラクターを選択する単純な戦略は失敗する可能性があります。これは、あまりに積極的に選択しすぎると、残りのスロットに残されるキャラクターが少なすぎる可能性があるためです。 

次の場合には別の問題が発生します。$k$非常に小さいです、例えば$k = 1$、ここで、答えは単に文字列全体の最小文字です。$k = n$、削除する必要はありません。 正しいアルゴリズムは、特殊なケース エラーを発生させることなく、これらの境界ケースを自然に処理する必要があります。 

## アプローチ

 強引なアイデアは、長さのすべてのサブシーケンスを生成することです。$k$、辞書編集上の順序を計算し、最良のものを採用します。 これはすべての有効な答えを探索するので概念的には正しいですが、部分列の数は次のようになります。$\binom{n}{k}$、中程度の場合でも天文学的に大きくなります$n$。 のために$n = 100000$、これはまったく不可能です。 

より構造化された動的プログラミングのアプローチでは、次のことが定義される可能性があります。$dp[i][j]$長さの最適な部分列として$j$最初から$i$文字。 これは論理的に機能しますが、文字列を繰り返し保存または比較する必要があるため、少なくとも$O(nk)$移行と潜在的に$O(k)$遷移ごとの比較は制限をはるかに超えています。 

重要な観察は、サブシーケンスの早い段階で小さな文字が大きな文字を置き換えることができることが確立されたら、文字を再考する必要がないということです。 左から右に答えを構築する場合、必要なのは、すべての位置で、有効な長さのサブシーケンスを完成できる最小の文字を選択することだけを保証することです。$k$。 

これは当然、貪欲な単調構造につながります。文字列をスキャンして、現在最適なプレフィックスを表す構造を維持し、後で選択できるものよりも悪い文字を削除します。 これはまさに古典的な「数字を削除 / 固定長の辞書編集上最小のサブシーケンス」パターンであり、スタックのような構造を使用して効率的に実装されています。

 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(k) | 遅すぎる |
 | 最適な貪欲スタック | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 現在選択されているサブシーケンスを表すスタックを使用して答えを構築します。 

1. 空のスタックを初期化し、まだ削除する必要がある文字数のカウンターを設定します。$n - k$。 これにより、柔軟性が追跡されます。削除するたびに、辞書編集上の順序を改善できます。 
2. 文字列の文字を左から右に繰り返します。 各文字で、現在の部分的な回答内の以前の文字を置き換えることができるかどうかを検討します。 
3. スタックが空ではありませんが、スタック内の最後の文字が辞書編集的に現在の文字より大きく、使用可能な除去がまだあるので、スタックをポップします。 このステップにより、より良い文字がより早く出現する可能性がある場合に、より悪い文字を保持しないことが保証され、辞書編集上の順序ができるだけ早く改善されます。 
4. 現在の文字をスタックにプッシュします。 これにより、現在の候補サブシーケンスが拡張されます。 
5. 許可された削除がなくなってもスタックに余分なキャラクターが残っている場合、それ以上削除することはできないため、プッシュを続け、後で必要に応じてトリミングします。 
6. すべての文字を処理した後、スタックには次の文字が含まれる可能性があります。$k$すべての除去を最適な位置で使用しなかった場合のキャラクター。 その場合、スタックを最初のスタックまで切り詰めます。$k$文字。 
7. 結果として得られるスタックは、辞書編集上の最小の長さの部分列です。$k$。 

これが機能する理由は、文字を削除するたびに、厳密に小さい文字が後で表示される場合にのみ削除し、長さを完了するのに十分な文字がまだ残っているためです。$k$順序。 これにより、常に可能な限り早期に辞書編集上の順序を改善しながら、有効な答えの形成を妨げることがなくなることが保証されます。 

### なぜ効果があるのか

 スキャンのどのプレフィックスでも、スタックは、長さまで拡張できるという制約の下で、処理された文字を使用して可能な限り最良のサブシーケンスを表します。$k$。 貪欲な削除ステップでは、削除バジェットが修正を許可する場合、前の文字が後の文字より大きくならないという意味で、スタックが単調であるという不変条件が維持されます。 各文字は最大 1 回プッシュおよびポップされるため、すべての決定は局所的に最適であり、辞書編集上の順序とグローバルに一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        s = input().strip()

        remove = n - k
        stack = []

        for c in s:
            while stack and remove > 0 and stack[-1] > c:
                stack.pop()
                remove -= 1
            stack.append(c)

        # If still have removals left, remove from end
        # (only needed if no better pops occurred)
        while remove > 0:
            stack.pop()
            remove -= 1

        print("".join(stack[:k]))

if __name__ == "__main__":
    solve()
```実装はスタックベースの貪欲な構造に直接続きます。 変数`remove`削除がまだ許可されている数を追跡します。 内部の while ループは重要な部分です。現在の文字よりも大きい以前の文字を削除することで、辞書編集上の改善を強制します。 

場合によっては、特に文字列がすでに増加しているか部分的に増加している場合、スキャン中に十分な有益な削除がトリガーされないため、最後のトリミング手順が必要です。 この手順を行わないと、スタックが長くなる可能性があります。$k$。 

スライス`stack[:k]`すべての貪欲な決定の後でも、最終出力が必要な長さを厳密に尊重するようにします。

 ## 特殊なケース

 重要なエッジケースは、文字列が厳密に減少している場合です。たとえば、`dcba`と$k = 2$。 アルゴリズムは、より小さなキャラクターが表示され、除去予算が利用可能である間継続的にポップし、安定した最小のプレフィックスを生成します。 

入力：```
4 2
dcba
```実行:

 スタックは次のように進化します`d -> c -> b`、小さな文字が到着するとすぐに、大きなプレフィックスを破棄するために削除が使用されます。 最終的なトリミングにより、正確に 2 文字が残り、次の結果が得られます。`ba`、これは長さ 2 のすべての部分列の中で辞書編集上最小です。 

別のエッジケースは、次のようにすでにソートされた入力です`abcde`と$k = 3$。 スタックはすでに増加しているため、除去はトリガーされず、最後の切り捨ては単に最初の 3 文字を取得し、`abc`これは、後で含めると辞書編集上の順序が悪化するため、最適です。 

これら 2 つのケースでは、積極的な削除が必要な場合と、削除しない方が有益な場合の両方にアルゴリズムが正しく適応していることが確認されています。
