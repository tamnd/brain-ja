 ## 解決策
 ## 問題の理解

 いくつかのチェックアウト列があるスーパーマーケットをシミュレートしています。 顧客は到着し、キューを選択し、順番に処理されるまでそのキューに留まります。 重要な展開は心理的なものです。顧客は、選択したキューで待っているときに、他のキューのアクティビティを観察すると、具体的には、顧客が出入りしている他のキューが「見える」場合に不満を感じます。 

入力はイベントの時系列シーケンスです。 一部のイベントは顧客を特定のキューに挿入し、他のイベントは先頭の顧客をキューから削除します。 キューは標準の FIFO 構造のように動作します。 すべての顧客は 1 回だけ割り当てられ、削除は常にキューの先頭に影響します。 

課題は、待機中にこの「可視」状態を経験した顧客を特定することです。 出力は、そのような顧客の数とその識別子がソートされた順序で続きます。 

制約は十分に大きいため、どのソリューションでもイベントを線形時間で処理する必要があります。 最大 100,000 人の顧客と 200,000 のイベントを抱えている場合、キューを再スキャンしたり、顧客ごとの可視性をシミュレートしたりするアプローチは遅すぎます。 正しいソリューションでは、状態を増分的に維持し、イベントごとの情報を O(1) または O(log n) 時間で更新する必要があります。 

アクティブなキューが 1 つだけの場合、またはイベントが 1 つのキューと多数のキューの間で交互に発生する場合、微妙なエッジ ケースが発生します。 このような場合、キューが変更されるたびに悲しみをマークする単純な実装では、監視している顧客がその時点で実際に待っているかどうかが考慮されないため、カウントが過剰になる傾向があります。 

## アプローチ

 直接シミュレーションのアプローチでは、すべてのキューを明示的に追跡し、顧客ごとに待機間隔全体をシミュレートします。 その間隔中に、他のキューにイベントがあるかどうかを確認します。 これには、顧客ごとに多くのイベントをスキャンする必要があり、最悪のケースとして O(n²) が発生し、遅すぎます。 

重要な観察は、顧客が積極的に待っている間に別のキューに少なくとも 1 つのイベントが存在する場合にのみ、顧客が悲しむということです。 顧客ごとのタイムラインを追跡する代わりに、「キューアクティビティの変化」というグローバルな概念を維持し、これらの変化を現在待っている顧客に関連付けることができます。 

問題の構造からわかることは、いつでも、複数のキューがアクティブであるかどうか、および特定の顧客の待機間隔がキュー間アクティビティと重複しているかどうかだけを知る必要があるということです。 これにより、キューごとにカウンターを維持し、顧客が前にいるか待っているかを追跡するという問題が軽減されます。 

これにより、各イベントを 1 回処理し、キューの状態を更新し、影響を受ける顧客を即座にマークすることができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n²) | O(n) | 遅すぎる |
 | キュー追跡を使用したイベント スイープ | O(n + k) | O(n + k) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 各チェックアウト ラインのキュー構造を維持します。 各キューには顧客が到着順に格納されます。 これは実際の FIFO の動作を反映しています。 
2. 各キューが現在「アクティブ」であるかどうか、つまり少なくとも 1 人の顧客がいるかどうかを追跡するブール値またはカウンターを維持します。 
3. 空ではないキューの数を示すグローバル カウンタを常に維持します。 悲しみは待機期間中に複数のキューにアクティビティがある場合にのみトリガーされるため、これは重要です。 
4. 各顧客のステータス配列を維持して、顧客が現在待機しているかどうか、およびすでに悲しいマークが付けられているかどうかを示します。 
5. 挿入イベントを処理するときに、顧客を対応するキューにプッシュします。 このキューが空から空でない状態に移行した場合は、アクティブなキュー カウンターをインクリメントします。 
6. 削除イベントを処理するときに、キューの先頭をポップします。 削除された顧客が待機中で、その時点で少なくとも 1 つの他のアクティブなキューが存在する場合、その顧客を悲しいとマークします。 
7. 削除後、キューが空になった場合は、アクティブなキュー カウンタをデクリメントします。 
8. どのイベントでも、「待機間隔が終了」する唯一の顧客は除外されます。 したがって、継続的にではなく、除去時にのみ悲しみをチェックする必要があります。 

重要な不変条件は、待機中に少なくとも 1 つの他のアクティブなキューがあった場合、顧客がそのキューを離れる瞬間に 1 回だけ悲しくなるということです。 グローバル アクティブ キュー カウンターは、待機中にそのような干渉が発生する可能性があるかどうかを正確に要約します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque

def solve():
    n, k = map(int, input().split())

    queues = [deque() for _ in range(k + 1)]
    active = [0] * (k + 1)
    active_count = 0

    # track if a queue is currently non-empty
    # track customers in each queue
    sad = [False] * (n + 1)

    for _ in range(2 * n):
        tmp = list(map(int, input().split()))
        typ = tmp[0]

        if typ == 1:
            _, p, f = tmp
            queues[f].append(p)
            if not active[f]:
                active[f] = 1
                active_count += 1

        else:
            _, f = tmp
            p = queues[f].popleft()

            # if more than one queue active, this customer saw activity elsewhere
            if active_count > 1:
                sad[p] = True

            if not queues[f]:
                active[f] = 0
                active_count -= 1

    res = [i for i in range(1, n + 1) if sad[i]]
    print(len(res))
    if res:
        print(*res)

if __name__ == "__main__":
    solve()
```入力を読み取った後、挿入と削除が一定時間になるように、各キューは両端キューを使用してモデル化されます。 active 配列は、キューに現在顧客が含まれているかどうかを追跡し、active_count は空ではないキューの数を維持します。 各削除イベントは顧客が離れていくことを直接識別し、その時点で複数のキューがアクティブかどうかに基づいて顧客が悲しんでいたかどうかを判断します。 

重要な点は、長期にわたる顧客ごとの可視性を決してシミュレートしないことです。 代わりに、プロセス全体をイベントベースの状態変化に圧縮します。

 ## 特殊なケース

 主なエッジケースは、キューが 1 つだけ使用される場合です。 この状況では、アクティブなキュー カウンタが 1 を超えることはないため、顧客が悲しいとマークされることはありません。 条件が次のとおりであるため、アルゴリズムはこれを正しく処理します。`active_count > 1`は決して真実ではありません。 

Another edge case occurs when a queue becomes empty and then refills multiple times. The active counter correctly decrements and increments, ensuring that only simultaneous multi-queue activity contributes to sadness detection.
