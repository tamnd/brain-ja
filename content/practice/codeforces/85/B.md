 ## 解決策
 ## 問題の理解

 大使館を訪問する人はそれぞれ、連続する 3 つの段階を通過する必要があります。 最初のステージには、`k1`同一のウィンドウで、各サービスが取得する`t1`時間。 第二段階には、`k2`サービスタイムのある窓口`t2`、そして第 3 段階では、`k3`サービスタイムのある窓口`t3`。 

人`i`時間通りに到着する`ci`。 その瞬間から第 3 段階が終了するまで、彼らは大使館内に残ります。 ステージの順序が維持され、一度に複数の人を担当するウィンドウがない限り、各人が各ステージに入るタイミングを正確に決定することができます。 

目標は、合計待ち時間や平均待ち時間を最小限に抑えることではありません。 すべての人の最大滞在時間を最小限に抑えたいと考えています。 

時間通りに人が到着したら`c`そして時間通りに終わる`f`とすると、室内で過ごした合計時間は`f - c`。 このような最大値ができるだけ小さくなるように、すべてのキューを編成する必要があります。 

この制約により、時間単位の粒度でのシミュレーションが即座に除外されます。 到着時間は最大で`10^9`、サービス数も膨大になる可能性があります。`10^5`人々。 時間そのものに比例するアルゴリズムは不可能です。 

人数は最大でも`10^5`、周囲に何かを強く示唆しています`O(n log n)`あるいは多分`O(n log^2 n)`が予想されます。 ウィンドウ自体はいくつでもできるので、`10^9`また、アルゴリズムが実際に使用されるウィンドウのみを保存しない限り、各ウィンドウを明示的に表すこともできません。 

難しいのは、最大完了時間を最小限に抑えることと、すべての段階で全員をできるだけ早く完了させることを貪欲に進めることと同じではないということです。 単純な実装では、ダウンストリームで誤ってボトルネックが発生する可能性があります。 

次の例を考えてみましょう。```
k1 = 2, k2 = 1, k3 = 1
t1 = 1, t2 = 100, t3 = 1
arrivals = [0, 0]
```両方の人がすぐにステージ 1 に入った場合、時間 1 にステージ 1 を終了します。その後、1 人はほぼずっと待機します。`100`ステージ 2 のタイムブロック。本当のボトルネックはステージ 1 ではなくステージ 2 です。 

多くの人が同時に到着する場合、別の微妙なケースが発生します。```
1 1 1
1 1 1
5
1 1 1 1 1
```正しい答えは、`7`、 ない`3`。 サービス自体は合計 3 ユニットしか必要としませんが、5 人目は開始するまでに 4 ユニット待ちます。 

よくある間違いは、各人の終了時間を個別に最小化することです。 それは必ずしも全員の最大滞在時間を最小限に抑えるわけではありません。 最適な戦略では、パイプラインのグローバルなバランスをとる必要があります。 

## アプローチ

 ブルートフォースの観点は単純明快です。 いくつかの候補の答えを推測するとします。`T`を意味します。`T`大使館内の時間単位。 

到着する人ごとに、`ci`、時間までに 3 つのステージすべてを完了する必要があります`ci + T`。 

すべての人に具体的な時間枠と時間を割り当てるスケジュールを明示的に検索してみることもできます。 完全な状態空間検索は即座に爆発的に行われます。 たとえステージの割り当てを貪欲に追跡したとしても、誰もが可能な限り多くのウィンドウの中から選択する可能性があります。 可能性の数は指数関数的に増加します。 

より構造化されたブルート フォース シミュレーションでは、人々を順番に処理し、常に各段階で最も早い利用可能なウィンドウに割り当てます。 これは、1 つの実現可能なスケジュールを計算する場合には機能しますが、最大滞在時間を最適化する場合には機能しません。 それでも、多くの可能なスケジュールまたは多くの可能な値を検索する必要があります。`T`。 

重要な観察は、固定の実現可能性です。`T`単調な構造を持っています。 

誰もがそれ以上の出費をしないように全員のスケジュールを設定できれば、`T`内部に時間がかかる場合は、より大きな値でも機能します。 これは、答えに対する二分探索を即座に示唆します。 

ここで問題は次のようになります。 

修正の実現可能性を確認できますか`T`効率的に？ 

到着する人にとっては、`ci`、3 段階のプロセス全体が間隔内に収まる必要があります。`[ci, ci + T]`。 

到着日から前倒しでスケジュールを立てるのではなく、締め切りから逆算してスケジュールを立てる方がはるかに簡単です。 

ある人が、ある時点でステージ 3 を開始するとします。`x`。 それから：```
x + t3 <= ci + T
```それで：```
x <= ci + T - t3
```同様に、ステージ 2 が次から始まる場合、`y`:```
y + t2 <= x
```ステージ 1 が開始される場合`z`:```
z + t1 <= y
```これにより、可能な最新の開始時刻のチェーンが作成されます。 

最適な実現可能性戦略は、貪欲なバックワード スケジューリングです。 私たちは最も遅い到着者から最も早い到着者まで人々を処理し、常に各ステージを可能な限り遅い時間帯にいくつかの利用可能なウィンドウに配置します。 

なぜこれが役立つのでしょうか? 後でスケジュールを設定すると、締め切りが厳しい人のために早い時間枠が確保されるからです。 

各ステージでは、すべてのウィンドウが、占有間隔が固定長のブロックであるマシンのように動作します。 逆方向にスケジュールした場合、各ウィンドウは単に最新の未使用の終了点を維持します。 

これにより、問題は優先キューを使用したクリーンな貪欲チェックに変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数関数的またはそれ以上 | 巨大な | 遅すぎる |
 | 最適 | O(n log n log 答え) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 実行可能な最小の答えを二分探索する`T`。 

多少なら`T`が機能する場合、すべての大きな値も機能するため、実現可能性は単調です。 
2. 修正の実現可能性チェックを実装する`T`。 

到着時間が最も長い人から最も短い人へ、逆の順序で人々を処理します。 
3. 各ステージの利用可能時間を維持します。 

ステージ 3 では、最初はすべてのウィンドウが将来にわたって永久に無料になります。 各ウィンドウは、新しいサービス ブロックが終了する可能性がある最新の時刻で表されます。 
4.到着時間のある方へ`ci`、可能な最新の仕上げ制約を計算します。 

ステージ 3 は遅くとも以下の時間までに開始する必要があります。```
ci + T - t3
```5. ステージ 3 のすべてのウィンドウの中で、現在利用可能な時間が最大であるが、それでも実行可能なウィンドウを選択します。 

時間まで窓口が空いている場合`a`で終了するステージ 3 を配置できます。`min(a, ci + T)`。 

開始は次のようになります。```
end - t3
```私たちはサービスを可能な限り遅くに配置します。 
6. ステージ 3 を修正した後、ステージ 2 の最新の可能な配置を導き出します。 

ステージ 2 はステージ 3 の開始時刻までに終了する必要があります。 
7. 同じ貪欲な配置をステージ 2 に対して繰り返し、次にステージ 1 に対しても繰り返します。 
8. いずれかの段階で、必要なブロックを収容できるウィンドウがない場合は、`T`実行不可能です。 
9. すべての人が正常にスケジュールされた場合、`T`実現可能です。 
10. 実行可能な最小値まで二分探索が続行されます。`T`が見つかりました。 

### なぜ効果があるのか

 貪欲な不変条件は、何人かのサフィックスをスケジュールした後、残りの未使用スロットができるだけ早くなるということです。 新しいサービス ブロックを常にできるだけ遅く配置することで、将来必要になる可能性のある初期の容量の無駄を回避します。 

到着が遅い人の有効期限は厳しいため、到着順に人を処理することが重要です。 早めに到着する人を先にスケジュールすると、後の到着者が必要とする遅い時間の枠を占有してしまう可能性があります。 

逆方向貪欲戦略は、交換引数によって最適化されます。 実行可能なスケジュールは、残りの人々の実行可能性を損なうことなく、割り当てられた各ブロックをできるだけ遅くするスケジュールに変換できます。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def possible(T, k, t, arrivals):
    n = len(arrivals)

    # For each stage we store available ending times.
    # Negative values simulate max-heaps.
    heaps = []

    INF = 10**30

    for cnt in k:
        h = [-INF] * cnt
        heapq.heapify(h)
        heaps.append(h)

    for c in reversed(arrivals):
        latest = c + T

        for stage in range(2, -1, -1):
            duration = t[stage]

            avail = -heapq.heappop(heaps[stage])

            end_time = min(avail, latest)

            start_time = end_time - duration

            if start_time < c:
                return False

            heapq.heappush(heaps[stage], -start_time)

            latest = start_time

    return True

def solve():
    k = list(map(int, input().split()))
    t = list(map(int, input().split()))

    n = int(input())
    arrivals = list(map(int, input().split()))

    lo = sum(t)
    hi = 10**18

    while lo < hi:
        mid = (lo + hi) // 2

        if possible(mid, k, t, arrivals):
            hi = mid
        else:
            lo = mid + 1

    print(lo)

solve()
```二分探索は次から始まります`sum(t)`なぜなら、待ち時間がゼロであっても、全員が少なくとも合計のサービス時間を大使館内で過ごさなければならないからです。 

実現可能性機能はソリューションの中核です。 各ヒープは 1 つのステージのすべてのウィンドウを表します。 今後ウィンドウが空いたときを保存するのではなく、最新の未使用時間を保存します。その前に、逆方向にスケジュールするときに別のサービス ブロックを配置することができます。 

現在、ステージに利用可能時間が設定されているとします。`A`。 つまり、このウィンドウに次に割り当てられるサービス ブロックは、遅くとも次の時間までに終了する必要があります。`A`。 長さのブロックを割り当てると`d`、その始まりは次のようになります`A - d`であり、このウィンドウでの今後の割り当ては、その開始前に終了する必要があります。 

微妙な実装の詳細が更新されています`latest`after every stage. いつかステージ3が始まると`x`、ステージ 2 は までに終了する必要があります`x`、したがって、その最新の終了時刻は正確になります。`x`。 

もう 1 つの簡単な間違いは、サービス間隔は人の到着時刻の完全に後でなければならないことを忘れていることです。 小切手:```
if start_time < c:
```不可能なスケジュールを検出します。 

すべての算術演算では Python 整数が使用され、当然、大きな値も安全に処理されます。

```アルゴリズムは逆方向にスケジュールを設定します。 最後の人が可能な限り最も新しい間隔を占め、次に 4 番目の人が次の最も新しい間隔を占め、以下同様に続きます。 すべての割り当てにより、将来の柔軟性が最大限に保たれます。 結果として得られる答えは、`7`、これは実際のパイプラインの長さに待機を加えたものと一致します。
