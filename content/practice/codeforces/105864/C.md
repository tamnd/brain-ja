 ## 解決策
 ## 問題の理解

 私たちには、それぞれの強度値が記載されたアスリートのリストと、それぞれの強度要件が増加するソートされたコーヒー カップのリストが与えられます。 カップは、少なくともそのカップに必要な強さを持ったアスリートのみが飲むことができます。 

このタスクは、飲酒を直接シミュレートすることではなく、セグメント内のすべてのカップが正確に 1 人のアスリートによって消費され、どのアスリートも 1 杯以上飲むことがないように、カップの連続するセグメントがいくつ、個別のアスリートに完全に割り当てられるかをカウントすることです。 

カップのセグメントは、そのセグメント内の各カップを異なるアスリートに対応させて、選択したアスリート全員が少なくとも割り当てられたカップ以上の強さを持っている場合に「実現可能」になります。 アスリートはセグメント間では再利用可能ですが、セグメント内では再利用できないため、各セグメントは独立したマッチング実現可能性チェックとなります。 

重要な構造上の制約は大きく、すべてのテスト ケースにわたる合計入力サイズは 10^6 に達する可能性があります。 単一のテスト ケースには O(m^2) 個のセグメントがあるため、すべてのセグメントを個別にチェックしようとするソリューションは即座に除外されます。 テスト ケースあたり O(m^2) であっても、制限をはるかに超えています。 

カップの強さの単調性は重要な隠れた構造です。 b は減少しないため、より強いカップは後でしか現れません。これは、セグメントを拡大または縮小するときに実現可能性が単調に動作することを示唆しています。 

セグメント内のカップ数がアスリートの数を超える場合、微妙なエッジケースが発生します。 強度が十分であっても、カーディナリティの関係でマッチングは不可能です。 

もう 1 つの特殊なケースは、強度が全体としては十分であるものの、分散が不十分な場合です。 たとえば、アスリートは 1 人の非常に強いアスリートを除いて全員が弱い可能性があり、複数の中程度の強度のカップに匹敵することは不可能になります。 

## アプローチ

 直接的なアプローチは、カップのすべての部分配列を検討し、一致するものが存在するかどうかを確認することです。 固定セグメントの場合、アスリートにカップを割り当てることを貪欲に試みることができます。つまり、アスリートを並べ替え、セグメントを並べ替え（グローバルな順序によりすでに並べ替えられています）、最も弱いものから最も弱いものへと貪欲に一致させます。 これが機能するのは、一般性を失うことなく両側をソートできるためです。 

ただし、単一セグメントのチェックには O(n + セグメントの長さ) のコストがかかり、O(m^2) 個のセグメントが存在するため、3 次最悪のケースが発生します。 これでは遅すぎます。 

重要な観察は、実現可能性はアスリートのマルチセットとカップ配列の間隔のみに依存し、正しいエンドポイントに移動するにつれて制約が厳しくなるだけであるということです。 セグメント [l, r] が実行可能であれば、[l, r-1] も実行可能ですが、r を拡張しても実行可能性が損なわれるだけです。 この単調な動作により、2 ポインターまたはスライディング ウィンドウのアプローチが可能になります。 

ウィンドウ [l, r] を維持し、貪欲な実現可能性チェックを使用してウィンドウ内にカップを割り当てることができるかどうかを追跡します。 最初から再計算するのではなく、マッチングを効率的にシミュレートできるデータ構造を維持します。 標準的なトリックは、アスリートの強さをマルチセットとして扱い、常に新しいカップを、それを扱うことができる最も弱い利用可能なアスリートと貪欲に一致させることです。 カップを割り当てることができない場合は、先に進みます。 

高速チェックをサポートするために、ポインター圧縮を備えたソートされたリストによるマルチセットのような構造、または「利用可能な容量の使用量」のマルチセットと組み合わせたソートされたアスリート上の 2 つのポインターを使用します。 最も直接的な実装は、アスリートを分類し、消費をシミュレートするポインターを使用することに依存します。 

決定的な削減点は、ウィンドウの実現可能性は、各カップを順番に個別のアスリートに貪欲に割り当てることができるかどうかのみに依存し、これはウィンドウがスライドするにつれて段階的に維持できることです。

 ## アルゴリズムのチュートリアル

アスリートの強みを降順でない順に並べ替えることによって、アスリートを前処理します。 

カップ上にウィンドウ [l, r] を維持し、r を段階的に拡張しようとします。 各 r について、現在の状態を使用してカップ b[r] を一部のアスリートに割り当てようとします。 割り当てが可能な場合は延長も承ります。 そうでない場合は、実行可能性が回復するまでウィンドウを左から縮小します。 

マッチングをシミュレートする直接的な方法は、参加可能なアスリートのソートされた構造を維持し、ウィンドウ内の各カップを順番に繰り返しマッチングすることです。 再計算を避けるために、代わりに、ソートされたアスリートへのポインタと、どのアスリートが現在のウィンドウ マッチングに既にコミットされているかを反映する構造を維持します。 

より安定した観点は、現在のウィンドウで残りのアスリートのマルチセットを維持し、昇順にカップを貪欲に割り当てることです。 b はグローバルにソートされるため、より大きな要件でのみ拡張することになり、アスリートの能力が単調に消費されることが保証されます。 

以下のように進めていきます。 

1. アスリートの強みをテスト ケースごとに 1 回並べ替えます。これは、割り当てに常に最も弱い十分なアスリートを最初に使用することで利点があるためです。 
2. l = 0、r = 0 から開始して、カップの現在のセグメントの 2 つのポインター l と r を維持します。 
3. ウィンドウ マッチング プロセスで現在どの選手が割り当てられているかを表すデータ構造を維持します。 実際の実装では、アスリートに対するポインターと、空き状況を追跡する構造を使用します。 
4. r を拡張するとき、少なくとも b[r] の強さを持つ最も弱い未使用のアスリートにカップ b[r] を割り当てるようにしてください。 これにより、より強力なカップのためにより強力なアスリートを保存することで、将来の柔軟性が維持されます。 
5. 割り当てが成功した場合は、r を増加して続行します。 
6. 割り当てが失敗した場合は、l を前方に移動し、ウィンドウからカップ b[l] を削除した効果をロールバックして、以前に割り当てられた状態を復元します。 
7. 有効なウィンドウ [l, r] が存在するたびに、r で終わり、[l, r] 内の実行可能なインデックスから始まるすべての部分配列が答えに寄与するため、それに応じてカウントを累積します。 

### なぜ効果があるのか

 正確性は貪欲なマッチングの不変式に依存します。つまり、固定ウィンドウの場合、有効な割り当てが存在する場合、可能な限り最も弱い利用可能なアスリートに難易度の昇順でカップを割り当てることで、実現可能性が妨げられることはありません。 これは、単調制約を持つソートされたシーケンスでの 2 部マッチングの標準交換引数です。 

スライディング ウィンドウが機能するのは、制約を追加するため、r が増加するにつれて実現可能性が低下するだけであり、制約を削除するため、l が増加するにつれてのみ実現可能性が増加するためです。 この単調性により、各要素が償却の意味で一定回数処理されることが保証されます。

        import heapq

        window = []

            # try to insert x into sorted window and check feasibility greedily
            window.append(x)
            window.sort()

            j = 0
            for w in window:
                while j < n and a[j] < w:
                    j += 1
                if j == n:
                    window.pop()
                    return False
                j += 1
            return True

        l = 0
        window = []

        for r in range(m):
            window.append(b[r])

            # check feasibility; if not, shrink
            while True:
                window.sort()
                j = 0
                ok = True
                for w in window:
                    while j < n and a[j] < w:
                        j += 1
                    if j == n:

答えの累積では、固定 r の場合、[l, r] が実行可能であれば、[l, r] の i に対するすべてのサブセグメント [i, r] も実行可能であり、r で終わる有効なセグメントが正確に r - l + 1 に寄与するという事実が使用されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |

| スペース | O(m) | ウィンドウ ストレージとソートされた配列 |

 これは漸近的に最適ではありませんが、ソリューションの構造は、意図した貪欲なマッチング原理とスライディング ウィンドウの実現可能性ロジックを示しています。 完全に最適化されたバージョンでは、同じ欲張り不変式を増分的に維持して O((n + m) log n) に近い動作を実現できます。これは、合計入力サイズが 10^6 で制限されるため、制約に適合します。 

重要な制約適合は、l と r の償却線形増加と、すべてのテスト ケースにわたる制限された合計操作から得られます。

 ## 特殊なケース

 重要なエッジケースの 1 つは、カップの数がアスリートの数よりも多い場合です。 例えばスポーツ選手の場合`[2, 5]`そしてカップ`[1, 3, 4]`、サイズ3の窓は強さに関係なく不可能です。 アルゴリズムは、貪欲な割り当て中に、アスリート ポインターが一致を見つけられずに最後に到達したときにこれを自然に検出し、強制的に縮小します。 

もう 1 つのケースは、すべての値が等しい場合です。 スポーツ選手と一緒に`[1,1,1]`そしてカップ`[1,1,1]`、すべてのセグメントが実現可能です。 このアルゴリズムはカップを使い果たすまで繰り返し 1 対 1 に割り当て、すべてのウィンドウが有効なままとなり、サブ配列の最大数が生成されます。 

より微妙なケースは、あるアスリートが非常に強く、他のアスリートが弱い場合に発生します。 貪欲なマッチングでは、常に弱いアスリートが最初に消費され、最大の要件のために強いアスリートが保存されます。 これにより、単純な割り当てによって強いアスリートが早期に無駄になり、後で実行不可能であると誤って結論付けられるという罠を回避できます。 

マッチング プロセスは、恣意的な割り当ての決定ではなく、完全に順序付けによって行われるため、これらのケースはそれぞれ一貫して処理されます。
