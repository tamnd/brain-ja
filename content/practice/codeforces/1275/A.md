 ## 解決策
 ## 問題の理解

 次の有向友情グラフが与えられています。$n$ユーザー。各ユーザーは他のユーザーを友達としてリストします。 重要なのは、友情が相互に保証されるわけではないということです。 ユーザーの場合$u$リスト$v$という意味ではありません。$v$リスト$u$。 

課題は、すべての「隠された友情」、つまりすべての順序付きペアを検出することです。$(u, v)$そのような$u$考慮します$v$友達だけど$v$考慮しない$u$友人です。 グラフ用語では、隣接リスト内で往復していないすべての有向エッジを探します。 

入力は基本的に、1 から 2 までの頂点を持つ有向グラフの隣接リスト表現です。$n$。 出力では、逆エッジが存在しないすべての有向エッジをリストし、そのようなエッジがいくつ存在するかをカウントする必要があります。 

以来$n \le 100$、エッジの総数は最大で約$n^2$、最大でも 10,000 です。 これは、隣接性をチェックするあらゆるソリューションで使用できるほど小さいものです。$O(1)$あるいは$O(n)$エッジごとに十分な速度になります。 ナイーブ$O(n^3)$アプローチも通過しますが、不要です。 

微妙な点は、各隣接リスト内には重複が存在しないということですが、リスト間の非対称性がまさに答えを定義するものです。 もう 1 つのエッジ ケースは、友達が 1 人もいないユーザーです。これは、発信される隠れたエッジを生成すべきではありませんが、依然として他のユーザーのリストにターゲットとして表示される可能性があります。 

よくある間違いは、対称性を仮定したり、反対側のリストの存在を確認せずに 1 つの方向のみを確認したりすることです。 もう 1 つの間違いは、出力には同時に両方向に異なるユーザーのペアだけでなく、すべての非対称エッジを含める必要があることを忘れていることです。 

たとえば、ユーザー 1 が 2 をリストしているが、ユーザー 2 が 1 をリストしていない場合、(1, 2) を出力する必要があります。 ユーザー 2 が 1 をリストしているが、ユーザー 1 が 2 をリストしていない場合も、(2, 1) を出力します。 これらは独立した有向チェックであり、単一の無向の不一致ではありません。 

## アプローチ

 簡単なアイデアは、すべてのユーザーに対して反復処理を行うことです。$u$そしてすべての友人のために$v$で$u$のリストがあるかどうかを確認してください$u$に登場する$v$のリスト。 そうでない場合は、$(u, v)$隠れた友情です。 

ブルートフォース実装では、メンバーシップをチェックします。$v$線形検索を使用した のリストは次のようになります$O(n)$小切手ごとに。 各ユーザーは最大で$O(n)$各エッジのチェックを実行すると、全体の複雑さは次のようになります。$O(n^3)$最悪の場合。 と$n = 100$、これはまだ許容範囲内ですが、構造的に非効率であり、不必要です。 

主な改善点は、各隣接リストをハッシュ セットとして表現することです。 これにより、メンバーシップのクエリが平均的なクエリに変換されます。$O(1)$操作。 次に、すべての有向エッジに対して、$u \to v$かどうかを確認するだけです。$u \in adj[v]$。 そうでない場合は出力します。 

これが機能するのは、問題が有向グラフ内のエッジ存在クエリに帰着し、ハッシュベースのセットが定数時間のメンバーシップ チェックを提供し、三重の入れ子構造を二次スキャンに崩壊させるためです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース（リスト検索） |$O(n^3)$|$O(n^2)$| 受け入れられるが非効率的 |
 | ハッシュセットの検索 |$O(n^2)$|$O(n^2)$| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 各ユーザーの隣接リストを読み取り、セットとして保存します。 これにより、相互関係を検証する際のメンバーシップのチェックが迅速に行われます。 
2. 回答を保存するために空のリストを初期化します。 
3. ユーザーごとに$u$、すべての友人を反復処理します$v$彼らのセットで。 これにより、グラフ内のすべての有向エッジが列挙されます。 
4. ペアごとに$(u, v)$、どうかを確認してください$u$の隣接セットに存在します$v$。 そうでない場合は追加します$(u, v)$回答リストへ。 これにより、欠落している逆エッジが直接識別されます。 
5. すべてのユーザーを処理した後、保存されているペアの合計数を出力し、続いて各ペアを出力します。 

ステップ 4 の背後にある推論は、有向グラフの相反性がまさに条件であるということです。$u \in adj[v]$。 この条件が満たされない場合は、エッジが片側であることを意味します。 

### なぜ効果があるのか

 すべての候補ペアが次のとおりであるという不変条件を維持します。$(u, v)$入力内の明示的な隣接関係から直接得られます。 逆の関係が存在しない場合にのみ、ペアを出力します。 すべての有向エッジを正確に 1 回スキャンし、その逆エッジの存在を個別にチェックするため、隠れた友情を見逃すことはなく、有効な相互エッジが誤って含まれることもありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
adj = [set() for _ in range(n + 1)]

for i in range(1, n + 1):
    data = list(map(int, input().split()))
    cnt = data[0]
    for v in data[1:]:
        adj[i].add(v)

res = []

for u in range(1, n + 1):
    for v in adj[u]:
        if u not in adj[v]:
            res.append((u, v))

print(len(res))
for u, v in res:
    print(u, v)
```この実装では、メンバーシップのチェックが一定時間行われるように、各隣接リストをセットとして保存します。 外側のループはすべてのユーザーを反復し、内側のループは宣言された友達を反復します。 重要な決定は条件です`u not in adj[v]`、非対称要件を直接エンコードします。 

よくある落とし穴は、リストをセットに変換するのを忘れることです。これにより、二次ループ内の二次メンバーシップ チェックのパフォーマンスが静かに低下します。 もう 1 つの微妙な問題は、インデックス作成の一貫性を維持せずに生の入力リストを反復処理することです。これにより、off-by-one エラーが発生する可能性があります。 ここでは明示的に割り当てます`n + 1`ユーザーの番号付けがインデックスと一致するようにします。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import defaultdict

    n = int(input())
    adj = [set() for _ in range(n + 1)]

    for i in range(1, n + 1):
        data = list(map(int, input().split()))
        for v in data[1:]:
            adj[i].add(v)

    res = []
    for u in range(1, n + 1):
        for v in adj[u]:
            if u not in adj[v]:
                res.append((u, v))

    out = [str(len(res))]
    for u, v in res:
        out.append(f"{u} {v}")
    return "\n".join(out)

# sample
assert run("""3
1 2
1 3
1 1
""") == """3
1 2
2 3
3 1"""

# custom 1: no edges

""") == """0"""

 ## 特殊なケース

 重要なエッジ ケースは、ノードに発信エッジがない場合です。 たとえば、ユーザー 2 のリストが空の場合、発信ペアは生成されませんが、それでも他のユーザーの隠れた友情のターゲットになる可能性があります。 既存の隣接エントリを反復処理するだけなので、アルゴリズムはこれを自然に処理します。 

もう 1 つのケースは完全に非対称のチェーンで、すべてのエッジが前方を向いていますが、後方には決して向いていません。 すべての逆引き参照は失敗するため、アルゴリズムはすべてのエッジを出力します。 これにより、方向性が正しく保存され、暗黙的な対称性が想定されていないことが確認されます。 

最後の微妙なケースは、より大きなグラフに埋め込まれた相互ペアです。 たとえば、1 には 2 がリストされ、2 には 1 がリストされますが、1 には 3 もリストされ、3 には 1 がリストされない場合、(1,3) のみが表示されます。 このアルゴリズムは各有向エッジを独立して分離するため、無関係な相互エッジの存在が正確さを妨げることはありません。
