 ## 解決策

 ## 問題の理解

 概念的には 4 × 7 のグリッドとして配置された 28 個のブロックで構成される固定ストレージ システムが与えられています。 最初の 15 ブロックは元の画像部分であり、残りの 13 ブロックは、行と列の関係を通じて欠落したデータを回復できるように構築された冗長コードです。 

主要な構造ルールは、各行が他の 5 つを使用してその行から最大 2 つの欠落要素を回復できるコードのように動作し、各列が他の 3 つを使用して最大 1 つの欠落要素を回復できるコードのように動作することです。 リカバリは 1 つのステップではなく反復的です。ブロックがリカバリされると、そのブロックはすぐに他のブロックのリカバリに使用でき、行と列の制約は任意の順序で繰り返し適用できます。 

サイズ k のすべてのサブセットにわたって均一に、28 ブロックのうちちょうど k 個をランダムに削除します。 削除後、ルールを使用してできるだけ多くのブロックを復元しようとします。 このプロセスを通じてブロックを一意に決定できない場合、そのブロックは回復不可能とみなされます。 元の 15 個の画像ブロックのうち、一部のサブセットが回復不能になる可能性があります。 

15 枚の画像のうち少なくとも 1 枚が回復不能である確率と、回復不能な画像ブロックの予想数という 2 つの量を計算する必要があります。 

k が最大 28 であるため、入力サイズは見かけ上小さいですが、隠れた複雑さは組み合わせによるものです。サブセットの総数がわずか 2^28 であるため、サブセットに対する単純なシミュレーションは原理的にはまだ実行可能ですが、サブセットごとの単純な伝播ループで繰り返し実行すると、回復チェックが真のボトルネックになります。 

明らかではない問題は、回復が局所的ではないことです。 ブロックは、いくつかの連鎖的な推論の後にのみ回復可能になる場合があります。 行または列の制約を一度だけチェックする単純なアプローチでは、誤って失敗と判断されてしまいます。 

微妙なエッジ ケースとしては、最初はリカバリに有効な行や列が存在しないが、別の場所で 1 つのブロックをリカバリした後、システムが完全な再構築にカスケードされる場合があります。 もう 1 つは、すべての行と列が「ほとんど壊れている」ように見えても、行と列の制約が重なっているために一意に解決できる場合です。 

素朴な推論による失敗の例: 7 つのブロックの行で 2 つのブロックが欠落している場合、リカバリは不可能であると考えるかもしれませんが、列リカバリではまず欠落しているエントリが復元され、行欠落数が 1 に減り、行全体の再構築が可能になります。 

これらの依存関係により、システムを独立した制約ではなくクロージャ プロセスとして扱わざるを得なくなります。 

## アプローチ

 強引なアイデアは、削除された k 個のブロックのすべてのサブセットを列挙し、各サブセットの回復を個別にシミュレートすることです。 サブセットごとに、すべての行と列を繰り返しスキャンします。行に最大 2 つの欠落ブロックがある場合は常に、それらを再構築します。 列に最大 1 つの欠落ブロックがある場合は必ず、それを再構築します。 進行できなくなるまで繰り返し、どの画像ブロックが欠けているのかを確認します。 

これはルールを正確にモデル化しているため正しいですが、最悪の場合コストが高くなります。 がある$\binom{28}{k}$サブセットごとに、収束するまで 4 行 7 列を繰り返しスキャンします。 28 は小さいとはいえ、サブセットごとの反復伝播は自明ではありませんが、それでも管理可能な境界線にあります。 

本当の洞察は、k はサブセットを組み合わせて扱うのに十分小さいが、各サブセットを個別にシミュレートする代わりに、構造によってサブセットを分類できるということです。 このシステムは、固定された有限集合に対する線形閉包問題のように動作します。 最終的な状態は、回復を妨げる「禁止されたパターン」がどのサブセットに含まれているかによってのみ決まります。 どの削除パターンが失敗につながるかを特定したら、それらを組み合わせて数えて、確率と期待値の両方を直接計算できます。 

重要な単純化は、失敗はクロージャ プロセスで回復不能になる行または列が存在するかどうかによって完全に決定され、この条件は最終的に到達可能なクロージャ グラフ内の行および列ごとの削除数にのみ依存するということです。 これにより、問題はシミュレーションではなく、構造化された不正な構成に対する組み合わせカウントに帰着します。

 ## アルゴリズムのチュートリアル

 この問題を、一部の画像セルの完全な回復を妨げるサイズ k の削除セットを数えることとして再構成します。 

各イメージは、行と列の両方の制約によって十分な情報が伝達されない構造の一部でない限り、回復可能です。 すべての行と列の制約が相互作用するため、システムには単調な特性があります。つまり、ブロックが回復可能になると、そのブロックは永久に使用可能なままになります。 これにより、純粋に最小限のブロック パターンの観点から障害を特徴付けることができます。 

以下のように進めていきます。 

1. 削除によって行と列の両方の再構成パスから少なくとも 1 つのイメージが分離される「ブロッキング構成」が作成されない限り、すべてのイメージの復元が成功することがわかります。 
2. 各画像ブロックを、4 x 7 構造で属する行と列によって分類します。 冗長構造により、すべての行と列がパリティのような制約システムを形成します。 
3. どの行に少なくとも 3 つの生き残ったブロックがあり、どの列に少なくとも 4 つの生き残ったブロックがあるかをマークすることによって状態を定義します。 リカバリ ルールには十分な既知のエントリが必要であるため、伝播に使用できるのはこれらのみです。 
4. k 個の削除のサブセットごとに、すべての画像が最終的に少なくとも 1 つの使用可能な行チェーンまたは列チェーンでカバーされるかどうかを計算します。 シミュレーションする代わりに、少なくとも 1 つの画像を破壊するサブセットの数を数えます。 
5. 画像に対する包含を使用します。固定画像の行と列の両方がクロージャーによって回復可能にならない構成をカウントすることによって、固定画像が回復不能である確率を計算します。 
6. 対称性を利用します。すべての画像ブロックは構造上同等であるため、回復不可能な画像の予想数は、固定画像が回復不能である確率の 15 倍になります。 
7. 最後に、補数推論を使用して、有効な削除セットの総数からすべての画像が回復可能な削除セットを差し引いた数に対して、少なくとも 1 つの画像が失われる確率を計算します。 

### なぜ効果があるのか

 回復プロセスは単調かつ合流的です。任意の順序で行または列の再構築を適用しても、同じ最大のクロージャが得られます。 これは、すべての削除セットに、最終的に到達可能な一意のブロック セットがあることを意味します。 したがって、ダイナミクスをシミュレートする代わりに、最初の削除パターンが、クロージャにすべての画像ノードが含まれる構成のセットにあるかどうかを純粋に推論できます。 これにより、動的なプロセスが静的な組み合わせ分類に変わり、引数を数えても安定します。

import sys
input = sys.stdin.readline

def solve():
    k = int(input().strip())

    n = 28
    m = 15

    from math import comb

    total = comb(n, k)

    # Precompute all subsets of deletions as bitmasks
    # 28 is small enough for 2^28, but we only need k-sized subsets
    from itertools import combinations

    bad = 0
    exp_bad = 0

    # grid mapping: first 15 are images
    images = list(range(15))

    # predefine row/col structure
    # 4 rows, 7 cols
    def idx(r, c):
        return r * 7 + c

    # image positions (first 15 filled row-wise)
    img_set = set(range(15))

    for rem in combinations(range(28), k):
        rem_set = set(rem)

        alive = [i not in rem_set for i in range(28)]

        # simulate closure
        changed = True
        while changed:
            changed = False

            # row rules: each row of 7, if >=5 alive -> restore all
            for r in range(4):
                row = [idx(r, c) for c in range(7)]
                missing = [x for x in row if not alive[x]]
                if len(missing) <= 2:
                    for x in missing:
                        alive[x] = True
                        changed = True

            # column rules: each col of 4, if >=3 alive -> restore missing
            for c in range(7):
                col = [idx(r, c) for r in range(4)]
                missing = [x for x in col if not alive[x]]
                if len(missing) <= 1:
                    for x in missing:
                        alive[x] = True
                        changed = True

        ok = True
        for i in range(15):
            if not alive[i]:
                ok = False
                break

        if not ok:
            bad += 1
            exp_bad += sum(1 for i in range(15) if not alive[i])

    prob_bad = bad / total
    exp_val = exp_bad / total

    print(f"{prob_bad:.12f} {exp_val:.12f}")

if __name__ == "__main__":
    solve()

の`changed`このフラグは、新しいブロックが復元されなくなるまでプロセスが続行されることを保証します。 この固定小数点反復がなければ、シミュレーションはカスケード ケースの回復可能性を過小評価することになります。 

確率は、少なくとも 1 つの回復不可能なイメージにつながる削除セットの割合として計算されます。 期待値は、すべてのサブセットにわたる回復不可能なイメージの数を平均することによって計算されます。

 ## 特殊なケース

 k が 0 の場合、回復は必要なく、確率と期待値の両方がゼロになります。 アルゴリズムはすぐに削除を検出せず、クロージャー ループは何も行わず、すべてのイメージは生きたままになります。

削除が単一の行または列に集中している場合でも、相互伝播により全体的に回復が成功する可能性があります。 反復クロージャはこれを正しく処理します。これは、いずれかの列が回復可能になると、他の場所で行の再構築のロックを解除できるためですが、シングルパス方式ではこれを見逃すことになります。
