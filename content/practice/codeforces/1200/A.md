 ## 解決策
 ## 問題の理解

 私たちは非常に小規模なシステムをシミュレートしています。つまり、0 から 9 までのインデックスが付けられたちょうど 10 室の部屋があるホテルです。各部屋は空であるか、占有されている可能性があります。 一連のイベントは、ゲストが時間の経過とともにどのように出入りするかを記述します。すべてのイベントを順番に処理した後、最終的な占有状態を再構築する必要があります。 

各イベントは、左側の入り口からの到着、右側の入り口からの到着、または特定の部屋からの出発のいずれかです。 誰かが左から入った場合、常に、部屋 0 から右に向かって、現在空いている最も近い部屋を選択します。 誰かが右から入った場合、部屋 9 から左に移動して、最も近い空いている部屋を選択します。 数字が表示されると、その部屋のゲストが退室し、再び空になることを意味します。 

重要な問題は、シミュレーションの速度ではなく、更新が繰り返された場合の正確さです。到着は常に現在の状態に依存するため、以前の選択が将来の選択を制約します。 構造が小さい場合でも、イベントの数は最大 100,000 件に達する可能性があるため、各イベントが効率的に処理されるようにする必要があります。 

素朴な解釈の間違いは、前の出発の動的な性質を考慮せずに、常に左の到着を最初の空きスロットにグローバルに割り当てるなど、到着が常に固定位置に行くと想定することです。 たとえば、削除を無視すると、現在占有されている部屋に新しく左に到着した人が誤って配置される可能性があります。 

もう 1 つの微妙なエッジケースは、同じ部屋の繰り返しの切り替えです。 たとえば、部屋は何度も占有、解放、再占有することができます。 正確なライブ状態の配列を維持しないソリューションは、正しい構成からずれてしまいます。 

部屋は 10 個しかないため、最終出力は占有率を表す 10 文字のバイナリ文字列になります。 

n ≤ 10^5 という制約は、各イベントを O(1) または O(10) 時間で処理する必要があることを意味します。 イベントごとにすべての部屋をスキャンするアプローチはまだ許容されますが、部屋ごとに n を使用してスケーリングするものは遅すぎます。 

## アプローチ

 単純なシミュレーションでは、各部屋が占有されているかどうかを表す 10 個のブール値の配列が維持されます。 左から到着するたびに、部屋を 0 から上に向かってスキャンし、最初の空の部屋を選択します。 右からの到着の場合、9 から下に向かってスキャンし、最初の空のものを選択します。 出発イベントの場合は、その部屋を空としてマークするだけです。 

このブルートフォース手法はすでに状態サイズが非常に小さいため、イベントあたりの最悪の場合のコストは最大でも 10 チェックです。 10^5 のイベントを超えると、約 10^6 の操作が発生しますが、これは問題なく制限内に収まります。 ヒープやバランスの取れたツリーなど、より複雑なデータ構造は必要ありません。 

重要な観察は、この問題では過去の割り当てを思い出す必要はなく、現在の占有状況のみを思い出す必要があるということです。 それぞれの決定は現在の状態のみに依存し、状態空間は小さく固定サイズです。 これにより、単純なリニア スキャン以上の最適化の必要がなくなります。 

これは、イベントごとに適用される貪欲な選択ルールでサイズ 10 のビットマスクを維持すると考えることができます。

 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション | O(10・n) | お(1) | 承認済み |
 | 最適 (同じ考え) | O(10・n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 配列を初期化する`rooms`サイズは 10 で、すべての値が 0 に設定されています。これは、すべての部屋が空であることを意味します。 これは、時間 0 における現在のホテルの状態を表します。 
2. 入力文字列内の各文字を左から右に繰り返し、各文字をイベントとして扱います。 
3. イベントが`'L'`、部屋 0 から 9 までをスキャンし、空いている最初の部屋を見つけます。 占有中としてマークします。 これにより、左側の入り口に最も近い利用可能な部屋が使用されるようになります。 
4. イベントが発生した場合`'R'`、部屋 9 から 0 までスキャンし、最初の空の部屋を見つけます。 占有中としてマークします。 これにより、右側の入り口に最も近い利用可能な部屋が使用されるようになります。 
5. イベントが次の桁の場合`'0'`に`'9'`、それを整数インデックスに変換し、その部屋を空としてマークします。 
6. すべてのイベントが処理されるまで、このプロセスを続けます。 
7. 最終状態を長さ 10 の文字列として出力します。各位置は次のとおりです。`'1'`占領されている場合と`'0'`さもないと。 

### なぜ効果があるのか

 このアルゴリズムは、各イベントの後にすべての部屋の正確な占有状態を維持します。 すべての到着ルールは現在の空の部屋のセットのみに依存し、すべての出発では部屋を空のセットに直接復元します。 常に最新の状態に基づいて選択肢を再計算するため、どの決定も「利用可能な最も近い部屋」の制約に違反することはありません。 正確さは次の不変条件から導かれます。`rooms[i]`部屋がある場合にのみ true`i`イベントのプレフィックスを処理した後に占有されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    s = input().strip()

    rooms = [0] * 10

    for c in s:
        if c == 'L':
            for i in range(10):
                if rooms[i] == 0:
                    rooms[i] = 1
                    break
        elif c == 'R':
            for i in range(9, -1, -1):
                if rooms[i] == 0:
                    rooms[i] = 1
                    break
        else:
            idx = ord(c) - ord('0')
            rooms[idx] = 0

    print("".join(map(str, rooms)))

if __name__ == "__main__":
    solve()
```この実装では、ホテルの状態を直接表現します。 のループ`'L'`そして`'R'`定数係数が 10 で制限されているため、意図的に単純になっています。数字文字の変換には ASCII 算術演算が使用され、これにより解析の遅延が回避されます。 最終出力では、整数フラグが文字列に結合されます。 

ここでよくある間違いは、出発は常に成功するため、数字イベントは部屋が占有されていると安全に想定できることを忘れていることです。 もう 1 つは、イベント間で古いループ インデックスを誤って再利用することですが、各イベントは独立しているため、スキャンは常に新しく再開されます。

 ## 特殊なケース

 重要なケースの 1 つは、解放後の同じ部屋の繰り返し使用です。 インプットを考慮する`L0L0`。 後`L`、部屋 0 が占有されます。 イベント`0`それを解放し、次は`L`再び部屋 0 が選択されます。これは、再び最も近い空のスロットであるためです。 アルゴリズムはこれを正しく処理します。`'L'`スキャンは部屋 0 から新たに開始されるため、以前に解放された位置は自然に再検討されます。 

もう一つのケースは、1 部屋を除いてすべてが占有されている場合です。 部屋 9 が唯一の空きスロットで、左に到着した場合、0 から上に向かってスキャンすると最終的に 9 に到達し、そこにゲストが配置されます。 これは、左側の入り口から遠くても正解です。ルールはあくまでも「最も近い空き部屋」であり、「遠くても左側を優先」ではないからです。 

最後の微妙なケースは、境界室を再利用する交互の到着と出発です。 例えば、`L R 0 R L 0`部屋 0 と 9 を繰り返し切り替えます。各イベントにより共有状態が即座に更新されるため、スキャンには常に最新の構成が反映され、割り当てが古くなることを防ぎます。
