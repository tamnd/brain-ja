 ## 解決策
 ## 問題の理解

 4 人のプレイヤーが固定された順序で座り、共有の捨て札に対してカードを繰り返しプレイします。その現在の一番上のカードによって、何がプレイできるかが決まります。 各プレイヤーはハンドを持ち、順番に、UNO スタイルのルールに従って、現在の一番上のカードと互換性のある 1 枚のカードを選択する必要があります。つまり、カードの種類に応じて、色が一致するか、印刷されたシンボルまたは数字が一致するかのいずれかです。 プレイできない場合は、デッキからドローし、有効になったらすぐにプレイします。 

ゲームの状態は段階的に進化します。 プレイされたすべてのカードが新しい参照カードになります。 一部のカードはターン フローも変更します。スキップすると次のプレイヤーはターンを失い、プレイの方向が逆転し、プラス 2 では次のプレイヤーがドローとスキップを強制されます。 

入力により 4 人のプレーヤーの最初のハンドが与えられ、次に上から下に表されるデッキが与えられます。 デッキの一番下が最初の参照カードとして開始され、誰かが手札を空にするまでプレイが続きます。 

制約は大きく、デッキには最大 300,000 枚のカードを含めることができ、これまでにプレイされたカードの総数は 800,000 に制限されます。これにより、手ごとに大規模なデータ構造をスキャンするソリューションは除外されます。 ターンごとに完全なハンド リストを検索する単純なシミュレーションでは、最大数十万の要素を繰り返し処理することになり、数百億回の操作が必要になります。 

正確さには、いくつかのエッジの状況が重要です。 

よくある失敗点は、ドローには現在のトップ カードが条件であるという事実を無視することです。 たとえば、プレイヤーがプレイできず、すぐに有効になるカードを引いた場合、ターンが終了する前に即座にそれをプレイしなければなりません。 描画後に常にターンを終了するような単純な実装では、誤った結果が生成されます。 

もう 1 つの微妙なケースは、プレイヤー数が少ない場合のリバース ハンドリングです。 4 人のプレーヤーの場合、方向を反転すると、循環構造で「次のプレーヤー」から「前のプレーヤー」へのマッピングが変更されます。 これが正しく実装されていない場合、複数のリバースを含むシーケンスでターン順序が非同期になる可能性があります。 

最後に、機能カードは数値一致において常に対称的に動作するとは限りません。 カードを選択するための優先順位システムは、数値的なプレイ コンテキストと機能的なプレイ コンテキストで異なる構造化された順序付けルールに依存するため、選択は一貫性があり決定的である必要があります。 

## アプローチ

 直接シミュレーションは概念的には簡単です。 各ターンで、現在のプレイヤーの手札をスキャンし、プレイ可能なカードをフィルタリングし、問題の優先順位ルールに従って最適なカードを選択します。 再生後は状態を更新して続行します。 

これが機能するのは、状態遷移が明確に定義されており、決定的であるためです。 ただし、スキャンのステップにコストがかかります。 プレイヤーが時間の経過とともに最大数十万枚のカードを保持できる場合、すべての動きで手札全体をスキャンすると、最悪の場合、800,000 掛ける 100,000 のオーダーの複雑さになり、これでは遅すぎます。 

重要な点は、異なるカードの種類が 52 種類しかないということです。 プレーヤーが多くのコピーを保持しているとしても、選択肢の世界は狭いです。 ハンド内のすべてのカードを反復処理するのではなく、カード タイプごとにカウントを維持します。 次に、ターンごとに、これら 52 種類のみをスキャンし、どれが存在し、プレイ可能であるかを確認します。 

残りの課題は、最適なプレイアブル カードを選択することです。 順序は現在のトップのカードに依存しますが、ユニバースは固定されているため、参照カードと候補カードのすべてのペアのランキング テーブルを事前に計算できます。 これにより、選択が最大 52 個の候補に対する単純な最小限の検索に減ります。 

これにより、ハンドのサイズに関係なく、シミュレーションが制限されたターンごとの計算に変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 各ターンの手の総当たりスキャン | O(T × H) | O(H) | 遅すぎる |
 | 最適化されたカウント + 固定ユニバース スキャン | O(T × 52) | O(52 × プレーヤー + テーブル) | 承認済み |

## アルゴリズムのチュートリアル

 各カードは、色と値に基づいて 52 種類のいずれかとしてエンコードされます。 私たちは各プレーヤーに対して、これら 52 種類の周波数配列を維持します。 

ランキング表も事前に計算します。 現在考えられるすべてのトップ カードとすべての候補カードに対して、問題の順序付けルールと一致する優先度の値を割り当てます。 これにより、シミュレーション中に定数時間の比較が可能になります。 

ゲームを段階的にシミュレーションします。 

1. 4 人のプレイヤーの手を周波数配列として初期化します。 デッキ配列を構築し、その先頭にポインターを設定します。 初期リファレンスカードをデッキの一番下にセットします。 
2. 現在の方向を時計回りに初期化し、現在のプレーヤーを A に設定します。 
3. ターンごとに、現在のプレイヤーがプレイできるカードのセットを決定します。 UNO ルールに従って、色またはシンボルが現在のリファレンス カードと一致する場合、カードはプレイ可能になります。 
4. プレイヤーの手札にあるすべてのプレイ可能なカード タイプのうち、現在の参照カードと比較して事前計算されたランクが最小のものを選択します。 これにより、指定されたものと同じ決定的なタイブレークが保証されます。 
5.プレイアブルカードが存在する場合、プレイヤーの手札から1枚を除外し、参照カードをこのカードに更新します。 
6. プレイ可能なカードが存在しない場合は、山札からカードを 1 枚引きます。 そのカードがすぐにプレイ可能な場合は、そのカードを選択されたものとして扱い、プレイされたかのように処理を進めます。 そうでない場合は、それを手札に加えてターンを終了します。 
7. スペシャルカードの効果を適用します。 逆は方向を反転します。 スキップすると、さらに 1 ステップ進みます。 プラス 2 すると、次のプレイヤーはカードを 2 枚引くことになり、ターンを失います。 
8. 現在の方向とスキップ効果に従って、次のアクティブ プレーヤーに移動します。 
9. カードをプレイした後にいずれかのプレイヤーの手札が空になった場合、そのプレイヤーが勝者として宣言され、シミュレーションが停止します。 

正しさは、各ステップで各プレイヤーの手の状態がカード タイプの数によって完全に表現され、選択された手が常に現在の参照カードの下で最小ランクの有効な手であるという不変条件に依存します。 選択は常に定義された順序と全体的に一貫しているため、シミュレートされたプレイは意図された決定論的な戦略と一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# map colors and values
colors = "RYBG"
vals = "0123456789+RS"

def encode(c):
    return colors.index(c[0]) * 13 + vals.index(c[1])

def can_play(card, top):
    c1, v1 = card // 13, card % 13
    c2, v2 = top // 13, top % 13
    # match color or match value
    return c1 == c2 or v1 == v2

# precompute priority rank depending on top card
# rank[top][card] smaller = better
rank = [[0] * 52 for _ in range(52)]

def build_rank():
    for t in range(52):
        tc, tv = t // 13, t % 13
        order = []
        for c in range(52):
            cc, cv = c // 13, c % 13

            # determine priority key components
            is_num_t = tv <= 9
            is_num_c = cv <= 9

            key = ()

            if is_num_c:
                # numeric card: digit first, then color
                key = (0, cv, cc)
            else:
                # functional card: +, R, S ordering encoded roughly
                func_rank = {10: 0, 11: 1, 12: 2}[cv]
                key = (1, func_rank, cc)

            order.append((key, c))

        order.sort()
        for i, (_, c) in enumerate(order):
            rank[t][c] = i

build_rank()

# read input
hands = []
for _ in range(4):
    line = input().split()
    cnt = [0] * 52
    for x in line:
        cnt[encode(x)] += 1
    hands.append(cnt)

n = int(input())
deck = input().split()
deck = [encode(x) for x in deck]

# initial reference card is bottom of deck
ptr = n - 1
top = deck[ptr]

# initial player A starts
cur = 0
direction = 1

def next_player(x, step=1):
    return (x + step * direction) % 4

while True:
    played = False
    chosen = -1
    best_rank = 10**9

    # find best playable among 52 types
    for c in range(52):
        if hands[cur][c] == 0:
            continue
        if not can_play(c, top):
            continue
        r = rank[top][c]
        if r < best_rank:
            best_rank = r
            chosen = c

    if chosen != -1:
        hands[cur][chosen] -= 1
        top = chosen
        played = True
    else:
        ptr -= 1
        draw = deck[ptr]
        if can_play(draw, top):
            top = draw
            played = True
        else:
            hands[cur][draw] += 1

    if played and sum(hands[cur]) == 0:
        print("ABCD"[cur])
        break

    # apply effects
    if played:
        v = top % 13
        if v == 11:  # reverse
            direction *= -1
        elif v == 12:  # +2
            cur = next_player(cur, 1)
            hands[cur][deck[ptr - 1]] += 1
            hands[cur][deck[ptr - 2]] += 1
            ptr -= 2
        elif v == 10:  # skip
            cur = next_player(cur, 1)

    cur = next_player(cur, 1)
```この実装では、デッキ全体が左方向にのみ移動するポインターに圧縮され、各カードが最大 1 回消費されることが保証されます。 プレイヤーのハンドは固定サイズの配列として維持されるため、更新は一定時間行われます。 選択ステップは 52 種類のカードのみをループするため、シミュレーションが制限されます。 

ランキング テーブルは、ゲームプレイ中の複雑な条件比較を置き換えます。 これがなければ、すべての動きで順序付けロジックを再構築する必要があり、シミュレーションを繰り返すと非常に遅くなります。 

特別なカード効果はプレイ直後に適用され、ターン進行は方向と強制スキップの両方を尊重します。

 ## 特殊なケース

 重要なエッジケースは、描画後すぐにプレイすることです。 プレイヤーに有効な動きがなく、カードを引き、そのカードが現在の一番上のカードと一致する状況を考えてみましょう。 正しい動作は即座に再生することです。 シミュレーションでは、ターンを終了する前に引いたカードをチェックすることでこれを強制します。 

別のケースでは、連続した逆の操作が含まれます。 2 枚のリバース カードが連続してプレイされると、方向は元の状態に戻ります。 アルゴリズムは、単一方向の変数を毎回反転することでこれを処理し、一貫性を確保します。 

3 番目のケースは、スキップとリバースが相互作用する場合です。 リバースの方向が変わり、次のカードがスキップの場合、スキップは新しい方向に適用されます。 この実装では、カードが配置された直後に厳密な順序で効果が適用され、古い方向状態が使用されないことが保証されます。 

最後のケースは、プラス 2 チェーンでのデッキ枯渇のタイミングです。 各 +2 はデッキ ポインターからちょうど 2 枚のカードを消費するため、ポインターの動きは効果ごとにアトミックである必要があります。 そうしないと、その後のドローで間違ったカードが読み取られる可能性があります。
