 ## 解決策
 ## 問題の理解

 単一種類のプリミティブ ブラケット構造から構築された、再帰的に定義された文字列ファミリーが与えられます。 基本オブジェクトは、最も単純な有効なペア「()」です。 そこから、2 つの操作を使用してより大きな構造を構築できます。1 つは既存の構造を一対のかっこで囲む操作、2 つの既存の構造を連結してその結果を再度ラップする操作です。 

各クエリは 1 つの括弧文字列を指定し、ベース「()」から始まるこれらのルールを繰り返し適用することによってその文字列を生成できるかどうかを尋ねます。 タスクは、文字列が標準的な正しい括弧シーケンスであるかどうかをチェックすることではなく、文字列がこのより制限的な文法に属しているかどうかをチェックすることです。 

入力には、合計長が最大 300,000 の文字列を含めることができます。 これにより、すべての分解を探索したり導出を明示的にシミュレートしようとするソリューションは即座に除外されます。 考えられるすべての方法で文字列を分割したり、部分文字列にわたって DP を維持しようとすると、最悪の場合は 2 次関数になり、制限を超えてしまいます。 

よくある落とし穴は、これがバランスのとれた括弧シーケンスをチェックすることと同等であると想定することです。 「()(())」のような標準的な有効なシーケンスは、文法によって課される構造制約によっては生成できない可能性があるため、これは失敗します。 もう 1 つの罠は、汎用解析による文法メンバーシップ問題として扱うことです。これは、直接実装した場合、部分文字列に対する 3 次 DP が必要になります。 

違いを明らかにする小さな例は「()()」です。 これは有効な括弧シーケンスですが、この文法では、正しい順序で制約をラップせずに 2 つの独立したコンポーネントを導出で許可しない場合は、必ずしも構築可能ではありません。 逆に、一部のネストされたフォームは、不必要に制約されているように見える場合でも許可されます。 

本当の難しさは、文法が任意のコンテキストフリー動作ではなく、任意のインターリーブではなくツリー状の分解を強制する非常に特殊な「外側のラッピングと内部のオプションの連結」構造を持っていることです。 

## アプローチ

 この問題を考える強引な方法は、それを文法メンバーシップのチェックとして扱うことです。 dp[l][r] が部分文字列 S[l:r] がセットに属するかどうかを示す DP を定義できます。 部分文字列が有効であるためには、X が有効な「(X)」か、両方の部分が有効で最も外側のかっこが適切に一致する「(X)(Y)」のいずれかである必要があります。 

これにより、すべての間隔内のすべての分割点がすぐに試行され、間隔ごとに構造の一致が検証されます。 メモ化を行った場合でも、間隔の数は O(n²) であり、各遷移には分割点のスキャンが必要であり、最悪の場合は O(n³) 個の動作が発生します。 n が合計 3×10⁵ までなので、これは不可能です。 

重要な観察は、文法が非常に厳密な構造を強制していることです。すべての有効な文字列は、単一のプリミティブなラップされた構造か、2 つの小さな有効な構造のラップされた連結のいずれかです。 どちらの場合も、最も外側のかっこのペアは常に、連続する有効なブロックへの分解を囲みます。 

これは、任意の分割の代わりに、プリミティブ ブロック上にルート付きの順序付けされたバイナリ分解ツリーを構築するプロセスとして解釈できることを意味します。 各ノードはバランスの取れたセグメントに対応し、分割の構造は、各括弧内に存在する最上位コンポーネントの数によって完全に決定されます。 

これを把握する標準的な方法は、現在開いている構造を維持し、各深さで形成された「完全なコンポーネント」の数をカウントするスタックを使用することです。 括弧を閉じるたびに、プリミティブを終了するか、完成した子を現在のレベルにマージします。 この構造は、順序付けの制約に決して違反せず、最外部レベルで単一の完成した構造で終わる場合にのみ有効です。

 | 部分文字列に対するブルート DP | O(n3) | O(n²) | 遅すぎる |
 | スタックベースの構造解析 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ネストされた構築フレームを表すスタックを使用して、各文字列を個別に処理します。 各フレームは、フレーム内に少なくとも 1 つの完成したコンポーネントが存在するかどうかを追跡します。 

1. 空のスタックを初期化します。 各スタック エントリは、現在開いている括弧コンテキストと、完了した部分構造が蓄積されているかどうかを表します。 
2. 文字列を左から右にスキャンします。 「(」が表示されると、新しいフレームを作成してスタックにプッシュします。これは、再帰定義で新しい構築層を開始することに対応します。
 3. 「)」が表示されると、現在のフレームが閉じられます。 この時点で、フレームは完全に構築された下部構造を表します。 ポップする前にスタックが空の場合、開始コンテキストなしで閉じているため、文字列は無効になります。 
4. 上部フレームを外します。 このフレームに完成した部分構造も内部の有効な構成も含まれていない場合、それは基本「()」ケースを表すため、依然として単一ユニットとして有効です。 
5. ポップ後、この完成したユニットを上位フレームに属する「ブロック」として扱います。 スタックが空でない場合は、親フレームが少なくとも 1 つの完成した子コンポーネントを受信したことをマークします。 
6. アクティブなフレームがないときに閉じ括弧に遭遇した場合、またはスキャンが終了して開いたフレームが残っている場合、その文字列は無効です。 
7. 最後に、最外部レベルで正確に 1 つの完全な構造が形成された場合、文字列は有効です。つまり、スタック処理が正常に終了し、文字列全体が 1 つのルート ブロックに折りたたまれます。 

重要な考え方は、文法では構造の構築に 2 つの方法しか許可されていないということです。ラッピングと、すでに完成した構造の連結です。 スタックにより、部分的な構造ではなく、完全な部分構造のみがマージされることが保証されます。 

### なぜ効果があるのか

 スキャンのどの時点でも、各スタック フレームは現在構築中の部分文字列に対応し、完了するとバランスが保たれることが保証されます。 不変条件は、フレームをポップするたびに、以前に完成したコンポーネントから完全に形成された最大有効な構造を表すということです。 

この文法では、すでに有効なコンポーネントの合成のみが許可されているため、有効な導出では不完全なセグメント内での分割が必要になる可能性があります。 逆に、スタックがフレームを完了するたびに、文法が一貫した 1 つのユニットが正確に構築されます。 最後の受け入れ条件は、文字列全体が単一のそのような単位に折りたたまれ、セットの再帰的定義と一致することを強制します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def is_valid(s: str) -> bool:
    stack = []
    
    for ch in s:
        if ch == '(':
            # start a new frame, no completed children yet
            stack.append(0)
        else:
            if not stack:
                return False
            
            # finish current frame
            had_child = stack.pop()
            
            # we now have a completed block; attach it to parent if exists
            if stack:
                stack[-1] = 1  # parent now has at least one component
    
    return len(stack) == 0

def main():
    t = int(input())
    for _ in range(t):
        s = input().strip()
        print("YES" if is_valid(s) else "NO")

if __name__ == "__main__":
    main()
```この実装では、各エントリが現在のフレームに少なくとも 1 つの完了した内部ブロックが既に蓄積されているかどうかを示す単純なマーカーであるスタックを使用します。 右括弧が見つかった場合、フレームをポップし、それを完成したユニットとして扱います。 親フレームが存在する場合、有効なコンポーネントを受信したものとしてマークします。 

正確かどうかは、一致しない閉じ括弧を決して受け入れず、開いているすべてのフレームが最後までに閉じられるかどうかにかかっています。 最終スタックが空であることにより、構造全体が単一の有効な構造に縮小されます。 

## 実用的な例

 2 つの文字列をトレースして、スタックがどのように進化するかを確認します。 

まず、文字列「(()())」について考えてみましょう。 

| ステップ | シャア | スタック状態 |
 | --- | --- | --- |
 | 1 | ( | [0] |
 | 2 | ( | [0, 0] |
 | 3 | ) | [0] |
 | 4 | ( | [0, 0] |
 | 5 | ) | [0] |
 | 6 | ) | [] |

 各閉じ括弧で、最も内側の構造を単一のユニットに折りたたんで、それを上方に伝播させます。 スタックは空で終わり、単一の有効なルート構造が確認されます。 これは、内部の有効なブロックが文法規則に従って結合される入れ子の構成に対応します。 

ここで「(()))」を考えてみましょう。 

| ステップ | シャア | スタック状態 |
 | --- | --- | --- |
 | 1 | ( | [0] |
 | 2 | ( | [0, 0] |
 | 3 | ) | [0] |
 | 4 | ) | [] |
 | 5 | ) | 無効 |

 ステップ 5 では、アクティブなフレームのない括弧を閉じようとしますが、これは直ちに構築規則に違反します。 これは、スタックが完全な解析を必要とせずに構造違反を早期に検出する方法を示しています。 

最初の例では、適切なネストされたリダクションが確認され、2 番目の例では、無効なクロージャーが構築プロセスをどのように中断するかを明らかにしています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各文字は最大 1 回プッシュまたはポップされます。 
| スペース | O(n) | スタックには開き括弧ごとに最大 1 つのエントリが保存されます。 

合計入力サイズは最大 3×10⁵ 文字であるため、テスト ケースごとのリニア スキャンは制限内に問題なく収まります。 メモリ使用量も、文字列の長さによって制限される最大ネスト深さにおいて線形です。 

## テストケース```python
import sys, io

def solve():
    input = sys.stdin.readline
    t = int(input())
    for _ in range(t):
        s = input().strip()
        stack = []
        ok = True
        for ch in s:
            if ch == '(':
                stack.append(0)
            else:
                if not stack:
                    ok = False
                    break
                stack.pop()
                if stack:
                    stack[-1] = 1
        if stack:
            ok = False
        print("YES" if ok else "NO")

def run(inp: str) -> str:
    old_stdin = sys.stdin
    sys.stdin = io.StringIO(inp)
    old_stdout = sys.stdout
    sys.stdout = io.StringIO()
    solve()
    out = sys.stdout.getvalue()
    sys.stdin = old_stdin
    sys.stdout = old_stdout
    return out.strip()

# provided samples
assert run("""5
((())())
(()())
()()
(()()))
((()())())""") == """YES
YES
NO
NO
YES"""

# minimum size
assert run("""1
()""") == "YES"

# simple invalid
assert run("""1
)("""") == "NO"

# nested deep
assert run("""1
(((())))""") == "YES"

# multiple components invalid for this grammar
assert run("""1
()()""") == "NO"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | () | はい | 最小限の有効な構造 |
 | )( | NO | 早期の無効な終了 |
 | (((()))) | はい | 深いネストの正しさ |
 | ()() | いいえ | フラット連結構造は許可されていません |

 ## 特殊なケース

 重大なエッジ ケースの 1 つは、「()()」など、通常の意味ではバランスが取れているものの、構造的に文法と互換性のない文字列です。 スタックは無効なブラケットに遭遇することなくそれを処理しますが、最終的な構造は単一のルート フレームに折りたたまれず、複数のトップレベル コンポーネントが残ります。 スタックが最後に空ではないため、アルゴリズムはこれを拒否します。これは、文字列全体が単一の構築されたオブジェクトを表す必要があるという要件と一致します。 

もう 1 つのエッジ ケースは、「)(」のような初期の無効なクロージャーです。最初の文字は存在しないフレームを閉じようとし、即座に拒否を引き起こします。これは、アルゴリズムがグローバル バランスだけでなく、プレフィックスの有効性を正しく強制していることを示しています。

 3 番目のケースは、「(((())))」のような深くネストされた文字列です。ここでは、すべての開始括弧が新しいフレームを作成し、すべての終了括弧がそれをきれいに折りたたみます。 スタック サイズは直線的に増加し、その後ゼロに戻ります。これにより、純粋なネストが構築ルールの下で常に有効であることが確認されます。
