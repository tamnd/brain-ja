 ## 解決策
 ## 問題の理解

 完全にゼロから始まる長さ n の配列が与えられています。 配列を直接観察する代わりに、バイナリ文字列を通じてのみ最終状態がわかります。各位置によって、そのインデックスの最終値が 0 であるかどうかがわかります。 配列を作成する隠れたプロセスは、一連のフェンウィック ツリー ポイント更新です。位置 p での各更新では、実数値 v が p に追加され、インデックス p、p + lowbit(p)、p + lowbit(p + lowbit(p)) などを介して上向きに伝播されます。 

重要な問題は、1 つの更新が 1 つのポジションだけに影響を与えるわけではないことです。 これは、インデックスのバイナリ表現によって決定される構造化されたインデックスのセットに影響します。 タスクは、最終的なゼロ/非ゼロ パターンのみから、それを生成した可能性のあるそのような更新の最小数を再構築することです。 

入力サイズは大きく、テスト ケースの数は最大 10^5、合計 n は最大 10^6 です。 これにより、テスト ケースごとに線形または線形に近い解決策が強制されます。 更新を明示的にシミュレートしたり、操作のサブセットを検索しようとしたりすることは、テスト ケースごとに O(n log n) であっても、合計すると遅すぎるため、直ちに不可能になります。 

微妙な点は、値が実数であるため、キャンセルが可能であることです。 位置が更新の影響を受けていても、値が正確にキャンセルされていれば、位置はゼロになることがあります。 ただし、更新の数を最小限に抑えているため、最終的なゼロ/非ゼロのパターンが一致するように更新に値を割り当てることができるかどうかのみを考慮します。 

単純な間違いは、1 とマークされた各位置でその位置での独立した更新が必要であると考えることです。 1 つの更新が多くのポジションに影響を与える可能性があるため、これはすぐに失敗します。 たとえば、位置 1 を更新すると、すべての位置に影響します。 したがって、1 つの演算で多くの 1 を満たすことができますが、潜在的にゼロと干渉する可能性もあり、構造が自明ではなくなります。 

誤解を招きやすいもう 1 つのケースは、交互のパターンが表示される場合です。 たとえば、101010 のような文字列は、1 ごとに更新を貪欲に配置する誘惑に駆られるかもしれません。しかし、伝播が重なると、より少ない更新で十分になったり、逆に、ゼロからの制約によりより多くの更新が強制される可能性があります。 

## アプローチ

 ブルート フォース ビューでは、必要な各更新を何らかの位置と値に割り当て、フェンウィックの伝播をシミュレートして、結果のゼロ/非ゼロ パターンがターゲット文字列と一致するかどうかを確認します。 これは組み合わせ構築問題になります。つまり、開始位置と実際の値の複数のセットを効果的に選択していることになります。 開始位置の選択に限定したとしても、2^n 通りの可能性があり、各候補には O(n log n) のシミュレーションが必要です。 これはまったく実現不可能です。 

重要な洞察は、視点を逆転させることです。 価値を生み出す更新という観点から考えるのではなく、最終的なパターンを説明するために独立した「影響源」がいくつ必要かという観点から考えます。 各更新では、インデックスのバイナリ分解と密接にリンクされているフェンウィック ツリー構造に従う伝播パスが導入されます。 

位置 p から始まるフェンウィックの更新は、低ビット セグメントを繰り返し追加することによって定義された範囲内のすべてのインデックスに寄与します。 この構造は、各インデックス i が、暗黙的なフェンウィック ツリー内の i の特定の祖先チェーン上に p が位置するように、すべての位置 p で開始される更新の影響を受けることを意味します。 

次に、インデックスを左から右に処理することを考えてみましょう。 位置 i で 1 が表示された場合、i に到達する何らかの更新から少なくとも 1 つの非ゼロの寄与を受け取る必要があります。 まだ説明できない新しい 1 をカバーするために最小限の数の更新を常に「アクティブ化」するようにすれば、必要なアクティブなフェンウィック伝播チェーンの数を効果的に維持することができます。

重要な観察は、フェンウィック構造がバイナリ リフティング間隔の森のように動作するということです。 各インデックス i は、制約をゼロに設定した場合、前のインデックスによって常に満たされるとは限らない要件を導入します。 ゼロはブロッカーとして機能します。キャンセルが手配されない限り、アクティブな更新チェーンがそれらをカバーすることを禁止しますが、更新の数を最小限に抑えているため、不必要な重複チェーンの導入は避けたいと考えています。 

これは、以前の有効な伝播構造によってまだ「カバーされていない」1 に遭遇した位置で、いくつの独立したセグメントを開始する必要があるかを追跡することに帰着します。 フェンウィック構造は、カバレッジの依存関係がロービットによるプレフィックス分解と一致することを保証するため、問題は、インデックスのバイナリ分解に関して文字列をスキャンするときに必要な新しい独立した開始の数をカウントすることに集約されます。 

依存関係構造を単純化した後、最適な解決策は貪欲な線形スキャンになり、追加の独立した更新を導入することなくゼロを強制的に非ゼロにすることはできないことを考慮しながら、すべての 1 を説明するために必要なアクティブな更新ソースの最小限のセットを維持します。

 ## アルゴリズムのチュートリアル

 現在「アクティブ」で将来のポジションに貢献できる独立したフェンウィック更新ソースの数を維持しながら、文字列を左から右に処理します。 

1. 将来の 1 を説明するために現在利用可能な更新チェーンの数を表すカウンターを初期化します。 
2. 値 1 の位置 i に到達すると、まず既存のアクティブ チェーンの使用を試みます。 構造体を再利用しても操作の数が増えることはないため、存在する場合は、この位置をカバーするためにそれを割り当てます。 
3. アクティブなチェーンが使用できない場合は、位置 i で新しい更新を開始する必要があります。 以前の操作ではこの 1 を説明できないため、これは Fenwick 更新プロシージャへの 1 回の呼び出しに相当します。 
4. 0 に遭遇した場合、この位置を強制的にゼロ以外にする不必要なアクティブ カバレッジを誤って保持しないようにする必要があります。 アクティブなチェーンがある場合は、フェンウィックの伝播境界と一致する方法でカバレッジを「終了」または消費することで問題を解決し、使用可能なチェーンの数を効果的に削減します。 
5. このプロセスを最後まで継続し、新しいアップデート ソースの導入が強制されるたびに合計します。 

主な困難は、「アクティブ チェーン」を正しく解釈することです。 フェンウィックの用語では、各更新はバイナリ分解に合わせた伝播パターンを定義します。 チェーンは、構造上の競合 (強制ゼロ) がブロックしていないセグメント間でのみ使用可能です。 

### なぜ効果があるのか

 各更新は、フェンウィック格子内に 1 つの独立した伝播源を作成すると解釈できます。 任意の 1 は少なくとも 1 つの情報源によって説明されなければならないため、答えは下限になります。 ゼロは、ソースを共有できるインデックスのセットを制限します。これは、単一の更新が必然的にゼロの位置に寄与する場合、キャンセルの複雑さを導入せずにその構造を再利用できないためです。 最適な構築ではキャンセルによって必要なソースの数が減らないため、必要な各ソースを構造的に独立したものとして扱うことができます。 貪欲スキャンは、これらのソースを最大限に再利用して、すべての 1 が確実にカバーされるようにし、既存の構造が現在のインデックスに合法的に拡張できない場合にのみ新しいソースを導入します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        s = input().strip()

        ans = 0
        active = 0

        for ch in s:
            if ch == '1':
                if active > 0:
                    active -= 1
                else:
                    ans += 1
                    active += 1
            else:
                active = 0

        print(ans)

if __name__ == "__main__":
    solve()
```コードでは 2 つの量が維持されます。 答えは、新しいフェンウィック アップデート ソースをいくつ作成する必要があるかを数えます。 の`active`変数は、今後の 1 をカバーするためにまだ使用できるソースがいくつあるかを表します。 

1 が表示された場合、可能であれば既存のソースを再利用し、そうでない場合は新しいソースを作成します。 0 が表示されると、アクティブな再利用容量をリセットします。これは、この位置をカバーする進行中の伝播は、最終パターンでこのインデックスを 0 に保つという制約と互換性がないためです。 

実装の重要な詳細は、ゼロに遭遇するとすぐにリセットが行われることです。 これにより、禁止された位置を越えてソースを誤って再利用することがなくなります。

## 特殊なケース

 最小のエッジケースは単一のゼロです。 配列をゼロに保つための更新は必要なく、アクティブなチェーンも作成されないため、アルゴリズムは即座にゼロ演算を生成します。 

最初に 1 つだけ更新すると 1 つの更新ソースが作成され、その後はアクティブな再利用は行われません。これは、ゼロ以外の値を生成するには少なくとも 1 つのフェンウィック更新が必要であるという考えと一致します。 

みたいなパターン`101010`強制リセットと新しいソースを交互に実行するため、これは重要です。 このアルゴリズムは、ゼロごとにアクティブな容量をリセットします。これにより、ギャップ間の不正な再利用が防止され、ゼロの後に表示される孤立した 1 がそれ​​ぞれ新しいソースを開始します。 これを追跡すると、アクティブなチェーンが存在しない限り、ゼロから 1 への遷移ごとに答えが増加することが確認されます。このモデルでは、アクティブなチェーンはゼロをまたいで存続することはありません。
