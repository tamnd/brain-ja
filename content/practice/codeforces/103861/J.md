 ## 解決策
 ## 問題の理解

 頂点 1 が開始ハブであり、頂点 n が最終的にクリアする必要がある最終ターゲットである無向グラフが与えられます。 1 を除くすべての頂点には、初期強度を持つボスが含まれています。 プレイヤーには強さの値もあり、時間の経過とともに進化します。 

時間は離散的な日単位で進みます。 毎日の開始時に、残っているすべてのボスの強さが固定量 B だけ増加します。その後、プレイヤーは頂点 1 から到達可能な頂点を 1 つだけ選択し、そのボスと戦います。 プレイヤーの現在の強さがそのボスよりも厳密に大きい場合、ボスは永久に除去され、プレイヤーは A の強さを獲得します。 

生きているボスによって移動が制限されます。 すべての中間頂点にアクティブなボスがすでに存在しないパスが存在する場合にのみ、頂点 1 から頂点にアクセスできます。 これは、おそらく戦いのために到達しようとしているエンドポイントを除いて、生きているボスがブロッカーとして機能することを意味します。 

タスクは、頂点 n のボスを倒すのに必要な最小日数を決定するか、不可能であると報告することです。 

この制約は、強力に最適化されたソリューションが必要であることを示唆しています。 テスト ケース全体の頂点とエッジの総数は 10^6 に達する可能性があるため、単純な方法でエッジを再検討したり、到達可能性を繰り返し再計算したりするアプローチは遅すぎます。 n の二次関数や、状態ごとに繰り返される BFS は、直ちに除外されます。 

微妙な難しさは、時間と構造の間の相互作用から生じます。 ノードは、グラフの接続性の観点からは到達可能であっても、強度が不十分なため強制終了できない場合があります。 逆に、ノードが十分に弱いにもかかわらず、単一の生きている頂点がすべてのパスをブロックするため、到達できない場合もあります。 

いくつかの失敗例が落とし穴を浮き彫りにしています。 

頂点 2 だけがその先のすべてへのパスをブロックしている折れ線グラフ 1 - 2 - 3 - 4 を考えてみましょう。 たとえ頂点 4 が早期に殺されるほど弱くても、頂点 2 が削除されるまで到達することはできません。 強度だけをチェックして到達可能性を無視する単純なアプローチでは、誤って 2 のスキップが許可されてしまいます。 

もう 1 つの故障モードはタイミングによって発生します。 頂点が 1 日目にはほとんど強すぎなかったが、プレイヤーが A によってスケーリングしたため、2 日目には倒せるようになったとします。B が大きい場合、遅延によってプレイヤーよりも早くボスの強さが増す可能性もあるため、「待つのが常に良い」または「早いのが常に良い」と仮定する誤った貪欲な戦略は失敗します。 

正しいソリューションでは、動的に削除された頂点の下での到達可能性と、ノードが破られる最も早い日を同時に追跡する必要があります。 

## アプローチ

 総当たりシミュレーションでは、毎日ゲームを処理しようとします。 毎日、すでに死亡している頂点のみを中間ノードとして使用して、どの頂点が 1 から到達可能であるかを再計算し、到達可能なすべての頂点をチェックしてどれを強制終了できるかを確認します。 これには、1 日あたり最大 n 日間の BFS または DFS が必要で、最悪の場合は O(n(n + m)) となり、制限をはるかに超えています。 

重要な観察は、唯一の意味のある状態は、生きているボスと死んだボスの完全な構成ではなく、既にクリアされたノードを通じて到達可能になった頂点のセットと現在の日のインデックスであるということです。 頂点を削除してもパスが開くだけなので、頂点が到達可能になると、再び到達不能になることはありません。 

これは、到達可能性をノード 1 から始まる成長フロンティアとして扱うことを示唆しており、そこではすでにクリアされた頂点のみが内部ルーティング ポイントとして使用できます。 頂点を削除するたびに、通過可能な領域が永続的に拡張されます。

独立して、プレイヤーの強さとボスの強さは両方ともキル数 (1 日あたり 1 人) に比例して変化するため、強さの状態は経過日数のみに依存します。 k を既に実行されたキル数とすると、翌日にはプレイヤーの強さは l1 + kA になり、ボス v の強さは l_v + kB になります。 したがって、各頂点には k のしきい値があり、それを超えると消去可能になりますが、到達可能になった場合のみ考慮されます。 

これにより、頂点を越える最短パス スタイルのプロセスが自然に導かれます。「距離」は頂点を倒すことができる最も早い日 (またはキル数) であり、既にクリアされた領域から頂点に到達できるようになったときに遷移が発生します。 

頂点を削除するたびに、その近隣の頂点を潜在的に到達可能なものとしてロック解除し、頂点を削除できる最も早い日を計算します。 これは、実現可能な最も早い殺害日が優先される、ディクストラのような拡張を形成します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | BFS による日々のシミュレーション | O(n(n + m)) | O(n + m) | 遅すぎる |
 | 到達可能な州に関するダイクストラ | O((n + m) log n) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 ### 1. 強制終了順序の観点からプロセスをモデル化する

 このプロセスは、頂点が削除される順序を選択するものであると解釈します。 頂点が k 番目のアクションとして殺された場合 (最初のキルでは k = 0 から開始)、現在の日は k + 1、プレイヤーの強さは l1 + kA、すべてのボスの強さは l_i + kB になります。 

これにより、時間が単一の整数パラメータ k に変換され、比較が簡素化されます。 

### 2. 頂点を強制終了するための実現可能条件を導出する

 頂点 v は、厳密な不等式が成り立つ場合に限り、ステップ k で削除できます。 

l1 + kA > l_v + kB。 

並べ替えると次のようになります。 

l1 - l_v > k(B - A)。 

これにより、v が到達可能であれば、v が kill 可能になる最も早い k がわかります。 

成長の方向性が重要です。 A > B の場合、プレイヤーは時間の経過とともに有利になるため、待つことが役立ちます。 A ≤ B の場合、遅延しても実行可能性は決して向上せず、殺害が困難になるか変化がなくなるだけです。 

### 3. 頂点 1 からの動的な到達可能性を維持する

 すでに削除された頂点を介して 1 に接続されている頂点のみに到達できます。 生きている頂点はトラバースをブロックします。 

したがって、すでに削除されている「アクティブ化された」頂点のセットを維持します。 これらから、まだ殺されていない隣人にまで拡大することができます。 頂点は、少なくとも 1 つの近傍がすでにアクティブ化されている場合にのみ候補になります。 

これにより、進化するグラフで現在到達可能な頂点のみを考慮することが保証されます。 

### 4. 最も早いキルタイムよりも優先キューを使用する

 最もよく知られている値 dist[v]、つまり v が到達可能な間に強制終了できる最小の k を維持します。 k = 0 ですでにアクティブになっている頂点 1 から始めます。 

アクティブ化された各頂点 u について、まだアクティブ化されていない隣接する頂点 v をスキャンします。 v がステップ k で発見された場合、不等式に基づいて v に対する最も早い実行可能なキル ステップ k' を計算します。 また、到達可能になる前に kill できないため、k' ≥ k であることも保証します。 

(k', v) を優先キューにプッシュし、常に最小の k' を持つ頂点を拡張します。 

### 5. キルタイムを増やすための頂点の処理

 優先キューから最小 k の頂点を繰り返し抽出します。 すでに確定している場合はスキップします。 それ以外の場合は、殺されたとマークし、現在の k をその値に設定し、プレイヤーの強さを暗黙的に更新します。 

次に、すべての近隣者を緩和し、より早い到達可能性により最も早い実行可能なキル時間を短縮する可能性があります。 

### なぜ効果があるのか

アルゴリズムはどの時点でも、優先キュー内のすべての頂点がすでに強制終了された頂点を介して到達可能であることを保証し、その保存された値は、現在の進行下で強制終了できる最も早いステップになります。 到達可能性と実現可能性の両方は、キルされた頂点を追加するにつれて単調に改善するだけであるため、最小の k で抽出された頂点は後で改善することはできません。 これは、ダイクストラのアルゴリズムとまったく同じ正確性の原則です。つまり、最小の実現可能な状態が選択されると、その後のパスはより小さい有効キル タイムを生成できなくなります。 

## Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m, A, B = map(int, input().split())
        
        g = [[] for _ in range(n + 1)]
        for _ in range(m):
            u, v = map(int, input().split())
            g[u].append(v)
            g[v].append(u)
        
        l = [0] + list(map(int, input().split()))
        
        INF = 10**30
        
        dist = [INF] * (n + 1)
        used = [False] * (n + 1)
        
        # node 1 is already reachable and "killed" at time 0
        dist[1] = 0
        pq = [(0, 1)]
        
        def earliest_k(v, k):
            # check minimal k' >= k such that:
            # l1 + k'*A > l[v] + k'*B
            # (A - B)*k' > l[v] - l1
            
            if A == B:
                if l[1] > l[v]:
                    return k
                return INF
            
            if A > B:
                # k' > (l[v] - l1) / (A - B)
                need = l[v] - l[1]
                if need < 0:
                    k0 = 0
                else:
                    k0 = need // (A - B) + 1
                return max(k, k0)
            
            # A < B: only possible if already satisfied at current k
            if l[1] + k * A > l[v] + k * B:
                return k
            return INF
        
        while pq:
            k, u = heapq.heappop(pq)
            if used[u]:
                continue
            used[u] = True
            
            for v in g[u]:
                if used[v]:
                    continue
                nk = earliest_k(v, k)
                if nk < dist[v]:
                    dist[v] = nk
                    heapq.heappush(pq, (nk, v))
        
        print(-1 if dist[n] == INF else dist[n])

if __name__ == "__main__":
    solve()
```コードはグラフを構築し、頂点に対してダイクストラ スタイルのプロセスを実行します。優先順位は、処理済みのノードから到達可能な状態を維持しながら頂点を破ることができる最も早い日です。 機能`earliest_k`プレイヤーとボスの強さの間の時間依存の不平等をエンコードし、A が B を超えるかどうかに応じて、待つことが役立つ場合もあれば悪い場合もあるという事実を尊重します。 

プライオリティ キューは、最適なキル日の昇順で頂点がファイナライズされることを保証します。`used`配列により、各頂点が 1 回処理されることが保証されます。

 ## 特殊なケース

 A ≤ B の場合に重要なエッジ ケースが発生します。この状況では、すべての遅延は何も起こらないか、将来の戦いをより困難にするかのどちらかです。 アルゴリズムは、頂点が到達可能ですでに削除可能であるまさにその瞬間にのみ頂点を受け入れることによってこれを処理します。 発見後すぐに殺せない場合は事実上廃棄されます。 

もう 1 つのエッジ ケースは、生きているボスの長いチェーンが原因で頂点 n に最初は到達できない場合です。 到達可能性はアクティブ化された頂点を介してのみ伝播するため、アルゴリズムは、そのブロッカーが明示的に強制終了されるまで、最初のブロックされた頂点を超えてノードを緩和することを正しく拒否します。 

最後の微妙なケースは、頂点が非常に早い段階で到達可能になるが、k が増加した後になって初めて削除可能になる場合に発生します。 優先キューは、それが時期尚早に選択されないことを保証し、代わりに、計算された最も早い実現可能な k がすべての候補の中で最小になるまで待機します。
