 ## 解決策
 ## 問題の理解

 ベラは毎日、自宅と職場という 2 つの固定された場所の間を移動します。 彼女は 1 日にちょうど 2 回バスに乗って、1 回目は自宅から職場へ、もう 1 回目は職場から自宅へ帰ります。 それぞれの場所に、ある程度の数の傘を保管している可能性があります。 

彼女は毎回旅行の前に、その特定の乗り物の天気をチェックします。 天気は雨が降るか降らないかのどちらかです。 彼女の決断は、純粋に天気に基づいているわけではありません。彼女は、雨が降っていないときでも傘を持たなければならないという規則に従っています。 

意思決定プロセスは 2 つのアイデアによって推進されます。 旅行中に雨が降った場合、彼女はいつも傘を持っています。 雨が降っていない場合、目的地に現在傘が保管されていない場合に限り、彼女は傘を持ち歩きます。そのため、場所を完全に空にすることは避けます。 彼女が傘を持ち歩くたびに、傘は現在地から目的地まで移動します。 彼女が傘を持っていなくても、傘の配布は変わりません。 

このタスクは、自宅にいるベラから始めて、自宅と職場での最初の傘の数を指定して、すべての 2N 旅行をシミュレートし、各旅行で彼女が傘を持ち歩いているかどうかを出力することです。 

制約は小さく、N は最大 10^4 で、各シミュレーション ステップは O(1) であるため、2N ステップにわたる線形シミュレーションは容易に制限内に収まります。 これは、旅行全体にわたる再計算やスキャンを伴うソリューションが不要であることも意味します。 

雨が降ったときだけ傘を持ち歩くと仮定すると、微妙な失敗例が生じます。 たとえば、天気が乾燥しているが、目的地に傘が 1 本もない場合でも、ベラは 1 本を移動します。これにより、将来の決定が変わります。 もう 1 つのエッジ ケースは、両方の場所が片側に傘がない状態で開始する場合です。最初のドライ トリップでは、雨が降っていなくても転送が強制され、その後の無効な状態が防止されます。 「宛先が空」ルールを無視した単純なアプローチは、すぐに正しい状態から乖離してしまいます。 

## アプローチ

 素朴な視点は、それぞれの旅行を独立して扱うことです。つまり、天気を確認し、雨の有無のみに基づいて傘を持っていくかどうかを決定します。 これは、「雨が降ったら傘を持っていく」ルールでは機能しますが、雨が降らない旅行になるとすぐに機能しません。これは、システムが家庭と職場の間での傘の配布の進化に依存しているためです。 それぞれの決定が将来の状態を変更するため、独立性の仮定は失敗します。 

強引だが正しい解釈は、このステートメントが説明していることを正確にシミュレートすることになります。つまり、両方の場所で傘の数を維持し、旅行のたびにそれらを更新します。 旅行ごとに、雨が降っていないか、目的地に傘がないかどうかを確認します。 どちらかの条件が当てはまる場合は、傘を 1 本現在の場所から目的地まで移動し、ベラが傘を持っていたことをマークします。 移動するたびに次の状態が変化するため、これは本質的に逐次的です。 

各トリップは前のトリップによって生成された正確な状態に依存するため、これ以上の漸近的な改善はありません。 ただし、構造は非常に単純であるため、ブルート シミュレーションはすでに最適化されています。 重要な観察は、必要な情報がすべて決定論的に展開する 2 つの整数に含まれているため、追加のデータ構造や前処理が必要ないことです。

 ## アルゴリズムのチュートリアル

 自宅の傘と職場の傘という 2 つの値を追跡しながら、システムを段階的にシミュレートします。 ベラの現在位置も追跡します。

1.自宅でBellaを初期化します。 自宅 = H、職場 = W とします。現在の場所は自宅です。 
2. 毎日、自宅から職場までの最初の移動を処理し、次に職場から自宅までの 2 番目の移動を処理します。 
3. 旅行ごとに、現在位置に基づいて目的地を特定します。 ベラが家にいる場合、目的地は仕事です。 それ以外の場合、目的地は自宅です。 
4. この旅行の天気を読みます。 雨が降っている場合、ベラは傘を持っていかなければなりません。 雨が降っていない場合、目的地に現在傘がない場合にのみ、彼女は傘を持って行きます。 

このルールにより、将来必要になる可能性がある状況で、少なくとも 1 本の傘を用意せずにその場所に到着することがなくなります。 
5. ベラが傘を取ることにした場合は、現在の場所でカウントをデクリメントし、目的地でカウントをインクリメントします。 旅行中に物理的に傘を持ち歩くモデルです。 
6. 彼女が傘を持った場合は「Y」を出力し、そうでない場合は「N」を出力します。 
7. ベラは常に家と職場の間を移動するため、旅行のたびにベラの現在の位置を反転します。 

### なぜ効果があるのか

 システムの状態は、自宅の傘、職場の傘、ベラの現在位置という 3 つの変数によって完全に記述されます。 各遷移は、現在の状態と次の気象条件にのみ依存します。 すべてのアクションは問題のルールと一貫して状態を更新するため、シミュレーションでは、カウントが常に各移動後の傘の真の分布を反映するという不変条件が維持されます。 将来の決定はこの状態以外のものに依存しないため、時間を順番にステップ実行することで正確さが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, h, w = map(int, input().split())
    
    home = h
    work = w
    at_home = True  # True = home, False = work
    
    out = []
    
    for _ in range(n):
        s = input().strip()
        
        for i in range(2):
            rain = s[i]
            
            if at_home:
                cur = home
                dest = work
            else:
                cur = work
                dest = home
            
            take = False
            if rain == 'Y' or dest == 0:
                take = True
            
            if take:
                if at_home:
                    home -= 1
                    work += 1
                else:
                    work -= 1
                    home += 1
                out.append('Y')
            else:
                out.append('N')
            
            at_home = not at_home
    
    # print grouped by day
    for i in range(0, len(out), 2):
        print(out[i] + out[i+1])

if __name__ == "__main__":
    solve()
```実装はシミュレーションに直接従います。 ブール値`at_home`ベラの位置を追跡し、現在の旅行の方向を常に把握できるようにします。 重要な決定ラインは条件です`rain == 'Y' or dest == 0`、問題の両方のルールをエンコードします。 更新ステップでは、場所間で傘を 1 つだけ移動し、合計数を維持します。 

出力はフラット リストに収集され、必要な形式に合わせて 1 日あたり 2 部ずつ印刷されます。 

よくある間違いは、移動のたびに位置を反転するのを忘れたり、ソースをデクリメントせずに目的地のみを誤って更新したりすることです。 どちらも傘の保存に違反し、後の状態の矛盾を引き起こす可能性があります。

 ## 特殊なケース

 エッジ ケースの 1 つは、1 つの場所で傘が 0 から始まる場合です。 そのような状況では、雨が降っていなくても、他の場所からの最初の移動でほとんどの場合、強制移動がトリガーされます。 条件が次のとおりであるため、シミュレーションはこれを自然に処理します。`dest == 0`が true になると、アルゴリズムはすぐに傘を移動し、状態が確実にバランスが取れるようにします。 

もう 1 つのケースは、雨が降ったり降らなかったりすることが交互に起こり、傘が場所間で揺れる場合です。 ステップバイステップのシミュレーションでは、次の決定が行われる前に各旅行で正確な位置カウントが更新されるため、正確さが保証されます。 

最後のケースは、傘が片側に大量に溜まる場合です。 それでも、ルールは目的地がゼロか雨が降っているかどうかにのみ依存するため、カウントが大きくても複雑さや正確さは変わりません。 アルゴリズムは、大きさに関係なく、同じ定数時間遷移ルール​​を適用し続けます。
