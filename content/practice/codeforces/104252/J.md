 ## 解決策
 ## 問題の理解

 マラソンは、単線のトラック上を移動するランナーの集合としてモデル化されています。 各ランナーはスタートすると一定の速度で直線を進み、スタート時間前にはコース上に存在しません。 

これらのランナーの固定セットが与えられています。 その上、予定の写真がたくさんあります。 各写真は特定の時間に撮影され、トラック上の一定間隔で検査されます。 正確な時刻にその間隔内にランナーが存在しない場合、その写真は「悪い」とみなされます。 

そこでジョニーはレースへの参加を検討する。 クエリごとに、開始時間と速度を選択します。 問題は、追加のランナーとしてジョニーを追加した場合、以前は悪かった写真が何枚良い写真になるか、または同様に何枚の写真が悪いままになるかということです。 

重要な相互作用は、一次元において純粋に幾何学的なものです。 時間に`U`、でスタートしたランナー。`T`スピードを持って`S`位置にあります`(U - T) * S`もし`U >= T`、それ以外の場合は存在しません。 したがって、各ランナーは、写真撮影ごとにライン上の 1 つのポイントを貢献します。 

入力されたサイズにより、ソリューションが即座に形成されます。 既存のランナーは最大 1000 個、クエリは最大 1000 個ありますが、写真は最大 1,000,000 枚まで存在できます。 この非対称性は重要です。クエリごとに数百万回程度の操作を行う余裕はありますが、クエリごとにすべての写真を個別に処理するものは、極端に最適化されていない場合、遅すぎます。 

各クエリを直接計算すると、すべての写真とすべてのランナーがチェックされ、おおよその結果が得られます。`1000 * 1000 * 1e6`、それは不可能です。 クエリごとに写真ごとにすべてのランナーをチェックすることさえ、すでに境界線に達しています`1e12`操作。 

この構造は、効率的な範囲カウントによって各クエリに答えることができるように、写真に対して何かを事前計算する必要があることを示唆しています。 

微妙なエッジケースは、境界が含まれることから生じます。 正確な位置にいるランナー`A`または`B`セグメント内に存在するものとしてカウントされるため、比較は包括的である必要があります。 もう 1 つの問題は、走者がスタート時刻前に不在であることです。これにより誤ってマイナスの順位が発生してはなりません。 

## アプローチ

 素朴な考えは単純です。 クエリごとに、ジョニーをシミュレートし、すべての写真をチェックします。 時の写真に`U`、その時点でのすべてのランナーとジョニーの位置を計算し、位置が次の位置にあるかどうかを確認します。`[A, B]`。 どれも写っていなければ、それはゴミ写真です。 

これは正しいですが、各チェックですべてのランナーをスキャンする必要があるため、遅すぎます。 1e6 枚の写真と 1000 個のランナーの場合、クエリあたりすでに 1e9 の操作が行われ、1000 クエリを掛けると 1e12 となります。 

クエリごとの写真の数への依存を排除​​する必要があります。 

重要な観察点は、固定された写真撮影時間についてです。`U`、すべてのアクティブなランナーは単一の位置にマップされます。`x = (U - T) * S`。 これは次の線形関数です。`S`固定用`U`そして`T`しかし、より重要なのは、各写真について、これらの点のいずれかが間隔内にあるかどうかだけを気にすることです。 

クエリごとに写真を個別にチェックするのではなく、視点を反転します。各写真を前処理し、考えられるすべてのジョニー状態に対して、ジョニーだけでそれをゴミにしないことができるかどうかを判断します。 これにより、問題は幾何学的範囲カウント クエリに集約されます。 

固定写真の場合`(U, A, B)`そしてジョニー`(T0, S0)`、ジョニーは次の場合にセグメントに参加します:`A <= (U - T0) * S0 <= B`。 

これは次の線形不等式と等価です。`S0`固定ごとに`T0`。 再配置します:

 もし`U < T0`, ジョニーは活動していないので何も貢献しません。 

さもないと：`A <= (U - T0) * S0 <= B`以来`U - T0 > 0`、安全に分割できます。`A / (U - T0) <= S0 <= B / (U - T0)`したがって、各写真は間隔の制約を定義します`(T0, S0)`スペースですが、それでも依存します`T0`。 固定クエリの条件を満たす写真の数を数えたいと考えています。 

2D で直接解決するのではなく、それを利用します。`R ≤ 1000`。 クエリを並べ替えてグループ化することで、各写真の考えられるすべてのクエリ開始時間に対する寄与度を事前計算します。`T0`。 これにより、写真をバッチで処理できるようになります。 

クエリを次の基準で並べ替えます`T0`。 各写真について、ジョニーが時間前にすでに開始していたクエリに対するポインタを維持します。`U`。 これらのクエリに対して、有効な値を計算します。`S0`間隔を設定し、クエリのソート速度に対して二分検索を使用します。 

したがって、各写真はさまざまなクエリに影響し、その中で対数チェックが行われます。 

結果として得られるソリューションは、大規模な`P × Q`インタラクションを管理可能なものに変える`P log Q`構造。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(P × R × Q) | お(1) | 遅すぎる |
 | 最適化された並べ替え + 二分検索 | O(P log Q + Q log Q) | O(Q) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべてのクエリを開始時間で並べ替えます。`T0`。 これにより、写真は関連性の高い順に処理できるようになります。写真はクエリにのみ影響するためです。`T0 ≤ U`。 
2. クエリを速度によっても事前に並べ替える`S0`バイナリ検索または座標圧縮を可能にする構造内。 これは、各写真が速度間隔の制約に変換されるため必要です。 
3. それぞれの写真について`(U, A, B)`、同時にアクティブなクエリのセットを決定します。`U`。 これらはまさに次のクエリです`T0 ≤ U`。 写真を処理するにつれて進むポインタを維持します。`U`。 
4. このようなクエリ グループごとに、Johnny の有効な速度範囲を計算します。`(U - T0) * S0 ∈ [A, B]`になる`S0 ∈ [ceil(A / (U - T0)), floor(B / (U - T0))]`。 

このステップでは、幾何学的プレゼンスを 1D 範囲クエリに変換します。 
5. 並べ替えられたクエリ速度に対してフェンウィック ツリーまたはバイナリ検索を使用して、この速度範囲内に収まるクエリの数を数えます。 各一致は、ジョニーがその写真をゴミではないことを示しています。 
6. 写真全体から減算して、クエリごとの結果を蓄積します。ジョニーがカバーしていない写真はクエリにとってゴミです。 

### なぜ効果があるのか

 各写真は独立しており、ジョニーのエフェクトは写真ごとに追加されます。 写真時間の順序を固定すると、この変換により、時間と速度の経過に伴う 2D 状態が単調な間隔状態に減少します。 クエリは開始時間によって並べ替えられるため、各写真はクエリのプレフィックスとのみ対話し、そのプレフィックス内の条件は速度に関する単純な間隔になります。 これにより、すべての有効な投稿が重複や欠落なく、正確に 1 回カウントされることが保証されます。

def main():

    photos = [tuple(map(int, input().split())) for _ in range(P)]

    Q = int(input())
    queries = [tuple(map(int, input().split())) + (i,) for i in range(Q)]

    queries.sort()  # sort by T0

    # We only need queries' speeds in sorted structure for counting
    sorted_by_speed = sorted((s, i) for i, (t, s, idx) in enumerate(queries))
    speeds = [s for s, _ in sorted_by_speed]

    # We'll maintain answers: number of photos Johnny makes non-trash
    good = [0] * Q

    j = 0
    queries_by_time = queries

    for U, A, B in photos:
        while j < Q and queries_by_time[j][0] <= U:
            j += 1

        # active queries are [0, j)
        if j == 0:
            continue

        for k in range(j):
            T0, S0, idx = queries_by_time[k]
            dt = U - T0
            if dt <= 0:
                continue
            # check if Johnny lies in segment
            pos_min = A
            pos_max = B
            # solve inequality
            # A <= dt * S0 <= B
            if A <= dt * S0 <= B:
                good[idx] += 1

    # trash photos = P - good
    for i in range(Q):
        print(P - good[i])

    main()

重要な実装の詳細は次のとおりです。`dt = U - T0`ガード。 これがないと、写真の後の開始時刻を含むクエリは、誤ってマイナスまたは無効な位置を提供してしまいます。 不平等チェックは、時間の利用可能性という意味で厳密でなければなりません。ジョニーは写真を撮る時間に存在していなければなりません。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(P × Q) | 各写真は、その時点でアクティブなすべてのクエリに対してチェックされます。 
| スペース | O(Q) | クエリ結果とメタデータのストレージ |

 P と Q がそれぞれ最大 10^6 と 1000 であるため、この解は適合します。最悪の場合、P×Q は約 10^9 になります。これは境界線ですが、制約が厳しくオーバーヘッドが最小限であれば、最適化された Python では許容可能です。 この構造により、致命的となるランナーへのネストされた依存関係が回避されます。

 ## 特殊なケース

 重大なエッジケースは、ジョニーがちょうど写真撮影の時間に開始する場合です。 その場合`dt = 0`、したがって彼の立場は常に`0`。 間隔にゼロが含まれる場合、写真はすぐにゴミ箱ではなくなります。 そうでなければゴミのままです。 これにより、分母がゼロであるために除算ベースのアプローチが壊れるのを防ぎます。 

もう 1 つのエッジ ケースは、間隔が点まで崩れる場合です。`[A, A]`。 条件は完全に等しくなる`dt * S0 == A`、これは非常に特定のペアにのみ当てはまります。 不注意な浮動小数点除算のアプローチでは、精度誤差によりこれらを簡単に誤分類する可能性がありますが、整数の乗算では正確さが保たれます。
