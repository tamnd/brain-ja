 ## 解決策
 ## 問題の理解

 ランタンの列を表すバイナリ文字列が与えられます。各位置は 0 または 1 です。1 回の操作で、連続するセグメントを選択し、その中のすべてのビットを反転して、0 を 1 に、1 を 0 に変換します。目標は、セグメントの反転をできるだけ少なくして、文字列全体がすべて 0 またはすべて 1 になる構成に到達することです。 

重要な点は、単一ポジションのフリップに限定されないということです。 各移動は間隔全体に影響を与える可能性があるため、適切に選択されたセグメントに複数の不一致がある場合、1 回の操作で複数の不一致を一度に修正できます。 難しいのは、新しい境界を作成するのではなく、将来の修正の数を減らすセグメントを選択することにあります。 

入力サイズは最大 100,000 文字まで可能です。 考えられるすべてのセグメントを試行したり、インデックスのすべてのペア間の遷移を評価したりするソリューションには、n² または n³ のオーダーの操作が含まれますが、これは実現可能な限界をはるかに超えています。 1 秒の制約の下では O(n log n) または O(n) が現実的なターゲット範囲であるため、線形または線形に近い戦略が必要です。 

素朴だが魅力的なアイデアは、左から右への反転操作を貪欲にシミュレートし、常にその位置から後の点に反転することで最初の不一致を修正することです。 早期の決定により、以前に修正された領域に新たな不一致が生じる可能性があるため、これは失敗する可能性があります。 

たとえば、次のように考えてみましょう`S = 0101`。 貪欲にすべてを 0 にしようとすると、計画なしにプレフィックスや最小限のセグメントを反転すると、操作が過剰にカウントされる可能性があります。 間違った貪欲な選択はひっくり返る可能性があります`01`→`10`、その後続行すると、最適な 2 回のフリップにもかかわらず、必要以上の操作が必要になります。`[1..4]`または境界を揃える 2 つの構造化されたフリップ。 

もう 1 つの微妙なエッジ ケースは、文字列がすでに均一である場合です。`00000`または`11111`。 少なくとも 1 つの操作が必要であると想定するアルゴリズムでは、ゼロではなく正の値が誤って返されます。 

最後に、次のような文字列を交互に配置します。`010101...`重要です。 すべての位置がセグメント間の境界であるため、これらは、ソリューションが実際の値ではなく遷移の数に敏感であるかどうかを明らかにします。 

## アプローチ

 ブルートフォースの観点は、各操作を間隔を選択して反転し、文字列が均一になるまでその間隔の可能なシーケンスをすべてシミュレートすることであると考えることです。 深さを k 個の操作に制限した場合でも爆発が発生します。操作ごとに O(n²) 個の選択肢があり、シーケンスが指数関数的に増加します。 これは、n が小さい場合でもすぐに実行不可能になります。 

問題を捉える別の方法は、間隔を主な対象として考えるのをやめ、代わりにセグメントを反転したときに文字列の構造がどのように変化するかに焦点を当てることです。 反転は均一領域内では問題ではなく、0 と 1 の間の遷移が発生する場所でのみ変化します。 重要なのは、個々の文字ではなく、連続する異なる文字間の境界であるということです。 

文字列をすべて 0 にしようとすると、連続する 1 のブロックをすべて削除する必要があります。 各操作では、その選択方法に応じて、そのようなブロックを 1 つ以上正確に削除できますが、最小限の戦略はこれらのブロックを数えることに対応します。 同様に、すべての 1 をターゲットにする場合は、代わりに 0 のブロックをカウントします。 各フリップは間違ったビットの連続する 1 つのグループを最適に削除できるため、答えはこれら 2 つのカウントの間の最小値になります。 

問題は、文字列をスキャンし、等しい文字の連続をカウントすることに帰着します。 各ランは、同一ビットの最大セグメントを表します。 すべて 0 に変換するには 1 の実行数がかかり、すべて 1 に変換するには 0 の実行の数がかかります。

 ## アルゴリズムのチュートリアル

 問題を文字間の遷移をカウントすることに還元します。これは、連続したブロックをカウントすることに直接対応します。 

1. 文字列内の連続する同一文字のセグメントの数を計算します。 これは、左から右にスキャンし、現在の文字が前の文字と異なるたびにカウンタをインクリメントすることによって行われます。 これにより、実行の合計数が得られます。 
2. 0 と 1 の実行数を別々に導出します。 合計実行数が k 個の場合、それらは 0 と 1 の間で切り替わるので、開始文字に応じて両方のカウントを計算できます。 
3. 1 に対応する実行の数を数えます。 これは、すべての 1 ブロックを少なくとも 1 回の反転操作で削除する必要があるため、すべてを 0 にしたい場合に必要な操作の数に等しくなります。 
4. 0 に対応する実行の数を数えます。 これはすべてを 1 に変えるコストです。 
5. これら 2 つの値の最小値を出力します。 

両方のターゲットを明示的に評価する理由は、どちらの均一な状態でも自由に終了できること、および構造に応じて 1 つの方向で必要な反転が厳密に少なくなる可能性があるためです。 

### なぜ効果があるのか

 連続したセグメントを反転すると、その境界にある実行全体のステータスのみが変更されます。 実行内での反転は新しい構造を作成せず、実行の値を切り替えるだけです。 したがって、最小のフリップ数は、望ましくない値のランをすべて削除することに相当し、隣接するランを暗黙的にマージすることなく複数の交互境界構造を削除する操作はありません。 これにより、特定の値の実行数の下限が決まり、各実行を個別に選択することで達成可能になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    s = input().strip()

    if n == 0:
        print(0)
        return

    # count runs of 0 and 1
    runs0 = 0
    runs1 = 0

    prev = None

    for ch in s:
        if ch != prev:
            if ch == '0':
                runs0 += 1
            else:
                runs1 += 1
        prev = ch

    # cost to make all 0s = number of 1-runs
    # cost to make all 1s = number of 0-runs
    print(min(runs0, runs1))

if __name__ == "__main__":
    solve()
```このコードは、新しい実行がいつ開始されるかを追跡しながら、文字列に対して 1 回のパスを実行します。 現在の文字が前の文字と異なる場合は常に、ランが検出されます。 すべての実行を明示的に保存する代わりに、0 実行と 1 実行に対してカウンターを直接インクリメントします。 

微妙な詳細は、`prev`として`None`これにより、最初の文字が常に新しい実行を開始するようになります。 もう 1 つの詳細は、境界でのみ実行カウンターをインクリメントすることで、二重カウントを回避します。

 ## 特殊なケース

 次のような完全に均一な文字列の場合`00000`、ループは依然として 0 の実行を 1 回、1 の実行を 0 回だけカウントします。 遷移がトリガーされず、反転も必要ないため、最小値はゼロになります。 

次のような完全に交互の文字列の場合`010101`、文字が変更されるたびに新しい実行がトリガーされ、0 と 1 の両方の実行の最大数が生成されます。 アルゴリズムは自然に各境界をカウントし、最終的な答えは、すべての交互ブロックを単一の均一な状態にマージするために必要なセグメント反転の最小数を反映します。 

単一の文字入力の場合は次のようになります`1`、イニシャル`prev = None`実行が正しく作成されることを保証します。また、遷移がないため、結果はゼロとなり、文字列がすでに均一であるという事実と一致します。
