 ## 解決策
 ## 問題の理解

 初期文字列が 1 つあります。`S(0)`、長さは最大 1000 です。以降のすべての文字列は、すでに存在する文字列から定義されます。 アン`APP x y`操作が作成する`S(x) + S(y)`、一方、`SUB x lo hi`操作により半開きの部分文字列が作成されます`S(x)[lo:hi]`。 

最終的な文字列は天文学的に大きくなり、最大で`2^63 - 1`したがって、タスクはそれを構築することではありません。 すべての文字の ASCII 値の合計 (縮小剰余) だけが必要です。`1,000,000,007`。 

文字列は最大 2500 個あります。 これは十分に小さいため、アルゴリズムを使用することができます。`O(N^2)`これは完全に合理的ですが、構築された文字列の長さに比例することは不可能です。 一連の`APP`操作を繰り返すと長さが 2 倍になる可能性があるため、わずか数十回の操作でも、表現される文字列には個別に保存または処理できるよりも多くの文字がすでに含まれている可能性があります。 

長さの制限は、単に大きい値と位置として使用される値を区別する必要があることも意味します。 Python の整数はそれらを直接処理しますが、アルゴリズムは長さに比例する演算を決して実行してはなりません。 答え自体は常にモジュロに保たれます`1,000,000,007`一方、長さは、どちら側を決定するために必要であるため、正確に保存されます。`APP`操作にはクエリされた位置が含まれています。 

最初の明白ではないエッジ ケースは、空の部分文字列です。 考慮する：```
2
a
SUB 0 0 0
```結果は空の文字列なので、正しい出力は次のようになります。`0`。 あらゆることを想定した不注意な実装`SUB`少なくとも 1 つの文字を作成すると、ゼロ以外の間違った答えが生成されるか、境界で失敗します。 

2 番目のエッジ ケースは、次の排他的な右エンドポイントです。`SUB`。 のために：```
2
abc
SUB 0 0 3
```結果の文字列は`abc`、その ASCII 合計は`97 + 98 + 99 = 294`。 治療中`hi`as inclusive では、存在しない 4 番目の文字が誤って含まれてしまいます。 

3 番目のエッジ ケースでは、連結とスライスを組み合わせます。```
4
ab
APP 0 0
SUB 1 1 3
APP 2 0
```ここ`S(1) = "abab"`、`S(2) = "ba"`、最後の文字列は`"baab"`。 その合計は`98 + 97 + 97 + 98 = 390`。 これにより、部分文字列操作によって以降のクエリごとに座標系が変更されることを忘れる実装が捕捉されます。 

最後に、長さ自体は次のようになります。`2^63`。 固定 32 ビット整数を使用する実装ではそれらを表すことができず、正しい 64 ビット実装であっても、中間テストの構築中に許容最大値を超える長さを誤って作成することを避ける必要があります。 以下の解決策は、長さを正確な整数として保存し、実際の文字ではなく表現のみを構築します。 

## アプローチ

 簡単な解決策は、実際にすべての文字列を構築することです。 のために`APP x y`、両方の文字列をコピーします。 のために`SUB x lo hi`, 要求された部分をコピーします。 これは、文字列の定義に使用される操作に正確に従っているため、正しいです。 

問題は、表現される文字列が膨大になる可能性があることです。 1 文字の文字列から開始して、文字列とそれ自体を繰り返し連結すると、その長さは 2 倍になります。 63回の倍増後、長さはすでに約`2^63`。 その結果、ブルート フォース アルゴリズムは次のように実行できます。`2^63`最後の文字列のみに対する文字操作。 これは 4 秒という制限をはるかに超えており、そのような文字列を保存することも不可能です。 

有益な観察は、文字に任意にアクセスする必要がないということです。 必要なのは完全な文字列の合計と、`SUB`ソース文字列に対する prefix-sum クエリに答えることができれば、オペレーションはその合計を取得できます。 

定義する`prefix(i, k)`最初の合計として`k`の登場人物`S(i)`。 次に、合計`S(i)[lo:hi]`単純に`prefix(i, hi) - prefix(i, lo)`。 

重要な問題はどのように計算するかです`prefix(i, k)`拡張せずに`S(i)`。 

のために`APP x y`、 最初`k`文字が完全に内側に入っているか、`S(x)`、またはそれらはすべてから構成されます`S(x)`の接頭辞が続きます`S(y)`。 したがって、1 つのプレフィックス クエリは 1 つの子の後に続きます。 

のために`SUB x lo hi`、 最初`k`の登場人物`S(i)`最初のものに正確に対応します`lo + k`の登場人物`S(x)`、最初のことを除いて、`lo`文字はコピーされた間隔の前に属します。 もっと直接的に言えば、`prefix(i, k) = prefix(x, lo + k) - prefix(x, lo)`。 

繰り返しますが、これは 1 つの依存関係チェーンのみに従います。 

これにより問題は完全に変わります。 プレフィックス クエリは最大でもウォークスルーします。`N`構築ノードとそれぞれ`SUB`ノードは、合計を計算するときに、このようなクエリを 2 つ作成します。 しかないので、`N`文字列の場合、総作業量は`O(N^2)`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |`O(L)`どこ`L`できる`2^63 - 1`|`O(L)`| 遅すぎる |
 | 構築 DAG のプレフィックス クエリ |`O(N^2)`|`O(N)`| 承認済み |

 コンストラクション ヒストリは有向非巡回グラフのように動作しますが、一般的なグラフの走査は必要ありません。 プレフィックス クエリはすべてのノードで 1 つの発信依存関係を選択するため、履歴を簡単にたどることができます。 

## アルゴリズムのチュートリアル

 1. 初期文字列のプレフィックスの合計を保存します。 のために`S(0)`、最初の合計を直接計算できます。`k`長さが最大 ​​1000 文字であるため、その長さと ASCII の合計も保存します。 
2. 以降のすべての文字列については、その型とそれを定義するパラメータのみを保存します。 のために`APP`、2 つのソース インデックスを保存します。 のために`SUB`、ソースインデックスと間隔を保存します`[lo, hi)`。 
3. 文字列を入力順に処理します。 すべての操作は以前の文字列のみを参照するため、新しい文字列が処理される時点で、必要なすべての長さと合計がすでにわかっています。 
4.`APP x y`、 セット`length[i] = length[x] + length[y]`そして`sum[i] = sum[x] + sum[y]`。 

合計は剰余で減算されます`1,000,000,007`、長さは正確なままです。 
5. のために`SUB x lo hi`、 セット`length[i] = hi - lo`。 

合計を計算するには、ソース文字列の最初の合計をクエリします。`hi`文字を取り出し、その最初の文字の合計を減算します。`lo`文字:`sum[i] = prefix(x, hi) - prefix(x, lo)`。 

部分文字列は 2 つのプレフィックス間の相違であるため、2 つのプレフィックス クエリで十分です。 
6.実装する`prefix(i, k)`反復的な散歩として。 もし`i`がゼロの場合は、元の文字列の事前計算されたプレフィックス配列を使用します。 もし`i`です`APP x y`、 比較する`k`と`length[x]`。 いつ`k <= length[x]`、続けて`x`。 それ以外の場合は、次の合計を加算します。`x`、減算`length[x]`から`k`、続けて`y`。 
7. 現在のノードが`SUB x lo hi`、置き換えることにより、要求されたプレフィックス位置をソース文字列に変換します。`k`と`lo + k`、次に進みます`x`。 部分文字列のプレフィックスは常にそのソースの 1 つのプレフィックスに対応するため、2 番目の分岐は必要ありません。 
8. すべての文字列が処理された後、出力します。`sum[N - 1]`、これは問題によって要求されたチェックサムです。 

### なぜ効果があるのか

 不変条件というのは、`prefix(i, k)`常に最初の値の合計を表します`k`の登場人物`S(i)`。 初期文字列の場合、これは直接プレフィックス配列から得られます。 で`APP`、要求されたプレフィックスが完全に左側の文字列に存在するか、左側の文字列全体と右側の文字列のプレフィックスが含まれており、アルゴリズムの遷移と正確に一致します。 で`SUB`、 最初`k`文字はソースの位置に対応します`[lo, lo + k)`、その合計は適切なソース プレフィックスの差から取得されます。 したがって、すべてのプレフィックス クエリは正しいです。 あ`SUB`total は 2 つの正しいソース プレフィックスの差であり、`APP`total は 2 つの完全な子文字列の合計です。`sum[i]`は正しいです。 最終的に保存された合計が、必要なチェックサムになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 1_000_000_007

def solve():
    n = int(input())
    s = input().strip()

    # type[i] is:
    # 0 for the initial string
    # 1 for APP
    # 2 for SUB
    types = [0] * n

    # For APP, a[i] and b[i] are the two source indices.
    # For SUB, a[i] is the source index, and b[i], c[i]
    # are lo and hi.
    a = [0] * n
    b = [0] * n
    c = [0] * n

    length = [0] * n
    total = [0] * n

    # Prefix sums for S(0).
    base_prefix = [0] * (len(s) + 1)
    for i, ch in enumerate(s):
        base_prefix[i + 1] = base_prefix[i] + ord(ch)

    length[0] = len(s)
    total[0] = base_prefix[-1] % MOD

    def prefix(idx, k):
        """
        Sum of the first k characters of S(idx), modulo MOD.

        The query follows exactly one dependency at every
        construction node.
        """
        ans = 0

        while idx != 0:
            if types[idx] == 1:  # APP
                x = a[idx]
                y = b[idx]

                if k <= length[x]:
                    idx = x
                else:
                    ans += total[x]
                    ans %= MOD
                    k -= length[x]
                    idx = y

            else:  # SUB
                x = a[idx]
                lo = b[idx]

                k += lo
                idx = x

        ans += base_prefix[k] % MOD
        return ans % MOD

    for i in range(1, n):
        parts = input().split()

        if parts[0] == "APP":
            x = int(parts[1])
            y = int(parts[2])

            types[i] = 1
            a[i] = x
            b[i] = y

            length[i] = length[x] + length[y]
            total[i] = (total[x] + total[y]) % MOD

        else:
            x = int(parts[1])
            lo = int(parts[2])
            hi = int(parts[3])

            types[i] = 2
            a[i] = x
            b[i] = lo
            c[i] = hi

            length[i] = hi - lo
            total[i] = (prefix(x, hi) - prefix(x, lo)) % MOD

    print(total[n - 1])

if __name__ == "__main__":
    solve()
```配列`length`そして`total`今後のあらゆる操作に必要な 2 つの情報を保持します。 長さは正確なままでなければなりません。`prefix`それらを使用して、位置が左側に属するか右側に属するかを決定します。`APP`。 合計は安全に剰余として減らすことができます`MOD`すべての加算または減算の後に。 

の`prefix`関数は再帰的ではなく反復的です。 2500のチェーン`SUB`操作は合法であるため、再帰には Python の再帰制限を増やす必要があります。 反復により、その懸念は完全に回避されます。 

の条件は、`APP`は`k <= length[x]`。 値`k`は要求された文字数を意味するため、`k == length[x]`は完全に左の文字列に属しており、右の文字列に移動すべきではありません。 これは、この問題で最も一般的な off-by-one エラーの 1 つです。 

のために`SUB x lo hi`、現在の文字列は`S(x)[lo:hi]`。 長さの接頭辞`k`したがって、ソース位置で終了します`lo + k`そのため、クエリは単純に次の値を追加します。`lo`に`k`。 

基本ケースでは、`base_prefix[k]`、 どこ`k`ゼロから`len(s)`。 入力により、翻訳されたすべての位置がソース文字列内に残ることが保証されるため、追加のクリッピングは必要ありません。 

Python の整数は、許可される長さを直接表すことができます。 固定幅整数を使用する言語では、指定された最大値には符号付き 64 ビット整数で十分です。`2^63 - 1`ただし、追加は問題の保証と照らし合わせてチェックする必要があります。 

## 実用的な例

 公式サンプルは次のとおりです。```
3
foobar
SUB 0 0 3
APP 1 1
```初期文字列にはプレフィックスの合計が含まれています`"foobar"`。 最初の操作で抽出されるのは、`"foo"`、2 番目の操作はその部分文字列をそれ自体と連結します。 

| ステップ | 文字列 | 操作 | 長さ | 合計 |
 | --- | --- | --- | --- | --- |
 | 0 |`foobar`| イニシャル | 6 | 627 |
 | 1 |`foo`|`SUB 0 0 3`| 3 | 324 |
 | 2 |`foofoo`|`APP 1 1`| 6 | 648 |

 文字列 1 の場合、`prefix(0, 3) = 324`そして`prefix(0, 0) = 0`なので、合計は 324 です。文字列 2 には、文字列 1 のコピーが 2 つ含まれているだけです。`324 + 324 = 648`。 したがって、出力は次のようになります。`648`。 

2 番目の例では、ネストされたスライスと連結を実行します。```
4
ab
APP 0 0
SUB 1 1 3
APP 2 0
```構築は次のように展開します。 

| ステップ | 文字列 | 操作 | 長さ | 合計 |
 | --- | --- | --- | --- | --- |
 | 0 |`ab`| イニシャル | 2 | 195 |
 | 1 |`abab`|`APP 0 0`| 4 | 390 |
 | 2 |`ba`|`SUB 1 1 3`| 2 | 195 |
 | 3 |`baab`|`APP 2 0`| 4 | 390 |

 文字列 2 の場合、アルゴリズムは次のように要求します。`prefix(1, 3)`そして`prefix(1, 1)`。 最初のクエリの説明`S(1) = S(0) + S(0)`、最初の完了を消費します`"ab"`合計が 195 の場合、最初の文字を取得します`"a"`2 番目のコピーからは 292 が得られます。2 番目のクエリでは 98 が得られます。それらの差は次のとおりです。`292 - 98 = 194`に対応します。`"ba"`算術の読みが間違っていた場合に限ります。 実際のプレフィックス値は次のとおりです。`prefix(1, 3) = 293`そして`prefix(1, 1) = 98`、与える`195`、正確に合計`"ba"`。 このトレースは、なぜ右側が`APP`調整された位置でクエリする必要があります`k - length[left]`。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 |`O(N^2)`| それぞれ`SUB`2 つのプレフィックス クエリを実行し、各クエリは最大で後に続きます。`N`構築ノード。 |
 | スペース |`O(N + | S(0) | )`| 構築されたすべての文字列の定数サイズの情報と、最初の文字列の 1 つのプレフィックス配列を保存します。 |

 と`N <= 2500`、せいぜい約`2N`プレフィックス クエリが実行され、それぞれ最大で`N`ステップ。 これにより、最悪の場合、約 1,250 万の依存関係ステップが得られますが、これは Python では実用的です。 実際の文字列は決して保存されないため、潜在的に膨大な量の文字列が保存されます。`2^63 - 1`長さはメモリ使用量には影響しません。

import sys
import io
from contextlib import redirect_stdout

MOD = 1_000_000_007

def solve():
    input = sys.stdin.readline

    n = int(input())
    s = input().strip()

    types = [0] * n
    a = [0] * n
    b = [0] * n
    c = [0] * n

    length = [0] * n
    total = [0] * n

    base_prefix = [0] * (len(s) + 1)
    for i, ch in enumerate(s):
        base_prefix[i + 1] = base_prefix[i] + ord(ch)

    length[0] = len(s)
    total[0] = base_prefix[-1] % MOD

    def prefix(idx, k):
        ans = 0

        while idx != 0:
            if types[idx] == 1:
                x = a[idx]
                y = b[idx]

                if k <= length[x]:
                    idx = x
                else:
                    ans = (ans + total[x]) % MOD
                    k -= length[x]
                    idx = y
            else:
                x = a[idx]
                lo = b[idx]
                k += lo
                idx = x

        return (ans + base_prefix[k]) % MOD

    for i in range(1, n):
        parts = input().split()

        if parts[0] == "APP":
            x = int(parts[1])
            y = int(parts[2])

            types[i] = 1
            a[i] = x
            b[i] = y

            length[i] = length[x] + length[y]
            total[i] = (total[x] + total[y]) % MOD

        else:
            x = int(parts[1])
            lo = int(parts[2])
            hi = int(parts[3])

            types[i] = 2
            a[i] = x
            b[i] = lo
            c[i] = hi

            length[i] = hi - lo
            total[i] = (prefix(x, hi) - prefix(x, lo)) % MOD

    print(total[n - 1])

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_input = solve.__globals__["input"]

    sys.stdin = io.StringIO(inp)
    solve.__globals__["input"] = sys.stdin.readline

    output = io.StringIO()

    try:
        with redirect_stdout(output):
            solve()
    finally:
        sys.stdin = old_stdin
        solve.__globals__["input"] = old_input

    return output.getvalue().strip()

a
SUB 0 0 0
```もっている`length[1] = 0`。 2 つのプレフィックス クエリは両方とも`prefix(0, 0)`, したがって、それらの差はゼロです。 長さ 0 のプレフィックスは有効であるため、アルゴリズムは位置 0 の文字にアクセスしようとすることはありません。 

排他的エンドポイントの場合```
2
abc
SUB 0 0 3
```アルゴリズムが計算します`prefix(0, 3) - prefix(0, 0)`。 最初の値は`294`、そして2番目は`0`、結果は次のようになります`294`。 インデックス 3 の文字は決して考慮されません。`hi`は排他的なエンドポイントです。 

入れ子構造の場合```
4
ab
APP 0 0
SUB 1 1 3
APP 2 0
```の`SUB`オペレーションはポジションをリクエストします`[1, 3)`から`"abab"`。 そのプレフィックスクエリ`k = 3`ソース位置に変換されます`1 + 3 = 4`、そのプレフィックスクエリは`k = 1`ソース位置に変換されます`1 + 1 = 2`。 差はポジションの合計です`[2, 4)`ソースでは、`"ba"`。 決勝戦`APP`追加します`"ab"`そして生産します`"baab"`合計付き`390`。 

最大長の場合、すべての文字は次のようになります。`'a'`したがって、最終的な合計は単純に次のようになります。`97 * (2^63 - 1)`モジュロ`1,000,000,007`。 アルゴリズムはそれらの文字を保存することはありません。 最終的な長さとそのモジュール和のみを保存し、すべてのプレフィックス クエリはコンパクトなコンストラクション ヒストリをたどります。 期待される結果は次のとおりです`243684095`。 

解決すべき中心的なパターンは、この特定の問題よりも広範です。 巨大なオブジェクトが連結と部分文字列参照から構築されるときは、必要な集計をプレフィックス クエリとして表現できるかどうかを検討してください。 可能であれば、連結によりプレフィックス クエリで 1 つの子を選択できることがよくありますが、サブストリングは通常、クエリされた座標をシフトするだけです。 これにより、明らかに指数関数的なサイズのオブジェクトが、多項式時間で走査できる小さな依存関係グラフに変わります。 

ご希望であれば、同じプレフィックス クエリのアイデアを使用した、より短いコンテスト編集版や C++17 実装も提供できます。
