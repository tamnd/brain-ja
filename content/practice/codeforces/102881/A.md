 ## 解決策
 ## 問題の理解

 左から右にたどって文字を収集するために使用できる、文字列の最も短い連続部分を見つける必要があります。`A`、`B`、`C`、...、`Z`順番に。 選択した部分はアルファベットと直接一致する必要はありません。 余分な文字は、その中に正確に昇順のアルファベットのサブシーケンスが存在する限り許可されます。 

各テスト ケースでは、英大文字の文字列が与えられます。 答えは、文字に完全なアルファベットが部分列として含まれる部分文字列の最小長です。 入力により、そのような部分文字列が存在することが保証されます。 

文字列の長さは最大 777、テスト ケースの数は最大 44 です。これらの制限は十分に小さいため、二次解が可能です。 すべての部分文字列を試して慎重にチェックするソリューションは、チェックが効率的であれば許容されます。 7773 は最悪の場合でも 5 億回近くのオペレーションを必要とするため、3 次アプローチには依然としてリスクが伴います。 

主なエッジ ケースは、文字の余分なコピーや、すべての文字が必要な順序で含まれていない部分文字列によって引き起こされます。 

たとえば、次のことを考えてみましょう。```
1
26
ABCDEFGHIJKLMNOPQRSTUVWXYZ
```答えは次のとおりです。```
26
```すべての文字が出現するかどうかのみをカウントする不注意な実装はここでは機能しますが、順序が間違っている文字列ではその考えは失敗します。 

例えば：```
1
26
ZYXWVUTSRQPONMLKJIHGFEDCBA
```アルファベットの部分列を形成できないため、この入力からの答えは無効です。 頻度ベースのアプローチでは、必要な文字がすべて存在すると誤って認識されてしまいます。 

もう 1 つの注意が必要なケースは、より短いウィンドウがより大きな有効領域内に隠れている場合です。 

例：```
1
29
XXXABCDEFGHIJKLMNOPQRSTUVWXYZ
```答えは次のとおりです。```
26
```最初の有効な部分文字列を見つけてそれを縮小しないソリューションでは、29 が出力され、最適な答えが見つかりません。 

## アプローチ

 直接的なアプローチは、考えられるすべての部分文字列を試してみることです。 開始位置ごとに、終了位置を一度に 1 文字ずつ拡張し、現在の部分文字列にサブシーケンスとしてアルファベットが含まれているかどうかを確認します。 存在する場合は、その長さを記録し、より小さい長さの検索を続けます。 

この方法は正しいです。考えられる答えはすべて何らかの部分文字列であり、それらすべてを明示的に検査するからです。 費用がかかる部分はチェックプロセスです。 O(n²) 個の部分文字列があり、各チェックで部分文字列がスキャンされると、最悪の場合は O(n³) になります。 n = 777 の場合、これはおよそ 4 億 7,000 万文字のチェックに相当しますが、これは不要です。 

重要な観察は、必要なプロパティが単調であるということです。 部分文字列に次のものが含まれる場合、`ABCDEFGHIJKLMNOPQRSTUVWXYZ`サブシーケンスとして文字を追加しても、そのプロパティを false にすることはできません。 有効なウィンドウは展開しても有効なままです。 これにより、スライディング ウィンドウを使用できるようになります。 

現在のウィンドウを記述する 2 つのポインターを保持します。 ウィンドウが有効になるまで右側を展開します。 有効になったら、左側から文字を削除しても短くすることしかできないため、プロパティが true のままで左側から縮小を繰り返します。 これにより、現在の右ポインタで終了する最短の有効なウィンドウが検索されます。 

残りの問題は、有効性を迅速にテストする方法です。 必要なサブシーケンスは 26 文字しかないため、マッチングに必要な最新の情報を保存できます。 現在のウィンドウをスキャンし、次に必要な文字を貪欲に照合します。 ウィンドウ サイズは最大 777 なので、この小切手は安価です。 別の実装ではさらに多くの状態を維持できますが、単純なバージョンでもすでに十分に高速です。 

ブルートフォース手法は、すべての候補者を検査するため機能します。 重複する部分文字列に対して同様の作業を繰り返すため、失敗します。 スライディング ウィンドウは、有効なウィンドウを左から安全に短縮できるという事実を利用して、この繰り返しを回避します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n3) | お(1) | 最悪の場合は遅すぎる |
 | スライディングウィンドウ | O(n²) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 空のウィンドウから開始し、両方のポインタを文字列の先頭に置きます。 現在のウィンドウは、テストしている文字列の一部を表します。 
2. 右ポインタを前方に移動し、ウィンドウに新しい文字を含めます。 展開するたびに、現在のウィンドウにサブシーケンスとしてアルファベットが含まれているかどうかを確認します。 有効なウィンドウが見つかるまでは、より短いウィンドウを表示できないため、展開する必要があります。 
3. ウィンドウが有効になったら、回答を現在の長さで更新します。 これにより、この正しいポインタで終了する最適なソリューションが記録されます。 
4. ウィンドウが有効なまま左ポインタを前方に移動します。 削除が成功するたびに、より小さい有効な部分文字列が作成されるため、それも考慮する必要があります。 
5. 右ポインタが文字列の末尾に到達するまで続けます。 記録された最小のウィンドウが答えです。 

なぜ効果があるのか:

 このアルゴリズムは、ウィンドウが有効であるたびに、縮小フェーズ後の現在の右境界で終了する最小有効ウィンドウであるという不変条件を維持します。 最適な答えには必ず正しい境界線があります。 アルゴリズムがその境界に達すると、有効になるまで拡張し、不要な文字を左側からすべて削除します。 考えられるすべての正しい境界が考慮されるため、グローバル最小値が見つかります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def valid(s, l, r):
    need = 0
    for i in range(l, r + 1):
        if s[i] == chr(ord('A') + need):
            need += 1
            if need == 26:
                return True
    return False

def solve():
    t = int(input())
    ans = []

    for _ in range(t):
        n = int(input())
        s = input().strip()

        left = 0
        best = n

        for right in range(n):
            while left <= right and valid(s, left, right):
                best = min(best, right - left + 1)
                left += 1

        ans.append(str(best))

    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```の`valid`関数は、現在の部分文字列がアルファベットを生成できるかどうかをチェックします。 次に必要な文字を貪欲に検索します。 26 文字すべてが見つかると、それ以上スキャンしても結果が変わることはないため、関数はすぐに戻ります。 

メインループはスライディングウィンドウを制御します。 右ポインタは常に前方に移動し、さらに文字を追加します。 左ポインタはウィンドウが有効になった後にのみ前方に移動するため、各位置は順番に処理され、後方に移動することはありません。 

縮小ループの境界条件は重要です。 単一文字ウィンドウのテストを許可する必要があるため、条件は次のようになります。`left <= right`。 答えは次のように初期化されます`n`because the entire string is always a valid upper bound according to the problem guarantee.

 ## 特殊なケース

 アルファベットが反転されている場合、貪欲なマッチング順序は次から先に進むことができないため、アルゴリズムはウィンドウを有効としてマークしません。`A`に`B`そしてさらに先へ。 周波数のみのソリューションは順序を無視するため、ここでは失敗します。 

回答の前に不要な文字が含まれる文字列の場合、アルゴリズムはアルファベットが見つかるまで拡張され、その後すぐにそれらの文字の削除をテストします。 これがまさに、スライディング ウィンドウが最初の有効な部分文字列で停止しない理由です。 

複数の可能なアルファベットのサブシーケンスを含む文字列の場合、存在することだけが必要なため、貪欲な妥当性チェックで十分です。 次に必要な各文字が最も早く出現すると、常に後の文字用に最も多くのスペースが残されるため、1 つの完全なサブシーケンスが見つかると、ウィンドウが有効であることが証明されます。 

同じ縮小ウィンドウの推論を維持しながら、妥当性チェックを置き換えることによって、この編集スタイルを他のサブシーケンス ウィンドウの問題に適応させることができます。
