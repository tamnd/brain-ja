 ## 解決策

 ## 問題の理解

 モンスターが一定の体力値から開始し、2 種類のアクションを繰り返し適用できるターンベース システムをシミュレートしています。 各アクションは決定論的な方法でヘルスを変更します。1 つのアクションはヘルスをおよそ半分にしますが、その後固定定数を追加し、もう 1 つのアクションは固定定数を減算します。 

目標は、各アクションの使用回数の上限を考慮して、最終的にヘルスをゼロ以下にする一連のアクションが存在するかどうかを判断することです。 

各テスト ケースでは、初期ヘルス値と、各呪文を使用できる回数を表す 2 つのカウンターが与えられます。 これらの制限された操作の順序によっては、健全性が非プラスになる可能性があるかどうかを判断する必要があります。 

どちらの制限も最大 30 であるため、操作数に関する制約は小さくなります。これにより、大きな状態空間にわたる複雑なグラフ検索の必要性が即座に排除されます。 組み合わせの数は最大でも 31 × 31 であるため、考えられるすべての呪文カウントにわたる状態探索さえも、最悪の場合には実現可能です。ただし、注意が必要なのは、一方の操作では値が非線形に縮小され、もう一方の操作では線形に減算されるため、順序が重要であるということです。 

主な落とし穴は、固定の貪欲な順序付けが正当化されずに常に機能すると仮定していることです。 たとえば、常に最初に半減呪文を適用すると失敗する可能性があります。 

入力:```
x = 64, n = 1, m = 3
```最初にボイド吸収を適用すると、64 → 42、次に 3 回の攻撃 (12 → 2 → -8 → -18) が得られ、これは機能します。 しかし、同様のケースで選択を誤って反転すると、簡単にゼロを超える状態に陥る可能性があります。 半分にすることと減算の間の相互作用は、素朴な意味では単調ではありません。 

半分にすることが有害になる場合、別の失敗例が現れます。 

入力:```
x = 10, n = 1, m = 0
```Void Absorption は Floor(10/2)+10 = 15 を与え、健康状態を減らすのではなく増加させます。 利用可能なボイド吸収を常に使用する単純な戦略は、状況をすぐに悪化させるでしょう。 

したがって、重要な問題は、この呪文は一律に有益ではなく、最適な選択は現在の健康状態に依存するということです。 

## アプローチ

 ブルート フォース ソリューションでは、最大 n + m の操作の可能なシーケンスをすべて試行します。 各ステップで、残りのカウントを考慮して、Void Absorption を適用するか、Lightning Strike を適用するかに応じて分岐します。 これは、デシジョン ツリー全体を調査するため、正しいです。 ただし、分岐係数により約 2^(n+m) 状態が発生し、最悪の場合は 2^60 に達し、実現可能な限界をはるかに超えます。 

重要な観察は、健康値が小さくなると減少する傾向があり、唯一の危険な状況は、空虚吸収が一時的に増加するか、値をほとんど減少させない場合です。 体力が大きくなったら、ライトニング ストライクのみを使用するのが合理的です。なぜなら、半分にプラス 10 を加える方が、繰り返し 10 を引くよりも悪い場合が多いからです。 しかし、体力が少なくなると、直接減算に比べて値の増加または減少が遅すぎるため、Void Absorption を適用しても役に立ちません。 

この構造は、枝刈りを伴う貪欲なシミュレーションを示唆しています。体力が十分に大きい場合は、可能な限り Lightning Strike を常に優先し、規模を減らすのに役立つ場合または打撃が枯渇した場合にのみ Void Absorption を使用します。 n と m が小さいため、長いチェーンを心配することなく、すべての意味のある遷移を安全にシミュレートできます。 

これを公式化するきれいな方法は、有益な場合は常に Lightning Strike を貪欲に適用し、時折 Void Absorption を適用して大きな値をより速く減らすことですが、必要以上に適用しないことです。 状態空間が小さいため、これ以上の改善が不可能になるか、限界がなくなるまで安全にシミュレーションできます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^(n+m)) | O(n+m) | 遅すぎる |
 | 貪欲なシミュレーション | テストごとに O(n+m) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちはテスト ケースごとにプロセスをシミュレーションし、常に可能な限り効率的にヘルス状態を軽減しようとします。 

1. 利用可能なボイド吸収の使用法がまだあり、それを適用すると有用性を維持しながら体力が大幅に減少する場合、体力が大きいときに適用することを検討します。 

変換は大きさに応じて値を増減させることができるため、選択的に使用する必要があります。 
2. それ以外の場合は、Lightning Strike を優先します。これは、厳密に単調であり、常に一定量だけ体力を減少させるためです。 
3. ヘルスがゼロまたはマイナスになるか、両方の操作がなくなるまで、この決定プロセスを繰り返します。 
4. 有効なアプリケーションをすべて使い果たした後でヘルスをゼロ以下に減らすことができない場合、それは不可能であると結論付けます。 

重要な考え方は、各操作の数には制限があり、すべての操作は健全性を低下させるか、最終的には代替操作よりも悪化するため、システムには無限に利用できるサイクルが存在しないということです。 これにより、シミュレーションが迅速に収束します。 

不変条件は、貪欲な優先順位の下で残りの操作を考慮して、各ステップで達成可能な最高の健全性を維持するということです。ライトニングストライクは、削減に直接寄与する場合に常に使用されますが、ボイド吸収は、回避可能な悪化につながらない場合にのみ使用されます。 どちらの操作も制限されており、変換によって有効な検索スペースが厳密に削減されるため、シミュレーションで有効なシーケンスを見逃すことはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        x, n, m = map(int, input().split())

        # We try a greedy reduction:
        # Use Void Absorption only while it helps reduce large values.
        # Otherwise use Lightning Strike.
        h = x

        # First, try to use Void Absorption when it is clearly beneficial.
        # Empirically, it is useful only when h > 20.
        while n > 0 and h > 20:
            h = h // 2 + 10
            n -= 1

        # Then use all Lightning Strikes
        h -= 10 * m

        if h <= 0:
            print("YES")
        else:
            print("NO")

if __name__ == "__main__":
    solve()
```この実装は、Void Absorption は健康状態が高い場合にのみ役立つという観察を反映しています。 値が小さなしきい値を下回ると、半減プラス 10 は直接減算と比較して効率的ではなくなるため、早期に使用を中止し、残りのすべてのリソースを直接ダメージに変換します。 

しきい値の動作は重要な微妙な点です。しきい値の動作がないと、単純なインターリーブ戦略では動作が不安定になったり、無駄な動作が発生したりする可能性があります。 選択したカットオフにより、進捗を増やしたり遅らせたりするような変換を決して適用しないことが保証されます。

 ## 特殊なケース

 重大なエッジケースは、ヘルスが少なく、ボイド吸収によってヘルスが増加する場合です。 たとえば、使用可能なストライクがなく、無効な呪文が 1 つある状態で 10 から開始すると、変換によって 15 が生成され、状況が厳密に悪化して失敗につながります。 このアルゴリズムは、健康状態が低い状況では Void Absorption を決して適用しないことでこれを回避します。 

もう 1 つのエッジ ケースは、ヘルスが大きいにもかかわらず、使用できるボイド スペルが少数しかない場合に発生します。 このような場合、すべての無効呪文を早期に適用すると、ストライクが優勢な領域にすぐに値を下げることができるため、有益です。 貪欲なしきい値により、戦略を切り替える前にこの加速が確実に発生します。 

最後のエッジケースは、Lightning Strike のみが存在する場合です。 次に、解決策は m * 10 が少なくとも x であるかどうかをチェックすることになりますが、これは最後の減算ステップで正しく処理されます。
