 ## 解決策
 ## 問題の理解

 単一の小文字文字列が与えられ、3 つの条件を同時に満たす最長の文字列を見つける必要があります。 

選択した文字列は、元の文字列の接頭辞、接尾辞である必要があり、また厳密に文字列内のどこかに存在する必要があります。 内部オカレンスでは、プレフィックス全体またはサフィックス位置全体を使用することはできません。 

たとえば、`fixprefixsuffix`、文字列`fix`単語の最初、最後、そして単語の中に現れます`prefix`, したがって、それは有効な答えです。 

文字列の長さは 100 万文字に達する場合があります。 これにより、二次関数は即座に除外されます。 たとえ`O(n^2)`アルゴリズムには次のようなものが必要です`10^12`最悪の場合の操作は 2 秒に収まる時間をはるかに超えます。 線形または線形に近い解決策が必要です。 

厄介な点は、文字列がプレフィックスとサフィックスの両方であるかどうかをチェックしないことです。 これは、標準的な文字列テクニックを使用して実行できます。 本当に難しいのは、同じ文字列が途中にも出現するかどうかを確認することです。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

次の入力を考えてみましょう。```
aaaa
```正しい答えは次のとおりです。```
aa
```接頭語`aaa`も接尾辞ですが、厳密には文字列内に現れません。 その 2 つの出現箇所は、正確にプレフィックスとサフィックスの位置です。 不用意に実装すると、誤って返される可能性があります`aaa`。 

もう一つの危険なケースは次のとおりです。```
abcdabc
```接頭語`abc`も接尾辞ですが、中間の出現はありません。 正しい出力は次のとおりです。```
Just a legend
```プレフィックスとサフィックスの同一性のみをチェックする実装は、ここで失敗します。 

最小限のケースも重要です。```
a
```空でない部分文字列は、同時に適切な接頭辞、適切な接尾辞、および中間の部分文字列になることはできません。 答えは次のようになります。```
Just a legend
```文字列が繰り返されると、別の微妙な状況が生じます。```
aaaaa
```正しい答えは次のとおりです。```
aaa
```文字列`aaaa`はプレフィックスとサフィックスの両方ですが、ここでも厳密には内部で発生しません。 重複するオカレンスと有効な内部オカレンスを区別する必要があります。 

## アプローチ

 ブルートフォースアプローチは簡単です。 文字列の可能なすべてのプレフィックスを列挙します。 各プレフィックスについて、それがサフィックスでもあるかどうか、および中間のどこかに表示されているかどうかを確認します。 

文字列の長さが`n`。 がある`n`可能な接頭辞。 プレフィックスとサフィックスを比較すると、最大で次のコストがかかります。`O(n)`、文字列内の別の出現箇所の検索にも、最大で次のコストがかかります。`O(n)`。 全体の複雑さは次のようになります。`O(n^2)`検索方法によっては、それ以上の場合もあります。 

と`n = 10^6`、 平`O(n^2)`全く実現不可能です。 

重要な観察点は、問題は文字列の境界のみを考慮しているということです。 ボーダーは、プレフィックスとサフィックスの両方である部分文字列です。 すべての部分文字列をテストする代わりに、境界を調べるだけで済みます。 

これは当然、Knuth-Morris-Pratt アルゴリズムのプレフィックス関数につながります。 プレフィックス関数`pi[i]`位置で終わるサフィックスでもある文字列の最も長い適切なプレフィックスの長さを格納します`i`。 

完全な文字列の場合、`pi[n - 1]`最長の境界線の長さを与えます。 その境界線もプレフィックス関数配列のどこか前に出現する場合、それは中央に出現し、有効な答えになります。 

そうでない場合は、接頭辞関数リンク自体を使用して、次の小さな境界線にジャンプできます。 これが KMP のエレガントな部分です。ボーダーがチェーンを形成します。 何かを再計算する代わりに、一定時間内に 1 つの境界から次の小さな境界に繰り返し移動します。 

これにより、問題は線形スキャンといくつかの境界ジャンプに変換され、次のようになります。`O(n)`複雑。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | お(1) | 遅すぎる |
 | 最適 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

prefix 関数は、すべての位置について、そこで終わる最長の境界線の長さを示します。 
2. 見てください`pi[n - 1]`。 

この値は、文字列全体の接尾辞でもある最長の接頭辞の長さです。 
3. 最後の位置の前に現れるすべてのプレフィックス関数値を記録します。 

私たちはポジションだけを気にします`0`を通して`n - 2`最後の位置は、中間の出現ではなく、文字列サフィックス自体全体に対応するためです。 
4. しましょう`x = pi[n - 1]`。 

This is our current candidate answer length.
 5. ながら`x > 0`、どうかを確認してください`x`プレフィックス関数配列の前のどこかに出現しました。

6. もし`x`これより前に表示されない場合は、次のコマンドを使用して次の小さな境界線に移動します。```
x = pi[x - 1]
```これが機能するのは、境界線の境界線も境界線であるためです。 
7. ループが次のように終了した場合`x = 0`、有効な部分文字列が存在しません。 

### なぜ効果があるのか

 prefix 関数は、文字列内のすべての境界関係をキャプチャします。 

すべての有効な回答は完全な文字列の境界である必要があるため、次から始めます。`pi[n - 1]`候補者を最長から最短の順に検討することを保証します。 

境界の長さが接頭辞関数配列のどこかで前に現れる場合、それは同じ接頭辞が内部の位置で終わっていることを意味し、部分文字列が中央にあることが証明されます。 

移行`x = pi[x - 1]`文字列全体の小さい有効な境界線は現在の境界線でもある必要があるため、次の可能な境界線に正しく移動します。 

境界線を降順に検査するため、最初の有効な境界線が自動的に最長になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    pi = [0] * n

    j = 0
    for i in range(1, n):
        while j > 0 and s[i] != s[j]:
            j = pi[j - 1]

        if s[i] == s[j]:
            j += 1

        pi[i] = j

    seen = [False] * (n + 1)

    for i in range(n - 1):
        seen[pi[i]] = True

    x = pi[n - 1]

    while x > 0:
        if seen[x]:
            print(s[:x])
            return
        x = pi[x - 1]

    print("Just a legend")

solve()
```最初の部分では、KMP プレフィックス関数を線形時間で計算します。 

変数`j`現在一致したプレフィックス長を保存します。 文字が一致しない場合は常に、ゼロから再開するのではなく、以前に計算されたプレフィックス関数の値を使用して逆方向にジャンプします。 これが、KMP が線形を維持する理由です。 

の`seen`配列は、最終位置の前に出現した境界線の長さを記録します。 セットの代わりにブール配列を使用すると、非常に大きな入力でのハッシュ オーバーヘッドが回避されます。 

検索ループは、文字列全体の最も長い境界から開始されます。 その境界線が内部的に表示された場合は、候補を最大から最小の順に検査するため、すぐにそれを印刷します。 

行:```
x = pi[x - 1]
```最も重要な移行です。 何も再計算せずに境界チェーンを通過します。 

よくある間違いは、以下を含むすべてのポジションをチェックすることです。`n - 1`充填するとき`seen`。 これにより、完全な接尾辞としてのみ出現する境界線が誤って受け入れられてしまいます。 

もう 1 つのよくあるオフバイワン バグは次の場合に発生します。`pi[x - 1]`。 prefix 関数は終了位置ごとに情報を格納するため、長さのプレフィックスの境界は`x`インデックスで見つかります`x - 1`。
