 ## 解決策
 ## 問題の理解

 元々は区切り文字なしで連続して書かれた複数のファイル名で構成される 1 つの長い文字列が与えられています。 有効なファイル名はすべて次のようにする必要があります。`name.ext`。 

規則は厳しいです。 ドットの前の部分には小文字のみが含まれ、長さは 1 ～ 8 です。ドットの後の拡張子にも小文字のみが含まれ、長さは 1 ～ 3 です。各ファイル名には、ドットが 1 つだけ含まれている必要があります。 

私たちのタスクは、すべての部分文字列が有効なファイル名になるように、文字列全体を連続した部分文字列に分割することです。 そのようなパーティションが存在する場合は、それらのいずれかを印刷します。 それ以外の場合は印刷します`NO`。 

入力できる長さは次のとおりです。`4 * 10^5`、それは問題についてどのように考えなければならないかを完全に変えます。 すべてのパーティションを再帰的に試行するソリューションは、指数関数的に爆発的に増加します。 たとえ`O(n^2)`動的プログラミング ソリューションは、この規模ではリスクが高くなります。`1.6 * 10^11`最悪の場合の運用。 

重要な点は、有効なファイル名の制限長が非常に小さいということです。 名前は最大 8 文字、拡張子は最大 3 文字、ドットは 1 つだけ含まれます。 したがって、すべての有効なセグメントの全長は 3 ～ 12 になります。つまり、どの位置からでも、考えられる次のカットの一定数をチェックするだけで済みます。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

ドットのない文字列は機能しません。 

例えば：```
abcdef
```すべてのセグメントに正確に 1 つのドットが必要なため、有効なファイル名を作成する方法はありません。 

複数のドットを含むセグメントも無効です。 

例えば：```
a..b
```不注意なパーサーはそれを次のように分割する可能性があります`a.`そして`.b`ですが、名前と拡張子の両方に文字が含まれている必要があるため、どちらの側もルールを満たしていません。 

もう 1 つの注意が必要なケースは、ドットが一端に近すぎる場合です。 

例えば：```
abcdefghij.k
```名前部分の長さは 10 で、最大値の 8 を超えています。 

同様に:```
a.abcd
```延長長は 4 となり、最大値の 3 を超えます。 

もう 1 つの微妙な問題は、ローカルで有効な選択が将来を妨げる場合に発生します。 

考慮する：```
ab.cdex.f
```部分文字列`ab.c`は有効ですが、残りは`dex.f`名前の長さが 3 で有効であるためではありません。実際、これは機能します。 より良い例は次のとおりです。```
a.bcdefghi.j
```貪欲に摂取すれば`a.b`、 残り`cdefghi.j`有効です。 ただし、他の貪欲な戦略は、さまざまな入力で失敗する可能性があります。 この問題では、サフィックスも正しくパーティション化できるかどうかを確認する必要があります。 

これは自然に動的プログラミングにつながります。 

## アプローチ

 ブルートフォースのアイデアは単純です。 文字列の先頭から始めて、ファイル名を表す可能性のある次の部分文字列をすべて試します。 次に、残りのサフィックスを再帰的に解決します。 

これは、すべての有効なパーティションが最終的に探索されるため機能します。 問題はパーティションの数です。 各セグメントの長さは制限されていますが、分岐係数は依然として指数関数的な動作を引き起こすのに十分な大きさです。 長さの文字列`4 * 10^5`この方法で処理するのは不可能でしょう。 

メモ化により物事は劇的に改善されます。 

重要な観察は、残りの作業の有効性は現在のインデックスのみに依存するということです。 サフィックスが位置から始まるかどうかがわかったら、`i`分割できるため、再度再計算する必要はありません。 

さらに良いことに、各状態には一定の遷移しかありません。 有効なファイル名の長さの範囲は 3 ～ 12 であるため、各位置から最大 10 個の候補部分文字列が試行されます。 1 つの部分文字列が有効かどうかを確認する場合も、最大長が小さいため一定の時間がかかります。 

これにより、指数関数的探索が線形動的計画法に変換されます。 

私たちは定義します`dp[i]`サフィックスがインデックスで始まるかどうか`i`有効なファイル名に分割できます。 答えは`dp[0]`。 

から移行するには`i`、すべてのエンドポイントを試します`j`そのような`s[i:j]`有効なファイル名である可能性があります。 部分文字列が有効であり、`dp[j]`それは本当です、それでは`dp[i]`も真実です。 

将来の値がすでにわかっているように、状態を右から左に処理します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(n) 再帰 | 遅すぎる |
 | 最適なDP | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 部分文字列が有効なファイル名であるかどうかをチェックするヘルパー関数を定義します。 

部分文字列にはドットが 1 つだけ含まれている必要があります。 ドットの前の部分の長さは 1 ～ 8 で、小文字のみを含める必要があります。 ドットの後の部分の長さは 1 ～ 3 で、小文字のみを含める必要があります。 
2. DP アレイを作成する`dp`サイズの`n + 1`。`dp[i]`インデックスから始まるサフィックスを意味します`i`正常に分割できます。 設定しました`dp[n] = True`空のサフィックスはすでに有効であるためです。 
3. 別の配列を作成する`nxt`答えを再構築します。 

有効なセグメントを選択すると、`i`に`j`、私たちは保管します`nxt[i] = j`。 
4. インデックスを右から左に処理します。 

それぞれのポジションで`i`、ファイル名の長さは 3 から 12 までしかないため、3 から 12 までのすべての部分文字列の長さを試してください。 
5. 各候補部分文字列について`s[i:j]`, 2つの条件を確認してください。 

まず、部分文字列自体が有効なファイル名である必要があります。 

2番、`dp[j]`これは、残りのサフィックスも分割できることを意味します。 
6. 両方の条件が当てはまる場合は、マークを付けます。`dp[i] = True`そして保管する`nxt[i] = j`。 

有効なパーティションであればどれでも受け入れられるため、それ以上の候補のチェックを停止できます。 
7. DP テーブルに記入したら、チェックを入れます。`dp[0]`。 

falseの場合は出力します`NO`。 

それ以外の場合は、部分文字列を繰り返し取得して答えを再構築します`s[pos:nxt[pos]]`。 

### なぜ効果があるのか

 DP 不変式は単純です。`dp[i]`で始まるサフィックスの場合にまさに true になります。`i`有効なファイル名に分割できます。 

すべての有効なパーティションは有効なファイル名で始まる必要があるため、移行は完了しました。`s[i:j]`。 最初のセグメントを削除した後、残りのサフィックスは次から始まります。`j`, したがって、これも解決可能である必要があります。 

マークを付けるたびに移行が確実に行われます。`dp[i] = True`、有効な最初のセグメントと残りのサフィックスの有効なパーティションが明示的に見つかりました。 

右から左に処理するため、計算時に必要な将来の状態はすべて既知です。`dp[i]`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def valid_file(t: str) -> bool:
    if t.count('.') != 1:
        return False

    name, ext = t.split('.')

    if not (1 <= len(name) <= 8):
        return False

    if not (1 <= len(ext) <= 3):
        return False

    return name.islower() and ext.islower()

def solve():
    s = input().strip()
    n = len(s)

    dp = [False] * (n + 1)
    nxt = [-1] * (n + 1)

    dp[n] = True

    for i in range(n - 1, -1, -1):
        for length in range(3, 13):
            j = i + length

            if j > n:
                break

            if valid_file(s[i:j]) and dp[j]:
                dp[i] = True
                nxt[i] = j
                break

    if not dp[0]:
        print("NO")
        return

    print("YES")

    pos = 0
    while pos < n:
        print(s[pos:nxt[pos]])
        pos = nxt[pos]

solve()
```ヘルパー関数はファイル名ルールを直接エンコードします。 部分文字列の最大長は 12 のみであるため、次のような演算を使用します。`count('.')`そして`split('.')`完全に安全であり、一定時間です。 

各状態は将来の位置に依存するため、DP 配列は右から左に埋められます。 空のサフィックスは、到達可能であるとマークされます。`dp[n] = True`、これは基本ケースとして機能します。 

内側のループは 3 ～ 12 の長さのみを試行します。有効なファイル名として可能な最小値は次のとおりです。`"a.b"`長さは 3 です。最大値は次のとおりです。`"abcdefgh.abc"`長さ12。 

再構築アレイ`nxt`次のセグメントが始まる場所を格納します。 それがなければ、解決策が存在するかどうかだけがわかり、解決策を印刷する方法はわかりません。 

実装の微妙な詳細の 1 つは、初期の`break`有効なトランジションが見つかった後。 この問題は有効なパーティションを受け入れるため、検索を続行する必要はありません。 

もう 1 つの重要な詳細は、`j > n`停止条件としては。 これにより、範囲外のスライス ロジックが回避され、不可能な部分文字列のチェックが回避されます。

import sys, io

def solve_io(inp: str) -> str:
    input_data = io.StringIO(inp)
    output_data = io.StringIO()

    input = input_data.readline

    def valid_file(t: str) -> bool:
        if t.count('.') != 1:
            return False

        name, ext = t.split('.')

        if not (1 <= len(name) <= 8):
            return False

        if not (1 <= len(ext) <= 3):
            return False

        return name.islower() and ext.islower()

    s = input().strip()
    n = len(s)

    dp = [False] * (n + 1)
    nxt = [-1] * (n + 1)

    dp[n] = True

    for i in range(n - 1, -1, -1):
        for length in range(3, 13):
            j = i + length

            if j > n:
                break

            if valid_file(s[i:j]) and dp[j]:
                dp[i] = True
                nxt[i] = j
                break

    if not dp[0]:
        print("NO", file=output_data)
    else:
        print("YES", file=output_data)

        pos = 0
        while pos < n:
            print(s[pos:nxt[pos]], file=output_data)
            pos = nxt[pos]

    return output_data.getvalue()

# provided sample
out = solve_io("read.meexample.txtb.cpp\n")
assert out.startswith("YES")

# minimum valid case
assert solve_io("a.b\n") == "YES\na.b\n"

# no dot
assert solve_io("abcdef\n") == "NO\n"

# extension too long
assert solve_io("a.abcd\n") == "NO\n"

# maximum allowed lengths
assert solve_io("abcdefgh.abc\n") == "YES\nabcdefgh.abc\n"

# multiple valid partitions
out = solve_io("ab.cd.ef\n")
assert out.startswith("YES")

 ## 特殊なケース

 次の入力を考えてみましょう。```
a..b
```部分文字列には 2 つのドットが含まれています。 検証中に、`count('.') != 1`すぐにそれを拒否します。 有効な DP 遷移がないため、アルゴリズムは次のように出力します。```
NO
```これにより、不正な名前がすり抜けてしまうのを防ぎます。 

次に、次のことを考えてみましょう。```
abcdefghij.k
```可能なファイル名の分割は次のとおりです。```
abcdefghij.k
```名前の長さは 10 で、制限の 8 を超えています。バリデーターはそれを拒否するため、`dp[0]`偽のままです。 

出力は次のとおりです。```
NO
```次に調べます:```
a.abcd
```拡張子の長さは 4 です。バリデーターは以下をチェックします。`1 <= len(ext) <= 3`、失敗します。 ここでも有効な遷移は存在しません。 

最後に次のことを考慮してください。```
a.ba.bc
```ローカルカットの可能性は複数あります。 The algorithm checks all feasible substring lengths from each position and only accepts a segment if the remaining suffix is also solvable.

 有効なパーティションの 1 つは次のとおりです。```
a.ba
.bc
```実は`.bc`名前を空にすることはできないため、無効です。 DP はこのパスを正しく回避します。 代わりに、次のことを選択することもできます。```
a.b
a.bc
```両方のセグメントが制約を満たしているため、アルゴリズムは有効な答えを出力します。 これは、単に貪欲な選択をするのではなく、サフィックスの実現可能性が移行の一部である必要がある理由を示しています。
