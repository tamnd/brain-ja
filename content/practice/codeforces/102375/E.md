 ## 解決策
 ## 問題の理解

 私たちは国会議事録を時系列で渡されます。 毎`Add x`イベントとはそのパーティーのことです`x`新しい法案を提出します。 新たに提出された法案が直ちに審議されることになるため、審議される前に審議されていた法案は停止されます。 毎`Vote x`イベントは、現在議論されている法案が採決されることを意味し、記録される当事者はその法案を提出した当事者である必要があります。 採決後、議論はその下で保留されていた法案に戻る。 

これはまさにスタック規律です。 アン`Add`すべての未完の請求書の上に新しい請求書を置きます。 あ`Vote`現在一番上にある紙幣を削除する必要があります。 イベントに記載された当事者は、その最上位の法案に同意する必要があります。 ログが終了するとき、未処理の紙幣があってはならず、したがってスタックは空でなければなりません。 

入力には最大 1000 個のイベントが含まれます。 これは十分に小さいため、二次アルゴリズムでも簡単に終了しますが、問題の構造により、スタックのみで線形の解決策が得られます。 グラフ アルゴリズム、動的プログラミング、または可能な次数の検索は必要ありません。 実際、イベントの順序によってスタックの状態が完全に決まります。 

最初のエッジケースは、法案が提出される前の投票です。 例えば、```
1
Vote z
```生産しなければならない`No`。 現在採決すべき法案はないため、以前のイベントが使用されたかどうかだけをチェックする不注意な実装`z`不可能なセッションを受け入れることができます。 

2 番目のエッジケースは、現行法案ではなく保留中の法案に賛成票を投じることです。 例えば、```
4
Add a
Add b
Vote a
Vote b
```生成する`No`。 後`Add b`、 請求書`b`議論されており、法案は`a`停止されています。 次の投票は次のものでなければなりません`b`、 ない`a`。 かどうかをチェックするだけの実装`a`未完了の請求書の中にあると、シーケンスが誤って受け入れられてしまいます。 

3 番目のエッジケースは、同じパーティの繰り返し使用です。 例えば、```
6
Add a
Add a
Vote a
Vote a
Add b
Vote b
```生成する`Yes`。 二人`a`同じ政党ラベルが付いている場合でも、紙幣は異なる紙幣です。 スタックはこれを自然に処理します。`Add a`別の個別のスタック エントリを作成します。 

最後のエッジケースは、最後に未完成の法案です。 例えば、```
1
Add a
```生成する`No`。 この法案は提出されたが採決されなかったため、会期は合法的に終了することができなかった。 

## アプローチ

 直接的な総当たりシミュレーションにより、投票のたびに未完了の法案のセットを繰り返し再構築できます。 ログの先頭から始めて、すべて以前に処理します`Add`そして`Vote`イベントを調べて現在のスタックを再構築し、そのスタックの最上部で現在の投票を検査します。 プレフィックスの後のスタックはそのプレフィックスによって完全に決定されるため、これは正しいです。 

このバージョンの問題は繰り返し作業です。 (K) 個のイベントがあり、すべてのイベントに対してスタックを再構築する場合、最初のイベントには 1 つの操作が必要となり、2 番目のイベントには 2 つの操作が必要になる可能性があります。 最悪の場合、これには約

 [
 1 + 2 + \dots + K = O(K^2)
 ]

 不要な操作です。 

重要な観察は、プレフィックスの後の状態を再構築する必要がないということです。 直前のイベントによって生成された状態のみが必要です。 アン`Add x`押す`x`、そして`Vote x`現在のトップをチェックしてポップします。 スタック自体はまさに議会規則の数学モデルです。 

イベント履歴からすべてのプレフィックスをシミュレートできるため、ブルート フォースは機能しますが、同じ履歴を何度も再計算することで失敗します。 各イベントが 1 つのローカルな方法でのみスタックを変更するという観察により、1 つのパスで段階的に状態を維持できるようになります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(K²) | O(K) | K ≤ 1000 の場合は受け入れられますが、不必要に遅くなります。 
| 最適 | O(K) | O(K) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 空のスタックを作成します。 これは、現在審議されている法案を筆頭に、提出されたものの最終投票をまだ受けていないすべての法案を表しています。 
2. イベントを左から右に読んでください。 セッションの時系列記録のため、順序を変えることはできません。 
3.`Add x`イベント、プッシュ`x`スタックに。 新しい法案は前の議論を即座に中断するので、新しいトップにならなければなりません。 
4.`Vote x`イベントが発生した場合は、まずスタックが空かどうかを確認します。 空の場合は現在審議中の法案がないため、ログは取得できません。 
5. スタックが空でない場合は、その最上位要素を次の要素と比較します。`x`。 両者が異なる場合、現在審議されている法案のみ採決できるため、開催は不可能となる。 戻る`No`。 
6. 上位が等しい場合`x`、ポップしてください。 その法案は現在終了しており、その下にある法案が存在する場合、再び活発な議論が行われることになります。 
7. すべてのイベントが処理された後、スタックが空かどうかを確認します。 空のスタックは、提出されたすべての法案が投票を受けたことを意味します。 スタックが空ではないということは、少なくとも 1 枚の請求書が未完了のままであることを意味します。`No`。 

### なぜ効果があるのか

 不変条件は、有効なプレフィックスを処理した後、スタックには、現在議論されている請求書を先頭にして、中断順序で未完了の請求書が正確に含まれるということです。 アン`Add`は、新しくアクティブになったビルを最上位に置くことで、この不変条件を保持します。 有効な`Vote`アクティブな請求書を正確に削除し、以前に一時停止されていた請求書を公開することで、それを保存します。 投票がトップ以外のものを参照している場合、有効なセッションがそのイベントを生成することはできません。 スタックが最後に空でない場合、一部の議論は未完了です。 したがって、アルゴリズムは有効なイベント シーケンスを正確に受け入れます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    k = int(input())
    stack = []

    for _ in range(k):
        event, party = input().split()

        if event == "Add":
            stack.append(party)
        else:
            if not stack or stack[-1] != party:
                print("No")
                return
            stack.pop()

    print("Yes" if not stack else "No")

if __name__ == "__main__":
    solve()
```の`stack`list には、すべての未完了の請求書に対するパーティーレターが保存されます。 それぞれの発生`Add`同じ政党によって提出された 2 つの法案はまだ別の法案であるため、党書簡が既に存在する場合でも、新しいスタック エントリが作成されます。 

のために`Vote`にアクセスする前に空のチェックを行う必要があります。`stack[-1]`。 そうしないと、最初のイベントとしての投票により、インデックス作成操作が生成されず、無効なインデックス付け操作が発生します。`No`。 

との比較`stack[-1]`の前に起こる`pop`。 ラベルが異なる場合、下位要素を削除すると中断ルールに違反するため、ログ全体が直ちに拒否されます。 

最後にチェックすると、`not stack`すべてのディスカッションが最終的に終了する必要があるという要件に対応します。 Python の整数はアルゴリズムに現れないため、オーバーフローの心配はありません。 すべてのイベントは 1 回だけ処理されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(K) | 各イベントは一定量のスタック作業を実行します。 
| スペース | O(K) | 最悪の場合、すべての K イベントが`Add`投票前のイベント |

## テストケース```python
import sys
import io

def solve():
    input = sys.stdin.readline
    k = int(input())
    stack = []

    for _ in range(k):
        event, party = input().split()

        if event == "Add":
            stack.append(party)
        else:
            if not stack or stack[-1] != party:
                print("No")
                return
            stack.pop()

    print("Yes" if not stack else "No")

def run(inp: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    result = sys.stdout.getvalue().strip()

    sys.stdin = old_stdin
    sys.stdout = old_stdout

    return result

""") == "No", "sample 1"

""") == "No", "sample 3"

 ## 特殊なケース

 ### 追加する前に投票してください

 のために```
1
Vote z
```スタックは空から始まります。 イベントは、`Vote`したがって、アルゴリズムはスタックの上部を確認する前にスタックをチェックします。 現在の請求書がないため、印刷されます`No`すぐに。 これにより、不可能なイベントを受け入れたり、空のスタックにアクセスしようとしたりすることが回避されます。 

### 保留された法案に賛成票を投じる

 のために```
4
Add a
Add b
Vote a
Vote b
```スタックは次のようになります`[a, b]`2回目のイベント後。 次回のイベントでは投票をお願いします`a`、 しかし`stack[-1]`は`b`。 アルゴリズムは何もポップせずにログを拒否します。 これは、中心的なネスト ルールを捉えています。つまり、中断された請求を再開するには、新しい請求が完了する必要があります。 

### 繰り返しのパーティラベル

 のために```
6
Add a
Add a
Vote a
Vote a
Add b
Vote b
```スタックは次のように進化します`[a]`、`[a, a]`、`[a]`、`[]`、`[b]`、`[]`。 二人`a`ラベルが同一であっても、エントリは別個の請求書として扱われます。 最上位のみが重要であるため、アルゴリズムは紙幣をグローバルに識別しようとすることはありません。 

### 最後に未完の議論

 のために```
3
Add a
Add b
Vote b
```最後のスタックは`[a]`。 への投票`b`有効だったから`b`は有効な法案でしたが、古い法案です`a`議論は中断されたままで未完了のままだ。 最終的な空性チェックが結果的に出力されます。`No`。 

### 請求書が完了するたびにスタックを空にする

 のために```
6
Add a
Vote a
Add b
Vote b
Add c
Vote c
```スタックはペアごとに空に戻ります。 新しい法案が出るたびに新たな議論が始まり、保留された法案はありません。 すべての投票が上位と一致し、最終スタックが空であるため、アルゴリズムは受け入れます。 

### 同じ当事者がネストされた法案を導入できる

 のために```
4
Add x
Add x
Vote x
Vote x
```どちらの投票も有効です。 最初`Vote x`内側の紙幣を取り外すと、古い紙幣が現れます。`x`法案は削除され、2 回目の投票でその法案は削除されます。 アクティブなパーティのセットのみを保存するソリューションではこの区別が失われますが、スタックでは未処理の請求書の数とネスト順序が自然に保存されます。
