 ## 解決策
 ## 問題の理解

 このタスクは、2 つの同じサイズのグループ間のマッチング プロセスをモデル化します。最初の側の各参加者は、2 番目の側のすべての参加者に対してランク付けされた優先リストを持ち、その逆も同様です。 このプロセスは提案によって進められます。提案する側の個人は、自分が好む相手とペアを形成しようと繰り返し試みますが、受信側は自分の好みに基づいて受け入れるか拒否するかを決定します。 

入力には、各側の参加者の数と両方のグループの優先順位が記述されます。 各優先リストは厳密な順序付けになっており、同順位はなく、すべての候補者が 1 回だけ表示されることを意味します。 出力は、すべての人が 1 人のパートナーと正確に一致するように、2 つのグループ間の完全なペアリングになります。 

制約の観点から見ると、これは通常、合計で最大約 10^5 のプリファレンス エントリまたは参加者向けに設計されており、すべての相互作用の二次シミュレーションは除外されます。 優先リストを繰り返しスキャンしたり、ランキングを最初から再計算したりするソリューションは O(n^2) まで低下します。これは、n が大きい場合には遅すぎます。 これにより、各提案と各拒否を一定時間または対数時間で処理できる構造へと私たちは向かっていきます。 

単純なシミュレーションでは、いくつかの特殊なケースが見落とされがちです。 1 つは、提案する側の全員が最初は同じ候補者を好む場合です。たとえば、男性全員が同じ女性を 1 位にランク付けします。 設定リストを繰り返しスキャンする単純なアプローチでは、同じ組み合わせが繰り返し再検討され、著しく劣化する可能性があります。 

好みのサイクルが密接に絡み合っている場合、別の特殊なケースが発生します。 たとえば、双方の好みが完全に逆転した場合、あらゆる提案は最後の瞬間まで即座に拒否され、ランキングを最初から再計算する非効率な実装では同じ比較を繰り返し行う可能性があります。 

最後に、最初に受け入れ可能なパートナーが優先リストの奥深くにある場合、優先ランクの前処理に失敗する実装が公開されます。 逆ランキング テーブルがないと、新しい提案を受け入れるかどうかを決定するにはリスト全体をスキャンする必要があり、時間がかかりすぎます。 

## アプローチ

 ブルートフォース解釈はプロセスを直接シミュレートします。 ペアになっていない各提案者は、希望リストの次の人を繰り返し選択して提案します。 受け取り手は、新しい求婚者と現在のパートナーを比較し、より好む方を選択します。 このシミュレーションはシステムのルールを正確に反映しているため、正確です。 ただし、その非効率性は、ランキングを記憶せずに優先リストを繰り返しスキャンしたり、比較を繰り返したりすることから生じます。 最悪の場合、各プロポーザはほぼ全体の設定リストを複数回走査する可能性があり、実装の詳細に応じて O(n^2) またはさらに悪い動作が発生する可能性があります。 

重要な観察は、受信側の各参加者は、現在の一致と新しい提案という 2 つの候補を比較するだけでよいということです。 O(1) で「どちらが好ましいか」を答えることができれば、すべての提案は定数時間になります。 これは、各プロポーザーをそのプリファレンス インデックスにマッピングする各受信者のランク配列を事前計算することによって実現されます。 この構造では、比較はリスト スキャンではなく、直接の整数比較になります。 

プリファレンスがインデックス付けされると、各提案者はプリファレンス リストを単調に下に移動し、以前の選択を再検討することはありません。 これにより、各提案が最大 1 回作成されることが保証され、プロセス全体がすべてのプリファレンス エントリにわたって直線的な時間に短縮されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(n^2) | O(n^2) | 遅すぎる |
 | インデックス付きプリファレンス + プロポーザル キュー | O(n^2) | O(n^2) | 承認済み |

 ## アルゴリズムのチュートリアル

前処理された優先順位ランキングを使用して、標準的な提案主導のマッチング プロセスについて説明します。 

1. 両側の参加者の数を読み取り、好みのリストを保存します。 これにより、誰が誰に提案できるか、およびどの順序でマッチングを試みるかの構造が定義されます。 
2. 受信側のすべての参加者について、すべての提案者に数値スコアを割り当てるランキング マップを作成します。 ランクが低いほど優先度が高くなります。 これにより、任意の 2 つの適合者間の定数時間の比較が可能になります。 
3. 提案側のすべての参加者をフリーとして初期化し、それらをキューまたは一致しない個人のスタックに配置します。 これにより、パートナーをまだ必要としている人を常に処理できるようになります。 
4. 自由な提案者がいる間に、提案者を 1 人指名し、希望リストに載っているまだ提案していない次の人に提案してもらいます。 このステップの単調な性質により、同じ候補者に繰り返し提案が行われないことが保証されます。 
5. プロポーザルが発生すると、受信者はそれらが現在一致していないかどうかを確認します。 もしそうなら、パートナーがいないよりは良いので、すぐに受け入れます。 
6. 受信者にすでにパートナーがいる場合は、事前に計算されたランキング テーブルを使用して、現在のパートナーと新しい提案者を比較します。 受信側は優先度の高い方を保持し、もう一方を拒否します。 拒否された提案者は再び自由になり、次の希望から続行します。 
7. 自由な提案者がなくなるまで繰り返し、その時点ですべての参加者が 1 回だけ一致します。 

核となる不変条件は、各受信者が優先順位に従って、これまでに見た中で最良のパートナーを常に保持しているということです。 新しい提案は、受信者にとって厳密に優れている場合にのみ、現在の一致を置き換えます。 提案は各提案者の優先度が低い順に進むため、提案者が以前に拒否された候補に戻ることはなく、受信者が現在の比較を超えて過去の決定を再考する必要はありません。 

この不変条件により、プロセスが確実に終了し、安定したマッチングが生成されます。つまり、割り当てられたパートナーよりもお互いを優先する参加者のペアが存在しないことを意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    
    men_pref = [list(map(int, input().split())) for _ in range(n)]
    women_pref = [list(map(int, input().split())) for _ in range(n)]
    
    # build rank: rank[w][m] = preference order of man m for woman w
    rank = [[0] * n for _ in range(n)]
    for w in range(n):
        for i, m in enumerate(women_pref[w]):
            rank[w][m] = i
    
    # next proposal pointer for each man
    ptr = [0] * n
    
    # current partner of each woman, -1 means free
    partner = [-1] * n
    
    from collections import deque
    free = deque(range(n))
    
    while free:
        m = free.popleft()
        
        w = men_pref[m][ptr[m]]
        ptr[m] += 1
        
        if partner[w] == -1:
            partner[w] = m
        else:
            cur = partner[w]
            if rank[w][m] < rank[w][cur]:
                partner[w] = m
                free.append(cur)
            else:
                free.append(m)
    
    # build answer: partner of each man
    ans = [-1] * n
    for w in range(n):
        if partner[w] != -1:
            ans[partner[w]] = w
    
    print("\n".join(map(str, ans)))

if __name__ == "__main__":
    solve()
```実装では、アルゴリズムを段階的に反映します。 の`rank`table は、プリファレンスの比較を O(1) 操作に変換する重要な前処理ステップです。 これがないと、すべての比較が優先リストの線形スキャンに劣化してしまう可能性があります。 

の`ptr`配列は、各提案者が優先リストのみを前に進むことを強制します。 これは、同じ候補者への繰り返しの提案を防止し、提案総数が線形になるようにするメカニズムです。 

無料の提案者のキューにより、処理の公平性が保証されます。拒否された人はすぐにシステムに再入力し、中断したところから続行されます。 

## 実用的な例

 両側に 3 人の参加者がいる小さな例を考えてみましょう。 

入力:

 - 男性の好み:

 - M0: W0 W1 W2
 - M1: W0 W1 W2
 - M2: W1 W0 W2
 - 女性の好み:

 - W0: M1 M0 M2
 - W1: M0 M1 M2
 - W2: M0 M1 M2

 ### トレース

 | ステップ | 男 | 女性 | 現在のパートナー | アクション |
 | --- | --- | --- | --- | --- |
 | 1 | M0 | W0 | なし | W0 は M0 を受け入れます |
 | 2 | M1 | W0 | M0 | W0 は M1 を優先し、| を切り替えます。 
| 3 | M0 | W1 | なし | W1 は M0 を受け入れます |
 | 4 | M2 | W1 | M0 | W1 は M2 を優先し、スイッチ |
 | 5 | M0 | W1 | M2 | M0 が W2 に移動し、W2 が M0 を受け入れます。 
| 6 | M1 | W0 | M1 | W0 は M1 に残ります |
 | 7 | M2 | W1 | M2 | M2 は W1 に残ります |

 最終的なマッチングは M1-W0、M2-W1、M0-W2 になります。 

このトレースは、受信者がパートナーを複数回変更する可能性があることを示していますが、それは優先順位が向上する方向にのみです。 各スイッチは受信者の状況を厳密に改善し、参加者がより悪いパートナーに移動することは決してないという不変条件を確認します。 

### 2 番目の例: 逆の設定

 男性と女性は互いに逆の順序でランク付けされます。 これにより、最大のチャーンが発生します。どの提案も一時的に一致し、より上位の提案者が到着するとすぐに置き換えられます。 この不安定性にもかかわらず、拒否されるたびにポインタが永続的に進むため、各ペアは依然として一定回数処理されます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n^2) | n 個の提案者のそれぞれが最大 n 個の提案を行い、各提案はランク テーブル | を使用して O(1) で処理されます。 
| スペース | O(n^2) | 優先リストとランク テーブルのストレージ |

 二次境界は、n が最大数千である場合、または入力サイズが優先リストによって支配される場合の、安定したマッチング問題の典型的な制約に適合します。 定数時間の決定構造により、これらの制限内でのスケーラビリティが保証されます。

 ## 特殊なケース

 すべての提案者が最初に同じ受信者をターゲットにすると、アルゴリズムは拒否カスケードを繰り返しトリガーします。 たとえば、3 人の提案者がすべて W0 を 1 位にランク付けしている場合、W0 は 1 つを受け入れ、その後 2 回置き換えます。 実装はこれを正しく処理します。拒否されるたびに、置き換えられた提案者がすぐにキューに戻され、提案が失われないことが保証されます。 

優先リストがサイド間で厳密に逆転している場合、すべての受信者は最初にランクの低いパートナーを受け入れ、その後、より優れた提案者が到着するにつれてそのパートナーを置き換えます。 ランク テーブルでは、各比較が O(1) であることが保証されるため、マッチングが頻繁に進化しても、操作の合計数は優先リスト内のエッジの数によって制限されたままになります。 

提案者が連続して複数回拒否された場合、ポインタは、以前の提案を再度検討することなく、次の候補から続行することを保証します。 これにより、無限ループが防止され、プロポーザーごとに最大 n 回の提案後の終了が保証されます。
