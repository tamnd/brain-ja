 ## 解決策
 ## 問題の理解

 各曲には 2 つの属性があります。 その長さは`l`そして独立してマナオはそれを確率で好きになります`p`。 

曲が初めて再生されると、2 つのうちのいずれかが起こります。 

彼が気に入った場合、その曲は思い出の曲のコレクションに追加されます。 

それが気に入らない場合は、覚えている曲をすべて一度だけすぐに再生します。 

思い出された曲は、まさに以前に処理されたすべての曲の中で気に入った曲です。 一度気に入った曲はずっと好きであり続けます。 

曲は任意の順序で並べることができます。 すべての順列の中で、予想される総リスニング時間を最大化する必要があります。 

入力には最大 50,000 曲が含まれます。 二次アルゴリズムには約 25 億のペア相互作用が必要ですが、これは制限をはるかに超えています。 解決策は次のようなものでなければなりません`O(n log n)`。 

主な難点は、曲の貢献度がその前に登場する曲によって異なることです。 将来嫌いになる曲があるために、曲は何度も再生される可能性があるため、ローカルの貪欲な選択はすぐにはわかりません。 

いくつかの特殊なケースは、誤って処理されやすいものです。 

決して好まれない曲を考えてみましょう。```
1
100 0
```予想される聴取時間は正確に`100`。 記憶された曲がないため、リプレイは発生しません。 処理せずに確率を盲目的に乗算する式`p = 0`正しく行うと、誤った追加の寄与が生成される可能性があります。 

常に好まれている曲を考えてみましょう。```
1
100 100
```答えもまた、`100`。 この曲は一度再生されますが、それ以降の曲は存在しないため、再実行されることはありません。 一部の導出では誤って自己相互作用をカウントし、より大きな値を取得します。 

もう 1 つの微妙なケースは、1 つの確率がゼロである場合です。```
2
100 100
200 0
```最初の曲が 2 番目の曲より前に配置されている場合、合計聴取時間は次のようになります。```
100 + 200 + 100 = 400
```なぜなら、2 番目の曲は確実に嫌いで、1 番目の曲の再プレイを引き起こすからです。 

順序が逆の場合、合計は```
200 + 100 = 300
```したがって、1 つの確率が決定的である場合でも、順序は重要です。 

## アプローチ

 ブルートフォース ソリューションでは、曲のあらゆる順列を試し、予想される視聴時間を計算し、最大値を維持します。 

固定順列の場合、期待値は確率式から計算できます。 残念ながら、あります`n!`順列。 たとえ`n = 15`これはすでに絶望的ですが、実際の限界は`50,000`。 

重要な観察は、期待は線形であるということです。 完全な実行について考える代わりに、曲のペア間の各相互作用の予想される寄与を計算できます。 

歌だと仮定して`i`曲の前に登場する`j`。 

歌`i`曲が再生されると`j`嫌いですが、それは歌の場合に限ります`i`前に好きでした。 

その出来事の確率は$$P(i\text{ liked}) \cdot P(j\text{ disliked})$$等しい$$\frac{p_i}{100}\left(1-\frac{p_j}{100}\right).$$それが起こるたびに、追加の`l_i`秒が聴取されます。 

したがって、注文されたすべてのペア`(i,j)`と`i`前に`j`貢献する$$l_i \cdot \frac{p_i}{100}\left(1-\frac{p_j}{100}\right)$$期待に応えて。 

すべての曲の最初の再生の予想される長さは、順序に関係なく、常に 1 回だけカウントされます。$$\sum l_i.$$したがって、最適化問題は次のようになります。$$\sum l_i + \sum_{i<j} l_i \cdot \frac{p_i}{100} \left(1-\frac{p_j}{100}\right).$$定数項は順列に依存しません。 ペアごとの項のみが重要です。 

目標がペアごとの寄与の合計として記述できる場合は常に、交換引数が適切なツールとなることがよくあります。 隣接する 2 つの曲を比較し、どちらの順序が優れているかを決定します。 これにより並べ替え基準が生成され、問題は 1 回の並べ替えだけで済みます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |`O(n! · n)`|`O(n)`| 遅すぎる |
 | 最適 |`O(n log n)`|`O(n)`| 承認済み |

 ## アルゴリズムのチュートリアル

 ### 順序付けルールの導出

 2曲考えてみましょう`A`そして`B`。 

させて$$a=l_A,\quad x=\frac{p_A}{100}$$そして$$b=l_B,\quad y=\frac{p_B}{100}.$$それらを交換すると、相互作用のみが変化します。 

もし`A`前に来る`B`、ペアが貢献します$$a x (1-y).$$もし`B`前に来る`A`、ペアが貢献します$$b y (1-x).$$私たちが欲しいのは`A`前に`B`いつ$$a x (1-y) > b y (1-x).$$乗算`100^2`分数を避けるには$$a p_A (100-p_B) > b p_B (100-p_A).$$これは 2 つの曲間の完全な比較ルールです。 

### ステップ

 1. すべての曲を読みます。 
2. コンパレーターを使用して曲を並べ替えます$$l_i p_i (100-p_j) > l_j p_j (100-p_i).$$この不等式が成り立つなら、歌`i`曲の前に表示する必要があります`j`。 

1. ソート後、期待値を計算します。 
2. メンテナンス$$S=\sum_{\text{processed}} l_i \cdot \frac{p_i}{100}.$$

`S`は、以前に処理されたすべての曲の後で記憶される曲の予想される合計長を表します。 

1. 曲を左から右に処理します。 
2. 曲自体の最初のプレイを追加します。`l_i`、答えへ。 
3. 今の曲はかなりの確率で嫌いです$$1-\frac{p_i}{100}.$$その場合、記憶されているすべての曲が再生されます。 予想される全長はまさに`S`。 

追加$$S\left(1-\frac{p_i}{100}\right)$$答えに。 

1.アップデート$$S \leftarrow S + l_i\frac{p_i}{100}.$$1. 最終的な期待値を出力します。 

### なぜ効果があるのか

 ペアワイズ目標は加算的です。 隣接する 2 つの曲の場合、考えられる 2 つの順序間の寄与の差は、これら 2 つの曲にのみ依存します。$$a p_A (100-p_B) - b p_B (100-p_A).$$この値が正の場合は常に、`A`前に`B`期待が高まります。 これにより、有効なペアごとの順序関係が定義されます。 その関係に従ってソートすると、隣接する反転がすべて削除されることが保証されます。 標準的な交換引数によれば、これ以上交換しても配置を改善できないため、結果として得られる置換は最適になります。 

期待値の線形性により、記憶されている曲のランダムなセットをその期待される全長で置き換えることができるため、期待値の計算も正確です。`S`。 各曲は独立して貢献しています`l_i p_i/100`予想される記憶された長さまで。 

## Python ソリューション```python
import sys
from functools import cmp_to_key

input = sys.stdin.readline

def solve():
    n = int(input())
    songs = []

    for _ in range(n):
        l, p = map(int, input().split())
        songs.append((l, p))

    def cmp(a, b):
        l1, p1 = a
        l2, p2 = b

        left = l1 * p1 * (100 - p2)
        right = l2 * p2 * (100 - p1)

        if left > right:
            return -1
        if left < right:
            return 1
        return 0

    songs.sort(key=cmp_to_key(cmp))

    ans = 0.0
    remembered = 0.0

    for l, p in songs:
        prob = p / 100.0

        ans += l
        ans += remembered * (1.0 - prob)

        remembered += l * prob

    print("{:.12f}".format(ans))

if __name__ == "__main__":
    solve()
```コンパレータはソリューションの中心です。 これは、一対の曲の 2 つの可能な順序を比較することから直接得られます。 相互乗算を使用すると、ソート時の浮動小数点精度の問題が回避されます。 

変数`remembered`すでに記憶されている曲の予想される合計長さを保存します。 これは、1 回の実行中の実際のランダムな長さではありません。 期待値の線形性により、期待値のみを追跡すれば十分です。 

答えは徐々に蓄積されます。 すべての曲は、独自の初期再生長さに影響します。 そうすると、確率的には`1 - p/100`、記憶されているすべての曲が再生されます。 これらの曲の予想される長さは正確に`remembered`。 

コンパレータ内のすべての演算では整数が使用されます。 最大値はおよそ$$1000 \cdot 100 \cdot 100 = 10^7,$$これは Python の整数の範囲と比較すると小さいです。

## テストケース```python
import sys
import io
from functools import cmp_to_key

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    input = sys.stdin.readline

    n = int(input())
    songs = [tuple(map(int, input().split())) for _ in range(n)]

    def cmp(a, b):
        l1, p1 = a
        l2, p2 = b

        x = l1 * p1 * (100 - p2)
        y = l2 * p2 * (100 - p1)

        if x > y:
            return -1
        if x < y:
            return 1
        return 0

    songs.sort(key=cmp_to_key(cmp))

    ans = 0.0
    remembered = 0.0

    for l, p in songs:
        prob = p / 100.0
        ans += l
        ans += remembered * (1.0 - prob)
        remembered += l * prob

    return f"{ans:.12f}"

# provided sample
assert run(

150 50
100 50
"""
) == "537.500000000000", "sample 1"

# minimum size

"""
) == "400.000000000000", "replay triggered once"

"""
) == "180.000000000000", "no remembered songs ever"

 ## 特殊なケース

 ### 好きではなかった曲

 入力:```
1
100 0
```ソート順は変更されません。 最初は`remembered = 0`。 

曲が貢献してるよ`100`初めてのプレイに。 以来`remembered`がゼロの場合、リプレイ期間もゼロになります。 答えはまさに`100`。 

### いつも好きだった曲

 入力:```
1
100 100
```曲が貢献してるよ`100`。 リプレイ確率はゼロなので、何も追加されません。 その後`remembered`になる`100`, しかし、その後の曲はありません。 結果は残る`100`。 

### 決定的な好きの後の決定的な嫌い

 入力:```
2
100 100
200 0
```コンパレーターは、2 番目の曲よりも 1 番目の曲を優先します。$$100 \cdot 100 \cdot 100 > 200 \cdot 0 \cdot 0.$$最初の曲を処理した後、`remembered = 100`。 

2曲目は確かに嫌いなのでリプレイ貢献度はまさに`100`。 

最終的な答えは、$$100 + 200 + 100 = 400.$$これにより、アルゴリズムが両極端の確率を正しく処理し、並べ替えルールを通じてリプレイの機会を正しく活用していることが確認されます。
