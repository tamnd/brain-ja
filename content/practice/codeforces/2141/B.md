 ## 解決策
 ## 問題の理解

 2 人のプレイヤーはそれぞれ、楽しんでいるゲームの固定ソート リストを保持しています。 彼らはどの一般的なゲームを選択すればよいのかすぐには分からないため、提案を繰り返すことなく、個人的に好きなゲームを一度に 1 つずつ提案する決定的な交互プロセスを経ます。 

プロセスはアリスから始まります。 彼女の番では、リストからこれまで提案されていないゲームを提案する必要があります。 ボブもそのゲームが好きなら、プロセスはすぐに終了します。 そうでなければ、ボブは自分のリストから新しい未使用のゲームを提案することで応答し、アリスはそれをチェックします。 提案されたゲームのいずれかが両方のリストに属するまで、このように交互に繰り返します。 

私たちが必要とする量は、両方のプレイヤーがこの交差点をできるだけ遅らせる方法で行動すると仮定して、最終的に共通のゲームに到達するまでに強制できる提案の最大数です。 

入力制約は小さく、各リストには最大 100 個の要素が含まれ、値も 100 で制限されますが、最大 1000 個のテスト ケースが与えられます。 これにより、テスト ケースごとに超二次関数が必要になることが即座に排除されます。 値ごとの単純な線形スキャンまたはいくつかのセット操作でも十分です。 

単純なアプローチでは、考えられるすべての提案順序をシミュレートしようとする可能性があります。 これは、各プレイヤーが未使用の要素を選択できるため、分岐が組み合わせ的に爆発的に増加するため、失敗します。 順列に限定しても、系列の数は n と m で階乗的に増加しますが、これは n = m = 100 の場合でも完全に不可能です。 

微妙な間違いは、答えが 1 つの最適な共通要素 (たとえば、最も古い交差点または最も新しい交差点を選択するなど) にのみ依存すると仮定することから発生します。 これでは十分ではありません。最適な戦略は、交差が発生する場所だけでなく、両側の交差の外側にある要素の数に依存するためです。 

小さなトラップの例は次のとおりです。 

入力:```
1
3 3
1 2 3
3 4 5
```ここで唯一の共通要素は 3 であり、プロセスは 3 で終了する必要があります。交差点関連の位置を選択して「遅延」しようとする素朴な推論は、すべての非共通要素は 3 に到達する前に単に無駄な提案であるという事実を見落としています。 

## アプローチ

 重要な観察は、リストはすでに固定されているため、このプロセスは実際には各リスト内の順序付けや戦略に関するものではないということです。 唯一の自由は各ターンでどの未使用要素を選択するかですが、提案の数を最大化しているため、両方のプレイヤーは常に非共有要素を最初に使い果たすことで共有要素を可能な限り遅らせます。 

これは、各リストを、アリスに固有の要素、ボブに固有の要素、および両方に共有される要素の 2 つの部分に分けることができることを意味します。 共有セットのサイズを c、アリスのみのサイズを a、ボブのみのサイズを b とします。 

プレイヤーがゲームを提案するたびに、それが他のリストにない場合は、固有の要素を 1 つ消費します。 最終的に、両側ですべての固有の要素が使い尽くされると、次の提案は共通の要素でなければならず、提案されるとすぐにプロセスが終了します。 

最適な戦略では、共通要素が正常に提案される前に、両側のすべての非共通要素がシーケンス内に強制的に出現するようになります。 したがって、プロセスの長さは、交差の外側にある要素の数と最終的に成功した提案 1 つによって決まります。 

より正確には、どちらかの側からのすべての一意の要素が終了前に 1 回だけ提案され、最後の 1 つの提案によって一致がトリガーされます。 

したがって、答えは次のようになります。 

合計提案数 = (アリスのみの要素数) + (ボブのみの要素数) + 1。 

集合演算のみが必要なため、交差サイズを計算し、その他すべてを導出します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべての選択肢のブルート フォース シミュレーション | 指数 | 指数 | 遅すぎる |
 | 固有要素と共通要素のセットベースのカウント | テスト ケースごとに O(n + m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 集合演算を使用して各テスト ケースを個別に解決します。 

1. アリスのリストとボブのリストを読み取り、重複や順序が問題にならないように両方をセットに変換します。 これにより、メンバーシップのみが関連するため、推論が簡素化されます。 
2. 両方のプレイヤーが好むゲームを表す、両方のセットの共通部分を計算します。 
3. アリスの設定サイズから交差サイズを減算して、アリスに固有の要素の数を数えます。 これにより、ゲームをすぐに終了することなく、アリスが提案できるすべての要素が提供されます。 
4. ボブにも同じことを行います。 
5. 答えは、アリスのみの要素、ボブのみの要素、および共有ゲームが提案され受け入れられる最後の 1 つの動きの合計です。 

この順序が有効である理由は、両方のプレイヤーが繰り返しを避け、共通の提案が発生した場合にのみ終了する必要があるため、共有要素が選択される前に、すべての非共有要素が交互のプロセスのある時点で出現する必要があるためです。 

### なぜ効果があるのか

 終了前のどの時点でも、プロセスはどちらかのセットの以前に使用されていなかった要素を単純に消費しています。 共有要素はゲームを終了できる唯一の要素であるため、提案の数を最大化することは、最初の共有要素をできるだけ長く遅らせることと同じです。 共有要素を強制する前に、すべての非共有要素を提案する必要があるため、プロセスの長さは固定されており、非共有要素の合計数に 1 つの端末共有提案を加えたものに等しくなります。 この不変式は順序の選択には依存しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    n, m = map(int, input().split())
    a = set(map(int, input().split()))
    b = set(map(int, input().split()))
    
    common = len(a & b)
    only_a = len(a) - common
    only_b = len(b) - common
    
    print(only_a + only_b + 1)
```このコードでは、Python セットを使用してメンバーシップ関係を直接計算します。 交差点`a & b`共有ゲームを提供します。 各セットからそのサイズを引くと、各側の独占ゲーム数が得られます。 1 つ追加すると、プロセスが終了する最後の共有ゲームのアカウントが作成されます。 

重要な点は、重複は問題ではないということです。 この問題では入力リストが厳密に増加しているにもかかわらず、それらをセットとして扱うことは、「それぞれの異なるゲームを最大 1 回提案する」というロジックに直接一致します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        n, m = map(int, input().split())
        a = set(map(int, input().split()))
        b = set(map(int, input().split()))
        common = len(a & b)
        out.append(str(len(a) - common + len(b) - common + 1))
    return "\n".join(out)

 ## 特殊なケース

 エッジケースの 1 つは、すべてのゲームが共通である場合です。 そのような状況では、最初に何を提案しても、ゲームはすぐに終了します。 この式では、両側の一意の要素が 0 に 1 を加えて 1 が生成されます。これは、最初の提案がすでにプロセスを終了しているという事実と一致します。 

もう 1 つのケースは、一方のみに多くの独自要素があり、もう一方にはほとんどユニークな要素がない場合です。 たとえば、アリスが 100 の固有のゲームを持ち、ボブが 1 つだけを共有する場合、プロセスは共有ゲームに到達する前に、必然的に 100 のアリス専用要素すべてとボブ専用要素を消費することになります。 ソリューションの構造は、最終的な共有の手を追加する前に両側を独立して処理するため、この非対称性を適切に考慮しています。 

最後の微妙なケースは、共有要素が複数ある場合です。 それでも、プロセスを終了するために必要なのはそのうちの 1 つだけであるため、すべての共有要素を個別にカウントすると過剰にカウントされてしまいます。 このアルゴリズムは、すべての共有要素を個別に処理するのではなく、単一の終了イベントに集約することでこれを回避します。
