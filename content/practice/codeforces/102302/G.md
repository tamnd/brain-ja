 ## 解決策
 ## 問題の理解

 左から右に配置された 3 つのスタックがあります。`a`、`b`、 そして`c`岩。 毎ターン、現在のプレイヤーは空ではないスタックを 1 つ選択し、次のスタックを削除します。`1`そして`m`岩。 唯一の制限は、スタックの最後のロックを削除することです。スタックが空になるのは、その左側のすべてのスタックがすでに空になっている場合のみです。 

最初のスタックの左側にはスタックがないため、いつでも空にすることができます。 2 番目のスタックは最初のスタックが消えた後にのみ空にでき、3 番目のスタックは前のスタックが両方とも消えた後にのみ空にできます。 全体のポジションから最後の石を取り除いたプレイヤーが勝利となるため、これは通常プレイの公平なゲームです。 最適なプレイの下で、初期位置が Tomaz の勝ちなのか、Tomaz の負けなのかを判断する必要があります。 

4 つの入力値はすべて (10^{18}) に達します。 これにより、岩石の数に対する動的計画法は即座に排除され、回転数に比例するシミュレーションさえも不可能になります。 解は剰余剰余などの算術特性のみに依存する必要があります。`m + 1`、一定または対数の実行時間で。 

誤って処理しやすい境界効果が 2 つあります。 まず、前のスタックが空でない間は後のスタックを空にすることはできません。 たとえば、`m = 1`そして入力`1 1 2`, 最初のスタックにはまだ岩が 1 つ含まれているため、Tomaz は最初の動きで 2 番目のスタックから 1 つの岩を取り除くことができません。 3 つのスタックを独立した減算ゲームとして扱う解決策では、ゲームの状態が誤ってしまいます。 

2 番目のエッジ ケースは、最初のスタックが常に空になる可能性があることです。 と`m = 3`そして入力`3 1 1 1`, トマズは最初のスタックから唯一の岩を削除し、その後ダンフティトは 2 番目のスタックに強制的に移動し、トマズは 3 番目のスタックから最後の岩を取り出します。 正しい答えは、`Tomaz`。 「左側に何かがある間は空にできない」という制限を最初のスタックに適用するソリューションは、勝利した最初の手を誤って拒否します。 

3 番目の微妙なケースは、スタックが 1 回の移動で空にできるほど小さい場合に発生します。 たとえば、`m = 3`、を含むスタック`1`、`2`、 または`3`岩はゼロへの直接移動を持ちますが、スタックには`4`しません。 したがって、最適な式では、最大でも値に対して別の処理が行われます。`m`。 

## アプローチ

 直接再帰的解決策はゲームの定義に従います。 州から`(a,b,c)`、各スタックから削除するすべての法定数の岩を試し、結果の局面が勝ちであるかどうかを再帰的に判断し、少なくとも 1 つの手が負けの局面に到達した場合に、現在の局面が勝ちであると宣言します。 これは正しいです。すべての動きが厳密に岩の総数を減らすため、ゲーム グラフは有限です。 

問題は状態と移動の数です。 州は最大で次のものを持つことができます`3m`合法的な手、ゲームには最大で次のものを含めることができます。`a + b + c`曲がる。 (10^{18}) ほど大きい値では、仮想の線形走査でもすでに制限をはるかに超えています。 再帰的なゲーム ツリーは指数関数的に悪化します。 

重要な観察は、スタックをまだ空にすることはできませんが、そこから岩を 1 つ減算することは、1 つ少ない岩で通常の減算ゲームをプレイするのと同じであるということです。 単一の引き算ゲームの場合、以下を削除する可能性があります。`1`を通して`m`岩、サイズの山のグランディ値`x`は`x mod (m + 1)`。 したがって、スタックが左側の空でないスタックによってロックされている間、スタックの山は`x`岩石はサイズの減算の山のように動作します`x - 1`、グランディの価値を与える`(x - 1) mod (m + 1)`。 

これにより、右側のロックされたスタックが通常の Nim 位置に変わります。 唯一の特別なイベントは、現在アクティブな一番左のスタックが 1 回の移動で空にできるほど小さい場合です。 その時点で、ゲームはサフィックスのロックされたバージョンから完全にロック解除されたバージョンのサフィックスに変わります。 スタックが 3 つしかないため、この遷移を明示的に処理できます。 

同じ推論で、最初に 2 スタック ゲームを解き、次にその結果を 3 スタック ゲームのサフィックス状態として使用できます。 最初のスタックが十分に大きい場合、1 回の移動で空にすることはできないため、現在のゲームは、最初のスタックの減算ゲーム値とロックされたサフィックス値の単純な XOR になります。 最初のスタックが小さい場合は、ゼロ化移動が利用可能で、ロック解除されたサフィックスが勝っているか負けているかに応じて、その最初のスタックのパリティに従って結果が交互に変わります。

 ## アルゴリズムのチュートリアル

 1. しましょう`k = m + 1`。 を取り除く通常の引き算ゲーム`1`を通して`m`岩にはグランディの価値がある`x mod k`。 
2. まず、2 つのスタックの位置を解決します。`(b,c)`、元の 3 スタック ゲームのロック解除されたサフィックスになるためです。 
3. その間`b`空ではない、スタック`c`空にすることはできません。 したがって、そのロックされた値は次のようになります。`(c - 1) mod k`。 もし`b > m`、スタック`b`また、一度の動きで空にすることはできないため、2 つのスタックは値を使用した独立した減算ゲームとして動作します。`b mod k`そして`(c - 1) mod k`。 XOR がゼロの場合、ポジションは正確に負けています。 
4. もし`b <= m`、スタック`b`すぐに空にすることができます。 もし`(c - 1) mod k`がゼロでない場合、ロックされたサフィックスの Nim 値はゼロではないため、プレーヤーはサフィックスをゼロの Nim 値に変更できるため、現在の位置が勝ちとなります。 
5. 残りの 2 スタックのケースは、`(c - 1) mod k = 0`。 ロックされたサフィックスは負けのポジションになります。 空にする`b`通常の 1 スタック ゲームに直接移行します`(c)`。 その 1 スタックのポジションがまさにいつ負けるか`c mod k = 0`。 
6. したがって、次の場合、`b <= m`そして`(c - 1) mod k = 0`、2 つのスタックの位置は次のパリティで交互になります。`b`。 もし`(c mod k) != 0`、ロック解除されたサフィックスが勝っているので、奇妙です`b`負けの立場を与えます。 もし`(c mod k) == 0`、ロックされていないサフィックスは負けているので、`b`負けの立場を与えます。 
7. 次に、元のサフィックスのロックされた Grundy 値を計算します。`(b,c)`:`locked = ((b - 1) mod k) XOR ((c - 1) mod k)`。 
どちらでもないため、これは有効です`b`または`c`その間空になる可能性があります`a`はポジティブです。 
8. もし`a > m`、最初のスタックを 1 回の移動で空にすることはできません。 したがって、位置全体は、減算ゲームの通常の素の合計になります。`a`そしてロックされたサフィックス。 トーマズが勝つのはまさにそのときだ`a mod k XOR locked != 0`。 
9. もし`a <= m`そして`locked != 0`, トマズはロックされたサフィックス内で勝ち手を決めることができるので、ポジションは勝ちです。 
10. もし`a <= m`そして`locked == 0`、変化するすべての動き`b`または`c`勝利の位置に行きます。 残る唯一の問題は、最初のスタックがゼロになったときに何が起こるかということです。 その移動はすでに計算された 2 スタックの位置に到達します`(b,c)`。 そのサフィックスが勝っている場合、次の州が勝ちます。`a = 1,2,3,...`奇数の負け状態から始まる代替`a`。 サフィックスが負けている場合は、偶数で負けている状態から交互に開始します。`a`。 

### なぜ効果があるのか

 不変条件は、空になることが禁止されたスタックが、そこから 1 つの概念的な岩を取り除いた後、減算ゲームとまったく同じように動作するということです。 その正当な値は次のとおりです。`x -> x-d`のために`1 <= d <= min(m,x-1)`、これはまさに通常の引き算ゲームです。`x-1`岩。 したがって、ロックされたサフィックスは、これらのシフトされた残基の XOR 演算によって得られる標準 Nim 値を持ちます。 

このロックされた Nim モデルで表されない唯一の動きは、現在の左端のスタックを空にする動きです。 このような動きは、次のスタックのロックを解除できるようになるため、サフィックスのルールを変更します。 2 つのスタックについては、このロックされていないサフィックスを直接計算し、それを最初のスタックの最終結果として使用します。 小さな最初のスタックは、すべての小さな正のサイズに移動でき、ゼロに移動することもできるため、勝ちと負けの状態はパリティによって交互になります。 最初のスタックが大きい場合、1 回の移動ではゼロに到達できないため、通常の XOR 特性が適用されます。 これらの訴訟はあらゆる法的措置をカバーしており、正確に正しい結果をもたらします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def two_stack_wins(m, b, c):
    k = m + 1

    # While b > 0, c cannot be emptied.
    locked_c = (c - 1) % k

    if b > m:
        return ((b % k) ^ locked_c) != 0

    # b can be emptied immediately.
    if locked_c != 0:
        return True

    # If b is emptied, the remaining game is a normal
    # one-stack subtraction game on c.
    suffix_wins = (c % k) != 0

    # With locked suffix of Grundy value 0, outcomes alternate
    # as b goes through 1, 2, ..., m.
    if suffix_wins:
        # Losing for odd b.
        return (b % 2) == 0
    else:
        # Losing for even b.
        return (b % 2) == 1

def solve():
    m, a, b, c = map(int, input().split())
    k = m + 1

    # Outcome of the suffix after the first stack has been emptied.
    suffix_wins = two_stack_wins(m, b, c)

    # While a > 0, both later stacks are locked against becoming empty.
    locked = ((b - 1) % k) ^ ((c - 1) % k)

    if a > m:
        # The first stack cannot reach zero in one move, so the
        # position is an ordinary disjoint sum.
        first_value = a % k
        wins = (first_value ^ locked) != 0
    else:
        if locked != 0:
            wins = True
        else:
            # locked suffix is a P-position. The only exceptional
            # transition is a -> 0, which reaches the unlocked suffix.
            if suffix_wins:
                # P for odd a.
                wins = (a % 2) == 0
            else:
                # P for even a.
                wins = (a % 2) == 1

    print("Tomaz" if wins else "Danftito")

if __name__ == "__main__":
    solve()
```の`two_stack_wins`関数は、ウォークスルーからの再帰的なサフィックス分析を実装します。 表現`(c - 1) % k`はシフトされた減算ゲームの値です`c`スタックしながら`b`まだ空ではありません。 

いつ`b > m`、2 番目のスタックを 1 回の移動で空にすることはできないため、特別な遷移には到達できません。 この状態は、2 つのロックされた減算ゲームの単なる XOR です。 いつ`b <= m`、ゼロ化遷移は個別に処理する必要があります。 

main 関数は、1 レベル前とまったく同じ考え方を適用します。 値`locked`はシフトされた値の XOR です。`b`そして`c`。 もし`a > m`、最初のスタックからはゼロに到達できないため、通常の XOR テストで十分です。 もし`a <= m`、ゼロ化遷移が存在し、結果はすでに計算されたロック解除されたサフィックスに依存します。 

Python の整数には任意の精度があるため、(10^{18}) の範囲には特別なオーバーフロー処理は必要ありません。 表現`m + 1`も安全であり、モジュロ演算は XOR 比較の前に実行されます。

 ## 特殊なケース

 最初の重要なエッジ ケースは、最初のスタックが常に空になる可能性があることです。 のために`3 1 1 1`、`a = 1 <= m`、Tomaz が直接移動できるようにする`(0,1,1)`。 2 つのスタックの接尾辞`(1,1)`Danftito が 2 番目のスタックを空にする必要があるため、負けています。その後、Tomaz が最後のロックを取得します。 アルゴリズムは計算します`locked = 0`、サフィックスが負けていることがわかり、奇数を使用します`a`元の状態を勝利として分類します。 

2 番目のエッジ ケースは、まだ空にすることができない後のスタックです。 考慮する`1 1 2 1`。 ここ`k = 2`、サフィックスのロックされた値は次のとおりです。`((2-1) mod 2) XOR ((1-1) mod 2) = 1`。 ロックされた値はゼロ以外であるため、現在位置がすぐに勝ちになります。 プレーヤーは、2 番目のスタックを不正に空にすることなく、ロックされたサフィックス内でプレイできます。 治療中`b`通常のヒープではこの制限が適用されないためです。 

3 番目のエッジ ケースは、次より大きい最初のスタックです。`m`。 のために`1 2 1 1`、最初のスタックには 2 つの岩が含まれていますが、1 回の移動で削除できるのは 1 つだけなので、すぐにゼロになることはありません。 ロックされたサフィックスの値はゼロであり、`a mod 2 = 0`、合計 XOR がゼロになります。 Tomaz は負けている状態に移行することができないため、答えは次のとおりです。`Danftito`。 これはまさに、通常の Nim 分解が再び有効になる状況です。 

最後のエッジ ケースは、まさにモジュラス境界にあるスタックです。 と`m = 3`、山積み`4`引き算ゲームの価値がある`4 mod 4 = 0`、ロックされた山がありながら、`4`価値がある`(4-1) mod 4 = 3`。 これら 2 つの式を混同することは、古典的な off-by-one エラーです。 アルゴリズムが使用するのは、`x % (m+1)`空にできるスタックのみ、そして`(x-1) % (m+1)`現在空にすることが禁止されているスタックについて、各フェーズの実際の合法的な動きと一致します。
