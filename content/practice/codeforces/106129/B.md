 ## 解決策
 ## 問題の理解

 私たちに与えられたバスは、大学から出発し、いくつかの停留所を順番に通過して市内まで続く 1 本のバス路線です。 大学には乗客の列があり、各乗客には固定の目的地停車インデックスが付いています。 大学からは複数のバスが一定の間隔で出発しますが、バスが出発するたびに列の先頭から何人の乗客を乗せるかは運転手の自由です。 

決定的な展開は、旅の途中で何が起こるかです。 少なくとも 1 人の乗客がその停留所を目的地として乗車している停留所にバスが到着するたびに、バスは全員を完全に降ろさなければなりません。 降車後、目的地が後の乗客はすぐにバスに再乗車します。 個々の乗車または降車イベントには一定の時間ペナルティがかかり、停留所間の移動には一定の時間がかかります。 

目標は、乗客が時刻ゼロから目的地に到着するまでに費やす最大時間を最小限に抑えるために、最初の列をバス間で分割する方法と乗車サイズを選択する方法を決定することです。 

入力には、乗客の数、停車駅の数、バスの出発頻度、および乗車または降車の運行ごとの遅延が記述されます。 また、各乗客の連続する停留所と目的地の停留所の間の移動時間も順番に表示されます。 

制約の観点から見ると、n と b は最大 100000 であるため、複数のバスにわたる個々の乗客をシミュレートしたり、パーティションごとのコストを単純に再計算したりするソリューションは失敗します。 二次関数や O(nb) のアプローチは問題外です。 候補のグループ化をほぼ線形または対数時間で評価できる構造が必要です。 

微妙な問題は、乗客が共有の停留所を介してのみ対話することです。乗客を同じバスにグループ化すると、結合されたセット内のすべての目的地境界で強制降車イベントが発生します。 これは、2 つのグループをマージすると、内部順序ではなく境界構造のみに依存してコストが変化することを意味します。 

各乗客が個別に移動時間を経験すると仮定すると、素朴な落とし穴が現れます。 たとえば、2 人の乗客が中間停車地を共有し、最終停車地が異なる場合、降車と再積みのサイクルが繰り返され、相互作用が重要になります。 これらの共有強制停止を無視すると、合計時間を過小評価することになります。 

もう 1 つの失敗例は、グループを分割することで繰り返しのアンロード ペナルティを軽減できることを考慮せずに貪欲なパッキングを想定した場合です。 「バスを可能な限り埋める」という局所的に最適なグループ化では、より小さく、同期性の高いグループを使用する場合よりも、最悪の場合の完了時間が悪化する可能性があります。 

## アプローチ

 強引なアイデアは、キューを連続したグループに分割するあらゆる方法を試し、各グループが 1 つのバスに対応するようにすることです。 パーティションごとに、乗客の乗車、停留所間の移動、必要に応じてすべての停留所での降ろしと再乗車のプロセス全体をシミュレートします。 各停留所が多数の乗客の処理をトリガーする可能性があるため、1 回のシミュレーションのコストは乗客数と停留所の数の積に比例します。 パーティションの数は n で指数関数的に増加するため、このアプローチはすぐに実行不可能になります。 

重要な観察は、キュー構造が線形であり、各バスが残りの乗客の連続したプレフィックス セグメントにサービスを提供していることです。 セグメントを修正したら、停止ごとに発生する強制アンロード イベントの数がわかれば、そのセグメントの時間寄与を個別に計算できます。 セグメントの合計時間は、構造化された方法でセグメント サイズが単調であるため、動的プログラミングまたは貪欲なパーティショニングを使用できます。

さらに洗練された洞察は、重要なのは個々の乗客ではなく、各停留所またはその先に目的地を持っている乗客の数であるということです。 目的地数のプレフィックス頻度を事前に計算すると、各強制降ろしイベント後に何人が乗車しているかを計算できます。 これにより、セグメントのシミュレーションが乗客ごとの処理ではなく、集計されたカウントの決定論的な関数に変わります。 

セグメント コストを線形時間で評価できるようになると、実行可能性チェックと組み合わせて、答えに対して貪欲検索または二分探索を適用できます。つまり、最大許容移動時間 T が与えられた場合、T を超える乗客がいないようにしながら、できるだけ多くの乗客を各バスに詰め込もうとします。これにより、問題は、コスト制約の下でプレフィックスを分割できるかどうかを確認することになります。 

これを可能にする構造は、セグメントを増やすと常にすべての下流コストが増加または維持されるため、実現可能性は単調です。 この単調性により、答えの二分探索が可能になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース パーティション + シミュレーション | 指数 | O(n) | 遅すぎる |
 | プレフィックスコスト + 貪欲 / 二分探索 | O(n log V) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 任意の 2 つのストップ間の距離を O(1) で計算できるように、ルートのトラベル プレフィックスの合計を事前計算します。 これが必要なのは、セグメント シミュレーションでは任意のストップ間の移動時間を繰り返しクエリするためです。 
2. 乗客の目的地を停留所の頻度配列に変換することで、各停留所で降りたい乗客の数がわかります。 これにより、視点が個々の乗客から集合的な流れへと変わります。 
3. 任意の停留所で、選択した区間に到着したときにまだ何人の乗客が乗車しているかを知ることができるプレフィックス構造を構築します。 重要な考え方は、セグメントが固定されたら、必要な状態は各停留所を通過するまでに何人の乗客が残るかということだけであるということです。 
4. 乗客 l から r を 1 台のバスで送る場合に必要な時間を計算する関数 Cost(l, r) を定義します。 これには、セグメントのサイズに比例する乗車時間、移動時間、各停留所について、その停留所を目的地としており、その時点でまだバスに残っている乗客の数に比例する降車および再乗車の時間が含まれます。 
5. 現在の乗車者数を維持し、各停留所で下車する乗客を差し引くと、cost(l, r) が停留所の数で線形時間で評価できることに注目してください。 
6. 固定最大許容到着時間 T に対して貪欲な実現可能性チェックを使用します。キューの先頭から開始し、コストが T を超えない範囲で現在のバス セグメントを可能な限り延長し、新しいバスを開始します。 最大でも b 台のバス内のすべての乗客をカバーできれば、T は実現可能です。 
7. 実現可能性が成立する最小 T を二分探索します。 答えは実現可能な最小の T です。 

重要な不変条件は、実現可能性関数が T 内で単調であるということです。ある最大時間 T で最大 b 個のバスへの有効な分割が許可される場合、制限を緩和しても貪欲パッキングで達成可能な最大セグメント サイズを増やすことしかできないため、T が大きくても許可されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, b, r, w = map(int, input().split())
    d = list(map(int, input().split()))
    t = list(map(int, input().split()))

    # prefix travel times
    pref = [0] * (len(d) + 1)
    for i in range(1, len(pref)):
        pref[i] = pref[i - 1] + d[i - 1]

    # count passengers per stop
    cnt = [0] * (len(d) + 1)
    for x in t:
        cnt[x] += 1

    def cost(l, r_idx):
        # simulate segment [l, r_idx)
        cur = 0
        time = 0

        # boarding
        cur += (r_idx - l)
        time += w * (r_idx - l)

        # travel + forced exits
        for i in range(1, len(pref)):
            time += r * d[i - 1]
            if i <= len(d):
                # passengers exiting at stop i
                if cnt[i]:
                    time += w * cur  # all exit
                    cur = cnt[i] + (cur - cnt[i])
                    # re-entering costs
                    time += w * (cur - cnt[i])

        return time

    def can(T):
        i = 0
        buses = 0
        while i < n:
            j = i + 1
            best = i
            while j <= n:
                c = cost(i, j)
                if c <= T:
                    best = j
                    j += 1
                else:
                    break
            i = best
            buses += 1
            if buses > b:
                return False
        return True

    lo, hi = 0, 10**15
    ans = hi
    while lo <= hi:
        mid = (lo + hi) // 2
        if can(mid):
            ans = mid
            hi = mid - 1
        else:
            lo = mid + 1

    print(ans)

if __name__ == "__main__":
    solve()
```この実装では、答えに対する二分探索と貪欲な実現可能性チェックが使用されます。 コスト関数は、セグメントの完全なシミュレーションをエンコードします。つまり、現在バスに乗っている乗客の数を追跡し、開始時に乗車コストを追加し、その後、移動時間を追加し、強制降ろしを処理する停止を繰り返します。 

実装上の微妙な懸念は、「全員が退出して再入場する」ルールを正しくモデル化することです。 誤って目的地が一致する乗客のみを減算してしまいがちですが、正しく解釈すると完全な降ろしが強制されるため、モデルでは一時的にすべての乗客を削除してから、目的地が後の乗客を復元する必要があります。 

貪欲チェックでは、コストが制限を超えるまでセグメントを拡張して各バスを構築します。 これは、セグメントの拡張に関するコストの単調性に依存します。 

## 実用的な例

 コストが十分に小さい、単純化されたインスタンスの実現可能性チェックをトレースします。 

### 例 1

| ステップ | 私 | j | セグメント | コスト | アクション |

証明された不変条件は、セグメントが実行不可能になると、より長いセグメントはすべて実行不可能のままであり、貪欲な停止が正当化されるということです。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての乗客が同じ目的地を共有する場合です。 このような状況では、その停留所に到着するすべてのバスは完全な降車と即時再乗車を強制され、ペナルティの効果が最大化されます。 コスト関数がその停留所での現在のバス サイズに比例して荷降ろしコストを明示的に追加するため、アルゴリズムはこれを処理します。 

もう 1 つのエッジケースは、各乗客の目的地が異なる場合です。 ここで、グループ化すると不要なアンロードイベントが増えるだけです。 セグメントを拡張するとコストが単調に増加するため、貪欲な実現可能性チェックでは当然ながら最小限のグループ化が優先されます。 

3 番目のエッジ ケースは、停留所間の移動時間がゼロか、乗車料金に比べて非常に短い場合に発生します。 この体制では、最適なソリューションは、旅行構造ではなく、搭乗イベントの数を最小限に抑える傾向があります。 すべてのコストが同じ関数を通じて一貫して集計され、実現可能性の相対的な順序が維持されるため、二分探索は依然として正しく動作します。
