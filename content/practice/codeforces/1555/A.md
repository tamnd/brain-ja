 ## 解決策
 ## 問題の理解

 各ピザが一定のスライス数と一定の焼き時間の両方を提供するピザの注文を作成するように求められます。 選択できる「アイテム」は 3 つあります。1 つは 15 分で 6 スライス、もう 1 つは 20 分で 8 スライス、最大のものでは 25 分で 10 スライスです。 各タイプを任意の数購入できますが、スライスの合計数は少なくとも`n`。 目標は、選択したすべてのピザの焼き時間の合計である合計焼き時間を最小限に抑えることです。 

したがって、これは 3 つの項目タイプにわたる無制限の選択問題になり、時間の線形コストを最小限に抑えながらスライス単位で目標合計に到達する必要があります。 各テスト ケースは独立しており、ターゲットは非常に大きくなる可能性があります。$10^{16}$これにより、明示的に組み合わせを探索したり、値空間に対して動的プログラミングを実行しようとするアプローチは即座に除外されます。 

状態空間が大きすぎるため、スライスに対する単純な DP は失敗します。 常に「1 分あたり最高のスライス数」のピザを選択する貪欲な試みでも、効率はすべての組み合わせで単調ではないため、失敗する可能性があります。 重要な問題は、オーバーシュートが許されていることです`n`、場合によっては、より優れた比率の項目でオーバーシュートすることが最適な場合があります。 

微妙なエッジケースが現れるのは、`n`小さいです。 たとえば、次の場合`n = 1`、どのソリューションでも少なくとも 1 つのピザを選択する必要があり、最小の有効な選択肢は 15 分のコストがかかる 6 スライスのピザです。 もう 1 つのエッジ状況は次のような場合です。`n`は、2、3、または 5 つのスライスの組み合わせでは割り切れません。つまり、正確な一致は不可能であり、オーバーシュートは慎重に処理する必要があります。 

## アプローチ

 ブルートフォースソリューションでは、すべてのトリプルが試行されます。$(a, b, c)$、小、中、大のピザの数を表し、$6a + 8b + 10c \ge n$、最小コストを追跡します$15a + 20b + 25c$。 これは、有効な注文をすべて列挙するため、正しいです。 しかし、その瞬間、`n`境界が大きくなり、$a, b, c$巨大化する。 次のような合理的な制限に制限することさえ$n/6$のために`a`まだ最大まで続く$10^{16}$計算上不可能な最悪の場合の可能性もあります。 

問題の構造により、より強力な単純化が可能になります。 すべてのスライス値とコストは 2 と 5 の倍数であり、さらに重要なのは、比率が非常に近いことです。 

- 6 スライス → 15 分 → 1 スライスあたり 2.5 分
 - 8枚切り → 20分 → 1枚あたり2.5分
 - 10 スライス → 25 分 → 1 スライスあたり 2.5 分

 すべてのピザの効率はまったく同じで、スライスあたり 2.5 分です。 これにより、タイプ間のトレードオフがなくなります。 残りの唯一の目標は、少なくとも次のレベルに達しながら、スライスの数を最小限に抑えることです。`n`より多くのスライスを組み合わせた場合、それに比例してより多くの時間がかかるためです。 

これにより、問題はきれいな算術観測に変換されます。つまり、最小の総スライス数 ≥ が必要なだけです。`n`これは 6、8、10 を使用して形成し、2.5 を掛けます。 

すべてのスライス サイズは偶数であるため、単純化するためにすべてを 2 で割ります。 

- 3、4、5 スライス
 - コストはそれぞれ 7.5、10、12.5 分ですが、比率は同じです

 ここで、最小の整数が必要になります ≥`n`3、4、5 を使用して形成し、その後縮小することができます。 

残りの構造は、3、4、5 が一定時間の構築を可能にするのに十分小さいということです。 最適な戦略は、最初に大きな部分を使用し、小さな残りを修正することです。 モジュロ 3 または 4 に対する短い事前計算されたパターンまたは貪欲なパターンで十分ですが、受け入れられている解決策はさらに単純化されています。3、4、5 は連続しているため、十分に大きな数であればどれでも表現できます。`n`最小限の組み合わせを直接テストします。 

実際には、最もクリーンな導出では、表現理論を完全に回避し、直接的な貪欲な洞察を使用します。すべてのピザの効率が同じであるため、ピザの種類ごとにスライスを最大化するだけで済みます。つまり、常に 10 スライスのピザを優先する必要があります。 答えは次のようになります。 

できるだけ多くの 10 スライスのピザを取得し、小さな定数検索を使用して残りを最適に処理します。 

これにより、テスト ソリューションごとに O(1) が得られます。

 ## アルゴリズムのチュートリアル

 私たちは、問題を、できるだけ多くの大きなピザを使用した後の一定数の残りのケースのみを処理することに帰着させます。 

1. 大きなピザだけを使用した場合、10 枚切りのピザが何枚必要になるかを計算します。 これは`n // 10`。 これは、アイテム サイズごとのスライス パッキングを最大化するため、自然なベースラインです。 
2. 残量を確認する`r = n % 10`。 もし`r == 0`、解決策は正確なので完了です`k * 25`。 
3. 残りがある場合は、特大のピザを 1 枚使用するか、溶液の一部を小さいピザに置き換えるかを決定する必要があります。 すべての効率は同じであるため、大きなピザを置き換えても離散化のみに影響し、最適性には影響しません。 
4. カバーするために必要な最小限の追加コストを計算します。`r`6、8、10 スライスの組み合わせを使用します。 以来`r < 10`、これは定数検索の問題です。 
5. 10 スライスのピザ全体のコストと最良の残りのソリューションを組み合わせます。 

重要な推論ステップは、すべてのピザのスライスあたりのコストが等しいため、グローバル構造がサイズ 10 に一定の補正を加えた独立したブロックにきれいに分解されるということです。 

### なぜ効果があるのか

 すべての種類のピザのコストとスライスの比率は同一であるため、合計スライス数を維持して再配置すると、合計時間を節約できます。 これは、問題が少なくとも達成可能な最小の合計スライス数を見つけることに集約されることを意味します。`n`。 その合計の表現を固定すると、時間は一意に決定されます。 スライス サイズは小さい定数であるため、残りの調整は制限されており、独立しています。`n`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_one(n):
    # all pizzas have 2.5 minutes per slice equivalently
    # so we minimize slices, then multiply by 2.5 * 10 = 25 per 10-slice pizza logic
    
    k = n // 10
    r = n % 10
    
    # base cost from full 10-slice pizzas
    ans = k * 25
    
    if r == 0:
        return ans
    
    # handle remainder by brute checking small combinations
    best = float('inf')
    
    # try taking one extra 10-slice pizza
    for extra10 in [0, 1]:
        for a in range(3):  # 6-slice
            for b in range(3):  # 8-slice
                for c in range(3):  # 10-slice
                    slices = a * 6 + b * 8 + c * 10 + extra10 * 10
                    if slices >= r and slices <= r + 10:
                        time = a * 15 + b * 20 + c * 25 + extra10 * 25
                        best = min(best, time)
    
    return ans + best

t = int(input())
for _ in range(t):
    n = int(input())
    print(solve_one(n))
```この実装では、大規模な構造 (10 スライスのブロック) を残りのローカル補正から明示的に分離します。 ネストされたループは一定の範囲で動作し、依存しないため安全です。`n`。 小さなオーバーシュート ウィンドウのみを考慮すればよいという制約により、大きな状態空間を探索することなく正確性が保証されます。 

微妙な点は、`extra10`支店。 これがないと、9 スライスや 8 スライスなどの一部の残りは、残りのみに厳密に適合させるよりも、10 スライス ブロックの一部を変換することで満たす方がコストが安くなる可能性があります。

 ## 特殊なケース

 主なエッジケースは次のような場合です`n`は 10 の倍数をわずかに上回る値です。`n = 11`, 単純な貪欲な人は、10 枚のスライスのピザを取り、次に 1 枚のピザを別のピザで満たそうとし、少なくとも 6 枚の追加のピザを強制するかもしれません。 代わりに、最適解は、残りの構造に応じて 10 スライスの選択を完全に置き換えた方が良い可能性があることを認識します。 

もう一つのエッジケースは、`n = 1`。 割り切れることを前提としたソリューションや、10 単位でスケールしようとするソリューションはすべて、ここで中断されます。 部分的に詰めることは不可能であるため、正しい動作は、すぐに 6 スライスのピザを 1 枚選ぶことです。 

最後に、次のような大きな値$10^{16}$ソリューションが線形アプローチまたは DP アプローチを回避しているかどうかをテストします。 このアルゴリズムは定数演算のみを実行するため、オーバーフローやパフォーマンスの問題を発生させることなくこれらの入力を処理します。
