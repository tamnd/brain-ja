 ## 解決策
 ## 問題の理解

 1 から始めて隙間なく上に向かって無限に番号が振られたアイテムを 2 人で順番に食べます。 重要なルールは、各人が決まった量を食べるのではなく、順番に、現在の「容量」が許す限り多くのアイテムを食べるということです。 この容量はどちらも 1 から始まります。 

自分の番が終わった後、もう一人は食べたアイテムの数を観察し、その分だけ自分の能力を増やします。 その後、役割が交互に行われます。最初に月火、次に暦、次に再び月火というようになります。 

したがって、食べたアイテムのシーケンスは、正の整数を連続したブロックに分割したものであり、そのサイズは 2 人のフィードバック ループに基づいて時間の経過とともに変化します。 各ブロックは完全に 1 人に割り当てられます。 

このタスクは、10^18 までの範囲全体でプロセスを完全にシミュレートすることではありません。 代わりに、複数の独立したクエリが求められます。つまり、無限シーケンス内の特定の位置 x について、そのアイテムが月火ターン中に食べられるか暦ターン中に食べられるかを決定します。 

この制約により、直接シミュレーションが不可能になります。 シーケンスはブロック単位で成長し、そのサイズは非常に急速に増加する可能性があり、x は 10^18 に達する可能性があるため、線形構築は即座に除外されます。 最大クエリを超えるまでブロックを構築する貪欲なシミュレーションでも、最悪の場合は 10^9 以上の繰り返しが必要となり、これは 2 秒をはるかに超えます。 

微妙なエッジ ケースは、ブロック サイズがどのように急速に増加するか、およびブロック サイズがどのように交互するかによって発生します。 単純なアプローチでは、最大のクエリに到達するまでブロックを事前計算しようとする可能性がありますが、クエリが大きい場合や間隔が広い場合には機能しません。 もう 1 つの障害モードは、クエリごとに独立してシミュレーションすることです。これは、各シミュレーションが最初から再開され、同じプレフィックスが繰り返し再計算されるためです。 

## アプローチ

 直接シミュレーションは簡単に説明できます。シーケンス内の現在の位置を維持し、両方のプレーヤーの現在の能力を維持し、交互にターンします。 各ターンで、そのサイズのブロックを生成し、それを現在のプレーヤーに割り当て、他のプレーヤーの容量を更新し、クエリされた最大のインデックスを渡すまで続けます。 

これは正しいですが、非常に遅いです。 必要なブロックの数は容量の進化とともに増加し、容量自体も累積的に増加します。 最悪の場合、x に到達する前に sqrt(x) 個以上のブロックが生成される可能性があり、各クエリではこの推論を繰り返すか、大きなプレフィックス間隔をスキャンする必要があります。 

重要な観察は、プロセスが完全に決定的であり、一連のばらばらの連続セグメントを生成するということです。 各セグメントには固定の所有者があり、長さは既知です。 個々のアイテムについて考えるのではなく、シーケンスを月火または暦のいずれかでタグ付けされた [L, R] 形式の間隔に圧縮します。 

これがわかると、問題は古典的なプレフィックス間隔分解問題になります。必要な最大範囲に達するまでセグメントを生成し、それらを格納し、どのセグメントに x が含まれるかをバイナリ検索して各クエリに答えます。 

残る唯一の課題は、セグメント長を効率的に計算することです。 繰り返しは単純です。現在のプレーヤーのブロック サイズが現在の容量になります。 食べると、相手の能力がそのブロックサイズ分増加します。 これにより、単一の進化する値のペアが生成され、各ステップは O(1) になります。 最大クエリ値を渡すまでセグメントを生成するだけで済みます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとのブルート フォース シミュレーション | O(n · k) | お(1) | 遅すぎる |
 | セグメントの事前計算 + 二分探索 | O(n + s log s) | O(s) | 承認済み |

 ここで、 s は、最大クエリ位置までの生成されたセグメントの数です。 

## アルゴリズムのチュートリアル

 シーケンス全体を連続したラベル付きセグメントとして構築します。

1. 最大クエリ値を決定します。 これは私たちが検査する必要がある最も遠い位置です。 累積長がこの値を超えるまでのみシーケンスを構築します。 
2. 月火と暦の現在の容量を 1 と 1 に初期化します。位置カウンターを 1 に初期化します。月火から順に誰のターンであるかを示すフラグを設定します。 
3. 現在位置が最大クエリを超えていない間に、次の操作を行います。 

現在のプレーヤーの容量を次のセグメントのサイズとして取得します。 これはブロック [pos, pos + size − 1] を定義します。 

これが機能する理由は、各ターンがちょうど同じ数の連続したアイテムを消費し、プロセスが重複やスキップがなく厳密に連続しているためです。 
4. このセグメントをその所有者、開始インデックス、終了インデックスとともに記録します。 次に、位置ポインタを次の未使用の整数に進めます。 
5. 消費されたばかりのセグメントのサイズを追加して、対戦相手の容量を更新します。 これはフィードバック ルールを捉えています。つまり、x 個のアイテムが食べられると、罪悪感が x 増加します。 
6. ターンを他のプレイヤーに切り替えて繰り返します。 
7. すべてのセグメントを構築したら、どのセグメントに x が含まれているかを特定して、各クエリに個別に答えます。 セグメントは位置によってソートされるため、セグメントの開始点で二分検索が可能です。 

### なぜ効果があるのか

 このプロセスでは、正の整数を連続する素の区間に分割することが定義されます。 各間隔は 1 回のターンによって一意に決定され、全​​体の進化は決定論的に更新される累積容量のみに依存します。 必要な最大範囲までのすべての間隔が生成されると、すべてのクエリは、特定のインデックスがどの間隔に含まれているかを識別することになります。 後のセグメントが前の位置に影響を与えることはできないため、前処理は十分かつ正確です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    xs = list(map(int, input().split()))
    max_x = max(xs)

    seg_l = []
    seg_r = []
    seg_owner = []

    tk = 1  # Tsukihi capacity
    kk = 1  # Koyomi capacity

    pos = 1
    turn = 0  # 0 Tsukihi, 1 Koyomi

    while pos <= max_x:
        if turn == 0:
            sz = tk
        else:
            sz = kk

        l = pos
        r = pos + sz - 1

        seg_l.append(l)
        seg_r.append(r)
        seg_owner.append('T' if turn == 0 else 'K')

        if turn == 0:
            kk += sz
        else:
            tk += sz

        pos = r + 1
        turn ^= 1

    import bisect

    def get_owner(x):
        i = bisect.bisect_left(seg_r, x)
        return seg_owner[i]

    out = []
    for x in xs:
        out.append(get_owner(x))

    print(''.join(out))

if __name__ == "__main__":
    solve()
```コードは、必要な最大のインデックスに達するまでセグメント境界を構築します。 各セグメントにはその範囲と所有者が格納されます。 キャパシティはプロセスで説明されているとおりに正確に更新され、各ターン後に非アクティブ プレーヤーのみが変更されます。 

セグメント エンドポイントに対するバイナリ検索により、各クエリが対数時間で解決されることが保証されます。 重要な詳細は、セグメントが連続していて重複していないため、正しいエンドポイントで検索することです。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(s + n log s) | s セグメントは 1 回生成され、各クエリは二分検索を使用します。 
| スペース | O(s + n) | セグメントストレージと出力配列 |

 容量は累積的に増加し、ターンごとに相手の容量が増加するため、セグメントの数は少なくなります。 これにより、x が 10^18 までの場合でも、合計シミュレーションが制限内に十分に収まります。 

このソリューションは、管理可能であり、クエリが対数時間で処理されるため、時間とメモリの制限の両方に簡単に適合します。

 ## 特殊なケース

 重大なエッジケースは、クエリがまさにセグメント境界にある場合です。 たとえば、セグメントが位置 6 で終了する場合、6 をクエリすると、次のセグメントではなく、そのセグメントの所有者が返される必要があります。 右端点に対する二分探索では、端が少なくとも x である最初のセグメントを選択することにより、等価性が正しく処理されることが保証されます。 

もう 1 つのケースは、10^18 などの非常に大規模なクエリです。 アルゴリズムは、その値まで直接シミュレートしようとすることはありません。 構築されたセグメントが最大クエリを超えると停止します。 これにより、個々のクエリが遠く離れている場合でも実現可能性が保証されます。 

最後に、両方の容量が 1 である最初のステップでは、最初のセグメントが常にツキヒによって所有される単一の要素であることが保証されます。 最初のセグメントを記録する前に誤って容量を増やす実装を行うと、シーケンス全体がシフトされ、最初のクエリから誤った応答が生成されます。
