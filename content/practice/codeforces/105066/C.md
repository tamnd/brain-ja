 ## 解決策
 ## 問題の理解

 私たちにはノックアウトトーナメントが与えられています$N$選手、どこ$N$は 2 の累乗です。 試合は固定です。現在のリスト内の隣接するプレイヤーがプレイし、勝者が順番に次のラウンドに進みます。 これは 1 人のチャンピオンが残るまで続きます。 

各参加者は 3 つのタイプのいずれかです。 本物のプレーヤーには、インデックスによって与えられる固定の強さがあり、2 人の本物のプレーヤーが対戦すると、常に小さいインデックスが勝ちます。 Alternet は、本物のプレイヤーにはいつも負けますが、友達にはすべて勝つ特別なプレイヤーです。 友達は柔軟に行動します。各友達は、実際の参加者を 1 人だけ倒すように訓練することができ、そうでない場合は、実際のプレイヤーに対して通常の弱い参加者として振る舞うことができます。 友達がお互いに、またはオルターネットに会うとき、彼らの結果はオルターネットを助けるために任意に選択できます。 

問題は、Alternet がトーナメント全体の最終勝者となるように、フレンド マッチの結果を割り当て、各フレンドの 1 つの「ターゲットの本当の対戦相手」を選択できるかどうかです。 

トーナメントの構造は重要です。なぜなら、試合は各ラウンドで固定の組み合わせであるためです。そのため、Alternet の存続は、強さの割り当てだけでなく、ブラケット ツリー内で敗退が発生するかどうかにも依存します。 

という点では制約は小さい$N \le 1024$そして$T \le 1000$、だから、$O(N^2)$あるいは$O(N^3)$試験溶液ごとに許容されます。 ただし、本当の難しさは計算ではなく、バイナリ トーナメント ツリーを通じて敗者がどのように伝播するかをモデル化することです。 

単純な解釈は、友人が強い本物のプレイヤーを倒すように割り当てられているにもかかわらず、別のブラケットセグメントで早期に敗退したためにまだ到達できないというエッジケースでは失敗することがよくあります。 

いくつかの代表的な問題のあるシナリオ:

 たとえば、Alternet が最初のラウンドで実際のプレイヤーと直接ペアになった場合、`AR`、Alternet は実際の試合に勝つことができないため、答えは常に「いいえ」です。 

すべての現実のプレイヤーがブラケットの片側に集中し、友人が分散している場合、単純なアプローチでは、各友人が独立して 1 人の現実のプレイヤーを無力化すると仮定する可能性がありますが、それらの友人が目標を達成するために実際に生き残るかどうかを検討できません。 

友人に割り当てられた現実の対戦相手が、別の現実のプレイヤーによって早期に敗退した場合 (現実対現実では常に、より低いインデックスが勝つため)、その友人は「無駄」になり、もう助けることができなくなります。 これにより、ブラケット構造を無視する貪欲な割り当てが無効になります。 

重要な問題は、実現可能性は、友達がトーナメント ツリーを通じてルーティングされ、必要な本物のプレーヤーを排除される前に阻止できるかどうかによって決まることです。 

## アプローチ

 ブルートフォースのアイデアは、友人対友人の試合の結果を割り当てるすべての可能な方法と、実際のターゲットに対する各友人の可能なすべての割り当てをシミュレートすることです。 各シミュレーションにはトーナメント全体を実行する必要があり、すでに費用がかかります$O(N \log N)$。 各友達が最大 1 つを選択できるため、友達をターゲットに割り当てる方法の数は飛躍的に増加します。$O(N)$本物の選手たち。 これはすぐに$O(N^F)$、中程度の人でも不可能です$N$。 

構造的な洞察は、トーナメントをバイナリ マージ ツリーとして見ることで得られます。 ブラケットの各セグメントで 1 人の勝者が生成され、その勝者が誰になるかは、Alternet が彼の進路に実際のプレイヤーが生き残らないようにできるかどうかによって決まります。 

個々の試合を追跡する代わりに、利用可能な友人を使用してブラケットのセグメントから実際のプレイヤーを「クリア」できるかどうかだけを知る必要があります。 各フレンドは、それが配置されているサブツリーのどこかから実際のプレイヤーを 1 人だけ削除できる使い捨てブロッカーとして機能します。フレンドは順序を並べ替えることができ、フレンド間の試合結果は完全に制御可能であるため、セグメント全体に分散された柔軟なリソースとしてフレンドを扱うことができます。 

セグメントはボトムアップで処理されます。 セグメントごとに、そのセグメントに友達を最適に割り当てた場合に実際のプレイヤーが何人生き残るかを計算します。 いかなる時点でも、セグメントに参加可能な友達と子供たちからのサポートよりも多くの実際のプレイヤーがセグメントに含まれている場合、そのセグメントをクリアすることは不可能です。 

重要な観察は、トーナメントの構造がインターバルの結合のように動作することです。各セグメントでは、おそらくオルタナティブにつながる 1 つのパスを除いて、すべての本物のプレイヤーを排除するのに十分な「フレンド パワー」が必要です。 オルターネットのパスに沿ったすべてのセグメントを安全にすることができれば、オルターネットは決勝に進出し、勝利することができます。 

これにより、問題は、オルタネットの位置と一致するすべてのサブツリーで利用可能なフレンド リソースによって実際のプレイヤーの数が支配されるかどうかを確認することに帰着します。

 ## アルゴリズムのチュートリアル

 トーナメントを配列インデックス上の完全なバイナリ ツリーとしてモデル化します。葉はプレーヤー、内部ノードは試合を表します。 

### ステップ

 1. 配列上に暗黙的なトーナメント ツリーを構築します。 各ノードは、最終的に 1 人の勝者を生み出すプレイヤーのセグメントに対応します。 

重要な考え方は、一致を明示的にシミュレートしないということです。 カウントを上向きにのみ伝播します。 
2. すべてのリーフに、実際のプレーヤーの数と利用可能な友達の数という 1 組の値を割り当てます。 リアルノードは 1 人のリアルプレイヤーに貢献し、フレンドは 1 人のフレンドリソースに貢献し、オルタナネットはどちらにも貢献せず、ターゲット位置をマークします。 
3. 各内部ノードについて、実際の数と友人の数を合計することによって、その 2 つの子を結合します。 これにより、対話前のそのセグメント内のリソースの生のプールが得られます。 
4. 各ノードで、利用可能なフレンドを使用してリアル プレイヤーを減らします。各フレンドは、そのセグメント内のリアル プレイヤーを 1 人だけ排除できます。 

したがって、次のように計算します。$$\text{remaining real} = \max(0, \text{real} - \text{friends})$$5. 残りの実際の数と合計友達数を上に渡します。 残りの実際の数は、このセグメントで無力化できない避けられない脅威を表します。 
6. ツリーを構築したら、Alternet のリーフを見つけます。 次に、このリーフからルートまでのパス上のすべてのノードをチェックし、このパス上のすべてのセグメントで残りの実数がゼロであることを確認します。 いずれかのセグメントに実数 > 0 が残っている場合、Alternet は最上位に到達する前に除去されます。 
7. Alternet のパス上のすべてのセグメントがクリーンな場合は「Yes」を出力し、そうでない場合は「No」を出力します。 

### なぜ効果があるのか

 重要な不変条件は、友人に実際のプレイヤーに対する結果を任意に割り当てることができ、サブツリー内の目標を達成するように配置できるため、各サブツリーを独立して削減できることです。 リアル対リアルの結果は決定的であるため (インデックスが小さい方が勝ち)、システムで制御可能な唯一の機能は、フレンドを使用してリアル プレーヤーを削除する機能です。 したがって、各セグメントは予算の問題のように動作します。友人が予算であり、実際のプレイヤーがコストであり、実現可能性はオルターネットの生存経路に沿ったすべての集約レベルで予算が十分であるかどうかによって決まります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    T = int(input())
    for _ in range(T):
        n = int(input())
        s = input().strip()

        # find Alternet position
        a = s.index('A')

        # we will simulate upward segment checks
        # each level doubles segment size
        ok = True

        l = r = a

        # move up in implicit segment tree
        while True:
            # expand segment to the nearest power-of-two boundary at current level
            # simulate by growing to aligned segment of size 2^k containing a
            if l == 0 and r == n - 1:
                break

            # find current segment size
            size = r - l + 1
            nl = l - (l % size)
            nr = nl + 2 * size - 1

            nl = max(0, nl)
            nr = min(n - 1, nr)

            real = 0
            friend = 0

            for i in range(nl, nr + 1):
                if s[i] == 'R':
                    real += 1
                elif s[i] == 'F':
                    friend += 1

            if real > friend:
                ok = False
                break

            l, r = nl, nr

        print("Yes" if ok else "No")

if __name__ == "__main__":
    solve()
```The code first identifies Alternet’s position in the lineup. The main idea is to repeatedly expand the segment containing Alternet to match the tournament’s hierarchical merge structure. 各拡張ステップで、拡張されたセグメント内に何人のリアル プレーヤーとフレンドが存在するかを再計算し、フレンドがその領域内のすべてのリアル プレーヤーを完全に無力化できるかどうかを確認します。 

条件`real > friend`は失敗条件です。これは、そのサブツリー内に利用可能な除去よりも多くの避けられない脅威があることを意味します。 これが Alternet の上りパスで発生すると、Alternet はルートまで存続できなくなります。 

拡張ロジックは、セグメントを外側に対称的に成長させることによって暗黙的なバイナリ ツリー レベルを近似します。これは、各ラウンドで隣接するブロックがどのようにマージされるかを反映しています。 

微妙な点は、Alternet を含むセグメントのみを考慮するため、ツリーの無関係な部分を必要以上に処理することは決してないことです。

 ## 特殊なケース

 重大なエッジ ケースの 1 つは、当初は安全に見えても拡張後に安全でなくなるセグメントに Alternet が配置される場合です。 たとえば、友人が Alternet のローカル セグメントに存在するが、すべての友人が真のトーナメント マージ境界の外側にある場合、初期のチェックが誤って通過する可能性があります。 拡張ベースのアプローチでは、正しく位置合わせされたトーナメント セグメントを常に再計算することでこれを回避します。 

もう 1 つのエッジ ケースは、すべての友人がブラケットの一方の側にいて、すべての本物のプレイヤーがもう一方の側にある場合です。 素朴なローカルカウント手法では、合計数のバランスが取れていると言えるかもしれませんが、括弧が早期に混合することはないため、Alternet は必要なフレンドのリソースから孤立する可能性があります。 セグメントの拡張により、構造的に到達可能な友人のみが各レベルでカウントされるようになり、この誤った楽観主義が防止されます。
