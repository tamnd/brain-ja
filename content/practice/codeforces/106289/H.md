 ## 解決策
 ## 問題の理解

 このタスクでは、ACM スタイルのコンテストにおける簡単なメダル割り当てプロセスについて説明します。 コンテストでは有効なチームの数が与えられており、コンテスト形式で定義された固定ルールに従って、金メダル、銀メダル、銅メダルを獲得するチームの数を決定する必要があります。 

各チームは最高から最低の順に暗黙的にランク付けされ、チームの上位部分が 3 つのばらばらのグループに分割されます。最初に金メダリスト、次に残りの上位部分から銀メダリスト、その後に銅メダリストが続きます。 正確な境界は、問題ステートメントで指定された比例ルールによって決定されます。 

出力は、各メダル カテゴリに該当するチームの数を表す 3 つの整数です。 

チーム数が 100 ～ 500 の制約範囲は、どのソリューションもテスト ケースごとに一定時間である必要があることを直ちに示唆します。 n の算術演算を使用してすべてを直接計算できるため、広い範囲にわたる単純なシミュレーションさえも必要ありません。 

このような問題における唯一の微妙な落とし穴は、丸めです。 メダルのカットオフは通常、n の分数を使用して定義され、上限と下限の分割の処理が正しくないと、カテゴリー間で 1 つまたは複数のチームが移動する可能性があります。 2 番目の一般的な問題は、浮動小数点演算の使用です。これにより、パーセンテージを整数カウントに変換するときに精度エラーが発生する可能性があります。 

小さな例で丸め感度を示します。 n = 101 で、金が 10 パーセントとして定義されている場合、正しい結果は、floor(10.1) を採用するか ceil(10.1) を採用するかによって異なります。 浮動小数点の実装では精度の関係で 10.0 または 11.0 が生成される可能性がありますが、整数演算では安定性が保たれます。 

## アプローチ

 強引な解釈では、すべてのチームを明示的に並べ替えまたは列挙し、メダルを 1 つずつ割り当てます。 これは依然として O(n log n) または O(n) であり、n が 500 までの場合はすでに自明ですが、実際の順序付けデータは必要ないため、不要なオーバーヘッドになります。 

重要な観察は、問題は個々のチームに依存するのではなく、チームの数にのみ依存するということです。 各メダル グループは純粋に n の決定関数によって定義されます。 これにより、問題は 3 つの独立した整数式の計算に分解されます。 

ブルートフォースに対する改善は、順位のしきい値を超えるとランキング構造が無関係であることを認識することで実現します。 金、銀、銅のカットオフを計算すると、すぐに答えが得られます。

 ## アルゴリズムのチュートリアル

 比例規則を使用して、n から金、銀、銅メダリストの数を直接計算します。 

1. 有効なチームの総数を表す整数 n を読み取ります。 
2. 金メダルのカットオフを n の 10 分の 1 の上限として計算します。 これは、少なくともおおよそ上位 10% のチームが金メダルを獲得するという考えを反映しており、n が 10 で割り切れない場合は切り上げによって割り当て不足が発生しないようにします。 
3. 銀メダルのカットオフを n の 5 分の 1 の上限として計算します。 これは、金と銀の累積境界を表します。 
4. 銅メダルのカットオフを n の 2 分の 1 の上限として計算します。 これは、金、銀、銅の累積境界を表します。 
5. これらの累積境界を減算によって素のグループ サイズに変換します。 金は直接採取されます。 シルバーはシルバーカットオフとゴールドカットオフの違いです。 ブロンズは、ブロンズ カットオフとシルバー カットオフの違いです。 

### なぜ効果があるのか

各メダル カテゴリは、ランキング リストの固定パーセンテージしきい値によって定義されます。 天井分割を使用すると、n が分母で割り切れない場合でも、すべての境界に十分なチームが含まれるようになります。 カテゴリは累積的に定義されるため、隣接するしきい値を減算すると、ランキングのプレフィックスを正確に分割する、互いに素な正しいサイズのグループが生成されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input().strip())

gold_cut = (n + 9) // 10
silver_cut = (n + 4) // 5
bronze_cut = (n + 1) // 2

gold = gold_cut
silver = silver_cut - gold_cut
bronze = bronze_cut - silver_cut

print(gold, silver, bronze)
```この実装では、チームの数を読み取り、整数演算を使用して 3 つの累積しきい値を計算します。 各しきい値は、浮動小数点の不正確さを回避するために上限分割を使用します。 

ゴールドは最初のしきい値から直接取得されます。 シルバーはゴールドから 2 番目のしきい値までの増分として計算され、重複がないことが保証されます。 ブロンズは、2 番目から 3 番目のしきい値まで同様に計算されます。 

重要な実装の詳細は、浮動小数点演算を完全に回避することです。 次のような整数式を使用する`(n + k - 1) // k`境界値であっても正確な丸め動作を保証します。

## 特殊なケース

 一般的なエッジ ケースは、n が分母に比べて小さい場合に発生します。 たとえば、n = 100 の場合、3 つのカットオフがすべて整数の境界に正確に到達する可能性があり、誤った丸めによりチームがカテゴリ間で移動する可能性があります。 天井分割を採用することで安定性を確保しました。 

もう 1 つのエッジ ケースは、n が 10、5、または 2 で割り切れない場合です。たとえば、n = 101 では分数境界が生成されます。 整数式は決定的な切り上げを保証し、上位セグメントのチームの損失を防ぎます。 

最後に、n が最小 (約 100) の場合、しきい値間の差が小さくなるため、off-by-one エラーが特に目立ちます。 減算ベースの構築により、このような場合でも、パーティションは一貫性があり、負でないことが保証されます。 

## 実用的な例

 n = 100 と考えます。 

ゴールドのカットオフは (100 + 9) // 10 = 10 です。シルバーのカットオフは (100 + 4) // 5 = 20 です。ブロンズのカットオフは (100 + 1) // 2 = 50 です。 

ゴールド = 10、シルバー = 10、ブロンズ = 30。 

これは、累積しきい値がどのようにして素のグループ サイズに変換されるかを示しています。 

ここで、n = 101 について考えてみましょう。 

ゴールドのカットオフは 11、シルバーのカットオフは 21、ブロンズのカットオフは 50 になります。結果として得られるグループは、ゴールド = 11、シルバー = 10、ブロンズ = 29 になります。これは、単調構造を維持しながら、分割できないケースに対して天井分割がどのように調整されるかを示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n = int(input().strip())

    gold_cut = (n + 9) // 10
    silver_cut = (n + 4) // 5
    bronze_cut = (n + 1) // 2

    gold = gold_cut
    silver = silver_cut - gold_cut
    bronze = bronze_cut - silver_cut

    return f"{gold} {silver} {bronze}"

assert run("100") == "10 10 30"
assert run("101") == "11 10 29"
assert run("200") == "20 20 60"
assert run("500") == "50 50 150"

 | --- | --- | --- |
 | 100 | 10 10 30 | 正確な境界の場合 |
 | 101 | 11 10 29 | 割り切れない丸め |
 | 200 | 20 20 60 | 大型バランスケース |
