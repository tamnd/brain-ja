 ## 解決策
 ## 問題の理解

 タスクは非常に小さく直接的です。複数の人から一連の回答が与えられ、それぞれの回答は「これは簡単です」または「これは難しいです」のいずれかです。 目標は、その問題が全体的にまだ簡単であると考えられるかどうかを判断することです。 

ルールは簡単です。 一人でもその問題が難しいと思う人がいると、最終的な判定は「難しい」になります。 それが簡単であるということに誰もが同意する場合にのみ、私たちはそれを簡単なものとして受け入れます。 

したがって、入力は単なる二項対立の意見のリストであり、一方の値は「簡単」を表し、もう一方の値は「難しい」を表します。 出力は、「厳しい」意見が存在するかどうかを要約した 1 つの単語です。 

制約は小さく、意見は最大 100 件です。 これにより、パフォーマンスに関する懸念はすぐに排除されます。 二次スキャンやネストされたスキャンでも問題ありませんが、構造上、必要なのは 1 回のパスのみであることがわかります。 

主なエッジケースは、主に最小限の入力と均一な入力に関するものです。 一人しかいないのに簡単だと言ったら、答えも簡単なはずです。 同じ一人の人が厳しいことを言うと、答えはすぐにひっくり返ります。 もう 1 つの微妙なケースは、厳しい意見が最後または最初に表示される場合です。これは正しさに影響を与えることはありませんが、誰かが不注意に実装すると誤った早期終了ロジックが露呈する可能性があります。 

## アプローチ

 ブルートフォース解釈では、入力を値のコレクションとして扱い、サブセットを繰り返しチェックするか、意思決定プロセスをシミュレートします。 たとえば、すべての接頭辞をチェックし、その接頭辞に厳しい意見が「含まれていない」かどうかを再計算することを想像するかもしれません。 これは正しいですが、各チェックで同じ要素が再度スキャンされるため、不必要に繰り返します。 最悪の場合、それは人の数で二次関数になります。$n^2$、これはまだ些細なことですが、$n \le 100$しかし、すでに無駄な作業が示されています。 

重要な観察は、決定は存在のみに依存するということです。 どれだけの人がそれを難し​​いと思っているか、また彼らがどこに現れるかは気にしません。 リストに少なくとも 1 つの「1」が存在するかどうかだけを知る必要があります。 これにより、問題全体がブール フラグを使用した 1 回のスキャンに軽減されます。 

これがわかると、解決策はストリーミング チェックになります。厳しい意見が現れるとすぐに、答えが決まります。 正確さを期すためにさらに要素を処理する必要はありません。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (プレフィックスの再チェック) | O(n²) | お(1) | 受け入れられるが不要 |
 | シングルパススキャン | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 意見の数を読む。 これにより、スキャンする値の数がわかりますが、ループの範囲を超えるロジックには影響しません。 
2. フラグを初期化する`hard_found`偽りとして。 この変数は、問題を難しいとマークする意見にすでに遭遇したかどうかを表します。 
3. リスト内の各応答を繰り返し処理します。 各値について、それが「強硬」投票を表す 1 に等しいかどうかを確認します。 
4. ハード投票が見つかった場合は、`hard_found`本当のこと。 この時点で、実装の簡素化を追求し続けたとしても、最終的な答えはすでに論理的に決定されています。 
5. すべての値を処理した後、次の場合は「HARD」を出力します。`hard_found`true の場合、「EASY」を出力します。 

早期検出の背後にある理由は、問題は実質的にすべての入力に対する OR 削減であるということです。 1 つの真の値が確認されると、グローバル OR はすでに true になります。 

### なぜ効果があるのか

 決定ルールは、すべての入力値に対して論理 OR を計算することと同等で、1 は true に寄与し、0 は false に寄与します。 最終的な答えは、この OR が true と評価されるかどうかによってのみ決まります。 OR は冪等で順序に依存しないため、順番にスキャンして真の値が現れるかどうかを追跡することで正確さが保たれます。 再配置や集計は必要なく、以前に確認された厳しい意見を後の値で無効にすることはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
arr = list(map(int, input().split()))

hard_found = False

for x in arr:
    if x == 1:
        hard_found = True

print("HARD" if hard_found else "EASY")
```このソリューションは、すべての値を一度に読み取り、1 回スキャンします。 私たちが維持する唯一の状態はブール値フラグです。 早期終了は必要ありませんが、正確さを変更せずに追加できます。 

よくある実装の間違いは、カウントやセグメントのロジックを賢く使いすぎようとすることです。 これにより、不必要な複雑さが生じます。 もう 1 つの問題は、入力が 1 行のスペースで区切られた整数であることを忘れていることです。これにより、誤って処理されると部分的な読み取りが発生する可能性があります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各意見はリニア スキャンで 1 回だけチェックされます。 
| スペース | お(1) | 単一のブール値フラグのみが保存されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from sys import stdout
    input = sys.stdin.readline

    n = int(input())
    arr = list(map(int, input().split()))

    hard_found = False
    for x in arr:
        if x == 1:
            hard_found = True

    return "HARD" if hard_found else "EASY"

# provided samples
assert run("3\n0 0 1\n") == "HARD"
assert run("1\n0\n") == "EASY"

# custom cases
assert run("5\n0 0 0 0 0\n") == "EASY", "all easy"
assert run("4\n1 1 1 1\n") == "HARD", "all hard"
assert run("6\n0 1 0 0 0 0\n") == "HARD", "single early hard"
assert run("2\n0 1\n") == "HARD", "minimal mix"
```| テスト入力 | 期待される出力 | 検証内容 |

 | すべてゼロ | 簡単 | 厳しい投票はありません |
 | すべてのもの | ハード | ユニフォームハードケース |
 | 初期のハード | ハード | 早期終了の正しさ |

 ## 特殊なケース

 エッジケースの 1 つは、参加者が 1 人だけの場合です。 ループが 1 回だけ実行され、その 1 つの意見が直接反映されるため、アルゴリズムは引き続き機能します。 

もう一つは、最後の最後に厳しい意見が出てくるケースです。 早期終了を誤って想定したり、入力を読み間違えたりする単純な実装では、フラグを見逃す可能性がありますが、リニア スキャンは、フラグが表示されたときにフラグを正しく更新します。 

最後のケースは、すべての値が easy である場合です。 ここで、フラグは全体を通して false のままであり、出力は正しく「EASY」のままであり、証拠の欠如が曖昧さではなく厳密さの欠如として扱われることを確認します。
