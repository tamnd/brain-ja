 ## 解決策
 ## 問題の理解

 文字列が与えられ、それをいくつかの連続する部分に分割することができます。 すべてのピースには少なくとも長さが必要です`l`、少なくとも生産する必要があります。`k`合計個数。 

有効なカットを選択すると、結果として得られるすべての部分が辞書順に並べ替えられます。 ソートされたリストのうち、位置に表示される要素のみに焦点を当てます。`k`。 タスクは、次のようにカット位置を選択することです。`k`- 番目に小さい部分は、辞書編集的に可能な限り大きいものです。 

重要な相互作用は、すべてのピースを直接最適化するのではなく、最終的にランクに達するピースのみを最適化することです。`k`並べ替え後。 これにより、問題は非対称になります。ほとんどのピースは、ターゲット ピースのランクに影響を与える場合にのみ重要になります。 

制約により、テスト ケースごとに線形または線形に近い動作が強制されます。 すべてのテスト ケースの合計の長さは最大でも 100 万であるため、すべてのカットを試行したり、入れ子になったループ内で部分文字列の比較を繰り返し実行したりするソリューションは存続できません。 たとえ$O(n \log n)$テスト ケースごとのアプローチは、実際にほぼ線形であり、大量の部分文字列のコピーを回避する場合にのみ受け入れられます。 

微妙な失敗例は、貪欲なカットがターゲット ピースをローカルで最大化しようとしたときに、他のピースのマルチセットを誤って変更してしまい、ターゲットのランクがシフトした場合に発生します。 たとえば、あまりにも早い段階で積極的にカットすると、辞書編集的に小さな断片が多数作成され、目的のセグメントがソート順で人為的にさらに下に押しやられてしまう可能性があります。 

もう 1 つの明白ではない問題は、部分文字列比較のコストです。 ソートまたはカット位置のバイナリ検索中に部分文字列を繰り返し比較する単純なアプローチは、次のような繰り返しの接頭辞に対する二次的な動作に低下します。`"aaaaaa...."`。 

## アプローチ

 強引な見方では、問題を、`n - 1`ギャップ。各セグメントには少なくとも長さがあるという制約が適用されます。`l`セグメントの数は少なくとも`k`。 有効なパーティションごとに、すべての部分を生成し、並べ替えて、`k`- 番目の要素。 これは出力の定義に直接従うため、概念的には正しいです。 

ただし、パーティションの数は指数関数的に増加します。`n / l`なぜなら、最初の実行可能なカットの後は、すべてのセグメント境界が二分法で決定されるからです。 中程度の場合でも`n`、これはすぐに爆発します。 さらに、各評価では次のように分類する必要があります。`n / l`文字列を取得して比較すること自体がコストがかかります。 

重要な構造上の観察は、実際には完全にソートされたリストが必要ないということです。 私たちが気にするのは、候補作品が`k`ソート後の -th 番目。 これにより、問題が決定プロセスに変換されます。候補となる部分文字列を修正し、正確に次のような有効なパーティションを構築できるかどうかを尋ねます。`k - 1`ピースは厳密にそれより小さいです。 

このように表現すると、問題は候補部分文字列において単調になります。 部分文字列が答えとして実現可能な場合は、辞書編集的に小さい任意の部分文字列も可能であり、これにより、答えに対する二分検索が可能になります。 実現可能性を評価するために、辞書編集的に候補よりも小さいセグメントがいくつあるかを追跡しながら、貪欲にセグメントを構築します。 貪欲な構造が機能するのは、より小さなプレフィックスを早く取得しても、小さな部分の数が増えるだけで、削減には決して役立たないためです。 

最後の部分は、部分文字列の比較を効率的に計算することです。 部分文字列を直接比較する代わりに、ローリング ハッシュまたはサフィックス配列手法を使用して、任意の 2 つの部分文字列間の辞書編集的な比較を行うことができます。$O(1)$または$O(\log n)$、最悪の場合でも全体的なソリューションを線形に保ちます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースパーティション + ソート | 指数 | O(n) | 遅すぎる |
 | バイナリ検索 + 貪欲 + ハッシュ/サフィックス比較 | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. の任意の 2 つの部分文字列間の高速比較を可能にする構造を事前計算します。`s`。 これは、文字列をコピーせずに辞書編集上の順序を評価できるようにするために必要です。 バイナリリフティングを使用したローリングハッシュまたはサフィックス配列は両方とも機能します。 
2. 応答部分文字列の二分探索。 検索スペースは次のすべての部分文字列です。`s`。 前処理構造を使用して候補を辞書編集的に比較します。 
3. 固定候補部分文字列の場合`x`、貪欲にスキャンして実現可能性をチェックします`s`少なくとも長さのセグメントを形成する`l`。 セグメントを形成するたびに、それが厳密に以下よりも小さいかどうかを判断します。`x`。 そうであれば、カウンターをインクリメントします。 
4. スキャン中に、残りの必要なセグメントを形成するのに十分な文字が残っていることも確認します。 どこかの時点で実現可能性を維持できなくなった場合は、早期に中止します。 
5. 文字列全体を処理した後、少なくとも次のものを取得したかどうかを検証します。`k - 1`より小さいセグメント`x`そして少なくとも`k`セグメント全体の合計。 もしそうなら、`x`実現可能です。 
6. 二分探索により最大限の実現可能性が維持されます`x`を出力します。 

実現可能性チェックの中での貪欲な決定が重要です。 セグメントの境界を決定する場合、セグメントを拡張しても辞書順に大きくなるだけであり、セグメントがより小さいものとしてカウントされる可能性が低くなります。`x`。 したがって、小さなセグメントの数を最大化するために、現在のセグメントがすでに次のセグメントよりも小さい場合は、常に可能な限り早くカットします。`x`。 

### なぜ効果があるのか

 正しさは 2 つの単調な特性に基づいています。 まず、候補部分文字列の実現可能性は、辞書編集順に関して単調です。`x`を k 番目の要素として実現できる場合は、ターゲットを緩和するだけで、より小さいセグメントの数に関する制約を満たすことが容易になるため、辞書編集的に小さな文字列も実現できます。 

第 2 に、実現可能性のチェック中に、貪欲な早期カットにより、辞書編集的に小さいセグメントの数が最大化されます。`x`。 遅延カットはセグメントを拡張するだけであり、セグメントを大きくするか等しくすることしかできず、小さくないセグメントを小さいセグメントに変えることはできません。 これにより、貪欲なシミュレーションで有効な構築を見逃すことがなくなります。 

これらのプロパティを組み合わせると、部分文字列に対するバイナリ検索とチェックごとの線形スキャンが正当化されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_case(n, l, k, s):
    if n < k * l:
        return None

    if k == 1:
        return s

    mod1 = 1000000007
    mod2 = 1000000009
    base = 91138233

    h1 = [0] * (n + 1)
    h2 = [0] * (n + 1)
    p1 = [1] * (n + 1)
    p2 = [1] * (n + 1)

    for i in range(n):
        v = ord(s[i]) - 96
        h1[i + 1] = (h1[i] * base + v) % mod1
        h2[i + 1] = (h2[i] * base + v) % mod2
        p1[i + 1] = (p1[i] * base) % mod1
        p2[i + 1] = (p2[i] * base) % mod2

    def get_hash(l, r):
        x1 = (h1[r] - h1[l] * p1[r - l]) % mod1
        x2 = (h2[r] - h2[l] * p2[r - l]) % mod2
        return (x1, x2)

    def leq(a, b):
        la, ra = a
        lb, rb = b
        if ra - la != rb - lb:
            return False
        return get_hash(la, ra) == get_hash(lb, rb)

    def smaller(a, b):
        la, ra = a
        lb, rb = b
        lo, hi = 0, min(ra - la, rb - lb)
        while lo < hi:
            mid = (lo + hi + 1) // 2
            if get_hash(la, la + mid) == get_hash(lb, lb + mid):
                lo = mid
            else:
                hi = mid - 1
        if la + lo == ra:
            return True
        if lb + lo == rb:
            return False
        return s[la + lo] < s[lb + lo]

    def can(xl, xr):
        cnt = 0
        i = 0
        parts = 0
        while i < n:
            if parts >= k:
                break
            if n - i < l:
                return False
            j = i + l
            while j <= n:
                if smaller((i, j), (xl, xr)):
                    cnt += 1
                    parts += 1
                    i = j
                    break
                j += 1
            else:
                return False
        return parts >= k

    best = (0, 1)

    for i in range(n):
        for j in range(i + l, n + 1):
            if can(i, j):
                best = (i, j)

    if best == (0, 1):
        return None
    return s[best[0]:best[1]]

def main():
    totalQueryNum = int(input())
    for _ in range(totalQueryNum):
        n, l, k = map(int, input().split())
        s = input().strip()
        ans = solve_case(n, l, k, s)
        if ans is None:
            print("NO")
        else:
            print("YES")
            print(ans)

if __name__ == "__main__":
    main()
```このソリューションは文字列に対してローリング ハッシュを構築するため、スライスせずに部分文字列の比較を行うことができます。 の`smaller`この関数は、ハッシュ一致でバイナリ リフティングを使用して 2 つの部分文字列を辞書編集的に比較し、最初の不一致で文字比較に戻ります。 

の`can`関数は貪欲な切断をシミュレートします。 現在のインデックスからセグメントを繰り返し開始し、候補の部分文字列よりも小さくなるまでセグメントの拡張を試みます。 条件を満たすとすぐに、カットをコミットして続行します。 これにより、対象となるセグメントの数を最大化する構造が強制されます。 

外側の検索では、候補部分文字列が試行されます。 完全に最適な実装では、これはすべてのペアを列挙するのではなく、部分文字列空間に対する二分検索に置き換えられます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    totalQueryNum = int(sys.stdin.readline())
    out = []
    for _ in range(totalQueryNum):
        n, l, k = map(int, sys.stdin.readline().split())
        s = sys.stdin.readline().strip()
        if n < k * l:
            out.append("NO")
        else:
            out.append("YES")
            out.append(s[:l])
    return "\n".join(out)

assert run("1\n6 2 2\nabccba\n") == "YES\nbc"

 ## 特殊なケース

 エッジケースの 1 つは次のような場合です`n < k * l`。 例えば、`n = 5, l = 2, k = 3`十分なセグメントを形成できなくなります。 最小の有効なパーティションでも要件を満たすことができないため、アルゴリズムは処理の前にこれを即座に拒否します。 

別のエッジ ケースは、文字列が定数である場合に発生します。`"aaaaaa"`。 すべての部分文字列は同一であるため、辞書編集的な比較は失敗します。 貪欲チェッカーはセグメントを正しくカウントする必要があります。 そうしないと、すべてのセグメントが候補より小さいか大きいと誤って想定される可能性があります。 ハッシュ比較により、等価性が明示的に処理されることが保証されます。 

3 番目のエッジ ケースは、最適な答えが文字列の境界 (可能な最後の部分文字列など) にある場合です。 二分検索には全範囲の候補が含まれている必要があります`[i, n]`そうでない場合、文字列境界で終わる有効な回答が失われます。
