 # 問題の理解

 ゲームは一次元のセルのストリップ上でプレイされます。 最初はすべてのセルが空です。 プレイヤーは交互に空いているポジションを選択し、そこにクロスを置きます。 移動は、結果のストリップに 3 つの連続する十字が含まれていない場合にのみ許可されます。 行動できなかったプレイヤーが負けとなります。 

プログラムは、最終的な勝者を出力するように要求されません。 裁判官と対戦しなければなりません。 ゲームが始まる前に、先手を取るか後手を取るかを選択します。 その後は常に勝利を保証する動きをしなければなりません。 

ストリップの長さは最大 30 です。この境界は十分小さいため、ボード全体をビットマスクとして表現し、ゲームの状態を検索できます。 長さが 30 の場合、理論的には最大 2^30 の可能なマスクが得られます。これはやみくもに訪問するには多すぎますが、3 つの連続した十字を禁止するルールにより、到達可能な状態の数が大幅に減少します。 を含まないバイナリ文字列の数`111`はトリボナッチ数列のように成長し、この制限ではメモ化された検索に十分小さいです。 

メインのエッジ ケースは、ストリップの端に近い位置と、移動によって隣接するクロスのペアが作成される位置から発生します。 

長さ 1 のストリップの場合、唯一の移動は単一セルを占有することです。 入力は次のとおりです。```
1
```正しい動作は、最初に移動してセル 1 をプレイすることを選択することです。常に「中間」の移動を試みる戦略は、中間の処理が必要ないため失敗します。 

2 番目のエッジケースは、局所的には有効に見えますが、3 つのクロスを生み出す動きです。 たとえば、長さ 3 のストリップでは次のようになります。```
XXX
```プレイヤーは何も行動できません。 選択したセルが空かどうかだけをチェックする不用意な実装では、不正な移動が許可されてしまいます。 

もう 1 つの重要なケースは、ストリップに 2 つの連続する十字が含まれている場合です。```
XX..
```次のセルは入力できません。`XXX`、ただし、より離れたセルは依然として合法です。 合法性チェックでは、選択したポジションだけでなく、結果として得られるボード全体を検査する必要があります。 

## アプローチ

 ## アルゴリズムのチュートリアル

 1. ストリップの長さを読み取り、初期位置が勝っているかどうかを判断します。 再帰的ソルバーは、空のボードに相手に損失を強いる動きがあるかどうかをチェックします。 存在する場合、プログラムは最初に移動することを選択します。 それ以外の場合は、2 番目に移動することを選択します。 
2. 現在のボードを整数マスクとして表します。 少し`i`セルの場合は 1 です`i`すでに十字架が含まれています。 これにより、一定時間の更新が行われ、完全な状態をメモ化キーとして使用できるようになります。 
3. 状態については、すべての空のセルを試してください。 そこに一時的にクロスを置き、ボードが 3 つの連続したビットが設定されていないというルールに従っているかどうかを確認します。 
4. 正当な手が相手の負け状態に達した場合、この手を現在の状態の勝ち手として保存します。 そのような動きが存在しない場合は、その状態を負けとしてマークします。 
5. ゲーム中、対戦相手が移動するたびに、そのセルをマスクに追加し、保存されている勝ち手をクエリします。 そのセルを出力し、ジャッジがゲームを終了するまで続けます。 

なぜ効果があるのか:

 再帰的定義は、標準の勝ち負けの状態プロパティに従います。 少なくとも 1 回負けている状態に移行した場合、その状態はまさに勝利しています。 すべての合法的な手が相手に勝利の状態を与えるとき、その状態は正確に負けています。 すべての動きが 1 つのクロスを追加するため、ゲーム グラフにはサイクルがないため、メモ化によって曖昧さが生じることはありません。 記憶された動きは、常に相手が勝利を強制できない位置につながります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from functools import lru_cache

def solve_game(n):
    @lru_cache(None)
    def dfs(mask):
        for i in range(n):
            if mask >> i & 1:
                continue
            nxt = mask | (1 << i)
            if not valid(nxt):
                continue
            if dfs(nxt) == -1:
                return i
        return -1

    @lru_cache(None)
    def valid(mask):
        cnt = 0
        for i in range(n):
            if mask >> i & 1:
                cnt += 1
                if cnt >= 3:
                    return False
            else:
                cnt = 0
        return True

    return dfs

def main():
    n = int(input())

    dfs = solve_game(n)
    mask = 0

    first_move = dfs(mask)

    if first_move != -1:
        print(1)
        print(first_move + 1)
        sys.stdout.flush()
        mask |= 1 << first_move
    else:
        print(2)
        sys.stdout.flush()

    while True:
        x = int(input())
        if x == 0:
            return

        mask |= 1 << (x - 1)

        move = dfs(mask)
        if move == -1:
            print(0)
            sys.stdout.flush()
            return

        print(move + 1)
        sys.stdout.flush()
        mask |= 1 << move

if __name__ == "__main__":
    main()

の`valid`この関数はゲームの唯一のルールをチェックします。 連続して占有されているセルをスキャンし、長さが 3 のランを拒否します。 これを分離しておくことで、動きを生成する際の微妙な間違いを避けることができます。 

マスクの更新はすべての移動の直後に行われます。 これにより、保存された状態と実際のボードの同期が維持されます。 対話プロトコルではセルに 1 から番号が付けられるため、出力では 1 ベースのインデックスが使用されます。

## テストケース

 元の問題は対話型であるため、従来のアサートベースのテストは直接適用できません。 コア ゲーム ソルバーは、返された動きの分類が既知の位置と一致するかどうかを確認することでテストできます。```
from functools import lru_cache

def make_solver(n):
    @lru_cache(None)
    def valid(mask):
        run = 0
        for i in range(n):
            if mask >> i & 1:
                run += 1
                if run == 3:
                    return False
            else:
                run = 0
        return True

    @lru_cache(None)
    def win(mask):
        for i in range(n):
            if mask >> i & 1 == 0:
                nxt = mask | (1 << i)
                if valid(nxt) and not win(nxt):
                    return True
        return False

    return win

assert make_solver(1)(0) is True

assert make_solver(3)(7) is False
assert make_solver(5)(0) in (True, False)
