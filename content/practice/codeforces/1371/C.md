 ## 解決策
 ## 問題の理解

 2種類のクッキーと2種類のゲストが与えられます。 クッキーはバニラとチョコレートの数に分かれており、ゲストの行動タイプも 2 種類あります。 ゲストは私たちが選択できる順序で到着し、各ゲストは残りのバニラ クッキーとチョコレート クッキーの数の現在の比較にのみ基づいて決定を下します。 

タイプ 1 のゲストは現在の状態を観察します。 バニラ クッキーが厳密にチョコレート クッキー以上である場合、彼らはバニラを選択します。 それ以外の場合はチョコレートを選択します。 タイプ 2 のゲストは、同じ比較の下で反対の好みを選択します。 フレーバーを選択した後、ゲストは、利用可能な場合はそのフレーバーのクッキーを 1 つ食べます。そうでない場合は、その注文のプロセスはすぐに失敗します。 

このタスクは、すべてのゲストがクッキーを正常に食べるような順序が存在するかどうかを判断することです。 

制約は非常に大きく、Cookie 数とゲスト数は最大 10^18 になります。 これにより、ゲストにわたるシミュレーションや、分岐決定による個々のゲストの線形処理に依存する状態の拡張が即座に排除されます。 有効な解決策では、問題をテスト ケースごとの算術チェックの数を一定に減らす必要があります。 

Cookie タイプのいずれかが 0 から始まる場合、微妙な問題が発生します。 たとえば、チョコレート クッキーはないが、少なくとも 1 人のゲストがある時点でチョコレートを選択する可能性がある場合、注文ではそのようなことが起こらないようにする必要があります。 同様に、ある時点で両方のタイプが等しい場合、タイブレーク動作は決定的になりますが、それでも後続のゲストの結果が反転する可能性があります。 

主な問題点は、システムがカウントだけではなく、すべての決定を決定する差分 v − c の符号によって駆動されることです。 これは、プロセス全体が「バニラ優位」体制に留まるか「チョコレート優位」体制に留まるかによって制御されることを意味します。 

単純なアプローチでは、ゲスト タイプのすべての順列をシミュレートしたり、貪欲に次のゲストを選択したりする可能性があります。 これは、順列の数が n + m では階乗であるため失敗します。また、局所的な選択が v − c における将来の符号の変化に影響を与えるため、貪欲なシミュレーションでも失敗する可能性があります。 

## アプローチ

 ブルートフォース手法では、n + m 個のゲストのすべての順列を列挙し、それぞれの順序をシミュレートします。 ゲストのシーケンスごとに (v, c) を追跡し、ルールを段階的に適用して、怒っているゲストがいるかどうかを確認します。 これはプロセスを直接反映しているため、これは正しいです。 ただし、順列の数は (n + m)! であり、これは入力が非常に小さい場合でも不可能であり、各シミュレーションのコストは O(n + m) であるため、合計はまったく実行不可能です。 

重要な洞察は、システムの動作はバニラ クッキーとチョコレート クッキーの絶対値ではなく、その違いのみに依存するということです。 各ゲストはバニラまたはチョコレートのいずれかをちょうど 1 減らします。選択は v − c の符号によって決まります。 

したがって、正確なシーケンスという観点から考えるのではなく、システムの一貫性を保ちながら、各「タイプ効果」を何回安全に適用できるかという観点から推論します。 

差 d = v − c を定義しましょう。 タイプ 1 ゲストは、より大きな山から消費してシステムをバランスに向けて推進しますが、タイプ 2 ゲストはシステムを反対方向に推進します。 重要な観察は、各ゲスト タイプが、希望する選択肢が利用可能な方向に向かってシステムを安定化させようとするということです。 

これにより、問題は、対応する要求が満たされる前にいずれかの Cookie タイプが使い果たされることを防ぐ順序でゲストを割り当てることができるかどうかを確認することに変わります。 正しい条件は、一方が他方に比べて小さすぎる場合に、強制的に符号矛盾を回避できるかどうかにのみ依存します。

これを明確に表現する方法は、次のとおりです。システムは、どちらの側も、初期の可用性を超える「反対の選択の要求」に対応することを強制されない場合にのみ実行可能です。これは、n と m を、a と b のシフトされたバージョンと比較することに基づく単純な条件につながります。 

問題を、ゲスト タイプ間の強制的な不均衡を考慮した後で、より小さいリソースをサポートできるかどうかを確認することに集約します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (順列) | O((n+m)! · (n+m)) | O(n+m) | 遅すぎる |
 | 貪欲な不変量削減 | お(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 重要なのは、動的プロセスを不均衡に基づいた実現可能性チェックに変換することです。 

## ステップ 1: 問題を正規化する

 バニラとチョコレートを対称的に扱います。 どちらが実質的に強いのか、強制的な不一致が起こらないようにゲストを配置できるかどうかを分析すると仮定します。 

中心的な考え方は、正確な順序ではなく、相対的な優位性のみが重要であるということです。 

## ステップ 2: 強制消費構造を観察する

 各ゲストは、タイプに応じて、現在大きい山から、または小さい山から消費します。 これは、ゲストがシステムをバランスに向けて、またはバランスから遠ざけるために効果的に「押す」ことを意味します。 

あるタイプのゲストが、反対タイプの利用可能な Cookie に比べて多すぎる場合、最終的には必要な Cookie タイプが利用できなくなる状態に陥ります。 

## ステップ 3: 不均衡を解消する実現可能性

 方向性の圧力を考慮した上で、どちらの側も供給に対して過剰な要求がないことを確認することで、構成がすべてのゲストを維持できるかどうかを確認します。 

これにより、崩壊を防ぐ方法で、ゲスト タイプ間の違いが最初の Cookie の違いと互換性があるかどうかを確認することができます。 

具体的には、ゲスト タイプ間の絶対的な不均衡が、初期クッキーの方向性圧力の吸収能力を超えない場合、このシステムは実現可能です。 

## ステップ 4: 最終決定

 比較から導き出される必要なバランス条件を計算します。 

- タイプ 1 およびタイプ 2 のゲストは何人存在しますか
 - バニラクッキーとチョコレートクッキーの間にどれだけの初期余剰が存在するか

 優位性が決して行き止まりにならないようにシステムを命令できる場合は、「はい」を出力し、それ以外の場合は「いいえ」を出力します。 

### なぜ効果があるのか

 このプロセスは、v − c の符号によって完全に支配されます。 すべてのゲストの決定は、現在この差がプラスの状態か、マイナスの状態か、またはゼロの状態にあるかによってのみ決まります。 つまり、シーケンス全体が整数のウォークを制御していると見なすことができ、各ステップが片側から 1 ユニットを消費し、符号が反転する可能性があります。 

失敗する唯一の方法は、ゲストが要求した瞬間に必要な Cookie タイプが空の状態に強制されることです。 ゲストを任意に並べ替えることができるため、唯一の本当の制約は、弱い側の早期枯渇を防ぎつつ、反対の要求を満たすのに十分な移行を許可するスケジュールが存在するかどうかです。 

これは、ゲストの数と初期の Cookie の非対称性の間のバランス状態に帰着します。そのため、一定時間のチェックで十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        a, b, n, m = map(int, input().split())

        # Symmetry: ensure a >= b by swapping if needed
        if a < b:
            a, b = b, a
            n, m = m, n

        # Now a is the larger or equal pile
        # We check feasibility based on whether the smaller pile can support demand
        # derived from imbalance between guest types
        if m <= b:
            print("Yes")
        else:
            print("No")

if __name__ == "__main__":
    solve()
```この実装では、対称性を使用して状態空間を削減します。 バニラ (a) が少なくともチョコレート (b) と同じくらい大きいという観点から常に推論できるように、クッキーのタイプを交換します。 これにより、型の整列を一貫して解釈できるようになります。 

次に、意思決定チェックでは、「反対の要求をする」ゲストが小さいパイルの容量を超えているかどうかに焦点を当てます。 そうでない場合は、いつでもゲストをインターリーブして、消費が有効なままにすることができます。 そうしないと、必然的に、必要な Cookie タイプが枯渇する状態に陥ります。 

重要な点は、スワップに Cookie 数とゲスト数の両方が含まれるようにすることです。 n と m を入れ替えることを忘れると、対称性の議論が崩れ、不正確な実行可能性チェックが行われる可能性があります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    def solve():
        t = int(input())
        res = []
        for _ in range(t):
            a, b, n, m = map(int, input().split())
            if a < b:
                a, b = b, a
                n, m = m, n
            res.append("Yes" if m <= b else "No")
        return "\n".join(res)

    return solve()

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、両方の Cookie 数が等しく、ゲストが大きく偏っている場合です。 たとえば、a = b であるが m が大きい場合、スワップは何も変更せず、条件は m が b に吸収できるかどうかを直接チェックします。 この場合、b は a に等しいため、実現可能性は対称容量が維持されるかどうか、つまり条件が正しく捉えるかどうかに完全に依存します。 

もう 1 つのエッジ ケースは、1 つの Cookie タイプが最初はゼロである場合です。 a = 0 および b > 0 の場合、スワッピングにより常に大きい側から分析することが保証され、アルゴリズムが存在しないパイルにゲストを割り当てようとする誤検知を防ぎます。 

3 番目のエッジ ケースは、n と m が非常に大きい (最大 10^18) 場合に発生します。 このアルゴリズムは反復を行わないため、比較と交換のみを使用してこれらの値を安全に処理し、Python の整数には制限がないため、オーバーフローを完全に回避します。
