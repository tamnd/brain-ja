 ## 解決策
 ## 問題の理解

 架空の Pindows オペレーティング システムで記述された単一のコマンド ライン文字列が与えられます。 コマンド ラインは、プログラムに渡されるトークンである語彙素で構成されます。 

語彙素が現れる方法は 2 つあります。 

通常の語彙素は、スペース以外の文字の最大のシーケンスです。 たとえば、次のようになります。```
run.exe one two
```語彙素は`run.exe`、`one`、 そして`two`。 

引用された語彙素は次で始まります`"`そしてマッチングで終わります`"`。 これらの引用符の間にあるものはすべて、スペースも含めて 1 つの語彙素に属します。 中身が空の場合もあります。 例えば：```
"a b" ""
```2 つの語彙素が含まれています。`a b`そして空の文字列。 

入力は有効なコマンド ラインであることが保証されます。 引用符は決して曖昧ではなく、引用符で囲まれたブロックは適切に閉じられており、すべての語彙素はスペースまたは文字列の末尾によって隣接する語彙素から分離されています。 

私たちのタスクは、コマンドラインを解析し、すべての語彙素をそれぞれの行に次のように出力することです。`<`そして`>`。 

文字列の長さは最大でも$10^5$。 これにより、大きな部分文字列を繰り返しコピーしたり、入力の一部を再スキャンしたりするアプローチは即座に排除されます。 トークン境界を識別する必要があるのは一度だけであるため、リニア スキャンは自然なターゲットです。 

いくつかの特殊なケースは注目に値します。 

空の引用符で囲まれた引数を考えてみましょう。```
""
```正しい出力は次のとおりです。```
<>
```すべてのトークンに少なくとも 1 つの文字が含まれると想定するパーサーは、誤ってこの引数を破棄してしまいます。 

引用符で囲まれた引数にスペースが含まれているとします。```
"a b c"
```正しい出力は次のとおりです。```
<a b c>
```入力をスペースで分割すると、誤って 3 つの別々の部分が生成されます。 

単一のスペースで構成される引用符で囲まれた引数を考えてみましょう。```
" "
```正しい出力は次のとおりです。```
< >
```これは空の引数とは異なるため、引用符内のすべての文字を正確に保持する必要があります。 

最後に、隣接する句読点を考慮します。```
run.exe one, two!
```正しい出力は次のとおりです。```
<run.exe>
<one,>
<two!>
```句読点は語彙素の一部です。 スペースと引用符のみが特別な意味を持ちます。 

## アプローチ

 最も直接的なアイデアは、文字列を 1 文字ずつ処理し、現在の語彙素を構築することです。 引用符の外側にスペースがある場合は常に、現在の語彙素を終了します。 引用符に遭遇するたびに、一致する終了引用符を見つけて、それらの間のすべてを 1 つのトークンとして扱います。 

ブルートフォース実装では、一致する引用符を前方検索して繰り返し新しい部分文字列を作成する可能性があります。 各検索は文字列の大部分を横断する可能性があるため、最悪の場合の複雑さは次のように低下​​する可能性があります。$O(n^2)$。 と$n = 10^5$、それは高くなりすぎます。 

入力の構造により、より優れたオプションが提供されます。 すべてのキャラクターは、次の 3 つのカテゴリのいずれかに正確に属します。 

1. 引用符の外側の区切りスペース。 
2. 引用された語彙素内の文字。 
3. 引用符で囲まれていない語彙素の文字。 

文字が処理されると、それを再度確認する必要はありません。 これは、単一の左から右へのスキャンを示唆しています。 

重要な観察は、引用された語彙素は常に次で始まることです。`"`、そしてステートメントはコマンドラインが有効であることを保証します。 開始相場が表示されるとすぐに、対応する終了相場まで進み続けることができます。 それらの間の内容は 1 つの完全な語彙素を形成します。 引用符で囲まれていない語彙素の場合は、次のスペースまで進みます。 

各キャラクターは一定の回数訪問され、線形の解決策が得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 遅すぎる |
 | 最適 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 入力行全体を読み取ります。 
2. インデックスを維持する`i`現在の位置を指します。 
3. もし`s[i]`スペースです、前進します`i`。 

語彙素の外側のスペースは単なる区切り文字であるため、どのトークンにも属しません。 
4. もし`s[i]`が二重引用符である場合は、引用された語彙素の解析を開始します。 

開始引用符を過ぎて進み、開始位置を覚えて、対応する終了引用符まで続けます。 これらの引用符間の部分文字列は 1 つの語彙素です。 
5. その語彙素を保存し、終了引用符を超えて進みます。 
6. それ以外の場合は、引用符で囲まれていない語彙素の解析を開始します。 

スペースまたは文字列の終わりに到達するまで前進を続けます。 走査された文字は 1 つの語彙素を形成します。 
7. 語彙素を保存します。 
8. 文字列全体が処理されるまで繰り返します。 
9. で囲まれた保存されている各語彙素を出力します。`<`そして`>`。 

### なぜ効果があるのか

 どの位置でも、パーサーは語彙素の外側か、正確に 1 つの語彙素の内側にあります。 入力により、引用符が適切に一致し、語彙素がスペースまたは文字列境界で区切られていることを保証します。 

引用符が見つかった場合、一致する引用符までのすべての文字は、定義により同じ語彙素に属します。 非引用符、非スペース文字が出現すると、語彙素は次の区切り文字スペースまで拡張されます。 これらはまさにコマンドライン仕様で使用されるルールです。 

すべての語彙素は定義された境界条件に従って抽出され、すべての文字は正確に 1 つの処理領域に属するため、アルゴリズムはコマンド ラインで表される語彙素を正確に出力します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().rstrip('\n')

    n = len(s)
    i = 0
    tokens = []

    while i < n:
        if s[i] == ' ':
            i += 1
            continue

        if s[i] == '"':
            i += 1
            start = i

            while i < n and s[i] != '"':
                i += 1

            tokens.append(s[start:i])
            i += 1  # skip closing quote
        else:
            start = i

            while i < n and s[i] != ' ':
                i += 1

            tokens.append(s[start:i])

    sys.stdout.write('\n'.join(f'<{token}>' for token in tokens))

if __name__ == "__main__":
    solve()
```実装は解析ロジックに直接に従います。 

外側のループは常に最初の未処理の文字を指します。 スペースは語彙素に属さないため、すぐにスキップされます。 

引用符に遭遇すると、コードは開始引用符の直後に位置を記録し、終了引用符まで進みます。 スライス`s[start:i]`引用された内容が正確に含まれています。 引用符が隣接している場合、これは空の文字列を自然に処理します。`start == i`そしてスライスは空です。 

通常の語彙素の場合、パーサーは次のスペースまで進みます。 有効な入力では引用符で囲まれていない語彙素内に引用符を含めることはできないため、追加のチェックは必要ありません。 

よくある間違いは、`split()`入力上で。 これにより、引用されたセクションに関する情報が破壊され、空の引数を表すことができなくなります。 もう 1 つの微妙な点は、引用された語彙素内のスペースを保持することです。 部分文字列抽出では、外側の引用符文字のみが削除されるため、これが自動的に行われます。

 ## 特殊なケース

 次の入力を考えてみましょう。```
""
```パーサーは開始引用符を認識し、すぐに次の引用符に進み、それらの間の部分文字列を抽出します。 この部分文字列の長さは 0 であるため、保存される語彙素は空の文字列になります。 出力は次のようになります。```
<>
```特殊なケースのコードは必要ありません。 

考慮する：```
" "
```引用符付きモードに入ると、パーサーは引用符の間の単一のスペースを収集します。 抽出された部分文字列は次のとおりです`" "`それよりも`""`、生産:```
< >
```これにより、引用符内のスペースは区切り文字ではなくデータであることが確認されます。 

考慮する：```
"a b" c
```最初の語彙素は完全に引用符内で解析され、次の結果が得られます。`a b`。 終了引用符の後、パーサーは分離スペースをスキップし、引用符で囲まれていない語彙素を解析します。`c`。 出力は次のとおりです。```
<a b>
<c>
```引用符付きモードでは、対応する終了引用符に到達するまで区切り文字のセマンティクスが無視されるため、内部スペースは最初の引数の一部のままになります。 

考慮する：```
run.exe one, two!
```パーサーは句読点を特別に扱うことはありません。 引用符で囲まれていない解析は、スペースに到達した場合にのみ停止します。 抽出された語彙素は次のとおりです。```
<run.exe>
<one,>
<two!>
```これにより、句読点が入力に表示されるとおりにトークンに属していることが検証されます。
