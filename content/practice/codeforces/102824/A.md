 ## 解決策
 ## 問題の理解

 この問題は、エッジが整数の重みを持つ木について説明します。 2 つの頂点間を移動するコストは、ツリー パス上のエッジの重みの合計ではありません。 代わりに、2 つの頂点間の直接移動のコストは、固有のツリー パス上のすべてのエッジの重みのビット単位の XOR になります。 任意の一連の移動を使用できるため、タスクは、選択した開始頂点から他のすべての頂点までの可能な最短距離を見つけて、それらの距離の合計を出力することです。 

木はダイナミックです。 更新操作では、同じ値をすべてのエッジの重みに XOR します。 クエリ操作では、指定された 1 つの頂点からの最短距離の合計が求められます。 

重要な観察は制約から始まります。 最大で大きな値を持つツリー`n`また、多くのクエリでは、更新のたびにすべての距離を再計算する余裕はありません。 すべてのクエリに対してツリーをたどるソリューションは二次式になります。 各クエリを少量の作業量 (通常は頂点の数で対数) に減らす必要があります。 

XOR パス値を使用してツリーを表現する便利な方法は、それを任意の頂点にルートして定義することです。`value[v]`ルートからルートまでのパス上のエッジの重みの XOR として`v`。 2 つの頂点間の XOR 距離`u`そして`v`になる`value[u] ^ value[v]`。 

XOR 距離の完全なグラフにおける最短パスは、常に直接の XOR 距離です。 中間頂点の場合`x`、間で異なるすべてのビット`u`そして`v`まさに次のうちの 1 つに貢献します`(u ^ x)`そして`(x ^ v)`、一方、ビットが等しいと追加コストがかかるだけです。 したがって、中間頂点を使用しても距離を小さくすることはできません。 

これにより、問題は、クエリされた値とすべての格納された値の間の XOR の合計を維持することに変わります。 

グローバル エッジ アップデートには特別な構造があります。 ツリーがルート化されている場合、奇数の深さのすべてのノードのルート XOR 値は更新値によって切り替えられますが、偶数の深さのすべてのノードは同じ値を保持します。 これは、頂点が深さの同等性に基づいて 2 つのグループに自然に分割されることを意味します。 

厄介なケースは、このパリティ分割に関連しています。 すべての頂点が 1 つのグループとして処理される場合、更新により保存されている値が破損します。 

たとえば、次のことを考えてみましょう。```
3 2
1 2 5
2 3 7
1 1
2 1
```最初は頂点 1 をルートとして、値は次のようになります。`0, 5, 2`。 最初のクエリは頂点 1 からの距離を求めます。```
0^0 + 0^5 + 0^2 = 7
```すべてのエッジを更新した後、`1`、値は次のようになります`0, 4, 2`奇数の深さの頂点のみが変更されるためです。 すべての保存された値を XOR するソリューション`1`間違って取得してしまう`1, 4, 3`。 

もう 1 つのエッジ ケースは、単一の頂点ツリーです。```
1 1
2 1
```答えは`0`。 エッジはなく、唯一の頂点からそれ自体までの距離はゼロです。 少なくとも 1 つのエッジがあることを前提としたコードは、ここで失敗する可能性があります。 

3 番目の重要なケースは、クエリされた頂点が奇数の深さにある場合です。 頂点自体に格納されている値は更新後に変更され、更新は別の奇数深さの頂点と比較する場合にのみキャンセルされます。 これを忘れると、奇数の深さの頂点からのクエリに対して間違った答えが返されます。 

## アプローチ

 簡単なアプローチは、すべてのクエリのすべての最短距離を計算することです。 2 つの頂点間の最短距離はそれらのルート値の XOR にすぎないため、すべてのルート値を保存し、クエリごとにすべての頂点を反復処理して追加することができます。`value[s] ^ value[i]`。 

このアプローチは、答えの定義を直接評価するため、正しいです。 ただし、`n`頂点と`q`クエリを実行します`O(nq)`XOR 演算。 両方の値が大きい場合、これは非常に遅くなります。 

有益な観察は、クエリが任意のペアを要求していないことです。 1 つの数値と固定の数値セットの間の XOR の合計を要求します。 バイナリ トライは、各ビットを独立して決定することで、このようなクエリに効率的に答えることができます。 すべてのビットにおいて、そのビットに 0 または 1 がある数値がいくつあるかを知ることが最も効果的です。 

残りの難関はグローバル エッジの更新です。 更新のたびにすべての値を再構築することは不可能です。 パリティ観測はこれを解決します。 2 つのバイナリ試行を保持します。1 つは偶数の深さの頂点用、もう 1 つは奇数の深さの頂点用です。 奇数深さのトライは、すべての論理値が更新のたびに同じ数だけシフトされるため、遅延 XOR タグをサポートします。 

クエリが到着すると、ソース頂点の現在の論理値を決定し、両方の試行で XOR 合計を求めます。 各トライクエリには対数時間がかかります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | 最適 | O((n + q) log A) | O(n log A) | 承認済み |

 ここ`A`可能な最大値の範囲であり、最大でも`2^30`, したがって、トライの高さは 30 になります。 

## アルゴリズムのチュートリアル

 1. ツリーの頂点にルートを作成します`1`そしてDFSを実行します。 トラバース中に計算します`value[v]`、ルートからエッジの重みまでの XOR`v`、およびすべての頂点の深さのパリティ。 深さが偶数か奇数かに応じて、これらの値を 2 つのグループに保存します。 
2. 各パリティ グループのバイナリ トライを構築します。 トライには、そのグループ内のすべての現在の論理値が保存されます。 奇数深さのトライは、構造にプッシュされていない更新を表す遅延 XOR 値も保持します。 
3. 値を含む更新の場合`x`、XOR を奇数深さのトライにのみ遅延的に適用します。 偶数の深さの頂点は変更されませんが、奇数の深さの頂点はすべて同じ XOR を受け取ります。 
4. 頂点からのクエリの場合`s`、現在の値を見つけます。 もし`s`深さは均一であり、変化しません。 もし`s`深さが奇数です。その現在の値は`value[s] ^ lazy_xor_of_odd_group`。 
5. 両方の試行に対して、この値からの XOR 距離の合計を求めます。 2 つの結果を加算し、答えを出力します。 

なぜ効果があるのか:

 不変条件は、各トライが常にそのパリティ グループ内のすべての頂点の現在のルート XOR 値を正確に表すことです。 遅延タグは、保存された物理構造を変更せず、保存された数値の解釈方法のみを変更します。 try クエリは、同じ遅延 XOR によって要求された値を変換し、実際の現在の値との比較と同等の比較を行います。 

2 つの頂点間の最短距離はルート値の XOR であるため、2 つのトライの結果を合計すると、必要な合計距離が正確に得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

BITS = 30

class Trie:
    def __init__(self):
        self.child = [[-1, -1]]
        self.cnt = [0]
        self.sum = [[0] * 2]
        self.lazy = 0

    def add(self, x):
        node = 0
        self.cnt[node] += 1
        for b in range(BITS - 1, -1, -1):
            bit = (x >> b) & 1
            if self.child[node][bit] == -1:
                self.child[node][bit] = len(self.child)
                self.child.append([-1, -1])
                self.cnt.append(0)
                self.sum.append([0, 0])
            self.sum[node][bit] += 1 << b
            node = self.child[node][bit]
            self.cnt[node] += 1

    def query(self, x):
        x ^= self.lazy
        node = 0
        ans = 0
        for b in range(BITS - 1, -1, -1):
            if node == -1:
                break
            bit = (x >> b) & 1
            same = self.child[node][bit]
            diff = self.child[node][bit ^ 1]
            if diff != -1:
                ans += self.cnt[diff] * (1 << b)
                node = same
            else:
                node = same
        return ans

    def xor_all(self, x):
        self.lazy ^= x

def solve():
    n, q = map(int, input().split())
    graph = [[] for _ in range(n)]
    for _ in range(n - 1):
        u, v, w = map(int, input().split())
        u -= 1
        v -= 1
        graph[u].append((v, w))
        graph[v].append((u, w))

    val = [0] * n
    depth = [0] * n

    stack = [(0, -1)]
    while stack:
        u, p = stack.pop()
        for v, w in graph[u]:
            if v != p:
                val[v] = val[u] ^ w
                depth[v] = depth[u] ^ 1
                stack.append((v, u))

    even = Trie()
    odd = Trie()

    for i in range(n):
        if depth[i] == 0:
            even.add(val[i])
        else:
            odd.add(val[i])

    out = []
    for _ in range(q):
        query = list(map(int, input().split()))
        if query[0] == 1:
            odd.xor_all(query[1])
        else:
            s = query[1] - 1
            cur = val[s]
            if depth[s]:
                cur ^= odd.lazy
            out.append(str(even.query(cur) + odd.query(cur)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```DFS セクションは、ツリー表現を XOR ラベルに変換します。 この変換後は、すべてのペアの距離が 2 つのラベルのみに依存するため、ツリーの正確な形状は問題になりません。 

トライ挿入では、パリティで区切られた初期値が格納されます。 トライ自体は、各分岐を通過する値の数をカウントする通常のバイナリ トライです。 クエリ中に反対のビットを選択すると、`2^b`そのブランチ内のすべての数値について、答えを上位ビットから下位ビットまで貪欲に蓄積できるのはこのためです。 

奇数トライの遅延フィールドは、主な実装の詳細です。 更新後に保存されているすべての値を変更することはありません。 代わりに、クエリ操作は、同じ遅延マスクを使用して要求された値を変換することによって、保留中の XOR を論理的に適用します。 これにより、トライの再構築が回避されます。 

ソース頂点値も遅延更新を考慮する必要があります。 奇数の深さの頂点のみが変更されるため、奇数の深さの頂点からのクエリでは`value[s] ^ odd.lazy`、一方、偶数の深さの頂点は元の値を使用します。

 ## 特殊なケース

 単一の頂点ツリーの場合、2 つの試行には 1 つの値のみが含まれます。 その頂点からのクエリはそれ自体までの距離を要求しますが、XOR 比較のみが行われるため、トライは正しくゼロを返します。`0 ^ 0`。 

すべての頂点が 1 つの長いチェーン内にあるツリーの場合、多くの頂点が偶数と奇数の深さを交互に持ちます。 更新では頂点のちょうど半分が変更されるため、ツリー全体が均一に変更されると仮定するのではなく、2 つのグループを分離するため、ソリューションは成功します。 

奇数の深さの頂点で始まるクエリの場合、アルゴリズムはまず奇数グループの遅延 XOR をソース値に適用します。 ソース頂点自体が更新されたグループに属しているため、これが必要になります。 次に、2 つのトライ クエリが正確な現在のラベルと比較され、正しい合計が生成されます。
