 ## 問題の理解

 石の山がいくつかあります。 すべての石にはタイプがあり、石にもタイプがあります`i`最終的には山になるに違いない`i`。 移動すると、現在空ではない山の頂上にある石が取り出され、別の山の上に置かれます。 目標は、動きの数を最小限に抑えることではなく、許容制限内で有効なシーケンスを生成することだけです。 

入力は初期スタックを記述します。 それぞれの山について、その中に含まれている石の数と、それらの石の種類が上から下までわかっています。 出力は移動のリストであり、各移動はソース パイルと宛先パイルを指定します。 

制約が十分に大きいため、可能な手を探索しようとすることは不可能です。 あたりまでで`10^5`石の場合、状態を調査したり、移動するたびに構成全体を繰り返しスキャンしたりするアプローチは、遅すぎます。 すべての石を一定の回数だけ処理する構造が必要です。 

難しいのは、山の真ん中にある石に自由にアクセスできないことです。 移動できるのは一番上の石だけなので、すべての山からすべてのタイプを直接抽出しようとするアプローチは、間違って配置された石がその下の石をブロックする可能性があるため、行き詰ってしまいます。 

直接ソートが失敗する理由を簡単な例で示します。```
1
3
2 1 3
```型を移動しようとすると`1`石を直接山に入れる`1`、それはタイプの下に埋もれています`3`石。 唯一の合法的な最初の動きは、一番上の石を取り除くことです。 スタックの内容へのランダム アクセスを前提とした不用意な解決策は、無効な移動を引き起こす可能性があります。 

もう 1 つのエッジ ケースは、杭にすでに正しいタイプのみが含まれている場合です。```
1
3
1 1
2 2
3 3
```構成はすでに解決されているため、回答は空でもかまいません。 現在の状態を確認せずに常にセットアップ移動を実行するソリューションはまだ機能する可能性がありますが、移動が無駄になり、大規模なケースでは制限を超える可能性があります。 

重要なのは、石を一時的に集めてから、積み重ねの順序を尊重しながら正しい山を再構築することです。

 ## アルゴリズムのチュートリアル

 1. すべての山をスタックとして読み取ります。 入力では石が上から下にリストされるため、最後の要素が常に現在の先頭になるように、石を内部的に逆の順序で保存します。 
2. 山からすべての石を移動します`2`を通して`M`山の中へ`1`。 これにより、すべての石を含む 1 つの作業用の山が作成されます。 それぞれの動きは答えに記録されます。 
3.積み上げながら`1`まだ石があるので、上部の石を調べてください。 石に種類がある場合`1`または`2`、それを山に移動します`2`。 それ以外の場合は、今後の操作で邪魔される必要がないため、それを最後の山に直接移動します。 
4.積み上げながら`2`まだ石があるので、一番上の石を調べてください。 移動タイプ`1`石を山に戻す`1`、まだ一時ストレージから分離する必要があるためです。 移動タイプ`2`積み上げる石`3`、一時的な場所として使用されます。 
5. 山の頂上にいる間`3`タイプです`2`石、山に戻します`2`。 このステップの後、積み上げます`2`タイプのみが含まれます`2`石。 

なぜ効果があるのか:

 重要な不変条件は、ステップ 3 の後、仮杭を除くすべての杭には正しいタイプの石のみが含まれるということです。 未解決の石は種類だけです`1`そして`2`、それらは一時保管に使用される山だからです。 ステップ 4 でこれら 2 つのタイプを分離し、ステップ 5 で一時タイプを削除します。`2`山から出た石`3`。 すべての石は最終的にそのタイプに一致する杭に配置されるため、最終的な構成は正確になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    data = input().split()
    if not data:
        return
    n, m = map(int, data)

    piles = [[] for _ in range(m + 1)]

    for i in range(1, m + 1):
        row = list(map(int, input().split()))
        cnt = row[0]
        stones = row[1:]
        piles[i] = stones[::-1]

    ans = []

    def move(a, b):
        ans.append((a, b))
        piles[b].append(piles[a].pop())

    for i in range(2, m + 1):
        while piles[i]:
            move(i, 1)

    while piles[1]:
        t = piles[1][-1]
        if t == 1 or t == 2:
            move(1, 2)
        else:
            move(1, t)

    while piles[2]:
        t = piles[2][-1]
        if t == 1:
            move(2, 1)
        else:
            move(2, 3)

    while piles[3] and piles[3][-1] == 2:
        move(3, 2)

    out = [str(len(ans))]
    out.extend(f"{a} {b}" for a, b in ans)
    print("\n".join(out))

if __name__ == "__main__":
    solve()
```入力変換は、最初の微妙な実装の詳細です。 ステートメントは上から下に石を与えるので、すべての山を反転すると、`pop()`一定時間内に一番上の石にアクセスします。 

の`move`ヘルパーは、操作の記録とシミュレートされたスタックの更新の両方を担当します。 この 2 つの動作を一緒に行うことで、出力シーケンスと内部状態が一致しないミスを防ぐことができます。 

最初のループでは石を収集するだけで、それらを分類しようとはしません。 次の 2 つのフェーズでは、実際の分離が実行されます。 杭の特殊な取り扱い`1`、`2`、 そして`3`これらは一時的に間違った石を含む唯一の山であるため、これは意図的なものです。 

Python の整数には制限がないため、オーバーフローの心配はありません。 主な制限は保存された手の数です。各フェーズで各石が最大 1 回動くため、これは線形です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 ## 特殊なケース

 すべての石がすでに目的の山にある場合でも、すべての石を山に移動するため、アルゴリズムは引き続き機能します。`1`そしてそれらを再構築することは常に有効です。 出力には不必要な手が含まれていてもよいため、正確さは最初の配置を維持するかどうかには依存しません。 

タイプの石の場合`1`または`2`他の石の下に埋もれている場合、アルゴリズムはそれに直接アクセスしようとしません。 まず、ブロックしている石を上から取り除きます。これがまさにすべての石を山に集める理由です。`1`便利です。 

石が多い場合、手数は制限されたままになります。 各フェーズは、現在作業中の山にある石のみをスキャンし、すでに完成した山を繰り返し検索するフェーズはありません。 これにより、構造が出力制限内に保たれます。
