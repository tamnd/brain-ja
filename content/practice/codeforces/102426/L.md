 ## 解決策
 ## 問題の理解

 あります`n`から番号が付けられた宝くじ`1`に`n`。 その通り`m`そのうちの 1 つは幸運であり、その位置は入力で与えられます。 Miamiao は 1 つの間隔を選択します`[l, r]`、それぞれの`n(n+1)/2`可能な間隔は同様の可能性であり、その間隔内のすべてのチケットを購入します。 

選択した間隔に正確に含まれる確率が必要です。`k`幸運のチケット。 確率は有理数であるため、必要な出力は、その分子にその分母のモジュロの逆モジュラを乗じたものになります。`998244353`。 

この問題の便利な部分は、すべての間隔の内容を個別に検査する必要がないことです。 上限`n <= 10^6`さえ十分な大きさです`O(n^2)`列挙は不可能です。 すでにあります

 [
 \frac{n(n+1)}2
 ]

 に達する間隔`500000500000`いつ`n = 10^6`。 間隔ごとに一定の作業を実行するアルゴリズムは、すでに制限時間をはるかに超えています。 必要なのは`O(n)`または`O(m)`スタイルのソリューション。 

いくつかの境界ケースは誤って処理されやすいものです。 いつ`k = 0`、ラッキー チケットがまったく含まれていない間隔をカウントしているため、ラッキー ポジション自体が配列を独立したストレッチに分割する必要があります。 たとえば、```
3 1 0
2
```有効な間隔は次のとおりです`[1,1]`そして`[3,3]`、したがって、確率は次のようになります。`2/6 = 1/3`、そのモジュラー表現は`332748118`。 少なくとも 1 つのラッキー チケットを含むインターバル用にのみ設計されたメソッドは、誤ってゼロを返したり、インターバルにタッチしたチケットをカウントしたりする可能性があります。`2`。 

その反対の極端は、`k = m`。 例えば、```
3 2 2
1 3
```両方のラッキーチケットを含む間隔が必要です。 のみ`[1,3]`動作するので、答えは次のとおりです`1/6 = 166374059`。 境界計算を不用意に行うと、ラッキー ブロックが最初のチケットで始まるか、最後のチケットで終わる区間を見逃す可能性があります。 

ラッキーチケットが境界を占有することもあります。 と```
3 1 1
1
```成功間隔は`[1,1]`、`[1,2]`、 そして`[1,3]`、与える`3/6 = 1/2 = 499122177`。 最初の幸運なチケットの前に常に通常のチケットがあると仮定した解決策は、このケースを誤ります。 

チケットは 1 つのラッキー チケットのみであるため、重複したラッキー ポジションは有効な入力ではありません。 したがって、「すべてが等しい値」テストは法的に存在できません。 意味のある極端なケースは、すべてのチケットが幸運であるということです。`1 2 3 4`。 

## アプローチ

 最も直接的な解決策は、すべての間隔を列挙することです。`[l,r]`。 プレフィックス合計を前処理すると、`prefix[i]`内のラッキーチケットの数です`1..i`、次にラッキーチケットの数`[l,r]`は`prefix[r] - prefix[l-1]`, そのため、各間隔を一定時間で確認できます。 問題は間隔の数です。 のために`n = 10^6`、 がある`500000500000`したがって、この最適化されたブルート フォースでも、およそ 5 兆回の間隔チェックが必要になります。 間隔自体をスキャンする実装はさらに悪くなり、次のような状態になります。`O(n^3)`最悪の場合。 

必要な構造は、すべての間隔のセットよりもはるかに小さいです。 適切なエンドポイントごとに`r`の選択肢がいくつあるのかを考えてみましょう。`l`せいぜい与える`x`のラッキーチケット`[l,r]`。 ラッキーチケットの数は次の場合にのみ増加できるため、`l`左に移動するか、`r`右に移動すると、2 ポインター ウィンドウは線形時間で左端の有効な開始位置を維持できます。 

させて`A(x)`最大で次の値を含む間隔の数になります。`x`幸運のチケット。 正確に含まれるすべての間隔`k`ラッキーチケットの数え方`A(k)`, ただし、それはカウントされません`A(k-1)`。 その結果、

 [
 \text{正確に}k=A(k)-A(k-1)。 
]

 固定右エンドポイントの場合`r`、 仮定する`L_k`は、次のような最小の左端点です。`[L_k,r]`多くても含まれる`k`幸運のチケット。 次に、からのすべての左端点`L_k`を通して`r`は「最大でも`k`「条件、与える」`r-L_k+1`間隔。 

同様に、次の場合も`L_{k-1}`は最大でも対応する境界です`k-1`ラッキーチケット、あります`r-L_{k-1}+1`そういった間隔。 彼らの違いは、

 [
 (r-L_k+1)-(r-L_{k-1}+1)=L_{k-1}-L_k。 
]

 だから、あらゆる人にとって`r`、で終了する間隔の数`r`まさに`k`ラッキーチケットは単純に`L_{k-1}-L_k`。 

特別な場合`k = 0`はさらに簡単です。 ラッキーチケットを含まない間隔の数だけが必要です。 連続する 2 つのラッキー チケットの間、ギャップの内側に完全にあるすべての間隔には、ラッキー チケットが含まれません。 隙間に長さがある場合`g`、貢献します`g(g+1)/2`間隔。 チケットのスキャン中に 1 つのポインターで同じ数量を直接蓄積できます。 

有利な間隔を数えた後、間隔の合計数で割ります。 

[
 \frac{n(n+1)}2.
 ]

 係数は素数であり、`n < 998244353`、だからどちらでもない`n`または`n+1`は係数で割り切れます。 したがって、分母は可逆であり、フェルマーの小定理はその逆数を次のように与えます。`denominator^(MOD-2)`モジュロ`998244353`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | プレフィックス合計によるブルート フォース |`O(n²)`|`O(n)`| 遅すぎる |
 | ツーポインタのカウント |`O(n + m)`|`O(n)`| 承認済み |

 ## アルゴリズムのチュートリアル

 1.読む`n`、`m`、 そして`k`、バイナリ配列を作成します`lucky`どこ`lucky[x] = 1`まさにそのときのチケット`x`幸運です。 チケットごとに 1 バイトのみを保存することで、たとえチケットごとにメモリ使用量が少なく抑えられます。`n = 10^6`。 
2. もし`k = 0`、左から右にスキャンし、ラッキー チケットを含まない現在のストレッチの先頭を維持します。 いつでもチケット`r`は幸運ではありません。前のラッキー チケットの後のすべての開始点は、次で終了する有効な間隔を与えます。`r`。 同様に、現在のゼロのみのストレッチに長さがある場合、`g`、貢献します`g`右端点が 1 位置だけ拡張されたときの新しい間隔。 これにより、すべてのゼロラッキー間隔がカウントされます。`O(n)`時間。 
3. もし`k > 0`、2 つのスライディング ウィンドウを維持します。 最初のウィンドウには最大でも次の内容が含まれます`k`ラッキーチケット、その左側の境界は`left_k`。 2 番目には最大でも次の内容が含まれます`k-1`幸運のチケット、境界線付き`left_less`。 
4. 新しい右エンドポイントを処理する場合`r`、 追加`lucky[r]`両方の窓に。 最初のウィンドウに次の内容が含まれている場合、`k`ラッキーチケット、移動`left_k`ウィンドウが再び有効になるまで。 2 番目のウィンドウについても、最大で次のものが含まれるまで同じ操作を行います。`k-1`幸運のチケット。 
5. あります`r-left_k+1`で終わる間隔`r`せいぜい`k`ラッキーチケットと`r-left_less+1`最大間隔`k-1`。 彼らの違いは、`left_less-left_k`、これはまさに次で終わる数字です。`r`まさに`k`幸運のチケット。 この値を有利なカウントに加算します。 
6. 可能な間隔の合計数を次のように計算します。`n(n+1)/2`。 必要な確率は`favorable / total`、だから乗算してください`favorable`モジュラー逆関数により`total`。 
7. 結果のモジュロを削減します。`998244353`そしてそれを印刷します。 

2 ポインター方式の背後にある不変条件は、すべての右エンドポイントの後に次のことが行われることです。`r`、`left_k`間隔が次で終了する最小の開始位置です。`r`多くても含まれる`k`幸運のチケット。 したがって、以前のすべての開始`left_k`ラッキーチケットが多すぎますが、すべてのスタートは`left_k`以降が有効です。 同じ性質が当てはまります`left_less`そして`k-1`。 2 つの有効な範囲を減算すると、以下の間隔をすべて削除します。`k`幸運のチケットとまさにそれらを残します`k`。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

def solve(data=None):
    if data is None:
        data = sys.stdin.buffer

    n, m, k = map(int, data.readline().split())

    lucky = bytearray(n + 1)
    for x in map(int, data.readline().split()):
        lucky[x] = 1

    if k == 0:
        favorable = 0
        length = 0

        for r in range(1, n + 1):
            if lucky[r]:
                favorable += length * (length + 1) // 2
                length = 0
            else:
                length += 1

        favorable += length * (length + 1) // 2

    else:
        left_k = 1
        left_less = 1
        cnt_k = 0
        cnt_less = 0
        favorable = 0

        for r in range(1, n + 1):
            value = lucky[r]

            cnt_k += value
            while cnt_k > k:
                cnt_k -= lucky[left_k]
                left_k += 1

            cnt_less += value
            while cnt_less > k - 1:
                cnt_less -= lucky[left_less]
                left_less += 1

            favorable += left_less - left_k

    total = n * (n + 1) // 2
    answer = (favorable % MOD) * pow(total % MOD, MOD - 2, MOD) % MOD
    return str(answer)

if __name__ == "__main__":
    print(solve())
```最初の部分のビルド`lucky`として`bytearray`。 100 万の整数からなる Python リストは必要以上に多くのメモリを消費しますが、バイト配列はチケットごとにおよそ 1 バイトを使用します。 入力により、リストされた各ポジションが有効なチケット番号であることが保証されるため、設定`lucky[x] = 1`で十分です。 

のために`k = 0`、`length`現在の連続した不運チケットの長さです。 ラッキーチケットが出現すると、そのストレッチは終了し、貢献します`length * (length + 1) // 2`間隔。 計算をトリガーするためのラッキー チケットがその後にないため、最後のストレッチはループの後に追加する必要があります。 

のために`k > 0`、`left_k`そして`left_less`は独立したポインタです。 ラッキー チケットの数に異なる上限が適用されるため、これらをマージしないでください。 ウィンドウが無効になると、コードは必要な境界が復元されるまで、左側からチケットを削除します。 

インデックス作成は次から始まります`1`チケット自体に番号が振られているため、`1`に`n`。 これも次のような表現になります`r - left + 1`可能な開始位置の数を直接表します。 以来`lucky`長さがある`n + 1`、アクセス中`lucky[r]`そして、左に移動するポインタが範囲外に出ることはありません。 

すべてのカウントは Python 整数を使用して実行されるため、次のような積が得られます。`n(n+1)`また、有利な間隔の数がオーバーフローすることはありません。 モジュロ演算は最後の確率計算まで延期されるため、組み合わせの解釈が明確になります。 

入力は読み取られます`data.readline()`だから同じ`solve`関数はテスト ハーネスから呼び出すこともできます。 問題にはテスト ケースが 1 つだけあるため、外側のテスト ケース ループは必要ありません。
