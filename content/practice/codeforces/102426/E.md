 ## 解決策
 ## 問題の理解

 を取り揃えております。`n`正の整数。 すべてのインデックスのペア`l <= r`は 1 つの連続した部分配列を定義し、その値は次のすべての要素の合計です。`l`を通して`r`。 まさにあります`n(n+1)/2`異なる部分配列は魔法の異なる結果に対応するため、等しい合計は別々にカウントされます。 

課題は、`k`-これらすべての合計を非降順でソートした後の最小の部分配列の合計。 たとえば、`2 3 1 4`、10 個の部分配列によりソートされたシーケンスが生成されます。`1, 2, 3, 4, 4, 5, 5, 6, 8, 10`、 それで`k = 6`与える`5`。 

配列の長さは次のとおりです`10^5`。 つまり、約`5 * 10^9`サブアレイ。 サブ配列ごとに一定の作業を実行するアルゴリズムでさえすでに遅すぎ、メモリ制限の下ではすべてのサブ配列の合計を明示的に格納することは不可能です。 要素は次のように大きくできます。`10^9`、したがって、部分配列の合計は約に達する可能性があります`10^14`、固定幅整数を使用する言語では 64 ビット整数演算も必要です。 

一人ひとりのポジティブな姿勢`ai`が重要な構造上の制約です。 その結果、プレフィックスの合計は厳密に増加するため、線形時間で指定された値以下の部分配列の合計がいくつあるかを数えることができます。 積極性がなければ、2 つのポインタをカウントする議論は機能しません。 

実装を静かに破壊する可能性のある境界ケースがいくつかあります。 のために`n = 1`、考えられる唯一の結果は単一の要素です。 例えば、`1 1`に続く`7`答えがあります`7`; 誤ってサブ配列の空の範囲を検索するコードは、ここで失敗する可能性があります。 

等しい部分配列の合計は多重度を使用してカウントする必要があります。 のために`3 4`に続く`2 2 2`、ソートされた合計は次のようになります。`2, 2, 2, 4, 4, 6`、したがって、答えは次のとおりです`4`。 結果を個別の値として扱うソリューションでは、考えられる結果が 3 つだけであると誤って認識されてしまいます。 

可能な最小および最大のランクにも意味があります。 のために`3 1`に続く`1 5 2`、最小の部分配列の合計は`1`、その間、`3 6`答えは配列全体の合計です。`8`。 カウント関数で厳密な不等式を使用する二分探索では、どちらの境界でも 1 ずつずれる可能性があります。 

## アプローチ

 直接的なアプローチは、すべての連続するサブ配列を列挙することです。 左側の端点ごとに、右側の端点を一度に 1 位置ずつ拡張し、現在の合計を維持して、次のすべての部分配列の合計を求めます。`O(1)`追加の作業。 これは正しいです。なぜなら、どのペアも`(l, r)`は 1 回だけ表示されます。 がある`n(n+1)/2`そのようなペア、つまり`5,000,050,000`いつ`n = 100000`。 それだけ多くの値を生成するだけではすでに期限をはるかに超えており、それらを並べ替えると状況はさらに悪化します。 

ブルートフォースアプローチが機能するのは、コレクションを明示的に構築するためです。`k`- 番目の要素が必要です。 問題は、コレクション自体のサイズが 2 次であることです。 視点を変えると効果的なのは、すべての部分配列の合計を求めるのをやめ、代わりに数を数える質問をすることです。`x`、和を持つ部分配列の最大数`x`?

 カウント操作が高速になると、元の選択問題は二分探索になります。 計算できれば`count(x)`、部分配列の合計の数は以下になります。`x`、 それから`count(x)`単調です。 小型用`x`、適合する合計はほとんどありません。 として`x`増加すると、カウントは増加するだけです。 答えはまさに最小です`x`誰のために`count(x) >= k`。 

計算するには`count(x)`、プレフィックスの合計を定義します`p[0] = 0`そして`p[i] = a1 + a2 + ... + ai`。 

部分配列の合計`l..r`は`p[r] - p[l-1]`。 すべての配列要素が正であるため、`p`厳密に増加しています。 固定右プレフィックスインデックスの場合`r`、必要です`p[r] - p[i] <= x`これは以下と同等です`p[i] >= p[r] - x`。 

プレフィックスの合計はすでにソートされているため、最初の適切なプレフィックスを見つけることができます。`i`すべての二分探索によって`r`、与える`O(n log n)`数えています。 もっと良くできるはずです。 として`r`右に移動し、`p[r]`増加するため、しきい値は`p[r] - x`も増えます。 最初の有効な`i`決して後退することはできません。 したがって、単一の移動ポインターですべての有効な開始がカウントされます。`O(n)`時間。 

外部二分探索のニーズ`O(log S)`反復、ここで`S`配列の合計です。 以来`S <= 10^14`、これは 50 回未満の反復です。 結果として生じる複雑さは、`O(n log S)`、これは実用的です`n = 10^5`。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n² log n) | O(n²) | 遅すぎる |
 | 最適 | O(n log S) | O(n) | 承認済み |

 ここ`S`は配列全体の合計を表します。 

## アルゴリズムのチュートリアル

 1. プレフィックス合計配列を構築する`p`。 セット`p[0] = 0`、 それから`p[i] = p[i-1] + a[i]`。 だって全部`ai`が正の場合、プレフィックスの合計は厳密に増加しています。 
2. 関数を定義する`count(x)`合計が最大である連続する部分配列の数を返します。`x`。 For each right endpoint represented by prefix index`r`、すべてを数える必要があります`i < r`満足のいく`p[r] - p[i] <= x`。 
3. 条件を次のように書き換えます。`p[i] >= p[r] - x`。 ポインタを維持する`left`この条件を満たす最初のプレフィックス合計に変換します。 その間`left < r`そして`p[left] < p[r] - x`、 前進`left`。 
4. ポインタが停止すると、すべてのプレフィックスのインデックスが作成されます。`left`を通して`r-1`で終わる有効な部分配列を与えます`r-1`。 がある`r - left`その数をカウントに追加します。 

ポインタを後方に移動する必要はありません。 いつ`r`増加すると、しきい値が増加します`p[r] - x`プレフィックスの合計が増加しているため、増加します。 したがって、すでに小さすぎるプレフィックス合計は、後で有効になることはありません。 
5. 間の答えを二分探索します。`1`そして`p[n]`、配列の合計。 中間点に向けて`mid`、計算する`count(mid)`。 カウントが少なくとも`k`、 それから`mid`を含むのに十分な大きさです`k`-番目に小さい合計なので、左半分を検索します。 それ以外の場合は、右半分を検索します。 
6. 二分探索が終了すると、カウントが到達した最小値が下限になります。`k`。 その値を出力します。 

### なぜ効果があるのか

 固定ごとに`x`、カウント関数は、考えられるすべての正しいエンドポイントを考慮します。 そのエンドポイントでは、プレフィックスの合計が増加しているため、有効な左側のプレフィックス インデックスが以前のプレフィックス インデックスの 1 つのサフィックスを形成します。 移動ポインタはそのサフィックスの最初のメンバーを識別するため、`r - left`そこで終わるすべての有効なサブ配列を正確にカウントします。 したがって`count(x)`は正確に最大でも部分配列の合計の数です`x`。 

述語`count(x) >= k`増加するため単調です`x`追加のサブ配列の合計を大きすぎるものから有効なものに変えることしかできません。 したがって、二分探索では最小値が見つかります。`x`少なくとも含む`k`部分配列の合計。 部分配列の合計は整数であるため、その値は正確に`k`- 番目に小さい合計。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    a = list(map(int, input().split()))

    prefix = [0] * (n + 1)
    for i in range(1, n + 1):
        prefix[i] = prefix[i - 1] + a[i - 1]

    total = prefix[n]

    def count_at_most(x):
        left = 0
        count = 0

        for right in range(1, n + 1):
            threshold = prefix[right] - x

            while left < right and prefix[left] < threshold:
                left += 1

            count += right - left

            if count >= k:
                return count

        return count

    lo = 1
    hi = total

    while lo < hi:
        mid = (lo + hi) // 2

        if count_at_most(mid) >= k:
            hi = mid
        else:
            lo = mid + 1

    print(lo)

if __name__ == "__main__":
    solve()
```プレフィックス構築では、最初の合計が格納されます。`i`位置の要素`i`。 余分なゼロは、`prefix[0]`空のプレフィックスを表します。インデックスで始まるサブ配列に必要です。`1`。 

内部`count_at_most`、`right`終了プレフィックスインデックスです。 対応するサブ配列は、プレフィックス インデックスの後に始まります。`left`。 不平等`prefix[left] >= prefix[right] - x`これは、結果として得られる部分配列の合計が以下を超えないという条件と正確に一致します。`x`。 

中の状態は、`while`ループは使用します`<`、 ない`<=`。 もし`prefix[left] == prefix[right] - x`、結果の部分配列は正確に合計を持ちます`x`そして数えなければなりません。 等価性を除外すると、関数は厳密に以下の合計のカウントに変わります。`x`、二分探索の答え​​がシフトします。 

の`left < right`この条件により、空の部分配列を表すことになる同じプレフィックス インデックスを両側で使用することができなくなります。 すべての有効なサブ配列には、次のようなプレフィックス インデックスの異なるペアがあります。`left < right`。 

早期復帰のとき`count >= k`正確性を保つためには必要ありませんが、二分探索でこれがすでにわかっている場合は、残りのプレフィックスの合計をスキャンする必要がなくなります。`x`十分な大きさです。 Python の整数は 64 ビットの範囲を超える合計を自動的に処理しますが、実際の制約では次の値のみが必要です。`10^14`。 

二分探索では、`lo = 1`すべての配列要素が正であるため、空でないすべての部分配列は正の合計を持ちます。`hi = total`配列全体自体がその合計を持ち、それが可能な最大の部分配列の合計であるため、これは有効です。

 と`n <= 10^5`そして`S <= 10^14`の場合、二分探索で実行されるカウント パスは 50 回未満です。 各パスは線形であるため、アルゴリズムは数十億のサブ配列操作ではなく、数百万のポインター操作のみを実行します。 プレフィックス配列も線形メモリを使用します。これは、ある程度の注意が必要な場合に限り、Python で規定されている 64 MB の制限内に快適に収まります。 この実装では、入力配列とプレフィックス配列のみが保存され、部分配列の合計の二次コレクションは保存されません。 

## テストケース```python
import sys
import io

def solve_data(data: str) -> str:
    old_stdin = sys.stdin
    old_stdout = sys.stdout

    sys.stdin = io.StringIO(data)
    sys.stdout = io.StringIO()

    n, k = map(int, sys.stdin.readline().split())
    a = list(map(int, sys.stdin.readline().split()))

    prefix = [0] * (n + 1)
    for i in range(1, n + 1):
        prefix[i] = prefix[i - 1] + a[i - 1]

    def count_at_most(x):
        left = 0
        count = 0

        for right in range(1, n + 1):
            threshold = prefix[right] - x

            while left < right and prefix[left] < threshold:
                left += 1

            count += right - left

            if count >= k:
                return count

        return count

    lo, hi = 1, prefix[n]

    while lo < hi:
        mid = (lo + hi) // 2
        if count_at_most(mid) >= k:
            hi = mid
        else:
            lo = mid + 1

    result = str(lo)

    sys.stdin = old_stdin
    sys.stdout = old_stdout
    return result

# Minimum-size input
assert solve_data("1 1\n7\n") == "7", "single element"

# All values equal, with duplicate sums
assert solve_data("3 4\n2 2 2\n") == "4", "duplicate sums"

# Smallest possible rank
assert solve_data("4 1\n5 1 3 2\n") == "1", "k = 1"

# Largest possible rank, which must be the whole-array sum
assert solve_data("4 10\n5 1 3 2\n") == "11", "k = n(n+1)/2"

# The expected value can be computed directly without enumerating subarrays.
n = 100000
a = "1 " * (n - 1) + "1"
k = n * (n + 1) // 2
expected = n
assert solve_data(f"{n} {k}\n{a}\n") == str(expected), "maximum n"

 ## 特殊なケース

 単一要素の場合、入力`1 1`に続く`7`プレフィックスの違いは 1 つだけです。`7 - 0 = 7`。 数えているうちに、`right = 1`そして`left = 0`, したがって、カウントは次のようになります`1`。 二分探索には、`lo = hi = 7`、すぐに戻ります`7`。 

合計が重複する場合は、次の点を考慮してください。`3 4`に続く`2 2 2`。 で`x = 3`、ポインタは 3 つの長さ 1 の部分配列を正確にカウントし、次のようになります。`3`、以下にあります`k = 4`。 で`x = 4`、長さ 2 の 2 つの部分配列も有効になるため、カウントは次のようになります。`5`。 したがって、少なくとも 4 つの結果がある最小のしきい値は次のようになります。`4`。 このアルゴリズムは合計を重複排除しないため、多重性は自然に維持されます。 

可能な限り小さいランクの場合、`4 1`に続く`5 1 3 2`最小の部分配列合計があります`1`。 述語`count(x) >= 1`最初に真になるのは`x = 1`。 二分探索では、カウントが次の値に達するたびに下位半分が保持されます。`k`、つまり、まさに次のようになります。`1`。 

可能な最大のランクについては、`4 10`に続く`5 1 3 2`10 番目と最後の部分配列の合計を求めます。 すべての要素が正であるため、完全な配列の合計は最大になります。`5 + 1 + 3 + 2 = 11`。 で`x = 10`、10 個のサブ配列すべてが条件を満たすわけではありませんが、`x = 11`、10人全員がそうします。 したがって、二分探索では次の結果が返されます。`11`。 

最大サイズのオールワンテストには、`100000`要素と`k = n(n+1)/2`、したがって、要求された結果は最大の部分配列の合計になります。`100000`。 カウント関数は、約 50 億個のサブ配列を構築することはありません。 そのポインタは、バイナリ検索の反復ごとに 1 回プレフィックスの合計を単純に進めます。これは、考えられる結果の 2 次数が 2 次アルゴリズムを強制しない理由を示しています。
