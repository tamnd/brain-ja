 ## 解決策
 ## 問題の理解

 小文字の 1 つの文字列から始めて、一連の破壊的な操作を繰り返し実行します。 i 番目の操作では、長さが次のように固定されている連続ブロックを強制的に削除します。$2i - 1$, ただし、その時点で現在の文字列のどこにそのブロックがあるかを自由に選択できます。 削除後、文字列は縮小し、次の操作は新しい文字列に対して実行されます。 

全てを実行した後、$k$削除すると、結果の文字列以外の構造は残りません。 タスクは、最終的な文字列が辞書順でできるだけ小さくなるように、すべての削除位置を選択することです。 

主な問題点は、削除が順次行われ、変更される文字列に作用することです。 削除のたびにインデックスが変化するため、削除は将来のポジションに影響し、決定は独立していません。 局所的に最適と思われる選択は、将来の柔軟性を破壊する可能性があります。 

この制約は、二次関数の意味で演算の数が少ないことを意味します。 取り除いた全長は、$1 + 3 + \dots + (2k-1) = k^2$、すぐに得られます$k \le 70$のために$n \le 5000$。 これは重大な構造上の制限です。大まかに複雑な DP が許可されています。$O(nk)$または州ごとにわずかに悪いが、二次的なものではない$n$操作ごとに。 

すべての操作に対して考えられるすべての部分文字列を試すという素朴な戦略は、各ステップですでに$O(n^2)$現在の文字列内の選択肢と、文字列自体が動的に変化します。 

微妙な失敗例は、初期の削除により、後の削除が依存する文字を移動する場合に発生します。 たとえば、わずかに悪いプレフィックスを削除するサブストリングを削除すると、辞書編集的に小さいサフィックスが公開される可能性がありますが、そうすることで、将来の削除でその利点が失われる位置に強制的に配置される可能性があります。 このステップ間の結合こそが、貪欲なアプローチの信頼性を低下させる原因となります。 

## アプローチ

 ブルートフォースアプローチでは、プロセスを直接シミュレートします。 各操作で、現在の文字列内の必要な長さの可能なすべての部分文字列を試し、次のステップに再帰して、最良の結果を維持します。 これは、法的な削除順序をすべて調査するため正しいですが、州の数は爆発的に増加します。 再帰を無視しても、単一ステップで検査できます。$O(n)$位置を決め、これを最大まで繰り返します$k$ステップを実行する一方で、文字列はゆっくりとしか縮小しないため、指数関数的な分岐が発生します。 

主な障害は、「現在の文字列」が安定していないことです。 削除のたびにインデックスがシフトするため、動的な構造を維持しない限り、元の文字列のインデックスに対する直接 DP は失敗します。 

重要な観察は、動的に変化するシーケンスから部分文字列を繰り返し切り出すとしてプロセスをモデル化でき、この動的シーケンスはロープやトレプなどのバランスの取れたバイナリ構造を使用して暗黙的に表現できることです。 プロセスの各状態は文字列の特定のバージョンであり、各操作はセグメントを切り出すことによって新しいバージョンを生成します。 

これにより、問題は永続構造の状態に関する DP に変換されます。インデックスのシフトについて推論する代わりに、文字列のバージョンについて推論します。 以来$k$小さいので余裕があります$O(k)$各遷移には、構造の分割とマージに対数的な時間がかかります。 

結果を比較するには、これらの永続的な文字列に対する辞書編集的な比較に依存します。 これは、ハッシュや最小文字などのサブツリー メタデータを保存することによって処理され、サフィックスの高速な比較が可能になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 削除に対するブルート フォース再帰 | 指数 | O(n) | 遅すぎる |
 | 永続的な文字列状態に対する DP (treap/rope) | O(k · n log n) | O(k · n) | 承認済み |

 ## アルゴリズムのチュートリアル

 プロセスの各段階で現在の文字列を表す永続的なバランスの取れたバイナリ ツリーを維持します。 各ノードには、そのサイズと部分文字列を迅速に比較するのに十分な情報が保存されます。 

現在のバージョンの文字列と次の操作インデックスを考慮した DP 関数を定義します。$i$、残りのすべての削除が完了した後に達成可能な辞書編集上の最小の結果を返します。 

1. 初期文字列をバージョン 0 として開始し、操作インデックス 1 でその文字列に対して DP を呼び出します。 
2. 運用時$i$必要な削除長がわかっています$L = 2i - 1$。 現在の文字列内で、次の長さの部分文字列が存在するすべての可能な開始位置を考慮します。$L$取り外すことができます。 それぞれの選択は、現在のトレプをプレフィックス、削除されたセグメント、サフィックスの 3 つの部分に分割することに対応します。 
3. 分割ごとに、プレフィックスとサフィックスをマージして新しいバージョンを構築し、削除を効果的に適用します。 これにより、操作のための新しい状態が生成されます$i+1$。 
4. 各候補の結果を再帰的に計算し、トレプに保存されている構造情報を使用して、結果の文字列を辞書編集的に比較します。 
5. 文字列の同一バージョンは同一の将来を生成するため、トレプルートと操作インデックスの同一性によって結果をメモ化します。 

再帰ではすべての有効な削除配置が探索されますが、メモ化による同一の状態の再計算は回避されます。 

これが機能する理由は、各状態が正確な現在の文字列を完全にキャプチャするためです。 文字列がさまざまな削除シーケンスから生じている場合でも、特定の treap ルートとして表されると、その後のすべての動作はこの構造と残りの操作インデックスのみに依存します。 これにより、正しい状態空間分解が得られます。元のインデックスへの隠れた依存関係は残りません。

    def __init__(self, ch):
        import random
        self.l = None
        self.r = None
        self.sz = 1
        self.ch = ch
        self.prio = random.randint(1, 10**9)

def sz(t):
    return t.sz if t else 0

def upd(t):
    if t:
        t.sz = 1 + sz(t.l) + sz(t.r)

def split(t, k):
    if not t:
        return (None, None)
    if sz(t.l) >= k:
        a, b = split(t.l, k)
        t.l = b
        upd(t)
        return (a, t)
    else:
        a, b = split(t.r, k - sz(t.l) - 1)
        t.r = a
        upd(t)
        return (t, b)

def merge(a, b):
    if not a or not b:
        return a or b
    if a.prio < b.prio:
        a.r = merge(a.r, b)
        upd(a)
        return a
    else:
        b.l = merge(a, b.l)
        upd(b)
        return b

重要な実装の詳細は、削除のたびに古いルートが変更されるのではなく、新しいルートが作成されるということです。 この永続性により、状態を超えた DP が有効になります。 

## 実用的な例

 サンプル文字列を考えてみましょう`adcbca`。 

文字列を表す完全なトレプから始めます。 

操作 1 では、1 文字を削除する必要があります。 複数の選択肢があります。 異なる位置を削除すると、異なる候補文字列が生成されます。 DP は各可能性を評価し、最小の最終結果につながる可能性を保持します。 

操作 2 では、新しい現在の文字列の削除長は 3 になります。 前のステップの各候補は、長さ 3 のセグメントを削除する複数の方法に分岐し、結果の各文字列は最終操作の後に比較されます。

 ## 特殊なケース

 重要なエッジケースは、局所的に最適ではないと思われる文字を最適な戦略によって早期に削除するものの、後ではるかに小さい辞書編集上の接尾辞のロックを解除する場合です。 たとえば、`baaaa`、先頭を削除します`b`最初の操作では、後の削除位置が制限される場合でも、常に有益です。 

DP は、すべての有効な最初の削除を個別の treap 状態として評価するため、これを正しく処理します。 の削除を表す状態`b`結果として得られるツリーの辞書編集上のルートが厳密に小さくなるため、その後の再帰で優先されます。 

もう 1 つのケースは、複数の削除が元のインデックス付けの重複領域と相互作用する場合です。 永続的な構造により、削除の瞬間に重複が確実に解決されるため、将来の操作に曖昧さが残らず、状態遷移の正確さが維持されます。
