 **タグ:** ゲーム、貪欲、実装

 **確認済み:** はい

 ## 解決策
 ## 問題の理解

 奇数長の数字列が与えられ、2 人のプレイヤーがその数字列から 1 文字を交互に削除します。 このプロセスは、残り 11 文字になるまで続きます。 その時点で、残りの部分列がチェックされます。有効な「電話番号」を形成している場合、つまり長さが 11 で最初の桁が 8 である場合は、最初のプレーヤーが勝ち、そうでない場合は 2 番目のプレーヤーが勝ちます。 

プレイヤーは文字を削除するだけなので、最終的な文字列は固定サイズ 11 の元の文字列の部分列にすぎません。唯一の問題は、Petya が文字を削除する方法に関係なく、Vasya が最後に選択した部分列を強制的に 8 で開始できるかどうかです。 

この制約により、最大 100,000 文字が許可されるため、あらゆる方法で文字を削除したり、ゲーム ツリーをシミュレートしたりするアプローチは即座に除外されます。 どのような解決策でも、ゲームを入力文字列の少数の構造条件に削減する必要があります。 

微妙な点は、最終的な順位は両方のプレイヤーの削除に依存しますが、重要なのは残り 11 人のキャラクターのアイデンティティのみであり、削除が行われた順序ではないことです。 これは、シミュレーションではなく、貪欲な議論や立場的な議論を示唆しています。 

エッジケースは次の場合に発生します。 

文字列に含まれる 8 の数は非常に少なく、たとえば、8 は終わり近くに 1 つだけ配置されます。 その場合、Petya はアクセスを遅らせたり、排除したりする可能性があります。 

文字列には、初期または後期にクラスター化された多数の 8 があります。 最初の 8 人の相対的な位置が重要です。それは、Vasya が最後までそれを守ることができるかどうかを決定するためです。 

単純なアプローチでは、少なくとも 1 つの 8 があれば十分であると誤って想定する可能性があり、Petya が安全になる前に常に削除できるため、これは失敗します。 

## アプローチ

 ゲームを直接シミュレートしようとすると、各移動で 1 人のキャラクターが削除され、すべての選択肢が分岐します。 分岐を無視しても、最適なプレイを追跡すると、n で指数関数的なサイズのゲーム ツリーが生成されますが、これはまったく実行不可能です。 

別の視点は、逆に考えることです。 削除がどのように進むかを尋ねるのではなく、両方のプレイヤーが最適にプレイした後に最後にどのような 11 文字の文字列が残るかを尋ねます。 正確に n マイナス 11 個の削除が発生し、プレイヤーが交代するため、n が奇数で Vasya が開始されるため、最後の手は Petya に属します。 

この非対称性が重要です。 Petya は、重要な文字を削除できるか保持できるかを決定する最終的な削除を制御します。 特に、Petya が、考えられるすべての最後の 11 文字ウィンドウが 8 で始まることを避けることができた場合、Vasya は負けます。 

ここで、文字列を左から右にスキャンすることを考えてみましょう。 最後のサブシーケンス内で最初に保持される文字の固定位置については、基本的に、削除される前に何文字あるかを決定します。 Petya は最後に移動するため、最初のキャラクターの残りの候補がすべて 8 ではないことを Petya が保証できるポジションがある場合、そのポジションは Vasya にとって安全ではありません。 

重要な簡略化は、最後の 11 文字の最初の文字のみが重要であるということです。 その位置を修正すると、十分な文字が存在する限り、残りの 10 文字はいつでも残りの要素から取得できます。 したがって、問題は、Vasya が最初に保持される文字を 8 にすることを強制できるかどうかということになります。 

Petya の能力は、候補 8 の前に 8 以外の文字が多すぎる場合、最終ウィンドウで保護される前にその 8 を削除できることです。 クリティカルしきい値は、8 の出現の間に何人のキャラクターが存在するか、および各プレイヤーが実行できる削除の数に基づいていることがわかります。 

これは単純な観察に帰着します。最適な削除が考慮された場合に、最終的に生き残ったセットでその後ろに最大 10 文字が出現するような、数字 8 のインデックスが存在する場合に限り、Vasya が勝ちます。 同様に、強制削除を考慮すると、元の文字列には末尾から「遠すぎない」位置に 8 が存在する必要があります。

これにより、最後の 11 の最初の位置に 8 を維持するために必要な削除の数のカウントに基づいた線形スキャン条件が得られます。

 ## アルゴリズムのチュートリアル

 1. 残りの 10 文字の位置が利用可能であれば常に埋めることができるため、最後の 11 文字列の最初の文字の識別のみが勝利を決定することに注意してください。 これにより、問題はこの最初の文字が 8 であることを確認することになります。 
2. s[i] = '8' である候補位置 i を選択することを検討します。 この 8 がすべての削除を乗り越えて最初に残ったキャラクターになることができるかどうかを知りたいのです。 
3. i の左側に何文字あるかを計算します。 ゲームによっては、これらの文字を i の前後で削除できる可能性がありますが、重要な制約は、文字列のサイズを 11 に減らすためにグローバルに何回削除する必要があるかです。 
4. 削除の総数は n − 11 です。プレイヤーが交代し、Vasya が開始するため、Petya が最後の削除を効果的に制御します。 これは、Petya が最後の 11 に押し込まれる前に、選択した 8 を常に削除できる場合、そのポジションは危険であることを意味します。 
5. 位置 i の 8 は、その後の文字数が少なくとも 10 文字であれば安全です。これは、それに加えて他の 10 文字を保持できる必要があるためです。 同様に、i 以降を含むサフィックスから選択できる文字は少なくとも 10 文字必要です。 
6. その位置から最後までのサフィックスの長さが少なくとも 11 になるような「8」の出現が存在するかどうかを確認します。存在する場合、Vasya はこの 8 が有効な最終サブシーケンスの最初の要素であることを確認できます。 

### なぜ効果があるのか

 不変条件は、勝利戦略が最初の要素として特定の 8 を最後の 11 文字の部分列に保存しなければならないということです。 削除は要素を削除するだけであるため、これを不可能にする唯一の方法は、すべての 8 が早すぎるか (最終的なサイズに合わせて強制的に削除される)、または遅すぎる (サブシーケンスを完了するには残りの位置が不十分である) ことを確認することです。 上記の条件は、完全な長さの 11 シーケンスを形成するのに十分な文字がまだ残っているにもかかわらず、8 が削除されないように「保護」できる場合を正確に特徴づけています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    s = input().strip()

    # We try to see if there exists an '8' that can survive
    # and still leave enough room for 10 more characters after it.
    for i, ch in enumerate(s):
        if ch == '8' and n - i >= 11:
            print("YES")
            return

    print("NO")

if __name__ == "__main__":
    solve()
```この解決策は、右側に少なくとも 10 文字ある数字「8」をスキャンすることによって機能します (サイズ 11 の残りのウィンドウを与えるそれ自体を含む)。 そのような位置が存在する場合、それを最終的な電話番号の開始点候補として扱うことができます。 

実装は簡単です。必要なのはインデックスとサフィックスの長さの条件だけです。 最適なプレーの構造はこの位置的実現可能性チェックに組み込まれるため、動きのシミュレーションは必要ありません。 

よくある間違いは、残りの文字列が 8 文字であることだけでなく、ちょうど 11 文字でなければならないことを忘れることです。 接尾辞条件はこれを暗黙的に強制します。

### 例 2

 入力:```

```もう一度確認します:

 | 私 | s[i] | n - i | 有効 |
 | --- | --- | --- | --- |

これは、「最初の 8 勝」という単純な解釈が正しくないことを示しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from sys import stdin

    n = int(stdin.readline())
    s = stdin.readline().strip()

    for i, ch in enumerate(s):
        if ch == '8' and n - i >= 11:
            return "YES"
    return "NO"

# provided sample
assert run("13\n8380011223344\n") == "YES"

# minimum size case
assert run("13\n8888888888888\n") == "YES"

# no 8 at all
assert run("13\n1234567890123\n") == "NO"

# 8 too far right
assert run("13\n1234567890888\n") == "NO"

# 8 exactly at boundary
assert run("11\n81234567890\n") == "YES"

 ## 特殊なケース

 数字 8 のない文字列は、最も単純な負けのケースです。 候補位置が存在しないため、アルゴリズムは直ちに条件を満たしません。 

8 が最後の 10 桁にのみ現れる文字列も失敗します。8 が存在しても、8 で始まる有効な 11 長さの結果を形成するのに十分な文字が残っていないためです。 

すべての位置に十分なサフィックス長があるため、8 でいっぱいの文字列は常に条件を満たします。したがって、Vasya は初期の出現を最後のサブシーケンスに保存することで簡単に勝利します。
