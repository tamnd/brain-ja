 ## 解決策
 ## 問題の理解

 このタスクは、XOR 値に対する制約のシステムに取り組んでいるように見えますが、制約はエッジとノードに関して直接記述されません。 代わりに、それらは配列のセグメントに対する演算から生じており、グラフ問題に再解釈できます。 

まず、各操作が XOR を使用して連続セグメントを変更する配列のような構造から始めます。 重要な観察は、セグメント操作を配列の差分表現に対する制約に変換できるということです。 差分配列に切り替えると、各操作は 2 つの位置にのみ影響します。つまり、各操作は正確に 2 つの変数間の関係になります。 

この変換の後、各位置に必要な XOR 値があり、各エッジが両方のエンドポイントに寄与する値を割り当てる操作に対応するグラフのような構造が得られます。 問題は、すべてのノードについて、インシデントエッジ値の XOR が指定されたターゲットと一致するように、エッジに値を割り当てることになります。 

出力は、すべてのノード制約を満たすエッジ重みの完全な割り当て、または割り当てが存在しないという宣言のいずれかです。 

この制約は、ノードとエッジの数において少なくとも線形時間処理が必要であることを意味します。 すべての割り当てを試行したり、エッジのサブセットを反復処理したりする解決策は、エッジの数に応じて可能性の数が指数関数的に増加するため、直ちに不可能になります。 ノードごとに独立してシステムを解決しようとするアプローチでも、エッジがグラフ全体で制約を結合するため失敗します。 

接続コンポーネントのノード値の XOR 合計がゼロ以外である場合、微妙なエッジ ケースが発生します。 たとえば、コンポーネント内の 3 つのノードの値が 1、2、および 4 である場合、それらの XOR は 7 となり、ゼロ以外になります。 このような場合、すべてのエッジがちょうど 2 つのノードに寄与するため、割り当てがすべての制約を同時に満たすことはできません。つまり、コンポーネント全体にわたる XOR の合計が常に相殺される必要があることを意味します。 このグローバル条件を無視する単純なソルバーでも構築が試行され、一貫性のない結果が生成される可能性があります。 

グラフがツリーではない場合、別の障害モードが発生します。 サイクルが存在し、構築戦略を慎重に選択しない場合、エッジを再検討するときに任意の割り当てにより矛盾が生じる可能性があります。 このため、スパニング ツリーのような構造化された分解が不可欠です。 

## アプローチ

 直接的な試みでは、各エッジを変数として扱い、すべてのノードの XOR 方程式を満たす値を同時に割り当てようとします。 これは、フィールド GF(2) 上の線形方程式系になりますが、XOR 形式で記述されます。 理論的には、ガウス消去法を使用して直接解くことができます。 ただし、グラフ構造により、より単純な構築が可能になります。 

ブルート フォースの観点では、エッジに 1 つずつ値を割り当て、最後にすべてのノードの制約が満たされているかどうかを確認します。 これには、エッジの重みの組み合わせを試す必要があり、最悪の場合、エッジの数に応じて指数関数的に増加します。 ノード要件から得られる値を制限したとしても、ローカルでの決定によって不整合がグラフの遠くまで伝播し、後戻りが余儀なくされる可能性があります。 

重要な構造的洞察は、各エッジが各エンドポイントに 1 回ずつ、正確に 2 回寄与しているということです。 これは、接続されたコンポーネント内では、すべてのノード値の XOR がゼロでなければならないことを意味します。 この条件が成立すると、任意のグラフの観点から考えるのをやめ、その代わりに構造をスパニング ツリーに縮小することができます。これは、サイクルによって一貫性を超える自由が提供されないためです。

木では、葉から上に向かって問題を解決できます。 リーフ ノードには入射エッジが 1 つだけあるため、必要な XOR によってそのエッジの値が直接決まります。 エッジが修正されたら、リーフを削除し、その効果を隣接するリーフに伝播することができます。 このプロセスを繰り返すことであいまいさがすべて排除され、すべての制約が 1 回だけ満たされることが保証されます。

 ## アルゴリズムのチュートリアル

 1. 各エッジを 2 つのノードを接続する制約として解釈して、入力からノードとエッジのグラフを構築します。 各ノードは、インシデント エッジの重みの XOR に等しくなければならない必要な XOR 値を保持します。 
2. 接続されたコンポーネントごとに、すべてのノード値の XOR を計算します。 この XOR がゼロ以外の場合は、そのコンポーネントに対する有効な割り当てが存在しないと直ちに結論付けます。 これは、すべてのエッジが 2 つのノードに寄与するため、すべての寄与が合計でキャンセルされるという事実からわかります。 
3. コンポーネントが有効な場合は、コンポーネントのスパニング ツリーを抽出します。 これにより、ルートを除くすべてのノードが制約を解決できる親エッジを 1 つだけ持つ形式に構造が縮小されます。 
4. スパニング ツリーを任意にルート化し、一連のリーフを維持します。 リーフは、現在のツリー構造における次数 1 のノードです。 
5. ルートではないリーフ ノードを繰り返し取得し、その現在必要な XOR 値を読み取り、この値をその一意のインシデント エッジの重みとして割り当てます。 この割り当てにより、リーフの制約が即座に満たされることが保証されます。 
6. エッジを割り当てた後、ツリーからリーフを削除し、その値を近隣の要件に XOR 演算することによってその値を近隣に伝播します。 削除されたエッジは以前に両方のエンドポイントに寄与していたので、これにより正確さが維持されます。 
7. ルートだけが残るまでこのプロセスを続けます。 この時点で、グローバル XOR 条件により、ルートの要件が自動的に満たされることが保証されます。 

### なぜ効果があるのか

 この構築では不変条件が維持されます。つまり、各ステップで、残りの各ノードの XOR 要件が、残りのサブツリー内の未処理のエッジによって提供される必要がある XOR 寄与に等しいということです。 リーフを削除すると、正確に 1 つの自由度を使用して 1 つの制約が解決され、伝播ステップでは残りの構造の一貫性が維持されます。 すべてのエッジが 1 回だけ処理され、すべてのノード制約が 1 回だけ考慮されるため、最初の実現可能性チェック後に矛盾が生じることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    val = list(map(int, input().split()))
    
    g = [[] for _ in range(n)]
    edges = []
    
    for i in range(m):
        u, v = map(int, input().split())
        u -= 1
        v -= 1
        g[u].append((v, i))
        g[v].append((u, i))
        edges.append((u, v))
    
    vis = [False] * n
    ans = [0] * m
    
    from collections import deque
    
    for s in range(n):
        if vis[s]:
            continue
        
        # gather component
        comp = []
        stack = [s]
        vis[s] = True
        
        while stack:
            u = stack.pop()
            comp.append(u)
            for v, _ in g[u]:
                if not vis[v]:
                    vis[v] = True
                    stack.append(v)
        
        # check XOR condition
        x = 0
        for u in comp:
            x ^= val[u]
        
        if x != 0:
            print("NO")
            return
        
        # build parent structure via BFS tree
        parent = [-1] * n
        parent_edge = [-1] * n
        order = []
        
        dq = deque([s])
        parent[s] = s
        
        while dq:
            u = dq.popleft()
            order.append(u)
            for v, ei in g[u]:
                if parent[v] == -1:
                    parent[v] = u
                    parent_edge[v] = ei
                    dq.append(v)
        
        # process in reverse BFS (leaf-like removal)
        for u in reversed(order):
            if u == s:
                continue
            p = parent[u]
            ei = parent_edge[u]
            ans[ei] = val[u]
            val[p] ^= val[u]
        
        # root handled automatically
    
    print("YES")
    print(*ans)

if __name__ == "__main__":
    solve()
```コードはまずグラフを連結成分に分解します。 各コンポーネントについて、ノード値の XOR がゼロでなければならないという必要条件が検証されます。 これが失敗すると、関数は早期に終了します。 

実現可能性が確認された後、任意のノードをルートとする BFS スパニング ツリーを構築します。 親配列は、各ノード (ルートを除く) がエッジの重みを割り当てるために使用される親エッジを 1 つだけ持つツリー構造をエンコードします。 

BFS の逆順序は、リーフの削除をシミュレートします。 各ノードの値は、そのノードをその親に接続するエッジに割り当てられ、そのノードは直ちに満たされます。 次に、その値が XOR を使用して上方に伝播され、親の要件が更新されます。 

微妙な点ですが、変更します。`val`その場で。 子が処理されるにつれて残りの要件が蓄積されるため、これは不可欠です。 この伝播がないと、親ノードは残りの制約を正しく反映できません。

 ### 例 1

 チェーン内に 3 つのノードがある小さなコンポーネントを考えてみましょう。 

初期ノード値:`[3, 5, 6]`エッジ:`1-2`、`2-3`| ステップ | ノードが処理されました | エッジが割り当てられています | 使用される値 | 親の更新 |
 | --- | --- | --- | --- | --- |
 | 1 | 3 | (2,3) | 6 | val[2] ^= 6 |
 | 2 | 2 | (1,2) | 更新された val[2] | val[1] ^= val[2] |

 ノード 3 の処理後、エッジ (2,3) は 6 に固定され、ノード 2 の要件は次のようになります。`5 XOR 6 = 3`。 次に、ノード 2 がエッジ (1,2) = 3 を割り当て、ノード 1 が一致します。 

これは、リーフの削除によって制約がボトムアップでどのように自然に解決されるかを示しています。

 ## 特殊なケース

 エッジ ケースの 1 つは、各ノードが分離された完全に切断されたグラフです。 この場合、各ノードは独自のコンポーネントを形成し、XOR 条件は自明に満たされます。 このアルゴリズムは各ノードを独立して処理し、エッジを割り当てず、ただちに成功を返します。 

もう 1 つのケースは、単一サイクルのコンポーネントです。 BFS スパニング ツリーは、サイクルから 1 つのエッジだけを削除し、それをツリーに変換します。 リーフベースの再構成によってスパニング ツリー上の一貫性がすでに保証されているため、削除されたサイクル エッジは正確性を保つために必要ありません。 

最後のケースは、すべてのノード値がゼロの場合です。 BFS は引き続き実行されますが、割り当てられたすべてのエッジは重みが 0 になり、伝播によってすべての値が変更されないままになります。 XOR 制約はすべてのノードで簡単に満たされるため、出力は有効なままになります。
