 ## 解決策
 ## 問題の理解

 私たちは、算術値ではなく、その桁構造を通じて基本的に扱われる数値を扱っています。 任意の整数の場合\(x\)、その桁のマルチセットのみに依存する変換を繰り返し適用します。 順序、先頭のゼロ、位置の意味を気にするのではなく、各数字が何回出現するかだけを気にします。 

各クエリでは、この数字ベースの変換を一定回数繰り返し適用することについて推論するよう求められます。 数字から始める\(x\)、その桁から新しい数値を導き出し、このプロセスを繰り返します\(n\)回。 タスクは、変換が繰り返された場合に同じ桁マルチセットの動作を共有するすべての有効な開始番号にわたって、結果の値のプロパティを決定することです。 

重要な問題は、順序を忘れて桁数だけを保持すると、多くの異なる整数が同じ状態に崩壊してしまうことです。 この崩壊が単純なシミュレーションのコストを高くしている原因です。すべての整数を列挙することは、たとえ中程度の桁長であってもすぐに不可能になります。 

入力は複数のクエリを記述し、それぞれが固定数の Kaprekar のような数字マルチセット変換後の結果を要求します。 出力は、開始番号ごとに長い変換チェーンを再計算することなく、各クエリに効率的に応答する必要があります。 

複雑さの観点から見ると、暗黙的な状態空間は桁のマルチセットによって決定されます。 付きの番号の場合\(d\)桁数、個別のマルチセットの数は\(\binom{d+9}{9}\)で多項式に増加します。\(d\)しかし、十分に大きくなり、制約までの長さのすべての整数を単純に列挙することは不可能になります。 すべての値を反復するソリューション\(x\)または、各クエリを個別にシミュレートすると、桁の長さが一般的な Codeforce の制限に達すると時間制限を超えます。 

同じ桁のマルチセットを共有しているが値が異なる数値からは、微妙なエッジ ケースが発生します。 例えば、\(x = 102\)そして\(x = 210\)数値表現が異なっていても、桁数のみに依存する変換では同じように動作します。 数字のマルチセットではなく整数値によってインデックスを作成する単純なアプローチでは、作業が重複し、遷移が過剰にカウントされます。 

ある表現では先行ゼロが暗黙的に無視され、別の表現では無視されない場合、別の障害モードが発生します。 たとえば、「0012」を「12」とは異なる状態として扱うと、数字のマルチセットは同一であり、単一の状態に折りたたむ必要があるため、正確性が損なわれます。 

## アプローチ

 直接シミュレーションのアプローチでは、すべての整数に対して反復処理が行われます。\(x\)有効な範囲内で、その桁マルチ​​セットを計算し、Kaprekar スタイルの変換を 1 回適用し、このプロセスを繰り返します。\(n\)回。 各ステップは数字のみに依存するため、これは概念的には簡単であり、変換は明確に定義されています。 

ただし、整数の数は桁の長さに応じて指数関数的に増加するため、固定桁数に制限しても、\(10^d\)可能性。 と\(d\)10 以上のような一般的な制約までは、ブルート フォースはすでに境界線に達しており、複数のクエリを使用すると完全に実行不可能になります。 各変換自体は \(O(d)\) であるため、完全なシミュレーションは \(O(10^d \cdot d \cdot n)\) になります。 

重要な観察は、変換が数字の順序には依存せず、マルチセットのみに依存するということです。 これにより、問題全体が桁数ベクトルの有限状態空間に分解されます。 各状態は、固定和を持つ 10 次元ベクトル \((c_0, c_1, \dots, c_9)\) として表現できます。\(d\)。 このような状態の数は次のように制限されます。\(\binom{d+9}{9}\)、これは事前計算には十分小さいです。 

各マルチセットが状態であることを受け入れると、変換は状態間の決定論的なマッピングになります。 これにより、状態に関する有向グラフが生成されます。 すべてのクエリは、この遷移関数を適用することと同じになります。\(n\)回。 クエリごとに再計算する代わりに、すべての遷移を事前計算してから、この関数グラフで高速累乗または反復二乗を使用します。 

変換構造が桁分布のみに依存することに注目して、プロセスをさらに圧縮します。そのため、特定のマルチセットのすべての計算をクエリ間で再利用できます。 すべての状態について、その次の状態と、そこにマッピングされる元の整数の数を事前計算します。 次に、繰り返される遷移にわたってカウントを伝播します。 

これにより、問題は整数の反復から状態の反復に、またクエリごとのシミュレーションから事前計算されたジャンプに軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 |---|---|---|---|
 | ブルートフォース | \(O(10^d \cdot d \cdot n)\) | \(O(10^d)\) | 遅すぎる |
 | 最適 | \(O(S \cdot d + Q \log n)\) | \(O(S)\) | 承認済み |

 ここ\(S = \binom{d+9}{9}\)、桁マルチセットの数。 

## アルゴリズムのチュートリアル

 まず、各状態を長さ 10 の桁頻度ベクトルとして形式化します。有効な数値はすべて、そのようなベクトル 1 つに正確に対応し、複数の数値が同じベクトルにマッピングされる場合があります。 

1. 必要な桁長の有効な桁マルチセットをすべて列挙します。 これは、残りの合計制約を使用して、0 ～ 9 の数字に対する再帰的な構築を使用して行われます。 このステップはシステムの完全な状態空間を定義するため必要です。 

2. 各桁のマルチセットについて、並べ替えられた順序で桁を展開することによって代表的な数値を再構築します。 正確な順序は重要ではありませんが、変換を一貫して計算するには正規形式が必要です。 

3. 各状態について、その桁を取得し、問題で定義された演算を実行し、新しい桁マルチセットを生成することによって、その Kaprekar スタイルの変換を計算します。 これにより、ある状態から別の状態への有向エッジが得られます。 

4. 各状態が 1 つの次の状態を正確に指す遷移テーブルを作成します。 これにより、問題は有限状態空間にわたる繰り返し関数の適用に変わります。 

5. バイナリリフティングを使用して遷移関数のべき乗を事前計算します。 各状態および 2 のべき乗ごとに、変換を適用した後の結果の状態を保存します。\(2^k\)回。 

6. 各クエリに対して、最初の数字のマルチセットを表し、バイナリ リフティングを適用して前方にジャンプします。\(n\)\(O(\log n)\) のステップを実行して、最終状態を取得します。 

正確さは、すべての変換が桁のマルチセットに対して決定論的であるという事実に左右されるため、状態グラフはノードごとに 1 つの出次数を持つ関数グラフになります。 

### なぜ効果があるのか

 各状態は、将来の進化に関連するすべての情報を完全に取得します。 変換は桁数のみに依存するため、同じマルチセットを持つ 2 つの数値は常に同じように進化します。 これにより、システムは状態レベルでメモリレスになります。次の状態は、現在の状態にのみ依存し、そこに到達するために使用されるパスには依存しません。 したがって、遷移関数の反復適用は累乗を使用して構成でき、バイナリ リフティングは反復構成を正確にシミュレートします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from functools import lru_cache

# factorial helpers for multinomial counts
fact = [1] * 55
for i in range(1, 55):
    fact[i] = fact[i - 1] * i

def multinomial(cnt):
    n = sum(cnt)
    res = fact[n]
    for c in cnt:
        res //= fact[c]
    return res

def digits_from_cnt(cnt):
    res = []
    for d in range(10):
        res.extend([d] * cnt[d])
    return res

def cnt_from_digits(arr):
    cnt = [0] * 10
    for x in arr:
        cnt[x] += 1
    return tuple(cnt)

def transform(cnt):
    digits = digits_from_cnt(cnt)
    digits.sort()
    small = digits
    large = digits[::-1]
    a = int("".join(map(str, large)))
    b = int("".join(map(str, small)))
    c = a - b
    return cnt_from_digits(map(int, str(c)))

def gen_states(d):
    states = []

    def dfs(pos, left, cur):
        if pos == 10:
            if left == 0:
                states.append(tuple(cur))
            return
        for take in range(left + 1):
            cur[pos] = take
            dfs(pos + 1, left - take, cur)

    cur = [0] * 10
    dfs(0, d, cur)
    return states

def build(d):
    states = gen_states(d)
    idx = {s: i for i, s in enumerate(states)}

    nxt = [0] * len(states)
    for i, s in enumerate(states):
        nxt[i] = idx[transform(s)]

    return states, idx, nxt

def build_lift(nxt):
    m = len(nxt)
    LOG = 20
    up = [[0] * m for _ in range(LOG)]
    up[0] = nxt[:]
    for k in range(1, LOG):
        for i in range(m):
            up[k][i] = up[k - 1][up[k - 1][i]]
    return up

def solve():
    q = int(input())
    d = int(input())

    states, idx, nxt = build(d)
    up = build_lift(nxt)

    for _ in range(q):
        x = input().strip()
        cnt = [0] * 10
        for ch in x:
            cnt[int(ch)] += 1

        v = idx[tuple(cnt)]
        steps = int(input())

        for k in range(20):
            if steps & (1 << k):
                v = up[k][v]

        print(multinomial(states[v]))

if __name__ == "__main__":
    solve()

バイナリリフティングテーブル`up[k][i]`ストアの状態`i`後に終わります\(2^k\)変化。 これにより、クエリごとに各ステ​​ップを個別にシミュレートする必要がなくなります。 

最終的な答えは、各マルチセットが複数の桁の並べ替えに対応し、その状態によって表されるすべての有効な元の数値を考慮する必要があるため、多項カウントを使用します。 

よくある落とし穴は、整数の同一性が重要であると仮定することです。 このソリューションは、桁数のみを操作することでこれを完全に回避し、すべての同等の表現が正しく折りたたまれるようにします。

 ## 特殊なケース

 エッジ ケースの 1 つは、数値に多くのゼロが含まれる場合に発生します。 1000 のような入力の場合、桁のマルチセットは大きく偏っており、減算により桁数の少ない数値が生成される可能性があります。 このアルゴリズムは、常に完全な桁数ベクトルに変換し直すことでこれを処理し、先行ゼロが消えた場合でも状態の次元を保持します。 

もう 1 つのエッジ ケースは、変換が固定点に達する場合です。 このような場合、バイナリ リフティングによって状態がそれ自体に繰り返しマッピングされます。 昇降テーブルはこれを正しくエンコードします。`up[k][i]`すべての大きなサイズで安定する\(k\)発振エラーや無限ループを防ぎます。 

3 番目のエッジ ケースは、複数の数字の並べ替えが同じ状態に対応するが、異なる中間整数表現を生成する場合です。 すべての算術演算は数字を並べ替えた後に実行されるため、表現は標準的であり、そのようなすべての順列は同一の状態に崩壊し、一貫した遷移が保証されます。
