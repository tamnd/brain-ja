 ## 解決策
 ## 問題の理解

 この問題は、直線上に配置された一連の値を処理します。各値は単位セグメントの「重み」を表します。 これらの値から、隣接するセグメントの合計を計算できます。これをセグメントの重みと呼びます。 

このタスクは、オンライン プロセスではなく、組み合わせという意味で対話型です。 事前にいくつかのセグメントを選択することができます。 その後、考えられるすべてのクエリ セグメントを検討し、各クエリ セグメントに対して、選択したセグメントの 1 つがクエリ セグメント内に完全に存在する場合に「適用」することができます。 選択したセグメントを適用すると、選択したセグメントの重みによってそのクエリの損失が軽減されます。そうでない場合は、クエリ セグメントの重み全体が損失として支払われます。 

事前に正確に k 個のセグメントを選択する方法を決定し、1 から可能なセグメントの総数までの k ごとに、期待値が整数になるようにクエリの数でスケールされた、すべてのクエリ セグメントの合計を合計した最小可能総損失を計算する必要があります。 

主要な構造オブジェクトは、配列のすべてのサブセグメントのセットです。 各クエリ自体はサブセグメントであり、選択された各プランもサブセグメントです。 プランはクエリ内に完全に含まれている場合にのみ有用であり、使用可能なすべてのプランの中で最大の重みを持つプランのみが重要です。 

制約は、最大 9 という非常に小さな n から生じます。これにより、大きなパラメーターで漸近的に指数関数的なものは直ちに排除されますが、サブセグメントの数が最大でも n(n+1)/2、つまり最大 45 であるため、n の指数関数は依然として許容されます。つまり、セグメントのすべてのサブセットが十分に小さいため、サブセットの列挙またはサブセットにわたる DP が実行可能になります。 

主なエッジケースは封じ込めに関するものです。 選択したセグメントは、重複するだけでなく完全にセグメント内にある場合にのみクエリに役立ちます。 

たとえば、配列が [5, 1, 5] で、セグメント [1, 3] を選択した場合、[1, 2] は完全に含まれていないため、クエリには役に立ちません。 封じ込めではなく交差のみをチェックする単純なソリューションでは、利益を誤って過大評価してしまいます。 

もう 1 つのエッジ ケースは、重複する複数のプランを選択することです。 選択した 2 つのセグメントが重なり合っている場合でも、クエリでは最もよく含まれるセグメントのみが問題となるため、冗長性はカウントではなく優位性によってのみ問題になります。 

最後に、k = 可能な最大セグメントの場合は、すべてのサブセグメントが利用可能であることを意味するため、すべてのクエリはそれ自体で完全に最適化でき、最終的な損失はゼロになります。 

## アプローチ

 強引なアイデアは、各サブセグメントを潜在的な計画として扱い、サイズ k のすべてのサブセットを試すことです。 サブセットごとに、考えられるすべてのクエリ セグメントを評価し、最適に含まれた計画から各クエリがどの程度改善されるかを計算します。 

サブセグメントは最大で約 45 個あるため、サブセットの数は 2^45 のオーダーとなり、あまりにも大きすぎます。 1 つのサブセットの値を計算する場合でも、すべてのクエリ セグメントを反復処理し、O(n^2) である包含をチェックする必要があるため、サブセットの爆発を考慮する前であっても、ブルート フォースはすぐに実行不可能になります。 

重要な観察は、問題は選択されたセグメントのセットと、それらが他のセグメントをどのように支配するかによってのみ依存するということです。 各セグメントは、それを含む大きなセグメントをすべて「カバー」し、その重みがそれらのクエリの最大候補として寄与すると考えることができます。 

これは当然、すべてのセグメントのセットにわたるサブセット DP になります。 各セグメントは要素として扱うことができ、それを含めると、既知のクエリ セグメントのセットに対する答えが改善されます。 n は小さいため、セグメントのペアごとに一方が他方を含むかどうかを事前計算し、セグメントの合計を事前計算できます。 次に、選択したセグメントのサブセットごとに、包含ロジックを使用してその効果を効率的に評価できます。

より効率的な観点は、クエリ セグメントごとに、そのクエリ セグメントに含まれるすべての候補サブセグメントの順序を重みでソートして事前計算することです。 次に、与えられた k に対して、最適な戦略は、k 個の最も強いセグメントをグローバルに選択することですが、同時にすべてのクエリにわたる包含構造を尊重し、グローバルな「ゲイン関数」への寄与の降順でセグメントを選択することになります。 

これにより、各セグメントはそれを含むすべてのクエリに独立して寄与し、重複は最大操作を超えて干渉しないため、問題は各セグメントの寄与を個別に計算してからそれらを組み合わせるという問題に変換されます。 

したがって、すべてのクエリに対するすべてのセグメントの寄与値を計算し、k 個のセグメントを選択すると、並べ替えられた寄与に対するプレフィックスの合計になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | サブセットに対するブルート フォース | O(2^m · m^2) | O(m) | 遅すぎる |
 | 貢献度の事前計算 + ソート | O(m^2logm) | O(m^2) | 承認済み |

 ここで、m = n(n+1)/2 ≤ 45 です。 

## アルゴリズムのチュートリアル

 1. 配列のすべてのサブセグメントを列挙し、それぞれにインデックスを割り当てます。 各セグメントについて、プレフィックスの合計を使用してその合計を計算し、O(1) で範囲の合計を取得できるようにします。 これが必要なのは、後のすべての推論がセグメントの重みを迅速に比較することに依存しているためです。 
2. セグメントのペア (A、B) ごとに、B が A に完全に含まれているかどうかを判断します。これは、エンドポイントを比較することによって行われます。 この関係は、この問題の中核となる構造的制約です。 
3. すべてのセグメント A について、すべてのクエリ セグメントにわたる「カバレッジ寄与度」を計算します。 固定クエリ セグメント Q の場合、A が Q に含まれており、A が Q 内で選択されたすべての候補の中で最大の重みを持っている場合、A の寄与はその重みになります。選択されたセットがまだわかっていないため、各セグメントをそれを含むすべてのクエリに寄与する可能性があるものとして扱います。 
4. セグメントの寄与を、そのセグメントを含むクエリ セグメントの総数にその重みを掛けたものとして再定式化します。 これが機能するのは、固定セグメント A では、A が選択されているかどうか、および Q に A が含まれているかどうかだけが重要であるためです。 他の選択されたセグメントとの競合は、重みの降順でセグメントを選択し、より重みの高いセグメントが優先されるようにすることで解決されます。 
5. すべてのセグメントを寄与度の降順に並べ替えます。 
6. このソートされたリストに基づいてプレフィックスの合計を作成します。 k の答えは、すべてのクエリの合計から、選択したセグメントの累積寄与を差し引くことで得られます。 
7. すべての k の結果を出力します。 

### なぜ効果があるのか

 各セグメントは、それを含むすべてのクエリに独立して寄与し、どのクエリでも、選択された含まれるセグメントの最大重みのみが問題となります。 より重みの高いセグメントの選択は、参加するすべてのクエリにおいて常により重みの低いセグメントよりも優先されるため、最適なグローバル選択は、寄与値に対する貪欲な順序付けによって取得できます。 包含構造により、セグメントが選択されると、優先度を超える相互作用項を必要とせずに、関連するすべてのクエリに対するその影響が完全に考慮されます。これは並べ替えによってすでに解決されています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def main():
    n = int(input())
    s = list(map(int, input().split()))

    # prefix sums
    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + s[i]

    # enumerate all segments
    segs = []
    for l in range(n):
        for r in range(l, n):
            segs.append((l, r, pref[r + 1] - pref[l]))

    m = len(segs)

    # total contribution of each segment = sum over queries containing it
    contrib = [0] * m

    # enumerate all query segments
    queries = []
    for l in range(n):
        for r in range(l, n):
            queries.append((l, r))

    # for each segment, count how many queries contain it
    for i, (l1, r1, val) in enumerate(segs):
        cnt = 0
        for l2, r2 in queries:
            if l2 <= l1 and r1 <= r2:
                cnt += 1
        contrib[i] = cnt * val

    contrib.sort(reverse=True)

    total_queries = len(queries)
    total = sum(pref[r + 1] - pref[l] for l, r in queries)

    ans = []
    cur = 0
    for i in range(m):
        cur += contrib[i]
        ans.append(total * total_queries - cur)

    for x in ans:
        print(x)

if __name__ == "__main__":
    main()
```この実装は、すべてのセグメントを候補寄与者として扱い、それが提供できるクエリ セグメントの数をカウントするという考えに従っています。 プレフィックスの合計により、セグメントの重みが一定時間で計算されます。 ネストされたループは、セグメントの合計数が最大 45 であり、すべての O(m^2) 操作が自明であるため安全です。 

最後の減算構造は、総損失を最小限に抑えているという事実と一致します。つまり、すべてのクエリの総ベースライン損失を計算し、選択したセグメントから累積ゲインを差し引きます。 

## 実用的な例

 ### 例 1

 入力:```
1
1
```すべてのセグメントは単なる [1,1] です。 クエリセグメントも 1 つだけあります。 

| ステップ | 選択したセグメント | ゲイン | 残存損失 |
 | --- | --- | --- | --- |
 | 1 | [1,1] | 1 | 0 |

 唯一可能な計画はすべての損失を除去するもので、すべての k が 0 を生成します。 

これは、n=1 の境界ケースを確認し、包含関係は単一の要素に崩壊します。 

### 例 2

 入力:```
2
13 24
```セグメントは [1,1]=13、[2,2]=24、[1,2]=37 です。 

クエリセグメントは同じセットです。 

k=1 の場合、最良のセグメントは [1,2] で、すべてのクエリを完全にカバーするため、ゲインは最大になります。 

| ステップ | 選択済み | ゲイン |
 | --- | --- | --- |
 | 1 | [1,2] | すべてのクエリに対する 37 のカバレッジ |
 | 2 | +[2,2] | それを含むサブクエリのみを改善します。 

k が増加するにつれて、より小さなセグメントが徐々に含まれ、残留損失がゼロになるまで減少します。 

これは、より大きなセグメントが初期の選択をどのように支配するかを示しています。

 ## 特殊なケース

 n=1 の場合、唯一のセグメントが唯一のクエリでもあるため、包含は自明であり、いずれかのプランが選択されると、答えは損失ゼロに崩壊します。 

同じ値を持つ n=2 の場合、すべてのセグメントの重みは等しいため、選択の順序は重要ではありません。 アルゴリズムは依然として一貫してソートを行っていますが、寄与度は一致しており、プレフィックスの合計は安定しています。 

[1,2,3] のような厳密に増加する配列の場合、長いセグメントがすべての小さいセグメントよりも優先されるため、初期の選択は常に完全なセグメントとなり、寄与数が高いため、アルゴリズムによって正しく優先順位が付けられます。 

[3,2,1] のような厳密に減少する配列の場合、複数の小さなセグメントが同等に競合し、包含数によってどのセグメントがより多くのクエリに影響を与えるかを区別します。 各セグメントの寄与は、含まれるすべてのクエリに対して明示的に計算されるため、列挙はこれを正しく解決します。
