 ## 解決策

 ## 問題の理解

 ソフトウェア プロジェクトのコレクションが与えられ、各プロジェクトは名前だけでなくバージョン番号でも識別されます。 各プロジェクトは他のプロジェクトに依存し、有向非循環依存関係グラフを形成できます。 入力の最初のプロジェクトは Polycarp の現在のプロジェクトであり、私たちのタスクは、プロジェクトを構築または分析するときに含める必要があるすべてのものを決定することです。 

微妙な点は、同じプロジェクト名が複数のバージョンに存在する可能性があり、依存関係が同じ名前のプロジェクトの異なるバージョンを参照する可能性があることです。 ただし、同じ名前の複数のバージョンが到達可能な場合、最終的に解決された依存関係セットに実際に保持されるバージョンは 1 つだけです。 選択するバージョンは、Polycarp のプロジェクトからの依存関係の距離の点で「最も近い」バージョンである必要があり、複数のバージョンの距離が同じ場合は、バージョン番号が大きいバージョンが優先されます。 

出力は、この解決プロセス後に残るすべてのプロジェクト (Polycarp のルート プロジェクトを除く) のセットで、選択したバージョンとともにプロジェクト名ごとに辞書編集順に印刷されます。 

n ≤ 1000 という制約は、O(n²) または O(n log n) のグラフ走査は問題ないが、大きなサブセットに対する繰り返しの再計算を伴うものはすべて合格することを直ちに示唆します。 各プロジェクトは直接の依存関係を明示的にリストしており、ノードの総数は最大でも 1000 であるため、グラフは構造上まばらです。 

重要なエッジケースは、グラフの異なる部分に現れる同じ名前の複数のバージョンに由来します。 (名前、バージョン) を個別に扱う単純な DFS には、競合するバージョンが同時に含まれることになります。 たとえば、プロジェクト a が b 1 に依存し、別のチェーンを通じて b 2 にも依存する場合、最終的な解決では b の 1 つのバージョンのみが許可される場合でも、単純な走査には両方が含まれる可能性があります。 

もう 1 つの微妙な問題は、「最適なバージョン」は依存関係グラフ内のルートからの最短距離に依存するため、より深いが数値的に大きいバージョンは、より近いバージョンを優先して破棄される可能性があることです。 名前ごとの最適距離を追跡せずに、訪問したノードのみを追跡するソリューションは、後の検出によりより良いバージョンが得られる場合には失敗します。 

## アプローチ

 簡単なアプローチは、すべての (名前、バージョン) ペアをグラフ内の個別のノードとして扱い、Polycarp のプロジェクトから DFS または BFS を実行して、到達可能なすべてのノードを収集することです。 これにより、すべての依存関係が正しく検索されますが、同じ名前のバージョン間の衝突ルールは解決されません。 走査後、名前でグループ化し、最適なバージョンを選択することにより、セットを後処理する必要があります。 

問題は、到達可能性だけでは十分ではないことです。 正しいバージョンは最短パス距離に依存するため、名前ごとに、これまでに発生した最小距離を追跡する必要があります。 単純に行うと、2 回目のトラバースまたは繰り返しの緩和が必要になります。 最悪の場合、同じプロジェクトの複数のバージョンが異なる深さで表示され、単純な伝播によって選択肢が繰り返し更新され、二次的な動作が発生する可能性があります。 

重要な観察は、依存関係グラフが Polycarp のプロジェクトに根ざした DAG であり、BFS で計算できる重み付けされていないグラフの最短パス距離のみを考慮しているということです。 ルートからすべてのノード (名前、バージョン) までの最小距離を計算したら、距離が最も短いバージョンを選択することで各名前を個別に解決でき、より大きなバージョン番号を選択することで関係を解消できます。 これにより、反復的な改良の必要がなくなります。 

次に、すべてのノードに対して 2 回目のパスを実行して、名前ごとに選択されたバージョンを抽出して出力します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース DFS + 後処理 | O(n²) 最悪の場合 | O(n) | 許容範囲ですが壊れやすい |
 | BFS + 名前ごとの最適な選択 | O(n + m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、各ノードが (名前、バージョン) で識別されるプロジェクト インスタンスであるグラフへの入力を正規化します。 また、効率的な隣接ストレージのために各ノードに一意の整数 ID を割り当てます。 

次に、すべてのエッジが重み付けされておらず、依存関係チェーンの長さを最小限に抑えたいため、BFS を使用して Polycarp のプロジェクトから最短距離を計算します。 

1. すべてのプロジェクトを解析し、依存関係の隣接リストを保存しながら、それぞれ (名前、バージョン) にノード ID を割り当てます。 これにより、フィルタリングを行わずに完全な依存関係グラフが構築されます。 
2. 最初のプロジェクトから BFS を実行します。 その距離を 0 として初期化し、キ​​ューにプッシュします。 
3. ノードを処理するときは、そのすべての依存関係を調べます。 依存関係がまだ訪問されていない場合は、距離 current_ distance + 1 を割り当ててキューにプッシュします。 BFS は距離の増加順に拡張するため、最初に割り当てる距離は最小値であることが保証されます。 
4. BFS が完了すると、Polycarp のプロジェクトから到達可能なすべての (名前、バージョン) までの最短距離が得られます。 
5. プロジェクト名ごとに、到達したその名前のすべてのバージョンを調べます。 距離が最小のバージョンを選択します。 複数のバージョンが同じ距離を共有する場合、最大のバージョン番号を持つバージョンが選択されます。 
6. 最後に、ルート プロジェクトを除く、選択したすべての (名前、バージョン) ペアを名前で辞書順に並べて出力します。 

正確さは、BFS が各ノードに可能な最小の依存関係距離を割り当てるという不変式に依存します。 距離が固定された後でのみ同じ名前のバージョンを比較するため、決定を再考したり修正したりする必要はありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque, defaultdict

n = int(input())

nodes = []
id_map = {}
adj = []

def get_id(name, ver):
    key = (name, ver)
    if key not in id_map:
        id_map[key] = len(nodes)
        nodes.append(key)
        adj.append([])
    return id_map[key]

# read input
i = 0
lines = [line.rstrip("\n") for line in sys.stdin if line.strip() != ""]
p = 0

# first pass parse
while p < len(lines):
    name, ver = lines[p].split()
    ver = int(ver)
    u = get_id(name, ver)
    p += 1

    k = int(lines[p])
    p += 1

    for _ in range(k):
        dn, dv = lines[p].split()
        dv = int(dv)
        v = get_id(dn, dv)
        adj[u].append(v)
        p += 1

root = 0

dist = [-1] * len(nodes)
dist[root] = 0
q = deque([root])

while q:
    u = q.popleft()
    for v in adj[u]:
        if dist[v] == -1:
            dist[v] = dist[u] + 1
            q.append(v)

best = {}

for i, (name, ver) in enumerate(nodes):
    if dist[i] == -1:
        continue
    if name not in best:
        best[name] = (dist[i], ver)
    else:
        d, v = best[name]
        if dist[i] < d or (dist[i] == d and ver > v):
            best[name] = (dist[i], ver)

root_name = nodes[0][0]

ans = []
for name, (d, ver) in best.items():
    if name == root_name and ver == nodes[0][1]:
        continue
    ans.append((name, ver))

ans.sort()
for name, ver in ans:
    print(name, ver)
```この実装では、隣接リストが単純な整数リストになるように、すべてのプロジェクト バージョンの統一インデックスが構築されます。 BFS は、最初にノードに到達するときに常に最短の依存関係チェーンを経由することを保証します。 

フィルタリングの手順は、トラバーサル中ではなく BFS の後に実行されます。これは、バージョンに関する初期の決定が、後で短いパスの検出によって無効になる可能性があるためです。 最初にすべての距離を固定しておくことで、この不安定性を回避できます。 

微妙な詳細の 1 つは、入力解析の処理です。空行はプロジェクト ブロックを区切るため、正しいグループ化を保証するために空行を明示的に無視します。 

## 実用的な例

 ### サンプル 1

 入力プロジェクトは、ルートが同じプロジェクト名の異なるバージョンにつながる 2 つの分岐に依存する小さなグラフを形成します。 

| ステップ | キュー | 処理されたノード | 更新された距離 |
 | --- | --- | --- | --- |
 | 0 | a3 | - | a3:0 |
 | 1 | b1、c1 | a3 | b1:1、c1:1 |
 | 2 | c1 | b1 | (b2 はすでに存在しますが、まだ到達できません) |
 | 3 | b2 | c1 | b2:2 |

 BFS の後、b のバージョンを比較し、距離が小さく、c1 が直接含まれる b1 を選択します。 

これは、BFS がどのように自然に最短の依存関係の選択を強制するかを示しています。 

### サンプル 2

 このケースでは、一方のバージョンが構造的により深いものの、無視する必要がある依存関係の競合バージョンが導入されます。 

| ステップ | キュー | 処理されたノード | 更新された距離 |
 | --- | --- | --- | --- |
 | 0 | ルート | - | ルート:0 |
 | 1 | エクストラ1、マシャDB2 | ルート | extra1:1、mashadb2:1 |
 | 2 | マシャDB2 | おまけ1 | - |
 | 3 | extra3 (後で無視されます) | マシャDB2 | エクストラ3:2 |

 ここでは、extra3 が存在しますが、extra1 のパスが短いため無視されます。 BFS 距離により、バージョン選択の正確さが保証されます。

| スペース | O(n + m) | 隣接関係リスト、ノード マッピング、距離配列のストレージ |

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    from collections import deque, defaultdict

    n = int(sys.stdin.readline())

    nodes = []
    id_map = {}
    adj = []

    def get_id(name, ver):
        key = (name, ver)
        if key not in id_map:
            id_map[key] = len(nodes)
            nodes.append(key)
            adj.append([])
        return id_map[key]

    lines = [line.rstrip("\n") for line in sys.stdin if line.strip() != ""]
    p = 0

    while p < len(lines):
        name, ver = lines[p].split()
        ver = int(ver)
        u = get_id(name, ver)
        p += 1

        k = int(lines[p])
        p += 1

        for _ in range(k):
            dn, dv = lines[p].split()
            dv = int(dv)
            v = get_id(dn, dv)
            adj[u].append(v)
            p += 1

    dist = [-1] * len(nodes)
    dist[0] = 0
    q = deque([0])

    while q:
        u = q.popleft()
        for v in adj[u]:
            if dist[v] == -1:
                dist[v] = dist[u] + 1
                q.append(v)

    best = {}
    for i, (name, ver) in enumerate(nodes):
        if dist[i] == -1:
            continue
        if name not in best:
            best[name] = (dist[i], ver)
        else:
            d, v = best[name]
            if dist[i] < d or (dist[i] == d and ver > v):
                best[name] = (dist[i], ver)

    root_name, root_ver = nodes[0]

    ans = [(name, ver) for name, (d, ver) in best.items() if not (name == root_name and ver == root_ver)]
    ans.sort()

    return "\n".join(f"{a} {b}" for a, b in ans)

 ## 特殊なケース

 エッジ ケースの 1 つは、ルートからまったく同じ距離にある複数のバージョンで同じプロジェクト名が表示される場合です。 その状況では、アルゴリズムはより高いバージョン番号を選択します。 たとえば、b1 と b2 の両方が 1 つのステップで到達可能な場合、BFS は両方の距離 1 を割り当て、選択ステップでは b2 が維持されます。 

もう 1 つのケースは、より長いバージョンに到達できるが、より長い依存関係チェーンを介してのみ到達できる場合です。 一見望ましいように見えても、BFS 距離の比較により、確実に破棄されます。 入力構造ではサイクルが保証されないため、最短パスは常に明確に定義され、BFS 順序付けにより、ノードに距離が割り当てられると、その後は距離が改善されないことが保証されます。
