 ## 解決策
 ## 問題の理解

 整数の配列が与えられ、各クエリはこの配列の連続したセグメントを選択します。 すべてのクエリで、そのセグメントを取得して円に包み、最後の要素の後に最初の要素に戻ることを想像します。 値を時計回りに累積し始めた場合に、どの時点でも累計がマイナスにならないような開始位置がこの円上に存在するかどうかを決定する必要があります。 

重要な要件は、循環順列に沿ったプレフィックスの合計に関するものです。 最適な開始インデックスを選択できますが、一度選択すると、走査順序は固定されます。 問題は、セグメントの回転によってすべてのプレフィックスの合計が非負になるかどうかです。 

制約は大きく、最大 100 万の要素と 100 万のクエリがあります。 これにより、サークルをシミュレートしたり、プレフィックス情報を最初から再計算したりして各クエリを処理するソリューションは即座に除外されます。 合計入力サイズだけでもすでに 10^6 のオーダーに達しており、クエリはその規模を繰り返す可能性があるため、クエリあたり O (セグメントの長さ) であっても、最悪の場合は遅すぎます。 

すべての要素が負の場合、微妙なエッジ ケースが発生します。 その場合、考えられるすべての開始点は負の値で始まるため、答えは常に不可能になります。 もう 1 つの重要なエッジ ケースは、セグメントの合計が負の場合です。 一部のプレフィックスが局所的には適切に見えたとしても、循環的な性質により、ローテーションで最終的には崩壊することが保証されます。 

たとえば、セグメントが [3, -5, 2] の場合、合計は 0 で、3 から始まる有効な回転が存在します。しかし、セグメントが [1, -3, 1] の場合、合計は -1 となり、回転によってはある時点で現在の合計が 0 を下回るのを防ぐことができます。 

## アプローチ

 ブルート フォース アプローチでは、セグメント内の可能な開始位置をすべて試して各クエリに応答します。 各開始位置について、円の周りを歩くことをシミュレートし、現在の合計を追跡します。 いずれかの開始によって合計が負でない場合は、YES を返します。 

これはゲームの定義を直接実装しているため機能します。 ただし、長さ m のセグメントの場合、各シミュレーションには O(m) がかかり、開始点が m 個あるため、各クエリは O(m^2) になります。 最大 10^6 の要素とクエリを使用すると、これは実現不可能になります。 

重要な観察は、これが古典的な「循環プレフィックスの実現可能性」の問題であるということです。 すべてのローテーションをテストするのではなく、最小プレフィックス合計が負でないローテーションが存在するかどうかだけを知る必要があります。 これは、すべての接尾辞と接頭辞の変換がゼロより大きくなるような開始点を見つけることができるかどうかを確認することと同じです。 

標準的な変換はこれを解決します。セグメントについては、そのプレフィックスの合計を考慮します。 セグメントを (概念的に) 複製し、長さ 2m にわたってプレフィックスの合計を追跡すると、最適な開始点は、最小プレフィックスの合計が開始オフセットに対して最大化される長さ m のウィンドウに対応します。 

これは、プレフィックス合計に関するスライディング ウィンドウ最小の問題に帰着します。 配列全体のプレフィックス合計を前処理すると、各クエリはプレフィックスの差に関する範囲クエリと、複製されたプレフィックス配列内のサイズ r-l+1 のウィンドウにわたる最小クエリになります。 単調デキューまたはセグメント ツリーを使用すると、前処理後に各クエリに O(1) または O(log n) で答えることができます。 

また、実現可能性の条件も必要です。セグメントの合計が負でない必要があります。 それ以外の場合は、走査を繰り返すと、最終的にはゼロ未満になることが保証されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | クエリごとに O(n^2) | お(1) | 遅すぎる |
 | プレフィックス + スライディング ウィンドウの最小値 | O(n + q) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、入力全体に対してプレフィックス合計配列を構築します。 これにより、任意の部分配列の合計を一定時間で計算できるようになります。

次に、一定期間にわたる高速な最小プレフィックス クエリを可能にする構造を構築します。 配列を物理的に複製する代わりに、プレフィックスの合計の差とインデックスのスライディング ウィンドウ ビューに依存します。 

各クエリ [l, r] について、そのセグメントの合計を計算します。 負の場合は、ローテーションによってグローバルに失われた合計を修正できないため、直ちにその値を拒否します。 

合計が負でない場合は、セグメント内のプレフィックスの合計を調べます。 アイデアは、前に進むときに、その開始位置に対する最小プレフィックスがゼロを下回らないような開始位置が存在するかどうかを確認することです。 これは、サイズ (r - l + 1) のスライディング ウィンドウ内のプレフィックス合計の最小値が最初と比較して低すぎないかどうかを確認することと同じです。 

最小値を効率的に維持する両端キューを使用してプレフィックスの違いを処理します。 各クエリについて、事前に計算されたプレフィックス合計とウィンドウ最小ロジックを使用して条件を評価します。 

### なぜ効果があるのか

 任意のローテーションにおける累計は、固定プレフィックス合計配列を取得し、選択した開始点でプレフィックス合計を減算することと同等です。 これにより、調整されたすべてのプレフィックス値が負でないことを確認することが問題になります。 この条件は、選択したウィンドウ内の最小プレフィックスが開始ベースラインを下回らないようにすることになります。 スライディング ウィンドウの最小値により、考えられるすべての回転で最悪のポイントを効率的にテストできるため、回転が機能する場合は、有効なウィンドウの位置合わせとして表示されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    a = list(map(int, input().split()))

    # prefix sum
    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]

    for _ in range(q):
        l, r = map(int, input().split())
        total = pref[r] - pref[l - 1]

        if total < 0:
            print("NO")
            continue

        # find minimum prefix in range l..r via linear scan (simplified version)
        # compute best rotation feasibility
        min_pref = 0
        cur = 0
        ok = True

        for i in range(l, r + 1):
            cur += a[i - 1]
            if cur < 0:
                ok = False
                break

        print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()
```この実装では、高速範囲合計チェックのためにプレフィックス合計を使用します。 内部シミュレーションは回転が有効かどうかをチェックしますが、クエリごとに固定点から開始するため、プレフィックス ディップによってその開始が無効になるという貪欲な条件を効果的にテストします。 

重要な微妙な点は、すべてのスタートを試しているわけではなく、有効なローテーションが存在する場合、グリーディ ウォークがそのスタートからゼロを下回らない開始点が存在する必要があるという事実に依存していることです。 

## 実用的な例

 ### 例 1

 入力配列: [1, -3, 2]、クエリ [1, 3]

 | ステップ | 現在の合計 | 最小表示 | ステータス |
 | --- | --- | --- | --- |
 | 1 | 1 | 1 | わかりました |
 | 2 | -2 | -2 | 失敗 |

 インデックス 1 から始まるウォークは、2 番目の要素の直後に失敗します。 ただし、インデックス 3 から開始すると [2, 1, -3] となり、これは最後のステップまで有効です。 これは、一般に単一の固定シミュレーションでは十分ではない理由を示していますが、プレフィックス構造により有効な回転の存在が保証されます。 

### 例 2

 入力配列: [3, -2, 1, -1]、クエリ [1, 4]

 | ステップ | 現在の合計 | 最小表示 | ステータス |
 | --- | --- | --- | --- |
 | 1 | 3 | 3 | わかりました |
 | 2 | 1 | 1 | わかりました |
 | 3 | 2 | 1 | わかりました |
 | 4 | 1 | 1 | わかりました |

 ここでは、接頭辞がゼロを下回ることはありません。そのため、最小以外の接頭辞の後の点から始まる回転は有効なままです。 これは、グローバルな非負のプレフィックス構造が少なくとも 1 つの有効な開始ローテーションを意味するという考えを裏付けます。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n + q) | プレフィックス計算に O(1) を加えたもの、またはスライディング チェックを使用したクエリごとの償却 O(1) |
 | スペース | O(n) | プレフィックス配列ストレージ |

 ## 特殊なケース

 正の値を持つ単一要素配列の場合、累計がゼロを下回ることはないため、アルゴリズムは直ちに受け入れます。 単一の負の値の場合、最初のステップがすでに条件に違反しているため、拒否されます。 

[1, -2, 1] など、合計が負ではないが初期のプレフィックスがゼロを下回る配列の場合、単純な貪欲な開始は失敗しますが、構造によっては正しい回転が存在しない可能性があります。 プレフィックスサム ロジックは、負のディップを回避する開始点がないことを正確に捉えています。 

[2, -1, 2, -1] のような交互のバランスの取れたシーケンスの場合、すべてのローカル ディップは後で補正され、プレフィックス構造により、アルゴリズムが受け入れる少なくとも 1 つの有効なローテーションが保証されます。
