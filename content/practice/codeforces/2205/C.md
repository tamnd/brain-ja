 ## 解決策
 ## 問題の理解

 いくつかの独立したシナリオが与えられています。 それぞれのブログには複数の「ブログ」があり、各ブログにはユーザー ID の順序付きリストが含まれています。 これらのブログを公開する順序を決定する必要があり、この選択は世界的な順序に影響します。$Q$ブログを 1 つずつ処理するにつれて進化します。 

進化ルールはローカルですが永続的です。 ブログが公開されると、そのリストを左から右にスキャンします。 ユーザー ID を見つけるたびに、その ID を先頭に移動します。$Q$存在しない場合は挿入します。 したがって、各ブログは、共有リストに適用される一連の「前へ移動」操作のように機能します。 

目標は、順序付けを行った後に最終的なリストを計算することだけではありません。 ブログの順序は自由に選択できますが、最終的な順序が必要です。$Q$辞書編集的に最小になります。 

問題は、以前のブログでは、後のすべての要素の相対的な順序が永続的に変更される可能性があることです。 単純なアプローチでは、さまざまなブログの順序を試し、プロセスをシミュレーションし、最良の結果を選択します。 ブログの順列の数は階乗的に増加するため、これはすぐに実行不可能になります。 

制約の合計サイズは小さく、テスト ケースにわたるすべてのユーザーの言及の合計は 3000 以内に制限されます。$O(L \log L)$または$O(L)$テストごとのソリューションが期待されており、順列を調査したり、完全なシミュレーションを繰り返したりするものは除外されます。 

ブログ内の重複によって微妙な問題が発生します。 発生するたびに最前面への移動がトリガーされるため、1 つのブログ内で繰り返される値は、同じ要素を繰り返し「更新」するように動作します。 ブログ内で重複を排除するような不注意な実装は、正確性を損なうことになります。 

もう 1 つのエッジ ケースは、値が複数のブログに表示される場合です。 その最終的な位置は、それに触れる最後のブログ (処理順序で) によって決まりますが、以前に発生したものは依然として中間構造に影響を与えます。 この相互作用こそが、貪欲な順序付けを必要とするものです。 

## アプローチ

 ブルートフォース戦略では、ブログの順序のすべての順列を列挙します。 順列ごとに、すべてのブログにわたって最前面に移動するプロセスをシミュレートし、その結果の結果を計算します。$Q$。 各シミュレーションの費用$O(L)$、合計は$O(n! \cdot L)$、これはたとえ$n = 10$。 

重要な観察は、要素の最終的な順序は、ブログ処理のシーケンス全体における最後の「効果的なタッチ」によって決定されるということです。 要素にタッチするたびに、その要素が前面にジャンプします。 したがって、後で変更される要素は、最終リストの中で先に置かれます。 ただし、「後で」とは時間ステップだけを意味するものではなく、処理中に要素が表示された最後のブログを意味します。 

これは視点を逆転させることを示唆しています。 ブログの構築方法を考えるのではなく、$Q$、各要素に、その要素が最後に含まれるブログによって決定される最終的な優先順位を割り当てることを考えることができます。 ブログの順序を修正すると、各要素の最後の出現が決定され、要素の最終的な順序は、最後の出現回数による並べ替えに対応します。 

したがって、本当の問題は、これらの「ラストタッチ タイムスタンプ」の辞書編集上の最小性を最大化するブログの順序を選択することになります。 小さい ID を持つ要素ができるだけ早い段階で表示されるようにしたいと考えています。$Q$、これにより、処理順序のできるだけ遅い時点で最後にタッチされるようになります。 

最終的に構築する順序で右から左にブログを貪欲に処理すると、構造はさらに単純化されます。 次に配置するブログを決定するたびに、小さな要素を後の大きな要素の後ろに時期尚早にロックしないようにしたいと考えています。 

これは貪欲な構築につながります。つまり、最終的なブログ順序の構築を逆方向にシミュレートし、残りの目に見えない要素に対して可能な限り最小の「新しい情報」を紹介するブログを常に選択します。 

これを形式化する標準的な方法は、ユーザーごとにそのブログがまだ「未公開」であるかどうか、またブログごとにそのブログに含まれる未公開のユーザーの数を追跡することです。 私たちは、必要以上に大きな辞書編集上の接頭辞を強制することなく、安全に次に配置できるブログを繰り返し選択します。 貪欲な正しい選択は、利用可能なブログの中から、そのブログが提供する最初の新しい要素を最小限に抑えるものを選択すると同時に、小さな要素を配置する唯一の残された方法であるブログを延期しないようにすることであることがわかりました。 

実際の実装では、候補ブログに対する優先順位構造を使用します。順序キーは各ブログ内のまだ処理されていない最小の要素から導出され、要素がカバーされると動的に更新されます。

 ## アルゴリズムのチュートリアル

 私たちは、辞書編集上最小限の最終結果を保証するブログの有効な処理順序を決定することによって答えを構築します。$Q$。 主な問題は、各ブログの貢献度が、ブログを選択した時点でどの要素がまだ「関連性」があるかによって決まることです。 

1. まずすべてのユーザー ID を収集し、圧縮表現を準備します。これにより、構築段階で値が考慮されているかどうかを効率的に追跡できます。 raw ID を繰り返しスキャンすると時間がかかりすぎるため、これは重要です。 
2. 各ブログについて、まだ処理されていない最初の要素へのポインタを維持します。これを「現在の候補」と呼びます。 最初は、これは単にブログの最初の要素です。 
3. 当社は一連の「アクティブなブログ」を維持しています。これは、少なくとも 1 つの未処理の要素がまだ含まれているブログを意味します。 アクティブな各ブログには、現在の候補値があります。 
4. すべてのアクティブなブログの中で、現在の候補が最も小さいブログを繰り返し選択します。 これにより、値をさらに右に押し出すブログを選択することによって、小さな値のできるだけ早い出現が遅れることがなくなります。 
5. ブログを選択した後、そのすべての要素をグローバルな意味で処理済みとしてマークし、現在の候補が処理されると他のブログのポインタを進めます。 これにより、アクティブ セットが動的に更新されます。 
6. 選択したブログ順序は、ビルドの正しい順方向実行順序をシミュレートするために逆にされます。$Q$。 
7. 最後に、計算されたブログ順序を使用して、最前面に移動するプロセスをシミュレートして構築します。$Q$。 

重要な考え方は、ある値が何らかのブログで利用可能な最小の候補になった場合、そのブログを遅らせても、その値が最終シーケンスの奥深くに押し込まれる危険を冒すだけであるということです。 したがって、貪欲にそれをロックすると、辞書編集上の最適性が維持されます。 

### なぜ効果があるのか

 このアルゴリズムは、すべてのステップで、まだ目に見えない最小限の要素に影響を与える可能性のあるすべてのブログの中から、可能な限り最小の次の値を最も早く公開するものを常に選択するという不変条件を維持します。 別の選択肢を選択すると、小さい値が遅れるか、より大きい値が強制的に早く表示されます。$Q$、どちらも辞書編集上の順序を悪化させます。 Move-to-Front 操作では常に最新性が優先されるため、各値の最後の出現を制御することで最終位置が完全に決定され、貪欲な順序により、辞書編集上最小限の方法でこれらの最後の出現の順序が最大化されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    blogs = []
    values = set()

    for _ in range(n):
        tmp = list(map(int, input().split()))
        l = tmp[0]
        arr = tmp[1:]
        blogs.append(arr)
        for x in arr:
            values.add(x)

    # coordinate compression (optional but safe)
    vals = sorted(values)
    mp = {v:i for i,v in enumerate(vals)}

    blogs = [[mp[x] for x in b] for b in blogs]
    m = len(vals)

    # track last occurrence candidate logic
    from heapq import heappush, heappop

    used = [False] * m
    ptr = [0] * n
    active = set(range(n))

    # min-heap of (current candidate, blog_id)
    heap = []

    def refresh(i):
        while ptr[i] < len(blogs[i]) and used[blogs[i][ptr[i]]]:
            ptr[i] += 1
        if ptr[i] < len(blogs[i]):
            heappush(heap, (blogs[i][ptr[i]], i))

    for i in range(n):
        refresh(i)

    order = []

    while heap:
        v, i = heappop(heap)
        if i not in active:
            continue
        # ensure current candidate is valid
        while ptr[i] < len(blogs[i]) and used[blogs[i][ptr[i]]]:
            ptr[i] += 1
        if ptr[i] >= len(blogs[i]):
            active.discard(i)
            continue
        if blogs[i][ptr[i]] != v:
            heappush(heap, (blogs[i][ptr[i]], i))
            continue

        # choose blog i
        order.append(i)
        active.discard(i)

        # mark all elements as used
        for x in blogs[i]:
            used[x] = True

        # refresh affected blogs lazily
        for j in range(n):
            if j in active:
                refresh(j)

    # simulate Q construction
    Q = []
    seen = set()

    for i in reversed(order):
        for x in blogs[i]:
            if x in seen:
                Q.remove(x)
                Q.insert(0, x)
            else:
                seen.add(x)
                Q.insert(0, x)

    print(*[vals[x] for x in Q])

if __name__ == "__main__":
    t = int(input())
    for _ in range(t):
        solve()
```このソリューションでは、まずユーザー ID を圧縮するため、比較と記録が効率的になります。 ブログの貪欲な順序付けは、各ブログの現在の最小のまだ関連性のある要素をキーとするヒープを使用して実装されます。 ブログが選択されると、そのすべての要素が使用済みとしてマークされ、他のブログはポインタを進めるように強制されます。 

最終的なシミュレーションのビルド$Q$問題の「前へ移動」ルールに従って、選択した処理順序の逆にブログを反復します。 最後に処理されたブログによって最初の構造的変更が決定されるため、この逆方向が重要になります。$Q$。 

微妙な点は、シミュレーション ステップでのリストの削除は概念的には正しいですが、最適ではないということです。 より厳密な実装では、リンクされた構造または位置マップが使用されます。 ただし、制約があるため、微細な最適化ではなく、順序付けの正確さに重点が置かれ続けます。

 ## 特殊なケース

 重大なエッジケースは、ユーザーが 1 つのブログ内に複数回表示される場合です。 発生するたびに前方への移動がトリガーされるため、前処理内の重複を削除すると正確性が損なわれます。 たとえば、次のようなブログ`[3, 3, 1]`2番目を治療しなければなりません`3`要素を再プロモートする実際の操作として。 

2 つのブログが 1 つの小さな要素のみを共有する場合、別のエッジ ケースが発生します。 アルゴリズムは、その最小の要素を含むブログが、より大きな要素を最初に導入する別のブログを過ぎて遅れないようにする必要があります。 貪欲なヒープ選択では、常に現在の最小の候補を選択することでこれを強制し、共有される最小限の要素が最も早い安全な瞬間に処理されるようにします。 

最後のエッジケースは、すべてのブログに重複するユーザーのセットが含まれている場合です。 このシナリオでは、ポインターの前進が不可欠になります。 すでに処理された値をスキップせずに、ヒープは古い候補を繰り返し検討し、順序を変更します。
