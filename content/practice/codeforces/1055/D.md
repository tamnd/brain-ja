 ## 問題の理解

 いくつかの文字列のペアが与えられます。各ペアは、変数名が現在どのように見えるか、および単一のグローバル リファクタリング操作後にどのように見えるべきかを記述します。 リファクタリング ツールは非常に特殊な方法で動作します。2 つの文字列を選択し、それらを呼び出します。$s$そして$t$次に、すべての変数名を左からスキャンします。 もし$s$部分文字列として出現し、最初に出現したものだけが次の文字列に置き換えられます。$t$。 表示されない場合、文字列は変更されません。 

タスクは、単一のペアが存在するかどうかを判断することです。$(s, t)$このルールをすべての初期名に同時に適用すると、正確にすべてのターゲット名が生成されます。 可能であれば、有効なペアを 1 つ出力する必要があります。 

重要な問題は、同じ部分文字列の置換では、変更されたすべての文字列を一度に説明しなければならない一方で、未変更の文字列は完全にそのままにしておく必要があることです。 これにより、グローバルな一貫性制約が作成されます。同じパターンがすべての変換を担当する必要があります。 

この制約により、長さ 3000 文字までの文字列が 3000 文字まで許可されるため、合計文字数は約 3000 文字に達する可能性があります。$9 \times 10^6$。 これにより、すべての部分文字列を試行したり、多くの候補の置換を個別にシミュレートしたりするアプローチは除外されます。 二次関数またはそれより劣る文字列ごとのメソッドは遅すぎます。 

単純な間違いは、1 つの文字列がターゲットと異なる位置を選択してビルドできると仮定することです。$s$その文字列のみからローカルで。 他の文字列には別のコンテキストが必要な可能性があるため、これは失敗します。 

たとえば、1 つのペアが次のとおりであるとします。```
abcde -> abXde
```そしてもう1つは次のとおりです。```
abfde -> abYde
```選ぶなら$s = c$1 つ目からは、2 つ目では何も機能しません。 選ぶなら$s = d$、変更されていない文字列内の意図しない位置に誤って表示され、誤った置換が発生する可能性があります。 

もう 1 つの微妙な失敗は、候補部分文字列が「適切な」文字列の前に出現するときに発生します。 意図した位置で正しく変換された場合でも、ルールは最初に出現したもののみを置き換えるため、以前に出現したものは正確性を静かに破ります。 

## アプローチ

 強引なアイデアは、考えられるすべての選択肢を試してみることです。$s$任意の初期文字列の任意の部分文字列として、各候補についてすべての文字列の変換をシミュレートし、適切な文字列を選択してすべてのターゲットに一致するかどうかを確認します。$t$。 有効なソリューションは少なくとも 1 つの入力文字列に存在する部分文字列を使用する必要があるため、これは概念的には正しいです。 ただし、$O(nL^2)$部分文字列と各シミュレーションのコスト$O(nL)$、実行不可能な結果につながります$O(n^2 L^3)$最悪の場合。 

重要な点は、文字列がターゲットと異なる最初の位置によって変換が完全に決定されるということです。 この位置により、影響を受けるすべての文字列内で部分文字列が「開始」する場所が強制されます。これより前の位置は、変更された文字列に影響しないか、変更されていない文字列に誤って影響を与えるためです。 

このアンカー位置から、最小の部分文字列の構築を試みることができます。$s$これは、変更されたすべての文字列にわたって一貫しており、同時に次のように導出されます。$t$ターゲット文字列から。 開始位置を固定すると、変更されたすべてのペア間で一貫性を維持しながら、部分文字列を貪欲に拡張できます。

 ## アルゴリズムのチュートリアル

 私たちは最適な建設戦略に重点を置いています。 

まず、最も早い位置を見つけます$p$少なくとも 1 つのインデックスが存在するようにする$i$と$w_i[p] \ne w'_i[p]$。 この位置は、変換を有効にする必要がある最初の場所です。 任意の有効な部分文字列$s$この位置を含める必要があります。そうでないと、異なる文字が変更されません。 

次に、すべてのインデックスを収集します$i$どこ$w_i \ne w'_i$。 これらは、リファクタリング操作によって変更する必要がある「アクティブな」文字列です。 

3 番目に、位置から始まる候補部分文字列の構築を試みます。$p$。 設定しました$s$最初は$w_i[p]$任意のアクティブな文字列に対して$i$すべてのアクティブな文字列がこの文字に一致する必要があるためです。 彼らが同意しない場合、解決策は存在しません。 

4 番目に、部分文字列を可能な限り右に拡張します。 各拡張ステップでは、すべてのアクティブな文字列が元の文字列内の同じ文字を共有している必要があります。$s$、また、ターゲット文字列内の同じ文字を共有します。$t$。 これにより、両方が保証されます。$s$そして$t$すべての変換にわたって一貫性を保ちます。 

5 番目に、拡張を停止したら、次のように定義します。$s$元の文字列から$t$この間隔のターゲット文字列から。 

6 番目に、候補者を検証します。 すべてのアクティブな文字列について、最初に出現した文字列を置換する効果をシミュレートします。$s$。 重要なチェックは、この最初の出現が正確な位置で開始する必要があることです。$p$そうでない場合は、別のオカレンスが置き換えられ、結果が分岐します。 

7 番目に、非アクティブな文字列ごとに (ここで、$w_i = w'_i$)、私たちはそれを保証します$s$は文字列のどこにも現れません。 そうしないと、操作によって誤って変更されてしまいます。 

すべてのチェックに合格した場合、ペアを出力します$(s, t)$。 そうでなければ、答えは不可能です。 

### なぜ効果があるのか

 この構造により、置換ウィンドウが最初のグローバル不一致位置に強制的に揃えられます。 有効な解決策は少なくとも 1 つの異なる文字に影響を与える必要があり、そのような最も早い位置が左側の境界を固定します。 この境界が固定されると、変更されたすべての文字列にわたる一貫性により、部分文字列の一意の拡張が強制されます。 検証ステップでは、意図しない以前の出現が存在しないことを保証し、「最初の出現のみ」ルールの正確さを維持します。 これにより、変更されていない文字列での過剰適用と、変更された文字列での不整合な置換の両方が防止されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    w = [input().strip() for _ in range(n)]
    t = [input().strip() for _ in range(n)]

    changed = []
    first_diff = None

    for i in range(n):
        if w[i] != t[i]:
            changed.append(i)
            if first_diff is None:
                for j in range(len(w[i])):
                    if w[i][j] != t[i][j]:
                        first_diff = j
                        break

    if not changed:
        print("YES")
        print("a")
        print("a")
        return

    p = first_diff

    # build s and t by extending to the right
    l = p
    r = p

    m = len(w[changed[0]])

    while True:
        if r + 1 >= m:
            break

        ok = True
        for i in changed:
            if w[i][r + 1] != w[changed[0]][r + 1]:
                ok = False
                break
            if t[i][r + 1] != t[changed[0]][r + 1]:
                ok = False
                break

        if not ok:
            break

        r += 1

    s = w[changed[0]][l:r+1]
    tt = t[changed[0]][l:r+1]

    def apply(s, tt, x):
        pos = x.find(s)
        if pos == -1:
            return x
        return x[:pos] + tt + x[pos+len(s):]

    # validate changed
    for i in changed:
        if apply(s, tt, w[i]) != t[i]:
            print("NO")
            return

    # validate unchanged
    for i in range(n):
        if i not in changed:
            if s in w[i]:
                print("NO")
                return

    print("YES")
    print(s)
    print(tt)

if __name__ == "__main__":
    solve()

の`apply`関数は、を使用してエディターの動作を正確に反映します。`find`、左から最初に出現するものを返します。 たとえ部分文字列が複数回出現したとしても、最初に出現したものだけが影響を受けるため、これは非常に重要です。 

最後に、検証によって両方向が安全であることが確認されます。変更された文字列は変換後に正確に一致する必要があり、変更されていない文字列にはパターンがまったく含まれていてはなりません。

 ## 特殊なケース

 厄介な状況の 1 つは、候補部分文字列が変更されていない文字列の前に出現する場合です。 アルゴリズムは、次のような解決策を明示的に拒否することでこれを処理します。$s$文字列内で発生したものは変更しないでください。 これにより、「最初のみ」ルールによる誤った変更が防止されます。 

もう 1 つの微妙なケースは、複数の異なる文字列が部分文字列の異なる拡張子を示唆する場合です。 この構造では、拡張中にすべてのアクティブな文字列が文字ごとに一致することを要求することにより、一貫性が確保されます。 発散が発生した場合、拡張は直ちに停止し、他の文字列を犠牲にして 1 つの文字列にオーバーフィットすることがないようにします。 

最後のエッジ ケースは、最初の不一致位置によって、変更された文字列の置換を一意にトリガーしない部分文字列が発生する場合です。 検証ステップでは、構造的な仮定に依存するのではなく、実際の置換動作をシミュレートすることでこれを捉えます。
