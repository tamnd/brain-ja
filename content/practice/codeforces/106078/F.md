 ## 解決策
 ## 問題の理解

 この問題は、時間間隔の集合が与えられたシステムをモデル化しており、各間隔は、そのタイプに応じてリソースに寄与または消費するイベントを表します。 各イベントには時間とラベルがあり、スケジュール プロセスにおいてイベントが「開始」アクションのように動作するか、「終了」アクションのように動作するかを決定します。 このタスクは、タイミングと順序条件が尊重される場合にのみペアリングが有効であるという制約の下で形成できる、互換性のあるイベントの完全なペアの最大数を決定することです。 

これをより具体的に理解する方法は、各項目が指示された機会として解釈できるということです。イベントによっては、特定の瞬間にキャパシティを生み出すものもあれば、後からそのキャパシティを必要とするイベントもあります。 目標は、時間順序を考慮して、以前に作成された容量を使用して満たせる要件の数を最大化することです。 

入力は複数の独立したシナリオで構成されます。 シナリオごとに、イベントのリストを読み取ります。各イベントは、時間値と、それが「供給タイプ」のイベントであるか「需要タイプ」のイベントであるかを示すバイナリ フラグによって記述されます。 各シナリオの出力は単一の整数、つまり有効な供給イベントと照合できる需要イベントの最大数です。 

重要な制約の意味は、イベントの数が十分に大きくなり、二次ペアリング戦略が即座に実行不可能になる可能性があることです。 供給イベントと需要イベントのすべてのペアをチェックするソリューションでは、最悪の場合 O(n²) の比較が必要になりますが、n が約 10⁵ に達すると機能しなくなります。 

複数のイベントが同じタイムスタンプを共有する場合、微妙なエッジケースが発生します。 イベントを任意の順序で処理する素朴な貪欲なアプローチでは、同時に発生する需要と供給を誤って組み合わせる可能性がありますが、順序付けルールによっては実際には使用できません。 たとえば、需要と供給の両方が時刻 5 で発生し、ルールが厳密な時間的優先順位を必要とする場合、不用意に実装すると、それらを交換可能なものとして扱う可能性があります。 

すべてのイベントが同じタイプである場合、別の失敗ケースが発生します。 すべてが供給イベントの場合、ペアリングは不可能であり、答えはゼロでなければなりません。 すべてがデマンド イベントの場合も、ペアリングはできません。 チェックを行わずに各タイプの少なくとも 1 つを想定するソリューションは、誤って縮退します。 

## アプローチ

 この強引なアイデアは、すべての需要イベントをすべての互換性のある供給イベントと明示的に一致させようとすることです。 需要ごとに、以前に発生したすべての供給をスキャンし、まだ使用されていないものを選択します。 これは、ペアリング制約を直接強制するため、簡単で正しいものです。 

このアプローチの問題は、最大 n 個のイベントのそれぞれについて、他のほぼすべてのイベントをスキャンする可能性があることです。 これにより、最悪の場合、約 n × n 回の比較が行われることになり、n が 105 の場合、およそ 10¹⁰ 回の演算になります。 これは、一般的な 2 秒の制限が処理できる範囲をはるかに超えています。 

重要な構造的観察は、イベントの絶対的なアイデンティティではなく、時間内でのイベントの順序のみが重要であるということです。 イベントを時間別に分類すると、利用可能な供給能力のプールを維持できるタイムラインを効果的にシミュレートすることになります。 各デマンドは、このプールから 1 ユニットを消費するか、プールが空の場合はスキップされます。 

これにより、問題は単一パスの貪欲なプロセスに変換されます。 すべてのペアリングを試す代わりに、これまでに確認された未使用の供給イベントの数を表すカウンターを維持します。 需要イベントに遭遇すると、可能であればすぐにそれにマッチし、カウンターから 1 ユニットを消費します。 供給イベントに遭遇すると、カウンターが増加します。 

これが機能するのは、時間順序が厳密に劣る早期のソリューションを優先して供給の一致を延期することによって最適なソリューションが恩恵を受けることは決してないからです。 将来の需要を満たすには、最も早い時期に利用可能な供給は常に、その後の供給と少なくとも同程度に優れています。

 ## アルゴリズムのチュートリアル

 1. テスト ケース内のすべてのイベントを読み取り、それぞれを (時間、タイプ) のペアとして表します。 このステップは、順序付けが意味のある形式に問題を線形化するために必要です。 
2. すべてのイベントを時間の増加順に並べ替えます。 これにより、イベントが発生した正確な順序でタイムラインを処理することが保証されます。ペアリングは一時的な実現可能性に依存するため、これが必要です。 
3. カウンタの初期化`available`ゼロに。 この変数は、発生した未使用の供給タイプのイベントの数を追跡します。 
4. 並べ替えられたイベントを繰り返し処理します。 イベントごとに、そのタイプに基づいて分岐します。 
5. イベントが供給イベントの場合、インクリメントします。`available`1つずつ。 これは、その時点でシステムに使用可能な容量が 1 単位追加されることを表します。 
6. イベントがデマンド イベントの場合は、`available`はポジティブです。 そうであれば、デクリメントします`available`この需要を以前に確認された供給と一致させることができるため、答えを 1 増やします。 
7. もし`available`要求を処理するときはゼロなので、スキップします。 これは、これを満足できる以前の供給が存在しないことを意味します。 

### なぜ効果があるのか

 あらゆる時点で、`available`は、発生したがまだ需要に割り当てられていない供給イベントの数を正確に表します。 有効なマッチングでは、各需要を個別の以前の供給と組み合わせる必要があり、貪欲な手順では、ID ではなくカウントのみを追跡することによって、常に最も早い利用可能な供給を暗黙的に使用します。 将来の決定は、どの特定の電源が使用されたかには決して依存せず、残りの数にのみ依存するため、カウンタは関連するすべての状態を完全に捕捉します。 この不変条件により、需要が一致するたびに、その選択肢を以前の未使用の供給に置き換えても、タイムラインの残りのサフィックスの実現可能性が変わらないことが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        events = []
        for _ in range(n):
            time, typ = map(int, input().split())
            events.append((time, typ))

        events.sort()

        available = 0
        ans = 0

        for time, typ in events:
            if typ == 0:
                available += 1
            else:
                if available > 0:
                    available -= 1
                    ans += 1

        print(ans)

if __name__ == "__main__":
    solve()
```実装はアルゴリズムに直接に従います。 ソートは唯一の非線形ステップであり、グリーディ スイープに必要な時間構造を確立します。 整数`available`はシステム全体の状態であるため、明示的に構造を一致させる必要がありません。 

よくある実装上の間違いの 1 つは、型フラグの解釈を混同することです。 需要と供給が逆転した場合でもアルゴリズムは実行されますが、系統的に不正確な結果が生成され、小規模なテストでは妥当に見えることがよくあります。 もう 1 つの問題は、時間による並べ替えを忘れることです。これにより、早い供給品が常に最初に処理されるという前提が崩れ、不正確なペアリング順序が発生します。 

## 実用的な例

 ### 例 1

 イベントを考慮します: (1, 供給)、(2, 需要)、(3, 供給)、(4, 需要)

 ソート後も順序は変更されません。 

| イベント | 利用可能 | 答え |
 | --- | --- | --- |
 | (1,供給) | 1 | 0 |
 | (2,需要) | 0 | 1 |
 | (3,供給) | 1 | 1 |
 | (4,需要) | 0 | 2 |

 このトレースは、各需要が可能な限り早い供給と一致していることを示しており、供給が不必要に無駄にならないという貪欲な不変条件を裏付けています。 

### 例 2

 イベントを考慮します: (1,需要)、(2,供給)、(3,需要)、(4,供給)

 | イベント | 利用可能 | 答え |
 | --- | --- | --- |
 | (1,需要) | 0 | 0 |
 | (2,供給) | 1 | 0 |
 | (3,需要) | 0 | 1 |
 | (4,供給) | 1 | 1 |

 これは、供給より前に到着した需要は正しく無視されますが、後の供給は将来の需要に対して依然として有用であることを示しています。

 ## 特殊なケース

 重要なエッジケースの 1 つは、供給よりも先に需要が現れる場合です。 入力用`(1,demand) (2,supply)`、アルゴリズムは最初に要求を処理し、正しく何も実行しません。`available`はゼロです。 供給が後で到着した場合、それは将来の需要に対してのみ使用可能になり、遡って使用することはできないため、正確さが保たれます。 

もう 1 つのケースは、単一の需要の前に複数の供給がある場合です。 のために`(1,supply) (2,supply) (3,demand)`、カウンターは 1 回消費される前に 2 回増加し、未使用の供給が 1 つ残ります。 このアルゴリズムは、追加の簿記を必要とせずに、後の需要に備えて残りの容量を自然に保存します。 

最後の微妙なケースは、貪欲な順序が視覚的には重要だが論理的には重要ではないインターリーブです。`(1,supply) (2,demand) (3,demand)`。 最初の需要は利用可能な供給のみを消費し、2 番目の需要はスキップされます。 後の需要のために供給を「予約」しようとする別の解釈は、供給の貢献度が区別できないため、結果を改善しません。
