 ## 解決策
 ## 問題の理解

 いくつかのレシピが与えられ、それぞれのレシピには、材料が満たされたときに固定数のスロットを備えた製造装置がどのように動作するかが記述されています。 レシピは k 個の位置にわたるパターンであり、各位置は空であるか、特定の種類の材料が含まれています。 デバイスが使用されるたびに、現在の構成がレシピと一致する場合、そのレシピが実行され、パターンに含まれる空でない各スロットから 1 ユニットが消費されます。 

最初はすべての材料が無制限ですが、レシピが実行されると、対応するスロットのカウントが減少します。 このプロセスは、少なくとも 1 つのレシピが適用できる限り継続されます。 一致するレシピを繰り返し適用することで、少なくとも 1 回実行できる個別のレシピの数を最大化できるように、k 個のスロットの初期充填を選択したいと考えています。 

重要な点は、レシピが任意のリソースをグローバルに消費しないことです。 一致する特定のスロットからのみ消費します。 これにより、システムは、材料のグローバルなカウントではなく、位置と値間でレシピがどのように重複するかに完全に依存するようになります。 

n、k ≤ 2000 という制約は、O(n²) または O(nk) スタイルのソリューションが境界線で許容可能であることを意味しますが、レシピ アプリケーションのシーケンスをシミュレートしたり、スロットの可能なすべての充填を考慮しようとしたものは大きすぎます。 スロットへの材料の割り当てに対する強引な操作は k において指数関数的であり、直ちに不可能です。 

単純な失敗例は、複数のレシピが部分構造を共有する場合に発生します。 たとえば、2 つのレシピが 1 つのスロットでのみ異なる場合、異なる初期割り当てにより両方が許可される場合でも、そのスロットについて貪欲な決定を行うと、誤って一方が削除される可能性があります。 これは、レシピごとのローカルな決定が信頼できないことを示しています。 

重要な隠された構造は、各スロットに配置される材料の種類を決定すると、レシピは完全に互換性を持つか、まったくトリガーされないかのどちらかになるということです。 プロセス全体は、その中に「含まれる」レシピ パターンの数を最大化する k 長の割り当てを選択することに帰着します。つまり、ゼロ以外のエントリはすべて正確に一致します。 

単純なアプローチでは、実行順序をシミュレートするか、互換性のあるレシピを 1 つずつ貪欲に選択しようとしますが、互換性は有用な方法で動的に変化しません。 スロットが固定されると、その後の選択に合わせてスロットを調整することはできません。したがって、問題は基本的に、多くのパターンを同時に満たすグローバル割り当てを選択することになります。 

## アプローチ

 この強引なアイデアは、k 個のスロットの可能なすべての充填を試し、各充填に対してどのレシピをトリガーできるかをシミュレートすることです。 各スロットが入力レシピに表示される値に制限されても、各スロットは独立して多くの値を取ることができるため、依然として指数関数的な数の構成が残ります。 各構成について、n 個のレシピをすべてチェックするには O(nk) がかかるため、合計は完全に不可能になります。 

重要な洞察は、視点を逆転させることです。 充填レシピを選択してレシピをテストするのではなく、レシピをスロット割り当ての制約とみなします。 各レシピは、ゼロ以外の位置ごとに、そのレシピを実行可能にする場合にスロットに何を含める必要があるかを指定します。 いずれかのスロットで 2 つのレシピが一致しない場合、同じ初期充填で両方を同時に満たすことはできません。 

これにより、問題は、必要なスロット割り当てに関してペアごとに一貫性のあるレシピの最大のサブセットを選択することに変わります。 一貫性はスロットごとに定義されます。2 つのレシピが同じ位置にゼロ以外の値を指定する場合は常に、その値に一致する必要があります。 空のエントリはワイルドカードのように動作し、スロットを制限しません。

最適な充填は、任意の最大一貫セットから構築できます。スロットごとに、選択したレシピによって制約される場合、値は固定されます。 それ以外の場合は任意にすることができます。 この割り当てが選択されると、一貫性のあるセット内のすべてのレシピが実行可能になります。これは、レシピのパターンがスロット構成と一致し、リソース競合によってレシピが少なくとも 1 回出現することが妨げられないためです。 

したがって、問題は、どの位置でも競合しないレシピの最大グループを見つけることに帰着します。これは、k 次元にわたる構造化された互換性最大化問題です。

 ## アルゴリズムのチュートリアル

 1. すべてのレシピを読み取り、各レシピを k スロットにわたる部分的な割り当てとして扱います。ここで、ゼロ以外のエントリのみが制約を課します。 この再定式化により、各レシピは (位置、値) ペアのセットになります。 
2. 各レシピについて、選択したレシピのセットを表す成長構造と互換性があるかどうかを判断します。 最初に最終セットを明示的に構築する代わりに、スロット制約を段階的に維持します。 
3. レシピを任意の順序で処理し、スロットごとに「未割り当て」または固定の材料値を記録する配列を維持します。 この配列は、現在の暗黙的な塗りつぶしを表します。 
4. レシピを検討するときは、ゼロ以外のすべての位置を確認します。 スロットが割り当てられていない場合は、レシピの値を採用できます。 すでに割り当てられている場合は、レシピの値と一致する必要があります。そうでない場合、このレシピは現在の一貫性のあるセットに含めることができません。 
5. レシピに互換性がある場合は、それを受け入れ、それに接触するすべての未割り当てスロットを更新します。 これにより、現在の割り当てが、これまでに選択されたすべてのレシピと一貫性を保つことが保証されます。 
6. 受け入れられたレシピの数を数えます。 このカウントは、最大の一貫したセットを表し、その多くの個別の実行可能レシピを達成する有効な充填に対応します。 

この貪欲な構築が機能する理由は、スロットに値が割り当てられると、その割り当てがそのスロットを使用する最初のレシピによって強制されるためです。 これに矛盾する将来のレシピは同じ構成内に共存できないため、拒否することは避けられません。 すべてのスロット制約は絶対的なものであり、一貫性を超えて順序に依存しないため、割り当ての決定を延期してもメリットはありません。 

### なぜ効果があるのか

 このアルゴリズムは、受け入れられたすべてのレシピが、これまでに割り当てられたすべてのスロットに一致するという不変条件を維持します。 新たに受け入れられたレシピはすべて、新しい制約を導入するか、既存の制約に同意します。 競合がある場合は、単一のグローバル割り当てが現在の構造と新しいレシピの両方を満たすことができないことを直ちに意味するため、競合をスキップしても、達成可能な一貫したセットの最大値は減りません。 したがって、最終セットはペアごとに一貫したレシピの最大セットであり、すべてを実現する実現可能な充填に直接対応します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    recipes = [list(map(int, input().split())) for _ in range(n)]

    slot = [-1] * k
    used = 0

    for r in recipes:
        ok = True
        for i in range(k):
            if r[i] == 0:
                continue
            if slot[i] == -1:
                continue
            if slot[i] != r[i]:
                ok = False
                break

        if not ok:
            continue

        for i in range(k):
            if r[i] != 0:
                slot[i] = r[i]

        used += 1

    print(used)

if __name__ == "__main__":
    solve()
```コードは単一のグローバル割り当て配列を維持します。`slot`、これはクラフターの現在の暗黙の構成を表します。 各反復内の最初のループは、レシピがこの部分的な割り当てと共存できるかどうかをチェックします。 2 番目のループは、受け入れられた場合にその制約を適用します。 

一般的な実装の落とし穴は更新です`slot`互換性を完全に検証する前に。 それは状態を破壊し、矛盾するレシピを誤って受け入れることになります。 検証パスとそれに続く更新パスに分割することで、これを防ぐことができます。 

もう 1 つの微妙な点は、ゼロ エントリを正しく処理することです。 ゼロは空の強制割り当てではなく「制約なし」を表すため、既存のスロット値を決して上書きしてはなりません。

 ## 特殊なケース

 重要なエッジ ケースは、複数のレシピが同じスロットに異なる値を割り当てようとしたときに、部分的な割り当てがすでに行われた後にのみ発生します。 たとえば、最初に受け入れられたレシピがスロット 0 を値 5 に固定する場合、スロット 0 を 7 にする必要があるその後のレシピは直ちに拒否されなければなりません。 アルゴリズムは、更新を適用する前に整合性をチェックすることでこれを処理し、スロットへの最初の割り当てが永続的な制約になるようにします。 

レシピにゼロ以外のエントリがない場合、別のケースが発生します。 このようなレシピには制約が課されず、常に互換性があります。 検証ループでは競合する位置が検出されず、更新ループでは割り当てが実行されないため、アルゴリズムはスロットを変更せずにそれを正しく受け入れます。 

これらのケースは、グローバルに一貫した割り当てを維持しながら、ソリューションが制約と非制約を正しく区別していることを確認します。
