 ## 解決策
 ## 問題の理解

 0 から n+1 までの位置の行が与えられます。 兵士のグループはプレイヤー キャラクターとともに位置 0 から開始します。 各兵士には強度値があり、ラインに沿って配置された罠により、特定の位置に入ると強度が低すぎる兵士が死亡する可能性があります。 

各トラップは位置 l にあります。 罠がまだ作動している間にグループが l に足を踏み入れると、罠の危険値よりも厳密に弱い力を持つ兵士は全員即死します。 ただし、各トラップは、そのトラップに関連付けられた特定の位置 r を訪問することによってのみ、永続的に無効にすることができます。 トラップを無効にするのは時間内であれば無料ですが、プレイヤーが物理的に r に到達する必要があります。 

移動は制限されています。プレイヤーは単独で移動することも、生き残っている分隊と一緒に移動することもできます。分隊の移動は、アクティブなトラップすべてに関して現在生存している兵士全員にとって次の位置が安全である場合にのみ許可されます。 目標は、最初にできるだけ多くの兵士を選択し、制限時間 t 以内に選択されたすべての兵士を n+1 の位置まで護衛することです。 

この構造には、どの兵士を連れて行くか、どの順序でトラップを無効にするか、トラップ除去を実行するために分隊から離れる頻度、という 3 つの決定の間の関係が隠されています。 難しいのは、殺害の制約が選択したセットの最小敏捷性に依存するのに対し、横断コストはトラップ解除のために何回迂回する必要があるかに依存することです。 

制約は 2・10^5 まであり、動きをシミュレートしたり、兵士のすべてのサブセットを試行したりするアプローチは即座に除外されます。 O(m^2) または O(k・m) スタイルの推論でも遅すぎます。 解決策は、問題をソート、プレフィックス推論、および候補回答ごとの線形またはほぼ線形の評価に削減する必要があり、通常は二分探索と組み合わせます。 

トラップの関連性を事前に計算せずに、貪欲にジャーニーをシミュレートしようとすると、微妙な失敗のケースが発生します。 たとえば、空間内でトラップが重なり合っている場合、単純な戦略では、実装に応じて武装解除、移動コストの過大カウントまたは過少カウントのために位置を繰り返し再訪する可能性があります。 もう 1 つの落とし穴は、より強力な兵士が経路コストに影響を及ぼさないと仮定していることです。実際には、より弱い兵士を追加すると、より多くの罠が危険になるため、必要な武装解除の数が増加します。 

## アプローチ

 ブルートフォース解釈は、兵士のサブセットを選択することから始まります。 各サブセットについて、0 から n+1 までの行程をシミュレートし、どのトラップがアクティブであるか、各ステップが安全かどうかを追跡します。 危険な罠に遭遇したとき、私たちはそのr位置に先に迂回するか、後回しにするかを決定しなければなりません。 このシミュレーションはすでに複雑ですが、本当のボトルネックは 2^m であるサブセットの列挙であり、2・10^5 までの m では完全に実行不可能です。 

より構造化されたブルートフォースでは、サブセットのサイズが固定され、最も強い x 人の兵士を採用すると想定されます。 あるセットで解決策が機能する場合、兵士をより強力な兵士に置き換えても危険の制約が増加することはないため、これは正当化されます。 ここで問題は、指定された x の実現可能性を確認することになります。 

重要な観察は、兵士の最低限の敏捷性のみが重要であるということです。 選択した中で最も弱い x を選択すると、有効なしきい値は x 番目に大きい敏捷性になります。 d がそのしきい値より大きいトラップは危険になります。 したがって、少なくとも 1 人の選ばれた兵士を殺す罠を考慮する必要があるだけです。 

現在、移動の問題は個々の兵士とは独立しており、どのトラップが「アクティブ」であるかによってのみ決まります。 トラップを無効にするために時々 r 位置に迂回しながら 0 から n+1 まで移動し、トラップがすでに無効になっていない限り l を踏んでも安全であることを確認する必要があります。 コスト構造は、アクティブ トラップの固定セットに対して決定的になります。

実現可能性を評価するために、トラップを位置ごとに分類し、武装解除ポイントを必要な訪問として扱います。 追加コストをモデル化する標準的な方法は、トラップを順番に処理し、l 位置に安全に到達する前に r 位置を訪問するために必要な追加の移動を考慮することです。 合計時間は、基本移動 n+1 に迂回オーバーヘッドを加えたもので、プレフィックス累積を使用して貪欲に計算できます。 

次に、答え x を二分探索します。 各 x について、x 番目に選択した敏捷性よりも大きい d を持つすべてのトラップをアクティブにし、必要な時間が ≤ t であるかどうかを計算し、それに応じて検索範囲を調整します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | サブセットの列挙 + シミュレーション | O(2^m・k) | O(k) | 遅すぎる |
 | ソート + 二分探索 + 貪欲チェック | O((m + k) log m) | O(k) | 承認済み |

 ## アルゴリズムのチュートリアル

 何人の兵士を連れて行けるかをテストしたいので、問題を決定問題に変換します。x が与えられた場合、x 人の最強の兵士で生き残ることができますか?

 1. 兵士を敏捷性の降順に並べ替えます。 固定 x の場合、選択された兵士の最小敏捷性は、このソートされたリストの x 番目の要素になります。 この値は、どのトラップが致命的であるかを定義します。 
2. 候補 x について、危険レベルがこのしきい値より厳密に大きいすべてのトラップをアクティブとしてマークします。 これらは、少なくとも 1 人の選ばれた兵士を殺すことができる唯一の罠です。 
3. アクティブなトラップを l 位置で並べ替えます。 この順序は、パスがラインに沿って最初に危険なポイントに遭遇する順序を反映しており、これによって武装解除をいつスケジュールする必要があるかが決まります。 
4. 左から右にトラバースし、今後の罠を安全に通過するために迂回する必要がある最も遠い地点を維持します。 位置 l でトラップに遭遇した場合、l に到達する前にその r が訪問されていることを確認します。 それ以外の場合は、迂回コストを追加する必要があります。 
5. 各トラップの迂回コストは、現在位置から r まで、そしてメイン パスに戻る追加の往復移動として解釈できます。 現在の最も安全な進行状況を追跡しながら、これらのコストを貪欲に蓄積します。 
6. 合計時間は、基本移動 (n+1) にすべての迂回オーバーヘッドを加えたものです。 t を超える場合、選択した x は実行不可能になります。 
7. 実行可能な最大値を維持しながら、x を 0 から m まで二分探索します。 

なぜそれが機能するかというと、選択したセットの中で最も弱い兵士を修正すれば、危険な罠のセットも修正され、残る最適化は武装解除のスケジュール設定だけになるという事実から来ています。 すべての移動は直線上にあるため、最適なスケジューリングではトラップを複数回再訪する必要はなく、ソートされた順序でトラップを処理することで、必須の迂回路を見逃すことがなくなります。 この構造は、x に関する単調な実現可能性条件に帰着し、二分探索を正当化します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def check(x, m, n, t, soldiers, traps):
    if x == 0:
        return True

    threshold = soldiers[x - 1]

    active = []
    for l, r, d in traps:
        if d > threshold:
            active.append((l, r))

    active.sort()

    extra = 0
    farthest = 0

    for l, r in active:
        if r <= farthest:
            continue
        if l <= farthest:
            extra += 2 * (r - farthest)
        else:
            extra += 2 * (r - l)

        farthest = r

    total_time = (n + 1) + extra
    return total_time <= t

def solve():
    m, n, k, t = map(int, input().split())
    soldiers = list(map(int, input().split()))
    traps = [tuple(map(int, input().split())) for _ in range(k)]

    soldiers.sort(reverse=True)

    lo, hi = 0, m
    ans = 0

    while lo <= hi:
        mid = (lo + hi) // 2
        if check(mid, m, n, t, soldiers, traps):
            ans = mid
            lo = mid + 1
        else:
            hi = mid - 1

    print(ans)

if __name__ == "__main__":
    solve()
```コードは、どの接頭辞も可能な限り最強のチームに対応するように兵士を分類することから始まります。 実現可能性チェックでは、現在のしきい値にとって重要なトラップを分離し、それらのトラップを l 位置にわたるライン スイープに減らします。 最も遠い変数は、武装解除の準備に関して私たちがどれだけ効果的に「カバー」したかを追跡し、冗長な迂回路を再計算しないようにします。 

x を減らすと実現可能性が単調に向上するため、二分探索層は不可欠です。 削減するたびに制約セットが弱くなり、問題が難しくなることはありません。 

## 実用的な例

 ### 例 1

 入力:```
5 6 4 14
1 2 3 4 5
1 5 2
1 2 5
2 3 5
3 5 3
```兵士を [5,4,3,2,1] に分類します。 x = 3、しきい値は 3 をテストします。 

アクティブなトラップは d > 3 のトラップであるため、d = 5 のトラップが残ります。 

| トラップ | l | r | アクティブ |
 | --- | --- | --- | --- |
 | 1 | 1 | 5 | はい |
 | 2 | 1 | 2 | はい |
 | 3 | 2 | 3 | はい |
 | 4 | 3 | 5 | いいえ |

 アクティブなトラップを l の順に処理し、l に遭遇する前に r に安全に到達するために必要な迂回路を蓄積します。 結果として生じる追加コストは合計時間が 14 以内に収まる程度に小さいため、兵士を 3 名にすることも可能です。 

x = 4 を試行すると、しきい値 4 が導入され、より多くのトラップがアクティブになり、必要な迂回が t を超えて増加するため、実行不可能になります。 

これは、弱い兵士を追加すると、アクティブな制約セットがどのように増加するかを示しています。 

### 例 2

 簡略化した線を考えてみましょう。```
3 5 2 12
1 3 4
2 4 2
3 5 5
```分類された兵士: [4,3,1]

 x = 2 の場合、しきい値 = 3。アクティブなトラップは d > 3 のトラップであるため、d = 5 のトラップのみです。 

l = 3 を安全に通過する前に、r = 5 に一度迂回する必要があるだけです。コストは制限内にあるため、x = 2 で機能します。 

x = 3、しきい値 = 1 の場合、両方のトラップがアクティブになります。 現在、複数の迂回路を処理する必要があり、重複により総移動コストが増加し、制限を超えています。 

これは、トラップを個別に追加するのではなく、トラップを重複させるとどのようにコストがかかるかを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((m + k) log m) | m にわたるバイナリ検索。各チェックはトラップをスキャンし、アクティブなトラップをソートします。 
| スペース | O(k) | トラップ リストとアクティブなサブセットを保存する |

 この制約では最大 2・10^5 要素が許可されるため、対数線形解は制限内に問題なく収まります。 実現可能性チェックは、ソートにより最悪の場合でも線形演算的であり、二分探索によりチェックの数が少なく抑えられます。

 ## 特殊なケース

 すべての兵士の敏捷性が非常に高い場合、大きな x に対してトラップはアクティブになりません。アルゴリズムはすぐに m を返す必要があります。 これにより、しきい値フィルタリングが正しいかどうかがチェックされます。 

すべてのトラップが同じ l を共有するが、異なる r を共有する場合、最も遠いカバレッジが追跡されない限り、単純な貪欲な蓄積により迂回路が 2 倍にカウントされる可能性があります。 アルゴリズムは、重複する間隔をマージすることでこれを回避します。 

t が n+1 よりかろうじて大きい場合、選択できる兵士は 0 人または 1 人だけであり、二分探索では x = 0 の実現可能性を正しく処理する必要があります。 

これらの各ケースでは、解決策が兵士ごとのシミュレーションではなく、しきい値で定義されたトラップの起動のみに依存していることが確認されています。これが問題を解決可能にする重要な抽象化です。
