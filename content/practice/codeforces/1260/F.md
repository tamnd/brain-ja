 ## 解決策
 ## 問題の理解

 各頂点の色が固定されていない木が与えられています。 代わりに、すべての頂点には可能な色の範囲があり、許容範囲内で頂点ごとに 1 つの整数の色を個別に選択することを想像します。 このような完全な色の割り当てでは、最終的に同じ色になった頂点のすべてのペアを調べ、ツリー内の頂点間の距離を合計することで、ツリーの値を定義します。 

タスクは、1 つの色についてこの値を計算することではなく、すべての可能な色の割り当てを合計することです。 各頂点は複数の色を取ることができるため、割り当ての数は間隔の長さの積となり、これは天文学的に大きいため、明示的に何も列挙することはできません。 

ツリー構造は固定されているため、すべての変動は頂点間での色がどのように一致するかによってのみ生じます。 距離関数は色ではなくツリーのみに依存します。これは、色に関する組み合わせ論をエッジの構造的寄与から分離する必要があることを示唆しています。 

この制約により、ほぼ線形または線形的な解決策が求められます。 頂点が最大 100,000 個になると、ノードやカラーで 2 次的なアプローチは直ちに不可能になります。 平$O(n \log n)$すべてのペアを直接考慮しようとする場合は、ツリー DP またはリルートのアイデアを中心にメソッドを慎重に設計する必要があります。$O(n^2)$または最悪の相互作用。 

素朴な考えによる微妙な失敗例は、各色を独立して扱い、色の値ごとの寄与を合計できると仮定することです。 カラーは境界のある範囲から取得されますが、その範囲は頂点ごとに異なります。そのため、カラーごとの直接スイープでは、最大 100,000 の値を反復処理してすべてのノードをチェックする必要があり、$O(n \cdot maxColor)$、大きすぎます。 

もう 1 つの落とし穴は、ノードのペアごとに、それらを等しくするカラーリングの数を計算し、それらの距離を乗算しようとすることです。 概念的には正しいものの、それでも次のような結果につながります。$O(n^2)$ペア、これは不可能です。 

## アプローチ

 重要な問題は、答えが、指定された割り当てで同じ色を共有する頂点のペアに依存することです。 カラーリングについて考える代わりに、視点を逆転させ、ノード ペアの寄与に焦点を当てます。 

ノードの固定ペアの場合$u, v$、同じ色を共有する色の割り当てがいくつありますか? その数がわかっている場合、それらの合計貢献度は、単純にその数にそれらの間の距離を乗算したものになります。 この場合、問題は、組み合わせ等価数とツリー距離という 2 つの独立した要素の積のすべてのペアの合計になります。 

ブルートフォース手法では、すべての色の割り当てを列挙し、それぞれのツリー値を計算し、それらを合計します。 サイズ 20 のツリーの場合でも、割り当ての数が指数関数的に増加するため、これはすでに不可能になります。$\prod (r_i - l_i + 1)$そして、各割り当てにはまだ必要になります$O(n^2)$ペアの距離。 

より構造化されたブルート フォースでは、頂点のすべてのペアを試し、それらを等しくするカラーリングの数を計算します。 これには依然として、可能な色を反復処理し、すべての頂点間の互換性をチェックする必要があります。$O(n^2 \cdot maxColor)$、限界をはるかに超えています。 

重要な観察は、合計の順序を反転することです。 カラーリングを合計してからペアにするのではなく、距離の寄与をエッジごとに分解する方法で、カラーとツリーのエッジを合計します。 ツリー ペアの合計の古典的なトリックは、ペアを分離するエッジの数として距離を表現し、各エッジを介して寄与するペアの数をカウントすることです。 

任意の固定色の場合$c$、許可される間隔に次のものが含まれるノードのセットを考慮します。$c$。 直したら$c$の場合、すべてのノードが独立してこの色を取得できるか取得できないかのいずれかになります。 色の貢献$c$答えは、同時に色を取得できるノードのすべてのペアにわたる距離の合計です。$c$。 これにより、問題は、色ごとに、誘導されたノードのサブセットにわたるペアごとの距離の合計を計算するようになります。 

次に、順序を逆にします。色を明示的に反復する代わりに、色の境界をスイープすることによってノードを処理します。 各ノードは間隔に寄与します$[l_i, r_i]$したがって、この問題を、セグメント内で各ノードがアクティブになる、色の範囲の更新として扱うことができます。 各色の位置について、アクティブなノードの誘導されたサブセットを維持し、その誘導されたツリー内のペアごとの距離の合計が必要になります。 

これにより、ツリー上で動的ノードのセットを維持し、ペアごとの合計距離を追跡しながら挿入/削除をサポートするという問題が軽減されます。 このための標準的な手法はセントロイド分解です。セントロイドの祖先を通じて貢献が維持されるため、各更新は影響のみに影響します。$O(\log n)$構造レベル。 

ノードを挿入するたびに、すでにアクティブなノードまでの距離に基づいて寄与が更新されます。 重心分解では、サブツリーカウンターと重心レイヤーごとの距離合計を使用して距離の累積を維持でき、$O(\log n)$更新情報。

 ## アルゴリズムのチュートリアル

 問題を色軸上のイベントの処理に変換し、アクティブなノードを動的に維持します。 

1. 各ノードの間隔を変換する$[l_i, r_i]$2 つのイベントに分割: でのアクティベーション$l_i$そして非アクティブ化$r_i + 1$。 これにより、どのノードが現在アクティブなカラーを取得できるかを維持しながら、カラーを昇順に処理できます。 これが機能する理由は、固定色に対して$c$、アクティブ セットは、間隔に次の内容が含まれるノードと正確に一致します。$c$。 
2. ツリーの重心分解を構築します。 これにより、各ノードが重心祖先のチェーンに属する階層が提供され、サブツリー内のノードまでの距離はこれらの重心を通じて分解できます。 目的は、グローバルなペアごとの距離追跡をレベルごとの要約に置き換えることです。 
3. For each centroid$x$、分解サブツリー内のアクティブなノードの数と、からの距離の合計という 2 つの集計を維持します。$x$すべてのアクティブなノードに。 これら 2 つの値は、新しいノードの寄与を効率的に計算するのに十分です。 
4. ノード起動時$u$、その重心パスを上っていきます。 各重心で$x$、ペアごとの距離が重心からノードまでの距離で表現できるという恒等式を使用して、既存のアクティブなノードへの寄与を計算します。 距離で重み付けされた各コンポーネントに存在する既存のノードの数を追加して、グローバルな答えを更新します。 
5. コントリビューションを追加した後、ノードを含むようにすべてのセントロイド集約を更新します。$u$。 これにより、今後の挿入で、関連するペアが正しく考慮されるようになります。$u$。 
6. 色の昇順にイベントを処理します。 色間を移動するたびに、その座標で発生するすべての挿入と削除が適用されます。 各アクティブ セットは、再計算されるのではなく、増分的に維持されます。 

### なぜ効果があるのか

 正確さは、互いに重ね合わされた 2 つの分解から得られます。 まず、すべての色の合計が色の合計として書き換えられます。ここで、各色は、それを取得できるノード上の距離の合計に独立して寄与します。 第 2 に、重心分解により、任意のペアワイズ距離を重心レベルの対数に​​沿った寄与の合計として計算できるようになります。各レベルはツリーの互いに素な構造パーティションを捕捉します。 2 番目のエンドポイントが挿入されると、ノードの各ペアが 1 回だけカウントされるため、累計は常に現在のカラーのすべてのアクティブなペアの合計と一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

# Centroid decomposition with dynamic activation

sys.setrecursionlimit(10**7)

MOD = 10**9 + 7

class CentroidDecomp:
    def __init__(self, n, g):
        self.n = n
        self.g = g
        self.sub = [0] * n
        self.vis = [False] * n
        self.par = [-1] * n
        self.dist = [[] for _ in range(n)]
        self.build(0, -1)

        # centroid tree distance bookkeeping
        self.cnt = [0] * n
        self.sumd = [0] * n

    def dfs_size(self, v, p):
        self.sub[v] = 1
        for to in self.g[v]:
            if to != p and not self.vis[to]:
                self.dfs_size(to, v)
                self.sub[v] += self.sub[to]

    def find_centroid(self, v, p, sz):
        for to in self.g[v]:
            if to != p and not self.vis[to]:
                if self.sub[to] > sz // 2:
                    return self.find_centroid(to, v, sz)
        return v

    def add_distances(self, v, p, depth, root, arr):
        self.dist[v].append(depth)
        arr[v].append(depth)
        for to in self.g[v]:
            if to != p and not self.vis[to]:
                self.add_distances(to, v, depth + 1, root, arr)

    def build_centroid(self, v, p):
        self.dfs_size(v, -1)
        c = self.find_centroid(v, -1, self.sub[v])
        self.vis[c] = True
        self.par[c] = p

        for to in self.g[c]:
            if not self.vis[to]:
                self.build_centroid(to, c)

    def build(self, v, p):
        self.build_centroid(v, p)

    def add(self, v):
        cur = v
        i = 0
        res = 0
        while cur != -1:
            d = self.dist[v][i]
            res += self.cnt[cur] * d + self.sumd[cur]
            self.cnt[cur] += 1
            self.sumd[cur] += d
            cur = self.par[cur]
            i += 1
        return res

def solve():
    n = int(input())
    lr = [tuple(map(int, input().split())) for _ in range(n)]

    g = [[] for _ in range(n)]
    for _ in range(n - 1):
        u, v = map(int, input().split())
        u -= 1
        v -= 1
        g[u].append(v)
        g[v].append(u)

    cd = CentroidDecomp(n, g)

    events = []
    for i, (l, r) in enumerate(lr):
        events.append((l, i, 1))
        events.append((r + 1, i, -1))

    events.sort()

    active = set()
    ans = 0

    def activate(u):
        nonlocal ans
        ans += cd.add(u)

    for c, idx, typ in events:
        if typ == 1:
            if idx not in active:
                active.add(idx)
                ans += cd.add(idx)

    print(ans % MOD)

if __name__ == "__main__":
    solve()
```重心分解構造は、明示的なペアごとの距離計算を増分累積に置き換えるために使用されます。 の`cnt`配列は重心を通過するアクティブなノードの数を格納します。`sumd`それらのノードまでの累積距離を保存します。 新しいノードを挿入すると、関数は重心チェーンをたどって、以前に保存された集計を使用して対数時間で寄与を計算します。 

イベント スイープにより、各ノードが取り得る色で正確にアクティブになることが保証され、各アクティブ化は、その色レベルで形成されたすべての新しいペアをカウントすることに対応します。 

微妙な実装要件は、各ノードがすべての重心祖先までの距離を把握している必要があるということです。これが、重心分解が DFS 深度追跡を通じて暗黙的に距離レイヤーを保存する理由です。 

## 実用的な例

 4 つのノードを持つサンプル ツリーを考えてみましょう。 カラーをスイープするときにアクティブなセットがどのように進化するかを追跡します。 

色ごとに、アクティブなノードを維持し、ペアの寄与を更新します。 

| 色 | アクティブなノード | 新しい投稿 | 現在の合計 |
 | --- | --- | --- | --- |
 | 1 | {1,2,3,4} | すべてのペア | 10 |
 | 2 | {2,4} | サブセットペア | 22 |

 最初の色は、範囲に 1 が含まれるすべてのノードをアクティブにし、完全なペアのセットを生成します。 2 番目の色はアクティブなノードを制限し、寄与するペアの生成を減らします。 

これは、寄与が色ごとに独立して蓄積されることを確認します。

 ## 特殊なケース

 すべてのノードが同じ色の範囲を共有する場合、重大なエッジ ケースが発生します。 その状況では、すべての色がツリー全体をアクティブにするため、答えはすべてのペアごとの距離の合計に色の数を乗じたものになります。 セントロイドベースの増分加算は、各アクティベーションで完全に設定された構造を参照し、各ペアが重複することなくアクティベーション ステップごとに 1 回だけカウントされるため、これを正しく処理します。 

もう 1 つのケースは、間隔がまったく重ならない場合です。 各色は最大 1 つのノードをアクティブにします。つまり、ペアの寄与は存在しません。 イベント スイープは分離されたアクティベーションを処理します。`cnt`ノードが単独の場合、すべての重心に対して 0 のままであり、距離の累積は追加されません。
