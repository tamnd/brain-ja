 ## 解決策
 ## 問題の理解

 この問題は、国を都市のツリーとしてモデル化します。 各都市は電力ゼロから始まります。 隕石は都市に 1 回衝突することができ、落下するとその都市に初期エネルギー量が与えられ、衝突時間以降は 1 秒ごとに 1 ずつ減少します。 クエリでは、2 つの都市間の一意のパスに沿った各都市に現在存在する合計電力が求められます。 簡易バージョンには十分な制限があり、$n \le 2000$そして$q \le 5000$これにより、ハード バージョンでは遅すぎる解決策が可能になります。 

入力により、最初にツリー構造が与えられ、次に一連のイベントが与えられます。 タイプ 1 イベントは、特定の時刻に都市に落下した流星を記録します。 タイプ 2 イベントは、特定の時点でのパス上のパワーの合計を要求します。 同じタイムスタンプを持つイベントでは、そのタイムスタンプで経路クエリに答える前に流星の着陸を適用する必要があります。 出力は、すべてのタイプ 2 イベントのパスの合計です。 

の小さな値$n$ハード版と比べて戦略が変わります。 都市が 2,000 しかない場合、ツリー トラバースを使用してパスをスキャンすると、せいぜいコストがかかります$O(n)$。 クエリは 5,000 件しかないため、約 1,000 万回の都市訪問で十分であり、これは Python で簡単に管理できます。 ここでは、重いツリー データ構造を伴うアプローチは必要ありません。 

主なエッジケースは時間の処理に起因します。 クエリ時間に正確に落下する流星は、すでにその初期エネルギーをすべて提供しています。 例えば：```
3
1 2
2 3
2
1 5 2 10
2 5 1 3
```正しい出力は次のとおりです。```
10
```のときだけ流星を発動させるという迂闊な実装。`query_time > meteor_time`2 つの時間が等しいため、流星を見逃してしまいます。 

もう 1 つの簡単な間違いは、クエリされた経路の外側にある都市に隕石が影響を与えることです。 例えば：```
3
1 2
2 3
2
1 1 1 7
2 1 3
```正しい出力は次のとおりです。```
7
```都市 1 が経路上にあるため、都市 1 の流星が寄与します。 すべてのアクティブな流星をグローバルに合計するソリューションでは、現在の経路に無関係な流星もカウントされます。 

負の値も保持する必要があります。 例えば：```
1
1
2
1 0 1 0
2 10 1 1
```正しい出力は次のとおりです。```
-10
```流星は、その値がマイナスになった後でも継続的にエネルギーを失います。 寄与をゼロに固定すると、間違った答えが生成されます。 

## アプローチ

 直接的なアプローチは、イベントを時系列に処理し、すでに着陸した流星を維持することです。 すべてのパス クエリについて、ツリー パスをたどって、そこで見つかったすべての流星の現在の寄与を計算します。 これは正しいです。各都市の力は、その都市の隕石が落下したかどうかと現在時刻にのみ依存するからです。 

最初の試行では、クエリごとにすべての都市の電力を再計算する可能性があります。 最悪の場合、これはすべてに影響を及ぼします$n$すべてのクエリに対して都市を指定すると、$O(nq)$操作。 与えられた境界では、これは約$10^7$操作は許容範囲内です。 同じアイデアをブルート フォース ツリー ソリューションとみなすこともできます。つまり、制約によってこの作業量が意図的に小さく抑えられているため、パス クエリを最適化する必要がありません。 

重要な単純化は流星の公式です。 もしもその時に隕石が落ちたら$t_0$価値のあるもの$v$、その後、時間に$t$その貢献は次のとおりです。$$v-(t-t_0)=(v+t_0)-t$$単一のクエリの場合、現在時刻は固定されているため、経路上のどの都市に流星があるかを知る必要があるだけです。 ツリー DFS は、複雑なデータ構造を維持することなく、パスの合計を直接収集できます。 

簡単なバージョンではツリーとクエリ数の両方が小さく保たれるため、ブルート フォースが機能します。 両方の値が大きくなるハード バージョンでは失敗します。大きなパスを何千回も歩くとコストがかかりすぎるためです。 簡単な制約により直接トラバースが可能になるという観察により、実装を単純に保つことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 承認済み |
 | 最適 | O(nq) | O(n) | 簡易バージョンで承認されました |

 ## アルゴリズムのチュートリアル

 1. ツリーを読み取り、その隣接リストを保存します。 ツリーには任意の 2 つの都市の間に単純なパスが 1 つだけあるため、そのパス上の都市を回復するには DFS で十分です。 
2. すべてのクエリをタイムスタンプで並べ替えます。 複数のクエリがタイムスタンプを共有する場合は、パス クエリの前に流星イベントを配置します。 これは流星の到着時刻の法則と一致します。$t$時点ではクエリに対してすでにアクティブです$t$。 
3. 流星を受け取った都市に対して 2 つのアレイを維持します。 1つの店舗$v+t_0$、流星の貢献度の定数部分、およびその他の部分は、都市に現在流星があるかどうかを格納します。 
4. 流星クエリの場合は、その値と着陸時間を保存して、対応する都市をアクティブにします。 各都市は最大 1 回更新されるため、削除ロジックは必要ありません。 
5. パス クエリの場合は、出発都市から目的地が見つかるまで DFS を実行します。 再帰を解きながら、そのパス上のすべての都市の寄与を追加します。 都市での活動的な流星の場合$x$、 追加：$$(v_x+t_x)-t$$どこ$t$はクエリ時間です。 

1. 元のクエリの順序で回答を出力します。 並べ替えは時間を正確にシミュレートするために内部的にのみ使用されます。 

アルゴリズムの背後にある不変条件は、クエリを一度に処理する前の条件です。$t$、最大でも着陸時間のあるすべての流星$t$はすでに起動されており、今後の流星は起動されません。 パス クエリは、要求されたパス上の都市のみを訪問するため、そのパスに属するアクティブな寄与を正確に合計します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    graph = [[] for _ in range(n)]
    for _ in range(n - 1):
        u, v = map(int, input().split())
        u -= 1
        v -= 1
        graph[u].append(v)
        graph[v].append(u)

    q = int(input())
    queries = []

    for i in range(q):
        data = list(map(int, input().split()))
        queries.append((data[1], 0 if data[0] == 1 else 1, i, data))

    queries.sort()

    active = [False] * n
    base = [0] * n
    ans = [0] * q

    def get_path_sum(start, target, time):
        stack = [(start, -1, 0)]
        parent = [-1] * n
        order = []

        while stack:
            node, par, state = stack.pop()
            if state == 0:
                parent[node] = par
                order.append(node)
                if node == target:
                    break
                for nxt in graph[node]:
                    if nxt != par:
                        stack.append((nxt, node, 0))

        cur = target
        total = 0
        while cur != -1:
            if active[cur]:
                total += base[cur] - time
            if cur == start:
                break
            cur = parent[cur]

        return total

    for time, _, _, data in queries:
        if data[0] == 1:
            _, t, x, val = data
            x -= 1
            active[x] = True
            base[x] = t + val
        else:
            _, t, a, b = data
            a -= 1
            b -= 1
            ans[_] = get_path_sum(a, b, t)

    for x in ans:
        print(x)

if __name__ == "__main__":
    solve()
```隣接リストにはゼロから始まるインデックスを持つツリーが保存されるため、トラバースが簡単になります。 の`active`配列は都市が流星を受け取ったかどうかを記録し、`base`変換された値を保存します$v+t_0$。 これにより、クエリごとにランディング時間の調整を再計算する必要がなくなります。 

クエリは時間順に並べ替えられます。 並べ替えタプルの 2 番目の要素は、同じタイムスタンプでパス クエリの前にメテオ クエリを配置します。 隕石が同時に着陸するため、この順序が必要です$t$すぐに貢献する$t$。 

パス検索では、DFS スタックを使用して、目的地に到達するまで親情報を構築します。 ターゲットに到達した後、コードは親ポインターを逆方向に進み、そのパス上の都市のみを蓄積します。 開始ノードでの停止条件により、無関係なブランチを誤って追加することがなくなります。 

Python の整数は、考えられる大きな合計を自動的に処理するため、特別なオーバーフロー処理は必要ありません。

 ## 特殊なケース

 タイムスタンプが等しい場合:```
2
1 2
2
1 5 2 10
2 5 1 2
```両方のイベントが時刻 5 で発生するため、流星クエリが最初に処理されます。保存される値は次のとおりです。$10+5=15$、パスには都市 2 が含まれているため、答えは次のようになります。$15-5=10$。 並べ替えではタイプ 1 のクエリがタイプ 2 のクエリの前に同時に配置されるため、アルゴリズムはこれを処理します。 

パス フィルタリングの場合:```
3
1 2
2 3
2
1 1 1 7
2 1 3
```都市1の流星が貢献しています$7$時刻 1。1 から 3 へのパスは次のとおりです。$1 \rightarrow 2 \rightarrow 3$, つまり流星も含まれます。 クエリが都市 2 から都市 3 へのものであった場合、都市 1 はそのパス上にないため、寄与はゼロになります。 DFS 親再構築により、パス都市のみがカウントされるようになります。 

負の減衰の場合:```
1
2
2
1 0 1 0
2 10 1 1
```流星の基本値はゼロです。 時間 10 での寄与は、$0-10=-10$。 コードはこの式を直接評価し、下限を適用しないため、必要な負の結果を返します。
