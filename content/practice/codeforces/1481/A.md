 ## 解決策
 ## 問題の理解

 グリッド上の原点の開始点とターゲット座標が与えられます。 これに加えて、4 つの基本方向の単位ステップからなる一連の移動コマンドが与えられます。 各コマンドは順番に実行され、位置が対応する方向に正確に 1 単位だけ移動します。 

残りのコマンドの相対的な順序を維持しながら、コマンドのサブセットを削除することができます。 削除後、残りのシーケンスは原点から左から右に実行されます。 問題は、最終位置が正確にターゲット座標になるようにコマンドのサブセットを選択できるかどうかです。 

すべてのテスト ケースにわたって、すべてのコマンド文字列の合計長が最大 100,000 であるという制約は、どのソリューションでも基本的に各文字を 1 回または一定の回数処理する必要があることを意味します。 サブシーケンスの数は文字列の長さに応じて指数関数的に増加するため、サブシーケンスを列挙したり削除を明示的にシミュレートしようとするアプローチはすぐに失敗します。 

単純ですがよくある落とし穴は、文字列に合計で正しい方向への動きが十分に含まれていれば、答えは常に「はい」であると仮定することです。 これは不正確です。なぜなら、動きを並べ替えることはできず、削除するだけであるという意味で順序が重要だからです。 たとえば、文字列「DDRRUU」から (1, 1) に到達することを考えてみましょう。 R と U の動きは十分にありますが、すべての U の動きの後に R だけが出現した場合でも、それらを選択してターゲットに到達できるため、順序によって実際に実行可能性が制限されることはありません。 微妙なのは、削除によって無関係なものがすべてスキップされるため、順序によって実行可能性が決して妨げられないことです。 

誤解を招きやすいもう 1 つのケースは、ターゲットをプレフィックス形式で正確に一致させる必要があると考えることです。 たとえば、「URDL」から (1, 1) に到達することは、貪欲にシミュレーションすると不可能に見えるかもしれませんが、「UR」のみを選択すると完全に機能します。 

本当の難しさは、問題が文字列から複数の動きのセットを選択することに帰着し、順序を維持することによってのみ制約され、隣接性を維持することによって制約されないことを認識することです。 

## アプローチ

 ブルートフォース解釈では、文字のすべてのサブセットを試し、結果のパスをシミュレートし、それがターゲットに到達するかどうかを確認します。 これは 2^n 個の可能性を検討しますが、n = 40 の場合でも、n が 100000 までであることは言うまでもなく、これは実行不可能になります。このアプローチの正しさは、すべての有効な削除を明示的にチェックするため簡単ですが、指数関数的に増加するため使用できなくなります。 

重要な点は、キャラクターを削除すると、動きのサブセットを完全に自由に選択できるようになりますが、順序を変更することはできないということです。 順序は最終的な座標に影響を与えないため、方向の数のみが重要になります。 選択した各キャラクタは独立してディスプレイスメントに寄与するため、最終的な位置は U、D、L、R の移動数にのみ依存します。 

(p_x, p_y) に到達するには、削除後の正味の水平移動が p_x に等しく、正味の垂直移動が p_y に等しいことを確認する必要があります。 これは、少なくとも |p_x| が必要になることを意味します。 必要な水平方向に移動し、少なくとも |p_y| 必要な垂直方向に移動します。 

したがって、問題は、文字列に必要な各方向が十分に含まれているかどうかをチェックすることになります。

 ## アルゴリズムのチュートリアル

 各テストケースを個別に処理します。

1. 文字列内に各方向が何回出現するかを数えます。 これにより、順序を考慮せずに、U、D、L、R の移動の利用可能な供給が得られます。 これが機能する理由は、サブセットの選択は配置ではなく可用性のみに依存するためです。 
2. 目標座標から各軸で何回移動する必要があるかを計算します。 p_x が正の場合、p_x を右に移動する必要があります。 負の場合は、-p_x を左に移動する必要があります。 p_y についても同様に up と down を指定します。 
3. 文字列に、p_x が正の場合に少なくとも p_x R が移動するか、p_x が負の場合に少なくとも -p_x L が移動するかどうかを検証して、x 軸の実現可能性を確認します。 
4. U カウントと D カウントを使用して、y 軸に対しても同じことを行います。 
5. 両軸が独立して満足できる場合は YES を出力し、そうでない場合は NO を出力します。 

### なぜ効果があるのか

 すべての移動は最終的な変位に独立して寄与し、削除は方向間の相互作用を導入せずにカウントを減らすだけです。 最終的な位置は独立した単位ベクトルの合計であるため、実現可能性は必要な各方向で十分なベクトルを選択できるかどうかにのみ依存します。 不要なプレフィックスは簡単に削除できるため、順序制約によって有効な選択が妨げられることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        px, py = map(int, input().split())
        s = input().strip()

        r = s.count('R')
        l = s.count('L')
        u = s.count('U')
        d = s.count('D')

        ok_x = (px >= 0 and r >= px) or (px < 0 and l >= -px)
        ok_y = (py >= 0 and u >= py) or (py < 0 and d >= -py)

        print("YES" if ok_x and ok_y else "NO")

if __name__ == "__main__":
    solve()
```この実装は、方向カウントのみが重要であるという観察に直接従っています。 各テスト ケースは、文字列に対して線形時間で 4 つのカウントを計算し、それらを必要な変位コンポーネントと比較します。 

微妙な点は、符号を正しく処理することです。正の x は R に対応し、負の x は L に対応し、y についても同様に U および D に対応します。これらの条件を混合すると、不正確な実行可能性チェックが発生します。

 ## 特殊なケース

 エッジ ケースの 1 つは、(0, y) など、ターゲットが完全に 1 つの軸内にある場合です。 この状況では、横方向の動きは関係なく、U と D のカウントのみが重要になります。 アルゴリズムは軸ごとに必要な方向のみをチェックするため、これを自然に処理します。 

別のエッジ ケースは、ストリングに正確にバランスのとれた反対の動きが含まれている場合 (L と R の数が等しいなど)、ターゲットがネット シフトを必要とする場合に発生します。 このソリューションは、元の文字列の正味の変位には依存せず、可用性だけに依存するため、文字列全体のキャンセル効果を正確に無視し、選択の実現可能性にのみ焦点を当てます。
