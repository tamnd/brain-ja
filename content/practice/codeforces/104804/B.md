 ## 解決策
 ## 問題の理解

 私たちは、4 人のプレイヤーが一定のサイクルで座る、非常に構造化されたドラフト プロセスをシミュレートしています。 各ラウンドごとに、すべてのプレイヤーは、プールがなくなるまで、共通のプールから騎士トークンを 1 つだけ取得します。 唯一の工夫は、プレーの順序が固定されていないことです。4 つのピックが行われる各ラウンドの後、順序は周期的に循環するため、最初にいた人が最後になり、全員が 1 つ前にポジションを移動します。 

イゴールが定位置で先発出場$k$、そして私たちは、彼がその前に何回行動するかを決定したいと考えています。$n$トークンがなくなります。 

入力は 2 つの値で構成されます。 1 つ目は利用可能な同一のトークンの合計数、2 つ目は 4 人のプレイヤーの間でのターン順序における Igor の初期位置です。 出力は単に、Igor がトークンを取得できたターン数です。 

制約は非常に小さく、$n \le 100$したがって、すべてのピックを直接シミュレーションするだけでも十分です。 漸近的な複雑さの観点から最適化する必要はなく、$O(n)$または$O(n \cdot 4)$行動は些細なことです。 

微妙な点は、プレーヤーのローテーションによって、各プレーヤーが 4 つの動きの完全なサイクルごとに 1 回だけ行動するという事実が変わらないことです。 ローテーションでは、各ポジションに誰が就くかを変更するだけであり、出現頻度は変更されません。 このため、各プレイヤーは 4 つのピックのラウンドごとに 1 回だけ登場します。 唯一の複雑な点は、イゴールのアイデンティティが予測可能な周期的なパターンで位置を移動することです。 

次のような小さな境界チェックを超える意味のあるエッジケースはありません。$n = 1$、最初の位置のみが 1 回のみ機能する、または$k = 4$、Igor は最初のサイクルで最後から開始します。 

## アプローチ

 直接のシミュレーションが最も直接的な解釈です。 現在のオーダーを代表する 4 人のプレーヤーの配列を維持します。 各トークンについて、オーダーの先頭のプレーヤーを選択し、トークンを割り当て、4 回のピックごとにオーダーをローテーションします。 これはゲームのルールを正確に反映しているため、正しく機能します。 

ただし、回転のシミュレーションは不要です。 重要な観察は、各ラウンド後のローテーションによってアイデンティティが変更されるだけで、各プレーヤーがラウンドごとに 1 つのピックを獲得するという事実は変わらないということです。 4 つの手の連続するブロックでは、4 人のプレイヤーはそれぞれ 1 回だけ登場します。 したがって、全体にわたって、$n$トークンの場合、Igor が出現する回数は、内部ローテーション構造ではなく、完全なラウンドまたは部分的なラウンドが発生する回数によってのみ決まります。 

これにより、問題は単純な定期的な計数タスクに縮小されます。 4 つのピックのグループごとに各プレーヤーに 1 つのピックが割り当てられるため、イゴールは 4 つの完全なグループごとに 1 つのピックを受け取り、さらに、彼のポジションが残った不完全なグループ内にある場合は追加で 1 つのピックを受け取ります。 

ブルート フォース アプローチでは、すべての配列のピックと回転をシミュレートするため、ピックごとに一定の作業が必要になりますが、状態遷移を管理するオーバーヘッドが含まれます。 最適化されたビューでは、すべての状態が削除され、すべてがサイクル上の算術演算に還元されます。

 ## アルゴリズムのチュートリアル

 1. 4 つのピックのフルラウンドが何回存在するかを計算します。$n$。 これは$n // 4$。 各ラウンドでは、Igor のピックが 1 つだけ保証されます。 
2. これらの全面的な貢献を Igor の回答に追加します。 これがベースライン数を形成します。 
3. 剰余を計算します$n \% 4$、不完全な最終ラウンドがある場合はそれを表します。 
4. イゴールの位置を確認する$k$最初の範囲内に該当します$r$ラウンドの位置。 「はい」の場合、Igor は追加のピックを 1 つ受け取ります。 
5. 累計を出力します。 

重要な考え方は、4 つの手の各サイクル内で、ポジション 1 ～ 4 がすべて 1 回だけ使用されるため、最後の部分サイクルにおける唯一の問題は、サイクルが終了する前にイゴールのポジションに到達できたかどうかということです。 

### なぜ効果があるのか

 このシステムは、長さ 4 の繰り返しスケジュールのように動作し、すべてのプレイヤーが全期間ごとに 1 回の出現を保証されます。 ラウンド間のローテーションによりアイデンティティが並べ替えられますが、各アイデンティティはサイクルごとに 1 回出現するという不変条件が維持されます。 したがって、イゴールの総出現数は、存在する完全なサイクルの数と、彼が最終サイクルの不完全なサフィックスにスケジュールされているかどうかにのみ依存します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n, k = map(int, input().split())

full = n // 4
rem = n % 4

ans = full

if k <= rem:
    ans += 1

print(ans)
```コードはサイクル分解を直接実装します。 整数を 4 で割ると完全なラウンドがカウントされ、それぞれがイゴールの確実な 1 つのピックに貢献します。 残りは部分的なラウンドをキャプチャし、比較`k <= rem`Igor のポジションがその未完了のセグメントでまだアクティブであるかどうかを確認します。 

回転はサイクルごとの周波数に影響を与えないため、シミュレーションは必要なく、プレーヤーの回転を明示的に表現する必要もありません。 

## 実用的な例

| ステップ | 全サイクル (n//4) | 残り (n%4) | k | 追加のピック？ | 合計 |

 これは、Igor が完全なラウンドからのみ恩恵を受け、残りの 1 つのムーブがポジション 3 に到達しないため、追加のピックは許可されないことを示しています。

これにより、剰余ロジックが部分サイクルの参加を正しくキャプチャしていることが確認されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n, k = map(int, input().split())

    full = n // 4
    rem = n % 4
    ans = full
    if k <= rem:
        ans += 1
    return str(ans)

# provided samples
assert run("9 3") == "3"
assert run("11 2") == "3"
assert run("12 3") == "3"

# custom cases
assert run("1 1") == "1"
assert run("4 4") == "1"
assert run("5 1") == "2"
assert run("7 4") == "1"
assert run("8 2") == "2"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 1 | 1 | 最小ケース、単一選択 |
 | 4 4 | 1 | 全サイクル境界 |
 | 5 1 | 2 | 第 2 サイクルへの移行 |
 | 7 4 | 1 | 部分サイクル内にない最後の位置 |
 | 8 2 | 2 | 複数の完全なサイクルと残り |

 ## 特殊なケース

 のために$n = 1$、アルゴリズムは次のように計算します。$full = 0$、$rem = 1$。 もし$k = 1$、条件$k \le rem$が成立するため、結果は 1 になります。これは、ピックが 1 つだけ発生し、位置 1 の Igor がすぐにそれを取得するという事実と一致します。 

のために$n = 4$、完全な 1 サイクルが得られ、残りは得られません。 イゴールを含む各選手は、$k$、ちょうど 1 つのピックを受け取ります。 数式は戻ります$1$なぜなら$full = 1$そして$rem = 0$, そのため、余分な追加は発生しません。 

以下の場合については、$k = 4$、残りだけが重要です。 もし$n \mod 4 < 4$, イゴールは 4 位に到達した場合、最後の部分サイクルでのみ貢献します。 それ以外の場合、彼はフルサイクルの寄付のみを受け取ります。
