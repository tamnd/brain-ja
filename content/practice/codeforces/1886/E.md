 ## 解決策
 ## 問題の理解

 私たちには、それぞれストレス耐性レベルを持つ一連のプログラマーと、それぞれに難易度を持つ一連のプロジェクトが与えられます。 目標は、すべてのプロジェクトに少なくとも 1 人のプログラマーが存在し、複数のプロジェクトに携わるプログラマーが存在しないように、プロジェクトにプログラマーを割り当てることです。また、プロジェクトに割り当てられた各プログラマーのストレス許容度が、少なくともプロジェクトの難易度をプロジェクトに割り当てられたプログラマーの数で割った値になるようにすることです。 出力は、これが不可能な場合は「NO」、または「YES」の後に有効な割り当てが続くかのいずれかになります。 

制約は重要です。 最大 200,000 人のプログラマが存在できますが、プロジェクトは最大 20 個までです。 これは、プロジェクトの数が指数関数的に増加するアルゴリズムを開発できるが、プログラマーの数は増加しないことを示唆しています。 プロジェクト間のプログラマの可能なすべての分割を考慮する単純な総当り攻撃は直ちに除外されます。$m^n$可能な割り当ては、天文学的なものになります。$n$は20万です。 ただし、プロジェクトの数が少ないことから、プロジェクトに対してビットマスクなどの手法を使用できることがわかります。 

エッジケースとは、単純なアプローチでは失敗する可能性があるケースです。 たとえば、すべてのプロジェクトが非常に難しく、プログラマが非常に弱い場合、アルゴリズムは正しく「NO」を返さなければなりません。 1 つのプロジェクトが非常に簡単な場合、慎重に制御しないと、すべてのプログラマーが貪欲な割り当てに集まってしまう可能性があります。 プロジェクトの難易度を割り当てられたプログラマーの数で割った値が、一部のプログラマーのストレスにまったく等しい場合、不用意に実装すると浮動小数点エラーにより誤った比較が生じる可能性があります。 

たとえば、次のように考えてみましょう`n=3`、`m=2`、`a=[2,3,4]`、`b=[6,1]`。 不注意で貪欲な割り当てを行うと、プログラマ 3 をプロジェクト 1 に割り当てようとし、有効な割り当てが存在するにもかかわらず、プロジェクト 2 を正しく割り当てられない可能性があります。つまり、プロジェクト 1 にはプログラマ 2 と 3 が割り当てられ、プロジェクト 2 にはプログラマ 1 が割り当てられます。 

## アプローチ

 強引なアプローチは、プログラマーをプロジェクトに割り当てるためにあらゆる方法を試みることです。 プロジェクトごとに、残りのプログラマーの一部を選択し、ストレス耐性条件をチェックし、残りのプロジェクトについて再帰的に実行します。 これは原理的には機能しますが、1 つのプロジェクトであってもプログラマのサブセットの数は$2^n$、これは不可能です$n$200,000まで。 

重要な洞察は、プロジェクトが少ないということです。 なぜなら$m \le 20$、これはプログラマーの分散の問題として考えることができます。$m$バケットごとに単純な算術条件を確保しながら、バケットを分割します。 プログラマーを分類し、残りの最大のストレス耐性を、難易度対プログラマーの比率が最も大きいプロジェクトに割り当てることは、有益なアプローチです。 具体的には、現在残っている「割り当てられたプログラマごとの難易度」要件が最も大きいプロジェクトに、次に利用可能なプログラマを常に割り当てる場合、各プロジェクトに少なくとも 1 人のプログラマを確保しながら、ストレス条件に違反しないことを保証します。 

この観察により、プログラマをストレスの降順に処理して貪欲に割り当て、最小ヒープまたは同様の構造を維持して、次のプログラマを最も必要とするプロジェクトを効率的に見つけることができます。 これにより問題は次のように縮小されます$O(n \log m)$各割り当てで最大サイズのヒープの更新のみが必要なため、時間がかかります。$m$。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | お($2^n$) | O(n) | 遅すぎる |
 | 最適 | O(n log m) | O(n + m) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 元のインデックスを追跡しながら、プログラマをストレス耐性の降順に並べ替えます。 これにより、常に最も優秀なプログラマを最初に割り当てようとするため、柔軟性が最大限に高まります。 
2. プロジェクトの最小ヒープを初期化します。各プロジェクトは、現在割り当てられているプログラマの数とプロジェクトの難易度を含むタプルとして表されます。 現在の「プログラマーごとの難易度」を簡単に計算できるように、概念的に 1 人のプログラマーを割り当てて各プロジェクトを開始します。 ヒープは必要な有効応力によってソートされます$b_i / k_i$。 
3. 各プログラマをストレスの降順で繰り返します。 必要なストレスを最大にしてプロジェクトをポップします (これは、最大ヒープをシミュレートするために負の値を格納するヒープを使用して効率的に実行できます)。 プログラマーのストレス許容度が、このプロジェクトに現在必要なストレス以上であるかどうかを確認してください。 「はい」の場合は、プログラマーを割り当て、プロジェクトに割り当てられたプログラマーの数を増やし、更新された必要なストレスを使用してプロジェクトをヒープに戻します。 プログラマーが最も要求の厳しいプロジェクトの要件を満たすことができない場合、有効な割り当ては存在しません。 
4. すべてのプログラマが割り当てられるまで、またはすべてのプロジェクトに少なくとも 1 人のプログラマが割り当てられるまで続行します。 ループの後、すべてのプロジェクトに少なくとも 1 人のプログラマがいることを確認します。 そうであれば、「YES」に続いて割り当てリストを出力します。 それ以外の場合は、「NO」を出力します。 

機能する理由: このアルゴリズムは、既に割り当てられているプログラマーの数を考慮すると、プロジェクトに現在必要なストレスが常に最小化されるという不変条件を維持します。 最も必要とされるプロジェクトに最も優秀なプログラマーを割り当てることで、将来の割り当てが妨げられることはありません。 プログラマーを分類することで、プロジェクトの要件を満たすことができる場合にのみ、より弱いプログラマーが割り当てられるようになります。 

## Python ソリューション```python
import sys, heapq
input = sys.stdin.readline

n, m = map(int, input().split())
a = list(map(int, input().split()))
b = list(map(int, input().split()))

prog = sorted([(val, i + 1) for i, val in enumerate(a)], reverse=True)
projects = [(b[i], i) for i in range(m)]
assignments = [[] for _ in range(m)]

# Initialize heap: (current_needed_stress, num_assigned, project_index)
heap = []
for diff, idx in projects:
    heap.append((diff, 1, idx))  # start with 1 programmer to avoid divide by zero
heapq.heapify(heap)

for stress, prog_idx in prog:
    # get project with highest required stress
    curr_needed, count, proj_idx = heapq.heappop(heap)
    if stress * count < b[proj_idx]:  # b/k > stress check
        print("NO")
        sys.exit(0)
    assignments[proj_idx].append(prog_idx)
    count += 1
    heapq.heappush(heap, (b[proj_idx] / count, count, proj_idx))

print("YES")
for lst in assignments:
    print(len(lst), *lst)
```このコードはプログラマーを一度ソートし、ヒープを使用して次のプログラマーを最も必要とするプロジェクトを追跡します。 ヒープには浮動小数点値が格納されます`b[proj_idx]/count`現在必要な応力を表します。 使用する`stress * count < b[proj_idx]`浮動小数点精度の問題を回避します。
