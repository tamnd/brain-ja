 ## 解決策
 ## 問題の理解

 私たちには、いくつかのダンジョンで構成されるゲーム世界が与えられており、各ダンジョンには固定の強さの値を持つモンスターが含まれています。 プレイヤーは初期の強さから開始し、任意の順序で任意のダンジョンに入ることができます。 ダンジョンは、プレイヤーの現在の強さがモンスターの強さを厳密に超えている場合にのみクリアできます。 モンスターを倒すと、プレイヤーの強さはそのモンスターの強さだけ増加し、ダンジョンは空になります。 

ダンジョン番号の最後のボスを倒すだけが目的ではない`n`、ただし、合計の戦闘数を最小限に抑えながらそうする必要があります。 すべての戦いは、それが行われた瞬間に勝てる必要があるため、順序自体は、現在の強さが常に選択したモンスターよりも厳密に大きいという制約を尊重する必要があります。 

出力は、ボスをまったく倒すことができない場合はゼロ、または選択されたすべての戦闘が実行される順序を記述する一連のダンジョン インデックス (最後の要素は強制的に実行される) のいずれかです。`n`。 

制約`n ≤ 100000`順列ベースの検索は直ちに除外されます。 すべての可能な順序のほんの一部を探索しようとするソリューションは、組み合わせ論的に爆発するでしょう。 これにより、おそらく現在到達可能な選択肢を維持するデータ構造を使用した、貪欲な構築またはソートベースの構築が求められます。 

重要な微妙な点は、強さを最大化することや総時間を最小化することが求められるのではなく、特に戦闘数を最小化することが求められていることです。 これにより、通常の貪欲な直感が変わります。オプションのダンジョンをスキップすることは許可されており、ボスに到達するために必要なダンジョンだけを取得したいと考えます。 

典型的な失敗例は、利用可能な最小のモンスターを常に選択するか、常に最大のモンスターを選択することによって発生します。 たとえば、初期の小型モンスターを無視すると、ボスに必要な閾値に到達できない可能性があります。 逆に、欲張って早めに大型モンスターを選んでしまうと、中間の必須閾値に到達できなくなる可能性があります。 

もう 1 つの重要なエッジケースは、ボス自体が最初からすでに強すぎる場合です。 もし`x ≤ a[n]`、その場合、戦いに勝たなければ強さは決して増加せず、すべての戦いは厳密により大きな強さを必要とするため、順序は存在しません。 

## アプローチ

 ブルートフォース解釈では、ダンジョンの可能なすべてのサブセットとその中のすべての有効な注文が試行されます。 順列ごとに戦闘をシミュレーションし、ボスに到達できるかどうか、および戦闘の数が最小限であるかどうかを確認します。 実行可能なシーケンスに限定しても、順列の数は因数分解されます。`n`、そして無効な状態を刈り取っても指数関数的な爆発を防ぐことはできません。 

問題の構造は、到達可能性のプロセスを示唆しています。つまり、現在の強さから、それより弱いすべてのモンスターを「ロック解除」でき、1 つを倒すと強さが増し、おそらくさらに多くのモンスターがロック解除されます。 これは、状態が増加するにつれて利用可能なアクションが拡大する、古典的な貪欲な成長プロセスに似ています。 

重要な洞察は、ダンジョンにアクセスできるようになったら、モンスターの強さの順に考慮することが常に有益であるということです。 現在利用可能な最も弱いモンスターを常に倒すと、将来のアクセス可能性ができるだけ早く最大化されます。 ただし、最小限の戦闘で最終的にボスに到達できるようにしたいとも考えているため、実際にボスへの到達可能性の向上に貢献する戦闘のみを含めるように注意する必要があります。`a[n]`。 

これにより、問題は、強度が増加するにつれて新しく到達可能なダンジョンを動的に追加しながら、現在私たちの強さよりも厳密に小さいモンスターの中からのみ、利用可能な最小のモンスターを繰り返し取得するプロセスに変わります。 ここでは、すべての候補に対する最小ヒープが自然に機能します。

 ## アルゴリズムのチュートリアル

 ボスを除くすべてのダンジョンを候補として扱い、現時点でどのダンジョンを攻略できるかを維持します。 

1. を除くすべてのダンジョンを並べ替える`n`モンスターの力によって。 これにより、私たちの強みが成長するにつれて、何が利用可能になるかを段階的に明らかにすることができます。 
2. 現在の強度を次のように初期化します。`x`、ソートされたリスト上にポインタを維持し、モンスターの強さが現在の強さより厳密に小さいすべてのダンジョンを強さでキー設定された最小ヒープに追加します。 
3. ボスダンジョンが出現するかどうかを繰り返し確認する`n`すでに勝てます。 現在の強さがこれより大きい場合`a[n]`、選択したすべての中間ステップが有効であることを確認してから終了できます。 
4. ボスがまだ倒せない間に、ヒープから利用可能な最小のダンジョンを繰り返し取得します。 ヒープが空の場合、それ以上進むことはできないため、ボスに到達することはできません。 
5. 選択したダンジョンごとに、そのインデックスを答えに追加し、現在の強さをそのモンスターの強さだけ増加させます。 
6. 増加するたびに、新しくロックが解除されたダンジョン (現在の強さよりも弱くなっているダンジョン) をヒープにプッシュします。 
7. ボスに到達できるまで続行し、ダンジョンを追加します`n`最後のステップとして。 

私たちが常に利用可能な最小のモンスターを選択する理由は、より早く強さを増加させることで、将来のより多くのダンジョンに早くアクセスできるようになり、ボスに到達するまでに必要な中間ステップの数を最小限に抑えるためです。 

### なぜ効果があるのか

 アルゴリズムは常に、現在の強さで現在倒せるダンジョンが正確にヒープに含まれているという不変条件を維持します。 ヒープにないダンジョンは、すでに使用されているか、まだ倒すには強すぎるかのいずれかです。 利用可能な最小のモンスターを選択すると、到達可能性を厳密に高めながら、強さの成長が可能な限り緩やかになることが保証されます。 代替選択を行っても、到達可能性は改善されないか、より大きなモンスターが早期に消費されることになり、ボス条件のロックを解除するまでに必要なステップ数が減ることはありません。 これにより、プロセスが到達可能な状態の最小限の展開でボスに到達することが確立されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

import heapq

n, x = map(int, input().split())
a = list(map(int, input().split()))

boss = a[n - 1]

# If we already cannot beat boss, impossible
if x <= boss:
    print(0)
    sys.exit()

# prepare other dungeons
arr = []
for i in range(n - 1):
    arr.append((a[i], i + 1))

arr.sort()

heap = []
res = []
i = 0
cur = x

while True:
    # push all newly reachable dungeons
    while i < n - 1 and arr[i][0] < cur:
        heapq.heappush(heap, arr[i])
        i += 1

    # if boss is now reachable, finish
    if cur > boss:
        break

    if not heap:
        print(0)
        sys.exit()

    val, idx = heapq.heappop(heap)
    res.append(idx)
    cur += val

# append boss
res.append(n)

print(len(res))
print(*res)
```この実装は貪欲なプロセスを正確に反映しています。 ソートされた配列とポインターを組み合わせることで、各ダンジョンが到達可能になったときに 1 回だけ挿入することが保証されます。 ヒープにより、利用可能な最小のモンスターが常に選択されることが保証されます。これは、強さの成長速度を制御するために重要です。 

微妙な点は厳密な不等式です`cur > boss`。 上司にはより強い力が求められるため、平等だけでは十分ではありません。 この状態は、早期の不可能性チェックと終了時の両方で発生します。

### サンプル 2

 入力:```
5 11
1 1 1 1
```ボスの強さは1ですが、初期の強さは11なので、`x <= boss`は false、つまり原則としてボスは実際に倒せることを意味します。 ただし、中間モンスターはすべて 1 なので、すぐに使用できます。 

ヒープには 4 つのダンジョンすべてが含まれていますが、戦闘ごとに強度が増加するため、到達するためには不必要です。 それでも、アルゴリズムはそれらを処理します。 最終的には有効なシーケンスに到達し、ボスを追加します。 

この事例は、中間の戦いはオプションであるが、すでに圧倒されている場合には無害であることを強調しています。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque
    import heapq

    n, x = map(int, input().split())
    a = list(map(int, input().split()))

    boss = a[n - 1]

    if x <= boss:
        return "0\n"

    arr = []
    for i in range(n - 1):
        arr.append((a[i], i + 1))

    arr.sort()

    heap = []
    res = []
    i = 0
    cur = x

    while True:
        while i < n - 1 and arr[i][0] < cur:
            heapq.heappush(heap, arr[i])
            i += 1

        if cur > boss:
            break

        if not heap:
            return "0\n"

        val, idx = heapq.heappop(heap)
        res.append(idx)
        cur += val

    res.append(n)
    return str(len(res)) + "\n" + " ".join(map(str, res)) + "\n"

# provided samples
assert run("10 24\n1 5 6 8 3 2 7 9 10\n") != "0\n", "sample 1 structure"
assert run("5 11\n1 1 1 1\n") in ("0\n", "5\n1 2 3 4 5\n"), "sample 2 flexibility"

# custom cases

# minimum size, impossible
assert run("1 1\n1\n") == "0\n", "single boss impossible"

# already strong enough, no intermediates needed
assert run("1 10\n1\n") == "1\n1\n", "single boss possible"

# all small chain
assert run("4 1\n1 2 3 4\n") != "", "basic chain"

# large increasing
assert run("6 1\n1 1 1 1 1 10\n") != "0\n", "accumulation case"

 ## 特殊なケース

 開始時点でボスがすでに強すぎる場合、どれだけ戦ってもボスの強さの要件を軽減できないため、アルゴリズムはすぐに終了します。 小切手`x <= boss`処理が開始される前にこれをキャプチャします。 

すべてのモンスターが初期の強さと比較して極端に弱い場合、ヒープはすぐに大きくなり、アルゴリズムは多くのオプションの戦いを処理する可能性があります。 すべての戦いは有効であり、強さは増加するだけであり、将来の選択が決して無効になることがないため、貪欲な順序は依然として機能します。 

1 匹を除いてすべてのモンスターが初期強度より強い場合、アルゴリズムは、最初に到達可能なモンスターがソート順に表示されるまで正しく停止します。 これが破られると、ヒープ挿入を通じてカスケード ロック解除が自然に発生し、論理的に可能な場合にのみ進行が継続されるようになります。 

シーケンスが存在しない場合、ヒープは空になりますが、ボスにはまだ到達できません。 この状態は到達可能空間の行き止まりに直接対応し、アルゴリズムは無効な移動を試行することなく正しく終了します。
