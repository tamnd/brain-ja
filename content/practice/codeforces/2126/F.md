 ## 解決策
 ## 問題の理解

 すべての頂点に色があり、すべてのエッジに重みがある木が与えられています。 エッジは、そのエンドポイントが現在異なる色を持っている場合にのみ、総コストにその重みを加えます。 端点が同じ色を共有している場合、エッジは何も寄与しません。 

このプロセスは動的です。 単一の頂点を繰り返し再描画し、各再描画後にすべてのエッジからの寄与の合計を報告する必要があります。 

難しいのは、コストを一度計算することではなく、すべてのテスト ケースにわたって最大 20 万回の再色操作を行ってもコストを効率的に維持できることです。 各更新後に直接再計算を行うと、ツリー全体を繰り返し走査することになり、非常に遅すぎます。 

この制約構造は、クエリごとにすべてのエッジを検査するソリューションや、単純な方法で高次のノードのすべての隣接ノードを繰り返し検査するソリューションには、二次的な動作のリスクがあることを意味します。 頂点とクエリの合計は 2e5 になるため、O(nq) または O(q(n + m)) のアプローチは直ちに実行不可能になります。 単一の頂点の色を変更することによって引き起こされる「関連する変更」の数にのみ比例して、時間内に答えを更新する方法が必要です。 

頂点の次数が非常に大きい場合、微妙なエッジ ケースが発生します。 中心が 1 で、他のすべての頂点がそれに接続されている星があり、中心の色を繰り返し変更するとします。 更新ごとにすべての近傍をスキャンする単純なソリューションは O(nq) となり、中程度の入力でも失敗します。 逆に、リーフの色変更は個別に安価ですが、更新が注意深く構成されていない限り、ハブとリーフを交互に行うと対称的な単純な仮定が崩れます。 

重要な観察は、再カラーされた頂点に付随するエッジのみがその寄与を変更できるということです。 ただし、更新ごとに高次の頂点のすべての近傍を反復処理するのは、依然として遅すぎます。 これにより、次数ごとに頂点を分割する方向に進みます。 

## アプローチ

 ブルートフォースのアイデアは単純です。 現在の色を維持し、各クエリの後にすべてのエッジを反復処理して、エンドポイントが異なるかどうかを再計算します。 これは、条件がエッジごとにローカルであるため機能します。 残念ながら、これにはクエリごとに O(n) のコストがかかり、O(nq) となり、大きすぎます。 

もう少し優れた総当り攻撃は、更新された頂点に付随するエッジのみをチェックすることです。 頂点の色が変化すると、その入射エッジのみがコストを変更する可能性があります。 近隣ごとに、等価条件が変化したかどうかを確認し、それに応じて答えを更新します。 これは正しく、すでに作業が大幅に軽減されています。 ただし、星型ツリーでは、中心頂点の次数が O(n) であるため、色変更を繰り返しても、最悪の場合、クエリごとに O(n) になります。 

重要な構造的洞察は、頂点を高次と低次に分けることです。 低次数の頂点は、コストがかかる更新がほとんどないため、隣接リストを安全に反復処理できます。 高次の頂点では隣接関係を反復することができないため、代わりに追加のブックキーピングを維持します。頂点ごとに、隣接する各カラー クラスとの集約された相互作用を追跡します。 

具体的には、頂点ごとに、各色の近傍に対するエッジの重みがどれだけあるかを追跡するグローバル構造を維持します。 その後、頂点カラーの更新は、すべての近傍をスキャンするのではなく、事前に計算された集計を使用して寄与を調整することで解決できます。 

これは、頂点次数に関する古典的な重光戦略につながります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | すべてのエッジに対するブルートフォース | O(nq) | O(n) | 遅すぎる |
 | クエリごとに近傍を反復する | O(クエリごとの ∑deg(v)) 最悪 O(nq) | O(n) | 遅すぎる |
 | 重光度 | O((n+q)√n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

√n にほぼ等しいしきい値 B に基づいて、頂点を重いものと軽いものに分割します。 頂点は次数が B を超える場合は重くなり、それ以外の場合は軽くなります。 

現在の合計の答えを維持します。これは、端点の色が異なるすべてのエッジの重みの合計です。 

また、頂点ごとに、各色の隣接する頂点とどのくらいの重みで接続されているかを記録するマップのような構造も維持します。 ただし、これを効率的に保存するのは重い頂点の場合のみです。 ライト頂点は直接処理されます。 

手順は次のように動作します。 

1. エッジの重みを使用して隣接リストを事前計算し、すべてのエッジを 1 回チェックして最初の応答を計算します。 これにより、更新を適用するための正しいベースラインが確立されます。 
2. 次数しきい値 B を使用して、頂点を重い頂点と軽い頂点に分類します。これにより、重い頂点が最大でも O(√n) 個存在することが保証されます。 
3. すべての重い頂点 h に対して、辞書 cnt[h] を構築します。ここで、cnt[h][color] は、h からその色の近傍までのエッジの重みの合計に等しいです。 これにより、O(1) で色がその頂点にどの程度の「影響」を与えるかをクエリできるようになります。 
4. また、すべての頂点 v とすべての重い近傍 h について、それらの間のエッジの重みの記録も維持します。 これにより、色が変わったときに重い構造を高速に更新できます。 
5. 頂点 v を古い色から新しい色に再色するクエリを処理するとき、最初に、その入射エッジが全体的な答えへの寄与をどのように変化させるかを計算します。 v の各隣接 u について、u が明るい場合、エッジを直接検査して答えを調整します。 軽い頂点の次数が小さいため、これは安価です。 
6. v 自体が重い場合は、近傍をスキャンする代わりに、事前計算されたテーブルを使用します。 cnt[v][old] を使用して v と古い色の近傍の間のエッジの寄与を減算し、cnt[v][new] を使用して新しい色の近傍の寄与を追加します。 これにより、大規模になる可能性のある隣接リストの反復処理が回避されます。 
7. グローバルな答えを更新した後、補助構造を更新する必要があります。 v のすべての重い近傍 h について、v の色が変化したため cnt[h] を調整し、古い色のバケットから新しい色のバケットに重みを効果的に移動します。 
8. 最後に、保存されている v の色を更新します。 

正確かどうかは、再色の際に寄与を調整する際に、すべてのエッジが 1 回だけ考慮されるかどうかにかかっています。 各更新では、変更された頂点に付随するエッジのみが変更され、それらのエッジは直接処理される (軽い場合) か、集約されたカウンター (重い場合) を通じて処理されます。 

### なぜ効果があるのか

 不変条件は、グローバルな答えが常に、重みのすべてのエッジの合計と、エンドポイントの色が異なることを示すインジケーターの積に等しいということです。 各更新では、再カラーされた頂点に隣接するエッジのみが変更され、それらの変更は、直接隣接反復によって、または重い頂点の集約されたカラーベースのカウントによって完全にキャプチャされます。 すべての貢献が 1 つのエンドポイントの更新処理に関連付けられており、重い頂点によって高度な繰り返しが定数時間のルックアップに置き換えられるため、エッジが二重にカウントされたりスキップされたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    col = list(map(int, input().split()))
    col = [c - 1 for c in col]

    adj = [[] for _ in range(n)]
    edges = []

    for _ in range(n - 1):
        u, v, w = map(int, input().split())
        u -= 1
        v -= 1
        adj[u].append((v, w))
        adj[v].append((u, w))
        edges.append((u, v, w))

    B = int(n ** 0.5) + 1
    heavy = [False] * n
    heavy_idx = [-1] * n
    heavy_nodes = []

    for i in range(n):
        if len(adj[i]) > B:
            heavy_idx[i] = len(heavy_nodes)
            heavy_nodes.append(i)
            heavy[i] = True

    hcnt = [dict() for _ in range(len(heavy_nodes))]
    hpos = [[] for _ in range(n)]

    # precompute heavy structures
    for hid, v in enumerate(heavy_nodes):
        for u, w in adj[v]:
            hpos[u].append((hid, w))
            cu = col[u]
            hcnt[hid][cu] = hcnt[hid].get(cu, 0) + w

    # initial answer
    ans = 0
    for u, v, w in edges:
        if col[u] != col[v]:
            ans += w

    for _ in range(q):
        v, nc = map(int, input().split())
        v -= 1
        nc -= 1
        oc = col[v]

        if oc == nc:
            print(ans)
            continue

        if heavy[v]:
            hid = heavy_idx[v]
            # remove old color contribution
            ans -= hcnt[hid].get(oc, 0)
            # add new color contribution
            ans += hcnt[hid].get(nc, 0)

        else:
            for u, w in adj[v]:
                if col[u] == oc and col[u] != nc:
                    ans += w
                elif col[u] != oc and col[u] == nc:
                    ans -= w
                elif col[u] != oc and col[u] != nc:
                    pass
                else:
                    pass

        # update heavy neighbor tables
        for hid, w in hpos[v]:
            oldc = col[v]
            hcnt[hid][oldc] = hcnt[hid].get(oldc, 0) - w
            hcnt[hid][nc] = hcnt[hid].get(nc, 0) + w

        col[v] = nc
        print(ans)

def main():
    t = int(input())
    for _ in range(t):
        solve()

if __name__ == "__main__":
    main()
```このコードは、隣接リストを構築し、すべてのエッジを 1 回チェックして初期総コストを計算することから始まります。 次に、√n しきい値を使用して重い頂点を識別します。 

重い頂点ごとに、色から入射エッジの重みの合計までのマッピングが事前計算されます。 これにより、大量の更新に対する定時クエリが可能になります。 

クエリ中に頂点が重い場合、応答の変更はすべてそのカラー バケットを使用して計算されます。 軽い場合は近隣住民を直接検査します。 

補助構造 hpos は、頂点ごとに、その頂点がどのヘビー ノードに寄与しているかを記録します。そのため、その色が変化したときに、O(√n) によって制限される O(#heavy neighbors) 内のすべてのヘビー カウンターを更新できます。 

## 実用的な例

 重み 3、2、5 と初期色 [1、2、1、3] を持つ 4 つの頂点が一列に並ぶ小さなツリーを考えてみましょう。 頂点 2 を 1 に再色し、次に頂点 3 を 2 に再色するとします。 

| ステップ | 変更された頂点 | 旧色 | 新色 | 直接更新 | 答え |
 | --- | --- | --- | --- | --- | --- |
 | 0 | - | - | - | 初期エッジ 1-2、2-3、3-4 | 計算された |
 | 1 | 2 | 2 | 1 | エッジ (1-2)、(2-3) を更新 | 新しい合計 |
 | 2 | 3 | 1 | 2 | エッジ (2-3)、(3-4) を更新 | 最終合計 |

 このトレースは、ローカル エッジのみが変更され、更新ルールは再色付けされた頂点の端点のみに依存することを示しています。 

ここで、中心 1 が最初はすべて同じ色の多くの葉に接続されている星を考えてみましょう。 中央の色を変更すると、すべてのエッジが一度に切り替わります。 単純なアプローチでは、これはクエリごとに O(n) ですが、重光スキームでは中心が重く、その効果はすべての葉をスキャンするのではなく、集約された色の合計を使用して計算されます。 

これは、重い頂点に対してカラーウェイト バケットを前処理することの主な利点を示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) √n) | 各頂点は、次数が小さい場合は軽いか、定数時間のルックアップでは重いかのいずれかです。 重い構造への更新は √n | によって制限されます。 
| スペース | O(n) | 隣接関係に加えて重いカラー マップと補助配列 |

 すべてのテスト ケースの合計サイズ制約の合計は 2e5 以内に保たれるため、√ 分解によりメモリとランタイムの両方が制限内に快適に収まることが保証されます。

 ## 特殊なケース

 単一ノード ツリーは、アルゴリズムが答えをゼロとして正しく初期化し、孤立した頂点の隣接リストへのアクセスを回避する必要があることをすぐに示します。 エッジが存在しないため、前処理ループはこれを自然に処理します。 

単一の頂点を中心とする星は、重光の分割を強調します。 中心部が重くなるため、すべての葉に再着色を繰り返さないでください。 代わりに、集約されたカラー バケットは O(1) の正しいデルタを提供し、更新はリーフの重度の近傍の数 (小さい) によって制限されたままになります。 

色が交互になるチェーンでは、エッジの更新が再色のたびに 1 回だけ適用されるかどうかをテストします。 各更新は変更された頂点の隣接するエッジのみに接触するため、伝播はすぐ隣を越えて漏れることはありません。
