 ## 解決策
 ## 問題の理解

 A と B の 2 つの文字のみで構成される文字列が与えられます。これは、隣接するタイルの行と考えることができます。 唯一許可される動きは、A の直後に B が続く位置を選択し、A が 1 ステップ右に移動するようにそれらを交換することです。 2 つの文字の間の各位置は、交換位置として最大 1 回使用できますが、交換は任意の順序で適用でき、交換が実行されると文字列が進化します。 

タスクは、プロセス全体で実行できるこのようなスワップの最大数を決定することです。 

すべてのテスト ケースの長さの合計が最大 2⋅10^5 であるという制約は、テスト ケースごとの O(n²) シミュレーションが遅すぎることを直ちに示唆します。 どのソリューションも、テスト ケースごとに本質的に線形または線形に近いものでなければなりません。 

重要な点は、スワップによって文字列が変更されるため、ローカルでの貪欲な決定が、後で同じインデックスで別のスワップが可能になるかどうかに影響を与える可能性があることです。 もう 1 つの罠は、「AB」の最初の出現をカウントするだけで十分であると想定していることです。 たとえば、ABAB では、位置 1 で交換した後、BAAB が得られ、最初は存在しなかった別の位置に新しい「AB」が作成されます。 

2 番目の微妙なケースは、スワップによって B の長いブロック全体で A が「移動」される場合です。 たとえば、ABBBBA では、1 つの A が複数の境界と相互作用する可能性がありますが、各インデックスは 1 回しか使用できないため、無制限のバブリングは防止されます。 

重要な問題は、スワップが独立していないことです。スワップはポジションを消費しますが、文字列構成は他の場所で新しいスワップを可能にする方法で進化します。 

## アプローチ

 ブルート フォース シミュレーションでは、文字列を繰り返しスキャンし、AB が存在するがまだ使用されていないインデックス i を見つけ、スワップを適用し、残りの動きがなくなるまで繰り返します。 各スワップは次の有効な操作を見つけるのに O(n) かかりますが、病的な場合には最大 O(n²) 個のスワップが発生する可能性があり、単純な実装では合計で O(n³) 個の動作が得られます。 慎重に帳簿を付けたとしても、スワップはローカルで機会を生み出したり破壊したりするため、有効なポジションの動的なセットを維持するには依然としてコストがかかります。 

重要な点は、実際には文字列の進化をシミュレートする必要がないということです。 各スワップは、境界で A が B を横切ることに対応し、各境界インデックスは最大 1 回使用できます。 文字列の変更という観点から考えるのではなく、どのような潜在的な「交差」が実現できるかを追跡します。 

すべての A を B を横切って右方向に移動できるものとして解釈すると、各スワップは本質的に局所的な反転 AB → BA を解決します。 ただし、インデックス i でスワップが発生すると、その境界は永続的に使い果たされるため、この構造は、展開する隣接グラフで互いに素な有効な AB 遷移を選択することに近づきます。 

重要な簡略化は、このプロセスは使用可能な AB 境界を繰り返し消費することに相当しますが、新しい AB 境界は A が B を横切って移動するときにのみ表示されることを理解することです。これにより、各 A を複数の B ブロックと組み合わせることができるフローのような効果が作成されますが、各インデックスは 1 回しか使用できません。 これを捉える正しい方法は、B トランジションを消費するために「左側で使用できる」 A の数を維持しながら、左から右に処理することです。 

私たちは、まだ右に移動できるアクティブな A の数を維持します。 B が表示されるたびに、その左側にある A のいずれかと交換される可能性がありますが、これは未使用の境界が存在する場合に限られます。 各 B は事実上、1 つの利用可能な A コントリビューションの潜在的な消費を表し、成功した各ペアリングは 1 つの有効な操作に対応します。 

これにより、A を蓄積し、B に遭遇したときにそれらを消費する貪欲なスイープが発生し、各インタラクションが一意のインデックスの使用に対応することが保証されます。

 ## アルゴリズムのチュートリアル

 文字列を左から右に処理し、将来のスワップに参加できる現在利用可能な A の数を維持します。 

1. カウンタを初期化する`available_A = 0`そして答え`ops = 0`。 
2. 文字を左から右にスキャンします。 
3. を見たとき`A`、増やします`available_A`by 1。これは、将来の B を横切って移動する可能性がある A を表します。 
4. を見たとき`B`、その左側に利用可能な A があるかどうかを確認します。 もし`available_A > 0`、1 つの操作を実行します。この B を 1 つの利用可能な A と照合し、インクリメントします。`ops`1 ずつ減分`available_A`。 

直感的には、成功した各一致は、A がこの B 境界を越える 1 つのスワップに対応します。 

1. 文字列の終わりまで続けます。 
2. 出力`ops`。 

B を常に最も早い利用可能な A と一致させるという貪欲な選択は、将来のスワップに寄与するという点で左側の A は交換可能であるため、安全です。 各 B は有益なペアリングで最大 1 回しか使用できないため、試合を遅らせても将来の試合の数を増やすことはできません。 

### なぜ効果があるのか

 スキャンのどの時点でも、`available_A`は、右側の B とのスワップに参加する未使用の可能性をまだ持っている A の数を表します。 B 経由で 1 つを消費するたびに、1 つの異なるインデックスレベルのインタラクションにコミットすることになります。 成功した各操作は、左側 A の容量と B 位置の 1 ユニットを永続的に消費するため、制御された方法で可用性を低下させることを除いて、他の操作に干渉することはありません。 これにより、起こり得るスワップの単調な計算が維持され、カウントされたすべての操作が、何らかの達成可能なシーケンス内の有効かつ個別の AB スワップ位置に対応することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        s = input().strip()

        available_A = 0
        ops = 0

        for ch in s:
            if ch == 'A':
                available_A += 1
            else:
                if available_A > 0:
                    available_A -= 1
                    ops += 1

        print(ops)

if __name__ == "__main__":
    solve()
```The solution is structured around a single pass per test case. The only state we maintain is how many A’s are currently usable for future swaps and how many swaps we have already counted.

 重要な実装の詳細は、明示的にスワップをシミュレートしたり、文字列を変更したりしないことです。 これにより、誤った連鎖反応や新しく作成された AB ペアの欠落のリスクが回避されます。 スキャン順序により、すべての B が厳密にその左側にある A のみを考慮することが保証され、これは許可された操作の方向性の性質と一致します。

 ## 特殊なケース

 微妙なエッジ ケースは、すべての A が左側にあり、すべての B が右側にある場合です。たとえば、`AAABBB`。 アルゴリズムは最初にすべての A を処理し、累積します。`available_A = 3`、B が出現するとそれらを消費し、3 つの操作を生成します。 これは、各 B が以前の 1 つの A とペアになることができるという事実と一致します。 

もう 1 つのエッジ ケースは、A と B が頻繁に交互に現れる場合です。 例`ABABAB`これは、すべての B が可能であれば 1 つの利用可能な A を即座に消費し、新しく出現した A は後で正しく考慮されるため、貪欲なマッチングが引き続き成功することを示しています。 

最後のエッジ ケースは、次のように、B の後に A が続くプレフィックスです。`BBBAAA`。 B に遭遇したときに使用可能な A がないため、操作はまったく不可能であり、方向の制約により、後の A は前の B に遡って影響を与えることはできません。
