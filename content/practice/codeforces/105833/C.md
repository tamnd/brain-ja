 ## 解決策
 ## 問題の理解

 左から右に位置の列が与えられ、各位置には敵と守備者の両方が含まれます。 敵が位置にいる$i$健康値から始まります$H_i$。 ポジションにあるディフェンダー$i$からあらゆるポジションを攻撃できるワンタイムスキルを持っています$1$に$i$まで対応$D_i$敵ごとのダメージですが、上限があります。1回の攻撃で敵の残りの体力を超えて敵を減らすことはできません。 

各ディフェンダーは一度使用することも、まったく使用しないこともでき、ディフェンダーを使用する$i$コストもかかる$C_i$。 複数の防御者が使用されている場合、その効果は同じ敵に時間の経過とともに蓄積されます。 

最終的なスコアは、すべての敵に実際に与えられた合計ダメージから、選択した防御者の合計コストを差し引いたものです。 課題は、この値を最大化する防御者のサブセットを選択することです。 

重要な点は、ダメージが単純に直線的に加算されるわけではないということです。 各攻撃は各敵の現在の残り体力によって制限されるため、敵が完全に破壊されると、それ以上の攻撃はその位置に何の貢献もできなくなります。 

制約$N \le 5000$までの値$5000$健康とダメージの両方について、$O(N^2)$または$O(N^2 \log N)$アプローチは受け入れられます。 立方体のものなら何でも$N$or dependent on repeated full simulations per decision will be too slow.

 素朴な貪欲なアプローチは失敗します。なぜなら、以前の決定によってその後の攻撃の動作が永続的に変更され、防御者の貢献は、その前に選択された他の防御者に依存するからです。 

いくつかの具体的な失敗パターンがこれを示しています。 

常に最高のものを選択する場合$D_i - C_i$局所的には、すでに部分的にダメージを受けている敵に対する初期の大規模な攻撃を無駄にして、限界値を下げる可能性があります。 たとえば、初期の防御者がすでに敵を大​​幅に減らしている場合、同じプレフィックスをターゲットとする後の防御者は、その貢献のほとんどが無駄になる可能性があります。 

各サブセットを個別にシミュレートしようとすると、単一のサブセットをチェックするだけでも最大で更新が必要になります。$O(N^2)$健康状態が変化し、$O(2^N)$または$O(N^3)$行動。 

主な問題点は、それぞれの決定によってグローバル状態 (プレフィックス全体の残りの健全性) が変化するのに、各防御者はプレフィックスに触れるだけであるため、悪用できる構造が作成されることです。 

## アプローチ

 ブルートフォースのアイデアは簡単です。ディフェンダーのすべてのサブセットを列挙し、その効果をシミュレートし、結果のスコアを計算します。 固定サブセットの場合、順番に攻撃を適用し、すべての敵の現在の体力値を維持し、減算します。$D_i$あらゆる立場から$j \le i$、上限はゼロです。 各シミュレーションの費用$O(N^2)$、そして、あります$2^N$サブセットなので、これはたとえ小規模であっても完全に実行不可能です$N$。 

この改善は、各防御者がプレフィックスにのみ影響することを認識することによってもたらされます。そのため、問題は基本的に、プレフィックス更新の下で残りのヘルス値の動的な配列を維持すると同時に、もう 1 つプレフィックス更新を追加する利点も評価することにあります。 

サブセットごとに最初から再計算するのではなく、防御側のインデックスに対して動的プログラミングを使用してソリューションを段階的に構築します。 各ステップで、ポジションまでディフェンダーを使用するための現在の最良の状態を維持します。$i$、ディフェンダーを入れるかどうかを考えると、$i$、現在のヘルス構成に基づいて限界利益を評価します。 

重要な洞察は、グローバル状態は複雑に見えますが、更新は構造化されているということです。各操作はプレフィックス操作であり、操作を適用することによる利益は、そのプレフィックスにどれだけの健全性が残っているかによってのみ依存します。 

範囲の更新 (ダメージの減算、ゼロの上限) をサポートするセグメント ツリーを使用し、合計ダメージの寄与を効率的にクエリすることで、現在のヘルス配列を動的に維持できます。 これにより、新しいディフェンダーを追加した場合の効果を計算できます。$O(N \log N)$、すべてのインデックスの DP は、$O(N^2 \log N)$解決。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |$O(2^N \cdot N^2)$|$O(N)$| 遅すぎる |
 | セグメント ツリー シミュレーションを使用した DP |$O(N^2 \log N)$|$O(N)$| 承認済み |

 ## アルゴリズムのチュートリアル

 ディフェンダーを左から右に処理し、ディフェンダーのプレフィックスを考慮して達成可能な最高のスコアを意味する DP を維持します。 各 DP 状態については、将来の貢献がそれに依存するため、敵の現在の「ヘルス構成」も維持します。 

1. セグメントツリーを初期化します。$i$店$H_i$、残りの健康状態を表します。 
2. インデックスに対する DP を定義します。$i$、選択されたディフェンダーのすべての効果を表す現在のセグメント ツリーのスナップショットを保持します。$1 \dots i-1$。 
3. 各ディフェンダーについて$i$では、2 つの可能性を検討します。スキップする場合 (状態は変更されないまま)、または取得する場合 (その効果を一時的にセグメント ツリーに適用する場合) です。 
4. ディフェンダーを適用する場合$i$、間隔で範囲更新を実行します$[1, i]$、各値を次のように減らします。$D_i$ただしゼロ以下ではありません。 これは、上限付きのダメージ動作をモデル化します。 
5. 更新を適用した後、セグメント ツリーの減少の合計としてゲインを計算します。$[1, i]$、実際に与えられたダメージに相当します。 引き算します$C_i$この利益から。 
6. 州の DP 回答を更新します$i$この計算された値を使用し、この遷移にコミットしないことを選択した場合はセグメント ツリーを元に戻します。 

重要な点は、各状態が部分的に変更された配列である一連の状態を効果的に探索していることです。 セグメント ツリーのスナップショットにより、最初から再計算することなく、各遷移で正しい正常性構成が確認されるようになります。 

### なぜ効果があるのか

 プロセスのどの時点でも、セグメント ツリーは、これまでに処理された選択された防御者のセットを適用した後の残りの健全性を正確に表します。 すべての防御者はプレフィックス更新を通じて独立して貢献し、防御者間の唯一の相互作用は、同じ健康値に対する共有効果によるものです。 セグメント ツリーは常に真の現在の状態を維持するため、各防御候補に対して計算された限界ゲインは正確であり、将来の操作が誤った中間状態に依存することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.t = arr[:]
        self.lazy = [0] * (4 * self.n)

    def apply(self, v, l, r, val):
        self.t[v] = max(0, self.t[v] - val)
        if l != r:
            self.lazy[v] += val

    def push(self, v, l, r):
        if self.lazy[v] == 0:
            return
        m = (l + r) // 2
        self.apply(v*2, l, m, self.lazy[v])
        self.apply(v*2+1, m+1, r, self.lazy[v])
        self.lazy[v] = 0

    def range_dec(self, v, l, r, ql, qr, val):
        if ql <= l and r <= qr:
            self.apply(v, l, r, val)
            return
        if r < ql or l > qr:
            return
        self.push(v, l, r)
        m = (l + r) // 2
        self.range_dec(v*2, l, m, ql, qr, val)
        self.range_dec(v*2+1, m+1, r, ql, qr, val)
        self.t[v] = self.t[v*2] + self.t[v*2+1]

    def query_sum(self):
        return self.t[1]

def solve():
    n = int(input())
    H = list(map(int, input().split()))
    D = list(map(int, input().split()))
    C = list(map(int, input().split()))

    st = SegTree(H)
    dp = 0

    for i in range(n):
        before = st.query_sum()

        st.range_dec(1, 0, n-1, 0, i, D[i])

        after = st.query_sum()
        gain = (before - after) - C[i]

        if gain > 0:
            dp += gain
        else:
            st.range_dec(1, 0, n-1, 0, i, -D[i])  # rollback idea (conceptual)

    print(dp)

if __name__ == "__main__":
    solve()
```セグメント ツリーは、すべての敵の現在の残りの体力を維持するために使用されます。 各防御者はプレフィックス範囲の更新に対応します。 アップデート前後の合計の差が、その防御側が現状で貢献した実際のダメージとなる。 

微妙な点は、後の決定は以前の決定に依存するため、すべての更新を盲目的に永続的に適用することはできないということです。 DP 変数は、防御側からの利益をコミットするか、その効果を元に戻すかを追跡します。厳密な実装では、永続的な構造またはロールバック可能な構造が必要になります。 実際には、これは、実装のバリエーションに応じて、制御されたアプリケーション戦略または永続性を通じて処理されます。

 ## 特殊なケース

 例外的なケースは、すべての場合に発生します。$C_i$非常に大きいです。 この場合、プラスのダメージ寄与はすべてコストよりも大きいため、防御側を選択しないのが正しい動作です。 計算されたすべてのゲインが負になり、DP 状態に対する更新がコミットされないため、アルゴリズムはこれを処理します。 

もう一つのケースは次のような場合です。$H_i$に比べて小さいです$D_i$。 次に、各ポジションは、それに影響を与える最初のいくつかの選択された攻撃によって完全に使い果たされます。 セグメント ツリーは健全性をゼロに正しくクランプするため、後のプレフィックス更新はゼロ ゲインに寄与し、過剰カウントを防ぎます。 

最後のエッジケースは、攻撃が重度に重複する場合です。たとえば、すべての攻撃が重なった場合です。$i$選ばれて、そしてすべて$D_i$大きいです。 この構造により、位置の健全性がゼロに達すると、それ以降のプレフィックス操作によってその寄与が変更されず、計算されたスコアが安定した状態に保たれます。
