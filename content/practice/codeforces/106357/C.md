 ## 解決策
 ## 問題の理解

 私たちは構造が決して変わらない根のあるツリーを扱っていますが、「ルート」が何を意味するのかという概念は固定されていません。 時間の経過とともに、ツリーのルートが別のノードに移動する可能性があり、現在のルートの下で最も共通する祖先のクエリに答えるように求められます。 

各クエリは、ルートとみなされるノードを変更するか、現在のルートに関して 2 つのノードの最も低い共通祖先を尋ねます。 重要な微妙な点は、「最下位の共通祖先」がルートの定義に依存するため、ルートが移動すると、基礎となるエッジが同じであっても、祖先の関係が実質的に変化することです。 

入力は、次の初期ツリーを記述します。`n`ノードの後に​​一連の操作が続きます。 一部の操作ではルートを特定のノードに再割り当てし、その他の操作では現在のルート構成にある 2 つのノードの LCA を要求します。 出力は、クエリ操作に対する回答のみで構成されます。 

この制約は、ルートが変更されるたびに祖先構造を最初から再計算できないことを意味します。 もし`n`クエリの数は次のとおりです`2 * 10^5`、親ポインターを再構築したり、クエリごとに DFS を再実行したりするソリューションは、すぐに時間制限を超過します。 クエリごとの線形スキャンでさえ、最悪の場合二次的な動作につながるため、遅すぎます。 これにより、すべての構造情報が一度準備され、各クエリが対数時間で応答される静的前処理アプローチが強制されます。 

よくある失敗例は、ツリーを常にノード 1 にルートしているかのように扱う場合に発生します。たとえば、ツリーがチェーンであると仮定します。`1 - 2 - 3 - 4`。 ルートが次のように変更された場合`4`、次に次の LCA`2`そして`3`新しいルートの下には`3`、 ない`2`または`1`。 元のルートで計算された単純な LCA は、誤った値を返します。`2`。 この静的ルート定義と動的ルート定義の不一致が、最大の問題点です。 

別のエッジ ケースは、クエリされたノードの 1 つが現在のルートである場合に発生します。 その場合、他のノードに関係なく、答えは常にルート自体になります。 多くの誤った実装では、この特別な構造が忘れられ、依然として固定根 LCA 式が適用され、誤った祖先が生成されます。 

## アプローチ

 ブルートフォース戦略では、ルートが変更されるたびに親と深さの情報が再計算されます。 ルートが変更されるたびに、祖先テーブルを再構築するために新しいルートからの完全な DFS が必要になり、各 LCA クエリは標準のバイナリ リフティング手法を使用して応答されます。 各構成は有効なルート ツリーであるため、これは論理的に機能しますが、非常に遅すぎます。 まで`10^5`運用と各再構築のコスト計算`O(n)`、最悪の場合に達します`O(nq)`のオーダーです。`10^10`操作。 

重要な観察は、基礎となるツリーが決して変更されないということです。 ルートを移動すると、祖先の視点だけが変わります。 構造を再構築する代わりに、任意の固定ノード (通常はノード) をルートとする単一の前処理を再利用できます。`1`。 標準的なバイナリ リフティング LCA 構造を取得したら、ツリー パスの幾何学的プロパティを使用して、さまざまなルートの結果を再解釈できます。3 つの LCA のうち任意のツリー上で`lca(u, v)`、`lca(u, r)`、 そして`lca(v, r)`、ルート依存の LCA クエリの答えは、これら 3 つのノードのいずれかである必要があります。 

これは、ルートを変更しても、一意のパスのどのセグメントが別のノードの「下」と見なされるかを変更するだけであるという事実から来ています。 動的ルートの下にある正しい LCA は、常にこれら 3 つの候補の中で最も深いノードになります。

 ## アルゴリズムのチュートリアル

 通常、任意のノードを修正します。`1`、前処理のルートとして使用し、標準のバイナリ リフティング テーブルを構築します。 

1. ノードから DFS を実行する`1`計算する`depth[u]`そして直属の親`up[u][0]`。 これにより、一貫したルート構造が得られます。 
2. バイナリリフティングテーブルを構築する`up[u][k]`、 どこ`up[u][k]`です`2^k`- 番目の祖先`u`。 これにより、対数時間でツリーをジャンプすることができます。 
3. 変数を維持する`root`に初期化されました`1`。 これは、現在のアクティブなルートを表します。 
4. ルート変更操作の場合は、単純に更新します。`root`指定されたノードに送信されます。 構造的な更新は実行されません。 
5. お問い合わせの場合`(u, v)`、固定ルート構造を使用して 3 つの標準 LCA を計算します。`a = lca(u, v)`、`b = lca(u, root)`、 そして`c = lca(v, root)`。 
6. 中で`a`、`b`、 そして`c`、元のツリーで最大の深さのノードを選択します。 そのノードがクエリに対する答えです。 

ステップ 6 が機能する理由は、これらの候補のうち 1 つだけが、現在のルートの下で祖先を定義するパスの「再ルートされた」交差点に存在できるためです。 

### なぜ効果があるのか

 前処理により、参照ツリー構造が固定されます。 ルートを変更しても距離や経路は変更されず、祖先を解釈する方向のみが変更されます。 任意の 2 つのノードの場合`u`そして`v`、ルートの下の真の LCA`r`接続する 3 つのパスの交差点になければなりません`u`、`v`、 そして`r`。 その交差部分は、元のルート ツリーで計算された 3 つのペアワイズ LCA によって完全にキャプチャされます。 それらの中で最も深いものを選択すると、両方に最も近いノードが特定されます。`u`そして`v`新しいルートの方向と一貫性を保ちながら、これはまさに動的 LCA の定義です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

n, q = map(int, input().split())
g = [[] for _ in range(n + 1)]

for _ in range(n - 1):
    u, v = map(int, input().split())
    g[u].append(v)
    g[v].append(u)

LOG = (n).bit_length()
up = [[0] * (LOG + 1) for _ in range(n + 1)]
depth = [0] * (n + 1)

def dfs(v, p):
    up[v][0] = p
    for to in g[v]:
        if to == p:
            continue
        depth[to] = depth[v] + 1
        dfs(to, v)

dfs(1, 0)

for j in range(1, LOG + 1):
    for i in range(1, n + 1):
        up[i][j] = up[up[i][j - 1]][j - 1]

def lift(v, k):
    for i in range(LOG + 1):
        if k & (1 << i):
            v = up[v][i]
    return v

def lca(a, b):
    if depth[a] < depth[b]:
        a, b = b, a
    a = lift(a, depth[a] - depth[b])
    if a == b:
        return a
    for i in range(LOG, -1, -1):
        if up[a][i] != up[b][i]:
            a = up[a][i]
            b = up[b][i]
    return up[a][0]

root = 1
out = []

for _ in range(q):
    tmp = input().split()
    if tmp[0] == '0':
        root = int(tmp[1])
    else:
        u, v = map(int, tmp[1:])

        a = lca(u, v)
        b = lca(u, root)
        c = lca(v, root)

        ans = a
        if depth[b] > depth[ans]:
            ans = b
        if depth[c] > depth[ans]:
            ans = c

        out.append(str(ans))

print("\n".join(out))
```DFS はノードに固定ルート ツリーを構築します。`1`、深さと祖先ポインターを計算するためにのみ使用されます。 バイナリリフティングテーブル`up`上向きに 2 倍のジャンプ力を可能にします`O(log n)`時間。 

の`lca`この関数は静的ツリーの標準です。深さを等しくして、親が一致するまで両方のノードを上に登ります。 

唯一の動的部分は、`root`変数。 各クエリは静的ルートの下で 3 つの LCA を計算し、最も深いノードを選択します。これにより、何も再構築せずに現在のルートの下で祖先が効果的に再構築されます。 

よくある実装上の間違いは、スワップを忘れることです`(u, v)`深さによって`lca`、1 つのノードが深くなると正確さが失われます。 もう 1 つの微妙な問題は、深さは常に元のルートを参照する必要があるため、候補を比較するときに間違った深さ参照を使用することです。`1`、動的ルートではありません。 

## 実用的な例

 入力操作:`root = 4`、クエリ`(2, 3)`| ステップ | あなた | v | ルート | lca(u,v) | lca(u,r) | lca(v,r) | 選ばれた |

これらの例は、アルゴリズムが親関係を明示的に再構築しないにもかかわらず、パスの構造的交差に依存することでさまざまなルートに正しく適応することを示しています。

 ## 特殊なケース

 星型のツリーの中で、ノードを言う`1`他のすべてに接続すると、リーフ間のルートを変更すると、ほとんどの LCA が中心に折りたたまれる状況が作成されます。 すべてのペアワイズ LCA が中心または葉の 1 つであり、静的ルート ツリーの中間候補よりも構造的に深い場合、深さの比較により中心が正しく選択されるため、アルゴリズムはこれを自然に処理します。 

線形チェーンでは、終点での再ルートにより、認識されている祖先の方向が逆転します。 エンドポイントと中間ノードを含むクエリでも正しい結果が生成されます。これは、3 つの LCA の 1 つがノードとルートの間のパス上の最も深い交差点を常にキャプチャし、単純な固定ルート解釈で発生する誤った「上向き」ジャンプを防ぐためです。
