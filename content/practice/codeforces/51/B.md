 ## 解決策
 ## 問題の理解

 簡略化された HTML テーブル言語を表す文字列が与えられます。 この言語には 3 種類のタグのみが含まれています。`<table>`、`<tr>`、 そして`<td>`、対応する終了タグとともに。 テーブルには行が含まれており、各行にはセルが含まれており、セルは空であるか、別の完全なテーブルを含んでいます。 

タスクは、ネストされたテーブルを含む、文書内に表示されるすべてのテーブル内の直接セルの数を見つけることです。 各テーブルについて、その数を数えます。`<td>...</td>`要素は、セル内にネストされたテーブルではなく、そのテーブルに直接属します。 すべてのカウントを収集した後、それらを非降順で出力します。 

入力長は最大 5000 文字です。 これは線形アルゴリズムや二次アルゴリズムには十分小さいですが、大きな部分文字列の再帰的再解析は不注意に実装すると依然としてコストが高くなる可能性があります。 5000 個の操作は制限時間をはるかに超えているため、キュービック パーサーはすでに危険です。 スタックを備えたクリーンなシングルパスパーサーは、制約内に簡単に適合します。 

文法によって入力が有効であることが保証されるため、不正な形式のタグから回復する必要はありません。 すべての開始タグには一致する終了タグがあり、ネストは常に正しく行われます。 

問題の微妙な部分は、直接セルとネストされたテーブルに属するセルを区別することです。 

次の入力を考えてみましょう。```
<table><tr><td><table><tr><td></td></tr></table></td></tr></table>
```ネストされたテーブル内に別のセルが存在する場合でも、外部テーブルにはセルが 1 つだけあります。 正しい出力は次のとおりです。```
1 1
```単純にすべてをカウントする単純なカウンター`<td>`テーブル範囲内のタグが誤ってレポートする`2`外側のテーブルの場合。 

もう 1 つの簡単な間違いは、テーブルは必ずしも長方形ではないということを忘れていることです。 

例：```
<table><tr><td></td><td></td></tr><tr><td></td></tr></table>
```このテーブルにはセルが 4 つではなく、合計 3 つあります。 行の長さは異なる場合があります。 

3 番目の落とし穴は、最初にすべての行を連結するのではなく、入力を 1 行ずつ処理することです。 このステートメントでは、任意の改行を明示的に許可します。 

例えば：```
<table><tr>
<td></td>
</tr></table>
```これらの行は一緒になって 1 つの有効な文字列を形成します。 行を個別に処理すると、パーサーが壊れます。 

## アプローチ

 最も簡単なアプローチは、すべてのテーブルを個別に解析することです。 私たちが何かに遭遇するたびに、`<table>`、一致するものを検索します`</table>`、その部分文字列を抽出し、直接の数を数えます`<td>`タグはそれに属します。 ネストされたテーブルのセルをカウントしないようにするには、部分文字列のスキャン中に別のネスト カウンタが必要になります。 

これは論理的に機能しますが、作業を何度も繰り返します。 最悪の場合、テーブルが深くネストされていると、各テーブルの残りの文字列のほぼ全体を再スキャンする必要があります。 ネストの深さが`n`、合計作業量はおおよそ次のようになります。```
n + (n - 1) + (n - 2) + ...
```それは二次関数です。 

長さ 5000 の場合でも、`O(n²)`おそらくパスしますが、一致するタグを繰り返し検索し、同じ領域を繰り返し走査するため、実装が面倒になります。 

文法の構造により、より明確なアイデアが得られます。 すべてのタグは、かっことまったく同じように、適切にネストされた順序で表示されます。 つまり、スタックを使用して文字列を左から右に 1 回処理できるということです。 

重要な観察は、テーブルを閉じるときにテーブルのセル数が正確に分かることです。 すべてのダイレクト`<td>`テーブルがアクティブなときに発生したものは、そのテーブルに属します。 ネストされたテーブルはより深いスタック レベルで処理されるため、干渉しません。 

したがって、部分文字列を再解析する代わりに、現在開いているテーブルのスタックを維持します。 見ると`<table>`、新しいカウンターを作成します。 見ると`<td>`、現在のテーブルのカウンターをインクリメントします。 見ると`</table>`、そのテーブルを完成させ、そのカウントを保存します。 

これにより、問題は単純な線形スキャンに変わります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n²) | O(n) | 受け入れられるが非効率的 |
 | 最適 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべての入力行を読み取り、それらを 1 つの文字列に連結します。 

文法では行の境界が無視されるため、パーサーは結合された文字列を操作する必要があります。 
2. 文字列を左から右にスキャンします。 

意味のあるすべてのトークンは、次のような完全なタグです。`<table>`または`</td>`。 タグ セットは小さくて固定されているため、文字列プレフィックス チェックを使用してタグを識別できます。 
3. 各要素が開いているテーブルの直接セルの現在の数を格納するスタックを維持します。 

スタックの最上位は常に、現在いるテーブルを表します。 
4. 遭遇したとき`<table>`、 押す`0`スタックに。 

新しいテーブルは、これまでにカウントされたセルが 0 個の状態から始まります。 
5. 遭遇したとき`<td>`、スタックの最上位要素をインクリメントします。 

毎`<td>`現在アクティブなテーブルに直接属します。 後でこのセルに別のテーブルが含まれる場合でも、それは依然として現在のテーブルの 1 つの直接のセルです。 
6. 無視する`<tr>`、`</tr>`、 そして`</td>`。 

これらは構造の有効性に影響しますが、セル数は変更しません。 
7. 遭遇したとき`</table>`、スタックから最上位の値をポップし、回答リストに追加します。 

現時点では、テーブルは完全に処理されているため、その直接のセル数は最終的なものになります。 
8. スキャンが終了したら、収集したカウントを並べ替えます。 
9. カウントをスペースで区切って出力します。 

### なぜ効果があるのか

 スキャン中のどの位置でも、スタックは現在開いているテーブルのチェーンを最も外側から最も内側まで正確に表します。 毎`<td>`文法では現在のテーブルの行内にのみセルを許可するため、タグは最も内側の開いたテーブルに属します。 ネストされたテーブルは新しいスタック レベルを作成するため、そのセルが親カウンターに影響を与えることはありません。 いつ`</table>`というメッセージが表示された場合、そのテーブルの内容はすべてすでに処理されており、保存されているカウンターが完全で正しいことを意味します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = "".join(line.strip() for line in sys.stdin)

    stack = []
    ans = []

    i = 0
    n = len(s)

    while i < n:
        if s.startswith("<table>", i):
            stack.append(0)
            i += 7

        elif s.startswith("</table>", i):
            ans.append(stack.pop())
            i += 8

        elif s.startswith("<td>", i):
            stack[-1] += 1
            i += 4

        elif s.startswith("</td>", i):
            i += 5

        elif s.startswith("<tr>", i):
            i += 4

        elif s.startswith("</tr>", i):
            i += 5

    ans.sort()
    print(*ans)

if __name__ == "__main__":
    solve()
```最初のステップでは、すべての入力行を 1 つの連続した文字列に連結します。 使用する`strip()`実際のマークアップを保持しながら改行文字を削除します。 

パーサーは単一のインデックスを処理します`i`。 有効なトークンはすべて固定長であるため、タグに一致した直後にポインタを進めることができます。 

スタックには、開いているテーブルごとに 1 つの整数が格納されます。 新しいテーブルが開始されると、プッシュします`0`。 毎`<td>`直接の所有権は常に現在のテーブルに属するため、最上位の要素のみが増分されます。 

条件の順序は多少重要です。`<table>`そして`</table>`プレフィックスを共有します。 終了タグの前に開始タグをチェックすることで、明確な一致が維持されます。 

行タグは必要な回答に影響を与えないため、完全に無視します。 それらの唯一の役割は文法の妥当性を強制することであり、それはステートメントによってすでに保証されています。 

テーブルが閉じると、そのカウンターが完了するので、それをポップして保存します。`ans`。 

最後に、並べ替えにより、必要な非降順の順序が生成されます。

 ## 特殊なケース

 入れ子になったテーブルのケースをもう一度考えてみましょう。```
<table><tr><td><table><tr><td></td></tr></table></td></tr></table>
```実行は外部テーブルのカウンターから始まります`[0]`。 最初`<td>`に変更します`[1]`。 内部テーブルが開始されると、スタックは次のようになります。`[1, 0]`。 内側の`<td>`最上位レベルのみをインクリメントし、`[1, 1]`。 内部テーブルを閉じると、回答リストには次のものが含まれます。`[1]`、外側のカウンターは変更されません。 外部テーブルを閉じると別のテーブルが追加されます`1`。 最終的にソートされた出力は次のようになります。```
1 1
```これにより、ネストされたセルが親カウントに決して漏れないことが確認されます。 

次に、非長方形のテーブルを考えてみましょう。```
<table><tr><td></td><td></td></tr><tr><td></td></tr></table>
```パーサーは次の 3 つに遭遇します。`<td>`同じテーブルがアクティブである間はタグが付けられるため、そのカウンターは次のように変化します。```
0 -> 1 -> 2 -> 3
```カウントには行は関係ありません。 最終的な出力は次のとおりです。```
3
```これにより、すべての行の幅が等しいと想定するというよくある間違いを回避できます。 

最後に、複数行の入力について考えてみましょう。```
<table><tr>
<td></td>
</tr></table>
```このアルゴリズムは、まず、除去されたすべての行を次のように連結します。```
<table><tr><td></td></tr></table>
```その後、解析は正常に進行し、次のものが生成されます。```
1
```連結しないと、パーサーは改行境界を意味のある構造として誤って処理します。
