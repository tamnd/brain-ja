 ## 解決策
 ## 問題の理解

 それぞれのトラックに「かっこよさ」の数値が設定された循環プレイリストが与えられます。 選択したトラックから開始して、循環的な順序で前方に聞き続け、必要に応じてトラックを再訪問します。 聴いている間も、これまでにない最大限のかっこよさを維持しています。 

停止ルールは、この実行最大値に応じて異なります。 新しく再生されたトラックのクールさが現在の最大値の半分よりも厳密に低いと、すぐにリスニングが停止します。 トラックから開始するコストは、停止するまでに再生できたトラックの数であり、サイクルが終了した場合は繰り返しの訪問をカウントします。 

開始位置ごとに、どれくらいの時間聞き続けているかを計算するか、決して止まらないことを報告する必要があります。 

重要な制約は、n が最大 100,000 になる可能性があるため、各起動を個別にシミュレートするソリューションは直ちに遅すぎるということです。 単純なシミュレーションを開始ごとに行うと、最大 O(n) トラックが再訪され、O(n^2) 個の作業が必要になり、これを通過することはできません。 

微妙な難しさは、停止条件が、前進するにつれて進化するグローバル最大値に依存するため、このプロセスが単純な固定しきい値の比較ではないことです。 最大値は後で増加して制約が緩和される可能性があり、これにより単純な貪欲な停止決定が不正確になります。 

典型的なエッジケースは、数ステップ後に最大値が大幅に増加する場合に発生します。 たとえば、小さい値から開始すると、最初はすぐに停止すると予想されるかもしれませんが、後で値を大きくすると、しきい値が押し上げられ、より多くのトラバースが可能になる可能性があります。 これにより、純粋にローカルな推論が破壊されます。 

もう 1 つの注意が必要なケースは、すべての値が等しい場合です。 この場合、最大値は決して変化せず、厳密にその半分より小さい値は存在しないため、ウォークは決して停止せず、答えはすべてのインデックスで -1 になります。 最終的に障害が発生することを想定したソリューションは、誤って終了します。 

## アプローチ

 ブルートフォースアプローチは簡単です。 開始インデックス i ごとに、円の周りを前進し、これまでに確認された最大値を更新し、各ステップでの停止状態を確認することをシミュレートします。 i に戻るか、停止ルールがトリガーされるまで続行します。 

これは、説明されているプロセスを正確に反映しているため、正しいです。 ただし、最悪の場合、各開始は停止する前にほぼ配列全体を横断する可能性があり、n 個の開始があるため、O(n^2) 個の遷移が発生します。 n が最大 10^5 であるため、これは実現可能な限界をはるかに超えています。 

重要な観察は、このプロセスは、セグメント内の最大値と比較して小さすぎる値に遭遇する前にどこまで拡張できるかのみに依存しているということです。 i から始まるウォークを考えると、最大オーバープレフィックスは新しい最大値に達したときにのみ増加し、最大値の間のしきい値は固定されます。 これは、段階的にシミュレーションするのではなく、重要なポイント間をジャンプする必要があることを示唆しています。 

このような周期的な「次の悪い位置」クエリを高速化する標準的な方法は、値が特定のしきい値と比較して「危険なほど小さくなる」次のインデックスを位置ごとに事前計算することです。 しきい値はセグメントの最大値に依存するため、対数時間で次の故障候補点に繰り返しジャンプできる構造を構築することで問題を再構築します。 これは通常、セグメント ツリーまたはスパース テーブルを 2 倍の配列に対するバイナリ リフティングと組み合わせて使用​​して実現されます。 

周期的な動作を線形に処理するために配列を複製し、範囲の最大値を事前計算します。 次に、開始位置ごとにジャンプをシミュレートします。すべての要素が現在の最大値の少なくとも半分に保たれる、到達可能な最も遠い位置で二分探索を使用して、制約が満たされたまま可能な限り遠くまで拡張します。 新しい最大値に遭遇するたびに、しきい値が増加し、続行します。 各ジャンプは多くの中間位置をスキップし、遷移ごとの複雑さを対数的に軽減します。

重要な構造上の考え方は、プロセスは新たな最大値に達した場合にのみ「状態を変更」でき、それらのイベントは十分にまばらであるため、イベント間を効率的にジャンプできるということです。

 ## アルゴリズムのチュートリアル

 二重化された配列で作業します`b`長さの`2n`、 どこ`b[i] = a[i]`そして`b[i+n] = a[i]`。 これにより、周期的な動きを線形セグメントとして扱うことができます。 

1. 範囲最大構造を構築する`b`なので、任意の間隔で最大値を効率的にクエリできます。 これが必要なのは、決定がセグメント内でこれまでに確認された最大値に依存しており、それを迅速に再計算する必要があるためです。 
2. 各開始位置について`i`元の配列で初期化します`pos = i`、`end_limit = i + n - 1`、`cur_max = 0`、 そして`answer = 0`。 
3. その間`pos <= end_limit`、最も遠い位置を計算します`r`すべての値が`[pos, r]`少なくとも`cur_max / 2`更新を考慮した後。 スキャンする代わりに、二分探索を行います。`r`範囲の最小/最大クエリを使用して実現可能性を確認します。 

実現可能性チェックにより、`[pos, r]`、現在の最大値と比較して条件に違反する要素はありません。 有効なセグメントは違反要素に遭遇する前に最大値でなければならないため、可能な限り拡張します。 
4.移動`pos`に`r + 1`、更新します`answer += (r - pos + 1)`それに応じて。 
5. セグメントを消費した後、更新します`cur_max`そのセグメントの最大値。 これは、歩行距離を延長した場合にのみランニング最大値が増加するという事実を反映しています。 
6. いずれかの時点で進歩が見られない場合、または 2 倍の境界を超えた場合は、停止します。 違反が発生することなく少なくとも 1 つの完全なサイクルを完了した場合、プロセスは無期限に継続するため、-1 を返します。 

正確さは、しきい値が安定した状態でウォークを最大有効セグメントに分解できるかどうかにかかっています。 各セグメントは、値が現在の最大値の下で条件に違反する時点で終了し、その時点で次のセグメントが潜在的により大きな最大値で始まります。 

### なぜ効果があるのか

 不変条件は、各セグメントの開始時に、`cur_max`これまでに確認されたすべての値の最大値に等しく、現在のセグメント内のすべての要素がこの最大値に対する条件を満たします。 閾値は に関して単調であるため、`cur_max`、違反は要素が現在の最大値の半分を下回る最も早い位置で発生する必要があります。 常に最大の有効な拡張子にジャンプすることで、潜在的な停止点をスキップしたり、有効なセグメントを途中で切断したりすることがなくなります。 これにより、シミュレーションが圧縮形式ではあるものの、元の段階的なプロセスと一致することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        n = len(arr)
        self.n = 1
        while self.n < n:
            self.n *= 2
        self.seg = [0] * (2 * self.n)
        for i in range(n):
            self.seg[self.n + i] = arr[i]
        for i in range(self.n - 1, 0, -1):
            self.seg[i] = max(self.seg[2 * i], self.seg[2 * i + 1])

    def query(self, l, r):
        if l > r:
            return 0
        l += self.n
        r += self.n
        res = 0
        while l <= r:
            if l % 2 == 1:
                res = max(res, self.seg[l])
                l += 1
            if r % 2 == 0:
                res = max(res, self.seg[r])
                r -= 1
            l //= 2
            r //= 2
        return res

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    b = a + a

    st = SegTree(b)

    ans = []

    for i in range(n):
        pos = i
        end = i + n - 1
        cur_max = 0
        cnt = 0

        while pos <= end:
            lo, hi = pos, end
            best = pos

            while lo <= hi:
                mid = (lo + hi) // 2
                mx = st.query(pos, mid)
                if mx >= cur_max / 2:
                    best = mid
                    lo = mid + 1
                else:
                    hi = mid - 1

            if best < pos:
                break

            seg_max = st.query(pos, best)
            cnt += best - pos + 1
            cur_max = max(cur_max, seg_max)
            pos = best + 1

        if pos > end:
            ans.append(-1)
        else:
            ans.append(cnt)

    print(*ans)

if __name__ == "__main__":
    solve()
```この実装では、すべての範囲最大クエリが対数になるように、2 倍の配列に対してセグメント ツリーを構築します。 次に、各開始インデックスはバイナリ検索を使用して貪欲なセグメンテーションを実行し、条件が破られる前に到達可能な最も遠いポイントを見つけます。 の`cur_max`変数は、トラバースに沿って変化する最大値を追跡します。 

微妙な点は、モジュラー演算の代わりに 2 倍の配列を使用していることです。 これにより、モジュロ演算の繰り返しが回避され、セグメント クエリがインデックスに対して純粋に線形になります。 もう 1 つの重要な点は、延長する前に停止条件が現在の最大値と比較してチェックされ、セグメント内に違反要素が決して含まれないようにすることです。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての値が等しい場合です。 どこからでも開始すると、最大値はすぐにその値に等しく、後続の要素は厳密に半分より小さいことはないため、走査は決して終了しません。 このアルゴリズムは、違反セグメントを決して見つけず、2 倍の間隔をすべて使い切って、-1 を返すことでこれを処理します。 

もう 1 つのエッジ ケースは、いくつかの小さな値の後に非常に大きな値が表示される場合です。 このような状況では、実行最大値が遅くジャンプするため、しきい値が一時的に厳しくなります。 セグメントベースのシミュレーションは、有効な各セグメントが完了した後にのみ最大値が更新されるため、これを正確に捕捉し、ジャンプ全体で安定したしきい値を誤って想定しないようにします。 

最後のエッジケースは、開始自体がグローバル最大値である場合です。 その場合、すぐに閾値が高くなり、最初の違反要素が 1 ～ 2 ステップ以内に現れる可能性があります。 セグメントにわたるバイナリ検索により、最初の無効な位置をオーバーシュートするのではなく正確に検出できます。
