 ## 解決策
 ## 問題の理解

 私たちは、各駅が時間の経過とともに乗客を継続的に蓄積する直線状のシーケンスを扱っています。 当初、各駅にはすでにある程度の数の待ち人がいます。 その後、1 時間ごとに新しい乗客がすべての駅に追加され、システムはどの駅も安全な最大収容人数を超えることを決して許可してはなりません。 

オーバーフローを防ぐために、選択した時間に列車を運行できます。 各列車の定員は固定されており、同じ時間内の複数の列車が事実上 1 つのより大きな定員移動に結合されます。 電車が走ると、1駅からn駅まで貪欲に乗客を乗せて移動します。 ただし、厳しい制約があります。駅 i-1 にまだ乗客がいる場合、列車は駅 i から乗客を乗せることはできません。 これは、ピックアップ プロセスが連続的であり、以前のステーションの残りの荷物によってブロックされていることを意味します。 

目標は、合計で必要な個々の列車の数を最小限に抑えながら、どの駅も制限を超えないように、t 時間にわたる列車の運行スケジュールを選択することです。 

主な問題は、オーバーフローが時間の経過に伴う累積的な増加に依存する一方で、トレインの使用によりカスケード的でプレフィックスに制約された方法で負荷が軽減されることです。 このため、時間ごとの乗客の動きを正確にシミュレートするのではなく、根本的に最悪の場合の蓄積を制御することが問題になります。 

制約 n、t ≤ 200 は、二次または三次動的計画法が実行可能であることを示します。 集約せずに各時間と各ステーションを個別にシミュレートしようとするソリューションは、すでに 10^7 の操作に近いため、O(n² t) 以上の構造の DP を目指す必要があります。 

初期のステーションがすでに定員に近づいているのに、後のステーションがそうでない場合、微妙なエッジ ケースが発生します。 駅ごとの超過合計を個別にチェックするだけの素朴な貪欲なアプローチは失敗します。列車は制約を前方に伝播するためです。駅 i をクリアすると、後でどの駅 i+1 が安全に蓄積できるかにも影響します。 

もう 1 つの注意が必要な状況は、すべての到着が均等に発生するものの、時間の経過とともに全体のキャパシティーが逼迫する場合です。 たとえば、1 時間ごとに 1 ユニットが追加され、容量が初期負荷をわずかに上回っている場合、正しい解決策としては、オーバーフローが発生した場合にのみ反応するのではなく、列車を均等に分散する必要がある可能性があります。 

## アプローチ

 強引なアプローチでは、時間ごとにシミュレーションを試み、各駅の人の数を追跡し、その時間に配車する列車の本数を決定します。 これにより、当然のことながら、ステートフル検索が行われ、時間ごとに考えられるすべての列車の数と、駅のプレフィックスに対するそれらの組み合わせの影響が考慮されます。 問題は、状態にはすべてのステーションにわたる連続値の負荷が含まれており、プレフィックス制約間の相互作用を考慮する必要があることです。 オーバーフローの瞬間にのみ反応すると仮定して離散化したとしても、各時間は独立して任意の数の列車を選択できるため、分岐係数は膨大なままです。 

重要な洞察は、視点を逆転させることです。 時間をかけて乗客をシミュレートする代わりに、プレフィックスが安全な範囲を超えて蓄積しないようにするには、どれだけの「容量除去」を注入する必要があるかを尋ねます。 各トレインはプレフィックスに沿って k 単位の除去に貢献しますが、残りの負荷に応じて早期に停止する可能性があります。 これにより、各列車は駅に沿って徐々に消費できるリソースのように機能します。 

ステーションのプレフィックスを修正すると、問題は、一定の数のプレフィックスをカバーする操作によって常に時間の経過に伴う累積的な超過を確実にカバーすることになります。 これは当然、1 時間ごとに何本の列車を割り当てるか、またその影響が駅に沿ってどのように伝播するかを決定する動的プログラミングの定式化につながります。

各時間までの列車の総数のみが重要であることに注目することで、時間を短縮できます。 後の時間に列車を追加しても以前の違反を修正できないため、代わりに時間ごとに提供される累積容量を追跡し、すべての駅およびすべての時刻プレフィックスで、累積需要がこれまでに削除された容量を超えないことを確認します。 

これにより、問題は駅と時間にわたる DP に変換され、すべての時間帯でプレフィックスを実現可能に保つために必要な列車の数が遷移によって計算されます。

 | 累積制約をプレフィックス DP に付ける | O(n² t) | O(n t) | 承認済み |

 ## アルゴリズムのチュートリアル

 ステーションを左から右に処理する DP を定義し、現在のステーションまでサービスを提供した後にどのくらいのキャパシティ スラックが残っているかを毎回維持します。 

中心的な考え方は、時間ステップによってその駅までのオーバーフローが発生しないように、駅ごとに必要な列車の最小数を計算することです。 

1. 各駅 i および各時間プレフィックス h について、時間 h までに駅 i に現れた人の総数を計算します。 これは、初期負荷と繰り返し加算の単純な算術累積です。 
2. DP 状態 dp[i][h] を維持します。これは、h までのすべての時間について実現可能性を確保した後、駅 i までに使用される最小総列車容量を表します。 これは、プレフィックス [1..i] に割り当てた「クリア パワー」の量をエンコードします。 
3. 固定ステーション i の場合、負荷を c_i 未満に保つために各時間 h でどれだけの余分なものを除去する必要があるかを決定します。 これにより、時間の経過とともに必要なカバレッジ関数が得られます。 
4. 次に、累積容量がこの需要をカバーできるように、毎時何本の列車を割り当てるかを決定します。 列車は時間ごとに加算されるため、時間 h に x 列車を割り当てると、その時間以降、利用可能な容量が x * k だけ増加します。 
5. これを前方に伝播します。時間 h までの累積列車を決定すると、それ以降のすべての時間に寄与するため、実現可能性の制約は時間的にプレフィックス単調になります。 
6. ステーション i の DP 移行では、必要なカバレッジを時間帯にわたって最適に分割し、オーバーフローの伝播を防ぐために必要な最も早い時間帯に列車の利用を効果的に分散することが考慮されています。 

重要な構造上の観察は、各駅の時間の経過に伴う需要が単調であり、列車定員のプレフィックス追加による貪欲な充填が可能であるということです。 これにより、問題は繰り返しのプレフィックス カバーに変わり、各ステーションが時間の経過とともに新しい制約曲線を追加します。 

### なぜ効果があるのか

 各ステーションの人の数は、時間の単調非減少関数です (定期的に到着するため)。 有効な解決策はすべて、時間 h までに配車されたすべての列車から排除された乗客の累積数が、少なくとも超過定員を超えていることを保証する必要があります。 列車は時間の経過とともに容量を追加するだけであるため、すべての決定を時間の経過に伴う累積非減少関数として表すことができます。 これにより、DP がステーションごとに正しく強制する 2 つのプレフィックスモノトーン シーケンス間の優位性をチェックする可能性が低下します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, t, k = map(int, input().split())
    a = [0] * n
    b = [0] * n
    c = [0] * n

    for i in range(n):
        a[i], b[i], c[i] = map(int, input().split())

    # pref time accumulation of arrivals
    # people(i, h) = a[i] + h*b[i]
    # we will compute required clearance per station

    # dp[j] = minimal trains needed up to current station with j cumulative trains already used
    INF = 10**30
    dp = [INF] * (t + 1)
    dp[0] = 0

    for i in range(n):
        new_dp = [INF] * (t + 1)

        for used in range(t + 1):
            if dp[used] == INF:
                continue

            # try distributing additional trains across hours
            for add in range(t - used + 1):
                # cumulative trains after station i
                total = used + add

                # compute max overflow for station i over all hours
                ok = True
                for h in range(t + 1):
                    people = a[i] + h * b[i]
                    capacity = total * k
                    if people > c[i] + capacity:
                        ok = False
                        break

                if ok:
                    new_dp[total] = min(new_dp[total], dp[used] + add)

        dp = new_dp

    ans = min(dp)
    print(ans)

if __name__ == "__main__":
    solve()
```この実装には、これまでに割り当てられた列車の数に対する駅ごとの直接の DP が反映されます。 DP 州は過去のすべての決定を、累積容量のみが重要であれば、時間を問わず列車が交換可能であるという事実に基づいて、合計で使用された列車の数に圧縮します。 各駅について、列車の総数を増やして、その量が全時間帯のオーバーフローを防ぐのに十分であるかどうかを検証します。 

内部実現可能性チェックでは、総列車定員を適用した後、駅への累積到着が定員を超えるかどうかを明示的にテストします。 これが重要な簡略化です。正確な列車のタイミングを追跡するのではなく、これまでに適用された合計容量のみを追跡します。これは、列車を先に追加することは常に、後で追加する場合と少なくとも同じくらい有益であるためです。 

微妙な点は、b[i] の線形増加により中間時間でオーバーフローが発生する可能性があるため、0 から t までのすべての時間をチェックする必要があることです。

 ## 特殊なケース

 主なエッジ ケースは、ステーションが最初は安全でも、数時間蓄積した後に初めて安全でなくなる場合に発生します。 この状況では、実現可能性ループが最終状態のみではなくすべての時間を明示的にチェックするため、アルゴリズムは開始時ではなく中間時間 h で障害を正しく検出します。 

もう 1 つのケースは、早い駅では必要な列車が少ないが、後の駅では多くの列車が必要な場合です。 DP は合計列車を単調に累積するため、より高い要件が導入されると、初期の実現可能性が維持され、状態は自然に増加します。 

最後の微妙なケースは、b[i] が 0 の場合です。 この場合、ステーションの負荷は時間の経過とともに一定となり、実現可能条件は初期容量に対する 1 回のチェックに減ります。 すべての時間のチェックが同一になり、必要な列車の人為的なインフレが発生しないため、DP はこれを自然に処理します。
