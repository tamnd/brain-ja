 ## 解決策
 ## 問題の理解

 1 から n までのインデックスが付けられた交差点の線として表される 1 次元の町が与えられています。 各位置には、タイプ A (バス互換セグメント マーカー) またはタイプ B (路面電車互換セグメント マーカー) のいずれか 1 つのタイプの交通ステーションがあります。 文字列 s はこのレイアウトをエンコードします。 

Petya は位置 1 から開始し、位置 n に到達したいと考えています。 移動は公共交通機関を利用する場合にのみ意味があります。任意の位置 i から、i から j−1 までのすべての位置が A の場合はバスを使用し、i から j-1 までのすべての位置が B の場合は路面電車を使用して j にジャンプできます。このようなジャンプには、交通機関の種類に応じて固定料金がかかります (バス区間の場合は a、路面電車区間の場合は b)。 

Petya は、お金を支払わずに最初からある位置 i まで歩くことができ、その後、終点に到達するために i からのトランスポート ジャンプのみを使用する必要があります。 目標は、i から n までの合計コストが p を超えないように、可能な限り最小の開始位置 i を選択することです。 

重要な構造は、移動コストが文字列内の連続した一様なセグメントにのみ依存するということです。 同一の文字の各最大ブロックは強制「モード」セグメントに対応し、そのような各ブロック内で、Petya は 1 枚のチケットを使用して自由に移動できます。 

この制約により、テスト ケース全体で合計 10^5 文字までが許可されるため、開始位置ごとにコストを最初から再計算するソリューションは除外されます。 各 i から移動コストを再計算する二次アプローチでは、最悪の場合、10^10 の演算に達しますが、これは実行不可能です。 テストケースごとに線形または線形に近い前処理が必要です。 

微妙なエッジ ケースは、Petya が文字列の終端近くの同種ブロック内で開始する場合です。 たとえば、s = "AAAAA" で、a が大きく、p が小さい場合、コストは正確な位置ではなくブロック間の遷移のみに依存するため、同じブロック内で開始が早くても遅くてもコスト構造は変わりません。 

もう 1 つの特殊なケースは、「ABABAB」のような文字列を交互に使用することです。 ここでは、すべてのステップが新しいセグメントであるため、コストは遷移の数に応じてほぼ直線的に増加するため、グループ化については貪欲な直感を注意深く適用する必要があります。 

## アプローチ

 強引なアイデアは、考えられるすべての開始位置を試してみることです。 各 i について、定数文字の新しいセグメントを入力するたびに前方にスキャンしてコストを合計することにより、i から n までの行程をシミュレートします。 各シミュレーションには O(n) 時間がかかり、すべての i に対してこれを実行すると、テスト ケースごとに O(n^2) が発生します。これは、n が 10^5 に達すると遅すぎます。 

重要な観察は、i から n までのコストは、i から始まる最大の連続ブロックのシーケンスのみに依存するということです。 文字列をブロックに圧縮する場合、たとえば「AABBBBAA」が長さの A、B、A になると、ブロック内の任意の i からのコストは、そのブロックから始まるこのブロック シーケンスのサフィックスのみに依存します。 

これは、右から左への動的プログラミング構造を示唆しています。 cost[i] を位置 i から n に移動するための最小コストとして定義すると、コストを逆の順序で計算できます。 位置 i にいるときは、同じ文字ブロック内に留まるか、現在の文字に応じて a または b を払って次のブロックに移行します。 s[i] == s[i+1] の場合、依然として同じセグメント内にあり、その境界では新しいチケットは必要ないため、cost[i] =cost[i+1] となります。 それ以外の場合は、チケット 1 枚とコスト [i+1] を支払います。 

すべてのcost[i]がわかったら、cost[i] ≤ pとなるような最小のiを見つけるだけです。 

この改善は、cost[i] がcost[i+1]とローカル文字の比較にのみ依存するため、サフィックスコストを繰り返し再計算するのは冗長であるという認識から来ています。

 | --- | --- | --- | --- |
 | 各 i | からのブルート フォース シミュレーション O(n^2) | お(1) | 遅すぎる |
 | サフィックスコストに対する逆DP | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

1. すでに目的地に到達している場合は移動する必要がないため、サイズ n+1 の配列コストを事前計算します (コスト [n] = 0)。 
2. 文字列を右から左に、i = n−1 から 1 までたどって、cost[i+1] からcost[i] を計算します。 これにより、cost[i] を計算するときに、サフィックス コストがすでにわかっていることが保証されます。 
3. s[i] が s[i+1] と同じ場合、cost[i] =cost[i+1] を設定します。 これは、同じトランスポート タイプのブロック内に留まることに相当し、このステップでは新しいチケットは必要ありません。 
4. s[i] が s[i+1] と異なる場合、A と B の間の境界を越えています。この場合、i から始まるセグメントのチケットのコストを支払わなければなりません。 s[i] == 'A' の場合、a を追加します。 それ以外の場合は b を追加します。 次に、コスト[i] = コスト[i+1] + その値を設定します。 これは、セグメント タイプが変更されるたびに新しいチケットが強制的に作成されるという事実を捉えています。 
5. すべてのコストを計算した後、i = 1 から n までスキャンし、cost[i] ≤ p となる最小のインデックス i を返します。 これは、Petya が最後まで移動できる最も早い時点を表します。 

### なぜ効果があるのか

 重要な不変条件は、cost[i] が、連続した均一文字の最適なセグメント化を使用して i から n に移動するのに必要な正確な最小コストを表すことです。 有効なパスはセグメント境界を尊重する必要があり、各境界交差は s[i] が s[i+1] と異なるかどうかによって一意に決定されるため、再帰化により、ジャーニーの考えられるすべての分解が最大の単色セグメントにキャプチャされます。 文字制約を変更せずに境界をスキップすることは不可能であるため、代替パスによってコストを削減することはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    a, b, p = map(int, input().split())
    s = input().strip()
    n = len(s)

    cost = [0] * n
    cost[-1] = 0

    for i in range(n - 2, -1, -1):
        if s[i] == s[i + 1]:
            cost[i] = cost[i + 1]
        else:
            cost[i] = cost[i + 1] + (a if s[i] == 'A' else b)

    ans = 0
    for i in range(n):
        if cost[i] <= p:
            ans = i + 1
            break

    print(ans)
```この実装は DP の繰り返しを直接反映しています。 コスト配列のインデックスは 0 ですが、問題のインデックスは 1 であるため、最終的な答えはインデックスを変換するときに 1 を追加します。 逆走査により、計算されていない状態にアクセスすることがなくなります。 

よくある間違いは、最初にセグメントを圧縮してからジャンプをシミュレートしようとすることです。 有効ではありますが、境界条件は不必要であり、間違いが起こりやすいのです。 この DP は、明示的なセグメント構築を完全に回避します。 

## 実用的な例

 ### 例 1

 入力:

 s = "ABAB"、a = 2、b = 1

 コストを右から左に計算します。 

| 私 | s[i] | s[i+1] | コスト[i+1] | 遷移 | コスト[i] |
 | --- | --- | --- | --- | --- | --- |
 | 3 | B | - | 0 | ベース | 0 |
 | 2 | あ | B | 0 | +a | 2 |
 | 1 | B | あ | 2 | +b | 3 |
 | 0 | あ | B | 3 | +a | 5 |

 p = 3 の場合、有効な開始位置はコスト ≤ 3 の位置、つまり i = 2 および i = 3 (1 から始まるインデックス: 3 および 4) です。 最小のものは 3 です。 

このトレースは、変更ごとに新しい支払いがどのように強制されるか、およびサフィックスの再利用がどのように正しく蓄積されるかを示します。 

### 例 2

 入力:

 s = "AABBB"、a = 3、b = 2

 | 私 | s[i] | s[i+1] | コスト[i+1] | 遷移 | コスト[i] |
 | --- | --- | --- | --- | --- | --- |
 | 4 | B | - | 0 | ベース | 0 |
 | 3 | B | B | 0 | 同じ | 0 |
 | 2 | B | B | 0 | 同じ | 0 |
 | 1 | あ | B | 0 | +a | 3 |
 | 0 | あ | あ | 3 | 同じ | 3 |

 p = 3 の場合、Petya は i = 1 (1 からインデックス付けされた 2) 以降で開始できます。 有効なインデックスの最小値は 2 です。 

これにより、長く均一なブロックは内部コストを蓄積せず、境界遷移のみが問題となることが確認されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        a, b, p = map(int, input().split())
        s = input().strip()
        n = len(s)

        cost = [0] * n
        cost[-1] = 0

        for i in range(n - 2, -1, -1):
            if s[i] == s[i + 1]:
                cost[i] = cost[i + 1]
            else:
                cost[i] = cost[i + 1] + (a if s[i] == 'A' else b)

        ans = 0
        for i in range(n):
            if cost[i] <= p:
                ans = i + 1
                break

        out.append(str(ans))

    return "\n".join(out)

""") == """2

""") == "1"

# alternating tight budget

 ## 特殊なケース

 「AAAAA」のような完全に同一の文字で構成される文字列の場合、遷移が発生しないため、すべてのコスト[i]はゼロになります。 このアルゴリズムは、cost[n−1] = 0 を設定し、等価性を逆方向に伝播し、すべての i に対してcost[i] = 0 を生成するため、インデックス 1 は常に正しく返されます。 

「ABABAB」のような完全に交互の文字列の場合、各ステップで新しいセグメント境界が導入されます。 DP はインデックスごとに a または b を追加するため、cost[i] は最後までの距離に応じて線形に増加します。 このアルゴリズムは、明示的なセグメンテーションを必要とせずに、予算内で最も早いサフィックスを正確に識別します。 

a または b が p よりもはるかに大きい場合、末尾に近い位置のみが有効です。 DP は、初期の不一致がすぐにコストを蓄積し、局所的な貪欲さによる不正確な実現可能性を防ぐため、これを依然として正確に捉えています。
