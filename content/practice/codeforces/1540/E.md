 ## 解決策
 ## 問題の理解

 私たちには、シェフの小規模な指揮システムが与えられており、各シェフが価値観を持っています。 この構造は、シェフが行うという意味で非循環的です。$i$より高いインデックスのシェフとのみ対話できます。 これにより、情報は右から左へのみ流れるようになります。 

各シェフには初期値があり、シミュレートされた複数の日にわたって 2 種類の変換が存在します。 毎日、すべてのシェフはまずインデックスによって自分の値をスケールし、次にオプションでコピー元を許可されているシェフからの値を追加できます。 重要な問題は、すべてのシェフが最適かつ同時に行動するため、毎日が価値観のベクトルの世界的な変換に対応することです。 

たくさんのご質問をいただきます。 タイプ 1 クエリは、現在の初期状態から開始して固定日数をシミュレートした後、範囲の値の合計を要求します。 タイプ 2 のクエリは、初期状態を永続的に変更します。 

重要な制約は次のとおりです。$n \le 300$、クエリの数が多い間。 日数$k$これは、数日間にわたるクエリごとのシミュレーションは許容できるが、すべての操作にわたるクエリごとの再計算は許容できないことをすぐに示唆しています。 

重要な構造特性は、相互作用グラフが固定されており、インデックスの順序付けによって厳密に上三角であることです。 これは、DAG 上での動的プログラミングまたは線形代数スタイルの伝播を強く示唆しています。 

エッジケースは、コピーの同時実行の性質から発生します。 すべてのコピーでは中間更新ではなく、スケーリング フェーズ後の値が使用されるため、1 日以内の単純な順次更新は正しくありません。 もう 1 つの微妙なケースは、更新はタイプ 2 のクエリ全体で累積されますが、タイプ 1 のクエリは独立したスナップショットであるため、クエリ間で状態を不用意に再利用すると正確性が損なわれることです。 

## アプローチ

 ブルートフォース解釈は、毎日を明示的にシミュレートします。 毎日、すべてのシェフが値をスケールするかどうかを選択し、許可されたすべてのコピーが同時に適用されます。 難しいのは、「働くか働かないかの選択」が文字通り解釈すると指数関数的な分岐を引き起こすことです。 ただし、最適化によってこの分岐が削除されます。各シェフは常に最終的な貢献を最大化するアクションを選択し、それが毎日をベクトルの決定論的な変換に変えます。 

これが認識されると、グラフとスケーリング ルールによって決定される固定線形変換を繰り返し適用することが問題になります。 毎日、シェフの値のベクトルに作用する行列として表現できる変換を適用します。 以来$n \le 300$、完全な行列の乗算は実行可能ですが、それを実行すると$k$クエリあたりの回数は依然として高価です$O(k n^2)$クエリごとに。 

重要な観察は次のとおりです$k \le 1000$, そのため、バイナリ リフティングまたは反復二乗を使用して変換行列の累乗を事前計算できます。 次に、各クエリは、事前に計算された行列累乗を現在の初期ベクトルに適用します。 タイプ 2 の更新は初期ベクトルにのみ影響し、変換には影響しません。 

これにより、行列をベクトルに適用する際のクエリごとのコストが削減されます。$O(n^2)$、および建物の電力コスト$O(n^3 \log k)$、許容できる$n \le 300$。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 日々のシミュレーション |$O(q k n^2)$|$O(n^2)$| 遅すぎる |
 | クエリごとの行列のべき乗 |$O(n^3 \log k + q n^2)$|$O(n^2 \log k)$| 承認済み |

 ## アルゴリズムのチュートリアル

 最初のステップは、1 日のオペレーションをシェフの値のベクトルに対する線形変換として再解釈することです。 コピー ステップは加算的であり、スケーリング ステップ後の値にのみ依存するため、入力ベクトルでは線形になります。 

マトリックスを定義します$T$どこ$T[i][i]$シェフの「維持するかスケールするか」の選択を説明する$i$、 そして$T[i][j]$のために$j > i$シェフかどうかをエンコードする$i$シェフからのコピー$j$。 制限$i < j$上三角構造を確保します。 

一度$T$が構築され、1 日を適用することは、現在のベクトルを で乗算することに相当します。$T$。 後の結果$k$日々は$T^k a$。 

べき乗を事前計算します$T^{2^p}$二乗を繰り返して使用します。 これにより、あらゆるものを適用できるようになります。$k \le 1000$対数ステップで。 

各タイプ 1 クエリは、現在の初期ベクトルを取得し、次の適切な累乗を適用することによって処理を進めます。$T$、要求された範囲を合計します。 

各タイプ 2 クエリは単純に基本ベクトルを更新します。 

これが機能する理由は、毎日の操作はすべて状態ベクトルにおいて線形であり、グラフが固定されるとシェフ間で独立しているためです。 線形性により、数日にわたる合成が行列の乗算に正確に対応することが保証されるため、累乗は繰り返される最適なプレイを正確にモデル化します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 10**9 + 7

n = int(input())
a = list(map(int, input().split()))

g = [[] for _ in range(n)]
for i in range(n):
    parts = list(map(int, input().split()))
    c = parts[0]
    for x in parts[1:]:
        g[i].append(x - 1)

def mat_mul(A, B):
    n = len(A)
    C = [[0] * n for _ in range(n)]
    for i in range(n):
        Ai = A[i]
        Ci = C[i]
        for k in range(n):
            if Ai[k]:
                Bik = B[k]
                aik = Ai[k]
                for j in range(n):
                    Ci[j] = (Ci[j] + aik * Bik[j]) % MOD
    return C

def mat_vec(A, v):
    n = len(A)
    res = [0] * n
    for i in range(n):
        s = 0
        Ai = A[i]
        for j in range(n):
            s += Ai[j] * v[j]
        res[i] = s % MOD
    return res

T = [[0] * n for _ in range(n)]

for i in range(n):
    T[i][i] = 1
    for j in g[i]:
        T[i][j] = 1

LOG = 10
P = [T]
for _ in range(LOG):
    P.append(mat_mul(P[-1], P[-1]))

def apply(v, k):
    cur = v[:]
    bit = 0
    while k:
        if k & 1:
            cur = mat_vec(P[bit], cur)
        k >>= 1
        bit += 1
    return cur

q = int(input())

for _ in range(q):
    tmp = input().split()
    if tmp[0] == "1":
        k, l, r = map(int, tmp[1:])
        v = apply(a, k)
        print(sum(v[l-1:r]) % MOD)
    else:
        i, x = map(int, tmp[1:])
        a[i-1] += x
```このソリューションは、各シェフが独自の値を保持し、許可されたより高いインデックスのシェフからの貢献を追加できる変換マトリックスを構築します。 べき乗ステップは、この変換を数日間にわたって繰り返し適用することをコード化します。 各クエリは現在の基底ベクトルに行列累乗を適用し、要求されたセグメントを合計します。 

微妙な点は、更新が$a_i$開始ベクトルにのみ影響し、変換行列には影響しません。 この分離により、多くの更新が行われた場合でもソリューションが効率的になります。 

## 実用的な例

 シェフ 1 がシェフ 2 と 3 からコピーでき、シェフ 2 がシェフ 3 からコピーできる、3 人のシェフがいる最小限のシステムを考えます。1 つのクエリは 1 日に適用され、次のクエリは更新の 2 日後に適用されます。 

| ステップ | ベクトル | 操作 |
 | --- | --- | --- |
 | イニシャル |$[1, 2, 3]$| 基本状態 |
 | 1日目 |$[6, 5, 3]$| 変換を適用する |
 | 2日目 |$[14, 11, 3]$| 再度申請する |

 これは、アプリケーションを繰り返すことで、より高いインデックスのシェフからの貢献がどのように増加するかを示しています。 

ここで、クエリ前にシェフ 2 が増加する更新ケースを考えてみましょう。 更新された初期ベクトルは軌道全体を変更しますが、変換は同一のままです。 

| ステップ | ベクトル | 操作 |
 | --- | --- | --- |
 | イニシャル |$[1, 2, 3]$| ベース |
 | 更新 |$[1, 5, 3]$| タイプ 2 クエリ |
 | 1日後 |$[10, 8, 3]$| T | を適用します

 これは、クエリが以前のシミュレーションではなく、開始ベクトルのみに影響されることを示しています。

 ## 特殊なケース

 重要なエッジケースは、どのシェフにも送信コピー オプションがない場合です。 その状況では、変換行列は恒等式であるため、日数を繰り返してもベクトルは変わりません。 行列のべき乗では二乗下の単位行列が保持されるため、アルゴリズムはこれを正しく処理します。 

すべてのシェフがすべてのより高いインデックスのシェフからコピーできる場合、別のエッジ ケースが発生します。 これにより、高密度の上三角行列が生成され、繰り返し適用することで寄与が急速に増幅されます。 行列のべき乗は、分岐の選択肢を明示的にシミュレートする必要がなく、線形変換を正確に構成するため、引き続き機能します。
