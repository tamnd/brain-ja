 ## 解決策
 ## 問題の理解

 試合中のキルイベントの時系列ログが与えられます。 各イベントでは、あるプレイヤーが別のプレイヤーを排除することが示されています。 犠牲者はすぐにリスポーンし、再び殺害される可能性がありますが、時間の経過とともに誰が誰を殺害したかの順序のみを考慮します。 

このタスクは、試合中のある時点で「ペンタ キル」を達成したプレーヤーが少なくとも 1 人存在するかどうかを判断することです。 これは、同じプレイヤーが 5 回連続でキルを行った場合、犠牲者は全員異なることを意味します。 キルはそのプレイヤーのアクションの間で時間的に連続している必要があり、すべてのプレイヤーが参加する連続したグローバル イベントである必要はありません。 

出力は、そのようなシーケンスがどのプレイヤーにも存在するかどうかという 1 つの判定です。 

制約は小さく、合計 Kill イベント数は最大 1000 です。 これは、二次時間までのあらゆる解法が安全であることを直ちに示唆しますが、問題の構造により、イベントごとに一定の作業を行う直接線形スキャンが可能になります。 

微妙な点は「並んで」の解釈です。 素朴な解釈では、イベントのグローバルな隣接性が考慮されるかもしれませんが、それは異なる殺人者を誤って混合することになります。 正しい解釈はプレイヤーごとです。私たちは、単一のプレイヤーによって実行されたキルのシーケンスのみを時系列で見ます。 

2 番目の特殊なケースは、被害者が繰り返されることです。 プレイヤーは 5 回連続でキルしても、犠牲者を繰り返す可能性があり、ペンタキルは無効になります。 たとえば、A が X を殺す、A が X を殺す、A が Y を殺す、A が Z を殺す、A が W を殺すといったシーケンスは、5 回の連続キルのうち X が 2 回出現するため失敗します。 

もう 1 つのエッジ ケースは、ペンタ キルがどこででも発生する可能性があり、必ずしも最初のキルから始まり、最後のキルで終わる必要はないということです。 

## アプローチ

 ブルートフォース手法では、各プレイヤーがすべてのキルを順番に収集し、サイズ 5 のすべてのウィンドウをチェックして、5 人の犠牲者が別個であるかどうかを確認します。 プレイヤーのキル数が k の場合、プレイヤーあたりのコストは O(k * 5) となり、キル数は実質的に線形になります。 各イベントは一定の回数処理されるため、すべてのプレーヤーにわたって、これは合計で O(n) のままです。 

より単純なグローバルなアプローチでは、完全なイベント リスト内の長さ 5 のすべての連続セグメントをチェックし、すべてのキルが同じプレイヤーによるものであり、個別の犠牲者がいるかどうかを確認しようとします。 「in a row」条件はグローバルな隣接関係を参照しておらず、正しく一般化することも難しいため、これは概念的には失敗します。 

重要な観察は、プレイヤーごとに最後の 5 キル以上を保存する必要がないということです。 プレイヤーが少なくとも 5 回のキルを達成すると、その時点で終了する有効なペンタ キルの検出には最新の 5 回のみが問題となります。 これにより、問題はプレーヤーごとのスライディング ウィンドウの維持と小さな固定サイズの条件のチェックに変換されます。 

n は最大でも 1000 であるため、プレイヤー名から最近の犠牲者のリスト (または両端キュー) までの辞書を安全に維持できます。 新しい kill はそれぞれ、その構造を O(1) 時間で更新し、最大 5 つの値をチェックします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | プレーヤーごとのブルート フォース Windows | O(n) | O(n) | 承認済み |
 | プレーヤーごとのスライディング ウィンドウ | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは各プレイヤーについて、これまでに殺害した犠牲者の順序を維持しますが、それ以前のものは後で終了する新しい有効なペンタキルに寄与できないため、最後の 5 つのエントリのみを維持します。

1. キル イベントを時系列に 1 つずつ読みます。 それぞれの出来事で殺人者と犠牲者が発生します。 「連続」は時間に依存するため、この順序は非常に重要です。 
2. 各イベントについて、最近殺害した殺人者の個人リストに被害者を追加します。 リストが 5 つの要素を超える場合は、最も古い要素を削除します。 これにより、履歴の中で最も関連性の高いサフィックスのみを追跡することが保証されます。 
3. リストを更新した後、殺人者が少なくとも 5 人の殺害を記録している場合は、最後の 5 人の犠牲者がすべて異なるかどうかを確認します。 これが、このイベントでペンタキル終了を確認するために必要な唯一の条件です。 
4. いずれかのプレイヤーが最後の 5 回のキルの区別条件を満たした場合、答えは肯定的であるとすぐに結論付け、それ以降のイベントの処理を停止できます。 
5. そのようなプレイヤーが見つからずにすべてのイベントの処理が終了した場合、答えは否定になります。 

最後の 5 つのエントリのみをチェックする理由は、有効なペンタ キルはそのプレイヤーの現在のイベントで終了する必要があり、それより前の候補ウィンドウは終了時にすでにチェックされているためです。 

### なぜ効果があるのか

 どのプレイヤーにとっても、可能なすべてのペンタ キルは、時系列順に自分の 5 つのキルの連続ブロックに対応します。 サイズ 5 のローリング ウィンドウを維持することで、そのようなすべてのブロックがプレイヤー履歴のサフィックスとなる瞬間に 1 回だけ検査されるようになります。 今後のウィンドウに必要な情報を決して破棄せず、常に最新の 5 つのイベントを保持するため、有効なシーケンスをスキップすることはできません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    recent = {}  # player -> list of last kills
    
    for _ in range(n):
        a, b = input().split()
        
        if a not in recent:
            recent[a] = []
        
        recent[a].append(b)
        
        if len(recent[a]) > 5:
            recent[a].pop(0)
        
        if len(recent[a]) == 5:
            if len(set(recent[a])) == 5:
                print("PENTA KILL!")
                return
    
    print("SAD:(")

if __name__ == "__main__":
    solve()
```中心的な構造は、プレイヤー名をキーとする辞書で、最後の数人の犠牲者のみを保存します。 これにより、完全な履歴を保存する必要がなくなります。 

唯一の微妙な実装の詳細は、スライディング ウィンドウのトリミング ステップです。 リストが 5 つの要素を超える場合は常に先頭から削除され、一定のサイズが確保されます。 最大サイズが固定されており小さいため、リストを使用すれば十分です。そのため、償却演算は O(1) で十分です。 

また、一意性を確認するためにセットの構築にも依存します。 ウィンドウ サイズは最大 5 であるため、このチェックは一定時間になります。

## 特殊なケース

 エッジ ケースの 1 つは、ログの最後でペンタ キルが発生する場合です。 ウィンドウの更新後にすべてのイベントがチェックをトリガーするため、アルゴリズムは依然としてそれを検出します。 たとえば、プレーヤーの最後の 5 つのイベントがすべて異なる場合、最後の反復で即座にそれを捕捉し、成功を出力します。 

もう 1 つのケースは、プレイヤーが 5 キルを超えていて、有効なペンタ キルが履歴の後半で発生する場合です。 常に最後の 5 つのキルのみを保持するため、古いシーケンスは自動的に破棄されますが、有効なシーケンスは終了時点で最後の 5 つ以内に終了する必要があるため、これは安全です。 スライディング ウィンドウにより、以前の履歴は必要なくなります。 

最後の微妙なケースは、複数のプレイヤーがペンタキルを達成する可能性があることです。 アルゴリズムは最初の検出で停止します。これは正しいことです。出力には、ID やカウントではなく、存在のみが必要であるためです。
