 ## 解決策
 ## 問題の理解

 私たちには、価値をすぐに受け入れるべきか、それとももう一度「成長」させるべきかについての決定に至る、単純なインタラクティブなストーリーが与えられています。 

開始金額$x$初めての人に提供されます。 チェーン内の各人は、現在の金額を受け入れてプロセスを終了するか、拒否して次の人に強制的に金額を 2 倍にすることができます。 ただし、グローバルな制約があります。ホストには、$d$ドルが利用可能です。 現在の金額を2倍にすると超える場合$d$、ホストはそれが起こることを許可されておらず、現在の人に直ちにお金を受け入れるように強制する必要があります。 

課題は、最初に金額を決定することです$x$、すべての人が許可されるときはいつでも2倍にすることを好むと仮定して、その人が「それを取る」または「2倍にする」と言うかどうか。 

制約から得られる重要な観察点は、両方とも$x$そして$d$までです$10^9$。 これは十分に小さいため、各ステップで値が指数関数的に増加するため、繰り返し 2 倍化を多くのステップにわたって継続することはできません。 実際、最大 30 回の 2 倍化の後、値はすでに 32 ビット整数の制限を超えており、約 30 ～ 31 ステップ後には値が 32 ビット整数の制限を超えています。$10^9$。 

ステップ数は対数であるため、停止条件に達するまで繰り返し 2 倍になる単純なシミュレーションは、ここでも安全です。$d$。 しかし、実際の問題はさらに単純です。現在の状態でもう 1 回の 2 倍化が許可されるかどうかを決定するだけで済みます。 

主なエッジケースは、決定が将来のステップに依存するのか、それとも当面の次のアクションに依存するのかを誤解していることです。 もう 1 つの潜在的な間違いは、問題がチェーン内の最初の決定のみを求めているのに、不必要に複数の人物をシミュレートすることです。 

たとえば、次の場合$x = 123$そして$d = 246$、2 倍にするとちょうど 246 となり、これは有効なので、答えは「2 倍にする」になります。 もし$x = 345$そして$d = 678$、2倍にすると690となり制限を超えてしまうので、すぐにお金を取らなければなりません。 

プロセス全体は、単一の不等式をチェックすることに集約されます。 

## アプローチ

 強引な解釈は文字通り物語に沿っています。 価値から始めます$x$、順番に人物のシミュレーションを繰り返します。 各ステップで、現在の値を 2 倍にすると次の値を超えるかどうかを確認します。$d$。 そうであれば、私たちは停止し、強制的に受け入れます。 それ以外の場合は、2 倍にして続行します。 誰かがお金を受け取るまで繰り返します。 

これが機能するのは、このプロセスが決定論的であるためです。強制されない限り、誰もが常に 2 倍にすることを選択します。 ただし、反復回数は、超過するまでに 2 倍にできる回数に比例します。$d$、最大でも$O(\log d)$。 これはすでに小さいですが、問題が最初の決定のみを要求していることを考えると、それでも不必要な作業です。 

重要な洞察は、将来のすべての参加者の行動は現在の決定とは無関係であるということです。 唯一の問題は、現在の金額を一度だけ法的に2倍にすることができるかどうかです。 もし$2x > d$, そうすると、すぐに倍増は不可能なので、答えは強制承認です。 もし$2x \le d$、その後、倍増が許可され、その人は常にそれを選択します。 

これにより、プロセス全体が一定時間の比較に短縮されます。

 | 全プロセスのシミュレーション |$O(\log d)$|$O(1)$| 承認済み |
 | 直接チェック$2x \le d$|$O(1)$|$O(1)$| 承認済み |

 ## アルゴリズムのチュートリアル

 最初の人が送金を許可されるかどうかを判断するだけで済みます。 

1. 値を読み取る$x$そして$d$。 これらは現在のオファーと最大許容予算を表します。 
2. コンピューティング$2x$。 これは、その人がダブルを選択した場合に次のオファーがどのようになるかを表します。 
3. 比較する$2x$と$d$。 もし$2x$厳密には次より大きいです$d$、その場合、倍増は許可されないため、その人はすぐに同意する必要があります。 
4. それ以外の場合、$2x \le d$、その人は自分の好みに従い、二重にすることを選択します。 

決定はこの 1 つのステップで完全に決定されるため、それ以上のシミュレーションは必要ありません。 

### なぜ効果があるのか

 プロセスのどの時点でも、動作を制限する唯一の制約は、倍増が予算に違反するかどうかです。 参加者には強制されない限り早めに参加する理由はないため、唯一の阻止条件は次のとおりです。$2 \cdot \text{current} > d$。 初期状態についてのみ質問されるため、システム全体は最初の 2 倍化が有効かどうかをチェックすることになります。 将来のチェーンは、このローカルな実現可能性条件に影響を与えません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

x, d = map(int, input().split())

if 2 * x > d:
    print("take it")
else:
    print("double it")
```ソリューションは 2 つの整数を読み取り、1 回の算術比較を実行します。 唯一の微妙な点は、比較の前に乗算が確実に行われるようにすることですが、Python では任意精度の整数を使用できるため、これは安全です。 

決定ロジックはアルゴリズムを直接反映しています。つまり、2 倍化後の次の状態が制約の下で有効かどうかをテストします。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    x, d = map(int, sys.stdin.readline().split())
    return "double it" if 2 * x <= d else "take it"

# provided samples
assert run("123 246\n") == "double it"
assert run("345 678\n") == "take it"

# custom cases
assert run("1 1\n") == "take it", "doubling exceeds even smallest bound"
assert run("1 2\n") == "double it", "exact boundary case"
assert run("500000000 1000000000\n") == "double it", "max boundary valid"
assert run("500000001 1000000000\n") == "take it", "just over half boundary"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 1 | 取ってください | 2 倍化が失敗する最小エッジ |
 | 1 2 | 倍にする | 最小の有効な 2 倍の場合 |
 | 500000000 1000000000 | 倍にする | 等価性が成り立つ大きな境界 |
 | 500000001 1000000000 | 取ってください | d の半分あたりから 1 ずつオフ |

 ## 特殊なケース

 主なエッジケースは次のような場合です$2x = d$。 入力用`123 246`、アルゴリズムは次のように計算します。$2x = 246$を超えない$d$なので、「double it」が正しく出力されます。 これは、平等が強制的な受け入れを引き起こすものではないことを裏付けています。 

もう 1 つのエッジケースは次のような場合です$x = d$。 入力用`100 100`、計算します$2x = 200$を超える$d$したがって、出力は「take it」になります。 これは、最初のオファーが十分に手頃な価格であっても、2 倍化がすでに無効である可能性があることを示しています。 

3 番目のケースは次の場合です。$x$の半分以下です$d$、 のような`499999999 1000000000`。 2 倍化はまだ有効であるため、プロセスは続行されます。 でも増えたら$x$1つ増えると、決定はすぐに変わります。 これは、この解法が完全に境界駆動型であり、単一の不等式のみに敏感であることを強調しています。$2x \le d$。
