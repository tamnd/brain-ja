 ## 解決策
 ## 問題の理解

 各テスト ケースに文字列が与えられ、それが回文からどれだけ離れているかを測定したいとします。ここで、「距離」は、挿入、削除、置換が許可される標準の編集距離です。 

文字列を別の任意の文字列に変換する代わりに、ターゲットは任意の回文に制限されます。 したがって、各入力単語について、前後から同じように読める文字列に変換するために必要な最小限の編集回数を探します。 対象となる回文は事前に固定されておらず、可能な限り最適なものを選択することができます。 

重要な問題は、最も近い回文が局所的にさえ明らかではない可能性があることです。 将来のコストを削減するために、代わりに文字を削除または挿入し、配置を変更することができるため、端の不一致によって置換が強制されることはありません。 このため、貪欲な推論は信頼できなくなります。 

入力制約の全長は小さく、すべての文字列の長さの合計は最大 3000 です。これは、テスト ケースごとに O(n²) 個の動的プログラミング ソリューションが受け入れられることをすぐに示唆していますが、文字列のペアにわたる三次または大きな状態空間を含むものは、依然として合格しますが、不要です。 

単純なアプローチでは、文字列をすべての回文と暗黙的に比較しようとします。 同じ長さの回文に制限しても、位置ごとに 26 の選択肢がすでに得られており、長さを変更する編集操作と組み合わせると指数関数的になります。 これは、中程度の文字列であってもすぐに実行不可能になります。 

エッジケースはほとんどが構造的なものです。 

「x」のような 1 文字の文字列はすでに回文になっているはずなので、答えは 0 です。 「bababac」など、1 文字を除いてほぼ対称な文字列は、多くの場合、一端を 1 回置換するだけで修正できますが、不注意なアルゴリズムにより、削除を考慮せずに対称位置を厳密に一致させると、編集数が過剰にカウントされる可能性があります。 

もう 1 つの微妙なケースは、最適な位置合わせを行うために、不一致を直接置換するのではなく文字を削除する必要がある場合です (たとえば、「abcda」)。 両端の直接置換が常に最適であるとは限りません。 中間構造を削除すると、編集の回数が減ります。 

## アプローチ

 ブルートフォースの観点は、すべての回文を生成し、入力文字列から各候補までの編集距離を計算し、最小値を取ることを想像することです。 最大でも入力長の 2 倍の長さの回文に制限したとしても、回文の数は長さに応じて指数関数的に増加します。 各比較自体のコストは標準の編集距離を介して O(n²) であるため、このアプローチは実行可能な制限をはるかに超えています。 

より構造化されたビューは、回文がその左半分によって完全に決定されることを観察することで得られます。 ただし、可能な半分すべてを最適化しようとしても、依然として膨大な検索スペースに直面します。 

重要な点は、ターゲット文字列について明示的に考えるのをやめるということです。 代わりに、動的プログラミング中に元の文字列の間隔で回文制約を直接適用します。 もっと単純な質問をします。部分文字列 w[l..r] を回文に変えるのに必要な編集の最小回数はどれくらいですか? これにより、ターゲットを完全に列挙する必要がなくなりました。 

このように問題を組み立てると、その構造は局所的なものになります。 任意の間隔 [l, r] で、文字がすでに一致している場合は、内側の間隔を解決するだけで済みます。 一致しない場合は、置換によって修正するか、片側を削除して内部のより適切な位置合わせを可能にします。 

これにより、各不一致に 3 つの意味のある選択肢があり、置換、左からの削除、右からの削除をキャプチャする古典的な区間 DP が得られます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 回文に対する総当たり攻撃 | 指数 | O(n) | 遅すぎる |
 | インターバルDP | 文字列あたり O(n²) | O(n²) | 承認済み |

 ## アルゴリズムのチュートリアル

dp[l][r] を、部分文字列 w[l..r] を回文に変換するために必要な編集操作の最小数として定義します。 

1. すべての単一文字と空の間隔の dp をゼロとして初期化します。 長さ 0 または 1 の文字列はすでに回文であるため、編集する必要はありません。 
2. 長さ 2 から完全な文字列まで、長さの昇順に部分文字列を考慮します。 まず小さな間隔を処理すると、dp[l][r] を計算するたびに、すべての小さな部分問題がすでにわかっていることが保証されます。 
3. 各区間 [l, r] について、文字 w[l] と w[r] を比較します。 それらが等しい場合、それらを直接変更する必要はないため、コストは正確に dp[l+1][r-1] になります。 これは、両端をペアにして内部を独立して解くことに相当します。 
4. w[l] と w[r] が異なる場合、不一致を解決する 3 つの方法を検討します。 一方のエンドポイントをもう一方のエンドポイントに置き換えることができます。これには、1 に dp[l+1][r-1] を加えたコストがかかります。 コスト 1 に dp[l+1][r] を加えた左側の文字を削除して、間隔を効果的に右にシフトすることができます。 1 に dp[l][r-1] を加えたコストの右の文字を削除し、間隔を左にシフトします。 
5. これらのオプションの最小値を取得し、それを dp[l][r] に保存します。 これにより、最終的に対称性を強制するすべての有効な編集シーケンスがキャプチャされます。 
6. 各テスト ケースの答えは dp[0][n-1] です。 

これが機能する理由は、文字列に対する編集操作の最適なシーケンスはすべて、ある間隔で最も外側の未解決の不一致を徐々に解決すると解釈できるためです。 最適なソリューションでは、続行する前に現在の端を揃えるか、どちらかの端を削除する必要があります。 これにより、有効な位置合わせパスを見逃すことなく、構造的に異なる最適な変換をすべて再帰的に探索することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve_one(s: str) -> int:
    n = len(s)
    if n <= 1:
        return 0

    dp = [[0] * n for _ in range(n)]

    for length in range(2, n + 1):
        for l in range(n - length + 1):
            r = l + length - 1

            if s[l] == s[r]:
                dp[l][r] = dp[l + 1][r - 1]
            else:
                dp[l][r] = min(
                    dp[l + 1][r - 1] + 1,
                    dp[l + 1][r] + 1,
                    dp[l][r - 1] + 1
                )

    return dp[0][n - 1]

def main():
    t = int(input())
    out = []
    for _ in range(t):
        s = input().strip()
        out.append(str(solve_one(s)))
    print("\n".join(out))

if __name__ == "__main__":
    main()
```このソリューションでは、各エントリが部分文字列の間隔を表す 2 次元の DP テーブルを使用します。 入れ子になったループが長さを超えているため、すべての遷移は厳密に短い間隔のみを参照するため、必要なときにすべての依存関係がすでに計算されています。 

3 つのケースの最小値は、置換か削除の決定を直接エンコードします。 置換の場合は両端を同時に固定することに対応し、削除の場合は将来の一致が可能になるように位置合わせをシフトすることに対応します。 この構造により、編集距離の動作を回文制約に組み込むことができます。 

## 実用的な例

 ### 例 1: 「こんにちは」

 主要な状態に焦点を当てて、間隔にわたる dp を計算します。 

| 間隔 | s[l] vs s[r] | 使用されるトランジション | dp値 |
 | --- | --- | --- | --- |
 | [0,0] | h | ベース | 0 |
 | [1,1] | e | ベース | 0 |
 | [2,2] | l | ベース | 0 |
 | [3,3] | l | ベース | 0 |
 | [4,4] | o | ベース | 0 |
 | [0,4] | h vs o | 最小 3 つのオプション | 3 |

 間隔 [0,4] が重要です。 直接置換と内部解決では、不一致のエンドポイントを慎重に削除するよりもコストがかかり、DP は対称性を強制する前に文字の削除またはシフトと同等のシーケンスを正しく選択します。 

これは、最適なソリューションでは、即時の文字修正よりも構造編集を優先する可能性があることを裏付けています。 

### 例 2: 「バババック」

 | 間隔 | s[l] vs s[r] | 使用されるトランジション | dp値 |
 | --- | --- | --- | --- |
 | [0,6] | b 対 c | 選択肢の削除/置換 | 1 |

 不一致は外側の境界でのみ発生します。 最後の文字を削除または変更すると、完全な回文「バババブ」になるため、DP は 1 回の編集ですぐに収束します。 

これは、単一の境界修正が構造全体を解決するときをアルゴリズムが自然に認識していることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | テスト ケースあたり O(n²) | すべての間隔 [l, r] は、O(1) 回の遷移で 1 回計算されます。 
| スペース | O(n²) | DP テーブルにはすべての部分文字列の結果が格納されます。 

テスト ケースの合計の長さは最大 3000 であるため、DP 状態の総数は約 900 万になります。 各状態は定数時間で計算されるため、Python の時間制限内に無理なく収まります。

 ## 特殊なケース

 「x」のような 1 文字の文字列は、長さ 1 の間隔として DP に入力され、基本ルールが即時に適用され、不一致の可能性がないため編集は行われません。 アルゴリズムは長さ 1 の遷移を試行しないため、偶発的なオーバーカウントは発生しません。 

「ab」のような 2 文字の文字列は、不一致によって最小限の置換または削除が引き起こされる間隔 [0,1] を 1 つだけ作成します。 両方のパスのコストは正しく 1 であり、無効な中間間隔はアクセスされません。 

「abba」などのすでに回文になっている文字列は、再帰のすべてのレベルで常に s[l] == s[r] を満たすため、DP は基本ケースに到達するまで繰り返し内部区間に縮小し、全体でコストがゼロになります。
