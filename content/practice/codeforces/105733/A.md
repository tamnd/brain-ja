 ## 解決策
 ## 問題の理解

 GDSC と BKAC の 2 つのグループは、単一の文字列を左から右に 1 文字ずつスキャンしています。 各グループには固定のターゲット文字セットがあります。 GDSC は、文字 G、D、S、および C を収集しようとしています。BKAC は、B、K、A、および C を収集しようとしています。文字列に文字が出現するたびに、両方のグループは、それがターゲット セットに属しているかどうかを個別にチェックします。 存在する場合はコレクションに追加し、存在しない場合は無視します。 必要な文字をすべて少なくとも 1 回集めることができた最初のグループが勝ちです。 両方がスキャン内の同じ位置でコレクションを完了した場合、結果は引き分けになります。 

重要な点は、文字列内の文字の順序によってタイムラインが定義されるということです。 サブシーケンスを並べ替えたり選択したりするわけではありません。 私たちは、各ステップが一方または両方のチームに貢献する可能性がある一連のプロセスをシミュレートしています。 

制約は小さく、文字列の長さは最大 100、テスト ケースは最大 100 です。 これにより、テスト ケースごとに 1 回のリニア スキャンを超える高度なデータ構造や最適化の必要性が即座に排除されます。 O(n²) アプローチでも快適にパスしますが、単一パスよりも複雑なものは不要なオーバーヘッドです。 

共通のキャラクター C から微妙なエッジケースが発生します。両方のチームがそれを必要としています。 これにより、非明確な方法で進行状況を同期できるシナリオが作成されます。 たとえば、C が非常に早い段階で出現しても、残りの必須文字が分散している場合、1 つの主要な文字の進行状況を共有しているにもかかわらず、両チームが異なる時間で完了する可能性があります。 

もう 1 つの特殊なケースは、あるチームが要求する文字がずっと早くに表示されているにもかかわらず、最後の文字が 1 つ欠けていると完了が遅れる場合です。 たとえば、BKAC が最初の数位で B、K、A を集めたが、C が遅れて出現し、GDSC が着実に早く文字を蓄積した場合、勝者は出現頻度や多数派ではなく、最後に欠けていた要件に完全に依存します。 

最後に、繰り返される文字が重要です。 単純な間違いは、必要な各文字が少なくとも 1 回表示されたかどうかを追跡せずに、出現回数を数えることです。 たとえば、次のような文字列では`GGGG`, GDSC は、頻度に基づく解釈が誤って進歩を示唆している可能性があるにもかかわらず、まだ D、S、および C が不足しているため、何も完了していません。 

## アプローチ

 強引なアイデアは、説明どおりにプロセスを正確にシミュレートすることです。 文字列のプレフィックスごとに、各チームがこれまでに収集したものを表す 2 つのセットを維持します。 すべての位置でセットを更新し、必要な文字がすべて含まれているかどうかを確認します。 これはルールを直接反映しているため、これは正しいです。 

このアプローチは、各文字が 1 回処理され、集合演算が定数時間であるため、テスト ケースごとに O(n) で実行されます。 各ステップで必要な文字を繰り返しスキャンして慎重に実装したとしても、それでも O(n × 8) 以内に収まるでしょう。n ≤ 100 であれば、これは自明のことです。 

問題の構造は本質的に逐次的なものであるため、より深い最適化は必要ありません。 唯一意味のある観察は、過去の文字を再検討したり、「必要な文字をすべて確認したか」以上のことを計算したりする必要がないということです。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション | O(n) | お(1) | 承認済み |
 | 最適なシングルパストラッキング | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列をタイムラインとして扱い、チームごとに 2 つのブール トラッカーを維持します。 

1. 4 つのブール配列またはセットを初期化します。1 つは GDSC の進行状況用、もう 1 つは BKAC の進行状況用です。 まだ文字が表示されていないため、それぞれは空から始まります。 
2. 必要なセットを事前定義します。GDSC には G、D、S、C が必要です。 BKAC には B、K、A、C が必要です。 
3. 文字列を左から右にスキャンします。 キャラクターがそれぞれの必要なセットに属している場合、キャラクターごとに両チームの進行状況を更新します。 このステップにより、両方のチームが同じ入力ストリーム上で独立して同期的に進行することが保証されます。 
4. 文字を更新した後、GDSC に必要な 4 つの文字がすべてあるかどうかを確認します。 その場合、現在のインデックスを完了ポイントとして記録します。 
5. BKAC に対しても同じチェックを実行し、その完了時点を記録します。 
6. スキャンが終了したら、記録された完了インデックスを比較します。 どちらかが小さければ、そのチームが勝ちます。 両者が等しい場合、結果は引き分けです。 

重要な設計上の選択は、各チームが完成する最初の瞬間のみを考慮することです。 チームがすべての手紙を集めたら、その後の出来事は勝者を決定するのに重要ではありません。 

### なぜ効果があるのか

 各チームの状態は、必要な各文字が以前または現在の位置で少なくとも 1 回出現したかどうかによってのみ決まります。 この状態は単調であり、一度収集された手紙は決して失われることはありません。 このため、必要な文字がすべて存在する最初の位置は一意に定義され、結果を決定するのに十分です。 これらの最初の完了位置を比較すると、プロセスで説明した競合状況が完全に把握できます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input().strip())
        s = input().strip()

        need_gdsc = set("GDSC")
        need_bkac = set("BKAC")

        have_gdsc = set()
        have_bkac = set()

        finish_gdsc = -1
        finish_bkac = -1

        for i, ch in enumerate(s):
            if ch in need_gdsc:
                have_gdsc.add(ch)
            if ch in need_bkac:
                have_bkac.add(ch)

            if finish_gdsc == -1 and have_gdsc == need_gdsc:
                finish_gdsc = i
            if finish_bkac == -1 and have_bkac == need_bkac:
                finish_bkac = i

        if finish_gdsc < finish_bkac:
            print("GDSC")
        elif finish_bkac < finish_gdsc:
            print("BKAC")
        else:
            print("DRAW")

if __name__ == "__main__":
    solve()
```実装はシミュレーションに正確に従います。 セット`have_gdsc`そして`have_bkac`これまでに見つかった必須文字を追跡します。 チームが完了に達すると、その後の更新によって上書きされないように、完了インデックスがロックされます。 

微妙な点は、完了インデックスを -1 に初期化することです。 これにより、チームが終了した後に結果を再計算したり、誤って変更したりすることがなくなります。 最後の比較は、最初の完了時間にのみ基づいています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、両チームが共有文字 C に大きく依存しているにもかかわらず、他の必要な文字がまったく異なるタイミングで表示される場合です。 のような入力の場合`CCCCDGSKBA`、両チームはほぼ即座に C を収集しますが、完了は最後の欠落している非共有文字によって完全に決まります。 部分的な進行ではなく、完全なセットが満たされた場合にのみ完了がトリガーされるため、アルゴリズムはこれを正しく処理します。 

もう 1 つのケースは、無関係な文字が繰り返されることです。 のような文字列で`ZZZZGDSC`, GDSC は、それ以前に無関係な文字が多数出現しても、C が最後に出現した時点でのみ完了します。 アルゴリズムは不要な文字を完全に無視するため、状態遷移には影響しません。
