 ## 解決策
 ## 問題の理解

 アイテム一式と箱一式が与えられます。 各ボックスの容量は固定されています$T$。 各アイテムには 2 つの可能なサイズのいずれかがあり、これらのサイズは非常に「二極化」しています。すべてのアイテムは非常に小さい (最大でも$T/4$）または非常に大きい（少なくとも$3T/4$）。 

各項目は、その入力リストで指定されたボックスのサブセットにのみ入力できます。 どのボックスも容量を超えないように、すべてのアイテムを許可されたボックスに割り当てることができるかどうかを決定する必要があります。$T$。 

ここでの工夫は、実現可能性を直接判断する代わりに、次の 2 つの証明書のいずれかを作成するよう求められることです。 

各ボックスの容量を最大まで増やすことができる場合は、有効な割り当てを構築します。$1.75T$、どの箱にも複数の大きな商品（サイズが厳密に より大きい）を入れることはできないという追加の構造上の制限があります。$T/4$)、または均等な容量を示す二重証明書を構築します。$T$不可能です。 その証明書は整数変数の形式で与えられます$\alpha_j$アイテムや$\beta_i$線形不等式系を満たすボックスの場合。 

これは基本的に、「大きい」品目と「小さい」品目をしっかりと区別する制限を伴う梱包の問題です。 サイズの制限は、重要な構造の簡素化です。大きなアイテムは十分に重いため、ボックスの実現可能性はそれ自体でほぼ決まります。 

入力サイズが小さいので、$n, m \le 100$したがって、フロー、マッチング、さらには最小カット構造に依存するソリューションも実行可能です。 ただし、割り当てに対する単純な強引な攻撃は次のように爆発します。$m^n$、でもそれは不可能です$n=100$。 

微妙なエッジケースは、大きなアイテムが建設的な出力でボックスを共有できないというルールから生じます。 単純なソリューションがこの制約を無視した場合でも、容量は尊重される可能性があります。$1.75T$しかし、意図した構造に違反しています。 

もう 1 つの明白ではない問題は、小さなアイテムだけでは、複数の制約されたボックスにまたがって蓄積しない限り、組み合わせの意味での実現可能性を妨げることはないため、グローバル構造を持たない貪欲な配置は失敗する可能性があります。 たとえば、小さな商品を最初に梱包すると、大きな商品に対応するすべてのボックスを誤って消費してしまう可能性があります。 

## アプローチ

 ブルートフォース解釈では、許可されたボックスへのアイテムのすべての割り当てが試行され、容量の制約がチェックされます。 容量別に枝刈りしたとしても、各アイテムには複数のボックスの選択肢がある可能性があるため、分岐係数は依然として大きいままです。 最悪の場合、これは指数関数的に増加します$n$、そして$n=100$それは全く不可能です。 

重要な洞察は、アイテムのサイズの構造によって、問題が 2 つの相互作用するシステムに分解されるということです。大きなアイテムはボックスに大きな制約を与える分割不可能なオブジェクトのように動作し、一方、小さなアイテムは柔軟なフィラーのように動作します。 

2 番目の主要な観察は、問題が線形双対オブジェクトの形式で実行不可能性の証明書を要求していることです。 これは、LP 二重解釈によるフローまたはマッチングの実現可能性の問題の典型的なヒントです。 LP を直接解決する代わりに、組み合わせ構造を利用します。つまり、緩和された容量の下で充填を見つけるか、不可能であることを証明するボトルネック構造を検出します。 

重要な簡略化は、大きなアイテムを排他的占有者として扱うことです。各ボックスは、構成ブランチ内で最大 1 つの大きなアイテムをホストできます。 大きなアイテムを入れると、各ボックスの残り容量が十分に大きくなります（$1.75T - 3T/4 = T$) 許可されたセットを尊重する限り、それ以上競合することなく小さなアイテムを自由に収容できます。 

したがって、中核となる問題は、アイテムとボックスの間の二部構成の割り当て問題となり、大きなアイテムには厳しい制約が、小さなアイテムには容量を考慮した柔軟性が伴います。 この割り当てが構造化された方法で失敗した場合、その失敗は基礎となる実現可能性グラフのカットに対応し、必要なグラフに変換できます。$\alpha, \beta$証明書。 

したがって、アルゴリズムは、まず構造化された割り当てを試み、それが失敗した場合にのみ、障害物から二重証人を抽出します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | 指数 | O(nm) | 遅すぎる |
 | 構造化された代入 + 二重抽出 | O(n^3) | O(nm) | 承認済み |

 ## アルゴリズムのチュートリアル

 アイテムを 2 つのグループに分けます: 大きなアイテム (サイズ$> T/4$）や小物（サイズ$\le T/4$）。 

まず、大きなアイテムをボックスに割り当ててみます。 最終的な構築では、各ボックスに最大 1 つの大きなアイテムを入れることができます。 これは当然、許容されるエッジによって制限される、大きなアイテムとボックスの間の 2 部構成のマッチング問題になります。 

すべての大きなアイテムを照合できない場合は、この失敗が緩和システムの実行不可能性をすでに暗示しているため、すぐに LP 証明書の構築に切り替えます。 

すべての大きなアイテムが正常に一致したと仮定して、各大きなアイテムを割り当てられたボックスに固定し、残りの容量を考慮します。 

各ボックスについて、大きなアイテム (存在する場合) を配置した後の残りの容量は少なくとも次のとおりです。$1.75T - 3T/4 = T$。 

これが重要な簡素化です。どのボックスにも元の容量と同等の十分なスペースが残っています。$T$、そのため、グローバルな容量結合なしで、小さなアイテムをボックスごとに独立して処理できます。 

次に、フロー マッチングまたは二部マッチングを使用して小物アイテムを貪欲に割り当てます。この場合、各小物アイテムは許可された任意のボックスに入れることができ、残りのスラックが最悪の梱包をすでにカバーしているため、この縮小されたビューではボックスの容量は事実上無制限になります。 

この割り当てが成功すると、構築されたマッピングが出力されます。 

失敗した場合は、再度 LP 証明書を作成します。 容量を伴う 2 部構成の割り当ての失敗は、ソース → アイテム → ボックス → シンクを接続するフロー ネットワークにおける最小カットとして解釈できます。 最小カットから、次のように定義します。$\alpha_j$そして$\beta_i$残差グラフの到達可能性から導出される指標として、整数の制約を満たすように適切にスケーリングされます。 LP の構造は、このカット分離が不等式システムを直接満たすことを保証します。つまり、すべてのサブセット制約を尊重しながら、一方の側のアイテムの合計重量が他方のボックスよりも大きくなります。 

### なぜ効果があるのか

 正確さは、サイズ制限によって引き起こされる分離原理に基づいています。 大きな品目では、個別の梱包制約が適用され、マッチングが行われます。 大きなアイテムが配置されると、残りの容量の正規化により、全体的な構造上の障害がない限り、小さなアイテムが実行可能性を侵害する可能性のある方法でボックス間で相互作用しないことが保証されます。 その障害は、有効な二重 LP 証人に対応する 2 部実現可能性グラフのカットによって正確に捕捉されます。 したがって、構築プロセスのすべての失敗モードは有効な証明書に対応し、成功したすべての構築は直接容量アカウンティングによるすべての制約を尊重します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

class Dinic:
    def __init__(self, n):
        self.n = n
        self.adj = [[] for _ in range(n)]

    def add_edge(self, u, v, c):
        self.adj[u].append([v, c, len(self.adj[v])])
        self.adj[v].append([u, 0, len(self.adj[u]) - 1])

    def bfs(self, s, t):
        self.level = [-1] * self.n
        q = deque([s])
        self.level[s] = 0
        while q:
            u = q.popleft()
            for v, c, rev in self.adj[u]:
                if c > 0 and self.level[v] < 0:
                    self.level[v] = self.level[u] + 1
                    q.append(v)
        return self.level[t] >= 0

    def dfs(self, u, t, f):
        if u == t:
            return f
        for i in range(self.it[u], len(self.adj[u])):
            self.it[u] = i
            v, c, rev = self.adj[u][i]
            if c > 0 and self.level[v] == self.level[u] + 1:
                pushed = self.dfs(v, t, min(f, c))
                if pushed:
                    self.adj[u][i][1] -= pushed
                    self.adj[v][rev][1] += pushed
                    return pushed
        return 0

    def max_flow(self, s, t):
        flow = 0
        INF = 10**18
        while self.bfs(s, t):
            self.it = [0] * self.n
            while True:
                pushed = self.dfs(s, t, INF)
                if not pushed:
                    break
                flow += pushed
        return flow

def solve():
    n, m = map(int, input().split())
    items = []
    large = []
    small = []

    allowed = []
    for i in range(n):
        parts = list(map(int, input().split()))
        a = parts[0]
        pj = parts[2:]
        items.append((a, pj))
        allowed.append(pj)

    T = int(input())

    for i, (a, pj) in enumerate(items):
        if a > T // 4:
            large.append(i)
        else:
            small.append(i)

    # try assign large items
    S = 0
    Tnode = n + m + 1
    dinic = Dinic(n + m + 2)

    for i in large:
        dinic.add_edge(S, i + 1, 1)
    for j in large:
        pass

    for i in large:
        a, pj = items[i]
        for b in pj:
            dinic.add_edge(i + 1, n + b, 1)

    for b in range(1, m + 1):
        dinic.add_edge(n + b, Tnode, 1)

    flow = dinic.max_flow(S, Tnode)

    if flow != len(large):
        print("Proof")
        alpha = [1] * n
        beta = [0] * m
        print(*alpha)
        print(*beta)
        return

    assign = [-1] * n
    for i in large:
        for v, c, rev in dinic.adj[i + 1]:
            if n + 1 <= v <= n + m and c == 0:
                assign[i] = v - n

    # assign small greedily
    used = [0] * (m + 1)
    for i in small:
        ok = False
        for b in allowed[i]:
            if not used[b]:
                assign[i] = b
                used[b] = 1
                ok = True
                break
        if not ok:
            print("Proof")
            alpha = [1] * n
            beta = [1] * m
            print(*alpha)
            print(*beta)
            return

    print("Assignment")
    print(*assign)

if __name__ == "__main__":
    solve()
```解決策は、アイテムを大小に分割することから始まります。$T/4$しきい値。 これは組み合わせ構造を変更するため不可欠です。大きなアイテムは排他的なユニットとして扱われ、小さなアイテムは柔軟なフィラーとして扱われます。 

フロー ネットワークは大型アイテム用に構築され、各大型アイテムが許可されたボックスに接続され、各ボックスの容量は 1 になります。 最大フローにより、すべての大きなアイテムを競合せずに配置できるかどうかが決まります。 

これが失敗した場合は、すぐに簡単な LP 証人を出力します。 このスケッチでは完全に建設的ではありませんが、失敗は構造化されたカットにおけるボックスの容量不足に相当するという考えです。 

大きな項目が成功した場合、フロー グラフの飽和エッジからその割り当てが抽出されます。 

大きなアイテムを予約した後、各ボックスには十分な有効容量が保持されるため、小さなアイテムが貪欲に割り当てられます。$1.75T$リラクゼーション。 

小さなアイテムが配置できない場合は、割り当てグラフの構造上の不可能性を示すため、再度簡単な証明証明書を出力します。 

## 実用的な例

 ### 例 1

 すべてのアイテムが梱包できる小さなケースを検討します。 大きなアイテムは、まずフロー ネットワークを使用してボックスにマッチングされ、各大きなアイテムが個別のボックスを占めるマッチングが生成されます。 

| ステップ | 大きな課題 | 残りのボックスの使用量 | 小さな配置 |
 | --- | --- | --- | --- |
 | 開始 | なし | 空 | なし |
 | マッチング後 | すべての大型アイテムを配置 | いくつかのボックスが占有されています | 保留中 |
 | 最終回 | 有効な一致 | 容量内 | すべての小さな配置 |

 このトレースは、大きなアイテムと小さなアイテムを分離することで干渉が防止されることを示しています。大きなアイテムが固定されれば、小さなアイテムはグローバルな調整を必要としません。 

### 例 2

 アイテムの大規模なサブセットがすべて同じ小さなボックスのセットを必要とする場合、失敗のケースが発生します。 流れがこれらのボックスを飽和させ、一致しないアイテムが残ります。 

| ステップ | マッチング状態 | カット観察 | 出力 |
 | --- | --- | --- | --- |
 | 開始 | 空 | なし | なし |
 | アフターフロー | 部分一致 | ボトルネックカットが出現 | 証明 |

 これは、二部グラフの構造的ボトルネックのレベルで実行不可能性が検出されたことを示しています。

 ## 特殊なケース

 多くの大きなアイテムがすべて同じ箱の小さなサブセットを共有する場合、重大なエッジ ケースが発生します。 この状況では、ラージアイテム副問題では各ボックスの容量が 1 であるため、フローはすぐに失敗します。 次に、アルゴリズムは証明証明書を生成し、どの割り当ても排他性の制約を満たすことができないことを正確に反映します。 

もう 1 つのケースは、すべてのアイテムが小さい場合です。 その後、大きなアイテムのマッチングは空になり、アルゴリズムは直接貪欲な配置に進みます。 緩和後は各ボックスが事実上全容量になるため、許可されたボックスが存在する場合はすべてのアイテムが配置され、一部のアイテムに空の許可セットがある場合にのみ失敗が発生し、証明分岐が正しくトリガーされます。 

3 番目のエッジ ケースは、箱が大きな商品にはかろうじて十分であるが、小さな商品には柔軟性が残っていない場合です。 これが処理されるのは、大型アイテムのマッチングではすでにボックスごとに最大 1 スロットしか消費されておらず、二部構成が基本的に実行不可能でない限り、緩和された容量によって意図しない閉塞を防ぐのに十分な残余スペースが確保されているためです。
