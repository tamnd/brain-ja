 ## 解決策
 ## 問題の理解

 保管室のネットワークを説明するツリーが与えられます。 各部屋がノードであり、各接続が鉄道です。 この構造は任意ではありません。すべてのノードが 1 つの中央パスから最大 2 の距離内にあるという強い制限があります。 これは、「スパイン」パスが存在し、他のすべてのノードがそのパス上にあるか、そのパスに直接接続されているか、またはもう 1 つの中間ノードを介して接続されていることを意味します。 

この木の上に同じ薬品タンクを置きます。 配置は、占有されている 2 つの部屋がエッジで直接接続されていない場合にのみ有効であるため、選択した部屋は独立したセットを形成します。 

各テスト ケースに対して、同じ数のタンクの 2 つの有効な構成 (初期 1 つとターゲット 1 つ) が与えられます。 タスクは、初期構成を目標構成に変換するまで、すべての中間ステップで妥当性を常に維持しながら、隣接する部屋にタンクを一度に 1 つずつ移動できるかどうかを決定することです。 戦車は区別できないため、アイデンティティではなく、占有されているセットのみが重要になります。 

ツリー サイズの制約は、テスト ケースあたり最大 10,000 ノードであり、テスト ケースは最大 10 個あります。 これにより、独立したセットの完全な再構成状態空間を探索しようとするアプローチが除外されます。これは、再構成状態空間が指数関数的に増大するためです。 実行可能な解決策は、ツリーを、線形または線形に近いパスを使用して移動を推論できる構造に圧縮する必要があります。 

最初の微妙な点は、両方の構成が有効な独立したセットであっても、一方を別の構成に変換できるとは限らないということです。 素朴な考えは、空のノード内でトークンを自由に「スライド」できると仮定することです。 中間ステップで隣接関係が強制される可能性があるため、分岐制約のあるツリーではこれは失敗します。 

2 番目のエッジ ケースは、スパインに接続された小さなブランチ内のトークンを再配置することによってのみ 2 つの構成が異なる場合です。 局所的には交換可能に見えるかもしれませんが、脊椎を通って移動すると一時的に動きが妨げられ、独立条件に違反する可能性があります。 正しいソリューションは、これらのローカルのボトルネックを考慮する必要があります。 

最後に、すべてのノードが中央パスから距離 2 以内にあるという要件が重要です。 これにより、深い枝分かれが防止され、あらゆる障害物が樹木全体に広がるのではなく、局所的に脊椎の周囲に構造化されることが保証されます。 

## アプローチ

 ブルート フォース ビューは、各有効な構成をグラフ内の状態として扱います。エッジは、独立性を維持しながら単一のトークンを隣接する空いているノードに移動することに対応します。 初期セットから開始してサイズ m のすべての有効な独立セットに対して BFS または DFS を実行し、ターゲット セットに到達することを期待します。 小さなツリーでも、独立セットの数は指数関数的であり、ブランチごとのフィボナッチの増加にほぼ等しいため、このアプローチは n が 30 または 40 付近ですぐに爆発します。n が 10000 までの場合、完全に実行不可能です。 

重要な観察は、ツリーの構造から得られます。 すべてのノードは中心パスから距離 2 以内にあるため、ツリーは長さが最大 ​​2 つまでの短い「アーム」を備えた脊椎のように動作します。 これにより、トークンの相互作用方法が強力に制限されます。 一方の腕にあるトークンは、背骨を介する場合を除いて、遠く離れた別の腕に影響を与えることはできず、背骨自体が競合を強いられる狭い通路として機能します。 

これは削減を示唆しています。トークンの動きについて全体的に考える代わりに、スパインに接続された各ローカル構造単位にどれだけのトークンが存在できるかを分析します。 このような各ユニットの内部再配置能力は非常に限られており、重要なことに、トークンはスパインを通過しない限り永久にユニットを離れることができないため、保存のような制約が課せられます。 

これらの局所的な不変量を特定すると、問題はスパイン分解によって引き起こされるすべての不変量に​​関して初期構成とターゲット構成が一致するかどうかをチェックすることになります。

 ## アルゴリズムのチュートリアル

 まず、ツリーを再構築し、その中心スパイン パスを特定することから始めます。 グラフはすべてのノードがこのパスから 2 番目の距離内にあるツリーであるため、概念的にはスパインをバックボーンとして扱い、その他すべてを小さな付属コンポーネントとして扱うことができます。 

スパインが特定されたら、すべてのノードを 3 つの役割のいずれかに分類します。 ノードは脊椎上、脊椎から 1 歩離れたところ、または 2 歩離れたところにあります。 距離 2 のノードは常に、中間ノードを介してスパイン ノードに接続された小さなチェーンに属します。 

変換の問題は、トークンが相互に通過することができず、ツリーの異なる部分間の移動はスパインを通過する必要があるという事実によって決まります。 これにより、ローカル保存ルールが作成されます。隣接関係の制約に一時的に違反することなく、接続された異なるサブ構造間でトークンを任意に再配布することはできません。 

したがって、ノードを、再構成時に独立して動作する最小限のコンポーネントにグループ化します。 このような各コンポーネントは、スパイン ノードとそれに接続された長さ 1 または 2 のブランチで構成されます。 

各コンポーネントについて、ソース構成からのトークンがその中にいくつあるか、ターゲット構成からのトークンがその中にいくつあるかを計算します。 これらのカウントはすべてのコンポーネントで一致する必要があります。これは、境界で中間の不正な隣接関係を強制せずに、コンポーネントが「所有する」トークンの数を変更する有効な移動シーケンスがないためです。 

次に、すべてのコンポーネントにわたってこれらの数を比較します。 すべてのコンポーネントのソースと宛先のトークン数が同じであれば、変換は実行可能であると判断します。 そうでなければ不可能です。 

### なぜ効果があるのか

 不変条件は、スパインに接続された各コンポーネントは、スパイン上の制約された境界頂点を通過しない限り、他のコンポーネントとトークンを交換できないということです。 このような転送には、2 つの隣接するスパイン領域が同時に競合する位置にトークンを保持する瞬間が必要となり、独立性ルールに違反します。 したがって、コンポーネントごとのトークン数は、有効な再構成シーケンスを通じて不変のままであり、これらの不変条件を一致させることが必要かつ十分です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, m = map(int, input().split())
        r = list(map(int, input().split()))
        s = list(map(int, input().split()))
        d = list(map(int, input().split()))

        adj = [[] for _ in range(n + 1)]
        for i, p in enumerate(r, start=2):
            adj[i].append(p)
            adj[p].append(i)

        is_spine = [False] * (n + 1)

        deg = [len(adj[i]) for i in range(n + 1)]

        spine = []
        for i in range(1, n + 1):
            if deg[i] > 2:
                spine.append(i)

        if not spine:
            spine = list(range(1, n + 1))

        for x in spine:
            is_spine[x] = True

        comp_id = [-1] * (n + 1)
        cid = 0

        def dfs(u, p, root):
            comp_id[u] = root
            for v in adj[u]:
                if v != p and not is_spine[v]:
                    dfs(v, u, root)

        for i in spine:
            dfs(i, -1, i)
            cid += 1

        cnt_s = {}
        cnt_d = {}

        for x in s:
            root = x
            while root and not is_spine[root]:
                for v in adj[root]:
                    if deg[v] > deg[root]:
                        root = v
                        break
                else:
                    break
            cnt_s[root] = cnt_s.get(root, 0) + 1

        for x in d:
            root = x
            while root and not is_spine[root]:
                for v in adj[root]:
                    if deg[v] > deg[root]:
                        root = v
                        break
                else:
                    break
            cnt_d[root] = cnt_d.get(root, 0) + 1

        print(1 if cnt_s == cnt_d else 0)

if __name__ == "__main__":
    solve()
```実装では、親配列表現からツリーを構築し、一連のスパイン ノードをマークします。 そこから、すべてのノードをスパイン ノードをルートとするコンポーネントに分類しようとします。 重要な操作は、占有されている各ノードを関連するスパイン コンポーネントにマッピングし、ソースと宛先の各コンポーネントに属するトークンの数をカウントすることです。 

微妙な点は、マッピングが一貫している必要があるということです。つまり、すべてのノードが一意のスパイン アンカーに決定的に解決される必要があります。 これは、脊椎に到達するまで高次の構造に向かって登ることによって強化されます。 

コンポーネントの数は n で線形であり、周波数の等価性のみが必要なため、最後の比較ではハッシュ マップを使用します。 

## 実用的な例

 3 つのノードからなるスパインに長さ 2 本以下の短い枝がある小さな木を考えてみましょう。 初期構成で 2 つの異なるブランチにトークンが均等に配置され、ターゲットがトークンを交換するとします。 

| ステップ | アクション | コンポーネントA | コンポーネント B |
 | --- | --- | --- | --- |
 | 1 | ソーストークンをカウントする | 2 | 1 |
 | 2 | 宛先トークンをカウントする | 1 | 2 |
 | 3 | 比較 | 不一致 | 不一致 |

 このケースは、両方の構成が有効な独立したセットであるにもかかわらず、スパイン コンポーネント間の不均衡により有効な変換が妨げられていることを示しています。 

次に、同じコンポーネント内でのみトークンが再配置される 2 番目のケースを考えてみましょう。 

| ステップ | アクション | コンポーネントA | コンポーネント B |
 | --- | --- | --- | --- |
 | 1 | ソーストークンをカウントする | 1 | 1 |
 | 2 | 宛先トークンをカウントする | 1 | 1 |
 | 3 | 比較 | 一致 | 一致 |

 ここでは、トークンがコンポーネントの境界を越える必要がないため、移動が可能です。

 ## 特殊なケース

 重要なエッジ ケースは、すべてのトークンがスパインに接続された 1 つの小さなブランチ内に完全に存在する場合です。 この状況では、単純な解決策では、トークンがスパインを介して自由にシャッフルできると考えるかもしれませんが、実際には、隣接関係に違反しない利用可能なスパイン パスがない限り、ブランチは閉じたコンテナとして機能します。 コンポーネントをカウントするアプローチにより、同じルートに割り当てられたすべてのトークンが正しく維持され、等価性チェックにより、違法な再配布が想定されていないことが保証されます。 

もう 1 つのケースは、トークンが背骨の反対側に対称的に表示される場合に発生します。 ローカルではこれらは交換可能に見えるかもしれませんが、一方の側をもう一方の側に移動するにはスパイン ノードを通過する必要があり、一時的に隣接関係の競合が強制されます。 不変条件により、双方がすでに一致するカウントを持っていない限り、そのようなスワップは防止されます。これは実現可能性と一致します。
