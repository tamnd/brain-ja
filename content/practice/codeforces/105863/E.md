 ## 解決策
 ## 問題の理解

 正の整数の配列が与えられており、この配列を連続したブロックに分割することに依存する関数を評価する必要があります。 For each possible block size parameter$k$、配列をサイズの連続したグループに分割することを想像します。$k$、最後のグループはおそらくより小さい可能性があります。$n$で割り切れない$k$。 各要素は、そのグループのインデックスに等しい乗数 (1 から始まる) でその構成の総コストに寄与します。 

タスクは、あらゆるものについて計算することです。$k$1から$n$、このグループ化ルールに基づく配列の重み付き合計を計算し、問題の要件に従ってこれらの結果を結合します (そのような値をすべて全体にわたって暗黙的に合計します)$k$）。 

主な問題点は、単純な解釈ではすべての要素に対して完全な加重合計が再計算されることです。$k$これは、すべての要素およびすべてのグループ サイズにわたる二次またはそれより悪いプロセスを即座に示唆します。 

制約の観点から見ると、自然な入力サイズは最大です。$n \approx 10^5$。 それぞれのグループ化を明示的にシミュレートしようとするソリューション$k$について自主的に演奏します$n$パス、それぞれの取得$O(n)$、につながる$O(n^2)$これは、一般的な 2 秒の制限には遅すぎます。 

最後に部分グループを処理するときに、微妙な落とし穴が現れます。 すべてのグループがフルサイズであると仮定すると、$k$、特に小規模なブロックでは、最後の不完全なブロックが誤って処理されることがよくあります。$k$、多くの部分ブロックが存在します。 もう 1 つの問題は、グループ化構造が完全に変化することを忘れていることです。$k$なので、1 つの貢献度が事前に計算されます。$k$慎重に集計しないと再利用できません。 

たとえば、配列が次の場合、$[5, 1, 4, 2]$、その後、$k = 2$、グループは$[5,1]$そして$[4,2]$、しかし、$k = 3$、彼らはなる$[5,1,4]$そして$[2]$。 固定セグメンテーションを前提としたり、単一のパーティショニングを再利用しようとしたりするソリューションは、これらの構造の変化で失敗します。 

## アプローチ

 ブルートフォースのアイデアは単純明快です。$k$、配列をサイズのブロックに明示的に分割します。$k$、最初のブロックに乗数 1、2 番目のブロックに 2 というように割り当てて、加重和を計算します。 これは、定義が直接シミュレートされるため機能します。 ただし、それぞれについて、$k$すべての要素に一度触れますので、合計の作業量は次のようになります。$\sum_{k=1}^{n} O(n) = O(n^2)$、全体的には実行不可能になります$n$。 

重要な観察は、固定された$k$、配列はセグメントに分割され、すべての要素が位置にあります。$[1..k]$乗数 1 を取得し、$[k+1..2k]$乗数 2 を取得するなど。 これにより、インデックスを超えた個々の要素の位置への依存がなくなり、各要素の寄与はインデックスとブロック サイズのみに依存することになります。$k$、動的構造上ではありません。 

問題をこのように見ると、それぞれの$k$定数乗算器を使用した連続範囲にわたる合計に還元されます。 これにより、プレフィックス合計を使用してセグメント合計を一定時間で計算できるようになります。 要素を反復する代わりに、ブロックを反復します。 与えられた$k$、約あります$n/k$ブロックなので 1 つを処理する$k$費用$O(n/k)$。 全体をまとめると$k$、調和級数構造が得られます。$\sum_{k=1}^{n} n/k$、次のように動作します$O(n \log n)$。

 ## アルゴリズムのチュートリアル

 まず、配列のプレフィックス合計を事前計算して、セグメント合計を一定時間内にクエリできるようにします。 最適化全体が要素ごとの累積をブロックごとのクエリに置き換えることに依存しているため、これは不可欠です。 

の各値に対して、$k$1から$n$、サイズをジャンプして配列をスキャンします$k$。 各ジャンプは 1 つのブロックに対応し、その乗数はブロック インデックスによって決まります。 

このスキャン内では、プレフィックス合計を使用して現在のセグメントの合計を計算し、それにブロック インデックスを乗算して、その答えに加算します。$k$。 

このプロセスを全員に対して繰り返します$k$、最終的な答えを積み上げます。 

### なぜ効果があるのか

 このアルゴリズムは、固定値の不変式に依存します。$k$、同じブロック内のすべての要素は同じ乗数を共有し、ブロックは連続していて重複しません。 これにより、すべての要素が 1 回につき 1 回正確にカウントされることが保証されます。$k$、その寄与はブロック インデックスに従って正しく重み付けされます。 プレフィックス合計は正確なセグメント合計を保持するため、ブロック内の反復を範囲クエリに置き換えても、計算値は変わりません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    # prefix sums
    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + a[i]

    ans = 0

    for k in range(1, n + 1):
        block = 1
        i = 0

        while i < n:
            j = min(n, i + k)
            seg_sum = pref[j] - pref[i]
            ans += block * seg_sum
            block += 1
            i = j

    print(ans)

if __name__ == "__main__":
    solve()
```この解決策はプレフィックス合計の構築から始まり、任意のセグメント合計を O(1) で計算できるようになります。 メインループは可能なすべてのブロックサイズを反復します。$k$、それぞれについて$k$、サイズの塊で配列を調べます。$k$。 変数`block`各セグメントの乗数を追跡します。 

オフバイワンの一般的なリスクは、セグメントの正しい境界を誤って処理することです。 表現`min(n, i + k)`無効なインデックスにアクセスすることなく、最後のブロックが安全に切り捨てられるようにします。 もう一つの微妙な点はリセットです`block`それぞれ1に$k$乗算器は新しいパーティショニング スキームごとに再起動されるためです。

 ## 特殊なケース

 単一要素の配列は最も単純な境界です。 入力あり$[5]$、あるだけです$k=1$、1 つのブロック、乗数 1 なので、答えは 5 です。アルゴリズムはプレフィックスの合計を正しく初期化し、正確に 1 つのセグメントを処理するため、特別な大文字と小文字を区別する必要はありません。 

次のような 2 要素の配列の場合$[100, 1]$、 のために$k=1$結果は$100 + 2 \cdot 1 = 102$、そしてのために$k=2$それはです$100 + 1\cdot 1 = 101$、合計は 203 になります。実装は、次の理由により最後の部分ブロックを正しく処理します。`min(n, i + k)`境界ロジック。要素がスキップされたり二重にカウントされたりしないようにします。
