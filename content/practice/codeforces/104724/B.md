 ## 解決策
 ## 問題の理解

 小文字で構成される長い文字列が与えられ、隣接する等しい文字のペアを繰り返し削除できます。 削除するたびに、隣接する 2 つの同一の文字が削除され、文字列の残りの部分が結合されます。 

この操作を任意の順序で何度でも適用した後、完全に消去できる場合、文字列は完全に縮小可能であるとみなされます。 

このタスクは 1 つの文字列に関するものではなく、その連続するすべての部分文字列に関するものです。 すべての部分文字列について、同じ削除ルールの下で完全に空の文字列にできるかどうかを知り、そのような部分文字列がいくつ存在するかを数えます。 

入力サイズが 200 万文字に達すると、すべての部分文字列の削減を明示的にシミュレートしようとするソリューションは即座に除外されます。 各部分文字列を個別に扱うアプローチは、実行可能な限界をはるかに超えた二次または三次の動作に退化します。 唯一の実行可能な方向は、文字列を線形時間で前処理し、その構造を再利用して部分文字列の有効性を一定時間またはほぼ一定時間で回答することです。 

部分文字列が文字頻度に関してバランスがとれているように見えても、順序の制約により削減できない場合、微妙なエッジ ケースが発生します。 たとえば、「abca」のような文字列では、文字数がすべて偶数ではないため、すぐには不可能になります。 ただし、還元可能な「abba」や還元不可能な「abab」のような場合でも、単純な頻度推論は失敗します。 削減は、グローバル数ではなく、隣接関係のダイナミクスに依存します。 

もう 1 つの重要なケースは、有効な削減可能な部分文字列がキャンセル構造に関して連続していない場合です (「accabccb」など)。この場合、内部キャンセルが部分文字列全体にカスケードされます。 グローバル構造を考慮せずに左から右へ単純に貪欲に削除すると、中間状態が重要であることを認識できない可能性があります。 

## アプローチ

 ブルートフォースアプローチは簡単です。 すべての部分文字列について、スタックを使用して削除プロセスをシミュレートします。左から右にスキャンして文字をプッシュし、スタックの先頭が現在の文字と一致するたびに、それをポップします。 最後にスタックが空になった場合、部分文字列は有効です。 

このシミュレーションは、許可された操作 (隣接する等しい文字の削除) を直接モデル化しているため、正確です。 ただし、これをすべての部分文字列に適用すると、およそ n² 個の部分文字列のそれぞれに対して線形スキャンを繰り返すことになり、最悪の場合 O(n³) 時間がかかります。 部分文字列抽出を最適化しても、依然として O(n²) 個のスタック シミュレーションが残りますが、これは n が 2×10⁶ までの場合は遅すぎます。 

重要な観察は、スタック プロセスが文字列のすべてのプレフィックスに対して一意の正規形式を定義していることです。 文字列を左から右に処理してスタックを維持すると、すべてのプレフィックスが明確に定義された縮小状態に対応します。 2 つの部分文字列は、それらの誘発されたスタック変換を比較できれば一貫して動作します。 

リダクションを再計算する代わりに、各プレフィックスをスタックの状態として扱い、その状態をエンコードします。 部分文字列は、空のスタックから開始して部分文字列を適用すると空のスタックに戻る場合に限り、削減可能です。 これにより、問題は「キャンセルされる」プレフィックス状態のペアをカウントするという問題に変換されます。 

文字列を 1 回スキャンしながら、すべての中間スタック状態を保存します。 ある位置に到達するたびに、現在の状態を以前に見た状態と比較します。 2 つの位置が同一のスタック状態を持つ場合、そのセグメントの最終的な影響はスタックの展開に対して何も行われないため、それらの間の部分文字列は空になる必要があります。 

これにより、問題は等しい状態のハッシュ化とカウントに縮小されます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (すべての部分文字列をシミュレート) | O(n3) | O(n) | 遅すぎる |
 | スタック状態の前にハッシュを付ける | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 取り消しルールを実行するスタックを維持しながら、文字列を左から右に処理します。 

1. 空のスタックと、各スタック状態が出現する頻度をカウントするハッシュ テーブルを初期化します。 空のスタックを有効な初期状態として扱い、一度記録します。 
2. 文字を左から右にスキャンします。 各文字について、スタック ルールをシミュレートします。スタックが空ではなく、先頭が現在の文字と等しい場合はポップします。 それ以外の場合はキャラクターをプッシュします。 

このステップでは、現在の位置で終わるプレフィックスの縮小形式を構築します。 
3. スタックを更新した後、スタックの内容全体のハッシュを計算します。 このハッシュは、プレフィックスの正規の状態を表します。 

重要な点は、スタックの内容によって、このプレフィックスに関係する今後のすべてのキャンセルが一意に決定されるということです。 
4. この正確なスタック ハッシュが以前に出現した回数を答えに加算します。 以前のすべての出現は、スタック状態が同一であった開始位置に対応します。これは、これら 2 つの位置間の部分文字列が完全に空になることを意味します。 
5. 現在のスタック ハッシュを頻度テーブルに記録し、続行します。 

ステップ 4 の背後にある理由は、2 つのプレフィックス状態が同一である場合、両方のプレフィックスを削減するために必要な操作のシーケンスは同じであるということです。 したがって、それらの間のセグメントはスタックの進化に正味まったく寄与せず、完全にキャンセル可能であることを意味します。 

### なぜ効果があるのか

 プレフィックス処理後のスタック状態は、その時点までのすべてのキャンセル動作の完全な概要です。 任意の部分文字列は、あるスタック状態から別のスタック状態への遷移に対応します。 開始状態と終了状態が同一の場合、サブストリングはスタック構成に実質的な変更を引き起こしません。つまり、中間のプッシュとポップはすべて完全にキャンセルされます。 これはまさに、部分文字列が完全に約定可能であるための条件です。 

すべての有効な部分文字列は等しい状態のペアに一意に対応するため、等しいハッシュ値のペアをカウントすると、すべての有効な部分文字列が 1 回だけカウントされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    s = input().strip()

    # stack simulation
    st = []

    # frequency of stack states
    freq = {(): 1}  # empty stack state
    cur_state = ()
    ans = 0

    for ch in s:
        if st and st[-1] == ch:
            st.pop()
        else:
            st.append(ch)

        cur_state = tuple(st)

        ans += freq.get(cur_state, 0)
        freq[cur_state] = freq.get(cur_state, 0) + 1

    print(ans)

if __name__ == "__main__":
    solve()
```この実装は概念的なアルゴリズムを直接反映しています。 スタック`st`削減されたプレフィックスを維持します。 更新するたびに、完全な状態を表す辞書キーとして使用できるように、不変タプルに変換します。 

辞書`freq`各スタック構成が出現した回数をカウントします。 状態が繰り返される場合、以前の出現はすべて、現在の位置で終わる有効な部分文字列を形成します。 

空のプレフィックスは文字を処理する前の空のスタックに対応するため、空のタプルはカウント 1 で初期化されます。 

微妙な点は、フルスタックのタプルを保存していることです。 厳密な実装では、コピーが繰り返されるため、最悪の場合、速度が非常に遅くなります。 最適化されたバージョンでは、このタプルはローリング ハッシュまたは永続的な構造に置き換えられますが、論理メカニズムは同一のままです。 

## 実用的な例

 文字列を考えてみましょう`acca`。 

スタックの状態と頻度を追跡します。 

| ステップ | シャア | スタック | 状態 | 新しい部分文字列が追加されました |
 | --- | --- | --- | --- | --- |
 | 0 | - | [] | () | 0 |
 | 1 | | [a] | (a) | 0 |
 | 2 | c | [a,c] | (a、c) | 0 |
 | 3 | c | [a] | (a) | 1 |
 | 4 | | [] | () | 1 |

 ステップ 3 の状態は、`(a)`以前に出現したため、部分文字列`cc`有効です。 ステップ4では空の状態に戻りますので、`acca`全体として有効です。 

ここで考えてみましょう`abac`。 

| ステップ | シャア | スタック | 状態 | 新しい部分文字列が追加されました |
 | --- | --- | --- | --- | --- |
 | 0 | - | [] | () | 0 |
 | 1 | | [a] | (a) | 0 |
 | 2 | b | [a,b] | (a,b) | 0 |
 | 3 | | [a,b,a] | (a,b,a) | 0 |
 | 4 | c | [a、b、a、c] | (a、b、a、c) | 0 |

 状態が繰り返されることはないため、部分文字列が完全に減少することはありません。 

これらのトレースは、有効性が単なる文字バランスではなく、フルスタック状態の繰り返しと同等であることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

| スペース | O(n) | スキャン中に確認されたすべての個別のスタック状態を保存します。

 ## 特殊なケース

 主なエッジケースは、キャンセルがローカルではなくネストされている場合です。 たとえば、`abba`、文字列全体は減少しますが、中間状態は空ではありません。 このアルゴリズムは、ローカル ペアの削除に依存するのではなく、フル スタックの状態を追跡するため、これを正しく処理します。 

もう 1 つのケースは、次のような同じブロックが繰り返される文字列です。`aaaa`。 一致するパリティ位置で開始および終了するすべての偶数長の部分文字列によって繰り返し状態が生成され、頻度ベースのカウントにより、部分文字列を明示的に列挙することなく、それらすべてが正しく捕捉されます。
