 ## 解決策
 ## 問題の理解

 色付きのブロックが縦に 2 つ積み重ねられています。 各スタックは、青を表す B と赤を表す R の 2 つの記号のみで構成される文字列として下から上に記述されます。 唯一許可される動きは、一方のスタックの一番上のブロックを取得して、もう一方のスタックの上に置くことです。これを何度でも繰り返します。 

目的は、最終構成でどちらのスタックにも同じ色の 2 つの隣接するブロックが列のどこかに含まれないように、2 つのスタック間でブロックを再配置できるかどうかを判断することです。 言い換えれば、各スタックは厳密に下から上に色を交互に配置する必要があります。 

重要な観察は、移動によって結合された各スタック内のブロックのマルチセットは変更されませんが、時間の経過とともに上位要素の任意の再配分が可能になるということです。 最上位ブロックを繰り返し転送できるため、スタック順序の制約を尊重する限り、2 つのスタックの任意のインターリーブに到達できます。 

制約は非常に小さく、各タワーには最大 20 個のブロックがあり、最大 1000 個のテスト ケースがあります。 これにより、すべての動きのシーケンスをシミュレートしようとする状態の大量の検索が即座に除外されます。 単一のケースでは状態空間が小さい場合でも、移動シーケンスの分岐は組み合わせ的に爆発的に発生する可能性があります。 

素朴なアイデアは、これを各状態がスタックのペアであり、各移動が 1 つの最上位要素を転送する状態にわたる BFS として扱うことです。 移動するたびに到達可能な構成の数が大幅に増加するため、これはすでに深さとともに指数関数的に増加しています。 

タワー間のすべてのブロックを自由に並べ替えることができると仮定すると、さらに微妙な問題が生じます。 スタックは内部的に順序を保持するため、これは直接的には当てはまりません。 たとえば、スタック制約を無視した貪欲な再配布により、実際には到達できない構成が生成される可能性があります。 

誤解を招くシナリオは、両方のスタックに交互のパターンが含まれているものの、「位置がずれている」場合です。 

入力:```
1
3 3
RBR
BRB
```これは常に有効だと言いたくなりますが、移動順序によっては、順序制約が無視されると誤った実現可能性が想定される可能性があります。 正しい答えは「はい」ですが、単純な「カウントのみ」の推論は、より構造化されたケースでは依然として失敗します。 

本当の困難は、カウントや順列ではなく、すべてのブロックが単一の順序付けられた転送プロセスから得られることを考慮しながら、最終的な交互構造を 2 つのスタックに分離できるかどうかです。 

## アプローチ

 ブルート フォース シミュレーションでは、両方のスタックを明示的にモデル化し、考えられるすべての一連の動きを試します。 各移動は 2 つのスタックのうち 1 つを選択し、その一番上のブロックをもう一方に移動します。 枝刈りを行ったとしても、各ブロックがスタック間で複数回振動する可能性があるため、状態の数は急速に増加し、指数関数的な分岐係数が発生します。 

重要な簡素化は、実際には移動の実行順序は気にせず、最終的な配置だけを気にするという認識から生まれます。 最終的には、合法的な最上位転送のシーケンスによって任意のブロックをいずれかのスタックに移動できるため、唯一の実際の制約は、結果として得られる各スタックの色が交互になるように、各ブロックを 2 つの交互シーケンスのいずれかに割り当てることができるかどうかです。 

これにより、問題は、ブロックのマルチセットを 2 つの交互のシーケンスに分割できるかどうかを確認することになります。 各シーケンスはそれ自体が有効である必要があります。開始色が固定されると、スタックの残りの部分が強制されます。 

したがって、考えられる割り当てごとに、スタックが 2 つ連続して同じ色になることがないことを確認するだけで済みます。 両方のスタックは合計カウントを除いて独立しているため、交互制約を考慮した有効な分割が存在するかどうかを確認するだけで済みます。 

これは直接的な建設的なチェックにつながります。各スタックの開始色について両方の可能性を試し、各スタックの B と R の数を競合せずに交互のパターンに配置できるかどうかを検証します。

 ## アルゴリズムのチュートリアル

 1. 両方のスタックにわたる B ブロックと R ブロックの合計数を計算します。 これらの合計は固定されており、配布できるすべての利用可能なリソースを表します。 
2. 有効な最終構成は 2 つの交互のシーケンスで構成されている必要があることに注意してください。 各シーケンスは、開始色と長さが固定されると完全に決定されます。 
3. スタック長が固定の場合、交互シーケンスには正確な要件があります。B で始まる場合、B は奇数の位置を占めなければなりません。 R で始まる場合、R は奇数の位置を占めます。 これにより、長さと必要な数の間の直接マッピングが作成されます。 
4. 2 つのスタックの開始色のすべての組み合わせを試します。 選択ごとに、B と R のグローバル数を使用して、両方のスタックの交互の要件を満たすことができるかどうかをシミュレートします。 
5. 各割り当てについて、各スタックに必要な B と R の数を計算します。 必要な合計が利用可能な数と正確に一致する場合、構成は実行可能です。 
6. いずれかの割り当てが機能する場合は、YES を出力します。 それ以外の場合は、NO を出力します。 

### なぜ効果があるのか

 有効な最終状態は、ブロックを 2 つの交互のシーケンスに分割する方法によって完全に決定されます。 移動によりブロックのアイデンティティを変更せずに任意の再分配が可能になるため、実現可能性は B と R のグローバルな供給が 2 つの交互の需要パターンを満たせるかどうかによってのみ決まります。 交互構造により、各スタック内のすべての自由がなくなり、問題は一定数のパリティ構成に対する有限チェックに変わります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def required_counts(length, start):
    # start = 'B' or 'R'
    # returns (need_B, need_R)
    if start == 'B':
        need_B = (length + 1) // 2
        need_R = length // 2
    else:
        need_R = (length + 1) // 2
        need_B = length // 2
    return need_B, need_R

t = int(input())
for _ in range(t):
    n, m = map(int, input().split())
    s1 = input().strip()
    s2 = input().strip()

    total_B = s1.count('B') + s2.count('B')
    total_R = n + m - total_B

    ok = False

    for start1 in ['B', 'R']:
        for start2 in ['B', 'R']:
            b1, r1 = required_counts(n, start1)
            b2, r2 = required_counts(m, start2)

            if b1 + b2 == total_B and r1 + r2 == total_R:
                ok = True

    print("YES" if ok else "NO")
```この実装では、最初に色のグローバル インベントリが計算されます。 次に、2 つの交互スタックの開始色を選択する 4 つの可能な方法を列挙します。 構成ごとに、スタックが完全に交互になっている場合に各スタックに必要な B と R の数を正確に計算します。 

微妙な点は、動きを決してシミュレートしないということです。 操作モデルではブロックの完全な転送可能性が保証されているため、実現可能性は必要な合計が利用可能な合計と一致するかどうかによってのみ決まります。 

ヘルパー関数は、交互スタックの決定論的構造をエンコードします。開始色が固定されると、他のすべての位置が強制されるため、カウントは一意に決定されます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from sys import stdout
    import sys as _sys

    input = _sys.stdin.readline

    t = int(input())
    out = []

    def solve():
        n, m = map(int, input().split())
        s1 = input().strip()
        s2 = input().strip()

        total_B = s1.count('B') + s2.count('B')
        total_R = n + m - total_B

        def req(length, start):
            if start == 'B':
                return (length + 1) // 2, length // 2
            else:
                return length // 2, (length + 1) // 2

        ok = False
        for a in 'BR':
            for b in 'BR':
                b1, r1 = req(n, a)
                b2, r2 = req(m, b)
                if b1 + b2 == total_B and r1 + r2 == total_R:
                    ok = True

        out.append("YES" if ok else "NO")

    for _ in range(t):
        solve()

    return "\n".join(out)

NO"""

 ## 特殊なケース

 まれなケースは、一方のスタックがすでに交互になっているが、もう一方のスタックが交互になっていない場合に発生します。 このアルゴリズムは初期構造に依存せず、合計カウントのみに依存するため、引き続き機能します。 例えば：```
2 2
BR
RR
```合計 B = 1、合計 R = 3。長さ 2 と 2 を交互に割り当てるには、少なくとも 1 つのスタックに 2 B または 2 R のいずれかが必要ですが、これは満たされないため、出力は NO になります。 

もう 1 つのエッジ ケースは、両方のスタックが均一である場合 (すべて B など) です。移動によってブロックを再分配できますが、長さが 1 を超える交互スタックには両方の色が必要であり、カウント チェックにすぐに失敗するため、交互構成は不可能です。
