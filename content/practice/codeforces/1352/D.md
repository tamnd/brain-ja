 ## 解決策

 ## 問題の理解

 それぞれ正のサイズのキャンディーの列が与えられ、2 人のプレーヤーが反対側からキャンディーを消費します。 アリスは常に左側から消費し、ボブは右側から消費します。 彼らは交互にターンを行い、各ターンはそれぞれの側から 1 つ以上の連続したキャンディーを食べることで構成されます。 

重要なルールは、自分のターンのプレイヤーは、消費する合計サイズが前のターンに相手が食べた量を厳密に超える量のキャンディーを食べなければならないということです。 アリスは最初にスタートし、最初の動きでキャンディーを 1 つだけ食べることを強制されます。 その後、両プレイヤーは常に相手の以前の動きの合計を最小限に超えるように努めます。 

ゲームはすべてのキャンディーが消費されるまで続き、発生したターン数と各プレイヤーが食べたキャンディーの総量を報告する必要があります。 

この制約により、最大 5000 個のテスト ケースと合計 200000 個のキャンディーが許可されます。 これは、各キャンディーを一定の回数だけ処理するソリューションであれば十分であることを意味します。 テスト ケースごとの 2 次シミュレーションは、すでに処理されたセグメントを繰り返し再スキャンする場合、最悪の場合、非常に遅くなります。 プロセスの構造は、各キャンディーが 1 回消費される 2 ポインター シミュレーションを示唆しています。 

1 人のプレイヤーが必要とするターゲットが残りのターゲットを超える場合、微妙なエッジケースが発生します。 そのような状況では、プレイヤーは単に残りのキャンディーをすべて食べるだけで、プロセスはすぐに終了します。 もう 1 つの注意が必要なケースは、多くの小さなキャンディーが累積して前の合計をわずかに超える場合であり、ターンごとに複数のポインターを強制的に進める可能性があります。 ポインターを誤ってリセットしたり、合計を最初から再計算したりするソリューションは、長い 1 のシーケンスが交互に現れると失敗する可能性があります。 

## アプローチ

 直接シミュレーションは文字通りルールに従います。各ターンで、現在の左または右ポインターからスキャンし、合計が前の対戦相手の合計を超えるまでキャンディーの値を蓄積します。 各ターンの後、プレイヤーを切り替えて続行します。 これはゲームの定義を正確に反映しているため、これは正しいです。 

ただし、合計を再計算したり、セグメントを繰り返し再スキャンしたりする単純な実装では、テスト ケースあたりの動作が O(n²) になる危険があります。 すべてのケースのような最悪のケースでは、各ターンは 1 ステップしか進めず、スキャンを繰り返すと多くの要素が不必要に再訪問されてしまいます。 

重要な観察は、各キャンディーが正確に 1 回消費され、ポインターが内側にのみ移動することです。 したがって、2 つのポインターを維持し、要素を再検討することなく合計を段階的に蓄積します。 各ステップは、条件が満たされるまで現在のプレーヤーの合計を拡張します。

 ## アルゴリズムのチュートリアル

 左端と右端の 2 つのポインターと、各プレーヤーの累計を使用してゲームをシミュレートします。 

1. ポインタの初期化`l = 0`、`r = n - 1`。 セット`alice_sum = 0`、`bob_sum = 0`、 そして`prev = 0`前の動きの食べた合計を追跡します。 アリスが最初に開始するため、ターン数も 0 に初期化します。 
2. アリスの最初の動きでは、左からちょうど 1 つのキャンディーを食べなければなりません。 追加します`a[l]`彼女の合計に増加します`l`、 セット`prev`その値まで移動回数を増やします。 これは強制的なルールであり、開始時に対称性が崩れます。 
3. ボブに切り替えます。 ボブのターンでは右側から積み上げて繰り返しテイクしていきます。`a[r]`そして減少しています`r`ボブの現在のターン合計が厳密に大きくなるまで`prev`。 
4. ボブが超えたら`prev`、更新します`prev`ボブのターン合計に合わせて移動カウントを増やし、アリスに戻ります。 
5. アリスの一般的なターンでは、再び左から積み上げ、合計が超えるまでキャンディーを追加します。`prev`、次にアリスの合計を更新し、`prev`。 
6. すべてのキャンディーが消費されるまで、手順 3 ～ 5 を繰り返します。 キャンディーが残っていないため、いずれかの時点で必要な条件を満たすことができない場合、現在のプレーヤーが残りのキャンディーをすべて受け取り、プロセスは直ちに終了します。 

### なぜ効果があるのか

 重要な不変条件は、すべてのキャンディ インデックスが 1 回だけアクセスされ、ポインタの動きによって指示された順序でアリスまたはボブのいずれかに永続的に割り当てられることです。 各ターンは、一方の側から消費されるセグメントの合計を厳密に増加させ、停止条件により、単調な累積の下で各移動が最小限になることが保証されます。 どちらのポインタも内側にのみ移動し、反転することはないため、要素が再検討されることはなく、シミュレーションは冗長な作業を行わずにゲームの状態を忠実に再構築します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    out = []

    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))

        l, r = 0, n - 1
        moves = 0
        alice = 0
        bob = 0
        prev = 0

        turn_alice = True

        while l <= r:
            s = 0

            if turn_alice:
                if l == 0:
                    s = a[l]
                    l += 1
                else:
                    while l <= r and s <= prev:
                        s += a[l]
                        l += 1
                alice += s
            else:
                while l <= r and s <= prev:
                    s += a[r]
                    r -= 1
                bob += s

            if s == 0:
                break

            prev = s
            moves += 1
            turn_alice = not turn_alice

        out.append(f"{moves} {alice} {bob}")

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```このソリューションは 2 つのポインターを維持し、それらを内側にのみ展開します。 交互の旗は誰の番かを追跡しますが、`prev`次のプレイヤーが必要なしきい値を知ることができるように、最後の手の合計を保存します。 各ループは少なくとも 1 つのキャンディーを消費し、終了を保証します。 

よくある実装の落とし穴は、アリスの最初の強制的な動きを別々に誤って処理し、最初のセグメントを誤ってスキップしたり二重にカウントしたりすることです。 もう一つは、累計をリセットするのを忘れていることです`s`これはターンごとに誤って蓄積され、厳密な比較条件を破ってしまいます。

 ## 特殊なケース

 単一のキャンディ入力は、アリスがそれを完全に消費し、両方のポインタが交差することでループが終了するため、アリスの強制的な最初の動きによって即座に処理されます。 すべて等しい値のシーケンスにより、アルゴリズムはほぼすべてのステップを最小の増加で交互に実行し、「以前より厳密に大きい」条件が正しく実装されているかどうかをテストします。 増加するシーケンスはボブの後の動きを強調し、右側の累積がアリスの増加する合計を超えるには複数のピックが必要になる可能性があり、ポインタの動きと合計のリセットがターンをまたいで漏れないことを確認します。
