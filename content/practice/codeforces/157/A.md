 ## 解決策
 ## 問題の理解

 私たちに与えられているのは、`n × n`すべてのセルに整数が含まれるボード。 各セルについて、2 つの量を比較します。 

最初の数量は、そのセルの行内のすべての数値の合計です。 2 番目の数量は、そのセルの列内のすべての数値の合計です。 列の合計が行の合計よりも厳密に大きい場合、セルは勝利と呼ばれます。 

タスクは、この条件を満たすセルの数を数えることです。 

基板サイズは非常に小さいです。 以来`n ≤ 30`、グリッド全体には最大でも次のものが含まれます`30 × 30 = 900`細胞。 すべてのセルに対して追加の作業を実行するアルゴリズムであっても、制限内で快適に実行されます。 これは、高度な最適化手法は必要ありませんが、繰り返しの計算については慎重に検討する必要があることを意味します。 

直接実装すると、セルごとに行全体の合計と列の合計を個別に再計算する場合があります。 各再計算にはコストがかかります`O(n)`、そして、あります`n²`セルなので、全体の複雑さは次のようになります。`O(n³)`。 と`n = 30`、操作の総数はわずか約であるため、これでも十分高速です。`27,000`。 

それでも、問題の構造からすると、当然、よりクリーンなアプローチが示唆されます。 行の合計と列の合計は何度も再利用されます。 それらを一度計算すると、すべてのセルを一定時間でチェックできます。 

不注意な実装を黙って破壊してしまう可能性のあるエッジケースがいくつかあります。 

可能な限り最小の基板を考えてみましょう。```
1
1
```唯一の行合計は`1`、唯一の列の合計も`1`。 条件は厳密に大きいので、答えは次のようになります。`0`。 

よくある間違いは、`>=`の代わりに`>`。 

もう 1 つの微妙なケースは、すべての値が同一である場合です。```
2
5 5
5 5
```すべての行の合計はすべての列の合計に等しいため、どのセルも勝者になりません。 正しい出力は次のとおりです。```
0
```不用意に実装すると、誤って等しい合計が有効なものとしてカウントされる可能性があります。 

もう 1 つの注意が必要な状況は、一部の行と列のみが異なる場合です。```
3
1 1 10
1 1 10
1 1 10
```行の合計はすべて`12`。 列の合計は次のとおりです。`3`、`3`、 そして`30`。 

3 列目のみが勝利セルを生成するため、正解は次のようになります。```
3
```これにより、合計の計算中に行インデックスと列インデックスを混同する実装が捕捉されます。 

## アプローチ

 最も直接的な解決策はブルートフォースです。 あらゆる細胞に`(i, j)`、行の合計を計算します`i`すべての列を反復処理して、列の合計を計算します。`j`すべての行を反復処理します。 列の合計が大きい場合は、答えを増やします。 

これが機能するのは、勝利セルの定義がこれら 2 つの合計にのみ依存するためです。 実装は簡単で、問題のステートメントを正確に反映しています。 

問題は繰り返し作業です。 同じ行の合計はその行のセルごとに 1 回再計算され、同じ列の合計はその列のセルごとに 1 回再計算されます。 

たとえば、次の場合`n = 30`、その後、それぞれ`900`細胞のパフォーマンスは約`60`追加すると、おおよそ次のようになります`54,000`全体的に追加。 これはここでも完全に許容できますが、繰り返す必要はありません。 

重要な点は、行の合計と列の合計が決して変化しないことです。 それらを一度計算すると、関連するすべてのセルで再利用できます。 

まず 2 つの配列を構築します。`row_sum[i]`行の合計を格納します`i`。`col_sum[j]`列の合計を格納します`j`。 

そうすれば、各セルのチェックは簡単になります。 

もし`col_sum[j] > row_sum[i]`、セルが勝利しています。 

これにより、複雑さが軽減されます。`O(n³)`に`O(n²)`同時にロジックをよりクリーンにします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n3) | お(1) | 承認済み |
 | 最適 | O(n²) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 整数を読み取る`n`そして`n × n`グリッド。 
2. 配列を作成する`row_sum`サイズの`n`ゼロで初期化されます。 
3. 配列を作成する`col_sum`サイズの`n`ゼロで初期化されます。 
4. グリッド全体を 1 回横断します。 

あらゆる細胞に`(i, j)`、その値を次の値に追加します。`row_sum[i]`そしてへ`col_sum[j]`。 

これにより、すべての行の合計と列の合計が 1 回のパスで計算されます。 
5.初期化`answer = 0`。 
6. グリッドを再度横断します。 

あらゆる細胞に`(i, j)`、 比較する`col_sum[j]`そして`row_sum[i]`。 
7. もし`col_sum[j] > row_sum[i]`、増分`answer`。 

この問題では、以上ではなく、厳密に大きいことが求められます。 
8. 印刷`answer`。 

### なぜ効果があるのか

 このアルゴリズムは単純な不変式に依存しています。つまり、最初の走査の後、`row_sum[i]`行内のすべての値の合計に等しい`i`、 そして`col_sum[j]`列内のすべての値の合計に等しい`j`。 

これらの値は元のグリッドから 1 回だけ計算され、その後は変更されないため、その後のすべての比較では正しい合計が使用されます。 各セルは問題ステートメントの正確な条件に対して個別にチェックされるため、すべての勝利セルは 1 回だけカウントされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

n = int(input())
grid = [list(map(int, input().split())) for _ in range(n)]

row_sum = [0] * n
col_sum = [0] * n

for i in range(n):
    for j in range(n):
        row_sum[i] += grid[i][j]
        col_sum[j] += grid[i][j]

answer = 0

for i in range(n):
    for j in range(n):
        if col_sum[j] > row_sum[i]:
            answer += 1

print(answer)
```最初の部分では、ボードを 2D リストに読み込みます。 

次のネストされたループは、行の合計と列の合計を同時に計算します。 同じ走査内で両方の配列を更新すると、グリッド上の不要なパスが回避されます。 

2 番目のネストされたループは、すべてのセルを個別にチェックします。 条件は以下を使用します`>`これは、ステートメントでは列の合計が厳密に大きくなる必要があるためです。 

のような小さな基板の場合、特別な取り扱いは必要ありません。`n = 1`。 行の合計と列の合計が唯一のセルで等しいため、ロジックは自然に機能します。 

ここでは、Python の整数も完全に安全です。 最大の場合でも、行または列の最大合計はわずか`30 × 100 = 3000`。

## テストケース```python
# helper: run solution on input string, return output string
import sys, io

def solve():
    input = sys.stdin.readline

    n = int(input())
    grid = [list(map(int, input().split())) for _ in range(n)]

    row_sum = [0] * n
    col_sum = [0] * n

    for i in range(n):
        for j in range(n):
            row_sum[i] += grid[i][j]
            col_sum[j] += grid[i][j]

    ans = 0

    for i in range(n):
        for j in range(n):
            if col_sum[j] > row_sum[i]:
                ans += 1

    print(ans)

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    sys.stdout = io.StringIO()

    solve()

    return sys.stdout.getvalue()

# provided sample
assert run("1\n1\n") == "0\n", "sample 1"

# all equal values
assert run(
    "2\n"
    "5 5\n"
    "5 5\n"
) == "0\n", "all sums equal"

# one dominant column
assert run(
    "3\n"
    "1 1 10\n"
    "1 1 10\n"
    "1 1 10\n"
) == "3\n", "third column wins everywhere"

# asymmetric case
assert run(
    "2\n"
    "1 100\n"
    "1 100\n"
) == "2\n", "second column only"

# larger mixed case
assert run(
    "4\n"
    "5 7 8 4\n"
    "9 5 3 2\n"
    "1 6 6 4\n"
    "9 5 7 3\n"
) == "6\n", "mixed values"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 |`1 × 1`ボード |`0`| 最小サイズの入力 |
 | すべての値は等しい |`0`| 厳密な比較処理 |
 | 1 つの支配的な列 |`3`| 正しい列の累積 |
 |`[[1,100],[1,100]]`|`2`| 行/列のインデックス付けの正確性 |

 ## 特殊なケース

 可能な限り最小の基板を考えてみましょう。```
1
1
```アルゴリズムは以下を計算します。`row_sum = [1]`

`col_sum = [1]`唯一のセルの場合、比較は次のようになります。`1 > 1`、これは誤りです。 アルゴリズムは以下を正しく出力します。```
0
```これは、平等はカウントされないことを確認します。 

ここで、すべての番号が同じであるボードを考えてみましょう。```
2
5 5
5 5
```行の合計は次のようになります。`[10, 10]`、列の合計も次のようになります。`[10, 10]`。 

あらゆる比較は、`10 > 10`、これは誤りです。 セルはカウントされないため、答えは次のようになります。```
0
```このケースでは、実装が誤って使用していないことを検証します。`>=`。 

最後に、優勢な列があるケースを考えてみましょう。```
3
1 1 10
1 1 10
1 1 10
```アルゴリズムは以下を計算します。`row_sum = [12, 12, 12]`

`col_sum = [3, 3, 30]`すべての行について、3 番目の列のみが次の条件を満たします。`30 > 12`。 

ちょうど 3 つのセルがカウントされるため、出力は次のようになります。```
3
```これにより、行と列のインデックスが正しく処理され、合計がすべてのセルで一貫して再利用されることが確認されます。
