 ## 解決策
 ## 問題の理解

 この問題は言語を文字の構造的特性に還元します。 英語の小文字は、問題設定者が使用する特定のフォントで描画されたときに含まれる「穴」の数によってのみ分類されます。 ちょうど 1 つの文字には 2 つの穴があり、6 つの文字には 1 つの穴がありますが、他のすべての文字には穴がありません。 

大文字で構成される文字列が与えられた場合、タスクは、このフォント マッピングを使用して文字列が書かれたときに、合計で何個のホールが現れるかを判断することです。 文字が出現するたびに、そのホール数に応じて独立して寄与するため、文字が繰り返されるとその寄与が蓄積されます。 

入力は単一の文字列です。 出力は、すべての文字にわたる穴の合計数を表す単一の整数です。 

このステートメントは短いですが、重要な考え方は、マッピングが固定されており小さいため、計算は純粋に文字ごとの分類問題になるということです。 

複雑さの観点から、入力の長さは一般的な Codeforce の方法で大きく、最大約 10^5 文字以上であると想定できます。 これは、解が文字列の長さにおいて線形である必要があることを直ちに意味します。 ネストされたループで各文字を複数回スキャンまたは処理するアプローチでは、速度が非常に遅くなります。 アルファベットのサイズは一定であるため、文字ごとに一定時間の検索が必要です。 

問題のカスタム定義ではなく、通常の英語のタイポグラフィーを想定していると、いくつかの特殊なケースが見落とされやすくなります。 たとえば、フォントの仮定に応じて「B」や「D」などの文字を一貫性なく扱うと、正確性が損なわれます。 もう 1 つの微妙なケースは、文字列にゼロホール文字のみが含まれている場合です。これは、空の結果や初期化されていない値ではなく、正しくゼロを出力する必要があります。 最小限の例が入力されています`C`、返さなければなりません`0`なぜなら、この文字にはこの定義に穴がないからです。 

## アプローチ

 この問題を解決する直接的な方法は、文字ごとに、それが 1 穴文字のセットに属しているか、それとも特殊な 2 穴文字に属しているかを手動で確認することです。 すべての文字について、関連する 7 文字すべてと比較し、それに応じて答えを蓄積することができます。 これが機能するのは、分類が静的で文字ごとに独立しているためです。 

ブルートフォース解釈では、文字ごとに、既知のホールを含む文字のリストを反復処理し、メンバーシップをチェックする可能性があります。 キャラクターごとに最大 7 回の比較を行うと、総コストは 7n に比例します。 これは実際にはすでに線形ですが、メンバーシップ チェックをブール配列やハッシュ セットなどの定数時間ルックアップ構造に変換すると、構造が若干すっきりします。 これにより、繰り返しの比較が不要になり、ロジックが簡素化されます。 

重要な観察点は、アルファベットが固定されており、非常に小さいということです。 文字からホール数へのマッピングを事前計算し、1 回のパスで文字列全体の値を合計することができます。 これにより、問題は文字ごとの配列のインデックス付けに軽減されます。 

メンバーシップを検査するだけなので、総当り的なアプローチは機能しますが、不必要に反復的になります。 最適化されたアプローチでは、すべての分類ロジックが定数時間のテーブル ルックアップに圧縮されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | リストに対する文字ごとの比較 | O(n) | お(1) | 承認済み |
 | 文字ごとの直接ルックアップ テーブル | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字からその穴数への直接マッピングを構築し、文字列を 1 回スキャンしながら結果を蓄積します。 

1. 穴が 1 つだけある文字のセットを次のように定義します。`A, D, O, P, Q, R`。 それぞれに値 1 を割り当てます。穴が 2 つある文字を次のように定義します。`B`、値 2 が割り当てられます。他のすべての文字は暗黙的に 0 にマップされます。このエンコーディングは、視覚的なプロパティを算術に変換します。 
2. 各大文字をそのホール数にマッピングするルックアップ構造 (通常はサイズ 26 の配列または辞書) を作成します。 これにより、比較を繰り返すことなく、文字ごとに一定時間のアクセスが保証されます。 
3. アキュムレータ変数を初期化する`ans = 0`文字列全体の穴の総数が保存されます。 
4. 入力文字列内の各文字を繰り返し処理します。 文字ごとに、そのマップされた値を次の値に追加します。`ans`。 正確さは、各文字の出現を独立して処理することで得られます。 
5. 出力`ans`すべての文字を処理した後。 

### なぜ効果があるのか

 各文字は合計に独立して寄与し、寄与度は処理中に変更されない固定分類にのみ依存します。 このアルゴリズムは、最初の k 文字を処理した後、次の不変条件を維持します。`ans`は、それらの k 個の文字のホール カウントの合計に等しくなります。 各ステップでは現在の文字に対する正しい寄与のみが追加されるため、不変式は文字列の終わりまで保持され、必要な合計に等しくなります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

s = input().strip()

hole = [0] * 26
hole[ord('A') - ord('A')] = 1
hole[ord('D') - ord('A')] = 1
hole[ord('O') - ord('A')] = 1
hole[ord('P') - ord('A')] = 1
hole[ord('Q') - ord('A')] = 1
hole[ord('R') - ord('A')] = 1
hole[ord('B') - ord('A')] = 2

ans = 0
for ch in s:
    ans += hole[ord(ch) - ord('A')]

print(ans)
```このソリューションは固定配列を事前計算します。`hole`ここで、各インデックスは文字に対応します。 マッピングでは ASCII オフセットが使用されるため、各文字は一定時間でインデックスに変換されます。 これにより、ループ内の条件付きチェーンが回避されます。 

蓄積ループはソリューションの中核です。 各反復では、配列アクセスと加算のみが実行され、どちらも定数時間の操作になります。 状態が将来の文字に依存しないため、操作の順序は簡単です。 

よくある間違いは、文字列検索や比較の繰り返しを使用してメンバーシップを再計算することですが、これは不必要なオーバーヘッドです。 もう 1 つの微妙な問題は、入力を削除するのを忘れることです。これにより、改行文字が導入され、インデックス作成が中断される可能性があります。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各文字は定数時間ルックアップで 1 回だけ処理されます。 
| スペース | お(1) | マッピング配列は入力の長さに関係なく固定サイズ (26) です。 

このソリューションは、10^5 文字の場合でも 10^5 の単純な配列アクセスのみが実行されるため、一般的な制約内に簡単に適合します。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    s = input().strip()
    hole = [0] * 26
    hole[0] = 1
    hole[3] = 1
    hole[14] = 1
    hole[15] = 1
    hole[16] = 1
    hole[17] = 1
    hole[1] = 2
    ans = 0
    for ch in s:
        ans += hole[ord(ch) - 65]
    return str(ans)

assert run("ABCD\n") == "4"
assert run("QQQ\n") == "3"
assert run("C\n") == "0"
assert run("BBBB\n") == "8"
assert run("ADOPQR\n") == "6"
assert run("Z\n") == "0"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | ABCD | 4 | 混合文字、基本的な正確さ |
 | QQQ | 3 | 繰り返しの累積 |
 | C | 0 | ゼロホール文字の処理 |
 | BBBB | 8 | 2 穴文字スケーリング |
 | アドプQR | 6 | ワンホールセットを完全網羅 |
 | Z | 0 | リストにない文字の正確性 |

 ## 特殊なケース

 1 つのエッジ ケースは、完全にゼロホール文字で構成される入力です。 たとえば、入力`XYZ`生産すべき`0`。 アルゴリズムは各文字を処理し、ルックアップ テーブルでゼロを見つけ、何も蓄積しません。 最終的な合計はゼロのままですが、これは正しいことです。 

もう 1 つの特殊なケースは、2 穴の文字を最大限に繰り返すことです。 入力用`BBBBB`、各ステップで 2 が加算されるため、累計は 2、4、6、8、10 と変化します。ルックアップは文字ごとに独立しているため、特別な処理は必要なく、大量の繰り返しでも結果は安定しています。 

最後の微妙なケースは、正しい文字のインデックス付けを保証することです。 マッピング配列が ASCII オフセットを使用して構築されている場合、すべての大文字がそのインデックスと正しく位置合わせされている必要があります。 インデックス作成時に 1 つずつずれたエラーが発生すると、文字が誤って分類されますが、各文字は直接マッピングされるため、`ord(ch) - 65`、マッピングはすべての入力にわたって一貫性を保ちます。
