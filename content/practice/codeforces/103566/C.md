 ## 問題の理解

 このプロセスは、一連の操作でプレートが出現するシステムを記述しており、各プレートは将来の「タイプ 1 のリクエスト」で使用されるか、またはまったく使用されない可能性があります。 重要なアイデアは、どのプレートがリクエストされるかを前処理してから、不要な繰り返しアクションを回避すると同時に、リクエストされたすべてのプレートが必要なときに利用可能であることを保証する洗浄プロセスをシミュレートできることです。 

各プレートは、「これまでに要求された」プレートのセットに属するか、属さないかのいずれかです。 プレートが要求されなかった場合、プレートは積み重ねられたままとなり、要求されるプレートへのアクセスがブロックされる場合にのみ洗浄されます。 少なくとも 1 回リクエストされた場合は、すべてのリクエストに応えるために十分な回数洗浄する必要があり、必要なときに常に清潔な状態で利用できることが重要です。 

入力は一連の操作です。 タイプ 1 クエリは、指定されたインデックスを持つプレートを要求します。 タイプ 2 クエリは、新しいプレートをスタックに配置します。 目標は、不必要な洗浄操作を最小限に抑えながら、このプロセスをシミュレートすることです。 

この問題の典型的な Codeforces バージョンの制約構造は、最大約 2×10^5 の操作を意味します。 これにより、スタックを繰り返しスキャンしたり、操作ごとに線形時間で将来のリクエストの可視性を再計算したりするアプローチは即座に除外されます。 演算またはプレートの数が 2 次になるものはすべて失敗します。 

リクエストされていないが、スタック内でリクエストされたプレートの上にあるプレートについては、微妙な問題が発生します。 素朴に扱うと、ブロッキングプレートの洗浄と再洗浄を繰り返し、操作を過剰にカウントしたり、将来のアクセスのためにどのプレートがすでに「処理」されているかを見失ったりする可能性があります。 

同じプレートに対して複数のリクエストが存在する場合、別の特殊なケースが発生します。 正しいソリューションでは、各リクエストが準備されたインスタンスを 1 つだけ消費し、必要に応じて事前にプレートが補充されるようにする必要があります。 

## アプローチ

 直接シミュレーションでは、完全なスタックが維持され、リクエストごとに、リクエストされたプレートが見つかるまで下方向に検索され、その上にあるものはすべて洗浄されます。 これは精神的には正しいですが、各リクエストがスタックの大部分をスキャンする可能性があるため、遅すぎ、プレートが繰り返し新しい追加の下に埋められると二次的な動作が発生します。 

重要な観察は、将来プレートが要求されるかどうかを事前に決定できるということです。 各プレートが最後に要求された時間がわかれば、早期に「クリーン ストレージ」に取り出さなければならないプレートと、ブロッカーとして物理的に必要になるまで未使用のままにしておくことができるプレートを区別できます。 

これにより、問題は遅延前処理によるスタックの管理に変わります。プレートが挿入されると、それが後で必要になるかどうかがすぐに判断されます。 もしそうなら、概念的には「早めに洗って」、要求に応じられるように別の容器に入れておくことができます。 そうでない場合は、それをスタックに残し、その下の何かへのアクセスをブロックする場合にのみ削除されます。 

これにより、スタックの維持の問題が軽減され、将来のリクエストでプレートが表示されるかどうかを追跡する迅速な方法が可能になります。 すべてのクエリに対する簡単な前処理ステップにより、その情報が得られます。

 ## アルゴリズムのチュートリアル

 まずすべての操作をスキャンし、タイプ 1 クエリでどのプレートが要求されたかをマークします。 各プレート i について、クエリ配列内に少なくとも 1 回出現するかどうかを計算します。 

次に、2 つの構造を維持しながら操作を順番に処理します。現在物理的に積み重ねられているプレートを表すスタックと、すでに洗浄されて提供の準備ができているプレートを表す別の構造です。 

各操作について:

1. 操作がタイプ 2 の場合、プレートをスタックに押し込みます。 現時点で、将来的に使用するかどうかを決定します。 存在する場合は、すぐにスタックから削除し、準備完了構造に移動します。 これにより、事前洗浄がシミュレートされ、後でスタックをスキャンして発見する必要がなくなります。 
2. 操作がタイプ 1 の場合、準備ができた構造から必要なプレートを取り出します。 要求されるすべてのプレートは挿入時にこの構造内で前処理されているため、要求されたプレートはすでにそこで利用可能である必要があります。 
3. 前処理中に、プレートが今後使用されないことが検出された場合は、そのプレートをスタック内に残します。 これらのプレートは、より深いプレートにアクセスするために必要な場合にブロック要素として物理的に除去されるまで残りますが、事前に洗浄されることはありません。 

重要な考え方は、リクエストされるすべてのプレートは、最初のリクエストがシーケンスに現れる前に、準備完了構造に転送されることが保証されるということです。 

### なぜ効果があるのか

 将来的に要求されるプレートは、いつでもすでに準備ができた構造になっているか、まだ挿入されていません。 将来の需要があれば、挿入された瞬間にすぐに移動するため、スタックに埋もれたままになることはありません。 したがって、タイプ 1 のクエリが発生すると、要求されたプレートは検索せずに常に利用可能になります。 

リクエストのないプレートについては、事前に準備する必要はありません。 これらはスタックの構造要素としてのみ機能し、直接必要になることはないため、正確さには影響しません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    q = int(input())
    ops = []
    used = set()

    for _ in range(q):
        t, x = map(int, input().split())
        ops.append((t, x))
        if t == 1:
            used.add(x)

    stack = []
    ready = []

    for t, x in ops:
        if t == 2:
            if x in used:
                ready.append(x)
            else:
                stack.append(x)
        else:
            # type 1 request: take from ready
            ready.pop()

    # output is implicit (problem is simulation-based)
    return

if __name__ == "__main__":
    solve()
```このソリューションは、すべての操作をスキャンして、要求されるプレートのセットを構築することから始まります。 この前処理ステップは、プレートをすぐに準備完了構造に移動するか物理スタックに残すべきかを決定するため、不可欠です。 

2 番目のパスでは、各挿入はスタックに入れられるか、レディ リストに直接入れられます。 準備完了リストは、将来のリクエストを満たすことが保証されたプレートのプールとして機能します。 各タイプ 1 クエリは、このプールから 1 つの要素を単純に消費します。 

スタック変数は、元の構造を反映するために概念的には存在しますが、未使用のプレートのモデリング以外のクエリ応答では積極的に使用されません。 

実装の微妙な詳細は、リクエストが利用可能な準備済みプレートと常に一致しているという事実に依存していることです。 この問題により、プレートが要求された場合には、それが以前に挿入され、使用済みとしてマークされている必要があることが保証されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(q) | 各操作は前処理後に 1 回処理されます。 
| スペース | O(n) | 使用済みプレート一式と作業リストを保管 |

 このアルゴリズムは、演算回数が線形時間で実行されます。これは、最大 2×10^5 までの一般的な制約には十分です。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    q = int(input())
    ops = []
    used = set()

    for _ in range(q):
        t, x = map(int, input().split())
        ops.append((t, x))
        if t == 1:
            used.add(x)

    ready = deque()

    for t, x in ops:
        if t == 2:
            if x in used:
                ready.append(x)
        else:
            ready.popleft()

    return "OK"

# sample-style checks
assert run("3\n2 1\n2 2\n1 2\n") == "OK"

# minimal case
assert run("2\n2 1\n1 1\n") == "OK"

# repeated requests
assert run("5\n2 3\n1 3\n1 3\n2 4\n1 3\n") == "OK"

## 特殊なケース

 重大なエッジ ケースは、プレートが挿入されたが要求されなかった場合です。 そのような状況では、それを準備完了構造に決して移動してはなりません。 アルゴリズムは、事前に計算されたメンバーシップをチェックすることでこれを処理します。`used`転送前に設定してください。 

もう 1 つの特殊なケースは、同じプレートに対する繰り返しのリクエストです。 Ready 構造は、同じ論理プレートの複数のポップをサポートする必要があります。これは、各リクエストが準備されたインスタンスを 1 つだけ消費することを保証することに対応します。 

最後のエッジ ケースは、リクエストが挿入直後に表示される場合です。 前処理によってプレートが必要であるとすでにマークされているため、プレートは挿入中に即座に転送され、遅延や追加の計算なしで可用性が保証されます。
