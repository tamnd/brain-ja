 ## 解決策
 ## 問題の理解

 1 から n までの番号が付けられた一連のセルが与えられます。 すべてのセルから、より大きなインデックスを持つセルへの決定的なジャンプが 1 つだけ存在するため、任意の位置から開始してジャンプ ルールを繰り返し適用すると、常に厳密に右に移動し、最終的にセル n に到達します。 この構造により、1 から n までの明確に定義された単一のパスが存在することが保証されます。 

各セルには関連するコストもあり、移動のコストは、開始セルが含まれるかどうかについて若干の規則があり、この固有のパスに沿って訪問したすべてのセルのコストの合計として定義されます。 最初の追加は個別に調整できるため、正確なルールは主要なアイデアには影響しません。 

入力は更新をサポートします。単一セルのジャンプ ルールが変更されます。これは、その位置からの出力エッジが変更されることを意味します。 更新のたびに、新しい構造の下で 1 から n までのパスのコストを再計算する必要があります。 

主な問題点は、パスが一意であるにもかかわらず、動的に変化するジャンプ ポインタに依存していることです。 各更新後の単純な再計算では、1 から n へのウォークがシミュレートされ、クエリごとに O(n) 個のセルにアクセスする可能性があります。n と更新数の両方が大きい場合、これは非常に遅くなります。 

更新がチェーン内の初期の位置に影響を与える場合、エッジ ケースが発生します。 たとえば、セル 1 からのジャンプを変更すると、パス構造全体が変更される可能性があるため、依存関係を再構築せずにローカル情報のみを更新するソリューションは失敗します。 

2 番目の微妙なエッジ ケースは、ジャンプが大きく、インデックスの複数のブロックを即座にスキップする場合です。 グループ化を行わずにローカル伝播を前提とするメソッドは、操作ごとに線形時間まで低下します。 

## アプローチ

 ブルート フォース アプローチは簡単です。更新のたびにセル 1 から開始し、セル n に到達するまで固有のジャンプを繰り返し、途中でコストが蓄積されます。 これは正しいです。グラフは関数チェーンであり、可能なパスは 1 つだけであるためです。 ただし、各クエリは O(n) 個のセルを横断する可能性があり、最大 O(n) 個の更新を行うと、合計の複雑さは O(n²) になり、これは実行不可能です。 

重要な点は、変更のたびに完全なパス構造を実際に再計算する必要がないということです。 パスは長いですが、インデックスを連続したセグメントに分割すると、安定したブロック構造になります。 各セグメント内で、セグメントからどこまで出るか、セグメント内にとどまっている間に蓄積されるコストを事前に計算できます。 これにより、クエリは個々のセル間ではなくセグメント間をジャンプできるようになります。 

これは標準的な平方根分解の考え方です。 インデックスを約 k のサイズのブロックに分割します。 各位置 i について、2 つの値を事前計算します。エンドポイント to[i] (i から開始してブロックを出るまでジャンプを繰り返した後に到達する最初のセル) と、co[i] (このブロック内トラバーサル中に蓄積されたコスト) です。 これらが計算されると、クエリに答えることは、n に到達するまでブロック出口からブロック出口へと繰り返しジャンプするプロセスになります。 

更新は 1 つのブロックにのみ影響します。 位置 i でのジャンプ ルールが変更された場合、同じブロック内およびその左側の位置のみが事前計算された出口を変更される可能性があります。これは、ブロック内シミュレーションが i を通過する唯一の開始点であるためです。 他のブロック内のすべては変更されません。 

これにより、更新ごとに O(k) 回の再計算が行われ、クエリごとに O(n/k) 回の走査が行われます。 k = √n を選択すると、両方のコストのバランスが取れます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | クエリあたり O(n) | O(n) | 遅すぎる |
 | ブロック分解 | 操作ごとに O(√n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 ジャンプ関数 next[i] とコスト配列 val[i] を維持します。 インデックスをサイズ k のブロックに分割します。

各インデックス i について、to[i] と co[i] を事前計算します。ここで、to[i] は、i からブロックを出るまで繰り返しジャンプした後に到達する最初の位置、co[i] は、i 自体のコストを除いた、この内部ウォークに沿って収集された総コストです。 

### アルゴリズムのチュートリアル

 1. 配列を固定サイズ k のブロックに分割し、各インデックスが 1 つのブロックに正確に属するようにします。 これにより、再計算を局所的に行うことができます。 
2. すべてのインデックス i について、i からのジャンプをシミュレートすることによって to[i] と co[i] を計算します。ただし、次の位置が同じブロック内にある場合に限ります。 ブロックを出たら停止し、出口点を記録します。 これにより、長い内部チェーンが 1 つのエッジに圧縮されます。 
3. 1 から n までのクエリに答えるには、i = 1 から開始し、事前に計算された遷移を使用してジャンプを繰り返します。つまり、i が n に達するまで、答えに co[i] を追加し、i = to[i] に設定します。 最後に、定義で必要な場合は開始位置のコストを追加します。 
4. 更新によって next[i] が変更されると、i と同じブロック内のインデックスに対してのみ to と co が再計算され、右から左に処理されます。 同じブロック内の以前の状態は後の状態に依存するため、この順序付けは重要です。 
5. 再計算中に、各位置に対してステップ 2 で使用したのと同じブロック内シミュレーションを再実行し、ブロック出口の一貫性を確保します。 

### なぜ効果があるのか

 重要な不変条件は、すべてのインデックス i について、to[i] は常に真のジャンプ関数に従って到達するブロック外の最初の位置を表し、co[i] は常にブロックを出る前に蓄積された正確なコストを表すということです。 ジャンプは決して後戻りしないため、ブロックを右から左に再計算すると、必要なときにそのブロック内のすべての依存関係がすでに正しくなります。 更新された位置を含まないブロックは、内部シミュレーションが変更されたセルを通過しないため、影響を受けません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, q = map(int, input().split())
    val = [0] + list(map(int, input().split()))

    # next pointer is i + val[i] (assumed forward jump structure)
    nxt = [0] * (n + 1)
    for i in range(1, n + 1):
        nxt[i] = min(n, i + val[i])

    k = int(n ** 0.5) + 1
    block = [0] * (n + 1)
    for i in range(1, n + 1):
        block[i] = (i - 1) // k

    to = [0] * (n + 1)
    co = [0] * (n + 1)

    def rebuild(b):
        L = b * k + 1
        R = min(n, (b + 1) * k)
        for i in range(R, L - 1, -1):
            j = nxt[i]
            if j > R:
                to[i] = j
                co[i] = val[i]
            else:
                to[i] = to[j]
                co[i] = val[i] + co[j]

    for b in range((n + k - 1) // k):
        rebuild(b)

    def update(i, x):
        val[i] = x
        nxt[i] = min(n, i + x)
        rebuild(block[i])

    def query():
        i = 1
        ans = 0
        ans += val[1]
        while i != n:
            ans += co[i]
            i = to[i]
        return ans

    out = []
    for _ in range(q):
        t = input().split()
        if t[0] == '1':
            i = int(t[1])
            x = int(t[2])
            update(i, x)
        else:
            out.append(str(query()))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```コードはインデックス空間全体でブロック分解を維持します。 再構築関数は、ブロック内の出口ポイントとコストを右から左に再計算し、各位置が同じブロック内のさらに先にある位置のすでに計算された結果を再利用できるようにします。 クエリは複数のジャンプをブロック遷移に圧縮し、完全なトラバースを回避します。 

ローカル変更の影響を受けるのはそのブロックから始まるブロック内パスのみであるため、更新関数は 1 つのブロックのみを再構築します。 

## 実用的な例

 n = 6 の小さなインスタンスと、val = [2, 1, 1, 1, 1, 1] で next[i] = i + val[i] によって暗黙的に定義されたジャンプを考えてみましょう。 

| ステップ | 現在の i | アクション | 答え | メモ |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 開始 | 0 | 値[1]を追加 |
 | 2 | 1 | co[1] を追加 | 2 | ブロックの概要を介してジャンプ |
 | 3 | 3 | co[3] を追加 | 4 | ジャンプを続ける |
 | 4 | 5 | co[5] を追加 | 5 | 到達点 |

 このトレースは、セルごとのシミュレーションを回避して、複数の単一ステップがどのようにブロック ジャンプに圧縮されるかを示しています。 

ここで、val[2] をさらに右にリダイレクトするように変更する更新について考えてみましょう。 インデックス 2 を含むブロックのみが再計算されます。 他のブロックのインデックスは変更されず、局所性を示します。 

| ステップ | 変更されたインデックス | 再計算されたブロック | 効果 |
 | --- | --- | --- | --- |
 | 更新 | 2 | ブロック(2) | ローカルから/co までのみ再構築 |
 | クエリ | 1 | 変更されていないブロック | 高速再計算 |

 これは、更新がグローバルに伝播しないことを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O((n + q) √n) | 各更新は 1 つのブロックを O(√n) で再構築し、各クエリは O(√n) ブロック間をジャンプします。 
| スペース | O(n) | ジャンプ ポインターとブロック サマリーのストレージ |

 ブロック サイズを選択すると、再計算とクエリ時間のバランスがとれます。 最大 2·10⁵ までの一般的な制約では、√n は約 450 となり、更新とクエリの両方が制限内に快適に保たれます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、更新された位置がブロックの最初の要素である場合です。 その場合、ブロック内のすべての位置はブロック内チェーンを通じてその位置に依存するため、右側の境界から下方向への再計算に失敗すると、 to と co に古い値が残ることになります。 

もう 1 つのケースは、ジャンプがブロックからすぐに出る場合です。 ここで co[i] には現在のノード コストのみを含める必要があります。そうでないと、クエリ中に個別に処理されるはずの別のブロックからのコストが誤って蓄積されてしまいます。 

最後のケースは、大きなジャンプによりパスの長さが極端に短くなる場合です。 この状況では、ほとんどのインデックスはブロックのはるか外側を指す to[i] を指定する必要があり、ブロック内チェーンの繰り返しを前提とする実装は、次のステップがブロックをすぐに離れる境界条件を明示的に処理しない限り機能しません。
