 ## 解決策
 ## 問題の理解

 私たちは串の山を使ってプレイされる 2 人用の決定的なゲームを与えられます。 初めに、`x`スキュワーとパラメータ`k`。 プレイヤーは交互にターンを行い、常に OC が最初に動きます。 プレイヤーの番では、削除する串の数を 1 から現在の値までの範囲で選択します。`k`十分な数の串が残っている場合に限ります。 すべての移動後の値は、`k`ちょうど 1 だけ減少します。1 回`k`が0になるとそれ以上の移動は不可能となるため、その時点で移動した人が即時に負けとなります。 

勝者は完全に最適なプレイに依存します。つまり、両プレイヤーは常に勝つ可能性を最大化する手を選択します。 

入力により複数の独立したゲームが提供されます。 各ゲームは初期パイルサイズによって定義されます`x`そして初動制限`k`。 出力は単に勝者の ID です。 

制約は私たちを`O(1)`または`O(log x)`試験溶液ごとに。 まで`10^5`テストケースと最大値`10^18`、動きや状態に関するシミュレーションは不可能です。 単一のゲームをシミュレートすることさえ不可能です。`k`それ自体は次のように大きくできます`10^18`。 

微妙なエッジケースが現れるのは、`k`に比べて大きい`x`。 たとえば、次の場合`x = 4, k = 10`, 最初の動きで最大10枚の除去が許可され、ゲームは即座に終了するため、OCはすぐにすべての串を奪うことができます。 ゲームが常に正確に続くことを前提とした素朴なアプローチ`k`動きは間違っているでしょう。 

もう 1 つの例外的なケースは次のような場合です。`k = 1`。 最初のプレイヤーはちょうど 1 本の串を取り除くことができますが、その直後に`k`は 0 になります。これは、残りの串に関係なく、2 番目のプレーヤーには正当な手がないことを意味します。 これにより、最初のプレーヤーの勝利は、`x`に限って`x ≥ 1`。 

最後に、いつ`x`非常に大きく、`k`が小さい場合、パイルが使い果たされる前に単純に移動制限の減少によってゲームが終了するため、串は問題になりません。 

## アプローチ

 ブルートフォースシミュレーションでは、ゲームを明示的にプレイします。各ターンに、1から6までの可能なすべての除去を試します。`k`、結果を再帰的に評価し、削減します`k`それぞれのステップ。 これはゲーム ツリー全体を探索するため、最適なプレイを正確にモデル化します。 

ただし、分岐係数は次のとおりです。`k`、深さも最大です。`k`、 以来`k`ゼロになるまですべての動きを減らします。 無視しても`x`、実際には状態の数は階乗のような爆発のように増加します。 と`k`まで`10^18`、これはまったく不可能です。 

重要な洞察は、パイルのサイズです。`x`問題となるのは、それが遊びを制限しないほど十分に大きくなるまでだけです。 その後、ゲームは完全に一連の減少する移動制限によって支配されます。 移動するたびに減少します`k`ちょうど 1 だけなので、ゲームには決定的な最大ターン数があり、最大でも次のターンで停止します。`k`先に山が尽きない限り移動します。 

したがって、本当の疑問は、合計で何回の手が実際に発生するのかということになります。 移動するたびに減少します`k`1 までなので、その後`k`移動すると値が0になり、次のプレイヤーは移動できなくなります。 したがって、山が尽きなければ、ゲームは常に正確に続きます。`k`移動し、勝者はパリティによって決まります。次の場合、OC が勝ちます。`k`が奇数である場合、KP が勝ちます。`k`は均等です。 

唯一の複雑な問題は、杭がより早く終了するかどうかです。`k`動く。 ただし、OC は常に少なくとも 1 つの串を毎ターン取り除くことができるため、`t`少なくとも動く`t`串は取り外されました。 したがって、もし`x < k`、ゲームはちょうどその後に終了します`x`移動します。`x`移動すると山は空になり、次のプレイヤーは移動できなくなります。 もし`x ≥ k`、ゲームはちょうどその後に終了します`k`～によって動く`k`ゼロに達する。 

したがって、移動数は単純に`min(x, k)`、その数字が奇数か偶数かによって勝者が決まります。

 ## アルゴリズムのチュートリアル

 ゲームを実際に行われる手の数を数え、誰が最終的な手を打つかを決定します。 

1. コンピューティング`m = min(x, k)`。 これは、ゲームの続行が不可能になるまでに実際に発生する可能性のある最大手の数を表します。 
2. 同等性に基づいて勝者を決定します。`m`。 OC が先手を取るので、次の場合は OC が勝ちます。`m`奇数である場合、KP が勝ちます。 

最初のステップの背後にある理由は、各移動で少なくとも 1 本の串が確実に取り除かれ、減少するということです。`k`ちょうど 1 の差なので、どちらのリソースもゲームでそれを超えることはできません`min(x, k)`動く。 

2 番目のステップは交互のターンから始まります。 合計の手数が奇数の場合、最初のプレーヤー OC は最後の有効な手を実行し、2 番目のプレーヤーには何も手をつけずに残します。 偶数の場合、KP が最後の手を実行し、OC が次にスタックします。 

### なぜ効果があるのか

 ゲームのあらゆる段階で、串刺しと移動許容量という 2 つの独立した「予算」が減少します。 スキュワーは移動ごとに少なくとも 1 つ減少し、移動制限は移動ごとにちょうど 1 つ減少します。 どちらも単調に減少し、どちらも回避できないため、ゲームはどちらのリソースが最初になくなるかによって完全に決まります。 すべての手が常に串を 1 つだけ取り除く方法で実行できることを認識すると、最悪の場合の持続時間は強制され、戦略的な選択はそれを超えてゲームを延長または短縮することはできません。`min(x, k)`。 この減少の後、ゲームは単純な交互のターン数になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        x, k = map(int, input().split())
        m = x if x < k else k
        if m % 2 == 1:
            print("OC")
        else:
            print("KP")

if __name__ == "__main__":
    solve()
```このコードは、単純な最小操作を使用して有効な手の数を直接計算します。 比較`x < k`関数呼び出しのオーバーヘッドを回避し、テスト ケースごとに一定の時間を確保します。 次に、常に最初に開始する OC に基づいて、パリティ チェックによって勝者が決定されます。 

よくある実装上の間違いは、ゲームが常に正確に続くと仮定することです`k`動く。 それが失敗するのは、`x < k`、山が早く空になるからです。 もう 1 つの間違いは、可変の除去量で貪欲に手をシミュレートしようとすることですが、最適なプレイは総手数に影響を与えないため、これは不要です。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        x, k = map(int, input().split())
        m = x if x < k else k
        out.append("OC" if m % 2 == 1 else "KP")
    return "\n".join(out) + "\n"

# provided samples

# custom cases

assert run("1\n10 1\n") == "OC\n"
assert run("1\n1 10\n") == "OC\n"
assert run("1\n100 100\n") == "KP\n"

 ## 特殊なケース

 いつ`k = 1`、ゲームはすぐに崩壊します。 OCは1回移動し、減少します`k`0 になり、串が何本残っているかに関係なく、KP には正当な手はありません。 アルゴリズムは計算します`m = min(x, 1) = 1`、これは奇数であるため、OC が正しく勝ちます。 

いつ`x < k`、 のような`x = 2, k = 10`、移動制限ではなく串の枯渇によりゲームが終了します。 OC は串を 1 つ取り除き、KP は串を 1 つ取り除き、2 移動後に山が空になります。 アルゴリズムが使用するのは、`m = 2`、2番目の手が最終的なため、KPに勝利が与えられます。 

いつ`x = k`、両方の制約が完全に一致し、ゲームは常に正確に続きます。`k`動く。 解はきれいに等価になります`k`、ターンの交互構造に一致します。
