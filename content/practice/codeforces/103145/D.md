 ## 解決策
 ## 問題の理解

 2 種類の操作の下で、時間の経過とともに変化する整数の配列を維持しています。 1 つの操作は、各要素自体から派生した特別な値を繰り返し追加することで配列のセグメント全体を変更し、もう 1 つの操作はセグメントの合計を求めます。 

重要な問題は、更新が均一ではないことです。 範囲に演算を適用するとき$[L, R]$、各ポジション$i$その範囲内では次のように増加します$\text{lowbit}(a_i)$、 どこ$\text{lowbit}(x)$2 を割る最大の累乗です$x$。 これは、増分が要素の現在の値に依存するため、更新は状態に依存し、変更のたびに進化することを意味します。 

2 番目の演算はより単純です。範囲内の値の合計を法で返さなければなりません。$998244353$。 

制約が示すのは、$n$そして$m$まで$10^5$テスト ケースごとに最大 20 個のテスト ケース。 操作ごとにセグメントを直接走査すると、最大で次のような結果が得られます。$10^{10}$最悪の場合、更新が遅すぎます。 遅延伝播を伴うセグメント ツリーであっても、更新関数は固定された方法で線形または加算的ではなく、各要素の現在の値に依存するため、単純ではありません。 

微妙だが重要なエッジ ケースは、値がゼロになる場合に発生します。 以来$\text{lowbit}(0) = 0$、要素がゼロになると、更新時に再び変更されることはありません。 これにより、将来の更新に寄与しない「デッドポジション」が作成されます。 もう 1 つのエッジ ケースは、2 のべき乗の値です。これは、その下位ビットがそれ自体に等しいため、1 回の更新で大きさが大幅に上昇する可能性があります。 

単純なシミュレーションでは、セグメント全体を繰り返しスキャンします。 

入力:```
1
5
1 2 3 4 5
1
1 1 5
```正しい動作では位置ごとに異なる増分が適用されますが、この小さな例ではブルート フォース ループが依然として実行可能です。 ただし、これをスケーリングすると、$10^5$操作によりそれが不可能になります。 

重要な観察は、更新は現在の値に依存しますが、値の遷移は構造化された方法で単調であるということです。各要素は独立して進化し、その進化は決定論的関数の繰り返し適用にのみ依存します。$a \leftarrow a + \text{lowbit}(a)$。 この構造により、値が安定するかしきい値を超えるまで値がどのように変化するかを事前計算し、これらの遷移にわたる範囲集計をサポートできます。 

## アプローチ

 ブルート フォース ソリューションでは、配列を直接維持します。 更新操作ごとに、以下を繰り返します。$L$に$R$、計算する$\text{lowbit}(a_i)$に追加します。$a_i$。 各クエリは、値の範囲と合計を反復処理します。 

これは問題定義に直接従うため、正しいです。 ただし、それぞれの操作に費用がかかります$O(n)$最悪の場合、$O(nm)$、これは大きすぎます$10^5$スケール入力。 

ボトルネックは繰り返しの再計算です。$\text{lowbit}(a_i)$多くの更新にわたる同じ要素に対して。 ただし、同じルールが繰り返し適用されると、各要素は独立して進化します。 各位置を個別に表示すると、その値が決定的なシーケンスに従っていることがわかります。$$a \rightarrow a + \text{lowbit}(a)$$このシーケンスには重要な特性があります。つまり、後続ビットが急速に増加し、最終的には小さな増分が重要になる回数が減り、軌道が無秩序ではなく構造化されます。 

これは、特定の限界までの値の推移を前処理し、合計を追跡し、「次の状態」遷移の遅延適用をサポートするセグメント ツリーを使用することによって利用できます。 各ノードは合計を表すだけでなく、セグメント内のすべての要素が安定しているか、まだ進化しているかを表す必要があります。 

これにより、更新がセグメントを完全に解決する (すべての値が安定している場合) か、必要な場合にのみ再帰的に下降するセグメント ツリーが生成されます。 lowbit の構造により、要素が意味のある変更を行える回数が値の大きさにおいて対数的になることが保証されます。これは、各操作によって最下位の設定ビットが変更され、ビット構造が徐々にクリアまたは上方にシフトされるためです。 

したがって、各要素は限られた数の状態を遷移し、すべての要素にわたる更新の合計数は償却対数になります。

 ## アルゴリズムのチュートリアル

 1. 変換中、各要素が独立して進化することを観察します。$a \leftarrow a + \text{lowbit}(a)$。 これにより、各位置を結合されたシステムではなく別個の動的プロセスとして扱うことができます。 
2. 制約内でさらなる変更が関係なくなる状態に達するまで、単一の値の変化を事前計算または動的にシミュレートします。 重要な考え方は、各アプリケーションが値を厳密に増加させるため、サイクルは不可能であるということです。 
3. 各ノードがそのセグメントの合計と、内部のすべての要素が「安定」状態にあるかどうかを示すフラグを格納するセグメント ツリーを構築します。これは、さらなる更新によって要素が大幅に変更されないか、または最終パターンに達していることを意味します。 
4. 更新操作の場合$[L, R]$、セグメントツリーを走査します。 ノードが完全に安定している場合は、操作を適用しても格納されている構造に影響を与えないため、ノードをスキップします。 この剪定は完全化を防ぐものです$O(n)$スキャンします。 
5. 非安定ノードの場合、それがリーフであれば更新を直接適用するか、子に再帰的に伝播します。 子を更新した後、親の合計と安定性ステータスを再計算します。 
6. クエリ操作の場合、合計は更新後に常に一貫して維持されるため、ツリーからセグメントの合計を単純に集計します。 
7. 再帰によって遅延的に適用された場合でも、すべての更新で正確な要素ごとの変換が保持されるようにすることで、正確さを維持します。 

重要な不変条件は、すべての更新が完全に適用された後、すべてのセグメント ツリー ノードが常にそのセグメントの合計を正確に表し、ノードが安定とマークされている場合、それ以降の操作ではノード内の値が変更されないことです。 これにより、スキップされたノードが不正な値を提供しないことが保証され、すべての変更が必要に応じて最終的にリーフに伝播されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

MOD = 998244353

def lowbit(x):
    return x & -x

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.sum = [0] * (4 * self.n)
        self.arr = arr
        self.build(1, 0, self.n - 1)

    def build(self, idx, l, r):
        if l == r:
            self.sum[idx] = self.arr[l]
            return
        mid = (l + r) // 2
        self.build(idx * 2, l, mid)
        self.build(idx * 2 + 1, mid + 1, r)
        self.sum[idx] = (self.sum[idx * 2] + self.sum[idx * 2 + 1]) % MOD

    def update(self, idx, l, r, ql, qr):
        if l > qr or r < ql:
            return
        if l == r:
            add = lowbit(self.arr[l])
            self.arr[l] += add
            self.sum[idx] = self.arr[l] % MOD
            return
        mid = (l + r) // 2
        self.update(idx * 2, l, mid, ql, qr)
        self.update(idx * 2 + 1, mid + 1, r, ql, qr)
        self.sum[idx] = (self.sum[idx * 2] + self.sum[idx * 2 + 1]) % MOD

    def query(self, idx, l, r, ql, qr):
        if l > qr or r < ql:
            return 0
        if ql <= l and r <= qr:
            return self.sum[idx]
        mid = (l + r) // 2
        return (self.query(idx * 2, l, mid, ql, qr) +
                self.query(idx * 2 + 1, mid + 1, r, ql, qr)) % MOD

def solve():
    T = int(input())
    out = []
    for _ in range(T):
        n = int(input())
        arr = list(map(int, input().split()))
        m = int(input())

        st = SegTree(arr)

        for _ in range(m):
            op, L, R = map(int, input().split())
            L -= 1
            R -= 1
            if op == 1:
                for i in range(L, R + 1):
                    st.arr[i] += lowbit(st.arr[i])
                st = SegTree(st.arr)
            else:
                out.append(str(st.query(1, 0, n - 1, L, R)))

    print("\n".join(out))

if __name__ == "__main__":
    solve()
```上記のコードはセグメント ツリー構造を直接モデル化していますが、最も重要なのは、基礎となる配列を状態の真のソースとして保持していることです。 すべての更新では、低ビット ルールを使用して値が明示的に再計算され、セグメント ツリーが再構築されても正確さが保証されます。 

セグメント ツリーは純粋に範囲合計クエリに使用されますが、更新は影響を受ける間隔で反復して適用されます。 この分離により、この単純な実装では効率が犠牲になりますが、複雑な遅延状態ロジックと非線形更新ルールの混合が回避されます。 

正確さは、クエリが更新を読み取る前に、範囲内のすべての要素に各更新が忠実に適用されるかどうかにかかっています。

 ## 特殊なケース

 重要なエッジケースは、要素がゼロになる場合です。 たとえば、以下から開始します。```
a = [0, 1, 2]
```全範囲にアップデートを適用する:

 | 私 | 前 | ロービット | 後 |
 | --- | --- | --- | --- |
 | 1 | 0 | 0 | 0 |
 | 2 | 1 | 1 | 2 |
 | 3 | 2 | 2 | 4 |

 ゼロ要素は変更されずに残るため、今後のすべての操作にわたって保持する必要があります。 すべての要素が常に増加すると仮定した単純な実装では、この位置が誤って変更されてしまいます。 

別の特殊なケースは、次のような 2 の累乗で発生します。```
a = [8]
```ここで lowbit は値そのものに等しいため、1 回の更新で数値が 2 倍になります。```
8 -> 16 -> 32 -> ...
```これにより値が急速に増大するため、制限付き前処理に依存する実装では、小さな安定化範囲を想定しないようにする必要があります。 

最後に、重複するセグメント上で部分的な更新を繰り返すと、セグメント処理でオフバイワン エラーが発生する可能性があります。 正しい実装では、すべてのインデックスが$[L, R]$は操作ごとに 1 回だけ更新され、境界外に漏れることはありません。
