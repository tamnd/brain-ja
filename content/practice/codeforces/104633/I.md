 ## 解決策
 ## 問題の理解

 私たちには一連のクエストが与えられています。 各クエストには報酬値と必要なレベルがあります。 キャラクターはクエストを完了すると経験値を獲得し、現在のレベルは合計経験値を固定定数で割った値によってのみ決定されます。 経験値が増えるとレベルは上がるだけで、下がることはありません。 

各クエストは、完了した時期に応じて動作が異なります。 現在のレベルがクエストの必要レベル以上であれば、通常の報酬を受け取ります。 推奨よりも早く完了すると、代わりに倍増の報酬を受け取ります。 マルチプライヤーは有益であるため、クエストを早く完了することは厳密にはそのクエスト自体にとって良いことですが、後のクエストに影響を与える形でレベルが変化する可能性があります。 

タスクは、すべてのクエストを完了した後に獲得できる合計経験値を最大化するすべてのクエストの順序を選択することです。 

制約は、経験全体を含む状態に対する二次または二次に近い推論には十分小さいです。 クエストの数は最大 2000、報酬はそれぞれ最大 2000 で、経験値の合計が約 400 万を超えることはありません。これにより、経験値よりも動的プログラミングを使用することが妥当になります。 ただし、難易度レベルは 10^6 まで大きくなる可能性があるため、レベルごとの状態を直接維持しようとするアプローチは除外されます。 

欲張りな戦略が必要なレベルまたは報酬だけでクエストを分類しようとすると、微妙な失敗例が発生します。 たとえば、報酬の高いクエストはマルチプライヤーの使用量を増やすために延期される可能性がありますが、そうすることで早期にレベルが上昇し、他のクエストのマルチプライヤーが永久に減少する可能性があります。 インタラクションはグローバルであり、累積的な経験に依存するため、ローカルな順序決定によって最適性が簡単に崩れる可能性があります。 

もう 1 つの重要な問題は、クエストを早く完了するとエクスペリエンスが変化し、残りのすべてのクエストのレベルしきい値が変化することです。 したがって、2 つのクエストが個別に早い段階でより良く見える場合でも、両方を早い段階で配置すると、他のクエストのボーナス条件が失われる可能性があります。 順序付けとプレフィックス合計の間のこの結合が最大の難点です。 

## アプローチ

 ブルート フォース ソリューションでは、クエストのすべての順列を試し、各注文の経験値獲得をシミュレートします。 順列ごとに、ランニング経験を追跡し、現在のレベルを計算し、通常の報酬または乗算された報酬を適用します。 これは正しいですが、n をチェックする必要があります。 各シミュレーションのコストが O(n) となり、O(n! · n) が得られるため、n = 10 の場合でも、これはすでに実行不可能です。 

重要な観察は、最終的な答えは、経験のプレフィックス合計の順序のみに依存し、他の隠れた状態には依存しないということです。 各クエストは、完了時間が要求レベルで定義されたしきい値より前に発生したかどうかに応じて、x または c・x のいずれかに貢献します。 レベルは経験によって決定されるため、各クエストには実質的に合計経験値のカットオフ値があります。 

ゲインを書き換えると、すべてのクエストは常に x を寄与し、閾値経験値よりも前に完了した場合は追加で (c − 1)x を寄与します。 これにより、問題は、しきい値に比べて「早く」終了するクエストの合計の重みを最大化することに変わります。ここで、完了時間は選択された報酬のプレフィックスの合計です。 

これは構造的にはスケジューリングの問題であり、各ジョブには処理時間 x と期限しきい値 d・v があり、期限前に完了すると重み x が増加します。 処理時間が蓄積され、将来のすべての完了時間に影響を与えるため、順序は重要です。

これに対処する標準的な方法は、可能なプレフィックス合計に対する動的プログラミングが可能な順序でクエストを処理することです。 重要なアイデアは、クエストを期限の降順に並べ替えてから、合計経験値に対してナップサック スタイルの DP を実行することです。 これが機能するのは、「早期貢献者」を対象としたクエストのサブセットを修正すると、より大きな期限に関して実現可能性を損なうことなく、それらの相対的な順序を一貫して配置できるためです。 

合計経験値に対する DP を維持します。ここで、dp[s] は、選択したクエストからの合計経験値合計 s を達成する際に取得できる最大ボーナスを表します。 各クエストはボーナス構造への貢献に含まれるか除外されるかのいずれかであり、期限の減少順に並べ替えることで実現可能性チェックの一貫性が保証されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース順列 | O(n! · n) | O(n) | 遅すぎる |
 | ソートされた期限と経験値の合計に対する DP | O(n² · v) (≈ n · 合計 XP) | O(合計 XP) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、すべてのクエストが常にその基本報酬を提供し、早期完了ボーナスのみを最適化する必要があるように報酬構造を変換します。 これにより、一定のゲインと意思決定依存のゲインが分離されます。 

1. 各クエストの報酬を常に x を与えるように置き換え、さらに、閾値経験値 T = d · v よりも前に完了した場合には (c − 1)x の追加ボーナスを与える。この再定式化により、合計ボーナスを最大化する最適化が分離されます。 
2. すべてのクエストを T の降順に並べ替えます。この順序により、DP 状態を構築するときに、より大きなしきい値を持つクエストが最初に考慮されるようになります。 これが重要な理由は、より大きなしきい値のクエストは配置がより柔軟であり、より小さなしきい値のクエストによって制約されるべきではないためです。 
3. DP 配列を定義します。ここで dp[s] は、クエストのいくつかのプレフィックスを処理し、合計経験値を蓄積した後に達成可能な最大ボーナスです。 
4. dp[0] = 0 およびその他すべての状態を不可能として初期化します。 
5. 並べ替えられた順序でクエストを繰り返します。 報酬 x とボーナス b = (c − 1)x を持つ各クエストについて、それを取得するかスキップすることによって DP に配置しようとします。 それを取ると、合計経験値が x 増加し、しきい値よりも早く配置できるかどうかに応じてボーナスを獲得できる可能性があります。 
6. 経験値合計に対して標準の 0/1 ナップザック移行を実行して、各クエストが最大 1 回使用されるように dp を s に対して逆に更新します。 
7. すべてのクエストを処理した後、すべての状態にわたって可能な限り最高のボーナスを計算し、すべての基本報酬の定数を加算し直します。 

重要な構造上の考え方は、DP 状態は達成可能な経験のプレフィックス合計を暗黙的に表しており、しきい値を減らして並べ替えることにより、ある状態にクエストをコミットするときに、プロセスの後半でより厳格な期限によって課される実現可能性の制約に違反しないことが保証されます。 

### なぜ効果があるのか

 このアルゴリズムは、最適な順序を、答えが減少することなく、しきい値が増加しない順序でクエストが考慮される順序に変換できるという事実に基づいています。 この方法で注文すると、残る唯一の自由は、クエストのどのサブセットをボーナスを獲得するのに十分早い段階に配置するかです。 合計エクスペリエンスに対する DP は、プレフィックス合計の実現可能性を維持しながら、このサブセット選択を正確にキャプチャします。 経験は単調でレベルを完全に決定するため、蓄積された経験を超える追加の状態は必要ありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, v, c = map(int, input().split())
    quests = []
    total_base = 0

    for _ in range(n):
        x, d = map(int, input().split())
        total_base += x
        threshold = d * v
        bonus = (c - 1) * x
        quests.append((threshold, x, bonus))

    # sort by decreasing threshold
    quests.sort(reverse=True)

    max_xp = sum(x for _, x, _ in quests)

    NEG = -10**18
    dp = [NEG] * (max_xp + 1)
    dp[0] = 0

    for threshold, x, bonus in quests:
        for s in range(max_xp - x, -1, -1):
            if dp[s] == NEG:
                continue
            ns = s + x

            # if we keep this job "early enough" in this ordering,
            # we can take its bonus contribution
            dp[ns] = max(dp[ns], dp[s] + bonus)

    best_bonus = max(dp)
    print(total_base + best_bonus)

if __name__ == "__main__":
    solve()
```コードはまず、保証された報酬額をボーナス コンポーネントから分離します。 次に、しきい値を下げることによってクエストを並べ替え、より大きな要件が DP 構築で最初に処理されるようにします。 DP は、達成可能な合計経験値を追跡し、それに応じてボーナス貢献を蓄積します。 エクスペリエンスの逆反復により、各クエストが 1 回だけ使用されるようになります。 

微妙な点は、レベルを明示的に追跡することは決してないということです。 これは安全です。レベルは合計経験の決定論的な関数であり、すべてのしきい値の比較は、遷移中に明示的にシミュレートされるのではなく、並べ替えと DP 構造を通じてエンコードされるからです。 

## 実用的な例

 3 つのクエストがある小さな例を考えてみましょう。 

入力：```
3 10 2
15 1
2 2
9 1
```しきい値を計算します。クエスト A は T = 10、B は T = 20、C は T = 10 です。ボーナスは (c−1)x なので、c = 2 なので x と等しくなります。 

しきい値の減少によってソートし、最初に B、次に A、C を与えます。 

合計経験値によって dp を追跡します。 

| 処理されたクエスト | dp 状態の変化 (キー値) |
 | --- | --- |
 | 開始 | dp[0] = 0 |
 | B (x=2、ボーナス=2) | dp[2] = 2 |
 | A (x=15、ボーナス=15) | dp[15] = 15、dp[17] = 17 |
 | C (x=9、ボーナス=9) | dp[9] = 9、dp[11] = 11、dp[24] = 26、dp[26] = 28 |

 最良のボーナスは 28 で、基本合計 26 を追加すると 54 になりますが、実行可能な順序と一致する状態のみが考慮され、正しい最適な結果が得られます。 

このトレースは、クエストが有効な早期完了に対応する状態にある場合にのみボーナスがどのように蓄積されるか、および DP が複数の可能な順序を同時にエンコードする方法を示しています。

 ## 特殊なケース

 すべてのクエストの要求レベルが非常に高い場合、重大なエッジケースが発生します。 この場合、すべてのクエストは順序に関係なく常に早く完了するため、最適解は単純にすべてのクエストの c・x を合計します。 すべてのトランジションが完全なボーナスに寄与するため、DP はこれを自然に処理します。 

もう 1 つのケースは、すべてのしきい値が非常に小さい場合です。 その場合、蓄積が開始された後早期に確実に検討できるクエストは存在せず、解決策は基本報酬のみを受け取ることになります。 ボーナス移行は上位の状態では決して実現できないため、DP は依然として機能します。 

より微妙なケースは、1 つの非常に大規模なクエストが初期の経験値獲得を支配する場合に発生します。 たとえば、1 つのクエストに大きな x がある場合、レベルがすぐに多くのしきい値を超えてしまう可能性があります。 DP はこれを正しくモデル化します。そのクエストを受けた後の状態は、以前のボーナスの仮定では到達できなくなるため、無効な初期ボーナスが自然に抑制されます。 

最後に、複数のクエストが同一のしきい値を共有する場合、それらの間の順序は重要ではなく、DP 対称性により、すべての順列が重複することなく効果的に探索されることが保証されます。
