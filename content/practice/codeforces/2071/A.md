 ## 解決策
 ## 問題の理解

 3 人のプレーヤーが、ちょうど 2 人がアクティブで 1 人が観戦している試合を繰り返しプレイします。 役割の割り当ては、2 つのルールを使用して前の試合から決定的に展開されます。 誰かがすでに 2 試合連続でプレーしている場合、その人は次の試合から欠場することを余儀なくされます。 それ以外の場合は、勝者と前の観客が次の試合のプレイヤーとなり、敗者が観客になります。 

私たちはプレイヤーのアイデンティティをシミュレートするように求められません。 重要なのは、特定のプレーヤー、つまり最初の試合の観客の立場だけです。 各クエリ インデックス k について、ゲームの有効な展開の下で、この同じプレーヤーが k 番目の試合の観客にもなれるかどうかを判断する必要があります。 

この制約により、k は最大 10^9 まで許容されるため、照合を段階的に明示的にシミュレートするアプローチは直ちに実行不可能になります。 線形シミュレーションでは、テスト ケースごとに最大 10 億回の遷移が必要になりますが、これは 1000 個のクエリでも時間制限をはるかに超えています。 

重要な隠された構造は、試合の結果には分岐が導入されるが (勝者が変わる可能性があるため)、観客の役割は「3 連続プレー禁止」ルールによって引き起こされる厳密な周期的制約によって進化するということです。 これにより、最初の試合の観客に対してシステムが強制的に短いサイクルになります。 

エッジケースは主に小さな k 値に関するものです。 k = 1 の場合、答えは明らかです。 k = 2 の場合、正確に 2 人のプレーヤーがプレーしなければならないため、最初の試合の観客は観客のままでいられず、その観客はすぐに強制的にプレーを始めます。 この強制参加を無視した推論は、k = 2 で即座に破綻します。 

## アプローチ

 ブルートフォースアプローチでは、元の観客がまだその役割を果たしているかどうかを追跡しながら、考えられるすべての試合状態をシミュレートします。 各状態は、最後の 2 つまたは 3 つの試合構成と観客のアイデンティティによって異なります。 勝者が固定されていないため、これは分岐プロセスとなり、試合数が爆発的に増加する可能性があります。 

単純化して単一の決定論的なシーケンスのみを追跡したとしても、クエリごとに最大 k 個の遷移を計算する必要があります。 k が 10^9 までの場合、これは不可能です。 

重要な点は、すべてのプレイヤーの完全な ID 追跡は必要ないということです。 少なくとも 1 つの有効な進化において、指定された 1 人のプレーヤーが時刻 k で観客の役割を占めることができるかどうかを知る必要があるだけです。 これにより、問題は、最近の参加パターンによって決定される非常に小さな状態空間における到達可能性の分析に集約されます。 

どのプレイヤーも 3 試合連続でプレーすることを禁止するルールにより、役割の定期的な交代が強制されます。 最初のいくつかの遷移を展開した後、システムは期間 3 の観客参加の繰り返しパターンに安定します。有効なシーケンスを直接検査すると、試合 1 の観客は 1 の法 3 に一致する位置でのみ観客として再出現できることがわかります。 

これにより、問題がシミュレーションからモジュラー演算に変換されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | テストあたり O(k) | お(1) | 遅すぎる |
 | 周期観測 | テストごとに O(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

1. 最初の数試合を観察し、最初の試合の観客の観客の役割のみを追跡します。 私たちはプレーヤーの完全な身元を追跡するのではなく、そのプレーヤーが観戦者のままであるか、強制的にプレーに参加させられているかどうかのみを追跡します。 
2. マッチ 1 からマッチ 2 まで、試合ごとに 1 人のプレーヤーだけがアイドル状態であり、役割の制約により交代が強制されるため、観客は参加する必要があります。 これにより、有効な観客の位置として k = 2 が除外されます。 
3. さらにいくつかのステップで推論を続けます。 2 回プレイしたプレーヤーは次の席から外さなければならないため、システムは各プレーヤーが最大 2 回連続して参加し、その後強制休憩を挟むという厳格なローテーションを強制します。 
4. このパターンを十分なステップ分拡張すると、観客の役割が 3 試合ごとに循環する繰り返し構造が観察されます。 
5. 最初の試合の観客は、k ≡ 1 (mod 3) である試合 k に正​​確に現れると結論付けます。 

機能する理由: 観客のアイデンティティに関連するシステムの状態は、「3 連続試合禁止」ルールにより、長さ 2 の制限された履歴によって完全に決定されます。 これにより、到達可能な状態がわずかしかない有限オートマトンが生成されます。 単一の進化する役割シーケンス上の有限オートマトンは最終的に周期的になる必要があり、直接列挙すると、インデックス 1 での初期アライメントで周期が 3 であることが示されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    k = int(input())
    if k % 3 == 1:
        print("YES")
    else:
        print("NO")
```実装では、周期性の結果が直接適用されます。 各テスト ケースは独立しており、必要なモジュロ演算は 1 つだけです。 

唯一微妙な点はアライメントです。 最初の試合は k = 1 としてインデックス付けされ、この位置では観客は自明のことながら同じプレイヤーであるため、正しい合同クラスは 0 モジュロ 3 ではなく、1 モジュロ 3 です。 

## 実用的な例

 サンプル入力を考えてみましょう。 

k = 1、2、333、1e9 の場合、k を 3 を法として評価します。 

| k | k mod 3 | 結果 |
 | --- | --- | --- |
 | 1 | 1 | はい |
 | 2 | 2 | いいえ |
 | 333 | 0 | いいえ |
 | 1000000000 | 1 | はい |

 最初のケースは基本条件を確認します。 2 番目のケースは、最初の試合後の強制ブレークを示しています。 3 番目と 4 番目のケースは、モジュラー位置のみが問題となる、大きなインデックスにわたる周期構造を示しています。 

## 複雑さの分析

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    t = int(input())
    out = []
    for _ in range(t):
        k = int(input())
        out.append("YES" if k % 3 == 1 else "NO")
    return "\n".join(out)

# provided samples
assert run("4\n1\n2\n333\n1000000000\n") == "YES\nNO\nNO\nYES"

# minimum case
assert run("1\n1\n") == "YES"

# second position always fails
assert run("1\n2\n") == "NO"

# periodic checks
assert run("3\n3\n4\n5\n") == "NO\nYES\nNO"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 | はい | 基本ケース k = 1 |
 | 2 | いいえ | 即時遷移制約 |
 | 3、4、5 | いいえ、はい、いいえ | 周期性の一貫性 |

 ## 特殊なケース

 k = 1 の場合、観客は自明のことながら初期観客と同じであるため、遷移が適用されなければ出力は YES になります。 モジュロ ルールは正しく 1 mod 3 = 1 を生成します。 

k = 2 の場合、システムは前の観客を積極的にプレイさせるため、答えは NO でなければなりません。 ルール k % 3 = 2 はこれを直ちに確認します。 

k = 3 の場合、複数の進化が可能であっても、観客の役割はすでに元の観客から離れているため、答えは NO のままです。 モジュロ条件 k % 3 = 0 はこれを正しく除外します。 

k = 4 の場合、このサイクルによりアライメントがリセットされ、元の観客が観客として再出現できる状態にシステムが戻り、k % 3 = 1 に一致します。
