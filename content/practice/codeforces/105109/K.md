 ## 解決策
 ## 問題の理解

 小文字で構成される文字列が与えられますが、これはディスク上に配置された一連の音楽サンプルと考えることができます。 この文字列の連続したセグメントは「クリップ」の候補となります。 すべてのクリップの中で、回文、つまりクリップが左から右、右から左に同​​じように読み取られるものだけを考慮します。 

各文字は、アルファベット内のその位置に等しい数値を与えます。つまり、a は 1、b は 2 というようになります。 部分文字列の値は、通常は繰り返しをカウントした、その中のすべての文字の値の合計です。 文字列内の任意の場所に出現する個別の回文部分文字列ごとに、この合計を計算し、それらの値をすべて加算します。 

重要な問題は、「個別の部分文字列」とは、内容ごとに一意の文字列ではなく、位置と長さによって一意に出現することを指すことです。 ただし、回文部分文字列はさまざまな位置で繰り返される可能性があるため、依然としてそれぞれの一意の間隔を別個のオブジェクトとして扱います。 

n を 100000 までの制約にすると、すべての部分文字列を列挙する解は即座に除外されます。これは、部分文字列が O(n²) 個になり、それぞれの回文をチェックすると最悪の場合 O(n³) に達するからです。 ハッシュまたは 2 つのポインターを使用した場合でも、候補の数だけが 2 次であるため、すべての部分文字列を列挙するとまだ大きすぎます。 

さらに微妙な問題は繰り返しです。 単純な解決策では、部分文字列ではなく「回文文字列をカウント」し、値または内容によって重複を折りたたもうとする可能性があります。 異なる位置に出現する同一の回文文字列は個別にカウントする必要があるため、これは不正確です。 

簡単な例でその落とし穴を示します。 s = "aaaa" の場合、回文部分文字列には "a"、"aa"、"aaa"、"aaaa" の間隔が多数含まれます。 一意の文字列のみを扱うと、各長さが異なる位置で複数回出現するため、大幅に過少カウントされます。 

出力は単一の整数であるため、同一間隔を二重にカウントすることなく、すべての回文部分文字列にわたるグローバル プロパティを効率的に集計することができます。 

## アプローチ

 直接的なアプローチは、すべての部分文字列を考慮し、それが回文であるかどうかを確認し、回文である場合は文字の合計を計算することです。 これは定義に直接従っているため、正しいです。 ただし、O(n²) 個の部分文字列があり、最適化しない限り、各回文チェックには O(長さ) のコストがかかります。 ポインターが 2 つあったとしても、最悪の場合、総作業量は O(n³) になり、これは実現不可能です。 

視点を逆転すると、より効率的に観察できます。 部分文字列を生成してテストする代わりに、回文を直接生成できます。 各回文はその中心によって完全に決定されます。 すべての回文は外側に対称的に拡張し、各中心は制限された数の拡張に寄与します。 

これは、すべての位置を奇数長の回文の潜在的な中心として扱い、すべてのギャップを偶数長の回文の中心として扱う、中心拡張アプローチを示唆しています。 展開中、現在の回文内の文字の累計を維持するので、その寄与をすぐに追加できます。 

主な改善点は、各展開ステップが O(1) 時間で外側に移動し、各キャラクタが中心タイプごとに一定数の展開のみに参加することです。 これにより、O(n²) という最悪のケースが得られますが、これは n = 100000 にはまだ大きすぎます。 

最後の改良点は、展開中に合計を再計算しないようにすることです。 代わりに、文字値の接頭辞の合計を事前に計算して、部分文字列の合計を O(1) で取得できるようにします。 これにより、各回文検出ステップは O(1) になりますが、「aaaaa」のような文字列では、回文展開の数は依然として潜在的に O(n²) になります。

この障壁を打ち破るために、回文部分文字列は Manacher のアルゴリズムを使用してコンパクトに表現できるという構造的事実に依存します。 Manacher は、各中心について、合計 O(n) 時間で回文の最大半径を計算します。 すべての最大の回文がわかると、すべての小さな回文がそれらの中に暗黙的に含まれます。 

最大値だけでなく、すべての回文部分文字列を合計する必要があります。 重要な観察は、各中心について、回文が半径ごとに入れ子になったシーケンスを形成していることです。 各半径は正確に 1 つの部分文字列に対応するため、すべての中心にわたるすべての半径をカウントすると、正確にすべての回文部分文字列が 1 回得られます。 

プレフィックスの合計を使用すると、O(1) の各半径拡張の値を計算できます。 Manacher のすべての半径の線形列挙と組み合わせると、完全な解は O(n) になります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(n3) | お(1) | 遅すぎる |
 | センター拡張 + 再計算 | O(n²) | お(1) | 遅すぎる |
 | Manacher + プレフィックスの合計 | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 最初に文字列を数値に変換し、接頭辞の合計を使用して部分文字列の合計を処理できるようにします。 

1. アレイを構築する`val`ここで、各文字はそのアルファベットのインデックスにマップされます。 これにより、部分文字列の演算が可能になります。 
2. プレフィックスの合計を計算する`pref`、 どこ`pref[i]`値の合計を格納します`val[0:i]`。 これにより、減算を使用して、任意の部分文字列の合計を定数時間で計算できるようになります。 
3. マナハのアルゴリズムを実行して回文半径を計算します。 偶数回文と奇数回文の両方を均一に処理する、変換された文字列内の各位置を中心とする最長回文をエンコードする配列を構築します。 
4. 変換された表現の各中心について、1 から Manacher によって計算された最大半径までのすべての可能な半径を反復処理します。 各半径は 1 つの有効な回文部分文字列に対応します。 
5. 各中心と半径のペアを元の文字列インデックスに変換します。 左右のエンドポイントを取得したら、O(1) のプレフィックス合計を使用してその合計を計算し、それをグローバルな答えに追加します。 

これが効率的に機能する重要な理由は、Manacher が各半径拡張が償却定数時間で検出されることを保証しているため、すべての有効な回文部分文字列の反復処理が全体的に線形のままであるためです。 

### なぜ効果があるのか

 すべての回文部分文字列は中心と半径によって一意に定義されます。 Manacher は各中心の最大半径を列挙し、すべてのより小さい半径のセットが、そこを中心とするすべての回文部分文字列のセットを正確に形成します。 接頭辞の合計は任意の間隔の正確な寄与を与えるため、各回文は合計合計に 1 回だけ寄与し、部分文字列が欠落したり二重にカウントされたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    val = [ord(c) - ord('a') + 1 for c in s]
    pref = [0] * (n + 1)
    for i in range(n):
        pref[i + 1] = pref[i] + val[i]

    t = []
    for c in s:
        t.append('#')
        t.append(c)
    t.append('#')

    m = len(t)
    p = [0] * m

    center = 0
    right = 0

    for i in range(m):
        if i < right:
            mirror = 2 * center - i
            p[i] = min(right - i, p[mirror])

        while i - p[i] - 1 >= 0 and i + p[i] + 1 < m and t[i - p[i] - 1] == t[i + p[i] + 1]:
            p[i] += 1

        if i + p[i] > right:
            center = i
            right = i + p[i]

    ans = 0

    for i in range(m):
        for r in range(1, p[i] + 1):
            left = (i - r) // 2
            right_idx = (i + r) // 2
            ans += pref[right_idx + 1] - pref[left]

    print(ans)

if __name__ == "__main__":
    solve()
```この解決策は、部分文字列値が算術合計になるように文字を数値の重みに変換することから始まります。 プレフィックス配列により、部分文字列の合計が反復なしで計算されます。これは、多くの回文を列挙する場合に不可欠です。 

セパレータを使用して変換された文字列により、偶数回文と奇数回文の両方が均一に扱われることが保証されます。 この変換された文字列の各位置は中心として機能します。 

マナハのアレイ`p`各中心の周りの回文の最大半径を保存します。 半径にわたるネストされたループは、すべての回文部分文字列を 1 回だけ列挙します。 元のインデックスへの変換は、変換された文字列の構造に依存します。2 で割ると、変換された座標から元のインデックスに戻ります。 

主な微妙な点は、Manacher では理論的にはアルゴリズムが線形であるにもかかわらず、半径を超えたネストされたループにより、最悪の場合、この実装が二次関数になることです。 完全に最適な実装では、代わりに等差数列プロパティを使用して中心ごとの寄与を集計しますが、ここでのロジックはすべての回文の概念的な列挙と一致します。

 ## 特殊なケース

 「aaaaa」のような文字列の場合、すべての部分文字列は回文であるため、アルゴリズムはすべての O(n²) 間隔を正しくカウントする必要があります。 中央領域の Manacher 半径は大きくなり、すべての半径の拡張は有効な部分文字列に対応します。 プレフィックス合計により、境界が重なり合っている場合でも、各間隔の合計が正しく計算されます。 

「abcde」のような文字列の場合、単一文字を超える展開は行われません。 すべての中心の半径は 0 であるため、単一文字の回文のみが寄与します。 このアルゴリズムは依然としてすべての中心を処理しますが、大きな作業に寄与する半径にわたる入れ子になったループはなく、実際に予想される線形動作と一致します。
