 ## 解決策
 ## 問題の理解

 曲のコレクションが与えられます。各曲には 2 つのプロパティがあります。1 つはタイトルの長さから得られるバイト単位で測定されるストレージ コスト、もう 1 つは報酬値です。 アンバーには、バイト単位の固定容量を持つデジタル ヴァイナルがあります。 彼女は任意の曲をレコードに何度も置くことができ、各コピーはそのコストをバイト単位で提供し、その価値を報酬総額に再度追加します。 

タスクは、合計使用バイト数が容量を超えないようにしながら、合計の累積値を最大化するように、保存する各曲のコピー数を選択することです。 

これは古典的な無制限の選択問題ですが、「重み」は直接与えられません。 代わりに、各アイテムの重みは暗黙的にその文字列の長さとなり、その長さは長くなる可能性があります。 曲全体のすべての文字列の長さの合計には制限があるため、これらの重みの計算は全体として線形時間で実行可能です。 

主な問題点は、最大 2 · 10^5 の容量を超える単純な動的プログラミングは境界線にあるものの、まだ実行可能であることですが、実際の制約は、問題が比較的小さい容量の無制限のナップザックにきれいに縮小されることを認識していることです。 

この制約は、O(nm) より悪い解は失敗することを意味します。 n と m は両方とも 2・10^5 までであるため、2 次アプローチは不可能です。 最悪の場合は O(nm) でも大きすぎますが、ここでは各項目が 1 回処理されるため、O(nm) のナップザックは慎重に実装された場合にのみ許容され、隠れた余分な要素が出現しないようにする必要があります。 

曲の長さが非常に短い場合 (たとえば 1 バイト)、微妙なエッジ ケースが発生します。 その場合、最適な解決策には、最大 m 回実行することが含まれる可能性があります。 値と長さの比率のみに基づく貪欲なアプローチは、項目を混合すると局所的に最適な選択が支配される可能性があるため、安全ではありません。 

## アプローチ

 強引な解釈では、各曲の可能なカウントをすべて試し、基本的に容量内に収まる繰り返しのすべての組み合わせを探索します。 曲を最大 m 回繰り返すことができ、曲が n 個ある場合、すべての選択肢が多くの可能なカウントに分岐するため、指数関数的な検索スペースが生じます。 曲ごとの繰り返しを制限したとしても、最悪の解釈では m^n に比例する状態爆発が発生しますが、これは完全に実行不可能です。 

より構造化されたブルート フォースでは、これを標準的なナップザック動的プログラミングの問題として扱います。 dp[x] を、正確に x バイトを使用して達成できる最大値として定義します。 曲ごとに、すべての容量を繰り返し、追加を複数回試みます。 ただし、この単純な定式化は、実装が不十分な場合、項目ごとに O(nm) になります。これは、各曲がネストされたループ内のすべての状態を繰り返し更新するためです。 

重要な点は、各曲が独立しており、無制限に使用できるため、容量 m の無制限のナップザックを扱っていることです。 各項目のコストは文字列の長さであり、その値が指定されます。 これにより、容量を小さいものから大きいものまで反復し、各曲を 1 回使用して更新する標準の 1D DP が可能になります。 これが機能するのは、一度曲を処理すると、同じ DP パス内でそれを再利用して複数のコピーを許可できるためです。 

これにより、問題は、各項目が線形時間ですべての容量にわたる遷移に寄与するクリーンな最適化構造に分解されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース列挙 | 指数 | お(1) | 遅すぎる |
 | アイテムごとに素朴な繰り返しのナップサック | アイテムあたり O(nm) | O(m) | 遅すぎる |
 | 無制限のナップザック DP | O(nm) | O(m) | 承認済み |

 ## アルゴリズムのチュートリアル

 各曲を、タイトルの長さに等しい重みと、指定されたスコアに等しい値を持つアイテムとして扱います。

1. すべての曲タイトルの長さを計算します。 これは、その曲を 1 回使用するコストを定義します。 この問題では重みが明示的に与えられるのではなく文字列内に隠蔽されるため、この手順が必要です。 
2. ゼロで初期化されたサイズ m + 1 の DP 配列 dp を作成します。 dp[x] は、正確に x バイト以下を使用して達成可能な最良の値を表します。 以前と現在の状態のみが必要なため、1D のままにします。 
3. 各曲について、その重みから m までの容量を昇順に繰り返します。 各容量 c で、dp[c - 重み] + 値を使用して dp[c] の改善を試みます。 この遷移は、より小さい容量ですでに有効な状態に達した後、曲のコピーをもう 1 つ取得することを表します。 
4. 新しい値が大きい場合は、dp[c] を更新します。 これにより、各容量に対して最もよく知られた組み合わせが常に維持されるようになります。 
5. すべての曲を処理した後、答えは 0 から m までのすべての容量の最大値です。 容量を正確に埋める必要がないため、これが必要になります。 

容量を昇順に繰り返す理由は重要です。 これにより、1 回の反復で同じ曲を複数回再利用できます。 逆に繰り返すと、各曲の使用を最大 1 回に制限することになり、問題は 0/1 ナップザックになりますが、これはここでは正しくありません。 

### なぜ効果があるのか

 DP は、最初の k 曲を処理した後、容量 c 内でそれらの k 曲の無制限のコピーを使用して達成可能な最大値が dp[c] に含まれるという不変条件を維持します。 各アップデートでは、現在の曲の追加コピーが 1 つ追加されることで、有効な設定が正しく拡張されます。 遷移は dp[c -weight] のみに依存するため、以前に計算されたすべての最適な状態は有効なままであり、将来の状態によって過去の最適な部分構造が無効になることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    
    dp = [0] * (m + 1)
    
    for _ in range(n):
        parts = input().rstrip().split()
        s = parts[0]
        v = int(parts[1])
        w = len(s)
        
        if w > m:
            continue
        
        for c in range(w, m + 1):
            val = dp[c - w] + v
            if val > dp[c]:
                dp[c] = val
    
    print(max(dp))

if __name__ == "__main__":
    solve()
```このソリューションでは、単一の DP 配列を使用して、達成可能な最良の値を保存します。 各曲は 1 回だけ処理され、繰り返し使用できるように各曲ごとに容量が拡張されます。 重みが m より大きい曲を早期にスキップすることで、不必要な作業が回避されます。 

一般的な実装の落とし穴は、容量を間違った方向に反復することです。 m から w まで繰り返すと、各曲は 1 回だけ使用され、無制限の要件を破ります。 もう 1 つの微妙な点は、部分的な容量の使用が許可されているため、最後にすべての dp 状態の最大値を取得することです。 

## 実用的な例

 ### サンプル 1

 入力:```

Creep 1

```関連するアップデートでのみ dp を追跡します。 

| 歌 | 重量 | 値 | 容量の更新 (主要な状態) |

 | クリープ | 5 | 1 | dp[5]=1、dp[6]=1、dp[7]=1 |
 | ホテルカリフォルニア | 15 | 2 | 無視 (体重 > m) |
 | 1 | 3 | 3 | dp[3]=3、dp[6]=6、dp[7]=6 |

 最終的なdpの最大値は6です。 

このトレースは、短い曲「One」が限られた容量内で繰り返し可能であるという点でどのように優位を占めているかを示しています。 

### サンプル 2

 入力:```
5 30
BohemianRhapsody 20
HeyJude 12
DancingQueen 19
PurpleHaze 23
commatose 52
```「commatose」だけが、繰り返し可能な有用な重みと値の組み合わせを持っています。 

| 歌 | 重量 | 値 | 主な効果 |
 | --- | --- | --- | --- |
 | ボヘミアンラプソディ | 17 | 20 | 限られた組み合わせに貢献します |

合計 = 52 × 3 = 156。 

この例は、価値密度の高いアイテムが繰り返し再利用されることにより DP を通じて自然に伝播することを示しています。

| スペース | O(m) | 容量を超える単一 DP アレイ |

 ## 特殊なケース

 重要なエッジ ケースは、曲の長さが 1 の場合です。その場合、すべての DP 状態は継続的に改善され、最終的な答えは値の m 倍になります。 順方向反復により、明示的なカウントを必要とせずに、各状態が繰り返し使用を正しく蓄積することが保証されます。 

もう 1 つのエッジ ケースは、すべての曲が容量を超える場合です。 遷移が発生しないため、DP はすべて 0 のままであり、出力は正確に 0 になります。 

3 番目のケースは、複数の曲が同じ長さだが値が異なる場合です。 DP は当然、より高い値の遷移を好み、上書きを繰り返すことで、容量全体にわたって最適な組み合わせのみが確実に残ります。
