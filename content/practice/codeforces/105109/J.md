 ## 解決策
 ## 問題の理解

 ボブは、1 から n までの番号が付けられたレコードのコレクションを持っています。 次の n 日間、彼はこれらのレコードの一部を毎日聴きます。 ボブがそれ以前の日に一度も聴いたことがないレコードは、その日に新しいとみなされます。 

私たちは毎日、その日に演奏されたレコードのうち、ボブの全聴取履歴の中で初めて登場するレコードが何枚あるかを気にしています。 タスクは、全日にわたるそのような「新しいレコード数」の最大値を決定することです。 

入力は、一連の n 日のリスニング ログです。 各ログには、その日に再生されたレコード ID のリストが表示されます。 レコードは 1 日内または数日にわたって繰り返すことができますが、各レコードの最初に出現した日のみが「新規」カウントに影響します。 

出力は単一の数値、つまり 1 日に出現した未確認のレコードの最大数です。 

制約は小さく、n は最大 1000、記録された再生の総数は最悪の場合でも最大 10^6 です。 これは、Python では 2 秒の制限内で約 10^6 の操作が安全であるため、O(合計エントリ) または O(n^2) のシミュレーションで十分であることを直ちに示唆しています。 

微妙な点は、1 日内の重複によってカウントが膨らむべきではないということです。 レコードが同じ日に複数回出現する場合でも、全体として初めて出現する場合は、「新規」として 1 回だけ寄与します。 

2 番目の微妙な点は、レコードをその日の処理後にのみグローバルに表示されるものとしてマークする必要があることです。そうしないと、同じ日内の重複が誤って早期に抑制される可能性があります。 

## アプローチ

 直接的なアプローチは、ボブがすでに聞いたすべてのレコードのグローバル セットを維持しながら、プロセスを毎日シミュレートすることです。 毎日、m 個のエントリすべてをスキャンし、グローバル セットに含まれていないエントリの数を数えます。 まだ見ていないレコードに遭遇するたびに、その日のカウントをインクリメントし、それを既読としてマークします。 

これが機能するのは、「新しい」の定義が、当日のレコードの位置ではなく、そのレコードが前日に出現したかどうかのみに依存するためです。 必要な唯一の注意は、同じレコードがその日のリストで繰り返される場合、1 日に複数回カウントしないようにすることです。 これは、1 日あたりの一時的なセットによって、またはグローバルに 1 回のみマークし、同じ日内のその後の繰り返しを無視することによって処理できます。 

ブルート フォース動作は構造的にすでに最適化されています。各レコードは、最初に新規として検出されたときに 1 回処理されるため、グローバル セットへの有効な挿入の総数は n によって制限されます。 オーバーヘッドはすべてのエントリをスキャンすることであり、これは最大 10^6 の操作であり、十分に制限内です。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | グローバル セットを使用してスキャン | O(合計m) | O(n) | 承認済み |
 | 1 日あたりのネストされたチェック | O(n * m) 最悪 | O(n) | 受け入れられるが不要なオーバーヘッド |

 ## アルゴリズムのチュートリアル

 1. 前日にすでに出現したすべてのレコードを格納する空のセットを初期化します。 このセットは、ボブのリスニングの世界的な歴史を表しています。 
2. 変数の答えを 0 に初期化します。これにより、1 日に観察された新しいレコードの最大数が追跡されます。 
3. 毎日、再生されたレコードのリストを読みます。 
4. その日について、カウンター day_new を 0 に初期化します。 
5. その日のリストの各レコードを繰り返し処理します。 記録が未公開の場合は、これが初登場であることを意味します。 day_new を 1 だけインクリメントし、レコードを seen に追加します。 
6. 記録がすでに見られている場合は、新しい発見には寄与しないため、完全に無視してください。 
7. その日のすべてのレコードを処理した後、回答を max(answer, day_new) として更新します。 
8. すべての日数が処理された後、回答を出力します。

実装上の重要な決定は、レコードが最初にグローバルに検出されたときに即座に更新が行われるかどうかです。 これにより、後日、古いものとして正しく扱われるようになり、後のスキャンでの二重カウントも防止されます。 

### なぜ効果があるのか

 処理中のどの時点でも、表示されるセットは、以前に出現したすべての個別のレコードのセットと正確に一致します。 新しい日を処理するとき、すべてのレコードは、見たかどうかに基づいて正しく分類されます。 各レコードは、正確に 1 日分、特にレコードが表示された最初の日のカウントに寄与します。 day_new は、以前に表示されていないレコードが見つかったときにのみインクリメントされるため、レコードが 2 回カウントされることはなく、貢献を見逃すことはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    seen = set()
    ans = 0

    for _ in range(n):
        arr = list(map(int, input().split()))
        m = arr[0]
        records = arr[1:]

        day_new = 0
        for r in records:
            if r not in seen:
                seen.add(r)
                day_new += 1

        ans = max(ans, day_new)

    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションでは、単一のグローバル セットを使用して、レコードが以前に参照されたかどうかを追跡します。 毎日の入力はリストに解析され、最初の要素はカウント m です。 残りはレコード ID です。 

重要な実装の詳細は、新しいレコードを検出すると、すぐに認識されたセットを更新することです。 これにより、数日間にわたる正確性が保証されます。 1 日内の重複は問題にならないため、1 日ごとのセットは必要ありません。レコードが既知のマークを付けられると、同じ日にその後発生したものは自然に無視されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(合計m) | 各レコードは 1 回チェックされ、最大 1 回セットに挿入されます。 
| スペース | O(n) | セットには、各個別のレコード ID が最大 1 回保存されます。 

全日にわたるレコード エントリの総数は 10^6 に制限されるため、ハッシュを使用したリニア スキャンは時間制限内に問題なく収まります。 メモリ使用量も、個別のレコードの数 (最大 n) によって制限されます。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    def solve():
        n = int(input())
        seen = set()
        ans = 0
        for _ in range(n):
            arr = list(map(int, input().split()))
            m = arr[0]
            records = arr[1:]
            day_new = 0
            for r in records:
                if r not in seen:
                    seen.add(r)
                    day_new += 1
            ans = max(ans, day_new)
        print(ans)

    from io import StringIO
    out = StringIO()
    backup_stdout = sys.stdout
    sys.stdout = out
    solve()
    sys.stdout = backup_stdout
    return out.getvalue().strip()

# provided sample
assert run("""3
1 1
2 1 3
3 1 2 3
""") == "1"

# minimum input
assert run("""1
1 1
""") == "1"

# all same repeats
assert run("""3
3 1 1 1
3 1 1 1
3 1 1 1
""") == "1"

# staggered unique introduction
assert run("""3
1 1
1 2
1 3
""") == "1"

# maximum new on first day
assert run("""2
3 1 2 3
2 4 5
""") == "3"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 3日間のシングルリピート | 1 | 1 日以内に重複 |
 | 1要素の場合 | 1 | 最小境界 |
 | 同一のリストが繰り返される | 1 | グローバル重複排除 |
 | 順次発見 | 1 | 数日間にわたる追跡 |
 | 大初日 | 3 | 正しい最大トラッキング |

 ## 特殊なケース

 1 日内にレコードが繰り返されるケースでは、日内の重複によってカウントが膨らまないことが確認されます。 たとえば、入力`1: [1, 1, 1]`は 1 回だけカウントする必要があります。 seen に 1 が追加されると、それ以降の出現は無視されるため、アルゴリズムはこれを処理します。 

先に何度も繰り返した後、レコードが遅れて表示されるケースは、グローバルな追跡を裏付けます。 たとえば、5 が最終日のみに表示される場合でも、その日に 1 回だけカウントされるはずです。 このセットにより、以前にカウントされないことが保証されます。 

毎日、前に見た要素のみが繰り返される場合、最初の日以降は答えがゼロになる可能性があることが確認されます。 すべてのレコードが含まれていることが確認されると、将来のすべての日数はゼロとなり、最大値は以前の計算から正しく保存されます。
