 ## 解決策
 ## 問題の理解

 私たちは、円形ディスク プレーヤーで固定された一連の曲として表現されたアルバムを与えられます。 ディスクは最初の曲から始まり、常に順番に進み、最後の曲の後に最初に戻ります。 

ノアはただ順番に聞くだけではありません。 代わりに、同じアクションを繰り返し実行します。つまり、ディスク上の現在の位置から、指定された数の曲をスキップし、次に到達した次の曲を聴きます。 彼が曲を聴くと、その曲はすでに消費されているため今後の検討から削除され、残りの曲は新たな循環順序に閉じ込まれます。 

各スキップ値は、次に聞く曲を選択する前にスキップする残りの曲の数を示します。 重要な詳細は、スキップは元の固定配列ではなく、現在残っている曲に対してカウントされるということです。 

出力は、選択された順序での正確な曲のシーケンスです。 

制約は最大 100,000 曲と 100,000 操作に達するため、リスト上のステップごとの動きをシミュレートするソリューションはすぐに遅すぎます。 クエリごとにリストをスキャンまたはローテーションする直接的なアプローチは、最悪の場合、1 秒間に許可される操作をはるかに超える二次的な動作に低下します。 

主な困難は、2 つの操作を効率的にサポートする必要があることです。1 つは現在の生きている曲の数を法とする値で前にジャンプする操作、もう 1 つは循環順序を維持しながら選択した曲を削除する操作です。 

Python リストを使用し、インデックスによって繰り返し回転またはポップする単純な実装では、微妙な失敗が発生します。 たとえば、曲をリストに保存して繰り返し実行すると、`pop(k)`操作では、各ポップが後のすべての要素をシフトするため、大きな入力を伴う 1 回の実行でも約$O(n^2)$仕事。 

もう 1 つの間違ったアプローチは、要素を削除せずに元の配列のモジュロ演算を使用して次のインデックスを計算することです。 削除後に循環構造が変化するため、これは破綻します。 たとえば、曲が次のような場合`[A, B, C, D]`そして私たちは削除します`B`、次のスキップで処理する必要があります`[A, C, D]`、元のインデックス作成ではありません。`C`まだインデックス 2 にあります。 

主な困難は、k 番目の選択と削除を高速に行う動的な循環シーケンスを維持することです。 

## アプローチ

 ブルートフォース シミュレーションでは、現在の曲リストを保持し、クエリごとに一度に 1 ステップずつ前進し、必要に応じてラップアラウンドし、削除された曲をスキップします。 各スキップは最大で次の範囲まで移動する可能性があります$O(n)$要素、そして私たちはこれを行います$m$クエリ、それにつながる$O(nm)$最悪の場合の行動。 と$n = m = 10^5$、これはまったく不可能です。 

構造的な洞察は、必要な操作は動的に縮小するセットに対する順序統計操作のみであるということです。循環順序で k 番目に残っている要素を繰り返し見つけて削除する必要があります。 これはまさに、フェンウィック ツリーまたはバイナリ アライブ アレイ上のセグメント ツリーがサポートしているものです。 各位置は生きているか削除されており、プレフィックスの合計により、位置の前に生きている要素がいくつ存在するかを数えることができます。 これにより、ツリー上のバイナリ リフティングを使用して、k 番目の生きている要素を見つけることができます。 

現在の状態を生きているインデックスのセットとして表すと、循環移動は明示的な走査ではなく、生きている要素のカウントに基づいた算術になります。 スキップを残りの要素の中のターゲット ランクに変換し、そのランクの構造をクエリします。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース シミュレーション | O(nm) | O(n) | 遅すぎる |
 | フェンウィック / 注文統計 | O(m log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 曲のインデックスに対してフェンウィック ツリーを維持します。 各位置には、曲がまだ利用可能な場合は 1 が格納され、それ以外の場合は 0 が格納されます。 

変数も維持します`pos`、オリジナルのインデックスではなく、残りの曲の中でのランクの観点から現在の位置を表します。 

1. 最初はすべての曲が利用可能であるため、フェンウィック ツリーをすべての位置に 1 で初期化します。 セット`pos = 0`、つまり、残りの循環順序の最初の曲から開始します。 
2. 各スキップ値について`s_i`、残りの曲のサイズを計算します`rem`。 位置を次のように更新します`pos = (pos + s_i) % rem`。 これにより、スキップが現在の循環順序のターゲット インデックスに変換されます。 
3. を見つけて、この論理位置を元の配列内の実際のインデックスに変換します。`(pos + 1)`- 番目の生きている要素はフェンウィック ツリーを使用します。 このステップは、k 次の統計クエリです。 
4. そのインデックスの曲を出力し、値を 0 に設定してフェンウィック ツリーから削除します。 
5. 削除後、次の開始位置は縮小循環順序の同じインデックスになります。 単純にランクで言うとこんな感じです`pos`なぜなら、削除後のすべては暗黙の順序付けで 1 つ左にシフトされるからです。 

### なぜ効果があるのか

 すべてのステップで、フェンウィック ツリーは現在の循環シーケンスを生きている要素の圧縮された配列として表します。 変数`pos`この圧縮された順序付けでは、常に有効なインデックスを参照します。 モジュロ更新では、サイズの循環シーケンスをスキップするため、正確さが維持されます。`rem`算術剰余と同等です`rem`。 k 番目のクエリは、配列を明示的に再構築することなく、この抽象ランクを元のインデックス空間に変換します。 削除では要素が削除されるだけで、残りの要素が並べ替えられることはないため、フェンウィック ツリーによって維持される相対的な順序は、進化するプレイリストと正確に一致します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def build(self, arr):
        for i in range(1, self.n + 1):
            self.bit[i] += arr[i]
            j = i + (i & -i)
            if j <= self.n:
                self.bit[j] += self.bit[i]

    def update(self, i, delta):
        while i <= self.n:
            self.bit[i] += delta
            i += i & -i

    def prefix_sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def total(self):
        return self.prefix_sum(self.n)

    def find_kth(self, k):
        idx = 0
        bitmask = 1 << (self.n.bit_length())
        while bitmask:
            nxt = idx + bitmask
            if nxt <= self.n and self.bit[nxt] < k:
                k -= self.bit[nxt]
                idx = nxt
            bitmask >>= 1
        return idx + 1

def solve():
    n, m = map(int, input().split())
    songs = [""] + [input().rstrip() for _ in range(n)]
    skips = [int(input()) for _ in range(m)]

    fw = Fenwick(n)
    for i in range(1, n + 1):
        fw.update(i, 1)

    pos = 0
    rem = n

    for s in skips:
        pos = (pos + s) % rem
        rem = fw.total()
        idx = fw.find_kth(pos + 1)
        print(songs[idx])
        fw.update(idx, -1)
        rem -= 1

solve()
```フェンウィック ツリーは、曲の位置に対する動的頻度テーブルとして使用されます。 の`find_kth`関数は、プレフィックス合計に対してバイナリ リフティング検索を実行して、k 番目の生きている曲のインデックスを見つけます。 の`pos`変数は常に残りの要素間のランクとして保持され、曲を出力する必要がある場合にのみ実際のインデックスに変換されます。 

微妙な点の 1 つは、削除と一貫して残りの数を再計算または維持することです。 モジュロ演算では常に、生きている要素の現在の数を使用する必要があります。そうしないと、削除後に回転が誤ってドリフトする可能性があります。 

## 実用的な例

 A から E までのラベルが付けられた 5 曲からなる小さなアルバムを考えてみましょう。 

入力スキップは、`[1, 2, 1]`。 

最初はすべての曲が生きていて、`pos = 0`。 

| ステップ | アライブソング | 前の位置 | スキップ | mod後の位置 | 選んだ曲 | 残り |
 | --- | --- | --- | --- | --- | --- | --- |
 | 1 | A B C D E | 0 | 1 | 1 | B | ＡＣＤＥ |
 | 2 | ＡＣＤＥ | 1 | 2 | 3 % 4 = 3 | あ | CDE |
 | 3 | CDE | 3 | 1 | 0 | C | ＤＥ |

 トレースはそれを示しています`pos`は常に、元の位置ではなく、圧縮されたアライブ配列内の循環インデックスを参照します。 モジュロ演算は削減された構造に適用されるため、削除した後でも有効なままです。 

ここで、スキップが複数回ラップする場合を考えてみましょう。 歌とともに`[A, B, C, D]`そしてスキップします`[5]`、から始めます`rem = 4`、 それで`pos = (0 + 5) % 4 = 1`。 生存順序の 2 番目の要素は、`B`、ラッピングが正しく動作することを確認します。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import deque

    class Fenwick:
        def __init__(self, n):
            self.n = n
            self.bit = [0] * (n + 1)

        def update(self, i, delta):
            while i <= self.n:
                self.bit[i] += delta
                i += i & -i

        def sum(self, i):
            s = 0
            while i > 0:
                s += self.bit[i]
                i -= i & -i
            return s

        def total(self):
            return self.sum(self.n)

        def find_kth(self, k):
            idx = 0
            bitmask = 1 << (self.n.bit_length())
            while bitmask:
                nxt = idx + bitmask
                if nxt <= self.n and self.bit[nxt] < k:
                    k -= self.bit[nxt]
                    idx = nxt
                bitmask >>= 1
            return idx + 1

    def solve():
        n, m = map(int, input().split())
        songs = [""] + [input().rstrip() for _ in range(n)]
        skips = [int(input()) for _ in range(m)]

        fw = Fenwick(n)
        for i in range(1, n + 1):
            fw.update(i, 1)

        pos = 0
        out = []

        for s in skips:
            rem = fw.total()
            pos = (pos + s) % rem
            idx = fw.find_kth(pos + 1)
            out.append(songs[idx])
            fw.update(idx, -1)

        return "\n".join(out)

    return solve()

 ## 特殊なケース

 残り 1 曲だけになると、コーナーケースが発生します。 その状況では、1 によるモジュロは常に 0 になるため、すべてのスキップ値は無関係になります。アルゴリズムはこれを自然に処理します。`pos % 1`は常にゼロであり、フェンウィック ツリーは唯一の生きているインデックスを返します。 

もう 1 つの微妙なケースは、スキップが非常に大きく、次のような場合に発生します。$10^9$。 直接の反復は失敗しますが、モジュロ削減により、現在の残りのサイズ内でのみ移動することが保証されます。 サイズは減少するだけなので、演算は制限されたままで安全です。 

最後のケースは、現在位置の近くで削除が発生する場合です。 フェンウィック ツリーはインデックスを動的に圧縮するため、要素を削除するとランクが自動的にシフトします。 の`pos`変数は常に生のインデックスではなくランク空間で解釈されるため、有効なままです。そのため、削除するたびに手動で調整する必要はありません。
