 ## 問題の理解

 同じ長さの 2 つの文字列が与えられ、どちらも小文字のラテン文字で構成されます。 唯一許可される操作は、現在の文字列の最初の文字を取得し、それを削除し、先頭または末尾を含む文字列内の任意の場所に再挿入することです。 この操作は何度でも繰り返すことができます。 目標は、初期文字列をターゲット文字列に変換するために必要なそのような操作の最小数を決定するか、それがまったく実行できないと判断することです。 

操作自体から得られる重要な観察点は、文字を削除したり作成したりすることは決してないため、複数の文字セットは 2 つの文字列間で同一でなければならないということです。 これにより、必要な条件がすぐに得られます。文字の頻度が 2 つの文字列間で異なる場合、文字を並べ替えるだけなので、一連の操作ではそれを修正できません。 

この制約により、長さ 200,000 までの文字列が許可されるため、変換の二次シミュレーションや、文字列を明示的に繰り返し再構築するアプローチは即座に除外されます。 ネストされたループで文字を何度も再表示するソリューションは、遅すぎます。 線形または線形に近いプロセスを目指す必要があり、グリーディ スキャンまたはキューのようなシミュレーションが含まれる可能性が高くなります。 

文字がマルチセット内で一致しても順序どおりに整列できない場合、微妙なエッジ ケースが発生します。 たとえば、s = "ab" および t = "ba" は有効ですが、s = "ab" および t = "ac" はカウントが一致しないため不可能です。 もう 1 つの興味深いケースは、s と t が頻繁に繰り返される順列である場合です。 単純な貪欲な交換戦略は、将来の制約を考慮せずにキャラクターを任意に配置できると仮定すると失敗する可能性があります。 

## アプローチ

 ブルート フォースの観点では、プロセスを明示的にシミュレートします。 文字列を維持し、最初の文字を繰り返し取得し、考えられるすべての挿入位置を試します。 これにより、巨大な分岐要素が生成されます。各ステップには O(n) 個の選択肢があり、最大 n 個のステップが存在する可能性があるため、検索空間は指数関数的に増大します。 状態空間は本質的に制約された回転によって到達可能なすべての置換であり、依然として巨大であるため、枝刈りさえも十分に役立ちません。 

重要な構造上の洞察は、この操作では任意の交換は許可されていませんが、現在の前面のキャラクターを背面または後の位置に送信することで「延期」できるということです。 言い換えれば、文字列を左から右にスキャンしていますが、ターゲット文字列の構築にすぐには役に立たない文字を遅らせることができます。 

これにより、問題は s と t の間の貪欲なマッチング プロセスに再構成されます。 s を前からスキャンしながら、t を順番に一致させようとします。 s の現在の先頭文字が t の次に必要な文字と一致するときは常に、両方を消費します。 一致しない場合は、そのキャラクターを遠ざけた（後ろに移動した）ものとして扱い、１操作を払って続行します。 

この貪欲なアイデアにより、すべての挿入位置を明示的に探索することが回避されます。 唯一の決定は、現在のキャラクターがゲームの進行に役立つか、延期する必要があるかです。

 ## アルゴリズムのチュートリアル

 ソース文字列にはキューのような構造を使用し、ターゲット文字列にはポインターを使用して、両方の文字列をシミュレートします。

1. まず、両方の文字列の文字数が同じであることを確認します。 そうでない場合は、どの一連の操作も差異を調整できないため、すぐに -1 を返します。 
2. ターゲット文字列上にポインタ j を保持します。初期値は 0 で、次に照合する文字を表します。 
3. ソース文字列をキューとして扱います。 その正面のキャラクターを繰り返し検証します。 
4. 先頭の文字が t[j] に等しい場合、両方のポインタを進めます。 これは、キャラクタを延期することなく、正しい最終的な相対位置に配置することに相当するため、操作コストは発生しません。 
5. 先頭の文字が t[j] と一致しない場合、許可された操作の実行をシミュレートします。それを削除して文字列の最後に挿入し、操作カウンターを 1 つ増やします。 
6. ターゲット文字列のすべての文字が一致するまでこのプロセスを続けます。 

重要な考え方は、挿入位置を明示的に選択する必要がないということです。 役に立たない文字は単純に押し戻され、正確性が保たれます。これは、その最終的な位置が、最終的に有用になるときによって暗黙的に決定されるためです。 

### なぜ効果があるのか

 いつでも、次に必要な文字を t に配置しようとしています。 キューの先頭がすでに一致している場合、それを遅らせても操作が増えるだけでメリットはありません。 一致しない場合は、前に置いておくと t が進まないため、延期する必要があります。 これにより、貪欲な不変条件が作成されます。すべての文字は、必要なターゲット位置に一致する場合にはすぐに消費されるか、進行を妨げる場合には延期されます。 これにより、不必要な延期を決して行わず、有効な試合の機会を逃すことがなくなります。 

すべての文字は、シミュレーション内でポインターを厳密に進める方法で照合または戻されるため、プロセスは t の進行という点で単調であるため、無限に循環したり最適性を失ったりすることはありません。 

## Python ソリューション```python
import sys
from collections import Counter, deque

input = sys.stdin.readline

def solve():
    n = int(input().strip())
    s = input().strip()
    t = input().strip()

    if Counter(s) != Counter(t):
        print(-1)
        return

    dq = deque(s)
    j = 0
    ops = 0

    while j < n:
        if dq[0] == t[j]:
            dq.popleft()
            j += 1
        else:
            dq.append(dq.popleft())
            ops += 1

    print(ops)

if __name__ == "__main__":
    solve()
```不一致があると操作に関係なく変換が不可能になるため、解決策は文字数を使用した実現可能性のチェックから始まります。 メインのシミュレーションでは、両端キューを使用して、進化する文字列を表します。 ポインタ j は、ターゲット文字列の進行状況を追跡します。 

各ステップは、一致する文字を消費するか、前の文字を後ろに回転させて、1 回の操作と数えます。 t のすべての文字が一致すると、ループは終了します。 

実装の微妙な詳細は、常に dq[0] にアクセスするため、j < n の間は両端キューが空であってはなりません。 これが保証されるのは、両方の文字列の長さが同じであり、一致または移動された場合にのみ文字を削除し、シミュレーションの周期的な意味でのサイズの一貫性を維持するためです。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) 償却 | 各文字は、制限された回数だけ前から後ろに移動され、最終的に消費されます。 
| スペース | O(n) | Deque はシミュレーション中にすべての文字を保存します。 

すべての操作は定数時間であり、ターゲット ポインターの単調な消費によりデキュー操作の合計数は実際には線形であるため、アルゴリズムは制約内に収まります。 

## テストケース```python
import sys, io
from collections import Counter, deque

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)

    n = int(input().strip())
    s = input().strip()
    t = input().strip()

    if Counter(s) != Counter(t):
        return "-1"

    dq = deque(s)
    j = 0
    ops = 0

    while j < n:
        if dq[0] == t[j]:
            dq.popleft()
            j += 1
        else:
            dq.append(dq.popleft())
            ops += 1

    return str(ops)

assert run("2\nab\nbb\n") == "-1"

assert run("1\na\na\n") == "0"
assert run("5\nabcde\neabcd\n") == "4"
assert run("6\naabbcc\nccbbaa\n") == "6"
assert run("4\nabca\naabc\n") == "3"

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、ターゲット文字列に存在する文字が必要であるが、現在キューの奥深くでブロックされている場合です。 たとえば、s = "baaa"、t = "aaab" となります。 アルゴリズムは、十分な数の「a」文字が先頭に到達するまで、先頭の「b」を繰り返し回転させます。 シミュレーションでは、「b」が関連するまでに必要な回数だけ延期されることが保証されます。 

別のケースは、s がすでに t に等しい場合です。 この状況では、すべての比較はすぐに成功するため、ローテーションは実行されず、答えはゼロになります。 最初の比較は常に成功し、操作をトリガーせずに両方のポインターを進めるため、アルゴリズムはこれを自然に処理します。 

最後のエッジケースは、文字列が同一のマルチセットを持っているが、完全な反転など、大規模な再配置が必要な場合です。 この場合でも、すべての不一致は 1 回の回転で処理され、各文字がターゲット シーケンスの正しいフェーズの先頭に到達すると、最終的には正確に整列し、構造内での直線的な進行が保証されます。
