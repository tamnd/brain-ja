 ## 解決策
 ## 問題の理解

 それぞれの GPA 値が 0 ～ 5 の学生のグループが与えられます。学生は、改善の可能性があり GPA が少なくとも 2.8 に達した場合にのみ「安全」とみなされます。 

学生に複数回適用できるポーションがあり、完全に適用するたびにその学生の GPA がちょうど 1 増加します。ただし、ポーションは遅いです。各使用には一定の時間が消費され、総時間予算は限られています。 重要なのは、各生徒は個別に改善する必要があり、生徒間でポーションの使用を分配する方法を選択できることです。 

課題は、利用可能な時間を最適に使用した後、2.8 未満にとどまる生徒の数を最小限に抑えることです。 同様に、各「アップグレード」には一定の時間コストがかかりますが、生徒ごとに必要なアップグレード数が異なることを考慮して、少なくとも 2.8 まで引き上げることができる生徒の数を最大化したいと考えています。 

この制約は、これをアップグレード可能なアイテムに対するリソース割り当ての問題として扱う必要があることを意味します。 一般的な Codeforce スケールの入力 (最大約 10^5 の生徒) では、すべての生徒とポーションの割り当てに対する二次シミュレーションは遅すぎます。 おそらく貪欲な選択に基づく、O(n log n) または O(n) 戦略が必要です。 

いくつかの特殊なケースが重要です。 

すでに 2.8 以上のレベルにある学生はアップグレードを必要とせず、常に直ちに安全であるとみなされる必要があります。 たとえば GPA リスト`[3.0, 4.2]`時間に関係なく、未硬化の結果は 0 になるはずです。 

しきい値をわずかに下回る生徒は 1 つまたは 2 つのアップグレードしか必要としないかもしれませんが、はるかに下回る (0.1 など) 生徒はさらに多くのアップグレードを必要とする可能性があります。 最も低い GPA を優先する単純な戦略は、早期に高価なコンバージョンに時間を浪費する可能性があるため、失敗する可能性があります。 

もう 1 つの微妙なケースは、一部の生徒にとって 1 回のアップグレードさえも時間が足りない場合です。 合計時間をポーションの使用ごとの時間で割った値がゼロの場合、改善は不可能であり、答えは単純に GPA のカウント < 2.8 になります。 

## アプローチ

 強引な解釈では、生徒にポーションの使用を割り当てるあらゆる可能な方法がシミュレートされます。 各生徒に対して、必要な制限まで 0、1、2、... のアップグレードを適用して、残りの時間を他の生徒に再帰的に分配することができます。 各生徒が複数の分岐選択肢を導入するため、これはすぐに指数関数的になります。n が最大 10^5 の場合、生徒ごとに 10 の選択肢を考慮したとしても、不可能な状態空間サイズにつながります。 

重要な単純化は、各生徒が独立して、2.8 に達するまでのポーション使用における固定の「コスト」を持っていることを観察することです。 GPAを持っている学生の場合`a`、その後、彼らは必要とします`ceil(max(0, 2.8 - a))`ポーションのアプリケーション。 各申請にかかる時間は同じなので、`m`、問題は次のようになります。各生徒には重み (必要な使用回数) があり、総使用量の予算があります。`k // m`。 私たちは、完全に支払うことができる重量の数を最大化したいと考えています。 

これは古典的な貪欲選択の問題です。 各生徒は同じ「価値」（1 人を節約）を生み出しますが、コストは異なるため、ポーションの使用量が少ない生徒を常に優先する必要があります。 必要な用途を昇順に並べ替えることで、完全に治癒した生徒の数を最大化することができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (割り当てをシミュレート) | 指数 | O(n) | 遅すぎる |
 | 必要なアップグレードに貪欲 | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、各生徒がしきい値 2.8 に達するために必要なポーションの塗布回数を計算します。 学生がすでに 2.8 以上である場合、この値はゼロです。 

次に、利用可能な合計時間をポーションの塗布ごとの時間で割ることにより、許容できるポーションの合計塗布数を計算します。 

第三に、必要な申請書がゼロの学生をすべて破棄します。学生はすでに治癒しており、リソースを消費しないためです。 

第 4 に、残りの必要な適用数を昇順に並べ替えて、安価な治療法が最初に来るようにします。 

5 番目に、このソートされたリストを繰り返して、生徒ごとに、ポーションの申請がまだ十分に残っているかどうかを確認します。 「はい」の場合、そのコストを差し引いて、治癒したものとしてカウントします。 それ以外の場合は、停止してください。 

最後に、治癒していない生徒の数は、残っている生徒の数から治癒に成功した生徒の数を引いたものです。 

### なぜ効果があるのか

 正しさは貪欲な交換の議論に基づいています。 私たちが、治せるはずの安価な学生をスキップして、より高価な学生を選ぶことがあったと仮定してください。 両者を交換しても、治癒した生徒の数は決して減りません。両方とも同じ「価値」を消費するからです（1人の治癒者）が、より安価な方が他の生徒のためにより多くの予算を確保できます。 したがって、最適なソリューションは、最適性を損なうことなく、常にコストが減少しない順序で生徒を選択するソリューションに変換できます。 

これにより、貪欲な選択により、固定予算内で治癒する生徒の数が最大化されることが保証されます。 

## Python ソリューション```python
import sys
import math
input = sys.stdin.readline

def solve():
    m, k = map(int, input().split())
    n = int(input())
    
    # total potion uses available
    total_uses = k // m
    
    costs = []
    already_ok = 0
    
    for _ in range(n):
        a = float(input().strip())
        
        if a >= 2.8:
            already_ok += 1
            continue
        
        need = 2.8 - a
        # each use adds exactly 1 GPA
        uses = math.ceil(need)
        costs.append(uses)
    
    costs.sort()
    
    cured = 0
    for c in costs:
        if total_uses >= c:
            total_uses -= c
            cured += 1
        else:
            break
    
    print(n - (already_ok + cured))

if __name__ == "__main__":
    solve()
```このソリューションは、合計時間をポーション適用の個別の予算に変換することから始まります。 部分的なアプリケーションは許可されないため、各 GPA は上限演算を使用して必要な整数のアプリケーションに処理されます。 

すでに資格を取得した学生は、予算を消費することなく最終的な安全カウントに貢献するため、明示的に分離します。 残りの学生はコストに換算されて分類されるため、常に最も安価な治療法が最初に試行されます。 

このループは予算を貪欲に消費するため、安価な学生をまだ処理できるにもかかわらず、高額な費用の学生にリソースを浪費することがなくなります。 

微妙な点は、計算時の浮動小数点処理です。`2.8 - a`。 入力は小数点以下 1 桁までで与えられるため、ここでは浮動小数点精度が安全ですが、より厳密な設定では、スケーリングされた整数を使用した方が適切に処理されます。

 ## 特殊なケース

 重要なエッジケースは、すべての生徒がすでにしきい値を超えている場合です。 この場合、コスト リストは空であり、並べ替えや予算ロジックを実行しなくても、答えはゼロになるはずです。 アルゴリズムはこれを自然に処理します。`already_ok`等しい`n`そして`costs`は空です。 

もう 1 つのケースは、予算でポーションの使用がゼロである場合です (`k < m`）。 それから`total_uses = 0`、そして費用リストの学生は誰も治せません。 ループでは演繹がまったく実行されないため、最終的な答えは 2.8 未満の生徒の数になります。 

最後の微妙なケースは、浮動小数点値が 2.8 に非常に近い場合に発生します。 この問題では 10 進数の入力を使用するため、計算`ceil(2.8 - a)`他の言語では精度の問題が直接発生する可能性があります。 このアルゴリズムは安定した入力精度を前提としていますが、より堅牢な実装では、値を 10 または 100 でスケーリングすることで、浮動小数点の問題が完全に排除されます。
