 ## 問題の理解

 アルカディはカツレツを合計で調理します$2n$数秒であり、物理的原理は単純です。どの瞬間も、それはちょうど一方の側にあり、彼がそれをひっくり返すたびに、即座に側が変わります。 要件は、調理間隔全体にわたって、それぞれの面が正確に蓄積する必要があることです。$n$数秒間の露出。 

難しいのは、揚げること自体ではなく、裏返すことが一定の時間間隔でのみ可能であるという事実です。 各インターバル$[l_i, r_i]$Arkady が任意の整数を自由に選択できることを意味します$t$その範囲内でフリップを実行します。 これらの範囲外では、彼は現在のチームを維持することを余儀なくされます。 

したがって、タスクは、最初の面で費やされる合計時間が正確に一致するように、許可された間隔から選択された一連のフリップ時間が存在するかどうかを判断することです。$n$、そうであれば、必要なフリップの最小数を見つけます。 

入力制約$n \le 10^5$あらゆる解が長さの時間軸に線形に依存することを即座に示唆します$2n$境界線にありますが、まだ実現可能です。 ただし、潜在的なフリップ サブセットの数は、次のように指数関数的に増加するため、すべてのフリップの組み合わせを単純に検索することは不可能です。$k$、そして順序決定さえも組み合わせの大規模な爆発を引き起こします。 

固定された瞬間にフリップが厳密に要求されない場合、微妙な問題が発生します。 貪欲な「可能な場合は常に反転する」アプローチは簡単に失敗する可能性があります。これは、初期の反転によって各側の将来のセグメントの長さが変更され、正確に到達するかどうかに影響するためです。$n$まだ可能です。 

たとえば、Arkady が重複するウィンドウを自由に反転できますが、連続的にはできないとします。 貪欲な戦略は反転が早すぎて、一方の側に正確にバランスを取るのに十分な時間が残らない可能性があります。$n$たとえ、後でフリップしてもうまくいったとしても。 

もう 1 つの障害モードは、間隔ごとに最大 1 回のフリップのみが必要であると仮定した場合に発生します。 間隔は重複しており、セグメントのパリティ構造を調整するのに役立つ場合、最適なソリューションには同じ間隔内で複数の反転が必要になることがよくあります。 

## アプローチ

 重要な問題は、反転によって時間が消費されるのではなく、将来の時間が最終的なバランスにどのように寄与するかが変化することです。 これにより、タイムラインをサイド A とサイド B の間で長さが交互に変わるセグメントに分割することが本質的に問題になります。 

強引なアイデアは、間隔内のすべての整数点から選択された反転時間の考えられるすべてのシーケンスを試し、それらを並べ替えて、調理プロセスをシミュレートすることです。 これは正しいですが、まったく実行不可能です。 候補回数は最大です。$2n$、すべてのサブセットを試すと指数関数的になります。 剪定でも$k \le 100$各間隔には多くの可能な反転位置が含まれているため、役に立ちません。 

重要な観察は、特定の時点のみが構造的に重要であるということです。 可用性が変化する 2 つの関連する境界間では、反転制約については何も変わりません。 これは、時間軸を一連の臨界点、つまりすべての間隔のエンドポイントに圧縮できることを意味します。$0$そして$2n$。 これにより得られるのは最大でも$2k + 2 \le 202$ポジション。 

時間が圧縮されると、プロセスはこれらのポイントを通過するパスになります。 ある点から次の点に移動すると、これまでに反転した回数が偶数回か奇数回かに応じて、どちらかの側に一定の時間がかかります。 さらに、各ポイントでオプションで反転を実行できますが、これはその時間が少なくとも 1 つの許可された間隔内にある場合に限ります。 

これにより、問題が圧縮タイムライン上の動的プログラミング プロセスに変換され、パリティ (現在どのサイドがアクティブであるか) と最初のサイドで蓄積された時間の両方が追跡されます。

## アルゴリズムのチュートリアル

 ### 1. タイムラインを圧縮する

 すべてのエンドポイントを収集する$l_i, r_i$、 追加$0$そして$2n$、重複を並べ替えて削除します。 これらは、構造的に何も変化しないセグメントを定義します。 

隣接する各ペアは、固定期間の間隔を定義します。 

### 2. 反転が許可される場所を事前計算する

 圧縮された各時点について、それが少なくとも 1 つの元の間隔内にあるかどうかを判断します。 これにより、まさにその瞬間にフリップを実行できるかどうかがわかります。 

これにより、DP 中にすべての間隔を繰り返しチェックすることがなくなります。 

### 3. DP 状態を定義する

 しましょう`dp[i][p][a]`圧縮時間インデックスに到達するために必要なフリップの最小数になります。`i`、 どこ：

-`p`パリティ: 0 は現在の面が元の面であることを意味し、1 は反転された面を意味します
 -`a`元の側ですでに費やされた時間の合計です

 正確に到達できるかどうかだけを気にします`a = n`。 

### 4.初期化

 時間インデックス 0 では、フリップなし、累積時間ゼロの状態で開始します。`dp[0][0][0] = 0`。 

### 5. 時間の前進による移行

 インデックスの状態から`i`、次のセグメントの長さを計算します`len = time[i+1] - time[i]`。 

パリティが 0 の場合、このセグメント全体が元のサイドタイムに寄与します。 パリティが1の場合は相手に寄与し増加しない`a`。 

したがって、次のように移動できます。 

- 反転せずに`i`- オプションで反転`i`許可されていれば

 フリップは時間を消費しませんが、パリティを切り替えてフリップ数を増やします。 

### 6. 境界を強制し、状態を更新する

 移行するときは常に次のことを保証します`a`決して超えない`n`それ以上のものは無意味だからです。 

### 7. 最終的な答え

 最後の時点で$2n$、すべてのパリティ状態をチェックし、累積されたオリジナル側時間が正確に等しい最小の反転を取得します。$n$。 

存在しない場合は、「Hungry」と出力します。 

### なぜ効果があるのか

 DP は、圧縮された各時間境界までの調理プロセスの完全な記述を維持します。 どのステップにおいても、関連するプロパティは 2 つだけで、最初のサイドで蓄積された時間と、どちらのサイドが現在アクティブであるかです。 将来のすべての寄与はこれら 2 つの値と次のセグメントの長さにのみ依存するため、追加の履歴は問題になりません。 すべての有効な反転スケジュールは 1 つの DP パスに正確に対応し、すべての DP パスは有効なスケジュールに対応するため、DP 状態全体にわたる最適性によりグローバルな最適性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    intervals = [tuple(map(int, input().split())) for _ in range(k)]

    points = {0, 2 * n}
    for l, r in intervals:
        points.add(l)
        points.add(r)

    coords = sorted(points)
    m = len(coords)

    # mark allowed flip times
    allowed = [False] * m
    for i, x in enumerate(coords):
        for l, r in intervals:
            if l <= x <= r:
                allowed[i] = True
                break

    INF = 10 ** 9
    dp = [[[INF] * (n + 1) for _ in range(2)] for _ in range(m)]
    dp[0][0][0] = 0

    for i in range(m - 1):
        seg_len = coords[i + 1] - coords[i]

        for p in range(2):
            for a in range(n + 1):
                cur = dp[i][p][a]
                if cur == INF:
                    continue

                # move without flipping
                if p == 0:
                    na = a + seg_len
                    if na <= n:
                        dp[i + 1][p][na] = min(dp[i + 1][p][na], cur)
                else:
                    dp[i + 1][p][a] = min(dp[i + 1][p][a], cur)

                # flip at current point
                if allowed[i]:
                    np = 1 - p
                    dp[i][np][a] = min(dp[i][np][a], cur + 1)

    ans = min(dp[m - 1][p][n] for p in range(2))
    if ans == INF:
        print("Hungry")
    else:
        print("Full")
        print(ans)

if __name__ == "__main__":
    solve()
```この実装では、最初に関連するすべての時間境界が圧縮され、意味のある構造上の変更のみが残ります。 次に、DP は、元の側での累積時間を追跡しながら、これらのセグメント内の移動をシミュレートします。 重要な点は、時間の進行が連続する圧縮ポイント間を移動する場合にのみ DP に影響を与えるのに対し、フリップは有効なポイントでの瞬間的な遷移として処理されることです。 

よくある間違いは、累積時間を追跡せずにパリティのみで DP を試みることです。これにより、正確な時間を強制する能力が失われます。$n$制約。 もう 1 つは、状態空間を無効にする間隔制限を無視して、すべての圧縮ポイントで反転を常に可能なものとして扱うことです。

 ## 特殊なケース

 主なエッジケースは、間隔が存在しない場合です。 DP ではフリップは決して許可されないため、可能な構成はゼロフリップのみです。つまり、一方の側がすべてを取得します。$2n$秒。 これは等しくないので、$n$、アルゴリズムは正しく「Hungry」を返します。 

もう 1 つのケースは、間隔は存在するが、カットのバランスを正確に保つために必要な境界点が含まれていない場合です。 当然、DP は累積時間が等しい状態に到達できません。$n$セグメントの寄与は固定されており、有効な反転位置がないと調整できないためです。 

さらに微妙なケースは、複数の間隔が重なる場合に発生します。 このアルゴリズムは、重複するすべてのカバレッジを共有ポイントでのフリップを許可するものとして正しく処理し、DP はすべてのパリティ遷移を独立して調査して、有効な組み合わせが見逃されないようにします。
