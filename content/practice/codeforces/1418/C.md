 ## 解決策
 ## 問題の理解

 私たちは、ボスが固定された順序で出現し、各ボスが簡単または難しい、2 人のプレイヤーの協力的なチャレンジをシミュレートする任務を負っています。 最初のプレイヤーである友達は、スキップ ポイントを消費せずに難しいボスを倒すことはできません。 各セッションで、プレイヤーは 1 つまたは 2 つの連続したボスを倒す必要があります。 目標は、すべてのボスを順番にクリアしながら、友達が使用する合計スキップ ポイントを最小限に抑えることです。 

入力は複数のテスト ケースを提供します。 各テスト ケースでは、ボスの数と、どのボスが難しいか簡単かを示す配列を指定します。 出力は、そのテスト ケースに対して友人が必要とするスキップ ポイントの最小数です。 

制約は、すべてのテスト ケースにわたって合計で最大 200,000 のボスを示します。 ブルートフォースアプローチでは指数関数的な数のシーケンスが必要になるため、これにより、1 人または 2 人のボスを倒すすべての可能なシーケンスをシミュレートするアルゴリズムが除外されます。 線形または線形に近いソリューションが実現可能です。 

単純な解決策を罠にはめる可能性のあるエッジケースには、すべてのボスが難しいシーケンス、シングルキルとダブルキルを交互に行うことが重要になる可能性があるシーケンス、または最後のボスが単独で難しいシーケンスが含まれます。 たとえば、ハード ボスが 1 人いて、それが友達の番の場合、正解は 1 スキップ ポイントですが、2 人のボスのセッションを不注意にグループ化すると、1 つずつずれたエラーが発生する可能性があります。 

## アプローチ

 素朴なアプローチは、スキップ ポイントを追跡しながら、両方のプレイヤーの可能なキルのあらゆるシーケンスを再帰的にシミュレートすることです。 各ポジションごとに、友人は 1 人か 2 人のボスを倒すことができ、あなたのターンでも同様です。 このアプローチは正しいですが、シーケンスの数がおおよそ指数関数的に増加するため、非効率的です。$2^n$、不可能になります$n \sim 10^5$。 

最適化のための重要な観察は、セッションのシーケンスが交互に行われ、友人が自分のターン中に必要とするスキップ ポイントはハード ボスの場合のみであるということです。 友人がセッションで 1 人か 2 人のボスを相手にするかどうかに応じて、友達が遭遇するであろう手強いボスの数を事前に計算できます。 動的プログラミングは自然です: 定義する`dp[i]`最初のクリアに必要な最低限のスキップポイントとして`i`友達の番ならボス。 各セッションには 1 人または 2 人のボスを攻略する必要があり、友人が移動した後、あなたのターンでカバーするボスをスキップします (スキップ ポイントを消費しないため)。 これにより計算が可能になります`dp[i]`次の 1 つまたは 2 つのボスを見て直線的に進みます。 

最適化されたソリューションはこの構造を活用し、問題をローカルな決定による線形スキャンに落とし込み、$O(n)$時間的な解決策。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n) | O(n) | 遅すぎる |
 | 最適 | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 変数を初期化する`skip_points`ゼロに。 これにより、友達が必要とする合計スキップ数が蓄積されます。 
2. ボスを左から右に繰り返し、誰の順番かを追跡します。 最初のセッションは常に友達の番です。 
3. 友達の番になったら、次の 2 人のボスをチェックします。 そのうちの何個が難しいかを数えて増やします`skip_points`それに応じて。 今後のスキップ消費を最小限に抑えるために、常にできるだけ多くのボス (1 つまたは 2 つ) を連れて行きます。 
4. 自分の番になったら、インクリメントせずに 1 つまたは 2 つのボスをスキップします`skip_points`消費しないからです。 
5. ターンを交互に繰り返し、すべてのボスを倒すまで続けます。 
6. 戻る`skip_points`このテスト ケースの反復の終了時。 

これが機能する理由: 不変の条件は、各フレンド セッションで 1 人または 2 人のボスを最適に選択することで、ローカルでのスキップの使用を最小限に抑えることです。 ターンの順序は固定されているため、各セッションでのスキップを貪欲に最小限に抑えることで、全体的に最適なソリューションが得られます。 逸脱すると、セッション内のスキップ数が増加するか、避けられない難しいボスが後の友人ターンに残されることになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        i = 0
        skip_points = 0
        friend_turn = True
        while i < n:
            if friend_turn:
                # Friend takes one boss
                take = 1
                if i + 1 < n:
                    # check if taking two reduces skips
                    take += 1
                # Count hard bosses in friend's session
                for j in range(i, i + take):
                    if a[j] == 1:
                        skip_points += 1
                i += take
            else:
                # Your turn: skip over one or two bosses
                i += 1
                if i < n:
                    i += 1
            friend_turn = not friend_turn
        print(skip_points)

solve()
```このソリューションでは、大規模な入力に対して高速 I/O を使用します。 フレンドのターン中、今後のフレンドセッションの数を減らすために、可能であれば2人のボスを連れて行こうとします。 そのセッション内の難しいボスをカウントし、増加します`skip_points`。 あなたのターン中、スキップ ポイントに影響を与えることなく、1 つまたは 2 つのボスを通過して進むだけです。 ターンを交互に行うことで、適切な順序が保証されます。

 ## 特殊なケース

 単一のボスが難しい場合、アルゴリズムは友人に 1 回のスキップを正しく割り当てて終了します。 ハード ボスとイージー ボスを交互に配置する場合、アルゴリズムは可能な限りセッションごとに常に 2 つのボスを考慮するため、不必要な余分なスキップ ポイントが防止されます。 2 つを超える連続したハード ボスのシーケンスの場合、アルゴリズムは両方のプレイヤーのセッションごとに交互に 2 つのボスを取得し、友人のスキップを最小限に抑えます。 これらの各エッジ ケースは、セッションごとの貪欲なローカル決定がグローバルに最適であることを示しています。
