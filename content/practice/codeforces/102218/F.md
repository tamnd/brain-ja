 ## 解決策
 ## 問題の理解

 を取り揃えております。`n`日と毎日の需要値。 アップデートにより、特定の日の需要が増加します。 メンテナンス前に工場で生産`b`一日あたりのチョコレート。 その間、`k`メンテナンス日は何も生産せず、何も販売できません。 メンテナンス終了後、生産します`a`一日あたりのチョコレート。 メンテナンス開始日`p`はタイプ 2 クエリに対してのみ選択されるため、現在の需要配列は固定されたままですが、すべてのクエリで異なる可能な生産スケジュールが尋ねられます。 元の問題では、まさにこの更新およびクエリ モデルが使用されています。 

重要な制限は、その日の注文であることです。`i`前日までに満足できない`i`, ただし、未使用のチョコレートは保管して後で販売することができます。 したがって、工場は生産が需要を上回った日に在庫を蓄積し、その後の注文にその在庫を費やすことができます。 

させて`D_i`日中の総需要になります`1..i`、そしてさせてください`P_i`選択したメンテナンス開始時のその日の総生産量になります。 もし`D_i > P_i`、それでは少なくとも`D_i - P_i`最初からの注文`i`日々は決して満たされない。 このようなプレフィックス不足の最大値によって、総需要のどれだけが必然的に失われるかが決まります。 

この制約により、直接シミュレーションは不適切になります。 と`n`まで`10^5`そして`q`まで`2 * 10^5`、アルゴリズム`O(n)`すべてのクエリが実行できるのは`2 * 10^10`最悪の場合の運用。 更新とクエリごとにほぼ対数の作業が必要です。 すべての需要更新がその日以降のすべてのプレフィックス合計に影響を与えるという事実は、遅延セグメント ツリーを直接示しています。 

実装が静かに誤動作する可能性がある境界がいくつかあります。 まずは当日からのメンテナンスです`1`。 例えば、```
3 1 3 1 3
1 1 2
1 3 1
2 1
```答えは`1`。 当日の製造・販売はございません`1`, その日の2つの注文は失われます。 日々生み出されるチョコレート`2`そして`3`その日に1つの注文のみをサポートできます`3`。 総需要と総生産量のみを比較する不注意なソリューションでは、3 つの注文はすべて販売可能であると誤って主張する可能性があります。 

もう一つの境界線はメンテナンスがちょうどその日に終わることです`n`。 考慮する```
4 2 3 1 2
1 4 10
2 3
```答えは`2`。 と`p = 3`、生産は日のみに行われます`1`そして`2`、チョコレートを2つあげますが、数日は`3`そして`4`両方ともメンテナンス日です。 メンテナンス間隔を次のように扱う`[p, p+k]`の代わりに`[p, p+k-1]`生産スケジュールを変更し、間違った結果をもたらします。 

いつ`k = n`、工場全体が使用できなくなります。 例えば、```
3 3 2 1 3
1 1 1
1 3 5
2 1
```答えがあります`0`。 たとえ名目上の修理生産率が高くても、生産も販売もありません。 メンテナンス後の範囲を盲目的に評価する実装では、毎日誤って本番環境が導入される可能性があります。`n`。 

最後に、ゼロ需要には特別な処理が必要です。 のために```
2 1 2 1 1
2 1
```答えは`0`。 最大プレフィックス不足は負またはゼロにすることができますが、満たされていない注文の数を負にすることはできません。 を忘れて`max(0, ...)`このような場合、最終的な式で否定的な答えが得られる可能性があります。 

## アプローチ

 単純な解決策は、すべてのタイプ 2 クエリに対してファクトリを明示的にシミュレートすることです。 選ばれた人のために`p`、すべてを歩き回ることができます`n`現在の在庫を維持し、生産が許可されたらその日の生産量を追加し、その日の需要に対してできるだけ多くのチョコレートを販売し、販売数を累積します。 これは正しいです。なぜなら、毎日できるだけ多く販売しても、将来に悪影響を与えることは決してないからです。今日売れなかったチョコレートは、後で入手できるようになりますが、在庫のある注文をすぐに満たしても、最終的に販売できる量を減らすことはできません。 

問題はコストです。 1 つのタイプ 2 クエリにかかる時間`O(n)`、そしてそれがあるかもしれません`q = 2 * 10^5`クエリ。 最悪の場合こうなる`O(nq) = O(2 * 10^10)`日中の業務は利用可能な時間をはるかに超えています。 

有益な観察は、実際には在庫をシミュレートする必要がないということです。 固定の生産スケジュールの場合は、日付の接頭語を考慮します。`1..i`。 せいぜい`P_i`それまでにチョコレートは生産できているはずなので、少なくとも`max(0, D_i-P_i)`そのプレフィックスからの注文は失われるはずです。 最悪のプレフィックス不足は、スケジュール全体に関する重要な唯一の情報です。 

最大のプレフィックス不足があると仮定します。`L`。 それならせいぜい`D_n-L`チョコレートが売れる。 この限界は、注文が利用可能になるたびに貪欲に売ることで達成できるため、答えは正確に次のとおりです。`D_n - max(0, max_i(D_i-P_i))`。 

残りのタスクは、需要が更新されている間にその最大値を迅速に評価することです。 

メンテナンス開始に向けて`p`、生産には 3 つの単純な形式があります。 メンテナンス前に、`P_i = bi`。 メンテナンス中は、`P_i = b(p-1)`。 メンテナンス後の生産は、`b(p-1) + a(i-p-k+1)`。 

プレフィックス要求から 3 つの配列を定義します。`F_i = D_i - bi`

`H_i = D_i`

`G_i = D_i - ai`。 

すると、メンテナンス前の最大赤字が最大値となります。`F_i`のために`i < p`。 メンテナンス中は最大値です`H_i`のために`p <= i <= p+k-1`、マイナス`b(p-1)`。 メンテナンス後は最大値です`G_i`のために`i >= p+k`にのみ依存する定数を加えたもの`p`。 

日中の需要更新`d`すべてのプレフィックス要求が増加します`D_i`と`i >= d`。 したがって、同じ値を追加します`F_i`、`H_i`、 そして`G_i`接尾語に`[d,n]`。 したがって、サフィックスの追加と範囲最大クエリをサポートするデータ構造が必要です。 遅延セグメント ツリーは、まさにこの操作を処理します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース |`O(nq)`|`O(n)`| 遅すぎる |
 | 最適 |`O((n+q) log n)`|`O(n)`| 承認済み |

 ## アルゴリズムのチュートリアル

 1. 3 つの概念配列を構築する`F`、`H`、 そして`G`すべての需要が最初はゼロであると仮定します。 位置で`i`、それらの値は`-bi`、`0`、 そして`-ai`。 これらは、まさに 3 つの制作フェーズに必要な表現です。 
2. 3 つの配列のそれぞれの最大値をすべてのセグメント ツリー ノードに格納します。 遅延値は、ノード全体に適用されたものの、その子にはまだプッシュされていない追加を記録します。 
3. アップデート時`(1, d, x)`が到着すると、総需要が増加します`x`。 プレフィックスの要求`D_i`のみ変更します`i >= d`ので、追加します`x`サフィックスの 3 つのセグメント ツリー値すべてに適用`[d,n]`。 
4. お問い合わせの場合`(2, p)`、 させて`m = p+k-1`。 日を 3 つの範囲に分割する`[1,p-1]`、`[p,m]`、 そして`[m+1,n]`。 セグメントツリーは、関連する最大値を次から見つけることができます。`F`、`H`、 そして`G`これらの範囲の場合。 
5. メンテナンス前までの日数については、`L = max(F_i)`以上`1 <= i < p`。 生産が行われているため、`bi`当日`i`、まさにこれです`max(D_i-P_i)`その範囲内で。 
6. メンテナンス日については、`M = max(H_i)`以上`p <= i <= m`。 メンテナンス日の終了までの生産は、`b(p-1)`、したがって、対応する赤字は`M-b(p-1)`。 
7. メンテナンス後の日数については、`R = max(G_i)`以上`m+1 <= i <= n`。 そんな日のために`i`、生産は`b(p-1) + a(i-p-k+1)`。 

この式を並べ替えると、`P_i = ai + (b-a)(p-1) - ak`。 

したがって、`D_i-P_i = G_i + (a-b)(p-1) + ak`。 

したがって、維持後の赤字は、`R + (a-b)(p-1) + ak`。 
8.テイク`L`、`M`、 そして`R`失われた需要の量はマイナスにはならないため、ゼロと組み合わせます。 もし`bad`が最大値である場合、答えは`D_n-bad`。 

### なぜ効果があるのか

 日で終わるすべてのプレフィックスについて`i`を超える戦略はありません。`P_i`そのプレフィックスに属する注文のチョコレート。 したがって、少なくとも`D_i-P_i`この数量が正の場合、注文は失われます。 したがって、最大のプレフィックス不足は、失われた注文数の下限になります。 

注文が入るたびにできるだけ多くのチョコレートを販売するという貪欲な戦略は、まさにこの限界を実現しています。 在庫が不十分な場合、その不足は正確に現在のプレフィックス需要からプレフィックス生産を差し引いたものとなり、発生する最大の不足は最大プレフィックス不足になります。 その後の生産が到着すると、その後の注文に対応できますが、すでに逃した注文を修復することはできません。 したがって、プレフィックスの最大赤字はまさに避けられない損失であり、それを総需要から差し引くことで、販売されるチョコレートの最適な数が得られます。 

セグメント ツリーは常に現在の値を表します。`F_i`、`H_i`、 そして`G_i`。 更新では、その要求の影響を受けるすべてのプレフィックス合計に同じ量が追加されるため、遅延サフィックス更新では 3 つの定義がすべて保持されます。 クエリは、各フェーズの正確な生成式に従ってプレフィックス不足を分割するため、ツリーによって返される最大値は、正確に考えられる最大のプレフィックス不足になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

NEG = -(10 ** 30)

class SegmentTree:
    def __init__(self, n, a, b):
        self.n = n
        self.a = a
        self.b = b

        size = 4 * n + 5
        self.f = [0] * size
        self.h = [0] * size
        self.g = [0] * size
        self.lazy = [0] * size

        self._build(1, 1, n)

    def _build(self, v, l, r):
        if l == r:
            self.f[v] = -self.b * l
            self.h[v] = 0
            self.g[v] = -self.a * l
            return

        mid = (l + r) >> 1
        self._build(v << 1, l, mid)
        self._build(v << 1 | 1, mid + 1, r)
        self._pull(v)

    def _pull(self, v):
        left = v << 1
        right = left | 1

        self.f[v] = max(self.f[left], self.f[right])
        self.h[v] = max(self.h[left], self.h[right])
        self.g[v] = max(self.g[left], self.g[right])

    def _apply(self, v, x):
        self.f[v] += x
        self.h[v] += x
        self.g[v] += x
        self.lazy[v] += x

    def _push(self, v):
        x = self.lazy[v]
        if x:
            left = v << 1
            self._apply(left, x)
            self._apply(left | 1, x)
            self.lazy[v] = 0

    def add_suffix(self, start, x):
        self._add_suffix(1, 1, self.n, start, x)

    def _add_suffix(self, v, l, r, start, x):
        if r < start:
            return

        if start <= l:
            self._apply(v, x)
            return

        self._push(v)

        mid = (l + r) >> 1
        self._add_suffix(v << 1, l, mid, start, x)
        self._add_suffix(v << 1 | 1, mid + 1, r, start, x)

        self._pull(v)

    def query_phases(self, p, m):
        return self._query_phases(1, 1, self.n, p, m)

    def _query_phases(self, v, l, r, p, m):
        if r < p:
            return self.f[v], NEG, NEG

        if l > m:
            return NEG, NEG, self.g[v]

        if p <= l and r <= m:
            return NEG, self.h[v], NEG

        self._push(v)

        mid = (l + r) >> 1

        lf, lh, lg = self._query_phases(v << 1, l, mid, p, m)
        rf, rh, rg = self._query_phases(
            v << 1 | 1, mid + 1, r, p, m
        )

        return (
            max(lf, rf),
            max(lh, rh),
            max(lg, rg),
        )

def solve():
    n, k, a, b, q = map(int, input().split())

    seg = SegmentTree(n, a, b)
    total_demand = 0
    out = []

    for _ in range(q):
        query = list(map(int, input().split()))

        if query[0] == 1:
            d, x = query[1], query[2]

            total_demand += x
            seg.add_suffix(d, x)

        else:
            p = query[1]
            m = p + k - 1

            before, during, after = seg.query_phases(p, m)

            bad = before

            if during != NEG:
                bad = max(bad, during - b * (p - 1))

            if after != NEG:
                bad = max(
                    bad,
                    after + (a - b) * (p - 1) + a * k
                )

            bad = max(0, bad)
            out.append(str(total_demand - bad))

    sys.stdout.write("\n".join(out))

if __name__ == "__main__":
    solve()
```同じプレフィックス需要が 3 つの異なる生成式と比較されるため、セグメント ツリーには各ノードに 3 つの最大値が含まれます。 3 つの値はすべてまったく同じサフィックスの追加を受け取るため、ノード全体には 1 つの遅延値で十分です。 

日の初期値`i`は`-bi`のために`F`、`0`のために`H`、 そして`-ai`のために`G`。 明示的な要求配列は必要ありません。 今日の更新`d`すべてのプレフィックスの合計を次から変更します`D_d`これが、更新がサフィックス範囲の追加となる理由です。 

クエリ ルーチンは、標準の範囲最大クエリよりもわずかに特殊化されています。 二つの境界線`p`そして`p+k-1`アレイ全体を 3 つの生産フェーズに分割します。 セグメントが完全に 1 つのフェーズ内にある場合は、対応する保存された最大値をすぐに返すことができます。 2 つの境界のうちの 1 つを越えるノードのみを再帰する必要があります。 これにより、3 つの独立した範囲クエリを回避しながら、各クエリの対数を維持します。 

の`NEG`値は空のフェーズにのみ使用されます。 これは、考えられる実際の値よりも意図的に大幅に小さくなっています。 総需要は最大でも`2 * 10^9`そして生産はせいぜい約`10^10`, ここで、Python の整数にはオーバーフローの懸念はありません。 

メンテナンス間隔は、`[p, p+k-1]`したがって、その右端点は次のように計算されます。`m = p+k-1`。 メンテナンス後の範囲は次から始まります`m+1 = p+k`。 これら 2 つの式は、オフバイワンの間違いが最も発生する場所です。

 ## 特殊なケース

 ### メンテナンスは 1 日目から開始します

 のために```
3 1 3 1 3
1 1 2
1 3 1
2 1
```我々は持っています`D = [2,2,3]`。 以来`p=1`そして`k=1`、生産量は`[0,3,3]`。 接頭辞の欠損は次のとおりです。`2`、`-1`、 そして`-3`したがって、最大赤字は`2`。 総需要は`3`、与える`3-2=1`。 

セグメントツリークエリでは、メンテナンス前の範囲は空で、メンテナンス範囲は日です。`1`、メンテナンス後の範囲は日です。`2..3`。 空の範囲が貢献します`NEG`, したがって、偶然に答えになることはありません。 

### メンテナンスはn日目に終了します

 のために```
4 2 3 1 2
1 4 10
2 3
```クエリには`p=3`そして`m=4`。 生産は`1`日に`1`そして`2`、その後生産が行われない日が続く`3`そして`4`。 工場にはちょうど 2 つのチョコレートがあり、注文はその日のものだけです`4`、したがって、答えは次のとおりです`2`。 

ツリーはメンテナンス範囲を使用します`[3,4]`そして空のメンテナンス後の範囲。 これはそれを直接確認します`p+k-1`、 それよりも`p+k`、最終メンテナンス日です。 

### メンテナンスは毎日カバーされます

 のために```
3 3 2 1 3
1 1 1
1 3 5
2 1
```我々は持っています`p=1`そして`k=3`、 それで`m=3=n`。 毎日がメンテナンスの日です。 保存されるメンテナンスの最大値は、`D_3=6`、他の 2 つの位相範囲は空です。 最大赤字は、`6`、総需要に等しいので、答えは次のようになります。`0`。 

実装には特別なケースは必要ありません。`k=n`。 前後の空の範囲は次のように表されます。`NEG`、一方、中間範囲は自然にセグメント ツリー全体をカバーします。 

### 需要ゼロ

 のために```
2 1 2 1 1
2 1
```すべての需要値はゼロです。 当日メンテナンス開始に伴い`1`、保存されたプレフィックス式はすべて非正であるため、生の最大赤字は最大でもゼロになります。 申請中`max(0, bad)`それを正確にゼロに変換すると、答えは次のようになります。`D_n-bad = 0`。 

これが、最終的なゼロへのクランプが 3 相計算の範囲外に属する理由です。 プレフィックスには余剰生産が存在する可能性がありますが、余剰生産によって負の数の不満た注文が生じることはありません。 

### 同じ日に繰り返し更新

 複数のタイプ 1 クエリが同じ日をターゲットにしている場合、各更新は既存の需要を置き換えるのではなく、既存の需要を追加します。 1 日が増分を受け取ると仮定します`4`、 それから`7`。 その需要は次のようになります`11`、その日以降に始まるすべてのプレフィックスは ずつ増加します。`11`合計で。 セグメント ツリーは 2 つのサフィックスの追加を実行するため、効果は自動的に蓄積されます。 

これは、毎日の最終需要のみを保存するだけでは処理中に不十分になる理由でもあります。 すべての更新により、後のタイプ 2 クエリで使用されるプレフィックス式が即座に変更され、遅延ツリーはプレフィックスの合計を再構築せずにそれらの変更を保存します。
