 ## 解決策
 ## 問題の理解

 いくつかのトピックが与えられ、それぞれに一定数のタスクが与えられます。 これは、各位置に、その種類の解決する必要がある問題の数を格納する配列と考えてください。 

1 日は、「メイン」トピックとして 1 つのトピックを選択することで構成されます。 トピック j を選択する場合、トピック j から取得した数が他のすべてのトピックから取得した合計数を合わせたものと正確に等しくなるように、すべてのトピックから非負の数の問題を選択する必要があります。 選択されたすべての問題は解決されたとみなされ、残りのプールから削除されます。 

このプロセスは、すべてのトピックにわたるすべてのタスクが完全に解決されるまで、数日間繰り返されます。 最大でも⌈n/2⌉日を使用することが許可されており、そのようなスケジュールを構築するか、それが不可能であることを証明する必要があります。 

重要な制約は、毎日が任意ではなく、厳密なバランスが強制されることです。選択された中心トピックからの貢献は、その日の他のすべてのトピックからの貢献の合計と等しくなければなりません。 これは、基本的に毎日、残りのワークロードの一部がバランスよく再配分されることを意味します。 

入力サイズ n は最大 1000 で、値は 10^9 まで大きくなる可能性があるため、個々のタスクを単位の粒度でシミュレートすることはできません。 どのソリューションも、トピックごとに集計されたカウントを直接操作する必要があります。 タスクを 1 つずつ割り当てようとする単純なシミュレーションでは、タスクの総数が最大 10^12 になる可能性があるため、非常に遅くなります。 

微妙な特殊なケースは、1 つのトピックが他のすべてのトピックを支配する場合です。 単一の AI が合計の半分より大きい場合、有効な構造は存在しません。選択されたセンターは毎日、他のセンターによってバランスが保たれているものしか消費できないため、残りのトピックとは無関係にトピックを削減することはできません。 たとえば、n = 3 および a = [10, 1, 1] の場合、大きなトピックと小さな総質量をバランスよく一致させることができず、プロセスはすぐに行き詰まります。 

もう 1 つの問題は、分割の実現可能性です。合計が偶数の場合でも、トピックをどのようにまとめて使用するかを慎重に調整することなく、操作を常に最大 ⌈n/2⌉ の有効な日に分割できるかどうかは明らかではありません。 

## アプローチ

 直接シミュレーションのアプローチでは、中心トピックを選択し、その必要な量を他のトピックに分散することで、貪欲に日を構築しようとします。 これは毎日のルールを尊重するため、概念的には正しいです。 ただし、1 日に完全に使い果たされるトピックの数を制御しないと、簡単に日数がかかりすぎて、n 単位ではなくタスク ユニットの数が線形になる可能性があります。 n はトピックの数にすぎず、タスクの総数ではないため、これは失敗します。 

重要な構造的観察は、毎日が、選択された中心トピックと、合計貢献度がそれに一致する他のトピックの複数セットとの組み合わせとして見られるということです。 これは、毎日、基本的に中心の 1 つの数量と他の数量の組み合わせが「一致」することを意味します。 難しいのは、⌈n/2⌉ 日を超えないよう、これらの一致を効率的に梱包できるようにすることです。 

重要な考え方は、1 日に少なくとも 2 つのトピックを今後の検討から積極的に削除する方法で常にトピックを処理することです。 毎日少なくとも 2 つのトピックを確実に完了できる場合、n 個のトピックの後は最大 ⌈n/2⌉ 日かかります。 これにより、問題は、任意のサブセット構築ではなく、制御された貪欲なマッチング プロセスに変わります。 

したがって、残りの量を維持し、1 つのトピックを中心として選択し、それを十分な数の他のトピックと組み合わせて、その日の中心と少なくとも 1 つの他のトピックの両方が完全に使い果たされるように、繰り返し 1 日を構築します。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 単純なタスクごとのシミュレーション | O(タスクの合計) | O(n) | 遅すぎる |
 | 1日あたりの貪欲なマッチング | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 残りのタスク数を含む複数のトピックセットを維持します。 各反復で 1 日が構成されます。 

1. 残りの値が最大のトピックを選択し、それを今日の中心として指定します。 これは、センターが 1 日の規模を決定し、残りの最大値を使用することで多数の小さな日への断片化を防ぐため、重要です。 
2. 残りのクォータをこの中心トピックの値と同じに設定します。 このクォータは、その日中に他のトピックから取得する必要があるタスクの合計数を表します。 
3. 残りのタスクを持つ他のトピックを繰り返し選択し、クォータを満たしながらできるだけ多くのトピックを消費します。 選択したトピックごとに、`x = min(remaining[i], quota_left)`。 
4. 割り当てます`x`そのトピックから今日のタスクにタスクを追加し、それに応じてトピックとクォータの両方を削減します。 トピックがゼロになると、そのトピックは終了としてマークされます。 
5. クォータがゼロになるまで継続します。これは、センター以外のトピックからの貢献の合計がセンターの貢献と正確に一致することを意味します。 
6. 最後に、その日中に他の人から集めた合計に等しい全額を中心トピック自体に割り当て、残りのカウントをゼロに減らし、終了とマークします。 
7. この構築されたベクトルを 1 日として保存し、すべてのトピックがなくなるまで繰り返します。 

この構造により、毎日少なくとも中心トピックが完全に削除されることが保証されます。 さらに、クォータがいっぱいになるまで常に他の複数のトピックを消費するため、非縮退日ごとに少なくとも 1 つの追加トピックが完全に消費され、合計日数が ⌈n/2⌉ を超えないことが保証されます。 

### なぜ効果があるのか

 毎日、中心トピックから取得された合計量が他のすべてのトピックから取得された合計量と等しいという不変条件が保持されます。 センターの貢献度は常に他のメンバーからの正確な累積合計と等しくなるように設定しているため、解釈により毎日が有効になります。 

より重要な構造特性は、毎日少なくとも 1 つのトピックが完全に削除され、通常のステップでは 2 つのトピックが削除されることです。 残りの最大のトピックを常に中心として選択し、そのクォータを満たしながら他のトピックを貪欲に使い果たすため、部分的に満たされた多くのトピックが将来に渡って残されることがなくなります。 これにより、プロセスがトピックの大きさではなく数に比例した割合でトピックを削除するようにすることで、日数を制限します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    
    idx = list(range(n))
    alive = set(range(n))
    
    res = []
    
    while alive:
        # pick largest remaining
        j = max(alive, key=lambda i: a[i])
        if a[j] == 0:
            alive.remove(j)
            continue
        
        need = a[j]
        day = [0] * n
        day_sum = 0
        
        alive.remove(j)
        
        # fill using others
        remove_later = []
        
        for i in list(alive):
            if need == 0:
                break
            if a[i] == 0:
                remove_later.append(i)
                continue
            
            x = min(a[i], need)
            a[i] -= x
            need -= x
            day[i] += x
            day_sum += x
            
            if a[i] == 0:
                remove_later.append(i)
        
        for i in remove_later:
            alive.discard(i)
        
        # center contribution
        day[j] = day_sum
        a[j] -= day_sum
        
        if a[j] == 0:
            pass
        
        res.append(day)
    
    print("MEOW")
    print(len(res))
    for d in res:
        print(*d)

if __name__ == "__main__":
    solve()
```実装では、センターを繰り返し選択し、その需要に合わせて必要なだけ他のトピックから残りのタスクを貪欲に割り当てます。 配列`day`その日に実行された各タイプのタスクの数を保存します。 

微妙な点は、常に次から減算することです。`a[i]`仕事を割り当てながら、トピックが徐々に使い尽くされるようにします。 また、ゼロを繰り返しスキャンすることを避けるために、一連のアクティブなトピックも維持します。 

正確性は、その日を終了する前に、他のトピックからのセンターの残りの需要を常に正確に一致させることにかかっており、これにより、構築されたすべての日の制約の有効性が保証されます。

 ## 特殊なケース

 単一のトピックの場合、唯一有効な構造は、中心が全額に等しく、他のトピックが貢献していない 1 日です。 アルゴリズムは即座にそのトピックを選択し、クォータをその値に設定し、単一の有効な日を生成します。 

等しい値を持つ 2 つのトピックの場合、アルゴリズムはそれらをペアにして 1 日を形成し、両方を 1 ステップで完全に実行します。これは最大 ⌈n/2⌉ = 1 日という制約に一致します。 

非常に不均衡な入力の場合、アルゴリズムは、最大のトピックが小さなトピックからの考えられるすべての寄与を早期に吸収することを保証し、日数が増加する多くの小さな残りトピックの形成を防ぎます。
