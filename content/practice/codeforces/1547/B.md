 ## 解決策
 ## 問題の理解

 文字列が与えられましたが、それが左から右の選択肢から文字列を構築する非常に特殊なプロセスによって構築された可能性があるかどうかを判断する必要があります。 このプロセスは空の文字列から始まり、次にアルファベット順に文字を導入します。`'a'`、 それから`'b'`、 等々。 新しい文字が到着するたびに、現在の文字列の中央ではなく、左端または右端に配置する必要があります。 

したがって、最終的な文字列は、次のアルファベット文字を繰り返し取得し、それがすでに構築されているものの左境界に行くか右境界に行くかを決定した結果です。 問題は、これらの境界挿入のシーケンスによって指定された文字列が生成されるかどうかです。 

重要な構造上の制約は、各文字が`'a'`に`'z'`は構築プロセスで最大 1 回しか表示されず、文字が配置されると、その端が唯一のアクティブな挿入ポイントとなる成長ブロックの一部になります。 

テスト ケースごとの入力サイズは最大 26 文字であるため、高度な最適化や組み合わせ検索は必要ありません。 26 は定数なので、すべての文字を複数回検査するソリューションでも安全です。 最大 10^4 のテスト ケースでも、約 2.6 × 10^5 文字の操作のみを実行しますが、これは簡単です。 

主な非明白な障害のケースは、局所的には一貫しているように見えても、有効な境界挿入によって形成できない文字列に起因します。 

典型的な例は次のとおりです`"acb"`。 アルファベットの接頭辞に連続した文字が含まれているため、一見、もっともらしく見えますが、挿入する方法はありません。`'c'`後`'a'`そして`'b'`すでにそのように位置付けられています`'c'`エンドポイントでのみ移動できます。 別の例は`"ca"`、 どこ`'a'`そして`'c'`～という規則に違反する`'b'`前に現れる必要があります`'c'`最終的な文字列に存在しない場合でも、構築プロセスで使用されます。 

もう一つの微妙なケースは、`"aa"`。 同じ文字を異なる端に 2 回挿入すると重複が発生するように見えますが、プロセスでは各文字が 1 回ずつ明示的に挿入されるため、繰り返しにより文字列が即座に無効になります。 

## アプローチ

 ブルートフォースアプローチでは、文字列を構築する可能なすべての方法をシミュレートしようとします。 テストケースごとに、再帰的に配置してみることができます。`'a'`どちらかの端で、その後`'b'`どちらかの端などで、ターゲット文字列に到達できるかどうかを確認します。 各ステップで可能性の数が 2 倍になるため、これは 2^n 状態になります。 n は最大 26 ですが、2^26 はすでに大きく、テスト ケースが 10^4 の場合、このアプローチは概念的にコストが高すぎて不必要になります。 

重要な観察は、どの文字が出現する必要があるかという点で、プロセスが完全に決定的であるということです。文字列には、から始まるアルファベットの連続した接頭辞が正確に含まれている必要があります。`'a'`、各ステップは、次に期待される文字の残りの有効な位置の左端または右端のいずれかを削除します。 これは、プロセスを構築する代わりに、プロセスを逆にできることを意味します。 

文字列を前方に構築する代わりに、現在予想される最小の文字を繰り返し識別します (`'a'`) を調べて、それが現在の文字列のどちらかの端にあるかどうかを確認します。 存在する場合は、それを削除して続行します。 いずれかの時点でどちらかの端になければ、建設は不可能です。 

これにより、配置に対する指数関数的な検索の問題が、テスト ケースごとの線形の貪欲なチェックに軽減されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^n) | O(n) | 遅すぎる |
 | 最適な貪欲さ | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 文字列を、アルファベット順に文字を剥がすにつれて縮小する動的な間隔として扱います。 

1. 2 つのポインタを初期化します。1 つは文字列の左端に、もう 1 つは文字列の右端にあります。 期待される文字を次のように設定します`'a'`。 これは、建設中に導入されたに違いないことを反映しています。`'a'`初め。 
2. 予期される文字が文字列内に存在する最大文字を超えていない場合は、その文字を現在間隔の両端にある文字と比較します。 
3. 左端が予想される文字と一致する場合、左ポインタを内側に移動し、予想される文字を次の文字に進めます。 これは、構築中に文字が左側に挿入された場合に対応します。 
4. 右端が予想される文字と一致する場合は、右ポインタを内側に移動して、予想される文字を進めます。 これは右側への挿入に相当します。 
5. どちらの端も予期される文字と一致しない場合は、終了して NO を返します。これは、この文字を内部に配置できる有効な構築ステップがないためです。 
6. すべての文字が順番に正常に消費された場合は、YES を返します。 

この貪欲な選択が有効である理由は、各ステップで、次に必要な文字が境界の 1 つで公開される必要があるためです。 有効な構造は、それが挿入された時点でアクセス可能な状態にしておく必要があります。これは、小さな文字はすべてすでに配置されており、考慮から除外されているためです。 

### なぜ効果があるのか

 有効な構造のどの時点でも、残りの部分文字列は、まだ配置されていない文字によって形成される連続ブロックに正確に対応します。 次に必要な文字は、未使用のアルファベットの最小文字であり、その段階で残っている構造の最後に追加されている必要があります。 したがって、現在の間隔の両端のいずれかに位置する必要があります。 それがどちらの端にもない場合、以前の一連の左または右の挿入によって、構築順序に違反することなく中央にそれを隠すことはできませんでした。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    s = input().strip()
    l, r = 0, len(s) - 1
    
    expected = ord('a')
    ok = True
    
    while l <= r:
        if s[l] == chr(expected):
            l += 1
            expected += 1
        elif s[r] == chr(expected):
            r -= 1
            expected += 1
        else:
            ok = False
            break
    
    print("YES" if ok else "NO")
```この実装は、貪欲なアイデアを直接反映しています。 2 つのポインターは、まだ検証されていない文字列の現在のアクティブなセグメントを維持します。 の`expected`変数は、次に必要なアルファベット文字を追跡します。 各反復では正確に 1 文字を消費するため、テスト ケースごとに直線的な時間が保証されます。 構築ルールでは境界での挿入のみが許可されるため、両端のチェックで十分です。 

よくある間違いは、建設を前からシミュレーションしようとすることで、配置の選択が曖昧になってしまいます。 プロセスを逆にすると、その曖昧さが完全に排除されます。

 ## 特殊なケース

 のために`"a"`、アルゴリズムセット`l = r = 0`、わかります`'a'`左側で、それを消費し、すぐに成功で終了します。 これにより、単一文字の文字列が自明に有効であることが確認されます。 

のために`"aa"`、最初の比較が一致します`'a'`一方の端ではそれを消費しますが、もう一方の端では`'a'`予期されるシーケンスが次の文字に移動するため、予期される次の文字に一致することはできません。`'b'`。 2キャラ目はまだなので`'a'`の場合、プロセスは失敗し、重複は正しく拒否されます。 

のために`"z"`単独では、期待される文字は次から始まります`'a'`、しかしどちらの端も一致しないため、アルゴリズムはすぐに拒否し、構造内で以前のアルファベット文字をスキップすることが不可能であることを反映しています。
