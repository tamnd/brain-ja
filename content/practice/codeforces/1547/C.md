 ## 解決策
 ## 問題の理解

 2 人のプログラマーが同じファイルの編集に貢献していますが、彼らの作業履歴は時間の経過とともに交互に挿入されます。 私たちには、各人に 1 つずつ、2 つの順序付けられた一連のアクションが与えられます。 各アクションは、ファイルの末尾への挿入、または既存の行の編集のいずれかです。 ファイルは初期の行数で始まり、両方の人が同じ進化するファイル状態の下で操作します。 

課題は、すべての行動の有効なグローバル タイムラインを再構築し、このタイムラインを各人の行動に順番に投影すると、元のシーケンスが復元されるようにすることです。 同時に、すべての編集アクションは、その時点でターゲット行がファイル内にすでに存在した後にのみ実行する必要があります。 

したがって、この構造は、動的状態変数を使用した 2 つのシーケンスの制約されたマージです。ファイル内の現在の行数は挿入によってのみ増加し、編集はその数が十分に大きいかどうかに依存します。 

各シーケンスの長さは最大 100 で、テスト ケースの数は最大 1000 であるため、制約は十分小さいため、O(nm) の動的構築は既に快適に通過します。 これにより、最悪の場合の操作の合計は最大でも数千万回程度になりますが、単純な遷移では Python ではまだ安全です。 ただし、問題の構造により、よりクリーンな貪欲な構築が可能になります。 

単純で間違ったアプローチは、編集が現在有効であるかどうかを追跡せずに、どちらかのシーケンスから次に利用可能なアクションを常に実行することによって、単純に貪欲にマージすることです。 たとえば、ファイルのサイズが 3 で、次に選択されたアクションが「10 行目の編集」である場合、後で挿入することで可能になったとしても、これは無効になります。 これは、実現可能性がローカル順序だけでなく将来の挿入に依存するため、失敗します。 

もう 1 つの微妙な失敗は、一方のシーケンスが、他方のシーケンスが現在提供しているよりも多くの挿入を必要とする初期の編集を強制した場合に発生します。 現在のファイル サイズを明示的に追跡しない場合、不可能なインターリーブを受け入れたり、間違ったプレフィックスにすでにコミットした後で誤って -1 を返したりする可能性があります。 

## アプローチ

 ブルートフォースの観点は、現在のファイル サイズを維持し、すべての編集が有効であることを確認しながら、各ポイントで Monocarp の次のアクションまたは Polycarp の次のアクションのいずれかを選択して、マージされたシーケンスを段階的に構築することを考えることです。 これは基本的にすべてのインターリーブに対する検索であり、最悪の場合はすべての二項 (n + m, n) の可能性を探索します。 枝刈りを行っても、分岐因子は 2 のままで、深さは n + m になるため、指数関数的になります。 

重要な観察は、恣意的に推測する必要は決してないということです。 各ステップで、いずれかのシーケンスで挿入が可能な場合は、編集によってファイル サイズを増やす必要がない限り、挿入を遅らせても安全です。 進行を妨げる可能性がある唯一の制約は、現在のサイズより大きい行番号をターゲットとする編集です。 これは、挿入が自由に延期できるリソースのように動作するのに対し、編集は現在の状態に厳密な最小要件を課すことを意味します。 

これにより、シーケンスへの 2 つのポインターを維持し、ファイルをシミュレートする貪欲な構築が可能になります。 次のアクションが両方とも編集である場合、または一方の編集が現在不可能である場合は、ファイルが十分に大きくなるまで、最初に挿入を選択する必要があります。 両方のアクションが挿入である場合は、どちらかを安全に選択できます。 

これにより、一度アクションが実行されると、ファイル サイズの制約を尊重する限り、将来の実現可能性が無効になることはないため、すべての後戻りが排除されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(2^(n+m)) | O(n+m) | 遅すぎる |
 | 貪欲なシミュレーション | O(n+m) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 ファイル内に現在何行存在するかを追跡しながらプロセスをシミュレートします。

1. ファイル サイズを k として初期化し、2 つのシーケンスの先頭に 2 つのポインター i と j を設定します。 また、空の結果リストも維持します。 
2. 各ステップで、Monocarp の次のアクションを実行できるか、Polycarp の次のアクションを実行できるかを確認します。 
3. 両方のシーケンスが枯渇した場合、プロセスは終了し、結果が出力されます。 
4. Monocarp にアクションがまだ残っている場合は、次のアクションを確認します。 挿入の場合、挿入はファイル サイズに依存しないため、常に有効です。 行 x に対する編集の場合、x が現在のファイル サイズ以下である場合にのみ有効です。 
5. Polycarp の次のアクションに対しても同じ妥当性チェックを実行します。 
6. 次のアクションが両方とも有効な場合は、将来の柔軟性が制限されないため、どちらかの挿入が存在する場合は、どちらかの挿入を優先します。 両方が編集である場合は、有効な方を選択する必要があります。 
7. 次の 2 つのアクションのうち 1 つだけが有効な場合は、それを実行する必要があります。 
8. どちらのアクションも有効でない場合は、どちらもまだ存在しない行を必要とする編集であることを意味します。 その場合、可能な唯一の方法は将来の挿入を必要とすることですが、どちらのシーケンスもシミュレーションのこの時点では挿入を許可していないため、答えは不可能です。 
9. 挿入を行うと、ファイル サイズが増加します。 編集してもファイルサイズは変わりません。 

### なぜ効果があるのか

 重要な不変条件は、すべてのステップで、現在のファイル サイズがマージされたシーケンス内にすでに配置されている挿入の数と等しいということです。 編集は最大でもこのサイズのインデックスを参照する場合にのみ受け入れられるため、無効な状態が構築されることはありません。 挿入は今後の編集によって制約されることがないため、挿入を延期しても実現可能性が低下することはなく、柔軟性が高まるだけです。 したがって、選択肢が存在する場合は常に、挿入を優先しても有効な解決策が妨げられることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

t = int(input())
for _ in range(t):
    input()
    k, n, m = map(int, input().split())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    i = j = 0
    cur = k
    res = []

    ok = True

    while i < n or j < m:
        moved = False

        if i < n and a[i] == 0:
            res.append(0)
            cur += 1
            i += 1
            moved = True
        elif j < m and b[j] == 0:
            res.append(0)
            cur += 1
            j += 1
            moved = True
        elif i < n and a[i] <= cur:
            res.append(a[i])
            i += 1
            moved = True
        elif j < m and b[j] <= cur:
            res.append(b[j])
            j += 1
            moved = True

        if not moved:
            ok = False
            break

    if ok:
        print(*res)
    else:
        print(-1)
```このソリューションは、進化するファイルの直接シミュレーションを維持します。 ポインタのペアは各シーケンスがどれだけ消費されたかを追跡し、変数は`cur`現在の既存の行数を表します。 挿入するとこのカウンタがすぐに増加します。これは、その後の編集の有効性がこのカウンタに依存するため重要です。 順序付けロジックは、制約を消費することなく将来の編集の実現可能性を厳密に高めるため、可能な限り挿入を優先します。 

微妙な点は、編集は編集が行われた時点の現在のサイズに対してのみチェックされ、将来の潜在的なサイズに対しては決してチェックされないことです。 これが、貪欲な戦略を安全にする理由です。編集が現在有効でない場合、まだスケジュールすることはできません。また、編集を遅らせることができるのは、少なくとも 1 つのシーケンスの後で何らかの挿入が出現する場合のみです。 

## 実用的な例

 k = 3、Monocarp が [2, 0]、Polycarp が [0, 5] であるサンプルを考えてみましょう。 

最初は、cur = 3、i = 0、j = 0 です。両方の最初のアクションが使用可能ですが、Polycarp には最初に挿入があるため、Polycarp から 0 を取得します。 現在 cur = 4 です。次に、Monocarp は編集 2 を実行できるので、それを実行します。 次に、Monocarp が挿入し、次に Polycarp が 5 を編集します。 

| ステップ | 私 | j | カー | 実行されたアクション | 状態 |
 | --- | --- | --- | --- | --- | --- |
 | 1 | 0 | 0 | 3 | 0 (ポリカルプ) | cur=4 |
 | 2 | 0 | 1 | 4 | 2 (単果皮) | cur=4 |
 | 3 | 1 | 1 | 4 | 0 (単果皮) | cur=5 |
 | 4 | 2 | 1 | 5 | 5 (ポリカルプ) | 完了 |

 これは、後の編集のロックを解除するために、挿入を早期に使用する方法を示しています。 

ここで、失敗のケースを考えてみましょう: k = 0、a = [1]、b = [2]。 初期状態では cur = 0 であり、次のアクションは両方とも無効な編集です。 どちらのシーケンスも最初に挿入を提供しないため、アルゴリズムはすぐに停止し、-1 を返します。 これは、どちらの編集も事前の挿入がなければ有効になりませんが、どちらのシーケンスも先頭に編集を提供していないため、順序付けが不可能であるという事実を反映しています。

 ## 特殊なケース

 重要なエッジ ケースは、両方のシーケンスが k より大きいライン インデックスを必要とする編集で始まる場合です。 たとえば、k = 1、a = [5]、b = [6]です。 どちらのシーケンスも、最初のアクションが必要になる前にファイル サイズが増加するほど早い段階で挿入を行うことができないため、アルゴリズムは正しく -1 を返します。 

もう 1 つのケースは、一方のシーケンスでは挿入が遅延しているが、もう一方のシーケンスでは挿入が可能である場合です。 貪欲な選択により、利用可能な場合は常に挿入がすぐに消費されるようになり、ファイル サイズの増加に依存する後の編集が人為的にブロックされるのを防ぎます。
