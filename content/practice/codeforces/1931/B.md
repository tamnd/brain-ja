 ## 解決策
 ## 問題の理解

 いくつかの独立したシナリオが与えられています。 各シナリオには一連のコンテナがあり、それぞれにある程度の量の水が入っています。 水を移動することは許可されていますが、左側の容器から右側の容器に移動することのみです。 目標は、最終的にすべての容器にまったく同じ量になるように水を再分配できるかどうかを決定することです。 

唯一許可される操作は方向性移動です。つまり、i < j でインデックス i と j を選択し、負でない量の水を i から j に移動します。 これは、水は右方向にのみ流れることができ、左方向には決して流れることができませんが、中間位置を介して任意に分割したり結合したりできることを意味します。 

すべてのテスト ケースにわたる n が最大 2⋅10^5 という制約は、テストごとに線形または線形に近い解が必要であることを意味します。 転送のシミュレーションや位置の繰り返しの固定などの 2 次的な操作は、最悪の場合の合計操作が 10^10 を超えるため、すぐに失敗します。 

合計を n で割った値は小さいが、初期のコンテナーが低すぎる場合、微妙なエッジ ケースが発生します。 たとえば、最初の要素がすでにターゲットよりも大きい場合、失敗が疑われるかもしれませんが、超過分は右方向に押し出される可能性があるため、自動的に失格になるわけではありません。 逆に、初期のプレフィックス合計が常に「あるべき」値を下回っている場合、水は左に移動できないため、後で補償することができない可能性があります。 

素朴な直感による小さな失敗例を次に示します。 

入力:

 n = 3、a = [0、3、0]

 目標は1です。合計は割り切れるのに、最初のコンテナが目標よりも下から始まりますが、右側から受信できるので問題ありません。 ただし、方向の制約を逆にすると状況は大きく変わり、方向性が問題の核心であることがわかります。 

## アプローチ

 ブルートフォース シミュレーションでは、不均衡を減らすために i < j のペアを繰り返し選択し、水を前方に押し出そうとします。 目標より上の位置をスキャンし、余分な部分を右に押し出すループを維持することもできます。 最悪の場合、水の各ユニットは O(n) 個の位置を移動する可能性があり、O(sum a_i) 個のユニットが存在します。 これにより、最悪の場合、演算が 10^9 から 10^10 のオーダーで複雑になりますが、これは現実的ではありません。 

重要な構造上の観察は、操作制約によって接頭辞条件が課されるということです。 水は右にのみ移動するため、プレフィックス内の不足は、より早い段階でそのプレフィックス内から完全に満たされる必要があります。 接頭辞の境界を超えると、以前の不足を解消するために水を戻すことはできません。 

これにより、きれいな不変条件が得られます。つまり、すべてのプレフィックスで、そのプレフィックスが最終的な均一レベルに達するのをサポートするのに十分な総水量が必要になります。 最終レベルは avg = total / n として固定されているため、最初の k 位置で必要な量は正確に k * avg です。 したがって、重要なのは、実行中のプレフィックスの合計が k * avg を下回るかどうかだけです。 

これにより、問題は 1 回のリニア スキャンに軽減されます。

 | ブルートフォースシミュレーション | O(n · 合計) | お(1) | 遅すぎる |
 | プレフィックスバランスチェック | O(n) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 目標値 avg = sum(a) / n を計算します。 総質量は保存されるため、これがコンテナごとに可能な唯一の最終値です。 
2. 実行中のプレフィックス合計変数を 0 に初期化します。 
3. 配列を左から右に繰り返します。 
4. 各位置 i で、実行中のプレフィックス合計に a[i] を加算します。 
5. このプレフィックスに必要な量、つまり (i + 1) * avg を計算します。 
6. どこかの時点でプレフィックスの合計が厳密に必要な値を下回った場合は、直ちにそれは不可能であると結論付けます。 
7. ループが違反なく完了した場合は、可能であると判断します。

必要なプレフィックスの合計と比較する理由は、インデックス i を超えると、その後の操作で水をインデックス ≤ i に戻すことができないためです。 したがって、実現可能性は完全に、初期のポジションが蓄積した以上の水を「借りている」かどうかにかかっています。 

### なぜ効果があるのか

 水を右にのみ移動させるプロセスは、接頭語が将来のセグメントとは無関係に一方向に進化することを意味します。つまり、将来の位置はそれ自体とその右側の位置のみを助けることができます。 したがって、プレフィックスの不足は回復できません。 

最終的な構成を想像すると、すべてのプレフィックスに正確に比例した割合の水が含まれている必要があります。 スキャン中に現在のプレフィックスの合計が必要な値よりも少ないことが観察された場合、たとえすべての残りの水が最適に配置されたとしても、すでに違反したプレフィックス境界を補償することはできません。補償するには水を境界を越えて左に移動する必要があるためです。 

この不変条件は、実現可能性を完全に特徴づけます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n = int(input())
        a = list(map(int, input().split()))
        
        total = sum(a)
        avg = total // n
        
        pref = 0
        ok = True
        
        for i, x in enumerate(a):
            pref += x
            if pref < (i + 1) * avg:
                ok = False
                break
        
        print("YES" if ok else "NO")

if __name__ == "__main__":
    solve()
```このソリューションでは、最初にグローバル目標値を計算します。 次に、左から右にスキャンしながらプレフィックス アキュムレータを維持します。 重要なチェックでは、蓄積された水をその時点までに必要な均一な分布と比較します。 プレフィックスが不足すると、後から修正することはできないため、関数は早期に停止します。 

よくある実装上の落とし穴は、この問題では割り切れる可能性が保証されているため、ここでは整数の割り算が安全であることを忘れていることです。 もう 1 つの微妙な問題は、明示的なプレフィックス比較の代わりに実行中の「差分」を使用することです。 どちらも機能しますが、プレフィックスの定式化の方がエラーが発生しにくくなります。

 ## 特殊なケース

 重要なエッジ ケースは、初期の要素がターゲットよりも小さいが、後の要素に十分な余剰が含まれている場合です。 たとえば、[0, 0, 10] (avg = 3) です。合計は十分ですが、最初の位置には 3 単位が必要ですが 0 があり、最終状態の解釈では右側から受け取ることができないため、最初のプレフィックスはすでに要件に違反しています。 

もう 1 つのケースは、配列がすでに均一である場合です。 アルゴリズムは引き続きプレフィックスをチェックしますが、違反することはないため、操作を実行せずに正しく YES を返します。 

最後に、再配布が必要なく、プレフィックス条件がすべてのステップで空に満たされるため、単一要素配列は常に成功します。
