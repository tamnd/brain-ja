 ## 問題の理解

 同じ長さの 2 つの配列が与えられています。 最初の配列は、値の二乗和を通じてセグメントのコストに寄与し、2 番目の配列は、要素の二乗のビット単位の OR を通じてセグメントの値に寄与します。 

インデックスからの任意のサブ配列の場合`l`に`r`、2 つの量を計算します。 1つ目は累積合計です`a[i]^2`その範囲を超えています。 2 番目は単一の数値の 2 乗、つまりすべての数値のビット単位の OR です。`b[i]`その範囲内で。 最初の数量が 2 番目の数量よりも厳密に小さい場合、セグメントは良好と呼ばれます。 

タスクは、この不等式を満たすサブ配列の数を数えることです。 

制約により、最大 200,000 個の要素が許可されます。 すべての O(n^2) 部分配列を直接検査するソリューションは、最悪の場合でも 4e10 程度の評価が必要となるため、直ちに遅すぎます。 O(n^2) の前処理ですら実行不可能であるため、ソリューションではセグメント値を最初から再計算することを回避する必要があります。 

微妙な難しさは OR 演算にあります。 合計とは異なり、可逆ではありませんが、単調です。セグメントを拡張しても、OR 結果からビットが削除されることはなく、追加または保持されるだけです。 この単調性が重要な構造特性です。 

小さなエッジケースは、素朴な思考が失敗する理由を示しています。 すべてだとします`b[i] = 0`。 この場合、すべてのセグメントの OR は 0 に等しいため、右側は常に 0 になります。 条件はこうなります`sum of squares < 0`、それは不可能なので、答えはゼロです。 誤って正の値を仮定したり、二乗を忘れたりするアプローチは、カウントを誤る可能性があります。 

もう 1 つの特殊なケースは、すべてが`b[i]`は同じ大きな値です。 この場合、OR はセグメントの長さによって変化しないため、右側は一定ですが、左側は長さに応じて増加します。 これは、非常に短いセグメントのみが適格であることを意味し、プルーニングを行わない単純な拡張ベースのアプローチでは、長い無効なセグメントを探索する時間が無駄になります。 

## アプローチ

 ブルート フォース ソリューションでは、すべての部分配列を列挙し、両方の量を独立して計算します。 それぞれについて`(l, r)`の二乗和を計算します。`a[l..r]`とのOR`b[l..r]`、ORを二乗して比較します。 これは正しいですが、プレフィックスの合計がある場合でも、サブ配列ごとに O(n) の作業が必要です。`a`。 ビット数を維持しない限り、OR を効率的に更新することはできません。その場合でも、各更新は O(1) ですが、依然として O(n^2) 状態を超えます。 これにより、最悪の場合、およそ 2e10 回の操作が必要となり、これは制限をはるかに超えています。 

重要な観察は、両方の式が区間拡張に関して反対の方法で単調に動作することです。 平方和は、右の端点を延長した場合にのみ増加します。 OR も増加するか同じままであるため、その 2 乗も減少しません。 これは、固定された左側のエンドポイントの場合、セグメントが有効または無効になると、右側のエンドポイントを延長しても予測不能に振動することはないことを意味します。 

この構造は、2 ポインターまたはスライディング ウィンドウ手法を示唆しています。 それぞれの左端点について、条件を維持しながら右端点をどこまで延長できるかを見つけたいと考えています。 両方の量を増分的に維持できれば、ポインタを線形時間でシフトできます。 

現在のウィンドウを維持します`[l, r]`。 の二乗和を段階的に更新します。`a`とのOR`b`。 不等式が成立する場合、安全に拡張できます。`r`。 失敗したら移動する`l`転送してその寄与を削除します。 課題は、OR から削除するにはビット数を追跡​​して、ビットがウィンドウから完全に消えた時期を知る必要があることです。 

これにより、各要素がウィンドウに出入りするのは最大 1 回となり、O(n) の償却構造が得られます。

### なぜ効果があるのか

 固定左端点の場合は、次の関数を定義します。`r`比較する`sum(a[l..r]^2)`そして`(OR(b[l..r]))^2`。 として`r`増加しますが、両側は減少しません。 したがって、ある時点で条件が false になった場合、`r`、すべての大きなインデックスに対して false のままになります。 これは、各エンドポイントの正しいエンドポイントの連続した有効なプレフィックスを意味します。`l`。 2 ポインター方式はこのプレフィックス長を正確に取得し、すべての有効なサブ配列が 1 回だけカウントされるようにします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    b = list(map(int, input().split()))

    bit_count = [0] * 32
    cur_or = 0
    cur_sum = 0

    def add(x):
        nonlocal cur_or, cur_sum
        cur_sum += x * x
        for i in range(32):
            if x & (1 << i):
                bit_count[i] += 1
                cur_or |= (1 << i)

    def remove(x):
        nonlocal cur_or, cur_sum
        cur_sum -= x * x
        for i in range(32):
            if x & (1 << i):
                bit_count[i] -= 1
                if bit_count[i] == 0:
                    cur_or &= ~(1 << i)

    r = 0
    ans = 0

    for l in range(n):
        while r < n:
            # try add b[r]
            x = b[r]
            old_sum = cur_sum
            old_or = cur_or

            add(a[r])
            add_b = x
            # temporarily simulate b addition separately
            new_or = cur_or | x

            if cur_sum < new_or * new_or:
                cur_or = new_or
                r += 1
            else:
                cur_sum = old_sum
                cur_or = old_or
                break

        ans += r - l

        remove(a[l])
        remove(b[l])

    print(ans)

if __name__ == "__main__":
    solve()

微妙な点の 1 つは、失敗した拡張機能を永続的に適用しないようにすることです。`r`。 コードは追加を一時的にシミュレートします。`b[r]`、有効性をチェックし、条件を破る場合はロールバックします。 これにより、正確性を維持しながら、より複雑なロールバック構造の必要性が回避されます。

 ## 特殊なケース

 すべての値が`b`がゼロの場合、OR は常にゼロになるため、すべての 2 乗 OR はゼロになります。 アルゴリズムは正しく維持します`current_or = 0`ずっと、そしてそれ以来`current_sum`が負でない場合、条件は決して満たされません。 スライディング ウィンドウではセグメントが追加されないため、答えはゼロのままです。 

いつすべて`b`値が同一である場合、OR は最初に含めた後は変化しません。 ビット カウンター ロジックは引き続き要素を正しく追跡しますが、OR は安定したままです。 ウィンドウは二乗和がこの固定しきい値を超えるまで拡張され、それ以降は拡張できなくなります。 単調ロールバックにより、無効なセグメントがカウントされなくなります。 

いつ`a`大きな値が含まれていると、二乗和が急速に増大し、ウィンドウ拡張が早期に終了してしまいます。 このアルゴリズムは常に以前に計算された部分和を再利用し、範囲を再計算しないため、各要素は 1 回だけ処理され、数値が大きい場合でも複雑さのオーバーフローが回避されます。
