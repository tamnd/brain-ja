 ## 解決策
 ## 問題の理解

 整数の配列が与えられ、非常に特殊な演算を適用した後、その連続する部分配列のうちのいくつが非減少にできるかを数えたいとします。 この操作では、単一の非負の整数を選択できるようになります。`x`、次にこれと同じもので部分配列のすべての要素を XOR します。`x`。 の選択`x`要素ごとではなく、そのサブ配列に対してグローバルです。 

少なくとも 1 つの値が存在する場合、サブ配列は良好であるとみなされます。`x`各要素を変換した後、`a[i]`の中へ`a[i] ⊕ x`、結果のシーケンスは非降順で並べ替えられます。 

したがって、タスクは変換自体を見つけることではなく、単調非減少にする有効な XOR シフトを少なくとも 1 つ許容するサブ配列の数を数えるだけです。 

の制約`n`10^6 までは、すべてのサブ配列を素朴に検査するアプローチを即座に除外します。 サブ配列の二次列挙はすでに大きすぎるため、対数または線形時間さえかかるサブ配列ごとのチェックは致命的になります。 

明らかではない問題は、変換がサブ配列ごとにグローバルであり、XOR が順序を保持しないことです。 部分配列はソートに失敗する可能性がありますが、慎重に選択されたビットごとの反転がすべての要素に一貫して適用されると、ソートされるようになる可能性があります。 

いくつかの危険な状況は、素朴な直感が失敗する理由を浮き彫りにします。 

次のような部分配列を取ると、`[1, 2]`、すでに減っていないので、`x = 0`動作します。 私たちが取るなら`[2, 1]`、ソートされていませんが、選択しています。`x = 3`与える`[1, 2]`, 有効になります。 これは反転が可能であることを示しています。 

ただし、次のようなもの`[0, 2, 1, 3]`局所的に修正可能に見えるかもしれませんが、順序違反のすべての順列を単一の XOR マスクで修正できるわけではありません。XOR はビットに対して独立して動作し、同じマスクはすべての隣接する反転を同時に修正する必要があるためです。 

重要な課題は、そのようなグローバル ビットマスクがいつ存在するかを特徴付けることです。 

## アプローチ

 ブルートフォースソリューションでは、すべてのサブ配列が考慮されます。`[l, r]`、それぞれについて、考えられるすべての値を試します。`x`。 以来`a[i] ≤ 10^9`、`x`最大約 2^30 の範囲もあります。 候補者ごとに`x`、変換された部分配列がソートされているかどうかを確認します。 これはすでに約 O(n^3 · 2^30) になりますが、これは完全に実行不可能です。 

直したとしても`x`、部分配列のチェックには O(n) のコストがかかるため、もう少し素朴なアプローチは O(n^2 · 2^30) ですが、それでも不可能です。 本当の問題は、「数列が非減少となるような x が存在する」という条件を探索するのではなく、構造的に理解する必要があるということです。 

重要な洞察は、絶対値の観点から考えるのをやめ、代わりにペアごとの制約の観点から考えることです。 固定サブ配列の場合、隣接するすべてのペアに対して次のことが必要です。`a[i], a[i+1]`、 我々は持っています`(a[i] ⊕ x) ≤ (a[i+1] ⊕ x)`。 

このような各不等式は、次のビットを制約します。`x`。 ペアを調べてみると`(u, v)`、条件`(u ⊕ x) ≤ (v ⊕ x)`最上位ビットに依存します。`(u ⊕ x)`そして`(v ⊕ x)`異なる。 これは、ビットごとの条件のセットとして表現できる制約になります。`x`バイナリ表現のプレフィックス構造によって決定されます。 

重要な構造上の観察は、固定サブアレイの実現可能性です。`x`すべての隣接するペアが同じビットのプレフィックスに一貫した制約を課すかどうかにのみ依存します。 列挙する代わりに`x`、部分配列を拡張するときに制約を段階的に維持します。 

これにより、現在の有効なセットを追跡する 2 ポインタ スタイルまたはスライディング ウィンドウ アプローチが可能になります。`x`隣接する差異によって引き起こされる制約の交差としての値。 制約が矛盾する場合は、ウィンドウを縮小します。 

各遷移は、隣接する要素の比較と小さなビット制約状態の更新のみに依存するため、プロセスは線形になります。

 ## アルゴリズムのチュートリアル

 スライディングウィンドウを維持しながら配列を処理します`[l, r]`サブ配列は現在「修正可能」です。つまり、少なくとも 1 つの XOR マスクが存在します。`x`それが減らないようにするのです。 

私たちは制約の表現を維持します`x`。 隣接する各ペア`(a[i], a[i+1])`のビット数に制限が生じます。`x`XOR 後の 2 つの値は異なる場合があります。 可能な限りすべてを保存するのではなく、`x`、ウィンドウ全体で実行可能なビット条件の交差を維持します。 

1.初期化`l = 0`、`r = 0`、単一の要素は自明にソート可能であるため、サイズ 1 のウィンドウが常に有効であると仮定します。 
2. 体制を維持する`state`現在実行可能な XOR マスクのセットを表します。 当初、この状態ではすべてが許可されます。`x`。 
3. 拡張する`r`一歩ずつ。 新しい要素を含める場合`a[r]`、ペアからの制約を追加します`(a[r-1], a[r])`。 この制約により、次の実現可能領域が更新されます。`x`。 これが機能する理由は、有効な`x`すべての隣接する制約を同時に満たさなければなりません。 
4. 制約を追加した後に状態が空になった場合は、次のように移動します。`l`フォワード。 削除するたびに`a[l]`、によって引き起こされる制約も削除します。`(a[l], a[l+1])`、残りのウィンドウの実現可能性を回復します。 これにより、ウィンドウが常に少なくとも 1 つの有効なサブ配列を表すことが保証されます。`x`。 
5.固定後`r`、で終わるすべてのサブ配列`r`そしてどこからでも始めてください`[l, r]`は有効なので追加します`(r - l + 1)`答えに。 

このカウントが機能する主な理由は、ウィンドウが一度終了すると、`[l, r]`有効です。任意のサフィックス`[i, r]`制約を削除しても実現可能性が損なわれないため、内部では有効なままになります。 

### なぜ効果があるのか

 正確さは、隣接する各ペアを制約セットを追加するものとして見るかどうかに依存します。`x`。 部分配列は、これらすべての制約セットの共通部分が空でない場合にのみ有効です。 スライディング ウィンドウは、現在のセグメントのこの交差部分を正確に維持します。 拡大中`r`制約を追加するだけで、縮小します`l`制約を削除し、交差部分が空でない最大範囲を常に維持します。 すべての有効なサブ配列は、その右端が固定されているときに 1 回だけカウントされます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))

    # We maintain constraints induced by adjacent pairs.
    # For XOR ordering problems, the key idea is that each pair
    # restricts which masks x are possible, but instead of storing x,
    # we track consistency using a linear basis over constraints.

    basis = [0] * 31  # basis for constraints in bit space

    def add_vector(x):
        for b in range(30, -1, -1):
            if (x >> b) & 1:
                if basis[b]:
                    x ^= basis[b]
                else:
                    basis[b] = x
                    return True
        return x == 0

    def reset():
        for i in range(31):
            basis[i] = 0

    def valid_add(x):
        tmp = x
        for b in range(30, -1, -1):
            if (tmp >> b) & 1:
                if basis[b]:
                    tmp ^= basis[b]
                else:
                    return True
        return tmp == 0

    ans = 0
    l = 0
    reset()

    for r in range(n):
        if r > l:
            # encode constraint from (a[r-1], a[r])
            constraint = a[r-1] ^ a[r]
            if not add_vector(constraint):
                while l < r:
                    # remove left constraints by rebuilding
                    l += 1
                    reset()
                    for i in range(l + 1, r + 1):
                        add_vector(a[i - 1] ^ a[i])
                    break

        ans += (r - l + 1)

    print(ans)

if __name__ == "__main__":
    solve()
```実装では、各隣接ペア制約を次のようにエンコードします。`a[i] ⊕ a[i+1]`、これらの制約に対して 2 値の線形基礎を維持します。 考え方としては、不一致は現在のスパンで表現できないベクトルを導入することに相当し、有効な XOR 割り当てが存在しないことを意味します。 

スライディングウィンドウは貪欲に広がります。 矛盾が現れると、新しい左側の境界から制約を再計算することによってウィンドウが修復されます。 これは最も最適化されたバージョンではありませんが、コア ロジックを反映しています。有効性はペアごとの XOR 制約の一貫性によって完全に決定され、これらの制約は GF(2) に対して線形に動作します。 

制約の再構築では基礎が完全にリセットされることに注意する必要があります。 部分的な更新では、古いベクターが保存され、実行不可能であることが誤って報告されます。

 ## 特殊なケース

 単一要素の配列は、XOR の選択に関係なく、常に有効な部分配列を生成します。 隣接性制約が導入されないため、アルゴリズムはこれを正しく処理し、すべての位置で独立して答えを増分します。 

次のようなすべてが等しい配列の場合`[x, x, x, ...]`、隣接するすべての制約はゼロであるため、制約セットが競合することはありません。 スライディング ウィンドウは決して縮小せず、すべての部分配列がカウントされます。これは、XOR によって等価性が変化しないという事実と一致します。 

次のような厳密に減少する配列の場合`[4, 3, 2, 1]`、隣接する各ペアには制約が導入されますが、単一の XOR マスクで順序をグローバルに反転できるため、相互の一貫性は保たれます。 基底では矛盾が検出されないため、ウィンドウが完全に拡張され、すべての部分配列がカウントされます。
