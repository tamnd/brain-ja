 ## 解決策
 ## 問題の理解

 一連の入力要求が与えられます。 各リクエストは、整数ラベルで識別される特定のキーが指定された回数だけ繰り返し押されることになっていると述べています。 ハードウェアの問題をすべて無視した場合、キーごとに必要な押下回数の合計が単純に累積されることになります。 

この問題はキーボードの故障によって引き起こされます。 キーが少なくとも k 回連続して押された場合、同じキーをさらに押してもすぐには効果がありません。 つまり、同じキーを k 回連続して押すと、キーボードはそのキーがブロックされた状態になります。 この状態から回復するには、正確に 2 つのオプションがあります。別のキーに切り替える (連続ストリークが途切れる) か、同じキーを意図的に k 回以上押してメカニズムをリセットするかのいずれかです。 

プロセス全体がインタラクティブで順序に依存しますが、私たちが解決するように求められているタスクは、入力プロセス自体をシミュレートすることではありません。 代わりに、すべての制約を最適に解決した後は、各キーについて、最終的に有効な戦略で実際に押された回数を出力するだけで済みます。 したがって、出力は、最適なタイピング プラン全体にわたって集計された、キーごとの押下頻度の概要です。 

入力は n 個のセグメントを記述し、各セグメントは意図したテキスト内のキー ai の 2 回連続した出現に寄与します。 n が 10^5 までの制約は、セグメントを線形または線形に近い時間で処理する必要があることを意味します。 値 ai、bi、k は、bi と k で最大 10^9 まで大きくなる可能性があるため、個々のキーの押下をシミュレートすることはできません。 押すたびにセグメントやモデルを明示的に展開するソリューションは非常に遅くなり、最悪の場合、最大 10^14 の操作が必要になる可能性があります。 

同じキーを持つ連続したセグメントから微妙な問題が発生します。 bi を合計することで素朴にそれらをマージすると、ブロッキング動作を引き起こすことなく常に連続して入力できると暗黙のうちに仮定します。 ただし、累積されたランが k の倍数を超える場合、キーボード メカニズムは強制的にリセットします。 単にキーごとに bi を集計する不注意なソリューションでは、これらのリセットが無視され、解釈に応じて過大カウントまたは過小カウントされます。 正しい推論では、異なるキー間の遷移と強制リセットによって実行がどのように中断されるかを考慮する必要があります。 

2 番目の微妙なケースは、k が 1 に等しい場合です。この場合、リセットし続けない限り、同じキーを 2 回連続で押しても効果はありません。これにより、交互または継続的にリセットしない限り、実質的に連続した繰り返しが不可能になります。 どのアルゴリズムも、この縮退状況を正しく処理する必要があります。 

## アプローチ

 ブルート フォース ビューでは、文字通りセグメントごとにタイピングをシミュレートし、各セグメント内でアクティブなキーの現在の連続長さを追跡しながら各押下をシミュレートします。 ストリークが k に達するたびに、k 回のプレスを切り替えるかリセットを実行します。 このシミュレーションは単純でルールに忠実に従っているので、正しいです。 ただし、各セグメントには O(bi) 操作が必要な場合があり、bi は最大 10^9 になる可能性があるため、これはすぐに実行不可能になります。 合計しても、シミュレートされた操作の合計が爆発的に許容限度を超える可能性があります。 

重要な観察は、重要な状態は現在のキーとそのキーの現在のストリーク長だけであるということです。 同じキーの異なるセグメントを結合することはできますが、他のキーによって中断される可能性があります。 すべてのプレスをシミュレートする代わりに、サイズ k のブロックで推論することができます。 同じキーを k 回連続して押すたびに、概念的には 1 つの「ブロック」が消費され、連続動作がリセットされます。

これにより、問題は、キー間の遷移によって連続性がどのように損なわれるかを正確に考慮しながら、キーごとに、グローバルな型付けプロセスに寄与するサイズ k の完全なブロックの数を維持することに変わります。 重要な単純化は、プロセスは逐次的であるにもかかわらず、最終的な答えは、ストリーク構造の再起動を強制される頻度を考慮した後の、キーごとの有効寄与の合計にのみ依存するということです。 

これをより構造化した方法で見ると、各キーが独立して寄与を蓄積し、k 回連続して押すたびに、同じキーの将来の押下に対するブロック制約が効果的に無効化されます。 これは、キーごとの最終的なカウントは、その総需要をサイズ k のグループにパックできる回数と、中断に耐えて残った部分的な貢献を加えた回数によって決定されることを意味します。 

したがって、問題を部分的な蓄積のグローバル構造の維持と完了したブロックの定期的なフラッシュに集約します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ブルートフォースシミュレーション | O(トータルバイ) | お(1) | 遅すぎる |
 | ブロックベースの蓄積 | O(n) | O(個別のキーの数) | 承認済み |

 ## アルゴリズムのチュートリアル

 私たちは、各キーが現在システムに「入力」されている回数の継続的な累積を維持します。また、強制された場合にのみ寄与を k の倍数で終了することによって、k ストリーク ルールを暗黙的に尊重するグローバル構造を維持します。 

1. すべてのセグメントを読み取り、順番に処理します。各 (ai、bi) は、進行中の入力ストリームにキー ai の bi の出現を追加する要求として処理されます。 
2. マップ cnt を維持します。ここで、cnt[x] には、これまでにキー x に割り当てられた有効な完了した押下回数の合計が格納されます。 また、現在アクティブなキーとそれが連続して何回拡張されたかを記述する実行カウンター cur_key と cur_streak も維持します。 
3. セグメント (a、b) を処理するときは、まず a が cur_key と等しいかどうかを確認します。 そうであれば、同じストリークを継続していることになるので、単純に cur_streak を b だけ拡張します。 cur_streak が k に達するか超える場合、そこからサイズ k の完全なブロックを繰り返し抽出し、完全なブロックごとに k を cnt[a] に追加し、残りを新しい cur_streak として保持します。 
4. a が cur_key と異なる場合、ストリークは途切れます。 cur_key を a に、cur_streak を b にリセットします。 この分割は、異なるキー間で誤ってマージすることがないことを保証するため、非常に重要です。 
5. 各更新後に、cur_streak からできるだけ多くの完全な k ブロックを再度抽出し、それらの寄与を cnt[cur_key] に追加します。 これは、サイズ k のフル ストリークのみが状態遷移を引き起こすことができるというキーボード ルールをモデル化します。 
6. すべてのセグメントが処理された後、cur_streak には完全な k ブロックを形成しなかった残りがまだ含まれている可能性があります。 残りの部分はブロックをトリガーせず、直接 cnt[cur_key] に追加されます。 
7. 最後に、すべてのキーを対応する cnt 値とともに昇順で出力します。 

キーの不変条件は、どの時点でも、cur_streak が完全な k ブロックの寄与にまだ解決されていない現在のキーの実行のサフィックスを表すことです。 完成したkサイズのブロックはすべてすでにcntに移動されているので、二重にカウントしたり、寄与分を失ったりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, k = map(int, input().split())
    
    cnt = {}
    
    cur_key = None
    cur_streak = 0
    
    def flush_blocks(key, streak):
        full = streak // k
        rem = streak % k
        cnt[key] = cnt.get(key, 0) + full * k
        return rem
    
    for _ in range(n):
        a, b = map(int, input().split())
        
        if cur_key == a:
            cur_streak += b
        else:
            if cur_key is not None:
                cur_streak = flush_blocks(cur_key, cur_streak)
            cur_key = a
            cur_streak = b
        
        cur_streak = flush_blocks(cur_key, cur_streak)
    
    if cur_key is not None:
        cur_streak = flush_blocks(cur_key, cur_streak)
        cnt[cur_key] = cnt.get(cur_key, 0) + cur_streak
    
    items = sorted(cnt.items())
    print(len(items))
    for c, d in items:
        print(c, d)

if __name__ == "__main__":
    solve()
```この実装は、単一のアクティブな実行を維持するという考えに従っています。 ヘルパー関数`flush_blocks`現在のストリークからすべての完全な k 長チャンクを抽出し、それらをグローバル カウンターにプッシュし、残りだけを未解決のままにします。 これにより、個々のキーの押下をシミュレートすることがなくなります。 

重要な点は、キーの切り替え時と各セグメント拡張後の両方でフラッシュが発生する必要があることです。そうしないと、その寄与をすべて抽出できずに k を超えるストリークが蓄積される危険性があります。 最後のフラッシュにより、残った部分実行が失われないことが保証されます。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n) | 各セグメントは 1 回処理され、各フラッシュはキー更新ごとの定数時間演算です。 
| スペース | O(m) | m はマップに格納されている個別のキーの数です |

 このアルゴリズムは、線形時間で最大 10^5 のセグメントを処理し、キーごとに集計されたカウントのみを保存するため、メモリ制限内に簡単に収まります。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    from collections import defaultdict
    
    n, k = map(int, input().split())
    cnt = defaultdict(int)
    
    cur_key = None
    cur_streak = 0
    
    def flush(key, streak):
        full = streak // k
        rem = streak % k
        cnt[key] += full * k
        return rem
    
    for _ in range(n):
        a, b = map(int, input().split())
        if cur_key == a:
            cur_streak += b
        else:
            if cur_key is not None:
                cur_streak = flush(cur_key, cur_streak)
            cur_key = a
            cur_streak = b
        cur_streak = flush(cur_key, cur_streak)
    
    if cur_key is not None:
        cur_streak = flush(cur_key, cur_streak)
        cnt[cur_key] += cur_streak
    
    items = sorted(cnt.items())
    out = [str(len(items))]
    for c, d in items:
        out.append(f"{c} {d}")
    return "\n".join(out)

 ## 特殊なケース

 重要なエッジ ケースは、単一のセグメントが k よりもはるかに大きい場合です。 その状況では、アルゴリズムは 1 回の更新内で完全なブロックを繰り返し抽出します。 たとえば、k = 4 で入力 (1, 10) の場合、ストリークは 10 になり、すぐに 8 が cnt[1] にフラッシュされ、残りとして 2 が残ります。 コードはこれを 1 つの算術演算で処理するため、プレスごとのシミュレーションを回避します。 

もう 1 つの重要なケースは、セグメントが小さいキーを頻繁に切り替えることです。 たとえば、k = 3 で入力 (1,1)、(2,1)、(1,1)、(2,1) とします。 ここで、セグメントが単独で k に到達することはありませんが、正確かどうかは、異なるキー間で決してマージしないことに依存します。 このアルゴリズムは各スイッチで cur_streak をリセットするため、無効なグループ化は発生せず、すべての寄与は最終的な集計までわずかな残差のままになります。 

最後の微妙なケースは、最後のキーにゼロ以外の剰余がある場合です。 将来のセグメントはフラッシュをトリガーできないため、最後の追加ステップにより、この残りが 1 回だけ保存され、後続のコントリビューションがサイレントに失われることが回避されます。
