 ## 解決策
 ## 問題の理解

 私たちはツリー構造の王国を与えられています。これは、n − 1 本の道路で接続された n 個の都市があり、任意の 2 つの都市の間には 1 つの単純な経路が存在することを意味します。 これらの都市の一部は重要としてマークされており、一部の都市には軍隊が駐留しています。 

各部隊は、近接性に基づいて重要な都市を「カバー」します。重要な都市については、すべての部隊までの距離を計算し、その距離が最小距離の部隊に割り当てられます。 複数の軍隊が同じ最小距離で結ばれた場合、重要な都市はすべての軍隊によって保護されていると見なされます。 

これにより、双方向のカウント問題が発生します。 各部隊について、最終的に最も近い重要な都市の数を知りたいと考えています。 重要な都市ごとに、その都市に最も近い都市に何人の軍隊がいるのかを知りたいと考えています。 

重要な構造は、すべての距離がツリー上の最短パス距離であるため、一意のパスを持つ標準のグラフ距離と同様に動作するということです。 

制約は最大 200,000 ノードに達し、すべての軍隊からすべての重要な都市までの距離を個別に計算するソリューションは即座に除外されます。 単純なアプローチでは、各部隊から BFS または DFS を実行するようなことを試みますが、これには最悪の場合 O(mn) のコストがかかり、m と n の両方が大きい場合は明らかに制限を超えます。 各距離クエリは O(n) であるため、ペアごとに距離を計算しても遅すぎます。 

2 番目の単純なアイデアは、すべての部隊からマルチソース BFS を実行し、すべてのノードに最も近い部隊を記録することです。 この部分は実際には実現可能ですが、重要なノードのみを考慮し、タイカウントも必要になるため、慎重に扱わないと単純な単一ラベルの伝播が機能しなくなることが複雑です。 

いくつかの微妙なケースは、素朴な推論が失敗する場所を明らかにします。 ライン ツリー 1-2-3-4-5 を考えてください。軍隊が 1 と 5、重要な都市が 3 です。距離は対称であるため、両方の軍隊が最も近く、カウントする必要があります。 最初に発見された情報源を選択する貪欲な割り当てでは、誤って 1 つの部隊のみに割り当てられてしまいます。 別の問題は、部隊が重要な都市に直接配置されている場合に発生します。距離ゼロがすべてを支配するため、たとえ他の都市が同等に近い場合でも、その都市はその部隊にのみ割り当てられなければなりません。 

したがって、重要な問題は、タイを認識して複数のソース間の正しい最短距離を維持しながら、重要なノードのみで結果を効率的に集約できるようにすることです。 

## アプローチ

 ブルートフォース手法では、ツリー上の BFS または DFS を使用して、すべての重要な都市について、すべての部隊までの距離を計算します。 ツリー上の各距離の計算は O(n) であり、k 個の重要な都市と m 個の軍隊について計算するため、これは距離の評価だけで O(km) になり、最悪の場合は O(n²) に縮退します。 前処理を使用して各距離クエリを O(1) に最適化しても、重要なノードごとにすべての軍隊を比較する必要があるため、役に立ちません。 

問題の構造は視点を逆転させることを示唆しています。 「各重要都市について、どの軍隊が最も近いか」を尋ねる代わりに、軍隊からの情報を同時に伝播することができます。 ツリー上のマルチソース BFS により、すべての部隊からの最短距離を一度に計算できます。 ただし、どの部隊が最小距離に達するかを保存する必要もあります。 

重要な観察は、等距離の層で局所的に関係を解決できることです。 各状態が距離だけでなく軍隊の発信元の ID も伝える BFS を実行すると、複数の発信元から同じ距離にあるノードを緩和しようとするたびに、衝突を検出してカウントすることができます。 

すべての都市が最も近い軍隊のセットを把握したら、残りは純粋な集計です。重要な都市ごとに最も近い軍隊をすべて増分し、重要な都市ごとにそのタイ数を増分します。 

すべてのエッジの重みが等しいため、ツリー構造では BFS が十分であることが保証されます。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルート フォース (重要な都市ごとの BFS/DFS から全部隊へ) | O(n²) | O(n) | 遅すぎる |
 | タイ追跡を備えたマルチソース BFS | O(n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 最初はすべての部隊を BFS ソースとして扱いますが、それらを単一のスーパー ソースに統合するのではなく、個別に区別する必要があります。 

1. ツリーの隣接リストを作成します。 これにより、BFS 拡張のために近隣ノードの O(1) トラバーサルが可能になります。 
2. 距離配列を初期化する`dist[node]`無限とコンテナを使って`best[node]`これには、最も近い軍隊のセット、またはタイ数の圧縮表現が保存されます。 
3. すべての部隊を距離 0 の初期状態として BFS キューにプッシュし、各エントリに部隊 ID をタグ付けします。 各部隊ノードに対して、それ自体のみを含むように最適なソース セットを設定します。 
4. 標準的な方法で BFS を実行します。 状態を拡張するとき`(node, troop)`距離が d の場合、すべての近隣を訪問しようとします。 
5. 近隣がまだ訪問されていない場合、距離 d + 1 を割り当て、現在の部隊をその固有の最も近い候補として継承します。 
6. 近隣ノードが距離 d + 1 ですでに到達している場合、同点状況が検出されます。これは、別の部隊が同じ最短距離で同じノードに到達することを意味します。 この場合、既存の割り当ては上書きされませんが、このノードが複数の部隊によって競合されていることを記録します。 
7. BFS が終了すると、すべてのノードは、単一の最も近い部隊、または関連付けられた最も近い部隊のセットのいずれかを認識します。 
8. 次に、重要な都市を処理します。 重要な都市ごとに、最も近いセット内のすべての部隊の回答を増加させます。 また、その都市のカウンターを、その最も近いセットのサイズと同じように増分します。 

重要な点は、BFS が正しい距離の順序でノードを処理することで、より長いパスが誤って最適なものとして割り当てられることがないようにすることです。 キューは、レイヤの距離の増加を保証します。 

### なぜ効果があるのか

 BFS の不変条件は、ノードが最初に発見されるとき、少なくとも 1 つの部隊から可能な最小距離で発見されるということです。 BFS では距離が減少しない拡張が保証されているため、同じ距離でのその後の検出は、より短いパスではなく結合に対応します。 すべてのエッジの重みが等しいため、最初にノードに到達するとその最短距離が固定され、等距離での到着は代替の最適なソースに正確に対応します。 これにより、割り当てと同点カウントの両方の正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
from collections import deque, defaultdict

def solve():
    n, m, k = map(int, input().split())
    p = list(map(int, input().split()))

    adj = [[] for _ in range(n + 1)]
    for i, parent in enumerate(p, start=2):
        adj[i].append(parent)
        adj[parent].append(i)

    troops = list(map(int, input().split()))
    important = list(map(int, input().split()))

    INF = 10**18
    dist = [INF] * (n + 1)

    owner = [[] for _ in range(n + 1)]

    q = deque()

    for t in troops:
        dist[t] = 0
        owner[t] = [t]
        q.append(t)

    while q:
        v = q.popleft()
        for to in adj[v]:
            nd = dist[v] + 1
            if dist[to] == INF:
                dist[to] = nd
                owner[to] = owner[v][:]
                q.append(to)
            elif dist[to] == nd:
                # tie: merge sets (small optimization is not needed conceptually)
                for x in owner[v]:
                    if x not in owner[to]:
                        owner[to].append(x)

    troop_ans = [0] * (n + 1)
    city_ans = [0] * (n + 1)

    for c in important:
        city_ans[c] = len(owner[c])
        for t in owner[c]:
            troop_ans[t] += 1

    print(*[troop_ans[t] for t in troops])
    print(*[city_ans[c] for c in important])

if __name__ == "__main__":
    solve()
```BFS は、すべての部隊によって初期化される単一のキューを使用して実装されます。 各ノードには、最も近い部隊所有者のリストが含まれています。 ノードに最初に到達すると、ノードはその親から所有者リストを継承します。 等しい距離で同点が発生した場合、所有権リストをマージします。 

重要な実装の詳細は、時期尚早の上書きを避けることです。`owner[to]`。 最初の訪問時に一度だけ割り当て、等距離の再訪問時にのみそれを延長します。 これにより、厳密に長いパスが結果に影響を与えることがなくなります。

 ## 特殊なケース

 重要なエッジケースの 1 つは、軍隊が重要な都市に直接配置される場合です。 その場合、その距離はゼロとなり、別の部隊も同じノード上にいない限り、他の部隊はそれに勝つことができません。これは入力制約によって禁止されています。 BFS はそのノードを距離 0 で初期化するため、他の場所で等距離にタイが発生しない限り、そのノードが常に一意の最も近いソースになります。 アルゴリズムは、そのノードの所有者セットをまさにその部隊として正確に保持します。 

もう 1 つのエッジ ケースは、重要な都市が 2 つの軍隊のちょうど中間に位置する、完全にバランスのとれたツリーです。 BFS は両側から同じ距離で到達するため、両方の部隊が所有者リストに表示されます。 これは等距離マージ ステップによって処理され、両方の寄与が確実にカウントされます。 

3 番目のエッジ ケースは、重要な都市に 1 つを除くすべての軍隊から遠く離れたリーフ ノードが含まれている場合です。 BFS は、最も近いパスのみが最初に到達することを保証します。すべての代替パスは厳密に長いため、結合は発生しません。
