 ## 解決策
 ## 問題の理解

 1 から n までのラベルが付けられた人々の円形配置に対するヨセフス スタイルの消去法をシミュレートしています。 クラシック バージョンとの違いは、ステップ サイズが固定されていないことです。 代わりに、q 個のラウンドがあり、各ラウンドは独自のステップ値 k を提供します。 

ラウンドの開始時に、現在の人物の前に立ち、円に沿って前方に数え始め、n を通過したときに回り込みます。 1、2、3…と数えてkに達すると、その位置にいる人が円から外されます。 次のラウンドは、削除された人の次の人から時計回りにすぐに始まります。 タスクは、各ラウンドで削除された人の ID を出力することです。 

重要な問題は、n と q が最大 5 × 10^5 と大きいことです。 円の周りを物理的に段階的に進めるシミュレーションは、各エリミネーションごとに多くの位置を歩く必要があるため、遅くなりすぎます。 最悪の場合、すべてのラウンドにわたる合計ステップ数はおよそ n × q に達する可能性があり、これは許容範囲をはるかに超えています。 

この構造により、単純な配列シミュレーションはパフォーマンスの面でも脆弱になります。 ブール値のアライブ配列を維持し、毎回 k ステップを順方向にスキャンする場合、デッド要素のスキップには依然として密な状態の n に比例した時間がかかるため、償却除去でも十分ではありません。 

k が残りの要素に比べて大きい場合、微妙なエッジ ケースが発生します。 たとえば、円のサイズが 3 で k が 10 の場合、消去は 10 mod 3 によって決定されますが、文字通り 10 ステップをカウントする単純なシミュレーションでは、ラッピングを適切に処理しない限り、線形進行が必要であると誤って想定される可能性があります。 

もう 1 つの落とし穴は、削除するたびに開始位置が次の生きている要素に移動することを忘れていることです。 毎回誤って固定インデックスまたは元の 1 から再起動すると、異なるプロセスをシミュレートし、それぞれの単一消去が正しく計算されたとしても、不正確な出力が生成されます。 

## アプローチ

 ブルートフォース手法では、残りの人々の明示的なリストを維持し、k 歩進むことで各排除をシミュレートします。 それぞれの削除では、リストを反復処理したり、削除された位置をスキップしたり、要素を物理的に削除したりする必要があります。 ベクトルと消去操作を使用すると、削除ごとに O(n) が発生し、これを q 回実行すると O(nq) になります。これは 5 × 10^5 ではまったく実行不可能です。 

重要な観察は、その構造が動的な順序統計の問題であるということです。 いつでも、循環順序で k 番目の生きている要素を見つけて削除する必要があります。 削除後は次の要素から続行します。 これはまさに、削除における「k 番目のアクティブな要素」のクエリです。 

これにより、プレフィックス数と順序統計を効率的にサポートするデータ構造を使用するようになります。 インデックス 1 ～ n にわたるフェンウィック ツリーまたはセグメント ツリーは、どの位置がまだ生きているかを維持できます。 各ポジションは、生きている場合は 1 を与え、除去された場合は 0 を与えます。 次に、プレフィックスの合計を計算し、ツリー上のバイナリ リフティングによって k 番目の生きている要素を見つけることができます。 

循環カウントは剰余のみに依存するため、クエリごとに k モジュロの現在のサイズが減少します。 次に、(current_index_rank + k) mod size 番目の生きている要素の位置を見つけます。 これにより、各消去が O(log n) 操作に変換されます。 

ブルート フォースは円を明示的にシミュレートするため機能しますが、n が大きい場合は失敗します。 動的セット内のランク情報のみが必要であるという観察により、プレフィックス合計クエリとポイントの削除に対する円上の移動を減らすことができます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(nq) | O(n) | 遅すぎる |
 | フェンウィック ツリー / BIT | O(q log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

インデックス 1 から n までのフェンウィック ツリーを維持します。各インデックスの初期値は、人が生きていることを示す値 1 です。 インデックスに関しても現在の開始位置を維持しますが、常にそれを生きている要素間のランクに変換します。 

1. すべての位置を 1 に設定してフェンウィック ツリーを初期化し、生きているすべての人々を表します。 生きている人の総数は n です。 
2. 各ラウンド i について、k を読み取り、現在の生存数を使ったモジュロを使用してそれを減らします。 モジュロ後に k が 0 になった場合、それを現在の生存数に設定します。 この調整により、冗長な全回転を行わずに常に円形構造内を移動できるようになります。 
3. フェンウィック ツリーのプレフィックス合計クエリを使用して、現在の開始位置よりも前に生存している人の数を厳密に計算します。 これにより、生きている順序付けにおける現在のランク オフセットが得られます。 
4. ターゲット ランクは、(current_rank + k) 法 current_alive_size です。 このランクは、生きている要素に対する 1 から始まるインデックス付けで定義されます。 結果が 0 の場合は、最後に生きている要素をターゲットにしていることを意味します。 
5. フェンウィック ツリーの「k 番目の検索」操作を使用して、このターゲット ランクに対応する [1, n] 内の実際のインデックスを見つけます。 このステップは、循環移動からプレフィックスカウントへの核となる変換です。 
6. このインデックスを削除された人物として出力し、フェンウィック ツリーを更新して、そのインデックスで 1 を減算してこの位置を死亡としてマークします。 
7. 開始位置を、削除されたインデックスの次に有効な要素になるように更新します。 これは、削除された要素のランクに設定し、次の反復でその位置から継続することによって行われます。 

トランジションの正しさは、ラベルの増加によって順序付けされた生きているインデックスの動的配列として円を常に解釈することに依存しており、フェンウィック ツリーはその順序を暗黙的にエンコードします。 

### なぜ効果があるのか

 生きている人々はいつでも、元の配列をフィルタリングすることによって得られる順序付けられたシーケンスを形成します。 フェンウィック ツリーはこのシーケンスにわたるプレフィックス数を維持するため、プレフィックスの合計をクエリすると、このフィルター処理された順序内の任意の位置のランクが得られます。 円内のすべての動きは、この暗黙のシーケンスで前進することに正確に対応します。 削除では、生存者の相対的な順序を変更せずに要素のみが削除されるため、更新のたびにランク構造の一貫性が保たれ、各 k ステップのジャンプが k 次の統計クエリに正しく変換されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def build(self):
        for i in range(1, self.n + 1):
            self.add(i, 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

    def find_kth(self, k):
        idx = 0
        bit_mask = 1 << (self.n.bit_length())
        while bit_mask:
            nxt = idx + bit_mask
            if nxt <= self.n and self.bit[nxt] < k:
                k -= self.bit[nxt]
                idx = nxt
            bit_mask >>= 1
        return idx + 1

n, q = map(int, input().split())
fw = Fenwick(n)
fw.build()

cur = 1
alive = n

for _ in range(q):
    k = int(input())
    if alive == 0:
        break

    k %= alive
    if k == 0:
        k = alive

    cur_rank = fw.sum(cur - 1)
    total_before = cur_rank

    target_rank = total_before + k
    if target_rank > alive:
        target_rank -= alive

    pos = fw.find_kth(target_rank)
    print(pos)

    fw.add(pos, -1)
    alive -= 1

    if alive == 0:
        break

    # move to next alive position
    cur_rank_after = fw.sum(pos)
    if cur_rank_after == alive + 1:
        cur = fw.find_kth(1)
    else:
        cur = fw.find_kth(cur_rank_after + 1)
```フェンウィック ツリーは生きているセットをカプセル化しており、`sum`関数は、位置を残りの要素内のランクに変換します。 の`find_kth`関数は、フェンウィック構造に対する標準的なバイナリ リフティングであり、ランクから実際のインデックスを回復できます。 

変数`cur`次のラウンドが始まる場所を追跡します。 取り外し後`pos`、後続ランクを見つけることによって、次に生きている要素を見つけます。 最後の生きている要素を削除した場合は、最初の生きている要素に戻ります。 

k のモジュロ削減は、円の周りの不必要な走査を避けるために不可欠です。 これがないと、大きな k 値が同じアライブ セットを繰り返し循環することになります。 

## 実用的な例

 ### 例 1

 n = 5、q = 2、k 値 2 および 3 の小さなケースを考えてみましょう。 

初期状態：alive = [1, 2, 3, 4, 5]、cur = 1。 

| ラウンド | カー | k | 目標ランク | 削除されました |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 2 | 2 | 2 |
 | 2 | 3 | 3 | 1 | 5 |

 2 を削除すると、生存シーケンスは [1, 3, 4, 5] になります。 3 から開始し、3 歩移動すると 5 に着地します。 

これにより、アルゴリズムが削除後に円のインデックスを正しく再作成していることが確認されます。 

### 例 2

 n = 6、q = 3、k = [4, 2, 5] とします。 

| ラウンド | カー | k | アライブセット | 削除されました |
 | --- | --- | --- | --- | --- |
 | 1 | 1 | 4 | [1,2,3,4,5,6] | 4 |
 | 2 | 5 | 2 | [1,2,3,5,6] | 6 |
 | 3 | 1 | 5 | [1,2,3,5] | 3 |

 削除するたびに構造が圧縮され、ランクがシフトしますが、プレフィックスの合計は正しい順序を維持します。 

これらのトレースは、アルゴリズムが物理的な隣接性にまったく依存せず、ランクの一貫性にのみ依存していることを示しています。 

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |

 | 時間 | O(q log n) | 各ラウンドでは、フェンウィック ツリーに対して k 番目のクエリが 1 つと更新が 1 つ実行されます。

 ## 特殊なケース

 エッジ ケースの 1 つは、k が残りの要素の数より大きい場合です。 たとえば、n = 4 および k = 10 の場合、正しい動作は 10 mod 4 = 2 にのみ依存します。アルゴリズムは、フェンウィック ツリーをクエリする前にモジュロ リダクションを通じてこれを処理します。 これにより、不必要なラップアラウンド トラバーサルが回避され、常に現在の有効なサイズ内で動作することが保証されます。 

もう 1 つのケースは、削除によって現在の順序の最後の要素が削除される場合です。 アライブ セットが [3, 5, 7] で、7 を削除するとします。次の開始点は 3 に戻る必要があります。実装では、これは、後続ランクがアライブ カウントを超えたときを検出し、次を使用して最初の要素に明示的にリセットすることによって処理されます。`find_kth(1)`。 

3 番目のケースは、k = 1 の場合の削除の繰り返しです。このシナリオでは、アルゴリズムは現在の開始位置を繰り返し削除します。 フェンウィック ツリーは、削除のたびに後続のすべてのランクを 1 つずつ下にシフトし、ランク クエリを超えた特別なケースを使用せずに後続の計算の正確さを維持するため、ランクを引き続き正しく更新します。
