 ## 問題の理解

 私たちにはプロセスの集合が与えられています。 各プロセスは特定の時間に利用可能になり、処理の長さは固定されています。 いつでもクエリ時に$t$、すでに到着しているプロセスのみを考慮します。つまり、到着時間は最大でも$t$。 これらの利用可能なプロセスのうち、待機時間と必要なサービス時間に基づいて、各プロセスのスコアを評価します。 スコアは待ち時間に応じて直線的に増加し、プロセスの長さによって正規化されます。 

到着時間のある処理の場合$x_i$そしてサービスタイム$s_i$、その時点のスコア$t$は$$1 + \frac{t - x_i}{s_i}.$$各クエリでは、時間までに到着したすべてのプロセスの中で最大のスコアが求められます。$t$。 プロセスがまだ到着していない場合、答えは次のようになります。$-1$。 

制約は厳しいです: まで$10^6$プロセスと$10^6$クエリ。すべての時間とサイズは次のように制限されます。$10^6$。 これにより、クエリごとにすべてのプロセスを検査するアプローチは除外されます。$10^{12}$最悪の場合の運用。 

主な微妙な点は、スコアリング関数がクエリ時間に依存することです。$t$。 これは、プロセスの値が事前に固定されておらず、時間の経過とともに直線的に変化することを意味します。 どのソリューションでも、クエリごとにすべての値を最初から再計算することを避ける必要があります。 

よくある落とし穴は、各クエリを個別に処理し、アクティブなプロセスをすべてスキャンすることです。 複数のプロセスが同時に到着すると、別の微妙な問題が発生します。 質問に正確に答える前に、それらすべてを考慮する必要があります。 

## アプローチ

 直接的なアプローチは簡単です。クエリ時間ごとに$t$、到着時間が最長ですべてのプロセスを反復します。$t$、スコアを計算し、最大値を取得します。 これは定義に正確に従っているため、正しいです。 ただし、各クエリには最大で次のものが含まれる場合があります。$n$プロセスにつながる$O(nm)$これは実現可能な限界をはるかに超えています。 

重要な観察は、各プロセスが次の機能に貢献しているということです。$t$:$$f_i(t) = 1 + \frac{t}{s_i} - \frac{x_i}{s_i}.$$固定プロセスの場合、これは次の線形関数です。$t$傾斜あり$\frac{1}{s_i}$そしてインターセプト$1 - \frac{x_i}{s_i}$。 問題は、行の動的なセットを維持することに帰着します。行は時間の経過とともに (プロセスが到着したとき) 追加され、さまざまな時点で最大値をクエリします。$t$。 

到着時間が事前にわかっているため、プロセスとクエリの両方を時間で並べ替え、昇順にオフラインで処理できます。 時間が進むにつれて、より多くのラインがアクティブになります。 各クエリで、現在の時点で評価されたすべてのアクティブな行の最大値が必要です。$t$。 

これは、挿入とクエリのみを昇順で実行する古典的な動的凸包トリック シナリオです。$t$。 傾きが正であり、挿入は時間の経過とともに単調であるため、線の凸包を維持し、ポインターまたは二分探索を使用して効率的にクエリを実行できます。 

より単純ですが同様に効果的な観点は、各線が傾きによってソートされたプロセスに対応する凸包を維持し、潜在的に最適なものだけを維持することです。 昇順でクエリを実行するため、$t$、船体に沿ってポインタを移動できます。

 ## アルゴリズムのチュートリアル

 私たちは問題をラインの維持に変換します。 各プロセスは次の行になります。$$y = \frac{t}{s_i} + \left(1 - \frac{x_i}{s_i}\right).$$イベントを時間の増加順に処理します。 

1. すべてのプロセスとクエリを読み取り、インデックスとともに保存します。 各処理が「挿入イベント」であり、各クエリが「クエリイベント」です。 これにより、時間を順番にシミュレーションすることができます。 
2. すべてのイベントを時間順に並べ替えます。 プロセスとクエリが同じ時間を共有する場合は、挿入プロセスが最初に行われます。 これにより、プロセスが時間どおりに到着することが保証されます$t$で問い合わせが可能です$t$、定義と一致します$x_i \le t$。 
3. プロセスごとに、傾きで定義される直線に変換します。$m = 1/s_i$そしてインターセプト$b = 1 - x_i/s_i$。 これらを凸構造に挿入するために保管します。 
4. 傾きによってソートされたラインの凸包を維持します。 新しい行を挿入するときは、以前に保存された無関係な行を削除します。 隣接する線との交点が将来にとって決して最適ではない場合、その線は冗長です。$t$。 
5. クエリ時間までのすべての挿入を処理した後、次の時点で最大行を評価します。$t$。 クエリは昇順に処理されるため、前方にのみ移動するポインタをハル上に維持できます。 
6. クエリ時に行が存在しない場合、出力$-1$。 それ以外の場合は最大値を出力します。 

重要な単純化は、傾きがすべて正であり、挿入が時間順に単調であることです。これにより、ハル ポインタの異常な振動が防止されます。 

### なぜ効果があるのか

 常に、アクティブなプロセスのセットは線形関数のセットに正確に対応します。 アルゴリズムは、これらのラインの上部エンベロープのみを維持します。 船体のメンテナンス中に除去されたラインは、その支配領域が隣接するラインによって完全にカバーされているため、将来のクエリ時間では最大値にならないことが証明されています。 クエリは昇順に評価されるため、$t$、ハルの以前の部分を再検討する必要はなく、ポインタの移動は常に現在の最大エンベロープ セグメント上に留まるため、正確さが維持されます。

def intersect_x(a, b):
    # returns x-coordinate where line a becomes equal to line b
    # a: (m, c), b: (m, c)

    m2, c2 = b
    return (c2 - c1) / (m1 - m2)

    t = int(input())
    events.append((t, 1, i))  # 1 = query

events.sort()

# convex hull: lines and pointer
lines = []

def bad(l1, l2, l3):
    return (l3[1] - l1[1]) * (l1[0] - l2[0]) >= (l2[1] - l1[1]) * (l1[0] - l3[0])

ptr = 0
ans = [-1] * m

for event in events:

        _, _, m1, c1 = event
        lines.append((m1, c1))
        while len(lines) >= 3 and bad(lines[-3], lines[-2], lines[-1]):
            lines.pop(-2)
        if ptr > len(lines):
            ptr = len(lines) - 1

        t = event[0]

            continue

            m1, c1 = lines[ptr]
            m2, c2 = lines[ptr + 1]
            if m1 * t + c1 <= m2 * t + c2:
                ptr += 1
            else:
                break

        m1, c1 = lines[ptr]
        ans[idx] = m1 * t + c1

for x in ans:

 ## 特殊なケース

 エッジ ケースの 1 つは、クエリ時にプロセスが到着していない場合に発生します。 たとえば、次のプロセス$x=5$そして、次のクエリ$t=3$。 イベントの順序付けにより、クエリは空のハルを認識し、アルゴリズムは次の結果を返します。$-1$行の評価が行われる直前に。 

もう 1 つの微妙なケースは、複数のプロセスが同時に到着する場合です。 並べ替えでは、クエリの前に同じタイムスタンプで挿入が行われるため、そのようなプロセスはすべて評価前に含まれます。 この順序付けをしないと、クエリは一度に$t$プロセスを誤って無視する可能性がありました$x_i = t$、定義に違反します。 

3 番目のケースは、大きな斜面により斜面が非常に近い場合です。$s_i$。 船体は評価には浮動演算を使用しますが、構造の維持には整数相互乗算を使用するため、精度の問題は評価にのみ影響し、構造の正確さには影響しません。 各クエリは少数の候補行のみを評価するため、最大誤差は必要な許容範囲内に留まります。
