 ## 問題の理解

 スクロールには一連の 10 進数が含まれています。 スクロールの断片は、左右の位置を指定することによって選択されます。 そのフラグメントについては、2 つの異なる位置の順序付きペアをすべて調べます。 最初の位置の数字は十の位を形成し、二番目の位置の数字は一の位を形成し、2 桁の数字が作成されます。 フラグメントに必要な値は、これらすべての数値の合計です。 

タスクは、多くの独立したフラグメント クエリに迅速に答えることです。 あらゆるクエリに対して`[l, r]`、位置から部分文字列のポテンシャルを出力する必要があります`l`位置を決める`r`。 

シーケンスの長さとクエリの数は両方とも最大です。`100000`。 これにより、すべてのクエリ内のすべての位置のペアの処理が即座に除外されます。 長さの断片`k`含まれています`k * (k - 1)`順序ペアであるため、直接シミュレーションを行うとクエリごとに 2 次の時間がかかります。 と`100000`クエリでは、中程度のサイズのフラグメントであっても、数十億の操作が発生する可能性があります。 

主な課題は、ペアの列挙自体ではなく、すべてのポジションがまったく同じように貢献していることを認識することです。 1 桁の寄与が理解されると、各クエリを単純な範囲の合計にまとめることができます。 

いくつかの特殊なケースでは、ペアの定義に文字通りに従う実装が壊れる可能性があります。 1 桁のフラグメントには有効なペアが含まれていません。 例えば：```
Input:
1
5
1
1
1

Output:
0
```不注意な解決法を行うと、その数字が数字を構成するものとして数えられる可能性があります`55`, ただし、2 つの位置は異なる必要があるため、加算する数値はありません。 

もう 1 つのよくある間違いは、ペアが順序付けされていることを忘れることです。 例えば：```
Input:
2
78
1
1
2

Output:
165
```有効な数値は次のとおりです。`78`そして`87`、だけでなく`78`。 逆の順序を無視すると、小さすぎる答えが得られます。 

最後のエッジ ケースは、数字が繰り返される部分文字列です。```
Input:
3
111
1
1
3

Output:
44
```6 つの順序ペアがあり、すべてのペアが数値を作成します。`11`、合計は`66`? いいえ、これは一般的なカウントの間違いを明らかにします。ペアのカウントは正しいですが、式では各位置の寄与を個別に考慮する必要があります。 正しい計算は、`11 * (3 - 1) * (1 + 1 + 1) = 66`。 正しい出力は次のとおりです。```
66
```重要なのは桁値ではなく位置であるため、個別の桁ペアのみをカウントする実装はここで失敗します。 

## アプローチ

 単純な解決策では、各クエリを個別に処理します。 ある長さのセグメントの場合`k`、順序付けされたすべての位置のペアを列挙し、2 桁の数値を計算して、それを答えに追加できます。 これは定義に直接従うため、正しいです。 ただしペア数は`k(k - 1)`。 最悪の場合、文字列全体をカバーするクエリは次のようになります。`100000`桁数はほぼ必要になります`10^10`ペア操作は利用可能な時間をはるかに超えています。 

重要な観察は、個々のペアを知る必要がないということです。 次のセグメントを考えてみましょう`k`数字を入力し、そのすべての数字の合計を次のようにします。`S`。 

任意のポジションを選択してください。 その桁が 10 の位になると、1 つおきの位置で使用されるため、次のように表示されます。`k - 1`数字。 その役割における貢献は次のとおりです。`10 * digit * (k - 1)`同じ数字が 1 つおきの位置で 1 の数字になることもあり、次のような影響があります。`digit * (k - 1)`1 つの数字を組み合わせると、次のことが可能になります。`11 * digit * (k - 1)`すべての数字が同じように動作するため、セグメント全体の答えは次のようになります。`11 * (k - 1) * S`これで、すべてのクエリに必要な値は 2 つだけになります。セグメントの長さとセグメント内の桁の合計です。 長さは境界から直接わかり、桁の合計はプレフィックスの合計を使用して答えることができます。 

ブルート フォース ソリューションは、可能なすべての数値を明示的に構築するため機能します。 同じ寄与度の計算を何度も繰り返すため、失敗します。 上記の観察により、これらすべてのペアが 1 つの算術式に圧縮されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | 最適 | O(1) per query after O(n) preprocessing | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. スクロールの数字に対してプレフィックス合計配列を構築します。 インデックスの値`i`最初の合計を格納します`i`数字を使用して、セグメントの合計を減算によって見つけることができます。 これにより、クエリ セグメントを再度スキャンする必要がなくなります。 
2. クエリごとに`[l, r]`、セグメントの長さを次のように計算します。`r - l + 1`。 これにより、選択した各桁と組み合わせられる位置の数がわかります。 
3. プレフィックスの合計を使用して、セグメントの桁の合計を求めます。`prefix[r] - prefix[l - 1]`。 
4. 式を適用する`11 * (length - 1) * digit_sum`そして結果を出力します。 要因`length - 1`は、各桁が別の位置と何回組み合わせられるかを表し、因数は`11`10 と 1 の貢献を組み合わせます。 

なぜ効果があるのか:

 クエリされたセグメント内のすべての数字について、正確に`length - 1`他のポジションの選択肢。 数字がペアの最初の位置にある場合、その値は 10 倍になります。 2 番目の位置の場合は、その値を 1 回提供します。 したがって、数字の寄与度の合計は次のようになります。`11 * digit * (length - 1)`。 これをすべての桁で合計すると、`11 * (length - 1) * sum_of_digits`、まさに必要なポテンシャルです。 プレフィックス合計はすべてのクエリ範囲の正確な桁合計を与えるため、アルゴリズムは常に直接定義と同じ値を計算します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    s = input().strip()

    prefix = [0] * (n + 1)
    for i, ch in enumerate(s):
        prefix[i + 1] = prefix[i] + (ord(ch) - ord('0'))

    q = int(input())
    ans = []

    for _ in range(q):
        l = int(input())
        r = int(input())

        length = r - l + 1
        digit_sum = prefix[r] - prefix[l - 1]

        ans.append(str(11 * (length - 1) * digit_sum))

    print("\n".join(ans))

if __name__ == "__main__":
    solve()
```プレフィックス配列は 1 つの追加要素を使用して構築されるため、範囲は位置から始まります。`1`自然に機能します。 クエリの場合は、`prefix[r] - prefix[l - 1]`要求された数字の正確な合計を返します。 

クエリの長​​さの計算では、入力からの 1 から始まる位置が使用されます。 1での減算`(length - 1)`数字はそれ自体とペアにできないため、これが必要です。 これは、この問題で最も一般的な off-by-one エラーです。 

Python の整数はオーバーフローしませんが、最大の答えは大きくなる可能性があります。 表現はおおよそに達することができます`11 * 100000 * 900000`したがって、通常の整数演算を使用するだけで十分です。
