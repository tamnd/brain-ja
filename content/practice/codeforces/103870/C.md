 ## 解決策
 ## 問題の理解

 ここでは、うるう年以外の簡略化されたカレンダーを使用しています。1 年は 365 日あり、毎日イベントが含まれる場合もあれば、空白の場合もあります。 入力は最終的に、どの特定の日にイベントがあるかを記述し、それ以外は暗黙的に空になります。 

タスクは、イベントがまったくない連続した最長の日数を特定することです。 言い換えれば、すべてのイベント日をマークしたら、それらのマークされた日が 1 つも表示されない連続した日のブロックの最大長が必要になります。 

これについて考えるのに役立つ方法は、各位置が 1 年の 1 日に対応する長さ 365 の配列を想像することです。 値 1 はその日にイベントが発生することを意味し、0 はその日が空いていることを意味します。 目標は、最長の連続するゼロのセグメントを見つけることです。 

配列の長さが 365 に固定されているため、カレンダー サイズの制約は非常に小さくなります。たとえ多数のイベント記述がある場合でも、シミュレーション全体はこの一定サイズの構造によって制限されます。 これにより、大きな入力に対する対数最適化または線形最適化に関する懸念が即座に排除されます。 1 年全体を繰り返しスキャンする単純なシミュレーションでも十分に高速です。 

主な微妙な点は、イベントの説明を日ごとのマークに正しく変換することです。 単純なアプローチでは、カレンダーの日付や繰り返しの間隔を適切に変換せずにイベントを直接のインデックスとして処理しようとする可能性があり、これにより日付が不正確にマークされる可能性があります。 

ここではいくつかの特殊なケースが重要です。 1 つはイベントがまったくない場合です。 この場合、1 年全体が無料となり、答えは 365 になるはずです。少なくとも 1 つのイベントが誤って 0 を返す可能性があると想定した不注意な実装です。もう 1 つのケースは、イベントが毎日をカバーする場合です。 この場合、最長の空きセグメントは 0 となり、オフバイワンのミスは誤って 1 を返すことがよくあります。 3 番目のケースは、イベント生成で繰り返しステッピングが使用され、ステッピングがオーバーシュートしたり、日のインデックス付けとずれたりする場合に発生します。これにより、365 日などの境界日のマーキングが通知なくスキップされる可能性があります。 

## アプローチ

 この強引なアイデアは、どの日が占有されているかがわかれば、365 日の配列をスキャンして連続するゼロをカウントするだけでよいという観察から始まります。 この部分は、非常に小さな定数で線形であるため、単独ではすでに最適です。 

より難しいのは、イベント日の配列を作成することです。 各イベントは、365 日目を過ぎるまで固定ステップ サイズ C を繰り返し追加することで、影響を受ける複数の日を生成できる方法で定義されます。そのようなシーケンスごとに、カレンダー内の対応する位置にマークを付けます。 

単純な構築では、イベント ソースごとに、繰り返し日をインクリメントし、配列を直接マークすることになります。 これはすでに正しく、各シーケンスの反復回数が最大 365/C であり、更新の総数はイベント ソース数の 365 倍に制限されるため、依然として十分に効率的です。 すべてのマーキングが完了すると、1 回のスキャンで最長のゼロの連続が検出されます。 

重要な洞察は、高度なデータ構造や間隔のマージが必要ないということです。 カレンダーは固定されており小さいため、直接シミュレーションがすべてを支配します。 等差数列更新を繰り返す構造は、ブール値のマーキング配列に完全に適合します。 

各イベントは予測可能な一連の離散日にのみ影響を与えるため、総当り攻撃は機能しますが、時期尚早に最適化しようとすると概念的に混乱してしまいます。 ドメインが 365 日しかないという観察により、すべてを直接のシミュレーション問題として扱うことができます。

 ## アルゴリズムのチュートリアル

 ### 1. カレンダー配列を初期化する

 配列を作成します`v`サイズは 366 (1 ベースのインデックス付けが便利です)、ゼロに初期化されます。 各インデックスは、その日にイベントが発生したかどうかを表します。 

これにより、毎日の状態をマークしてクエリする直接的な方法が得られます。 

### 2. 各イベント ジェネレーターを解析する

 各イベントの説明は、最初の日から開始します`d`ステップ サイズを繰り返し追加します`C`。 有効な日 (≤ 365) に到達するたびに、`v[d] = 1`。 

日が 365 を超えるまでこのプロセスを続けます。 

閉じた形式の範囲を計算する代わりにステップを実行する理由は、各イベントが連続的な間隔ではなく、離散的な等差数列を定義するためです。 

### 3. 完全なイベント カレンダーを作成する

 すべてのイベント ジェネレーターを処理した後、少なくとも 1 つのイベントがある毎日が 1 としてマークされます。`v`。 イベントのない日は0のままです。 

複数のジェネレーターが同じ日をマークする可能性があるため、この集計は重要ですが、少なくとも 1 つのイベントが存在するかどうかのみを考慮します。 

### 4. 最長連続ゼロをスキャンします。 

実行中のカウンターを維持しながら、1 日目から 365 日目まで配列を走査します。`cur`現在の空の日の連続のために。 

もし`v[i] == 0`、増分します`cur`場合は答えを更新します`cur`大きくなります。 

もし`v[i] == 1`、リセットします`cur`0 に設定されますが、グローバル最大値はリセットされません。 

現在の連続値とグローバル最大値との間のこの分離により、正確性が保証されます。 

### なぜ効果があるのか

 カレンダーのどの位置でも、その日が占有されているかどうかの正確な分類が維持されます。 次に、スキャンによって問題はバイナリ配列内の最長の連続セグメントを見つけることになり、これは不変式を維持することで解決されます。`cur`は常に、現在のインデックスで終わる連続したゼロ値エントリの数と等しくなります。 毎日が 1 回だけ処理され、マーキング ステップですべてのイベントの発生が完全にキャプチャされるため、セグメントが欠落したり、セグメントの無効な拡張が発生したりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    
    v = [0] * 366  # 1..365
    
    for _ in range(n):
        d, c = map(int, input().split())
        
        while d <= 365:
            v[d] = 1
            d += c
    
    ans = 0
    cur = 0
    
    for i in range(1, 366):
        if v[i] == 0:
            cur += 1
            if cur > ans:
                ans = cur
        else:
            cur = 0
    
    print(ans)

if __name__ == "__main__":
    solve()
```この解決策は 2 つのフェーズに分かれています。まず、等差数列によって生成されたすべてのイベント日をマークしてカレンダーを構築します。 while ループにより、年の範囲内にのみ留まることが保証されます。 2 番目のフェーズは、マークされていない日の最長連続を計算する単一の線形スキャンです。 

一般的な実装上の落とし穴は、イベントの日に遭遇したときに現在のストリークをリセットするのを忘れることです。これにより、別々の無料期間が誤って結合されてしまいます。 もう 1 つは、日の 1 から始まるインデックスの処理を誤っており、調整せずに 0 から始まる配列を使用すると、すべての結果が 1 つずれる可能性があります。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、イベント ジェネレーターがない場合です。 この状況では、カレンダーは完全にゼロで埋められたままになります。 スキャンは 1 日目に開始され、継続的に増加します`cur`これは、アルゴリズムが正しく機能するために少なくとも 1 つのイベントの発生に依存していないことを確認します。 

もう 1 つの特殊なケースは、毎日がイベントとしてマークされる場合に発生します。 たとえば、ジェネレータが 1 から開始してステップ 1 を介してすべての日をカバーする場合、`v`スキャン中は、`cur`はステップごとにリセットされ、0 を超えて累積することはないため、最終的な答えは 0 になります。これにより、部分的な状態を誤って保持することなく、連続したリセットが正しく処理されることが検証されます。 

最後の微妙なケースは、イベント シーケンスがちょうど 365 日目に終了する場合です。 while ループ条件`d <= 365`365 日に達した場合は確実に含まれます。 たとえば、ステップ 1 で 365 日から開始すると、365 日のみがマークされます。その後、スキャンは 365 日をブロッカーとして正しく扱い、それを超えて空き期間を延長しません。
