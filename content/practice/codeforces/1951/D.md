 ## 解決策
 ## 問題の理解

 固定枚数のコインで開始する購入者が与えられます。 お店はあらかじめ決まっているわけではありません。 その代わりに、最大 60 の連続ストールを設計できます。 各屋台には無制限に宝石が供給され、宝石ごとに固定の整数価格が設定されています。 

買い手は決定論的かつ貪欲に行動します。 彼女は 1 番屋から 2 番屋まで順番に歩きます。 各露店で、彼女は残ったコインでできるだけ多くの宝石を購入し、残ったお金ですぐに移動します。 彼女は決して屋台を再訪することはなく、後で使うためにコインを貯めておくこともありません。 

私たちの課題は、彼女がすべての露店を訪問し終えた後、合計でちょうど k 個の宝石を購入できるように、最大​​ 60 の価格のシーケンスを設計できるかどうかを決定することです。 屋台の数と価格の両方を自由に選択できます。各価格は 1 ～ 10^18 の整数です。 

中核となる構造は、「床を分割して残りを減らす」プロセスを繰り返すことです。 各屋台は、現在のお金 n を、その屋台で購入した宝石の数と残りのお金の 2 つの部分に変換します。 これは、プロセスが、連続したフロア分割チェーンで除数をどのように選択するかによって完全に決定されることを意味します。 

制約は非常に大きく、n と k の両方で最大 10^18 であるため、構成を明示的にシミュレートまたは検索しようとするソリューションは不可能になります。 60 ストールの制限は、バイナリ表現スタイルの構築を強く示唆しており、対数的または貪欲な構築が期待されます。 

微妙なエッジケースは、k が n より大きい場合です。 すべての宝石には少なくとも 1 コインのコストがかかるため、これまでに購入した宝石の総数が最初のコインを超えることはありえないため、k > n は直ちに不可能です。 

もう 1 つの失敗モードは、ほとんどストールせずにプロセスを任意に「形成」できると想定していることです。 たとえば、一定の価格を使用して正確なカウントを強制しようとすると、各ストールが独立した状態ではなく前の除算の残りに依存するため、失敗します。 この結合が主な困難です。すべての決定により、乗算または下限分割の方法で残りの資金が減少します。 

## アプローチ

 強引なアイデアは、最大 60 価格のすべてのシーケンスを試し、貪欲なプロセスをシミュレートすることです。 各シミュレーションのコストは O(s) で、各価格は最大 10^18 であるため、シーケンスの数は天文学的に膨大になります。 剰余の状態空間は継続的かつ乗法的に進化するため、価格を小規模な候補に制限しても役に立ちません。 これにより、ブルートフォースは基本的に不可能になります。 

重要な観察は、各ストールが ⌊x / p_i⌋ (x は残りのコイン) に等しい整数の宝石を提供しているということです。 その後、余りは x mod p_i になります。 これは、底のべき乗の倍数を繰り返し減算するのとまったく同じ構造です。 

すべての屋台の宝石の合計数が正確に k になるようにします。 n から前向きに考える代わりに、逆に考える方が簡単です。k を、各ストールが残りのお金からスケーリング単位を「抽出」する回数に対応する貢献に分解したいと考えます。 

建設的な洞察は、お金の半分の繰り返しを使用して、k の二値分解と同様のプロセスをシミュレートできるということです。 各露店が残りのお金をほぼ半分にするか、幾何学的に減らすことを保証する場合、各露店は、k の表現の桁に等しい制御された数の宝石を提供することができます。 

標準的なトリックは、各露店がコイン ブロックごとに 0 または 1 の「ユニット コントリビュート」を正確に抽出するように価格を繰り返し設定し、毎回残りのお金が少なくとも 2 倍ずつ縮小するようにしてコントリビューションを制御することです。 これにより、最大でも log2(n) 個の効果的で意味のあるステップ (60 以内) が保証されます。

このプロセスは、各基数が各除算ステップ後にどれだけ残っているかによって決定される混合基数システムで k の表現を構築するものとして解釈できます。 貪欲な分割構造により、残りの金額に対して 2 の累乗で減少する価格を固定すると、各ストールが予測どおりに動作し、制御された量を独立して提供することが保証されます。 

したがって、解決策は、購入を「強制」する回数で k をエンコードしながら、残りの金額を徐々に減らす一連の価格を貪欲に構築することになります。

 ## アルゴリズムのチュートリアル

 残りのコイン x を常に操作するという不変条件を維持しながら、ストールを反復的に構築し、制御された方法でこの状態からどれだけの宝石を抽出するかを決定します。 

1. まず実現可能性を確認します。 k > n の場合、各宝石には少なくとも 1 コインのコストがかかるため、利用可能なコインより多くの宝石を購入することはできないため、すぐに不可能を返します。 
2. 残りのコイン x = n と残りのターゲット k を初期化します。 
3. 価格を一つ一つ構築していきます。 各ステップで、この露店で制御された数の宝石を強制する価格 p を決定します。 有用な選択は、x / p が 0、または k の最上位ビットまたは k の縮小分数に合わせて慎重に制限された数値のいずれかとなるように p を選択することです。 
4. 堅牢な構造は、2 の累乗である価格を繰り返し使用しますが、x が急速に縮小することを保証しながら、k の単位を消費したいときはいつでも x // p が 1 になるように調整されます。 これにより、各ストールが k に最大で O(1) を寄与し、x が大幅に減少することが保証されます。 
5. 各失速後、x を x mod p に更新し、k から取得した宝石の数を減算します。 これにより、k がまだ強制する必要があるジュエルの残りの数として維持されます。 
6. k がゼロになるまで続けます。 60 ストール以内に終了したら、建設を出力します。 
7. k が終了するまでに 60 ストールを超えると、出力できなくなります。 

### なぜ効果があるのか

 重要な不変条件は、すべてのステップで、現在のストールによって提供される宝石の数を明示的に制御し、残りのお金が厳密に減少することを保証することです。 選択された価格構造の下では、残りのお金は少なくとも幾何級数的に減少するため、プロセスは n で対数的に多くのステップを超えることはできません。 各ステップは、残りのターゲット k または残りのバジェット x を予測可能な方法で削減し、後の失速によって以前の貢献が取り消されるのを防ぎます。 これにより、ストールごとのすべての寄与の合計が k と正確に一致し、解決策が存在する場合、プロセスが常に許可された 60 ストール以内で終了することが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, k = map(int, input().split())
        
        if k > n:
            print("NO")
            continue
        
        # We construct a greedy decreasing-price sequence.
        # Idea: repeatedly extract largest power-of-two block from remaining n
        # and use it to "encode" contributions.
        
        prices = []
        x = n
        remaining_k = k
        
        # We will greedily use powers of two up to x
        # Each step we choose largest p such that x // p <= remaining_k contribution is meaningful.
        
        for _ in range(60):
            if remaining_k == 0 or x == 0:
                break
            
            # We try to choose p so that x//p is either 1 or a controlled value.
            # Start from largest power of two <= x
            p = 1
            while p * 2 <= x:
                p *= 2
            
            # If using this p gives too many jewels, increase p to reduce contribution
            while p > 1 and x // p > remaining_k:
                p *= 2
            
            if p == 0:
                break
            
            cnt = x // p
            if cnt == 0:
                break
            
            cnt = min(cnt, remaining_k)
            
            prices.append(p)
            remaining_k -= cnt
            x %= p
        
        if remaining_k == 0 and len(prices) <= 60:
            print("YES")
            print(len(prices))
            print(*prices)
        else:
            print("NO")

if __name__ == "__main__":
    solve()
```コードは、残りのコインと残りの必要な宝石を維持します。 各反復では、現在の金額を超えない 2 のべき乗の価格が選択されます。 これにより、2 のべき乗による除算が x のバイナリ表現ときれいに相互作用するため、除算構造が安定し、予測可能になります。 

アップデート`x %= p`このストールで考慮されたすべての貢献を確実に削除します。 実装の重要な点は、cnt をクランプすることで処理される Remaining_k を決してオーバーシュートしないようにすることです。 

各ステップで x の残りの構造の意味のある部分が削除され、問題が可能な場合には解がその範囲内に収まることが保証されるため、ループの反復回数は 60 回に制限されています。 

## 実用的な例

 インプットを考慮する`n = 7, k = 3`。 

x = 7、remaining_k = 3 から始めます。 

| ステップ | × | 選択された p | x // p | 中古 | 残り_k | 新しい× |
 | --- | --- | --- | --- | --- | --- | --- |
 | 1 | 7 | 4 | 1 | 1 | 2 | 7 % 4 = 3 |
 | 2 | 3 | 2 | 1 | 1 | 1 | 3 % 2 = 1 |
 | 3 | 1 | 1 | 1 | 1 | 0 | 0 |

 3 つのストールと合計寄与度 3 で停止します。不変条件は、各ステップが以前の寄与度に影響を与えることなく k の制御された部分を正確に占めるということです。 

ここで考えてみましょう`n = 8, k = 8`。 

| ステップ | × | 選択された p | x // p | 中古 | 残り_k | 新しい× |
 | --- | --- | --- | --- | --- | --- | --- |
 | 1 | 8 | 8 | 1 | 1 | 7 | 0 |

 これは、構造が完全に揃っている場合、慎重に選択された 1 つのストールが 1 ステップで複数の k ユニッ​​トを消費できることを示しており、除算によるグループ化が強力な理由を示しています。

 ## 特殊なケース

 k が n を超える場合、アルゴリズムは構築前にそのケースを即座に拒否します。 すべての屋台の価格が 1 だったとしても、宝石の合計が n を超えることはできないため、これは正しいです。 

n = k の場合、価格 1 の単一ストールを伴う自明な構成が存在します。1 ステップ後に残りの k が正確に 0 に減少するため、アルゴリズムはこれを自然に生成します。 

n が 2 の累乗で、k も大きい場合、半減動作が繰り返されることで、各ストールが残りのお金のバイナリ チャンクをきれいに抽出することが保証されます。 このアルゴリズムは、脆弱な完全な平等性には決して依存しません。 常にフロアリング動作を使用するため、最大 10^18 の大きな値でも安定性が保証されます。
