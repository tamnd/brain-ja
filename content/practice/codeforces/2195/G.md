 ## 解決策
 ## 問題の理解

 すべての頂点がちょうど 2 つの子を持つか、葉であるルート付き二分木が与えられます。 ルートは頂点 0 で、他のすべての頂点には 1 から n までの番号が付けられます。 プロセスはある頂点 v から開始され、非常に具体的なステートフル ルールに従って段階的に進みます。 

各頂点には、空、L、または R の 3 つのマークのいずれかが格納されます。最初はすべての頂点が空です。 ボブが頂点に立ったとき、彼の次の動きは、ツリーの構造とその頂点に以前に書き込まれた内容の両方に依存します。 現在の頂点がリーフの場合、常にその親に移動します。 それ以外の場合、頂点は小さな 3 状態のオートマトンのように動作します。 最初の訪問では L を書き込んで左に移動し、2 回目の訪問では R に上書きして右に移動し、3 回目の訪問では消去して上向きの親に送信します。 その後、このサイクルが繰り返されます。 

多くのクエリでは、特定の頂点 v から開始して正確に k 回の動きについてこのプロセスをシミュレートするように求められますが、k がルートに逃げるのに必要な時間よりも厳密に短いことが保証されます。 したがって、実際には頂点 0 での吸収状態に到達することはなく、これにより終了に関連する複雑さが解消されます。 

制約は大きく、全体で最大 3e5 頂点と 4e5 クエリです。 移動ごとにツリーの状態を文字通り更新する単純なシミュレーションでは、クエリごとに O(k) が必要になりますが、k は 1e9 に達する可能性があるため、これはまったく実行不可能です。 クエリは独立していますが、ツリー上で同じ暗黙的な無限ステート マシンを共有するため、クエリごとの完全なシミュレーションさえも不可能です。 

微妙なエッジケースは、プロセスが単純な走査ではないことです。 頂点は複数回訪問することができ、その頂点の出方向は周期的なローカル状態に依存します。 たとえば、左の子がリーフであるノードから開始すると、最初の訪問では左への移動が強制されますが、次に同じノードを訪問すると方向が完全に変わります。 パスが固定されていないため、DFS の素朴な直感は崩れます。 

もう 1 つの失敗モードは、ルートに向かう単調な動き、または予測可能なパターンで常に左右に交互に動くことを想定していることです。 「親へ消去」ステップでは、ノードが訪問された回数に応じたバックトラッキングが導入されます。これは、現在の位置だけでなく、完全な履歴に依存します。 

## アプローチ

 直接シミュレーションでは、すべてのノードの状態が維持され、クエリごとに k 回の遷移が実行されます。 各遷移は O(1) ですが、k は最大 1e9 になる可能性があるため、最悪の場合の複雑さは O(q · k) となり、制限をはるかに超えています。 

各ノードからの遷移を固定状態でキャッシュしようとしても、難しいのは、ノードの状態がローカルであるだけでなく、現在の実行でそのノードがアクセスされた回数に依存することです。 異なるクエリは異なるノードから開始されるため、グローバルに共有された状態の進化はありません。 

重要な観察は、グローバル状態は進化しますが、各頂点が訪れるたびに決定論的な 3 段階のサイクルに従うということです。 これは、動作が木の端に沿って繰り返される構造化された回遊としてモデル化できることを意味します。ボブはノードから、葉に当たるまで繰り返し子に下降し、その後上に戻ります。これらの回遊は、方向の決定が訪問パリティ モジュロ 3 に依存する点を除いて、オイラー ツアーと同様のパターンで繰り返されます。 

移動をシミュレートする代わりに、すべてのノードから開始する場合、プロセスの決定論的な走査順序全体を事前計算しますが、ルートへの戻りが関係する点までに限ります。 これにより、プロセスは、ノードがペア (頂点、状態) である暗黙的な有向グラフ上を歩くものとして解釈されます。ここで、状態は、空、L、R の遷移を表す 0、1、2 です。

重要な簡略化は、各クエリがこの拡張された状態グラフ上の決定論的ウォークのプレフィックスを要求することです。 k はエスケープ時間より小さいため、終端ノード 0 に到達することはありません。これは、グラフの循環部分内にとどまることを意味します。 したがって、この状態グラフの時間ステップにわたるバイナリ リフティングを使用してジャンプ ポインターを前処理できます。 

1 つの移動後に次の (頂点、状態) を与える遷移関数 nxt[v][s] を構築します。 次に、O(log n) で k ステップをジャンプできるようにバイナリ リフティング テーブルを構築します。 

難しいのは、すべての訪問のすべての状態を明示的に保存せずに nxt を効率的に構築することです。 遷移はローカル状態のモジュロ 3 のみに依存し、子の構造は固定されるため、各頂点を独立して処理することで nxt を O(n) で計算できることを利用します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースシミュレーション | O(q・k) | O(n) | 遅すぎる |
 | 状態グラフ + バイナリ リフティング | O((n + q) log n) | O(n log n) | 承認済み |

 ## アルゴリズムのチュートリアル

 各頂点 v は、現在のサイクルで何回使用されたかを表す 3 つの内部状態を持つものとしてモデル化されます。 (v, state) が与えられると、1 回移動した後に次の位置を返す関数を定義します。 

1. 各頂点の状態 0、1、2 を定義して、それぞれ空、L、R の動作を表します。 これは、繰り返しの訪問時にノードがどのように動作を変更するかを正確にエンコードするため、ツリーを動的に変更する必要がなくなります。 
2. 各 (v, state) について、ツリー構造を使用して次の位置を明示的に計算します。 v が葉の場合、状態に関係なく、次の頂点がその親になります。 これは強制脱出ルールです。 
3. v が葉ではない場合、次の規則に従います。 

状態が 0 の場合、左の子に移動して状態を 1 に更新します。 

状態が 1 の場合、右側の子に移動して状態を 2 に更新します。 

状態が 2 の場合、親に移動して状態を 0 にリセットします。 

これにより、グローバル メモリを変更せずにローカル オートマトンが完全にエンコードされます。 
4. 3(n+1) 状態にわたる有向グラフを構築します。各ノードは出力エッジを 1 つだけ持ちます。 これにより関数グラフが形成されます。 
5. 各状態について、遷移の 2 倍化を繰り返して、log K までのバイナリ リフティング祖先を事前計算します。 各ステップは、関数グラフ内の遷移を構成します。 
6. 各クエリ (v, k) について、それを初期状態 (v, 0) にマッピングし、バイナリ リフティングを適用して関数グラフに沿って k ステップを移動します。 
7. 結果の状態の頂点コンポーネントを出力します。 

### なぜ効果があるのか

 重要な不変条件は、(頂点、状態) でエンコードされると、プロセス全体がメモリレスになるということです。 すべての動きはこのペアのみに依存しており、世界の歴史には依存しません。 したがって、ラベルを進化させる元のプロセスは、サイズ 3(n+1) の固定有向グラフ上の決定論的なウォークと等価です。 各クエリは特定のノードから始まるこのウォークのプレフィックスを要求するため、バイナリ リフティングはシミュレーションなしで k 回の遷移後の正確な位置を正しく計算します。 エンコードされた状態の外部の情報に依存するステップはないため、正確さは遷移システムの等価性から生じます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

LOG = 20

def solve():
    n, q = map(int, input().split())
    l = [0] * (n + 1)
    r = [0] * (n + 1)
    par = [0] * (n + 1)

    for i in range(1, n + 1):
        li, ri = map(int, input().split())
        l[i], r[i] = li, ri
        if li:
            par[li] = i
        if ri:
            par[ri] = i

    # state id: v * 3 + s
    N = (n + 1) * 3

    def id(v, s):
        return v * 3 + s

    nxt = [0] * N

    for v in range(n + 1):
        for s in range(3):
            if v == 0:
                nxt[id(v, s)] = id(v, s)
                continue

            if l[v] == 0 and r[v] == 0:
                nxt[id(v, s)] = id(par[v], 0)
                continue

            if s == 0:
                to = l[v]
                ns = 1
            elif s == 1:
                to = r[v]
                ns = 2
            else:
                to = par[v]
                ns = 0

            nxt[id(v, s)] = id(to, ns)

    # binary lifting
    up = [[0] * N for _ in range(LOG)]
    for i in range(N):
        up[0][i] = nxt[i]

    for k in range(1, LOG):
        prev = up[k - 1]
        cur = up[k]
        for i in range(N):
            cur[i] = prev[prev[i]]

    for _ in range(q):
        v, k = map(int, input().split())
        cur = id(v, 0)
        for i in range(LOG):
            if k & (1 << i):
                cur = up[i][cur]
        print(cur // 3)

if __name__ == "__main__":
    solve()
```この実装では、展開された状態に対して明示的な遷移グラフを構築し、標準のバイナリ リフティングを適用します。 微妙な点は、各ノードと状態のペアが決定論的なマシン状態として扱われるため、変更可能なノードごとのラベルを決して保存しないことです。 代わりに、状態の進化はグラフ構造自体に吸収されます。 最後に 3 で除算すると、エンコードされた状態から頂点インデックスが復元されます。 

よくある落とし穴は、0 または葉の親の処理が一貫性を欠いていることです。 ここで、頂点 0 は、遷移が決して頂点 0 から離れることがないように吸収されており、クエリが k が厳密に 0 に達する前であることを保証するという事実と一致します。 

## 実用的な例

 1 に子 2 と 3 があり、2 と 3 の両方が葉である小さな木を考えてみましょう。 状態 0 の頂点 1 から開始するとします。 

| ステップ | (v、状態) | アクション | 次へ (v, 状態) |
 | --- | --- | --- | --- |
 | 1 | (1,0) | 左に行く | (2,1) |
 | 2 | (2,1) | 葉→親 | (1,0) |
 | 3 | (1,0) | 左に行く | (2,1) |
 | 4 | (2,1) | 葉→親 | (1,0) |

 これは、ローカル状態の動作をオーバーライドするリーフ ルールにより、プロセスが親とリーフの間で振動することを示しています。 

ここで、それ自体が内部にある右側の子を持つノードから開始することを考えてみましょう。 (1,0) から開始:

 | ステップ | (v、状態) | アクション | 次へ |
 | --- | --- | --- | --- |
 | 1 | (1,0) | 左 | (L,1) |
 | 2 | (L,1) | 葉か内部に依存します | ... |

 これは、シーケンスが固定された走査順序ではなく、エンコードされた遷移に完全に依存していることを示しています。 

これらの例では、各頂点と状態のペアを決定論的なノードとして表すことで、元のプロセスの正確なダイナミクスが保存されることが確認されています。
