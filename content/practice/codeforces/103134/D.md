 ## 解決策
 ## 問題の理解

 私たちには一連の参加者が与えられており、各参加者は特定の日から参加可能になり、その後は毎日参加可能になります。 したがって、各参加者はしきい値時間を提供し、選択した日には、その日にしきい値が最大であるすべての参加者を考慮します。 

いつの日も$D$、存在する参加者の数は単に値の数です。$a_i \le D$。 ただし、コンテストは、このカウントが 3 で割り切れる場合にのみ有効です。そのようなすべての有効な日の中で、可能な最大参加者数という意味で最も早い日、より正確には、その数を 3 で割り切れる範囲内で最大の参加者が得られる日が必要です。そのような日が存在しない場合は、-1 を出力します。 

重要な点は、日数が入力サイズに制限されないことです。 それぞれ$a_i$と同じ大きさにすることができます$10^{18}$したがって、答えは常に指定された値の 1 つ、または概念的にはそれらの「間」になりますが、カウントが変化するのはちょうどそのときだけです。$a_i$価値観。 Between two consecutive distinct$a_i$、アクティブな参加者のセットは変わりません。 

これは、最適な日の候補がどれも異なる日の 1 つに絞り込めることをすでに示唆しています。$a_i$2 つの値の間で厳密に日を選択すると、より小さい境界と同じ参加者数が生成されますが、実現可能性は決して向上しないためです。 

範囲は次のとおりであるため、考えられるすべての日にわたる単純なスキャンは不可能です。$10^{18}$。 ソートされた順序ですべての値をスキャンすることさえも、重複を圧縮し、ブレークポイントでのみ推論する場合にのみ実現可能です。 

ここで重要となるエッジケースは、値の繰り返しと割り算の調整です。 たとえば、同じ日に多くの参加者が参加可能になる場合、カウントは 1 を超えてジャンプし、3 の倍数を完全にスキップする可能性があります。 たとえば、ある日のカウントが 2 から 4 になった場合、要件は正確な 3 の倍数に依存するため、これら 2 つのカウントの間に有効な日は存在しません。 

もう 1 つのエッジ ケースは、最終的な参加者の合計数が 3 で割り切れない場合です。たとえ最終日に全員が含まれていたとしても、無効になる可能性があるため、カウントが 3 の倍数に達する最も近い以前のプレフィックスを見つける必要があります。 

## アプローチ

 この強引なアイデアは、日を昇順にシミュレートし、毎日、アクティブな参加者の数を計算することです。 それぞれのアクティビティでのみ変化するため、$a_i$場合は、配列をソートしてスイープし、個別の値ごとにカウントを再計算します。 これにより、正確なプレフィックス サイズが得られ、3 で割り切れるかどうかを確認できるようになります。 

ただし、毎日繰り返すような不用意な実装は不可能です。$10^{18}$範囲。 すべての個別の値を反復処理することも問題ありませんが、毎回カウントを最初から再計算すると遅すぎて、$O(n^2)$最悪の場合の行動。 

重要な観察は、配列をソートすると、答えがプレフィックス サイズのみに依存するプレフィックス構造が得られるということです。 ソートされた位置で$i$、アクティブな参加者の数は$i+1$。 私たちが気にするのはインデックスだけです。$i+1$は 3 で割り切れます。これらの指数の中で最良の日は、単にその指数の値です。 複数の値が等しい場合でも、それらは個別の参加者として扱われるため、重複は順序ではなく数のみが問題になります。 

したがって、問題はソートとスキャンを 1 回行い、プレフィックス サイズが 3 で割り切れる最後のインデックスを選択することに帰着します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 数日間にわたるブルート フォース シミュレーション | O(10^18) | O(n) | 遅すぎる |
 | ソート + プレフィックス チェック | O(n log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. すべての参加者の可用性日数を配列に読み取ります。各値は、参加者が常に存在するしきい値を表すためです。 これらの値を並べ替えると、アクティブ セットが時間の経過とともにどのように増加するかを理解できます。 
2. 参加者が利用可能になった順に処理されるように、配列を非降順で並べ替えます。 これにより、問題は任意の日について推論するのではなく、プレフィックス サイズの追跡に変わります。 
3. インデックスを使用してソートされた配列を反復処理します。$i$、その時点でのアクティブな参加者の数は$i+1$。 これが機能するのは、しきい値がそれより小さいか等しいすべての参加者が、まさにプレフィックス内の参加者であるためです。 
4. 各インデックスについて$i$、どうかを確認してください$i+1$は 3 で割り切れます。割り切れない場合は、その日はチーム サイズが 3 の倍数でなければならないという制約に違反するため、スキップしてください。 
5.いつでも$i+1$3 で割り切れる場合は、対応する日の値を記録します$a[i]$答えの候補として。 後のインデックスはより多くの参加者に対応するため、常に以前の候補を上書きします。これは、目的の下では厳密に優れているためです。 
6. すべての値を処理した後、最後に記録された有効な日を出力します。 有効なインデックスが見つからなかった場合は、-1 を出力します。 

### なぜ効果があるのか

 いつでも$D$、参加者の数は、ソートされたプレフィックスのサイズと正確に一致します。$a_i$それは以下です$D$。 アクティブな参加者のセットは次の場合にのみ変更されるため、$D$配列内の値と交差する場合、答えのすべての意味のある変更は、ソートされた位置の 1 つに対応します。 3 で割り切れる条件はプレフィックスの長さにのみ依存するため、インデックスをチェックすると、中間日を見逃したり、連続範囲を考慮したりする必要がなく、考えられるすべての有効な構成が直接取得されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input())
    a = list(map(int, input().split()))
    a.sort()

    ans = -1

    for i in range(n):
        if (i + 1) % 3 == 0:
            ans = a[i]

    print(ans)

if __name__ == "__main__":
    solve()
```ソートのステップは、問題を任意のアクティブ化時間に関する推論からプレフィックス サイズに関する推論に変換するため、不可欠です。 次に、ループは、3 で割り切れるカウントのみが有効であるという制約を直接エンコードします。 最終的な割り当てには常に、制約の下で可能な最大出席者数に対応する最新の有効な日が保持されます。 

ここでよくある間違いは、すべての一意の値を評価しようとし、並べ替え順序と同期していないポインターを使用してカウントを再計算しようとすることです。 これにより、重複が存在する場合、通常、off-by-one エラーや遷移の欠落が発生します。 プレフィックス解釈はそれを完全に回避します。

 ## 特殊なケース

 重要なエッジケースは、すべての値が同一である場合です。 その場合、すべてのプレフィックス ジャンプは同じ日に行われるため、アルゴリズムは依然として各参加者を個別に処理する必要があります。 並べ替えではこれが保持され、プレフィックス サイズのみが有効性を制御するため、最後の 3 のプレフィックスの倍数によって正しく答えが得られます。 

もう 1 つのエッジケースは次のような場合です$n < 3$。 3 で割り切れるサイズのプレフィックスが存在しないため、アルゴリズムは正しく答えを -1 のままにします。 

最後の微妙なケースは、有効なプレフィックス サイズは存在するが、個別の日に到達できない場合です。 重複により複数の有効なプレフィックス サイズが同じ日の値に対応する場合でも、重複は同時に参加している個別の参加者を表すため、最後の出現を選択すると正しい最大の参加者数が得られます。
