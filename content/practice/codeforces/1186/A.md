 ## 解決策
 ## 問題の理解

 小さな分布問題が与えられました。 コンテストには複数の参加者がおり、各参加者はペン 1 つとノート 1 つという 2 つのアイテムを受け取る必要があります。 主催者はペンとノートの在庫を一定にしており、全員が同時に満足できるかどうかを判断することが課題となります。 

形式的には、n 人の参加者のそれぞれが 1 つのペンと 1 つのノートを必要とするため、合計の需要は n 本のペンと n 冊のノートになります。 問題は単に、利用可能な量 m と k がこれら 2 つの独立した要件を同時にカバーするのに十分であるかどうかです。 

制約は非常に小さく、すべての値が 100 で制限されています。これにより、最適化や複雑なデータ構造の必要性が即座に排除されます。 単純なシミュレーションでもせいぜい数百ステップしか実行しないため、一定数の操作を実行するソリューションであればどれでも十分です。 

意味のある障害が発生するのは、2 つのリソースのうち一方が豊富であっても、一方が不足している場合のみです。 たとえば、n = 8、m = 5、k = 100 の場合、ノートだけで十分であっても、ペンだけではタスクを実行できません。 同様に、m = 100、k = 2、n = 5 の場合、ノートブックだけでは実現可能性が妨げられます。 もう少し微妙な間違いは、アイテムの合計 m + k を 2n と誤って比較しようとした場合に発生し、1 つのカテゴリが完全に欠落している無効な分布が発生する可能性があります。 

## アプローチ

 ブルートフォース解釈では、参加者ごとにアイテムを割り当てようとします。 n 人の参加者それぞれについて、在庫からペンとノートを 1 冊ずつ減らし、ゼロを下回ることがないかどうかを確認します。 これは流通プロセスを直接シミュレートしているため、これは正しいです。 

ただし、この総当りは単純ではありますが、必要ありません。 これは n 回の反復を実行し、それぞれが一定の作業を実行します。これはここではまだ問題ありませんが、概念的には冗長です。 さらに重要なのは、問題の構造が曖昧になることです。各参加者は、各リソース プールから正確に 1 ユニットを独立して消費します。これは、実現可能性の条件が 2 つの独立したチェックに分解されることを意味します。 

重要な洞察は、参加者間には数を数えること以外の相互作用は存在しないということです。 各参加者が正確に 1 つのペンと 1 つのノートを使用していることがわかれば、問題全体は 2 つの不等式を検証することになります。つまり、ペンが少なくとも n であるかどうか、およびノー​​トが少なくとも n であるかどうかです。

 ## アルゴリズムのチュートリアル

 1. 整数 n、m、k を読み取ります。これらはそれぞれ参加者、ペン、ノートの数を表します。 
2. ペンの数が n 以上であるかどうかを確認します。 この条件により、すべての参加者に 1 本のペンを使い果たすことなく割り当てることができます。 
3. ノートブックの数が n 以上であるかどうかを確認します。 これにより、ノートブックに対しても同じ実現可能条件が保証されます。 
4. 両方の条件が同時に成立する場合は、「Yes」を出力します。 それ以外の場合は「いいえ」を出力します。 

### なぜ効果があるのか

 各参加者は、2 つの独立したリソースからそれぞれ 1 つのユニットを必要とします。 ペンとノートを共有、再利用、または代替することはできません。 つまり、実現可能性は、各リソース プールが個別に需要 n を満たすかどうかによって完全に決定されます。 割り当てはすべての参加者に対して独立していて同一であるため、両方のグローバル制約を満たすと有効な配布が保証され、どちらかの制約が満たされない場合は、他のリソースがどのように配布されるかに関係なく、配布が不可能になります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m, k = map(int, input().split())
    if m >= n and k >= n:
        print("Yes")
    else:
        print("No")

if __name__ == "__main__":
    solve()
```コードは 3 つの入力値を読み取り、2 つの必要な条件を直接チェックします。 どちらのリソースも他方のリソースの不足を補うことができないため、比較はペンとノートに対して個別に行われます。 出力はこのブール条件に基づいてすぐに出力され、解は定数時間になります。 

よくある実装上の間違いは、m + k >= 2 * n のみをチェックすることです。これにより、各参加者が両方のアイテムを同時に受け取る必要があるという要件が無視されます。 もう 1 つの間違いは、結合されたプールから貪欲に減算することです。これにより、リソースの混合が誤って許可されてしまいます。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    n, m, k = map(int, sys.stdin.readline().split())
    return "Yes" if m >= n and k >= n else "No"

# provided samples
assert run("5 8 6") == "Yes"
assert run("3 9 3") == "Yes"

# custom cases
assert run("1 1 1") == "Yes"
assert run("1 0 1") == "No"
assert run("10 100 9") == "No"
assert run("100 100 100") == "Yes"

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、一方のリソースが n に正確に等しいのに、もう一方のリソースがはるかに大きい場合です。 たとえば、n = 4、m = 4、k = 100。アルゴリズムは m ≥ n および k ≥ n をチェックするため、True を返します。 ペンが余っても参加者全員に 1 冊のノートが必要なので、これは現実と一致します。 

もう 1 つのエッジ ケースは、n = 10、m = 19、k = 1 など、両方のリソースの合計が大きいものの、カテゴリごとにバランスが取れていない場合です。m + k が 20 で 2n を超えている場合でも、k < n であるため、アルゴリズムは正しく No を返します。 段階的に、ノートブックのチェックはすぐに失敗し、無効な配布が防止されます。 

最後のエッジ ケースは、最小入力 n = 1、m = 0、k = 1 です。ペン条件が失敗するため、アルゴリズムは No を出力します。これは、参加者が 1 人でも完全に装備できないという事実と一致します。
