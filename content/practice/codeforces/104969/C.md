 ## 解決策
 ## 問題の理解

 シェリーが到着する前に、私たちには一定の人数の列が与えられ、ピザのスライス、タコス、ソースの部分が共有されます。 列に並んでいる各人は、何品を取るかを独立して選択しますが、2 つのルールによって制限されます。1 つは合計で最大 2 つの食品を取ることができ、ちょうど 2 つのソースを取る場合は、自分が選択した 1 つの追加の食品を取ることが許可されます。 

シェリーの注文はピザ 1 枚とタコス 1 つとすでに決まっているので、彼女の関心は彼女自身の選択ではなく、彼女がカウンターに着くまでにピザまたはタコスのいずれかを使い果たすのに十分なリソースを前の人​​が消費できるかどうかです。 問題は、シェリーの番の前にピザまたはタコスの在庫の少なくとも 1 つがゼロまたはマイナスになるような、前の人たちに有効な選択肢の順序が存在するかどうかです。 

入力により、Shelly の前の人数が示され、その後にピザ、タコス、ソースの初期数量が続きます。 出力は単に、有効な選択順序の下でピザまたはタコスのいずれかを枯渇させることが可能かどうかです。 

この制約では、最大 100,000 人の人物と最大 100,000 のアイテム数が許可されます。 これにより、たとえ小さな分岐要素であっても指数関数的な時間に爆発的に増加するため、人ごとに可能な選択肢のすべての組み合わせを調査しようとするシミュレーションは即座に除外されます。 解決策は、問題を 1 人当たりの最悪の場合の消費量についての推論に帰着させる必要があります。 

微妙な問題は、ソースの入手可能性によって、各人が摂取できる量が変わる可能性があることです。 注意して扱わないと、ソースは無関係である、または常に十分であると誤って考える可能性があります。 もう 1 つの罠は、各人が常に同じ数のアイテムを取ると仮定していることです。実際には、「ソースが 2 つ追加されたアイテム」ルールにより、誰かがピザまたはタコスの使用量を最大化できるかどうかに影響を与える 2 つの異なる消費モードが作成されます。 

最も重要なエッジケースは、ソースがすべての人に余分な消費を可能にするのに十分な場合であり、これにより、可能な総需要が大幅に増加し、枯渇が達成可能かどうかが変わる可能性があります。 

## アプローチ

 ブルートフォースの観点では、n 人の各人が制約に従って品目を選択できるすべての可能な方法をシミュレートし、残りのピザ、タコス、ソースを追跡しようとします。 各人について、食料品を 0 品目か 1 品目か 2 品目を取るか、ソースを費やすかどうかで分岐します。 リソースがマイナスになったときに無効な状態を取り除いたとしても、各人が複数の独立した決定を導入するため、可能な状態の数は n とともに指数関数的に増加します。 n = 10^5 では、これは完全に不可能です。 

重要な観察は、選択の正確な順序は気にせず、ピザまたはタコスを使い果たす順序が存在するかどうかだけを気にしているということです。 これにより、問題は「可能な最大の消費」の問題に変わります。 人々を個別にシミュレートするのではなく、最適な敵対的行動の下で最初の n 人が摂取できるピザまたはタコスの最大数はいくらか、と尋ねます。 

1 人につき 2 品目まで、ソースが 2 つある場合は 3 品目まで取ることができます。 これは、本当の問題は、何人の人が 2 つのアイテムではなく 3 つのアイテムを取るように「アップグレード」できるかということを意味します。そのような各アップグレードではちょうど 2 つのソースが消費されるため、アップグレードされる人の数は Z と n の両方によって制限されます。 

したがって、取得されるアイテムの最大数は、3 つのアイテムを取得し、残りが 2 つのアイテムを取得する人数を最大化することによって制限されます。これから、取得されたすべてのアイテムがピザ (またはタコス) に集中していると仮定して、単一のアイテム タイプの最悪の消費量を計算します。 X または Y のいずれかが、単一カテゴリのこの最大可能需要以下の場合、枯渇の可能性があります。 

問題は、次のことを確認することに帰着します。 

最大でも min(n, Z // 2) 人が 3 つのアイテムを取得でき、残りは 2 つのアイテムを取得できるとすると、n 人に十分な「アイテム スロット」を割り当てることができます。

 ## アルゴリズムのチュートリアル

 この問題を、最初の n 人が消費できるアイテムの最大数を計算する問題に変換します。 

1. 何人がソースから追​​加アイテムを受け取ることができるかを計算します。 1 人あたり 2 つのソースが必要となるため、アップグレードされる人の数は`k = min(n, Z // 2)`。 これにより、ソースの供給量や利用可能な人数を超過することなく、ソースを利用できる人の数が最大化されます。 
2. これらの k 人について、それぞれが 2 つではなく 3 つのアイテムを受け取り、貢献します。`3k`消費したアイテムの合計。 
3. 残りについて`n - k`人々は、それぞれが基本最大 2 つのアイテムのみを受け取り、貢献します`2(n - k)`アイテム。 
4. これらの貢献を合計して、シェリーが到着するまでに消費できるアイテムの合計最大数を取得します。`total = 3k + 2(n - k)`。 
5. ピザかタコスがなくなるかどうかだけを気にするため、最悪の場合の集中を考慮します。すべての消費アイテムが 1 種類である場合、1 つのリソースの最大消費可能量は次のようになります。`total`。 比較します`total`X と Y の両方に対して。 
6. X <= 合計または Y <= 合計のいずれかの場合は「yes」を出力し、それ以外の場合は「no」を出力します。 

### なぜ効果があるのか

 重要な不変条件は、すべての選択肢の有効な順序が 1 人あたり最大 2 品目の選択に対応し、一部の人々はソースを 2 つ消費した場合に限り、オプションで正確に 1 品目の追加アイテムを獲得できるということです。 表現`3k + 2(n-k)`これは、ソース限定のアップグレードと 1 人あたりの上限という両方の制約を独立して飽和させるため、有効な構成で生成できるアイテム スロットの最大合計数を取得します。 実際の実行ではこの制限を超えることはできず、可能な限り 1 人あたりのアイテム数を常に最大化することでこの制限を達成する戦略が存在します。 これにより、敵対的な質問が 1 つのスカラー比較に縮小されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n = int(input().strip())
    X, Y, Z = map(int, input().split())

    k = min(n, Z // 2)
    total = 3 * k + 2 * (n - k)

    if X <= total or Y <= total:
        print("yes")
    else:
        print("no")

if __name__ == "__main__":
    solve()
```実装では、ソースを使用してアップグレードできる人の数を直接計算し、総消費容量を導き出します。 唯一の微妙な点は、整数の除算を確実にすることです`Z // 2`、アップグレードした人はそれぞれちょうど 2 つのソースを消費するためです。 

どちらかのリソースが枯渇すれば十分であるため、最後の比較では両方のリソースを独立してチェックします。

 ## 特殊なケース

 エッジケースの 1 つは、前に人がいない場合です。 その場合、消費は起こらず、ピザもタコスもシェリーより先になくなることはありません。 式は次のようになります`k = 0`、`total = 0`、正しく「いいえ」となります。 

もう 1 つのケースは、ソースの供給量が非常に多いが、n が小さい場合です。 Z が巨大な場合でも、アップグレードは n によって制限されるため、アルゴリズムは消費量の過大評価を適切に防ぎます。 

3 番目のケースは、Z がゼロの場合です。 その場合、アップグレードは不可能となり、総消費量は厳密に制限されます。`2n`。 これは、誰も 2 つの項目を超えてはいけないという制約を正しくモデル化しています。
