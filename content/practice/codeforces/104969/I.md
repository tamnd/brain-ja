 ## 解決策
 ## 問題の理解

 巨大な 2D グリッド上の一連の点が与えられます。 各点は、その座標に位置する敵を表します$(x_i, y_i)$そして重みを運ぶ$s_i$。 2 人の敵が同じ座標を共有することはありません。 

敵ごとに、原点からその敵の位置までの長方形の領域にどれだけの総戦力が存在するかを計算する必要があります。 つまり、クエリポイントの場合、$(x_i, y_i)$、すべての敵の強さを合計します$(x_j, y_j)$そのような$x_j \le x_i$そして$y_j \le y_i$。 

したがって、各出力値は、座標優位性によって定義される 2D 半順序にわたるプレフィックスの合計です。 

難しさは規模から来ます。 最大 200,000 点と最大座標値$2 \cdot 10^9$、グリッドを構築したり、座標全体にわたるプレフィックスの蓄積を直接シミュレートしたりすることはできません。 クエリごとに以前のすべてのポイントを検査しようとするアプローチでは、おおよその結果が得られます。$O(N^2)$限界をはるかに超えた行動。 

単純なアプローチでも、次の基準だけで並べ替えようとすると、微妙に失敗します。$x$そして蓄積する$y$-prefix は慎重な構造を持たずに合計されます。 その理由は、支配関係が 1 次元ではなく 2 次元であるため、2 次元にわたる構造を積極的に維持しない限り、単一のソート順で処理しても自動的に正確性が保たれないためです。 

座標は明確に区別されることが保証されているため、厄介な重複座標の問題はありませんが、値が大きくなる可能性があるため、圧縮するか直接インデックス付けを回避する必要があります。 

## アプローチ

 直接的な方法は、すべての点をスキャンし、両方の座標が小さいか等しいかどうかを確認することによって、各クエリに個別に答えることです。 これは定義を正しく実装しますが、次のことが必要です。$N$クエリごとの比較、その結果$O(N^2)$総仕事量。 と$N = 2 \cdot 10^5$、のオーダーになります。$4 \cdot 10^{10}$比較することは不可能です。 

重要な観察は、クエリが 2 次元の古典的な支配的なプレフィックスの合計であるということです。 ポイントを昇順に処理できれば$x$、ポイントを処理する瞬間$(x_i, y_i)$、すべての点が小さい$x$すでに計上されています。 残りの課題は、これらを満たすものを効率的に合計することです。$y \le y_i$。 

これにより、問題は、動的構造を維持することになります。$y$- プレフィックス合計とポイント更新をサポートする座標。 各ポイントはその強度に一度寄与します。これまでに挿入された合計重量がどのくらいかをクエリする必要があります。$y$- しきい値によって境界が定められた座標。 

なぜなら$y$まで可能です$2 \cdot 10^9$、座標をランクに圧縮します。 圧縮後、フェンウィック ツリー (バイナリ インデックス ツリー) を使用します。$y$-ランク。 すべてのポイントを次の基準で並べ替えます$x$、それらを昇順に処理し、各ポイントについて、フェンウィック ツリーにプレフィックスの合計を問い合わせます。$y$-ランク。 次に、その重りをフェンウィック ツリーに挿入します。 

微妙な点の 1 つは、入力ポイントの元の順序で回答を出力する必要があることです。 したがって、正確性を保つためにソートされた順序で処理しながら、結果をインデックスごとに保存します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |

 | ブルートフォース | O(N^2) | お(1) | 遅すぎる |
 | ソート + フェンウィック ツリー | O(N log N) | O(N) | 承認済み |

 ## アルゴリズムのチュートリアル

 まず、問題を、一方の軸に沿って段階的に処理できるものに変換し、もう一方の軸では高速なクエリをサポートします。 

1. 各ポイントに、その入力位置に対応するインデックスを割り当てます。 これは、処理中にポイントの順序を変更しますが、回答を元の順序で出力する必要があるために必要です。 
2. すべて抽出する$y_i$値を取得し、連続した範囲に圧縮します$[1, N]$。 このステップでは、順序を維持しながら、フェンウィック ツリーを使用できるようにします。 相対的な順序付けのみであるため、圧縮は機能します。$y$-values はプレフィックスの合計に重要です。 
3. すべてのポイントを昇順に並べ替えます$x_i$。 2 つの点が等しい場合$x$、座標が別個であるため、ここではそれらの間の順序は重要ではありませんが、そうでない場合でも、通常は任意に関係を解除します。 
4. 圧縮されたファイル上でフェンウィック ツリーを初期化します。$y$-range、最初は空です。 
5. ソートされた順序でポイントをスイープします。$x$。 それぞれのポイントについて$(x_i, y_i, s_i)$:

 1. 圧縮されたすべての強度の合計についてフェンウィック ツリーをクエリします。$y \le y_i$。 これにより、必要な長方形内にある、以前に処理されたすべての点の合計寄与が得られます。 
2. この値を現在の点の答えとして保存します。 
3.追加してフェンウィックツリーを更新します。$s_i$位置にある$y_i$、将来のポイントが大きくなります$x$その貢献がわかります。 

すべてのポイントを処理した後、保存された回答は要求された内容に正確に対応します。$F(x_i, y_i)$。 

これが機能する理由は、クリーンな不変条件を維持することにあります。フェンウィック ツリーは、スイープのどの時点でも、すべてのポイントの強度の合計を正確に保存します。$x$- 座標が現在のスイープ位置以下である$x$、彼らによってインデックス付けされます$y$-座標。 したがって、プレフィックスクエリは$y$両方の座標制約を満たすサブセットを正確に選択します。 すべてのポイントは、その寄与がそれ自体に対してクエリされた後に正確に 1 回挿入されるため、値が欠落したり二重にカウントされたりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.bit = [0] * (n + 1)

    def add(self, i, v):
        while i <= self.n:
            self.bit[i] += v
            i += i & -i

    def sum(self, i):
        s = 0
        while i > 0:
            s += self.bit[i]
            i -= i & -i
        return s

n = int(input())
pts = []
ys = []

for i in range(n):
    x, y, s = map(int, input().split())
    pts.append((x, y, s, i))
    ys.append(y)

ys_sorted = sorted(set(ys))
comp = {v: i + 1 for i, v in enumerate(ys_sorted)}

pts.sort(key=lambda p: p[0])

bit = Fenwick(len(ys_sorted))
ans = [0] * n

for x, y, s, idx in pts:
    cy = comp[y]
    ans[idx] = bit.sum(cy)
    bit.add(cy, s)

print("\n".join(map(str, ans)))
```フェンウィック ツリーは、圧縮されたネットワーク上で効率的なプレフィックス集約を可能にするコア構造です。$y$-軸。 の`add`関数は対数時間で点の更新を実行しますが、`sum`プレフィックスの合計を取得します。 座標圧縮により、座標に比例してメモリが割り当てられることがなくなります。$2 \cdot 10^9$。 

並べ替え順$x$ポイントを処理するときに、それ以下のすべての有効な貢献者が確実に処理されるようにします。$x$すでに構造の中にあります。 元のインデックスによって結果を保存すると、出力の順序が維持されます。 

よくある落とし穴は、クエリと更新の順序を入れ替えることです。 正しい動作は、最初にクエリを実行し、次に現在のポイントを挿入することです。これは、問題定義で明示的に意図されていない限り、ポイントは独自のプレフィックス合計に寄与すべきではないためです。これは、ここでは、処理されたプレフィックスに厳密に含めることに正確に対応します。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべてのポイントが同じものを共有する場合です。$x$-座標。 この状況で並べ替えると、$x$すべてをグループ化すると、答えは純粋に次のものに依存します。$y$-プレフィックスの蓄積。 アルゴリズムは依然として機能します。$x$、更新はクエリの後に行われるため、同じバッチ内の別のバッチにポイントは寄与しません。 例えばポイントの場合$(1,3,10), (1,1,5), (1,2,7)$、処理によりすべてのクエリがゼロとして返されます。これは、厳密に小さい点はないため、定義と一致します。$x$。 

もう 1 つのエッジ ケースは、次のように座標を厳密に減少させることです。$(3,3), (2,2), (1,1)$。 ソート後、スイープは増加し、各ポイントは以前の小さなペアのみを参照します。 フェンウィック ツリーは、入力順序が逆であっても、支配関係が正しく評価されることを保証します。 

最後の微妙なケースは、値が大きくてまばらな場合です。 圧縮がなければ、フェンウィック ツリーを割り当てることは不可能です。 圧縮では順序が維持されるため、次のような値でも$y = 10^9$一度マッピングされると、小さなインデックスと同じように動作します。
