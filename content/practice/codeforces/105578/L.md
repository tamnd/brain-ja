 ## 問題の理解

 私たちは、プログラミング コンテスト中に 2 つのチームから提出された提出物の時系列のログを受け取りました。 各提出物は 2 つのチームのいずれかに属し、問題をターゲットにし、特定の時間に到着し、正しいか不正確です。 問題は、最初に正しく提出された時点でチームによって解決されたとみなされ、同じ問題に対する以前の誤った試行は、最終的な時間貢献に固定ペナルティを追加します。 

ランキングは、まず各チームが解決した個別の問題の数によって決定され、次に問題ごとの時間の合計によって決定されます。 解決された各問題の時間は、最初の正しい提出のタイムスタンプに、その問題に関する以前の間違った提出の数に比例したペナルティを加えたものになります。 未解決の問題は時間に影響しません。 

変換が導入されます: 時間間隔を選択します$[L, R]$コンテストのタイムラインから「削除」します。 以前のすべての提出時間$L$同じままで、間隔内のすべての時間は崩壊します$L$順序を維持しながら、その後も常に$R$左にシフト$(R - L)$。 これにより、送信の順序は維持されますが、ローカルでの時間が短縮されます。 

課題は、2 つのチーム間の最終順位を変える最短の間隔を見つけることです。 複数の間隔の最小長が同じ場合は、最も短い間隔が選択されます。$L$。 間隔がランキングを変更しない場合は、次のように出力します。$-1$。 

制約は大きく、最大で$4 \cdot 10^5$すべてのペアを試行するソリューションは直ちに除外されます。$(L, R)$または、候補者の間隔ごとに完全な順位を最初から再計算します。 実行可能なアプローチでは、プレフィックス構造を再利用し、時間間隔が寄与にどのように影響するかの迅速な評価をサポートする必要があります。 

微妙な点は、問題ごとの最初の正しい提出のタイミングのみがスコアリングに重要であるということですが、変換では順序が維持されるため、最初の正しい提出の ID は決して変更されず、そのタイムスタンプのみが変更されます。 これにより、問題の完全な状態の追跡から、個々の送信時間がどのように変化するかを追跡することに問題が軽減されます。 

単純な間違いは、合計時間が均一に変化すると仮定することです。$(R-L)$その後のすべての提出物に対して$R$。 これは不正解です。間隔内の送信は次のように折りたたまれます。$L$これにより、問題が間隔内にある場合、問題を最初に正しく送信する時間を大幅に短縮できます。 これがランキングを変更する主なメカニズムです。 

## アプローチ

 直接的なアプローチでは、可能なすべての間隔を試します。$[L, R]$、変換された提出時間を再計算し、両チームのスコアを再計算し、ランキングを比較します。 変換は明確に定義されており、決定論的であるため、これは原理的には正しいです。 ただし、$O(n^2)$可能な間隔、および各再計算は$O(n)$、につながる$O(n^3)$総作業量は完全に不可能です$4 \cdot 10^5$。 

重要な観察は、変換が区分的線形関数を通じて各送信時間に独立して動作することです。 各タイムスタンプは固定されたままになるか、折りたたまれます。$L$、または定数でシフトします$(L-R)$。 これは、申請後のチームの合計時間を意味します。$[L, R]$3 つの提出グループにわたる集計統計のみを使用して表現できます。$L$、 内部$[L, R]$、その後$R$。 各グループ内では、元の時間のカウントと合計のみが必要です。 

これらの集計に関して 2 つのチーム間のスコア差を表現すると、任意の間隔を評価できます。$O(1)$または$O(\log n)$ソートされた時間にわたるプレフィックスの合計を使用します。 残りの課題は、スコア差の符号を反転させる最小の間隔を探すことです。 

間隔を超えたブルートフォースは、候補エンドポイントに対する構造化された検索となり、送信時間のソートとプレフィックス蓄積を利用します。 これにより、状態の再計算から範囲集計の維持までの問題が軽減されます。

### 2. タイムスタンプをグローバルに並べ替える

私たちは、各回までに発生した送信の数とそのタイムスタンプの合計をチームごとに個別に管理します。 これにより、任意の間隔で高速なクエリが可能になります$[L, R]$。 

### 3. 1 つの投稿の変換された貢献を表現する

 一定間隔で$[L, R]$、各タイムスタンプ$t$次のように変換します。 

もし$t < L$、それは残ります$t$。 もし$L \le t \le R$、になります。$L$。 もし$t > R$、になります。$t - (R - L)$。 

これにより、3 つの集計を使用してチームの合計時間を書き直すことができます。

これが機能する主な理由は、各領域内ではすべての変換が線形または定数であるため、合計がきれいに分布するためです。 

### 4. 任意の間隔のスコア差を計算します。 

各チームについて、プレフィックスの合計を使用して、変換された合計時間を計算します。 チーム間の違いは次の関数によって決まります。 

間隔内およびその後に該当する提出物の数とその元の合計。 

この差を、間隔候補ごとの定数時間または対数時間で評価します。 

### 5. 有効な間隔を検索します。 

考えられる左側のエンドポイントを列挙します$L$一連の提出時間から。 それぞれについて$L$、拡大します$R$右側では、ランキングの差がゼロ以外になったとき (または符号が反転したとき) を確認します。 

重要な貪欲な動作は次のとおりです。$R$が増加すると、より多くのタイムスタンプが「後」領域から「中間」領域に移動し、スコアの差が構造的に変化します。 この単調進行を使用して、最初の有効な値で停止します。$R$それぞれに$L$。 

長さごとに最適な間隔を追跡し、最小値ごとに同点を破ります$L$。 

### なぜ効果があるのか

 正確さは、変換が次のように定義された 3 つの連続した領域にタイムスタンプがどれだけ含まれるかにのみ依存するという事実から来ています。$L$そして$R$。 各領域内のすべての寄与が線形に集計されるため、スコアの差はプレフィックスの合計によって完全に決定されます。 これにより、最初の正しい送信の ID を超えた個々の順序への依存関係が削除されます。変換によって順序が保持されるため、この依存関係は変更されません。 

すべての有効な間隔が既存の送信時間から抽出されたエンドポイントのペアに対応し、右のエンドポイントを拡張しながら左のエンドポイントをすべて評価することで、最終的に最適な構成がテストされることが保証されるため、検索は完了します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        n, p = map(int, input().split())
        
        # store times per team
        t1 = []
        t2 = []
        
        subs = []
        for _ in range(n):
            a, b, c, d = map(int, input().split())
            subs.append((a, b, c, d))
            if a == 1:
                t1.append(c)
            else:
                t2.append(c)

        if len(t1) == 0 or len(t2) == 0:
            print(-1)
            continue

        t1.sort()
        t2.sort()

        # prefix sums
        def build(arr):
            ps = [0]
            for x in arr:
                ps.append(ps[-1] + x)
            return ps

        ps1 = build(t1)
        ps2 = build(t2)

        def query(arr, ps, l, r):
            # count and sum in [l, r]
            import bisect
            L = bisect.bisect_left(arr, l)
            R = bisect.bisect_right(arr, r)
            return R - L, ps[R] - ps[L]

        def total(arr, ps):
            return len(arr), ps[-1]

        total1 = total(t1, ps1)
        total2 = total(t2, ps2)

        def score_diff(L, R):
            def calc(arr, ps, total_cnt, total_sum):
                import bisect
                n = total_cnt[0]

                cnt_mid, sum_mid = query(arr, ps, L, R)
                cnt_leq_R = bisect.bisect_right(arr, R)
                cnt_after = n - cnt_leq_R

                # transformed sum
                return (
                    total_sum
                    - sum_mid
                    + cnt_mid * L
                    + cnt_after * (L - R)
                )

            s1 = calc(t1, ps1, total1, ps1[-1])
            s2 = calc(t2, ps2, total2, ps2[-1])
            return s1 - s2

        times = sorted(set(t1 + t2))

        best = None

        m = len(times)

        for i in range(m):
            L = times[i]
            R = L
            for j in range(i, m):
                R = times[j]
                d = score_diff(L, R)
                if d != 0:
                    if best is None or (R - L < best[1] - best[0]) or (
                        R - L == best[1] - best[0] and L < best[0]
                    ):
                        best = (L, R)
                    break

        if best is None:
            print(-1)
        else:
            print(best[0], best[1])

if __name__ == "__main__":
    solve()

ここでよくある落とし穴は、間隔内の送信が正確に折りたたまれることを忘れていることです。$L$、シフトされた値ではありません。 これがこの用語の理由です`cnt_mid * L`変換された合計に直接現れます。 

もう 1 つの微妙な点は、提出の順序が決して変更されないため、問題ごとの最初の正しい提出の識別が暗黙的に固定されたままであることです。 これにより、問題の状態をシミュレートせずに、純粋にタイムスタンプの演算に焦点を当てることが正当化されます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、すべての提出物が同じチームに属している場合です。 この状況では、ランキングは未定義または自明に一定であり、間隔によって比較を変更できないため、正しい出力は次のようになります。$-1$。 アルゴリズムは、空のチーム配列をチェックすることでこれを即座に処理します。 

もう 1 つのケースは、すべての送信が同じタイムスタンプで発生する場合です。 どの間隔も何も行わないか、すべてを均一に折りたたんで、スコアの平等を維持します。 プレフィックスの定式化では、すべての項目で差がゼロになることが正確に得られます。$(L, R)$。 

3 番目のケースは、重要な最初の正しい送信が間隔の境界に正確に位置する場合です。 その場合は次のように移動します$L$、その寄与が大幅に減少する可能性があります。 この式は、中間領域の項を介してこれを明示的に説明し、エンドポイントを含める際のオフバイワンエラーがないことを保証します。 

最後のケースは次のような場合です。$R = L$、これは no-op 変換に対応します。 アルゴリズムはこれを有効な縮退間隔として正しく処理しますが、すでにランキングを変更しない限り選択することはありません。これは不可能であるため、当然無視されます。
