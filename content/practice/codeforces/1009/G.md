 ## 解決策
 ## 問題の理解

 最初の 6 文字の小文字のみからなる文字列が与えられます。 任意の位置を何度でも交換することで文字を任意に再配置することができるため、事実上、完全な置換の自由を備えた文字のマルチセットとして扱うことができます。 

これに加えて、一部の位置には制約があります。特定のインデックスは、許可される文字のサブセットに制限されます。 すべての制約付きポジションは最大 1 人の投資家に属しますが、制約のないポジションでは任意の文字が許可されます。 

タスクは、制約セットに従ってすべての位置が有効な文字を受け取るように、文字のマルチセットを再配置することです。また、すべての有効な割り当ての中で、辞書編集的に最小の結果の文字列が必要です。 割り当てが不可能な場合は、失敗を報告する必要があります。 

構造上の重要な点は、文字列の長さは最大 100,000 まで可能ですが、アルファベットのサイズはわずか 6 であることです。これは、位置に指数関数的に依存するいかなる解法も不可能であり、位置の数が 2 次であっても合格しないことをすぐに示唆しています。 解決策は、問題をフローや文字数と位置要件の間のマッチングのようなものに落とし込む必要があります。そこでは、実現可能性と最適性を貪欲にチェックするか、小さな容量構造の最大フローを介してチェックできます。 

単純な間違いは、これを位置ごとに独立したものとして扱い、最小の有効な文字を貪欲に選択することです。 たとえば、常に各位置に許容される最小の文字を割り当てると、小さな文字を簡単に消費しすぎて、後で制約された位置がブロックされてしまう可能性があります。 

もう 1 つの失敗モードは、グローバル文字数を完全に無視することです。 各位置に個別に有効な選択肢がある場合でも、制約された位置全体で必要な文字の出現の合計数が、文字列が提供する数を超える可能性があります。 たとえば、文字 'a' を必要とする位置が 10 個あり、そのすべてに文字 'a' が必要であるが、文字列に 5 つの 'a' しか含まれていない場合、ローカル妥当性チェックは合格しますが、グローバル割り当ては不可能です。 

最後に、微妙な問題は、制約のないポジションは貪欲な意味で真に自由ではないということです。 これらは残った文字を吸収するバッファとして機能し、その役割は実現可能性のバランスを取る上で不可欠です。 

## アプローチ

 ブルート フォース解釈では、制約を尊重しながら位置に文字を割り当て、元の文字列とのマルチセットの同等性を検証することで実現可能性をチェックします。 バックトラックしようとしても、各ポジションで最大 6 つの選択肢があり、100,000 ポジションともなると、これは天文学的な大きさになります。 

正しい視点は、2 つの構造層を分離することです。 まず、どの文字がどの制約された位置に配置されるかを決定します。 第 2 に、制約のない位置では残りの文字が自動的に取得されます。 スワップでは任意の順列が許可されるため、互換性の制約の下で複数の文字セットを位置に割り当てるという問題が発生します。 

これは当然ながら、位置と容量を持つ文字の間の 2 部構成のマッチング問題です。 各文字には、元の文字列内のその頻度に等しい固定供給があります。 各位置には、許可されているサブセットからのみ、正確に 1 つの文字が必要です。 ただし、辞書編集的な最小性も必要なので、実現可能性だけを解決することはできません。 私たちは秩序を強制しなければなりません。 

重要な洞察は、文字を辞書編集順に処理し、より小さい文字をできるだけ早く配置するように努めることですが、そうする場合に限り、残りの位置の実現可能性が損なわれないようにします。 この実現可能性チェックはフロー モデルによって処理されます。つまり、文字の割り当てを段階的にシミュレートし、残りのシステムがまだ満足できるかどうかをテストします。

アルファベットのサイズは定数 (6) であるため、カウントに等しい容量でソースが文字ノードに接続し、許可されていれば文字ノードが位置に接続し、位置がシンクに接続するフロー ネットワークを構築できます。 次に、最大流量がポジションの数と等しいかどうかを確認します。 辞書編集上最小の文字列を構築するには、位置を左から右に繰り返し、各位置で「a」から上に向かって文字を試し、一時的に容量を減らし、完全な補完が可能かどうかを確認します。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォースバックトラッキング | O(6^n) | O(n) | 遅すぎる |
 | 欲張った施工の流れ | O(6^2 * n * maxflow_check) ~ O(6 * n * F) | O(n + 6) | 承認済み |

 ここで、各実現可能性チェックは 6 文字のノードを持つ小さな 2 部構造で動作するため、F は非常に小さな定数係数によって効果的に制限されます。 

## アルゴリズムのチュートリアル

 固定マルチセットから制約のある位置に文字を分配するという問題をモデル化します。 

1. 元の文字列内の各文字の出現回数を数えます。 これにより、サイズ 6 の供給配列が得られます。これは、再配布が許可されている唯一のリソースです。 
2. 位置ごとに、許可された文字のセットを作成します。 位置に制約がない場合、許可されるセットはすべて 6 文字です。 これは互換性グラフを定義します。 
3. 左から右に答えを作成します。 位置 i では、可能な限り小さい文字を割り当てようとします。 
4. 「a」から「f」までの各候補文字 c について、使用可能な数を一時的に 1 つ減らし、残りの接尾辞をまだ埋めることができるかどうかを確認します。 
5. 実現可能性チェックは、小さな最大フロー インスタンスを使用して、残りの文字と残りの位置の間に 2 部一致が存在するかどうかを検証することによって行われます。 グラフには、残りのカウントに等しい容量を持つ文字ノードと、許可されている位置へのエッジがあります。 
6. 流れが残りのすべての位置で飽和した場合、この文字を位置 i に固定して続行します。 それ以外の場合は、カウントを復元し、次の文字を試します。 
7. 位置にどの文字も機能しない場合、構成は不可能です。 

この貪欲な選択が辞書編集的に最小の結果を生み出す理由は、各位置で、グローバルな実現可能性を損なわない最小の文字を取り消し不能に選択するためです。 このステップで拒否された小さな文字は、有効な補完に含めることができません。これは、その文字を使用するとサフィックスの補完がブロックされることが実現可能性チェックですでに確認されているためです。 

### なぜ効果があるのか

 このアルゴリズムは、最初の i 位置を固定した後、残りのマルチセットを使用して少なくとも 1 つの有効な補完が存在するという不変条件を維持します。 各ステップでは、その接頭辞と一致する完全な補完が存在する場合にのみ文字が選択されます。 文字は常に昇順で試行されるため、最初の実行可能な選択は、その位置の辞書編集上可能な最小の選択でもあります。 これにより、実行可能なプレフィックス拡張に関する標準の貪欲交換引数を通じてグローバルな最適性が保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

from collections import deque

class Dinic:
    def __init__(self, n):
        self.n = n
        self.adj = [[] for _ in range(n)]

    def add_edge(self, u, v, c):
        self.adj[u].append([v, c, len(self.adj[v])])
        self.adj[v].append([u, 0, len(self.adj[u]) - 1])

    def bfs(self, s, t, level):
        q = deque([s])
        level[:] = [-1] * self.n
        level[s] = 0
        while q:
            u = q.popleft()
            for v, c, rev in self.adj[u]:
                if c > 0 and level[v] < 0:
                    level[v] = level[u] + 1
                    q.append(v)
        return level[t] >= 0

    def dfs(self, u, t, f, level, it):
        if u == t:
            return f
        for i in range(it[u], len(self.adj[u])):
            it[u] = i
            v, c, rev = self.adj[u][i]
            if c > 0 and level[v] == level[u] + 1:
                pushed = self.dfs(v, t, min(f, c), level, it)
                if pushed:
                    self.adj[u][i][1] -= pushed
                    self.adj[v][rev][1] += pushed
                    return pushed
        return 0

    def maxflow(self, s, t):
        flow = 0
        level = [0] * self.n
        INF = 10**9
        while self.bfs(s, t, level):
            it = [0] * self.n
            while True:
                pushed = self.dfs(s, t, INF, level, it)
                if not pushed:
                    break
                flow += pushed
        return flow

def can_finish(pos_allowed, rem_cnt):
    n = len(pos_allowed)
    S = 6
    N = S + n + 2
    SRC = S + n
    SNK = S + n + 1

    dinic = Dinic(N)

    for i in range(6):
        if rem_cnt[i]:
            dinic.add_edge(SRC, i, rem_cnt[i])

    for i in range(n):
        node = S + i
        for c in pos_allowed[i]:
            dinic.add_edge(c, node, 1)
        dinic.add_edge(node, SNK, 1)

    flow = dinic.maxflow(SRC, SNK)
    return flow == n

def solve():
    s = input().strip()
    n = len(s)

    cnt = [0] * 6
    for ch in s:
        cnt[ord(ch) - 97] += 1

    allowed = []
    for i in range(n):
        allowed.append(set(range(6)))

    m = int(input())
    for _ in range(m):
        pos, letters = input().split()
        pos -= 1
        allowed[pos] = set(ord(c) - 97 for c in letters)

    answer = []
    rem = cnt[:]

    for i in range(n):
        for c in range(6):
            if rem[c] == 0:
                continue
            if c not in allowed[i]:
                continue

            rem[c] -= 1
            if can_finish(allowed[i+1:], rem):
                answer.append(chr(c + 97))
                break
            rem[c] += 1
        else:
            print("Impossible")
            return

    print("".join(answer))

if __name__ == "__main__":
    solve()
```この実装では、残りの文字の頻度配列が保持され、一度に 1 つの位置で答えが構築されます。 実現可能性チェックでは、文字ノードが容量を供給し、位置ノードが正確に 1 つのユニットを要求するフロー ネットワークを構築します。 チェックは各位置の候補文字ごとに繰り返され、小さな最大フロー計算を繰り返すことを犠牲にして正確性が保証されます。 

実装の微妙な詳細は、実行可能性チェックごとにフロー グラフを段階的に更新するのではなく、再構築することです。 これにより、複雑なロールバック ロジックが回避され、正確さが単純に保たれます。これは、生の定数要素ではなく推論に対する厳しい制約を考慮すると重要です。

 ## 特殊なケース

 重要なエッジケースは、制約によってレアな文字が早期に強制され、後で実現可能性が妨げられる可能性がある場合です。 たとえば、文字列に 1 つだけが含まれている場合、`f`、ただし、制約のあるアーリーポジションでは、`f`、アルゴリズムは、それ以降のポジションが必要ないことを保証する必要があります。`f`満足できない形で。 容量が不十分になると最大流量が失敗するため、実現可能性チェックでこれが検出されます。 

もう 1 つの特殊なケースは、制約のない位置が優勢な場合に発生します。 アルゴリズムは依然として、残った文字の柔軟なシンクとしてそれらを扱う必要があります。 のような文字列の場合`abcdef`制約がなければ、あらゆる文字の順序付けに対してすべてのステップが実行可能であり、貪欲なプロセスは単純にソートされた順序を再構築します。`abcdef`。
