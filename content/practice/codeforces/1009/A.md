 ## 解決策
 ## 問題の理解

 ショップには、それぞれ固定価格のゲームが並べられており、マキシムはそれらを左から右に厳密に見ていきます。 同時に、彼は紙幣の行列のように動作する財布を持ち歩いています。つまり、前札だけが考慮され、現在のゲームの支払いに十分であるかどうかに応じて、消費されるかそのままの状態に留まります。 

ゲームの各ポジションで、マキシムは 1 回だけ試行します。財布の最初の紙幣を確認します。 ウォレットが空の場合、そのゲームはまったく操作できず、そのまま先に進みます。 最初の請求書に少なくともゲーム価格以上の価値がある場合、彼はゲームを購入し、その請求書は財布から消えます。 それ以外の場合は、購入に失敗して同じ請求書を保持し、次のゲームに進みます。 重要な点は、試行が失敗してもウォレット ポインタは進められず、購入が成功した場合のみ進められるということです。 

このタスクは、すべてのゲームを順番に処理した後、正常に購入されたゲームの数を判断することです。 

制約は小さく、ゲーム数と請求額の両方が最大 1000 です。これにより、タイムアウトのリスクなしで二次関数の最悪のケースでの簡単なシミュレーションがすぐに可能になります。 約 10^6 の演算までのソリューションは、快適に安全です。 

主な微妙な点は、購入が失敗した場合に同じ請求書が継続することを正しくモデル化することにあります。 よくある間違いは、成功に関係なく常にウォレット ポインタを進めることです。これにより、プロセスが完全に変更され、購入数が過少にカウントされます。 

2 番目のエッジケースは、ゲームが終了する前にウォレットが空になるときに発生します。 この状況では、それ以上の比較はできないため、残りのすべてのゲームをスキップする必要があります。 たとえば、すべての請求書が早期に消費された場合、答えは単にそれまでの購入数となり、それ以上のやり取りはありません。 

## アプローチ

 このプロセスについて考える素朴な方法は、説明されているように各ステップを文字通りシミュレートすることです。 ゲームのインデックスと、最初の未使用の請求書へのポインタを維持します。 ゲームごとに、現在の請求額を確認します。 十分な場合は、それを消費し、請求書ポインタを進めます。 そうでない場合は、請求書ポインタを固定したままにして、次のゲームに進みます。 

各請求書は 1 回だけ消費でき、各ゲームは 1 回処理されるため、このシミュレーションはすでに十分に効率的です。 つまり、実際に状態を変更するポインタの移動は最大で n + m 回、ウォレットの状態を変更しないチェックは最大 n 回失敗することを意味します。 最悪のケースでもゲーム数は直線的です。 

より概念的な見方は、プロセスが 2 点の移動であるということです。 1 つのポインターがゲーム内を厳密に前方に移動します。 2 番目のポインタは、購入が成功した場合にのみウォレット内を移動します。 重要な洞察は、過去のゲームや法案を後戻りしたり見直したりする必要はまったくないということです。 それぞれの決定はローカルなものであり、取り消すことはできません。 

これにより、ネストされたループや検索が不要になります。 シミュレーションはプロセスの構造を直接反映します。

 ## アルゴリズムのチュートリアル

 私たちは 2 つのインデックスを維持しています。1 つはゲーム用、もう 1 つはウォレット内の現在の請求用です。 また、購入を成功させるためのカウンターも維持しています。 

1. ポインタを初期化する`j = 0`最初の会計とカウンターの場合`ans = 0`。 ポインタは、ウォレット内の現在アクティブな紙幣を表します。 
2. 各ゲームを反復処理する`i`左から右へ。 各ステップで、購入の試みが可能かどうかを検討します。 
3. ウォレットが空の場合 (`j == m`)、ウォレットのチェックを完全に停止し、残りのゲームをスキップし続けます。 すべての請求書が消費されると、それ以上の購入は不可能になるため、これは機能します。 
4. それ以外の場合は、現在の請求額を比較します`a[j]`現在のゲームコストで`c[i]`。 
5. もし`a[j] >= c[i]`、ゲームが購入されたので答えをインクリメントし、設定によってウォレットポインタを前に移動します。`j += 1`。 これは請求書の消費をモデル化します。 
6. もし`a[j] < c[i]`、ウォレットポインタには何もしません。 同じ請求書は次のゲームでも利用できるため、次のゲーム インデックスに進むだけです。 
7. すべてのゲームが処理されるまで続行します。 

重要な設計上の選択は、ウォレット ポインタが成功した場合にのみ移動することです。これは、失敗しても請求書は消費されないというルールと正確に一致します。 

### なぜ効果があるのか

 いつでも、アルゴリズムは次の事実を保持します。`a[j]`最初の未消費の請求書です。 すべてのゲームは、この請求書を消費するか、変更しないままにしておきます。 どの操作も以前の請求書をスキップしたり変更したりすることはないため、ポインタは`j`次に利用可能なリソースを常に正確に追跡します。 購入が成功するたびにウォレットのサイズが厳密に削減され、各ゲームは 1 回だけ評価されるため、有効な購入機会がスキップされたり重複したりすることはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    c = list(map(int, input().split()))
    a = list(map(int, input().split()))
    
    j = 0
    ans = 0
    
    for i in range(n):
        if j == m:
            break
        if a[j] >= c[i]:
            ans += 1
            j += 1
    
    print(ans)

if __name__ == "__main__":
    solve()
```このソリューションは、ゲーム全体にわたる単一のパスを中心に構成されています。 ポインタ`j`請求書が消費された場合にのみ進み、プロセスで説明されている動作と正確に一致します。 早期退場時`j == m`ウォレットが空になると不要な比較を防ぎますが、それがなくてもソリューションは正しいままです。 

よくある実装上の間違いは、インクリメントすることです。`j`購入に失敗した場合でも。 それは不変条件を破ります`a[j]`は常に最初に利用可能な請求書であり、使用可能な請求書を人為的にスキップすることになります。

 ## 特殊なケース

 エッジケースの 1 つは、最初の請求額がどのゲームでも小さすぎる場合に発生します。 その状況では、ウォレットポインタは決して動かず、答えはゼロのままです。 例えば、`c = [5, 6, 7]`そして`a = [1]`単一の請求書は決して消費されないため、まったく進歩がありません。 

もう 1 つのエッジ ケースは、すべてのゲームが請求額に比べて非常に安い場合です。 その後、どちらかのリストが終了するまで、すべてのゲームでちょうど 1 つの請求書が消費されます。 のために`c = [1, 1, 1]`そして`a = [10, 10]`、2 番目の紙幣が消費され、答えが 2 になるまで、ゲームごとにポインタが進みます。
