 ## 解決策
 ## 問題の理解

 動作が隠しパラメータに依存するテキスト エディタを操作しています。$W$、線の幅。 記事は一連の単語長であり、エディターは貪欲に単語を行に配置します。次の単語がオーバーフローするまで現在の行を埋めます。$W$、新しい行が始まります。 単一の単語が超過した場合$W$、記事が表示できません。 私たちの目標は発見することです$W$最大 2 つのクエリを使用します。各クエリは単語長のシーケンスです。 すべてのクエリの記事の長さの合計は次を超えることはできません$2.5 \cdot 10^4$。 各クエリの後、記事が占める行数を観察するか、記事の幅が広すぎる場合はゼロを観察します。 

制約は、個々の幅を強引に調べることは不可能であることを示唆しています。$W$と同じ大きさにすることができます$10^5$、記事の長さの合計には制限があるため、選択する言葉には十分な注意が必要です。 単一の単語を 1 から 10^5 まで段階的にクエリするなどの不注意なアプローチは、長さの制限を超える可能性があります。 エッジケースが発生するのは次のような場合です$W$たとえば、最小限です$W=1$、1 より長い単語はすぐに失敗します。 同様に、$W$非常に大きいため、語長の合計が超過する可能性があります$2.5 \cdot 10^4$注意しないと、すべての単語の合計を 1 つのクエリとして簡単にテストすることはできません。 

## アプローチ

 単純なアプローチでは、エディターが失敗するまで連続した単語長を試し、最後に成功した単語長が次のことを示すことになります。$W$。 これが機能するのは、単語が長さよりも長い場合にのみエディターが失敗するためです。$W$。 ただし、これには潜在的に最大で$10^5$クエリまたは合計の長さが制限を超えています。 それは原理的には正しいですが、実際には不可能です。 

重要な洞察は、エディターの改行動作を利用することです。 選択した長さの複数の単語を含む記事を投稿した場合、行数から各行の単語の合計と、$W$。 記事の合計が都合の良い境界をちょうど超えるクエリを構築することで、次の結果を導き出すことができます。$W$返答より。 具体的には、単語の算術シーケンスを使用すると、予測可能な改行が保証されます。 たとえば、単語を送信する$[1, 2, \dots, n]$そして行数を受け取る$l$計算できるようになります$W$合計額の上限を で割ったものとして$l$。 2 番目のクエリは、必要に応じて、行のオーバーフローを引き起こすか、正確な最大フィッティング幅を確認するために、より大きな単語を選択することによって推定値を調整します。 これにより、全長の制約を超えることなく、ソリューションが 2 つのクエリに減ります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ブルートフォース | O(W) | お(1) | 遅すぎます、長さの制限を超えています |
 | 最適 | テスト ケースごとに O(1) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 最初の記事を作成します。$n$長さのある言葉$1, 2, \dots, n$、 どこ$n$全長が長くなるように選択されます。$\sum_{i=1}^n i \le 2.5 \cdot 10^4$。 これにより、全長制限を超えないようにすることができます。 長さを増分することにより、各行が予測どおりに埋められることが保証されます。 
2. この記事を最初のクエリとして送信します。 エディターは行数を返します$l$。 If the response is zero, it means the largest word in our query exceeded$W$、そしてすぐに推測できます$W$適合する最大の単語として、1 から始まるシーケンスがある場合は前の整数になります。 
3. 最初のクエリが成功した場合は、単語の合計を行数で割った値の上限としておおよその幅を計算します。$$W \approx \left\lceil \frac{\text{sum of words}}{l} \right\rceil$$これが機能するのは、エディターが各行を貪欲に埋めていくため、おそらく最後の行を除く各行がほぼいっぱいになっているためです。 

1. 洗練する$W$正確には、必要に応じて 2 番目のクエリを作成します。 Choose words that sum exactly to the hypothesized width plus or minus 1, so the editor’s response confirms whether$W$高いか低いかです。 これにより、次の正確な値を決定できます。$W$2 番目のクエリを使用します。 
2. 検出されたものを印刷します$W$最終的な答えとして。 

機能する理由: このアルゴリズムは 2 つの不変条件に依存しています。 まず、編集者の行数応答は、次に従って合計を予測どおりに分割します。$W$。 Second, by carefully choosing word lengths and observing the response, we can deduce inequalities that pin down the exact value of$W$。 長さの制約を考慮して、最大 2 つのクエリが必要です。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    t = int(input())
    for _ in range(t):
        # First query: arithmetic sequence starting from 1
        # Compute n such that sum 1..n <= 2.5e4
        n = 223  # 223*224/2 = 24976 <= 2.5e4
        words = list(range(1, n+1))
        print("?", n, *words)
        sys.stdout.flush()
        lines = int(input())
        if lines == 0:
            # Largest word exceeded W
            print("! 1")
            sys.stdout.flush()
            continue
        total = sum(words)
        W_estimate = (total + lines - 1) // lines
        # Second query to confirm exact W
        words2 = [W_estimate]*1  # single word of length W_estimate
        print("?", len(words2), *words2)
        sys.stdout.flush()
        lines2 = int(input())
        if lines2 == 0:
            W_estimate -= 1
        print("!", W_estimate)
        sys.stdout.flush()

if __name__ == "__main__":
    solve()
```最初のクエリは、合計が最大許容長をわずかに下回るシーケンスを構築し、全長の制約を超えないようにします。 の計算`W_estimate`部分的な行を考慮するために整数の上限を使用します。 2 番目のクエリは、推定された幅を正確に検証するための 1 つの単語であり、次のようなエッジ ケースを処理します。`W`最初の見積もりよりも小さいです。 対話型プロトコルに準拠するために、各クエリの後に出力がフラッシュされます。

 ここでは、最初の単語が 1 行になります。 もっと長い単語をクエリした場合、応答はゼロになり、W=1 と正しく推定されます。
