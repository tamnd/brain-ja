 ## 解決策
 # 問題の理解

 倉庫ログには、作業者が実行したアクションが記述されます。 ワーカーは元のログに複数回表示される場合がありますが、最終スケジュールでは、各ワーカーは 1 回だけ入力し、記録されたすべてのアクションを元の相対的な順序で内部的に実行する必要があります。 

目標は、すべての在庫アクションで元のログに表示される倉庫の状態が引き続き表示されるように、ワーカーの順序を変更することです。 セクターの場合、もともと在庫アクションが配送アクションの前に発生した場合、在庫担当者は配送担当者より前に留まる必要があります。 在庫アクションの前に配送が発生した場合、配送担当者は在庫担当者よりも先に待機する必要があります。 すべての有効なワーカー オーダーの中で、ワーカー ID の辞書順で最小の順列が必要です。 要件が互いに矛盾する場合、順序は存在しません。 

入力には最大 100,000 人のワーカーと最大 2 倍のログ エントリが含まれます。 ログ エントリのすべてのペアを比較するソリューションは、二次関数になる可能性があります。 200,000 のアクションがある場合、Python では 10 億の操作でも遅すぎるため、線形または線形に近いグラフの構築が必要です。 

問題は、多くのアクションを含むセクターが多くのペアごとの制約を暗示する可能性があることです。 たとえば、50,000 人の作業者がセクターを検査し、その後 50,000 人の作業者がそのセクターに配達する場合、単純なグラフには 25 億のエッジが含まれます。 実装では、これらの制約のグループをコンパクトに表現する必要があります。 

いくつかの特殊なケースは見落とされがちです。 同じ部門に複数回勤務する労働者が自己依存を生み出してはなりません。 例えば：```
2 2
1 A I
1 A D
```正しい出力は次のとおりです。```
1 2
```2 つのアクションは同じワーカーに属しており、ワーカーは必要な内部順序ですでにそれらを実行しています。 ワーカー 1 からワーカー 1 にエッジを追加する不注意な実装では、サイクルが誤って報告されてしまいます。 

もう 1 つの注意が必要なケースは、アクションの繰り返しによって間接的に生じる矛盾です。 考慮する：```
3 6
1 A I
2 B I
3 B I
2 B D
2 A D
3 B I
```正しい出力は次のとおりです。```
-1
```セクター B の在庫に続いて配送が行われるため、ワーカー 3 はワーカー 2 より前に存在する必要があります。 作業者 2 の配達後の作業者 3 による後の在庫は、逆の依存関係を作成するため、グラフにはサイクルが含まれます。 

# アプローチ

 直接的なアプローチは、すべてのエッジが配置された有向グラフを構築することです。`a -> b`労働者を意味します`a`労働者より先に入らなければなりません`b`。 同じセクター内のすべてのアクションのペアについて、そのタイプに順序付けが必要かどうかを確認し、対応するエッジを追加できます。 必要な関係はすべて明示的に表現されているため、これは正しいです。 

問題は辺の数です。 セクターには、多くの在庫アクションとその後に続く多くの配送アクションを含めることができます。 すべての在庫担当者はすべての配達担当者に先行する必要があり、完全な 2 部グラフを作成します。 ワーカーが 100,000 人いる場合、数十億のエッジが作成される可能性があり、保存したり処理したりすることはできません。 

重要な点は、これらの制約はプレフィックスに関するものであるということです。 1 つのセクターのログを左から右にスキャンすると、在庫アクションは以前のすべての配送アクションのみを考慮し、配送アクションは以前のすべての在庫アクションのみを考慮します。 以前のワーカーの大規模なセットを、そのセットを表す小さな補助グラフ ノードに置き換えることができます。 

各セクターごとに 2 つのチェーンを維持しています。 1 つのチェーンはこれまでに確認されたすべての在庫作業員を表し、もう 1 つのチェーンはこれまでに確認されたすべての配達員を表します。 新しいアクションが出現すると、反対側のチェーンに接続して必要な依存関係を強制し、その後のアクションもそのチェーンに依存するように独自のチェーンを拡張します。 

このコンパクトなグラフを構築した後、残りのタスクはトポロジカルな順序付けです。 実際のワーカーに対する最小ヒープを備えたカーンのアルゴリズムを使用して、辞書編集的に最小の答えを取得します。 補助ノードは内部で記録されているだけであり、応答には表示されないため、使用可能になるたびに処理されます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(㎡) | O(㎡) | 遅すぎる |
 | 最適 | O(n + m) | O(n + m) | 承認済み |

 # アルゴリズムのチュートリアル

 1. ワーカー ノードと補助ノードを含む有向グラフを作成します。 各エッジは、送信元ノードが宛先ノードの前に処理される必要があることを意味します。 
2. セクターごとに、2 つの初期補助ノードを作成します。 1 つは、そのセクターですでに確認されているすべての在庫アクションを表し、もう 1 つは、すでに確認されているすべての配送アクションを表します。 
3. 元のログを順番にスキャンします。 作業者による在庫アクションの場合`x`、現在の配信概要ノードからエッジを追加します。`x`なぜなら、それ以前のすべての配送はこの在庫よりも前に行われる必要があるからです。 次に、新しいインベントリ概要ノードを作成し、以前のインベントリ概要とノードの両方を接続します。`x`それに。 
4. 作業者による配送行為の場合`x`、現在の在庫概要ノードからエッジを追加します。`x`なぜなら、以前のすべての在庫はこの配送前に発生する必要があるからです。 次に、新しい配信サマリー ノードを作成し、以前の配信サマリー ノードと配信サマリー ノードの両方を接続します。`x`それに。 
5. カーンのアルゴリズムを実行します。 入次数が 0 のワーカーのヒープと、入次数が 0 の補助ノードのキューを保持します。 可能なすべての補助ノードを繰り返し削除し、使用可能な最小のワーカー ID を取得します。 
6. 以下の場合`n`ワーカーが出力され、グラフにはサイクルが含まれているため、出力します`-1`。 それ以外の場合は、作業者の指示を印刷します。 

なぜ効果があるのか:

 不変条件は、すべてのサマリー ノードが、1 つのセクターの現在のポイントより前に出現した 1 つのアクション タイプのワーカーのセットを正確に表すということです。 ワーカーがサマリー ノードに接続されている場合、今後の反対のアクションはすべて、そのワーカーを待機する必要があります。 サマリー ノードが前方に接続されると、以前のアクションはすべて保存されます。 したがって、圧縮されたグラフには、元のペアごとのグラフとまったく同じ順序付け要件が含まれます。 

カーンのアルゴリズムは、有効なトポロジー順序が存在する場合は常に、それを出力します。 補助ノードは最終的な置換には表示されないため、次のワーカーを選択する前に補助ノードを処理しても、ワーカー間の相対的な選択は変わりません。 最小ヒープは常に可能な限り最小の次のワーカーを選択し、辞書編集的に最小の有効な順序を与えます。 

# Python ソリューション```python
import sys
import heapq

input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())

    actions = [[] for _ in range(26)]
    for _ in range(m):
        x, c, d = input().split()
        actions[ord(c) - 65].append((int(x), d))

    graph = []
    indeg = []

    def new_node():
        graph.append([])
        indeg.append(0)
        return len(graph) - 1

    workers = [new_node() for _ in range(n)]

    def add_edge(a, b):
        graph[a].append(b)
        indeg[b] += 1

    for sector in range(26):
        inv_summary = new_node()
        del_summary = new_node()

        for x, typ in actions[sector]:
            w = workers[x - 1]

            if typ == 'I':
                add_edge(del_summary, w)

                nxt = new_node()
                add_edge(inv_summary, nxt)
                add_edge(w, nxt)
                inv_summary = nxt
            else:
                add_edge(inv_summary, w)

                nxt = new_node()
                add_edge(del_summary, nxt)
                add_edge(w, nxt)
                del_summary = nxt

    worker_ids = [i + 1 for i in range(n)]
    heap = []
    aux = []

    for i in range(len(graph)):
        if indeg[i] == 0:
            if i < n:
                heapq.heappush(heap, i)
            else:
                aux.append(i)

    ans = []
    while len(ans) < n:
        while aux:
            v = aux.pop()
            for u in graph[v]:
                indeg[u] -= 1
                if indeg[u] == 0:
                    if u < n:
                        heapq.heappush(heap, u)
                    else:
                        aux.append(u)

        if not heap:
            break

        v = heapq.heappop(heap)
        ans.append(v + 1)

        for u in graph[v]:
            indeg[u] -= 1
            if indeg[u] == 0:
                if u < n:
                    heapq.heappush(heap, u)
                else:
                    aux.append(u)

    if len(ans) != n:
        print(-1)
    else:
        print(*ans)

if __name__ == "__main__":
    solve()
```コードの最初の部分ではグラフを作成します。 ワーカー ノードが最初に作成されるため、ワーカー ID はワーカー ノードのノード インデックスに直接対応します。`0`に`n - 1`。 補助ノードは後で追加されます。 

の`add_edge`関数はエッジが作成される唯一の場所であるため、すべての依存関係によって宛先の次数が自動的に更新されます。 

セクター スキャンは、二次構成の圧縮バージョンです。 要約ノードは各アクションの後に更新されるため、後のアクションはすべてのペアを保存せずに、以前の反対のタイプに依存します。 

トポロジカル ソートには 2 つのコレクションがあります。 ヒープは利用可能なワーカーを格納し、辞書編集的に最小の選択肢を保証します。 補助リストには、使用可能な内部ノードが格納されます。 補助ノードを最初に処理することが必要なのは、次のワーカーを選択する前に考慮すべきワーカーを解放する可能性があるためです。

 # エッジケース

 同じ部門で在庫と配送の両方を実行する作業者の場合、アルゴリズムは自己依存関係を作成しません。 入力では:```
2 2
1 A I
1 A D
```在庫アクションは要約ノードを指し、配信アクションはその要約から読み取ります。 ワーカー 1 は引き続き利用可能なため、出力は次のようになります。```
1 2
```同じタイプのアクションの後に反対のタイプが続くセクターの場合、アルゴリズムはすべてのペアの関係を拡張しません。 たとえば、多くの労働者が部門を検査する場合、`A`そしてその後多くの人が`A`、インベントリ概要ノードにはグループ全体が保存されます。 各配信では、そのサマリー ノードから 1 つのエッジのみが追加されますが、必要な順序付けはすべて強制されます。 

矛盾するログの場合、圧縮されたグラフでもサイクルが維持されます。 2 番目のサンプルでは、​​在庫と配送の概要によって、明示的なグラフと同じ 2 つの反対の依存関係が作成されます。 カーンのアルゴリズムでは、最終的には利用可能なワーカーがなくなりますが、一部のワーカーは残り、不可能なスケジュールを正確に識別します。
