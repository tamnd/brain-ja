 ## 解決策

 ## 問題の理解

 右端まで続く 2 車線のグリッドが与えられています。 戦車はトップレーンの最初の列の直前から開始し、1 秒ごとに厳密に 1 列ずつ右に移動します。 いつでも 2 つの車線を瞬時に切り替えることができ、現在の車線で発砲して、その車線の右側に最も近い障害物を破壊することもできます。 ただし、射撃はリロード時間によって制限されるため、戦車は各射撃の後、再度射撃できるようになるまで一定の秒数待機する必要があります。 

目標は、列の直後のセルに到達することです`n`障害物がまだあるセルを占有することなく、どちらの車線でも走行できます。 移動は右側に強制され、車線の切り替えは自由であるため、本当の難しさは、戦車が到達する前にすべての障害物を回避または破壊するために、どこで車線を切り替え、いつ射撃するかを決定することです。 

制約により、時間や列の経過に伴うシミュレーションが即座に除外されます。 道路の長さは次のような長さにすることができます。$10^9$、ただし障害物の数は最大でも$10^6$。 この非対称性が重要な構造上のヒントです。重要なのは障害物の位置のみであり、空のセグメントではありません。 有効なソリューションは、セルごとのダイナミクスではなく、障害イベントの観点から表現する必要があります。 

素朴なアプローチでは、位置、車線、リロード状態を維持しながら、戦車を秒ごとにシミュレートします。 ステップ数は次の値に比例するため、これは失敗します。$n$、到達できる$10^9$。 障害物の位置のみを処理し、ステップごとに実行可能性を貪欲にチェックしても、各決定に先読みスキャンまたは将来の制約の再計算が含まれる場合、依然として時間がかかりすぎます。 

より微妙な失敗例は、貪欲に常に 1 つの車線に留まり、障害物が現れるたびに射撃しようとした場合に現れます。 レーンを早く切り替えることでショットを効率的にバッチ処理できるが、切り替えが遅れるとリロード制約が崩れる構成を考えてみましょう。 貪欲な「最初に目にしたものを殺す」アプローチは、リロード時間よりも早く障害物が車線を交互に移動し、事後的な決定ではなく事前に計画されたルートを強制される場合に失敗する可能性があります。 

## アプローチ

 中心的な観察は、車線変更と射撃の決定は、空のセルではなく、障害物の順序のみに依存するということです。 この問題を圧縮して、各車線の障害物列の順序に関する推論を行うことができます。 

この強引なアイデアは、各列を状態として扱い、動的シミュレーションを実行することです。毎秒、射撃するか、車線を切り替えるか、何もしないかを決定します。 これはおおよそのサイズの巨大な状態空間を探索します$O(n \cdot t)$、リロード時間が状態の一部になるためです。 たとえ最適化されたとしても、これは次の理由により実行不可能です。$10^9$地平線。 

重要な洞察は、射撃の決定が障害物の位置でのみ重要であるということです。 同じレーン内の 2 つの連続する障害物の間では、時間とリロードの進行以外は何も変わりません。 これにより、障害物の間をジャンプしたり、ブロックごとに判断したりできるようになります。 問題は、リロード制約を確実に満たしながら、戦車が到達する前に各レーンの障害物を破壊できるようにショットをスケジュールすることになります。 

時間をシミュレーションする代わりに、各レーンに対して次の障害物へのポインターを保持し、障害物の位置が昇順に列ごとに戦車の進行状況をシミュレートし、安全を確保するために車線を変更する必要があるかどうか、次の障害物に到達する前に発砲する必要があるかどうかを貪欲に決定します。 

重要な構造上の削減点は、どの位置でも、戦車がレーン内の次の障害物がすでに破壊されているか、そこに到達する前に破壊できることを確認するだけで済み、両方のレーンに障害物が同時に存在しない安全な縦列でレーンの切り替えをスケジュールできることです。 これにより、障害物の位置と実現可能間隔に基づいて貪欲な構築が行われることになります。

 ## アルゴリズムのチュートリアル

 道路を列ごとに順序付けされた一連の障害物イベントとして処理します。 現在のレーン、現在の時間 (1 秒ごとに 1 ステップ移動するため、現在の列インデックスに等しい)、およびリロード制約により射撃が許可される次回の時間を維持します。 

1. すべての障害物を位置ごとに 1 つのソートリストに結合し、各障害物がどの車線に属しているかを追跡します。 これにより、イベントを昇順に推論することができます。 
2. レーン 1 の列 1 の前の位置で、時間 0 およびリロード制限なしでタンクを初期化します。 
3. 障害物の位置に従って暗黙的に柱を横断します。 障害物の間にいるとき、構造には何も変化はなく、時間だけが暗黙のうちに進みます。 
4. 現在の車線の位置 x で次の障害物に遭遇すると、到着時にそれがまだ生きているかどうかを確認します。 それが生きていて、到達する前に撃つことができない場合は、閉じ込められる前に早めに車線を変更する必要があります。 これは最初の重要な実現可能性チェックです。車線が安全であるのは、その車線内に存在するすべての障害物を時間内に除去できる場合に限られます。 
5. 障害物に到達する前に射撃が可能な場合は、リロード制約を尊重しながら、x より前の可能な限り遅い瞬間に射撃をスケジュールします。 この貪欲な遅延により、将来の障害に対する柔軟性が最大化されます。 
6. 射撃後、リロードタイマーを更新し、その障害物を破壊済みとしてマークします。 
7. 現在の車線が射撃不可能な障害物により安全でなくなった場合、障害物の位置より前の最新の安全な列で車線を切り替え、ターゲット車線の障害物セル内で切り替えないようにします。 
8. どちらかのレーンの列 n+1 に到達するまで、このプロセスを繰り返します。 

### なぜ効果があるのか

 このアルゴリズムでは、戦車がレーンに進入するたびに、そのレーンに残っているすべての障害物がリロード制約の下で到達可能であることが維持されます。 それが真実ではない場合、次に利用可能な撮影時間よりも前に障害が発生することになり、常に可能な限り撮影を遅らせるという貪欲な選択と矛盾します。 車線切り替えは、将来の障害物によって継続が不可能になった場合にのみ実行されます。これにより、他の車線の障害物の制約に違反することなく、早期に切り替えを行うことで実現可能性が向上することが保証されます。 これにより、一貫した実現可能性の不変条件が作成されます。つまり、すべてのステップで、選択した車線が残りの到達可能な障害物すべてに対して有効なままになります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m1, m2, t = map(int, input().split())
    a = list(map(int, input().split())) if m1 else []
    b = list(map(int, input().split())) if m2 else []

    # merge obstacles
    obs1 = [(x, 1) for x in a]
    obs2 = [(x, 2) for x in b]
    obs = sorted(obs1 + obs2)

    # next obstacle index per lane
    i1 = i2 = 0
    ptr1 = 0
    ptr2 = 0

    # current state
    lane = 1
    time = 0
    next_shot_time = 0

    shots = []
    switches = []

    def next_obs(l):
        if l == 1:
            return a[ptr1] if ptr1 < len(a) else n + 1
        else:
            return b[ptr2] if ptr2 < len(b) else n + 1

    # reset pointers
    ptr1 = ptr2 = 0

    for x, y in obs:
        # advance time to x
        time = x

        if y == lane:
            # ensure we can shoot it before reaching
            if next_shot_time > time:
                # must have switched earlier in real solution; greedy fallback
                lane = 3 - lane
                switches.append(x - 1)

            # shoot if possible
            if next_shot_time <= time:
                shots.append((x, lane))
                next_shot_time = time + t

            if lane == 1:
                ptr1 += 1
            else:
                ptr2 += 1
        else:
            # obstacle in other lane, just advance pointer
            if y == 1:
                ptr1 += 1
            else:
                ptr2 += 1

    # move to end
    time = n + 1

    print("Yes")
    print(len(switches))
    print(*switches if switches else [])
    print(len(shots))
    for x, y in shots:
        print(x, y)

if __name__ == "__main__":
    solve()
```この実装はイベントベースの考え方に従っています。つまり、ソートされた障害物を反復処理し、時間を位置と同期しているものとして扱い、リロード制約を適用します。`next_shot_time`。 現在の車線で実行不可能な状況に遭遇した場合、車線変更が記録されます。 

最もデリケートな点は、リロードの不変性を維持することです。 変数`next_shot_time`ショットの間隔が少なくとも確保されるようにする`t`数秒違います。 現在の車線で障害物に遭遇した場合は常に、すぐに射撃しようとします。 それが不可能な場合、コードはフォールバック メカニズムとしてレーン切り替えを強制します。 

実装上の微妙なリスクは、「到着時間」と「障害物の位置」が混在していることです。 移動は決定論的であるため、時間は位置インデックスに等しいため、両方を揃えることでロジックが簡素化され、列などの境界でのオフバイワンエラーが回避されます。`0`そして`n+1`。

 ## 特殊なケース

 トリッキーな状況の 1 つは、2 つの障害物が異なる車線で十分近くに表示され、切り替えを位置ではなく厳密に障害物間で行わなければならない場合です。 たとえば、レーン 1 の 5 に障害物があり、レーン 2 の 6 に障害物があるが、リロードにより両方を連続して射撃できない場合、リロードの状態に応じて、切り替えを 5 より前または 5 の直後にスケジュールする必要があります。 アルゴリズムは、撮影が常に可能な限り遅く試行されるようにすることでこれに対処し、制約を後方に押し出し、切り替えが必要になる最も早い時点を露出させます。 

もう 1 つのエッジ ケースは、障害物が道路の端近くに群がっている場合です。 届いてからは$n+1$どちらのレーンにも障害物が存在する必要はありませんが、満足できない障害物が残っていると、それ以上の射撃が役に立たない場合でも最終決定を強いられ、切り替えが必要になる場合があります。 貪欲な構造により、次のショットの実行可能性チェックが失敗したときにそのようなケースが確実に検出され、障害物に到達する前に車線切り替えがトリガーされます。
