 ## 解決策

 ## 問題の理解

 時間の経過とともに熱が一定にならない調理プロセスをシミュレートしています。 ストーブはオンとオフを繰り返します。一定時間が経過すると自動的にオフになりますが、ジュリアは必要に応じて時々戻ってきて再びオンにします。 重要な問題は、鶏肉が継続的に調理されますが、その速度はコンロがオンかオフかによって異なります。 ストーブがオンの場合は進行が速くなり、オフの場合は進行が遅くなります。 

入力により 3 つの値が得られます。 1 つ目は、ストーブが作動した後に連続して点灯し続ける最長時間です。 2 つ目は、ジュリアがキッチンに戻り、コンロを再起動する可能性がある間隔です。 3 番目は、「コンロの使用時間」の単位で測定される合計有効調理要件です。 コンロが常にオンであれば、調理はちょうどその分で終了しますが、時間の一部はコンロを止めたまま過ごすため、実際の経過時間は長くなります。 

出力は、交互の調理速度を考慮した、鶏肉が完全に調理されるまでの合計リアルタイム時間です。 

制約は非常に大きく、最大 10^18 です。 これにより、分またはイベントの粒度でのシミュレーションが即座に除外されます。 各活性化サイクルのシミュレーションでさえ、病的な場合には潜在的に大きすぎる可能性があります。これは、答えが 10^18 のオーダーになる可能性があるためです。 解は対数時間または定数時間で機能する必要があります。 

単純な間違いは、ジュリアの訪問と自動シャットダウンの間の重複を慎重にモデル化せずに、コンロが常にオンであるか、単純な定期的な方法で常にリセットされていると想定することです。 もう 1 つの微妙な失敗例は、オフ期間中に調理が半分の速度で継続されることを無視して、すべての時間を均一として扱うことです。 

具体的なエッジ ケースは、ジュリアがシャットダウン時間と比較して非常に頻繁に復帰する場合に発生します。 たとえば、コンロが 10 分後にオフになるが、ジュリアが 1 分ごとに戻ってくる場合、コンロは事実上常にオンになっており、答えはまさに理想的な調理時間になります。 反対の極端な場合は、ジュリアがほとんど戻ってこないため、ストーブが冷えることが多く、進行が大幅に遅くなります。 正しい解決策は、脆弱なケースのロジックに分岐することなく、両方の状況をスムーズに処理する必要があります。 

## アプローチ

 ブルートフォース手法では、時間を分ごとにシミュレートします。 各ステップで、コンロがオンかオフか、ジュリアが再起動に到着するかどうか、その分間にどれだけ調理が進んでいるかを追跡します。 プロセスは完全に決定的であるため、これは概念的には簡単です。 ただし、調理要件は最大 10^18 有効単位になる可能性があるため、1 分ごとにシミュレーションしたとしても、最大 10^18 の反復が必要になる可能性がありますが、これは不可能です。 

重要な観察は、システムが区分的に線形であるということです。 いつでも、調理速度は 1 (コンロオン) または 1/2 (コンロオフ) のいずれかであり、状態はコンロの停止とジュリアの訪問などの個別のイベント時間にのみ変化します。 時間を段階的にシミュレートする代わりに、イベント間の各間隔でどれだけの調理が完了したかを計算し、それを直接蓄積することができます。 

さらに重要な簡素化は、明示的なイベント シミュレーションを完全に避けることです。 このプロセスは次のように扱うことができます。時間の経過とともに、コンロは長さ k の「オン セグメント」の間を循環しますが、間隔 d でジュリアが訪問すると、オフ状態が中断され、フルスピード調理が再開される可能性があります。 これにより、問題は、k と d の間の重なりのみに依存する平均実効レートの計算に変換されます。

最適なアプローチにより、長さ d のサイクルごとにどの程度の効果的な調理が生成されるかを計算し、その後スケーリングするという問題が軽減されます。 この関数は時間的に線形であり、構造的に周期的であるため、長さ d の各間隔でどれだけの調理が得られるかを推論し、最後の部分間隔を正確に処理することで、必要な合計時間を直接計算できます。 

これにより、定数時間の算術解が得られます。

 | --- | --- | --- | --- |
 | ブルートフォース | O(t) | お(1) | 遅すぎる |
 | 最適 | お(1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 状態をオフからオンに「修復」できるのは、d 分ごとのジュリアの訪問という観点からプロセスを解釈します。 次の訪問の間に、コンロは最長で k 分間点灯したままになり、その後自動的に停止します。 
2. コンロに完全に火が入った瞬間に調理を開始した場合、長さ d の 1 つの間隔でどれだけの効果的な調理が完了するかを計算します。 その間隔の最初の k 分間、調理は全速力で進行し、k 単位の進行に貢献します。 残りの d − k 分間は、ストーブがオフになっているため、半分の速度で進行し、(d − k)/2 が寄与します。 
3. k ≥ d の場合、次の訪問の間にストーブはオフになりません。 長さ d のすべての間隔は完全に高速調理であるため、各分が 1 単位の進行に寄与します。 この場合、合計時間はちょうど t になります。 
4. k < d の場合、長さ d の各完全な間隔でどれだけ進歩したかを計算します。これは k + (d − k)/2 です。 
5. 目標調理量 t に達するまでに必要な調理間隔を決定します。 これは、浮動小数点演算に注意しながら、t を間隔ごとの寄与で割ることによって行われます。 
6. 全インターバルを処理した後、完全オン状態から開始する最終セグメントをシミュレートすることで残りの部分的な進行を処理し、再度最大 k 分間レート 1 を適用し、その後 1/2 を適用します。 
7. 完全な間隔と、正確に t 単位の調理を完了するのに必要な最後の部分間隔を加えた合計経過時間を累積します。 

なぜそれが機能するかは、プロセスの周期特性に基づいています。 長さ d のすべての間隔は、再起動の瞬間に開始すると、同じように動作します。これは、ジュリアがストーブをオフにするたびにリセットするためです。 これにより、システムは、調理の進行における決定論的なゲインの同一ブロックの繰り返しに還元可能になります。 クッキングは各状態内で時間的に線形であるため、これらのブロックにわたる寄与を合計すると、正確な正確さが維持されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

k, d, t = map(int, input().split())

# If stove never turns off before Julia returns
if k >= d:
    print(float(t))
    sys.exit()

cycle_gain = k + (d - k) / 2.0
cycles = t // cycle_gain
rem = t - cycles * cycle_gain

time = cycles * d

# process remaining part
if rem > 0:
    if rem <= k:
        time += rem
    else:
        time += k
        rem -= k
        time += rem * 2

print(time)
```最初のブランチは、シャットダウンがジュリアの訪問頻度を妨げない体制を処理します。 この場合、速度が低下することはなく、答えは単純に t です。 

変数`cycle_gain`長さ d の完全な間隔ごとにどれだけ効果的な調理が完了するかをエンコードします。 各完全な間隔はフルスピードで k 単位に寄与し、残りはハーフスピードで寄与し、これを等価なフルスピードの時間単位に変換します。 

次に、このような完全な間隔が必要な数を計算し、経過したリアルタイム時間に変換します。 残った進行状況は、同じ区分的レート ロジックを使用して明示的に処理されます。 

最後の変換ステップは重要です。全サイクル後の残りの調理は、最初の k 分間は 1 単位あたり 1 単位を使用し、その後は単位あたり 2 分を使用して、リアルタイムに変換し直す必要があります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    k, d, t = map(int, input().split())

    if k >= d:
        return str(float(t))

    cycle_gain = k + (d - k) / 2.0
    cycles = t // cycle_gain
    rem = t - cycles * cycle_gain

    time = cycles * d

    if rem > 0:
        if rem <= k:
            time += rem
        else:
            time += k + (rem - k) * 2

    return str(time)

 ## 特殊なケース

 k ≥ d の場合、ジュリアの訪問の間にストーブが強制的にオフになることはありません。 たとえば、入力`10 3 7`結果は常にフルスピードでクックされるため、答えは正確に 7 になります。アルゴリズムは不等式チェックを通じてこれを即座に検出し、浮動小数点演算を回避します。 

k が d よりもはるかに小さい場合、ストーブはほとんどの時間を低速段階で費やします。 入力用`1 100 10`、各サイクルは 1 ユニットが速く、99 ユニットが遅く寄与し、実効レートが大幅に低下します。 サイクルベースの計算では、均一な速度を仮定するのではなく、両方の部分が正しく集約されます。 

t が 10^18 など、非常に大きい場合でも、アルゴリズムは定数算術演算のみを実行します。 結果は常に必要な許容誤差に対して十分な精度を持つ実数として表されるため、浮動小数点除算の使用はこのスケールでの正確さに影響しません。
