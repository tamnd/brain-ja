 ## 解決策

 ## 問題の理解

 大きなグリッド上の一連のセルが与えられます。 各セルは都市であり、グリッド上のエッジを共有する 2 つの都市の間には道路が存在します。 重要な幾何学的制約は、選択したセルのセットが 1 つの接続された領域を形成し、空のセルも 1 つの接続された領域を形成するということです。 これは、穴のな​​い単一の「固体」ポリオミノの内部で作業していることを意味します。 

この領域では、一連のイベントを処理します。 都市に新しい「ショップ」を追加するイベントもあれば、すでにオープンしている最も近いショップまでの都市の距離を求めるイベントもあります。 距離はグリッドのエッジに沿った最短経路の長さとして測定され、移動は指定された一連の都市内でのみ許可されます。 

主な難点は、グラフが最大 300,000 頂点と大きく、更新とクエリの両方がオンラインであることです。 クエリは、以前に追加されたすべてのショップを反映する必要があります。 

素朴な解釈では、BFS を使用してすべてのクエリ ノードからすべてのショップへの最短パスを再計算することになります。 これは、各 BFS のコストが O(n) であり、最大 300,000 のクエリに対して実行すると O(nq) のソリューションが得られ、制限をはるかに超えているため、すぐに失敗します。 

さらに微妙な問題は、フルグリッドでは距離がユークリッドまたはマンハッタンではないことです。 これらは形状によって制約された最短パスであるため、欠落しているセルを通るショートカットは不可能です。 単純な座標幾何学を仮定するアプローチでは、凹面領域では不正確な答えが生成されます。 

小さな故障例としては、U 字型の領域があります。 パスは欠落している内部を迂回する必要があるため、2 つの点の座標は近くても、グラフの距離は遠くなることがあります。 次のような座標距離を使用する解決策`abs(x1-x2)+abs(y1-y2)`距離を過小評価してしまうでしょう。 

したがって、課題は、ソースの挿入と距離クエリの繰り返しのみを伴う、大規模な疎な重み付けされていないグラフ上の動的マルチソース最短経路問題です。 

## アプローチ

 簡単な解決策は、すべてのクエリを独立して処理することです。 タイプ 2 のクエリごとに、その都市から開始して BFS を実行し、いずれかの店舗に到達したときに停止します。 重み付けされていないグラフの BFS は常に最短パスを見つけるため、これは正しいです。 ただし、k 個のショップがあり、各クエリが BFS をトリガーする場合、最悪の場合、各 BFS はほぼグラフ全体を探索します。 これにより、およそ O(nq) になりますが、これは大きすぎます。 

重要な点は、複数のソースからの BFS をマージできることです。 すべての店舗が事前にわかっていれば、単一のマルチソース BFS を実行して、ノードごとに最も近い店舗までの距離を計算できます。 難しいのは、時間の経過とともにショップが挿入されるため、挿入の間に応答が必要になることです。 

これは、新しい情報源が出現するにつれて進化するグローバル最短経路プロセスを維持することを示唆しています。 最初から再計算する代わりに、すべてのエッジの重みが 1 であることを除いて、ダイクストラのアルゴリズムとまったく同じように優先キューを保持します。各ショップの挿入は、距離 0 の新しいソースをこのグローバル プロセスに挿入するのと同等です。 

重要な考え方は、計算を再開する必要がないということです。 私たちは、時を超えて世界的な緩和プロセスを維持します。 新しいお店が登場すると、優先キューに入れます。 クエリを処理するときは、伝播を十分に継続することによって、クエリされたノードの距離が完全に確定していることを確認します。 

これにより、問題は、ソースが追加されるだけで削除されない動的マルチソース BFS/ダイクストラ プロセスの維持に変わります。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | クエリごとに BFS を再実行する | O(nq) | O(n) | 遅すぎる |
 | グローバル インクリメンタル ダイクストラ (マルチソース) | O((n + q) log n) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 グリッドを、各セルがノードであり、領域に属する隣接するセル間にエッジが存在する重み付けされていないグラフとして解釈します。 

その後、グローバルな最短パス構造を維持します。 

1. 指定されたすべてのセルの隣接リストを作成します。 各セルについて、その 4 つの隣接セルを確認し、隣接セルも有効なセルである場合はエッジを接続します。 これにより、O(n) 個のエッジを持つ暗黙的なグラフが得られます。 
2. 距離配列を維持する`dist`、無限大に初期化されたブール配列`done`ノードまでの最短距離が確定したかどうかを示します。 
3. ペアを格納するグローバル最小ヒープ優先キューを維持する`(distance, node)`。 
4.ノードにショップを追加した場合`v`、設定しました`dist[v] = 0`そして押します`(0, v)`山の中へ。 すぐに伝播するわけではありません。 
5. クエリは順番に処理されます。 ノードのクエリに答える前に`u`、ノードまでダイクストラプロセスを順方向に実行します。`u`確定します:

 1. 最小の要素を繰り返しポップします`(d, v)`山から。 
2. もし`v`すでに完成しているのでスキップしてください。 
3. マーク`v`確定して設定されたものとして`dist[v] = d`。 
4. 隣人全員をリラックスさせる`to`の`v`。 もし`to`最終決定されておらず、`d + 1 < dist[to]`、 アップデート`dist[to]`そして押します`(d + 1, to)`。 
6. ワンスノード`u`完了しました、その`dist[u]`という質問に対する答えです。 以前にヒープが空になった場合`u`に到達すると、その時点では到達可能なショップがないため、出力します。`-1`。 

微妙な点は、グラフ全体を処理する必要がないということです。 クエリ ノードに到達するまでダイクストラ フロンティアを拡張するだけで済みます。 エッジの重みは均一であるため、これはすべてのショップから外側に広がる BFS 波面とまったく同じように動作します。 

### なぜ効果があるのか

 優先キューには、これまでに挿入されたすべてのショップから発見されたものの最終化されていないすべての最短パス候補が常に含まれています。 新しいショップを追加するたびに、距離 0 の新しいソースを同じグローバル構造に導入します。 ダイクストラのアルゴリズムでは、距離が減少しない順序でノードがファイナライズされることが保証されているため、ノードがポップされると、すでに挿入されているソースを今後緩和してもノードを改善することはできません。 新しいショップはゼロ距離ソースを追加するだけなので、同じプロセスに自然に組み込まれる追加のリラクゼーションを生み出すだけです。 したがって、最終的にノードを完成させるときは、それまでに挿入されたショップの完全なセットからその最短距離を計算します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline
import heapq

def solve():
    n = int(input())
    cells = set()
    coords = []

    for _ in range(n):
        x, y = map(int, input().split())
        coords.append((x, y))
        cells.add((x, y))

    # build adjacency
    adj = {}
    for x, y in coords:
        adj[(x, y)] = []
        for dx, dy in ((1,0), (-1,0), (0,1), (0,-1)):
            nx, ny = x + dx, y + dy
            if (nx, ny) in cells:
                adj[(x, y)].append((nx, ny))

    q = int(input())

    INF = 10**18
    dist = {c: INF for c in cells}
    done = {c: False for c in cells}

    pq = []

    def push(v, d):
        heapq.heappush(pq, (d, v))

    def process_until(target=None):
        while pq:
            d, v = heapq.heappop(pq)
            if done[v]:
                continue
            done[v] = True
            dist[v] = d
            if target is not None and v == target:
                return
            for to in adj[v]:
                if not done[to] and d + 1 < dist[to]:
                    dist[to] = d + 1
                    push(to, d + 1)
        return

    for _ in range(q):
        t, x, y = map(int, input().split())
        v = (x, y)

        if t == 1:
            dist[v] = 0
            push(v, 0)
        else:
            process_until(v)
            print(dist[v] if done[v] else -1)

if __name__ == "__main__":
    solve()
```隣接関係の構築では、座標のハッシュ セットを使用して、O(1) の近隣チェックを保証します。 グリッド座標は大きいものの、まばらであるため、これが必要になります。 

優先キューはすべての操作で共有されるため、以前のフェーズで検出された距離が再利用されます。 の`process_until`この関数は核心です。この関数は、クエリされたノードを完成させるために必要な範囲に限り、グローバル最短パスの拡張を進めます。 

微妙な実装の詳細は、ノードが更新されたときではなく、ヒープからポップされたときにのみノードを完了済みとしてマークすることです。 これにより、ダイクストラの順序の正確さが保たれます。 もう 1 つの重要な点は、クエリ間で構造を決してリセットしないことです。 ショップは同じグローバル キューに自然に蓄積されます。

    import heapq

    n = int(input())
    cells = set()
    coords = []

        x, y = map(int, input().split())

    q = int(input())

    INF = 10**18
    dist = {c: INF for c in cells}
    done = {c: False for c in cells}
    pq = []

    def push(v, d):
        heapq.heappush(pq, (d, v))

    def process(target=None):
        while pq:
            d, v = heapq.heappop(pq)
            if done[v]:

            done[v] = True
            dist[v] = d
            if target == v:

            push(v, 0)

 ## 特殊なケース

 特殊なケースとしては、ショップが存在する前にクエリが尋ねられる場合があります。 その状況では、優先キューは空のままであり、ノードは決してファイナライズされません。 アルゴリズムは正しく返します`-1`なぜなら、`done`クエリされたノードのフラグが true になることはありません。 

もう一つは、長い廊下を通って拡張を繰り返すケースです。 一方の端でショップが追加され、もう一方の端でクエリが発生すると、ダイクストラ プロセスは廊下に沿って徐々に拡大します。 コリドーの長さが最大 ​​n である場合でも、各頂点は一度確定されるため、クエリを繰り返しても、既に確定済みの領域が再処理されることはありません。 

最後の微妙なケースは、複数のショップが互いに近くに追加されることです。 それらの BFS ウェーブは優先キューでマージされますが、ダイクストラ順序付けにより、最小距離が常に優先されるため、更新が異なる順序で到着した場合でも、誤った上書きは発生しません。
