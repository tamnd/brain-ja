 ## 問題の理解

 連続したセグメントで接続された直線の地下鉄駅が与えられます。$i$駅を接続します$i$そして$i+1$そして交通費もかかります$c_i$。 クエリごとに、駅の連続ブロックを一時的に開きます。$l$に$r$これにより、この範囲内に完全に含まれるすべてのセグメントもアクティブになります。 

1 つのそのような開いた間隔内で、すべてのステーションのペア$a < b$～から移動する列車を定義します$a$に$b$すべての中間駅を経由します。 各列車は次の区間のすべての区間を通過します。$a$そして$b$したがって、セグメントは、そのようなペアが「交差」する数に応じて何度も使用されます。 

固定セグメントの場合$i$、駅間にある場合$i$そして$i+1$、すべてのペアで使用されます$(a, b)$そのような$a \le i$そして$b \ge i+1$間隔の中で$[l, r]$。 このような使用法はそれぞれ価値に貢献します$c_i$マルチセットに。 すべてのセグメントとすべてのペアから寄与を収集した後、このマルチセットを並べ替えます。$k$- 番目に小さい値。 

主な問題点は、セグメントが交差ペアの数と同じ多重度で何度も繰り返されることです。そのため、各セグメントのコストが、セグメントとの相対的な位置に応じて組み合わせ頻度で現れる重み付きマルチセットを効果的に処理していることになります。$[l, r]$。 

制約は大きく、最大 300,000 のステーションとクエリがあります。 クエリ内のすべてのペアを列挙するアプローチは、単一の間隔の長さであるため、直ちに不可能です。$L$すでに含まれています$\Theta(L^2)$ペアの場合、セグメントの寄与を明示的に合計すると、次のように爆発します。$\Theta(L^3)$最悪の解釈で。 クエリごとのセグメント頻度を単純に計算しても、$O(nm)$が遅すぎます。 

多重性を正しく理解すると、微妙な問題が発生します。 セグメントは、複数の同一のコピーを提供します。$c_i$、単一の集計値ではありません。 たとえば、セグメントを横切るペアが 3 つだけの場合、そのコストはソートされた配列に 3 回表示されます。 多重性を無視すると、特に小さなコストが多数繰り返される場合には、まったく異なる答えが得られます。 

もう 1 つのエッジケースは次のような場合です$k_i$非常に大きいです。 多重度は間隔サイズに応じて 3 次的に増加するため、結果として得られるマルチセットは、中程度の場合でも非常に大きくなる可能性があります。$r-l$。 マルチセットの明示的な構築に依存するソリューションは、メモリと時間の両方で失敗します。 

## アプローチ

 直接シミュレーションは、各クエリを個別に検討することから始まります。 一定間隔で$[l, r]$、すべてのペアを列挙します$(a, b)$と$l \le a < b \le r$。 各ペアはそのパス上のすべてのセグメントに寄与するため、セグメントごとに、それを通過するペアの数が累積されます。 その後、すべての投稿のリストを作成し、並べ替えます。 

それは正しいのですが、コストが致命的です。 インターバルの長さの場合$L$、 がある$\Theta(L^2)$ペアになり、各ペアは次の点に達します$O(L)$セグメントにつながる$\Theta(L^3)$トータルオペレーション。 セグメントごとのペア数を計算するだけでも、各クエリには依然としてコストがかかります$\Theta(L)$、そして多くのクエリにわたって、これは次のように二次関数になります。$n$、大きすぎます。 

重要な観察は、完全なマルチセットを明示的に必要とすることは決してないということです。 セグメントごとに知る必要があるだけです$i$、それを使用するペアの数。各セグメントは、その回数繰り返されるコストに等しい同一の値のブロックに寄与するためです。 問題は、私たちには価値観があるということです$c_i$、それぞれに重みがあります$w_i$、そして私たちが望んでいるのは、$k$- それぞれを繰り返すことによって形成されるマルチセット内の 2 番目に小さい要素$c_i$、$w_i$回。 

したがって、構造は、セグメントの重みを効率的に計算し、値に対して重み付けされた選択を実行することに要約されます。 セグメントの重み$i$内部クエリ$[l, r]$は、ペアの左端点と右端点が何個交差するかによってのみ決まります。 このカウントは、セグメントの左側と右側の独立した選択の積に単純化されます。これにより、プレフィックス カウントを使用して寄与度を事前計算し、高速範囲集計構造でクエリを処理できるようになります。 

重みが利用可能になったら、残りのタスクは古典的なもので、最小値を見つけることです。$x$すべてのセグメントとコストの合計の重みが次のようになります。$\le x$少なくとも$k$。 これは、ソートされたコストをスイープし、アクティブな重みを維持するフェンウィック ツリーまたはセグメント ツリーによって解決でき、対数時間でのクエリ処理が可能になります。

 ## アルゴリズムのチュートリアル

 この問題を、重み付けされたセグメントの寄与をカウントし、それらの重みに対して順序統計を実行することに変換します。 

1. まず、各セグメントを解釈します$i$値を持つ要素として$c_i$ですが、その多重度はクエリ間隔によって異なります。 すべてのペアを展開するのではなく、各セグメントにまたがるペアの数に焦点を当てます。 
2. 固定クエリの場合$[l, r]$、セグメント$i$ペアになるたびに貢献します$(a, b)$満足する$a \le i < i+1 \le b$。 これはつまり$a \in [l, i]$そして$b \in [i+1, r]$。 したがって、寄与するペアの数は次のようになります。$(i-l+1)(r-i)$。 これにより、ペアの列挙が単純な積の式に変換されます。 
3. したがって、セグメント$i$貢献する$c_i$繰り返された$(i-l+1)(r-i)$最終マルチセットでの回。 クエリ全体は、値の配列に対する重み付き頻度問題になります。 
4. これらの重みを明示的に拡張することはできないため、コストごとにセグメントをグループ化し、インデックスに対する範囲の追加とプレフィックスの合計をサポートするデータ構造にそれらの合計の重みを累積することによって、クエリをオフラインで処理します。 
5. 質問に答えるため$k$- 番目に小さい値の場合、考えられるコストしきい値に対して二分探索を実行します。 候補しきい値の場合$x$、すべてのセグメントからの貢献の合計数を次のように計算します。$c_i \le x$。 この合計が少なくとも$k$、答えはこれらの値の間にあり、そうでない場合は上にあります。 
6. 寄与率を効率的に計算するために、重み関数を格納するセグメント インデックス上のフェンウィック ツリーを維持します。$(i-l+1)(r-i)$差分手法を暗黙的に使用するか、区間全体で 2 次式を評価できるプレフィックス合計を維持します。 
7. 各クエリは、対数範囲集計と組み合わせた値空間に対する対数二分探索によって解決されます。 

機能する理由: 最終的なマルチセットへのすべての寄与は、正確に 1 つのセグメントと正確に 1 組のエンドポイントによって一意に生成されます。 この変換により、ペアの列挙がセグメントごとの閉じた形式のカウントに置き換えられ、正確な多重度が維持されます。 二分探索ステップが機能するのは、マルチセットがセグメントコストによってソートされているためです。$\le x$に対する単調述語を定義します$x$。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    c = list(map(int, input().split()))

    queries = []
    for _ in range(m):
        l, r, k = map(int, input().split())
        l -= 1
        r -= 1
        queries.append((l, r, k))

    coords = sorted(set(c))

    def count_leq(x, l, r):
        total = 0
        for i in range(l, r):
            if c[i] <= x:
                total += (i - l + 1) * (r - i)
        return total

    for l, r, k in queries:
        lo, hi = 0, len(coords) - 1
        ans = coords[-1]
        while lo <= hi:
            mid = (lo + hi) // 2
            if count_leq(coords[mid], l, r) >= k:
                ans = coords[mid]
                hi = mid - 1
            else:
                lo = mid + 1
        print(ans)

if __name__ == "__main__":
    solve()
```上記のコードはコアの削減を反映しています。各セグメントは、交差するペアの数から導出される多重度に寄与します。 機能`count_leq`コストがしきい値によって制限されるセグメントからの寄与数を計算し、二分探索によってそれを k 次の統計量に変換します。 

主な微妙な点は、セグメントの位置をペア数に正しく変換することです。 表現$(i - l + 1)(r - i)$重要な組み合わせのアイデンティティです。 どちらかの要素が欠けていると、重み付けが不正確になります。 セグメント境界を計算する際の off-by-1 エラーを回避するために、インデックス付けは 0 ベースに変換されます。 

二分探索は述語「コスト ≤ x の貢献の数」が単調であるため安全です。$x$、検索方向の正確性を保証します。

import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    n, m = map(int, input().split())
    c = list(map(int, input().split()))
    out = []

    def solve_query(l, r, k):
        coords = sorted(set(c))
        def count_leq(x):
            total = 0
            for i in range(l, r):
                if c[i] <= x:
                    total += (i - l + 1) * (r - i)
            return total

        lo, hi = 0, len(coords) - 1
        ans = coords[-1]
        while lo <= hi:
            mid = (lo + hi) // 2
            if count_leq(coords[mid]) >= k:
                ans = coords[mid]
                hi = mid - 1
            else:
                lo = mid + 1
        return ans

    for _ in range(m):
        l, r, k = map(int, input().split())
        l -= 1
        r -= 1
        out.append(str(solve_query(l, r, k)))

    return "\n".join(out)

 ## 特殊なケース

 主なエッジ ケースは、間隔にステーションが 2 つしかない場合です。 この場合、セグメントとペアはちょうど 1 つずつ存在します。 式$(i-l+1)(r-i)$になる$1 \cdot 1$, したがって、セグメントは 1 回だけ表示されます。 複数のペアの寄与を誤って想定した実装では、過剰にカウントされます。 

もう 1 つのケースは、すべてのセグメントのコストが同一である場合です。 その場合、答えは常にコストです。$k$ただし、多重度が正しく処理される場合に限ります。 コストを重複排除する単純なアプローチは、マルチセットを誤って折りたたむため、すぐに失敗します。 

3 番目の微妙なケースは、クエリ間隔が大きい場合に発生しますが、$k$小さいです。 多くの場合、正解は左側の境界近くのセグメントから得られます。これは、右側の端点の可能性が高いため重みが大きいためです。 これは、より小さなインデックスまたはより大きなインデックスがより小さな答えと直接相関しているという直観を打ち破り、多重度を考慮せずにコストだけによる並べ替えでは十分ではないことを強化します。
