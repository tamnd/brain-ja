 ## 解決策
 ## 問題の理解

 コンテストはすでに終了しており、スコアボードは凍結されています。 あなたは自分のチームの最終結果、つまり解決した問題の数と合計ペナルティ時間を完全に把握しています。 ペナルティは ICPC ルールに従っており、すべての問題は最初に受理された提出時間に加え、最初に受理された問題が提出されるまでに誤った提出があった場合は 20 分が加算されます。 

あなたは現在、別の特定のチームを分析しています。 フリーズ時間前のすべての送信について、どの試行が受け入れられ、どの試行が拒否されたかがすべてわかります。 ただし、フリーズ時間が経過すると、そのチームからのすべての提出物は、最終的に受け入れられるか拒否されるかは分からず、問題に対するタイムスタンプ付きの試みとしてのみ表示されます。 これらの凍結後の提出はそれぞれ独立して、受け入れられた解決策になることもあれば、間違った試みになる可能性もあります。 

問題は、すべての最終ランキングをシミュレーションすることではありません。 代わりに、そのチームが最終ランキングで自分のチームを厳密に上回れる可能性があるかどうかを判断する必要があります。そうである場合、そのために最終的に解決しなければならないフリーズ後の問題の最小数を見つける必要があります。 

「厳密に高いランク」は、通常の ICPC ルールに従います。つまり、より多くの問題を解決したチーム、または同じ数の問題を解決してもペナルティが小さいチームの方が優れています。 

重要な微妙な点は、凍結後の不確実性は個々の提出物に関するものではなく、各問題が凍結後に最終的に解決されるかどうかに関するものであり、解決された場合、承認されたものとして扱うことを決定した最も早い凍結後の提出物のみがスコアリングの対象となるということです。 

制約は、問題の数という点で非常に少なく、最大でも 15 です。これは、どのソリューションでも問題のサブセットに対して指数関数的な推論ができることをすぐに示唆しています。$2^{15}$はわずか 32768 であり、快適に小さいです。 送信の数は最大でも 1000 件で、慎重に前処理する必要があるほど十分な数ですが、それでも問題ごとの集計が簡単であるほど十分に小さいです。 

誤った解決策につながる素朴な誤解は、凍結後の各送信を個別に扱い、貪欲に承認/拒否を割り当てようとすることです。 複数の提出物が同じ問題に属しており、最初に承認されたものだけが重要であるため、これは失敗します。 

もう 1 つのよくある間違いは、凍結後の送信では常に複雑な方法でペナルティが増加すると考えることです。 実際には、問題が凍結後に解決されると決定された場合、最適な戦略は常に、凍結後の最も早い提出を受け入れられたものとして採用することです。これは、それ以降に受け入れても利益はなく、ペナルティが増加するだけであるためです。 

## アプローチ

 ブルート フォース ビューは、凍結後の送信が承認または拒否された結果に解決される可能性があるあらゆる方法を検討することから始まります。 凍結後の提出物のサブセットごとに、最終的な ICPC スコアを再計算し、それをチームと比較します。 これは、不確実性と一致するすべての世界を列挙するため、原理的には正しいです。 

しかし、このアプローチはすぐに爆発します。 凍結後の送信が最大 1000 件ある場合、受け入れ/拒否できる割り当ての数は次のとおりです。$2^{1000}$、それは完全に不可能です。 

ICPC スコアリングの構造により、この問題は圧縮可能になります。 重要な観察は、凍結後の決定は、「凍結後にどの問題が解決されるか」という粒度だけが重要であるということです。 問題が解決されると決定されると、その最適な受け入れポイントは決定的であり、その問題に対するフリーズ後の最も早い提出時点になります。 それ以外の場合はスコアに影響しないか、厳密に言うとスコアが悪くなります。 

これにより、問題は、提出物についての推論から、問題についての推論へと軽減されます。 未解決の問題はそれぞれ、二者択一の項目になります。未解決のままでいるか、または 1 つの追加の解決済み問題と固定のペナルティ コストに寄与するかのどちらかです。 

ここで問題は、最大 15 個の項目のサブセットを選択することになります。 選択されたアイテムの可能な数ごとに、達成可能な最小ペナルティ合計が必要です。 これは、非常に小さな次元にわたる標準的なナップザック スタイルの動的プログラミングです。 

次に、私たちよりも多くの問題を解決するか、解決した問題数が同程度でペナルティが小さいことによって、対戦相手の方が厳密に有利になる、選択された問題の最小数を確認します。

 ## アルゴリズムのチュートリアル

 まず、すべての情報を問題ごとの状態に圧縮し、すでに修正されているものと不確実なものを分離します。 

1. 各問題について、フリーズする前にすでに解決されているかどうかを計算します。 そうであった場合、解決されたカウントとペナルティへの寄与は固定されており、変更することはできません。 
2. 凍結前に解決されなかった問題については、凍結後の提出物をすべて抽出します。 その中で、最も古いタイムスタンプを特定します。 フリーズ後に問題が解決すると判断した場合、これが唯一の候補時間です。 フリーズ後にこの問題を解決することによるペナルティの寄与は、このタイムスタンプに、この問題のそのタイムスタンプより前の間違った提出数の 20 倍を加えたものになります。これは、フリーズ後の最初の提出が受け入れられるまでに、その問題に関する正確な提出数となります。 
3. 対戦相手の最終状態を 2 つの部分に分割します。フリーズする前にすでに解決されている問題の数と、残りの問題です。 すでに解決された数を次のようにします$S_0$。 
4. 候補となる「アップグレード可能な問題」のリストを作成します。それぞれのコストは、凍結後に解決することにした場合のペナルティの増加に等しく、追加の解決済み問題が 1 つ追加されます。 
5. ナップザック動的プログラミングを実行します。$dp[k]$正確に選択することで達成可能な追加ペナルティの最小合計を格納します$k$アップグレード可能な問題。 
6. それぞれの可能性について$k$、結果として得られる合計解決数を計算します。$S_0 + k$。 これがチームの解決数を超えた場合は、ペナルティを課すだけで十分です。$k$実現可能です。 それが解決済みカウントと等しい場合は、さらに、最小ペナルティが$dp[k]$ペナルティよりも厳密に小さいです。 
7. 答えは最小です$k$どちらかの条件を満たすもの。 いいえの場合$k$動作すると、-1 が出力されます。 

これが機能する理由は、フリーズ後のすべての決定が問題ごとにきれいに分解されるためです。 ICPC スコアリングでは問題間に相互作用はありません。各問題は解決済みカウントとペナルティの両方に独立して寄与します。 この独立性により、各問題を単一のコスト項目に最適化することで、すべてのグローバルな最適構造が維持されることが保証されます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**18

def solve():
    n, a, b = map(int, input().split())
    s = int(input())

    solved_before = [False] * n
    pre_wrong = [0] * n

    post_first_time = [INF] * n

    freeze_time = 240

    for _ in range(s):
        parts = input().split()
        t = int(parts[0])
        p = ord(parts[1]) - ord('A')
        v = parts[2]

        if t < freeze_time:
            if v == "ac":
                solved_before[p] = True
            else:
                pre_wrong[p] += 1
        else:
            post_first_time[p] = min(post_first_time[p], t)

    base_solved = sum(solved_before)

    items = []
    for i in range(n):
        if solved_before[i]:
            continue
        if post_first_time[i] == INF:
            continue
        cost = post_first_time[i] + 20 * pre_wrong[i]
        items.append(cost)

    m = len(items)

    dp = [INF] * (m + 1)
    dp[0] = 0

    for cost in items:
        for k in range(m, 0, -1):
            if dp[k - 1] + cost < dp[k]:
                dp[k] = dp[k - 1] + cost

    if base_solved > a:
        print(0)
        return

    ans = INF

    for k in range(m + 1):
        total_solved = base_solved + k

        if total_solved > a:
            ans = min(ans, k)
        elif total_solved == a and dp[k] < b:
            ans = min(ans, k)

    print(-1 if ans == INF else ans)

if __name__ == "__main__":
    T = int(input())
    for _ in range(T):
        solve()
```コードはまず、送信ログから問題ごとの情報を再構築します。 フリーズ前の動作は、問題がすでに解決されているかどうか、および解決するまでに何回間違った試行が行われたかによって固定されます。 フリーズ後のサブミットは、ペナルティを軽減するためにそれ以降のフリーズ後のサブミットを使用できないため、問題ごとに単一の最も古いタイムスタンプに圧縮されます。 

その後、未解決の問題はそれぞれ、選択した場合に固定のペナルティコストがかかるナップザックアイテムになります。 DP は、さらに解決された問題の数ごとに達成可能な最良のペナルティを計算します。 

最後に、ランキング条件が満たされるまで、追加されたソルブの値を増加させてテストします。 

## 実用的な例

 2 つの問題があり、チームがペナルティ 300 で 1 つの問題を解決した単純化されたシナリオを考えてみましょう。 

対戦相手はフリーズ前にすでに解決済みの問題が 1 つあり、フリーズ後の送信で時間 250 で未解決の問題が 1 つあるとします。 

| ステップ | ベース解決済み | k が選択されました | 合計_解決済み | dp[k] | 比較 |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 1 | 0 | 1 | 0 | 等しい解決、ペナルティの比較 |
 | 1 | 1 | 1 | 2 | 費用 | より大きな解決策 |

 で$k=0$、解決済みカウントは同点ですが、追加のペナルティがないため、固定ペナルティがすでに小さくなっていない限り負けます。 で$k=1$、厳密に解決数を上回っているため、ペナルティに関係なく勝ちます。 

このトレースは、解決済みカウントがペナルティを支配する理由を示しています。つまり、解決済みカウントが増加すると、ペナルティは無関係になります。 

ここで、両チームの最初の解決数が等しい場合を考えてみましょう。 

| ステップ | ベース解決済み | k が選択されました | 合計_解決済み | dp[k] | 状態 |
 | --- | --- | --- | --- | --- | --- |
 | 0 | 2 | 0 | 2 | 0 | ペナルティを比較 |
 | 1 | 2 | 1 | 3 | 費用 | 解決済みを超えています |

 ここでの移行点は、まさに解決済みの問題が 1 つ追加されたときです。 DP は、そのような移行が最も安価なものを選択することを保証します。

 ## 特殊なケース

 微妙なケースの 1 つは、フリーズ後の仮定の前に、解決済みの問題において対戦相手がすでに厳密に先を行っている場合です。 この状況では、フリーズ後の決定は重要ではありません。 アルゴリズムはこれを即座に捕捉します。$base\_solved > a$0を返します。 

もう 1 つのエッジ ケースは、問題に複数のフリーズ後の送信がある場合です。 それ以降に受け入れてもペナルティが増加するだけであるため、最も早い時点のみが重要です。 アルゴリズムは、コストを計算する前に問題ごとの最小タイムスタンプを取得することでこれを強制します。 

最後のケースは、凍結後の送信がまったくない場合です。 するとナップザックセットは空になり、$k = 0$テストされます。 比較は、すでに固定されたスコアが十分であるかどうかをチェックすることになり、まだ改善されていない場合は正しく -1 が返されます。
