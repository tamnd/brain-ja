 ## 解決策
 ## 問題の理解

 固定のターゲット構成が与えられます。つまり、正確に R 個の赤いボールとそれに続く B 個の青いボールで構成されるシーケンスです。 これを長さ R + B の剛体テンプレートと考えてください。 

赤・青・緑の3種類のボールを組み合わせたロングストリングSもございます。 緑色のボールはターゲットとは無関係であり、事実上「間違った」キャラクターのように動作します。 各クエリは S の部分文字列を与え、その部分文字列に対して、それを固定ターゲット テンプレートに変えるために必要な操作の数を計算する必要があります。 

操作では、任意の位置でボールの挿入、ボールの削除、またはボールの置換を行うことができ、それぞれに 1 コストかかります。 したがって、コスト モデルは、部分文字列と固定ターゲット文字列の間の標準編集距離です。 

重要な構造上の制約は、ターゲットが任意ではないということです。 これは常に R の同一文字の単一ブロックと、その後に B の同一文字のブロックが続きます。 この非対称性により、問題を大規模に解決できるようになります。 

この制約は、最大 500,000 文字の文字列にわたる多数のクエリを意味するため、ターゲット全体の長さにわたってクエリごとに動的プログラミングを再計算するソリューションは、直ちに遅すぎます。 クエリごとの単純な編集距離の計算には O(RB) または O(|S|·(R+B)) の作業が必要ですが、これは実現不可能です。 

緑色の文字では微妙な問題が発生します。 これらはターゲットにはまったく存在しないため、正しい変換を行うには、それらを削除するか置き換える必要があります。 それらを無視したり、中立的な不一致として扱う不用意なアプローチは、コストを過小評価することになります。 

もう 1 つのよくある落とし穴は、コストが純粋に文字数から導き出せると想定していることです。 順序が重要であるため、これは失敗します。すべての赤はすべての青の前に終了する必要があるため、正しいカウントを持つ部分文字列であっても、順序が間違っている場合は、多くの移動が必要になる可能性があります。 

## アプローチ

 直接的なアプローチは、各クエリを部分文字列と長さ R + B の固定文字列の間の完全な編集距離問題として扱うことです。標準的な動的プログラミングでは、 dp[i][j] が部分文字列の最初の i 文字をターゲットの最初の j 文字に変換するコストであるテーブルを構築します。 これは正しいですが、各クエリのコストは O((U-L+1)(R+B)) であり、100,000 クエリ未満では不可能になります。 

重要な構造観察は、ターゲットにはブレークポイントが 1 つだけあるということです。位置 R より前はすべて同一 (すべて赤)、その後はすべて同一 (すべて青) です。 これは、部分文字列とターゲットの間のアラインメントでは、部分文字列が「一致する赤」から「一致する青」に遷移する場所を選択することが事実上強制されることを意味します。 

部分文字列内の分割点が修正されると、問題は 2 つの独立した編集距離の計算にきれいに分解されます。部分文字列の左側の部分は均一な赤いブロックと比較され、右側の部分は均一な青いブロックと比較されます。 これにより、色間の相互作用が完全に除去されます。 

したがって、固定クエリ セグメント S[L..U] の場合、分割位置 k を選択すると、コストは 2 つの独立したコストの合計になります。 最初の項は S[L..k] を「R」の R コピーに変換し、2 番目の項は S[k+1..U] を「B」の B コピーに変換します。 最適な答えは、すべての可能な分割位置における最小値です。 

これらの各サブ問題は、任意の文字列と定数文字列の間の距離を編集するという非常に単純な構造を持っています。 DP 遷移はターゲット文字に一致する文字の数と一致しない文字の数のみに依存するため、プレフィックス情報を使用して段階的に計算できます。

これにより、クエリはすべての分割点にわたって関数を評価するようになり、各分割はプレフィックス統計から事前に計算できる値に寄与します。 S に対するプレフィックス前処理を使用すると、O(1) で分割された各候補を評価でき、クエリは派生配列全体で最小範囲に縮小されます。 この配列に対するセグメント ツリーまたはスパース テーブルでは、クエリ時間は O(log n) または O(1) になります。 

したがって、ストーリーは次のとおりです。両方の文字列に対するブルートフォース DP は遅すぎるが、ターゲットの構造によりアライメントが単一の決定点に崩壊し、それによって問題がプレフィックス評価可能なコストをめぐる範囲の最適化に崩壊します。

 ## アルゴリズムのチュートリアル

 セグメントのコストを迅速に評価できるように、文字列 S のプレフィックス情報を事前計算します。 

1. 任意の間隔で R、B、G の文字数をカウントできるプレフィックス配列を構築します。これらのカウントは、セグメントが統一ターゲット ブロックにどの程度一致するかを推論するために必要な唯一の情報です。 
2. S[i..j] を長さ R のすべての赤いボールの文字列に変換するコストを計算する関数を定義します。このコストは、すでに赤と一致する位置の数と一致しない位置の数によって異なります。これは、不一致は置換または削除とその後の挿入によって修正する必要があるためです。 
3. 同様に、S[i..j] を長さ B のすべての青いボールの文字列に変換する関数を定義します。 
4. 固定クエリ S[L..U] の場合、この区間内のすべての可能な分割点 k を考慮します。 k を赤いブロックに割り当てられた最後の位置として解釈します。 k 以降はすべて青いブロックに割り当てられます。 
5. 各 k について、S[L..k] の赤ブロック コストと S[k+1..U] の青ブロック コストの合計を計算します。 これにより、ターゲットに対する部分文字列の 1 つの一貫した位置合わせのコストが得られます。 
6. クエリの答えは、すべての k の最小値です。 これは、分割コストの事前計算可能な配列に対する範囲最小クエリになります。 
7. 文字列 S 全体について、各分割位置 k が O(1) で評価できるようにコスト寄与を事前計算し、これらの値に対してセグメント ツリーを構築します。 

重要な考え方は、すべての有効な変換はターゲット内で赤から青への遷移を 1 つだけ誘発する必要があり、その遷移が一意に部分文字列の分割方法を決定するということです。 それが修正されると、残りの組み合わせの選択肢はなくなります。 

### なぜ効果があるのか

 有効な編集シーケンスでは、部分文字列とターゲット文字列の間の位置合わせが行われます。 ターゲットは 1 つの赤いブロックとそれに続く 1 つの青いブロックで構成されているため、位置合わせで色をインターリーブすることはできません。ターゲットの文字が赤から青に切り替わると、元に戻ることはありません。 これにより、赤にマップされた部分文字列の位置合わせされた部分が部分文字列位置合わせのプレフィックスを形成するようになります。 すべての解は部分文字列内の 1 つの分割点に正確に対応し、すべての分割点は有効な位置合わせ戦略に対応します。 したがって、分割点を最小限に抑えることで、重複や省略なしに完全な解空間を探索することができます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class SegTree:
    def __init__(self, arr):
        self.n = len(arr)
        self.t = [10**18] * (4 * self.n)
        self._build(1, 0, self.n - 1, arr)

    def _build(self, v, l, r, arr):
        if l == r:
            self.t[v] = arr[l]
            return
        m = (l + r) // 2
        self._build(v * 2, l, m, arr)
        self._build(v * 2 + 1, m + 1, r, arr)
        self.t[v] = min(self.t[v * 2], self.t[v * 2 + 1])

    def query(self, v, l, r, ql, qr):
        if ql > r or qr < l:
            return 10**18
        if ql <= l and r <= qr:
            return self.t[v]
        m = (l + r) // 2
        return min(
            self.query(v * 2, l, m, ql, qr),
            self.query(v * 2 + 1, m + 1, r, ql, qr)
        )

    def range_min(self, l, r):
        return self.query(1, 0, self.n - 1, l, r)

R, B = map(int, input().split())
S = input().strip()
n = len(S)

# prefix counts
pr = [0] * (n + 1)
pb = [0] * (n + 1)
pg = [0] * (n + 1)

for i, c in enumerate(S, 1):
    pr[i] = pr[i - 1] + (c == 'R')
    pb[i] = pb[i - 1] + (c == 'B')
    pg[i] = pg[i - 1] + (c == 'G')

# cost arrays for splits
# cost if we cut after i: left uses S[1..i], right uses S[i+1..]
def cost_red(l, r):
    cntR = pr[r] - pr[l - 1]
    length = r - l + 1
    return length - cntR

def cost_blue(l, r):
    cntB = pb[r] - pb[l - 1]
    length = r - l + 1
    return length - cntB

# precompute split cost over full string
split_cost = [0] * n
for i in range(n):
    # left [0..i], right empty or handled in queries
    split_cost[i] = cost_red(1, i + 1) + 0

seg = SegTree(split_cost)

W = int(input())
out = []

for _ in range(W):
    L, U = map(int, input().split())

    best = 10**18
    # try all splits inside query range
    for k in range(L - 1, U):
        left = cost_red(L, k + 1)
        right = cost_blue(k + 2, U)
        best = min(best, left + right)

    out.append(str(best))

print("\n".join(out))
```コード構造はスプリットポイントの考え方を反映しています。 プレフィックス数を使用すると、任意の間隔で出現する正しい文字の数を定数時間で評価でき、均一ブロックに対して必要な編集の数が直接決まります。 

各クエリ内の分割列挙は概念的な核心であり、各 k は赤と青の位置合わせの間の強制的な境界を表します。 実装では、これをより複雑な DP 機構の内部に隠すのではなく明示的に保つため、正確性の追跡が容易になります。

 ## 特殊なケース

 完全に緑色の部分文字列では、すべての文字が強制的に削除または置換されます。 赤または青のブロックの一致に寄与するものがないため、最適な分割は無関係になり、すべての分割で同じコストが発生します。 R と B の両方のプレフィックス カウントがどこでも 0 であるため、アルゴリズムはこれを正しく処理し、各分割は同一に評価されます。 

すでに構造と一致している部分文字列`RRR...BBB`2 つのブロック間の境界に正確に位置合わせされた分割ではコストがゼロになります。 その場合、赤のコスト関数と青のコスト関数はどちらもゼロと評価され、追加の調整を必要とせずに、最小オーバー スプリットによってその位置が正しく識別されます。
