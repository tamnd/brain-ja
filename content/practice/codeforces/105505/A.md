 ## 解決策
 ## 問題の理解

 2 段階のプロセスで生成された単一の大文字文字列が与えられます。 まず、誰かがオリジナルの文字列を持っていた`t`。 次に、次の文字列をすべて取得して 2 番目の文字列を作成しました。`t`、アルファベット順に並べ替え、各文字を 1 回ずつ書きます。 最後に、元のファイルをこの派生文字列で置き換えるのではなく、元のファイルに追加しました。 

したがって、入力文字列は`S`実は`S = t + g(t)`、 どこ`g(t)`に出現する一意の文字のソートされた文字列です。`t`。 

任務は再構築ではない`t`それ自体で長さを決定するだけです。 

この制約により、文字列の長さは最大 2000 まで許可されます。これは、二次または二次に近い解が問題なく通過できるほど十分に小さいですが、変換にはソートと重複排除が含まれるため、隠された構造特性があることも示唆されます。通常、情報は小さな固定アルファベット サイズに縮小されます。 

重要な観察は次のとおりです`g(t)`明確な大文字のみが含まれています。 大文字は 26 個しかないため、追加されるサフィックスの長さは最大 26 になります。これにより、境界を末尾近くの非常に小さな領域に局在化できるため、主要な戦略として 2000 インデックスすべてにわたって任意の分割位置を試みるアプローチは即座に排除されます。 

単純な間違いは、文字列内のどこにも分割点が不明であると仮定することです。 たとえば、与えられた`S = "ICPCCIP"`、多くの位置に分割してそれぞれを検証しようとするかもしれませんが、これは機能しますが、不要です。 

もう 1 つの微妙なエッジケースは次のような場合です。`t`それ自体には、ソートされた順序で正確にすべての個別の文字がすでに含まれています。 たとえば、次の場合`t = "ABC"`、 それから`g(t) = "ABC"`、最終的な文字列は次のようになります`"ABCABC"`。 慎重に推論しないと、重複により分割点があいまいであるように見える可能性があります。 

本当の課題は、サフィックスがプレフィックス内の文字セットによって完全に決定され、その長さが制限されていることを認識することです。 

## アプローチ

 直接的な総当たりアプローチにより、考えられるすべての分割ポイントが試行されます。`i`から`1`に`n-1`。 分割ごとに、`S[:i]`候補として`t`、文字のセットを計算し、並べ替えて、次と比較します。`S[i:]`。 一致する場合は戻ります`i`。 

これは、構造の定義を直接強制するため、正しいです。 ただし、分割ごとにセットを再構築し、最大 26 文字を並べ替えることができます。これは安価ですが、それを実行します。`O(n)`回、約`O(n^2)`最悪の場合は文字処理が行われます。 と`n = 2000`、これはまだ境界線に問題ありませんが、不要です。 

重要な洞察は、2 番目の部分です。`g(t)`は正確にソートされた文字セットです`t`したがって、その長さは、次の異なる文字の数になります。`t`。 この数は最大 26 です。つまり、分割ポイントは文字列の最後の 26 文字以内になければなりません。 

したがって、可能なすべての接尾辞の長さを試すことができます`k`から`1`に`26`、 解釈する`S[n-k:]`候補者として`g(t)`、ソートされたプレフィックスの一意の文字と一致するかどうかを確認します。`S[:n-k]`。 これらのうち 1 つが一致します。 

これにより、最大 2000 の分割ポイントをスキャンする問題が、最大 26 個の候補をチェックする問題に軽減されます。

 | --- | --- | --- | --- |
 | ブルートフォース分割チェック | O(n²) | O(1) おまけ | 受け入れられるが不要 |
 | 接尾辞の長さ ≤ 26 を試してください | O(26・n) | O(1) おまけ | 承認済み |

 ## アルゴリズムのチュートリアル

 追加された部分は元の文字列のソート済みの重複排除バージョンであるという事実を利用するため、そのサイズはプレフィックス内の個別の文字の数によって完全に決定されます。 

1. しましょう`n`の長さになる`S`。 接尾辞は次のものに対応すると考えます。`k`人によっては独特のキャラクター`k`間`1`そして`26`。 これは、大文字が 26 文字しかないため、重複排除された文字列はこの長さを超えることができないためです。 
2. 各候補者について`k`、最後を取ります`k`の登場人物`S`可能性として`g(t)`。 This is the hypothesized suffix.
 3. プレフィックスを計算します`S[:n-k]`、次のように解釈します`t`、その文字セットを抽出します。 このセットをソートすると、期待される形式が生成されます。`g(t)`。 
4. 計算されたソートされた一意の文字列をサフィックスと比較します。 それらが正確に一致する場合、`n-k`元の文字列の正しい長さです。 
5. 帰ります`n-k`一致するものが見つかったらすぐに。 

### なぜ効果があるのか

 この構造により、接尾辞が接頭辞内の文字セットによって一意に決定されることが保証されます。 したがって、分割点の候補を修正すると、サフィックスはそのプレフィックスのソートされた一意の文字と強制的に等しくなります。 真のサフィックスもこの条件を満たす必要があるため、テストされた値の中に現れる必要があります。`k`。 上限の 26 により、正しい分割を見逃すことがなくなり、文字セットや順序の不一致によって構造が崩れるため、無効な分割が誤って等価条件を満たすことはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    s = input().strip()
    n = len(s)

    for k in range(1, 27):
        if k > n:
            break
        suffix = s[n - k:]
        prefix = s[:n - k]

        if len(set(prefix)) != k:
            continue

        if ''.join(sorted(set(prefix))) == suffix:
            print(n - k)
            return

solve()
```この実装では、可能なサフィックスの長さにわたって境界検索を直接エンコードします。 唯一の微妙な点は、文字列自体よりも長いサフィックスを試行しないようにすることと、サフィックスをプレフィックスの正規形式と比較することです。 

よくある間違いは、サフィックスがソートおよび重複排除されていることを忘れているため、ソートされていないセット表現との比較が失敗することです。 もう 1 つは、分割ポジションを最大まで反復することです。`n`これは不要であり、アルファベットのサイズ制限を使用するよりも構造化されていません。

 ## 特殊なケース

 特殊なケースの 1 つは、すべての文字が`t`は同一です。 例えば、`S = "AA"`。 唯一の有効な解釈は、`t = "A"`そして`g(t) = "A"`、したがって、答えは次のとおりです`1`。 アルゴリズムチェック`k = 1`、プレフィックスを計算します`"A"`、そのユニークなソート形式`"A"`、接尾辞と一致します`"A"`。 

もう 1 つのエッジケースは次のような場合です`t`26文字すべてが含まれています。 この場合、サフィックスの長さは正確に 26 です。このアルゴリズムは、26 までのすべての値を明示的にテストし、完全なアルファベットのサフィックスと一致するため、引き続き機能します。 

3 番目のケースは、プレフィックスに文字列全体に散在する繰り返し文字が含まれている場合です。`"ABABAB"`。 重複排除のステップにより、計算されたサフィックスが安定したままであることが保証されます。`"AB"`したがって、繰り返される文字の順列は正確さに影響しません。
