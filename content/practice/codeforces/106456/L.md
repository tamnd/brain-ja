 ## 解決策
 ## 問題の理解

 駐車場はグリッドであり、各セルには空きがあるか、移動方向が固定された車が収容されています。 各車は、自分が向いている方向にのみグリッドから離れることを試みることができ、その位置からグリッド境界までの直線セグメント全体にその時点で他の車が含まれていない場合にのみ成功します。 

私たちが実行できる操作は、車を選択し、「出発」コマンドを送信することです。 進行方向の進路に障害がなければ、車は消え、そのセルは空になります。 そうしないと、その瞬間には何も有益なことが起こらないため、有効な解決策は、ブロックされた車両での無駄な移動を回避する必要があります。 

タスクは、すべての車両が最終的に出発するようなコマンド発行の順序が存在するかどうかを判断することです。 このような順序が存在する場合は、有効な座標シーケンスを削除の順序で出力する必要があります。 全車クリアできない場合は-1を出力します。 

グリッド サイズは 2000 ごとに最大 400 万個のセルが存在する可能性があります。 操作ごとに行全体または列全体を繰り返しスキャンしようとするアプローチは、各スキャンが次元内で線形であり、車両ごとに 1 回繰り返される可能性があるため、時間がかかりすぎます。 これにより、セル数の最悪の場合の二次関数の動作が発生します。 

単純なシミュレーションの微妙な失敗例は、自動車が依存関係のサイクルに関与している場合です。 たとえば、2 x 2 のグリッドを考えてみましょう。```
RD
UL
```各車が進行方向の他の車をブロックし、最初は明確な進路を持たない車がないサイクルを形成します。 「現在取り外し可能な」車を削除しようとする貪欲な戦略は、たとえよりグローバルな依存関係の観点から削除命令が存在しないことが示されていても、最初は条件を満たすものがないため、すぐに行き詰まってしまいます。 

もう一つの微妙な問題が長い連鎖に現れます。 自動車が同じ行または列の遠く離れた別の自動車に依存している場合、削除するたびにライン全体を繰り返しスキャンすると、同じ構造が何度も再計算され、時間がかかりすぎます。 

## アプローチ

 強引な解釈では、グリッドを繰り返しスキャンし、現在境界への経路が明確になっているすべての車両を特定し、そのうちの 1 台を削除し、これを繰り返します。 各反復では最大 O(NM) 個のセルをチェックする必要があり、車の経路をチェックするには最大 O(N) または O(M) 個のスキャンが必要です。 最大 O(NM) 個の除去では、これは O((NM)^2) となり、200 万台以上の自動車の制限をはるかに超えています。 

重要な構造的観察は、車が発進できるかどうかは、同じ行または列に沿って進行方向にある最初の車にのみ依存するということです。 最も近いブロック車が存在する場合、それ以上のことは問題になりません。 これにより、グローバルな可視性条件がローカルな依存関係に変換されます。つまり、各車両はその方向にある隣接車両 1 台のみに依存します。 

このように依存関係を表示すると、プロセスは動的グラフの問題になります。 各車両はノードであり、その方向にある他のノードが最大 1 つによって「ブロック」されます。 妨害車両が撤去されると、周囲の車両の依存関係が解消され、新たに撤去の対象となる場合があります。 

これは、車が消えたときに次の潜在的な障害物をすぐに見つけられるように、各行と列の隣接性を維持することを示唆しています。 行ごとおよび列ごとに二重リンクされた構造により、近隣車両を O(1) 時間で更新でき、空になった車両はキューで処理されます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 繰り返しスキャン | O((NM)^2) | O(NM) | 遅すぎる |
 | 行/列の隣接メンテナンス + BFS | O(NM) | O(NM) | 承認済み |

 ## アルゴリズムのチュートリアル

 すべての車をノードとして扱います。ノードは、現在進行方向に障害物がない場合にのみ削除できます。 高速な更新をサポートするために、各車両の 4 つの隣接ポインタ (他の車両の行または列内で左、右、上、下) を維持します。 

1. すべての車両のリストを作成し、各車両にその位置を割り当てます。 すべての行で左から右に車をリンクし、すべての列で上から下に車をリンクします。 これにより、どの方向にいても、次に残っている車両にすぐにアクセスできるようになります。 
2. 各車両について、その方向のすぐ隣の車両のみを見て、最初に取り外し可能かどうかを確認します。 その隣の車が存在しない場合、車はすでに出発できるため、列に押し込まれます。 
3. キューを繰り返し処理します。 車を取り除くたびに、その座標を回答シーケンスに記録します。 
4. 車が削除されると、その車は行と列の両方のリンク リストから削除されます。 これは、その左隣とその右隣、およびその上の隣とその下の隣を再接続することを意味します。 
5. 車を撤去した後は、同じ行または列のすぐ隣の車だけがブロック構造を変更できます。 このような近隣の車両ごとに、取り除いたばかりの車がその方向の障害となる近隣車両であるかどうかを確認します。 「はい」の場合、更新されたリンク構造を使用して、新しい最も近いブロッカーを再計算します。 その方向にブロッカーがない場合は、それをキューにプッシュします。 
6. キューが空になるまで続行します。 すべての車を記録したら、シーケンスを出力します。 それ以外の場合、一部の車はサイクルに閉じ込められているか、除去できない構造物によってブロックされているため、-1 を出力します。 

正しさは、各車両の「出口の可視性」がその方向に最も近い残りの車両にのみ依存し、この最近隣構造がリンクされたリストによって完全に維持されるという事実に基づいています。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    n, m = map(int, input().split())
    grid = [list(input().strip()) for _ in range(n)]

    # store only car cells
    cars = []
    idx = [[-1] * m for _ in range(n)]

    for i in range(n):
        for j in range(m):
            if grid[i][j] != '.':
                idx[i][j] = len(cars)
                cars.append((i, j))

    k = len(cars)
    if k == 0:
        print(-1)
        return

    # linked lists in rows and cols
    L = [-1] * k
    R = [-1] * k
    U = [-1] * k
    D = [-1] * k

    row = [[] for _ in range(n)]
    col = [[] for _ in range(m)]

    for id, (i, j) in enumerate(cars):
        row[i].append(id)
        col[j].append(id)

    for i in range(n):
        row[i].sort(key=lambda x: cars[x][1])
        for t in range(len(row[i])):
            if t > 0:
                L[row[i][t]] = row[i][t - 1]
            if t + 1 < len(row[i]):
                R[row[i][t]] = row[i][t + 1]

    for j in range(m):
        col[j].sort(key=lambda x: cars[x][0])
        for t in range(len(col[j])):
            if t > 0:
                U[col[j][t]] = col[j][t - 1]
            if t + 1 < len(col[j]):
                D[col[j][t]] = col[j][t + 1]

    def get_blocker(i):
        x, y = cars[i]
        d = grid[x][y]
        if d == 'U':
            return U[i]
        if d == 'D':
            return D[i]
        if d == 'L':
            return L[i]
        return R[i]

    from collections import deque
    q = deque()
    inq = [False] * k

    for i in range(k):
        if get_blocker(i) == -1:
            q.append(i)
            inq[i] = True

    removed = [False] * k
    ans = []

    while q:
        v = q.popleft()
        if removed[v]:
            continue
        removed[v] = True
        ans.append(v)

        x, y = cars[v]

        l, r = L[v], R[v]
        u, d = U[v], D[v]

        if l != -1:
            R[l] = r
        if r != -1:
            L[r] = l
        if u != -1:
            D[u] = d
        if d != -1:
            U[d] = u

        def try_push(u):
            if u == -1 or removed[u]:
                return
            if not inq[u] and get_blocker(u) == -1:
                q.append(u)
                inq[u] = True

        if l != -1: try_push(l)
        if r != -1: try_push(r)
        if u != -1: try_push(u)
        if d != -1: try_push(d)

    if len(ans) != k:
        print(-1)
    else:
        for v in ans:
            x, y = cars[v]
            print(x + 1, y + 1)

if __name__ == "__main__":
    solve()
```このソリューションでは、更新がグリッド スキャンではなくポインター ベースになるように、まずグリッドを自動車ノードのリストに圧縮します。 行と列の並べ替えにより、最初の隣接関係が構築され、これらの関係は、車両が削除されるときに動的に維持されます。 

機能`get_blocker`は重要な依存関係ルールを捉えています。つまり、車はその方向に最も近い車のみを考慮します。 BFS キューは、既にブロッカーを持たないすべての車両から開始されます。 削除するたびに、行および列構造内のローカル近傍のみが更新され、グローバルな再計算が回避されます。 

実装の微妙な点は、リンクされた構造内の隣接する車両のみを削除後にチェックする必要があることです。これは、削除された車両を最も近いブロッカーとして使用できるのはそれらの車両のみであるためです。

 ## 特殊なケース

 タイトなサイクルは最も重要な故障モードです。 各車両が他の車両をブロックする 2 バイ 2 構成では、各車両がその方向にブロックしている車両があるため、最初のキューは空になります。 このアルゴリズムは空のキューを正しく初期化し、ノードをまったく処理しないため、削除された車両数と車両総数の間に最終的な不一致が生じ、-1 がトリガーされます。 

2 番目のケースは、取り外しによって次の車のロックが徐々に解除される長い直線チェーンです。 ここでは、リンク リスト構造により、妨害車両が取り除かれると、列全体または行全体をスキャンしなくても、次の隣接車両がすぐに検出可能になります。 これにより、完全な再スキャンに依存した単純なアプローチでは見逃したり、処理が遅すぎたりするロック解除イベントの見逃しが防止されます。 

3 番目のケースには、複数の独立したコンポーネントが含まれます。 各車両はその行および列に隣接する車両とのみ対話するため、コンポーネントは独立して進化し、キューはグローバルな調整を必要とせずに自然にコンポーネントの削除をインターリーブします。
