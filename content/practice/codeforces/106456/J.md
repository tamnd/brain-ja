 ## 解決策
 ## 問題の理解

 すべてのノードが数値を保持するルート付きツリーが与えられます。 ツリーは固定されていますが、値はグローバルな単調特性を維持する制約の下で時間の経過とともに変化します。つまり、すべての親は常に、少なくともそれぞれの子と同じ大きさの値を持たなければなりません。 

このタスクは 2 つのオンライン操作をサポートします。 1 つの操作では、ノード u から開始してルートに向かって上向きに歩き、値が少なくとも指定されたしきい値 w である最初のノードを見つけることが求められます。 もう 1 つの操作は、結果の値が親と子の両方に関してツリーを有効に保つ場合に限り、増分によってノードの値を調整しようとします。 

ここで重要な構造は、値が任意ではないということです。 すべての親は常にその子と少なくとも同じ大きさであるため、ルートからリーフへのパスに沿った値は下方向に増加することはなく、したがって上方向に減少することもありません。 この単一の単調な事実により、両方の操作が管理可能になります。 

この制約は、N と Q の両方がテスト グループごとに 100,000 に達し、すべてのテストで合計 200,000 に達する可能性があることを意味します。 これにより、クエリごとにツリーをたどったり、更新のたびにサブツリー情報を最初から再計算したりするソリューションは即座に除外されます。 1 操作あたり O(N) であっても、すでに遅すぎます。 操作ごとに基本的に O(log N) が必要です。 

微妙な点は、更新が独立していないことです。 1 つのノードを変更すると、その親と子の両方の実現可能性制約に影響します。 クエリ時に親と子だけをチェックする単純なアプローチでは、特にノードが親に比べて大きすぎる場合、または最大の子に比べて小さすぎる場合に、以前の更新によって作成された違反を見逃してしまいます。 

たとえば、ノード x に値 10 と 20 の子があり、x の値が 30 であるとします。x を 15 にデクリメントすると、1 つの子がまだ値 20 を持つため、構造は無効になります。親の制約だけを調べる単純なチェックでは、更新が誤って受け入れられてしまいます。 

## アプローチ

 クエリの直接的なアプローチは、値が少なくとも w であるノードが見つかるまで、単純に u からその親に繰り返し移動することです。 パスは一意であるため、これは正しいですが、最悪の場合、ツリーの高さが O(N) になる可能性があるため、各クエリが線形時間まで低下する可能性があります。 

単純な設定では、更新はさらに悪化します。変更のたびに、子の最大値を再計算したり、サブツリー全体を再検証したりする必要があり、最悪の場合、更新ごとに O(N) になる可能性があるためです。 

重要な構造上の観察は、ノードからルートまでのどのパスに沿っても、値が単調に減少しないことです。 これは、上に移動し始めると、値は、しきい値クエリに関する実現可能性の観点から並べ替えられたシーケンスのように動作することを意味します。 

この単調性により、バイナリ リフティングを先祖だけでなく「値条件付きジャンプ」にも使用できるようになります。 ノード v の値が w より小さいことがわかっている場合、u と v (両端を含む) の間のセグメント上のすべてのノードも w より小さい値を持ちます。 これは、上に移動するにつれて値が増加するだけなので、v はすでにそのセグメントの最大値を表しているためです。 これにより、正確さを維持しながら 2 のべき乗で上にジャンプすることができます。 

更新の場合、構造制約はローカルです。更新されたノードの親と子のみが破られることができます。 これは、すべてのノードについて、その子の間の最大値を維持することを示唆しています。 対数時間での更新をサポートするには、ノードごとのマルチセットで十分です。 

私たちは、祖先クエリのためのバイナリ リフティングと、妥当性維持のためのノードごとのマルチセットという 2 つのアイデアを組み合わせます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 単純な上向きスキャン + 再計算 | 操作ごとに O(N) | O(N) | 遅すぎる |
 | バイナリリフティング + 子マルチセットメンテナンス | 操作ごとに O(log N) | O(N log N) | 承認済み |

 ## アルゴリズムのチュートリアル

各ノードの親、その深さ、および 2 の累乗で祖先にジャンプするためのバイナリ リフティング テーブルを保存することによって、ツリーを前処理します。 また、子の値を格納するノードごとにマルチセットを維持することで、O(1) で子の最大値をクエリし、O(log N) で更新できるようにします。 

### クエリ操作: 値 ≥ w の最初の祖先を検索します。 

1. ノード u から開始して、その値がすでに少なくとも w であるかどうかを確認します。 そうであれば、それはパス上の最低点であるため、u がすぐに答えになります。 
2. それ以外の場合は、値がまだ w より低いノードに留まりながら上に登る必要があります。 目標は、M[v] < w となる最上位の祖先 v を見つけることです。 
3. 2 の大きなべき乗から下方へバイナリ リフティング レベルを繰り返します。 v から祖先 anc[v][k] への候補ジャンプの場合、その祖先での値がまだ w より小さいかどうかを確認します。 
4. それが w より小さい場合、単調性によって間にあるすべてのノードも w より小さいことが保証されるため、安全にジャンプします。 
5. すべてのジャンプが終了した後、M[v] < w で最高位のノード v に着地します。 その親は、存在する場合、値が少なくとも w であるパス上の最初のノードです。 

これが機能する理由は、述語「value < w」が u から始まり上に伸びる連続セグメントを形成しているためです。 バイナリ リフティングでは、対数時間でこのセグメントの境界を見つけます。 

### 更新操作: v によってノードを変更します。 

1. 候補となる新しい値 x = M[current] + v を計算します。 
2. 親制約を確認します。 ノードがルートではない場合は、x ≤ M[parent] であることを確認します。 これが失敗すると、アップデートは拒否されます。 
3. x ≥ 子の間の最大値を検証して、子の制約を確認します。 ノードがリーフの場合、この条件は自動的に満たされます。 
4. 両方の制約に合格した場合、更新を適用します。 
5. ノードの古い値をその親の子値のマルチセットから削除し、新しい値を挿入します。 

これにより、グローバルに何も再計算しなくても、すべてのノードがサブツリーの境界条件に関する正しい情報を常に保持できるようになります。 

### なぜ効果があるのか

 正しさは 2 つの不変条件に基づいています。 まず、親の値は常に子の値と少なくとも同じ大きさであるため、ルートからリーフへのパスに沿った単調性が保証されます。 第 2 に、各ノードのマルチセットはその直接の子を正確に追跡するため、更新によって導入された違反は変更の時点でローカルに検出されます。 

すべての制約はローカルであり、グローバル構造はこれらのローカル チェックを通じて強制されるため、隠れた不整合が導入時に検出されずに伝播することはありません。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

sys.setrecursionlimit(10**7)

def solve():
    t = int(input())
    for _ in range(t):
        n, q = map(int, input().split())
        a = list(map(int, input().split()))
        g = [[] for _ in range(n)]
        
        for _ in range(n - 1):
            u, v = map(int, input().split())
            u -= 1
            v -= 1
            g[u].append(v)
            g[v].append(u)
        
        parent = [-1] * n
        depth = [0] * n
        
        stack = [0]
        order = [0]
        parent[0] = -1
        
        while stack:
            u = stack.pop()
            for v in g[u]:
                if v == parent[u]:
                    continue
                parent[v] = u
                depth[v] = depth[u] + 1
                stack.append(v)
                order.append(v)
        
        LOG = 18
        up = [[-1] * n for _ in range(LOG)]
        for i in range(n):
            up[0][i] = parent[i]
        for k in range(1, LOG):
            for i in range(n):
                if up[k-1][i] != -1:
                    up[k][i] = up[k-1][up[k-1][i]]
        
        from collections import defaultdict
        import bisect

        children = [[] for _ in range(n)]
        for v in range(1, n):
            children[parent[v]].append(v)

        import heapq

        # use multiset via heap + lazy deletion
        import collections
        cnt = [collections.Counter() for _ in range(n)]
        child_max = [0] * n

        for u in range(n):
            for v in children[u]:
                cnt[u][a[v]] += 1
            if cnt[u]:
                child_max[u] = max(cnt[u].keys())
            else:
                child_max[u] = 0

        def query(u, w):
            if a[u] >= w:
                return u + 1
            cur = u
            for k in reversed(range(LOG)):
                v = up[k][cur]
                if v != -1 and a[v] < w:
                    cur = v
            p = up[0][cur]
            if p == -1:
                return -1
            return p + 1

        for _ in range(q):
            opt, x, y = map(int, input().split())
            if opt == 1:
                u = x - 1
                w = y
                print(query(u, w))
            else:
                x -= 1
                new_val = a[x] + y

                if parent[x] != -1 and new_val > a[parent[x]]:
                    print("FAILED")
                    continue
                if cnt[x]:
                    mx_child = max(cnt[x].keys())
                else:
                    mx_child = 0
                if new_val < mx_child:
                    print("FAILED")
                    continue

                # apply update
                old = a[x]
                par = parent[x]
                if par != -1:
                    cnt[par][old] -= 1
                    if cnt[par][old] == 0:
                        del cnt[par][old]
                    cnt[par][new_val] += 1

                a[x] = new_val
                print("SUCCESS")

solve()
```バイナリリフティングテーブル`up`高速上向きジャンプのために祖先をエンコードします。 クエリ関数の重要な考え方は、値がまだしきい値を下回っている先祖のみにジャンプするということです。 値はパスに沿って単調であるため、これにより最初の有効なノードをスキップしないことが保証されます。 

更新のために、各ノードはその子の値のカウンターを維持します。 これにより、子の最大値のチェックが簡単になり、変更が成功した後の更新は変更されたノードの親のみに影響します。 

実装の微妙な詳細の 1 つは、子の最大値が明示的に維持されるのではなくカウンターから導出されるということです。 子の数が全体として十分に少なく、更新が全体的に対数のままであるため、これは許容できます。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、更新されるノードがルートである場合です。 この場合、子の制約のみが問題になります。 ルートには親がないため、増加はその子に対してのみチェックされ、減少は依然として最大の子より上位に留まる必要があります。 

もう 1 つのエッジ ケースは、ノードに子がない場合です。 その後、子の制約は完全に消え、親の制約のみが関連します。 これにより、多くの場合、内部ノードでは危険と思われる更新を受け入れることになります。 

最後の微妙なケースは、開始ノードがすでにしきい値を満たしている場合、クエリの動作で発生します。 登ると最初の有効なノードを通過して正解をスキップする可能性があるため、アルゴリズムは登ろうとせずにすぐに戻る必要があります。
