 ## 解決策
 ## 問題の理解

 黄色、赤、青の 3 種類のチケットが渡されます。 これらのチケットは、厳密な階層内で上位に変換できます。 青チケット10枚で赤チケット1枚、赤チケット10枚で黄チケット1枚と交換できます。 最後に、黄色のチケット 10 枚で 1 つの報酬と交換できます。 

このプロセスは完全に決定的です。変換では常に 10 進数の単位で値が保持されますが、階層内では上方向にしか移動できないため、方向が重要になります。 タスクは、黄色、赤、青のチケットの初期カウントから開始し、任意の変換シーケンスを適用した場合に、最終的に獲得できる報酬の数を計算することです。 

この制約では、3 つの値のそれぞれを 2 × 10^9 まで大きくできるため、どのソリューションもテスト ケースごとに一定時間で実行する必要があります。 変換を 1 つずつ繰り返し適用するシミュレーションは、最悪の場合、非常に遅くなります。変換に対する単純なループには最大で数十億のステップが必要になる可能性があるためです。 

素朴な考え方による微妙な失敗例は、キャリーの伝播を考慮せずに、可能な場合にのみ一方向に貪欲に変換すると仮定することです。 たとえば、多数の青いチケットから始めて、不注意に実装すると、一度に 1 ユニットずつ青から赤、次に赤から黄色、そして黄色から報酬への変換が繰り返され、終了するずっと前にタイムアウトになってしまう可能性があります。 

もう 1 つの概念的な落とし穴は、キャリーを完全に伝播せずに、青から赤、または赤から黄色に変換した後、早期に停止することです。 コンバージョンはカスケードするため、部分的な正規化では最終的な黄色のチケットの数、つまり特典の数が過小評価される可能性があります。 

## アプローチ

 ブルートフォースアプローチは、交換ルールを直接シミュレートすることです。 青チケット 10 枚のグループを赤チケットに変換し、次に赤チケット 10 枚のグループを黄色チケットに変換し、最後に黄色チケット 10 枚のグループを報酬に変換することを繰り返します。 変換ごとに 1 つのカテゴリが減少し、別のカテゴリが増加します。これらの操作は、変更ができなくなるまで適用され続けます。 

このアプローチはルールを正確に反映しているため、正しいです。 ただし、その弱点は、すべての変換でカウントが局所的に 10 分の 1 しか減らないという事実にあり、値が青いチケットに集中している異常なケースでは、システムが安定するまでに非常に多くの回数の削減を繰り返す必要がある場合があります。 個々のステップは単純ですが、ステップの合計数は入力の大きさに比例して増加する可能性があるため、2 × 10^9 までの値では実行できなくなります。 

重要な観察は、このシステムが本質的に 3 桁の 10 進数の位置番号システムであるということです。 青いチケットは基本 10 の 3 階層に配置されたユニットを表し、赤は 10 の層を表し、黄色は 100 の層を表します。 すべての完全な正規化は、状態全体を単一の整数値に変換し、10 で繰り返し除算することに対応します。 転送を段階的にシミュレートする代わりに、青と赤の寄付をすべて引き継いだ後に有効な黄色のチケットが何枚存在するかを直接計算できます。 

これにより、問題は単純な算術キャリー伝播に帰着します。

 ## アルゴリズムのチュートリアル

 青切符を最小単位、赤を青切符10枚、黄を赤切符10枚と解釈します。 まずすべてを同数の黄色のチケットに変換し、次にそれらの黄色のチケットが生み出す報酬の数を数えます。

1. 10 による整数除算を使用して青チケットを赤チケットに変換します。商は赤チケットに寄与し、余りは残りの青チケットとして残ります。 残りは完全なレッドチケットを形成できないため、より高いコンバージョンには無関係です。 
2. 青変換で新しく作成した赤チケットを既存の赤チケットに追加します。 
3. 10 による整数除算を使用して、赤いチケットの合計を黄色のチケットに変換します。ここでも、残りの赤いチケットは完全な黄色のチケットを形成できないため、それ以上寄与しません。 
4. 赤の変換で新しく作成した黄色のチケットを既存の黄色のチケットに追加します。 
5. 10 による整数除算を使用して、黄色のチケットの合計を報酬に変換します。これにより、答えが直接得られます。 

各ステージは 10 進数システムのキャリー操作であり、下位レベルの変換が上方に伝播するため、順序が重要になります。 

これが機能する理由は不変条件に基づいています。つまり、各ステップの後、下位レベルから次のレベルへの可能なすべての変換が完全に適用されています。 青チケットの処理が完了すると、未使用のまま残された 10 枚の青チケットのグループはなくなります。 赤チケットの処理後、未使用のまま残っている 10 枚の赤チケットのグループはありません。 各変換では合計値が 10 進数の加重単位で保持されるため、各レベルを貪欲に折りたたんでも最上位レベルの最終的な商を変更することはできません。 システムは、算術加算におけるキャリー正規化を繰り返すように動作します。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

y = int(input())
r = int(input())
b = int(input())

# convert blue -> red
r += b // 10
b = b % 10

# convert red -> yellow
y += r // 10
r = r % 10

# convert yellow -> rewards
print(y // 10)
```実装はキャリー伝播構造に直接続きます。 各変換ステップでは、整数の除算とモジュロを使用して、10 個の完全なグループを残りから分離します。 順序は重要です。赤が黄色に処理される前に、青が赤に処理されなければなりません。そうしないと、より深いレベルからの寄与が失われることになります。 

よくある間違いは、中間更新を行わずに 1 つの式ですべてを折りたたもうとすることです。 可能ではありますが、キャリーを追跡するとエラーが発生しやすくなります。 3 つのレベルを明示的に保つことで、正確性が保証され、伝播構造が明確になります。

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    import sys
    input = sys.stdin.readline

    y = int(input())
    r = int(input())
    b = int(input())

    r += b // 10
    b %= 10
    y += r // 10
    r %= 10
    return str(y // 10)

# provided sample
assert run("9\n9\n10\n") == "1"

# minimum case
assert run("0\n0\n0\n") == "0"

# only blue cascade
assert run("0\n0\n100\n") == "1"

# only red case
assert run("0\n100\n0\n") == "1"

# boundary mixed
assert run("9\n9\n9\n") == "1"
```| テスト入力 | 期待される出力 | 検証内容 |

 | 0 0 0 | 0 | ゼロ処理 |

 ## 特殊なケース

 エッジ ケースの 1 つは、すべての値がゼロの場合です。 このアルゴリズムは変換を実行せず、整数除算では正しくゼロの報酬が得られます。 状態は全体を通して安定したままです。 

もう 1 つのエッジ ケースは、入力など、青いチケットのみが存在する場合です。`0 0 100`。 青は赤に変換されます`100 // 10 = 10`、その後、赤は黄色に変換されます`10 // 10 = 1`、黄色は 1 のみであるため、最終的に報酬は生成されません。各ステージでは反復を必要とせずに整数の除算が完全に適用されるため、アルゴリズムはこれを正しく処理します。 

3 番目のケースは、値がコンバージョンしきい値をわずかに下回る場合です。`9 9 9`。 青は完全な赤チケットを形成しないため、残りとして破棄されます。 赤になる`9 + 0 = 9`、これも黄色には変換されません。 黄色は 9 のままで、報酬のしきい値に達しないため、出力はゼロになります。
