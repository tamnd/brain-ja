 ## 解決策
 ## 問題の理解

 このタスクは意図的に最小限に抑えられています。プログラムは標準入力で単一のトークンを受け取り、ブタの固定 ASCII 描画で応答する必要があります。 必要な変換、解析ロジック、および構造に関する計算がないため、入力は一般的な文字列処理の問題ではありません。 代わりに、入力はトリガーとして機能し、出力は常に同じ複数行のアートワークになります。 

アルゴリズムの観点から見ると、ここでの「データ」は存在する以上に本質的に無関係です。 実際の要件は、出力フォーマット中に破損しやすいスペース、バックスラッシュ、句読点などの事前定義されたテキスト ブロックを正しく再現することです。 

制約プロファイルは、競技プログラミングの意味では自明です。 最も標準的な制限である 1 秒と 256 メガバイトを想定したとしても、ソリューションはそれらの制限に意味のある形で近づくことはできません。 唯一の本当のリスクは、生の文字列を処理する際の実装エラー、特に Python でのバックスラッシュのエスケープと正確な空白の保持です。 

エッジケースはアルゴリズムの分岐に関するものではなく、出力の忠実度に関するものです。 いくつかの具体的な故障モードがこれを示しています。 

ソリューションがバックスラッシュを慎重にエスケープせずに通常の文字列連結で ASCII アートを構築しようとすると、次のような行が表示されます。`(\____/)`または`/ @__@ \`文字が失われるか、無効なエスケープ シーケンスが生成される可能性があります。 また、単純な実装では、書式設定関数を使用するときに末尾のスペースを誤って削除してしまう可能性があり、ロジックが正しい場合でも描画が微妙に破損する可能性があります。 

開発者が入力文字列に基づいて出力を「計算」しようとすると、別の障害モードが発生します。 入力は常に正しいので、`"pig"`、不必要な条件ロジックがあると、正確性の値が追加されずに、不一致の動作が発生する可能性が高くなります。 

## アプローチ

 タスクのブルート フォース解釈では、入力文字列を読み取り、それが予期されるトリガー ワードと一致することを確認し、関連する ASCII アートを 1 行ずつ出力します。 出力に変動はないので、これで十分です。 実行される作業は、出力テキストのサイズに線形であり、一定です。 

より複雑なブルート フォースの試みには、ASCII アートを文字列のリストとして保存し、それを反復処理して各行を出力することが含まれる場合があります。 これは依然として正しいですが、複雑さや動作を変えることなく不必要な構造を導入します。 重要な観察は、出力を印刷する必要があるかどうかを検証する以上に、入力が出力に影響を与えないということです。 

最適な解決策は、すべてを 1 つの定数時間の決定にまとめます。つまり、入力コンテンツを無視し、事前定義されたブロックを直接出力します。 問題の構造により、有効な出力が 1 つだけ存在し、入力の変化に基づく条件分岐がないため、これが可能になります。

 ## アルゴリズムのチュートリアル

 1. 値が結果に影響しない場合でも、標準入力から入力文字列を読み取ります。 これは、問題の入力コントラクトを満たすためだけです。 
2. 出力仕様の要求どおりに、ブタの ASCII アートを表す固定の複数行文字列を準備します。 
3. 文字列を変更せずに標準出力に出力します。 

重要な考え方は、問題は単一の有効な出力状態を定義するため、分岐は必要ないということです。 

### なぜ効果があるのか

 正しさは、問題が有効な入力から単一の固定出力への決定論的なマッピングを定義しているという事実から来ています。 すべての有効な入力は事実上同一であるため、出力関数は一定です。 アルゴリズムは入力コンテンツを検査する必要はありません。 必要なのは、必要な文字列の忠実な再現を保証することだけです。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def solve():
    _ = input().strip()

    art = r"""(\____/)
 / @__@ \
( (oo) )
‘-.~~.-’
 /
 \
 @/
 \_
 (/ /
 \ \)
WW‘----’WW
"""
    sys.stdout.write(art)

if __name__ == "__main__":
    solve()
```入力は出力をトリガーすること以外には無関係であるため、実装は入力を読み取って破棄します。 ASCII アートは生の複数行文字列として保存されるため、バックスラッシュは手動エスケープを必要とせずに保持されます。 これにより、次のようなシーケンスが発生する一般的な Python の落とし穴が回避されます。`\_`または`\ `そうしないと、エスケープ シーケンスとして解釈される可能性があります。 

出力は次を使用して直接書き込まれます。`sys.stdout.write`環境によっては、印刷時に発生する可能性のある誤ったフォーマットや追加の改行挿入を避けるためです。

 ## 特殊なケース

 微妙なエッジ ケースの 1 つは、ASCII アートにおける末尾の空白の保持です。 行の先頭または末尾のスペースが失われている場合、プログラムが論理的に「正しい」場合でも、ブタの形状は視覚的に不正確になります。 生の文字列アプローチでは、書式設定をそのまま保持することで、これを完全に回避します。 

もう 1 つの特殊なケースは、バックスラッシュの誤ったエスケープ解釈です。 たとえば、書くこと`/ \`生の文字列がないと、Python が誤って解釈する可能性があります`\`エスケープ接頭辞として。 選択した表現により、各バックスラッシュがリテラル文字として扱われることが保証されます。 

最後に、実装によっては、入力が次と等しい場合にのみ条件付きで出力しようとする場合があります。`"pig"`。 これは指定された制約の下で機能しますが、入力の正確さに対する不必要な依存が生じます。 この問題では単一の有効な入力形式が保証されているため、最も安全なアプローチは無条件の出力であり、これにより一連の障害シナリオ全体が削除されます。
