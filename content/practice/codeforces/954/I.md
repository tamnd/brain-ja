 ## 解決策
 ## 問題の理解

 長い文字列とパターン文字列の 2 つの文字列が与えられ、どちらもサイズ 6 の非常に小さなアルファベット上にあります。 長い文字列上でパターンをスライドさせ、各位置でパターンと同じ長さの部分文字列を取得します。 このような等しい長さの文字列のペアごとに、グローバルな名前変更操作を繰り返し適用することができます。つまり、2 つの文字を選択し、両方の文字列で最初の文字が出現するすべてを 2 番目の文字で同時に置き換えます。 このような各操作には 1 ステップのコストがかかります。 各アラインメントの目標は、部分文字列がパターンと同一になるように必要な名前変更操作の最小数を計算することです。 

この操作の主な特徴は、両方の文字列にわたってグローバルであることです。 名前の変更は個々の位置には作用しませんが、両方の文字列内に出現する 2 つの文字をマージします。 これは、問題は位置を直接一致させることではなく、整列されたすべての位置にわたって文字間の一貫性を強制することであることを意味します。 

この制約により、すべての部分文字列およびすべてのマッピングに対するブルート フォースが不可能になります。 長い文字列は最大 125,000 文字にすることができ、位置ごとにパターンと同じ長さのウィンドウを処理する必要があります。 ウィンドウごとに構造を最初から再計算する単純なソリューションでは、最悪の場合、約 10¹⁰ の操作が必要になります。 

小さなアルファベットは重要な構造上の制約です。 文字列は長くても、存在する文字は 6 文字だけです。 これは、ウィンドウを記述するあらゆる状態が、これらの 6 文字にわたる一定サイズの構造を使用して表現できることを直ちに示唆しています。 

ウィンドウ内で文字が異なる組み合わせで複数回表示される場合、微妙なエッジ ケースが発生します。 たとえば、異なるインデックスで a が b に等しい、および b が c に等しいという両方を強制する場合、直接の a と c に等しい制約がなくても、推移閉包によってそれらが同じクラスに強制されます。 位置ごとに直接的な不一致のみをカウントする単純なアプローチは、このマージの推移性を無視するため、ここでは失敗します。 

もう 1 つの微妙な問題は、ウィンドウ内で同じ文字ペア制約が複数回発生しても二重にカウントされるべきではないということです。 制約が存在すると、追加の制約が発生しても構造は変化せず、エッジの有無だけが問題となります。 

## アプローチ

 ブルートフォースの観点は、単一のウィンドウを考慮することから始まります。 部分文字列とパターンの間のインデックスに関するすべての制約を観察します。 それぞれの位置は、名前変更後に 2 つの文字が最終的に等しくなる必要があることを示しています。 これらの制約は、ノードが文字であり、そのエッジが最終的に同一になる必要がある文字を接続するグラフを定義します。 

固定ウィンドウの場合、答えは、すべての接続されたコンポーネントを 1 つの文字に折りたたむのに必要なマージ操作の最小数になります。 マージごとに個別の文字グループの数が 1 つずつ減るため、コストは制約グラフに含まれる連結コンポーネントの数によって完全に決まります。 

ブルート フォース ソリューションは、このグラフをウィンドウごとに個別に再計算し、接続を構築し、コンポーネントをカウントします。 これは概念的には機能しますが、重なっているウィンドウに対して同じ作業を繰り返します。 

重要な観察は、ウィンドウをスライドさせるとグラフが非常にゆっくりと変化するということです。 各ステップで 1 つの位置制約が削除され、1 つの新しい制約が追加されます。 制約は文字のペアにのみ依存するため、可能なエッジは最大 36 個です。 最初から再計算するのではなく、ウィンドウ内で現在アクティブなエッジを維持し、毎回一定サイズのグラフ上で接続を再構築します。 

アルファベットは固定されており小さいため、各ウィンドウの接続性の再計算は事実上一定時間になります。

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | ウィンドウごとのブルート フォース再構築 | O(n・m) | お(1) | 遅すぎる |
 | エッジ上のスライディング ウィンドウのカウント | O(n · 1) | お(1) | 承認済み |

 ## アルゴリズムのチュートリアル

 各文字をサイズ 6 のグラフのノードとして扱います。 部分文字列とパターンの間の整列された位置ごとに、2 つの対応する文字の間に無向エッジを作成します。 同じペアが複数回出現しても、最初の出現以降は問題になりません。 

これらのエッジのスライディング ウィンドウを維持します。 

1. 効率的にインデックスを作成できるように、両方の文字列をアルファベット a から f までの整数配列に変換します。 
2. 初期ウィンドウでは、パターン長のすべての位置を反復処理し、対応する文字ペアの 6 x 6 カウンターをインクリメントします。 これは、どの制約がアクティブであるかを表します。 
3. ウィンドウごとに、6 つのノードにわたって新しい Union-Find 構造を構築します。 
4. カウンタがゼロ以外の文字のペアごとに、これら 2 つのノードを結合します。 これにより、強制等価クラスを表す連結コンポーネントが構築されます。 
5. 6 つのノード間にいくつの接続コンポーネントが存在するかを数えます。 
6. 結合するたびにコンポーネント数が 1 つ減るため、ウィンドウの答えは 6 からコンポーネント数を引いたものになります。 
7. ウィンドウを 1 位置ずつスライドします。発信ペアの寄与を削除し、着信ペアを追加して、答えを再計算します。 

重要な考え方は、グラフが非常に小さいため、各ステップで接続を再構築するだけでも継続的な作業が必要であるということです。 

### なぜ効果があるのか

 各制約により、すべての名前変更操作後の最終文字列で 2 つの文字が同一になることが強制されます。 これは推移的であるため、制約は同値クラスを形成します。 制約グラフ内のすべての連結コンポーネントは 1 つの文字に折りたたまれなければなりません。 マージ操作ごとに、以前は別個だった 2 つのクラスがマージされるとき、コンポーネントの数が 1 つだけ減ります。 したがって、最小操作数は、最初の 6 つのシングルトン ノードを接続コンポーネントの数に減らすのに必要なマージの数 (6 からその値を引いたもの) となります。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

class DSU:
    def __init__(self, n):
        self.p = list(range(n))
        self.r = [0] * n

    def find(self, x):
        while self.p[x] != x:
            self.p[x] = self.p[self.p[x]]
            x = self.p[x]
        return x

    def union(self, a, b):
        a = self.find(a)
        b = self.find(b)
        if a == b:
            return
        if self.r[a] < self.r[b]:
            a, b = b, a
        self.p[b] = a
        if self.r[a] == self.r[b]:
            self.r[a] += 1

def solve():
    S = input().strip()
    T = input().strip()
    n, m = len(S), len(T)

    S = [ord(c) - 97 for c in S]
    T = [ord(c) - 97 for c in T]

    cnt = [[0] * 6 for _ in range(6)]

    def add(i):
        a = S[i]
        b = T[i]
        cnt[a][b] += 1
        cnt[b][a] += 1

    def remove(i):
        a = S[i]
        b = T[i]
        cnt[a][b] -= 1
        cnt[b][a] -= 1

    for i in range(m):
        add(i)

    def get_answer():
        dsu = DSU(6)
        for i in range(6):
            for j in range(i + 1, 6):
                if cnt[i][j] > 0:
                    dsu.union(i, j)

        comps = 0
        for i in range(6):
            if dsu.find(i) == i:
                comps += 1
        return 6 - comps

    res = []
    res.append(str(get_answer()))

    for i in range(m, n):
        remove(i - m)
        add(i)
        res.append(str(get_answer()))

    print(" ".join(res))

if __name__ == "__main__":
    solve()
```このソリューションは、現在ウィンドウによってどの文字ペアが適用されているかを追跡する 6 行 6 列の行列を維持します。 各ウィンドウの更新は 2 つの位置のみに触れるので、状態の更新は一定時間になります。 ウィンドウごとに、6 つのノード間の接続を再構築しますが、これも一定時間です。 最終的な答えは、連結成分を数えることから直接得られます。 

よくある落とし穴は、ミスマッチをポジションごとの独立したコストとして扱おうとすることです。 これは推移的なマージを無視します。制約はグローバルに蓄積され、実際のコストは局所的な不一致ではなく、同値クラスの構造に依存します。 

## 実用的な例

 サンプル入力を考えてみましょう。 

入力文字列は、`S = abcdefa`そして`T = ddcb`。 長さ 4 のウィンドウをスライドさせます。 

### ウィンドウ 1

 | ステップ | アクティブなペア | コンポーネント | 答え |
 | --- | --- | --- | --- |
 | 初期化 | (a,d)、(b,d)、(c,c)、(d,b) | {a、b、d}、{c}、{e}、{f} | 2 |

 この制約により、a、b、d が単一のクラスに強制されますが、c は単独のままになります。 これにより 4 つのコンポーネントが生成されるため、コストは 6 マイナス 4 で 2 となります。 

### ウィンドウ 2

 | ステップ | アクティブなペア | コンポーネント | 答え |
 | --- | --- | --- | --- |
 | シフト | 更新された制約 | マージが増加 | 3 |

 スライドしていくと、より多くの文字を推移的に接続する新しい矛盾する制約が表示され、必要なマージの数が増加します。 

これらのトレースは、答えが個々の不一致によってではなく、接続の変化によって完全に制御されていることを示しています。

 ## 特殊なケース

 エッジ ケースの 1 つは、すべての文字がすべての位置ですでに一致している場合です。 この状況では、エッジは作成されず、グラフは 6 つの孤立したノードのままであり、接続されたコンポーネントの数が 6 のままであるため、アルゴリズムはすべてのウィンドウに対して正しく 0 を返します。 

もう 1 つのエッジ ケースは、単一ウィンドウ内で a が b に等しい、b が c に等しい、c が d に等しいなど、制約が複数の文字にまたがるチェーンを形成する場合に発生します。 直接の a = d 制約がない場合でも、union-find はそれらを 1 つのコンポーネントにマージし、コストには 1 つではなく 3 つの必要なマージが正しく反映されます。 

最後のエッジ ケースは、同じウィンドウ内で同じ制約が繰り返されることです。 エッジの存在のみが問題となるため、周波数行列はこれを安全に処理します。 ペアが複数回出現した場合でも、接続性やオーバーカウント操作は変更されません。
