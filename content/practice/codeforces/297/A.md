 ## 解決策
 ## 問題の理解

 2 つのバイナリ文字列が与えられ、動的に尾が伸びるスライディング ウィンドウのように動作する 2 つの操作を使用して最初の文字列を変換できます。 

最初の操作では、文字列内の現在の 1 の数のパリティによって決定される単一ビットを追加します。 2 番目の操作では、左端の文字が削除され、実質的にウィンドウが右にシフトされます。 最初の文字列から始めて、これらの一連の操作の後でターゲット文字列に正確に到達できるかどうかを知りたいと考えています。 

追加されるビットは任意ではないため、これは単純な文字列書き換えの問題ではありません。 これは、1 のパリティを通じて現在の文字列全体に依存するため、グローバルな依存関係が生じます。 一方、削除により、文字列は成長し続けるシーケンス上で移動するウィンドウのように動作します。 

両方の文字列の長さが最大 ​​1000 であるという制約は、考えられるすべての操作シーケンスをシミュレートできないことを意味します。 各追加の決定は現在のパリティに依存し、削除は任意の点で発生する可能性があるため、状態空間は指数関数的に増加します。 州に対する単純な BFS は、実行可能な制限を超えてすぐに爆発します。 

最初の文字列がすでにターゲットと一致している場合、微妙なエッジ ケースが発生しますが、中間操作により、有効な構成に戻る前に一時的に構造が壊れる可能性があります。 もう 1 つの厄介な状況は、1 のパリティが将来追加されるビットを制限する形で反転し、ローカルで到達可能に見えても特定のサフィックスが不可能になる場合に発生します。 

## アプローチ

 ブルート フォース ビューは、各文字列をグラフ内のノードとして扱います。エッジはパリティの追加または最初の文字の削除に対応します。 これは、到達可能なすべての構成を調査するため、原則的には正しいです。 ただし、各状態はさらに最大 2 つの状態を生成する可能性があり、切り捨てが優勢になり始める前に文字列が無限に増大する可能性があります。 長さに上限を設けたとしても、長さ 1000 の個別のバイナリ文字列の数は$2^{1000}$、探索が不可能になります。 

重要な観察は、削除がシーケンス上でスライディング ウィンドウのように機能し、すべての新しい文字がそれまでのプレフィックスのパリティによって決定されることです。 文字列全体の変換という観点から考えるのではなく、プロセスを無限のバイナリ シーケンスを生成するものとして再解釈します。次の各ビットはパリティのみに依存し、文字列操作はこのシーケンスの連続セグメントの選択に対応します。 

このようにプロセスを理解すると、この問題は、ターゲット文字列が初期状態から開始して有効な生成されたシーケンスの部分文字列として表示されるかどうかを確認することと同等になります。 残る唯一の問題は、初期状態が初期パリティに寄与し、それがその後に生成されるすべてのビットに影響を与えることです。 

この問題は、可能なすべてのアライメントをカバーするのに十分な順方向のシミュレーションを行い、現在の文字列ウィンドウとパリティ状態の両方を追跡することで解決します。 パリティは 2 つの値のみであるため、反復中に効率的にパリティを維持できます。 

| アプローチ | 時間計算量 | 空間の複雑さ | 評決 |
 | --- | --- | --- | --- |
 | 文字列に対するブルート フォース BFS | 指数 | 指数 | 遅すぎる |
 | パリティ + 到達可能なシーケンスのシミュレーション | O(n²) | O(n) | 承認済み |

 ## アルゴリズムのチュートリアル

 1. 開始文字列内の 1 の数の初期パリティを計算します。 このパリティは、最初に追加されたビットがどのように動作するかを完全に決定します。 
2. 追加された各文字が現在のパリティによって決定され、追加後にパリティが更新されるシーケンスを生成するプロセスを概念化します。 これにより、開始状態を修正すると、プロセスが決定的になることが保証されます。 
3. すべての操作を調べる代わりに、ターゲット文字列を含む可能性がある十分な長さのシーケンスを生成するのに十分なステップをシミュレートします。 削除はウィンドウをシフトするだけなので、ターゲットの有効な構造は連続したセグメントとして現れる必要があります。 
4. 生成されたシーケンスに対してスライディング ウィンドウを維持し、各ステップでターゲット文字列と比較します。 
5. いずれかの時点で現在のウィンドウがターゲットと一致する場合、変換は可能であると結論付けます。 
6. 安全限界 (ターゲットの長さの 2 倍と初期の長さの合計で十分) まで一致が見つからずにシミュレーションが終了した場合は、不可能であると結論付けます。 

### なぜ効果があるのか

 重要な不変条件は、すべての有効な演算シーケンスが、初期パリティ状態から生成される一意に決定される無限シーケンス内の開始位置の選択に対応するということです。 削除はこの開始位置を前方に移動するだけですが、追加はパリティに従って一貫してシーケンスを拡張します。 したがって、ターゲット文字列に到達できる場合は、生成されたシーケンスの連続した部分文字列として現れる必要があります。 このシーケンスを十分にシミュレートすることで、考えられるすべてのアライメントをカバーします。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

def build_sequence(a, limit):
    s = list(a)
    ones = sum(c == '1' for c in s)
    seq = s[:]
    
    # generate enough characters
    for _ in range(limit):
        parity = ones % 2
        seq.append(str(parity))
        if parity == 1:
            ones += 1
    return ''.join(seq)

def possible(a, b):
    n, m = len(a), len(b)
    
    # generate enough prefix
    seq = build_sequence(a, 2 * (n + m) + 5)
    
    return "YES" if b in seq else "NO"

if __name__ == "__main__":
    a = input().strip()
    b = input().strip()
    print(possible(a, b))
```この実装では、パリティを最初から再計算するのではなく、1 の数を明示的に追跡するため、各拡張子は O(1) に保たれます。 生成されたシーケンスは、ターゲットのサイズに比例した安全な長さに制限され、ターゲットの埋め込みが存在する場合には確実にキャプチャされます。 

有効な削除シーケンスは、この生成されたシーケンス内の連続するウィンドウの選択に対応するため、部分文字列のチェックで十分です。

## 複雑さの分析

 | 測定 | 複雑さ | 説明 |
 | --- | --- | --- |
 | 時間 | O(n²) | ターゲット サイズに比例した長さのシーケンスを生成し、部分文字列チェックを実行します。 
| スペース | O(n) | 生成されたシーケンスを保存します |

 境界は十分小さいので、$n \le 1000$、この規模の文字列操作は Python で効率的です。 

## テストケース```python
import sys, io

def run(inp: str) -> str:
    sys.stdin = io.StringIO(inp)
    
    a = input().strip()
    b = input().strip()

    def build(a, limit):
        ones = sum(c == '1' for c in a)
        seq = a
        for _ in range(limit):
            p = ones % 2
            seq += str(p)
            if p == 1:
                ones += 1
        return seq

    seq = build(a, 2000)
    return "YES" if b in seq else "NO"

assert run("01011\n0110\n") == "YES", "sample 1"

assert run("1\n1\n") == "YES", "same string"
assert run("0\n1\n") == "NO", "cannot create ones from zero parity"
assert run("1\n0\n") == "YES", "parity flip allows zero"
assert run("01\n111\n") == "NO", "impossible long pattern"
assert run("10\n01\n") == "YES", "short reachable swap pattern"
```| テスト入力 | 期待される出力 | 検証内容 |
 | --- | --- | --- |
 | 1 / 1 | はい | 同一の文字列 |
 | 0 / 1 | いいえ | パリティ制約により作成が妨げられる |
 | 1/0 | はい | パリティ フリップはゼロを生成する可能性があります。 
| 01 / 111 | いいえ | 到達不可能な長いラン |
 | 10 / 01 | はい | 小さな建設的な到達可能性 |

 ## 特殊なケース

 エッジケースの 1 つは、初期文字列がすでにターゲットと等しい場合です。 部分文字列の一致にはオフセット 0 が含まれるため、アルゴリズムは引き続きシーケンスを生成し、最初の位置での一致をすぐに検出します。 

最初の文字列に 1 がない場合、別のエッジ ケースが発生します。 この場合、パリティは 1 が導入されるまで常に 0 です。これは、構造的な変更が発生する前に、生成されたシーケンスに強制的に 0 が長く続くことを意味します。 パリティが明示的に追跡され、シーケンスが強制的な決定論を反映しているため、シミュレーションはこれを正しく処理します。 

最後のエッジ ケースは、数回のパリティ フリップの後にのみターゲットが表示される場合です。 追加するたびにパリティが反転される可能性があるため、生成されたシーケンスは、すべての可能な操作シーケンスと一貫した方法で自然に交互になり、部分文字列チェックはターゲットの遅延した出現を捕捉します。
