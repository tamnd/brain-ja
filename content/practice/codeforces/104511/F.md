 ## 解決策
 ## 問題の理解

 いくつかの種類のコーヒーが提供されますが、最終的に価値があるのはタイプ1だけです。 このプロセスには 2 つの段階があります。 

まずはスミカさんからイニシャルコーヒーをいただきます。 彼女は、マイナスでない実際の量のコーヒーを提供できますが、`1`バイナリ文字列で。 唯一の制限は、私たちが彼女から受け取る総量が超えてはいけないということです`v`。 これは、一定の規模の予算を配分できることを意味します`v`コーヒーの種類のサブセット全体にわたって。 

その後、繰り返し取引を行うことができます。 各取引には 2 つの入力コーヒー タイプが含まれ、1 つの出力タイプが生成されます。 取引は係数によって記述されます: スケールのある取引を実行するには`k`、私たちは与えなければなりません`k * a`1種類のユニットと`k * b`別のタイプのユニットを受け取ります`k`3番目のタイプのユニット。 値`k`は負でない実数であるため、すべての取引は完全に線形であり、継続的にスケーリングできます。 

目標は、このような一連の取引の後に最終的にどれだけのタイプ 1 のコーヒーを入手できるかを最大化することです。 

重要な構造的制約は次のとおりです。`n`は最大 50 ですが、取引数は最大 1000 です。これは、ソリューションがすべての取引に対して繰り返し緩和できることは可能ですが、連続フローをシミュレートしたり、取引シーケンスに対して組み合わせ検索を試みたりすることはできないことをすぐに示唆しています。 実数値スケーリングの存在は、問題が離散的ではなく本質的に線形であることを強く示唆しています。 

微妙なエッジケースは、Sumika が複数の可能な開始タイプを提供しているという事実から生じます。 すべてを一定の割合で摂取する必要があるわけではありません。 総予算の任意の配分を選択できます`v`。 もう 1 つのエッジ ケースは、トレードで、後で他のトレードで役立つ中間型も生成される可能性があることです。これは、単純な 1 ステップの変換では不十分であることを意味します。 

## アプローチ

 直接シミュレーションでは、すべての種類のコーヒーの数量を追跡し、任意の順序で取引を繰り返し適用しようとします。 問題は、取引は継続的であり、無限に多くの方法で構成できるため、単純な状態のシミュレーションではすぐに管理できなくなることです。 

代わりに、問題を線形変換コストのシステムとして再解釈します。 それぞれのコーヒーの種類には「価格」があると考えてください。これは、その種類のコーヒー 1 個を生産するのにどれくらいのスミカ予算が必要かを意味します。 各タイプの生成にかかる最小コストがわかっている場合、最良の戦略は、単にタイプ 1 を生成する最も安価な方法にすべての予算を費やすことです。 

最初は、Sumika から直接取得できるすべてのソース タイプのコストは 1 ユニットあたり 1 です。これは、そのタイプの 1 ユニットを取得するのに 1 ユニットの予算を費やすことができるためです。 他のタイプはすべて不可能として開始されます。 

次に、取引を考えてみましょう。 1種類のユニットを生産できれば`x`実費で`cost[x]`と 1 つのタイプのユニット`y`実費で`cost[y]`、その後、生産します`k * a`そして`k * b`費用`k * (a * cost[x] + b * cost[y])`、そしてそれは得ます`k`型の単位`z`。 したがって、タイプ単位あたりの暗黙のコストは、`z`は：```
cost[z] = a * cost[x] + b * cost[y]
```これにより、各エッジが既知の 2 つのノードに依存する点を除き、最短パスと同様の緩和ルールが得られます。 以来`n`が小さい場合は、改善が得られなくなるまでこれらの緩和を繰り返し適用するだけで十分です。 

最小限のコストがすべて安定したら、答えは簡単です。`v / cost[1]`最も安価な変換チェーンを通じて予算全体をタイプ 1 に変換するためです。

 ## アルゴリズムのチュートリアル

 1. 配列を初期化する`cost`サイズの`n`。 セット`cost[i] = 1`sumika が直接タイプを提供できる場合`i`、それ以外の場合は無限大に設定します。 これは、最初はそれらのタイプのみが単価で入手可能であるという事実をモデル化します。 
2. 値が変化しなくなるまで、すべての取引で緩和を繰り返します。 各取引の最新情報`cost[z]`公式を使って`a * cost[x] + b * cost[y]`。 この値が現在より小さい場合`cost[z]`、更新してください。 
3. すべての取引を完全に通過しても改善が得られなくなるまで、緩和プロセスを続けます。 すべての更新でコストが厳密に削減されるため、プロセスは収束します。 
4. 収束後、最終的な答えを次のように計算します。`v / cost[1]`。 これは、利用可能なすべての予算をタイプ 1 の最も効率的な生産ルートに変換することを表します。 

### なぜ効果があるのか

 コストの定義は単調な不等式を形成します。 すべての取引は、達成可能なコストに対して線形制約を強制し、有効な一連の取引はこれらの制約を繰り返し適用することに対応します。 緩和プロセスでは、直接ソースから始めて、すべての貿易制約を満たす最大の固定点を下から効果的に計算します。 各更新ではコストが減少するだけであり、コストはゼロ以下に制限されるため、プロセスは各タイプの実現可能な最小限の生産コストに収束します。 タイプ 1 のコストがわかったら、その逆数で予算全体をスケーリングすると、達成可能な最大額が得られます。 

## Python ソリューション```python
import sys
input = sys.stdin.readline

INF = 10**30

def solve():
    t = int(input())
    for _ in range(t):
        n, m, v = map(int, input().split())
        s = input().strip()

        cost = [INF] * n
        for i, ch in enumerate(s):
            if ch == '1':
                cost[i] = 1.0

        edges = []
        for _ in range(m):
            a, x, b, y, c, z = map(int, input().split())
            x -= 1
            y -= 1
            z -= 1
            edges.append((a, x, b, y, z))

        changed = True
        for _ in range(n * n):
            changed = False
            for a, x, b, y, z in edges:
                if cost[x] < INF and cost[y] < INF:
                    val = a * cost[x] + b * cost[y]
                    if val < cost[z]:
                        cost[z] = val
                        changed = True
            if not changed:
                break

        if cost[0] >= INF / 2:
            print(0.0)
        else:
            print(v / cost[0])

if __name__ == "__main__":
    solve()
```この実装は、問題の緩和的な観点を反映しています。 の`cost`配列には、各タイプの 1 つのユニットを作成するために必要な最小限の初期予算が格納されます。 コスト 1 で許可された sumika タイプのみを初期化します。 

各反復ではすべての取引をスキャンし、双線形緩和ルールを適用します。 収束チェックにより、トレードでコストが改善されない場合には早期に停止することが保証されます。 

最後に、タイプ 1 のコストが総予算を換算します。`v`達成可能な最大量まで。 

よくある落とし穴は、緩和を適用する前に、取引の両方の入力タイプにすでに有限コストが必要であることを忘れていることです。 もう 1 つは、単一のパスで十分であると想定している一方で、実際には改善は一連の取引を通じて伝播する可能性があります。 

## 実用的な例

 スミカがタイプ 2 とタイプ 3 を与え、それらをタイプ 1 に変換する取引がある小さなシステムを考えてみましょう。 

まずコストから始めます。 

| タイプ | 初期費用 |
 | --- | --- |
 | 1 | インフ |
 | 2 | 1 |
 | 3 | 1 |

 トレードを適用した後、次を使用してタイプ 1 を生成できるとします。`2 + 3`したがって、次のようになります。 

| 反復 | コスト[1] | コスト[2] | コスト[3] | 更新理由 |
 | --- | --- | --- | --- | --- |
 | 0 | インフ | 1 | 1 | 初期化 |
 | 1 | 2 + 1 = 3 | 1 | 1 | 貿易が適用されました |
 | 2 | 安定した | 1 | 1 | 収束 |

 最終的な答えは、`v / 3`。 

ここで、タイプ 4 が直接到達できないものの、役立つようになるチェーン ケースを考えてみましょう。 

| タイプ | 初期費用 |
 | --- | --- |
 | 1 | インフ |
 | 2 | 1 |
 | 3 | インフ |
 | 4 | インフ |

 トレード 1 は 2 と 2 から 3 を生成し、トレード 2 は 3 と 2 から 1 を生成します。 

| ステップ | 更新 |
 | --- | --- |
 | 1 | コスト[3]は2になります |
 | 2 | コスト[1]は3になります |
 | 3 | 安定した |

 これは、中間の生産経路がいかに重要であるか、そしてなぜ繰り返し緩和が必要であるかを示しています。

 ## 特殊なケース

 重要なエッジ ケースの 1 つは、タイプ 1 がまったく到達できない場合です。 その場合、そのコストは無限のままであり、それで割ることは無効になります。 実装ではこれを明示的にチェックし、ゼロを出力します。 

もう 1 つのケースは、Sumika が複数の使用可能な開始タイプを提供する場合です。 初期化ではそれらすべてにコスト 1 が割り当てられ、緩和では明示的な割り当てロジックを必要とせずに、それらの中から最も効率的なものが自然に選択されます。 

3 番目のケースは、長い依存関係チェーンであり、タイプ 1 はいくつかの中間改良の後にのみ到達可能になります。 緩和ループを繰り返すことで、最終的な答えが計算される前に、これらの改善が完全に伝播されます。
